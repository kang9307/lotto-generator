공유 가능한 그래프 기반 AI Memory MCP - 에이전트 영속 메모리의 새 패러다임

AI 에이전트가 장기 기억을 그래프 구조로 저장하고 MCP로 공유한다 - 왜 지금 이 방식이 부상하는가

2026-06-18 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: AI가 기억하지 못한다는 진짜 의미

AI 에이전트를 실무에 도입하고 나서 가장 먼저 맞닥뜨리는 벽은 성능이 아니다. 기억력이다. 어제 내가 설명한 프로젝트 컨텍스트를 오늘 다시 처음부터 설명해야 한다. 지난주에 확정한 결정 사항을 에이전트는 모른다. 팀원 A가 에이전트와 합의한 코딩 규칙을, 같은 코드베이스를 다루는 팀원 B의 에이전트는 공유받지 못한다. 이것은 LLM의 구조적 한계다. 무상태(stateless) 설계는 수평 확장과 재현성을 위한 의도적 선택이지만, 그 대가로 에이전트는 매번 새로 태어난다.

2026년 6월, 이 문제를 정면으로 겨냥하는 오픈소스 프로젝트 하나가 주목받고 있다. MemoryWeft는 AI 대화와 문서를 SQLite 또는 PostgreSQL에 저장하고, MCP(Model Context Protocol)를 통해 여러 에이전트가 그 기억을 공유할 수 있도록 설계된 MCP 서버다. 핵심 아이디어는 두 가지다. 첫째, 기억을 단순 텍스트가 아니라 그래프 구조로 저장한다. 둘째, 그 그래프를 MCP 공개 엔드포인트로 노출해 Claude, Gemini, Codex 같은 이질적인 에이전트들이 동일한 지식 기반을 읽고 쓴다.

이 글은 그 방향성이 왜 의미 있는지, 어떤 한계가 있는지, 그리고 2026년 AI 메모리 인프라 지형에서 이 접근이 어디에 위치하는지를 분석한다. 이전에 다룬 Supermemory AI 컨텍스트 엔진이 단일 에이전트 맥락 관리와 빠른 검색에 집중했다면, 이 글은 그래프 구조·MCP 표준·다중 에이전트 공유라는 세 축을 중심으로 다룬다.

1. LLM은 왜 기억을 잃는가 - 구조적 원인

영속 메모리가 왜 필요한지 이해하려면 LLM이 왜 망각하는지부터 봐야 한다.

1.1 무상태 설계의 역설

LLM은 설계 철학 수준에서 무상태다. 각 API 호출은 독립적인 컨텍스트 윈도를 받아 처리하고, 호출이 끝나면 중간 계산은 전부 버려진다. 이 무상태성이 있기 때문에 동일 모델을 수만 명의 사용자가 동시에 사용할 수 있고, 같은 입력은 같은 출력을 낸다(재현성). 클라우드 규모의 AI 서비스가 가능한 것은 이 무상태 구조 덕분이다.

하지만 대가가 있다. 에이전트가 사용자 선호를 학습하려 해도, 그 학습은 컨텍스트 윈도 밖으로 나가는 순간 증발한다. 긴 프로젝트에서 에이전트와 여러 의사결정을 축적해도, 다음 세션에서 에이전트는 처음으로 돌아온다. 팀이 여러 에이전트를 운용하면 각 에이전트는 서로의 결정을 모르는 채 독립적으로 움직인다. 이것이 메모리 문제의 본질이다.

1.2 컨텍스트 윈도의 착시

100만 토큰 컨텍스트 모델이 나오면서 "이제 긴 기억도 컨텍스트에 다 넣으면 된다"는 기대가 생겼다. 하지만 이 접근에는 세 가지 문제가 있다. 첫째, 매 호출마다 수십만 토큰을 입력에 붙이는 비용은 실용 한계가 빠르게 온다. 둘째, 중요한 것과 그렇지 않은 것을 구분 없이 쌓으면 검색 정밀도가 떨어진다. 셋째, 그리고 결정적으로, 컨텍스트 윈도는 세션이 끝나면 사라진다. 긴 윈도는 단기 기억의 용량을 늘렸을 뿐, 장기 기억 문제를 해결하지 않는다.

2026년 기준, AI 에이전트 메모리 분야의 주류 견해는 이렇다. 영속 메모리 레이어는 선택적 최적화가 아니라 에이전트 인프라의 하중 지지 요소다. 메모리가 없으면 에이전트는 도구에 머물고, 메모리가 있어야 협력자가 된다.

2. 그래프 메모리가 벡터보다 나은 이유

메모리 저장 방식의 첫 번째 세대는 벡터 데이터베이스였다. 대화 내용을 임베딩으로 변환해 유사도 기반으로 검색하는 방식이다. 효과적인 경우도 많지만, 구조적 한계가 있다.

2.1 벡터 저장소의 세 가지 한계

첫째, 시간 무감각이다. 벡터 데이터베이스는 타임스탬프를 검색 가중치에 반영하지 않는다. 6개월 전 결정과 어제 결정이 텍스트 유사도가 같다면 동등하게 반환된다. 에이전트가 최신 상태를 기반으로 판단해야 할 때 오래된 사실이 같은 비중으로 섞여 들어온다.

둘째, 관계 순회 불가다. 벡터 저장소는 유사한 청크의 평면 랭킹을 반환한다. "이 모듈을 마지막으로 수정한 사람이 의존하는 다른 모듈은?" 같은 다중 홉(multi-hop) 질의는 벡터로 표현할 수 없다. 관계는 텍스트 유사도가 아니라 명시적 엣지로만 표현된다.

셋째, 맥락 단절이다. 개별 청크는 서로를 참조하지 않는다. 에이전트가 "A와 B 사이에 어떤 일이 있었나"를 물을 때, 벡터 저장소는 A에 관한 청크와 B에 관한 청크를 따로 반환할 뿐, 그 관계 자체를 저장하지 않는다.

2.2 그래프 메모리가 더 나은 세 가지 이유

그래프 메모리는 엔티티(노드)와 관계(엣지)와 시간 마커를 함께 저장한다. 이 구조는 앞의 세 한계를 직접 보완한다.

첫째, 시간 추론이다. 그래프 엣지에 valid_from, valid_until, recorded_at 같은 시간 속성을 붙이면, "지난주 기준 상태"와 "현재 상태"를 명확히 구분해 질의할 수 있다. Graphiti(Zep)가 개발한 실시간 지식 그래프 프레임워크는 이 시간 추론 덕분에 LongMemEval 벤치마크에서 GPT-4o 기준 63.8%를 기록했는데, 이는 벡터 기반 Mem0의 49.0%보다 약 15포인트 높다.

둘째, 관계 순회다. 그래프에서는 "Alice가 완료한 인증 서비스" → "그 서비스를 의존하는 결제 모듈" → "결제 모듈 담당자 Bob" 같은 다중 홉 경로를 자연스럽게 질의할 수 있다. 엔티티 간 관계가 명시적 엣지로 존재하기 때문이다.

셋째, 진화하는 스키마다. MemoryWeft의 ECKG(Event-Centric Knowledge Graph) 접근처럼, 사전에 관계 유형을 정의하지 않아도 데이터가 쌓이면서 그래프가 자연스럽게 성장하는 방식이 가능하다. 이는 경직된 스키마 없이도 복잡한 도메인 지식을 누적할 수 있게 한다.

2.3 언제 벡터가 여전히 맞는가

그렇다고 그래프가 항상 우월하다는 뜻은 아니다. 비구조화된 긴 텍스트의 의미 검색, 단순 유사도 기반 리콜, 빠른 설정과 낮은 운영 복잡도가 중요한 경우에는 벡터가 여전히 실용적이다. 2026년 프로덕션 아키텍처의 주류는 단일 선택이 아니라 벡터와 그래프의 하이브리드다. 에피소딕 메모리(특정 사건 이력)에는 벡터, 시맨틱 메모리(개념·관계)에는 그래프, 작업 상태에는 별도 상태 저장소를 쓰는 3레이어 구조가 커뮤니티 표준으로 자리잡고 있다.

3. MCP로 메모리를 공유한다는 것의 의미

MemoryWeft가 단순한 메모리 저장 도구와 구분되는 핵심은 공유다. MCP를 통해 메모리를 노출하면 무엇이 달라지는가.

3.1 메모리 사일로 문제

기존 에이전트 메모리 설계의 지배적 가정은 "메모리는 단일 에이전트 또는 단일 세션에 귀속된 상태"라는 것이었다. Claude Desktop의 메모리와 Cursor의 메모리와 Gemini CLI의 메모리는 각각 분리된 사일로다. 같은 코드베이스를 다루더라도, 어제 Claude와 합의한 아키텍처 결정을 오늘 다른 도구에서 불러올 방법이 없었다.

이 사일로 문제는 단순히 불편한 것이 아니다. 복수의 에이전트를 조율하는 워크플로에서 각 에이전트가 다른 상태를 갖고 움직이면, 충돌과 중복과 비일관성이 불가피하게 발생한다.

3.2 MCP 공유 메모리의 아키텍처

MCP(Model Context Protocol)는 Anthropic이 제안한 개방형 표준으로, AI 에이전트와 외부 도구·데이터 소스 간의 인터페이스를 표준화한다. 이 표준 위에 메모리 서버를 구현하면, 어떤 MCP 호환 에이전트든 동일한 프로토콜로 메모리를 읽고 쓸 수 있다.

MemoryWeft는 이 설계를 실제로 구현해, Claude, Codex, Gemini CLI라는 세 이질적인 AI 플랫폼이 하나의 메모리 서버를 공유하는 것을 지원한다고 발표했다. 실제 의미는 이렇다. A 에이전트가 설계 결정을 그래프에 기록하면, B 에이전트가 같은 그래프를 읽어 그 결정을 맥락으로 삼아 작업을 이어갈 수 있다. 단일 지식 기반 위에서 여러 에이전트가 협력하는 구조다.

3.3 팀 협업으로의 확장

개인 사용자 수준에서도 유용하지만, MemoryWeft가 강조하는 더 큰 가치는 팀원 간 메모리 공유다. 팀의 여러 구성원이 각자의 에이전트를 사용하더라도, 공유된 MCP 메모리 서버를 통해 팀 전체의 지식 그래프를 축적하고 질의할 수 있다. A가 인프라 결정을 기록하면, B는 그 결정의 맥락 위에서 코드를 작성하고, C는 그 이력을 참조해 문서를 쓴다. 각자의 에이전트가 분리된 도구에서 움직이더라도 지식은 한 곳에 쌓인다.

이것은 에이전트 협업의 패러다임 전환을 암시한다. 에이전트는 더 이상 개인 비서가 아니라 공유 지식 기반 위에 서 있는 팀 구성원이 된다.

4. 2026년 AI 메모리 생태계 지형

MemoryWeft는 고립된 프로젝트가 아니다. 2026년에 이미 성숙 단계에 들어선 AI 에이전트 메모리 생태계의 한 지점이다.

4.1 생태계 현황

2026년 6월 기준, AI 에이전트 메모리 프레임워크는 21개 이상의 프레임워크, 20개 이상의 벡터 저장소, 그리고 관리형 클라우드·오픈소스 자체 호스팅·로컬 MCP라는 세 가지 호스팅 모델로 분화됐다. 주요 플레이어를 정리하면 이렇다.

4.2 공통 방향: 표준화와 공유

이 생태계에서 나타나는 공통 방향성은 두 가지다. 하나는 표준 프로토콜로의 수렴이다. MCP가 사실상 표준으로 자리잡으면서, 대부분의 메모리 솔루션이 MCP 호환 인터페이스를 추가하거나 MCP를 기본 인터페이스로 채택하고 있다. 다른 하나는 단일 에이전트 메모리에서 다중 에이전트 공유 메모리로의 이동이다. 개인 맞춤화에서 팀 지식 공유로 중심이 이동하고 있다.

주목할 학술 흐름도 있다. 2026년 6월 발표된 "Memory as a Service(MaaS)" 논문은 메모리를 단일 에이전트에 귀속된 상태가 아니라 서비스 지향 모듈로 추상화하는 방향을 제안한다. 이는 MemoryWeft의 공유 메모리 철학과 같은 방향이다.

4.3 프로덕션 실전에서의 고려 사항

이론적 장점과 별개로, 실제 도입에서 따져봐야 할 것이 있다. 첫째, 일관성 보장이다. 여러 에이전트가 동시에 같은 그래프를 쓰는 환경에서 쓰기 충돌을 어떻게 처리하는가. MemoryWeft는 PostgreSQL을 쓸 때 이 문제를 데이터베이스 트랜잭션으로 위임하지만, 분산 환경에서는 추가 고려가 필요하다. 둘째, 정밀도 vs. 리콜 트레이드오프다. MemoryWeft는 정밀도보다 연관성 발견(힌트 제공)을 우선한다고 명시한다. 이는 정답을 틀리더라도 단서를 주는 방향이 AI 보조 도구로서 더 유용하다는 판단이다. 이 철학이 본인 워크로드에 맞는지 검토해야 한다. 셋째, 운영 복잡도다. 로컬 SQLite로 시작하면 단순하지만, 팀 규모로 PostgreSQL 공유 서버를 운용하면 별도의 인프라 관리 부담이 따른다.

5. 그래프 기반 공유 메모리가 여는 가능성

이 방향이 실질적으로 의미 있는 이유를 세 가지 시나리오로 풀어보자.

5.1 장기 소프트웨어 프로젝트의 지식 축적

6개월짜리 소프트웨어 프로젝트를 상상해 보자. 팀은 수백 개의 아키텍처 결정을 내린다. 왜 이 라이브러리를 택했는가, 왜 저 패턴을 포기했는가, 어떤 트레이드오프를 수용했는가. 현재 이 지식은 문서에 일부 기록되고, 대부분은 개인 기억과 Slack 히스토리에 흩어진다. 신규 입사자나 외부 AI 에이전트는 이 맥락을 모른다.

그래프 기반 공유 메모리가 있다면, 이 결정들이 그래프 노드와 엣지로 누적된다. "왜 TypeScript를 택했는가" → "어떤 대안을 검토했는가" → "그 결정이 이후 어떤 변경을 촉발했는가"가 탐색 가능한 관계망이 된다. 에이전트는 이 그래프를 맥락으로 삼아 현재 변경의 역사적 배경을 파악한 채 작업한다.

5.2 다중 에이전트 워크플로의 조율

코드 리뷰 에이전트, 문서 작성 에이전트, 테스트 생성 에이전트가 분업하는 워크플로를 생각해 보자. 각 에이전트가 독립적 메모리를 갖는다면, 코드 리뷰 에이전트가 발견한 설계 문제를 문서 에이전트가 모르고, 테스트 에이전트도 모른다. 공유 그래프가 있다면 코드 리뷰 에이전트가 "이 모듈은 X 이유로 취약하다"는 노드를 쓰는 즉시, 문서 에이전트와 테스트 에이전트가 그 맥락을 이어받는다. 분업하되 지식은 공유하는 구조다.

5.3 사용자 맥락의 플랫폼 독립적 이식

개인 사용자 입장에서도 강력한 시나리오가 있다. 오늘 Claude Desktop에서 에이전트와 작업하고, 내일 Cursor로 전환하고, 모레 Gemini CLI를 써도, 공유 MCP 메모리 서버에 누적된 내 컨텍스트는 어떤 도구에서든 접근할 수 있다. 도구를 바꿀 때마다 처음부터 설명하는 반복이 사라진다. 메모리가 사용자에게 귀속되는 것이지 도구에 귀속되지 않는 구조다.

6. 한계와 냉정한 시각

장점만 보여주는 것은 부정직하다. 지금 이 방향의 한계도 직시해야 한다.

6.1 그래프 구성 품질이 전부다

그래프 메모리의 가치는 그래프를 얼마나 의미 있게 구성하느냐에 완전히 달려 있다. 에이전트가 어떤 사건을 노드로 만들고, 어떤 관계를 엣지로 연결할지를 결정하는 것이 핵심이다. 이 추출이 잘못되면 그래프는 노이즈 덩어리가 된다. ECKG처럼 스키마 없이 진화하는 접근은 유연하지만, 관계가 일관되게 표현될 보장이 없다.

6.2 보안과 프라이버시

팀 단위로 공유 메모리를 운용하면 누가 무엇을 읽고 쓸 수 있는지에 대한 접근 제어가 필수다. MemoryWeft 같은 초기 오픈소스 프로젝트가 세밀한 권한 관리를 얼마나 지원하는지는 실제 배포 전에 확인해야 한다. 공유 그래프에 민감한 비즈니스 결정이 쌓이는 경우 이 문제는 더 중요해진다.

6.3 MCP 생태계의 성숙도

MCP는 좋은 표준이지만 아직 빠르게 발전하는 표준이다. MCP 호환성을 주장하는 도구 사이에서도 세부 동작 방식의 차이가 있을 수 있다. 여러 에이전트가 실제로 단일 MCP 메모리 서버를 동시에 사용할 때의 안정성은 실제 부하 환경에서 검증이 필요하다.

7. 결론 - 에이전트 메모리 인프라의 다음 단계

2026년 6월 기준, AI 에이전트 메모리의 방향은 명확하다. 무상태 LLM 위에 영속 메모리 레이어를 씌우는 것은 선택이 아닌 필수가 됐다. 그리고 그 메모리의 저장 구조로 그래프가 벡터의 한계를 보완하는 핵심 수단으로 부상하고 있다. 여기에 MCP를 통한 공유가 더해지면, 에이전트는 개인 도구에서 공유 협력자로 도약한다.

MemoryWeft는 이 세 요소를 한 번에 구현하려는 오픈소스 시도다. 아직 초기 단계이고, 프로덕션 규모에서의 검증은 더 필요하다. 하지만 방향은 맞다. 그래프·MCP·공유라는 세 축의 조합은 2026년 에이전트 인프라의 핵심 진화 벡터다.

지금 당장 적용할 수 있는 세 가지를 꼽는다면 이렇다. 첫째, 본인 에이전트 워크플로에서 "왜 같은 맥락을 매번 다시 설명하는가"를 비용으로 측정하라. 그 비용이 크다면 메모리 레이어 투자의 근거가 된다. 둘째, Anthropic 공식 Knowledge Graph Memory MCP 서버부터 로컬에서 시험해 보라. 설정이 간단하고 그래프 메모리의 기본 동작을 확인하기에 좋다. 셋째, 팀 단위 공유가 필요하다면 MemoryWeft나 Graphiti를 PostgreSQL 백엔드로 구성해 실제 협업 시나리오에서 테스트하라. 그래프 품질과 보안 설계를 먼저 확인한 뒤 프로덕션으로 가져가는 순서가 안전하다.
