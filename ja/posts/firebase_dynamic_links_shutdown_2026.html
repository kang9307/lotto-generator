Firebase Dynamic Links 終了後 - ディープリンクを一から設計し直した移行記

ユニバーサルリンク・AASA・カカオトーク共有まで、FDLなき世界でディープリンク基盤を自前構築して学んだこと

2026年7月10日 開発・インフラ

はじめに: FDLが消えた場所で学び直したこと

2025年8月25日、GoogleはFirebase Dynamic Links(FDL)サービスを完全に終了した。page.linkサブドメインであれカスタムドメインであれ、その日以降、以前に発行されたすべてのFDLリンクは新規リクエストに対してHTTP 404を返し始めた。QRコードに印刷しておいたリンク、カカオトークやSMSで既に配布した共有リンク、マーケティングキャンペーンに埋め込んだ短縮リンクが、一夜にして死んだリンクになったということだ。2026年7月時点でもう1年近く経つが、この終了が残した宿題は依然として現在進行形だ。移行を先送りしていたチーム、FDLを取り除いたもののディファードディープリンクやカカオトーク共有のような細部を見落としたチームが、今も遅れて問題を発見している。

本人がこのテーマを改めて取り上げた理由は単純だ。FDLの終了は単に一つのサービスが消えた事件ではなく、「ディープリンクはSDKを一つ入れれば終わり」という安易な前提が崩れた事件だからだ。この記事はGeekNewsで紹介されたある開発者の自前インフラ移行の体験談をきっかけに、その体験を貫くディープリンクの基本概念と、自前構築時に実際にぶつかる問題を本人の視点で整理したものである。原文を要約するのではなく、「なぜこれが難しいのか」と「何を準備すべきか」に焦点を当てる。

1. 正確に何が壊れたのか - FDLがひそかに担っていた三つの役割

FDLがなくなったと聞くと、漠然と「短いリンクが使えなくなるんだな」程度に考えがちだ。しかし実際にはFDLは目立たない三つの役割を同時に果たしており、この三つが一斉に崩れた。

1.1 短いリンクの裏に隠れたルーティング

FDLの最も表面的な役割は、短く見栄えの良いURLを発行することだった。しかし本当の価値はその裏にあった。一つのリンクがiOSでクリックされればApp Storeかアプリへ、Androidでクリックされればプレイストアかアプリへ、デスクトップでクリックされればWebページへ - プラットフォームを自動判別して行き先を変えるルーティング層が短いリンクの裏に隠れていた。このルーティングロジック自体が失われたことが第一の破壊だ。

1.2 アプリ未インストール時のストア誘導

二つ目は、アプリがない利用者を自然にストアへ送るフォールバックだ。マーケティングの観点ではこれは思った以上に重要である。リンクをクリックしたのにアプリがないからと真っ白な画面やエラーが出れば、利用者はそのまま離脱する。FDLはこの分岐を自動で処理してくれていたが、今後はこの分岐ロジックを自分で書く必要がある。

1.3 ディファードディープリンク - インストール前のクリック文脈の引き継ぎ

三つのうち最も難しいのがディファードディープリンク(deferred deep link)だ。アプリがない状態で特定の商品・イベントにつながるリンクをクリックした利用者が、ストアを経てアプリをインストールし初めて起動したときにも、本来見ようとしていたその画面へ連れて行く機能である。この三つがすべてFDL一つに乗っていたため、FDLが消えるとディープリンク・ストア誘導・ディファードディープリンクが同時に崩れたのだ。

2. ディープリンクの基礎を立て直す - ユニバーサルリンクとApp Links

自前構築をするなら、まずディープリンクの基本メカニズムを正確に理解する必要がある。FDLのようなツールが代わりに処理してくれていたものを、今度は自分で設計しなければならないからだ。

2.1 iOSユニバーサルリンクとAASA

iOSのユニバーサルリンク(Universal Links)は、通常のhttps://リンクをそのまま使いながらアプリへルーティングされる仕組みだ。核となるのはAASA(apple-app-site-association)ファイルである。このファイルはドメインの/.well-known/apple-app-site-associationにHTTPSで、リダイレクトなしで、128KB以内のサイズでホスティングしなければならない。アプリ側ではAssociated Domains entitlementにapplinks:接頭辞付きでドメインを登録する必要があり、この両者が互いを指し合ってはじめて検証が成立する双方向の信頼構造だ。実務でよく見落とされるのが、iOS 14以降Appleが自社CDNにAASAファイルをキャッシュして配布している点だ。サーバー側のAASAファイルを修正してもAppleのCDNに反映されるまでタイムラグが生じうるため、開発中は?mode=developer entitlementでキャッシュを回避し直接サーバーから取得させる設定にしておくとデバッグが楽になる。

2.2 Android App Linksとassetlinks.json

Androidの対応概念はApp Linksであり、検証ファイルは/.well-known/assetlinks.jsonに置く。このファイルにはアプリのパッケージ名と署名証明書のSHA-256フィンガープリントを明記しなければならない。実務で最も多い失敗の原因は、Playアプリ署名(Play App Signing)を使う際に開発署名と配布署名のフィンガープリントが異なり、assetlinks.jsonに登録したフィンガープリントと実際に配布されたアプリのフィンガープリントが食い違うケースだ。このファイルもリダイレクトなしでHTTP 200とapplication/jsonのContent-Typeで応答する必要があり、アプリインストール後の検証には約20秒ほどの非同期処理時間がかかる点も考慮すべきだ。

2.3 カスタムスキームがなお必要な理由

ユニバーサルリンク・App Linksがあっても、myapp://のようなカスタムURLスキームを完全に手放すことはできない。カカオトークのアプリ内ブラウザのように、OS標準のルーティングが期待どおりに動作しない環境では、むしろカスタムスキームの方が安定して動作する場合があるからだ。結局実務では、ユニバーサルリンクを基本としつつ、特定の流入経路ではカスタムスキームをフォールバックとして併用する二重構造を組むことになる。

3. ディファードディープリンク、最も厄介な部分

3.1 なぜ特に難しいのか

ユニバーサルリンクとApp Linksは、アプリが既にインストールされていることを前提に動作する。問題はアプリがないときだ。利用者がアプリをインストールするためにストアへ移動した瞬間、元々クリックしたリンクのパラメータはそのまま失われる。ストアは「この利用者がどのリンクをクリックして来たのか」をインストール完了後にアプリへ自動的に渡してはくれない。そのためディファードディープリンクは、クリック時点の文脈とインストール後の起動時点の文脈をサーバーが別途つなぎ合わせる必要がある問題になる。

3.2 Android Install Referrerの限界

AndroidにはまだGoogle Play Install Referrer APIという公式な経路がある。アプリが初めて起動するときにこのAPIを通じて「どのリファラーパラメータを伴ってインストールされたか」を受け取ることができる。ただしこの方法はPlayストア経由のインストールにのみ適用され、サイドローディングや他のストア経由のインストールには通用しないという限界がある。

3.3 iOSは結局確率的マッチングに頼る

iOSにはこうした公式な経路自体が存在しない。そのため自前構築を選ぶと、結局フィンガープリンティングに基づく確率的マッチングに頼ることになる。リンククリック時点の端末情報・IPアドレス・タイムスタンプ・User-Agentをサーバーに保存しておき、アプリが初めて起動する瞬間に同じ組み合わせの情報が再び観測されるかを比較して、「おそらくこのクリックからのインストールだろう」と推定する方式だ。これは本質的に近似値であり、複数の利用者が同じネットワーク・近い時間帯に接続すると誤マッチングが発生しうる。BranchやAdjustのような商用プラットフォームが対価を得る理由の一つは、まさにこの確率的マッチングの精度を大規模なデバイスグラフで引き上げている点にある。

4. 自前インフラで再構築する際に必要なもの - チェックリスト

FDLを代替する自前インフラを作るなら、最低限次の四つの軸を用意する必要がある。

4.1 ドメインと静的ファイルホスティング

ディープリンク専用のドメイン(またはサブドメイン)を確保し、そのドメインの/.well-known/パスにAASAとassetlinks.jsonを安定して配信しなければならない。ここで重要なのは、これらのファイルがリダイレクトなしで、常に同じドメインから、キャッシュ方針まで考慮して配信される必要がある点だ。CDNを前段に置く場合はキャッシュ無効化戦略も併せて設計する必要がある。

4.2 サーバールーティングロジック

利用者のUser-Agentを見てiOS・Android・デスクトップを判別し、それぞれユニバーサルリンク・App Links・Webページへ送るサーバーロジックが必要だ。加えて「アプリがインストールされているか」を事前に知り得ないという根本的な不確実性の上で、アプリがない場合のフォールバック(ストア誘導)とある場合の処理(カスタムスキームまたはユニバーサルリンク)の両方を用意する必要がある。

4.3 短縮リンクとパラメータ設計

外部サービスのEOLリスクを避けるには、短縮リンクの生成・解決パイプライン自体を自ドメイン内で管理するのが安全だ。短いコード(base62エンコーディングなど)と元のパラメータをマッピングするストレージを用意し、クリック時点で元のパラメータへ復元してルーティングに使う。短縮処理が失敗したり遅延したりする状況に備え、そもそも全パラメータを含んだ長いフォールバックURLも併せて用意しておけば、機能的には優雅に性能が低下する構造を作れる。

5. 韓国特有の事情 - カカオトーク共有の落とし穴

5.1 アプリ内ブラウザが標準を無力化する

ここからは純粋にiOS・Android公式ドキュメントだけを見ていても出てこない、韓国国内サービス特有の問題だ。カカオトークで共有されたリンクは、利用者のデフォルトブラウザではなくカカオトーク内蔵のアプリ内ブラウザで開かれる。このアプリ内ブラウザ環境では、ユニバーサルリンク・App LinksのOSレベルの横取りが期待どおりに動作しないケースがよく報告されている。つまりiOS・Androidの標準を完璧に実装しても、カカオトーク経由のトラフィックではディープリンクが機能しない可能性があるということだ。

5.2 executionParamsに基づく分岐

この問題を回避する実務的な方法の一つが、カカオリンク(カカオトーク共有SDK)のexecutionParamsのようなパラメータを活用することだ。メッセージを送る際に実行時パラメータを添えて、既にアプリがある利用者はカスタムスキームで直接アプリを開き、未インストールの利用者は別のWebランディングページへ送る分岐をアプリ側・サーバー側で自前設計する方式である。ある開発者はこの状況を「죽은 단축링크의 해부」(死んだ短縮リンクの解剖)と表現していたが(原文は参考資料を参照)、標準仕様だけでは解決しない韓国国内メッセンジャーエコシステム特有の事情をよく示していると思う。

6. 商用SaaS vs 自前構築 - 何を買い、何を作るか

6.1 コスト構造の比較

FDL終了後にGoogleが公式に案内した代替策は、Branch・Adjust・AppsFlyer OneLink・Kochavaのような商用ディープリンク・アトリビューションプラットフォームだ。おおよそのコスト構造を比較すると次のようになる。

6.2 判断基準

本人の判断基準は明確だ。ディープリンクの要件が共有リンク・単純なルーティング中心で、トラフィック規模が大きくないなら、自前構築の初期投資が商用SaaSの継続的な購読料より総所有コストの面で有利になりうる。逆に大規模マーケティングキャンペーンのアトリビューション、不正インストール検知、複数ストア・プラットフォームをまたぐ精巧なディファードディープリンクが中核的なビジネス指標に直結するなら、検証済みの商用プラットフォームの精度と保守負担移転の効果の方が大きい。FDLが「無料」だったためにこの判断自体を一度もしたことがないチームが多かったというのが、今回の終了事態の本当の教訓だと思う。

7. 実務移行チェックリスト

  • FDL終了前に既存のリンク・クリックデータをエクスポートしていたか確認(既に過ぎていれば復旧不可を前提に再設計)
  • ディープリンク専用ドメインの確保と/.well-known/apple-app-site-association、/.well-known/assetlinks.jsonのホスティング準備
  • iOS Associated Domains entitlement、Android App Links intent filterのアプリコードへの反映
  • サーバールーティングロジック - User-Agentベースのios/Android/デスクトップ分岐とストアフォールバックの実装
  • ディファードディープリンクの要件が実際にあるか確認 - なければ自前構築の範囲を大幅に減らせる
  • カカオトークアプリ内ブラウザ経由のトラフィックを別途テスト - executionParams分岐の必要性を確認
  • 短縮リンクパイプライン(生成・解決・リダイレクト)を自ドメイン内で構築するか、商用サービスを選定するか
  • Branch・Adjust・AppsFlyer OneLinkなど商用代替の総所有コストを自前構築と比較見積もり
  • AASA・assetlinks.jsonのキャッシュ遅延(iOSのCDN、Androidの約20秒検証)を考慮した配布・ロールバック計画
  • QRコード・SMS・メールなどオフラインチャネルに既に印刷・送信済みの旧リンクのリダイレクト対応の要否を点検

結論: FDL終了は警告ではなく、すでに起きたことだ

2026年7月時点で、FDL終了はもはや「備えるべき未来」ではなく「すでに起きた過去」だ。それでもこの事態が依然として有効な理由は、ディープリンク基盤をSDK一つでひとまとめに理解する慣性が今も多くのチームに残っているからだ。ユニバーサルリンク・App Linksはドメインとアプリが互いを検証し合う信頼構造であり、ディファードディープリンクは根本的にサーバーが確率的に埋めなければならない隙間であり、カカオトークのような国内メッセンジャー環境はその上にもう一つの例外を重ねる。この三層を理解すれば、商用SaaSを使うにせよ自前構築を選ぶにせよ、少なくとも何を買い、何を背負うのかを正確に把握したうえで決められる。本人はトラフィックが大きくないサービスなら自前構築を、アトリビューションが売上に直結するサービスなら商用プラットフォームを勧める。ただしどちらを選ぶにせよ、今回の移行チェックリストの項目は一度自分で点検してみることを勧める。
