databow and ADBC - A Command-Line Tool for Columnar Zero-Copy Database Queries

The Apache Arrow project's ADBC standard cuts past the row-oriented bottleneck of ODBC and JDBC - how it differs from psql, usql, and the DuckDB CLI

Jul 6, 2026 Dev & Infra

Intro: Why databow and ADBC, Right Now

Every data engineer or analyst knows the scene: production runs on PostgreSQL, the analytics warehouse is Snowflake or BigQuery, and local experiments happen in DuckDB or SQLite. Running a single query means opening a different client every time, re-learning a different connection syntax, and dealing with yet another result format. As of July 2026, a tool aimed squarely at this problem is databow. Featured on GeekNews, it is a Rust-based command-line SQL client built by a company called Columnar, running on top of ADBC (Arrow Database Connectivity), a standard from the Apache Arrow project.

This post weighs the idea underneath databow - ADBC - more heavily than the tool itself. CLI tools come and go, but the idea of unifying every database's different protocol into columnar Arrow data looks like a structural shift that will shape the data-tooling ecosystem for years. From the vantage point of someone who works across multiple databases from the command line every day, I want to soberly work out how this tool fundamentally differs from psql, usql, and the DuckDB CLI, and whether it is ready to put into practice right now.

1. What Is ADBC - Apache Arrow's Database Connectivity Standard

1.1 Why It Was Built

ADBC is an API standard the Apache Arrow project released in early 2023. The goal is simple: instead of routing through each client's own protocol when pulling data from different databases, provide a single API that exchanges data directly in Arrow's columnar format. Arrow itself is an in-memory columnar format designed to share data across language and process boundaries without copying, so ADBC essentially extends that Arrow ecosystem down to the database-connection layer.

1.2 Where It Fundamentally Differs From ODBC and JDBC

ODBC and JDBC have been the de facto standards for database connectivity for decades, but both were designed row-oriented. JDBC's API itself is built to extract values row by row, which makes an efficient bridge to a columnar format like Arrow structurally hard. ODBC fares somewhat better with bulk retrieval via block cursors, but details such as representing nulls as integer indicators do not sit well with columnar data, adding conversion overhead. ADBC routes around this by being columnar from the start. For workloads that must pull massive row counts at once, like analytical queries, the core win is removing the round trip of packing into rows and then unpacking back into columns. That said, ADBC does not fully replace ODBC and JDBC. As the Apache Arrow team itself has said, ADBC is closer to a complement specialized for bulk columnar retrieval and ingestion, while the existing standards still handle general workloads such as transaction processing.

1.3 Its Relationship to Flight SQL

ADBC is often mentioned alongside Flight SQL. Flight SQL is a client-server protocol aimed at database developers, while ADBC is an application-side standard that wraps various database client technologies, including that protocol, into one API. In other words, if a database implements Flight SQL, it can support ADBC, JDBC, and ODBC clients all at once. Snowflake and DuckDB adopted this within months of ADBC's introduction, and some reports describe result-retrieval times cut by more than 90% in certain cases - figures that come from vendor and community reports and warrant re-verification in your own environment.

2. Introducing databow - A Rust CLI Built on ADBC

2.1 What the Tool Does

databow is a command-line tool built by Columnar and released under the Apache-2.0 license. It offers an interactive shell with command history and SQL syntax highlighting, formatted tables with dynamically sized columns, and the ability to export results straight to JSON, CSV, or Arrow IPC files. It supports both an interactive mode and a non-interactive, single-query mode, making it comfortable to drop into scripts or explore by hand.

2.2 Installation and Basic Usage

You can install it via uv tool install databow or cargo install databow. Taking DuckDB as an example: first pull that ADBC driver with dbc install duckdb, then open an interactive shell with databow --driver duckdb, or run a one-off query directly with something like databow --driver duckdb --query 'SELECT 42 AS the_answer'. Reading a SQL file with --file and dropping results into a file with --output will feel familiar to anyone who has used psql or usql. The only real difference is that, underneath, the data moving around is an Arrow columnar batch, not rows.

3. The Practical Value - Why It Matters to Data Engineers and Analysts

3.1 People Who Live Across Multiple Databases

In my view, the real demand for a tool like databow comes from people who repeatedly explore, verify, and migrate data across different database engines within a single project - pulling a sample from production Postgres, attaching it to a local DuckDB to poke at, then checking it lines up with the format expected before loading into Snowflake. In that kind of workflow, the cost of switching clients and re-learning connection strings and output formats every time adds up more than it looks. Being able to move across multiple engines with one CLI and one shell syntax alone cuts down on context-switching cost.

3.2 What Columnar Zero-Copy Actually Buys You

The performance gain is not an abstract claim - it depends on the workload. If you are pulling millions of rows to hand off to a columnar analysis tool like pandas or Polars, receiving Arrow data from the start and passing it straight through is unambiguously faster than receiving rows and converting them back to columns. Conversely, for workloads with no columnar benefit to begin with - a handful of rows from a transactional lookup, or a single-row update - ADBC's advantage is not something you will feel. In short, databow's value is maximized in pipelines that move large analytical datasets into other columnar tools.

4. A Driver Ecosystem That Is Still Limited - A Sober Look

4.1 Maturity Varies Wildly by Driver

This is where caution is warranted. Looking at the ADBC driver documentation, maturity differs sharply from driver to driver. The Snowflake driver is marked Stable, making it the most trustworthy. The PostgreSQL driver is usable in practice across several language bindings - C/C++, C#, Go, R, Ruby, Rust. BigQuery, on the other hand, still sits at Beta for its C# driver and Experimental for its Go driver, and the official docs explicitly note that the SQLite driver is a reference implementation used during development that has not received optimization attention.

4.2 Translating That Into Production Risk

In other words, the fact that an ADBC driver exists for a database does not mean it is ready to drop straight into production. A mature driver like Snowflake's can be used with confidence, but a driver still at Beta or Experimental may behave unexpectedly on edge cases. That databow's official examples center on DuckDB reads, to me, as a signal of where the ecosystem's current center of gravity sits. This is the usual fate of a new standard, but at this stage the right question is not 'can I use it' but 'how mature is this specific driver for my specific database' - checked one driver at a time.

5. Compared With psql, usql, and the DuckDB CLI

5.1 psql - Proven, But Single-Database and Row-Oriented

psql, the PostgreSQL-only client, remains the benchmark for stability and feature completeness. But it was never aimed at multiple databases, and its protocol is row-oriented. If you only ever touch Postgres, it is still close to the best choice available.

5.2 usql - Universal, But Not Columnar

usql is a universal CLI inspired by psql, spanning PostgreSQL, MySQL, Oracle, SQL Server, and SQLite, as well as ClickHouse, CockroachDB, Presto, Trino, and BigQuery, all through Go's database/sql interface. Its goal of moving across many databases from a single shell matches databow's, but internally it wraps each database's standard driver - generally row-oriented - as-is. So usql currently has broader reach in unifying many databases under one UX, but on the axis of columnar zero-copy transfer, its design philosophy is fundamentally different from databow/ADBC.

5.3 DuckDB CLI - Pulls Data In and Computes With Its Own Engine

The DuckDB CLI can attach to external databases through extensions like the postgres scanner and mysql scanner and run cross-database queries. But this approach pulls data from other databases into DuckDB's own analytical engine to compute there. Because DuckDB is a powerful in-process analytical engine, this is excellent for local analysis, but it points in a different direction from ADBC's approach of receiving a database's own native execution result directly, still columnar. The choice comes down to whether the goal is to compute with DuckDB or to move each database's own result out quickly, as-is.

5.4 databow/ADBC - Moves Native Results With Zero-Copy

To sum up, where databow differs from the other three is that it receives the result each database engine has already computed as an Arrow columnar batch, without packing it into rows first. If usql emphasizes UX unification and the DuckDB CLI emphasizes consolidating the compute engine, databow/ADBC emphasizes the efficiency of the transport layer. It is more accurate to see these three as solving different problems than as competing head-to-head.

6. When to Use What

My own operational rule of thumb is this. If you only use one database, that database's native client (psql, etc.) is still the safe default. If you move across multiple databases and unified UX with broad driver coverage is the priority, usql is more practical today. If you want to attach several local sources and analyze quickly, the DuckDB CLI fits. And if your core task is pulling large columnar datasets out of several databases and streaming them straight into an Arrow-based pipeline such as pandas, Polars, or Arrow itself, that specific point is where databow and ADBC are worth seriously evaluating - but check whether the target database's ADBC driver has reached Stable first.

Conclusion

databow itself is still a small tool. But the ADBC layer underneath it is a standard with a clear direction: redesigning database connectivity from row-oriented to columnar. That Snowflake and DuckDB climbed aboard quickly is likely because this direction addresses a real bottleneck in analytical workloads. Still, as of July 2026, driver maturity varies sharply by database - this is an early stage. There is no reason to rip out psql or usql today and move to databow, but if you operate pipelines that frequently move large columnar datasets, this is a trend worth watching.
