Masking at the Output Is Already Too Late - Stopping Sensitive Values at the Source

Output-stage masking only blocks the formats you know, and by then the copies have multiplied

2026-08-01 Development/Infrastructure

Introduction: Deleted from the log, still there in the backup

The usual sequence goes like this. Someone reading a log spots a value that should not be there. A masking rule is written and shipped in a hurry. The next day the log screen is clean. Then about a month later, someone unpacking an old backup for an incident review finds the same value again.

In that story the masking rule did its job. The problem is the moment it started working. By then the value had already gone to standard output, been written to a file, been shipped to a collector, been rotated, and landed in a backup. Masking at the output stage means fixing one copy after several have already been made.

So the claim of this article is not that you should mask more. Masking is the last line of defence, and the real fix is keeping the value out of the log path in the first place. To do that you have to flip the direction of the rule. Do not choose what to strip out. Choose what to put in.

  • Output-stage masking only blocks the patterns you know. A small format change passes straight through, and nothing fails
  • Logging a whole object drags in fields added later. The logging code is unchanged while the leaking set grows
  • By the time you decide to fix it, several copies exist. Nobody knows which copies still hold the value
  • Wrap the value and mistakes stop producing it. Concatenate it into a string, put it in a log, same result

Environment. Every output below was actually run on Windows 10 Pro (10.0.19045) with Node.js v22.16.0 (win32). Every script was saved to a file and executed, and files were created only inside a temporary directory.

All example values are fake, matching the format only. Digit counts are correct but every digit is zero (000000-0000000, 0000-0000-0000-0000, 010-0000-0000), and the email uses a reserved domain that can never receive mail. None of this is real personal data. The article covers only the structure of how values escape, not any method of circumvention or extraction.

What this article does not cover. Deciding which data may go into an external tool and how the internal rules should be written belongs to Can Company Data Go Into an LLM. The level convention for deciding what gets logged at which severity was covered in Why WARN Becomes a Landfill, so it is not repeated here. The general procedure for flipping a denylist into an allowlist is in A Denylist Is Always Late. This article is that principle applied to one point: the log path.

On the law. Organizations handling personal data carry obligations around collection, storage and destruction. However, this article quotes no statute and no amount. Scope and retention periods vary by business model and jurisdiction, so check the applicable laws and your internal policy to decide. What this article covers is only the technical implementation.

1. Log a whole object and later fields come along

Start with the most important reproduction. Understanding this one is half the article. The defect is not that a sensitive value was logged, it is that nobody pinned down the set of things that get logged.

Take a call that serializes a whole object into a log line, then let time pass and have another team add fields for an unrelated feature. The logging call is not touched.

node v22.16.0 / win32
--- 1-1. release v1: the object has 3 fields ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z"}

--- 1-2. release v2: product adds fields. the log call is UNCHANGED ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","cardNumber":"0000-0000-0000-0000","nationalId":"000000-0000000"}

--- 1-3. diff: what the log gained without a code change ---
fields logged in v1 : 3  id,nickname,createdAt
fields logged in v2 : 6  id,nickname,createdAt,phone,cardNumber,nationalId
newly leaking        : phone,cardNumber,nationalId
lines of code changed to cause this : 0

The last line summarizes the whole article. The number of lines changed to cause this is zero. The person who added the fields never read the logging code, and the person who wrote the logging code does not know the fields exist. Neither did anything wrong, and the value leaks.

This class of defect does not get caught in code review. All the reviewer sees is a change that adds three fields, and taken on its own that change is perfectly fine. The problem lives in the distance between two changes.

1.1 Spreading and nesting behave identically

It is natural to think you just need to avoid passing the object directly. Two common workarounds are not workarounds at all.

--- 1-4. the same happens through spread, nesting and ORM rows ---
spread into context  : {"requestId":"r-0001","id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","card ...
nested one level     : nationalId still present
depth does not help  : JSON.stringify walks the whole tree
  • Spreading into a context object selects nothing. The same fields simply moved up one level
  • Wrapping one level deep does nothing either. The serializer walks the whole tree, so depth is not a defence
  • Passing a database row object straight through is the worst case. Adding a column widens the log, and columns are added by people with no connection to logging
  • Attaching the entire request body to a context has the same shape. Server code does not decide what a client sends
  • They share one property. The party that fixes the scope is not the party writing the log. That is the definition of the defect

2. Output-stage masking only blocks the formats you know

The first response that comes to mind is a regex applied just before output, and it is genuinely common. Where it breaks down was checked with harmless values only: phone-shaped and employee-number-shaped strings, all digits zero.

node v22.16.0 / win32
--- 2-1. a typical output-stage masker ---
input                                 after masking
------------------------------------------------------------------------------
contact 010-0000-0000 assigned        contact 010-****-**** assigned
contact 010 0000 0000 assigned        contact 010 0000 0000 assigned   <- NOT MASKED
contact 01000000000 assigned          contact 01000000000 assigned   <- NOT MASKED
contact +82-10-0000-0000 assigned     contact +82-10-0000-0000 assigned   <- NOT MASKED
contact 010.0000.0000 assigned        contact 010.0000.0000 assigned   <- NOT MASKED
owner EMP-000000 approved             owner EMP-****** approved

owner emp-000000 approved             owner emp-000000 approved   <- NOT MASKED
owner EMP-0000001 approved            owner EMP-0000001 approved   <- NOT MASKED

samples: 9   missed: 7

Seven of the nine went straight through. And every reason they did is trivial.

  • The separator changed from a hyphen to a space or a dot. The day an upstream system changes its normalization, the rule stops working
  • There is no separator at all. That is the common shape when stored in a database
  • A country code appeared in front. One layer normalizing to an international form produces this
  • The case differs. A single missing flag on the regex is the whole story
  • The employee number gained one digit. Only the numbering policy changed, and the rule missed
  • What they share is that nothing fails. There is no signal saying the masking did not apply

2.1 It is wrong in the other direction too

There is a second, less discussed failure mode: the rule destroying what it should have left alone.

--- 2-2. why the rule cannot be finished ---
the masker matches shapes. the data is defined by MEANING.
every upstream format change is a silent hole, and nothing fails loudly.

--- 2-3. and the rule can be too greedy in the other direction ---
order 010-0000-0000 shipped           order 010-****-**** shipped   <- masked, but this was not personal data
build EMP-000000 finished             build EMP-****** finished   <- masked, but this was not personal data

a pattern rule has two failure modes at once: it misses, and it destroys.

An order code and a build tag happened to fit the shape. Here masking destroys a non-sensitive value and blocks debugging. People then loosen the rule, and the loosened rule starts missing again. This pendulum never settles.

The root cause fits in one sentence. A regex matches a shape; sensitive data is defined by meaning. The same eleven digits are personal data in one context and an order number in another, and that difference is not inside the value.

3. By the time you decide to fix it, several copies exist

Now the third axis. The two previous sections were about what gets missed; this one is about when. The ordinary life of a single log line was traced by running it.

Eight of nine copies still hold the original. You fixed one. And a different person sets the retention on each of those eight.

  • Rotated files are governed by server configuration, usually owned by infrastructure rather than the application team
  • Collector segments are governed by collector policy. If an index exists, the value is searchable too
  • Backups are governed by backup policy. Typically the longest, and the hardest to reach into
  • Incident snapshots and ticket attachments are governed by nobody. If the person who made them forgets, they stay forever
  • So before you can say it was deleted, this list has to exist. In most organizations it does not

3.1 Eight is only what you can enumerate

--- 3-5. and these are the ones you can enumerate ---
not counted here: collector replicas, object-storage versions,
search-engine inverted index, alert payloads already delivered,
an engineer terminal scrollback, and any chat message quoting the line.
the retention clock of each copy is set by a different owner.

This is where the central claim of the article comes from. Chasing copies is a fight you cannot win. The moment the value is born the copies are already scheduled, and every later measure touches only a subset of them. You have to move the fight earlier, to before the value enters that path.

4. The error object carries it for you

However well you tidy up your logging calls, one path remains. Exceptions. They print without anyone deciding to log anything.

node v22.16.0 / win32
--- 4-1. route A: the value goes into the message ---
e.message           : invalid nationalId: 000000-0000000
first stack line    : Error: invalid nationalId: 000000-0000000

--- 4-2. route B: the value rides on a property ---
e2.message          : payment declined   (clean)
JSON of e2.context  : {"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}

--- 4-3. what each common serializer emits ---
JSON.stringify(e2)            : {"name":"AppError","context":{"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}}
  -> CONTAINS nationalId
String(e2)                    : AppError: payment declined
  -> clean
util.inspect(e2) contains     : CONTAINS nationalId
console.error path uses inspect, so the terminal shows it too

The two routes have different characters.

  • Route A is visible. Putting the value into a validation failure message is a helpful habit, so it is very common and therefore leaks very commonly. Put it in the message and it lands in the first stack line too
  • Route B is invisible. The message is clean while the whole request hangs off a context property. And that habit is a recommended one, so it spreads further
  • Judging by the message alone is wrong. What the serializer walks determines what actually leaves
  • Terminal output goes through the same inspection path, so it shows on screen too

4.1 Cause chains, unhandled exceptions and a safe-looking trap

--- 4-4. the cause chain carries it further ---
outer.message                 : checkout failed   (clean)
inspect(outer) contains       : CONTAINS nationalId
a wrapper error looks innocent while dragging the original context

--- 4-5. why JSON.stringify(err) looks safe and is not ---
JSON.stringify(new Error(payload.phone)) : {}
message and stack are non-enumerable, so plain JSON drops them,
which is exactly why teams add a custom error serializer,
and the custom serializer is what puts message, stack and context back in.

--- 4-6. an unhandled rejection prints it with no logging code at all ---
uncaught handler saw : AppError: payment declined
full text contains   : CONTAINS nationalId

nobody called a logger here. the runtime did.

4-5 is the instructive one. The default serialization turns an error into an empty object, because message and stack are non-enumerable. Teams then hit the annoyance that errors do not show up in logs and add a dedicated error serializer. That serializer puts the message, the stack and the context back in. They remove the safe default themselves.

  • An outer error wrapping a cause looks even safer because its message is clean, while it drags the inner context along
  • Unhandled exceptions are printed by the runtime without anyone calling a logger. Auditing logging calls will never list this path
  • So you need a rule that error contexts carry identifiers only: request id, user id, order id
  • Validation messages should say what was wrong rather than the value. Format mismatch on field nationalId is enough
  • This rule enforces itself once the wrapper from section 5 is in place, because a wrapped value put into a message does not produce the original

5. Stop it at the source with a wrapper you must unwrap

Now the fix. The idea is simple. Do not carry a sensitive value as a string. Wrap it in a type that yields the original only through an explicit call. From that point on, mistakes expose a placeholder rather than a value.

const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // explicit, greppable, the only way out
  expose() { return this[RAW]; }
  // every implicit path returns the same placeholder
  toString() { return '[' + this.label + ' redacted]'; }
  toJSON()   { return '[' + this.label + ' redacted]'; }
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }
}

const phone = new Secret('010-0000-0000', 'phone');

Covering the four hooks together is the point. Miss one and everything leaves through that hole. Thirteen paths where a mistake can happen were picked and run.

Thirteen paths, zero leaks. Put it in a template literal, add it to a string, join it in an array, serialize it, serialize it nested, swap the format specifier three ways, and the original never appears. That is what stopping it at the source means in practice. You are not forbidding mistakes, you are making mistakes harmless.

--- 5-3. console.log goes through inspect, so it is covered too ---
  direct  : [phone redacted]
  nested  : {
  requestId: 'r-0001',
  user: { id: 'u-0001', contact: [phone redacted] }
}

--- 5-4. the only way to the value is a call you can grep for ---
  phone.expose() : 010-0000-0000
  a code search for .expose( lists every real use site.
  a code search for the field name does not, because the field is everywhere.

The last two lines of 5-4 are the biggest operational win. The only route to the original is one named method, so a single code search lists every place the value is genuinely used in raw form. Searching by field name does not produce that list, because the field name is everywhere. The audit surface shrinks from hundreds of places to a dozen.

5.1 A half implementation is worse than none

--- 5-5. what happens if you implement only half of it ---
  toString only, template : [redacted]
  toString only, JSON     : {"v":"010-0000-0000"}   <- LEAK
  toString only, inspect  : HalfSecret { v: '010-0000-0000' }   <- LEAK
  a partial wrapper is worse than none: it reads as safe.

--- 5-6. the strict variant: refuse instead of substituting ---
  concat -> TypeError: Secret must be unwrapped with .expose() before use
  JSON  -> "[phone redacted]"   (toJSON still substitutes, so logs never crash)
  throwing catches mistakes in tests; substituting keeps production quiet.
  a common split: throw in dev and test, substitute in production.

--- 5-7. the wrapper does not survive the network boundary ---
  after JSON round trip : {"contact":"[phone redacted]"}
  the type is a source-side guard. across a boundary you must re-wrap on parse.
  • A wrapper implementing only string conversion hid the value on screen but emitted the original through serialization and inspection. And that is the actual log path
  • A half wrapper is more dangerous than none, because whoever reads the code concludes that it is wrapped and therefore safe
  • The strict variant throws when you try to use it as a string. It catches mistakes immediately in tests, at the risk of creating a new production incident
  • A common compromise is to throw in development and test, substitute in production. The serialization hook keeps substituting on both sides so logs never crash
  • The wrapper does not cross boundaries. Serialize and send it and the other side receives a placeholder, so the receiving side has to re-wrap. This approach has to be established per service
  • Also, a type system makes it stronger. Passing a wrapped value where a string is required fails at compile time

6. Choose the fields to include, not the fields to strip

The wrapper protects the value. But the problem in section 1 was not the value, it was the scope. This section pins the scope down. Only one question is in play here: how to keep sensitive fields out.

// direction 1. choose what to strip
const DENY = ['phone', 'cardNumber', 'nationalId'];
function denylist(obj) {
  const out = { ...obj };
  for (const k of DENY) delete out[k];
  return out;
}

// direction 2. choose what to include
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];
function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

On the schema they were written for, the two functions are indistinguishable. That is why this defect survives so long.

node v22.16.0 / win32
--- 6-1. both rules look fine on the schema they were written for ---
  denylist (v2)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}
  allowlist(v2)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}

--- 6-2. now the schema moves. neither rule is edited ---
  denylist (v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","national_id":"000000-0000000","backupPhone":"010-0000-0000","kyc":{"documentNo":"D-000000000"}}
  allowlist(v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}

  sensitive values present in denylist output  : id-shaped value, phone-shaped value, document-shaped value
  sensitive values present in allowlist output : none

The schema was moved in three directions. The same data arrived under a different naming convention, a new field nobody announced was attached, and a nested structure appeared. The strip list let all three through; the include list blocked all three. This is the exact mirror of section 1. What leaked automatically there is blocked automatically here.

--- 6-3. the asymmetry, stated plainly ---
  denylist  fails OPEN : an unknown field is emitted
  allowlist fails CLOSED: an unknown field is dropped
  a new field is added by someone who has never read the logging code.
  so the rule has to be safe when nobody updates it.

--- 6-4. what you lose, and how to notice ---
  fields dropped from the log : phone, cardNumber, nationalId, national_id, backupPhone, kyc
  a field you needed for debugging is now missing, and that is the cost.
  make it visible instead of silent:
  {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","_dropped":6}
  the count tells you the schema moved, without telling you what moved.

--- 6-5. the allowlist has to be applied at build time, not at write time ---
  event object keys : ["id","nickname","createdAt","plan"]
  the wide object never reaches the logger, so no later stage can widen it.
  narrowing inside the logger is one layer too late: everything upstream
  of the logger, including error handlers, still sees the wide object.
  • They fail in opposite directions. A strip list emits unknown fields; an include list drops them. The rule must be safe while nobody updates it, so the latter is correct
  • There is a cost. A field you needed for debugging silently disappears. That is the real price of an allowlist and it should not be hidden
  • 6-4 shows a cheap way to make the cost not silent: emit just the count of dropped fields. It says the schema moved without saying what moved
  • When that number suddenly grows, it is a signal that something upstream changed and a prompt to review the allowlist
  • Where you apply it is decisive. Narrowing inside the logger is one layer too late. Everything above the logger, especially error handlers, still sees the wide object
  • So the narrowing belongs at the moment the event object is built. If the wide object never reaches the logger, no later stage can widen it again

7. When only the last four digits may show, where do you cut?

Partial display is a real requirement. A support agent needs the last four digits of a card to verify a caller. The requirement itself is legitimate. The question is where you cut.

node v22.16.0 / win32
--- 7-1. the requirement: a support screen shows the last 4 digits ---
  requested display value : ****-****-****-0000

--- 7-2. attempt A: keep both on the same record ---
  record  : {"userId":"u-0001","cardNumber":"0000-0000-0000-0000","cardLast4":"0000"}
  the display value exists, and so does the original, one key apart.
  every whole-object log, error context and API response carries both.
  the partial value did not reduce anything. it added a field.

--- 7-3. attempt B: cut at the source, keep only the derived value ---
  record  : {"userId":"u-0001","cardLast4":"0000","card":"[card redacted]"}
  inspect : { userId: 'u-0001', cardLast4: '0000', card: [card redacted] }
  the screen gets cardLast4. the logger gets cardLast4. nothing else is reachable
  without calling .expose(), and .expose() is greppable.

--- 7-4. the two attempts under the same accidental log line ---
  A : {"msg":"checkout","data":{"userId":"u-0001","cardNumber":"0000-0000-0000-0000","cardLast4":"0000"}}
      -> ORIGINAL PRESENT
  B : {"msg":"checkout","data":{"userId":"u-0001","cardLast4":"0000","card":"[card redacted]"}}
      -> derived value only

7-2 is a very common mistake. The cut value and the original sit side by side in the same object. The screen uses the cut value so the requirement is met. But the moment that object is logged whole, the original goes with it. Partial display reduced nothing; it added a field.

7-3 is the answer. Cut once at the boundary, keep only the derived value, and leave the original wrapped. Then both the screen and the logger receive only the cut value.

--- 7-5. cutting late produces drift ---
  input                : "0000 0000 0000 0000"
  last4  (digits only) : 0000
  last4v2(naive slice) : "0000"
  same field name, two values, depending on which layer computed it.
  cutting once at the boundary makes the answer single-valued.

--- 7-6. a partial value is still personal data ---
  one record may hold several partials : {"u-0001":["0000","010-0000","a***@example.invalid"]}
  each is harmless alone. joined on the same subject they narrow the set.
  so a partial is a display format, not a declassification.
  keep the same retention and access rules on it.
  • 7-5 is the second problem with cutting late. When cutting code appears in several layers, the same field name carries different values. One strips to digits before cutting, the other just slices the end of the string
  • On an input containing spaces the two results diverged. One is four digits, the other is four characters including a space. You end up with a value that looks different depending on the screen, and that comes back as a support ticket
  • Cutting once at the boundary makes this problem disappear by definition, because there is exactly one place that produces the derived value
  • 7-6 is the final caution. A partial value is still personal data. Any one of them is harmless, but several partials attached to the same subject narrow the set
  • So a partial is a display format, not a declassification. Keep the same retention and access rules you apply to the original
  • The exact digit count and display scope vary by industry and contract. Check the applicable laws, your internal policy and any payment network rules to decide

8. Finding the risky spots in existing logs, and the order of rollout

Everything so far was about what to do from now on. This section is about what to do with what has already piled up. Diagnosis takes two passes.

--- 8-1. build a sample log tree ---
  api.log       3 lines
  worker.log    2 lines
  auth.log      2 lines
  batch.log     3 lines

--- 8-2. pass 1: key names, not value shapes ---
  file          lines   risky keys found
  ----------------------------------------------------------------------
  api.log       3       phone(1) context.cardNumber(1)
  worker.log    2       -
  auth.log      2       authorization(1) password(1)
  batch.log     3       national_id(1) nationalId(1) email(1)

--- 8-3. pass 2: key inventory, to catch names you did not list ---
  distinct keys in the sample : 14
  matched the risk list       : 7
  NOT on the risk list        : 7
  lvl, msg, path, userId, context, jobId, durationMs
  read this list by hand once. that is the review, and it is finite.
  a value-shape scan cannot produce this list at all.

The first pass searches key names rather than value shapes. As section 2 showed, value formats vary with whatever is upstream, while key names are comparatively stable. Nested keys have to be captured by path, which is how context.cardNumber was caught.

But the second pass matters more: list every key that did not match the risk list and have a person read it once. In the sample there were fourteen distinct keys and seven of them were off the list. That list is finite. Reading it once finishes the job. And it is a list a value-shape scan cannot produce at all.

--- 8-4. rank by blast radius, not by count ---
  file          keys   retain   copies   score
  ----------------------------------------------------------
  batch.log     3      365d     3        3285
  auth.log      2      365d     4        2920
  api.log       2      90d      4        720
  worker.log    0      14d      1        0
  score = risky keys x retention days x number of destinations.
  a low-volume line kept for a year in four places outranks a noisy one kept for two weeks.

--- 8-5. order of work, by how hard each step is to undo ---
  # action                                cost      undo                  buys you
  ------------------------------------------------------------------------------------------------------------
  1   collector-side drop rule              minutes   fully reversible      stops NEW copies today
  2   shorten retention on the worst file   minutes   reversible            shrinks the window
  3   purge existing copies                 days      NOT reversible        needs an owner list first
  4   allowlist the event builders          weeks     reversible by revert  the actual fix
  5   wrapper type on the fields            weeks     reversible by revert  makes step 4 hold
  6   remove the collector rule             minutes   reversible            only after 4 and 5 are verified

8-4 ranks by blast radius rather than count, multiplying risky keys by retention days by destination count. That pushed a quiet log kept for a year and replicated to three places above a noisy one kept for three months. Sorted by count the order would have been reversed.

One point in the rollout is contested: collector first or code first? The answer in 8-5 is collector first, and the reason is not that it is a better fix.

  • The collector rule comes first because it is a tourniquet. It applies globally with no deploy, and it can be pulled off just as fast if it is wrong
  • At the same time, a tourniquet is not treatment. It does nothing for copies already made, and it is exactly the pattern matching section 2 showed to be incomplete
  • Do not rush the purge. It is the only irreversible step, and running it without an owner list means you cannot claim it was deleted
  • Code work is ordered 4 then 5 because the allowlist pins the scope and the wrapper keeps it pinned. Reversed, new unwrapped fields keep arriving
  • Step 6 happens only after verification, and verification is simple: turn the collector rule off, run the same scan in staging, and confirm the risky key count is zero
  • For a new service the order is reversed. Do 4 and 5 only; no collector rule is needed

8.1 Checklist

  • Found every place a logging call receives a whole object (including spreads, nesting, database rows and request bodies)
  • Listed the fields to include at the point the event object is built. Did not specify fields to strip
  • Applied the allowlist at event assembly, not inside the logger
  • Emitted the count of dropped fields so schema drift is detectable
  • Applied a wrapper type to sensitive fields, implementing all four hooks
  • Grepped the wrapper's unwrap call and reviewed every use site
  • Established a rule that error contexts carry identifiers only
  • Validation failure messages carry the field name, not the value
  • Checked what the custom error serializer walks
  • Partial display is cut once at the boundary and not stored next to the original
  • Partial values carry the same retention and access rules as the original
  • Scanned existing logs by key name and had a person read every key off the list
  • Ranked by key count x retention days x destination count
  • Documented the destination list and owner for each log copy
  • Confirmed handling scope and retention against the applicable laws and internal policy

Conclusion: do not choose what to strip, choose what to include

Laying the verified results out one line at a time: logging a whole object gained three leaking fields with zero lines changed. An output-stage regex missed seven of nine harmless format variants and destroyed two non-sensitive values at the same time. A single log line became nine copies through ordinary operations, and masking fixed one of them.

The other side was verified too. A wrapper covering four hooks produced zero leaks across thirteen accidental paths. A serializer that chose what to include let nothing through even after the schema moved in three directions. In the same situation, the version that chose what to strip let all three through.

So the conclusion is not to mask better. Masking is the last line of defence. Output-stage masking blocks only the patterns you know, and by then the copying is finished. The real fix lives before the value enters the log path, and the rule to apply there is singular. Do not choose what to strip; choose what to include. Only a rule that leans toward dropping unknown fields survives the years in which nobody updates it.

There is something you can do right now. Find one logging call that receives a whole object and print that object's field list today. If you cannot remember when you last checked that list, then you also do not know what has been added since. The second pass in section 8 exists to finish that check in one go.

# Stopping Sensitive Values at the Source — Wrapper, Allowlist, Triage

> Source: braindetox.kr — Masking at the Output Is Already Too Late
> Basis: verified by running on Windows 10 / Node.js v22.16.0
> Paste this file into an AI assistant and ask it to review your log path against these criteria.
> Every example value below is fake and matches only the format. Digit counts are right, all digits are zero.
> Decide the scope of personal data handling and retention periods by checking the applicable laws and your internal policy.

## 0. The one-line principle

Masking is the last line of defence. The real fix is keeping the value out of the log path,
and the rule to use there is singular. **Do not choose what to strip; choose what to include.**

| Approach | On an unknown field | Verdict |
|---|---|---|
| List of fields to strip | Emits it (fail open) | Leaks as soon as the schema moves |
| List of fields to include | Drops it (fail closed) | **Use this one** |
| Output regex | Passes if the format differs | A tourniquet, not a fix |

## 1. Wrapper type — the original comes out only when you unwrap it

Cover **all four** hooks. Miss one and everything leaves through that hole.

```js
const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // the only exit. it is named, so a code search lists every use site
  expose() { return this[RAW]; }

  toString() { return '[' + this.label + ' redacted]'; }   // templates, concat
  toJSON()   { return '[' + this.label + ' redacted]'; }   // serialization
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }  // console.log
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }   // implicit coercion
}
```

Zero leaks across the 13 verified paths:
template literal / string concat / String() / array join / JSON.stringify /
nested JSON / util.inspect / nested inspect / format %s / format %j /
format %o / String.prototype.concat / the + operator

Cautions:
- **Half an implementation is worse than none.** toString alone still leaks through serialization and inspection
- A common compromise is to throw in dev and test, substitute in production. Keep toJSON substituting on both
- **It does not cross boundaries.** Serialize and send it and the other side gets a placeholder. Re-wrap on receipt

## 2. Allowlist serialization — narrow at the moment the event is built

```js
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];

function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

// where you narrow is decisive. here, not inside the logger.
function buildEvent(user) {
  const picked = allowlist(user);
  const droppedCount = Object.keys(user).length - Object.keys(picked).length;
  return { event: 'signup', user: picked, _dropped: droppedCount };
}
```

- Narrowing inside the logger is one layer too late. Error handlers and anything above still see the wide object
- Emitting the dropped count tells you the schema moved **without telling you what moved**
- If that number suddenly grows, it signals an upstream change. Review the allowlist

## 3. Error context rules

- **Do not put the value in a validation failure message.** Format mismatch on field nationalId is enough
- Error contexts carry **identifiers only**: request id, user id, order id
- An outer error wrapping a cause looks clean in its message but **drags the inner context along**
- Unhandled exceptions are printed by the runtime **without a logger call**. Auditing log calls will not find them
- Do not relax because default serialization turns errors into empty objects. **A custom serializer puts it back**

## 4. Triage procedure — two passes

1) **Pass 1: search key names** (not value shapes)
   - Nested keys by full path: context.cardNumber
   - Value formats vary with whatever is upstream; key names are comparatively stable
2) **Pass 2: list every key off the risk list and have a person read it**
   - The list is finite. Reading it once finishes the job
   - A value-shape scan cannot produce this list at all
3) **Priority = risky key count x retention days x destination count**
   - Do not sort by volume. A quiet log kept long and widely outranks a noisy one

## 5. Rollout order — hardest to undo goes last

| # | Step | Time | Undo | Buys you |
|---|---|---|---|---|
| 1 | Collector drop rule | Minutes | **Fully reversible** | Stops new copies today |
| 2 | Shorten retention | Minutes | Reversible | Shrinks the exposure window |
| 3 | Purge existing copies | Days | **None** | Owner list comes first |
| 4 | Allowlist at event assembly | Weeks | Revert the code | **The actual fix** |
| 5 | Wrapper type on fields | Weeks | Revert the code | Keeps step 4 holding |
| 6 | Remove the collector rule | Minutes | Reversible | Only after 4 and 5 verify |

- The collector goes first not because it is a better fix but because it is a **tourniquet**
- For a new service the order reverses. Do 4 and 5 only; no collector rule needed

## 6. Checklist

- [ ] Found every place a logging call takes **a whole object** (spreads, nesting, DB rows, request bodies)
- [ ] **Listed the fields to include** at event assembly (not the fields to strip)
- [ ] Applied the allowlist **at event assembly, not inside the logger**
- [ ] Emitted the **count** of dropped fields
- [ ] Applied a wrapper to sensitive fields with **all four hooks** implemented
- [ ] Grepped the unwrap call and reviewed **every use site**
- [ ] Established that error contexts carry **identifiers only**
- [ ] Validation failure messages carry **the field name, not the value**
- [ ] Checked **what the custom error serializer walks**
- [ ] Partial display is cut **once at the boundary** and not stored next to the original
- [ ] Partial values carry **the same retention and access rules as the original**
- [ ] Scanned existing logs **by key name** and read **every key off the list**
- [ ] Ranked by **key count x retention days x destination count**
- [ ] Documented **the destination list and owner** for each log copy
- [ ] Confirmed handling scope and retention against **the applicable laws and internal policy**

## 7. Do not

- ❌ Pass objects, DB rows or request bodies **whole** into logs — new fields follow with zero lines changed
- ❌ Treat output regex masking **as the fix** — format variants defeat it and it destroys harmless values
- ❌ Keep the cut value and **the original in the same object** — one whole-object log emits both
- ❌ Put **the value** in a validation failure message — it lands in the first stack line too
- ❌ **Purge first** without an owner list — it is the only irreversible step
- ❌ Add a collector rule and **call it done** — it does nothing for copies already made
- ❌ Implement the wrapper **halfway** — it is more dangerous because it reads as safe
