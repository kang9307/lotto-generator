「出力が同じ」は「同じ関数だ」ではない - バイトではなく振る舞いで関数を判定するとき残る誤検知と見逃し

形が崩れた場所に何が残るのか、そして実行して比べるという決定が請求する代償

2026-09-10 開発・インフラ

名前が消された実行ファイルを前にしたとき、まず決めるべきなのは「この関数は何か」ではない。何を根拠に「同じ」と言うのかである。根拠を決めなければ答えも決まらず、根拠が変われば同じファイルから別の答えが出る。

根拠は古くから二系統あった。一つは形を測る道である。バイトがどれだけ重なるか、制御フローのグラフがどれだけ似ているかを見る。もう一つは振る舞いを測る道である。関数に値を入れて何が出てくるか、その過程で何を読み何を書くかを見る。二つの道は得意なことが違い、それ以上に間違え方の形が違う。

以下で辿る軸は二つ目の道である。とりわけその道を選んだとき必ず付いてくる二つの失敗 — 別々の関数を同じだと呼ぶ誤検知と、同じ関数を別物だと呼ぶ見逃し — がそれぞれどこで生まれ、何によって減るのかである。

きっかけ - 実行時の振る舞いで関数を突き合わせる道具

きっかけになったのは fnprint という道具である。リポジトリの README は自らをこう規定する。バイトや制御フローグラフがどう見えるかではなく、関数が何をするかでバイナリ内の関数を突き合わせる、と。各関数を小さなエミュレータの中で適当な値を入れて走らせ、その過程で残る効果を記録して指紋に変える。

README が挙げる用途は三つである。シンボルが削られたバイナリに名前を付けること、二つのビルド間の振る舞いの変化を突き止めること、そして既知の脆弱なコード群と修正済みのコード群に照らして正体不明の関数の順位を付けることである。現在は x86-64 ELF のみを扱い、ARM64 と MIPS、PE と Mach-O のローダーは計画として書かれている。Rust で書かれ MIT ライセンスである。

道具そのものより興味深いのは、この道具が選んだ判定の根拠である。実行して比べるという決定はただではない。それが何を買い何を支払うのかが本題である。そして支払いの内訳は道具の善し悪しの話ではなく、この判定方式そのものに付いてくる構造の話である。別の実装を選んでも同じ請求書が届く。

形で判定するということ - バイトとグラフ

形を測る道は古く、今も実務の基本である。大きく三つを数える。

  • バイト列 — 関数の先頭の機械語をそのまま照合する。ただしアドレスや再配置が入る位置は値が毎回変わるので、その位置を可変と印を付けておき、残りが重なるかを見る。
  • 制御フローの形 — 基本ブロックを頂点、分岐を辺とするグラフを作り、二つの関数のグラフがどれだけ似ているかを測る。命令が一つ変わっても骨格が残る場合が多く、バイト照合より耐える。
  • 付いている目印 — 文字列定数、マジックナンバー、呼び出す外部シンボルの名前といったものである。最適化がめったに触らないので手掛かりとしての価値は大きいが、目印がそもそも無い関数には使えない。

これらの方式が得意なことは明確である。速く、実行せず、当たるときは非常に正確だ。同じビルド環境で作られた同じライブラリを見分ける作業なら、これに勝るものは見つけにくい。問題はビルド環境が変わる瞬間である。

なぜ形が崩れるのか - 同じソースが違う機械語になる経路

「同じ関数を見つける」のが難しい理由は関数が難しいからではなく、同じソースが常に同じ機械語になるとは限らないからである。コンパイルはソースから機械語へ向かう一方向の変換であり、その変換にはソースに書かれていない決定が大量に入り込む。最適化のレベル、コンパイラの種類と版、対象アーキテクチャ、リンク時点の選択がすべて結果を揺らす。

具体的に何がバイトを崩すのかを分けておくとこうなる。

変換何が起きるかバイト照合への影響グラフ照合への影響
インライン化小さな関数が呼び出し側に展開される独立した関数が消え、照合する対象が無い呼び出し側のグラフが膨らみ元の形が溶け込む
命令の並べ替え依存の無い命令の順序が入れ替わる同じ命令の並びなのに順序が違って重ならないブロック内の順序だけなら骨格は残る

振る舞いで判定するという発想

ここで別の問いが出る。形が揺れるなら揺れないものは何か。最適化はプログラムのすることを変えない範囲で形を変える。ならば「すること」を直接測ればよいのではないか。

これが振る舞い基準の判定の発想である。関数に値を入れて走らせ、その過程で外に現れる効果を記録して要約にする。fnprint の README は記録するものをアーキテクチャに縛られない効果の流れと呼び、こう列挙する。引数として受け取ったバッファと構造体のどの位置を読みどこに書くか、書く値がどの種類か — 入力の複製か、小さな定数か、ポインタか — どの呼び出しをするか、どの分岐を通るか、何を返すかである。

そうして作られた効果の流れは断片に切られ、要約署名に変えられる。二つの関数の類似度はその署名の枠がどれだけ噛み合うかの割合で計算される。候補を総当たりで比べる作業を避けるため、束ねた索引が前に置かれる。概念だけ絵にすると、一つの関数の観測結果はおおよそこういう形になる。

読み   arg0[0 .. n)        連続アクセス
書き   arg1[0 .. n)        入力の複製
呼出   1回                 記録のみ、中には入らない
分岐   2回                 長さ 0 の検査 / 整列の検査
戻り   arg1                入力ポインタをそのまま

この要約には命令の順序も、レジスタの名前も、絶対アドレスも入っていない。README は絶対アドレスを捨ててオフセットと形だけを残すと書く。形を揺らす変換が届かない層まで降りたのである。並べ替えもレジスタ割り当ても、この要約の上では何も動かさない。その代わりこの層は別の対価を要求する。しかもその対価は、形を測る方式が一度も払わずに済んでいたものである。

実行するという決定が請求する四つの代償

入力を与えて出力を比べるとは、関数を実際に走らせるという意味である。静的解析には無かった問題がその瞬間から生まれる。四つに分かれる。

副作用 - 解析が世界を変える

関数は値を返すだけではない。ファイルを消し、ソケットを開き、グローバル変数を書き換え、プロセスを終わらせる。正体不明の関数を本物の機械の上でそのまま走らせれば、解析行為が観測対象の外を変えてしまう。だからこの方式は多くの場合、実際の実行ではなく模擬された実行を選ぶ。命令を真似る層の上で走らせ、外へ出る通路を塞ぐ。

入力空間 - 何を入れるか決めなければならない

関数の引数として入り得る値の種類は事実上無限である。そのうち何個を選んで入れるかが判定の質を決める。適当な値を入れれば実行はたいてい関数の前半だけを通る。長さが 0 かを見てすぐ戻る関数、ヌルポインタを弾く関数がそうだ。入力が浅ければ観測も浅い。逆に入力を精巧に作ろうとすれば関数が何を期待するかを知る必要があるが、それを知ることこそ元々解こうとしていた問題である。

環境依存 - 同じ関数が違って出る

実行結果は関数だけのものではない。初期化されていないメモリを読めば、そこに何があったかが結果に混ざる。時刻を読んだり乱数を引いたりする関数は呼ぶたびに違う値を出す。スタックに残っていた前の呼び出しの痕跡、整列の位置、マップされたアドレスがすべて観測に割り込む。この揺れを消さなければ同じ関数を二度測って別物だと判定することになる。

隔離コスト - 知らないコードを走らせるということ

正体の分からないコードを実行することには、それ自体に費用が付く。誤ったアドレスに触れて実行が死なないようにしなければならず、無限反復に陥ったとき断ち切る仕掛けが要り、一つの関数の実行が別の関数の実行に痕を残してはならない。そしてこれらの仕掛けはすべて速度を削る。バイト照合が毎秒数万個を舐める場所で、模擬実行は関数一つごとに何度も走らねばならない。

代償なぜ生じるかよくある対応対応しても残るもの
副作用関数が値の返却の外で世界を変える模擬実行、外へ出る呼び出しの遮断遮断された呼び出しの先の振る舞いは観測されない
入力空間あり得る入力が事実上無限である標本を決めて複数回繰り返す深い条件の先のコードには届かないままである
環境依存メモリ初期値、時刻、乱数が混ざる未設定メモリに定まった値を与え手順を固定決定性は再現性であって正答の保証ではない
隔離コスト正体の分からないコードを走らせる誤ったアクセスを吸収し実行の上限を設定速度が静的照合に大きく及ばない

きっかけの道具はその代償をどう処理するのか

四つの代償をどう扱うかがこの方式を評価する基準になる。fnprint の README に書かれていることだけを移すと次のようになる。

  • 未設定メモリ — 用意していない場所から読めば定まった値が返り、そのページはその場でマップされると書かれている。初期化されていないメモリという揺れを、値の規則で抑え込んだのである。
  • 誤ったポインタ — 見当違いのアドレスを扱っても実行が死なず、同じ入力は常に同じ記録を出すと書かれている。隔離と再現性を一つの文に束ねた記述である。
  • 他の関数の呼び出し — 外へ出る呼び出しは記録だけして飛ばすと書かれている。おかげで標準ライブラリの中へ潜り込まず、観測がその関数に留まる。
  • 絶対アドレス — 絶対アドレスは捨ててオフセットと形だけを残すと書かれている。同じコードが別の場所に置かれても同じ記録になるようにする仕掛けである。

ここまでが文書にあるものである。文書に無いものも同じくらい重要だ。システムコール命令に到達したとき何をするのか、隔離をどの水準で保証するのかについての記述が README に無い。関数一つごとに何個の入力を入れるのか、その値をどんな規則で作るのかも無い。導入に必要なものとして広く使われる CPU 模擬フレームワークと逆アセンブラの二つが書かれているが、そのうち CPU 模擬の側は自らを命令を真似る枠組みだと紹介するだけで、オペレーティングシステム層まで真似るのかはそのリポジトリの紹介文でも分けて書かれていない。

文書に無いということは処理していないという意味ではない。文書だけでは判定できないという意味である。正体の分からないコードを走らせる道具を実務に入れるとき、分けておくべき項目がまさにこの場所である。

同じさの層 - 「観測が重なる」と「同じ関数だ」

ここでこの方式の核心の問題に入る。二つの文は層が違う。

第一に、選んだ入力で観測した結果が重なる。これは観測についての言明である。何を入れて何が出たかについての事実であり、入れた値の範囲の中でだけ真である。第二に、二つの関数は同じ関数だ。これは正体についての言明である。あらゆる入力で同じく振る舞うという主張を含む。

前者は後者を含意しない。この隙間が誤検知の生まれる場所である。別々の二つの関数が選んだ入力で偶然同じ観測を出すことは珍しくない。README も純粋計算の関数を弱い場所として挙げ、バッファを読んで数を一つ返す二つのチェックサムは外から見ればほとんど同じだと書く。

関数 A   読み buf[0..n)   書き無し   4バイト整数を返す
関数 B   読み buf[0..n)   書き無し   4バイト整数を返す

外から観測される要約は同一である。
中で何を掛け何を足したかは外に残らない。

逆方向もある。同じ関数なのに観測条件が違って別物に見える場合である。最適化が強くかかった二つのビルドを突き合わせると、外に現れる振る舞い自体が薄くなる。インライン化で呼び出しが消え、分岐が条件無しの命令に畳まれれば、記録する効果が残らない。そして記録するものが少なければ、あらゆる関数が互いに似て見える。

誤検知と見逃しは対称ではない

誤検知 - 別のものを同じだと呼ぶとき

誤検知は静かである。間違った名前が付いた関数は、その後は名前が付いているという理由で二度と開かれない。その名前を前提に隣の関数が解釈され、その解釈を前提にまた別の判断が積まれる。一つの誤った判定がその上に載ったすべてを汚染するのに、汚染された成果物は見た目には完結している。自動で付けた名前が数千個ある状況では、この危険は個数に比例して大きくなる。

見逃し - 同じものを別だと呼ぶとき

見逃しはうるさくないが残る。脆弱なコード群と突き合わせる作業で一つの関数を取り逃がせば、その関数はそのまま残る。ただし見逃しには誤検知に無い性質がある。たいていは人が見直せば発見される。候補一覧の上位いくつかを人が眺める手順が付いていれば、見逃しのかなりの部分が回収される。README も正確にその点を突く。ある組で最上位の候補が正しい確率が 93% なのに、上位五つの中に正解が入っている確率は 96.6% だと書き、少ない検討予算がその隙間の大部分を埋めると付け加える。

ここから出る結論は単純である。誤検知と見逃しは同じ重さではない。人の検討が付く手順では見逃しは回収可能な失敗であり、誤検知は回収されない失敗である。逆に人の検討が無い自動手順ではこの非対称が消え、誤検知の費用だけが残る。

信頼度は「いくつの入力で一致したか」に掛かっている

一度の一致は偶然と区別がつかない。二つの関数を一個の入力で突き合わせて同じ結果を得たなら、それはほとんど情報ではない。入力を増やすほど偶然重なり続ける確率が減り、その分だけ一致が正体の証拠に近づく。判定の信頼度は関数の性質ではなく観測の量から出る。

そして観測の量は入力の個数だけで決まらない。関数が現すものをどれだけ持っているかのほうが大きな役割を果たす。引数を三つ受け取ってバッファを舐め条件によって違う値を書く関数は残す痕跡が多い。値をそのまま渡す一行の関数は残す痕跡が無い。README はこの性質を信号の量と呼び、信号の少ない関数は判定自体を保留すると書く。

同じ文書が公開した測定値はこの構造をそのまま見せる。zlib 1.3.1 の関数 84 個を対象に、同じソースを異なる条件でビルドした二つの成果物を突き合わせた値である。

突き合わせた二つのビルド最上位候補の正答率精度読み方
同じコンパイラ、最適化無しから 1 段階へ97.1%93.8%片方が最適化前なら振る舞いが豊かに残る
同じコンパイラ、最適化無しから 2 段階へ93.1%83.3%正答率は保たれるが確信の質が落ちる

識別方式別の強弱と失敗の形

ここまでの内容を一枚に畳むとこうなる。どの方式もあらゆる軸で勝つことはなく、それぞれ違う方向へ間違えるというのが要点である。

識別方式何に強いか何に弱いか主に現れる失敗
バイト列の照合同じビルド環境の同一ライブラリ、速度最適化・コンパイラ・アーキテクチャの交換すべて見逃し — 同じ関数なのに重ならず取り逃がす
制御フローグラフの比較命令水準の細かな変動、部分的な修正インライン化、ループ展開、分岐の畳み込み見逃し優勢 — 骨格が描き直されると取り逃がす
文字列・定数の目印目印のある関数への確定力目印の無い関数、目印の除去見逃し — 対象そのものが無く判定不能
振る舞い指紋最適化・コンパイラの交換、アーキテクチャ越え小さな関数、純粋計算、深い条件の先のコード誤検知 — 外から似て見えるものを同じと呼ぶ
振る舞い指紋 + 保留確信した判定の質回収率、判定を下せない関数の割合見逃しへの転嫁 — 曖昧なものに答えない
形と振る舞いの併用互いの失敗を覆う組み合わせ運用費用、二つの結果が食い違うときの判断不一致 — どちらを信じるかが改めて問題になる

一番下の二行が実務で実際に選ぶ場所である。保留を許せば確信したものの質は上がり、答えられない関数が増える。二系統を併走させれば失敗の形が互いに違うのでかなりの部分が覆われるが、二つの結果が食い違う関数が新たな検討対象として残る。どちらにせよ失敗は消えず、場所を移すだけである。移した先で誰がそれを受け取るのかを決めていなければ、移動は解決に見えるだけの先送りになる。

用途ごとに高くつく失敗が違う

同じ道具を使っても、何をしようとしているかによって基準線を別の場所に置くべきである。誤検知と見逃しのどちらが高くつくかが作業ごとに違うからだ。

用途誤検知が招く損見逃しが招く損どちらへ傾けるか
静的リンクされたライブラリ関数への命名間違った名前がその後の解釈全体を汚染する名前の無い関数が残る誤検知の抑制 — 曖昧なら名前を付けない
パッチ前後の比較による変更点の抽出変わっていない関数を変わったと見て検討が増える実際の変更を見過ごす見逃しの抑制 — 候補を広く取り人が絞る
重複コードの検出無関係な関数を絡めてしまう重複を見つけられず整理の機会を逃す均衡 — 候補一覧に回し判断は人がする
脆弱な版か修正済みの版かの選り分け安全なものを危険と見て対応が無駄になる危険なものがそのまま残る見逃しの抑制 — 取り逃がすほうがはるかに高い
大量の自動分類人が見ない分そのまま結果になる分類されない項目が積み上がる誤検知の抑制 — 検討が無ければ回収も無い

表の最後の行が前節の非対称と繋がる。人の検討が手順に入っているかどうかが、誤検知と見逃しの相対価格をひっくり返す。道具の設定値を決める前に決めるべきは手順の形である。

保留という三つ目の答え

同じと違うの間には言わないがある。この選択肢は失敗を減らさないが、失敗の種類を選べるようにしてくれる。README も確信の持てない組については推測する代わりに判定を控えると書き、だから精度が高く保たれる一方で同じ基準線での回収率は低いと説明する。

保留を手順に入れるとき分けておくとよいのは三つである。

  • 保留と見逃しを同じ欄に入れないこと — 答えていない関数は間違った答えではなく、まだ答えの無い関数である。二つを一つの数字に合わせると手順のどの部分を直すべきかが見えなくなる。
  • 保留した関数をどこへ送るか決めておくこと — 人が見る一覧へ回すか、別系統の判定へ渡すか、そのままにするかを先に決めなければ、保留はただの静かな抜け落ちになる。
  • 信号が少なくて保留したものと候補が拮抗して保留したものを区別すること — 前者は入力を増やしても良くならず、後者は観測を増やせば分かれる余地がある。対応が違う。

法と契約が課す条件

バイナリを解析する行為に一つの答えは付かない。同じ作業でも、どこでどんな目的で行われたかによって評価が分かれる。だからこの節は、やってよいとかやってはいけないという文を書かない。判断が掛かる地点だけを書く。

法と契約は互いに別の層である。プログラムの利用に関する規律は国ごとに条文が違い、どんな条件でどんな目的の解析が許されるかも併せて違う。そして法が定める範囲とは別に、そのプログラムを手に入れるときに同意した利用規約とライセンスが条件を別途課す。法の側が開いていても契約の側が閉じていることがあり、その逆もある。二つの層はそれぞれ確認すべきものであり、一方の結論を他方へ移して使うことはできない。

技術的保護手段はさらにもう一つの層である。アクセスや複製を統制するために掛けられた手段を無力化する行為は、解析そのものの適法性とは別に扱われる。その手段を越える手順はここに書かない。上で扱ったのは、すでに手元にあり、すでに実行できるコードについてこの関数とあの関数が同じかを判定する方法の性質であって、何かを開け放つ方法ではない。

実務ではこの境界はたいてい目的と記録の形で管理される。何のために解析するのか、成果物を誰にどんな形で残すのか、解析対象をどんな経路で確保したのかが残る。判断が必要な事案なら、法域と契約を並べて法務の確認を受けるのが手順である。

整理 - 五つの文に縮めると

  1. 「同じ関数を見つける」のが難しい理由は関数が難しいからではなく、同じソースが常に同じ機械語になるとは限らないからである。インライン化と並べ替えとレジスタ割り当てがバイトシグネチャを崩す。
  2. 形が揺れる場所で振る舞いは揺れにくい。しかし振る舞いを測るには実際に実行しなければならず、その決定は副作用・入力空間・環境依存・隔離コストという四つを請求する。
  3. 「選んだ入力で観測が重なる」と「同じ関数だ」は層の違う命題である。前者は後者を含意せず、その隙間が誤検知の生まれる場所である。
  4. 判定の信頼度はいくつの入力で一致したかとその関数が現すものをどれだけ持っているかから出る。両方が薄くなればどの方式もコイン投げに近づく。
  5. 誤検知と見逃しは同じ重さではなく、どちらが高くつくかは手順に人の検討が入っているかが決める。設定値より手順を先に決めるほうが順序に合う。

確かめられなかったこと

  • システムコールに到達したときの動作 — 模擬実行中にシステムコール命令へ到達したとき何をするのかについての記述が README に無い。外へ出る関数呼び出しを記録して飛ばすという記述だけがある。
  • 関数あたりの入力の個数と生成規則 — 引数の位置に適当な値を入れるという記述はあるが、何個入れるのかとその値をどんな規則で作るのかは README に書かれていない。この値が判定の信頼度を直接左右する。
  • 隔離の保証水準 — 誤ったポインタで実行が死なないという記述はあるが、それがどの範囲までの隔離を意味するのかは文書で分けて書かれていない。正体の分からないコードを扱う道具でこの項目は別途の評価が要る場所である。
  • 公開測定値の範囲外の性能 — 公開された数値は一つのライブラリの 84 個の関数を対象にしたものである。別の規模、別の言語で書かれたコード、別の最適化の組み合わせでの値は文書に無い。
  • バイト照合系の道具の内部仕様 — 広く使われるライブラリ関数識別技術の詳細仕様書はここでは開いていない。上の記述はその系統が共通して持つ性質に限ったものであり、特定の実装の仕様を移したものではない。
