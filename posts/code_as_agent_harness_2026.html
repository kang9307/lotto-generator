Code as Agent Harness — 코드를 AI 에이전트 실행 기반으로 보는 새로운 관점

UIUC·Meta·Stanford 102페이지 서베이가 제시한 패러다임: 코드는 결과물이 아니라 에이전트의 추론·행동·검증을 구조화하는 하네스다

2026-06-26 개발/인프라

서론: 코드의 역할이 뒤집혔다

지난 몇 년간 우리가 AI를 이야기하는 방식은 대체로 일정한 틀을 따랐다. LLM이 있고, 그 LLM이 코드를 생성한다. 프롬프트를 주면 함수가 나오고, 버그를 설명하면 수정 패치가 따라온다. 이 관계에서 코드는 항상 결과물이었다.

2026년 5월, UIUC·Meta·Stanford 공동 연구팀이 arXiv에 올린 102페이지 서베이(arXiv: 2605.18747)는 이 그림을 정면으로 뒤집는다. 서베이가 제시하는 핵심 명제는 간결하다. "에이전트 시스템에서 코드는 더 이상 단순한 생성 목표가 아니다. 코드는 에이전트가 추론하고, 행동하고, 환경을 모델링하고, 실행 기반 검증을 수행하는 운영 기반(operational substrate)으로 기능한다."

말이 추상적이라 와닿지 않을 수 있다. 이 글은 그 전환이 무엇을 의미하는지, 왜 중요한지, 그리고 실무에서 무엇이 달라지는지를 서베이 내용을 기반으로 본인의 시각으로 풀어낸다. 2026년 6월 기준 에이전트 AI 개발이 어디를 향하고 있는지를 이 서베이는 가장 체계적으로 정리한 문서 중 하나다.

1. 패러다임 전환: 코드는 출력이 아니라 기반이다

에이전트 시스템을 실제로 만들어 본 사람이라면 이미 직관적으로 알고 있는 것이 있다. LLM의 텍스트 출력 자체로는 아무것도 되지 않는다. 그것이 실제 환경에서 무언가를 하려면 반드시 실행 가능한 구조로 감싸여야 한다. 그 감싸는 구조가 바로 서베이가 말하는 하네스다.

서베이는 코드가 에이전트 시스템에서 수행하는 역할을 세 가지로 정리한다.

  • 추론을 실행 가능하게(Reasoning Executable): 코드는 모델의 내부 추론을 외부에서 검증 가능한 연산으로 드러낸다. 외부 인터프리터, 기호 논리 솔버, 실행 트레이스가 중간 단계를 점검하고 정제한다.
  • 행동을 프로그래밍 가능하게(Action Programmable): 코드는 고수준의 의도를 실제 실행 가능한 조작—도구 호출, 로봇 정책, GUI 명령—으로 변환한다. 구조화된 인터페이스를 통해 의도가 행동으로 착지한다.
  • 환경 상태를 검사 가능하게(Environment State Inspectable): 코드는 세계 상태, 전이 동역학, 피드백 신호를 리포지토리·시뮬레이터·테스트·실행 로그로 표현한다. 에이전트는 이것을 실행하고, 편집하고, 질의하며 환경을 이해한다.

이 세 가지가 맞물려 돌아갈 때 에이전트는 단순히 텍스트를 반환하는 것이 아니라 환경과 루프를 형성하는 시스템이 된다. 코드는 그 루프의 뼈대다.

2. 하네스의 해부: 3계층 구조

서베이는 에이전트 하네스를 세 개의 연결된 계층으로 분해한다. 이 구조를 이해하면 에이전트 시스템이 왜 지금의 형태로 설계되는지가 명확해진다.

2.1 하네스 인터페이스 — 코드가 에이전트와 환경을 연결하는 방식

1계층은 코드가 추론·행동·환경 모델링에서 인터페이스 역할을 하는 방식이다. 에이전트가 세계를 인식하고 그 인식을 행동으로 전환하는 접점이 여기에 있다. AGENTS.md 파일처럼 에이전트에게 무엇을 해야 하는지 알려주는 가이드(Guide), 그리고 타입 체커·린터·테스트 러너처럼 무엇이 잘못됐는지 알려주는 센서(Sensor)가 이 계층의 핵심 구성요소다.

흥미로운 것은 Claude Code의 CLAUDE.md나 OpenAI의 AGENTS.md가 이미 이 가이드 역할을 수행하고 있다는 점이다. 모델이 읽는 구조화된 지시 문서가 하네스의 일부로서 에이전트 행동을 제약하고 방향을 잡는다.

2.2 하네스 메커니즘 — 장기 실행을 가능하게 하는 엔진

2계층은 하네스가 실제로 작동하게 만드는 메커니즘이다. 서베이는 네 가지를 제시한다.

  • 계획(Planning): 장기 과제를 선형·구조 기반·탐색 기반·오케스트레이션 기반 전략으로 분해한다.
  • 메모리(Memory): 작업 상태(working state), 의미 지식, 경험 기록, 공유 상호작용 이력을 유지한다.
  • 도구 사용(Tool Use): 에이전트를 API, 검증 시스템, 실행 환경에 연결한다.
  • 피드백 제어 및 최적화(Control & Optimization): "계획-실행-검증(plan-execute-verify)" 루프를 런타임 피드백으로 반복적으로 수리하고 적응한다.

이 중 "계획-실행-검증" 루프는 특히 중요하다. 에이전트가 단순히 출력을 내는 게 아니라, 출력을 실행하고, 그 결과를 확인하고, 다음 행동을 결정하는 닫힌 루프를 코드가 구조화한다는 것이 핵심이다. 코드가 없으면 이 루프는 성립하지 않는다.

2.3 하네스 확장 — 단일 에이전트에서 멀티에이전트로

3계층은 하네스를 다중 에이전트 환경으로 확장하는 방식이다. 여러 에이전트(관리자·코더·리뷰어·테스터)가 역할을 분담할 때, 공유된 코드 아티팩트가 조정(coordination)의 기반이 된다. 에이전트들이 같은 리포지토리를 보고, 같은 테스트 결과를 공유하고, 동일한 상태를 기준으로 행동을 결정한다. 코드는 여기서 에이전트 간 통신 매체이자 공유 진실의 근거가 된다.

3. 하네스의 4가지 속성: 무엇이 좋은 하네스를 만드는가

서베이는 에이전트 하네스가 갖춰야 할 네 가지 속성을 제시한다. 이것은 하네스 설계의 요건 명세로 볼 수 있다.

속성의미실무 예시
실행 가능성(Executable)의도된 결과를 형식적으로 검증 가능테스트 러너, 코드 인터프리터
검사 가능성(Inspectable)구조화된 트레이스가 중간 계산을 노출실행 로그, 단계별 트레이스
상태 유지(Stateful)태스크 진행 상태를 지속적으로 표현리포지토리 상태, 메모리 구조
통제 가능성(Governed)권한 경계·샌드박스·안전 제약 적용도구 권한 제한, 샌드박스 실행

이 네 속성은 서로 독립적이지 않다. 실행 가능성이 없으면 검증이 불가능하고, 상태 유지가 없으면 장기 과제가 성립하지 않고, 통제 가능성이 없으면 에이전트가 의도하지 않은 행동을 하더라도 막을 방법이 없다. 하네스는 이 네 가지를 함께 갖춰야 신뢰 가능한 에이전트 시스템이 된다.

4. 하네스 엔지니어링의 부상: "에이전트 = 모델 + 하네스"

서베이와 함께 2026년에 빠르게 부상한 개념이 하네스 엔지니어링(Harness Engineering)이다. 공식은 단순하다. 에이전트 = 모델 + 하네스. 모델이 뇌라면 하네스는 그 뇌가 작동하는 신체이자 환경이다.

이 관점이 실무에 가져오는 변화는 생각보다 크다. 기존 접근은 "더 좋은 모델을 쓰면 에이전트가 더 잘 동작한다"는 모델 중심 사고였다. 하네스 엔지니어링은 여기에 도전한다. 모델 가중치를 고정한 채로 하네스—시스템 프롬프트, 도구 정의, 미들웨어, 검증 루프, 메모리 구조, 장기 기억—를 발전시키는 것만으로 에이전트 성능을 크게 끌어올릴 수 있다는 것이다.

실증이 있다. Agentic Harness Engineering(AHE) 연구는 기반 모델을 고정한 상태에서 하네스만 관찰 기반으로 진화시켜 Terminal-Bench 2에서 84.7%라는 성과를 달성했다. GPT-5.4를 10번 반복 개선으로 69.7%에서 77.0%로 끌어올렸다. 하네스 개선이 모델 업그레이드를 대체하거나 보완할 수 있다는 실험적 증거다.

본인이 이 점에서 특히 주목하는 것은 하네스의 가역성과 이식성이다. 잘 설계된 하네스는 모델을 교체해도 대부분의 행동이 유지된다. 이것은 특정 모델 벤더에 대한 의존도를 낮추는 구조적 수단이기도 하다. 모델이 아니라 하네스에 투자할수록, 에이전트 시스템의 포터빌리티가 올라간다.

5. 코드의 새로운 의미: 도구 정의, AGENTS.md, 실행 트레이스

하네스 관점에서 "코드"의 범위는 우리가 흔히 생각하는 것보다 훨씬 넓다. 서베이는 코드를 "실행 가능하거나 기계가 확인할 수 있는 아티팩트"로 정의하며, 다음을 포함한다.

  • 프로그램·스크립트·공식 명세
  • 증명 스크립트·API 스키마·도구 정의
  • 테스트·리포지토리·시뮬레이터·설정 파일
  • 실행 트레이스·로그 같은 코드 인접 아티팩트
  • AGENTS.md 같은 가이드 문서

이 목록을 보면 흥미로운 것이 보인다. 도구 정의(tool definition)가 코드의 일부다. 에이전트에게 어떤 도구를 어떻게 사용할 수 있는지 알려주는 스키마 자체가 하네스의 핵심 구성요소다. 서베이가 인용하는 2025년 실증 연구는 이것이 얼마나 중요한지를 보여준다. 도구 수가 10개일 때 완수하는 작업을 107개 도구 환경에서는 사실상 실패한다는 비선형 성능 하강이 관찰됐다. 하네스 설계에서 도구 노출 방식이 에이전트 성능을 결정한다.

AGENTS.md, CLAUDE.md 같은 가이드 문서도 마찬가지다. 이것은 단순한 설명문이 아니다. 에이전트가 실행 시점에 읽고 행동 방침을 결정하는, 코드와 동등한 지위를 갖는 실행 기반이다. Claude Code의 소스에서 확인됐듯 이 파일들은 시스템 프롬프트와 함께 "사용자 콘텐츠"로 조립되어 에이전트에 전달된다. 주석이 아니라 행동의 제약이다.

6. 장기 실행 에이전트와 하네스의 역할

에이전트 AI에서 "장기 실행(long-horizon execution)"은 아직 풀리지 않은 가장 어려운 문제 중 하나다. 단발 질의는 인상적으로 잘 동작한다. 하지만 수십 스텝에 걸쳐 계획을 세우고, 실행하고, 중간 결과를 반영하고, 목표를 유지하는 에이전트는 여전히 불안정하다.

하네스는 이 문제에 구조적 해법을 제시한다. 첫째, 메모리 구조가 에이전트가 "지금 어디쯤 왔는지"를 잃지 않도록 한다. 둘째, 계획 레이어가 긴 과제를 실행 가능한 단위로 분해한다. 셋째, 검증 루프가 중간 결과가 올바른지 확인하고 경로를 수정한다. 이 세 가지가 코드로 구현된 하네스 안에 있을 때, 에이전트는 자기 자신을 구조적으로 교정하면서 진행할 수 있다.

서베이가 제시하는 이 그림에서 본인이 강조하고 싶은 것은 검증의 위치다. 검증은 최종 출력을 사람이 확인하는 사후 과정이 아니다. 하네스 안에 내장된, 실행 루프의 일부다. 테스트가 통과하지 않으면 에이전트는 진행하지 않는다. 이것이 코드 하네스가 제공하는 자기 수정 능력의 핵심이다.

7. 멀티에이전트 시스템과 공유 코드 기반

단일 에이전트를 넘어 여러 에이전트가 협력하는 시스템에서 하네스의 역할은 더욱 중요해진다. 관리자 에이전트, 코딩 에이전트, 리뷰 에이전트, 테스트 에이전트가 분업할 때, 이들을 조율하는 것은 자연어 메시지만이 아니다. 공유된 리포지토리 상태, 동일한 테스트 스위트, 공통의 도구 정의가 그 조율의 구조적 기반이다.

이것이 서베이가 말하는 "공유 코드 아티팩트(shared code artifacts)"다. 멀티에이전트 시스템에서 일관된 상태를 유지하려면 에이전트들이 동일한 코드 기반을 기준으로 행동해야 한다. 그러지 않으면 한 에이전트가 고친 것을 다른 에이전트가 덮어쓰거나, 충돌하는 가정 위에서 각자 행동하는 문제가 생긴다. 코드가 에이전트 간 진실의 단일 소스(single source of truth)가 되는 것이다.

8. 아직 풀리지 않은 문제들: 서베이가 제시하는 과제

서베이는 패러다임을 제시하는 동시에 아직 해결되지 않은 도전 과제도 솔직하게 나열한다. 이 목록은 2026년 기준 에이전트 AI 연구가 집중해야 할 영역을 가리킨다.

  1. 최종 성공 이상의 평가: 하네스 중간 단계의 신뢰성을 측정하는 지표가 아직 부족하다.
  2. 불완전한 피드백 하에서의 검증: 완전한 오라클(oracle) 없이 의미적 올바름을 어떻게 확인할 것인가.
  3. 회귀 없는 하네스 진화: 하네스를 개선할 때 기존 능력이 저하되지 않으려면 어떻게 해야 하는가.
  4. 멀티에이전트 간 공유 상태 일관성: 여러 에이전트가 동시에 수정하는 환경에서 트랜잭션 의미론을 어떻게 보장할 것인가.
  5. 안전 중요 작업에서의 인간 감시: 실행 가능한 하네스 상태로서 책임 소재를 어떻게 구현할 것인가.
  6. 멀티모달 확장: 비전·로보틱스·지각 등 비-코드 영역으로 하네스를 어떻게 확장할 것인가.

이 과제들은 하네스 패러다임의 한계가 아니라 다음 단계의 연구 지도다. 특히 불완전한 피드백 하에서의 검증 문제는, 현실 세계 에이전트가 이상적인 테스트 환경 밖에서 어떻게 자기 행동을 확인하느냐는 매우 실용적인 문제와 직결된다.

9. 실무에서의 함의: 무엇이 달라져야 하는가

Code as Agent Harness 서베이는 학술적 틀이지만, 본인이 읽는 실무적 함의는 구체적이다.

9.1 하네스 설계를 모델 선택보다 먼저 하라

에이전트 시스템을 구축할 때 가장 먼저 하는 질문이 "어느 모델을 쓸까"인 경우가 많다. 하지만 하네스 관점에서는 이 질문의 순서가 뒤집혀야 한다. 에이전트가 어떤 도구에 접근할 수 있는가, 어떤 검증 루프가 있는가, 어떤 메모리 구조를 갖는가를 먼저 설계하고, 모델은 그 하네스에 맞는 것을 선택하는 것이 더 옳다. 하네스가 바뀌면 같은 모델도 완전히 다른 에이전트가 된다.

9.2 AGENTS.md와 도구 정의를 코드처럼 관리하라

AGENTS.md, 시스템 프롬프트, 도구 정의는 설명 문서가 아니다. 에이전트 행동을 결정하는 실행 가능한 명세다. 버전 관리하고, 테스트하고, 리뷰 프로세스를 거쳐야 한다. 하네스 코드가 변경되면 에이전트 행동이 변한다는 것을 팀 전체가 인식해야 한다.

9.3 도구 수보다 도구 품질에 집중하라

도구 수 107개에서 비선형 성능 하강이 관찰됐다는 실증은 직관과 반대다. 더 많은 도구를 줄수록 에이전트가 더 많은 일을 할 것 같지만, 실제로는 선택지가 너무 많아질수록 에이전트가 길을 잃는다. 잘 정의되고 명확한 소수의 도구가 막연하게 많은 도구보다 낫다. 하네스 설계에서 도구 정리(tool hygiene)가 성능의 핵심 변수다.

결론: 하네스 엔지니어가 에이전트 시대의 인프라 설계자다

Code as Agent Harness 서베이가 그리는 세계는, 코드의 위상이 높아진 세계가 아니라 코드의 역할이 바뀐 세계다. 에이전트가 코드를 생성하는 시대에, 그 코드를 생성하는 에이전트를 감싸고 지탱하는 구조 자체가 코드로 이뤄진다. 코드는 결과물이면서 동시에 기반이다.

하네스 엔지니어링이라는 규율의 부상은 이 변화를 실무로 내려온 형태다. 에이전트 시스템의 성능은 모델 단독으로 결정되지 않는다. 모델을 감싸는 하네스—도구 정의, 가이드 문서, 검증 루프, 메모리 구조, 권한 경계—가 함께 결정한다. 이 하네스를 설계하고 발전시키는 일이 에이전트 시대의 인프라 엔지니어링이다.

2026년 6월 기준, 에이전트 AI는 여전히 빠르게 변하고 있다. 하지만 이 서베이가 제시하는 프레임은 변화의 방향을 읽는 데 유효한 나침반이다. 코드를 어떻게 짜느냐만큼, 코드로 무엇을 감싸느냐가 중요한 시대가 왔다.
