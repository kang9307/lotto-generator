まだEmacsを使っている人はいるの? — 50年エディタの生命力

VS Code・Cursor・AIエディタが席巻する2026年でもEmacsを選ぶ理由 — 拡張性・org-mode・ハッカー文化・AI統合を分析する

2026-06-22 開発・インフラ

はじめに：議論を生んだ一つの質問

GeekNewsに投稿されたトピック「まだEmacsを使っている人はいるの?」が29ポイントを獲得し、活発な議論を呼んだ。VS Codeが開発者の75.9%を占め、CursorやClaude CodeのようなAIネイティブエディタが急成長している2026年6月の時点で、50年前のテキストエディタがこれほどの反響を得たことは、単なる懐古趣味では説明できない。

EmacsはRichard StallmanがMIT AIラボで1976年に作った。GNU Emacsとして1984年に再スタートし、以来ずっと開発が続いている。2026年6月時点の安定版はGNU Emacs 30.2（2025年8月14日リリース）だ。50年前のソフトウェアが新バージョンを出し続け、新たに入門する開発者がいる。なぜか。

この記事はEmacsの称賛でも否定でもない。「なぜこのエディタがまだ生きているのか」を真剣に分析し、AIコーディング時代のエディタ選択が何を意味するかを考える。

1. 50年生き延びた理由 — エディタではなくプラットフォーム

1.1 Lispインタープリタとしてのエディタ

Emacsをテキストエディタと呼ぶのはすでにやや不正確だ。正確にはEmacs Lispインタープリタの上に構築されたテキスト編集環境である。この違いが50年の生存力の核心だ。

VS CodeはJSON設定と拡張機能で動作を変えられるが、エディタの核心的な振る舞い自体を書き換えることはできない。Emacsは違う。カーソルが動くとき、キーを押すとき、ファイルを保存するとき — すべてのイベントにLisp関数を差し込める。エディタのあらゆる動作をプログラムで置き換えるか拡張できる。「Emacsはプラットフォーム」という意味はここにある。使用者が望む形にエディタ自体を設計し直せるのだ。

この構造から、通常の拡張機能の域を超えたものが生まれた。Magit（Gitクライアント）、mu4e（メールクライアント）、elfeed（RSSリーダー）、dired（ファイルマネージャ）、org-mode（生産性システム）。これらは別のアプリケーションに近く、統一されたキーバインド体系とバッファモデルでつながっている。

1.2 OSのように使う人たち

GeekNewsの議論で、あるユーザーは自分のワークフローをこう説明した。Git → Magit、メール → mu4e、RSS → elfeed、ノート・TODO・カレンダー → org-mode、ファイル管理 → dired。ブラウザ以外のほぼすべての作業がEmacs内で完結している。ここまでくるとEmacsはエディタではなく個人コンピューティング環境そのものだ。

そういうユーザーに「VS Codeに乗り換えろ」というのは単純な道具の交換ではない。数年かけて積み上げた設定、キーバインドの筋肉記憶、org-modeのデータベース、カスタムワークフロー全体を捨てることになる。乗り換えコストが極めて高い。これが根強いロイヤルティの源であり、深く投資した人が居続ける理由だ。

2. org-mode — 代替不可能なキラーアプリ

2.1 org-modeとは何か

Emacsユーザーに最大の魅力を聞くと、ほぼ必ずorg-modeが挙がる。org-modeはBastien Guerryらコミュニティが数十年かけて育てたプレーンテキストベースの生産性システムだ。機能を列挙するとこうなる。

  • 構造化ノート作成（見出し・リンク・表）
  • プロジェクト・タスク管理（TODOステート・優先度・タグ）
  • 時間追跡（CLOCK IN/OUTの自動記録）
  • カレンダー・アジェンダビュー（期限・繰り返しスケジュール）
  • コードブロック実行（org-babel — Python・Shell・SQL等）
  • 多形式エクスポート（HTML・PDF・LaTeX・Markdown・EPUB）

これらすべてが単一のプレーンテキストファイル体系で動く。テキストなのでGitでバージョン管理でき、grepで検索でき、どのエディタでも開ける。しかしEmacsのorg-modeで開いたときだけ、すべての機能が生きてくる。

2.2 なぜ代替できないのか

Notion、Obsidian、Roam Research、Logseq — いずれも優れたツールだ。しかしそれぞれorg-modeの一部を実装しているに過ぎない。ドキュメント内でコードを実行して結果を埋め込む（org-babel）、アジェンダ・CLOCK計測・タスク管理を一体で持つ、そしてEmacs Lispですべてをプログラム可能にする — この三つを同時に持つツールはまだない。

開発者には特にorg-babelが響く。Pythonでデータを取得し、表にまとめ、LaTeXドキュメントとしてエクスポートする一連の流れが、一つのorgファイルの中で再現可能に記録される。これはノートアプリではなく文芸的プログラミング（literate programming）の実用的な実装だ。

3. 学習曲線と報酬 — 正直な計算

3.1 なぜ難しいのか

Emacsの学習曲線が悪名高いのには理由がある。第一に、キーバインド体系が現代の慣習と異なる。C-x C-sで保存、C-x C-fでファイルを開く — 数十年前に設計された体系だ。Ctrl+S・Ctrl+Oに慣れた手は最初に反乱する。第二に、設定がLispだ。JSONやYAMLで設定できる現代ツールと違い、Emacs設定はEmacs Lispのコードを書くことになる。習熟するほど強力になるが、入門の壁は高い。第三に、「正しい始め方」が多すぎる。素のEmacs、Doom Emacs、Spacemacs、フルスクラッチ — どこから始めればいいかわからない。

3.2 Doom EmacsとSpacemacsが変えたこと

この入門の壁を下げたのがプリセット配布版だ。Doom EmacsはVimスタイルのキーバインド（Evilモード）と最適化されたパッケージ構成を提供する。SpacemacsはVimとEmacsをレイヤーベースで統合する。どちらを使っても、最初からLispを書かなくていい。Vimユーザーなら親しみのある手の動きのままEmacs生態系に入れる。

2026年にはAIの助けも加わった。gptelでLLMにEmacs Lispの設定方法を聞けば、かつてはメーリングリストを掘り返していた作業が対話形式になる。カスタマイズの壁が大幅に下がった。

3.3 投資対効果の計算

ある開発者の試算が現実的な基準を与える。Emacsで1日15分節約すれば、年間で約65時間（約3日）が手に入る。10年では30日だ。過大な数字ではない。Emacsに習熟したユーザーは、ファイル探索・検索・置換・バッファ切り替え・Git操作のすべてをキーボードだけでこなす。ただしこの30日の節約を実現するには、最初に100時間以上の投資が必要だ。長いキャリアを見据えた開発者には合う計算だが、今すぐ納品が必要な場面には向かない戦略だ。

4. ハッカー文化と哲学 — Emacsが象徴するもの

4.1 フリーソフトウェア運動の最初のキラーアプリ

GNU Emacsは単なるソフトウェアではない。Richard StallmanがGNUプロジェクトを1983年に立ち上げたとき最初に作ったツールだ。フリーソフトウェアが商用ソフトウェアに匹敵できることを最初に証明した事例とされている。Stallmanは1970年代のMIT AIラボのハッカー文化 — ソースを公開し、誰でも修正でき、ソフトウェアは共有されるべきという哲学 — の生き残りと自らを表現した。GNU EmacsはそのGPL哲学の具現化だ。

Emacsを使うことにはこの歴史と哲学が伴う。Emacsコミュニティが独特の結束力を持つのはそのためだ。単にエディタを使うのではなく、特定の技術倫理に同意することでもある。

4.2 キーボードの自律性とリモートワーク

Emacsユーザーが共通して強調するのはマウスなしで作業できることだ。これは好みの問題ではなく生産性の問題だ。手がキーボードからマウスへ、マウスからキーボードへ移動する時間は、繰り返されると積もる。Emacsのキーバインドはその切り替えを最小化するよう設計されている。熟練ユーザーは「キーボードが思考の延長になる」と表現する。

この自律性はSSH環境で特に際立つ。リモートサーバーへのSSH接続でも、GUIなしにEmacsは完全な機能を発揮する。VS CodeのRemote SSHがこれを大幅に補完したが、接続が不安定だったりリソースが制限された環境では、ターミナルネイティブのエディタが依然として有利だ。インフラエンジニアやシステム管理者がリモートサーバーでEmacsを常時稼働させている理由だ。

5. 現在の利用状況 — 正直な数字

5.1 市場シェアの現実

数字は明確だ。Stack Overflow 2025開発者調査でVS Codeは75.9%だ。EmacsはLinuxQuestionsのポールで8〜9%程度 — Vim/Neovimの37〜38%にも遠く及ばない。AIネイティブエディタでは、Cursorが17.9%、Claude Codeが9.7%を初年度に獲得したのに対し、Emacsは統計に現れないほど小さい。人気指標でEmacsを擁護する方法はない。

5.2 活発な開発が別の物語を語る

開発活動は別の指標だ。GNU Emacs 30.2は2025年8月にリリースされ、現代化への投資を示す変更が含まれている。

  • ネイティブコンパイルをデフォルト化：libgccjitでEmacs LispをAOTコンパイル、MagitとOrg-modeの実行速度が大幅向上
  • which-keyを内蔵：サードパーティパッケージなしでキーバインドヒントを表示
  • EditorConfigの内蔵サポート
  • Tree-Sitterモードの拡張：Elixir・HEEx・HTML・Lua・PHP等の新言語モード
  • Androidネイティブサポート（タッチスクリーン・仮想キーボード）
  • JSONパース・サブプロセス処理のパフォーマンス改善

これはレガシーを惰性で保守しているプロジェクトではない。以前はサードパーティパッケージが必要だった機能を内蔵し、新しいプラットフォームへ拡張している。

6. AIコーディング時代のEmacs

6.1 AI統合のエコシステム

AIコーディングツールがエディタ選択の決定的な変数になった2026年、Emacsの対応は予想以上に堅実だ。

  • gptel：Claude・GPT・Gemini・Ollamaなどを任意のEmacsバッファで対話形式で使えるLLMクライアント。MCP（Model Context Protocol）統合も対応。バージョン0.9からAnthropicバックエンドをネイティブサポート。
  • copilot.el：GitHub Copilot言語サーバーに直接接続し、インラインゴーストテキスト補完を提供。2025年初頭に公式Nodeパッケージベースにアップグレード。
  • ellama：Ollama等のローカルLLMを使ったコード要約・リファクタリング・翻訳などのタスク特化コマンド。
  • aider.el：AIペアプログラミングツールAiderのEmacs統合。
  • Claude Code：ターミナルベースでエディタ無関係。EmacsユーザーはターミナルでClaude Codeを使い、結果をEmacsバッファで確認する。

Emacsの「何でも拡張できる」という特性はAI統合にも通じる。gptelとorg-babelを組み合わせてAIの回答をorgドキュメントに自動記録したり、AIが生成したコードをバッファ内で即実行したりするワークフローは、硬直した環境では再現しにくい。

6.2 AIネイティブエディタには及ばない部分

正直に言えば、インラインAIコーディング体験ではCursorやCopilot統合のVS CodeがEmacsより滑らかだ。CursorはAIを核心に設計されており、マルチファイルコンテキスト・コードベース全体への質問・即時適用が一つの環境で完結する。EmacsのAIツール群は強力だが組み立てが必要だ。「完成品」ではなく「パーツを組み合わせるもの」に近い。これはEmacs哲学に一致するが、設定なしで最高のAIコーディング体験を求めるユーザーには本物のトレードオフだ。

7. 2026年にEmacsを選ぶべき人・選ばないほうがいい人

7.1 Emacsが向いている場合

  • 知識をコードのように管理したい → org-mode
  • エディタの動作をLispで完全に設計し直したい → Emacs Lispの拡張性
  • SSHやリソース制約の多い環境で作業する
  • 数十年間同じツールを維持したい
  • フリーソフトウェア哲学（GNU GPL）に共感する

7.2 Emacsが向いていない場合

  • チームがVS Codeに統一されており共同作業拡張が重要
  • 最も滑らかなAIインライン体験をすぐに使いたい → Cursorが適切
  • 今すぐ生産的にならなければならない → 学習曲線が負担
  • GUIで設定を管理したい → VS CodeのGUI設定が合っている

7.3 二項対立ではなくスペクトラム

「エディタ戦争はVS Codeの圧勝で終わった」とよく言われる。しかしそれは「Emacsが間違っていた」という意味ではない。特定の仕事に手道具を選ぶ職人が「非効率」と断じられないのと同じで、特定の作業と特定の開発者にはその選択が最適だ。Emacsは「一生学ぶエディタ」という体験を提供する。完成品を受け取るのではなく、自分が望む道具を作り続けるプロセスだ。そのプロセスを楽しめる人にとって、Emacsは生産性ツールではなくプログラミングの技の延長だ。

8. おわりに — 50年後もEmacsを使う人はいる

GeekNewsの問いに答えるなら：そうだ、まだEmacsを使っている人はいる。そしてこれからもいるだろう。理由は人気ではない。Emacsが満たす特定のニーズが消えないからだ — org-modeで知識をプログラム可能なテキストとして管理すること、Emacs Lispで自分の思考に合わせてエディタを再設計すること、どんな環境でも同じキーボード体系で作業すること。

2026年6月時点で、GNU Emacs 30.2は活発に開発中であり、新たに入門する開発者がおり、AI統合パッケージが継続的にリリースされている。50年生き延びたエディタの生命力は市場シェアからではない。代替不可能な機能と無制限のカスタマイズ可能性から来ている。それは、次世代のAIエディタがCursorを時代遅れに見せる頃も、まだ立っていられるだけの基盤だ。
