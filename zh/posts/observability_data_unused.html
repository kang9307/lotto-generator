收集的可观测性数据为何无人查看 - 日志、指标与追踪回答的是不同问题

接入埋点只做一次，查看却是每天的事

2026年8月23日 开发/基础设施

引言：仪表盘有四十块，故障时只打开三块

把可观测性工具跑了几年的团队，大都有同一幅景象。仪表盘目录里躺着几十个页面，其中大多数标题的含义只有做它的人清楚。真出故障时，没有人去打开那个目录。大家各自打开自己记得的三块，剩下的查询当场重写。

这件事很奇怪。数据都在。采集器在跑，存储账单每月照付，接入埋点的工作耗掉了好几个季度的人力。可到了真正需要的那一刻，攒好的东西没人用，反而当场重做一遍。

面对这道落差，常见的诊断要么是工具太弱，要么是大家太懒。两种说法都不对。这不是个人习惯问题，而是因为收集和使用的成本结构不同而必然产生的偏移。接入埋点这件事有终点，查看这件事没有终点。当只有有终点的一侧才被分配预算和绩效指标时，结果从一开始就定下了。

恰好有一篇文章从旁边戳到了这个主题：用仓库数据去追问 OpenTelemetry 为什么交付缓慢的 OTel isn't going well, and I made a spreadsheet about it。那篇讲的是标准迟迟才到位。本文看的是它下面一层：标准已经到位、数据也都收上来了，为什么还是没人打开。

本文不涉及的内容。 具体厂商的计费结构和产品对比不在范围内。哪种存储引擎更适合日志，写在 ClickHouse为何在可观测性之争中领先；免费组合能走多远，写在 不要自己造监控轮子。这里只看选型之前的那一步，也就是收什么、为什么收、什么时候真正去打开它。

1. 原文实际数了什么 - 瓶颈并不是语义约定

先把引发本文的那篇文章简短而公允地转述一遍。作者 Mat Duggan 针对 OpenTelemetry 多个语言 SDK 仓库以及语义约定仓库，收集了24 个月的合并记录，并把 Prometheus 和 Envoy 放在旁边作为对照组。他想数清两件事：合并到底是谁在做，以及评审卡在哪里。

结果非常鲜明。在多个语言 SDK 中，大部分合并由一个人完成。

以上数字是 Mat Duggan 在自己博客上公开的统计。样本为各仓库最近 24 个月已合并的 PR，统计时点为 2026 年 8 月。作者本人写明是用临时拼凑的 Python 脚本抓取的，因此更适合当作量级差异的指示，而不是精确统计。

最有意思的一段，是作者亲手推翻了自己的假设。他起初以为瓶颈是语义约定的讨论，实际耗时最多的却是单个功能的公开 API 审批评审。他列出的最慢案例中，语义约定仓库的一个 PR 耗时 277.5 天、经过 115 次评审，Python SDK 的一个 PR 耗时 361.1 天、经过 19 次评审。队伍之所以拉长，不是评审不足，而是拥有批准权限的人太少。

作者提出了三条建议。第一条是在实验阶段与稳定阶段之间设一个有时长保证的 Beta 层级，他举的例子是十二个月。第二条是如实公开各语言的维护水平，理由是让所有语言看起来水平相同会误导使用者。第三条是稳定性承诺、支持范围和人手三者之中必须调整其一，三样都想保住，速度就被拖死了。

到这里是原文。这是一份成立的诊断，第二条建议从使用者的位置看尤其有价值。但这份分析站的位置是供给侧，讲的是标准何时交付什么。使用者每天撞上的问题在它下面一层：标准到位了，埋点也接上了，可这样收上来的数据打不开。

2. 三个轴不是同一样东西的三种形态 - 它们问的问题不同

介绍可观测性的文章通常把日志、指标、追踪称为三大支柱。这个说法会带来一个误解：听上去像是同一批事实被存成了三种格式。这样理解下去，自然就会得出反正都在、随便打开一个都行的结论。实际并非如此。

三者不同之处不在装了什么，而在问了什么。 每个轴的数据形状都为回答某一类问题而预先固定，而这个形状会挡住别的问题。

  • 指标是按事先约定的维度预先聚合好的数值。写入时单个事件就已经消失了。因此它回答现在是否正常、从何时开始变坏、相对基线坏了多少
  • 日志是对单个事件的描述。可以挂任意字段，能把一次发生完整还原。因此它回答这次请求为什么失败、当时传进来的是什么值
  • 追踪记录一次请求走过的路径与各段耗时，因果关系跨越服务边界连着。因此它回答时间消耗在哪里、哪一跳慢

这个差别不是口味问题，而是成本曲线的差别。只要时间序列条数不变，流量涨十倍指标的存储成本几乎不动。日志随流量成正比增长。追踪同样成正比，然后靠采样削掉一部分。三个轴的保留期本来就没有理由相同。

轴回答的问题存储单位成本膨胀的来源不能用这个轴做的事
指标现在是否正常、从何时起时间序列（标签组合）标签取值的种类数还原单次请求
日志这一件为什么这样单条事件请求量与行数常态化的比例与趋势聚合
追踪时间消耗在哪一跳Span（按请求）请求量与 Span 深度统计准确的次数

2.1 什么时候用哪一个

是有顺序的。谷歌 SRE 手册把监控要回答的问题分成什么坏了和为什么两项。前者是症状，后者是原因，书里说这个区分是写出信号最大、噪声最小的监控时最重要的分岔。把这个区分直接铺到三个轴上，顺序就出来了。

指标在最前。 什么坏了、用户是否真的受到影响，都在这里判断。同一本书提出的四个黄金信号，也就是延迟、流量、错误和饱和度，就落在这一站。接下来是追踪。 确认影响范围之后，收窄到时间消耗在哪一段。在跨多个服务的请求里跳过这一步，最后就会去翻别人服务的日志。日志放在最后。 把区间收窄之后，再打开里面的单个事件。一上来就进日志，只会在不知道自己在找什么的情况下不断换关键词。

这个顺序同时也是成本顺序。只在收窄后的时间窗内打开日志，这个习惯本身就是查询账单的削减。反过来，从日志开始的习惯意味着每次都用最宽的范围去扫最贵的那个轴。

2.2 选错轴，错误答案会悄无声息地出现

把轴搞混，一般会出现两种结果之一：成本爆炸，或者更糟的错误答案看起来很像那么回事。

成本爆炸这一侧容易认出来。把日志当聚合轴，每次查询都变成全量扫描；一旦某块仪表盘开始每五分钟扫一天的日志，这个页面就成了团队里最贵的一块。把请求标识或用户标识塞进指标标签也是同一个故事：一开始跑得挺好，等到某天流量上来，先倒下的是采集器。

真正危险的是另一侧。用追踪去数次数不会在任何地方留下警告。追踪大多是采样送达的，因此数失败次数会得到远小于实际的结果，而页面上并没有任何提示。数字悄悄错了，判断却基于这个数字做出。

3. 埋点只做一次，查看是每天的事

接下来是正题。数据没人看，原因不在于谁勤快与否，而在于这两件事的性质不同。

接入埋点这件事有终点。工单打开，PR 提上去，评审跟进，合并之后关闭。它能被算作产出，也能写进季度目标。查看则没有终点。昨天看过的图表今天还要再看一遍，什么都没发生时就不会留下任何产物。因为看得仔细而避免了一次事故的那一天，是不会被记录下来的一天。

组织会把资源投到有终点的工作上。于是时间一长就是这个形状：收集量单调上升，查看量被人数锁住而停滞。两条线之间的距离，就是那些收上来却没人看的数据。

同样的不对称也留在代码里。加埋点要过评审，去掉埋点没人看，所以实际上没有回退挡。新服务复制现有模板，而模板里装着上一个团队当初需要的埋点。要给删除找依据，就得先拿出没人用的证据，而收集这份证据本身又是一项工作。最后固化下来的结构是：新增由个人决定，删除需要共识。

3.1 仪表盘越多越没人看的结构

同样的不对称在页面上表现得更严重。仪表盘靠一个复制按钮就能增加，创建时不需要审批。问题出在之后。

  • 名字不解释自己。 页面标题装着创建者当天的上下文，半年后对别人来说就成了必须打开才知道的名字
  • 一块坏掉的面板会削掉整页的信任。 指标改名或标签消失留下一张空图，连带周围面板上的数字也一起被怀疑。故障中，可疑的页面不会被打开
  • 重复会拖慢判断。 名字相近的页面有三块，各自挂着不同的时间范围和不同的过滤条件，第一笔时间先花在确认哪一块才对
  • 没有归属人。 创建者换了团队，页面就退出了维护范围，却不会退出列表

正面写下这个问题的公开文档，是谷歌 SRE 手册。它的原话是：已经在采集、但没有出现在任何仪表盘、也没有被任何告警使用的信号，属于可以删除的候选。 同一章还说，越是能抓住真实事故的规则，越应该简单、可预测、可信赖，并且警告监控本身可能变成脆弱、难改、又要人不断维护的负担。

3.2 于是真正活下来的是什么

在现场活得久的不是仪表盘，而是告警。理由很简单：告警错了会疼。误报会把人叫醒，漏报会让事故变大。所以它会被照料。仪表盘错了谁也不疼，无非是不再被打开而已。

所以活得久的页面，大多是从告警里链接过去的页面。只要存在被使用的路径，坏掉就会立刻被发现。嵌在运行手册里的查询同样长寿：使用场景一旦被写进文档，它当天就成了维护对象。反过来，因为觉得说不定哪天要看而建的页面无一例外被闲置，因为看它的契机从来没有被定义过。

更大的问题是，新加入的人根本看不出这个区别。活着的页面和死掉的页面混在同一份列表里，该信哪一个只能靠问人来学。入职成本悄悄上升的地方就在这里。

4. 标准解决什么，不解决什么

这里需要把标准的地界划清楚，因为 OpenTelemetry 真正解决的问题和它本来就不负责的问题，常常被混在一起讨论。

标准解决的是埋点与后端之间的耦合。以前换一家可观测性厂商，等于把应用代码重写一遍。现在埋点是写在标准 API 上的，传输走统一协议，所以更换后端大体降级成了配置问题。库自带埋点时，应用侧什么都不用写。跨语言边界的上下文传播也是标准的活。

标准不解决的是它上面的那一整层。

  • 测什么属于领域知识。支付失败按什么粒度计数、重试算不算独立事件，约定不会替你决定
  • 怎么读更是如此。标准定的是数据的形状，不是问题
  • 删什么没有人替你决定。标准化过的数据如果没人看，同样只是成本
  • 告警阈值与噪声治理因服务而异，这不是标准能伸手的领域

更何况，引入了标准这句话在不同团队里含义不同。看官方状态页面就会发现，即便在同一个标准内部，成熟度也随语言与信号的组合而分化。

这张表在实务上的含义很明确：在多语言技术栈里，能把三个轴都铺到同一水平的语言是有限的。 原文作者的第二条建议之所以对使用者格外有价值，原因也在这里。知道哪个轴还没准备好，就可以不去建依赖这个轴的仪表盘。

5. 成本 - 基数、保留期、采样

如果没人看的数据是无害的，这篇文章到这里就可以收尾。它并非无害，原因是成本，而成本从三条路进来。

5.1 基数 - 加一个标签是乘法而不是加法

这是指标最常炸掉的地方。Prometheus 官方埋点指南把话说得很死：每一组标签都是一条额外的时间序列，会带来内存、CPU、磁盘和网络的开销。 同一份文档给出的实务标准是：把单个标签的取值种类控制在十个以内，超过这个数的标签在整个系统里只能是极少数，一旦超过一百就该考虑别的方案。

  • 三个标签各有十种取值，组合就是一千条。再加一个就是一万条。人的直觉跟不上这种增长
  • 最糟的是把取值实际上无上限的东西放进标签。请求标识和用户标识是典型，这类值需要把轴挪到日志或追踪，也就是处理单个事件的那一侧
  • 路径尤其是陷阱。不像 /orders/{id} 那样归一化成模板，每一笔订单都会生出一条时间序列
  • 如果已经炸了，光删标签还不算完。旧序列会在保留期内继续存在，让查询一直慢下去

5.2 保留期与采样 - 全都留下反而变成用不了的东西

把三个轴的保留期设成一样，是因为省事，不是因为正确。指标体积小、有用时间长，要和去年同月对比就需要一年的量。日志体积大，通常几天之内就被用完。追踪比这还短。

在追踪上，采样策略就是成本设计。OpenTelemetry 文档把它分成两类。头部采样尽可能早地做决定，因此易于理解、配置简单、效率高，但由于是在没看到整条链路的情况下决定的，它无法保证一定保留含错误的链路。 尾部采样在看过链路中大部分或全部 Span 之后再决定，所以可以按是否含错误、延迟或特定属性值来挑选。代价同一份文档也写得很清楚。

  • 尾部采样是有状态的系统。在做出决定之前必须把 Span 攥在手里，因此需要内存和节点，规模一大可能需要数十到数百个节点
  • 系统一变，规则就要持续更新。这不是写一次就能忘掉的配置
  • 文档还指出，有效的尾部采样可能被限制在特定厂商的方案里。对于为了厂商中立才引入标准的组织，这算是个讽刺
  • 实务上常见的折中是把错误和慢请求全部保留，其余按低比例保留。只是这样一来，就不能用剩下的样本去算比例了

这里就接上了标题里的那个悖论：全都留下反而变成用不了的东西。 存量一多查询就变慢，查询一慢人就不再打开。而没人打开的数据，存储费照收不误。也就是说，先全都收着这个决定看似是保守的选择，实际上往往是一边抬高成本、一边压低使用率的选择。

6. 故障时真正会看的东西

平时的仪表盘和故障时需要的查询，目的不同。平时的页面用来确认正常范围。只要看几条时间序列是不是保持着熟悉的形状就够了，所以页面固定也无妨。

故障时需要的正相反：需要的是收窄什么变了的能力，而这个问题在固定页面上得不到答案，因为必须不停地拆维度。

  • 把错误率按发布版本拆开。如果只集中在刚上线的版本上，原因立刻被收窄
  • 按路由或接口拆开。不是全局而是只有一条路径变差，就去怀疑某个依赖
  • 按可用区或节点拆开。偏向一侧就是基础设施的问题
  • 按客户端类型或客户等级拆开。只有某一路对接失败的情况比想象中常见
  • 而且要能这样拆，那个维度必须事先就被埋点。 故障中是加不了埋点的

6.1 可以提前准备的事

故障时的速度来自平时铺好的连接，而不是当下的手速。能提前做的事是明确的。

  • 放入把三个轴连起来的标识。 每一行日志都带上追踪标识，就能在指标上看到异常之后一步落到单次请求。没有这条连接，三个轴就各自孤立在三套工具里
  • 把发布与配置变更放到同一条时间轴上。 发布时刻、功能开关切换、基础设施变更都画在图上，什么变了这个问题的候选就能在屏幕内收窄
  • 把故障时用的查询保存下来。 临时写的查询会当场消失，所以反复用到的应当命名保存，并从运行手册和告警正文里直接给出链接。只要让接到告警的人不必从搜索开始，初动就能快上几分钟
  • 把正常基线用文字写下来。 当知道这个指标平时是多少的人不在位子上时，光看数字判断不了是否异常
  • 告警按症状来配。 给每个疑似原因都挂告警只会制造噪声，而且清单上没有的新原因反正也抓不住

7. 另一面 - 标准化与自动埋点确实带来了什么

读到这里如果得出以前更好的结论，那是错的。必须把标准化之前的样子一并摆出来才算公允。

标准化之前，每家厂商都有自家的探针和自家的 SDK。换一套可观测性工具等于去动应用代码，而这个代价实际上就是一把锁。各个服务的指标命名和标签规则各行其是，同一家公司内部都无法复用仪表盘。语言不同，请求上下文就在边界断掉，跨服务把请求串起来每次都是手工活。要加埋点就得改应用代码，也是那个时代的事。如今这些工作的相当一部分由库和自动埋点代劳了。

这不是小改进。引发本文的那篇原文，其作者也是先承认厂商中立这个目标本身已经达成才开始写的。他质疑的是速度，不是方向。评论区里同样混着认可中立性已实现的评价、希望改进日志支持的意见，以及不同语言体验差别很大的说法。

归纳一下：标准做到了自己那一份。 剩下的是标准本来就填不了的格子，而测什么、什么时候打开它，是要由懂业务的人来定的事。把这份期待押在标准上然后失望，是期待的方向错了。

8. 落地顺序 - 先定问题，再挂埋点

把上面这些换成顺序，会收敛到一条原则：先有问题，而不是先有埋点。 大多数团队的顺序是反的：装上探针，打开默认仪表盘，确认数据进来了，然后才去想用这些数据看什么。这样一来，该填的格子原封不动地空着。

  1. 把要回答的问题写成句子。 五到十条就够。像支付失败率是否高于平时、昨天发布后延迟是否变差这样，答案能落在是或否上的形式最好
  2. 给每个问题分配一个轴。 比例和趋势归指标，分段延迟归追踪，单次失败的原因归日志。这里分不出轴的问题，说明问题本身还太含糊
  3. 只挂那个轴需要的最小埋点。 事先定好要拆的维度，只把这些维度放进标签。因为觉得以后可能用得上而加的标签，占了基数事故的绝大多数
  4. 每个问题建一条保存好的查询。 问题和页面一对一绑住，页面才会有归属人
  5. 告警只按症状配。 给每个疑似原因挂告警会增加噪声，噪声一多真正的告警就被埋掉了
  6. 每个季度列一次没人打开的东西。 对象是不在任何仪表盘上、也不被任何告警使用的信号，以及没有访问记录的页面。删除前先通知归属人，没有回应就删
  7. 让新埋点的 PR 写明问题。 如果一行都写不出这个埋点回答的是哪个问题，那它现在还不需要。这一行以后会成为删除判断的依据

第六条其实最难，因为删除只有风险没有功劳。所以它必须是排进日程的流程，而不是个人意志。每季度一次，定好时间，至少把列清单这一步自动化。

未能确认的部分

  • 原文作者的统计未做独立复现。 上表中的数字只应被读作量级差异的指示
  • 关于仪表盘查看率的公开统计没有找到。本文所说的没人看不是测量值，而是从成本结构推出的结构性解释
  • 三个轴的合适保留期没有行业标准数值。它随监管要求与事故处理节奏而变化
  • 各厂商的计费结构与成本对比不在本文范围内。资费经常调整，结果也随使用形态而异
  • 原文提出的 Beta 层级是否会被真正采纳，截至撰写时尚未确定
  • OpenTelemetry 的各语言状态为 2026 年 8 月 23 日的情况，每次发布都会变动

结论：没人看的数据，和没有数据不是一回事

没人看的数据比没有数据更糟。没有的数据成本为零，也不会让谁误以为它存在。没人看的数据一边收着存储费，一边还额外奉送一种已经准备好了的错觉。 故障中打开页面才发现需要的维度根本没埋，正是这种错觉的结果。

引发本文的原文谈的是供给侧的速度。使用侧的问题在另一个位置：标准定下了数据的形状，却没有定下问题，而没有问题就收上来的数据不会被打开。 一旦接受三个轴回答的是不同问题，接下来的事就简单了：先写下要回答的问题，为每个问题挑合适的轴，再只埋那个轴需要的最小限度。

然后每季度一次，把没人打开的东西删掉。做加法这一侧已经有足够的推力，真正需要被做成流程的是做减法。
