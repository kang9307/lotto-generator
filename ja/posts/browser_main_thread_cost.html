ブラウザのメインスレッドはなぜ一本しかないのか - その一本を分け合うもの、外に出せるもの

スクリプトとレンダリングが互いを塞ぐ仕組み、三つの指標がそれぞれ測るもの、そして最後まで出られない仕事の境界

2026-09-05 開発・インフラ

ウェブ画面がもたつくとき、真っ先に出てくる診断はたいていコードが遅いというものだ。だからアルゴリズムを直し、ライブラリを差し替え、バンドルを削る。ところがそこまでやっても体感が変わらないことが少なくない。問題は速度ではなく場所だったからである。

ブラウザのタブ一つの中で、画面に関わる仕事はほぼすべてがたった一本のスレッドの上で起きる。JavaScript もそこで回り、スタイル計算もそこで行い、レイアウトもペイント命令の生成もそこだ。押された座標にどの要素があるかを判定する仕事さえそこにある。この一覧に載っているものは互いを待つ。一つがスレッドを掴んでいる間、残りは列を作る。

この記事は最適化のコツ集ではない。その一本のスレッドを何が分け合っているのか、遅いという体感がどの指標で捉えられるのか、そしてその上の仕事のうち外へ出せるものと最後まで出られないものの境界がどこに引かれているのかを見る。境界を知れば、どの最適化がそもそも成り立たないのかも同時に見えてくる。

以下の指標の定義としきい値は、すべて web.dev、Chrome for Developers、W3C 草案、MDN、WHATWG HTML 標準の原文に書かれているとおりである。性能指標のしきい値は改訂されるため、古い記事に書かれた数字をそのまま写すのが最もよくある誤りだ。下の表の値も、引用した時点と一緒に読む必要がある。

きっかけ - 問題はコードの速度ではなく場所だ

2026年9月初め、韓国の開発者コミュニティにブラウザのメインスレッドは高価だという記事が上がった。韓国語で書かれた原文で、要旨は一文に圧縮されている。コードが遅いからではなく、そのコードがよりによってメインスレッドを掴んでいるから問題になるのだ、というものだ。原文はその診断の上に七つの処方を積む。分割、まとめ、優先度、先送り、コンポジタへ載せる、ワーカーへ送る、そして仕事そのものをなくす、である。原文はこのうち最後のものが最も大きく残ると書いている。

処方の一覧は役に立つ。ただし一覧はなぜその処方が効くのかを説明しない。分割すると速くならないのになぜ反応が良くなるのか、ワーカーへ送れる仕事と送れない仕事を分ける線が何なのか、コンポジタへ載せるという言葉が正確にどの段階を飛ばすことなのかは、構造を見なければ出てこない。

そこでこの記事は処方の代わりに構造と境界を整理する。原文が扱っていないものも含まれる。Long Animation Frames、OffscreenCanvas、requestIdleCallback は原文には出てこない。逆に原文が扱った content-visibility、INP、TBT はここでも扱うが、公式文書の定義をそのまま添える。性能の話で最もよくある事故は誰かが写した数字をまた写すことだからだ。

メインスレッドが実際に背負っている仕事の一覧

Chromium のレンダリングアーキテクチャ文書は、レンダープロセスの中のメインスレッドが担う仕事を一文で列挙している。スクリプトの実行、レンダリングのイベントループ、ドキュメントライフサイクル、ヒットテスト、スクリプトイベントのディスパッチ、そして HTML や CSS をはじめとするデータ形式のパースである。同じ文書は、レンダープロセスにコンポジタスレッドと複数の補助スレッドが別にあることも併せて記す。つまりブラウザはシングルスレッドではない。画面の真実を計算する場所が一つなだけだ。

この一覧で注目すべきなのは、項目どうしが性質としてはまったく別物なのに同じ列に並んでいるという点だ。ソートのアルゴリズムとスタイルの再計算とクリックハンドラの呼び出しには何の関係もないが、実行の席を共有した瞬間、互いの遅れの原因になる。

メインスレッドが担う仕事具体的には何かここで詰まると出る症状
スクリプトの実行イベントハンドラ、タイマーのコールバック、ネットワーク応答の処理、フレームワークの内部ロジックその間に届いた入力がキューで待たされる
レンダリングのイベントループとドキュメントライフサイクルスタイル計算、レイアウト、プリペイント、ペイント命令の生成フレームが遅れて画面が止まって見える
ヒットテストどの座標にどの要素が置かれているかの判定押したのに何も起こらない
スクリプトイベントのディスパッチキャプチャとバブルの経路に沿って登録済みハンドラを呼ぶ入力遅延がそのまま積み上がる
HTML・CSS などのパース文書とスタイルシート、その他のデータ形式の解釈初期レンダーが後ろへずれる

表の右の列が利用者が実際に遭うもので、左の列が開発者がコードで見るものだ。この二つの列に橋を架けるのが次の節である。

一度に一つ - タスクは最後まで回ってから席を譲る

この構造が問題になる本当の理由は、スレッドが一本だという事実そのものではなく実行単位がプリエンプトされないところにある。JavaScript のタスクは一度始まれば最後まで回る。途中でもっと急ぐ仕事が届いても、ブラウザがそれを切って割り込ませることはできない。OS のスケジューラならタイムスライスが尽きたところで強制的にコンテキストを切り替えるが、イベントループにそういう仕掛けはない。

だから300ミリ秒かかる関数が回っている間に利用者がボタンを押すと、そのクリックは存在するがまだ誰も知らない状態でキューに置かれる。関数が終わってからディスパッチが始まり、ハンドラが終わってからレンダリング更新の番が来る。この待ち区間が後で見る INP の最初の区間、すなわち入力遅延である。

ここでよくある誤解を一つ片付けておく必要がある。非同期は並列ではない。 async 関数も、プロミスチェーンも、fetch の応答処理も、結局はメインスレッドのタスクかマイクロタスクとして戻ってくる。ネットワーク待ちはスレッドを手放すが、応答が届いた後にそれをパースし、状態を更新し、一覧を描き直す仕事はすべて同じ席で起きる。非同期で書いたからといって重い計算がどこかへ移るわけではない。

フレーム予算 - 16.6ミリ秒のうち実際に使えるもの

画面が滑らかに見えるにはフレームが規則的に出なければならない。web.dev のレンダリング性能の文書は、60Hz の画面でブラウザがフレーム一つを作るのに16.66ミリ秒を持つと書く。そしてすぐに但し書きを付ける。ブラウザ自体のオーバーヘッドがフレームごとにあるので、開発者の作業は10ミリ秒以内に終わらなければならないというものだ。

この数字が重要なのは絶対値よりも比率のほうだ。画面のリフレッシュレートが上がれば予算はその分だけ減る。120Hz の画面ではフレーム間隔が半分になるので使える時間も半分になる。高性能な機器ほど余裕が生まれそうに思えるが、リフレッシュレートも一緒に上がるなら実際にはむしろ厳しくなるわけだ。

そして10ミリ秒はJavaScript だけの予算ではない。 スタイル計算、レイアウト、ペイント命令の生成が全部その中に入らなければならない。スクリプトが8ミリ秒を使えば残り全部が2ミリ秒で終わらなければならないということだ。一覧を描き直すコードが速く見えても、その後ろに付くレイアウトの費用が予算を超えればフレームはそのまま落ちる。

互いを塞ぐ仕組み - 五段階の依存関係

web.dev はフレーム一つが作られる過程を五段階と呼ぶ。JavaScript、スタイル、レイアウト、ペイント、合成である。JavaScript が視覚的な変化を作り、スタイル段階がどの CSS 規則がどの要素に適用されるかを突き合わせて計算値を出す。レイアウトは要素の大きさと画面上の位置を決めるが、この段階の特徴はある要素の変化がツリー全体に波及しうることだ。ペイントはその結果をピクセル塗りの命令に変え、合成は描かれたレイヤーを正しい順序で画面に載せる。

この順序がそのまま依存関係である。レイアウトの結果なしにペイントはできず、スタイル計算なしにレイアウトはできない。ここから二つのことが導かれる。

  • どのプロパティを変えるかによってパイプラインへの入り口が変わる。 幅や位置を変えればレイアウトからやり直し、色だけ変えればレイアウトを飛ばしてペイントから始まる
  • レイアウトとペイントを両方とも飛ばせるプロパティがある。web.dev は、レイアウトもペイントも必要としないプロパティを変えればブラウザは直ちに合成段階へ進めるとし、これが最も安価で望ましい経路だと明記している
  • 同じフレームの中で読みと書きを交互に行うと、ブラウザは最新のレイアウト値を返すために計算を前倒しで実行する。読むものを先に全部読み、書くものを後でまとめて書く習慣が要るのはこのためだ
  • この強制計算はコードでは見えにくい。要素の大きさや位置を尋ねるプロパティ一つがその場でレイアウトを誘発し、それがループの中にあれば項目の数だけレイアウトが回る

まとめると、メインスレッドの仕事は単に席を分け合っているのではなく互いの入力であり出力だ。だから一箇所の遅れが別の場所へ波及し、一箇所の節約が別の場所まで救う。

遅さを測る三つの指標としきい値

構造が分かったら次は測定だ。遅いという言葉はそのままでは何の情報でもなく、何をどう測る値なのかを決めておかなければ改善したかどうかも分からない。ウェブで通用する軸は三つある。

INP - 押してから画面が変わるまで

Interaction to Next Paint は、訪問の期間全体で発生したすべてのクリック・タップ・キー入力の遅延を観測してそのページの全体的な応答性を表す値だ。一回の操作は三区間に割れる。ハンドラが実行され始めるまで待った入力遅延、ハンドラのコールバックが回る処理時間、そしてコールバックが終わってから次のフレームが描かれるまでの表示遅延である。スクロールとホバーと拡大は INP の計算に入れない。INP は2024年に安定したコアウェブバイタルとなり FID を置き換えた。

TBT - 読み込み中にメインスレッドが塞がっていた総量

Total Blocking Time は First Contentful Paint 以降、メインスレッドが入力への応答を妨げるほど長く掴まれていた時間の合計である。計算方法が単純なので定義をそのまま覚えておく価値がある。メインスレッドで50ミリ秒を超えて回るタスクをロングタスクと呼び、各ロングタスクで50ミリ秒を超えた分だけを足す。120ミリ秒のタスクは70ミリ秒を寄与し、45ミリ秒のタスクは0を寄与する。TBT はラボ指標だ。web.dev は、フィールドで測ること自体は可能だが利用者の操作が値を大きく揺らしてばらつきが増えるため勧めないと書いている。

LoAF - フレーム単位で見る遅れと、その犯人

Long Animation Frames はタスクではなくフレームを数える。W3C 草案の定義は、継続時間が50ミリ秒を超える二つの場合をロングアニメーションフレームとする。レンダリングの更新が必要でないタスク一つ、そしてレンダリングの更新が必要なタスクでレンダリングが実際に更新されるまでの区間だ。エントリには startTime、duration、renderStart、styleAndLayoutStart、blockingDuration、firstUIEventTimestamp、そして原因スクリプトの配列である scripts が入る。

指標何を測るかどこで測るか公式文書が言う良い値
INPクリック・タップ・キー入力の後、次のペイントまでの遅延。訪問全体で観測実利用者のフィールドデータ。コアウェブバイタルの判定用200ミリ秒以下は良い。200超500以下は改善が必要。500超は悪い。判定は75パーセンタイル
TBTFCP 以降、ロングタスクが50ミリ秒を超えた分の合計ラボのツール。フィールド測定は web.dev が勧めない平均的なモバイル機器で200ミリ秒未満
LoAFレンダリング更新が50ミリ秒を超えて遅れたフレーム一つひとつと、その原因スクリプトPerformanceObserver で観測。Chrome 123 以上、Edge 123 以上単一のしきい値はない。フレームの継続が50ミリ秒を超えれば記録対象
参考: コアウェブバイタル三種LCP は読み込み、INP は操作性、CLS は視覚的安定性フィールドデータ。モバイルとデスクトップを分けて集計LCP 2.5秒以下、INP 200ミリ秒以下、CLS 0.1以下。いずれも75パーセンタイル

三つの指標は同じ現象を別の角度から見る。TBT は読み込み区間の総量であり、INP は実利用者が遭った応答性であり、LoAF はどのフレームで誰がやったかだ。改善作業の順序として使えば、LoAF で犯人を見つけ、TBT で回帰を防ぎ、INP で実際の利用者に届いたかを確かめる流れになる。

ロングタスクだけでは足りなかった理由

Long Tasks API は長らくメインスレッドの占有を見る基本の道具だった。ところがこの API には構造的な死角がある。タスク一つが50ミリ秒を超えないと記録されないという点だ。40ミリ秒のタスクが五つ続けて並び一フレームを200ミリ秒塞いでも、ロングタスクは一つも捉えられない。利用者は200ミリ秒待ったのに計器盤は静かなままである。

LoAF はこの死角をフレーム単位で埋める。Chrome for Developers の文書は、LoAF がタスクではなくフレーム全体を見るため複数の小さなタスクが集まってレンダリングを塞ぐ状況を捉えられ、詳細なタイミングの分解とスクリプトの帰属がはるかに優れていると説明する。ここで blockingDuration の計算方法が面白い。W3C 草案は、フレーム内のタスクの継続時間を降順に並べ、レンダリングがあったなら最も長いタスクにレンダー区間を足し、各項目で50ミリ秒を超えた分を合計すると記す。TBT の計算規則をフレームの内側へ移した形だ。

スクリプトの帰属も実務での体感が大きい。PerformanceScriptTiming の項目には呼び出し元の情報である invoker と invokerType、実行開始時刻の executionStart、ソース位置を指す sourceURL と sourceFunctionName と sourceCharPosition、そしてそのスクリプトが強制的に誘発したスタイル・レイアウト時間である forcedStyleAndLayoutDuration が入っている。最後の項目は前節で述べた読み書きの交錯の費用を数字で返してくれる場所だ。

ただし対応範囲は狭い。Chrome 123 以上と Edge 123 以上でのみ動き、Firefox と Safari にはまだない。したがって LoAF は診断の道具であって利用者全体の計器盤ではない。この区別を曖昧にすると、Safari 利用者の比率が大きいサービスで誤った安心をしてしまう。

譲る - スレッドを手放してまた掴む技術

プリエンプションがないなら、残る方法は自ら手放すことだけだ。長い仕事を複数のタスクに切って、断片の間にブラウザが割り込む隙間を作ってやる。ここで必ず押さえておくべき点がある。譲っても総作業量は減らない。 むしろタスク切り替えの費用のせいで全体の時間は少し増える。代わりにその間に入力処理とレンダリングが入る場所が生まれる。同じ仕事をしながら応答性だけを買う取引だ。

譲る手段はいくつかあり性質が違う。setTimeout で先送りするとその作業はキューの一番後ろに付く。その間に他のタスクがたくさん入っていれば自分の作業はずっと後で再開される。しかも入れ子が深くなるとクランプが掛かる。WHATWG HTML 標準は、入れ子レベルが5を超えタイムアウトが4より小さければタイムアウトを4に引き上げると規定している。

scheduler.yield() はこの問題を正面から扱う。web.dev は、これがプロミスを返す関数であり、現在のタスクの続きが同じ種類の他のタスクより先に実行されると説明する。つまり譲るが列の最後尾には行かない。対応は Chrome 129 以上、Edge 129 以上、Firefox 142 以上で、Safari にはない。

// 長い一覧を分けて処理しながら、フレームごとにメインスレッドを手放す。
async function processInChunks(items, work) {
  const CHUNK_BUDGET_MS = 5;        // 一度に掴む時間 (経験則)
  let start = performance.now();

  for (let i = 0; i < items.length; i++) {
    work(items[i]);

    // 予算をまだ使い切っていなければ掴んだまま進む。
    if (performance.now() - start < CHUNK_BUDGET_MS) continue;

    // scheduler.yield があればそれを使う。
    // 続きの実行が同じ種類の他のタスクより先に戻ってくる。
    if (typeof scheduler !== 'undefined' && 'yield' in scheduler) {
      await scheduler.yield();
    } else {
      // 代替経路。キューの最後尾へ行き、入れ子が深いと 4ms にクランプされる。
      await new Promise((resolve) => setTimeout(resolve, 0));
    }
    start = performance.now();
  }
}

ここで廃れた助言を一つ押さえておく必要がある。入力が待機中のときだけ譲ろうという発想で isInputPending() を使うパターンがしばらく出回った。web.dev は今やこの API を勧めておらず、入力が待機中かどうかに関わらず譲れと明記している。偽陰性の可能性と対象範囲の不完全さが理由だ。古いブログ記事に残っているコードをそのまま持ってこないほうがよい。

仕事に優先度を付けるということ

譲るだけでは足りない場面がある。手放した席を誰が先に取るかはまだ決まっていないからだ。Prioritized Task Scheduling API がその部分を担う。scheduler.postTask() は三段階の優先度を受け取り、MDN は実行が優先度の順、同じ優先度の中では宣言の順で起きると記す。

優先度指定の仕方どんな仕事に付けるか
user-blockingオプションに明示する利用者が結果を待っていて画面更新を塞いでいる仕事
user-visible省略すればこれ (既定値)画面には見えるが即時性が低い仕事
backgroundオプションに明示する誰も待っていない仕事。事前計算やログ送信のようなもの

優先度を後で変える必要があるなら、オプションに値を直接入れてはいけない。MDN は変わりうる優先度は TaskController を作ってそのシグナルを渡し、setPriority() で調整せよと案内する。あらかじめゆっくり計算していた仕事が利用者のクリック一つで急に急ぎになる状況がまさにこの場合だ。

似た場所に requestIdleCallback もある。MDN は、これがブラウザのアイドル区間に関数を予約し、アニメーションや入力応答のような遅延に敏感なイベントに影響を与えずに背景の低優先度作業を回せるようにすると説明する。コールバックは IdleDeadline を受け取り timeRemaining() で残り時間を尋ね、didTimeout でタイムアウトのために呼ばれたかを確かめる。但し書きが二つある。必ず実行されなければならない作業ならtimeout オプションを強く勧めるということと、そのタイムアウトが満了すると性能に悪影響を与える危険を冒してでもコールバックがキューに載るということだ。対応状況は広くなく、MDN は最も広く使われるブラウザの一部で動かないため Baseline ではないと表示する。この API は原文には出てこない。

出せるもの その一 - ワーカーへ出る計算

ここからが本論だ。メインスレッド上の仕事のうち本当に外へ出られるものは何か。最初の通路はウェブワーカーである。

ワーカーの境界は非常に鮮明だ。MDN は、ワーカーの中からDOM を直接操作できず、window オブジェクトの既定のメソッドやプロパティの一部も使えないと釘を刺す。ワーカーでできない核心は親ページに直接影響を与えることであり、そこには DOM の操作とそのページのオブジェクトの使用が含まれる。グローバルスコープが Window ではなく DedicatedWorkerGlobalScope なので window、document、parent はない。逆に fetch、XMLHttpRequest、タイマー、標準の組み込みオブジェクト、importScripts() は使える。

二つ目に知っておくべきはデータがどう渡るかだ。既定はコピーである。MDN の表現をそのまま移すと、メインページとワーカーの間でやり取りされるデータは共有されるのではなくコピーされ、渡すときに直列化され反対側で逆直列化されて両側にそれぞれ複製ができる。これが構造化クローンだ。だから大きな配列を毎フレームやり取りすると、ワーカーへ移した利得が直列化の費用で相殺される。

転送可能オブジェクトがこの問題を解く。所有権を丸ごと渡すのでコピーが起きない。MDN は、ArrayBuffer をワーカーへ転送すると元の ArrayBuffer は空になりもう使えなくなると記す。文字どおり中身が移ったのだ。

// main.js - 大きなバッファはコピーせず所有権ごと渡す。
const worker = new Worker('./heavy.js');
const pixels = new Uint8ClampedArray(width * height * 4);
// ... pixels を埋める ...

worker.postMessage(
  { buffer: pixels.buffer, width, height },
  [pixels.buffer]                 // 第二引数が転送リストだ
);
// この行の後から pixels.buffer は空になる (byteLength === 0)

worker.onmessage = (e) => {
  const out = new ImageData(new Uint8ClampedArray(e.data.buffer), e.data.width);
  ctx.putImageData(out, 0, 0);    // DOM に触れる仕事はここ、メインスレッドで
};

// heavy.js - DOM はない。データだけ入り、データだけ出る。
self.onmessage = (e) => {
  const { buffer, width, height } = e.data;
  const buf = new Uint8ClampedArray(buffer);
  for (let i = 0; i < buf.length; i += 4) {
    const g = (buf[i] * 0.299 + buf[i + 1] * 0.587 + buf[i + 2] * 0.114) | 0;
    buf[i] = buf[i + 1] = buf[i + 2] = g;
  }
  self.postMessage({ buffer: buf.buffer, width, height }, [buf.buffer]);
};

キャンバスはこの境界に例外的な扉を一つ持っている。OffscreenCanvas はDOM とキャンバス API を分離して <canvas> 要素が DOM に全面的に依存しないようにする。MDN は、描画処理をワーカーのコンテキストの中で回すことで重い仕事をメインスレッドから外せると説明する。使い方は transferControlToOffscreen() で制御権を切り離しワーカーへ転送することで、ワーカーの中で requestAnimationFrame() まで使える。ブラウザ全般で2023年3月から使えると表示されている。この API も原文には出てこない。

出せるもの その二 - コンポジタへ出る動き

二つ目の通路は性質が違う。コードを移すのではなくブラウザが自ら別のスレッドで処理するように条件を整えてやることだ。

Chromium の文書は、レンダープロセスのコンポジタスレッドが入力処理、スクロール、アニメーションを担い、画像デコードとラスタ処理を調整すると記す。そしてメインスレッドとコンポジタスレッドを分離することが、アニメーションとスクロールをメインスレッドの作業から性能的に隔離するうえで決定的に重要だと明記する。より具体的には、視覚効果のアニメーションとスクロールはレイアウトとプリペイントとペイントを飛ばすことができ、その三段階を飛ばせるならすべてコンポジタスレッドで回りメインスレッドを飛ばせると書かれている。

実務に移すと規則は単純になる。位置を動かすアニメーションを left/top で作れば毎フレームレイアウトが回り、そのレイアウトはメインスレッドの仕事だ。同じ動きを transform で作ればレイアウトとペイントを飛ばして合成だけが残る。不透明度も同様である。だからメインスレッドが重い状態でも滑らかなままのアニメーションと、スクリプト一行で止まってしまうアニメーションが分かれる。

スクロールにも同じ原理が働くが、ここには開発者が自分で元へ戻してしまうよくある落とし穴がある。イベントリスナーの passive オプションだ。MDN は、passive を true にするとリスナーが既定動作を取り消さないと宣言することになるので、ブラウザはリスナーの終了を待たずに直ちに既定動作を始められると説明する。逆に取り消し可能なリスナーが付いていると、ブラウザは preventDefault() が呼ばれるかどうかを知りようがないので待たなければならない。 その待ち時間がすなわちスクロールの遅延である。

既定値を正確に知っておく必要がある。MDN は、passive が指定されなければ false だが、Safari 以外のブラウザでは Window、Document、Document.body という文書レベルのノードに付く wheel、mousewheel、touchstart、touchmove に限って true が既定だと記す。つまり文書レベルでない特定の要素に付けたタッチリスナーは依然として既定が false だ。明示的に { passive: true } と書く習慣が要る場所である。

出せないもの - 境界はどこに引かれているか

ここからは反対側だ。どう工夫しても出られない仕事があり、その理由は性能ではなく定義にある。

DOM に触れなければならない仕事

ワーカーに document がないのは実装の未整備ではなく設計だ。DOM は複数のスレッドが同時に触れば一貫性を保てない可変のツリーであり、だからアクセスを一つのスレッドに束ねた。この決定を受け入れるとスタイル計算とレイアウトも一緒に束ねられる。 どちらも DOM ツリーとスタイルシートを読まなければならないからだ。Chromium の文書がドキュメントライフサイクルをメインスレッドの仕事として記しているのは、まさにこの意味である。

取り消されうる必要がある入力

ヒットテストとイベントディスパッチも同様だ。どの座標にどの要素があるかを知るには最新のレイアウトが要り、レイアウトはメインスレッドにある。そしてリスナーが preventDefault() を呼べるという可能性そのものがブラウザを待たせる。 スクロールをコンポジタで処理していても、取り消し可能なリスナーが現れれば判定をメインスレッドに問い合わせなければならない。

やろうとしている仕事メインスレッドの外へ出られるかなぜそうなのか
パース、圧縮、ソート、画像のピクセル処理のような純粋計算出られる — ウェブワーカーDOM を使わず入出力がデータだけだ
キャンバスに描く仕事出られる — OffscreenCanvas とワーカーキャンバスを DOM から切り離し制御権だけワーカーへ渡せる
transform・opacity のアニメーション出られる — コンポジタスレッドレイアウトとプリペイントとペイントを飛ばせる
スクロールおおむね出られる — コンポジタスレッドただし取り消し可能なリスナーが付くとメインスレッドに問い直す必要がある
DOM の読み書き出られないワーカーには window・document・parent がない
スタイル計算とレイアウト出られないドキュメントライフサイクルがメインスレッドの仕事として定義されている
入力イベントハンドラの実行出られないスクリプトイベントのディスパッチ自体がメインスレッドで起きる
ヒットテスト出られない最新のレイアウトを読まなければ判定できない

この表が与える結論はやや断固としている。メインスレッドを空ける最善の方法は移すことではなく減らすことだ。 移せる項目は表の上の四つだけで、実際のウェブアプリケーションで最も時間を食うのはたいてい下の四つだからである。

仕事そのものを減らす - 封じ込めと省略

減らす方法のうち最も構造的なのが CSS の封じ込めだ。MDN は、CSS containment がページのサブツリーを残りの DOM から隔離し、ブラウザがその独立した部分のレンダリングを最適化できるようにすると説明する。contain プロパティの値はそれぞれ別のものを閉じ込める。size は要素の大きさの計算を内容から切り離し、layout はレイアウトの再計算をその要素と子孫の中に束ね、style はスタイルの再計算を、paint はペイントを要素の境界の内側に閉じ込める。content は layout・style・paint をまとめた短縮形で大きさは含まない。strict はそこに size まで加えた最も強い形だ。

封じ込めが実際の利得に変わる代表的な場所が content-visibility である。web.dev の文書は、content-visibility: auto が付いた要素がレイアウト・スタイル・ペイントの封じ込めを得て、画面外にあれば大きさの封じ込めまで得ると記す。その間ブラウザは要素ボックス自体のスタイルとレイアウトだけを行い、中身のペイントとヒットテストは行わない。同じ文書の旅行ブログの例で初期レンダリング時間は232ミリ秒から30ミリ秒へ縮み、文書はこれを7倍の向上と呼んでいる。

/* 画面外のカードのスタイル・レイアウト・ペイントを省く */
.feed-card {
  content-visibility: auto;

  /* 省いている間に使う代替サイズ。
     これがないと画面外の要素の高さが 0 に潰れ、
     スクロールバーの長さが揺れ続ける。 */
  contain-intrinsic-size: auto 480px;
}

/* 大きさまで隔離してよい場所にだけ strict を使う。
   strict = size + layout + style + paint */
.widget-frame {
  contain: strict;
  width: 320px;
  height: 240px;
}

contain-intrinsic-size は大きさの封じ込めが効いたときに使う自然な大きさを指定するプロパティだ。これがないと画面外の要素が高さ0に潰れスクロールバーの大きさが揺れる。web.dev はこのプロパティを、描画された内容の代わりに置かれるプレースホルダーの大きさと呼ぶ。

一つ気を付ける点がある。content-visibility: auto で省かれた内容はページ内検索が効き、その場所へ移動できる。 display: none や visibility: hidden と違う点であり利点でもある。ただしそのために画面外のランドマーク要素がアクセシビリティツリーにそのまま現れるので、必要なら aria-hidden を付けて整理せよと文書は案内する。性能を得ながらアクセシビリティツリーを散らかさない均衡を別途配慮せよということだ。

ここまで来ると、なぜ原文が仕事そのものをなくすところから最も大きな利得が出ると書いたのかが説明される。移せるものは少なく、移すのにも費用が掛かり、そもそもしなかった仕事はどのスレッドでも時間を使わない。

きっかけとなった記事とこの記事が分かれる地点

原文は処方を与える。何をすればよいかを七つに分けて例と一緒に見せる。実務ですぐ手に取れる形であり、とくに分割・まとめ・優先度の三つはフレームワークなしでも適用できる水準に具体的だ。原文が挙げた数字もこの記事のものと食い違わない。16.6ミリ秒のフレーム予算、50ミリ秒のロングタスク基準、INP と TBT を併せて言及する部分がそうである。

この記事は境界を描く。処方の前に何がなぜその場所になければならないのかを先に定めておけば、新しい処方が出たときそれがどこに入るのかを自分で判断できる。そこで次の三つを原文の外から持ってきて添えた。

  • Long Animation Frames — 原文には出てこない。ロングタスクの基準だけでは小さなタスクが集まってフレームを塞ぐ状況を捉えられず、その死角を埋めるのがこの API だ
  • OffscreenCanvas — 原文には出てこない。ワーカーが DOM に触れないという規則に空いた唯一の実用的な穴なので、境界の話から外せない
  • requestIdleCallback — 原文には出てこない。優先度の話の反対側、すなわち最も低い等級を扱う古い手段であり、対応範囲が狭いという事実まで一緒に見る必要がある
  • 逆に content-visibility は原文も言及する。原文は似た効果を CSS 一行で狙うプロパティだと短く紹介し、この記事はそれが得る封じ込めの種類と一緒に使うべきプロパティまで広げた

測定の話を一つ添えると、遅れを感じる感覚と計器盤の値はしばしば食い違う。その隔たりを扱った記事として遅くてもいいという合意はどう作られたかがあり、画面状態の一貫性が信頼につながる側はすべてのフレームを完璧にが扱う。描画をキャンバスへ移したとき何を失うかはcanvas に HTML を描く APIで、大量の一覧を仮想化で乗り切る具体例はTrees というファイルツリー描画ライブラリですでに整理したので、ここでは繰り返さない。

最後に順序を一つ提案する。コードを直す前にどのフレームがなぜ遅れたのかから見る。LoAF で原因スクリプトを見つけ、そのスクリプトがしている仕事が上の表のどの行に属するかを確かめる。上の四つなら移し、下の四つなら減らす。この判定さえきちんとできれば成り立たない最適化に時間を使うことはなくなる。

確認できなかったこと

  • 入れ子タイマーの最小遅延の値が文書ごとに違って書かれている。WHATWG HTML 標準は入れ子レベルが5を超えタイムアウトが4より小さければ4に引き上げると規定するのに対し、web.dev のロングタスクの文書は5ミリ秒と書く。本文は標準側の値を使ったが、なぜ二つの文書が違うのかは確認できなかった
  • IdleDeadline.timeRemaining() が返す値に50ミリ秒のような上限があるかは MDN の文書で明示を見つけられなかった。よく引用される値だが規格の文を直接確認できなかったので本文には入れなかった
  • INP が FID を置き換えた正確な日付は確認できなかった。確認できたのはコアウェブバイタルの文書の「2024年に安定指標になった」という記述と、発表記事に「今日がその日だ」とだけ書かれているという事実までである
  • Long Animation Frames の50ミリ秒の基準を調整できるのか、そしてこの指標が今後コアウェブバイタルへ昇格する計画があるのかは確認できなかった
  • OffscreenCanvas がWebGPU のコンテキストに対応するかは MDN の概要文書で確認できなかった。その文書に出ている例は 2D と WebGL だけである
  • 原文が示した一フレームあたり5ミリ秒のチャンク予算は規格ではなく経験則だ。その値の出典や根拠は原文に書かれておらず確認できなかった。本文の例にも経験則と表示しておいた
  • Safari の requestIdleCallback・scheduler.yield() 対応の可否は、MDN の「最も広く使われるブラウザの一部で動かない」という記述と web.dev の「Safari 非対応」までしか確認できず、バージョン別の互換性表は直接開いていない
  • WHATWG HTML 標準の「update the rendering」の下位手順の順序は文書を開いたが該当節が切れていて確認できなかった。本文のパイプラインの順序は web.dev と Chromium アーキテクチャ文書の記述を根拠に書いた
