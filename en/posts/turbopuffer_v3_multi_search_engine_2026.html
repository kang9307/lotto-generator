Context — Limitations of Vector-Primary Design and v3 Announcement

On September 30, 2026, search infrastructure company turbopuffer published an engineering blog post titled "RIP, vector database". Originally built as a serverless vector database, turbopuffer revealed that it is undertaking a fundamental overhaul of its storage architecture for version 3 (v3). The core of this announcement is not the elimination of vector search, despite the provocative title, but the structural decision to demote the Approximate Nearest Neighbor (ANN) vector index from its role as the primary storage index to a secondary index.

By leveraging cloud object storage as the single source of truth and combining it with tiered NVMe SSD and in-memory caches, turbopuffer established an economic and low-latency balance that has supported demanding production workloads for major tech enterprises such as Cursor and Notion. However, as customer demands expanded to non-vector queries including full-text search, regex search, attribute filtering, and analytical aggregations, the original design—where every document was physically tied to its vector position—ran into three major physical barriers: storage amplification, write amplification, and constrained vectorization in query execution. The principal engineering objectives established in the official announcement are as follows:

  • Decoupling the physical document storage layout from the vector index to eliminate redundant storage of non-vector data
  • Isolating background vector rebalancing routines to prevent cascading relocations of hundreds of inverted index entries
  • Unshackling query block sizes from rigid ANN cluster boundaries to fully utilize modern vectorized CPU execution pipelines
  • Enabling the high-throughput migration of complex SQL analytical and scanning workloads onto the turbopuffer engine

Ultimately, this architectural shift in v3 is not merely an incremental performance patch. It represents a categorical transition from a single-purpose specialized vector database into a versatile multi-search query engine capable of unifying vector embeddings, full-text inverted indices, and structured relational queries on top of cloud object storage.

v1 Architecture — Object Storage Paired with Hierarchical Clustering

The design goal of turbopuffer v1 was to serve extremely cheap and reasonably fast vector searches in a serverless model. At the time of launch, graph-based vector indexes like HNSW represented prevailing industry wisdom. However, graph traversal patterns involve arbitrary memory pointer chases that conflict heavily with the high network latency and large-block read characteristics of cloud object storage. Instead of a graph, turbopuffer adopted a hierarchical clustering index, which is far better aligned with object storage semantics.

While the initial implementation utilized Microsoft's SPANN algorithm, the system soon transitioned to the SPFresh algorithm to support incremental indexing for streaming writes. Vectors are clustered into groups, whose centroids are clustered in turn, repeated recursively to form a tree structure with a single root. The underlying storage layer presents as a key-value map with sorted, unique keys. Each cluster is assigned a ClusterId, and vectors within each cluster receive a dense LocalId. Combining these two identifiers yields an ANN address such as C0L1.

// turbopuffer v1: Sorted key-value storage mapping keyed by ANN addresses
                    // Leaf cluster C0 storing vector embeddings and source document IDs
                    K::Vector(C0L0) = vec![0.45, 0.32, ...];
                    K::Id(C0L0)     = 7;
                    
                    K::Vector(C0L1) = vec![-0.28, 0.96, ...];
                    K::Id(C0L1)     = 13;
                    
                    // Upper tree level clustering centroid vectors pointing to sub-clusters
                    K::Vector(C1L4) = vec![0.64, -0.48, ...];
                    K::Id(C1L4)     = C0; // References subordinate cluster identifier

The foundational design principles and physical characteristics governing the v1 architecture can be distilled into four pillars:

  • Designating object storage as the authoritative source of truth to minimize disk costs while buffering latencies via tiered NVMe caches
  • Avoiding pointer chasing by organizing vectors into hierarchical clusters optimized for large sequential block reads from cloud storage
  • Employing a sorted key-value store where composite ANN addresses (ClusterId plus LocalId) serve as the primary record identifiers
  • Routing top-down tree traversals through centroid vectors to prune search branches with minimal round-trip network I/O operations

As demonstrated in the code example above, not only the raw vector embedding but also the document ID was physically keyed by the combined ClusterId and LocalId ANN address. This meant that the primary index determining data layout inside the database engine was the vector index itself. This layout was exceptionally well-suited for retrieving only the necessary vector cluster blocks from object storage with minimal I/O operations.

v2 Evolution — Inverted Attribute Filtering and BM25 Full-Text Search

As adoption matured, applications demanded more than raw vector cosine similarity; metadata attribute filtering and BM25 full-text search (FTS) became essential query plans. In what the team informally termed v2, turbopuffer integrated an inverted attribute index and full-text search engine. To ensure rapid filtering alongside high recall, the attribute index mapped attribute values directly to the ANN addresses of documents containing those values.

For instance, filtering ornithological records by family or genus allowed the engine to immediately fetch the matching list of ANN addresses, thereby pruning the vector search space upfront. Furthermore, because queries often projected document attributes via the include_attributes parameter, the document attributes were stored alongside the ID and vector under the exact same ANN address.

// turbopuffer v2: Attribute inverted index and BM25 full-text search schema
                    // Mapping attribute values to document ANN addresses
                    K::AttrIndex("family", "Alcidae")    -> vec![C0L3, C1L2, C1L3, ...];
                    K::AttrIndex("genus", "Fratercula")  -> vec![C0L3, C1L2, C1L9, ...];
                    
                    // Inlining metadata attributes under ANN address for include_attributes projections
                    K::Vector(C0L0)          = vec![0.45, 0.32, ...];
                    K::Id(C0L0)              = 7;
                    K::Attr(C0L0, "family")  = "Alcidae";
                    K::Attr(C0L0, "genus")   = "Fratercula";
                    
                    // BM25 posting list: storing term frequency and document length with ANN address
                    K::FTS("description", "Atlantic")    -> vec![(C0L0, 2, 37), (C9L4, 1, 42), ...];
                    K::Attr(C0L0, "description")         = "A sharply dressed seabird with a multicolored bill...";

To support increasingly sophisticated enterprise workloads, turbopuffer progressively shipped a wide spectrum of advanced query execution engines and indexing mechanisms:

  • Inverted attribute filtering: resolving metadata predicates to sets of ANN addresses for rapid pre-filtering
  • BM25 full-text search: maintaining posting lists enriched with term frequency and document length for relevance ranking
  • Regex and fuzzy matching: enabling flexible substring exploration, regular expressions, and typo-tolerant search
  • Sparse vector retrieval: facilitating hybrid search by combining learned sparse embeddings with dense vectors
  • Attribute-based sorting and aggregations: providing basic statistical summarization and field-level result ordering

The platform even became the foundation for non-search workloads, such as Linear's delta synchronization read path. Yet beneath all these newly added query plans, the foundational storage layout remained bound to the vector-primary storage architecture.

Structural Bottleneck ① — Storage Amplification from Multi-Vector Embeddings

Storing all document attributes under the vector's ANN address caused little trouble when each document had exactly one vector embedding. In that 1:1 mapping, non-vector attributes were written to disk exactly once alongside the vector. However, modern retrieval-augmented generation (RAG) and retrieval techniques have moved decisively beyond single-vector document representations.

Advanced systems frequently employ document nesting—splitting long documents into multiple chunk embeddings—or late interaction architectures (such as ColBERT models) that generate per-token embeddings. These paradigms assign multiple vector embeddings to a single document. Under turbopuffer's v1 and v2 layouts, each vector was clustered independently and assigned a separate ANN address. This generated severe structural inefficiencies:

  • If a document produced 10 embedding vectors, its entire non-vector metadata and textual payload had to be duplicated across 10 distinct ANN addresses.
  • For documents with extensive metadata or large textual descriptions, the duplicated document payload quickly dwarfed the raw vector storage footprint.
  • Storage bloat directly multiplied cloud object storage costs and accelerated premature evictions in local NVMe SSD caches.
  • Degraded cache hit ratios saturated network bandwidth and substantially constrained multi-tenant query concurrency.
  • This forced turbopuffer to enforce strict namespace-level limits on the maximum number of vector columns allowed per document.

Structural Bottleneck ② — Write Amplification Cascades in SPFresh Rebalancing

The second acute bottleneck was write amplification during data ingestion, updates, and deletions. In hierarchical clustering indexes, continuous mutations cause cluster drift, threatening search recall if left unchecked. To maintain search quality, turbopuffer's SPFresh algorithm continually rebalances vector clusters in the background.

Because every attribute and index reference was keyed on the ANN address, rebalancing a vector was not an isolated operation. When a vector shifted from cluster A to cluster B, its ANN address changed (e.g., from C0L3 to C2L8). This cascaded into rewriting the entire document content and updating hundreds of attribute inverted indexes and BM25 postings that pointed to the former address.

  • Rebalancing a single vector triggered cascading physical relocations for hundreds of associated attribute and index entries.
  • In update-heavy workloads, the physical I/O overhead on disk and object storage reached tens to hundreds of times the volume of the incoming data.
  • Efforts to optimize indexing throughput encountered diminishing returns due to the sheer volume of cascading rewrites.
  • Excessive write I/O degraded background compaction cycles and created latency spikes for real-time read queries.
  • The resulting saturation slowed data ingestion pipelines and drove cloud infrastructure operational costs upward.

Structural Bottleneck ③ — Query Block Sizing and Vectorized Execution Limits

The third bottleneck centered on vectorized execution, the cornerstone of modern database query performance. Modern query engines process values in tight loops over fixed-size blocks to maximize CPU pipeline saturation and exploit SIMD vector instructions. However, optimal block sizes vary radically depending on the query operator.

Engine & Query PlanOptimal Processing Block SizeExecution Characteristic & Hardware Target
DuckDB (Vectorized OLAP)2,048 rows per batchL1/L2 cache locality and SIMD vectorized arithmetic
ClickHouse (Large-scale Analytics)Up to ~65,000 rows per blockMaximum columnar scan throughput and compression density
Apache Lucene (FTS Postings)256 docs per blockFast integer skip-lists and SIMD bitpacking (PForDelta)
turbopuffer ANN Vector Index~100–200 docs per clusterCentroid distance calculation accuracy and I/O locality
turbopuffer FTS v1 (Legacy)Median ~1.5 postings per blockSeverely fragmented by partitioning along ANN cluster bounds

As outlined in the table above, turbopuffer's ANN index operates most efficiently when clusters contain roughly 100 to 200 documents. But because document storage was physically coupled to this cluster size, analytical scans and aggregations (such as GROUP BY, SUM, or COUNT) that require scanning thousands of rows were constrained to iterating through small 100–200 document chunks.

The critical impact of block sizing was previously demonstrated when turbopuffer re-architected its full-text search engine from v1 to v2. In FTS v1, posting lists were partitioned along ANN cluster boundaries, yielding a median block size of only ~1.5 postings. In FTS v2, posting lists were decoupled into uniform blocks of ~256 documents; as a result, index size shrank by 10x and query speeds surged up to 20x. Posting lists could achieve this because they merely pointed to documents. However, analytical scans reading document columns remained bottlenecked by the 100–200 document cluster boundary.

The v3 Remedy — Decoupling Document Storage and Secondary Indexing

To eliminate these three architectural bottlenecks, turbopuffer v3 adopted a straightforward yet profound design principle: stop keying documents on the ANN address. Version 3 completely decouples document layout, compaction, and retrieval from the vector cluster tree, establishing the following structural breakthroughs:

  • Independent Document Storage: Documents are stored independently of vector cluster boundaries, keyed by their own identifiers in columnar blocks sized for optimal scanning. A document with multiple vectors stores its body only once, eliminating storage amplification.
  • ANN as a Secondary Index: The vector index is no longer the foundational backbone of the system; it becomes a secondary index alongside inverted attribute and full-text indexes.
  • Isolation of Write Cascades: When SPFresh rebalances vector clusters, only the internal pointers within the vector index update. The underlying document contents and associated attribute indexes remain untouched.
  • Unconstrained Vectorized Processing: Aggregations and table scans break free from the 100–200 document cluster size, processing thousands of rows in contiguous memory blocks that saturate modern hardware pipelines.
  • Foundation for General SQL: Normalizing document storage establishes the architectural foundation needed to execute broader SQL query shapes directly and efficiently within turbopuffer.
  • Independent Compaction Schedules: Document compaction routines and vector index rebalancing cycles run on distinct cadences, substantially improving operational stability.

The engineering team is currently conducting extensive benchmarking to guarantee performance parity and beyond before initiating the production rollout.

What Could Not Be Verified

  • The precise on-disk and object-storage file format adopted for the decoupled document store in v3 (e.g., Apache Parquet or a custom binary columnar format). The blog post outlines architectural decoupling without detailing container formats.
  • The exact production release date for v3. The announcement confirms 100% CI completion and ongoing benchmarks, but provides no fixed rollout calendar.
  • The specific online migration protocol and downtime requirements for transitioning existing v2 namespaces to v3 storage.
  • Measured percentage latency improvements for aggregation (GROUP BY) queries under v3. (The 10x index reduction and 20x query speedup cited in the text refer to historical FTS v2 benchmarks).
  • The complete roster of enterprise customers participating in private alpha or beta evaluations of v3 beyond publicized clients (Cursor, Notion, Linear).
  • Internal node-level caching policies and additional memory overhead introduced by operating the ANN index strictly as a secondary structure in v3.
