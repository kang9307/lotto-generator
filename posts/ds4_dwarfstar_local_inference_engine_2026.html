계기 — 단일 아키텍처 전용 엔진에서 복수 프론티어 지원으로의 확장

Redis의 창시자인 Salvatore Sanfilippo(antirez)가 주도하는 오픈소스 로컬 추론 엔진 DwarfStar 4(ds4)가 프로젝트 공식 문서 사이트(dwarfstar.sh)를 공개하며 기술적 진전을 알렸다. ds4는 당초 대규모 전문가 혼합(MoE) 구조를 지닌 DeepSeek V4 Flash(2,840억 매개변수)를 개인 워크스테이션에서 구동하기 위해 시작된 C 기반 추론 엔진이다. 그러나 최근 갱신을 통해 GLM 5.x(GLM 5.2 및 GLM 5.3 Flash)와 Qwen3.8 Flash Next까지 지원 모델군을 전격 확장했다.

초거대 MoE 모델을 로컬 환경에서 실행하려는 시도는 메모리 대역폭과 용량의 한계라는 거대한 벽에 부딪혀 왔다. 수천억 매개변수에 달하는 가중치는 양자화를 거치지 않고서는 128GB 수준의 단일 머신에 상주할 수 없으며, 일반적인 서빙 프레임워크는 클라우드 분산 클러스터를 전제로 설계되어 있다. ds4는 대용량 통합 메모리를 갖춘 Apple Silicon Mac, Linux CUDA, AMD ROCm 머신을 타깃으로 삼아 정반대의 제약 조건에서 출발했다. 로컬 환경에서의 LLM 실행 배경과 하드웨어 제약은 로컬 LLM 실행 가이드와 Mac 통합 메모리 구조 분석에서도 살펴본 주제다.

단일 모델 계열에 극도로 특화되었던 전용 엔진이 다른 프론티어 오픈웨이트 계열까지 포섭하게 되면서, 아키텍처의 설계 철학과 하드웨어 자원 배분 방식에 어떠한 변화가 생겼는지 공식 문서를 통해 점검할 필요가 있다.

설계 원칙 — 범용 GGUF 실행기가 아닌 좁은 최적화 엔진

공식 문서가 가장 명확하게 선을 긋는 대목은 「ds4는 범용 GGUF 실행기가 아니다(Not a generic GGUF runner)」라는 점이다. llama.cpp나 Ollama 같은 도구들이 커뮤니티에서 변환된 수많은 모델 포맷을 범용적으로 수용하는 것을 지향한다면, ds4는 극소수의 선정된 모델 계열과 프로젝트가 직접 레이아웃을 종단 간(end-to-end) 검증한 전용 GGUF 파일만을 로드한다.

  • 프로젝트에서 공식 검증한 모델 레이아웃만을 허용하며, 일반적인 커뮤니티 GGUF 파일은 로드되지 않는다.
  • 선택된 모델의 수식과 어텐션 구조에 맞춰 C 커널과 가속 백엔드(Metal, CUDA, ROCm)를 직접 최적화한다.
  • 모든 지원 모델에 대해 공식 원본 모델의 추론 출력과 레이어별 연산 결과를 대조 검증한다.

이러한 협소화(narrow on purpose) 전략은 유지보수 비용을 낮추는 대신, 각 모델 구조의 병목을 극한까지 파고들 수 있게 만든다. 특정 모델의 어텐션 메커니즘이나 MoE 라우팅 특성을 범용 추상화 계층 없이 엔진 레벨에서 직접 C 코드로 구현하기 때문이다.

비대칭 2비트 양자화와 MoE 압축 구조

DeepSeek V4 Flash나 GLM 5.x와 같은 모델이 단일 워크스테이션에 적재될 수 있는 기술적 비결은 「비대칭 2비트 양자화(Asymmetric 2-bit quantization)」에 있다. MoE 아키텍처에서는 토큰마다 활성화되는 전문가(routed experts)의 비율이 극히 일부에 불과하다. ds4는 이 특성을 공략한다.

라우팅되는 대다수 전문가 가중치는 2비트(q2) 수준으로 공격적으로 압축하여 전체 용량을 급격히 줄인다. 반면, 모든 토큰이 통과하는 중요한 공유 경로(shared paths)와 어텐션 핵심 가중치는 정밀도를 유지한다. 공식 문서에서는 이를 「압축되었으나 뇌절제되지 않은 상태(Compressed, not lobotomized)」로 표현한다. 이로써 2,840억 매개변수의 거대한 신경망이 96GB~128GB 메모리 대역 안에 수용되면서도 기초적인 추론 능력을 보존할 수 있게 된다.

가중치 다운로드 스크립트에서도 ds4f-q2, glm53-q2, qwen38-q2처럼 프로젝트가 자체 튜닝한 양자화 프로파일 명칭이 사용된다. 또한 중요도 행렬(imatrix)을 기반으로 추가 보정된 프로파일(pro-q2-imatrix 등)도 함께 제공된다.

디스크 시민으로서의 KV 캐시 — SSD 영속화와 프리필 생략

에이전트 코딩 환경에서 가장 빈번하게 발생하는 낭비는 동일한 코드베이스 프롬프트를 매 세션마다 처음부터 다시 계산하는 프리필(prefill) 오버헤드다. 수만 토큰에 달하는 컨텍스트를 다룰 때 프리필은 막대한 시간과 메모리를 소모한다.

ds4는 KV 캐시를 메모리에만 가두지 않고 「디스크의 1등 시민(disk citizen)」으로 격상시켰다. 엔진은 렌더링된 프롬프트 프리픽스의 SHA1 해시값을 계산하여 이를 키로 삼고, 긴 프리픽스에 대한 KV 캐시 상태를 SSD에 직접 영속화한다. 데모 터미널 기록에 나타난 실제 동작 방식은 다음과 같다.

프로세스가 재시작되더라도 이전에 저장된 프롬프트 프리픽스와 일치하는 해시가 감지되면, 모델은 연산을 재수행하지 않고 SSD에서 직렬화된 KV 캐시를 메모리로 즉시 로드한다. 수천 라인의 파일을 컨텍스트에 올린 상태에서 세션이 끊기더라도, 재기동 시점에 즉각적인 질의응답이 재개된다. 긴 컨텍스트 에이전트 작업에서 세션 지속성을 확보하는 전략은 로컬 에이전트 코딩 실현성 분석에서도 강조된 핵심 요소다.

단일 엔진과 세 가지 인터페이스 — CLI·서버·네이티브 에이전트

ds4 아키텍처의 독특한 면모는 단일 C 추론 코어 위에서 세 가지 상호작용 레이어가 완전히 동일한 모델 상태와 KV 캐시를 공유한다는 점이다.

  • ./ds4: 터미널 기반의 대화형 CLI 도구. /read, /think, /ctx 등의 명령어를 내장하여 단독 실행 환경을 제공한다.
  • ./ds4-server: 외부 개발 도구 연동을 위한 로컬 HTTP API 서버. --ctx 100000 등으로 컨텍스트 크기를 지정해 실행한다.
  • ./ds4-agent: 지속적인 코딩 세션과 도구 호출(tool use)을 자체 수행하는 네이티브 코딩 에이전트.

특히 ./ds4-server는 업계 표준인 OpenAI 호환 규격(/v1/chat/completions, /v1/responses)뿐만 아니라 Anthropic 호환 규격(/v1/messages)을 네이티브로 제공한다. 따라서 Claude Code, OpenAI Codex CLI, OpenCode, Pi 등의 외부 코딩 에이전트에서 베이스 URL을 로컬 localhost 엔드포인트로 설정하기만 하면, 클라우드 API 호출 대신 로컬 ds4 인스턴스로 모든 요청을 전환할 수 있다. 데스크톱 통합 도구의 연결성은 DeepSeek Harness 분석과도 맞닿아 있다.

지원 모델 계열과 64GB~1024GB 하드웨어 적합성 기준

ds4 공식 사이트의 적합성 검사기(Fit Check)와 하드웨어 가이드는 가용 메모리 용량에 따른 구체적인 실행 기준을 명시하고 있다. 대형 오픈 모델을 무턱대고 다운로드하기 전에 자신의 하드웨어 등급을 확인해야 한다.

플랫폼별로는 Apple Silicon(Metal)이 최우선 지원 플랫폼이며, NVIDIA DGX Spark 및 일반 CUDA Linux 환경, 그리고 AMD Strix Halo(Framework Desktop 등) ROCm 환경이 공식 지원 범위에 포함된다. 단, Strix Halo 환경에서는 V4 Flash와 GLM 경로가 지원되며 V4.1 및 Qwen3.8은 ROCm 대상에서 제외되어 있다.

실측 벤치마크 분석 — 프리필과 생성 속도의 분리 평가

로컬 대형 모델의 성능을 논할 때 가장 흔한 오류는 단일 토큰 생성 속도만 측정하는 것이다. 에이전트 워크플로에서는 수만 토큰의 코드베이스를 읽어 들이는 프리필(prefill) 처리량이 작업 체감의 80% 이상을 좌우한다. ds4 공식 벤치마크 표는 프리필과 생성을 엄격히 분리하여 수치를 제시한다.

  • M5 Max (128GB, Q2, 2,048 토큰): 프리필 790.2 토큰/초, 생성 39.4 토큰/초.
  • M5 Max (128GB, Q2, 65,536 토큰): 프리필 398.5 토큰/초, 생성 27.6 토큰/초.
  • DGX Spark (128GB, Q2, 2,048 토큰): 프리필 825.8 토큰/초, 생성 18.1 토큰/초.
  • DGX Spark (128GB, Q2, 65,536 토큰): 프리필 823.0 토큰/초, 생성 13.8 토큰/초.

이 측정치는 하드웨어 아키텍처의 차이를 선명하게 드러낸다. 통합 메모리 대역폭이 높은 Apple Silicon은 긴 컨텍스트에서도 생성 속도(27.6 t/s)를 비교적 견고하게 유지한다. 반면 DGX Spark는 65K에 달하는 극한의 긴 컨텍스트에서도 프리필 속도가 823.0 토큰/초로 거의 저하되지 않는 압도적인 병렬 연산 특성을 보여준다. 참조 32K 컨텍스트 기준으로는 M5 Max가 생성 34.4 t/s 및 프리필 557 t/s, DGX Spark GB10이 생성 14.4 t/s 및 프리필 856 t/s를 기록했다.

빌드와 실행 절차 — 백엔드별 컴파일과 안전한 명령어

ds4는 순수 C 언어로 작성되었으며 별도의 복잡한 패키지 의존성을 요구하지 않는다. 공식 문서에 명시된 설치 및 구동 단계는 다음과 같이 단순하다.

가중치 다운로드는 프로젝트 저장소 클론 후 전용 스크립트를 통해 수행된다.

git clone https://github.com/antirez/ds4
                    cd ds4 && ./download_model.sh ds4f-q2

컴파일은 호스트 머신의 가속기에 맞춘 make 타깃을 호출한다.

make              # macOS Metal
                    make cuda-spark   # Linux NVIDIA DGX Spark
                    make cuda-generic # Linux generic CUDA
                    make strix-halo   # Linux AMD Strix Halo
                    make cpu          # CPU-only for diagnostics

구동 단계에서는 대화형 CLI를 직접 띄우거나, 컨텍스트 길이를 명시하여 API 서버를 시작할 수 있다.

./ds4
                    ./ds4-server --ctx 100000
                    ./ds4 -m gguf/GLM-5.3-Flash-Q2.gguf --ctx 32768
                    ./ds4 --ctx 8192 --prefill-chunk 1024

외부 코딩 도구를 연동할 때는 ds4-server가 열어 둔 로컬 엔드포인트를 지정한다.

# OpenAI 호환 엔드포인트:
                    POST /v1/chat/completions
                    # Anthropic 호환 엔드포인트:
                    POST /v1/messages
                    # Responses 엔드포인트:
                    POST /v1/responses

확인하지 못한 것

  • SSD에 저장되는 KV 캐시의 자동 만료(TTL) 정책이나 용량 제한(eviction) 관리 메커니즘은 공식 문서에 명시되지 않았다.
  • Windows 환경(WSL2 제외)에서의 네이티브 MSVC 컴파일 지원 여부는 기재되지 않았다.
  • Claude Code 및 Codex 연동 시 복잡한 멀티턴 도구 호출(Tool Calling / Function Calling)의 파싱 정확도 통계는 문서에 없다.
  • AMD ROCm 백엔드에서 Qwen3.8과 DeepSeek V4.1 모델이 제외된 구체적인 기술적 원인(커널 미구현 등)은 밝혀지지 않았다.
  • 두 대의 Mac Studio를 분산 연결할 때 Thunderbolt 링크 외의 일반 10GbE 이더넷 환경에서의 지연 시간 수치는 측정되지 않았다.
  • 비전(Vision) 입력 처리 시 지원되는 구체적인 해상도 제한과 비전 인코더의 메모리 오버헤드는 수치로 제공되지 않았다.
  • 2비트 비대칭 양자화 적용 시 원본 FP16 모델 대비 벤치마크 점수(MMLU 등)의 정량적 정밀도 손실률은 제시되지 않았다.
  • CPU 전용 진단 모드(make cpu)에서의 실제 토큰 생성 속도는 기재되지 않았다.
