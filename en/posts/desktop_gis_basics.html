After You Add a Latitude and Longitude Column

What makes geographic data different from ordinary data - reference frames, vector and raster, spatial queries, and the moment coordinates point at a person

August 30, 2026 Dev & Infra

Adding a latitude and a longitude column to a table of locations takes half a day. Points appear on a map, the screen looks convincing, and the work seems basically done. The trouble starts when the second dataset arrives. You drop a boundary file from another team onto the same view and your points sit outside the boundaries. Both sets of numbers are correct. They still do not agree.

In late August 2026 a lightweight desktop GIS surfaced on GeekNews. Per its repository description it is built on Tauri v2 with React and TypeScript, layered over MapLibre GL JS, DuckDB-WASM Spatial and deck.gl, and it loads vector layers from GeoJSON, GeoParquet, GeoPackage and Shapefile. A layer panel handles visibility, opacity and ordering; fill, outline and similar styling can be edited live; attribute tables can be opened; and working state saves to a project file. Basemaps, layer controls and other features attach as plugins, and an optional Python sidecar can be enabled. The license is stated as MIT. That is the extent of what the repository documents.

What interests me is not that particular program but the question behind it: why does geographic data need a category of software of its own? A coordinate looks like two ordinary numbers, yet in practice it behaves unlike any other numeric column. This piece works through the differences one at a time.

This article does not recommend adopting any particular tool and makes no claim about one product being better than another. The repository that prompted it serves only as a starting point, and since it publishes no performance or capacity figures, none appear here. It also leaves aside the question of how a map should look - the visual impressions a projection creates, the conventions of cartographic display. What follows is about the nature of the data and how it is processed.

1. A location is not two numbers

Latitude 37.5, longitude 127.0. Writing those two numbers down does not fix a point on Earth. Something is missing: what were they measured against?

The Earth is not a smooth sphere and its surface is uneven. Calculation needs a simple mathematical model, so an ellipsoid of revolution is used - but which ellipsoid was chosen, and how it was fitted to the actual planet, differs between datasets. That pairing of chosen ellipsoid and chosen fit is the datum. Some datums are set to fit the whole globe on average; others are set to fit one country's territory as closely as possible. The latter are more accurate inside that country and badly wrong outside it.

A second layer sits on top. Latitude and longitude are angles on a curved surface, which makes distance and area awkward to compute, so the surface is flattened into planar coordinates in metres. How it is flattened changes the numbers for the same point completely. Degree values and metre values are not the same kind of quantity to begin with.

The third layer is convention. Some places write the axes as latitude-longitude, others as longitude-latitude. Swapped values still look plausible as numbers, so you usually discover the problem when a point lands on the wrong continent.

Coordinates therefore do not travel alone. The reference system they were measured in has to travel with them, and the identifier most widely used for that is the EPSG code. The four below come up regularly in work involving Korean data.

2. Which is why stacked layers drift apart

The moment data from different sources goes onto one screen, all of the above becomes concrete. One layer arrives in degrees, another in metres, a third built on a cadastral coordinate system. Stacking the three means moving them onto a single basis. That move is a transformation.

Transformations come in two kinds with different characters. Changing only the projection within one datum is a defined formula: deterministic, with error at the level of floating-point rounding. Converting between two different datums is an approximation. The relationship between two datums does not reduce to one clean equation, so the work is done with parameter sets fitted to measured points or with regional correction grids. Several such parameter sets can exist depending on which observations they were fitted to, and whichever you pick, a residual remains.

The result shows up as visible misalignment. The map looks fine from far away and separates as you zoom. A road centreline runs through the inside of a building, two agencies' boundary lines sit parallel but shifted, a coastal point floats offshore. None of it matters on a low-accuracy display, and all of it matters the moment you compute an area or decide whether two parcels are adjacent.

  • Transform once, from the original. Going A to B to C and back to A accumulates residuals. Rather than re-transforming intermediate outputs, return to the source and go to the target system in one step.
  • Never generalize an offset you eyeballed. A correction that lines things up perfectly in one neighbourhood is wrong elsewhere. The size of the drift varies with position.
  • Files often do not declare their system. Sidecar metadata goes missing constantly, leaving the recipient to guess. Digit count and magnitude let you infer a system, but inference is not confirmation.
  • Make the choice of a single basis an early decision. Unify late and you will find outputs already built in several systems and referencing each other.

3. Vector and raster

Geographic data is held two ways. One draws features as points, lines and polygons - vector. The other cuts space into a grid and stores a value per cell - raster. They do not substitute for each other, because what they represent well is different from the start.

Vector is strong on things with edges: buildings, parcels, roads, administrative districts - anything where you can say that this much is one object. It is a list of vertex coordinates plus attributes, so lines stay crisp at any zoom and filtering by attribute is natural. Its weakness is continuously varying quantities. Elevation or temperature, which have a value everywhere, only fit into vector by force.

Raster is the reverse. Satellite imagery, elevation models, rainfall distribution - things where values are spread across the whole space. One value per cell keeps computation simple, and overlaying two rasters to add or subtract cell by cell works immediately. Its weakness is that it has no notion of an object; the raster itself does not know which cells form one building. And resolution is fixed when the data is made, so you cannot later look closer.

Vector carries one more concern: topology. Do two adjacent districts meet with no gap and no overlap? A list of coordinates does not guarantee it. Two polygons digitized separately can describe their shared edge slightly differently, and that sliver stays invisible on screen until the sum of areas fails to match. Raster has no such problem, because cells cannot overlap or leave a gap.

4. Size becomes a problem in a different way

In an ordinary table, weight is measured in rows. A million rows cost a million rows' worth. That intuition transfers poorly to geographic data, where the cost is set not by row count but by the extent and the resolution you are working at.

For raster the relationship is plain arithmetic. Halve the cell size and covering the same area takes four times as many cells. A decision to go one step finer returns immediately as four times the storage and four times the computation. Doubling the extent behaves the same way. Slightly more detail and slightly more coverage attach quadratically, not linearly.

Vector goes wrong differently. Nothing guarantees a row is light. One coastline can be a single geometry with tens of thousands of vertices while the rectangular building beside it has five. Both are one row in the table and their weights are not comparable. Counting rows therefore tells you nothing about whether a dataset is heavy.

This is where drawing only what is on screen comes from. Instead of loading everything into memory and rendering it at once, a mapping tool pulls out only the part matching the current view and the current scale. Pre-cut tiles, pre-reduced low-resolution copies per scale, and simplified geometry for distant views are the machinery for that.

  • Simplification is for display. Dropping vertices speeds rendering but changes lengths and areas and can open slivers between neighbouring polygons. Feed simplified data into analysis and values go quietly wrong.
  • Separate the source from the display copy. Decide this early or you will later be unable to tell which file is which.
  • Narrow the extent first. Clipping away what is off screen removes most of the cost. Working on a dataset cut to the area you need is the cheapest optimization available.
  • Let the requirement set the resolution. As fine as possible is not a requirement, it is a cost decision. What you have to determine dictates the resolution you need.

5. What a spatial query is

Questions asked of geographic data take roughly three shapes. Does this fall inside that shape? Does it overlap? What is nearest to here? None of the three is served well by an ordinary index.

The reason lies in what an index does. The familiar kind lines values up in order, which works beautifully for one axis. But position has two. Sorting by latitude narrows the latitude range and filters nothing in longitude, and even after bounding both axes the work of testing whether a point lies inside an actual polygon remains entirely undone. Nearest-neighbour is worse: it is a ranking problem rather than a range condition, so without a radius you logically have to compare against everything.

The idea behind a spatial index is to replace the shape with something that is not a shape and filter on that. In place of a complicated polygon stands the smallest rectangle enclosing it. Deciding whether two rectangles overlap comes down to comparing four numbers. If the rectangles do not overlap, the original shapes certainly do not, so most candidates can be discarded safely at this stage.

Processing therefore becomes two phases. The index filters down to candidates; only the survivors are tested exactly against real geometry. The first phase is fast, approximate and never drops a true match. The second is slow, exact and applied to few. That structure buys the cost reduction without making the answer wrong. Besides grouping rectangles upward into a tree, partitioning space into a grid or quadtree and numbering the cells, or folding two dimensions into a single ordered value so that an ordinary index applies, are the same goal solved differently.

  • Loose rectangles cost efficiency. A shape stretched along a diagonal has an enclosing rectangle far larger than its actual footprint, so it keeps surviving the filter without ever overlapping.
  • Bound the nearest query. Asking for the nearest without a radius widens the search even with an index. In practice the question usually becomes the five nearest within a radius.
  • Distance in degrees is not uniform. Apply a radius directly to latitude and longitude values and north-south and east-west come out as different real distances. The gap widens with latitude.
  • Check that geometry is valid first. Self-intersecting or unclosed polygons produce unpredictable results in overlap and containment tests. Invalid geometry is a data problem, not an index problem.

6. Where the desktop still earns its place

A large share of map work now finishes inside a browser. Some of it does not, and those cases are why desktop tools have not gone away.

First is the size of the source. A browser works by loading what it receives into memory, so datasets exist that simply cannot be shipped. Often the natural arrangement is a source on local disk with only the needed portion read in place. Second is offline work. Field survey, surveying proper, disaster response - the places without connectivity are frequently the places where the data is needed most. Third is precise editing. Snapping vertices one at a time and combing through topology errors is high-touch work, and a round-trip delay on every action makes the task unworkable rather than merely slow. Fourth is data that must not leave. Situations arise where the whole pipeline has to complete locally.

Conversely, sharing and viewing, several people talking over the same screen, and checking small standardized datasets all go better in a browser. It is less a choice between the two than a case of the nature of the task deciding where it belongs. That is why the common arrangement is heavy work on the source locally and distribution of results on the web.

7. Location data can point at a person

A list of coordinates looks anonymous. No names, no phone numbers, just numbers in rows. Yet the sequence of places a person leaves behind is close to an identifier in itself.

One study addresses this directly. Unique in the Crowd, published by de Montjoye and colleagues in Scientific Reports in 2013, analysed fifteen months of mobility data for one and a half million people and reported that when position is recorded hourly at the spatial resolution of carrier antennas, four spatio-temporal points are enough to uniquely identify 95 percent of individuals. Striking as that is, the second finding matters more in practice. The same paper reports that uniqueness decays only as roughly the one-tenth power of resolution. Coarsening the temporal and spatial precision does not buy a matching amount of anonymity.

The reason makes sense on reflection. The combination of places each person frequents differs from everyone else's. Where someone is at night and where they are during the day already narrows the field dramatically. Blurring coordinates makes each point fuzzier; it does not dissolve the uniqueness of the combination.

  • Truncating decimals - the points snap to a grid and the shape of the trajectory survives intact. Which cells were visited in which order is still there.
  • Adding random jitter - when the same place is recorded repeatedly, the average of the jittered values drifts back toward the true position. More observations, weaker protection.
  • Replacing only the identifier - if the trajectory shape remains, it can be joined against other data. A fresh identifier does not sever the link.
  • Publishing aggregates - this looks safe, but in sparsely populated cells the aggregate becomes one person's value. Without a minimum-count condition per cell it is exposed outright.
  • Coordinates that ride along - capture location embedded in photo files, the map extent left in a screenshot, position recorded in logs, all leaving with the main dataset.

So the decision point moves earlier. Ahead of asking how to blur before export sits a different question: is there a reason to collect at full resolution at all, how long is it retained, and who can reach the raw data? Precision never collected cannot leak. Anonymization is hard; reducing what is collected is a choice available at design time.

It is also worth noting that some jurisdictions regulate location information under separate rules. Requirements should be confirmed for the relevant jurisdiction before data is published or handed to a third party, and this article does not substitute for that assessment.

8. Provenance and licensing

A single map view usually stacks data from several sources: the basemap behind everything, administrative boundaries, road networks, addresses, plus whatever layers you made yourself. Each arrived under different terms. And the license of the tool and the license of the data are entirely separate matters. The repository that prompted this article states MIT for its code, which says nothing about what you may do with what you display in it.

Three axes generally need checking. May it be used commercially? May derived output be redistributed? If attribution is required, where and in what wording? A few further items attach to those.

  • Does output inherit the terms? Some conditions require that anything built from the data carries the same conditions. That causes no trouble internally and bites the moment something goes out.
  • Tile services carry separate terms of use. The conditions on the data and the terms of the service delivering it are two different documents. Rate limits and permitted purposes live in the latter.
  • Institutional data may come with procedure. Application, stated purpose and restrictions on onward provision are sometimes attached separately.
  • Record provenance per layer. Where it came from, what the terms were, when they were checked - if that is not kept in the project, you cannot reconstruct it months later. Data you cannot trace becomes data you cannot use.

Terms differ by source and are revised over time. This article cannot state any particular source's conditions with certainty. What can be said is that the conditions of that source have to be checked directly before use.

9. What comes up additionally in Korea

Working with Korean data adds two more things: a coordinate systems question and a regulatory one.

On coordinate systems, Korean datasets do not arrive only in globally common frames. EPSG:5179 and EPSG:5186 in the table above are examples. Both are projected systems on the Korean datum, but 5179 covers the country as a single extent while the registry records 5186 as covering the belt between 126 and 128 degrees east. In other words, a family of systems exists in which the territory is managed as several belts, and joining data from different belts without checking the system produces misalignment. The registry lists cadastre and topographic mapping as the uses for 5186.

On the regulatory side, a procedure exists concerning the export of survey results abroad. The National Geographic Information Institute maintains operating rules for a consultative body on the overseas export of survey results and publishes amendments to them, and the enabling statute is cited as the Act on the Establishment and Management of Spatial Data. What this article has confirmed is that such a framework and a responsible agency exist - no more than that.

Which datasets fall within scope, what processing counts as export, and how storing or processing on overseas infrastructure is treated are not matters this article judges. Case-by-case determinations must be confirmed directly with the National Geographic Information Institute and other relevant authorities.

In practice the first questions come down to three. What coordinate system is this data in? How far may it be published or provided? Are there conditions on where it is stored and processed? All three need answers before work starts. Find the answers after processing and the outputs you already built become the problem.

10. At what point do you need GIS?

Reading this far invites the opposite question. Does every job involving a map need machinery like this? No. Two extra columns in a table really are enough in a great many cases.

What you want to doTwo columns sufficeSpatial capability needed
Storing coordinates and showing themSufficient—
A rough within-radius listUsually sufficientNeeded if accuracy is at metre level
Deciding if a point is inside a district—Boundary geometry and containment tests
Using area or length as a value—Must be computed on a projected system
Overlaying different sources—Frame checking and transformation
Imagery, elevation and other grids—Raster processing
Different rendering per scale—Simplification and a tile structure

Three questions narrow the judgment. First, does an area enter the problem? Storing and plotting points ends with two columns. The moment the question is whether this point is inside that zone, geometry is required. Second, is there more than one source? With one, the frame problem never surfaces. With two, transformation arrives. Third, is the accuracy requirement at metre level? Nearby survives simple arithmetic, but if a value decides something, it has to be computed on a proper coordinate system.

There is also a wide middle ground. A spatial extension in the database is often enough, with no need for a separate desktop tool at all. You cross to the next step when the source gets large or when the work requires seeing and fixing things by eye.

In summary

What sets geographic data apart reduces to four things. A basis travels with the numbers. Size is set by extent and resolution rather than row count. Queries filter by space rather than by order along one axis. And those numbers can point at a person.

Tools handle much of the first three. They read the coordinate system and convert, draw only the visible extent, build the spatial index. They do not handle the fourth. Whatever software you use, the fact that blurring coordinates is not anonymization stays exactly where it was, and it returns as a question to settle at collection time.

Three decisions made at the start get cheaper for having been made. Declare the coordinate system on every layer. Split source data from display copies from day one. Fix how fine you collect and how long you keep it before the data piles up. Each takes a day to decide, and undoing the absence of the decision takes far longer.
