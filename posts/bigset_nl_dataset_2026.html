bigset — 자연어 한 문장으로 살아있는 웹 데이터셋을 만드는 오픈소스 도구

AI 에이전트+웹 스크래핑+ETL의 결합이 데이터 수집을 어떻게 민주화하는가

2026-06-24 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 데이터 수집의 병목은 여전히 사람 손에 있다

2026년 6월 기준, AI가 코드를 짜고 문서를 요약하고 이미지를 생성하는 시대가 됐지만, 정작 "지금 채용 중인 AI 스타트업 목록을 뽑아줘"라는 요청 하나를 처리하려면 여전히 엔지니어가 scraper를 짜거나, 데이터 팀이 파이프라인을 설계하거나, 누군가가 수작업으로 스프레드시트를 채워야 한다. 이 병목은 생각보다 오래됐다. 웹에는 방대한 구조화 가능 데이터가 흩어져 있지만, 그것을 쓸 수 있는 표로 만드는 진입 비용이 너무 높아 소수의 기술 조직만 누려 왔다.

bigset은 이 병목을 자연어로 부수겠다는 시도다. TinyFish가 개발한 오픈소스(AGPL-3.0) 멀티에이전트 시스템으로, 사용자가 한 문장을 입력하면 AI가 스키마를 추론하고 자율 에이전트들이 라이브 웹을 뒤져 검증된 데이터를 표로 반환한다. 주기적 자동 갱신도 지원해 "살아있는 데이터셋"이 된다. 이 글은 bigset의 아키텍처와 실제 동작을 분석하고, 진짜 유용한 시나리오와 놓치면 안 되는 한계, 그리고 이 도구가 제기하는 법적·윤리적 질문을 정직하게 다룬다.

1. bigset이란 — 자연어에서 구조화 데이터셋으로

bigset의 핵심 약속은 단순하다. 자연어 한 문장 → 구조화 데이터셋. "현재 엔지니어를 채용 중인 YC 기업, 펀딩 단계·위치·채용공고 수 포함"이라고 입력하면 그 형태의 표가 나온다. 사용자가 컬럼을 설계하거나 XPath를 짜거나 ETL 파이프라인을 구성할 필요가 없다.

1.1 핵심 기능 요약

2026년 6월 기준 bigset이 공개한 기능은 다음과 같다. 스키마 자동 추론: 사용자 입력에서 컬럼명·데이터 타입·기본 키를 AI가 결정한다. 병렬 웹 에이전트: 개체마다 독립 서브에이전트가 병렬로 라이브 웹을 조사한다. 중복 제거와 출처 추적: 기본 키 기반 중복 제거 후 각 행에 출처 URL이 자동 기록된다. 자동 갱신: 30분·6시간·12시간·일간·주간 주기로 에이전트가 재실행돼 데이터셋을 최신 상태로 유지한다. 내보내기: CSV·XLSX 형식으로 다운로드 가능하다.

1.2 설치와 시작

bigset은 npm 패키지로 제공된다. npm install --global @adamexu/bigset 후 bigset 명령으로 로컬 UI를 127.0.0.1:3500에 올릴 수 있다. Node.js 22+가 필요하며, TinyFish API 키(웹 검색·페이지 가져오기), OpenRouter 키(LLM 호출), Clerk(인증)까지 세 가지 외부 서비스 연동이 필요하다. CLI로는 bigset create "topic" --rows 10 --wait --csv output.csv 형태로 직접 데이터셋을 만들 수 있다.

2. 아키텍처 — 멀티에이전트 파이프라인의 5단계

bigset의 내부 동작을 이해하면 어디서 잘 작동하고 어디서 실패하는지가 보인다. 5단계 파이프라인이다.

2.1 1단계: 스키마 추론 (Claude Sonnet)

자연어 입력이 들어오면 가장 먼저 Claude Sonnet이 스키마를 추론한다. 웹에 접근하기 전, 언어 이해만으로 "이 문장에서 행은 무엇이고, 컬럼은 무엇이며, 어디서 찾아야 하나"를 결정한다. 이 단계가 전체 품질의 상한선을 결정한다. 입력이 모호하거나 멀티해석 가능하면 스키마 추론이 어긋나고 이후 모든 단계가 엉뚱한 방향으로 흐른다.

2.2 2단계: 오케스트레이터 에이전트 (Qwen)

스키마가 확정되면 Qwen 기반 오케스트레이터가 TinyFish Search를 활용해 "행을 이룰 개체들"을 광범위하게 발견한다. 이 단계는 얼마나 많은 후보를 찾아내느냐 — 즉 리콜(recall)을 결정한다. 검색 품질이 낮거나 타깃 데이터가 잘 색인되지 않은 곳에 있으면 후보 목록 자체가 부실해진다.

2.3 3단계: 병렬 서브에이전트

오케스트레이터가 후보 개체 목록을 만들면, 각 개체마다 독립 서브에이전트 하나가 배정돼 병렬로 실행된다. 핵심 제약이 있다. 서브에이전트당 도구 호출 6회 한도다. 이 한도 안에서 개체의 세부 데이터를 최대한 수집해야 한다. 복잡한 개체(예: 재무 정보·여러 페이지에 분산된 데이터)는 이 한도 내에서 충분히 처리되지 않을 수 있다. 병렬 처리가 속도를 높이지만, 한도가 정밀도의 천장을 만든다.

2.4 4단계: 중복 제거·출처 기록

병렬 에이전트들이 반환한 데이터에서 기본 키 기반 중복 제거가 이루어진다. 동시에 각 행에 출처 URL이 자동 기록된다. 이 출처 추적은 단순한 편의 기능이 아니라 데이터 신뢰성의 핵심이다. 결과를 받은 사람이 "이 숫자가 어디서 왔나"를 확인할 수 있어야 교차 검증이 가능하다.

2.5 5단계: 최종 표 생성과 내보내기

검증된 데이터가 최종 표로 조립되어 UI에서 탐색 가능하고 CSV·XLSX로 내보낼 수 있는 상태가 된다. 전체 과정에 2~5분이 소요된다. 실시간 결과가 아니라 에이전트들이 실제로 웹을 뒤지는 시간이다.

3. 데이터 수집의 민주화 — 무엇이 달라지나

bigset이 표방하는 "데이터 수집 민주화"는 과장처럼 들릴 수 있다. 그러나 실제로 무엇이 달라지는지를 기존 방식과 비교하면 주장의 핵심이 보인다.

3.1 기존 방식의 진입 비용

기존에 "현재 채용 중인 AI 스타트업 목록"을 만들려면 세 가지 경로가 있었다. 첫째, 엔지니어가 scraper를 직접 작성한다. Python+BeautifulSoup+Playwright 조합, 대상 사이트별 선택자 유지보수, rate limit 처리, 스케줄러 설정이 필요하다. 진입 비용이 높고 유지보수 부담이 크다. 둘째, 유료 데이터 제공자를 쓴다. Clearbit, ZoomInfo, LinkedIn Data API 같은 서비스는 비용이 높고 커버리지가 제한적이며 갱신 주기가 느리다. 셋째, 수작업 수집이다. 인력 비용이 높고 대규모화가 어렵다. bigset이 제거하는 것은 이 진입 비용의 대부분이다. 비기술직 사용자도 자연어로 요청을 표현할 수 있고, 에이전트가 선택자·파이프라인·스케줄러를 대체한다.

3.2 AI 에이전트+웹 스크래핑+ETL의 결합

bigset이 흥미로운 이유는 세 가지 기존 범주를 하나의 플로우로 묶기 때문이다. AI 에이전트(LLM 기반 스키마 추론·자율 탐색), 웹 스크래핑(라이브 웹 데이터 수집), ETL(추출·변환·적재·갱신 스케줄)이 단일 자연어 입력으로 통합된다. 이 결합이 단순한 편의 도구를 넘어 데이터 접근 방식의 패러다임 변화라고 볼 수 있는 이유다. 기존에는 이 세 레이어가 각각 전문 기술과 도구를 요구했다.

3.3 활용 사례 — 어디에 쓸 수 있나

bigset이 GitHub README와 공개 문서에서 제시한 예시와 본인이 파악한 적합한 시나리오를 정리한다. 경쟁 인텔리전스: 특정 산업의 채용 현황·자금 조달 단계·제품 출시를 주기적으로 추적. 시장 조사: 오픈소스 프로젝트별 GitHub 스타·라이선스·지원 환경 비교표. 가격 모니터링: GPU 소매가, AI 모델 API 단가 등 빠르게 바뀌는 수치의 자동 갱신 표. 리드 발굴: 특정 조건의 기업 목록을 영업·파트너십 팀이 비기술직으로 직접 생성. 연구 보조: 학술·저널리즘 분야에서 다수 개체의 공개 속성을 빠르게 집계.

4. 한계 — 정직하게 짚어야 할 5가지

bigset은 공식 문서에서 스스로를 "실험 단계 소프트웨어"로 규정한다. 어디서 기대치를 낮춰야 하는지 명확히 봐야 한다.

4.1 스키마 추론의 불완전성

1단계 스키마 추론은 자연어 이해에 의존한다. 입력이 모호하거나 도메인 지식이 많이 필요한 경우 추론이 어긋난다. bigset 공식 문서도 "스키마 추론이 항상 완벽하지 않다"고 명시한다. 특히 멀티해석 가능한 질의(예: "좋은 스타트업" — "좋다"의 기준이 없음)나 고도로 전문화된 도메인에서는 결과물의 컬럼 구성이 기대와 다를 수 있다.

4.2 서브에이전트 도구 호출 한도

서브에이전트당 도구 호출 6회 제한은 효율과 정밀도의 맞교환이다. 한 개체의 데이터가 여러 페이지에 흩어져 있거나 동적 로딩이 필요한 경우, 6회 안에 충분한 데이터를 수집하지 못하면 해당 행이 부분적으로만 채워진다. 이 한도는 병렬 처리 비용을 통제하기 위한 설계 선택이지만, 복잡한 데이터 요구에는 제약이 된다.

4.3 LLM 환각과 데이터 정확성

LLM 기반 추출의 근본 한계다. 모델이 실제 웹 페이지에서 읽은 내용을 잘못 해석하거나, API 타임아웃·레이트 리밋 상황에서 응답이 불완전해질 수 있다. 유사 도구(ScrapeGraphAI-100k)의 연구에서 LLM 기반 웹 추출의 스키마 검증 통과율이 93%대로 보고됐는데, 이는 구문적 정합성일 뿐 의미적 정확성은 별개다. bigset이 각 행에 출처 URL을 기록하는 이유가 여기 있다. 중요한 데이터는 반드시 원본을 직접 확인해야 한다.

4.4 외부 서비스 의존성과 비용

bigset 자체는 오픈소스지만, 동작에 TinyFish API·OpenRouter·Clerk 세 가지 유료 외부 서비스가 필요하다. 이는 "오픈소스"이지만 "무료"는 아니라는 뜻이다. 특히 대규모 데이터셋이나 고빈도 자동 갱신은 API 비용이 빠르게 누적된다. 사용자당 월 2,500회 행 작업 한도도 있다. 프리티어 기준으로 대규모 운영은 어렵다.

4.5 SQL 미지원과 기능 미성숙

현재(2026년 6월 기준) SQL 쿼리로 데이터를 필터링하거나 조인하는 기능이 없다. 로드맵에 포함돼 있지만 미출시다. 생성된 데이터셋을 세부 조건으로 분석하려면 CSV를 내보내 별도 도구(스프레드시트, pandas, DuckDB 등)로 처리해야 한다. 오픈소스로서의 커뮤니티와 생태계 성숙도도 초기 단계다.

5. 법적·윤리적 질문 — robots.txt, 개인정보, EU AI Act

bigset이 "라이브 웹에서 데이터를 수집"한다는 사실은 기술적 편의의 이면에 중요한 질문을 제기한다. 이 부분을 회피하면 절름발이 분석이다.

5.1 robots.txt와 법적 경계

2026년 기준 미국·EU 법제에서 공개 웹 데이터 스크래핑은 원칙적으로 합법이다. 그러나 robots.txt 위반은 단순한 예의 문제가 아니다. CFAA 유사 법률에서 명시적 접근 제한을 우회한 것으로 해석될 수 있고, EU 맥락에서는 계약 위반이 될 수 있다. 중요한 점은 robots.txt는 접근 제어만 표현하고 사용 목적을 표현하지 못한다는 것이다. "검색 색인은 허용하되 AI 훈련은 금지"처럼 세밀한 의도를 표현하는 표준(ai.txt, llms.txt)이 논의되고 있지만, 2026년 현재 법적 구속력 있는 표준은 없다. bigset 사용자는 수집 대상 사이트의 robots.txt와 이용약관을 직접 확인해야 한다.

5.2 개인정보와 GDPR

bigset이 수집하는 데이터에 개인 식별 정보(이름, 이메일, 직위 등)가 포함되면 GDPR·국내 개인정보보호법의 적용을 받는다. 공개 웹에 있는 정보라도 이를 수집·조합·저장하는 행위는 정보 주체의 권리와 데이터 처리 근거를 고려해야 한다. bigset은 이 부분을 도구 차원에서 자동으로 처리해 주지 않는다. 사용자 책임이다.

5.3 EU AI Act와 데이터 출처 투명성

EU AI Act는 AI 시스템 구축에 사용되는 데이터의 출처 투명성을 요구한다. bigset이 각 행에 출처 URL을 기록하는 설계는 이 요건에 부분적으로 대응한다. AI 학습 데이터나 고위험 AI 시스템 구축에 bigset 결과물을 사용한다면, 더 엄격한 데이터 거버넌스 문서화가 필요하다. "데이터가 어디서 왔는지"를 증명할 수 있어야 한다는 점에서 bigset의 출처 추적 설계는 올바른 방향이지만, EU AI Act의 전체 요건을 충족하기엔 아직 충분하지 않다.

6. bigset이 보여주는 방향 — ETL의 LLM화

bigset 자체의 완성도를 넘어, 이 도구가 가리키는 방향이 중요하다. 데이터 엔지니어링의 ETL 레이어가 LLM으로 추상화되는 흐름이다.

6.1 코드 없는 데이터 파이프라인

전통적 ETL은 Extract(데이터 소스 커넥터), Transform(스키마 매핑·정제), Load(타깃 저장소 적재)를 각각 코드와 설정으로 관리했다. bigset은 이 세 단계를 자연어 한 문장으로 추상화한다. 불완전하지만 방향은 명확하다. LLM이 자연어에서 의도를 파악하고, 에이전트가 실행을 맡는 구조가 ETL 전 과정에 적용되면, 데이터 파이프라인의 진입 장벽은 코딩 역량에서 질문 능력으로 이동한다.

6.2 "살아있는 데이터셋"의 의미

bigset의 자동 갱신 기능은 단순한 편의가 아니다. 전통적 데이터셋은 수집 시점의 스냅숏이다. bigset은 사용자가 설정한 주기(최소 30분)마다 에이전트가 다시 실행돼 데이터셋이 항상 현재 웹 상태를 반영한다. 채용 현황, 가격 정보, 오픈소스 프로젝트 통계처럼 변화 속도가 빠른 데이터에서 이 차이는 결정적이다. "스냅숏이 아닌 라이브 데이터"는 데이터의 유효기간 문제를 다르게 다루는 접근이다.

6.3 경쟁 도구와의 비교

bigset이 서 있는 위치를 기존 도구와 비교해 보자.

bigset의 차별점은 라이브 갱신과 완전 자연어 인터페이스의 결합이다. 다만 진입 비용이 낮다는 것은 외부 서비스 연동 비용이 없다는 뜻이 아니라 기술 역량 문턱이 낮다는 의미다.

7. 본인의 평가 — 신호인가 과장인가

bigset을 어떻게 봐야 하는가. 몇 가지 관점을 정리한다.

7.1 진짜 새로운 것

자연어 → 스키마 추론 → 병렬 에이전트 수집 → 자동 갱신을 하나의 플로우로 통합한 것은 기존 도구 조합으로는 달성하기 어려운 수준의 추상화다. 특히 비기술직 사용자가 직접 데이터셋을 만들 수 있다는 점, 그리고 갱신 스케줄을 설정해 데이터가 자동으로 살아있게 된다는 점은 진짜 가치다. 데이터 수집을 "엔지니어에게 티켓 올리기"가 아닌 "문장 입력"으로 바꾸는 것은 조직 내 데이터 접근 구조를 바꿀 수 있다.

7.2 과장하면 안 되는 것

bigset은 공식 문서 스스로 "실험 단계"라고 밝힌다. 정밀도·완성도·비용 효율 면에서 아직 프로덕션 ETL을 대체할 수준은 아니다. 특히 데이터 정확성이 핵심인 금융·법률·의료 용도에는 결과물을 그대로 쓰면 안 된다. 또한 "오픈소스"라는 라벨이 무료를 의미하지 않으며, 외부 API 비용이 실제 운용 비용의 대부분을 차지할 수 있다는 점을 인식해야 한다.

7.3 어떤 팀에 적합한가

bigset이 가장 빛나는 곳은 세 가지다. 첫째, 빠른 시장 조사나 경쟁 인텔리전스가 필요하지만 데이터 엔지니어가 없는 팀. 둘째, 변화 속도가 빠른 데이터(채용·가격·오픈소스 현황)를 주기적으로 업데이트된 상태로 유지하고 싶은 조직. 셋째, 데이터 파이프라인 시제품을 빠르게 만들어 개념 검증(PoC)을 하려는 엔지니어링 팀. 반면 대규모·고정밀·개인정보 포함 데이터 파이프라인에는 적합하지 않다.

8. 결론 — 데이터 수집의 언어화

bigset은 데이터 수집의 진입 장벽을 낮추는 방향에서 의미 있는 시도다. AI 에이전트+웹 스크래핑+ETL의 결합을 자연어 인터페이스로 통합한 것은 기술 조직만 누려 온 구조화 데이터 생성을 더 넓은 사용자에게 여는 방향이다. 그러나 2026년 6월 기준 bigset은 여전히 실험 단계이며, 정확성·비용·법적 책임은 사용자 몫이다.

더 중요한 것은 이 도구가 가리키는 방향이다. 데이터 파이프라인의 자연어화, ETL의 LLM 추상화, 그리고 "살아있는 데이터셋" 개념의 부상은 데이터 수집이 특정 기술 직군의 전유물에서 문장을 쓸 수 있는 사람의 역량으로 이동하는 흐름을 보여준다. bigset이 그 종착지일 필요는 없다. 그러나 이 흐름의 좌표로서 주목할 만한 도구임은 분명하다.
