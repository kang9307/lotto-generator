Introduction - failure is judged in three separate places

When a PowerShell script fails, the caller (Task Scheduler, a CI runner, or another script) receives a single value: the process exit code. Yet inside PowerShell there are three separate ledgers on which that value depends. The first is the exception, that is, terminating errors and try/catch. The second is $?, which holds whether the previous command succeeded. The third is $LASTEXITCODE, which holds the exit code of the last native program that ran. The three ledgers are not wired together automatically. A failure written in one of them does not appear in the other two.

A few terms are used throughout. A cmdlet is a PowerShell command implemented as a .NET class, such as Get-Item. A native command is an external executable such as cmd.exe or git.exe, started as a separate process that returns an integer exit code. An ErrorRecord is the object PowerShell builds for every error; it carries the exception, the error category, the target object and the script position. Whether a failure was raised as an exception or only written to the error stream decides what the rest of this article observes.

In bash, set -e and $? explain most of the behavior. PowerShell layers the integer exit codes of native programs on top of an object-based error model, so the same failure looks different in each ledger. The errexit and pipefail blind spots on the bash side are laid out with execution output in Shell Exit Codes and set -e - What It Catches and What It Misses, so this article stays strictly within PowerShell.

The questions answered here are the following.

  • Where is the boundary between errors that try/catch catches and errors it does not?
  • How far does $ErrorActionPreference reach, and when it collides with -ErrorAction, which one wins?
  • When a native command fails, which of $?, $LASTEXITCODE and exceptions changes?
  • How do exit and return show up in the process exit code?
  • When the same script is called with -File and with -Command, how does the exit code change?
  • What do Write-Error and throw, errors in the middle of a pipeline, and the $Error collection each leave behind?

Terminating and non-terminating errors - what try/catch sees

The Microsoft Learn topic about_Try_Catch_Finally defines what try/catch handles. PowerShell has two kinds of terminating errors: statement-terminating errors, which stop the current statement, and script-terminating errors, which unwind the entire call stack. Both are caught by try/catch. What falls outside that is the non-terminating error: a cmdlet writes an error to the error stream and continues with the next item. The $ErrorActionPreference entry in the documentation describes this default as Continue, which displays the error message and continues executing.

The first piece of code used to test the boundary runs Get-Item on a path that does not exist.

try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
Get-Item : Cannot find path 'C:\demo\nope.txt' because it does not exist.
                    At C:\demo\e1.ps1:3 char:7
                    + try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught:  ...
                    +       ~~~~~~~~~~~~~~~~~~~~~~~~~
                        + CategoryInfo          : ObjectNotFound: (C:\demo\nope.txt:String) [Get-Item], ItemNotFoundException
                        + FullyQualifiedErrorId : PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
                    
                    after Get-Item

The error message appeared on screen, but the catch block did not run, and the next statement inside try, 'after Get-Item', executed normally. The reason follows from the definition above: Get-Item reports this error as non-terminating and keeps going, so no exception is raised. Adding -ErrorAction Stop to the same code changes the result.

try { Get-Item C:\demo\nope.txt -ErrorAction Stop; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
caught: ItemNotFoundException

This time the catch block ran and 'after Get-Item' was not printed. The documentation explains that setting $ErrorActionPreference to Stop escalates non-terminating errors to script-terminating errors, and that the -ErrorAction common parameter overrides the preference for one specific command. The table below shows the result of putting several kinds of failure inside try/catch in the same script.

The rules that can be read from the table are as follows.

  • Errors that a cmdlet writes to the error stream by itself (a missing path from Get-Item, or Write-Error) do not reach catch under the default settings.
  • Errors raised directly by the language (division by zero, a failed cast, a nonexistent command, throw) are exceptions, so they always enter catch.
  • The same failure from the same cmdlet becomes a catch target with a single -ErrorAction Stop. To apply it to the whole script, use $ErrorActionPreference = 'Stop'.
  • $_ inside catch is an ErrorRecord, and the type of $_.Exception can be used to sort error kinds. The documentation states that PowerShell wraps all exceptions in a RuntimeException.

The scope of $ErrorActionPreference and -ErrorAction

about_Preference_Variables lists SilentlyContinue, Stop, Continue (the default), Inquire and Ignore as values for $ErrorActionPreference, and states that a change applies only in the scope where it is made and in child scopes. The following code checks the scope by execution.

'start: ' + $ErrorActionPreference
                    function Inner { 'inner sees: ' + $ErrorActionPreference }
                    function SetsStop { $ErrorActionPreference = 'Stop'; 'in SetsStop: ' + $ErrorActionPreference; Inner }
                    SetsStop
                    'after SetsStop: ' + $ErrorActionPreference
start: Continue
                    in SetsStop: Stop
                    inner sees: Stop
                    after SetsStop: Continue

The value changed to Stop inside the function is visible to the function it calls (Inner), and once the function ends and control returns to the caller, the original Continue is back. The reverse direction behaves the same way. When the caller set $ErrorActionPreference = 'SilentlyContinue' and then called Inner, the output was inner sees: SilentlyContinue. In other words, this variable is inherited downward along the call chain and does not leak upward.

When the two settings collide, the per-command -ErrorAction wins.

$ErrorActionPreference = 'Stop'
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    'survived: ' + $?
survived: False

Although the global setting was Stop, the script reached the next line, and no error message was printed. $?, however, is False. Hiding an error is not the same as making the failure not have happened.

SilentlyContinue and Ignore both hide the message, but they differ in what they leave in $Error. The documentation states that Ignore does not add the error to $Error.

$Error.Clear()
                    Get-Item C:\demo\a.txt -ErrorAction SilentlyContinue
                    'after SilentlyContinue, $Error.Count = ' + $Error.Count
                    Get-Item C:\demo\b.txt -ErrorAction Ignore
                    'after Ignore, $Error.Count = ' + $Error.Count
after SilentlyContinue, $Error.Count = 1
                    after Ignore, $Error.Count = 1

After SilentlyContinue, one record had accumulated, and after Ignore the count was still 1. Because Ignore leaves no record at all, there is no clue left to trace back through $Error later.

The documentation also lists Ignore as a value of $ErrorActionPreference, but on 5.1 Ignore could be used only as the value of the cmdlet's -ErrorAction parameter. Assigning it to the variable raised no error by itself, and the moment an error occurred in that state a NotSupportedException was raised.

$ErrorActionPreference = 'Ignore'
                    'preference set to: ' + $ErrorActionPreference
                    Get-Date | Out-Null
                    'after Get-Date, preference: ' + $ErrorActionPreference
                    try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().FullName; $_.Exception.Message }
                    'preference now: ' + $ErrorActionPreference
preference set to: Ignore
                    after Get-Date, preference: Ignore
                    caught: System.NotSupportedException
                    The value Ignore is not supported for an ActionPreference variable. The provided value should be used only as a value for a preference parameter, and has been replaced by the default value. For more information, see the Help topic, "about_Preference_Variables."
                    preference now: Continue

Get-Date, which raises no error, ran normally and the variable stayed Ignore. But when Get-Item raised its error, a NotSupportedException entered the catch, and the original ItemNotFoundException never reached it. The message says that Ignore cannot be used as the value of a preference variable, only as the value of a preference parameter, and that the provided value has been replaced by the default value. On the last line the variable had indeed returned to Continue. In short, on 5.1 Ignore can be used only in a parameter such as -ErrorAction Ignore; if the variable is set to Ignore, the first error turns into this exception. This behavior is the result of running on 5.1, and it was not run on 7.

One more behavior is announced in the Note of about_Try_Catch_Finally. When $ErrorActionPreference is SilentlyContinue or Ignore, even throw does not propagate and execution continues with the next statement. That sentence is the documentation's; the run below used SilentlyContinue only. Ignore cannot be put in the variable, as seen above, so it could not be confirmed.

$ErrorActionPreference = 'SilentlyContinue'
                    throw 'boom'
                    'line after throw ran'
line after throw ran

The message boom was not printed and the next line ran. For SilentlyContinue, the result matches the documentation. If this setting is put at the top of a script out of habit, even the stopping points created with throw disappear.

What is left in $Error after using Stop was also examined by execution.

$Error.Clear()

                    $Error[0].Exception.GetType().FullName

The official documentation says that Stop emits an ActionPreferenceStopException object to the error stream in addition to the original error. In this run, $Error held one record, and its exception type was ItemNotFoundException. This run alone is not used to interpret how the two statements relate.

$? and $LASTEXITCODE - a native failure is not an exception

about_Automatic_Variables defines $? as the execution status of the last command (True for success, False for failure) and $LASTEXITCODE as the exit code of the last native program or script that ran. For native commands, a following sentence says $? is True when $LASTEXITCODE is 0 and False for any other value. What the three ledgers show when a native command fails was observed by execution.

cmd /c exit 3
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = False
                    $LASTEXITCODE = 3

The failure was written in $? and $LASTEXITCODE. What about the exception ledger? The same command was run inside try with $ErrorActionPreference set to Stop.

$ErrorActionPreference = 'Stop'
                    try { cmd /c exit 3; 'next line ran' } catch { 'caught' }
next line ran

The catch block did not run, and the next statement did. A non-zero exit code from a native program is a value, not an error. PowerShell does not stop on its behalf, so even in a script with Stop turned on, a native failure can only be detected by reading $LASTEXITCODE directly. Running a program name that does not exist (nosuchprogram.exe) is a different story. In that case PowerShell could not find the command, so a CommandNotFoundException was caught inside try. A failure after a program has started and a failure to start it at all sit on different ledgers.

The lifetimes of the two variables also differ. The next code runs a cmdlet after a native call.

cmd /c exit 3
                    Get-Date | Out-Null
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = True
                    $LASTEXITCODE = 3
                    $? = False
                    $LASTEXITCODE = 3

After a successful cmdlet and after a failing cmdlet, $LASTEXITCODE stayed at 3. The variable is updated only when a native program or script runs, so it is possible to read a value left over from several lines earlier as if it were the result of the current call. $? is the opposite, with a lifetime of one statement.

Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    $ok = $?
                    '$? read once = ' + $ok
                    '$? read again (after the assignment) = ' + $?
$? read once = False
                    $? read again (after the assignment) = True

The assignment $ok = $? was itself a successful command, so reading $? again gives True. When a judgment is needed, copy the value into a variable in the statement immediately after the failing command. Inside functions there is one more layer. The documentation says Write-Error sets $? to False immediately after it runs but does not set it to False for the caller of that function, and the execution agreed.

function T { Write-Error 'bad' -ErrorAction SilentlyContinue; 'inside: ' + $? }
                    T
                    'outside: ' + $?
inside: False
                    outside: True

Merging native stderr into the error stream with 2>&1 reaches the exception ledger as well. The same command behaved differently under Stop depending on whether the redirect was present. Below, cmd /c writes one line to stdout and one line to stderr and ends with exit code 2.

$ErrorActionPreference = 'Stop'
                    try {
                      $out = cmd /c "echo to-stdout & echo to-stderr 1>&2 & exit 2" 2>&1
                      'no exception; lines captured: ' + @($out).Count

                      'caught: ' + $_.Exception.GetType().Name + ' / ' + $_.FullyQualifiedErrorId

caught: RemoteException / NativeCommandError

Once stderr was merged, the stderr line became an ErrorRecord and was promoted to an exception under Stop. But this single case does not tell whether the exception came from stderr or from exit code 2. Case 2, with exit code 0 but stderr merged, raised the exception, and case 3, with exit code 2 but no stderr line, did not. This behavior is the result of running the four combinations on 5.1; other redirects such as 2>$null were not tested.

exit and return - what sets the process exit code

The process exit code is determined by different rules depending on how the process is invoked. about_PowerShell_exe says that for -File, when the script ends with exit, that number becomes the process exit code, and a script-terminating error gives 1. For -Command, it says the exit code is 0 when $? of the last command is True and 1 when it is False, and that if the last command is an external program or a script that sets an exit code other than 0 or 1, the code is converted to 1. The table below shows the same script invoked both ways, with $LASTEXITCODE read in the parent PowerShell. Each script is a single line.

Script content-File exit code-Command "& script" exit codeWhat the output showed
'script body ran'00Normal completion
'before'; throw 'boom'; 'after'11Stopped after before, no after
'before'; Write-Error 'bad'; 'after'00Ran through after, error message printed
'before'; exit 5; 'after'51No after
'before'; return 5; 'after'00The number 5 appeared as output, no after
cmd /c exit 3; 'done'00done printed
'first'; cmd /c exit 3000 even though the last line failed
cmd /c exit 3; if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }; 'done'31No done
$ErrorActionPreference='Stop'; cmd /c exit 3; 'done'00done printed despite Stop
try { 'in try'; exit 4 } finally { 'in finally' }41in finally was printed
function F { exit 7 }; 'before'; F; 'after'71exit inside the function ends everything, no after
function F { return 7 }; 'before'; F; 'after'007 appeared as output and after also ran
try { throw 'x' } catch { 'handled'; exit 2 }21handled printed
try { throw 'x' } catch { 'handled' }00Catching and swallowing counts as success
'ok'; if ( { (syntax error)11Even the ok on the first line was not printed

The items in the table with a clear reason can be unpacked as follows.

  • exit 5 comes out as 5 with -File but is converted to 1 with -Command "& script". This matches the documented rule that codes other than 0 and 1 are converted to 1.
  • return 5 is output, not an exit code. At the top level of a script, return merely ends the script and the value goes to the output stream, so the process exit code is 0. For the same reason, return 7 inside a function puts 7 on screen.
  • exit 7 inside a function ends the whole process, not just the function. after was not printed on the caller side.
  • Even when the last line of the script is a native failure (cmd /c exit 3), -File returns 0. This matches the documented rule that a script completing normally gives 0, and handing the value over requires exit $LASTEXITCODE.
  • In try { exit 4 } finally { ... }, the finally block ran. The same direction of result was obtained for exit inside try as the sentence about_Try_Catch_Finally gives for exit inside catch.
  • $ErrorActionPreference = 'Stop' also failed to block the native exit code 3, so done was printed. That is the same result as the previous section.
  • A script with a syntax error runs not even its first line and gives exit code 1. The documentation says parse errors do not affect $?, but since this is a failure at a stage before the script executes, the process exit code came out as 1.

When a command string is passed directly, the fact that -Command judges by $? of the last command becomes even more obvious. The results below come from passing each of the following strings to powershell.exe -NoProfile -Command from a parent PowerShell.

The conclusion of the second table fits in one line. -Command looks only at the success of the last command, so a failure in the middle is erased by a single successful command after it. For automation in which the caller needs a specific exit code or needs to know about a mid-script failure, -File is the safer choice, and if -Command must be used, append exit $LASTEXITCODE to the string. That is also the method the documentation presents.

Errors in the middle of a pipeline

about_Pipelines explains that a pipeline sends objects to the next command one at a time. Because of this, an error in a middle stage does not affect items that have already passed, and the question becomes whether the later items keep flowing. Division by zero inside a script block was run in three ways.

1,2,0,4 | ForEach-Object { 10 / $_ }
10
                    5
                    Attempted to divide by zero.
                    At C:\demo\e4.ps1:2 char:28
                    + 1,2,0,4 | ForEach-Object { 10 / $_ }
                    +                            ~~~~~~~
                        + CategoryInfo          : NotSpecified: (:) [], RuntimeException
                        + FullyQualifiedErrorId : RuntimeException
                    
                    2.5

The error occurred on the item 0, yet the item 4 was still processed and 2.5 was printed. The error stopped only that item's statement, and the pipeline kept flowing. Wrapping the same pipeline in try/catch changes this.

try { 1,2,0,4 | ForEach-Object { 10 / $_ } } catch { 'caught: ' + $_.Exception.Message }
10
                    5
                    caught: Attempted to divide by zero.

2.5 was not printed. The moment catch received the error, the whole pipeline was aborted. The result was the same under $ErrorActionPreference = 'Stop', and a throw inside the script block (thrown at the item 3) also ended with caught: three after item 1 and item 2. So for a design of the kind process the remaining items and collect only the failures, try/catch must not sit outside the pipeline. It has to catch per item, inside the item-processing block.

When a single cmdlet receives several inputs, non-terminating errors come out mixed in with the results. Four paths (two of them missing files) were passed to Get-Item at once, the result was captured in a variable with 2>&1, and the types were counted.

$r = Get-Item C:\demo\e1.ps1, C:\demo\nope1.txt, C:\demo\e2.ps1, C:\demo\nope2.txt 2>&1
                    $r | ForEach-Object { $_.GetType().Name }
FileInfo
                    ErrorRecord
                    FileInfo
                    ErrorRecord

Successful objects and ErrorRecords came out interleaved in input order. A failing item did not block the processing of the items after it. Without knowing this structure, finding error objects mixed into a result variable is a surprise.

Reading $? after a pipeline finishes shows behavior that depends on the stage.

Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue | ForEach-Object { 'x' }
                    '$? = ' + $?
                    Get-Date | ForEach-Object { Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue }
                    '$? = ' + $?
$? = False
                    $? = True

In the pipeline where the first-stage cmdlet wrote an error, $? was False even though the last stage succeeded. Conversely, a failure that occurred inside the script block of the last stage was not reflected in $?. The documentation's definition of $? as the status of the last command fits the second result, but the first result is not explained by that definition alone. Either way, $? after a pipeline is hard to trust as a failure detector. Collecting per-stage failures with -ErrorVariable or $Error is the better route.

Following the result through to the exit code makes the difference larger. The log shows the error, but Task Scheduler sees success.

The parameters of Write-Error can set the error classification. The next code specifies a category and an identifier and then reads $Error[0].

throw can throw an exception object as well as a string, and catch can sort by type. A thrown string is wrapped in a RuntimeException.

try { throw [System.IO.FileNotFoundException]::new('typed') } catch [System.IO.FileNotFoundException] { 'typed catch: ' + $_.Exception.Message }
                    try { throw 'plain string' } catch { $_.Exception.GetType().FullName + ' / ' + $_.CategoryInfo.Category }
typed catch: typed
                    System.Management.Automation.RuntimeException / OperationStopped

To sum up, Write-Error means this item failed but carry on, while throw means stop here. A library-style function that reports failures per item should use the former, and one whose premises have broken so that it cannot go further should use the latter.

The $Error collection - what accumulates

about_Automatic_Variables describes $Error as an array of the most recent error objects, with the newest at $Error[0]. The defaults table of about_Preference_Variables gives 256 for $MaximumErrorCount. The result of raising two errors in a row and then reading the collection follows.

$Error.Clear()
                    Get-Item C:\demo\first.txt -ErrorAction SilentlyContinue
                    Get-Item C:\demo\second.txt -ErrorAction SilentlyContinue
                    'count: ' + $Error.Count
                    '$Error[0] : ' + $Error[0].Exception.Message
                    '$Error[1] : ' + $Error[1].Exception.Message
count: 2
                    $Error[0] : Cannot find path 'C:\demo\second.txt' because it does not exist.
                    $Error[1] : Cannot find path 'C:\demo\first.txt' because it does not exist.

The later error sits at index 0 and the earlier one is pushed back. The properties carried by a single ErrorRecord were also read by execution. The code was run in the same script right after the previous block, so ScriptLineNumber is line 3, where the second Get-Item is.

Caught errors also go into $Error. The documentation says that when an error occurs in the try block it is first saved to $Error, and the run agreed: after try { throw 'caught-me' } catch { ... }, $Error.Count was 1. -ErrorVariable is a common parameter that collects errors into a named variable, and in this run it also recorded them in $Error.

$Error.Clear()
                    Get-Item C:\demo\third.txt -ErrorAction SilentlyContinue -ErrorVariable ev
                    'ev.Count: ' + $ev.Count + ' / $Error.Count: ' + $Error.Count

                    'ev.Count: ' + $ev.Count

                    ev.Count: 2

The first line is the value after one failure with -ErrorVariable ev, and the second line is $ev.Count after a second failure accumulated with -ErrorVariable +ev (with a leading +). Without the +, the variable is overwritten each time. In practice, a workable routine is to call $Error.Clear() once at the top of the script and, right before exit, audit whether any errors were swallowed with $Error.Count and $Error | Select-Object -First 5. The SilentlyContinue from the earlier section is caught by this audit, and Ignore is not.

A practical pattern - a native-call wrapper and exit code propagation

Combining the rules obtained from the executions above into one script gives the following. At the top, Stop is turned on so that cmdlet errors become exceptions. Native calls go through a wrapper that checks $LASTEXITCODE and converts it into a throw. In catch, the exit code the caller will read is set with exit, and cleanup goes in finally.

$ErrorActionPreference = 'Stop'
                    function Invoke-Native {
                        param([scriptblock]$Command)
                        & $Command
                        if ($LASTEXITCODE -ne 0) { throw ('native command failed with exit code ' + $LASTEXITCODE) }
                    }
                    try {
                        'step 1'
                        Invoke-Native { cmd /c exit 0 }
                        'step 2'
                        Invoke-Native { cmd /c exit 3 }
                        'step 3 (not reached)'
                    }
                    catch {
                        'ERROR: ' + $_.Exception.Message
                        exit 3
                    }
                    finally {
                        'cleanup runs'
                    }

This is the result of running the script with powershell.exe -NoProfile -File and reading $LASTEXITCODE in the parent.

exit code = 3
                    step 1
                    step 2
                    ERROR: native command failed with exit code 3
                    cleanup runs

The third step did not run, the finally cleanup ran even after exit 3, and the process exit code was 3. Every fact this pattern depends on was observed by execution in earlier sections.

  • A native failure is not an exception, so the wrapper promotes it to a throw (section 4).
  • finally runs even when exit is present (section 5).
  • -File returns the value of exit as it is (section 5).

The points to check when using this pattern are as follows.

  • Is the value of $ErrorActionPreference at the top of the script the intended one? With SilentlyContinue, even throw is swallowed.
  • Is $LASTEXITCODE read immediately after the native call? A value several lines later may belong to an earlier call.
  • If the caller invokes with -Command, is there an exit $LASTEXITCODE at the end of the string?
  • Could a native call with stderr merged by 2>&1 turn into an exception under Stop without going through the wrapper?
  • Right before exit, is $Error.Count checked to audit errors swallowed by SilentlyContinue rather than Ignore?

What Could Not Be Verified

  • The Ignore part of the documentation Note that throw does not propagate when $ErrorActionPreference is Ignore. On 5.1, putting Ignore in the variable turns the point where an error occurs into a NotSupportedException, so it could not be reproduced; only SilentlyContinue was confirmed.
  • The behavior of PowerShell 7 (pwsh). pwsh is not installed on this PC, so differences from 5.1 could not be compared by execution. The only things the official documentation states inside the 5.1 pages are that statements wrapped in parentheses (...), $(...) or @(...) always reset $? to True before PowerShell 7 and that this changed in 7, and that the limitation of not being able to pass an explicit Boolean value to a switch parameter with -File was removed in PowerShell 6 (pwsh.exe).
  • A PowerShell setting that corresponds to bash pipefail on 5.1. It was not found in the five official documents that were consulted.
  • Where the ActionPreferenceStopException that the documentation says Stop emits shows up in the error stream. In this run there was only one record in $Error.
  • How cmd.exe, Task Scheduler and CI runners receive these exit codes. This article read them only through $LASTEXITCODE in a parent PowerShell.
  • The exit code on Ctrl+C interruption. The documentation says 0 for -File and 1 for -Command, but interactive interruption is hard to automate, so it was not run.
  • Inheritance of $ErrorActionPreference in cmdlets inside script modules or binary modules, and error propagation in remote execution (Invoke-Command) and background jobs.
  • The initial value of $LASTEXITCODE in a session that has never run a native program, and results on other Windows builds.
  • Whether the error display format differs by host (console, ISE, VS Code integrated terminal) even within 5.1.
