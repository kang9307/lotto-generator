What was released - the facts confirmed from the September 29, 2026 announcement

OpenAI released GPT-6.1 Sol at DevDay 2026. TechCrunch, relaying the announcement, wrote that GPT-6.1 Sol is available starting today, and the date is September 29, 2026. Two sentences carry the announcement. One says the model reaches nearly the same level of intelligence as GPT-6 Astra for agentic coding, computer use and professional work. The other says it costs one-fifth of Astra's standard input and output token prices. Together they were compressed into the headline of Astra-class performance at one-fifth the price. Neither statement is a price or a measurement by itself; each one needs the figures that stand behind it.

A compressed headline loses information in three places: the denominator of the multiple, the basis of the discount, and who is making the performance claim. This article recalculates those three from the original figures and separates what a reader can rely on when deciding which work to give this model from what still has no evidence behind it. The lineage of the models has already been covered in the two linked articles, so the focus here is the pricing structure and selection criteria of GPT-6.1 Sol alone.

The facts confirmed from the announcement come first, gathered in one table. The source column shows where each value came from, and a value that appeared in only one source names only that source.

One price table - input, output and cached input for four models

Comparing prices gets confusing because there are four models and three kinds of unit price. Putting the standard prices of GPT-6 Astra, GPT-6 Sol, GPT-6.1 Sol and GPT-6 Luna on the same axis shows at a glance where 6.1 Sol stands. The Astra cached input price does not appear as a stated value in the announcement material; it is back-calculated from VentureBeat's description that the 6.1 Sol cached input is one-tenth of Astra's. The cached values for GPT-6 Sol and Luna are calculated from the 90% cache-read discount summarized in the September 23 article.

Three facts can be read straight off this table. First, the standard input and output prices of 6.1 Sol are the same as GPT-6 Sol. Both are $2 input and $10 output. The generation moved up while the standard price stayed put, and the only value that changed is the cached input. Second, the standard price of 6.1 Sol is exactly one-fifth of Astra. Third, Luna is another twentieth of 6.1 Sol. That third relation also means Luna is one-fiftieth of Astra on input, and on output, at $0.50 against $50, one-hundredth.

Reading the same table another way shows that 6.1 Sol sits not as a cheaper edition of Astra but as an improved edition of GPT-6 Sol. In the price table the lineage belongs to Sol, while the performance target is placed on Astra. A team comparing invoices across generations should keep two questions apart: what the model is priced like, and what the model is expected to do like. That difference returns when the multiple is interpreted later, because the one-fifth multiple holds only against Astra, and against GPT-6 Sol the multiple on standard prices is one.

The denominator of one-fifth - it applies to standard input and standard output only

The wording of OpenAI that TechCrunch relays is one-fifth the standard input and output token prices. Each word sets the scope. Standard means the standard unit price and does not cover variant prices such as cached, Fast, Batch or Flex. Input and output means that one-fifth applies to input and to output separately. VentureBeat put it more explicitly: 6.1 Sol therefore costs exactly one-fifth as much for standard uncached input and output. The condition is uncached, meaning input that did not hit the cache.

Recalculated from the original unit prices, the statement works out as follows.

Price typeAstra6.1 SolMultiple (recalculated)
Standard input (no cache)$10$25x cheaper (one-fifth)
Standard output$50$105x cheaper (one-fifth)
Cached input$1.00 (back-calculated)$0.1010x cheaper (one-tenth)

Input and output are both exactly one-fifth, so the headline of one-fifth is true at standard prices. That multiple cannot be applied directly to an invoice, however. An invoice is the unit price multiplied by the number of tokens, and the number of tokens differs by model. Given the same task, a model that reasons longer or calls more tools produces more output tokens. In the code review measurement of Luna and Astra, the unit price gap was 42 to 50 times, yet the cost gap per review narrowed to about 28 times, because the cheaper model used more than three times the output tokens. That measurement left the lesson that the unit price multiple is closer to a ceiling for the billing multiple.

There are therefore three safe ways to read one-fifth. Each of the three is a claim about a different object: a price list, an invoice and a workload.

  • It is true as a unit price. Standard input and output are each one-fifth, and recalculating from the developer documentation values shows no discrepancy.
  • It is conditional as an invoice. The multiple approaches 5x only when both models use similar tokens for the same task, and it shrinks if 6.1 Sol uses more tokens.
  • The multiple changes once the cache applies. Cached input is one-tenth, so a task whose input mostly hits the cache can show a gap larger than 5x (section 8).

Cached input at $0.10 - what the 95% and the 50% are each a percentage of

The material relaying the announcement describes cached input in two ways. One says it is 95% lower than the standard input price, and the other says it is 50% lower than the GPT-6 Sol cached input. The two sentences look as if they give different numbers, but both point at $0.10. Only the basis differs. A reader who sees only one of the three ratios can reach a very different conclusion about how much the cache changed between generations.

ComparisonBase value6.1 Sol cached inputCalculation (recalculated)Result
Against standard input$2$0.100.10 / 2 = 0.0595% lower
Against GPT-6 Sol cached input$0.20$0.100.10 / 0.20 = 0.5050% lower
Against Astra cached input$1.00 (back-calculated)$0.100.10 / 1.00 = 0.1090% lower (one-tenth)

The point of the table is that three ratios attach to one value. When a figure such as 95% off appears in promotional wording, the question to ask is 95% of which value. Here it is 95% of the uncached standard input of $2, and against the cache price of the previous generation it is half. It is true that 6.1 Sol treats the cache more generously than its predecessor, but the improvement is not 95%; it is 50%.

For the cache to work in practice there is a condition. The same leading portion, the prefix, as a previous request has to be sent again and again. System prompts, tool definitions, long documents and accumulated conversation history are such things. An agentic coding task resends earlier context on every call as the session grows, which is a structure in which the cache hits easily. By contrast, work in which the leading portion differs on every request, for example a batch job that classifies unrelated documents one at a time, sees almost no cache hits. Details such as the cache lifetime and the minimum number of cacheable tokens do not appear in the sources behind this article, so the relevant section of the official documentation has to be checked separately before predicting an invoice.

One more point deserves mention. The developer documentation contains the sentence: Fast mode prices are 2x Standard, and Batch and Flex prices are 50% lower than Standard. In other words, one standard price carries a separate multiplier for each processing mode. Batch and Flex are half of standard and Fast is double. To compare one-fifth across different processing modes, the same mode has to be applied to both sides.

Where near Astra comes from - OpenAI's own announcement and the missing third-party measurement

The price is easy to check because a value is written in documentation. Performance is different. The phrase nearly the same level of intelligence is TechCrunch relaying the OpenAI announcement, and the figures backing it were reported as benchmarks run by OpenAI. The reported values, with attribution, are as follows.

  • Gap to Astra. According to TechCrunch relaying the OpenAI announcement, the error rate stays within 1.9% of Astra. Whether that 1.9% is percentage points or a relative ratio cannot be told from the relayed sentence alone.
  • OSWorld 2.0. According to VentureBeat, it comes within 2.1 percentage points of Astra. This is a computer-use benchmark and the value was run by OpenAI.
  • DeepSWE v1.1. It beats the best GPT-6 Sol result by 6.4 percentage points. The comparison target is the previous Sol, not Astra.
  • AutomationBench. It improves 4.8 percentage points over GPT-6 Sol. Again the comparison target is the previous Sol.
  • Factual errors. At low reasoning effort they fall from 11.4% for GPT-6 Sol to 7.7%. The value is relayed from the OpenAI announcement.

What to notice when reading this list is the comparison target. Near Astra is compared directly with Astra in only two places, the 2.1 percentage points on OSWorld 2.0 and the 1.9% error rate. DeepSWE and AutomationBench are comparisons with the previous-generation Sol, so they are evidence of improvement over Sol and not evidence of closeness to Astra. Mixing the two kinds of comparison spreads the impression that 6.1 Sol is at Astra level more widely than the actual figures support.

That every figure is a value run by OpenAI is also a condition. Benchmark values change with the harness, the prompt, the reasoning effort and the tool settings, and a value the vendor ran to suit its own model can differ from one a third party runs under the same conditions. Among the sources behind this article, no independent measurement of 6.1 Sol was opened. A model page on a third-party analysis site appeared in the search results, but it was outside the scope consulted and its content is not reflected here. So the sentence that it comes close is read most accurately as OpenAI claims it.

This distinction is a structure repeated in earlier announcements. The GPT-6 Astra announcement commentary covered a case in which the same model on the same benchmark gave widely different values depending on conditions. When one benchmark value is quoted without its conditions, the next person to quote it loses those conditions.

Ultrafast - not out yet, and priced on a different structure

The announcement also came with a processing option called Ultrafast. According to VentureBeat it advertises up to 300 tokens per second, token generation up to 8x faster in Codex and up to 6x faster in the API, at a price of 6x standard. Multiplying the standard prices by six makes 6.1 Sol Ultrafast $12 input and $60 output. Astra Ultrafast is $60 input and $300 output. The arithmetic checks out as a recalculation.

OptionInputOutputStatus
GPT-6.1 Sol standard$2$10Available
GPT-6.1 Sol Ultrafast$12 (standard x 6)$60 (standard x 6)Due in the coming days, not yet released
GPT-6 Astra standard$10$50Available
GPT-6 Astra Ultrafast$60 (standard x 6)$300 (standard x 6)Available in the API

Two things in this table need attention. First, 6.1 Sol Ultrafast had not come out at the time of the announcement. VentureBeat wrote that it is due in the coming days. Even if a brief mentions up to 8x faster generation in Codex, that is a speed after release and not an option that can be used now. The model page in the developer documentation had no Ultrafast entry, only Fast mode at 2x and the Batch and Flex discounts. When the Ultrafast price will be reflected in that documentation has not been established.

Second, turning on Ultrafast removes the one-fifth-of-Astra property. The 6.1 Sol Ultrafast input of $12 is more expensive than the Astra standard input of $10, and the output of $60 is also more than the Astra standard output of $50. Recalculated, 6.1 Sol Ultrafast is 1.2 times the Astra standard price. The value of one-fifth holds only for standard against standard, or for Ultrafast against Ultrafast ($12 out of $60). A team that picks Ultrafast because it needs fast responses has to move the baseline of the price comparison from Astra standard to Astra Ultrafast. The one-fifth headline therefore describes the default mode, and a latency-sensitive team pays a premium that the headline does not mention. Which combination of speed and price is favorable is settled by actual latency requirements and token usage, and the sources behind this article contain no measurement of that.

Turning it into an invoice - cache share and token usage change the multiple

The purpose of this section is to turn the unit price table into actual cost. The calculation below is an example built on assumptions: one agent task using 10 million input tokens and 1 million output tokens is run on both models with the same token counts. The Astra cached input is the back-calculated $1.00. Every value is recalculated.

Scenario (10M input, 1M output tokens)AstraGPT-6.1 SolMultiple
No cache$100 + $50 = $150$20 + $10 = $305.00x
80% of input cached (8M cached, 2M regular)$20 + $8 + $50 = $78$4 + $0.80 + $10 = $14.80about 5.27x
80% cached, 6.1 Sol uses 1.5x the tokens$78$14.80 x 1.5 = $22.20about 3.51x

What the three rows show is this. Without a cache the multiple is exactly the unit price multiple of 5x. When most of the input hits the cache, the input term becomes small on both sides and the output term dominates the total. In this example the output of $50 against $10 makes up most of the total, so even with a tenfold gap in cache price the total multiple stays near 5x. The third row assumes 6.1 Sol uses 1.5 times the tokens for the same task, and the multiple falls to 3.5x. Because output tokens cost five times as much as input tokens on both models, a task with long generated answers moves the total far more than one that mainly reads. The break-even point is where 6.1 Sol uses about 5.27 times the tokens of Astra, and below that 6.1 Sol is still cheaper.

The money meaning of the cache being cheaper on 6.1 Sol than on GPT-6 Sol can also be calculated. In the same scenario with 8M cached, GPT-6 Sol comes to $4 + $1.60 + $10 = $15.60 and 6.1 Sol to $14.80. The difference is $0.80, about 5.1% as a ratio. That means the halving of the cache price shows up as a little over 5% of the total. The effect is larger for tasks with a higher cache share and less output, so the impact is felt in search and analysis tasks that read long documents repeatedly and is small in generation tasks with large output.

Before adopting it, the assumptions in this table have to be replaced with the values of one's own workload. Four values are needed.

  • Input tokens per task and the share of them that hits the cache
  • Output tokens per task
  • The difference in token usage between the two models on the same task
  • The number of calls that grows through retries and failures

These four values cannot be obtained from public material and only come out of running some of one's own traffic. Concluding from the unit price table alone that it is one-fifth and therefore five times cheaper leaves out the third and fourth values.

Which work to give it - selection criteria and a self-evaluation procedure

Turning the facts so far into criteria gives three branches: what has evidence, what has none, and what depends on conditions.

Judgments with evidence (price).

  • The standard input and output prices are one-fifth of Astra and the same as GPT-6 Sol. A team already on Sol sees no change in standard price by moving to 6.1.
  • Work with long, repeated input gains a lot from the $0.10 cached input. Agent sessions with a fixed leading portion and queries over long documents are typical.
  • If Ultrafast is needed, put into the budget the fact that it is more expensive than Astra standard.

Judgments without evidence (performance).

  • Nearly the same as Astra is OpenAI's claim and has no third-party measurement. A decision to move from Astra on the basis of that sentence cannot be made without a self-evaluation.
  • Finer abilities such as code review precision, security vulnerability detection and concurrency bugs have no published measurement for 6.1 Sol. The Luna and Astra measurement covers a different pair of models, so it cannot be carried over to 6.1 Sol.
  • For work where errors are expensive, such as changes applied directly to production systems or work involving money or legal judgments, even a small performance gap can make up most of the cost.

Judgments that depend on conditions.

  • For interactive work where latency matters, wait for Ultrafast to be released or consider Fast mode (2x standard). There is no public measurement yet of the actual response time of each option.
  • To use it in Copilot the plan must be Pro+ or above, and an administrator policy may be blocking access.
  • For bulk, non-urgent processing, Batch and Flex are 50% lower than standard according to the developer documentation. The conditions under which that discount actually applies to 6.1 Sol have to be checked in that documentation.

The smallest procedure that puts these criteria into practice is a self-evaluation. Pick 30 to 50 tasks the team actually hands over, run Astra and 6.1 Sol on the same inputs, and have people grade the results. What to look at is not the correct-answer rate alone. Recording the following four together shows how the unit price multiple turns into a billing multiple.

  • Whether the task succeeded (by the team's own standard)
  • Input, cached and output token counts
  • Number of retries and total elapsed time
  • Time a person spent fixing it when it was wrong

With the table built up this way, the question of how far one-fifth of the price goes can be answered with the team's own values. What has been published is the price, and performance is a value that has to be measured on each team's own work. A table like this also survives the next model release, since the same 30 to 50 tasks can be replayed against whatever comes next.

What could not be confirmed

  • The body of the OpenAI announcement. The announcement page on openai.com refused access, so the announcement content relies on what TechCrunch, VentureBeat, the developer documentation and the GitHub Changelog relayed.
  • The official Astra cached input price. It is back-calculated from VentureBeat's description that the 6.1 Sol cache is one-tenth of Astra's, and is not a value confirmed directly in an OpenAI price list.
  • The basis of the error rate within 1.9%. Whether it is percentage points or a relative ratio, and on which benchmark it was measured, cannot be told from the relayed sentence.
  • Third-party performance measurement. The result of an independent body measuring 6.1 Sol under the same conditions is not among the sources opened for this article.
  • The release timing and final price of Ultrafast. Sol Ultrafast was reported only as due in the coming days, and the 6x multiple is also a description in coverage with no entry in the developer documentation.
  • Detailed cache rules such as lifetime and minimum token count, and how cached input is billed in Copilot.
  • The difference in token usage between GPT-6 Sol and 6.1 Sol. The GitHub Changelog gives an early-testing description of fewer tokens and steps than earlier models, but no figures.
