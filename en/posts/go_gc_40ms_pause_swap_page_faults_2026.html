Problem Statement: A 40ms Pause with Swap Enabled

The original starts from an experience in which the author almost slapped their forehead after deciding to run swap in production to absorb memory spikes. The author says the post is written so that readers do not have to do the same. The setup is simple: one cgroup with two processes. One is a Go process that calls io.ReadAll and then proto.Unmarshal, creating a blob and then a graph struct, which Go's allocator marks as scan. The other is an HTTP server that mostly stays quiet.

The author's first expectation went like this. Whenever the collector runs, it reads those scan spans pointer by pointer and decides what to do with them. Under memory pressure the kernel evicts pages to the swap device, but eviction happens per cgroup and not per process, so the pages of both processes get evicted. Therefore the chance of a sad dance of swap-in and swap-out between the kernel and the garbage collector should be small. The author then writes that this was wrong.

The problem found during the experiment is this. Go's garbage collector reads its metadata, which lives outside the heap in a region that is not freed, during a stop-the-world pause, and that metadata can be in swap. The author ran a mock run on a Hetzner box with kernel 6.8 and MGLRU enabled. The median pause was around 51µs, and with the metadata on the NVMe the worst pause was 40ms.

  • Median and worst case: The median is about 51µs and the worst case is 40ms (detailed measurement 39,902µs). The original says 40ms is 800 times the median. Dividing 39,902 by 51 directly gives about 782 times (calculated).
  • Measurement condition: In the original's wording, the worst value is the one "with the metadata on the NVMe". Whether swap was in use when the 51µs median was measured is not stated in the original.
  • Global stop: Because every P is stopped, a goroutine whose I/O completes during the pause has nobody to handle it, which is the original's own illustration.

The point the original stresses is that these 40ms arise not in one goroutine but in the interval where the world is stopped. The author admits the length may look harmless at first, then points out that it is a stop-the-world pause. The original also notes that such pauses repeated two or three times per memory spike during the test. In other words, the 40ms is not an average cost spread thinly across many requests. It is one contiguous interval in which every P is stopped, and the author's own comparison puts it at 800 times the median pause, which is why the author calls it a lot.

Two STW Points and the GC Call Sites Where the Faults Occurred

According to the original, Go's GC has to stop the world at two points: when it performs a sweep termination and when it performs a mark termination. In the author's experiment there were 312 such pauses in 30 minutes.

The author wrote a small bpf script that counts page faults while the world is stopped. The output for the single worst case was: pause 39,902µs, faults during it 228, 39,013µs in faults. The author summarizes this as 39 of those 40ms having been spent in 228 page faults. The faults happened inside the GC's bookkeeping, and the original shows ten call sites in addr2line output.

  • runtime.(*spanSet).reset — internal/runtime/atomic/types.go:194
  • runtime.finishsweep_m — mcentral.go:71, and in the other stack mgcsweep.go:268
  • runtime.gcStart.func2 — mgc.go:724
  • runtime.systemstack — asm_amd64.s:518
  • runtime.gcStart — mgc.go:722
  • runtime.nextMarkBitArenaEpoch — mheap.go:2481

The ten lines read as two stacks of five frames. One starts at spanSet.reset and the other at nextMarkBitArenaEpoch, and both continue through finishsweep_m, gcStart.func2, systemstack and gcStart. This matches the repository script capturing five frames with ustack(5). The original does not explain what each function does or which STW point these call sites correspond to, so this article also stops at names and locations. Readers who want to know what each of these functions does, or which of the two STW points each stack belongs to, would have to open the Go runtime source for the version the author used, and the original does not tell us that version either.

The Kernel Path the Original Describes: From Eviction to Major Fault

The reason the original gives runs like this. The runtime allocates those pages. They are not freed but reused. And they are read during GC cycles. Because the kernel evicts pages by age, it sends the least recently accessed pages to swap. When the GC stops the world and tries to read those pages, they are already in swap, so a major page fault occurs.

The author lists the handling of one fault, "just to keep it short", as follows. The kernel reads the PTEs, calls do_swap_page, finds a new frame, charges it to the cgroup, submits a bio to read the pages, waits for the disk, and puts them back in memory. Next to these steps the original links to the matching lines of the Linux 6.8 source (mm/memory.c, mm/swap_state.c, mm/page_io.c).

  • Eviction criterion: access time. The pages that have gone longest without being accessed go to swap first.
  • Eviction unit: in the author's premise it is the cgroup, not the process, so even the pages of the quiet HTTP server are under the same pressure.
  • Access pattern of the metadata: in the original's words those pages are read in GC cycles, which means they may go untouched between cycles.
  • Cost of one fault: because the list above ends with waiting for the disk, in the original's worst case 228 faults occurred inside a single pause.

The same fault has a different reach depending on where it happens. Discussing the delay of the goroutine that builds a 511 KiB message, the author writes that only the goroutine doing the allocation pays that cost, so it is localized rather than global like the metadata pause. A metadata fault, by contrast, occurs while the world is stopped, so every P waits together. This contrast, between a fault that stalls one goroutine and a fault that stalls the whole runtime, is the reason the author treats the two measurements as separate findings rather than as one number.

Experimental Setup and the bpftrace Script: stw.bt in Full

The original mock run was done on a Hetzner box with kernel 6.8 and MGLRU enabled. Everything about the experiment, including plots, the mock allocator, the bpf scripts and the python scripts, is in the go-gc-swap-cost repository, so the numbers quoted here can be traced back to code that the author published alongside the post. The observation lasted 30 minutes and contained 312 STW pauses. Below is the full bpf/stw.bt from that repository, copied verbatim including comments. The placeholder BIN stands for the path of the Go binary as seen by bpftrace, so the script cannot be run unchanged and must be pointed at the binary under test.

// BIN: path of the Go binary as seen by bpftrace, e.g. /proc/<pid>/root/tmp/pagefault
                    // both processes run the same binary, so everything is keyed by pid: a fault counts only
                    // against a pause of its own process
                    uprobe:BIN:runtime.stopTheWorldWithSema /comm == "pagefault"/ {
                      @stw_start[pid] = nsecs; @stw_faults[pid] = 0; @stw_fault_ns[pid] = 0;
                    }
                    uprobe:BIN:runtime.startTheWorldWithSema /@stw_start[pid]/ {
                      $d = (uint64)(nsecs - @stw_start[pid]);
                      @stw_us = hist($d / 1000); @stw_n[pid] = count(); @stw_ns[pid] = sum($d);
                      printf("stw t=%d pid=%d %d us, faults during it %d, %d us in faults\n",
                             elapsed / 1000000, pid, $d / 1000, @stw_faults[pid], @stw_fault_ns[pid] / 1000);
                      delete(@stw_start[pid]);
                    }
                    // swap-in and file-backed faults both: the binary's own code pages can be evicted too
                    kprobe:do_swap_page, kprobe:filemap_fault /comm == "pagefault" && @stw_start[pid]/ {
                      @f_start[tid] = nsecs; @stw_faults[pid]++; @stw_stack[ustack(5)] = count(); // five frames reach gcStart
                    }
                    kretprobe:do_swap_page, kretprobe:filemap_fault /@f_start[tid]/ {
                      @stw_fault_ns[pid] += (uint64)(nsecs - @f_start[tid]); delete(@f_start[tid]);
                    }
                    END { clear(@stw_start); clear(@f_start); clear(@stw_faults); clear(@stw_fault_ns); }

The script has four parts. First, the uprobe on stopTheWorldWithSema records the start time per pid and zeroes the fault count and fault time. Second, the uprobe on startTheWorldWithSema computes the pause $d, adds it to a microsecond histogram, prints the pause, the fault count and the fault time in one line, and then deletes the start time of that pid. Third, the kprobe records a timestamp on entry to do_swap_page and filemap_fault, increments the fault count, and aggregates the call stack with ustack(5). Fourth, the kretprobe adds the elapsed time to the fault time when those two functions return.

The script's comments reveal two things. Both processes run the same binary, so every value is keyed by pid and a fault is counted only against a pause of its own process. And both swap-in and file-backed faults are counted, because the binary's own code pages can be evicted too. Reading the script shows that the 228 in the original is the sum of do_swap_page and filemap_fault calls. The original text itself speaks only of page faults, so the split between the two kinds is something one can read from the probes but not from the prose.

  • Observation: 312 STW pauses in 30 minutes.
  • Worst case: pause 39,902µs, 228 faults, 39,013µs in faults in total.
  • Share of faults: 39,013 ÷ 39,902 ≈ 97.8% (calculated). The original's own statement is "39 of those 40ms".
  • Time outside faults: 39,902 − 39,013 = 889µs (calculated). The original gives no breakdown of this time.
  • Repetition: in the test, such pauses came two or three times per memory spike.

Message Construction Latency: A Cost Paid by One Goroutine

The author noticed one more thing. Building a single 511 KiB message, which usually takes 3-5ms, jumped to 105ms when swap was on the NVMe and to 903ms when it was on Hetzner's network volume. The author writes that per message this costs more than the metadata pause. However, only the goroutine doing the allocation pays that price, so at least the cost is localized and not global like the metadata one.

  • Scope: the delay is confined to the goroutine performing the allocation. Unlike the global STW, it does not stop the other Ps.
  • Medium difference: 903ms against 105ms is about 8.6 times (903÷105, calculated). The same job changed by this much depending on the swap medium, which is why the original names both media explicitly instead of giving a single figure.
  • Breakdown of the time: the author states directly that they have not confirmed where this time goes.

The author's reason for including this item is that it is "another cost you would have to pay". The author did not attribute this time to the same cause as the metadata faults, and also did not say how many of the 511 KiB messages were measured or how the 3-5ms baseline was obtained. Accordingly, this article does not read the message construction delay as a result of the same mechanism as the STW faults.

Green Tea GC Re-Measurement and What Go Officially Says

The September 14 update in the original is short. Someone asked whether Go 1.26's Green Tea garbage collector changed the way the GC reads metadata, the author measured it, and the impact was negligible. The measurement environment and numbers were not published. The update is therefore a result without a table: it answers the reader's question in one sentence, and a reader who needs the figures would have to repeat the experiment with the repository's scripts.

Go's official material describes Green Tea as follows. According to the Go blog (October 29, 2025), the key idea is to work with pages, not objects. Instead of scanning objects it scans whole pages, instead of tracking objects on the work list it tracks whole pages, and it tracks marked objects locally within each page rather than across the whole heap. The blog explains this in connection with cache locality. In Go, a page is 8 KiB regardless of the hardware virtual memory page size.

  • Go 1.25: an experiment enabled with GOEXPERIMENT=greenteagc. The blog says many workloads spend around 10% less time in the garbage collector and some see a reduction of up to 40%.
  • Go 1.26: per the release notes, Green Tea, previously an experiment, is now enabled by default, and it improves marking and scanning of small objects through better locality and CPU scalability. Real-world programs that use the garbage collector heavily are expected to see a 10-40% reduction in GC overhead (Go's official figure).
  • Further improvement: on newer amd64 CPUs (Intel Ice Lake, AMD Zen 4 and newer), the collector uses vector instructions when scanning small objects, and about 10% further reduction in GC overhead is expected.
  • Opting out: it can be disabled at build time with GOEXPERIMENT=nogreenteagc, and this setting is expected to be removed in Go 1.27.

The nature of the official figures must be kept apart. The 10-40% is a benchmark expectation for the CPU overhead of the GC, whereas the original's problem is the faults on metadata reads during STW. Because the two measure different things, one cannot be used to estimate the other. The Go documents describe how Green Tea scans, while the original describes where the stalled reads happened, and neither source claims to cover the other's subject. What this article confirmed is a single sentence: the author measured that the impact on metadata reads with Green Tea is negligible.

The Original Conclusion and Cautions When Reading It

The conclusion of the original is a sentence and a half. The author agrees with Chris Down that swap is not evil. But swap did not behave well with garbage collection, and the author adds that their production workload collects a lot. The original contains no recommendation to turn swap off or to change any setting. Any such advice found in summaries of the post therefore comes from the summarizer rather than from the author, and it should be checked against the original text before it is repeated.

  • Confirmed by the author directly: a metadata fault occurred while the world was stopped, and there was a case where that fault accounted for most of the pause.
  • Stated as unconfirmed by the author: the breakdown of the time in the 511 KiB message construction delay.
  • Treated only briefly by the author: the Green Tea re-measurement, which gives only the result without numbers.
  • Absent from the original: operational recommendations, setting values, and reproduction in other environments.

Only a cautious general lesson can be drawn from this case. Even in an interval with a short pause, if the memory that interval reads is in swap, disk latency lands directly on the pause. How often that happens in which production environments is something the original does not answer. The measurements come from one mock allocator, one kernel version and one hardware provider, and the author presents them as a failure mode to be aware of, not as a prediction for every deployment. For a reader who runs Go services with swap enabled, the practical use of the post is to know that this failure mode has been observed and how it was measured, using a script that anyone can read and rerun.

Unconfirmed Details

  • The condition under which the 51µs median was measured. Whether it was a value while swap was in use is not stated in the original.
  • The breakdown of the 105ms and 903ms for building a 511 KiB message. The original author also wrote that where the time goes is unconfirmed.
  • The worst STW pause when the metadata is on the network volume. The original gives only the 40ms of the NVMe case.
  • The numbers and run conditions of the Green Tea GC re-measurement. The original says only that the impact is negligible.
  • Reproduction results on anything other than a Hetzner box and on kernels other than 6.8.
  • The ratio of swap-in faults (do_swap_page) to file-backed faults (filemap_fault) among the 228 faults. The script counts them together.
