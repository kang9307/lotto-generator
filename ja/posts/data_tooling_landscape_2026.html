2026年のデータツール地形

何があるかではなく、何が変わって選定基準がどう動いたか

2026-07-29 IT・技術

序論: 「とりあえず分散処理から」が既定値でなくなった理由

データスタックを新しく組む場面で最も多く投げられる質問は「最近は何を使うのか」だ。この問いにツール名を並べて答えると、半年後にはその一覧の大半が誤りになる。バージョンが変わり、プロジェクトの運営主体が移り、昨日まで無関係だった二つのツールが同じ規約を実装しはじめる。一覧は古びるが、判断基準はそれほど古びない。だからこの記事はカタログではなく基準を扱う。

この数年でデータ処理・分析スタックにおいて実際に動いたものは三つある。第一に、単一ノードで処理できる領域が大きく広がった。第二に、保存フォーマットとカタログがエンジンより上位の決定になった。第三に、メモリ表現と転送規約が標準化され、道具を差し替える費用が層ごとにはっきり分かれた。この三つの移動が「何を選ぶか」の文法を変えた。

先に原則をひとつ置く。本稿に記した事実はすべて各プロジェクトの公式文書・公式リポジトリで 2026 年 7 月 29 日に直接確認したものであり、確認できなかった項目は最初から外した。バージョン番号には確認時点を併記するが、この分野のバージョンは数週間単位で変わるため、読者が読む時点では違っている可能性がある。またこの記事は特定の商用製品を勧めない。オープンソースのプロジェクトと商用サービスは区別して表記する。

1. 実際に変わったこと - 公式文書で確認できた範囲だけ

変化を体感で語ると検証不能な主張になる。そこでまず確認可能な事実だけを並べる。

  • インプロセス分析エンジンの成熟 — DuckDB の公式文書は、このエンジンが別プロセスとして動かずホストプロセスの中に完全に埋め込まれること、そしてインストール・更新・保守すべき DBMS サーバソフトウェアが存在しないことを述べる。対象は OLAP、すなわち保存されたデータセットの相当部分を走査する比較的長時間の複雑なクエリだ。
  • 単一ノードの上限が上がった — 同じ文書は、資源の限られたエッジ機器から100 個以上の CPU コアを備えた数テラバイトメモリのサーバまでを対象とし、対応するレイクハウスフォーマットを通じてペタバイト規模まで拡張しうると記す。
  • RAM より大きいことは分散の理由ではない — Polars の公式文書は、ストリーミング API が全データを同時にメモリへ置かずに結果を処理させ、利用可能な RAM よりはるかに大きいデータセットを扱うと明記する。エンジン自体は Rust で書かれ、追加設定なしで利用可能な CPU コアへ作業を分配する。
  • テーブルフォーマットの仕様が世代を越えた — Apache Iceberg の仕様は、バージョン 1(分析データテーブル)、2(行単位の削除)、3(拡張型と機能)を完了・採択済みとし、バージョン 4(メタデータ構造と表現)は活発に開発中でまだ正式採択されていないと記録する。
  • フォーマット間の翻訳層が生まれた — Delta Lake の Universal Format と、Apache のインキュベーティングプロジェクトである XTable が、それぞれ異なる方式でフォーマット間のメタデータ変換を扱う。差は後段の表で整理する。
  • カタログが共通規約になった — Apache Polaris はIceberg の REST API を実装し、Apache Doris、Flink、Spark、Dremio OSS、StarRocks、Trino など複数のプラットフォーム間で多エンジンの相互運用を可能にすると述べる。
  • 変換ツールの中核が書き直された — dbt の公式文書は、Fusion エンジンがRust で書かれ、複数のエンジン方言にまたがって SQL をネイティブに理解し、誤った SQL をウェアハウスに届く前に捕まえると説明する。当該ページの最終更新日は 2026 年 7 月 25 日である。
  • オーケストレータがメジャー世代を変えた — Apache Airflow のリリースノートは、3.0.0 が 2025 年 4 月 22 日に出てタスク実行 API と Task SDK、React ベースの UI 再作成、DAG バージョニング、資産ベースのスケジューリングを含んだと記す。文書上の最新は3.3.0(2026 年 7 月 6 日)である。

この一覧で名前より重要なのは方向だ。計算はより小さい単位へ降り、保存とメタデータはより共通の規約へ上がった。以下ではこの方向が実務の判断をどう変えるかを順に扱う。

2. データ規模の現実 - 分岐点はどこにあるか

本稿の中心軸はここだ。ほとんどの組織が実際に扱うデータは、分散処理を必要とする規模ではない。それでもスタック設計は「後で大きくなるから」を根拠に、最も重い選択肢から出発することが多い。この出発点は二つの費用を即座に生む。クラスタの面倒を見る人の時間と、開発の反復速度の低下だ。

規模を語るときによくある誤解がひとつある。「データが RAM より大きい」を分散の根拠にすることだ。すでに引用したとおり Polars の文書はストリーミング API で RAM より大きいデータセットを扱うと明記し、DuckDB の文書はレイクハウスフォーマットを通じてペタバイト規模まで拡張しうると記す。つまり規模だけでは分岐点にならない。実際に分かれるのは、次の表のように規模以外の軸だ。

状況既定値とすべき方式その選択が壊れる条件先に確認すること

表の最後の二行が実務で最も誤読されやすい。分散が必要になる本当の理由は、データ規模ではなく失敗範囲と同時実行数である場合が多い。ジョブが 6 時間走って 5 時間 30 分の地点で落ちるなら、問題はスループットではなく再試行の単位だ。この状況はエンジンを替えるよりも作業を分割することで解決する場合がはるかに多い。

判断を単純にする問いをひとつ提案する。「この処理を 1 台で走らせたことがあるか」だ。なければ、その答えを先に作らなければならない。代表的なワークロードをひとつ単一ノードで最後まで走らせて実測して初めて、分散が必要かどうかが事実として確定する。この実測なしに下す決定はすべて推定である。

3. 単一ノードエンジンが実際に覆う領域

単一ノードの方式が広がった理由はハードウェアとソフトウェアの両側にある。1 台に載るコアとメモリが増え、エンジンがそれを使う方法が良くなった。ここで重要なのは、二つのエンジンの性格が互いに異なることだ。

DuckDB は SQL インターフェースを持つインプロセス OLAP エンジンである。公式文書は、インストール・更新・保守すべきサーバソフトウェアがなく、主要な OS と CPU アーキテクチャすべて向けにコンパイルできると述べる。実務でこの性質が与える利点は配布単位がライブラリひとつで済むことだ。オブジェクトストレージ上のファイルをそのままクエリする形が最も多い使い方になる。

-- オブジェクトストレージの列指向ファイルをそのままクエリする
-- パーティション経路で絞ることが性能の大半を決める
SELECT category,
       count(*)     AS n,
       sum(amount)  AS total
FROM 's3://bucket/events/year=2026/month=07/*.parquet'
WHERE amount > 0
GROUP BY category
ORDER BY total DESC
LIMIT 20;

Polars はデータフレーム API を持つエンジンだ。公式文書によれば Rust で書かれ、追加設定なしで利用可能なコアへ作業を分け、ストリーミング API でメモリより大きいデータを処理する。Arrow のデータを多くの場合ゼロコピーで消費・生成するが、内部の計算とバッファの実装は独自であると文書がはっきり記している。この区別は重要だ。Arrow と相互運用するという言明は、Arrow の実装の上に載っているという意味ではない。

import polars as pl

# スキャンは即座に読まない。条件と列の選択がファイル読み取りの段階まで押し下げられる
q = (
    pl.scan_parquet("events/*.parquet")
      .filter(pl.col("amount") > 0)
      .group_by("category")
      .agg(
          pl.len().alias("n"),
          pl.col("amount").sum().alias("total"),
      )
      .sort("total", descending=True)
)

df = q.collect()      # 実行はここで初めて起きる
print(df.head(20))

二つのコードの共通点を見よう。どちらも、読むファイルを絞ることが性能の大半を決める。エンジンの選択ではなくパーティション設計と列の選択が先だ。この事実は、後段で扱う「フォーマットが先」という結論とまったく同じ場所を指している。

選定基準を整理するとこうなる。SQL がチームの共通語で成果物がテーブルなら SQL エンジン側が、パイプラインが Python コードの中にあり中間段階に Python のロジックが混ざるならデータフレーム側が摩擦が少ない。両方を併用するのも正常だ。ただし同じ変換を二か所に重複実装した瞬間、整合性の事故が予約される。

4. フォーマットはエンジンより長く生きる

スタックの中で最も寿命が長い決定はデータをどんな形で残すかである。エンジンはプロセスだ。気に入らなければ別のプロセスを立てればよい。一方、保存フォーマットの変更は保管したデータ全体を書き直す作業であり、カタログの変更はそのデータを指すすべての参照を書き直す作業になる。だから決定の順序はフォーマット、カタログ、エンジンでなければならない。

テーブルフォーマットがファイルフォーマットと違う点から押さえよう。列指向ファイルは「このファイルに何が入っているか」しか知らない。テーブルフォーマットは「このテーブルは今どのファイル群なのか」を原子的に管理する。ここからスナップショット、タイムトラベル、スキーマ進化、同時書き込み制御が生まれる。

世代の変化を最も明確に文書化しているのは Iceberg だ。仕様は各バージョンを名前と状態で区別する。バージョン 1 は分析データテーブル、2 は行単位の削除、3 は拡張型と機能であり、三つとも完了・採択済みだ。バージョン 3 が追加した項目として仕様はナノ秒タイムスタンプ、unknown・variant・geometry・geography 型、列の既定値、パーティションと整列のための多引数変換、行系譜の追跡、バイナリ削除ベクタ、テーブル暗号鍵を挙げる。バージョン 4 はメタデータ構造と表現を扱い、まだ正式採択されていない開発中の状態だ。

この一覧を実務の言葉に置き換えるとこうなる。削除と更新が安くなり、形の変わる半構造データと空間データが一級市民になり、行単位の追跡と暗号化が仕様の内側に入った。以前はアプリケーションが背負っていた問題がフォーマット層へ降りてきたのだ。だから「テーブルフォーマットを使うか」はもはや規模の問いではなく運用要件の問いである。監査証跡が要るか、誤ったバッチを戻す必要があるか、スキーマが変わるか。ひとつでも該当すればすでに対象だ。

  • バージョン番号はライブラリと仕様で別物 — 仕様バージョン 3 と実装のリリース番号は別だ。文書がどちらを指すか確認しないと互換性の判断がずれる。
  • 書き込み対応は常に後から来る — あるエンジンが新仕様に「対応」と言うとき、読み取りだけか書き込みまでかを確認する。この差が移行計画を左右する。
  • パーティション設計をフォーマットが代行してくれるわけではない — 誤ったパーティションはどのフォーマットでも全走査を招く。最も頻繁に使うフィルタを基準に決める。
  • 小さなファイル問題は残る — 頻繁なコミットはファイル数を増やす。圧縮と統合を運用項目として立てておかないと数か月後にクエリが遅くなる。
  • フォーマットを決めてからエンジンを選ぶ — 逆にすると、エンジンが対応するフォーマットの一覧が組織の保存戦略を代わりに決めてしまう。

5. フォーマットの収束はどんな形で起きているか

「フォーマット戦争の勝者」式の記述は多くがベンダー資料から出る。公式資料だけで言えることはより慎重だが、より有用だ。単一のフォーマットへ統一される代わりに、フォーマットの間を行き来する層のほうが先に定着している。確認できた方式は性格の異なる二つだ。

方式公式文書が述べる内容方向性実務上の制約
Delta Lake Universal FormatDelta テーブルを Iceberg・Hudi のクライアントから読めるようにし、Delta のコミット後に非同期でメタデータを生成Delta から他フォーマットへ出る一方向Iceberg・Hudi の観点では読み取り専用。列マッピングの有効化などの前提条件がある
Apache XTable(インキュベーティング)新しいフォーマットではなく、レイクハウステーブルフォーマットのメタデータを翻訳する抽象と道具Delta・Hudi・Iceberg 間の全方向インキュベーティング段階。元フォーマットの書き込み主体は依然ひとつに定める必要がある
Iceberg 仕様自体の世代進化v1・v2・v3 は採択完了、v4 は開発中・未採択フォーマット内部での機能吸収エンジンごとに対応時期が異なる。読み書きの対応範囲を個別に確認する必要がある

表の読み方はこうだ。現時点で「ひとつだけ選べば安全」という条件は成立しない。代わりに実質的な安全弁になるのは「自分のデータが他フォーマットの読み手に読まれる経路があるか」である。一方向の変換しかない構成なら、その方向が組織の将来の選択肢を決める。全方向の翻訳層を使う場合でも、書き込み主体はひとつでなければならないという原則は変わらない。二つのシステムが同じテーブルへ同時に書きはじめれば、どんな翻訳層も整合性を保証できない。

DuckLake は別の軸の事例として見る価値がある。メタデータをファイル木ではなく SQL データベースに置く方式であり、公式 FAQ はこれを Unity Catalog とともに使う Delta Lake、あるいは Lakekeeper や Polaris とともに使う Iceberg と似た構成だと説明する。ここで確認できるのは特定製品の優劣ではなく、カタログが独立した決定項目として分離したという事実だ。

6. カタログが新しい決定地点になった

数年前までカタログは「メタストアに何を使うか」程度の副次的な問いだった。今は違う。複数のエンジンが同じテーブルを共有する構造では、カタログはアクセス制御とトランザクション境界が出会う地点である。そしてこの地点が標準化されつつある。

公式資料で確認できる代表例が Apache Polaris だ。このプロジェクトは自らを Apache Iceberg のためのオープンソースのカタログと紹介し、Iceberg の REST API を実装して Apache Doris、Apache Flink、Apache Spark、Dremio OSS、StarRocks、Trino を含む複数のプラットフォーム間で多エンジンの相互運用を可能にすると述べる。ここで重要なのは製品名ではなく構造だ。カタログが REST の規約として公開されればエンジンはその規約のクライアントになり、クライアントは交換可能な部品になる。

逆の構造を想像すれば、なぜこれが決定地点なのかがはっきりする。カタログが特定プラットフォームの内部にしか存在しなければ、新しいエンジンを足すたびに、そのプラットフォームがそのエンジンに対応しているかを尋ねることになる。選択権が組織から供給者へ移る。この移動は請求書の項目として現れないため気づきにくい。

  • カタログは権限の境界だ — テーブルの一覧を知る主体が、そのままアクセスを統制する主体になる。ストレージ権限だけでは細かい統制が難しい。
  • 規約ベースかを先に確認する — 公開された API 規約を実装するのか、専用 SDK でしか到達できないのか。この答えが後の移行費用の半分以上を決める。
  • エンジン対応の一覧は時点情報だ — 今日の一覧にないエンジンが来年入ることもあれば、その逆もある。一覧より規約を見る。
  • 名前空間の設計を後回しにしない — 名前空間とテーブルの命名規則は、後で変えるとすべての参照に触れることになる。初期に決める。
  • テーブル保守作業の主体を決める — スナップショットの期限切れ、孤立ファイルの整理、ファイル統合を誰がいつやるか決めないと、費用と性能が同時に悪化する。

7. Arrow が接着剤になった理由

道具が増えれば普通は統合費用が跳ね上がる。ところがこの数年のデータスタックには、道具が増えたのに組み合わせ費用がむしろ下がった区間がある。その理由の相当部分がメモリ表現の標準化だ。

Apache Arrow の公式仕様は、このフォーマットが言語非依存のインメモリデータ構造仕様、メタデータのシリアライズ、そしてシリアライズと汎用データ転送のプロトコルを含むと規定する。設計目標としては逐次アクセスのためのデータ隣接性、定数時間のランダムアクセス、SIMD とベクトル化への親和性、そしてポインタスウィズリングなしで再配置可能であり共有メモリで真のゼロコピーアクセスが可能である点を挙げる。代価も明記されている。分析性能とデータ局所性を得る代わりに変更操作が相対的に高価だ。

この仕様がなぜ接着剤なのかは、その上に載った二つの規約を見れば明らかになる。

  • ADBC — 公式文書はこれを高速な Arrow ネイティブのデータベースアクセスのための標準 API とライブラリの集合として紹介する。結果を Arrow の列形式で直接返して複製と変換をなくすと述べ、C/C++、C#、Go、Java、JavaScript、Python、R、Ruby、Rust を対応言語として挙げる。ドライバとしては Flight SQL、PostgreSQL、SQLite などが文書化されている。
  • Arrow Flight SQL — 公式文書はこれをArrow のインメモリ形式と Flight RPC フレームワークで SQL データベースとやり取りするプロトコルと定義する。Flight の既存 RPC メソッドを再利用し、Protobuf で定義された要求・応答メッセージを組み合わせてコマンドを提供する。文書は JDBC・ODBC など既存ドライバとの互換のため、サーバ実装がオプション値の文字列表現を受け入れることを強く推奨すると記す。
import adbc_driver_postgresql.dbapi as pg

# 結果を行単位のオブジェクトへ展開して再び束ね直すことなく列形式のまま受け取る
with pg.connect("postgresql://localhost:5432/analytics") as conn:
    with conn.cursor() as cur:
        cur.execute(
            "SELECT category, amount FROM events WHERE amount > 0"
        )
        table = cur.fetch_arrow_table()

print(table.num_rows, table.schema)

実務でこの標準化が生む差は「組み合わせの自由度」だ。保存は列指向ファイル、計算は単一ノードエンジン、伝達は Arrow、可視化は別言語のライブラリ、といった構成が各境界でデータを作り直さずにつながる。ADBC 自体とその上に出てきた道具をより深く扱った記事はADBC ベースのクエリ道具にまとめてある。Arrow がなぜこの形に設計されたかについての作り手の視点はArrow・pandas 創始者の展望で扱った。

8. エンジンを替えても生き残るコード - API 層の収束

エンジンの交換費用を下げようとする試みは古いが、今は実際に使われる形へ絞られた。公式リポジトリで確認できる二つの筋がある。

Ibis は自らを可搬な Python データフレームライブラリと紹介し、20 個以上のバックエンドに同じデータフレーム API を使い、1 行だけ変えてローカルで反復しリモートへ配備できると述べる。既定のローカル実行は DuckDB を通じて行われ、遅延式と対話モードを提供する。リポジトリが列挙するバックエンドには Apache DataFusion、Druid、Flink、Impala、PySpark、Athena、BigQuery、ClickHouse、Databricks、DuckDB、Exasol、Materialize、MySQL/MariaDB、Oracle、Polars、PostgreSQL、RisingWave、SingleStoreDB、SQL Server、SQLite、Snowflake、Trino が含まれる。

Narwhals は性格が異なる。リポジトリはこれをデータフレームライブラリ間のきわめて軽量で拡張可能な互換層と説明し、依存関係がゼロで、利用者が渡したものだけを使うのでライブラリを軽く保てると述べる。全 API に対応するバックエンドとして cuDF、Modin、pandas、Polars、PyArrow を、遅延専用として Daft、Dask、DuckDB、Ibis、PySpark、SQLFrame を挙げる。利用先としては scikit-learn、Plotly、Bokeh、Altair、LightGBM、py-shiny などが並ぶ。

import narwhals as nw

# 渡されたオブジェクトがどのライブラリのデータフレームでも同じコードで処理し
# 同じ型で返す。ライブラリを作る側で特に有用だ
def summarize(df_native):
    df = nw.from_native(df_native)
    out = (
        df.filter(nw.col("amount") > 0)
          .group_by("category")
          .agg(nw.col("amount").sum())
    )
    return nw.to_native(out)

選定基準は自分が何を作っているかで分かれる。ライブラリや再利用可能な道具を作るなら、利用者がどのデータフレームを渡すか分からないので互換層の側が合う。依存を増やさないという性質がここで決定的だ。分析パイプラインを作り実行場所を変えたいなら、複数バックエンドへコンパイルされる式の層の側が合う。

  • 抽象化は無料ではない — バックエンドごとに対応範囲が異なる。共通部分集合の外へ出た瞬間、可搬性は消える。
  • 性能チューニングは結局エンジン固有の領域 — ヒント、パーティション戦略、統計は抽象層が隠してくれない。
  • テストは実際のバックエンドで行う — ローカルで通った式が、リモートのエンジンでは別の SQL に翻訳されうる。
  • 抽象化を使う理由を文書に残す — 「いつか替えるかもしれないから」は理由ではない。替える計画があるか、利用者が多様な場合にのみ値打ちがある。

9. オーケストレーションと変換 - 重心の移動

パイプラインを「何をいつ実行するか」で見ていた視点が「どのデータ資産が最新か」へ移る流れは、公式文書からも読み取れる。

Apache Airflow のリリースノートは、3.0.0(2025 年 4 月 22 日)でタスク実行 API と Task SDK、React ベースの UI 再作成、DAG バージョニング、資産ベースのスケジューリング、Edge Executor、スケジューラが管理するバックフィルが導入されたと記す。文書上の最新版は 3.3.0(2026 年 7 月 6 日)である。ここで実務的に大きい項目はDAG バージョニングだ。パイプラインの定義が変わったとき、過去の実行がどの定義で動いたか追跡できなければ、事故の原因分析が推測に依存することになる。

Dagster の公式文書は自らをデータエンジニアのために作られ、系譜と可観測性が統合され、宣言的なプログラミングモデルと最上級のテスト容易性を備えたデータオーケストレータと紹介し、資産中心の考え方を前面に置く。タスクではなく成果物を宣言し、その間の依存を記述する方式だ。

dbt 側の変化は中核の書き直しだ。公式文書は Fusion エンジンがRust で書かれ、複数のエンジン方言にまたがって SQL をネイティブに理解し、モデルの誤った SQL をウェアハウスに到達する前に即座に捕まえると説明する。自動補完、ホバー情報、入力中のインラインエラーといったエディタ機能や、プロジェクト全体にわたるモデル・列定義の追跡も明記されている。文書は Fusion がdbt をインストールしたときの既定の体験であり無料で使え、Apache 2.0 のランタイムを基盤とすると記す。当該ページの最終更新日は 2026 年 7 月 25 日である。

三つの変化の共通点は検証を実行より前に引き寄せることだ。パイプラインが壊れる地点を実行時からコンパイル時へ移そうとする試みであり、同じ問題意識を型システムの側から扱った事例は型検査でスキーマドリフトを防ぐ方式で、意味層の側から扱った事例は関係を宣言するモデリング言語でそれぞれ扱った。

  • オーケストレータを二つ使わない — チームごとに別のオーケストレータを使うと、失敗通知と再試行方針が分かれ、障害時にどこを見るべきか分からなくなる。
  • スケジュールではなく依存を宣言する — 時刻で束ねたパイプラインは、上流が遅れると静かに古いデータを作る。
  • バックフィル経路を先に作る — 過去区間の再処理は例外ではなく定期作業だ。初期に設計しないと毎回手作業になる。
  • 定義のバージョンとデータのバージョンを一緒に残す — どのコードがどのスナップショットを作ったかがつながらなければ再現は不可能だ。
  • 検証をパイプラインの外に置かない — 別スクリプトで回る品質検査は、保守から真っ先に脱落する。

10. ロックインはどこに生じ、抜ける費用はいくらか

ロックインをひとつの塊として語ると議論が感情的になる。層ごとに抜ける費用が違うという事実を認めれば、はるかに現実的な対話になる。次の表は層ごとに移行が実際に何を要求するかを整理したものだ。

ロックインが生じる層抜けるとき実際にやること相対費用費用を下げる事前措置
コンピュートエンジン同じデータを読む別のプロセスを立てて性能を再調整低いエンジン固有機能をパイプライン全体にばらまかない
SQL 方言関数・型・ウィンドウ構文の差を全数修正し結果を突き合わせる中方言依存の構文を一か所に集めるか、可搬な層を使う
オーケストレーションDAG・資産の定義、再試行と通知の方針、バックフィル手順を書き直す中業務ロジックをオーケストレータの API の外に置く
保存フォーマット保管したデータ全体を書き直し、その間は両方を並行運用する高い公開仕様に基づくフォーマットを使い、変換経路を事前に確認する
カタログテーブル・権限・系譜の参照をすべて移し、全消費者を再接続する高い公開 API 規約を実装するカタログを選ぶ
独占的な保存層書き出し経路が制限されると移行そのものが交渉対象になる最も高い契約段階で大量書き出しの方式と費用を文書で確認する

表から得る結論は単純だ。費用の低い層では好きに選び、費用の高い層では公開規約を選ぶ。エンジンは好みで選んでよいが、フォーマットとカタログを好みで選んではいけない。そして最も高い費用は技術ではなく契約から発生する。データを大量に書き出す経路がないか費用が非対称なら、そのシステムから出る決定は技術の決定ではなく交渉になる。

バランスもひとつ書いておく。ロックイン回避を最優先の価値に置くと、それ自体が費用になる。すべての層を交換可能にしようとする設計は抽象が厚くなり、どのエンジンの長所も十分に使えない結果に終わりやすい。実務の均衡点は移行費用の高い層だけを公開規約で縛り、残りは今いちばん合うものを使うことだ。

11. 導入すべきでない信号

「どのツールが最良か」という問いに答えはない。代わりに「自分たちの状況で何が過剰か」にはかなり正確な答えが可能だ。以下は実務で繰り返し確認される過剰の信号とその処方である。

観測される信号実際に起きていることまず試すべき措置
クラスタが一日の大半で遊休状態待機資源が計算資源より高くなった状態単一ノードで代表ジョブを最後まで実行して実測
ストリーミングなのに消費者は一日 1 回照会要求されていない鮮度に運用負担を払っているSLA 文書の数字を原文で確認
ツールの担当が事実上ひとりその構成要素が単一障害点人員が増えないなら構成要素を減らす
パイプライン数よりツール数が速く増加統合費用が成果物の価値を超えつつある同じ役割のツールをひとつに統合
同じ変換が二つの言語で重複実装整合性の事故が予約された状態単一の定義地点を決め、残りは参照にする
導入根拠が前四半期の事故ではなく予測経験していない問題への先行投資実際に起きた障害の一覧で優先順位を書き直す

ここで最も重要な行は三番目だ。ツールの適正数はデータ規模ではなく人数で決まる。各構成要素はアップグレード、セキュリティパッチ、障害対応、使い方の文書化を要求する。この負担の総和がチームの能力を超えると、スタックは静かに古びはじめ、古びたスタックはある日、更新できない状態で発見される。

逆に導入を正当化する信号も整理しておく。前四半期に同種の障害が繰り返し発生し、その原因が現構成の構造的限界で説明され、新しい構成要素を日常的に世話する人員が二名以上確保され、失敗したときに戻れる経路が文書で存在するときだ。四つのうちひとつでも欠ければ、導入時期を先送りするほうが概ね正しい。

12. 決定の順序 - 実行可能な手順

ここまでの内容を順序へ圧縮する。この順序どおりに踏めば、たいていの議論は 3 段階か 4 段階で片づく。

  1. 代表的なワークロードをひとつ固定する — 実運用から出たものでなければならない。合成データは結論を楽観的にする。
  2. 単一機で最後まで走らせて実測する — 所要時間、最大メモリ、失敗地点を記録する。この数値のない規模論争はすべて推定だ。
  3. 要求される鮮度を文書で確認する — 契約や合意文書に書かれた数字を見る。慣行として固まった秒単位の期待は根拠ではない。
  4. 保存フォーマットを先に決める — 公開仕様があり、他フォーマットへ出る経路が確認できるものを選ぶ。
  5. カタログを次に決める — 公開 API 規約を実装するか、エンジンがクライアントとして接続できるかを見る。
  6. エンジンは最後に選ぶ — この時点でエンジンは交換可能な部品なので、チームの言語と運用能力で選べばよい。
  7. パーティションとファイルサイズの方針を一緒に決める — フォーマットを決める場で同時に決める。後で変えると全体の書き直しになる。
  8. テーブル保守を運用項目として登録する — スナップショットの期限切れ、孤立ファイルの整理、ファイル統合の周期と担当を明示する。
  9. 変換の定義を一か所に集める — 同じ指標が二か所で計算されないよう、単一の定義地点を作る。
  10. オーケストレーションは依存ベースで宣言する — 時刻ではなく上流資産の更新を基準に起動する。
  11. 戻す経路を作り、実際に試す — 以前のスナップショットへ復帰する手順をリリースごとに一度は回してみる。
  12. 四半期ごとにスタックの構成要素数を数える — 増えたなら、その分だけ担当も増えたかを一緒に確認する。そうでなければ減らす時期だ。

結論: 道具の一覧は古びるが、順序は残る

2026 年のデータツール地形を一文に縮めるとこうなる。計算はより小さい単位へ降り、保存とメタデータはより共通の規約へ上がった。その結果、実務者が答えるべき問いが変わった。以前は「この規模を担えるだけ大きいものを選んだか」だったが、いまは「この規模に比べて過剰なものを選んでいないか」だ。

この記事が繰り返した判断規則は三つだ。第一に規模の論争は単一ノードの実測のあとに始める。第二に決定の順序はフォーマット、カタログ、エンジン。第三に移行費用の高い層だけを公開規約で縛り、残りは今いちばん合うものを使う。この三つは特定の道具の興亡と無関係に維持される。

最後にこの記事の賞味期限を明かしておく。ここに記したバージョン番号と状態は2026 年 7 月 29 日に各プロジェクトの公式文書で確認したものであり、この分野でその値は速く変わる。だから道具の名前と数字は確認用としてだけ使い、持ち帰るものは順序と基準にするのがよい。道具は変わり続けるが、抜けにくいものを先に決め抜けやすいものを後で決めるという原則は、そう簡単に変わらない。
