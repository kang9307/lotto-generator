이 글의 코드와 출력은 Windows 10의 Git Bash(bash 5.2.37, GNU coreutils date 8.32)·Windows PowerShell 5.1(5.1.19041.6456)·Node.js v22.16.0·Python 3.13.3에서 얻은 값이고 출력은 그대로 옮겼다. 시각은 모두 UTC로 출력하며 지역 시간대와 서머타임은 관여하지 않는다. 항목마다 「코드 → 실제 출력 → 이유」 순서이고, 이유에서 공식 문서를 옮긴 곳은 문서의 문장임을 밝힌다. 「약 N년」으로 적은 값은 평균 연 길이(31556952초)로 나눈 계산값이다.

서론 - 숫자는 하나인데 단위는 넷이다

Unix 시각은 1970-01-01T00:00:00Z(에포크) 이후 경과한 시간을 정수로 센 값이다. Python 문서는 time 모듈의 에포크를 모든 플랫폼에서 1970년 1월 1일 00:00:00(UTC)이라고 적고, MDN은 JavaScript의 Date가 에포크 이후의 밀리초를 담는다고 적는다. 기준 시점은 같은데 세는 단위가 초·밀리초·마이크로초·나노초로 갈린다. 그래서 같은 정수가 파일과 API 사이를 지날 때 단위가 어긋나면 날짜가 1970년 초나 수만 년 뒤로 간다.

  • 초를 밀리초로 읽으면 날짜가 1970년 1월 안으로 들어간다.
  • 밀리초를 초로 읽으면 연도가 5만 년대로 간다.
  • 자릿수(10·13·16·19자리)로 단위를 판별하는 규칙은 특정 기간에만 맞는다.
  • 32비트 정수는 2038년에 초 값을 담지 못한다.

다루는 질문은 다음과 같다.

  • 같은 값을 초·밀리초·마이크로초·나노초로 읽으면 날짜가 각각 어디로 가는가.
  • 자릿수로 단위를 판별하는 규칙은 어느 시각 구간에서 맞고 어디서 깨지는가.
  • 판별 함수를 네 도구에서 같은 방식으로 쓰면 같은 답이 나오는가.
  • Python·Node·PowerShell·date의 현재 시각 API는 각각 몇 자리를 돌려주는가.
  • 32비트 경계와 각 도구의 표현 한계는 어디인가.

엑셀의 직렬값처럼 기준일이 다른 날짜 숫자는 엑셀 직렬값 글이, 시간대 규칙의 변화는 타임존 데이터 글이, 벽시계와 단조 시계의 구분은 단조 시계 글이 다룬다. 여기서는 Unix 에포크 기준 정수의 단위만 본다.

같은 숫자를 초와 밀리초로 읽으면

1700000000(10자리)과 1700000000000(13자리)을 네 도구에서 초와 밀리초로 읽었다. Python은 timezone.utc를 지정한 fromtimestamp이고, Node는 new Date와 toISOString, PowerShell은 DateTimeOffset의 FromUnixTimeSeconds·FromUnixTimeMilliseconds, bash는 GNU date의 -d @이다.

  • 1700000000을 초로 읽으면 네 도구 모두 2023-11-14T22:13:20이다. 같은 값을 밀리초로 읽으면 네 도구 모두 1970-01-20T16:13:20이다.
  • 1700000000000을 초로 읽은 결과는 도구마다 다르다. GNU date는 55840-11-08T22:13:20Z를, Node는 +055840-11-08T22:13:20.000Z를 출력했다. Python은 OSError: [Errno 22]를, PowerShell은 ArgumentOutOfRangeException을 냈다.
  • Python 문서는 fromtimestamp가 플랫폼 C 라이브러리의 localtime() 또는 gmtime() 범위를 벗어나면 OverflowError를, 그 함수가 실패하면 OSError를 낼 수 있고 보통 1970~2038년으로 제한된다고 적는다. 이 Windows 빌드에서 OSError가 난 것은 이 문장과 같은 방향이다.
  • Microsoft Learn은 FromUnixTimeSeconds의 유효 범위를 -62,135,596,800 이상 253,402,300,799 이하로 적고 벗어나면 ArgumentOutOfRangeException이라고 적는다. 출력의 메시지와 같은 범위이다.
  • 마이크로초 값 1700000000000000을 초로 읽으면 Node는 getTime이 NaN인 Invalid Date가 되고 toISOString은 RangeError를 낸다. GNU date는 53872825-06-17T22:13:20Z를 출력했다.

네 단위를 서로 바꿔 읽은 전체 표를 계산했다. 같은 순간 1700000000초를 각 단위로 쓴 정수가 행이고, 읽는 단위가 열이다.

from datetime import datetime, timezone, timedelta
                    EPOCH = datetime(1970, 1, 1, tzinfo=timezone.utc)
                    SCALE = {'s': 1, 'ms': 10**3, 'us': 10**6, 'ns': 10**9}
                    base = 1700000000  # 2023-11-14T22:13:20Z in seconds
                    def read_as(value, unit):
                        sec = value // SCALE[unit]
                        if sec < 253402300800:
                            return (EPOCH + timedelta(seconds=sec)).strftime('%Y-%m-%d %H:%M:%S')
                        return 'year ~%d' % (1970 + value / SCALE[unit] / 31556952)
                    print('%-28s' % 'value (written as)' + ''.join('%-24s' % ('read as ' + u) for u in SCALE))
                    for u, k in SCALE.items():
                        v = base * k
                        print('%-28s' % ('%d (%s)' % (v, u)) + ''.join('%-24s' % read_as(v, r) for r in SCALE))

자릿수 판별 규칙과 그 규칙이 깨지는 경계

흔한 규칙은 자릿수이다. 10자리면 초, 13자리면 밀리초, 16자리면 마이크로초, 19자리면 나노초로 본다. 이 규칙이 맞는 시각 구간을 계산했다. 각 자릿수가 시작되는 순간이다.

from datetime import datetime, timezone, timedelta
                    EPOCH = datetime(1970, 1, 1, tzinfo=timezone.utc)
                    def at(sec):
                        return (EPOCH + timedelta(seconds=sec)).strftime('%Y-%m-%d %H:%M:%S') if sec < 253402300800 else 'year > 9999'
                    print('first instant (UTC) whose Unix value reaches N digits:')
                    for d, unit, per in ((10, 'seconds', 1), (11, 'seconds', 1), (13, 'millis', 1000), (16, 'micros', 10**6), (19, 'nanos', 10**9)):
                        print('  %2d digits  %-8s  starts at %s' % (d, unit, at(10 ** (d - 1) / per)))
                    print('last instant of the 10-digit seconds range:', at(9999999999))
                    print('9-digit seconds range: 100000000 =', at(100000000), ' ... 999999999 =', at(999999999))

자릿수 규칙과 임계값 규칙을 1970-01-01부터 2300-12-31까지 약 1.01일 간격 119193개 시각에 적용했다. 임계값 규칙은 절댓값이 1e11 미만이면 초, 1e14 미만이면 밀리초, 1e17 미만이면 마이크로초, 그 이상이면 나노초로 본다. 먼저 그 임계값이 어느 날짜인지 계산했다.

from datetime import datetime, timezone, timedelta
                    EPOCH = datetime(1970, 1, 1, tzinfo=timezone.utc)
                    def by_digits(v):
                        n = len(str(abs(v)))
                        return {10: 's', 13: 'ms', 16: 'us', 19: 'ns'}.get(n, '?')
                    def by_threshold(v):
                        a = abs(v)
                        return 's' if a < 10**11 else 'ms' if a < 10**14 else 'us' if a < 10**17 else 'ns'
                    SCALE = {'s': 1, 'ms': 10**3, 'us': 10**6, 'ns': 10**9}
                    EDGES = [0, 10**8, 10**9, 10**10, int((datetime(2301, 1, 1, tzinfo=timezone.utc) - EPOCH).total_seconds())]
                    def d(sec): return (EPOCH + timedelta(seconds=sec)).strftime('%Y-%m-%d %H:%M:%S')
                    secs = list(range(EDGES[0], EDGES[-1], 86400 + 1234))
                    print('tested instants:', len(secs))
                    for i in range(4):
                        print('window %d: %s .. %s' % (i + 1, d(EDGES[i]), d(EDGES[i + 1] - 1)))

                        print(rule.__name__ + '  (wrong / tested)')
                        print('  %-8s %12s %12s %12s %12s' % ('window', 's', 'ms', 'us', 'ns'))

                            cells = ['%d/%d' % (sum(1 for s in w if rule(s * k) != u), len(w)) for u, k in SCALE.items()]
                            print('  %-8d %12s %12s %12s %12s' % ((i + 1,) + tuple(cells)))

판별 함수 - 네 도구에서 같은 답이 나오는가

임계값 규칙을 네 도구로 구현해 같은 입력 8개를 넣었다. 입력은 0, -1, 86400000, 1700000000, 1700000000123, 1700000000123456, 1700000000123456789, 253402300799이다. Node는 19자리 값을 정확히 다루려고 BigInt를 쓰고, PowerShell은 Int64, bash는 64비트 산술을 쓴다.

  • JavaScript에서 (2**31)|0은 -2147483648이고 그 값을 초로 쓴 날짜는 1901-12-13T20:45:52.000Z이다. 같은 값을 double로 계산하면 2038-01-19T03:14:08.000Z로 정상이다. 비트 연산자가 값을 32비트로 줄이기 때문이다.
  • 부호 없는 32비트 최댓값 4294967295는 2106-02-07 06:28:15 UTC이다.
  • 밀리초를 부호 있는 32비트에 담으면 2147483647밀리초(약 24.86일)인 1970-01-25 20:31:23에서 넘친다. 2038년이 아니라 에포크 직후 25일이다.
  • Python 문서는 time 모듈이 에포크 이전이나 먼 미래의 날짜를 다루지 못할 수 있고 상한은 C 라이브러리가 정하며 32비트 시스템에서는 보통 2038년이라고 적는다. 이 PC의 Python은 3000-12-31과 3001-01-01은 변환했고 253402300799는 OSError를 냈으며, 같은 값은 EPOCH + timedelta로는 9999-12-31T23:59:59까지 표현했다.
  • JavaScript Date의 범위는 ±8,640,000,000,000,000밀리초이다. 8.64e15는 +275760-09-13T00:00:00.000Z이고 1을 더하면 getTime이 NaN인 Invalid Date가 되어 toISOString이 RangeError를 낸다. MDN이 적은 범위와 같다.
  • PowerShell의 FromUnixTimeSeconds는 253402300799(9999-12-31 23:59:59)까지 되고 253402300800은 ArgumentOutOfRangeException이다. int32 최댓값과 최솟값은 각각 2038-01-19 03:14:07과 1901-12-13 20:45:52로 변환된다.
  • GNU date 8.32는 2147483648과 -2147483648을 정상 변환했고 bash의 64비트 산술은 9223372036854775807에 1을 더하면 -9223372036854775808이 되었다.

2286년 이후 초 값이나 5138년 이후 임계값 경계규칙이 판정하지 못하거나 오판3절 구간 4, 4절 253402300799

  • 추정이 불가피하면 임계값 규칙을 쓰되 맞는 구간(1973-03-03 ~ 5138-11-16)을 코드 주석과 테스트로 못박는다.
  • 변환 결과가 1970년 1월이나 5천 년대 이후이면 단위 오류를 먼저 의심한다.
  • 32비트 정수 컬럼·프로토콜·파일 형식에 시각을 넣을 때는 2038년이 한계이고, 밀리초라면 25일이 한계이다.
  • 도구마다 범위를 벗어난 값에 대한 반응이 달라서(OSError, ArgumentOutOfRangeException, Invalid Date), 한 도구에서 통과한 값이 다른 도구에서 실패할 수 있다.

확인하지 못한 것

  • Linux·macOS에서 Python fromtimestamp의 한계. 이 PC의 Windows 빌드에서는 253402300799에서 OSError가 났지만 다른 플랫폼의 값은 실행하지 못했다.
  • 32비트 time_t를 쓰는 실제 시스템의 동작. 2038년 경계는 Python 정수 계산과 ctypes 변환으로만 보였다.
  • 윤초의 영향. Python 문서는 에포크 이후 초에서 윤초가 제외된다고 적지만 윤초가 있는 구간의 값은 실행하지 않았다.
  • 지역 시간대와 서머타임. 모든 출력을 UTC로 고정했다.
  • Python fromtimestamp가 3001년 이후 어느 값부터 OSError를 내는지의 정확한 경계.
  • Java·Go·C#·데이터베이스 타임스탬프 타입의 단위와 범위.
  • Windows FILETIME처럼 에포크 기준이 1601년인 형식과 엑셀 직렬값의 단위 혼동.
  • 소수점 초(float)로 표현한 시각의 정밀도 손실.
  • PowerShell 5.1 이외의 .NET에서 FromUnixTimeSeconds의 범위.
