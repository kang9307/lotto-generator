数据库容量规划的困境与生产环境扩缩容频次

在传统的单体数据库体系中，变更服务器硬件规格往往伴随着高昂的运维风险与业务中断。普通的云数据库托管服务在升级实例类型时，通常需要经历物理节点重启，或者借助主从切换来完成实例替换。在这一切换过程中，正在执行的长事务会被强制中断，活跃的连接池全部被断开，应用层往往会遭遇短暂的连接风暴和报错波动。因此，基础设施架构师通常倾向于过度配置，宁可常年为闲置资源买单，也不愿承担线上切换的抖动风险。

水平分片与垂直自动扩缩容的本质分野

拓展数据库的处理能力主要分为两条技术演进路径：将数据拆分到多个物理节点的水平扩展（分片），以及弹性伸缩单节点硬件配额的垂直自动扩缩容。正如我们在前作把Postgres拆分至多台机器的选择 - 水平扩展向事务、连接与约束收取的代价中所详尽剖析的，将PostgreSQL进行水平拆分会引入极高的架构税，包括分布式两阶段提交（2PC）带来的网络延迟累加、跨分片Join的执行衰退、以及全局唯一约束与序列号生成的复杂化。而Lakebase Postgres所实现的实时垂直自动扩缩容，则是在完整保留单节点全功能关系模型、强ACID事务与复杂SQL便利性的前提下，仅动态伸缩底层虚拟机的vCPU与内存配额。

月均32,016次、约81秒一次的真实伸缩节奏

Neon披露的真实运行统计显示，处于生产运行状态的数据库实例平均每月经历32,016次计算规格变更。这一数据意味着系统大约每81秒就会对虚拟机的计算单元（CU）进行一次向上微调或向下回收。现实生活中的业务负载极具潮汐特征，早晚业务高峰、定时统计任务或者促销推广期间系统需要数倍的算力支持，而在深夜低谷期则仅需基础配额维稳。81秒的敏捷响应周期使得算力供给能够严密贴合实时需求曲线，让企业真正只为产生实际业务价值的计算周期付费。

  • 规避前期静态预估的盲目性：彻底摆脱在未知真实查询行为前强制选型带来的算力错配。
  • 原地无中断动态热插拔：在不切断既有网络连接的前提下直接调整运行中虚拟机的资源配额。
  • 双向对称调节的成本原则：不仅要保障高负载时的快速冲顶，更要确保闲置时的即刻回收。
  • 生产级海量实证的可靠性：每月32,016次（约81秒周期）的自动化调节验证了控制体系的成熟度。

计算与存储分离：无停机热调整的架构基石

传统PostgreSQL之所以难以原地自由伸缩硬件规模，根本原因在于其计算进程与持久化数据存储被强行绑定在同一台物理机器及其本地磁盘上。在这种紧耦合设计下，更换机器规格本质上是一次复杂的存储卷重新挂载或节点数据同步操作。Lakebase Postgres通过解耦架构打破了这道枷锁，将运算执行与数据持久化完全划分至不同的系统层次。

无状态计算节点与分布式持久存储层

在Lakebase体系中，计算层被彻底改造为一个纯粹负责运行PostgreSQL引擎与执行查询的无状态层。计算节点充分利用本地RAM以及高速NVMe固态硬盘构建高性能的只读缓存，但其本地并不保留任何持久化的唯一数据状态。所有的持久化、WAL日志复制以及数据多版本历史，全部交由底层的分布式存储子系统统一接管。该存储子系统包含三个核心组件：

  • Safekeeper：运行于高IOPS固态存储上的共识日志节点，负责快速接收并同步PostgreSQL生成的WAL日志，确保提交的持久性。
  • Pageserver：同样基于SSD构建的分布式页面重构节点，负责回放WAL历史并实时按需重组任意历史版本的数据页供计算节点读取。
  • 对象存储：依托低成本、高可靠的云端对象存储（如S3），归档存放所有不可变的长周期数据块与基础检查点。

由于计算节点本地没有不能丢失的有状态文件，数据库引擎无需搬迁任何底层数据，即可在集群内部自由实现启动、停止、跨宿主机漂移以及在线配额重调。存储计算分离为无感弹性伸缩奠定了决定性的结构前提。

保持私有IP不变的热迁移（Live Migration）机制

在单台Kubernetes宿主机物理节点内部，只要物理内存尚有富余，动态追加vCPU与RAM的操作即可在宿主机内部原地瞬时完成。然而在集群高负载情况下，某台宿主机的物理资源可能已被完全占满，无法满足某数据库实例进一步扩展的诉求。Lakebase架构利用基于QEMU/KVM的热迁移技术攻克了这一单机天花板。

当宿主机节点出现物理资源瓶颈时，NeonVM控制器可在毫秒级别将整台运行中的数据库虚机热迁移至另一台负载宽松的宿主机。在迁移过程中，虚拟机内部绑定的私有虚拟IP与网络接口始终保持不变，客户端应用所持有的上千个TCP长连接连接池完全察觉不到底层物理服务器的变换。加之计算节点无需迁移庞大的持久化数据盘，仅需传输内存脏页与CPU运行时上下文，使得整个跨节点热迁移过程在极短的时间内即可收敛完成。

决定目标容量的三大指标：CPU、内存与工作集大小

即便具备了底层的热插拔调整能力，如何精准裁定伸缩时机与调整幅度依然是决定系统成败的关键。过于激进的触发策略会导致虚机规格剧烈振荡（Chapping），而迟缓的反应又会使系统在突发流量前反应迟退导致性能骤降。Lakebase Postgres通过同时采集三路相互独立的信号来综合计算目标容量：

  • CPU负载目标：监测算力饱和度的 cpuGoalCU。
  • 内存使用目标：防范系统崩溃与保障缓冲余量的 memGoalCU。
  • 工作集大小目标：保障本地数据块缓存命中率的 lfcGoalCU。

控制算法分别计算这三个信号所期望的计算单元（CU），并取其中的最大值作为最终期望规格，最后将其限定在用户为该数据库预设的最小和最大容量限制（Autoscaling Limits）区间内：

goalCU = max(cpuGoalCU, memGoalCU, lfcGoalCU)

基于1分钟平均负载的CPU调节 (cpuGoalCU)

CPU控制机制重点跟踪虚拟机的1分钟CPU平均负载（Load Average）。运行在宿主机上的 autoscaler-agent 每隔5秒采集一次该指标，其调节目标是使1分钟负载水平稳定在可用CPU算力的90%以内。采用1分钟移动平均值能够平滑数十毫秒级的偶发尖峰噪点，而5秒的高频轮询则保证了对真实的持续算力需求攀升能够做出灵敏反应。当计算负载持续增加时，cpuGoalCU 会被立即抬高；而在压力缓解后则会稳步平滑下调。

100毫秒超高频检测与防OOM内存防线 (memGoalCU)

与CPU相比，内存具有完全不同的严重失效模式。CPU算力不足顶多表现为查询耗时上升，而内存耗尽则会直接诱发Linux内核的OOM Killer机制，强行通过SIGKILL终止PostgreSQL的关键工作进程，导致数据库瞬间崩溃并转入崩溃恢复流程。因此，内存防线必须拥有比CPU敏锐得多的检测速度。

系统设计了双重监控频率：宿主机层面的 autoscaler-agent 每5秒读取一次整机物理内存概况，而虚机内部驻留的 vm-monitor 则以每100毫秒（0.1秒）的超高频直接观察PostgreSQL的实际内存分配。内存控制目标是将使用率控制在分配RAM的75%以下。剩余的25%作为关键安全缓冲，既能吸收大查询的突发分配，也为虚拟机内核与其他系统守护进程预留运作空间。

早期工程团队曾尝试依托Linux cgroup的 memory.high 事件驱动调整，但一旦触碰该阈值，Linux内核便会立即介入强制回收内存并对cgroup内进程实施节流限速，从而引发查询响应时间的不可控抖动。为此系统全面切换为100毫秒轮询机制，实现了极为平稳可控的内存监测。

消除网络等待盲区的缓存控制 (lfcGoalCU)

传统的扩缩容控制器最容易折戟的场景正是数据库的缓冲缓存。在OLTP系统中，决定查询吞吐的核心在于经常访问的热点索引与表页能否全部驻留在本地高速缓存中。一旦本地缓存容量不足诱发大量Cache Miss，查询线程就会被迫陷入等待远程Pageserver通过网络传输数据页的阻塞状态。

在网络I/O等待期间，CPU核心处于闲置状态，其使用率往往只有极低的10%至20%。纯粹依据CPU指标判定的传统扩缩容系统会严重误判为低负载，进而做出错误的缩容决策，使已经遭受缓存不足折磨的系统雪上加霜。为了攻克这一盲区，Lakebase Postgres将过去被称为Local File Cache（LFC）的高性能本地计算缓存纳入核心监控，设立了独立估算实际活跃工作集的 lfcGoalCU 信号。

融合时间维度的HyperLogLog实时缓存需求预测

所谓数据库的工作集（Working Set），是指在特定时间段内被频繁反复读取与写入的数据页及索引页的集合。为了确保最优响应效率，该工作集应全部纳入本地计算缓存之中。然而，如果在内存中对每一个访问过的数据块ID进行精确的哈希集合计数，本身就会造成严重的内存膨胀与计算开销。

标准HyperLogLog的固有局限与单调累加缺陷

利用极小的内存状态估算超大规模基数时，经典的基数算法是HyperLogLog（HLL）。标准HLL通过对数据块哈希后利用部分比特位分桶，并记录其余比特的最大连续前导零数量，仅需数KB的固定内存即可在可控误差范围内统计数以亿计的独立数据块访问量。

但标准HLL应用在动态扩缩容场景时存在一个致命死穴：其寄存器数值是纯粹单调递增的。它只能记录某个桶曾观察到多大的特征值，却完全无法记录该特征值产生的具体时间。一旦清晨执行了一次全表备份或离线大查询，这些在数小时内不会再被访问的数据块就会永久留在统计桶中，使系统在后续的整个白天都误以为系统依然需要巨大的缓存，进而长期维持过度配置状态。

用时间戳替换静态比特位的滑动窗口基数估计

Lakebase工程团队巧妙改造了HyperLogLog的内部结构：在哈希观察命中某个特征槽位时，不再仅仅置位标志位，而是将**当前的观察时间戳**直接存入寄存器对应位置。

当系统需要推算历史某时间点T至今的唯一访问块数时，算法只需将时间戳晚于T的寄存器视为有效槽位，将早于T的历史记录按空槽位过滤，随后套用HLL标准算法进行基数推导。通过这种改造，单个精巧的数据结构即可同时导出当前任意滑动时间窗口下的动态活跃工作集：

  • 过去1分钟内所访问的唯一数据块估计值。
  • 过去5分钟内所访问的唯一数据块估计值。
  • 过去60分钟内（1小时）持续访问的唯一数据块估计值。

每隔20秒，宿主机上的 autoscaler-agent 便会读取这组时间感知型HLL寄存器，完整构建出从1分钟到60分钟的多跨度工作集扩展曲线。

时间窗口突增检测与微周期先行缓存分配

即便掌握了动态时间窗口的推断能力，如何选取一个合理的时间窗口作为判断依据仍需在灵敏与稳定之间权衡。若窗口定得太短（如1到2分钟），在大查询结束后能迅速下调规格，但也会在短暂停顿时过早丢弃缓存导致后续请求命中率暴跌；若窗口定得太长（如60分钟），虽然缓存得以保全，却会让已经退场的负载长期占据昂贵的内存。

5分钟后的突增点（Jump）检测算法

Lakebase Postgres采用了一套突增检测算法，通过观察窗口逐步扩大时基数估计值的增长斜率来化解矛盾。在常规的稳定业务中，由于频繁访问的是相同的热点数据，将时间窗口从5分钟逐步扩大到30分钟时，新观测到的唯一数据页数量增长有限，其曲线会迅速呈现平坦的高原状（Plateau）。

而如果前不久刚刚结束了一项重型批处理任务，曲线就会展现出独特的跳变特征：短窗口内仅能看到当前轻量级常规查询的平缓小工作集，但当时间窗口向后延伸触及早先重型任务发生的时刻时，基数估计曲线会产生急剧的垂直攀升。算法正是通过捕捉这一跳变点，选定跳变前平缓阶段的估计值作为当前真正需要维持的工作集大小。

start after the initial downscale delay

for each working-set window:
    measure growth before this point
    measure growth after this point

    if later growth is much larger than earlier growth:
        return the estimate before the jump

return the estimate from the 60-minute window

这一判定逻辑被严格限制在5分钟之后的时间跨度开始执行。这能够防止在短暂业务微歇时盲目缩容引发随后的反复冲顶抖动。如果整个60分钟跨度内均未检测出明显的急剧跳变，则说明系统的热点数据在整整一小时内都在持续稳定运行，此时直接采用60分钟窗口的安全估计值。

20秒评估周期与不足1分钟的短程先行投影

仅对已经发生的数据访问进行事后统计在突发扫描新表时依然存在滞后性。如果等新数据块全部读完才扩容缓存，前期载入的页面早已因容量挤占而被逐出，迫使后续查询再次跨网络重新向Pageserver请求。

为了做到未雨绸缪，算法通过计算各窗口区间的增长导数，向未来短周期推算**下一个控制周期预期增加的工作集量**（Projection）。鉴于 autoscaler-agent 每20秒评估一次，这一预测仅向前推算不足1分钟的极微短周期。避免长期预测能防止突发的瞬时噪点被过度放大成虚高的算力暴增。最终推导出的预估规模即为 lfcGoalCU，系统最多可调拨虚机内存的75%用于动态承载本地缓存。

协调运行中虚拟机动作的四大组件与三层控制循环

在目标容量 goalCU 计算完毕后，系统必须将其安全无缝地应用到底层运行中的数据库环境中。由于常规Linux容器在运行状态下动态重定物理内存上限方面受到诸多约束且隔离性相对偏弱，Lakebase Postgres选择将每个数据库实例部署于Kubernetes集群内专用的轻量级微虚拟机（MicroVM）中，从而兼顾强内核隔离与硬件级实时热插拔特性。

autoscaler-agent、vm-monitor、定制调度器与NeonVM的分工

为了在线完成无感调整，四大分布式基础设施模块在不同层级上协同作业：

  • autoscaler-agent：以守护进程形式部署在各个Kubernetes计算节点上，采集本节点上所有Postgres虚拟机的遥测指标，算出goalCU并驱动扩缩容工作流。
  • vm-monitor：常驻于每个虚拟机内部的客户机操作系统中，以100毫秒的极高频度紧盯PostgreSQL进程内存，把关缩容安全性并动态分配本地缓存。
  • 定制Kubernetes调度器：维护集群底层物理资源的统一全局视图，严格审批所有向上扩容内存的请求，避免物理超配。
  • NeonVM控制器：基于QEMU/KVM深度定制的Kubernetes自定义资源控制器，负责在线向虚拟机执行vCPU与内存的物理热插拔并管理热迁移。

一个标准的向上扩容（Scale-up）按照严密的五步流程推演：

  1. autoscaler-agent通过综合CPU、内存和工作集三大指标确定需要扩充的全新goalCU。
  2. 向定制Kubernetes调度器提交申请，核查宿主机物理剩余内存是否足以覆盖此次扩容。
  3. 获得调度器正式批准后，autoscaler-agent将新的配额规格写入NeonVM自定义资源。
  4. NeonVM控制器调用底层QEMU管理套件，直接向运行中的虚拟机热插拔对应的vCPU核心与内存块。
  5. 虚机内部的vm-monitor感知到RAM容量提升，动态扩展本地文件缓存池，迅速为查询提供加速。

必须将定制调度器设立为全局分配的唯一仲裁者，这是为了防止与Kubernetes标准容器调度产生冲突。如果缺乏这层全局统筹，标准调度器可能会在宿主机空余空间上排入新的外部应用Pod，而此时自动扩缩容代理恰好将同一块物理内存追加给了Postgres虚机，从而导致宿主机发生毁灭性的物理内存超卖（Overcommit）。

向下缩容（Scale-down）同样依托上述链条，但在虚机内部加入了更严苛的逆向安全审计。因为扩容失败最多只会导致系统性能稍慢，而激进的过度缩容则会直接诱发OOM宕机。一旦接收到缩容意向，虚机内部的 vm-monitor 会立即对当前正在处理的复杂查询及操作系统所需开销进行深度验算，只要评估认为可能危及内存安全边界，缩容操作就会被立即驳回。

100毫秒、5秒、20秒构建的多级控制回路

整体控制体系由三套交织演进的不同时间步长回路共同组成：

  • 100毫秒回路（极致防御）：由vm-monitor紧盯PostgreSQL内部内存分配，防御极端突增并阻断不安全的盲目缩容。
  • 5秒回路（中短期趋势）：由autoscaler-agent综合评估1分钟CPU负载与系统分配，敏锐捕获业务算力波动。
  • 20秒回路（长效缓存治理）：由autoscaler-agent深度分析HyperLogLog多时间窗口并在短周期内做出先行缓存调配。

在面对激增时反应迅捷，在负载回落后毫不迟延地归还富余容量，这种双向对称的治理思路构成了现代化自动扩缩容最本质的核心价值。

对工程实践的启示：摆脱过度配置与提升成本效能

纵观诸多电商、互联网科技以及企业SaaS的真实基础架构现状，受限于业务的剧烈波动，数据库的严重超额配置已然成为一笔庞大的日常隐形浪费。大促活动、突发热点推送或定时跑批任务仅持续数十分钟，但为了避免这一偶发峰值击垮服务，不少企业长年累月维系着高出基线流量数倍的昂贵高配数据库。

在AI算力大潮推高全球数据中心资源单价的2026年，为了数天罕至的业务峰值而支付整整365天的最高规格账单，已不再是一种具备可持续性的工程策略。Lakebase Postgres给现代数据库架构改造带来了极为明确的路径指引：

  • 重新审视分布式分片的引入门槛：在被迫接受水平分片所带来的分布式事务开销、跨分片Join限制与复杂改造成本之前，应优先评估无断连高性能垂直扩缩容是否足以吸收业务峰值。
  • 建立基于缓存状态的精细化可观测体系：跳出单一盯防CPU使用率的狭隘告警视角，构建能够精准分离网络I/O等待与真实空闲状态的工作集命中率监控看板。
  • 以对称扩缩容策略收回闲置资本：不仅要确保扩容的敏锐度，更要通过严格可信的在线安全校验推进高频缩容，在业务平息后即刻回退至低配底座以压缩云账单。

目前，Lakebase Postgres既作为Neon云原生平台的核心底座服务于广大开发者与初创企业，同时也已被深度整合进入Databricks的Data Intelligence Platform体系，直接与Unity Catalog数据治理平台及Lakehouse智能分析流协同，实现了算力效能的显著提升。
