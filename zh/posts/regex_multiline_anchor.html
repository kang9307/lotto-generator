引言 - 多行标志并不是让正则支持多行的开关

正则引擎会把包含多行的字符串当作一个字符串。默认情况下 ^ 对应字符串的开头，$ 对应字符串的结尾(Python、.NET、Perl中也包括末尾换行之前)；打开多行标志(Python re.M、JavaScript m、.NET Multiline、Perl /m)后，它们在行边界处也会匹配。因此与名称不同，按Python文档，标志改变的并不是「处理多行的能力」，而只是这两个锚点是否承认行边界。点号(.)能否跨越换行，由另一个开关(s)决定(第8节)。

实际中容易出问题的地方有两处。一处是输入末尾带一个换行时 $ 对应哪里，另一处是换行为 \r\n(CRLF)而不是 \n 时，$ 不会对应在 \r 之前。两处的答案都因工具而异。语言和工具之间正则方言的整体差异见可移植正则表达式的文章，CR字节在Shell脚本和git中引起的问题见CRLF与LF的文章；这里只用同一份输入比较锚点对行边界的解释和CRLF输入的结果。

涉及的问题如下。

  • 默认情况下 ^ 和 $ 对应哪里，多行标志会怎样改变它。
  • 在输入末尾换行的前后，$ 和 ^ 的结果在各工具中相同吗。
  • 哪些工具有 \A、\z、\Z，它们会受多行标志影响吗。
  • 在grep、sed、awk中，锚点已经是按行的吗。
  • 在CRLF输入中 $ 对应哪里，又该如何应对。

两份相同的输入 - LF与CRLF，以及直观查看位置的方法

所有演示都使用同样的两份输入。LF输入是 a1\nb2\n(两行，末尾有一个换行)，CRLF输入是 a1\r\nb2\r\n。查看锚点匹配位置的方法在各处一致：在 ^ 匹配的位置插入 <，在 $ 匹配的位置插入 >，再以转义形式输出该字符串。例如 'a1\nb2>\n>' 表示 $ 在两处匹配：b2 之后和字符串的最末端。下面输出的读法有三点。

  • $ 的 > 是否也出现在最后一个 \n 之前(末尾换行之前的匹配)。
  • ^ 的 < 是否也出现在最后一个 \n 之后的空位置(末尾换行之后的匹配)。
  • 在CRLF中，> 是出现在 \r 之前，还是出现在 \r 与 \n 之间。

Python re - 默认的 $ 在两处匹配

Python 3.13文档对 re.M 的描述是：「When specified, the pattern character '^' matches at the beginning of the string and at the beginning of each line (immediately following each newline); and the pattern character '$' matches at the end of the string and at the end of each line (immediately preceding each newline). By default, '^' matches only at the beginning of the string, and '$' only at the end of the string and immediately before the newline (if any) at the end of the string.」(出处：docs.python.org/3.13/library/re.html)输出与这段话的形状一致。

  • LF默认：$ 得到 'a1\nb2>\n>'，在 b2 之后(末尾换行之前)和最末端匹配。^ 只在最开头一处匹配。
  • LF加 re.MULTILINE：^ 得到 '<a1\n<b2\n<'，共三处，包括最后一个 \n 之后的空位置。$ 得到 'a1>\nb2>\n>'，每行一处再加最末端。
  • CRLF：$ 得到 'a1\r>\nb2\r>\n>'，匹配在 \r 与 \n 之间。\r 被当作行内的字符。
  • 因此在CRLF中，^\w\d$(re.M)得到 []，即0条。^\w\d\r?$ 能匹配两行，但值包含 \r，如 'a1\r'。splitlines() 得到 ['a1', 'b2']，把 \r\n 当作一个行边界。
  • \A 与 \Z：\A 只在最开头一处匹配，\Z 得到 'a1\nb2\n>'，只在最末端一处匹配，加不加 re.M 结果相同。在3.13中，\Z 不会在末尾换行之前匹配。
  • \z 在3.13中是 re.error: bad escape \z。3.14之后版本的文档把 \z 写作「Added in version 3.14」，把 \Z 写作「The same as \z. For compatibility with old Python versions.」(docs.python.org/3/library/re.html 中3.14及之后版本的写法)。

MDN关于输入边界断言的文档写道：「If the m flag is set, ^ also matches if the character to the left is a line terminator character, and $ also matches if the character to the right is a line terminator.」(出处：developer.mozilla.org的Input boundary assertion页面)同一页面的注释还写道：「To match the start and end of the entire string in m mode, use the buffer boundary assertions \A, \z, and \Z.」输出如下。

  • LF默认：$ 得到 "a1\nb2\n>"，只有最末端一处。与Python不同，它没有在末尾换行之前匹配。
  • LF加 m 标志：与Python形状相同。^ 也会匹配最后一个换行之后的空位置("<a1\n<b2\n<")。
  • CRLF加 m 标志：^ 得到 "<a1\r<\n<b2\r<\n<"，在 \r 与 \n 之间也匹配；$ 得到 "a1>\r>\nb2>\r>\n>"，在 \r 之前和 \n 之前都匹配。\r 被当作行终止符。
  • 结果是，即使在CRLF中，/^\w\d$/gm 也以 ["a1","b2"] 匹配了两行。相反，/^.*$/gm 得到 ["a1","","b2","",""]，中间混入了空字符串。点号没有越过行终止符 \r，\r 与 \n 之间的位置则单独匹配出一个空行。
  • m 标志的行终止符不只是 \n。在 \u2028 和 \r 之后 ^ 会匹配("<a<LS><b"、"<a\r<b")，在垂直制表符之后则不匹配("<a<VT>b")。
  • \A：在这个Node中，不带 u 标志时它被当作字符 A，匹配了 'Aa1\n'(false true 输出的第二个值)，带 u 标志时则是 SyntaxError: Invalid regular expression: /\Aa1/u: Invalid escape。与MDN的注释不同，在这个Node v22.16.0中，\A 没有作为缓冲区边界断言工作。

Microsoft Learn关于锚点的文档直接写明了 $ 在CRLF下的情况：「Note that $ is satisfied at \n but not at \r\n (the combination of carriage return and newline characters, or CR/LF). To handle the CR/LF character combination, include \r?$ in the regular expression pattern. Note that \r?$ will include any \r in the match.」它还把 \Z 定义为「The match must occur at the end of the string, or before \n at the end of the string」，把 \z 定义为「The match must occur at the end of the string only」，并说 \Z 「identical to the $ anchor, except that \Z ignores the RegexOptions.Multiline option」。(出处：learn.microsoft.com的Anchors in regular expressions页面)

  • 默认情况与Python相同。$ 在末尾换行之前和最末端两处匹配(a1\nb2>\n>)，在 Multiline 下 ^ 连最后一个换行之后的空位置共三处。
  • \Z 与 $ 在相同位置(a1\nb2>\n>)匹配，加 Multiline 结果也相同。\z 只在最末端一处匹配。输出与文档的定义一致。
  • CRLF：$ 如 a1\r>\nb2\r>\n> 那样匹配在 \r 之后。^\w\d$(Multiline)得到0条，^\w\d\r?$ 得到2条，值为 a1\r,b2\r，包含 \r。与文档中的「\r?$ will include any \r in the match」一致。
  • 内联 (?m) 在PowerShell的 -replace、-match 运算符中也产生了相同效果(-match '(?m)^b2$' 在LF上为True，在CRLF上为False)。
  • 文档写道，从.NET 11起可以用 RegexOptions.AnyNewLine 让 $ 把 \r\n 识别为一个单位。在这台电脑的5.1中，RegexOptions 枚举名称列表里没有该项(输出的最后一行)。

                    LF   \A -> <a1\nb2\n   \z -> a1\nb2\n>   \Z -> a1\nb2>\n>   \Z with /m -> a1\nb2>\n>
                    CRLF \A -> <a1\r\nb2\r\n   \z -> a1\r\nb2\r\n>   \Z -> a1\r\nb2\r>\n>   \Z with /m -> a1\r\nb2\r>\n>
                    --- whole-line match
                    LF   ^(\w\d)$ /m -> [a1,b2]   ^(\w\d)\r?$ /m -> [a1,b2]
                    CRLF ^(\w\d)$ /m -> []   ^(\w\d)\r?$ /m -> [a1,b2]
                    --- /s is a different switch
                    /    (no match)
                    /s   a1\nb2\n
                    /m   a1
                    /ms  a1\nb2\n

perlre把 /m 描述为「change "^" and "$" from matching the start of the string's first line and the end of its last line to matching the start and end of each line within the string」，把 \Z 描述为「Match only at end of string, or before newline at the end」，把 \z 描述为「Match only at end of string」。(出处：perldoc.perl.org/perlre)

  • 默认情况以及 $、\Z、\z 与Python、.NET在相同位置匹配(a1\nb2>\n>，\z 在最末端)。
  • 不同之处在于 /m 下的 ^。在LF上得到 <a1\n<b2\n，仅两处，没有在Python、JavaScript、.NET匹配的最后换行之后的空位置匹配。
  • CRLF的情况与Python相同。^(\w\d)$ 得到空列表，^(\w\d)\r?$ 得到 [a1,b2](值是捕获组，因此不含 \r)。

  • grep -c '^b2$' 对LF文件和CRLF文件都是1。但用 grep -U(二进制模式)读取时，CRLF上是0，模式中带CR的 ^b2\r$ 仅在CRLF上是1。这台电脑上Git Bash的grep在默认模式下是去掉行尾CR之后再匹配的。
  • sed 在默认模式下输出的字节中没有CR(<a1>\n)，而 sed -b 的结果是 <a1\r>\n，> 位于CR之后。也就是说在保留CR的状态下，$ 匹配在 \r 之后、\n 之前。
  • awk 也一样。默认模式去掉了CR，使用 -v BINMODE=3 时CR被保留。
  • sed 'N;s/^/</g' 只在合并后的两行(a1\nb2)的最开头加了 <，加上 M 修饰符后得到 <a1\n<b2\n，第二行之前也加上了。让 ^ 在合并块内承认行边界的开关就是 M。
  • 把记录分隔符改为 \001，让awk把整个文件作为一条记录读取后，^ 和 $ 各在记录的最开头和最末端匹配一次(<a1\nb2\n>)。

点号(.)与s标志 - 与锚点不同的开关

四种语言的输出末尾包含同样的实验：对LF输入(a1\nb2\n)应用模式 ^a1.*$，只改变开关的组合。结果在每个工具中都相同。

开关结果含义
无无匹配(Python []，JavaScript null，Perl (no match)).* 在第一行末尾停止，而 $ 只在最末端(或末尾换行之前)匹配，因此无法衔接
s(点号包含换行)整个 a1\nb2\n.* 越过换行一直走到最末端的 $
m(锚点承认行边界)仅 a1$ 在第一行末尾匹配，但点号仍然无法越过换行
m和s同时开启整个 a1\nb2\n点号越过换行，$ 既承认行尾也承认最末端，所以匹配延伸到最长的一侧
  • 只开 m 时，.* 在第一行结束；只开 s 时，它走到字符串的最末端而不是行边界。两个开关是独立的。
  • PowerShell中的 Singleline、Python中的 re.S 起相同作用，输出结果也相同。
  • 因此，目的是「逐行匹配」时用 m，目的是「跨多行的一次匹配」时用 s，两者都需要时就同时开启。

CRLF下 $ 落空时 - 应对分输入、模式、开关三条路

工具应对方式输出中确认的结果
Python在模式中加入 \r?$，或先用 splitlines() 分行\r?$ 能匹配两行但值含 \r，splitlines() 得到 ['a1', 'b2']
JavaScriptm 标志把 \r 当作行尾，所以直接使用 $；使用点号的模式要过滤空匹配/^\w\d$/gm 得到 ["a1","b2"]，/^.*$/gm 混入空字符串
.NET(PowerShell)文档给出的 \r?$从0条变为2条，值含 \r
Perl\r?$从空列表变为 [a1,b2](值是捕获组，所以不含 \r)

  • 对输入做规范化(像Python的 splitlines() 那样先分行)，模式就不需要知道行尾字符，因此同一个模式在LF和CRLF上都能原样使用。
