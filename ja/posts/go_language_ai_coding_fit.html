AI生成コードの検証コストを下げる言語特性

Goが有利になる5つの特性、そして代償として何を差し出すのか

2026年8月16日 開発・インフラ

序論: レビュー待ち行列が伸びる場所

エージェントにチケットを一つ渡して会議から戻ると、800行の変更が待っている。ビルドは通り、テストも緑だ。それでもマージボタンを押す前に確認すべきものが残っていて、その確認に掛かる時間は去年とまったく同じだ。チームで実際に詰まるのはここだ。

書くコストと確かめるコストが同じ速さで落ちなかったこと、この非対称性ひとつが今の言語論争の背景にある。2026年8月11日、GoチームのCameron BalahanとGoogle CloudのRichard SeroterがGoogle開発者ブログにGoはAI支援ソフトウェアエンジニアリングに理想的な言語であるという記事を公開し、翌日には各国のコミュニティに伝わって、おなじみの言語優劣論争がまた一巡した。

だがその記事で本当に価値があるのは結論ではない。言語のどの特性が検証コストを下げるのかという問いのほうだ。これはGoに限った話ではなく、Goを使わないチームでも今日から使える基準になる。この記事ではその特性を五つに絞って整理し、Goがそれをどう手に入れたのか、代わりに何を請求書として受け取るのか、そして正反対の戦略を採った言語が同じ問題にどう答えているのかまで見る。

先に釘を刺しておく。この記事はどの言語が優れているとは言わない。特性には必ず対価が付いていて、どの対価なら耐えられるかはそのチームの制約が決める。

1. 検証コストは何でできているか

800行を前にしたレビュアーがやっていることは一つではない。五つに分かれる。

  • 形の把握 — インデント・改行・括弧の配置に目が慣れるまでの時間
  • イディオムの照合 — 同じ処理に複数のやり方がある場合、ここで使われた方式が自分たちのコードベースの方式と合うかの確認
  • APIの実在確認 — 呼ばれている関数やパッケージが本当にあるか、シグネチャは合っているか、そのバージョンに存在するか
  • 意味の検証 — 要件と合っているか、境界条件が抜けていないか
  • 副作用の追跡 — この変更が他の経路に何を残すか

ここで分かれる。前の三つは言語とツールに肩代わりさせられるが、後の二つはどの言語を使っても人の担当として残る。だから言語特性が介入できる場所は正確に前の三つであり、そこを機械に押し出した分だけ人の注意が後の二つに残る。レビュー時間が短くなること自体が目的ではなく、残った注意がどこへ向かうかが目的だ。

Google記事で引く価値があるのもここだ。AIに繰り返し直させるとき、最初の一回が95%正しくても反復するほど誤り率が累積するという記述があるが、これは要するに一周をどれだけ速く回し、どれだけ確実に濾せるかが結果を決めるという意味になる。回転速度と濾過網の性能が言語の問題になる地点がここで生まれる。

2. 検証コストを下げる5つの特性

言語が前記の前三項目を削る方法は五つに整理できる。Goを外して読んでも成り立つように書いておく。

特性削る検証項目機械で確認する方法代償
構文の表面積が小さい形の把握レビュアーが覚えるべき構文規則の数表現力の制約 — ドメインを構文で狭められない
イディオムが一つに収束するイディオムの照合同じ作業の標準解が文書に一つあるか巧い解法も拒否される — 本文が長くなる
フォーマッタが強制される形の把握差分に書式だけ変わった行が0かチームの好みを反映できない
標準ライブラリが広いAPIの実在確認新規依存の追加件数標準が古びると言語ごと古びる
コンパイルが速い三項目すべての回転数変更から最初のエラーまでの時間最適化と検査強度を一部あきらめる

五つのうち前の三つは読む量を減らす特性で、後の二つは機械が代わりに読む速度を上げる特性だ。性格が違うので、一つの言語が五つ全部を備える必要はない。

この中で最も過小評価されているのが三番目だ。フォーマッタの強制は美学の問題として扱われがちだが、生成物が増えてから性格が変わった。モデルは同じコードを毎回違う書式で出す。書式が自由な言語ではその差がそのまま差分に残り、意味の変わっていない行までレビュアーの目を通る。書式が強制されればその行はそもそも発生しない。静的型付けがなぜ2010年代半ばから再び支持を集めたのかと同系統の話で、その経緯は静的型付けの台頭のほうに整理してある。

3. Goがこの特性を持つ仕組み

Goは五つの特性を言語設計というより配布されるツール一式で確保した側に近い。ここが他の言語と分かれる点だ。

  • gofmt — 書式が言語の配布に含まれる。スタイル論争が組織ごとに再発せず、差分に書式だけ変わった行が残らない。
  • go vet — コンパイルは通るが疑わしい構成を標準ツールが捕まえる。書式文字列の不一致やロックのコピーといった類だ。
  • govulncheck — 依存関係の既知の脆弱性を標準ツールで点検する。生成物が増えるほど価値が上がる検査だ。
  • go fixとモダナイザ — 古いイディオムを機械が現行へ移す。モデルが古いコードを学習して古い書き方を出しても戻す経路がある。
  • 組み込みファジング — Go 1.18からgo testに入った。別途インストールなしでランダム入力試験が付く。
  • pprof・実行トレース・PGO — 性能劣化を人の感覚ではなくプロファイルで捕まえる。

まとめると、このパイプラインが標準配布だけで成立する。

# 書式差を差分から消す
gofmt -l ./...

# コンパイルは通るが疑わしい構成を捕まえる
go vet ./...

# 依存関係の既知の脆弱性を見る
govulncheck ./...

# テストと競合検出を同時に回す
go test -race ./...

四行すべてが別途インストールなしで動く点が肝だ。ツールを選びバージョンを合わせ設定ファイルを合意する過程がなければ、新しいリポジトリでも初日から同じ濾過網が掛かる。エージェントが自分で直しながら反復するとき、この濾過網は人が介在しなくても働く。

標準ライブラリの広さとサプライチェーン

Google記事が指摘したもののうち、実務に最も速く効くのがこちらだ。モデルは学習時点のパッケージ名をそのまま出すので、もはや保守されていないパッケージや、そもそも存在しないパッケージを自信たっぷりに呼ぶ。標準ライブラリが広ければその呼び出しがそもそも減る。HTTPサーバ、JSON、暗号、テンプレートが標準にあればモデルが外部を探しに行く理由が減り、新たに入る依存の件数が減れば監査すべき表面も減る。

Go 1互換の約束が実際にカバーする範囲

長く維持されるコードで価値を出す特性だ。Goの互換性文書はGo 1仕様に沿って書かれたプログラムは、その仕様の存続期間を通じて変更なしにコンパイルされ正しく動作することを意図すると書いている。ただし範囲は正確に押さえておく必要がある。

  • 保証はソースレベルのみだ。コンパイル済みパッケージのバイナリ互換はリリース間で保証されない。
  • セキュリティ上の問題、仕様が定義していない挙動に依存したコード、仕様自体の誤りの修正、バグ修正はすべて例外として明記されている。
  • キーを省いた構造体リテラル、埋め込み型に後からメソッドが追加される場合、ドットインポート、unsafeの使用も例外一覧にある。

つまり絶対に壊れないではなく、壊れうる場合をあらかじめ文書に書いておき、その外側では守るという形だ。生成コードが積み上がる状況でこの違いは大きい。例外一覧に引っかからないように書くこと自体がコーディング規約になる。

コンパイル速度の主張はどこまでが事実か

Google記事はGoのコンパイルがJava・C#・Rustなどに比べて桁違いに速いという趣旨を述べる。方向自体はGoを使ったことのある人の体感と違わないが、その記事にはハードウェア・コード規模・ツールチェーンのバージョンといった条件が付いていない。条件のない比較は順位表として使えない。この種の数値は自分のリポジトリで直接測る以外に代替がなく、測った値もキャッシュ状態とモジュール数で大きく揺れる。

4. 代償 — 短い構文の請求書は本文の長さで来る

特性には値段が付く。Goが差し出すものは大きく四つだ。

エラー処理の冗長さ

Goでエラーを扱う方法は一つに収束していて、だから呼び出しごとに同じ形が付く。

f, err := os.Open(path)
if err != nil {
    return nil, fmt.Errorf("open %s: %w", path, err)
}
defer f.Close()

data, err := io.ReadAll(f)
if err != nil {
    return nil, fmt.Errorf("read %s: %w", path, err)
}

生成側ではこれが負担にならない。繰り返しのブロックはモデルが最も安定して出す形で、タイピングのコストも人が払わない。負担は読む側で生まれる。差分のかなりの部分が同じ形になると、そのうち一箇所だけエラーをそのまま飲み込んで進むコードは目に付きにくい。繰り返しがノイズになると、本当の信号がノイズに埋もれる。

この代償はすぐ消える種類のものではない。2019年のtry提案が却下された後も複数の案が出たが、2025年6月、Goチームはエラー処理の構文変更を当面追求しないと表明し、その構文を主題とする提案を一括で終了させた。同じ記事で、調査上エラー処理がGo利用における最大の具体的な課題として挙がる点も併せて認めている。つまり分かったうえで維持する設計だ。

表現力の制約

Goには直和型も網羅的なパターンマッチもない。結果として分岐が抜けた状態機械をコンパイラが拒否してくれない。状態を文字列や整数定数で表しswitchにdefaultを置く形になるが、新しい状態を追加してもコンパイルは通る。その検証がテストと人に降りてくる。

ジェネリクス以前の痕跡

型パラメータはGo 1.18で入った。それ以前、コンテナ系のユーティリティは型ごとに複製するかinterface{}で受けてアサーションする方式が標準で、その時代のコードが公開リポジトリに大量に残っている。モデルが古いイディオムを出すことがあるのはこのためだ。ただしその頻度がどれほどかを示す公開された測定値はない。対応は頻度を推定する方向ではなく、モダナイザと静的解析をCIに掛ける方向になる。

並行性 — 構文が易しいことと安全なことは別だ

最も注意すべき箇所だ。go一語でゴルーチンが起動しチャネル構文が簡潔だということは、生成器が並行コードを気軽にばら撒くという意味でもある。ところがデータ競合はコンパイラが捕まえない。-raceは捕まえるが、その経路が実際に実行されたときだけだ。この記事をめぐるコミュニティの議論でもAIが生成したGoコードの並行性の欠陥を懸念する指摘が出たが、これは上で整理した五つの特性がカバーしない領域だという点で重要だ。書式が統一されイディオムが一つでも、競合は形には現れない。

5. 反対側の答え — 検証を型に押し込む戦略

同じボトルネックに正反対から答える言語がある。Goが読む量を減らす側なら、こちらは読まなくて済むようにコンパイラに拒否させる側だ。どちらが優れているのではなく、請求書を受け取る主体が違う。

  • Rust — 所有権と借用検査でメモリエラーとデータ競合の大きな分類をコンパイル段階で拒否する。直和型とmatchの網羅性検査があるので、状態を追加すると未処理の箇所がコンパイルエラーとして現れる。人が読まないコードが増える状況でこれはそのまま価値になる。代償はビルド時間、学習曲線、unsafe境界の管理だ。GoとRustの移行判断はGoからRustへの移行ガイドで軸を分けてある。
  • TypeScript — 判別可能なユニオンで状態を閉じられ、strictやnoUncheckedIndexedAccessといった設定で検査強度を調整できる。代償は二つ。型定義の品質がパッケージごとに違うことと、anyという抜け道が常に開いていて生成物が静かに検査をすり抜けうることだ。
  • Python — 型ヒントは実行に影響しない。したがって別の型検査器をCIに掛けなければ、検証はすべてテストと実行時に降りる。代わりにデータ・機械学習のエコシステムの広さが圧倒的で、他の特性では埋められない場所がある。

欠陥の種類ごとに誰が捕まえるかを並べると、選択の性格がはっきりする。

欠陥の種類GoRustTypeScriptPython
存在しないAPI・シグネチャ不一致コンパイラコンパイラ型検査器実行時か別途検査器
不在値へのアクセス実行時(nilパニック)コンパイラ(Option)設定時に型検査器実行時
状態分岐の漏れテストと人コンパイラ(matchの網羅性)判別可能ユニオン利用時に型検査器テストと人

表を縦に読むとGoは書式とサプライチェーンで強く、型で捕まえる欠陥の範囲が狭いという形が出る。Rustは逆だ。自分たちの障害履歴がどの行に偏っているかを先に見れば判断がずっと速くなる。障害が起きていない行の特性を良いからと選んでも得はない。

6. AIがうまく書く言語と人が読みやすい言語は同じか

おおむね重なるが全部は重ならない。そして分かれる区間で判断を誤る。

  • 重なる側 — イディオムの収束と書式の強制は双方に得だ。モデルは学習で見た一つのパターンを再現すればよく、人は照合する基準が一つしかない。
  • 分かれる側その一 — 繰り返しだ。人は繰り返しをノイズとして読むが、生成器は繰り返しにコストを払わない。だから同じコードが生成の観点では良く、レビューの観点では悪いことがありうる。
  • 分かれる側その二 — 圧縮された表現だ。関数型パイプライン一行は熟練者には密度の高い情報だが、間違っているときは丸ごと間違っていて部分検証が効かない。
  • 分かれる側その三 — 文書化の慣行だ。人はコメントが少なくても文脈で埋めるが、ツールはシグネチャと型にない情報を作り出す。

だからAIフレンドリーという表現は互いに異なる二つの主張を一つに束ねている。一つはモデルがその言語で正確に生成するかであり、もう一つは人がその結果を速く検証できるかだ。前者は学習データの分布とモデル特性の問題で外部から確認する手段が事実上なく、後者はツールと言語設計で確認できる。確認できる側だけを根拠に使うのが安全だ。言語を最初からエージェント専用に設計しようとする試みとその限界はエージェント専用プログラミング言語のほうで別に扱った。

7. どの主張に根拠があり、どれがまだないのか

この話題で誤読が多いのは、性格の違う主張が一つの段落に混ざって出てくるからだ。層を分けておけば、そのまま使うものと保留するものが分かれる。

主張性格根拠の状態実務では
ボトルネックが記述から検証へ移る算術生成量は増え、人の一日は増えていない前提として使ってよい
強制フォーマッタが書式差分を消すツールの事実自分のリポジトリで即確認できる今日有効にすればよい
標準配布に検証ツールが入っているツールの事実公式文書で確認通過条件に格上げする
Go 1のコードが最新ツールチェーンでビルドされる文書化された方針ソースレベル限定・例外一覧あり例外一覧をコーディング規約に翻訳
Goのコンパイルが他より遥かに速い比較の主張条件(ハードウェア・規模・版)が未明示自分のリポジトリで直接測定
エージェントがGoをうまく書くコミュニティの証言公開された測定・採点基準が未確認判断根拠には使わない
言語別の生成精度の差定量の主張公開数値が未確認存在しないものとして扱う

ベンチマークを引くときの規則もここから出る。モデルのバージョン・ハードウェア・課題の種類・採点基準が併記されていない数値は順位表ではない。特にコーディング課題の点数は課題構成によって順序が入れ替わるので、条件の欠けた引用は方向すら保証しない。

8. 言語選定を実際に決めるもの

現場で言語を決める力は検証コストより手前にある。順序を逆にすると、特性の良い言語を選んでおいて存在しないライブラリを自作する羽目になる。

  • エコシステム — そのドメインの成熟したライブラリがあるか。決済連携、文書パース、機械学習パイプラインはこれ一つで候補が決まる。
  • 採用と引き継ぎ — その言語を保守する人を継続して確保できるか。できなければ検証コストが引き継ぎコストへ席を移すだけだ。
  • ランタイム要件 — GCの停止をどこまで許容するか、メモリ上限があるか、コールドスタートが指標に入るか。
  • 配布形態 — 単一の静的バイナリで終わるか、ランタイムを同梱する必要があるか、イメージサイズと起動時間がコストに乗るか。
  • 規制・調達 — 官公庁や金融では許容言語とツールが契約書に書かれる場合がある。特性論争以前に選択肢が狭まる。
  • 既存資産 — 社内共通ライブラリ・認証モジュール・ログ規格がどの言語にあるか。

実務の順序はこう組むのが安全だ。上の制約が候補を二つか三つに絞る。検証コストの特性はその中で順位を決める。特性が候補を作るのではなく、残った候補を分ける。枯れた技術を先に選べという古い助言がAI時代になぜ強くなるのかは退屈な技術を選べ、再考で扱った。

9. 日本のチームでこの判断が再現する条件

同じ結論がどこで成立しどこで成立しないかを分けるほうが実用的だ。

  • 再現しやすい側 — 社内プラットフォームAPI、ゲートウェイ、バッチパイプライン、運用CLIツール。ドメインライブラリへの依存が低く、配布が単一バイナリで終わり、レビュアーが複数チームに散らばっていて書式とイディオムの統一の利得が大きい場合だ。
  • 再現しにくい側 — データ・機械学習のパイプラインはエコシステムが決める。フロントエンドは型検査器がすでにその席を占めている。金融・SIerの既存資産は要員プールと調達仕様が先に効く。
  • 採用の現実 — 日本のバックエンド採用ではJavaとPHPの人材層が厚く、Goの実務経験者はWeb系やスタートアップに偏る傾向がある。特性が良くても維持する人がいなければその選択は負債になる。
  • 組織構造 — レビュアーが一人二人に集中しているチームほど書式とイディオムの統一の利得は大きい。逆にレビューがすでに自動化されているなら、その利得は回収済みだ。

替えると決めたなら全面移行よりレビュー待ち行列が最も長い経路一つから始めるほうがよい。失敗しても戻す範囲が一つのサービスに限られ、その経路でレビュー時間が実際に減ったかどうかが次の判断の根拠になる。人が保守する前提でコードを書く問題とつながる地点は人間が保守するかのようにコードを書けを併せて読むとよい。

10. 確認できなかったこと

この話題で今埋まらない場所を一箇所にまとめておく。以下の項目は本文で根拠として使っていない。

  • 言語別のAI生成精度の公開数値 — モデル・課題・採点基準を明示した比較資料は確認できなかった。
  • 学習データの言語分布 — 主要モデルはいずれも公開していない。特定言語のデータが多いから有利だという説明は検証不能だ。
  • エージェントがGoをうまく書くという社内観測の証言 — コミュニティの議論に引用された形でのみ確認される。測定方法と標本を示した一次資料は確認できなかった。
  • 英語圏の原文議論スレッド — アクセスが繰り返し遮断され原文を開けなかった。本文の反論はコミュニティのまとめで確認できた範囲までを反映している。
  • コンパイル速度比較の条件 — ハードウェア・コード規模・ツールチェーンのバージョンが原文に明示されていない。
  • 生成されたGoコードの並行性欠陥の頻度 — 懸念の提起は確認できるが、頻度を測った資料は確認できなかった。

結論: 選んだのは言語ではなく検証予算の配置だ

生成速度が上がった後に値上がりしたのは確かめる時間だ。言語はその時間を誰に請求するかを決める装置である。書式とイディオムをツールに渡す方式があり、型検査器に渡す方式があり、そのまま人に置く方式がある。三つとも答えであり、対価が違うだけだ。

明日から適用できるものは三つだ。

  1. レビュー時間を五項目に分けて測る。形の把握・イディオムの照合・APIの実在確認で時間が漏れているなら、それは言語を替えるべき合図ではなくツールを入れていない合図であることが多い。
  2. 今使っている言語で有効にできる特性を全部有効にする。フォーマッタをCIで強制し、静的解析と脆弱性検査を通過条件に格上げし、型検査の厳格設定を新規コードから適用する。言語の入れ替えはその次だ。
  3. 条件のない比較を根拠に使わない。バージョン・ハードウェア・課題・採点基準のない数値は方向すら保証しない。

一行に縮めるとこうなる。Goが正解だから有利なのではなく、検証コストがボトルネックである条件でGoの持つ特性が値を出す。その条件でないチームでは、同じ特性が表現力の損失と本文の長さだけになって残る。言語を選ぶ作業は今後も、制約を先に書き出す作業だ。
