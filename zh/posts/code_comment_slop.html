注释应当说代码说不出的话

复述代码的注释会索取的代价，以及那个位置该放什么

2026年8月30日 开发/基础设施

话很多却什么也没留下的注释有了名字

打开同事提交的改动，一个函数上面压着三十行注释。老老实实读完，知道了下面这段代码在做什么 — 而这本来直接读代码就知道。真正想知道的那几件事，为什么这里要再排一次序、为什么重试次数是三，在那三十行里一个字也没有。

最近有位开发者给这类文字取了个名字：yap。意思大致是「为说话而说的话」 — 不是指望对方接收的表达，而是说话的人为了把思路接下去而漏出来的声响。那篇文章的提议很简单：与其在评审里每次都把同一条意见展开写一长段，不如用一个短词来叫它，而这个词代表一句指令 — 退一步想想，这条注释在这里究竟提供了什么价值。以上是缘起，接下来要处理的是它背后那个问题。注释究竟是为了什么。

有件事先说清楚。把代码原样抄一遍的注释并不是新冒出来的现象。人写这种注释已经写了很久 — 因为入门时就是这么学的，因为公司规范要求每次改动都得带注释，或者因为不加任何说明只提交代码，看上去像是没用心。最近变的不是种类而是数量，数量上来了，才终于显眼到值得取个名字。所以该问的不是谁写的，而是那个位置里应该放什么。

代码已经在说它做了什么 — 留给注释的三格

谷歌公开的代码评审指南里，对这个问题有一句现成的话。注释是为了代码本身无论如何也承载不了的信息，比如某个决定背后的理由。同一份文档还补了一句：注释通常是在解释代码为什么存在时才有用，而不应该去解释代码在做什么。

要把这条标准真正用起来，「为什么」还得再拆开。注释要填的格子有三个。

格子代码说得出来吗空着会失去什么
为什么这样做说不出来。留下的是结果，理由消失了下一个人要把同一轮权衡从头再做一遍
决定不做什么说不出来。被放弃的方案在代码里不留痕迹会来一个改动，退回到已经失败过的做法
压着哪些前提只能一部分。到类型和校验能承载的边界为止前提破掉那天，找原因要花掉好几天
在做什么已经在说了，而且比注释更准什么也不会失去

表里最后一行是整篇文章的起点。代码是关于自身行为的一份永远最新、永远准确的说明，因为代码本身就是行为。把同样的内容在旁边再写一遍，等于多了一份副本，而这份副本既不保证最新，也不保证准确。同一个事实旁边并排站着两句不同的陈述，读的人就得先决定该信哪一句。

// 代码已经说了的话
// 把重试次数设为 3
const RETRY = 3;

// 代码说不出的话
// 对方网关从第 4 次请求开始封锁 30 分钟。3 是它下面的最大值。
const RETRY = 3;

两条注释字数差不多。可是上面这条删掉不会有任何事发生，下面这条删掉，半年后就会有人把重试提到 5 然后被封。注释的价值与其按长度算，不如按删掉它会失去什么来算更准。

复述代码的注释会索取的代价

把复述型注释的问题概括成「浪费阅读时间」，说到的只是实际代价里最小的一块。时间是其中最便宜的一项，真正的代价要等时间过去才结账。

机理只有一句。代码会变，旁边那条注释通常不会跟着变。原因不是懒。来改代码的人是来改行为的；编译器、静态检查、测试，没有一样会去读注释里写了什么。没有任何装置会告诉你某条注释已经失真，于是注释就悄悄地旧掉。Python 的 PEP 8 把这一点钉得很短 — 与代码相矛盾的注释，比没有注释更糟。同一份文档还写道：陈述显而易见之事的行内注释不仅没有必要，反而会分散注意力。

什么时候什么代价谁来付
刚写完评审者读它、再回头和代码对照的时间评审者
几个月后只有代码动了，注释旧掉，留下一张错的地图下一个打开这个文件的人
出故障时拿过期注释当依据，立起一个错的假设参与处理的所有人
长期真正该读的那一行被埋在复述之间所有人
变更历史里与行为无关的行撑大 diff，把评审密度拉低团队

第三行尤其贵。缺失的注释会把人送回代码里，错的注释却会把人扣在错误的地方。注释写着「这个值来自缓存」，于是在缓存里翻了一下午也翻不出答案 — 这种经历大多数人都有过一次。那条注释在半年前还是真的。

第四行也不轻。读注释这个习惯是建立在信任上的。十条里有九条是把代码抄了一遍，人很快就会开始跳过注释，于是剩下的那一条 — 真正在提示风险的那一行 — 也被一起跳了过去。复述型注释毁掉的最大的东西不是那个文件，而是注释这套机制本身的信用。

这类注释是怎么长出来的 — 两边都不是恶意

把成因分成人这一侧和生成这一侧来看，会发现两条不同的路径走到了同一个结果。

人这一侧的理由大致有三个。

  • 习惯 — 最初学的时候，学到的是「注释用来解释代码」。在教学例题里这是对的，因为学的人还读不懂代码。麻烦在于这个习惯被原封不动带进了生产代码。
  • 规定 — 只要有「没注释的改动会被打回」这条规则，注释就一定会出现，而最容易写的注释就是把上面那行抄下来。
  • 不安 — 觉得不加任何说明只提交代码会显得不认真。这不是技术问题，是团队氛围问题。

生成这一侧的理由是结构性的。不给上下文、按行去要说明，回来的就是按行的说明。只看一行，无从知道这行为什么必要，能说的就只剩它在做什么。这不是能力问题，而是请求的形状决定了答案的形状。换成让一个人「给每一行都加上说明」，结果也差不多。

两边还有一个更深的共同原因。「做什么」摆在眼前，所以好写；「为什么」在脑子里，所以难写。写为什么，得把自己权衡过什么、放弃过什么重新翻出来，而那是代码刚写完、人已经累了的时刻最不想干的事。于是手往容易的那边偏。这是坡度，不是过错。

「注释要写足」这条老规则造出了什么

很多组织都有「注释要写足」这样的规范。用意没错，分岔出现在拿什么来判定足不足。判定标准一旦是条数或比例，人就会去把条数填满。这不是诚意问题，是度量问题 — 有什么被计数，行为就会朝可计数的那一侧对齐。

  • 统计注释行占比的指标 — 抬高比例最省事的办法就是写复述型注释。写「为什么」是一行，把代码抄一遍是十行。
  • 要求每个函数都有注释的规则 — 名字本已说清一切的函数，也会被配上一句把名字展开的话。
  • 评审清单里的注释项 — 只看有没有，那么有就通过。

有个值得摆在旁边的反例。Go 的文档注释规范要求所有导出的（首字母大写的）名字都应当有文档注释。形式上看和上面那些规则很像，结果却不同，因为 Go 的文档注释会被工具抽取出来发布成公开文档。那些注释有确定的读者 — 第一次使用这个包的外部开发者。有去处的规则，会变成契约而不是填空。

由此得到的判断标准是：制定注释规则时，与其定条数，不如定读者。「这条注释谁在什么时候会读」有答案，注释就大概率有用；没有答案，剩下的就只有数量。从可维护性角度重建评审标准这件事，在从可维护性角度看代码评审那边另作了处理。

好注释该坐在什么位置

那么注释写在哪里。位置大致是三处。

  • 看起来不对劲的代码旁边 — 写法与惯例相悖的部分。下一个人会以为「这是写错了吧」而动手去改的地方，需要一个标记说明这是有意为之。
  • 容易回退的决定旁边 — 临时处置、绕行、暂定的常量。把回退的条件一并写上，这条注释以后会自己到期。
  • 体现外部约束的地方 — 对方 API 的行为、法规、硬件上限，这类在仓库内部无从核实的情况。

三者的共同点是信息的来源在仓库之外。代码读多少遍、测试跑多少轮都还原不出来，所以只能靠人写下来。

// 再排一次序的原因：对方 API 不保证顺序。
// 规格文档写着已排序，但实际响应里存在不一致的情况。
// 等对方修好之后，这一行可以删掉。
items.sort(byCreatedAt);

这三行把表里那三格都装进去了：为什么这样做（不信任顺序）、前提是什么（文档与实际不符）、什么时候可以回退（等对方修好）。删掉，三样一起消失，剩下的那行 sort 在下一个人眼里就成了重复排序。

哪些东西可以从注释搬进代码

动笔写注释之前，有个问题值得先问一遍。这句说明能不能让代码自己去说。能搬就搬，因为搬进代码的说明不会旧掉 — 编译器和测试会替你守着。

  • 命名 — 用来解释某个值是什么的注释，大多能被名字吸收掉。如果注释是因为单位容易搞混才加的，就把单位写进名字或类型。
  • 函数拆分 — 同一个函数里出现三次「从这里开始是做什么的部分」，那就是在提示拆成三个函数。注释在充当小标题时，那个小标题就是函数名。
  • 类型与枚举 — 「这个参数只能是 0、1、2 之一」这句注释，搬进类型就变成了规则。注释违反了也就违反了，类型违反了会让构建停下来。
  • 校验与测试 — 「不要传负数」这句注释，可以换成一处输入校验或一条测试。文字要被读到才起作用，测试没人读也照样起作用。
// 搬之前 —— 由注释守住单位
// t 是秒。不要传毫秒
function expire(t) { /* ... */ }

// 搬之后 —— 由名字守住单位
function expire(ttlSeconds) { /* ... */ }

这一节的重点不是省事，而是想写注释的那个瞬间，有时正是该回头看设计的信号。一旦冒出「这块有点复杂，加段说明吧」的念头，先看看复杂的那一侧能不能收拾掉，再决定要不要写说明。当然不是全都能搬。被放弃的方案、对方系统的状况、这段代码什么时候可以删掉，这些在代码里没有落脚点。这些句子才是注释本来的位置，削减复述的理由也正是为了把这块地方空出来。

文档与注释的边界在哪里

不是所有说明都得挨着代码。定边界有两条标准就够用。

  • 改这段代码的人是不是非看不可 — 不看就会出错的句子放在代码旁边。写进维基是不会有人去看的。
  • 这句话会不会跟代码一起变 — 一起变就靠近代码，各走各的就挪出去。不会在同一个提交里被修订的句子，放在代码旁边最终也会旧掉。
  • 读的人有没有可能根本不看代码 — 面向的是只调用这个函数的外部开发者，那就是文档注释的位置，有一层专门由工具抽取并发布。
  • 是读一遍就完，还是要反复查 — 部署和运维步骤这类按顺序走的文字更适合放文档。散在代码旁边，顺序就看不出来了。
句子的性质放在哪里理由
这一行为什么长这样代码旁的行内注释只有改这一行的人需要看到
函数的前提、返回值、异常文档注释工具会抽出来变成公开文档
这个模块为什么存在模块顶部或仓库文档它不绑定在单个文件上
系统结构与决策记录仓库文档横跨多个模块，且单独更新
部署与运维步骤仓库文档有顺序的文字不适合放在代码旁

模糊地带总归会剩下一些。碰到这种情况，把更可能没人去更新的那一侧放得离代码更近是比较安全的做法 — 只要在代码旁边，至少还会落进打开这个文件的人的视线。API 文档与代码走偏的路径在结构层面的处理，放在API 文档治理那边。

评审里该怎么处理注释

这里是最需要留神的地方。指出一条多余的注释，非常容易被读成对人的评价。被指出代码有 bug，听上去是「我的代码错了」；被指出文字不好，听上去是「我写的话有问题」，这要个人化得多。

  • 把问题的方向掉个个儿 — 不问「你为什么这么写」，而问「这一行让读的人得到什么，能用一句话说清吗」。说得出来，那句话就是新注释；说不出来，删掉即可。
  • 规则不要在评审现场第一次拿出来 — 作为团队共识先在规范里写上一段。共识在前，之后的意见就是在套用规则，而不是口味之争。
  • 简短代称只有写进文档才成立 — 同一条意见反复出现，缩短来说确实省事；但如果这个代称的含义哪里都没写，它就只剩下一句生硬的话。
  • 把阻断项和建议项分开标注 — 多余的注释多半不是该拦住合并的事。把必须挡下的和以后再改的用标记分开，意见就会变轻。

另外有一条线最好不要越过。不要拿注释的文风去推测写的人。一旦开始把句子长、语气正式当成判断改动如何产生的依据，评审就从代码挪到了人身上。这类推测为什么容易垮，在文体位移测量能说什么、不能说什么里处理过 — 要点是，在群体层面看得见的趋势，一旦套到单篇文档上，依据就没有了。在团队内部代价还要更大：判错一次，那个人从此在评审里就会变得防御。

评审里要问的最好收成一句。这条注释在这个位置上产生价值了吗。谁写的，不是这个判断需要的输入。

用生成工具之前该先定的事

工具本身聊到这里就够了，剩下的是把该定的定下来。请求定住了，结果也就定住了。

  • 值得要的 — 这个函数假定为真的条件、没有选的方案和理由、如果是可回退的措施就写清回退条件。都是代码承载不了的项。
  • 不必要的 — 逐行说明、把推理过程留下来、把函数名展开的摘要。要了就会有，有了就得删。
  • 在规范文件里写上一段 — 把注释规则写进项目指引文件，就不必每次重复同样的话。重要的是同一段也同样适用于人。
  • 把草稿和提交物分开 — 干活时留的备忘，活干完就清掉。问题在于草稿的残留被原样合并进去，而不在于草稿里留备忘本身。

最后一道防线不是工具设置，而是提交之前，用第一次看到它的人的眼睛把自己的改动读一遍。这不是新增的纪律，本来就是提交的一部分。只是拿到代码的速度快了，读的时间相对显得更奢侈了而已。编写变便宜、理解变昂贵的这个结构，在代码经济学之变那边处理得更细。

标准很简单。无论是手写的还是拿来的，提交的那一刻，这段代码上署的就是提交者的名字。让别人去读自己都没读过的文字才是失礼，用了工具并不失礼。

批量清理会顺手删掉什么

意识到复述型注释有多少之后，很容易想一次清干净 — 用正则把短注释全删掉，或者把「删除不必要的注释」交给工具。这项工作里藏着一个不好回退的风险。删掉一条你不知道为什么存在的注释，和判断它没必要之后删掉，是两回事。前者不是判断，是省略了判断。

  • 最短的注释有时最重要 — 「不要调换顺序」这样的一行就是。按长度筛，先没的就是这种行。
  • 删之前只需问一句 — 没有这一行，下一个人会犯什么错？只要想得出一种错，这条注释就留下。
  • 过期的注释先看能不能修，而不是先删 — 过期意味着它曾经为真，那个位置上大概率仍有值得写下来的事实。
  • 把提交拆开 — 几百处塞进一个提交，没人评审得动。以无法评审的体量提上来的清理，不是清理，是赌。

安全的顺序是：按文件过一遍，过期的修掉，没有依据修的删掉，把删的理由写进提交信息。看着慢，但这项工作的目的不是把注释数量降下来，而是让剩下的注释可以被相信。只把数字压下去，目的就丢了。

没能确认的部分

  • 作为缘起的那篇文章，原文页面没有打开，只从话题页和讨论帖里留下的摘要里把握了要点。原文的示例与具体措辞没有搬到这里。
  • 注释密度规则对实际缺陷率或维护成本有什么影响，没有取得可以引用的定量研究。文中相关段落谈的是规则设计，不是测量结果。
  • 不同生成工具之间注释量差多少，没有找到公开的对比资料。工具之间的高下不在本文处理范围内。
  • 不同语言社区、不同组织的注释惯例并不一致。受监管行业的编码标准尤其可能提出与这里所写不同的要求，在那种环境里以内部标准为先。

小结 — 注释是说代码说不出的话的地方

留下来的是三句话。代码已经在说它做了什么 — 而且比注释更准、永远最新。注释要填的是为什么这样做、决定不做什么、压着哪些前提 — 三样都不可能从代码里还原出来。复述型注释真正的代价不是阅读时间，而是变旧 — 代码变了注释留着，最后成了一张比没有更糟的地图。

落到做法上可以收成一句。写注释之前，先想一下删掉它会失去什么。什么也不会失去，那这一行本来就不必有；确实会失去点什么，那就是这条注释存在的理由，把那句话写下来就好。

还有一句要补。说要减少多余注释，不等于说要少写注释，恰恰相反 — 多数仓库里写了「为什么」的注释是不够的。清掉复述是为了腾出空位，而填进那个空位的句子只存在于写代码那个人的脑子里。现在不写下来，半年后没有人还原得出来。
