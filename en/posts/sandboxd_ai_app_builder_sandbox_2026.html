sandboxd: Open-Source Sandbox Engine for AI App Builders

How AI-generated code is safely isolated and executed — infrastructure analysis and security perspective

Jun 18, 2026 Dev & Infra

Introduction: Who Watches the Code AI Writes?

As of June 2026, AI app builder services like Lovable, Bolt, v0, and Replit have become infrastructure that tens of millions of people use daily. A user types "build me a todo app" and AI generates code that immediately runs somewhere, producing a working web app link. This process feels so natural that many people miss the critical infrastructure problem lurking behind it. Code generated by AI is untrusted code.

What happens when this code runs on a server? Can a maliciously crafted prompt cause code that deletes server files? Can one user's sandbox access another user's data? Can API keys or database passwords stored in environment variables be exposed? Answering all of these questions is what sandbox isolation is about — and sandboxd is an open-source project that addresses these problems through self-hosting.

This article analyzes how sandboxd works, explains why code execution isolation is a core infrastructure problem in the AI app builder ecosystem, and explores what technologies like Firecracker, gVisor, and WebContainers each bring to the table. Everything here is based on the actual GitHub repository and related technical documentation as of June 2026.

1. What Is sandboxd — Architecture and Philosophy

1.1 Core Concept

sandboxd is, in a word, "the open-source backend engine for AI app builder products." It provides the infrastructure needed to self-host services that do what Lovable, Bolt, and v0 do — take a prompt and produce a working app link in seconds. According to the official repository (github.com/tastyeffectco/sandboxd), a single HTTP request triggers three things:

  • Create an isolated sandbox: a Linux container with an independent filesystem and memory
  • Run an AI coding agent: takes a user prompt and writes code inside the container
  • Provide a live preview URL: the dev server is immediately accessible at a shareable external URL

1.2 Technology Stack

sandboxd's technology choices are deliberately simple. A single Go binary controls Docker, Traefik handles preview URL routing, and SQLite in WAL mode stores state. No Kubernetes, no separate database, no message queue. The included agents are OpenCode and Claude Code CLI, pre-installed in each container.

The implications of this stack choice matter. Designing to run on a single server without Kubernetes reflects a philosophy that lets startups or individual developers launch an AI app builder service without cloud provider markups. The focus is on eliminating complexity while proving the thing actually works.

1.3 Cost Efficiency — Idle Shutdown and Instant Wake-Up

In a multi-tenant sandbox service, cost boils down to how many containers are running at once. sandboxd addresses this with idle shutdown and instant wake-up: sandboxes that aren't in use are automatically stopped to reclaim memory, and reconnecting to the preview link restarts them transparently. Disk state is persisted, so previous work is never lost. This design means a low-end single server can serve dozens of user environments instead of needing multiple always-on VMs.

2. Why Isolated Execution Is Core to AI App Builders

2.1 The Threat Model for Untrusted Code

In any service that handles AI-generated code, isolation is not optional — it is a prerequisite. Consider the concrete threat scenarios. First, prompt injection: a malicious user inputs "write me code that deletes the entire file system." The AI can generate that code. Without isolation, running it breaks the server. Second, cross-tenant data breach: if user A's sandbox can access user B's files, data leaks occur. Third, credential theft: if a sandbox can read environment variables containing API keys or database passwords, severe security incidents follow.

According to 2026 infrastructure research, sandboxed agents reduce security incidents by roughly 90% compared to agents with unrestricted host access. Even if that number is inflated, isolation as a core layer of defense-in-depth is hard to argue against.

2.2 The Fundamental Tension in Multi-Tenancy

AI app builder services are inherently multi-tenant. Thousands of users share the same server infrastructure. In multi-tenant environments, isolation has two dimensions. Resource isolation: one user's computation should not degrade another user's performance. Security isolation: one user's code should not access other users or the host system.

Satisfying both simultaneously while maintaining cost efficiency is the core technical challenge of AI app builder infrastructure. sandboxd provides basic isolation with Docker containers, but explicitly states that stronger isolation layers are required for production.

2.3 Real Incidents from Isolation-Free Services

Early AI coding services did experience security issues from missing isolation. Cases were reported where environment variables from one user's session could be read in another user's shared execution context, and filesystem traversal allowed reading code from other projects. These incidents are what elevated isolation from a nice-to-have to a core infrastructure requirement in the AI app builder ecosystem.

3. The Spectrum of Isolation Technologies — From Docker to MicroVMs

3.1 The Limits of Standard Docker Containers

sandboxd currently uses Docker. Docker containers are fast, familiar, and low-overhead. But they have a fundamental limit: they share the host kernel. If a kernel vulnerability exists, container escape becomes possible. Historically, multiple CVEs have been discovered in runc, cgroups, and namespace implementations. For trusted internal users, Docker is sufficient. But for multi-tenant AI app builders where external users run arbitrary code, Docker alone does not meet the bar — and that is the 2026 infrastructure consensus.

3.2 Firecracker MicroVMs — Strong Isolation, Fast Start

Firecracker, the foundation of AWS Lambda and Fargate, is MicroVM technology that gives each workload a dedicated Linux kernel. With no kernel sharing, container escape is structurally impossible. It boots in roughly 125ms with less than 5MB of memory overhead per VM, and can create up to 150 VMs per second per host. E2B — an AI agent sandbox service — achieves 150ms startup times by building on Firecracker. It is becoming the de facto industry standard for untrusted multi-tenant code execution.

The tradeoff is complexity. Firecracker requires more setup and operational overhead than Docker, and needs KVM hypervisor support, which constrains cloud instance selection. But for untrusted multi-tenant code execution, this tradeoff is worth it.

3.3 gVisor — Reduce Attack Surface with a User-Space Kernel

Google's gVisor takes a different approach. Rather than creating separate VMs, it intercepts container system calls and handles them in user space. This reduces the number of syscalls that reach the host kernel from hundreds to dozens, dramatically shrinking the attack surface. Services like Modal and Northflank use gVisor. Unlike Firecracker, it integrates natively with Kubernetes, making it particularly useful in Kubernetes-based infrastructure.

gVisor's tradeoff is performance. Intercepting every syscall has a cost — I/O-intensive workloads see 10–30% overhead. AI coding agent workloads involve heavy file reading and writing, so this overhead must be factored in.

3.4 WebContainers — A Sandbox Inside the Browser

StackBlitz's WebContainers, which power bolt.new, take a completely different isolation approach. They compile Node.js to WebAssembly and run it inside the browser tab. No remote server needed at all. Code execution happens within the browser's sandbox boundary — the code cannot access local filesystems or arbitrary networks. As of 2026, WebContainers support the vast majority of the npm ecosystem with near-native performance, and cache node_modules in IndexedDB for near-instant subsequent loads.

WebContainers' limitation is that they are browser-bound. Supporting environments outside Node.js — Python, Rust, databases — is difficult. Server-side business logic cannot be hidden from the client. This is why sandboxd chose server-side isolation: no language or runtime constraints, full use of server resources.

4. sandboxd's Security Model and Limitations

4.1 Current Security Posture (Beta)

sandboxd explicitly states it is beta-quality, and does not hide that its defaults are configured for local development. API authentication is disabled by default, preview links are accessible to anyone with the URL, and there are no egress restrictions. Exposing this default configuration externally creates serious security problems.

However, the fact that sandboxd does not hide these issues actually builds trust. Many open-source projects bury security concerns in small print, while sandboxd explicitly lists production requirements up front.

4.2 Required Steps for Production

The official sandboxd documentation's recommended production checklist includes:

  • Enable API authentication: Set SANDBOXD_API_AUTH_DISABLED=false and implement token-based auth
  • Gate preview URLs: Apply Forward-auth hooks to allow only authenticated users
  • Network control: Firewall + egress rules to restrict container external communication
  • Disk quotas: Volume and filesystem quotas to prevent single-user disk abuse
  • Replace isolation runtime: For untrusted code, replace Docker with gVisor, Kata, or Firecracker

4.3 An Honest Assessment of Docker-Based Isolation

From my perspective, sandboxd's current Docker-based isolation is adequate for internal teams or small groups of trusted users. But for a public service where external users type arbitrary prompts, it is insufficient. Without Firecracker integration, fully satisfying the "for AI app builder products" label in a public production environment is a stretch.

Recognizing this gap reveals what sandboxd's next milestone should be — integration with Firecracker or gVisor needs to be on the project's roadmap.

5. What Open-Source Sandboxes Mean for the AI App Builder Ecosystem

5.1 Breaking Free from Commercial Service Lock-In

Lovable, Bolt, and v0 are excellent services, but their internal infrastructure is not open. To replicate them on your own servers, you currently depend on sandbox services like E2B, Modal, or Northflank. These are great services, but they use usage-based billing that can scale sharply as your business grows. sandboxd provides a path to controlling infrastructure costs on your own server without those markups.

Especially in a startup's early stages, operating at cost rather than paying cloud service margins is significant. If a single server can serve dozens of users, the cost advantage is substantial before scale demands more.

5.2 Data Sovereignty and Code Privacy

Using an external AI app builder service means users' prompts and generated code transit through that service's servers. For internal enterprise tools, regulated industry prototypes, or services handling sensitive business logic, this data movement can be problematic. Deploying sandboxd on your own infrastructure means code and prompts never leave your perimeter. This is especially meaningful in financial services, healthcare, and public sector environments with data residency requirements.

5.3 Lowering the Barrier to Entry for AI App Builder Services

Before sandboxd, building a "prompt to instant running web app" service meant implementing isolation infrastructure, preview URL routing, and idle management from scratch — a significant engineering barrier. sandboxd reduces that complexity to a single ./install.sh. This lowers the market entry barrier for AI app builder services and creates a foundation for specialized vertical services: education-specific, language-specific, or enterprise-internal AI app builders.

6. Current Limitations and Honest Assessment

6.1 Beta Reliability

sandboxd is beta-quality, which means using it directly in production services carries risk for SLA and stability. The GitHub issue tracker shows edge-case bugs still being discovered. "Built to be read and extended" — the official description — means the code quality is good, but operational maturity needs to be built up by the adopter.

6.2 No Strong Isolation Runtime Built In

As noted above, Docker-based isolation is insufficient for untrusted external user code execution. Without Firecracker or gVisor integration in the current state, using sandboxd as the backend for a public AI app builder service requires doing the runtime replacement work yourself — a substantial engineering effort.

6.3 Single-Server Scale Ceiling

sandboxd's simplicity stems from assuming single-server operation. That assumption is an advantage early on, but horizontal scaling becomes difficult as traffic grows. No Kubernetes means no auto-scaling. For services handling more than a few hundred concurrent users, sandboxd alone hits a ceiling, and additional infrastructure work is needed.

7. When to Use sandboxd — and When Not To

7.1 Where sandboxd Fits Well

sandboxd is a reasonable choice for internal tooling or environments with a small number of trusted users, for PoC or early-stage MVPs of AI app builder services, for educational institutions or hackathons providing temporary per-user development environments, and for enterprise internal AI development platforms where data sovereignty matters. Getting started without complexity is fast, and the MIT license allows free modification and customization.

7.2 Where sandboxd Falls Short

For publicly open AI app builder services, hundreds or more concurrent users, regulated industries (healthcare, finance, public sector), or production environments requiring SLA guarantees, sandboxd in its current form is a hard fit. Firecracker integration, horizontal scaling, and enhanced authentication layers are needed on top. In these environments, commercial services like E2B or Modal may be the more realistic starting point.

7.3 Value as an Open-Source Reference

sandboxd's real value lies not just in the code itself, but in the fact that it publicly documents the design patterns of AI app builder sandbox infrastructure. Idle-shutdown and instant-wake-up, preview URL routing, API-based container lifecycle management — these patterns are now visible in a working implementation. Even if you do not use sandboxd directly, it is a valuable reference for building your own sandbox infrastructure.

Conclusion — Infrastructure Challenges in the Age of AI-Written Code

As of June 2026, AI app builders are no longer future technology. They are present-day infrastructure used by tens of millions of people every day. And the safety of that infrastructure depends on sandbox isolation as a technical problem. sandboxd is an open-source answer to that problem — imperfect, in beta, missing strong isolation runtimes. But the design philosophy is clear, and the implementation is readable and extensible.

In the broader picture, the existence of projects like sandboxd signals that the AI app builder ecosystem is maturing. AI infrastructure that once depended entirely on cloud services is being open-sourced, raising accessibility and creating foundations for specialized vertical services. Firecracker, gVisor, and WebContainers are each answers to different threat models, and the right choice is not a single answer but one determined by each service's threat model and operational capabilities.

In the age when AI writes code, who watches that code and how is a core challenge of technical infrastructure. sandboxd shows one open-source approach to that challenge.
