A Startup's PostgreSQL Survival Guide - From Connection Exhaustion to Partitioning

Connection pooling, indexes, autovacuum, zero-downtime migrations, and backup drills - the pitfalls teams actually hit, and how to handle them

Jul 24, 2026 Dev & Infra

Intro: Why Postgres Keeps Surprising Startups

A startup's database usually does not fail all at once. Early on, a single Postgres instance runs for months, sometimes a year or two, without incident. Things change once traffic crosses a certain line. Connections suddenly bottom out right after a deploy. A query that was fine yesterday now takes five seconds. Autovacuum eats all the CPU at 3am. A single-column migration locks up the entire service. Each of these is hard to diagnose the first time, and most teams only realize afterward that "this is something we should have known before it happened."

This post is a survival guide that walks through those pitfalls in a practical order. Rather than news or a product announcement, it covers the problems you actually run into operating Postgres - connection exhaustion, indexes, N+1 queries, autovacuum and bloat, locking and zero-downtime migrations, backup and recovery, monitoring, scaling order, and the managed-versus-self-hosted decision - down to the concept and command level. I cross-checked official documentation and practitioner references for accuracy, and this reflects information as of July 2026.

1. Connection Exhaustion - PgBouncer and Connection Pooling

The first pitfall most startups hit is connection exhaustion. Postgres's default max_connections sits around 100, and once your backend runs on multiple instances - or on autoscaled/serverless infrastructure where each instance keeps its own pool - that number is exhausted fast. Every connection costs Postgres a dedicated backend process, so as the count rises, context-switching and memory pressure rise with it.

1.1 Why an Application-Level Pool Isn't Enough

The connection pool your ORM or driver provides only operates per instance. With 10 instances each holding a pool of 20, the database can see up to 200 connections at once. Add batch jobs, an admin console, and monitoring agents, and exceeding max_connections is only a matter of time. A "connection storm" - a burst of connections all at once during a redeploy or restart - is a common incident pattern too.

1.2 Filtering at the Front With PgBouncer

The most proven fix is placing a connection pooler such as PgBouncer between the application and Postgres, decoupling the number of connections the application sees from the number of real database connections. In transaction mode (pool_mode = transaction), a connection is held only for the duration of a single transaction and returned right after, so far fewer database connections can serve far more application connections.

[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
listen_port = 6432
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
reserve_pool_size = 5

1.3 The Catch With Transaction Mode

Because transaction mode reassigns a connection to a different client the moment a transaction ends, it conflicts with code that assumes session state persists. Features that assume "this connection stays mine" - unwrapped SET commands, session-level prepared statements, advisory locks - misbehave in transaction mode. If your code relies on any of these, route that path through session mode instead, or rewrite it to fit transaction mode. Size the pool based on the database server's CPU core count rather than an arbitrary number, and tune it while watching client-wait metrics (cl_waiting, average wait time).

2. Missing or Excess Indexes - Finding the Balance

Indexes are where startups most often err at both extremes: none at all, or an index slapped on every column out of habit.

2.1 What Happens Without an Index

When a column commonly used in WHERE, JOIN, or ORDER BY lacks an index, the optimizer falls back to a sequential scan across the whole table. It's invisible with a small dataset, but once a table grows to hundreds of thousands or millions of rows, the same query suddenly starts taking seconds. Because this shift creeps in alongside growing traffic, it feels like the app "suddenly got slow one day," when really the table just crossed a threshold.

2.2 The Cost of Too Many Indexes

Conversely, over-indexing means every INSERT, UPDATE, or DELETE has to update each related index, adding write latency and consuming storage. It's common for an index added "just in case" to never actually be used. Check actual usage via the idx_scan column in pg_stat_user_indexes and drop indexes that see no scans.

SELECT relname AS table_name, indexrelname AS index_name, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY relname;

2.3 Designing Composite Indexes

If many queries filter on several columns together, a single composite (multi-column) index is often more effective than several single-column indexes. Column order matters: put equality (=) columns first, and range (>, BETWEEN) or sort columns after. Always create new indexes on live tables with CREATE INDEX CONCURRENTLY so you don't lock the table.

3. N+1 and Slow Queries - Catching Them With EXPLAIN and pg_stat_statements

Even with connections and indexes handled, N+1 queries at the application-code level remain a separate problem.

3.1 How to Spot an N+1 Query

N+1 is the pattern of fetching a list, then issuing a separate query per item to fetch related data - very common with ORMs. Logs alone rarely surface this, since each individual query is fast, often under a millisecond. But pg_stat_statements shows the same query pattern called tens of thousands of times in a short window. "A fast query with an abnormally high call count" is the signal.

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY calls DESC
LIMIT 20;

3.2 Reading EXPLAIN ANALYZE

Once you've found a slow-query candidate, run EXPLAIN (ANALYZE, BUFFERS) to see the actual plan and timing. A Seq Scan on a large table, a big gap between the estimated and actual row counts, or a large Buffers: shared read value (meaning heavy disk I/O) are all signals there's room to tune.

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at > now() - interval '7 days';

3.3 Total Time vs. Average Time

It's more efficient to prioritize by "total execution time" than by "slowest single query." A 10ms query run a million times a day often contributes more overall load than a single query that takes a full second. Sorting pg_stat_statements by total_exec_time is useful for setting this priority.

4. Autovacuum, Table Bloat, and Transaction ID Wraparound

This is the pitfall startup teams learn about last, but it's also the one with the most severe consequences if ignored.

4.1 MVCC and Dead Tuples

Postgres's MVCC (multi-version concurrency control) design means an UPDATE or DELETE doesn't immediately remove the old row - it leaves behind a prior version, a dead tuple. Autovacuum runs periodically to reclaim these, keeping tables and indexes from growing beyond their real data size. If autovacuum falls behind or its settings don't fit the workload, bloat accumulates, and the same query has to read far more pages, getting slower.

4.2 Per-Table Tuning Is the Right Approach

The default autovacuum_vacuum_scale_factor (20%) is far too loose for large, high-write tables. On a table with millions of rows, waiting for 20% of rows to change before vacuuming is much too late. Rather than disabling autovacuum entirely, the correct move is lowering the setting per table via ALTER TABLE.

ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit = 2000
);

4.3 The Cliff Called Transaction ID Wraparound

Postgres's transaction ID (XID) is 32 bits and wraps around at roughly four billion. Old row versions must be frozen before their XID age crosses a threshold. Around 1.6 billion, warning logs start piling up; past 1.8 billion, forced vacuums kick in; and as it approaches roughly 2 billion, Postgres itself starts refusing new writes to prevent data corruption. Reaching that point causes a severe, service-wide outage. Autovacuum depends on track_counts being enabled, so leaving that setting alone is the default rule. It's worth making a habit of periodically checking each table's XID age with a query like this.

SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY xid_age DESC
LIMIT 10;

5. Locking and Zero-Downtime Migrations

Schema changes are a pitfall startups run into repeatedly. An ALTER TABLE that worked fine early on turns into a service-stopping incident once enough data has accumulated.

5.1 Which DDL Is Dangerous

Operations that rewrite the whole table - changing a column type, creating an index without CONCURRENTLY, adding NOT NULL on older Postgres versions - hold a strong (ACCESS EXCLUSIVE) lock for the entire duration. Other queries queue up behind that lock, and a growing queue of waiting queries can cascade into connection exhaustion as well. Postgres 11 improved adding a column with a default to be instant (the value is stored in the catalog and applied on read), but operations that genuinely rewrite the table, like a type change, remain heavy.

5.2 The Expand-Contract Pattern

The standard safe pattern for zero-downtime changes is expand-contract. ① Deploy adding the new column as nullable. ② Deploy the app to dual-write to the new and old columns. ③ Backfill existing data into the new column via a background batch. ④ Verify, then switch reads to the new column. ⑤ After a safe period with no issues, drop the old column. Splitting each step into its own deploy makes rollback easy if any one step fails.

5.3 Session Timeouts and Tooling

Always set short lock_timeout and statement_timeout on migration sessions, so a lock wait is cut off early rather than queuing up a chain of other blocked queries. For online reorganization of large tables, consider pg_repack (a shadow copy with a brief swap lock) or expand-contract automation tools like pgroll.

SET lock_timeout = '2s';
SET statement_timeout = '5s';
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders (customer_id);

6. Backup, PITR, and Recovery Drills

What matters is not that a backup exists, but that recovery has actually been proven to work.

6.1 The Components of PITR

Point-in-time recovery (PITR) replays a WAL (write-ahead log) archive on top of a physical base backup made with pg_basebackup, rolling the database back to an arbitrary moment just before an incident. When a table was accidentally dropped, or a deploy bug corrupted data, a snapshot restore alone isn't enough - you need to roll back to precisely "a few minutes before the incident."

6.2 Tools Like pgBackRest

Rather than managing pg_basebackup and WAL archiving by hand, production environments standardly use a dedicated tool such as pgBackRest or WAL-G, which automate incremental/differential backups, encryption, parallelism, and retention.

pgbackrest --stanza=mydb --type=full backup
pgbackrest --stanza=mydb --type=diff backup

# Restore to a specific point in time
pgbackrest --stanza=mydb --type=time \
  --target="2026-07-24 03:00:00" restore

6.3 Why a Recovery Drill Matters More Than the Backup

A backup that has never been restored is a backup with an unknown success rate. Treat "recovery," not the backup file, as the actual deliverable. At least once a quarter, run a full point-in-time restore in a separate environment and verify data integrity as a scheduled drill. Define your RPO (acceptable data loss window) and RTO (acceptable recovery time) targets first, then use the drill to confirm those targets are actually achievable.

7. Monitoring Metrics - Cache Hit Ratio, Waits, Replication Lag

Knowing which numbers to watch is what lets you catch trouble before an outage. Three metrics matter most.

7.1 Cache Hit Ratio

The buffer cache hit ratio is the share of read requests served from memory (shared_buffers) rather than disk. Generally 99% or higher is ideal; dropping below 80% signals the cache is undersized for the working set, or queries are causing unnecessary disk I/O.

SELECT
  sum(heap_blks_hit) / nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0) AS cache_hit_ratio
FROM pg_statio_user_tables;

7.2 Connection Saturation and Query Waits

Watch how close the current connection count is to max_connections, alongside how many queries are queued waiting on locks. A growing queue of waiting queries is a leading indicator that the connection exhaustion or heavy DDL locking discussed earlier is actually happening.

7.3 Replication Lag

If you run read replicas, replication lag must be monitored. Rising lag means data read from a replica may be stale, and if lag has grown large right when the primary fails, the potential data loss during failover grows with it. Putting all three metrics - cache hit ratio, connection waits, and replication lag - on one dashboard via Prometheus's postgres_exporter and Grafana, with threshold alerts, is practically sufficient.

8. Scaling Order - From Vertical Scale to Sharding, Don't Skip Steps

Some teams jump straight to sharding the moment traffic grows, but following the order in practice is overwhelmingly safer and cheaper.

8.1 Vertical Scaling and Connection Management Come First

The first things to try are vertical scaling (bigger instance), the config tuning covered above, and connection management via PgBouncer. For most startup-scale traffic, this stage alone buys a surprisingly long runway.

8.2 Read Replicas and Partitioning

If reads dominate, add read replicas via streaming replication to spread read traffic. Next comes partitioning: physically splitting one large table into pieces so a query only scans the pieces it needs. RANGE partitioning by date suits time-series data; HASH partitioning by tenant ID or user ID suits spreading write load evenly.

8.3 Sharding Is Genuinely the Last Resort

Sharding - spreading data across multiple independent database nodes - is the last resort, since it forces the application to know which shard holds which data, a real structural complexity. It only becomes worth considering when the primary node's CPU/I/O stays above 70% even after tuning, the largest tables are hundreds of gigabytes and growing faster than storage can handle, tenant-level data isolation is a requirement, or backup/restore windows are themselves unacceptably long. Designing for sharding before any of these signals appear is usually over-engineering.

9. The Managed (RDS, Supabase, Neon) vs. Self-Hosted Decision

This call is driven more by team circumstances than by technology.

9.1 When Managed Wins

An early-stage startup without dedicated database operations staff reduces failure cost by starting with a managed service that handles backups, failover, patching, and monitoring. Neon and Supabase stand out with serverless pricing and branching (instantly cloning a dev database), which helps early development speed, while RDS brings AWS ecosystem integration and long-proven tooling.

9.2 When Self-Hosting Wins

If cost optimization matters and the team can genuinely run Patroni-style HA, pgBackRest backups, and its own monitoring, self-hosting can be far cheaper for the same specs. But it's important to recognize clearly that this savings is traded for the team carrying the operational burden itself.

9.3 A Principle That Holds Either Way

Whichever you choose, it's important not to lean too deeply on any single vendor's proprietary extensions or non-standard features from the start, and to keep standard Postgres compatibility. That way, when growing traffic eventually forces a switch, the migration cost stays a configuration change rather than a rewrite.

10. What to Set Up Early - A Checklist

Here's everything above condensed into a checklist you can act on during initial setup.

  • Put PgBouncer between the application and database from day one. Attaching it while traffic is still small means you won't be forced to adopt it in a rush later.
  • Enable the pg_stat_statements extension from the start. Turning it on only after a problem hits means you're missing exactly the data you'd need.
  • For large, high-write table candidates (event logs, sessions, etc.), plan per-table autovacuum settings in advance.
  • Make the expand-contract pattern and CREATE INDEX CONCURRENTLY your default workflow for schema changes from the start.
  • Build a PITR-capable backup system (pgBackRest, etc.) early, and put recovery drills on a recurring calendar.
  • Put cache hit ratio, connection saturation, and replication lag on one dashboard with threshold alerts.
  • Define RPO/RTO targets in writing first, then decide managed versus self-hosted based on those targets and your team's capacity.
  • Design high-volume time-series/event tables with a partition-friendly schema (a date column, etc.) from the start, so partitioning later can be introduced without downtime.

Conclusion

The places where Postgres surprises startups tend to look alike across teams: connections run out without warning, indexes are missing or excessive and left unattended, autovacuum falls behind and bloat piles up, a schema change triggers an unexpected lock, and a backup exists but recovery has never been tested. Every item covered here costs little if known and prepared for ahead of time, but costs downtime and lost trust if learned the hard way after an incident. Checking how many items on this list your team's Postgres already has covered is the most practical next step you can take today.
