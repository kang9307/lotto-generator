Self-Hosting Your Deployment Platform

The cost you delete and the cost you create are not the same currency - and the deploy tool's own path back

2026-07-30 Dev & Infra

Introduction: what are you actually buying when you decide to deploy from your own server

The first look at a self-hosted deployment platform usually produces the same reaction. 「With this, we would not need a managed service.」 On screen there is a flow that connects a repository, works out the stack on its own, builds an image, and attaches a domain and a certificate. Hearing that this flow can run inside your own server, of course it looks attractive.

But the real content of that decision is not the removal of cost, it is a change in the kind of cost you carry. What goes away is usage-linked recurring spend and dependence on one provider's conventions. What arrives is operational ownership: operating system patches, backups and the rehearsal of restoring them, certificate renewal, the disk that build cache eats, incident response, and one item almost nobody mentions — what do you deploy with when the deployment system itself is dead.

This article is not a tool introduction. It ranks nothing and quotes no prices, because prices change often enough that a figure becomes misinformation shortly after the day it was checked. Instead it itemizes the conditions attached to the sentence 「we will host it ourselves」. The starting point is one recently published open-source project. Every factual claim was verified directly against the official repository and the official documentation of each component on 2026-07-30, and figures that could not be verified were left out. The example domain is example.com and the example address is 192.0.2.1.

For the record, choosing a hosting type is out of scope here. The decision tree that separates static, shared, VPS, and PaaS is already covered in how to choose a web hosting type. This article picks up after that decision has already landed on 「we are using a server」, and asks whether the deployment automation should go on it too.

1. The starting point - only what the official repository confirms

The subject is Openship. The official repository is github.com/oblien/openship, and it describes itself as an open-source, self-hostable deployment platform with built-in CI/CD. The license is Apache License 2.0. The important point here is that this project does not aim to replace a PaaS or a CI system but both at once. Code comes in, becomes an image, runs as a container, and gets its public route and certificate, all inside one system.

The documented behaviour has five stages: detect, build, run, route and secure, push-to-deploy. In the detect stage it reads package.json, framework configuration, lockfiles, and optionally docker-compose.yml or openship.json to work out the stack and build commands. In the build stage it produces a Docker image or what the repository calls a bare release on the target server, and in the run stage it runs a container or a supervised host process. In the routing stage an OpenResty edge creates a reverse-proxy virtual host and provisions Let's Encrypt certificates. The final stage is GitHub webhooks, which re-run the pipeline when a push lands on a tracked branch.

What could not be confirmed is stated plainly too. The official repository documentation does not specify minimum memory, CPU, or disk requirements. No latest release version was found either. So this article prints no specification figures. If you are evaluating adoption, that number is something to measure against your own workload rather than estimate. Builds in particular spike memory usage in bursts, and when they run on the same server as a live service the resources that break first are memory and disk.

One more thing. The repository lists multi-node clusters, a load-balancing UI, private networking, advanced monitoring, and visual CI/CD pipelines as upcoming. An item on a roadmap is an item that is not present now. If you intend to design around deployments spanning several nodes and sophisticated monitoring, you have to account for those premises currently living outside the tool.

2. The cost you delete and the cost you create are not the same currency

Self-hosting debates spin in circles mostly because two kinds of cost get compared in one unit. One arrives monthly as a number on an invoice. The other is human time and the risk of an incident. The second looks like zero on ordinary days and is billed all at once on the day something breaks.

DimensionWhat shrinks or disappearsWhat newly appearsWhen the new item shows itself
Spend shapeRecurring charges tied to usageHuman time and standby burdenInvisible on normal days, visible on incident day
Lock-inDependence on platform-specific conventionsDependence on your own setup, the lock-in you builtWhen the owner changes or the documentation is missing
LimitsMetered limits such as build counts and bandwidthPhysical resource limits: disk, memory, IOPSAbruptly, at the hour when builds pile up
SecuritySome public exposure such as an admin consoleA new surface: webhook intake and build executionWhen a public repository or outside contributions appear
AvailabilityBeing swept up in a provider's outageA single point of failure in your own stackWhen you urgently need to deploy and the deploy system is down
DataUncertainty about where data is storedBackup, restore, and retention policy in fullThe moment you attempt a restore for the first time

The right-hand column of that table is the real subject of this article. And the right-hand column contains many items that do not scale with size. Whether you run one service or ten, operating system patches come around on the same cycle, and so does certificate renewal. That is why at small scale self-hosting easily becomes the worst shape for operational cost per unit. This structure is not an argument against self-hosting; it is an argument that you have to calculate the scale at which it starts to pay.

3. The newly created operational items - the side that sends no invoice

Below is the list of things that become your job from the day you put a deployment platform on your own server. Each item is only complete once you have decided who does it and how you learn that it failed. If either half is blank, the item does not yet exist.

  • Operating system and runtime patches — the container runtime, the database, and the edge proxy each have their own security update cadence. Enable automatic updates and you accept unannounced restarts; disable them and you accept an accumulating backlog. Either way, someone has to look regularly.
  • Free disk space — a deployment system piles up images, build cache, logs, and a database at the same time. When the disk fills, builds are not the only thing that fails; database writes stop too. Covered separately below.
  • Backups and restore rehearsals — having a backup feature and having a working restore are different facts. A backup you have never restored is an unverified procedure you will execute for the first time on incident day.
  • Secret management — if environment variables and deploy keys live only inside the platform, then when the platform dies the values you need in order to deploy are locked in with it. They need a second home.
  • Certificate renewal and failure detection — wiring up automatic renewal and knowing that a renewal failed are two separate pieces of work. Both are needed before the arrangement is finished.
  • Protecting the webhook endpoint — a build that runs on an inbound request means that path is an execution trigger.
  • Build isolation — a build executes repository code and dependency install scripts. The privileges it runs with, and where it runs, are the size of the risk.
  • Monitoring and night-time alerting — a process that died with nobody noticing is the most common form of a long outage. You need a check that connects from outside.
  • Log retention and rotation — with no logs you cannot find the cause, and with unmanaged logs you fill the disk. Retention and rotation have to be numbers, not intentions.
  • Incident response procedure — if you have not decided in advance what to cut first when the build server starts being used as somebody else's tool, the judgement made that night is usually the worst one available.
  • Change history — where platform settings and service definitions are recorded. Configuration changed only in a UI effectively does not exist when you have to rebuild.
  • The bootstrap procedure — the most frequently omitted item on this list, and the subject of the next section.

If your reaction to this list is 「most of it can be automated」, you are half right. Automation is possible, but without a mechanism that tells you the automation failed, automation increases risk instead of reducing it. For the same reason a silently failing backup is worse than no backup at all.

4. The most commonly missed item - the deploy tool's own path back

This is the core of the article. With a managed platform you never have to imagine the deployment system dying. If it dies, the provider fixes it. The moment you move to self-hosting that situation becomes a real scenario, and the probability that it coincides with the moment your service needs an urgent fix is not low. Builds failing because the disk is full, and therefore neither a rollback nor a deployment being possible, is the classic shape.

Separating 「what stops when this stops」 from 「what brings it back」 for each component in advance makes the scenario far less dangerous. Organized around the self-hosted stack components the Openship repository states, it looks like this.

ComponentWhat stops when it stopsMeans of recoveryWhat to prepare in advance
Edge proxy on 80 and 443Every external path to the serviceStand up a minimal reverse proxy yourself and bypass itWhere copies of vhost configuration and certificate files live
Platform API and dashboardNew deployments and rollback controlsRun the container directly with runtime commandsThe list of image tags currently running
Metadata databaseService definitions, history, configuration lookupsRestore from backup, or regenerate definitions from codeKeeping service definitions in the repository as well
Cache layerPipeline behaviour that depends on queues or sessionsRetry after restart, flush the cache if neededConfirming that cache loss is not data loss
Container runtimeEvery container, meaning the platform and the services at onceRecover the runtime, then rely on restart policies to bring things upAn explicit restart policy per component
Host diskBuilds, logs, and database writes alikeClean up and restart, or move to another hostA free-space threshold alert and a list of cleanup commands

The last column is what you actually have to prepare. And most of those preparations only mean anything if they live outside the platform. Information you need while the deployment system is dead, stored only inside the deployment system, is the same as no information.

Restart policy is one place where the details change the outcome. Docker's official documentation defines four restart policies. no is the default and does not restart automatically. on-failure restarts the container when it exits with a non-zero exit code, but the documentation states it does not restart the container if the daemon restarts. always always restarts a stopped container, except that a container stopped manually comes back only when the Docker daemon restarts or the container is manually restarted. unless-stopped is similar to always, except a stopped container is not restarted even after the Docker daemon restarts. The same page recommends using restart policies and avoiding process managers to start containers, and warns that combining the two creates conflicts. It also notes that a restart policy only takes effect after a container has started successfully and stayed up for at least ten seconds.

Why does this matter? Because the right answer depends on whether you expected a container you deliberately stopped for maintenance to come back after a server reboot, or expected it not to. The deployment platform's database and edge must come up after a reboot; an experiment you left standing must not. If that distinction is not written down as policy, a single reboot becomes an outage.

# Things to write in the bootstrap runbook - all values are examples
# 1) What to bring back, and the minimum information needed
EDGE_HOST=192.0.2.1
APP_DOMAIN=example.com
CURRENT_IMAGE=<current-production-image-tag>

# 2) The minimum path to run the service without the platform
docker run -d --restart unless-stopped \
  --name fallback-app -p 8080:8080 \
  --env-file /root-of-secrets/<service-name>.env \
  "$CURRENT_IMAGE"

# 3) A minimal proxy rule to stand in for the edge (replace the angle brackets)
#    https://<service-domain>/  =>  http://<internal-address>:8080
#
# 4) Write here the date on which this procedure was actually executed.
#    If nothing is written, it is a hope rather than a plan.

The most common omission in a bootstrap procedure is secrets. If the values behind --env-file in the example above lived only inside the platform database, you could not create that file and the procedure would stop on its first line. So secrets need a second copy somewhere other than the deployment platform. This is not a convenience question; it is a precondition of bootstrapping.

5. Write the restart policy per component

Translating the previous section's principle into configuration comes down to one question: is the policy written in a declarative file. Something clicked once in a UI vanishes when you rebuild; a policy written in a file survives. If you bring the stack up in Compose form, the following is about the minimum. Compose usage itself is covered separately in the Docker Compose part.

# State a restart policy for each platform component - values are examples
services:
  api:
    image: <platform-api-image>
    restart: unless-stopped
  db:
    image: postgres:<version>
    restart: unless-stopped
    volumes:
      - <data-volume>:/var/lib/postgresql/data
  cache:
    image: redis:<version>
    restart: unless-stopped
  edge:
    image: <edge-image>
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - <certificate-volume>:/etc/letsencrypt

# Checks
# - is the certificate volume included in the host backup set
# - is the db volume in the backup set, and has a restore been rehearsed
# - have you decided whether a manually stopped container should survive a reboot

One more point. The certificate volume is frequently missing from the backup list. Everyone thinks of the database as a backup target, but certificates and edge configuration are easy to wave off with 「we can just reissue them」. Yet walking through issuance from scratch on incident day is the surest way to extend recovery time. The issuance procedure itself is covered step by step in issuing and applying a free SSL certificate.

6. Build cache and disk - the failure cause that grows quietly

The most common first incident on a self-hosted deployment system is not a breach, it is the disk. The reason is simple. Builds leave cache behind, and cache exists in order to make things faster, so it is designed by default not to be deleted. And if a database sits on the same host, the moment the disk fills it does not stop at a failed build; it spreads into failed writes.

Docker's official documentation is specific about build cache cleanup. Alongside the statement that the BuildKit daemon clears the build cache when the cache size becomes too big, or when the cache age expires, it explains that the default policies are evaluated in order. There are four: remove cache that can easily be regenerated if it has not been used for more than 48 hours, remove cache that has not been used in a build for more than 60 days, remove unshared cache that exceeds the build cache size limit, and finally remove any build cache that exceeds the size limit. For the Docker driver, the documentation states that defaultKeepStorage defaults to 20GB.

The BuildKit configuration defaults appear on the same page. reservedSpace is 10 percent of total disk space or 10GB, whichever is lower; maxUsedSpace is 60 percent of total disk space or 100GB, whichever is lower; and minFreeSpace is 20GB. It also explains that when both values are set, a garbage collection sweep leaves the cache size between those two thresholds.

The practical thing to read here is not the numbers themselves but how ratio-based defaults behave on a small disk. A rule permitting cache to grow to 60 percent of the total disk is reasonable on generous storage, but on a small server where the service and the database share a volume it also means nothing is reserved for the space other processes need. So when you put a deployment platform on the same disk as a service, you need one of two things: an explicitly lowered cache ceiling, or a separate volume for builds.

  • Decide the free-space threshold first — setting it in gigabytes rather than percent is safer. A percentage loses meaning as the disk grows.
  • Route the alert to a human — if crossing the threshold is only shown on a dashboard, it is useless in the situation where that dashboard will not open.
  • Decide the cleanup commands in advance — trying to judge on incident day what is safe to delete is how you delete the thing that was not.
  • Separate the build volume — stopping the database and the build cache from sharing a volume is the most reliable defence.
  • Logs create the same problem — if you never set a retention period for container and build logs, logs sometimes fill the disk before cache does.
  • Image tags accumulate — a new tag per deployment makes image storage grow linearly. Decide how many generations to keep.
# Check what is eating the disk right now
docker system df -v | head -n 20

# Look at build cache alone, clear the entries unused for over 48 hours first
docker buildx du
docker builder prune --filter until=48h

# Narrow down from the top-level paths on the host side
df -h /
du -xh --max-depth=1 /var/lib/docker 2>/dev/null | sort -h | tail -n 10

# Threshold watch example - treat free space below the bar as a failure and alert
# (set the bar yourself according to the service profile)

7. The new attack surface created by webhooks and build execution

A flow where pushing deploys automatically is convenient, but look at the structure again and it is a path by which an external signal causes code to execute on your server. Read that sentence literally and the reason for caution is immediately visible.

This risk is not specific to self-hosted deployment platforms; it is shared by every arrangement that runs builds on your own infrastructure. GitHub's official documentation states a clear warning about self-hosted runners: we recommend that you only use self-hosted runners with private repositories, and the reason given is that forks of your public repository can potentially run dangerous code on your self-hosted runner machine by creating a pull request that executes the code in a workflow. The same logic applies to a home-grown build system. As long as a build executes scripts from a repository, anyone who can put code in that repository can run commands on your server.

  • Do not mix public repositories with your own builds — running builds for a repository that accepts outside contributions on your own server is dangerous without special isolation.
  • Give every build a clean environment — when files left by the previous build affect the next one, a single contamination keeps propagating.
  • Drop build privileges to the minimum — if a build runs with privileges that see the whole host, one build script is effectively host access.
  • Require signature verification on webhooks — if the intake point is open on the internet, no pipeline should run without a step confirming that the sender is genuine.
  • Keep the control plane off the public internet — just as the Openship repository describes the desktop app mode as having a local control plane and no public exposure, an arrangement that keeps the admin surface off the internet is the smaller surface where it is possible.
  • Check the vulnerability reporting path — the same repository asks that vulnerabilities be disclosed privately rather than in a public issue or pull request, and points to security advisories as the preferred route. Whether such a process exists is worth reading as a maturity signal when adopting a tool.
  • Keep secrets out of build logs — streaming logs are convenient, but the set of people who can read those logs becomes the exposure boundary for your secrets.
# First, count what is exposed externally
ss -ltnp | grep -E ':(80|443)\b'

# Check which user privileges builds run under
id
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}'

# Knock on the admin surface from a public address yourself
curl -sS -o /dev/null -w '%{http_code}\n' https://example.com/<admin-path>/

CI syntax and workflow authoring are out of scope here. GitHub Actions usage is covered in CI/CD automation with GitHub Actions; this section only picks out what changes when you move that execution seat onto your own server.

8. Certificates and the edge - the layer where you detect automation failing

Having the deployment platform issue certificates for you is a real convenience. But that convenience is about issuance, and the thing that causes operational trouble is renewal. The official Let's Encrypt FAQ states that default certificates are valid for 90 days and that subscribers can opt in to short-lived certificates valid for six days. The renewal guidance is every 60 days for 90-day certificates and every three days for six-day certificates. And it states flatly that there is no way to adjust these lifetimes, there are no exceptions. The same document explains that ACME clients perform routine renewals at random times rather than at a fixed hour.

Move those facts into a self-hosted context and there is one conclusion. Renewal must be automatic, and the failure of automatic renewal must reach a human. On a managed platform the second half belonged to the provider; now it is yours. And renewal failures happen quietly. Nothing at all happens on the day it fails, and it surfaces as a total outage days later on the day the certificate expires.

Validation failedAn error only in the log while the service looks fineThe alert stays inside the dashboardForward the renewal job's exit code to an external alert
The new certificate was not picked upThe file is renewed but the response serves the old certificateThe edge reload step is not verified separatelyCheck the expiry of the actually served certificate from outside
The certificate volume is not in the backupAfter a restore, only the certificates are goneOnly the database is thought of as a backup targetInclude a certificate check in the restore rehearsal

9. The conditions for doing it, and the signals that say do not

「Is it a good tool」 is a hard question to answer, and 「can we carry this right now」 is an answerable one. The conditions below are not about the quality of the tool but about the readiness of the organization.

  • The acceptable downtime is defined — you should be able to answer in minutes. Without that number there is no baseline for a recovery design.
  • There is a night and weekend response path — whose phone the alert reaches, and who is next when that person cannot connect, has to be decided.
  • At least two people can operate it — with only one, that person's holidays and resignation become availability risk directly.
  • A restore from backup has actually been performed — you should be able to point to a date. 「The feature exists」 is not an answer.
  • The bootstrap procedure has been executed — the path to bring the service up without the platform should have been walked at least once.
  • Builds do not fight the service for resources — whether they share a host, and whether volumes are split, has to be settled at design time.
  • Configuration lives in files — a setup that survives only through UI clicks is a setup that cannot be rebuilt.

Conversely, if the signals below are present, the answer is not now. These are not fixed by changing tools; they are fixed by changing readiness.

  • There is exactly one operator — if that person is unreachable on the day the deploy system dies, there is no alternative.
  • Restore from backup has never been rehearsed — self-hosting in this state is practically the same as having no backup.
  • There is no path by which a night-time failure is noticed — an outage learned about in the morning is an outage that lasted all night.
  • Nobody watches free disk space — as seen above, the first incident usually comes from here.
  • You plan to run builds for public repositories on your own server — without an isolation design, avoid this combination.
  • Secrets live only inside the platform — bootstrapping is then structurally impossible.
  • Cost reduction is the only reason for adopting it — if the saving is smaller than the value of the operational time, the arithmetic already fails.

One misunderstanding is worth clearing up here. The claim is not that self-hosting is expensive. The claim is that the point at which it becomes favourable depends on scale and readiness. A case that worked through the self-hosting cost structure for a different kind of workload is covered in the self-hosted AI workspace piece, and the shape of the conclusion there was the same. Real cost comes from resources and human time, not from a price sheet.

10. Migration cost - what is tied down when you leave

The item almost nobody calculates during evaluation is the cost of leaving. And that cost does not become zero merely because something is open source. A permissive license and an easy migration are separate matters.

Where you get tiedWhy the move gets hardHow to reduce it in advance
Build configurationRules the platform auto-detected become an undocumented specificationState build commands and artifact definitions in a file inside the repository
SecretsValues live only in the platform store, so even the list cannot be reproducedDuplicate the key-name list and the value location outside the platform
Domains and certificatesIssuance and renewal automation is bound to the edgeKeep issuance on standard ACME and lower cache time before cutover
DataExport format and reload time are the downtimeSchedule standard-format exports and restore rehearsals
Service definitionsConfiguration created only in the dashboard is absent from codeManage services, ports, volumes, and environment in declarative files
Image storage locationImages exist only in the platform's internal storePush them to a standard registry as well

There is one rule visible in that table. Lock-in comes from design, not from a contract. The more convenience features you use, the more the decisions those features made on your behalf disappear from documentation, and on the way out a human has to make those decisions again. So features like auto-detection are safer used, but with the result pinned into a file. That the artifact is a standard container image is a genuinely favourable condition, but if all you have is the image and no record of how it was run, the migration is still a rewrite.

There is also a separate piece on database backup and restore. For how to design backup targets, cadence, and restore rehearsals in a self-hosted environment, read it alongside self-hosted database backup.

Look again at the rows where 「self-hosted」 is the suggestion and a pattern appears. They are either organizations already operating servers, or cases with a requirement money cannot buy, such as data location. The rows recommending 「managed」 share a different pattern: human time and response structure are short. It is that condition, not tool quality, that decides the conclusion.

Conclusion: self-hosting is not a saving, it is an exchange

Putting a deployment platform on your own server is not a bad decision. It just has to be made with a clear view of what is being traded for what.

  • What goes away is fees and vendor lock-in — less need to design around metered limits, and if the artifact is a standard container, portability remains.
  • What arrives is operational ownership — patches, disk, backups and restore rehearsals, detection of certificate renewal failure, isolation of webhooks and build execution, and incident response, as one bundle.
  • The most frequently omitted item is bootstrapping — with no answer to what brings the deployment system back, a tool adopted for convenience becomes a single point of failure.
  • The criterion is readiness, not the tool — acceptable downtime, an on-call structure, and experience of a restore. Those three settle the answer.

One last note on stance. Neither a piece that recommends self-hosting unconditionally nor one that warns it is simply dangerous is useful. What is needed is counting the items attached to each choice without skipping any. That is why this article prints no prices, why figures that could not be confirmed in official documentation — such as system requirements — were left out entirely, and why every figure that is printed carries its source. Those sources change. On the day you decide, there is no safer method than opening them again yourself.
