タイムゾーンはコードではなくデータである - 更新すると過去の時刻の解釈まで変わる

保存した値は変わらないのに画面の時刻が変わる理由、そして後から再計算するために何を保存すべきか

2026-07-30 開発・インフラ

序論: 保存した値はそのままなのに、昨日と違う時刻が見える

最も理解しにくい種類のバグがある。データベースの値は誰も触っていないのに、画面に出る時刻が昨日と違う。監査ログのタイムスタンプが一時間ずれている。数年前の記録の時刻が変わっている。デプロイしたのはライブラリのバージョン上げひとつだけだった。

このとき人がまず疑うのはコードだ。変換関数を読み直し、サーバー時刻を確認し、誰がデータを書き換えたのか監査記録をたどる。そして何も見つからない。値は本当にそのままだからだ。変わったのは値ではなく値を読む規則のほうである。

この記事の心臓は一文だ。

時刻は値であり、タイムゾーンは規則である。規則はコードではなく定期的に更新されるデータファイルとして配布される。だから更新すると同じ値の解釈が変わる — 未来だけでなく過去も。

抽象的に聞こえるだろう。だからこの記事は主張をひとつもせずに始める。代わりにいまこの機械で実行した出力でその一文を証明する。この機械にはタイムゾーンデータをそれぞれ抱えた実行環境が二つあり、その二つのデータバージョンが違う。だから同じ保存値を両方に渡すと、ある過去の時点では互いに違う答えが出る。何件違うのか、どの地域のどの年で違うのかを全部数えた。

実行環境。以下の出力はすべてWindows 10 Pro (10.0.19045)で実際に実行した結果だ。実行環境はNode.js v22.16.0 (win32 x64)とPython 3.13.3 (win32 AMD64)である。両者のタイムゾーンデータの出所とバージョンは次のとおりだった。

  • Node.js — 同梱されたICU 77.1がタイムゾーンデータを持つ。process.versions.tzが2025bを報告した
  • Python — zoneinfo.TZPATHが空タプルだった。つまりこのプラットフォームにはシステムのタイムゾーンデータベースがなく、PyPIのtzdataパッケージがデータを供給する。そのパッケージは2025.3で、tzdata.IANA_VERSIONは2025cだった
  • 同じ日にIANAの配布ページが告知する最新リリースは2026c(2026-07-08)だった。両方とも最新ではなく、互いにも一致していない

この記事はシステムのタイムゾーンデータを更新も変更もしていない。「更新すると解釈が変わる」ことの証明に更新は必要なかった。データバージョンの違う二つの実行環境を同じ機械で並べて走らせるだけで足りた。スクリプトはすべてファイルに保存して実行した。

この記事が扱わないこと。経過時間を測るのにどの時計を使うかは別の主題なので触れない。DST境界の二つの穴は一節だけで押さえて先へ進む。それ自体で記事一本を要する主題だ。エンコーディング境界で文字が壊れる問題はcp949とUTF-8にある。

1. 時刻は値であり、タイムゾーンは規則である

まず用語を正確に切り分ける必要がある。この区別がぼやけると以降の話がすべて成り立たない。

  • 瞬間(instant) — 宇宙で一度だけ起きた地点だ。通常は基準時点からの秒数、つまりepoch値で表す。これは値である。どの政府もこの数字を変えられない
  • 地方時(local time) — その瞬間を特定の地域の人々が呼ぶ名前だ。「2026年7月30日13時」のようなもの。これは計算結果である
  • オフセット(offset) — その瞬間にその地域が基準時からどれだけ離れていたか。+09:00のように書く。これも計算結果である
  • タイムゾーン(time zone) — 瞬間を地方時に変える規則の履歴そのものだ。Asia/Seoulのような地域識別子がこの規則の束を指す。これがデータである

核心は最後の項目だ。Asia/Seoulは「プラス9時間」という意味ではない。1890年からいままでこの地域の時計がどんな規則に従ってきたかについての記録の束という意味だ。その束はIANAタイムゾーンデータベースに入っており、政府が規則を変えたり過去の記録の誤りが見つかったりすると新しいリリースとして配布される。

IANAの配布ページは、このデータが「政治機構がタイムゾーン境界・基準時オフセット・夏時間規則に加えた変更を反映するために定期的に更新される」と書いている。そして最終利用者は「通常、ソフトウェアとオペレーティングシステムの提供者を通じてこのデータの更新を受け取る」という。この二文がこの記事のすべての問題を作る。規則は外側で変わり、我々はそれをいつ受け取ったのかをおおむね知らない。

4. 同じ機械、二つのデータバージョン、33件の不一致

ここがこの記事の中心だ。システムデータに触れずに「データバージョンが違えば解釈が違う」を証明するには、バージョンの違う二つのデータを並べればよい。この機械にはすでにそれがあった。

--- H-4. version check commands, exactly as run ---
  > node -p "process.versions.tz + ' / icu ' + process.versions.icu"
  2025b / icu 77.1
  > python -c "import tzdata;print(tzdata.IANA_VERSION)"
  2025c
  > python -c "import importlib.metadata as m;print(m.version('tzdata'))"

5. オフセットだけ保存すると何を失うか

ここでよくある反問が出る。「ならオフセットも一緒に保存すればよいのでは?」 2026-01-15T10:00:00+09:00のように書けば曖昧さがないように見える。何が消えるのかを数えた。

--- B-1. an offset does NOT identify a region ---
  offset +09:00 at that instant :  12 zone ids  e.g. Asia/Chita, Asia/Dili, Asia/Jayapura, Asia/Khandyga
  offset +05:30 at that instant :   3 zone ids  e.g. Asia/Calcutta, Asia/Colombo, Asia/Kolkata
  offset -05:00 at that instant :  47 zone ids  e.g. America/Atikokan, America/Bogota, America/Cancun, America/Cayman
  offset +01:00 at that instant :  53 zone ids  e.g. Africa/Algiers, Africa/Bangui, Africa/Brazzaville, Africa/Casablanca
  total distinct offsets in use at that instant : 38

ある一瞬に+09:00を使う地域が12個、-05:00は47個、+01:00は53個だ。そしてその瞬間に世界中が使う互いに違うオフセットは38種類しかない。つまりオフセットは地域を指すにはあまりに狭い情報だ。

重要なのは「曖昧だ」ということではない。再計算が不可能になるということだ。オフセットは計算の結果であり、結果だけ保存するのは入力を捨てたことである。規則が変わったときに計算し直す材料がない。

  • オフセットを保存すれば瞬間は保たれる。その値がどのepochかを計算し直せる。それだけが必要な用途には十分だ
  • しかし「この地域で6か月後の同じ時刻」を問われたら答えられない。どの地域かを知らず、その地域がそのときどんな規則かも知らない
  • 地域識別子なしにオフセットだけあれば規則訂正の恩恵も受けられない。データを更新してもその値の解釈は変わらない。4節で見たことが良いことにもなりうる点を裏返して考えるべきだ
  • 利用者が「自分の地域」を選んだ画面からオフセットだけをサーバーへ送るフロントエンドは、まさにこの地点で情報を捨てている。地域識別子も一緒に送らねばならない

6. 同じ約束を三通りに保存してみると

--- B-2. a rule change that is IN the data: Europe/Istanbul ---

  2015-01-15 10:00 local -> offset +02:00  abbr EET   dst 0:00:00 -> UTC 08:00Z

  2016-07-15 10:00 local -> offset +03:00  abbr EEST  dst 1:00:00 -> UTC 07:00Z

オフセットだけ保存瞬間ひとつ + 結果値不可 — 地域識別子がないFalse (上と同じ瞬間)1時間
壁時計 + 地域識別子意図 + 規則参照可能 — 毎回計算し直すTrue (10:00を維持)0
壁時計だけ(地域なし)意図だけ不可 — どの規則か不明判定不可未定
UTC + 地域識別子を併記瞬間 + 規則参照可能 — 両方残るTrueに復元可能0

ここが「UTCで保存しなさい」という助言が足りなくなる地点だ。UTC保存は瞬間を守るが意図を捨てる。人々が約束したのは瞬間ではなく「その地域の朝10時」だった。規則が変われば、その意図を守るために瞬間が変わらねばならない。瞬間を固定して保存するのは意図が壊れる側に固定したということだ。

  • 「すでに起きた出来事」は逆だ。そのときの瞬間が確定なので瞬間を保存するのが正しい
  • 「これから起きる約束」は壁時計の意図が本質なので地域識別子と壁時計を保存せねばならない
  • 最も安全なのは表の最後の行だ。両方保存し、不一致が生じたら警告を出す。その不一致自体が「規則が変わった」という唯一の通知になる
  • この検査を自動化すればtzデータの更新を事後にでも検知できる。保存されたUTCと、地域識別子で計算し直したUTCを毎日照合し、差の出た行を抜き出すバッチだ

7. 未来は確定ではなく、過去も安全ではない

人はたいてい逆に考える。「過去は確定で未来が不確実だ」と。半分だけ正しい。二つの方向をそれぞれ確認した。

7.1 未来 — データは確定と推定を区別してくれない

まずこの実行環境が未来について何を「すでに知っている」と言うのかを見た。

--- B-4. past is settled, future is projected ---
  America/New_York transitions the data already asserts for 2027-2030:
      2027-03-14 -> -04:00
      2027-11-07 -> -05:00
      2028-03-12 -> -04:00
      2028-11-05 -> -05:00
      2029-03-11 -> -04:00
      2029-11-04 -> -05:00
      2030-03-10 -> -04:00
      2030-11-03 -> -05:00
  ...and for the year 2100:
      2100-03-14 -> -04:00
      2100-11-07 -> -05:00
  Asia/Seoul transitions 2027-2031 : none

2100年の転換日まで答えが出る。当然誰もその日付を決めていない。現在の規則を無限に延長した推定だ。問題はこれである。この出力には「推定」という表示がない。2027年の答えと2100年の答えが形式的にまったく同じだ。呼び出したコードは両者を区別する方法がない。

7.2 未来 — この機械の答えはすでに古びていた

もっと具体的に確かめることがあった。この機械のデータは2025cでIANAの最新は2026cだ。その間のリリースに未来の規則変更が入っていたなら、この機械は取り消された時計転換をまだ予定しているはずだ。tzプロジェクトNEWSの2026b・2026cの項目は、いくつかの地域が季節転換をやめて通年固定へ移ると書いている。この機械に尋ねた。

--- F-3. does this runtime still schedule clock changes that were cancelled? ---
  America/Edmonton     2026-2027 : 2026-03-08 -> -06:00, 2026-11-01 -> -07:00, 2027-03-14 -> -06:00, 2027-11-07 -> -07:00
  America/Vancouver    2026-2027 : 2026-03-08 -> -07:00, 2026-11-01 -> -08:00, 2027-03-14 -> -07:00, 2027-11-07 -> -08:00
  Africa/Casablanca    2026-2027 : 2026-02-15 -> +00:00, 2026-03-22 -> +01:00, 2027-02-07 -> +00:00, 2027-03-14 -> +01:00
  Europe/Chisinau      2026-2027 : 2026-03-29 -> +03:00, 2026-10-25 -> +02:00, 2027-03-28 -> +03:00, 2027-10-31 -> +02:00

--- F-2. and the resulting local time this runtime reports ---
  zone                   date (12:00Z) offset     abbr
  --------------------------------------------------------
  Africa/Casablanca      2026-10-15   +01:00     +01
  America/Edmonton       2026-12-15   -07:00     MST
  America/Vancouver      2026-12-15   -08:00     PST

そのとおりだ。この機械は2026年11月1日に時計を戻す予定として答える。ところが公式リリースノートは該当地域がその転換をしないと記録している。つまり今日この機械で計算した「今年12月の現地時刻」はすでに誤った答えだ。例外もなく、警告もなく、ただ一時間ずれた値が出る。

  • これがtzデータの更新をデプロイパイプラインに入れるべき実務的な理由だ。更新しなければ未来の計算が静かに誤ったまま運用される
  • 誤る時点が規則が変わった日ではなく計算対象の日付である点が罠だ。今日何の問題もなくても11月になれば予約が一時間ずれる
  • だから「いま動いているから大丈夫」という確認は無意味だ。未来の日付でテストしてはじめて表に出る

7.3 過去 — 確定だが訂正されうる

過去はすでに4節で証明した。整理するとこうだ。過去の瞬間は確定である。その瞬間を地方時で呼ぶ名前は確定ではない。その名前はデータに書かれた記録であり、記録には誤りがありうるし、誤りは訂正される。

tzプロジェクトのリリースノートが「Changes to past timestamps」という節を別に設けているという事実自体がこの点を語る。確認したリリースには、数十年前の転換時刻を00:00に訂正したり、特定の地域が特定の期間に観測した規則を変える項目が入っていた。

区分値(瞬間)地方時の表示なぜ変わるか変わったことをどう知るか
過去確定変わりうる履歴記録の訂正知りようがない — リリースノートを読むしかない
近い未来未確定変わりうる規則変更の公表データ更新後に再計算して照合
遠い未来未確定ほぼ確実に変わる現在の規則の無限延長(推定)データが推定であることを表示しない
転換のない地域の未来未確定比較的安定固定オフセットなので変更の余地が少ないそれでも変更事例がある

8. 略称は識別子ではない

画面にKSTやCSTを出すのは人に親切だ。それを保存したり解析したりすると別の話になる。ある一瞬の全地域の略称を集めて数えた。

--- B-5. abbreviations are not identifiers ---
  KST  :  3 zone ids, offsets ['+09:00']
           Asia/Pyongyang           +09:00
           Asia/Seoul               +09:00
           ROK                      +09:00
  CST  : 44 zone ids, offsets ['+08:00', '-05:00', '-06:00']
           America/Bahia_Banderas   -06:00
           America/Belize           -06:00
           America/Chicago          -06:00
           America/Chihuahua        -06:00
  IST  :  5 zone ids, offsets ['+02:00', '+05:30']
           Asia/Calcutta            +05:30
           Asia/Jerusalem           +02:00
           Asia/Kolkata             +05:30
           Asia/Tel_Aviv            +02:00
  EST  : 35 zone ids, offsets ['-05:00']

CSTは44の地域が使い、その地域のオフセットが+08:00、-05:00、-06:00の三種類だ。ISTは+02:00と+05:30を同時に意味する。最大誤差が14時間である。ではその文字列をパーサに入れるとどうなるかを見た。

--- C-1. parsing a string that carries an abbreviation (Python) ---
  2026-01-15 10:00 KST       -> ValueError: time data '2026-01-15 10:00 KST' does not match format '%Y-%m-%d %H:%M %Z'
  2026-01-15 10:00 CST       -> ValueError: time data '2026-01-15 10:00 CST' does not match format '%Y-%m-%d %H:%M %Z'
  2026-01-15 10:00 UTC       -> 2026-01-15T10:00:00        tzinfo=None
  2026-01-15 10:00 GMT       -> 2026-01-15T10:00:00        tzinfo=None
  2026-01-15 10:00 +0900     -> 2026-01-15T10:00:00+09:00  tzinfo=UTC+09:00

三通りの違う失敗がひとつの画面にある。

  • KSTとCSTは解析そのものが失敗する。このパーサはごく狭い略称の集合しか受け付けない。つまり「利用者が送った文字列をそのまま読み返す」往復が成り立たない
  • UTCとGMTは解析はできるのにtzinfoがNoneだ。略称を読んで捨てた。結果はnaiveな値で、この値をそのまま使うとプロセスのローカル時刻として解釈される。例外がないので最も危険だ
  • 数値オフセットだけが生き残る。そして5節で見たとおり、生き残ったそれは地域識別子ではない

別の実行環境では失敗の形がまた違う。

--- G-3. what Date parsing does with each written form (Node) ---
  local zone of this process : Asia/Seoul
  "2026-07-30"                     -> 2026-07-30T00:00:00.000Z  epoch 1785369600
  "2026-07-30T00:00:00"            -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026-07-30T00:00:00Z"           -> 2026-07-30T00:00:00.000Z  epoch 1785369600
  "2026-07-30T00:00:00+09:00"      -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026/07/30 00:00:00"            -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "July 30 2026 00:00:00"          -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026-07-30 00:00:00 KST"        -> Invalid Date
  "2026-07-30 00:00:00 CST"        -> 2026-07-30T06:00:00.000Z  epoch 1785391200

最後の二行が圧巻だ。KSTはInvalid Dateになり、CSTは解析に成功する。ところが結果が06:00Zだ。つまりこのパーサはCSTを-06:00として読んだ。+08:00を意味するCSTを送った人がいたなら14時間ずれた値が静かに保存される。

  • 最初の二行も罠だ。2026-07-30は基準時の深夜として、2026-07-30T00:00:00はローカルの深夜として読まれた。時刻部分を付けたかどうかで9時間の差が出た
  • つまり「日付だけの文字列」と「深夜を明示した文字列」が違う瞬間になる。日付選択UIがどの形式を送るかによって集計が一日ずつずれる
  • スラッシュ形式と英字の月名形式はローカルとして読まれた。ログ解析コードがこの形式に出会うとサーバーの地域によって答えが変わる
  • 結論は単純だ。機械が読む値はオフセットを明示した一種類の形式に固定し、地域識別子は別のフィールドへ移す

9. DST境界の二つの穴

この主題はそれ自体で記事一本を要するが、保存形式の議論に直接かかる部分だけ一節で押さえる。転換のある地域には存在しない壁時計時刻と二度来る壁時計時刻がある。

--- C-2. the two holes at a DST boundary (America/New_York, 2026) ---
  nonexistent local time 2026-03-08 02:30
    fold=0 -> offset -05:00 abbr EST  -> UTC 07:30Z -> back to zone 2026-03-08 03:30 EDT
    fold=1 -> offset -04:00 abbr EDT  -> UTC 06:30Z -> back to zone 2026-03-08 01:30 EST
    round trip preserved the wall clock : False

  ambiguous local time 2026-11-01 01:30
    fold=0 -> offset -04:00 abbr EDT  -> UTC 05:30Z -> epoch 1793511000
    fold=1 -> offset -05:00 abbr EST  -> UTC 06:30Z -> epoch 1793514600
    the two are equal by ==            : True
    seconds apart in real time         : 3600

二つの穴の性格が正反対だ。

  • 存在しない時刻は例外を投げない。値を受け付けて、往復すると違う壁時計になる(False)。02:30を入れたのに03:30または01:30が返る。保存して読み直すと値が変わるということだ
  • 二度来る時刻はもっと巧妙だ。二つの値が==比較で同じと出るのに実際は3,600秒離れている。同じと判定された二つの値が違う瞬間である
  • 区別はfoldのような追加ビットでのみ可能だ。そしてそのビットはISO文字列にも、たいていのDBカラムにも入らない
  • だから曖昧な時刻を壁時計 + 地域識別子だけで保存すると情報が足りない。この区間にかかる値は瞬間(UTC)も一緒に保存せねばならない

これが6節の表の最後の行(両方保存)が必要な二つ目の理由だ。未来の約束には地域識別子が要り、曖昧な境界には確定した瞬間が要る。

10. 24時間後と明日の同じ時刻は違う

「一日後」という言葉が二つを意味することを実行で確かめた。出発点は転換の前日の正午だ。

  start + timedelta(hours=24)    : 2026-03-08 12:00 -0400
    real seconds elapsed         : 82800

    real seconds elapsed         : 86400
  the two answers differ by      : 12:00 vs 13:00

  the same pair over the autumn boundary

  instant +24h                   : 2026-11-01 11:00 -0500  real seconds 86400

  and where a zone with a 30 minute shift lands (Australia/Lord_Howe)
    start        : 2026-10-03 12:00 +1030
    wall +24h    : 2026-10-04 12:00 +1100  real seconds 84600

  • 「毎日午前9時の通知」は壁時計のほうが正しい。経過時間が日ごとに変わるのを受け入れねばならない
  • 「決済後24時間以内は取消可能」は瞬間のほうが正しい。地域の規則が利用者の権利を増やしたり減らしたりしてはならない
  • 危ういのはこの選択が暗黙のうちになされる点だ。上の出力で壁時計の計算はawareな値にそのままtimedeltaを足した結果である。何の警告もない
  • 30分転換の地域では誤差が30分なので「1時間差」だけを検査するテストを通過する
  • 「営業日基準で3日」の類の計算は日付境界そのものが地域に依存するので、必ず地域識別子を入力として受け取らねばならない

11. 並べ替えと比較はUTCでのみ成り立つ

複数の地域の記録をひとつの画面に集めると並べ替えの問題が出る。地方時の文字列で並べたものと瞬間で並べたものを並べて出した。

--- C-4. sorting local-time text vs sorting instants ---
  as written
  id        local text            zone                  fold  offset UTC
  order-A   2026-11-01 01:30:00   America/New_York      0     -04:00 2026-11-01 05:30:00Z
  order-B   2026-11-01 01:30:00   America/New_York      1     -05:00 2026-11-01 06:30:00Z
  order-C   2026-11-01 09:00:00   Asia/Seoul            0     +09:00 2026-11-01 00:00:00Z
  order-D   2026-10-31 22:00:00   Europe/London         0     +00:00 2026-10-31 22:00:00Z
  order-E   2026-11-01 14:30:00   Australia/Lord_Howe   0     +11:00 2026-11-01 03:30:00Z

  sorted by the local text  : ['order-D', 'order-A', 'order-B', 'order-C', 'order-E']
  sorted by the real instant: ['order-D', 'order-C', 'order-E', 'order-A', 'order-B']
  the two orders agree      : False

二つの順序がまったく違う。地方時の文字列の並べ替えではorder-Aが二番目なのに、実際の順序では四番目だ。

  • 地方時の文字列は同じ軸の値ではない。互いに違うものさしで測った長さを数字だけ比べるのと同じだ
  • order-Aとorder-Bは文字列がまったく同一だ。地方時のテキストだけあればどんな並べ替えでもこの二つの順序を決められない
  • 同じ地域の中でも転換時刻をまたげば文字列の並べ替えが壊れる。「ひとつの地域しか使わないから大丈夫」は安全ではない
  • だから並べ替え・比較・範囲検索はすべて瞬間(UTC)のカラムでやらねばならない。地方時は画面に描くときだけ計算する
  • 表示用の地方時をカラムに保存してインデックスを張っていたなら、そのインデックスは並べ替えの目的には使えない

12. シリアライズとDBの境界で規則が蒸発する

地域識別子をきちんと持っていても、値がプロセスの外へ出る瞬間に消える場合が多い。往復を打ってみた。

--- F-5. serialization round trips ---
  original object      : datetime.datetime(2027, 6, 15, 14, 30, tzinfo=zoneinfo.ZoneInfo(key='Asia/Seoul'))
  original tzinfo type : ZoneInfo -> Asia/Seoul
  isoformat()          : 2027-06-15T14:30:00+09:00
  fromisoformat()      : datetime.datetime(2027, 6, 15, 14, 30, tzinfo=datetime.timezone(datetime.timedelta(seconds=32400)))
  tzinfo type after    : timezone -> UTC+09:00
  same instant         : True
  region id survived   : False

  the same pair for a zone that does have transitions:
    stored           : 2027-01-15T14:30:00-05:00
    region form + 6 months : 2027-07-15 14:30 -0400
    offset form + 6 months : 2027-07-15 14:30 -0500
    those are different instants, one hour apart

ISO文字列で書き出して読み返すと瞬間は保たれ(True)地域識別子は消える(False)。型がZoneInfoから固定オフセットへ変わった。見た目は同じ値なのでこの損失は目につかない。

ところがその値を基準に次の計算をすると表に出る。転換のある地域で6か月動かすと地域識別子のほうは-04:00、オフセットのほうは-05:00となり一時間違う瞬間が出る。値を保存して取り出しただけで規則が凍りついたのだ。

--- G-4. JSON round trip (Node) ---
  JSON.stringify        : {"label":"meeting","when":"2027-06-15T05:30:00.000Z"}
  the zone the user chose is nowhere in that payload
  same instant revived  : true
  toString() (local)    : Tue Jun 15 2027 14:30:00 GMT+0900
  toISOString()         : 2027-06-15T05:30:00.000Z
  in Asia/Seoul         : 2027-06-15, 14:30:00 GMT+09:00
  in America/New_York   : 2027-06-15, 01:30:00 GMT-04:00

--- F-6. an SQL boundary: with and without zone information ---
  meeting  text=2027-06-15T14:30:00+09:00        epoch=1813037400 zone='Asia/Seoul'
           read back -> 2027-06-15T14:30:00+09:00        tzinfo=UTC+09:00
           with the zone column, recomputable -> 2027-06-15 14:30 +0900
  naive    text=2027-06-15T14:30:00              epoch=1813037400 zone=''
           read back -> 2027-06-15T14:30:00              tzinfo=None
           without a zone column, the reader must guess
  • JSONのシリアライズはオフセットすら残さない。常に基準時の形式で出るので、利用者が選んだ地域がpayloadのどこにもない
  • 同じオブジェクトをtoString()で打つとプロセスのローカル地域で見える。ログとAPIの応答が違う時刻を語るよくある原因だ
  • DBでは地域識別子を収める別のカラムがあるかが分かれ道だ。オフセットを抱く型も規則は抱けない。抱くのは結果値だけである
  • 地域のないnaiveな値は読み返すとtzinfo=Noneだ。どの地域かはスキーマの外の慣習に残る — つまりどこにもない
  • だから未来の約束のテーブルには瞬間のカラムと地域識別子のカラムを両方置くのが正解だ。ひとつでは足りない

--- H-3. does TZ reach Python zoneinfo on this platform? ---
  TZ=<unset>            local astimezone() -> +0900  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=America/New_York   local astimezone() -> +0100  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=Europe/London      local astimezone() -> +0100  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=UTC                local astimezone() -> +0000  | ZoneInfo('America/New_York') -> -0400  | tzset available: False

二つの実行環境の反応がまったく違う。

  • NodeではTZがきちんと動いた。地域識別子を入れると同じ壁時計の引数が互いに違う瞬間になる。EST5EDTという旧名は正規の識別子へ解決されて答えが出た
  • Python側は違う。time.tzsetがこのプラットフォームにない(False)。ところがローカル地域の判定にはTZが影響を与え、その結果が誤っていた。America/New_Yorkを入れたとき+0100が出た。7月のその地域は-0400である
  • さらに悪いのはEurope/Londonを入れたときもまったく同じ+0100が出た点だ。偶然合って見えるが同じ値なので地域識別子として解決されたのではない
  • 逆にZoneInfo('America/New_York')はすべての場合に-0400だった。明示的に指定した地域は環境に揺さぶられなかった

結論はひとつだ。地域は値の一部として明示する。プロセスの環境から読み取る方式はプラットフォームによって静かに誤った答えを出す。とくにコンテナとローカルの開発機が違う環境を持つのが正常な世界で、環境変数は再現可能な入力ではない。

14. 対応手順 — 何を何として保存するか

ここまでの実行結果を決定規則として整理する。出発点は「UTCで保存しなさい」ではなく「この値の性格は何か」だ。

14.1 値の性格別の保存形式判断表

値の性格本質は何か保存形式規則が変わったら再計算可能
起きた出来事 (ログ・決済・監査)瞬間瞬間(UTC)ひとつ瞬間はそのまま、表示だけ変わりうる表示の再計算が可能
未来の約束 (会議・予約)壁時計の意図壁時計 + 地域識別子、瞬間はキャッシュ瞬間が変わってこそ意図が守られる可能 — 毎回計算し直す
繰り返しの予定 (毎日09:00)規則 + 壁時計壁時計 + 地域識別子 + 繰り返し規則次の発生時刻が変わる可能 — 瞬間を保存すると不可
営業日・締切地域の日付境界地域識別子 + 日付 (+休日カレンダー)日付境界が移動しうる可能
誕生日・記念日暦の上の日付日付だけ (時刻・地域なし)影響なし該当なし
境界にかかる値 (曖昧・不在の時刻)瞬間が二つのうち一方瞬間 + 壁時計 + 地域識別子のすべて瞬間が確定なので安全可能
オフセットだけ (+09:00)計算結果避ける — 補助情報としてのみ何も起きない不可
略称 (KST・CST)人が読む表示保存しない該当なし不可

14.2 tzデータの更新をデプロイパイプラインに入れる理由

7.2節が理由のすべてだ。更新しなければ未来の計算が静かに誤ったまま運用される。今日の結果が正常でも計算対象の日付が来れば誤る。そしてこの誤りは例外を投げないので監視に引っかからない。

  • tzデータはアプリケーションの依存として管理する。どの実行環境がどこからデータを受け取るのかを文書に書いておく — この機械の場合、一方は同梱ICU、他方はパッケージだった
  • 実行環境が複数あるならバージョンを揃える。4節で見たとおり、違えば静かに違う答えが出る
  • バージョンを起動ログに出す。事故のあとで「あのときどのバージョンだったか」を知る方法はそれしかない
  • 更新を定期作業に入れつつ、更新自体をデプロイとして扱う。更新は過去データの解釈を変えうる変更である
  • OSパッケージの更新がアプリケーションの使うデータを変えないこともある。同梱データを使う実行環境はOSを更新してもそのままだ

14.3 更新後の回帰確認の方法

更新したなら何が変わったのかを数えねばならない。4節で使った方法がそのまま手順になる。

  • 更新前にスナップショットを取る。サービスが使うすべての地域識別子 × 関心期間のオフセットを表に保存する。上の実験は地域418個 × 時点564個で23万行を作り、数秒で終わった
  • 更新後に同じ表をもう一度取り、差分だけを見る。33行のような小さな数が出るのが正常だ。0行なら更新が反映されていないので、それも信号である
  • 差分をリリースノートと突き合わせる。ノートにない変化が出たらデータではなくコードや設定の問題だ
  • 保存された未来の約束を全数再計算して照合する。保存された瞬間と、地域識別子で計算し直した瞬間を比べて差の出た行を抜く。6節の表の最後の行を使っているなら、これがそのまま通知になる
  • 地域識別子の有効性を確認する。利用者データにある地域文字列が更新後もすべて解決されるかを見る。4節で見たとおり実行環境の間で180個の差があった
  • テストに過去と未来の日付を入れる。現在時刻しか使わないテストはこの種の回帰を原理的に捕まえられない
  • 転換の境界を固定値でテストする。存在しない時刻と二度来る時刻をそれぞれケースとして埋め込んでおく

14.4 レビューで問うべきこと

  • この値は起きた出来事か、これからの約束か? — 答えが違えば保存形式が違う
  • 地域識別子をどこに保存するか? — 「オフセットに入っている」という答えは誤答だ
  • この値であとから計算し直すことがあるか? — あるなら規則の参照が残っていなければならない
  • 並べ替え・比較をどのカラムでやるか? — 地方時のカラムなら直す
  • 「一日後」が壁時計か経過時間か? — 要件の文書に書かれているか
  • 実行環境が複数あるならtzデータのバージョンは同じか? — 起動ログで確認できるか
  • 利用者に略称を見せてそれを受け取り直すか? — 受け取り直すなら直す
  • 過去の記録の表示が変わってもよい画面か、変わってはいけない画面か? — 後者なら表示文字列も一緒に保管する

一行で。時刻は値でありタイムゾーンは規則である。値だけ保存すれば規則が変わったときに計算し直せず、規則の参照だけ保存すれば規則が変わったときに答えが変わる。どちらが正しいかは、その値が「起きたこと」なのか「することにしたこと」なのかが決める。そしてその判断を一度もしていないシステムが、ある日ライブラリをひとつ上げたあとで過去の記録の時刻が変わるのを見ることになる。

# タイムゾーンは更新されるデータ — 保存形式の判断表と更新後の点検リスト

> 出典: braindetox.kr — タイムゾーンはコードではなくデータである
> 根拠: Windows 10 / Node v22.16.0 (ICU 77.1, tz 2025b) / Python 3.13.3 (tzdata 2025.3 = IANA 2025c) 実行検証
> このファイルをそのままAIに貼って「この基準で我々のスキーマとデプロイパイプラインを点検して」と書けばよい。
> ⚠ 観測事実: 同じ機械の二つの実行環境が235,752組のうち33組で違う過去のオフセットを答えた。保存値はひとつも変わっていない。

## 0. 大前提 — 時刻は値でありタイムゾーンは規則である

| 概念 | 何か | 誰が変えるか |
|---|---|---|
| **瞬間(instant)** | epoch値。宇宙で一度起きた地点 | **誰も変えられない** |
| **地方時** | その瞬間を特定の地域が呼ぶ名前 | 計算結果 |
| **オフセット** | その瞬間その地域が基準時から離れた量 | 計算結果 |
| **タイムゾーン** | 瞬間を地方時に変える**規則の履歴そのもの** | 政府が変えIANAが配布 |

**規則を失う保存方式(オフセットだけ)は未来に答えを出せない。**

## 1. 値の性格別の保存形式判断表 — この表が核心だ

| 値の性格 | 本質 | 保存形式 | 規則が変わったら | 再計算 |
|---|---|---|---|---|
| **起きた出来事** (ログ・決済・監査) | 瞬間 | **瞬間(UTC)ひとつ** | 瞬間は維持、表示だけ変わりうる | 表示の再計算が可能 |
| **未来の約束** (会議・予約) | 壁時計の意図 | **壁時計 + 地域識別子**、瞬間はキャッシュ | 瞬間が変わってこそ意図が守られる | **可能** |
| **繰り返しの予定** (毎日09:00) | 規則 + 壁時計 | **壁時計 + 地域識別子 + 繰り返し規則** | 次の発生時刻が変わる | **可能** (瞬間保存では不可) |
| **営業日・締切** | 地域の日付境界 | **地域識別子 + 日付** (+休日カレンダー) | 日付境界が移動しうる | 可能 |
| **誕生日・記念日** | 暦上の日付 | **日付だけ** (時刻・地域なし) | 影響なし | 該当なし |
| **境界にかかる値** (曖昧・不在の時刻) | 瞬間が二つのうち一方 | **瞬間 + 壁時計 + 地域識別子のすべて** | 瞬間が確定なので安全 | 可能 |
| オフセットだけ (`+09:00`) | 計算結果 | **避ける** — 補助情報としてのみ | 何も起きない | **不可** |
| 略称 (`KST`・`CST`) | 人が読む表示 | **保存しない** | 該当なし | **不可** |

### 判定規則を三行で

- すでに**起きた**ことか → 瞬間を保存する
- これから**することにした**ことか → 壁時計 + 地域識別子を保存する
- 両方必要か → **両方保存し、再計算結果とずれたら警告する**

## 2. tzデータのバージョン確認コマンド

```bash
# Node — 同梱ICUがデータを持つ
node -p "process.versions.tz + ' / icu ' + process.versions.icu"
# 実測: 2025b / icu 77.1

# Python — システムDBがなければPyPIのtzdataパッケージが供給する
python -c "import tzdata;print(tzdata.IANA_VERSION)"
python -c "import importlib.metadata as m;print(m.version('tzdata'))"
python -c "import zoneinfo;print('TZPATH:', zoneinfo.TZPATH)"
# 実測: 2025c / 2025.3 / TZPATH: ()   (空タプル = システムDBなし)

# 知っている地域識別子の数 — 実行環境の間の差を見る
node -p "Intl.supportedValuesOf('timeZone').length"
python -c "import zoneinfo;print(len(zoneinfo.available_timezones()))"
# 実測: 418 vs 598  (Pythonだけが知る互換リンク180個)
```

- **実行環境が複数ならバージョンを揃える。** 違えば静かに違う答えが出る
- **バージョンを起動ログに出す。** 事故後に「あのときどのバージョンだったか」を知る唯一の方法だ
- OSパッケージの更新が**同梱データを使う実行環境を変えないことがある**

## 3. 更新後の回帰点検リスト

- [ ] **更新前のスナップショット**を取った — サービスが使う全地域識別子 × 関心期間のオフセット表
- [ ] **更新後に同じ表**を取り直し、**差分だけ**を見た (実測: 418地域 × 564時点 = 23万行、数秒)
- [ ] 差分が**0行ではなかった** — 0行なら更新が反映されていない
- [ ] 差分を**リリースノートと突き合わせた** — ノートにない変化はコード・設定の問題だ
- [ ] **保存された未来の約束を全数再計算**して保存された瞬間と照合した
- [ ] 利用者データの**地域識別子が更新後もすべて解決される**かを確認した
- [ ] テストに**過去の日付と未来の日付**を入れた (現在時刻だけのテストでは捕まらない)
- [ ] **転換の境界を固定値で**テストした — 存在しない時刻、二度来る時刻
- [ ] **秒単位のオフセット**(例: `+08:27:52`)が来てもスキーマが耐えるか確認した
- [ ] **30分・45分のオフセット**(`+05:30`, `+05:45`, `+08:45`, `+10:30`)で壊れないか確認した
- [ ] `+14:00`の地域のせいで**日別集計が二日にまたがる**場合を定義した
- [ ] 更新を**デプロイとして扱った** — 過去データの解釈を変えうる変更である

## 4. レビューで問う文

- この値は**起きた出来事か、これからの約束か?** — 答えが違えば保存形式が違う
- 地域識別子を**どこに保存するか?** — 「オフセットに入っている」は誤答だ
- この値で**あとから計算し直すことがあるか?** — あるなら規則の参照が残っていなければならない
- 並べ替え・比較・範囲検索を**どのカラム**でやるか? — 地方時のカラムなら直す
- 「一日後」が**壁時計か経過時間か?** — 要件の文書に書かれているか
- 実行環境が複数なら**tzデータのバージョンは同じか?** — 起動ログで確認できるか
- 利用者に**略称を見せてそれを受け取り直すか?** — 受け取り直すなら直す
- 過去の記録の表示が**変わってはいけない画面か?** — ならば表示文字列も一緒に保管する

## 6. やってはいけないこと

- ❌ **オフセットだけ保存する** — 瞬間は残るが再計算の材料が消える
- ❌ **略称を保存したり解析したりする** — `CST`ひとつが3つのオフセットを意味する
- ❌ **未来の約束をUTCで確定保存する** — 規則が変われば意図が壊れる側に固定される
- ❌ **地方時のカラムで並べ替え・比較する** — 違うものさしで測った値を数字だけ比べることだ
- ❌ **プロセスの環境変数(`TZ`)に地域を任せる** — プラットフォームによって静かに誤る (実測: ある実行環境で`America/New_York`が`+0100`と出た)
- ❌ **現在時刻だけでテストする** — この種の回帰を原理的に捕まえられない
- ❌ **tzデータの更新を抜いてデプロイする** — 未来の計算が静かに誤ったまま運用される
- ❌ **オフセットを時間単位の整数でスキーマに埋める** — 45分・秒単位のオフセットが実際に存在する
