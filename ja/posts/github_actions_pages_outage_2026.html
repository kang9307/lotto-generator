序論: 赤いワークフローより怖いもの

大規模障害が起きると画面はたいてい赤く染まる。失敗したジョブ、再実行ボタン、キューに刺さって動かないジョブ。ところが2026年8月6日のGitHub Actions障害で最も高くついた損失は、赤い印ではなかった。そもそも一覧に現れなかった実行のほうだ。

GitHubはインシデントを閉じる際に、プッシュやプルリクエストを含む一部のワークフロートリガーイベントが処理されず、自動的に再生できないと告知した。失敗は見えるが不在は見えない。チェック一覧が空のコミットは、通過したコミットと画面上で区別がつきにくい。そしてそのコミットがマージされれば、障害が終わっても結果だけが残る。

この記事は障害報道ではない。事件そのものは短くまとめ、デプロイ経路全体を一社に預けるという決定が実際にどんな費用を請求するのかに踏み込む。何が止まり何が回り続けるのか、ステータスページが正常なのに自分だけ落ちるときどう切り分けるのか、そして趣味のサイトがマルチクラウドを組むのがなぜ損なのかまで扱う。

この記事はActionsの使い方の記事ではない。ワークフロー構文、トリガーの種類、ジョブとステップの構成といった基礎はGitHub ActionsとCI/CD - Git & GitHub コラボレーションマスター 第5編で扱った。ここではそのワークフローが回る土台が止まったときの判断だけを取り上げる。

1. 公式記録だけで組んだタイムライン

事後記事やコミュニティの要約は時刻が少しずつ食い違う。以下はGitHubステータスページのインシデント更新に残った内容だけを抜いたものだ。時刻はすべてUTCで、日本時間はここに9時間を足せばよい。

1.1 開始と終了

  • インシデント開設: 2026年8月6日15時22分UTC。最初の文言はActionsの性能低下の報告を調査中というものだった
  • 影響等級: critical。構成要素はActionsとPagesの二つが記録された
  • 緩和宣言: 8月7日00時05分UTC。その直前の00時01分に、システム全体のキューが空になり新しいジョブが処理され始めたという更新が出ている
  • インシデント終了: 8月7日02時04分UTC。全体の窓は10時間42分になる
  • 日本時間では8月7日午前0時22分開始、同日午前11時4分終了だ。日本の勤務時間が始まるころにはすでに回復の尾の区間に入っていた

1.2 Pagesが二度上下した区間

Pagesは最初からインシデントに入っていたわけではない。30分ほど遅れて合流し、いったん正常に戻ってからまた落ちた。

1.3 回復曲線が教えてくれること

成功率が30〜40パーセントから65パーセントへ、さらに97パーセントと99パーセントへ上がった経路は、スイッチを入れ直せば戻る類の復旧ではなかったという意味だ。キューを空けながら正常処理の割合を少しずつ引き上げる形であり、だから中間地点で個々の利用者が体感する結果は運任せだった。

  • 回復局面でGitHubはWebhookの処理量を意図的に絞った。回復を助けるための措置で、一時は処理量が通常の15パーセント程度という更新があった
  • Webhookが絞られているあいだ、プッシュやプルリクエストは新しいワークフロー実行を生み出せなかった
  • 回復局面で言及された他の影響対象には、Copilotコードレビュー、Copilotコーディングエージェント、ホステッドランナー、セルフホストランナー、Webhook配信、GitHub Enterprise Importerの移行があった
  • セルフホストランナー側には、登録時にエラーやレート制限が出る可能性があるという案内が別に出た。ランナーを自分側に置いても制御プレーンへの依存は消えないという事実がここで露わになる

2. ActionsとPagesが止まると実際に止まるもの

備えを設計するにはまず影響の境界を正確に引く必要がある。ここでよくある誤りが二方向に出る。一つはGitHubが死ねば全部死ぬと決めつけること、もう一つは静的サイトだから関係ないと決めつけることだ。どちらも違う。

2.1 止まるもの

  • 新規デプロイ。PagesのデプロイをActionsのワークフローで回しているなら、デプロイはすなわちCIだ。Actionsが止まれば新しい記事も新しいバージョンも上がらない
  • マージゲート。必須ステータスチェックを掛けたリポジトリは、チェックが回らないあいだマージが止まる。これはむしろ安全装置が正しく働いた結果だ
  • リリース自動化。タグを押すとビルドして署名して成果物を添付する流れは丸ごと止まる
  • 予約ジョブ。cronスケジュールで回る整理・バックアップ・レポートのワークフローは、その時間帯の実行分がそのまま消える。待って後で回るわけではない
  • Actions APIに依存する監視ツール。実行状態をAPIで読んでダッシュボードに描いていたものがエラーを受け取る
  • コンテナイメージのビルド・プッシュの流れ。レジストリが生きていても、イメージを作って押し込む主体がActionsなら結果は同じだ

2.2 止まらないもの

  • すでにデプロイされ別の場所で配信中の成果物。ビルド成果物を自前サーバーや別のCDNに上げてあるなら、その配信経路はActionsと無関係に回り続ける
  • ローカル開発。クローン済みのリポジトリでブランチを切り、コミットし、テストを回すことはすべてローカルでできる。Gitはもともと分散バージョン管理だ
  • すでに取得済みの依存。ロックファイルとキャッシュがあれば、外部レジストリが生きているかぎりビルド自体は手元で再現する
  • 別のCIに掛けたパイプライン。リポジトリはGitHubに置きつつビルドを別のランナーで回す構成なら、ソースにアクセスできれば進み続ける

2.3 今回はっきり分かれなかった境界

いちばん知りたい点がまさに公開記録では分かれない。Pagesが低下したという表示は新規デプロイだけが止まったのか、すでに公開されたサイトの配信まで揺れたのかがそれだ。ステータスページの文言は二つの状況を区別して書いていない。コミュニティスレッドに上がった報告はデプロイ失敗のほうが圧倒的に多かったが、それは利用者報告の分布にすぎず、配信が無事だった証拠ではない。

実務ではこの区別が備えの設計を丸ごと変える。次の表は二つの場合を分けたものだ。

区分デプロイだけ止まる場合配信まで揺れる場合
利用者の体感サイトは開き、中身が古いままサイトが開かない、または断続的にエラー
損失の性質鮮度の損失。たいてい取り返せる売上と信頼の損失。取り返せない
合理的な備え成果物の保管と再実行で足りる配信経路の二重化の検討が正当になる

まとめるとこうだ。配信まで揺れた事例が確認される前に、配信二重化を前提として予算を使わないほうがいい。一方、デプロイが半日止まっても耐えられるようにする側は、ほとんど費用がかからない。

3. この障害の本当の請求書 - 消えたトリガー

10時間以上失敗したワークフローは回し直せばいい。本当のコストはそのあとに来る。

3.1 Webhookのスロットリングが作った静かな失敗

ワークフローは勝手に回らない。プッシュやプルリクエストといった出来事が実行を生み出す。その配信経路が回復を助けるために絞られていて、絞られているあいだに発生した出来事の相当数はあとで配信されるキューに積まれたのではなく、そのまま処理されなかった。

そこから出てくる結果がこうだ。

  • コミットはリポジトリに正常に入っている。コードは一つも失っていない
  • ところがそのコミットに付くチェック一覧が空だ。失敗ではなく不在である
  • 必須チェックを掛けていないリポジトリなら、その状態でマージされる。レビュアーは赤い印がないので問題を感じない
  • リント・テスト・セキュリティスキャンが丸ごと飛ばされたコミットがデフォルトブランチに入る
  • 数日後に別の理由でCIが回り、そのコミットの問題が出て、原因は見当違いの最新変更に指さされる

GitHubの案内は明確だった。新しいコミットをプッシュするか、プルリクエストを更新するか、可能ならワークフローを手動で再実行してトリガー行為そのものを繰り返せというものだ。自動再生がないという文がそこに付く。

3.2 障害が終わったあと必ず洗うもの

インシデントが閉じたから仕事が終わったわけではない。以下は終了後に人が確認すべき一覧だ。

  • 障害の窓の内側に入ったコミット一覧。時刻をUTCに合わせ、その区間のデフォルトブランチのコミットを抜く
  • チェック一覧が空のコミット。失敗したものではなく、何も付いていないものを探す。これが核心だ
  • その区間にマージされたプルリクエスト。承認は人がしていても自動チェックは回っていない可能性がある
  • 予約ワークフローの欠番。毎日回るバックアップや整理作業が一日分抜けたかを見る。これは失敗通知も来ない
  • デプロイ状態と実際の配信内容の一致。最後の成功デプロイが本当に最新のソースかを確認する
  • 途中でキャンセルまたは強制終了したジョブの後片付け。ロックファイル、一時リソース、途中まで上がった成果物が残っている可能性がある

いちばん安い方法は、障害区間の直後にデフォルトブランチへ空コミットを一つ押して全ワークフローを一度回すことだ。これで少なくとも現在のHEADがチェックを通るかは確実になる。ただし途中で挟まってマージされた個々のコミットの問題はこの方法では捕まらないので、上の一覧は別途洗う必要がある。

4. ステータスページは緑なのに自分のワークフローだけ落ちるとき

今回のように等級がcriticalまで上がれば判断は簡単だ。難しいのはステータスページが正常なのに自分だけ動かない状況のほうだ。実務ではこちらのほうがはるかに頻繁に来る。

4.1 順番に絞り込む

  • 第1段階。同じワークフローを最近成功させた実行があるかを見る。なければ自分の変更が原因の確率が高い
  • 第2段階。別のリポジトリの無関係なワークフローを一つ回してみる。それも動かなければアカウント・組織範囲の問題だ
  • 第3段階。失敗地点がジョブ開始前か開始後かを分ける。開始前ならランナー割り当てとキュー、開始後なら自分のスクリプトだ
  • 第4段階。同じコマンドをローカルで回す。ローカルで再現するならインフラ障害ではない
  • 第5段階。ここまで来て原因が出ないなら、そのときステータスページとコミュニティのインシデントスレッドを見る

順番をこうする理由は単純だ。ステータスページは常に遅い。今回も利用者の症状と最初の調査告知のあいだに時差があり、等級が最終水準に上がるまでに1時間以上かかった。ステータスページが緑だという事実は障害でない証拠ではなく、まだ集計されていないという情報にすぎない。

4.2 自分側が原因のときに出る信号

  • 失敗が特定のジョブや特定のステップにだけ集中する
  • エラーメッセージが具体的だ。モジュールが見つからない、権限がない、といった調子である
  • 同じコミットを回し直しても同じ地点で同じメッセージで死ぬ
  • 最近アクションのバージョン、ランナーイメージ、依存のロックファイルのどれかを変えた
  • 別のリポジトリのワークフローは問題なく回る

4.3 提供者側が原因のときに出る信号

  • ジョブが実行されもせずキューに長く留まる
  • エラーが漠然としている。ランナーがジョブを取得できなかったという調子の文が出る
  • 再実行のたびに失敗地点が変わる。決定論的でないというのは強い手がかりだ
  • 自分のコードと無関係なワークフローも一緒に失敗する
  • Web UIやAPIの応答が普段より遅い、または断続的にエラーを出す

障害中にやると状況をさらに悪くする行動。失敗したからと反射的に全体再実行を繰り返すことだ。回復が階段状に進む局面で大量の再試行はキューをまた膨らませ、自分の回復も遅らせる。今回の事例でも回復はキューを空けながら成功率を引き上げる方式で進んだ。再実行は成功率が目に見えて上がったあとにまとめてやるほうがいい。

5. 自分のデプロイ経路に単一障害点はいくつあるか

ここからが本論だ。GitHubにデプロイを掛けるという決定は悪い決定ではない。ただしその決定が実際にいくつの枠を一社に寄せているかは数えてみる必要がある。

5.1 四つの枠に割る

デプロイ経路はおおむねこの四つに分かれる。

  • ソース保管。コードが住む場所。リモートリポジトリ
  • トリガー。出来事を実行に変える層。Webhookとスケジューラ
  • 演算。実際にビルドとテストを回すマシン。ランナー
  • 配給。できた成果物を利用者に届ける場所。ホスティングとCDN

典型的な構成でこの四つがどう配置されるかを見れば、なぜ一社の障害がデプロイ全体を止めるのかがすぐ見える。

  • ソース保管 = GitHub
  • トリガー = GitHubのWebhook
  • 演算 = GitHubホステッドランナー
  • 配給 = GitHub Pages
  • 四つとも同じ会社。この構成で単一障害点の数は1ではなく4だ

5.2 セルフホストランナーが減らしてくれる枠

ランナーを自前インフラに移せば演算の枠が抜けそうに見えるが、今回の事例がその期待を正確に反証している。セルフホストランナー側でも登録時のエラーやレート制限が報告され、自前のKubernetesクラスタで回るActions Runner Controllerのランナーはアイドル状態で固まり、人がポッドを消すかアプリケーションを再デプロイする必要があった。

  • ランナーが自分のインフラにあってもジョブを割り当てる制御プレーンは依然としてGitHubだ
  • だからセルフホストは演算の容量と環境を自分のものにする手段であって、制御プレーン依存を断つ手段ではない
  • むしろ障害時に復旧すべき対象が一つ増える。固まったランナーポッドを片付けるのは自分の仕事だ
  • セルフホストの正当な理由はセキュリティ境界、社内網アクセス、特殊ハードウェア、コストだ。可用性はその一覧にない

6. 備えごとのコストと効果

備えは全部やるか全部やらないかではない。ほとんど費用のかからないものからかなり高いものまで層があり、たいていは下の三行で終わる。

6.1 安いものから

備えの手段かかるコスト今回の型の障害での実効果推奨対象
ビルド成果物をアーティファクトで保管ほぼ0。ワークフロー数行高い。ビルドし直さず手で上げられる全員
ローカルで同じコマンドでビルドできる状態を保つ低い。規律の問題高い。CIなしでも成果物を作れる全員
ステータスページの通知購読0中。原因の切り分け時間を減らす全員
必須ステータスチェックの強制0。設定一度高い。チェック不在コミットのマージを防ぐ全員
障害後のコミット洗い出し手順の文書化低い高い。消えたトリガーを捕まえる唯一の方法チーム以上
デプロイスクリプトのCIからの分離中。リファクタ一度中〜高。人手で同じデプロイができる売上が掛かるサービス
他のCIへ移せるワークフローの維持中。二重管理中。移行に時間がかかり当日の障害には間に合わないチーム以上
配給経路の二重化(別ホスティング常時待機)高い。DNS・証明書・同期配信が死ぬ型にのみ有効可用性が売上の場
リポジトリ自体の常時ミラー高い。権限・フック・Issue同期低〜中。今回の型にはほぼ無効規制・契約要求のある場

6.2 表から読むべき一行

表の上四行はコストが事実上0なのに効果が高い。下の二行はコストが大きく今回の型には効果が限定的だ。ところが障害直後に人々が議論し始めるのはたいてい下の二行のほうだ。順番が逆である。

  • アーティファクト保管はワークフローにアップロードのステップを一つ足す作業だ。障害中でも最後の成功ビルドの成果物が手元にある
  • ローカルビルドの再現性は別途のツールではなく習慣だ。CIでしか回らない魔法のような手順を作らなければ自然に保たれる
  • 必須ステータスチェックは今回の障害の核心的損失であるチェック不在コミットを構造的に遮断する。チェックが回らなければマージできないので人が気づく
  • デプロイスクリプトをCI構文から切り離しておけば、同じスクリプトをノートPCで実行して急ぎのデプロイができる

7. どこからが過剰か - 規模別の線引き

大型障害のあとには必ず過剰対応がついてくる。マルチクラウドはほとんどの場合で損だ。損である理由を正確に押さえてこそ議論が終わる。

7.1 趣味・個人サイト

  • 半日デプロイが遅れても失うものがない。損失そのものが0に近いのに備えに金と時間を入れれば純損失になる
  • 二重ホスティングを常時維持すると構成自体が新しい故障要因になる。DNS切り替え、証明書の二組、リダイレクト規則、同期スクリプトが増える
  • 実際にほとんどの事故は障害ではなくこれらの部品で起きる。使わない予備経路は静かに腐る
  • ここでの合理的な上限は成果物の保管、ローカルビルドの維持、ステータス通知の購読の三つだ。すべて無料で、すべて今日終わる
  • あえてもう一つやるなら、静的な成果物を圧縮して別のリポジトリやクラウドストレージに定期的に落としておく程度だ

7.2 売上が掛かった小規模サービス

  • 基準が変わる。デプロイが止まることとサービスが開かないことを分けて値付けする必要がある
  • デプロイ遅延はたいてい耐えられる。半日遅れた機能デプロイで会社が揺れることは稀だ
  • 配信停止は違う。ここには二重化が正当になる。ただしその場合の備えの対象はCIではなくホスティングとDNSだ
  • つまりこの規模でもCIの二重化はたいてい無駄だ。金は配信経路のほうに使うのが正しい
  • 実質的に値打ちが大きいのはデプロイスクリプトをCI構文から分離しておくことだ。障害中でも人が同じ手順を実行できる

7.3 チーム・会社規模

  • ここからは損失が時間あたりで計算される。開発者数かける時間がそのままコストだ
  • それでも最初の投資は二重化ではなく手順だ。障害時に誰が判断しどの順で洗うかが決まっていれば損失の大部分が減る
  • リリース日程に余裕の区間を入れるほうが二重化より安く確実だ
  • CIの二重化を検討するならパイプライン全体の複製ではなく中核経路を一つだけ別のランナーでも回せるようにする形が現実的だ
  • 二重化した経路は定期的に実際に回さなければならない。回らない予備経路は障害当日に必ず失敗する

8. 自前ランナーを置けば解決するのか

前でも一度触れたが、今回の事例があまりに鮮明なので別立てで整理する。今回の障害でセルフホストランナーを使っていた側はより楽ではなかった。

  • ランナー登録の段階でエラーとレート制限が報告された。ランナープロセスは自分のサーバーにあっても、登録はGitHubと通信する必要がある
  • KubernetesでActions Runner Controllerを使ってランナーを回していた側は、ポッドがアイドル状態で固まる現象に遭った
  • GitHubの案内は固まったポッドをkubectlで消すかARCアプリケーションを再デプロイせよというものだった。そうすれば代替ランナーが自動的に生成される
  • つまり回復作業の最後の区間で人手が必要だったのは自前クラスタを持つ側だった
  • ホステッドランナーだけを使っていた側はキューが空くのを待てばよかった

この対比はセルフホストが悪いという意味ではない。セルフホストの理由の一覧から可用性を消せという意味だ。社内網リソースにアクセスする必要がある、特定のGPUが要る、長時間ジョブのコストが問題だ、コンプライアンス上ビルド環境を統制する必要がある。そうした理由ならセルフホストは正しい。ところがその理由で導入したあとに可用性まで良くなったと期待すると食い違う。

9. リリース日程に余裕を入れる実務

いちばん安い備えは技術ではなく日程だ。ただしこれは金曜デプロイ禁止のような話とは違う。

9.1 再試行予算という考え方

  • リリース計画にデプロイが最初に失敗すると仮定した余裕時間を明記しておく。数時間で十分だ
  • 余裕があれば障害中に無理に押し通す決定が出ない。無理な決定はたいてい余裕がないから出る
  • 外部告知が掛かったリリースはデプロイ完了と告知時刻を分離する。デプロイは先に、公開切り替えはあとで
  • 静的サイトなら成果物を先に作っておき公開だけあとにする形が自然だ
  • 規模の大きいリリースほどパイプラインの再試行回数が増える。余裕は規模に比例して取る

9.2 障害中に下してはいけない決定

  • チェックを一時的に切ること。急ぐからと必須ステータスチェックを解除すると、まさに今回の障害が作った損失を自分で作ることになる
  • パイプラインの大手術。障害中にワークフローを大きく直すと、あとで何が原因だったのかを分けられなくなる
  • 他のCIへの即席移行。準備なしの移行はその日のうちに終わらず、終わっても検証されていないパイプラインが残る
  • 大量再実行。回復局面でキューをまた膨らませる
  • 手動デプロイの痕跡を残さないこと。急いで手で上げたなら、何をどのコミットから上げたかを必ず記録する。次の自動デプロイがそれを上書きしうる

10. 確認できなかったこと

根拠が確保できなかった項目を一か所にまとめる。

  • 根本原因。GitHubは15時45分UTCの更新で障害の発生源を特定したと述べたが、それが何だったのかはインシデント終了の時点まで公開していない
  • 回復局面で言及された表現の位置づけ。有効でないジョブを割り当てられるランナー、アイドル状態で固まったARCポッドは症状と緩和対象として言及されたのであって、原因の記述として確認されてはいない
  • すでに公開されたPagesサイトの配信への影響。デプロイだけ止まったのか配信まで揺れたのかは公開された文言では分かれない
  • コミュニティで流れる原因の説明。負荷増加やインフラ移行を原因と指す話があるが出所がGitHubではない。本記事では事実として扱わない
  • 影響規模の絶対数値。いくつのリポジトリ、何件の実行が影響を受けたかについての公開数値は確認されていない
  • SLA補償の有無。このインシデントに対するクレジット方針がどう適用されるかは公開記録では確認できなかった
  • 事後詳細報告の発行有無と時期。本記事の執筆時点では出ていない。あとで更新されうる
  • Webhookスロットリング区間の正確な開始・終了時刻。15パーセントという数値は回復局面の更新に登場するが、絞り始めた時点と完全解除の時点が分単位で明示されてはいない

11. よくある質問

今回のGitHub障害はいつ始まっていつ終わったのか?

GitHubステータスページ基準で、インシデントは2026年8月6日15時22分UTCに開かれ、8月7日02時04分UTCに終了処理された。全体の窓は10時間42分になる。ただしこの数字をそのままダウンタイムとして読んではいけない。途中に緩和完了の時点が別にあり、システム全体のキューが空になり緩和されたという更新が8月7日00時05分UTCに出ている。その後の約2時間は、Actions Runner Controllerのランナーが遅れて回復する尾の区間を片付けるのに使われた。日本時間に直すと8月7日午前0時22分に始まり、同日午前11時4分に閉じた計算になるので、日本の勤務時間帯にはすでに終わっていた障害だ。

GitHubはこの障害の原因を公開したのか?

公開していない。ステータスページの更新には15時45分UTCに障害の発生源を特定し緩和作業中であるという文があるが、その発生源が何だったのかはインシデントが閉じるまで文章として出てこなかった。回復局面で言及された表現、たとえばもう有効でないジョブを割り当てられ続けるランナーや、アイドル状態で固まったActions Runner Controllerのポッドといったものは症状と緩和対象であって、根本原因の記述ではない。ネット上に流れているいくつかの説明は出所がGitHubではなくコミュニティの推測なので、事実として扱わないほうが安全だ。

障害中にプッシュしたコミットがCIを回せなかった場合はどうなるのか?

自動では戻らない。GitHubは最後の更新で、プッシュやプルリクエストを含む一部のワークフロートリガーイベントがインシデント中に処理されず、自動的な再生ができないと述べている。この場合は新しいコミットをプッシュするか、プルリクエストを更新するか、可能ならワークフローを手動で再実行して、トリガー行為そのものを繰り返す必要がある。実務で危ないのは失敗したワークフローではなく、一覧にまったく現れなかったワークフローのほうだ。赤い印は目につくが、実行そのものが存在しないコミットは画面上に痕跡がなく、チェックを通過したように見えてしまう。

すでに公開済みのGitHub Pagesサイトは表示され続けたのか?

この点は公開記録では判別できない。Pagesはインシデントの構成要素として上がり、性能低下と正常のあいだを行き来したが、公開された更新の文言は、新規デプロイが止まったのか、すでに公開されたサイトの配信まで影響を受けたのかを区別して書いていない。コミュニティスレッドに報告された症状はデプロイ失敗のほうが圧倒的に多かった。ただしそれは利用者報告の分布にすぎず、配信が無事だった根拠にはならない。したがって本記事は配信無事を前提にした判断を一切行わず、確認できなかった項目として分けて置いている。

個人ブログでも別のホスティングを用意しておくべきか?

おおむね不要だ。趣味や個人のサイトで二重ホスティングを常時維持すると、その構成自体が新しい故障要因になる。DNS切り替え、証明書の二組、リダイレクト規則、同期スクリプトが増え、たいていは障害ではなくこれらの部品が先に問題を起こす。半日デプロイが遅れても損が出ないサイトなら、合理的な備えは三つで足りる。一つ、ビルド成果物をアーティファクトとして残し、作り直さなくて済むようにする。二つ、ローカルで同じコマンドでビルドできるかをときどき確認する。三つ、ステータスページの通知を購読して、障害なのか自分のミスなのかを判断する時間を減らす。

結論: 今日持ち帰る三つ

第一に、今回の障害の損失は失敗ではなく不在だった。10時間以上赤く染まったワークフローは回し直せば済む。問題はトリガー自体が処理されず実行一覧に何も残らなかったコミットで、それは自動では戻らない。障害が終わったあとその区間のコミットを人が洗う手順があるかないかが実際の損失を分ける。

第二に、単一障害点の数は会社の数ではなく枠の数で数える。ソース・トリガー・演算・配給の四つの枠が一社に寄っていれば、その会社の障害がデプロイ全体を止める。そしてランナーだけ自分のインフラに移してもトリガーと制御プレーンはそのまま残る。今回、自前クラスタを持つ側のほうが手でポッドを片付ける羽目になったのがその証拠だ。

第三に、備えの費用対効果の順序をひっくり返すな。成果物の保管、ローカルビルドの再現、必須ステータスチェック、障害後の点検手順。この四つは事実上ただなのに今回の型の損失をほとんど防ぐ。一方、配給経路の二重化とリポジトリのミラーは高くつき、今回のようにデプロイが止まる型には効果が限定的だ。ところが障害直後の会議で先に出てくる話はいつも高いほうである。

最後に一つ。ステータスページの緑は正常だという証拠ではなく、まだ集計されていないという情報だ。今回も利用者の症状と告知のあいだ、告知と等級引き上げのあいだに時差があった。だから切り分けは常に自分の側から始めるべきだ。同じコマンドをローカルで回すのにかかる数分のほうが、他人のステータスページを更新しながら過ごす1時間よりましだ。
