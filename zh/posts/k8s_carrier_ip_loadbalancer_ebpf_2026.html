在云之外自建LoadBalancer意味着什么

从EXTERNAL-IP停在pending，到ARP代答与非对称路由

2026年7月28日 开发/基础设施

引言：EXTERNAL-IP一动不动的那天

从托管Kubernetes转到本地机房或家庭实验室的人，几乎都会遇到同一个画面。创建了一个type: LoadBalancer的服务，过了好几分钟，EXTERNAL-IP那一列仍然是等待状态。

$ kubectl get svc web
NAME   TYPE           CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
web    LoadBalancer   10.96.31.10    <pending>     80:31942/TCP   12m

多数人此时开始翻日志。但这里并没有需要修的错误。这不是失败，而是缺少对手方。Kubernetes官方文档把这一点写得很明白：如果云提供商支持负载均衡器，就会为服务配置一个外部地址，而分配该地址的责任在云提供商。没有这个对手方，也就没有可填的值。

2026年7月出现在GeekNews上的一篇文章，把这个抽象问题变得非常具体。为了把运营商通过DHCP下发的IPv4地址用作Kubernetes LoadBalancer的外部地址，作者写了一个不把地址挂到网卡上的DHCP客户端，用eBPF代为应答ARP，最后还得处理非对称路由。这可以当作一篇成功记录来读，但我认为它真正的价值在别处：它诚实地展示了云上一个复选框背后，究竟藏着多少互相独立的层。

所以本文不是某个实现的介绍。它把在非云环境中要让LoadBalancer类型的服务成立，究竟需要自己完成什么逐层拆开，说明每个选项各自要付出的代价，以及出问题时该从哪里看起。无论最终用的是MetalLB、Cilium还是自己写的守护进程，理解下面这套结构都会让判断快得多。

1. 云上是谁发放IP - type LoadBalancer的真实约定

1.1 Kubernetes并不创建地址

先澄清一个误解。Kubernetes里面并没有实现负载均衡器的代码。把服务声明为type: LoadBalancer，与其说是下达指令，不如说是提交一份请求。实际发生的过程是这样的：

  • 用户创建一个type LoadBalancer的服务
  • 外部控制器观察到这个请求，在云上就是cloud-controller-manager
  • 控制器在自己的环境中取得地址，并准备真正的负载均衡资源
  • 把取得的地址写入服务的status.loadBalancer.ingress
  • 这时kubectl get svc的EXTERNAL-IP列才被填上

也就是说EXTERNAL-IP是汇报结果的一栏，而不是下达命令的一栏。接受这一点之后，本地环境要做的事就自动确定了：必须自己立起一个能填上这个状态字段的主体。

1.2 想指定特定地址的时候

过去可以用spec.loadBalancerIP请求特定地址，但该字段目前在文档中标记为已弃用，原因是各实现的解释不一致，且无法表达双栈场景。现在改用下面两种方式：

  • 各实现自定义的注解 — 按每个控制器定义的方式指定地址或地址池。可移植性差，但表达力强
  • spec.loadBalancerClass — 当集群中同时存在多个负载均衡实现时，指定由哪一个来处理该服务。在本地环境中让MetalLB与其他控制器共存时尤其有用

1.3 本地环境里出现了两件事

这是全文最重要的区分。在云上看起来是一整块的事情，到了本地就分成性质完全不同的两项工作。

  • 分配 — 给这个服务哪个地址。这是IPAM问题：管理地址池并且不重复地发放
  • 通告 — 怎样把发往该地址的流量牵引到自己的集群。要么是链路层的ARP与NDP，要么是网络层的路由协议

两者互相独立，而Cilium把这种分离做成了结构。按其官方文档，LB IPAM只负责从CiliumLoadBalancerIPPool中挑选地址并分配给服务，真正把地址通告出去的工作由BGP控制平面或L2 Announcements这类独立功能承担。MetalLB在内部也是同样的结构。

本地排障之所以困难，原因就在这里。EXTERNAL-IP出现了地址，只说明分配完成，完全不能保证这个地址可以访问。地址有了却连不上的情形，绝大多数发生在通告层。

层次云上由谁完成本地由谁完成失败时的症状
地址分配（IPAM）云提供商MetalLB地址池、Cilium LB IPAM、自研控制器EXTERNAL-IP卡在等待状态

表中最后两行是本地环境里最折磨人的项目。按官方文档，externalTrafficPolicy默认值Cluster会路由到所有端点，而Local只发往本节点上的端点，同时保留客户端源IP。需要在访问日志中记录真实来访地址的服务离不开这个设置，但正如后文所述，Local有时会与通告层冲突。

2. 本地方案的三条路径 - 二层通告、BGP与自研

在本地解决通告问题的方法大致有三种。按在哪一层替别人说话来分类，比按产品名分类更容易理解。

2.1 二层模式 - 在链路层代为应答

这是使用最广的方式。照搬MetalLB官方文档的说法，在这种模式下集群中的一台机器取得服务的所有权，并使用标准的地址发现协议（IPv4用ARP，IPv6用NDP）让这些IP在本地网络上可达。技术上就是让那个节点看起来像在自己的网卡上持有多个地址。

优点很明确：不需要动路由器。交换机也不必知情。在办公室或家庭实验室这类对网络设备权限受限的场景中，这实际上是唯一现实的选择。但文档指出的代价同样明确。

  • 带宽上限就是一个节点。用文档的话说，发往某个服务IP的全部流量都会去往一个节点。增加节点并不会提高该服务的入向带宽
  • 故障切换取决于客户端。MetalLB会发送非请求的链路层报文来通告MAC变更，多数现代操作系统能在数秒内生效，但实现不佳的客户端会一直向旧MAC发送，直到缓存过期
  • 对于计划内切换，文档建议让旧的主节点再存活一段时间，以便替缓存陈旧的客户端转发几分钟流量
  • 主节点选举是无状态的。每个speaker各自计算一份对节点与VIP做哈希后的有序列表，排第一就负责通告。新增节点可能导致主节点变更
  • 文档明确提到网络分区时的脑裂风险。若彼此误判对方已失效，可能出现多个speaker同时通告同一个VIP，或者没有任何一个通告

Cilium的L2 Announcements处在同样的物理规律之下。其文档写明，由于ARP与NDP的特性，主机对每个IP只保存一个MAC，因此集群中只能有一个节点应答，于是每个服务对应一个Kubernetes Lease，由持有者负责应答。不过这个功能附带了不少在实践中容易踩到的条件：

  • 文档标注为测试版，且必须启用kube-proxy替代模式
  • Lease的获取是先到先得，文档指出这可能造成节点之间负载不均
  • 明确写明与externalTrafficPolicy: Local不兼容，因为服务IP可能在没有容器组的节点上被通告，导致流量被丢弃。如果需要保留源IP，这个组合从一开始就应当回避
  • 不接受免费ARP的客户端要等到自身表项老化才会重新查询，因此可能经历比租约时长更久的中断

kube-vip在ARP模式下也使用同样的原理。按其文档，虚拟IP在节点之间迁移时会广播免费ARP以更新IP与MAC的对应关系，主节点选举同样基于Kubernetes Lease。无论实现是什么，链路层能做到的事情，上限都是一样的。

2.2 BGP模式 - 把路径告诉路由器

在BGP模式下，每个节点与邻近路由器建立对等会话，通告通往服务IP的路径。路由器把多个节点视为等价路径并用ECMP分担。二层模式的单节点瓶颈随之消失，还能借助路由器策略做更细的控制。

但这里藏着本地负载均衡中最常被低估的陷阱，MetalLB文档对此直接提出了警告。路由器通过对报文头部的若干字段做哈希来选择下一跳，常见的是三元组（协议、源IP、目的IP）或再加上端口的五元组，目的是让同一会话的报文落到同一个节点。问题出在下一步。

后端集合的规模一旦变化，现有连接会被近乎随机地重新哈希。—— MetalLB BGP文档

重启一个节点，或者一条BGP会话断开，就在那一刻，与该节点毫无关系的连接也会被重新分配到别的节点。新节点上没有这些连接的状态，通信随即中断。文档给出的缓解手段更像是妥协而非解决：在路由器上使用具有弹性的ECMP哈希、把工作负载固定到特定节点、在流量低谷期做变更、通过DNS在服务之间迁移、增加客户端重试逻辑、引入入口控制器层，以及对非关键服务接受偶发的连接重置。

实践中最可行的答案通常是最后两项的组合：只用BGP暴露少数几个入口控制器，把真正的应用放在它们后面。这样重新哈希的影响范围就被限制在入口层。

2.3 自研 - 当既有工具的前提不成立时

第三条路径是自己动手。听起来鲁莽，但当工具所依赖的前提在自己的环境里根本不成立时，有时也只剩这一个选择。本次的案例正是如此。

MetalLB的前提是运维人员知道地址池。用文档的话说，MetalLB无法凭空造出IP地址，所以必须由管理员提供地址池。而在通过运营商DHCP获取地址的环境中，这个前提不成立：事先无法知道会拿到哪些地址，而且它们还可能变化。项目的问题跟踪里长期挂着对接外部IPAM与DHCP的诉求，但要支持动态分配就得改动包括单线程假设在内的内部结构，因此一直没有实现。

3. 运营商线路上会变的东西 - DHCP带来的限制

开始之前。不同线路套餐在可用地址数量、是否允许运行服务器、静态地址的提供条件上都不相同，这些由合同与服务条款约定。技术上可行与合同上允许是两回事，因此在动手搭建之前先阅读条款，必要时向运营商咨询，才是正确顺序。本文讲的是网络的工作原理与排查方法，不涉及绕开运营商政策的做法。

3.1 DHCP地址是租用而非拥有

这是最根本的限制。RFC 2131把客户端标识符或硬件地址与所分配网络地址的组合，定义为该租约的唯一标识。而租约是有期限的。客户端在T1时刻以单播方式尝试续租，失败则在T2时刻改用广播重试。服务器若判断客户端对地址的认知有误，或租约已到期，就会发送DHCPNAK告知无效。

从服务地址的角度看，这个事实分量很重。地址发生变化不是故障，而是正常运行。因此设计必须把下面这些当作正常场景纳入：

  • 续租可能失败，地址可能被收回。那么使用该地址的服务会怎样
  • 重启或线路切换之后可能拿到另一个地址。DNS由谁来更新
  • 地址一变，证书、防火墙白名单、对外登记信息会同时失配
  • DHCP客户端进程一旦退出，租约会悄无声息地过期。它在监控范围内吗

3.2 一个地址对应一个MAC

第二个限制是标识。既然租约与标识绑定，要拿到多个地址就得用不同的标识分别发起请求。原文案例之所以创建多个虚拟网卡并让它们各持不同的MAC，原因正在于此：通过单个物理网卡自然地取得多份租约并没有现成的办法。

由此产生一个实务上需要留意的点。上游网络设备可能限制每个端口可学习的MAC数量，或把意料之外的MAC视为异常。这类策略是为了维持网络稳定而存在的正当机制，因此不应被当作规避对象，而应当作为设计约束接受，并事先确认。

3.3 网关与防火墙不属于你

第三个限制是控制权的边界。在云上，整个网络实际上都在自己的管理范围内；而在运营商线路上，默认网关之外全是别人的地盘。这条边界带来以下后果：

  • 源地址与预期不符的报文可能在上游被过滤掉。这正是后文非对称路由问题的根源
  • 某些端口可能在上游被阻断，而这一点仅凭本地设备的配置无法确认
  • 诸如QoS标记之类的头部字段可能在跨越边界时被改写。RFC 2474本身就假定码点可以在进入另一个域时被重新标记
  • 在互联网与广播业务捆绑的线路上，改动布线或配置可能影响到另一项业务

4. 代替地址应答ARP - 会坏掉什么，又能得到什么

4.1 为什么必须有人代答

ARP是IPv4网络中以广播方式发问的协议：持有这个IP的设备，请告诉我你的MAC地址。同一链路上的路由器或客户端要收到这个应答，才能发出以太网帧。由于服务IP并不是真实设备的地址，而是集群所主张的虚拟地址，如果没有人代它作答，这个地址在链路上就等同于不存在。

最简单的办法是把该地址真正挂到节点网卡上，让内核自动应答。但这种方式会带来本地环境特有的副作用：

  • 由于地址在本机存在，节点自身可能在内部就把发往该地址的流量处理掉
  • 内核可能把它选为源地址，导致出站报文带上意料之外的源IP
  • 如果对应端口没有监听者，内核会立刻返回连接拒绝，哪怕在静默丢弃更合适的场景下也是如此
  • 把同一个地址挂到多个节点上就会造成地址冲突

这就是原文案例中出现安静的DHCP客户端这一说法的由来。选择是只取得租约，但绝不把地址挂到网卡上。在Linux网络栈看来这个地址并不存在，上述副作用自然无从发生。代价是再也没有人来应答ARP，于是需要一个独立的应答装置。

4.2 代答之后随之而来的问题

一旦接管ARP应答，下面这些问题会同时到来。无论用什么工具，性质都一样。

  • 真相必须只有一个。主机对每个IP只缓存一个MAC，两个以上同时应答时后到者胜出。因此必须有机制保证应答者恰好只有一个，也就是主节点选举
  • 缓存不会立刻更新。主节点变了，客户端缓存在过期前仍会使用旧MAC，而且有些实现根本不接受免费ARP
  • 免费ARP会被怀疑。同样的手法也用于地址欺骗，因此忽略它是常见策略。发出去就以为已经生效，这个假设很危险
  • 会与安全功能冲突。动态ARP检测、端口安全这类交换机功能，本来就是为了阻止未经授权的地址主张而设计的。在这类环境中必须事先与网络管理员达成一致
  • 节点故障就是服务故障。二层模式下应答节点一旦宕机，在新主节点选出且缓存刷新之前，该服务不可达

顺带一提，Linux确实有arp_ignore、arp_announce、arp_filter等调节邻居缓存行为的参数，在多宿主配置中它们也确实会制造麻烦。但从未挂到网卡上的地址根本不在内核的管理范围内，这些开关帮不上忙。这正是需要一个独立应答器的原因，无论它跑在用户态还是XDP里。

5. 选择用eBPF与XDP来应答ARP

5.1 XDP位于协议栈之前

XDP是在网卡驱动接收路径的最前端，也就是报文进入内核网络栈之前执行eBPF程序的钩子。程序的返回值决定驱动接下来的动作。按内核文档，主要动作如下：

  • XDP_DROP — 丢弃报文并把它放回它到达时的接收环队列。最简单也最快
  • XDP_PASS — 交给常规的内核协议栈处理
  • XDP_TX — 把收到的报文从它进来的那张网卡原路弹回去，通常在修改报文内容之后返回该值
  • XDP_ABORTED — 表示程序出错，报文会被丢弃。正常代码不应返回这个值

为什么ARP应答器正好契合这里，也就一目了然了。收到ARP请求帧后，交换发送方与目标方、改写成应答格式，再以XDP_TX弹回去，即使内核协议栈根本不认识这个地址，链路上也会出现一份完整的应答。这与不把地址挂到网卡上的决定在逻辑上严丝合缝。

5.2 得到什么，付出什么

这种方式带来的好处是实打实的：

  • 地址不会暴露给协议栈。前面提到的源地址选择错误与非预期的连接拒绝都不会发生
  • 任何地址都能立刻纳入应答范围。无需改动网卡配置，更新映射表即可，很适合地址动态变化的环境
  • 没有协议栈负担。广播的ARP请求在入口就被处理，不必一路上送

反过来，代价同样明确：

  • 调试难度大幅上升。ip neigh和ip addr里没有任何痕迹。一个在链路上会应答、却不存在于主机配置中的地址，离开tcpdump几乎无从判断
  • 存在驱动依赖。原生XDP的支持情况因驱动而异，退回通用模式就达不到预期性能。虚拟化环境尤其需要确认
  • 处在观测工具的盲区。多数监控看的是协议栈之上的指标。在XDP里处理或丢弃的东西，不自己埋计数器就看不见
  • 运维人员的门槛更高。故障发生的那个时刻，有几个人能读懂这一层，直接决定实际恢复时间
归纳起来，eBPF与XDP对于如何应答ARP这个问题是个优雅的答案，但代价是系统的真实状态在标准工具中变得不可见。这是运维问题，不是性能问题。

6. 非对称路由 - 响应不走来时的那扇门

6.1 为什么会发生

从这里开始，是本地负载均衡搭建中最耗人的一段。症状总是相似：同一栋楼、同一台交换机下都正常，从外网访问就没有响应。

原因通常很简单。请求从某条路径进来，响应却从服务器的默认路由出去。服务器只看目的地址就在路由表中选择出口，默认并不考虑这个请求是从哪里进来的。在多线路、隧道、经过多台路由器的拓扑中，这种不一致会自然出现。

同一个局域网内为什么正常？因为响应不经过路由器，直接在链路层送达对端。只是路径太短，问题没有暴露出来而已。这种差异造就了内网正常、外网不通这一典型模式。

6.2 rp_filter - 那个静静丢包的开关

路径非对称本身并不总是问题。真正的问题始于中间某一方决定丢弃这个报文的时候。在Linux上作出这个决定的典型机制是反向路径过滤。按内核文档，各取值的含义是：

  • 0 — 不做源地址校验
  • 1 — RFC 3704的严格模式。把入向报文与路由信息比对，如果该接口不是最佳反向路径就判定校验失败
  • 2 — RFC 3704的宽松模式。只有当源地址经由任何接口都不可达时才判定失败

实践中还有两点必须知道。第一，实际生效的值是conf/all与conf/{接口}中的较大者。只把接口值调成0，然后困惑于关掉了为什么还不行，事故往往由此而来。第二，内核文档本身就说明若使用非对称路由或其他复杂路由，推荐使用宽松模式。也就是说调整这个值是有文档依据的选项，而不是旁门左道。

# 实际生效值取 all 与接口设置中的较大者
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.eth0.rp_filter

# 被丢弃报文的痕迹（条目随内核构建而异）
grep -i martian /proc/net/stat/* 2>/dev/null
nstat -az | grep -i -E 'InAddrErrors|InNoRoutes'

不过调低这个值，也意味着相应地放弃了对源地址伪造的防护。所以顺序很重要：先看路径能不能纠正，只有在结构上确实做不到时才放宽过滤。顺序反过来，就成了原因照旧、只把症状掩盖起来。

6.3 解决方案的几条路径

应对非对称大致有四种办法，正确答案随场景而变。

方法原理优点缺点适用场景
收敛为单一路径把入向路径合并为一条，从根上消除非对称最简单也最稳固放弃多线路的好处实际只有一条线路，或以简单为先
连接标记加策略路由把入向接口记录在连接上，回程时还原以强制出口在多线路下也能准确工作需要状态跟踪，规则会变复杂有两条以上线路且都对外提供服务
源地址转换在前端改写源地址，使响应必定折返实现容易且确定真实客户端IP从日志中消失源IP并不重要的服务
放宽反向路径过滤降低校验强度以容忍非对称立竿见影削弱防伪造能力，原因仍在结构上无法避免非对称时的辅助手段

实践中用得最多的是第二种，思路很简单：进来时把从哪里进来记在连接上，出去时取出这条记录来决定出口。在Linux上用防火墙的连接跟踪标记与策略路由规则组合实现。

# 只保留能看清概念的最小形式
# 1) 带标记的报文去查另一张路由表
ip rule add fwmark 0x64 lookup 100

# 2) 把该表的默认路由指向对应线路的网关
ip route add default via 203.0.113.1 dev eth1 table 100

# 3) 确认
ip rule show
ip route show table 100

# 4) 计算某个响应实际会从哪条路径出去
ip route get 198.51.100.7 from 203.0.113.10 mark 0x64

最后那条ip route get是这一段里最有用的命令，因为它不靠猜测，而是直接问内核。打标记与还原标记的部分在防火墙层用连接跟踪标记完成，也就是把值存在连接上、再在回程报文上还原。无论用nftables还是iptables，思路完全一致。

7. 原文案例选择的路 - DSCP打标及其代价

7.1 问题的形状

原文案例的拓扑更复杂一些。有一台接收运营商地址的边缘路由器，而集群位于隧道另一端的另一个位置。外部客户端的请求经边缘路由器进入集群，响应却试图从集群这侧直接走向互联网。于是报文的源地址与实际出口位置对不上，在上游网络被过滤掉。同一栋楼里的客户端因为在链路层就完成了通信，所以一切正常，这个差异让问题更加难以捉摸。

常规答案是上一节的第二种，即基于源地址的策略路由。但按原文记录，这种做法造成了反方向的非对称：发往本地网络客户端的响应也被绕回了边缘路由器。仅凭源地址无法表达这条连接是从哪扇门进来的，这个局限就此暴露。

7.2 为什么偏偏是DSCP

于是选定的方案是把入向点标识写进报文头部的DSCP字段。DSCP是RFC 2474定义的DS字段中的6位码点，原本用于选择报文在每一跳上获得的处理行为。流程概括如下：

  • 在边缘入向时，由eBPF把报文从哪个边缘进入标记到DSCP值上
  • 路径上的守护进程依据这个标记跟踪流
  • 响应出去时用策略路由送回它进来的那个边缘
  • 在离开进入运营商网络之前还原原本的DSCP值

不要误读最后一步。这不是为了隐藏什么，而是把内部信号约束在内部边界之内的卫生措施。DSCP本是服务于QoS策略的字段，随意约定的内部取值一旦流入别人的网络，对对方的策略而言就是毫无意义的输入。何况RFC 2474本身就假定码点可能在跨越域边界时被重新标记，这个值从一开始就不能当作端到端信号来信任。只在边界内使用、并在边界处还原，才符合协议的设计意图。

7.3 不要把它当成通用解

这是个聪明的解法，但照搬之前需要先掂量以下几点。

  • 可用的标记空间非常小。只有6位，其中一部分还有约定俗成的用途，实际可用取值更少。入向点一多很快就不够用
  • 可能与既有QoS策略冲突。若组织内已经用DSCP管理优先级，内部信号就会与QoS意图混在一起
  • 边界之外无法保证保留。中间设备可能改写该值，因此必须明确信任区间到哪里为止
  • 连接跟踪标记才是更标准的答案。如果问题能在同一台设备内解决，就没有理由把信息塞进报文头部
  • 诊断工具对这个值的呈现并不友好。故障当下若不知道查看步骤，定位会明显变慢

总之，这是在需要跨越多台路由器传递流信息这一相当特殊约束下得出的答案。绝大多数本地环境用上一节的连接标记加策略路由就已足够。借用别人的解法时，必须连同他的约束一起借来，这条原则在这里同样适用。

8. 故障排查顺序 - 先在哪里抓包

这套方案坏掉时最浪费时间的做法是从容器组开始查。这里的问题往往发生在低得多的位置。建议自下而上推进。

顺序检查对象观察位置正常表现异常信号
1地址分配kubectl get svc、控制器日志EXTERNAL-IP有值持续等待，说明控制器或地址池有问题
2ARP应答在客户端侧链路观察ARP来自单一MAC的一致应答无应答，或MAC不断变化
3请求到达节点物理网卡能看到SYN看不到则是上游路径或防火墙问题
4响应方向在同一位置观察反方向响应从同一张网卡出去从另一张网卡出去即为非对称
5内核判断ip route get、ip rule show、rp_filter算出的是预期路径算成默认路由，说明缺少策略规则
6节点内部转发节点内部网卡与数据平面状态能转发到后端只在特定节点上失败
7应用容器组日志、端点请求到达了应用走到这一步就是应用的问题

每一步用到的命令大致如下，示例地址取自文档专用网段。

# 第2步 - 谁在主张这个地址属于自己
tcpdump -ni eth0 arp and host 203.0.113.10

# 第3至4步 - 在同一位置一并观察请求与响应
tcpdump -ni eth0 host 203.0.113.10 and tcp port 80

# 第4步补充 - 确认响应有没有从别的网卡漏出去
tcpdump -ni eth1 host 203.0.113.10 and tcp port 80

# 第5步 - 不要猜，直接问内核
ip route get 198.51.100.7 from 203.0.113.10
ip rule show

再补充几条实务经验。

  • 两端同时抓。只看一侧，讨论就会卡在看起来发出去了却没收到。把客户端与服务器的抓包按时间对齐，才能确定报文在哪一段消失
  • 从ARP看起。这里无应答的话，再怎么看上层都是白费。反之MAC来回跳动，就是主节点选举或重复主张的问题
  • 把同网段与外网分开测试。内网通、外网不通是非对称路由的典型指纹
  • 过滤条件不要设得太窄。只按端口过滤会漏掉ICMP错误报文，而路径问题的线索常常就在那里
  • 先查变更记录。如果刚做过节点扩容、重启、内核升级或防火墙规则下发，原因候选会大幅收窄
  • 只在自己有管理权限的网络中抓包。未经同意记录他人通信可能带来法律问题

9. 那么该怎么选 - 按场景判断

把上述内容落到实际选择上，结果如下。绝大多数环境在前两行就结束了。

场景推荐起点理由注意事项
家庭实验室或小型办公室，没有路由器权限二层通告唯一无需路由器配置即可成立的方案每个服务只有单节点带宽，切换时缓存滞后
自行运维路由器，需要超过单节点的带宽BGP通告用ECMP分担到多个节点后端变动会重新哈希无关连接
拥有静态地址的本地机房固定地址池加二层或BGP既有工具的前提原样成立管理好地址池与实际分配段不要错位
地址会动态变化的线路先打通动态生效路径再决定固定地址池的前提被打破先看条款，把地址变更设计为正常场景
需要在日志中保留来访IP考虑externalTrafficPolicy: Local可以保留源IP与部分二层实现不兼容，注意容器组分布不均
服务数量持续增长引入入口或网关层一个外部IP服务于多个服务层次一多，故障点也随之增多

最后一行尤其值得强调。在本地环境滥用LoadBalancer类型服务，需要管理的外部地址会随服务数量线性增长。地址越稀缺，越应当把对外入口保持在少数，再在其后按域名分流，这样的结构要耐用得多。实际上在多数本地集群中，入口控制器前面放一两个LoadBalancer类型服务就足够了。

10. 纠正常见误解

  • EXTERNAL-IP显示pending是个缺陷 — 不是。这是没有控制器负责分配时的正常状态。本地环境需要自己立起这个角色
  • 装上MetalLB就跟云上一样了 — 分配与通告的问题解决了，但回程路径、源IP保留、故障切换依然是运维人员的活
  • BGP无条件优于二层 — 带宽上确实更优，但存在文档记载的局限：后端变动时重新哈希会切断无关连接，而且需要路由器运维能力
  • 用了eBPF就会变快 — 在这个语境下eBPF的好处不是速度，而是不触碰协议栈也能在想要的层次介入。代价是状态在标准工具中不再可见
  • 把rp_filter设成0就解决了 — 症状可能消失，但原因仍在，防伪造能力被削弱。人们还经常忘记生效值取all与接口值中的较大者
  • 内网能通，所以不是防火墙问题 — 恰恰是相反的指纹。同网段不经过路由器，路径问题自然不会暴露
  • DHCP拿到的地址反正也是我的 — 那是租用。它可能被收回，可用范围由线路条款约定
  • 反正在集群内部，QoS字段可以随便用 — 跨越边界可能被重新标记，还可能影响别人的策略。内部信号应当在边界处还原

结论

云上那一行type: LoadBalancer所做的事情，其实是至少五项工作的打包：取得地址、把地址通告到网络、把流量牵引到节点、在节点内部转发到后端、让响应沿来路返回。云把这五件事打包出售，所以我们以为它是一件事。一旦自己动手，就会发现每一件都是独立的问题。

这个案例之所以有意思，不在于技术栈有多花哨，而在于它准确指出了既有工具的前提在哪里破裂。MetalLB假定运维人员知道地址池，这个假定在绝大多数环境中都成立；但在地址动态获取的环境中就不成立了。确认在那个点上需要自己造什么的过程本身，就是在了解别人构建的抽象之下究竟有什么。

实用的结论反而很朴素。多数本地与家庭实验室环境用二层通告就够了，能运维路由器的话BGP是下一个选择。自研只在这两个前提明确破裂时才值得考虑，而且即便如此，把工作原理与排查步骤写成文档也属于实现范围。至于在运营商线路上搭建方案，确认条款要排在技术评估之前。在合同范围内设计出来的结构，才是最耐用的。

最后再说一点。这个领域的故障不会在应用日志里留下任何痕迹。报文在内核或上游网络中悄然消失，开发者看到的只是超时。所以如果决定运行这类方案，把检查ARP、路径与过滤的顺序事先练熟，比任何自动化都更实在。
