glob 与正则不同 - 星号含义分岔的那一刻

把同一个模式交给 ls 和 grep，得到的答案不一样。实际运行后确认的分岔口

2026年9月1日 开发/基础设施

ls ab* 给出的是以 ab 开头的名字。把同样四个字符放进 grep 'ab*'，连一个 ab 都没有的行也跟着出来了。既不是打错，也不是版本问题。在这两个位置上，* 属于两套不同的语法。

挑选文件名的那套语法叫 glob，用规范里的术语说是模式匹配记法。grep、sed、awk 这一侧用的是正则表达式。两边重叠的符号很多 — *、?、[...] 两边都有 — 带着一边的直觉去写另一边，就会得到不报错却是错的结果。麻烦就在这里。报错还能察觉，悄悄抓到别的东西这种事，往往上线之后才浮出水面。

下面的输出全部是实际运行后抄下来的。凡是答案会随 shell 版本或 shopt 设置变化的地方，都当场点明了。

本文所有输出都来自下面「运行环境」一节里写明的那一台机器。shell 的模式行为受 shell 种类、版本和 shopt 状态影响，所以在各自环境里先跑一遍再用会更稳妥。在别的 shell 上结果会反过来的地方，正文里都做了标记。

* — 「任意字符串」与「前一项零次以上」

先看用得最多的符号。把同一个 ab* 放进两边试了一下。

# glob - 由 shell 与文件名比对
$ ls ab*
ab.txt
abb.txt

# 正则 - 由 grep 与每一行比对
$ printf '%s\n' a.txt ab.txt abb.txt b.txt | grep 'ab*'
a.txt
ab.txt
abb.txt

glob 那边两个，正则这边三个。多出来的那一个是 a.txt，这正是关键。在 glob 里 ab* 是「a、b，然后任意字符串」。在正则里 ab* 是「a，然后 b 出现零次以上」。b 出现零次也算数，所以没有 b 的名字也被抓住了。

归纳一下。glob 的 * 是本身就带含义的符号。正则的 * 是让前面那一项重复的运算符，单独放着没有含义。正则里对应 glob 的 * 的写法是 .*，必须展开成「任意单个字符出现零次以上」才是同一个意思。

用去掉扩展名的短列表再确认一次，差别会更清楚。

$ printf '%s\n' a ab abb xabz | grep 'ab*'
a
ab
abb
xabz

$ printf '%s\n' a ab abb xabz | grep -E '^ab*$'
a
ab
abb
  • glob * = 任意字符串，包含空串，所以 ab* 也能匹配 ab 本身
  • 正则 * = 紧邻前一个元素重复零次以上。前面没有元素时，要么是语法错误，要么按字面量处理
  • 正则里想表达「任意字符串」要写 .*。. 是「任意单个字符」，* 是「重复它」
  • xabz 被抓到不是因为 *，而是因为部分匹配。这一点隔一节会单独讲

? 与 . — 指代单个字符的两种写法

两边都有表示「任意单个字符」的符号，只是用的字不同。glob 用 ?，正则用 .。而且在 glob 里 . 就是个句点，完全没有特殊含义。

# glob 的 ? - 恰好一个字符
$ ls ?.txt
a.txt
b.txt

# 在 glob 里 ? 连点也一并抓住。点在 glob 中只是普通字符
$ ls a?txt
a.txt

# 正则的 . - 这里也是一个字符，所以非点的东西同样会被抓到
$ printf '%s\n' a.txt axtxt aatxt | grep 'a.txt'
a.txt
axtxt
aatxt

最后这段输出在实际工作中经常闯祸。写 grep 'a.txt' 时人以为自己在找「a.txt 这个文件名」，而 grep 读到的是「a、任意一个字符、txt」。用正则去找文件名、域名这类含点的字符串时，必须写成 a\.txt 来转义那个点。反过来在 glob 里根本没有转义点的场合，它本来就不是特殊字符。

  • glob ? — 恰好一个字符。零个不行，两个也不行
  • glob . — 字面意义上的句点，无需转义
  • 正则 ? — 「前一项出现零次或一次」。在基本正则（BRE）里要写成 \?，在 grep -E 里直接写 ?
  • 也就是说 ? 这一个字符在两边干的是完全不同的活。glob 里是「消耗一个字符」，正则里是「让前一项可有可无」

锚定 — 整个名字还是其中一段

这个差别比 * 的含义差别更容易让人绊倒。glob 是与整个名字比对的，前后隐含地被钉死了。正则默认是部分匹配，只要出现在行里的某处就算命中。

# glob - 整个名字必须是 txt。没有这样的文件
$ ls txt
ls: cannot access 'txt': No such file or directory

# 正则 - 行里任何位置有 txt 就算命中
$ printf '%s\n' a.txt notes.log | grep 'txt'
a.txt

所以在正则里要表达「整个名字就是这个」，必须自己加上 ^ 和 $。上一节的 grep -E '^ab*$' 之所以把 xabz 甩掉，原因就在这里。反过来在 glob 里要表达「某处包含」，得两边都加 * 写成 *txt*。

[...] 在否定处分岔

方括号是两边最相像的部分。[abc]、[a-z]、[[:digit:]] 这类写法在 glob 和正则里含义相同，连 POSIX 字符类都是共用的。然而在否定这一处写法分岔了。

# glob 的标准否定写法是 [!...]
$ ls [!a]*.txt
b.txt

# bash 在 glob 里也接受 [^...] 作为否定
$ ls [^a]*.txt
b.txt

# 正则的否定是 [^...]
$ printf '%s\n' a.txt ab.txt b.txt | grep '^[^a]'
b.txt

# 在正则里 [!...] 不是否定，而是「! 或 a」这个集合
$ printf '%s\n' a.txt ab.txt b.txt '!x.txt' | grep '^[!a]'
a.txt
ab.txt
!x.txt

看最后这段输出，情况就清楚了。在正则里写 [!a]，得到的不是「不是 a 的东西」，而是「! 或 a」。它和意图正好相反地运行着，却不报任何错。

bash 的宽松会变成可移植性问题

ls [^a]*.txt 跑得挺好，于是很容易得出「glob 里也能用 [^...]」的结论。那是 bash 的扩展。把同一个模式交给 dash，结果是这样的。

$ dash -c 'cd /tmp/demo; echo [!a]*.txt'
b.txt

$ dash -c 'cd /tmp/demo; echo [^a]*.txt'
a.txt ab.txt abb.txt

彻底反了。在 dash 里 [^a] 不是否定，而是「字符 ^ 或字符 a」这个集合，于是它把以 a 开头的名字全都挑了出来 — 恰好把本想排除的东西选中了。而且这里同样连一行警告都没有。

目标系统上 /bin/sh 指向 dash 的情况并不少见。如果这种反转发生在删除或搬移文件的脚本里，结果会悄无声息地滑向最糟的那一端。

  • glob 用 [!...]、正则用 [^...]。只用这两种，在任何 shell 上含义都不会变
  • bash 接受 [^...]，并不等于可以用它。让测试通过的宽松，在可移植性上就是危险
  • 范围 [a-z] 受区域设置的排序规则影响。想稳妥就用 [[:lower:]] 这类字符类
  • [[:digit:]] 这类 POSIX 字符类两边通用。ls *[[:digit:]]*.txt 和 grep '[[:digit:]]' 都能跑

glob 不是文件名专用语法

只把 glob 理解为「在命令行上挑文件用的东西」，那只知道一半。bash 中使用 glob 的地方有四处，其中三处完全不涉及文件。

case 语句的每个分支

$ for v in report.log a.txt sub README; do
>   case "$v" in
>     *.log)  echo "$v -> log" ;;
>     *.txt)  echo "$v -> text" ;;
>     [A-Z]*) echo "$v -> uppercase-start" ;;
>     *)      echo "$v -> other" ;;
>   esac
> done
report.log -> log
a.txt -> text
sub -> other
README -> uppercase-start

case 的每个分支标签都是 glob。最后那个 *) 之所以能充当「其余全部」，也是因为 glob 的 * 匹配任意字符串。往这里放正则，多半哪个分支都不会命中。写 case $v in ^ab.*$) 就成了在找「以 ^ab 开头、以 $ 结尾的字符串」。

参数展开中的模式位置

$ p="/var/log/app/server.access.log"

$ echo "${p##*/}"
server.access.log

$ echo "${p%.*}"
/var/log/app/server.access

$ echo "${p%%.*}"
/var/log/app/server

$ n="v1.2.3-rc4"
$ echo "${n//[!0-9]/}"
1234

${v#pat}、${v##pat}、${v%pat}、${v%%pat}、${v/pat/rep}、${v//pat/rep} 里 pat 的位置全都是 glob。这里的 * 同样是「任意字符串」，而单字符版与双字符版（# 与 ##）的区别在于分别按最短和最长去截。

最后那个例子 ${n//[!0-9]/} 之所以能当作「删掉所有非数字字符」来用，也是靠 glob 的 [!...] 否定。顺带一提，dash 里根本没有 ${v//pat/rep}，会直接以 Bad substitution 死掉。${v#pat} 和 ${v%pat} 属于 POSIX，所以在 dash 里也能跑。

== 是 glob，只有 =~ 是正则

bash 里使用正则的地方只有 [[ x =~ re ]] 一处。紧挨着它的 [[ x == pat ]] 是 glob。两个运算符并排待在同一对方括号里，语法却不同，这正是此处的难点。

$ s="aXbXc"

$ [[ $s == a*c ]] && echo true || echo false
true

$ [[ $s =~ a*c ]] && echo true || echo false
true

$ [[ $s =~ ^a*c$ ]] && echo true || echo false
false

$ t="aaac"
$ [[ $t =~ ^a*c$ ]] && echo true || echo false
true

第二行是陷阱。往 =~ 里放了 a*c，却返回了 true。不是因为它表现得像 glob，而是因为正则 a*c 意为「a 零次以上之后跟一个 c」，光靠字符串里那一个 c 就成立了。因为是部分匹配，所以碰巧为真。只有加了锚的第三行才终于返回 false。

碰巧对的结果最难缠。它会通过测试、发布上线，等输入形态稍有变化时才第一次出错。用 =~ 时养成随手加锚的习惯更好。

作为补偿，也有只有 =~ 才能做的事：把匹配到的部分取出来。

$ v="v2.10.3"
$ [[ $v =~ ^v([0-9]+)\.([0-9]+)\.([0-9]+)$ ]] &&
>   echo "major=${BASH_REMATCH[1]} minor=${BASH_REMATCH[2]} patch=${BASH_REMATCH[3]}"
major=2 minor=10 patch=3

$ [[ $v == v*.*.* ]] && echo "matched, but no captured parts"
matched, but no captured parts

glob 没有捕获，== 只给真假。要拆版本字符串、要从日志行里抠字段，那都是正则的活，结果装在 BASH_REMATCH 数组里。第 0 个元素是匹配到的整体，从第 1 个开始是括号分组。

引号决定语法

同一行里，一个引号就能改变含义。这一节不谈shell 引号规则的全貌，只看glob 与正则分岔的那一部分。

$ f='report.log'
$ pat='*.log'

$ [[ $f == $pat ]]   && echo true || echo false
true

$ [[ $f == "$pat" ]] && echo true || echo false
false

$ re='^rep.*\.log$'

$ [[ $f =~ $re ]]    && echo true || echo false
true

$ [[ $f =~ "$re" ]]  && echo true || echo false
false

规则只有一条。把 == 或 =~ 的右边用引号括起来，它就不再是模式，而变成字面字符串。[[ $f == "*.log" ]] 问的是「文件名是否恰好是星号、点、l、o、g 这六个字符」，没有这样的名字，所以是 false。

=~ 这边中招的人更多。正则里有空格于是加了引号，结果突然什么都匹配不上了。把正则装进变量、不加引号地使用，才是标准写法。

  • [[ $f == *.log ]] — 右边是 glob 模式。真
  • [[ $f == "*.log" ]] — 右边是字面量。假
  • [[ $f =~ $re ]] — 按正则解释。这是推荐写法
  • [[ $f =~ "$re" ]] — 降级为字面量，正则元字符全部失效
  • 反过来，想做字面比较时就故意加引号。原样比较用户输入时很有用
  • 交给 grep、find 的模式一定要加引号，否则 shell 会抢先按 glob 展开

没有匹配项时模式会原样留下

这是 glob 独有的行为，也是脚本事故的常客。没有任何文件匹配模式时，shell 会把模式字符串原封不动地留下。

$ ls *.csv
ls: cannot access '*.csv': No such file or directory

$ for f in *.csv; do
>   echo "loop sees: [$f]"
>   [ -e "$f" ] && echo "  exists" || echo "  DOES NOT EXIST"
> done
loop sees: [*.csv]
  DOES NOT EXIST

明明没有 .csv 文件，循环却跑了一轮。而且 $f 里装的是 *.csv 这五个字符。拿它去 rm 或 mv 会发生什么，我就没有特意去试了。

办法有三个。

$ shopt -s nullglob
$ cnt=0; for f in *.csv; do cnt=$((cnt+1)); done; echo "iterations: $cnt"
iterations: 0

$ shopt -u nullglob; shopt -s failglob
$ for f in *.csv; do echo "$f"; done
bash: no match: *.csv

$ shopt -u failglob
$ for f in *.csv; do [ -e "$f" ] || continue; echo "processing $f"; done

最后那个是不依赖任何选项的做法，所以要在别人环境里跑的脚本用它更合适。nullglob 用着省事，但它是全局开关，在脚本中途打开会连别处指望的行为一起改掉。failglob 在交互式 shell 里抓打字错误很好用。

  • 默认（nullglob off）— 匹配不上就保留模式本身。这是最危险的默认值，但 POSIX 就是这么规定的
  • nullglob on — 匹配不上就什么都不留，循环跑零次
  • failglob on — 匹配不上就报错停下，输出 no match 且退出状态非零
  • 手工防御 — 在循环体第一行写 [ -e "$f" ] || continue，在任何 shell 上行为一致
  • 正则里压根没有这个问题。grep 找不到时输出为空、退出状态为 1，模式绝不会摇身变成数据

以点开头的名字

glob 还有一条正则没有的规则。开头的点必须被显式匹配。* 号称是「任意字符串」，却抓不到 .bashrc。

$ echo *
a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ echo .*
.bashrc .hidden

$ shopt -s dotglob; echo *
.bashrc .hidden a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ shopt -u dotglob
$ shopt globskipdots
globskipdots    on

$ shopt -u globskipdots; echo .*
. .. .bashrc .hidden

三件事一次显现出来。第一，* 会跳过隐藏文件。这是 shell 的特殊规则，并不是从 * 的含义里推导出来的。第二，打开 dotglob 之后这条规则消失，* 就全都抓了。第三，echo .* 输出里没有 . 和 ..，是因为 bash 5.2 新增的 globskipdots 默认是开着的。关掉它，旧行为就回来了。

最后这一条很重要。过去 rm -rf .* 这类命令曾导致连上级目录都被动到的事故。在 bash 5.2 以上默认已经堵住了，但在更老的 shell 上依然是敞开的。

  • glob — 开头的点被特殊对待。想抓 .bashrc，模式本身就得以点开头
  • 正则 — 没有这种规则。grep '.*' 会直接抓到 .bashrc
  • dotglob — 打开后 * 连隐藏文件一起包含。备份脚本里常常会开
  • globskipdots — bash 5.2 新设，默认 on，把 . 和 .. 从 glob 结果里剔除
  • 斜杠也类似。glob 的 * 不跨越 /。想抓下级目录，要么像 */*.log 那样写明层级，要么打开 globstar

find -name 是 glob，find -regex 是正则

find 把两套语法都装在一条命令里，所以是最容易搞混的地方。-name、-path 是 glob，-regex 是正则。而且连比对的对象都不一样。

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

$ find . -name 'deep.log'
./sub/deep.log

$ find . -regex 'deep\.log'

$ find . -regex '.*/deep\.log'
./sub/deep.log

$ find . -name 'sub/*'

第三条命令什么都没输出，这就是陷阱。-regex 是与遍历生成的整条路径字符串比对的，而且是全体匹配而非部分匹配。实际路径是 ./sub/deep.log，所以 deep\.log 绝对匹配不上，必须用 .*/ 把前面放开。

第五条也类似。-name 只看路径的最后一段，所以带斜杠的模式在结构上就绝不可能匹配。要按路径形状过滤，得用 -path '*/sub/*'。

再叠上引号的问题，错误信息就变得费解了。

$ find . -name *.log
find: paths must precede expression: `report.log'
find: possible unquoted pattern after predicate `-name'?

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

第一条命令失败，跟 find 没有关系。是shell 抢先把 *.log 展开成 find . -name notes.log report.log 再交过去的。find 把第二个参数当成路径于是提出抗议。它还挺贴心地在第二行点出了原因，只是没见过这条信息的人不容易读懂。

更糟的是连错都不报的情况。当前目录里恰好只有一个 .log 文件时，find . -name *.log 会安静地只找到那一个，然后在文件变成两个的那天崩掉。

  • -name — glob，只以文件名（路径最后一段）为对象，斜杠绝不匹配
  • -path — glob，以整条路径为对象。它的 * 会跨越 /，这一点与 shell 的 glob 不同
  • -regex — 正则，以整条路径为对象，全体匹配。GNU find 的默认方言是 emacs 系，可用 -regextype posix-extended 更换
  • BSD、macOS 的 find 用 -E 而不是 -regextype。给 GNU findutils 4.10.0 传 -E 会被以 unknown predicate 拒绝
  • 把结果交给别的命令时的空格与换行问题，在find 与 xargs 的空格陷阱那边另行讨论过

扩展 glob 与 globstar

基本 glob 既没有重复运算符也没有选择（alternation）。bash 用 extglob 来补，但默认是关的。

$ shopt extglob
extglob         off

$ ls !(*.log)
ls: cannot access '!(*.log)': No such file or directory

$ shopt -s extglob
$ ls @(a|b).txt
a.txt
b.txt

$ ls +(a)b*.txt
ab.txt
abb.txt

$ ls a*(b).txt
a.txt
ab.txt
abb.txt

关着的时候，!(*.log) 不是模式，而只是一个用来找同名文件的字符串。打开之后，a*(b).txt 把 a.txt、ab.txt、abb.txt 全都抓到了。*(b) 意为「b 零次以上」，干的是与正则 b* 相同的活，只是括号的位置反过来而已。

globstar 的情形也一样。

$ shopt globstar
globstar        off

$ echo **/*.log
sub/deep.log

$ shopt -s globstar
$ echo **/*.log
notes.log report.log sub/deep.log

$ echo **
a.txt ab.txt abb.txt b.txt notes.log report.log sub sub/deep.log sub/deep.txt

关着时的 ** 只是两个 *，所以和 */*.log 一样只看下面恰好一层。打开后 **/ 会横跨零层以上，于是当前层的 notes.log 也被包含进来。不知道这一点就用了 ** 的脚本，会在「为什么不往下级目录找」上耗掉时间。

扩展 glob 写法含义正则对应所需选项
?(p)p 出现零次或一次(p)?extglob
*(p)p 出现零次以上(p)*extglob
+(p)p 出现一次以上(p)+extglob
@(a|b)a 或 b 中恰好一个(a|b)extglob
!(p)不是 p 的东西否定前瞻等extglob
**/零层以上的目录无对应globstar
[[:digit:]]一个数字[[:digit:]]不需要

!(p) 的正则对应之所以不干净，是因为「不是某某的字符串」在正则里本来就是个别扭的要求。要用否定前瞻，而那本身是另一个主题，整理在前瞻实战那边了。

哪里是 glob，哪里是正则

比起背符号，记住位置在实际工作中见效更快。写模式之前先判断「这里属于哪一边」，剩下的自然就跟上来了。

位置语法比对对象锚定
命令行上的 ls *.logglob文件名全体匹配
for f in *.txtglob文件名全体匹配
case $v in *.log)glob字符串（与文件无关）全体匹配
[[ $v == pat ]]glob字符串全体匹配
${v#pat} ${v%pat} ${v//pat/}glob字符串前、后、全局
[[ $v =~ re ]]正则（ERE）字符串部分匹配
grep re / grep -E re正则（BRE/ERE）行部分匹配
sed 's/re/rep/'正则（BRE）行部分匹配
awk '/re/'正则（ERE）行或字段部分匹配
expr s : re正则（BRE）字符串仅从开头
find -name / -pathglob文件名 / 路径全体匹配
find -regex正则整条路径全体匹配

表的最后一列也要一并看。grep 是部分匹配，而 find -regex 是全体匹配，所以把同一个正则挪过去，结果就会变。expr 又不一样，它只从字符串开头比对，并把匹配到的长度以数字返回。

$ printf '%s\n' a ab abb | sed 's/ab*/X/'
X
X
X

$ printf '%s\n' a ab abb xyz | awk '/ab*/'
a
ab
abb

$ expr 'abb' : 'ab*'
3

sed 把 a 换成 X、awk 输出 a，都是同一个原因：正则 ab* 与没有 b 的 a 匹配。expr 返回的 3，意思是 abb 三个字符全部匹配上了。

该用哪一边

大多数时候根本不用纠结，位置定了语法也就定了。会出现选择的，是同一件事有两种做法的时候，而那种时候通常 glob 更好。

  • 挑文件就用 glob。没有理由把 ls *.log 改写成 ls | grep '\.log$'，后者在含空格或换行的文件名上会崩
  • 判断扩展名、前缀、后缀就用 glob。[[ $f == *.tar.gz ]] 比 [[ $f =~ \.tar\.gz$ ]] 短，也不用转义
  • 从路径里切片段就用参数展开。${p##*/} 不会起外部进程，比调用一次 basename 快，也不需要 $(...)
  • 需要取出片段就用正则。一旦需要捕获，glob 就出局了。拆版本字符串、抠日志字段都属于这一类
  • 涉及个数就用正则。「三到五位数字」这类条件，离了 {3,5} 很难表达，extglob 也无法指定次数
  • 牵涉可移植性时 glob 更稳。正则的方言按工具分岔，而基本 glob 在各个 POSIX shell 上几乎一致 — 只是 [^...] 和 extglob 是例外

用正则处理夹杂韩文的数据时还会多出一层问题：音节层面的匹配与直觉相悖，那部分单独整理在韩文正则陷阱里。

小结

同样是 * 而答案不同，理由只有一个。glob 的 * 本身就表示「任意字符串」，而正则的 * 是让前面那一项重复的运算符。由此 ? 与 . 的角色对调，锚定的默认值分岔，方括号的否定符号也分岔。

实际工作中该记住的不是符号表，而是位置。bash 里 case、[[ == ]]、${}、文件名展开全是 glob，正则只有 [[ =~ ]] 一处。走到外面，grep、sed、awk、expr 是正则，而 find -name 又回到 glob。

而且这块领域会因为一行 shopt 改变行为。知道 nullglob、failglob、dotglob、extglob、globstar、globskipdots 各自开关的是什么，「昨天还好好的今天就不行了」有一半可以事先猜到。确认只要一行：不带参数敲 shopt，全都出来了。

未能确认的部分

  • 所有输出都只来自Windows 10 上的 Git Bash（MSYS2）、GNU bash 5.2.37 这一个环境，没有与 Linux 原生 bash 或 macOS 对照。尤其在文件系统不区分大小写的环境里，[a-z] 范围以及与 nocaseglob 相关的结果可能不同
  • zsh 和 ksh 这台机器上没装，没能跑起来。zsh 的 glob 语法扩展得相当多（修饰符、类正则 glob 等），本文「基本 glob 没有重复运算符」这句话对它并不原样成立。正文里的跨 shell 比较，只在 dash 上确认过
  • 关于 globskipdots 是 bash 5.2 新增的这一点，只确认到本机 5.2.37 上该选项存在且默认为 on。5.1 及更早版本没有这个选项，我并没有亲自跑过。若要接触老服务器，最好各自用 shopt globskipdots 确认一下
  • GNU find 4.10.0 的 -regex 在不带 -regextype 的情况下接受了 .+。文档上的默认值是 emacs 系，但究竟能通过哪些语法，我没有穷举测试边界。需要可移植性时，写明 -regextype posix-extended 更好
  • 区域设置导致的 [a-z] 范围变化没有实测。推荐字符类是遵循了广为人知的建议，并非我自己的实验结果
  • POSIX 规范原文的 Pattern Matching Notation 一节没能打开。记法规则是与 GNU bash 手册的对应章节比对的，规范条文本身并未引用
