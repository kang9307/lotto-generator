缘起 - 用配置文件而非代码定义智能体

Docker Agent 是 Docker 公开的开源工具，属于 Docker CLI 插件：把智能体的模型、指令、工具以及协作的其他智能体写进 YAML 文件，用 docker agent 命令运行。README 用一句话介绍为「Build, run, and share AI agents with a declarative YAML config, rich tool ecosystem, and multi-agent orchestration」，正文中写明「no code required」。

官方文档的开头是「Docker Agent is to AI agents what docker run is to containers」。文档解释说，LLM 编排循环、工具执行、多智能体委派和流式输出都由 Docker Agent 处理，用户只需关注智能体该做什么，而不是如何拼接各部分。

该项目于 2026 年 10 月 8 日登记在 GeekNews。按仓库元数据，所有者是 docker 组织，许可证为 Apache-2.0，创建于 2025 年 9 月 1 日，最新发布版本是 2026 年 10 月 7 日的 v1.149.0。这些值来自 GitHub 仓库信息和发布页面的显示，之后可能变化。

安装文档给出三条途径。Docker Desktop 4.63 及以上版本已预装该插件，可直接运行 docker agent；Homebrew 使用 brew install docker-agent 安装；把 GitHub 发布页的二进制文件放到 ~/.docker/cli-plugins，同样可以用 docker agent 调用。安装文档写明，从源码构建需要 Go 1.27 或更高版本。

Docker Agent 的定位 - 是什么与不是什么

官方文档首页有四张概括该工具性质的介绍卡片。以下是对其文字的转述。

  • 是什么： 运行以 YAML 或 HCL 声明式定义的 AI 智能体的 CLI。
  • 不是什么： 不是需要写代码的框架，不是托管 SaaS，也不是新模型。
  • 面向谁： 想在工作流中使用智能体而不写胶水代码（glue code）的开发者。
  • 能得到什么： 文档列出 TUI、CLI、HTTP API、MCP 服务器、A2A 和 OCI 分发。
  • 出处： 文档介绍它是制作 Docker Engine、Docker Desktop、Docker Hub 和 Docker Scout 的 Docker 的开源工具。

文档用两种方式对比同一个编程助手。用代码实现的示例中，客户端初始化、工具模式、分发函数和消息循环合计约 30 行 Python 胶水代码，每个项目都要写一遍；用 Docker Agent 则是 8 行 YAML 加一条 docker agent run agent.yaml 命令。行数是文档所举示例中的数值。

单智能体 YAML 结构与字段

README 的第一个示例在 agents 下放一个 root 智能体，写出模型、说明、指令和工具。运行命令是 docker agent run agent.yaml。

agents:
                      root:
                        model: openai/gpt-5-mini
                        description: A helpful AI assistant
                        instruction: |
                          You are a knowledgeable assistant that helps users with various tasks.
                          Be helpful, accurate, and concise in your responses.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo

官方文档的介绍页还给出了使用文件系统、shell 和 think 工具的编程助手示例。

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: A coding assistant
                        instruction: |
                          You are an expert developer. Help users write clean,
                          efficient code. Explain your reasoning step by step.
                        toolsets:
                          - type: filesystem
                          - type: shell
                          - type: think

下表整理了这两个示例和智能体配置参考中出现的主要字段。参考文档写道「A configuration must define at least one agent under agents」。

字段 类型 文档的说明 备注
agents 映射 以智能体名称为键的顶层项 至少定义一个智能体
model 字符串 模型引用，示例采用 提供方/模型 的形式 除非设置了 harness，否则标为必填
description 字符串 该智能体做什么 在模式中为可选
instruction 字符串或列表 系统提示词 不能与 instruction_file 同时使用，列表以空行连接
toolsets 列表 工具配置列表 用 type 选择工具，mcp 再加 ref
sub_agents 列表 本地或外部子智能体引用 用于委派模式
handoffs 列表 该智能体可以把对话交给的智能体名称 用于交接模式

关于模型提供方，README 列出 OpenAI、Anthropic、Gemini、AWS Bedrock、Mistral、xAI 和 Docker Model Runner 等，并补充「and more」。介绍页说明只需改动 model: 一行即可更换模型，并提到本地模型可通过 Docker Model Runner 或 Ollama 使用。README 还指引读者至少设置一个 API 密钥，或用 Docker Model Runner 运行本地模型。

配置参考的完整模式还带注释地列出了更多项目，这里挑出四项。

  • instruction_file： 从相对于配置文件的路径读取系统提示词。
  • fallback： 指定备用模型列表以及重试次数和冷却时间。
  • max_iterations： 限制工具调用循环的最大次数。
  • harness： 委托给外部编程 CLI 的设置，type 取值列为 claude-code、codex、opencode 和 pi。

文档还说明 HCL 只是同一配置模型的另一种语法。凡接受 .yaml 或 .yml 的地方也接受 .hcl，HCL 会在内部转换成等价的 YAML 结构，再经过相同的模式校验。

多智能体的两种模式 - 委派与交接

多智能体页面解释说，复杂任务适合分工：与其让单个智能体包办，不如组建由协调者、开发者、审查者和研究者组成的团队，每个智能体有自己的模型、工具和指令。两种模式的对比依据文档中的表格。

项目 委派（sub_agents） 交接（handoffs）
结构 层级式（父、子、父） P2P 图（A、B、C、A）
会话 子智能体在子会话中运行 对话保持在同一会话
上下文 子智能体拿到整理好的任务描述 下一个智能体看到完整对话历史
控制流 父智能体等待子智能体完成后继续 活动智能体切换，前一个智能体退出循环
工具 transfer_task handoff
适用场景 把任务委派给专家 流水线式工作流、对话路由

在委派中，带有 sub_agents 的智能体会自动获得 transfer_task 工具。工具页面说明参数有 agent、task、expected_output 三个，且都是必填。调用会阻塞到子智能体返回结果，文档还写明同一份配置中可以同时使用 sub_agents 和 handoffs。

交接是把整个对话交给另一个智能体的方式。文档的示例是协调者交给研究者，研究者交给摘要智能体，摘要智能体再回到协调者。

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: Coordinator that routes queries
                        instruction: |
                          Route research queries to the researcher.
                        handoffs:
                          - researcher
                    
                      researcher:
                        model: openai/gpt-5
                        description: Web researcher
                        instruction: |
                          Search the web, then hand off to the summarizer.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo
                        handoffs:
                          - summarizer
                    
                      summarizer:
                        model: openai/gpt-5
                        description: Summarizes findings
                        instruction: |
                          Summarize the research results, then hand off
                          back to root.
                        handoffs:
                          - root

交接页面指出，该工具只面向同一配置文件中声明的本地智能体，不会打开网络连接。要委派给远程智能体，则指引使用 A2A 工具集。每个智能体只能交接给自己 handoffs 数组中列出的名称。

文档给出的选择标准如下。

  • sub_agents： 协调者需要把任务发给专家并汇总结果时使用。
  • handoffs： 多个智能体轮流处理同一段对话的流水线或路由场景使用。
  • background_agents： 多个相互独立的任务需要同时运行时使用。文档列出的工具名有 run_background_agent、list_background_agents、view_background_agent、wait_background_agents 和 stop_background_agent。

文档指出，普通交接由模型自行决定是否调用 handoff 工具，因此可能不调用。force_handoff 用来弥补这一点：智能体给出最终回复时，由运行时把对话转给指定的智能体。文档写明加载配置时会检查三条规则：目标必须在配置中定义，智能体不能指向自己，force_handoff 的链条不能形成环。

  • 拒绝环路： 指向当前委派链中已有智能体的委派（例如 a 到 b 再到 a）会以错误失败。
  • 深度上限： 嵌套委派最多 10 层，根智能体委派给第一个子智能体算深度 1。

工具生态 - 内置工具集与 MCP 服务器

工具页面解释说，智能体发起工具调用后，Docker Agent 运行时执行工具并返回结果，智能体再利用结果继续工作。内置工具集通过在 toolsets 列表中写入 type 来启用。

工具 type 文档标明的行为 文档标明的限制
文件系统 filesystem 通过 read_file、write_file、edit_file、list_directory、search_files_content 等读写和搜索文件 默认不受限制，可用 allow_list 与 deny_list 缩小可访问目录
Shell shell 执行 shell 命令，每次调用使用全新的隔离 shell 会话 默认超时 30 秒，不使用 --yolo 时需要用户确认
脚本 script 把预先定义的 shell 命令作为带类型参数的具名工具暴露 文档称其比通用 shell 工具自由度更低、更安全
MCP mcp 接入 Model Context Protocol 服务器的工具 三种方式：Docker MCP、本地 stdio、远程
推理与记忆 think、todo、memory README 列出内置的 think、todo、memory 工具 —
检索增强 rag README：可插拔的 BM25、嵌入、混合检索与重排序 —

MCP 工具页面把接入方式分为三种。

  • Docker MCP（推荐）： 通过 MCP Gateway 以 Docker 容器运行服务器，用 ref: docker:duckduckgo 这样的写法引用 Docker MCP 目录中的定义。
  • 本地 stdio： 用 command 和 args 启动本地进程，通过标准输入输出通信。
  • 远程： 用 remote.url 与 transport_type（streamable 或 sse）连接网络上的服务器。页面说明 OAuth 流程会自动处理。
  • 工具过滤与自动安装： 可用 tools 列表限定暴露给模型的工具；本地命令不在 PATH 中时，会到 aqua 注册表查找并安装，可通过 DOCKER_AGENT_AUTO_INSTALL=false 关闭。

通过 OCI 注册表共享智能体

分发页面说明，智能体可以推送到 Docker Hub、GitHub Container Registry 等任何 OCI 兼容注册表，并在任何地方拉取运行。文档中的推送与拉取示例如下。

docker agent share push ./agent.yaml docker.io/username/my-agent:latest
                    docker agent share pull docker.io/username/my-agent:latest
  • 运行： README 的快速开始展示了 docker agent run myorg/agent:tag，可直接运行注册表中的智能体。
  • 签名： 使用 share push --key，拉取方可以验证发布者以及内容未被篡改。此时 YAML 本身始终以明文推送，只有证明材料写入 OCI 清单的注解。
  • 加密： 加上 --encrypt，整份 YAML 的加密副本也会记录在注解中。文档的示例使用 Ed25519 密钥和对称密钥两种。
  • 证明格式： 签名覆盖封装在 DSSE 信封中的 in-toto Statement v1，文档称这是 cosign 与 in-toto 工具使用的格式，无需 Docker Agent 也能读取和验证。
  • 外部子智能体： 多智能体页面说明，子智能体不必在本地定义，可以引用 OCI 注册表中的智能体。

权限页面警告，从 URL 或 OCI 注册表获取的配置可能带有作者选定的默认值，运行前应审查第三方配置。签名验证检查的是完整性和来源，并不保证配置内容安全。

权限与安全模式 - 批准流程的结构

工具页面把默认行为写为：Docker Agent 在执行 shell 命令、文件写入等有副作用的工具前会请求用户确认，使用 --yolo 则自动批准所有工具调用。权限页面对此给出了更细的结构。

  • 评估顺序： 权限规则按 deny、allow、ask 的顺序评估。deny 优先，未匹配任何规则的调用交由会话的安全模式处理。
  • 四种安全模式： strict 对每次调用都询问；balanced 静默执行安全调用，其余询问；restricted 只执行安全调用，其余不询问直接拒绝；autonomous 全部执行。
  • --yolo 的位置： 文档把 autonomous 称为旧的 --yolo 行为，并将 --yolo 视为保留下来的旧写法别名。模式通过 --safety 参数选择。
  • 命令分类： shell 命令被标为 safe、destructive 或 unknown。ls、git status 之类的读取命令是 safe，rm -rf 之类是 destructive，其余是 unknown。
  • transfer_task 与交接： transfer_task 始终自动批准，handoff 只能交给自身 handoffs 列表中的对象。
  • 路径限制： 不设置 allow_list 和 deny_list 时，filesystem 工具不受限制。文档示例把主目录下的 .ssh 和 .aws 放入 deny_list。
  • 沙箱模式： docker agent run --sandbox agent.yaml 在 Docker Sandboxes 的虚拟机中运行智能体。关于 restricted 模式，文档写道「defense in depth, not a security boundary」，并指引真正的隔离使用沙箱模式。
  • 遥测： README 说明为改进工具会收集匿名使用数据，并指向遥测页面。

「无需代码」的范围与文档标明的边界

「no code required」是 README 的表述。同一套文档里有几项内容可以用来衡量其范围。

  • script 工具： 把预先定义的 shell 命令作为带类型参数的具名工具暴露。命令本身仍需用户自己编写。
  • Go SDK 指南： 有单独的指南，说明如何把 Docker Agent 当作 Go 库，将智能体嵌入应用程序。
  • shell 工具的地位： 文档称 shell 是最强大的工具之一，智能体可以借此运行构建、安装依赖、查询 API 并与系统交互。
  • 配置的广度： 配置参考中有 hooks、structured_output、cache、code_mode_tools 等项目，显示仅靠 YAML 能触及的功能范围。
  • 对运行环境的依赖： 安装页面列出提供方 API 密钥、账号登录、Docker Model Runner 或编程 harness，作为访问模型的方式。
