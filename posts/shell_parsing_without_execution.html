셸 명령은 실행하기 전에는 무엇을 할지 확정되지 않는다 - 구조는 읽히고 결과는 읽히지 않는 경계

파싱은 안전 판정의 1차 필터일 수는 있어도 보안 경계는 되지 못한다

2026-09-10 개발/인프라

셸 명령 한 줄을 눈으로 읽고 그것이 무엇을 할지 말할 수 있는가. 대부분의 사람은 말할 수 있다고 여긴다. 그런데 echo *.json 이라는 여덟 글자를 놓고 이 명령이 인자를 몇 개 받는지를 물으면 답이 나오지 않는다. 그 수는 이 여덟 글자 안에 없기 때문이다. 어떤 저장소의 최상위에서 이 줄은 43개의 단어로 펼쳐지고, 그 아래 한 디렉터리에서는 1개로 펼쳐진다. 같은 텍스트, 다른 인자 벡터다.

이것이 셸이라는 언어의 성격을 정한다. 셸 소스는 그 자체로 프로그램이 아니라, 실행 시점에 프로그램을 만들어 내는 지시문에 가깝다. 최종적으로 execve 에 넘어가는 인자 배열은 텍스트가 아니라 그 순간의 파일 시스템·환경 변수·앞선 명령의 출력·셸 옵션 상태가 함께 만든다. 텍스트만 보고 그 배열을 확정하는 일은 원리적으로 불가능하다.

그렇다고 정적 분석이 무용하다는 결론이 나오지는 않는다. 결과가 안 읽힐 뿐 구조는 읽힌다. 파이프가 몇 단계인지, 리다이렉션이 어느 파일 서술자에 걸려 있는지, 명령어 자리에 무엇이 놓였는지, 어디서 서브셸이 생기는지는 텍스트만으로 확정된다. 문제는 이 두 가지를 구분하지 않고 쓸 때 생긴다. 특히 AI 에이전트가 실행할 셸 명령을 승인하거나 거절하는 게이트가 그 구분 위에 서 있다.

계기는 unbash 라는 TypeScript 파서다. bash 소스를 실행하지 않고 위치 정보가 붙은 구문 트리로 바꾼다. 흥미로운 것은 이 저장소가 스스로 그어 놓은 선이다. 코드를 실행하지 않고, 셸 확장을 수행하지 않으며, 샌드박스를 제공하지 않고, 어떤 명령이 안전한지 판정하지 않는다. 이 네 줄이 이 글 전체의 요약이다.

이 글의 실행 예시는 전부 읽기 전용이다. 출력은 GNU bash 5.2.37(1)-release (x86_64-pc-msys) 에서 나온 것이며, 파일을 만들거나 지우는 예시는 쓰지 않았다. 아래의 어떤 줄도 복사해 그대로 돌릴 것을 전제로 쓰지 않았다 — 문법의 성질을 보이기 위한 최소 예시다. 파괴적 명령은 예시에서 중립적인 명령으로 바꿔 두었다.

「실행하지 않고 분석한다」가 정확히 뜻하는 것

이 문장은 두 가지로 읽힌다. 하나는 「돌려 보지 않고도 무슨 일이 일어날지 안다」이고, 다른 하나는 「돌려 보지 않고 텍스트의 구조만 파악한다」이다. 셸에서 가능한 것은 두 번째뿐이다.

차이가 사소해 보이지만 결과는 정반대다. 첫 번째 읽기를 전제로 게이트를 만들면 그 게이트는 자기가 검사하지 않은 것을 검사했다고 보고한다. 두 번째 읽기를 전제로 만들면 게이트는 자기가 무엇을 모르는지 알고, 모르는 것을 만나면 다음 방어선으로 넘긴다. 같은 파서를 쓰고도 결과가 갈리는 지점이 여기다.

구문 트리를 얻는다는 것은 텍스트를 문법 요소로 쪼갠다는 뜻이다. 이 단어는 명령 이름, 저 단어는 인자, 이 기호는 파이프, 저 덩어리는 서브셸. 각 요소에 원본에서의 시작·끝 위치가 붙으면 편집기가 정확한 줄과 열에 표시를 찍을 수 있고, 입력이 도중에 끊겨도 거기까지의 부분 트리와 오류 위치를 돌려줄 수 있다. 이것은 텍스트에 대한 사실이고, 전부 참이다.

그런데 이 사실들은 실행에 대한 사실이 아니다. 명령 이름 자리에 ls 라는 세 글자가 있다는 것은 참이다. 그 세 글자가 실행될 때 무엇이 되는지는 별개의 문제이고, 그 답은 텍스트가 아니라 그 셸의 별칭 표와 함수 표와 PATH 에 있다. 파서는 앞의 사실을 주고, 사람들은 자주 뒤의 사실을 기대한다.

파서가 스스로 그은 선

unbash 의 README 는 무엇을 하고 무엇을 하지 않는지를 나눠서 적어 놓았다. 이런 경계 서술이 있는 도구는 드물고, 있으면 그대로 인용할 값이 있다.

다루는 문법으로 열거된 것은 다음과 같다. 명령·제어 흐름·파이프라인·리다이렉션·할당, 복합 명령, 매개변수 확장과 단어 확장, 프로세스 치환과 중첩 치환, coproc, 히어독과 히어스트링, C 스타일 for, select, 배열 할당, 확장 글롭, case 의 관통 연산자(;&·;;&), 그리고 bash 5.3 의 명령 치환 형태다. 즉 bash 문법의 대부분을 덮는다.

하지 않는 일로 명시된 것은 네 가지다. 코드를 실행하지 않고, 셸 확장을 수행하지 않고, 샌드박스를 제공하지 않고, 명령이 안전한지 판정하지 않는다. 여기에 더해 PowerShell 과 cmd.exe 는 대상이 아니라고 적혀 있고, 프로세스 인자를 파싱하는 용도로 쓸 물건도 아니라고 적혀 있다. 복구에도 한계가 명시돼 있다 — 깊게 중첩된 매개변수 확장과 산술 확장에서는 오류 복구가 제한된다.

보안 관련 문장이 특히 정직하다. 보안에 민감한 소비자는 각 스크립트의 단어 조각(word parts)·중첩 스크립트·오류 목록을 직접 검사해야 한다는 요구를 README 가 직접 걸어 둔다. 이 문장을 뒤집으면 이렇게 된다. 파서가 트리를 돌려줬다는 사실 자체는 아무것도 승인하지 않는다. 트리를 받은 쪽이 그 트리를 가지고 판정 규칙을 세워야 하고, 그 규칙의 품질이 게이트의 품질이다.

성능과 크기도 적혀 있다. 외부 의존성이 없는 동기 API이고, 최소화 기준 80KB · gzip 기준 19KB이며, ISC 라이선스다. 처리량 수치와 다른 파서 대비 배수도 README 에 있는데, 그 값들은 저장소가 자기 환경에서 잰 것이므로 조건 없이 옮길 값은 아니다.

셸이 정적 분석에 저항하는 다섯 가지 이유

여기가 이 글의 심장이다. 셸이 정적 분석을 어렵게 만드는 것은 문법이 복잡해서가 아니다. 문법이 의도적으로 실행 시점의 상태를 끌어들이도록 설계돼 있기 때문이다. 다섯 갈래로 나뉜다.

① 글로브는 그 순간의 디렉터리가 정한다

패턴이 몇 개의 단어로 펼쳐지는지는 패턴 안에 없다. 파일 시스템에 있다. 그리고 매칭되는 이름이 하나도 없을 때의 행동은 셸 옵션 상태에 따라 세 갈래로 갈린다.

# 같은 텍스트, 다른 디렉터리 — 단어 수가 다르다
$ echo *.json          # 저장소 최상위
PHASE2_STAGES.json _h2_index.json ... package.json trend_topics.json   # 43개 단어

$ echo *.json          # 그 아래 posts 디렉터리
index.json                                                             # 1개 단어

# 매칭이 하나도 없을 때 — 기본값은 패턴을 그대로 남긴다
$ echo zzz*.nosuch
zzz*.nosuch

$ ( shopt -s nullglob; echo "[" zzz*.nosuch "]" )
[ ]                                              # 단어가 사라진다

$ ( shopt -s failglob; echo zzz*.nosuch )
bash: no match: zzz*.nosuch                      # 명령 자체가 실행되지 않는다

세 줄이 전부 같은 패턴이다. 그런데 결과는 1개 단어 · 0개 단어 · 실행 안 됨으로 갈린다. 어느 쪽이 될지는 그 셸 인스턴스가 어떤 옵션을 켜고 있는지에 달렸고, 그 상태는 텍스트에 없다.

그래서 정적 분석이 말할 수 있는 것은 이 정도다. 이 자리에 패턴이 있다. 이 단어는 인자 개수가 가변이다. 개수의 하한은 0이고 상한은 정해지지 않는다. 말할 수 없는 것은 개수와 값 전부다. 글로브 문법 자체와 정규식의 차이는 글롭과 정규식은 다르다 - * 가 서로 다른 뜻인 순간에서 따로 다룬다.

② 변수 확장과 명령 치환은 실행해야 값이 정해진다

$VAR 의 값은 환경에 있고, $(...) 와 백틱의 값은 그 안의 명령을 실제로 돌려야 나온다. 후자가 특히 성가신 이유는 값이 결정적이지도 않다는 데 있다. 같은 텍스트를 두 번 평가하면 다른 값이 나오는 경우가 흔하다.

# 명령 치환 — 안쪽을 돌려야 값이 나온다
$ echo "$(echo one two)"
one two

# 같은 텍스트, 매번 다른 값
$ echo $RANDOM; echo $RANDOM
11194
27279

# 확장 결과는 다시 파싱되지 않는다 — 연산자가 되지 않는다
$ v='echo a; echo b'; $v
a; echo b

$ v='echo a | tr a-z A-Z'; $v
a | tr a-z A-Z

마지막 두 예가 중요하다. 변수 안에 ; 나 | 를 담아도 그것들은 연산자가 되지 않고 그냥 인자가 된다. 이 성질 덕분에 정적 분석의 골격이 대체로 지켜진다. 확장으로 구조가 새로 생기지는 않는다는 뜻이다.

정적 분석이 말할 수 있는 것은 치환이 있다는 사실과 그 안의 중첩된 스크립트 구조다. $(...) 안쪽도 셸 문법이므로 그 안의 명령 이름과 파이프 구조는 어휘적으로 읽힌다. README 가 중첩 스크립트를 검사하라고 요구하는 이유가 이것이다. 말할 수 없는 것은 값, 그리고 그 값이 바깥 명령의 인자 경계를 어떻게 바꾸는지다.

③ 같은 이름이 서로 다른 것을 가리킨다

명령어 자리에 놓인 단어가 무엇을 실행하는지는 이름 해석 규칙이 정한다. 별칭이 먼저, 그다음 함수, 그다음 빌트인, 마지막으로 PATH 순회다. 같은 이름이 이 네 층 전부에 존재할 수 있다.

# 한 이름에 네 개의 후보가 동시에 존재한다
$ type -a echo
echo is aliased to `echo A'
echo is a function
echo is a shell builtin
echo is /usr/bin/echo

# 함수가 외부 명령을 가린다
$ printf() { builtin printf "FUNC:%s\n" "$*"; }; printf hello
FUNC:hello

# PATH 를 좁히면 방금까지 찾히던 것이 안 찾힌다
$ type -p node
/c/Program Files/nodejs/node
$ PATH=/usr/bin; type -p node || echo "not found"
not found

# 별칭에는 타이밍까지 있다 — 같은 줄에서 정의하고 쓰면 먹지 않는다
$ shopt -s expand_aliases; alias hi="echo ok"; hi
bash: hi: command not found          # 같은 줄

$ shopt -s expand_aliases
$ alias hi="echo ok"
$ hi
ok                                    # 다음 줄

마지막 예가 정적 분석의 한계를 가장 선명하게 보인다. 별칭 확장은 셸이 줄을 읽는 시점에 일어나는데, 그 시점의 별칭 표는 그 셸의 실행 상태다. 즉 파싱 단계에서 이미 실행 상태가 개입한다. 같은 텍스트를 다른 셸 인스턴스에 넣으면 파싱 결과부터 달라질 수 있다.

정적 분석이 말할 수 있는 것은 「명령어 자리에 이 텍스트가 있다」까지다. 그 텍스트가 실행 시점에 무엇으로 해석되는지는 말할 수 없다. 게이트를 만들 때 이 구분을 지키면 판정문이 정확해진다. 「이 명령은 ls 다」가 아니라 「이 명령어 자리의 단어는 ls 다」로 적어야 한다.

④ eval 은 문자열을 다시 코드로 만든다

③에서 확장 결과가 다시 파싱되지 않는다고 했다. eval 은 그 규칙의 예외다. 인자로 받은 문자열을 셸 소스로 다시 읽는다.

# 확장만으로는 명령이 하나다
$ v='echo a; echo b'; $v
a; echo b

# eval 은 같은 문자열을 두 개의 명령으로 만든다
$ v='echo a; echo b'; eval "$v"
a
b

# 문자열이 할당과 산술 확장까지 담을 수 있다
$ s='a=1; echo $((a+1))'; echo "$s"
a=1; echo $((a+1))
$ eval "$s"
2

eval 이 등장하는 순간 구문 트리는 실행 시점에 새로 태어난다. 정적 분석이 말할 수 있는 것은 「여기서 새 스크립트가 생긴다」까지이고, 그 스크립트의 내용은 문자열 값에 달려 있으므로 ②의 문제로 되돌아간다. . 와 source 도 성질이 같다. 다른 파일의 내용을 현재 셸에 들여오므로, 그 파일이 무엇을 담고 있는지가 텍스트 밖에 있다.

⑤ 단어 분할과 따옴표가 인자 경계를 바꾼다

확장된 값이 몇 개의 인자가 되는지는 인용 여부와 IFS 변수가 정한다. 인용하지 않은 확장 결과는 분할되고, 인용한 확장 결과는 분할되지 않으며, 무엇을 경계로 볼지는 런타임 변수 하나가 정한다.

$ x='a b c'

$ set -- $x;   echo "argc=$#"      # 인용 없음 — 세 개로 쪼개진다
argc=3
$ set -- "$x"; echo "argc=$#"      # 인용 — 한 개 그대로
argc=1

# 빈 값은 인용하지 않으면 아예 사라진다
$ e=''
$ set -- a $e b;   echo "argc=$#"
argc=2
$ set -- a "$e" b; echo "argc=$#"
argc=3

# 경계를 정하는 것은 런타임 변수다
$ y='a:b:c'
$ ( IFS=:; for w in $y; do printf ' [%s]' "$w"; done; echo )
 [a] [b] [c]

두 번째 예가 게이트 설계에 직접 걸린다. 인자 하나가 통째로 사라질 수 있다. 텍스트에는 세 개의 단어가 있는데 실행되는 것은 두 개짜리 인자 벡터다. 위치를 세어 판정하는 규칙은 여기서 어긋난다.

정적 분석이 말할 수 있는 것은 「이 단어는 인용되지 않았으므로 분할될 수 있다」는 가능성 판정이다. 인용 여부 자체는 어휘적으로 완전히 읽히기 때문에 이 판정은 정확하다. 개수는 여전히 읽히지 않는다. 어느 따옴표가 어느 확장을 끄는지는 셸 인용부호 규칙 - 어느 따옴표가 무엇을 막는가에 정리돼 있다.

확장 순서가 정하는 관할 경계

다섯 갈래가 제각각인 것처럼 보이지만 하나의 규정에 묶여 있다. GNU Bash 매뉴얼은 확장의 순서를 이렇게 못박는다. 중괄호 확장, 그다음 틸드 확장·매개변수와 변수 확장·산술 확장·명령 치환(왼쪽에서 오른쪽으로), 그다음 단어 분할, 그다음 파일명 확장, 마지막으로 인용 제거.

단어의 개수를 늘릴 수 있는 것은 중괄호 확장·단어 분할·파일명 확장 셋뿐이며, 나머지 확장은 한 단어를 한 단어로 확장한다.

이 한 줄이 정적 분석의 관할 경계를 정확히 그어 준다. 단어 수를 바꿀 수 있는 세 단계 중 둘이 런타임 상태에 의존한다. 단어 분할은 IFS 와 확장 값에, 파일명 확장은 디렉터리 내용과 셸 옵션에 달려 있다. 그래서 인자 벡터가 정적으로 확정되지 않는다.

그런데 나머지 하나, 중괄호 확장은 순수하게 어휘적이다. 파일 시스템도 환경 변수도 보지 않는다. 이것이 유일한 예외이고, 그래서 파서가 결과까지 정확히 말할 수 있는 단 하나의 확장이다.

# 중괄호 확장은 파일 시스템을 보지 않는다
$ echo {a,b}.txt
a.txt b.txt

$ echo /nonexistent/{p,q}/r          # 존재하지 않는 경로여도 그대로 펼쳐진다
/nonexistent/p/r /nonexistent/q/r

$ set -- {a,b,c}.txt; echo "argc=$#"  # 단어 수가 정적으로 확정된다
argc=3

# 인용하면 확장 자체가 일어나지 않는다 — 이것도 어휘적으로 판정된다
$ echo "{a,b}.txt"
{a,b}.txt

POSIX 셸 명세는 확장 순서를 조금 다르게 적는다. 틸드 확장·매개변수 확장·명령 치환·산술 확장이 먼저이고, 그다음 필드 분할, 그다음 경로명 확장(set -f 가 걸려 있지 않다면), 인용 제거는 수행된다면 언제나 마지막이다. 목록에 중괄호 확장이 없다.

단계bash 매뉴얼의 순서POSIX 명세의 순서정적으로 결과가 확정되나
중괄호 확장1번 — 가장 먼저순서 목록에 없음확정
틸드 확장2번 묶음1번 묶음홈 디렉터리 값에 의존
매개변수·변수 확장2번 묶음1번 묶음미확정
산술 확장2번 묶음1번 묶음변수를 참조하면 미확정
명령 치환2번 묶음 · 좌에서 우로1번 묶음미확정
단어 분할 · 필드 분할3번2번미확정 — IFS 에 의존
파일명 · 경로명 확장4번3번 — set -f 면 생략미확정 — 디렉터리에 의존
인용 제거5번 — 마지막언제나 마지막확정

표의 마지막 열이 이 글의 절반이다. 확정되는 두 줄은 문법이 스스로 닫혀 있는 단계이고, 나머지는 전부 바깥 상태를 끌어들인다. 파서가 보는 것은 이 사다리의 맨 위이고, 실행이 보는 것은 맨 아래다. 그 사이에서 단어가 늘어나고 줄어들고 사라진다.

그래도 실행 전에 확정되는 것

지금까지가 못 하는 쪽이었다면 여기부터가 되는 쪽이다. 그리고 되는 쪽의 목록이 생각보다 길다.

# 파이프라인 구조는 어휘적으로 확정된다
$ echo hi | tr a-z A-Z
HI

# 리다이렉션은 명령 이름 앞에도 올 수 있다 — 첫 단어가 명령이라는 규칙은 틀린다
$ 2>/dev/null echo redir-first-ok
redir-first-ok

# 앞에 붙은 것이 할당인지 명령인지도 어휘적으로 갈린다
$ A=1 B=2 env | grep -E '^(A|B)=' | sort
A=1
B=2

# 서브셸 경계 — 괄호는 새 셸, 중괄호는 같은 셸
$ x=1; ( x=2; echo "inner=$x" ); echo "outer=$x"
inner=2
outer=1
$ x=1; { x=2; echo "brace=$x"; }; echo "after=$x"
brace=2
after=2

리다이렉션이 명령 이름 앞에 올 수 있다는 사실은 실무적으로 큰 차이를 만든다. 「줄의 첫 단어가 명령 이름이다」라는 규칙으로 만든 검사기는 이 형태에서 바로 어긋난다. 구조 파서는 이것을 리다이렉션 하나와 명령 하나로 정확히 나눈다. 반대로 할당만 있고 명령이 없는 문장도 있는데, 이때 「명령 이름」이라는 슬롯 자체가 비어 있다는 것 역시 정적으로 확정된다.

서브셸 경계가 확정된다는 것은 어느 할당이 바깥으로 새고 어느 할당이 갇히는지를 실행 없이 말할 수 있다는 뜻이다. 이 경계가 만드는 실무 사고는 파이프 안 while에서 변수가 사라지는 이유 - 서브셸 2026에서 따로 다룬다.

# 흐름 연산자 — 후보는 확정되고 실행 여부는 종료 코드가 정한다
$ true && echo ran-A; false && echo ran-B; echo always-C
ran-A
always-C

# 히어독 본문의 확장 여부는 구분자의 인용으로 어휘적으로 판정된다
$ v=VALUE; cat <<EOF
plain: $v
EOF
plain: VALUE

$ v=VALUE; cat <<"EOF"
quoted: $v
EOF
quoted: $v

흐름 연산자에서 확정되는 것은 실행될 수 있는 명령의 상한 집합이다. 어느 것이 실제로 도는지는 종료 코드에 달려 있으므로 미확정이지만, 상한이 확정된다는 것만으로도 허용 목록 판정에는 충분하다. 상한에 속한 모든 명령이 허용 목록 안에 있으면 어느 분기를 타든 안전 조건이 유지된다. 종료 코드가 실제로 무엇을 잡고 무엇을 놓치는지는 셸 종료 코드와 set -e - 무엇을 잡고 무엇을 놓치는가에 정리돼 있다.

히어독 쪽도 깔끔하다. 구분자에 따옴표가 붙어 있는지 여부만 보면 본문 안에서 확장이 일어나는지가 정해진다. 구분자가 인용돼 있으면 본문은 순수 텍스트이므로 그 안에 명령처럼 보이는 문자열이 있어도 명령이 아니다. 인용돼 있지 않으면 본문 안의 치환이 살아 있으므로 중첩 스크립트로 세어야 한다. 이 판정은 어휘적이고 정확하다. 히어독 자체의 사용법은 히어독 실전 - 변수 확장을 끄고 켜기, 들여쓰기 함정에 있다.

여기까지를 한 문장으로 줄이면 이렇게 된다. 구조는 읽을 수 있고 결과는 읽을 수 없다.

구성 요소별 판정표

다섯 갈래와 확장 순서를 하나의 표로 합치면 게이트 규칙을 쓸 때 그대로 참조표가 된다. 왼쪽에서 오른쪽으로 읽으면 「이것은 확정되는가 → 무엇에 달려 있는가 → 그러면 무엇까지 적을 수 있는가」가 된다.

구성 요소실행 전에 확정되나무엇에 달려 있나정적 분석이 말할 수 있는 것
파이프라인 단계 수와 연결확정—단계 수, 각 단계의 명령어 자리 단어

리다이렉션 대상 경로미확정확장 결과대상 자리가 있다는 것, 확장을 포함하는지 여부
명령어 자리에 놓인 단어확정—그 자리의 텍스트와 원본 위치
그 단어가 실제로 실행할 실체미확정별칭·함수·빌트인·PATH같은 이름의 후보가 여럿일 수 있다는 사실
중괄호 확장의 결과확정—펼쳐진 단어 목록 전체

변수 확장과 명령 치환의 값미확정환경 · 앞선 명령의 출력치환 자리, 그리고 그 안의 중첩 스크립트 구조

.·source 가 들여오는 내용미확정대상 파일의 내용 · 경로 확장소스 지시가 있다는 것과 그 대상 자리
인자 문자열 안에 든 다른 언어셸 관점에서는 한 단어그 언어의 해석기단어의 경계와 위치까지 — 의미는 셸 문법 밖

마지막 줄이 자주 잊힌다. 어떤 인자는 그 자체가 다른 언어로 쓰인 프로그램이다. 패턴 처리 도구에 넘기는 스크립트 본문, 원격 셸에 넘기는 명령 문자열, 인자를 받아 다른 명령을 조립하는 도구의 뒤쪽 전부가 그렇다. 셸 파서에게 그것들은 따옴표로 묶인 단어 하나일 뿐이다. 셸 AST 가 완벽해도 그 안쪽은 셸 문법의 관할이 아니다.

문자열 매칭으로 거르면 무엇이 새는가

「위험한 명령을 차단한다」를 문자열 매칭으로 구현하면 거짓 안심이 만들어진다. 이유는 세 층이다.

  • 표기의 집합이 열려 있다. 셸은 같은 단어에 도달하는 방법을 여러 개 제공한다. 이 글은 그 방법들을 열거하지 않는다 — 요점은 목록의 길이가 아니라 목록이 닫히지 않는다는 성질이기 때문이다. 열거로 막는 규칙은 열거되지 않은 한 가지가 있으면 그 한 가지에서 무너진다.
  • 검사 대상이 확장 전 텍스트다. 실제로 실행되는 인자 벡터는 §4의 사다리를 전부 내려온 뒤에 만들어진다. 문자열 매칭은 사다리의 맨 위에서만 본다. 위에서 무해해 보이는 단어가 아래에서 무엇이 되는지는 검사되지 않았다.
  • 경계가 없다. 정규식은 명령어 자리와 인자 자리와 문자열 내부와 주석 내부를 구분하지 않는다. 그래서 거짓 통과와 거짓 차단이 동시에 난다. 히어독 본문 안의 단어를 명령으로 오인해 정상 스크립트를 막는 쪽도, 리다이렉션이 앞에 붙어 첫 단어가 명령이 아닌 형태를 놓치는 쪽도 같은 원인에서 나온다.

세 번째가 특히 곤란한 이유는 실패가 양방향이기 때문이다. 한쪽으로만 실패하는 검사기는 보정할 수 있다. 통과가 너무 헐거우면 규칙을 조이고, 차단이 너무 빡빡하면 예외를 판다. 양방향으로 실패하는 검사기는 조일수록 정상 작업이 막히고 풀수록 판정이 헐거워진다. 두 다이얼이 같은 축에 묶여 있다.

그리고 실무에서는 거짓 차단이 먼저 문제가 된다. 정상 명령이 자꾸 막히면 사람이 게이트를 우회할 방법을 찾거나 규칙을 통째로 느슨하게 만든다. 거짓 차단이 쌓이면 결국 거짓 안심으로 귀결된다. 이것이 문자열 매칭 게이트가 시간이 지날수록 나빠지는 경로다.

구조 기반 판정이 더 잡는 것과 못 잡는 것

구문 트리를 받으면 무엇이 달라지는지부터 정리한다.

  • 슬롯을 구분한다. 명령어 자리와 인자 자리와 문자열 내부가 다른 노드다. 문자열 안의 단어를 명령으로 세지 않으므로 거짓 차단이 크게 줄어든다.
  • 파이프의 모든 단계를 센다. 앞단만 보거나 뒷단만 보고 통과시키는 실수가 구조적으로 불가능해진다.
  • 중첩 스크립트를 별도 집합으로 센다. 명령 치환·프로세스 치환·인용되지 않은 히어독 본문 안의 명령들이 각각 자기 노드를 가진다.
  • 리다이렉션의 위치에 흔들리지 않는다. 명령 앞에 오든 뒤에 오든 같은 구조로 읽는다.
  • 파싱 실패를 신호로 쓸 수 있다. 구문이 성립하지 않는 입력은 거절한다는 규칙이 성립한다. 이것은 문자열 매칭에는 없는 축이다.
  • 위치 정보로 판정 근거를 남긴다. 어느 줄 어느 열의 어느 노드 때문에 거절했는지가 로그에 남으면 규칙을 고칠 수 있다.

그런데 여전히 못 잡는 것이 있고, 그 목록이 §3과 정확히 겹친다.

  • 확장 결과. 글로브가 무엇으로 펼쳐지는지, 치환이 어떤 값을 내놓는지는 트리에 없다.
  • 이름의 해석. 명령어 자리의 단어가 별칭인지 함수인지 실행 파일인지는 그 셸의 상태다.
  • eval·source 뒤에 생기는 코드. 트리는 「여기서 새 트리가 생긴다」까지만 말한다.
  • 인자의 의미론. 인자 문자열 안에 든 다른 언어는 셸 문법 밖이다.
  • 부수 효과의 크기. 같은 명령이 어느 디렉터리에서 도느냐에 따라 영향 범위가 완전히 달라지는데, 작업 디렉터리는 실행 상태다.
검사 방식보는 것거짓 통과거짓 차단확장 결과에 작용하나
문자열·정규식 매칭확장 전 텍스트, 슬롯 구분 없음많다 — 표기 집합이 열려 있다많다 — 문자열·주석 안을 명령으로 센다아니오
구조 기반 판정구문 트리, 슬롯 구분 있음줄지만 남는다 — 이름 해석과 확장크게 준다아니오
문법 부분집합 허용 목록트리 + 허용된 노드 타입만더 준다 — 모르는 형태를 거절한다는다 — 정상 작업도 막힌다아니오
실행 환경 격리텍스트를 보지 않는다해당 없음 — 피해 범위를 제한한다해당 없음예 — 결과에 작용한다

표의 마지막 열이 순서를 정한다. 앞의 세 줄은 전부 텍스트를 보고, 마지막 줄만 결과를 본다. 원리적으로 확정되지 않는 것을 텍스트로 판정하려는 시도는 정확도를 올릴 수는 있어도 보장을 만들지는 못한다.

격리·허용 목록·차단 목록의 순서

세 가지 방어의 강도는 무엇에 작용하는지로 정해진다.

  • 격리는 결과에 작용한다. 명령이 무엇으로 확장되든 파일 시스템 접근 범위·네트워크 도달 범위·권한이 밖에서 제한돼 있으면 피해의 상한이 정해진다. 이 상한은 텍스트를 한 글자도 읽지 않고 성립한다.
  • 허용 목록은 여집합에 작용한다. 열거된 것만 통과시키므로 열거되지 않은 전부가 막힌다. 표기의 자유도가 공격 표면이 아니라 거절 사유로 뒤집힌다. 모르는 형태를 만나면 거절이 기본값이다.
  • 차단 목록은 열거한 것에만 작용한다. 알려진 것만 막는다. 새 표기 하나가 목록 밖에 있으면 그 하나로 뚫린다.

그래서 순서는 격리 → 허용 목록 → 차단 목록이다. 차단 목록이 쓸모없다는 뜻은 아니다. 명백한 실수를 일찍 잡아 사람에게 알려 주는 역할은 있다. 다만 그것이 첫 번째 방어선이 되면 그 순간 거짓 안심이 된다.

허용 목록을 구조 파싱으로 구현하면 형태가 이렇게 된다. 이것은 「위험한 것을 거른다」가 아니라 「받아들일 문법의 부분집합을 정의한다」는 작업이다.

  • 파싱이 실패했거나 오류 목록이 비어 있지 않으면 거절한다.
  • 허용한 노드 타입 밖의 구성 요소가 있으면 거절한다. eval·source·프로세스 치환·coproc·중첩 명령 치환은 「모르는 것」 쪽에 두는 편이 안전하다.
  • 명령어 자리의 단어가 허용 목록 밖이면 거절한다. 파이프의 모든 단계와 중첩 스크립트의 모든 명령에 같은 규칙을 적용한다.
  • 인용되지 않은 확장이 인자에 있으면 거절하거나, 격리 강도를 한 단계 올린 채로만 통과시킨다.
  • 리다이렉션 대상이 확장을 포함하면 같은 취급을 한다.
  • 통과한 명령도 격리 안에서 돈다. 게이트를 통과했다는 것이 격리를 면제하지 않는다.

이 목록에서 모든 판정이 「거절」 쪽으로 기울어 있다는 점이 중요하다. 정적 분석의 불확실성은 전부 거절 쪽에 실려야 한다. 확정되지 않은 것을 통과 쪽에 실으면 그 불확실성이 그대로 위험이 된다.

값을 하는 자리와 못 하는 자리

셸 파서가 값을 하는 자리는 분명히 있고, 그 자리들에는 공통점이 있다. 판정의 실패가 곧 사고가 되지 않는 자리다.

쓰임필요한 것실패했을 때적합한가
코드 리뷰·린팅구조와 정확한 위치지적이 하나 빠진다적합 — 사람이 최종 판단
CI 에서 스크립트 형태 검사금지 형태의 구조적 탐지빌드가 한 번 통과한다적합 — 다른 게이트가 뒤에 있다
에이전트 명령 게이트의 1차 필터허용 문법 부분집합 판정다음 방어선인 격리가 받는다적합 — 단독으로 서지 않는 조건에서
로그의 명령 정규화·집계명령 이름과 형태의 추출집계 항목이 하나 어긋난다적합 — 안전이 아니라 관측 문제
편집기 하이라이팅·자동완성불완전 입력의 부분 트리표시가 잠깐 어긋난다적합 — 오류 복구가 오히려 요구된다
스크립트 리팩터링 도구노드 단위 변환과 위치변환이 거절된다적합 — 확장 의미를 바꾸지 않는 범위에서
보안 경계 그 자체확장 결과에 대한 보장경계가 뚫린다부적합 — 원리적으로 확정되지 않는다
임의 스크립트의 안전·위험 이진 분류실행 결과의 예측잘못된 승인이 나간다부적합 — 문제 정의 자체가 성립하지 않는다

네 번째 줄인 로그 정규화는 덜 알려졌지만 정적 분석이 가장 깔끔하게 맞는 자리다. 실행된 명령 문자열을 그대로 집계하면 인자마다 값이 달라 카디널리티가 폭발한다. 구조로 파싱해서 명령 이름과 옵션 형태만 남기고 인자 값을 자리 표시자로 바꾸면 같은 모양의 명령이 한 항목으로 모인다. 여기서는 확장 결과를 모르는 것이 오히려 이점이다. 알고 싶은 것이 값이 아니라 모양이기 때문이다.

반대로 마지막 두 줄은 어떤 파서를 써도 달라지지 않는다. 파서의 완성도 문제가 아니라 물음 자체가 텍스트로 답할 수 없는 물음이기 때문이다. 실행 전 검증이 무엇을 보장하고 무엇을 보장하지 못하는지의 일반적인 형태는 --dry-run을 제대로 만드는 법 - 흉내가 아니라 검증과 같은 구조를 가진다.

방언 - 어느 셸을 파싱하는지

마지막 축이 하나 남았다. 파서가 어느 방언을 대상으로 하는지 확인하지 않으면 판정이 어긋난다.

POSIX 셸 명세와 bash 는 상당 부분이 겹치지만 같지 않다. 배열은 POSIX 명세에 없고, 프로세스 치환도 없다. [[ 와 ]] 는 현행 판이 구현이 예약어로 인식할 수 있는 낱말 목록에 올려 두었을 뿐 의미를 규정하지 않는다. 반면 달러 기호가 붙은 작은따옴표 형태는 현행 판에 전용 절이 있다. set -f 로 경로명 확장을 끄는 규정처럼 양쪽이 같은 곳도 있고, 중괄호 확장처럼 한쪽에만 있는 것도 있다.

여기에 이름과 실체가 어긋나는 문제가 더해진다. 이 글의 출력을 낸 환경에서 sh 는 별도의 구현이 아니라 bash 다. sh -c 'echo $BASH_VERSION' 이 5.2.37(1)-release 를 내놓는다. 즉 이 환경에서 sh 로 시험한 결과는 POSIX 를 시험한 결과가 아니다. §3의 ③이 말한 「같은 이름이 다른 것을 가리킨다」가 셸 자체에도 그대로 적용된다.

이 어긋남이 게이트에서 어떻게 나타나는가. #!/bin/sh 로 시작하는 스크립트를 bash 문법 파서로 통과시키면, 실제 실행 환경에서는 문법 오류가 될 것을 통과시킬 수 있다. 반대 방향도 있다. bash 확장을 쓴 스크립트를 POSIX 기준으로만 검사하면 파싱 실패가 나고, 파싱 실패를 거절 신호로 쓰는 게이트에서는 정상 스크립트가 막힌다.

마지막 줄은 unbash 가 스스로 밝혀 둔 범위이기도 하다. Windows 계열 셸은 대상이 아니다. 하나의 게이트가 여러 플랫폼의 명령을 받는다면 방언마다 별도의 파서와 별도의 허용 목록이 필요하다. 셸이 다르면 같은 문자열의 인용 규칙부터 다르다는 점은 한글 파일명이 셸마다 다르게 보이는 이유 - Git Bash와 PowerShell의 어긋난 규칙에서 이름 처리를 예로 다룬다.

명령 게이트에 배선하는 순서

지금까지의 내용을 실제 배선으로 옮기면 순서가 이렇게 된다.

  1. 격리를 먼저 세운다. 파서를 붙이기 전에, 명령이 무엇을 하든 피해 범위가 정해져 있는 상태를 만든다. 이 단계가 없으면 뒤의 모든 단계가 최선 노력에 불과하다.
  2. 방언을 고정한다. 어느 셸로 실행할 것인지와 어느 문법으로 검사할 것인지를 같게 맞춘다. 두 개가 다르면 판정과 실행이 다른 언어를 본다.
  3. 파싱 실패를 거절로 처리한다. 오류 목록이 비어 있지 않으면 통과시키지 않는다.
  4. 문법 부분집합으로 좁힌다. 허용한 노드 타입 밖은 거절한다. 새 문법이 필요해지면 규칙을 명시적으로 넓힌다.
  5. 명령 이름 허용 목록을 적용한다. 파이프의 모든 단계와 중첩 스크립트의 모든 명령에 빠짐없이 적용한다.
  6. 확장이 남아 있으면 강등한다. 인용되지 않은 확장이나 글로브가 있으면 거절하거나 더 좁은 격리로 보낸다.
  7. 판정 근거를 남긴다. 어느 노드의 어느 위치 때문에 거절했는지를 기록한다. 근거 없는 거절은 결국 규칙을 통째로 끄게 만든다.

이 순서를 지키면 파서의 역할이 자연스럽게 제자리를 찾는다. 파서는 게이트의 문지기가 아니라 접수처다. 형식이 맞는지 보고, 모르는 것은 되돌려 보내고, 통과한 것도 안쪽의 진짜 경계로 넘긴다.

그리고 이 글의 첫 문장으로 돌아가면 이렇게 정리된다. 셸 명령 한 줄을 읽고 그것이 무엇을 할지 말하는 일은 불가능하다. 그러나 그것이 어떤 모양인지를 말하는 일은 가능하고, 모양이 정해진 집합 안에 있는지 판정하는 일도 가능하다. 게이트가 답해야 하는 물음을 앞의 것에서 뒤의 것으로 바꾸는 것 — 정적 분석이 실제로 하는 일은 그것이다.

확인하지 못한 것

  • GNU Bash 매뉴얼의 파일명 확장 항목 — 해당 페이지가 두 차례 모두 HTTP 429 응답으로 열리지 않았다. 매칭되는 이름이 없을 때 패턴이 그대로 남는다는 동작과 nullglob·failglob 의 효과는 위의 실행 출력으로만 뒷받침되며, 매뉴얼 조항과 대조하지 못했다. 확장 순서 항목은 매뉴얼에서 그대로 인용했다.
  • POSIX 명세에서 경로명 확장이 매칭에 실패했을 때의 규정 — 확장 순서 절에는 이 경우의 서술이 없었고, 별도 절까지는 확인 범위를 넓히지 못했다.
  • unbash 의 AST 노드 타입 전체 목록과 각 노드의 필드 — README 가 보여 주는 예시 범위 밖은 확인하지 못했다. 따라서 위의 「허용한 노드 타입」 설계는 일반적인 형태이지 이 파서의 실제 타입 이름에 맞춘 것이 아니다.
  • README 의 처리량 수치와 다른 파서 대비 배수 — 저장소의 자체 측정값이며, 측정 조건과 입력 집합을 재현하지 못했다. 조건 없이 옮길 수 없는 값으로 둔다.
  • unbash 가 담는 bash 문법의 버전 범위 — README 는 5.3 의 명령 치환 형태를 언급하지만 버전별 대응표는 없었다.
  • POSIX 명세 판본 사이의 차이 — 위의 서술은 현행 판을 기준으로 한 것이며, 달러 작은따옴표나 예약어 목록이 이전 판에서 어떠했는지는 확인 범위 밖이다.
  • 다른 셸 방언의 파서들 — zsh·mksh·dash 를 대상으로 하는 파서들이 같은 경계를 어떻게 다루는지는 다루지 않았다.

  • 파이프 안 while에서 변수가 사라지는 이유 - 서브셸 2026 — 서브셸 경계가 만드는 실무 사고
  • 셸 종료 코드와 set -e - 무엇을 잡고 무엇을 놓치는가 — 흐름 연산자가 실제로 무엇을 잡는지
  • --dry-run을 제대로 만드는 법 - 흉내가 아니라 검증 — 실행 전 검증이 보장하는 것과 못 하는 것
