エラーコード体系を作るということ - 番号か文字列か、そして誰が増やすのか

コードの価値は、クライアントがそれを見て別の行動を取れるときにだけ生まれる

2026-08-01 開発/インフラ

序論: クライアントがエラーメッセージの文字列を比較していた

決済画面のバグ報告を追いかけていて、こんなコードに出会った。

if (res.body.message.includes('already paid')) {
  goToReceipt();
}

最初の反応は「誰が書いたのか」だった。ところがサーバーの応答を開いてみると、その開発者を責められなくなった。サーバーが返しているのはステータスコード 400 と、人間が読む文が1つだけだったのだ。その状態で「すでに決済済みの注文」と「残高不足」を見分けるには、文を比較する以外に方法がない。

つまりこれはクライアントの落ち度ではなく、サーバーが契約を渡していないということだ。そしてこの契約の名前がエラーコードである。

ここからよくある反応は2つに割れる。一方は「ではエラーコードを作ろう」と一覧を作り始める。もう一方は「コードが増えると管理できない」と先送りする。どちらも同じものを見落としている。エラーコードは文書ではなく契約だ。文書は間違っていれば直せばよいが、契約は一度相手に渡したら自分の都合では変えられない。

この記事はその契約を設計する話だ。コードをいくつ作るかではなく、何を基準に切るべきか、なぜコードは変えられないのにメッセージは変えてよいのか、そして一覧が放置されないために何を自動化すべきかを扱う。

実行環境。以下のすべての出力は Windows 10 Pro (10.0.19045) 上で Node.js v22.16.0 (win32) により実際に実行した結果である。登場する API・エラーコード・チーム名はすべて架空で、注文と決済というありふれたドメインを借りて再現したものだ。スクリプトはファイルに保存して実行した。

この記事が扱わないこと。入力検証のエラーでどのフィールドが誤っているかを指し示す方法は応答スキーマの details の内側の問題なので別途扱う。一覧が放置されたときに誰がまだそのコードを受け取っているか探す方法も別の主題だ。ここではコードそのものの設計と寿命だけを見る。応答の他の契約面については API 文書を機械が読む契約へ と オフセットページングができないこと にある。

1. ステータスコードが答えられない問い

まず問題を正確に再現した。架空の決済 API を作り、6種類の異なる失敗を起こしてみる。

6種類の失敗がステータスコード1つにまとまった。観測された異なるステータス値は 400 だけだ。ところが右の列を見ると、クライアントがすべきことは6種類すべて違う。ステータスだけを見て分岐する関数を実際に書いて動かすと、6件すべてが判断不能に落ちた。

ここで誤解しやすい点がある。これはステータスコードが悪いという意味ではない。ステータスコードはプロキシとキャッシュと再試行層が読む軸であり、その目的には十分よく合っている。問題はその軸の解像度で利用者に何を見せるかを決めようとしたことだ。軸が違う。

1.1 だから人は文を比較し始める

--- 1-3. the workaround: matching the message string ---
missing id      show the raw message
bad id format   show the raw message
already paid    send user to the receipt
window closed   show the raw message
no money        offer another card
gateway down    retry in 30 seconds

--- 1-4. server rewords one message, nothing else changes ---
before : this order is already paid          -> send user to the receipt
after  : This order has already been paid.   -> show the raw message
same failure, different client action : true
nobody deployed the client. nobody changed the status. a copy edit did this.

文を比較したら3件は正確に分かれた。だからこの方法は生き残る。最初はうまく動き、誰も問題を感じない。

そのうち誰かが文面を整える。最後のブロックがその瞬間だ。先頭を大文字にして句点を打ち、語順を直しただけなのに、同じ失敗に対するクライアントの行動が変わった。クライアントを配布した人もいなければ、ステータスコードを変えた人もいない。文面の修正1つがやったことだ。

  • この事故はデプロイ履歴に残らない。サーバーのコード1行、しかも文字列リテラルだけが変わったからだ
  • テストにも引っかかりにくい。サーバーのテストはステータスコードを見るし、クライアントのテストは自分が用意した偽の応答を使う
  • 翻訳を付けた瞬間に1言語でしか動かない分岐になる。英語の文に合わせた比較は他の言語ですべて失敗する
  • 根本原因はサーバーが人間用のフィールドしか出していないことだ。クライアントはあるもので分岐するしかない

標準もこの点を明示している。HTTP API のエラー本文の形式を定めた RFC 9457 は、利用側が人間向けの詳細文をパースすべきではなく、その用途には拡張フィールドが適していると書いている。機械が読む軸を別に用意せよ、という意味だ。

打ち間違いの結果が決定的だ。番号の一覧が密に埋まった状態で1桁を間違えると別の実在コードにそのまま着地する。4つの誤入力のうち3つがそうなり、その3つは例外も警告もなく別の分岐へ行った。一方で単語を間違えると一覧に無いので既定分岐へ落ちる。5つの誤入力はすべてそこで止まった。

検索も同じだ。ログで数字だけを探すと、遅延時間やバイト数に偶然同じ数字があるため実際の2件を見つけるのに5行かかった。正確に探すにはフィールド名まで付ける必要がある。文字列は誤検出がゼロだった。

もちろん番号にも得るものがある。下の表が実行で確認した双方の性質だ。

性質番号 (E1043)文字列 (ORDER_ALREADY_PAID)判断

  • それ以外では16バイトはヘッダー1つより小さい。この費用で半年後の可読性を買うことになる
  • 両者を混ぜる折衷もある。文字列を契約とし、番号は補助フィールドとして一緒に送る形だ。ただし2つの軸を維持する費用が生じる
  • どちらにせよ一度決めたら変えられない。形を変えることは全コードを一度に変えることと同じだ

3. ドメインが増えると名前がぶつかる

文字列に決めても終わりではない。チームが1つのときに付けた名前は、チームが3つになった瞬間にぶつかる。3チームがそれぞれ平坦な一覧を作った状況を再現した。

11個のコードがゲートウェイを通って6個に減った。5件が衝突し、衝突した箇所では先に登録した側が勝ち、残りは消えた。消えた側のチームはこの事実を知らない。自分のサービスを単独でテストすればうまく動くからだ。

3-2 がその結果だ。配送照会の失敗で NOT_FOUND が来たのに、クライアントの分岐は注文チームが先に書いたものだ。分岐が間違っているのではなく、コードが曖昧なのだ。「無い」とだけ言って「何が」が無い。

接頭辞を付けると11個が11個のまま残った。衝突ゼロ。代償はコードあたり平均7.4文字だ。

ここでよく出る反論は「どうせサービス名が URL にあるのに、なぜまた入れるのか」だ。理由はコードが応答の外でも生きることにある。ログ集計、指標のラベル、サポートのチケット、クライアントの列挙型の中で、コードは URL 抜きで単独で現れる。その場で NOT_FOUND は何も語らない。

  • 接頭辞は一層で十分だ。会社・製品・ドメインを全部付けた42文字はログ列を壊すし、付けた情報のうち実際に使われるのは1つだけである
  • ORDER_ORDER_NOT_FOUND のような単語の重複は、ドメイン名と対象名が同じときに自動的に生じる。検査器で捕まえられる
  • _ERROR、_EXCEPTION、_FAILURE の接尾辞は情報量がゼロだ。エラーコード一覧にあるものはすべてエラーである
  • 区切り文字はログのパースだけ見れば何でも通るが、コードが列挙型のメンバー名や指標のラベルになった瞬間にアンダースコアだけが生き残る。ドットとハイフンは生成された定数名にできない
  • 長さの上限を決めておくほうがよい。32文字ならログ列の整列と可読性が同時に保てる

4. 安定性こそ契約だ - コードは変えられず、メッセージは変えてよい

この記事で最も重要な節だ。1月に配布されて利用者の携帯に入ったクライアントがあるとしよう。取り戻せない。その状態でサーバーを2通りに変えてみた。

node v22.16.0 / win32
--- 4-1. baseline: the shipped client against server v1 ---
case      code                          client action
------------------------------------------------------------------------
paid      ORDER_ALREADY_PAID            showReceipt
funds     PAYMENT_INSUFFICIENT_FUNDS    offerAnotherCard
window    ORDER_WINDOW_CLOSED           reopenPaymentSheet

--- 4-2. v2: every message rewritten, codes untouched ---
paid      showReceipt           same as before: true
funds     offerAnotherCard      same as before: true
window    reopenPaymentSheet    same as before: true
branches broken by the rewrite : 0 / 3

--- 4-3. v3: one code renamed for readability, messages same as v2 ---
paid      ORDER_PAYMENT_ALREADY_COMPLETED   showGenericError      BROKEN
funds     PAYMENT_INSUFFICIENT_FUNDS        offerAnotherCard      ok
window    ORDER_WINDOW_CLOSED               reopenPaymentSheet    ok
branches broken by one rename  : 1 / 3
the user now lands on a generic error screen instead of the receipt.

対比が鮮明だ。メッセージを3つとも書き直しても壊れた分岐はゼロだった。文面をいくら変えてもクライアントはコードを見るからだ。一方で読みやすいという理由でコード名を1つ変えると、その分岐は即座に死んだ。利用者はレシートではなく汎用エラー画面を見る。

これが「メッセージは変えてよいがコードは変えられない」という規則の根拠だ。そしてこの規則は機械が読む識別子を渡したときにだけ成り立つ。コードが無ければ逆になる。クライアントが文に依存するのでメッセージのほうが凍りつく。大規模な API の設計指針も同じ順序で書いている。機械用の識別子を一緒に渡した API は文面を変えられるが、識別子なしで始めた API は文面を固定しなければならない、というものだ。

4.1 それでも名前を変えたいときは

--- 4-4. a release gate that compares the published code set ---
v2 (messages only)
  added   : (none)
  removed : (none)
  verdict : allow
v3 (one rename)
  added   : ORDER_PAYMENT_ALREADY_COMPLETED
  removed : ORDER_ALREADY_PAID
  verdict : REJECT - a published code disappeared

--- 4-5. the same rename, done without breaking anyone ---
paid      ORDER_ALREADY_PAID            showReceipt           ok
funds     PAYMENT_INSUFFICIENT_FUNDS    offerAnotherCard      ok
window    ORDER_WINDOW_CLOSED           reopenPaymentSheet    ok
v4 (rename announced, old code still emitted)
  added   : (none)
  removed : (none)
  verdict : allow

ゲートは単純だ。前バージョンのコード集合と比べ、消えたコードがあればビルドを止める。コードの追加は通す。知らないコードはクライアントで既定分岐に落ちるだけで壊れないからだ。

本当に名前を変えたいなら v4 のようにする。新しい名前を代替コードのフィールドで告知するだけにし、通信に出る値は据え置く。実際の入れ替えは旧コードの放出件数がゼロになったのを確認してからだけ行う。そしてそれは文書ではなくトラフィックだけが教えてくれる。

  • コード名は値であってラベルではない。良い名前を後から付けようとする誘惑が最も危険だ
  • 同じ理由でコードの HTTP ステータスも変えられない。プロキシと再試行層がそれで判断している
  • 再試行の可否もコード単位で固定だ。これが変わるとクライアントの自動再試行の挙動が音もなく変わる
  • 逆に details にフィールドを追加するのはいつでも可能だ。加算的な変更なので、古いクライアントは無視すればよい
  • コードを消すことは名前を変えるのと同じくらい危険だ。廃止の手順を別に用意すべき理由である

サーバーが文を選ぶ方式はフォールバックの連鎖が肝だ。要求された言語があればそれを、無ければ既定言語を、それも無ければコード文字列そのものを返す。最後の段階は奇妙に見えるが空の画面よりはましだ。

5-3 がクライアント自前翻訳の弱点を示している。サーバーが新しいコードを出し始めると、そのコードを知らない配布版には見せる文が無い。クライアントは再配布の周期が長く、利用者は更新を先送りするので、この状態は何か月も続く。

5-2 がクライアント組み立ての利点だ。金額をサーバーの文に埋め込まず数値と通貨だけを送れば、クライアントが自分のロケールの書式で組み立てる。サーバーがすべての言語の桁区切り規則を知る必要がない。

だから答えはどちらか一方ではなく両方だ。5-4 のようにクライアントは自前の翻訳があればそれを使い、無ければサーバーの文をそのまま出す。新しいコードが出ても画面は空にならず、既存のコードはロケール書式を守る。

  • 5-5 がやってはいけないことを示している。コードを言語ごとに作ると分岐は1言語でしか生きない。3言語のうち1つでしか発火しなかった
  • コードは識別子であって文ではない。言語を持たないことがコードの性質である
  • 翻訳のカバレッジは CI で表にできる。5-6 では6つのマスが空だった
  • 重要なのは翻訳の穴とコードの欠落では重みが違うことだ。翻訳が無ければ既定言語で耐えられるが、コードが無ければクライアントは何も決められない
  • サポートの観点もある。利用者が撮って送ってくるのは文だ。文の中にコードを一緒に出しておくと問い合わせの処理時間が大きく減る

6. 機械が読むフィールドと人が読むフィールド

ここで応答本文の全体を設計する。原則は1つだ。各フィールドが誰のためのものかを決め、それを契約として書く。

node v22.16.0 / win32
--- 6-1. the response body, split by audience ---
{
  "error": {
    "code": "PAYMENT_GATEWAY_UNAVAILABLE",
    "message": "The payment provider is not responding. Please try again shortly.",
    "retryable": true,
    "retryAfterMs": 30000,
    "traceId": "01J8ZQ9K3M7T4V2N6P0R5S8W1X",
    "details": [
      {
        "subcode": "GATEWAY_TIMEOUT",
        "attempt": 2
      }
    ]
  }
}

field         for       contract
------------------------------------------------------------------------------
code          machine   the only field a branch may read
message       human     never parsed, freely reworded, localized
retryable     machine   decides whether the transport retries at all
retryAfterMs  machine   how long to wait, absent means caller decides
traceId       both      machine copies it, human quotes it to support
details       machine   structured extras, additive only

この表が契約書であり、この契約が4節の規則を作る。以下は各フィールドが何を変えてよいかの整理だ。

フィールド対象変えてよいか理由
code機械公開後は絶対に不可分岐が読む唯一のフィールド
message人間いつでもパースしないと契約している
HTTP ステータス機械コード単位で固定プロキシと再試行層がこれで判断
retryable機械コード単位で固定自動再試行の挙動が変わる
retryAfterMs機械値は毎回異なる無ければ呼び出し側が決める
traceId両方毎回異なる設計上不透明な値
details機械フィールド追加のみ加算的な変更だけが安全

6.1 再試行の可否をコードに入れるか、フィールドに出すか

現場で最も意見が割れる点だ。2つの設計を並べて動かした。

--- 6-2. design A: retryability baked into the code ---
PAYMENT_GATEWAY_UNAVAILABLE_RETRYABLE     retry=true
PAYMENT_GATEWAY_UNAVAILABLE_PERMANENT     retry=false
ORDER_ALREADY_PAID_PERMANENT              retry=false

--- 6-3. design B: retryability as a field ---

PAYMENT_GATEWAY_UNAVAILABLE               retry=false

--- 6-4. now the operational question: can it flip at runtime? ---

  design A series : {"PAYMENT_GATEWAY_UNAVAILABLE_RETRYABLE":2,"PAYMENT_GATEWAY_UNAVAILABLE_PERMANENT":2}
  design B series : {"PAYMENT_GATEWAY_UNAVAILABLE":4}

コードの数だけ見れば4対3で大きな差ではない。違いは 6-4 で出る。決済事業者の障害が続いて回路遮断器が開くと、同じ失敗が再試行可から不可へ移る。A の設計ではそのときコード文字列そのものが動く。

その結果が最後の2行だ。コードで束ねたダッシュボードで1つの事象が2本に割れた。B の設計では1本のまま保たれる。指標を割ることがなぜ悪いかは障害対応の最中に分かる。グラフが突然半分になり、新しい名前のグラフが生まれるのだが、それが新しい障害なのか同じ障害なのかその瞬間には分からない。

--- 6-5. a transport layer that only reads the machine fields ---
PAYMENT_GATEWAY_UNAVAILABLE     retryable=true      sleep 30000ms then retry
ORDER_ALREADY_PAID              retryable=false     surface to caller
SOMETHING_WE_ADDED_LAST_WEEK    retryable=undefined surface to caller

--- 6-6. what happens when a client parses the human field ---
version contains "try again"      contains "unavailable"    text
--------------------------------------------------------------------------------------------------------------
v1      true                      true                      The payment provider is unavailable. Please try again shortly.
v2      false                     false                     We could not reach the payment provider. Retry in a moment.
v3      false                     true                      Payment temporarily unavailable.
two heuristics, three wordings, no stable answer. meanwhile:
v1      code=PAYMENT_GATEWAY_UNAVAILABLE retryable=true  -> unchanged
v2      code=PAYMENT_GATEWAY_UNAVAILABLE retryable=true  -> unchanged
v3      code=PAYMENT_GATEWAY_UNAVAILABLE retryable=true  -> unchanged

--- 6-7. the trace id is the field support actually uses ---
has traceId   what support can do
----------------------------------------------------------------------
true          exact match, 1 request
false         scan by code + time window, thousands of rows
  • 6-5 の3行目が重要だ。フィールドがそもそも無いとき再試行不可として読んだ。これが安全な既定値である。無いフィールドを「再試行可」と解釈すると、新しいコードが出るたびに無限再試行が生まれる
  • 6-6 が1節の話を別の角度から再確認する。3つの文面に2つの当て推量を当ててみると安定した答えが1つも無かった。同じ期間、コードと再試行フィールドは変わらなかった
  • traceId はコードと役割が違う。コードは失敗の種類を、追跡 id はその1件を指す。サポートが実際に使うのは後者だ
  • 追跡 id が無いとコードと時間帯でなめる必要があり、その範囲は数千件になる。すべてのエラー応答に必ず入れるという規則は安くて効果が大きい
  • details はコードで分けるほどではない細部を入れる場所だ。ここに入れられるものを新しいコードにしないことが一覧を小さく保つコツである

  • すべてのコードに所有者を書いておく。所有者のないコードは半年後に誰も消せない
  • 最後の行が最も重要だ。UNKNOWN_ERROR が30日で918件ならそれはコードではなく分類されていない失敗918件である。分割の第一候補だ
  • 一覧が放置されたという合図は、数ではなく包括コードの比率で読むほうが正確だ

10. チェックリストとやってはいけないこと

最後に、いま手元にある API へすぐ当ててみる一覧だ。

  • クライアントのコードにメッセージ文字列を比較する分岐が0件である
  • 同じ HTTP ステータスで出る失敗がコードで区別できる
  • すべてのエラー応答に code と追跡 id が必ず入る
  • 再試行フィールドが無いとき、再試行層が不可として読む
  • コードに再試行の可否が文字列で埋め込まれていない
  • ドメイン接頭辞があり、接頭辞なしの NOT_FOUND 類が0件である
  • コード一覧がファイル1つにあり、文書とクライアント定数はそこから生成される
  • リリースゲートが消えたコードを捕まえる
  • 廃止対象コードの放出件数を計測している
  • 各コードに所有者が書かれている
  • 包括コードが全エラーの何パーセントかを把握している

そしてやってはいけないこと。

  • ❌ HTTP ステータスだけで分岐する — 同じ400が6通りの理由で返る
  • ❌ メッセージ文字列の部分一致で分岐する — 文面の手直し一回で死ぬ
  • ❌ 読みやすいという理由で公開済みコード名を変える — 配布済みクライアントは戻せない
  • ❌ 接頭辞のない NOT_FOUND — ドメインが増えれば必ず衝突する
  • ❌ コード文字列に再試行の可否を埋める — 障害中に指標が2本に割れる
  • ❌ _ERROR、_EXCEPTION の接尾辞 — 情報量ゼロで長さだけ増える
  • ❌ コードを言語別に翻訳する — コードは識別子であって文ではない
  • ❌ 文書とクライアント定数を手で維持する — 必ずずれる
  • ❌ 廃止日だけ書いてトラフィックを見ない — 消したのに誰かがまだ受け取っていた
  • ❌ 「あとで使うかもしれない」でコードを作る — 未使用コードは一覧の信頼を削る

まとめるとこうだ。エラーコードは文書ではなくクライアントと結ぶ契約である。契約の価値は、相手がそれを見て別の行動を取れるときにだけ生まれる。だから数ではなく行動で分かれる単位で切るべきであり、一度出したコードはメッセージと違って変えられない。この2文が残りの規則をすべて作る。

# エラーコード体系の設計 — コピペ用スキーマ・判断表・手順

> 出典: braindetox.kr — エラーコード体系を作るということ
> 根拠: Windows 10 / Node.js v22.16.0 での実行検証（架空の注文・決済APIで再現）
> このファイルをそのままAIに貼り、「この基準でうちのエラー応答を点検して」と書けば使えます。
> 大前提: エラーコードはクライアントと結ぶ契約である。一度公開したコードは、メッセージと違って変えられない。

## 0. 判断の出発点 — このコードに価値はあるか

コードを1つ増やす前にこの質問に答える。3つとも「いいえ」なら、そのコードは作らない。

| 質問 | 「はい」のときの意味 |
|---|---|
| クライアントがこのコードを見て**別の画面・別の動作**をするか | 分岐する価値がある |
| 運用者がこの失敗だけを**個別に数える・通知を張る**必要があるか | 指標の軸として価値がある |
| 自動リトライの可否が**違う**か | リトライ契約として価値がある |

- 数ではなく**行動で分かれる単位**で切る
- 同じ画面・同じ動作で終わる2つの失敗は、コード1つと `details` で足りる
- 「あとで使うかもしれない」は根拠ではない。コードは増やすのは簡単で、減らすのはほぼ不可能だ

## 1. 応答本文のスキーマ — 機械用と人間用を分ける

```json
{
  "error": {
    "code": "PAYMENT_GATEWAY_UNAVAILABLE",
    "message": "決済事業者が応答していません。しばらくしてからお試しください。",
    "retryable": true,
    "retryAfterMs": 30000,
    "traceId": "01J8ZQ9K3M7T4V2N6P0R5S8W1X",
    "details": [
      { "subcode": "GATEWAY_TIMEOUT", "attempt": 2 }
    ]
  }
}
```

| フィールド | 対象 | 変えてよいか | 規則 |
|---|---|---|---|
| `code` | 機械 | **絶対に不可**（公開後） | 分岐が読んでよい唯一のフィールド |
| `message` | 人間 | **いつでも** | 決してパースしない。言語ごとに異なる |
| `retryable` | 機械 | コード単位で固定 | 無い場合は `false` として読む |
| `retryAfterMs` | 機械 | 値は毎回異なる | 無い場合は呼び出し側が決める |
| `traceId` | 両方 | 毎回異なる | 人は問い合わせに添え、機械はログをつなぐ |
| `details` | 機械 | **フィールド追加のみ** | 既存フィールドの削除・意味変更は禁止 |
| HTTPステータス | 機械 | コード単位で固定 | プロキシ・リトライ層がこれで判断する |

- `retryable` を**コード文字列に埋め込まない**（`..._RETRYABLE` / `..._PERMANENT`）
- 理由: 同じ失敗が状況によってリトライ可・不可に振れると、**コード自体が動いて指標が2本に割れる**
- リトライ可否は**フィールド**、失敗の種類は**コード**。軸が違う

## 2. コード形式の判断表

| 判断項目 | 選択肢 | どんなとき | 代償 |
|---|---|---|---|
| 番号 vs 文字列 | **文字列を推奨** | ログ・スタックトレースを人が読む | 応答あたり15〜20バイト増 |
| | 番号 | 帯域が本当に高価（組込み・SMS） | 半年後に誰も読めない |
| 名前空間 | **ドメイン接頭辞** | ドメインが2つ以上 | コード長が7文字前後増える |
| 区切り | **アンダースコア** | コードが列挙型・メトリクスラベルになる | なし |
| | ドット・ハイフン | 階層を視覚的に見せたい | 列挙型のメンバー名にできない |
| 大文字小文字 | **すべて大文字** | 定数であることを示す | なし |
| 接尾辞 | **付けない** | `_ERROR` `_EXCEPTION` は情報量ゼロ | なし |
| 長さ | **32文字以下** | ログ列の整列と可読性 | 超えると略語が要る |

### 番号を選ぶと何を失うか（実行で確認）

- 1文字の打ち間違いが**別の有効なコード**になり、静かに誤った分岐へ行く。文字列は大抵一覧に無く既定分岐に落ちる
- ログで `1043` を探すと `latency_ms=1043` や `bytes=1043` まで一緒に引っかかる。フィールド名まで付けないと正確にならない
- 得られるもの: 固定幅の整列、数値帯によるドメイン区分

## 3. 名前空間の規則

```
{ドメイン}_{対象}_{状態}     例) ORDER_WINDOW_CLOSED
{ドメイン}_{状態}            例) SHIPPING_NOT_FOUND
```

- 接頭辞のない `NOT_FOUND` `EXPIRED` `INVALID` `RATE_LIMIT` は、**ドメインが増えれば必ず衝突する**
- 衝突するとゲートウェイでは**先に登録した側が勝ち**、残りは消える。クライアントには何が欠けたか分からない
- 単語を繰り返さない: `ORDER_ORDER_NOT_FOUND` は不可
- 情報のない接尾辞を付けない: `..._ERROR` `..._EXCEPTION` `..._FAILURE` は不可
- 接頭辞は**一層**で十分。`COMMERCE_ORDER_PAYMENT_WINDOW_CLOSED_ERROR` は42文字でログ列を壊す

## 4. 安定性の規則 — 何を変えられて何を変えられないか

| 変更 | 可否 | 理由 |
|---|---|---|
| メッセージ文面の全面書き換え | **可** | 誰もパースしないという契約だから |
| 翻訳の追加・修正 | **可** | コードに言語は無い |
| `details` にフィールド追加 | **可** | 加算的な変更 |
| 新しいコードの追加 | **可**（下の手順） | 知らないコードは既定分岐に落ちる |
| コード名の変更 | **不可** | 配布済みクライアントの分岐が即死する |
| コードの削除 | **不可**（廃止手順のみ） | 同上 |
| コードのHTTPステータス変更 | **不可** | プロキシ・リトライ層がこれで判断する |
| コードの `retryable` 変更 | **不可** | 自動リトライの挙動が変わる |

- **名前を変えたいなら**: 新しい名前を `supersededBy` フィールドで**告知するだけ**にし、通信に出る値は据え置く
- 実際の入れ替えは、旧コードのトラフィックが**ゼロになったのを確認してから**だけ
- リリースゲート: 前バージョンのコード集合と比べ、**消えたコードがあればビルド失敗**

## 5. 翻訳とメッセージ

- サーバーが `Accept-Language` で文を選ぶ。無い言語は**既定言語へフォールバック**、それも無ければコード文字列
- クライアントが自前の翻訳だけを使うと、**自分の知らない新しいコードで画面が空になる**
- だから両方送る。クライアントは自前の訳を優先し、無ければサーバーの `message` をそのまま表示する
- 数値・金額・日付はサーバー文に埋め込まず `details` か `params` で渡し、**クライアントがロケール書式で組み立てる**
- **コード自体を翻訳しない。** `ORDER_ALREADY_PAID_KO` のようなものを作ると、分岐が1言語でしか生きない
- CIに言語カバレッジのレポートを置く。翻訳の穴はフォールバックで耐えるが、**コードの欠落は耐えられない**

## 6. コードを増やす手順

1. **行動を先に書く。**「クライアントがXをする」を一文で。書けないならコードは要らない
2. **既存の一覧で同じ行動を探す。** 同じ行動＋同じHTTPステータス＋同じリトライ可否なら、**新コードではなく `details` だ**
3. 名前を付ける。`{ドメイン}_{対象}_{状態}`、大文字、アンダースコア、32文字以下
4. レジストリ（単一ファイル）に追加: `code` / `http` / `retryable` / `action` / `since` / `owner`
5. リンターを回す（第8節）。エラー0でなければマージしない
6. 文書とクライアント定数は**手で書かない。** レジストリから生成する
7. 所有者を書く。所有者のないコードは半年後に誰も消せない

## 7. コードを廃止する手順

1. `deprecated` の日付と `supersededBy` をレジストリに書く — **この時点では何も消えない**
2. サーバーは旧コードを出し続ける。新しいコードは並べて追加する
3. 旧コードの**放出件数を計測**する
4. 30日連続でゼロなら削除候補。ゼロでなければ**先に呼び出し元を探す**
5. 削除はレジストリだけ。クライアント定数と文書は再生成で追随する

- 廃止の日付がコードを消すのではない。**トラフィックが消す**
- `UNKNOWN_ERROR` や `INTERNAL` の放出件数が大きいなら、それはコードではなく**分類されていない失敗の山**だ。分割の第一候補

## 8. 自動検証 — レジストリ一箇所、残りは生成と照合

レジストリ自体のリント規則:

- [ ] `duplicate-code` — 同じ名前が二度登録されている
- [ ] `bad-shape` — `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*` に違反
- [ ] `too-long` — 32文字超
- [ ] `repeated-word` — 接頭辞と本体が同じ単語を繰り返す
- [ ] `useless-suffix` — `_ERROR` `_EXCEPTION` `_FAILURE` で終わる
- [ ] `vague-name` — `INTERNAL` `UNKNOWN_ERROR` `INVALID` `FAILED` のような包括語
- [ ] `no-namespace` — アンダースコアが無く、ドメイン接頭辞が無い
- [ ] `unstable-http` — 同じコードが2つのステータスで登録されている
- [ ] `retryable-4xx` — リトライ可なのに401/408/429でない4xx
- [ ] `non-retryable-5xx` — 5xxなのにリトライ不可
- [ ] `deprecated-orphan` — 廃止の印だけあり代替コードが無い

クライアントのソースとの照合:

- [ ] **死んだ分岐** — クライアントが分岐しているのにレジストリに無いコード。決して発火しない → **ビルド失敗**
- [ ] **未処理のコード** — サーバーが出せるのに分岐が無いコード → カバレッジの数値で報告
- [ ] 死んだ分岐には**最も近い登録済みコードを提案**する（トークンの重なり率）

生成物:

- [ ] クライアント定数（凍結オブジェクト・列挙型）
- [ ] 文書の表（コード / HTTP / リトライ / クライアントがすべきこと）
- [ ] コード一覧のスナップショット — リリースゲートが前バージョンと比較する

## 9. 点検リスト

- [ ] クライアントのコードに**メッセージ文字列を比較する分岐が0件**である
- [ ] 同じHTTPステータスで出る失敗が**コードで区別**できる
- [ ] すべてのエラー応答に `code` と `traceId` が**必ず**入る
- [ ] `retryable` が無いとき、リトライ層が**`false` として読む**
- [ ] コードにリトライ可否が**文字列で埋め込まれていない**
- [ ] ドメイン接頭辞があり、接頭辞なしの `NOT_FOUND` 類が**0件**である
- [ ] コード一覧が**ファイル1つ**にあり、文書とクライアント定数はそこから**生成**される
- [ ] リリースゲートが**消えたコード**を捕まえる
- [ ] 廃止対象コードの**放出件数を計測**している
- [ ] 各コードに**所有者**が書かれている
- [ ] 同じ行動＋同じステータス＋同じリトライ可否のコード群を**定期的に見直す**
- [ ] `UNKNOWN_ERROR` 類が全エラーの何パーセントかを**把握している**
- [ ] 翻訳カバレッジのレポートがCIにある

## 10. やってはいけないこと

- ❌ HTTPステータスだけで分岐する — 同じ400が6通りの理由で返る
- ❌ メッセージ文字列の部分一致で分岐する — 文面の手直し一回で死ぬ
- ❌ 読みやすいという理由で公開済みコード名を変える — 配布済みクライアントは戻せない
- ❌ 接頭辞のない `NOT_FOUND` — ドメインが増えれば必ず衝突する
- ❌ コード文字列にリトライ可否を埋める — 指標が2本に割れる
- ❌ `_ERROR` `_EXCEPTION` の接尾辞 — 情報量ゼロで長さだけ増える
- ❌ コードを言語別に翻訳する — コードは識別子であって文ではない
- ❌ 文書とクライアント定数を手で維持する — 必ずずれる
- ❌ 廃止日だけ書いてトラフィックを見ない — 消したのに誰かがまだ受け取っていた
- ❌ 「あとで使うかも」でコードを作る — 未使用コードは一覧の信頼を削る

参考資料

  • RFC 9457 - Problem Details for HTTP APIs (2023-07, Standards Track). HTTP API のエラー本文の標準形式。利用側が人間向けの詳細文をパースすべきではなく拡張フィールドを使えという指針、問題タイプの識別子を主たる識別子とせよという規定が、この記事の1節と6節の根拠である。RFC 7807 を置き換える
  • RFC 9110 - HTTP Semantics (2022-06, Standards Track). 4xx・5xx ステータスコード階層の定義。ステータスコードがどの軸を表すよう設計されたかを確認するために参照した
  • AIP-193 Errors. 大規模 API の設計指針。機械が読む識別子を一緒に提供する API はエラー文面を変えられるが、識別子なしで始めた API は文面を固定しなければならないという記述が、この記事の4節の論旨と直接対応する
