The find and xargs Whitespace Trap - One Filename Breaks the Whole Script

Not another 「just use -print0」 post - real output from things we broke on purpose

Jul 29, 2026 Dev & Infra

Introduction: the file that got deleted was the wrong one

You run a cleanup script. One error line appears: rm: cannot remove './data': No such file or directory. It looks harmless. It just means something was already gone, right? Then you look at the directory again and find that the file you meant to delete is still sitting there, and a different file you had no reason to touch has vanished.

This article starts by reproducing that exact moment. The cause, to state it up front, is a single space inside a filename. And the story does not end with the sentence 「just use -print0」. Ending there leaves you not knowing why things break, and it hides three further classes of defect that survive even after you fix the separator.

So this is not a conceptual explanation. We created a temporary directory, built hostile filenames by hand, and pasted in the output of things that actually broke. Every code block below is a real run, not an illustration typed from memory. The order is as follows.

  • Why it breaks — the fundamental mismatch between filenames as byte strings and pipelines that cut text
  • How it breaks — spaces, newlines, dashes and globs reproduced one at a time, with a check on what actually got deleted
  • What is safe — null separation, the two options on read, the three shapes of -exec, argument length limits, and the character of -delete

Safety notice before you run anything. Every reproduction in this article was performed inside a freshly created temporary directory and nowhere else. Where rm * or rm -rf appears in the text, it is confined to that temporary directory and its children. Do not follow along on a real server or in a working directory. In particular the 「filename starting with a dash」 reproduction further down wipes an entire subdirectory with a single rm *. When testing destructive commands, first replace rm with echo or ls and inspect the target list with your own eyes before running the real thing.

1. The environment and what this article rests on

All output below comes from real runs. The environment was as follows.

$ uname -s
MINGW64_NT-10.0-19045
$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)
$ find --version | head -1
find (GNU findutils) 4.10.0
$ xargs --version | head -1
xargs (GNU findutils) 4.10.0

This is MSYS2 / Git Bash on Windows 10, with GNU findutils 4.10.0 and bash 5.2. Word splitting, null separation and -exec behaviour are the same GNU code paths as on Linux, so the results carry over directly. That said, three constraints are specific to this environment and are stated up front, because you need them in order to judge the results.

  • Filenames containing a backslash cannot be created here, because it is the path separator on Windows. So the backslash reproduction uses a string sent through a pipe instead of a file. Since the point is to observe what read does, the result is the same.
  • getconf ARG_MAX returns undefined on this platform. The argument length section therefore uses the real numbers reported by xargs --show-limits.
  • We could not reproduce a glob length overflow. Creating 40,000 files and expanding a 1.9 MB glob did not fail here. On Linux that size would have produced Argument list too long. What was not confirmed is written down as not confirmed. Instead we include the way to check the limit on your own machine.

Two verdict criteria were fixed for the whole article. Does the real file count match the count the script processed, and does every iteration point at a path that actually exists. If those two disagree, the pipeline is already broken. Counting was done with find . -type f -printf 'x\n' | wc -l. That prints one fixed character per file instead of the filename, so the act of counting is itself immune to hostile names.

2. Why it breaks - filenames are bytes, pipelines cut text

The root cause is simple. What the kernel allows in a filename and how a shell pipeline splits a list do not agree.

Under POSIX there are effectively only two bytes you cannot put in a filename: the null byte and the slash. Slash is the path separator, and null terminates a string. Everything else is legal. Spaces, newlines, tabs, asterisks, quotes and dashes can all be perfectly ordinary parts of a filename.

Meanwhile find ... | xargs cuts text. The POSIX xargs specification states that arguments on standard input are 「delimited by unquoted blank characters, unescaped blank characters, or newline characters」. In other words xargs was never given any basis for distinguishing a space inside a filename from a space between filenames. Both are the same 0x20 byte.

One framing matters here. This is not a defect in the tool. xargs was not designed to receive a list of files; it was designed to receive a whitespace separated argument string. The mismatch appeared when we started using it as a file list transport. So the fix is not 「repair xargs」 but 「use a separator that can never appear in a filename」. The null byte is that separator.

3. Reproduction 1: a space, and the wrong file gets deleted

Here is the most common accident, reproduced exactly. The directory holds two files. data backup.log is the one we want gone; backup.log must not be touched. find matches only data*.

--- before ---
backup.log
data\ backup.log
--- find output (what xargs receives) ---
./data backup.log
--- run: find . -name 'data*' | xargs rm ---
rm: cannot remove './data': No such file or directory
  exit=123
--- after ---
data\ backup.log

Read that slowly. ls -b renders special characters with backslashes, so data\ backup.log is one file containing a space. find matched only that one file. Yet after the run the only survivor is data backup.log. That is:

  • The file we wanted deleted survived. rm received the name ./data and no such file existed.
  • backup.log, which was never matched, is gone. It was rm's second argument.
  • There is exactly one error line. The second argument really existed, so that deletion succeeded quietly.

The damage ran in precisely the opposite direction, and the log retains only a harmless looking line about a file that was not there. That is why this pattern is dangerous in production: it trains you to believe the error message points at the damage.

3.1 Even -t will not show it to you

xargs -t echoes the command line before running it. It exists for debugging. In this accident it does not help.

$ find . -name 'data*' | xargs -t echo RM
echo RM ./data backup.log
RM ./data backup.log

The echoed line is echo RM ./data backup.log. You cannot tell whether that is one argument or two. It looks fine. With null separation, on the other hand, xargs -t adds quotes.

$ find . -name 'data*' -print0 | xargs -0 -t ls -b
ls -b './data backup.log'
./data\ backup.log

Quotes mean one argument. When auditing a pipeline, do not just add -t; add -0 -t so the real boundaries become visible.

4. Reproduction 2: a newline, and two files iterate three times

A space is at least visible. A newline is not. It is tempting to assume nobody puts a newline in a filename, but they arrive in practice through web uploads, external integrations and copy-paste mishaps. Creating one takes a single line.

$ touch $'line1\nline2.txt'
$ touch plain.txt
$ ls -b
line1\nline2.txt
plain.txt

There are two files. What ls -b renders as \n is one name containing a newline. Now put that through the most common loop there is.

--- find . -type f | while IFS= read -r f ---
GOT: [./line1] exists=NO
GOT: [line2.txt] exists=NO
GOT: [./plain.txt] exists=yes
--- true file count (find -printf) ---
2

Two real files, but the loop ran three times and two of those iterations pointed at paths that do not exist. Two things deserve attention here.

  • IFS= and -r were already present and it still broke. Those two options fix what happens after a line has been received; they cannot change the rule used to cut lines apart. The separator problem must be solved on the producer side, at find.
  • It fails quietly. Running rm on the two exists=NO entries would at least have printed two errors, but with chmod, touch or statistics gathering, where failure leaves no trace, your numbers simply come out wrong and nobody notices.

Your counting is contaminated too. Counting files with find . -type f | wc -l returns 3 in that directory. The truth is 2. Do not count filenames; count one character per file. find . -type f -printf 'x\n' | wc -l is that shape. Where -printf is unavailable, find . -type f -exec printf 'x\n' {} + | wc -l gives the same answer.

5. Reproduction 3: a leading dash, and one rm wipes a directory

This is the most dangerous reproduction in the article. It was executed only inside a temporary directory. The layout is this: a subdirectory project/ holding two files, plus an empty file literally named -rf, plus note.txt.

--- before ---
-rf
note.txt
project
tree:
.
./-rf
./note.txt
./project
./project/README
./project/src
./project/src/main.c
--- run: rm * (inside the temp directory) ---
  exit=0
--- after ---
.
./-rf

The whole directory is gone. Exit status 0. Not one error line. The shell expands * into rm -rf note.txt project, and rm reads -rf as an option rather than a file. Recursive deletion has been switched on.

The control case is the same layout with the -rf file removed.

--- control: rm * with no dash file present ---
rm: cannot remove 'project': Is a directory
  exit=1
--- after ---
.
./project
./project/README
./project/src
./project/src/main.c

rm refuses directories by default. That safety catch was disabled by one empty file. Which means that simply creating a file named -rf is enough to make somebody else's cleanup script perform a recursive delete, and this is why find and xargs handling is classified as a security matter rather than a cosmetic one.

5.1 Watching a filename become an option

A file named --help makes it even more blatant.

$ touch ./--help ./real.txt
$ ls * | head -4
Usage: ls [OPTION]... [FILE]...
List information about the FILEs (the current directory by default).
Sort entries alphabetically if none of -cftuvSUX nor --sort is specified.

$ ls -- *
--help
real.txt

You asked for a file listing and got a help page. Adding -- makes everything after it an operand, and normal service resumes.

5.2 Three defences and the limits of each

$ ls *          # -rf is swallowed as options
normal.txt
$ ls -- *       # end-of-options marker
-rf
normal.txt
$ ls ./*        # path prefix
./-rf
./normal.txt
$ find . -name '-rf' -exec ls -b {} \;   # find is immune by construction
./-rf
  • -- (end of options) — the most standard answer. Be aware that some very old utilities do not support it, and a few tools still do their own parsing afterwards.
  • A ./ prefix — works with every tool. Even if the name is -rf, ./-rf does not begin with a dash. This is the most robust defence. The cost is a ./ in your output.
  • find's -exec — immune from the start. Paths from find already include the starting point, and they are handed to execve without passing through a shell, so nothing re-parses them. That is why ls -b behaved normally on the last line above.

The working rule follows: when passing names created by users or external systems to a command, add --, or use the ./ prefixed paths that find already produces.

6. Reproduction 4: ls piped into grep is not a file list

「Don't parse ls」 is widely repeated advice, usually without the reason. Break it once and the reason becomes obvious. Three files exist, one containing a newline.

--- true file count ---
3
--- ls | wc -l ---
4
--- ls | grep log ---
log1
log2.txt
my log.txt
--- ls | grep log | wc -l ---
3

Three real files, but ls emits 4 lines. What comes out of grep is 3 lines, which looks correct, so it passes a visual review. What matters is what happens when that list is actually used.

$ ls | grep log | xargs ls
ls: cannot access 'log1': No such file or directory
ls: cannot access 'log2.txt': No such file or directory
ls: cannot access 'my': No such file or directory
ls: cannot access 'log.txt': No such file or directory

Four names were looked up and not one of them is a real file. The name containing a newline split into two lines, and the name containing a space then split into two arguments.

There is a less known trap on top of that. ls emits different bytes depending on its output target. Writing to a terminal it substitutes unprintable characters with ? and similar; writing to a pipe it passes the raw bytes straight through. In other words the shape a person inspected and the bytes the next stage receives are not the same. That is the classic route by which a reviewed pipeline breaks in production.

6.1 Unquoted command substitution breaks twice

for f in $(find ...) is more common than ls | grep and worse, because word splitting and glob expansion happen back to back. We checked in a directory of four files, one of which is literally named *.

$ ls -b
*
a.txt
b.txt
my\ file.txt
$ for f in $(find . -type f); do printf 'GOT [%s]\n' "$f"; done
GOT [./a.txt]
GOT [./b.txt]
GOT [./my]
GOT [file.txt]
GOT [./*]
GOT [./a.txt]
GOT [./b.txt]
GOT [./my file.txt]
--- count ---
real files = 4
iterations = 8

Four files, eight iterations. Two stages stacked up.

  • Word splitting — ./my file.txt split into ./my and file.txt.
  • Glob re-expansion — the filename ./* was reinterpreted as a pattern and swelled into the whole directory, so a.txt and b.txt were each processed twice.

There is a curious detail. The final GOT [./my file.txt] has its space intact, because the results of glob expansion are not split again. The same file was processed once broken and once whole. That asymmetry is exactly why such pipelines 「work sometimes」.

7. -print0 and -0 - what comes back to life

Now the remedy. The null byte is the one byte that can never occur in a filename, which makes it a safe separator. We re-ran both earlier accidents.

--- find -print0 | xargs -0 -t (the space case) ---
ls -b './data backup.log'
./data\ backup.log

--- find -print0 | while IFS= read -r -d '' (the newline case) ---
GOT: [./backup.log] exists=yes
GOT: [./data backup.log] exists=yes
GOT: [./line1
line2.txt] exists=yes

All three files report exists=yes. The name with the newline appears on two lines of output but is a single value. Two lines on screen does not mean two entries, and the exists check is what proves it.

7.1 An up to date fact about portability

You will often read that 「-print0 is a GNU extension and not POSIX」. As of 2024 that is no longer accurate. The Open Group Base Specifications Issue 8 (IEEE Std 1003.1-2024) added find's -print0 to the standard, and its change history records that 「Austin Group Defect 243 is applied, adding the -print0 primary」. The same defect number brought -0 and -r to xargs.

Still, being in the standard and being on the server in front of you are different things. Issue 8 is the 2024 edition, and the find on an older Unix or a minimal container may not know -print0. Where portability matters, -exec ... {} + is the safer choice. That form has been standard far longer and carries spaces and newlines intact without any null separation.

$ find . -type f -exec sh -c 'for p do printf "portable: [%s]\n" "$p"; done' _ {} +
portable: [./a b.txt]
portable: [./c
d.txt]

7.2 When no null ever reaches read -d ''

Fix the consumer without fixing the producer and nothing gets processed at all. No error either.

$ find . -type f -print | while IFS= read -r -d '' f; do printf 'GOT [%s]\n' "$f"; done
  (no output)
  iterations = 0   real files = 1

-print terminates with a newline while read -d '' waits for a null. The null never arrives, read eventually fails at end of input, and the loop body never executes once. Exit status is 0 and the log stays quiet. -print0 and -d '' travel strictly as a pair.

8. IFS= and -r on read - what each one prevents

People memorise while IFS= read -r -d '' f as an incantation, but rarely know what each fragment blocks. We removed them one at a time.

8.1 Drop IFS= and the outer whitespace disappears

Tested with a file whose name is pad followed by two spaces, and another with a tab in the middle.

--- WITH IFS= ---
[./pad  ] len=7 exists=yes
[./ta	b] len=6 exists=yes
--- WITHOUT IFS= ---
[./pad] len=5 exists=NO
[./ta	b] len=6 exists=yes

The length fell from 7 to 5 and the path became exists=NO. Before storing a value, read strips whitespace characters found in IFS from both ends, and the default IFS contains space, tab and newline. IFS= empties that list so nothing is stripped.

Notice too that the interior tab survived. With a single variable, read assigns the entire remainder, so interior delimiters are preserved and only the ends are trimmed. That is why this defect fires only on names with leading or trailing whitespace, and such names are invisible on screen. Hence the late discovery.

Working with basenames rather than paths makes it even starker.

$ find . -name '*lead*' -printf '%f\0' | while IFS= read -r -d '' f; do ...
[  lead.txt] len=10
$ find . -name '*lead*' -printf '%f\0' | while read -r -d '' f; do ...
[lead.txt] len=8

8.2 Drop -r and backslashes get eaten

Since this environment cannot create files containing a backslash, we sent a string through a pipe instead. The point is to observe read, so the result is identical.

$ printf 'C:\\temp\\new\n' | while IFS= read -r x; do ...
with -r    : [C:\temp\new]
$ printf 'C:\\temp\\new\n' | while IFS= read    x; do ...
without -r : [C:tempnew]

The backslashes vanished entirely. Without -r, read treats a backslash as an escape character, passes the following character through unchanged and consumes itself. The worse case is a backslash at end of line.

$ printf 'one\\\ntwo\n' | while IFS= read -r x; do ...
with -r    : [one\]
with -r    : [two]
$ printf 'one\\\ntwo\n' | while IFS= read    x; do ...
without -r : [onetwo]

Two lines merged into one, because backslash-newline was treated as line continuation. For a file list that means two files mashed into one nonexistent path.

8.3 When the last line has no newline

Unrelated to null separation but frequent in the same loops: if a file does not end with a newline, the final line disappears completely.

--- while IFS= read -r line ---
GOT [a]
GOT [b]
--- while IFS= read -r line || [ -n "$line" ] ---
GOT [a]
GOT [b]
GOT [c]

When read hits end of input without meeting a delimiter, it still fills the variable but returns non-zero. The while condition is therefore false and the body is skipped. Appending || [ -n "$line" ] rescues that last fragment. If you have a bug where the final item of a list is quietly missing, this is a good first suspect.

9. The three shapes of -exec - semicolon, plus, and xargs

-exec never involves a shell, so all three shapes are safe against spaces and newlines. What differs is invocation count, speed and exit status. We counted invocations directly on 500 files, every one of which had a space in its name.

-exec {} \;  invocations=500  args=500
-exec {} +   invocations=1    args=500
--- first two args as the child received them (cat -A) ---
files/f 1.txt$
files/f 10.txt$

$ marks end of line. The spaces are intact and one argument corresponds to one file. Speed was measured on 2000 files.

--- -exec /bin/true {} \; ---
real	1m25.965s
--- -exec /bin/true {} + ---
real	0m0.252s
--- xargs -0 /bin/true ---
real	0m0.291s

A factor of 340. Do not take that multiplier at face value, though: this environment is MSYS2 on Windows, where process creation costs far more than on Linux. On Linux the gap is smaller. The direction holds everywhere; the multiplier is environment specific.

9.1 The exit status diverges

This is the less known part. We checked what find returns when the child fails.

$ find . -name '*.txt' -exec false {} \;   ; echo $?
0
$ find . -name '*.txt' -exec false {} +    ; echo $?
1
$ find . -name '*.txt' -print0 | xargs -0 false ; echo $?
123

The semicolon form returns 0. The child failed and the pipeline reports success. Use that form in CI and a failure passes as a green build. The GNU documentation states, for the plus form only, that 「if any invocation with the '+' form returns a non-zero value as exit status, then find returns a non-zero exit status」. That matches what we observed.

The xargs exit status scheme is worth knowing too. These are values we confirmed directly.

child exits 3     -> xargs 123
child exits 255   -> xargs 124  (xargs: exited with status 255; aborting)
command not found -> xargs 127
  • 123 — one or more invocations exited between 1 and 125. The child's real status is lost.
  • 124 — the child exited 255, and xargs aborts immediately. Remaining batches never run.
  • 126 / 127 — the command could not be executed / could not be found.

The practical implication is clear. If you need to know which file failed, the xargs exit status will not tell you. The child has to record failing paths itself.

9.3 Never paste {} into an -exec sh -c string

The moment a shell is invoked again, the safety is gone. Checked with a file whose name contains a single quote.

--- BAD: {} pasted inside the shell string ---
$ find . -name '*.txt' -exec sh -c 'echo FILE={}' \;
sh: -c: line 1: unexpected EOF while looking for matching `''

--- GOOD: {} passed as an argument ---
$ find . -name '*.txt' -exec sh -c 'echo FILE="$1"' _ {} \;
FILE=./it's here.txt

In the first form the filename is interpreted as shell source code. Here it merely ended in a syntax error, but if the name contained a semicolon or a backtick, the commands written there would run. That is command injection. The second form receives the filename as $1, that is as data, so no character in it can execute. The _ is a placeholder filling the $0 slot; omit it and the first file silently lands in $0 and is skipped.

10. Argument length limits - it splits quietly and overwrites quietly

Sometimes you have fixed the separator and quoted everything and the result is still short. This section is about that. When the list is long xargs splits it into several runs on its own. A convenience, but it does not tell you it happened.

$ xargs --show-limits < /dev/null
Your environment variables take up 5825 bytes
POSIX upper limit on argument length (this system): 24127
POSIX smallest allowable upper limit on argument length (all systems): 4096
Maximum length of command we could actually use: 18302
Size of command buffer we are actually using: 24127

The POSIX specification says xargs shall 「limit the command line length such that when the command line is invoked, the combined argument and environment lists shall not exceed {ARG_MAX}-2048 bytes」. The gap between the second and fourth lines above is that reserve plus the environment's share. The first line also shows that a shell with many environment variables has less usable length.

Here is how the split count moves.

$ seq 1 200000 | xargs echo | wc -l
68
$ seq 1 200000 | xargs -n 1000 echo | wc -l
200
$ seq 1 200000 | xargs -s 4096 echo | wc -l
316

10.1 What actually breaks when it splits

Splitting into batches is not itself a problem. It becomes one when you redirect to a file inside a batch. Reproduced with 30,000 files.

real file count = 30000
--- xargs -0 sh -c 'printf "%s\n" "$@" > out.txt' _ ---
lines in out.txt = 426
--- fix 1: append (>>) instead of truncate ---
lines in out2.txt = 30000
--- fix 2: move the redirection outside xargs ---
lines in out3.txt = 30000
--- batches xargs used ---
62   (batch: 482 args ...)

Thirty thousand paths went in and 426 lines came out. Sixty-two batches each truncated the same file in turn, and only the last one survived. No errors, exit status 0. This applies to every command that creates a fresh output file — tar -cf, zip, plain redirection. Archives that mysteriously contain only part of the tree usually look exactly like this.

There are three responses.

  • Switch to appending — use >>, but truncate the target before you start. Without that reset, re-running accumulates.
  • Move the redirection outside xargs — with xargs ... > out.txt the file is opened exactly once.
  • Use a command with an append mode — for archives, add to the archive rather than creating it. Note that you must create on the first batch and append thereafter, so the initialisation has to be separated out.

10.3 With empty input, the command runs once

This behaviour is written into the standard, and not knowing it causes accidents. The POSIX specification states that 「if no arguments are supplied on standard input, the utility named by utility shall be executed zero times if the -r option is specified and shall be executed exactly once if the -r option is not specified」. We confirmed it.

$ find . -name 'nothing*' -print0 | xargs -0 echo "RAN with args:"
RAN with args:
  exit=0
$ find . -name 'nothing*' -print0 | xargs -0 -r echo "RAN with args:"
  (did not run)
$ find . -name 'nothing*' -exec echo "RAN with args:" {} +
  (did not run)

Nothing was found and the command ran anyway. If fixed trailing arguments are attached, the command runs on those alone. That is why this shape is dangerous in cleanup scripts. Add -r (--no-run-if-empty), or use -exec ... +, which does not have the problem at all. The third line demonstrates that.

11. How find -delete differs from -exec rm

Deletion has a dedicated action, -delete. Reproduce each and the difference in character is plain. Safety first: we created three files with spaces, newlines and dashes in nested directories and removed them in one go.

--- before ---
./a/-rf.tmp
./a/b/c/hostile name.tmp
./a/b/line1
line2.tmp
--- find . -name '*.tmp' -delete ---
  exit=0
--- after ---
.
./a
./a/b
./a/b/c

All three gone cleanly, because neither a shell nor rm stands in the middle. find issues the removal call itself. The shape of the filename never gets a chance to matter.

11.1 It turns on -depth and kills -prune

There is a price. -delete changes the traversal order.

default order (pre-order):  x → x/y
-depth order (post-order):  x/y → x

You must empty the inside before removing a directory, so that is the natural choice. The catch is that this -depth disables -prune. Anyone who wrote exclusions with -prune loses them the moment -delete is added. Fortunately GNU find refuses the combination.

$ find . -path ./keep -prune -o -name '*.tmp' -delete
find: The -delete action automatically turns on -depth, but -prune does
nothing when -depth is in effect.  If you want to carry on anyway, just
explicitly use the -depth option.
  exit=1
survivors: ./drop/b.tmp  ./keep/a.tmp

It refused and deleted nothing. Good design. If you ignore the warning and add -depth yourself, -prune is silently ignored while the deletion proceeds, so that particular piece of advice is best left unfollowed. Write exclusions with ! -path instead.

$ find . -name '*.tmp' ! -path './keep/*' -delete
survivors: ./keep/a.tmp

11.2 It will not remove a non-empty directory

$ find . -name 'full' -delete
find: cannot delete './full': Directory not empty
  exit=1

Removing a whole directory takes more than -delete; you have to match the contents as well. Its character differs from rm -rf, and that conservatism is an advantage: a wrong match limits the damage to individual files.

12. Safe form comparison by situation

Folding all of the above into one place: the left column is a form that actually broke, and the right column is a form that passed all six hostile filenames under the same conditions.

Finally we verified that the right hand forms really do pass. Six files carrying a space, a newline, a dash, a quote, an asterisk, a tab and outer spaces went through four different mechanisms.

--- inventory (ls -b) ---

All four handled exactly six as six, in contrast to the naive pipeline that got the count wrong before it did anything else.

12.1 Building hostile filenames for testing

To audit your own scripts, create these files first. Always inside a fresh temporary directory.

$ mkdir -p /tmp/fx-test && cd /tmp/fx-test
$ touch -- 'space name.txt' $'newline\nname.txt' -dash.txt \
      "quote'name.txt" 'glob*name.txt' $'tab\tname.txt' \
      '  pad  .txt' 'semi;name.txt' 'dollar$name.txt'
$ find . -type f -printf 'x\n' | wc -l     # the real count
9
$ ls | wc -l                               # what a naive pipeline sees
10

The verdict takes two lines. If your script processed anything other than 9, it is already broken. Checking that [ -e "$f" ] is true on every iteration then tells you which entry went wrong. Drop the -- before touch and you can also watch -dash.txt be read as an option, so the test files never get created in the first place.

12.2 Unicode is a slightly different problem

One last category, unrelated to separators: files that look the same but are not.

$ ls -b
cafe?\201.txt
café.txt
$ (byte check)
10 bytes   c  a  f  e 314 201  .  t  x  t     <- combining form (NFD)
 9 bytes   c  a  f 303 251  .  t  x  t        <- precomposed (NFC)
$ find . -type f -printf 'x\n' | wc -l
2

Both render as café.txt on screen, yet the bytes differ so they are separate files. find -name matched only its own form in each case. The rule to take away is single: compare filenames as bytes, not by eye. Build the habit of checking with ls -b or a byte dump, and when comparing sorted listings, use LC_ALL=C sort to remove locale influence so results reproduce.

Behaviour also varies by filesystem. On a filesystem that does not normalise, the two files coexist as above; on one that normalises or ignores case, they merge or collide. If a cross-platform sync ever reports 「I definitely copied it and it is not there」, this is worth suspecting.

Conclusion: choosing a boundary, not an option

「Use -print0」 is correct and it is half the story. Folding this article back up, the defects lived on four layers and null separation covers exactly one of them.

  • The separator layer — spaces and newlines cut entries apart. Covered by -print0, -0 and -d ''.
  • The quoting layer — an unquoted value is split again inside the loop and globs re-expand. That was the four files becoming eight iterations.
  • The option parsing layer — a leading dash becomes an option regardless of separator. Covered by -- or ./. The rm * that wiped a directory belongs here.
  • The batching layer — a long list splits silently. Thirty thousand files becoming 426 lines belongs here.

So the working rule is better expressed as a judgement about boundaries than as a list of options. Never create a point where a filename passes through shell syntax. That single sentence covers all four layers. It is also why -exec ... + makes such a good default: no shell involved, batching handled for you while doing as much as possible per call, child failures surfaced in the exit status, and long enough in the standard to run anywhere.

If only one habit survives from this article, make it the count check. Two lines comparing the real count from find ... -printf 'x\n' | wc -l against what your script processed will surface defects from all four layers in testing rather than in production. Creating the nine hostile filenames and running those two lines takes about a minute.

# Safe find/xargs batch patterns — copy-paste snippets

> Source: braindetox.kr — The find and xargs whitespace trap
> Basis: POSIX Issue 8 (find, xargs), GNU findutils 4.10.0, Bash 5.2, verified by execution
> Paste this file straight into an AI assistant and say "rewrite our script to these rules".
> ⚠ Always try destructive commands in a fresh temporary directory first.

## 0. Three lines at the top of the script

```bash
#!/usr/bin/env bash
set -Eeuo pipefail          # do not swallow failures
IFS=$'\n\t'                 # drop the space from the default IFS
shopt -s nullglob           # an unmatched pattern must not survive as a literal
```

`set -o pipefail` matters most here. In a `find ... | while ...` pipeline, only the
last command's status survives, so a dying `find` would otherwise go unnoticed.

## 1. Deleting

```bash
# Preferred - no shell in the middle
find "$ROOT" -type f -name '*.tmp' -mtime +7 -delete

# For exclusions use ! -path, not -prune (-delete turns on -depth, which kills -prune)
find "$ROOT" -type f -name '*.tmp' ! -path "$ROOT/keep/*" -delete

# When rm is genuinely required
find "$ROOT" -type f -name '*.tmp' -exec rm -f -- {} +

# Prune empty directories only (innermost first)
find "$ROOT" -depth -type d -empty -delete
```

- [ ] `-delete` comes **after** the conditions (before them it deletes before testing)
- [ ] Guarded against an empty root — `[ -n "${ROOT:-}" ] && [ "$ROOT" != "/" ]`
- [ ] `--` added to `rm` so leading-dash names cannot become options
- [ ] Swapped `-delete` for `-print` first and inspected the targets by eye

## 2. Moving and copying

```bash
# One batched call
find "$SRC" -type f -name '*.log' -exec mv -t "$DST" -- {} +

# Where mv has no -t (BSD and friends), run per file
find "$SRC" -type f -name '*.log' -exec sh -c '
  for p do mv -- "$p" "$DST/"; done
' _ {} +

# Copy while preserving the directory structure
find "$SRC" -type f -print0 |
  while IFS= read -r -d '' f; do
    rel=${f#"$SRC"/}
    mkdir -p -- "$DST/$(dirname -- "$rel")"
    cp -p -- "$f" "$DST/$rel"
  done
```

- [ ] Used `mv -t DEST SRC...` so the last batched argument is never mistaken for a destination
- [ ] **Quoted the pattern** when stripping a prefix, as in `${f#"$SRC"/}`
- [ ] Exported `$DST` or passed it as an argument before using it inside `sh -c`

## 3. Renaming

```bash
# Change an extension in bulk
find "$ROOT" -type f -name '*.jpeg' -exec sh -c '
  for p do mv -- "$p" "${p%.jpeg}.jpg"; done
' _ {} +

# Spaces to underscores, touching the basename only
find "$ROOT" -depth -name '* *' -exec sh -c '
  for p do
    d=$(dirname -- "$p"); b=$(basename -- "$p")
    n=${b// /_}
    [ "$b" = "$n" ] || mv -n -- "$p" "$d/$n"
  done
' _ {} +
```

- [ ] Added `-depth` — renaming a parent first invalidates every child path
- [ ] `mv -n` so an existing file is never overwritten
- [ ] Used **shell parameter expansion** such as `${p%.jpeg}` rather than building paths with `sed`

## 4. Replacing content

```bash
# Select only the matching files, then substitute in a batch
find "$ROOT" -type f -name '*.conf' -exec grep -lZ -e 'OLD' -- {} + |
  xargs -0 -r sed -i -e 's/OLD/NEW/g' --

# Keeping a backup
find "$ROOT" -type f -name '*.conf' -exec sed -i.bak -e 's/OLD/NEW/g' -- {} +
```

- [ ] Chained null separation with `grep -Z` plus `xargs -0`
- [ ] `xargs -r` so `sed` does not run on empty input with zero matches
- [ ] `--` after `sed` and `grep`
- [ ] Pattern passed via `-e` so a leading-dash pattern is not read as an option

## 5. Archiving

```bash
# ★The classic accident: when xargs splits, the second batch overwrites the archive
# Bad:   find ... -print0 | xargs -0 tar -cf out.tar
# Good - let tar read the list itself
find "$ROOT" -type f -name '*.log' -print0 |
  tar --null --files-from=- -cf out.tar

# Without GNU tar: build a list file and run exactly once
find "$ROOT" -type f -name '*.log' -print0 > list.nul
tar --null --files-from=list.nul -cf out.tar

# zip reads a list on stdin (-@ is newline separated, so it breaks on newline names)
find "$ROOT" -type f -print0 | xargs -0 -r zip -q out.zip --
```

- [ ] No command that **creates a fresh output file** sits downstream of `xargs`
- [ ] Where batching is unavoidable, split it into **create on the first batch, append afterwards**
- [ ] Null separation preserved end to end (`-print0` with `--null`)

## 6. Counting and aggregating

```bash
# Counting - count one character per file, never the filenames
find "$ROOT" -type f -printf 'x\n' | wc -l
find "$ROOT" -type f -exec printf 'x\n' {} + | wc -l   # where -printf is missing

# Total size
find "$ROOT" -type f -printf '%s\n' | awk '{s+=$1} END{print s+0}'

# Newest single file, safe against newline names
find "$ROOT" -type f -printf '%T@\t%p\0' | sort -zrn | head -zn1 | cut -zf2-

# Sorting only reproduces if the locale is pinned
find "$ROOT" -type f -print0 | LC_ALL=C sort -z
```

- [ ] Never used `find | wc -l` (one newline filename skews the number)
- [ ] `-z` (null separated) on `sort`, `head` and `cut`
- [ ] `LC_ALL=C` pinned for sorting

## 7. Parallel processing

```bash
find "$ROOT" -type f -print0 |
  xargs -0 -r -P "$(nproc)" -n 20 sh -c '
    for p do process_one -- "$p" || echo "FAILED: $p" >> "$FAILLOG"; done
  ' _
```

- [ ] `-P` used **together with** `-n` (without `-n` one batch swallows everything)
- [ ] The child records failing paths itself — `xargs` flattens everything into 123
- [ ] If children write to one file, use append (`>>`) and confirm interleaved lines are acceptable

## 8. Forbidden patterns

| Do not use | Why |
|---|---|
| `find ... \| xargs cmd` | Arguments split apart on spaces and newlines |
| `for f in $(find ...)` | Word splitting and glob re-expansion stack up |
| `ls \| grep pat` | `ls` cannot guarantee one line equals one file |
| `ls -1 \| while read f` | Same as above, and `-r` / `IFS=` are easily forgotten |
| `-exec sh -c 'cmd {}' \;` | The filename is parsed as shell source (command injection) |
| `find ... \| wc -l` | A newline filename inflates the count |
| `rm $f` / `cp $f $d` | An unquoted variable is split and expanded again |
| `cmd *` on user-created files | A name like `-rf` becomes an option |
| `xargs` without `-r` | The command runs once even with empty input |
| `-delete` with `-prune` | `-depth` is turned on and `-prune` stops working |

## 9. Verification procedure — one minute

```bash
# ⚠ In a fresh temporary directory, always
LAB=$(mktemp -d) && cd "$LAB" || exit 1

# Nine hostile filenames
touch -- 'space name.txt' $'newline\nname.txt' -dash.txt \
  "quote'name.txt" 'glob*name.txt' $'tab\tname.txt' \
  '  pad  .txt' 'semi;name.txt' 'dollar$name.txt'

REAL=$(find . -type f -printf 'x\n' | wc -l)     # must be 9
MINE=$(your_script_here | wc -l)                  # what your script processed

echo "real=$REAL  script=$MINE"
[ "$REAL" = "$MINE" ] || echo "★ already broken"

# Does every entry actually exist
find . -type f -print0 | while IFS= read -r -d '' f; do
  [ -e "$f" ] || echo "★ missing path: [$f]"
done
```

- [ ] The real count and the processed count are **identical**
- [ ] Every iteration points at a path that **exists**
- [ ] The dash file (`-dash.txt`) was not swallowed as an option
- [ ] The newline file was counted as **one** entry
- [ ] The padded name did not lose length
- [ ] Cleaned up afterwards with `cd / && rm -rf "$LAB"`

## 10. Portability

| Feature | Standard status | Fallback |
|---|---|---|
| `-exec ... {} +` | POSIX (long standing) | — (the safest default) |
| `-print0` | Added in POSIX **Issue 8** (2024) | `-exec ... {} +` |
| `xargs -0` | Added in POSIX **Issue 8** | `-exec ... {} +` |
| `xargs -r` | Added in POSIX **Issue 8** | `-exec ... {} +` (no empty-input problem) |
| `-printf` | GNU extension | `-exec printf ... {} +` |
| `-delete` | GNU/BSD extension | `-exec rm -f -- {} +` |
| `grep -Z` / `sort -z` | GNU extension | Go via a list file |
| `globstar` | bash 4+ | `find` |
