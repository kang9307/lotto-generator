What Gets Thrown Out First Tells You What a Language Really Is - The Order Revealed by Fitting a Python Interpreter into 1,024 Bytes of C

Error handling goes first, the standard library second, performance third, and grammar survives to the very end

2026-09-08 Dev & Infra

Shrink a budget far enough and the design underneath becomes visible. When there is room to spare, every layer sits beside every other layer and nothing distinguishes the core from the decoration. Once the budget falls below a few kilobytes, an order is forced. Something gets cut first and something survives to the end. That order is the system declaring its own priorities.

An interpreter is an unusually good subject for this experiment, because the layers it needs are fixed almost as a matter of textbook definition. Lexical analysis, syntactic analysis, evaluation, an environment that ties names to values, and error handling. Five of them. There is no way to fit all five into 1,024 bytes, which means the sequence in which they were shaved becomes directly observable.

What follows is about that sequence. Not a catalogue of size-reduction tricks, but the order in which you decide what to give up, and the conditions under which that order flips.

Every figure here carries conditions. The 1,024 bytes is the size of one C source file, and the build selects the C89 standard under GCC with warnings switched off. The MicroPython, Lua and QuickJS numbers each measure a different axis and do not compare directly against one another. A size figure with no axis attached is generally worthless.

The trigger - what is 1,024 bytes the size of

The piece that set this angle is Austin Z. Henley's post from 6 September 2026. The title is Making a Python interpreter in 1024 bytes, and the opening line attaches the conditions: 1,024 bytes of C code, with no macros and no library tricks. That sentence already contains three separate claims, and all three drop out if you read only the summary line.

First, the 1,024 is the size of a C source file. It is not the size of the compiled artifact. The repository holds a readable version and a golfed version separately; the golfed one lands on exactly 1,024 bytes while the readable one runs past 4,800. The two implement the same language. The difference is notation and nothing else.

Second, the figure is not self-contained. Among the byte-saving techniques the author enumerates is relying on the compiler linking libc. The character input and output code that vanished from the source did not disappear; it moved onto a different budget. Skip this distinction and 1,024 bytes starts to read as though it were everything execution requires.

Third, what runs is not Python. The author states outright that fitting the whole language into 1,024 bytes is impossible, and re-aims at something that looks like Python. The markers he cites are def, colons, indentation and conditionals without parentheses. In other words the outward shape of the grammar was the target from the start.

The build conditions are part of the size figure too. Here is the command the repository gives.

gcc-16 -std=gnu89 -w python1024.c   # roll back to C89 and silence the warnings
./a.out < fizzbuzz.py               # the program to run arrives on standard input
wc python1024.c                     # the size check the repository suggests

-std=gnu89 is required for a reason that returns later: some of the golfing tricks depend on C89's implicit int declarations and implicit return types. -w switches off the warning storm that follows. The repository notes GCC rather than Clang, which means the same source does not produce the same result on every compiler.

Put together: 1,024 bytes is the size of one C source file that, under a specific compiler and a specific language standard, and on the assumption that libc will be linked in, executes a subset of grammar that resembles Python. Repeat the claim as Python runs in 1,024 bytes and you are wrong in four separate places.

The five layers an interpreter cannot do without

Regardless of implementation style, an interpreter does five jobs. Sketching what survives when each is squeezed to its limit turns the inventory that follows into a map rather than a list.

  • Lexical analysis - cuts a character stream into meaningful units. Squeezed to the limit, one character becomes one token. Cap the length of a name at one and this layer disappears wholesale.
  • Syntactic analysis - decides whether the token sequence fits the grammar and builds a structure from it. Squeezed to the limit, it builds no structure and computes as it reads. A recursive descent parser that returns values needs no tree.
  • Evaluation - turns structure into actual behaviour. This is the layer with the least give. Without it, the thing is a grammar checker rather than an interpreter.
  • Environment - ties names to values. Squeezed to the limit, it becomes a single array. When a name is one character, that character's code is the array index.
  • Error handling - catches input that violates the rules and reports it. Squeezed to the limit it becomes zero bytes. It is the only one of the five that can be removed completely.

That last item is the crux. The other four leave something behind no matter how hard you compress them. Zero evaluation means nothing runs; zero environment means there are no variables; zero syntactic analysis means there is nothing to compute. Only error handling can go all the way to zero. That is why it goes first.

Kept and dropped - the inventory inside 1,024 bytes

Setting the author's supported-feature list beside the corresponding clauses of the Python language reference produces the following. The right-hand column is what the official reference specifies.

Read the table downward and the cuts are visibly uneven. Arithmetic, iteration and functions kept their shape. Names, truthiness and blocks kept their shape but lost their guarantees. Errors are gone entirely.

The loop else is the interesting row. The supported list includes an else clause on while and for, and the same list contains no break. In the Python reference, the whole meaning of that else clause is that it runs only when the loop was not left through a break. With no break in the language, the else always runs. The grammar survived; the reason the grammar exists did not.

The order in which things get thrown out

This is the centre of the argument. When a budget contracts, the order in which layers disappear follows a rule, and the rule is contribution to the correct path.

OrderWhat goesEffect on valid inputWhat is lost insteadState in the 1,024-byte version
1Error handling and diagnosticsNone whatsoeverBehaviour on invalid input becomes undefinedCompletely absent
2Standard libraryNone if you were not using itThe range of things a program can doA single print
3Performance and intermediate representationSame result, more timeRepetition cost and the possibility of static analysisNo tokens, no tree
4Name length and namespacesNone if you shorten the namesScale, readability and scopeOne lowercase letter, no isolation
5Quantifiers attached to the grammarNone if you split the expressionExpressive powerOne comparison per expression
6The shape of the grammarIt stops being the languageIdentityLeft untouched

The layer that contributes nothing to the correct path goes first

Error handling never executes in a correct program. Delete it and correct programs still run exactly as before. That is the first reason it sits at rank one.

The second reason is physical. The substance of a diagnostic is a string, and strings consume budget literally. Logic can be compressed; messages cannot. A single twenty-seven character phrase is 2.6 percent of a 1,024-byte budget. Fill the whole budget with nothing but such phrases and thirty-eight lines is the ceiling. No golfing technique gets past that wall.

The price has to be stated precisely. Removing error handling does not mean invalid input does nothing; it means invalid input can do anything. The author says as much, describing an implementation that rests on a strong assumption that the code is correct. Keyword recognition is the example.

if (ch == 'w' || ch == 'i' || ch == 'f') {
    int keyword = ch;
    int loop_var = 0;

    if (keyword == 'f') {        /* the "for K in range(N):" shape */
        pos += 2;                /* skip past "or"                */
        loop_var = next();
        pos += 8;                /* skip past "inrange("          */
        vars[loop_var] = 0;
    } else if (keyword == 'w')
        pos += 4;                /* skip past "hile"              */
    else
        pos += 1;                /* skip the "f" of "if"          */

Only the first character is inspected; the rest is counted over, not read. Whether the word for is actually written there is never checked. Write fog and control takes the same path. That is what zero bytes of error handling looks like in practice.

What sits outside the language goes next

The standard library can be removed without touching the grammar. That is why it holds rank two. It is the same property that lets MicroPython describe its own scope as including a small subset of the Python standard library while still calling itself an implementation of Python 3. Shrinking the library does not shake the identity of the language.

The 1,024-byte version keeps only print, and only in the form that accepts one string literal or one integer expression. There is a detail here that is easy to miss: in Python, print and range are not keywords. Neither appears among the thirty-five reserved words the reference lists. Both are names that can be rebound. In a world where names have been capped at one character, that property cannot hold. As the code above shows, range has become a fixed pattern that the parser skips eight characters past. A library function hardened into grammar.

What produces the same answer more slowly goes third

Performance is not something correctness observes. A slower program still returns the right answer, which puts it at rank three. What went here is the entire compilation stage. The author describes CPython as working through tokenization, syntax tree construction, analysis, optimization, bytecode emission and interpretation, and says his own implementation does not use that pipeline.

Rank three is not universal, though. In real-time control, performance is defended first and capability is cut instead. The order is set by the kind of constraint, not by the nature of the layer. The sequence in this article is the sequence for when size is the ceiling.

Why grammar survives to the end

There are two reasons grammar goes last.

First, once the grammar is gone there is nothing left to justify calling it that language. The moment the author changed direction at 512 bytes demonstrates this. He started from an addition expression, added assignment, then added conditionals, and the verdict on the result was that it was a calculator rather than a Python interpreter. The layers were all present. What was missing was any grounds for calling it Python. So the target moved from 512 to 1,024.

Second, grammar is the only asset an implementation gains without spending its own budget, because it is already installed in the reader's head. Show someone def, a colon and indentation and they read it as Python. The implementation pays not a single byte to produce that recognition. Error messages, by contrast, are not preinstalled anywhere and must be paid for in full.

And what actually got cut was not the shape of the grammar but a quantifier attached to it. The Python reference states that comparisons chain arbitrarily. Unlike C, all comparison operations share one priority, lower than arithmetic, and a three-value chain is interpreted the way mathematics interprets it. The supported list for the 1,024-byte version pins comparisons at at most one per expression. The operators survived; only the chaining died.

The author writes that he came close to removing comparison expressions altogether, on the grounds that truthiness covers the same ground. Instead of asking whether a remainder is zero, put the remainder itself in the condition. It is a trade that deletes grammar and pays with semantics, and it was available only because Python treats the integer zero as false. Semantics decided how much grammar could be dropped.

What the phrase Python interpreter actually covers

Sameness between implementations splits into three layers: grammar, semantics and standard library. Blur the three together and any claim looks true.

LayerWhat sameness meansThe 1,024-byte versionHow to check
GrammarThe same source text is judged well-formedA subset only, and one with a name-length capWhether the same file is read by both
SemanticsThe same source produces the same resultDiverges on integer range and on scopeTest with a large number and a variable inside a function
Standard libraryThe same modules and builtins existOne shape of printWhether an import statement exists at all

The original claims only the outward shape of the grammar, and even that is described as a subset by the author himself. The sentence stating that looking like Python is the goal is the exact boundary of the claim. He did not blur that line.

The blurring usually happens downstream. A sentence like a Python interpreter in 1,024 bytes makes no distinction among the three layers. The same trap appears in other implementations. Some tools match only the grammar; some try to match semantics and collide with the host language; for others the real question is how much of the standard library came across. Where a language hosted on top of another language runs into trouble is covered separately in the piece on glojure, and the point at which interpreted execution and compiled execution diverge is in the piece on adding a REPL to Go.

What single-letter names delete along with themselves

Capping names at one character looks like a size optimization. It is in fact a change of semantics.

Start with what is gained. The Python reference splits name rules into a start character and continuation characters and imposes no length limit. Honouring that rule requires a loop that reads the name, a buffer to hold it, a function to compare it, and, since the number of names is unbounded, a hash table or something equivalent. Cap names at one character and all of that disappears.

char src[999];       /* the whole program with most spaces removed */
int  vars[256];      /* symbol table                               */
int  pos;            /* position of the next character in src      */
int  ch;             /* the character currently in hand            */
int  line_start;     /* where the current line begins              */

The symbol table is one line: int vars[256]. A lookup is a single array access using the character's code as the index. No hashing, no collision handling, no string comparison, no allocation.

But something leaves with it. The supported list records indentation-based blocks and adds, in parentheses, without scope isolation. The Python execution model states that a name bound within a block is a local variable of that block. In a world where one global array is the whole environment, that clause cannot hold. A name used inside a function and the same name used outside it look at the same slot.

It goes further: values of different kinds land in the same slot. A function definition stores the source position of its body in the symbol table. So vars[k] may be an integer or it may be a code location, and there is no tag distinguishing the two. It is not that types are absent; it is that there is nowhere to check a type. The place where integers and identity comparison tangle is surprising in CPython too, and that story is set out in the piece on integer caching.

No tokens, no syntax tree - execution by rewinding the source

The strongest way to shrink the syntactic analysis layer is to build no structure at all. A recursive descent parser normally returns tree nodes; make it return values instead and the entire tree becomes unnecessary.

int parse_sum(void) {
    int value = parse_term();
    while (ch == '+' || ch == '-') {
        if (ch == '+')
            value = value + parse_term();
        else
            value = value - parse_term();
    }
    return value;
}

The return type is int. That one word decides the whole design. Computation happens as the text is read, so there is no intermediate representation and none of the code that builds, walks and frees one. In exchange, the source text itself becomes the execution state.

Control flow is therefore implemented by moving a position within the source. With no compilation stage there is no address to jump to, so pos is rewound instead. A loop remembers where its condition expression sits and, once the body finishes, returns to that spot and parses it again. A function call saves the call site, jumps to the position of the function body, and returns to the saved spot when the body ends. A single pos plays the role of a program counter.

Block boundaries are decided by indentation.

void run_block(int min_indent) {
    for (;;) {
        int indent = read_indent();

        if (ch == '\n')
            continue;

        if (indent < min_indent || ch == 0) {
            pos = line_start;
            return;
        }

Here sits the most interesting substitution in the whole implementation. The Python reference specifies indentation handling as a stack. A single zero is pushed before the first line of the file is read, the values always increase from bottom to top, and when the indentation decreases the new value must be one of the numbers already on the stack. That last clause is the rule that catches inconsistently indented code.

The 1,024-byte version never builds that stack. Because run_block calls itself recursively, the C call stack plays the part instead. Block nesting depth and recursion depth correspond one to one, so a separate data structure has no reason to exist. A data structure the language demanded was repaid with a data structure of the host language.

Except that dropping the stack also drops the checking that stack was doing. With no record of which indentation levels have appeared, there is no way to ask whether a reduced indentation is a valid level. Misaligned indentation stops being an error and simply attaches itself to some block. This is the most generalizable observation in the whole piece. Data structures usually double as validators. When deciding what to remove, the thing worth counting is not the bytes the structure occupies but the list of checks it was quietly performing.

Small is not one thing

The word small points at four different axes at minimum. A size figure that does not name its axis cannot be used for comparison.

AxisWhat it measuresWhere the pressure landsHow to reduce it
Source bytesThe amount a human reads and auditsCode golf, early stage boot codeShave identifiers, whitespace and structure itself
Binary sizeStorage and flash occupancyEmbedded firmware, container imagesExclude features at build time and strip with the linker
Resident memoryRAM in use while runningMicrocontrollersChange data structures and the reclamation strategy
Dependency countPortability, supply chain, audit costSandboxes, air-gapped networksImplement independently rather than pulling libraries

The 1,024 bytes measures the first axis only. And since it leans on libc being linked, it does worse on the second and fourth axes. What left the source is put back by the linker.

The contrast sharpens when you look at which axis other implementations choose when they state their own size.

  • MicroPython - says it is compact enough to fit and run within just 256k of code space and 16k of RAM. It states the second and third axes separately, because on a microcontroller they are different resources.
  • Lua - says that on 64-bit Linux the interpreter built with all standard libraries takes 293K and the library takes 484K. The source is around 32,000 lines of C, and the distributed tarball is 390K compressed. Size is stated as a build artifact, not as a line count.
  • QuickJS - says it is just a few C files with no external dependency, at 367 KiB of x86 code for a simple hello world program. Size and dependency count sit in the same sentence.

Those three numbers do not compare. The axes differ and so do the measurement conditions. Lua's 293K names its platform, QuickJS's 367 KiB names an architecture and a target program, and MicroPython's 256k is an artifact size rather than a source size. When a size figure is repeated, stripping the conditions makes it false.

Where smallness is genuinely required

There are places where making things small is a requirement rather than a hobby. Each of them demands a different kind of small, and so the discard order flips.

Microcontrollers - the ceiling is RAM

Here the third axis dominates, and the order established earlier inverts at exactly one position. MicroPython advertises an interactive prompt, arbitrary precision integers, closures, list comprehensions, generators and exception handling as its features. The layer the 1,024-byte version discarded first is the one MicroPython puts on the front page.

The reason is plain. A program on a microcontroller runs where nobody is standing over it. A state in which bad input can do anything is not acceptable there. Something else gets shaved instead, and that something is the standard library, which the project itself describes as a small subset. Where RAM actually sets the ceiling for on-device work is laid out with numbers in the measurements on running a small model on an ESP32-S3.

Early stage firmware - the one place the ceiling is written into a specification

The first stage of boot is a rare case where a size ceiling appears in a specification. The ordering question does not even arise. It is not what to discard but what single thing to keep. The first stage does not do the work; it does just enough to load the next stage and then steps aside.

The lesson from this position is that discarding capability is stronger than discarding layers. Shave a layer and you do the same job badly; move a capability and the job happens somewhere else entirely. It is the same structure as the libc point earlier.

Sandboxes - small means the amount you can audit

Where untrusted code runs, small refers not to bytes but to the quantity of code a person can read. That is why QuickJS leads with a few C files and no external dependency. Attack surface grows with the breadth of the dependency graph, not with source size.

Yet the same page also claims almost complete ES2025 support and says it passes nearly one hundred percent of the standard test suite. In other words neither grammar nor semantics is discarded here. What is discarded is the fourth axis alone, the dependencies. In a position that accepts untrusted code, reducing the language specification to a subset turns the boundary of that subset into a new vulnerability.

Teaching - small means what one person can follow

In an implementation written to teach, small means an amount that can be read in a day. What gets discarded here is performance and optimization. What is kept largest, by contrast, is the names of the stages. Lexical analysis, syntactic analysis and evaluation each have to be visible.

The contrast is dramatic. Code golf deleted tokens and syntax trees first; teaching implementations keep exactly those two at their largest. The same phrase, making it small, points in opposite directions. Purpose sets the axis, and the axis sets the order.

Code golf and minimal implementation are different jobs

The byte-saving techniques listed in the original are these.

  • Cut variable and function names down to one letter
  • Lean on the fact that the compiler links libc
  • Use globals in place of temporary variables
  • Exploit the zero-initialization of globals
  • Use C89 implicit int declarations and implicit return types
  • Use function parameters as temporaries preserved on the stack
  • Write ASCII values directly instead of character literals
  • Use the ternary and comma operators
  • Replace logical operations with bitwise ones

All nine share a property. Not one of them changes the behaviour of the language. Every one is a transformation at the level of notation. That is why the 4,800-byte version and the 1,024-byte version implement the same language.

/* skip to the end of the line - the readable version */
void skip_to_eol(void) {
  if (ch != 0 && ch != '\n') {
    next();
    skip_to_eol();
  }
}

/* the same function, golfed */
Y(){c&&c-10&&Y(G());}

/* the golfed form of the parse_sum shown earlier */
e(){for(z=t();c-43u<3;)y=44-c,z+=y*t();return z;}

Single-letter variable names, absent error handling and missing scope isolation are a different matter. Those are design decisions. No amount of renotation shrinks them.

The test that separates the two is simple. Does behaviour change when you undo it? If it does not, it was golf. If it does, it was design. Going from 4,800 to 1,024 was golf. Going from Python to something that resembles Python was design. Call both by one name and neither lesson survives.

Golf also carries a hidden cost in build conditions. Leaning on C89 implicit int means rolling the standard back, which produces a warning storm, which means the warnings must be switched off, which restricts the set of compilers where the combination works. That is why the repository notes GCC rather than Clang. Strip those conditions when repeating the size figure and it stops reproducing. What new bills appear when a compiler backend is swapped out is examined from a different angle in the piece on an LLVM-backed Go compiler.

The order for finding what your own code does not need

Transposed onto your own code, the sequence looks like this. It is not a list of techniques but an order of questions.

RankCandidateThe deciding questionCost of reversal
1Diagnostics, logging, metricsDoes the correct path produce the same result without itLow, you switch it back on
2Features nobody callsDoes the supported list match the call recordLow, you put it back
3Fast paths to the same answerIs the answer identical when it is slowerMedium, time is recoverable
4Names, structure, generalizationDoes it hold up as the scale growsHigh, it is paid in reader time
5Interfaces and contractsIs it still the same thing without thisVery high, this is identity

Three qualifications attach when the order is used on production code.

  • Rank one is about making it switchable, not deleting it. The 1,024-byte version removed error handling outright, but that works because the input is one file written by the author himself. Make the same decision in code other people run and it is not golf, it is an incident.
  • Rank two is decided by records, not documents. Supported feature lists are almost always wider than reality. Only a comparison against call records separates a live feature from a dead one.
  • From rank four the cost of reversal rises sharply. Shortening a name shrinks things now and is paid for later in the time of everyone who reads the code again. That the payment does not end after one instance is the difference between golf and production code.

And there is something to write down before the order is applied at all: the list of things that leave alongside. Drop the indentation stack and indentation validation goes with it. Turn the symbol table into an array and scope goes with it. Delete the intermediate representation and the possibility of static analysis goes with it. In all three cases one data structure was removed and two things were lost. Before counting bytes, count what that data structure was quietly doing.

Finally, the condition that flips the order: what the ceiling is made of. If it is RAM, start with data structures. If the code will be audited, start with dependencies. If a specification sets the limit, start with capability. Only when size is the ceiling does the order in this article hold as written.

What could not be confirmed

  • The size of the compiled executable - it appears neither in the original nor in the repository. The 1,024 is a source size, and executable size varies with compiler, platform and linkage. That is why no binary size figure appears in this article.
  • Exactly what the size check reports - the repository suggests wc for checking size. That command prints lines, words and bytes together, so the command alone does not settle which of the three the 1,024 refers to. The byte count used here is the one the author states.
  • Which installation gcc-16 refers to - which distribution, which package, and whether other versions produce the same outcome, is not recorded in the repository.
  • Comment syntax - the supported list includes comment support, but whether it follows the hash-character rule the Python reference defines cannot be settled from the prose of the original alone.
  • The official description of the CPython pipeline - the compiler page of the Python developer guide returned only a redirect notice on two attempts. The description of CPython stages in this article follows the wording used by the original author, while every statement about language rules comes from the official language reference and standard library documentation.
  • Execution speed figures - the original contains no measurement of how much slower the rewind-and-reparse approach actually is. Only the structural fact that each iteration reparses is stated here.
  • The specified size ceiling for the first boot stage - a widely quoted number exists, but the specification text itself was not consulted, so no figure is given.
