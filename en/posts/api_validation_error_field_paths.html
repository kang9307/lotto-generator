The Screen Cannot Tell Which Field Is Wrong - Putting Field Paths in Validation Errors

Dot notation, JSON Pointer and brackets implemented and run: escaping, array indices, and why notation is a contract

2026-08-01 Dev & Infra

Opening: the red outline landed on the entire form

An order was submitted and the server answered with 422 and one sentence: the input is invalid. The screen could not decide what to do with that sentence, so it outlined all fourteen inputs in red. The user starts working through the whole form again, including the eight boxes that were perfectly fine. The server knew exactly six places were wrong, and that knowledge never crossed the wire.

Summarising this as an unfriendly error message misses the problem. Friendliness is secondary. The real point is that the consumer of a validation error response is a screen, not a person. Users never read the response body. Code reads it, and that code has exactly one job: decide which input element gets the mark.

For that decision to be possible, every error needs a where. And that where must not be a sentence a human reads; it has to be a machine coordinate the screen can match against its own inputs. That is where the notation question begins. The same location can be written items.2.qty, or /items/2/qty, or items[2].qty. To a human they read the same. To the parsing code they are three different objects, and in front of certain field names two of the three quietly collapse.

This article is about that. I implemented a schema validator, pushed a request with three levels of nesting and arrays through it, printed the resulting errors in all three notations and parsed them back to compare with the originals. Where escaping breaks, where a shifted array index puts a red outline on the wrong box, where putting a field name into a message destroys translation: all of it confirmed by running it. The conclusion up front is that notation is not taste, it is a contract.

Environment. Every output below was actually executed on Windows 10 Pro (10.0.19045). The runtime is Node.js v22.16.0 (win32) and the shell is GNU bash 5.2.37 (MSYS2/MinGW64). The validator and every experiment script were saved as files and executed, inside a scratch working folder outside any repository. Passing code through a heredoc silently mangles quotes and backslashes.

Every example is fictional. The order API, field names, product codes and line identifiers that appear here were invented for the explanation. No validation library is chosen or judged. The validator used here is a 200 line toy written to expose the argument, on the premise that the shape of the response is what does not change whichever tool you use.

What this article does not cover. How to name error codes and how to grow the catalogue is covered in what it means to design an error code catalogue. Here the code is assumed to exist and the focus is only on the where. The coordinate problem in list responses, where items shift as you turn pages, is in what offset pagination structurally cannot do.

1. Reproduction - what one sentence leaves the screen with

First the problem has to become a number. I built an order body with three levels of nesting and two layers of arrays, and pushed it through the validator. Six problems were planted deliberately.

A 36 byte response is perfect on bandwidth. But the number of inputs the screen can point at is zero. Two options remain: mark nothing, or mark everything. Marking everything drops precision to 0.43 and drags eight innocent boxes into the accusation. The user spends time checking each of those eight.

Attach a location to the same six failures and the screen behaves completely differently.

--- 1-3. response style B: same failures, each carrying a location ---
{

--- 1-4. does the path actually point at a real place in the body? ---
  orderId                    resolves = true   depth = 1
  customer.name              resolves = true   depth = 2
  customer.contact.email     resolves = true   depth = 3
  items.2.sku                resolves = true   depth = 3
  items.2.qty                resolves = true   depth = 3
  items.2.options.0.value    resolves = false   depth = 5

deepest path in this response : items.2.options.0.value

The response grew from 36 bytes to 313. What those extra 277 bytes bought is precision from 0.43 to 1.00 and false positives from 8 to 0. Compared with the resources one user round trip consumes, the arithmetic is not close.

One detail in 1-4 deserves attention. items.2.options.0.value resolves to undefined when you pull the value out of the body, because the required field is simply absent. In other words a path stays valid even when there is no value at the place it points to. A path is not the address of a value, it is the address of a slot. Miss that distinction and a client will invent a rule that drops any path it cannot resolve in the body, swallowing every missing-required error at once.

  • The server already knew the failing rule and the location. The problem is not computation, it is transmission
  • With no path the best a screen can do is mark everything, which is close to marking nothing in usability terms
  • A depth of five shows up in practice. Object inside array inside object inside array is not an exotic structure, it is an ordinary order form
  • The validator collected failures as segment arrays rather than strings. Printing was deferred to the last step, so changing notation required no change to the validation logic

2. The same error in three notations

There are broadly three ways to turn a segment array into a string. I printed the same six failures all three ways at once.

--- 2-1. the same six failures, printed three ways ---
rule       dot                      json pointer               bracket
------------------------------------------------------------------------------------------------
pattern    orderId                  /orderId                   orderId
minLength  customer.name            /customer/name             customer.name
pattern    customer.contact.email   /customer/contact/email    customer.contact.email
minLength  items.2.sku              /items/2/sku               items[2].sku
min        items.2.qty              /items/2/qty               items[2].qty
required   items.2.options.0.value  /items/2/options/0/value   items[2].options[0].value

--- 2-2. size of the whole response in each notation ---
  dot      302 B    longest path = 23
  pointer  308 B    longest path = 24
  bracket  306 B    longest path = 25

--- 2-3. how much code does the CLIENT need to read it back ---
  dot      chars 154   needs a tokenizer loop: no
  pointer  chars 302   needs a tokenizer loop: no
  bracket  chars 472   needs a tokenizer loop: yes

The size difference is negligible: six bytes across the whole response, under two percent. The meaningful difference is on the parsing side. The dot parser is a one line split. The JSON Pointer parser adds two substitutions to undo the escapes. Only bracket notation needs a loop that walks the string character by character, because an opening bracket has to find its closing partner and the boundary between dots and brackets has to be handled by hand.

On ordinary paths all three are fine. Print, parse back and compare with the original segments and every case passes.

--- 2-4. round trip on the ordinary paths: print then parse then compare ---
segments                        dot     pointer  bracket
------------------------------------------------------------
["orderId"]                     true    true     true
["customer","name"]             true    true     true
["customer","contact","email"]  true    true     true
["items",2,"sku"]               true    true     true
["items",2,"qty"]               true    true     true
["items",2,"options",0,"value"] true    true     true

--- 2-5. same path, resolved against the body through each notation ---
  dot      items.2.qty          -> ["items",2,"qty"] -> value 0
  pointer  /items/2/qty         -> ["items",2,"qty"] -> value 0
  bracket  items[2].qty         -> ["items",2,"qty"] -> value 0

--- 2-6. is the notation self describing? a lone path with no schema at hand ---
  dot      items.2.options.0.value    array steps are invisible, 2 could be a key
  pointer  /items/2/options/0/value   array steps are invisible, 2 could be a key
  bracket  items[2].options[0].value  array steps are marked by brackets

  none of the three can prove 2 is an index without the schema;
  bracket only records what the SERVER believed when it printed.

Block 2-6 clears up a common illusion. Bracket notation genuinely has the advantage that array steps are visible. Reading logs by eye, items[2] parses faster than items.2. But that information is only a record of what the server believed at print time. A client cannot use that marking to re-verify that the step really was an array. Whether a number is an index or a key is always the schema's call, and no notation makes that call for you.

3. The escaping trap - when a name contains a dot, a slash or a bracket

This is where the choice actually matters. A JSON object key can hold almost any character, and real bodies are full of such keys: config maps keyed by version string, dictionaries keyed by header name, user supplied tag names, aggregates keyed by year. I built nine cases, printed them in all three notations and parsed them back.

--- 3-1. print each key with all three notations ---
case                        dot                       pointer                     bracket
--------------------------------------------------------------------------------------------------------
plain key                   meta.source               /meta/source                meta.source
dot in key                  meta.app.version          /meta/app.version           meta.app.version
slash in key                headers.x-forwarded/for    /headers/x-forwarded~1for   headers.x-forwarded/for
bracket in key              tags.group[a]             /tags/group[a]              tags.group[a]
tilde in key                tags.draft~2              /tags/draft~02              tags.draft~2
digits as key               byYear.2024.total         /byYear/2024/total          byYear.2024.total
empty key                   tags.                     /tags/                      tags.
dot plus index              rows.3.unit.price         /rows/3/unit.price          rows[3].unit.price
key that looks like a path  fields.items.0.qty        /fields/items.0.qty         fields.items.0.qty

--- 3-2. now parse them back and compare with the original segments ---
case                        dot     pointer  bracket
--------------------------------------------------------
plain key                   true    true     true
dot in key                  false   true     false
slash in key                true    true     true
bracket in key              true    true     false
tilde in key                true    true     true
digits as key               false   false    true
empty key                   true    true     false
dot plus index              false   true     false
key that looks like a path  false   true     false
--------------------------------------------------------
survived                    5/9     8/9      4/9

Five for dot, four for brackets, eight for JSON Pointer. The gap comes from the presence of a rule, not from capability. Dot and bracket notation have no specification at all for what to do when the separator appears inside a name. So information is lost at print time and there is no way to recover it at parse time.

Looking at what the client actually receives when a notation collapses makes the severity obvious.

--- 3-3. what the client actually receives when a notation collapses ---
  dot in key
    server meant : ["meta","app.version"]
    printed as   : meta.app.version
    client reads : ["meta","app","version"]
    segments     : 2 -> 3
  digits as key
    server meant : ["byYear","2024","total"]
    printed as   : byYear.2024.total
    client reads : ["byYear",2024,"total"]
    segments     : 3 -> 3
  dot plus index
    server meant : ["rows",3,"unit.price"]
    printed as   : rows.3.unit.price
    client reads : ["rows",3,"unit","price"]
    segments     : 3 -> 4
  key that looks like a path
    server meant : ["fields","items.0.qty"]
    printed as   : fields.items.0.qty
    client reads : ["fields","items",0,"qty"]
    segments     : 2 -> 4

--- 3-4. bracket notation on a key that contains a bracket ---
  server meant : ["tags","group[a]"]
  printed as   : tags.group[a]
  client reads : ["tags","group",null]
  the printer has no escape rule for ] at all, so the string is not recoverable

The case where segments grow from two to four is the worst. The client has no way to know it read it wrong. fields.items.0.qty looks like a syntactically perfect path, parsing succeeds and no exception is raised. It just points at a slot that does not exist. Case 3-4 is even blunter: meeting a closing bracket inside a name, the parser emitted null as a segment. With no escape rule in the printer, the string itself became unrecoverable.

JSON Pointer behaves differently here, because the rule is written down.

--- 3-5. the only notation with a written escape rule ---
  key "x-forwarded/for"    pointer /headers/x-forwarded~1for  back "x-forwarded/for"    equal true
  key "draft~2"            pointer /tags/draft~02             back "draft~2"            equal true
  key "a~/b"               pointer /tags/a~0~1b               back "a~/b"               equal true

--- 3-6. and the one it still cannot settle by itself ---
  object with a numeric KEY : {"byYear":{"2024":{"total":0}}}
  pointer                   : /byYear/2024/total
  parsed with number guess  : ["byYear",2024,"total"]
  parsed as pure strings    : ["byYear","2024","total"]
  RFC 6901 says: try the string key first, treat it as an index only for arrays.
  a client that guesses by shape alone will mislabel numeric object keys.

A slash becomes ~1 and a tilde becomes ~0. The third line shows how careful the rule is: a~/b becomes a~0~1b and comes back exactly. The order of undoing matters. Turn ~1 into a slash first, then ~0 into a tilde. Reverse that order and an input like ~01 comes out differently. That is precisely why RFC 6901 specifies the order.

One thing JSON Pointer still cannot settle alone remains: a numeric object key. If a client receiving /byYear/2024/total from an aggregate keyed by year decides that anything shaped like a number is an index, it is wrong. RFC 6901 is explicit: against an object the token is a member name, and it is only interpreted as an index for arrays. The deciding factor is not the look of the string but the type of the value sitting at that place.

4. The lifetime of an array index - when one item disappears

Solving escaping leaves a different problem for arrays. An index is a coordinate valid only for the array as it looked when the request left. I built a four row cart, planted a problem in the third row, and reproduced the user deleting the second row while the response was in flight.

--- 4-1. the cart as sent, and the errors that came back ---
  [0] ln_7742  sku="SKU-A1"  qty=2
  [1] ln_9310  sku="SKU-B7"  qty=1
  [2] ln_5518  sku=""        qty=0
  [3] ln_2064  sku="SKU-D3"  qty=5

  items.2.sku     rule=required  lineId=ln_5518
  items.2.qty     rule=min       lineId=ln_5518

--- 4-2. the user removes row 1 while the response is in flight ---
  [0] ln_7742  sku="SKU-A1"  qty=2
  [1] ln_5518  sku=""        qty=0
  [2] ln_2064  sku="SKU-D3"  qty=5

--- 4-3. apply the index paths to the cart as it is NOW ---
path from server  index  row now at that index correct row
----------------------------------------------------------------------
items.2.sku       2      ln_2064 (SKU-D3)      NO  should be ln_5518
items.2.qty       2      ln_2064 (SKU-D3)      NO  should be ln_5518

  misplaced marks : 2 of 2

--- 4-4. what the screen shows after the shift ---
  items.2.sku       -> marks ln_2064.sku     value "SKU-D3"  a red line on a VALID field
  items.2.qty       -> marks ln_2064.qty     value 5         a red line on a VALID field

Both errors landed on the wrong row. And the values at that row are SKU-D3 and 5, entirely valid. From the user's side: a red outline appears on a healthy row while the actually broken row shows nothing. The user clears and retypes a correct value, submits again, and the server returns the same error every time. There is no way for the user to work out the cause from that state.

This looks like a timing accident but it is not. The cause is that an index carries no identity. Give each item a stable identifier that the client sends with the request and the server echoes back on the error, and the problem disappears.

--- 4-5. same errors carried by a stable id instead ---
  ln_5518.sku       row still present, mark it
  ln_5518.qty       row still present, mark it
  misplaced marks : 0 of 2

--- 4-6. the response that carries both ---
{
 "error": "validation_failed",
 "errors": [
  {
   "path": "items.2.sku",
   "keyPath": "items[lineId=ln_5518].sku",
   "rule": "required"
  },
  {
   "path": "items.2.qty",
   "keyPath": "items[lineId=ln_5518].qty",
   "rule": "min"
  }
 ]
}

  bytes index only  : 117
  bytes both        : 193

--- 4-7. does the server even know the client id? only if the client sent it ---
  body the client sent : {"sku":"","qty":0}
  fields the server can echo back : sku, qty
  stable handle available : no
  so the id has to be part of the REQUEST schema, not invented in the response.

Switching to a stable identifier moved misplacements from 2 to 0. If the item was deleted, it becomes explicit that the error has nowhere to attach, so dropping it is safe. An index cannot make that judgement. An index always points at somebody, and there is no way to know whether that somebody is the original target.

Block 4-7 holds the most commonly missed precondition. A server cannot echo an identifier the client never sent. If the request body contains only sku and qty, those two are all the server can echo. The stable identifier is therefore a matter of request schema design, not response design. The moment you decide to put it in the error response, the request side of the contract changes too.

  • Do not throw the index path away, send both. Indices remain convenient for logs and server side debugging
  • Carrying both coordinates grows the response from 117 to 193 bytes: 38 bytes per error
  • The identifier can come from the server or be a temporary value the client made up. It only has to stay unchanged between request and response
  • The same problem appears when the client adds an item. Deletion is not the only thing to watch
  • If the screen lets users reorder rows, indices are unusable from the start

5. Stop at the first failure, or collect them all

Having decided to attach locations, the next decision is quantity. Return immediately on the first failure, or gather everything and answer once. I processed the same body both ways, driving a user who fixes only the box they were told about against a server that reports one error at a time.

--- 5-1. stop at the first failure: how many round trips to a clean form ---
  trip 1  server says: orderId                   (pattern)
  trip 2  server says: customer.name             (minLength)
  trip 3  server says: customer.contact.email    (pattern)
  trip 4  server says: items.2.sku               (minLength)
  trip 5  server says: items.2.qty               (min)
  trip 6  server says: items.2.options.0.value   (required)
  total round trips : 6

--- 5-2. collect everything: one round trip ---
  errors returned   : 6
  total round trips : 1

--- 5-3. three response shapes for the same six failures ---
  flat path list      302 B    client walk = one loop
  plus params         459 B    client walk = one loop
  plus english text   859 B    client walk = one loop
  nested tree         217 B    client walk = recursive

  the nested tree, printed:
{"orderId":["pattern"],"customer":{"name":["minLength"],"contact":{"email":["pattern"]}},"items":{"2":{"sku":["minLength"],"qty":["min"],"options":{"0":{"value":["required"]}}}}}
  note: to find a leaf the client must recurse, and array levels look like objects.

Six versus one. From the user's side that is six submissions and six waits. It is the classic shape of a form with a rising abandonment rate, and on the server side it is six times the requests. If validation has no side effects, collecting is almost always better.

The nested tree in 5-3 is an interesting trap. At 217 bytes it is the smallest and the structure looks tidy. But array levels look like objects. In "items":{"2":{...}} the 2 is an index serialised as a key: the numeric key problem from section 3 reproduced exactly. On top of that the client has to recurse to find a leaf. The flat list loses slightly on size and wins with a single loop.

Having chosen to collect, you have to know how far the size grows.

--- 5-4. how big does collect-all get on a bulk request ---
  items   errors  flat B    with params B  with text B
  ------------------------------------------------------
  1       2       118       172            296
  10      20      820       1360           2600
  100     200     8020      13420          26000
  1000    2000    81820     135820         263600

--- 5-5. capping the list, and saying so ---
  total failures     : 2000
  returned           : 50
  truncated flag     : true
  bytes uncapped     : 81820
  bytes capped       : 2056
  without the flag the screen believes it has the whole list and clears the rest.

--- 5-6. two failures on ONE field: does the list keep both ---
  orderId       minLength {"min":10,"got":1}
  orderId       pattern   {"hint":"ORD-000000"}
  items.0.qty   max       {"max":99,"got":500}
  grouped by path : {"orderId":["minLength","pattern"],"items.0.qty":["max"]}
  a map keyed by path (path -> one message) would silently drop the loser.

A bulk request of a thousand items produces two thousand errors, and adding human sentences takes the response to 263 kilobytes. The screen only shows the first few anyway. So a cap is right, but you must announce that you truncated. A screen that does not know the list was cut concludes that anything missing has been resolved and clears the remaining marks.

Block 5-6 gives one decisive reason for the response shape. Two rules can fail on the same field at once. Here orderId is both too short and malformed. Build the errors as a map keyed by path and the later entry overwrites the earlier one, so one disappears. The user fixes the length, resubmits, and only then hears about the format. That is why it has to be a list and not a map.

6. Separating human wording from machine paths

A common compromise appears here: put the field name in the message and both the user and the screen can work with it. Run it and both expectations collapse.

--- 6-1. the server bakes the label into the sentence, one language only ---
  response : [{"message":"Quantity must be at least 1."}]

  a screen in another language now has three bad options:
    1. show the English sentence to a non English reader
    2. translate the sentence at runtime, per request
    3. match the sentence text to decide which box to mark

--- 6-2. option 3 in practice: matching on the sentence ---
  screen locale en   label on screen Quantity     found in the sentence: true
  screen locale de   label on screen Menge        found in the sentence: false
  screen locale es   label on screen Cantidad     found in the sentence: false
  screen locale pt   label on screen Quantidade   found in the sentence: false
  labels matched : 1 of 4
  the only locale that matches is the one the server happened to be written in.

--- 6-3. the same sentence after a harmless copy edit on the server ---
  before : Quantity must be at least 1.   -> client match on "Quantity" = true
  after  : The quantity must be at least 1.   -> client match on "Quantity" = false
  a wording change is a breaking change once the screen parses the wording.

Only one of four locales matched, and that one was the language the server code was written in. The other three cannot find their own field label in the sentence. But 6-3 is more dangerous. Adding a single article to the front of the sentence broke the match immediately. The moment a screen parses wording, editing copy becomes a breaking change. And that break shows up in no test at all, because on the server side someone merely polished a sentence.

The fix is to split. Location, rule code and parameters from the server; the human sentence from the screen.

--- 6-4. split it: path and rule stay, wording moves to the client ---
{"error":"validation_failed","errors":[{"path":"orderId","rule":"pattern","params":{"hint":"ORD-000000"}},{"path":"customer.name","rule":"minLength","params":{"min":1,"got":0}},{"path":"customer.contact.email","rule":"pattern","params":{"hint":"name at host"}},{"path":"items.2.sku","rule":"minLength","params":{"min":1,"got":0}},{"path":"items.2.qty","rule":"min","params":{"min":1,"got":0}},{"path":"items.2.options.0.value","rule":"required","params":{}}]}

  bytes : 459

--- 6-5. one response, rendered by four screens ---
  path                      locale  what the user reads
  ------------------------------------------------------------------------------
  items.2.qty               en      Quantity must be at least 1.
  items.2.qty               de      Menge muss mindestens 1 betragen.
  items.2.qty               es      El campo Cantidad debe ser al menos 1.
  items.2.qty               pt      O campo Quantidade deve ser no minimo 1.
  items.2.options.0.value   en      Option value is required.
  items.2.options.0.value   de      Optionswert wird benoetigt.
  items.2.options.0.value   es      El campo Valor de opcion es obligatorio.
  items.2.options.0.value   pt      O campo Valor da opcao e obrigatorio.

--- 6-6. sentence length across the four, same path every time ---
  en   chars 28   Quantity must be at least 1.
  de   chars 33   Menge muss mindestens 1 betragen.
  es   chars 38   El campo Cantidad debe ser al menos 1.
  pt   chars 40   O campo Quantidade deve ser no minimo 1.
  path is 11 chars in all four : items.2.qty

--- 6-7. the fallback the server still owes you ---
  rule from server : skuBlockedForRegion
  client knows it  : false
  with no fallback : the box is marked red with an empty tooltip
  with a fallback  : the server also ships a plain default sentence
  {"path":"items.0.sku","rule":"skuBlockedForRegion","params":{"region":"KR"},"message":"This item cannot be shipped to the selected region."}
  the message is a LAST RESORT for unknown rules, never the thing the screen parses.

Block 6-6 is the summary of this section. Sentences ranged from 28 to 40 characters while the path was 11 characters all four times. Wording differs by language and drifts over time; the path stays put unless the schema changes. Mix the changing and the unchanging into the same string and the part that should not change gets dragged along by the part that does.

Removing the sentence entirely is not the answer either, and 6-7 shows why. When the server adds a new rule code that the screen's phrase dictionary does not carry yet, you get a box painted red with an empty explanation. So the server must ship a default sentence for unknown rules. What matters is its role: a last resort, never the thing the screen parses. The screen uses its own phrasing for rules it knows and only falls back to the server sentence for rules it does not.

  • The server produces three things: path, rule code, parameters. Parameters carry the numbers and hints that get slotted into a sentence
  • The screen produces two: field labels and sentences. The dictionary key is the path with indices removed, so every array row shares one entry
  • Rule codes must be stable. Renaming a code carries the same weight as changing a path
  • The server fallback sentence only needs one language. It is never used for rules the screen knows
  • Make an unknown rule code log a warning so that a server side rule addition does not quietly go missing after deployment

7. The code that binds a path to an input element

Now the last piece. Even a well built response does nothing if the screen cannot bind the path to its own input elements. I built a screen with 14 input widgets and 6 region containers and pushed the response straight through it.

The binding itself is trivial: make the name attribute of the input equal to the path and one lookup finishes it. What matters is not writing those names by hand. If the code that builds the request body and the code that builds the input names do not share a function, the two will drift apart. Array indices especially.

The real problem is in 7-2. Of the six paths in the response, three have no matching input on this screen. The reasons differ. billing.taxId is a field this step does not show at all, items.9.sku is a ninth item the screen does not have, and the empty path names the whole body as a cross field error. This is not an edge case, it is the default. Servers and screens do not deploy at the same rate.

8. Meeting a path the screen does not recognise

There are three choices: drop it, promote it to a banner at the top, or walk the path backwards to find a containing region and attach it there. I applied all three to the same response.

The result of the ignore policy is right there in 7-5. The submission failed and nothing on the page explains why. The user presses the button again and the same thing happens. This is the classic cause behind support tickets that do not go down even after the validation error response was improved. The server reported it correctly and the screen quietly threw it away.

Block 7-6 is the actionable item. Hold one invariant on the client. The number of errors in the response and the number displayed somewhere on the page must match. Raising that as a warning in development builds alone catches the swallowing accident before release when the server adds a new field.

The prefix promotion policy is a bit kinder. For items.9.sku it tried items.9, found nothing, then tried items and attached the mark to the whole cart region. The user at least knows which area to look at. That policy has a limit too: for billing.taxId not even the parent billing exists on the screen, so it ended up in the banner.

I wrote the requirements gathered so far as rules and ran them against five response shapes. This is not a validator for requests, it is a linter for the contract.

10. Design rules and the checklist

Everything confirmed by running it comes to five lines. The evidence behind each rule is the output above.

  • Pick one notation and write it down. If there is any chance a name contains a special character, that is JSON Pointer. It was the only notation to pass 8 of 9 round trips, and its escape rule lives in a standard document
  • Never mix notations inside one response. If framework errors and domain checks land in the same array, normalise the notation in one place just before it goes out
  • Give array items both an index and a stable identifier. That requires the identifier to exist in the request schema first. It is the one rule you cannot satisfy by changing the response alone
  • Return errors as a list, not a map. Two rules can fail on one field at once, and a map quietly discards one of them
  • Let the screen build the wording, but keep one server sentence. It is the only safety net for a rule code the screen has never seen

The most commonly skipped decision. Meetings get held about which notation to use, but no meeting is held about what to do with an unrecognised path. Yet in the measurement, half of the response consisted of paths with no matching element on the screen. Without that rule each screen decides for itself, and most choose to drop silently. That is how you end up with a third of the errors the server correctly reported never reaching the user.

The checklist follows. Every item is something a failure was actually produced for above.

  • The notation is written into the specification document
  • A sample with dots, slashes and brackets in field names passes the round trip test
  • You checked that a numeric object key is not mistaken for an index
  • Array item errors carry a stable identifier
  • That identifier is defined in the request schema too
  • Errors are a list, and one field can carry two of them
  • The list has a cap and ships a flag saying it was truncated
  • The screen does not parse sentences
  • Every rule code has a phrase entry on the screen, and a missing one logs a warning
  • The convention that an empty path means the whole body is documented
  • The screen holds a displayed count invariant
  • Input element names and request body paths come from the same function
  • The policy for unrecognised paths is the same on every screen

11. What this article did not verify

  • Accessibility wiring in a real browser. Binding paths to inputs was confirmed, but how the resulting marks reach assistive technology is outside this experiment
  • State management in nested form components. How a screen keeps paths and component state in sync while items are added, removed and reordered differs by framework
  • Partial success responses. How to carry successful and failed items together when only part of a bulk request fails is a separate design problem
  • Asynchronous validation. Rules that need a server round trip, such as uniqueness checks, deliver errors mid typing rather than on submit. The lifetime of a path there resembles the array problem here but is not identical
  • Response size at production scale. The numbers in section 5 come from synthetic data. Real field names are longer and parameters are richer

Conclusion: the recipient of an error response is a screen, not a person

Start from the idea of reporting validation errors well and the conclusion drifts towards writing friendlier sentences. What running it actually showed points the other way. A friendly sentence can be built on the screen, but only the server knows which box is wrong. What the server has to send is a coordinate, not a sentence.

Deciding to send a coordinate immediately drags in the notation question. And notation turned out not to be a matter of taste. A single dot inside a field name grew two segments into three, and the client had no way to know it read it wrong. Bracket notation emitted a null segment over one closing bracket inside a name. The difference between a notation with a written escape rule and one without showed up as 5 versus 8 in the round trip test.

Arrays were a separate problem. An index carries no identity, so deleting one item put both errors on the wrong row, leaving a red outline on a healthy field and no mark at all on the broken one. Switching to a stable identifier took it to zero, but doing so required changing the request schema first. It was not a problem the response could solve alone.

So the conclusion is this. Notation is a contract. The rule the server prints with and the rule the screen parses with must be the same, that rule must be written down somewhere, and it must not wobble inside a single response. Only with that contract in place does an error response start earning its keep.

There is one thing you can check right now. Open the code that handles validation errors on the screen you are working on and look for a line comparing the number of errors in the response with the number actually displayed. If it is missing, that screen may be quietly discarding errors the server reported correctly. And no amount of care in building the error response will reveal it.

# Validation error field paths - notation table and response schema, ready to paste

> Source: braindetox.kr - the screen cannot tell which field is wrong
> Evidence: verified by running a hand written validator on Windows 10 / Node.js 22.16 (win32) / bash 5.2.37 (MSYS2)
> Paste this straight into an AI tool and say: review our error responses against these criteria.
> Principle: the recipient of an error response is a screen, not a person. It only earns its keep if the screen can bind the path to an input.

## 1. Three notations compared (measured round trips)

| Property | Dot `items.2.qty` | JSON Pointer `/items/2/qty` | Bracket `items[2].qty` |
|---|---|---|---|
| Parser size | 154 chars | 302 chars | **472 chars** |
| Tokenising loop | not needed | not needed | **needed** |
| Escape rule | **none** | tilde `~0` and slash `~1` | **none** |
| Array step visible | no | no | yes (server claim) |
| Standard document | convention | **RFC 6901** | convention |
| Naming the whole body | needs a convention | empty string | needs a convention |
| Awkward keys, 9 round trips | 5 | **8** | 4 |

**Verdict: if a name might contain a special character, use JSON Pointer.**

## 2. Where escaping breaks

| Character in the key | Dot | Pointer | Bracket | Symptom |
|---|---|---|---|---|
| Dot `app.version` | broken | ok | broken | segments 2 to 3 |
| Slash `x-forwarded/for` | ok | ok | ok | dot is safe by accident |
| Bracket `group[a]` | ok | ok | broken | parser returns a null segment |
| Tilde `draft~2` | ok | ok | ok | escape rule restores it exactly |
| Numeric key `2024` | broken | broken | ok | key mistaken for an index |
| Empty string key | ok | ok | broken | the segment quietly disappears |
| Key that looks like a path | broken | ok | broken | 2 to 4, points at nothing |

- Order matters when undoing: `~1` to slash first, then `~0` to tilde
- Decide a numeric token by **the type of the value at that place**, not by notation (object means name, array means index)

## 3. The lifetime of an array index

- An index is a coordinate valid only for **the array as it looked when the request left**
- Delete one item and the errors shift down a row: red outline on a healthy box, nothing on the broken one
- Measured: 2 of 2 misplaced, dropping to 0 of 2 with a stable identifier
- **The identifier has to be in the request schema first.** A server cannot echo what the client never sent
- Adding and reordering cause the same problem. Deletion is not the only case to watch

## 4. Response schema

```
{
  "error": "validation_failed",
  "truncated": false,
  "totalErrors": 6,
  "errors": [
    {
      "path": "items.2.qty",
      "keyPath": "items[ln_5518].qty",
      "rule": "min",
      "params": { "min": 1, "got": 0 },
      "message": "Default sentence, used only for rules the screen does not know"
    }
  ]
}
```

| Field | Who uses it | Without it |
|---|---|---|
| `path` | screen and logs | no way to decide which box to mark |
| `keyPath` | screen (arrays) | a shifted row gets the mark |
| `rule` | screen (phrase choice) | wording gets parsed, copy edits break things |
| `params` | screen (phrase assembly) | the 1 in at least 1 cannot reach the sentence |
| `message` | screen (unknown rules only) | a red box with no explanation |
| `truncated` | screen (list handling) | a cut list is treated as complete |
| `totalErrors` | screen and monitoring | cannot tell the user how many were cut |

- **A list, not a map.** Two rules can fail on one field at once
- First error only measured 6 round trips; collecting everything took 1
- 1,000 items in bulk = 2,000 errors = 263 KB with sentences, so a cap plus `truncated` is mandatory

## 5. Client mapping

```
function applyErrors(resp, form) {
  let shown = 0;
  for (const e of resp.errors) {
    const el = form.querySelector('[name="' + cssEscape(e.path) + '"]');
    if (el) { markField(el, textFor(e.rule, e.params)); shown++; continue; }
    if (e.path === '') { banner(textFor(e.rule, e.params)); shown++; continue; }
    // unknown path: walk the prefix back to find a containing region
    const segs = parsePath(e.path);
    let box = null;
    for (let n = segs.length - 1; n > 0; n--) {
      if (box) break;
      box = form.querySelector('[data-scope="' + printPath(segs.slice(0, n)) + '"]');
    }
    if (box) { markScope(box, textFor(e.rule, e.params)); shown++; }
    else { banner(fallbackText(e)); shown++; }
  }
  // invariant: errors in the response must equal errors shown on the page
  if (shown !== resp.errors.length) warnInDev(resp.errors.length - shown);
}
```

| Policy | Surfaced | What the user sees | Risk |
|---|---|---|---|
| Ignore | 4/6 | submit fails, no explanation | **invariant broken, never the default** |
| Banner | 6/6 | raw paths at the top | internal field names leak |
| Prefix promotion | 6/6 | region marked, rest in a banner | too wide a target misleads |

## 6. Human wording versus machine paths

- The server produces: **path, rule code, parameters**
- The screen produces: **field labels, sentences**
- Measured: picking a box by matching the server English sentence worked in 1 of 4 locales
- Adding a single article in a copy edit broke the match instantly, so **editing copy is a breaking change**
- Sentences ranged 28 to 40 characters; the path was 11 characters all four times
- The server keeps **one default sentence for unknown rules** (a last resort, not a parsing target)

## 7. Checklist

- [ ] The **notation is written into the specification** document
- [ ] Field names containing dots, slashes and brackets pass a **round trip test**
- [ ] You checked that a **numeric object key** is not mistaken for an index
- [ ] Array item errors carry a **stable identifier**
- [ ] That identifier is defined in the **request schema** too
- [ ] Errors are a **list**, and one field can carry two of them
- [ ] The list has a **cap** and ships a flag saying it was truncated
- [ ] The screen **does not parse sentences**
- [ ] Every rule code has a **phrase entry**, and a missing one logs a warning
- [ ] The convention that an **empty path** means the whole body is documented
- [ ] The screen holds a **displayed count invariant**
- [ ] Input element names and request body paths come from **the same function**
- [ ] The policy for unrecognised paths is **the same on every screen**

## 8. What not to do

- Do not **mix notations** inside one response, where framework errors meet domain errors
- Do not return errors as a **map keyed by path**, one of two rules on a field disappears
- Do not point at array errors **by index alone**, deletion, insertion and reordering all shift them
- Do not let the screen **parse server sentences**, a copy edit becomes an outage
- Do not **silently drop** an unrecognised path, the submit fails with no explanation
- Do not **truncate the list without saying so**, the screen treats the rest as resolved
- Do not **hand write input element names**, they diverge from body paths on the first insert
