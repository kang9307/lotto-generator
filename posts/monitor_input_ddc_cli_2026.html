모니터 입력을 커맨드라인에서 전환하기 - DDC/CI와 monitor-input-rs 완전 정리

KVM 스위치 없이 한 모니터로 여러 PC를 오가는 법 - DDC/CI 프로토콜의 원리와 실전 활용

2026-07-22 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: KVM 없이 한 모니터를 여러 PC가 나눠 쓴다는 것

작업용 PC와 게임용 PC를 한 책상에 두고, 모니터는 한 대뿐인 환경을 떠올려 보자. 두 컴퓨터를 오갈 때마다 모니터 앞으로 손을 뻗어 입력 소스 버튼을 몇 번씩 누르고, OSD(온스크린 메뉴)를 뒤져 HDMI1에서 DisplayPort로 바꾸는 일을 반복해 본 적이 있다면 이 불편함이 무엇인지 바로 감이 올 것이다. 하드웨어 KVM 스위치를 사면 해결되긴 하지만, 영상 신호를 한 번 거치는 장치가 늘어나는 만큼 해상도·주사율 제한이나 HDCP 문제가 새로 생기는 경우도 드물지 않다.

GeekNews(hada.io)에 소개된 monitor-input-rs는 이 문제를 완전히 다른 층위에서 푼다. 하드웨어를 하나 더 사는 대신, 이미 모니터 안에 들어 있는 제어 기능을 명령줄에서 직접 두드리는 방식이다. 이 글은 그 바탕이 되는 DDC/CI 프로토콜이 실제로 무엇을 하는지, 이 도구가 왜 지금 방식으로 만들어졌는지, 그리고 어디까지 기대하고 어디서부터는 조심해야 하는지를 정리한다. 2026년 7월 기준으로 확인한 저장소와 관련 문서를 근거로 삼았다.

1. DDC/CI란 무엇인가 - 모니터를 소프트웨어로 제어하는 표준

DDC/CI(Display Data Channel / Command Interface)는 VESA가 제정한 표준으로, 호스트 PC와 모니터가 영상 케이블 안에 함께 지나가는 보조 채널을 통해 서로 대화하게 해준다. 요점은 간단하다. 모니터의 밝기·명암·입력 소스 같은 설정이 물리 버튼을 누르지 않아도 소프트웨어 명령으로 바뀔 수 있다는 것이다.

1.1 I2C 위에 얹힌 제어 채널

DDC/CI는 HDMI·DVI·DisplayPort 케이블 안에 함께 지나가는 I2C 버스를 물리 계층으로 쓴다. 컴퓨터가 마스터, 모니터가 슬레이브 역할을 맡아 정해진 주소로 짧은 명령 시퀀스를 주고받는다. 화면에 그려지는 영상 신호와는 완전히 별개의 채널이라, DDC/CI 명령을 보낸다고 화면이 깜빡이거나 끊기지 않는다.

1.2 VCP 코드와 MCCS 표준

이 채널 위에서 실제로 무엇을 어떻게 요청할지 정의하는 것이 MCCS(Monitor Control Command Set)다. MCCS는 설정 항목마다 VCP(Virtual Control Panel) 기능 코드를 부여한다. 예를 들어 밝기는 0x10, 입력 소스 선택은 0x60번 코드로 다뤄진다. 리눅스의 ddcutil 같은 도구에서 setvcp 60 0x0f 식으로 값을 지정해 입력을 바꾸는 것도 결국 이 표준 위에서 벌어지는 일이다. monitor-input-rs는 이 저수준 코드를 사용자가 직접 외울 필요 없이, 모니터 이름과 입력 이름 같은 사람이 읽기 편한 문자열로 감싸 놓은 도구라고 이해하면 된다.

2. monitor-input-rs가 푸는 실제 불편

monitor-input-rs는 일본 개발자 kojiishi가 공개한 오픈소스 프로젝트로, DDC/CI를 이용해 모니터 입력 소스를 명령줄에서 전환하는 것이 유일한 목적이다. 화려한 GUI도, 트레이 아이콘도 없다. 그 단순함이 오히려 스크립트와 단축키에 물려 쓰기 좋은 이유이기도 하다.

2.1 물리 버튼 대신 명령 한 줄

모니터 OSD를 통해 입력을 바꾸는 절차는 기종마다 버튼 배치가 다르고, 메뉴 depth도 제각각이다. 반면 monitor-input-rs는 모니터명=입력값 형태의 통일된 문법을 제공한다. 한 번 스크립트나 단축키로 등록해 두면, 이후로는 그 조합을 누르는 것만으로 전환이 끝난다. GeekNews 댓글에서도 실제 사용자가 셸 별칭(alias)으로 mon 같은 짧은 명령을 만들어 윈도우와 맥 사이를 오간다는 경험이 공유됐는데, 이것이 이 도구가 노리는 정확한 사용 패턴이다.

2.2 왜 크로스플랫폼·Rust인가

DDC/CI 자체는 플랫폼마다 접근하는 방식이 다르다. 윈도우는 자체 모니터 설정 API, 맥OS는 IOKit 계열 접근, 리눅스는 i2c-dev 커널 모듈을 경유한다. monitor-input-rs는 이 차이를 ddc-hi라는 크레이트로 흡수해, 같은 CLI 문법이 세 플랫폼 모두에서 동일하게 동작하도록 만들었다. Rust로 작성된 점도 실용적인 이유가 있다. 별도 런타임 설치 없이 단일 실행 파일로 배포되고, 시작 지연이 사실상 없어 단축키나 자동화 스크립트에 물려 써도 체감 지연이 없다. 커맨드라인 우선 설계이기 때문에 셸 함수, 크론잡, 핫키 매니저 등 어떤 자동화 도구에도 그대로 끼워 넣을 수 있다는 점이 GUI 전용 도구와 가장 크게 갈리는 지점이다.

3. 실제로 어떻게 쓰는가 - 설치와 명령 개념

공식 저장소 기준으로 설치와 기본 사용법을 정리하면 다음과 같다. 정확한 최신 옵션은 저장소 문서를 확인하는 것이 안전하다.

3.1 설치

Rust 툴체인이 설치돼 있다면 cargo install monitor-input 한 줄로 crates.io에 등록된 배포판이 설치된다. 저장소에서 바로 빌드하려면 cargo install --git https://github.com/kojiishi/monitor-input-rs를 쓴다. 리눅스에서는 libudev 개발 패키지가 미리 있어야 빌드가 된다. 윈도우에서 콘솔 창을 띄우지 않고 백그라운드 실행 파일로 쓰고 싶다면, -F winapp 기능 플래그를 붙여 설치하면 monitor-inputw.exe가 만들어지고 오류는 콘솔 대신 윈도우 알림으로 표시된다.

# crates.io에서 설치
cargo install monitor-input

# 저장소에서 직접 설치
cargo install --git https://github.com/kojiishi/monitor-input-rs

# 윈도우용 콘솔리스 버전
cargo install monitor-input -F winapp

3.2 기본 명령

사용법은 모니터를 나열하고, 이름으로 좁히고, 입력값을 지정하는 세 단계로 요약된다. 값 여러 개를 나열하면 실행할 때마다 다음 값으로 넘어가는 토글·순환 동작도 지원한다.

# 연결된 모니터 전체 나열
monitor-input

# 모니터명에 특정 문자열이 포함된 것만 검색
monitor-input Dell

# 특정 모니터의 입력을 DisplayPort 1로 지정
monitor-input U2723=dp1

# hdmi1과 usbc2 사이를 실행할 때마다 토글
monitor-input P3223=hdmi1,usbc2

# hdmi1 → usbc2 → dp1 순으로 순환
monitor-input P3223=hdmi1,usbc2,dp1

이 문법의 핵심은 값을 쉼표로 나열하면 자동으로 순환한다는 점이다. 즉 단축키 하나에 monitor-input P3223=hdmi1,usbc2만 걸어 두면, 누를 때마다 두 입력을 오가는 토글 버튼이 완성된다. VCP 코드나 벤더별 값 표를 직접 찾아볼 필요가 없다는 것이 ddcutil 같은 저수준 도구 대비 가장 큰 사용성 차이다.

4. 활용 시나리오 - 어디에 끼워 넣을 것인가

4.1 작업 PC ↔ 게임 PC

가장 직관적인 쓰임새다. 업무 노트북과 게임용 데스크톱을 한 모니터에 물려 놓고, 단축키 하나로 넘나든다. 물리 버튼을 누르는 몇 초의 마찰이 사라지면, 실제로 전환 빈도 자체가 늘어나는 경험을 하는 사용자가 많다. 번거로움이 줄면 행동 패턴이 바뀐다는 흔한 UX 원리가 여기서도 그대로 나타난다.

4.2 홈랩·다중 서버 콘솔

서버 여러 대나 미니 PC 클러스터를 한 모니터로 관리하는 홈랩 환경에서도 유용하다. 콘솔 KVM을 따로 두지 않고, 각 머신을 모니터의 서로 다른 입력에 연결한 뒤 스크립트로 순환시키면 저비용으로 비슷한 편의를 얻을 수 있다. 물론 이 경우 키보드·마우스 전환은 별도로 해결해야 한다는 점은 뒤에서 다시 짚는다.

4.3 회의·발표 환경과 개발 환경 분리

회의실 모니터를 노트북과 발표용 PC 사이에서 오가야 하는 상황, 혹은 개발 환경을 물리적으로 분리한 별도 머신과 평소 업무 머신을 오가는 구성에서도 같은 패턴이 적용된다. 스크립트로 묶어 두면 회의 시작 매크로에 입력 전환 명령을 포함시키는 것도 가능하다.

5. 유사 도구와 비교 - "소프트웨어 KVM"과 헷갈리지 말 것

이 분야를 찾아보면 이름이 비슷한 도구가 많아 혼동하기 쉽다. 정리해 보자.

5.1 리눅스: ddcutil

ddcutil은 훨씬 오래되고 성숙한 리눅스용 DDC/CI 도구다. ddcutil detect로 모니터를 찾고, ddcutil setvcp 60 0x0f처럼 VCP 코드와 16진수 값을 직접 지정한다. 기능은 강력하지만 코드 표를 직접 찾아야 하는 저수준 인터페이스다. monitor-input-rs는 같은 원리를 쓰되 이름 기반의 사람 친화적 문법을 얹었고, 무엇보다 리눅스 전용이 아니라 세 플랫폼에서 동일하게 쓸 수 있다는 점이 다르다.

5.2 윈도우: ControlMyMonitor·ddcswitch류

윈도우 진영에는 NirSoft의 ControlMyMonitor를 배치 스크립트로 감싸 쓰는 방식이나, DDC/CI 전용으로 만들어진 ddcswitch 같은 윈도우 전용 CLI가 있다. 기능적으로는 monitor-input-rs와 겹치지만 윈도우에만 묶여 있다는 한계가 있다. 맥과 윈도우를 함께 쓰는 사람에게는 플랫폼마다 다른 도구를 익혀야 한다는 부담이 생긴다.

5.3 맥OS: Lunar와 자동 트리거 도구

맥OS에는 Lunar처럼 밝기와 입력을 GUI로 제어하는 DDC/CI 도구가 있고, 여기에 기기 연결을 감지해 자동으로 전환 명령을 쏘는 보조 도구를 얹어 쓰는 사례도 보고된다. 이런 조합은 사람이 단축키를 누르지 않아도 케이블을 꽂는 순간 자동으로 전환된다는 장점이 있지만, monitor-input-rs 자체는 자동 감지 기능 없이 순수하게 명령이 오면 실행하는 도구다. 자동 트리거가 필요하다면 별도의 스크립트나 훅으로 감싸야 한다.

5.4 "소프트웨어 KVM"은 사실 다른 문제를 푼다

Synergy, Input Director, Barrier 같은 이른바 소프트웨어 KVM은 검색 결과에 자주 같이 등장하지만 실제로는 다른 계층의 문제를 푼다. 이들은 여러 컴퓨터가 각자 자기 모니터를 갖고 있는 상황에서, 마우스 커서를 화면 경계 너머로 이동시켜 키보드·마우스 입력만 넘기는 도구다. 모니터 자체는 한 대인데 여러 PC의 영상 케이블이 물려 있고 그중 하나만 화면에 표시해야 하는 상황이라면, 키보드·마우스를 공유해도 화면에 무엇이 보이는지는 바뀌지 않는다. 그 화면 자체를 바꾸는 것이 DDC/CI와 monitor-input-rs의 영역이다. 두 종류의 도구는 종종 함께 쓰인다. 소프트웨어 KVM으로 키보드·마우스를 넘기고, monitor-input-rs로 영상 입력을 같은 타이밍에 맞춰 전환하는 식이다.

6. 한계와 주의사항

6.1 모니터가 DDC/CI를 제대로 지원해야 한다

DDC/CI는 표준이지만 구현 품질은 제조사와 기종마다 편차가 크다. 저가형 모니터 일부는 아예 DDC/CI를 지원하지 않고, 지원하더라도 특정 포트에서만 동작하는 경우가 있다. 예컨대 일부 초광각·게이밍 모니터는 DisplayPort에서는 DDC 제어가 막혀 있고 HDMI에서만 동작한다는 사례가 보고돼 있다. 도구를 들이기 전에 보유한 모니터가 DDC/CI를 어느 포트에서 지원하는지 먼저 확인하는 것이 순서다.

6.2 USB-C 도킹스테이션·MST 허브의 함정

USB-C 도킹스테이션이나 MST(멀티스트림 트랜스포트) 허브를 거치면 영상 신호는 멀쩡히 나오는데 DDC 제어 채널만 누락되는 경우가 흔하다. 도킹스테이션 펌웨어가 DDC 패스스루를 제대로 구현하지 않은 것이 원인인 경우가 많고, 이때는 모니터를 PC에 직접 케이블로 물려 원인을 좁히는 것이 가장 빠른 진단법이다. 노트북 하나에 도킹스테이션까지 물린 구성이라면 이 지점에서 막히는 사례가 실제로 자주 보고된다.

6.3 절전 모드·신호 감지·리눅스 배포판 편차

입력을 전환한 뒤 해당 PC가 절전 모드로 들어가면, 모니터가 신호를 찾다가 엉뚱한 입력에 고정되거나 무신호 화면을 띄우는 경우가 있다. 완전 자동화를 노린다면 절전 상태 전환 타이밍까지 함께 고려해야 한다. 또한 GeekNews 댓글에서는 Ubuntu 24.04에서 장치가 인식되지 않는다는 호환성 문제도 보고됐다. 리눅스 배포판·커널 버전에 따라 i2c-dev 모듈 활성화 여부나 권한 설정이 달라 첫 실행에서 바로 되지 않을 수 있다는 점을 감안해야 한다.

결론 - 누구에게 필요한가

monitor-input-rs는 화려한 신기술이 아니라, 이미 대부분의 모니터 안에 잠들어 있던 DDC/CI라는 오래된 표준을 커맨드라인 시대의 습관에 맞게 다시 꺼내 쓴 도구에 가깝다. 하드웨어 KVM을 살 필요 없이, 이미 갖고 있는 모니터와 케이블만으로 문제를 해결한다는 점이 이 도구의 진짜 가치다.

한 모니터를 작업용과 게임용, 혹은 여러 홈랩 머신 사이에서 물리 버튼 없이 오가고 싶은 사람, 그리고 이미 셸 스크립트나 단축키 매니저로 워크플로를 자동화하는 습관이 있는 사람에게 특히 잘 맞는다. 반대로 모니터의 DDC/CI 지원 여부가 불확실하거나, 도킹스테이션을 여러 겹 거치는 복잡한 배선을 쓰고 있다면 먼저 monitor-input(인자 없이 실행)으로 모니터가 인식되는지부터 확인해 보는 것이 순서다. 키보드·마우스까지 함께 넘기고 싶다면 소프트웨어 KVM과 조합해 쓰는 구성을 권한다.
