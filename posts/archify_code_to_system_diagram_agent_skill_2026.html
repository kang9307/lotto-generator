이 글은 Archify 저장소의 README와 스킬 정의(SKILL.md), GeekNews 소개 글에 적힌 내용만 근거로 삼는다. README에 없는 동작은 추정하지 않으며, 실행 결과가 아니라 문서가 말하는 계약을 다룬다. 버전 표시는 3.0.1, 라이선스는 MIT다.

무엇을 입력받아 무엇을 내놓는가

Archify는 에이전트에게 설치하는 스킬이다. README의 첫 문장은 이해하고, 계획하고, 공유하고 싶은 것을 인터랙티브한 시각 자료로 바꾼다는 것이다. 시스템 구조도에만 한정하지 않아 여행 일정이나 학습 지도 같은 사례도 함께 소개하지만, GeekNews 소개 글과 이 글의 관심사는 코드와 설명에서 시스템 다이어그램을 만드는 쪽이다. 핵심은 사람이 그림 도구를 조작하는 것이 아니라 에이전트가 그림의 원본을 쓰고, 렌더러가 그것을 화면으로 바꾼다는 분업이다.

입력은 세 갈래로 정리된다. 첫째는 시스템을 말로 옮긴 설명이다. README의 예시는 브라우저가 API를 호출하고, API가 Redis를 확인하고, 캐시 미스가 나면 PostgreSQL을 조회해 캐시를 채운다는 한 문장이다. 둘째는 저장소다. 에이전트에게 저장소를 읽게 하고 근거가 있는 아키텍처 다이어그램을 요청할 수 있으며, 저장소는 필수가 아니라고 README가 명시한다. 셋째는 이미 나온 그림을 다듬는 후속 요청이다. Redis를 추가하라, 인증을 왼쪽으로 옮겨라, 롤백 경로를 강조하라 같은 요청이며 Archify가 타입이 있는 원본을 보관하므로 지정한 부분만 고친다고 적혀 있다.

산출물은 다음과 같이 나뉜다.

  • 단일 HTML 파일. 노드 상세와 경로 탐색이 파일 안에 들어 있어 받은 사람은 Archify를 설치하지 않고 브라우저로 연다. 외부 사이트나 지도 링크만 네트워크가 필요하다.
  • 타입이 있는 JSON 중간 표현. 렌더러가 붙는 모든 모드에 스키마가 있고, 같은 원본에서 같은 결과를 다시 만들 수 있다고 README는 설명한다.
  • 이미지와 영상 내보내기. PNG를 클립보드로 복사하거나 정적·동작 형식으로 내려받는다. GeekNews 소개 글은 PNG, SVG, WebM을 언급한다.
  • 공유 카드. 추적한 경로나 도달 범위를 1200×630 PNG로 내려받는다. 전체 다이어그램이 맥락으로 남는다.
  • 비교 화면. 변경 전후의 스냅숏을 비교하는 Architecture Delta가 별도 모드로 있다.

이 글의 관점은 두 가지 질문으로 압축된다. 에이전트가 코드를 읽어 그림을 만드는 과정에서 무엇이 자동으로 처리되는가, 그리고 그 결과를 받은 사람이 무엇을 직접 대조해야 하는가. 이미 다룬 인접 주제는 반복하지 않는다. 그림의 시각 규칙을 후처리로 입히는 접근은 Diagram Design 스킬 글에, 정적 분석과 LLM을 결합해 아키텍처를 뽑는 접근은 CodeBoarding 글에 있다. Archify는 이 둘과 달리 에이전트가 판단해서 쓴 JSON을 검증 관문에 통과시키는 구조이므로, 관문이 무엇을 보장하고 무엇을 보장하지 않는지가 읽을 지점이다.

설치와 호출 — README에 있는 명령만

설치는 npx로 하는 스킬 설치 명령 한 줄이 기본이다. 지원 대상으로 Cursor, Claude Code, Codex CLI, OpenCode가 적혀 있다. 아래 두 줄은 README가 그대로 싣는 명령이며, 첫째 줄이 기본 설치, 둘째 줄이 설치 없이 시험하는 방식이다.

npx skills add tt-a1i/archify -g
                    npx skills use tt-a1i/archify@archify --agent codex

Cursor에는 대화형 질문 없이 설치하는 명시적 형태가 따로 적혀 있다. 이 명령은 스킬 이름과 에이전트, 전역 설치, 복사 방식, 확인 생략을 옵션으로 모두 지정한다. 호출은 명령이 아니라 자연어다. 에이전트에게 Archify를 써서 다이어그램을 그려 달라고 요청하면 되고, README의 첫 예시가 그 문장이다. 이후에는 인증을 추가하라거나 캐시 미스 경로를 강조하라거나 밝은 테마로 바꾸라는 식으로 대화를 이어 간다.

설치 위치는 에이전트마다 다르다. README의 표를 요약하면 다음과 같다.

  • Claude Code. ~/.claude/skills/ 또는 프로젝트의 .claude/skills/. 렌더러와 검증 절차 전체가 동작한다.
  • Codex CLI와 opencode. 각자의 스킬 디렉터리에 놓이며 같은 전체 절차가 동작한다고 표에 적혀 있다.
  • Claude.ai. 설정의 스킬 항목에 archify.zip을 올린다. 동작 범위는 샌드박스에서 Node.js를 쓸 수 있는지에 달려 있다고 명시된다.
  • 프로젝트 지식(Project Knowledge). 같은 zip을 올리면 프롬프트 기반의 아키텍처 대체 경로가 된다. 렌더러와 검증 절차를 쓰는 경로와는 다르다.

이 목록에서 실무적으로 중요한 것은 마지막 두 항목이다. 렌더러와 검증기는 Node.js로 실행되므로, Node를 실행할 수 없는 환경에서는 Archify가 약속하는 검증 단계 자체가 빠진다. 설치했다는 사실과 검증 절차가 돈다는 사실은 별개이며, 이 차이가 뒤의 표에서 사람이 확인할 항목으로 다시 나온다. 커뮤니티가 붙인 Hermes Agent와 DeepSeek Harness 연동도 README에 있으나, 각각 공식 제품이 아니며 텔레메트리가 없다는 단서와 함께 옵트인으로 표시되어 있다.

다섯 가지 유형과 프롬프트에 넣을 것

Archify는 그림의 종류를 다섯 가지로 나눈다. 유형을 고르는 것은 스킬 절차의 첫 단계이며, 사용자가 프롬프트에 무엇을 적느냐가 결과의 정확도를 좌우하도록 README가 유형별로 넣을 정보를 안내한다.

유형어울리는 대상프롬프트에 넣을 것
Architecture컴포넌트, 서비스, 저장소, 경계범위, 핵심 컴포넌트, 주 경로
WorkflowCI/CD, 승인, 도구 호출, 런북참여자, 순서, 분기, 예외
SequenceAPI 호출, 캐시 폴백, 인증, 비동기 추적호출자, 피호출자, 반환, 시점
Data Flow파이프라인, 계보, 개인정보, 소비자원천, 변환, 저장소, 경계
Lifecycle상태, 재시도, 대기, 종료 결과상태, 이벤트, 재시도와 취소 경로

표에서 눈여겨볼 것은 오른쪽 열이다. 프롬프트에 넣을 것이라고 적힌 항목은 곧 그림에 들어갈 사실의 목록이다. 에이전트가 코드에서 알아내는 경우에도 사람이 미리 범위와 핵심 컴포넌트를 정해 주면 그림이 좁혀진다. README의 저장소 분석 예시는 이 원칙을 그대로 문장으로 옮긴 것이다.

Analyze this repository, then use archify to create a high-level runtime architecture diagram.
                    Show 8–12 core components, one primary path, external dependencies, and trust boundaries.
                    Put supporting detail in cards instead of adding more edges.

이 예시는 세 가지를 요구한다. 컴포넌트를 8개에서 12개로 제한하고, 주 경로를 하나만 두며, 보조 정보는 선을 늘리지 않고 카드에 담는다. 수를 제한하는 것은 그림을 읽기 좋게 만드는 목적이지만, 사람에게는 다른 뜻도 있다. 12개 안에 들어가지 못한 컴포넌트는 그림에서 빠진 것이고, 빠졌다는 사실은 그림에 표시되지 않는다. 범위를 정한 사람만 무엇이 빠졌는지 안다.

  • 범위 문장에 시스템의 이름과 경계를 적으면 스킬이 무엇을 포함할지 정하기 쉽다.
  • 주 경로를 하나로 못 박아 두면 나머지는 보조 정보로 밀려나 선이 얽히지 않는다.
  • 신뢰 경계와 외부 의존성은 요청하지 않으면 그림에 없을 수 있으므로 명시하는 편이 안전하다.

생성 흐름 — JSON 중간 표현과 검증 관문

Archify의 구조에서 가장 특징적인 부분은 그림 대신 JSON을 쓴다는 점이다. README의 설명과 스킬 정의를 합치면 흐름은 다음 순서다.

  1. 유형 판별. 요청이 아키텍처인지 워크플로인지 시퀀스인지 데이터 흐름인지 수명주기인지 정한다.
  2. 스키마와 예시 읽기. 해당 유형의 스키마와 예시를 나누어 읽는다.
  3. 후보 JSON 작성. 완성된 후보 JSON을 에이전트가 직접 쓴다. 스킬 정의는 노드, 관계, 출처, 뷰, 카드, 경계의 개수가 목표도 상한도 아니라고 적고, 사전 스케치나 산문으로 된 좌표 계획을 만들지 말라고 한다.
  4. 최종 처리(finalize). 검증과 전달을 한 번에 실행한다. 통과했다는 것은 검증, 전달, 엄격 검사, 실제 브라우저에서의 검사 관문이 통과했다는 뜻이라고 스킬 정의가 못 박는다.
  5. 실패 수리. 실패한 관문이 있으면 JSON을 고쳐 다시 실행한다. 수정 기회는 두 번으로 제한된다.

전달 단계는 원자적이다. 같은 디렉터리에 후보를 렌더링해 검사하고, 통과한 결과물만 기존 결과물을 원자적으로 교체한다. 그 결과 저장 도중 잘못된 파일이 마지막 정상본을 덮어쓰는 일이 없다. README는 검사 항목으로 스키마, 레이아웃, HTML/SVG, 경로, 라벨과 경로 사이의 간격을 든다. 저장소 명령으로는 다음과 같이 검증과 전달을 각각 실행할 수 있다.

cd archify
                    node bin/archify.mjs validate workflow examples/agent-tool-call.workflow.json --quality showcase --json
                    node bin/archify.mjs deliver workflow examples/agent-tool-call.workflow.json /tmp/workflow.html --quality showcase --open --json

실패했을 때의 형식도 정해져 있다. validate --json 과 deliver --json 은 JSON 객체 하나를 내놓고, 그 안에 안정적인 규칙 코드, 문제가 된 대상, 측정된 증거, 지원되는 수리 방법만 담긴다. 에이전트는 진단 항목마다 붙은 지원 수리만 적용하도록 되어 있고, 스킬 정의는 종료 코드가 0이 아닌데 성공을 주장하는 일과 실제 캡처 없이 눈으로 검토했다고 주장하는 일을 금지한다. 이것은 에이전트의 보고를 기계 출력에 묶어 두는 장치다.

  • 검증 실패는 스택 트레이스가 아니라 규칙 코드와 측정값으로 나온다. 재시도가 추측이 아니라 지정된 수리가 된다.
  • 선택 기능인 미리보기는 127.0.0.1의 임의 포트에서만 열리며, 최신 후보가 모든 관문을 통과할 때만 화면이 갱신된다.
  • 동작 효과는 요청했을 때만 켜지고 기본 출력은 정적이다.
  • 시각 검토는 자동 검사와 분리되어 있다고 README가 적는다.

코드에서 그린 그림의 근거 — SRC n과 고정된 커밋

저장소를 읽어 그리는 경우 가장 큰 질문은 그림의 각 상자가 코드의 어디에 해당하느냐다. README는 이를 근거 표시라는 선택 기능으로 다룬다. 요청했을 때만 켜지며, 켜지면 근거가 있는 아키텍처 노드가 스스로 SRC n 이라는 표식을 달고, 하나의 공개 커밋에 고정된 파일과 줄 범위를 열어 준다. 파일 위치는 Git으로 확인된 것이라고 README는 설명한다. 요청하지 않은 일반 결과물은 출처가 없는 상태로 남는다.

실제 사례로 README는 공개 저장소 mco-org/mco를 든다. 커밋 9f1a1cf 시점의 저장소를 추적해 런타임 아키텍처를 그렸고, 검사를 거친 지도라고 소개한다. 결과 HTML과 타입이 있는 JSON 원본이 저장소의 문서 디렉터리에 함께 공개되어 있어, 그림과 원본을 대조해 볼 수 있다. 이 사례에서 읽을 점은 결과물이 특정 커밋에 묶여 있다는 것이다. 코드가 바뀌면 그림은 그 커밋 시점의 사실이 되고, 저절로 갱신되지 않는다.

근거 표시가 무엇을 보장하는지는 정확히 구분해야 한다. SRC n 은 노드가 참조하는 파일과 줄 범위를 열어 준다. 그 범위가 노드의 설명을 뒷받침하는지, 관계가 실제 호출 경로인지는 사람이 열어 읽어야 알 수 있다. 근거의 존재와 근거의 적합성은 다른 층위이며, 자동화는 앞의 것을 돕고 뒤의 것은 사람에게 남긴다.

  • 표식이 붙은 노드는 그 노드가 가리키는 파일을 열어 설명과 맞는지 읽는다.
  • 표식이 없는 노드는 근거 없이 그려진 것으로 취급하고 출처를 묻는다.
  • 고정된 커밋과 현재 브랜치의 차이를 확인한다. 그림은 그 커밋의 스냅숏이다.
  • 8~12개로 줄인 그림에서 빠진 컴포넌트가 무엇인지 프롬프트를 쓴 사람이 기록한다.
  • 외부 의존성과 신뢰 경계는 프롬프트에 요구한 만큼만 그림에 존재한다.

자동화되는 것과 사람이 확인할 것

여기까지의 내용을 단계별로 모으면 다음 표가 된다. 왼쪽에서 두 번째 열은 README와 스킬 정의에 실제로 적힌 것이고, 세 번째와 네 번째 열은 그 문서를 근거로 사람이 해야 할 일과 남는 한계를 정리한 해석이다. 문서에 없는 항목은 —로 두었다.

단계README에 있는 것사람이 확인할 것한계

표의 요지는 자동화가 형식과 재현성에서 강하고 내용의 진실성에서는 사람에게 넘긴다는 것이다. 검증 관문은 그림이 깨지지 않았음을 증명하며, 그림이 맞음을 증명하지 않는다. 이것은 결함이 아니라 문서가 스스로 그은 선이다. 스킬 정의가 시각 검토와 자동 검사를 별개로 두고, README가 도달 범위 내보내기에 런타임 영향을 주장하지 않는다는 단서를 붙이는 이유가 여기에 있다.

  • 그림이 예쁘게 나왔다는 사실은 검증 통과와 관계가 있어도 코드와의 일치와는 관계가 없다.
  • 에이전트가 최종 응답에 적은 성공 보고보다 종료 코드와 진단 JSON이 우선한다.
  • 같은 저장소를 두 번 그려 노드 구성이 달라지는지 비교하면 판단이 흔들리는 지점이 드러난다. 이 글의 근거 자료에는 그런 재현 결과가 없으므로 시도해 볼 만한 절차로만 적는다.
  • 공유 전에 그림 제목 옆에 기준 커밋과 작성 날짜를 적어 두면 낡은 그림이 최신으로 읽히는 일을 줄인다.
  • 보안 경계나 개인정보 흐름을 다룬 그림은 담당자의 검토를 별도로 거친다.

그림이 말하지 않는 것 — 작성된 관계와 런타임 영향

Archify가 눈에 띄게 신경 쓰는 부분은 인터랙션이 무엇을 주장하는가다. README는 이를 정직한 인터랙션이라 부른다. 포커스, 상류와 하류의 도달 범위, 정확한 경로, 역할 비교, 스토리는 작성자가 쓴 노드와 관계만 재사용하며, 토폴로지를 지어내거나 런타임 영향을 주장하지 않는다. 노드를 선택해 하류 도달 범위를 켜면 그 노드 아래로 이어지는 선이 강조되는데, 그것은 JSON에 적힌 관계를 따라간 결과다. 장애가 실제로 어디까지 번지는지에 대한 예측이 아니다.

이 구분은 사람이 그림을 읽는 태도와 직결된다. 화면에서 하류가 넓게 강조된 노드를 보고 이것이 영향 범위라고 읽으면 그림이 말하지 않은 것을 읽은 것이다. 실제 호출이 조건부인지, 비동기인지, 사용되지 않는 경로인지는 그림에 없다. 배포 소유권 프로필도 같은 태도를 보인다. 작성된 소유자, 리전 배치, 비공개 데이터베이스 범위, 이름이 붙은 경계 교차 중 하나라도 없으면 실패하는 방식이며, 암묵적으로 켜지지 않고 실제 인프라를 조사하지도 않는다고 README가 적는다.

변경 비교도 같은 원칙이다. Architecture Delta는 검증된 Before, Delta, After 스냅숏을 기계 영수증과 함께 비교하고, 작성된 변경을 선택하거나 한정된 길이의 검토 재생을 볼 수 있다. 영향, 위험, 병합 안전성은 추론하지 않는다. 비교 명령은 README에 다음과 같이 적혀 있다.

node archify/bin/archify.mjs compare architecture base.json head.json architecture-delta.html --json

이 명령은 두 JSON을 입력으로 받는다. 두 JSON은 사람이나 에이전트가 각 시점의 구조를 기술한 것이므로, 비교의 정확도는 두 기술의 품질에 종속된다. 코드 리뷰에서 이 화면을 쓴다면 변경된 사실을 빠르게 훑는 용도로 쓰고, 승인 판단의 근거로 삼지 않는 편이 문서의 선과 맞는다.

  • 도달 범위는 작성된 관계를 따라간 결과이며 런타임 영향의 예측이 아니다.
  • 경로 추적은 그림에 그려진 경로를 보여 줄 뿐 실제 트래픽이 그 경로로 흐른다는 증거가 아니다.
  • 배포 소유권 프로필은 작성된 정보의 누락을 막을 뿐 실제 인프라와의 일치를 조사하지 않는다.
  • Delta 화면은 변경된 사실을 나열하며 위험을 평가하지 않는다.

범위 밖으로 둔 것과 운영상의 성질

README는 무엇을 하지 않는지도 분명히 적는다. Mermaid 자동 파싱, 범용 자동 배치, 호스팅 공유, WYSIWYG 편집은 의도적으로 현재 범위 밖이다. 범용 그림 편집기나 Mermaid 테마가 아니며 기술적 의도를 커뮤니케이션 산출물로 바꾸는 도구라고 스스로 정의한다. 배치도 자동 배치 알고리즘이 아니라 에이전트가 계층, 간격, 경로, 강조를 판단해 정하고, 공유되는 자동 종점만 결정적으로 분산시켜 화살표가 한 점에 몰리지 않게 한다는 설명이다. 이미 Mermaid나 draw.io 자산을 가진 팀이라면 그것을 직접 읽어 들이는 기능이 없다는 뜻이므로, 기존 자산을 다시 설명하는 작업이 필요하다.

운영상의 성질도 몇 가지 적혀 있다.

  • 업데이트 확인. 고정된 안정판 매니페스트를 GET 하여 선택적 알림을 보여 줄 뿐 내려받거나 설치하지 않는다. 성공한 확인은 약 24시간, 실패는 6시간 후 재시도하고 이어서 24시간 간격이다. 서버는 IP와 시각 같은 일반 HTTP 메타데이터를 보지만 버전, 에이전트, 프로젝트 데이터, 프롬프트, 계정과 기기 식별자는 받지 않는다고 적혀 있다. ARCHIFY_UPDATE_CHECK_DISABLED=1 로 네트워크와 알림 상태 쓰기를 끈다.
  • 언어. meta.locale 은 페이지 제목, 범례, 상태와 오류, 접근성 문구, HTML/SVG의 lang 속성을 현지화하지만 작성된 내용은 번역하지 않는다. 영어와 중국어 간체(zh-CN)가 내장이고, 그 밖의 언어는 번역 테이블을 주지 않으면 영어로 대체되며 대체 사실이 표시된다. 한국어 사용자는 그림의 제목과 범례가 영어로 나올 수 있음을 감안해야 한다.
  • 접근성. 독자가 조작하는 동작 효과는 유한하며 시스템의 동작 줄이기 설정을 따르고, 기본 내보내기에는 들어가지 않는다.
  • 뷰어 조작. 물음표 키가 도움말, 슬래시가 노드 검색, R이 경로, L이 역할 비교, M이 개요, F가 발표 모드다. 링크 해시로 초점, 관계, 경로, 렌즈 상태를 복원할 수 있다.
  • 유지 상태. 저장소의 버전 표시는 3.0.1이고 라이선스는 MIT이며, 커뮤니티 연동은 공식 제품이 아님이 명시되어 있다. GeekNews 댓글에는 개발 중에 시각화를 요청하면 이 스킬로 그려 준다는 사용 후기가 있으나, 개인의 사용 경험이므로 성능의 근거로 삼을 수는 없다.

정리하면 Archify를 도입하는 팀이 정할 것은 세 가지다. 그림을 누가 검토하는가, 그림에 기준 커밋과 날짜를 어떻게 붙이는가, 업데이트 확인 같은 네트워크 동작을 허용하는가. 도구는 형식을 검증하고 사람은 내용을 검증하는 분업이 문서에서 읽히는 설계다.

확인하지 못한 것

  • 실제 저장소에 스킬을 실행한 결과. 이 글은 README와 스킬 정의, 소개 글의 기술만 다루며, 생성된 그림의 정확도를 측정한 자료는 없다.
  • 스킬 정의 전문 가운데 저장소 저작 절차(Repository authoring)의 세부. 요약된 규칙만 근거로 삼았다.
  • Node.js의 최소 요구 버전. README에는 커뮤니티 연동 항목에만 버전 조건이 있고 기본 스킬의 조건은 확인되지 않는다.
  • Claude.ai 샌드박스에서 검증 절차가 실제로 도는 범위. README는 Node.js 접근에 따른다고만 적는다.
  • GitHub 트렌딩 순위와 언론 소개에 관한 README의 서술. 작성자의 게시물을 근거로 한 내용이라 이 글에서 사실로 인용하지 않았다.
  • GeekNews 등재 날짜의 정확한 값. 페이지에는 상대 시각만 표시된다.
