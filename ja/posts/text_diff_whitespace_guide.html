レビュー依頼が一件上がってくる。変更ファイル三つ、51行追加に51行削除。開いてみるとインデントがタブからスペースに変わっていて、行末の空白が整理されていて、その間のどこかにオプションが一つ追加されている。レビュアーがやるべきなのはその一箇所を見つけることなのに、画面には残りの100行がまったく同じ赤と緑で並んでいる。

この状況で人がやることはたいてい二つに一つだ。スクロールしながら目で追って見落とすか、あるいはそのまま承認を押すか。どちらもレビューではない。そしてこれはレビュアーの真面目さの問題ではなく、信号対雑音比が1対50の画面を人間に渡した側の問題だ。

以下の命令と出力はすべて §2 に記した環境で、空のリポジトリを新しく作って直接実行した結果だ。貼った出力は実際に出たもので、実行できなかった項目は §20 に別途まとめた。例に出てくるパスはすべて任意の名前である。

一行が100行に埋もれる構造

空白のノイズはたいてい人が意図して作るものではない。保存のたびに自動で走るフォーマッタ、メンバーごとに違うエディタのタブ幅設定、保存時に行末の空白を落とす設定を有効にしている人としていない人。この三つがあるだけで、ファイルを開いて閉じるだけで全体が変更対象になる。

問題はその先だ。diff は行単位で比較するので、行の中の目に見えないバイトが一つ変わっただけでもその行は削除と追加の対として表示される。40行の関数のインデントを変えれば削除40行に追加40行、つまり80行が画面を埋める。その中に本当の修正が一行入っていても、視覚的には他の79行と区別がつかない。

ここでよく出てくる対応が二つあるが、どちらも部分的にしか正しくない。一つはフォーマッタを使うのをやめようというもので、これはフォーマッタが消してくれていた別種のレビューの無駄を復活させる。もう一つはレビュアーがもっと丁寧に見ようというもので、これは道具で解決する問題を人の集中力で返済しろという要求なので長続きしない。実際に使えるのは三つ目だ。画面に載せる前に空白の差を計算から外すこと。

実行環境と実験の方法

以下の出力はすべて次の環境から出たものだ。オプションの挙動は git のバージョンによって細部が変わりうるので、バージョンも併記しておく。

$ git --version
git version 2.48.1.windows.1

$ diff --version | head -1
diff (GNU diffutils) 3.10

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -s -r -o
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64 Msys

# 実験はすべて空の使い捨てリポジトリで行う
$ mkdir /tmp/demo && cd /tmp/demo
$ git init -q .
$ git config user.name  Demo
$ git config user.email demo@example.com
$ git config core.autocrlf false   # 改行変換が実験を汚さないように

最後の行が重要だ。Windows で core.autocrlf が有効だと、git がリポジトリに入れる際と取り出す際に改行を書き換えるので、改行にまつわる実験結果が設定によって変わってしまう。実験用リポジトリではこの値を切ってから始める。

空白の変更には五つの種類がある

空白の変更を一つにまとめて扱うとオプションを選べない。git の無視オプションはそれぞれ違うものを無視するからだ。実務で出くわす種類は五つあり、生まれてくる経路もそれぞれ違う。

種類どう発生するか目に見えるかdiff への影響
行末の空白編集中に残ったスペースやタブ。保存時整理を有効にした人がファイルを開くと一気に消える見えないその行全体が変更として表示される
インデントの変換タブとスペースの相互変換。フォーマッタやエディタ設定の差ほぼ見えないインデントされた行すべてが変更として表示される
行内の空白の量桁を揃えようと等号の周りなどの空白を増減させる見えるその行が変更として表示される
空行の増減フォーマッタの空行規則。人が段落を分ける癖見える追加削除行が生じ hunk の範囲が広がる
ファイル末尾の改行最終行を改行なしで保存する道具見えない最終行が削除と追加として表示される

六つ目として改行コードそのものがある。CRLF と LF は性格が少し違うので §13 で別に見る。目に見えないバイトがファイルを汚すもう一つの例としてはファイル先頭に付く BOM の3バイトがあるが、こちらは diff より実行そのものを壊す。

一つのファイルに五種類すべてを入れてみる

オプションを説明する前に比較対象を一つ作る。六行の設定ファイルに上の五種類をすべて入れ、その中に本当の変更を一つだけ混ぜておく。本当の変更は timeout の値が30から60になったものだけだ。残りはすべて空白である。

$ cat -A app.conf          # コミット済みの原本。^I がタブ、$ が行末
server {$
^Ilisten 8080;$
^Iretries = 3;$
^Itimeout = 30;$
log_level = info;$
}$

$ cat -A app.conf          # 編集したあと
server {   $               <- 行末の空白3つ
    listen 8080;$          <- タブがスペース4つに
^Iretries  =  3;$          <- 行内の空白の量が変化
^Itimeout = 60;$           <- 本当の変更 (30 -> 60)
$                          <- 空行を追加
    log_level = info;$     <- なかったインデントが付いた
}                          <- ファイル末尾の改行を削除 ($ がない)

この状態でオプションなしの git diff を回すとこうなる。六行のファイルが六行削除、七行追加になる。変わったのは実質数字一つなのにファイル全体が割れる。

$ git diff
diff --git a/app.conf b/app.conf
index bd81bfd..d0ea0b8 100644
--- a/app.conf
+++ b/app.conf
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
-}
+server {
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
+}
\ No newline at end of file

ここでレビュアーが timeout の行を見つけるには十二行を目で突き合わせることになる。六行のファイルだからできる話で、400行のファイルなら不可能だ。

無視オプションを一つずつ掛ける

同じファイルにオプションを一つずつ掛けていく。三つを順に見ると、各オプションが正確にどこまで飲み込むかが見えてくる。

$ git diff --ignore-space-at-eol      # 行末の空白だけ無視
@@ -1,6 +1,7 @@
 server {                             <- 文脈行に下がった
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
 }
\ No newline at end of file

$ git diff -b                         # --ignore-space-change
@@ -1,6 +1,7 @@
 server {
     listen 8080;                     <- タブ -> スペースも飲み込んだ
 	retries  =  3;                   <- 行内の空白の量も飲み込んだ
-	timeout = 30;
-log_level = info;
+	timeout = 60;
+
+    log_level = info;                <- なかったインデントは残る
 }
\ No newline at end of file

$ git diff -w                         # --ignore-all-space
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;                    <- 残ったのは本当の変更と
+
     log_level = info;                <- 追加された空行だけ
 }
\ No newline at end of file

三つの出力を並べると、-b と -w の違いがちょうど一行で分かれるのが見える。log_level = info; は元々インデントがなかった行なのにスペース四つが付いた。-b は空白が一つ以上ある区間どうしを同じとみなすので、0個と4個は同じではない。 -w は空白をそもそも無いものとして扱うのでこれも飲み込む。

  • --ignore-space-at-eol は行末だけを見る。インデントの変換はそのまま残るのでフォーマッタのノイズには力が弱い
  • -b は行末の空白まで含めて無視する。つまり --ignore-space-at-eol の上位集合だ
  • -w は -b の上位集合である。三つは包含関係で整理できる
  • どのオプションも空行の追加は消せない。 空行は別オプションの担当で、しかもそれには条件が付く
  • もう一つ注目したい点。--ignore-space-at-eol を掛けたら最後の } の行が文脈行に下がった。ファイル末尾の改行の有無も行末の空白として扱われるということだ

四つのオプションの違いを表に

上の実行結果をそのまま表に移すとこうなる。縦軸は §3 の五種類で、印はそのオプションがその変更を diff から消してくれるかである。

変更の種類オプションなし--ignore-space-at-eol-b
(--ignore-space-change)		-w
(--ignore-all-space)		--ignore-blank-lines
行末の空白見える消える消える消える見える
タブとスペースのインデント見える見える消える消える見える
行内の空白の量見える見える消える消える見える
なかったインデントが付く見える見える見える消える見える
ファイル末尾の改行を削除見える消える消える消える見える
空行の増減 (単独の hunk)見える見える見える見える消える
空行の増減 (他の変更と同じ hunk)見える見える見える見える見える

表で太字にした二つのセルが実務で人を惑わせる場所だ。一つは -b が新しくできたインデントを消せないこと、もう一つは --ignore-blank-lines が条件付きでしか動かないことである。二つ目を別に見る。

--ignore-blank-lines は hunk 単位で判断する

§5 の最後の出力で -w を掛けたのに追加された空行が残っていた。ならば --ignore-blank-lines も一緒に掛ければよいと思いがちだが、実際に掛けるとそうはならない。

$ git diff --ignore-blank-lines       # §4 のあのファイルに単独で
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
...                                   # 何も減っていない

$ git diff -w --ignore-blank-lines    # -w と一緒に掛けても
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;
+                                     <- 空行がそのまま残っている
     log_level = info;
 }

# ところが空行だけが変わったファイルでは完全に動く
$ git diff blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta

$ git diff --ignore-blank-lines blanks.txt
                                      # 出力なし。すべて抑制された

$ git diff -w blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta                                # -w は空行を消せない

挙動の規則はこうだ。--ignore-blank-lines は行単位ではなく hunk 単位で判断する。ある hunk の変更がすべて空行なら hunk を丸ごと捨て、一つでも中身のある変更が混じっていれば hunk 全体をそのまま出す。だから空行の整理だけをしたコミットでは完璧に動き、空行とロジックが同じ場所で変わったコミットでは何の効果もない。

  • フォーマッタが空行規則だけに手を入れたコミットをレビューするとき --ignore-blank-lines は最も強力だ。それ以外では期待値を下げるべきだ
  • -w と --ignore-blank-lines は担当領域が重ならないので、二つを一緒に掛けるのを既定と考えてよい
  • この hunk 単位の規則は GNU diff の -B も同じだ。§16 で同じ現象を確認する

この変更が大半フォーマットかを数字で判定する

レビューを始める前に知りたいのはたいてい一つだ。この変更の中に本当の変更が何行あるのか。 これは目で数える必要がなく二行で出る。統計オプションが -w をそのまま尊重するからだ。

# ファイル3つ: a.js は純粋な再フォーマット、b.js は再フォーマット + 本当の変更1行、c.js は本当の変更のみ
$ git diff --shortstat
 3 files changed, 51 insertions(+), 51 deletions(-)

$ git diff -w --shortstat
 2 files changed, 2 insertions(+), 2 deletions(-)

# ファイル別に見たいなら
$ git diff --numstat
30	30	a.js
20	20	b.js
1	1	c.js

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # a.js が一覧から消えた

$ git diff -w --stat
 b.js | 2 +-
 c.js | 2 +-
 2 files changed, 2 insertions(+), 2 deletions(-)

51行対2行。この比率一つ見ればその変更をどう扱うべきかが決まる。ところがここに落とし穴が一つある。--name-only は -w を無視する。 ファイル一覧だけ取り出して自動化に使おうとした人が引っかかる場所だ。

$ git diff -w --name-only
a.js
b.js
c.js                                  # a.js は空白だけなのに出てくる

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # こちらは正確だ

# ファイル別に確実に分類するには終了コードを使う
$ git diff --quiet -w -- a.js; echo $?
0                                     # 0 = 空白以外は変わっていない
$ git diff --quiet    -- a.js; echo $?
1                                     # 1 = バイトは変わった
$ git diff --quiet -w -- c.js; echo $?
1                                     # 本当の変更がある

$ for f in $(git diff --name-only); do
>   if git diff --quiet -w -- "$f"; then echo "  空白のみ : $f"; else echo "  本当     : $f"; fi
> done
  空白のみ : a.js
  本当     : b.js
  本当     : c.js

--quiet と -w を組み合わせた最後の形が実務では最も使える。終了コードで答えが出るのでフックや CI の中で空白だけ変わったファイルを自動で外せる。ファイル一覧が必要なら git diff -w --numstat の三列目を使えばよい。

git blame -w - フォーマッタが履歴を飲み込むとき

空白の変更が残す二つ目の被害は diff ではなく blame だ。ある行がなぜこうなったのかを追おうと blame を回したのに、すべての行が半年前のフォーマッタのコミットを指していたら、その履歴は事実上消えたのと同じである。

確かめるためにコミット三つのリポジトリを作る。Alice がロジックを書き、Bob がフォーマッタを回し、Carol が本当のバグを直す。Bob のコミットはタブをスペース四つに変え、シングルクォートをダブルクォートに変えただけだ。動作は一つも変わっていない。

$ git log --oneline
db3b770 fix: include zero total          <- Carol
007e2a5 style: run formatter over the repo   <- Bob
5c720df feat: aggregate rows             <- Alice

$ git blame --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
007e2a59 (Bob   2026-02-02 2)     total = 0
007e2a59 (Bob   2026-02-02 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# 七行のうち五行が Bob のものになった。Bob はロジックを一文字も触っていない。

$ git blame -w --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# 三行は Alice に戻ったが、引用符が変わった三行は依然として Bob だ。

-w の限界がここで正確に出る。-w は空白だけを無視する。 インデントだけ変わった行は生き返らせたが、同じコミットの中で引用符の文字が変わった行は空白の変更ではないのでそのまま Bob に残る。ところが現実のフォーマッタはほぼ必ず空白と空白でないものを一緒に変える。引用符の流儀、行の折り返し位置、末尾のカンマ、括弧の整列がすべてそうだ。

つまり -w ではフォーマッタのコミットを消せない。 半分だけ消えた blame はある意味もっと悪い。一部の行が生き返ったので全部済んだと錯覚させるからだ。まともな答えは別のところにある。

.git-blame-ignore-revs - コミットを blame から外す

git は特定のコミットを blame の計算から丸ごと飛ばす機能を持っている。飛ばしたコミットが作った行は、その前のコミットの側に責任が移る。慣例としてリポジトリのルートに .git-blame-ignore-revs というファイルを置き、そこに飛ばすコミットの SHA を書く。

$ cat .git-blame-ignore-revs
# 2026-02-02 リポジトリ全体のフォーマッタ実行 (タブ -> スペース4つ、引用符の流儀)
# 動作変更なし。blame では飛ばす
007e2a5974bd7a4c76aba4ee206b690c1410c23d

# 方法1. 一度だけ使う - ファイルのパスを直接渡す
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
^5c720df (Alice 2026-01-10 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
^5c720df (Alice 2026-01-10 6)         return {"total": total}
^5c720df (Alice 2026-01-10 7)     return {"total": 0}

# 方法2. ずっと使う - 設定に書いておく
$ git config blame.ignoreRevsFile .git-blame-ignore-revs
$ git blame --date=short report.py
                                      # 上とまったく同じ出力

# 方法3. ファイルなしでコミット一つだけ
$ git blame --ignore-rev 007e2a5974bd7a4c76aba4ee206b690c1410c23d --date=short report.py
                                      # やはり同じ出力

-w では三行が Bob に残ったのに、今度は七行すべてが元の場所を取り戻した。 Alice が六行、Carol が実際に直した一行。これがこのファイルの本当の履歴だ。

比較項目git blame -w.git-blame-ignore-revs
無視する対象空白の差指定したコミット全体
引用符や折り返し位置の変更消せない消せる
設定なしですぐ使えるか使える--ignore-rev で使える
チーム全体への共有各自がオプションを付ける必要があるファイルがリポジトリに一緒にコミットされる
対象コミットを人が選ぶ必要があるかいいえはい。SHA を自分で書く
間違えたとき影響なし本当の変更を含むコミットを入れると履歴が歪む

ファイルがリポジトリに一緒にコミットされる点が実務では最も大きい。一人が SHA を追加すればチーム全体の blame が一緒に直る。 GitHub は2022年3月24日の変更ログで、リポジトリのルートにある .git-blame-ignore-revs を blame 画面で認識すると述べた。つまりこのファイル一つでローカルの CLI とウェブ画面が一緒に整う。

ignore-revs を使うときに引っかかること

機能そのものは単純だが、初めて使うときに引っかかる点がいくつかある。すべて実際に再現して確認したものだ。

# 1. SHA は必ず40文字すべてでなければならない
$ git rev-parse --short HEAD~1
007e2a5
$ echo 007e2a5 > short-revs
$ git blame --ignore-revs-file=short-revs report.py
fatal: invalid object name: 007e2a5
                                      # 短縮ハッシュは blame 自体を失敗させる

# 2. 飛ばした行に印を残せる
$ git config blame.markIgnoredLines   true
$ git config blame.markUnblamableLines true
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df  (Alice 2026-01-10 1) def load(rows):
^?5c720d  (Alice 2026-01-10 2)     total = 0
^?5c720d  (Alice 2026-01-10 3)     for r in rows:
^?5c720d  (Alice 2026-01-10 4)         total += r["amount"]
db3b770e  (Carol 2026-03-05 5)     if total >= 0:
^?5c720d  (Alice 2026-01-10 6)         return {"total": total}
^?5c720d  (Alice 2026-01-10 7)     return {"total": 0}
                                      # 疑問符の付いた行 = 無視したコミットを跨いで推定された行

# 3. どのコミットを入れるかを判断する方法
$ git show --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 12 ++++++------
 1 file changed, 6 insertions(+), 6 deletions(-)

$ git show -w --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 6 +++---
 1 file changed, 3 insertions(+), 3 deletions(-)
                                      # -w で半分消えるなら空白の比重が大きいコミットだ

一つ目が最もよく引っかかる。コミットの SHA を貼るとき癖で短縮ハッシュを使うと blame がそもそも回らない。git rev-parse HEAD で完全な SHA を取り出して入れるのが安全だ。

  • コメントは # で始まる行に書く。そのコミットがなぜ一覧にあるのかを書いておかないと、数か月後には誰も手を出せなくなる
  • 入れる前にそのコミットが本当にフォーマットだけかを確認する。上の3番の git show -w --stat がその判定に使える。-w を掛けても行数が変わらないなら、そのコミットには本当の変更が入っている
  • 本当の変更が混じったコミットを一覧に入れるとその変更の責任者が永遠に隠れる。 これは blame の汚染より悪い
  • blame.markIgnoredLines を有効にしておくとどの行が推定値かが目に見える。チームにこのファイルを初めて導入するときに有効にしておくと説明が楽になる
  • このファイルは blame だけを変える。git log や git diff は影響を受けないので履歴が消えるわけではない

ファイル末尾の改行と No newline at end of file

§4 の出力の最後の行に \ No newline at end of file があった。この印はファイルの最後のバイトが改行ではないという意味だ。エラーではなく事実の記述である。

この印が存在する理由はテキストファイルの定義にある。POSIX は行を改行文字で終わる0個以上の文字列と定義し、テキストファイルをそうした行の並びと定義する。この定義に従えば、改行なしで終わった末尾の断片は厳密には行ではない。だから wc -l が一行少なく数えたり、ファイル二つを連結したときに最終行と先頭行が一行にくっついてしまうことが起きる。

$ git show HEAD:eof.txt | tail -c 12 | xxd
00000000: 650a 7477 6f0a 7468 7265 650a            e.two.three.
$ tail -c 12 eof.txt | xxd
00000000: 6e65 0a74 776f 0a74 6872 6565            ne.two.three
                                      # 末尾の 0a が一つ消えた。それだけだ

$ git diff
@@ -1,3 +1,3 @@
 one
 two
-three
+three
\ No newline at end of file
                                      # 同じに見える行が削除と追加として表示される

$ git diff --ignore-space-at-eol; echo "終了コード $?"
終了コード 0                           # 完全に隠される
$ git diff -w
                                      # -w も同じく出力なし
$ git diff --check; echo "終了コード $?"
終了コード 0                           # --check はこれをエラーと見なさない

最後の二行が重要だ。git diff --check は行末の空白は拾うがファイル末尾の改行の欠落は拾わない。 だからコミットフックに --check だけを掛けておいてこれも防げると考えてはいけない。こちらはエディタの設定で防ぐのが正しい。

改行コードが diff 全体をひっくり返す

改行コードが CRLF と LF の間で変わるとファイルのすべての行が変更になる。目に見えないバイトが行ごとに一つ付いたり抜けたりするからだ。CRLF と LF がそもそもなぜ分かれ、.gitattributes でどう固定するかは改行コードを扱った記事で別に整理した。ここではそれが diff をどう汚すかだけを見る。

$ cat -A notes.txt                    # ファイル全体を CRLF に変え、単語一つを修正
line one^M$
line two^M$
line THREE^M$                         <- 本当の変更はここ一つ
line four^M$

$ git diff --stat
 notes.txt | 8 ++++----
 1 file changed, 4 insertions(+), 4 deletions(-)
                                      # 四行のファイルが丸ごと変わったと出る

$ git diff
@@ -1,4 +1,4 @@
-line one
-line two
-line three
-line four
+line one
+line two
+line THREE
+line four
                                      # どの行が本当なのか画面上で区別できない

$ git diff --ignore-cr-at-eol
@@ -1,4 +1,4 @@
 line one
 line two
-line three
+line THREE
 line four                            # 一行に減る

$ git diff -w
                                      # -w も同じ結果。CR も空白文字だからだ
  • git にはこの場合のためだけの --ignore-cr-at-eol が別にある。-w より範囲が狭く安全だ
  • GNU diff 側には同じ目的の --strip-trailing-cr がある。§16 で確認する
  • 根本的な対策は .gitattributes でリポジトリの改行を固定することだ。オプションは症状の緩和であって解決ではない

そもそも発生させない

ここまでは既に生じたノイズを画面から消す方法だった。より良いのはノイズがコミットに入らないようにすることだ。層が三つあり、それぞれ止める地点が違う。

一つ目の層はエディタだ。リポジトリのルートに .editorconfig を置けば、対応するエディタが保存の時点で整理してくれる。エディタごとに対応範囲が違うのでこれは規約であって強制ではない。

$ cat .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = 4
trim_trailing_whitespace = true       # 行末の空白を除去
insert_final_newline = true           # ファイル末尾の改行を保証

[Makefile]
indent_style = tab                    # ここではタブが文法だ

[*.md]
trim_trailing_whitespace = false      # 行末スペース二つが改行を意味する

二つ目の層はコミット直前の検査だ。git diff --check は設定なしで動き、問題を見つけると終了コード2で終わるのでフックや CI にそのまま組み込める。

$ cat -A ws.txt
ok line$
trailing spaces here   $
trailing tab here^I$
 ^Ispace before tab$
$
$

$ git diff --check
ws.txt:2: trailing whitespace.
+trailing spaces here
ws.txt:3: trailing whitespace.
+trailing tab here
ws.txt:4: space before tab in indent.
+ 	space before tab
ws.txt:5: new blank line at EOF.
$ echo $?
2                                     # フックでそのまま使える終了コード

$ git config --get core.whitespace
                                      # 空 = 組み込みの既定値が適用される
                                      # blank-at-eol, space-before-tab, blank-at-eof

三つ目の層は適用時点での修正だ。他人が送ってきたパッチに行末の空白が入っているとき、git apply --whitespace=fix は適用しながらそれを取り除く。

$ tail -3 patch.diff | cat -A
 ok line$
 clean tail$
+new line with trailing ws   $        <- パッチに行末の空白が入っている

$ git apply --whitespace=fix patch.diff
patch.diff:8: trailing whitespace.
new line with trailing ws
warning: 1 line applied after fixing whitespace errors.

$ cat -A ws.txt
ok line$
clean tail$
new line with trailing ws$            <- 空白が除去された状態で適用された
手段止める時点行末の空白末尾の改行スペースの後のタブ強制力
.editorconfig保存時除去保証間接的エディタの対応が必要
git diff --checkコミット前検出検出しない検出終了コード2でフックが遮断
git apply --whitespace=fixパッチ適用時除去扱わない修正適用する側が選ぶ
.gitattributesコミットとチェックアウト時扱わない扱わない扱わない改行コードに限り強制

フォーマット用コミットを分ける習慣

ここまでのオプションをすべて知っていたとしても、最も効果が大きいのは道具ではなくコミットを分ける習慣だ。理由は単純である。オプションはレビュアーが毎回覚えて付ける必要があるが、分けておいたコミットは何も覚えなくてよい。

規則は一文だ。フォーマッタを回した結果はそれだけを入れたコミットにする。ロジックの修正と同じコミットに入れない。こうすると三つが同時に解決する。レビュアーはフォーマット用コミットを開かずに飛ばせるし、blame はその SHA 一つを .git-blame-ignore-revs に入れればよく、問題が起きたときに戻す範囲が明確になる。

# フォーマッタを既に回してロジック修正と混ざってしまったときの立て直し手順
$ git stash                           # 今の作業を一旦よけておく
$ prettier --write .                  # フォーマッタをリポジトリ全体に実行
$ git commit -am "style: run formatter (no behaviour change)"
$ git rev-parse HEAD >> .git-blame-ignore-revs
$ git stash pop                       # ロジック修正を取り出し直す
$ git commit -am "fix: 実際の修正内容"

# コミットする前にこのコミットが本当にフォーマットだけかを確認する一行
$ git diff --cached --quiet -w && echo "空白のみ" || echo "本当の変更がある"
  • フォーマッタの導入は一度にリポジトリ全体を回すほうがよい。ファイルごとに少しずつ回すやり方はフォーマット用コミットが数十個に増えて無視一覧の管理が不可能になる
  • フォーマット用コミットのメッセージには動作の変更がないことを明記する。数か月後にそのコミットを判断する人にとって、その一文がすべてだ
  • コミットを分けるのはレビュアーへの気遣いではなく履歴を読める状態で残す仕事だ。レビューは数日で終わり、履歴は数年続く

git がない場所 - GNU diff

配備サーバで設定ファイル二組を比較する場面のように、git リポジトリでない場所も多い。GNU diff にも同じオプションがあり名前もほぼ同じだ。ただし -B の hunk 単位の挙動まで git と同じなので、その点も確認しておく。

$ diff -u old.txt new.txt              # オプションなし
@@ -1,6 +1,7 @@
-alpha
-	beta = 1
-epsilon
+alpha
+    beta  =  1
+    epsilon
+

 gamma
-delta
+delta!

$ diff -u -b old.txt new.txt           # 空白の量の変化だけ無視
@@ -1,6 +1,7 @@
 alpha
 	beta = 1
-epsilon
+    epsilon                           <- なかったインデントは残る
+

 gamma
-delta
+delta!

$ diff -u -w old.txt new.txt           # 空白をすべて無視
@@ -2,5 +2,6 @@
 	beta = 1
 epsilon                               <- 今度は消えた

+
 gamma
-delta
+delta!

$ diff -u -B old.txt new.txt           # 空行だけ無視
@@ -1,6 +1,7 @@
-alpha
-	beta = 1
...                                   # 効果なし。git と同じ hunk 単位の規則

$ diff -q -w -B old.txt new.txt; echo $?
Files old.txt and new.txt differ
1                                     # 0 = 同じ、1 = 異なる、2 = エラー
  • -u は統合形式の出力だ。文脈三行が一緒に出るので人が読みやすく、patch で適用することもできる
  • -b と -w の違いは git とまったく同じだ。なかったインデントが付いた epsilon の行で分かれる
  • -B も git の --ignore-blank-lines と同じく hunk 単位なので、他の変更と混じると効果がない
  • CRLF が混じっているなら --strip-trailing-cr も一緒に渡す。これがないとすべての行が違うと出る
  • 終了コードで判定するときは -q を使う。出力が一行に減りスクリプトで扱いやすい

空白が意味を持つ場所

この記事の内容をすべて適用したあと最後に残る危険が一つある。-w を習慣にすると空白が文法であるファイルで本当の変更を見落とす。 これは仮定ではなく再現する事実だ。

$ git diff                            # Python ファイルで一行をループの外に出した
@@ -2,7 +2,7 @@ def total(rows):
     s = 0
     for r in rows:
         s += r
-        print(s)
+    print(s)
     return s

$ git diff -w
                                      # 出力なし。-w は何も変わっていないと言う

$ git diff -w --stat
                                      # ここも空だ

# ところが実際の動作はこう変わる
$ python total.py                     # 修正前
1
3
6
$ python total.py                     # 修正後
6

出力が三行から一行に変わった。プログラムの動作が明らかに変わっているのに git diff -w は変わったものはないと報告する。 Python においてインデントは書式ではなくブロック構造そのものだからだ。

対象空白が持つ意味-w を掛けると推奨
Pythonインデントの深さがブロック構造ブロックの移動を丸ごと隠す-w 禁止。必要なら --ignore-space-at-eol
Makefileレシピ行の先頭は必ずタブタブがスペースに変わったのを隠す-w 禁止
YAMLインデントが入れ子構造キーが別の親に移ったのを隠す-w 禁止
Markdown行末スペース2つ = 改行改行の消失を隠す--ignore-space-at-eol も危ない
Go・Java・C 系空白は区切りにすぎない安全-w を既定にしてよい
文字列リテラル・テスト用データ空白がデータの一部期待値の変更を隠すファイル単位で例外扱い

実務の基準はこう置けば無難だ。-w はレビューを始めるときにノイズを払う用途にだけ使い、承認の直前にオプションなしでもう一度見る。 一つ目はどこを見るべきかを決める段階で、二つ目は見落としがないかを確認する段階だ。二つの段階を一つにまとめようとした瞬間、上の表の危険が生き返る。

レビューで大量のフォーマット変更を扱う

ほとんどのレビューツールは空白無視の表示を持っている。それを有効にすれば画面は整うが、それだけでは残る問題がある。レビューの意見を特定の行に付ける機能はたいてい元の行番号を基準にするので、フォーマットで行がずれると以前の意見の位置が食い違う。そして §9 で見たとおり blame の汚染はレビュー画面のオプションでは解決しない。

だから大量のフォーマット変更がロジック修正と一塊で上がってきたときは分離を依頼するほうがよい。 依頼するとき感情や好みではなく数字を根拠にすると会話が短くなる。§8 の命令がその数字を作ってくれる。

  • git diff --shortstat と git diff -w --shortstat の二行をそのまま貼る。51行対2行のような対比は説明が要らない
  • 空白だけ変わったファイルの一覧を git diff -w --numstat で取り出して一緒に出す。それらのファイルにはレビューするものがないという意味だ
  • 依頼の形はコミットの分離であって差し戻しではない。フォーマッタを使うなという意味に読まれると論点がずれる
  • 分離したフォーマット用コミットの SHA を .git-blame-ignore-revs に入れるところまでを同じ依頼に含める。そうしないと blame の問題が残る
  • 逆にフォーマットだけの純粋なコミットは素早く承認する。 分離を依頼しておいてそのコミットを長く抱えると、次から誰も分けなくなる
  • リポジトリにフォーマッタの設定がコミットされていて CI がそれを検査しているなら、フォーマット用コミットの中身自体は人が検討するものではない。検討すべきなのは設定ファイルが変わったかどうかだけだ

まとめ

空白ノイズの問題は二つの層に分かれる。既に生じたものを画面から消す仕事と、そもそも生じさせない仕事だ。前者はオプション四つでほぼ片付く。行末だけ消すなら --ignore-space-at-eol、インデントの変換まで消すなら -b、なかったインデントまで消すなら -w、空行整理のコミットには --ignore-blank-lines。三つは包含関係にあり、最後の一つだけ性格が違う。

blame は別の問題だ。-w ではフォーマッタのコミットを消せないことを §9 で確認した。実際の答えは .git-blame-ignore-revs にそのコミットの40文字の SHA を書き、blame.ignoreRevsFile を設定することだ。ファイルがリポジトリに一緒にコミットされるので、一度入れればチーム全体が一緒に直る。

そして後者の層、つまりそもそも防ぐ仕事のほうが結局は大きい。.editorconfig で保存の時点で整理し、git diff --check をコミットフックに掛け、フォーマッタの結果はそれだけを入れたコミットで出す。 この三つができれば前のオプションを覚えておく必要はほとんどなくなる。ただし最後に一つ残る。Python と YAML と Makefile の前では -w を手放さなければならない。その場所では空白は書式ではなくコードだ。

確認できなかったこと

  • --ignore-rev と --ignore-revs-file が git のどのバージョンから入ったのかは一次資料で確認できなかった。複数の場所で2.23と書かれているがリリースノートを直接開いて突き合わせていないので、バージョン番号は本文に書かなかった。上の出力はすべて2.48.1から出たものだ
  • Makefile のレシピ行がタブでないときに出るエラーは直接再現できなかった。 実験に使った Git Bash に make がなかった。そのため §17 の Makefile の行は規則だけを書き、実行出力は貼っていない
  • .editorconfig の各キーがエディタごとに実際どこまで適用されるかは確認していない。このファイルは git が解釈するものではなくエディタやプラグインが解釈するものなので、対応範囲が道具ごとに違う
  • GitHub 以外のレビューツールが .git-blame-ignore-revs をどこまで認識するかは確認していない。§18 はそのため特定の道具の名前を出さず一般的な対応だけを書いた
  • すべての出力は Windows の Git Bash 一箇所だけで得たものだ。Linux や macOS の別の git ビルド、特に BSD 系の diff ではオプション名や出力が違いうる
