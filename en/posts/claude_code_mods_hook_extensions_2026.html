Definition and Architecture of Mods — Resident Structure vs Settings Hooks

The post defines a mod as a small JavaScript or TypeScript file that runs inside your Claude Code session. A mod can watch what is happening in the session, change what Claude Code does, or draw its own UI, in the terminal or in the desktop app. You do not have to learn the API first: you run claude, describe the mod you want, allow hot reload when Claude Code asks, and the mod shows up when the turn ends. Because Claude Code itself knows how to write mods, the loop stays conversational afterwards: you can keep asking for tweaks, such as making Storm start at 70% or adding the dollar cost at the end, and each change reloads in place.

Claude Code already lets you change a good deal about how it behaves through settings, permission rules, slash commands, skills, and a status line. The post says mods go further, because they can rewrite or replace what Claude Code does and draw custom UI. Under the hood a mod is a hook that ships inside a plugin, and each mod sees every event in your session as it happens. The post presents this as a way to fit Claude Code to how you work: a readout you check all the time, a guard in front of the commands that make you nervous, or a review view built for how you like to read changes.

The post sums up the difference from settings hooks in one short paragraph. A settings hook runs a shell command for each event and passes JSON over stdin and stdout, whereas a mod is loaded once and stays in the session. Four things follow from that structure.

  • Loaded once, kept in the session: no process is started per event; the module stays loaded for as long as the session lives.
  • State is kept: values placed in $.state, which the host holds, instead of in module variables survive a reload.
  • UI is updated: the mod draws UI that updates as events happen, rather than a one-off output.
  • Callbacks into Claude Code: a mod can open a pane, run a process, register a slash command, or register a tool that the model can call.

According to the post, Claude Code uses mods itself. Some of its own features are built as mods, including AGENTS.md support and the /diff pane beside the conversation. Their source, with tests, sits in the public anthropics/claude-code repository under mods/, so you can read how the team builds them.

Hook Chains and Three Patterns — Mechanics of Observe, Rewrite, and Answer

A mod runs as a chain of plugin hooks. The module exports register(on, options), and inside it on(event, matcher?, hook) adds a hook. Every hook has the same shape, and the comments in the original code explain what the three parameters are.

on("tool.call", { tool: "Bash" }, async ($, e, next) => {
                      // $    the mods API: ui, session, state, store, fs, process, clock, http, tool, command, model, ...
                      // e    this event's input, as plain data
                      // next passes e to the other plugins and then to Claude Code's own behavior
                      return next(e);
                    });

Hooks form a chain, like middleware. A hook that simply returns next(e) therefore changes nothing at all. Your hook runs first, next(e) hands the event to the next plugin, and at the bottom Claude Code does what it would have done anyway. A hook can make one of three moves. To observe, it writes const r = await next(e);, looks at the result, and returns it unchanged, for example to record every file edit or to take a reading after each turn. To rewrite, it returns next({ ...e, command: safer }), which changes what the rest of the chain sees. To answer, it returns { deny: "…" } without calling next, which refuses a tool call or lets the hook serve a command or a tool itself.

PatternCode SignatureExample from the PostPlace in the Chain
Observeconst r = await next(e); /* look */ return rRecord every file edit; take a reading after each turn, then return the result unchangedLooks at the result after calling next
Rewritereturn next({ ...e, command: safer })Change what the rest of the chain seesChanges the input before calling next
Answerreturn { deny: "…" } (without next)Refuse a tool call; serve a command or a tool yourself, without the rest of the chain ever seeing the eventEnds the chain and answers in its place

The post describes the events as covering tool calls, the prompt as submitted, turns starting and finishing, the session starting and ending, slash commands, and ui.render, which stands for every piece of the interface as it is drawn. The names that can be confirmed from the text and the code are the following.

  • tool.call: a tool call, which can be narrowed to one tool with a matcher such as { tool: "Bash" }.
  • prompt.submit: the prompt as submitted; the post lists a hook that adds your team conventions to every prompt as an idea.
  • turn.start and turn.complete: a turn starting and finishing, with subagent turns told apart by e.agentId.
  • session.start: the session starting; the post lists both the starting and the ending of the session among the events.
  • command.run: a registered slash command being run, narrowed by command name as in { command: "replay" }.
  • ui.render: a piece of the interface being drawn, narrowed by component as in { component: "AbovePrompt" }.

The module runs in a sandbox of its own, with no DOM and no Node, so everything outside it goes through $; file, process, and network access therefore appear as $.fs, $.process, and $.http. The comment in the original code says $ holds ui, session, state, store, fs, process, clock, http, tool, command, model, and more. Because the API can change between releases, the post names the type declarations that Claude Code writes for your build as the reference for every event, every method on $, and every element's props.

Mod Plugin Components — Manifests, Type Contracts, and $.state

A mod is not a separate format but an ordinary plugin folder. This is the layout the post shows for Token Weather.

token-weather/
                    ├── .claude-plugin/
                    │   ├── plugin.json
                    │   └── types/            (written by Claude Code when it loads the mod)
                    ├── hooks/
                    │   ├── hooks.json
                    │   └── token-weather.mjs
                    ├── types/
                    │   └── index.d.ts        (added in step 3)
                    └── tests/
                        └── token-weather.test.ts   (added in step 5)

The comments in the tree show when each file arrives: .claude-plugin/types/ is written by Claude Code when it loads the mod rather than by you, types/index.d.ts is added in step 3, and tests/token-weather.test.ts is added in step 5. Each part has its own job.

  • .claude-plugin/plugin.json: the standard plugin manifest, which carries name, version, description, and author; the post's example uses the name token-weather and the version 0.1.0.
  • hooks/hooks.json: points at exactly one module under modules; the post puts it as "A mod has exactly one".
  • types/index.d.ts: the type contract that declares the values you keep in $.state inside the PluginState interface; the manifest must then gain "types": "./types/index.d.ts".
  • .claude-plugin/types/: the folder Claude Code writes the declarations for your build into every time it loads the mod, so your editor and tsc -p work with no extra step.

The habit the post stresses most is planning for hot reload. A module-level let readings = [] looks like the obvious choice, but a hot reload is a fresh load: register runs again, session.start fires again, and module variables start over. The history belongs in $.state, which holds named values in the host and so survives reloads. A value is addressed by plugin and key, as in { plugin: "token-weather", key: "readings" }, and is read and written with $.state.get and $.state.set. In the post's code each write appends the new reading to the stored history and keeps only the latest twelve with .slice(-HISTORY).

If you skip the declaration, claude plugin validate stops you with an error that names the fix. The error the post shows is "token-weather.readings is not declared: the manifest's types contract must name it in interface PluginState { … }". There is also a reward for doing it properly: a $.state.get made while a render hook runs subscribes that drawing, so every later $.state.set redraws the band and you never call $.ui.invalidate.

Example 1: Token Weather — Context Consumption and 12-Turn Sparkline

The first mod the post builds from an empty folder is Token Weather. After each turn it reads how full the context window is and draws one line in the band directly above the prompt. That line holds a weather icon, the percentage, the tokens used out of the window, a small chart of recent turns, and how much the last turn added. The whole module is about 80 lines, and the post shows the band filling over three turns that each read more files, from 18% Clear to 67% Showers to 81% Storm of a 200k window.

The post also offers a shortcut that skips the six steps. Claude Code knows how to write mods, so you can start a session with claude, paste a prompt that describes the one-line display, and let it do the work. Claude asks once whether to turn on hot reloading for the session. Once you allow it, the band appears above the prompt when Claude's turn ends, and every later change reloads in place. The mod loads only in that session and its folder is cleaned up later, so to keep it you copy the folder out and install it like any plugin. The prompt in the post asks for the percentage used, the tokens used out of the window such as 134.4k / 200k, a chart of the last 12 turns drawn with ▁▂▃▄▅▆▇█, and how much the last turn added, such as ▲ +98.3k last turn.

The band directly above the prompt is a component called AbovePrompt. The post notes that Claude Code draws nothing there itself, which makes it a good first target. The same logic explains how a level is chosen: the code takes the first FORECAST entry whose upTo is above the current percentage, so exactly 25% already counts as Cloudy rather than Clear. You hook its ui.render event and return a tree of elements. This is the code of the post's second step.

// hooks/token-weather.mjs
                    export function register(on) {
                      on("ui.render", { component: "AbovePrompt" }, ($, e, next) => {
                        const { Box, Text } = $.ui.resolve(e);
                        return Box({
                          paddingX: 1,
                          children: [Text({ color: "yellow", bold: true, children: "☀  Clear skies" })],
                        });
                      });
                    }

The elements are not globals. Each surface Claude Code draws on supports a slightly different set, so $.ui.resolve(e) returns the constructors for the surface being drawn. After claude --plugin-dir ./token-weather starts a session, "☀ Clear skies" appears above the prompt, and because the folder is watched every save reloads the module in place with no restart. The post says this quick feedback loop is most of what makes mods fun to write, and it adds that JSX works too, with h as the factory.

The numbers come from $.session.usage(), which returns the same figures as the status line, namely context.tokens, context.window, and context.percent. The call is free: it only sends a token-count request if you ask for a breakdown. The hooks on session.start and turn.complete call next(e) first and then only observe, and if (!e.agentId) keeps subagent turns out so that only main-loop turns are read. The history keeps the last 12 readings and is drawn with the characters ▁▂▃▄▅▆▇█.

The post singles out three details worth copying. The component props are on e.props: when hasSurvey is true a survey wants the band, so the hook yields with next(e), and bodyColumns is the real width of the band, which is narrower than the terminal while a pane is docked beside the transcript. This code adds the chart and the delta only when the width is 60 columns or more. When you have nothing to draw, returning next(e) gives the band back to Claude Code and to other mods. Finally, single-width symbols rather than emoji line up in every terminal font. Only e.component, e.surface, e.requestId, and e.viewport sit at the top level of e, so anything else you expect to find there is actually under e.props.

Example 2: Blast Radius — Risky Command Interception and Dry-Run Reporting

When Claude calls Bash with any of the following, Blast Radius holds the call. It works out what the command would touch and opens a pane with Proceed and Cancel. If you press 2, Claude gets a refusal with the reason, and if you press 1, the command runs as written.

  • rm -rf
  • git reset --hard
  • git clean
  • a force push
  • a database migration

The post's screenshot caption shows it holding rm -rf build and listing the 9 files (1.1 MB) that the command would delete; Cancel refuses it, and on the second try Proceed runs it. The mod uses three hooks: tool.call on Bash, and ui.render on Pane and on AbovePrompt. The core of it is the answer move from the table above, and the post gives the code below.

on("tool.call", { tool: "Bash" }, async ($, e, next) => {
                      const risk = classify(String(e.command ?? ""));
                      if (risk === null) return next(e);                 // everything else runs as normal
                      const report = await measure($, risk, await $.session.cwd());  // git status, git clean -n, du, ...
                      held = { command: e.command, risk, report, decision: null };
                      const opened = await $.ui.open({ id: "blast-radius", title: "Blast Radius", focus: true });
                      if (!opened.isPlaced) held.where = "band";         // too narrow for a pane: draw above the prompt
                      while (held.decision === null && !next.signal.aborted) {
                        await $.process.run(["sleep", "0.25"]);          // time inside $ calls doesn't count against the hook's time limit
                      }
                      if (held.decision === "proceed") return next(e);   // let it run
                      return { deny: `Blast Radius held this command: the user pressed Cancel. It would have: ${report.summary}.` };
                    });

The post points to four lessons in this code. First, dry runs go through $.process.run. The report comes from the tools' own commands, git status --porcelain, git clean -n, git log HEAD..origin/main, and showmigrations, and because the arguments go in as an argv array, nothing in a path is run as shell code. Second, holding a call: a hook gets 10 seconds of its own time per dispatch, but time spent waiting inside a $ call does not count. The loop therefore waits on short sleep processes until the onPress of a button sets the decision, and it gives up when next.signal aborts, which happens when you press Esc. When the decision is not proceed, the hook returns a deny whose text tells Claude why: Blast Radius held this command, the user pressed Cancel, and then what it would have done, taken from report.summary.

Third, buttons can carry hotkeys: Button({ label: "Proceed", hotkey: "1", onPress }) works by click, by Tab and Enter, or by the digit. Fourth, the mod degrades to the band. The terminal docks a pane beside the transcript when it is wide enough, and when $.ui.open answers isPlaced: false, the same report is drawn above the prompt. The post's caption for this case shows the report for git reset --hard drawn in the band at 120 columns. In the code, a command that classify does not flag returns next(e) and runs as normal.

The post also states the limit plainly. This mod is a safety net, not a permission system. It reads the command text, so $(…), aliases, and scripts that call rm get past it. For a hard block, use permission rules.

Example 3: Replay Theater — Step-by-Step Diff Playback of File Edits

While a turn runs, Replay Theater records every Edit and Write call: the file, plus the text before and after. When the turn ends, a hint appears above the prompt. If you press r or type /replay, a pane walks through the edits one diff at a time, with a strip of numbered steps and Prev, Next, and Close buttons. The mod never blocks or changes an edit; it only observes, and the post gives the code below.

on("tool.call", async ($, e, next) => {
                      if (EDIT_TOOLS.has(e.tool)) state.pending.push(...(await stepsFor($, e)));  // old/new text → diff
                      return next(e);                                                              // the edit runs untouched
                    });
                    on("turn.start", ($, e, next) => { if (!e.agentId) state.pending = []; return next(e); });
                    on("turn.complete", async ($, e, next) => {
                      const r = await next(e);
                      if (!e.agentId && state.pending.length) state.replay = state.pending;       // one replay per turn
                      return r;
                    });
                    on("session.start", async ($, e, next) => {
                      const r = await next(e);
                      await $.command.register({ name: "replay", description: "Step through the last turn's file edits" });
                      return r;
                    });
                    on("command.run", { command: "replay" }, async ($, e) => ({ text: (await openReplay($)) ? "Replaying" : "No edits" }));

The post lists four things this code teaches. The first is pairing events: turn.start and turn.complete bracket the edits into one replay per turn, and e.agentId keeps subagent turns out of the grouping. The second is registering a slash command: $.command.register is called in session.start and the command is answered on command.run. The third is reading files: for a Write, $.fs.read gets the old contents just before the write lands, so the diff is real. The fourth is that placement is the surface's job: in fullscreen the pane docks on the right, at 80 columns it opens inline above the prompt, and the mod draws the same tree either way. In the code, EDIT_TOOLS.has(e.tool) selects the Edit and Write calls, the pending list is cleared at turn.start of a main-loop turn, it is promoted to state.replay at turn.complete only when it is not empty, and the command.run hook answers with the text Replaying or No edits. The post's example is a five-edit rename across three files, shown as the hint first and then as steps 1 to 5 in the pane.

Mod Distribution and Security Boundaries — Local Permissions and Source Auditing

Step five of the post is validation and testing. claude plugin validate reads the manifest and the module's source the same way Claude Code will, and reports which events the module hooks and which $ methods it calls. claude plugin test runs the plugin *.test.ts files against the real Claude Code runtime. Hooks that a test registers with on run after the mod in the chain and stub what Claude Code would answer, so you control exactly what $.session.usage() returns. In the post's test the stubbed usage starts at 36,100 tokens of a 200,000 window and the test expects the band to show Clear; after the stub is raised to 134,400 it expects Showers, 67% of context, and ▲ +98.3k last turn. The post notes that this test also checks the redraw behavior from step 3, since the band updates after turn.complete without the mod ever asking for a redraw. The claude plugin validate run in the same step prints that the types file declares the state token-weather.readings, lists the hooks session.start, turn.complete, and ui.render{component=AbovePrompt}, lists the calls $.session.usage, $.state.get, $.state.set, and $.ui.resolve, and ends with Validation passed.

claude plugin validate ./token-weather
                    claude plugin test ./token-weather
                    claude --plugin-dir ./token-weather

A mod is a plugin, so it ships the same way as one. A folder with a .claude-plugin/marketplace.json is enough to act as a marketplace, and when you put it in a GitHub repo that repo becomes your marketplace, which you update with a normal push. A marketplace can be as simple as that: the post's example file names the marketplace my-mods and lists the plugin token-weather with the source ./token-weather, and from a local folder you run claude plugin marketplace add ./my-mods and claude plugin install token-weather@my-mods --scope user. Installing takes three commands inside Claude Code: /plugin marketplace add your-org/my-mods, /plugin install token-weather@my-mods, and /reload-plugins. The mod starts when you reload, and if it does not show up you restart Claude Code. Plugins that include mods can also be submitted to the Claude directory at claude.ai/directory/manage, so that people can find a mod without a link from its author. The post stresses that there is nothing new to learn here, because a mod is shared exactly like any other plugin.

On security the post has one central sentence. A mod is code that runs inside Claude Code on your machine with the same access Claude Code has, and it is written by its publisher, not Anthropic, so you should "install mods the way you'd install a package: read the repo first and only install from people you trust". Around that sentence, the following facts can be confirmed from the post.

  • The access a mod has is the same access that Claude Code has.
  • The author of a mod is its publisher, not Anthropic, which is why you read the repo first and install only from people you trust.
  • Nothing gets installed until you run the command.
  • The module runs in a sandbox with no DOM and no Node, and every contact with the outside goes through $; the post does not describe this sandbox as permission isolation.
  • A hook gets 10 seconds of its own time per dispatch, and time spent waiting inside a $ call does not count.

The post's own example points the same way: Blast Radius is a safety net and not a permission system, so for a hard block you should use permission rules.

The post closes with four habits: lean on the types Claude Code writes for you, read props from e.props, plan for hot reload by keeping data in $.state, and, when a drawing does not show, run claude --debug and look for a line saying a hook returned a tree that does not validate. The post then asks what you will mod and offers starting ideas: a cost or rate-limit meter built from $.session.usage() as a status line with $.ui.status, a prompt.submit hook that adds your team's conventions to every prompt, a pane that lists the files Claude read this session as a live map of what it has seen, a focus timer that sends a toast with $.ui.toast when a long turn finishes, and a tool.call guard tuned to your stack, such as production kubectl contexts or terraform apply. Unconfirmed Details

  • The error message or fallback behavior when a mod is loaded on Claude Code 2.1.286 or earlier; the post says only that the API can change between releases and that the generated type declarations are the authority for your version.
  • Whether values in $.state are restored when a session is closed and resumed; the post only says they survive reloads.
  • The full list of $.ui components available on surfaces other than the terminal and the desktop app, such as a VS Code extension.
  • The review criteria applied when a mod is submitted to claude.ai/directory/manage; the post says only that the directory accepts plugins that include mods.
  • How asynchronous timers or background work created inside a hook are cleaned up when the session ends; the post describes only the 10-second budget of a hook per dispatch and the abort signal on next.signal.
