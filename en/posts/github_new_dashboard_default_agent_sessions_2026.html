Background — Transition from Feature Preview to Default Experience

The GitHub Changelog entry dated October 1, 2026, titled "New dashboard experience now the default", states that the new dashboard experience, previously available as a feature preview, is now the default view for everyone. The Changelog calls it a productivity-focused dashboard that helps you focus on the work that matters most and makes it easier to find and act on what you need next. The entry is filed under Improvement.

The order of events only becomes visible when the two sources are placed side by side. The Community announcement (#208952) was posted on September 28 and already said GitHub is making the new dashboard the default experience for everyone. The Changelog entry is dated three days later, October 1, and says "is now the default". The Changelog does not give the date the default actually changed, so it cannot be asserted that the switch happened on October 1.

According to the announcement, GitHub introduced the new productivity-focused dashboard as a feature preview last year, and many users have since shared feedback about both the new and the previous dashboard. The announcement says the new dashboard becomes the default for everyone based on that feedback. The announcement lists four things the new dashboard lets you do, while the Changelog groups the same content into three bullets. Each item and the GitHub Docs wording are covered in the following sections. Items that could not be confirmed are collected, with reasons, in the section on unverified details.

Key Components of the New Dashboard Specified in the Changelog

The Community announcement lists four things you can do with the new dashboard. The Changelog merges the first two into a single bullet and so has three bullets.

  • One place for work: View your active agent sessions, issues, and pull requests in one place.
  • Filters and a list cap: Filters choose what appears in each section, with up to 12 items in each list.
  • A separate Feed tab: Repository and organization activity is caught up on in the separate Feed tab. The Changelog describes this as keeping your feed distinct from your productivity-focused dashboard.
  • Starting work from the dashboard: The examples given are assigning an issue to Copilot coding agent and opening a pull request in Copilot Chat.

The announcement says the dashboard is designed to provide a focused view of your current work and help you decide what to do next. The number 12 appears in both sources only as one sentence: filter each section and show up to 12 items per list. Neither source says how to see items beyond 12; the only related statement is in GitHub Docs, where View all on the agent session list opens the agents tab (next section).

Unifying Agent Sessions, Issues, and PRs into a Work-Focused Interface

The Changelog only says that agent sessions, issues, and pull requests are viewed in one place. What appears in each list is described in the Home dashboard view part of the GitHub Docs page "Personal dashboard". That part describes the updated home dashboard as a public preview subject to change, and says you must first enable New Dashboard Experience in feature preview. Because this differs in time from the Changelog saying it is the default, the Docs wording below may have been written before the change of default.

  • Agent sessions: A list of your running and past Copilot cloud agent sessions. View all opens the agents tab.
  • Pull requests: A list of the most recent pull requests that you authored, reviewed, were mentioned on, or where you were requested as a reviewer.
  • Issues: A list of the most recent issues assigned to you or involving you.
  • Filters and the 12 items: This is the wording of the Changelog and the announcement; the Docs home dashboard part mentions neither filters nor the number 12.

The same Docs page also describes a Recent activity section apart from the home dashboard. It previews up to 4 updates from the last two weeks, and open issues and pull requests appear there when you opened them, when someone commented on one you opened, when one was reopened, when your review was requested, when you were assigned, when you referenced one in a commit, or when you commented. The Top repositories list is generated automatically and cannot be edited; it includes repositories where you made commits, opened or commented on issues, or opened or commented on pull requests, and repositories drop off one year after your last interaction. Docs does not describe how these two appear on the new dashboard.

Collaboration around issues and pull requests is covered in our earlier article Git & GitHub Mastery Part 4: Pull Requests and Code Review.

Separation of the Feed Tab — Distinguishing Social Updates from Core Work

The Changelog says updates are caught up on in a separate Feed tab, keeping the feed distinct from the productivity-focused dashboard. Which activities appear in the feed is listed under Feed activity in the GitHub Docs page "Personal dashboard". That part says the new feed is also a public preview subject to change, and that updates appear when someone you follow performs the listed actions.

  • Definition of the Feed tab (Changelog and announcement): The Changelog says you catch up on updates in the Feed tab; the announcement calls it the place to catch up on repository and organization activity.
  • Docs feed events (1): Someone you follow stars a repository, follows another user, or creates a public repository.
  • Docs feed events (2): Someone you follow opens an issue or pull request with the help wanted or good first issue label on a repository you are watching, or pushes commits to a repository you watch.
  • Docs feed events (3): Someone you follow forks a public repository or publishes a new release. The Quickstart page says a Filter dropdown in the upper right corner of the feed lets you choose which event types to see.

The Changelog does not list which events appear in the Feed tab, so neither document states whether the Docs list matches the contents of the Feed tab. What is confirmed is that the Changelog places the feed in a separate tab and that Docs defines feed events as the types above.

Direct Dashboard Actions — Integration with Copilot Coding Agent and Chat

The Changelog gives two examples of starting work directly from the dashboard, and the announcement gives the same two. GitHub Docs separately describes the Copilot-related elements of the home dashboard.

  • Assigning an issue to Copilot coding agent: The Changelog gives "assigning an issue to Copilot coding agent" as an example.
  • Opening a pull request in Copilot Chat: The Changelog gives "opening a pull request in Copilot Chat" as an example.
  • The Copilot prompt box in Docs: The home dashboard includes a prompt box where you can prompt GitHub Copilot, assign Copilot cloud agent to tasks, create an issue with GitHub Copilot, and start building with GitHub Spark.
  • Agent tracking in the Docs quickstart: From the dashboard you can prompt Copilot directly, track the latest agent sessions you triggered, open agent logs to see progress, and manage the resulting pull requests and tasks.

The Changelog says "Copilot coding agent" while Docs says "Copilot cloud agent", so the naming differs. Permission questions for browser-based development environments are covered in github.dev 1-Click Token Theft Vulnerability Analysis, and task specifications handed to agents in OpenSpec AI Coding Agent Specification.

How to Switch Back to the Previous Dashboard — Preview Dropdown

The Changelog says that if you would rather keep the previous experience, you can switch back at any time by clicking the dropdown next to Preview. The Community announcement likewise says that if you prefer the previous dashboard, you can switch back at any time using the dropdown next to Preview.

  • Path: Click the dropdown next to the Preview label.
  • Timing: Both the Changelog and the announcement say at any time.
  • Feedback channel: The Changelog invites questions and feedback as comments in the Community discussion. The announcement asks for comments on what helps you stay productive, what gets in your way, and what you would most like improved.
  • Follow-up improvements: The announcement says GitHub has received a significant amount of feedback over the last few weeks and is exploring several directions for follow-up improvements based on the themes it has heard most consistently.

The announcement says GitHub will share more about those improvements in the next few weeks, and that in the meantime those who prefer the previous dashboard can switch back with the dropdown.

The checks can be done in this order without touching any setting.

  • Confirm that the active agent sessions, issues, and pull requests sections appear on the dashboard.
  • Check whether any issue assigned to you or any PR awaiting your review is missing from a list because of the 12-item limit.
  • Open the Feed tab and check whether activity from people you follow and repositories you watch appears as the types listed in Docs.
  • If you need the previous view, switch back from the dropdown next to Preview.
  • Leave problems or suggestions as a comment in the Community discussion (#208952).

Unverified Details

  • Whether the two GitHub Docs pages were updated after the change of default. Both pages are available; they describe the home dashboard as a public preview and its activation as New Dashboard Experience in feature preview. The wording differs in time from the Changelog saying it is the default, and Docs has no statement on the 12-item limit, the Feed tab separation, or reverting.
  • Whether organization or enterprise administrators have a policy control to fix the previous dashboard as the default for members. It is not written in any document.
  • Whether the 12-item display count can be changed in user settings, and how to see issues or PRs beyond 12. Docs has only View all for agent sessions.
  • How long the way back to the previous dashboard via the dropdown next to Preview will last. No end date is written.
  • Unofficial reactions and satisfaction statistics in external developer communities. Only the wording of the Changelog, the announcement, and Docs was checked, and reactions that are not official documents were left out.
