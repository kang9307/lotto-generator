Designing an Internal Knowledge Platform - Sources, Permissions, Chunking and Cost

Wiring up connectors is not the finish line - where permissions, duplication, freshness and budget actually break

July 28, 2026 Dev & Infra

Introduction: the decisions start the moment you add the first connector

Every proposal for internal search opens with the same sentence. The answers are already inside the company; people just cannot find them. That is true. The root cause of a past outage lives in an incident channel from three years ago. The deployment procedure lives in the wiki. The reason a module was written that way lives in commit messages and code review. Why the customer wanted the feature at all lives in a ticket. The problem is that those four things sit in four systems, behind four permission models, at four different levels of freshness.

The recipe for fixing this is by now standardised. Add connectors, generate embeddings, layer on hybrid search, attach a chat interface. A weekend is enough for a prototype. The real work starts afterwards. Most internal knowledge platforms do not fail because the retrieval algorithm was bad. They fail because the wrong sources were connected, because permissions were enforced in the wrong place, because the same answer comes back five times, and because the bill turned out to be ten times the estimate.

In July 2026 Cerebras published how it built Cerebras Knowledge, its internal knowledge platform. Roughly three months after launch it was handling more than 15,000 questions a day, used by people, automations and agents alike. This article is not a tour of that system. It is an attempt to work backwards from the architecture to the decisions that produced it, and to lay out the choices any team building something similar will actually face. There are five: which sources to connect, how to enforce permissions, what to keep out of the index, how to split and deduplicate, and where the cost concentrates.

What this article does not cover. The slow decay that sets in after launch - document expiry, marking the authoritative copy, handling contradictions, measuring staleness, re-indexing triggers - was covered in Your internal knowledge base rots quietly. This one stays on integration design at build time. Turning a codebase into a graph is handled in code knowledge graphs and graphify, and verifying generated answers is handled in the fact-check process.

1. The architecture Cerebras chose - gathering without moving

The first thing worth noticing in the published description is not a technology choice but a rejected option. The team did not migrate company data into one platform.

1.1 One schema, not one store

Information is created wherever it is convenient. Chip design discussion accumulates in Slack, code in repositories, procedures in document tools, operational metrics in internal databases. Those tools are products refined for their own domains over years, so demanding consolidation is usually a demand that people change their habits. Cerebras went the other way. Data stays where it is, and what gets unified is a single Postgres table schema carrying embeddings, raw summaries and metadata. Each source defines only three things: what the data is, how to connect to it, and how often to fetch.

This distinction matters enormously in practice. Physical consolidation (move the data) and logical consolidation (unify the query interface) are entirely different projects. The first delivers nothing until the migration completes, and it usually never completes because it runs into organisational politics. The second delivers value with every source you attach. Its price is synchronisation code and permission mapping that grow with the number of sources.

1.2 Why the system is split into three layers

The published structure has three layers: collection and storage, query, and a layer for authentication, authorisation, auditing and analytics. Standing that last layer up separately is the notable part. In a knowledge platform, authorisation and audit should be a layer, not a feature. Permission models differ per source, so scattering permission handling across connectors adds one hole per connector.

The query layer has a language model plan which retrieval tools to use and call them in parallel. The published tool list includes unified vector search, direct Slack retrieval, string search across repositories, recent pull requests, per-file summary indexes, and a tool for finding who knows about a topic. The important note is that the tools themselves are deliberately simple and free of language model calls. Put an LLM inside a retrieval tool and latency and cost multiply instead of adding.

1.3 How far this case study should be trusted

Sourcing, stated up front. The original is a thread posted by the official Cerebras account on X in July 2026. At the time of writing that URL does not open without authentication, so the content was confirmed through a public mirror and secondary write-ups. The figures and implementation details below are therefore second-hand, and it is a company describing its own tool. No benchmark or accuracy numbers were published, so this configuration should not be read as a guarantee of retrieval quality. What is worth borrowing is not the numbers but the structure of the choices.

2. Integration cost and value per source - where to start

Connect everything is not a plan. Sources differ in authority, structure, permission model and refresh rate, and that combination sets integration difficulty. Below are the five candidates that come up most often.

SourceAuthorityClarity of permission modelStructure and unitIntegration difficultyPilot priority
Code repositoriesHigh (what runs is the truth)Clear (repo and org level)Clear (file, function, class)Medium (needs incremental re-embedding)First
Wiki and documentsMedium (drafts mixed with finals)Medium (space and page inheritance)Medium (headings and paragraphs)LowFirst
Tickets and issuesMedium (only resolved ones are near-authoritative)Clear (project level)Clear (fields plus free text)LowSecond
Conversation (Slack and similar)Low (provisional consensus)Complex (public, private, DM, shared)Unclear (thread boundaries are fuzzy)HighSelected channels only
Operational databasesHigh (numbers are facts)Complex (row-level permissions exist)Structured (needs schema knowledge)HighLater

2.1 The most valuable sources are usually the hardest

The rule to read out of that table is simple. Value and difficulty move in the same direction. A wiki is easy to attach, but questions answered by the wiki are already answered by people searching the wiki. What is genuinely valuable is the answer that exists nowhere else. Why a parameter was changed during a 3 a.m. incident three years ago exists only in Slack. And Slack is precisely the hardest source to attach.

So the practical order is usually this: build the pipeline and the evaluation harness on the easy, safe sources first, then layer the hard ones on top. Start with code and wiki until retrieval quality is measurable, then open Slack channel by channel. Start with Slack and you will not be able to tell whether poor quality came from the data or the pipeline.

2.2 What really sets the order is the permission model

When you prioritise sources, the binding constraint turns out to be neither value nor difficulty but how clean the permission model is. Three questions narrow it down.

  • Can you enumerate the principals? If an API cannot tell you who may read a given document, that source cannot go into the index. If it cannot, index only the company-wide public scope, or nothing.
  • Can you learn that a permission changed? Without change events or an incremental query, full re-verification is the only option, and its cost becomes the floor on your synchronisation interval.
  • How many levels of inheritance are there? If permissions cascade from org to space to folder to document, one change at the top rewrites thousands below. That path is the one most often missed in synchronisation design.

3. Three ways to enforce permissions in search

This is the decisive difference between internal and public search. The same query must return different results for different people. There are three broad approaches, and the industry calls the first two early binding and late binding.

3.1 Early binding - store permissions with the document

At ingest you write the user and group identifiers that may read the document into the index, then filter on that field at query time. This is what Azure AI Search documentation describes as the security filter pattern: create a string field in the index, pass the caller identity in as a filter string, and exclude documents that do not match. Being plain string comparison rather than an API-bound feature is presented as the advantage, since it works on any stack.

A step beyond that is the permission filter. Here the same document carries permission metadata in the index, and the query attaches the user token as a request header; the search service compares user, group and scope claims in the token against that metadata and trims the results. The documentation is explicit that the difference from a plain security filter is that this is recognised as directory authentication rather than string matching.

3.2 Late binding - ask the source on every query

Permissions are kept out of the index; after results come back, each item is checked against the source system to ask whether this person may see it. Permissions are always current, which is the single but powerful advantage. The drawbacks are consistently flagged in vendor and industry material: it is slow, it loads the source system on every query, and it forces a decision about what happens when the source does not answer. The last one is the dangerous part. Implement the timeout as show it anyway and permissions leak at that moment; implement it as hide it and search returns empty results whenever a source wobbles.

3.3 Delegation - hand retrieval back to the source

The third option skips the index entirely and calls the source system's own search API with the user's token, letting the source handle permissions. The separate direct Slack retrieval tool in the Cerebras design can be read in this category. Permission accuracy is the best available, but ranking quality varies per source and merging results into one ordering is hard.

DimensionEarly bindingLate bindingDelegation to source
Permission freshnessLags by the sync intervalAlways currentAlways current
Query latencyLow (one filter)High (per-item check)Medium to high (external API)

3.4 Choosing - this is not a single-answer question

The real answer is usually a mix. Four criteria organise the decision.

  • Rate of permission change. Sources where project membership churns lean toward query-time checks; sources stable at the org level lean toward early binding.
  • Blast radius of exposure. For people, legal and security sources, a stale permission is an incident. Those sources are safer left out of the index, or handled by delegation.
  • Scale. Fetching 100 results and checking each survives growth in document count, but if most results are trimmed you need repeated round trips just to fill the top k.
  • Whether copies are allowed at all. Some sources cannot legally or contractually be replicated into an index store. Delegation is then the only option.

For reference, Azure AI Search documentation lists four approaches in this space: string-based security filters, POSIX-like ACL and RBAC scopes, Purview sensitivity labels, and SharePoint ACL ingestion. The last three are marked as preview at the time of writing. On the AWS side, Bedrock Knowledge Bases guidance describes segmenting access with metadata filters, supporting boolean, string, double and integer attribute types. Both vendors ultimately trim on metadata attached to documents; the difference is how much of the wiring to your identity system they do for you.

4. How permissions leak - it breaks in synchronisation, not design

What this section is for. What follows is a list of paths by which permissions leak accidentally, and the point is to block them in advance. Techniques for getting around access controls are out of scope and are not discussed.

4.1 Chunking drops the permission metadata

This is the quietest and most common failure. You attach an ACL to a document, then split that document into twenty chunks for the vector index. If the ACL is not reattached to each chunk, the chunks become unowned fragments. Azure AI Search documentation warns about this explicitly: when a skillset splits documents, ACL fields must move from indexer field mappings to index projections, and without that projection chunk-level references are not filtered. The same caution is repeated for sensitivity labels.

The reason internal builds hit this so reliably is that permission testing is done at document level only. Document listing looks correct while content leaks through the citation snippets in a chat answer.

4.2 Inherited permission changes do not follow automatically

The Azure AI Search notes on SharePoint ACL ingestion draw this distinction sharply. Changes on items with unique permissions are picked up incrementally on each indexer run, but changes inherited from a parent scope such as a site, library or folder require an explicit refresh. In other words, tightening a folder's permissions can leave the indexed permissions of the documents beneath it unchanged.

Generalised: revocation propagates far more slowly than granting. Granting gets complaints immediately; revocation gets no complaints at all, which is why it goes unnoticed.

4.3 Summaries and derivatives lose the original permissions

This is the path unique to language-model-based knowledge platforms. If the design stores a distilled summary as its own row, the summary must inherit the same access controls as the source. The Cerebras approach of distilling a thread into a one-line question, a summary and a resolution is good for retrieval quality, but if the distilled row does not inherit the channel's permissions, conclusions from a private channel can surface in summary form. Per-file summary indexes, auto-generated FAQs, embedding caches and snippets in query logs all carry the same exposure.

4.4 Side channels - logs, analytics and evaluation sets

  • Query logs. If you log full result snippets for debugging, permission to read logs becomes permission to read every document in the company.
  • Analytics dashboards. A panel listing the twenty most cited documents leaks information through titles alone. Project code names escape this way routinely.
  • Evaluation sets. Copying real document text into a golden set and committing it to a repository creates a copy fully detached from the original permissions.
  • Agent tools. When retrieval is exposed as a tool and the tool runs under a service account, the caller's identity disappears. The design has to carry user identity through to the tool call. That topic is treated separately in AI agent permission design.

4.5 Existing oversharing surfaces all at once

This is the point Microsoft repeats throughout its Copilot rollout guidance. The assistant only handles content the user can already access, but most organisations do not actually know who can access what. Broad sharing links, broken permission inheritance and abandoned sites accumulate for years, then a single natural-language question exposes them together. That is why the documentation recommends site access reviews, permission cleanup and sensitivity labelling before deployment. A knowledge platform does not create the permission problem. It makes the existing one searchable.

5. Indexing Slack - what goes in and what does not

Conversation data is the most valuable and the most dangerous source at once. Start with its properties.

5.1 Three properties of conversation data

  • Context is scattered. The question is in the first message, the clue is in the middle, the conclusion is in the last one. And the conclusion is often a single line like that fixed it, which is not retrievable on its own.
  • It is not authoritative. Agreement reached in conversation is provisional, and nobody edits the old thread when it is later reversed.
  • Everything is mixed together. Personal data, customer names, small talk and people-related remarks flow through the same channel. Unlike documents, separating them is structurally impossible.

5.2 The unit is the thread, not the message

That first property leads straight to a conclusion. In the Cerebras design, a message event triggers refetching the entire thread and storing it as a single row, after which a language model extracts a one-line question, a summary, the resolution, and the systems and code references mentioned, producing a normalised document. The trick is that the raw transcript is retained but not embedded directly. The text humans read and the representation search consumes are separated.

The published description also includes a mechanism for message runs that are not threads. Consecutive messages from one author are embedded separately with thread context prepended, so signal from tangential discussion is not lost. Layered on top is a scoring filter based on rare-token weight, message length and reactions. It exists to keep small talk out.

5.3 Indexing policy by channel type

In practice you end up needing a channel-level policy table. Below is a defensible starting default. Every organisation will adjust it.

Incident response channelsInclude after resolutionCauses and fixes recorded nowhere elseIndex after the thread closes, mask customer names
Private team channelsConditionalHigh value but permission mapping is mandatoryOnly if channel membership maps to a document ACL
Shared channels with customers or partnersExclude by defaultExternal org data, possible contractual limitsDo not open without a legal review
People, hiring and payroll channelsExcludeExposure is not recoverableSafer to keep as a no-exception rule

5.4 API constraints - internal app or distributed app changes everything

One fact bears directly on the design. Effective 29 May 2025, Slack limits commercially distributed apps that are not Marketplace-approved to one request per minute and a maximum of 15 objects per request for conversations.history and conversations.replies. The same changelog states that internal customer-built apps are not affected and retain 50+ requests per minute with a 1,000-object maximum.

For an internal knowledge platform the implication is clear. Build it as an internal app and bulk backfill is feasible; ship the same code externally and the architecture has to be redesigned. The Cerebras choice of a persistent socket connection for real-time events also reads naturally in this light: an event-push path is under far less quota pressure than periodically scraping history. Events alone, however, never fill in the past, so a separate backfill path is still required.

6. Code and tickets - the chunk boundary is the retrieval unit

6.1 Code is split on syntax boundaries

Code is not prose. A fragment cut in the middle of a function is useless to a human too. Cerebras used the open source framework CocoIndex for code indexing; it splits hierarchically along class, method and block boundaries using a syntax tree, and when a commit lands it re-embeds only the changed chunks. It is Apache 2.0 licensed with a Rust core.

Incremental re-embedding is closer to mandatory than optional. An active repository takes dozens of commits a day, and full re-embedding per commit makes cost scale with engineering activity. Keep synchronisation metadata so only deltas are processed, and build that in from the start.

6.2 Semantic chunking is not the default

On the perennial chunking question there is academic evidence. Is Semantic Chunking Worth the Computational Cost?, in Findings of NAACL 2025, evaluated semantic chunking across document retrieval, evidence retrieval and retrieval-based answer generation, and reported that the added computation was rarely justified by consistent gains. On realistic document structures, fixed-size splitting performed as well or better. Documents artificially stitched from diverse topics showed slight improvements, but inconsistently.

The practical conclusion is short. Chunking sophistication is a later problem. Start with fixed sizes and heading or paragraph boundaries for documents, syntax boundaries for code, thread grouping for conversation. The gains there dwarf the gains from semantic splitting.

6.3 For tickets, status is more signal than body text

Tickets and issues are structured and easy to attach, but noisy if ingested raw. Three treatments pay off.

  • Favour resolved tickets. Speculation in an open ticket is not authoritative. Use the status field as a retrieval signal.
  • Separate and emphasise the title and the closing comment. Embedding the whole ticket as one unit lets the initial symptom description drown the conclusion.
  • Keep the links as metadata. Ticket to pull request to deployment to incident channel is itself a strong retrieval signal.

6.4 Changing chunking is a migration

One fact routinely underestimated: changing chunk boundaries means regenerating every embedding. It costs the same as swapping the embedding model. So fix the chunking strategy early, and when you do change it, prove the improvement on an evaluation set first. Keeping raw text and metadata in a source store outside the vector database makes that regeneration far cheaper.

7. Deduplication - when the same answer appears five times

Internal data is more duplicated than the public web. The same runbook lives in the wiki, is copied into a repository README, pasted again into onboarding docs, and dropped wholesale into Slack. Index it untreated and the top ten results become five copies of the same thing. That is not a cosmetic problem, it is wasted context. Every slot taken pushes out a document with a different perspective.

Duplicate typeTypical exampleWhen to handleMethodCaution
ExactSame file at two pathsAt ingestContent hash, index one representativeDifferent paths may carry different permissions
Near duplicateCopy with a different preambleBefore indexingFingerprint similarity, pick a representativeA low threshold swallows genuinely different documents
QuotationA document pasted whole into SlackBefore indexingDrop the quoted span where it overlaps the originalKeep the added commentary around it
VersionsPolicy v1, v2, v3Keep themDistinguish by version metadataDo not delete - historical questions exist
Result-stageMany adjacent chunks of one documentAfter retrievalCap chunks per document, diversify the orderingOverdo it and the evidence is truncated

7.1 The real decision is where you remove them

Deduplication is not a yes-or-no question but a question of which stage. Removing at ingest saves both storage and embedding cost but cannot be undone. Cleaning up at the result stage is flexible, but the cost has already been paid. The practical default is exact duplicates at ingest, near duplicates before indexing, diversity adjustments after retrieval.

7.2 Duplicates you must not remove

  • Version chains. What did last year's policy say is a real, frequent query. Delete the old version and you cannot answer it.
  • Per-environment or per-region copies. Two runbooks that look nearly identical often target different clusters. This is the most dangerous place for automatic merging.
  • Translations. The same content in another language is not a duplicate but a separate entry point for different queries.
  • Contracts and legal documents. Where the original text matters, merging and summarising are not appropriate.

8. One retrieval method is never enough

8.1 Why four signals get combined

The combination Cerebras described is full-text search, embedding search, inverse document frequency and age decay. Each covers a different failure.

  • Full-text search. Catches queries that must match exactly that token - error strings, flag names, hostnames. Embeddings are surprisingly weak here.
  • Embedding search. Catches the same meaning expressed in different words. Especially useful when internal jargon and official names diverge.
  • Inverse document frequency. Separates common words from rare ones. Internal documents are heavy on boilerplate, so this correction does real work.
  • Age decay. Lifts recent threads. But note this is a ranking correction, not document governance. What to do about ageing documents is a separate problem.

8.2 RRF and the constant 60

The near-standard way to merge results from different retrievers is reciprocal rank fusion (RRF). Because it uses ranks rather than scores, retrievers on different scales can be merged without normalisation. The original paper is Cormack, Clarke and Buettcher, Reciprocal rank fusion outperforms condorcet and individual rank learning methods, SIGIR 2009, where the smoothing constant is 60. The same value appears in the Cerebras description. The constant exists to stop one or two top-ranked results from dominating the fusion.

RRF is convenient for another reason. Adding a retriever does not require relearning weights. It fits the early stage, when you are still experimenting with which signals to include.

8.3 The reranker goes last

In the Cerebras design a small reranker scores fused candidates from 0 to 10, and the top ten are expanded with surrounding context before being emitted as evidence. One practical note: the reranker is invoked once per candidate per query. Pass in more than a hundred candidates and cost and latency multiply accordingly. Candidate count is the dial that trades quality against cost directly, so you want an evaluation set before you set it.

8.4 Do not mix signals without evaluation

Combining many signals makes it easy to lose track of which one is contributing. Have at least this much in place before starting.

  • A golden set of 50 to 100 queries drawn from real logs, with humans marking the correct documents.
  • A comparison of each signal alone against the fused result. A signal that contributes nothing alone only adds cost.
  • Measurement split by query type. Exact-token, conceptual and people-finding queries are served by different signals.
  • A log schema that records the document IDs cited in each answer. Without it you cannot reconstruct anything later.

9. Four places where the initial build cost explodes

Budget overruns rarely come from unexpected line items. They come from misjudging the size of expected ones. Work out these four in advance.

Cost itemWhen it occursWhat drives growthHow to control it
Initial backfill embeddingAt build, and again on every strategy changeDocuments x chunks x retriesCap the time window, allowlist channels and repos, expand in stages
Per-ingest language model summarisationContinuousInternal activity, not query volumePre-filter on length and reactions, use a lighter summarisation model
Per-query planning and rerankingContinuousQueries x tool calls x candidatesKeep tools simple and LLM-free, cap candidate count
Human timeBefore and during early buildSources x permission complexity x number of teamsShrink pilot scope, settle exclusion lists first

9.1 Backfill is not a one-time event

Treating the initial embedding cost as one-off is the first mistake. Change the chunking strategy, change the embedding model, or change the summarisation prompt, and full regeneration follows. In the first year that happens several times. Which is why making re-indexing a job you can rerun at any moment, rather than a one-off script, is the cheapest choice in the end.

9.2 Beware costs tied to internal activity

Calling a language model to summarise every ingest event does help retrieval quality. In exchange, cost grows independently of usage. In a week when nobody searches, an active company still generates the bill. That is why pre-filtering matters. Filter on length, rare tokens and reactions so that only what is worth summarising reaches the model.

9.3 The underestimated item is always human time

Permission cleanup, owner assignment, agreeing on exclusion lists, legal and security review, negotiating channel policy. None of these can be reduced by code, and they scale with the number of teams. Items requiring cross-department agreement are effectively impossible to schedule. This is the strongest single argument for a narrow pilot.

10. Sources you should not connect - exclusion is the cheapest design

The most common bad default is connect everything and remove it if there is a problem. It is bad because removal is not symmetric with addition. Adding is one batch job; removing has to chase embeddings, summaries, caches, logs, evaluation sets and answers the model has already produced. Deleting exposed information from an index does not delete it from the memory of whoever read it.

10.1 Five criteria for exclusion

  • Principals cannot be enumerated. A source where an API cannot tell you who may read each document is not an indexing candidate.
  • There is structurally no authority. Spaces that only accumulate drafts, and personal working folders, cannot serve as answer evidence.
  • Exposure is unrecoverable. Performance reviews, payroll, hiring evaluations, legal advice, unreleased financials. Search convenience does not offset those.
  • There is no query demand. Areas nobody asks about do not get used once connected. Bot alert channels are the archetype.
  • Upkeep exceeds value. An internal database with a frequently changing schema keeps breaking its connector, and a broken connector quietly serves stale data.

10.2 A list worth excluding by default

  • Direct messages and personal channels or folders
  • Spaces for people operations, hiring, payroll and reviews
  • Vulnerability trackers and incident response records
  • Operational tables containing customer personal data (index the schema and column descriptions only if needed)
  • Legal advice and in-progress contract negotiations
  • External channels shared with customers and partners
  • Draft spaces that accumulate endless versions, such as design mockups and marketing copy

When something on this list is opened, treat it as a decision to change the default and record who approved it.

11. How to scope the pilot

The last borrowable device from the Cerebras design is the notion of a project: a named bundle of specific Slack channels, repositories, databases and document spaces, from which users pick a default matching their domain. The same source can belong to several projects without duplication, and queries operate within that scope by default.

That idea maps directly onto pilot design. Do not try to build company-wide search. Finish search for one team. There are four axes for cutting scope.

  • People. One team, 20 to 50 individuals. Small enough that you can collect feedback directly.
  • Sources. Two or three. One repository, one wiki space, three or four Slack channels is about right.
  • Time. Cap the backfill at the last 12 to 24 months. This reduces cost and stale-data problems at once.
  • Queries. Write down the question types you intend to serve. Incident cause lookup, procedure confirmation and finding the right person is a reasonable narrowing.

11.1 Write the success and stop criteria first

  • Success criteria. Weekly active user share and the share of answers where the cited document was actually opened track perceived usefulness better than a satisfaction survey.
  • Stop criteria. Put a clause in the pilot document stating that a single permission incident halts the pilot until the cause is understood.
  • Cost ceiling. Write the backfill and monthly operating caps as numbers. Pilots that start without a ceiling usually end without one.
  • Expansion conditions. Decide in advance what has to be true before the next source is attached. No additions until the current sources are stable is a common form.

12. Pre-adoption decision checklist

The decisions covered here, collected in checkable form. Answering them in writing before you start avoids most of the rework.

  • Have you decided explicitly whether to move data or only unify the schema
  • Have you confirmed, per source, that principals can be enumerated through an API
  • Have you chosen a permission approach per source (early binding, late binding, delegation)
  • Have you actually tested that permission metadata follows each chunk after splitting
  • Do you know, per source, when inherited permission changes take effect
  • Do model-generated summaries and derivatives inherit the source permissions
  • Have you checked that query logs and analytics screens do not become new exposure paths
  • Does a written Slack channel include and exclude policy exist
  • Do you treat conversation at thread level or message level
  • Have you chosen the deduplication stage and listed the duplicates that must survive
  • Have you capped the backfill window
  • Have you distinguished costs that scale with queries from those that scale with internal activity
  • Is re-indexing a job you can rerun at any time
  • Have you prepared an evaluation golden set and a cited-document log schema first
  • Is the default exclusion list agreed, and is there an approval path for exceptions

Conclusion: what gets decided before retrieval quality

The thing you will spend the longest on while building an internal knowledge platform is retriever tuning, yet the decisions that determine success are settled far earlier. Which sources you connected, where permissions are evaluated, and what you deliberately left out. Once those three are set, the range a retrieval algorithm can move is narrower than it feels.

What is worth taking from the Cerebras case is not a specific technology stack either. They did not ask anyone to move data, did not trust a single retrieval signal, kept the tools simple, and scoped queries with projects. All four are designs that follow from accepting organisational and cost constraints first. The approaches that fail are usually more technically ambitious: ingest everything at once, add permissions later, look at cost later.

One balancing note to close. What this article organises is a list of decisions, not a set of correct answers. The published case reports a usage figure of 15,000 queries a day and no accuracy metrics, and there is no guarantee the same configuration produces the same outcome elsewhere. Different data distributions and permission cultures produce different optima. One thing is certain: adding connectors is the beginning of this project, not the halfway mark.
