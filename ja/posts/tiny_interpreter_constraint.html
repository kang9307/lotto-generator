きっかけ - 1,024 バイトはなんの大きさか

この角度を取らせたのは、オースティン・ヘンリーが 2026 年 9 月 6 日に出した記事である。題は 1024 バイトで Python インタープリターを作る、で、本文の冒頭に条件が付いている。マクロもライブラリの小細工もなしで C コード 1,024 バイト。この一文にすでに三つのことが入っているのに、紹介文だけを読むと三つとも抜け落ちる。

第一に、1,024 は C のソースファイルの大きさである。コンパイル結果物ではない。リポジトリには読める版とゴルフ版が別々に入っていて、ゴルフ版がちょうど 1,024 バイト、読める版は 4,800 バイトを超える。二つの版は同じ言語を実装している。違いは表記だけである。

第二に、その大きさは 自立した値ではない。著者が並べたバイト節約の手口のなかに、コンパイラが libc をリンクしてくれることに寄りかかるという項目がある。ソースから消えた文字入出力のコードは無くなったのではなく、別の予算へ移っただけである。この区別を落とすと、1,024 バイトがまるで実行に必要な全部であるかのように読める。

第三に、実行されるものは Python ではない。著者本人が、言語全体を 1,024 バイトに収めるのは不可能だと釘を刺し、目標を Python のように見えるものへ取り直している。根拠に挙げるのは def とコロンとインデントと括弧なしの条件だ。つまり 文法の見た目が最初から狙いだった。

ビルド条件も大きさの一部である。リポジトリが示すコマンドは次のとおり。

gcc-16 -std=gnu89 -w python1024.c   # C89 に戻し、警告を切る
./a.out < fizzbuzz.py               # 実行するプログラムは標準入力から入る
wc python1024.c                     # リポジトリが示す大きさの確認方法

-std=gnu89 が要る理由は後でまた出てくる。ゴルフの手口のなかに、C89 の暗黙の int 宣言と暗黙の戻り値型に頼る項目があるからだ。-w はその代償として降り注ぐ警告を切るスイッチである。リポジトリは Clang ではなく GCC を使うと書いている。同じソースがすべてのコンパイラで同じ結果を出すわけではないという意味だ。

まとめるとこうなる。1,024 バイトとは、特定のコンパイラと特定の標準のもとで、libc がリンクされるという前提の上で、Python に似た文法の部分集合を実行する C ソース一ファイルの大きさである。この条件抜きに 1,024 バイトで Python が動くとだけ移すと、四か所で間違える。数値そのものは正しいのに、その数値が指す対象と成立の前提がすべて入れ替わってしまうからだ。大きさの話でいちばん壊れやすいのは数字ではなく、数字に付いていた但し書きのほうである。

インタープリターが最低限そなえる五つの層

実装の種類にかかわらず、インタープリターは五つの仕事をする。それぞれを極端に絞ったらなにが残るかを先に押さえておけば、後に出る一覧が羅列ではなく地図として読める。

  • 字句解析 - 文字列を意味の単位に切る。極端に絞ると文字一つがそのままトークンになる。名前の長さの上限を 1 に縛れば、この層はまるごと消える。
  • 構文解析 - トークンの並びが文法に合うかを判定し、構造を作る。極端に絞ると構造を作らず、読んだそばから計算する。再帰下降パーサーが値を返せば木は要らない。
  • 評価 - 構造を実際の動作に変える。ここは削る余地が最も少ない。この層が無ければ、それはインタープリターではなく文法チェッカーである。
  • 環境 - 名前と値をつなぐ。極端に絞ると配列一つになる。名前が一文字なら、その文字のコード値がそのまま配列の添字だ。
  • エラー処理 - 規則から外れた入力を捕まえて知らせる。極端に絞ると 0 バイトになる。五つのうち唯一、完全に無くせる層である。

最後の項目が肝である。ほかの四つはどれだけ絞ってもなにかは残る。評価が 0 なら実行できず、環境が 0 なら変数が無く、構文解析が 0 ならなにを計算するのか分からない。エラー処理だけが 0 まで行ける。だからそれが一番に行く。言い換えれば、捨てる順序を決めているのは設計者の好みではなく、その層が 0 まで縮められるかどうかという性質のほうである。好みが入り込むのは、0 まで行ける層が複数あるときだけだ。

先に捨てられるものの順序

ここがこの記事の中心である。予算が縮むとき層が消える順序には規則があり、その規則は 正常な経路への寄与である。

1エラー処理と診断メッセージまったく無し誤った入力での動作が未定義になる完全に不在
2標準ライブラリ使っていなければ無しプログラムができることの幅print 一つ
3性能と中間表現結果は同じで時間だけ延びる反復のコストと静的解析の可能性トークンも木も無し
4名前の長さと名前空間名前を縮めれば無し規模と可読性とスコープ小文字一文字、隔離なし
5文法に付いた数量の制限式を分ければ無し表現力比較は一つの式に一つ
6文法の形その言語でなくなる同一性手を付けない

正常な経路に寄与しない層が先に行く

エラー処理は正しいプログラムでは一度も実行されない。消しても正常なプログラムはそのまま動く。これが一位である第一の理由だ。

第二の理由は物理的である。診断の中身は文字列であり、文字列は予算をそのまま食う。論理は圧縮できるがメッセージは圧縮されない。二十七文字の文句一つで 1,024 バイト予算の 2.6 パーセントだ。予算全部を文句だけで埋めても三十八行が限界である。コードゴルフのどの手口もこの壁を越えない。

代償は正確に述べる必要がある。エラー処理を消すと、誤った入力でなにも起きなくなるのではなく なにが起きてもおかしくない状態になる。原文も、コードが正しいという強い仮定の上に立っていると書く。キーワード認識がその例だ。

if (ch == 'w' || ch == 'i' || ch == 'f') {
    int keyword = ch;
    int loop_var = 0;

    if (keyword == 'f') {        /* "for K in range(N):" の形 */
        pos += 2;                /* "or" を飛ばす             */
        loop_var = next();
        pos += 8;                /* "inrange(" を飛ばす       */
        vars[loop_var] = 0;
    } else if (keyword == 'w')
        pos += 4;                /* "hile" を飛ばす           */
    else
        pos += 1;                /* "if" の "f" を飛ばす      */

最初の一文字だけを見て、残りは 数えて飛ばす。実際にそこへ for と書かれているかは検査しない。fog と書いても同じ経路をたどる。これがエラー処理 0 バイトの実際の姿である。

言語の外にあるものが次に来る

標準ライブラリは文法を変えずに抜ける。これが二位である理由だ。MicroPython が自分の範囲を標準ライブラリの小さな部分集合を含むと書きながら、それでも Python 3 の実装だと言える根拠がこの性質である。ライブラリを縮めても言語の同一性は揺らがない。

1,024 バイト版は print 一つだけを残した。それも文字列リテラル一つか整数式一つだけを受ける形である。ここで落としやすい点が一つある。Python において print と range は キーワードではない。リファレンスが並べる三十五個の予約語にどちらも無い。二つは束縛し直せる名前だ。ところが名前が一文字に縛られた世界では、その性質が成り立たない。先のコードのとおり、range は八文字を飛ばす固定のパターンになっている。ライブラリ関数が文法へ固まった。

同じ結果を遅く出すものが三番目だ

性能は正しさの観測対象ではない。遅くなったプログラムも依然として正しい答えを出す。だから三位である。ここで切られたのはコンパイル段階の全体だ。原文は CPython がトークン化、構文木の生成、解析、最適化、バイトコードの放出、解釈の順に働くと書き、自分の実装はそのパイプラインを使わないと明かす。

ただし三位がつねに真とはかぎらない。実時間制御では性能が一位で守られ、むしろ機能が先に切られる。順序を決めるのは層の性質ではなく制約の種類である。この記事の順序は、大きさが上限であるときの順序だ。

文法が最後まで残る理由

文法が最後である理由は二つある。

第一に、文法が消えると、それをなんの言語だと言う根拠が消える。著者が 512 バイトで方向を変えた箇所がそれを示す。加算式から始めて代入式を入れ、条件文まで入れたのに、その成果物は Python インタープリターではなく電卓だという判断が出た。層はすべて揃っていた。無かったのはそれを Python と呼ぶ根拠のほうだ。だから目標を 512 から 1,024 へ動かした。

第二に、文法は実装の予算を使わずに手に入る唯一の資産である。読む人の頭のなかにすでに設置されているからだ。def とコロンとインデントを見れば、人はそれを Python として読む。実装の側はその認識を作り出すのに一バイトも使わない。逆にエラーメッセージは読む人の頭のなかに無く、全部をバイトで支払うしかない。

そして実際に切られたのは文法の形ではなく、文法に付いた 数量だった。Python リファレンスは比較を任意に連鎖できると明記する。C と違ってすべての比較演算の優先順位が同じで、三つの値を並べた式は数学で使うとおりに解釈されるという条項だ。1,024 バイト版の対応一覧は比較を 一つの式に最大一つと釘を刺す。演算子は生き残り、連鎖だけが死んだ。

著者は比較式そのものをほとんど外しかけたと書く。根拠は真偽の判定が代わってくれるということだ。剰余が 0 かを問う代わりに、剰余そのものを条件に入れればよい。文法を消して意味論で返す取引だが、この取引ができたのは Python が整数の 0 を偽として扱うからである。捨てられる文法の範囲を決めたのは意味論だった。

Python インタープリターという言葉が覆う範囲

実装がどの層まで同じかを分けると三層になる。文法、意味論、標準ライブラリ。この三つをひとまとめにすると、どんな主張も真に見える。

層同じであるとはどういうことか1,024 バイト版確かめ方
文法同じソーステキストが文法に合うと判定される部分集合のみ。しかも名前の長さ制限が付く同じファイルが両方で読まれるか
意味論同じソースが同じ結果を出す整数の範囲とスコープで分かれる大きな数と関数内の変数で試す
標準ライブラリ同じモジュールと組み込み関数があるprint 一種類の形だけインポート文が存在するか

原文はこの三つのうち 文法の見た目だけを主張する。それも部分集合だと自分で書いている。Python のように見えるものが目標だと明示した一文が、その主張の範囲だ。著者はこの線をぼかさなかった。

線がぼやけるのはたいてい移す側である。1,024 バイトで Python インタープリターという一文は三層を区別しない。同じ罠はほかの実装にもある。ある道具は文法だけが同じで、ある道具は意味論まで合わせようとしてホスト言語と衝突し、ある道具は標準ライブラリをどれだけ移したかが実際の争点になる。ホスト言語の上に別の言語を載せる実装がどこで詰まるかは glojure を扱った記事で別に触れ、コンパイル言語に対話的実行を付けるとき解釈実行とコンパイル実行が分かれる地点は Go インタープリターを扱った記事にある。

一文字の変数名が一緒に消すもの

名前を一文字に縛る決定は、見かけ上は大きさの最適化である。実際には 意味論の変更だ。

得るものから見るとこうなる。Python リファレンスの名前規則は開始文字と後続文字を分け、長さの上限を置かない。その規則を守るには、名前を読む繰り返し、名前を入れるバッファ、名前を比べる関数、そして名前が何個まで増えるか分からないのでハッシュテーブルかそれに準じるデータ構造が要る。名前を一文字に縛れば、その全部が消える。

char src[999];       /* ほとんどの空白を抜いたプログラム全体 */
int  vars[256];      /* シンボルテーブル                     */
int  pos;            /* src で次に読む文字の位置             */
int  ch;             /* いま見ている文字                     */
int  line_start;     /* 現在の行が始まった位置               */

シンボルテーブルが int vars[256] の一行だ。参照は文字のコード値を添字に使う一回の配列アクセスで終わる。ハッシュの計算も、衝突の処理も、文字列の比較も、メモリの確保も無い。

ところが 一緒に消えるものがある。原文の対応一覧はインデント基準のブロックを書きながら、スコープの隔離が無いと括弧で添える。Python の実行モデルは、ブロックのなかで名前が束縛されればそれはそのブロックのローカル変数だと定める。グローバルな配列一つが全部の世界では、この条項が成り立たない。関数の内で使った名前と外で使った名前が同じ枠を見る。

さらに 同じ枠に種類の違う値が入る。関数定義はその関数本体のソース位置をシンボルテーブルへ格納する。つまり vars[k] は整数かもしれないしコード位置かもしれない。どちらかを区別するタグは無い。型が無いのではなく 型を確かめる場所が無いのである。整数と同一性比較が絡む場所は CPython でも人を驚かせるが、その話は 整数キャッシュを扱った記事に別途まとめてある。

トークンも構文木もなく - 巻き戻して読み直す実行

構文解析の層を縮める最も強い方法は 構造を作らないことである。再帰下降パーサーは本来は木のノードを返すが、ノードの代わりに値を返させれば木の全体が要らなくなる。

int parse_sum(void) {
    int value = parse_term();
    while (ch == '+' || ch == '-') {
        if (ch == '+')
            value = value + parse_term();
        else
            value = value - parse_term();
    }
    return value;
}

戻り値の型が int だ。この一語が設計の全体を決める。読んだそばから計算するので中間表現が無く、中間表現を作って歩いて解放するコードも全部無い。代わりに ソーステキストそのものが実行の状態になる。

だから制御の流れがソース位置を動かす方式で実装される。コンパイル段階が無いので飛ぶ先のアドレスが無く、代わりに pos を巻き戻す。反復文は条件式の位置を覚えておき、本体の実行が終わればその場所に戻って もう一度パースする。関数呼び出しは呼び出し地点を保存して関数本体の位置へ飛び、本体が終われば保存した場所へ復帰する。pos 一つがプログラムカウンターの役を果たす。

ブロックの境界はインデントが決める。

void run_block(int min_indent) {
    for (;;) {
        int indent = read_indent();

        if (ch == '\n')
            continue;

        if (indent < min_indent || ch == 0) {
            pos = line_start;
            return;
        }

ここにこの実装で最も興味深い取り替えがある。Python リファレンスはインデントの処理を スタックとして規定する。ファイルの最初の行を読む前に 0 を一つ入れ、値は下から上へつねに増え、インデントが減ったらその値は 必ずスタックにすでにある値のどれかでなければならない。この最後の条項が、インデントの食い違ったコードを捕まえる規則である。

1,024 バイト版はそのスタックを作らない。run_block が自分自身を再帰呼び出しするので、C の呼び出しスタックがその役を代わりに務める。ブロックの入れ子の深さと再帰の深さが一対一に対応するのだから、データ構造を別に置く理由が無い。言語が要求するデータ構造を、ホスト言語のデータ構造で返したわけだ。

ところが スタックを捨てると、そのスタックがしていた検証も一緒に消える。すでに現れたインデント値の一覧が無いので、減ったインデントが有効な値かを問えない。食い違ったインデントは誤りになる代わりに、どこかのブロックへそのまま付く。ここがこの記事で最も一般化できる観察だ。データ構造はたいてい検証を兼ねている。なにを捨てるか決めるとき実際に数えるべきものは、そのデータ構造が占めるバイトではなく、それが静かに行っていた検査の一覧である。

小ささは一種類ではない

小さいという言葉は、少なくとも四つの互いに違う軸を指す。軸を明かさない大きさの数値は比較に使えない。

軸なにを測るか圧迫される場所縮める方法
ソースのバイト人が読んで監査する量コードゴルフ、初期段階のブートコード識別子と空白と構造そのものを削る
バイナリの大きさストレージとフラッシュの占有組み込みファームウェア、コンテナイメージ機能をビルドから外し、リンカで取り除く
常駐メモリ実行中の RAM 使用量マイクロコントローラーデータ構造と回収の戦略を変える
依存の数移植性と供給網と監査のコストサンドボックス、閉域網外部ライブラリを使わず自前で実装する

1,024 バイトは 一つ目の軸だけを測った値である。しかも libc のリンクに寄りかかっているので、二つ目の軸と四つ目の軸ではむしろ悪い。ソースから抜けたものをリンカが埋める。

ほかの実装が自分の大きさをどの軸で語るかを見ると、対比が鮮やかになる。

  • MicroPython - コード領域 256k と RAM 16k のなかに収まって動くと書く。二つ目の軸と三つ目の軸を 別々に明かす。マイクロコントローラーでは二つが別の資源だからだ。
  • Lua - 64 ビットの Linux で標準ライブラリをすべて含めてビルドしたインタープリターが 293K、ライブラリが 484K だと書く。ソースは C でおよそ 3 万 2 千行、配布の圧縮物は 390K である。行数ではなく ビルド成果物で大きさを語る。
  • QuickJS - ファイルが数個だけで外部依存が無く、簡単なプログラム一つが x86 コードで 367 KiB だと書く。大きさと 依存の数を一文に並べている。

三つの数値は互いに比較できない。軸が違い測定の条件も違う。Lua の 293K にはプラットフォームが明記され、QuickJS の 367 KiB にはアーキテクチャと対象プログラムが付き、MicroPython の 256k は成果物の大きさであってソースの大きさではない。大きさの数値を移すとき 条件を外せばその値は偽になる。

実際に小さく作る場所

小さく作ることが趣味ではなく要件である場所がある。ところが場所ごとに求める小ささが違い、だから捨てる順序もひっくり返る。

マイクロコントローラー - 上限は RAM である

ここでは三つ目の軸が支配する。そして先に立てた順序がちょうど一か所でひっくり返る。MicroPython は自分の特徴として対話プロンプト、任意精度整数、クロージャ、リスト内包表記、ジェネレーター、そして 例外処理を挙げる。1,024 バイト版が真っ先に捨てた層を、MicroPython は看板として掲げる。

理由は明確だ。マイクロコントローラー上のプログラムは 人が付いていない場所で動く。誤った入力が来たときになにが起きてもおかしくない状態は、ここでは許されない。代わりに別のものを削る。標準ライブラリを小さな部分集合に縮めると自ら明かすほうがそれだ。端末側でなにかを載せるとき RAM が実際にどこで上限を引くかは ESP32-S3 で小さなモデルを動かした実測の記事に数字で整理してある。

初期段階のファームウェア - 上限が規格で釘打ちされる唯一の場所

起動の最初の段階は、大きさの上限が規格に書かれている珍しい場合である。ここでは順序そのものが成り立たない。なにを捨てるかではなく なに一つを残すかの問題になる。最初の段階は自分では仕事をしない。次の段階を呼べるだけのことをして退く。

この場所から学ぶのは 機能を捨てるほうが層を捨てるより強いという事実だ。層を削れば同じ仕事を悪くこなすが、機能を移せばその仕事をまるごと別の場所でやることになる。先の libc の話と同じ構造である。

サンドボックス - 小ささとは監査できる量である

信頼できないコードを動かす場所で小さいという言葉は、バイトではなく 読めるコードの量を指す。QuickJS がファイル数個と外部依存の無さを前面に掲げる理由がそれだ。攻撃面はソースの大きさではなく依存グラフの広さで増える。

ところが同じページが ES2025 をほぼ完全に支え、標準テスト群のほぼ 100 パーセントを通ると書きもする。つまり ここでは文法も意味論も捨てない。捨てるのは四つ目の軸、依存だけである。信頼できないコードを受ける場所で言語仕様を部分集合に縮めると、その部分集合の境界そのものが新しい脆弱性になる。

教育 - 小ささとは一人が追える量である

教えるための実装で小さいとは、一日で読み切れる分量を指す。ここで捨てるのは性能と最適化だ。逆に 最も大きく残すのが段階の名前である。字句解析と構文解析と評価がそれぞれ目に見えなければならない。

対比が劇的である。コードゴルフはトークンと構文木を真っ先に消し、教育用の実装はまさにその二つを最も大きく残す。同じ小さく作るなのに正反対へ向かう。目的が軸を決め、軸が順序を決める。

コードゴルフと最小実装は別の仕事である

原文に出てくるバイト節約の手口は次のとおりだ。

  • 変数と関数の名前を一文字に縮める
  • コンパイラが libc をリンクしてくれる事実に寄りかかる
  • 一時変数の代わりにグローバル変数を使う
  • グローバル変数が 0 で初期化される性質を利用する
  • C89 の暗黙の int 宣言と暗黙の戻り値型を使う
  • 関数の仮引数をスタックに保存される一時変数として使う
  • 文字リテラルの代わりに ASCII 値を直接書く
  • 三項演算子とカンマ演算子を使う
  • 論理演算をビット演算に置き換える

この九つには共通点がある。どれ一つとして言語の動作を変えない。すべて表記の水準の変換である。だから 4,800 バイト版と 1,024 バイト版は同じ言語を実装している。

/* 行末まで飛ばす関数 - 読める版 */
void skip_to_eol(void) {
  if (ch != 0 && ch != '\n') {
    next();
    skip_to_eol();
  }
}

/* 同じ関数のゴルフ版 */
Y(){c&&c-10&&Y(G());}

/* 先に出た parse_sum のゴルフ版 */
e(){for(z=t();c-43u<3;)y=44-c,z+=y*t();return z;}

一方、一文字の変数名、エラー処理の不在、スコープの隔離の欠如はゴルフではない。設計の決定である。表記をいくら変えてもこの三つは縮まない。

区別する方法は簡単だ。戻したときに動作が変わるか。変わらなければゴルフ、変われば設計である。4,800 から 1,024 へ行ったのはゴルフで、Python から Python に似たものへ行ったのは設計だ。二つの仕事を一つの名前で呼ぶと、どちらの教訓も残らない。

そしてゴルフには ビルド条件という隠れた費用が付く。C89 の暗黙の int に頼るには標準を戻さねばならず、そうすると警告が降り注ぐので警告を切らねばならず、その組み合わせが通るコンパイラが限られる。リポジトリが Clang ではなく GCC を使うと書く理由である。大きさの数値を移すときこの条件を外せば再現しない。コンパイラの後段を替えるときどんな請求書が新たに生じるかは LLVM 基盤の Go コンパイラを扱った記事で別の角度から突いた。

自分のコードで無くてよいものを探す順序

ここまでの順序を自分のコードへ移すとこうなる。手口の一覧ではなく 問いの順序である。

順位候補判別の問い戻すコスト
1診断とログと統計消しても正常経路の結果が同じか低い。また入れ直せばよい
2誰も呼ばない機能対応一覧と呼び出し記録が一致するか低い。また入れればよい
3同じ結果を速く出す経路遅くなっても答えが同じか中くらい。時間は取り戻せる
4名前と構造と一般化規模が増えても持ちこたえるか高い。読む人の時間で支払う
5インターフェイスと契約これが無くても同じものか非常に高い。同一性そのもの

実務でこの順序をそのまま使うとき、付く但し書きが三つある。

  • 一位は消すのではなく切れるようにすることである。1,024 バイト版はエラー処理をまるごと無くしたが、それが成り立つのは入力が著者自身のファイル一つだからだ。他人が使うコードで同じ決定をすれば、ゴルフではなく事故である。
  • 二位の判別は文書ではなく記録で行う。対応一覧はたいてい実際より広い。呼び出し記録と突き合わせて初めて、どれが死んだ機能かが分かれる。
  • 四位からは戻すコストが急に上がる。名前を縮めれば今は減るが、そのコードをまた読む人の時間で支払うことになる。その支払いが一度で終わらない点が、ゴルフと製品コードの違いだ。

そして順序を決める前に書き出しておくべきものがある。一緒に付いて出るものの一覧だ。インデントのスタックを消せばインデントの検証が一緒に消え、シンボルテーブルを配列に替えればスコープが一緒に消え、中間表現を消せば静的解析の可能性が一緒に消える。三つとも消えたのはデータ構造一つなのに、失ったのは二つである。バイトを数える前に、そのデータ構造が静かにやっていた仕事を数えるほうがよい。

最後に順序をひっくり返す条件だ。上限がなにで引かれているかが決める。RAM ならデータ構造から、監査の対象なら依存から、規格なら機能から手を付ける。大きさが上限であるときにだけ、この記事の順序がそのまま成り立つ。だから自分の現場に当てはめる前にまず答えるべき問いは、なにを削るかではなく、そもそもなにが上限を引いているのかという一つである。その一つが決まらないうちに削り始めると、いちばん安全に削れたはずの層を最後まで残したまま、いちばん高くつく層から手を付けることになる。

確認できなかったこと

  • コンパイル済み実行ファイルの大きさ - 原文にもリポジトリにも無い。1,024 はソースの大きさであり、実行ファイルの大きさはコンパイラとプラットフォームとリンクの方式によって変わる。この記事でバイナリの大きさを語らなかった理由である。
  • 大きさ確認コマンドの正確な判定 - リポジトリは wc で大きさを見るよう書く。このコマンドは行と語とバイトの三つの値を一緒に出すので、1,024 がそのうちどれなのかはコマンドだけでは断定できない。本文は原文が明かしたバイト数をそのまま移した。
  • gcc-16 が指す正確なインストール物 - どのディストリビューションのどのパッケージなのか、別のバージョンでも同じ結果になるのかは、リポジトリが書いていない。
  • コメントの文法 - 対応一覧にコメントの対応が入っているが、それが Python リファレンスの定めるハッシュ記号の規則と同じ形かは、原文の記述だけでは分かれない。
  • CPython のパイプラインの公式記述 - Python 開発者ガイドのコンパイラ文書は、二度の要求でいずれもリダイレクトの案内だけが返ってきた。本文の CPython の段階の記述は原文の著者が書いた表現を移したものであり、言語規則に関する記述はすべて公式の言語リファレンスと標準ライブラリ文書から取っている。
  • 実行速度の数値 - 巻き戻して読み直す方式が実際にどれだけ遅いかの測定値は原文に無い。反復のたびに読み直すという構造的な事実だけを述べた。
  • 起動の最初の段階の規格上の大きさの上限 - 広く引かれる数値はあるが、規格の原文と突き合わせていないので数字は書かなかった。
