はじめに: ログの空欄ひとつから始まる判断

登録者一覧に毎日ほぼ同じ時刻ごろ、アカウントがいくつか増えている。投稿もしないし再ログインもしない。アクセスログを開くと、そのアカウントが作られたリクエストのUser-Agent欄が空になっている。次に浮かぶ考えはたいてい一つだ。User-Agentが空なら拒否しよう。

その一行は実際にゴーストアカウントを減らす。同時に、何の音もなく本物のユーザーの一部を外へ追い出す。弾かれた人はサポートに問い合わせず、ただタブを閉じるので、指標には「ブロック成功」だけが残り「失った人」は残らない。

この記事はその一行を入れる前に知っておくべきことを扱う。クライアントが送る値でなぜ人間と自動化を分けられないのか、では何を見るべきか、そして精度ではなく誤ったときのコストで対応強度を決める設計がなぜ実務で持ちこたえるのかまで行く。攻撃側の手口は扱わない。

1. 空のUser-Agentはボットの証拠ではない

HTTPの意味論を定義するRFC 9110は10.1.5節でA user agent SHOULD generate a User-Agent header fieldと書いている。SHOULDであってMUSTではない。送らなくても違反ではない。

同じ節はa user agent MAY allow its User-Agent value to be configured by the userと付け加える。値をユーザーが変えることも仕様が想定した動作だ。この欄は最初からクライアントが埋めても空にしてもよい場所として設計されており、だからこそ現実のトラフィックではさまざまな理由で空になったり奇妙になったりする。

ログで観察されるものよくある原因自動化か
値なしブラウザではないネイティブアプリやモバイルSDKの接続違う。自社アプリの利用者だ
値なし社内プロキシやセキュリティゲートウェイのヘッダー正規化違う。法人顧客のトラフィックだ
単純または空の値プライバシー拡張や設定で値を消した利用者違う。意図的な選択だ
見慣れない古い文字列組み込み機器、スマートテレビ、キオスク端末おおむね違う
ツール名が入った値コマンドラインツール、APIクライアント、連携スクリプト自動化だがたいてい正当なものだ
完全なブラウザ文字列実際のブラウザか、ブラウザを動かす自動化この値では区別できない

表の最後の行がこの節の結論だ。空の値は自動化の証拠ではなく、完全な値は人間の証拠ではない。両方向とも崩れているので、この欄ひとつではどちらにも判定できない。

  • 送ることは推奨であって義務ではない - なくても正常なリクエストだ
  • 値の内容はクライアントが決める - 設定で変えることも想定された動作だ
  • サーバーが値を検証する手段がプロトコルにない - 照合すべき原本が存在しない

2. 偽装は自由 - 主張であって証拠ではない

三番目の項目が核心だ。User-Agentはクライアントが自分で書いて送る自己紹介であり、サーバーには照合する原本がない。クライアントが送った値を信頼境界の内側に入れてはいけない理由がここにも当てはまる。リクエストボディの価格フィールドを信じてはいけないのと同じ理由で、ヘッダーの身元の主張も信じられない。

ブラウザの文書を作る側もこの値で分岐する慣行を戒めている。MDNはUser-Agentの文書の冒頭に、ブラウザごとに違うコンテンツを返すのがたいてい悪い考えである理由を別途読むよう警告を置いており、このヘッダーが特定のユーザーエージェントを識別してフィンガープリンティングに使われうると書いている。

その結果が値の縮小だ。ブラウザ各社はこのヘッダーに載る情報を意図的に減らし、さらに必要なら別のヒント方式で要求するよう案内している。この文字列で何かを区別するルールは時間が経つほど解像度が落ちる。

2.1 それでも残っている使い道

役に立たないという話ではない。アクセスを許可し拒否する単独の根拠にできないという意味であって、値そのものは三つの場所で今も働いている。

  • 統計と監査 - どんなクライアント構成がサービスに来ているかを把握する用途。判定に使わないので偽装可能性は問題にならない
  • 自らを名乗るクローラーの識別 - 検索クローラーはたいてい名前と案内先を値に書く。ただし確認は別の軸が行う必要がある。グーグルは検証の文書で、逆引きの後に正引きで辿り直す方法と、公開されたアドレス帯に照合する方法を案内している
  • 候補を絞る - どこをさらに見るかを決める手がかり。判定は後に来る軸が行う

まとめると - 自らを名乗るボットは名前で見分けられるが、名乗らないと決めた自動化はそうはいかない。User-Agentベースのルールは正直な側だけをふるい落とす非対称を作る。正直なクローラーへの方針はrobots.txtで宣言するほうがよい。

3. 誤ブロックのコスト - 静かに去っていく人たち

ブロックルールを評価するときによく見る数字は「ブロックした件数」だ。この数字はルールが正しく働いているかは教えてくれない。知るべきなのはブロックされたもののうち人間がどれだけ混ざっていたかだが、それは標準のログには残らない。誤ブロックが危ういのは静かだからだ。

  • ボットは失敗しても再び来る。再試行が既定なので、ブロックは自動化の総量を減らすうえで思ったほど効かない
  • 人間は失敗すると戻ってこない。登録画面で一度拒否された人が再挑戦する割合は高くない
  • 不満がこちらに届かない。問い合わせにはたいていログインが必要で、登録で弾かれた人にアカウントはない
  • 共有アドレスの後ろに人が多い。通信事業者単位のアドレス共有や企業プロキシのため、一つの送信元の後ろに数百から数千人がいることがある

ここにアクセシビリティの問題が重なる。支援技術、低スペック機器、細い回線、自動入力やパスワード管理ツールを使う利用者は「人間らしくない」パターンを自然に作り出す。判別器を精緻にするほどこの層が先に引っかかりやすい。検証方式がどんどん重くなる流れで繰り返し指摘される問題も同じだ。

だからルールを入れる前に踏む段階が観測モードだ。ルールを適用せず、適用されていたらどのリクエストが引っかかったかだけを記録する。一日二日分を目で追えば、自社アプリの利用者や法人顧客が混ざっているかはたいていすぐ見える。この段階を飛ばしたルールは、自分が何を切り落としたかを教えてくれない。

4. シグナルを組み合わせる - 行動・ネットワーク・時間

では何を見るのか。軸は大きく三つあり、三つとも単独では弱いことが前提だ。

4.1 行動 - 入力の速度と順序

  • 人はフォームを上から下へ一度で埋めない。戻って直すし、フィールド間の間隔がばらつく
  • タイピングと貼り付けが混ざり、画面の外へフォーカスが移って戻ることも多い
  • 自動化はたいてい均一だ。ただし均一さはパスワード管理ツールや自動入力からも生じる

4.2 ネットワークと接続の特性

  • 同じ送信元から短時間に繰り返される生成リクエスト。個々のリクエストではなく束で見ると現れる
  • 宣言と実際の動作のずれ。完全なブラウザ文字列を送りながら、ブラウザが常に一緒に取りに行く副次リソースの要求が一つもなければ、その不一致が観察対象だ
  • ここでも単独判定は禁物だ。送信元が一つでも人が一人とは限らない

4.3 時間分布 - 集合でしか見えないシグナル

  • 人の登録は一日の曲線を描く。朝に増え未明に減り、曜日にも形がある
  • 正確に同じ時分に繰り返される生成は人のリズムではなくスケジューラのリズムだ。数日分を重ねて初めて浮かび上がる
軸何を見るか単独で弱い理由重なったとき意味するもの
宣言された値User-Agentなどリクエストヘッダーの構成クライアントが自由に決める他の軸とずれたときにだけ意味が生じる
行動入力順序と間隔の分布支援技術や自動入力が同じ形を作る時間分布と重なると可能性が上がる
ネットワーク送信元別の束、宣言と動作の不一致アドレス一つの後ろに多数の人がいる同じ送信元で同じ時刻の型なら強まる
時間分布生成時刻の日次・曜日分布人も特定の時間帯に集まりうる分単位の反復は人では説明しづらい

個々のシグナルは単独では根拠にならず、複数の軸が同じ方向を指したときにだけ強くなる。強くなったという言葉が「ブロックしてよい」を意味しないことが次の節の主題だ。

5. 誤検知が高くつく側と安くつく側

ボット対応が失敗する地点は、たいてい判別精度ではなく対応が二値であることにある。通すかブロックするかの二つだけなら、あらゆる判断が死刑宣告になる。そうなるとルールを緩く置くほかなく、緩いルールは何も止められない。まず作るべきはしきい値ではなく段階だ。

シグナルの強さ対応誤ったとき利用者が被ること巻き戻すコスト
弱い記録だけ残すないない
弱い〜中一覧への表示を遅らせ、索引対象から外す自分の投稿が遅れて見える表示状態を戻すだけ
中新規アカウントの一部機能を保留するリンク投稿や招待を後から使う保留を解けば終わる
中〜強い人が確認する待ち行列へ送る承認まで待つ承認処理の時間
強い登録拒否またはアカウント停止使えずたいていそのまま去る戻しても本人は戻らない

最後の列が設計のすべてだ。上の三行は誤っても巻き戻せるが、一番下の行は戻しても回復しない。巻き戻せる対応を使い切ってから最後の行を出す。

思いつきの方針ではない。OWASPが自動化の脅威をまとめた一覧で大量アカウント生成はOAT-019として登録されており、推奨される対応の一つがlimiting the functionality and/or capacity available to all newly created accountsだ。悪い側だけを選んで制限せよということではなく、新規アカウント全体の初期権限を下げよという意味である。

5.1 スコアと決定を分ける

シグナルの評価と決定が一塊になっていると、基準を変えるたびにデプロイが要り、過去のリクエストに新しい基準を当ててみることもできない。

// 概念例 - 構造を示すためのものであり、実行して検証していない。
// 重みと境界値はサービスごとに異なるので、そのまま使わないこと。

score = 0
if (ua_absent)            score += 1   // 弱いシグナル。単独では何も決めない
if (source_burst)         score += 2   // 同じ送信元から短時間に反復
if (schedule_like_timing) score += 2   // 集合を重ねて初めて見えるシグナル
if (declared_vs_observed) score += 3   // ブラウザと宣言したが副次リクエストがない

decision =
    score >= 6 ? "queue_for_human_review"   // 人が見る
  : score >= 3 ? "limit_new_account"        // 巻き戻せる制限
  :              "log_only"                 // 記録だけ

// ブロックはこの表にない。自動で下す最上位は人へ渡すところまでだ。

最後のコメントが要点だ。自動で下せる最も強い決定を「人へ渡す」に置けば、判別器の誤検知が利用者に直接届かない。

6. 後で判別するために今何を残すか

ボット判別はたいてい事後に行われる。おかしなアカウントが目に留まり、それからログを開く。そのとき答えを出せるかは、今日何を残したかで決まる。量ではなく構造の問題だ。

  • 時刻はミリ秒まで。時間分布を見るには秒単位では足りない。サーバー間で時計が合っているかも確認する
  • リクエストとイベントをつなぐ相関キー。アカウント生成がどのリクエストから出たかつながらなければ文脈を復元できない。このキー一つが調査時間を数日から数分に縮める
  • ルール識別子とスコアと決定を一緒に。結果だけ残すとルールを直せない。どのルールが何点を付け何を決めたかが同じ行にある必要がある
  • 観測モードの仮判定。ブロックせず「ブロックしたはず」とだけ印を付けた記録
  • ヘッダーは値ではなく形で。どのヘッダーがあり集合がどんな形だったかが判別に使われる。値全体を残せば不要な個人情報だけが増える

残してはいけないものも明確だ。入力内容そのものは残さない。必要なのは間隔の分布であって何を打ったかではない。ログ等級を決めるときの基準がここにも当てはまる。答えるべき問いを先に決め、それに必要なものだけを残す。

7. 個人情報の観点 - 判別用の値も個人情報

ボットを選り分けるために集めた値だという理由で個人情報の規律から外れることはない。むしろこちらのほうが敏感だ。判別力を上げる方向と識別力を上げる方向が事実上同じだからである。

欧州の一般データ保護規則は前文30項でこの点を直接述べている。自然人は機器・ツール・プロトコルが提供するオンライン識別子と結び付きうるものであり、そこにはinternet protocol addresses, cookie identifiersのようなものが含まれ、こうした痕跡が他の情報と結び付いてプロファイルを作り、個人を特定するのに使われうるという内容だ。

韓国の個人情報保護法も同じ方向を向く。第3条は処理目的を明確にしその目的に必要な範囲で最小限の個人情報だけを収集させ、目的外の利用を禁じる。第21条は目的を達して不要になったとき遅滞なく破棄し、復旧や再生ができないよう措置させる。

7.1 設計に落とすと四つ

  • 目的を書く。「自動登録の防止」のように狭く書き、その値を個人化やマーケティングに回さない
  • 保存期間を切る。時間分布を見るには数週間で足りる。生の値を一年ずつ抱える理由はたいてい無い
  • 解像度を下げる。正確なミリ秒の代わりに区間、正確なアドレスの代わりに帯単位にしても「反復しているか」はそのまま見える
  • プライバシーポリシーに書く。何をなぜどれだけ集めるか書けないなら、その収集自体を見直すべきという合図だ

フィンガープリントの精度を上げ続ける方向はこの規律とぶつかる。セッション全体の行動を見る方式が論争になる地点もここだ。

実務の基準を一つ - 新しいシグナルを足すたびに「この値が漏れたら利用者にどんな被害が及ぶか」をまず答えてみる。答えが「機器と習慣が露わになる」なら、そのシグナルは得られる判別力に比べて高い。

8. シグナルより先にフローを直す側

ここまでが判別の話なら、この節は判別する必要を減らす話だ。そしてたいていこちらのほうがずっと安い。

自動登録が大量に生じるサービスを開けてみると、アカウント生成がユーザーの明示的な操作より前に置かれていることが多い。アプリが起動したとき、画面が最初に開いたときに匿名アカウントを先に作り、後から情報を埋める構造だ。便利だが代償がある。リンクを開くものすべてが登録者になる。プレビューを作る側もインデックスを作る側も含まれる。攻撃ではなく、ただのウェブの日常だ。

直す方向は判別器を付けることではなく順序を変えることだ。アカウント生成を同意して始めるという明示的な操作の後ろへ移せば、自動訪問はアカウントを作らない。判別する対象が消えるのでシグナルが正確である必要もなくなる。これはセキュリティ対策である前に計測の問題だ。登録数が膨らんでいればコンバージョン率もアクティブユーザー数も誤った値になる。直した後に登録数が減るのは損ではなく数字が正直になることだ。

一般化すればこうだ。状態を変える操作を、自動リクエストが偶然通れる場所に置かない。閲覧しただけでカウンターが上がる画面、プレビュー要求だけで通知が飛ぶフロー、リンクを開くだけで招待が消費される設計は、すべて同じ問題を抱えている。

2026年8月、韓国の開発者コミュニティにこの問題を3週間追った記録が上がった。匿名コミュニティの運営者がクローラー名を弾くルールと空のUser-Agentを拒否するルールを順に入れたが、実際のアプリ利用者まで一緒に弾かれる副作用に遭い、最後に同意ボタンを押すまでは接続もアカウント生成も行わないようフローを変えて解決したという内容だ。結論がシグナルの一覧ではなくフローの変更だった点にこの記録の価値がある。

9. 確認できなかったこと

  • 自動化がトラフィックに占める割合や特定方式の検知率はこの記事に入れていない。公開されている数値は測定主体と定義と母数がまちまちで、自社製品の効果を示す目的で作られた資料が多い
  • 商用のボット管理製品の性能は比較していない。販売者と独立に同じ条件で測定した公開資料を確認できなかった
  • リアルタイム通信ライブラリがどんな条件でUser-Agentを送るかは実装と転送方式によって変わる。公開された運用記録の事例としてのみ扱い、一般的な動作と断定していない
  • 本文のコード片は構造を示すための概念例であり、実行して検証していない

10. よくある質問

空のUser-Agentはボットと見なしてよいか

いいえ。HTTPの仕様はこのヘッダーを推奨としているだけで、値をユーザーが変えることも想定された動作として書いている。空の値は「ボットである」ではなく「ブラウザらしい自己紹介がない」という観察であり、他の軸と重なったときにだけ意味を持つ。

ではUser-Agentはまったく役に立たないのか

アクセスを許可・拒否する単独の根拠にできないという意味だ。統計と監査には十分で、自らを名乗るクローラーを識別するのにも使える。ただし確認は逆引きや公開アドレス帯との照合が行う必要がある。

シグナルがいくつ重なればブロックしてよいか

個数で決める問題ではない。記録だけ残す、新規アカウントの機能を保留するといった巻き戻せる対応はシグナルが弱くても掛けられる。登録拒否のように利用者がその場で去る対応は、複数の軸が同じ方向を指すときにだけ使う。

ボット判別のために集めたアドレスやヘッダーも個人情報か

そう扱うのが正しい。欧州の規則はプロトコルアドレスやクッキー識別子が個人の特定に使われうると明記し、韓国の法も最小限だけ収集し不要になれば遅滞なく破棄させる。目的を狭く書き、保存期間を切り、解像度を下げる。

自動登録を減らす最も安価な方法は何か

判別器を付ける前に、アカウントが作られる地点を移すことだ。明示的なユーザー操作の後ろに生成を押しやれば自動訪問はアカウントを作らず、判別する対象自体が減る。

11. 結論 - 今日決める三つ

第一に、今あるブロックルールを観測モードで一日だけ回してみる。ブロックせず、引っかかったはずの一覧だけを集めて目で追う。その一覧に自社アプリの利用者や法人顧客が見えたなら、そのルールはすでに人を切っていたということだ。

第二に、通過とブロックの間に段階を一つ作る。新規アカウントの初期権限を下げておくのが最も手間が少ない。この一段があれば判別器が粗くても利用者は傷つかない。

第三に、アカウントがどの地点で作られるかコードで確認する。ユーザーの明示的な操作より前にあるなら、そこから移す。判別器を一つ付けるよりこちらのほうが、たいてい少ないコードで多くの問題を消す。

最もよくある錯覚は、正確なシグナルを見つければ問題が終わるという考えだ。クライアントが送る値は検証できず、行動と時間は人の側にも例外が多い。完璧なシグナルは来ない。代わりに誤ってもよい構造は今日作れる。それが長く持ちこたえる順序だ。
