どの欄が間違っているか画面が特定できない - 検証エラーにフィールドパスを付ける

ドット表記・JSON Pointer・角括弧を実装して走らせたエスケープ、配列インデックス、そして表記法が契約である理由

2026-08-01 開発・インフラ

導入: 赤線がフォーム全体に引かれた

注文書を送信したら、サーバが422とともに「入力が不正です」の一文を返してきた。画面はその一文で何をすべきか決められず、結局14個の入力欄すべてに赤い枠を付けた。利用者は問題のない8個を含めて最初から見直しはじめる。サーバは正確に6か所が誤りだと知っていたのに、その情報がレスポンスを渡ってこなかった。

この状況を「エラーメッセージが不親切だ」とまとめると問題を取り逃がす。親切さは副次的である。核心は検証エラーレスポンスを実際に消費するのが人ではなく画面だという事実だ。利用者がレスポンス本文を読むことはない。読むのはコードであり、そのコードがすべきことは一つしかない。どの入力要素に印を付けるかを決めること。

その判断が可能になるには、エラーごとに「どこ」が付いていなければならない。そしてその「どこ」は人が読む文ではなく、画面が自分の入力要素と照合できる機械用の座標である必要がある。ここから表記法の問題が始まる。同じ位置をitems.2.qtyとも、/items/2/qtyとも、items[2].qtyとも書ける。人の目には三つとも同じに読める。ところがパースするコードにとっては別物であり、あるフィールド名の前では三つのうち二つが静かに崩れる。

この記事はその地点を扱う。スキーマ検証器を自分で実装し、入れ子3段と配列が混ざったリクエストを通し、出てきたエラーを三つの表記法で出力して再びパースし元と比較した。エスケープが壊れる場所、配列インデックスがずれて別の欄に赤線が行く場所、メッセージにフィールド名を入れたとき翻訳が崩れる場所を、すべて実行で確認した。結論を先に言えば、表記法は好みではなく契約である。

実行環境。以下の出力はすべてWindows 10 Pro (10.0.19045)で実際に実行した結果だ。ランタイムはNode.js v22.16.0 (win32)、シェルはGNU bash 5.2.37 (MSYS2/MinGW64)である。検証器と実験スクリプトはすべてファイルに保存して実行し、リポジトリの外にある一時作業フォルダでのみ走らせた。ヒアドキュメントでコードを渡すと引用符とバックスラッシュが静かに変形するからだ。

例はすべて架空である。登場する注文API、フィールド名、商品コード、項目識別子は説明のために作ったものだ。特定の検証ライブラリを選んだり評価したりはしない。ここで使う検証器は論点を露わにするために自作した200行の玩具であり、どの道具を使っても変わらないのはレスポンスの形だというのがこの記事の前提である。

この記事が扱わないこと。エラーコード自体の命名や増やし方はエラーコード体系を作るということで扱った。ここではコードがすでにあるものとして「どこ」だけに集中する。一覧レスポンスの座標問題、つまりページをめくるときに項目がずれる話はオフセットページングが構造的にできないことにある。

1-4に注目すべき点が一つある。items.2.options.0.valueは本文から値を取り出すとundefinedになる。必須フィールドがそもそも存在しないからだ。つまり経路が指す場所に値がなくても経路自体は有効である。経路は値の住所ではなく場所の住所だ。この区別を落とすと、クライアントが「本文で見つからない経路は捨てる」という規則を作り、必須欠落エラーを丸ごと飲み込むことになる。

  • サーバは失敗した規則と位置をすでに知っていた。問題は計算ではなく伝達である
  • 経路のないレスポンスで画面ができる最善はすべて表示であり、それは使い勝手の面で表示しないのとほぼ同じだ
  • 深さ5の経路が実際に出る。配列の中のオブジェクトの中の配列の中のオブジェクトは特殊な構造ではなく、ありふれた注文書である
  • 検証器は失敗を文字列ではなくセグメント配列として集めた。出力は最後の段階に回したので、表記法を変えるのに検証ロジックを触る必要がなかった

2. 同じエラーを三つの表記法で

セグメント配列を文字列に変える方法は大きく三つある。同じ6件の失敗を三方式で同時に出力した。

--- 2-1. the same six failures, printed three ways ---
rule       dot                      json pointer               bracket
------------------------------------------------------------------------------------------------
pattern    orderId                  /orderId                   orderId
minLength  customer.name            /customer/name             customer.name
pattern    customer.contact.email   /customer/contact/email    customer.contact.email
minLength  items.2.sku              /items/2/sku               items[2].sku
min        items.2.qty              /items/2/qty               items[2].qty
required   items.2.options.0.value  /items/2/options/0/value   items[2].options[0].value

--- 2-2. size of the whole response in each notation ---
  dot      302 B    longest path = 23
  pointer  308 B    longest path = 24
  bracket  306 B    longest path = 25

--- 2-3. how much code does the CLIENT need to read it back ---
  dot      chars 154   needs a tokenizer loop: no
  pointer  chars 302   needs a tokenizer loop: no
  bracket  chars 472   needs a tokenizer loop: yes

大きさの差は無視してよい。レスポンス全体で6バイト、2パーセント以内だ。意味のある差はパース側にある。ドット表記のパーサは一行のsplitで終わり、JSON Pointerのパーサは脱出文字を戻す二回の置換が加わる。角括弧表記だけが文字を一つずつ舐めるトークン化ループを必要とする。開き括弧に出会えば閉じ括弧を探さねばならず、ドットと括弧が混ざる境界を自分で処理する必要があるからだ。

ありふれた経路では三つとも問題ない。出力してから再びパースし元のセグメントと比較する往復試験を回してもすべて通過する。

--- 2-4. round trip on the ordinary paths: print then parse then compare ---
segments                        dot     pointer  bracket
------------------------------------------------------------
["orderId"]                     true    true     true
["customer","name"]             true    true     true
["customer","contact","email"]  true    true     true
["items",2,"sku"]               true    true     true
["items",2,"qty"]               true    true     true
["items",2,"options",0,"value"] true    true     true

--- 2-5. same path, resolved against the body through each notation ---
  dot      items.2.qty          -> ["items",2,"qty"] -> value 0
  pointer  /items/2/qty         -> ["items",2,"qty"] -> value 0
  bracket  items[2].qty         -> ["items",2,"qty"] -> value 0

--- 2-6. is the notation self describing? a lone path with no schema at hand ---
  dot      items.2.options.0.value    array steps are invisible, 2 could be a key
  pointer  /items/2/options/0/value   array steps are invisible, 2 could be a key
  bracket  items[2].options[0].value  array steps are marked by brackets

  none of the three can prove 2 is an index without the schema;
  bracket only records what the SERVER believed when it printed.

2-6が重要な思い違いを一つ整理してくれる。角括弧表記には配列の段が目に見えるという利点が確かにある。ログを人が読むときitems[2]はitems.2より理解が速い。ところがその情報はサーバが出力するときにそう信じていたという記録にすぎない。クライアントがその表示を根拠に配列かどうかを再確認することはできない。数値がインデックスかキーかの最終判定はつねにスキーマの仕事であり、表記法がその判定を代わってくれることはない。

3. エスケープの罠 - 名前にドット・スラッシュ・角括弧が入ると

ここが表記法の選択が実際に分かれる地点だ。JSONオブジェクトのキーにはほとんど何の文字でも入る。そして実務の本文にはそういうキーが多い。バージョン文字列をキーにする設定マップ、ヘッダ名をそのままキーにする辞書、利用者が入力したタグ名、年をキーにする集計結果などである。9つの事例を作り、三つの表記法で出力してから再びパースした。

--- 3-1. print each key with all three notations ---
case                        dot                       pointer                     bracket
--------------------------------------------------------------------------------------------------------
plain key                   meta.source               /meta/source                meta.source
dot in key                  meta.app.version          /meta/app.version           meta.app.version
slash in key                headers.x-forwarded/for    /headers/x-forwarded~1for   headers.x-forwarded/for
bracket in key              tags.group[a]             /tags/group[a]              tags.group[a]
tilde in key                tags.draft~2              /tags/draft~02              tags.draft~2
digits as key               byYear.2024.total         /byYear/2024/total          byYear.2024.total
empty key                   tags.                     /tags/                      tags.
dot plus index              rows.3.unit.price         /rows/3/unit.price          rows[3].unit.price
key that looks like a path  fields.items.0.qty        /fields/items.0.qty         fields.items.0.qty

--- 3-2. now parse them back and compare with the original segments ---
case                        dot     pointer  bracket
--------------------------------------------------------
plain key                   true    true     true
dot in key                  false   true     false
slash in key                true    true     true
bracket in key              true    true     false
tilde in key                true    true     true

ドット表記5件、角括弧4件、JSON Pointer 8件。差の原因は能力ではなく規則の有無だ。ドット表記と角括弧には、区切り文字を名前の中に入れたときどう表示するかの規定がそもそもない。だから出力の段階で情報が消え、パースの段階で復元する方法が残らない。

崩れたときクライアントが実際に何を受け取るのかを見ると、深刻さがはっきりする。

--- 3-3. what the client actually receives when a notation collapses ---
  dot in key
    server meant : ["meta","app.version"]
    printed as   : meta.app.version
    client reads : ["meta","app","version"]
    segments     : 2 -> 3
  digits as key
    server meant : ["byYear","2024","total"]
    printed as   : byYear.2024.total
    client reads : ["byYear",2024,"total"]
    segments     : 3 -> 3
  dot plus index
    server meant : ["rows",3,"unit.price"]
    printed as   : rows.3.unit.price
    client reads : ["rows",3,"unit","price"]
    segments     : 3 -> 4
  key that looks like a path
    server meant : ["fields","items.0.qty"]
    printed as   : fields.items.0.qty
    client reads : ["fields","items",0,"qty"]
    segments     : 2 -> 4

--- 3-4. bracket notation on a key that contains a bracket ---
  server meant : ["tags","group[a]"]
  printed as   : tags.group[a]
  client reads : ["tags","group",null]
  the printer has no escape rule for ] at all, so the string is not recoverable

セグメント数が2から4に増える事例が最も悪い。クライアントは自分が読み違えたという事実すら知りえない。fields.items.0.qtyは文法的に完璧な経路に見え、パースも成功し、例外も出ない。ただ存在しない場所を指すだけである。3-4の角括弧の事例はもっと露骨だ。名前の中の閉じ括弧に出会ったパーサがnullをセグメントとして吐いた。出力器に脱出規則がないため文字列そのものが復元不能になったのである。

JSON Pointerはこの地点で違う振る舞いをする。規則が文書に書かれているからだ。

--- 3-5. the only notation with a written escape rule ---
  key "x-forwarded/for"    pointer /headers/x-forwarded~1for  back "x-forwarded/for"    equal true
  key "draft~2"            pointer /tags/draft~02             back "draft~2"            equal true
  key "a~/b"               pointer /tags/a~0~1b               back "a~/b"               equal true

--- 3-6. and the one it still cannot settle by itself ---
  object with a numeric KEY : {"byYear":{"2024":{"total":0}}}
  pointer                   : /byYear/2024/total
  parsed with number guess  : ["byYear",2024,"total"]
  parsed as pure strings    : ["byYear","2024","total"]
  RFC 6901 says: try the string key first, treat it as an index only for arrays.
  a client that guesses by shape alone will mislabel numeric object keys.

スラッシュは~1に、チルダは~0に変わる。三行目が規則の精緻さを示す。a~/bはa~0~1bになり正確に戻ってきた。戻すときは順序が重要だ。~1を先にスラッシュへ、その次に~0をチルダへ変える。順序を逆にすると~01のような入力で結果が変わる。RFC 6901がこの順序を明示する理由である。

それでもJSON Pointerが単独で解決できないものが一つ残る。数値のオブジェクトキーだ。年をキーにする集計オブジェクトで/byYear/2024/totalを受け取ったクライアントが「数値に見えるからインデックス」と判断すれば誤りである。RFC 6901の規定は明確だ。対象がオブジェクトならその文字列を名前として扱い、配列のときだけインデックスとして解釈する。つまり判定基準は文字列の見た目ではなくその場所にある値の型である。

4. 配列インデックスの寿命 - 項目が一つ消えると

エスケープを解決しても配列には別種の問題が残る。インデックスはリクエストを送った瞬間の配列状態にのみ有効な座標だということだ。カート4行を作り、3行目に問題を仕込み、レスポンスが届く間に利用者が2行目を削除する状況を再現した。

--- 4-1. the cart as sent, and the errors that came back ---
  [0] ln_7742  sku="SKU-A1"  qty=2
  [1] ln_9310  sku="SKU-B7"  qty=1
  [2] ln_5518  sku=""        qty=0
  [3] ln_2064  sku="SKU-D3"  qty=5

  items.2.sku     rule=required  lineId=ln_5518
  items.2.qty     rule=min       lineId=ln_5518

--- 4-2. the user removes row 1 while the response is in flight ---
  [0] ln_7742  sku="SKU-A1"  qty=2
  [1] ln_5518  sku=""        qty=0
  [2] ln_2064  sku="SKU-D3"  qty=5

--- 4-3. apply the index paths to the cart as it is NOW ---
path from server  index  row now at that index correct row
----------------------------------------------------------------------
items.2.sku       2      ln_2064 (SKU-D3)      NO  should be ln_5518

--- 4-4. what the screen shows after the shift ---
  items.2.sku       -> marks ln_2064.sku     value "SKU-D3"  a red line on a VALID field
  items.2.qty       -> marks ln_2064.qty     value 5         a red line on a VALID field

エラー2件がいずれも別の行に付いた。そして付いた場所の値はSKU-D3と5で完全に正常である。利用者の側で起きることはこうだ。問題のない行に赤線が引かれ、実際に誤っている行には何の印もない。利用者は正常な値を消して入力し直し送信を繰り返し、サーバは毎回同じエラーを返す。この状態で利用者が原因を突き止める方法はない。

この問題はタイミング事故のように見えるがそうではない。インデックスが同一性を持たないことが原因だ。項目ごとにクライアントが付けた固有の識別子をリクエストに載せて送り、サーバがそれをエラーに返せば問題は消える。

--- 4-7. does the server even know the client id? only if the client sent it ---
  body the client sent : {"sku":"","qty":0}
  fields the server can echo back : sku, qty
  stable handle available : no
  so the id has to be part of the REQUEST schema, not invented in the response.

安定識別子に変えると誤配置が2件から0件になった。項目が削除されていれば、そのエラーは付ける先がないという事実が明確に表れるので静かに捨てても安全だ。インデックスはその判断ができない。インデックスはつねに「誰か」を指し、その誰かが本来の対象かどうかを知る方法がない。

4-7が最もよく見落とされる前提である。サーバはクライアントが送っていない識別子を返せない。リクエスト本文にskuとqtyだけが入っていれば、サーバが返せるのもその二つだけだ。つまり安定識別子はレスポンス設計ではなくリクエストスキーマ設計の問題である。エラーレスポンスにそれを入れると決めた瞬間、リクエスト側の契約も一緒に変わる。

  • インデックス経路は捨てずに一緒に送るのがよい。ログとサーバ側のデバッグではインデックスが依然として便利だ
  • 二つの座標を一緒に載せるとレスポンスが117バイトから193バイトに増える。エラー1件あたり38バイトだ
  • 識別子はサーバが作ったものでもクライアントが作った一時値でもよい。リクエストとレスポンスの間で変わらなければよい
  • クライアントが項目を追加したときも同じ問題が起きる。削除だけ気を付ければよい問題ではない
  • 項目の並び替えを利用者ができる画面なら、インデックスは最初から使えない

5. 最初のエラーで止めるか、すべて集めるか

位置を付けると決めたら次の判断は件数だ。最初の失敗で即座に返すか、すべて集めて一度に渡すか。同じ本文を二方式で処理した。最初のエラーだけを返すサーバを相手に、利用者が指摘された欄だけを一つずつ直していく過程をそのまま走らせた。

--- 5-1. stop at the first failure: how many round trips to a clean form ---
  trip 1  server says: orderId                   (pattern)
  trip 2  server says: customer.name             (minLength)
  trip 3  server says: customer.contact.email    (pattern)
  trip 4  server says: items.2.sku               (minLength)
  trip 5  server says: items.2.qty               (min)
  trip 6  server says: items.2.options.0.value   (required)
  total round trips : 6

--- 5-2. collect everything: one round trip ---
  errors returned   : 6
  total round trips : 1

--- 5-3. three response shapes for the same six failures ---
  flat path list      302 B    client walk = one loop
  plus params         459 B    client walk = one loop
  plus english text   859 B    client walk = one loop
  nested tree         217 B    client walk = recursive

  the nested tree, printed:
{"orderId":["pattern"],"customer":{"name":["minLength"],"contact":{"email":["pattern"]}},"items":{"2":{"sku":["minLength"],"qty":["min"],"options":{"0":{"value":["required"]}}}}}
  note: to find a leaf the client must recurse, and array levels look like objects.

6回対1回である。利用者の側からすればこれは6回の送信と6回の待ちだ。フォームが長いほど離脱率が上がる典型的な形であり、サーバ側でもリクエストが6倍になる。検証に副作用がないなら、まとめて渡すほうがほぼつねによい。

5-3の入れ子ツリー形式は興味深い罠だ。217バイトで最も小さく、一見構造が美しい。ところが配列の段がオブジェクトのように見える。"items":{"2":{...}}の2はインデックスなのにキーとして直列化された。3節の数値キー問題がここでそのまま再現する。加えてクライアントは葉を見つけるために再帰を回さねばならない。平坦な一覧が大きさで少し損をする代わりに、ループ一つで終わる。

まとめて渡すと決めたら、大きさがどこまで育つのかを確認する必要がある。

--- 5-4. how big does collect-all get on a bulk request ---
  items   errors  flat B    with params B  with text B
  ------------------------------------------------------
  1       2       118       172            296
  10      20      820       1360           2600
  100     200     8020      13420          26000
  1000    2000    81820     135820         263600

--- 5-5. capping the list, and saying so ---
  total failures     : 2000
  returned           : 50
  truncated flag     : true
  bytes uncapped     : 81820
  bytes capped       : 2056
  without the flag the screen believes it has the whole list and clears the rest.

--- 5-6. two failures on ONE field: does the list keep both ---
  orderId       minLength {"min":10,"got":1}
  orderId       pattern   {"hint":"ORD-000000"}
  items.0.qty   max       {"max":99,"got":500}
  grouped by path : {"orderId":["minLength","pattern"],"items.0.qty":["max"]}
  a map keyed by path (path -> one message) would silently drop the loser.

項目1,000個の一括リクエストでエラーが2,000件になり、人が読む文まで入れるとレスポンスが263キロバイトになる。画面にはどうせ最初の数件しか見えない。だから上限を置くのが正しいが、切ったという事実を必ず知らせなければならない。切られたことを知らない画面は「一覧にないから解決された」と判断し、残りの表示を消す。

5-6はレスポンス形式を選ぶ決定的な理由を一つ与える。一つのフィールドに規則二つが同時に失敗しうる。orderIdが長さも足りず形式も合わない状況だ。エラーを経路をキーにするマップにすると、後のものが前のものを上書きして一つが消える。利用者は長さを直して再送信し、そこでようやく形式エラーを聞かされる。マップではなく一覧でなければならない理由がこれである。

6. 人向けの文言と機械向けの経路を分ける

ここでよくある折衷案が一つ出てくる。「メッセージにフィールド名を入れておけば利用者にも分かり画面も照合できるのでは」だ。実際に走らせると二つの期待が両方とも崩れる。

--- 6-1. the server bakes the label into the sentence, one language only ---
  response : [{"message":"Quantity must be at least 1."}]

  a screen in another language now has three bad options:
    1. show the English sentence to a non English reader
    2. translate the sentence at runtime, per request
    3. match the sentence text to decide which box to mark

--- 6-2. option 3 in practice: matching on the sentence ---
  screen locale en   label on screen Quantity     found in the sentence: true
  screen locale de   label on screen Menge        found in the sentence: false
  screen locale es   label on screen Cantidad     found in the sentence: false
  screen locale pt   label on screen Quantidade   found in the sentence: false
  labels matched : 1 of 4
  the only locale that matches is the one the server happened to be written in.

--- 6-3. the same sentence after a harmless copy edit on the server ---
  before : Quantity must be at least 1.   -> client match on "Quantity" = true
  after  : The quantity must be at least 1.   -> client match on "Quantity" = false
  a wording change is a breaking change once the screen parses the wording.

四つのロケールのうち一つだけが照合に成功し、その一つはサーバのコードを書いた人の言語だった。残りの三つは自分の画面のフィールド名を文の中に見つけられない。ところがもっと危険なのは6-3だ。文の先頭に冠詞を一つ足す些細な修正で照合が直ちに失敗した。文言を画面がパースした瞬間、コピー修正がそのまま互換性破壊になる。そしてこの破壊はどのテストにも掛からない。サーバ側では文を整えただけだからだ。

解法は分けることだ。位置と規則コードとパラメータはサーバが、人が読む文は画面が作る。

--- 6-4. split it: path and rule stay, wording moves to the client ---
{"error":"validation_failed","errors":[{"path":"orderId","rule":"pattern","params":{"hint":"ORD-000000"}},{"path":"customer.name","rule":"minLength","params":{"min":1,"got":0}},{"path":"customer.contact.email","rule":"pattern","params":{"hint":"name at host"}},{"path":"items.2.sku","rule":"minLength","params":{"min":1,"got":0}},{"path":"items.2.qty","rule":"min","params":{"min":1,"got":0}},{"path":"items.2.options.0.value","rule":"required","params":{}}]}

  bytes : 459

--- 6-5. one response, rendered by four screens ---
  path                      locale  what the user reads
  ------------------------------------------------------------------------------
  items.2.qty               en      Quantity must be at least 1.
  items.2.qty               de      Menge muss mindestens 1 betragen.
  items.2.qty               es      El campo Cantidad debe ser al menos 1.
  items.2.qty               pt      O campo Quantidade deve ser no minimo 1.
  items.2.options.0.value   en      Option value is required.
  items.2.options.0.value   de      Optionswert wird benoetigt.
  items.2.options.0.value   es      El campo Valor de opcion es obligatorio.
  items.2.options.0.value   pt      O campo Valor da opcao e obrigatorio.

--- 6-6. sentence length across the four, same path every time ---
  en   chars 28   Quantity must be at least 1.
  de   chars 33   Menge muss mindestens 1 betragen.
  es   chars 38   El campo Cantidad debe ser al menos 1.
  pt   chars 40   O campo Quantidade deve ser no minimo 1.
  path is 11 chars in all four : items.2.qty

--- 6-7. the fallback the server still owes you ---
  rule from server : skuBlockedForRegion
  client knows it  : false
  with no fallback : the box is marked red with an empty tooltip
  with a fallback  : the server also ships a plain default sentence
  {"path":"items.0.sku","rule":"skuBlockedForRegion","params":{"region":"KR"},"message":"This item cannot be shipped to the selected region."}
  the message is a LAST RESORT for unknown rules, never the thing the screen parses.

6-6がこの節の要約だ。文は28文字から40文字までばらばらなのに、経路は4回とも11文字で同じである。文言は言語ごとに異なり時が経てば変わるが、経路はスキーマが変わらない限りそのままだ。変わるものと変わらないものを同じ文字列に混ぜると、変わってはいけないほうが変わるほうに引きずられる。

ただし文言を完全になくすのも答えではない。6-7がその理由である。サーバが新しい規則コードを追加したのに画面の文言辞書にそのコードがまだなければ、欄は赤く塗られ説明は空という状態になる。だからサーバは知らない規則のための既定文を一つ載せるべきだ。重要なのはその文の役割である。最後の手段であって画面がパースする対象ではない。画面は知っている規則なら自分の文言を使い、知らない規則のときだけサーバの文をそのまま見せる。

  • サーバが作るのは経路・規則コード・パラメータの三つだ。パラメータは文に差し込む数値やヒントをそのまま持つ
  • 画面が作るのはフィールド名と文である。フィールド名辞書のキーはインデックスを除いた経路になるので、配列項目全体が一つの項目を共有する
  • 規則コードは安定していなければならない。コード名を変えるのは経路を変えるのと同じ重さの変更だ
  • サーバの既定文は一言語で十分である。どうせ画面が知っている規則では使われない
  • 翻訳ファイルにない規則コードに出会ったとき警告を残すようにしておけば、サーバが規則を追加した事実がリリース後に静かに埋もれない

7. 画面が経路を入力要素に結び付けるコード

さて最後の断片だ。レスポンスをうまく作っても、画面が経路を自分の入力要素に結び付けられなければ何も起きない。入力要素14個と領域コンテナ6個を持つ画面を作り、レスポンスをそのまま流した。

--- 7-1. the widgets this screen actually has ---
  orderId
  customer.name
  customer.contact.email
  customer.contact.phone
  items.0.sku
  items.0.qty
  items.1.sku
  items.1.qty
  items.1.options.0.code
  items.1.options.0.value
  items.2.sku
  items.2.qty
  items.2.options.0.code
  items.2.options.0.value
  input widgets : 14
  containers    : customer, customer.contact, items, items.0, items.1, items.2

--- 7-2. the response, and which paths the screen can resolve ---
  customer.name             minLength   widget found: true

結び付け自体は単純だ。入力要素の名前属性を経路と同じにしておけば照会一回で終わる。重要なのはその名前を手で書かないことである。リクエスト本文を作るコードと入力要素名を作るコードが同じ関数を使わなければ、二つは必ずずれる。とくに配列インデックスがそうだ。

--- 7-7. binding widgets by path, generated instead of hand written ---
  ["customer","contact","email"]  <input name="customer.contact.email">
  ["items",2,"qty"]               <input name="items.2.qty">
  ["items",2,"options",0,"value"] <input name="items.2.options.0.value">

  the row index in the widget name has to come from the same counter the
  request body was built with, or the two drift apart on the first insert.

7-2に本当の問題がある。レスポンスに含まれる六つの経路のうち三つはこの画面に対応する入力要素がない。理由はそれぞれ異なる。billing.taxIdはこの段階の画面にそもそもないフィールドであり、items.9.skuは画面にない9番目の項目、そして空の経路は本文全体を指す横断フィールドエラーだ。これは例外状況ではなく既定値である。サーバと画面は同じ速度でリリースされない。

8. 画面が知らない経路に出会ったとき

選択肢は三つだ。捨てるか、上部のバナーに上げるか、経路の前半を切り詰めながら上位領域を探して付けるか。三つの方針を同じレスポンスに適用した。

--- 7-3. three policies for the paths with no widget ---
  policy ignore   marked=3   promoted=0   banner=1   dropped=2
    banner lines : ["This combination is not allowed."]
  policy banner   marked=3   promoted=0   banner=3   dropped=0
    banner lines : ["Required. (billing.taxId)","Required. (items.9.sku)","This combination is not allowed."]
  policy prefix   marked=3   promoted=1   banner=2   dropped=0
    banner lines : ["Required. (billing.taxId)","This combination is not allowed."]

--- 7-4. what the user sees under each policy, field by field ---
  ignore   3 marked
      customer.name [Too short.]
      items.2.qty [Too small.]
      items.2.options.0.value [Required.]
  banner   3 marked
      customer.name [Too short.]
      items.2.qty [Too small.]
      items.2.options.0.value [Required.]
  prefix   4 marked
      customer.name [Too short.]
      items.2.qty [Too small.]
      items.2.options.0.value [Required.]
      items (container) [Required.]

--- 7-5. the failure mode of ignore ---
  http status the client saw : 422
  errors in the body         : 6
  errors shown anywhere      : 4
  errors silently dropped    : 2
  result: the submit button fails, and nothing on the page says why.

--- 7-6. the invariant a client should assert ---
  ignore   shown 4 of 6   invariant holds: false
  banner   shown 6 of 6   invariant holds: true
  prefix   shown 6 of 6   invariant holds: true

無視方針の結果が7-5にそのまま出ている。送信は失敗したのに画面のどこにも理由がない。利用者はボタンをもう一度押し、同じことが繰り返される。これが「検証エラーレスポンスをうまく作ったのに問い合わせが減らない」典型的な原因だ。サーバはきちんと知らせ、画面が静かに捨てた。

7-6がこの節の実践項目である。画面側に不変条件を一つ置く。レスポンスに含まれるエラー件数と画面のどこかに表示された件数が一致しなければならない。この検査を開発ビルドで警告として出すだけでも、サーバが新しいフィールドを追加したとき画面が飲み込む事故をリリース前に捕まえる。

接頭辞昇格方針はもう少し親切だ。items.9.skuでitems.9を試し、なければitemsを試してカート領域全体に印を付けた。利用者は少なくともどの区画を見ればよいか分かる。ただしこの方針にも限界がある。billing.taxIdは上位のbillingすら画面にないので結局バナーへ行った。

方針表示されたエラー利用者が見るもの危険
無視6件中4件送信失敗、説明なし不変条件が破れる。決して既定にしないこと

9. レスポンス設計をリンタで検査する

ここまで出た要求を規則として書き、五つのレスポンス形式に実際に走らせた。リクエストを検査する検証器ではなく契約を検査するリンタである。

--- 8-1. lint five candidate response shapes against the contract ---
  rule                                      A   B   C   D   E
  --------------------------------------------------------------
  R1 every error carries a path field       no  no  ok  ok  ok
  R2 one notation across the whole body     no  no  no  ok  ok
  R3 machine readable rule code present     no  no  no  ok  ok
  R4 wording is not the only carrier        no  no  no  ok  ok
  R5 params separated from the sentence     no  no  ok  ok  ok
  R6 array rows have a stable handle        no  no  no  no  ok
  R7 whole body errors have a defined path  no  no  ok  ok  ok
  R8 truncation is announced                no  no  ok  ok  ok
  R9 two failures on one field survive      no  no  ok  ok  ok
  --------------------------------------------------------------
  passed                                    0   0   5   8   9

  A sentence only     25 B
  B path keyed map    206 B
  C mixed notations   394 B
  D path plus rule    459 B
  E full contract     978 B

--- 8-2. why the path keyed map (candidate B) loses information ---
  errors in            : 2
  keys in the map      : 1
  map                  : {"orderId":"pattern"}
  the first rule is overwritten and never reaches the screen.

候補Cが5点にとどまった理由が、このリンタの存在理由を示す。Cは経路もあり大きさも小さいが一つのレスポンスの中で表記法が混ざっている。奇数番目のエラーはJSON Pointer、偶数番目はドット表記だ。実際にこういうレスポンスが出る経路がある。フレームワーク既定の検証器が作ったエラーと、人が手で入れたドメイン検証エラーが同じ配列に混ざって出るときである。画面の側からはエラーごとに表記法を推測せねばならず、推測が外れた瞬間に3節の事故が再現する。

候補Bは0点だ。経路をキーにするマップは構造そのものが情報を失う。8-2がそれを示す。エラー二件を入れたのにキーは一つしか残らなかった。

10. 設計規則と点検項目

実行で確認したことを規則にまとめると五行になる。各規則の根拠は前節の出力である。

  • 表記法を一つ選んで文書に書く。名前に特殊文字が入る余地が少しでもあればJSON Pointerだ。往復試験で9件中8件を通過した唯一の表記法であり、脱出規則が標準文書にある
  • 一つのレスポンスの中で表記法を混ぜない。フレームワークが作ったエラーとドメイン検証エラーが同じ配列に入るなら、出る直前の一か所で表記法を統一する
  • 配列項目にはインデックスと安定識別子を一緒に渡す。そのためには識別子がリクエストスキーマに先にある必要がある。レスポンスだけ直しても駄目な唯一の規則だ
  • エラーはマップではなく一覧で渡す。一つのフィールドに二つの規則が同時に失敗しうるし、マップはそのうち一つを静かに捨てる
  • 文言は画面が作るが、サーバは既定文を一つ残す。画面が知らない規則コードが来たときの唯一の安全網である

最もよく見落とされること。表記法を決める会議は開かれるのに、「知らない経路が来たらどうするか」を決める会議は開かれない。ところが実測ではレスポンスの半分が、画面に対応要素のない経路だった。この規則がなければ各画面が勝手に処理し、大半は静かに捨てるほうを選ぶ。サーバがきちんと知らせたエラーの三分の一が利用者に届かない状態がここで作られる。

点検項目は次のとおりだ。各項目は前節で実際に失敗を作ってみたものである。

  • エラーレスポンスの表記法が仕様書に書かれている
  • フィールド名にドット・スラッシュ・角括弧が入った標本で往復試験を通過させた
  • 数値のオブジェクトキーがインデックスと誤解されないか確認した
  • 配列項目のエラーに安定識別子が一緒に載る
  • その識別子がリクエストスキーマにも定義されている
  • エラーが一覧であり、一つのフィールドに二つ付きうる
  • 一覧に上限があり、切ったという表示が一緒に出る
  • 画面が文をパースしない
  • 規則コードごとに画面側の文言項目があり、ないとき警告が残る
  • 空の経路が本文全体を意味するという規約が文書にある
  • 画面に表示件数の不変条件がある
  • 入力要素名とリクエスト本文の経路が同じ関数から出る
  • 知らない経路の処理方針が画面ごとに同じである

11. この記事で確認できなかったこと

  • 実ブラウザでのアクセシビリティ連携。経路を入力要素に結び付けるところまでは確認したが、その表示が支援技術にどう伝わるかはこの実験の外だ
  • 入れ子フォーム部品の状態管理。画面が項目を追加・削除・並び替えするとき経路と部品状態をどう同期するかはフレームワークごとに異なる
  • 部分成功レスポンス。一括リクエストで一部だけ失敗したとき成功項目と失敗項目を一つのレスポンスにどう収めるかは別の設計問題だ
  • 非同期検証。重複確認のようにサーバ往復が必要な規則は、送信時点ではなく入力途中でエラーが届く。そのときの経路の有効期間はこの記事の配列問題に似ているが同じではない
  • 実サービス規模のレスポンスの大きさ。5節の数値は合成データだ。実際のフィールド名はもっと長く、パラメータももっと多い

結論: エラーレスポンスの受け手は人ではなく画面である

検証エラーをうまく渡そうという話から始めると、結論が「メッセージを親切に書こう」へ流れる。ところが実行して確認したことは逆方向を指す。親切な文は画面で作れるが、どの欄が誤っているかはサーバしか知らない。サーバが送るべきものは文ではなく座標だ。

座標を送ると決めると、直ちに表記法の問題が付いてくる。そして表記法は見かけと違い好みの領域ではなかった。フィールド名にドットが一つ入っただけでセグメント二つが三つに増え、クライアントは自分が読み違えたという事実すら知りえなかった。角括弧表記は名前の中の閉じ括弧一つでnullセグメントを吐いた。脱出規則が文書にある表記法とない表記法の差が、往復試験5件対8件として表れた。

配列は別の問題だった。インデックスは同一性がないので項目が一つ消えるとエラー二件がいずれも別の行に付き、問題のない欄に赤線が引かれ実際に誤っている行には何の印もない状態になった。安定識別子に変えると0件になったが、そのためにはリクエストスキーマから変える必要があった。レスポンスだけ直して解決する問題ではなかった。

だから結論はこうだ。表記法は契約である。サーバが出力する規則と画面がパースする規則が同じでなければならず、その規則がどこかに書かれていなければならず、一つのレスポンスの中で揺らいではならない。その契約が立って初めてエラーレスポンスに価値が生まれる。

いますぐ確認できることが一つある。いま扱っている画面で検証エラーを処理するコードを開き、レスポンスに含まれるエラー件数と画面に実際に表示された件数を比べる行があるか見てほしい。なければその画面は、サーバがきちんと知らせたエラーを静かに捨てている可能性がある。そしてその事実は、エラーレスポンスをどれだけうまく作っても表に出ない。

# 検証エラーのフィールドパス — 貼り付け用の表記法比較表とレスポンス設計

> 出典: braindetox.kr — どの欄が間違っているか画面が特定できない
> 根拠: Windows 10 / Node.js 22.16 (win32) / bash 5.2.37 (MSYS2) で自作の検証器を実行して検証
> このファイルをそのままAIに貼り「この基準でうちのエラーレスポンスを点検して」と書けば使えます。
> 原則: エラーレスポンスの受け手は人ではなく画面である。画面がパスを入力要素に結び付けられて初めて価値が生まれる。

## 1. 表記法3種の比較 (往復試験の実測)

| 項目 | ドット `items.2.qty` | JSON Pointer `/items/2/qty` | 角括弧 `items[2].qty` |
|---|---|---|---|
| パーサ規模 | 154文字 | 302文字 | **472文字** |
| トークン化ループ | 不要 | 不要 | **必要** |
| 脱出規則 | **なし** | チルダ `~0` ・ スラッシュ `~1` | **なし** |
| 配列段の表示 | 見えない | 見えない | 見える(サーバの主張) |
| 標準文書 | 慣行 | **RFC 6901** | 慣行 |
| 本文全体の指定 | 規約が必要 | 空文字列 | 規約が必要 |
| 厄介なキー9件の往復 | 5件 | **8件** | 4件 |

**結論: 名前に特殊文字が入る余地があるならJSON Pointer。**

## 2. エスケープが壊れる地点

| キーに入った文字 | ドット | Pointer | 角括弧 | 症状 |
|---|---|---|---|---|
| ドット `app.version` | 破綻 | 通過 | 破綻 | セグメント 2 → 3 |
| スラッシュ `x-forwarded/for` | 通過 | 通過 | 通過 | ドット表記は偶然安全 |
| 角括弧 `group[a]` | 通過 | 通過 | 破綻 | パーサが null セグメントを返す |
| チルダ `draft~2` | 通過 | 通過 | 通過 | 脱出規則が正確に戻す |
| 数値キー `2024` | 破綻 | 破綻 | 通過 | キーをインデックスと誤解 |
| 空文字列キー | 通過 | 通過 | 破綻 | セグメントが静かに消える |
| 経路のようなキー | 破綻 | 通過 | 破綻 | 2 → 4、存在しない場所を指す |

- 戻すときの順序に注意: `~1` → スラッシュ を先に、その次に `~0` → チルダ
- 数値キーの判定は表記法ではなく **その場所の値の型** で行う (オブジェクトなら名前、配列ならインデックス)

## 3. 配列インデックスの寿命

- インデックスは **リクエストを送った瞬間の配列状態** にのみ有効な座標だ
- 項目が一つ削除されるとエラーが下の行にずれる → 問題のない欄に赤線、誤った行には無表示
- 実測: 誤配置 2/2 → 安定識別子に変えると 0/2
- **識別子はリクエストスキーマに先になければならない。** クライアントが送っていない値をサーバは返せない
- 追加・並び替えでも同じ問題が起きる。削除だけ気を付ければよい問題ではない

## 4. レスポンス設計

```
{
  "error": "validation_failed",
  "truncated": false,
  "totalErrors": 6,
  "errors": [
    {
      "path": "items.2.qty",
      "keyPath": "items[ln_5518].qty",
      "rule": "min",
      "params": { "min": 1, "got": 0 },
      "message": "知らない規則のときだけ使う既定文"
    }
  ]
}
```

| フィールド | 誰が使うか | ないと |
|---|---|---|
| `path` | 画面・ログ | どの欄を塗るか決められない |
| `keyPath` | 画面(配列) | 項目がずれると別の行に表示 |
| `rule` | 画面(文言選択) | 文をパースすることになり修正が破壊に |
| `params` | 画面(文言組立) | 「最小1」の1を入れられない |
| `message` | 画面(未知の規則のみ) | 説明のない赤い欄 |
| `truncated` | 画面(一覧) | 切られた一覧を全部だと信じる |
| `totalErrors` | 画面・監視 | 何件切られたか知らせられない |

- **マップではなく一覧。** 一つのフィールドに規則二つが同時に失敗しうる
- 最初のエラーだけ渡すと実測往復6回、すべて集めれば1回
- 項目1,000個の一括リクエスト = エラー2,000件 = 文を含めると263 KB → 上限 + `truncated` が必須

## 5. クライアント紐付け

```
function applyErrors(resp, form) {
  let shown = 0;
  for (const e of resp.errors) {
    const el = form.querySelector('[name="' + cssEscape(e.path) + '"]');
    if (el) { markField(el, textFor(e.rule, e.params)); shown++; continue; }
    if (e.path === '') { banner(textFor(e.rule, e.params)); shown++; continue; }
    // 知らない経路: 接頭辞を切り詰めて上位領域を探す
    const segs = parsePath(e.path);
    let box = null;
    for (let n = segs.length - 1; n > 0; n--) {
      if (box) break;
      box = form.querySelector('[data-scope="' + printPath(segs.slice(0, n)) + '"]');
    }
    if (box) { markScope(box, textFor(e.rule, e.params)); shown++; }
    else { banner(fallbackText(e)); shown++; }
  }
  // 不変条件: レスポンスの件数と画面に表示された件数が一致すること
  if (shown !== resp.errors.length) warnInDev(resp.errors.length - shown);
}
```

| 方針 | 表示 | 利用者が見るもの | 危険 |
|---|---|---|---|
| 無視 | 4/6 | 送信失敗、説明なし | **不変条件が破れる。既定にしない** |
| バナー | 6/6 | 上部に経路が露出 | 内部フィールド名が利用者に見える |
| 接頭辞昇格 | 6/6 | 関連領域に表示 + 残りはバナー | 昇格範囲が広いと誤解 |

## 6. 人向けの文言と機械向けの経路

- サーバが作るもの: **経路 ・ 規則コード ・ パラメータ**
- 画面が作るもの: **フィールド名 ・ 文**
- 実測: サーバの英文で欄を特定する方式は4ロケール中1つしか成功しない
- 冠詞一つ足すコピー修正で照合が即座に失敗 → **文言修正 = 互換性破壊**
- 文の長さは28~40文字とばらばら、経路は4回とも11文字で同一
- サーバは **未知の規則用の既定文** を一つ残す (最後の手段、パース対象ではない)

## 7. 点検項目

- [ ] エラーレスポンスの **表記法が仕様書に書かれて** いる
- [ ] ドット・スラッシュ・角括弧の入ったフィールド名で **往復試験** を通過させた
- [ ] 数値の **オブジェクトキー** がインデックスと誤解されないか確認した
- [ ] 配列項目のエラーに **安定識別子** が一緒に載る
- [ ] その識別子が **リクエストスキーマ** にも定義されている
- [ ] エラーが **一覧** であり、一つのフィールドに二つ付きうる
- [ ] 一覧に **上限** があり、切ったという表示が一緒に出る
- [ ] 画面が **文をパースしない**
- [ ] 規則コードごとに画面側の **文言項目** があり、ないとき警告が残る
- [ ] **空の経路** が本文全体を意味するという規約が文書にある
- [ ] 画面に **表示件数の不変条件** がある
- [ ] 入力要素名とリクエスト本文の経路が **同じ関数** から出る
- [ ] 知らない経路の処理方針が **画面ごとに同じ** である

## 8. してはいけないこと

- ❌ 一つのレスポンスの中で **表記法を混ぜる** — フレームワークのエラーとドメインエラーが混ざる場所
- ❌ エラーを **経路キーのマップ** で渡す — 一つのフィールドの二規則のうち一つが消える
- ❌ 配列エラーを **インデックスだけで** 指す — 削除・追加・並び替えですべてずれる
- ❌ 画面が **サーバの文をパース** する — コピー修正がそのまま障害に
- ❌ 知らない経路を **静かに捨てる** — 送信失敗 + 説明なし
- ❌ 一覧を **黙って切る** — 画面が残りを解決済みとして扱う
- ❌ 入力要素名を **手で書く** — 最初の項目挿入で本文の経路とずれる
