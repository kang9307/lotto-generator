本稿は、AIコーディングツールNuancedの開発者であり元GitHubシニアエンジニアであるAyman Nadeemが発表した技術回顧録「Plan mode is dead」の記述に基づき執筆された。一次情報で確認された経験的観察と著者の判断を主軸とし、未検証の定量的指標や個別製品に対する恣意的な評価を排除して分析する。

1. 計画中心コーディングアプリの登場と回顧の原点

AIコーディングツールの急速な普及に伴い、ソフトウェア開発の現場ではかつてない認知的不協和が顕在化し始めた。大規模言語モデルがわずか数分で数千行に及ぶコードを自動生成できるようになった結果、開発者は「何を、なぜ構築しているのか」を十分に検討する前に、膨大な保守管理の重荷を背負い込むことになった。機械のコード生成速度が人間のレビューや把握能力を大幅に上回ったことで、アーキテクチャ境界が崩壊し、検証されていない前提がコードベースの深層に早期固定される事態が日常化した。

こうした課題意識から、開発の最前面に「計画（Planning）」を据えようとする試みが現れた。元GitHubシニアエンジニアであり、AIコーディング製品Nuancedを手掛けたAyman Nadeemはその理念に強い確信を抱いて製品設計に着手した。著者は原文で次のように振り返っている。"My belief in this idea was so strong that I built and launched an entire desktop coding app around it." モデルの生成速度とコード量は爆発的に増大したにもかかわらず、その加速した開発ペースを支えるべきユーザーインターフェースが過去の形態にとどまっていたという着眼点がNuancedの原動力であった。著者はClaude Code CLIからConductorへ、そして登場したCodexへとツールを渡り歩きながら計画を丹念に練り上げたが、それを繰り返し改訂していく明確な置き場所がなく、チャットから計画の断片を新しいメッセージにコピー＆ペーストして直す不便さを記している。計画に居場所を与えたいというこの不便さが、Nuancedを作った動機であった。

しかし、専用デスクトップアプリを開発し公開した末に著者が突きつけられた現実は、当初の構想とは大きくかけ離れていた。著者は、自らが採用した計画重視のアプローチが失敗に終わったことを率直に認めた。そしてその失敗は、より広い視点において従来の「計画モード（Plan mode）」という抽象概念がもはや実用的でなくなった現実を浮き彫りにしたと記している。原文の記述は極めて明瞭である。"Nuanced's approach to planning failed, but it also revealed to me how plan modes more broadly aren't as useful anymore."

ここで極めて重要なのは、「計画モードは死んだ」という挑発的な命題が、計画を立てる思考行為そのものを否定しているわけではないという点である。批判の対象となっているのは、「計画モード」という硬直したインターフェースの抽象化と、そこで出力される長大なAI生成の仕様書文書である。開発ループの内部では依然として膨大な量の計画行為が絶え間なく行われているが、それが「計画（the plan）」と名付けられた単一の文書として結実する必要はないというのが、この回顧の核心である。

  • AIの高速なコード生成と人間のレビュー速度の乖離によって生じる認知的不協和の顕在化
  • 設計と前提の整合性を図るべく計画段階を主軸に据えたコーディング製品Nuancedの開発
  • 実際の製品運用を通じて判明した計画モードアプローチの限界と著者自身の失敗の認定
  • 否定の対象が「計画行為」ではなく「計画モードというUI抽象化と膨大な成果物文書」であることの確認

2. 計画モードが担ってきた2つの歴史的目的

著者は、エージェント支援型コーディングにおいて計画モードが歴史的に解決しようとしてきた課題を、2つの独立した軸に分解して定義した。この2つの目的を混同したまま議論を進めると、現代の計画モードが直面している摩擦の本質を見失うことになる。

原文において著者は、計画モードが担ってきた目的を明確に整理している。"Historically, plan modes served two purposes: (1) they specified instructions that were sufficiently precise enough for an agent, and (2) they helped humans understand what they were building." 1つはエージェントの実行精度を担保するための精密な指示書としての機能であり、もう1つは人間の開発者がシステムの全体像を頭の中で把握するための認知的補助具としての機能である。

計画モードの歴史的目的 著者の判断 原文の根拠引用
目的1: エージェントに対する精密な指示の提示 モデル性能の飛躍的向上に伴い急速に形骸化 "I think #1 is rapidly becoming obsolete as models get better."
目的2: 人間によるシステム構造の理解支援 かつてないほど重要だが計画モードは不適切な抽象化 "I think #2 matters more than ever, but plan modes are the wrong abstraction for it"

2.1 エージェント向け精密指示の形骸化

初期世代の自律型コーディングエージェントにおいて、開発者は簡潔な自然言語プロンプトだけで期待通りの結果を得ることは困難であった。モデルが文脈を見失い、誤った前提をもとに既存コードを破壊する危険が常に存在したため、実装に着手する前に詳細な変更手順や影響範囲を記した計画書を出力させ、逸脱を防ぐための厳格なガードレールとして機能させることが不可欠であった。

しかし、フロンティアモデルの推論能力が劇的に向上したことで、状況は一変した。現代のモデルは簡潔な対話の中からでも背後にある意図を的確に汲み取り、暗黙の制約を自律的に補完しながら、ツール呼び出しを通じて自己修正を行える水準に達している。その結果、エージェントを一歩ずつ誘導するための詳細な事前仕様書を人間が介在して作成させる実務的価値は急速に薄れた。目的1は、モデルの進化によって急速に時代遅れになりつつある。

2.2 システム全体を把握しようとする人間の理解需要

一方で、2つ目の目的である「人間が何を作っているのかを理解すること」は、かつてないほど切実な課題として浮上している。エージェントが自律的に複数ファイルを一括変更できるようになった。著者は、ConductorやCodexのようなコーディングアプリでより多くのエージェントを並列に動かせるようになるにつれ、精神的に切り離され、ゾンビのような（zombie-like）感覚を覚えたと書いている。

著者はこの理解の問題こそが、ソフトウェア工学において永続的に問われ続ける本質的命題であると捉えた。機械が人間のレビュー速度を超えてシステムを変更し続ける環境下で、人間はいかにして一貫したメンタルモデルを維持できるかという問いである。しかし著者は、従来の計画モードというインターフェースはこの理解を支えるための抽象化として根本的に誤っていると結論付けた。

3. Nuancedが直面した失敗の4大要因

著者は、既存ツールの隙間についての考え自体が誤っていたというより、自分たちの実装が期待した解決策をもたらさなかったと見ており、その理由を原文で4つの命題にまとめている。"I conflated planning with a plan / models got really good / no one wants to read AI-generated text / we separated planning from building in a way that was disruptive".

第1に、「計画する行為（Planning）」と成果物としての「計画文書（Plan）」を混同したことである。ソフトウェア設計の本質は、何を作るべきか、なぜそれが重要なのかを考え抜き、トレードオフを比較検討する思考の動的プロセスにある。Nuancedはその思考の営みを静的なテキスト文書という成果物に閉じ込めてしまった。

第2に、基礎となるAIモデルの能力が予想を上回る速度で向上したことである。モデルが文脈を直接把握して高精度にコードを処理できるようになったため、よく練られた結果を出すようエージェントに明示的に指示する必要が大きく減った（"had shrunk"）。

第3に、人間はAIが生成した長文テキストを読みたがらないという普遍的な心理である。初期ユーザーは生成された仕様書に対して驚くほど関心を示さなかった("But early users had surprisingly little appetite for that spec.")。それどころか開発者である著者自身も、画面を埋め尽くすAI仕様書を前に集中力を失い、目がかすむような感覚を覚えた("My eyes kept glazing over.")。この問題を緩和するために導入した、仕様の重要な部分を案内する機能（Spec Tour）も、余計な複雑さを上乗せしただけに終わった("But that only bolted on an additional layer of complexity")。

第4に、計画モードと実装モードを分離した設計そのものが開発フローを分断したことである。ユーザーに対して「いま計画中か、実装中か」という状態遷移を意識させ、手動で切り替えさせる構造は認知負荷を増やした。著者は、こうした区別はAIがすでに保持している豊富な文脈に基づき自動的に判断すべき性質のものであると実感した("This felt like the kind of distinction AI should make for you based on context it already has")。

  • 思考の動的プロセスである計画行為を静的なテキスト成果物へ矮小化した概念的過誤
  • フロンティアモデルの急速な進化による中間仕様書の技術的有用性の急速な低下
  • AIが生成した長大で無機質なテキストに対する人間の強い読解忌避と疲弊
  • 計画と実装のモード分離がもたらした作業文脈の破壊的断絶と操作オーバーヘッド

4. 線形仕様パイプラインと循環型探索ループの対比

Nuancedが当初構築したのは、典型的なウォーターフォール式の線形パイプラインであった。エージェントとの対話で曖昧さを解消し、詳細な仕様書を生成して人間がレビュー・承認し、その後に実装へ進むという流れである。しかし実際の開発において真に機能したのは、チャットインターフェースを通じて必要に応じて計画を紡ぎ出す循環的な探索ループであった。

著者は原文において、自らが設計した初期パイプラインと、エージェントの向上によって可能になった別のループを原文の表記そのままに対比させた。この対比は、ソフトウェア開発におけるアプローチの根本的な転換を端的に示している。

ワークフロー区分 段階的な進行手順（原文の表記そのまま） 人間の介入ポイント（原文に基づく）
Nuancedの線形パイプライン chat → disambiguate by answering questions → generate spec → review spec → revise spec → approve → implement → review code 質問への回答、仕様書の確認および修正承認、最終コードレビュー
新たな循環型ループ understand → act → inspect → clarify → adjust → act again 原文はこのループでの人間の介入点を特に記していない（エージェントが自ら検査・修正できるようになって可能になったループとして説明）

4.1 8段階の線形構造が抱えていた脆弱性

Nuancedの線形モデルは、実装前の完全な仕様策定を前提としていた。開発者がチャットを開始すると、システムは質問を通じて曖昧さを排除し、完全な仕様書を自動生成する。開発者はその仕様書を精読し、修正を加えた上で正式に承認しなければ、エージェントによる実装を開始できなかった。

このアプローチの致命的な欠陥は、実際にコードが動作し画面に結果が反映されるまで、システムの挙動を直感的に体感できない点にあった。ソフトウェアの設計判断の多くは、具体的な動作を目の当たりにした瞬間に初めて明確になる。原文は、インターフェースが実装を始めるためにユーザーへ早まって「考えるのを終える」よう強いたこと、そして実装が始まると前段のチャットでの思考に戻ることがワークフローを後戻りするように感じられたことを記している（"There was no going back up the waterfall."）。

4.2 6段階の循環型ループがもたらす俊敏性

対照的に原文は、現在のCodexの動き方では計画と実行の境界が消えつつあると見て、エージェントが自律的に行動し、結果を検査した後にアプローチを修正することに長けるにつれ、別のループが可能になったと説明する。文脈を理解（understand）し、行動し（act）、その結果を検査（inspect）する。検査によって新たな課題が見えれば要件を明確化（clarify）し、方向性を調整（adjust）して、再び次の行動へと移る（act again）。

原文はこう記す。"There is still an enormous amount of planning happening inside that loop, but it doesn't necessarily need to appear as a document called “the plan”." つまり、このループの内部でも実質的な計画行為は絶えず行われている。ただし、それは独立した重厚な文書として固定化されるのではなく、対話の文脈やコードの差分の中に溶け込み、必要に応じて即座に洗練される。著者は、初期設定として強制されるのではなく必要に応じて計画が織り込まれるチャットインターフェースの簡潔さこそが、極めて優れていたと振り返っている("the simplicity of a chat interface where planning was done as-needed rather than by default, was actually pretty great.")。

# 従来の線形仕様パイプライン
chat → disambiguate by answering questions → generate spec → review spec → revise spec → approve → implement → review code

# 循環型探索ループ
understand → act → inspect → clarify → adjust → act again

5. 最大の過ち — 理解のプロセスを成果物文書へすり替えたこと

Ayman Nadeemの回顧録において最も鋭敏で核心的な告白は、自らの最大の過失を総括した次の一文に集約されている。"I think the biggest mistake I made was turning the plan into an artifact instead of designing a process for improved human understanding."

この指摘は、AIツール開発者が陥りがちな構造的盲点を突いている。開発者が必要としていた真の価値は、複雑化するシステムを手放さずに把握し続けるための「理解のプロセス」であった。しかしツールの設計においてその本質は見失われ、形式的に整えられた「計画文書という成果物」を作ることが自己目的化してしまった。

原文が挙げる理由は具体的である。AI生成テキストは、そのペース配分と過度に構造化された性質のために非常に読みにくいという（"There's something about the pacing and overly structured nature of AI-generated text that makes it very difficult to read."）。また原文は、チャットで判断を詰めていくほうが直感的だが、システムが変わるにつれてその理解を最新に保つことは依然として未解決の問題だと記している。

著者は計画モードという形態は終焉を迎えるべきだと論じつつも、思考の価値は決して失われていないと念を押している。"Thinking through what to build, why it matters, and evaluating decisions remains important. People need to build a coherent mental model of what's going on, but I don't think a large body of AI-generated text is the right interface for that." 何を作るべきか、なぜそれが重要なのかを考え抜き、設計判断を厳密に評価する営みはエンジニアリングの根幹であり続ける。人は何が起きているかについて一貫したメンタルモデルを築く必要があるが、AIが吐き出した長大なテキストの塊は、そのための適切なインターフェースではない。

  • 人間の認知的理解を向上させるプロセス設計を怠り成果物作成へ逃避した過ちの認識
  • AI生成テキストの読みにくさと、システムの変化に合わせて理解を最新に保つ問題が未解決であること
  • 何をなぜ作るべきかを問い直すエンジニアリング思考そのものの重要性の再確認
  • 長大なAI生成テキストが人間の直感的なアーキテクチャ把握を阻害するという明確な結論

6. 数百のエージェント時代における未解決の課題と人間の注意力

従来の計画モードが解法にならなかったことが判明したとしても、人間の理解という根本課題が解決されたわけではない。著者は、ツールが進化する陰で依然として未解決の課題が残っていると書いている。"We still haven't solved how to help people stay oriented as hundreds of increasingly capable agents change a system at once."

単一のエージェントが補助的なコードを書く段階を超え、高度な能力を持つ数十、数百のエージェントがバックエンドやフロントエンド、インフラ構成を並行して同時に改変していく時代が到来しつつある。システム全体のあらゆる部位が機械の手で一斉に書き換えられる状況下で、人間の開発者が迷子にならず方向感覚を保ち続けるための方法を、著者はまだ解決できていないと記している。

この未解決の問いに対し、著者はエージェントが果たすべき真の役割について明確な指針を提示した。エージェントがなすべきことは、何十ページもの冗長な仕様書を人間へ押し付けることではない。原文で著者はエージェントの責務を次のように定義している。"Agents need to identify the fewest places where human attention can have the greatest impact and surface enough context to make that attention useful."

人間の注意力は常に希少でスケーリングしない資源である。一方で、機械によるコード生成能力は事実上無制限に拡張可能である。したがって優れたエージェントであるならば、人間の限られた注意力が最も決定的な影響を及ぼし得る最小限の介入箇所を正確に特定しなければならない。そして人間が的確な意思決定を下せるよう、余計なノイズを排除した上で必要十分な文脈だけを簡潔に提示する対話インターフェースが求められている。

  • 数百のエージェントが並行してコードを変更するマルチエージェント環境下での方向感覚喪失リスク
  • テキスト生成主導の既存ツールが人間のメンタルモデル崩壊を防ぎきれていない現実
  • 人間の注意力が最大の影響力を発揮できる最小限の介入点を特定するというエージェントの責務
  • 意思決定に直結する高純度の文脈のみを精緻に浮き彫りにするインターフェース設計の必要性

7. 仕様書固定論との関係性 — 衝突ではなく前提の相違

以下の区別は本稿の解釈である。Ayman Nadeemの失敗回顧は、近年ソフトウェアエンジニアリング界隈で議論されている仕様駆動開発（Spec-Driven Development）の潮流と一見すると真っ向から対立しているかのように映るかもしれない。例えば、対話セッションの文脈蒸発を防ぐために提案書や設計書をリポジトリ上にファイルとして固定するOpenSpecフレームワークの分析や、実装前に数学的な不変条件を形式検証するTLA+に基づく仕様先行開発、さらにはエージェントの観測可能な振る舞いを明確に規定するエージェント振る舞い仕様の分析は、いずれも「仕様を文書として固定すること」の効用を説いているからである。

しかし、この相違を「仕様書を書くべきか否か」という短絡的な対立として捉えるのは建設的ではない。双方は衝突しているのではなく、解決しようとしている問題の前提条件と対象領域が異なっていると解釈するのが極めて妥当である。

OpenSpecのような仕様固定アプローチは、チーム間でのコラボレーション、非同期に投入される複数のエージェント間の規約共有、そしてGitの履歴上に設計意図を永続的に記録することを主眼に置いている。すなわち、分散した複数の人間や機械が共通の基準を参照できるようにするための成果物としての価値を追求している。

これに対しAyman Nadeemの回顧は、並列で動かすエージェントが増えるほど、人間がシステムへの理解と方向感覚を失わないようにするという問題に焦点を当てている。原文は目的2について計画モードは誤った抽象化だとしたうえで "especially as the number of parallel agents we run increases" という但し書きを付け、この問題はエージェントが5つから数百へと増えるほど難しくなると記す。そうした状況で、AI生成の長大な仕様書を逐一読み込み承認させる方式は、人間の理解を助ける適切なインターフェースではないという指摘である。したがって本稿の解釈では、チーム共有や永続的ガバナンスのための仕様固定が不可欠な領域が存在する一方で、人間のシステム理解を支える領域では、固定された計画モードとは別の抽象化が必要だということになる。

比較の視点 仕様書固定論（OpenSpec等） 計画モード回顧（Ayman Nadeem）
主たる問題意識 対話セッション終了に伴う設計意図の消失 AI生成の長大な計画文書を読む人間の認知的疲弊
仕様の性質 チーム共有と長期保守のための形式化された成果物 リアルタイムな探索ループを阻害する重い抽象化
最適な適用領域 複数エージェント間や複数人での開発契約の定義 並列エージェントが増えるほど人間が方向を見失わないようにする問題
中核となる狙い 設計文脈の永続的記録と客観的検証基準の確立 人間の注意力が最大効果を生む最小介入箇所の捕捉
