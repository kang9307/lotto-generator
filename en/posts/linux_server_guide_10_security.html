Introduction: Security is Not Optional

Server security requires a Defense in Depth strategy, not a single solution. In this final part, we cover the essentials of Linux server security hardening.

The commands and settings here were re-checked against the official documentation of OpenSSH, Linux-PAM, UFW, DNF Automatic and Greenbone (2026-09-29). Parts that differ by distribution (package names, service names, log locations) are marked in the text. When you change SSH, the firewall or PAM on a remote server, the premise of every procedure is to keep your current session open and test from a new terminal. Use these commands only on servers you own or are authorized to administer.

1. System Hardening Basics

1.1 Disable Unnecessary Services

# Check running services
systemctl list-units --type=service --state=running

# Disable unneeded services (an error just means the service is not installed)
sudo systemctl disable --now cups
sudo systemctl disable --now avahi-daemon
sudo systemctl disable --now bluetooth

# List services enabled at boot
systemctl list-unit-files --type=service --state=enabled

On a production server, check what depends on a service before you turn it off, for example with systemctl list-dependencies --reverse SERVICE.

1.2 Security Updates

# Ubuntu/Debian
sudo apt update && sudo apt upgrade -y
sudo apt install unattended-upgrades
sudo dpkg-reconfigure unattended-upgrades

# RHEL family (RHEL, Rocky Linux, AlmaLinux)
sudo dnf update -y
sudo dnf install dnf-automatic
# dnf-automatic.timer follows automatic.conf, and apply_updates defaults to False (nothing gets installed)
sudo systemctl enable --now dnf-automatic-install.timer

On the RHEL family, dnf-automatic.timer simply follows automatic.conf, and apply_updates defaults to False. Enabling only that timer therefore downloads or reports updates without installing them. To automate installation, use dnf-automatic-install.timer (DNF Automatic docs). The earlier version of this article told readers to enable the former, which would not actually install anything.

1.3 GRUB Security

# Debian/Ubuntu. Back up first and make sure you have console access
sudo cp -a /etc/grub.d/40_custom /root/40_custom.bak

# Generate the GRUB password hash
sudo grub-mkpasswd-pbkdf2
# Copy the hash

# Edit /etc/grub.d/40_custom
set superusers="admin"
password_pbkdf2 admin grub.pbkdf2.sha512...

# Apply (Debian/Ubuntu)
sudo update-grub

A GRUB password protects boot-menu editing, and a mistake can leave you unable to use the boot menu. Back up 40_custom and make sure you have console access (VM console, IPMI and so on) first. The RHEL family uses different commands, which this article does not cover.

2. User Security

2.1 Password Policies

# /etc/login.defs
PASS_MAX_DAYS   90    # Maximum age
PASS_MIN_DAYS   7     # Minimum age
PASS_WARN_AGE   14    # Expiry warning

# PAM password complexity (Debian/Ubuntu: /etc/pam.d/common-password)
password requisite pam_pwquality.so retry=3 minlen=12 dcredit=-1 ucredit=-1 ocredit=-1 lcredit=-1

# Apply to an existing user
sudo chage -M 90 -m 7 -W 14 username

The RHEL family has no /etc/pam.d/common-password. The same options (minlen and so on) go into the pwquality configuration; follow your distribution's documentation for the exact location. When editing PAM files, keep an open root session and test from another terminal with passwd.

2.2 sudo Configuration

# /etc/sudoers (always edit with sudo visudo - a syntax error can break sudo itself)
# Logging
Defaults logfile=/var/log/sudo.log
Defaults log_input, log_output

# Timeout
Defaults timestamp_timeout=5

# Allow only a specific command
username ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx

Use the NOPASSWD example only when it is narrowed to a single command. If the scope grows, compromising that account immediately means root access.

2.3 Account Lockout

# RHEL family: enable the faillock feature via authselect (replaces pam_tally2)
sudo authselect current
sudo authselect enable-feature with-faillock

# /etc/security/faillock.conf
deny = 5
unlock_time = 900

# Check failures / unlock
sudo faillock --user username
sudo faillock --user username --reset

pam_tally2 was removed in Linux-PAM 1.5.0 (1.5.0 release notes: "Removed deprecated pam_tally and pam_tally2 modules, use pam_faillock instead"). The pam_tally2.so deny=5 unlock_time=900 line used in the earlier version of this article does not work on later distributions; its successor is pam_faillock. The configuration file is /etc/security/faillock.conf, with defaults of deny 3 attempts, fail_interval 900 seconds and unlock_time 600 seconds (faillock.conf(5)). To prevent denial of service, root is not locked by default (pam_faillock(8)), but even_deny_root changes that. A locked remote root is hard to recover without console access, so confirm console access before turning it on.

On Debian/Ubuntu you have to add the pam_faillock lines to common-auth and common-account yourself, following the order in the man pam_faillock example (preauth in auth, pam_unix, authfail, then account). Back the files up first, and test by logging in as another account while keeping an open root session.

3. SSH Security Hardening

# 0) Back up before editing. Do NOT close your current SSH session
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

# /etc/ssh/sshd_config

# Change the default port (optional). Only after preparing the firewall (section 4) and, on RHEL family, the SELinux port label (section 6.1)
Port 2222

# Disable root login
PermitRootLogin no

# Disable password authentication - only after key login is confirmed in a NEW session
PasswordAuthentication no

# Allow key authentication
PubkeyAuthentication yes

# Forbid empty passwords
PermitEmptyPasswords no

# Limit login attempts
MaxAuthTries 3
LoginGraceTime 30

# Allow specific users only (if you also use AllowGroups, check the combination rules in sshd_config(5) and test first)
AllowUsers admin deploy
#AllowGroups sshusers

# (Protocol 2 is no longer needed: OpenSSH 7.4 removed SSH v1 server support)

# 1) Syntax check - no output means OK
sudo sshd -t
# 2) Show the effective settings
sudo sshd -T | grep -Ei '^(port|permitrootlogin|passwordauthentication|maxauthtries) '

# 3) Apply (service name is ssh on Debian/Ubuntu, sshd on RHEL family)
sudo systemctl restart ssh
sudo ss -tlnp | grep sshd

# 4) Keep the old session open and test from a NEW terminal
ssh -p 2222 admin@server

# 5) If it fails, roll back from the session you kept open
sudo cp -a /etc/ssh/sshd_config.bak /etc/ssh/sshd_config
sudo systemctl restart ssh

OpenSSH defaults are PermitRootLogin prohibit-password, MaxAuthTries 6 and LoginGraceTime 120 seconds (sshd_config(5)). The Protocol 2 line was dropped because it has no meaning since OpenSSH 7.4 removed SSH v1 server support (7.4 release notes). sshd -t checks the validity of the configuration file and keys, and sshd -T prints the effective configuration (sshd(8)). The Ubuntu documentation tells you to check the configuration with sudo sshd -t before restarting and warns that a mistake can lock you out of the server (Ubuntu Server docs). So follow the order above (back up, syntax check, restart, test from a new terminal, roll back on failure) and do not close the existing session until testing is finished.

It is unconfirmed whether changing Port takes effect on a plain restart when Ubuntu uses socket activation (ssh.socket). After restarting, check the port actually being listened on with ss -tlnp | grep sshd. Changing the port only reduces log noise from automated scans; the real defenses are key authentication and access restrictions. Read sshd_config(5) and test before combining AllowUsers with AllowGroups.

4. Firewall Configuration

4.1 UFW (Ubuntu)

# Default policy
sudo ufw default deny incoming
sudo ufw default allow outgoing

# ★ Allow SSH BEFORE ufw enable. The port must match what sshd actually listens on
sudo ss -tlnp | grep sshd
sudo ufw allow 2222/tcp comment 'SSH'
sudo ufw allow 80/tcp comment 'HTTP'
sudo ufw allow 443/tcp comment 'HTTPS'

# IP-based restriction (same SSH port 2222 as above)
sudo ufw allow from 192.168.1.0/24 to any port 2222 proto tcp

# Enable. If you get locked out, run sudo ufw disable from the console
sudo ufw enable
sudo ufw status verbose

The manual says ufw enable flushes its chains and may drop existing connections such as SSH (ufw(8)). So add the SSH allow rule before enable, and make its port match the port sshd actually listens on. The earlier version of this article changed SSH to 2222 but wrote the IP-restriction rule for port 22, which contradicted itself. A ufw limit rule denies connections from an IP that attempts 6 or more connections within 30 seconds.

4.2 firewalld (RHEL/CentOS)

# Check the default zone
sudo firewall-cmd --get-default-zone

# Allow services
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https

# Allow a port - open the new SSH port BEFORE restarting sshd with it
sudo firewall-cmd --permanent --add-port=2222/tcp

# Apply the rules, then verify
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

When you change sshd's Port, finish the firewall --permanent rule and --reload, plus the SELinux port label (section 6.1), before restarting sshd. If the order is reversed, you cannot connect on the new port, or sshd fails to start.

5. Intrusion Detection Systems

5.1 Fail2Ban

# Install (on RHEL family use dnf; which repository ships it varies by distribution)
sudo apt install fail2ban

# /etc/fail2ban/jail.local
[DEFAULT]
bantime = 3600
findtime = 600
maxretry = 3
# Add your admin IP so you never ban yourself
ignoreip = 127.0.0.1/8 ::1

[sshd]
enabled = true
port = 2222
# On journald-only systems (no /var/log/auth.log) read the journal instead
backend = systemd
# File-based logs: logpath = /var/log/auth.log

[nginx-http-auth]
enabled = true

# Start and check status
sudo systemctl enable --now fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
# Unban a wrongly banned IP
sudo fail2ban-client unban 203.0.113.10

Systems that use only the journal (journald), such as Debian 12, have no /var/log/auth.log, so a logpath alone leaves the sshd jail with nothing to read. On such systems use backend = systemd. This part, and the ignoreip and unban options, were confirmed from secondary sources rather than by checking the fail2ban documentation directly. After applying, verify the jail is actually working with fail2ban-client status sshd.

5.2 AIDE (Integrity Checking)

# Install (Debian/Ubuntu)
sudo apt install aide

# Initialize the database
sudo aideinit

# Run a check
sudo aide --check

# Update the database
sudo aide --update

6. SELinux / AppArmor

6.1 SELinux (RHEL/CentOS)

# Check status
getenforce
sestatus

# Change mode (until reboot). Permissive is for diagnosis only
sudo setenforce 0  # Permissive
sudo setenforce 1  # Enforcing

# Persistent setting (/etc/selinux/config)
SELINUX=enforcing

# If you changed the SSH port, label it BEFORE restarting sshd (otherwise bind fails with Permission denied)
sudo semanage port -a -t ssh_port_t -p tcp 2222
sudo semanage port -l | grep ssh_port_t

# Troubleshooting
sudo ausearch -m avc -ts recent
sudo sealert -a /var/log/audit/audit.log

On the RHEL family, if you changed the SSH port, SELinux only lets sshd bind to ports labeled ssh_port_t. Restarting without the label makes sshd fail with Permission denied. semanage ships in the policycoreutils-python-utils package. This procedure was confirmed from secondary sources, not official documentation. sealert may require installing an extra package. setenforce 0 is a diagnostic step to isolate the cause; switch back with setenforce 1 as soon as you are done.

6.2 AppArmor (Ubuntu)

# Check status
sudo aa-status

# Manage profiles
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx
sudo aa-complain /etc/apparmor.d/usr.sbin.nginx

# Check the logs
sudo journalctl -fx | grep apparmor

7. Vulnerability Scanning

7.1 Lynis

# Install
sudo apt install lynis

# Audit the system
sudo lynis audit system

# View the reports
sudo cat /var/log/lynis.log
sudo cat /var/log/lynis-report.dat

7.2 OpenVAS

# Greenbone Community Edition: follow the official container guide
# https://greenbone.github.io/docs/latest/22.4/container/index.html
# (Needs Docker/Podman and docker-compose. Officially documented distros: Debian stable, Ubuntu 24.04 LTS, etc.)
# Scan only systems you own or are authorized to scan
docker compose version

The earlier version of this article walked through apt install openvas and gvm-setup, but the official Greenbone documentation describes container installation (Docker/Podman plus docker-compose) and does not cover distribution-package installs. The distributions it states support for are Debian stable (bookworm), Ubuntu 24.04 LTS and others, and the container guide itself says it is not intended for production setups (Greenbone Community Containers). Scan only systems you own or are authorized to scan.

8. Log Monitoring

# Monitor suspicious activity
# Failed logins (Debian/Ubuntu)
sudo grep "Failed password" /var/log/auth.log | tail -20
# Failed logins (RHEL family)
sudo grep "Failed password" /var/log/secure | tail -20
# journald-only systems (use -u sshd on RHEL family)
sudo journalctl -u ssh --since today | grep "Failed password" | tail -20

# sudo usage
sudo grep "sudo" /var/log/auth.log

# System boot/shutdown
last reboot
last shutdown

# Currently logged-in users
who
w

# Network connections
ss -tuln

Log locations differ by distribution: /var/log/auth.log on Debian/Ubuntu, /var/log/secure on the RHEL family, and journalctl on systems that use only the journal. The netstat line from the earlier version was removed because it serves the same purpose as ss.

9. Security Checklist

#!/bin/bash
# security_audit.sh (read-only checks)

echo "=== Linux Security Audit ==="

echo -e "\n[1] Pending system updates"
apt list --upgradable 2>/dev/null | head -10

echo -e "\n[2] Root login (effective setting)"
sudo sshd -T 2>/dev/null | grep -i "^permitrootlogin"

echo -e "\n[3] Password authentication (effective setting)"
sudo sshd -T 2>/dev/null | grep -i "^passwordauthentication"

echo -e "\n[4] Listening ports"
ss -tuln | grep LISTEN

echo -e "\n[5] SUID files (same filesystem only)"
find / -xdev -perm -4000 -type f 2>/dev/null | head -10

echo -e "\n[6] Empty-password accounts (needs root)"
sudo awk -F: '($2 == "") {print $1}' /etc/shadow

echo -e "\n[7] Recent failed logins"
sudo grep "Failed password" /var/log/auth.log /var/log/secure 2>/dev/null | tail -5

echo -e "\n[8] Firewall status"
sudo ufw status 2>/dev/null || sudo firewall-cmd --state 2>/dev/null

echo -e "\nAudit complete"

# Remote Server Security Change Checklist - SSH, Firewall, PAM

As of: 2026-09-29
Sources: OpenSSH 7.4 release notes, sshd(8), sshd_config(5), ufw(8), Linux-PAM 1.5.0 release notes, faillock.conf(5), DNF Automatic docs, Greenbone Community Containers docs

---

## 1. Before any change (SSH, firewall, PAM)

- [ ] Keep your current session open until testing is finished
- [ ] Confirm you have console access (VM console, IPMI)
- [ ] Back up the file you are about to edit (`cp -a file file.bak`)

## 2. Order of an SSH configuration change

| Step | Action | Command |
|---|---|---|
| 1 | Back up | `sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak` |
| 2 | Syntax check (no output means OK) | `sudo sshd -t` |
| 3 | Show effective settings | `sudo sshd -T` |
| 4 | Restart (ssh on Debian/Ubuntu, sshd on RHEL family) | `sudo systemctl restart ssh` |
| 5 | Check the port actually listened on | `sudo ss -tlnp` |
| 6 | Test from a new terminal | `ssh -p PORT user@server` |
| 7 | On failure, roll back from the old session | restore `.bak`, restart |

- [ ] Key login succeeded in a new session before turning off password authentication
- [ ] Do not add a `Protocol 2` line (OpenSSH 7.4 removed SSH v1 server support)

## 3. If you change the SSH port (order matters)

- [ ] Open the new port in the firewall first (UFW: `ufw allow`; firewalld: `--permanent` then `--reload`)
- [ ] On the RHEL family, add the SELinux port label (`semanage port -a -t ssh_port_t -p tcp PORT`)
- [ ] Only then restart sshd
- [ ] With UFW, add the SSH allow rule before `ufw enable` (enable may drop existing connections)

## 4. Login-failure lockout

| Item | Value |
|---|---|
| `pam_tally2` | Removed in Linux-PAM 1.5.0 - do not use |
| Replacement | `pam_faillock` (config `/etc/security/faillock.conf`) |
| Defaults | deny 3 / fail_interval 900 s / unlock_time 600 s |
| root | Not locked by default (change with `even_deny_root`) |

- [ ] Confirmed console access before locking remote root
- [ ] After editing PAM files, tested by logging in as another account

## 5. Automatic updates (RHEL family)

- [ ] To automate installation, enable `dnf-automatic-install.timer`
- [ ] Enabling only `dnf-automatic.timer` installs nothing because `apply_updates` defaults to False

## 6. Where distributions differ

| Item | Debian/Ubuntu | RHEL family |
|---|---|---|
| SSH service name | `ssh` | `sshd` |
| Auth log | `/var/log/auth.log` | `/var/log/secure` |
| Journal-only systems | `journalctl -u ssh` | `journalctl -u sshd` |
| fail2ban journal use | `backend = systemd` | same |
