Perry - TypeScript를 LLVM 기계어로 직접 컴파일하는 네이티브 컴파일러 2026

트랜스파일도 JIT도 없이, TypeScript에서 곧장 네이티브 바이너리로

2026-06-09 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: TypeScript는 정말 '느린 언어'였을까

TypeScript로 작성한 CLI 도구를 배포해 본 적이 있다면, 한 가지 불편을 기억할 겁니다. 단순히 인사 한 줄을 출력하는 프로그램조차 Node.js 런타임 수십 MB를 들고 다녀야 하고, 프로세스가 뜨는 순간 V8 엔진이 깨어나 코드를 해석하고 최적화하기 시작합니다. 우리가 "TypeScript가 느리다"고 말할 때, 사실 느린 것은 타입 시스템이 아니라 실행 모델입니다. 타입은 컴파일이 끝나면 지워지고, 남은 JavaScript는 거대한 가상 머신 위에서 다시 한번 해석됩니다.

2026년 6월, GeekNews(news.hada.io)에서 화제가 된 Perry는 이 전제를 정면으로 뒤집습니다. Perry는 TypeScript를 JavaScript로 트랜스파일하지도, V8 같은 무거운 JIT 런타임에 얹지도 않고, LLVM을 거쳐 곧장 네이티브 기계어로 컴파일합니다. 프로젝트 소개에 따르면 Perry는 Rust로 작성되었고, 파싱에는 SWC를, 코드 생성에는 LLVM을 사용해 Node.js·Electron·브라우저 엔진 없이 동작하는 단일 실행 파일을 만들어 냅니다. 이 글은 그 작동 원리와, 왜 이것이 기술적으로 흥미로운지를 차근차근 풀어 봅니다.

1. 기존 TypeScript 실행의 3단 구조

Perry가 무엇을 푸는지 이해하려면 먼저 '지금까지 어떻게 실행했는가'를 정확히 그려야 합니다. 전통적인 TypeScript 실행은 대략 세 단계를 거칩니다.

TypeScript 소스 (.ts)
   │   ① 타입 검사 + 트랜스파일 (tsc / swc / esbuild)
   ▼
JavaScript 소스 (.js)   ← 타입 정보는 여기서 전부 사라짐
   │   ② 파싱 + 바이트코드 생성 (V8 / JavaScriptCore)
   ▼
바이트코드 인터프리터 실행
   │   ③ 핫 코드 감지 → JIT 컴파일 → 기계어
   ▼
네이티브 기계어 (실행 중에 비로소 생성)

여기서 두 가지 비용이 발생합니다. 첫째, 타입 정보의 소실입니다. ①단계에서 TypeScript의 정적 타입은 검증에만 쓰이고 출력 JavaScript에서는 완전히 지워집니다. 그 결과 ②③단계의 엔진은 모든 값을 '무슨 타입인지 모르는 동적 값'으로 다시 가정하고 출발해야 합니다. 둘째, JIT의 워밍업입니다. V8은 처음에는 인터프리터로 느리게 실행하다가, 자주 도는 코드를 런타임에 관측해 비로소 기계어로 컴파일합니다. 시작은 느리고, 빨라지기까지 시간이 걸리며, 그 과정 자체가 메모리와 CPU를 먹습니다.

이 모델은 브라우저처럼 '코드를 미리 알 수 없는' 환경에서는 합리적입니다. 하지만 우리가 직접 작성해 배포하는 CLI나 서버는, 실행 전에 코드가 전부 정해져 있습니다. 그렇다면 굳이 실행 시점에 최적화를 미룰 이유가 있을까요? 바로 이 질문이 AOT 컴파일의 출발점입니다.

2. AOT vs JIT - 최적화의 시점을 옮긴다

JIT(Just-In-Time)와 AOT(Ahead-Of-Time)의 차이는 한 문장으로 요약됩니다. 언제 기계어를 만드느냐입니다.

구분 JIT (V8/Node.js) AOT (Perry)
기계어 생성 시점 실행 중 (런타임) 실행 전 (빌드 타임)
시작 속도 워밍업 필요, 느림 즉시 시작 (0ms에 가까움)
런타임 의존성 엔진+런타임 필요 단일 바이너리, 의존성 없음
최적화 정보원 실행 중 관측한 타입 컴파일 시점의 정적 타입
동적 코드(eval) 자연스럽게 지원 구조적으로 어려움

JIT의 강점은 '실제로 어떤 타입이 흐르는지를 보고' 최적화한다는 데 있습니다. 반대로 AOT는 실행을 보지 못하는 대신, 컴파일 속도를 신경 쓸 필요가 없습니다. 빌드는 한 번이고 실행은 수없이 반복되므로, C++이나 Rust가 하듯 무거운 정적 분석과 공격적 최적화를 마음껏 적용할 수 있습니다. Perry가 노리는 지점이 정확히 여기입니다. TypeScript는 이미 풍부한 정적 타입을 갖고 있으니, 그 타입을 버리지 말고 컴파일 시점 최적화의 연료로 쓰자는 것입니다.

JIT는 "실행하면서 타입을 알아낸다." AOT는 "타입을 이미 알고 있으니 미리 최적화한다." TypeScript처럼 타입이 명시된 언어에서 후자는 자연스러운 선택지다.

3. LLVM이란 무엇이고, 왜 쓰나

Perry의 코드 생성 백엔드는 LLVM입니다. LLVM을 한 문장으로 설명하면, '여러 언어의 프런트엔드와 여러 CPU의 백엔드 사이에 끼어, 강력한 최적화를 담당하는 산업 표준 컴파일러 기반'입니다. Clang(C/C++), Rust, Swift가 모두 LLVM 위에서 동작합니다.

LLVM의 핵심은 LLVM IR이라는 중간 표현입니다. 언어 프런트엔드(Perry의 경우 TypeScript)는 소스를 LLVM IR로 낮춰(lower) 주기만 하면, 그다음 인라이닝·상수 전파·루프 벡터화·죽은 코드 제거 같은 수십 가지 최적화 패스와, x86·ARM·WebAssembly 등 다양한 타깃으로의 기계어 생성을 LLVM이 떠맡습니다. 새 언어를 만들 때 최적화기와 코드 생성기를 처음부터 짤 필요 없이, 검증된 백엔드에 올라타는 것입니다.

흥미롭게도 Perry는 처음부터 LLVM을 쓴 것은 아닙니다. 프로젝트 블로그에 따르면 초기에는 Cranelift(빠른 단일 티어 컴파일러, WebAssembly 진영에서 주로 쓰임)를 백엔드로 썼다가 LLVM으로 옮겼습니다. 이유는 둘이었습니다. 첫째, Cranelift는 의도적으로 '빠르게 컴파일하는' 단일 티어 최적화기인데, 이는 실행 성능이 최우선인 AOT 컴파일러에는 잘못된 트레이드오프라는 것. 둘째, Apple Watch용 arm64_32 같은 타깃 지원 폭이 LLVM이 넓다는 것입니다.

핵심
Perry가 LLVM을 택한 것은 "느리더라도 더 깊게 최적화하는" 쪽을 고른 것입니다. 빌드가 조금 느려지는 대가로, 실행 파일은 C·Rust가 누리는 수준의 최적화를 받습니다.

4. Perry의 컴파일 파이프라인

Perry가 .ts 파일을 실행 파일로 바꾸는 과정을, 프로젝트 설명을 토대로 정리하면 다음과 같습니다.

TypeScript 소스
   │   SWC로 파싱 → AST
   ▼
AST → HIR(고수준 IR)로 낮춤 + 타입 추론
   │   IR 변환·최적화 패스
   ▼
LLVM IR 생성 (codegen)
   │   LLVM 최적화 + 타깃 기계어 생성
   ▼
런타임 라이브러리와 링크 → 단일 네이티브 실행 파일

각 단계를 짚어 보겠습니다. SWC는 Rust로 작성된 초고속 TypeScript/JavaScript 파서로, Perry는 이를 프런트엔드로 써서 소스를 추상 구문 트리(AST)로 만듭니다. 그다음 AST를 고수준 중간 표현(HIR)으로 낮추며 타입을 추론하고, 여러 변환 패스를 거친 뒤 LLVM IR로 코드 생성을 합니다. 마지막으로 Perry가 네이티브로 구현한 런타임 라이브러리와 링크해, 의존성 없는 하나의 바이너리를 뽑아냅니다. 프로젝트 소개에 따르면 'hello world' 수준의 출력은 수백 KB 규모이고, 표준 라이브러리를 풍부하게 쓰는 앱은 수십 MB까지 커집니다.

5. 타입 정보를 활용한 최적화

Perry의 진짜 묘미는 '타입을 버리지 않는다'는 데서 나옵니다. 일반 JavaScript 엔진이 런타임에 고생해서 추론해야 하는 정보를, TypeScript는 컴파일 시점에 이미 알려 줍니다. Perry는 그 정보로 다음과 같은 최적화를 한다고 소개합니다.

  • NaN-boxing: 숫자 값을 포인터나 박싱 없이 표현하는 기법으로, 숫자 연산의 오버헤드를 줄입니다.
  • 인라인 객체 할당: 객체를 범프 할당기(bump allocator)로 인라인 할당해 메모리 접근 비용을 낮춥니다.
  • i32 루프 카운터: 정수 값으로만 도는 반복문에서는 일반 부동소수가 아닌 32비트 정수 카운터를 써 루프를 더 빠르게 만듭니다.
  • 형상 캐시(shape cache) 객체: 객체의 모양을 캐시해 필드를 동적 탐색 없이 직접 접근합니다.
  • fast-math 플래그: 부동소수 연산에 fast-math를 허용해 루프 벡터화의 여지를 넓힙니다.

이 최적화들의 공통점은, 모두 '값의 타입을 안다'는 전제 위에서만 가능하다는 것입니다. JavaScript 엔진은 x + y가 정수 덧셈인지 문자열 결합인지 실행해 보기 전까지 확신할 수 없지만, TypeScript에서 x: number로 선언되어 있으면 컴파일러는 곧장 정수/부동소수 명령으로 낮출 수 있습니다. 정적 타입이 곧 최적화 정보가 되는 셈입니다.

이런 '타입을 활용한 컴파일 최적화'의 사고방식은 시스템 언어의 무손실 압축이나 메모리 할당 설계와도 결이 같습니다. 압축에서 데이터의 구조를 알수록 더 줄일 수 있는 것처럼, 컴파일러도 값의 구조를 알수록 더 줄일 수 있습니다. 이 맥락은 별도 글 Rust로 다시 쓴 Zstandard와 mimalloc 고성능 할당기에서 더 깊이 다룹니다.

6. 'LLVM으로 옮겼더니 70배 느려졌다'는 역설

Perry의 백엔드 전환기에는 교훈적인 일화가 있습니다. 프로젝트 블로그에 따르면, Cranelift에서 LLVM으로 처음 갈아탔을 때 일부 벤치마크가 오히려 70배 느려졌습니다. 더 강력한 백엔드로 옮겼는데 왜 느려졌을까요?

원인은 '경계'였습니다. 초기 LLVM 버전은 대부분의 연산을 불투명한 런타임 헬퍼 함수 호출로 처리했고, LLVM 입장에서 그 호출 안쪽은 들여다볼 수 없는 블랙박스였습니다. 함수 경계를 넘나드는 최적화(인라이닝, 상수 전파)가 막히니, 최적화기가 아무리 강력해도 할 일이 없었던 것입니다. Perry 팀은 핫 패스를 의도적으로 인라이닝해 이 경계를 허무는 작업을 거친 뒤에야, 비로소 LLVM의 진가를 끌어냈다고 설명합니다.

강력한 최적화기를 붙이는 것만으로는 빨라지지 않는다. 최적화기가 '볼 수 있도록' 코드를 펼쳐 줘야 비로소 그 힘이 발휘된다. 이는 모든 컴파일러 설계의 일반 원리다.

7. 그래서 얼마나 빨라지나 - 벤치마크의 맥락

최적화를 마친 뒤 Perry는 의미 있는 성능 향상을 보고합니다. 프로젝트가 공개한 한 릴리스 기준 벤치마크에서, Node.js 대비 다음과 같은 결과가 인용됩니다.

  • 재귀 팩토리얼: 약 24.6배 빠름
  • 메서드 호출: 약 11배 빠름
  • 루프 오버헤드: 약 4.4배 빠름
  • 수치 집약 연산: 약 3.5배 빠름

다만 이 숫자들은 신중히 읽어야 합니다. 위 항목들은 대부분 타입이 명확하고 반복이 많은 마이크로 벤치마크로, AOT와 정적 타입이 가장 유리한 영역입니다. 실제 애플리케이션은 I/O 대기, 메모리 할당, 라이브러리 호출이 뒤섞여 있어 체감 차이는 작을 수 있습니다. 또한 V8은 오랜 세월 다듬어진 세계 최고 수준의 JIT라, 동적 패턴이 많은 코드에서는 여전히 강력합니다. 'Perry가 항상 N배 빠르다'가 아니라, '정적 타입과 AOT가 유리한 워크로드에서 큰 차이가 난다'로 이해하는 편이 정확합니다.

8. 기존 시도들 - Perry는 처음이 아니다

TypeScript/JavaScript를 네이티브나 WebAssembly로 컴파일하려는 시도는 Perry가 처음이 아닙니다. 계보를 이해하면 Perry의 위치가 또렷해집니다.

8.1 AssemblyScript

AssemblyScript는 TypeScript의 부분 집합(subset)을 WebAssembly로 컴파일합니다. 문법은 TypeScript와 비슷하지만, 실제로는 별도 언어에 가깝습니다. 임의의 TypeScript를 받아들이지 않고, 명시적 정수 타입 등 자체 규칙을 따라야 합니다. 백엔드는 LLVM이 아니라 Binaryen(WebAssembly 툴체인)을 씁니다. '타입을 엄격히 제한해 네이티브에 가깝게 만든다'는 접근입니다.

8.2 Static Hermes

Meta(페이스북)의 Static Hermes는 React Native용 Hermes 엔진의 차세대 버전으로, TypeScript/Flow 타입 주석이 붙은 '건전하게 타입이 정해진' JavaScript를 빌드 타임에 네이티브로 AOT 컴파일하는 것을 목표로 합니다. 정적 타입으로 JIT의 추측을 줄여 더 빠르고 작은 결과물을 노립니다. 다만 공개 자료 기준 TypeScript 지원은 실험적이고 불완전하다고 명시되어 있습니다. Perry와 철학(타입으로 AOT)이 가장 가깝지만, Static Hermes는 React Native 생태계라는 분명한 무대를 가집니다.

8.3 Porffor

Oliver Medhurst가 만든 Porffor는 JavaScript/TypeScript를 AOT로 WebAssembly와 네이티브 바이너리로 컴파일하는 실험적 엔진입니다. 인터프리터를 번들링하는 대신 코드 자체를 컴파일하므로, 소개에 따르면 결과물이 기존 'JS→Wasm' 대비 훨씬 작고(바이너리가 최대 1000배 작아진 사례 인용) 빠릅니다. Porffor는 TypeScript뿐 아니라 JavaScript 전반의 표준 적합성(Test262)을 추구하는 폭넓은 목표를 가집니다.

프로젝트 입력 백엔드 주 타깃
Perry TypeScript LLVM 네이티브 바이너리
AssemblyScript TS 부분집합 Binaryen WebAssembly
Static Hermes 타입 붙은 JS/TS 자체+LLVM 계열 네이티브(RN)
Porffor JS/TS 자체→Wasm/네이티브 Wasm·네이티브

Perry의 차별점은 '평범하게 작성한 TypeScript를 받아 LLVM으로 곧장 네이티브 실행 파일을 만든다'는 직접성과, Rust로 재구현한 표준 라이브러리·패키지를 함께 제공한다는 점에 있습니다.

9. 표준 라이브러리와 npm 호환의 현실

네이티브 컴파일러에서 가장 까다로운 문제는 언어가 아니라 생태계입니다. TypeScript의 힘은 수십만 개 npm 패키지에서 나오는데, 그 패키지들은 대부분 Node.js 런타임 API(fs, http, net 등)를 전제로 합니다. Perry는 V8/Node를 들고 가지 않으므로, 이 API들을 직접 다시 구현해야 합니다.

프로젝트 소개에 따르면 Perry는 Rust로 작성된 고성능 표준 라이브러리를 갖추고, console·fs·path·process·JSON·Math·Date·crypto·Buffer·Map/Set·worker_threads 등을 네이티브로 제공합니다. 나아가 fastify·axios·PostgreSQL·MySQL·Redis·bcrypt·JWT 같은 인기 패키지의 드롭인 대체 구현도 다수 포함한다고 합니다. 즉 '아무 npm 패키지나 그대로 동작'하는 것이 아니라, Perry가 네이티브로 재구현해 둔 범위 안에서 동작하는 모델입니다.

// 소개에 따른 개념 예시: 별도 런타임 없이 단일 바이너리로 빌드되는 HTTP 서버
import { createServer } from "http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("Hello from a native TypeScript binary");
});

server.listen(8080, () => {
  console.log("listening on :8080"); // Node.js 없이 실행되는 바이너리
});

10. 한계 - 동적 기능과 생태계의 벽

균형을 위해 한계를 분명히 짚겠습니다. AOT 네이티브 컴파일은 공짜가 아니며, JavaScript의 가장 동적인 부분과 본질적으로 충돌합니다.

  • 동적 평가: 문자열을 런타임에 코드로 실행하는 eval이나 new Function은 '실행 전에 모든 코드를 컴파일한다'는 AOT 전제와 정면으로 부딪칩니다. 정적 컴파일러가 다루기 가장 어려운 영역입니다.
  • 미지원 기능: 프로젝트 문서 기준 데코레이터는 현재 미지원으로 명시되어 있습니다. 표준의 광활한 모서리들이 점진적으로 채워지는 단계입니다.
  • 생태계 호환: 네이티브 런타임 API에 의존하지 않거나 Perry가 재구현한 패키지만 동작합니다. 깊은 npm 의존성 트리를 가진 기존 대형 앱을 그대로 옮기긴 어렵습니다.
  • 성숙도: 소개 기준 버전이 0.5.x대로, 활발히 개발 중인 초기 단계입니다. 프로덕션 전면 도입보다는 적합한 워크로드에서의 검증이 먼저입니다.

요컨대 Perry는 '모든 TypeScript 앱의 Node.js 대체재'가 아니라, '특정 워크로드에서 TypeScript를 시스템 언어처럼 쓰게 해 주는 도구'로 보는 편이 정확합니다.

11. 어디에 쓰면 좋은가 - 활용 시나리오

그렇다면 Perry의 강점이 빛나는 곳은 어디일까요? AOT·단일 바이너리·즉시 시작이라는 성격을 그대로 따라가면 답이 나옵니다.

  • CLI 도구: 런타임 의존성 없는 단일 바이너리는 배포가 단순하고 시작이 즉각적입니다. 사용자가 Node를 설치할 필요가 없습니다.
  • 서버리스·엣지: 콜드 스타트가 곧 비용·지연인 환경에서, 워밍업 없는 즉시 시작은 분명한 이점입니다.
  • 임베디드·제약 환경: 작은 바이너리와 낮은 메모리 사용은 자원이 빠듯한 디바이스에 유리합니다.
  • 성능 민감 워크로드: 타입이 명확하고 수치 연산이 많은 작업에서 네이티브에 가까운 성능을 노릴 수 있습니다.

이는 'Go에서 Rust로' 같은 시스템 언어 선택 논의와도 겹칩니다. 더 빠른 실행과 작은 바이너리, 예측 가능한 성능을 원할 때 어떤 언어/툴체인을 고를지의 문제이기 때문입니다. 이 맥락은 Go에서 Rust로 마이그레이션 가이드에서 더 깊이 이어집니다.

12. 결론 - TypeScript의 '두 번째 인생'

Perry가 던지는 메시지는 분명합니다. TypeScript의 타입은 단순한 개발 편의 도구가 아니라, 컴파일러가 쓸 수 있는 최적화 정보라는 것입니다. 트랜스파일로 타입을 지워 버리고 무거운 JIT 위에서 다시 추론하게 하는 대신, 그 타입을 LLVM에 그대로 넘겨 네이티브 기계어로 낮추면, TypeScript는 시스템 언어에 가까운 성능과 배포 편의를 얻을 수 있습니다.

물론 Perry는 아직 초기 단계이고, 동적 기능과 거대한 npm 생태계라는 만만찮은 벽이 남아 있습니다. 모든 앱이 내일 당장 네이티브로 컴파일되지는 않을 것입니다. 하지만 Static Hermes, Porffor, AssemblyScript와 함께 Perry가 그리는 큰 그림은 또렷합니다. '브라우저에서 태어난 동적 언어'라는 JavaScript/TypeScript의 정체성이, AOT 컴파일이라는 새 길을 통해 '시스템 영역으로도 진출할 수 있는 언어'로 확장되고 있다는 것입니다. TypeScript를 즐겨 쓰는 개발자라면, 이 흐름은 분명히 지켜볼 가치가 있습니다.
