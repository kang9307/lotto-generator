Mojo 编译器开源 - 一门语言被打开究竟改变了什么、又没有改变什么 2026

许可证终止之处，正是治理开始之处

2026年8月20日 开发/基础设施

引言：被压缩进一句话里的三个不同问题

在挑选公司统一语言的会议上，一句「那个是开源的」常常就把讨论结束了。这句话其实把三个不同的问题捆在了一起。能不能读源码，能不能修改并再分发，以及能不能坐进决定这门语言走向的席位。答案因项目而异，甚至在同一个仓库里也会因目录而异。

2026 年 8 月 18 日，Modular 公开了 Mojo 编译器与整套工具链。标准库早在 2024 年先行开放，用 Mojo 写的内核代码随后跟上，最后一块拼图编译器则在 1.0 之后落地。前两个问题由许可证回答，第三个问题由治理回答。今天确定下来的是前两个，尚未确定的是第三个。把这条界线画准，「要不要学」这个问题也就分成了若干条件。

1. 究竟开放了哪些部分、适用什么条款

Mojo 与 MAX 同处一个仓库 modular/modular。README 并列写着两句话：「本仓库及其贡献以 Apache License v2.0 with LLVM Exceptions 授权」，以及「MAX 的使用与分发以 Modular Community License 授权」。一个仓库，两套条款。

组成部分仓库位置条款外部贡献
Mojo 编译器与工具链/KGENApache 2.0（LLVM 例外）尚未接受
Mojo 标准库/mojo/stdlibApache 2.0（LLVM 例外）2024 年起接受
MAX 加速器内核（用 Mojo 编写）/max/kernelsApache 2.0（LLVM 例外）依仓库声明
MAX 框架、推理服务、流水线/max/python 等使用与分发适用 Modular Community License-

先说清楚LLVM 例外。Apache 2.0 要求分发物随附许可证副本与署名。当编译器的运行时片段被静态链接进产物二进制时，这项义务可能蔓延到用该语言写出的每一个程序。LLVM 例外正是切断这种传播的条款。LLVM 项目本身与 Swift 都采用同样的做法，它实际上是编译器采用 Apache 2.0 时的标准组合。

另一侧的 Modular Community License 性质不同。它是可读源码意义上的 source-available，但并非 OSI 认可的开源许可证。已公开的条款包括以下几项。

  • 分发衍生作品需保留以「MAX is licensed by Modular Inc under the Modular MAX Community License」开头、以「modified by [You]」结尾的声明
  • 衍生作品或应用必须具备超出所含 MAX 部分的实质性附加功能
  • 不得将 MAX 用作训练数据去产出重新实现或替代 MAX 的软件
  • 不得把衍生作品表述为 Modular 的产品或经 Modular 背书
  • 下游分发条款不得与本协议相抵触

实务上最关键的一点在这里。官方文档指引，做 GPU 编程需要安装 max 包，而这个包同时打包了 MAX 框架与 Mojo。也就是说，语言本身是 Apache 2.0，但这门语言最具代表性的用途——GPU 负载——却与 MAX 的条款相接。「Mojo 是开源的」和「我要做的事能在开源条款内完成」并不是同一句话。

2. Mojo 想解决的问题，以及站在 MLIR 之上的结构

数值计算与 AI 类代码库通常是两层。上层是 Python，下层是 C++ 或 CUDA。麻烦在于这条边界会变成组织边界而非技术边界。构建体系分叉，性能剖析接不上，最后人也分开了。发现瓶颈的人，修不了它。

Mojo 的设计前提是用一门语言覆盖这两层。语法取自 Python，而值语义、所有权、编译期元编程这些系统语言的工具则放进语言本身。1.0 的变更正体现了这个方向。

  • 可以用 Python 风格的 lambda 语法写内联闭包
  • 此前分散的闭包实现与指针类型各自收敛为一种
  • 新增了针对引用失效的内存安全诊断
  • where 子句改为输出说明失败原因的信息
  • 用于编辑器集成的 LSP 服务器稳定性改善

把指针类型合并不是什么华丽的活。但这类整理集中出现在 1.0 之前，本身就是信号，因为这是先把内部理顺、再固化外部表面的顺序。

再看结构。官方愿景文档称这门语言「纯粹构建在 MLIR Core 之上」，实际上是「MLIR 的语法糖」，并说明无需改动编译器就能在语言里直接书写 MLIR 方言的运算。这句话的分量与 LLVM IR 对照后才显出来。LLVM IR 大体是面向 CPU 的单一中间表示。MLIR 则以方言为单位，把中间表示叠成多层。张量运算这类高层语义可以在高层保持原样做优化，只在必要时向下降。

如果加速器只有一种，这个结构就是过度设计。但官方愿景明确把 CPU、GPU、定制加速器、ASIC 都列为目标。而编译器源码公开，恰恰在这里获得了具体意义。现在可以从外部追踪一段 Mojo 代码经过哪些方言、最终降到什么机器码。在编译器优化决定语言性能大半的领域，这不是小差别。沿同一条轴，配合阅读把 TypeScript 直接降到 LLVM 的尝试，图景会更清晰。

3. 开源化真正改变的四件事

把编译器开放后真正发生变化的部分逐条拆开来看。

3.1 可验证性 — 能把一个缺陷追到底

闭源编译器最棘手的是性能缺陷。崩溃只要能复现就能上报，而「为什么只有这个循环没被向量化」这类问题，看不到内部连复现都难以定义。源码开放后，可以确认优化阶段在哪里放弃，并构造出精确的最小复现例。

3.2 存续保险 — 「可以分叉」这件事本身的价值

Apache 2.0 是不可撤销的许可证。即便公司转向或砍掉产品，截至那一刻已公开代码上的权利不会消失。分叉能否真正运转是另一回事，多数分叉会因缺少维护者而枯萎。即便如此，「最坏情况下我们可以自己接手」这个选项的存在，本身就改变了引入风险的评估。保险不索赔也在起作用。

3.3 专利条款 — 在半导体公司持有的语言里不是装饰

Apache 2.0 要求贡献者明确授予专利许可，并规定一旦对该许可发起专利诉讼，权利即告终止。MIT 与 BSD 都没有这类条款。对于已经进入一家经营硬件与专利的组织之下的语言，这条是实实在在的安全阀。

3.4 缓解厂商锁定 — 但存在上限

锁定并没有消失。编译器开放了，但压榨性能的主路径 MAX 仍在另一套条款之上。准确地说，不是锁定消失了，而是锁定的边界被写成了文字、变得可见。看不见的锁定与被明示的锁定，管理难度完全不同。

4. 没有改变的部分 — 源码公开不等于开放治理

这里需要换一种语气。被公开的是读的权限，尚未开放的是写的权限。

  • 编译器与工具链的外部贡献目前不接受。Modular 表示目标是在今年内开始接受
  • 标准库自 2024 年起接受贡献，因此两条轨道的成熟度并不相同
  • 决定语言设计与路线图优先级的席位，仍在公司内部
  • 关于移交基金会的计划、技术指导机构、商标使用政策，未见公开文档

所有权结构也要一并看。高通于 2026 年 6 月达成收购 Modular 的协议，并在 7 月 29 日完成交易。联合创始人兼 CEO Chris Lattner 出任高通 Advanced AI Software and Platforms 事业部执行副总裁，Mojo、MAX 与 Modular Cloud 宣布将作为产品与品牌延续。缔造了 LLVM、Clang、Swift 与 MLIR 的人继续参与，从技术连续性看是积极信号。与此同时，决定这门语言方向的位置如今落在一家半导体公司的组织架构之内，这一事实同样没有变。

5. 与 Python 的关系 — 超集这个目标已经放下

早期的 Mojo 被介绍为要做 Python 的超集，逻辑是既有代码能原样运行就等于继承整个生态。这个目标后来被调整了。当前官方愿景文档写明，优先级是「打造释放高性能、可移植计算的能力，而不是快速达成表层的 Python 兼容」。

  • Mojo 不是运行既有 Python 程序的运行时。它借用了大量语法与概念，但作为一门独立语言前行
  • 调用 Python 模块要经由 CPython。官方文档说明使用未经修改的 CPython 运行时，因此与既有库完全兼容
  • 但一旦走上这条路径，执行就是 CPython 的性能。频繁跨越边界的代码会把迁移到 Mojo 的收益抵消掉
  • 从 Python 调用 Mojo 需要显式声明绑定，互操作要求 Python 3.10 至 3.14
  • 类、继承、无类型变量这类动态特性在路线图上属于 Phase 3，尚未启动

先知道这些再上手，第一印象会完全不同。抱着「Python 变快了」的预期会落空，抱着「用 Python 语法的系统语言」的预期则相符。如果目的是提升既有代码库的速度，先定位瓶颈、只把那一段降到原生仍是更短的路。

6. 1.0 保证了什么、又没有保证什么

Mojo 1.0 于 2026 年 8 月 11 日随 Modular 26.5 发布。人们赋予这个数字的期待与实际政策并不一致，因此把稳定性政策原样搬成表格。

项目政策上的状态
版本管理对被识别为稳定的语言特性与标准库 API 适用语义化版本
稳定的标记方式@stable(since='版本') 装饰器
标准库默认值没有 stable 标记即为不稳定
把结构体标记为 stable不代表其成员 API 也稳定
ABI不稳定。保证仅适用于源代码
async/await归类为不稳定
例外情形若已稳定的 API 出现致命问题，可作例外处理
破坏性变更1.x 以增量为主，必要时按成熟语言的演进方式管理

读法是这样的。1.0 并不意味着「语言不再晃动」，更接近「开始用文档标出哪些部分会晃动」。这已经是足够大的进步，因为没有标记就可以默认它会动。

不过 ABI 不稳定的分量不一样。这意味着还无法建立这样一种模式：把预编译的 Mojo 库以二进制形式分发，让另一个编译器版本构建的程序去链接它。如果贵组织以二进制形式分发内部公共库，应当先确认这一项。

7. 还欠缺的部分 — 路线图自己点出的空白

官方路线图分三个阶段。聚焦 CPU 与加速器高性能代码的 Phase 1 已完成，向系统应用编程扩展的 Phase 2 正在进行，加入动态面向对象特性的 Phase 3 尚未启动。Phase 2 剩下的语言特性如下。

  • 与类型和内存模型整合的一等 async 支持
  • 用于运行时抽象的存在类型与动态 trait
  • 代数数据类型与模式匹配
  • private 之类的访问控制，以及用于事后扩展的结构体扩展
  • 初步的分布式编程支持与动态反射
  • 内存安全方面，收敛集合引用所需的内部 origin，并支持可变别名

生态一侧的空白更直接。

  • 打包与包管理系统仍是路线图条目
  • 包含性能剖析器、交叉编译、更好调试器的稳定工具链仍在推进
  • 与其他语言的互操作改善、新硬件支持扩展并列其中
  • 平台方面，按官方 FAQ，macOS 与 Linux 原生支持，Windows 经由 WSL

只挑一项的话，选包管理器。它是衡量生态成熟度最快的指标，也是引入讨论中最先卡住的地方。编译器质量再好，只要没有确定依赖如何锁定与复现，团队规模的开发就无法启动。

8. 一门语言站稳的条件 — 先行案例给出的答案

「不能由一家公司掌握」这个通念与事实并不吻合。Go 由谷歌、TypeScript 由微软把握方向，却各自在自己的领域成为标准。Kotlin 由 JetBrains 打造，并与 Kotlin 基金会共同运营。Swift 在 2015 年开源后转入 Swift.org 的工作组结构，Rust 则从 Mozilla 出发，于 2021 年移交 Rust 基金会。形态各异，结果都在成功一侧。所以分水岭不在治理形态。

  • 是否积累了真正守住向后兼容的记录。是记录，不是承诺
  • 是否有不可替代的杀手级领域。TypeScript 是前端，Go 是服务端与命令行工具，Kotlin 是安卓，Swift 是苹果平台
  • 包仓库与构建工具是否与语言一同到位
  • 公司之外是否形成了就业市场。名字出现在招聘启事上的那一刻起，个人的学习才变成投资

把 Mojo 放到这四条轴上，图景相当清晰。杀手级领域很明确：加速器内核与 GPU 负载正是当下人才最稀缺、工具最不顺手的领域。向后兼容随 1.0 才刚开始计时。剩下两条，包生态与就业市场，都还在前方。

补充一句，语言消失的原因多半不是技术，而是迁移所得小于迁移成本。所以对一门新语言而言，重要的不是「更好」，而是「有些事按旧办法根本做不到」。如何检验这个条件，一支自己造过语言又调整方向的团队的复盘里有具体讨论。

9. 那么现在值得学吗 — 分条件来看

「该不该学」没有唯一答案。按处境拆开，答案就不一样。

你当前的处境判断理由
写 CUDA 与 C++ 内核，每天与 Python 团队跨越边界现在就看正面针对双语言问题的设计，试移植一个内核的成本很低
Python 服务慢，正在找替代方案不急它不是运行既有 Python 的运行时。先定位瓶颈、先看扩展模块
正在挑选公司统一语言还太早包管理、ABI、招聘市场都未定。这项成本来自人与工具，而非速度
在学习编译器与 MLIR正是时候一个真正投入使用的 MLIR 语言前端，全部源码已可阅读
想学 GPU 内核编程有条件语言是 Apache 2.0，但 GPU 路径要经过 MAX，应先读许可证
只是想当兴趣学一门新语言不必着急在包生态站稳之前，能做出来的东西范围有限

真要开始的话，按这个顺序走弯路更少。

  1. 先放下「Python 语法熟悉」这个前提，从值语义与所有权看起。这才是真正分岔的地方
  2. 弄清楚结构体、trait 与编译期参数如何解开泛型
  3. 再进入 SIMD 与向量化这类构成使用理由的功能。GPU 排在其后，并同时阅读 MAX 的条款
  4. 移植要从一个瓶颈而不是整体开始。来回跨越边界会抵消收益，少留边界才是要点

10. 未能确认的部分

以下项目未能从公开资料确认，因此没有写进正文。

  • 性能数字。1.0 的发布文中没有标明硬件、负载与对比对象的基准测试。不带条件的「比 Python 快多少倍」，会因基线是纯 CPython 还是 NumPy 而整整差出数量级，因此不予引用
  • 生产环境采用案例的企业名称与规模
  • 编译器贡献的具体流程。关于 RFC 流程、评审与提交权限政策、设计讨论是否公开，未见文档。已公开的只有年内开始接受这一方针
  • 治理文档。移交基金会的计划、商标使用政策、决策机构的构成
  • 在任意环境下从源码构建的可复现性。仓库基于 Bazel，同时也提供下载预构建每夜版二进制的配置。在各种发行版与架构上从零构建的表现如何，属于各自需要自行确认的范围
  • 收购对路线图的影响。关于特定硬件后端优先级如何调整，没有公开说明

11. 结论：确定的是许可证，未确定的是治理

已经确定的。编译器、工具链与标准库位于 Apache 2.0 with LLVM Exceptions 之上。商业使用与再分发开放，附带专利条款，且不可撤销。现在可以阅读并验证编译器内部，沿着 MLIR 的层次把性能问题追到底。

仍然敞开的。向编译器上游贡献的通道还在建设中，制定路线图的席位在公司内部。包管理系统是路线图条目，ABI 并不稳定。一旦用上 MAX，就多出一套条款。

归纳起来，许可证挡住最坏的情况，治理决定日常。Mojo 已经填满了前者，后者还在填。在这种状态下，合理的姿态既不是「引入」也不是「观望」，而是「在边界清晰的地方做试验」。移植一个内核，用它跑出来的数字去判断下一步，比读别人做的基准表更快给出答案。
