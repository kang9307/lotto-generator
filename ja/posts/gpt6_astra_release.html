きっかけ - 100パーセントと拒否が一つの文書にある

2026年9月初め、OpenAI が GPT-6 Astra を公開した。開発者コミュニティにも要約が上がり、要約には目を引く数字が並んでいた。そのうち二項目が隣り合っていた。一つは攻撃コード作成能力を測る評価で100パーセントを記録したというもの、もう一つは実際に出荷される本番モデルは高度なエクスプロイト作成を拒否するというものだった。

この二つは矛盾ではない。互いに別のことを言っているだけだ。前の文は評価環境でモデルが何を成し遂げられるかを測った値であり、後ろの文はその能力のうち何を外に出すかを配備方針が決めた結果である。能力は学習が作り、挙動はアラインメントと方針が作る。両者は同じモデルから出るが同じ値ではない。

普段はこの区別が見えにくい。ほとんどのベンチマークでは能力値と製品挙動がほぼ重なるからだ。数学の問題をよく解くモデルは製品でも数学の問題をよく解いてくれる。ところが攻撃セキュリティのように能力が高まるほど配備を狭める領域では、両者が正面から分かれる。だからこの事例が教材になる。ベンチマークのスコアと実際に使うことになる製品の挙動がもともと別の値だったという事実が、ここでは隠れる場所を持たない。

知識型評価と行動型評価がそれぞれ何を取りこぼすかはLLM 評価の死角で別に整理してあるのでここでは繰り返さない。本記事はその上に一層を重ねる。評価と製品のあいだに方針という層がもう一つあるという話だ。

同じモデル同じベンチマークで62.7と99.9

最も教訓的なのは ARC-AGI-3 だ。このベンチマークを運営する ARC Prize は自らの評価結果を直接公開しており、そこに同じモデルに対する二つのスコアが並んで書かれている。

区分標準ハーネスプロバイダアダプタ・ハーネス
スコア62.7%99.9%
推論強度の設定maxhigh
評価の総費用26,098ドル18,817ドル
要求間の状態モデルが自ら残したメモだけが引き継がれる内部の推論状態をそのまま保存し、長くなれば圧縮する
先行作業の再利用そのメモに書かれた分だけ可能

この表には常識を二度ひっくり返す箇所がある。第一に、推論強度をより高くしたほうが低いスコアだった。第二に、高いスコアを出したほうが費用はむしろ少なかった。26,098ドルを使って62.7が出て、18,817ドルを使って99.9が出た。スコアを上げたのは追加の演算ではなく実行方式だった。

違いは一つだけだ。アダプタ・ハーネスは要求と要求のあいだにモデルの内部推論状態をそのまま持っていく。標準ハーネスではその状態が毎回消え、モデルは自分が残すと決めたメモだけを次の回に渡せる。何回にもわたって環境を探索し規則を突き止める種類の課題では、この差が決定的になる。先に突き止めたものを失わないこと自体が能力の大きな部分だからだ。

ではこの二つの数字をどう扱うべきか

どちらも本物の数字だ。いずれも操作ではなく、ベンチマークの運営主体が両方とも公開した。問題は伝達の過程にある。99.9だけが運ばれた文を読んだ人は、このモデルを状態を持たない単発 API 呼び出しでつないで似た結果を期待することになる。その期待は62.7に近い現実に出会う。

ARC Prize 自身も解釈に線を引いた。ベンチマークを飽和させることが汎用人工知能の証明にはならず、この評価の環境は規則が決定的で目標が閉じており現実世界の複雑さと開かれた構造を代表しないと、同じ記事に書いている。ベンチマークを作った側が自ら付けたこの但し書きが、運ばれる過程で真っ先に消える文だ。ベンチマークがどれほど速く古び、なぜ古びるのかは評価方式の寿命を扱った記事で別に見た。

100パーセントが数えていたもの - 二つの攻撃評価

ExploitBench の100パーセントも同じやり方でほぐす必要がある。報告によればこの100は個別の課題をいくつ通過したかの比率ではなく能力カバレッジを集計したスコアだ。つまりどの種類の攻撃手法を扱えるかについての包括指標に近い。100という値が出やすい構造の指標である。

同じ発表に登場した ExploitGym は性格が異なる。ここでは42.4パーセントが出ており、それも6時間制限を解除した条件でだ。制限を外してようやく出る42.4と、カバレッジを集計した100は、同じ領域を測っているのに値が二倍以上開く。どちらが正しいかの問題ではなく二つが別の問いに答えていることが要点だ。

ここに発表は定性的な事実を二つ足した。評価の過程で堅牢化されたブラウザとオペレーティングシステムを対象にエクスプロイトを作り出し、広く使われる JavaScript エンジンで知られていない脆弱性を二件見つけたというものだ。数学の側では素数間隔の既存の上界を240から186に狭めたという記述もあった。この種の記述はスコアと性格が違う。スコアは標準化された問題集合に対する相対的な位置を語るが、新たに見つけた脆弱性二件は絶対的な出来事である。そして絶対的な出来事のほうが配備方針を動かす。

標準ベンチマークを信頼しにくくなると企業が自前の評価を作る流れは、すでに数年続いている。その背景とグッドハートの法則の話は自前のコーディングベンチマークを作った事例で整理し、論文水準の数値が再検証でどう崩れるかは再検証の事例に書いてある。

能力と配備は別の層で決まる

ここで最初の一対に戻る。なぜ100パーセントを記録したモデルが本番では拒否するのか。

OpenAI は自社の準備度フレームワークを置いてモデルの危険水準を分類している。今回のモデルはサイバーセキュリティ部門で最上位に該当すると自社が初めて分類した事例として報告された。そしてその分類の帰結として、攻撃コード作成と脆弱性発見に当たる高度な要求を一般アクセスから遮断した。その能力を必要とする防御目的の組織は、別の審査プログラムを通じてアクセスする構造だ。

整理すると介入地点が三つある。

  • 学習段階 — 能力そのものが作られる場所だ。ベンチマークが測るのはおおむねこの層の結果である
  • アラインメント段階 — どの要求にどう応じるかの傾向が決まる。同じ能力があってもここで応答が変わる
  • 配備方針の段階 — アクセス自体を等級と審査で分ける。能力の有無と無関係に、特定の利用者にはその機能がそもそも存在しない

ベンチマーク表は一番目の層しか見ない。利用者が実際に出会うのは三つの層をすべて通過した結果だ。だから表の数字が高いという事実は、自分がその仕事をさせられるという保証にはならない。とりわけセキュリティ、医療、法律、金融のように配備制約が強くかかる領域ほど、表と実際の距離が遠くなる。

この構造自体を否定的にだけ見るべきではない。知られていない脆弱性を自ら見つけ出す能力が何の条件もなく全員に開かれる状況が望ましいかは別の問いだ。要点は、評価と製品のあいだにこうした層があるという事実を表を読む人が知っておくべきだということである。セキュリティという分野がなぜとりわけ構造的に難しいのかについては別の記事に書いてある。

ベンチマーク表で実際に見るべき五行

今回の事例から取り出せる実用的な結論はこれだ。次にどのモデルのベンチマーク表を見ることになっても、数字の隣に五行が併記されているかをまず見る。

  • ベンチマークの正確な版 — 同じ名前に2.0と v2-offline のような枝があれば比較対象ではない
  • 実行ハーネスと状態保持の有無 — 今回の事例の62.7と99.9を分けた唯一の変数だ
  • 推論予算または思考強度の設定 — 設定によって同じモデルが別の等級のように動く
  • 試行回数と採点方式 — 一発で当てた値か複数回のうち最良か、通過率かカバレッジ集計か
  • そのスコアを出すのに要した費用または時間 — 今回のように費用が逆転することもある

引用するときも同じだ。自分の文書にスコアを写す機会があれば下の形を保つほうがよい。条件なしに運ばれた数字は次の読み手に何も伝えず、後になって自分自身にも根拠になってくれない。

  ARC-AGI-3 99.9%

[使える引用]

料金 - 10ドルと50ドルは基準線だ

第二の軸は料金だ。広く運ばれた値は100万トークンあたり入力10ドル、出力50ドルである。この値は正しい。ただしその二つの数字は料金表の全部ではなく基準線であり、上下に倍率が付く。

区分100万トークンあたり適用条件
入力10ドル基準
キャッシュ命中の入力1ドルプロンプトキャッシングがかかった部分
出力50ドル基準
長い入力の割増入力とキャッシュ2倍、出力1.5倍入力が272,000トークンを超える要求。超過分ではなく要求全体に適用
高速応答モード該当料率の2倍この2倍は速度の倍率ではなく価格の倍率だ
バッチおよび柔軟処理50%割引即時応答が要らない作業

ここに見出しがよく歪む箇所が一つある。高速応答モードが2倍という言葉は価格が2倍という意味だ。速度が2倍になるという意味ではない。倍率をそのまま運ぶと正反対に読まれやすい箇所である。

そして272,000という境界は実務でかなり鋭く働く。コンテキスト窓が105万だからといって105万を埋めるのが自然な使い方ではない。境界を一トークン越えた瞬間にその要求全体の料率が上がる。以下は同じ分量を境界の内側と外側で処理した場合の単純な比較だ。

仮定: 入力27万トークン、出力1万トークン、キャッシュ未適用

境界の内側 (272,000 以下)
  入力  270,000 x 10ドル / 1,000,000 = 2.70ドル
  出力   10,000 x 50ドル / 1,000,000 = 0.50ドル
  合計                                 3.20ドル

同じ作業に文脈を少し足して境界を越えた場合
  入力  280,000 x 20ドル / 1,000,000 = 5.60ドル   (料率2倍)
  出力   10,000 x 75ドル / 1,000,000 = 0.75ドル   (料率1.5倍)
  合計                                 6.35ドル

入力を3.7%増やしただけで請求額はおよそ2倍になる

公示価格が請求書になるまで

同じ公示価格でも実際の請求額はかなり変わる。そのあいだに割り込む項目が少なくとも四つある。

  • トークナイザ — 同じ文を何トークンに割るかがプロバイダごとに違う。韓国語と日本語と中国語はこの差がとりわけ大きく開く言語だ。自分の実テキストでトークン数を数えてみるまで単価比較は成立しない
  • 出力の長さ — 出力料率が入力の五倍という構造では総額を出力が支配する。同じ問題でも冗長に答える設定なら費用が数倍になる。推論強度の設定がここに直接かかる
  • キャッシュ命中率 — 長いシステムプロンプトや固定文書を繰り返し使う構造ならキャッシュが総額の大半を決める。このモデルはキャッシュ命中時に十分の一まで下がる
  • 再試行と失敗 — 形式が合わずに呼び直す呼び出し、ツール呼び出しがもつれて巻き戻す区間がすべて課金される。エージェント形態で使うほどこの取り分が大きくなる

だから導入検討で意味のある数字は公示単価ではなく自分のワークロード100件を実際に回してみた平均請求額である。この値は一日あれば得られるし、単価表をいくら長く眺めても出てこない。

コンテキスト105万が変えるものと変えないもの

コンテキスト窓1,050,000トークンは目を引く数字だ。ただしこの数字が何を解決し何を解決しないかは区別しなければならない。

  • 変わるもの — 長いコードベースや長い文書の束を分割せずに一回の要求に収められる。分割ロジックとそれが生む境界のエラーが減る
  • 変わらないもの — 長い入力のなかから必要な箇所を正確に拾い出す能力は窓の大きさとは別の項目だ。窓が大きくなったという事実だけでこの能力は保証されない
  • むしろ悪くなりうるもの — 272,000トークンの境界を越えると料率が跳ねる。大きな窓を使えることと使うほうがよいことは別の話だ
  • 出力は別枠 — 最大出力は128,000トークンだ。入力をいくら大きく入れても一回の応答で受け取れる量はこの上限を超えない

実務では文書を丸ごと押し込むより、必要な部分だけ選んで入れその前段をキャッシュに乗せるほうが概して安く結果も安定する。大きな窓は選択肢を増やしてくれるのであって設計を代わりにやってくれるのではない。

コンピュータを代わりに操るモデルがぶつかる場所

このモデルは画面を見てコンピュータとブラウザを操作する側に重心が置かれている。OSWorld 2.0 で72.6パーセント、作業あたり平均所要が前世代の75分から40分に減ったという値がその根拠として提示された。時間の側の減少は約47パーセントだ。

この系統の数値を見るときは別種の注意が要る。正解が一つに定まった問題解きと違い、コンピュータ操作は途中で何に触れたかが結果と同じくらい重要だ。ベンチマークはおおむね最終状態の達成可否で採点するので、途中で何を消したか何を押したかはスコアに残らない。実際の業務環境につなぐとき問題になるのはたいていこの途中の部分である。

  • 権限の境界 — どのアカウントで何にアクセスするかを人ではなくモデルが決めることになる。最小権限をあらかじめ切っておかないと事後監査が成立しない
  • 取り消せない操作 — 削除、送信、決済、承認のように取り消しの効かない行動は別の確認段階を置くほうがよい。72.6パーセントという成功率は残りの27.4パーセントが存在するという意味でもある
  • 画面への依存 — 対象ソフトウェアの UI が変わると静かに失敗する。成功率自体が対象環境の関数だ
  • 監査記録 — 何をなぜ押したかが残らなければ事故分析ができない。ログ設計を導入前に決めなければならない

導入を検討するなら先に決めること

新しいモデルが出たとき最もよくある失敗は、ベンチマーク表を見て決めたあとにワークロードをそこへ合わせることだ。順序が逆である。先に決めることが五つある。

  • 何を置き換えるのか — 非対応の一覧に埋め込みとモデレーションとリアルタイム音声が入っている。スタック全体は移せないのでどの区間だけ変えるかを先に決める
  • 状態を保持できる構造か — 今回の事例が示したとおり状態保持の有無が結果を大きく分ける。単発呼び出しでつなぐ計画なら状態保持条件のスコアを期待値にしてはならない
  • プロンプトが272,000トークンの境界近くか — 境界付近を行き来する設計なら請求額が要求ごとに跳ねる。境界の下に固定するほうが予測しやすい
  • ファインチューニングの計画があったか — このモデルでは対応していないのでドメイン特化の経路をプロンプトと検索ベースで組み直す必要がある
  • セキュリティ関連の作業が含まれるか — 脆弱性分析や攻撃コードに当たる要求は一般アクセスから遮断されている。評価スコアと無関係にその機能はないものとして計画すべきだ

前世代の等級構造とそのときの選択基準は直前世代の発表まとめと等級別の選択ガイドに書いてある。等級間の価格差と性能差をどの比率で見るかという判断の枠組みは、世代が変わっても大きくは変わらない。
