这个函数返回分隔符前面的部分还是后面的部分。把这个结构体转成JSON，字段名会长成什么样。答案三十秒就能出来，可为了看到它，你得建一个临时目录、写一个main函数、跑一次构建，看完再删掉。一天重复好几次的这段往返，与其说浪费时间，不如说打断了思路。

所以在以编译为前提设计的语言上加装交互式执行的尝试一直不断。最近再次进入视野的是Go解释器gomacro。它同时提供REPL与脚本执行，还在此之上加了Go本身没有的宏。

本文不是这个工具的使用说明。关心的只有一件事：把交互式执行叠加到编译型语言上，什么被打开，作为代价又有什么被计入账单。账单不是以性能的形式到来，它来自别处。在Go运行时之上承载另一门语言，见glojure — 在Go运行时上运行Clojure解释器的意义与技术挑战 2026；语言语法如何改变验证成本，见降低 AI 生成代码验证成本的语言特性 - Go 占优的五点及其代价。这里多出来的条件是同一门语言有了两种执行方式。

gomacro是什么 — 截至2026年8月确认到的范围

仓库把它介绍为用纯Go实现的、几乎完整的Go解释器。它同时支持交互式REPL与脚本执行，除导入第三方包之外，运行时并不需要Go工具链。要求Go 1.18及以上，按MPL 2.0发布。

有意思的地方在于它补上了标准Go没有的东西。仓库列为扩展的项目如下。

  • 集成调试器与可配置的特殊命令
  • 可在REPL中直接操作无类型常量，并隐式转换为*big.Int、*big.Rat、*big.Float
  • 零值构造器 — 写成T()即可得到该类型的零值
  • 宏与quoting、quasiquoting — 承自Lisp家族的代码生成机制
  • 未使用的变量与未使用的返回值不会报错

泛型仍处于实验阶段。仓库里同时带着两套不同实现，一套仿照C++模板，另一套是把契约视为接口的CTI方式，后者为默认。使用的是Pair#[T,U]之类的语法。仓库列出的当前约束有这些。

  • 泛型实参没有类型推断
  • 无法定义泛型方法
  • 类型是否满足契约不会被校验

这段介绍里值得盯住的词是几乎。本文余下的篇幅，实际上都是围绕这一个词展开的。

REPL真正改变的是什么

人容易以为往返消失省下的是时间。真正改变的是探索的粒度。

当编辑、构建、运行捆成一个昂贵的整块时，人会一次改动好几个假设。反正只跑一次，索性这里那里一起改了。于是结果出来的时候，你不知道是哪一处造就了这个结果。反过来，当往返几乎免费，人就会一次只改一处。原因之所以变得容易定位，不是因为工具变聪明了，而是因为人的行为变了。

第二个改变的是状态。写成文件去跑，每次都从头开始。交互式会话里，上一行造出来的值还在，下一行就在它之上运行。那些构造代价高昂的值 — 解析好的文档、开着的连接、填满的大型数据结构 — 可以造一次，敲很多次。对象越大，这个差距越明显。

  • 探索粒度变细 — 一次只验证一个假设，因而原因得以定位
  • 昂贵的准备被复用 — 只反复触碰你关心的那一部分
  • 试错成本几乎为零 — 没把握的表达式可以直接敲进去
维度编辑、构建、运行的往返保持状态的会话
一轮改动的假设数多个（因为往返昂贵）一个（因为往返便宜）
准备成本每次运行重付一遍每个会话付一次
失败的代价构建时间加上思路中断几乎为零
留下的产物文件 — 可提交、可评审、可重跑回滚缓冲 — 会话结束即消失
执行语义就是将要上线的代码将要上线代码的近似

编译型语言为何难以承接交互性

REPL在Python或Ruby里之所以自然，是因为那些语言本来就被设计成一次执行一个片段。编译型语言站在相反的前提上：一次看到全部、就此确定、并在这份确定之上做优化。障碍就从这三条前提里逐一冒出来。

静态类型 — 声明与使用在时间轴上被拆开

编译器同时看到整个包。函数a调用下方的b之所以不成问题，是因为两者都已经摆在眼前。而在REPL里，a先到，b还不存在。那么是拒绝a的定义，还是先收下?

Java的JShell正面处理了这个问题，选择了收下但拦住调用。官方文档给出的理由是支持探索式编程，因此接受引用了尚未定义之物的方法定义。

jshell> double volume(double radius) {
   ...>    return 4.0 / 3.0 * PI * cube(radius);
   ...> }
|  created method volume(double), however, it cannot be invoked until variable PI,
   and method cube(double) are declared

第二个问题是重定义。把x先声明成整数、再重新声明成字符串，那么此前用过这个x的函数该怎么办?JShell把这件事分成修改、替换、覆盖三档反馈，并在不兼容的重定义破坏了依赖它的定义时发出警告。编译型语言的REPL必须在语言规范帮不上忙的情况下自己发明这类规则。语言与工具，从这里就已经开始分岔。

包初始化 — 不存在叫做启动的那个时刻

在Go里，包级变量的初始化与init函数在程序启动时按确定顺序恰好运行一次。顺序依照依赖关系排定，而依赖这个顺序的代码确实存在。

交互式会话没有那个启动点。如果用户二十分钟后再加一个导入，初始化就在那一刻运行，而这在程序里本该早就结束了。依赖初始化顺序的代码、把全局状态注册进去的库、只为副作用而写的导入，在这里都获得了表现不同的余地。

链接 — 运行中引入新代码就得打破已定之事

Go的标准产物是一个静态链接的二进制。哪个符号在哪里，构建时就被钉死。想在运行途中引入新包，就得把这颗钉子拔出来。

gomacro选的路是这样：在Linux、macOS与*BSD上，它在内部编译并加载单个Go插件，其中包含import ( ... )里列出的所有包的导出声明。也就是说那一刻仍然需要Go工具链，而Go标准库plugin包附带的条件也就一并跟了过来。

  • 插件仅在Linux、FreeBSD与macOS上受支持，因此不适合以可移植性为目标的程序
  • 应用与插件必须用完全相同的工具链版本、构建标签与环境变量构建，共同依赖也必须出自同一份源码
  • 插件在首次加载时只初始化一次，而且无法关闭或卸载
  • 竞态检测器对其支持不佳，即便是简单的竞争也可能不会被自动检出

第三条最扎人。一边换着导入一边探索的图景，与一旦装上就卸不下来的性质正面冲突。标准文档自己就写道，实践中应用与插件必须一起构建，并建议改用套接字或RPC这类进程间通信作为替代。这不是解释器实现偷懒，而是Go这门语言所处位置带来的约束。

优化前提 — 优化连可观测的东西一并改变

编译器在掌握整个程序的前提下做内联、逃逸分析与边界检查消除。解释器建立不起这个前提，也就做不了同样的优化。到这里为止讲的是速度。

真正的问题在于优化改变的不只是速度。一个值坐在栈上还是逃到堆上，会改变内存行为；函数被内联，栈回溯的形状就会变。也就是说，优化保住了程序的结果值，却保不住程序对自身的观测。

解释执行与编译执行分道扬镳的地方

把仓库自己列出的限制清单与编译时的Go并排放，是这样的。

项目编译时的Go仓库所述的解释器状态
第三方导入构建时确定运行时导入仅限Linux、macOS与*BSD
包内的泛型直接使用导入时不会带入泛型
泛型定义语言特性在解释代码中属实验性且不完整
unsafe.Pointer转换支持不支持
接口断言与类型开关完整部分边角情形未实现
递归类型完整部分边角情形可能无法正确运作
goto前后皆可只能向后跳转
未使用的变量与返回值编译错误不算错误

大体一样最危险的位置

表里的条目分成两类。上面大部分属于解释器更窄的情形：编译时的Go做得到，这里做不到。这类差异是安全的，因为一试就当场失败。

危险的是最后一行那种解释器更宽的情形。未使用变量不算错误，在交互式摆弄时确实省事，可反过来看，它意味着标准Go下通不过编译的代码在这里能通过。这里通得过所以那里也通得过，这个推论并不成立。而且这类差异不会失败，所以当场也察觉不到。

  • 并发 — 限制清单对goroutine、channel、select的调度特性只字未提。没有提及并不是相同的保证，而是没有处理的意思。竞争本就取决于时序，执行方式不同，时序就不同。在解释器里没看到竞争，这个事实什么也证明不了。
  • 反射 — 在运行中翻查类型信息的代码，对这些信息由谁、以何种方式准备十分敏感。解释出来的类型与编译出来的类型在反射面前是否长得一样，公开资料并未给出保证
  • unsafe — 文档明确写了不支持指针转换。明示的约束反而好办，悄悄跑出不同结果的那一类始终更贵
  • 构建标签 — 决定哪些文件进入构建的机制。若解释器复现这个判断的方式有出入，同一份源码树就会执行不同的代码

所以只需立下一条规矩：在解释器里通过，不能代替编译构建的通过。反方向同样成立。两种执行并不是彼此的代理人。

当解释器补上语言没有的功能

这里是本文的核心。前面扩展清单里的宏与quasiquoting、自有的泛型语法、无类型常量的任意精度运算，都是标准Go没有的功能。而且每一项都确有用处。

宏尤其如此。Go是有意把宏拿掉的语言，正因为这份缺席，代码生成被推到了go:generate与独立程序那边。另写一个生成器、把它接进构建阶段、再把产物提交上去 — 这一整套流程，就是语言里没有宏而付出的成本。能在语言内部完成这件事，确实是一种力量。

然而用上这份力量的那一刻，这段代码就只能在那个解释器里运行。go build不会接收这份源码，因为语法不是Go。而交互式执行的价值恰恰在于探索、得出结论、再把结论搬进程序这条链路，扩展会把这条链路切断。

  • 只在标准Go的子集里玩 — 所得可以原样搬走。代价是解释器永远只能是一个快速确认的工具
  • 用上扩展 — 在当场强大得多。代价是那段代码被绑在工具上，工具的寿命就成了代码的寿命

这不是某个项目的缺陷，而是凡从语言之外补上语言所没有之物的工具，都要付的代价。宏在Lisp家族里之所以自然，是因为宏本就是语言的一部分，编译器看到的是同一样东西。从语言外面补，这份一致就断了，源码变成两个实现里只有一个肯接收的东西。

同样的边界问题在反方向上也会出现。Rust的交互式工具evcxr在文档中写明，目前没有办法从外部crate导入宏。把语言的功能完整带进REPL很难，把REPL里语言所没有的功能带出去同样很难。

所以判断标准既不是性能也不是语法偏好。此刻敲下的这段代码，是在一次会话里被消费掉，还是会被保存成文件?若是前者，扩展尽管放开用，代价很低。若是后者，它在那一刻就成了只有一个实现的新语言的源文件，时间越久越难搬动。

作为调试器时，诉求完全不同

gomacro也被用作源码调试器，并内置了一个集成调试器。进入方式有三种：在解释代码运行途中按CTRL+C、在提示符下敲:debug 语句、或在代码里塞一个break字符串。调试器接受的命令是step、next、finish、continue、env、inspect、list与print。

同一个执行器兼着两个角色，但两个角色要的东西不同，某种程度上还互相妨碍。

  • 脚本执行要的是速度与语义一致 — 跑得快，并且结果与编译时相同
  • 调试要的是停住与观察 — 在任意时刻停下、看全那一刻的局部变量、一行一行往前走

编译型语言的标准答案是在编译后的二进制里埋入调试信息，再挂上外部调试器。观察麻烦一些，但观察的对象是真正会上线的代码。解释器调试器的答案正相反。解释器本来就在一个节点一个节点地走，停下来不需要特别的装置，局部状态也在手里。代价是被观察的对象不是会上线的代码。

所以能抓到的缺陷也分了岔。我这段逻辑写错了这一类错误，用解释器调试器完全抓得住。而源自执行特性的错误 — 竞争、调度、内存布局、与优化的相互作用 — 抓不住，因为那些缺陷只存在于编译产物里。不是工具不够强，而是被观察的对象一开始就没带着那个缺陷。

用在哪里才值得

先从价值明确的位置写起。

  • 学习 — 对正在学这门语言的人收益最大。为了确认一个标准库函数的返回顺序而需要一个文件加一次构建，这是学习要交的税。Oracle介绍JShell时第一句就把它钉为用于学习与原型设计的工具，说的正是同一个位置
  • 探索 — 熟悉一个陌生的库时。确实有那么些场合，直接敲值比读文档更快
  • 原型设计 — 抓住那些形状还没定下来的东西
  • 配置与自动化脚本 — 想用Go的语法又不想留下构建产物时。不过这里也是最该小心的位置：脚本会被保存、被反复执行，前几节说的语义差异会随时间越咬越紧
  • 嵌入 — 放进程序里以接收用户自定义逻辑。这是仓库列出的用途之一

反过来，把它放到生产执行路径上，本文不作推荐。这不是对工具质量的评价。而是做这个判断所需的材料 — 并发语义一致到什么程度、长期运行时内存如何表现、版本之间以何种策略处理兼容 — 仅凭公开资料无法确认。

先例 — 站稳的地方与没站稳的地方

给编译型语言配交互式工具，这不是第一次尝试。站稳了的那些有共同点。

工具语言站稳的位置文档划出的界线
JShellJava学习与原型设计，随JDK一同分发自己写明它不取代IDE
evcxrRust笔记本与交互式探索代码一死进程就重启，所有变量丢失
gomacroGoREPL、脚本、嵌入、源码调试第三方导入受平台限制，泛型仍属实验性

evcxr的约束尤其耐人寻味。文档写道，代码若异常终止，运行它的进程会重启，所有变量随之丢失，并且指出会话里留存的变量不能引用其他变量。前面被列为REPL好处的状态得以留存这一性质，一旦撞上语言处理内存安全与所有权的方式，就变成了有条件的。交互性并不是能脱离语言自身性质而独立叠加上去的东西。

站稳了的工具，共同点最终汇到一处。

  • 它们与语言实现出自同一处 — JShell在JDK内部，Haskell的GHCi在编译器发行版内部，一起交付。版本一起走，语义分岔的余地就在结构上变小了
  • 独立项目没有这份优势 — 语言一变就得追，追不上的部分原样变成语义差异。泛型在Go 1.18进入语言，而解释器的泛型至今仍属实验性，正把这个结构摆在明面上

不过正因为是独立项目，有些事才做得成。像宏这种被语言刻意拿掉的功能，官方工具是绝不会加的。上一节那张可移植性的账单，恰恰是这份自由的背面。

另一面 — 直接编译运行仍然更合理的场合

这段往返在Go里之所以格外能忍，是有原因的。构建快、测试运行器是标配、可以按名字只跑一个、示例函数兼作文档与测试。也就是说，把临时确认变成长期资产的通道，语言里本来就有。

  • 确认的东西必须留下时 — 测试文件会留下，会话不会。要让确认过这件事对下一个人也成立，它就得是文件
  • 结果取决于执行特性时 — 并发、性能、内存。基于前面几节的理由，解释器的结果当不了代理
  • 需要团队一起看时 — 会话日志不是评审的对象
  • 牵涉构建标签或平台相关代码时 — 如果争的就是哪些文件真正进了构建，那就该用真实构建去看

反过来，交互式明确占优的位置也很窄、很清楚。

  • 答案用一次就扔的确认
  • 在准备成本高的对象上反复敲打的工作
  • 弄清陌生API返回什么、以什么顺序返回

归结起来，判断分野在结果的寿命。要留下就用文件，要扔掉就用会话。另外还要一并看到，REPL是便利而非能力 — 没有它，原来做的事照样做得成，所以它是要跟多一个依赖的成本放在天平上称量的东西。

没能确认的部分

以下条目仅凭公开资料得不出答案，本文也不用推测去填。

  • 解释执行与编译执行的语义一致范围。限制清单是公开的，但没有任何东西保证那份清单就是全部
  • goroutine、channel与select在解释器下具有的调度特性。限制清单未曾提及
  • 构建标签与条件编译是如何处理的
  • 性能。本文未核实任何基准测试，也不提出相对编译执行是多少倍的数字
  • 嵌入使用时的内存与隔离特性，以及长期运行下的表现
  • 两套泛型实现的成熟度差异，以及最终哪一套会留下来

除了用自己的代码亲自去量，别无他法，而这个事实本身就是把引入判断往后放的理由。

结论：是留下来的代码，还是要扔掉的代码

给编译型语言加上交互式执行，不是多挂一个便利功能。它是让同一份源码承载两套执行语义。这两套之所以难以完全一致，并不是因为实现还不够，而是因为编译这个阶段本来就要做那几件事 — 看到全部、就此确定、并加以优化。无论实现推进到什么地步，只要这三件事不放手，缝隙就仍在。

即便如此，得到的东西是实在的。而且这份收益并不是人们常说的省时间，而在于探索的粒度变细。一次只验证一个假设，原因就能被定位。

账单也来自同样明确的地方。用上语言所没有的功能的那一刻，那段代码就出不去了。看清这条界线再用，它是工具；看不清就用，它会变成日后搬不走的资产。所以要决定的只有一件事：此刻敲下的这段代码，是留下来的代码，还是要扔掉的代码?这个答案定了，工具用到哪一步也就跟着定了。
