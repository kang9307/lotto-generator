Firebase Dynamic Links 停服之后 - 从零重建深度链接体系的迁移实录

通用链接、AASA、KakaoTalk 分享 - 在没有 FDL 的世界里自建深度链接基础设施的经验

2026年7月10日 开发/基础设施

引言:在 FDL 消失的地方重新学到的东西

2025年8月25日，谷歌彻底停止了Firebase Dynamic Links(FDL)服务。无论是 page.link 子域名还是自定义域名，从那天起，之前生成的所有 FDL 链接对新请求都开始返回 HTTP 404。印在二维码上的链接、已经通过 KakaoTalk 或短信发出去的分享链接、嵌在营销活动里的短链接，一夜之间全部变成了死链接。截至2026年7月，这件事已经过去将近一年，但它留下的功课至今仍未做完。那些拖延迁移的团队，以及那些移除了 FDL 却漏掉延迟深度链接、KakaoTalk 分享等细节的团队，现在仍在陆续发现问题。

本人重新审视这个话题的理由很简单:FDL 的停服不只是一个服务消失的事件，而是戳破了「深度链接只要接一个 SDK 就完事了」这种偷懒假设的事件。这篇文章的契机是 GeekNews 上介绍的一位开发者自建基础设施的迁移经历，本文不打算复述原文，而是从本人的角度梳理贯穿这段经历的深度链接基本概念，以及自建时真正会遇到的问题 - 重点放在「为什么难」和「需要准备什么」上。

1. 到底坏了什么 - FDL 悄悄承担的三个角色

听到 FDL 没了，第一反应往往只是「短链接用不了了」。但实际上 FDL 同时默默承担着三个不太显眼的角色，而这三个角色是一起垮掉的。

1.1 短链接背后隐藏的路由

FDL 最表层的角色是签发简短好看的 URL。但真正的价值在其背后:同一个链接在 iOS 上点击会跳转到 App Store 或应用本身，在 Android 上点击会跳转到 Play 商店或应用，在桌面端点击则打开网页 - 这个自动识别平台并决定去向的路由层，一直隐藏在短链接背后。这套路由逻辑本身的消失，是第一重破坏。

1.2 应用未安装时的商店跳转

第二个角色，是把没有应用的用户平滑地引导到应用商店的回退机制。从营销角度看，这一点比想象中重要得多:如果点击链接后因为没有应用而只看到一片空白或报错，用户会立刻流失。FDL 一直自动处理这个分支，现在这套分支逻辑需要自己写。

1.3 延迟深度链接 - 把安装前的点击上下文带过去

三者中最难的是延迟深度链接(deferred deep link):用户在没有安装应用的情况下点击了指向某个商品或活动的链接，经由商店安装应用并首次启动时，仍然要被带到最初想看的那个页面。这三个角色全部压在 FDL 一个服务上，所以 FDL 消失时，深度链接、商店跳转、延迟深度链接是同时垮掉的。

2. 重新打好基础 - 通用链接与 App Links

要自建替代方案，首先必须准确理解深度链接的底层机制，因为以前由 FDL 这类工具代劳的部分，现在要自己动手设计。

2.1 iOS 通用链接与 AASA

iOS 的通用链接(Universal Links)沿用普通的 https:// 链接形式，却能路由到应用内部。核心是 AASA(apple-app-site-association)文件，必须以 HTTPS、无重定向、128KB 以内的大小，托管在域名的 /.well-known/apple-app-site-association 路径下。应用端则要在 Associated Domains entitlement 中以 applinks: 前缀注册该域名 - 这是一种双向信任关系，只有两端互相指向对方，验证才能成立。实务中容易被忽略的一点是:自 iOS 14 起，苹果会把 AASA 文件缓存在自家 CDN 上，服务器端的修改可能要滞后数小时才会反映到苹果边缘节点。开发阶段可以用 ?mode=developer entitlement 绕开缓存、直接从服务器拉取，调试会轻松很多。

2.2 Android App Links 与 assetlinks.json

Android 对应的概念是 App Links，验证文件放在 /.well-known/assetlinks.json。文件中必须写明应用包名和签名证书的 SHA-256 指纹。实务中最常见的失败原因，是使用 Play 应用签名(Play App Signing)时开发签名与发布签名的指纹不一致，导致 assetlinks.json 中登记的指纹与实际发布应用的指纹对不上。这个文件同样需要以无重定向的 HTTP 200 和 application/json 的 Content-Type 响应，应用安装后的验证是异步进行的，大约需要 20 秒左右才能完成，这一点也要纳入考虑。

2.3 为什么自定义 Scheme 依然有必要

即便有了通用链接与 App Links，像 myapp:// 这样的自定义 URL Scheme 也无法完全放弃。在系统标准路由无法按预期工作的环境中 - KakaoTalk 应用内浏览器就是韩国市场的典型例子 - 自定义 Scheme 反而可能更稳定。实务中最终的做法通常是:以通用链接为主，在特定入口路径上并行使用自定义 Scheme 作为回退。

3. 延迟深度链接，最棘手的一环

3.1 为什么格外难

通用链接与 App Links 都建立在「应用已安装」这个前提之上。问题出在应用还没安装的时候。用户被引导去商店安装应用的那一刻，原始点击链接携带的参数就已经丢失了 - 商店不会在安装完成后，自动把「这个用户点击的是哪个链接」这个信息交还给应用。因此延迟深度链接本质上变成了一个需要服务器单独拼接的问题:把点击时刻的上下文和安装后首次启动时刻的上下文重新对应起来。

3.2 Android Install Referrer 的局限

Android 好歹还有一条官方通道:Google Play Install Referrer API。应用首次启动时，可以通过这个 API 取回安装时携带的引荐参数。但这个方法仅适用于经由 Play 商店的安装，对旁加载或其他应用商店渠道的安装无效。

3.3 iOS 最终只能依赖概率匹配

iOS 上根本不存在这样的官方通道。所以选择自建，最终只能依赖基于指纹的概率匹配:在点击链接时把设备信息、IP 地址、时间戳、User-Agent 存到服务器上，应用首次启动时再比对是否观测到同一组信息，从而推断「这次安装大概率来自那次点击」。这在本质上只能是近似值，如果多个用户在同一网络、相近时间点击，就可能发生误匹配。Branch、Adjust 这类商业平台之所以收费，部分原因正是它们用大规模设备图谱把这种概率匹配的精度拉高了。

4. 自建基础设施需要准备什么 - 清单

如果打算用自建方案替代 FDL，至少要准备好以下四个方面。

4.1 域名与静态文件托管

需要一个专用于深度链接的域名(或子域名)，并在其 /.well-known/ 路径下稳定地提供 AASA 和 assetlinks.json。关键在于这些文件必须无重定向、始终来自同一域名、并考虑缓存策略地对外提供。如果前面挂了 CDN，还需要一并设计缓存失效策略。

4.2 服务器路由逻辑

需要能根据 User-Agent 判断 iOS、Android、桌面端，并分别路由到通用链接、App Links 或网页的服务器逻辑。此外，由于事先无法确定「应用是否已安装」这一根本不确定性，还必须同时准备好应用不存在时的回退(跳转商店)和应用存在时的处理(自定义 Scheme 或通用链接)。

4.3 短链接与参数设计

为规避外部服务停服的风险，更安全的做法是把短链接的生成与解析流水线整个放在自有域名内管理。维护一个把短代码(例如 base62 编码)映射回原始参数的存储，在点击时还原参数用于路由。同时准备好携带完整参数的长回退 URL，这样即使短链接环节失败或延迟，功能也能优雅降级而不是直接失效。

5. 韩国特有的坑 - KakaoTalk 分享的陷阱

5.1 应用内浏览器让标准失效

接下来这部分，单看 iOS、Android 官方文档是找不到答案的，是韩国本地服务特有的问题。通过 KakaoTalk 分享的链接，会在其内置的应用内浏览器中打开，而不是用户的默认浏览器。在这种环境下，通用链接、App Links 的系统级拦截经常无法按预期触发。也就是说，即便把 iOS、Android 的标准实现得再完美，来自 KakaoTalk 的流量里深度链接仍可能失效。

5.2 基于 executionParams 的分支处理

绕开这个问题的实务方法之一，是利用 KakaoLink(KakaoTalk 分享 SDK)的 executionParams 之类的参数。发送消息时附带执行时参数，由应用端和服务器端共同设计分支:已安装应用的用户通过自定义 Scheme 直接打开应用，未安装的用户则被引导到单独的网页落地页。原作者把这种状况称为「죽은 단축링크의 해부」(死掉的短链接解剖，原文见参考资料)，这个说法很好地体现了单靠标准规范无法解决的、韩国本地即时通讯生态特有的问题。

6. 商业 SaaS 与自建方案 - 该买什么、该造什么

6.1 成本结构对比

FDL 停服后谷歌官方推荐的替代方案，是 Branch、Adjust、AppsFlyer OneLink、Kochava 这类商业深度链接与归因平台。大致的成本结构对比如下。

方案大致计费优势取舍
Branch起价约每月 500 美元，可议价成熟的延迟深度链接、跨平台支持流量越大费用越高
Adjust约每月 500 美元或按安装计费防作弊、按 MAU 计费较可预测高流量场景下负担较重
AppsFlyer OneLink席位制加按安装计费与归因分析一体化只需深度链接也要付全套费用
自建方案仅服务器与开发人力成本数据完全自主、可深度定制精度与维护全部由团队承担

6.2 判断标准

本人的判断标准很明确:如果深度链接需求主要是分享链接、简单路由为主，流量规模不大，自建方案的初期投入在总体拥有成本上往往比商业 SaaS 的持续订阅费更划算。反过来，如果大规模营销归因、防作弊检测、跨多个应用商店和平台的精细延迟深度链接直接关系到核心业务指标，那么成熟商业平台在精度和维护成本转移上的优势会更明显。FDL 曾经是「免费」的，导致很多团队从未真正做过这道取舍题 - 这才是这次停服事件真正的教训。

7. 实务迁移清单

  • 确认 FDL 停服前是否导出了现有链接与点击数据(若已经错过，按数据不可恢复来重新设计)
  • 获取专用于深度链接的域名，并准备托管 /.well-known/apple-app-site-association 与 /.well-known/assetlinks.json
  • 在应用代码中落实 iOS Associated Domains entitlement 与 Android App Links intent filter
  • 构建服务器路由逻辑 - 基于 User-Agent 区分 iOS/Android/桌面端并实现商店回退
  • 确认是否真的需要延迟深度链接 - 如果不需要，可以大幅缩小自建范围
  • 单独测试经由 KakaoTalk 应用内浏览器的流量，确认是否需要 executionParams 式分支
  • 在自有域名内构建短链接流水线(生成、解析、跳转)，或选定商业服务
  • 对 Branch、Adjust、AppsFlyer OneLink 等商业方案做总体拥有成本估算，与自建方案对比
  • 制定考虑 AASA/assetlinks.json 缓存延迟(苹果 CDN、Android 约 20 秒验证)的发布与回滚计划
  • 排查二维码、短信、邮件等线下渠道中已经印发的旧链接是否需要处理跳转

结论:FDL 停服不是警告，而是已经发生的事实

截至2026年7月，FDL 停服已经不再是「需要提前准备的未来」，而是「已经发生的过去」。但这件事之所以仍然值得重提，是因为「深度链接靠一个 SDK 就能搞定」这种惯性思维，依然留在不少团队里。通用链接、App Links 本质上是域名与应用互相验证的信任关系;延迟深度链接从根本上是一个需要服务器概率性填补的缺口;而 KakaoTalk 这样的本地即时通讯环境，又在其上叠加了一层额外的例外。理解了这三层之后，无论选择商业 SaaS 还是自建方案，至少能清楚知道自己买的是什么、扛的是什么。本人的建议是:流量不大的产品可以自建，归因直接关系到收入的产品更适合用商业平台。但无论选哪一边，都值得亲自把这份迁移清单过一遍。
