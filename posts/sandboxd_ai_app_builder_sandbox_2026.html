sandboxd — AI 앱빌더를 위한 오픈소스 샌드박스 엔진

AI가 생성한 코드를 안전하게 격리·실행하는 인프라의 작동 원리와 보안 관점 분석

2026-06-18 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: AI가 쓴 코드는 누가 감시하는가

2026년 6월 기준, Lovable·Bolt·v0·Replit 같은 AI 앱빌더 서비스는 수천만 명의 사용자가 매일 사용하는 인프라가 됐다. 사용자가 "할 일 관리 앱 만들어줘"라고 입력하면 AI가 코드를 생성하고, 그 코드는 즉시 어딘가에서 실행되어 동작하는 웹 앱 링크가 나타난다. 이 과정이 너무 자연스러워서 많은 사람이 그 뒤에 있는 핵심 인프라 문제를 놓친다. AI가 생성한 코드는 신뢰할 수 없는 코드다.

이 코드가 서버에서 실행될 때 무슨 일이 일어날까. 악의적인 프롬프트로 유도된 코드가 서버 파일시스템을 삭제할 수 있는가. 한 사용자의 샌드박스가 다른 사용자의 데이터에 접근할 수 있는가. 환경 변수로 저장된 API 키나 데이터베이스 비밀번호가 노출될 수 있는가. 이 모든 질문에 답하는 것이 샌드박스 격리이고, sandboxd는 이 문제를 자체 호스팅으로 해결하려는 오픈소스 프로젝트다.

이 글은 sandboxd의 작동 구조를 분석하고, AI 앱빌더 생태계에서 코드 실행 격리가 왜 핵심 인프라 문제인지, 그리고 Firecracker·gVisor·WebContainers 같은 기술들이 각각 어떤 위협 모델을 다루는지 본인 관점으로 정리한다. 2026년 6월 기준 실제 GitHub 저장소와 관련 기술 문서를 기반으로 작성했다.

1. sandboxd란 무엇인가 — 구조와 철학

1.1 핵심 개념

sandboxd는 한 마디로 "AI 앱빌더 제품의 오픈소스 백엔드 엔진"이다. Lovable·Bolt·v0처럼 "프롬프트 입력 → 몇 초 후 동작하는 앱 링크 출력"하는 서비스를 자체 서버에서 구현하기 위한 인프라를 제공한다. 공식 저장소(github.com/tastyeffectco/sandboxd)에 따르면, HTTP 요청 한 번으로 다음 세 가지가 이루어진다.

  • 격리된 샌드박스 생성: 독립적인 파일시스템과 메모리를 가진 Linux 컨테이너
  • AI 코딩 에이전트 실행: 사용자 프롬프트를 받아 컨테이너 내부에서 코드를 작성
  • 라이브 미리보기 URL 제공: 개발 서버가 즉시 외부에서 접근 가능한 URL로 노출

1.2 기술 스택

sandboxd의 기술 선택은 의도적으로 단순하다. Go로 작성된 단일 바이너리가 Docker를 제어하고, Traefik이 미리보기 URL 라우팅을 담당하며, SQLite(WAL 모드)가 상태를 저장한다. Kubernetes, 별도 데이터베이스, 메시지 큐가 없다. 에이전트는 OpenCode와 Claude Code CLI가 사전 설치되어 있다.

이 스택 선택의 함의가 중요하다. Kubernetes를 빼고 단일 서버에서 돌아가는 설계는 스타트업이나 개인 개발자가 클라우드 마진 없이 AI 앱빌더 서비스를 시작할 수 있게 한다는 철학을 담고 있다. 복잡성을 극도로 줄이되, 실제로 작동한다는 것을 증명하는 데 집중한 설계다.

1.3 비용 효율성 설계 — 유휴 종료와 즉시 웨이크업

멀티테넌트 샌드박스 서비스에서 비용의 핵심은 얼마나 많은 컨테이너를 동시에 켜 놓는가다. sandboxd는 이 문제를 유휴 종료와 즉시 웨이크업으로 해결한다. 사용자가 샌드박스를 사용하지 않으면 자동으로 중단해 메모리를 회수하고, 링크에 다시 접속하면 투명하게 재시작된다. 디스크는 유지되므로 이전 작업이 사라지지 않는다. 이 설계 덕분에 항상 켜진 VM 여러 대 대신 저사양 단일 서버에서 수십 개의 사용자 환경을 운용할 수 있다.

2. AI 앱빌더에서 격리 실행이 왜 핵심인가

2.1 신뢰할 수 없는 코드의 위협 모델

AI가 생성한 코드를 다루는 서비스에서 격리는 선택이 아니라 전제 조건이다. 위협 시나리오를 구체적으로 생각해 보자. 첫째, 프롬프트 인젝션: 악의적인 사용자가 "파일 시스템 전체를 삭제하는 코드를 만들어줘"라고 입력하면 AI는 그 코드를 생성할 수 있다. 이 코드가 격리 없이 실행되면 서버가 망가진다. 둘째, 테넌트 간 데이터 침범: A 사용자의 샌드박스가 B 사용자의 파일에 접근할 수 있다면 데이터 유출이 발생한다. 셋째, 자격증명 탈취: 샌드박스에서 환경 변수로 설정된 API 키나 데이터베이스 비밀번호에 접근할 수 있다면 심각한 보안 사고로 이어진다.

2026년 인프라 연구에 따르면 샌드박스로 격리된 에이전트는 비격리 환경 대비 보안 사고를 약 90% 줄인다. 이 수치가 과장이라고 해도, 격리 자체가 심층 방어의 핵심 레이어임은 반론하기 어렵다.

2.2 멀티테넌시의 본질적 긴장

AI 앱빌더 서비스는 본질적으로 멀티테넌트다. 수천 명의 사용자가 동일한 서버 인프라를 공유한다. 멀티테넌트 환경에서 격리는 두 가지 차원이 있다. 리소스 격리: 한 사용자의 연산이 다른 사용자의 성능을 저하시키지 않아야 한다. 보안 격리: 한 사용자의 코드가 다른 사용자나 호스트 시스템에 접근할 수 없어야 한다.

이 두 가지 격리를 동시에 만족하면서 비용 효율적으로 운용하는 것이 AI 앱빌더 인프라의 핵심 기술 과제다. sandboxd는 Docker 컨테이너로 기본 격리를 제공하지만, 프로덕션에서는 더 강한 격리 레이어를 요구한다고 명시하고 있다.

2.3 격리 없는 서비스의 실제 사례

실제로 초기 AI 코딩 서비스들은 격리 문제로 보안 이슈를 겪었다. 공유 서버에서 사용자 코드를 실행하면서 다른 사용자의 환경 변수에 접근 가능했던 사례, 파일시스템 탐색으로 다른 프로젝트 코드를 읽을 수 있었던 사례 등이 보고됐다. 이런 사고들이 AI 앱빌더 생태계가 격리를 핵심 인프라 요건으로 격상시키는 계기가 됐다.

3. 격리 기술의 스펙트럼 — Docker부터 MicroVM까지

3.1 표준 Docker 컨테이너의 한계

sandboxd는 현재 Docker 기반이다. Docker 컨테이너는 빠르고 익숙하며 오버헤드가 작다. 그러나 근본적인 한계가 있다. 호스트 커널을 공유한다. 컨테이너 내부에서 커널 취약점을 악용하면 컨테이너 탈출(container escape)이 가능하다. 역사적으로 runc, cgroups, 네임스페이스 구현에서 여러 CVE가 발견됐다. 신뢰할 수 있는 내부 사용자만 있다면 Docker로 충분하다. 하지만 외부 사용자가 임의의 코드를 실행하는 멀티테넌트 AI 앱빌더에서는 Docker 단독으로는 부족하다는 것이 2026년의 인프라 컨센서스다.

3.2 Firecracker MicroVM — 강한 격리, 빠른 시작

AWS Lambda와 Fargate의 기반인 Firecracker는 각 워크로드에 전용 Linux 커널을 주는 MicroVM 기술이다. 커널 공유가 없으므로 컨테이너 탈출 자체가 불가능하다. 약 125ms에 부팅되고 VM당 5MB 미만의 메모리 오버헤드를 갖는다. 하나의 호스트에서 초당 최대 150개의 VM을 생성할 수 있다. E2B(AI 에이전트용 샌드박스 서비스)가 Firecracker를 기반으로 150ms 시작 시간을 달성하는 것이 대표적인 사례다.

Firecracker의 트레이드오프는 복잡성이다. Docker보다 설정과 운영이 어렵고, KVM 하이퍼바이저가 필요하므로 클라우드 인스턴스 타입을 가려야 한다. 그러나 신뢰할 수 없는 멀티테넌트 코드 실행에서 Firecracker는 사실상 업계 표준이 되어가고 있다.

3.3 gVisor — 사용자 공간 커널로 공격 표면 축소

Google이 개발한 gVisor는 다른 접근법을 택한다. 별도 VM을 만드는 대신, 컨테이너의 시스템 콜을 가로채 사용자 공간에서 처리한다. 호스트 커널에 도달하는 시스템 콜 수를 수백 개에서 수십 개로 줄여 공격 표면을 크게 감소시킨다. Modal, Northflank 같은 서비스가 gVisor를 사용한다. Docker와 달리 Kubernetes와 네이티브로 통합되어 있어 쿠버네티스 기반 인프라에서 특히 유용하다.

gVisor의 트레이드오프는 성능이다. 시스템 콜마다 가로채는 비용이 있어 I/O 집약적 워크로드에서 10~30% 오버헤드가 발생한다. AI 코딩 에이전트 워크로드는 파일 읽기쓰기가 많으므로 이 오버헤드를 고려해야 한다.

3.4 WebContainers — 브라우저 안의 샌드박스

bolt.new를 구동하는 StackBlitz의 WebContainers는 완전히 다른 격리 레이어를 택한다. Node.js 런타임을 WebAssembly로 컴파일해 브라우저 탭 안에서 실행한다. 원격 서버가 아예 필요 없다. 코드 실행이 브라우저의 샌드박스 경계 안에서 이루어지므로 로컬 파일시스템이나 네트워크에 접근할 수 없다. 2026년 기준 npm 생태계 대부분을 지원하며, 브라우저 IndexedDB로 node_modules를 캐싱해 재로드가 거의 즉시 이루어진다.

WebContainers의 한계는 브라우저에 묶인다는 것이다. Python, Rust, 데이터베이스 같은 Node.js 외 환경을 지원하기 어렵다. 또한 클라이언트 측에서 실행되므로 서버 사이드 비즈니스 로직을 숨길 수 없다. sandboxd가 서버 측 격리를 택한 이유가 여기에 있다 — 언어와 런타임에 제약이 없고, 서버 자원을 온전히 쓸 수 있다.

4. sandboxd의 보안 모델과 한계

4.1 현재 보안 상태 (베타)

sandboxd는 공식 문서에서 베타 품질임을 명시하고, 기본 설정이 로컬 개발용임을 숨기지 않는다. API 인증이 기본 비활성화되어 있고, 미리보기 링크는 URL을 알면 누구나 접근 가능하며, 네트워크 송신 제한이 없다. 이 설정 그대로 외부에 노출하면 심각한 보안 문제가 발생한다.

그러나 sandboxd가 이를 숨기지 않는다는 점이 오히려 신뢰를 준다. 많은 오픈소스 프로젝트가 보안 문제를 README에 작게 적어 넘어가는 반면, sandboxd는 프로덕션 요건을 명시적으로 나열한다.

4.2 프로덕션에서 필요한 조치

sandboxd 공식 문서가 권고하는 프로덕션 필수 조치를 정리하면 다음과 같다.

  • API 인증 활성화: SANDBOXD_API_AUTH_DISABLED=false 설정 후 토큰 기반 인증 구현
  • 미리보기 URL 게이팅: Forward-auth 훅으로 인증된 사용자만 접근 허용
  • 네트워크 제어: 방화벽 + 송신 규칙으로 컨테이너의 외부 통신 제한
  • 디스크 쿼터: 볼륨·파일시스템 쿼터로 단일 사용자 디스크 남용 방지
  • 격리 런타임 교체: 신뢰할 수 없는 코드에는 Docker 대신 gVisor·Kata·Firecracker 사용

4.3 Docker 기반 격리의 현실적 평가

본인 관점에서, sandboxd의 현재 Docker 기반 격리는 내부 팀이나 소수 신뢰 사용자가 쓰는 환경에서는 충분하다. 그러나 외부 사용자가 임의의 프롬프트를 입력하는 공개 서비스에서는 불충분하다. Firecracker 같은 MicroVM 통합이 없으면 "AI 앱빌더 제품을 위한" 수식어를 공개 프로덕션에서 완전히 충족하기 어렵다.

이 한계를 인식한다는 것은 sandboxd가 해결해야 할 다음 과제가 무엇인지 보여준다 — Firecracker나 gVisor와의 통합이 프로젝트의 미래 방향이어야 한다.

5. AI 앱빌더 생태계에서 오픈소스 샌드박스의 의미

5.1 상업 서비스 의존에서 벗어나기

Lovable·Bolt·v0는 뛰어난 서비스지만, 그 내부 인프라는 공개되어 있지 않다. 이를 자체 서버에서 재현하려면 E2B, Modal, Northflank 같은 샌드박스 서비스에 의존해야 한다. 이 서비스들은 훌륭하지만 사용량 기반 과금이고, 비즈니스 성장에 따라 비용이 급격히 늘어날 수 있다. sandboxd는 이 의존성을 끊고 자체 서버에서 인프라 비용을 통제할 수 있는 경로를 제공한다.

특히 스타트업 초기 단계에서는 클라우드 서비스의 마크업 없이 원가로 인프라를 운용할 수 있다는 점이 결정적이다. 단일 서버에서 수십 명의 사용자를 서비스할 수 있다면, 스케일이 필요해지기 전까지는 상당한 비용 이점이 생긴다.

5.2 데이터 주권과 코드 프라이버시

외부 AI 앱빌더 서비스를 쓴다는 것은 사용자의 프롬프트와 생성된 코드가 그 서비스의 서버를 거친다는 의미다. 기업 내부 도구, 규제 산업의 프로토타입, 민감한 비즈니스 로직을 다루는 서비스에서는 이 데이터 이동이 문제가 될 수 있다. sandboxd를 자체 인프라에 배포하면 코드와 프롬프트가 외부로 나가지 않는다. 데이터 거주 요건(data residency)이 있는 금융·의료·공공 분야에서 특히 의미 있는 장점이다.

5.3 AI 앱빌더 서비스 시장의 진입 장벽 낮추기

sandboxd가 등장하기 전, "프롬프트 → 즉시 실행 웹 앱" 서비스를 만들려면 자체적으로 격리 인프라, 미리보기 URL 라우팅, 유휴 관리를 모두 구현해야 했다. 이 복잡성이 상당한 진입 장벽이었다. sandboxd는 이 복잡성을 ./install.sh 한 줄로 낮춘다. 이는 AI 앱빌더 서비스의 시장 진입 장벽을 낮추고, 다양한 수직 시장(교육용, 특정 언어 특화, 기업 내부용 등)을 위한 특화 서비스가 나올 수 있는 토대가 된다.

6. 현재 한계와 냉정한 평가

6.1 베타 단계의 신뢰성 문제

sandboxd는 현재 베타 품질이며, 이는 프로덕션 서비스에 직접 사용하기엔 SLA와 안정성 측면에서 위험이 있다는 의미다. GitHub 저장소의 이슈 트래커를 보면 엣지케이스 버그가 여전히 발견되고 있다. "읽고 확장하도록 만들어졌다"는 공식 설명은 코드 품질 자체는 좋지만, 운영 성숙도는 스스로 다져야 한다는 뜻이다.

6.2 강한 격리 런타임의 부재

앞서 언급했듯, Docker 기반 격리는 신뢰할 수 없는 외부 사용자의 코드 실행에 충분하지 않다. Firecracker나 gVisor와의 통합이 없는 현재 상태에서는 공개 AI 앱빌더 서비스의 백엔드로 쓰기 위해 직접 런타임 교체 작업을 해야 한다. 이는 상당한 엔지니어링 작업이다.

6.3 단일 서버의 스케일 한계

sandboxd의 단순성은 단일 서버에서 작동한다는 전제에서 나온다. 이 전제는 초기 단계에서 장점이지만, 트래픽이 늘어나면 수평 확장이 어렵다. Kubernetes가 없다는 것은 자동 스케일링도 없다는 의미다. 수백 명 이상의 동시 사용자를 다루는 서비스라면 sandboxd만으로는 한계가 있고, 추가 인프라 작업이 필요하다.

7. 활용 판단 — 언제 쓰고 언제 쓰지 말 것인가

7.1 sandboxd가 잘 맞는 상황

내부 도구 또는 소수 신뢰 사용자를 위한 AI 코딩 환경, AI 앱빌더 서비스의 PoC 또는 초기 MVP, 교육 기관이나 해커톤에서 일시적으로 사용자별 개발 환경을 제공하는 경우, 데이터 주권이 중요한 기업 내부 AI 개발 플랫폼에서 sandboxd는 합리적인 선택이다. 복잡성 없이 빠르게 시작할 수 있고, MIT 라이선스로 수정과 커스터마이징이 자유롭다.

7.2 sandboxd만으로 부족한 상황

외부에 오픈된 공개 AI 앱빌더 서비스, 수백 명 이상의 동시 사용자, 규제 요건이 있는 산업(의료, 금융, 공공), 또는 SLA 보장이 필요한 프로덕션 환경에서는 sandboxd를 그대로 쓰기 어렵다. Firecracker 통합, 수평 확장, 강화된 인증 레이어가 추가로 필요하다. 이런 환경에서는 E2B나 Modal 같은 상용 서비스가 현실적인 출발점이 될 수 있다.

7.3 오픈소스로서의 기여 가치

sandboxd의 진짜 가치는 코드 자체뿐 아니라 AI 앱빌더 샌드박스 인프라의 설계 패턴을 공개했다는 점에 있다. 유휴 종료와 즉시 웨이크업, 미리보기 URL 라우팅, API 기반 컨테이너 생명주기 관리 같은 패턴을 실제 구현으로 볼 수 있다. 직접 사용하지 않더라도 자체 샌드박스 인프라를 구축하는 데 참조할 수 있는 좋은 레퍼런스 구현이다.

결론 — AI가 코드를 쓰는 시대의 인프라 과제

2026년 6월 기준, AI 앱빌더는 더 이상 미래 기술이 아니다. 매일 수천만 명이 쓰는 현재 인프라다. 그리고 이 인프라의 안전성은 샌드박스 격리라는 기술 문제에 달려 있다. sandboxd는 이 문제에 대한 오픈소스 답변이다 — 완벽하지 않고, 베타 단계이며, 강한 격리 런타임이 빠져 있다. 하지만 설계 철학은 명확하고, 구현은 읽기 쉽고 확장 가능하다.

더 큰 그림에서 보면, sandboxd 같은 프로젝트의 존재는 AI 앱빌더 생태계가 성숙하는 신호다. 클라우드 서비스에만 의존하던 AI 인프라가 오픈소스화되면서 접근성이 높아지고, 다양한 수직 시장에 특화된 서비스가 나올 토대가 만들어지고 있다. Firecracker·gVisor·WebContainers는 각자 다른 위협 모델에 대한 답이고, 올바른 선택은 단일한 정답이 아니라 각 서비스의 위협 모델과 운영 역량에 달려 있다.

AI가 코드를 쓰는 시대에, 그 코드를 누가 어떻게 감시하는가는 기술 인프라의 핵심 과제다. sandboxd는 그 과제에 대한 하나의 오픈소스 접근법을 보여준다.
