引言：为什么要看日志而不是图表

运营者谈论自己站点的流量时，拿出来的依据几乎总是分析工具的仪表盘。而仪表盘在结构上就看不见这个问题。网页分析只有在浏览器里执行了 JavaScript 才计一次，而自动化采集器几乎不跑 JavaScript。于是服务器实际上被砸得多重，那里根本没有记录。

现在有了一份用真实数字展示这个落差能拉到多大的记录。运营慈善捐赠人调研数据库 PatronView 的 Nick Gray 公开了自己150万页站点上一年的服务器日志观测。某一周里服务器处理了250万次外部请求，送出128万个页面。同一时段分析工具记录到的真人页面浏览是5,977次，不到千分之五。

本文不把这份记录当战绩来读，而是落在一个问题上：我的站点是不是也在被抓，如果是，先做什么。内容包括日志里该看哪些信号、各类应对手段在效果与成本与副作用上如何分岔，以及小站点绝对不该做的过度反应是什么。

先把话说清楚。本文只从防守方视角写。采集方的技法和绕过拦截的方法一律不涉及。而本文里最危险的项目不是抓取器，而是搜索爬虫的误封。一条规则写错，抓取器照样进来，消失的只有索引。这部分单独放在第7章。

1. 分析工具为什么看不见这个问题

不换测量仪器，诊断根本无从开始。这一步偏了，后面所有判断都会跟着偏。

1.1 JavaScript 标签只统计真人

Gray 表示自己用的是自托管的 Plausible Community Edition。无论工具是哪一个，性质都一样。埋在页面里的标签要在浏览器中执行才会记上一次，而采集器通常只取走 HTML、不执行脚本。所以分析数字作为「真人流量估计值」还算好用，作为「服务器负载」则完全不能用。

  • 在 Gray 的记录里，分析工具每捕获一次页面加载，背后就有约214次看不见的加载
  • 也就是说仪表盘显示每天1,000次页面浏览，并不代表服务器一天只干了1,000次活。这个倍率因站而异，不测就没人知道
  • 如果前面挡着 CDN 或反向代理，源站日志也留不全。需要同时看边缘侧日志或仪表盘上的请求数
  • 如果是静态托管、拿不到日志，至少要看带宽用量和请求数曲线。这两项是把机器人一起算进去的

1.2 第一次打开日志时先抽的四样

工具不必讲究。只要手上有访问日志，下面四样就足以勾出轮廓。

# 1) 按 User-Agent 统计请求数的前20
awk -F'"' '{print $6}' access.log | sort | uniq -c | sort -rn | head -20

# 2) 按客户端 IP 统计请求数的前20
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -20

# 3) 状态码分布 (404 突增是 URL 枚举的信号)
awk '{print $9}' access.log | sort | uniq -c | sort -rn

# 4) 总请求数 (与同一时段的分析数字并排比较)
wc -l access.log
  • 把第1项和第4项对齐到同一时段是关键。时段错开，倍率就失去意义
  • 第2项里如果排名靠前的 IP 集中在一两个，处理起来很轻松。反过来，如果均匀散在几万个 IP 上，封 IP 就不是答案
  • 第3项里 404 异常多，说明有人在遍历不存在的 URL。正常用户不会造出这种形状
  • 日志轮转周期太短就什么也看不到。打算做诊断的话，先把保留期拉长才是顺序

2. 在日志里辨认抓取器的信号

信号单独使用会造成误判。只在多项重叠时才下判断。

2.1 判别信号与各自的误报风险

日志里可见的信号怀疑什么误报风险
总请求数是分析数字的几十到几百倍自动采集主导了全部负载低。但需分离图片与 API 请求
User-Agent 为空按默认配置跑的脚本低。部分老旧客户端也会留空
请求从单一 ASN（数据中心）涌来跑在云上的采集器中。企业代理与 VPN 用户可能同 ASN
几万个 IP 各自只发几次经住宅代理的分布式采集高。与移动运营商 NAT 形状相近
冒充几年前的浏览器版本没更新过的伪造 UA中。确实存在使用老设备的用户
按顺序把列表页一路翻到底整站采集低。真人不会按这个顺序移动
404 比例突然飙升URL 模式枚举低。站点改版刚过是例外
不取静态资源（CSS、JS、图片）只抓 HTML 的客户端中。需与已缓存的回访者区分
Referer 始终为空自行拼出 URL 直接调用高。大量正常流量本就不发 Referer
深夜时段比平时还多与真人活动曲线无关的访问中。海外读者多的站点属正常

2.2 这张表怎么用

  • 不要用单一信号做规则。只凭误报风险为「高」的项去拦，先被拦住的是真人
  • 最稳妥的组合是「数据中心 ASN + 不取静态资源 + 顺序翻列表」三项同时成立
  • 反过来，「无 Referer」单独一项绝不能当规则材料。隐私设置、应用内浏览器、书签进入全都会落在这里
  • 拦截之前一定要用仅记录（log-only）模式跑几天，确认这条规则一天抓到多少次、其中有没有混进真人
  • Gray 加入老旧浏览器版本检查之后，也用数字确认了只有0.54%的真实流量命中该规则。先量「会命中多少」才是顺序

3. 抓取与引流之比 - 把判断压成一行

Gray 立下的判断标准不是技术的而是经济的。压成一句：这个爬虫拿走多少页，又送回来多少人。比值太差就拦。

3.1 已公开的实测比值

爬虫拿走的量送来的真人比值
Googlebot--每位访客46页
Bingbot（封锁前）--每位访客406页
Bingbot（后续观测）158,610页680人约233:1
Claude-SearchBot每周420,680页（4.63GB）12人（175KB）约35,000:1
Amzn-SearchBot每天约117,000次请求无已确认引流无法测量

这张表里值得盯住的是 Googlebot 的46:1。Gray 认为这个程度算是把本挣回来了。也就是说这个标准不是把所有机器人都当敌人的装置，而是一把把付得起代价的爬虫和付不起的分开的尺子。

3.2 这个指标的局限

  • 答案会随站点性质翻转。如果被 AI 回答引用本身就是目的，引流为零也没有理由去拦
  • 引流的测量本身就不准。很多路径不发 Referer，实际引流可能被低估
  • 也有只标注出处而不加链接的服务。这种情况品牌有曝光，日志上什么也不留
  • 反过来说，有引流也不等于这些引流有价值。只看抓取比而不看转化，就只看了一半
  • Gray 本人把问题定性为定价而非技术，说如果有按次抓取付费的机制，他会以公道价格把访问卖出去。拦截是没有谈判手段时的次优解

4. 抓取器实际在做什么

要定对策，先得把对手分型。Gray 的记录里出现了性质完全不同的三类。

4.1 报上名号来的那一类

大厂的爬虫会把自己的名字写进 User-Agent。它们遵守规范，所以处理起来最省事，效果也能立刻验证。

  • Anthropic 在2026年2月表示旗下三个爬虫尊重 robots.txt
  • Gray 的记录与该表述吻合。Claude-SearchBot 在封锁后几天内从每天六万次降到二十五次，降幅约99.96%
  • 反例也有。Amzn-SearchBot 在拦截规则生效后请求仍在进来，记录到43,150次。也就是收到拒绝应答后还在继续敲门
  • 对报名号的爬虫，做法很简单。量比值，差就按名字拦。到这一步风险还很低

4.2 藏着来的那一类 - 住宅代理与 UA 伪造

麻烦从这里开始。不报名字、装成普通浏览器、借家庭宽带线路进来的流量。

  • Gray 表示观测到一个冒充 Chrome 版本、经由从代理商租来的数千条普通家庭线路路由的僵尸网络。每一次请求看上去都像真人
  • 7月31日，独立 IP 数一天之内从18,000个跳到124,000个。这就是 IP 级封锁失去意义的临界点
  • 还有从 Microsoft Azure 一小时拿走23,000页的案例，分散在80多个 IP 上发送，因而没有触发既有的速率限制
  • 于是应对的轴心改变了。从 IP 转向 ASN，从单次请求转向整个会话的行为

会话级判别为何成为近期方向。只看一次请求，伪造的头部和真实浏览器无法区分。所以商用防御产品已从按请求的指纹转向整个会话的移动模式。这一思路的背景在Precursor 登场 - Cloudflare 为何通过全会话行为识别 AI 智能体中另行讨论。

4.3 一天之内的暴涨

不是缓慢爬升，而是一天之内翻好几倍。这实际上更接近一次负载事故。

  • 2026年4月22日，Gray 的站点一天记录到360万次请求、361,844个独立 IP，几乎全部来自中国
  • Cloudflare 的自动质询仅头10小时就处理了118万次
  • 他第二天上了国家级封锁，之后在看到同样模式时追加了越南和新加坡
  • 这类暴涨的特点是告警来得晚。只要服务器扛得住，错误率就不会上升，等账单来了才知道

5. 各类应对手段的效果、成本与副作用

这是本文的目的地。每种手段得到的和失去的都不一样。顺序搞错，效果看不到，副作用全带回家。

5.1 手段对照表

应对手段效果成本副作用与风险
在 robots.txt 里加 Disallow只对遵守规范的爬虫有效几乎没有对无视者为0。会公开你列出的路径
提高缓存命中率实实在在降低负载与账单配置时间几乎没有。应当最先做
按 User-Agent 名称拦截对报名号的爬虫立竿见影写规则的时间正则写宽会连搜索爬虫一起拦
IP 级封锁只对单一来源的暴涨有效低对分布式代理无力。名单维护负担
ASN（数据中心）级封锁对云上采集效果显著需维护名单误伤企业代理与 VPN 用户
速率限制抑制单一来源的暴涨低分散到多 IP 即可绕开。阈值过低会拦到真人
CAPTCHA 与托管质询大幅压低自动化通过率产品订阅费无障碍性下降，对辅助设备用户尤其苛刻
JavaScript 检测识别不执行脚本的客户端页面加载延迟性能分数下降。屏蔽脚本的用户流失
国家级封锁对特定地区暴涨立竿见影无把那个国家的真实用户全挡住。对方一换即失效
付费 WAF 与机器人管理产品把会话级判别整体外包月度订阅费出现误报时更难追踪原因
已验证机器人跳过规则从结构上防止搜索爬虫误封无不放在最前面就没有效果

5.2 这张表隐含的顺序

  • 缓存排第一。它是降低负载而几乎没有副作用的唯一手段。与其说是抓取器对策，不如说是基本功
  • 其次是已验证机器人跳过规则。必须放在拦截规则之前，后面的规则才不会碰到搜索爬虫。这个顺序一反，后面全都变危险
  • 第三是按名称拦截。把比值差的爬虫按名字明确拦掉。要用名单，不要用通配符
  • 第四是 ASN 与速率限制。误报从这里开始，所以先用仅记录模式量一量
  • 质询与国家封锁放在最后。只有账单或响应时间真的坏掉时才动用

5.3 Gray 最终定型的规则构成

作为参考，Gray 在一年之后定型的防火墙规则是九段结构。它说明顺序本身就是设计。

  1. 封锁特定国家（中国、越南）
  2. 按名称封锁12种 SEO 工具爬虫
  3. 封锁 AI 爬虫（robots.txt 路径作为例外放行）
  4. 让已验证机器人跳过后续规则
  5. 对北美以外地区下发托管质询
  6. 对空 User-Agent 下发质询
  7. 对46个数据中心 ASN 下发质询
  8. 对多年前的老旧浏览器版本下发质询
  9. 单 IP 每10秒超过30次请求即下发质询

请看第3条和第4条的位置关系。即便有一条封锁 AI 爬虫的规则，也要靠已验证机器人例外排在它后面，Googlebot 才能活下来。而第3条把 robots.txt 路径留作例外的理由同样清楚：如果把 robots.txt 本身也挡了，连想守规矩的爬虫都读不到哪些是禁止的。

6. robots.txt 能做什么、不能做什么

这里的误解最深。robots.txt 不是拦截装置。规范文件自己就是这么写的。

6.1 RFC 9309 实际规定了什么

机器人排除协议在2022年9月被标准化为 RFC 9309。核心条款如下。

  • 文件明确写道这些规则并不是一种访问授权形式，也就是没有强制力
  • 服务器对 robots.txt 请求以 4xx 应答时，爬虫可以访问服务器上的任何资源。文件不存在会被解读为全面放行
  • 反过来出现 5xx 时，爬虫必须假定全面禁止。所以提供 robots.txt 的路径若不稳定，抓取可能整体停摆
  • 缓存建议不要使用超过24小时。也就是说改了规则，仍会有爬虫按旧规则跑一天
  • 解析器至少要读到500 KiB。写在那之后的规则有可能永远读不到
  • 安全考量一节说得更直接：列出路径只会把它们暴露出去，需要访问控制就用真正的安全手段

6.2 那么 robots.txt 该怎么用

  • 当作意愿声明来用。对愿意遵守的一方是真管用。Claude-SearchBot 在封锁后降了99.96%就是证据
  • 不要把秘密路径写进去。把管理后台路径写进 Disallow 的那一刻，这条路径就公开了。该用认证守住的东西不该写在这里
  • robots.txt 本身要始终可访问。如果防火墙规则连这个文件也挡了，配合的爬虫也读不到规则
  • 别让这个文件返回 5xx。按规范会被解读为全面禁止，可能让整个索引动摇
  • 拦截要在防火墙层另行设置。robots.txt 和防火墙规则是目的不同的两套装置

7. 误封搜索爬虫，索引就会消失

这一章在本文里最重要。抓取器防御可能让你付出的最大代价不是服务器开销，而是搜索曝光。

7.1 事故是怎么发生的

  • 最常见的事故是只要 User-Agent 里含 bot、crawler、spider 就全拦的规则。Googlebot 和 Bingbot 直接中招
  • 第二是速率限制阈值定得太低。搜索爬虫本来就扫得快。按真人节奏定阈值，先被绊住的是爬虫
  • 第三是国家封锁盖住了爬虫的出口地。搜索厂商的抓取基础设施从哪些地区出去，站点运营者控制不了
  • 第四是对所有请求都下质询。爬虫不解质询。被索引的会是质询页面而不是内容页
  • 第五是把 robots.txt 路径本身也挡了。规则读不到，配合也就无从谈起

7.2 真正的危险在于损失浮现得晚

  • 封锁的那一刻排名不会掉。要等重新抓取周期转回来，页面才开始从索引里掉出去，需要几天到几周
  • 于是「上规则 → 流量下滑」的因果看不见，多数人会先怀疑别的原因而浪费时间
  • 恢复也不对称。解除封锁后，抓取预算还要花时间才回得来
  • 安全装置有三条。① 把已验证机器人例外放在拦截规则之前。② 拦截对象用名单明确写出。③ 上线后两周内盯住搜索控制台的抓取统计与索引数量
  • Cloudflare 以两条标准判定已验证机器人：诚实的自我标识（加密签名、公开 IP 名单配稳定 UA，或反向 DNS 三者之一）与非滥用行为（遵守 robots.txt、保持合理请求速率），并公开该名单。避免误封的实务依据就在这里
  • Gray 也是拦 AI 爬虫而继续放行 Googlebot 与 Bingbot。这是算账而不是宽容。46:1 和 233:1 是付得起代价的比值

8. 防御装置本身收取的代价

这是评估时最常被漏掉的一项。拦截的装置也不是免费的。它不只收费用，还收速度和无障碍性。

8.1 性能代价 - 有数字为证的案例

  • Gray 表示 Cloudflare 的 JavaScript 检测在中端手机上消耗了2,875毫秒，而站点自身的 JavaScript 是278毫秒
  • 也就是说安全功能制造了超过站点代码十倍的延迟
  • 关掉之后，一小时内移动端 Lighthouse 分数从58升到99
  • 代价也是有的。关掉之后，来自 Azure 的一波在一小时内拿走了23,000页。这就是取舍关系的直接呈现
  • 教训很清楚。开了安全功能之后，务必把性能再量一遍。能开和能一直开着是两回事

8.2 质询通过率是真人负担的指标

上了质询，就必须监控通过率（solve rate）。这个数字会告诉你到底拦住了什么。

  • Gray 的48小时观测：下发质询106,437次，解出252次，通过率0.24%
  • 来自新加坡的流量7,089次里只解出3次。来自印度的失败率99.14%，来自伊拉克的失败率100%
  • 最终规则生效后的24小时：直接拦截46,729次，下发质询63,969次，解出552次
  • 读法是这样的。通过率在0.2%上下，说明几乎全是自动化。反过来出现30%上下，说明大量真人正在被拦，得把规则收窄
  • 也有不能只看通过率的理由。质询一出现就放弃离开的人连失败统计都进不去。流失发生在这个数字之外

8.3 账单是怎么动的

  • Gray 给出的平时基础设施开销约为每月90美元（Workers、D1 等）
  • 抓取严重时这笔开销上涨约500%
  • 为使用安全规则所需的上位套餐是每月25美元
  • Gray 指出，如果是固定配置的服务器环境，这些流量会变成威胁存续的成本问题。按量计费还是包月，会让同样的流量呈现出不同的面孔
  • 由此得出一条实务结论：先确认计费结构。包月托管是响应速度先垮，按量计费则是速度没事而账单先到

9. 小站点不该做的过度反应

这是本文里最容易出错的地方。一天几百次访问的站点，把150万页站点的规则整套照抄，得不到什么，失去的却不少。

  • 不要对所有访客下质询。流量少的站点，一次质询造成的放弃就是实打实的流量损失，比拦掉机器人省下的开销更大
  • 不要照抄别人的封锁名单。ASN 名单和 UA 名单是按那个站点的读者构成做出来的。先看自己的读者从哪来
  • 不要拿国家封锁当第一张牌。那是锁定来源之后才用的手段。原因不明就去涂地图，被挡住的只有真人
  • 不要把 UA 正则写宽。大部分事故都从这里来。一个个写名字虽然枯燥但安全
  • 不要按真人节奏定速率限制阈值。真人在浏览器里打开一个页面，里面会飞出几十个资源请求。用页面级的直觉定阈值，会拦到正常用户
  • 不要把执行 JavaScript 当成访问条件。关掉脚本使用的用户、辅助设备用户、老旧设备会被一起挡住
  • 不要日志都没看就先买付费产品。不知道原因就往上叠产品，等误报发生时连是哪一层拦的都查不出来
  • 不要把机器人流量本身当目标。该降下来的不是请求次数，而是账单和响应时间。用拦截去解决缓存本能解决的负载，买到的只有副作用
  • 不要一次性上全部规则。九条同时打开，出问题时分不清是哪条。一条一条来，每条用仅记录模式跑几天
  • 不要以为拦了就完事。对方会移动。不按季度重新测量，就只剩规则而效果消失

也有反方向的意见。围绕这个案例的评论里，有观点认为问题的相当一部分不在机器人而在站点结构。如果有150万个无法缓存的动态页面，负载就算没有机器人也迟早会来。而且像旅游或电商那样，机器人访问反而有利的站点也存在。也就是说，拦截不是普适解法，而是由自己站点的经济结构决定的选择。

10. 先做什么 - 分阶段的顺序

顺序本身就是安全装置。照着下面的顺序走，很难闹出大事故。

  1. 先测量。把同一时段的服务器请求数和分析数字并排放。不知道倍率就做不了任何判断
  2. 确认成本。账单真的涨了吗，响应真的慢了吗。两者皆非的话，到这里停下也可以
  3. 整理缓存。提高命中率，减少重的动态路径。这是唯一没有副作用的区间
  4. 看 UA 排名。从榜单顶部挑出报名号的爬虫，逐个量抓取与引流之比
  5. 先上已验证机器人例外。放在之后所有拦截规则之前的位置
  6. 只按名字拦比值差的爬虫。用名单方式，不用通配符
  7. 仅记录模式跑几天。确认每条规则一天抓到多少次、有没有混进真人
  8. 再上 ASN 与速率限制。误报从这里开始，一次只改一处
  9. 盯两周索引。抓取统计或索引数量下滑就立刻回滚
  10. 还疼再上质询。同时看通过率，出现30%上下就把规则收窄
  11. 每季度重测一次。对方移动了，规则的效果也会跟着移动

11. 未能确认的部分

把依据不足的条目集中放在一处。

  • 原文正文的完整表述与防火墙规则的确切表达式。本文数字沿用 GeekNews 摘要与 PPC Land 报道中登载的值，规则的实际语法未作比对
  • 封锁后 Amzn-SearchBot 那43,150次请求的性质。这些请求是收到了拒绝应答，还是走了别的路径，未能确认
  • 一年间损失的搜索流量规模。国家封锁与质询究竟损失了多少真实用户，没有公开数值
  • 被封爬虫此后的重试模式。是否换个名字又回来，未能确认
  • 其他规模站点上的可复现性。这些数字出自一个150万页的数据库站点。没有依据认为几百页的站点会得到同样的倍率
  • 住宅代理流量背后真正的委托方。谁为了什么在采集，日志里看不出来
  • 其他厂商环境下的应对选项。本案例以特定 CDN 厂商的功能为前提。其他厂商同类功能的名称与行为是否一致，未能确认

12. 常见问题

怎么确认自己的站点是否正在被抓取?

要看服务器访问日志，而不是分析工具。Plausible 或 GA 这类工具只统计执行 JavaScript 的访客，而大多数抓取器根本不跑 JavaScript。PatronView 运营者 Nick Gray 公开的一周记录里，服务器处理了250万次请求、送出128万个页面，而分析工具记录到的真人页面浏览只有5,977次，不到千分之五。日志里要看四样东西。第一是同一时段总请求数与分析数字之间的落差，第二是按 User-Agent 排列的请求量，第三是集中在单一 IP 或单一 ASN 的请求，第四是以真人不会采用的顺序遍历 URL 的行为。这四项里对上两项，就可以认定自动化采集正在运行。

写好 robots.txt 就能挡住抓取器吗?

挡不住。把 robots.txt 标准化的 RFC 9309 明确写道，这些规则并不是一种访问授权形式；其安全考量一节还说，列出路径只会把这些路径公开出去，若需要访问控制就该使用真正的安全手段。也就是说 robots.txt 只对愿意遵守的一方有效。但它并非无用。对遵守规范的爬虫是真的管用。在 Gray 的记录里，Anthropic 的 Claude-SearchBot 在封锁后几天之内就从每天六万次降到二十五次左右。反过来，对无视规范的一方毫无作用，所以 robots.txt 应当作为意愿声明保留，真正的拦截要在防火墙层另外设置。

封锁 AI 爬虫会连搜索曝光一起减少吗?

取决于规则怎么写，而且风险是真实存在的。凡是 User-Agent 里含有 bot 或 crawler 之类词就一律拦截的宽泛正则，会把 Googlebot 和 Bingbot 一起抓进去。搜索爬虫被挡住后页面会从索引里掉出来，而且这种损失并不会在解除封锁的那一刻恢复。安全的做法分两步。其一，在所有拦截规则之前放一条已验证机器人的跳过规则，让 Googlebot 和 Bingbot 根本碰不到后面的规则。其二，拦截对象用名单明确列出，而不是用通配符。上线之后要在搜索控制台观察抓取统计和索引数量至少两周。

按国家封锁可以做吗?

效果很大，但副作用也是清单里最粗暴的。Gray 在2026年4月22日一天之内收到来自361,844个独立 IP 的360万次请求，第二天封锁了中国，随后在看到同样模式时又追加了越南和新加坡。如果站点读者仅限本国，这个选择可能是合理的。但要预先接受三点。第一，那个国家的真实用户、侨民、出差者和漫游用户会被一起挡住。第二，抓取器换个国籍就行，效果并不持久。第三，国家级封锁是在日志里锁定来源之后才用的手段，而不是在不知原因时先打出的牌。如果国际访客与营收挂钩，先尝试 ASN 级别的封锁更稳妥。

小站点也需要上付费 WAF 吗?

只要每月账单还不疼，就还不需要。防御装置本身也有代价，而且不只是订阅费，还有性能和无障碍上的代价。Gray 表示 Cloudflare 的 JavaScript 检测功能在中端手机上吃掉了2,875毫秒，关掉之后一小时内移动端 Lighthouse 分数就从58升到99。也就是说，原本用来过滤机器人的装置，先削掉的是真人的体感速度。判断标准很简单。流量增长是否真的抬高了账单或拖慢了响应，还是只有图表上的数字看起来吓人。如果是后者，把缓存命中率提上去、只对重路径加速率限制，多半就能收场。

结论：今天带走的三点

第一，先换诊断工具。分析工具是为统计真人而造的东西，原理上就看不见这个问题。仅仅把同一时段的服务器请求数和分析数字并排放，判断就完成了一半。Gray 的记录里这个倍率约为214倍。自己站点的倍率，不测就没人知道。

第二，判断标准是价值而不是机器人数量。压成抓取与引流之比这一条，应对就变简单了。Googlebot 的46:1 算是把本挣回来了，35,000:1 则不是。但这个标准会随站点翻转。被引用本身就是目的的站点，引流为零也不是损失。先定下自己站点的经济结构，规则才定得下来。

第三，可能失去的最大的东西不是服务器开销而是索引。一条写宽的正则、一个定低的速率阈值，先被拦住的就是搜索爬虫。而这种损失几天后才浮现，回滚了也不会立刻复原。把已验证机器人例外放在拦截规则之前，把拦截对象写成明确名单，上线后盯两周索引。这三点没有商量余地。

最后一点。这个案例里能长久留下的不是九条防火墙规则，而是它们的顺序。测量 → 确认成本 → 缓存 → 例外 → 拦截 → 观测。守住这个顺序，大多数站点会停在第3步。而停在第3步，通常就是正确答案。
