기술 문서를 통제된 언어로 강제하면 무엇이 달라지나

벌점 74에서 3으로, 어휘 34퍼센트 감소 - 그리고 이것을 모든 문서에 적용하면 안 되는 이유

2026-08-01 IT/기술

서론: 같은 문장을 두 사람이 반대로 이해했다

절차서에 이런 문장이 있었다고 하자. 「커버를 분리하기 전에 케이블이 분리되어야 한다」. 한 사람은 케이블을 먼저 뽑았고, 다른 사람은 커버를 먼저 열었다. 둘 다 그 문장을 읽었고, 둘 다 자기가 맞게 읽었다고 생각했다. 문장이 틀린 것이 아니다. 그 문장은 두 가지로 읽히는 것이 허용된 문장이었을 뿐이다.

이런 사고가 났을 때 보통 나오는 처방은 「문서를 더 자세히 쓰자」다. 그런데 자세히 쓸수록 문장은 길어지고, 길어질수록 갈라지는 지점이 늘어난다. 다른 방향의 처방이 있다. 쓸 수 있는 단어와 문장 구조를 미리 줄여 버리는 것이다. 갈라질 여지가 있는 표현을 애초에 쓰지 못하게 한다. 이것을 통제된 언어라고 부른다.

이 글은 그 방식을 다루되, 「쉬운 영어로 쓰자」는 이야기는 하지 않는다. 대신 두 가지를 한다.

  • 검사기를 직접 만들어 숫자로 잰다. 같은 절차 문단을 통제 전후로 넣어 문장 길이, 수동태 비율, 모호어, 용어 변형 수를 비교했다. 벌점 74가 3으로 떨어졌고, 뜻밖에도 전체 단어 수는 40퍼센트 줄었다
  • 적용하면 안 되는 곳을 같은 검사기로 증명한다. 잘 쓰인 개념 설명 문단을 넣었더니 문장의 60퍼센트가 규칙을 위반했다. 그 글은 나쁜 글이 아니라 목적이 다른 글이다

실행 환경. 아래 모든 숫자는 Windows 10 Pro (10.0.19045)의 Node.js v22.16.0 (win32)에서 직접 만든 검사기를 실행해 얻은 것이다. 외부 라이브러리는 쓰지 않았다. 검사기 전체 코드는 3절에 있고, 그대로 복사해 돌릴 수 있다.

규격 본문은 열지 않았다. 항공 분야의 대표 규격인 ASD-STE100은 공식 사이트에서 신청을 통해 PDF로 배포된다. 나는 공식 사이트의 개요와 FAQ 페이지, 그리고 공개 해설 문서까지만 확인했고 규격 PDF 본문은 읽지 않았다. 따라서 이 글에는 53개 규칙의 전체 목록도, 승인 어휘 900단어의 내용도 없다. 아래에서 인용하는 수치와 규칙은 공식 사이트와 공개 해설이 밝힌 범위이며, 본문에 나오는 구체적인 검사 규칙은 내가 만든 검사기의 규칙이지 규격의 규칙이 아니다.

이 글의 예문은 전부 가상이다. 등장하는 장비, 절차, 문서는 실재하지 않는다. 문서 포맷 자체의 문제는 AI 시대의 한국 문서 포맷에서 다뤘고, 이 글은 포맷이 아니라 문장을 다룬다.

1. 통제된 언어란 무엇인가

통제된 언어는 문체 지침이 아니다. 문체 지침은 「가급적 능동태를 쓰세요」라고 권하고, 통제된 언어는 수동태를 아예 쓸 수 없게 만든다. 권고와 금지의 차이가 아니라, 선택지가 있는 상태와 없는 상태의 차이다.

가장 널리 알려진 사례는 항공 정비 문서에서 나왔다. 공식 사이트의 설명에 따르면 배경은 이렇다. 복잡한 기술 지시는 오해될 수 있고, 오해는 사고로 이어질 수 있다. 그래서 영국·유럽 항공사들이 요청해 1980년대에 규격이 만들어졌다. 확인한 범위에서 이 규격의 구성은 다음과 같다.

  • 작성 규칙 53개가 9개 절로 나뉘어 있다. 문법과 문체를 다룬다
  • 승인 어휘 약 900개. 각 단어는 원칙적으로 뜻 하나, 품사 하나만 갖는다
  • 비승인 어휘 약 1,200개가 대체어와 함께 목록으로 제시된다. 널리 인용되는 예가 start는 승인되고 begin, commence는 승인되지 않는다는 것이다
  • 현재 판은 Issue 9 (2025년 1월)이고, 유지 관리는 1983년에 만들어진 전담 그룹이 맡는다
  • 항공에서 출발했지만 육상·해상 차량, 재생에너지, 의료기기 분야에서도 쓰인다고 공식 FAQ가 밝히고 있다

여기서 놓치기 쉬운 대목이 하나 있다. 승인 어휘 900개는 전부가 아니다. 공식 FAQ는 각 산업의 기술 명사와 기술 동사는 별도로 쓸 수 있다고 명시한다. 도면, 공식 문서, 사내 용어집에서 나온 용어라면 승인 목록 밖의 단어여도 된다는 뜻이다. 즉 통제된 언어는 어휘를 900개로 가두는 것이 아니라, 「일반 어휘는 900개로 고정하고 전문 용어는 근거 있는 목록으로만 늘린다」는 구조다. 이 구분을 모르고 도입하면 첫 주에 「이 단어를 못 쓴다」는 불만으로 무너진다.

2.1 수동태가 위험한 진짜 이유

수동태를 금지하는 이유가 「어색해서」라고 생각하면 절반만 맞다. 같은 지시를 세 가지로 써 놓고 비교해 보면 문제가 드러난다.

--- 같은 지시, 세 가지 표현 ---
(1) The cable must be disconnected before the cover is removed.
(2) Disconnect the cable. Then remove the cover.
(3) Remove the cover after disconnecting the cable.

                        (1)          (2)            (3)
누가 하는가              명시 없음    읽는 사람      명시 없음
무엇이 먼저인가          케이블       케이블         케이블
읽는 순서와 작업 순서    반대          일치           반대
한 문장에 든 지시 수     2개          1개            2개
「must」의 대상          불명확       불필요         불명확
  • (1)과 (3)은 읽는 순서와 작업 순서가 반대다. 급한 상황에서 앞부터 읽고 행동하면 순서가 뒤집힌다. (2)만 읽는 대로 하면 된다
  • (1)의 must는 누구에 대한 의무인지 말하지 않는다. 작업자인지, 설계인지, 소프트웨어인지 문장 안에 근거가 없다
  • (3)의 after disconnecting은 문법적으로 흠이 없지만 동명사가 시간 관계와 조건을 동시에 뜻할 수 있다. 「분리한 뒤에」인지 「분리한 경우에만」인지 갈린다
  • 수동태 금지의 실효는 문체가 아니라 행위자를 반드시 적게 만드는 것에 있다. 명령문으로 쓰면 행위자는 자동으로 읽는 사람이 된다

3. 검사기를 만들어 재 봤다 - 무엇을 어떻게 세는가

규칙을 말로 설명하는 것과 그 규칙이 실제로 문서를 얼마나 바꾸는지는 다른 문제다. 그래서 검사기를 만들었다. 어떤 규격도 구현하지 않았다. 통제 규칙이 묶는 네 가지, 즉 문장 길이·수동태·모호한 지시·용어 일관성만 센다.

// ste_check.js — Node 22, 의존성 없음.  실행: node ste_check.js doc.txt proc
const LIM = { proc: 20, desc: 25 }, PARA = 6, NOUN = 3;

const PASSIVE = /\b(?:is|are|was|were|be|been|being)\s+(?:not\s+|often\s+|normally\s+)?([a-z]+(?:ed|en)|done|set|put|kept|sent|made)\b/gi;

const VAGUE = ['as required', 'if necessary', 'as appropriate', 'properly', 'correctly',

핵심은 아래 세 함수다. 어형 변화 처리를 빼먹으면 검사기가 조용히 실패한다. 처음 만들었을 때 commence에 ed를 붙여 commenceed를 찾고 있었고, 그래서 동의어 혼용이 명백한 문단에서 위반 0을 돌려줬다. 검사기가 0을 돌려주면 문서가 깨끗한 것이 아니라 검사기가 고장 난 것일 수 있다.

// 명사 뭉치 — 문장부호, 기능어, 숫자에서 끊는다
function runs(s) { const out = [];
  for (const c of s.split(/[,;:.()]+/)) { let cur = [];
    for (const t of c.split(/\s+/).filter(Boolean)) {
      const l = t.toLowerCase().replace(/[^a-z0-9]/g, '');
      if (!l || /\d/.test(l) || STOP.has(l) || /(?:ed|ing|ly)$/.test(l)) {
        if (cur.length > NOUN) out.push(cur.join(' ')); cur = [];
      } else cur.push(t); }
    if (cur.length > NOUN) out.push(cur.join(' ')); }
  return out; }

4. 실측 - 같은 절차 문단, 통제 전후

가상의 장비 펌웨어 갱신 절차를 두 가지로 썼다. 내용은 완전히 같고 문장 규칙만 다르다. 먼저 흔히 보는 쪽이다.

--- A. 통제 없이 쓴 절차 (실무에서 흔한 문체) ---
Before the firmware update is started, it should be verified that the unit is powered
from the primary supply and that the redundant supply cable is disconnected, since the
update procedure cannot be commenced while both supplies are active. The configuration
backup file, which is normally generated by the maintenance console during the previous
session, must be copied to the removable media before proceeding, and it is recommended
that the operator confirms that the file size is not zero. If the status indicator is
flashing, the controller has not finished the previous write cycle and the operation
should be halted until the indicator becomes steady. After the media is inserted, the
update is initiated from the service menu, and the process, which typically takes about
eight minutes, must not be interrupted. The device will be restarted automatically; if
it is not restarted within two minutes, power should be removed and the unit should be
started again manually. Any configuration entries which were not migrated correctly can
be corrected later using the console, but the relevant log files should be retained for
analysis as required.
--- B. 같은 내용, 통제 규칙 적용 ---
Start this procedure only when the primary supply gives power to the unit.

Disconnect the redundant supply cable. Make sure that the backup file on the removable
media has a size of more than 0 bytes. If the status indicator flashes, wait until the
indicator is continuously on.

Put the removable media in the slot. Start the update from the service menu.
Do not stop the update. The update takes 8 minutes.

The unit starts again automatically. If the unit does not start again in 2 minutes,
remove the power. Then start the unit manually.

Keep the log files. You can correct the configuration entries with the console after
this procedure.

5. 번역이 쉬워진다 - 어휘 34퍼센트 감소가 뜻하는 것

통제된 언어의 도입 근거로 가장 자주 인용되는 것이 번역이다. 공식 FAQ도 원문의 변이가 줄어들기 때문에 번역이 쉬워진다고 적고 있다. 이 문장을 숫자로 옮기면 4절의 distinct 열이다. 107단어에서 71단어. 같은 내용을 옮기는 데 번역자가 판단해야 할 서로 다른 표현이 3분의 1 줄었다.

  • 번역 단가는 분량보다 변이에 좌우된다. 번역 메모리는 이전에 번역한 문장과 얼마나 비슷한지로 값을 매긴다. 문형이 반복되면 완전 일치와 근사 일치 비율이 올라가고, 새로 번역할 몫이 줄어든다
  • 기계번역이 틀리는 세 가지가 통제로 사라진다. 긴 문장에서 수식어를 엉뚱한 명사에 붙이는 오류, 수동태에서 행위자를 지어내는 오류, 대명사를 잘못 연결하는 오류다. 세 가지 모두 문장이 짧고 능동태이며 대명사가 없으면 일어날 자리가 없다
  • 용어 일관성이 번역에서 배로 커진다. 원문에서 start와 commence를 섞어 쓰면 번역자는 「뜻이 다르니까 다르게 썼겠지」라고 판단해 서로 다른 역어를 고른다. 원문의 무의미한 변이가 번역문에서는 의미 있는 차이로 굳어진다
  • 다만 이 이득은 원문을 규칙에 맞게 쓴 대가다. 번역기를 바꾸거나 후처리를 붙여서 얻는 것이 아니다. 비용은 원문 작성자가 낸다

여기서 정직해야 할 것이 하나 있다. 공식 FAQ는 규격을 지원한다고 주장하는 자동 도구를 인증하거나 보증하지 않는다고 명시한다. 어떤 도구도 규격 자체를 대신할 수 없다는 것이다. 내가 만든 검사기도 마찬가지다. 이것은 규칙을 재는 자이지 규칙이 아니다.

착각하기 쉬운 지점. 「통제된 언어를 도입하면 번역비가 준다」는 결론은 다국어로 내보내는 문서에 한해 성립한다. 국내에서만 쓰는 한국어 절차서에 이 논리를 그대로 가져오면 근거가 없다. 그 경우 이득은 번역비가 아니라 오독 감소이고, 그것은 사고 기록으로만 증명된다. 도입을 설득할 때 내 조직에 해당하지 않는 근거를 가져다 쓰면 첫 반론에서 무너진다.

6. 유지오탐 신고를 받아 규칙을 고친다분기마다 용어집이 갱신된다신고를 받고 문서를 고치라고 한다

9.1 경고 모드에서 강제 모드로

훅은 단순할수록 오래 간다. 경로로 모드를 나누고, 임계값 하나만 둔다.

# 절차서 경로 — 강제. 임계값을 넘으면 빌드를 세운다
for f in docs/procedures/*.md; do
  node ste_check.js "$f" proc | tee -a report.txt
done
node ste_gate.js report.txt --max-score=10 || exit 1

# 설명 문서 경로 — 경고만. 빌드는 세우지 않는다
for f in docs/concepts/*.md; do
  node ste_check.js "$f" desc
done

# 적용하지 않는 경로는 아예 실행하지 않는다
#   docs/tutorials/  docs/adr/  docs/postmortems/
  • 임계값은 문서 하나 기준으로 잡는다. 저장소 전체 합계로 잡으면 문서가 늘어날 때마다 저절로 실패한다
  • 우회 수단을 반드시 만들어 둔다. 특정 문단을 검사에서 빼는 주석을 허용하되, 그 주석이 몇 개나 쓰였는지 세어 보라. 늘어나면 문서가 아니라 규칙이 틀린 것이다
  • 새 문서에만 강제하고 기존 문서는 손대는 김에 고치게 한다. 전수 개정을 먼저 요구하면 도입 자체가 무산된다
  • 도입의 성패는 도구가 아니라 1단계 용어집에서 갈린다. 검사기는 용어집을 강제하는 수단일 뿐이고, 용어집이 없으면 강제할 것도 없다

10. 점검 목록과 하지 말 것

도입을 검토한다면 아래 항목으로 자기 조직의 상태를 먼저 확인하는 편이 낫다.

  • 적용하지 않을 문서 유형을 먼저 목록으로 적었다
  • 용어집의 대표어가 남의 목록이 아니라 우리 문서에서 나왔다
  • 절차서와 설명서에 다른 한도를 적용한다
  • 검사기의 지표가 합계 하나가 아니라 항목별로 보인다
  • 경고 모드로 4주 이상 돌려 기존 문서의 분포를 쟀다
  • 임계값에서 기존 문서의 절반 이상이 통과한다
  • 오탐 신고 경로가 있고, 신고가 오면 규칙을 고친다
  • 다국어로 내보내지 않는 문서에는 번역비 절감을 근거로 쓰지 않았다
  • 한국어 원문 규칙과 영어 규칙을 따로 정의했다
  • 검사기가 위반 0을 보고했을 때 검사기를 먼저 의심해 봤다

10.1 하지 말 것

  • 전 저장소에 강제 모드부터 켜는 것 — 개념 설명 문서가 막히고, 사람들은 검사기를 끈다
  • 남의 동의어 목록을 그대로 가져오는 것 — 4.1절의 remove와 disconnect처럼 다른 개념이 한 묶음에 들어간다
  • 벌점 절대값으로 문서를 평가하는 것 — 가중치는 임의다. 쓸 수 있는 것은 같은 문서의 전후 비교뿐이다
  • 영어 한도를 한국어 문서에 그대로 적용하는 것 — 20단어는 영어 기준이다
  • 번역 품질 문제를 번역 단계에서 고치려는 것 — 6절의 명사 뭉치는 한국어 원문에서 만들어진 것이다
  • 규격 문서를 읽지 않고 규칙을 지어내는 것 — 이 글도 규격 본문을 열지 않았고, 그래서 53개 규칙 목록을 적지 않았다
  • 튜토리얼과 사후 분석에 통제 규칙을 거는 것 — 「왜」를 적는 자리가 규칙 안에 없다

결론은 처음의 장면으로 돌아간다. 커버와 케이블의 순서를 두 사람이 다르게 읽은 것은 문서가 읽기 어려워서가 아니라, 두 가지로 읽히는 것이 허용됐기 때문이다. 통제된 언어가 하는 일은 문서를 쉽게 만드는 것이 아니라 해석의 폭을 없애는 것이다. 그러니 기준은 하나다. 이 문서의 목적이 「읽히는 것」인가, 「같은 뜻으로 읽히는 것」인가. 앞이면 통제하지 말고, 뒤면 통제하라. 모든 문서에 적용할 것이 아니다.

# 통제된 언어 도입 — 문장 규칙표 · 검사기 · 판단표 · 점검 목록

> 출처: braindetox.kr — 기술 문서를 통제된 언어로 강제하면 무엇이 달라지나
> 근거: Windows 10 Pro / Node.js v22.16.0 에서 아래 검사기를 직접 실행한 결과
> ⚠ 규격 본문 PDF는 열지 않았다. 아래 규칙은 공개 설명 범위와 자체 실험에서 나온 것이며,
>   53개 규칙의 전체 목록과 승인 어휘 목록은 여기에 없다.

## 0. 대전제

**문서의 목적이 「읽히는 것」이면 통제하지 말고, 「같은 뜻으로 읽히는 것」이면 통제하라.**
모든 문서에 적용할 것이 아니다.

## 1. 문장 규칙표

| 규칙 | 값 | 왜 |
|---|---|---|
| 지시문 한 문장 | **20단어 이하** | 수식 관계가 갈라질 자리를 없앤다 |
| 설명문 한 문장 | **25단어 이하** | 같은 이유, 다만 한도를 늦춘다 |
| 한 문단 | **6문장 이하** | 한 문단 한 주제 |
| 명사 나열 | **3단어 이하** | 4단어부터 수식 관계가 다의적이 된다 |
| 한 문장에 든 지시 | **1개** | 순서를 뒤집는 사고의 최대 원인 |
| 수동태 | **금지** | 행위자가 사라진다 |
| 지시 없는 대명사 | **금지** | it, this, that 은 사람마다 다르게 연결한다 |
| 한 개념 | **한 단어** | start / begin / commence 혼용 금지 |
| 모호어 | **금지** | properly, as required, regularly → 수치로 |

## 2. 검사기 (Node 22, 의존성 없음)

```js
// ste_check.js   실행: node ste_check.js doc.txt proc
const LIM = { proc: 20, desc: 25 }, PARA = 6, NOUN = 3;
const PASSIVE = /\b(?:is|are|was|were|be|been|being)\s+(?:not\s+|often\s+|normally\s+)?([a-z]+(?:ed|en)|done|set|put|kept|sent|made)\b/gi;
const VAGUE = ['as required','if necessary','as appropriate','properly','correctly','regularly',
  'periodically','normally','usually','typically','should','may','might','could','various','relevant'];
const SYN = { start:['start','begin','commence','initiate','launch'],
  stop:['stop','halt','cease','terminate','abort'],
  check:['check','verify','confirm','validate','ensure','make sure'],
  remove:['remove','detach','disconnect','unplug'],
  fix:['fix','repair','correct','rectify'] };
const STOP = new Set(('a an the and or but if then of to in on at by for with from into over under is are was were be been ' +
  'being do does did has have had will shall can may must should would could not no this that these those it its they them ' +
  'their you your we our as than so when while after before during until up down out off about again also only very each ' +
  'who which whom whose what where why how all any some both more most other such there here one two three').split(' '));

const forms = v => { const o = new Set([v, v+'s', v+'ed', v+'ing']);
  if (v.endsWith('e')) o.add(v+'d'); if (v.endsWith('y')) o.add(v.slice(0,-1)+'ied'); return [...o]; };
const sents = t => t.replace(/\s+/g,' ').trim().split(/(?<=[.!?:])\s+(?=[A-Z0-9(])/).filter(Boolean);
const wc = s => s.toLowerCase().replace(/[^a-z0-9' ]/g,' ').split(/\s+/).filter(Boolean);

function runs(s) { const out = [];
  for (const c of s.split(/[,;:.()]+/)) { let cur = [];
    for (const t of c.split(/\s+/).filter(Boolean)) {
      const l = t.toLowerCase().replace(/[^a-z0-9]/g,'');
      if (!l || /\d/.test(l) || STOP.has(l) || /(?:ed|ing|ly)$/.test(l)) {
        if (cur.length > NOUN) out.push(cur.join(' ')); cur = [];
      } else cur.push(t); }
    if (cur.length > NOUN) out.push(cur.join(' ')); }
  return out; }

function analyze(text, mode) {
  const lim = LIM[mode || 'proc'], paras = text.trim().split(/\n{2,}/), ss = paras.flatMap(sents);
  const lens = ss.map(s => wc(s).length), total = lens.reduce((a,b) => a+b, 0);
  const low = ' ' + text.toLowerCase().replace(/[^a-z0-9' ]/g,' ').replace(/\s+/g,' ') + ' ';
  const has = w => low.includes(' ' + w + ' ');
  const passive = (text.match(PASSIVE) || []).length;
  const pron = (text.match(/\b(?:it|they|them)\b/gi) || []).length;
  const vague = VAGUE.filter(has);
  const varied = Object.entries(SYN).filter(e => e[1].filter(v => forms(v).some(has)).length > 1).map(e => e[0]);
  const cl = ss.flatMap(runs), over = lens.filter(n => n > lim).length;
  const longP = paras.filter(p => sents(p).length > PARA).length;
  return { sents: ss.length, words: total, distinct: new Set(ss.flatMap(wc)).size,
    avg: +(total/ss.length).toFixed(1), max: Math.max(...lens), over, passive, pron,
    vague: vague.length, varied, clusters: cl.length,
    score: over*3 + passive*2 + vague.length + pron + varied.length*3 + cl.length*2 + longP*2 };
}
module.exports = { analyze };
if (require.main === module) { const fs = require('fs');
  console.log(analyze(fs.readFileSync(process.argv[2], 'utf8'), process.argv[3])); }
```

| 설치 · 배포 런북 | **강제** | proc | 처음 보는 사람이 그대로 따라 함 |
| API 레퍼런스 | **강제** | proc | 기계번역·검색 요약에 그대로 노출 |
| UI 문구 · 오류 메시지 | **강제** | proc | 변이가 그대로 번역 비용 |

**경계선: 독자가 읽으면서 동시에 손을 움직이는가.** 그렇다면 강제, 아니면 적용 안 함.

## 5. 한국어 원문에서 먼저 고칠 것

| 습관 | 영어에서 벌어지는 일 | 고치는 법 |
|---|---|---|
| 주어 생략 (「차단한다」) | 행위자가 없어 수동태가 된다 | 한국어 원문에 주체를 적는다 |
| 조사 생략 (「전원 차단」) | 명사 나열이 된다 | 「전원을 차단한다」로 서술어를 살린다 |
| 명사 나열 (「교체 부품 장착 상태」) | 4단어 명사구, 수식 관계 다의적 | 동사로 풀어 쓴다 |
| 연결어미로 잇기 (「-하고 -할 것」) | 한 문장에 지시 여러 개 | 지시 하나에 문장 하나 |
| 「-할 것」 종결 | 의무인지 권고인지 갈린다 | 필수는 명령문, 조건부는 if 절 |

**번역 품질은 번역 단계가 아니라 한국어 작성 단계에서 결정된다.**

## 6. 도입 점검 목록

- [ ] 적용하지 **않을** 문서 유형을 **먼저** 목록으로 적었다
- [ ] 용어집 대표어가 남의 목록이 아니라 **우리 문서**에서 나왔다
- [ ] 절차서와 설명서에 **다른 한도**를 적용한다
- [ ] 검사기 지표가 합계 하나가 아니라 **항목별**로 보인다
- [ ] 경고 모드로 **4주 이상** 돌려 기존 문서의 분포를 쟀다
- [ ] 임계값에서 **기존 문서의 절반 이상**이 통과한다
- [ ] 오탐 신고 경로가 있고, 신고가 오면 **규칙을 고친다**
- [ ] 다국어로 내보내지 않는 문서에 **번역비 절감을 근거로 쓰지 않았다**
- [ ] 한국어 원문 규칙과 영어 규칙을 **따로** 정의했다
- [ ] 검사기가 위반 0을 보고했을 때 **검사기를 먼저 의심**해 봤다

## 7. 하지 말 것

- ❌ 전 저장소에 **강제 모드부터** 켜는 것 — 사람들이 검사기를 끈다
- ❌ **남의 동의어 목록**을 그대로 가져오는 것 — 다른 개념이 한 묶음에 들어간다
- ❌ **벌점 절대값**으로 문서를 평가하는 것 — 가중치는 임의다
- ❌ 영어 한도(20단어)를 **한국어 문서**에 그대로 적용하는 것
- ❌ 번역 품질 문제를 **번역 단계에서** 고치려는 것
- ❌ 규격 본문을 읽지 않고 **규칙을 지어내는 것**
- ❌ 튜토리얼·사후 분석에 통제 규칙을 거는 것 — 「왜」의 자리가 없다
- ❌ 검사기의 **0을 증거로** 받아들이는 것 — 어형 변화 하나 빠져도 0이 나온다
