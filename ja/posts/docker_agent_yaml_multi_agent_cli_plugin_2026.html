契機 - コードではなく設定ファイルで定義するエージェント

Docker AgentはDockerが公開しているオープンソースのツールで、エージェントのモデルと指示、ツール、協力するエージェントをYAMLファイルに書き、docker agentコマンドで実行するDocker CLIプラグインである。READMEは「Build, run, and share AI agents with a declarative YAML config, rich tool ecosystem, and multi-agent orchestration」と一行で紹介し、本文で「no code required」と述べている。

公式ドキュメントの冒頭は「Docker Agent is to AI agents what docker run is to containers」である。ドキュメントは、LLMのオーケストレーションループ、ツール実行、マルチエージェントの委譲、ストリーミング出力をDocker Agentが処理するため、利用者は配線ではなくエージェントが何をすべきかに集中できると説明している。

GeekNewsには2026年10月8日に登録された。リポジトリのメタデータでは、所有者はdocker組織、ライセンスはApache-2.0、作成日は2025年9月1日で、最新リリースは2026年10月7日のv1.149.0である。これらの値はGitHubのリポジトリ情報とリリースページの表示であり、その後変わる可能性がある。

インストールは3つの経路で案内されている。Docker Desktop 4.63以降にはプラグインが同梱済みで、docker agentをすぐ実行できる。Homebrewではbrew install docker-agentでインストールする。GitHubリリースのバイナリを~/.docker/cli-pluginsに置けば、docker agentとしても使える。ソースからのビルドにはGo 1.27以上が必要だとインストールのページは記している。

Docker Agentの位置づけ - 何であり何ではないか

公式ドキュメントのトップには、ツールの性格を4つの枠で要約した紹介カードがある。以下はその文言を言い換えたものである。

  • 何であるか： YAMLまたはHCLで宣言的に定義したAIエージェントを実行するCLIである。
  • 何ではないか： コードを書くフレームワークではなく、ホスティング型SaaSではなく、新しいモデルでもない。
  • 誰のためか： 接着コード（glue code）なしで自分のワークフローにエージェントを入れたい開発者である。
  • 何が得られるか： TUI、CLI、HTTP API、MCPサーバー、A2A、OCI配布をドキュメントは挙げている。
  • 出自： ドキュメントはDocker Engine、Docker Desktop、Docker Hub、Docker Scoutを作るDockerのオープンソースツールと紹介している。

ドキュメントは同じコーディングアシスタントを2通りで比較している。コードで作る例ではクライアント初期化、ツールスキーマ、ディスパッチ関数、メッセージループを合わせて約30行のPython接着コードがプロジェクトごとに必要とされ、Docker Agentでは8行のYAMLとdocker agent run agent.yamlの1行で済むと対比される。行数はドキュメントが挙げた例の値である。

単一エージェントのYAML構造とフィールド

READMEの最初の例は、agentsの下にrootエージェントを1つ置き、モデル、説明、指示、ツールを書く形である。実行はdocker agent run agent.yamlである。

agents:
                      root:
                        model: openai/gpt-5-mini
                        description: A helpful AI assistant
                        instruction: |
                          You are a knowledgeable assistant that helps users with various tasks.
                          Be helpful, accurate, and concise in your responses.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo

公式ドキュメントの紹介ページには、ファイルシステム、シェル、thinkツールを持つコーディングアシスタントの例が載っている。

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: A coding assistant
                        instruction: |
                          You are an expert developer. Help users write clean,
                          efficient code. Explain your reasoning step by step.
                        toolsets:
                          - type: filesystem
                          - type: shell
                          - type: think

下の表は、この2つの例とエージェント設定リファレンスに現れる主なフィールドをまとめたものである。リファレンスは「A configuration must define at least one agent under agents」と述べる。

フィールド 型 ドキュメントの説明 備考
agents マップ エージェント名をキーとする最上位項目 最低1つのエージェントを定義する
model 文字列 モデル参照。例はプロバイダ/モデルの形式 harnessを使わない限り必須と表示される
description 文字列 このエージェントの役割 スキーマ上は任意
instruction 文字列またはリスト システムプロンプト instruction_fileとは併用できず、リストは空行でつながる
toolsets リスト ツール設定の一覧 typeでツールを選び、mcpにはrefを加える
sub_agents リスト ローカルまたは外部のサブエージェント参照 委譲パターンで使う
handoffs リスト このエージェントが会話を渡せるエージェント名 ハンドオフパターンで使う

モデルプロバイダについて、READMEはOpenAI、Anthropic、Gemini、AWS Bedrock、Mistral、xAI、Docker Model Runnerなどを挙げ、「and more」と添えている。紹介ページはmodel:の1行を変えるだけでモデルを入れ替えられると説明し、ローカルモデルはDocker Model RunnerまたはOllamaで使えると記している。READMEは、少なくとも1つのAPIキーを設定するか、ローカルモデルにDocker Model Runnerを使うよう案内している。

設定リファレンスの全体スキーマには、上記のほかにも項目が注釈付きで並ぶ。そのうち4つを挙げる。

  • instruction_file： 設定ファイルからの相対パスのファイルでシステムプロンプトを読み込む。
  • fallback： 代替モデルの一覧と再試行回数、待機時間を指定する。
  • max_iterations： ツール呼び出しループの最大回数を制限する。
  • harness： 外部のコーディングCLIに委ねる設定で、typeにはclaude-code、codex、opencode、piが記されている。

HCLも同じ設定モデルの別の文法だとドキュメントは述べる。.yamlや.ymlを受け付ける場所では.hclも受け付け、HCLは内部で同等のYAML構造に変換されてから同じスキーマ検証を通る。

マルチエージェントの2パターン - 委譲とハンドオフ

マルチエージェントのページは、複雑な作業では専門化が有効であり、単一のエージェントにすべてを任せる代わりにコーディネーター、開発者、レビュアー、リサーチャーのようなチームを組めると説明する。各エージェントは自分のモデルとツール、指示を持つ。2つのパターンの比較はドキュメントの表に従う。

項目 委譲（sub_agents） ハンドオフ（handoffs）
構造 階層型（親、子、親） P2Pグラフ（A、B、C、A）
セッション 子はサブセッションで実行 同じセッションで会話を維持
コンテキスト 子は整理されたタスク説明を受け取る 次のエージェントが会話履歴の全体を見る
制御フロー 親は子が終わるまで待ち、その後に続行 アクティブなエージェントが切り替わり、前のエージェントはループから外れる
ツール transfer_task handoff
向いている場面 専門家へのタスク委譲 パイプライン型の作業、会話のルーティング

委譲では、sub_agentsを持つエージェントにtransfer_taskツールが自動で提供される。ツールのページによると引数はagent、task、expected_outputの3つで、すべて必須である。呼び出しはサブエージェントが結果を返すまでブロックされ、ドキュメントは1つの設定内でsub_agentsとhandoffsを併用することもできると記している。

ハンドオフは会話全体を別のエージェントに渡す方式である。ドキュメントの例は、コーディネーターがリサーチャーに、リサーチャーが要約エージェントに渡し、要約エージェントが再びコーディネーターに戻る構成である。

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: Coordinator that routes queries
                        instruction: |
                          Route research queries to the researcher.
                        handoffs:
                          - researcher
                    
                      researcher:
                        model: openai/gpt-5
                        description: Web researcher
                        instruction: |
                          Search the web, then hand off to the summarizer.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo
                        handoffs:
                          - summarizer
                    
                      summarizer:
                        model: openai/gpt-5
                        description: Summarizes findings
                        instruction: |
                          Summarize the research results, then hand off
                          back to root.
                        handoffs:
                          - root

ハンドオフのページは、このツールが同じ設定ファイルで宣言されたローカルのエージェントだけを対象とし、ネットワーク接続を開かないと述べる。リモートのエージェントに委譲するにはA2Aツールセットを使うよう案内している。各エージェントは自身のhandoffs配列に書かれた名前にだけ渡せる。

ドキュメントが示す選択基準は次のとおりである。

  • sub_agents： コーディネーターが専門家にタスクを送り、結果を統合する必要があるときに使う。
  • handoffs： エージェントが同じ会話を順番に処理するパイプラインやルーティングに使う。
  • background_agents： 互いに独立した複数のタスクを同時に実行するときに使う。ドキュメントはrun_background_agent、list_background_agents、view_background_agent、wait_background_agents、stop_background_agentというツール名を挙げる。

通常のハンドオフではhandoffツールを呼ぶかどうかをモデルが決めるため、呼ばない可能性があるとドキュメントは指摘する。これを防ぐforce_handoffは、エージェントが最終応答を出すときにランタイムが指定のエージェントへ会話を渡す。設定読み込み時に、対象が設定内で定義されていること、自分自身を指せないこと、force_handoffの連鎖が循環しないことが検証されるという規則が書かれている。

  • 循環の拒否： 進行中の委譲チェーンにすでに含まれるエージェントを再び指す委譲（たとえばaからbからa）はエラーで失敗する。
  • 深さの上限： 入れ子の委譲は10段階までで、ルートが最初のサブエージェントに委譲すると深さ1と数える。

ツールエコシステム - 組み込みツールセットとMCPサーバー

ツールのページは、エージェントがツール呼び出しを行うとDocker Agentのランタイムがツールを実行して結果を返し、エージェントがその結果を使って作業を続けると説明する。組み込みツールセットは、toolsetsリストにtypeを書いて有効にする。

ツール type ドキュメントが示す動作 ドキュメントが示す制約
ファイルシステム filesystem read_file、write_file、edit_file、list_directory、search_files_contentなどによる読み書きと探索 既定では無制限で、allow_listとdeny_listで到達範囲を絞る
シェル shell シェルコマンドの実行。呼び出しごとに新しい隔離されたシェルセッション 既定のタイムアウトは30秒で、--yoloを使わない限りユーザー確認が必要
スクリプト script 定義済みのシェルコマンドを、型付き引数を持つ名前付きツールとして公開 汎用のシェルより自由度が低く安全だとドキュメントは説明
MCP mcp Model Context Protocolサーバーのツールを接続 Docker MCP、ローカルstdio、リモートの3方式
推論と記憶 think、todo、memory READMEが組み込みのthink、todo、memoryツールを列挙 —
検索拡張 rag README：BM25、埋め込み、ハイブリッド検索、リランキングを差し込める構造 —

MCPツールのページは、接続方式を3つに分けている。

  • Docker MCP（推奨）： MCP Gatewayを通じてDockerコンテナとしてサーバーを実行し、ref: docker:duckduckgoのようにDocker MCPカタログの定義を参照する。
  • ローカルstdio： commandとargsでローカルプロセスを起動し、標準入出力で通信する。
  • リモート： remote.urlとtransport_type（streamableまたはsse）でネットワーク上のサーバーに接続する。OAuthフローは自動で処理されるとページは述べる。
  • ツールの絞り込みと自動インストール： toolsリストでモデルに公開するツールを絞れ、ローカルコマンドがPATHにない場合はaquaレジストリで探してインストールされる。DOCKER_AGENT_AUTO_INSTALL=falseで無効にできる。

OCIレジストリで共有するエージェント

配布のページは、エージェントをDocker HubやGitHub Container RegistryのようなOCI互換レジストリにプッシュし、どこからでもプルして実行できると説明する。ドキュメントのプッシュとプルの例は次のとおりである。

docker agent share push ./agent.yaml docker.io/username/my-agent:latest
                    docker agent share pull docker.io/username/my-agent:latest
  • 実行： READMEのクイックスタートは、docker agent run myorg/agent:tagでレジストリのエージェントをそのまま実行する形を示している。
  • 署名： share push --keyにより、プルする側が公開者と改ざんの有無を確認できる。このときYAML自体は常に平文でプッシュされ、証明だけがOCIマニフェストのアノテーションに入る。
  • 暗号化： --encryptを加えると、YAML全体の暗号化されたコピーもアノテーションに記録される。ドキュメントの例はEd25519鍵と対称な秘密値の2種類である。
  • 証明の形式： 署名はDSSEエンベロープに入れたin-toto Statement v1を対象とし、cosignやin-totoのツールが使う形式なのでDocker Agentなしでも読み取り・検証できるとドキュメントは述べる。
  • 外部サブエージェント： サブエージェントをローカルに定義せず、OCIレジストリのエージェントを参照できるとマルチエージェントのページは案内している。

URLやOCIレジストリから取得した設定には作者が選んだ既定値が含まれうるため、実行前に確認するよう権限のページは警告している。署名検証は整合性と出所の確認であり、設定内容が安全だという保証ではない。

権限と安全モード - 承認フローの構造

ツールのページは既定の動作を次のように記す。Docker Agentはシェルコマンドやファイル書き込みのような副作用のあるツールの実行前にユーザー確認を求め、--yoloを使うとすべてのツール呼び出しを自動承認する。権限のページはこれをさらに細かい構造として説明している。

  • 評価順序： 権限ルールはdeny、allow、askの順に評価される。denyが優先され、どのルールにも当たらない呼び出しはセッションの安全モードに回る。
  • 4つの安全モード： strictはすべての呼び出しを確認する。balancedは安全な呼び出しを黙って実行し、残りを確認する。restrictedは安全な呼び出しだけを実行し、残りは確認せずに拒否し、autonomousはすべてを実行する。
  • --yoloの位置づけ： ドキュメントはautonomousを旧--yolo動作と呼び、--yoloを別名として残る旧表記として扱う。モードは--safetyフラグで選ぶ。
  • コマンドの分類： シェルコマンドはsafe、destructive、unknownに分類される。lsやgit statusのような読み取りコマンドはsafe、rm -rfのようなコマンドはdestructive、それ以外はunknownである。
  • transfer_taskとハンドオフ： transfer_taskは常に自動承認され、handoffは自身のhandoffsリストにある対象にしか渡せない。
  • パス制限： filesystemツールはallow_listとdeny_listを設定しない限り無制限である。ドキュメントの例は、ホームディレクトリ配下の.sshと.awsをdeny_listに入れる形である。
  • サンドボックスモード： docker agent run --sandbox agent.yamlは、Docker SandboxesのVM内でエージェントを実行する。restrictedモードについて、ドキュメントは「defense in depth, not a security boundary」であり、本当の隔離にはサンドボックスモードを使うよう記している。
  • テレメトリ： READMEは、ツール改善のために匿名の利用データを収集すると述べ、テレメトリのページへ案内している。

「コード不要」の範囲とドキュメントが示す境界

「no code required」はREADMEの表現である。同じドキュメント群には、その範囲を測る手がかりになる項目がある。

  • scriptツール： 定義済みのシェルコマンドを、型付き引数を持つ名前付きツールとして公開する。コマンド自体は利用者が書く必要がある。
  • Go SDKガイド： Docker AgentをGoライブラリとして使い、アプリケーションにエージェントを組み込む方法を説明する別のガイドがある。
  • シェルツールの位置づけ： ドキュメントはシェルを最も強力なツールの1つと呼び、ビルド、依存関係のインストール、API照会、システムとのやり取りまでエージェントができると説明している。
  • 設定の幅： 設定リファレンスにはhooks、structured_output、cache、code_mode_toolsなどの項目があり、YAMLだけで届く機能の広さを示している。
  • 実行環境への依存： モデルへの接続には、プロバイダのAPIキー、アカウントログイン、Docker Model Runner、コーディングハーネスのいずれかが必要だとインストールのページは記している。

確認できなかったこと

  • プロジェクト名の変更履歴。ドキュメントのユーザー設定パスに~/.config/cagent/config.yamlが残っているが、改名の時期や経緯を記した文書は読んだ範囲になかった。
  • Linuxのパッケージマネージャ（aptやdnf）によるインストール経路。インストールのページはDocker Desktop、Homebrew、バイナリリリース、ソースビルドを案内している。
  • Docker Model Runner利用時のハードウェアアクセラレーション要件。
  • OCIアーティファクトのレイヤー構造とメディアタイプの詳細仕様。
  • 複数のエージェントを同時に実行するときにCPUやメモリを制限する設定フィールドの有無。設定リファレンスの一覧にbudgetの項目があるが、内容は読んでいない。
  • 性能やコストに関する数値。READMEと読んだ文書には該当する数値がない。
