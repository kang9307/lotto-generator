引言 - 失败由三处分别判定

PowerShell脚本失败时，调用方(任务计划程序、CI运行器或其他脚本)拿到的只有一个值，即进程退出码。但在这个值确定之前，PowerShell内部有三本判定账簿。第一本是异常，也就是terminating错误与try/catch。第二本是保存上一条命令是否成功的$?。第三本是保存最后运行的原生程序退出码的$LASTEXITCODE。三本账簿之间不会自动联动，某一本记下了失败，并不意味着另外两本也会记下。

先说明几个术语。cmdlet是像Get-Item这样以.NET类实现的PowerShell命令；原生命令是像cmd.exe、git.exe这样作为独立进程运行并返回整数退出码的外部可执行文件；ErrorRecord是PowerShell为每个错误创建的对象，包含异常、错误类别、目标对象和脚本位置。失败是作为异常抛出，还是仅写入错误流，决定了本文观察到的所有差异。

在bash中，set -e和$?就能解释大部分行为。PowerShell则是在基于对象的错误模型之上，另外叠加了原生程序的整数退出码，所以同一个「失败」在不同账簿里看起来不同。bash一侧errexit与pipefail的盲区，已有文章Shell 退出码与 set -e - 它抓住什么又漏掉什么用运行输出整理过，因此本文只限于PowerShell。

terminating错误与non-terminating错误 - try/catch看到的是什么

Microsoft Learn的about_Try_Catch_Finally这样界定try/catch处理的对象：PowerShell的terminating错误有两种，一种是中止当前语句的statement-terminating错误，另一种是展开整个调用栈的script-terminating错误，两者都能被try/catch捕获。不在其中的就是non-terminating错误，即cmdlet把错误写入错误流后继续处理下一个项目。文档在$ErrorActionPreference一节中把这种默认行为写作Continue(显示错误信息并继续执行)。

用来验证界线的第一段代码，是对不存在的路径使用Get-Item。

try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
Get-Item : Cannot find path 'C:\demo\nope.txt' because it does not exist.
                    At C:\demo\e1.ps1:3 char:7
                    + try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught:  ...
                    +       ~~~~~~~~~~~~~~~~~~~~~~~~~
                        + CategoryInfo          : ObjectNotFound: (C:\demo\nope.txt:String) [Get-Item], ItemNotFoundException
                        + FullyQualifiedErrorId : PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
                    
                    after Get-Item

错误信息显示在屏幕上，但catch块没有执行，try里的下一条语句'after Get-Item'照常执行了。原因正如上面的定义：Get-Item把这个错误作为non-terminating写出并继续处理，所以没有异常发生。给同一段代码加上-ErrorAction Stop，结果就变了。

try { Get-Item C:\demo\nope.txt -ErrorAction Stop; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
caught: ItemNotFoundException

这次catch执行了，'after Get-Item'没有输出。文档说明，把$ErrorActionPreference设为Stop会把non-terminating错误升级为script-terminating错误，而-ErrorAction公共参数会针对单个命令覆盖该设置。下表是在同一个脚本中，把几种不同形式的失败放入try/catch后的结果。

try中的代码catch是否执行catch中$_.Exception的类型try中的下一条语句
Get-Item C:\demo\nope.txt否—执行
Get-Item C:\demo\nope.txt -ErrorAction Stop是ItemNotFoundException不执行
$ErrorActionPreference = 'Stop'之后的Get-Item C:\demo\nope.txt是ItemNotFoundException不执行
1/0是RuntimeException不执行
NonsenseString(不存在的命令)是CommandNotFoundException不执行
[int]'abc'(类型转换失败)是RuntimeException不执行
Write-Error 'from Write-Error'否—执行
throw 'from throw'是(消息为from throw)不执行

从表中可以读出的规则如下。

  • cmdlet自己写入错误流的错误(Get-Item的路径不存在、Write-Error)，在默认设置下不会到达catch。
  • 由语言直接引发的错误(除以零、类型转换失败、不存在的命令、throw)属于异常，总会进入catch。
  • 同一个cmdlet的同一个失败，只需一个-ErrorAction Stop就成为catch的对象。想作用于整个脚本，就使用$ErrorActionPreference = 'Stop'。
  • catch中的$_是ErrorRecord，可以用$_.Exception的类型区分错误种类。文档写明PowerShell会把所有异常包装为RuntimeException。

$ErrorActionPreference的作用范围与-ErrorAction

about_Preference_Variables把SilentlyContinue、Stop、Continue(默认)、Inquire、Ignore列为$ErrorActionPreference的取值，并写明修改只在其所在范围及子范围内生效。下面的代码用实际运行验证了范围。

'start: ' + $ErrorActionPreference
                    function Inner { 'inner sees: ' + $ErrorActionPreference }
                    function SetsStop { $ErrorActionPreference = 'Stop'; 'in SetsStop: ' + $ErrorActionPreference; Inner }
                    SetsStop
                    'after SetsStop: ' + $ErrorActionPreference
start: Continue
                    in SetsStop: Stop
                    inner sees: Stop
                    after SetsStop: Continue

在函数内部改成Stop的值，对该函数调用的函数(Inner)可见；函数结束回到调用方后，又恢复为原来的Continue。反方向也一样：调用方设为$ErrorActionPreference = 'SilentlyContinue'后调用Inner，输出的是inner sees: SilentlyContinue。也就是说，这个变量沿调用链向下继承，不会向上泄漏。

两种设置冲突时，以命令级的-ErrorAction为准。

$ErrorActionPreference = 'Stop'
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    'survived: ' + $?
survived: False

虽然全局设置是Stop，脚本仍然运行到了下一行，也没有输出错误信息。不过$?是False。隐藏错误，并不等于失败没有发生。

SilentlyContinue与Ignore都会隐藏信息，但在是否记入$Error上不同。文档写明Ignore不会向$Error添加错误。

$Error.Clear()
                    Get-Item C:\demo\a.txt -ErrorAction SilentlyContinue
                    'after SilentlyContinue, $Error.Count = ' + $Error.Count
                    Get-Item C:\demo\b.txt -ErrorAction Ignore
                    'after Ignore, $Error.Count = ' + $Error.Count
after SilentlyContinue, $Error.Count = 1
                    after Ignore, $Error.Count = 1

SilentlyContinue之后积累了1条，Ignore之后仍然是1条。Ignore连记录都不留，所以事后通过$Error回溯的线索就没有了。

文档也把Ignore列为$ErrorActionPreference的取值，但在5.1上，Ignore只能用作cmdlet的-ErrorAction参数的值。把它赋给变量本身不会报错，而在这种状态下一旦发生错误，就会抛出NotSupportedException。

$ErrorActionPreference = 'Ignore'
                    'preference set to: ' + $ErrorActionPreference
                    Get-Date | Out-Null
                    'after Get-Date, preference: ' + $ErrorActionPreference
                    try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().FullName; $_.Exception.Message }
                    'preference now: ' + $ErrorActionPreference
preference set to: Ignore
                    after Get-Date, preference: Ignore
                    caught: System.NotSupportedException
                    The value Ignore is not supported for an ActionPreference variable. The provided value should be used only as a value for a preference parameter, and has been replaced by the default value. For more information, see the Help topic, "about_Preference_Variables."
                    preference now: Continue

不产生错误的Get-Date正常运行，变量仍是Ignore。但Get-Item产生错误时，进入catch的是NotSupportedException，原本的ItemNotFoundException没有到达catch。消息说明，Ignore不能用作首选项变量的值，只能用作首选项参数的值，且提供的值已被替换为默认值。事实上，最后一行时变量已回到Continue。总之，在5.1上Ignore只能像-ErrorAction Ignore这样用在参数上；把变量设为Ignore，第一次出错时就会变成这个异常。这一行为是在5.1上运行得到的结果，没有在7上运行。

由这一节的结果可以得出简单的取舍：对确实可以忽略错误的某一条命令，加上-ErrorAction SilentlyContinue并保留记录；Ignore不会写入$Error，因此不要用在日后可能需要追查原因的处理上；脚本整体的默认值设为Stop，只在不希望变成异常的地方按命令覆盖，这种结构与到目前为止的运行结果并不矛盾。

about_Try_Catch_Finally的Note还提示了另一个行为：当$ErrorActionPreference为SilentlyContinue或Ignore时，连throw也不会传播，而是继续执行下一条语句。这句是文档的原话，下面的运行只使用了SilentlyContinue。Ignore如上所见无法放进变量，所以未能确认。

$ErrorActionPreference = 'SilentlyContinue'
                    throw 'boom'
                    'line after throw ran'
line after throw ran

消息boom没有输出，下一行被执行了。就SilentlyContinue而言，结果与文档的说明一致。如果习惯性地把这个设置放在脚本开头，用throw设置的中断点也会随之消失。

使用Stop之后$Error里留下什么，也做了运行观察。

$Error.Clear()
                    try { Get-Item C:\demo\nope.txt -ErrorAction Stop } catch { }
                    $Error.Count
                    $Error[0].GetType().FullName
                    $Error[0].Exception.GetType().FullName
1
                    System.Management.Automation.ErrorRecord
                    System.Management.Automation.ItemNotFoundException

官方文档写道，Stop除了原始错误之外，还会向错误流输出一个ActionPreferenceStopException对象。这次运行中$Error里有1条，其异常类型是ItemNotFoundException。两种说法之间的关系，仅凭这次运行不做解释。

$?与$LASTEXITCODE - 原生命令的失败不是异常

about_Automatic_Variables把$?定义为上一条命令的执行状态(成功为True，失败为False)，把$LASTEXITCODE定义为最后运行的原生程序或脚本的退出码。对于原生命令，文档接着写道：$LASTEXITCODE为0时$?为True，为其他值时为False。原生命令失败时三本账簿的情况，用运行观察如下。

cmd /c exit 3
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = False
                    $LASTEXITCODE = 3

失败记入了$?和$LASTEXITCODE。那么异常账簿呢？把$ErrorActionPreference设为Stop，在try中运行同一条命令。

$ErrorActionPreference = 'Stop'
                    try { cmd /c exit 3; 'next line ran' } catch { 'caught' }
next line ran

catch没有执行，下一条语句执行了。原生程序的非零退出码是值，不是错误。PowerShell不会替你中止，所以即使在启用了Stop的脚本里，原生调用的失败也必须亲自读取$LASTEXITCODE才能知道。如果运行一个不存在的程序名(nosuchprogram.exe)，情况则不同。这时是PowerShell找不到该命令，所以try中捕获到了CommandNotFoundException。程序启动后的失败，与连启动都没做到的失败，属于不同的账簿。

两个变量的寿命也不同。下面的代码是在原生调用之后又运行了cmdlet的情形。

cmd /c exit 3
                    Get-Date | Out-Null
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = True
                    $LASTEXITCODE = 3
                    $? = False
                    $LASTEXITCODE = 3

无论是成功的cmdlet之后，还是失败的cmdlet之后，$LASTEXITCODE都保持为3。这个变量只在运行原生程序或脚本时更新，所以有可能把几行之前留下的值误读成当前调用的结果。$?则相反，寿命只有一条语句。

Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    $ok = $?
                    '$? read once = ' + $ok
                    '$? read again (after the assignment) = ' + $?
$? read once = False
                    $? read again (after the assignment) = True

赋值$ok = $?本身就是一条成功的命令，所以再次读取$?得到True。需要判断时，应在失败命令的紧接着的下一条语句里把值转存到变量。在函数内部还多一层：文档说Write-Error在执行后立刻把$?设为False，但不会把调用该函数的一侧的$?设为False，实际运行也是如此。

function T { Write-Error 'bad' -ErrorAction SilentlyContinue; 'inside: ' + $? }
                    T
                    'outside: ' + $?
inside: False
                    outside: True

用2>&1把原生命令的stderr合并进错误流，会影响到异常账簿。同一条命令在有无重定向时，在Stop下的表现不同。下面的cmd /c向stdout写一行，向stderr写一行，并以退出码2结束。

$ErrorActionPreference = 'Stop'
                    try {
                      $out = cmd /c "echo to-stdout & echo to-stderr 1>&2 & exit 2" 2>&1
                      'no exception; lines captured: ' + @($out).Count
                    } catch {
                      'caught: ' + $_.Exception.GetType().Name + ' / ' + $_.FullyQualifiedErrorId
                    }
caught: RemoteException / NativeCommandError

一合并stderr，stderr的那一行就变成了ErrorRecord，并在Stop下升级为异常。但仅凭这一例，分不清异常是由stderr还是由退出码2引起的。于是设置对照组，每次只改变一个变量，在同样的Stop设置下运行了四种情形。

$ErrorActionPreference = 'Stop'
                    '1) stderr text, exit 2, with 2>&1'
                    $LASTEXITCODE = $null
                    try { $out = cmd /c "echo to-stdout & echo to-stderr 1>&2 & exit 2" 2>&1; 'no exception' } catch { 'caught: ' + $_.FullyQualifiedErrorId }
                    '   $LASTEXITCODE = ' + $LASTEXITCODE
                    '2) stderr text, exit 0, with 2>&1'
                    $LASTEXITCODE = $null
                    try { $out = cmd /c "echo to-stderr 1>&2 & exit 0" 2>&1; 'no exception' } catch { 'caught: ' + $_.FullyQualifiedErrorId }
                    '   $LASTEXITCODE = ' + $LASTEXITCODE
                    '3) no stderr text, exit 2, with 2>&1'
                    $LASTEXITCODE = $null
                    try { $out = cmd /c "echo to-stdout & exit 2" 2>&1; 'no exception' } catch { 'caught: ' + $_.FullyQualifiedErrorId }
                    '   $LASTEXITCODE = ' + $LASTEXITCODE
                    '4) the command of 1), 2>&1 removed'
                    $LASTEXITCODE = $null
                    try { cmd /c "echo to-stdout & echo to-stderr 1>&2 & exit 2"; 'no exception' } catch { 'caught: ' + $_.FullyQualifiedErrorId }
                    '   $LASTEXITCODE = ' + $LASTEXITCODE

退出码为0但合并了stderr的第2种情形出现了异常，退出码为2但没有stderr行的第3种没有异常。把第1种命令中的2>&1去掉的第4种，退出码同样是2，stderr行也相同，却没有异常。结合前面cmd /c exit 3仅凭退出码不产生异常的结果，在这四种组合中，是否出现异常只与stderr行是否经2>&1变成了错误流中的ErrorRecord相关联，而与退出码无关。这个行为是在5.1上运行这四种组合得到的结果，没有测试2>$null等其他重定向。因此，检测原生调用的失败，不要依赖重定向与否或Stop设置，在调用之后立即写出检查$LASTEXITCODE的代码最为可靠。

exit与return - 决定进程退出码的是什么

进程退出码按调用方式遵循不同的规则。about_PowerShell_exe写道：对于-File，脚本以exit结束时，该数字就是进程退出码，发生script-terminating错误时为1。对于-Command，最后一条命令的$?为True时是0，为False时是1，如果最后一条命令是设置了0和1之外退出码的外部程序或脚本，该退出码会被转换为1。下表是用两种方式调用同一个脚本、在父PowerShell中读取$LASTEXITCODE的结果，每个脚本都只有一行。

脚本内容-File的退出码-Command "& 脚本"的退出码从输出中读到的内容
'script body ran'00正常完成
'before'; throw 'boom'; 'after'11before之后中断，没有after
'before'; Write-Error 'bad'; 'after'00执行到after，输出错误信息
'before'; exit 5; 'after'51没有after
'before'; return 5; 'after'00数字5作为输出出现，没有after
cmd /c exit 3; 'done'00输出了done
'first'; cmd /c exit 300最后一行失败也是0
cmd /c exit 3; if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }; 'done'31没有done
$ErrorActionPreference='Stop'; cmd /c exit 3; 'done'00虽然是Stop，仍输出了done
try { 'in try'; exit 4 } finally { 'in finally' }41输出了in finally
function F { exit 7 }; 'before'; F; 'after'71函数内的exit结束整体，没有after
function F { return 7 }; 'before'; F; 'after'007作为输出出现，after也被执行
try { throw 'x' } catch { 'handled'; exit 2 }21输出了handled
try { throw 'x' } catch { 'handled' }00捕获后吞掉就算成功
'ok'; if ( {(语法错误)11连第一行的ok也没有输出

对表中原因明确的项目，逐条解释如下。

  • exit 5在-File下原样得到5，在-Command "& 脚本"下被转换为1。这与文档所写的「0和1以外的退出码转换为1」一致。
  • return 5是输出而不是退出码。在脚本最上层，return只是结束脚本，值进入输出流，所以进程退出码是0。函数内的return 7同样因此把7显示在屏幕上。
  • 函数内的exit 7结束的不是函数，而是整个进程。调用方一侧没有输出after。
  • 即使脚本最后一行是原生失败(cmd /c exit 3)，-File也返回0。这与文档所写的「脚本正常完成则为0」一致，要传递这个值就需要exit $LASTEXITCODE。
  • 在try { exit 4 } finally { ... }中，finally被执行了。about_Try_Catch_Finally对catch内exit写下的那句话，在try内的exit上也得到了同方向的结果。
  • $ErrorActionPreference = 'Stop'同样没能拦住原生退出码3，done被输出了。与上一节的结果相同。
  • 含语法错误的脚本连第一行也不会执行，退出码为1。文档写道解析错误不影响$?，但这属于脚本执行之前阶段的失败，所以进程退出码得到了1。

throw 'x'1script-terminating错误
exit 55exit的值
& C:\demo\x_exit5.ps11脚本的exit 5被转换为1
& C:\demo\x_exit5.ps1; exit $LASTEXITCODE5通过$LASTEXITCODE保留了值
& C:\demo\x_native3.ps10脚本本身正常完成

第二张表的结论一句话就能说完：-Command只看最后一条命令是否成功，所以中途的失败会被其后的一条成功命令抹掉。对于调用方需要具体退出码或需要知道中途失败的自动化，-File更安全；如果必须使用-Command，就在字符串末尾加上exit $LASTEXITCODE。这也是文档给出的方法。

管道中途发生的错误

about_Pipelines说明，管道把对象逐个送给下一个命令。因此，中间阶段的错误不会影响已经通过的项目，问题就变成后面的项目是否继续流动。在脚本块里除以零的情形，用三种方式运行了。

1,2,0,4 | ForEach-Object { 10 / $_ }
10
                    5
                    Attempted to divide by zero.
                    At C:\demo\e4.ps1:2 char:28
                    + 1,2,0,4 | ForEach-Object { 10 / $_ }
                    +                            ~~~~~~~
                        + CategoryInfo          : NotSpecified: (:) [], RuntimeException
                        + FullyQualifiedErrorId : RuntimeException
                    
                    2.5

0这个项目出了错，但项目4仍被处理，输出了2.5。错误只中止了该项目的那一条语句，管道继续流动。把同一个管道用try/catch包起来就不同了。

try { 1,2,0,4 | ForEach-Object { 10 / $_ } } catch { 'caught: ' + $_.Exception.Message }
10
                    5
                    caught: Attempted to divide by zero.

2.5没有输出。catch收到错误的瞬间，整个管道就被中止了。在$ErrorActionPreference = 'Stop'下结果相同，脚本块内的throw(在项目3处抛出的情形)也是在item 1、item 2之后以caught: three结束。所以对于「出错也处理其余项目，只收集失败」这类设计，不能把try/catch放在管道外面，而要在项目处理块内部逐项捕获。

由此可见，「跳过失败项继续」还是「在此整体停止」，取决于错误种类与try/catch位置的组合。把try/catch放在循环或ForEach-Object内侧就是按项目处理，放在外侧则第一个错误就会让整体停止。设计批处理时，应先决定想要哪种含义，再选择try/catch的位置。

当一个cmdlet接收多个输入时，non-terminating错误会混在结果里输出。一次把四个路径(其中两个是不存在的文件)传给Get-Item，用2>&1把结果接到变量里并统计类型。

$r = Get-Item C:\demo\e1.ps1, C:\demo\nope1.txt, C:\demo\e2.ps1, C:\demo\nope2.txt 2>&1
                    $r | ForEach-Object { $_.GetType().Name }
FileInfo
                    ErrorRecord
                    FileInfo
                    ErrorRecord

成功的对象与ErrorRecord按输入顺序交错输出。这意味着失败的项目没有妨碍其后项目的处理。不了解这种结构，看到结果变量里混有错误对象就会感到意外。

在管道结束后读取$?，可以看出按阶段不同的行为。

Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue | ForEach-Object { 'x' }
                    '$? = ' + $?
                    Get-Date | ForEach-Object { Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue }
                    '$? = ' + $?
$? = False
                    $? = True

第一阶段的cmdlet写入了错误的管道，即使最后一个阶段成功，$?也是False。相反，最后一个阶段的脚本块内部发生的失败没有反映到$?上。文档把$?定义为「最后一条命令」的状态，这一点与第二个结果吻合，但第一个结果仅凭这个定义无法解释。无论如何，管道之后的$?都很难作为失败检测手段信赖。按阶段的失败，用-ErrorVariable或$Error收集更好。

Write-Error与throw - 是否中断流程

这两个命令名字相近，但在错误模型中站在相反的两侧。把前面的运行结果合并成一张表。

观察项目Write-Errorthrow
错误的种类non-terminating(记录到错误流)script-terminating
下一条语句是否执行执行(输出after)不执行
默认设置下的try/catch抓不到抓得到
-File脚本的退出码01
设为$ErrorActionPreference = SilentlyContinue之后信息被隐藏，但仍记入$Error不传播，下一条语句执行
生成的异常类型WriteErrorException字符串throw为RuntimeException

在同一个脚本中各用一行运行这两个命令得到的输出，就是上表的依据。

try { Write-Error 'from Write-Error'; 'after Write-Error' } catch { 'caught: ' + $_.Exception.Message }
                    try { throw 'from throw'; 'after throw' } catch { 'caught: ' + $_.Exception.Message }
C:\demo\e1.ps1 : from Write-Error
                        + CategoryInfo          : NotSpecified: (:) [Write-Error], WriteErrorException
                        + FullyQualifiedErrorId : Microsoft.PowerShell.Commands.WriteErrorException,e1.ps1
                    
                    after Write-Error
                    caught: from throw

继续追到退出码，差距更大。用-File运行'before'; Write-Error 'bad'; 'after'，会依次输出before、错误信息和after，退出码是0。'before'; throw 'boom'; 'after'在before之后输出错误，没有after，退出码是1。如果脚本必须把失败告知调用方，只写一行Write-Error是不够的：日志里会出现错误，任务计划程序却会视为成功。

通过Write-Error的参数可以指定错误分类。下面的代码指定了类别和标识符，然后读取$Error[0]。

Write-Error -Message 'with category' -Category InvalidArgument -ErrorId 'My.Id' -ErrorAction SilentlyContinue
                    $Error[0].CategoryInfo.Category.ToString() + ' / ' + $Error[0].FullyQualifiedErrorId
InvalidArgument / My.Id,e7.ps1

throw除字符串外也可以抛出异常对象，catch可以按类型分流。抛出字符串时会被包装成RuntimeException。

try { throw [System.IO.FileNotFoundException]::new('typed') } catch [System.IO.FileNotFoundException] { 'typed catch: ' + $_.Exception.Message }
                    try { throw 'plain string' } catch { $_.Exception.GetType().FullName + ' / ' + $_.CategoryInfo.Category }
typed catch: typed
                    System.Management.Automation.RuntimeException / OperationStopped

总之，Write-Error的意思是「这个项目失败了，但继续」，throw的意思是「在这里停下」。按项目报告失败的库式函数用前者，前提已经破坏、无法再继续时用后者。

$Error集合 - 会积累什么

about_Automatic_Variables把$Error描述为最近错误对象的数组，最新的是$Error[0]。about_Preference_Variables的默认值表给出$MaximumErrorCount为256。连续引发两个错误后读取的结果如下。

$Error.Clear()
                    Get-Item C:\demo\first.txt -ErrorAction SilentlyContinue
                    Get-Item C:\demo\second.txt -ErrorAction SilentlyContinue
                    'count: ' + $Error.Count
                    '$Error[0] : ' + $Error[0].Exception.Message
                    '$Error[1] : ' + $Error[1].Exception.Message
count: 2
                    $Error[0] : Cannot find path 'C:\demo\second.txt' because it does not exist.
                    $Error[1] : Cannot find path 'C:\demo\first.txt' because it does not exist.

后发生的错误在索引0，之前的错误被往后推。单个ErrorRecord所含的属性，也用运行读取了。这段代码接在上一个代码块之后、在同一个脚本中运行，所以ScriptLineNumber是第二个Get-Item所在的第3行。

$e = $Error[0]
                    $e.GetType().FullName
                    'Exception          : ' + $e.Exception.GetType().FullName
                    'CategoryInfo       : ' + $e.CategoryInfo
                    'FullyQualifiedId   : ' + $e.FullyQualifiedErrorId
                    'TargetObject       : ' + $e.TargetObject
                    'ScriptLineNumber   : ' + $e.InvocationInfo.ScriptLineNumber
System.Management.Automation.ErrorRecord
                    Exception          : System.Management.Automation.ItemNotFoundException
                    CategoryInfo       : ObjectNotFound: (C:\demo\second.txt:String) [Get-Item], ItemNotFoundException
                    FullyQualifiedId   : PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
                    TargetObject       : C:\demo\second.txt

这些属性在$_(catch内)和$Error[0]中都能以相同名称读取。通知信息中同时写入FullyQualifiedErrorId和ScriptLineNumber，可以加快追查原因。

被捕获的错误也会进入$Error。文档写道try块中发生错误时会先保存到$Error，实际运行中，执行try { throw 'caught-me' } catch { ... }之后，$Error.Count也是1。不过，用ReferenceEquals比较catch内的$_与$Error[0]，得到的是False。两者指的是同一个错误，但是否为同一个对象引用没有得到确认。

$Error.Clear()
                    try { throw 'caught-me' } catch { 'in catch: $_ is $Error[0] -> ' + [object]::ReferenceEquals($_, $Error[0]) }
                    'count: ' + $Error.Count
in catch: $_ is $Error[0] -> False
                    count: 1

-ErrorVariable是把错误收集到指定变量的公共参数，在这次运行中它同时也记录到了$Error。

$Error.Clear()
                    Get-Item C:\demo\third.txt -ErrorAction SilentlyContinue -ErrorVariable ev
                    'ev.Count: ' + $ev.Count + ' / $Error.Count: ' + $Error.Count
                    Get-Item C:\demo\fourth.txt -ErrorAction SilentlyContinue -ErrorVariable +ev
                    'ev.Count: ' + $ev.Count
ev.Count: 1 / $Error.Count: 1
                    ev.Count: 2

第一行是用-ErrorVariable ev失败一次之后的值，第二行是用-ErrorVariable +ev(前面带+)再失败一次并累积之后的$ev.Count。没有+时变量每次都会被覆盖。实际工作中，可以在脚本开头调用一次$Error.Clear()，在退出前用$Error.Count和$Error | Select-Object -First 5检查是否有被吞掉的错误。前面一节的SilentlyContinue会被这种检查发现，Ignore则不会。

与bash的对应 - 对应set -e的与不对应的

熟悉bash的人写PowerShell脚本时，最先问的是「set -e在哪里」。根据上面的运行结果，简要整理对应关系。完整的命令对照是另一篇文章的内容，这里只限于错误和退出码。

bashPowerShell 5.1经运行确认的差异
set -e$ErrorActionPreference = 'Stop'只把cmdlet错误升级为异常。原生退出码3在Stop下也没有被拦住
$?(上一条命令状态的整数)$?(True/False)与$LASTEXITCODE(整数)值分成了两个。$LASTEXITCODE不会因运行cmdlet而更新
cmd || exit $?if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }用这种形式，在-File下传递了退出码3
trap ... EXITtry/finally即使在exit时finally也被执行(退出码4)
exit Nexit N即使在函数内使用，也会结束整个进程。return N是输出而不是退出码
传递脚本的结束状态使用-File，或在-Command字符串末尾加exit $LASTEXITCODE-Command会转换为0或1，不适合传递值

这张表里没有pipefail一行。管道各阶段的状态，如第6节所见，随阶段种类不同而对$?有不同的反映。bash的set -e例外规则与pipefail的细节，由bash那篇文章介绍。

实战模式 - 原生调用包装函数与退出码传递

把上面运行得到的规则合并成一个脚本，如下所示。开头启用Stop，把cmdlet错误变成异常；原生调用交给包装函数检查$LASTEXITCODE并转为throw；在catch中用exit确定调用方要读取的退出码；在finally中做收尾。

$ErrorActionPreference = 'Stop'
                    function Invoke-Native {
                        param([scriptblock]$Command)
                        & $Command
                        if ($LASTEXITCODE -ne 0) { throw ('native command failed with exit code ' + $LASTEXITCODE) }
                    }
                    try {
                        'step 1'
                        Invoke-Native { cmd /c exit 0 }
                        'step 2'
                        Invoke-Native { cmd /c exit 3 }
                        'step 3 (not reached)'
                    }
                    catch {
                        'ERROR: ' + $_.Exception.Message
                        exit 3
                    }
                    finally {
                        'cleanup runs'
                    }

这是用powershell.exe -NoProfile -File运行该脚本，并在父进程中读取$LASTEXITCODE的结果。

exit code = 3
                    step 1
                    step 2
                    ERROR: native command failed with exit code 3
                    cleanup runs

第三步没有执行，exit 3之后finally的收尾仍被执行，进程退出码是3。这个模式所依赖的事实，全都是前面各节运行观察到的。

  • 原生失败不是异常，所以由包装函数升级为throw(第4节)。
  • 即使有exit，finally也会执行(第5节)。
  • -File会把exit的值原样返回(第5节)。

使用这个模式时的检查项目如下。

  • 脚本开头的$ErrorActionPreference是否为预期的值？设为SilentlyContinue时，连throw也会被吞掉。
  • 是否在原生调用之后立即读取$LASTEXITCODE？几行之后的值可能属于更早的调用。
  • 如果调用方用-Command调用，字符串末尾是否有exit $LASTEXITCODE？
  • 没有经过包装函数、用2>&1合并了stderr的原生调用，在Stop下是否会变成异常？
  • 退出前是否检查$Error.Count，排查被SilentlyContinue而不是Ignore吞掉的错误？

未能确认的内容

  • 文档Note中关于$ErrorActionPreference为Ignore时throw不会传播的部分。在5.1上，把变量设为Ignore后，出错的地方会变成NotSupportedException，因此无法复现，确认过的只有SilentlyContinue。
  • PowerShell 7(pwsh)的行为。这台电脑上没有安装pwsh，无法通过运行比较与5.1的差异。官方文档在5.1页面中说明的只有：用括号(...)、$(...)、@(...)包裹的语句，在PowerShell 7之前总会把$?重置为True，7中已改变；以及-File无法给开关参数传递显式Boolean值的限制，在PowerShell 6(pwsh.exe)中已移除。
  • 5.1中对应bashpipefail的设置。在查阅的五份官方文档中没有找到。
  • 文档所说Stop会输出的ActionPreferenceStopException，出现在错误流的什么位置。这次运行中$Error里只有1条。
  • cmd.exe、任务计划程序和CI运行器如何接收这些退出码。本文只在父PowerShell中通过$LASTEXITCODE读取。
  • 用Ctrl+C中断时的退出码。文档写-File为0、-Command为1，但交互式中断难以自动执行，所以没有运行。
  • 脚本模块与二进制模块中的cmdlet对$ErrorActionPreference的继承，以及远程执行(Invoke-Command)和后台作业中的错误传播。
  • 从未运行过原生程序的会话中$LASTEXITCODE的初始值，以及其他Windows版本上的结果。
  • 即使同为5.1，不同宿主(控制台、ISE、VS Code集成终端)的错误显示格式是否不同。
