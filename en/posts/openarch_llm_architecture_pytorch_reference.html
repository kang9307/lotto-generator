Dissecting Llama, Qwen, and DeepSeek One File at a Time - OpenArch

Unveiling the structural diversity of modern large language models through clean, single-file PyTorch implementations built for direct code comparison

2026-09-15 Dev & Infra

Seeing the Real Face of Architecture, Buried in Production Code

Machine learning engineers, researchers, and systems practitioners frequently encounter a familiar cognitive barrier whenever a groundbreaking foundational language model is announced. Naturally, the first impulse is to inspect the official repository or review the Hugging Face transformers implementation to examine how the mathematical formulations translate into actual tensor transformations. However, what greets the reader is rarely a clean, uncluttered neural network definition. Instead, modern production codebases are dense labyrinths of distributed execution primitives, tensor parallelism hooks, specialized flash attention dispatchers, memory offloading shims, activation quantization wrappers, and elaborate conditional branches designed to maintain backward compatibility across multiple legacy checkpoint revisions.

The existence of these optimization layers is entirely justified in production environments. Modern enterprise serving frameworks must maximize hardware utilization across thousands of interconnected GPUs, handle heterogenous accelerator configurations, and provide absolute operational reliability under massive traffic. Nevertheless, this necessary production machinery creates immense cognitive friction for anyone seeking to understand the core architectural differences distinguishing contemporary architectures. When the underlying decoder skeleton is broadly shared across modern autoregressive transformers, understanding why Llama selected grouped-query attention, how Qwen strategically positioned its normalization layers, or how DeepSeek seamlessly interwoven multi-head latent compression with fine-grained mixture of experts becomes needlessly difficult.

This critical educational bottleneck motivated the creation of OpenArch, an open-source project maintained by anuj0456. OpenArch deliberately sets aside any competition with production-grade runtime frameworks, dedicating itself exclusively to 「clarity and learning」. By implementing each major open-source LLM architecture in a single, completely self-contained, and readable PyTorch file, OpenArch strips away the obfuscating plumbing of distributed computing and exposes the authentic architectural trade-offs directly in executable code. It offers developers an unprecedented environment for side-by-side inspection of modern model mechanics.

OpenArch's Design Philosophy and Repository Structure

At the center of OpenArch lies a strict philosophy of single-file completeness. Standard machine learning codebases typically decompose their logic across deep object-oriented class hierarchies, splitting tensor operations into shared utility modules, generic attention interfaces, configuration dataclasses, and abstract transformer blocks. While this adheres to classical software engineering principles of modularity and code reuse, it forces the reader to jump constantly across dozens of source files, rapidly destroying contextual comprehension. In contrast, OpenArch confines the entire forward execution path of each model architecture within a single model.py script.

The project draws its primary inspiration and organizational taxonomy from Sebastian Raschka's celebrated [LLM Architecture Gallery](https://sebastianraschka.com/llm-architecture-gallery/). As documented by the author, each model was manually reconstructed from original academic papers, technical reports released by model creators, reference config.json parameters, and supplementary analytical breakdowns by Sebastian Raschka and Machine Learning Mastery. The physical directory structure of the repository reflects this methodical curation, organizing architectures into clear text and multimodal divisions.

Inside every individual model subfolder resides a self-contained model.py capable of performing a forward pass, accompanied by a concise README.md that details the exact normalization choices, attention mechanisms, positional encodings, and feed-forward architectures implemented. Because the codebase deliberately eschews convoluted external dependencies in favor of standard PyTorch tensor manipulations, the setup environment is remarkably lightweight and instantly reproducible across ordinary workstations.

According to the project documentation, OpenArch maintains the following foundational principles:

  • It does not compete with production libraries on raw throughput, inference latency, or sharded deployment.
  • It makes structural choices (attention type, normalization placement, layer mix, MoE routing, positional encodings) totally explicit in code.
  • It enables readers to trace tensor shape transformations seamlessly from initial token embeddings to final logit projections within one file.
  • It verifies architectural correctness via executable forward passes without requiring heavy multi-node distributed initialization.

Design Choice 1 — The Divergence and Evolution of Attention Mechanisms

While virtually all modern foundational models share the overarching structure of an autoregressive transformer decoder, their internal attention mechanisms have diverged significantly over successive generations. The attention block constitutes the primary computational and memory bottleneck during generative sequence decoding. OpenArch highlights this developmental arc by placing generational implementations alongside one another, allowing engineers to witness how algorithmic shifts directly address hardware constraints.

From MHA (Multi-Head Attention) to GQA (Grouped-Query Attention)

Early foundational architectures such as the standard Transformer, GPT-2 XL, and initial open releases like Llama 2 (7B) and OLMo 2 (7B) relied strictly on conventional Multi-Head Attention (MHA). In an MHA configuration, the number of query heads matches the number of key and value heads exactly. While this maximizes expressive capacity across parallel attention subspaces, it inflicts severe memory penalties during autoregressive text generation. Storing the key-value (KV) cache for every individual head across extensive context lengths and large serving batches rapidly exhausts high-bandwidth GPU memory.

Contemporary architectures, exemplified by Llama 3 (8B), resolved this bottleneck by transitioning universally to Grouped-Query Attention (GQA). In GQA, multiple query heads share a significantly smaller number of key and value head pairs. This architectural trade-off drastically reduces KV cache memory consumption with virtually negligible impact on generation quality and downstream benchmark performance. By inspecting the Llama 2 and Llama 3 model.py files in OpenArch side-by-side, readers can observe that this transformative operational gain boils down to just a few lines of tensor repeating and broadcasting code inside the attention forward method.

MLA (Multi-Head Latent Attention) and Sliding-Window Attention

Pushing inference efficiency even further, flagship reasoning and long-context architectures such as DeepSeek R1 and Kimi K2 introduced Multi-Head Latent Attention (MLA). Rather than caching full-dimensional key and value projections, MLA projects keys and values into a dramatically compressed low-dimensional latent space before writing them to memory. During query computation, these compressed representations are decompressed or computed in latent form, breaking through the memory-bandwidth wall that historically limited multi-turn long-context serving.

In parallel, models like Gemma 3 and GPT-OSS leverage hybrid attention schedules, alternating between localized sliding-window attention and global attention layers. Restricting token attention to a constrained local receptive window eliminates quadratic computational growth across intermediate layers while retaining global contextual integration at scheduled intervals. OpenArch clearly isolates these mask construction routines into transparent tensor indexing operations that demystify complex attention patterns.

The core structural characteristics of these attention mechanisms include:

  • MHA (Multi-Head Attention): One-to-one correspondence across query, key, and value heads, offering maximum representational fidelity at the cost of high KV cache memory usage.
  • GQA (Grouped-Query Attention): Query heads grouped to share fewer key-value heads, substantially relieving memory bandwidth pressure during generative decoding.
  • MQA (Multi-Query Attention): Extreme compression where all query heads share a single key-value head pair across the layer.
  • MLA (Multi-Head Latent Attention): Low-rank latent vector projections that drastically compress memory cache demands for massive context windows.
  • Sliding-Window and Hybrid Schedules: Interleaving local context windows with periodic global attention layers to optimize computation across long sequences.

Design Choice 2 — Combining Normalization and Positional Encoding

A second architectural axis dictating training stability, gradient propagation, and sequence length extrapolation is the strategic combination of normalization techniques and positional encoding schemes. Historical conventions of simple LayerNorm and static sinusoidal embeddings have been superseded by sophisticated mathematical formulations designed to keep deep networks numerically stable and capable of processing hundreds of thousands of tokens.

Normalization Techniques: Pre-norm, RMSNorm, and QK-Norm

Whereas the earliest iterations of the GPT family placed normalization after the residual additions (Post-norm), all modern foundational architectures have migrated to Pre-norm configurations. Pre-norm applies normalization inside the residual branch prior to the multi-head attention and feed-forward sublayers, preserving an unimpeded gradient highway throughout the network and preventing catastrophic gradient vanishing in deep architectures.

Furthermore, leading open-source models including Llama, Mistral, and Qwen have systematically replaced LayerNorm with RMSNorm (Root Mean Square Normalization). By discarding the mean-centering step and scaling solely by the root mean square of activations, RMSNorm reduces computational overhead while maintaining equivalent regularizing properties. Furthermore, architectures like OLMo 2 incorporate QK-Norm, which applies direct normalization to query and key tensors immediately prior to their dot-product multiplication. This mechanism prevents attention logit magnitudes from exploding during extended training runs, eliminating a notorious source of mid-training instability.

Positional Encoding: From Absolute Position to RoPE and YaRN

Positional encoding has similarly undergone a complete conceptual overhaul. Absolute learned positional embeddings, which rigidly constrained models to predefined sequence limits, have been retired in modern decoder design. Rotary Position Embedding (RoPE) has emerged as the universal standard. RoPE decomposes query and key vectors into pairs of elements and applies a two-dimensional rotation proportional to their sequence position, inherently embedding relative token distances directly into inner-product calculations.

To extend pre-trained context windows to hundreds of thousands of tokens without complete model retraining, modern architectures employ advanced frequency-scaling adjustments such as YaRN (Yet another RoPE extensioN), partial RoPE allocations, or even hybrid models incorporating NoPE (No Positional Encoding) layers. In OpenArch, these rotary frequency calculations and complex rotation tensor transformations are written out cleanly as explicit helper functions, allowing readers to map mathematical equations directly to tensor operations.

Crucial aspects of modern normalization and positional encoding include:

  • LayerNorm versus RMSNorm: Comparing computational throughput and numerical invariance with and without mean-centering operations.
  • QK-Norm: Enforcing bounded variance on queries and keys to prevent attention entropy collapse during large-scale pre-training.
  • Sandwich Normalization: Positioning normalization layers both before and after sublayer transformations to stabilize extremely deep networks.
  • RoPE (Rotary Position Embedding): Injecting relative geometric positional properties directly into attention dot-products via frequency rotations.
  • NoPE and Partial RoPE: Exploring architectural inductive biases by withholding explicit positional signals from specific layers or head dimensions.

Design Choice 3 — Decoder Structure and MoE Routing

The third major architectural watershed separating contemporary models is the internal organization of the feed-forward network (FFN): specifically, the choice between dense computation and sparse Mixture of Experts (MoE). In dense models, every single parameter participates in processing every incoming token. While conceptually straightforward and structurally uniform, dense models suffer from a strict linear coupling between parameter capacity and token-level compute cost.

Sparse MoE architectures decouple this relationship by replacing monolithic feed-forward blocks with an ensemble of expert sub-networks, activating only a small subset of experts per token via a learned routing gate. OpenArch elegantly showcases this design divergence by offering side-by-side implementations within the same model family, such as Qwen 3. By comparing the dense Qwen 3 4B implementation with the sparse Qwen 3 30B-A3B model (where only approximately 3B parameters are activated per token), readers can inspect the exact mechanics of top-k gating, expert dispatching, and weighted output accumulation.

# Conceptual MoE forward routing flow in OpenArch style
# (Pure tensor operations stripping away distributed cluster communication)

import torch
import torch.nn as nn
import torch.nn.functional as F

class SimpleMoERouter(nn.Module):
    def __init__(self, hidden_dim: int, num_experts: int, top_k: int):
        super().__init__()
        self.gate = nn.Linear(hidden_dim, num_experts, bias=False)
        self.top_k = top_k

    def forward(self, x: torch.Tensor):
        # x shape: [batch_size, seq_len, hidden_dim]
        logits = self.gate(x)
        scores = F.softmax(logits, dim=-1)
        topk_weights, topk_indices = torch.topk(scores, self.top_k, dim=-1)
        # Renormalize top-k routing weights across selected experts
        topk_weights = topk_weights / topk_weights.sum(dim=-1, keepdim=True)
        return topk_weights, topk_indices

Advanced implementations like DeepSeek R1 and Kimi K2 extend this paradigm by incorporating shared experts—dedicated sub-networks that remain permanently active for all tokens alongside dynamically routed experts—ensuring reliable capture of foundational knowledge. OpenArch further exposes the structural presence of training innovations such as multi-token-prediction (MTP) auxiliary heads, latent expert projections, and gated attention mechanisms, demonstrating how modern architectures scale parameter counts efficiently.

Key dimensions of decoder and MoE design include:

  • Dense Decoders: Standard feed-forward blocks processing every token uniformly, seen in models like Llama 2/3 and OLMo 2.
  • Sparse MoE Routing: Gating mechanisms dynamically allocating tokens to specialized expert sub-networks based on top-k routing logits.
  • Shared Experts: Dedicated non-routed expert pathways that process every token to maintain consistent common-sense knowledge representations.
  • Latent Experts: Performing intermediate expert computations within compressed representation spaces to relieve memory bottlenecks.
  • Multi-Token-Prediction: Incorporating dual or auxiliary prediction heads to forecast multiple subsequent tokens simultaneously during forward passes.

A Code-Level Learning Workflow for Practicing Engineers and Researchers

For machine learning engineers, graduate students, and systems researchers seeking deep architectural intuition, OpenArch provides an exceptionally efficient learning methodology. Rather than struggling through dense mathematical papers filled with ambiguous tensor notation, opening a standalone model.py file prior to reading academic reports dramatically flattens the learning curve.

1. “Code-First” Exploration Before Reading the Paper

Academic literature often compresses or glosses over intermediate tensor dimension transformations and layer ordering nuances. In contrast, OpenArch exposes every dimensional alteration inside forward() methods explicitly—revealing how shapes evolve from [batch, seq_len, hidden_dim] into multi-head projections, how rotary rotation matrices are constructed, and how attention matrices are normalized. Grounding mental models in concrete tensor operations makes subsequent paper reading intuitive and rapid.

2. Opening Two Models Side by Side and Applying the “Diff Method”

The highest educational dividend of OpenArch comes from direct comparative diffing. By splitting an editor window between text/llama2/model.py and text/llama3/model.py, or between text/qwen3_4b/model.py and text/qwen3_30b_a3b/model.py, practitioners can visually isolate exactly how architectural innovations diverge. Free from hundreds of lines of framework glue code, the genuine design distinctions stand out with absolute clarity.

3. The Original Author’s Explicit Recommendation on Production Use

It is vital to reiterate the boundaries established by the project creator: OpenArch is explicitly not intended to replace production inference libraries. In enterprise deployment, large-scale distributed pre-training, or latency-critical serving environments, engineers must utilize hardened frameworks like Hugging Face transformers, vLLM, TensorRT-LLM, or official vendor packages. OpenArch achieves its peak utility when treated as an educational Rosetta Stone for architectural mastery.

Recommended practical avenues for leveraging OpenArch include:

  • Custom Fine-Tuning and Hook Prototyping: Rapidly validating architectural modifications or gradient flows in local scratchpads before writing complex training hooks.
  • Lightweight Architectural Experimentation: Using clean single-file baselines to benchmark experimental modifications such as altered GQA ratios or novel attention schedules.
  • Internal Engineering Seminars and Curriculum: Utilizing readable, zero-dependency PyTorch models to teach transformer fundamentals without distracting framework overhead.
  • Open-Source Contribution: Selecting unimplemented models from Sebastian Raschka's 72-model gallery, building single-file implementations, and submitting pull requests.

What We Could Not Confirm

In adherence to strict factual verification, the following details could not be conclusively determined from primary sources and were deliberately omitted from speculative assertion:

  • Explicit parameter counts for certain large MoE models: While OpenArch explicitly records parameter dimensions for GPT-2 XL (1.5B), Llama 2 (7B), Llama 3 (8B), OLMo 2 (7B), Qwen 3 (4B and 30B-A3B), and PaliGemma (3B), exact numerical sizes for models like DeepSeek R1, Kimi K2, GLM 4.5, and GPT-OSS were omitted or unlisted in the summary tables, and arbitrary figures were not fabricated.
  • Automated official weight loading and conversion tooling: While the repository explicitly confirms executable forward passes (✅) on simulated inputs, the exact extent of automated weight loading from Hugging Face checkpoints across all models remains an open contribution area and could not be verified comprehensively.
  • Concrete release schedules for models under construction: Architectures marked as under construction (🚧), including Grok-2.5 and Dall-e, lack publicly specified milestone delivery dates in the repository.
  • Sequential implementation backlog for the full 72-model gallery: Although achieving full coverage of Sebastian Raschka's 72 gallery models is stated as the overarching objective, the repository does not publish an official prioritized roadmap determining the exact order of upcoming model releases.
