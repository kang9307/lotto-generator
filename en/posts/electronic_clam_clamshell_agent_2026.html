How to Keep an AI Agent Running With the MacBook Lid Closed - Electronic Clam and Clamshell Sleep

Why people want long-running coding agents to keep going with the lid shut, and what you should know before you make it happen

2026-06-16 Tech & IT

Intro: Why people want to close the lid and still get work done

In June 2026, a small macOS menu bar app called Electronic Clam showed up on GeekNews. Its one-line pitch is simple: "keep your AI agent running even with the MacBook lid closed (clamshell)." On the surface it is a common keep-awake utility, but the reason it exists captures a slice of the 2026 development landscape. As long-running, autonomous AI coding agents became routine, a new demand emerged: people want that work to keep going even while they carry the laptop around with the lid shut.

Agentic tools like Claude Code and the Codex CLI now plan, execute, and debug on their own for tens of minutes, sometimes hours, after a single instruction. During that time the developer wants to step away. But a MacBook sleeps when you close the lid, and when it sleeps the agent pauses too. That small friction is the direct motivation behind tools like Electronic Clam. Rather than rehashing a press release, this piece lays out, in my own view, where the demand comes from, what macOS actually does when you close the lid, and how the various ways to block sleep (caffeinate, menu bar apps, pmset, a server) differ and what to watch out for.

A note on sourcing first. The macOS behavior and commands here are based on Apple's clamshell-mode documentation and public references for how caffeinate and pmset behave as of June 2026. The internal details of Electronic Clam itself are barely verified beyond its one-line description, so this article dissects the whole problem of "running an agent with the lid shut" rather than that single tool. It follows directly from the long-running agent workflows discussed in my Claude Code dynamic workflows analysis. If that was about the agent's "brain," this is about the physical environment that keeps the agent alive.

1. What Electronic Clam is - a tool born from a problem

Electronic Clam is a small utility that lives in the macOS menu bar, and its core job is to keep the system from sleeping even with the lid closed. The "Clam" in the name is a pun on the clamshell form factor of a laptop that opens and shuts like a shell.

1.1 A one-line feature with context behind it

The tool itself is simple: flip the menu bar icon on to block sleep, off to return to normal. But that simplicity is the point. macOS already ships caffeinate, so why does a separate menu bar app appear at all? Because the target user and the context have shifted. The classic demand for keep-awake was "don't let the screen dim during a presentation" or "stay up until this big download finishes." The new 2026 demand is "keep my autonomous coding agent working while the lid is shut." Same technology (power assertions), entirely different motivation.

1.2 The same root as caffeinate

Apps of this kind are almost always built on top of the macOS power-assertion mechanism. What caffeinate does in the terminal - asserting "keep the system awake right now" - a menu bar app wraps in a GUI. So you should not expect Electronic Clam to cast some "stronger magic" than caffeinate. The substance is the same; the difference is in usability and conditional control. Understanding that is how you pick the right tool.

2. What macOS does when you close the lid - sleep and clamshell

To understand this properly, you need to know what macOS decides internally the moment you close the lid. The key concept here is clamshell mode.

2.1 The default is to sleep

Close a MacBook lid with no special conditions and macOS enters sleep. Sleep pauses the CPU and most activity while keeping RAM contents, minimizing power draw. At that point any process running in the terminal - including a coding agent - pauses too. Work not progressing during sleep is by design, not a bug.

2.2 Clamshell mode: the conditions to stay awake while closed

The officially supported "keep using it with the lid closed" is clamshell mode, and its conditions are explicit. You must be connected to power and have an external display attached (HDMI, USB-C, Thunderbolt, DisplayLink, and so on). Meet those and macOS will not sleep when you close the lid; it turns off only the built-in screen and keeps driving the external monitor. This is the canonical way to use a MacBook like a desktop, and it works on every modern MacBook.

2.3 So what the tools are trying to imitate

This is where keep-awake tools diverge. To stay running while closed without an external monitor, you ultimately have to change how the system reacts to the "lid closed" signal, or trick it into thinking a display is attached. So in practice three branches exist: (a) fake a monitor with a dummy display adapter, (b) block sleep globally (pmset) so even lid-close sleep is suppressed, or (c) use an app that supports closed-lid control. That distinction is the backbone of this article.

3. Four ways to block sleep - caffeinate, menu bar apps, pmset, dummy display

There are several routes to the goal of "run it with the lid shut." Here is an honest comparison of how each works and where it breaks.

3.1 caffeinate - built in, but lid-close is separate

caffeinate is a terminal command built into macOS, present since Mountain Lion in 2012. caffeinate -i blocks idle sleep, -d blocks display sleep, and -s blocks system sleep while on power. The strongest pattern is to bind it to a process: caffeinate -i <command> stays awake only while that command runs and releases automatically when it finishes. But there is a decisive limit. The "idle-sleep" assertion caffeinate holds does not override lid-close sleep. Without an external display, the machine can still sleep the moment you close it even with caffeinate running.

3.2 Menu bar apps (Electronic Clam, Amphetamine, and friends) - usability and lid control

Menu bar apps wrap the caffeinate assertion in a GUI so non-developers can use a toggle. The standout here is Amphetamine, which goes beyond a plain on/off to offer conditional sessions (indefinite, a fixed duration, or while a specific app runs) and, from version 5.0 onward, explicitly supports staying awake with the lid closed. Simpler apps like KeepingYouAwake only handle the desktop or lid-open state and do not address closed-lid. Electronic Clam reads as a variant of this spectrum that puts the "keep AI agents alive" motivation front and center. The key point: not every menu bar app guarantees closed-lid behavior, so you must check whether closed-lid control is supported.

3.3 pmset disablesleep - a powerful but dangerous hammer

Running sudo pmset -a disablesleep 1 in the terminal blocks system sleep globally. This is stronger than caffeinate; it suppresses lid-close sleep so the machine stays awake when shut even without an external monitor. But it is a dangerous hammer. Forget to turn it off and the Mac never sleeps, even on battery, leading to drain and heat. When the job is done you must revert with sudo pmset -a disablesleep 0. I treat this as a temporary measure only for people who understand why and can revert immediately.

3.4 Dummy display adapter - tricking it with hardware

The most straightforward method is a dummy HDMI/USB-C adapter that makes the system think an external monitor is connected. With that, the real clamshell conditions are met and it stays up while closed. Because it does not rely on software settings, it is less likely to break with an OS update and pairs naturally with a desktop dock. The only downside is carrying a physical accessory.

4. The bigger question - should long-running agents even run on a laptop?

With the tool comparison done, let's step up a level. In my view the real question is not "how do I keep it running while closed" but "should this work run on a laptop at all?"

4.1 The weakness of running it on a laptop

Tie a long-running agent to a laptop and the survival of the work is held hostage to the machine's physical state. Sleep, a drained battery, a dropped network mid-move, an absentminded reboot - any one of them can wipe out a multi-hour autonomous run. On top of that, hammering the CPU while closed is fundamentally bad for heat, because shutting the lid blocks the heat path through the keyboard deck. There is a reason clamshell assumes power and an external monitor.

4.2 Server plus tmux, the canonical way

The canonical way to run an agent that goes for hours or days is on a remote server (VPS or workstation) inside a session manager like tmux. Run it inside tmux and the session lives on the server even if you drop the SSH connection or close the laptop, so the work continues regardless of whether you are attached. Multi-day runs of tools like Claude Code and the Codex CLI actually happen this way. The laptop becomes just a "window to look through," and the server owns the survival of the work.

4.3 So which choice is reasonable

My recommendation is not an either/or but a division of roles. Interactive pair-coding during the day runs on the laptop; overnight and long autonomous runs go to server tmux. "Run it while closed" fits best as a lightweight, temporary scenario - when you have no server to spare, or you just want to finish a one-off job while you step away for a bit. Tools like Electronic Clam are conveniences that bridge that temporary gap, not replacements for running on a server.

5. Practical tips and traps - what to cover when running closed

If you still have to run with the lid shut, covering the following will cut your risk substantially.

5.1 Secure power and airflow first

If you are going to run it closed, always stay plugged into power and make sure the body is not buried in cloth, a blanket, or a bag so airflow is preserved. Heat is the number-one enemy of a closed laptop. Where possible, creating real clamshell conditions with a dummy display is more stable than a software toggle.

5.2 Bind it to the process and let it release when done

Binding the lifetime to the task is safer than a global block. Tie it to a command with caffeinate -i <agent command> and the keep-awake releases the instant the work finishes, preventing the "forgot to turn it off and drained the battery" accident. If you used pmset disablesleep, make reverting to 0 right after the job a routine.

5.3 Handle the durability of the work separately

Blocking sleep only keeps "the laptop from sleeping"; it does not make the work resume if it is interrupted. For long-running agents, have them commit and save intermediate output often, and where possible use tmux or a background session to make them less fragile to a terminal closing. In my experience, "make it recover when cut off" buys far more peace of mind than "keep it from sleeping."

5.4 Don't forget security

A closed laptop that is awake means it is alive behind a lock screen. When you step away, confirm the screen actually locks and that your auto-lock policy is not defeated by the sleep block. Leaving an awake machine unattended in shared or mobile settings is a separate risk.

6. Limits and caveats

Showing only the upside would be dishonest. There are limits worth naming explicitly.

6.1 Heat and hardware stress

The biggest asterisk is heat. Pin the CPU for a long time with the lid closed and trapped heat can throttle performance or, over time, accumulate component stress. That clamshell was designed around an external display and power is partly for safety margin. I would not make "run it while closed" a permanent way of operating.

6.2 OS updates and changing behavior

Software-based sleep blocking is vulnerable to changes in macOS versions and power-management policy. A method that worked on one version can change on the next. That is why, over the long term, I trust approaches that depend less on OS policy - hardware-based (dummy display) or server operation - more.

6.3 A workaround, not a real fix

Every "run it closed" method is fundamentally a workaround to use a laptop like a server. For genuinely long-running, high-availability workloads, the right move is to place the work in an environment that does not get interrupted in the first place (a server or the cloud) rather than forcing a laptop to stay awake. Tools like Electronic Clam are best taken as conveniences that smooth that friction.

7. Conclusion - three things you can apply today

The arrival of Electronic Clam is more than the release of one small utility. It is a signal that long-running, autonomous AI agents have entered everyday development, and with them a new demand: "keep my work going even when I step away." As of June 2026, here are three concrete moves I recommend.

7.1 First ask whether lid-closed operation is truly needed

For a one-off job while you step away briefly, binding caffeinate to the command is enough. For a multi-day workload, do not fight your laptop's sleep - move it to server tmux. Lid-closed tools are only needed in the narrow band in between.

7.2 Cover power, airflow, and reverting as a set

If you run it closed, secure power and airflow first, and bind the sleep block to the task or release it the instant the job ends. If you enabled pmset disablesleep, put reverting it into your routine. Heat and drain arrive without warning.

7.3 Make the work itself recover when interrupted

More peace of mind comes from the durability of the work than from blocking sleep. Save intermediate output often, and use tmux or a background session to be less fragile to a terminal closing. For the wider context of operating agents, see my Claude Code dynamic workflows analysis.
