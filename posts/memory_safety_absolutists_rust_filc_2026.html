메모리 안전성 절대주의자들 - Rust와 Fil-C 논쟁

전면 재작성인가 점진적 안전화인가, 위협 모델과 코드 수명으로 판단하는 법

2026-07-27 개발/인프라

서론: 안전을 놓고 벌어지는 순수성 경쟁

메모리 안전성 논쟁이 이상한 방향으로 흐르고 있다. 처음에는 C와 C++로 짠 코드에서 왜 같은 종류의 취약점이 30년째 반복되는가라는 지극히 실용적인 질문이었다. 그런데 지금 커뮤니티에서 벌어지는 다툼은 성격이 다르다. Rust에는 unsafe라는 탈출구가 있으니 진짜 안전한 언어가 아니고, 따라서 Fil-C처럼 모든 위반을 런타임에 잡아내는 구현만이 정통이라는 주장이 나온다. 최근 화제가 된 「메모리 안전성 절대주의자들」이라는 글은 바로 이 태도를 정면으로 겨냥한다. 요지는 간단하다. Rust의 탈출구는 신랄하게 비판하면서 아무 검사 없이 컴파일되는 평범한 C·C++에는 같은 잣대를 들이대지 않는다면, 그것은 안전에 대한 관심이 아니라 진영에 대한 관심이라는 것이다.

이 글은 그 비판에 동의하는 지점과 동의하지 않는 지점을 함께 짚는다. 다만 감상 대신 숫자에서 출발한다. 메모리 안전성 취약점이 실제로 얼마나 되는지, Fil-C가 무엇을 대가로 안전을 사는지, Rust의 unsafe가 실제 생태계에서 얼마나 쓰이는지, C++ 진영이 내놓은 프로파일 방식은 어디까지 왔는지를 공개 자료로 확인한 뒤, 레거시 C 코드가 유난히 두꺼운 한국의 임베디드·통신·금융 코어에서 무엇이 실제로 가능한지를 따져 본다. 결론을 먼저 말하면, 정답은 언어 이름이 아니라 그 코드가 어떤 입력을 받고 앞으로 몇 년을 더 사는가에 달려 있다.

1. 논쟁 이전에 숫자부터 - 메모리 안전성은 실제로 얼마나 문제인가

이 논쟁에서 가장 자주 인용되는 수치는 70퍼센트다. 이 숫자는 감이 아니라 두 회사의 자체 집계에서 나왔고, 서로 독립적으로 비슷한 값에 도달했다는 점에서 신뢰할 만하다.

1.1 공개된 주요 통계

  • 마이크로소프트: 자사가 CVE를 부여해 수정한 보안 취약점의 약 70퍼센트가 메모리 안전성 문제라고 밝혔다. 12년 이상의 보안 업데이트를 집계한 값이다.
  • 구글 크로미움: 2015년 이후 스테이블 채널에서 수정한 고위험·치명 등급 버그 912건을 분석한 결과 약 70퍼센트가 메모리 관리·안전성 버그였고, 그중 절반가량이 해제 후 사용(use-after-free)이었다.
  • 안드로이드: 메모리 안전성 취약점 비중이 2019년 76퍼센트 → 2024년 24퍼센트로 떨어졌고, 이후 20퍼센트 아래로 내려갔다고 보고됐다.
  • 안드로이드의 Rust 코드: 약 500만 줄 규모에서 취약점 밀도가 100만 줄당 0.2건으로 추정됐다. 같은 조직의 C·C++ 역사적 밀도인 100만 줄당 약 1,000건과 비교하면 1,000배 이상의 차이다.
  • 부수 효과: 같은 보고에서 Rust 변경은 롤백률이 4배 낮고 코드 리뷰 시간이 25퍼센트 짧았다고 언급됐다. 안전성이 개발 속도를 깎아먹는다는 통념과 반대되는 대목이다.

1.2 이 숫자들이 말하는 것과 말하지 않는 것

여기서 조심할 점이 있다. 안드로이드의 0.2 대 1,000이라는 비교는 동일 조건 실험이 아니다. Rust로 새로 짠 코드는 대체로 새 기능이고, C·C++ 쪽은 수십 년간 공격자의 집중 조명을 받아온 오래된 코드다. 신규 코드가 상대적으로 덜 발굴됐을 가능성, 모듈의 위험도 차이, 발견 노력의 편중 같은 요인이 섞여 있다. 그럼에도 세 자릿수 배율은 측정 편향만으로 설명하기 어렵다. 그리고 76퍼센트에서 20퍼센트 아래로 내려간 안드로이드의 추세선은 기존 코드를 전부 다시 쓰지 않고도 비중이 급락했다는 사실을 보여준다. 이 점이 뒤에서 이야기할 실무 전략의 핵심 근거가 된다.

2. Fil-C는 무엇인가 - C를 그대로 두고 안전하게 만드는 길

2.1 작동 방식: 인비지캡과 동시성 GC

Fil-C는 「광적으로 호환되는 메모리 안전 C·C++ 구현」을 표방한다. 핵심은 InvisiCaps라는 포인터 모델이다. 포인터를 프로그램이 볼 수 있는 주소값과 볼 수 없는 능력치(capability)로 분리해, 경계·수명 정보를 별도 메타데이터에 보관한다. 프로그램은 여전히 포인터를 정수처럼 주무를 수 있지만, 실제 역참조 시점에는 숨겨진 능력치와 대조되어 범위를 벗어나면 패닉으로 즉시 중단된다. 수명 관리는 동시성·병렬 가비지 컬렉터가 맡아, 해당 객체를 가리키는 포인터가 모두 사라진 뒤에야 메모리를 회수한다. 그래서 해제 후 사용이 원천적으로 성립하지 않는다. 스레드는 역방향 제어 흐름 지점 같은 세이프 포인트에서만 멈추고, 시그널 핸들러도 세이프 포인트에서 실행되어 GC와 충돌하지 않는다.

성숙도 면에서 이 프로젝트는 장난감이 아니다. 공식 사이트 기준으로 CPython, OpenSSH, GNU Emacs, Wayland 등이 이식됐고, Pizlix라는 이름으로 리눅스 유저랜드 전체를 Fil-C로 빌드한 배포판까지 존재한다. 2026년 7월 초 기준 버전 0.681이 공개되어 있어 개발도 활발하다. 다만 버전 번호가 여전히 0으로 시작한다는 사실도 함께 읽어야 한다.

2.2 무엇을 대가로 지불하는가

안전은 공짜가 아니다. Fil-C가 치르는 비용은 명확하고, 이 비용이 곧 적용 가능 영역을 결정한다.

  • 실행 속도: 포인터 추적이 많은 코드에서 대략 1~6배, 나쁜 경우 4배 안팎의 감속이 보고된다. 반대로 셸(Bash 5.2.32)처럼 포인터 밀도가 낮은 프로그램은 체감 차이가 거의 없었다는 실측도 있다. 즉 워크로드 편차가 매우 크다.
  • 메모리 사용량: 포인터를 담은 구조체는 능력치 메타데이터가 따라붙어 사실상 두 배의 공간을 쓴다. 메모리가 빠듯한 임베디드에서는 이것만으로 탈락할 수 있다.
  • ABI 비호환: 일반 컴파일러가 만든 오브젝트와 링크되지 않는다. 의존성 전체를 다시 빌드해야 한다는 뜻이고, 바이너리로만 제공되는 상용 라이브러리가 하나라도 끼면 그 자리에서 막힌다.
  • 언어 간 연결: 현재 Rust와의 링크는 지원되지 않는다. 혼합 스택에서는 경계 설계가 까다로워진다.
  • GC의 존재: 하드 실시간, 커널·드라이버, 지터 규격이 걸린 신호 처리에는 가비지 컬렉터 자체가 부적격 사유가 된다.

정리하면 Fil-C는 기존 코드를 살리는 대신 실행 시점의 자원을 지불하는 설계다. 이 교환이 성립하는 영역이 분명히 있고, 성립하지 않는 영역도 분명히 있다.

3. Rust의 안전 모델과 unsafe의 현실

3.1 소유권과 대여 검사기

Rust는 반대 방향에서 접근한다. 값마다 소유자가 하나이고, 참조는 변경 가능한 것 하나 또는 읽기 전용 여럿 중 하나만 동시에 존재할 수 있다는 규칙을 컴파일 시점에 강제한다. 이 규칙 덕분에 해제 후 사용, 이중 해제, 데이터 레이스가 실행 전에 걸러진다. 런타임 검사와 GC가 필요 없으므로 성능 특성은 C에 근접한다. 대신 대가는 사람이 지불한다. 기존 C 코드의 자유분방한 별칭(aliasing) 관행은 이 모델에 그대로 옮겨지지 않아, 사실상 자료구조 설계부터 다시 하게 되는 경우가 많다.

3.2 같은 버그, 세 가지 결말

해제 후 사용 하나를 놓고 세 접근이 어떻게 갈리는지 보면 성질 차이가 분명해진다.

/* 표준 C: 컴파일 통과, 실행도 대개 통과, 그러나 공격 표면 */
char *buf = malloc(16);
free(buf);
strcpy(buf, "hi");   /* 해제된 메모리에 기록 - 임의 코드 실행으로 이어질 수 있음 */
/* Fil-C: 소스는 그대로. 실행 중 패닉으로 즉시 중단 */
/* 컴파일러가 포인터의 능력치를 확인하고 무효 접근을 차단한다 */
// Rust: 애초에 컴파일이 되지 않는다
let buf = vec![0u8; 16];
drop(buf);
// buf[0] = 1;  // error[E0382]: borrow of moved value: `buf`

세 결말의 차이는 비용을 어느 시점에 지불하는가다. C는 지불을 미루다 사고가 났을 때 전액을 낸다. Fil-C는 실행할 때마다 조금씩 낸다. Rust는 개발 시점에 한 번에 낸다. 어느 방식이 유리한지는 그 소프트웨어의 실행 빈도, 성능 여유, 남은 수명에 따라 달라진다. 이것이 언어 우열이 아니라 상황 판단인 이유다.

3.3 unsafe는 구멍인가, 감사 표면인가

절대주의자들의 핵심 공격 지점은 unsafe다. 이 비판이 완전히 틀린 것은 아니다. unsafe 안에서 잘못 쓴 코드가 안전한 코드에서 발현되는 버그를 만들 수 있다는 연구가 실제로 있고, 고위험 크레이트를 분석해 다수의 권고문과 CVE를 정리한 조사도 나와 있다. 그러나 규모 감각이 필요하다. 러스트 재단 조사에 따르면 crates.io의 크레이트 중 unsafe 키워드를 사용하는 비율은 약 20퍼센트이고, 사용처의 상당수가 C 상호운용이며, 전체 코드량 기준으로는 1퍼센트 안팎으로 추정된다.

여기서 얻는 실질적 이득은 안전의 유무가 아니라 감사 대상의 크기다. C 코드베이스에서는 모든 줄이 잠재적 unsafe다. Rust에서는 검토해야 할 지점이 문법적으로 표시되고 좁혀진다. 100만 줄 중 1만 줄을 집중 검토하는 일과 100만 줄 전체를 검토하는 일은 조직 관점에서 완전히 다른 과제다. 「탈출구가 있으니 무의미하다」는 주장은 이 차이를 지운다는 점에서 논리적으로 약하다.

4. 「절대주의」 비판의 요지 - 전면 재작성 요구는 현실적인가

원문 글쓴이의 비판은 두 갈래로 읽힌다. 첫째는 이중 잣대다. Rust의 unsafe는 치명적 결함으로 취급하면서, 아무 검사 없이 컴파일되는 일반 C·C++에는 같은 강도의 비난을 하지 않는다면 그 기준은 안전이 아니다. 둘째는 대안의 비대칭성이다. Fil-C를 유일한 정답으로 내세우려면 Fil-C가 감당하지 못하는 영역, 즉 GC를 둘 수 없고 ABI를 바꿀 수 없으며 4배 감속을 흡수할 수 없는 영역을 무엇으로 채울지 답해야 한다. 그 자리를 지금 메우고 있는 것이 바로 Rust다.

나는 이 비판에 대체로 동의하되, 한 가지는 덧붙이고 싶다. 절대주의는 Rust 반대 진영에만 있는 것이 아니다. 모든 C를 Rust로 다시 쓰라는 요구 역시 같은 종류의 절대주의다. 수백만 줄 규모의 검증된 코드를 재작성하는 일은 새 언어 학습 비용만의 문제가 아니라, 수십 년간 현장에서 다듬어진 예외 처리와 암묵적 요구사항을 통째로 잃는 문제다. 재작성 과정에서 메모리 버그는 사라지고 논리 버그가 새로 들어오는 교환이 벌어질 수 있다. 실제로 안드로이드가 보여준 성과는 전면 재작성이 아니라 새 코드부터 안전한 언어로라는 원칙에서 나왔다. 76퍼센트에서 20퍼센트 아래로의 하락은 옛 코드를 다 지워서가 아니라, 새로 유입되는 취약점의 원천을 막았기 때문에 만들어진 곡선이다.

표를 보면 두 선택지가 겹치지 않는 문제를 푼다는 사실이 드러난다. Fil-C의 최대 강점은 성능이 아니라 인력과 자산의 연속성이다. 기존 C 개발자가 그대로 남고 코드도 그대로 남는데 위험 등급만 내려간다. 반대로 Rust의 최대 강점은 안전성이 공짜에 가깝다는 점이다. 한 번 지불하면 이후 실행마다 비용이 붙지 않는다. 따라서 오래 살아남고 실행 빈도가 높은 핵심 컴포넌트일수록 Rust 쪽 산술이 유리해지고, 수명이 얼마 남지 않았거나 성능 여유가 큰 코드일수록 Fil-C 쪽 산술이 유리해진다.

6. C/C++ 진영의 반론 - 안전 프로파일과 C++26

C++ 표준화 진영은 언어를 버리는 대신 안전 프로파일이라는 경로를 택했다. 별도의 안전한 방언을 만드는 「Safe C++」 제안과 기존 코드에 점진 적용 가능한 「프로파일」 제안이 경쟁했고, 표결에서 프로파일 찬성 19표, Safe C++ 찬성 9표, 양쪽 모두 11표, 중립 6표로 프로파일 쪽이 앞서면서 그 방향이 채택됐다. 2026년 3월 런던 크로이던 회의에서 C++26의 기술 작업이 마무리됐고, 리플렉션·계약과 함께 재작성 없이 적용하는 안전 강화가 포함됐다. 미정의 동작을 더 줄이는 작업과 추가 프로파일 논의는 C++29를 겨냥해 이어지고 있다. 애플이 WebKit 400만 줄 이상을 프로파일 성격의 부분집합 방식으로 강화해 실효를 봤다는 사례도 제시됐다.

다만 이 접근의 한계도 솔직하게 볼 필요가 있다. 프로파일은 주로 공간적 안전성, 즉 경계 검사 쪽에서 힘을 발휘하고, 해제 후 사용으로 대표되는 시간적 안전성은 훨씬 어려운 문제로 남는다. 구글은 공개 입장에서 C++가 시간적 안전성까지 포함한 엄밀한 메모리 안전 언어로 진화할 현실적 경로를 보지 못한다고 명시했다. 앞서 본 크로미움 통계에서 메모리 버그의 절반이 해제 후 사용이었다는 점을 겹쳐 보면, 프로파일이 커버하지 못하는 영역이 곧 가장 아픈 절반일 수 있다는 뜻이다. 그래도 프로파일에는 결정적 장점이 있다. 이미 있는 코드에 오늘 적용할 수 있다는 것이다. 절반을 막는 조치를 지금 켜는 편이, 전부를 막는 계획을 5년 뒤에 시작하는 것보다 대체로 낫다.

7. 규제라는 변수 - 권고가 조달 요건으로 바뀌는 중

이 논쟁은 이제 취향의 문제만이 아니다. 미국 백악관 국가사이버국장실(ONCD)은 2024년 2월 「Back to the Building Blocks」 보고서에서 프로그래밍 언어 자체를 보안의 기반 요소로 지목했고, 사이버보안·인프라보안국(CISA)은 2023년 「메모리 안전 로드맵의 필요성」 공동 지침에 이어 제품 보안 관련 문서에서 소프트웨어 제조사에 다음을 권고했다.

  • 메모리 안전성 로드맵을 2026년 1월 1일까지 공개할 것. 이미 지난 시점이므로 지금은 이행 여부가 확인되는 단계다.
  • 로드맵은 네트워크 접점 코드와 암호 연산처럼 우선순위가 높은 구성요소부터 다룰 것.
  • 단순 선언이 아니라 취약점의 실질적·우선순위 기반 감소로 이어짐을 입증할 것.
  • 2030년 1월 1일 이전에 지원 종료가 공표된 제품은 대상에서 제외.
  • CISA 스스로 전환에 상당한 시간과 자원이 든다고 인정하며 단기 완화와 장기 제거를 병행하라고 권고.

주목할 대목은 마지막 두 항목이다. 규제 당국조차 전면 재작성을 요구하지 않는다. 우선순위와 기한을 요구할 뿐이다. 절대주의 논쟁의 양극단보다 오히려 규제 문서 쪽이 현실적인 셈이다. 한국 기업에도 남의 일이 아니다. 미국 공공·중요 인프라에 납품하는 통신 장비, 보안 어플라이언스, 자동차 부품, 산업 제어 소프트웨어는 조달 심사에서 이 로드맵의 존재 여부를 묻는 흐름에 곧 노출된다. 국내에서도 MISRA C, ISO 26262, IEC 62443 같은 기존 안전·보안 규격을 이미 다루고 있다면, 메모리 안전성 로드맵은 그 문서 체계 위에 얹기 어렵지 않다.

8. 한국 실무 관점 - 레거시가 두꺼운 현장에서 무엇이 가능한가

8.1 세 개의 서로 다른 전장

한국 산업 구조에서 C·C++ 코드가 가장 두껍게 쌓인 곳은 대략 세 군데다. 각각 제약 조건이 완전히 다르므로 같은 처방을 내리면 실패한다.

  • 임베디드·자동차: 메모리 수백 KB에서 수 MB, 하드 실시간 제약, 기능안전 인증 부담. GC가 붙는 순간 인증 논리가 흔들리므로 Fil-C는 사실상 배제된다. 현실적 경로는 MISRA 계열 규칙 강화, 정적 분석 확대, 그리고 신규 모듈 한정 Rust 도입이다.
  • 통신 장비·네트워크 소프트웨어: 패킷 파서와 프로토콜 상태 기계가 완전히 신뢰할 수 없는 입력을 직접 받는다. 위협 노출도가 가장 높은 자리다. 반면 성능 요구는 도메인마다 편차가 커서, 제어 평면이라면 안전한 언어로 다시 쓸 가치가 충분하고 데이터 평면 핫패스는 여전히 까다롭다.
  • 금융 코어·대사 처리: 전문 파싱과 배치 작업이 많고, 원장 정합성 때문에 재작성 리스크를 극도로 기피한다. 그런데 야간 배치는 성능 여유가 상대적으로 크다. Fil-C 계열 접근이 가장 잘 맞을 수 있는 자리이면서, 동시에 상용 바이너리 의존성이 많아 ABI 문제로 막히기도 쉬운 자리다.

8.2 인력 수급이라는 진짜 병목

기술적 타당성보다 조직을 실제로 멈춰 세우는 것은 사람 문제다. 국내에서 시스템 프로그래밍 인력은 이미 얇고, Rust를 실무 수준으로 다루는 인력은 더 얇다. SI·수탁 개발 비중이 높은 구조에서는 재작성 기간 동안의 기능 동결을 발주처가 받아들이기 어렵다는 현실적 벽도 있다. 이 관점에서 Fil-C 같은 접근의 매력은 성능이 아니라 사람을 바꾸지 않아도 된다는 데 있다. 반대로 Rust 도입을 결정한다면, 전면 전환 대신 새 모듈 한 개를 정해 6개월간 팀 두세 명이 학습과 산출을 겸하는 방식이 실패 확률이 낮다. 앞서 인용한 롤백률 4배 감소와 리뷰 시간 25퍼센트 단축은 학습 곡선을 넘긴 이후에 나타나는 지표라는 점도 함께 기억할 필요가 있다.

9. 성능 오버헤드는 어디까지 감수할 수 있는가

「4배 느려진다」는 문장은 그 자체로는 판단 근거가 되지 못한다. 4배가 치명적인 자리와 아무 문제가 없는 자리가 한 조직 안에 공존하기 때문이다. 도메인별로 감수 가능한 폭을 나눠 보면 선택이 자동으로 좁혀진다.

이 표에서 눈여겨볼 것은 위협 노출도가 높은 자리와 성능 여유가 큰 자리가 상당 부분 겹친다는 점이다. 파일 파서, 이미지·문서 변환기, 로그 처리기처럼 외부 데이터를 직접 씹는 코드는 대개 핫패스가 아니다. 바로 이 교집합이 Fil-C 계열 접근의 최적 진입점이다. 전면 도입을 논쟁하는 대신 이 교집합부터 재컴파일해 보는 것이 훨씬 생산적인 첫걸음이다.

10. 결론을 대신할 판단 프레임 - 진영이 아니라 위협 모델과 코드 수명

지금까지의 내용을 실무 결정으로 압축하면 질문은 네 개로 줄어든다. 언어 이름은 그다음에 나온다.

  1. 이 코드는 신뢰할 수 없는 입력을 직접 받는가? 받는다면 최우선 대상이다. 네트워크 경계, 파일 파서, 암호 연산, 사용자 업로드 처리 순으로 목록을 만든다.
  2. 이 코드는 앞으로 몇 년을 더 사는가? 3년 내 폐기 예정이라면 재작성 투자는 회수되지 않는다. 강화 옵션과 격리로 버티는 편이 합리적이다. 10년 이상 살 코드라면 재작성 산술이 성립하기 시작한다.
  3. 성능·메모리 여유가 몇 퍼센트인가? 여유가 2배 이상이고 의존성을 전부 소스로 확보할 수 있다면 Fil-C 계열 접근이 가장 싼 안전이다. 여유가 없다면 그 선택지는 지운다.
  4. 사람을 바꿀 수 있는가? 팀이 Rust를 익힐 여력과 채용 여건이 없다면, 전면 Rust 전환 계획은 문서로만 남는다. 이 경우 새 모듈 한 개로 좁힌 파일럿이 유일하게 작동하는 형태다.

이 네 질문에 답하고 나면 대부분의 조직에서 결론은 비슷하게 수렴한다. 새로 쓰는 코드는 안전한 언어로, 위협에 노출된 옛 코드는 재컴파일이나 격리로, 나머지는 그대로 두고 감시한다. 안드로이드가 76퍼센트에서 20퍼센트 아래로 내려간 경로가 정확히 이 모양이었다.

결론: 순수성은 지표가 아니다

「메모리 안전성 절대주의자들」이 지적한 이중 잣대는 유효하다. Rust의 unsafe를 근거로 Rust를 실격시키면서 아무 검사 없이 도는 C·C++를 묵인한다면, 그 기준은 안전이 아니라 소속이다. 동시에 반대 방향의 절대주의, 즉 모든 C를 지금 당장 Rust로 다시 쓰라는 요구 역시 현장에서는 작동하지 않는다. 두 진영이 공유하는 오류는 같다. 안전을 이분법으로 다루고, 그 코드가 처한 조건을 보지 않는다는 것이다.

실무자에게 유용한 태도는 훨씬 건조하다. Fil-C는 기존 자산과 인력을 유지한 채 실행 자원을 지불해 시간적·공간적 안전을 동시에 얻는 도구이며, ABI 재빌드와 GC를 감당할 수 있는 자리에서 강력하다. Rust는 개발 시점에 비용을 몰아 지불하고 실행 시점을 비워 두는 도구이며, 오래 살고 자주 실행되며 성능 여유가 없는 자리에서 유리하다. C++ 프로파일은 당장 켤 수 있는 절반의 방어이고, 그 절반이 0보다 훨씬 낫다. 셋은 경쟁 관계라기보다 서로 다른 제약 조합을 위한 장비다. 2026년 7월 현재, 규제 당국조차 우선순위와 기한을 말할 뿐 전면 재작성을 말하지 않는다. 진영 깃발을 고르는 데 쓸 시간을 내 코드가 어떤 입력을 받고 몇 년을 더 사는지 목록으로 만드는 데 쓰는 편이, 어떤 논쟁에 참여하는 것보다 취약점 하나를 더 줄인다.
