最悪を一定にすることは平均を速くすることとは別の目標だ - 静的アロケーションと一定の作業量

締め切りのある仕事を見分ける基準、手法ごとに得るものと失うもの、そしてそれを実際に確かめる指標

2026-09-05 開発・インフラ

性能を改善したという言葉はふつう「速くなった」という意味で使われる。ところがある種の場所では速くなることが目標ではない。いつでも同じ時間で終わることが目標だ。平均が半分になっても100回に1回が10倍に跳ねるなら、その場所ではそれは改善ではなく悪化である。

この記事はその二つの目標がどう違い、なぜたいてい互いを削り合うのかを見る。メモリ確保の小技を集めた記事ではない。実行中のアロケーションをなくすという選択が正確に何を買い何を売る取引なのか、そしてその取引の結果をどの指標で確かめるのかという話だ。

この記事の引用はすべて一次情報から取っており、きっかけになった記事が実際に言っていることと言っていないことを §1 で先に分けておく。原文にない論点は本文中でその都度「原文にはない」と断る。

きっかけ - 原文が言ったことと言っていないこと

2026年9月2日に matklad が Static Allocation, Constant Work を公開した。短い記事で、例示コードは Zig であり、注文マッチングエンジンをたとえに使っている。ただし著者本人が注文マッチングエンジンが何なのかは漠然としか分かっていないと書いており、この手が役立つのではないかと推測しているにすぎない。だからこの記事は特定領域への処方箋ではなく、二つの設計習慣についての話として読むのが正しい。

一つめの習慣が静的アロケーションだ。起動時に上限のぶんを一度だけ取り、そのあとは取らない。原文の例は上限をコマンドライン引数で受け取り、const orders: []Order = try gpa.alloc(Order, cli_args.orders_max); のように一度で確保する。そして実行中に上限を超える要求が来たら、あふれた要求は拒否する。理由は明快だ。原文の表現では、注文を一つ多く確保しようとしたせいでカーネルの OOM キラーが注文マッチングエンジン全体を殺し、残りの100万件を失わせるかもしれず、さらに悪ければ監督プロセスまで殺されて再起動すらできなくなる。

二つめの習慣が一定の作業量だ。生きている項目だけをインデックスやビットセットで別に追いかけるのではなく、固定長配列の全体をつねに回る。空いている場所には何もしない中立な状態を置く。原文の例では注文のタグが bid、ask、reserved の三つの値を取り、最後のものがその中立状態にあたる。

原文が実際に言っていること原文にないこと
起動時に上限のぶんを確保し、超過した要求は拒否するその上限を何を根拠に算定するのか
全部を回る走査のほうがベクトル化にもキャッシュのプリフェッチにもはるかに有利だその主張を裏づける測定値やベンチマーク
P100 レイテンシが負荷と無関係に平らになるP99 や中央値など他のパーセンタイルへの言及
オブジェクトプールとは、そのスロットに今どの世代のオブジェクトが住んでいるかをタグに持つタグ付き共用体だアリーナアロケータ、リングバッファ
型ごとに区画を分けた確保は型混同を緩和するが、インライン列挙型がその防御を壊すオーディオコールバック、ゲームのフレーム、制御ループといった応用例
これは武器庫に持っておく価値のある一つの手であって、あらゆる問題への万能解ではない電力やバッテリーの費用

ここで一つ押さえておくべきことがある。原文が平らになると書いたのはP99 ではなく P100 だ。P99 は最も遅い1パーセントを捨てたあとの最大値で、P100 は何も捨てていない本当の最大値である。要約を経るとこの区別はぼやけやすいが、次節で見るとおり締め切りのある仕事ではその1パーセントこそが問題になる1パーセントなのだ。

締め切りのある仕事とない仕事

一定であることがなぜ目標になるのかは、仕事の種類を先に分けないと見えてこない。基準は一つだ。決められた時刻までに結果が出なければ、その結果が無価値になるか。そうなら締め切りのある仕事で、そうでなければない仕事である。

締め切りのある側の典型は、オーディオコールバック、ゲームのフレーム、そして機械を動かす制御ループだ。オーディオデバイスは次のバッファを決まった時刻に要求し、そのときデータがなければ無音が入って音が途切れる。過ぎ去った時刻の音はあとで作っても意味がない。遅れた結果の価値がゼロかマイナスなのだ。この軸は原文にない。原文は締め切りという語も、オーディオやゲームも持ち出さない。

ただしこの性質を OS 側のドキュメントは昔から書き残している。Linux の mlockall(2) の説明は、リアルタイムアプリケーションは決定的なタイミングを要求し、スケジューリングと同様にページングが予期しない実行遅延の主要因の一つであると書く。同じ文書はさらに踏み込み、ページフォールトによる遅延を防ごうとするリアルタイムプロセスは時間的にクリティカルな区間に入る前に十分なロック済みスタックページを確保しておくべきであり、そうすれば関数呼び出しでもページフォールトが起きないと書いている。メモリを先に全部取っておくことがなぜ速度ではなく予測可能性の問題なのかが、この二文に収まっている。

/* リアルタイム区間に入る前に現在と将来のマッピングをすべてロックする */
mlockall(MCL_CURRENT | MCL_FUTURE);
問うべきこと締め切りがある締め切りがない
遅れて出た結果の価値ゼロか、むしろ有害遅れても価値は変わらない
遅延の溜まりかた次の周期を押して累積するキューが吸収する
再試行不可能か無意味可能でありふれている
見るべき統計最大値と締め切り超過の回数平均、中央値、スループット
改善の定義超過回数がゼロに収束すること単位時間あたりの処理量が増えること
失敗の見た目音が途切れ、画面がつっかえる少し遅い
余った資源の使い道最悪を下げるためだけに空けておく埋めて処理量を増やす

最後の行が実務でいちばん食い違う場所だ。同じ空き CPU を前にして、締め切りのあるシステムはそれを空けたまま最悪に備え、締め切りのないシステムはそれを埋めて処理量を増やす。二つのチームが同じダッシュボードを見ながら正反対の結論に至る理由がここにある。

平均と最悪はなぜ互いを削るのか

平均を下げる手法の多くは同じ形をしている。費用を今払わずに、まとめてあとで払う。キャッシュがそうで、遅延初期化がそうで、配列を倍々に伸ばす動的拡張がそうで、世代別ガベージコレクションがそうだ。ほとんどの呼び出しがとても安くなり、たまに一回がとても高くなる。合計は減る。最大値は増える。

この取引は平均だけを見るダッシュボードでは構造的に見えない。改善は平均のグラフに現れ、代償はグラフの外にある。だから締め切りのあるシステムのスタイルガイドは、たいていこの点を明示的に釘づけにする。TigerBeetle のスタイルガイドはすべてに上限を置けと書き、その例としてすべてのループとすべてのキューは、無限ループやテールレイテンシのスパイクを防ぐために固定の上限を持たなければならないと書いている。上限のないループと上限のないキューを、テールレイテンシの原因として並べて置いたわけだ。

逆方向も成り立つ。一定の作業量は平均をわざと悪くする。生きている項目が10個しかないのにスロット100個を全部回れば、90回はただ捨てる仕事だ。総作業量が増え、平均が増える。その代わり10個のときと100個のときが同じになる。原文の P100 の一文はまさにこの取引を指している。最悪を下げたのではなく、最悪を常時にして平らにしたのだ。

おまけがもう一つあり、原文はこれを性能上の利点と並べて書いている。性能が足りないという事実が、繁忙期の未明の呼び出しではなくロールアウトの時点で表に出る。負荷がなくても最大負荷と同じ仕事をするからだ。その意味で一定の作業量は、性能の手法というより観測の手法に近い。

実行中のアロケーションをなくすと何が消えるか

「実行中に確保しない」という規則を守ると何が消えるのかを、一つずつ数えたほうがいい。そうすれば自分のシステムにそのうち何個が実際にあったのかも数えられる。

  • 確保の呼び出しそのものが持つ可変費用 — 同じ大きさを要求しても毎回同じ時間で終わるわけではない。ちょうど合う空きブロックがあれば安く、分割や統合が要るなら高く、カーネルから新たにもらうならはるかに高い。実行中の確保がなければこの分布ごと消える
  • アロケータの前で並ぶこと — 複数のスレッドが同じアロケータを同時に叩けば、どこかで順番を決めなければならない。呼ぶことがなければ並ぶこともない
  • ページフォールト — 新しくもらったメモリは最初に触るときカーネルが介入する。さきほどの mlockall(2) の説明がページングを予期しない遅延の主要因と名指ししたのがこの箇所だ。起動時に取って一度ずつ触っておけば、この費用は起動区間に移る
  • ガベージコレクタの介入 — 確保がなければ回収を誘発する圧力もない。ただし GC のある言語ではこの関係がそう単純ではないので §10 で別に見る
  • 断片化が生むテールレイテンシ — 長く走ったプロセスほど大きな連続ブロックを取りにくくなる。この費用は最初はなく数日後に現れるので、短いテスト区間ではほとんど捕まらない
  • use-after-free の一系統 — TigerBeetle のスタイルガイドは静的アロケーションの理由として、性能の予測不可能性とともに use-after-free の回避を挙げる。解放と再確保がなければ、解放済みを指すポインタという概念そのものが縮む

そして一覧にないものがもう一つ消える。失敗の時刻だ。上限のぶんを起動時に取れば、その機械にそれだけの余裕がないときプロセスは起動直後に死ぬ。四日後の午前三時ではなくデプロイ直後に死ぬほうが、ほとんどの場合よい。TigerBeetle のスタイルガイドがすべてのメモリは起動時に静的に確保しなければならず、初期化以降はいかなるメモリも動的に確保したり解放して再確保したりしてはならないと釘を刺した理由の半分はここにある。

一定の作業量は何を裏返すのか

ふつうの感覚では「やることだけをやる」のが美徳だ。生きている項目のリストを別に保ち、そのリストだけを回る。原文はこの感覚を裏返す。配列全体を回り、空いた場所には結果を変えない中立な値を置いておく。

// 原文が勧めないほう - 生きているインデックスだけをたどる
for (orders_active) |order_index| {
    const order = orders[order_index];
    process(order);
}

// 原文が勧めるほう - スロット全部を無条件に回る
for (orders) |order| {
    process(order);
}

原文が挙げる理由は二つだ。上のほうはインデックスを一度読み、その値でもう一度配列を引きにいく、アクセスが二段になる形である。下のほうはメモリを前から後ろへ順に舐める。原文の表現では下のほうがコンパイラがベクトル化するにも、CPU キャッシュがプリフェッチするにもはるかに容易だ。そして生きている個数と無関係に同じ仕事をするので、P100 レイテンシが負荷と無関係に平らになる。

中立状態を置く設計は見た目より厄介だ。正しさが速さより先にくる。

  • 中立な値は結果を変えてはならない。合計なら0、積なら1、最小値の計算なら表現可能な最大値がその席だ
  • 中立スロットが集計に混ざると、プログラムは死なずに静かに間違った値を出す。この種のバグは性能問題よりはるかに長生きする
  • スロットを再利用するには世代を区別しなければならない。原文がオブジェクトプールをスロットに住むオブジェクトの世代をタグに持つタグ付き共用体と見たのはこのためだ。世代を落とすと古い参照が新しいオブジェクトを指す
  • 中立の処理費用が実際の処理費用と同程度のときにだけこの取引は成り立つ。中立がはるかに安ければ全部回るのはただの無駄で、中立のほうが高ければ話にならない
  • 配列がキャッシュに載らない大きさなら全走査はかえって損だ。プリフェッチの利得は連続したメモリを実際に全部使うときに出る
  • 原文は分岐予測を論じていない。分岐が消えるのではなく、中立状態を処理する分岐がループの内側に入ってくるだけである

原文は同じ考え方を、早期リターンのある探索ループにも当てはめる。const item = for (items) |item| { if (predicate(item)) break item; } else null; のように見つけた瞬間に抜ける形は平均には良いが、所要時間がデータに依存する。全部を舐める形はいつでも同じ時間で終わる。これもまた平均を差し出して一定さを買う取引だ。

手法ごとの取引 - 得るもの、失うもの、見る指標

静的アロケーションという言葉の下には、性格のかなり違う手法が束ねられている。それぞれが何を与え何を持っていくのか、そしてちゃんと効いているかを何で確かめるのかまで添えておくと、選ぶときに迷わない。アリーナとリングバッファは原文に出てこない。同じ系統の手法なので並べて置く。

代償1 - 上限をどう決めるのか

静的アロケーションの第一の代償は上限を前もって知らねばならないことだ。原文はこの問題をコードの外に押し出している。上限がコマンドライン引数で入ってくるからだ。それが正解である面もある。上限はコードではなく配置環境に依存する値なので定数で埋め込むべきではない。ただしその値を何を根拠に決めるのかは原文にない。

  • まず物理的な上限を探す。機械のメモリ容量、ファイル記述子の上限、ネットワークキューの深さがそれだ。これより大きい業務的上限は意味がない
  • 次に業務的な上限を探す。同時接続数、未決注文数、開いているセッション数の実測値だ。平均ではなく観測された最大値を見る
  • 観測期間が短ければ最大値はつねに過小評価だ。少なくとも一度の繁忙期が期間の中に入っていなければならない
  • 上限をコードに埋め込まず設定に出す。同じバイナリを大きな機械にも小さな機械にも載せられるべきだ
  • 上限に到達した回数を指標として出す。到達を数えなければ、その値が上限なのかただの大きな数字なのか分からない
  • 上限の一定割合に警報線を別に置く。到達したあとに知るのでは遅い
  • 上限を大きく取ることも無料ではない。最大量をつねに占有するので同じ機械に他のものを載せられなくなる

メモリをロックまでするなら制約がもう一つ加わる。mlockall(2) の文書は、Linux 2.6.9 以降は特権プロセスがロックできる量に制限はなく、RLIMIT_MEMLOCK ソフト上限が非特権プロセスのロック可能量を定めると書く。そして MCL_FUTURE を指定した場合、その後の mmap、sbrk、malloc がロック済みバイト数を許容最大値より増やすことになるなら失敗しうると明記する。上限の設計はアプリケーションの中で完結せず、配置環境の資源上限とかみ合っているという意味だ。

代償2 - あふれたとき何をするのか

第二の代償はもっと重い。上限を超えると優雅に失敗する方法がない。正確に言えば、上限の内側では優雅で、上限の外側では選択肢が五つしかなく、そのどれも「なんとかして全部さばく」ではない。

  • 即座に拒否 — 原文の選択だ。呼び出し側に再試行の方針があってこそ意味があり、なければただの喪失である。拒否は問題をなくしたのではなく呼び出し側に渡しただけだ
  • 待たせる — キューを置いて待たせる。ところがそのキューにも上限が要る。上限のない待ちキューは、いま消した上限をもう一度消したのと同じだ
  • 最も古いものを捨てる — リングバッファでよくある選択だ。最新の状態だけが意味を持つデータ、たとえばセンサ値や画面更新に合う
  • 最も新しいものを捨てる — 順序が意味を持つデータに合う。先に入ったものを守り、後ろを切り落とす
  • 縮退運転 — 精度や機能を落として受け付け続ける。締め切りのあるシステムでいちばんよくある答えであり、その場では遅れた正解より間に合った近似値のほうがよい

動的確保はこの五つのどれも選ばずに「なんとか」を真似る。そしてその真似が尽きる場所に OOM キラーがいる。原文が指摘したとおり、そのとき失うのはあふれた1件ではなく処理中だったすべてであり、最悪の場合は再起動の経路まで一緒に失う。上限を置くという選択の本質は、失敗をなくすことではなく失敗の形を選ぶことだ。

だから実際に決めるべき問いは「拒否するかどうか」ではない。何をいつ捨てるかであり、その答えをコードの中に見える形で書き残すことが静的アロケーションの実質的な利点の一つである。動的に取るコードではこの決定がどこにも書かれておらず、だから誰もレビューしない。

代償3 - 仕事がなくても最大量だけ働く

第三の代償は名前にすでに入っている。一定の作業量とは、負荷がないときも最大負荷と同じ仕事をするという意味だ。これが利点にしか見えないのは、専用機で締め切りを守ることが唯一の目標であるときだけである。

  • バッテリーで動く機器 — アイドルがアイドルでなくなる。画面が消えていても同じループが回る
  • 従量課金の環境 — CPU 時間がそのまま費用だ。平らな最大値を買うために常時最大の料金を払う
  • 共有機 — 自分のアイドル費用が隣のプロセスの遅延になる。隔離がなければ隣人が代わりに払う
  • 発熱制約のある機器 — 常時最大の作業はクロックの低下を招き、そうなると守ろうとしていた締め切りのほうが揺らぐ
  • 専用機で締め切りが唯一の目標のとき — この費用はそもそも見えない。どのみちその CPU で別の仕事をする予定がない

原文には電力やバッテリーの話がない。上の一覧は構造から出てくる代償であり、これを裏づける公開の測定値は確認できていない(§13)。だから自分の環境でアイドル時の CPU 使用率を適用前後で測ってみるほうが確実だ。

やわらげる変種もある。配列全体ではなく毎周期に固定された個数だけ舐め、次の周期に続けるやり方だ。最大値は依然として定数でアイドル費用は減る。その代わり一つの項目が処理されるまでの遅延の上限が配列の大きさに比例して伸びる。締め切りが項目単位なのか周期単位なのかによって、この変種が答えになることもならないこともある。

GC のあるランタイムではどうなるか

実行中に確保しないという規則は手動メモリ管理の言語を前提にしている。ガベージコレクタのあるランタイムでは、確保を減らすだけでコレクタが消えるわけではない。それでも方向は同じで、その理由が Go 公式の GC ガイドに書かれている。GC の CPU 費用は主として確保レートと、メモリを走査するバイトあたりの費用が決める。

ガイドが遅延の原因として並べた五つを見ると、なぜ確保レートがそれほど重要なのかがはっきりする。第一にマークとスイープの遷移時に起きる短い全停止、第二にマーク段階で GC が CPU の25パーセントを取ることによるスケジューリング遅延、第三に高い確保レートに応じてユーザーのゴルーチンが GC の仕事を肩代わりすること、第四にマーク段階でポインタ書き込みに追加作業が付くこと、第五にルートを走査するために実行中のゴルーチンを止めることだ。第三項目が要である。たくさん確保するコードは自分の遅延を自分で作っている。

# GC の介入を目で見るいちばん安い方法
GODEBUG=gctrace=1 ./myserver

上限を置く側にも同じ緊張がある。Go のメモリ上限はソフト上限だ。ガイドの表現ではランタイムはあらゆる状況でこの上限を維持すると保証せず、合理的な範囲の努力だけを約束する。ゆるくした理由も明記されていて、上限を超えることを許す逃げ道を残してこそスラッシングを避けられるからである。実際の仕組みは GC が使える CPU 時間に上限を置くことで、現在およそ50パーセント、窓は 2 * GOMAXPROCS CPU 秒だ。

逃げ道がなければどうなるかも同じ文書が書いている。GOGC を切って上限を下げ続けると、不可能なメモリ上限を守ろうとして GC が絶えず走り、アプリケーションの総所要時間が際限なく伸び始める。そして結論めいた一文が §8 の論旨とぴたりと重なる。多くの場合、際限なく止まっているほうがメモリ不足より悪い。後者ははるかに速い失敗で終わる傾向があるからだ。

まとめるとこうだ。原文が OOM キラーを避けるために上限を硬く置くことと、Go ランタイムが際限のない停止を避けるために上限をゆるく置くことは、同じ問題の両端である。どちらを選んでも「上限に達したとき何をするのか」に答えねばならない事実は変わらない。つまみ自体は単純で、ガイドによればGOGC を倍にするとヒープメモリの負担が倍になり、GC の CPU 費用はおよそ半分になる。メモリと CPU の取引を一本のつまみに露出させたわけだ。道具が占めるメモリを実際に測った話とコネクション上限を誤ったときに起きることは別にまとめてある。

サーバーに移すとき成り立つ部分と成り立たない部分

これらの原則は締め切りの厳しい場所で育った。サーバーや Web バックエンドに移すと、あるものは名前を変えてすでに使われており、あるものはそもそも成り立たない。

原則締め切りの厳しい場所でサーバー・Web バックエンドで
起動時に最大量を確保物理メモリが固定なので自然だインスタンスが増減する環境では一台の最大量がそのまま費用になる。ただし同時処理件数の上限に言い換えればそのまま成り立つ
超過した要求を拒否他に選択肢がないそのまま成り立つ。ロードシェディングという名前ですでに標準的な運用だ
全部を回る走査データ構造が小さくキャッシュに載るほとんど成り立たない。全ユーザー走査のようなものはキャッシュに載らない
P100 を目標に締め切りがあるので当然だリクエスト単位の締め切りが稀で、たいてい P99 や P99.9 が実質の目標になる
実行中の確保をなくす言語がそれを許すランタイムが代わりにやる。確保レートを下げる形で移ってくる
すべてに上限そのまま適用されるそのまま適用される。キューの深さ、コネクションプール、タイムアウト、再試行回数がすべて同じ話だ
中立状態でスロットを埋める配列が小さいので安いほとんど使わない。代わりにあらかじめ作っておいたコネクションやワーカープールが同じ役割をする

いちばんよく移る二行はすべてに上限を置けと超過は拒否せよだ。この二つは言語と無関係で、サーバー側ではすでに別の名前で使われている。コネクションプールの大きさ、キューの深さ、タイムアウト、同時要求数の上限がすべて「すべてに上限」の実例である。TigerBeetle のスタイルガイドが、外部の主体とやり取りする場所では外部イベントに直接反応して処理をするのではなくプログラムが自分のペースで走るようにせよと書いたのも同じ話であり、その理由として単位時間あたりの作業量の上限を維持しやすくなる点を挙げている。

いちばん移らないのは全部を回る走査だ。その利得は連続したメモリを実際に全部使うときに出るのだが、サーバーのデータ構造はたいていキャッシュに載らない。中間にあるのが起動時の最大量確保で、プロセス一つのメモリを固定する形では弾力的な環境では損になりうるが、同時に処理する件数の上限に言い換えればそのまま利得になる。

組み込みでもゲームでもない場所でこの規則を明示的に採用した例もある。ggml のリポジトリはサードパーティ依存なし、実行中のメモリ確保ゼロ、整数量子化のサポートを設計目標として書いている。推論ライブラリが実行中の確保ゼロを目標に掲げる理由は速さの自慢ではなく、どこに載せても同じ形で走ることに近い。ハードウェア側の制約が何を先に決めてしまうのかは推論ハードウェアの分かれ道で、ごく小さな装置に押し込むときの問題は8ドルのマイコンでモデルを走らせた事例で別に扱った。メモリ安全をどこまで言語に任せるかという論争はメモリ安全の絶対主義をめぐる話にまとめてある。

まず何を測るべきか

ここまでが判断の基準で、実際に手を付ける順番は短い。コードを直す前に測るべきものがある。

第1段階 - 締め切りがあるかどうかを決める

このシステムで遅れた結果が無価値になる場所はどこかを文章で書く。書けなければ締め切りはなく、ならばこの記事の手法の大半は要らない。締め切りがあるなら、その時刻と許容できる超過回数を数字で書く。「速くあるべきだ」は締め切りではない。

第2段階 - 最大値を記録する

平均と中央値の隣に最大値と締め切り超過の回数を並べて置く。この二列のないダッシュボードでは §3 の取引が見えない。同時に処理中の件数、キューの深さ、プール占有率の最大値も一緒に残す。上限を決めるときに使う値がまさにこれらだ。

第3段階 - 上限を入れて到達を数える

いちばん大きなデータ構造ひとつにだけ上限を入れ、上限に到達した回数を指標として出す。コードを静的アロケーションに書き換えるのはその次だ。到達回数がゼロなら上限が大きいという意味で、着実に到達するなら上限が小さいか上流が流しすぎているという意味である。この数字ひとつが §7 と §8 の決定の大半を代わりにやってくれる。

確認できなかったこと

  • ハードリアルタイムとソフトリアルタイムを分ける規範的な単一の定義は一次情報で確認できなかった。そのため本文はその用語を使わず、「締め切りがあるか」という機能的な基準だけで分けた
  • 優先度逆転の定義とその回避手法も一次情報で確認できなかったので本文ではまったく使っていない。ロックが締め切りに与える影響はこの記事の範囲外に置いた
  • 原文が挙げるベクトル化とプリフェッチの利得には測定値が付いていない。原文は根拠を示さず構造的な理由だけを書いているので、この記事も倍率を書かなかった
  • オーディオコールバックやゲームのフレームの具体的な締め切り時間の数値は一次情報で確認できなかったので書いていない。締め切りが存在するという性質だけを使った
  • アリーナアロケータについては特定の実装の公式文書を開けなかった。そのため表のアリーナ行は定義から出てくる性質だけを書き、数値は入れていない
  • アロケータの競合が実際にどれだけ遅延を生むのか、断片化が時間とともにテールレイテンシをどれだけ大きくするのかについての公開された測定値は見つけられなかった。本文の記述は構造から出たもので実測ではない
  • 一定の作業量が消費電力に与える影響の測定値も見つけられなかった。§9 の一覧は構造から出てくる代償である
  • TigerBeetle がこれらの規則で実際に得たレイテンシの数値は確認できなかった。引用したのはスタイルガイドの規範的な記述だけだ
