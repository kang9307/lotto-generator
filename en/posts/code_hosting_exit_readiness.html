Introduction: what one clone actually brings

The pull request page will not load. Meanwhile git push works fine in the terminal and git fetch is perfectly healthy. On a day like that, the first thing developers say is usually the same. Should we move?

Before answering, something needs pinning down. What the word move refers to is almost never defined. Moving a repository is one command. Distributed version control was designed that way. The trouble is that of everything a team has accumulated over three years, only the code and the commit log live inside the repository. Eight hundred issues and the discussion attached to them, the review comments explaining why a particular line had to change, the secrets and runners the workflows reference, the installers attached to every tag, forty wiki pages, the team structure defining who can reach what. Lock-in does not sit in the repository. It accumulates around it.

So this is not a comparison of which service is better. It puts the assets down one at a time and grades what comes out mechanically, what comes out with its shape mangled, and what does not come out at all. Get to a state where you can move, and whether you actually move can wait. The general theory of lock-in was covered in layered dependency in AI services and retaining access when storage is outsourced, so it is not repeated here.

1. Outages reveal coupling, not availability

On August 17, 2026 an incident went up on the status page. What deserves attention is not the duration but the list of affected components. Coding assistant, API requests, Git operations, issues, pull requests, pages, webhooks and actions sat on one line together. The preceding days looked similar. On August 13 a webhook incident pulled in Git operations, issues, packages and pull requests, and on August 12 login and release asset downloads wobbled together.

What that list reports is not how often a given company goes down. It is how many separate capabilities your working day is stacked on. If fetching code, reading reviews, running builds, downloading release files and logging in can all fall inside one incident at one provider, that is a coupling problem before it is an availability problem.

One observation from the community thread that day drew the line precisely. While pull requests would not open in the web interface, merges still went through on the command line. The distributed code layer was alive and the collaboration layer stacked on top of it had stopped. That is structure, not coincidence, and that structure is the subject of this article — the layer that survived is the layer that is easy to move.

  • A green status page is not evidence of health. It is information that nothing has been graded yet. User reports generally precede the notice
  • Moving purely for availability usually ends in disappointment. Every service has an incident history, and moving just resets your view of it to zero
  • Conversely, work done to reduce coupling stays valuable wherever you are. It pays off even if you decide not to move

Start with the map. The table below splits each asset by whether it comes out mechanically and what is left behind once it moves. Easier rows sit higher.

One line of summary. The top four rows are fully solved by countermeasures that cost almost nothing, and the bottom five leave losses no matter how well you prepare. Yet the time in these discussions goes to the top. People argue at length about where to keep the mirror and only discover what happened to review comment line positions after the move.

2.1 Code and history are genuinely easy

The brevity of this section is the thesis of the article. In distributed version control the code already sits on everyone laptop, and all that remains is pulling every reference without omission.

# branches, tags and remote refs, all of it
git clone --mirror https://host.example/org/repo.git

# freeze it into one file
cd repo.git
git bundle create ../repo-full.bundle --all

# the wiki is a separate repository
git clone https://host.example/org/repo.wiki.git

Bundles deserve a look. The official documentation names their purpose as full repository backup and moving history without a network. The result is a single file, so it can live anywhere, and it can later be cloned from directly. Incremental bundles carrying only changes since the last one are supported too. That the wiki is a separate repository is also under-known — append the wiki suffix to the repository address and it clones, and pushes to the default branch go live. It is the easiest asset to move and it is almost always missing from backup lists, because it never appears in the repository listing.

3. Issues and discussion - they export, and then there is a catch

The character of the problem changes here. Issues and comments export well through the API. The trouble starts afterward.

The most accurate source is, counterintuitively, the documentation on the receiving side. Import documentation usually spells out what will not arrive. GitLab documents that issues, pull requests, comments, reviews, labels, milestones, wikis, release notes and large file objects all come across. The same document also records the following.

  • Groups and organizations are not migrated. You are importing projects, not an org structure
  • Required status checks do not come across. The documentation says outright that they must be recreated manually
  • Some comments predating 2017 can be dropped due to API constraints, and problems are reported on issues with tens of thousands of comments
  • Pull request references embedded in descriptions are not preserved, because target numbers are not settled at import time

That last line hurts the most in practice. Writing another issue number as a reference inside an issue body is a universal habit. Once numbering restarts on the new instance, those references point at the wrong thing or at nothing. The text is still there, so nothing looks broken. No team fixes three years of discussion by hand.

Read the sending side too. The GitHub migration archive documentation lists issues, pull requests, wikis, releases, comments, reviews, milestones, protected branch settings, deploy keys and active webhooks as migrated, and records that fork relationships, large file objects and external authentication mappings are excluded. Reading what does not come out before what does is the more useful order. The conclusion is simple. Do not put the importer at the center of the plan. It gets used once on moving day and its score depends on someone else implementation. What you control is whether you hold a copy of the raw responses.

4. Review comments - where the shape disappears

This is the most important section, because it is the one asset where the data comes out and the meaning does not.

A single review comment carries more than text. Which line of which file, which side of the diff, where a multi line range starts, which commit it was anchored to, and who the parent is if it is a reply. In field names that is path, line, side, start_line, commit_id, in_reply_to_id, and the context slice stored as diff_hunk.

The key point is that these values assume the diff as it stood at a specific commit. Hence the warning in the documentation to that effect: if a later commit touches the line you specified, the comment is marked outdated. The older position field counted lines below the diff header rather than real file line numbers, and the API is moving toward line. Moving this to another service means reseating those coordinates on that service diff calculation and thread model. When the coordinate systems differ, they do not seat exactly.

  • The comment body survives. Text can go anywhere
  • Which line it hung on gets blurry. The file may survive while line level accuracy is not guaranteed
  • Reply relationships can flatten. Three threads lie down as a list of twelve comments
  • Multi line range selections collapse to a single start line when the target has no equivalent concept
  • Comments on a whole file may have nowhere to land. The archive documentation lists file level comments as excluded

There are only two countermeasures and both must happen before the move. First, always include diff_hunk in the export. With the diff slice present, a human can read the context back even when line numbers drift. Second, promote conclusions instead of leaving them in comments. Write down which rule you settled on and why, in an issue or a document inside the repository, and it survives independently of any coordinate system. A review thread is a volatile medium by nature — a decision that exists only inside one is fragile against time, never mind migration.

5. CI - you are moving coupling, not syntax

The CI configuration file lives inside the repository, so a mirror brings it. That makes it look easy. In practice it is among the most expensive assets to rewrite, because what has to move is not the file but everything the file assumes.

  • External action references. The convenience of calling someone else step in one line holds only inside that ecosystem
  • Tools already present on the runner image. Commands you never installed run because of the runner, and that is not written in the config
  • Secret injection semantics and naming. Values aside, injection timing and scoping rules differ per service
  • Cache keys and artifact retention rules. If they are why the build was half as long, day one after the move it doubles
  • What trigger conditions mean. The definition of when a given event fires differs in subtle ways

The remedy is old and unremarkable. Push the real work down into scripts inside the repository and leave the CI configuration as a thin shell that calls them.

# leave roughly this much in the CI config
steps:
  - run: ./scripts/build.sh
  - run: ./scripts/test.sh
  - run: ./scripts/package.sh

# the test: on a laptop with no network
./scripts/build.sh   # same artifact means portable

One test ends the argument. If the same command on a laptop gives the same result it is portable, and whatever only runs inside the CI interface is bound by that much. Complaints about CI syntax come up constantly in threads, but when the complaint is about syntax it is a symptom of coupling. Move to a service with simpler syntax and, as long as the logic lives in the config file, the next migration bills you the same amount again. Add required status checks to this. Importers document that they do not carry them. The morning after a move, the merge rule may be gone, and a vanished rule leaves no mark on any screen. Writing the rule list into a document is the whole countermeasure and it costs ten minutes.

6. Releases, wikis, permissions - each leaks differently

Binaries attached to releases can be listed and fetched individually through the API. You query the asset list by release identifier, then take each asset either through the browser download URL or by switching the request header to accept a binary stream. The documentation notes that the response may arrive as a redirect, so clients should handle both cases.

None of that is technically hard. The real problem is the address. A download URL contains the host name, and for the last five years other people have been embedding that URL in documents, scripts and install instructions. Move hosting and the files follow, but every one of those links dies. If you ship artifacts, it is better to keep a stable download path under your own domain and publish that one. Whatever it points at behind the scenes, the address the outside world sees never changes.

Permissions are a different character again. This is the stretch where the remaining work is human rather than mechanical.

  • Teams and organizations are in the archive but external authentication mappings are excluded. If you tied it to an identity provider, that connection is rebuilt
  • The importing side also states that groups and organizations are not migrated. Role names and permission granularity differ enough that some stretch will never map one to one
  • In the end account matching is done by people. Forty people is a day, four hundred is a project. The countermeasure is a permissions structure written into a file in the repository
  • Fork relationships are not migrated, and the documentation is blunt about it. There is no countermeasure, so accept it. For open source the loss is large, since contribution flow itself stands on forks

7. Keeping the names on your side

This is the cheapest and longest lasting countermeasure of the lot. And it is usually done far too late.

For projects that publish packages, the name is often the address. Go modules are the clearest case. The official documentation defines a module path as the canonical name for a module and notes that the path is used to locate the repository, and the leading element is by convention a domain name. Which means that if the hosting address is your module path, the moment you move, every import statement in the world is wrong. The fix is an old practice. Use your own domain as the module path and let that domain point at the actual repository. The same principle holds in other language ecosystems — you only need to check where ownership of the name lives.

  • Domain. Gather the docs site, download paths and issue tracker pointers under your own domain. What is behind can change while the front does not
  • Package namespace. Claim a scope under the organization name early. A name tied to a personal account is hard to move along later
  • Import paths. Check whether a host name is baked into the code. If it is, that is the strongest lock-in you have
  • Mail addresses and commit signatures. If you have been committing under an address the host issued, author identity in the history is bound to that service

All four are worth doing now even with no plan to move. They cost close to nothing, and later on the already published surface makes them impossible.

8. Running scheduled exports for real

Compress everything above into one task and it becomes scheduled export. Not a one time backup but something that runs periodically, and above all something you occasionally restore from for real.

TargetCadenceFormatCost
Repository mirrorDailyClone with every referenceNear zero
Bundle snapshotWeeklyA single fileNear zero
WikiDailySeparate repository mirrorNear zero
Issues, PRs, commentsWeeklyRaw API responses as they areLow
Review commentsWeeklyDiff hunk includedLow
Release assetsEvery releaseBinaries and checksumsLow
Permissions and check rulesMonthlyA table a human readsLow
Restore rehearsalTwice a yearActually load it into an empty instanceMedium

Only the last row costs anything meaningful, and the rest is one set of scripts plus a scheduler. Yet half the actual value sits in that last row. A backup nobody has restored from is a file named backup. Twice a year, push the mirror into an empty instance and recreate a handful of items from the issue snapshot, and everything that does not work shows up that day.

One common mistake. Run the export inside your CI and, on the day that CI stops, the export stops with it. And that is exactly the day you needed it. The scheduler belongs outside the thing you are preparing to leave.

9. What self hosting bills you for

By this point self hosting starts to look like the conclusion. Regaining control is real. But the cost moves rather than disappears. Laying out where it goes makes the judgment easier.

ItemWhen outsourcedWhen you run it
Security patchesHandled by the providerYour schedule. Long-running operators describe close to weekly work
AvailabilityProvider responsibility. You waitYour pager. The 3 AM alert rings your phone
UpgradesMostly automaticYour plan. You negotiate downtime with the team
Backup and restoreProvider copy plus your copyAll yours. Restore verification included
Spam and abuseThe providerOn a public instance this becomes standing work
Contributor inflowYou ride a large networkYou build it yourself. The most expensive item
ControlLowHigh. This is what you are paying for

The bottom two rows are where the decision lives. Community effects do not migrate. The threads made the point repeatedly — accounts of projects that moved and saw contribution fall off, and of an ecosystem that lives in one place so thoroughly that one person leaving accomplishes nothing. It is a question of where people look, so picking a better tool does not solve it.

So this framing tends to hold. The legitimate reasons for self hosting are regulatory requirements, internal network access, data control and cost structure. Availability and portability are not on that list. Portability is far cheaper to secure through scheduled exports and scripting wherever you are, and self hosting without exports is just one more single point with no backup. Over the last two days the names traded in threads spanned self installed, managed, federated and peer to peer options. Which is better is not this article business. But having options and being able to move are different problems, and this article is about the second.

Conclusion: three things to take today

First, readiness is judged by a list, not by a repository copy. The code is already safe. What is at risk is issue numbers drifting, review coordinates blurring, merge rules disappearing without a sound, and release links dying. Writing that list takes thirty minutes, and once written it decides what to prepare on its own.

Second, the four cheapest countermeasures fit inside today. Mirror copies of repository and wiki, raw snapshots of issues and review comments, CI logic pushed down into scripts, and domain and namespace on your side. All four pay off even with no plan to move, and all four get more expensive later. The last one in particular is effectively impossible once distribution has spread.

Third, an outage is a signal to count, not a signal to move. If one incident catches code and reviews and builds and deploys and login together, the issue is not that provider uptime but how many strands of your day are tied to one place. That untangling survives a decision not to move. The purpose of portability is not migration but having options, and with options you never have to decide in a hurry.
