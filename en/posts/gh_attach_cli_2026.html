gh-attach and GitHub's Missing Attachment API - What the CLI Workaround Really Does

A CLI tool that borrows a browser session to attach files to issues and PRs - what it bypasses, where it helps, and where it breaks

Jul 9, 2026 Dev & Infra

Introduction: A Feature That Lives Entirely Inside a Drag-and-Drop

You might ask what's so hard about attaching a screenshot to a GitHub issue or PR. Just drag an image into the comment box in your browser and you're done. But that "drag it and drop it" is, for all practical purposes, the only front door into this feature. As of July 2026, GitHub still offers no official REST or GraphQL API for uploading a file to an issue, PR, or comment. It's a door that only opens when a human sits in front of a browser and moves a mouse.

In a world where CLIs create issues, bots leave deployment logs as comments, and AI agents open their own PRs, that door is an obvious bottleneck. gh-attach doesn't try to break the door down - it goes around it. It was featured on GeekNews and drew a round of "I needed exactly this." Rather than repeating that reaction, this piece looks at what the tool actually bypasses, what it's worth in automation workflows, and how far you should trust it.

1. The Real Problem - Why There's No Attachment API

1.1 What Drag-and-Drop Actually Does

When you drop an image into the issue or PR comment box in a browser, the front-end code immediately sends a request to github.com/upload/policies/assets. That request only succeeds if it carries a user_session cookie - a logged-in browser session. With the issued upload policy, the file is pushed into an internal asset pipeline (storage plus CDN), and once complete, a link shaped like github.com/user-attachments/assets/{uuid} is inserted into the comment body. That's the origin of every image link you've ever seen in a GitHub issue.

1.2 A Request Repeated for Nearly Six Years

The catch is that this whole flow is session-cookie based, start to finish. There's no equivalent endpoint in the token- or OAuth-authenticated REST and GraphQL APIs. GitHub Community discussions have repeatedly asked for "an API to upload images to comments," and one issue in the gh CLI repository reframed the gap as "critical for agentic workflows," making the point that an agent can write a flawless issue body but still can't attach the screenshot that makes it actionable. That lineage of requests traces back to 2020-2021, and the issue itself was closed as a duplicate of an even older one. In other words, the same ask has been repeated for nearly six years, and there's still no official API.

2. What gh-attach Actually Bypasses

2.1 Borrowing a Session the Browser Already Has

The core idea behind sudosubin/gh-attach (written in Go, MIT licensed) is simple: let the CLI borrow the login session the browser already holds. It first checks the currently authenticated GitHub account and target repository via gh api. Then it searches the cookie stores of locally installed Chromium-family, Firefox-family, and Safari browsers for a session whose dotcom_user cookie matches that account.

2.2 Uploading Exactly the Way the Browser Does

Once a session is found, it uses those cookies to request an upload policy from /upload/policies/assets, uploads the file binary, and finalizes the asset. This is a faithful re-implementation, in code, of the exact steps the browser performs during a drag-and-drop.

2.3 The Same Output You'd Get From the Web UI

The resulting URL is shaped like github.com/user-attachments/assets/{uuid} - the exact same kind of link a person gets from manually dragging an image in. A single line, gh attach ./image.png -R owner/repo, returns that URL so you can drop it straight into an issue or PR body. A --json flag lets scripts parse the output, and --template lets you chain it into other commands. Browser and profile selection can be saved once in a ~/.config/gh/attach.yml config file so you don't have to repeat it.

3. The Value in CLI and Automation Workflows

3.1 Bots That Auto-Attach Screenshots and Logs

The most direct use case is a bot that leaves deployment failure logs, visual-regression screenshots, or performance graphs on an issue or PR without a human in the loop. Where the old flow was CI leaves an artifact, then a human reopens it and pastes a capture, gh-attach removes the manual step in between.

3.2 When an Agent Opens Its Own PR

As AI coding agents increasingly edit files and open their own PRs, there's a real desire to attach a screenshot or diagram showing what actually changed. The creator of gh-attach has in fact said the tool was built so agents could automatically attach diagrams and screenshots. A PR description that's text-only and one that visually shows what changed are entirely different experiences for a reviewer.

3.3 Its Place in the gh CLI Extension Ecosystem

gh-attach is a gh CLI extension installed with a single gh extension install owner/repo. GitHub officially documents and supports this extension mechanism, and anyone can publish a repository named gh-something. What's notable is that gh-attach isn't the only extension solving this problem - several independently authored implementations with overlapping names exist (for example, enthus-appdev/gh-attach, and Addono/gh-attach, which also doubles as an MCP server). That's evidence the bottleneck is common enough that multiple developers hit it independently - and also a sign that no industry "standard" has emerged yet.

4. The Risks of Depending on an Unofficial Endpoint

4.1 An Automation Tool That Doesn't Quite Fit Automated Environments

The first limitation worth naming is this: gh-attach is marketed around "agent and bot automation," yet its mechanism assumes a logged-in browser session. Most CI runners and agent sandboxes simply don't have one. To use it as-is in an automated pipeline, you need to provision an authenticated browser profile in that environment ahead of time, or copy a session into a headless browser. The picture of "a bot that just attaches a screenshot on its own" only holds once that groundwork is done - and that's exactly where people who mistake this for a fully automatic tool tend to trip.

4.2 A Contract That Can Break at Any Time

/upload/policies/assets is not an API GitHub documents or versions officially - it's an internal endpoint meant for its own web front end. If GitHub changes the upload flow, this can stop working without warning. That's a debt every scraping-style tool carries, and discussions around this gap explicitly frame this kind of workaround as a stopgap, with securing an official API left as the long-term goal.

4.3 The Weight of Reading Cookies

Reading a local browser's cookie store isn't a trivial thing to do. Some operating systems require access to a keychain or credential manager, and some browsers encrypt cookies at the OS level. Even for a trusted open-source tool, installing a CLI that reaches into your login session cookies is, on its own, a decision that widens your security surface - and that should be recognized plainly.

5. Comparing It With Official Workarounds

The GitHub CLI community is well aware of this gap. Alongside gh-attach's session-based bypass, two token-only alternatives have been discussed.

My own read is this: for a one-off manual attachment, gh-attach is the most natural fit. For an always-on CI bot that habitually leaves logs, a release asset is operationally safer since it carries no session-management burden. I'd treat the orphan-branch approach as a compromise for the cases that satisfy neither condition well.

Conclusion: gh-attach Is a Stopgap, Not the Final Answer

gh-attach is a genuinely good stopgap. Until GitHub ships an official attachment API for issues and PRs, this kind of session-bypass tool is structurally bound to keep appearing - and the fact that multiple independent implementations with overlapping names already exist is itself proof of the demand. If you just want to attach a screenshot from the CLI today, gh-attach is enough.

But keep two things in mind: bolting it onto a CI or agent pipeline leaves you with the homework of provisioning a session, and the endpoint it stands on is an unofficial contract that GitHub can retire at any time. The real fix is for GitHub to ship an official upload API that works with a token alone. Until then, it's most accurate to see gh-attach as one of several experiments filling that gap.
