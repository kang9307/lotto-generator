子プロセスが止まる本当の理由 - パイプバッファが満杯になって起きるデッドロック

小さな入力では通り、実データでだけ止まる - 境界値をバイト単位で測定した記録

2026-07-30 開発/インフラ

序論: 何のメッセージも無いまま止まっていた

夜間バッチを回しておいて朝に見ると、スクリプトがどこかで止まっている。エラーメッセージが無い。例外の追跡も無い。プロセスは一覧にそのまま残っており、CPU使用率は0パーセントだ。ログの最後の行は数時間前の時刻のままである。もう一度回すと同じ場所でまた止まる。ところが昨日、短い標本で回したときは5秒で終わっていた。

この状況では大半の時間が間違った場所で消費される。ロジックを読み直し、ログを増やし、ロックやネットワークを疑い始める。しかしコードには何の問題も無い。原因はコードではなくパイプのバッファの大きさであり、それはソースのどこにも書かれていない数字だ。だからいくらコードを読んでも見えない。

この記事はその数字を自分で測り、その数字が作る境界をバイト単位で確認した記録である。結論を先にまとめると三つの文になる。

  • パイプは有限のバッファである。 無限の通路ではなく決まった大きさの箱であり、この環境では4096バイトだった
  • 満杯になれば書く側は待つ。これはバグではなくフロー制御だ。 後段が遅くてもパイプラインは正常に完了する。待機そのものは正常である
  • デッドロックは読むべき人がすでに別のものを待っているときに起きる。 つまり問題の形は常に「双方が相手を待つ構造」だ

そしてこの構造が本当に怖い理由は最後の一つにある。出力がバッファより小さければ何も起こらない。 単体テストが使う標本はほぼ常にバッファより小さい。だからこの欠陥はすべてのテストを通過し、運用で実データに出会う初日にだけ現れる。

実行環境。 以下のすべての出力はWindows 10 Pro (10.0.19045)で実際に実行した結果である。シェルはGNU bash 5.2.37 (MSYS2 / MINGW64)、ランタイムはPython 3.13.3 (win32)とNode.js v22.16.0 (win32)だ。スクリプトはすべてファイルに保存して実行し、デッドロックを再現する実験なのですべての実行に10秒以内のタイムアウトを掛けた。 タイムアウトに掛かったものは「デッドロック確認」として記録した。

★バッファ容量は環境ごとに異なる。 以下の数値はこの環境の実測値であり、別のオペレーティングシステム・シェル・ランタイムでは違う値が出る。実際、同じ機械の中でも経路によって三つの異なる値が出た。だからこの記事は数字を覚えろとは言わず、測る方法を示す。例示の経路は/tmp/demoのようなプレースホルダで書いた。

この記事が扱わないこと。 パイプラインの終了コードの規約とステータス配列、パイプの失敗に気づく方法は終了コードとパイプですでに扱った。ここではバッファが満杯になって起きるデッドロックの一点だけに集中する。ファイル名に空白が混ざってパイプラインが壊れる問題はfindとxargsの空白の罠、引用規則はシェルの引用規則にある。

1. パイプは有限のバッファ - この環境では4096バイト

まず容量を自分で測らなければならない。パイプを一つ作り、読む側には触れないまま書き込みだけを続けた。どこかで書き込みが戻らなくなれば、それが容量である。無限待機に陥らないよう、書き込みは別スレッドに置いて5秒後に状態を確認した。

python 3.13.3 / win32
--- 1-1. raw os.pipe() capacity: write until it blocks ---
  writer thread is STILL BLOCKED after 5.0s  <- pipe is full
  bytes accepted before blocking : 4096

--- 1-2. same measurement, 1 byte at a time (exact) ---
  blocked after exactly 4096 bytes

--- 1-3. drain the pipe, does the writer resume? ---
  read 4608 bytes from the read end
  writer counter is now 8704 (was 8704)

--- 1-4. subprocess stdin pipe: child never reads ---
  parent is BLOCKED writing to a child that never reads
  bytes accepted : 4096
  child killed, test over

三つを読み取る必要がある。第一に、正確に4096バイトだ。512バイト単位で測っても4096、1バイト単位で測っても4096だった。概数ではなくきっちりした値である。第二に、書き込みスレッドは死なずに待機した。 エラーではなく待機だという点が核心だ。第三に、読む側から4608バイトを取り出すと書き込みがそのまま再開した。 カウンタが8704まで上がった。

この最後の観察がこの記事の前提を立てる。パイプが満杯で書く側が待つのは故障ではない。 空きが出れば自動で続く。POSIX規格も同じことを言っている。ノンブロックのフラグが立っていなければ「書き込み要求がスレッドをブロックさせうるが、正常完了時には要求したバイト数を返す」と書かれている。つまり設計された動作である。

1-4は方向だけ変えた同じ実験だ。子プロセスを起動して標準入力をパイプで開き、子が何も読まないようにした。親が書き込めた量も同じ4096バイトだった。パイプはどちらの向きに書いても同じ箱である。

1.1 同じ機械で値が三つに分かれた

ただしここで気をつけることがある。この4096という値はこの経路でだけ出た値だ。同じ機械で別の経路を測ってみると全部違った。

階層この環境の実測測る方法性格
ネイティブWindows匿名パイプ4096 B読まないパイプに1バイトずつ書くオペレーティングシステムのカーネルバッファ
MSYS2シェルパイプ65536 B後段が眠っているパイプラインに書くシェルランタイムが作るパイプ

Python stdio出力バッファ8192 Bランタイム定数を照会パイプとは無関係の別の層

表の最後の二行が特に重要だ。Nodeの停止境界131073バイトはオペレーティングシステムのパイプ容量でもストリームの水位表示でもない。 二つの値の単純な和でもない。複数の層が重なって作った結果値であり、その内部の会計を正確に確認できなかった。だからこの数字は測定値としてのみ示し、公式として一般化しない。

  • 皆さんの環境の値はここに書かれたどの数字とも違いうる。 LinuxとWindows、シェルの種類、ランタイムのバージョンがすべて変数だ
  • だから実務的に有用なのは数字ではなく測る手順である。1-1の実験は十行あれば再現できる
  • より重要なのは開発環境と運用環境の値が違いうることだ。開発で通って運用でだけ止まる二つ目の理由がここにある
  • コンテナの内外、ローカルとCI、シェルを経由する実行と直接実行はすべて別の経路だ。一つで通ったことが別の一つを保証しない

2. デッドロックの再現 - 4096と4097の間

ここから実際の事故の形を作る。最もよくある誤ったコードはこの順序だ。子を起動し、先に待機し、その後で出力を読む。 読む前に待ったという点が罠のすべてである。

python 3.13.3 / win32

--- 2-1. parent calls wait() first: small vs large output ---
  child writes     1024 B -> wait(3s) : finished (0.10s)
  child writes     4096 B -> wait(3s) : finished (0.10s)
  child writes     4097 B -> wait(3s) : DEADLOCK (2.01s)
  child writes     8192 B -> wait(3s) : DEADLOCK (2.02s)
  child writes    65536 B -> wait(3s) : DEADLOCK (2.01s)
  child writes  1048576 B -> wait(3s) : DEADLOCK (2.01s)

--- 2-2. bisect the exact boundary ---
  largest output that does NOT deadlock : 4096 bytes
  smallest output that DOES deadlock    : 4097 bytes
  probes                                : 13

この表がこの記事の心臓だ。4096バイトは0.10秒で終わり、4097バイトは永久待機に入る。 コードは一文字も違わない。子が書くバイト数が1バイト増えただけである。

DEADLOCKの表示は「タイムアウトに掛かった」という意味だ。待機呼び出しに2秒の上限を置き、上限を超えればデッドロックと判定した。上限なしで回すとこの実験自体が終わらない。デッドロックを扱う実験には必ずタイムアウトを掛けなければならないというのが最初の実務的教訓である。

二分探索で13回突いて境界を確定した。通る最大値が4096、止まる最小値が4097。この値は1節で測ったパイプ容量と正確に同じだ。 偶然ではなく、それが原因だという証拠である。

2.1 なぜ止まるのか - 二つの文で

構造は単純だ。子はパイプに空きが出るのを待つ。親は子が終わるのを待つ。空きを作れるのは親だけなのに親は待機中だ。子を終わらせられるのは書き込みの完了だけなのにそれが塞がっている。互いが相手の次の行動を待つ円が閉じた。

  • 出力が4096バイト以下なら子は全部書き込んでそのまま終了する。 パイプにデータが残っていても子はすでにいない。だから待機がすぐ戻る
  • 出力が4097バイトなら最後の1バイトを書けず子が終了できない。 待機は永遠に戻らない
  • この差はどこにもログとして残らない。 例外も無くエラーコードも無い。二つのプロセスが静かに互いを待つ
  • だから症状が「停止」なのだ。「失敗」ではなく何も起こらないことであり、これが診断を難しくする

Pythonの公式文書はこの危険を明示している。待機呼び出しの説明に「標準出力または標準エラーにパイプを使い、子がオペレーティングシステムのパイプバッファがさらに受け取るまでブロックするほど十分な出力を生成すると、この呼び出しはデッドロックに陥る」と書かれている。文書に書かれたそのままが実測で再現されたわけだ。

3. なぜテストは通るのか

2節の境界がこの欠陥の性質を決める。4096バイトは何でもない大きさだ。 テキストならおよそ2000文字、ログなら40行から50行である。単体テストに入れる標本がこれより大きいことは稀だ。

状況出力の大きさこの環境では結果
単体テストの短い標本数百 Bバッファの中に全部入る通過
手で確認した例示ファイル1〜2 KBバッファの中に全部入る通過
境界のすぐ手前4096 B正確に満杯の状態通過 (0.10秒)
境界を1バイト超過4097 B最後の書き込みが塞がる永久待機
運用データ1件数十 KBとっくに塞がっている永久待機
エラーが多く出た日数 MB標準エラーで塞がる永久待機

表の最後の行が実務では特に悪質だ。普段はうまく回っていたバッチが、よりによってエラーが多く出た日に止まる。 警告ログが増えて標準エラーの出力がバッファを超えたのだが、外からは「障害が起きたらバッチまで止まった」と見える。原因と結果が逆転したまま調査が始まる。

  • この欠陥は再現が容易だ。 標本の大きさを増やせば100パーセント再現する。問題は誰もその試みをしないことである
  • 逆に小さい標本では絶対に再現しない。 だから「自分の環境ではうまくいくのに」が成り立つ
  • したがってテスト標本にバッファ容量より大きいものを一つ入れることが最も安上がりな防御だ。1節の方法で容量を測り、それより大きい標本を作ればよい
  • さらに良いのは大きさと無関係に安全な構造にコードを変えることだ。4節からがその話である

4. 解決① 先に読み、その後で待つ

最も単純な解決は順序をひっくり返すことだ。出力を全部読んでパイプを空にしてから待つ。

--- 2-3. FIX A: read the output first, then wait ---
  read 1048576 bytes, then wait() returned 0 in 0.09s

--- 2-4. FIX A': communicate() does the same thing for you ---
  communicate() -> 1048576 bytes, rc=0, 0.10s

2節で永久待機に陥らせた同じ1048576バイトが0.09秒で終わった。変えたのは二行の順序だけだ。読んでいる間パイプが空き続けるので子が塞がることが無く、子が終わればストリームが閉じて読み取りも終わる。

2-4はその仕事をしてくれる標準関数を使ったものだ。Pythonの文書は「他のオペレーティングシステムのパイプバッファが満杯になって子がブロックするデッドロックを避けるには、直接の書き込み・読み取りではなく統合関数を使え」と勧めている。ただし文書は代償も併記している。「読み取ったデータはメモリにバッファリングされるので、データの大きさが大きい、または無限であればこのメソッドを使うな」というものだ。実際に確かめるとその代償が目に見える。

--- 9-4. streaming a huge output line by line: constant memory ---
  streamed 200000 lines in 0.31s, largest object held = 12 chars

--- 9-5. the same data via communicate(): held entirely in memory ---
  communicate() -> one object of 2600000 bytes (2.5 MB) in 0.53s

同じ20万行を二つの方式で受け取った。一行ずつストリーミングするとどの瞬間にも12文字のオブジェクト一つだけを持っていた。統合関数を使うと2.5メガバイトのオブジェクト一つがメモリに載る。20万行は小さいほうだ。出力の上限が無い子であれば、この方式はいつかメモリで破裂する。

  • 出力の上限が確実で小さいなら統合関数が最も安全で短い。上限をコードのコメントに書いておけばなお良い
  • 上限が無いならストリーミングかファイルで受けなければならない。統合関数はデッドロックは防ぐがメモリの問題を残す
  • ストリーミングはメモリ上限が一行という点で構造的に優れている。20万行が0.31秒で処理された
  • ただしストリーミングは子の出力バッファリングの影響を受ける。 9節で扱う

5. 最もよくかかる罠 - 二つのパイプ、一人の読み手

ここまではパイプが一つだった。実務のコードはたいてい標準出力と標準エラーを両方パイプで開く。エラーメッセージも捕まえたいので当然の選択だ。ところが読むコードはたいてい一つしかない。ここでパイプが二つなのに読み手が一人になる。

--- 2-5. the classic trap: stdout AND stderr piped, only stdout read ---
  stdout.read() has NOT returned after 4.0s -> DEADLOCK
  child alive : True   (it is blocked writing stderr)

子は標準エラーに200000バイトを書き、標準出力には10バイトしか書かない。親は標準出力だけを読む。標準出力は10バイトしか無いのに読み取りが終わらなかった。 4秒待っても戻らず、子は生きていた。

この場合が特に悪質な理由は自分が読んでいるストリームには何の問題も無いという点だ。標準出力は10バイト、バッファの400分の1である。コードをいくら見ても「出力が大きくて塞がった」という絵が出てこない。塞がっている場所は自分が開いておいて見ていない別のパイプだ。

Nodeでも同じように再現された。そしてNodeには層が一つ多いので境界値がはるかに大きい。

node v22.16.0 / win32 / 10.0.19045

--- 4-1. spawn, never touch child.stdout, wait for close ---
  child writes     1024 B: close fired, code=0 (93 ms)
  child writes     4096 B: close fired, code=0 (92 ms)
  child writes    65536 B: close fired, code=0 (95 ms)
  child writes  1048576 B: TIMEOUT after 2500 ms -> DEADLOCK

--- 4-2. exact boundary for the paused-stream case (bisect) ---
  largest output that does NOT hang : 131072 B
  smallest output that DOES hang    : 131073 B
  probes: 18

--- 4-5. stdout AND stderr piped, only stdout consumed ---
  only stdout consumed: TIMEOUT after 3000 ms -> DEADLOCK

注目すべきは65536バイトが通過した点だ。Pythonならとっくに塞がっている大きさである。Nodeはオペレーティングシステムのパイプから読んだデータを自分のストリームバッファに溜めるので、より長く耐える。つまりNodeではこの欠陥がより遅く、より大きなデータでだけ表面化する。 良い知らせではない。開発中に発見される確率がそれだけ低いという意味だ。

Nodeの公式文書はこの状況を正確に記述している。「既定では親のNodeプロセスと生成された子の間に標準入力・出力・エラーのパイプが作られる。これらのパイプは限られた、そしてプラットフォームごとに異なる容量を持つ。子が出力をキャプチャされない状態でその限界を超えて書くと、子はパイプバッファがさらに受け取るまで待ってブロックする」と書かれている。「プラットフォームごとに異なる容量」という表現が1節の表をそのまま説明している。

6. 解決② 同時に読む、③ ファイルで受ける、④ 一つに統合する

二つのパイプの問題の解決は三方向だ。三つとも実行して確認した。

--- 2-6. FIX B: read stderr concurrently in a thread ---
  stdout 10 B, stderr 200000 B, rc=0, 0.10s -> no deadlock

--- 2-7. FIX B': communicate() reads both streams at once ---
  communicate() -> stdout 10 B, stderr 200000 B, rc=0, 0.20s

--- 2-8. FIX C: give the child a real file instead of a pipe ---
  wait() first with files: rc=0 in 0.10s
  out.tmp 10 B, err.tmp 200000 B

--- 2-9. FIX D: merge stderr into stdout (one pipe, one reader) ---
  merged read 200010 B, rc=0, 0.09s
  first 4 bytes b'EEEE'  last 4 bytes b'OOOO'
  count O=10  E=200000

解決② 同時に読む。 標準エラーを読むスレッドを別に立て、本スレッドは標準出力を読んだ。4秒を超えても終わらなかったものが0.10秒で終わった。非同期ランタイムならスレッドの代わりに同時待機で同じことをする。原則は一つだ。パイプで開いたストリームの数だけ読む主体がいなければならない。

解決③ ファイルで受ける。 2-8が興味深い。出力を一時ファイルで受けると先に待機しても安全だ。 2節で永久待機を作ったあの順序なのに、今回は0.10秒で終わった。理由は明確である。通常のファイルには「満杯」という状態が無い。 パイプは固定の大きさの箱だが、ファイルはディスクが許す限り大きくなる。だから書く側が待つ理由が無く、デッドロックの前提そのものが消える。

解決④ 一つに統合する。 標準エラーを標準出力に統合すればパイプが一つになるので読み手一人で足りる。200010バイトを0.09秒で全部受け取った。ところが出力の先頭4バイトがEEEEで、末尾4バイトがOOOOだ。子は標準出力を先に書いたのに、結果では標準エラーが先に来た。順序がひっくり返った。

6.1 統合の代償 - 順序が混ざる

この現象を短い例でもう一度確認した。子が標準出力と標準エラーを交互に三回ずつ書くようにした。

--- 2-10. the price of merging: ordering gets scrambled ---
  merged (default buffering):
    ERR-0
    ERR-1
    ERR-2
    OUT-0
    OUT-1
    OUT-2
  merged (PYTHONUNBUFFERED=1):
    OUT-0
    ERR-0
    OUT-1
    ERR-1
    OUT-2
    ERR-2
  same bytes? False

子が書いた実際の順序はOUT-0、ERR-0、OUT-1、ERR-1、OUT-2、ERR-2だ。既定の設定で統合したときは標準エラーの三行が先に出て標準出力の三行が後に出た。まったく別の話として読める。

原因はパイプではなくプログラム自身の出力バッファだ。標準エラーはたいていバッファリングせず即座に送り出し、標準出力はパイプに接続されるとブロックバッファに切り替わって終了時点で一度に出ていく。だから時間の順序が並べ替えられる。無バッファのスイッチを入れると実際の順序がそのまま復元された。

  • 順序が重要なログを統合してはいけない。 進捗とエラーを時間順に読まなければならない状況でこれは致命的だ
  • 統合が楽なのは順序を見ない場合である。失敗時に全体の出力を塊で保存しておく用途なら問題無い
  • 順序も守りパイプも一つにしたいなら子を無バッファで動かさなければならない。 上の出力の二番目のブロックがそれだ
  • 統合しておいて後から「標準エラーだけ選り分ける」ことは不可能だ。統合した瞬間に出所の情報が消える

Node側の解決も対称的に確認した。

  4 MB with a data listener: close code=0, read 4194304 B (100 ms)

--- 4-4. FIX: resume() alone is enough (discard the data) ---

7. シェルのパイプライン - フロー制御はバグではない

付け加える観察が一つある。同じ状況でネイティブなWindowsのプログラムを前段に置くと、合図の代わりに書き込みエラーが出た。終了コードは1で、エラーメッセージは無効な引数を意味するものだった。つまり「読む側が消えた」という事実が伝わる方式さえ環境によって違う。 終了コードで原因を特定したいなら自分の環境でまず確認しなければならない。

8. バッファは一層ではない

ここまでパイプバッファだけを話してきたが、実際には層がもう一つある。プログラム自身の出力バッファだ。この二つはまったく別物であり、混ぜて考えると診断がずれる。

--- 5-1. what Python says about its own stdout buffering ---

ここで二つの層の違いを整理しておく必要がある。

この表が診断で重要な理由は二つの層の症状が違うところにある。出力バッファは遅延を作り、パイプバッファは停止を作る。「ログが遅く出る」と「プロセスが止まった」は別の問題であり解決も違う。

10. 双方が相手を待つ構造 - 双方向デッドロック

ここまでは出力方向だけを見てきた。子に大きな入力も渡さなければならない場合、デッドロックが最も純粋な形で現れる。親が入力を全部書いてから出力を読む順序だ。ところがここで予想外の結果が出た。

--- 6-1. child A (reads all, then writes) - like sort ---

  payload    65536 B -> ok         (wrote 65536 B, echoed 65536 B, 0.09s)
  payload  1048576 B -> ok         (wrote 1048576 B, echoed 1048576 B, 0.10s)
  payload  4194304 B -> ok         (wrote 4194304 B, echoed 4194304 B, 0.14s)

--- 6-2. child B (streaming filter) - like cat / grep / sed ---
  payload     1024 B -> ok         (wrote 1024 B before stopping, 0.10s)
  payload     4096 B -> ok         (wrote 4096 B before stopping, 0.10s)
  payload     8192 B -> ok         (wrote 8192 B before stopping, 0.09s)

子がどんな種類かによって結果が完全に分かれた。 これがこの実験で最も実用的な発見である。

  • 入力を全部読んでから出力する子(ソートのツールのような部類)は4メガバイトを入れてもデッドロックしなかった。子が読み続けるので親の書き込みが塞がらず、書き終えた後は親が読み取りに移っているからだ
  • 読みながら同時に書くストリーミングフィルタ(文字列の検索や置換のツールの部類)は9217バイトからデッドロックした。子が出力パイプで塞がると読み取りを止め、そうすると親の書き込みも塞がる
  • つまり同じ親のコードが相手によって通ったり止まったりする。 パイプラインの中間のツールを一つ替えたら止まり始めるという事故がここから出る
  • 親のコードだけ見ても判断できないという意味だ。子がストリーミングかどうかを知らなければならない

境界値9216バイトを分解すると構造が目に見える。4096 + 4096 + 1024 = 9216だ。子の出力パイプ4096バイトが満ち、親の入力パイプ4096バイトが満ち、最後の1024バイトの塊が伝達中の状態で円が閉じる。二つのパイプの容量の和がそのまま境界として現れた。 これが「双方が相手を待つ構造」の算術的な証拠である。

--- 6-4. FIX: feed and drain at the same time ---
  communicate() 4 MB in -> 4194304 B out, rc=0, 0.12s

--- 6-5. FIX: writer thread + reader in the main thread ---
  writer thread + main-thread reader -> 4194304 B, rc=0, 0.12s

解決は一つだけだ。入れる仕事と抜く仕事を同時に行う。 統合関数に任せても書き込みを別スレッドに出しても、4メガバイトが0.12秒で終わった。順序を分けた瞬間デッドロックになり、重ねた瞬間に解ける。

11. 止まったプロセスの診断手順

ここからは実務の状況だ。目の前に止まったプロセスがあり、これがこの問題かどうか判別しなければならない。特殊な道具なしで五段階に分ける。実際にデッドロック状態を作っておいて手順を踏んだ。

--- 7-1. start a pipeline that is stuck on purpose, then look at it ---
  step 1: are both ends still alive?
          372     369     365      22220  ?         197609 13:40:40 /usr/bin/sleep
          373     370     370       7504  ?         197609 13:40:40 .../python      

  step 2: is the writer making progress? (sample the counter twice)
    bytes written at t=2s : 65536
    bytes written at t=4s : 65536
    -> FROZEN at the same byte count

  step 3: is it burning CPU (a loop) or waiting (blocked)?
    CPU seconds sample 1 : 0.109375
    CPU seconds sample 2 : 0.109375
    -> equal CPU time + alive process = BLOCKED, not looping

  step 4: the decisive test - shrink the payload
     65536 B payload -> writer exit=0  (0 = finished on its own)
    400000 B payload -> writer exit=124  (124 = still blocked when timeout killed it)
    got 65536 B in before blocking
    same code, only the size changed -> the cause is the pipe buffer

四段階を順に読むと判定が狭まる。

  • 1段階、生存確認。 プロセス一覧に両方が見える。 死んで止まったのではなく生きて待っているのだ。これだけで「クラッシュ」の仮説が消える
  • 2段階、進捗確認。 書いたバイト数が2秒時点と4秒時点にどちらも65536だった。凍りついている。7節の表でフロー制御とデッドロックを分ける基準がこれだ
  • 3段階、CPU確認。 累積CPU時間が0.109375から0.109375へそのままだった。無限ループならこの値が上がる。上がらなかったので計算ではなく待機である
  • 4段階、決定的な試験。 大きさだけ変えて同じコードを二度回した。65536バイトは終了コード0で正常終了し、400000バイトはブロック状態のまま強制終了されて124を残した。入った量は正確に65536バイト、つまりシェルのパイプ容量だった
  • 5段階、コード確認。 待機呼び出しが読み取りより前にあるか、パイプで開いておいて消費していないストリームが無いかを見る。前の四段階が真ならここに必ず原因がある

4段階がなぜ決定的か強調するに値する。大きさ以外は何も変えていない。 コードも環境も入力の内容も同じだ。それなのに結果が分かれた。これより明確な証拠は無い。そしてこの試験は特別な道具がまったく要らない。

12. タイムアウト、ストリーミング、親が死んだとき

実務で一緒にかかる三つをさらに確認した。一つ目はタイムアウトの罠だ。

--- 9-1. wait(timeout=) does NOT kill the child; run(timeout=) does ---
  Popen.wait(1.5) raised TimeoutExpired
  child alive right after the exception : True
  after an explicit kill(), alive        : False

--- 9-2. run(timeout=) on a big output: does it survive? ---
  run(capture_output=True, timeout=5) -> rc=0, 2097152 B, 1.23s

--- 9-3. the trap: check_output on a child that also writes stderr ---
  check_output, stderr NOT a pipe (DEVNULL) -> 10 B, 0.38s
  check_output(stderr=PIPE)  -> 10 B, 1.15s

9-1が重要だ。待機呼び出しに上限を掛けて例外を受け取ったのに子はそのまま生きていた。 タイムアウトは「自分が待つのをやめる」という意味であり「相手を終わらせる」という意味ではない。明示的に終了させてようやく消えた。

  • タイムアウトだけ掛けて終了させないと孤児プロセスが溜まる。 バッチが繰り返し実行される環境では、これが静かに資源を食う
  • 例外を捕まえた場所で必ず終了を呼ばなければならない。そして終了後の回収までしなければならない
  • 9-2と9-3が示すように高水準の関数はこの処理をしてくれる。 2メガバイトの出力が上限の中で正常終了し、標準エラーをパイプで開いてもデッドロックしなかった
  • つまり自分で組み立てる理由が無いなら高水準の関数を使うほうが安全だ。 デッドロックの大半は自分で組み立てたコードから出る

二つ目は親が先に死んだときだ。この場合に子がどうなるかを二種類に分けて確認した。

--- 10-1. orphan that keeps WRITING to the dead parent's pipe ---
  1.5s after the parent exited, still running : False
  -> its next write failed, so it terminated on its own

--- 10-2. orphan that is NOT writing (just sleeping) ---
  1.5s after the parent exited, still running : True
  -> nothing ever tells it the parent is gone; it just keeps sleeping
  had to be killed explicitly

結果が分かれた。書き続ける子は自然に死んだ。 次の書き込みが失敗したからだ。一方書かずに待つ子は生き残った。 親が消えたという事実を知らせるきっかけが無いからである。明示的に終了させてようやく消えた。

  • 「親が死ねば子も片付く」という期待は半分しか合っていない。 書き込みを続ける子にだけ当てはまる
  • パイプは書くときにだけ相手の不在を知らせる。読んでいるか眠っているプロセスには何の合図も行かない
  • だから子を起動するコードには親の終了経路で子を片付ける処理が必要だ。正常終了だけでなく例外の経路にも無ければならない
  • この点はオペレーティングシステムとプロセスグループの設定によって違う動作をしうる。上の結果はこの環境の実測値である

14. チェックリストとやらないこと

コードレビューですぐ使える形に整理した。

  • パイプで開いたすべてのストリームに消費するコードがあるか数える。ストリームの数と読み手の数が同じでなければならない
  • 待機呼び出しが読み取りの後に来ているか見る。前にあればそれだけで欠陥だ
  • すべての待機呼び出しにタイムアウトがあるか見る。無ければ障害時に調査すらできない
  • タイムアウトの後に子を明示的に終了させているか見る。例外を受け取るだけでは子は死なない
  • 出力の上限が不明な子はファイルかストリーミングで受けているか見る
  • テスト標本の中にバッファ容量より大きいものがあるか見る。無ければこの経路は検証されたことが無い
  • 大きな入力を渡すコードで書きと読みが同時に回っているか見る
  • 順序が重要なログを統合していないか見る。統合すると時間の順序が壊れる
  • 進捗表示が必要な子が無バッファで回っているか見る
  • 出力を使わないのにパイプを作っていないか見る
  • 親の終了経路に子の片付けがあるか見る。眠っている子は自然には死なない
  • 運用環境のバッファ容量を自分で測ったか見る。開発環境と違いうる

逆にやってはいけないことだ。

  • ❌ パイプで開いておいて消費しないストリーム — 実務で圧倒的に多い原因であり、たいてい標準エラーだ
  • ❌ 先に待機、後で読み取り — 4096バイトまでしか通らないコードだ
  • ❌ 待機が失敗したから子も死んだと仮定すること — 実測の結果、生きていた
  • ❌ 小さい標本だけで合格判定 — 境界は実データでしか超えない
  • ❌ バッファ容量を別の環境の値で仮定すること — 同じ機械で4096、65536、131072に分かれた
  • ❌ 進捗ログの遅延をプログラムが遅いと誤診すること — バッファに溜まっているだけで原因が違う
  • ❌ 二つのストリームを統合しておいて順序を信頼すること — 実測で順序が完全にひっくり返った
  • ❌ タイムアウト無しの待機 — 再現実験そのものを不可能にする。この記事の実験もすべて上限を掛けて回した
  • ❌ 親のコードだけ見て安全だと判断すること — 10節のように子の種類が結果を変える

# パイプバッファのデッドロック — 子プロセス実行チェックシート

> 出典: braindetox.kr — 子プロセスが止まる本当の理由
> 根拠: Windows 10 / bash 5.2.37 (MSYS2) / Python 3.13.3 / Node.js 22.16.0 で実行検証
> このファイルをそのままAIに貼り、「この基準で我々のコードを点検して」と書けば使えます。
> ⚠ バッファ容量はOS・シェル・ランタイムごとに異なります。以下の数値は上記環境の実測値であり、各自の環境で測り直す必要があります。

## 0. 原理を一行で

パイプは**有限のバッファ**である。満杯になれば書く側は待つ — これはバグではなく**フロー制御**だ。
問題は、読むべき人がすでに待っているときに起こる。そのとき**双方が相手を待つ**構造になる。

## 1. 階層ごとの実測容量（参考値）

| 階層 | 実測 | 意味 |
|---|---|---|
| ネイティブWindows匿名パイプ | 4096 B | Python の os.pipe と subprocess の PIPE |
| MSYS2 シェルパイプ | 65536 B | bash の cmd1 パイプ cmd2 の形 |
| Node ストリームの highWaterMark | 16384 B | OSパイプの上に載るユーザ空間バッファ |
| Node 未消費 stdout の停止境界 | 131073 B | 実測値。上二つの単純な和ではない |
| Python stdio バッファ | 8192 B | io.DEFAULT_BUFFER_SIZE、パイプとは別の層 |

## 2. 実測したデッドロック境界

| パターン | 通る | 止まる | 境界の読み方 |
|---|---|---|---|
| Python: 先に待機、子が stdout へ出力 | 4096 B まで | 4097 B 以上 | パイプ容量そのもの |
| Node: data リスナ無しで close 待ち | 131072 B まで | 131073 B 以上 | ストリームバッファ + libuv の先読み |
| 親が入力を全量書いた後に読む（ストリーミングフィルタの子） | 9216 B まで | 9217 B 以上 | 4096 + 4096 + 1024 |
| 親が入力を全量書いた後に読む（全量読み込む子） | 4 MB でも通る | — | 子が読み続けるので詰まらない |

## 3. 実行方式の選択表

| 状況 | 選ぶ方式 | 注意点 |
|---|---|---|
| 出力が小さく上限が明確 | 高水準APIを一回呼ぶ（run / check_output / spawnSync） | 全量をメモリに載せる。上限をコードに明記する |
| 出力が大きい、または上限なし | ファイルディスクリプタへリダイレクト | 一時ファイルの後片付けとディスク残量は自分の責任 |
| 出力をリアルタイムに処理 | 一行ずつストリーミング消費 | 子の stdio バッファで遅れる → 子を無バッファで動かす |
| stderr も見る必要がある | 両ストリームを同時に消費（スレッド・非同期・高水準API） | 片方だけ読むと必ずデッドロックする |
| stderr の内容だけ必要で順序は不問 | stderr を stdout に統合 | 両者のバッファリングが違うため順序が混ざる |
| 子に大きな入力も渡す | 書きと読みを同時に（別スレッドか統合API） | 全量書いてから読むのは双方向デッドロック |
| 出力をまったく使わない | ヌルデバイスを指定 | PIPE で開いて放置するのが最悪 |

## 4. 安全な呼び出しパターン

### Python

# (2) 出力が大きい: ファイルで受ける。そのときは先に待機しても安全
with open("/tmp/demo/out.log", "wb") as fo, open("/tmp/demo/err.log", "wb") as fe:
    p = subprocess.Popen(cmd, stdout=fo, stderr=fe)
    rc = p.wait(timeout=600)

p = subprocess.Popen(cmd, stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
                     text=True, bufsize=1)
for line in p.stdout:
    handle(line)
p.wait(timeout=600)

# (4) 大きな入力と大きな出力: 投入と排出を同じ呼び出しに任せる
out, err = p2.communicate(payload, timeout=600)

## 5. 停止の診断手順（5段階）

1. **生きているか確認。** プロセス一覧に親と子の両方が見えるなら、死んだのではなく待機である。
2. **CPU時間を二回サンプリング。** 値が変わらなければ無限ループではなく**ブロック**だ。実測例: 0.109375 → 0.109375。
3. **進捗を二回サンプリング。** 書いたバイト数、出力ファイルのサイズ、最後のログ行が動いているか見る。
4. **決定的な試験 — 入力を小さくする。** 同じコードが一定サイズ以下で止まらなくなるなら、原因はロジックではなく**バッファ**だ。
   - 実測例: 65536 B は正常終了(0)、400000 B はブロックしたまま強制終了(124)、投入できた量は 65536 B。
5. **コードの順序を確認。** 待機呼び出しが読み取りより先に来ていないか。開いたまま消費していないストリームはないか。

| 観察 | 判定 |
|---|---|
| 生きていてCPU時間が止まっている | パイプでブロック（または別のI O待ち） |
| 生きていてCPU時間が増えている | 無限ループ。パイプの問題ではない |
| サイズを小さくすると通る | **パイプバッファのデッドロック確定** |
| サイズに関係なく常に止まる | パイプの問題ではない。ロック・ネットワーク・入力待ちを疑う |
| 子は終わったのに親が終わらない | 親がストリームを閉じていないか消費していない |

## 6. レビュー文（そのまま貼って使う）

- この呼び出しは子の出力の上限が何バイトですか。上限が無いならファイルかストリーミングに変えてください。
- stderr をパイプで開いていますが、消費するコードが見えません。片方だけ読むとデッドロックです。
- 待機呼び出しが読み取りより前にあります。順序を入れ替えるか統合APIに置き換えてください。
- 大きな入力を全量書いた後に出力を読んでいます。相手がストリーミングフィルタなら双方向デッドロックになります。
- タイムアウトがありません。待機には必ず上限を置き、超過時は子を明示的に終了させてください。
- テスト入力が小さいため、この経路は一度も検証されていません。バッファ容量より大きい標本を追加してください。
- 進捗ログが固まって出ています。パイプに繋がるとブロックバッファに切り替わります。生産者を無バッファで動かしてください。

## 7. チェックリスト

- [ ] パイプで開いた全ストリームに**消費するコード**がある
- [ ] 待機呼び出しが**読み取りの後**に来る（または統合APIを使う）
- [ ] すべての待機呼び出しに**タイムアウト**がある
- [ ] タイムアウト後に子を**明示的に終了**させる（待機の失敗は終了を意味しない）
- [ ] 出力上限が不明な子は**ファイルかストリーミング**で受ける
- [ ] テスト標本が**バッファ容量より大きい**
- [ ] 大きな入力を渡すとき**書きと読みが同時に**回る
- [ ] 順序が重要なログは**統合しない**（統合すると混ざる）
- [ ] 進捗表示が必要な子は**無バッファ**で動かす
- [ ] 出力を使わないなら**パイプを作らない**
- [ ] 親が死ぬときに子を**片付ける経路**がある
- [ ] 本番環境のバッファ容量を**自分で測った**（開発環境と違う可能性がある）

## 8. やらないこと

- ❌ パイプで開いたまま**消費しないストリーム** — 圧倒的に多い原因
- ❌ **先に待機、後で読み取り** — 小さい出力でしか通らない
- ❌ 待機が失敗したから子も死んだと**思い込む** — 実測では生きていた
- ❌ 小さい標本だけで合格判定 — 境界は実データでしか超えない
- ❌ バッファ容量を**別環境の値で仮定** — 同一マシンで 4096・65536・131072 に分かれた
- ❌ 進捗ログの遅延を**プログラムが遅いと誤診** — バッファに溜まっているだけ
- ❌ 順序が重要な二つのストリームを**統合した上で順序を信頼**する
- ❌ タイムアウト無しの待機 — 再現実験すらできなくなる
