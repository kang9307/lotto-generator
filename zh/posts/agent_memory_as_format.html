把记忆做成流程就会被锁死 - 让智能体记忆变成文件格式这个提案真正触到的地方

绑在流水线里的记忆，换工具的那一刻就跟不过来。做成格式会变什么，又有什么原样留着

2026年9月3日 开发/基础设施

讨论怎么给智能体加记忆时，话题几乎总会滑向流程那一侧。从对话里抽什么、怎么摘要、嵌入到哪里、按什么顺序检索取回。那份清单全是动词。可这份清单从来没有正面问过一件事。这样做出来的记忆，长什么样?是文件，是数据库里的一行，还是某个服务的内部状态。

这篇文章不比较工具，也不讨论为什么需要记忆。轴只有一条。记忆该表示成处理流程，还是表示成存储格式。这里只看这个选择决定了什么，又有什么依旧悬着。

本文依据的是截至2026年9月公开的规范文档与官方文档。文中谈到的格式提案自己写明处于草案阶段，本文不是对任何具体产品或公司的推荐或贬低。

缘起 - 不是流水线，而是文件格式

2026年9月初，一篇英文文章经由韩国开发者社区传开，把这场讨论放到了准确的位置。标题是「Agent memory as a file format」，正文里的一个小节标题更直白。记忆应该是数据格式，而不是多阶段流水线。

文章开头引了 Frederick Brooks 的一句老话。你把流程图给我看却把表藏起来，我只会继续困惑；把表给我看，流程图通常就不必了，因为它会变得显而易见。这句题词就是全文的论点。把数据结构定下来，流程自然跟着出来。

这里要马上说清一件事。这个提案不是已经确定的标准。规范文档自己写着草案 0.1，日期是2026年8月。所以这篇文章也该读成「这个方向触到了什么」，而不是「事情已经这么定了」。

原文实际主张了什么

原文把现有的记忆系统分成三类来批评。第一类是刻意把用户绑死在某个特定运行框架上的。第二类用原文的说法是荒唐地复杂 — 他举的例子是为了判断什么值得记住，得架起向量扩展、图数据库，还要一个自己的 LLM。第三类是他称作高度现代主义的一路，想象一种理想化的、理性主义的记忆形态，用图和逻辑命题把事实切下来装好；作者认为这样做把信息从语境里剥离，最后只剩孤立的碎片。

三类的共同点可以压成一句话。它们都把记忆当成流程。作者的替代方案在另一侧：记忆，尤其是对模型而言，用数据来表示要好得多。

理由也清楚。现有的检索增强流水线之所以复杂，是因为它在设法把人写的历史文档变得让智能体读得懂，而智能体记忆本来就不是那种东西。记忆生成的那一刻，写它的是一个会写散文的智能体。所以不需要分块、不需要富化、不需要二次摘要。真正提出来的格式只有三块。

  • Markdown 页面 — 一条记忆就是一个文件
  • 可选的 YAML frontmatter — 标题、uuid、创建与更新时间、摘要
  • 可选的 SQLite 向量索引 — 放在旁边供语义检索用的一个文件

这一整包的规范保存形态是 zip。这是为了让交换尽量容易而做的选择，规范在提供方式上刻意留了口子，本地文件、对象存储、HTTP 都行。打开目录大概是这个样子。

my-memories.memoryfield.zip
├── carbon-fibre-woks.md
├── finnish-bureaucracy-tips.md
├── wec-2026-season-notes.md
└── nomic-embed-text-v1.5.sqlite3

最好不要给原文加上它没有的主张。作者并没有说这就把记忆问题解决了。后面会看到，他自己留下的未决事项就有好几条。

做成流程，记忆就被关在实现里

用流水线做出来的记忆，真正的问题不是性能，是归属。当摘要规则在某家厂商的提示词里、向量由那家挑的模型算出、检索只在那家的索引上跑，记忆就成了那个实现的内部状态。表面上是我的记忆，可实际能搬走的只有原始会话日志，而要把日志重新变成同样的记忆，只能再跑一遍同样的流水线。

这种锁死很安静。换工具之前一点症状都没有。它在换的那天显形，而那天偏偏是已经积了好几个月、搬迁代价最大的时候。所以这个问题总是被晚发现。

原文提到的另一个角度也很务实。机械装置多的系统，智能体要够到目标就得穿过一座接口迷宫。接口大，光是把模式定义读进上下文就吃掉不少；接口小，能做的事又有限。就算平衡拿捏得当，那还是别人写的 API，没有预见到我的需要。作者在这里立下一条原则：多一点模型，少一点机械装置。

项目放成流程时放成格式时
记忆的实体服务索引的内部状态目录里的文件
更换工具把原始日志重跑一遍再生成另一个工具打开同样的文件
变更历史服务给多少就有多少版本管理工具原样处理
审计要另有手段去查存了什么打开来读
删除删除请求和真的删掉是两回事把文件删掉
故障追查要定位是流水线的哪一段收敛到一个文件

做成格式会变什么

变化最大的一点是别的工具会读同样的文件。格式一旦写成文档，读它的实现不必由原作者去做也会出现。这不是乐观，是观察：活下来的文件格式无一例外都走到了这一步。

其次是人这一侧的好处。文本文件能做 diff。能 diff 就能评审，能评审就留下什么在什么时候因为什么进来了。当一条错的记忆被写进去，追查是哪一次会话放进来的，就从向服务方提工单变成读一行日志。

  • 能读 — 要确认存了什么，不需要另一套查询工具
  • 能比 — 两个时间点之间多了什么、少了什么，直接就出来
  • 能搬 — 打个包发过去就完事。需要重算的只有索引，而索引可以从原件重建
  • 能删掉一部分 — 按文件删就是按记忆删
  • 别的工具能插进来 — 拼写检查器也好、泄漏检查器也好，是文本文件就能挂上

要注意的是，这份清单全都来自把表示放成文件这件事，而不是这一个提案的功劳。任何把记忆放成文本文件的设计都会得到同样的好处。所以下一节才重要。

早就长成这个样子的惯例

有意思的是，在有人提出这个方向之前，现场其实早就长成了这个形状。有两个例子很显眼。

AGENTS.md 把自己介绍成一种用来引导编码智能体的简单、开放的格式。更准确的说法是紧接着那一句 — 给智能体看的 README，一个专门的、可预期的地方，用来放语境和指示。没有必填字段，就是 Markdown。截至2026年9月，该站点写着有超过六万个开源项目在用，并说明维护方是 Linux 基金会旗下的 Agentic AI Foundation。

CLAUDE.md 这边的规则更细。按官方文档，这个文件会在工作目录以及其上的每一级目录里被找出来读取，找到的文件彼此不覆盖而是拼接。顺序是从文件系统根目录往工作目录方向下来。子目录里的文件则是在真正读取那个目录里的文件时才按需加载。它有一个 @路径 的导入语法可以引入别的文件，深度最多四跳。

同一份文档还确认了另一件事。工具自动积累的记忆也是文件。每个项目的目录里放着一个叫 MEMORY.md 的索引和一批按主题分的 Markdown 文件，每个文件的 frontmatter 里带一个表示种类的 type 字段。文档的措辞很明确 — 随时可以编辑或删除的普通 Markdown。

所以把记忆做成文件格式这个提案，并不是要造一个原本不存在的东西，而更接近把已经在这么做的事写成格式。工具那一侧怎么处理会话记忆，在 CTX解析 - 连接Claude Code跨会话记忆的持久化内存工具 和 把AI编程会话的易失上下文变成项目记忆 里分别谈过。

格式不是免费的

说做成格式更好，很容易。看看要成为格式实际得定下哪些东西，就没那么轻了。草案规范把这份清单摆得很清楚。一个页面的开头是这个样子。

---
title: Carbon Fibre Woks
created: '2026-03-01T09:00:00Z'
updated: '2026-08-22T14:30:00Z'
uuid: 6aa615f0-486f-48a7-a210-ba4f5ff18c8b
summary: Thermal properties of carbon fibre cookware
---

这里时间值被引号括起来不是审美偏好。规范把理由也写上了。日期与时间字段必须是加引号的字符串 — 否则 YAML 1.1 的解析器会把它强制转成日期对象。定义一个格式，就是这样一条一条钉下来。

必须定下的东西草案定的方式剩下的问题
模式title、uuid、created、updated 为建议项，summary 为可选项。实际上没有必填松所以兼容，松所以双方各自期待着不同的东西
版本文档自己写明是草案 0.1(2026年8月)出到 0.2 时该怎么读 0.1 的文件，还没有说
合并按页面的最后写入优先。条件写入服务端可以支持，但不得强制要求能让冲突显形，却不替你化解
大小上限页面最好不超过 8,192 字节，实现只处理前 8,192 字节也可以超出的内容怎么切分，是写入方自己的事
同一性存着的和传进来的 uuid 不一致时，建议以 409 拒绝同一个事实被写进两个文件的情况抓不到

表格右侧那一列就是这一节的要点。定义格式是把问题挪个地方，不是让问题消失。不同之处在于，挪过去的那个位置是写在文档里、可以拿出来争论的。

两边同时改怎么办 - 合并规则才是真正的考场

格式讨论里最常被跳过的就是这里。两个会话同时改同一份记忆，会怎么样。

草案给的答案诚实而简单。按页面的最后写入优先。用条件写入把冲突显形，比如在 ETag 上加 If-Match，服务端可以支持但不得强制要求。也就是说，格式给冲突留了显形的位置，却不做化解。

这是选择，不是缺陷。但得知道这个选择的代价。人写的文档里，最后写入优先通常靠两位编辑互相察觉就化解了。多个智能体同时跑的环境里，没有人会察觉。一方刚写下的东西悄悄消失。

  • 文件切得细，冲突就少。代价是同一个事实散落在多个文件里
  • 文件放得大，事实是聚在一起的。代价是两边碰同一个文件的概率上升
  • 8,192 字节这个上限，在这架天平上已经选好了一边，选的是切得细那一侧
  • 放到版本管理之上，冲突就看得见了。代价是新添一个问题：合并冲突由谁来解
  • 用 uuid 锁住页面同一性，改了文件名也仍算同一条记忆。代价是一旦混进没有 uuid 的文件，这个保证就断了

写什么进去，格式并不解决

有一点要说清楚。把表示形式定下来，什么才值得记住这个问题原封不动地留着。格式是容器，这是内容物的问题。

原文作者也被问到这个，他的回答是：无关的材料反正不会被语义检索捞出来，所以不构成问题；无关的记忆占地方，但不会妨碍智能体；因此放开了往里塞。他附的一条建议很实用 — 记忆里最好带上出处，尽量以 URL 的形式，这样以后再过一遍时能强化它，也方便智能体去核对过时或可疑的内容。

讨论里出现的反驳则完全朝相反方向。有人说自己干脆把记忆功能全关掉，把文档放在临时目录里不断整理和删除；有人说错的一行混进去，后面的结果就整片被污染；还有人说时间一长、规模一大，信息陈旧加上语境错配，它就没用了。只是占地方和会污染之间的这道缝，格式并不会替你合上。

挑选存什么这件事为什么那么难，在 为什么做记忆最后会变成分析引擎 里单独谈过，这里不重复。只搬要点：要挑存什么，就得知道它是什么意思，而要知道意思，最后总得做分析。

读的一侧的成本 - 筛选重新变成流程

这个话题里最诚实的一段在这里。文件一大，每次调用就装不下全部。于是需要一个挑选装什么的环节，那个环节就是筛选，筛选就是流程。以减少流程为出发点的讨论，又把流程叫了回来。

这个循环不是文字游戏，它以数字的形式露出来。把公开的上限并排放着，是这样。

对象加着的上限超过之后
草案规范里的记忆页面最好不超过 8,192 字节实现只处理前 8,192 字节也可以
指令文件 CLAUDE.md每个文件以 200 行以内为目标超过 4 MiB 的文件会被跳过
自动记忆索引 MEMORY.md前 200 行或 25KB，以先到者为准之后的内容在会话开始时不会被读入
按主题分的记忆文件启动时不加载需要时用文件工具去读

最后一行就是这一节的答案。不把全部装进去。索引始终装，正文需要时再读。而把索引维持得短，本身就是摘要，就是筛选。草案规范想让检索在两次工具调用内结束 — 检索一次、并行读取一次 — 回应的也是同一种压力。顺着链接走的方式，信息在第 N 层就要 N+1 次调用，每次调用还要搭上几秒。

所以准确的说法不是流水线不需要了，而是这句。流水线还在，只是它的产物落在流水线之外。流程没有消失，只是流程的结果降落在一个开放的格式上。把这个区分抹掉，提案本身就成了夸大的主张。语义检索建在什么之上也是同一性质的决定，草案选了单个 SQLite 文件，是为了让索引能从原件重建。选项的全貌在 向量检索该建在什么之上 里整理过。

活得久的格式共有的东西

提出一个新格式时，值得参照的是那些活下来的配置文件。把四个并排放着，共同点就很清楚。

格式放在哪里层级重叠时
.gitignore与目标路径同级的目录，以及各级上层目录上层文件的规则被下层文件覆盖。同一层里最后匹配到的规则胜出
.editorconfig所打开文件的目录以及全部上层目录自上而下读取，后找到的规则胜出。遇到 root = true 就停止向上查找
package.json包的根目录只有要发布时 name 和 version 才是必填。不发布则两者都可选
CLAUDE.md工作目录以及其上的每一级目录不覆盖而是拼接，顺序从根目录往工作目录方向下来
  • 位置已经成了惯例。不必问该看哪里
  • 层级合并规则写在文档里。重叠时谁胜出如果含糊，这个格式在每个工具里的行为就不一样
  • 必填项压到最少。连 package.json 对不发布的项目都没有必填字段
  • 留了逃生口。.editorconfig 的 root = true 就是切断向上查找的开关

最后一条值得原样搬到记忆格式上试试。凡是引入了层级合并的格式，无一例外都有一个说「从这里往上别看了」的位置。记忆也需要这样一条 — 比如工作仓库的记忆和个人记忆在同一棵目录树里重叠的时候 — 而草案里目前还看不到对应的东西。

拿 Markdown 当容器这件事

把记忆放进 Markdown，理由很清楚。模型处理得好，人读得懂，工具早就遍地都是。借用原文作者的说法，模型对 bash、对 Markdown、对 SQLite 都意外地非常在行。这在格式设计里是少见的一种优势：没有新语法要学。

短处也是已知的。Markdown 没有一份长期确定下来的统一语法。CommonMark 那边的说明把这个情况概括得很好 — 最初那份权威描述没能把语法规定得毫不含糊，正因为没有一份无歧义的规范，各家实现分岔得相当厉害。于是同一份文档在不同系统上渲染得不一样。

这件事在记忆文件里真正会咬人的地方，比听上去要窄。强调或表格渲染略有出入没关系。要命的是frontmatter 这种机器要读的部分。草案把日期的引号钉死，钉的正是这个位置。人读的部分可以宽容，机器读的部分不能宽容。

  • 正文就让它是散文。硬套结构，智能体会为了迁就形状而丢掉内容
  • 机器要读的字段定得窄、定得明确。解析器的差异不该改变一个值
  • 文件名要起得有意义。有些东西在检索之前，光看列表就能筛掉

记错的东西能不能删掉

格式还是流程，结果分岔最大的地方就在这里。记忆总有一天会错。可能是因为事实变了却没人告诉它，也可能一开始就写错了。那么该问的只有一件事。能不能把它找出来删掉。

放成文件，答案很短。打开，读，删。官方文档谈自动记忆时用的就是这个说法 — 随时可以编辑或删除的普通 Markdown，一条命令就能打开列表。审计、修正、删除变成同一个动作。

在流程里面，这三件事就分开了。看存了什么另有一套方法，改不改得了不一定，而删除的那个响应和东西真的没了是不是一回事，没有办法确认。删不掉错误记忆的系统，时间越久越糟。这不是预测，是算术：错的条目随时间增加，删不掉就不会减少。

顺带一提，模型是自己编出了答案，还是把在别处读到的东西吐了回来，这是性质不同的另一个题目，在 把看起来像推理的东西和回忆出来的东西分开 里单独谈过。

记忆文件进入仓库的时候

放成文件的好处之一，是它能进版本管理。这一节就是那句话的背面。提交的那一刻，它一起出去了。

记忆文件里会有什么。正在处理的系统名、内部主机、什么东西在什么路径、按什么步骤部署，还有误粘进去的值。人写的文档，提交前好歹会扫一眼。智能体写的记忆，没有指定的人去扫。

原文作者也点到了这个方向，措辞相当重 — 不要和不信任的对象共享上下文窗口，通过记忆共享同样不行。他写到，规范里之所以包含一个静态 zip 形态，理由之一就是让你能把别人给的记忆包手动过一遍，并用哈希钉住。他也承认了留下来的问题：智能体依然没有办法区分好提示和恶意提示。风险是双向的：出去的方向漏的是自己的东西，进来的方向来的是别人埋下的句子。

  • 记忆目录默认排除在版本管理之外，只把要共享的挑出来放进去，更稳妥
  • 按官方文档，自动记忆是机器本地的，不在机器之间共享。要共享就意味着人要有意去搬
  • 别人给的记忆包，在打开读过之前不予信任。哈希钉住只保证你拿到的是同一份，不保证那份是安全的
  • 提交前检查有没有混进凭据，需要另立一个习惯。最常漏的位置整理在 远程 URL 里嵌着令牌 里

惯例不等于标准

最后，用词得准确。本文谈到的这些，没有一个能叫标准。

  • 草案规范自己写着草案 0.1。带着版本号和是标准，是两回事
  • AGENTS.md 称自己是开放格式，不称标准。由基金会旗下的组织维护，意味着治理结构建立起来了，不意味着标准化已经完成
  • CLAUDE.md 是某一个工具的约定。正如其官方文档明确写的，那个工具读 CLAUDE.md 而不读 AGENTS.md，并指引你用导入或符号链接把两者接起来

最后一条把眼下的位置说得很清楚。目的相同的两套惯例不读对方的文件，指望由人来牵线。一家公司拿出的文件惯例被广泛使用，就成了事实上的惯例，但那和多个实现约定好互操作，是两种状态。定下一个文件和形成一份共识是两件事，难的永远是后者。把智能体的行为写成规格这个想法会撞上同一类墙，在 长时间运行的智能体该拿什么来打分 里谈过。

小结

把记忆表示成流程，拥有那个流程的一方就拥有记忆。表示成格式，握着文件的一方就握着记忆。这场讨论的骨架就是这个，其余都是这个决定带来的代价与收益。

格式这一侧买到的东西很明确：能读、能比、能搬、能删。付出的也很明确：得定模式，得管版本，得定合并规则，得加上限。草案给出的答案大体上倾向于只定最低限度、其余留白，那是一个让采用变容易、让互操作变难的选择。没有依据说这个选择是错的，但要知道代价是什么再去选。

然后还剩下格式不解决的两件事：写什么进去，以及每次调用装什么。后者终究是筛选，而筛选又是流程。所以这个提案准确的尺寸是这样。不是把流程消灭掉，而是把流程的产物留在流程之外。光是这一点差别就已经够大了，但读得比这更多，就会失望。

未能确认的部分

  • 原始的讨论帖没能直接打开。服务器返回了请求过多的响应，因此讨论内容只在韩国社区页面转载的范围内做了确认。个别发言的原文句子无法比对，所以本文也没有把任何说法归到具体某个人名下
  • 这个格式的实际采用规模 — 有多少实现在读写它 — 没有找到可供确认的材料。规范文档本身写明是草案 0.1
  • 没有找到做成格式比做成流程结果更好的比较测量。原文也没有给出这样的测量。本文整理的是收益与成本的清单，不是优劣的证据
  • AGENTS.md 的采用项目数是该站点自行标注的数字，没有找到独立核实过的统计
  • 不同工具实际读写同一份记忆文件的案例究竟有多少，没能确认。文档里写着可以用导入或符号链接把两套惯例接起来，这一点确认了，但那种接法被用得多不多是另一回事
