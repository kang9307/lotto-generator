The Collapse Point Differs by Metric - What to Measure Before You Pick a Bit Width

Reading which benchmark the words held and collapsed were actually about

2026-09-10 Tech & IT

The first wall anyone meets when trying to run a model locally is not quality, it is memory. A weights file of 55 gigabytes does not fit on a single consumer graphics card. So the bit width comes down. Narrower means smaller, and smaller means it fits.

As for what happens after the narrowing, one sentence circulates more than any other: 4-bit is usable, below that is risky. A measurement backing that sentence with real numbers appeared recently. One model was split into five widths and put through three benchmarks.

Yet folding that record into the single line that 4-bit holds and 1-bit collapses throws away the most useful thing in it. The three metrics parted at different widths. Instruction following showed no change down to 2-bit, while science knowledge and agentic coding had already separated at that same width. No single safe line ever emerged from the data.

So the question worth holding on to is not how many bits are safe. It is which metric drew the line between holding and collapsing, and what you have to measure alongside it to find that line in your own work. What a shrunken model loses is a separate subject, laid out in a piece on how the average survives while the tail is cut first. What this article deals with is the design of the measurement that reveals where the loss surfaces.

The figures and quotations here come from the source measurement article and the public documentation of the model and quantization distributors, retrieved on 10 September 2026. The 2-, 4- and 8-bit files the source used were replaced by the distributor on 19 August 2026, so the exact files used in most of those tests can no longer be downloaded under the same names. No model and no tool is being assessed here, and nothing below should be read as a promise of performance. The exact per-metric scores were presented in the source as charts, so they are not carried over here as values.

The trigger - one model split into five widths

The subject of the measurement is a single model, Qwen3.8-27B. Its model card describes a dense model at the 27 billion scale, a native vision-language model that handles images and video, carrying a control over how deeply it thinks. The native context is written as 262,144 tokens, extensible to one million.

The source article lined up the BF16 original of that model against five GGUF quantizations produced by a distributor. The table below reproduces the labels and sizes exactly as the source records them.

The inference engine was llama.cpp, and the source states it used a build dated 16 August 2026. The hardware was three kinds of NVIDIA card, an L40S with 48 gigabytes, an H100 with 80 and an H200 with 141, and the author reports spending roughly three thousand dollars on cloud GPU time. That a single model split five ways costs that much to measure explains, by itself, why measurements like this are rare.

One important caveat is attached. Because the distributor replaced the 2-, 4- and 8-bit files on 19 August 2026, the exact files used for most of the tests are no longer in the same place. There is no basis for assuming that a file downloaded today under the same name is the same file used then.

Three metrics drew the line between holding and collapsing

Here is the passage that matters most. The source produced no single overall score. It reported three tasks of entirely different character, each on its own.

MetricWhat it looks atContext in this runWhat the source records
GPQA DiamondHard science questionsAbout 8k reasoning tokens at the deepest thinking settingNo noticeable difference from the original down to 4-bit. At 1-bit the score falls to around random chance
IFBench (strict scoring)Whether instructions and formats were followedAround 4k tokensNo change between models down to a decent 2-bit build
Terminal-Bench 2.1Agentic coding in a terminal98k of context reserved4-bit matches the full model. The 2-bit build takes as many turns but writes about a quarter more tokens

Fold this table into one sentence and you get that 4-bit holds and 1-bit collapses. That is not a false summary. What it loses is that the answer changes depending on which column the 2-bit build sits in. For work that only has to obey a format there was no difference even at 10.7 gigabytes, whereas for science knowledge or agentic coding the same file had already dropped.

Put another way, the question of the width at which things break has no answer until a metric is named. The source itself attaches conditions to its own recommendation: for most tasks the 4-bit build should be good enough without any noticeable difference, and for some simpler tasks the 2-bit build should be more than fine. The centre of gravity in that sentence sits on the words most and simpler.

Each metric breaks in a different place

Why do they part? Because the three tasks ask the model for different things.

Why format compliance holds out longest

An instruction-following task usually checks surface constraints. Was the character count met, was the text divided into the specified sections, were forbidden words avoided. Judgements like these resolve in one pass, and the representations a model relies on to satisfy them are not specific rare facts but structural regularities spread thickly across all of its text. Narrowing the weights makes the probability distribution wobble a little, but the margin before the ordering of the top candidates flips is wide.

Why rare knowledge smears first

A hard science question demands the opposite. It requires pulling out, precisely, a fact that appeared infrequently in training. Common material is stored redundantly along several paths, while rare material survives thinly along a single one, and thin things vanish first under compression. This is the same root as the account of how the tail is cut first, treated in detail there.

Why multi-step tasks fail by accumulation

Agentic coding has a different character again. Instead of one judgement there are dozens of choices in sequence, and each step feeds the next. If the probability of a correct step drops only slightly, the probability of reaching the end across twenty steps drops noticeably. Worse, a step that goes astray becomes the premise for the next, so the error does not cancel out but stacks with a direction. The observation in the source that the 2-bit build takes the same number of turns yet writes about a quarter more tokens sits right against this property. It arrives at the same answer, but wanders more on the way.

What the phrase the average holds conceals

Here is the central claim of this article, stated plainly. Two systems scoring the same total do not give the same answers. A total is a summary of a distribution, and a summary by definition discards the shape of that distribution.

There are many ways to arrive at 80 out of 100. You can miss five items in each of four categories, or miss twenty items concentrated in a single category. The scores are identical, but the experience of putting those two models into production is nothing alike. The first is a tool that is occasionally wrong. The second is a tool that simply cannot do one kind of job.

The loss quantization creates is closer to the second. It does not degrade evenly, it degrades in clusters under particular conditions. Which is why the decision about bit width cannot be made from an average score. An average is a number carrying too little information to decide on.

What the source did well is exactly this. Rather than manufacturing a composite score it reported three axes of different character separately, and because of that the parting at 2-bit became visible. Had the three values been averaged into one headline number, the most interesting thing that happened in the 2-bit region would have hidden inside the statistic. Summarisation causing loss is not a property peculiar to models.

Two things labelled 4-bit are not the same thing

When two people use the phrase 4-bit, the odds they mean the same object are lower than one would expect. A bit width is nowhere near enough information to identify a quantization. At minimum two further facts are needed: where it was applied and by what method.

Point of applicationIn this measurementWhat it reducesSymptom that surfaces first
WeightsVaried across five stepsFile size and resident memoryDiffers by metric. The body of this article
KV cacheHeld at F16. About 2.3 GB per 32k tokensMemory proportional to context lengthLoss in the later part of long contexts
ActivationsNot mentioned in the sourceCompute bandwidth and intermediate buffersInstability in layers with large outliers
Embedding and output headNot separately specified in the sourceMemory tied to the vocabulary tableRare vocabulary and non-English orthography

The method side splits too. How many weights are grouped together to share one scale, whether calibration input is pushed through first to learn which weights contribute most to the output and that result then applied, whether outliers are pulled aside and kept at higher precision, whether different layers receive different widths - these are all distinct choices. Combine them differently under the same 4-bit label and the results part.

The combination the source used can be pinned down. GGUF files in the llama.cpp family, from a distributor's dynamic quantization line, with the 2-, 4- and 8-bit builds on version 2 of that line and the 1-bit builds on version 3. The KV cache is explicitly stated as held at F16 regardless of the model width. This is therefore a measurement in which only the weight width changed.

How that distributor allocates per-layer widths inside each label, and what it uses as calibration data, are not carried into this article as values. The reason is recorded in a later section. What the UD prefix on a label does show, simply by existing, is that a build belongs to a line different from the default, which is the point exactly: the same bit width can be a different file depending on whose rules made it.

The KV cache - the axis this measurement held fixed

One design choice in this measurement deserves attention. The KV cache was held at F16 regardless of the model width. The source puts its size at roughly 2.3 gigabytes per 32k tokens.

That choice means two things. First, what the measurement shows is purely the effect of weight width. Had the cache been narrowed at the same time, there would be no way to attribute a given loss to a given cause. As experimental design, this is the right call.

Second, there is a gap between it and real deployment. Someone dropping to 4-bit because memory is short usually wants to shrink the cache too, since the longer the context the larger the share the cache takes. For an agentic task reserving 98k of context, the arithmetic puts the cache alone at somewhere around 7 gigabytes. Add the 17 gigabytes of 4-bit weights and the total sits near 24, which already exceeds the capacity of a single high-end consumer card.

So the calculation that 4-bit fits on a card of a given size is a calculation counting only the weights. Until the context length is fixed, the memory requirement cannot be stated. The author of the source notes that cache-side quantization has not been measured yet and might be tried later. Hardware judgements are covered separately in the piece on choosing hardware for local LLMs.

Collapse arrives wearing a face other than the wrong answer

One description of how the 1-bit builds failed is especially valuable. At the deepest thinking setting, the 1-bit model more often reasoned until the token budget ran out and then returned an empty answer.

That is recorded on the scoreboard as a wrong answer, but in nature it is nothing like one. The model did not confidently assert something false, it failed to finish. An automatic grader cannot tell this apart from any other miss. The moment everything is merged into one number, being wrong from missing knowledge and producing nothing from failing to terminate land in the same cell.

In practice the remedies for those two are opposite. The first calls for a larger model or retrieval augmentation. The second calls for cutting the reasoning budget, enforcing an output format, or making the stopping condition explicit. The same drop in score can therefore justify prescriptions pointing in opposite directions.

Which is why a test should carry, separately from the score, a column that counts kinds of failure. Count format violations, empty outputs, budget exhaustion, malformed tool-call arguments and factual errors each on their own, and stepping the width down shows you which column grows first. This is the same lens used when examining the runtime and template layers that make identical weights behave differently.

Six things to check before the scores

When reading a table someone else produced, several things come before the numbers. If these six differ, the two tables were never comparable to begin with.

  • Same engine and same build - the source names a llama.cpp build dated 16 August 2026. A different engine gives a different result from the same file
  • Same chat template and system prompt - when the template is off, the model receives input in a shape that is not its own. This is the kind of thing that degrades quietly
  • Sampling settings written down - a table without temperature, top-candidate truncation and seed cannot be reproduced. Those values are absent from the source as well
  • How many runs and how wide the spread - the source states that its error bars are Wilson 95 percent confidence intervals and adds that these are very conservative with respect to run-to-run noise. The repeat count itself is not written down
  • What context length was reserved - the same model shows a different face on a 4k task and on a 98k one
  • What the thinking-depth setting was - the source says this value changed the score drastically and adds that the default can tip into overthinking

That last item weighs heavily in this particular measurement. Setting the thinking depth low could reduce how often the 1-bit model burns its budget and returns nothing. The score of the very same file would then change. Bit width and reasoning budget are not independent variables. Comparing one without fixing the other mixes two effects together.

And a number from a single run is one sample, not a ranking. Without knowing how much the same conditions wobble on a rerun, there is no way to say whether a gap between two values is a meaningful gap. What benchmarks structurally fail to see is written up further in the piece on the blind spots in evaluation.

What to measure alongside - separating the axes

Saying that one total cannot support a decision is the same as saying to split the axes apart and measure them. The table below separates out what has to be watched together when the width comes down.

Axis of measurementWhat it is sensitive toDoes it show in the total?How to measure it
Long contextKV cache precision, context length settingBarely. Standard tasks are mostly shortAttach the same question to a short document and a long one, and compare how often the answers agree
Rare vocabulary and proper nounsWeight width, embedding handlingNo. Frequency weighting tilts toward the commonBuild a list of internal terms and product names and count the rate of exact orthographic match
Multi-step reasoningWeight width, reasoning budgetOnly partly. It is buried in the final accuracyPlace checkpoints between steps and record which step is where the runs diverge
Format and instruction complianceRelatively insensitive. It breaks lateYes, if a dedicated metric existsAttach a schema validator and count the pass rate on its own
Non-English inputTokenizer, rare orthographyNot at all if only English tasks are usedRebuild the same task in the target language and run the two side by side
Tool calls and structured outputFormat compliance combined with argument accuracyPartly, when the task includes itValidate call arguments against a schema and count by error type
Termination behaviourReasoning budget, the decision to stopNo. It is smeared together with wrong answersCount empty outputs and budget exhaustion in separate columns
Output length and costThe detour taken to reach the same answerAbsent from an accuracy tableCompare tokens consumed across the cases both builds solved

The third column is the point. More than half of the axes do not show in the total. Those axes look as though they do not exist until someone measures them, and if the width comes down before anyone does, the loss is discovered after deployment by the people using it.

This is not a demand to measure all eight. The order is to decide first which axis your work actually sits on. A pipeline that only summarises and classifies may be well served by format compliance and non-English alone, while an agent that calls tools lives or dies on multi-step behaviour, tool calls and termination. Reading this next to the piece on what is enough and where it gets precarious helps sort the branches.

A procedure for your own work - measure first, then shrink

Not inverting the order is the whole of this section. The approach of dropping straight to a low width because memory is short and raising it again if things look off begins from a state with no vocabulary for what off means. It generally ends in the sentence that it just feels a bit worse.

Step 1 - write down the shape of failure

What does failure look like in your work? Write that first. Is the JSON broken. Are the arguments of a tool call wrong. Is a section at the back of a long document being missed. Is the spelling of a proper noun coming out altered. Are unsupported assertions increasing. Without a definition of failure there is no test to build.

Example failure definitions - internal document Q and A
  F1  the cited paragraph number differs from the source
  F2  a fact absent from the document appears in the answer
  F3  a required key is missing from the output JSON
  F4  an internal product name is spelled differently
  F5  answers are missed only in the last 30 percent of a document

Step 2 - build a test that catches only those failures

Thirty to a hundred cases is enough to begin. What matters is not the count but the composition. Filling it with easy cases means everything passes even at a low width and nothing gets measured. Deliberately mix in hard cases, long cases, non-English cases and cases with awkward formatting requirements. And make each case record not only pass or fail but which failure type it hit.

Step 3 - fix a baseline at the original width

Run at the widest setting first. Any case that already fails here is a problem with the task or the prompt, not with quantization. Failing to filter those out contaminates every comparison that follows. Run three or more times under identical conditions and record the spread as well. Any later difference smaller than that spread is not counted as a difference.

Step 4 - step down one level at a time, repeating the same test

Hold fixed  - engine build / chat template / system prompt
              temperature / seed / context length / thinking depth
Change      - weight width, and nothing else

Record      - failures by type / spread across repeats / tokens consumed
              time to first response / resident memory

Two mistakes are common here. One is changing something else along with the width. Narrow the weights while also shortening the context and lowering the thinking depth, and when the result gets worse the cause cannot be isolated. The other is recording only the total. Without counts by type, which axis buckled first disappears.

Step 5 - find the breaking point and stop one level above it

Once the width at which the baseline is left behind becomes visible, take the step directly above it. The reason for not stopping exactly at the boundary is that measured conditions and real load differ. A test runs on controlled input while real input is longer and dirtier. Leaving one notch of headroom is the better bet. The general branches for estimating model size and memory needs are set out in the piece on the four things the word size points at.

What this measurement does not answer

The better a measurement is, the clearer it is about what it did not measure. Here is what sits outside this one's range.

  • Transfer to other models - what was measured is one size in one family. Nothing inside it supports carrying a line found on a dense 27 billion model over to a much smaller model or a mixture-of-experts architecture
  • Non-English performance - all three tasks are in English. The width at which orthography starts to wobble on Korean input needs a separate test
  • The relationship to perplexity - the source did not use perplexity as a metric. How the commonly quoted perplexity figures correspond to results on these three tasks cannot be said from this measurement
  • Speed and throughput - a smaller file is generally faster, but that value is not the focus here. The observation that the 2-bit build writes more tokens does suggest a speed gain could be partly offset
  • Stability over time - this is a measurement of files at one moment. If the distributor updates them, results under the same label can change, and in fact a replacement happened three days after the tests

Conclusion - three things that remain

First, the question of the width at which things break has no answer until a metric is attached to it. On the same model, the same files and the same hardware, format compliance held down to 2-bit while science knowledge and agentic coding had already parted at that point. Instead of hunting for one safe line, the order is to decide first which axis your work sits on.

Second, an average is a number carrying too little information to decide on. Even at an identical total, which kind of input breaks first leaves no trace in that total. Long context, rare vocabulary, multi-step reasoning, format compliance, non-English input and termination behaviour are each sensitive to different things, and most of them do not show in the total. An axis nobody measured is discovered after deployment by the people using it.

Third, measure first, then shrink. Write down the shape of failure in sentences, build a test that catches only that failure, fix a baseline and its spread at the original width, then hold every other condition still and step the width down alone, repeating the same test. Once the breaking point appears, stop one notch above it. Keep that order and you trade the unanswerable question of which model is better for the answerable one of whether this width holds up in your work.

What could not be confirmed

  • The exact per-metric scores - the source presents results as bar charts and describes them in prose in the body text. Values read off a chart by eye cannot be guaranteed for precision, so they were not carried into this article as numbers, and only what the source states in sentences was carried over
  • Repeat count, temperature, seed and sample sizes - none of these values appear in the source. There is only the note that error bars are Wilson 95 percent confidence intervals, without stating how many items those intervals were computed over
  • The internal rules of the dynamic quantization line - the distributor documentation explaining what the calibration data is, how per-layer widths are allocated, and how labels with the UD prefix differ from those without could not be opened. The documentation address had moved and two attempts both returned no content, so the attempt was stopped as the rule requires. Only the existence of the labels and their family marking were carried over, with no description of the internal rules
  • Official definitions of the K-family and I-family labels - the quantization tool documentation in the llama.cpp repository lists the labels and a size table, but does not explain what each letter in a name such as Q4_K_M or IQ1_S means. Nor does it state for which labels an importance matrix is required
  • The file size of UD-IQ1_M - the source records sizes for the other labels but not for this one
  • The agentic coding value for Q8_0 - the source itself states that this combination was skipped and the value interpolated. The 8-bit point is therefore not a measured one
  • Results with the KV cache narrowed too - the source held the cache at F16 and noted only that cache quantization might be tried later. The cache material here stops at the size arithmetic, and quality effects cannot be stated as values
  • Identity with the replaced files - after the distributor replaced the 2-, 4- and 8-bit files, whether the current files under the same names match the ones used in the tests was not settled by the source either. Anyone attempting reproduction runs into this first
