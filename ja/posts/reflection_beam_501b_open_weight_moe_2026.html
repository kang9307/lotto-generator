発表の概要 — 501Bオープンウェイトモデル Beam と重み公開予定の範囲

2026年10月5日、Reflectionは同社初のオープンウェイトモデルBeamを発表した。重みは今月中に公開する予定で、発表の時点ではまだダウンロードできない。Beamはコーディング、推論、エージェントのワークロードを狙って作られたスパース混合エキスパート（Sparse Mixture-of-Experts、以下MoE）モデルだ。総パラメータは5,010億個（501B）で、トークンあたりのアクティブパラメータは230億個（23B）である。

原文は、Beamの能力は事前学習と強化学習（RL）の両方への大きな投資から生まれたと説明している。ウェブと独自のライセンスデータセットから選んだ23.8兆トークンで事前学習し、10.5K基のNVIDIA GB300 GPUで4週間、1億回を超えるロールアウトを生成する高計算量のRLを回した。原文はこれらを合わせて「フロンティア級の推論計算効率を備えた、競争力のあるオープンウェイト性能」とまとめている。

  • 公開日程：重み、技術レポート、モデルカード、開発者向け成果物を今月中（later this month）に公開すると書かれている。
  • ライセンス：今月中にApache 2.0ライセンスで重みを出し、モデルを実行・評価・ファインチューニングするためのドキュメントと全スタックも合わせて公開する計画だという。ローンチ時には配布パートナーのエコシステムや、多数のオープンソースライブラリとの統合も打ち出すとしている。
  • 現在のアクセス：モデルは最終的なレッドチーム評価と評価の途中で、原文は早期アクセスの申し込みリンクを案内し、選ばれたユーザーグループにだけ早期版を提供し、順番待ちリストを受け付けていると書いている。

したがって現在のBeamは、すでに配布されたオープンソースではなく、仕様とベンチマークが発表され、重みの公開が予告されたモデルである。この記事は原文が示す数値とその計算の分母を区別して書き、原文が述べていない部分は別にまとめておく。

アーキテクチャ仕様 — 総501B・アクティブ23Bのスパース MoE

Beamは総501Bパラメータのうちトークンあたり23Bがアクティブなスパース MoEモデルである。アクティブの割合は23÷501で約4.6%だ（計算）。原文は、アーキテクチャと最適化のレシピが、持続的な後続のRLの基盤となる数値的に健全な土台を重視していると説明し、事前学習の検証を次のように記している。段階的に大きくなるモデルの系列を事前学習してスケーリングのレシピを確立・検証し、最終的なBeam Baseは予測された性能と一致し、アクセス可能な同程度の大きさのオープンなベースモデルと同等かそれ以上だという。

  • 構成要素：ローカルアテンションとグローバルアテンションの交互配置、細分化されたルーティングエキスパート（fine-grained routed experts）、制御された残差ストリーム、複数の形のロードバランシングを組み合わせたと原文は要約している。
  • エキスパートの負荷分散：補助損失なしのロードバランシング（auxiliary-loss-free load balancing、DeepSeek-AI et al., 2024）を土台に、学習後半のルーティングの乱れを減らすため、エキスパートバイアス（expert-bias）の更新にコサイン減衰を導入した。
  • シーケンスレベルの均衡：事前学習の分布の外のデータでもエキスパートの利用が均等になるようシーケンスレベルの均衡を加え、下流のRLの分布の変化に備えるものだと説明している。
  • 均衡の結果：事前学習が終わった時点のベースはほぼ完全に均一な利用を示し、最も忙しいエキスパートの負荷はMoE層の平均で1.04倍だったという（Figure 7）。
  • 残差ストリーム：深さに応じたスケーリング方式でサブレイヤー出力が積み重なるときの活性化の増大を打ち消し、SandwichNorm、要素ごとのアテンションゲーティング、FP32での残差の累積（小さな更新を足すときの丸め誤差を減らす）と組み合わせた。
  • 安定性の範囲：52層すべてで残差ストリームのRMSが事前学習の間ずっと有界に保たれ（Figure 8）、この安定性が事前学習、強化学習、アライメントを通じて続いたと書かれている。

原文は、モデルがアクティブパラメータ基準でどれだけ軽いかを、ホスティングの要件に換算して説明してはいない。全重みをサービングするのに必要なメモリやGPU構成は原文になく、この記事もその数値を作らない。

事前学習とインフラ — 23.8兆トークンと6,144基のGB300

原文は、Beamをウェブ、公開ソース、独自のライセンスデータセットから集めた多様な高品質トークン23.8兆個で事前学習したと書いている。データパイプラインは、ソースコード、技術的な説明、数学と科学の知識をすべてのキュレーション段階で保存し、下流のエージェント的コーディングの土台を作るよう設計された。ウェブでアクセスでき、制限のないライセンスのコードとコードのドキュメントはほぼすべて学習に使ったという。

  • フィルタリング：パース、重複除去、キュレーションを経て、生のインターネットトークンの約95%が除かれる。一方、従来の手法なら見逃したはずの約1.8兆個の高品質トークンを保持しており、これにはキュレーションされたウェブコードトークンの87%が含まれる。1.8兆は最終選別の総量ではなく、従来のフィルタが見逃したはずの分量である。
  • 品質分類：ウェブ、コード、STEMコンテンツ向けの品質分類器を自前で学習し、データを細かな品質のティアに分けて、良質な素材に学習の重みを傾けた。
  • PDF処理：視覚言語OCRモデルに、自前の品質分類器と誤って復元された成果物を捉える欠陥検出器を組み合わせた高スループットのパイプラインを数千基のGPUに分散し、ペタバイト規模の技術データを処理した。
  • 計算インフラ：6,144基のNVIDIA GB300 NVL72 GPUのクラスターで4週間足らずで事前学習を終えた。トポロジーを認識するKubernetesベースのスケジューラ、ノードのライフサイクルシステム、半自律的な巻き戻しと再起動ができるサイレントデータ破損（silent data corruption、SDC）検出システムを自社で構築した。
  • 学習の安定性：非決定的な勾配ノルムの急上昇またはSDCの疑いが原因の半自動の巻き戻しを9回実行し、損失曲線には大きな不安定は観測されなかったという（Figure 9）。
  • Goodput：終盤に92.3%に達した。原文の定義では、最終モデルに残った学習ステップに費やした実時間（wall-clock）の割合である。

事前学習のあとのミッドトレーニング（midtraining）は、高計算量RLの土台を作るよう設計された。実際のタスクの構造と複雑さを取り込む多段階のデータキュレーションパイプラインで学習データを作り、有効コンテキスト長を100万トークンに拡張した。構造化されたコードリポジトリ、長期的なタスク、高品質の長文ドキュメントを組み合わせ、長い系列の中で関連する情報を見つけてつなぐことを教えるという。

高計算量の強化学習 — 10.5K GPUと1億回超のロールアウト

原文は、高計算量RLをBeamのスケーリングの中心軸にしたと説明している。10.5K基のNVIDIA GB300 GPUを4週間投入し、最大コンテキスト長256Kトークンで1億回を超えるロールアウトを生成し、学習と採点に約13億個のサンドボックスを使った。原文は、これはこれまでにオープンなラボが行った最大規模のRLの1つだと信じていると書く。評価スイート全体で、RLの計算を増やすほど能力が向上し続け、頭打ちの兆しはなかったという。

  • 環境：合成データのパイプラインを中心に、独自のベンダーデータとオープンソースの出典を加えた、ほぼ100万個の環境を作った。ドメインはソフトウェアエンジニアリング、ターミナル利用、競技コーディング、STEM、ウェブ検索、ツール使用、一般的な知識業務である。
  • 環境のキュレーション：タスクを合成または収集し、難易度（常に解けるわけでも不可能でもない）と品質（不明確、推測可能、ハック可能なタスクを除く）で絞り込み、RLで試して次の収集とフィルタリングに反映する反復の過程である。
  • サンドボックス：最大17万個を同時にサポートし、サンドボックスの作成要求は10億件を超え、20を超えるクラスター、2つのクラウド、4つのリージョンにまたがった。新しいサンドボックスの90%は10秒以内に準備できた。
  • 非同期実行：学習中は平均11万個のロールアウトが同時に動いた。トークンごとに生成したモデルのバージョンをタグ付けし、ポリシーの陳腐化（staleness）を学習アルゴリズムが考慮できるようにして、現在のポリシーより107の重みバージョン、約1日遅れたサンプルで学習しても数値が安定していたという（Figure 4）。
  • 計算の配分と重みの更新：推論と学習のGPU比率を3.9:1から5.4:1まで調整した。新しい重みは推論フリートに中央値で約12秒で反映され、ラック間のRoCEとラック内のNVLinkによる階層的な転送でラック間トラフィックを75%減らし、反映の速度を2.2倍にした。
  • 障害からの復旧とパッキング：学習中に起きた推論の障害71件を学習ジョブを止めずに処理し、容量は中央値8分で復旧し、失われた容量は経過したサービングGPU分の0.02%だった。動的パッキングで学習バッチは平均99.99%満たされた。

報酬の設計では、成功した解決を報酬とし不要なトークンを抑える、調整可能な長さペナルティを使った。RLの序盤は応答の長さが短くなりながらも性能が向上し、その後エージェント能力が強まるにつれて応答の長さが再び伸びたが、その追加のトークンが性能の向上を支えたという。ユーザーは推論の労力（reasoning effort）パラメータでこのバランスを調整できる。Figure 3は、全体で1億回を超えるロールアウトのうち推論エキスパートの学習に使われた8,000万回を示し、比較としてInklingは3,000万回、MiMoは75万3千回で学習したと書かれている。

「推論計算量3〜4分の1」という主張の算出式と除かれたコスト

原文は、高度な推論ベンチマークでBeamがGLM-5.2に匹敵するスコアを出しながら、推論計算量は3〜4倍少ないと書いている。2T+パラメータ級のモデル（例：Qwen 3.8-Max）と比べると、トークンあたりでずっと多くの計算が必要になるので効率の差はさらに際立つとも述べている。この主張の計算の分母はFigure 2のキャプションにある。以下はそのキャプションの全文で、読みやすいように文ごとに改行した以外は原文のままである。

Figure 2: Beam demonstrates frontier-level inference efficiency, both when measured in terms of FLOPS and token count across DeepSWE, Humanity’s Last Exam (HLE), and Terminal Bench 2.1.
                    We used data from Artificial Analysis and DataCurve, estimating generation forward-pass compute as FLOPs ≈ 2 × active parameter count × mean generated tokens per attempt, counting each multiply-add as two operations.
                    Generated tokens include both reasoning and the final answer.
                    For mixture-of-experts models, we used the parameters activated per token rather than the total model size.
                    These estimates exclude prompt prefill, context-dependent attention operations, and serving overhead, so they represent an approximate compute comparison rather than measured inference cost.
                    We use Artificial Analysis and DataCurve as sources for other model’s evals.

キャプションを読むと、この比較の前提がわかる。

  • 推定式：生成の計算量は、アクティブパラメータ数にattemptあたりの平均生成トークン数を掛けて2を掛けた値で、積和演算1回を2回の演算と数える。
  • 生成トークンの範囲：生成トークンには推論の過程と最終的な答えの両方が含まれる。
  • MoEのパラメータ基準：MoEモデルでは、モデル全体の大きさではなくトークンごとにアクティブになるパラメータを使った。
  • 除かれたコスト：プロンプトのプリフィル、文脈に依存するアテンション演算、サービングのオーバーヘッドが除かれており、測定された推論コストではなく大まかな計算量の比較である。

したがって「3〜4分の1」は、GPUクラスターの電力やホスティングのコストを測った結果ではなく、アクティブパラメータとattemptあたりの平均生成トークン数で推定した計算量の比較である。この式では、attemptあたりの生成トークン数が多いモデルほど推定計算量が大きくなる。

エージェント能力の転移事例と重み公開前に確認すること

原文は、RLを訓練タスクを超えて一般化する能力を育てるよう設計したと説明している。推論、ソフトウェアエンジニアリング、ターミナルのタスクを学習する段階で、RLの混合にブラウジングのタスクがなかったのにブラウジングの性能が着実に向上し、ウェブアクセスを与えられると、他の大規模言語モデルを検索して問い合わせ、OCR APIで文書を読むことを自ら身につけたという。原文は、Beamはテキスト専用だがテキストで表された他のモダリティの情報を扱えると付け加えている。

  • デモの事例：p5.jsの3D宇宙飛行士ゲーム、ニューヨークMTAの公開データで作ったリアルタイムの地下鉄マップ、小型モデルGemma-4向けのText2SQLファインチューニング用ノートブックの作成が紹介されている。ノートブックでGemmaをファインチューニングし、保留したテストセットの精度が66.5%上がったという。
  • 陸と海の実験：180×90の格子の16,200点の問題で95.5%を正解し、Opus 5（92.5%）とFable 5（97.8%）の間だと原文は書く。この値は原文自身のデモの結果である。
  • 安全とアライメント：事前学習のチェックポイントから別のSFT・RLパイプラインで安全・アライメント用のモデルをもう1つ学習し、マルチティーチャーのオンポリシー蒸留（MOPD）で2つの教師の能力を統合した。安全評価の結果は技術レポートに載せるという。
  • 重み公開後の確認：重みの公開時にApache 2.0の条項が実際の配布物にどう適用されるかは、公開されたライセンス文書で確認するのが望ましい。

要するに、原文が確認させてくれるのは、仕様、学習の規模、発表されたベンチマークの値、計算量の推定方法である。重みを実際に入手してサービングするまでは、原文の数値はReflectionの報告として読む必要がある。サービングフレームワークの対応状況のような実務的な情報は原文にないので、下の「確認できなかったこと」に残す。

確認できなかったこと

  • 重みが実際に公開されたかどうか、公開されたチェックポイントの容量と量子化版の計画。原文は今月中に公開するとだけ書いている。
  • 501Bの重みをホスティングするのに必要なハードウェア要件。原文にはサービングの要件がない。
  • vLLMやSGLangのようなオープンソースの推論エンジンの対応の有無と時期。原文は多数のオープンソースライブラリとの統合を予告しただけで、具体的な一覧はない。
  • 事前学習の23.8兆トークンのうち、ウェブ、公開ソース、独自のライセンスデータの構成比。
  • ベンチマーク表の値を第三者が独立に再現したかどうか。表はReflectionが発表したものである。
