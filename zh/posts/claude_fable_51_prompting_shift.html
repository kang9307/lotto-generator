还能跑和不用改是两回事 - 把提示词从 Claude Fable 5 迁到 5.1 时该重测什么

effort 扫描、三项破坏性变更、只能追加的会话历史。迁移时真正需要重新测量的地方

2026年9月4日 IT/技术

模型版本号往上跳一个小数位时，大多数团队什么都不做。只把名字换掉，看着还能跑就放在那里。这种做法危险的地方不在于会坏，而在于不会坏。没有显眼的失败就没有回头看的契机，而在这期间，提示词里有一半会变成存在理由已经消失的句子。

Claude Fable 5.1 的提示词指南在开头第一句就承认了这一点：现有的 Fable 5 提示词不作改动也应当表现良好，只是有若干值得知道的行为差异。本文只从迁移这一个角度去看那个若干。既不谈模型在什么上变强了，也不与别家模型比高下。轴心是已经在跑的提示词里，哪些地方需要重新测量。

正文中的规格、价格、模型 ID 与默认值，均为2026年9月4日从官方文档确认的数值。这类值几周就会过时。实际应用前请务必到原始页面复核当前值，并用自有评测集验证厂商的性能主张。未能确认的项目单独汇总在文末的专门小节。

缘起 - 一份以照旧能跑开篇的文档

2026年9月初，这份指南在韩国开发者社区被转发，其中一条反应大意是非得写得复杂，想写得简单就贵。这句话抓住了文档性质的某一面。它与其说是功能介绍，不如说更接近一份症状索引。开篇是这样排列的：工具调用之间几乎没有文本，去这一节；智能体循环里每轮只有一次工具调用，去这一节。

这种形式本身说明了一件事。那里写着的变化都不会报错。如果会报错，索引就没有必要了。它们表现为屏幕安静下来、多出一轮、回复变得密而难读。这是那种在部署几周之后，以最近好像有点慢的感觉被发现的差异。

Fable 5 这一代本身的背景，本站已有整理。发布时点的规格在第五代模型发布解读，适合接哪些活在实战应用案例，并入套餐的情况在Max 与 Team Premium 上限一文，围绕访问管制的经过分在出口管制禁用与管制解除两篇。本文是叠在其上的迁移视角一篇。

从迁移角度最先跳出来的是最后两行。数据保留要求和不支持 Priority Tier，会在与提示词无关的层面挡住部署。提示词打磨得再好，只要组织设置是零保留，请求本身就以 400 落地。按顺序先把这两项清掉再往下走更合适。

三项破坏性变更 - 只有这里真的会坏

前面说这次迁移的风险在于不会坏，准确地说有三处是会坏的。这三项与症状索引里的其余条目性质不同。其余的是悄悄抬高成本那一类，而这三项是请求以 400 落地，或者数据悄无声息消失那一类。所谓大多照旧能跑，说的是除这三项之外的其余部分。

会坏的地方如何显现应对
不支持强制工具调用把 tool_choice 设为 {"type": "any"} 或 {"type": "tool", "name": "..."} 会返回 400 invalid_request_error。词元计数端点也走同样的校验。auto（默认）与 none 不变若需强制模式，保持 auto 并转到严格工具使用或结构化输出。若要让它调用某个工具，就在提示词里写明何时使用该工具
thinking 块与生成它的模型绑定每个 thinking 块都记录是哪个模型产生的，保留是单向的。Fable 5.1 能读 Opus 5、Fable 5、Mythos 5 及更早模型的块，但那些模型都读不了 Fable 5.1 的块会话往 5.1 上走的方向保住推理。反过来，路由或回退在中途切回旧模型，那一段的推理就丢了。按这个方向设计回退路径
编辑先前轮次会使之后的 thinking 块失效系统提示词、工具清单或任一先前消息发生变化后再回放 thinking 块，返回 400。对2026年8月31日及之后创建的账号强制执行把历史当作只能追加来处理。下面有专门一节展开

第二项带着悄无声息地发生这一限定，值得单独看。当请求携带了目标模型读不了的块时，API 会在模型看到之前把它丢掉。被丢掉的块不计入 input_tokens，也不计费。问题在于通知。使用 thinking-binding-controls-2026-08-01 测试版标头时，这件事会报告在顶层的 input_transformations 数组里，而没有该标头时，丢弃是静默的。也就是说，如果你有一个会切换模型的路由，推理可能每次请求都被扔掉，而账单和响应里都不留痕迹。

拒绝的处理不属于破坏性变更，是从 Fable 5 原样延续下来的，但放进迁移清单里更稳妥。被拒绝的请求以 HTTP 200 返回，带着 stop_reason: "refusal" 以及标明触发了哪个策略领域的 stop_details。因为它不是错误码，不会走进异常处理路径，所以需要在读取响应正文之前先看 stop_reason 的代码。在产生任何输出之前到达的拒绝不计费，Fable 5.1 允许的回退目标是 Claude Opus 4.8 与 Claude Opus 5。

effort - 迁移时最先要动的值

effort 调节的是模型在一次回复上花掉的词元量。这里常有一个误解，以为它调节的只是思考块。官方文档明确写着 effort 影响回复中的所有词元：文本回复与解释、工具调用及其参数，还有思考。所以在不动用思考的请求上 effort 依然起作用，而在低 effort 下，工具调用本身也会变少变短。

级别有五个，文档给它们附的说明如下。

级别文档的说明文档举出的用途
max不对词元消耗设限的绝对最高能力需要尽可能深的推理与最彻底分析的任务
xhigh面向长周期工作的扩展能力超过30分钟、词元预算以百万计的智能体与编码任务
high高能力。等同于不设置该参数复杂推理、困难的编码问题、智能体任务
medium带适度词元节省的平衡点需要在速度、成本与性能之间取平衡的智能体任务
low最高效。显著节省词元，伴随一定能力下降需要最快速度与最低成本的简单任务，例如子智能体

文档补的一句限定很重要。effort 是行为信号，而不是严格的词元预算。在较低级别上，面对足够难的问题模型依然会思考，只是比在高级别处理同一问题时思考得少。所以不能把 low 读成关闭思考。这个模型上根本就没有关闭思考的开关。

提高级别时增加什么、减少什么，文档也分开写了。高级别下工具调用次数增加，行动前会先说明计划，变更摘要更详细，代码注释更多。低级别下多项操作合并为更少的调用，不作铺垫直接执行，完成后的确认消息更短。effort 与其说是质量旋钮，不如说更接近话量与动作总量的旋钮。如果界面本来就依赖模型的说明，那么调低 effort 的同时屏幕也会跟着空掉。

medium 更便宜且相当，确切条件是什么

这一段被截断引用得最多。原文的结构是这样：Fable 5.1 相对 Fable 5 的能力提升体现在各个 effort 级别上，并在较高设置上最大。而在 medium 上，结果大体与 Claude Fable 5 相当而成本更低，因此在自有评测显示质量得以保持的地方降到 medium 或 low。

限定条件叠了三层。

  • 比较对象是上一代。medium 追平的对手是 Fable 5，不是 Fable 5.1 的 high。是保住 5 的水准而更便宜，不是完整保住 5.1 而更便宜
  • 句中有大体二字。这是近似表述，不是对等宣告。理解为可能随任务性质而分化更稳妥
  • 在自有评测显示质量得以保持的地方这一限定就摆在那里。这是把核实责任交给使用方的句子。没有评测集就下调，不在这句话许可的范围内

同一节里还有一句关于 low 的话：低 effort 的 Fable 5.1 在每任务成本上往往可与 Claude Opus 和 Sonnet 系列一较高下，同时分数更高，所以凡是本来要用更小模型跑更高 effort 的场合，都可以把它放进比较对象。不过这是厂商对自家模型阵容作出的自我评估，用哪些基准、在什么条件下测的，这份文档里并未出现。所以这句话的用处止于把它加进候选名单，再往前就只能在自己的负载上测。

如果确实要评估 low，有一个随之而来的副作用需要先知道。在 low 上，Fable 5.1 调用检索类工具的次数比 Fable 5 少，更倾向于凭记忆作答。依赖检索的产品为省成本降到 low，省下的词元有多少，时效性就削掉多少。文档给的应对有两种：只对相关轮次提高 effort，或者在系统提示词里加一句，大意是在变化很快的领域里认得一个名字不等于知道它的现状，所以要按用户书写的原样去检索。

为什么扫描要从头再来

这次迁移里最便宜就能拿到的教训在这里。指南写道：即便已经在 Claude Fable 5 上跑过扫描也要重跑，因为 effort 的级别名称在不同模型之间并不对应同样的思考量。

这句话的意思很简单，后果却不小。medium 这个名字是相对刻度，只在某个模型内部有意义，而不是绝对刻度。Fable 5 的 medium 与 Fable 5.1 的 medium 是同一个名字，不是同一个量。所以上次我们得出 medium 最优这条记录，在模型更换的那一刻就失去了作为依据的寿命。陷阱在于配置文件里留着的那个值看上去依然有效。因为没坏，所以不会再看。

迁移指南从另一个角度重复了同一点：从 high 开始扫描，不要继承为 Fable 5 调好的设置，用自有评测集重新跑。随后它补了一条限定：5.1 的提升在 xhigh 与 max 上最大，但那两个级别同时也拉长思考时间和首次响应时间。得到的与失去的绑在同一个旋钮上。

Fable 5.1 还多了会话中途改 effort 的办法。插入一条不带文本、只载有 output_config 的 role: "system" 消息，新级别从下一个用户轮次开始生效，而且提示缓存不会失效。需要测试版标头 mid-conversation-output-config-2026-07-01。

{"role": "system", "content": [], "output_config": {"effort": "low"}}

文档建议在 Fable 5.1 上优先用这种形式，而不是改顶层值。理由有两条，第二条更有意思。改顶层值不仅让缓存从头开始，还对模型的引导更不可靠：它先前的回复是在旧级别下写的，它倾向于与那些回复保持一致。风格在一段会话里是有惯性的。

进度更新变少了，以及买回来的代价

实务中最先被感知到的变化很可能是这一项。Fable 5.1 的默认行为是在长时间的工具调用轮次中写比 Fable 5 更少的面向用户的文本，而且 effort 越高、工具链越长，这个倾向越明显。用户看到的是智能体一次安静好几分钟，或者最后一条消息只概括了最后一步而不是整件事。

这里守住顺序很重要。文档建议的第一步不是去改提示词。

  1. 先确认客户端到底收不收得到更新。模型在工具调用之间写的简短笔记（找到了什么、接下来做什么）以进度更新用的 thinking 块返回。而 thinking.display 的默认值是 omitted，所以那些块是空的。有可能你压根就没在请求它们
  2. 打开显示设置。设为 display: "updates"（测试版标头 thinking-display-updates-2026-08-18），就能在推理仍然隐藏的前提下，以文本形式收到进度更新。此时凡是内容非空的 thinking 块，直接渲染成状态行即可。"summarized" 则把它们与摘要过的推理混在一起返回
  3. 找出并删掉旧的抑制语句。早前的模型工作中更新给得太多，那个时期加进去的把所有发现留到最终回复之类的句子，常常还留在系统提示词里。在添加任何东西之前先把它拿掉
  4. 如果还不够，这时才去要求。把何时给、给什么都指定清楚：开始前用一行说明将要做什么，工作中给简短更新，最后给一段能独立成立的收尾摘要，让只看到最后一条消息的读者也能掌握全貌

之所以要守这个顺序，是因为权衡是实打实的。要求更多更新会增加输出词元并拉长轮次。如果这本来只需打开显示设置就能解决，或者沉默本来只是残留的抑制语句造成的，那笔费用就根本不必付。跳过顺序直接从第4步做起，原本就有的更新会与你要求的更新叠在一起，等于付了两遍。

还有一个相关的陷阱。如果产品的界面会折叠或隐藏工具输出，就要把这件事告诉模型。否则模型会为了给用户看而执行命令，而那些输出根本不会出现在屏幕上。文档建议把这条说明以轮次范围的系统消息（clear_at: "next_user_message"）传达。

把互不依赖的工具调用合进一次回复

Fable 5.1 多数时候会按预期发出并行的工具调用：请求明确点名了多个对象时，它会并行调用。出问题的地方窄而具体。当接下来需要的独立调用不是被明确要求的，而是由任务性质隐含的时候，也就是在自定义编码智能体、bash 与编辑器构成的框架、计算机操作循环里，它可能每轮只发一个。

文档把一点讲得很清楚：这不会降低回答质量。多出来的每一轮要花词元、一次往返和实际时间，这就是全部成本。所以这一项不会以质量回退的形式被抓住，只会显现在账单和体感速度上。应对是在当前请求末尾附上的一句话。

{
  "role": "system",
  "clear_at": "next_user_message",
  "content": "First privately list what you need next; then request every item that doesn't depend on another's result in this one response."
}

问题出在顺序依赖被藏起来的时候。这句话的防线只有不依赖他者结果的项目这一个条件从句，而作出判断的是模型。如果掺进了实际有顺序、但在模式定义上看不出来的工具——先拿锁再写的工具、读取先前调用所生成文件的工具、改变状态的工具与查询该状态的工具——批处理指令就可能一脚踩过那层依赖。防线放在工具那一侧更可靠：在描述里写明前置条件，让顺序不对的调用由工具返回错误。

放在哪里也有规矩。每次把工具结果送回去时，都在那条用户消息之后追加一份新的轮次范围系统消息，并且把先前的副本逐字节原样留着。一旦之后出现了用户消息，API 会清掉先前的副本，模型只读最新的那一份，被清掉的副本不消耗输入词元。删掉或改写它们就是在编辑先前轮次，而那正是下一节的主题。

会话历史变成了只能追加

这是迁移中最可能真的需要改代码的一项。规则一行就能说完：把助手轮次按 API 返回的原样、连同 thinking 块一起追加到历史里，并且不要在两次请求之间编辑先前的轮次。

强制的时点写得很明确。对2026年8月31日及之后创建的账号，Fable 5.1 的 thinking 块只在产生它的那一段会话里有效。前缀（系统提示词、工具清单或任一先前消息）发生变化之后再回放 thinking 块的请求会被 400 拒绝，错误信息的意思是该块绑定在另一段会话上。更早创建的账号目前还不强制，但文档说预计未来的模型会对所有账号强制这项检查，因此要现在就采用这个模式。也就是说今天能通过，并不构成明天的依据。

什么会触发检查、什么不会，文档分成两列列了出来。

会使之后所有 thinking 块失效不会使其失效
编辑、重排或删除先前轮次而保留之后的轮次从思考块序列的最前面连续地移除
每次请求往先前轮次注入提醒或状态行，下次请求再抽走让服务端压缩或上下文编辑去削减历史
在同一段会话中重建顶层的 system 或 tools 数组移动 cache_control 标记的位置
图片或文档 URL 在后续请求中返回不同的字节（检查看的是字节，不是 URL）在两次请求之间改变 effort

右列第一行附着一个条件。从最前面以外的位置抽走 thinking 块，会让它之后的所有 thinking 块失效。条件是从旧到新连续，而不是随便哪个旧的。从中间剪掉的那种优化在这个模型上不成立。

怎么查出自己的框架已经在编辑什么，文档也给了办法。带上测试版标头 thinking-binding-controls-2026-08-01 并使用下面的设置跑一段会话，记录响应里的 input_transformations，就会列出什么因为什么原因被丢掉。换模型之后出现的模型绑定不匹配条目属于正常，前缀绑定不匹配的条目才是要修的。

"thinking": {
  "block_binding": { "prefix_mismatch_behavior": "drop_block" }
}

旁边还并列了一个更简单的检查法。把框架在几个普通轮次里实际发出的请求原样抓下来，只看相邻两次请求在除去追加的轮次之后是否逐字节一致就行。这比读代码快，而且能抓到自己都没意识到在做的编辑。

长会话里留下什么、丢掉什么

把历史变成只能追加之后，接着就是那个问题：那越来越长的会话怎么缩。文档的第一答案是把缩减这件事交给服务端。服务端压缩与上下文编辑不算作编辑，因为检查比较的是你发送时的那份会话，所以它们移除的东西不会让之后的 thinking 块失效。

如果坚持在客户端做压缩，文档认可三种形态。

  • 简单压缩（推荐）。把整段历史整体替换为一条摘要消息加上新的用户轮次，其余一概不回放。没有 thinking 块被带过去，所以不存在会失败的东西，模型在压缩后的会话之上重新思考。文档提到 Claude 模型正是以这种方案训练长周期任务的，在多数负载上与更精巧的方案表现相当
  • 保留尾部的压缩。若要在摘要之后原样保留最近的几轮，就必须从那些轮次里剥掉 thinking 与 redacted_thinking 块（文本和工具调用可以留）。那些推理是基于完整历史产生的，在摘要之后并不成立
  • 后台压缩。如果摘要是在关键路径之外构建、稍后再换进去的，那么这期间产生的每一轮都带着换入之前的思考。要对所有仍携带换入前块的请求发送 drop_block，或者干脆改为同步压缩

三种形态有一条共同禁令。不要从记录中间剪掉单独的轮次。文档明确说，没有任何客户端侧的形态能避开这一点。

成本判断上还附带一个反转。由于 Fable 5.1 的缓存读取降到了基础输入价的0.025倍，文档说为省成本而提早压缩可能已不再是正确的取舍，建议把压缩的时点往后挪着试。如果迁移前的正解是长会话早点截断，那么这个判断的前提本身已经变了。套餐上限该怎么读、什么才是真正的成本，另在如何读懂 AI 套餐的用量上限里处理，而该往智能体里放什么这个设计问题在上下文工程实战规则里。

如果摘要由自己构建，指南整段给出了一份摘要指令。主旨是有六样必须保住：出现过的困难及其处理方式，提出、尝试或搁置的选项及其原因，凡是被要求、决定、同意、排除或确立为约束的内容要按原话保留，目前进展到哪一步，仍未了结或已作出承诺的事项，以及难以重建的具体信息（姓名、数字、日期、确切措辞、链接）。再附一条指令：给两种声音不同的权重。用户说过的要贴近他本人的措辞保留，模型自己的解释与推理则可以压缩得多得多，压到结论与产出的程度。

输出格式 - 旧的抑制规则如今反着起作用

输出格式的变化特殊在方向翻转了。早前的模型在对话里过度使用项目符号和加粗，为压住这一点而写的反格式规则，还原样留在许多提示词里。可 Fable 5.1 是往另一侧偏的：用加粗更少，也更不容易去用标题、列表或引号。旧的抑制规则叠在上面，连内容本身需要的结构都会被压掉。

文档给的处方是删掉那些句子，或者把禁止改写成条件：在被要求时、或内容足够多面而分点有助于清晰时使用列表；用户明确要求最简格式时就照办；在对话式、私人或带情绪的交流中保持纯文字。要点是从不要用挪到这种时候用。

散文密度是另一个条目。Fable 5.1 的文字套话更少、未加解释的术语也更少，但某些情况下比 Fable 5 更密，句子更长、分段更少。对此文档给的处方很有意思：不是写短一点，而是把反面模式定义给它。先说明以比喻和辞藻代替直陈的写法为什么有问题——让读者更费力以便作者表演，而比喻会带进作者没有选择的联想——再以有字面表达可用时就用它收尾。文档还说简短版本通常也管用。

摘要时不加引用标记就搬原文，也被归到格式问题里。Fable 5.1 在概括文档时，比 Fable 5 更容易不加标记地复现原文段落。处方不是规则，而是一个完整的示例：把用户的请求、正确的回复，以及解释该回复为何正确的一句话，整体放进系统提示词。

文档列出的其余默认行为变化

其余条目各自都短，但先扫一眼哪些会落到自己的负载上是划算的。

  • 活还没干完轮次就结束了。在复杂的异步任务里，模型有时会把接下来该做的事描述出来而不是做掉，或者为原始请求本已涵盖的步骤停下来征求许可。文档建议把两段系统提示词一起放进去，并说明若必须削减长度，仅第一段也能保住大部分效果。其中用户并未实时盯着这第一句承担了相当一部分作用
  • 没要求的修改和测试会跟着来。它可能顺手改掉附近的代码、扩展任务没提到的行为，或者提交比改动规模更多的测试文件。文档说，明确写出该排除什么之后，未经要求的追加大幅减少，而任务成功率没有可测量的变化
  • 小改动却重写整个文件。产物通常一样，但多花输出词元和时间。一句话——在其他条件相同时，用于编辑文件的词元以最小化为宜——就能让中小规模的改动回到 Fable 5 的水准
  • xhigh 与 max 上长产物会被截断。当一次请求要求一份长产物时，会出现在思考里先写好草稿、再作为回复写第二遍的情况。等待变长，输出词元翻倍。首选处方是把这类请求放在推荐起点 high 上跑；若确实要往上调，就按思考加回复的合计而不是回复长度来设 max_tokens
  • 安全分类器的误报。文档点出三种更容易误报的情形：询问能否编译的措辞（改问这个程序里有没有 bug）、较冷门的编程语言，以及经由工具输出进来的 base64 数据。在源代码中查找漏洞这件事本身是被允许的

迁移流程 - 做 A/B 要固定住什么

把上面这些一次性全部应用，就会搞不清是什么改变了什么。让迁移变得可测量的原则只有一条：一次只动一个轴。

阶段改动的固定的测量的
0什么都不改，在现行 Fable 5 上采集基线全部质量分、轮数、输入输出词元、首次响应延迟、总耗时
1只把模型 ID 换成 claude-fable-5-1提示词、effort、工具定义、评测集与阶段0相同的五个指标。这里拉开的差距就是默认行为变化
2只对 effort 做五个级别的扫描提示词、工具定义、评测集各级别的质量与成本、延迟。这张表成为生产级别的依据
3提示词，一次改一条模型、effort（阶段2的结论）、评测集逐条的效果。先做旧抑制语句的删除，再做新句子的添加

最常被违反的是阶段1，因为换模型时顺手把提示词也改了，感觉上很自然。可只有纯粹地守住阶段1，才能知道文档所说的默认行为变化在自己的负载上是否真的出现。在有的组织里进度更新变少根本不成问题，在另一些组织里它就是头号课题。

不把比较指标只放在质量上同样重要。文档指出的多数变化是被设计成不体现在质量上的变化。工具调用批处理被明确写为不影响回答质量，整文件重写也被写为产物通常一样。只看质量分，两者都会以没有回退通过，而成本悄悄上涨。这正是迁移指南在重新评测之外还要强调在自己的负载上重新采集成本与延迟基线的原因。词元数大体不变，但缓存读取的单价变了，会话长度与缓存命中率不同的负载不会朝同一个方向移动。

固定模型 ID 到底买到了什么

看重可复现性的团队大多有一条规矩：用带日期的版本 ID，不要用别名。别名哪天悄悄指向新的快照，昨天通过的评测今天就崩了。而在这一代，这条规矩的前提变了。

模型总览文档的脚注写明了：所有 Claude 模型 ID 都是固定的快照，包括自4.6代起使用的不带日期的 ID。对4.6之前的模型，别名是解析到带日期 ID 的便利指针；而不带日期的 ID 本身就是固定快照，别名那一行只是把同一个值重复了一遍。

因此 claude-fable-5-1 不是指向此刻最新版本的名字，它本身就是快照。为了可复现性去找一个带日期的另一个 ID 没有必要，而且找也找不到。同一张表的其他行里仍然出现带日期的形式（Haiku 4.5 的 API ID 是带日期的，别名是不带日期的），所以粗看这张表容易生出 Fable 5.1 大概也有带日期形式的印象。规则因代际而异，这才是这张表的陷阱。

真正该操心的另在别处。ID 固定不等于模型永在。退役承诺是以 Anthropic 自营平台为准不早于2027年9月1日，而 Amazon Bedrock 与 Google Cloud 各自另定日程。同一个 ID 在不同平台上寿命不同。而且可复现性并不由 ID 单独决定。这个模型对 temperature、top_p、top_k 传入非默认值一律返回 400，所以根本就没有可调的采样旋钮。真正意义上的版本轴是effort、系统提示词、工具清单与会话历史这四样，不把它们固定住，固定模型 ID 的价值并不大。

小结

这次迁移的性质浓缩成一句话：正因为不会坏才危险。换掉模型 ID 之后大多照旧能跑，于是回头看的契机永远不会出现。而在这期间，提示词里留着存在理由已经消失的句子（旧的反格式规则、留到最终回复那类抑制语句），在没人盯着的地方轮数与输出词元一路往上。

动手的顺序文档实际上已经定好了。组织设置（数据保留、服务层级）在先，其次是确认代码有没有在编辑会话历史，再次是从 high 起步的 effort 扫描，而添加提示词句子放在最后。而且这里写下的值本身也撑不了多久。价格、ID 与默认值是2026年9月4日确认的，带测试版标头的那些功能——轮次范围的系统消息、按消息设定的 effort、进度更新显示、思考块绑定控制——按定义就是会变动的地方。版本号往上跳一个小数位时，该重新打开的不是发布说明，而是自己的提示词。

未能确认的部分

  • Claude Fable 5.1 的发布日期未能确认。提示词指南、新增内容、迁移说明、模型总览，没有任何一页写了公开日期。文档中出现的日期性质不同。2026年8月31日是思考块会话绑定检查开始强制执行的账号创建基准日，而测试版标头上的日期（2026-07-01、2026-08-01、2026-08-18、2026-08-21）是各个测试版的标识符。本文没有把这些挪用为发布日期
  • 本文没有任何一个基准测试分数。所参考的官方文档只把能力提升描述为六个领域（长周期编码，文档、表格与幻灯片，研究与检索，视觉，长上下文，计算机操作），既不给数值也不给测量条件。没有条件的分数不用是原则，所以一个都没放进来
  • medium 大体与 Fable 5 相当、low 分数高于其他模型系列这两项主张的支撑材料未能确认。用哪些评测集、在哪种 effort 组合下测的，文档里没有。正文中仅标注为厂商主张，没有当作结论使用
  • 带日期的固定版本 ID 未能确认其存在。模型总览表的 Claude API ID 与别名两列都是 claude-fable-5-1，脚注也把不带日期的 ID 本身说明为固定快照。某处应该有带日期形式这样的推测没有写进来
  • 表示效果大小的数值在原文中同样没有。未经要求的追加大幅减少、平均完成时间下降之类的表述都在，但没写是百分之多少，正文也就停在同样的精度上
  • Claude Mythos 5.1 只有获批的参与者可用，因此无法观察其实际行为。文档能确认的范围是：规格与价格同 Fable 5.1 一致，且只有它不运行思考块的会话绑定检查
  • 本文是通过比对文档写成的，并未用自有评测集复现每条处方的效果。尤其是提示词句子的效果，属于会因负载而大幅分化的那一类
