This article is based on the sentences written in the retrospective "Friendship ended with Deno, now Node is my best friend", which David Bushell published on his own blog on October 3, 2026, in the Node.js v26.10.0 documentation, in the pnpm settings documentation and in the fnm README. The original is a personal retrospective mixed with satire; only its argument and its technical facts are covered here, and its assessments of particular companies have not been carried over.

The Trigger — Meeting Node Again on a SvelteKit Project

The author, David Bushell, writes that he has been using Node heavily this month on a SvelteKit client project. Deno had been his go-to runtime for so long that he had forgotten how to work with Node, and the starting point of the post is that, on coming back, he found the ECMAScript syntax supported and the old annoying APIs replaced or modernised. What he singles out as "most importantly" is that he never has to see require().

The retrospective has four parts: the choice of package management tools, running TypeScript, the experience of moving his own static site generator from Deno to Node, and the reasons he left Deno. It is a short personal record, not a piece written to measure or to run a comparative experiment. The sentence that he "kept using Deno out of habit and familiarity" is also his own.

What follows takes the things the author used on his way back to Node one at a time (a version manager, a package manager with its supply chain settings, and the built-in TypeScript support of Node) and places each of them next to the definition and the limits given in the relevant official documentation. The general axes along which a choice of runtime divides are laid out in the decision to rewrite a runtime.

Version Management and Package Management — fnm and pnpm

For switching Node versions the author chose Fast Node Manager (fnm). The reasons he gives are that his own old experience with NVM and npm had not been good, and that he had heard fnm was better for switching versions. He writes that he tends to run the newest version himself but has client projects that demand stability, so he needs to move between versions. The properties the fnm README states are the following.

  • What it is. The README introduces fnm as a "fast and simple Node.js version manager, built in Rust", and lists among its features that it is a single file with easy installation and instant startup.
  • Supported platforms. They are macOS, Windows and Linux.
  • Version files. It works with .node-version and .nvmrc files.
  • Ways to install. Besides an installation script, the README describes Homebrew, Winget, Scoop, Chocolatey, Cargo and a release binary.
  • Shell setup. Environment variables have to be set up before fnm can be used, which is done by evaluating the output of fnm env in the shell. Examples with the --use-on-cd option are given separately for Bash, Zsh, Fish and PowerShell.

As the package manager he chose pnpm. The reason the author gives for that choice is to avoid being compromised. Because some scripts he uses have hard-coded binary names, he says he added the following two aliases.

alias npm=pnpm
                    alias npx=pnpx

In a note he added later, the author explains that these aliases help when copying steps from install guides that assume npm is installed. Where the settings live is something the pnpm documentation defines separately. pnpm gets its configuration from the command line, from environment variables and from pnpm-workspace.yaml, and reads only auth and registry settings from .npmrc files. In the words of the documentation, "all other settings are configured in pnpm-workspace.yaml or the global config.yaml". That is why all of the settings discussed below go into pnpm-workspace.yaml.

The Release Delay and Trust Policy in pnpm — minimumReleaseAge and trustPolicy

The author added the following two lines to pnpm-workspace.yaml.

minimumReleaseAge: 1440
                    trustPolicy: no-downgrade

minimumReleaseAge — Time Elapsed Since Publication

The definition in the pnpm documentation is this. minimumReleaseAge defines the minimum number of minutes that must pass after a version is published before pnpm will install it. It applies to all dependencies, including transitive ones and not only direct ones. The documentation states the purpose as reducing "the risk of installing compromised or defective packages", and adds that in most cases malicious releases are discovered and removed from the registry within an hour.

  • Version added and default. It was added in v10.16.0. The default is 1440 since v11, and was 0 before v11.
  • What 1440 means. The unit is minutes, so 1440 is one day. The example in the documentation describes the same value as ensuring that only packages released at least one day ago can be installed.
  • Exclusion list. A package listed by name under minimumReleaseAgeExclude is installed immediately upon release. Patterns can be used from v10.17.0, and specific versions from v10.19.0.
  • When no version qualifies. This is governed by minimumReleaseAgeStrict (v11.0.0). When it is false, pnpm falls back to a version that does not meet the constraint so that installation can still succeed; when it is true, pnpm fails resolution instead. The value defaults to true when minimumReleaseAge has been configured explicitly, whereas the built-in default of 1440 on its own is non-strict for backward compatibility.
  • Registries without publish times. When minimumReleaseAgeIgnoreMissingTime (v11.0.0, default true) is on, the check is skipped for a package whose registry metadata does not include the time field.

The author writes that he first tried setting the minimum release age to "one month", that this "caused dependency issues where PNPM struggled to match suitable versions", and that he then settled for "one day" as the value to keep. The 1440 he wrote is the same number as the v11 default in the documentation. The difference is that writing the value into the file explicitly turns on the strict mode described above by default. That the problem he saw with one month may be related to this strict mode is an interpretation drawn from the wording of the documentation; the original post does not explain the cause.

trustPolicy — Versions Whose Trust Level Has Dropped

According to the pnpm documentation, when trustPolicy is set to no-downgrade, pnpm will fail if the trust level of a package has decreased compared to previous releases. The example the documentation gives is a package that was previously published by a trusted publisher but now only has provenance, or no trust evidence at all.

  • Version added and default. It was added in v10.21.0 and the default is off. The two possible values are no-downgrade and off.
  • Basis of comparison. Trust checks are based solely on publish date, not on semver. A package cannot be installed if any earlier-published version had stronger trust evidence.
  • Prereleases. Starting in v10.24.0, prerelease versions are ignored when evaluating trust evidence for the installation of a non-prerelease version.
  • Exclusion list. Packages or versions listed under trustPolicyExclude (v10.22.0) are excluded from the check.
  • Older versions. trustPolicyIgnoreAfter (v10.27.0) allows the check to be ignored for packages published more than the specified number of minutes ago.

The author writes that after moving to a Forgejo instance that he hosts himself, his packages lost "provenance", and that he had to configure the pnpm trust policy to allow his own packages. The original post does not say which key he used. In the documentation, the setting that corresponds to that purpose is trustPolicyExclude.

Blocking Install Scripts — allowBuilds and strictDepBuilds

The author notes in a single line that "PNPM also blocks post-install scripts". In the pnpm documentation, the settings that determine this behaviour are the following.

  • Default behaviour. Packages not listed in allowBuilds are disallowed from running scripts by default and are treated as "unreviewed".
  • Error or warning. Because strictDepBuilds defaults to true, an error is printed by default, and the installation exits with a non-zero exit code if any dependencies have unreviewed build scripts (which the documentation also calls postinstall scripts). If it is set to false, a warning is printed instead.
  • How to allow a build. allowBuilds is a map keyed by package matchers, in which true allows and false disallows. During install, dependencies whose builds were ignored are automatically added to pnpm-workspace.yaml with a placeholder value, and pnpm approve-builds and the --allow-build flag of pnpm add write their entries to the same place.
  • Earlier settings. onlyBuiltDependencies, neverBuiltDependencies, ignoredBuiltDependencies and related settings were removed in v11 and replaced by allowBuilds.
  • Allowing everything. If dangerouslyAllowAllBuilds (v10.9.0, default false) is set to true, the preinstall, install and postinstall scripts of dependencies run without requiring approval. The documentation attaches a warning that this allows all dependencies, including transitive ones, to run install scripts both now and in the future.
  • How it differs from ignoreScripts. ignoreScripts (default false) is a separate setting that does not execute any scripts defined in the project package.json or in its dependencies.

On the behaviour of npm, the original post leaves only one sentence ending in a question mark. The only supply chain incident the post names is Shai-Hulud, and how that unfolded is covered in the analysis of the npm supply chain attack.

Type Stripping in Node — The Scope the Documentation Defines

The author writes that Node can now run TypeScript. The Node.js v26.10.0 documentation, in "Modules: TypeScript", divides runtime TypeScript support into two ways. For full support of all of the syntax and features of TypeScript, a third-party package is used (the documentation takes tsx as its example); for lightweight support, there is the built-in type stripping.

The definition of the built-in feature is short. By default Node.js will execute TypeScript files that contain only erasable TypeScript syntax. It replaces TypeScript syntax with whitespace. No type checking is performed. To disable the feature, the flag --no-strip-types is used. The change history in the documentation reads as follows.

  • v22.6.0. Type stripping was added.
  • v23.6.0, v22.18.0. Type stripping became enabled by default.
  • v24.3.0, v22.18.0. It no longer emits an experimental warning.
  • v25.2.0, v24.12.0. Type stripping became stable.
  • v26.0.0. The --experimental-transform-types flag was removed. That flag had been added in v22.7.0.
Item What Node.js does Section of the documentation
Erasable TypeScript syntax Replaced with whitespace, then executed Type stripping
Type checking Not performed Type stripping
tsconfig.json Not read. Features that depend on its settings, such as paths or converting newer JavaScript syntax to older standards, are intentionally unsupported Type stripping
Enum declarations Error TypeScript features
namespace with runtime code Error (ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX). Namespaces that do not contain runtime code are supported TypeScript features
Parameter properties, import aliases Error TypeScript features
Decorators Not transformed; they result in a parser error TypeScript features
Type imports without the type keyword Treated as a value import, which results in a runtime error Importing types without type keyword
.tsx files Unsupported Determining module system
Source maps Not generated. Line numbers are preserved because types are replaced by whitespace Source maps
REPL, --check, inspect TypeScript syntax is unsupported Non-file forms of input
Files under node_modules Node.js refuses to handle them Type stripping in dependencies

The documentation explains that this scope is intentional. By deliberately not supporting syntaxes that require JavaScript code generation, and by replacing inline types with whitespace, Node.js can run TypeScript code without the need for source maps. On decorators it says that, since they are currently a TC39 Stage 3 proposal, they are not transformed, and that Node.js will not support them until they are supported natively in JavaScript. As a recommendation it names TypeScript version 5.8 or newer together with the following tsconfig.json settings.

{
                      "compilerOptions": {
                         "noEmit": true, // Optional - see note below
                         "target": "esnext",
                         "module": "nodenext",
                         "rewriteRelativeImportExtensions": true,
                         "erasableSyntaxOnly": true,
                         "verbatimModuleSyntax": true
                      }
                    }

According to the note in the documentation, noEmit is for cases where *.ts files are only executed, such as a build script, and is not needed if the intention is to distribute *.js files. The module system is not converted either. The module system of a .ts file is determined the same way as for a .js file, .mts files are always run as ES modules, and .cts files are always run as CommonJS modules. File extensions are mandatory in import statements, so an import is written as import './file.ts' and not as an import without the extension. The paths option of tsconfig is not transformed and therefore produces an error, and the documentation names subpath imports, with the limitation that they need to start with #, as the closest feature available. Among non-file forms of input, type stripping can be enabled for --eval and for STDIN.

Types Are Not Stripped Under node_modules

What the author ran into is the last row of the table above. He writes that one cannot simply publish TypeScript packages to npm as they are, and shows the following error.

error: [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]:
                    Stripping types is currently unsupported for files under node_modules

The Node.js errors documentation has an entry for ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING whose whole description is one sentence, "Type stripping is not supported for files descendant of a node_modules directory", and it records the code as having been added in v22.6.0. That is the same version as the type stripping feature itself. The reason is given in one sentence in the "Type stripping in dependencies" section of the TypeScript documentation: to discourage package authors from publishing packages written in TypeScript, Node.js refuses to handle TypeScript files inside folders under a node_modules path.

The author characterizes this restriction as "philosophical rather than technical". Inasmuch as the reason the documentation states concerns publishing practice and not a limitation of the implementation, that reading does not conflict with the wording of the documentation. He writes that he would love to see light "native types" in ECMAScript, and mentions that there are type annotation proposals while adding that he suspects he will be retired before those bear fruit. The consequences of this restriction for the work of the author are three.

  • A bundler. Since TypeScript packages cannot be published as they are, a bundling tool became necessary, and the author used Tsdown. It added two configuration files.
  • Number of configuration files. He writes that, taken together with deleting deno.json and the like, he breaks even.
  • Provenance. After the move to a self-hosted Forgejo instance the provenance of his packages was lost, which made the trust policy exception from the earlier section necessary.

Migrating a Static Site Generator — What Changed and the 15% Figure

What the author took as his final test for Node was converting his own static site generator from Deno. He writes that not many Node versions ago this would have required a major refactor, whereas with Node v26.10.0 he found surprisingly little work to do. The changes he lists, in the order in which the post presents them, are the following.

  • File system. The first of the required changes was to replace the file system API of Deno with node:fs. He writes that node:fs is vastly improved from what he remembers from about ten years ago.
  • HTTP server. The second was to replace Deno.serve with the node adapter of Hono. The author describes this adapter as a wrapper around node:http.
  • Path module. The only further change he made afterwards was to replace @std/path from Deno with node:path, which he says is a straight import swap.
  • Build time. After this minimum-viable migration, he writes, builds were 15% faster.
  • Room left. The codebase still favours idiomatic Deno, and he guesses that he is leaving performance on the table by not using other built-in Node APIs.

The 15% is a value from one site generator belonging to one author, which the post reports in a single sentence, saying he was "shocked to see 15% faster builds" after the minimum-viable migration. The original post gives no absolute build time, no size for the site, no number of measurements and no Deno version it was compared against. The number is a record that, when the same code was moved with minimal changes, builds did not get slower in the environment of the author; it is not a value that states a general performance difference between the two runtimes.

The Reasons the Author Gives for Leaving and the Scope of This Case

The author names three things as what finally pushed him away from Deno.

  • A ZSH integration that was broken for weeks
  • "429 (Too Many Requests)" responses from JSR
  • Bugs that made Deno choke on concurrent HTTP requests

Each of the three items is a single line in the original post, with no version, no reproduction conditions and no link to an issue. The post also says that JSR support was very quick to delete his account on request, and that none of his packages are visible while old versions remain installable. Beyond this, the original contains the assessment by the author of the direction of the company that makes Deno; that is a personal opinion and is separate from the technical facts above. Placing what the author used next to the official documentation gives the following.

What the author used Definition in the official documentation Limits and conditions the documentation states
fnm A Node.js version manager built in Rust. Works with .node-version and .nvmrc Requires shell setup that evaluates the output of fnm env
pnpm minimumReleaseAge Minimum number of minutes after publication before installation, transitive dependencies included When configured explicitly, resolution fails if no version qualifies (strict mode)
pnpm trustPolicy Installation fails for a version whose trust level has decreased compared to previous releases Based on publish date, not semver. Exceptions go in trustPolicyExclude

node:fs, node:path, the node adapter of Hono — —

The scope of what this case can tell us is narrow. It is a record of one person moving one static site generator of his own to Node v26.10.0. The author himself writes that the reason he kept using Deno was habit and familiarity, and adds that he has not exactly been enthused to write server-side JavaScript recently. Whether the same result would appear for a different kind of work or for a codebase of a different size cannot be known from the original post alone. What he gained on the Node side also comes with costs attached. Type stripping performs no type checking; in the case of the author, publishing a package written in TypeScript came to require a bundling step, because Node.js refuses to handle TypeScript files under node_modules; and the trust policy required a separate piece of configuration in order to allow his own packages.

What Could Not Be Verified

  • Measurement conditions for the 15%. The absolute build time, the size of the site, the number of measurements, the Deno version it was compared against and the execution environment are not in the original post.
  • The error seen with "one month". The error message and the value in minutes that was actually written are not in the original post, so it could not be verified which setting in the documentation the cause of the problem should be connected to.
  • The pnpm version the author uses. It is not stated in the original post. All that can be known from the documentation is that trustPolicy is available from v10.21.0.
  • The key used for the trust policy exception. There is only the statement that he allowed his own packages, without the configuration itself.
  • The Tsdown configuration. The original post does not say what the two added configuration files are.
  • Details of the three problems on the Deno side. Without the affected versions, reproduction conditions or issue numbers, it could not be verified whether they still reproduce today.
  • The statement about the NVM installation instructions. That the official Node documentation recommends installing NVM by piping a script to bash is a statement by the author, and those instructions were not included in the source material.
  • The default behaviour of npm for install scripts. The original post leaves it as a question only, and the npm documentation was not included in the source material.
  • The current stage of the type annotation proposals. The original post mentions only the fact that such proposals exist.
