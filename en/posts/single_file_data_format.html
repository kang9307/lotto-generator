One File, Two Identities - What Shifts When a Database Is Also an Executable

Extensions, magic numbers and content inspection can return different answers about the same file. What becomes possible in that gap, and what becomes fragile

Aug 25, 2026 Dev & Infra

Introduction: The extension does not tell you what a file is

You have looked at the end of an attachment's filename and relaxed, or tensed up. The reflex that .jpg means a picture and .exe means a program is so deeply worn in that it rarely surfaces that those are letters in a name with no contract at all with the bytes inside. The operating system, the browser and the antivirus each decide what a file is on different grounds. Those decisions can disagree.

SELF, published by Farid Zakaria in August 2026, puts that gap on display about as clearly as it can be put. It turns a Linux ELF binary into a SQLite database and the file still runs. The file command reports a SQLite database, you can query its symbol list with SQL, and typing its name in a shell still executes it. One byte stream, both data and program.

What is interesting is less the project than the structure its existence exposes: how a file format introduces itself, who receives that introduction and on what terms, and how wide the space between those two things is. That structure is the subject here. This article does not cover how to construct polyglot files or how to get past inspection with them — that is not the point, and as you will see below, it is not the interesting part either.

1. What SELF actually does - the confirmed scope

SELF stands for Structured Executable & Linkable Format, a name aimed squarely at ELF. Where ELF carries string tables and symbol indexes in purpose-built structures, SELF turns them into database tables and indexes. Segment bytes live in BLOB columns; a symbol becomes a row with columns for name, version, value, size, type and binding.

Questions that normally need dedicated tooling become SQL. Which libraries does this depend on, which symbols are defined and which are left undefined. In the other direction, you can DELETE the diagnostic tables and VACUUM the file down, and the program still runs. The format is the schema, so tools for handling the format do not have to be written from scratch. That is the design's whole argument.

1.1 Execution goes through a kernel extension point

The execution path is Linux's binfmt_misc. This subsystem lets the kernel recognise formats beyond the ones it knows natively, using formats a user has registered. Registration works two ways: by filename extension, or by magic bytes at a specified offset in the file. On a match, the kernel runs the registered interpreter and hands it the file.

SELF uses the latter. It stamps its own marker into a reserved field of the SQLite header, and the kernel that sees that marker invokes a dedicated interpreter. The interpreter reads segments and symbols out of the database, maps them into memory, performs relocations, and transfers control to the entry point. The detail worth pausing on is that what separates an ordinary SQLite database from a SELF file is one value in a reserved header field. The first 16 bytes are identical in both.

2. Three mechanisms that decide what a file is

To see why SELF works you first have to be clear about who decides what a file is, and how. In practice there are only three mechanisms.

The first is the extension: read the letters at the end of the name. It costs essentially nothing and humans can read it too. But the link to the contents is pure convention, so renaming changes the verdict. Windows Explorer hiding known extensions by default makes this a place where people get fooled by eye as well.

The second is the magic number: a fixed byte sequence near the start of the file. A SQLite database begins with a 16-byte header reading SQLite format 3 followed by a null byte. It inspects contents rather than names, which is a large improvement. But what it inspects is still a very small piece of the file.

The third is content inspection: actually run a parser and see whether the structure holds. It is the most accurate and the most expensive, and the answer depends on which parser you opened it with. The fact that one file can be simultaneously valid under several parsers does not go away at this level either.

MechanismWhat it looks atCostWhere it breaks
Extensionletters at the end of the nameeffectively zerochanges independently of contents
Magic numberfixed bytes near the frontlowdoes not represent the whole file
Content inspectionstructure as a parser reads ithighseveral formats can hold at once

On the web a fourth layer sits on top: the Content-Type header the server sends. Yet the WHATWG MIME Sniffing Standard opens from the observation that many servers supply a value which does not match the actual contents. Browsers started looking at the bytes because of that, and this document standardises the practice. Every additional decider adds another pair that can disagree.

3. Those three can disagree - why polyglot files hold together

A file that is simultaneously valid as two formats is a polyglot file. The important thing is that this is not a clever trick but a structurally open property, and the reasons come from perfectly ordinary format-design choices.

  • Formats announce themselves in different places. Some put a signature at the very front; others put their index at the very end. The ZIP family does the latter. A checker that reads the front and one that reads the back can look at the same bytes and disagree.
  • Every format ignores some region. A format that follows length fields never reads bytes outside those ranges. A chunked format skips chunks it does not recognise. Ignored regions are territory another format can occupy.
  • Parsers are lenient. The older the format, the more it was built to open damaged input somehow. Leniency was needed for compatibility, and it also loosens the conditions for validity.
  • Extension points are written into the specs. SQLite's application identifier is one. The 4-byte integer at offset 68 is set with PRAGMA application_id, and SQLite's own documentation says it exists so that tools like file(1) can name the specific kind of file. The spec built that seat.

SELF uses that last property honestly. Nothing is hidden or disguised. And the result still has different identities depending on who is asking. That is where it becomes clear that polyglot behaviour is a by-product of format design rather than a product of malice. The security problems below are not the kind you solve by keeping bad actors out.

4. Why SQLite gets picked as an application file format

SELF choosing SQLite was not arbitrary. SQLite has long kept a document recommending itself as an application file format, and the reasons listed there carry over intact into the executable setting.

  • A single file. One document stays one file. Copying, attaching and moving keep working the way people expect.
  • Atomic writes. A write happens completely or not at all, including across a crash or a power cut. The hardest part of rolling your own format arrives for free.
  • Incremental updates. Only changed pages hit the disk. Editing one value never rewrites the whole document, which makes writes faster and reduces SSD wear.
  • Portability. The file opens unchanged across 32-bit and 64-bit machines, big-endian and little-endian architectures, and Windows and Unix-like systems. This is the ground people get wrong every time they hand-roll a binary format.
  • Ubiquitous implementations and tooling. The contents are reachable with common command-line tools. In SQLite's own phrasing, it is not an opaque blob.

One more thing belongs on that list: you can query it. With a bespoke format, find-the-matching-items has to be hand-implemented every time; with SQLite, indexes and SQL are already there. SELF's ability to rummage through symbol tables in SQL was not a feature someone built — it arrived as a consequence of changing the format.

There is a price. Turning a document into a database raises the format's floor size and introduces page structure and internal fragmentation as new variables. Every program that opens the document has to carry a SQLite implementation. And you give up part of the open-with-anything quality that text-based formats offer. The appeal and the limits of single-file software as an idea are laid out from a different angle in the Bento experiment, where one file becomes an office app.

5. What blurs when data and execution live in one file

Up to here the story is clean engineering. The trouble starts next. If one file is both data and executable, then two very different human actions stop being distinguishable: looking at it and running it.

People treat those as entirely separate. Opening a document is a passive act of checking contents; running a program is an active act of lending your privileges to that code. The latter carries a moment of judgement — do I actually want to run this. Creating a place for that judgement is what a trust boundary is for.

Put data and execution in one file and that place disappears. It disappears in several ways.

  • Expectations diverge. The recipient believes they are opening data, and the act of opening triggers execution.
  • Verdict and handling split apart. The scanner classifies it as data and lets it through; the execution layer treats it as a program. Neither is wrong, and the outcome is outside anyone's control.
  • Privilege travels with the file. Execute bits, trusted directories and registered interpreters attach to a file's location and attributes. When the file moves, that context does not move with it.
  • The review unit grows. A file holding only data can be skimmed by a person. Mix code in and it becomes an effectively unauditable lump.

None of which says a project like SELF is dangerous. SELF is meant to run and is treated as an executable. The problem arises when that property enters a path where nobody expects execution.

6. Security consequences - scanning, quarantine and preservation get harder together

A file whose extension and contents disagree makes three things difficult at once. That each of them belongs to a different team is part of what makes the problem awkward to own.

6.1 Scanning

A large share of security controls rests on a single verdict about what a file is. Upload allowlists, mail gateway attachment policy, sandbox routing and signature matching all do. Break the assumption that there is one verdict and those controls quietly stop working. The pass itself is normal behaviour, so nothing unusual appears in the logs either.

The 2024 arXiv study On the Abuse and Detection of Polyglot Files (Koch, Oesch, Chaulagain et al.) catalogued real cases, identifying 30 samples and 15 attack chains, and reported that two well-known APT groups used polyglot files for detection evasion. The more uncomfortable conclusion is on the detection side: existing format-identification and embedded-file detection tools, including ones built specifically for polyglots, failed to reliably detect the polyglots seen in the wild. The paper's learning-based classifier PolyConv reported an F1 of 99.20%, but that figure lives on the paper's dataset.

  • The more an allowlist is built out of trusted formats, the better a file wearing one of those as a shell passes through it.
  • Content can be arranged so that not even partial signatures match, which leaves signature-based approaches structurally behind.
  • Services accepting file uploads and generative AI file-input surfaces share the same exposure, because both pick a safe handling path from a format verdict.

6.2 Quarantine and preservation

Quarantine is the simpler problem. Quarantining requires first deciding what to treat the thing as. A file with two identities has no obvious bin. Quarantine it as data and the execution path stays open; quarantine it as an executable and legitimate business files get blocked.

Preservation is the kind of problem that gets worse with time. Digital archives identify formats and build migration and rendering policy on that identification. A file with two identities does not tell anyone which way it should be revived decades later. Archived files also stay around, and executable code that is harmless today carries no guarantee about twenty years from now.

  • If the identification tool records only SQLite database, the fact that the file was also an executable vanishes from the record.
  • Classified as data during appraisal, the execution environment is not preserved alongside it, and no way of opening it later survives.

7. Defensive principles - judge by content, keep execution privilege apart

Filtering out every polyglot is not a realistic goal; the study above is largely a demonstration of that. What holds up better is building a structure where a wrong verdict does not become a large loss. There are only a handful of principles.

  • Do not trust the name. The extension and the user-supplied Content-Type are inputs, not facts. Decide from the content.
  • Do not let one content check finish the job. A check that reads only the leading signature cannot know what structure sits at the back. Pair it with a check that parses the whole thing.
  • Separate execution privilege from storage. The location that receives uploads should carry no execute permission, and the web server should not interpret that path as an executable resource. This is the layer that most reliably renders a failed verdict harmless.
  • Turn sniffing off. Serve user content with X-Content-Type-Options: nosniff so the declared type is used as-is. This situation is precisely why the MIME Sniffing Standard provides that opt-out.
  • Rebuild rather than admit. Instead of inspecting and passing a file through, extract only what is needed and reconstruct a fresh file. That is the approach taken by the sanitisation tool the paper tested against image-based polyglots.
  • Leave the execution decision with a person. Trust boundaries are not maintained by technology alone. Put an explicit confirmation at the point where execution happens.

8. Lessons already learned - self-extracting archives and document macros

I thought it was data and it ran is not a new problem. It is closer to a subject this industry has learned the same lesson about repeatedly.

Self-extracting archives existed so you could send a file to someone without the decompression tool. Bundle the extraction code with the compressed data and you have an executable. The purpose was legitimate and it stayed useful for a long time. Today it is among the first things attachment policy blocks, because of one property: checking the contents requires running it.

Macros inside documents are the more dramatic case. Putting automation into a spreadsheet was central to office productivity, and it served just as long as an attack channel. Microsoft eventually announced in February 2022 that it would block VBA macros by default in files from the internet, rolling it out in stages from version 2203. The blocking decision rests not on file contents but on the Mark of the Web — on where the file came from.

GIFAR is the textbook illustration of a gap created by format design. GIF puts its signature at the front of the file; JAR, being ZIP-based, puts its index at the end. One file could therefore be valid as both, and sites that accepted image uploads became the channel. Java closed it in JRE 6 Update 11, with the related CVE published in December 2008.

  • None of the three ended by removing the capability. Each was resolved by narrowing execution conditions, using provenance as the basis, or blocking the format combination.
  • That macro blocking moved to looking at provenance rather than contents is telling. The harder content verdicts get, the more where it came from becomes the trustworthy signal.
  • The shared pattern is convenience arriving first and control arriving later. The interval was the cost.

9. Where it is worth doing - conditions, not a recommendation

None of this makes the idea of one file holding data and execution categorically bad. The conditions under which it is worth it are simply narrow, and checking them first is the better move.

ConditionSingle file winsSeparation wins
Distribution pathtrusted internal paths onlycrosses organisational boundaries
Recipient's understandingknows it is an executableexpects data
Execution privilegeunder separate controldepends on file attributes alone
Lifetimeshort, versions change oftenlong-term preservation is the goal
Inspection patha human approvesan automated filter judges by format

If most of your answers sit in the left column, single-file distribution pays real dividends. Installation steps disappear, a version is pinned by a single file, and the thing works unchanged offline or inside an air-gapped network. Shipping data together with the viewer that reads it is the same case — you can leave someone opening it ten years later the means of opening it as well.

  • Internal diagnostic tooling and similar artefacts, where lifetime is short and the path is controlled.
  • Cases where a dataset and a minimal query interface have to move as one piece.
  • Cases where you want the format itself to be a tool. SELF making symbols queryable in SQL belongs to this family.

10. What I could not confirm

The parts of this article I cannot support with direct evidence, gathered in one place.

  • I did not build or run SELF. All the size and latency figures above are the author's published values, not something reproduced in a separate environment.
  • Progress since the prototype was published, its licence and its maturity were not checked.
  • There is no confirmed material on how actual security products classify a SELF-format file. The discussion above rests on general principles of format determination.
  • The polyglot detection figures come from that paper's dataset. Detection rates in any particular organisation's real environment will differ.

11. Conclusion - separation is usually the better default

SELF is a well-made experiment. It carries a genuine insight — turn a format into a schema and the tooling for that format arrives free — it publishes its numbers honestly, and it states its own limits. What experiments like this reveal is that boundaries we treated as given were actually conventions.

But what an experiment reveals and what a working default should be are different things. Putting data and execution in one file certainly makes distribution easier. In exchange, safety holds only if every system that meets the file reaches the same verdict. Deciders differ between organisations and multiply over time. Where you cannot guarantee that premise, the benefit is once and the cost is continuous.

So the default is separation. Keep data as data and ship the program that handles it separately. Combine them when there is a clear reason and most of the left column above applies. And if you do combine them, making sure the recipient perceives it as an executable is the minimum courtesy. The danger lives in letting people believe there is only one identity, not in a file containing a lot.
