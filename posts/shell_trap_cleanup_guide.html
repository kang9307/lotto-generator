서론: 정리 코드는 스크립트 마지막 줄에 있고, 스크립트는 거기까지 못 갔다

임시 디렉터리를 만들어 중간 산출물을 쌓고, 다 쓰면 마지막 줄에서 지우는 스크립트가 있다고 하자. 평소에는 아무 문제가 없다. 문제는 평소가 아닐 때 생긴다. 입력 파일이 없어서 중간에 exit 1로 빠져나가거나, 배포 중에 CI가 작업을 취소하거나, 누군가 터미널에서 Ctrl+C를 누른다. 그때마다 정리 코드는 실행되지 않는다. 그 줄까지 도달하지 못했으니까.

이런 잔여물은 조용히 쌓인다. 하나에 200MB짜리 작업 디렉터리가 하루 몇 개씩 남으면 몇 주 뒤 디스크 경고로 돌아온다. 그때 남은 디렉터리를 열어 봐도 언제 어느 실행에서 나온 것인지 알기 어렵다.

trap은 이 문제를 정면으로 다루는 도구다. 정리 코드를 「마지막에 실행할 줄」이 아니라 「셸이 끝날 때 반드시 실행할 코드」로 등록한다. 다만 이 문장에는 예외가 여러 개 붙는다. 어떤 종료는 잡히고 어떤 종료는 안 잡히며, 셸에 따라 결과가 갈리고, 잘못 쓰면 지우면 안 될 것을 지운다.

이 글의 명령과 출력은 GNU bash, version 5.2.37(1)-release와 dash에서 그대로 돌려 얻은 것이다. 지우는 명령은 전부 /tmp 아래 mktemp로 만든 경로에서만 실행했다. 셸 기본기가 필요하면 쉘 스크립트 기초와 쉘 스크립트 고급이 먼저다.

1. 어떻게 끝나든 지우게 만드는 한 줄

기본형은 짧다. 임시 파일을 만들고, 그 파일을 지우는 명령을 EXIT에 등록한다.

#!/usr/bin/env bash
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'rm -f "$tmp"' EXIT

EXIT은 시그널이 아니라 셸이 종료하는 순간을 가리키는 가짜 이름이다. 그래서 정상 종료든 exit 1이든 set -e에 걸린 실패든 전부 이 지점을 지난다. 세 경로를 각각 돌려 확인한 결과다.

$ bash t1.sh ok
created: /tmp/work.Z8kaai
doing work
[trap] cleaning /tmp/work.Z8kaai
exit=0

$ bash t1.sh fail            # 스크립트 중간의 exit 1
created: /tmp/work.af0aeI
about to exit 1
[trap] cleaning /tmp/work.af0aeI
exit=1

$ bash t1.sh err             # set -e 상태에서 명령 하나가 실패
created: /tmp/work.cLzp5n
about to run a failing command
[trap] cleaning /tmp/work.cLzp5n
exit=1

세 경우 모두 핸들러가 돌았고 종료 코드도 원래 값이 유지됐다. 여기까지가 trap이 확실하게 해 주는 일이다.

1.1 작은따옴표와 큰따옴표가 다른 결과를 만든다

트랩 본문은 등록할 때 한 번, 발동할 때 한 번 해석 기회가 있다. 어느 쪽에서 변수가 펼쳐지느냐가 따옴표로 갈린다.

$ tmp=/tmp/first
$ trap "echo [double] would remove $tmp" EXIT   # 큰따옴표: 지금 펼쳐짐
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[double] would remove /tmp/first

$ tmp=/tmp/first
$ trap 'echo "[single] would remove $tmp"' EXIT # 작은따옴표: 발동할 때 펼쳐짐
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[single] would remove /tmp/second

큰따옴표 쪽은 등록 시점의 값 /tmp/first를 지우려 든다. 임시 경로가 나중에 정해지거나 루프에서 바뀌는 스크립트라면 이 차이가 그대로 사고가 된다.

  • 트랩 본문은 작은따옴표로 감싸는 것을 기본으로 한다
  • 본문이 한 줄을 넘어가면 함수로 빼고 trap cleanup EXIT처럼 이름만 등록한다. 따옴표 고민이 사라진다
  • 함수로 빼면 trap -p로 확인할 때 등록 내용이 짧아 읽기도 쉽다
  • 디버깅용으로 값을 고정하고 싶을 때만 의도적으로 큰따옴표를 쓴다

2. Ctrl+C로 끊었는데 임시파일이 남는 이유

여기서부터가 실제로 갈리는 부분이다. EXIT 하나만 걸어 둔 스크립트를 시그널로 죽이면 어떻게 되는가. 스크립트가 자기 자신에게 시그널을 보내게 해서 확인했다.

$ cat t4.sh
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'echo "[EXIT trap] rm $tmp"; rm -f "$tmp"' EXIT
kill -"$1" $$
sleep 5
echo "SURVIVED the signal"

$ bash t4.sh INT
pid=1349 tmp=/tmp/work.ZaHJMi  sending SIGINT to self
[EXIT trap] rm /tmp/work.ZaHJMi
exit=130 tmpfile=cleaned

$ bash t4.sh TERM
[EXIT trap] rm /tmp/work.By1Y9n
Terminated
exit=143 tmpfile=cleaned

bash에서는 EXIT만 걸어도 SIGINT·SIGTERM·SIGHUP에서 핸들러가 돌았다. 종료 코드도 130과 143으로 정확하다. 128에 시그널 번호를 더한 값이다.

2.1 그런데 dash에서는 안 돈다

같은 스크립트를 dash로 돌리면 결과가 뒤집힌다.

$ bash /tmp/d2.sh          # EXIT 트랩만 등록, 자기 자신에게 SIGTERM
[EXIT] rm /tmp/work.LJpwWB
Terminated
  rc=143
  cleaned

$ dash /tmp/d2.sh
Terminated
  rc=143
  LEFTOVER /tmp/work.skxk0l

dash는 핸들러를 아예 실행하지 않고 파일을 남겼다. 셔뱅이 #!/bin/sh인 스크립트는 배포 환경에서 dash로 실행되는 경우가 흔하다. 개발 장비에서 /bin/sh가 bash로 연결돼 있으면 이 차이가 안 보인다. 운영에 올린 뒤에야 잔여물이 쌓이기 시작한다.

2.2 시그널을 명시하면 dash도 정리한다

고치는 방법은 EXIT 옆에 시그널을 나열하는 것이다.

cleanup() { rm -f "$tmp"; }
trap cleanup EXIT
trap 'cleanup; trap - INT;  kill -INT  $$' INT
trap 'cleanup; trap - TERM; kill -TERM $$' TERM
trap 'cleanup; trap - HUP;  kill -HUP  $$' HUP
$ dash /tmp/d3.sh
[cleanup] rm /tmp/work.Gjy9y6
Terminated
  rc=143
  cleaned

핸들러가 trap - INT로 자기 트랩을 해제한 뒤 같은 시그널로 자신을 다시 죽이는 부분이 중요하다. 그냥 exit 0으로 끝내면 호출한 쪽에서는 성공한 것처럼 보인다.

$ cat /tmp/reraise2.sh
trap 'echo "[INT] cleaning"; exit 0' INT
kill -INT $$

$ bash /tmp/reraise2.sh
[INT] cleaning
rc=0        # 중단됐는데 성공으로 보고된다

$ bash /tmp/reraise.sh      # 정리 후 같은 시그널로 재발생
pid=587 tmp=/tmp/work.QAJTr9
rc=130      # 128+2, 호출한 쪽이 기대하는 값

CI 러너나 상위 스크립트는 이 종료 코드로 「취소됨」과 「실패」와 「성공」을 구분한다. 정리를 잘 해 놓고 종료 코드를 망가뜨리면 상위 판단이 틀어진다.

3. 시그널별로 무엇이 돌고 무엇이 안 도는가

같은 스크립트를 두 가지 방식으로 무장하고 시그널을 하나씩 보내 표로 정리했다. A는 trap ... EXIT만, B는 EXIT에 INT TERM HUP QUIT를 더한 것이다.

시그널번호A: EXIT만B: EXIT+시그널종료 코드비고
SIGINT2정리됨정리됨130Ctrl+C가 보내는 것
SIGTERM15정리됨정리됨143kill의 기본값
SIGHUP1정리됨정리됨129터미널 연결 끊김
SIGQUIT3스크립트가 살아남음핸들러는 돌지만 계속 진행0비대화형 bash는 기본 무시
SIGKILL9잔여물 남음잔여물 남음137잡을 수 없음

표에서 A와 B가 같아 보이지만 이건 bash 이야기다. 2절에서 봤듯 dash에서는 A가 무너진다. 이식성을 생각하면 B가 기본형이다.

3.1 SIGQUIT는 기본으로 무시된다

표에서 혼자 튀는 줄이다. 비대화형 bash 스크립트는 트랩을 안 걸었을 때 SIGQUIT를 무시한다.

$ cat /tmp/q2.sh
echo "no trap armed; sending QUIT to self"
kill -QUIT $$
echo "survived"

$ bash /tmp/q2.sh
no trap armed; sending QUIT to self
survived
rc=0

트랩을 걸면 핸들러 자체는 돈다. 다만 핸들러가 exit를 하지 않으면 스크립트는 그대로 계속 진행한다.

$ bash /tmp/q1.sh
armed; sending QUIT to self
[QUIT handler] ran
survived (handler did not abort the script)
rc=0

dash에서도 같은 결과가 나왔다. 실무에서 SIGQUIT를 직접 다룰 일은 드물지만, 「트랩을 걸었으니 스크립트가 멈추겠지」라는 가정이 틀릴 수 있다는 예시로는 유용하다. 핸들러가 도는 것과 스크립트가 끝나는 것은 별개다.

4. kill -9로 죽으면 정확히 무엇이 남는가

SIGKILL은 프로세스에 전달되지 않는다. 커널이 프로세스를 직접 없애기 때문에 셸이 코드를 실행할 기회 자체가 없다. 64KB짜리 파일 다섯 개를 만든 작업 디렉터리를 kill -9로 끊고 남은 것을 세어 봤다.

$ bash /tmp/leftover.sh &
$ sleep 1; kill -9 $!
$ du -sh /tmp/work.yURWz1; ls -1 /tmp/work.yURWz1
320K    /tmp/work.yURWz1
    chunk.1
    chunk.2
    chunk.3
    chunk.4
    chunk.5

트랩은 EXIT INT TERM HUP에 전부 걸려 있었지만 아무것도 돌지 않았다.

4.1 bash는 KILL에 트랩 거는 것을 막지 않는다

여기가 진짜 함정이다. 문법 오류로 거절해 주면 좋을 텐데 그러지 않는다.

$ bash -c 'trap "echo caught" KILL; trap -p'
trap -- 'echo caught' SIGKILL
rc=0

trap -p 목록에 SIGKILL 항목이 버젓이 표시된다. 코드 리뷰에서 trap cleanup EXIT INT TERM KILL 같은 줄을 보면 KILL까지 막아 놨다고 읽히지만 그 자리는 아무 일도 하지 않는다. 오히려 없는 안전감을 만든다.

4.2 그래서 대책은 프로세스 바깥에 둔다

  • 임시 경로에 고정 접두사를 붙인다. mktemp -d /tmp/myjob.XXXXXX처럼 만들면 나중에 무엇이 남았는지 한눈에 보인다
  • 별도의 청소 작업이 그 접두사 중 오래된 것을 주기적으로 걷어 가게 한다. 마지막 수정 시각으로 거르면 실행 중인 것은 건드리지 않는다
  • 정말 큰 산출물이라면 /tmp 대신 용량 여유가 있는 별도 볼륨을 쓴다. 잔여물이 다른 서비스를 죽이지 않게 한다
  • SIGKILL이 오는 경로를 먼저 줄인다. 컨테이너 오케스트레이터나 서비스 관리자는 대개 정지 유예 시간을 넘기면 KILL로 올라간다. 정리가 그 시간 안에 끝나게 만들면 KILL을 볼 일 자체가 줄어든다
  • 정리에 수십 초가 걸리는 구조라면 정리를 줄이는 쪽이 맞다. 유예 시간을 늘리는 것은 그 다음이다

5. 정리 두 개를 걸었는데 하나만 도는 이유

같은 시그널에 트랩을 두 번 걸면 뒤에 건 것이 앞의 것을 덮어쓴다. 누적되지 않는다.

$ bash -c 'trap "echo first" EXIT; trap "echo second" EXIT; echo body'
body
second

오류도 경고도 없다. 함수 두 개가 각자 자기 임시 파일을 EXIT에 등록해 두면, 나중에 호출된 쪽만 살아남고 앞의 정리는 조용히 사라진다. 라이브러리 성격의 스크립트를 source로 불러 쓰는 구조에서 특히 자주 터진다.

5.1 정리 항목을 쌓아 두고 한 번에 실행한다

_cleanups=()
add_cleanup() { _cleanups+=("$1"); }
_run_cleanups() {
    for ((i=${#_cleanups[@]}-1; i>=0; i--)); do eval "${_cleanups[i]}"; done
}
trap _run_cleanups EXIT

add_cleanup "echo remove file A"
add_cleanup "echo remove dir B"
add_cleanup "echo release lock C"
$ bash /tmp/stack.sh
body
release lock C
remove dir B
remove file A

등록의 역순으로 도는 것이 핵심이다. 잠금을 먼저 잡고 디렉터리를 나중에 만들었다면, 해제는 디렉터리부터 지우고 잠금을 마지막에 푸는 것이 맞다.

5.2 기존 핸들러 뒤에 이어 붙이는 방법

이미 다른 곳에서 트랩을 걸어 둔 상황이라면 trap -p로 읽어 이어 붙일 수 있다.

add_exit() {
    local prev new
    prev=$(trap -p EXIT)
    prev=${prev#trap -- \'}
    prev=${prev%\' EXIT}
    if [ -z "$prev" ]; then new="$1"; else new="$prev; $1"; fi
    trap "$new" EXIT
}
$ bash /tmp/a1.sh
captured: trap -- 'echo first-handler' EXIT
now armed as: trap -- 'echo first-handler; echo second-handler; echo third-handler' EXIT
body
first-handler
second-handler
third-handler

동작은 하지만 두 가지를 감수해야 한다. 첫째, 핸들러 문자열에 작은따옴표가 들어 있으면 위 문자열 자르기가 어긋난다. 둘째, trap -p는 bash 확장이라 dash에서는 쓸 수 없다.

$ dash -c 'trap "echo x" EXIT; trap -p'
dash: 1: trap: Illegal option -p

dash에서 인자 없이 trap만 치면 목록은 나온다. 다만 그것을 파싱해서 되먹이는 방식은 인용부호 처리가 더 까다롭다. 이식성이 필요하면 5.1의 배열 방식이 낫다.

$ bash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' SIGINT

$ dash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' INT

bash는 SIGINT, dash는 INT로 적는다. 출력을 기계적으로 비교하는 검사기를 만든다면 이 차이가 걸린다.

5.3 트랩을 지우는 방법

trap - EXIT       # 기본 동작으로 되돌린다
trap '' INT       # 무시하게 만든다 (해제와 다르다)

두 번째 형태는 부작용이 있다. 무시로 설정된 시그널은 자식 프로세스에 상속되고, 자식은 그것을 되돌릴 수 없다.

$ cat /tmp/ig.sh
trap '' INT
bash -c 'trap "echo child handler" INT; trap -p INT'

$ bash /tmp/ig.sh
trap -- '' SIGINT

자식이 trap "echo child handler" INT를 실행했는데도 목록에는 빈 문자열, 즉 무시 상태가 그대로다. 부모가 무시로 넘긴 시그널을 자식이 다시 잡을 수 없다. 스크립트가 다른 명령을 감싸 실행하는 래퍼라면 이 상속이 그 명령의 Ctrl+C 반응을 없앤다.

6. 서브셸·백그라운드·함수에서 트랩이 어디까지 따라가나

파이프와 괄호가 프로세스를 하나 더 만든다는 이야기는 파이프 안 while에서 변수가 사라지는 이유에서 다뤘다. 트랩은 그 경계에서 변수와는 또 다르게 움직인다.

6.1 서브셸은 트랩을 물려받지만 자기 종료로는 발동하지 않는다

$ cat /tmp/sub_t.sh
trap 'echo "[EXIT] fired in BASHPID=$BASHPID"' EXIT
echo "parent BASHPID=$BASHPID"
( echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t.sh
parent BASHPID=340
  inside subshell BASHPID=341
subshell rc=3
[EXIT] fired in BASHPID=340

서브셸은 별도 프로세스(341)이고 exit 3으로 끝났는데 핸들러는 부모(340)에서 한 번만 돌았다. 같은 정리가 두 번 실행되는 것을 걱정할 필요는 없다. 반대로 서브셸 안에서만 쓰는 임시 파일이 있다면 그 안에서 따로 걸어야 한다.

$ cat /tmp/sub_t2.sh
trap 'echo "[parent EXIT] BASHPID=$BASHPID"' EXIT
( trap 'echo "  [subshell EXIT] BASHPID=$BASHPID"' EXIT
  echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t2.sh
  inside subshell BASHPID=344
  [subshell EXIT] BASHPID=344
subshell rc=3
[parent EXIT] BASHPID=343

서브셸 안에서 등록한 트랩은 서브셸이 끝날 때 그 안에서 돌고, 부모의 트랩은 부모가 끝날 때 따로 돈다. 서로 간섭하지 않는다.

6.2 백그라운드도 마찬가지고, 파이프라인 안쪽은 밖으로 안 나온다

$ bash /tmp/sub_t3.sh
parent BASHPID=346
  bg BASHPID=347
parent done
[EXIT] fired in BASHPID=346
$ bash /tmp/a2.sh
echo x | { trap 'echo "[inner EXIT]"' EXIT; cat > /dev/null; }
[inner EXIT]
parent continues
parent trap -p EXIT output:
(nothing between the two lines = the parent has no EXIT trap)

파이프라인 구성 요소 안에서 건 트랩은 그 구성 요소가 끝날 때 돌고 부모에는 남지 않는다. 스크립트 본문에서 트랩을 걸었는데 안 도는 것 같으면, 그 줄이 파이프 오른쪽이나 괄호 안에 있는지부터 본다.

6.3 함수 안에서 건 트랩은 함수를 벗어나도 살아 있다

$ bash -c 'f() { trap "echo [EXIT] set inside f" EXIT; echo "in f"; }; f; echo "after f"'
in f
after f
[EXIT] set inside f

EXIT 트랩은 셸 전체의 상태다. 함수 지역이 아니다. 함수가 자기 임시 파일을 정리하려고 EXIT에 등록하면 그 등록은 스크립트가 끝날 때까지 남고, 다른 함수의 등록을 덮어쓴다. 5절의 문제와 같은 뿌리다.

6.4 ERR와 RETURN은 옵션을 켜야 안쪽까지 간다

ERR 트랩은 명령이 실패할 때 도는데, 기본 설정에서는 함수·서브셸·명령 치환 안으로 들어가지 않는다.

$ bash -c 'set -e; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
rc=1                       # 핸들러가 돌지 않았다

$ bash -c 'set -eE; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
[ERR] caught
rc=1

set -E를 켜야 ERR이 함수 안까지 상속된다. RETURN과 DEBUG 트랩은 set -T가 같은 역할을 한다.

$ bash -c 'trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g

$ bash -c 'set -T; trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g
[RETURN]

발동 순서도 확인해 뒀다. 실패가 나면 ERR이 먼저, EXIT이 나중이다.

$ bash -c 'trap "echo [ERR]  seen" ERR; trap "echo [EXIT] seen" EXIT; set -e; false'
[ERR]  seen
[EXIT] seen
rc=1

ERR은 어디서 실패했는지 기록하는 데 쓰고, 실제 정리는 EXIT에 두는 배치가 자연스럽다. 그리고 ERR·RETURN·DEBUG는 전부 bash 확장이다.

$ dash -c 'trap "echo err" ERR; false; echo done'
trap: ERR: bad trap
done

$ dash -c 'trap "echo ret" RETURN; f(){ :; }; f'
trap: RETURN: bad trap

7. 지우면 안 될 것을 지우지 않게 만드는 방어

먼저 읽을 것. 이 절의 내용은 뒤 절의 예제보다 먼저 적용해야 한다. 정리 스크립트는 잘못 쓰면 지우면 안 될 것을 지운다. 삭제는 되돌릴 수 없고, 스크립트가 지운 파일은 휴지통으로 가지 않는다. 아래 세 가지 방어를 붙이기 전에는 rm -rf가 든 트랩을 실제 데이터가 있는 장비에 올리지 않는 편이 낫다.

7.1 변수가 비어 있으면 그 자리에서 멈춘다

트랩은 스크립트 어느 지점에서든 발동한다. 임시 경로 변수에 값이 들어가기 전에 시그널이 오는 경우가 실제로 있다. 그 상태에서 삭제 명령이 그대로 실행되면 대상이 무엇이 될지 예측할 수 없다.

cleanup() {
    : "${workdir:?cleanup called with no workdir}"
    ...
}

:는 아무 일도 안 하는 내장 명령이고, ${var:?메시지}는 변수가 비었으면 메시지를 내고 그 자리에서 셸을 멈추는 확장이다. 둘을 합치면 값 검사만 하는 한 줄이 된다.

$ bash -c 'cleanup() { : "${workdir:?cleanup called with no workdir}"; echo "would remove $workdir"; }
trap cleanup EXIT
echo body'
body
environment: line 2: workdir: cleanup called with no workdir

삭제 줄까지 가지 못하고 멈췄다. 이 한 줄이 없으면 무슨 일이 나는가는 돌려 보지 않고 설명만 한다. rm -rf -- "$workdir"는 변수가 비면 인자가 빈 문자열이 되어 대개 오류로 끝나지만, 흔히 쓰는 다음 형태들은 다르다.

  • rm -rf "$workdir"/* — 변수가 비면 /*가 된다. 루트 바로 아래 전부가 대상이 된다
  • rm -rf "$base/$sub" — 둘 중 하나만 비어도 남은 슬래시 때문에 의도한 것보다 한 단계 위가 지워진다
  • cd "$workdir" && rm -rf . — cd가 실패하면 현재 디렉터리에서 실행된다. &&가 있어도 cd가 성공하고 경로가 엉뚱한 곳이면 그대로 진행한다
  • rm -rf $workdir — 따옴표가 없으면 경로에 공백이 있을 때 여러 인자로 쪼개진다. 앞 조각만 존재하는 디렉터리면 그것이 지워진다

이 네 가지는 전부 시험 삼아 돌려 볼 성질의 것이 아니다. 방어를 먼저 넣고, 그 다음에 삭제 줄을 쓴다.

7.2 경로를 고정한다

값이 있는 것만으로는 부족하다. 값이 예상한 모양인지도 본다.

cleanup() {
    : "${workdir:?}"
    case "$workdir" in
        /tmp/myjob.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
        *)            echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
    esac
}
$ bash /tmp/guarded.sh
workdir=/tmp/work.nGJBt5
removed /tmp/work.nGJBt5
rc=0

접두사가 다르면 지우지 않고 경고만 남긴다. 스크립트를 고치다가 workdir에 다른 값이 들어가는 실수를 해도, 삭제는 일어나지 않고 로그에 흔적이 남는다.

7.3 트랩을 먼저 걸고, 그 다음에 만든다

순서가 뒤바뀐 코드가 흔하다.

# 취약한 순서: 두 줄 사이에서 죽으면 파일이 남는다
tmp=$(mktemp /tmp/work.XXXXXX)
... 준비 작업 40줄 ...
trap 'rm -f -- "$tmp"' EXIT

둘 사이가 짧아 보여도 그 구간에서 시그널이 오면 잔여물이 그대로 남는다. 반대로 하면 된다.

tmp=
cleanup() { [ -n "$tmp" ] && rm -f -- "$tmp"; echo "[cleanup] handled tmp=[$tmp]"; }
trap cleanup EXIT
tmp=$(mktemp /tmp/work.XXXXXX)
$ bash /tmp/race2.sh
trap armed before anything exists
created /tmp/work.35mmxL
[cleanup] handled tmp=[/tmp/work.35mmxL]

$ bash /tmp/race3.sh        # mktemp 전에 종료
[cleanup] handled tmp=[]
rc=1

아직 아무것도 안 만든 상태에서 죽어도 핸들러가 조용히 아무 일도 하지 않고 끝난다. tmp=로 미리 선언해 두는 것이 set -u 환경에서 특히 중요하다.

$ bash -c 'set -u; cleanup() { echo "rm -rf -- \"$workdir\""; }; trap cleanup EXIT; echo body'
body
environment: line 3: workdir: unbound variable

7.4 되돌릴 수 없는 지점

  • 삭제가 시작된 뒤에는 중단해도 소용없다. rm -rf가 절반쯤 진행된 상태에서 Ctrl+C를 눌러도 이미 지워진 것은 돌아오지 않는다
  • 임시 디렉터리에 원본을 옮겨 두는 설계는 위험하다. 복사가 아니라 이동으로 넣었다면 정리 트랩이 원본을 지우는 트랩이 된다
  • 정리 대상이 심볼릭 링크일 수 있는 구조라면 링크를 따라가는지 확인한다. 링크 자체를 지우려던 것이 링크가 가리키는 실제 데이터를 지우는 경우가 있다
  • 네트워크 파일시스템이나 공유 볼륨을 임시 공간으로 쓰면 다른 프로세스가 같은 경로를 쓰고 있을 수 있다. 접두사에 프로세스 식별자를 넣어 겹치지 않게 한다
  • 정리 로직을 바꿨으면 삭제 줄을 echo로 바꿔 한 번 돌려 본다. 어떤 경로가 대상이 되는지 눈으로 확인한 뒤에 실제 삭제로 되돌린다
  • 운영 장비에 처음 올릴 때는 rm 대신 mv로 격리 디렉터리에 옮기는 방식으로 며칠 돌려 본다. 예상 밖의 경로가 잡히는지 그 기간에 드러난다

8. 디렉터리 통째로 쓰고 통째로 지우기

파일 하나가 아니라 여러 개를 만드는 작업이면 mktemp -d로 디렉터리를 하나 잡고 그 안에서 전부 처리하는 편이 낫다. 정리 대상이 하나로 줄어든다.

#!/usr/bin/env bash
set -euo pipefail

workdir=
_cleaned=0

cleanup() {
    [ "$_cleaned" -eq 1 ] && return
    _cleaned=1
    trap '' INT TERM HUP
    if [ -n "$workdir" ] && [ -d "$workdir" ]; then
        case "$workdir" in
            /tmp/job.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
            *)          echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
        esac
    else
        echo "[cleanup] nothing to remove"
    fi
}

on_signal() {
    local sig=$1
    echo "[signal] SIG$sig received" >&2
    cleanup
    trap - "$sig" EXIT
    kill -"$sig" "$$"
}

trap cleanup EXIT
for s in INT TERM HUP; do trap "on_signal $s" "$s"; done

workdir=$(mktemp -d /tmp/job.XXXXXX)
echo "workdir=$workdir"

printf 'row1\nrow2\nrow3\n' > "$workdir/input.txt"
wc -l < "$workdir/input.txt"

세 경로 전부를 돌려 확인했다.

$ bash job.sh ok
workdir=/tmp/job.QoSGZJ
rows: 3
work finished
[cleanup] removed /tmp/job.QoSGZJ
rc=0
verified: /tmp/job.QoSGZJ gone

$ bash job.sh fail
workdir=/tmp/job.aHj3Nw
rows: 3
failing on purpose
[cleanup] removed /tmp/job.aHj3Nw
rc=1
verified: /tmp/job.aHj3Nw gone

$ bash job.sh signal
workdir=/tmp/job.ipwR33
rows: 3
signalling myself
[signal] SIGINT received
[cleanup] removed /tmp/job.ipwR33
rc=130
verified: /tmp/job.ipwR33 gone

이 템플릿에 들어간 요소를 하나씩 짚으면 이렇다.

  • workdir=를 먼저 선언하고 트랩을 건 뒤에 mktemp -d를 부른다 (7.3)
  • _cleaned 플래그로 정리가 두 번 돌지 않게 한다 (10절)
  • 정리 시작 시 trap '' INT TERM HUP으로 추가 시그널을 막는다
  • case로 경로 접두사를 확인한다 (7.2)
  • 시그널 핸들러는 정리 후 같은 시그널로 자신을 다시 죽여 종료 코드를 보존한다 (2.2)
  • local sig=$1로 핸들러가 자기 인자를 받게 해서 시그널 이름별로 따로 함수를 쓰지 않는다

8.1 자식 프로세스도 같이 정리한다

백그라운드로 띄운 작업이 있으면 디렉터리만 지우는 것으로는 부족하다. 지워진 경로를 계속 쓰려는 고아 프로세스가 남는다.

cleanup() {
    echo "[cleanup] killing $(jobs -p | wc -l) background job(s)"
    jobs -p | while read -r p; do kill "$p" 2>/dev/null; done
    : "${workdir:?}"
    rm -rf -- "$workdir"
}
$ bash /tmp/kids.sh
running with 2 children
[cleanup] killing 2 background job(s)
[cleanup] workdir removed
workdir gone: /tmp/work.47Wiqu

순서가 중요하다. 자식을 먼저 죽이고 디렉터리를 지운다. 반대로 하면 자식이 사라진 경로에 쓰다가 오류 로그를 쏟아낸다.

9. set -e와 같이 쓸 때 어긋나는 지점

set -e가 켜진 스크립트에서 트랩 핸들러는 어떻게 되는가. 핸들러 안에서 실패가 나면 나머지 정리는 어떻게 되는가. 이것부터 확인했다.

$ bash -c 'trap "echo [EXIT] start; false; echo [EXIT] still running; echo [EXIT] done" EXIT; echo body'
body
[EXIT] start
[EXIT] still running
[EXIT] done
outer rc=0

핸들러 중간의 실패는 나머지를 막지 않았고 종료 코드도 바뀌지 않았다. 그런데 핸들러 안에서 set -e를 켜면 얘기가 달라진다.

$ bash -c 'cleanup() { set -e; echo "[cleanup] step 1"; false; echo "[cleanup] step 2 - NOT REACHED"; }
trap cleanup EXIT
echo body'
body
[cleanup] step 1
outer rc=1

2단계가 실행되지 않았다. 정리 함수 안에서 첫 삭제가 실패하면 두 번째 삭제와 잠금 해제가 통째로 건너뛰어진다. 종료 코드도 1로 바뀌어 원래 결과를 덮었다.

  • 정리 함수 안에서는 set -e를 켜지 않는다. 정리는 실패해도 끝까지 시도해야 하는 성질의 코드다
  • 스크립트 상단의 set -e는 함수 안까지 유효하므로, 정리 함수 첫 줄에 set +e를 넣는 것이 안전할 때가 있다
  • 개별 명령의 실패를 흡수하려면 rm -f처럼 없어도 성공하는 옵션을 쓰거나 || true를 붙인다
  • 실패를 무시하되 기록은 남기고 싶으면 || echo "..." >&2 형태로 갈음한다

9.1 핸들러 안의 exit이 종료 코드를 덮어쓴다

$ bash -c 'trap "echo [EXIT] handler; exit 99" EXIT; exit 3'
[EXIT] handler
rc=99

$ bash -c 'trap "echo [EXIT] handler" EXIT; exit 3'
[EXIT] handler
rc=3

핸들러가 exit을 부르지 않으면 원래 종료 코드가 그대로 보존된다. 정리 핸들러에서 exit 0을 습관적으로 붙이면 실패한 실행이 성공으로 보고된다. 자동화 파이프라인에서 이보다 나쁜 결함은 드물다.

9.2 exec은 트랩을 데려가지 않는다

$ bash -c 'trap "echo [EXIT] should not print" EXIT; echo before-exec; exec echo after-exec'
before-exec
after-exec

exec은 셸 프로세스를 다른 프로그램으로 교체한다. 교체된 뒤에는 그 셸이 존재하지 않으므로 EXIT 트랩도 사라진다. 컨테이너 진입점 스크립트가 마지막에 exec으로 본 프로그램을 띄우는 구조라면, 그 앞에 걸어 둔 정리 트랩은 절대 돌지 않는다.

10. 정리 도중에 다시 Ctrl+C가 들어오면

정리가 2초 걸리는 상황에서 1초 간격으로 SIGINT를 세 번 보내 봤다. 방어가 없는 핸들러다.

$ bash /tmp/reenter.sh
start (05)
  [cleanup] enter  (06)
  [cleanup] enter  (08)      <-- 앞의 정리가 안 끝났는데 또 들어왔다
  [cleanup] leave  (10)
  [cleanup] leave  (10)
end (16)

enter가 두 번 연속으로 찍혔다. 정리 코드가 자기 자신 안에서 중첩 실행됐다. 이 상태에서 실제로 무슨 일이 나는가.

  • 같은 디렉터리를 두 번 지우려 든다. 두 번째는 대상이 없어 오류를 낸다
  • 잠금 해제가 두 번 돌면, 두 번째 해제가 다음 실행이 방금 잡은 잠금을 풀어 버릴 수 있다
  • 카운터를 되돌리거나 로그를 정리하는 코드라면 두 번 적용되어 값이 어긋난다
  • 중첩된 안쪽이 먼저 끝나면서 exit을 부르면 바깥쪽 정리가 절반만 실행된 채 프로세스가 사라진다

10.1 플래그와 시그널 차단을 같이 쓴다

_cleaned=0
cleanup() {
    [ "$_cleaned" -eq 1 ] && { echo "  [cleanup] already done, ignoring"; return; }
    _cleaned=1
    trap '' INT TERM HUP      # 정리하는 동안은 시그널을 무시한다
    ...
}
$ bash /tmp/reenter2.sh
start (17)
  [cleanup] enter  (18)
  [cleanup] leave  (20)
end (26)

같은 세 번의 SIGINT를 받았는데 정리는 한 번만 돌았다. 두 겹으로 막은 이유가 있다.

  • _cleaned 플래그는 EXIT과 시그널 핸들러가 둘 다 같은 정리 함수를 부르는 구조에서 중복을 막는다
  • trap '' INT TERM HUP은 정리가 도는 동안 새 시그널이 핸들러를 다시 부르는 것을 막는다
  • 플래그만 쓰면 두 번째 진입이 return으로 빠져나오긴 하지만, 그 사이 첫 번째 정리는 인터럽트를 한 번 맞은 상태가 된다
  • 차단만 쓰면 EXIT 경로에서 오는 중복은 못 막는다. EXIT은 시그널이 아니므로 차단 대상이 아니다

정리가 길면 차단은 위험도 된다. 시그널을 무시하는 구간이 길어지면 사용자가 Ctrl+C를 눌러도 아무 반응이 없다. 결국 kill -9로 이어지고, 그러면 4절 상황으로 되돌아간다. 정리는 짧게 유지하는 것이 최선의 방어다.

11. 핸들러가 늦게 도는 것처럼 보일 때

Ctrl+C를 눌렀는데 몇 초 동안 아무 일도 안 일어나는 경험이 있을 것이다. 셸이 포그라운드 자식 명령을 기다리는 동안에는 트랩 실행을 미룬다. 시그널 접수는 즉시지만 핸들러는 그 자식이 끝난 뒤에 돈다. 측정해 보면 이렇다.

$ bash /tmp/measure.sh 5        # sleep 5 를 포그라운드에 두고 t+1초에 SIGINT
  signal will arrive at t+1s
  [handler] ran at t+5s
  foreground sleep 5 returned at t+5s

$ bash /tmp/measure2.sh         # sleep 5 & 로 띄우고 wait 로 기다림
  signal will arrive at t+1s
  [handler] ran at t+1s
  wait returned at t+1s

같은 5초 대기인데 하나는 핸들러가 4초 늦었고 하나는 즉시 돌았다. 차이는 wait가 시그널로 중단되는 반면 포그라운드 sleep은 그렇지 않다는 데 있다.

11.1 반응을 빠르게 만드는 방법

  • 긴 대기는 sleep 300 & wait $! 형태로 바꾼다. 시그널이 오면 wait가 바로 반환한다
  • 쪼갤 수 있으면 쪼갠다. sleep 0.5를 여러 번 도는 루프로 확인했을 때 핸들러가 t+1초에 돌았다
  • 오래 걸리는 외부 명령을 백그라운드로 띄우고 wait로 기다리면 같은 효과가 난다. 대신 종료 코드를 wait "$job"의 반환값으로 받아야 한다
  • 이 지연은 정리가 안 되는 것이 아니라 늦게 되는 것이다. 급하게 Ctrl+C를 연타하면 10절의 재진입 문제로 넘어간다
$ bash /tmp/defer5.sh
[04:37] waiting on background sleep 4
  >>> [04:38] TERM handler
rc=143

12. 두 번 실행을 막는 잠금과 고아 잠금

정리 트랩의 가장 흔한 두 번째 용도가 잠금 해제다. mkdir은 이미 있으면 실패하고, 그 검사와 생성이 한 번에 일어나므로 잠금 원시 연산으로 쓸 수 있다.

lockdir=/tmp/myjob.lock
if ! mkdir "$lockdir" 2>/dev/null; then
    echo "another run holds $lockdir - exiting"
    exit 1
fi
trap 'rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
$ bash /tmp/lock.sh &          # 첫 실행
1854 holds the lock
$ bash /tmp/lock.sh            # 곧바로 두 번째 실행
another run holds /tmp/myjob.lock - exiting
second run rc=1
[cleanup] released /tmp/myjob.lock
lock released

12.1 SIGKILL이 남긴 잠금은 영원히 남는다

4절의 결론이 여기서 다시 나온다. kill -9로 죽으면 잠금 디렉터리가 그대로 남고, 그 뒤로는 아무 실행도 시작하지 못한다. 디스크가 차는 것보다 이쪽이 더 급한 사고다. 잠금 안에 소유자 정보를 남기면 다음 실행이 판정할 수 있다.

if mkdir "$lockdir" 2>/dev/null; then
    echo "$$" > "$lockdir/pid"
    trap 'rm -f "$lockdir/pid"; rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
else
    owner=$(cat "$lockdir/pid" 2>/dev/null)
    if [ -n "$owner" ] && kill -0 "$owner" 2>/dev/null; then
        echo "lock held by live pid $owner"
    else
        echo "STALE lock (owner $owner is gone) - safe to break"
    fi
fi
$ bash /tmp/lock2.sh &
acquired by 1862
$ bash /tmp/lock2.sh           # 소유자가 살아 있을 때
lock held by live pid 1862

$ kill -9 1862
$ bash /tmp/lock2.sh           # 소유자가 사라진 뒤
STALE lock (owner 1862 is gone) - safe to break

kill -0은 시그널을 보내지 않고 그 프로세스가 존재하는지만 확인한다. 다만 이 판정에는 구멍이 있다.

  • PID는 재사용된다. 죽은 소유자의 번호를 전혀 다른 프로세스가 물려받았으면 살아 있다고 잘못 읽는다
  • 여러 서버가 공유 볼륨의 같은 잠금을 쓰면 PID 검사가 무의미하다. 호스트 이름을 같이 기록해야 한다
  • 고아 잠금을 자동으로 깨는 로직은 그 자체가 경쟁 조건을 만든다. 두 실행이 동시에 「낡았다」고 판단할 수 있다
  • 안전한 절충은 자동으로 깨지 않고 경고만 내고 끝내는 것이다. 사람이 확인하고 지우게 한다
  • 소유자 정보에 시작 시각을 함께 남기면 낡음 판정이 훨씬 안전해진다

13. 그래서 무엇을 쓸 것인가

정리 방식별로 무엇을 잡고 무엇을 놓치는지 정리하면 이렇다.

패턴정상 종료exit 1 · 에러INT · TERMKILL이식성
마지막 줄에서 rm정리됨남음남음남음모든 셸
trap ... EXIT정리됨정리됨bash만 정리됨남음dash에서 시그널 취약
trap ... EXIT INT TERM HUP정리됨정리됨정리됨남음bash · dash 모두 확인함
위 + 재발생 · 재진입 방어정리됨정리됨정리됨 · 종료 코드 보존남음bash 기준 8절 템플릿
고정 접두사 + 외부 청소 작업———나중에 정리됨유일하게 KILL을 덮는 방법

마지막 줄이 중요하다. trap만으로는 모든 경우를 덮을 수 없다. 세 번째 줄까지가 스크립트 안에서 할 수 있는 최선이고, 그 위는 스크립트 바깥의 장치가 맡는다. 둘을 같이 두는 것이 실제 답이다.

13.1 최소 체크리스트

  • 정리 코드는 함수로 빼고 trap cleanup EXIT으로 등록한다. 따옴표 문제가 사라진다
  • EXIT 옆에 INT TERM HUP을 나열한다. bash에서 필요 없어 보여도 dash에서 필요하다
  • 시그널 핸들러는 정리 후 trap - SIG로 해제하고 같은 시그널로 자신을 다시 죽인다
  • 정리 함수 첫 줄은 : "${var:?}"다. 그 다음이 case 경로 검사다
  • 변수를 미리 빈 값으로 선언하고, 트랩을 건 뒤에 mktemp를 부른다
  • 재진입 플래그와 trap '' INT TERM HUP을 넣는다
  • 핸들러 안에서 exit 0을 부르지 않는다. 원래 종료 코드를 보존한다
  • 임시 경로에 고정 접두사를 넣고, 오래된 잔여물을 걷는 별도 작업을 둔다
  • 백그라운드 자식이 있으면 디렉터리를 지우기 전에 먼저 죽인다
  • 긴 대기는 & wait로 바꿔 반응 속도를 확보한다
  • 진입점 스크립트가 exec으로 끝난다면 그 앞의 트랩은 안 돈다는 것을 기억한다
  • 배포 대상 셸로 한 번은 실제로 돌려 본다. 이 글의 표를 만드는 데 든 시간은 몇 분이다

14. 확인하지 못한 것

이 글에서 실행으로 검증하지 못한 항목을 한자리에 모은다.

  • 실제 터미널에서 누른 Ctrl+C. 검증은 전부 비대화형 스크립트가 자기 자신이나 자식에게 시그널을 보내는 방식으로 했다. 터미널이 프로세스 그룹 전체에 SIGINT를 뿌리는 상황, 즉 셸과 자식이 동시에 시그널을 받는 경우는 재현하지 않았다. 그 조건에서 핸들러 실행 순서가 달라질 여지가 있다
  • 리눅스 glibc 환경. 이 글의 실행 환경은 x86_64-pc-msys용 bash 5.2.37과 같은 환경의 dash다. 시그널 전달 계층이 리눅스와 완전히 같지 않을 수 있다. 특히 3절의 SIGQUIT 무시 동작과 종료 코드는 배포 대상에서 한 번 재현해 보는 편이 확실하다
  • zsh와 ksh와 busybox ash. 실행 가능한 환경이 아니어서 확인하지 못했다. 최소 컨테이너 이미지에서 흔한 조합이라 실무에서는 중요한 공백이다
  • flock 기반 잠금. 이 환경에 flock이 설치돼 있지 않아 12절은 mkdir 방식으로만 확인했다. 파일 디스크립터가 닫힐 때 잠금이 자동으로 풀리는 성질은 검증하지 못했다
  • 서비스 관리자와 컨테이너 오케스트레이터의 정지 절차. 정지 유예 시간이 지나면 SIGKILL로 올라간다는 동작은 4절에서 대책의 근거로 언급했지만, 실제 서비스 정의를 만들어 재현하지는 않았다
  • 네트워크 파일시스템에서의 삭제 지연. 7.4에서 공유 볼륨을 임시 공간으로 쓰는 위험을 언급했으나 실제 지연이나 부분 삭제를 측정하지는 않았다
  • 대용량 삭제의 소요 시간. 10절에서 정리를 짧게 유지하라고 적었지만, 파일 개수에 따른 rm -rf 소요 시간을 재지는 않았다
  • 구버전 bash. trap -p와 set -E의 동작이 오래된 버전에서 같은지 확인하지 않았다

FAQ

Q1. trap cleanup EXIT 한 줄이면 충분하지 않나?

bash로만 돌린다면 대체로 충분하다. 실행해 확인한 결과 bash 5.2.37은 EXIT만 걸어도 SIGINT·SIGTERM·SIGHUP에서 핸들러를 돌렸다. 문제는 같은 스크립트를 dash로 돌렸을 때다. SIGTERM에서 핸들러가 실행되지 않고 임시 파일이 그대로 남았다. 셔뱅이 #!/bin/sh면 배포 환경에서 dash로 실행될 수 있고, 개발 장비에서 /bin/sh가 bash로 연결돼 있으면 이 차이가 보이지 않는다. 시그널을 명시적으로 나열하는 비용이 한 줄이니 그냥 나열하는 편이 낫다.

Q2. 정리 핸들러에서 exit 0으로 끝내면 안 되나?

안 된다. 확인한 결과 핸들러 안의 exit 99는 원래 종료 코드 3을 99로 덮었다. 핸들러가 exit을 부르지 않으면 원래 값이 그대로 보존된다. 정리 핸들러에 exit 0을 붙이면 실패한 실행과 중단된 실행이 전부 성공으로 보고된다. CI 러너는 그 코드로 재시도 여부를 정하고, 상위 스크립트는 그 코드로 다음 단계 진행을 정한다. 정리를 잘 해 놓고 종료 코드를 망가뜨리면 앞의 이득이 다 사라진다.

Q3. 트랩 핸들러 안에서 오류가 나면 남은 정리는 어떻게 되나?

기본 상태에서는 계속 진행한다. 핸들러 중간에 false를 넣어도 뒤 줄들이 전부 실행됐고 종료 코드도 안 바뀌었다. 다만 정리 함수 안에서 set -e를 켜면 첫 실패에서 멈춘다. 실제로 확인하면 1단계만 찍히고 2단계는 실행되지 않으며 종료 코드가 1로 바뀐다. 정리는 실패해도 끝까지 시도해야 하는 코드이므로 그 안에서는 set -e를 켜지 않는다. 삭제 명령에는 대상이 없어도 성공하는 옵션을 쓰고, 실패를 흡수해야 하는 자리에는 || true를 붙인다.

Q4. 함수마다 자기 정리를 EXIT에 걸면 왜 문제가 되나?

같은 시그널에 대한 트랩은 누적되지 않고 덮어쓰기 때문이다. 함수 A가 걸고 함수 B가 걸면 B만 남는다. 게다가 EXIT 트랩은 셸 전체의 상태라서 함수를 벗어나도 계속 남는다. 함수 지역이 아니다. 회피법은 정리 항목을 배열에 쌓아 두고 EXIT에는 그 배열을 역순으로 도는 함수 하나만 거는 것이다. 등록의 역순이 자원 해제 순서로도 맞다. 잠금을 먼저 잡고 디렉터리를 나중에 만들었다면 디렉터리부터 지우고 잠금을 마지막에 푼다.

Q5. 서브셸 안에서 만든 임시 파일은 어떻게 지우나?

그 서브셸 안에서 따로 트랩을 걸어야 한다. 실행해 확인한 결과 서브셸은 부모의 EXIT 트랩을 목록으로는 물려받지만 자기가 종료할 때 그것을 실행하지 않는다. 부모에서만 한 번 돈다. 반대로 서브셸 안에서 등록한 트랩은 서브셸이 끝날 때 그 안에서 돌고 부모에는 남지 않는다. 파이프라인 구성 요소 안에서 건 트랩도 마찬가지다. 그래서 트랩을 걸었는데 안 도는 것 같으면 그 줄이 파이프 오른쪽이나 괄호 안에 있는지부터 확인하면 된다.

결론: 오늘 바꿀 세 가지

첫째, 정리 코드를 마지막 줄에서 트랩으로 옮긴다. 그리고 EXIT 옆에 INT TERM HUP을 나열한다. bash에서는 없어도 되는 것처럼 보이지만 dash에서 무너진다. 시그널 핸들러는 정리 후 자기 트랩을 해제하고 같은 시그널로 자신을 다시 죽여 종료 코드를 보존한다.

둘째, 정리 함수 첫 줄에 : "${var:?}"와 경로 검사를 넣는다. 트랩은 스크립트 어느 지점에서든 발동하므로 변수에 값이 들어가기 전에 시그널이 오는 경우가 실제로 있다. 그 상태에서 삭제가 실행되면 무엇이 지워질지 알 수 없고, 지워진 것은 돌아오지 않는다. 그래서 이 두 줄은 삭제 줄보다 먼저 쓴다. 로직을 바꿨으면 삭제를 echo로 바꿔 한 번 돌려 대상 경로를 눈으로 확인한다.

셋째, trap이 모든 경우를 덮는다고 믿지 않는다. kill -9는 잡히지 않고, 실측으로 320KB짜리 작업 디렉터리가 통째로 남았다. bash가 trap ... KILL을 문법 오류로 거절하지 않고 목록에 표시까지 해 주기 때문에 코드만 읽으면 막아 놓은 것처럼 보인다. 임시 경로에 고정 접두사를 붙이고 오래된 잔여물을 걷는 별도 작업을 두는 것이, 스크립트 안에서는 절대 해결되지 않는 이 구멍을 메우는 유일한 방법이다.

마지막으로 하나. 이 글의 표와 출력은 전부 열 줄 안팎의 스크립트로 얻은 것이다. 정리가 도는지 안 도는지 궁금하면 추측하지 말고 mktemp로 파일 하나 만들어 놓고 죽여 보면 된다. 30초면 끝난다.
