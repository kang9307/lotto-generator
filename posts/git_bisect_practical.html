무엇을 푸는 도구인가

git bisect 가 답하는 질문은 하나다. 지금은 실패하고 예전에는 성공했다면, 그 사이 어느 커밋에서 바뀌었는가. 정상이었던 커밋 하나와 고장난 커밋 하나만 알려 주면, git 이 그 사이의 중간 커밋을 체크아웃해 주고, 사람이나 스크립트가 판정하고, 다시 반으로 줄인다.

여기서 중요한 것은 범인 커밋의 내용을 몰라도 된다는 점이다. 판정 기준만 있으면 된다. 성능 회귀든, 특정 로그가 안 찍히는 것이든, 어떤 파일이 안 만들어지는 것이든, 예/아니오로 답할 수 있는 시험이면 전부 대상이다. 그래서 이 도구는 코드를 읽어서 원인을 추론하는 방식과 성격이 다르다. 추론이 아니라 측정이다.

  • 필요한 것 셋 — 고장난 커밋(대개 HEAD), 정상이던 커밋(태그·릴리스·몇 달 전 커밋), 재현되는 시험
  • 없어도 되는 것 — 원인에 대한 가설. 오히려 가설이 있으면 그쪽만 보다가 놓친다
  • 탐색 대상은 구간 전체의 커밋이지 파일 변경분이 아니다. 그래서 여러 파일에 걸친 상호작용 문제도 잡힌다
  • 결과는 커밋 하나다. 그 커밋이 크면 다시 좁혀야 하지만, 히스토리 전체에서 한 커밋으로 줄어든 것만으로도 대개 판이 바뀐다

실험용 저장소 만들기

설명만으로는 감이 안 오니 저장소를 하나 만들어 두고 시작한다. 커밋 20개짜리다. total.sh 는 인자로 받은 숫자를 더하고, check.sh 는 그 결과가 맞으면 0으로, 틀리면 1로 끝난다. 13번째 커밋에서 total.sh 를 인덱스 순회로 바꾸면서 마지막 인자를 빼먹는 결함이 들어간다. 그 뒤로도 무관한 커밋이 일곱 개 더 쌓인다.

# /tmp/demo 에서
git init -b main

cat > total.sh <<'EOF'
#!/bin/bash
sum=0
for n in "$@"; do
  sum=$(( sum + n ))
done
echo "$sum"
EOF

cat > check.sh <<'EOF'
#!/bin/bash
out=$(bash ./total.sh 1 2 3 4)
if [ "$out" = "10" ]; then
  exit 0
else
  echo "expected 10, got $out"
  exit 1
fi
EOF

완성된 히스토리와 현재 상태는 이렇다. 결함은 c13 에 있고, HEAD 인 c20 에서 시험은 실패한다.

$ git log --oneline
f2ee06a c20: unrelated note 20
5d4dea0 c19: unrelated note 19
...
f1fec3f c13: refactor total.sh to index-based loop
4d711a9 c12: unrelated note 12
...
d6e191c c02: add check.sh
a25093a c01: add total.sh

$ bash ./check.sh; echo "exit=$?"
expected 10, got 6
exit=1

기본 흐름 - 세션 하나를 끝까지

순서는 넷이다. bisect start 로 세션을 열고, 지금이 고장났다고 bisect bad 로 알리고, 정상이던 커밋을 bisect good 으로 알린다. 그러면 git 이 중간 커밋을 체크아웃해 준다. 시험하고 good/bad 를 반복하다가, 끝나면 bisect reset 으로 나온다.

정상 지점을 c02, 고장 지점을 c20 으로 잡으면 후보는 c03부터 c20까지 18개다. 아래가 그 세션 전체다. 명령과 출력을 하나도 빼지 않았다.

$ git bisect start
status: waiting for both good and bad commits

$ git bisect bad
status: waiting for good commit(s), bad commit known

$ git bisect good d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

$ bash ./check.sh ; echo $?
0
$ git bisect good
Bisecting: 4 revisions left to test after this (roughly 2 steps)
[d21c4cae515e9a7c0cfcacc38374c8b127273674] c15: unrelated note 15

$ bash ./check.sh ; echo $?
expected 10, got 6
1
$ git bisect bad
Bisecting: 1 revision left to test after this (roughly 1 step)
[f1fec3fe55804001fae21aaf7b18a6914483662a] c13: refactor total.sh to index-based loop

$ bash ./check.sh ; echo $?
expected 10, got 6
1
$ git bisect bad
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[4d711a957c98da7528cf727b1db40974a3f9d199] c12: unrelated note 12

$ bash ./check.sh ; echo $?
0
$ git bisect good
f1fec3fe55804001fae21aaf7b18a6914483662a is the first bad commit
commit f1fec3fe55804001fae21aaf7b18a6914483662a
Author: demo <demo@example.invalid>

읽는 요령은 Bisecting: 줄이다. 이번 판정을 마치면 몇 개가 남는지를 알려 준다. 18개에서 8, 4, 1, 0으로 줄었고 시험은 네 번 했다. 그리고 bisect start 뒤에 인자 두 개를 붙이면 bad·good 두 줄을 생략할 수 있다. 순서는 나쁜 것이 먼저다.

$ git bisect start f2ee06a d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

커밋 1,000개는 정말 시험 10번인가

흔히 인용되는 계산이 맞는지 재 보는 편이 낫다. 커밋 1,000개짜리 저장소를 새로 만들고 674번째 커밋에서 설정값 하나를 망가뜨린 다음, 첫 커밋부터 HEAD까지 전 구간을 자동 탐색시켰다. 판정 스크립트가 몇 번 실행됐는지 세면 된다.

$ git rev-list --count HEAD
1000

$ git bisect start HEAD $(git rev-list --max-parents=0 HEAD)
$ git bisect run bash /tmp/bigtest.sh
Bisecting: 249 revisions left to test after this (roughly 8 steps)
Bisecting: 124 revisions left to test after this (roughly 7 steps)
Bisecting: 62 revisions left to test after this (roughly 6 steps)
...
fe0dcdad953018ee006623208fdde398e98ea338 is the first bad commit
    c0674
bisect found first bad commit

# 판정 스크립트가 실행된 횟수
10

정확히 10회다. 첫 커밋을 정상 지점으로 잡았으므로 후보는 999개이고, 999를 2로 계속 나누면 10번 만에 1 아래로 떨어진다. 여기서 중요한 성질은 절대 횟수가 아니라 늘어나는 속도다. 커밋을 두 배로 늘려도 시험은 딱 한 번 늘어난다.

후보 커밋 수필요한 시험 횟수비고
184위 20커밋 저장소에서 실측
999101,000커밋 저장소에서 실측
2,00011커밋이 두 배여도 한 번만 는다
100,00017대형 저장소도 스무 번 아래

표의 아래 두 줄은 실측이 아니라 같은 규칙을 이어 붙인 값이다. 요점은 커밋 수가 병목이 되는 일은 거의 없다는 것이다.

시험 한 번의 시간이 총 시간을 정한다

그렇다면 무엇이 병목인가. 같은 1,000커밋 탐색을 두 번 돌렸다. 한 번은 판정이 즉시 끝나는 시험으로, 한 번은 sleep 2 를 넣어 일부러 느리게 만든 시험으로 했다. 답은 같았고 시험 횟수도 같았다.

--- 즉시 끝나는 시험, 999커밋
tests run: 10
wall time: 3693 ms

--- 같은 탐색, 시험 한 번에 2초
tests run: 10
wall time: 24018 ms

같은 답? fe0dcdad... / fe0dcdad...

차이 20.3초는 2초 × 10회다. git 이 쓴 시간은 체크아웃 열 번분인 3.7초뿐이었다. 즉 총 소요는 거의 전부 시험 시간이고, 공식은 단순하다. 총 시간 ≒ 시험 한 번의 시간 × log₂(후보 수).

그래서 bisect 를 걸기 전에 시험을 줄이는 일이 실질적으로 가장 큰 이득이다. 전체 테스트 스위트가 5분이면 열 번에 50분이지만, 문제를 재현하는 최소 케이스를 만들어 30초로 줄이면 5분이 된다. 최소 재현을 먼저 만들라는 조언은 정성적인 권고가 아니라 10배 차이의 산수다.

  • 전체 스위트 대신 실패하는 시험 하나만 돌린다. 프레임워크 대부분이 단일 케이스 지정을 지원한다
  • 빌드가 필요하면 증분 빌드가 되게 한다. 매번 전체 재빌드가 걸리면 그 시간이 그대로 열 배가 된다
  • 네트워크·외부 서비스에 의존하는 부분은 잘라 낸다. 느린 것도 문제지만 간헐적으로 실패하면 답이 틀린다
  • 구간을 좁힐 수 있으면 좁힌다. 후보를 999개에서 60개로 줄이면 시험은 10회에서 6회로 준다

bisect reset 을 잊으면 생기는 일

범인을 찾은 직후 상태를 그냥 두면 분리된 HEAD 로 남는다. 마지막으로 검사한 커밋 위에 서 있고, 어떤 브랜치에도 붙어 있지 않다. 다행히 git 이 친절하게 알려 준다.

$ git status
HEAD detached at 4d711a9
You are currently bisecting, started from branch 'main'.
  (use "git bisect reset" to get back to the original branch)

nothing to commit, working tree clean

$ ls .git | grep -i bisect
BISECT_ANCESTORS_OK
BISECT_EXPECTED_REV
BISECT_LOG
BISECT_NAMES
BISECT_START
BISECT_TERMS

$ ls .git/refs/bisect
bad
good-d6e191c941eb0f49e6ad6b88f546215ef538eecf

여기서 무심코 코드를 고치고 커밋하면 그 커밋은 어떤 브랜치에도 속하지 않는다. 나중에 reflog 로 찾을 수는 있지만 겪을 필요 없는 일이다. 세션이 살아 있는지 확인하는 가장 빠른 방법은 위처럼 .git 안에 BISECT_* 파일이 있는지 보는 것이고, reset 하면 전부 사라진다.

$ git bisect reset
Previous HEAD position was 4d711a9 c12: unrelated note 12
Switched to branch 'main'

# 범인 커밋 위에 그대로 머물고 싶을 때
$ git bisect reset refs/bisect/bad
HEAD is now at f1fec3f c13: refactor total.sh to index-based loop

# 지금 커밋에서 움직이지 않고 세션만 정리
$ git bisect reset HEAD

덧붙여, 작업 트리가 더러우면 세션이 시작되지 않는다. 수정 중인 파일을 커밋하거나 stash 로 치워야 한다. 실제로 이렇게 끝난다.

$ git status --short
 M total.sh

$ git bisect start f2ee06a d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
error: Your local changes to the following files would be overwritten by checkout:
	total.sh
Please commit your changes or stash them before you switch branches.
Aborting

bisect run - 사람 없이 끝까지 돈다

여기서부터가 이 명령의 본체다. 판정을 스크립트로 넘기면 git bisect run 이 체크아웃과 판정과 다음 선택을 알아서 반복한다. 앞의 세션과 완전히 같은 저장소에서, 사람 개입 없이 한 줄로 끝난다.

$ git bisect start f2ee06a d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

$ git bisect run bash ./check.sh
running 'bash' './check.sh'
Bisecting: 4 revisions left to test after this (roughly 2 steps)
[d21c4cae515e9a7c0cfcacc38374c8b127273674] c15: unrelated note 15
running 'bash' './check.sh'
expected 10, got 6
Bisecting: 1 revision left to test after this (roughly 1 step)
[f1fec3fe55804001fae21aaf7b18a6914483662a] c13: refactor total.sh to index-based loop
running 'bash' './check.sh'
expected 10, got 6
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[4d711a957c98da7528cf727b1db40974a3f9d199] c12: unrelated note 12
running 'bash' './check.sh'
f1fec3fe55804001fae21aaf7b18a6914483662a is the first bad commit
commit f1fec3fe55804001fae21aaf7b18a6914483662a
Author: demo <demo@example.invalid>
Date:   Tue Sep 1 21:57:42 2026 +0900

    c13: refactor total.sh to index-based loop

 total.sh | 8 ++++++--
 1 file changed, 6 insertions(+), 2 deletions(-)
bisect found first bad commit

수동 세션과 정확히 같은 커밋을 짚었고, 사람이 친 명령은 두 줄이다. run 뒤에는 아무 명령이나 올 수 있다 — make, npm test, pytest -k some_case, 직접 만든 셸 스크립트 전부 된다. 인자를 붙여도 되고, 스크립트 경로는 체크아웃되는 저장소 밖에 두는 편이 안전하다. 저장소 안에 두면 옛 커밋에는 그 파일이 없을 수 있다.

종료 코드 규약

자동화의 전부는 종료 코드다. 규약을 잘못 알면 조용히 틀린 커밋을 지목한다. 스크립트를 각 코드로 고정해 놓고 돌려 본 결과를 정리하면 이렇다.

종료 코드git 의 해석실제로 나온 것
0정상(good/old)전부 정상으로 표시돼 나쁜 끝점 자체를 범인으로 지목했다
1 ~ 124, 126, 127결함(bad/new)1·2·124 는 동일하게 동작. 구간 맨 앞 커밋을 범인으로 지목
125판정 불가 - 건너뛰기전부 건너뛰면 We cannot bisect more! 후 bisect run cannot continue any more
126 · 127 (첫 회차)스크립트 실행 실패 의심정상 커밋에서 재시도 후 bogus exit code 127 for good revision 로 중단
128 이상탐색 중단bisect run failed: exit code 128 ... is < 0 or >= 128

문서상의 규약은 「0이면 정상, 125를 뺀 1~127이면 결함, 그 밖의 코드는 중단」이다. 그런데 126·127 을 실제로 돌려 보면 문서보다 한 겹 더 있다. 이 두 값은 POSIX 셸이 실행 불가·명령 없음 에 쓰는 값이라, git 은 첫 회차에 한해 알려진 정상 커밋으로 체크아웃해 같은 명령을 한 번 더 돌려 본다. 거기서도 같은 코드가 나오면 스크립트 자체가 잘못됐다고 보고 멈춘다.

$ git bisect run bash /tmp/rc.sh      # 스크립트가 항상 127 로 끝남
running 'bash' '/tmp/rc.sh'
[d6e191c941eb0f49e6ad6b88f546215ef538eecf] c02: add check.sh
running 'bash' '/tmp/rc.sh'
error: bogus exit code 127 for good revision
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

가운데 줄에서 정상 커밋 c02 로 넘어갔다가 다시 원위치한 흔적이 보인다. 이 안전장치 덕분에 스크립트 경로 오타로 전 구간이 결함으로 표시되는 사고는 대체로 걸러진다. 반대로 이 메시지가 뜨면 코드를 의심할 게 아니라 스크립트가 실행 가능한지부터 본다.

가장 위험한 값은 124 다. 시험에 타임아웃을 걸었을 때 나오는 값인데, 규약상 결함 있음으로 읽힌다.

$ timeout 1 sleep 5 ; echo $?
124

즉 느려서 잘린 커밋과 진짜로 실패한 커밋이 구분되지 않는다. 타임아웃을 쓸 거면 그 값을 판정 불가로 바꿔 주는 편이 정확하다.

판정 스크립트를 잘 쓰는 법

첫 번째 규칙은 재현되는 시험이어야 한다는 것이다. 이분 탐색은 각 판정을 진실로 믿고 그 절반을 통째로 버린다. 판정이 한 번만 틀려도 버려진 절반 안에 범인이 있을 수 있고, 그때 탐색은 오류를 알리지 않는다. 그럴듯한 커밋 하나를 자신 있게 내놓는다.

확인해 보기 위해 30% 확률로 거짓 실패를 내는 시험을 만들어 같은 저장소에서 다섯 번 돌렸다. 정답은 c13(f1fec3f) 이다.

--- 간헐적으로 실패하는 시험, 5회
round 1  f1fec3f...  (맞음)
round 2  f1fec3f...  (맞음)
round 3  f1fec3f...  (맞음)
round 4  f1fec3f...  (맞음)
round 5  9dc5458...  (c08 - 틀림)

--- 결정적인 시험, 3회
f1fec3f...  f1fec3f...  f1fec3f...

다섯 번 중 한 번이 엉뚱한 커밋을 지목했다. 게다가 그 출력만 봐서는 틀렸다는 표시가 어디에도 없다. 간헐적 실패가 의심되면 판정을 여러 번 반복해 한 번이라도 실패하면 결함으로 처리하는 쪽이 낫다.

두 번째는 부작용 정리다. bisect 는 커밋을 오갈 뿐이라 추적되지 않는 파일은 그대로 남는다. 옛 빌드 산출물이 남아 있으면 다음 커밋의 판정이 오염된다.

$ echo "stale artifact" > build.out    # 추적되지 않는 산출물
$ git bisect good                       # 다른 커밋으로 이동
$ cat build.out
stale artifact

실무에서 쓸 만한 골격은 이렇다. 빌드 실패는 125, 타임아웃도 125, 그 밖에는 시험 결과를 그대로 돌려준다.

#!/bin/bash
# /tmp/judge.sh - 저장소 밖에 둔다
set -u

rm -rf ./build            # 이전 회차 산출물 정리
make clean >/dev/null 2>&1

if ! make >/dev/null 2>&1; then
  exit 125                # 빌드 불가 - 판정하지 않고 건너뛴다
fi

timeout 60 ./run_one_test.sh
rc=$?
if [ "$rc" -eq 124 ]; then
  exit 125                # 타임아웃을 결함으로 오해하지 않게
fi
exit "$rc"
  • 스크립트는 저장소 밖에 둔다. 옛 커밋에는 그 파일이 없다
  • 종료 코드를 명시적으로 다룬다. 마지막 명령의 코드가 새어 나가면 의도와 달라진다
  • 산출물·캐시·임시 파일은 매 회차 정리한다. 남으면 다음 판정이 오염된다
  • 표준 출력은 줄여도 되지만 실패 이유 한 줄은 남긴다. 나중에 로그만 보고 판단해야 한다
  • 먼저 양 끝점에서 손으로 돌려 본다. 나쁜 끝점에서 실패하고 좋은 끝점에서 성공해야 탐색이 성립한다

bisect skip - 판정할 수 없는 커밋

구간 안에 빌드가 깨진 커밋이 있으면 판정할 수 없다. 그럴 때 git bisect skip 을 쓰면 git 이 근처의 다른 커밋을 대신 골라 준다. 자동 실행 중이라면 스크립트가 125 로 끝나면 같은 뜻이 된다.

다만 건너뛴 커밋이 답 근처에 몰리면 결과가 하나로 좁혀지지 않는다. 결함 전후 네 커밋(c11~c14)을 전부 건너뛰게 하고 돌린 결과다.

$ git bisect run bash /tmp/skipper.sh
...
There are only 'skip'ped commits left to test.
The first bad commit could be any of:
4d711a957c98da7528cf727b1db40974a3f9d199
f1fec3fe55804001fae21aaf7b18a6914483662a
71ed7e0a93f0b4029ba06d2d3cb95e019f141bb1
f9194e697f22b03a4aae2ef437dfc2497846eb63
d21c4cae515e9a7c0cfcacc38374c8b127273674
We cannot bisect more!
error: bisect run cannot continue any more

실패로 볼 일은 아니다. 커밋 18개가 후보 5개로 줄었고, 그 다섯 개는 손으로 볼 만한 양이다. 미리 못 쓸 구간을 알고 있으면 범위 표기로 한 번에 뺄 수도 있다.

$ git bisect skip c10..c14
Bisecting: 8 revisions left to test after this (roughly 3 steps)

$ git bisect log | grep skip
git bisect skip 71ed7e0a...   # c14
git bisect skip f1fec3fe...   # c13
git bisect skip 4d711a95...   # c12
git bisect skip f9194e69...   # c11

여기서 걸리기 쉬운 대목 — c10..c14 는 c10 다음부터 c14 까지다. 시작점 자체는 빠진다. 시작점까지 빼려면 git bisect skip c10 c10..c14 처럼 따로 적어 준다.

bisect terms - good/bad 가 안 맞을 때

찾는 것이 항상 버그는 아니다. 성능이 좋아진 시점이나 어떤 기능이 처음 들어온 시점을 찾을 때 「나쁜 커밋」이라는 말은 방향을 헷갈리게 한다. 이때 용어를 바꿀 수 있다. 내장 별칭 old/new 가 있고, 직접 지을 수도 있다.

$ git bisect start --term-old=works --term-new=broken
status: waiting for both good and bad commits

$ git bisect broken f2ee06a
status: waiting for good commit(s), bad commit known

$ git bisect works d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

$ git bisect terms
Your current terms are works for the old state
and broken for the new state.

$ git bisect run bash ./check.sh
...
f1fec3fe55804001fae21aaf7b18a6914483662a is the first broken commit
bisect found first bad commit

결과 줄이 first broken commit 으로 바뀌었다. 마지막 요약 줄만 여전히 first bad commit 인데, 스크립트로 출력을 파싱할 생각이라면 알아 둘 만한 차이다. 세션 중간에 지금 용어가 무엇인지 잊었으면 git bisect terms 로 확인한다.

  • 버그를 찾을 때 — 기본 good/bad 로 충분하다
  • 수정이 들어온 시점을 찾을 때 — old/new. 「나쁜 커밋」이라 부르지 않아도 된다
  • 성능 회귀 — --term-old=fast --term-new=slow 처럼 지어 두면 판정할 때 헷갈리지 않는다
  • 용어를 바꿔도 알고리즘은 같다. 말만 바뀐다

머지 커밋이 섞인 히스토리

기본 동작에서 bisect 는 머지 커밋도, 곁가지 안의 커밋도 전부 후보로 본다. 결함이 기능 브랜치 안에서 들어왔고 그 브랜치가 나중에 머지된 히스토리를 만들어 확인했다.

$ git log --oneline --graph --all
* 1f5a5ab m7: mainline work
* dc8284c m6: mainline work
*   36edf65 m5: merge feature
|\
| * fa26dce f4: feature polish
| * 9c3c4da f3: rewrite total.sh (THE BUG)
| * 13a2a60 f2: feature work
| * efe0833 f1: feature start
* | 0481885 m4: mainline work
|/
* 87b692a m3: mainline work
* 2606564 m2: mainline work
* 342914a m1: base

같은 저장소를 두 방식으로 탐색하면 답이 다르게 나온다. 둘 다 맞는 답이고, 묻는 질문이 다르다.

--- 기본: 곁가지 안까지 들어간다
running 'bash' './check.sh'   (3회)
9c3c4da9ba2ed3715032525e3699eeae971e583e is the first bad commit
    f3: rewrite total.sh (THE BUG)

--- --first-parent: 본류만 본다
$ git bisect start --first-parent HEAD 2606564
running 'bash' './check.sh'   (3회)
36edf65d0bd276c62c3fbae15ccab5a28196c39d is the first bad commit
Merge: 0481885 fa26dce
    m5: merge feature

기본 탐색은 결함을 쓴 커밋인 f3 를, --first-parent 는 결함이 본류에 들어온 지점인 머지 커밋 m5 를 짚었다. 원인 코드를 고치려면 앞쪽이 필요하고, 어떤 릴리스부터 문제가 있었는지 알려면 뒤쪽이 필요하다.

--first-parent 가 특히 유용한 경우가 하나 더 있다. 곁가지 중간 커밋들이 빌드조차 안 되는 저장소다. 개발 중에는 깨진 채로 커밋하고 머지 직전에 정리하는 방식이면, 기본 탐색은 그 깨진 커밋들에서 계속 막힌다. 본류만 보면 각 커밋이 대체로 온전하다.

범인을 찾은 다음

커밋 하나가 나왔다면 절반은 끝났다. 먼저 그 커밋이 무엇을 바꿨는지 본다.

$ git show --stat f1fec3f
 total.sh | 8 ++++++--
 1 file changed, 6 insertions(+), 2 deletions(-)

$ git log -p -1 f1fec3f
diff --git a/total.sh b/total.sh
@@ -1,7 +1,11 @@
 #!/bin/bash
+# refactor: iterate by index
 sum=0
-for n in "$@"; do
-  sum=$(( sum + n ))
+i=1
+while [ "$i" -lt "$#" ]; do
+  eval "v=\${$i}"
+  sum=$(( sum + v ))
+  i=$(( i + 1 ))
 done
 echo "$sum"

여기서는 한눈에 보인다. -lt 여야 할 자리가 아니라 -le 여야 했고, 그래서 마지막 인자가 빠졌다. 그런데 실무의 범인 커밋은 대개 이렇게 작지 않다. 파일 수십 개를 건드린 커밋이 나오면 그 안에서 다시 좁혀야 한다. bisect 는 커밋 단위라 안으로 들어가지 못하니, 부모에서 시작해 변경된 파일을 하나씩 얹으며 시험한다.

$ git show --stat HEAD
 alpha.conf | 1 +
 beta.conf  | 1 +
 delta.conf | 1 +
 gamma.conf | 2 +-
 4 files changed, 4 insertions(+), 1 deletion(-)

$ git checkout HEAD~1            # 부모로 이동
$ for f in alpha.conf beta.conf delta.conf gamma.conf; do
>   git checkout main -- "$f"
>   bash ./check.sh; echo "  + $f -> $?"
> done
  + alpha.conf -> 0
  + beta.conf -> 0
  + delta.conf -> 0
  + gamma.conf -> 1        <-- 여기서 깨진다

파일 하나로 좁혀졌고, 그 파일의 변경분만 보면 된다. 파일 안에서도 커야 한다면 같은 요령을 git checkout -p 로 조각 단위에 적용하면 된다. 그리고 범인 커밋 위에서 바로 작업하고 싶으면 앞서 본 git bisect reset refs/bisect/bad 가 그 자리로 데려다준다.

git blame 과 무엇이 다른가

둘 다 「언제 이렇게 됐지」에 답하는 것처럼 보이지만 질문이 다르다. blame 은 이 줄을 마지막으로 건드린 커밋을 말하고, bisect 는 동작이 바뀐 시점을 말한다. 대개는 같은 곳을 가리키지만, 갈리는 경우가 흔하다.

결함이 b3 에서 들어오고 그 뒤 b5 에서 같은 파일을 들여쓰기만 고친 저장소를 만들었다. 동작은 b3 이후 내내 같다.

$ git blame -- total.sh
^4ff6d88 ... 2) sum=0
75a65371 ... 3) i=1
75a65371 ... 4) while [ "$i" -lt "$#" ]; do
b44df25c ... 5)     eval "v=\${$i}"      <-- b5(서식만 고친 커밋)
b44df25c ... 6)     sum=$(( sum + v ))
b44df25c ... 7)     i=$(( i + 1 ))

$ git bisect run bash ./check.sh
75a65371be49176fd1a34827c369875cd78e8a1e is the first bad commit
    b3: switch to an index loop

blame 은 핵심 세 줄을 서식 커밋 b5 로 돌렸고, bisect 는 로직을 바꾼 b3 를 짚었다. blame 쪽도 공백 무시(-w)나 특정 커밋 제외(--ignore-rev)로 보정할 수 있고, 실제로 두 옵션 모두 b3 로 되돌려 준다. 이 주변 옵션은 잘 안 쓰는 git 히스토리 명령어 쪽에서 따로 다뤘다.

상황맞는 도구이유
이 줄이 왜 이렇게 쓰였는지 알고 싶다git blame줄 단위로 커밋과 메시지를 바로 준다
동작이 언제부터 달라졌는지 모른다git bisect어느 줄이 문제인지 몰라도 된다
문제 지점이 여러 파일의 조합이다git bisectblame 은 한 줄씩만 답할 수 있다
이 문자열이 언제 사라졌는지 찾는다git log -S내용 변화로 커밋을 걸러 낸다
범인 커밋을 알고 그 안을 보고 싶다git show · log -pbisect 결과를 받아 이어서 쓴다

bisect 가 안 맞는 경우

모든 회귀에 쓸 수 있는 것은 아니다. 안 맞는 조건이 몇 가지 분명하게 있다.

  • 커밋 단위로 빌드가 안 되는 저장소 — 건너뛸 커밋이 너무 많아지면 후보 여러 개로 끝난다. --first-parent 로 본류만 보거나, 릴리스 태그끼리 먼저 좁힌 뒤 그 구간만 정밀 탐색한다
  • 환경 의존 버그 — 라이브러리 버전·커널·컨테이너 이미지가 바뀌어 생긴 문제는 코드 히스토리 안에 없다. 이때는 코드가 아니라 환경을 이분 탐색해야 한다
  • 데이터 의존 버그 — 특정 레코드에서만 재현된다면 시험이 재현 가능해지도록 그 데이터를 먼저 고정해야 한다. 운영 데이터를 그대로 쓰면 판정이 흔들린다
  • 서서히 나빠진 문제 — 성능이 매 커밋 1%씩 나빠졌다면 「바뀐 한 커밋」이 존재하지 않는다. 임계값을 정해 억지로 이분해도 그 임계값이 답을 정할 뿐이다
  • 이미 원인을 아는 문제 — 스택 트레이스가 파일과 줄을 가리키고 있으면 blame 이 훨씬 빠르다. bisect 는 실마리가 없을 때의 도구다
  • 히스토리가 리베이스로 다시 쓰인 구간 — 커밋이 실제로 그 순서로 빌드된 적이 없으면 중간 커밋이 애초에 동작하지 않을 수 있다

Windows 사용자에게만 해당하는 함정도 하나 있다. bisect 는 refs/bisect/good-<40자리 해시> 라는 긴 이름의 참조를 만든다. 저장소 경로가 깊으면 이 경로가 260자 제한을 넘어 세션이 시작되지 않는다. 경로 길이만 바꿔 가며 확인한 결과가 이렇다.

root=192  refpath=255  -> 정상
root=203  refpath=266  -> error: update_ref failed for ref
   'refs/bisect/good-27fe9984...': couldn't set
   'refs/bisect/good-27fe9984...'

메시지가 경로 문제라고 말해 주지 않아서 원인을 찾기 어렵다. core.longpaths=true 를 켜도 이 참조에는 듣지 않았다. 저장소를 얕은 경로로 옮기는 것이 가장 확실했다. 리눅스·macOS 에서는 나오지 않는 문제다.

정리

정리하면 실무에서 외울 것은 많지 않다. 나쁜 커밋과 좋은 커밋을 주고, 판정을 스크립트로 넘기고, 끝나면 reset 한다. 세 줄이다.

$ git bisect start <나쁜 커밋> <좋은 커밋>
$ git bisect run /tmp/judge.sh
$ git bisect reset

나머지는 전부 판정 스크립트의 품질에 달려 있다. 시험이 재현되지 않으면 답이 틀리고, 시험이 느리면 그 시간이 열 배가 되고, 종료 코드를 대충 흘리면 타임아웃이 결함으로 둔갑한다. 탐색 알고리즘은 이미 완성돼 있고 손댈 것이 없다. 사람이 준비하는 쪽은 「됐다/안 됐다」를 한 번도 틀리지 않고 말해 주는 시험 하나뿐이다.

그래서 이 명령을 익히는 실제 순서는 문법이 아니다. 문제를 만나면 먼저 양 끝점을 손으로 확인하고, 시험을 최소 재현으로 줄이고, 그 다음에 run 을 건다. 이 순서를 지키면 대부분의 회귀는 커피 한 잔 안에 커밋 하나로 좁혀진다.

확인하지 못한 것

  • 모든 출력은 Windows + Git Bash 한 환경에서만 얻었다. 리눅스·macOS, 그리고 dash·zsh 같은 다른 셸에서 메시지 문구나 종료 코드 전달이 같은지는 확인하지 않았다
  • 탐색 중단 시 git bisect run 자체가 셸에 돌려주는 값은 일정하지 않았다. 스크립트가 128 로 끝나면 128, 129 로 끝나면 127 이 나왔는데 규칙을 알아내지 못했다. 판단은 종료 코드가 아니라 메시지로 하는 편이 안전하다
  • 126·127 재확인 동작은 관측한 출력으로만 적었다. git 소스에서 해당 처리를 직접 확인하지는 않았다
  • 커밋 1,000개 실측은 합성 저장소다. 파일이 수만 개인 대형 저장소에서는 체크아웃 비용이 커져 git 자체 시간의 비중이 달라질 수 있다
  • git bisect visualize 는 gitk 가 필요해 실행하지 않았다. --no-checkout 은 동작을 확인했지만 베어 저장소에서의 동작은 시험하지 않았다
  • 긴 경로 실패에서 core.longpaths 가 왜 듣지 않는지는 원인을 확인하지 못했다. 참조 파일 경로와 잠금 파일 중 어느 쪽이 걸리는지도 특정하지 못했다
