The Last Digits of a 64-bit ID Change When It Travels Through JSON

Nothing throws. Only the last two or three digits change, quietly

2026-07-30 Development/Infrastructure

Opening: the lookup fails and the ID was definitely correct

A ticket comes in from support. A customer entered an order number and the lookup returns nothing. The agent checks the number they wrote down, and the order is unmistakably present in the database. Yet searching the same number in the admin console returns no result. Put the number on the screen next to the number in the database and the first sixteen digits are identical and only the last three differ.

Three guesses usually follow. It was truncated during copy and paste, the screen is rounding for display, or there are two copies of the data. None of the three is right. The value did not change in the server, the database, or the screen. It changed in one line of JSON sitting between them.

The point of this article is not the conclusion that identifiers should be sent as strings. Everyone already knows that advice, and on its own it finds nothing in a system that is already running. What this article is about is where precision disappears, what you give up instead, and why this incident is always discovered late.

First, the nature of the problem in one sentence. That sentence explains everything else.

The JSON standard does not specify the precision of numbers. What breaks is not the standard but the parser, which means the language and its choices. So when the sender and the receiver are written in different languages, the value diverges while both sides behave perfectly correctly.

Execution environment. Every output below is copied verbatim from a run on Windows 10 Pro (10.0.19045). The runtimes are Node.js v22.16.0 (win32), Python 3.13.3 (win32), Perl v5.38.2 with JSON::PP 4.16, and SQLite 3.49.1. Every script was saved to a file before being run, and all IDs and amounts used as examples are fictional.

What this article does not cover. The principles of money arithmetic itself, meaning why you must not use floating point for amounts, were covered in the fintech engineering handbook. Here we look only at serialization at the JSON boundary. How to operate schemas and contract documents belongs to API documentation governance. For another case with the same shape, something quietly breaking at a boundary, see where an encoding breaks.

1. Reproduction: a 19-digit ID through one JSON round trip

The first thing to do is see it. As Twitter and snowflake style IDs are, this is a 19-digit integer put through a JSON round trip. The original and the result are printed side by side.

node v22.16.0 / win32

--- 1-1. snowflake-style 19-digit id through JSON round trip ---
sent text     : {"order_id":1234567890123456789,"amount":1000}
parsed value  : 1234567890123456800
re-serialized : {"order_id":1234567890123456800,"amount":1000}
original digits : 1234567890123456789

Read it this way. The text that was sent unmistakably contained 1234567890123456789. The parsed value is 1234567890123456800. The length is still 19 digits, and the first sixteen digits are unchanged. From the seventeenth digit on, 789 became 800.

  • There is no exception. The parse succeeded and so did the re-serialization. Nothing violated the standard
  • The length is the same. So a system that validates digit counts lets this through too
  • The leading digits match. A human scanning a log will not spot it either, because eyes read from the left
  • The re-serialized JSON is valid again. So it flows onward to the next system. Nobody can stop it

This was checked in several shapes rather than one, collecting the forms encountered in practice.

Several things deserve attention here.

  • 999999999999999999 became 1000000000000000000. It gained a digit. Eighteen digits became nineteen, so even a length check fails to survive
  • 9007199254740993 shrank by exactly one. The error is not large, it is precisely one. This is the most dangerous shape
  • A value that already ends in zero, like 1541815603606036480, drifted by twenty. IDs built by shifting a millisecond timestamp left commonly look like this
  • The 20-digit 12345678901234567890 drifted by 890. The more digits, the wider the loss

Why is an error of one especially dangerous? Because the neighbouring number may be a real, different order. A failed lookup is at least visible. But if the adjacent ID happens to exist, the lookup succeeds and somebody else's order opens. In that case the system never reports anything wrong at all.

That mnemonic is an approximation, though. The exact boundary is 9007199254740991, which is 2 to the 53rd minus one. Here is the region crossed one unit at a time.

This is one of the most important outputs in the article. Crossing the boundary does not break everything; only the even numbers survive.

  • 9007199254740992 was exact. It crossed the boundary and was still right
  • 9007199254740993 came down to 9007199254740992
  • 9007199254740994 was exact again
  • 9007199254740995 went up to 9007199254740996. The direction is not even consistent

A practically fatal trap follows from this. The sentence I tested it and it worked becomes true. Pick a handful of even IDs to check and every one passes. Pick odd ones and they fail. A verification approach that checks a few arbitrary records passes probabilistically in this region. That is why verification must use a list of boundary values rather than a sample.

Why do only even numbers survive? A double-precision float carries its significant digits in 53 bits of significand. Past 2 to the 53rd, the gap between representable values widens from one to two. Further up the gap keeps doubling to four and eight. How wide the gap is in the 19-digit region is shown directly by the errors of -11, -20 and 890 in section 1.

3. Equality will not catch it - two IDs become one value

This is the first wall you hit when trying to catch the problem with verification code. Comparison itself lies.

--- 3-1. two different integers become the same value ---
literal 9007199254740992 : 9007199254740992
literal 9007199254740993 : 9007199254740992
a === b                  : true
Object.is(a, b)          : true
a - b                    : 0

--- 3-2. x === x + 1 becomes true ---
x                  x+1                x === x+1
-----------------------------------------------------
9007199254740990   9007199254740991   false
9007199254740991   9007199254740992   false
9007199254740992   9007199254740992   true
9007199254740992   9007199254740992   true
1234567890123456800 1234567890123456800 true

Two different integer literals are written out in the code, and strict equality is true. Their difference is 0. It is not that the values became equal; they were read as the same value from the start.

What follows is even more counterintuitive. There is a point where x and x + 1 are equal. Adding one to 9007199254740992 leaves the value unchanged. For a 19-digit ID it goes without saying. Arithmetically this is impossible, and it holds only because what is being handled here is not an integer but an approximation of one.

Here is how that surfaces in real code.

--- 3-3. a lookup that silently matches the wrong row ---
key sent by client   : 1234567890123456789
key after JSON.parse : 1234567890123456800
Map lookup result    : undefined
deduplication test   : how many distinct ids survive?
  sent   : 4 distinct id strings
  after  : 1 distinct numbers -> ["1234567890123456800"]
  • A lookup with the key the client sent returns nothing. The key had already become a different value
  • The lower half is worse. Four distinct IDs were sent in an array and merged into one after parsing. The deduplication logic swallowed three of them
  • In that case the system concludes that duplicates were present and were cleaned up. It is recorded as normal operation
  • When this happens in a batch, the remaining three records go unprocessed while being counted as successful. The incident becomes visible when a customer asks about it

The one rule for verification. Never verify a round trip by comparing values. Two damaged values are equal to each other, so a value comparison passes. You have to compare the original text and the re-serialized text as strings for the loss to appear. That single-line difference decides whether the verification works at all.

5. What the standard specifies and what it leaves open

The specification has to be checked here, because mistaking this for an implementation bug points the whole response in the wrong direction.

The number section of RFC 8259 defines the grammar and then, on precision, records not a requirement but a recommendation. The wording confirmed by opening it reads as follows.

「good interoperability can be achieved by implementations that expect no more precision or range than these provide」

「numbers that are integers and are in the range [-(2**53)+1, (2**53)-1] are interoperable in the sense that implementations will agree exactly on their numeric values」

Read the sentences precisely. It does not say you must not exceed this range. Exceeding it is still perfectly valid JSON grammatically. What the standard says is that only within that range is there a guarantee that implementations agree on the same value. Outside it there is simply no guarantee, and no guarantee means breaking is not a specification violation.

The conclusion follows.

  • This is a problem with nobody to file a bug against. The parser is correct and so is the serializer
  • The only place that can be fixed is the contract, the single point where you decide which values travel in which form
  • So the remedy is not swapping a library but writing one line into the specification
  • That is also why the RFC spells out 2**53 explicitly. This number is written into the document not as a JavaScript quirk but as the common denominator of interoperability

The same document also nails down Infinity and NaN: 「Numeric values that cannot be represented in the grammar below (such as Infinity and NaN) are not permitted.」 That sentence is used again in section 10.

6. Putting it in a string - and what you give up

Now the best known remedy, checked for real. The same value was sent inside quotes.

--- 5-1. the id sent as a JSON string instead ---
parsed value : 1234567890123456789
parsed type  : str
exact        : True

--- 5-2. what you give up: string ordering is not numeric ordering ---
as numbers sorted : [9, 10, 99, 100, 999999999999999999, 1000000000000000000]
as strings sorted : ['10', '100', '1000000000000000000', '9', '99', '999999999999999999']
zero padded to 20 : ['00000000000000000009', '00000000000000000010', '00000000000000000099', '00000000000000000100', '00999999999999999999', '01000000000000000000']

--- 5-3. string ids do not survive arithmetic or range filters ---
string + 1 -> TypeError: can only concatenate str (not "int") to str
"9" > "100"  (lexicographic) : True
  9  > 100   (numeric)       : False

It is preserved, as it must be. A string is never interpreted as a number by the parser, so there is no reason to touch it. If it is that simple, why did nobody do it from the start? The second block is the answer.

  • The sort order changes. Numerically it is 9, 10, 99, 100; as strings, 10, 100, ... come first. Mix values of differing lengths and the order falls apart completely
  • Comparisons invert. In string comparison 9 is reported greater than 100, because it is lexicographic
  • Zero padding restores the order. Padded to twenty characters, the sorted result matched numeric order. In exchange, storage and index size grow, and a later increase in digit count forces a full rework
  • Arithmetic is blocked. Adding one to a string raises a type error. That is closer to a safety feature than a drawback
  • Range queries get harder. A design that expressed conditions such as IDs issued since yesterday using the ID itself has to be rewritten

So the criterion is use, not type. Do you perform arithmetic or range comparison on the value? If not, a string costs you essentially nothing. If you do, a string is not the answer and the right move is to bound the magnitude in the contract.

7. Is receiving it as a BigInt enough?

JavaScript has an arbitrary precision integer type, so the natural next question is whether you can just receive it as that. The short answer is that plainly, no.

node v22.16.0 / win32

--- 6-1. can JSON.parse produce a BigInt by itself ---
typeof JSON.parse("1234567890123456789") : number
JSON.stringify({v:10n}) -> TypeError: Do not know how to serialize a BigInt
BigInt("1234567890123456789")            : 1234567890123456789
BigInt from the already-parsed number    : 1234567890123456768
  -> converting AFTER parsing is too late, the digits are already gone

--- 6-2. reviver alone is not enough ---
reviver receives an already-damaged number:
  result : 1234567890123456768
  exact  : false

Two things are confirmed. First, the standard parser will not produce a BigInt for you. Going the other way, trying to serialize a BigInt raises an exception outright. Second, converting after parsing is far too late. Turning an already-damaged number into a BigInt merely preserves the damaged value precisely.

The reviver in the second block shows that trap directly. A reviver is a callback, so the intervention point looks early, but the value the callback receives has already been converted to a number. That is why the result is still 1234567890123456768.

Is there no way then? There is. You need access to the original text.

--- 6-3. the source text is required (context.source, ES2025) ---
reviver context.source available : true
  result : 1234567890123456789
  type   : bigint
  exact  : true

--- 6-4. the portable workaround: quote the digits before parsing ---
rewritten text : {"order_id":"1234567890123456789"}
  result : 1234567890123456789
  exact  : true
  caution: a text rewrite also hits digits that are inside real strings
  input  : {"memo":"call 01012345678901234567 back","id":1234567890123456789}
  after  : {"memo":"call 01012345678901234567 back","id":"1234567890123456789"}

--- 6-5. writing BigInt back out ---
toJSON via replacer (string form) : {"order_id":"1234567890123456789","amount":1000}
unquoted number form              : {"order_id":1234567890123456789,"amount":1000}
  the second form is valid JSON, and it breaks again at the next JS reader
  • On Node 22 in this environment, the reviver could receive the original text fragment as its third argument. Using it restores 1234567890123456789 exactly
  • In an environment without that feature, there is the approach of rewriting the text to add quotes before parsing. It is a widely used workaround
  • That workaround has a price, and the last case in the output above is it. Long digits inside a string must be left alone, and rewriting text with a regular expression can misjudge the boundary
  • The outgoing side is a problem too. Emitting a BigInt as a string is safe, but stripping the quotes to emit a number breaks again at the next consumer

In short, BigInt is a tool for calculation, not a tool for holding the JSON boundary. Holding the boundary requires intervening at the text layer anyway, and if that is the case, exchanging strings from the outset is simpler.

8. Float round trips - how many digits guarantee it

With integers done, on to decimals. Starting with the famous example.

--- 7-1. the classic float sum, in python ---

--- 7-2. how many decimal digits guarantee a float round trip ---
sys.float_info.dig     : 15  (digits guaranteed to survive text -> float -> text)
mant_dig               : 53 bits
  %.15g : 183351 failures out of 200000
      first failure  original 399955.7584213044 -> text 399955.758421304 -> back 399955.758421304
  %.16g :  51352 failures out of 200000
      first failure  original -377762.57764660777 -> text -377762.5776466078 -> back -377762.5776466078

--- 7-3. repr already picks the shortest text that round trips ---
  0.1                    len= 3  round trip: True
  0.30000000000000004    len=19  round trip: True
  0.3333333333333333     len=18  round trip: True
  1.4142135623730951     len=18  round trip: True
  1e-07                  len= 5  round trip: True

That 0.1 + 0.2 is not 0.3 is well known. What matters here is what comes next. Send that value out as JSON and read it back, and exactly the same value returns. In other words float round trips are safe. The exact opposite of integers.

The reason for that safety is in the second block, which round-tripped 200,000 values at each width.

  • Writing 15 digits failed more than 180,000 times. Fifteen digits does not guarantee a round trip
  • Sixteen digits still failed more than 50,000 times
  • At seventeen digits the failures dropped to zero. All 200,000 came back exactly

That is where the number seventeen comes from for double-precision floats. Distinguishing the values a 53-bit significand can represent requires that many decimal digits. It is easy to confuse this with the fifteen that Python reports as its guaranteed digits, but the two run in opposite directions. Fifteen is the guarantee when starting from decimal, and seventeen is what is needed when starting from binary.

The same experiment was run in JavaScript.

--- 7-4. the same float questions in JS ---

The results agree: zero failures at seventeen digits. And in both languages the serializer does not always write seventeen digits. 0.1 goes out as three characters and 0.30000000000000004 as nineteen. It picks the shortest text that guarantees a round trip, which is why specifying a digit count yourself introduces loss instead.

Working rule. When emitting decimals as JSON, do not specify the number of digits. An intervention meant to round it into something tidy breaks the round-trip guarantee. Decide display format on the screen and use default serialization on the wire.

9. Money - serialization at the JSON boundary

The principle that money must not use floating point was covered in the fintech engineering handbook. Here we look only at what happens at the JSON boundary.

--- 8-1. money at the JSON boundary (serialization only) ---
float sum of [19.99,19.99,19.99,0.1,0.2] = 60.27
JSON.stringify(sum)                     = 60.27
rounded to 2dp                          = 60.27
integer minor units sum                 = 6027  (60.27)
difference                              = 0 minor units

  the JSON boundary problem is not the arithmetic, it is the text:
    text 0.10      -> number 0.1       -> re-stringified 0.1       text preserved: false
    text 19.99     -> number 19.99     -> re-stringified 19.99     text preserved: true
    text 1234.50   -> number 1234.5    -> re-stringified 1234.5    text preserved: false
    text 100.00    -> number 100       -> re-stringified 100       text preserved: false
  trailing zeros and the scale of the amount are not part of a JSON number

Start at the top. In this sample the difference between the float sum and the integer sum was zero. The results matched after rounding, which shows that the folk belief that adding decimals always loses a unit of currency does not always hold. Sometimes it is lost and sometimes not, and this sample was the latter. Which makes it more dangerous. The test passes.

The real problem is below. What disappears at the JSON boundary is not the value but the notation.

  • Send 0.10 and 0.1 comes back. The trailing zero is gone
  • 1234.50 becomes 1234.5. Awkward as a money format, and in string comparison or signature verification it is a mismatch
  • 100.00 becomes 100. The decimal point itself disappears, and with it the information about the currency's fractional digits
  • Only 19.99 stayed the same, and only because the shortest text happened to equal the original

So a JSON number has no concept of scale. 100.00 and 100 are the same number and the serializer picks the shorter one. That becomes a problem in a system handling currencies with different fractional digits.

There are only two alternatives. Send integer minor units with the currency code alongside, or send a string and preserve the notation as written. The former is the general practice and the latter is for cases where fixing fractional digits in the contract is impractical. Either way, only one option drops out: sending money as a JSON number.

10. NaN and infinity - values the standard does not have

Exactly as the RFC sentence quoted in section 5 says, these two values do not exist in the JSON grammar. Yet programs create them, by dividing by zero or exceeding a range. So what does the serializer do?

--- 9-2. NaN and Infinity at the JSON boundary in JS ---
JSON.stringify(NaN)                  : null
JSON.stringify(Infinity)             : null
JSON.stringify(-Infinity)            : null
JSON.stringify({a:NaN,b:Infinity})   : {"a":null,"b":null}
JSON.stringify([NaN, Infinity])      : [null,null]
JSON.stringify(-0)                   : 0
JSON.parse(JSON.stringify(-0))       : 0  Object.is(-0) : false
  JSON.parse("NaN"        ) -> SyntaxError
  JSON.parse("Infinity"   ) -> SyntaxError
  JSON.parse("-Infinity"  ) -> SyntaxError
  JSON.parse("nan"        ) -> SyntaxError
  JSON.parse("1e400"      ) -> Infinity
  JSON.parse("-1e400"     ) -> -Infinity
  JSON.parse("1e-400"     ) -> 0

JavaScript chooses to turn them into null, with no exception and no warning. Consider what that means in practice. A value that became NaN because a measurement failed and a value that is null because nothing was ever measured become completely indistinguishable on the receiving side. No data and calculation failed merge into one value.

Some further findings.

  • Negative zero disappears. Emit -0 and it becomes 0, and the returning value is no longer a negative zero
  • A literal beyond the range becomes infinity. 1e400 is not a parse error but Infinity. So it accepts quietly on the way in and converts to null on the way out
  • A value too small becomes zero. 1e-400 parsed as 0. A non-zero value turning into zero is dangerous in code that divides
  • Conversely the reading side is strict. Put the letters NaN or Infinity in and you get a syntax error

Other languages behave differently again at this point.

--- 9-1. NaN and Infinity: python writes them, the standard has them not ---
json.dumps default      : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}
json.loads of that back : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}
json.dumps allow_nan=False -> ValueError: Out of range float values are not JSON compliant: nan

json.loads('Infinity')  : inf
with parse_constant     -> ValueError: rejected NaN

--- 11-5. NaN and Infinity in a third parser ---
  decode(NaN) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(Infinity) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(-Infinity) -> error: malformed number (no digits after initial minus),
  decode(1e400) -> Inf
  encode([inf, nan]) -> [Inf,NaN]

The asymmetry this output shows is large.

  • Python writes NaN and Infinity out by default. That is not standard JSON. And it can read back what it wrote, so testing only within one language never reveals it
  • Python has an option that forbids this, and turning it on raises an exception. The key point is that the default is the permissive one
  • Perl refuses to read them. Both NaN and Infinity are parse errors
  • Yet Perl writes them out. Encoding an array holding infinity and NaN produced [Inf,NaN]. That text Perl itself cannot read back

11. Exponent notation for large numbers - it walks past the digit check

Building the integer defence as a rule that sixteen or more digits is risky leaves a hole. Here is the size at which the notation switches.

--- 10-2. where JS flips to exponent notation ---
n                        String(n)                          JSON.stringify(n)
----------------------------------------------------------------------------------
10^18                    1000000000000000000                1000000000000000000
10^19                    10000000000000000000               10000000000000000000
10^20                    100000000000000000000              100000000000000000000
10^21                    1e+21                              1e+21
10^22                    1e+22                              1e+22
10^100                   1e+100                             1e+100

  and back again:
    JSON.parse(1e21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1e+21                   ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1E21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1000000000000000000000  ) -> 1e+21   re-stringified -> 1e+21
  a naive digit-count guard misses this shape entirely:
    text          : 1e+21
    /^\d{16,}$/   : false   <- the guard does not fire

Exponent notation begins exactly at 10 to the 21st. Up to 10 to the 20th below it, the digits are written out in full. This boundary is fixed by the language specification and does not shift arbitrarily.

Why does this matter in practice? The last two lines answer it. A regular expression looking for sixteen or more digits does not react to 1e+21, because the text is five characters long. A value that has actually lost twenty-one digits of precision passes the digit check untouched.

  • Re-parsing does not bring the original digits back. 1000000000000000000000 and 1e21 are treated as the same value
  • The uppercase 1E21 reads as the same value too. Forgetting case in the checking expression is a common mistake
  • Values in this region are rarely used as identifiers, but cumulative totals and byte counts do reach it
  • So the diagnostic procedure must include a separate item for exponent notation

  • 1e21 was recognized as a real type. So the text notation can decide the stored type as well

13. Duplicate keys, key order, canonical hashing

Neighbouring problems that tangle with numbers just as often were checked in the same run.

--- 13-1. duplicate keys: last one wins, silently ---
  JSON.parse({"id":1,"id":2,"id":3}) -> {"id":3}
  a signed payload can carry two values for the same field, and two
  parsers can disagree about which one is real

--- 13-2. key order is not preserved the way you think ---
  input  : {"b":1,"2":2,"a":3,"1":4}
  output : {"1":4,"2":2,"b":1,"a":3}
  integer-like keys are reordered ahead of the rest by the object model

--- 13-3. canonicalize before hashing, or the signature breaks ---
  a raw sha256      : 342ae634b438dfbe6c65969e
  b raw sha256      : 760edb200363c660478ae117
  c raw sha256      : 6225dd8ec799896b92e0af16
  a canonical sha256: 85bdc381b4aff3953e97ddeb
  b canonical sha256: 85bdc381b4aff3953e97ddeb
  c canonical sha256: 85bdc381b4aff3953e97ddeb
  canonical form of a : {"amount":19.99,"id":1234567890123456800}
  and here is the catch:
    canonical form still contains 1234567890123456800
    which is NOT the id that was sent. canonicalization does not undo the loss.

Three things emerge.

  • With duplicate keys the last value wins. RFC 8259 recommends that names be unique and records that behaviour is unpredictable when they are not. All three parsers checked took the last value, but that is convention, not a guarantee
  • Key order is rearranged. Keys that look like integers were pulled to the front. A design that gave meaning to order breaks here
  • Canonicalizing makes the hashes agree. Three texts differing only in whitespace and key order hashed identically after canonicalization

But the point of this section is in the last block. The ID inside the canonicalized result is already the damaged value. Canonicalization only removes differences in notation; it cannot bring back digits that are gone. A matching signature is therefore no guarantee that the value is the original. A system that confirms integrity by canonical hashing has to defend this separately.

--- 13-4. escapes and lone surrogates in the same payload ---
  JSON.parse of \u escaped digits stays a string:
    value : 1234567890123456789   length : 19
  numbers cannot be escaped that way:
    JSON.parse of an escaped bare digit -> SyntaxError
  JSON.stringify of a lone surrogate : "\ud800"  (well-formed output, ES2019)
    code unit : U+D800
    round trip identical : true
  and a number-shaped string is not a number:
    JSON.parse('"1e21"') typeof : string

--- 11-6. key order and duplicate keys, third parser ---
  decode of three identical keys -> id = 3
  canonical encode of {b,a,c}    -> {"a":2,"b":1,"c":3}
  default encode of the same     -> {"c":3,"b":1,"a":2}
  • Digits inside a string stay a string even when written as Unicode escapes. They are not damaged
  • Conversely a number literal cannot be escaped. Escape it and it is a syntax error
  • An unpaired surrogate was emitted safely in escaped form during serialization and round-tripped identically
  • A string that looks like a number is still a string. Put 1e21 in quotes and it does not become a number
  • In Perl too the last duplicate key won, and there was a separate option for fixing key order

14. Why it is always discovered late

The nastiest property of this incident is not technical but temporal. The reason discovery is late is structural.

  • Development data has small IDs. Develop with 1, 2, 3 and the problem does not exist. As the output in section 2 shows, everything up to sixteen digits is fine
  • Staging is usually small too. Production data is normally not used as is, so it does not surface here either
  • Early production does not catch it. With sequential numbering it takes a long time for an ID to reach sixteen digits
  • The detonation comes when the ID scheme changes. Move from sequential to distributed IDs, adopt timestamp-based IDs, or start ingesting another system's IDs, and 19 digits suddenly arrive
  • By then the code is in many places. What would have been one fix at design time is now the whole path
  • Every test passes. Because the IDs in the existing fixtures are small. Write new code and verify it with old fixtures and it still passes

The response is simple: mix 19-digit IDs into the development data. Changing one fixture surfaces the problem during development. It costs almost nothing and has the largest effect.

There is also a way to check whether this has already happened. Search logs and audit records for pairs of the same field differing only in the last one or two digits. If values that share all leading digits and differ at the tail appear repeatedly, that is not coincidence but the fingerprint of an incident that already occurred.

15. Diagnostic procedure - finding it in a live API

The order for inspecting a running API was built as executable code. The core principle is one: look at the raw text, not the parsed object.

  • Three integers past 2 to the 53rd: an order ID, a wallet balance, and a nanosecond timestamp
  • One exponent notation, the hole seen in the previous section
  • One decimal whose notation changes, where 1234.50 becomes 1234.5
  • The 20-digit number inside a string was not flagged. That is correct behaviour, because a string is not damaged

  {"order_id":1234567890123456789}

  {"memo":"ref 1234567890123456789","id":42}

  • A large integer sent as a number is caught
  • The same value sent as a string reports clean. That is the correct verdict
  • A long number inside a string is skipped, because the expression is written to consume strings first
  • The money notation 100.00 and the exponent form 1e21 are caught separately
  • The nanosecond timestamp is caught and the millisecond one reports safe. It genuinely is

A word on schema practice as well. Attaching format: int64 to an integer field in OpenAPI-style schemas is a widespread practice, but that annotation is a documentary declaration and does not compel a parser. It helps a code generator pick an appropriate type, and nothing more; writing it in the schema does not suddenly make a JavaScript consumer exact. How to operate a specification as a contract is the subject of API documentation governance.

17. What is not asserted here

Separating what was verified from what was not.

  • Not every language was checked. What was checked is JavaScript, Python, Perl and SQLite only. Other languages and other parser implementations may behave differently again
  • Even within one language there are several parsers. What is shown here is each language's default implementation; alternative parsers differ in options and behaviour
  • There is version dependence. Receiving the original text in a reviver is a comparatively recent specification and older runtimes lack it. It worked in this environment is not it works everywhere
  • The money experiment's result was not generalized. In this sample the float sum and the integer sum agreed. In another sample they diverge. This article states only that the difference depends on the sample
  • No spreadsheet application itself was run. Only the CSV text layer and the numeric conversion layer were checked. The behaviour of a specific product must be verified separately
  • Performance was not measured. How much string identifiers cost in indexing and lookup depends on data scale, so it has to be measured locally

Closing: the place the standard left blank

Written once more in one sentence: the JSON standard did not specify the precision of numbers, and each language filled that blank its own way. Because those choices differ, values diverge while both sides behave correctly.

So this problem cannot be fixed in code. Change the parser, change the library, change the language, and it happens again as soon as the next consumer is a different language. The only place that can be fixed is the contract: writing down which values travel in which form, and keeping that resident as a boundary test.

If you must pick a single cheapest action to take right now, it is to mix one 19-digit ID into the development data. One line of fixture. It is the absence of that line that makes this incident always appear in production, after the IDs have grown, through a customer enquiry.

# JSON Number Precision — Type Decision Table and Boundary Test Values

> Source: braindetox.kr — The Last Digits of a 64-bit ID Change When It Travels Through JSON
> Evidence: verified by execution on Windows 10 / Node 22.16.0 / Python 3.13.3 / Perl 5.38.2 (JSON::PP 4.16) / SQLite 3.49.1
> Specification: RFC 8259 Section 6 — the interoperable integer range is -(2^53)+1 through (2^53)-1

## 1. One-line summary

The JSON standard does not specify the precision of numbers. What breaks is the parser, which means the language.
When the sender and the receiver are written in different languages, the value changes **without raising anything**.

## 2. Data nature to type decision table

| Nature of the data | Example | Form to put in JSON | Reason | How to verify |
|---|---|---|---|---|
| Identifier (never arithmetic) | order number, user ID, snowflake ID | **string** | no arithmetic is needed, preserving digits is the only requirement | compare strings after a round trip for an exact match |
| Time in nanoseconds | epoch_ns, trace timestamp | **string** or integer milliseconds | 19 nanosecond digits exceed 2^53 | round trip a 19-digit sample and inspect the tail |
| Money | payment amount, balance | **integer minor units** plus a currency code (or a string) | neither the decimal notation nor the scale survives a JSON number | round trip 100.00 and see whether it becomes 100 |
| Quantity or count | stock level, page number | integer as is | there is no path to 2^53 | check that an upper bound is written in the contract |
| Measurement or ratio | latency, coordinate, probability | number as is | the precision loss is inside the tolerance | check that 17 significant digits round trip |
| Hash or signature | SHA-256, checksum | **hexadecimal string** | it was never a value to treat as an integer | validate the length and the character set |
| 64-bit bit flags | permission mask | **string** or array | some languages truncate bitwise operations to 32 bits | check that the top bit survives |

## 5. API contract sentences (paste into a specification or a review)

- This field is an **identifier** and is never subject to arithmetic. It is transmitted as a JSON string, with a maximum length of 20 characters.
- This field is transmitted as a JSON number, and the value is guaranteed to lie between -(2^53)+1 and (2^53)-1 inclusive.
- Money fields are transmitted as **integer minor units** of the currency. The unit and the currency code travel in the same object.
- NaN, Infinity, and -Infinity never appear in a response. An unmeasurable value is expressed as `null`.
- A consumer may assume that parsing any number field as a double-precision float loses nothing.
- Write both `type: integer` and `format: int64` in the schema, and state explicitly that `format` is documentation and does not compel any language parser.
- When a client sends an identifier back, it is required to return **the exact text it received**.

## 6. Diagnostic procedure for an API already in production

1. Capture the **raw response text**. Looking at the parsed object is already too late.
2. Find every integer literal of 16 or more digits in that text. Exclude digits that sit inside strings.
3. Compare each literal against `2^53-1`. A single value above it confirms the exposure.
4. Search separately for literals carrying exponent notation (`e`, `E`). A digit-count check never catches those.
5. Compare decimal literals against their re-serialized form **as strings**. Watch trailing zeros and scale disappear.
6. Search logs and audit records for pairs of the same field differing **only in the last one or two digits**. That is the fingerprint of an incident that already happened.
7. Put the boundary values from section 3 into the contract tests and assert on strings rather than on values.

## 7. Points of defence

| Point | What to do | What not to do |
|---|---|---|
| schema and contract | pin identifiers to strings and write the upper bound down | assuming that it usually does not get large |
| server serialization | emit identifiers as strings | emitting numbers and leaving it to the client |
| client parsing | find the large integers in the raw text and take them as strings or big integers | converting to a big integer after parsing, which is already too late |
| storage | put them in integer columns | float columns, and spreadsheet auto-conversion |
| testing | mix 19-digit IDs into the development data | developing with 1, 2, and 3 only |
| audit | keep the boundary values resident in the contract tests | checking only after an incident |

## 8. What not to do

- Converting a large integer to a string or a big-integer type after parsing — the digits are already gone at that moment
- A check that only counts digits — exponent notation walks straight through it
- Verifying a round trip by asking whether the values are equal — two damaged values are equal to each other
- Developing and testing only with low IDs — it detonates in production once the IDs have grown
- Confirming integrity by hashing after canonicalization — canonicalization cannot restore digits that are already gone
- Treating send-it-as-a-string as the end of the matter — you still have to decide where to pay for sorting, range queries, and comparison
