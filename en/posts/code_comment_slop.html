Comments Should Say What Code Cannot

What a comment that repeats the code costs, and what belongs in that space instead

Aug 30, 2026 Dev & Infra

A name for comments that say a lot and leave nothing

You open a colleague's change and there are thirty lines of comment sitting above one function. You read them dutifully. By the end you know what the code below does — which you would have known by reading the code. The thing you actually wanted to know, why there is a second sort here and why the retry count is three, appears nowhere in those thirty lines.

A developer recently gave this kind of prose a name: yap. Roughly, words for the sake of words — not speech aimed at a listener, but the noise a speaker makes while thinking. The proposal in that piece is simple. Rather than write the same long review remark over and over, call it by a short name, and let that name stand for a single instruction: step back and think about what value this comment actually provides here. That is the occasion for this piece. The question underneath it is the one worth spending time on. What is a comment for?

One thing is worth settling up front. A comment that restates the code is not a new phenomenon. People have been writing them for a very long time — because that is how they were taught, because a house standard demands a comment on every change, or because posting code with no prose feels like it will look careless. What changed recently is not the kind but the volume, and volume is why it finally became conspicuous enough to earn a name. So the question is not who wrote it, but what should be in that space.

Code already says what it does — the three slots left for a comment

Google's published code review guidance contains one sentence that settles most of this. Comments are for information that the code itself can't possibly contain, like the reasoning behind a decision. The same document adds that comments are usually useful when they explain why some code exists, and should not be explaining what the code is doing.

To use that in practice, the why needs splitting. A comment has three slots to fill.

SlotCan code express it?What is lost when it is empty
Why it was done this wayNo. The choice survives; the reasoning does notThe next person redoes the whole evaluation from scratch
What was ruled outNo. Rejected alternatives leave no trace in codeA change arrives that reverts to an approach already known to fail
What is assumedPartly. Only as far as types and validation reachThe day the assumption breaks, finding the cause takes days
What it doesIt already says so — more precisely than prose canNothing

The last row is where this whole argument starts. Code is a description of its own behavior that is always current and always accurate, because the code is the behavior. Write the same content beside it and you have created a copy, and that copy is neither guaranteed current nor guaranteed accurate. The moment two statements about the same fact sit side by side, the reader has to decide which one to believe.

// What the code already says
// Set the retry count to 3
const RETRY = 3;

// What the code cannot say
// The upstream gateway starts a 30-minute block on the 4th request.
// 3 is the largest value below that threshold.
const RETRY = 3;

The two comments are about the same length. Delete the first and nothing happens; delete the second and six months later someone raises the retry count to five and gets blocked. The value of a comment is measured less by its length than by what disappears when you remove it.

What a comment that repeats the code actually costs

Framing redundant comments as a waste of reading time describes the smallest line on the bill. Time is the cheap item. The expensive part arrives later.

The mechanism is one sentence long. Code changes; the comment next to it usually does not. Not out of laziness. Whoever came to edit the code came to change behavior, and no compiler, linter, or test ever inspects what a comment claims. Nothing anywhere reports that a comment has gone false, so comments rot quietly. PEP 8 nails the consequence in one line — comments that contradict the code are worse than no comments — and the same document adds that inline comments stating the obvious are unnecessary and in fact distracting.

WhenThe costWho pays it
Right after writingA reviewer reads it and cross-checks it against the codeThe reviewer
Months laterOnly the code moved. A wrong map is left behindThe next person to open the file
During an incidentA stale comment seeds a wrong hypothesisEveryone on the response
ContinuouslyThe one line worth reading is buried among restatementsEveryone
In historyLines unrelated to behavior inflate the diff and thin out reviewThe team

The third row is the expensive one. A missing comment sends someone back to the code; a wrong comment holds them somewhere else. Most engineers have spent an afternoon digging through a cache because a comment said the value came from the cache. That comment was true until six months ago.

The fourth row is not far behind. Reading comments at all is a habit that rests on trust. When nine of every ten are restatements of the code, people start skipping comments, and the tenth one — the line that was warning about something real — gets skipped with them. What redundant comments damage most is not the file, but the credit of commenting as a practice.

Why these comments appear — no bad intent on either side

Split the causes into the human side and the generated side and you can see two different routes arriving at the same output.

On the human side there are usually three.

  • Habit — the first lesson was that comments explain the code. In teaching material that is correct, because a learner cannot yet read the code. The trouble is that the habit walks straight into production work.
  • Policy — where a change without comments gets bounced, comments always appear. And the easiest comment to write is the one that paraphrases the line above it.
  • Anxiety — the sense that submitting bare code will look like you did not try. That is a team-atmosphere problem, not a technical one.

The generated side is structural. Ask for an explanation line by line, with no wider context, and line-by-line explanations come back. Looking at one line alone, there is no way to know why it is needed; all that remains to say is what it does. This is not a capability failure. The shape of the request fixed the shape of the answer. Ask a person to annotate every line and the result looks much the same.

Underneath both sits a deeper reason. The what is on screen and easy to write; the why is in your head and hard to write. Recording the why means pulling back out what you considered and discarded, and that is the last thing anyone wants to do once the code finally works. So hands move toward the easy side. It is a slope, not a sin.

What the old rule about commenting generously produced

Plenty of organizations have a standard saying to comment sufficiently. The intent is right. It turns on how sufficiency gets judged. When the judgment is a count or a ratio, people fill the count. That is not a failure of diligence; it is a property of measurement. Whatever is counted, behavior lines up with it.

  • Comment-line ratio metrics — the cheapest way to raise a ratio is to restate the code. The why fits in one line; the paraphrase takes ten.
  • A comment required on every function — functions whose names already say everything acquire a sentence that unpacks the name.
  • A comments item on the review checklist — checking only for presence means presence is enough to pass.

A counterexample is worth putting beside these. Go's documentation convention requires that every exported (capitalized) name should have a doc comment. Formally that looks like the rules above, yet the outcome differs, because Go's doc comments are extracted by tooling and published as documentation. Those comments have a defined reader: an outside developer meeting the package for the first time. A rule with a destination becomes a contract rather than a quota.

Which yields a usable criterion. When writing a comment rule, specify the reader rather than the number. If there is an answer to who reads this comment and when, the comment tends to be worth something; if there is no answer, only the count remains. Rebuilding review criteria around maintainability is treated separately in code review through the lens of maintainability.

Where good comments sit

So where do comments go? Broadly, three places.

  • Beside code that looks wrong — anything written against convention. Where the next person will assume it is a mistake and fix it, there has to be a marker saying it is intent, not error.
  • Beside decisions that are easy to reverse — stopgaps, workarounds, provisional constants. Write down the condition for reverting and the comment expires on its own later.
  • Where an external constraint is encoded — an upstream API's behavior, a regulation, a hardware limit: facts that cannot be checked from inside the repository.

What the three share is that the information originates outside the repository. No amount of reading the code and no number of test runs will recover it. Someone has to write it down.

// Second sort: the upstream API does not guarantee ordering.
// The spec document claims it is sorted, but some real responses are not.
// Once upstream fixes it, this line can go.
items.sort(byCreatedAt);

Those three lines carry all three slots from the table: why it was done this way (the ordering is not trusted), what is assumed (spec and reality diverge), and when it can be reverted (once upstream fixes it). Remove them and all three vanish, and the remaining sort looks to the next reader like a redundant call.

What can move out of a comment and into the code

Before writing a comment, one question is worth asking. Can the code say this itself? If it can, move it, because an explanation carried by code does not rot. The compiler and the tests keep it honest for you.

  • Names — a comment explaining what a value is usually gets absorbed into a name. If the comment exists because a unit is ambiguous, put the unit in the name or the type.
  • Function extraction — when a comment saying which part starts here appears three times inside one function, that is a signal for three functions. If a comment is acting as a section heading, that heading is the function name.
  • Types and enums — a comment saying this argument is 0, 1, or 2 becomes a rule when it moves into a type. Prose can be ignored; a type stops the build.
  • Validation and tests — a comment saying not to pass a negative number can become an input check or a single test. Prose is honored only if read; a test is honored whether or not anyone reads it.
// Before — a comment guards the unit
// t is in seconds. Do not pass milliseconds
function expire(t) { /* ... */ }

// After — the name guards the unit
function expire(ttlSeconds) { /* ... */ }

The point of this section is not economy. It is that the urge to write a comment is sometimes a design signal. When the thought arrives that this part is complicated enough to need an explanation, look first at whether the complicated part can be fixed. Not everything moves, of course. Rejected alternatives, the state of a system you do not control, when this code becomes safe to delete — none of them have anywhere to live in code. Those sentences are what comments were always for, and thinning the repetition is how you keep that space open.

Where the line between comments and documentation falls

Not every explanation has to sit next to code. Two criteria are usually enough to place one.

  • Must whoever edits this code see it? — a sentence whose absence causes a mistake belongs beside the code. Put it in a wiki and nobody reads it.
  • Does this sentence change with the code? — if it changes in the same commit, keep it close. If it moves on its own schedule, move it out. A sentence that is never revised alongside the code goes stale wherever it lives.
  • Might the reader never look at the code? — if the audience is an outside developer who only calls this function, that is doc-comment territory, a layer tooling extracts and publishes.
  • Read once, or consulted repeatedly? — install and operations procedures are sequential prose and belong in documents. Sequence is invisible when scattered beside code.
Kind of sentenceWhere it goesWhy
Why this line looks like thisInline, beside the codeOnly whoever edits that line needs it
A function's preconditions, returns, errorsDoc commentTooling extracts it into published docs
Why this module exists at allTop of the module, or repo docsIt is not tied to a single file
System structure, decision recordsRepo documentsSpans modules and is revised separately
Install and operations proceduresRepo documentsSequential prose does not fit beside code

A blurry band always remains. In that band it is safer to keep whatever is most at risk of never being updated closer to the code, because anything sitting beside the code is at least in the field of view of whoever opens the file. The structural version of the docs-drift problem for APIs is covered in API documentation governance.

How to handle comments in review

This is the part to be careful with. Flagging a redundant comment is read as a remark about the person far more easily than a bug report is. Being told the code is wrong lands as a fact about the code. Being told the prose is wrong lands as a fact about you.

  • Turn the question around — not why did you write this, but can we state in one sentence what a reader gets from this line. If an answer comes, that answer is the new comment. If none comes, the line goes.
  • Do not introduce the rule in the review — agree on it as a team and put a paragraph in the standards first. With the agreement already there, the remark is rule application rather than a clash of taste.
  • Shorthand only works when documented — a repeated remark is easier to abbreviate. But if the meaning of the abbreviation is written down nowhere, it lands as nothing more than a curt word.
  • Mark blocking and non-blocking apart — redundant comments are rarely a reason to hold a merge. Separating what blocks from what can wait makes the remark lighter to receive.

And there is a line worth not crossing. Do not infer things about the author from the style of a comment. Once length and formality start being read as evidence of how a change was produced, review has moved off the code and onto the person. Why such inferences break down is covered in what a style-drift measurement can and cannot say — briefly, a tendency visible at population scale loses its grounding the moment it is applied to a single document. Inside a team the price is higher still: get it wrong once and that person reviews defensively from then on.

Review is better off asking one question. Does this comment earn its place here? Who wrote it is not an input to that judgment.

What to settle before using a generation tool

That is as far as the tooling discussion needs to go; the rest is deciding what to ask for. Fix the request and you fix the output.

  • Worth asking for — the conditions a function assumes to be true, the alternative not taken and why, and for a reversible measure, the condition for reverting it. All items code cannot carry.
  • Not worth asking for — an explanation per line, a record of the reasoning, a summary that unpacks the function name. Ask and it arrives; once it arrives it has to be removed.
  • A paragraph in the conventions file — put the comment rules in the project instruction file and you stop repeating the same sentence. What matters is that the same paragraph governs people too.
  • Separate draft from submission — notes left during the work get cleaned up when the work ends. The problem is draft residue reaching the main branch, not the existence of drafts.

The last line of defense is not a tool setting. It is reading your own change once, before submitting, with the eyes of someone seeing it for the first time. That is not a new discipline; it was always part of submitting. What changed is that as code became faster to obtain, reading time started to look comparatively expensive. The shape of that shift is treated in the shifting economics of code.

The standard is simple. Written by hand or handed over, the moment it is submitted the code carries the name of whoever submitted it. Making other people read prose you did not read yourself is the discourtesy. Using a tool is not.

What a bulk cleanup deletes along the way

Once you notice how many restated comments there are, the urge is to clear them in one pass — a regex that strips every short comment, or handing a tool the job of removing unnecessary ones. There is one hard-to-reverse risk in that work. Deleting a comment you do not understand is not the same as deleting one you judged unnecessary. The first is not a judgment; it is a skipped step.

  • Sometimes the shortest comment matters most — a single line saying not to reorder these calls. Filter by length and that line goes first.
  • One question before deleting — what mistake does the next person make without this line? If a mistake comes to mind, the comment stays.
  • Prefer fixing a stale comment to deleting it — stale means it was true once, which makes it likely that something worth stating still belongs in that spot.
  • Split the commits — put hundreds of sites in one commit and nobody can review it. A cleanup that arrives at unreviewable size is not a cleanup; it is a bet.

The safe order runs like this: sweep file by file, repair what is stale, delete what you have no basis to repair, and record the reason in the commit message. It looks slow, but the goal is not fewer comments; it is that the remaining ones can be trusted. Drive the number down alone and the goal is lost.

In closing — a comment is where code says what it cannot

Three sentences remain. Code already says what it does — more precisely than prose, and always current. The slots a comment fills are why it was done this way, what was ruled out, and what is assumed — none of which survive in code. The real cost of a restated comment is not reading time but staleness — the code moves, the comment stays, and what is left is a map worse than none.

The practice reduces to one habit. Before writing a comment, picture what disappears if you delete it. If nothing disappears, the line was never needed. If something does, that is exactly why the comment exists — write that.

One more thing belongs here. Arguing against redundant comments is not arguing for fewer comments. If anything the opposite: most repositories are short on comments that say why. Clearing out repetition is how you make room, and the sentences that go into that room exist only in the head of the person who wrote the code. Written down now, they survive. Left unwritten, nobody recovers them six months from now.
