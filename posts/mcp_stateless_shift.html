MCP가 세션을 버렸다 - 무상태 전환이 서버 운영에서 바꾸는 것

스티키 라우팅과 재개 스트림이 사라진 자리에 무엇을 놓을 것인가

2026-08-16 개발/인프라

서론: 인그레스 설정 앞에서 멈춰 있던 MCP 서버

MCP 서버를 사내 클러스터에 올릴 때 손이 멈추는 자리는 대개 코드가 아니라 인그레스 설정이다. 파드를 두 개로 늘리는 순간 절반의 요청이 엉뚱한 인스턴스로 가서 「그런 세션 없음」을 돌려받는다. 그래서 세션 어피니티를 켜고, 그러면 배포할 때마다 진행 중이던 연결이 통째로 끊기고, 그걸 막으려고 공유 저장소에 세션을 넣으면 이번엔 그 저장소가 단일 장애점이 된다. 익숙한 순환이다.

MCP 명세의 2026-07-28 개정판은 그 순환의 뿌리를 잘랐다. 프로토콜 수준의 세션이 사라졌고 initialize 핸드셰이크도 없어졌다. 이제 요청 하나하나가 자기가 어떤 프로토콜 버전으로 말하는지, 클라이언트가 무엇을 할 수 있는지를 스스로 들고 간다. 서버는 앞 요청을 기억할 의무가 없어졌고, 인프라 입장에서는 MCP 트래픽이 평범한 HTTP 트래픽처럼 다뤄진다는 뜻이다.

공짜는 아니다. 세션이 떠받치던 것들 — 진행 중인 멀티스텝 작업, 서버가 먼저 말을 거는 구조, 끊긴 스트림의 재개 — 은 사라진 게 아니라 다른 곳으로 옮겨졌거나 아예 운영자 몫이 됐다. 이 글은 그 교환의 내용을 다룬다.

MCP 자체가 처음이라면 MCP(Model Context Protocol) 완벽 가이드가 개념을, Claude Code MCP 서버 고르는 기준 - 목록 말고 판단 축 여섯 개가 클라이언트 쪽에서 서버를 고르는 관점을 다룬다. 여기서는 반대편, 즉 서버를 만들고 굴리는 쪽의 이야기만 한다.

인용한 명세는 모두 2026-07-28 개정판이며, 이 글의 확인 시점은 2026년 8월 16일이다. MCP 명세는 날짜 스탬프로 버전을 매기고 하위 호환이 유지되는 동안에는 번호가 오르지 않으므로, 반년 뒤에 읽는다면 현재 개정판이 무엇인지부터 확인하는 편이 안전하다.

1. 세션이 만들던 운영 부담 - 무엇이 실제로 비쌌나

2025-03-26부터 2025-11-25까지의 Streamable HTTP는 서버가 Mcp-Session-Id 헤더로 세션을 발급하고, 클라이언트가 이후 요청에 그 값을 계속 실어 보내는 구조였다. HTTP DELETE로 세션을 끝냈고, GET으로 별도의 SSE 스트림을 열어 서버가 먼저 보내는 메시지를 받았으며, 스트림이 끊기면 Last-Event-ID로 재개했다.

설계로는 우아하다. 문제는 이 세 가지가 전부 인프라 계층에 제약을 건다는 점이다.

  • 스티키 라우팅이 사실상 강제된다. 세션 상태가 인스턴스 메모리에 있으면 같은 세션의 후속 요청은 반드시 같은 파드로 가야 한다. 쿠키 기반 어피니티가 없는 L4 앞단이라면 헤더 기반 해싱을 직접 짜야 한다.
  • 수평 확장이 균등하지 않다. 새 파드는 새 세션만 받으므로 부하가 기존 파드에 남는다. 오토스케일러가 인스턴스를 늘려도 즉시 효과가 나지 않고, 줄일 때는 살아 있는 세션 때문에 축출을 미뤄야 한다.
  • 배포가 곧 단절이다. 롤링 업데이트로 파드가 교체되면 그 파드가 들고 있던 세션은 소멸한다. 클라이언트는 「세션 없음」을 받고 처음부터 다시 붙는다. 무중단 배포를 표방하면서 실제로는 사용자 작업이 끊기는 전형적인 자리다.
  • 세션 저장소를 도입해도 문제가 옮겨갈 뿐이다. 상태를 외부 캐시로 빼면 라우팅은 자유로워지지만, 이번엔 그 캐시의 가용성·직렬화 비용·만료 정책이 새 운영 항목이 된다. 세션 취소가 규모에서 어떻게 무너지는지는 로그아웃이 즉시 반영되지 않는 이유 - 세션 취소가 규모에서 무너지는 지점에서 자세히 다뤘다.
  • 중간 장비가 내용을 모른다. 프록시 입장에서 모든 요청은 같은 엔드포인트로 가는 같은 모양의 POST다. 어떤 도구를 부르는 요청인지 알려면 본문을 파싱해야 하는데, 게이트웨이에서 JSON 본문을 뜯는 것은 성능과 보안 양쪽에서 달갑지 않다.

정리하면 비용의 정체는 세션 그 자체가 아니라 세션이 요구하는 위치 고정이었다. 요청이 어디로 가도 되는 시스템과 특정 인스턴스로 가야 하는 시스템은 운영 난이도가 한 단계 다르다.

2. 2026-07-28 개정판이 실제로 걷어낸 것

변경 폭이 넓어서 「무상태가 됐다」는 한 줄로는 감이 안 온다. 운영에 직접 닿는 항목만 추리면 이렇다.

먼저 핸드셰이크가 없다. initialize와 notifications/initialized가 제거되고, 모든 요청이 _meta 안에 프로토콜 버전과 클라이언트 능력을 담아 보낸다. 키 이름은 역도메인 형태로 io.modelcontextprotocol/protocolVersion, io.modelcontextprotocol/clientCapabilities, io.modelcontextprotocol/clientInfo다. 서버는 각 결과의 _meta에 자기 정보를 담아 응답한다. 버전이 맞지 않으면 서버가 UnsupportedProtocolVersionError를 돌려주면서 자기가 지원하는 버전 목록을 실어 보내고, 클라이언트가 그중 하나로 재시도한다. 협상 왕복이 아니라 거절과 재시도다.

둘째로 세션 헤더가 없다. Mcp-Session-Id와 프로토콜 수준 세션이 함께 제거됐다. 여기서 따라오는 결과가 하나 있는데 놓치기 쉽다 — tools/list·resources/list·prompts/list가 연결마다 달라질 수 없게 됐다. 연결별로 다른 도구 목록을 보여 주던 서버라면 그 설계부터 바꿔야 한다. 호출 사이에 상태가 필요하면 서버가 발급한 명시적 핸들을 평범한 도구 인자로 주고받으라는 것이 명세가 제시하는 방향이다.

셋째로 서버가 먼저 요청을 보내지 못한다. 예전에는 서버가 SSE 스트림 위로 roots/list나 sampling/createMessage, elicitation/create 같은 JSON-RPC 요청을 밀어 넣을 수 있었다. 이제는 결과 자체에 「입력이 더 필요하다」는 신호를 담아 돌려준다. 모든 결과에 resultType 필드가 붙고, 값이 input_required면 inputRequests에 무엇이 필요한지가 들어 있다. 클라이언트는 그것을 채워 inputResponses와 함께 원래 요청을 새 요청 ID로 다시 보낸다. 이 패턴을 다중 왕복 요청(MRTR)이라 부른다.

넷째로 GET 스트림이 없다. 서버가 밀어 주는 변경 알림을 받으려면 subscriptions/listen을 POST로 부르고, 그 응답 스트림이 장수 채널이 된다. 클라이언트는 받고 싶은 알림 종류를 명시적으로 고른다. 반면 notifications/progress처럼 특정 요청에 딸린 알림은 여전히 그 요청의 응답 스트림으로만 흐른다. 두 스트림의 역할이 분리됐다.

다섯째로 재개가 없다. Last-Event-ID와 SSE 이벤트 ID가 제거됐다. 응답 스트림이 끊기면 진행 중이던 요청은 잃어버린 것이고, 클라이언트는 새 요청 ID로 처음부터 다시 보내야 한다. 이 한 줄이 뒤에서 다룰 멱등성 이야기의 출발점이다.

운영에 크게 작용하는 변경이 하나 더 있다. Streamable HTTP POST에 Mcp-Method와 Mcp-Name 헤더가 필수가 됐다. 본문의 메서드명과 대상 이름을 헤더로 미러링하는 것인데 목적이 분명하다 — 중간 장비가 본문을 파싱하지 않고도 라우팅하고 관찰하게 하려는 것이다. 목록·읽기 결과에는 ttlMs와 cacheScope가 붙어 캐싱 계약이 명시화됐고, ping과 logging/setLevel은 제거됐다.

3. 전송 방식의 변천 - 셋은 서로 다른 세상을 전제했다

전송 방식을 나열하면 진화처럼 보이지만, 실제로는 각자 다른 배포 형태를 가정하고 만들어진 것이다. 어떤 전제가 깔려 있었는지 알면 왜 지금 이 모양이 됐는지가 보인다.

전송연결 모델세션서버 발신 요청스트림 재개확장 전제
stdio
(현행 유지)		 클라이언트가 띄운 자식 프로세스의 표준 입출력, 줄 단위 JSON-RPC 프로세스 수명이 곧 경계 현행 개정판에서는 결과 안에 입력 요청으로 실림 해당 없음 확장 개념 자체가 없음. 사용자 1인 1프로세스
HTTP+SSE
(2024-11-05, 현재 Deprecated)		 GET으로 SSE를 열고 별도 POST 엔드포인트로 송신 열린 연결이 곧 세션 SSE 스트림으로 자유롭게 밀어 넣음 정의 없음 엔드포인트 2개 + 연결 고정. 로드밸런서 뒤에 두기 가장 어려움
Streamable HTTP
(2025-03-26~2025-11-25)		 단일 엔드포인트 + 선택적 GET 스트림 Mcp-Session-Id 발급, DELETE로 종료 SSE 스트림 위에 JSON-RPC 요청 가능 Last-Event-ID로 재개·재전달 스티키 라우팅 또는 공유 세션 저장소 필요
Streamable HTTP
(2026-07-28)		 단일 엔드포인트, POST만. 메시지 하나가 POST 하나 프로토콜 세션 없음 금지. MRTR의 InputRequiredResult로 대체 없음. 새 요청 ID로 재발행 요청 단위 라우팅. 어느 인스턴스로 가도 무방

표에서 읽어야 할 것은 마지막 열이다. stdio는 애초에 확장을 생각하지 않은 전송이다. 내 노트북에서 도는 프로세스에 세션이라는 개념을 도입할 이유가 없다. HTTP+SSE는 브라우저 시대의 습관을 그대로 옮긴 것이고, 두 엔드포인트를 짝지어 유지해야 해서 프록시 구성이 지저분해진다. 중간의 Streamable HTTP는 엔드포인트를 하나로 합쳤지만 세션을 남겨 두는 바람에 단일 엔드포인트의 이점을 라우팅에서 회수하지 못했다. 현행 개정판은 그 마지막 매듭을 푼 셈이다.

요청 하나가 어떤 모양인지 보면 전환의 성격이 분명해진다. 자기소개가 전부 요청 안에 들어 있다.

POST /mcp HTTP/1.1
Accept: application/json, text/event-stream
Authorization: Bearer <access-token>
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: run_query

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "run_query",
    "arguments": { "sql": "select 1" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "example-client", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

헤더와 본문에 같은 값이 두 번 나오는 것이 이상해 보일 수 있는데, 이건 중복이 아니라 계약이다. 명세는 헤더 값과 본문 값이 어긋나면 서버가 400과 함께 HeaderMismatch 오류를 반환하도록 요구한다. 이유가 분명하다 — 로드밸런서는 헤더를 보고 라우팅하는데 서버는 본문을 보고 실행한다면, 둘이 다른 진실을 믿는 순간이 곧 공격면이 된다.

4. 얻는 것 - 배포와 확장이 평범해진다

무상태 전환의 이득은 대부분 MCP를 특별 취급하지 않아도 되는 데서 나온다.

  • 세션 어피니티를 끌 수 있다. 신세대 클라이언트만 상대한다면 요청은 아무 인스턴스로 가도 된다. 라운드로빈이든 최소 연결이든 기존 정책을 그대로 쓴다.
  • 롤링 배포의 파장이 요청 하나로 줄어든다. 예전에는 파드 교체가 세션 전체를 날렸다. 이제 영향받는 것은 그 순간 처리 중이던 개별 요청이고, 재시도로 회수된다. 단 장수 알림 스트림은 예외인데 이건 다음 절에서 다룬다.
  • 오토스케일링이 즉시 반영된다. 새 인스턴스가 뜨면 바로 다음 요청부터 부하를 나눠 받는다. 축소할 때도 진행 중인 요청만 빠지길 기다리면 되고, 세션 만료를 기다릴 필요가 없다.
  • 중간 장비가 똑똑해진다. Mcp-Method와 Mcp-Name이 헤더에 있으니 본문을 뜯지 않고도 도구 단위 레이트리밋, 무거운 도구 전용 풀로의 라우팅, 메서드별 지표 분리가 가능하다. 도구 파라미터를 헤더로 미러링하는 x-mcp-header 주석을 쓰면 테넌트나 리전 같은 값으로도 라우팅할 수 있다.
  • 캐싱이 계약이 됐다. 목록과 읽기 결과에 ttlMs와 cacheScope가 실린다. 공용 중간 캐시가 응답을 보관해도 되는지를 서버가 명시하므로, 폴링을 줄이는 근거가 추측이 아니라 응답 자체에서 나온다.

덧붙일 이득이 하나 더 있다. 목록 결과가 연결마다 달라질 수 없게 되면서 클라이언트 쪽 프롬프트 캐시 적중률이 올라간다. 명세가 tools/list 결과를 결정적인 순서로 반환하도록 권하는 것도 같은 이유다. 이건 인프라 이득이 아니라 토큰 비용 이득이다.

5. 잃는 것 - 진행 중 작업·구독·재개는 어디로 갔나

여기가 이 전환의 진짜 논점이다. 세션이 없어졌다고 세션이 하던 일이 없어진 것은 아니다. 셋으로 나눠 보면 각각 다른 곳에 착륙했다.

5.1 진행 중 작업 - 코어에서 확장으로

오래 걸리는 작업을 표현하던 실험적 Tasks는 코어에서 빠져 공식 확장 io.modelcontextprotocol/tasks로 옮겨졌다. 결과를 기다리며 막히는 호출 대신 폴링으로 상태를 조회하는 모양이 됐고, 지원 여부는 능력 협상의 extensions 필드로 주고받는다. 코어만 구현한 서버에는 이 기능이 아예 없다는 뜻이므로, 오래 걸리는 작업이 서비스의 본질이라면 확장 채택 여부가 곧 설계 결정이 된다.

5.2 서버가 먼저 말 걸기 - MRTR로 뒤집힘

사용자에게 확인을 받아야 하거나 모델 응답이 필요한 순간, 예전에는 서버가 클라이언트에게 요청을 보냈다. 이제는 서버가 요청을 반환한다. 방향이 뒤집힌 것이다. 실무적으로 중요한 차이는 두 가지다.

  • 서버가 대기 상태를 들고 있지 않아도 된다. 입력을 기다리는 동안 열려 있던 연결과 그에 매인 메모리가 사라진다. 재시도가 들어오면 어느 인스턴스든 처리할 수 있다.
  • 대신 맥락을 다시 실어 보내야 한다. 클라이언트는 원래 요청의 파라미터에 응답을 더해 재전송한다. 서버가 여러 왕복에 걸쳐 무언가를 상관지어야 한다면 requestState에 자기 식별자를 넣어 스스로 관리해야 한다. 왕복이 길어질수록 오가는 페이로드가 커진다는 대가는 실재한다.

5.3 구독과 재개 - 하나는 남고 하나는 없다

변경 알림은 subscriptions/listen이라는 장수 응답 스트림으로 남았다. 이름이 바뀐 게 아니라 성격이 바뀌었다 — 항상 열려 있던 GET 채널이 아니라, 원하는 알림 종류를 골라 명시적으로 여는 요청이 됐다. 조용한 구간에서 중간 장비가 끊지 않도록 서버가 주기적으로 SSE 주석 줄을 keep-alive로 흘리는 것이 권장된다. 리버스 프록시가 SSE를 버퍼링해 알림이 뭉쳐서 도착하는 문제는 X-Accel-Buffering: no 헤더로 다룬다.

재개는 남지 않았다. 끊긴 스트림은 되감기지 않는다. 이 결정은 무상태와 논리적으로 맞물려 있다 — 재개하려면 어느 인스턴스가 어디까지 보냈는지를 누군가 기억해야 하는데, 그 기억이 바로 걷어내려던 상태이기 때문이다. 그래서 롤링 배포는 요청 손실을 재시도로 회수하는 대신 열려 있던 알림 스트림은 확실히 끊는다. 클라이언트가 재구독을 알아서 하지 않으면 그 화면은 조용히 갱신을 멈춘다.

  • 취소 방식도 전송마다 다르다. HTTP에서는 클라이언트가 응답 스트림을 닫는 것이 곧 취소 신호이고, stdio에서는 취소 알림을 따로 보낸다.
  • 알림 스트림은 여전히 한 인스턴스에 붙어 있는 연결이다. 세션 고정을 지우는 것과 스트림이 무중단으로 유지되는 것은 별개 문제다.
  • 진행 알림과 변경 알림이 서로 다른 스트림으로 흐르므로, 클라이언트 구현에서 두 경로를 한 핸들러로 합쳐 두었다면 분리해야 한다.

6. 세션에 두던 것을 어디로 옮기나

이관에서 가장 어려운 부분은 코드 수정이 아니라 발견이다. 세션 객체에 무엇을 얹어 뒀는지는 대개 문서화돼 있지 않고, 오래된 서버일수록 여기저기 흩어져 있다. 찾는 요령은 단순하다.

  • 연결 수립 시점에 만들어져 요청 핸들러가 참조하는 객체를 전부 나열한다. 생성자에 들어가는 인자가 곧 세션 상태 목록이다.
  • 핸들러 안에서 인자로 오지 않았는데 값이 채워져 있는 변수를 찾는다. 그게 앞 요청이 남긴 흔적이다.
  • 인스턴스 로컬 디스크나 임시 디렉터리에 쓰는 경로를 훑는다. 업로드 버퍼와 중간 산출물이 여기 숨는다.
  • 도구 목록을 만드는 코드가 사용자·연결에 따라 분기하는지 본다. 분기가 있으면 현행 개정판에서는 성립하지 않는 설계다.

옮길 곳은 셋이다. 요청에 실어 보내는 것(불투명 커서, 서버 발급 핸들, MRTR의 requestState), 토큰에서 끌어내는 것(사용자 신원, 테넌트, 권한 범위), 공유 저장소에 두는 것(작업 진행 상태, 큰 중간 산출물). 기준은 하나다 — 클라이언트에게 맡겨도 안전한 값인가. 위조되면 권한이 넘어가는 값이라면 요청에 실으면 안 되고, 서버가 서명하거나 저장소에서 다시 검증해야 한다.

세션의 커서를 핸들로 바꾸는 모양은 개념적으로 이 정도 차이다. 아래는 특정 SDK의 API가 아니라 구조를 보이기 위한 의사 코드다.

// 이전: 연결 객체가 커서를 기억했다
session.cursor = result.nextCursor
handleNext(session)          // 같은 인스턴스여야 동작

// 이후: 서버가 발급한 불투명 핸들이 인자로 왕복한다
{ "method": "tools/call",
  "params": { "name": "list_rows",
              "arguments": { "cursor": "<서버가 서명해 발급한 문자열>" } } }
// 어느 인스턴스가 받아도 커서만 해석하면 이어서 처리된다

7. 기존 서버 이관 점검표

아래 표는 세션에 얹혀 있던 항목별로 어디로 옮기고 무엇으로 확인하는지를 정리한 것이다. 확인 방법 열은 실제로 돌려 보고 판정하라는 뜻이다 — 코드 리뷰로는 잘 안 잡힌다.

세션에 두던 것옛 동작옮길 곳확인 방법
프로토콜 버전·클라이언트 능력initialize 응답을 캐시요청마다 _meta와 MCP-Protocol-Version 헤더헤더를 뺀 요청이 400으로 거절되는지
인증 주체연결 시작 때 1회 확인요청마다 Bearer 토큰 검증 + 수신자 확인토큰 없는 호출이 401을 받는지
사용자별 도구 목록연결마다 다른 tools/list목록은 연결 불변. 구분은 토큰과 인자로같은 엔드포인트에 다른 토큰으로 목록을 비교
페이지네이션 커서세션 메모리의 오프셋서버가 발급한 불투명 커서 문자열페이지 사이에 인스턴스를 바꿔도 이어지는지
멀티스텝 작업 진행 상태세션 객체에 누적서버 발급 핸들 + 공유 저장소, 또는 Tasks 확장두 인스턴스에 요청을 번갈아 보내 재현

변경 알림 구독GET으로 연 SSE 스트림subscriptions/listen 응답 스트림롤링 배포 중 클라이언트가 재구독하는지

로그 레벨logging/setLevel 1회 설정요청마다 _meta의 logLevel레벨을 안 준 요청에 로그 알림이 안 나오는지

구세대 클라이언트를 받아야 한다면 서버를 이중 세대로 만든다. 명세는 두 세대를 같은 엔드포인트에서 동시에 서비스하는 것을 허용하고, 서버는 요청이 들어온 모양으로 판단한다 — 요청 단위 _meta를 들고 오면 무상태로, initialize로 시작하면 구세대 의미론으로 처리한다. 신세대만 지원하는 서버가 구세대 트래픽을 받으면 GET·DELETE에는 405를 주고, Mcp-Session-Id와 Last-Event-ID는 무시하되 세션 ID를 새로 만들거나 되돌려 주지 말라는 것이 명세의 지침이다.

세대 판정이 요청 하나의 성질이 아니라 서버라는 대상의 성질이라는 점도 기억할 만하다. 클라이언트는 그 판정을 서버 프로세스나 오리진 단위로 캐시한다. 서버를 신세대로 올린 날 클라이언트가 구세대라고 기억하고 있으면 한동안 엉뚱한 경로로 붙는다.

8. 멱등성과 재시도 - 끊긴 스트림은 되감기지 않는다

재개가 사라진 대가는 곧장 중복 실행 위험으로 나타난다. 시나리오가 아주 구체적이다. 클라이언트가 결제 도구를 호출한다. 서버가 SSE 스트림을 열고 처리를 시작한다. 중간에 네트워크가 끊긴다. 클라이언트는 최종 응답을 못 받았으므로 새 요청 ID로 다시 보낸다. 서버는 앞 요청을 이미 커밋했을 수도 있고 아닐 수도 있다. 프로토콜은 여기서 아무것도 보장하지 않는다.

예전에는 재개 메커니즘이 이 구멍을 부분적으로 덮었다. 이제는 도구를 만든 쪽이 직접 덮어야 한다. 정석은 세 가지다.

  • 부작용이 있는 도구에 멱등성 키를 인자로 받는다. 클라이언트가 같은 논리적 시도에 같은 키를 붙이게 하고, 서버는 키 단위로 결과를 기록해 두 번째 호출에는 저장된 결과를 돌려준다. 요청 ID는 재시도마다 바뀌므로 멱등성 키로 쓸 수 없다.
  • 취소를 완료로 착각하지 않는다. HTTP에서는 클라이언트가 스트림을 닫는 것이 취소 신호이므로, 서버는 그 시점에 작업을 가능한 한 빨리 멈추고 이후 메시지를 보내지 않아야 한다. 문제는 이미 외부 시스템에 나간 부작용은 취소되지 않는다는 점이다. 취소 처리 경로에 보상 트랜잭션이 필요한지 도구마다 판단해야 한다.
  • 긴 작업은 스트림에 매달지 않는다. 응답 스트림이 끊기면 잃는 구조이므로, 몇 분 단위 작업이라면 즉시 핸들을 돌려주고 상태를 따로 조회하게 만드는 편이 낫다. Tasks 확장이 정확히 이 형태를 표준화한 것이다.
  • 재시도 폭주를 클라이언트에만 맡기지 않는다. 스트림 단절은 대개 인프라 사건이라 여러 클라이언트에 동시에 발생한다. 재시도가 한꺼번에 몰릴 것을 전제하고 서버 쪽 레이트리밋과 백오프 유도를 준비해 둔다.

정리하면 이렇다. 무상태는 서버를 단순하게 만들지만 도구를 단순하게 만들지는 않는다. 프로토콜이 덮어 주던 몫이 도구 구현 쪽으로 내려왔고, 그 몫은 대부분 부작용이 있는 도구에 집중된다.

9. 인증·인가가 요청 단위로 내려올 때

세션이 있던 시절의 인증은 심리적으로 「접속」에 가까웠다. 한 번 통과하면 그 연결은 인증된 것으로 취급됐다. 무상태에서는 그런 자리가 없다. HTTP 전송에서 권한 부여 헤더는 클라이언트에서 서버로 가는 모든 요청에 포함되어야 한다. 토큰을 URI 질의 문자열에 넣는 것은 금지된다.

서버 쪽 의무도 요청마다 반복된다. MCP 서버는 OAuth 2.1 리소스 서버로서 토큰을 검증하고, 그 토큰이 자기 자신을 수신자로 발급된 것인지를 확인해야 한다. 다른 곳에 쓰라고 발급된 토큰을 받아서 통과시키거나 다른 서비스로 전달하는 것은 금지된다. 이 규칙 하나가 혼동된 대리인 공격의 상당 부분을 막는다.

  • 실패 지점이 넓어진다. 예전에는 연결 시작 때 한 번 나던 인증 오류가 이제 임의의 호출에서 난다. 토큰 만료가 작업 도중에 터질 수 있다는 뜻이므로, 클라이언트는 401을 만나면 갱신 후 재시도하는 경로를 갖춰야 한다.
  • 권한 부족은 별도로 다룬다. 토큰은 유효한데 범위가 모자라면 서버가 403과 함께 필요한 범위를 응답 헤더로 알려 준다. 클라이언트는 기존 범위와 새 범위의 합집합으로 재인가를 받아야 한다. 새 범위만 요청하면 이미 있던 권한을 잃는다.
  • 재인가 왕복은 한 번에 끝낸다. 명세는 서버가 한 작업에 필요한 범위를 한 번의 도전에 모아서 내보내도록 권한다. 부족한 범위를 하나씩 알려 주면 사용자가 동의 화면을 여러 번 보게 된다.
  • 토큰 대상은 반드시 지정한다. 클라이언트는 인가 요청과 토큰 요청 양쪽에 대상 리소스를 명시해야 하고, 그 값은 MCP 서버의 정규 URI여야 한다. 인가 서버가 이 파라미터를 지원하는지와 무관하게 보내라는 것이 요구사항이다.
  • stdio는 이 규격 밖이다. stdio 전송 구현은 이 인가 명세를 따르지 않고 환경에서 자격증명을 가져온다. 즉 로컬 서버의 권한 경계는 여전히 프로세스를 띄운 사용자 계정이다.

운영에서 실제 부담은 검증 비용이다. 요청마다 토큰을 확인해야 하는데 매번 인가 서버를 때릴 수는 없다. 서명 검증으로 끝나는 형식이면 공개 키를 캐시하면 되지만, 불투명 토큰이라 조회가 필요하다면 그 조회 계층이 새 병목이자 단일 장애점이 된다 — 세션 저장소를 없앴더니 토큰 조회 캐시가 그 자리를 물려받는 형국을 피하려면 처음부터 자체 검증 가능한 토큰을 쓰는 편이 낫다.

10. 관측 - 무엇을 남겨야 재현되는가

무상태로 옮기면 디버깅에서 사라지는 것이 하나 있다. 세션 ID라는 공짜 상관 키다. 예전에는 로그를 세션 ID로 묶으면 한 사용자의 흐름이 통째로 나왔다. 이제 그런 축은 프로토콜이 주지 않는다.

대신 명세가 마련해 둔 자리는 분산 추적이다. 추적 문맥을 _meta에 담아 전파하는 규약이 문서화됐고, 로깅 기능 자체는 폐기 예정으로 분류되면서 이관 경로로 stdio의 표준 오류 출력과 OpenTelemetry가 제시됐다. 프로토콜이 로그를 나르던 시대가 끝나고 관측은 일반 관측 스택의 일이 됐다는 선언에 가깝다. 재현 가능한 로그를 남기려면 아래 축을 한 줄에 모으는 것이 실용적이다. 필드 이름은 명세가 정한 것이 아니라 이 정도 축을 남기라는 뜻으로 보면 된다.

ts=2026-08-16T09:14:22Z  instance=mcp-7d9c-4kqp
mcp.version=2026-07-28   mcp.method=tools/call   mcp.name=run_query
req.id=1                 result.type=complete    dur_ms=812
trace=00-4bf92f...-00f067aa0ba902b7-01
auth.sub=u_8391          tenant=acme             scope=files:read
retry.key=6f1c9a2e       stream=closed_by_client
  • 프로토콜 버전을 반드시 남긴다. 이중 세대 서버라면 같은 엔드포인트에 두 종류의 트래픽이 섞여 들어온다. 버전 축이 없으면 구세대 경로에서만 나는 버그를 영영 못 가른다.
  • 메서드와 대상 이름을 헤더에서 뽑아 남긴다. 게이트웨이 접근 로그에도 같은 값을 남겨 두면 본문 없이도 애플리케이션 로그와 대조된다.
  • 결과 유형을 남긴다. 입력 요청으로 끝난 응답과 완료된 응답을 구분하지 않으면 MRTR 왕복이 실패로 집계되거나, 반대로 무한 왕복이 정상으로 보인다.
  • 스트림 종료 사유를 구분한다. 클라이언트가 닫았는지, 서버가 닫았는지, 중간 장비가 끊었는지는 완전히 다른 사건이다. 취소와 장애가 같은 지표에 섞이면 배포 영향을 측정할 수 없다.
  • 재시도를 묶을 키를 애플리케이션이 만든다. 요청 ID는 재시도마다 바뀌므로 그것만으로는 한 번의 논리적 시도를 복원할 수 없다. 멱등성 키나 추적 ID가 그 역할을 맡아야 한다.

지표에서 새로 볼 것은 둘이다. 스트림 조기 종료율은 배포·프록시 타임아웃·클라이언트 취소가 섞이므로 위 사유 구분과 함께 봐야 하고, MRTR 왕복 횟수 분포는 왕복이 늘수록 페이로드가 커지므로 비용 지표와 직결된다.

  • 폐기 예정으로 분류된 기능들이 실제로 어느 개정판에서 제거되는지는 정해져 있지 않다. 정책이 보장하는 것은 최소 12개월의 유예 창구이고, 신속 제거 예외에 해당하면 최소 90일이다.
  • 무상태 전환의 실측 효과 — 인스턴스당 처리량, 꼬리 지연, 비용 변화 — 를 담은 공개 벤치마크는 찾지 못했다. 이 글의 운영 서술은 명세가 요구하거나 허용하는 동작에서 도출한 것이지 측정치가 아니다.

자주 묻는 질문(FAQ)

MCP가 무상태가 되면 결국 REST API와 무엇이 다른가?

달라진 것은 연결 모델이지 프로토콜의 존재 이유가 아니다. MCP가 표준화한 것은 통신 방식이 아니라 도구·리소스·프롬프트의 서술 형식이다. 어떤 도구가 있고 입력 스키마가 무엇인지를 아무 서버에나 같은 방법으로 물어볼 수 있다는 점은 그대로다. 이 개정판은 그 위에 얹혀 있던 연결 상태를 걷어냈을 뿐이다. MCP의 가치 논쟁 자체는 MCP는 죽었는가? - Model Context Protocol의 한계와 2026 AI 에이전트 통합의 미래에서 따로 다뤘다.

기존 MCP 서버를 당장 고쳐야 하나?

당장은 아니다. 명세는 구세대 핸드셰이크 방식과 신세대 요청 단위 방식을 모두 지원하는 이중 세대 구현을 허용한다. 다만 조합에 따라 실패가 확정되는 칸이 있다 — 신세대 클라이언트가 구세대 전용 서버에 붙거나 그 반대인 경우다. 그래서 실무 순서는 서버를 이중 세대로 만들어 두고 클라이언트 채택을 보면서 구세대 경로를 걷어내는 것이다.

세션이 없어졌는데 여러 단계에 걸친 작업은 어떻게 유지하나?

상태를 없애라는 뜻이 아니라 상태를 프로토콜 밖으로 내보내라는 뜻이다. 호출 사이에 상태가 필요하면 서버가 발급한 명시적 핸들을 평범한 도구 인자로 주고받는다. 보관처는 세션 객체가 아니라 공유 저장소이고, 수명과 정리 정책은 서버 설계자가 정한다.

로드밸런서의 스티키 세션 설정을 지워도 되나?

신세대만 상대한다면 요청 단위 라우팅이 전제라 고정이 필요 없다. 두 가지만 먼저 보라. 구세대 클라이언트를 아직 받고 있다면 그 경로는 여전히 연결에 매인 세션을 쓴다. 그리고 장수 알림 스트림은 여전히 한 인스턴스에 열린 연결이며 재개되지 않는다. 세션 고정을 지우는 것과 무중단 스트림을 기대하는 것은 별개 문제다.

무상태가 되면 인증은 무엇이 달라지나?

인증을 한 번 하고 연결에 매어 두는 자리가 사라졌다. HTTP 전송에서 권한 부여 헤더는 모든 요청에 실려야 하고, 서버는 자기 자신을 수신자로 발급받은 토큰인지 매번 확인해야 한다. 실무에서 바뀌는 지점은 검증 비용과 실패 지점이다 — 연결 시작 때 한 번 나던 인증 오류가 이제 아무 호출에서나 나므로, 만료와 권한 부족을 구분해 다루는 재시도 경로가 클라이언트에 필요하다.

결론: 오늘 판단할 세 가지

이 개정판을 한 문장으로 줄이면 「연결을 신뢰 단위로 쓰던 관행의 종료」다. 그 관행은 편했지만 요청을 특정 인스턴스에 묶었고, 그 묶임이 배포·확장·장애 대응의 난이도를 결정했다. 매듭이 풀린 자리에는 인프라가 가져가는 이득과 도구 구현으로 내려온 책임이 함께 남는다.

  • 내 서버가 연결에 무엇을 얹고 있는지 목록부터 만든다. 이관 여부를 정하기 전에 발견이 먼저다. 특히 연결마다 다른 도구 목록을 내주고 있다면 그건 현행 개정판에서 성립하지 않는 설계다.
  • 부작용 있는 도구에 멱등성 키를 넣는다. 재개가 사라졌으므로 재시도는 늘어난다. 이건 개정판 채택 여부와 무관하게 지금 넣어도 손해가 없다.
  • 관측 축을 버전·메서드·결과 유형·스트림 종료 사유로 재정비한다. 세션 ID가 하던 상관 작업을 대신할 축을 미리 만들어 두지 않으면, 이관 직후의 장애를 재현할 수 없다.

남은 판단은 시점이다. 서버를 이중 세대로 만드는 비용과, 구세대로 버티다 클라이언트가 먼저 넘어갔을 때의 비용을 비교하면 된다. 폐기 예정 기능에는 최소 12개월의 유예가 걸려 있으니 급하지는 않다. 다만 세션 의존을 걷어내는 작업 자체는 개정판과 무관하게 이득이라는 점은 분명하다.
