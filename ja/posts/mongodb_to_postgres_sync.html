きっかけ - 難しかったのは同期ではなくマッピングだった

2026年9月初め、韓国の開発者コミュニティにMongoDB コレクションを PostgreSQL へ複製して同期するという記事が紹介された。原文は VisuaLeaf というチームのブログ記事で、診療来院記録を収めたコレクション一つを PostgreSQL のテーブルへ移し、合わせ続ける過程を記録している。著者が残した一文がこの記事の出発点だ。同期そのものより、MongoDB の文書構造を PostgreSQL のテーブルに合わせてマッピングする過程のほうが厄介だったというものである。

原文の性格を先に述べておくほうが誠実だろう。これは自社ツールを紹介する記事である。著者は VisuaLeaf Mongo Sync を使い、その理由として、元コレクションと対象テーブル、フィールドマッピング、同期状態を視覚的に構成したかったことを挙げている。ツールを勧める記事で最も信頼できる部分は、たいてい成功談ではなく詰まった場所の記録であり、この記事にはそれが二つ残っている。

一つ目は、対象テーブルにキー列がないため冪等に upsert できないというエラーだった。著者は MongoDB の _id を mongo_id という TEXT 列で受け、そこに主キーを掛けて解決している。二つ目は、元の labResults と対象の lab_results という名前の食い違いで、列が見つからないというエラーだった。フィールドを一つずつ明示的にマッピングするか、PostgreSQL 側で引用符を使ってキャメルケースをそのまま用いるのが解法である。

二つのエラーは見た目の大きさこそ似ているが、性質がまったく違う。後者は設定の誤りだ。一度直せば終わる。前者は違う。それは誤りではなく構造が要求したものであり、この記事で後に出てくる制約のほとんどがその一点につながっている。ここから先の半分は、なぜそのエラーが必然だったのかの説明である。

原文にないものも明確にしておく。データ量、文書数、処理速度、遅延といった数値は一つもない。初回の全複製とその後の変更反映をどんな順序でつなぐのか、その継ぎ目に生じる空白をどう埋めるのかも書かれていない。したがって原文の結果を根拠にこの方式が一般に速い、あるいは安全だと広げてはならない。原文が示したのは、一つのコレクション、一つのツール、一つのシナリオである。

二つの問題を切り分ける - 複製と整合は別の要求をする

一度移す仕事と合わせ続ける仕事は、名前でつながっているだけで要求するものが違う。最大の差は失敗したとき何ができるかにある。前者は失敗すれば最初からやり直せばいい。対象テーブルを空にして詰め直せば済み、その過程は定義上冪等だ。後者はそうはいかない。どこまで反映したかを知っていなければならず、その地点がまだ有効でなければならず、同じイベントが二度来ても結果が同じでなければならない。

検討すべきこと一度の複製継続的な同期
失敗からの復旧全体を再実行。副作用なし再開地点が必要で、その地点は失効しうる
重複一度しか読まないので発生しない再開区間で必然的に発生。取り込みが冪等でなければならない
順序無関係。最終状態さえ合えばよい同じ文書への更新は順序が入れ替わると状態が狂う
削除元になければ対象にもない。自動的に合う消えたものを知る別の仕掛けが要る
スキーマ変更次回実行時に新しいマッピングで作り直せばよい稼働中にマッピングを変える手順が別に要る
元データへの負荷実行時に集中。予測できる常時。開いたカーソルがサーバー資源を使い続ける
費用が膨らむ軸データ量運用期間と変更率

最後の行が実務では最も重い。一度の複製の費用はデータが大きくなれば大きくなり、それで終わる。同期の費用は時が経つほど積み上がる。トークンが失効し、コレクションが削除され、上流にフィールドが増え、やがてストリームが静かに止まっていたのに誰も気づかなかった三日間が生まれる。以降で扱うのはすべてこの軸の上の話だ。

片側でしか書き込みが起きないという前提も押さえておく価値がある。ここで扱うのは MongoDB が元で PostgreSQL が写しである一方向の構成だ。両側で書き込みが起きる構成は、衝突解決と因果関係の追跡が乗るまったく別の問題であり、その骨格はデータを手元に持つことの代償で別途扱っている。

スキーマのない文書がテーブルに入るとき強制される五つ

文書データベースでは先送りできた決定がある。関係テーブルはそれを先送りさせてくれない。列を作るには型を決めねばならず、型を決めるにはそのフィールドが何であるかを決めねばならないからだ。だからマッピング作業の実体は変換ではなく、先送りしてきた決定を一度に清算する仕事である。強制される決定は大きく五つだ。

  • 識別子 - _id をどんな型の列で受けるか。これが主キーにならなければ以降のすべてが崩れる
  • 型の推論 - 同じフィールドが文書ごとに違う型のとき、どちらに合わせるか
  • 入れ子 - 文書の中の文書を列に展開するか、一塊のまま置くか
  • 配列 - 子テーブルへ正規化するか、配列列や JSONB のまま置くか
  • 不在 - フィールドがないことと、フィールドが null であることを区別して保存するか

それぞれを順に見ていく。共通点は、どの選択も無料ではないということだ。選択ごとに、いま楽になることと後で難しくなることが対になっている。

_id を何として受けるか

最初に決めねばならず、最も戻しにくい決定である。MongoDB の既定の _id は ObjectId であり、公式文書によればそれは12バイトで構成される。先頭4バイトは Unix エポック基準の秒単位で表した生成時刻、続く5バイトはクライアント側プロセスごとに一度生成される乱数値、最後の3バイトは乱数から始まって増加するカウンタだ。文書は、タイムスタンプとカウンタについては上位バイトが先に来ると記し、これは他の BSON 値と逆であるとしている。

ここに実務上さらに重い記述が一つある。文書は、ObjectId の値が時間とともに増加するはずではあるが必ずしも単調ではないと明記している。理由は二つ挙げられている。時間解像度が1秒しかないため同じ秒に作られた値どうしには順序の保証がなく、値を作る主体がクライアントなのでシステム時計が互いに違いうる、というものだ。つまり _id を変更検知用のウォーターマークとして使う設計は最初から壊れている。この話はポーリングを扱う節でもう一度出てくる。

受ける側の選択肢は事実上二つだ。原文のように24文字の16進文字列へほどいて text 主キーで受けるか、12バイトをそのまま bytea で受けるか。前者は人が読めてどんな道具でも扱いやすいが、保存量が二倍になりインデックスもその分大きくなる。後者は元のサイズを保つが、問い合わせ結果を目で読めず道具の対応も薄い。多くのチームが前者を選ぶ理由は性能ではなく、運用中に人がその値を見る場面が多いからである。

どちらを選ぶにせよ、譲れない条件が一つある。その列が主キーでなければならない。原文がぶつかった最初のエラーがまさにこの地点だった。キーがなければ冪等な upsert ができず、冪等な upsert ができなければ再開区間の重複を吸収できず、そうなるとそもそも再開が不可能になる。加えて、後で見る削除イベントは文書の中身を載せてこないので、_id から導かれたキーがなければ何を消すべきか特定する手段そのものがない。

付け加えると、乱数性の高い値を主キーにする構成がインデックスに何をするかは別の主題だ。ObjectId は先頭が時刻なので完全な乱数キーよりは事情がよいが、その軸の一般論はUUIDを主キーにすべきでない理由にまとめてある。

同じフィールドが文書ごとに違う型のとき

文書データベースで最もよくあり、最も遅く発見される問題である。コレクションを作った最初の月は amount がすべて整数だったのに、ある時点から文字列が混ざり、どこかでは NumberDecimal で入ってきて、一部の文書にはそのフィールド自体がない。MongoDB はこれを止めない。だから取り込み処理が、その事実を初めて教えてくれる存在になる。

// 同じコレクション、同じフィールド名。型が文書ごとに違う。
db.visits.insertMany([
  { visitId: "VIS-1", amount: 12000,                  visitDate: ISODate("2026-09-01T09:00:00Z") },
  { visitId: "VIS-2", amount: "12,000",               visitDate: "2026-09-02" },
  { visitId: "VIS-3", amount: NumberDecimal("12000"), visitDate: ISODate("2026-09-03T09:00:00Z") },
  { visitId: "VIS-4",                                 visitDate: null },
  { visitId: "VIS-5", amount: null,                   visitDate: ISODate("2026-09-05T09:00:00Z") }
]);

// VIS-4 には amount フィールド自体がなく、VIS-5 にはあるが値が null だ。
// この二つを一つの列で受けると、両者の区別は消える。

選択肢は三つあり、それぞれ違うものを諦める。第一に、最も広い型で受ける。すべて text に入れれば取り込みは決して止まらない。代わりに整列と範囲問い合わせが文字列の規則に従い、"9000" が "12000" より大きくなる。第二に、厳密な型で受け、外れたら失敗させる。データ品質は守られるが、上流に値が一つ誤って入った瞬間に同期全体が止まる。第三に、正常な値は型付きの列へ、例外は別の列や JSONB へ流す。実装は増えるが、稼働中の停止と静かな損失を同時に避けられる。

ここに BSON 側の事情がもう一つ乗る。公式文書によれば BSON の Date は Unix エポック基準のミリ秒単位の64ビット整数であり、符号付きなので1970年より前も表せる。したがって timestamptz で受けること自体は自然だが、元データにミリ秒より細かい精度は最初から存在しなかったという事実は覚えておく値打ちがある。受け側の型がより精密でも、なかった情報が生まれるわけではない。

数値も同様だ。BSON は Double、32ビット整数、64ビット整数、Decimal128 を区別する。文書は Decimal128 が有効桁34桁、指数範囲は -6143 から +6144 までだと記している。金額を扱うコレクションが Decimal128 を使っているなら受け側の列は numeric でなければならず、double precision で受けた瞬間にその精度のために払った費用が消える。

入れ子の文書 - 平坦化と JSONB のあいだ

原文の選択は明確だった。単純なフィールドは通常の列に、入れ子のオブジェクトと配列は JSONB に格納した。visitId、status、visitDate はそれぞれ text、text、timestamptz の列になり、patient、doctor、symptoms、prescriptions、invoice、labResults のようなものはすべて JSONB 列になった。妥当な既定値だが、この選択が何を買い何を売るのかは明確にしておく必要がある。

平坦化が有利な場合

patient.fullName を patient_full_name 列に展開すれば、その列に制約を掛けられる。NOT NULL、検査制約、一意性、外部キーがすべて可能になる。プランナが使う統計も列単位で採られるので選択率の推定が正確になり、平凡な B-tree インデックスで足りるようになる。値が何であるか定まっていて、それで結合したり絞り込んだりする計画があるなら平坦化が答えだ。

代償はスキーマが元データを追いかけねばならない点である。MongoDB 側で入れ子の文書にフィールドを一つ足すのはデプロイなしに起きることだが、受け側ではそのたびに ALTER TABLE とマッピング修正がついてくる。元データのチームと写しのチームが別なら、この差はただちに運用上の負債になる。

JSONB が有利な場合

PostgreSQL の文書は json と jsonb の差をはっきり記している。json は入力テキストの正確な複製を格納するので処理関数が実行のたびに再解析しなければならず、jsonb は分解された二進形式で格納されるため入力時の変換オーバーヘッドで少し遅い代わりに、再解析が不要なので処理が著しく速い。文書の勧告は明示的だ。キー順序に関する旧来の前提のような特殊な事情がない限り、ほとんどのアプリケーションは JSON データを jsonb として格納するほうを選ぶべきである。

代わりに jsonb が捨てるものがある。文書は、jsonb が空白を保存せず、オブジェクトキーの順序を保存せず、重複キーを残さずに最後の値だけを保持すると記す。json はその三つをすべて保存する。元の文書のフィールド順序やバイト単位の原形が後で必要になりうるなら、この差は決定的だ。

インデックスが jsonb の最大の利点だという記述も文書にある。ただし演算子クラスの選択が後に影響する。既定の GIN 演算子クラスはキー存在演算子 ?、?|、?& と包含演算子 @>、jsonpath 一致演算子 @?、@@ をサポートする。既定でないクラスの jsonb_path_ops はキー存在演算子をサポートせず、@>、@?、@@ だけを扱う。代わりに文書は、jsonb_path_ops のインデックスが同じデータに対してたいていずっと小さく、特に頻出するキーを含む問い合わせで検索の特異度が優れると記している。

この選択が後で何を塞ぐのかは八番目の節でまた出てくる。キーが存在するかを問う問い合わせが必要になった瞬間、小さいインデックスを選んだという理由でその問いにインデックスで答えられなくなるからだ。

CREATE TABLE mongo_visits_sync (
    mongo_id     text PRIMARY KEY,        -- ObjectId を24文字の16進文字列として受ける
    visit_id     text,
    status       text,
    visit_date   timestamptz,
    -- フィールド構成が可変な入れ子の文書と配列は丸ごと jsonb に置く
    patient      jsonb,
    lab_results  jsonb,
    -- 元の文書にはない、同期そのものの状態を持つ列
    src_ts       timestamptz NOT NULL,
    deleted_at   timestamptz
);

-- キー存在演算子を使うには既定の演算子クラスでなければならない
CREATE INDEX ON mongo_visits_sync USING gin (patient);

-- 包含と jsonpath だけを使うなら、こちらのインデックスはずっと小さい
CREATE INDEX ON mongo_visits_sync USING gin (lab_results jsonb_path_ops);

このテーブル定義に、元データにはない列が二つ入っている点に目を留めたい。src_ts と deleted_at は文書の中身ではなく、同期という手続きそのものの状態である。こうした列が必要になるという事実が、複製と同期が別の問題であることの最も目に見える証拠だ。

配列 - 子テーブルと一つの列のあいだ

配列は入れ子より選択肢が一つ多く、その分だけ分岐が広い。スカラーの配列か文書の配列かで答えが分かれる。

タグの一覧のような文字列の配列なら PostgreSQL の配列型 text[] が自然だ。配列演算子が使えて GIN インデックスも掛かる。ただし要素ごとに付くメタデータが後から生じると、配列列にはそれを受ける場所がない。タグに登録時刻を付けようという要望が来た瞬間、構造を作り替えることになる。

文書の配列なら、問いは一つに圧縮される。その要素は独立に問い合わせる対象か。処方項目ごとの集計が要り、特定の薬品が入った来院記録を探す必要があり、項目単位で結合する計画があるなら、子テーブルへ正規化するのが正解だ。そうすれば本来の関係型の道具がすべて戻ってくる。

その代償は同期側で出る。元データで文書が一つ変わったというイベント一つが、受け側では子行の複数の削除と挿入に翻訳されねばならない。その複数の文が一つのトランザクションの中で原子的に終わらねばならず、途中で失敗すれば親行と子行の状態が食い違ったまま残る。一行の upsert 一回で済んでいた仕事が手続きになるのだ。

要素を丸ごとしか読み書きしないなら JSONB 一列のほうがよい。一文書 = 一行という対応が保たれるので、取り込みロジックは単純な upsert のまま残る。代わりに要素数を数えたり要素で並べ替えたりするたびに展開の費用を払う。判断の基準はデータの形ではなく、そのデータに投げる問いの形である。

フィールドの不在と NULL は同じではない

最も静かに情報が失われる場所だ。MongoDB の文書であるフィールドは三つの状態を取りうる。フィールドがそもそもないか、あるが値がnullか、値があるかである。この三つは意味が違う。アンケート回答なら、それぞれ訊いていない、訊いたが答えなかった、答えたに当たる。

これを通常の列に平坦化すると、前の二つの状態がまったく同じ SQL NULL になる。戻す方法はない。PostgreSQL の文書は JSON 原始型の対応表で、JSON の null に対応する PostgreSQL 型の欄にSQL NULL は別の概念であると記している。二つの世界が同じ語で違うものを指しているという警告だ。

三つの状態を守るには値を JSONB の中に残すしかない。そうすればキーが存在するかを問うことで不在と null を分けられる。ここで前節のインデックス選択が足を引っ張る。キー存在を問う ? 演算子は既定の GIN 演算子クラスでのみサポートされ、jsonb_path_ops ではサポートされない。インデックスが小さいという理由で jsonb_path_ops を選んでいたなら、三つの状態を保存しておきながらそれをインデックスで問えない状態になる。

同系統の落とし穴がもう二つある。PostgreSQL の文書は、jsonb が PostgreSQL の numeric の範囲を外れる数値を拒否するのに対し json はそうしないと記す。そして JSON 原始型の対応表で、数値については NaN と無限大は許されないと、文字列については \u0000 は許されず、データベースエンコーディングにない文字を表すユニコードエスケープも同様であると記している。

BSON の Double は NaN と無限大を持てる。計算誤りでそうした値が入った文書が一つコレクションに紛れていると、その文書はJSONB 列に入れない。文字列の中のヌル文字も同じだ。この二つは、初回の全複製では大人しく通り過ぎ、ある日一件の変更イベントで初めて破裂する種類の問題である。マッピング段階でそうした値の行き先を決めておかなければ、その日の同期は止まったまま発見を待つことになる。

変更をどう捕まえるか - ポーリングと変更ストリーム

ここから先は同期固有の問題だ。最初の問いは単純である。何が変わったかをどうやって知るのか。

ポーリングが実際に取りこぼすもの

まず思い浮かぶ方法は、定期的に問い合わせを投げて最近のものだけ取ってくることだ。実装が易しく、特別なデプロイ構成も要らない。しかしこの方式には三つの穴があり、三つとも静かである。

第一に、ウォーターマークに使える列が見当たらない。_id を使えば、先に見たとおり ObjectId が単調でないという問題に当たる。時間解像度が1秒でクライアントの時計が互いに違うため、すでに処理した地点より小さい ObjectId を持つ文書が後から挿入されうる。その文書は永遠に飛ばされる。updatedAt のようなアプリケーションのフィールドを使っても、そのフィールドを更新しない書き込み経路が一つでもあれば同じことが起きる。

第二に、削除が見えない。ポーリングは、いま存在する文書を条件で絞って取ってくる方式だ。消えた文書はどんな条件にも掛からない。だから対象テーブルには元データにない行が残り続け、積み上がっていく。

第三に、遅延と負荷が取引関係にある。周期を短くすれば元データに問い合わせが刺さり続け、長くすれば写しが古びる。そしてその周期の中で何度も変わった文書は最後の状態だけ見える。中間状態を根拠に何かを判断せねばならない用途なら、ポーリングはそもそも道具ではない。

変更ストリームが要求するもの

MongoDB の変更ストリームはこれらの穴を埋めるが、要件がある。マニュアルは変更ストリームがレプリカセットとシャードクラスタで利用できると記す。そのデプロイは WiredTiger ストレージエンジンを使い、レプリカセットプロトコルバージョン 1 でなければならない。保存時暗号化を使うデプロイでも動作し、多数決リードコンサーンのサポート有無とは無関係だと明示されている。単独サーバー構成ならこの経路そのものがない。

運用面の但し書きもマニュアルに複数あり、どれも後から知ると高くつくものばかりだ。変更ストリームはインデックスを使えず、MongoDB は oplog コレクションへのインデックス作成をサポートしないので、特定の対象を狙った変更ストリームを多く開くのは避けよと文書は勧告している。コレクションごとにストリームを一つずつ付ける設計が、コレクション数に比例してサーバーを削っていくという意味だ。

アービタメンバーのあるレプリカセットでは、データを持つメンバーが足りず操作を多数決コミットできない状況になると変更ストリームが待機状態にとどまりうるとも書かれている。障害時にストリームがエラーを出す代わりに静かになるのだ。シャードクラスタでは、活動のほとんどないコールドシャードが応答時間を悪化させる。変更の全順序を保証するには mongos がそのシャードにも問い合わせねばならないからである。逆に活動の多いシャードコレクションでは mongos が全シャードの変更に追いつけないことがあり、文書は $match で必要な操作だけを絞る通知フィルタを勧めている。

再開地点 - トークンが要求するもの

変更ストリームを選んだなら、次の問いは一つだ。プロセスが死んで生き返ったら、どこから読み直すのか。

マニュアルによれば、変更イベント通知は再開トークンを _id フィールドに載せて届く。トークンは二種類ある。特定の変更イベントを指すイベントトークンと、変更イベントがなくてもクラスタ時刻が進んだことを示すためにサーバーが定期的に生成するハイウォーターマークトークンだ。二つ目の種類があるという事実は実務でかなり重い。変更が稀なコレクションでも、保存してある再開地点を前へ進め続けられるという意味だからである。

再開の方法は三つあり、それぞれ違う状況のためのものだ。resumeAfter は特定のイベントの次から再開する。startAfter はその地点以降で新しいストリームを作る。startAtOperationTime は特定の時点でカーソルを開くが、文書はその時点が過去であればoplog の時間範囲の中になければならないと記す。

前二者の差は事故のときに露わになる。文書は無効化イベントがストリームを閉じた後は resumeAfter で再開できないと明言し、その場合は startAfter で新しいストリームを始めよと案内している。無効化イベントの例としてはコレクションの削除や名前変更が挙げられている。カーソルが閉じる条件はほかにも明示的な終了、接続の切断やタイムアウトがあり、シャードクラスタではシャードの除去が開いていたカーソルを閉じうるうえ、そうして閉じたカーソルは完全に再開可能とは限らないと記されている。

トークンが失効する条件も明確だ。文書はそのトークンに対応する操作を見つけられるだけの履歴が oplog に残っていなければならないと記す。したがって再開可能な時間の上限はoplog ウィンドウであり、これはデータベースの設定であって同期ツールの設定ではない。運用勧告の文書は、アップグレードや大きな障害のように相当のダウンタイムが見込まれるなら見込みのダウンタイムより長く操作が保持されるよう oplog のサイズを大きくすることを検討せよと記している。同期プロセスを数日止めておく計画があるなら、その一文がその日の唯一の防衛線になる。

// 保存してある再開地点を読む。なければ今から開く。
const saved = await loadResumeToken();

const options = { fullDocument: "updateLookup" };
if (saved) options.resumeAfter = saved;   // 無効化イベントの後はこれが失敗する

const stream = db.collection("visits").watch([], options);

for await (const event of stream) {
  // すべての変更イベントの _id がそのまま再開トークンだ
  await applyToPostgres(event);           // まず反映して
  await saveResumeToken(event._id);       // その後に地点を書く
  // この順序を逆にするとイベントを失う。この順序を守ると重複が生じる。
  // 失うほうは復旧できず、重複は冪等性で吸収できるので、この順序が正しい。
}

注釈の最後の二行がこの節の結論だ。反映とトークン保存は異なるシステムへの二回の書き込みであり、二つを一つのトランザクションにまとめる方法はない。だからどちらかを先にせねばならず、どちらを選んでも事故が起きる。先にトークンを書けば取りこぼし、先に反映すれば重複だ。復旧できるのは重複だけである。

少なくとも一回 - 冪等な取り込みが強制される理由

前節の選択がそのまま配送保証の等級を決める。反映を先にすると決めたなら、このパイプラインは少なくとも一回だ。同じ変更が二度以上届きうるし、それは欠陥ではなく設計された性質である。すると取り込み側が引き受けるべきものが定まる。

  • 同じイベントを二度適用しても結果が同じでなければならない - 状態を足す演算ではなく上書きする演算として表現せよ、という意味だ
  • キーがなければならない - 何を上書きするか特定できなければ冪等性は成立しない。原文がぶつかった最初のエラーがこれだった
  • 遅れて届いた古いイベントが新しい状態を覆ってはならない - 順序保証が崩れうる区間ではバージョン比較が必要になる

PostgreSQL でこれを表現する道具が ON CONFLICT だ。文書の定義は簡潔である。ON CONFLICT DO NOTHING は代替動作として行の挿入を単に回避し、ON CONFLICT DO UPDATE は挿入しようとした行と競合する既存行を更新する。競合対象は一意インデックスの推論で指定するか、ON CONSTRAINT で制約名を直接書く。

ここに見落としやすい規定がある。文書はDO NOTHING では競合対象の指定が任意だが DO UPDATE では必ず指定しなければならないと記す。そして更新に使う値はexcluded という特別なテーブルで参照する。文書の表現では、SET と WHERE 句が既存行にはテーブル名か別名で、挿入しようとした行には excluded でアクセスする。

最も高くつく落とし穴は最後にある。文書は ON CONFLICT DO UPDATE を伴う INSERT を決定的な文と呼び、この命令が単一の既存行に二度以上作用することは許されず、その状況が生じるとカーディナリティ違反エラーが送出されると記す。なぜこれが重いのか。変更ストリームをバッチにまとめて取り込むと、同じ文書に対するイベントが一つのバッチに複数入ることが日常的に起きるからだ。そのまま一つの文に入れればバッチ全体が失敗する。だから取り込みの直前に、キーごとに最新の一件だけを残す整理が必要になる。

-- 一つのバッチに同じ mongo_id が二度入るとカーディナリティ違反になる。
-- だから取り込みの直前に、キーごとに最新の一件だけを残す。
INSERT INTO mongo_visits_sync AS t (mongo_id, visit_id, status, visit_date, patient, src_ts)
SELECT DISTINCT ON (mongo_id)
       mongo_id, visit_id, status, visit_date, patient, src_ts
FROM   staging_changes
ORDER  BY mongo_id, src_ts DESC
ON CONFLICT (mongo_id) DO UPDATE
SET    visit_id   = EXCLUDED.visit_id,
       status     = EXCLUDED.status,
       visit_date = EXCLUDED.visit_date,
       patient    = EXCLUDED.patient,
       src_ts     = EXCLUDED.src_ts,
       deleted_at = NULL
WHERE  t.src_ts < EXCLUDED.src_ts;   -- 古いイベントが新しい状態を覆わないようにする

最後の WHERE 句が三つ目の要求を担う。既存行のバージョンが新しく届いたものより新しければ更新を飛ばす。これがなければ、再開区間で再生された古いイベントが、その間に反映された最新の状態を消してしまう。ちなみに文書は、INSERT、UPDATE、DELETE を一つの文の中で混ぜる必要があるなら MERGE を検討せよとも案内しており、ON CONFLICT より SQL 標準に近い代案だと記している。

加えて、変更ストリームが既定で更新操作におけるフィールドの差分だけを返す点も冪等性に絡む。文書全体を受け取るには fullDocument を updateLookup に設定せねばならないが、文書はこれを最新の多数決コミット済みバージョンをコレクションから読み直す別の照会だと説明している。だから但し書きが付く。更新と照会のあいだに文書が削除されたりコレクションが削除されたりすると fullDocument が欠けることがあり、そのあいだに多数決コミットされた別の操作があったなら返ってきた文書が更新時点の文書と大きく異なりうるというものだ。つまり updateLookup が与えるのはその時点の状態ではなく、いまの状態である。

この性質には明るい面もある。再生された古いイベントであっても照会は再生時点で起きるので、最終状態への収束が目的なら、むしろ自ら是正される。逆に変更の履歴をそのまま残したい用途なら updateLookup は適した道具ではない。6.0 から提供される事前イメージと事後イメージがその席のためのものであり、文書は挿入された文書に事前イメージはなく、削除された文書に事後イメージはないと記している。

サイズ制限も一つある。運用勧告の文書は、変更ストリームの応答文書が16MB の BSON 文書制限を守らねばならず、コレクションの文書サイズによっては通知文書がその限界を超えると通知が失敗しうると記す。文書全体を返すよう設定した更新操作や、限界に近い文書の挿入や置換がその例として挙げられている。6.0.9 からは $changeStreamSplitLargeEvent という集約ステージでイベントを断片に分割できる。大きな文書を扱うコレクションなら、この制限はマッピング段階で先に計算しておくほうがよい。失敗してから知るときには、すでにストリームが止まった後だ。

削除 - 消えた文書をどう知るか

同期で最も頻繁に抜け落ちる項目であり、抜けた事実が最も遅く表面化する項目でもある。挿入と更新は誤ると値がおかしくなるので目につく。削除の取りこぼしはあるべき場所にそのままある行として現れるので、誰も違和感を覚えない。

変更ストリームの削除イベントが何を載せるかはリファレンスに正確に書かれている。イベントには再開トークンである _id、oplog エントリのタイムスタンプである clusterTime、名前空間 ns、操作種別 operationType、そして documentKey が入る。文書は documentKey を当該 CRUD 操作が作成または変更した文書の _id 値を含む文書だとし、シャードコレクションではこのフィールドが完全なシャードキーも表示し、_id がすでにシャードキーの一部なら繰り返されないと記す。6.0 からはサーバーの日時である wallTime が加わる。

決定的な一文はこれだ。fullDocument は省略される。変更ストリームのカーソルが削除イベントをクライアントへ送る時点で、その文書はもはや存在しないからである。つまり削除イベントが教えてくれるのは何が消えたかという識別子だけだという意味だ。

この一文が、先のいくつもの決定を事後に正当化する。対象テーブルの主キーが _id から導かれたものでなければ、削除イベントを受け取ってもどの行を消すべきか割り出す方法がない。文書の中身で照合しようにも、その中身が届かないのだ。原文が最初にぶつかったキー列がなく冪等な upsert ができないというエラーは挿入側の問題に見えたが、実際には削除まで同時に塞いでいた。

削除前の中身が必要なら手はある。6.0 から createCollection、create、collMod でコレクションに changeStreamPreAndPostImages を有効にし、watch() で fullDocumentBeforeChange を required か whenAvailable に指定すれば、削除直前の文書を併せて受け取れる。ただし文書は二つの場合に事前イメージが使えないと記す。削除の時点でコレクションにその機能が有効化されていなかった場合と、expireAfterSeconds で定めた保持時間を過ぎて除去された場合である。つまりこの機能はあらかじめ有効にしておいた分だけ遡る。事故の後に有効化して過去を取り戻す用途には使えない。

-- 削除イベントには documentKey しか来ない。文書の中身は来ない。
-- だから受け側のキーが _id 由来でなければ、消す対象を特定できない。

-- 方法 1。論理削除。消えたという事実そのものを履歴として残す。
UPDATE mongo_visits_sync
SET    deleted_at = $2
WHERE  mongo_id = $1
  AND  deleted_at IS NULL;

-- 方法 2。物理削除。すでにない行を消してもエラーではないので、それ自体が冪等だ。
DELETE FROM mongo_visits_sync
WHERE  mongo_id = $1;

二つのどちらを選ぶかは写しの用途が決める。分析用の写しなら論理削除がたいていよい。いつ消えたかがそれ自体で事実であり、物理削除はその事実を消してしまうからだ。代わりにすべての問い合わせに deleted_at IS NULL の条件が付いて回り、それを一度落としたダッシュボードが静かに誤った数字を出す。元データとまったく同じ姿を求めるなら物理削除が正しく、このときはすでにない行を消すのがエラーでないという性質がそのまま冪等性を与えてくれる。

どちらにせよ突き合わせの手順は別に必要だ。ストリームが静かに切れていた区間、トークンが失効して最初からやり直した区間、無効化の後で新しいストリームを開いた区間では、削除イベントが丸ごと通り過ぎる。定期的に両側のキー一覧を突き合わせて対象側にだけあるキーを探し出す作業がなければ、その区間の取りこぼしは永遠に残る。

この構成を選ぶべきでないのはいつか

ここまでがこの構成の要求するものだ。今度は逆方向を見る番である。二つのデータベースを合わせ続ける費用が片方へ寄せる費用より大きくなる地点がある。

  • 写しが古くてもよい場合 - 数時間の遅延が許され、データが再取り込み可能な規模なら、定期的な全体の再取り込みが圧倒的に安い。再開トークンも冪等性も削除検知も要らない。元データにないものは新しい取り込みにもないので、削除は定義上ひとりでに合う
  • 両方を一つのトランザクションで読まねばならない場合 - 異なる二つのデータベースにまたがる原子的な読み取りは、どんな同期でも作れない。その要求が本物なら、必要なのは同期ではなく統合である
  • 両側で書き込みが起きる場合 - 一方向の写しとは難易度の違う問題へ移る。衝突解決の規則と因果関係の追跡が必要になり、そこからは道具ではなくドメイン規則が答えを決める
  • マッピングが揺れ続ける場合 - 上流のチームが文書へ自由にフィールドを足す文化なら、平坦化した列は恒久的な保守税になる。この場合は写しを JSONB 一列に置くか、そもそも写しを作らないほうがよい
  • 単独サーバーの MongoDB - レプリカセットでなければ変更ストリームがなく、残るのは先に見た穴を抱えたポーリングだけだ。この状態でリアルタイムの整合を約束すると守れない

逆に、この構成が確実に合う場所もはっきりしている。MongoDB が真実の源として残り、PostgreSQL は SQL の得意なこと、すなわち結合、ウィンドウ関数、BI ツールとの接続、臨時の集計のための読み取り専用の写しとしてのみ存在する場合だ。写しに書き込みがないという条件が、先の難しさの半分を消してくれる。写し側の Postgres を運用の観点でどう守るかはスタートアップのPostgres生存ガイドが、取り込み作業そのものを Postgres の中で再試行可能にする方法はPostgresで耐久性のあるワークフローを作るが扱っている。

まとめるとこうなる。原文の著者が同期よりマッピングが厄介だったと書いたのは半分だけ正しい。マッピングが厄介だった理由はそれが戻しにくい決定だったからであり、戻しにくい理由はそれらの決定がすべて同期が成立するための前提だったからだ。キーを何にするか、不在と null を区別するか、配列をどこに置くかは見た目こそスキーマ設計の問題だが、実際には再開と冪等性と削除検知が可能かどうかをその場で決める問題である。マッピングを先にして同期を後から付ける順序ではなく、同期が要求するものを知ったうえでマッピングをする順序が正しい。

確認できなかったこと

  • 変更ストリームの更新イベントが載せる差分の正確な構造は確認できなかった。マニュアルで確認できたのは既定で更新操作のデルタだけを返すという記述までであり、その中のフィールド名と形は別のリファレンスを開いていないので本文に書かなかった
  • PostgreSQL の numeric の正確な桁数と指数の限界は確認できなかった。確認したのは jsonb が numeric の範囲を外れる数値を拒否するという記述と、BSON Decimal128 の有効桁34桁、指数 -6143 から +6144 までである。二つの範囲の包含関係は計算していない
  • PostgreSQL の timestamp 系の内部的な時間解像度は原典で確認できなかった。本文では BSON の Date がミリ秒であるという確認済みの事実だけを根拠にした
  • oplog ウィンドウを外れた再開トークンで再開を試みたときサーバーが正確にどんなエラーを返すかは確認できなかった。マニュアルは履歴が十分でなければならないという要求だけを記し、失敗時のエラーコードはその文書にない
  • ハイウォーターマークトークンがどれくらいの頻度で生成されるのか、その周期を調整できるのかは確認できなかった。文書には定期的に生成するという記述だけがある
  • 原文が使ったツールが初回の全複製と変更ストリームをどうつなぐのかは確認できなかった。二つの区間の継ぎ目に生じる空白をどう埋めるかがこの種のツールの核心なのに、原文にその手順が書かれていない
  • 原文にはデータ量、文書数、処理速度、遅延についての数値が一つもない。したがってこの方式の性能特性については何も写していない
