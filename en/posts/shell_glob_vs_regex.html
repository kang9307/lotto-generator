Globs Are Not Regex - When the Asterisk Means Two Different Things

Feed the same pattern to ls and to grep and you get different answers. The fork, verified by running it

Sep 1, 2026 Dev & Infra

ls ab* gives you the names that start with ab. Put the same four characters into grep 'ab*' and lines with no ab in them at all come along for the ride. Not a typo, not a version problem. In those two places, * belongs to two different grammars.

The grammar that picks filenames is called globbing, or in specification language, pattern matching notation. grep, sed and awk use regular expressions. The symbol sets overlap heavily — *, ? and [...] exist on both sides — so carrying one intuition into the other territory produces a wrong result with no error attached. That is the annoying part. An error you notice. A pattern that quietly catches something else surfaces after it ships.

Every output below was copied from an actual run. Wherever the answer depends on the shell version or a shopt setting, that is called out on the spot.

All output in this article came from one machine, described in the 「Where this was run」 section below. Shell pattern behaviour tracks the shell, its version and the shopt state, so it is safer to run these once in your own environment before relying on them. Places where another shell flips the result are marked in the text.

* — 「any string」 versus 「zero or more of the previous」

Start with the symbol everyone uses most. The same ab*, fed to both sides.

# glob - the shell matches against file names
$ ls ab*
ab.txt
abb.txt

# regex - grep matches against each line
$ printf '%s\n' a.txt ab.txt abb.txt b.txt | grep 'ab*'
a.txt
ab.txt
abb.txt

Two on the glob side, three on the regex side. The extra one is a.txt, and that is the whole point. In a glob, ab* means 「a, then b, then any string」. In a regex, ab* means 「a, then b zero or more times」. Zero is allowed, so a name with no b in it qualifies.

Put plainly: the glob * is a symbol that means something on its own. The regex * is an operator that repeats whatever precedes it, and means nothing standing alone. The regex spelling equivalent to a glob * is .*. You have to say 「any single character, zero or more times」 to get the same idea.

Stripping the extensions and running it again makes the split sharper.

$ printf '%s\n' a ab abb xabz | grep 'ab*'
a
ab
abb
xabz

$ printf '%s\n' a ab abb xabz | grep -E '^ab*$'
a
ab
abb
  • Glob * = any string. The empty string counts, which is why ab* also matches ab itself
  • Regex * = zero or more of the element right before it. With nothing before it, you get a syntax error or a literal, depending on the tool
  • To say 「any string」 in a regex you write .*. . is 「any single character」 and * is 「repeat that」
  • xabz got caught not because of * but because of partial matching. That gets its own section two ahead

? and . — two ways to say one character

Both grammars have a symbol for 「any single character」, and they picked different letters for it. Globs use ?, regexes use .. And in a glob, . is just a period. It carries no special meaning at all.

# glob ? - exactly one character
$ ls ?.txt
a.txt
b.txt

# in a glob, ? also matches the dot. a dot is an ordinary character here
$ ls a?txt
a.txt

# regex . - one character here too, so non-dots match as well
$ printf '%s\n' a.txt axtxt aatxt | grep 'a.txt'
a.txt
axtxt
aatxt

That last output causes real trouble in practice. Write grep 'a.txt' and a human reads 「the filename a.txt」, while grep reads 「a, any character, txt」. When hunting for a string that contains dots — a filename, a domain — the regex has to escape the dot as a\.txt. In a glob there is nothing to escape. It was never a metacharacter.

  • Glob ? — exactly one character. Not zero, not two
  • Glob . — a literal period. No escaping needed
  • Regex ? — 「the previous element, zero or one time」. In basic regex (BRE) it must be written \?; with grep -E the bare ? works
  • So the single character ? does completely different jobs on the two sides. In a glob it consumes a character; in a regex it makes the previous thing optional

Anchoring — whole name or any part

This difference trips people more often than the meaning of * does. A glob is matched against the whole name. Both ends are implicitly pinned. A regex is partial by default. Being anywhere in the line is enough.

# glob - the whole name must be txt. no such file exists
$ ls txt
ls: cannot access 'txt': No such file or directory

# regex - anywhere in the line containing txt is a hit
$ printf '%s\n' a.txt notes.log | grep 'txt'
a.txt

So expressing 「the whole name is this」 in a regex takes an explicit ^ and $. That is why the earlier grep -E '^ab*$' dropped xabz. Going the other way, expressing 「contains this somewhere」 in a glob takes stars on both ends: *txt*.

Laying the pairs side by side is what makes them stick. Left and right in each row mean the same thing.

[...] splits at negation

Brackets are where the two grammars look most alike. [abc], [a-z] and [[:digit:]] mean the same thing in a glob and in a regex. Even the POSIX character classes are shared. And then one piece of notation splits: negation.

# the standard glob negation is [!...]
$ ls [!a]*.txt
b.txt

# bash also accepts [^...] as negation inside globs
$ ls [^a]*.txt
b.txt

# the regex negation is [^...]
$ printf '%s\n' a.txt ab.txt b.txt | grep '^[^a]'
b.txt

# in a regex, [!...] is not a negation. it is the set 「! or a」
$ printf '%s\n' a.txt ab.txt b.txt '!x.txt' | grep '^[!a]'
a.txt
ab.txt
!x.txt

That last output makes the situation plain. Writing [!a] in a regex does not give you 「not a」; it gives you 「! or a」. It does the exact opposite of what was intended, and nothing errors out.

Bash being lenient turns into a portability problem

Since ls [^a]*.txt worked, it is easy to conclude that [^...] is fine in globs too. That is a bash extension. Hand the same pattern to dash and this happens.

$ dash -c 'cd /tmp/demo; echo [!a]*.txt'
b.txt

$ dash -c 'cd /tmp/demo; echo [^a]*.txt'
a.txt ab.txt abb.txt

Completely inverted. In dash, [^a] is not a negation but the set 「the character ^ or the character a」, so it collects every name beginning with a. It selected precisely what was meant to be excluded. And here too, not one line of warning.

Target systems where /bin/sh points at dash are not rare. When this inversion lands inside a script that deletes or moves things, the result goes quietly to the worst case.

  • [!...] for globs, [^...] for regexes. Stick to those two and the meaning holds in any shell
  • Bash accepting [^...] is not permission to use it. Leniency that lets tests pass becomes a hazard the moment the script travels
  • The range [a-z] rides on locale collation order. For safety, use a character class such as [[:lower:]]
  • POSIX classes like [[:digit:]] carry over unchanged. Both ls *[[:digit:]]*.txt and grep '[[:digit:]]' work

Globs are not a filename-only grammar

Knowing globs only as 「the thing for picking files on the command line」 is half the picture. Bash uses globs in four places, and three of them involve no files at all.

Every label in a case statement

$ for v in report.log a.txt sub README; do
>   case "$v" in
>     *.log)  echo "$v -> log" ;;
>     *.txt)  echo "$v -> text" ;;
>     [A-Z]*) echo "$v -> uppercase-start" ;;
>     *)      echo "$v -> other" ;;
>   esac
> done
report.log -> log
a.txt -> text
sub -> other
README -> uppercase-start

Each branch label in case is a glob. The final *) acts as 「everything else」 for the same reason: the glob * matches any string. Put a regex there and usually no branch fires at all. case $v in ^ab.*$) ends up looking for 「a string starting with ^ab and ending with $」.

The pattern slot in parameter expansion

$ p="/var/log/app/server.access.log"

$ echo "${p##*/}"
server.access.log

$ echo "${p%.*}"
/var/log/app/server.access

$ echo "${p%%.*}"
/var/log/app/server

$ n="v1.2.3-rc4"
$ echo "${n//[!0-9]/}"
1234

The pat slot in ${v#pat}, ${v##pat}, ${v%pat}, ${v%%pat}, ${v/pat/rep} and ${v//pat/rep} is a glob every time. Here too * means 「any string」, and the one-character versus two-character form (# versus ##) is the difference between cutting as little as possible and as much as possible.

That last example, ${n//[!0-9]/}, works as 「delete every non-digit」 thanks to the glob [!...] negation. Worth noting: dash has no ${v//pat/rep} at all and dies with Bad substitution. ${v#pat} and ${v%pat} are POSIX, so they do work in dash.

== is a glob, only =~ is a regex

Inside bash there is exactly one place that takes a regex: [[ x =~ re ]]. Its immediate neighbour, [[ x == pat ]], is a glob. Having two operators sit inside the same brackets with different grammars is what makes this spot hard.

$ s="aXbXc"

$ [[ $s == a*c ]] && echo true || echo false
true

$ [[ $s =~ a*c ]] && echo true || echo false
true

$ [[ $s =~ ^a*c$ ]] && echo true || echo false
false

$ t="aaac"
$ [[ $t =~ ^a*c$ ]] && echo true || echo false
true

The second line is the trap. a*c went into =~ and came back true. Not because it behaved like a glob, but because the regex a*c means 「zero or more a followed by c」, and the lone c inside the string satisfies that. It was true by coincidence, thanks to partial matching. Only the anchored third line returns false.

Accidentally correct results are the worst kind. They pass the tests, ship, and first go wrong when the input shape shifts a little. Better to anchor =~ out of habit.

In exchange, there is something only =~ can do: pull the matched pieces back out.

$ v="v2.10.3"
$ [[ $v =~ ^v([0-9]+)\.([0-9]+)\.([0-9]+)$ ]] &&
>   echo "major=${BASH_REMATCH[1]} minor=${BASH_REMATCH[2]} patch=${BASH_REMATCH[3]}"
major=2 minor=10 patch=3

$ [[ $v == v*.*.* ]] && echo "matched, but no captured parts"
matched, but no captured parts

Globs have no capture. == gives you true or false, nothing more. Splitting a version string or pulling a field out of a log line is regex work, and the BASH_REMATCH array holds the result. Element 0 is the whole match; the parenthesised groups start at 1.

Quoting decides the grammar

One quotation mark changes the meaning of the same line. This section is not about shell quoting rules in general, only the part where globs and regexes diverge.

$ f='report.log'
$ pat='*.log'

$ [[ $f == $pat ]]   && echo true || echo false
true

$ [[ $f == "$pat" ]] && echo true || echo false
false

$ re='^rep.*\.log$'

$ [[ $f =~ $re ]]    && echo true || echo false
true

$ [[ $f =~ "$re" ]]  && echo true || echo false
false

One rule covers it. Quote the right-hand side of == or =~ and it stops being a pattern and becomes a literal string. [[ $f == "*.log" ]] asks 「is the filename exactly those six characters, star dot l o g」, and no such name exists, so it is false.

The =~ side catches people more often. There is a space in the regex, so it gets quoted, and suddenly nothing matches any more. Keeping the regex in a variable and using it unquoted is the standard idiom.

  • [[ $f == *.log ]] — right side is a glob pattern. True
  • [[ $f == "*.log" ]] — right side is a literal. False
  • [[ $f =~ $re ]] — read as a regex. This is the recommended form
  • [[ $f =~ "$re" ]] — demoted to a literal. Every regex metacharacter dies
  • Conversely, when you do want a literal comparison, quote it on purpose. Useful for comparing user input verbatim
  • Patterns handed to grep or find must always be quoted, or the shell glob-expands them first

With nothing to match, the pattern survives

This behaviour belongs to globs alone, and it is a regular source of script accidents. When no file matches the pattern, the shell leaves the pattern string in place.

$ ls *.csv
ls: cannot access '*.csv': No such file or directory

$ for f in *.csv; do
>   echo "loop sees: [$f]"
>   [ -e "$f" ] && echo "  exists" || echo "  DOES NOT EXIST"
> done
loop sees: [*.csv]
  DOES NOT EXIST

There is no .csv file, and the loop still runs once. And $f holds the five characters *.csv. What happens if you hand that to rm or mv is something I did not bother experimenting with.

There are three ways out.

$ shopt -s nullglob
$ cnt=0; for f in *.csv; do cnt=$((cnt+1)); done; echo "iterations: $cnt"
iterations: 0

$ shopt -u nullglob; shopt -s failglob
$ for f in *.csv; do echo "$f"; done
bash: no match: *.csv

$ shopt -u failglob
$ for f in *.csv; do [ -e "$f" ] || continue; echo "processing $f"; done

The last one is the option-independent approach, which makes it the better fit for scripts that run in somebody else's environment. nullglob is convenient but global, so switching it on mid-script also changes behaviour that other code was counting on. failglob earns its keep in an interactive shell by catching typos.

  • Default (nullglob off) — no match leaves the pattern intact. The most dangerous default, but POSIX specified it that way
  • nullglob on — no match leaves nothing behind. The loop runs zero times
  • failglob on — no match stops with an error. You get a no match message and a non-zero exit status
  • Manual defence — [ -e "$f" ] || continue as the first line of the loop. Behaves identically in every shell
  • Regexes have no such problem at all. If grep finds nothing the output is empty and the exit status is 1; the pattern never masquerades as data

Names that begin with a dot

Globs carry one more rule that regexes do not have. A leading dot has to be matched explicitly. * claims to be 「any string」 and yet will not catch .bashrc.

$ echo *
a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ echo .*
.bashrc .hidden

$ shopt -s dotglob; echo *
.bashrc .hidden a.txt ab.txt abb.txt b.txt notes.log report.log sub

$ shopt -u dotglob
$ shopt globskipdots
globskipdots    on

$ shopt -u globskipdots; echo .*
. .. .bashrc .hidden

Three things show up at once. First, * skips hidden files. That is a special shell rule, not something derived from what * means. Second, turning on dotglob removes that rule and * catches everything. Third, echo .* came back without . and .. because globskipdots, added in bash 5.2, is on by default. Switch it off and the old behaviour returns.

That last item matters. In the past, a command like rm -rf .* could reach into the parent directory. On bash 5.2 and later it is blocked by default, but on older shells it is still wide open.

  • Glob — the leading dot gets special treatment. To catch .bashrc, the pattern itself must start with a dot
  • Regex — no such rule. grep '.*' catches .bashrc without ceremony
  • dotglob — turn it on and * includes hidden files. Backup scripts often do
  • globskipdots — new in bash 5.2, on by default. Removes . and .. from glob results
  • The slash is similar. A glob * does not cross /. To reach subdirectories, spell out the level as */*.log or turn on globstar

find -name is a glob, find -regex is a regex

find is the most confusing spot because it carries both grammars inside one command. -name and -path take globs, -regex takes a regex. And they match against different things.

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

$ find . -name 'deep.log'
./sub/deep.log

$ find . -regex 'deep\.log'

$ find . -regex '.*/deep\.log'
./sub/deep.log

$ find . -name 'sub/*'

The third command printing nothing is the trap. -regex is matched against the entire path string the traversal produced, and it has to match all of it, not part. The real path is ./sub/deep.log, so deep\.log can never match. The front has to be opened up with .*/.

The fifth is similar. -name only sees the last component of the path, so a pattern with a slash in it can never match, structurally. To filter on path shape, use -path '*/sub/*'.

Layer the quoting problem on top and the error message gets cryptic.

$ find . -name *.log
find: paths must precede expression: `report.log'
find: possible unquoted pattern after predicate `-name'?

$ find . -name '*.log' | sort
./notes.log
./report.log
./sub/deep.log

The first command failed for reasons that have nothing to do with find. The shell expanded *.log first, turning it into find . -name notes.log report.log. find mistakes the second argument for a path and objects. It is kind enough to name the cause on the second line, though that message is hard to parse if you have never seen it.

The worse case is when there is no error at all. With exactly one .log file in the current directory, find . -name *.log quietly finds just that one. It breaks the day a second file appears.

  • -name — glob, matched against the filename (last path component) only. A slash never matches
  • -path — glob, matched against the whole path. Unlike a shell glob, its * does cross /
  • -regex — regex, whole path, full match. GNU find defaults to an emacs-flavoured dialect, changeable with -regextype posix-extended
  • BSD and macOS find use -E instead of -regextype. Passing -E to GNU findutils 4.10.0 gets rejected as unknown predicate
  • Whitespace and newline problems when piping results into another command are covered separately in the find and xargs whitespace trap

Extended globs and globstar

Plain globs have neither a repetition operator nor alternation. Bash fills that in with extglob, which is off by default.

$ shopt extglob
extglob         off

$ ls !(*.log)
ls: cannot access '!(*.log)': No such file or directory

$ shopt -s extglob
$ ls @(a|b).txt
a.txt
b.txt

$ ls +(a)b*.txt
ab.txt
abb.txt

$ ls a*(b).txt
a.txt
ab.txt
abb.txt

With it off, !(*.log) is not a pattern but a plain string naming a file to look for. With it on, a*(b).txt catches a.txt, ab.txt and abb.txt alike, because *(b) means 「b zero or more times」 and does the same job as the regex b*. Only the position of the parentheses differs.

globstar is in the same situation.

$ shopt globstar
globstar        off

$ echo **/*.log
sub/deep.log

$ shopt -s globstar
$ echo **/*.log
notes.log report.log sub/deep.log

$ echo **
a.txt ab.txt abb.txt b.txt notes.log report.log sub sub/deep.log sub/deep.txt

With it off, ** is just two stars, so it behaves exactly like */*.log and looks at exactly one level down. With it on, **/ spans zero or more levels, so notes.log at the current level is included too. Scripts written with ** by someone unaware of this burn time on 「why is it not descending」.

The regex counterpart for !(p) is not tidy because 「a string that is not something」 is an awkward request in regex to begin with. It takes negative lookahead, which is a topic of its own and lives in the practical lookaround piece.

Which places are globs and which are regexes

Memorising the places beats memorising the symbols in day-to-day work. Decide 「which side is this」 before writing the pattern and the rest follows.

The last column deserves attention too. grep is partial while find -regex is full, so copying a regex from one to the other changes the result. expr is different again: it matches only from the front and returns the matched length as a number.

$ printf '%s\n' a ab abb | sed 's/ab*/X/'
X
X
X

$ printf '%s\n' a ab abb xyz | awk '/ab*/'
a

abb

$ expr 'abb' : 'ab*'
3

sed turning a into X and awk printing a have the same cause. The regex ab* matches an a with no b. The 3 from expr means all three characters of abb matched.

Which one to reach for

Most of the time there is nothing to decide. The place fixes the grammar. A choice appears only when the same job can be done either way, and there the glob usually wins.

  • Picking files: glob. There is no reason to rewrite ls *.log as ls | grep '\.log$'. The latter breaks on filenames with spaces or newlines
  • Testing an extension, prefix or suffix: glob. [[ $f == *.tar.gz ]] is shorter than [[ $f =~ \.tar\.gz$ ]] and needs no escaping
  • Slicing a path: parameter expansion. ${p##*/} spawns no external process. Faster than a basename call and no $(...) needed
  • Extracting a piece: regex. The moment you need capture, globs drop out of contention. Splitting version strings and pulling log fields belong here
  • Anything involving counts: regex. A condition like 「three to five digits」 is hard to state without {3,5}. Even extglob cannot specify a count
  • When portability matters, globs are the safer side. Regex dialects fork across tools, while plain globs are near-identical across POSIX shells. [^...] and extglob are the exceptions

Handling Korean text with regexes brings a separate problem along. Syllable-level matching runs against intuition there, and that is written up in the Korean regex trap.

Wrapping up

There is one reason the same * gives different answers. The glob * means 「any string」 by itself, while the regex * is an operator that repeats what precedes it. From there, the roles of ? and . swap, the anchoring default forks, and the bracket negation symbol forks.

What to carry around is the places, not the symbol table. Inside bash, case, [[ == ]], ${} and filename expansion are all globs, and the only regex is [[ =~ ]]. Step outside and grep, sed, awk and expr are regexes while find -name is a glob again.

And this whole area shifts with one line of shopt. Knowing what nullglob, failglob, dotglob, extglob, globstar and globskipdots each turn on or off lets you guess half of 「it worked yesterday」 in advance. Checking takes one line: type shopt with no arguments and it all comes out.

What I Could Not Verify

  • Every output came from a single environment: Git Bash (MSYS2) on Windows 10, GNU bash 5.2.37. I did not cross-check against native Linux bash or macOS. In particular, on a case-insensitive filesystem the [a-z] range and anything touching nocaseglob may behave differently
  • zsh and ksh are not installed on this machine, so I could not run them. zsh extends glob syntax considerably (qualifiers, regex-style globs), so this article's claim that 「plain globs have no repetition operator」 does not carry over to it unchanged. The other-shell comparisons in the text were verified against dash only
  • For globskipdots being new in bash 5.2, I confirmed only that the option exists and defaults to on in the 5.2.37 here. I did not run anything to confirm its absence in 5.1 or earlier. If you work on older servers, check with shopt globskipdots yourself
  • GNU find 4.10.0 accepted .+ in -regex without any -regextype. The documented default is an emacs-flavoured dialect, but I did not exhaustively test where the boundary of accepted syntax lies. When portability matters, spell out -regextype posix-extended
  • Locale-driven changes to the [a-z] range were not measured. Recommending character classes follows widely known advice rather than an experiment of my own
  • The Pattern Matching Notation section of the POSIX specification itself would not open. The notation rules were cross-checked against the corresponding section of the GNU bash manual, and no specification text is quoted here
