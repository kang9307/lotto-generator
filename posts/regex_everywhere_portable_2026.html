어디서나 동작하는 정규표현식 — 언어·도구 간 호환성 함정과 해법

JS·Python·Go·PCRE·POSIX에서 같은 패턴이 왜 다르게 동작하나 — 방언 차이, 이식 가능한 정규식 원칙, 흔한 함정을 실용적으로 분석한다

2026-06-30 개발/인프라

서론: 정규식은 왜 "어디서나" 동작하지 않는가

정규표현식(regex)은 개발자라면 반드시 마주치는 도구다. 텍스트 검색, 로그 파싱, 입력 유효성 검증, 설정 파일 처리 — 어디에나 나온다. 그런데 Python 스크립트에서 멀쩡하게 동작하던 패턴을 Go 코드에 붙여 넣으면 컴파일 에러가 난다. grep으로 잘 잡히던 패턴이 sed에서 전혀 다른 결과를 낸다. JavaScript에서 유니코드 문자가 정규식 매칭에서 누락된다. 이런 경험이 있다면 이 글이 도움이 된다.

핵심 이유는 하나다. 정규표현식에는 단일 표준이 없다. POSIX BRE/ERE, PCRE, ECMAScript(JavaScript), Python re, Go RE2 — 이것들은 모두 같아 보이지만 문법, 지원 기능, 엔진 동작이 미묘하게 또는 근본적으로 다른 방언(flavor)이다. 2026년 6월 기준으로 이 방언 간 호환성 문제는 사라지지 않았으며, 오히려 Go·Rust 같은 신형 언어가 RE2 계열로 수렴하면서 PCRE 기반 패턴과의 단절이 더 선명해졌다.

이 글은 각 방언의 차이를 설명하고, 여러 환경에서 동작하는 이식 가능한 정규식을 쓰는 원칙을 정리하며, 흔한 함정과 디버깅 방법을 다룬다. 마지막으로 "정규식을 언제 써야 하고 언제 피해야 하는가"라는 더 근본적인 질문에 답한다.

1. 정규식 방언 지형도 — 무엇이 얼마나 다른가

정규식 엔진은 크게 세 계보로 나뉜다. POSIX 계열(BRE/ERE), PCRE 계열(Perl, PHP, Python, Java, Ruby, .NET, JavaScript), RE2 계열(Go, Rust의 regex 크레이트, Hyperscan)이다. 이 세 계보의 차이는 단순한 문법 취향이 아니라 엔진 설계 철학의 차이에서 비롯된다.

1.1 POSIX — 가장 오래된 표준, 가장 많은 오해

POSIX는 BRE(Basic Regular Expression)와 ERE(Extended Regular Expression) 두 가지를 정의한다. grep과 sed는 기본적으로 BRE 모드를 사용한다. 여기서 치명적인 함정이 있다: BRE에서 +, ?, (, ), |, {, }는 리터럴 문자다. 메타문자로 쓰려면 역슬래시를 붙여야 한다. ERE(grep -E, awk)에서는 반대로 이 문자들이 역슬래시 없이 메타문자다.

# BRE (grep 기본 모드)
grep '\(foo\)\+' file.txt      # 'foo' 한 번 이상 반복 - 그룹 + + 사용
grep '(foo)+' file.txt         # '(foo)+' 리터럴 검색 - 의도와 다름!

# ERE (grep -E)
grep -E '(foo)+' file.txt      # 올바른 그룹 + 반복
grep -E '\(foo\)+' file.txt    # '\(foo\)+' 리터럴 검색 - 역전됨!

awk는 ERE만 지원한다. sed는 BRE가 기본이고 sed -E 또는 sed -r로 ERE를 쓴다. 단, sed의 ERE에서 {는 유효한 수량자가 아니어도 역슬래시 없이 쓰면 에러가 나는 경우가 있어, grep -E나 awk보다 더 까다롭다. 이 세 도구를 섞어 쓰는 셸 파이프라인에서 발생하는 버그의 상당수가 이 BRE/ERE 혼동에서 비롯된다.

POSIX는 룩어헤드(lookahead), 룩비하인드(lookbehind), 백레퍼런스(\1 방식의 캡처 참조 제외), 명명된 그룹을 지원하지 않는다. 단순하지만 이식성은 가장 높다.

1.2 PCRE — 사실상 업계 표준, 그러나 구현마다 차이

PCRE(Perl Compatible Regular Expressions)는 Perl 정규식을 기반으로 Philip Hazel이 1997년 작성한 라이브러리다. PHP, Python(re 모듈), Ruby, Java(java.util.regex), .NET, JavaScript(ECMA 계열), Nginx가 이 계보를 따른다. 룩어헤드, 룩비하인드, 명명된 그룹, 원자 그룹, 비탐욕(lazy) 수량자, 백레퍼런스 등 현대 정규식의 대부분 기능이 여기서 나왔다.

그러나 "PCRE 계열"도 동질적이지 않다. 대표적 차이를 보면 다음과 같다.

룩비하인드 가변 길이제한적 지원지원 (Node 10+)지원지원

Python의 표준 re 모듈은 PCRE2의 일부 고급 기능(원자 그룹, 소유적 수량자)을 지원하지 않는다. 이 기능이 필요하면 써드파티 regex 모듈을 사용해야 한다. Java는 반대로 매우 풍부한 기능을 지원하지만 \p{L} 같은 유니코드 속성 클래스 문법이 PCRE2와 미묘하게 다르다.

1.3 RE2 — 성능 보장의 대가로 포기한 기능들

Go의 regexp 패키지는 Google이 개발한 RE2 엔진을 사용한다. RE2의 설계 원칙은 단 하나다: O(n) 선형 시간 보장. 입력 길이에 무관하게 매칭 시간이 선형 이하임을 보장하기 위해, RE2는 역추적(backtracking)을 사용하지 않는 Thompson NFA 알고리즘을 채택했다.

역추적이 없으면 구현 불가능한 기능들이 있다. 그래서 RE2는 다음을 지원하지 않는다.

  • 룩비하인드(lookbehind) — (?<=...), (?<!...)
  • 룩어헤드(lookahead) — (?=...), (?!...)
  • 백레퍼런스 — \1, \2 등 캡처 그룹 참조
  • 원자 그룹, 소유적 수량자

Python·JavaScript에서 동작하던 룩비하인드 패턴을 Go에 그대로 붙여 넣으면 regexp.Compile 시점에 에러가 난다. 이것은 버그가 아니라 의도된 설계다. 우회책은 두 개의 별도 매처를 조합하거나, 순수 코드로 로직을 직접 구현하는 것이다.

2026년 6월 기준, EPFL 연구팀이 RE2에 선형 시간 룩비하인드를 추가하는 연구를 발표했으나 아직 공식 RE2 엔진에 머지되지 않았다. 당분간 Go에서 룩비하인드는 사용 불가로 봐야 한다.

2. 흔한 함정 4가지 — 실제로 잘 틀리는 상황

2.1 룩비하인드: PCRE에서 Go로 이식 시 컴파일 에러

가장 자주 만나는 이식 실패 케이스다. 예를 들어 파이썬에서 (?<=@)\w+로 이메일의 도메인 앞부분을 추출했다면, 이 패턴은 Go에서 즉시 컴파일 에러가 난다. 해결책은 캡처 그룹으로 재작성하는 것이다.

# Python - 룩비하인드 사용
import re
m = re.search(r'(?<=@)[\w.]+', 'user@example.com')
# => 'example.com'

# Go - 캡처 그룹으로 대체
import "regexp"
re := regexp.MustCompile(`@([\w.]+)`)
m := re.FindStringSubmatch("user@example.com")
// m[1] => 'example.com'

본인이 자주 보는 패턴은 파이프라인 설정이나 WAF 규칙을 Python으로 프로토타입하고 Go 서비스에 옮길 때다. 이때 룩어라운드 의존성을 미리 파악하고 제거해야 Go 이식이 수월하다.

2.2 유니코드: JavaScript의 u 플래그 누락

JavaScript에서 \w는 u 플래그 없이 [a-zA-Z0-9_]와 동일하다. 즉 한글, 한자, 아랍문자 등 비ASCII 문자가 \w에 매칭되지 않는다. \b(단어 경계) 역시 ASCII 기준으로만 동작한다. u 플래그를 붙이면 유니코드 코드포인트 단위로 처리된다.

// u 플래그 없음 - 한글 누락
/\w+/g.exec('안녕hello')  // => ['hello'] 만 잡힘

// u 플래그 있음 - 코드포인트 단위
/\p{L}+/gu.exec('안녕hello')  // => ['안녕', 'hello'] 모두 잡힘

// 서로게이트 페어 문제 (이모지 등)
'😀'.length   // 2 (UTF-16 서로게이트 페어)
/^.$/u.test('😀')  // true (u 플래그로 코드포인트 단위)
/^.$/.test('😀')   // false (u 없으면 2문자로 인식)

다국어 입력을 처리하는 서비스라면 JavaScript 정규식에 u 플래그를 붙이는 것이 기본이어야 한다. 2026년 현재 Node.js와 모든 주요 브라우저에서 지원되므로 호환성 걱정 없이 쓸 수 있다.

2.3 앵커: 멀티라인 모드의 언어별 동작 차이

^과 $는 언어마다 기본 동작이 다르다. Python의 re.MULTILINE 플래그, JavaScript의 m 플래그를 붙이면 ^은 각 줄의 시작, $는 각 줄의 끝을 뜻한다. 플래그가 없으면 문자열 전체의 시작·끝이다.

# Python 앵커 차이
text = "line1\nline2\nline3"

re.findall(r'^line\d', text)              # ['line1'] — 멀티라인 미적용
re.findall(r'^line\d', text, re.M)        # ['line1', 'line2', 'line3']

# Python의 \Z vs $
# $는 문자열 끝 또는 \n 바로 앞을 매칭
# \Z는 반드시 문자열 끝만 매칭 (엄격)

특히 Python에서 $가 줄바꿈 직전도 매칭한다는 점을 모르고 \Z를 써야 할 곳에 $를 쓰면 의도치 않은 매칭이 생긴다. 엄격한 끝 매칭이 필요하면 Python에서는 \Z, JavaScript에서는 입력 모드(/pattern$/ 플래그 없이)를 구분해야 한다.

2.4 이스케이프: BRE/ERE 역전과 언어별 이중 이스케이프

POSIX BRE/ERE의 이스케이프 역전은 앞서 설명했다. 언어 수준에서도 이스케이프 중첩 문제가 있다. 문자열 리터럴에서 \\를 써야 정규식 엔진에 \ 하나가 전달된다. 원시 문자열(Python의 r"...", Go의 백틱 `` `...` ``)을 쓰면 이 이중 이스케이프를 피할 수 있다.

# Python - 이중 이스케이프 혼란
re.match("\\d+\\.\\d+", "3.14")   # 동작하지만 읽기 어려움
re.match(r"\d+\.\d+", "3.14")     # r 문자열로 깔끔하게

# JavaScript - 이중 이스케이프 불가피
new RegExp("\\d+\\.\\d+")   // 문자열 생성자 방식
/\d+\.\d+/                  // 리터럴 방식 - 이스케이프 한 번만

가능하면 원시 문자열 리터럴 또는 정규식 리터럴(/pattern/)을 사용하고, 동적으로 문자열에서 정규식을 생성할 때는 이중 이스케이프에 주의해야 한다.

3. 이식 가능한 정규식을 위한 원칙 5가지

여러 언어·도구에서 동작해야 하는 정규식을 짤 때 본인이 따르는 원칙이다.

원칙 1: 공통 기능만 쓴다 — PCRE 고급 기능 의존 최소화

룩어라운드, 명명된 그룹, 백레퍼런스는 PCRE 계열에서는 되지만 RE2(Go), POSIX에서는 안 된다. 이식성이 중요하다면 이 기능 없이 패턴을 재설계한다. 캡처 그룹으로 룩비하인드를 대체하고, 명명된 그룹 대신 순서 기반 그룹을 사용한다. 패턴이 복잡해지더라도 코드 로직으로 후처리하는 것이 이식성 측면에서 낫다.

원칙 2: 앵커와 플래그를 명시한다

멀티라인·유니코드·케이스 무시 여부를 묵시적으로 기대하지 않는다. 필요한 플래그를 항상 명시한다. JavaScript에서는 u 플래그를, Python에서는 re.UNICODE(기본이지만 코드로 명시), re.MULTILINE을 필요한 곳에 명시한다. 플래그가 다르면 같은 패턴이 다른 결과를 낼 수 있다.

원칙 3: 수량자 탐욕성(greediness)을 의식한다

.*는 기본적으로 탐욕적(greedy)이다. 가능한 한 많이 매칭한다. .*?는 비탐욕적(lazy)이다. HTML처럼 구분자가 있는 구조에서 탐욕적 수량자를 쓰면 첫 매치가 마지막 닫는 태그까지 쭉 잡아버린다. 의도를 정확히 표현하려면 수량자 탐욕성을 명시적으로 선택한다. RE2에서는 비탐욕 수량자를 지원하므로 이 부분은 큰 이식성 문제가 없다.

원칙 4: 패턴을 문서화한다

정규식은 작성할 때는 이해가 되지만 한 달 뒤에는 해독이 어렵다. 주석 모드(Python의 re.VERBOSE, PCRE의 (?x))를 활용해 패턴의 각 부분에 의도를 적는다. 또는 복잡한 패턴을 작은 조각으로 나눠 변수에 담고 조합한다.

# Python verbose 모드 예시
pattern = re.compile(r"""
    (?P<year>  \d{4})   # 4자리 연도
    -
    (?P<month> \d{2})   # 2자리 월
    -
    (?P<day>   \d{2})   # 2자리 일
""", re.VERBOSE)

원칙 5: 대상 엔진에서 직접 테스트한다

regex101.com은 PCRE2, ECMAScript, Python, Go, Java 방언을 선택해 결과를 확인할 수 있다. 이식 전에 반드시 대상 엔진 모드로 테스트한다. Regexper는 정규식을 철도 다이어그램(railroad diagram)으로 시각화해 패턴 구조를 직관적으로 보여준다. 이 두 도구를 조합하면 이식 전에 문제를 사전에 잡을 수 있다.

4. ReDoS — 정규식이 서버를 멈추는 방법

PCRE 계열의 역추적 엔진에는 치명적 약점이 있다. 중첩 수량자나 겹치는 교대(alternation) 패턴에 악의적으로 설계된 짧은 입력을 넣으면 역추적 횟수가 지수적으로 폭발해 서버가 멈춘다. 이를 ReDoS(Regular Expression Denial of Service)라 한다.

# 취약한 패턴 예시
# (b+)+z — 'bbbbbbbbbbbbbbbbc' 같은 입력에서 역추적 폭발
/^(b+)+z$/.test('bbbbbbbbbbbbbbbbc')  // JavaScript - 수십 초 걸림

# 비슷하게 위험한 패턴들
/^(a*)*$/       # 중첩 수량자
/^(a|aa)+$/     # 겹치는 교대
/^(\w+\s?)+$/   # 공백이 선택적인 반복 단어

CloudFlare가 2019년 ReDoS 공격으로 전 세계 서비스 장애를 겪은 것은 유명한 사례다. 방지책은 다음과 같다.

  • 중첩 수량자 (x+)+, (x*)* 패턴을 피한다
  • 겹치는 교대 (a|ab)+ 패턴을 피한다
  • 사용자 입력을 정규식으로 처리할 때 입력 길이를 엄격히 제한한다
  • Go(RE2)처럼 선형 시간 보장 엔진을 사용한다 — ReDoS가 구조적으로 불가능
  • regex101.com의 debugger 탭으로 역추적 횟수를 사전 확인한다

원자 그룹 (?>...)이나 소유적 수량자 x++는 역추적을 막아 ReDoS를 방지하지만, JavaScript와 Python re 모듈은 이를 지원하지 않는다(Python의 regex 모듈은 지원). 백엔드를 Go로 전환하는 것이 근본적 해결책이다.

5. 정규식을 언제 쓰고 언제 피해야 하는가

정규식이 강력하다고 해서 모든 곳에 써야 하는 건 아니다. 오히려 정규식이 나쁜 선택인 경우가 분명히 있다.

5.1 정규식이 맞는 곳

  • 단순 포맷 검증: 우편번호 5자리, 날짜 YYYY-MM-DD 형식, 전화번호 패턴
  • 로그에서 고정 패턴 추출: IP 주소, 타임스탬프, 에러 코드
  • 텍스트 에디터 검색·치환: 일회성 대량 치환
  • 설정 파일의 키워드 필터링: 특정 접두사·접미사 매칭
  • 토크나이저의 개별 토큰 패턴: 어휘 분석 단계

5.2 정규식이 나쁜 선택인 곳

  • HTML·XML 파싱: HTML은 정규 언어가 아니다. Nokogiri, BeautifulSoup, lxml을 쓴다
  • URL 분해: 표준 URL 파서(urllib.parse, URL API)가 훨씬 정확하다
  • 이메일 완전 유효성 검증: RFC 5322 완전 구현은 정규식으로 불가능에 가깝다. 간단한 형식 체크 후 실제 전송으로 확인하는 것이 현실적이다
  • JSON·YAML 파싱: json.loads, yaml.safe_load를 쓴다. 2026년 LLM 응답 파싱도 정규식 대신 구조화된 출력(structured output) API를 사용하는 것이 표준이 됐다
  • 소스 코드 분석: AST(추상 구문 트리) 파서를 쓴다. 정규식으로 코드를 분석하면 문자열 리터럴·주석·다중 줄 구문 처리에서 반드시 틀린다
  • 단순 문자열 검색: indexOf, contains, startsWith가 정규식보다 빠르고 명확하다

본인이 쓰는 판단 기준은 단순하다. "이 패턴이 입력이 더 복잡해지면 무너지나?" 정규식으로 HTML을 파싱하다가 중첩 태그나 속성 안 특수문자를 만나는 순간 패턴이 망가진다. 반면 IP 주소 패턴은 입력이 달라져도 패턴이 흔들리지 않는다.

6. 이식성 체크리스트 — 다음에 정규식을 옮길 때

2026년 6월 기준으로 본인이 쓰는 체크리스트다.

  1. 룩어라운드(lookbehind, lookahead) 포함 여부 확인 → Go 이식 불가, 캡처 그룹으로 재작성
  2. 백레퍼런스(\1) 포함 여부 → RE2 미지원, 코드 로직으로 분리
  3. BRE/ERE 모드 확인 → grep/sed 기본값은 BRE, -E 플래그 또는 awk 사용 시 ERE
  4. JavaScript라면 u 플래그, 다국어 문자 처리 여부 확인
  5. 중첩 수량자·겹치는 교대 패턴 점검 → ReDoS 위험, RE2 이전 또는 구조 재설계
  6. 앵커(^, $)의 멀티라인 동작 필요 여부 → 플래그 명시
  7. regex101.com에서 대상 엔진 모드로 테스트 후 배포

결론 — 정규식은 방언임을 전제하고 써야 한다

정규식은 단일 언어가 아니다. POSIX BRE, ERE, PCRE, ECMAScript, RE2 — 각자 다른 규칙을 가진 방언의 집합이다. 2026년 기준으로 이 방언 간 간극은 오히려 더 선명해졌다. Go와 Rust가 RE2 계열로 대세를 형성하면서 PCRE 패턴의 직접 이식이 더 자주 실패한다.

이식 가능한 정규식의 핵심은 최소 공배수 기능만 쓰는 것이다. 룩어라운드·백레퍼런스 없이도 캡처 그룹과 코드 로직으로 대부분의 작업을 처리할 수 있다. 고급 기능이 필요할 때는 대상 엔진을 명확히 정하고, 그 엔진에서만 테스트한다. 그리고 정규식이 애초에 맞는 도구인지를 먼저 물어야 한다. HTML을 파싱하거나 URL을 분해하는 데 정규식을 쓴다면 이미 틀린 길에 들어선 것이다.

정규식은 좁고 분명한 문제에 쓸 때 가장 강하다. 그 범위를 지키면 언어가 바뀌어도 함정이 줄어든다.
