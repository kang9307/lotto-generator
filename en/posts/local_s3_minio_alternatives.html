Why Re-Evaluating Single-Node Local S3 Is Essential in 2026

In modern cloud-native software architecture and data engineering pipelines, object storage is no longer merely an optional component; it is the fundamental substrate upon which applications are designed. Over the past decade, the AWS S3 API has evolved into the de facto universal storage protocol. Distributed compute systems, database engines, and web applications expect S3 API compatibility out of the box. In local workstations and continuous integration (CI/CD) runners, developers require lightweight, self-contained S3 emulators to validate functionality without incurring cloud costs, network latency, or credential management overhead.

The urgency for local S3 emulation has surged with the widespread adoption of open table formats such as Apache Iceberg and Delta Lake, coupled with fast local query engines like DuckDB and ClickHouse. Engineers routinely build end-to-end data workflows on laptops where Parquet files, partition structures, and metadata commit manifests are written directly to local S3 endpoints. A reliable, lightweight local S3 container is therefore the linchpin of reliable local software testing.

For many years, MinIO served as the unquestioned gold standard for this specific role. A single docker run command or a brief service declaration in a Docker Compose file provided a complete, battle-tested S3 API endpoint complete with an administrative web browser. Thousands of open-source projects, academic tutorials, and enterprise test suites built their foundation on MinIO.

However, as detailed in the original analysis by Robin Moffatt, the company behind MinIO made a strategic pivot in late 2025 toward other commercial endeavors, effectively abandoning the open-source maintenance of the project. Evidence across the Object Browser transition, GitHub issue comments (such as Issue #21647), and commit histories confirmed this retreat. This sudden shift disrupted developer workflows across the globe, forcing teams to identify viable, lightweight drop-in alternatives that can emulate S3 in local Docker environments with zero application code changes.

Three Evaluation Criteria and Excluded Scope

Selecting a local development S3 emulator involves fundamentally different engineering constraints than architecting an enterprise-grade distributed storage cluster. High availability, cross-region replication, and petabyte-scale durability take a back seat to container startup latency, minimal memory footprints, and effortless configuration.

Three Core Requirements: Docker, S3 Compatibility, and Free Open-Source

In his benchmark, Robin Moffatt defined three non-negotiable criteria for any viable MinIO replacement:

  • Official Docker Image Availability: Modern software demonstrations and developer testbeds are distributed primarily as Docker Compose stacks. If an alternative requires manual compilation from source or custom Dockerfile authoring, it fails the basic usability threshold for rapid prototyping.
  • S3 API Protocol Compatibility: Standard client libraries—including the AWS SDK, boto3, s3cmd, and the MinIO client (mc)—must interact with the storage engine seamlessly without requiring application-side code patches.
  • Free and Open-Source Licensing (OSI Compliant): The software must be freely usable without commercial lock-in, with a strict preference for permissive open-source licenses conforming to the Open Source Definition (OSD), such as Apache 2.0.

Scope Excluded from Single-Node Demo Testing

The scope of this evaluation was deliberately constrained to single-node local execution. Consequently, the following production criteria were deliberately excluded from consideration:

  • Multi-node clustering, consensus-driven quorum replication, and distributed erasure coding architectures
  • Extreme I/O throughput benchmarks, maximum concurrent connection tuning, and latency optimizations
  • Commercial enterprise support contracts, vendor service-level agreements (SLAs), and licensing fees
  • Advanced administrative web consoles (appreciated as a convenience, but strictly non-essential)

Baseline Verification Stack: DuckDB and Iceberg REST Catalog

To establish an empirical baseline, the author constructed a realistic modern analytical pipeline. Rather than executing primitive file upload tests, the benchmark exercised complex metadata manipulations and columnar Parquet file interactions typical of contemporary data lakehouse environments.

Baseline Docker Compose Architecture and Pipeline Flow

The baseline verification topology comprised three interconnected tiers:

  • Storage Tier: MinIO container functioning as the initial control baseline (replaced by candidate containers during bake-offs)
  • Catalog Tier: Apache Iceberg REST Catalog service managing table schemas and snapshot trees
  • Query and Client Tier: DuckDB executing analytical queries and the MinIO Client (mc) handling bucket provisioning

Upon container boot, the mc client verified endpoint readiness and automatically created target storage buckets. DuckDB connected to the Iceberg REST Catalog, initialized table schemas pointing to the S3 bucket, and inserted transactional records. The raw records were serialized into compressed Parquet objects, while schema evolutions and snapshot commits were persisted as Avro and JSON metadata files within the object store.

Automated Verification Script (test.sh) and mc CLI Compatibility

Candidate systems were subjected to an identical automated bash verification script (test.sh), which validated functionality in four sequential phases:

  • Phase 1: Verification of HTTP endpoint availability and automated bucket creation via mc
  • Phase 2: Table creation and data insertion executed through DuckDB via the Iceberg catalog
  • Phase 3: Query execution (SELECT) verifying analytical consistency and data integrity
  • Phase 4: Direct file system inspection of underlying Parquet files and metadata hierarchies

Because preserving existing automation was a primary objective, the MinIO client (mc) was retained to test backward compatibility. In setups seeking to purge all MinIO-related tooling, standard utilities such as the official aws CLI or s3cmd can be swapped in without architectural changes.

Immediate Replacements: S3Proxy and SeaweedFS

Of the seven candidate solutions evaluated, only S3Proxy and SeaweedFS received an unambiguous 「Yes」 verdict for immediate single-node local adoption.

S3Proxy 3.0.0: Extreme Simplicity with an Upstream Caveat

S3Proxy 3.0.0 is an open-source, Java-based gateway licensed under Apache 2.0. It acts as an S3 API translation proxy backed by local storage or secondary cloud providers.

  • Operational Simplicity: S3Proxy represents the cleanest architectural drop-in replacement. By running the official Docker image (andrewgaul/s3proxy) with a few environment variables, developers obtain an S3 endpoint mapped directly to a local directory without auxiliary database daemons.
  • Empirical Verification: The solution executed the DuckDB and Apache Iceberg validation suite flawlessly, exhibiting zero protocol mismatches or serialization failures.
  • Governance Consideration: S3Proxy relies on Apache jclouds as its foundational abstraction layer. In mid-2025, the Apache jclouds project was officially moved to the Apache Attic and retired. While its local file-system provider remains stable, upstream maintenance will inevitably depend on community fork vigilance.

The Compose definition used in the bake-off is published in the author’s verification repository rmoff/minio-alternatives as s3proxy/docker-compose.yml. It wires the S3Proxy container together with mc for bucket provisioning, the Iceberg REST Catalog, and DuckDB, so the stack boots exactly as downloaded.

SeaweedFS 4.06: Battle-Tested Stability with a Built-In Web UI

SeaweedFS 4.06 is a mature distributed object store written in Go, originally influenced by Facebook’s Haystack paper. It has provided full S3 API support since release v0.91 in 2018.

  • Seamless Transition and Administrative UI: SeaweedFS provides a remarkably smooth developer experience. A single container image (chrislusf/seaweedfs) launches the master server, volume store, filer, and S3 endpoint concurrently. It includes a functional browser-based user interface, allowing developers to visually inspect bucket contents during demos.
  • Empirical Verification: Configured using the lightweight weed mini architecture, SeaweedFS passed every stage of the Iceberg table creation, Parquet ingestion, and DuckDB analytical query benchmark.
  • Configuration Refinement: During testing, defining S3 credentials required mounting an inline configuration file in Docker Compose. On the day the original article went out, the SeaweedFS maintainer replied in the comments that the change removing this extra requirement was already completed and would ship in the next weekly release.
  • Commercial Perception: The SeaweedFS landing page prominently highlights enterprise licensing and support tiers; however, the core software remains entirely open-source under Apache 2.0.

The SeaweedFS variant lives in the same repository as seaweedfs/docker-compose.yml, pairing the SeaweedFS server with the same mc, Iceberg REST Catalog, and DuckDB services, which makes it directly comparable with the S3Proxy stack.

Conditional Candidates and Caveats: RustFS and Zenko CloudServer

Two candidates demonstrated technical compatibility but carried developmental or operational caveats that prevent an unreserved endorsement for general use.

RustFS 1.0.0-alpha.79: High Speed vs. Alpha Vulnerabilities

RustFS is a modern, high-performance object store developed in Rust, emphasizing memory safety, minimal footprints, and an integrated administrative web dashboard.

  • Key Strengths: Fast initialization times, lightweight memory consumption, and a polished modern web interface out of the box.
  • Maturity Limitations: The project remains in an early alpha phase (version 1.0.0-alpha.79). The documentation portal contains unresolved structural flaws, including multiple hyperlinks that circular-loop back to the root page.
  • Security Considerations: A critical security advisory (GHSA-h956-rh7x-ppgj) was recently published for the codebase. While isolated local developer sandboxes are relatively insulated, teams must exercise caution before deploying it across shared development clusters.

Zenko CloudServer 9.2.8: Robust Compatibility vs. Branding Confusion

Maintained by enterprise storage vendor Scality, Zenko CloudServer has a long heritage, formerly recognized across the open-source landscape as 「S3 Server」.

  • Technical Capability: Licensed under Apache 2.0, CloudServer possesses years of S3 protocol compliance hardening, serving as a dependable functional emulator.
  • Documentation Friction: Significant naming ambiguities exist between Scality, Zenko, and CloudServer. Official documentation frequently references legacy Docker Hub repositories holding outdated images, requiring users to manually seek out recent builds on GitHub Container Registry (GHCR).
  • Ecosystem Overhead: Concerns linger regarding whether standalone use might inadvertently drag in operational concepts from the broader Zenko multi-cloud orchestration suite.

Candidates Excluded for Local Demos: Garage, Apache Ozone, and Ceph RGW

The systems grouped below are outstanding engineering achievements in distributed data storage. However, their foundational design goals diverge sharply from the requirements of rapid, zero-overhead single-node local execution.

Garage 1.0.0: Configuration Rigor vs. Single-Node Friction

Garage is an AGPLv3-licensed distributed object store developed by the French non-profit Deuxfleurs and supported by the NGI/NLnet foundation. It is engineered specifically for geo-distributed, heterogeneous hardware environments.

  • Configuration Complexity: Unlike single-command containers, Garage enforces a formal topology initialization workflow. Provisioning layout layouts, node assignments, and bucket creation required running a separate orchestrator container (garage-init).
  • Strict Constraints: Garage mandates detailed TOML configuration files and enforces rigorous access key formats (requiring a GK prefix followed by a 12-byte hex-encoded string), making rapid ad-hoc testing cumbersome.
  • Production Excellence: These exact constraints make Garage extraordinarily dependable in multi-node edge deployments, as detailed in our comprehensive Complete Guide to Garage S3 Storage. However, for quick local demos, the setup overhead proved excessive. (Note: Version 2.3.0 introduced the garage server --single-node --default-bucket flag, significantly reducing this initialization friction.)

Apache Ozone and Ceph RGW: Multi-Node Footprints and Local Overhead

Enterprise and big-data storage titans encountered insurmountable architectural mismatch when reduced to single-node container roles.

  • Apache Ozone 2.1.0: Independent from Apache Hadoop since 2020, Ozone provides enterprise-scale object storage. However, Ozone cannot run as a standalone single-container process; it requires an orchestration of at least four interdependent services—Storage Container Manager (SCM), Ozone Manager (OM), DataNode, and S3 Gateway (S3G)—making it far too resource-intensive for local demos.
  • Ceph Object Gateway (RGW): Ceph is the undisputed pillar of open-source private cloud storage, as explored in our Complete Guide to Ceph Storage Architecture and Ceph RBD vs CephFS Comparison. However, Ceph’s extensive operational prerequisites (MONs, MGRs, OSDs, and Cephadm) led the author to exclude it after reviewing deployment requirements.

Governance Risks: The Fragility of Single Maintainers and Lack of Foundations

Beyond immediate feature compatibility, engineering architects must evaluate the long-term governance and community viability of developer tooling. The disruption caused by MinIO’s shift demonstrated the vulnerability of relying on single commercial entities for foundational infrastructure.

Bus Factor Hazards and Upstream Governance Shifts

The comparative governance audit reveals a profound structural reality: there is currently no neutral foundation-backed project tailored for local single-node S3 storage. Apache Ozone is the sole foundation-owned candidate, yet it cannot serve local single-node use cases.

  • Acute Bus Factor Exposures: Both top-tier candidates, S3Proxy and SeaweedFS, exhibit exceptional multi-year release track records but depend fundamentally on the continued dedication of single primary authors (Andrew Gaul and Chris Lu, respectively).
  • Vulnerability to Strategic Shifts: Projects outside neutral software foundations remain susceptible to unilateral abandonment or commercial privatization, reproducing the very dilemma presented by MinIO.
  • The CNCF S3 Standard Vacuum: Despite the central importance of object storage across the cloud-native ecosystem, the Cloud Native Computing Foundation (CNCF) has not yet recognized an official, neutral open-source standard for S3-compatible local emulation.

Practical Decision Framework for Engineering Teams

No single tool represents a silver bullet across all workflows. Engineering organizations must align tool selection with operational constraints and testing objectives.

CI/CD Pipeline Integration and Air-Gapped Network Constraints

In enterprise engineering environments, operational friction dictates tool viability:

  • Maximizing CI/CD Runner Efficiency: In automated CI workflows on GitHub Actions or GitLab CI, container spin-up latency directly dictates build durations and infrastructure costs. Zero-configuration tools like S3Proxy provide instant socket bindings without auxiliary daemon overhead. When configuring persistence, follow best practices from our Docker Network and Volume Guide.
  • Air-Gapped Container Ingestion: In restricted enterprise networks where external image registries are blocked, importing complex multi-image topologies requires extensive security reviews. Deploying a single compact binary image into internal private registries represents the most manageable operational path.

Unverified Items and Information Gaps

In adherence to strict technical verification standards, the following aspects could not be empirically validated from available primary sources:

  • Quantitative I/O Throughput and Latency Benchmarks: The primary source focused exclusively on configuration ergonomics and functional S3 protocol compatibility; precise IOPS, network transfer ceilings, and query execution latencies were not benchmarked and are intentionally omitted here.
  • Ceph Object Gateway Single-Container Execution Logs: Ceph RGW was disqualified during pre-flight requirement reviews due to heavy daemon dependencies, meaning empirical runtime failure traces were not generated.
  • Functional Gaps in Legacy Zenko Images: The exact API disparity between historical Docker Hub images and modern GitHub Container Registry (GHCR) v9.2.8 builds remains undocumented in upstream literature.
  • Exploit Reproducibility of the RustFS Security Advisory: While the security advisory identifier was confirmed, exploit verification was neither attempted nor documented in accordance with safety guidelines.
