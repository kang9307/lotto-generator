1. GA確定の経緯 — ビルド35と9件のJEP

Javaプラットフォームの最新標準仕様であるJDK 27が、2026年9月15日に正式リリース(General Availability、GA)を迎えました。OpenJDKプロジェクトのチーフアーキテクトであるMark Reinhold氏は、announceメーリングリストを通じてJava SE 27プラットフォームのリファレンス実装であるJDK 27の正式リリースを公表しました。本リリースはJEP 3で定められた6ヶ月周期の定期リリース計画通りに正確に公開されました。

公式告知によると、今回のGA確定の直接の基準となったのは、2026年8月20日にリリースされた第2リリース候補(Release Candidate 2)であるビルド35(build 35)でした。検証期間中に最高優先度であるP1レベルの不具合報告が寄せられなかったことから、ビルド35がバイナリの変更なしにそのまま最終GAビルドとして承認されました。現在OracleによるGPLv2(Classpath Exception付き)準拠のオープンソースプロダクションバイナリが公式サイトにてLinux(x64、AArch64)、macOS(x64、AArch64)、Windows(x64)向けに即時配布されており、告知は他ベンダーのビルドも間もなく登場するだろうと述べるにとどまり、ベンダー名も時期も示していません。

JDK 27には合計9件のJEP(JDK Enhancement Proposal)が含まれています。このうち2件はランタイムの長年のデフォルト動作を直接変更する機能であり、2件はセキュリティおよび診断テレメトリの強化、残る5件はプレビュー(Preview)およびインキュベータ(Incubator)状態のAPIです。公式告知では、これら9件の主要JEPに加えて「数百件の小規模改善と数千件のバグ修正("hundreds of smaller enhancements and thousands of bug fixes")」が統合されたと言及されています。表向きの言語構文の変更は少ないものの、JVMの根本的な挙動が2つの軸で切り替わった重要な転換点となるリリースです。

2. JDK 27 JEP 9件の全体現況

JDK 27に含まれる9件のJEPは、HotSpotランタイム、コアライブラリ、言語仕様、セキュリティ基盤にわたって配置されています。システム移行を担当するエンジニアリング組織は、どの機能が本番環境で即時に適用される確定仕様であり、どの機能がフラグを要する試験的APIであるかを明確に識別する必要があります。

3. デフォルト変更の第1の柱 — JEP 523 全環境でのG1標準指定

HotSpot JVMは長年にわたり、起動時にホスト環境のハードウェア構成を調査してサーバクラスマシン(Server-class machine)に該当するかを判定してきました。従来の基準では、2個以上の物理CPUコアと1792MB以上の物理RAMを備えている場合にG1(Garbage-First)コレクタが自動選択され、1コア環境や1792MB未満の軽量マシンではシングルスレッドのSerial GCが割り当てられていました。

Thomas Schatzl氏が主導したJEP 523は、この歴史的な分岐ロジックを全面的に廃止しました。コマンドラインでガベージコレクタが明示されていない場合、HotSpot JVMはCPUコア数やメモリ容量にかかわらず常にG1コレクタをデフォルトとして選択します。JEP 523の主目的は、従来のSerial GC選択環境においても、スループット、レイテンシ、メモリフットプリント、起動時間の著しい劣化を招くことなく現代的な世代別GCを提供することです。

また、JEP 523の非目標(Non-Goals)も明記されています。既存のSerial、Parallel、ZGCといったコレクタの非推奨化や削除は一切行われません。さらに、CLI引数で明示的にGCを指定した場合は、常にユーザーの指定が最優先されます。G1コレクタ自体のアルゴリズムや内部挙動パラメータが変更されたわけでもありません。

# Java 27の標準動作：環境を問わずG1 GCが自動選択される
java -jar application.jar

# 軽量コンテナで従来のシングルスレッドSerial GCを維持したい場合
java -XX:+UseSerialGC -jar application.jar

# バッチ処理等で高スループットなParallel GCを維持したい場合
java -XX:+UseParallelGC -jar application.jar

# 超低遅延な同時実行GCを明示的に選択する場合
java -XX:+UseZGC -jar application.jar

1vCPUや1792MB未満の軽量コンテナ環境でデフォルトGCがSerialからG1に切り替わることは、運用上非常に大きな影響を持ちます。Serial GCは停止時間中に単一スレッドで処理を行うためバックグラウンドのオーバーヘッドがほぼゼロでしたが、G1は並行マーキングスレッドや並行排他ワーカープールを常駐させるためです。

4. デフォルト変更の第2の柱 — JEP 534 コンパクトオブジェクトヘッダー標準適用

JDK 27におけるもう一つの重大なランタイム変更が、64ビット環境におけるオブジェクト構造を刷新したJEP 534(担当者: Roman Kennke氏)です。コンパクトオブジェクトヘッダーは、全64ビットアーキテクチャにおいてオブジェクトヘッダーの専有サイズを96ビット(12バイト)から64ビット(8バイト)へ標準的に縮小します。

従来の64ビットHotSpotでは、オブジェクトヘッダーは2つのネイティブワードで構成されていました。同期ロック状態やハッシュコード、GC世代年齢を保持する64ビットのMark Wordと、Metaspace内のクラスメタデータを指すKlass Wordです。圧縮クラスポインタ(Compressed Class Pointers)有効時、Klass Wordは32ビットを占有するため、合計96ビット(12バイト)となりました。しかし、64ビットJVMは8バイトアライメントを維持するため、フィールドを持たないオブジェクトであっても16バイトに切り上げられてメモリを消費していました。

コンパクトオブジェクトヘッダーは、Mark Word内の未使用上位ビット領域に圧縮クラスポインタを直接エンコードすることで、独立したKlass Wordを完全に取り除きました。その結果、Mark Word単体(64ビット、8バイト)の中にクラス情報と実行時メタデータがすべて収まるようになりました。JDK 24での実験的導入(JEP 450)、JDK 25での本機能化(JEP 519)を経て大規模な検証が行われ、JDK 27においてついにデフォルト有効化(Default)へと昇格しました。

# Java 27の標準動作：コンパクトオブジェクトヘッダー(64ビット)が自動適用される
java -jar application.jar

# JNIやプロファイラとの互換性のために従来の96ビットヘッダーに戻す場合
java -XX:-UseCompactObjectHeaders -jar application.jar

JEP 534では、旧来の96ビットヘッダーレイアウトが完全に削除されたわけではないと明記されています。問題が生じた場合は上記のように-XX:-UseCompactObjectHeadersで復元可能です。ヘッダーが4バイト削減されることで、オブジェクト数の多い大規模アプリケーションにおいてヒープ使用量の削減と同時に、CPUキャッシュ(L1/L2/L3)のデータ局所性(Data Locality)向上が期待されます。ただし、削減率はワークロードに依存するため公式ドキュメントに確定数値はありません。

5. コンテナインフラとの運用上の影響 — ヒープ計算とCPUスロットリング

現代のマイクロサービス環境において、JVMはベアメタルではなくKubernetesのPodやDockerコンテナ内で稼働することが一般的です。以前の記事「JVMはコンテナ境界をどう認識するか」で詳述した通り、JVMはコンテナのリソース制限を単に遵守するのではなく、Linuxのcgroup情報を解析してスレッド数やヒープサイズを自律的に決定します。

Java 27の2つのデフォルト変更は、このようなコンテナ制御メカニズムと密接に絡み合います。特にCPUが0.5や1.0、メモリが1GiB未満といった小さなPodでは以下の点に警戒が必要です。

  • CFS CPUクォータとG1バックグラウンドスレッド：Serial GCは単一スレッドで動作していたため、CPUクォータ超過によるスロットリングのリスクが極めて低く抑えられていました。しかしG1は並行マーキングスレッドを常時起動します。Podのデプロイ設定でCPU Limitが厳密に設定されている場合、GCマーキング時にCPU消費が突発的に跳ね上がり、CFSスロットリングによって応答遅延が急増する可能性があります。
  • コンパクトヘッダーによるヒープ密度の向上：ヘッダーが8バイトに縮小されたことで、同一のヒープ空間により多くのドメインオブジェクトを配置可能となり、小メモリコンテナでのメモリ枯渇圧力を緩和します。
  • ヒープ外ネイティブメモリとOOMKilledリスク：G1 GCは領域間の参照を追跡するためのRemembered Set(RSet)やカードテーブルなど、Serial GCよりも多くのネイティブメモリをヒープ外に割り当てます。-XmxをコンテナのメモリLimit値ギリギリに設定している場合、コンテナ全体のメモリ上限を超過してLinuxカーネルのOOM Killerに強制終了される危険が高まります。

したがって、小規模コンテナを運用するチームは、移行後にCPUスロットリングメトリクスとRSSメモリ推移を注意深く観察すべきです。遅延の平準化よりもリソースの最小化が要求される環境では、-XX:+UseSerialGCを明示的に指定することが依然として現実的な選択となります。

6. プレビューとインキュベータが意味する現実 — 531・532・533・537・538

JDK 27に収録された9件のJEPのうち、5件がプレビューおよびインキュベータに分類されています。OpenJDKの開発体系において、プレビューは機能の実装がほぼ完了しているものの、エコシステムからのフィードバックを得るために意図的に本番の標準仕様から隔離されている段階を指します。インキュベータはそれ以前の実験的APIです。

  • JEP 531 遅延定数(Lazy Constants、第3次プレビュー)：高コストなオブジェクトや設定値の初期化を、初回利用時まで安全かつロック不要で遅延させる機構を提供します。
  • JEP 532 基本データ型パターンマッチング(第5次プレビュー)：instanceofおよびswitch構文において、参照型だけでなくintやdouble等の基本データ型に対してもパターンマッチングを可能にします。
  • JEP 533 構造化並行性(第7次プレビュー)：非同期タスクのライフサイクルを単一のスコープとしてまとめ上げ、エラー処理とキャンセルを体系化します。
  • JEP 537 Vector API(第12次インキュベータ)：x64のAVXやAArch64のNEON/SVEといったSIMD並列演算をJavaから直接活用するためのAPIです。
  • JEP 538 暗号オブジェクトのPEMエンコーディング(第3次プレビュー)：X.509証明書や暗号鍵をサードパーティライブラリなしで標準的にPEM形式で変換・解析できるようにします。

これら5つの機能は、標準のコンパイルおよび実行オプションでは呼び出すことができず、明示的なフラグを必要とします。GeekNews等の技術コミュニティでは、Vector APIが第12次インキュベータに達するほど長期化している点や、値オブジェクト(Value Objects)を導入するProject Valhallaが本リリースに含まれなかったことに対する惜しむ声が上がっています。

7. 深層分析 — JEP 533 構造化並行性の進化と制約

構造化並行性(Structured Concurrency)は、仮想スレッド(Virtual Threads、JEP 444)の真価を引き出すために設計されたモダンな並行プログラミングモデルです。Alan Bateman氏、Viktor Klang氏、Ron Pressler氏によって執筆されたJEP 533は、JDK 27で第7次プレビュー(Seventh Preview)を迎えました。

従来のExecutorServiceによる非同期処理では、サブタスクが互いに無関係なスレッドで実行されるため、スレッドリーク(Thread Leak)やキャンセル遅延といった問題を内包していました。例えばユーザ情報取得と注文情報取得を並行実行した際、片方が例外で失敗しても、もう片方のタスクは背後で実行され続け、無駄なリソース消費や意図しない副作用を引き起こします。

JEP 533は、これらを単一の処理単位として束ねるStructuredTaskScopeを提供します。JDK 27における主な改修点は以下の通りです。

  • 型パラメータ R_X の追加：StructuredTaskScopeおよびJoinerインターフェースに、join()がスローしうる例外型を明示する第3の型パラメータR_Xが追加され、静的型安全性が強化されました。
  • open() 静的ファクトリの導入：UnaryOperatorを渡すことで、標準の結合ポリシーやスコープ設定を柔軟にカスタマイズ可能な新しいファクトリが導入されました。
  • Joinerファクトリの例外処理統一：allSuccessfulOrThrow()等の結合ファクトリが失敗時にExecutionExceptionを標準でスローするよう整理され、例外マッピング用の関数オーバーロードが提供されました。
  • 旧式APIの整理：従来のJoiner.awaitAll()が削除され、onTimeout()はタイムアウト原因を明確に保持するtimeout()メソッドへ移行しました。
// JEP 533 StructuredTaskScope の基本使用例 (プレビューAPI)
Response handle() throws ExecutionException, InterruptedException {
    try (var scope = StructuredTaskScope.open()) {
        StructuredTaskScope.Subtask<String> user = scope.fork(() -> findUser());
        StructuredTaskScope.Subtask<Integer> order = scope.fork(() -> fetchOrder());

        scope.join(); // 全サブタスクの完了または失敗を待機

        // サブタスクの結果を取得して合成
        return new Response(user.get(), order.get());
    }
}

このコードブロックは、try-with-resourcesを抜ける際に未完了のサブタスクが存在すれば自動的にキャンセルを発行し、スレッドリークを防止します。しかし第7次プレビューに至っても細部の設計見直しが継続している事実は、本APIがまだ標準仕様として固定されていないことを物語っています。

8. セキュリティ領域の2件 — JEP 527 耐量子ハイブリッド鍵交換とJEP 536 JFR匿名化

JDK 27に盛り込まれた2件の正式セキュリティ機能は、次世代暗号への備えと運用データの保護において極めて重要な役割を果たします。

JEP 527(TLS 1.3向け耐量子ハイブリッド鍵交換)：量子コンピュータの実用化により、RSAや楕円曲線暗号(ECC)に基づく公開鍵暗号基盤は危機に瀕しています。暗号化された通信を収集しておき、将来の量子計算機で復号する「今傍受し後で解読(Harvest Now, Decrypt Later)」の脅威に対し、JEP 527はTLS 1.3ハンドシェイクでハイブリッド鍵交換を標準サポートします。従来の古典暗号(ECDH)と格子暗号などの耐量子アルゴリズム(ML-KEM等)を組み合わせることで、双方が破られない限り安全性を維持します。

JEP 536(JFR In-Process Data Redaction — JFRデータのプロセス内編集)：Java Flight Recorder(JFR)は強力な診断ツールですが、ダンプファイル内にクエリ文字列、システムプロパティ、環境変数などの個人情報やトークンが含まれるリスクが指摘されていました。JEP 536は、データをディスクに書き出す前にJVMプロセス内部で事前定義されたルールに従い、機密データを自動的にマスキング・匿名化する機能を提供します。

特に見落とされやすいのは、コンテナのマニフェスト定義です。開発機では十分なリソースがあるためG1やコンパクトヘッダーがスムーズに動作しても、CPUクォータが極小に制限されたKubernetesノード上では予期せぬ停滞を招く場合があります。

10. 本番環境でプレビュー機能を有効化してはならない理由

構造化並行性(JEP 533)などの魅力的なAPIはコードを大幅に簡潔化するため、本番システムに先行導入したくなるケースがあります。しかし、プレビュー機能の本番利用は重大なリスクを孕んでいます。

# プレビュー機能を有効にしたコンパイル (本番バイナリでは禁止)
javac --release 27 --enable-preview MyApplication.java

# プレビュー有効化での実行
java --enable-preview -jar application.jar

プレビュー機能を本番で避けるべき理由は以下の3点に集約されます。

  • クラスファイルの後方互換性の欠如：--enable-previewでコンパイルされたクラスは、マイナーバージョンが65535として生成されます。このクラスは通常モードのJVMではロード自体が拒否されます。
  • 破壊的API変更の常態化：構造化並行性がJDK 25、26、27と進化する中でメソッド名やシグネチャが頻繁に変更されたように、次期バージョンでコードが動作しなくなる可能性が非常に高いです。
  • APMおよびバイトコード改変ツールとの衝突：ByteBuddy、cglib、Datadog等のエージェントツールがプレビュー仕様のバイトコードを正しくパースできず、クラッシュや監視不能を引き起こす危険性があります。

11. 確認できなかった事項

  • LTS(長期サポート)指定の有無：今回のOpenJDK公式告知(Mark Reinhold氏)では、JDK 27が主要ベンダーによってLTS版として指定されるか否かについて触れられていません。サポート期間は各ディストリビューション提供元の個別方針となります。
  • 次期JDK 28のリリース計画：半年後に予定されるJDK 28の開発スケジュールや組み込み候補となるJEPリストは公表されていません。
  • ワークロード別のコンパクトヘッダー確定削減率：JEP 534仕様書はヘッダーが96ビットから64ビットに縮小される事実を定めていますが、アプリケーション全体のヒープ削減率はデータ構造に依存するため、単一の公認数値は確認されていません。
  • Project Valhallaの正式合流時期：値オブジェクトを導入するProject ValhallaとVector API(JEP 537)の最終的な統合時期は、今回の公式発表では確定していません。
