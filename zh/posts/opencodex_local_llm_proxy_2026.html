opencodex — 在Codex中使用任意LLM的本地代理

将OpenAI Codex CLI从特定模型中解放，连接本地与第三方LLM — 厂商锁定回避、成本削减、隐私保护实用分析

2026-06-22 开发/基础设施

引言：如果想自由使用Codex

OpenAI Codex CLI是截至2026年6月在Terminal-Bench 2.1排行榜排名第一（83.4%）的强大终端AI编程代理。问题只有一个：仅限OpenAI模型。没有ChatGPT Plus（月费20美元）或Pro（月费200美元）订阅就无法使用。Claude、Gemini、DeepSeek、Ollama等本地/开源模型没有与Codex连接的途径。

解决这个问题的工具就是opencodex。这个在GeekNews上获得46分的项目可以用一句话描述：让Codex CLI、App和SDK能够使用任意LLM的本地代理。本文不是功能列表，而是从自身视角分析opencodex的工作原理、为何这种方法在技术上有效、与LiteLLM等替代方案相比处于什么位置，以及实际存在哪些风险。以下信息基于2026年6月。

1. 为何存在这个问题 — Responses API这道墙

1.1 Responses API的出现

OpenAI在2025年初引入了Responses API。这是比旧版Chat Completions API更针对多轮对话、工具调用（tool_calls）、推理token（reasoning tokens）和图像处理进行优化的接口。Codex CLI就是在这个Responses API之上构建的。代理循环中的工具调用、推理过程的token处理、流式响应都在Responses API中得到了优化。

1.2 其他提供商不懂Responses API

问题在于Anthropic的Claude、Google的Gemini、Ollama等大多数第三方LLM提供商都不支持Responses API，各有各的原生API格式。Anthropic用Messages API，Google用Gemini API，本地模型暴露Chat Completions兼容端点。Codex是"只会说Responses API的客户端"，而第三方提供商是"听不懂Responses API的服务器"。opencodex填补的就是这个协议鸿沟。

1.3 社区的呼声

openai/codex仓库的Issue #26「Support for local / other LLMs」展示了这一需求有多强烈。厌恶厂商锁定、担忧成本、不想把代码库发送给外部API的开发者从一开始就在要求这个功能。opencodex是社区直接解决OpenAI没有官方支持的这一需求的结果。

2. opencodex的工作原理 — 协议翻译器

opencodex的结构很简单：本地运行的翻译代理。

2.1 请求流程

Codex CLI / App / SDK
        │  (Responses API请求)
        ▼
   opencodex  (本地代理)
        │  (协议翻译)
        ▼
   目标LLM提供商
   (Claude / Gemini / DeepSeek / Ollama 等)

Codex发出Responses API请求，opencodex拦截后翻译成目标提供商的原生协议并转发。响应也以相反方向翻译后返回给Codex。从Codex的角度看，它始终在与Responses API端点通信，而实际上后端可以是任何模型。

2.2 五种协议适配器

适配器名称目标覆盖范围
anthropicClaude Messages API所有Anthropic模型（Claude 3.5/3.7等）
googleGemini APIGemini 2.0/2.5等Google模型
azure-openaiAzure OpenAI部署在Azure上的模型
openai-responsesOpenAI Responses直通OpenAI官方端点直接访问
openai-chatChat Completions兼容端点DeepSeek/GLM/Kimi/Qwen/Groq/OpenRouter/Ollama等40多个提供商

openai-chat适配器覆盖范围最广。任何暴露OpenAI Chat Completions兼容端点的提供商都可以使用。通过OpenRouter指定，可以在Codex中使用数百种模型。

2.3 双向功能转换

opencodex声称支持流式传输、工具调用、推理token和图像的双向翻译。这不是简单的文本中继，而是协议级翻译。Codex代理调用工具编辑文件或执行终端命令时，工具调用结构必须正确传递给目标模型，代理循环才能正常工作。

3. 安装与使用 — 三行命令搞定

前提条件只需Bun 1.1以上。之后三个命令完成：

npm install -g @bitkyc08/opencodex   # 或: bun install -g @bitkyc08/opencodex
ocx init    # 交互式设置：选择提供商、模型、API密钥
ocx start   # 作为后台服务启动代理

ocx init以交互方式配置提供商、模型和API密钥，并自动注入Codex CLI、TUI、App和SDK，无需手动编辑Codex配置文件。ocx start作为后台服务运行，并提供实时Web仪表板用于可视化请求流。MIT许可证开源项目。

4. 厂商锁定回避 — 为何重要

4.1 Codex CLI的结构性依赖

Codex CLI是Apache 2.0开源，但运行需要OpenAI订阅。工具本身是开放的，但驱动它的燃料（模型API）是锁定的。对开发者而言，这种依赖造成三个实质问题：①成本：Pro订阅（月200美元）对重度用户也是负担；②代码隐私：代码库经过OpenAI服务器；③缺乏模型选择权：即使有更适合特定任务的模型也无法使用。

4.2 opencodex打开的出口

在成本方面，切换到DeepSeek V3或Qwen等更便宜的OpenAI兼容提供商，可以用相同的Codex界面以更低的单价使用。通过Ollama连接本地模型，推理成本归属于硬件，每token边际成本趋近于零。在隐私方面，连接本地模型时代码不会外泄。在模型自由度方面，只需通过ocx init更改提供商，无需更改工作流程。

4.3 提供商无关设计的实用性

opencodex的核心价值不是"某个模型表现更好"，而是模型选择成为配置参数而非永久架构决策。这与LiteLLM在代码层实现的LLM抽象哲学相同，只是应用到了工具层。随着更好更便宜的模型不断涌现，切换成本趋近于零。

5. 与LiteLLM的比较 — 层次不同的工具

5.1 LiteLLM的角色

LiteLLM（v1.83.8，MIT）是将100多个提供商统一为OpenAI Chat Completions格式的Python SDK和网关代理，用于自己开发的应用程序代码。这是在SDK级别的抽象。2026年3月发生了供应链安全事件，团队公开了详情并进行了修复，目前仍是使用最广泛的开源LLM网关。

5.2 opencodex的角色

opencodex是针对Codex这个现有工具调用LLM时的抽象。你无法修改Codex的代码，但可以通过代理改变其行为。两者解决的是不同层次的问题。

5.3 组合使用场景

两者可以组合使用。将opencodex的openai-chat适配器端点指向LiteLLM代理服务器地址，就能实现opencodex → LiteLLM → 100多个提供商的链式连接，在Codex中访问LiteLLM支持的所有模型。

6. 类似项目与生态系统

6.1 codex-relay

用Rust编写的轻量级代理，专门将Responses API翻译为Chat Completions API。功能比opencodex更聚焦，但Rust的性能特性使其在高吞吐量场景中具有优势。

6.2 OpenCode — 另一条路

截至2026年6月拥有168,000多个GitHub星的OpenCode是原生支持75多个LLM提供商的开源CLI代理，可作为Codex CLI的完整替代方案。对Codex界面没有特殊执念的团队，直接替换工具可能是更简洁的长期选择。opencodex适合"想保留Codex工作流但只换模型后端"的团队。

7. 风险与注意事项 — 诚实评估

7.1 服务条款风险

opencodex作者本人发出的警告：「一些提供商——尤其是Anthropic（Claude）——可能会暂停或限制通过第三方代理路由API流量的账户。使用风险自担（Use at your own risk）。」必须事先确认每个提供商的服务条款。通过opencodex连接Claude时，需要意识到账户风险。

7.2 协议转换完整性

协议翻译并不总是完整的。当Codex请求目标模型不支持的功能（如特定格式的推理token）时，翻译可能不完整或功能丢失。务必在实际工作负载中验证代理循环的行为。

7.3 维护持续性

社区项目的固有风险：若OpenAI更改Responses API架构或Codex更新内部协议，opencodex适配器也需要更新。没有官方支持保证。在生产工作流采用前，请评估维护者的活跃程度。

8. 适合哪类开发者

8.1 适合的情况

已在Codex CLI工作流中有大量投入、只想更换模型的团队。需要代码隐私的环境（通过Ollama连接本地模型，代码不会外泄）。重度Codex用户且以成本优化为目标：连接更便宜的Chat Completions兼容提供商可大幅降低每token费率。

8.2 不适合的情况

使用Claude Code、Cline或OpenCode的团队（opencodex与非Codex工作流无关）。想连接Anthropic Claude但希望规避服务条款风险的情况。从零开始构建且需要多提供商支持的团队：选择原生支持多提供商的OpenCode，比给Codex增加代理复杂度更简洁。

9. 结论 — 协议抽象创造自由

opencodex不是华丽的工具，但其简洁性正是核心所在。它在Codex只能说Responses API而第三方提供商使用不同语言这个间隙中，精准地插入了翻译器。这个想法本身并不新颖——是将LiteLLM在代码层做的事情在工具层重复了一遍。新颖的是执行：三行安装、五种适配器、仪表板、MIT许可证。

2026年6月，AI编程工具市场的核心张力之一是开源工具与商用模型依赖的矛盾。Codex CLI是Apache 2.0，但没有OpenAI订阅实际上毫无意义。opencodex将这种张力缓解了一步。并不能完全消除——服务条款风险、翻译完整性的限制、维护不确定性依然存在。但这是社区秉持「我们使用的工具的自由由我们自己保护」理念所创造的成果的好例子。
