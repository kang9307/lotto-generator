서론: 22분간 일어난 일 - npm 생태계의 시한폭탄

2026년 5월 19일(UTC 기준 새벽) npm에서 메인테이너 계정 하나가 탈취되어, 그 계정이 관리하던 패키지 300여 개에 637개의 악성 버전이 약 22분 사이에 자동으로 게시된 사건이 보고되었습니다. 패키지 수는 보도에 따라 314개(The Register) 또는 317개(SafeDep 분석)로 조금 다릅니다. 분 단위로 환산하면 1분에 약 29개의 악성 버전이 올라간 셈이고, 사람 손으로는 낼 수 없는 속도라 자동화 스크립트로 일괄 게시한 것으로 봅니다. 22분이라는 짧은 시간과 계정 하나가 수백 개 패키지를 좌우한다는 사실이 이번 사건의 핵심이며, 자바스크립트 생태계가 메인테이너 자격증명이라는 단일 실패점에 얼마나 노출되어 있는지를 보여 줍니다.

이번 사건은 단발성 이슈가 아닙니다. 이 글에서 정리하듯 npm은 2018년 event-stream, 2021년 ua-parser-js, 2022년 colors/faker, 2024년 lottiefiles, 2025년 9월 Shai-Hulud 웜까지 거의 매년 대형 공급망 사고를 겪었습니다. SafeDep 분석에 따르면 이번 악성 코드는 약 3주 전 SAP 관련 npm 패키지 침해에 쓰인 Mini Shai-Hulud 도구와 같은 계열입니다. 영향받은 패키지에는 size-sensor(월 약 420만 다운로드), echarts-for-react(약 380만), @antv/scale(약 220만), timeago.js(약 115만)처럼 다른 라이브러리의 의존성으로 깊이 들어가 있는 것이 많아, 그 이름을 들어본 적이 없어도 영향을 받을 수 있습니다.

이 글은 사건 사실관계를 발견·분석 보고와 GitHub·npm 공식 공지로 확인한 뒤, 한국 개발자·팀이 오늘 안에 해야 할 응급 조치 4가지와 장기 방어 전략 7가지를 정리합니다. 사건 자체의 기술적 디테일보다 한국 환경에서 바로 적용할 수 있는 행동에 초점을 둡니다. 2026-09-29에 1차 출처와 다시 대조해 사실관계를 바로잡고 이후 경과를 덧붙였습니다.

사건 개요 - 무엇이, 언제, 어떻게 일어났나

공개된 분석과 보도로 확인되는 사건 윤곽은 다음과 같습니다. 보안 advisory를 직역하지 않고, 이 글이 확인한 사실만 다시 정리했습니다.

  • 시점: 2026년 5월 19일 UTC 01시 39분께 시작. SafeDep은 01:39~01:56과 02:05~02:06 두 차례의 물결로 나눠 기록했고, 보도는 약 22분의 일괄 게시로 요약합니다.
  • 규모: 악성 버전 637개. 패키지 수는 314개(The Register)~317개(SafeDep). @antv 범위의 패키지 다수와 size-sensor, echarts-for-react, timeago.js 등이 포함됩니다.
  • 침해 경로: 여러 메인테이너의 토큰이 아니라, AntV 관련 패키지 500여 개(SafeDep 집계 547개)를 관리하던 메인테이너 계정 하나. 그 계정이 어떻게 탈취되었는지는 공개 분석에서 밝혀지지 않았습니다.
  • 악성 코드 성격: postinstall이 아니라 preinstall 훅에서 약 498KB의 난독화된 Bun 스크립트를 실행. 클라우드(AWS·GCP·Azure) 자격증명, GitHub·npm 토큰, SSH 키, Kubernetes·Vault 토큰, DB 연결 문자열 등을 수집해 공격자가 만든 GitHub 공개 저장소와 외부 서버로 빼돌립니다.
  • 탐지·보고: 한 보안 연구자가 GitHub에 처음 보고했고, SafeDep이 상세 분석을 공개했습니다(The Register 보도).
  • 대응: 일부 버전은 「실수로 게시되었다」는 메시지와 함께 deprecate되고 일부는 삭제되었습니다. GitHub는 상황을 모니터링하며 이용 정책에 따라 악성 npm 패키지를 비활성화하고 있다고 밝혔습니다.

주목할 점은 "22분"이라는 짧은 윈도입니다. 이 시간이 의도적으로 설계된 것인지는 확인되지 않았습니다. 다만 짧은 시간에도 시맨틱 버전 범위(^, ~)로 의존성을 받는 CI 파이프라인은 그 사이 새 버전을 그대로 받아 설치할 수 있었다는 점에서, 탐지 속도보다 설치 시점의 게이트가 더 중요하다는 것을 보여 줍니다.

공격 메커니즘 분석 - 자격증명 침해 + 자동화 일괄 배포

이번 사건의 기술적 핵심은 화려한 zero-day가 아니라 "훔친 자격증명 + 자동화"라는 평범한 조합입니다. 평범하다는 것이 핵심입니다. 화려한 취약점이 필요 없을 만큼, 계정 하나가 수백 개 패키지의 게시 권한을 쥐고 있는 npm의 인증·게시 모델이 단일 실패점이 된다는 뜻이기 때문입니다.

1) 계정 탈취 단계

공개 분석은 계정이 어떤 경로로 탈취되었는지 밝히지 않았습니다. 일반적으로 npm 계정 탈취 경로로는 피싱, 메인테이너 PC 악성코드, 과거 유출된 토큰 재사용, .npmrc 파일 누출 등이 거론됩니다. 이번 악성 코드 자체가 npm 토큰과 GitHub 토큰을 수집한다는 점에서, 한 번의 감염에서 흘러나온 토큰이 다음 침해의 열쇠가 될 수 있다는 점은 분명합니다. 또 2FA를 켜 두었어도 2FA 우회용 토큰이 노출되면 공격자가 계정을 장악할 수 있었다는 점은 GitHub도 공지에서 인정한 문제입니다(이후 경과 참고).

2) 일괄 배포 단계 (22분의 윈도)

게시 권한을 가진 계정 하나를 손에 넣으면, 사전 준비한 악성 변종을 그 계정의 패키지에 차례로 publish하는 것은 어렵지 않습니다. npm publish를 자동화로 호출하면 분당 수십 개 게시도 가능하고, 22분 안에 637개 버전이 올라간 점은 이와 맞아떨어집니다.

3) 페이로드 실행 단계 (피해자 측)

악성 버전은 preinstall 훅에서 Bun 런타임으로 스크립트를 실행합니다. SafeDep은 설치 훅을 막더라도 github: 형식의 선택적 의존성으로 GitHub 커밋을 끌어오는 두 번째 경로가 있었다고 분석했습니다. 또 감염된 PC에서 AI 코딩 도구·에디터 설정 파일(.claude/settings.json, .vscode/tasks.json)에 자동 실행 항목을 심고 상주 서비스를 설치해, 한 번의 설치가 같은 PC의 다른 작업 공간까지 번지도록 했습니다. 한국 기업 환경에서 이 단계의 위협은 두 가지로 갈립니다. (a) 로컬 개발 PC 침해: 개발자가 무심코 npm install을 실행한 뒤 토큰·키 유출과 상주 백도어. (b) CI/CD 침해: GitHub Actions나 사내 Jenkins에서 빌드 시점 시크릿이 외부로 유출. CI 토큰은 권한 범위가 넓은 경우가 많아 이 글은 후자를 더 위험하게 봅니다.

유사 사건의 역사 - 같은 구조가 반복된다

npm 공급망 공격은 처음이 아닙니다. 대표적인 사건을 정리하면 다음과 같습니다.

  • 2018 event-stream: 메인테이너 교체 직후 새 메인테이너가 악성 페이로드를 끼워 넣어 비트코인 지갑 관련 프로젝트를 노린 사건. "신뢰의 양도"가 단일 실패점이라는 사실을 처음으로 대중에게 보여 줬습니다.
  • 2021 ua-parser-js: 메인테이너 계정 침해 후 악성 버전 배포. 다운로드 수가 매우 많은 패키지라 영향 범위가 넓었습니다.
  • 2022 colors/faker: 메인테이너 자신이 의도적으로 코드를 망가뜨린 사건. "신뢰는 자발적 협력"이라는 사실을 다시 환기했습니다.
  • 2023 typosquatting 다수: 인기 패키지 이름과 철자가 비슷한 악성 패키지가 대량 등록되었습니다.
  • 2024 lottiefiles 등: SDK 패키지 침해를 통해 사용자 지갑 정보를 노린 사건.
  • 2025년 9월 Shai-Hulud: 탈취한 메인테이너 계정으로 설치 스크립트를 심고 스스로 퍼지는 웜. GitHub 발표 기준 500개 이상 패키지가 침해되었고, 이를 계기로 GitHub가 npm 인증·토큰 강화 계획을 내놓았습니다.
  • 2026년 5월 이번 사건: 규모는 2025년 Shai-Hulud보다 작지만, 같은 계열 도구(Mini Shai-Hulud)가 몇 주 간격으로 재사용되고 있다는 점이 새롭습니다.

이 목록의 패턴은 명확합니다. 매번 "메인테이너 자격증명"이 깨지고, 매번 같은 방식으로 레지스트리가 게시를 허용합니다. 사건마다 임시 대응은 있지만 구조적 해결책은 도입이 느립니다. provenance·sigstore·trusted publishing 같은 장기적 해법이 등장했지만, 모든 패키지에 퍼지기까지는 시간이 걸립니다.

왜 npm은 반복적으로 공격받는가 - 구조적 취약점 5가지

1) 단일 메인테이너 모델

npm 패키지 상당수가 1~2명의 메인테이너로 운영됩니다. 이 한 명의 자격증명이 깨지면 수백만 다운로드짜리 패키지가 그대로 노출됩니다. 이번 사건처럼 한 계정이 수백 개 패키지 권한을 가진 경우에는 피해가 한꺼번에 번집니다. PyPI, crates.io 등 다른 레지스트리도 비슷한 구조지만, 작은 패키지를 잘게 나눠 쓰는 npm 문화는 영향을 키우기 쉽습니다.

2) 깊은 의존성 트리

프로젝트가 직접 의존하는 패키지가 10개여도, 간접 의존성까지 펼치면 실제 설치되는 패키지는 훨씬 많아집니다. npm ls --all로 직접 세어 보면 차이를 알 수 있습니다. 들어본 적도 없는 패키지가 빌드 환경에서 임의 코드를 실행할 수 있다는 뜻입니다.

3) 설치 스크립트의 임의 코드 실행

npm은 설치 과정에서 preinstall·install·postinstall 스크립트를 실행할 수 있습니다. 정상 용도(네이티브 빌드 등)도 있지만, 공격자에게는 페이로드 자동 실행 통로가 됩니다. 다른 패키지 매니저 중 일부는 이 훅을 기본 비활성화로 둡니다. 발행 당시 npm은 기본 실행이었으나, 2026년 7월 npm v12부터 의존성의 설치 스크립트가 기본 차단으로 바뀌었습니다(이후 경과 참고).

4) 메인테이너 신뢰 양도의 무방비

메인테이너가 다른 사람에게 패키지를 넘기는 절차는 가볍습니다. 새 메인테이너의 신원·이력·악의 여부에 대한 검증이 약하고, 사용자가 자동으로 알 수 있는 방법도 없습니다.

5) provenance 채택의 더딘 속도

npm provenance는 2023년 도입되었지만 모든 패키지가 쓰는 것은 아닙니다. provenance는 패키지가 어느 CI 워크플로에서 빌드되었는지를 증명할 뿐 코드가 안전하다는 보증은 아니며, CI 워크플로 자체가 침해되면 악성 빌드에도 provenance가 붙을 수 있습니다. 그래도 탈취한 토큰으로 개인 PC에서 게시한 버전과 정상 CI에서 게시한 버전을 구분하는 신호가 되므로, 채택이 넓어질수록 이번 같은 사건의 표면은 줄어듭니다.

오늘 안에 해야 할 4가지 응급 조치

이 섹션은 이 글에서 가장 실무에 가까운 부분입니다. 한국 개발팀이 오늘(늦어도 이번 주) 안에 처리해야 할 것 4가지입니다.

1) 의심 패키지 즉시 확인 - npm audit

가장 먼저 모든 활성 프로젝트에서 다음을 실행합니다.

npm audit --audit-level=high
npm audit signatures   # 레지스트리 서명·provenance 검증
npm outdated

npm audit signatures는 의외로 덜 알려진 명령으로, 내려받은 패키지의 레지스트리 서명과 provenance 증명을 검증합니다. 사건 시점(5월 19일) 전후에 받은 패키지가 있다면 이 명령으로 한 번 더 확인합니다.

2) lock 파일 변경 이력 검증

package-lock.json 또는 yarn.lock의 최근 변경과 영향 패키지 포함 여부를 확인합니다.

git log --since="2026-05-18" -- package-lock.json
grep -nE "size-sensor|echarts-for-react|timeago\.js|@antv/" package-lock.json

의심 시점에 lock 파일이 변경되었거나 영향 패키지가 트리에 있다면, 그 버전이 정상인지 GitHub Security Advisories와 발견 업체의 영향 목록과 대조합니다. 한 명의 개발자가 무심코 npm install 후 lock 파일을 같이 커밋하는 경우가 있기 때문에 PR 단위 점검이 필요합니다.

3) 빌드 캐시 즉시 무효화

로컬·CI·사내 npm 미러에 캐시된 악성 버전을 제거합니다.

npm cache clean --force
rm -rf node_modules
npm ci   # lock 파일 기준 깨끗한 재설치

GitHub Actions의 actions/cache, GitLab CI cache, 사내 Nexus/Verdaccio 미러도 같이 무효화합니다. 캐시에 악성 버전이 남아 있으면 응급 조치 의미가 사라집니다.

4) 노출 가능성 있는 토큰·시크릿 즉시 로테이션

이번 페이로드의 주 표적은 환경 변수·설정 파일 속 토큰과 키입니다. 다음 항목을 5월 19일 이후 영향 버전이 설치된 환경에 한 번이라도 두었다면 로테이션합니다.

  • npm publish 토큰 (CI에서 사용 중인 경우 최우선)
  • GitHub PAT·Actions 토큰
  • AWS·GCP·Azure 액세스 키
  • SSH 키·Slack 토큰·웹훅 URL
  • DB 연결 문자열·내부 API 시크릿

토큰 교체와 함께 SafeDep이 권고한 흔적도 확인합니다. 개발자 GitHub 계정에 모르는 공개 저장소가 생기지 않았는지, .claude/settings.json·.vscode/tasks.json에 낯선 자동 실행 항목이 없는지, 모르는 상주 서비스가 등록되지 않았는지 봅니다. 토큰만 바꾸고 상주 프로그램을 남겨 두면 새 토큰도 다시 새어 나갑니다.

장기 방어 전략 7가지 - 다음 사건을 막는 시스템

1) trusted publishing과 npm provenance 사용

npm에 패키지를 게시한다면 장기 토큰 대신 trusted publishing(OIDC)으로 옮깁니다. npm 문서 기준 npm CLI 11.5.1 이상, Node 22.14.0 이상이 필요하고, GitHub Actions에서는 permissions: id-token: write를 줍니다. GitHub Actions·GitLab CI/CD에서 trusted publishing으로 게시하면 provenance가 기본으로 자동 생성됩니다. 설정 뒤에는 패키지 설정에서 「Require two-factor authentication and disallow tokens」로 토큰 게시를 막을 것을 npm이 강하게 권합니다. 사용자 측에서는 npm audit signatures로 서명과 provenance를 검증할 수 있습니다.

2) Frozen lockfile 강제 (--frozen-lockfile / npm ci)

로컬에서 npm install을 쓰더라도, CI에서는 반드시 npm ci 또는 yarn install --frozen-lockfile을 강제합니다. lock 파일과 일치하지 않으면 빌드가 실패하도록 게이트를 두는 것이 핵심입니다. 이 한 가지만으로 "밤사이 누군가 새 버전을 publish해서 빌드가 그것을 가져가는" 경로가 거의 차단됩니다.

3) SBOM 생성·관리

매 빌드마다 SBOM(Software Bill of Materials)을 자동 생성해 저장합니다. 형식은 CycloneDX 또는 SPDX. @cyclonedx/cyclonedx-npm 같은 도구로 쉽게 도입할 수 있습니다. SBOM이 있으면 다음 사건이 터졌을 때 "우리가 그 패키지를 쓰는지"를 빠르게 답할 수 있습니다.

4) Dependabot / Renovate 도입

의존성 갱신을 사람의 의지가 아니라 자동 PR로 만듭니다. 단, 자동 머지는 켜지 않습니다. PR을 만들면 사람이 검토하는 절차가 강제됩니다. 검토 시 npm view로 최신 버전의 메인테이너·publish 시각·다운로드 추이를 한 번 확인합니다.

5) 정기 의존성 감사 사이클

분기에 한 번 의존성 감사 미팅을 둡니다. 안건은 세 가지입니다. (a) 안 쓰는 패키지 제거, (b) deprecated 패키지 교체, (c) 메인테이너 활동이 멈춘 패키지의 fork·교체 검토. 이 한 시간이 사고가 났을 때 영향 범위를 가려내는 시간을 크게 줄여 줍니다.

6) 미니멀 의존성 정책

"이 기능을 위해 100줄짜리 패키지를 추가할 가치가 있는가"를 PR 리뷰 단계에서 의무 질문으로 둡니다. 좌표 계산·문자열 유틸·날짜 포맷 같은 작은 기능은 직접 작성한 코드 10~30줄로 충분한 경우가 많습니다. 의존성이 적을수록 공격 표면이 작습니다.

7) 행위 기반 스캐너 (Socket.dev 등) 도입

전통적 npm audit은 알려진 advisory와 대조하지만, Socket.dev 같은 도구는 패키지 코드의 의심 행위(네트워크 호출, eval, 설치 스크립트 패턴 등)를 행위 기반으로 탐지합니다. 알려지지 않은 신규 침해를 잡을 가능성이 높아집니다. 발행 당시 함께 꼽은 Phylum은 2025년 1월 Veracode가 기술을 인수해 Veracode 제품군으로 들어갔습니다. CI에 PR comment 형태로 통합하는 것이 한국 팀 기준 가장 부드러운 도입 방식입니다.

CI/CD 파이프라인 강화 - GitHub Actions 예시

위 7가지 전략을 실제 GitHub Actions 워크플로로 묶으면 다음과 같은 형태가 됩니다. 핵심 게이트만 발췌한 예시이며, Node 20은 2026년 4월 지원이 끝났으므로 LTS인 24로 바꿨습니다. id-token: write는 게시(publish) 작업에만 주고 일반 빌드에서는 빼는 편이 안전합니다.

name: secure-build
on: [push, pull_request]
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: 'npm'

      # 1) frozen lockfile - lock과 불일치 시 즉시 실패
      - run: npm ci

      # 2) audit 게이트
      - run: npm audit --audit-level=high
      - run: npm audit signatures

      # 3) SBOM 생성
      - run: npx @cyclonedx/cyclonedx-npm --output-file sbom.json
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

      # 4) 행위 기반 스캔 (Socket.dev 예시)
      # - uses: socket-security/socket-cli-action@v1

      - run: npm test
      - run: npm run build

이 워크플로의 핵심은 "한 단계라도 실패하면 빌드 자체가 중단"이라는 점입니다. 응급 조치를 사람 의지에 맡기지 않고 CI 게이트로 시스템화하는 것이 이 글의 마지막 핵심 메시지입니다.

모니터링 도구 비교 - Snyk, Socket.dev, Phylum, npm audit

실무에서 자주 비교되는 도구를 정리합니다.

도구탐지 방식강점약점

한국 팀의 권장 조합은 다음과 같습니다. (1) 기본은 npm audit + Dependabot(무료, 즉시 도입). (2) 그 위에 Socket.dev 또는 Snyk 중 하나를 PR 리뷰 단계 보조 게이트로. (3) 여유가 있다면 Veracode(구 Phylum 기술) 같은 악성 패키지 차단 계층까지 더하는 3단 구성을 권합니다.

한국 기업·스타트업 환경에서의 적용

위 전략을 한국 환경에 옮길 때 자주 거론되는 마찰 지점을 정리합니다.

  • 스타트업: 보안 인력이 없는 경우가 많습니다. 무료 도구(npm audit, Dependabot, Socket.dev 무료 티어)만으로도 상당 부분을 막을 수 있으므로 일단 도입부터 합니다. 완벽을 추구하지 말고 "안 하던 것을 한다"를 목표로.
  • 중견·대기업: 사내 npm 미러(Nexus, Verdaccio)가 있다면 미러 자체에 allowlist·블록리스트를 적용합니다. 응급 사건 시 미러에서 차단하는 것이 모든 개발자에게 동시에 효과를 미칩니다.
  • 금융·공공: 망분리 환경이라도 npm 미러를 통해 외부 패키지를 들여오는 경로는 동일합니다. SBOM·서명 검증을 사내 표준으로 만드는 것이 효과적입니다.
  • 프리랜서·1인 개발: 개발자 PC가 곧 인프라입니다. 토큰을 평문으로 .env에 두는 습관을 즉시 버리고, 1Password CLI·doppler 같은 시크릿 매니저를 도입합니다.

개발자 개인 책임의 한계와 생태계 책임

이 글에서 정리한 11가지(응급 4 + 장기 7)를 모두 실행해도 공급망 공격은 100% 막지 못합니다. 그것이 현실입니다. 개인·팀 단위 노력의 한계가 분명히 있고, 그 한계를 넘는 것은 생태계 수준의 변화입니다.

발행 당시 이 글이 꼽은 생태계 책임은 세 가지였습니다. (1) npm(GitHub)의 메인테이너 인증 강화 - WebAuthn·하드웨어 키 의무화. (2) provenance 채택률을 끌어올리기 위한 인기 패키지 대상 인센티브. (3) 설치 스크립트의 기본 비활성화. 이 가운데 세 번째는 2026년 7월 npm v12에서 기본값이 되었고, 첫 번째 방향(2FA 우회 토큰 제한, trusted publishing 전환)도 단계적으로 진행 중입니다. 자세한 날짜는 이후 경과 절에 정리했습니다.

# npm 공급망 침해 뉴스를 볼 때 확인할 것 - 점검표

기준일: 2026-09-29 (SafeDep 분석, The Register 보도, GitHub Changelog·npm Docs 기준)

일반 정보입니다. 영향 버전과 권고는 발견 업체의 분석과 GitHub Security Advisories가 갱신되면 바뀔 수 있으니, 실제 조치 전에 최신 목록과 대조하십시오.

---

## 1. 이 사안을 볼 때 확인할 것

| 확인할 것 | 왜 보나 | 2026년 5월 사건에서 확인된 예 |
|---|---|---|
| 정확한 날짜와 시각(UTC)이 있는가 | 「5월 중순」만으로는 lock 파일·빌드 로그를 대조할 수 없다 | 2026-05-19 UTC 01:39께 시작, 두 물결(01:39~01:56, 02:05~02:06) |
| 숫자의 출처가 어디인가 | 보도마다 패키지 수가 다르면 어느 쪽이 1차 분석인지 가려야 한다 | 악성 버전 637개, 패키지 314개(The Register)~317개(SafeDep) |
| 계정 하나인가, 여러 개인가 | 침해 범위와 대응(한 계정 권한 정리 vs 생태계 전반)이 달라진다 | 500여 개 패키지를 관리하던 메인테이너 계정 하나 |
| 어떤 훅으로 실행되는가 | preinstall·postinstall·github: 의존성마다 막는 방법이 다르다 | preinstall 훅에서 Bun 스크립트 실행, github: 선택적 의존성 경로도 존재 |
| 무엇을 가져가는가 | 로테이션할 비밀의 범위를 정한다 | 클라우드 자격증명, GitHub·npm 토큰, SSH 키, Kubernetes·Vault 토큰, DB 연결 문자열 |
| 상주 흔적을 남기는가 | 토큰만 바꾸면 다시 새어 나갈 수 있다 | `.claude/settings.json`·`.vscode/tasks.json` 자동 실행 항목, 상주 서비스 |
| 레지스트리는 어떻게 대응했는가 | 「삭제됨」과 「deprecate됨」은 다르다 | 일부 deprecate, 일부 삭제. GitHub가 악성 패키지 비활성화 중이라고 밝힘 |
| 정책 변경이 이 사건 때문이라고 공식 발표했는가 | 시기가 겹친다고 인과가 있는 것은 아니다 | 이후 GitHub 공지들은 이 사건을 직접 언급하지 않음 |
