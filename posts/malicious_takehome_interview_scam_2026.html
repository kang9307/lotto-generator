가짜 채용 과제에 숨은 악성코드 - LinkedIn 인터뷰 사기가 개발자를 노리는 법

정상 코딩 과제로 위장한 비공개 저장소 하나가 PC·지갑·자격증명을 통째로 넘길 수 있다 - 수법과 실전 방어 수칙

2026-07-18 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 이력서 대신 악성코드를 받는 시대

LinkedIn 메시지 하나로 시작한다. 낯선 회사의 채용 담당자가 매력적인 포지션을 제안하고, 절차의 일부로 take-home 코딩 과제를 비공개 GitHub 저장소로 보내온다. 지원자 입장에서 이것은 지극히 익숙한 흐름이다. 실제로 많은 회사가 이런 방식으로 실무 역량을 평가하기 때문에, 의심할 이유가 딱히 없어 보인다.

문제는 이 익숙함 자체가 공격 표면이라는 데 있다. 2026년 들어 보안 업계가 반복적으로 경고하는 패턴은, 정상적으로 보이는 React·Web3 프런트엔드 과제 안에 난독화된 악성코드를 심어 지원자의 PC와 지갑을 탈취하는 캠페인이다. 실제 사고 사례를 보면, 겉보기엔 지갑 연결 UI를 개선하는 평범한 NFT 플랫폼 과제였지만, 개발자가 거의 열어보지 않는 빌드 설정 파일 뒤에 3만 바이트가 넘는 악성 코드 블록이 이어 붙어 있었다. 이 글은 그 수법을 해부하고, 겁주기가 아니라 오늘 바로 적용할 수 있는 방어 수칙을 정리하는 데 초점을 맞춘다. 2026년 7월 기준으로 정리했다.

1. 공격 수법 - 신뢰 형성에서 코드 실행까지

이런 공격이 통하는 이유는 기술이 아니라 사회공학(소셜 엔지니어링) 설계에 있다. 단계별로 뜯어보면 각 단계가 왜 의심을 피해 가는지 보인다.

1.1 접근 - 그럴듯한 채용 담당자

공격자는 LinkedIn에 실제와 유사한 프로필을 만들고, 실존하거나 그럴듯하게 지어낸 회사명을 내세워 개발자에게 먼저 연락한다. 블록체인·핀테크·AI 스타트업을 사칭하는 경우가 특히 많다고 보고된다. 대화는 정상적인 채용 절차처럼 흘러간다. 역할 소개, 화상 통화 일정, 그리고 자연스러운 다음 단계로서의 과제 안내까지 - 진짜 채용 과정과 구분하기 어렵다.

1.2 신뢰 굳히기 - 진짜 동작하는 과제

여기가 핵심이다. 전달되는 저장소는 대충 만든 미끼가 아니라 실제로 빌드되고 동작하는 프로젝트다. 지갑 연결 UI 개선처럼 구체적이고 현실적인 작업 지시가 딸려 있고, 코드 품질도 평범한 실무 수준이다. 그래서 지원자는 물론 코드를 검토하는 AI 코딩 에이전트조차 이상 신호를 놓치는 경우가 보고됐다. 겉으로 정상인 프로젝트가 신뢰를 대신 벌어 주는 셈이다.

1.3 실행 유도 - 설치가 곧 감염

마지막 단계는 지극히 평범한 요청이다. `npm install`이나 `yarn install`, 그리고 개발 서버 실행을 요청받을 뿐이다. 별다른 승인이나 관리자 권한 요청 없이도, 이 한 번의 설치·실행만으로 감염이 시작될 수 있다. 지원자는 자신이 코딩 과제를 수행하고 있다고 믿지만, 실제로는 공격자가 설계한 실행 체인을 그대로 따라간 것이다.

2. 왜 개발자가 특히 표적인가

같은 수법이 일반 사무직보다 개발자에게 특히 잘 통하는 데는 구조적인 이유가 있다.

2.1 코드 실행이 업무의 자연스러운 일부

일반 직군이라면 낯선 실행 파일 하나에도 경계하지만, 개발자에게 낯선 저장소를 클론하고 설치·빌드·실행하는 일은 하루 일과 그 자체다. 경계심이 구조적으로 낮을 수밖에 없다.

2.2 이미 확장돼 있는 의존성 신뢰

npm·PyPI 같은 패키지 생태계는 하나의 설치 명령으로 수백 개의 하위 의존성을 자동으로 내려받고, 그 안에 정의된 스크립트를 별도 확인 없이 실행하는 구조다. 개발자는 이미 이 자동 실행 체인을 신뢰하고 있고, 공격자는 그 신뢰의 사슬 어딘가에 한 조각만 끼워 넣으면 된다.

2.3 지갑·자격증명을 동시에 보유

개발자, 특히 Web3·블록체인 개발자의 업무용 PC에는 소스코드뿐 아니라 SSH 키, 클라우드 자격증명, API 토큰, 때로는 실제 자산이 든 암호화폐 지갑까지 한 기기에 모여 있다. 코드 실행 한 번이 개인 자산과 회사 인프라 접근권을 동시에 넘겨줄 수 있다는 뜻이다.

3. 악성 페이로드가 숨는 곳

실제 확인된 사고를 보면 은신처는 놀라울 만큼 평범한 곳이다. 어디를 특히 의심해야 하는지 정리한다.

3.1 설정 파일도 코드다

Tailwind·Webpack·ESLint 같은 빌드·설정 파일은 코드 리뷰에서도 가장 가볍게 훑고 지나가는 부분이다. 실제 사고 사례에서는 정상적인 설정 97줄 뒤에 3만 바이트가 넘는 난독화 코드 블록이 이어 붙어 있었는데, 에디터 화면상으로는 짧은 파일처럼 보였다. 파일 크기와 실제 표시 줄 수가 어긋나는 것 자체가 강력한 위험 신호다. 보안 연구자들이 공통으로 짚는 원칙은 명확하다 - 「설정 파일도, 의존성도, 빌드 도구도 모두 코드」라는 것이다.

3.2 postinstall 훅과 의존성 체인

package.json의 `preinstall`/`install`/`postinstall` 같은 라이프사이클 훅은 패키지 설치 시점에 사용자 확인 없이 자동 실행된다. 정상 패키지도 네이티브 모듈 컴파일 등에 이 훅을 쓰지만, 공격자에게는 임의 코드를 조용히 실행시키는 통로가 된다. 여기에 악성 패키지를 의존성 체인 깊숙이 끼워 넣으면, 최상위 package.json만 봐서는 알아채기 어렵다.

3.3 실행 이후 - 2차 페이로드

초기 코드는 대개 본체가 아니라 드로퍼다. 실행되면 외부 서버에서 암호화된 2차 페이로드를 받아 복호화해 실행하는 구조가 흔히 보고된다. 이후 단계에서 확인되는 기능 범주는 대략 이렇다 - 원격 제어가 가능한 백도어, 브라우저 저장 정보와 암호화폐 지갑 확장 데이터를 노리는 스틸러, `.env`·`.pem`·`.ssh`·`.aws` 같은 이름 패턴과 시드 구문 관련 키워드를 훑는 파일 스캐너, 그리고 클립보드에 복사된 비밀번호·개인키를 실시간으로 가로채는 클립보드 감시 모듈이다. 흥미로운 점은, 실제 사고에서 기존 백신은 물론 코드를 검토한 AI 코딩 에이전트도 이 코드를 악성으로 표시하지 못했다는 보고다. 자동 탐지에만 기대선 안 되는 이유다.

4. 방어 수칙 - 오늘 바로 적용할 것들

이 위협의 핵심은 결국 하나다. 신뢰할 수 없는 코드는 실제 자산이 있는 환경에서 실행하지 않는다. 구체적인 수칙을 정리한다.

4.1 격리 환경에서만 실행

출처를 확신할 수 없는 채용 과제는 일회용 가상머신이나 컨테이너에서만 클론·설치·실행한다. 실제 SSH 키, 클라우드 자격증명, 브라우저 로그인 세션이 없는 깨끗한 환경이어야 의미가 있다. 작업이 끝나면 환경을 그대로 폐기하는 것을 원칙으로 삼는다.

4.2 설치 전에 반드시 훑어보기

`npm install`이나 `yarn`을 실행하기 전에 package.json의 스크립트 항목, 그리고 Tailwind·Webpack·Vite 같은 설정 파일을 먼저 열어본다. 파일 크기가 에디터에 표시된 줄 수에 비해 비정상적으로 크다면 그 자체가 경고 신호다. `ls -la`나 `wc -c`처럼 파일 실제 바이트 수를 보여주는 명령으로 크로스체크하는 습관을 들인다.

4.3 네트워크 차단과 시크릿 분리

격리 환경의 아웃바운드 네트워크를 기본 차단하거나 최소한 모니터링해, 알 수 없는 IP로의 연결 시도를 눈에 띄게 만든다. 실제 지갑은 테스트넷이라도 낯선 프로젝트에 연결하지 않는다. 시드 구문·개인키는 애초에 개발용 기기에 두지 않는 것이 가장 안전하다.

4.4 npm 라이프사이클 스크립트 기본 차단

`npm install --ignore-scripts`로 설치하면 preinstall/install/postinstall 자동 실행을 막을 수 있다. 전역 설정(`npm config set ignore-scripts true`)으로 습관화하는 것도 방법이다. 실제로 업계에서도 공급망 공격 대응 차원에서 설치 스크립트를 기본 비활성으로 바꾸는 흐름이 이어지고 있다. 특정 패키지가 정말 훅이 필요하다고 확인되면 그때만 개별적으로 허용한다.

4.5 의심 신호 체크리스트

  • 채용 담당자 프로필의 연결·활동 이력이 매우 적거나 최근 생성됐다
  • 비공개 저장소 하나만 공유되고, 회사 소개나 공식 채용 페이지 링크가 부실하다
  • 과제 지시서에 비해 저장소 커밋 이력이나 라이선스 정보가 어색하다
  • 설정 파일 크기와 에디터 표시 줄 수가 맞지 않는다
  • 지원 절차를 유독 서두르며 빠른 실행·회신을 재촉한다
  • 실제 지갑 연결이나 시드 구문 입력을 과제 수행의 일부로 요구한다

5. 채용 사칭 판별법

기술적 방어와 별개로, 채용 절차 자체의 진위를 확인하는 습관이 1차 방어선이다. 회사 공식 도메인 이메일로 소통이 이어지는지, 채용 담당자가 회사 공식 채용 페이지나 링크드인 회사 계정에서 확인되는 인물인지 대조한다. 화상 통화를 요청해 신원을 확인하고, 회사명을 별도로 검색해 최근 사기 제보가 있는지 살핀다. 무엇보다, 정식 채용 절차에서 실제 자산이 연결된 지갑이나 운영 서버 접근 권한을 과제 수행 조건으로 요구하는 경우는 거의 없다는 점을 기준으로 삼는다.

6. 유사 위협 - 고립된 사건이 아니다

이런 캠페인은 특정 회사를 겨눈 한 번의 사기가 아니라, 수년째 이어지는 조직적 위협군의 일부로 보고된다. 보안 업계는 2022년 무렵부터 이어진 이런 유형의 캠페인을 「Contagious Interview」 계열로 분류하며, 북한 연계 위협 그룹(Lazarus 등으로 알려진 조직 및 하위 클러스터)과 연관지어 추적해 왔다. 공개된 분석에 따르면 이들은 npm·PyPI 레지스트리에 수백 개 단위의 악성 패키지를 반복적으로 올리고, 정보탈취·백도어 계열 악성코드를 유포해 왔으며, 대상은 주로 블록체인·핀테크·Web3 개발자였다. 2026년 들어서는 SVG 이미지에 코드를 숨기는 스테가노그래피, VS Code 작업 설정 악용, 커밋 조작 도구 등으로 수법이 계속 진화하고 있다는 보고도 나왔다. 요지는 이렇다 - 이건 한 번의 사기가 아니라 지속적으로 갱신되는 공격 도구함이며, 오늘 막은 수법이 내일은 다른 형태로 돌아올 수 있다.

7. 피해 시 대응 - 이미 실행했다면

의심스러운 과제를 이미 실행했다면, 속도가 피해 규모를 좌우한다.

  • 즉시 네트워크 차단: 인터넷 연결을 끊어 추가 데이터 유출과 원격 제어를 막는다.
  • 프로세스·잔존 파일 확인: 낯선 node 프로세스, 임시 폴더에 생성된 실행 파일을 점검하고 종료·삭제한다.
  • 전 자격증명 로테이션: SSH 키, GitHub·npm·클라우드 토큰, 저장된 비밀번호를 전부 새로 발급하고 기존 것은 폐기한다.
  • 브라우저 세션 폐기: 로그인 세션을 전부 무효화하고 재로그인한다.
  • 지갑 자금 이동: 시드 구문이나 개인키가 그 기기를 스쳤다면, 지체 없이 새 지갑으로 자산을 옮긴다.
  • 저장소·모듈 삭제, 재설치 검토: 감염 저장소와 node_modules를 삭제하고, 감염 범위가 불확실하면 운영체제 재설치까지 고려한다.
  • 회사 보안팀 신고: 재직 중이라면 회사 계정·CI/CD 접근권이 함께 노출됐을 가능성을 전제로 보안팀에 즉시 알린다.

결론: 겁먹기보다 격리하기

이 위협의 본질은 새로운 취약점이 아니라 익숙한 절차를 이용한 신뢰의 남용이다. 채용 과제라는, 개발자가 매년 여러 번 마주치는 지극히 평범한 상황이 공격 표면이 됐다. 그렇다고 채용 과정 자체를 피할 수는 없다. 현실적인 답은 겁먹는 것이 아니라 습관을 바꾸는 것이다. 낯선 코드는 격리된 환경에서만 실행하고, 실제 시크릿은 애초에 그 환경에 두지 않으며, 설치 전 훑어보기와 스크립트 차단을 기본값으로 만드는 것 - 이 세 가지만 지켜도 이런 유형의 공격 대부분을 무력화할 수 있다. 2026년 7월 기준으로, 이런 캠페인은 계속 진화하고 있다. 다음 채용 과제를 받으면, 이번 글의 체크리스트를 먼저 떠올리길 권한다.
