引言 - 语法上合法,取值却没有确定的文档

{"a":1,"a":2} 这样的文档并不违反 JSON 语法。RFC 8259 的对象语法只规定成员以逗号连接,没有禁止重复名称的条件。唯一性只作为「SHOULD be unique」这一条建议保留,而不是语法规则。因此,收到同一串字节的两个程序可能读出不同的值。

只用一个解析器的程序看不出这种差异,因为解析一次后一直使用该结果,无论取最后一个值还是第一个值都是一致的。问题出在同一文档被读取两次的结构里,典型情形是前端层检查请求体、后端层再次解析同一请求体。64 位 ID 精度一文的第 13 节把重复键作为数值精度话题中的一项来处理,本文把这一项扩展为按解析器对比、检测和复现。

本文讨论的问题如下。

  • 规范文档对重复键是怎么写的。
  • node、Python、PowerShell 5.1 对同一文档各给出什么值。
  • 键的顺序、仅大小写不同的键、用转义写成的键会被当作重复吗。
  • 服务器端的解析器给出的值与本地调用相同吗。
  • 检测重复键的脚本怎么写。
  • 当校验层与使用层看到不同的值时,实际上什么会被放行,又该如何阻止。

规范与官方文档的表述

以下是 RFC 8259 第 4 节、ECMAScript 规范中的 JSON.parse、Python json 模块文档以及 Microsoft Learn 的 ConvertFrom-Json 文档(5.1)中涉及重复键的语句,原文保持英文。

来源原文含义
RFC 8259 4The names within an object SHOULD be unique.名称唯一性是建议
RFC 8259 4When the names within an object are not unique, the behavior of software that receives such an object is unpredictable. Many implementations report the last name/value pair only. Other implementations report an error or fail to parse the object, and some implementations report all of the name/value pairs, including duplicates.重复时行为不可预测;有的实现只报告最后一对,有的报错,有的报告全部
ECMAScript JSON.parseIn the case where there are duplicate name Strings within an object, lexically preceding values for the same key shall be overwritten.规范明确规定前面的值被覆盖
Python json docsBy default, this module does not raise an exception; instead, it ignores all but the last name-value pair for a given name默认不抛异常而只用最后一对;可用 object_pairs_hook 改变
Microsoft Learn ConvertFrom-Json (5.1)if the JSON string contains duplicate keys, only the last key is used by this cmdlet存在重复键时只使用最后一个键

由该表可以归纳出四点。

  • RFC 只是建议唯一性,列出最后一个值、报错、全部报告三种做法后称其结果不可预测。
  • ECMAScript 规范直接规定 JSON.parse 中前面的值被覆盖。对 JavaScript 而言,「最后一个值生效」是规范语句,而非惯例。
  • Python 与 PowerShell 的文档同样写明使用最后一个值,这是各自实现的文档化行为。
  • RFC 留出的「报错」与「全部报告」两种行为,可以通过 Python 的 object_pairs_hook 这类扩展点实现。

  • 同一名称出现两次的文档,三个运行时都只保留了最后一个值,与所引规范和文档的方向一致。
  • 值为对象时也不会合并而是整体替换,第一个对象中的 x 在结果里消失了。
  • 数组内的对象是逐个判定的:只有第一个对象的 k 变为 2,第二个对象的 k 仍为 3。
  • Python 的 object_pairs_hook=list 返回了 [('a', 1), ('a', 2)]。这说明解析器读到了两对,只保留一个是之后构建 dict 那一步的事。

值取最后一个,位置取最先出现的

表中第二行 {"a":1,"b":2,"a":3} 在三个运行时中的结果都是 {"a":3,"b":2}。a 的值来自最后一次出现(3),但键的位置仍在 b 之前,也就是保留在第一次出现的位置。依据键顺序判断首个字段或按顺序处理的代码一旦收到重复键文档,就会遇到「值取后者、顺序取前者」的组合。

在 JavaScript 中可以用 reviver 函数观察解析过程。前面 node 输出的最后一行里,reviver 只收到两次调用:a=2 和根对象。值 1 没有传给 reviver。

  • JSON.parse 返回的对象只有一个键(keys=1),其中没有任何重复存在过的痕迹。
  • reviver 同样没有收到被覆盖的值,这次运行中无法通过 reviver 得知存在重复。
  • Python 有 object_pairs_hook,能拿到解析器读到的键值对列表本身。第 7 节的检测脚本建立在这一差异上。

看起来不同的同一个键

表中第四行是 a 与 A。node 和 Python 把它们当作两个不同的键,保留了 2 个键;PowerShell 5.1 则直接转换失败,抛出 InvalidOperationException。同一个文档在某一层被接受,在另一层却被拒绝。在这台电脑的韩文区域设置下,该异常消息包含意为「重复的键 'a' 与 'A'」的短语(原文为韩文,此处为译文)。消息本身就把重复键写成了拒绝的原因,因此 PowerShell 5.1 看来把仅大小写不同的键也判定为重复(措辞随区域设置而不同)。

第五行是用转义写成的键。文档中的 "\u0061" 解码后与 a 是同一个名称。三个运行时都把它视为重复,只保留最后一个值 2。下面的脚本展示这对基于文本搜索的校验意味着什么:第二个键用转义写成,使键 role 在文本中只出现一次。

import json
                    text = '{"role":"user","\\u0072ole":"admin"}'
                    print("raw text    : " + text)
                    print("text search : " + str(text.count('"role"')) + ' occurrence of "role"')
                    pairs = json.loads(text, object_pairs_hook=list)
                    print("parsed pairs: " + str(pairs))
                    print("parsed dict : " + str(json.loads(text)))
raw text    : {"role":"user","\u0072ole":"admin"}
                    text search : 1 occurrence of "role"
                    parsed pairs: [('role', 'user'), ('role', 'admin')]
                    parsed dict : {'role': 'admin'}
  • 原始文本里 "role" 只搜到 1 处,但解析器读到了两对 role,dict 中留下的是最后一个值 admin。
  • 用文本搜索或正则表达式统计键的校验会漏掉用转义写成的重复键,校验必须以解析器解码后的键为准。
  • 仅大小写不同的键在各运行时的处理并不相同。在使用多个解析器的结构里,这种差异也会让同一文档在不同层被读成不同内容。

服务器端解析器是否相同

以下是用 curl 发送同一请求体的两个本地 HTTP 服务器的响应。一个使用 Python 标准库的 http.server 和 json.loads,另一个使用 node 的 http 模块和 JSON.parse。两者都把解析结果序列化后作为响应体返回。

import json
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    class H(BaseHTTPRequestHandler):
                        def do_POST(self):
                            body = self.rfile.read(int(self.headers["Content-Length"]))
                            out = json.dumps(json.loads(body), separators=(",", ":")).encode()
                            self.send_response(200)
                            self.send_header("Content-Type", "application/json")
                            self.send_header("Content-Length", str(len(out)))
                            self.end_headers()
                            self.wfile.write(out)
                        def log_message(self, *a):
                            pass
                    
                    HTTPServer(("127.0.0.1", 18081), H).serve_forever()
const http = require('http');

重复键检测脚本

Python 文档把 object_pairs_hook 描述为「接收键值对列表并用返回值代替 dict 的扩展点」,因此在把键值对放进 dict 的过程中检查键是否已存在,就成了检测器。下面的脚本读取每行一个 JSON 文档的文件,逐行判定。

import json, sys
                    
                    def reject_duplicates(pairs):
                        obj = {}
                        for key, value in pairs:
                            if key in obj:
                                raise ValueError("duplicate key " + repr(key) + ": " + repr(obj[key]) + " then " + repr(value))
                            obj[key] = value
                        return obj
                    
                    for lineno, line in enumerate(open(sys.argv[1], encoding="utf-8"), 1):
                        text = line.rstrip("\n")
                        try:
                            json.loads(text, object_pairs_hook=reject_duplicates)
                            print(str(lineno) + ": OK    " + text)
                        except ValueError as err:
                            print(str(lineno) + ": FAIL  " + text)
                            print("    " + str(err))

输入文件共七行,最后一行是特意写坏的文档。运行结果如下。

1: OK    {"a":1,"b":2}
                    2: FAIL  {"a":1,"a":2}
                        duplicate key 'a': 1 then 2
                    3: OK    {"a":1,"A":2}
                    4: FAIL  {"a":1,"\u0061":2}
                        duplicate key 'a': 1 then 2
                    5: FAIL  {"l":[{"k":1,"k":2},{"k":3}]}
                        duplicate key 'k': 1 then 2
                    6: OK    {"a":1,"b":{"a":2}}
                    7: FAIL  {"a":1,
                        Expecting property name enclosed in double quotes: line 1 column 8 (char 7)
  • 第 2 行(a 出现两次)和第 5 行(数组内对象中的 k 出现两次)被检出。hook 针对每个对象调用,所以嵌套对象内的重复也被抓到。
  • 第 4 行用转义写成的 a 也被检出,因为它与上一节的文本搜索不同,查看的是解码后的键。
  • 第 3 行(a 与 A)和第 6 行(外层 a 与内层 a)通过了。该检测器只把同一对象内完全相同的名称视为重复。
  • 第 7 行不是因重复而是因语法错误被拒,在同一个 except ValueError 下只是消息不同。要区分语法错误与重复,需要分别捕获异常类型。

两层看到不同值的复现

构成有两部分。前端网关(Python)解析请求体,如果 role 为 admin 就以 403 拒绝,放行的请求则把原始字节原样转发给后端(node,即前面的 echo 服务器)。后端返回 JSON.parse 读到的结果,所以响应就是后端看到的值。网关的解析器用 object_pairs_hook 自行实现了「已存在的键不覆盖」的先到先得策略。这台电脑上的三个标准解析器都是后者优先,所以要得到策略不同的两层只能这样构造。这一策略差异是为演示设定的假设,并不表示哪个真实产品采用先到先得。

import json, os, sys, urllib.request
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    MODE = sys.argv[1]
                    PORT = int(sys.argv[2])
                    BACKEND = "http://127.0.0.1:18082/"
                    
                    def first_wins(pairs):
                        obj = {}
                        for key, value in pairs:
                            obj.setdefault(key, value)
                        return obj
                    
                    def reject_duplicates(pairs):
                        obj = {}
                        for key, value in pairs:
                            if key in obj:
                                raise ValueError("duplicate key " + repr(key))
                            obj[key] = value
                        return obj
                    
                    class H(BaseHTTPRequestHandler):
                        def reply(self, code, text):
                            data = text.encode()
                            self.send_response(code)
                            self.send_header("Content-Length", str(len(data)))
                            self.end_headers()
                            self.wfile.write(data)
                    
                        def do_POST(self):
                            body = self.rfile.read(int(self.headers["Content-Length"]))
                            hook = reject_duplicates if MODE == "reject" else first_wins
                            try:
                                doc = json.loads(body, object_pairs_hook=hook)
                            except ValueError as err:
                                return self.reply(400, "gateway: 400 " + str(err))
                            if doc.get("role") == "admin":
                                return self.reply(403, "gateway: 403 role admin is not allowed")
                            forward = json.dumps(doc).encode() if MODE == "canonical" else body
                            req = urllib.request.Request(BACKEND, data=forward, method="POST")
                            with urllib.request.urlopen(req) as r:
                                self.reply(200, "gateway: passed; backend saw " + r.read().decode())
                    
                        def log_message(self, *a):
                            pass
                    
                    HTTPServer(("127.0.0.1", PORT), H).serve_forever()

                    gateway: 403 role admin is not allowed
                    == 5. gateway, role twice (user then admin)
                    gateway: passed; backend saw {"user":"alice","role":"admin"}
                    == 6. gateway that rejects duplicates
                    gateway: 400 duplicate key 'role'
                    == 7. gateway that forwards what it parsed
                    gateway: passed; backend saw {"user":"alice","role":"user"}
                    == 8. gateway, role twice (admin then user)

编号请求体中的 role网关判定后端看到的 role
3user放行user
4admin403—
5user, admin放行admin
8admin, user403—
  • 请求 5 的请求体中 role 按 user、admin 的顺序出现两次。网关看到第一个值 user 并放行,后端读到的是最后一个值 admin。本应被拒绝的值穿过校验到达了后端。
  • 请求 8 只是把两个值的顺序颠倒。这次网关看到第一个值 admin 并以 403 拒绝。把变量收窄到顺序一项,就能从输出中分离出网关读取的是第一个值。
  • 请求 3 与 4 是对照组。没有重复的请求体中,网关的判定与后端的值一致。
  • 并不是哪个解析器错了。在 RFC 称为不可预测的领域里,两层只是各自做了不同的选择。问题在于被校验的文档与被使用的文档字节相同,取值却不同。

两种防范方法 - 拒绝,或转发已校验的内容

同一份网关代码只切换模式就运行了两种方法。reject 模式遇到已存在的键就让解析失败并返回 400;canonical 模式则把网关解析出的对象重新序列化后发给后端。请求体与上一节的请求 5 相同,结果就是 run.sh 的第 6 和第 7 项输出。

方法网关行为请求 5 同一请求体的结果
拒绝重复 (reject)遇到重复键即解析失败,不调用后端gateway: 400 duplicate key 'role'
把校验过的对象序列化后转发 (canonical)不转发原始字节,而转发由网关解析出的对象重新生成的 JSONgateway: passed; backend saw {"user":"alice","role":"user"}
不做修改 (raw)原样转发原始字节gateway: passed; backend saw {"user":"alice","role":"admin"}
  • reject 在请求到达后端之前就以 400 拦下。如果有合法客户端故意发送重复键,它的请求同样会得到 400。
  • canonical 方式下后端收到的是网关校验过的值 user。这等于把网关「取第一个值」的策略强加给后端,因此如果客户端本意是最后一个值,实际使用的就是另一个值。
  • 两种方法的共同点是让被校验的对象与被使用的对象取值相同:一个拒绝该文档,另一个只解释一次并转发结果。
  • 上一节的例子展示的是校验层与使用层各自重新解析原始字节的结构。对越过信任边界的输入只解释一次,与客户端信任边界一文讨论的原则相通。

实际工作中应检查的项目如下。

  • 是否存在对同一请求体解析两次以上的层?若有,解析器的种类与设置是否相同。
  • 校验依据的是解析器解码后的键,还是对原始文本的搜索。
  • 收到重复键时,是拒绝,还是按某一种策略规范化后转发,是否已有决定。
  • 是否确认了校验过的值与后端收到的字节一致。上面的输出中,canonical 模式下后端收到的请求体不是原始字节,而是网关重新生成的 JSON。
