Introduction: what is the hundred and first prompt worth?

Spend a few days with a coding agent and your hand starts moving before your eyes do. A confirmation dialog appears and you click approve before reading it. Almost every one of them was a request to edit a single file, and nothing bad happened, so the habit only gets stronger. The problem is that the habit works exactly the same way on the hundred and first prompt. That the hundred and first was different from the others is something you learn later.

None of that is new. What changed over the last few months is one layer deeper. As tools push to reduce interruption, they have started changing the default permission mode itself. For an individual that is a convenience improvement. For an organization it is a different kind of event, because your code did not change and nothing was deployed, yet the agent behaves differently.

This article is not about how to design permissions. The framework for grading work by reversibility and blast radius, then attaching isolation and audit logging, is laid out in What Should You Let an AI Agent Do - Permission Design and Circuit Breakers, and this piece starts on top of it. Two questions drive what follows. Does that design actually work in practice, and who decides its default? Product behavior changes, so everything below reflects the state as of August 11, 2026.

1. When approval is a control, and where that breaks

An approval prompt is not a control by itself. It is a control only while a human reads it and decides. That premise fails in roughly three places.

  • Frequency — a dialog that fires dozens of times a day is not read. This is not a willpower failure; it is ordinary habituation to a repeated stimulus.
  • Presentation — if the screen does not show what changes, how much, and whether it can be undone, there is nothing to judge. With no material to judge on, people do not judge. They pass it through.
  • The escape hatch — if a door exists that approves everything, a tired engineer eventually opens it. At that moment no gate remains at all.

There is a less discussed fourth place: when it is unclear what a single approval actually approves. Compound commands are the classic case. Chain several commands with operators and a human sees one line, while what executes is several things.

Handling differs by tool, and that difference is what dictates how you write rules. Per the official documentation, shell operators are recognized and a rule must match each subcommand independently. A safe-looking prefix does not extend coverage to whatever follows it. When you approve a compound command with the do-not-ask-again option, a separate rule is saved for each subcommand that required approval rather than one rule for the whole string, and the number saved at once is capped.

What a practitioner should take from this is how far a prefix rule reaches. The documentation describes a fixed set of wrappers stripped before rules are matched, and in the same breath it names things that are not on that list. Development environment runners are the notable group. Those tools execute whatever follows them as a command, so a broad rule naming only the runner ends up covering whatever comes next. The documented guidance follows directly: write a specific rule naming both the runner and the inner command, one rule per inner command you want to allow. Certain repeating-execution wrappers and the execution flags of search utilities are likewise documented as always prompting and never auto-approved by a prefix rule.

The lesson here is not which string slips past a check. It is that a broad prefix rule can apply more widely than you pictured, and the response is singular: write auto-approve rules narrowly, and when you want more breadth, do not lengthen the list — use the other layer discussed below. Why growing a blocklist loses structurally is covered separately in A blocklist is always one step behind.

2. What a permission mode actually bundles

A permission mode is not an individual permission but a bundle of layers. Reading, editing files, running commands, and making network requests are separate layers, and a mode fixes them as one package. Choosing a mode is therefore choosing an exchange rate between convenience and oversight.

Organized by layer, the currently published mode lineup looks like this. Names vary by tool, but the more interesting point is that the arrangement of the rungs converges across products.

ModeRuns without askingProtected-path writesBest for
Manual (default)Reads onlyPromptedGetting started, sensitive work
acceptEditsReads, file edits, common filesystem commandsPromptedIterating on code you are reviewing
planReads, plus classifier-approved commandsPrompted, or routed to the classifierExploring a codebase before changing it
autoEverything, with background safety checksRouted to the classifierLong tasks, reducing prompt fatigue
dontAskOnly pre-approved toolsDeniedLocked-down CI and scripts
bypassPermissionsEverythingAllowedIsolated containers and VMs only

The row worth pausing on is dontAsk. The name reads like it does everything without asking, but it is the opposite. It denies everything without asking. Only pre-approved tools and read-only commands run, and the session never waits for input. For automation running where no human is present, that direction is correct. Nobody present means nobody to approve, so the right default in that seat is refusal rather than passage.

One more thing. Modes only set the baseline; rules layer on top. Deny rules and explicit ask rules apply in every mode, including the one that skips everything else. Allow rules, conversely, mean nothing in a mode where everything is already approved. That asymmetry returns later.

3. Where to place a probabilistic gate

The core of the recently introduced middle mode is that a separate classifier model reviews each tool call before it runs. Per the published description, it targets escalation beyond what you asked for, actions aimed at unrecognized infrastructure, and behavior that looks driven by hostile content the agent read. Instead of asking a human every time, a machine filters first.

The direction is sound. As section one showed, high prompt frequency means humans stop reading, so passing through only what a human genuinely needs to see raises real oversight quality. Still, know exactly what kind of device this is. The official documentation itself states that it reduces permission prompts but does not guarantee safety, and advises using it where you trust the general direction rather than as a replacement for review on sensitive operations. Product documentation rarely says this about its own feature, and that sentence is worth adopting verbatim as an operating policy.

The deciding factor is that the costs of false positives and false negatives are not symmetric. Block a safe command and a human confirms once more; let an irreversible one through and there is no path back. A probabilistic device does not resolve that asymmetry. So placement matters.

  • Put the classifier in front — as a way to widen auto-approval. Fewer approvals means the remaining ones get read. Probabilistic is fine here.
  • Put deterministic rules behind — as the last line for irreversible work. A deny rule does not judge, it simply blocks, so it is unaffected by context length or model state.
  • Do not swap the two — trusting a probabilistic device as the final barrier is the most common mistake in this area.

It is also worth knowing how the trust boundary is drawn. The classifier trusts your working directory and the remotes that were configured when the session started. A remote added or repointed mid-session is not trusted. Pinning the reference point to session start prevents the baseline itself from moving during execution, which is a sensible choice. Even in the mode that skips everything, removals targeting the filesystem root or the home directory still prompt as a circuit breaker.

4. A boundary stated in chat is not a rule

This section is the most practical part of the article. If you write do not push or wait until I review before deploying during a session, the classifier treats that sentence as a block signal. It blocks matching actions even where the default rules would allow them, and the boundary stays in force until you lift it yourself. The agent deciding on its own that the condition has been met does not lift it.

So far it sounds like conversation is enough to manage this. Then the same documentation states the limit. These boundaries are not stored as rules. They are re-read from the transcript on every check, so if context compaction removes the message that stated one, the boundary disappears with it. And the documentation writes the conclusion for you: for a hard guarantee, add a deny rule instead.

A line drawn in conversation is a convenience for that session; only a line written as a rule survives into the next one. The test is easy. If you are stating the same prohibition for the second time, it has earned promotion. From the third time on, writing it is cheaper than saying it.

This is also a case of one design principle covered earlier being confirmed at the product layer — the principle that a prohibition written into instructions is not a control. One nuance is added, though. A conversational boundary is not powerless; it is a device whose power is real but whose lifespan is tied to context. On short tasks it is perfectly usable. On long ones it quietly disappears. Quietly is the dangerous part. No notification arrives to say the boundary has lapsed.

5. The layer settings cannot open

Work with permission settings long enough and you arrive at one question. If I write everything into the settings file, can I make anything run automatically? The answer is no, and the reason is interesting.

There is a concept called protected paths. Writes to a specific set of directories and files are never auto-approved in any mode other than the one that skips everything. The per-mode handling is already in the table above, but the sentence that matters most sits beside it: allow rules in settings files do not pre-approve protected-path writes. The safety check runs before allow rules are evaluated, so listing such a path in your allow list does not change the per-mode outcome.

Group the protected set by character and the design intent surfaces.

GroupWhat it coversWhy it is here
Repository stateVersion-control directory and its config filesDamage the reference point for undo and the recovery coordinates vanish
Files defining later executionShell startup files, hook config, pre-commit config, build wrapper pinsEditing one line now changes every execution that follows
Package resolutionPackage manager configuration filesThey control where artifacts are fetched from — a supply chain entrance
The agent's own configurationAgent settings directory and tool connection configIt becomes the path by which the agent loosens its own constraints
Editor and dev container configEditor settings directories, dev container definitionsThey contain setups where merely opening the project executes something

All five groups reduce to one idea. These are files that determine what will execute in the future, not what happens right now. Editing an individual file is reversible; editing the rules of execution contaminates every judgment after it. Why putting an agent's own permission definitions on a no-write list is not a trivial measure was already covered from the design side. What is new here is that it is implemented as a layer users cannot unlock through settings.

The operational implication is clear. When reviewing your permission policy, separate the items you genuinely control through settings from the items that were never settings-controlled in the first place. The latter are not items to drop from the checklist. They are the opposite: record them as safety nets that could disappear if you change tools.

6. What the org locks, what the individual locks

Once permissions can be written in several places, a precedence question appears immediately. When personal settings, settings checked into the repository, and managed settings deployed by the organization disagree, which wins?

The rules resolve along two axes.

  • Layer axis — managed settings sit highest. No other level, including command line arguments, can override a managed permission rule.
  • Direction axis — any layer may contribute to tightening. If a tool is denied at any level, no other level can allow it, and deny rules are evaluated before allow rules. A user-level allow colliding with a project-level deny loses to the deny, and the reverse holds too.

What this asymmetry means in practice: anyone can contribute in the safe direction, and only an authorized layer moves in the risky one. An individual tightening their own environment is always possible; an individual loosening organizational policy is not. This is the healthiest shape you can ask of a permission system.

On top of that, the tooling has places where settings crossing a trust boundary can only be changed from inside that boundary. Three facts point the same way.

  • The setting that makes the middle mode the starting default is read only from user or managed settings. Writing it in project or local settings is ignored — meaning a repository cannot push collaborators into the automatic mode.
  • Cloud sessions do not honor a checked-in default of the skip-everything mode. Settings living in a repository alone cannot start a remote session in the unrestricted mode.
  • Settings exist to disable specific modes entirely; when an administrator applies one org-wide, the mode leaves the cycle and the startup flag is rejected. The one covering the skip-everything mode works from any scope, so an individual can use it to lock themselves out.

The third is especially worth recommending to individuals. Locking yourself out removes one decision you would otherwise make late at night while tired.

7. A default change is a change management event

Per the official documentation, starting August 14, 2026, the default permission mode for new sessions moves to the automatic mode on certain plans. The accompanying conditions matter more operationally. You can switch modes at any time, a default you set yourself stays in place unless you accept the one-time switch prompt, and a default your organization manages is unchanged. Enterprise, the API, and cloud-partner deployments remain outside this shift.

That last clause captures the character of the change well. The vendor itself treated managed environments differently from individual ones. That is not a verdict on which mode is safer; it is a judgment about who ought to be the party deciding a default. Where a managing party is defined, letting that party decide is the right call. This is not something to criticize or defend so much as something to check your own position against.

Which is exactly why it is a change management event. No commit lands in your repository and nothing shows up in deployment history, yet agent behavior differs. Without an owner it simply passes. The review sequence, as a table:

CheckHow to verifyIf it does not hold
Are we in scope?Confirm the org account plan and deployment pathIf in scope, work through every row below
Is the default mode pinned explicitly?Check managed settings for a default mode entryWithout it you follow the vendor default. Write the value you intend
How are our current prohibitions written?Separate chat-stated boundaries from written rulesPromote the chat-dependent ones into deny rules
Which mode does automation run in?Check startup flags on unattended execution pathsWhere no human is present, refusal is the correct default
Do onboarding docs assume the old default?Compare internal guides against current mode behaviorStale docs mean only new joiners work from the old premise
Can we tell afterward?Verify records distinguish auto-approval from human approvalWithout the distinction you cannot evidence the gate worked

The third row is the heart of this table, and it is where audit and change management meet. When a default loosens, the first thing exposed is what you were actually relying on. Prohibitions written as rules stand unchanged; prohibitions resting on human habit and conversational boundaries weaken quietly. For teams operating under SOC 2 or a similar attestation, that distinction is also the difference between a control you can evidence and one you merely describe — a control nobody can reconstruct from records is difficult to present as operating effectively.

8. What belongs in which layer

Translating the above into configuration gives three layers: personal settings, settings checked into the repository, and managed settings. Which file to share and which to keep local is covered in how to split shared and local settings, so here we only set the criteria.

  • Things that may differ per person go in personal settings — editor preferences, personal working paths, and locks that further restrict only you. There is no reason to impose these on anyone else.
  • Things arising from the repository's nature get checked in — which commands are safe in this repository, which paths must not be touched. These should read identically for everyone who clones.
  • Things individuals must not be able to unlock go in managed settings — deny rules for irreversible work, modes blocked at the org level, and the pinned default mode. What lands here is not overturned even by command line arguments.

Two placement mistakes recur. First, keeping deny rules only in personal settings. Your own environment gets safer while the team gains nothing, and a new joiner starts with no protection at all. Second, loading too much into managed settings. When developers are blocked repeatedly during normal work, they start looking for ways around, and from that point on what you manage is not policy but policy avoidance. Managed settings last longer when they hold only what genuinely must not be unlocked.

A line on records is worth adding. The more auto-approval grows, the more valuable a log that distinguishes what passed automatically from what a human approved. Without that distinction there is no way to demonstrate after the fact that the gate functioned, and no basis for tuning approval policy either. The log field design itself is tabulated in the audit log section of the permission design article.

9. What could not be verified

This topic carries several widely repeated figures that could not be traced to a primary source. The following were deliberately left out.

  • Comparative approval gate effectiveness figures — several outlets circulate a tester count alongside a comparison of dangerous-command catch rates for humans versus automated review, but those figures could not be found in the vendor's own published announcement. The numbers are striking and easy to quote, which is precisely why they were excluded without a primary source.
  • Classifier false positive and false negative rates — no published figures. The placement guidance in this article rests on the structural asymmetry of error costs, not on measurements.
  • Mapping to certification frameworks — the documentation does not state which control objectives of SOC 2 or any similar framework a given permission mode or log field satisfies. Any such mapping should be confirmed directly with your auditor rather than inferred.
  • Rollout timing details — the transition date reflects only what the documentation states. Effective dates can read differently across release channels, so confirm against the notice on your own account.
  • Version-specific behavior — some behaviors are marked as applying only from certain versions onward. This article describes the direction of behavior; check the docs for the version you actually run.

Conclusion: fewer gates is what keeps gates alive

It is easy to read a default moving in the looser direction as a retreat from safety. Put the preceding sections together, though, and a different picture emerges. A setup that asks a human about everything is not a state of dense oversight but a state of formalized oversight. An approval prompt clicked a hundred times gets clicked the hundred and first. Filtering automatically what can be filtered automatically, and leaving humans only what genuinely needs judgment, is — when implemented properly — not a reduction in total oversight but an increase in its density.

That transition carries a condition, though. Probabilistic devices are for widening auto-approval, not for serving as the last line on anything irreversible. Hold that one line and the rest is placement. The sequence:

  • Enumerate irreversible operations first and nail them down with deny rules. No probability enters here.
  • Widen auto-approval across what remains to cut the number of approvals. The goal is that surviving prompts actually get read.
  • Pin the default mode explicitly in managed settings. Your value then survives a vendor default change.
  • Promote recurring conversational boundaries into rules. Said it twice? Time to write it.
  • Make records distinguish auto-approval from human approval. If you cannot answer afterward, you cannot evidence the gate existed.

One closing note. Every product detail here reflects August 11, 2026. Permission models are among the fastest-moving areas right now, and defaults will change again. What is worth keeping, then, is not the name of a particular mode but a question. Is what protects us right now a rule, or merely the fact that nobody has clicked the wrong button yet?
