The output is exactly what script files printed on Python 3.13.3 (Windows, 64-bit), and this article is limited to the sharing symptom of mutable class-body attributes (first reproduced in section 7 of the default-argument article) seen through lookup path, inheritance, ClassVar and dataclass handling.

Introduction - what the same name points to

When items = [] is written in a class body, every instance sees the same list. The Python tutorial section titled Class and Instance Variables presents this shape as a mistaken use of a class variable (the Dog.tricks example), and it separates the two roles: instance variables are for data unique to each instance, and class variables are for attributes and methods shared by all instances. Reproductions of the symptom itself already exist in section 7 of Why an empty list as a default argument keeps accumulating values across calls and in section 4.2 of What shuffling the test order reveals.

The root of the confusion is that the same name can exist on the instance and also on the class. A class attribute is a name assigned in the class body and kept in the class __dict__, and an instance attribute is a name kept in the instance __dict__. Which of the two holds the name decides the outcome of reading, writing and deleting. Below, the location is inspected directly and each operation is separated by the place it touches.

The questions covered are as follows.

  • Where does a value live, the instance or the class, and how can that be found out?
  • Do reading, writing and deleting look at the same place?
  • What happens to instances that already exist when the class-side value is changed?
  • What does += leave behind for an integer and for a list?
  • Does a subclass share the parent mutable attribute, and where does a value go when it is written through type(self)?
  • How do dataclass, ClassVar and __slots__ treat this distinction?
  • When sharing is intended, which form is clear to the reader?

Where the value lives - looking with __dict__ and vars

This section's output is an experiment covered in the earlier article (section 7), used here to look at where values live through vars() and type(obj).__dict__. The data model documentation says a class attribute reference is translated into a lookup in the class dictionary (C.x becomes C.__dict__["x"]), and that for a class instance the instance dictionary is the first place attribute references are searched; when the name is not found there and the class has an attribute by that name, the search continues with the class attributes. The output of both dictionaries follows.

class Cart:
                        items = []
                        label = 'cart'
                    
                    a = Cart()
                    b = Cart()
                    print('a.__dict__            :', a.__dict__)
                    print('vars(a)               :', vars(a))
                    print('Cart.__dict__ keys    :', [k for k in vars(Cart) if not k.startswith('__')])
                    print('type(a) is Cart       :', type(a) is Cart)
                    print('type(Cart.__dict__)   :', type(vars(Cart)).__name__)
                    print('a.items is Cart.items :', a.items is Cart.items)
                    a.items.append('x')
                    print('b.items               :', b.items)
a.__dict__            : {}
                    vars(a)               : {}
                    Cart.__dict__ keys    : ['items', 'label']
                    type(a) is Cart       : True
                    type(Cart.__dict__)   : mappingproxy
                    a.items is Cart.items : True
                    b.items               : ['x']

The dictionary of instance a is empty. items and label exist only in the dictionary of Cart. a.items is Cart.items is True, and after a value was appended through a it was visible through b.items as well. With no list on either instance, both instances were reading the single list on the class. The class dictionary is printed as a mappingproxy, and two calls, vars(obj) and vars(type(obj)), are enough to see where a value lives.

  • vars(obj) returns the instance dictionary. If it is empty, there are no instance attributes.
  • vars(type(obj)) returns the class dictionary. A name found only here is a class attribute.
  • Sharing is established when obj.name is type(obj).name is True while the name is absent from the instance dictionary.
  • Here is is used only on mutable objects such as lists. Cases where the result of is on small integers and strings differs by how the code is run are covered in Why a condition fails only in production while the tests pass.

Reads climb up while writes stop at the instance

Reading and writing the same name look at different places. The sentence in the data model documentation is: Attribute assignments and deletions update the instance's dictionary, never a class's dictionary. Reading climbs from the instance to the class, but assignment and deletion on an instance change only the instance dictionary. The output for a string attribute shows the asymmetry.

class Cart:
                        label = 'cart'
                    
                    a = Cart()
                    b = Cart()
                    a.label = 'mine'
                    print('a.__dict__ after set  :', a.__dict__)
                    print('a.label, b.label, Cart.label:', a.label, b.label, Cart.label)
                    del a.label
                    print('after del a.label     :', a.label, a.__dict__)
                    Cart.label = 'changed'
                    print('after Cart.label=...  :', a.label, b.label)
                    b.label = 'shadow'
                    Cart.label = 'again'
                    print('b shadowed, a not     :', b.label, a.label)
a.__dict__ after set  : {'label': 'mine'}
                    a.label, b.label, Cart.label: mine cart cart
                    after del a.label     : cart {}
                    after Cart.label=...  : changed changed
                    b shadowed, a not     : shadow again

After a.label = 'mine' an entry appeared in the dictionary of a and Cart.label was unchanged. After del a.label the dictionary was empty again and a.label returned to the class value. When Cart.label was changed on the class side, a, which had no value of its own, followed, and in the last two lines b, which had its own value, was unaffected by the new class value. The table collects which place each operation changes.

OperationPlace that changesResult (based on the output above)
a.label = va.__dict__Only a changes; the class and b stay as they were
del a.labelEntry removed from a.__dict__a reads the class value again
Cart.label = vCart.__dict__Every instance without its own value reads the new value
b.label = v then Cart.label = wAlready present in b.__dict__b keeps v; other instances read w

The last row of the table is the identity of the sharing symptom. a.items.append(x) reads a.items and then calls a method of that object, so no assignment to the instance dictionary takes place. The write rule applies only when a name is assigned, not when an object is modified in place.

Class-side changes: which instances follow and which do not

Assigning a new object to a class attribute and modifying the existing object reach instances differently. The name was rebound on the class side, then some instances were given their own value and the name was rebound again.

class Box:
                        items = []
                        n = 0
                    
                    a = Box()
                    b = Box()
                    Box.items = ['new']
                    print('class rebinding        :', a.items, b.items)
                    a.items = ['mine']
                    Box.items = ['newer']
                    print('after a has its own    :', a.items, b.items)
                    Box.n = 5
                    a.n += 1
                    Box.n = 9
                    print('a.n, b.n, Box.n        :', a.n, b.n, Box.n)
class rebinding        : ['new'] ['new']
                    after a has its own    : ['mine'] ['newer']
                    a.n, b.n, Box.n        : 6 9 9

Right after Box.items = ['new'] both instances read the new list, because the object the class dictionary name points to had changed and the instances had no value of their own. Then a.items = ['mine'] gave a its own value, and when the class was changed again only a did not follow. Numbers behave the same way. After Box.n = 5, a.n += 1 read 5, added 1 and put 6 into the dictionary of a; after Box.n = 9, b.n followed to 9 but a.n stayed at 6.

  • Rebinding a class attribute spreads only to instances that have no value of their own.
  • Once an instance has its own value for a name, class-side changes no longer reach it for that name.
  • So when only some instances of one class read a new setting, it depends on which instances have come to own a value.

What += leaves behind - integers versus lists

The integer part is an experiment covered in the earlier article (section 7), used here to see through vars() whether a name appears in the instance dictionary. In self.count += 1 a read and a write overlap on one line. The read on the right climbs up to the class and the write on the left stops at the instance. The same operation was applied to an integer and to a list.

class Counter:
                        hits = 0
                        log = []
                    
                    p = Counter()
                    q = Counter()
                    p.hits += 1
                    p.hits += 1
                    q.hits += 1
                    print('p.hits q.hits Counter.hits:', p.hits, q.hits, Counter.hits)
                    print('p.__dict__ :', p.__dict__)
                    p.log += ['p']
                    q.log += ['q']
                    print('p.log      :', p.log, ' Counter.log:', Counter.log)
                    print('p.log is Counter.log:', p.log is Counter.log)
                    print('p.__dict__ :', p.__dict__)
                    p.log = p.log + ['new']
                    print('after p.log = p.log + [...]:', p.log, Counter.log, p.log is Counter.log)
p.hits q.hits Counter.hits: 2 1 0
                    p.__dict__ : {'hits': 2}
                    p.log      : ['p', 'q']  Counter.log: ['p', 'q']
                    p.log is Counter.log: True
                    p.__dict__ : {'hits': 2, 'log': ['p', 'q']}
                    after p.log = p.log + [...]: ['p', 'q', 'new'] ['p', 'q'] False

The integer split as expected: p.hits is 2, q.hits is 1 and the class value is 0, because the name hits appeared in the dictionary of p. The list is different. After p.log += ['p'] and q.log += ['q'] the class list contained both values, and p.log is Counter.log is True. Yet the name log did appear in the dictionary of p. This matches the output if the += on a list extends the list attached to the class in place and then assigns the same list to the instance name. A name visible in the instance dictionary does not mean the instance owns the object.

The last line, p.log = p.log + ['new'], builds a new list and assigns it, so p.log came apart from the class list. The class list does not contain 'new' and is is False.

  • += on an integer creates a new object and binds it to the instance, so the sharing is released.
  • += on a list extends the same object and rebinds it, so the sharing remains.
  • x = x + [...] builds a new list and binds it, so the sharing is released. Two expressions that look equivalent behave differently.
  • Do not stop at checking whether the name is in the instance dictionary; also check obj.name is type(obj).name.

A subclass uses the parent list as is

The same rule continues in subclasses. The data model documentation says that when the name is not found in the class dictionary, the search continues in the base classes. The output below shows the location of the list for one parent and two children.

class Base:
                        tags = []
                    
                    class Child(Base):
                        pass
                    
                    class Other(Base):
                        tags = ['own']
                    
                    c = Child()
                    o = Other()
                    bs = Base()
                    print('Child.tags is Base.tags :', Child.tags is Base.tags)
                    print('Other.tags is Base.tags :', Other.tags is Base.tags)
                    c.tags.append('from child instance')
                    print('Base.tags               :', Base.tags)
                    print('bs.tags                 :', bs.tags)
                    print('o.tags                  :', o.tags)
                    print("'tags' in vars(Child)   :", 'tags' in vars(Child))
                    print('MRO of Child            :', [k.__name__ for k in Child.__mro__])
Child.tags is Base.tags : True
                    Other.tags is Base.tags : False
                    Base.tags               : ['from child instance']
                    bs.tags                 : ['from child instance']
                    o.tags                  : ['own']
                    'tags' in vars(Child)   : False
                    MRO of Child            : ['Child', 'Base', 'object']

Child did not have tags in its own dictionary, and Child.tags was the same object as Base.tags. When a value was appended through a child instance it was also visible through the parent class and through a parent instance. Other, which declared tags again when the class was created, had its own list that did not mix with the parent value. The lookup order climbs from the child to the parent as in the MRO output (Child, Base, object).

  • Creating a subclass does not by itself copy a class-attribute list.
  • Declaring the same name again in the subclass body gives that subclass its own object.
  • To give each subclass its own copy of a parent attribute, a new object must be assigned at the moment the subclass is created. Section 10 shows how.

Two ways to count - type(self) and the class name

Code that raises a class-side counter is written in two ways: with type(self), which points to the class of the instance, and by writing the class name directly. Once a subclass is involved the results diverge.

class Reg:
                        count = 0
                        def __init__(self):
                            type(self).count += 1
                    
                    class RegChild(Reg):
                        pass
                    
                    Reg(); Reg(); RegChild()
                    print('Reg.count, RegChild.count   :', Reg.count, RegChild.count)
                    print("'count' in vars(RegChild)   :", 'count' in vars(RegChild))
                    
                    class Reg2:
                        count = 0
                        def __init__(self):
                            Reg2.count += 1
                    
                    class Reg2Child(Reg2):
                        pass
                    
                    Reg2(); Reg2Child(); Reg2Child()
                    print('Reg2.count, Reg2Child.count :', Reg2.count, Reg2Child.count)
                    print("'count' in vars(Reg2Child)  :", 'count' in vars(Reg2Child))
Reg.count, RegChild.count   : 2 3
                    'count' in vars(RegChild)   : True
                    Reg2.count, Reg2Child.count : 3 3
                    'count' in vars(Reg2Child)  : False

type(self).count += 1 read the parent value 2 and wrote into the dictionary of RegChild itself. As a result RegChild.count became 3 and Reg.count stayed at 2. Reg2.count += 1, with the class name written directly, edited only the parent dictionary even when child instances were created, so everything gathered into the single value 3 and no name appeared in the dictionary of Reg2Child.

  • To count all instances in one value, writing the class name directly gathers them.
  • To count per subclass, use type(self), remembering that the first write starts from the current parent value.
  • If the two styles are mixed in one class hierarchy, the values of the same name drift apart between parent and child.

What dataclass looks at - fields, ClassVar and mutable defaults

The list ValueError is an experiment covered in the earlier article (section 7), placed here beside the field and ClassVar checks. A dataclass deals with this problem at declaration time. The documentation notes that default values are stored as class attributes and says a ValueError is raised for an unhashable default, on the assumption that an unhashable value is mutable, and it calls this a partial solution. It also says a field whose type is typing.ClassVar is excluded from being a field and is not returned by fields(). A field, a ClassVar and an attribute without annotation sit in one class below, followed by the output for four kinds of default.

from typing import ClassVar
                    from dataclasses import dataclass, field, fields
                    
                    @dataclass
                    class Plain:
                        name: str
                        tags: list = field(default_factory=list)
                        registry: ClassVar[dict] = {}
                        note = 'no annotation'
                    
                    p1 = Plain('a'); p2 = Plain('b')
                    print('fields          :', [f.name for f in fields(Plain)])
                    print('annotations     :', list(Plain.__annotations__))
                    print('registry shared :', p1.registry is p2.registry is Plain.registry)
                    print('tags shared     :', p1.tags is p2.tags)
                    print('p1.__dict__     :', p1.__dict__)
                    print('note is a field :', 'note' in [f.name for f in fields(Plain)], '/ Plain.note =', Plain.note)
                    try:
                        Plain('x', ['q'], {}, 'extra')
                    except TypeError as e:
                        print('TypeError       :', e)
                    
                    for kind, default in [('list', []), ('dict', {}), ('set', set()), ('tuple', ())]:
                        try:
                            @dataclass
                            class Probe:
                                x: object = default
                            print(kind, '-> accepted')
                        except ValueError as e:
                            print(kind, '-> ValueError:', e)
fields          : ['name', 'tags']
                    annotations     : ['name', 'tags', 'registry']
                    registry shared : True
                    tags shared     : False
                    p1.__dict__     : {'name': 'a', 'tags': []}
                    note is a field : False / Plain.note = no annotation
                    TypeError       : Plain.__init__() takes from 2 to 3 positional arguments but 5 were given
                    list -> ValueError: mutable default <class 'list'> for field x is not allowed: use default_factory
                    dict -> ValueError: mutable default <class 'dict'> for field x is not allowed: use default_factory
                    set -> ValueError: mutable default <class 'set'> for field x is not allowed: use default_factory
                    tuple -> accepted

fields() returned only name and tags. registry is in the annotations but dropped because it is a ClassVar, and note, which has no annotation, was never a field and stayed a plain class attribute. The constructor accepted at most two parameters, so passing four raised a TypeError. This message is the one printed on Python 3.13.3, and the message wording may differ between versions. tags was a different list per instance, while registry pointed from the instances and the class to the same dictionary.   • The error is raised when the class is defined, not when an instance is created.
  • The message even names the remedy (default_factory).
  • The check is a partial solution that decides by hashability.
  • A ClassVar annotation marks sharing but does not prevent it. The output shows registry still shared.

The clash between __slots__ and class attributes

In a class that uses __slots__, a class attribute of the same name is not allowed. The __slots__ section of the data model documentation (3.3.2.4) says: "class attributes cannot be used to set default values for slot variables; otherwise, the class attribute would overwrite the descriptor".

try:
                        class WithSlots:
                            __slots__ = ('x',)
                            x = 1
                    except ValueError as e:
                        print('ValueError:', e)
                    
                    class Ok:
                        __slots__ = ('x',)
                    o = Ok()
                    o.x = 1
                    print('slots instance has __dict__:', hasattr(o, '__dict__'))
ValueError: 'x' in __slots__ conflicts with class variable
                    slots instance has __dict__: False

A ValueError was raised the moment the class was created, and the message reports that the slot name conflicts with a class variable. The instance of the class that only declared slots had no __dict__. The scope of the documentation sentence is that class attributes cannot set default values for slot variables, and the output shows only that conflict and the absence of __dict__. A default for a slot variable is assigned in __init__.

Sharing on purpose - per-subclass registries and default copies

Sometimes sharing is the intent, as with registries and default settings. The issue then is not sharing itself but whether subclasses end up using the same object and whether a reader can recognise the intent. The output of three forms follows. The first two use __init_subclass__, which is called when a subclass is defined: one assigns a new list per subclass and the other gathers names into the parent list. The third is a form in which instances copy the default kept in the class dictionary.

class Plugin:
                        registry = []
                        def __init_subclass__(cls, **kw):
                            super().__init_subclass__(**kw)
                            cls.registry = []          # each subclass gets its own list
                            Plugin.registry.append(cls.__name__)
                    
                    class A(Plugin): pass
                    class B(Plugin): pass
                    print('Plugin.registry :', Plugin.registry)
                    print('A.registry      :', A.registry, ' B.registry:', B.registry)
                    
                    class Shared:
                        registry = []
                        def __init_subclass__(cls, **kw):
                            super().__init_subclass__(**kw)
                            cls.registry.append(cls.__name__)
                    class C(Shared): pass
                    class D(Shared): pass
                    print('Shared.registry :', Shared.registry, C.registry is D.registry)
                    
                    # per-instance copy of a class-level default
                    class Config:
                        defaults = {'retries': 3}
                        def __init__(self, **over):
                            self.opts = {**type(self).defaults, **over}
                    c1 = Config(retries=5); c2 = Config()
                    print('c1.opts, c2.opts, defaults:', c1.opts, c2.opts, Config.defaults)
Plugin.registry : ['A', 'B']
                    A.registry      : []  B.registry: []
                    Shared.registry : ['C', 'D'] True
                    c1.opts, c2.opts, defaults: {'retries': 5} {'retries': 3} {'retries': 3}

Plugin assigned a new empty list to each subclass whenever one was defined. A.registry and B.registry are separate lists, and the parent list gathered the two subclass names. Shared added names to cls.registry, so C and D pointed to the same list. Both are correct designs depending on intent, but which one is meant should be visible in the code. The last, Config, keeps the class-dictionary default as a read-only source and builds a new dictionary per instance holding only the overriding values. A value changed on c1 did not spread to c2 or to Config.defaults.

  • To gather into one parent, add to the parent list; to keep one per subclass, assign a new object.
  • If the class attribute is only read as the source of defaults and each instance makes a copy, sharing accidents are reduced structurally.
  • Annotate intended sharing with typing.ClassVar to mark that it is not an instance attribute. The typing documentation says this does not change runtime behavior and can be used by static type checkers.

What could not be verified

  • Behavior on Python versions other than 3.13.3. Whether the dataclass mutable-default check differed between versions was not compared by running.
  • The lookup order when a property or descriptor (__get__, __set__) is placed as a class attribute. The runs above dealt only with plain values.
  • Cases where a metaclass or a class decorator rewrites attributes.
  • How static type checkers such as mypy and pyright actually report ClassVar versus ordinary class attributes. The documentation says only that they can use it.
  • The behavior of a hashable mutable object as a dataclass default.
  • Safety when several threads modify a class-attribute list at the same time.
  • The calling rules of __init_subclass__ were not checked in the official documentation, and only the behavior shown by the output is described.
