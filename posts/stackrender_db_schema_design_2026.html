StackRender 등장 - 스키마 다이어그램을 프로덕션 DB로 만드는 오픈소스 도구

ERD 불일치와 마이그레이션 실수를 줄이는 시각적 스키마 설계 도구 - dbdiagram·DrawSQL·Prisma와 무엇이 다른가

2026-07-19 개발/인프라

서론: 방 안의 낡은 지도

거의 모든 팀에 있는 그림이 있다. Notion 어딘가에 박제된 ERD, 혹은 설계자가 퇴사하기 전에 내보낸 Lucidchart 파일. 처음엔 진실이었지만 지금은 틀렸다. 스키마는 몇 번의 ALTER TABLE과 마이그레이션 파일을 거치며 그림과 멀어졌고, 아무도 그림을 갱신할 시간을 내지 않았다. 이것이 대부분의 엔지니어링 팀에서 데이터베이스 문서화가 처한 정상 상태다.

2026년 7월 13일 GeekNews(hada)에 StackRender라는 오픈소스 프로젝트가 올라왔다. "사양에서 프로덕션 준비 데이터베이스까지"를 표방하는 스키마 다이어그램 생성기다. 이 글은 hada 소개를 그대로 옮기는 대신, StackRender의 공식 사이트와 GitHub 저장소를 직접 확인한 사실을 바탕으로 이 도구가 DB 스키마 설계의 어떤 실무 고통을 겨냥하는지, 기존 도구들과 무엇이 다른지, 그리고 어제 다룬 스펙 주도 개발 흐름과 어떻게 이어지는지를 본인 분석 중심으로 풀어본다. 모든 기능 설명은 stackrender.io와 GitHub README(2026년 7월 기준)에서 확인된 것만 다루며, 확인되지 않은 부분은 그렇다고 명시한다.

1. StackRender란 무엇인가 - 확인된 사실

1.1 핵심 기능과 워크플로

StackRender는 드래그 앤 드롭 인터랙티브 다이어그램 에디터로 테이블·컬럼·타입·제약조건을 정의하고, "Design Twice, Deploy Once"라는 모토 아래 세 단계 워크플로를 제시한다. 먼저 시각적으로 구조를 모델링하고, 몇 초 안에 마이그레이션을 생성하고, 모든 스키마 변경 이력을 기록으로 남긴다. 기존 SQL 스키마를 임포트해 다이어그램으로 역변환하는 기능과, 다이어그램을 SQL DDL로 내보내는 기능이 양방향으로 존재한다. 외래 키 순환 참조를 탐지·해결하는 기능, 성능 최적화를 위한 인덱스 추천 기능도 명시돼 있다. 클라우드 버전에는 자연어 설명으로 스키마 초안을 생성하는 AI 어시스턴트가 포함되며, 공식 문서는 "AI 어시스턴트는 사용자의 데이터베이스를 직접 변경하지 않는다"고 명시한다.

1.2 지원 DB와 기술 스택

PostgreSQL, MySQL, MariaDB, SQLite, Oracle, Microsoft SQL Server 6개 관계형 데이터베이스를 지원한다. GitHub 저장소 기준 TypeScript 98.6% 프로젝트로 React·React Flow·shadcn/ui 위에서 만들어졌다. 2026년 7월 확인 시점 기준 스타 382개, 포크 38개, 커밋 103개, 최신 릴리스는 v1.4.0(2026년 6월)이며 프로젝트는 퍼블릭 베타 단계다.

1.3 클라우드와 셀프호스팅

설치 없이 바로 쓸 수 있는 StackRender Cloud와, Docker(docker-compose up) 또는 Node.js(npm install && npm run dev)로 직접 띄우는 StackRender Community 두 갈래로 제공된다. 저장소 라이선스는 AGPL-3.0이다. 커뮤니티 사용자가 dev.to에 남긴 실사용기에 따르면, StackRender에서 설계한 스키마를 SQL 스크립트로 내보내 PostgreSQL에 직접 실행한 뒤 npx prisma db pull로 Prisma가 데이터베이스를 인트로스펙션해 schema.prisma를 자동 생성하는 흐름이 실제로 동작한다고 소개됐다. 이는 StackRender 공식 자료가 아니라 커뮤니티 활용 사례이지만, 다이어그램에서 ORM 코드까지 이어지는 파이프라인이 실제로 성립함을 보여준다.

2. DB 스키마 설계의 실무 고통 - 왜 이런 도구가 필요한가

2.1 ERD와 실제 스키마의 괴리

기능 요구가 들어오면 개발자는 테이블을 하나 늘리고, 마이그레이션 파일을 작성해 바로 적용한 뒤 코드를 배포한다. 이 순간부터 ERD는 - 애초에 있었다면 - 사실과 어긋난다. 스키마 변경이 데이터베이스 안에서 일어나고, 문서화 갱신이 그 변경에 자동으로 따라붙지 않기 때문에 벌어지는 구조적 문제다. 도구가 갱신을 충분히 쉽게 만들어주지 않으면 이 괴리는 반복된다.

2.2 마이그레이션 스크립트의 수작업 위험

수작업으로 작성한 ALTER TABLE 스크립트는 순서 실수, 롤백 스크립트 누락, 프로덕션 데이터 규모를 고려하지 않은 락 유발 같은 위험을 안고 있다. 여러 개발자가 각자 마이그레이션 파일을 만들면 파일 간 충돌과 적용 순서 문제도 흔하다.

2.3 팀 협업에서 스키마 리뷰의 어려움

스키마 변경은 코드 리뷰만큼 꼼꼼히 봐야 하지만, 실제로는 마이그레이션 SQL 텍스트만 보고 승인하는 경우가 많다. 테이블 관계나 인덱스 전략을 텍스트 diff만으로 직관적으로 파악하기 어렵기 때문에, 리뷰가 형식적으로 흐르기 쉽다.

3. 시각적 스키마 설계 도구의 가치 - 다이어그램이 진실의 원천이 될 때

3.1 다이어그램 ↔ DDL 양방향 왕복

StackRender처럼 임포트(기존 DB→다이어그램)와 익스포트(다이어그램→SQL)를 모두 지원하는 도구는, 다이어그램이 한 번 그리고 버려지는 산출물이 아니라 스키마의 현재 상태를 반영하는 살아있는 표현이 되게 한다. 레거시 DB를 처음 온보딩할 때도, 이미 존재하는 스키마를 리버스해 다이어그램으로 만든 뒤 그 위에서 변경을 시작할 수 있다.

3.2 타입·제약조건 시각화로 실수 예방

컬럼 타입, NULL 허용 여부, 기본값, 외래 키 제약을 다이어그램 위에서 한눈에 보면, SQL 텍스트만 읽을 때보다 누락이나 오타를 더 쉽게 발견한다. 특히 여러 테이블에 걸친 제약조건 일관성은 텍스트보다 그림에서 더 잘 드러난다.

3.3 관계 시각화와 순환 참조 조기 발견

외래 키 순환 참조는 텍스트 스키마만 봐서는 놓치기 쉽지만, 화살표로 그려진 관계도 위에서는 눈에 띈다. StackRender가 순환 참조 탐지·해결 기능을 별도로 명시한 것도 이 지점을 겨냥한 것으로 읽힌다.

4. 기존 도구 지형 - StackRender는 어디에 서 있나

DB 스키마 설계 도구 시장은 이미 여러 갈래로 나뉘어 있다. 본인이 조사한 범위에서 각 진영의 성격을 정리한다.

4.1 코드퍼스트 진영: dbdiagram.io, Prisma

dbdiagram.io는 DBML이라는 간결한 텍스트 DSL을 Monaco 에디터에 직접 타이핑하면 오른쪽에 다이어그램이 실시간으로 그려지는 방식이다. 실 데이터베이스 연결, AI 지원, ORM 익스포트(Prisma·Drizzle), 다중 스키마 지원은 없다. Prisma는 schema.prisma 파일에 스키마를 코드로 정의하는 ORM퍼스트 접근으로, 애초에 시각 설계 도구가 아니라 db pull/db push로 DB와 동기화하는 코드 중심 워크플로다.

4.2 비주얼 협업 진영: DrawSQL, drawDB

DrawSQL은 테이블을 드래그해 배치하고 패널에서 관계를 정의하는, 더 시각적이고 협업에 초점을 둔 편집기다. 다만 실 DB와 실시간 동기화 엔진은 아니라서 DB가 바뀌면 수작업으로 재임포트하거나 조정해야 한다. drawDB는 무료 브라우저 기반 드래그 앤 드롭 ERD 편집기로 MySQL·PostgreSQL·SQLite·MariaDB·SQL Server용 SQL 스크립트를 내보낸다. 처음부터 설계할 때 가장 빠른 편집기 중 하나로 꼽히고 스타 기준 커뮤니티도 크지만, 본질은 설계 도구이지 마이그레이션·버전관리 파이프라인은 아니다.

4.3 사후 문서화 진영: SchemaSpy

SchemaSpy는 정반대 방향에서 접근한다. 이미 존재하는 데이터베이스를 JDBC로 읽어 들여 클릭 가능한 ER 다이어그램과 javadoc 스타일 HTML 문서를 생성하는 리버스 엔지니어링·문서화 도구다. 누락된 인덱스나 고아 테이블 같은 설계 결함도 함께 짚어준다. 설계를 시작하는 도구가 아니라 이미 만들어진 스키마를 사후에 문서화하고 진단하는 도구라는 점에서 StackRender와 방향이 다르다.

StackRender의 포지션은 "그리기만 하는 도구"와 "코드로만 선언하는 도구" 사이의 틈을 메우는 데 있다. 다이어그램을 SQL로, SQL을 다시 다이어그램으로 왕복시키면서 마이그레이션 diff와 롤백 스크립트까지 같은 도구 안에서 관리하겠다는 것이 다른 도구들과 구분되는 지점이다. 다만 퍼블릭 베타 단계이므로 이 통합 파이프라인이 대규모 프로덕션에서 얼마나 안정적인지는 아직 검증 초기 단계로 봐야 한다.

5. 코드/스키마 우선 트렌드와 연결 - 어제의 스펙 주도 개발과 대비

어제 이 블로그는 코드 대신 한국어 명세를 커밋하는 스펙 주도 개발을 다뤘다. 자연어 명세가 진실의 원천이 되고 코드는 그로부터 파생되는 산출물이 된다는 내용이었다. StackRender를 들여다보면 같은 방향의 다른 갈래가 보인다.

5.1 "소스"의 정의가 이동하는 흐름

스펙 주도 개발에서는 자연어 명세가 소스이고 코드가 산출물이다. StackRender에서는 시각 다이어그램이 소스이고 SQL 스키마·마이그레이션이 산출물이다. 둘 다 사람이 직접 손으로 짜던 저수준 결과물(코드, DDL)을 도구가 생성하는 대상으로 밀어내고, 사람은 더 상위의 표현을 다루는 쪽으로 옮겨간다.

5.2 세 번째 갈래: 선언형 schema-as-code

이 흐름에는 조사 과정에서 확인한 셋째 갈래도 있다. Atlas 같은 도구는 스스로를 "Terraform for Database Migrations"라 부르며, HCL이나 SQL 텍스트로 원하는 최종 스키마 상태를 선언하면 도구가 현재 상태와의 차이를 계산해 마이그레이션 플랜을 만들어준다. Bytebase도 비슷하게 데이터베이스 변경을 코드 리뷰 프로세스에 편입시키는 DevOps형 접근을 취한다. 자연어(스펙 주도 개발), 시각 다이어그램(StackRender), 선언형 텍스트(Atlas)는 표현 형식이 다를 뿐, "실행 가능한 산출물은 파생물이고 상위 표현이 진실"이라는 철학을 공유한다.

5.3 공통점과 차이점

차이도 분명하다. 자연어 명세는 표현력이 넓지만 모호성을 완전히 없애기 어렵다. 선언형 텍스트는 정밀하지만 사람이 읽었을 때 관계의 전체 그림이 바로 보이지 않는다. 시각 다이어그램은 관계·구조를 직관적으로 드러내는 대신, 복잡한 조건부 로직이나 트리거 같은 절차적 요소를 표현하기엔 상대적으로 약하다. 세 갈래는 경쟁 관계라기보다, 각자 잘하는 표현 층위가 다른 상호보완적 도구로 보는 것이 정확하다.

6. 실무 도입 고려사항

6.1 마이그레이션 관리와 버전관리

StackRender는 스키마 변경을 자동으로 감지해 마이그레이션 파일과 롤백 스크립트를 생성하고 변경 이력을 기록한다고 밝히고 있다. 도입한다면 이 마이그레이션 파일을 애플리케이션 코드와 함께 Git 저장소에 커밋해 버전관리 대상으로 삼고, 배포 파이프라인의 리뷰 절차에 포함시키는 것이 정석이다. 다이어그램 자체를 스키마의 근거 진실(source of truth)로 둘지, 생성된 SQL 마이그레이션 파일을 근거 진실로 둘지 팀 내에서 합의해 두는 것이 좋다.

6.2 기존 DB 리버스 온보딩

레거시 프로젝트에 처음 도입할 때는 기존 스키마를 임포트해 다이어그램으로 역변환하는 기능이 유용하다. 다만 이 리버스 결과가 실제 프로덕션 스키마의 미묘한 부분(파티셔닝, 특정 DB 전용 확장 기능 등)까지 완전하게 반영하는지는 실제 임포트를 해보며 직접 검증해야 한다.

6.3 AGPL-3.0 라이선스와 벤더 종속 문제

StackRender Community는 AGPL-3.0이다. 이는 강한 카피레프트 라이선스로, 소스를 수정해 네트워크 서비스로 제공할 경우 수정본의 소스 공개 의무가 따라붙을 수 있다. 사내에서 단순히 셀프호스팅해 쓰는 것은 대개 문제가 되지 않지만, 이를 기반으로 파생 SaaS를 만들어 외부에 제공할 계획이라면 법무 검토가 필요하다. 오픈소스라는 사실 자체가 "벤더 종속에서 자유롭다"는 뜻은 아니라는 점도 함께 짚어야 한다. 클라우드 버전을 쓰기로 하면 데이터와 워크플로가 StackRender 클라우드 인프라에 묶이는 것은 다른 SaaS 도구와 다르지 않다.

6.4 퍼블릭 베타라는 리스크

2026년 7월 기준 스타 382개·릴리스 2개인 초기 프로젝트다. 기능 자체는 명확히 문서화돼 있지만, 대규모 스키마나 수억 행 테이블의 무중단 마이그레이션까지 이 도구가 안전하게 처리하는지는 확인되지 않았다. gh-ost·pt-online-schema-change류의 온라인 스키마 변경 도구가 갖춘 세밀한 락 회피 기법에 준하는 기능이 있는지도 공식 자료에서 명시되지 않았으므로, 대용량 테이블의 프로덕션 변경은 별도로 검증하거나 전용 도구와 병행하는 편이 안전하다.

7. 어떤 팀/단계에 맞나

본인의 판단으로는, 새 프로젝트를 빠르게 반복하며 스키마를 자주 바꾸는 초기 스타트업 팀, 여러 DB 벤더를 오가며 표준화된 시각 언어로 소통하고 싶은 팀, AI로 스펙에서 스키마 초안을 뽑아 시작점을 빠르게 만들고 싶은 팀에 StackRender가 잘 맞는다. 반대로 Flyway·Liquibase·Atlas 같은 성숙한 마이그레이션 파이프라인이 이미 자리 잡은 대규모 조직이라면, 기존 파이프라인을 통째로 교체하기보다 온보딩 문서화나 신규 서비스 설계 단계에서 보조 도구로 먼저 붙여보는 점진적 접근이 합리적이다.

8. 한계와 주의점

장점만 늘어놓는 것은 정직하지 않다. StackRender는 2026년 7월 기준 퍼블릭 베타이고, 커뮤니티 규모도 아직 크지 않다. AI 어시스턴트가 자연어에서 얼마나 정확한 스키마를 뽑아내는지에 대한 독립적인 벤치마크는 확인되지 않았다. 대용량·고동시성 프로덕션 환경에서의 마이그레이션 안전성도 공식적으로 검증된 바가 없다. 이런 도구를 도입할 때는 화려한 소개 문구가 아니라, 본인 팀의 실제 스키마 몇 개를 직접 임포트·익스포트해보며 결과 SQL을 눈으로 확인하는 것이 가장 안전하다.

9. 결론

StackRender가 던지는 질문은 새롭지 않다. "스키마 문서는 왜 항상 낡아 있는가"라는 오래된 불만에 대한 또 하나의 답이다. 다만 그 답의 형태 - 다이어그램을 진실의 원천으로 삼고 SQL을 산출물로 취급하는 접근 - 은 어제 다룬 자연어 스펙 주도 개발, 그리고 Atlas 같은 선언형 schema-as-code와 함께 2026년 개발 도구 지형이 "사람이 상위 표현을 다루고 도구가 저수준 산출물을 생성한다"는 방향으로 수렴하고 있음을 보여준다. 도입을 검토한다면 화려한 기능 목록보다, 본인 팀의 스키마로 직접 임포트·익스포트·마이그레이션 생성을 돌려보고 결과를 눈으로 확인하는 것이 가장 정확한 판단 근거다.
