给 LEFT JOIN 加上 WHERE 就变成了 INNER JOIN - ON 与 WHERE 的边界

在 SQLite 上实际复现十行变四行这个不报错的缺陷，并判断什么时候该用 ON、什么时候该用 WHERE

2026-07-30 开发/基础设施

症状: 每个月报表的人数都少一点

有一张按地区分的月度报表。营收合计和财务的数字对得上。但是纳入统计的客户数总是少一点。错误日志是空的，那段查询好几个月没人动过。某个月里有一个地区整块从表里消失了，可那个地区营收为 0，所以没人觉得奇怪。

原因就是一行。用 LEFT JOIN 把全部客户取出来之后，在下面加了 WHERE o.status = 'paid'。这一行把 LEFT JOIN 变成了 INNER JOIN。不是语法错误，没有告警，执行时间反而更快。唯一变小的是行数。

这种缺陷能活好几个月，是有原因的。

  • 不报错。语法和类型都没问题，所以没有任何工具会告警
  • 在开发库上复现不了。种子数据关系稠密，几乎没有缺失。没有缺失时，LEFT 和 INNER 的结果是一样的
  • 变少的那一侧是「没有的数据」。从屏幕上消失的都是取值为 0 或为空的行，看上去没有差别
  • 合计是对的。加金额的指标没变，只有数个数的指标错了，所以财务核对抓不到它

本文不再重复讲连接的种类。我在 SQLite 里建了三张表，把同一段查询一点点改动，逐个数行数。下面出现的每个数字和每段输出，都是当时屏幕上显示的原样。

执行环境。下面所有输出都是在Windows 10 Pro (10.0.19045)上实际执行的结果。引擎是SQLite 3.49.1，通过两条路径访问: 一条是CPython 3.13.3的 sqlite3 模块，另一条是Node.js v22.16.0内置的 node:sqlite。两边的结果在第 14 节做了比对。

所有脚本都先写成文件再执行。把查询和输出通过 shell 参数传递，引号会被悄悄改形。表和数据全是虚构的 customers、orders、shipments。

本文不涉及的内容。连接种类本身的概论和基本语法在SQL 入门整理里。索引、锁、N+1 这类性能话题在生产数据库生存整理里讲过。这里只深挖ON 与 WHERE 的边界这一个点。

1. 复现 - 十行变成四行的瞬间

表有三张。客户 10 人，订单 6 条，发货 4 条。其中有 4 个客户一条订单都没有。这 4 个人是本文的主角。

-- SQLite 3.49.1 -- the whole reproduction is three tables
CREATE TABLE customers (
  customer_id INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  region      TEXT NOT NULL
);
CREATE TABLE orders (
  order_id    INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL,
  status      TEXT NOT NULL,
  amount      REAL NOT NULL,
  ordered_at  TEXT NOT NULL
);
CREATE TABLE shipments (
  shipment_id INTEGER PRIMARY KEY,
  order_id    INTEGER NOT NULL,
  carrier     TEXT NOT NULL,
  shipped_at  TEXT NOT NULL
);

  (101,1,'paid',      120.0,'2026-07-02'),

  (104,4,'paid',      300.0,'2026-07-19'),

-- customers 10 rows | orders 6 rows | 4 customers have no order at all

先只加 LEFT JOIN，不带任何条件。

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ---------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  5            Eve   105       pending
  6            Finn  106       cancelled
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 10

10 行。7 号到 10 号客户没有可配的订单，所以右侧的列全被填成了 NULL。到这里完全符合预期: 客户名单完整保留，有订单就挂上来。

这时来了一个需求: 只看已付款的订单。最自然的动作就是在查询最下面加一行。

-- exactly the same query, one line added at the bottom
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  rows: 4

-- and now the same thing written as an INNER JOIN
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
INNER JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  rows: 4

10 行变成了 4 行。而紧接着用 INNER JOIN 重写的查询返回完全相同的 4 行。两段查询结果一致。也就是说上面那段里的 LEFT 这个词什么都没做。

把消失的 6 行拆开看，其实是性质不同的两类。

  • 2 行是有意的删除。5 号的 pending、6 号的 cancelled 订单。既然说只看已付款，这部分是对的
  • 4 行是无意的删除。7 号到 10 号客户。他们不是没有已付款订单，而是连订单本身都没有
  • 需求是「只看已付款订单」，不是「把客户去掉」。可查询把客户也去掉了
  • LEFT 这个词还原样留在查询里。评审时会被读成「是 LEFT JOIN，客户应该都出来」而放过去
  • 如果开发库里没有无订单的客户，两段查询会永远给出相同结果。测试抓不住

2. 把同样的条件挪到 ON 里

现在把同样的条件不放进 WHERE，而是用 AND 接在 ON 后面。字数差不多，条件表达式也一样。

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o
       ON c.customer_id = o.customer_id
      AND o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 10

又是 10 行。但内容和第 1 节的第一份输出不同。5 号客户的 pending 订单和 6 号客户的 cancelled 订单不是消失了，而是变成了 NULL。客户留下来了，只有不满足条件的订单掉了。

把行数和 NULL 的个数并排数一遍，三段查询的差别一目了然。

--- row counts, five spellings of nearly the same query ---
  LEFT JOIN, no filter           : 10 rows
  LEFT JOIN + WHERE status=paid  :  4 rows
  LEFT JOIN + ON   status=paid   : 10 rows
  INNER JOIN + WHERE status=paid :  4 rows
  INNER JOIN + ON   status=paid  :  4 rows

--- how many NULL order_id survive in each ---
  LEFT JOIN, no filter          : 10 rows, 4 NULL order_id
  LEFT JOIN + WHERE status=paid :  4 rows, 0 NULL order_id
  LEFT JOIN + ON   status=paid  : 10 rows, 6 NULL order_id
  • WHERE 版本是4 行，NULL 的右侧行 0 个。只剩下有已付款订单的客户
  • ON 版本是10 行，NULL 的右侧行 6 个。客户全部留下，只有符合条件的订单挂上来
  • NULL 行从 4 个增加到 6 个才是关键。两条不符合条件的订单不是被删除，而是被置成 NULL
  • 哪个才对，查询回答不了。报表原本想数什么才是答案

整理成表格是这样。同一个条件表达式放在哪里，会改变结果的含义。

查询形态行数NULL 的右侧行实际问的问题
LEFT JOIN, 无条件104全部客户, 有订单就带上
LEFT JOIN + WHERE40只要有已付款订单的客户
LEFT JOIN + ON106全部客户, 有已付款订单就带上
INNER JOIN + WHERE40和上面第二行是同一个问题
INNER JOIN + ON40相同。内连接里没有差别

最后两行很重要。在 INNER JOIN 里，ON 和 WHERE 的结果是一样的。所以在内连接上学会那条「条件最好写在 ON 里」的建议的人，根本没有机会体会到差别。差别只在外连接里显现。

3. 为什么 - 连接先发生, WHERE 后生效

原因只用一个顺序就能解释。连接先发生并产生中间结果，WHERE 作用在那份中间结果上。于是我把中间结果原样打印出来，在每一行旁边标注它是否能通过 WHERE。

--- the intermediate result, right after the join, before WHERE ---
  cid  name  order_id  status     -> does WHERE o.status=paid keep it?
  ---  ----  --------  ---------  --------------------------------------
  1    Ada   101       paid       KEEP
  2    Ben   102       paid       KEEP
  3    Cara  103       paid       KEEP
  4    Dan   104       paid       KEEP
  5    Eve   105       pending    DROP (not paid)
  6    Finn  106       cancelled  DROP (not paid)
  7    Gus   NULL      NULL       DROP (NULL = paid is NULL, not true)
  8    Hana  NULL      NULL       DROP (NULL = paid is NULL, not true)
  9    Ivan  NULL      NULL       DROP (NULL = paid is NULL, not true)
  10   Joy   NULL      NULL       DROP (NULL = paid is NULL, not true)
  join produced 10 rows, WHERE kept 4

被 NULL 填充的那四行是怎么死的，都写在最后一列。连接自己造出来的 NULL，在下一步被 WHERE 卡住，把这一行抹掉了。LEFT JOIN 费力留下的行，被 WHERE 又扔了一次。

做出这个判定的是三值逻辑。把比较表达式本身打印出来是这样。

SELECT NULL = 'paid'            AS null_eq_paid,
       NULL <> 'paid'           AS null_ne_paid,
       NULL IS NULL             AS null_is_null,
       (NULL = 'paid') IS NULL  AS comparison_is_null;

  null_eq_paid  null_ne_paid  null_is_null  comparison_is_null
  ------------  ------------  ------------  ------------------
  NULL          NULL          1             1
  rows: 1

-- a row survives WHERE only when the predicate evaluates to TRUE (1).
-- NULL = 'paid' is neither TRUE nor FALSE. It is NULL. So the row goes away.
-- NULL <> 'paid' does not rescue it either: that is NULL too.

NULL = 'paid' 不是假，而是NULL。WHERE 只留下结果为真的行，所以既不真也不假的行留不下来。这里分出一个常见的误解: 改写成 NULL <> 'paid' 也救不回来，那同样是 NULL。

把两个子句各自做的事按项目分开，就是下面这样。这张表是本文的骨架。

项目ONWHERE
求值时机正在构造连接的过程中连接结束之后
决定什么把什么配成一行配好之后留下什么
没有对象的左行用 NULL 填满右侧后保留不满足条件就丢掉
本例的结果行数104
内连接里的差别没有没有
执行计划LEFT-JOIN 标记还在标记消失
  • ON 是配对规则。它决定把哪个左行和哪个右行合成一行
  • LEFT 是救援规则。它把没找到对象的左行用 NULL 填满右侧保留下来
  • WHERE 是筛选规则。上面两条走完之后，只让满足条件的行通过
  • 所以在 WHERE 里写右表列的条件，就是把 LEFT 刚刚救下来的行再抹掉。两条规则正面相撞
  • 如果是左表列的条件就不会相撞。WHERE c.region = 'north' 保持 LEFT JOIN 的性质，只收窄左侧

PostgreSQL 官方文档也明确写了这个顺序。7.2.1.1 Joined Tables 一节写道，放在 ON 子句里的限制在连接之前处理，放在 WHERE 子句里的限制在连接之后处理，这个差别对内连接无关紧要，对外连接却关系重大。换句话说，这不是某个产品的怪癖，而是连接本身的定义。

4. IS NULL 这个例外 - 同样是 WHERE, 结果却相反

这里会有一个自然的反问: 那 WHERE o.order_id IS NULL 不也该全被过滤掉吗? 实际上恰好相反，留下来的只有没有订单的客户。我把三种写法并排跑了一遍。

-- 1. customers with no order at all
SELECT c.customer_id, c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id
  -----------  ----  --------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

-- 2. ON filter + IS NULL = customers with no PAID order
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 6

-- 3. orders.status is declared NOT NULL, yet IS NULL matches 4 rows
SELECT c.customer_id, c.name, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status IS NULL
ORDER BY c.customer_id;

  customer_id  name  status
  -----------  ----  ------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

第一种是4 行。原理和前面完全一样。IS NULL 是唯一一类对 NULL 返回真的条件。所以连接造出来的 NULL 行通过了 WHERE，反而是配上的行掉了。这个惯用写法叫做反连接。

第二种有用得多。条件放在 ON 里、IS NULL 放在 WHERE 里，得到的是一条已付款订单都没有的 6 个客户。这和前面的 4 个人不是同一批。5 号和 6 号有订单但没有已付款的，所以落在这里。

第三份输出值得单独记住。

  • IS NULL 是对 NULL 返回真的条件。其他比较运算符都返回 NULL
  • 所以它用来把连接造出来的 NULL 行挑出来。这是惯用写法，不是例外
  • 条件放 ON、再加 WHERE ... IS NULL，得到的是「没有符合那个条件的对象的左行」。本例是 6 行
  • ON 里不放条件，得到的是「完全没有对象的左行」。4 行。这是两个不同的问题
  • 对声明为 NOT NULL 的列写 IS NULL 也能命中。那个 NULL 不是表里存的值，是连接造出来的

5. 遇上聚合 - COUNT(o.order_id) 与 COUNT(*)

一旦加上聚合，同一个坑会换一张脸出现。我对连接结果做 GROUP BY，并排取了两种 COUNT。

SELECT c.customer_id, c.name,
       COUNT(*)          AS count_star,
       COUNT(o.order_id) AS count_order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  count_star  count_order_id
  -----------  ----  ----------  --------------
  1            Ada   1           1
  2            Ben   1           1
  3            Cara  1           1
  4            Dan   1           1
  5            Eve   1           1
  6            Finn  1           1
  7            Gus   1           0
  8            Hana  1           0
  9            Ivan  1           0
  10           Joy   1           0
  rows: 10

-- grand totals over exactly the same join
  count_star  count_order_id  count_status
  ----------  --------------  ------------
  10          6               6
  rows: 1

7 号到 10 号客户上两个值分开了。COUNT(*) 是 1，COUNT(o.order_id) 是 0。一条订单都没有的客户，订单数被报成 1，这就是本节的事故。原因很简单: 被 NULL 填充的行也是实实在在的一行，而 COUNT(*) 数的是行。

合计行上也有同样的差别。整体的 COUNT(*) 是 10，COUNT(o.order_id) 是 6。10 是客户数，6 是订单数。两个数字都对，但如果报表那一列写的是「订单数」，10 就是错的。

各个聚合函数在没有配上的分组里返回什么，整理如下。

表达式没有配上的分组的取值为什么实际后果
COUNT(*)1被 NULL 填充的行也是一行0 条订单被报成 1 条
COUNT(o.order_id)0不数 NULL 的参数通常想要的值
SUM(o.amount)NULL一个可加的值都没有不是 0。会扩散到上层计算
COALESCE(SUM(...), 0)0替换聚合结果推荐的位置
AVG(o.amount)NULL分母是 0上层平均的分母变小而被抬高
  • COUNT(*) 数的是行。被 NULL 填充的行也是一行，所以没有配上的分组会得到 1
  • COUNT(o.order_id) 数的是非 NULL 的值。没配上就是 0，通常这才是你要的数
  • 数哪一列也很重要。COUNT(o.status) 也得到 6。右表的任意 NOT NULL 列都可以
  • COUNT(DISTINCT c.customer_id) 又是另一个值。第 12 节的报表里，这个函数按地区给出了不同的答案

6. SUM 变成 NULL 而不是 0

金额这边的症状更安静。我把同一列用四种方式求和。

SELECT c.customer_id, c.name,
       SUM(o.amount)              AS sum_raw,
       COALESCE(SUM(o.amount), 0) AS coalesce_outside,
       SUM(COALESCE(o.amount, 0)) AS coalesce_inside,
       TOTAL(o.amount)            AS sqlite_total
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  sum_raw  coalesce_outside  coalesce_inside  sqlite_total
  -----------  ----  -------  ----------------  ---------------  ------------
  1            Ada   120      120               120              120
  2            Ben   80       80                80               80
  3            Cara  45       45                45               45
  4            Dan   300      300               300              300
  5            Eve   60       60                60               60
  6            Finn  210      210               210              210
  7            Gus   NULL     0                 0                0
  8            Hana  NULL     0                 0                0
  9            Ivan  NULL     0                 0                0
  10           Joy   NULL     0                 0                0
  rows: 10

-- what those NULLs do one layer further out
  from SUM(o.amount)             : sum=815  avg=135.83  count=6
  from COALESCE(SUM(o.amount),0) : sum=815  avg= 81.50  count=10
-- the totals agree, the averages do not: AVG skipped the four NULL groups.

没有配上时，SUM 是 NULL 而不是 0。因为一个可加的值都没有。这个 NULL 在原地看起来无害，问题出在往外走一层的时候。

同样的数据，平均值分成了 135.83 和 81.50。合计都是 815。AVG 不数 NULL 的分组，所以分母从 6 变成了 10。「人均消费额」这类指标，正是在这个点上被悄悄抬高。

COALESCE 该套在哪里，也实际验证了。

  • COALESCE(SUM(o.amount), 0) - 套在聚合结果上。整个分组为空时产出 0。通常这才是对的位置
  • SUM(COALESCE(o.amount, 0)) - 套在聚合之前。本数据集上答案相同，含义不同。当表里真的存了 NULL 金额时两者会分开
  • SQLite 有 TOTAL()，对空分组也返回 0。其他引擎没有这个函数，所以不要写进需要移植的查询里
  • 把 NULL 原样放出去，上层聚合就会悄悄算错。合计对、只有平均错的组合尤其危险
  • 对报表的每一列问一次「这个值可能是 NULL 吗」，大部分问题就挡住了

7. 三张表连起来 - 中间的条件会连带杀掉后面

表变成三张之后，坑也会传播。从客户到订单，再从订单到发货，做两次 LEFT JOIN。

SELECT c.customer_id, c.name, o.order_id, o.status, s.carrier
FROM customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id
LEFT JOIN shipments s ON o.order_id    = s.order_id
ORDER BY c.customer_id;

  customer_id  name  order_id  status     carrier
  -----------  ----  --------  ---------  -------
  1            Ada   101       paid       ACME
  2            Ben   102       paid       ACME
  3            Cara  103       paid       NULL
  4            Dan   104       paid       BOLT
  5            Eve   105       pending    NULL
  6            Finn  106       cancelled  ACME
  7            Gus   NULL      NULL       NULL
  8            Hana  NULL      NULL       NULL
  9            Ivan  NULL      NULL       NULL
  10           Joy   NULL      NULL       NULL
  rows: 10

10 行。3 号客户有订单但没有发货，所以只有 carrier 是 NULL；7 号到 10 号连订单都没有，所以后面全是 NULL。每一层的缺失出现在不同位置，这是这种结构的特点。

现在把条件分别放在两个位置。一个放在最后一张表上，一个放在中间那张表上。

-- filter on the LAST table
... LEFT JOIN shipments s ON o.order_id = s.order_id
WHERE s.carrier = 'ACME';

  customer_id  name  order_id  status     carrier
  -----------  ----  --------  ---------  -------
  1            Ada   101       paid       ACME
  2            Ben   102       paid       ACME
  6            Finn  106       cancelled  ACME
  rows: 3

-- filter on the MIDDLE table
... LEFT JOIN shipments s ON o.order_id = s.order_id
WHERE o.status = 'paid';

  customer_id  name  order_id  status  carrier
  -----------  ----  --------  ------  -------
  1            Ada   101       paid    ACME
  2            Ben   102       paid    ACME
  3            Cara  103       paid    NULL
  4            Dan   104       paid    BOLT
  rows: 4

条件放在最后一张表上，10 行变成 3 行。没有发货的 3 号客户，和没有订单的那 4 个人，一起消失了。也就是说把条件放在后面，会让它前面的两个 LEFT JOIN 同时失效。

条件放在中间那张表上是4 行。不过这一边还多一份损失。6 号客户那条已取消的订单是有发货记录的，订单被过滤掉之后，那条发货记录也从结果里消失了。没有被加条件的那张表的数据丢了。

再看把两个条件都挪到 ON 里会怎样。

SELECT c.customer_id, c.name, o.order_id, o.status, s.carrier
FROM customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id AND o.status  = 'paid'
LEFT JOIN shipments s ON o.order_id    = s.order_id    AND s.carrier = 'ACME'
ORDER BY c.customer_id;

  customer_id  name  order_id  status  carrier
  -----------  ----  --------  ------  -------
  1            Ada   101       paid    ACME
  2            Ben   102       paid    ACME
  3            Cara  103       paid    NULL
  4            Dan   104       paid    NULL
  5            Eve   NULL      NULL    NULL
  6            Finn  NULL      NULL    NULL
  7            Gus   NULL      NULL    NULL
  8            Hana  NULL      NULL    NULL
  9            Ivan  NULL      NULL    NULL
  10           Joy   NULL      NULL    NULL
  rows: 10

10 行原样保住了。4 号客户的已付款订单还在，但承运商不匹配，所以只有 carrier 变成 NULL。每层的条件只在自己那一层起作用。这就是在三张表上守住「也想看到没有的那些」这个意图的办法。

  • 条件只放在自己那一层。把后面表的条件放进 WHERE，前面的 LEFT JOIN 会一起失效
  • 链越长损失越大。三表连接里，最后一张表上的一个条件把 10 行变成了 3 行
  • 连没加条件的表的数据都会消失。过滤中间那张表，挂在它下面的后续行也会一起没了
  • 挪进 ON 之后每层就独立了。会出现像 4 号客户那样前一层通过、只在后一层变 NULL的行
  • 连锁连接要逐层跑探针。用逐层的 COUNT 收窄能最快定位是哪一层掉了行

8. RIGHT JOIN 与 FULL OUTER JOIN - 只是换了方向的同一个坑

我确认了换个方向是不是也一样。SQLite 在 3.39.0(2022 年 6 月 25 日发布)加入了 RIGHT JOIN 和 FULL OUTER JOIN，本环境是 3.49.1，所以两者都能跑。

我插入了一条客户编号在客户表里不存在的订单，让方向上的差别更清楚。

--- SQLite 3.49.1, same data ---
  RIGHT JOIN, no filter        : 10 rows
  RIGHT JOIN + WHERE           :  4 rows
  FULL OUTER JOIN, no filter   : 10 rows
  FULL OUTER JOIN + WHERE      :  4 rows

--- now insert one orphan order (customer_id 99 does not exist) ---
INSERT INTO orders VALUES (107, 99, 'paid', 500.0, '2026-07-25');

  LEFT JOIN             : 10 rows   <- orphan invisible
  RIGHT JOIN            :  7 rows   <- 6 orders + orphan, customers 7-10 gone
  FULL OUTER JOIN       : 11 rows   <- 10 customers + orphan
  FULL OUTER + WHERE o  :  5 rows   <- WHERE on the right table
  FULL OUTER + WHERE c  :  3 rows   <- WHERE on the LEFT table also collapses it

在 FULL OUTER JOIN 里，哪一侧的条件都会导致崩塌。右表条件放进 WHERE，11 行变 5 行；左表条件放进去，11 行变 3 行。它两侧都保留，所以两侧都脆弱。

按方向整理如下。

连接被保留的一侧把右表条件放进 WHERE本环境的支持
LEFT [OUTER] JOIN左变成内连接 (10 → 4)全部版本
RIGHT [OUTER] JOIN右变成内连接 (10 → 4)3.39.0(2022-06-25)之后
FULL OUTER JOIN两侧任一侧的条件都会崩塌 (11 → 5, 11 → 3)3.39.0 之后
INNER JOIN没有什么都不会发生全部版本
  • RIGHT JOIN 只是方向相反。它保留右表，把左表列的条件放进 WHERE 会发生同样的崩塌
  • FULL OUTER JOIN 两侧都脆弱。任意一张表的列进了 WHERE，那一侧的保留就被破坏
  • 插一条孤儿行，方向上的差别就清楚了。LEFT 给 10 行且看不到孤儿，RIGHT 给 7 行且看不到 4 个客户
  • 在 SQLite 里这两种连接只有 3.39.0 之后才能用。如果环境里混着旧构建，先确认版本

9. 执行计划说明的事情

优化器是否真的做了这个转换，用 EXPLAIN QUERY PLAN 来确认。

EXPLAIN QUERY PLAN <query>;

-- 1. LEFT JOIN, no filter
   SCAN c
   BLOOM FILTER ON o (customer_id=?)
   SEARCH o USING AUTOMATIC COVERING INDEX (customer_id=?) LEFT-JOIN

-- 2. LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- 3. LEFT JOIN + ON ... AND o.status = 'paid'
   SCAN c
   BLOOM FILTER ON o (status=? AND customer_id=?)
   SEARCH o USING AUTOMATIC PARTIAL COVERING INDEX (status=? AND customer_id=?) LEFT-JOIN

-- 4. INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

第 2 个和第 4 个计划完全相同。给 LEFT JOIN 加 WHERE，和一开始就写成 INNER JOIN，产生了逐字相同的执行计划。而且关键在于，第 1 个和第 3 个里出现的 LEFT-JOIN 标记，在第 2 个里不见了。

驱动顺序也反过来了。第 1 个和第 3 个从 SCAN c 开始扫客户，第 2 个和第 4 个从 SCAN o 开始扫订单。既然不再需要保留全部客户，从更小的表开始转就更有利。建了索引之后结论也一样。

CREATE INDEX idx_orders_customer ON orders(customer_id);

-- LEFT JOIN, no filter
   SCAN c
   SEARCH o USING COVERING INDEX idx_orders_customer (customer_id=?) LEFT-JOIN

-- LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

在实际工作里用这份输出的方法很简单。

  • 看计划里还有没有 LEFT-JOIN 标记。不见了就说明优化器已经当成内连接在处理
  • 看驱动表有没有变。原本先扫左表的计划变成先扫右表，就是保留约束消失的信号
  • 和改写成 INNER JOIN 的查询的计划做对比。两个计划相同，两段查询就是同一段查询
  • 这个检查不碰数据，所以在生产库上也能安全地跑

10. OUTER 关键字, USING, 以及常量条件

周边的语法也一起确认了。首先，OUTER 这个关键字改变了什么?

--- does the OUTER keyword change anything ---
  LEFT JOIN       rows: 10
  LEFT OUTER JOIN rows: 10
  result sets identical : True
  query plans identical : True

--- the inner-join spellings, same data ---
  JOIN        :  6 rows
  INNER JOIN  :  6 rows
  CROSS JOIN  :  6 rows   (SQLite accepts ON after CROSS JOIN)
  comma join  :  6 rows   (FROM customers c, orders o WHERE c.customer_id=o.customer_id)

什么都没改。结果集相同，连执行计划的字符串都相同。OUTER 是可选的，LEFT JOIN 本来就是外连接。反过来，JOIN、INNER JOIN、逗号连接全都是同样的 6 行。

USING 子句也原样带着同一个坑。

SELECT customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o USING (customer_id)
ORDER BY customer_id;
  rows: 10

-- append the filter to WHERE and the same collapse happens
LEFT JOIN orders o USING (customer_id) WHERE o.status = 'paid'
  rows: 4

-- there is no place to put an extra predicate inside USING
LEFT JOIN orders o USING (customer_id) AND o.status = 'paid'
  ERROR: near "AND": syntax error

-- which side does the merged column come from on an unmatched row?
SELECT customer_id, c.customer_id AS from_left, o.customer_id AS from_right
FROM customers c LEFT JOIN orders o USING (customer_id)
WHERE o.order_id IS NULL;

  customer_id  from_left  from_right
  -----------  ---------  ----------
  7            7          NULL
  8            8          NULL
  9            9          NULL
  10           10         NULL
  rows: 4

有两点值得注意。一是加上 WHERE 之后同样减到了 4 行。二是USING 没有可以接收额外条件的语法位置。加 AND 会报语法错误。也就是说写下 USING 的那一刻，「把条件挪到 ON 里」这个选项就没有了。要保住条件，只能改写成 ON，或者抽到子查询里去。

把两个子句的分工显示得最清楚的，是常量条件。

--- constant predicates, to isolate what each clause does ---
  ON c.customer_id=o.customer_id AND 1=1  : 10 rows
  ON c.customer_id=o.customer_id AND 1=0  : 10 rows   <- still 10
  ON 1=1 (no join key at all)             : 60 rows   <- 10 x 6 cartesian
  WHERE 1=1                               : 10 rows
  WHERE 1=0                               :  0 rows   <- everything gone
  WHERE c.region='north' (LEFT table!)    :  3 rows

--- ON ... AND 1=0 keeps every left row and nulls the right side ---
  customer_id  name  order_id
  -----------  ----  --------
  1            Ada   NULL
  2            Ben   NULL
  3            Cara  NULL
  ...
  10           Joy   NULL
  rows: 10

ON ... AND 1=0 原样保住 10 行。一个配对都不成立，可左边的行全部留下，只有右边变成 NULL。而 WHERE 1=0 是0 行。同一个假条件，在一个子句里被读成「不要配对」，在另一个里被读成「全部扔掉」。

  • OUTER 写不写都一样。结果集和执行计划都完全相同
  • JOIN、INNER JOIN、逗号连接都是同样的 6 行。SQLite 甚至允许给 CROSS JOIN 加 ON，结果相同
  • USING 没有接收额外条件的语法位置。把条件挪进 ON 这条退路被堵住了，所以会带条件的连接从一开始就用 ON 更好
  • USING 合并出来的列，在没配上的行里返回的是左侧的值。所以不能用那一列判断缺失。判断缺失要用右表的另一列
  • ON ... AND 1=0 和 WHERE 1=0 的差别直接展示了两个子句的分工。10 行对 0 行

11. 用子查询和 CTE 先过滤

条件变长之后 ON 子句就不好读了。替代做法是把条件放进子查询或 CTE，再连接它的结果。

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN (SELECT * FROM orders WHERE status = 'paid') o
       ON c.customer_id = o.customer_id
ORDER BY c.customer_id;
  rows: 10

--- three spellings that must agree, and do ---
  ON       : 10 rows
  subquery : 10 rows
  CTE      : 10 rows
  all three identical : True

--- and four that are not the same thing ---
  WHERE o.status='paid'                        :  4 rows
  WHERE o.status='paid' OR o.order_id IS NULL  :  8 rows
  EXISTS (paid order)                          :  4 rows
  NOT EXISTS (paid order)                      :  6 rows

三种写法都是 10 行，取值也相同。脚本里直接比较结果集，判定为一致。条件有好几个，或者子查询里还要做聚合的时候，这种写法更好读。

下面四行是四个不同的问题，这一点要说清楚。

  • ON、子查询、CTE 三种写法结果相同。选好读的那种就行
  • 条件有三个以上，或者子查询里还要做聚合时，CTE 好读得多
  • WHERE ... OR ... IS NULL 和挪进 ON 并不等价。它给出 8 行: 带着不符合条件的对象的行又活了回来
  • 如果只需要知道存不存在，EXISTS 更准确。连接可能把行变多，EXISTS 不会

12. 为什么日期范围条件最容易出这个问题

这个缺陷有一个特别高发的位置: 日期范围条件。月报和周报几乎没有例外地都带时间段条件，而那个条件所在的表，几乎必然是右边那张表。

--- a date range is the most common way to trip this ---
  no filter                                     : 10 rows
  WHERE o.ordered_at >= '2026-07-01'            :  5 rows
  ON ... AND o.ordered_at >= '2026-07-01'       : 10 rows
  WHERE o.ordered_at BETWEEN Jul01 AND Jul31    :  5 rows
  WHERE (o.ordered_at >= Jul01 OR o.id IS NULL) :  9 rows

-- the WHERE version drops two different populations at once:
--   the 4 customers with no order, and the 1 customer whose only order is from June.
-- the OR ... IS NULL version brings back the 4 but still hides the June customer.

WHERE 版本一次扔掉两类行。一类是完全没有订单的 4 个客户，另一类是唯一那条订单落在 6 月、因而在范围之外的 1 个客户。前面 4 个还有被发现的余地，后面这 1 个是「本月没有活动的客户」，找出来难得多。

常用的绕法 OR ... IS NULL 也只管一半。跑出来是 9 行。没有订单的 4 个人回来了，但 6 月下单的那个客户还是缺着。这和把条件挪进 ON 并不等价。

我把它做成实际报表的样子，两个版本并排跑。开头讲的症状在这里原样重现。

-- the report, WHERE version
SELECT c.region,
       COUNT(DISTINCT c.customer_id) AS customers_in_report,
       COALESCE(SUM(o.amount), 0)    AS revenue
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.region ORDER BY c.region;

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    1                    300
  north   2                    165
  south   1                    80
  rows: 3

-- the report, ON version
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    2                    300
  north   3                    165
  south   3                    80
  west    2                    0
  rows: 4

-- revenue per region is identical. the customer counts are not,
-- and the whole 'west' region is missing from the first report.

各地区的营收在两个版本里完全一样。所以能通过财务核对。不一样的是客户数: north 是 2 对 3，south 是 1 对 3。而且west 地区在 WHERE 版本里根本不在表上。看报表的人很难注意到一个营收为 0 的地区不再出现了。

  • 时间段条件几乎必然在右边那张表上。客户没有时间段，订单有。所以报表查询在结构上就暴露在这个坑里
  • 消失的有两类。完全没有对象的行，和有对象但落在时间段之外的行。后一类难找得多
  • OR ... IS NULL 是部分绕法。它把没有对象的行救回来，但依然藏着时间段外的那些
  • 金额合计在两个版本里相同。所以能过财务核对。分开的只有计数类指标
  • 营收为 0 的分类会整块从表里掉出去。本例里 west 地区消失了。很少有人会注意到一行不在那里

13. 诊断法 - 从已经上线的查询里找出来

现在换个方向: 从已经在跑的查询里找出这个缺陷。分成三步。

--- probe 1. how many rows does the WHERE remove? ---
  driving table rows       : 10
  after LEFT JOIN          : 10
  after WHERE              : 4
  lost by the WHERE clause : 6  (60%)

--- probe 2. unmatched ratio, straight from the join ---
SELECT COUNT(*)                                           AS joined_rows,
       SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END) AS unmatched_rows,
       ROUND(100.0 * SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)
             / COUNT(*), 1)                               AS unmatched_pct
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

  joined_rows  unmatched_rows  unmatched_pct
  -----------  --------------  -------------
  10           4               40
  rows: 1

--- probe 3. the one that settles it ---
SELECT (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id)                        AS rows_join_only,
       (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_with_where,
       (SELECT COUNT(*) FROM customers c JOIN      orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_if_inner;

  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              4                4
  rows: 1

-- rows_with_where equals rows_if_inner -> the word LEFT is doing nothing.

第三个探针能收尾。如果 rows_with_where 和 rows_if_inner 相等，那段查询里的 LEFT 就是装饰。两个数相等，意味着保留左表的意图并没有被执行。

第二个探针的 unmatched_pct 要一起看。本例里是 40%。如果这个值在开发库上是 0，那里就绝不会复现。用缺失很少的数据验证通过的查询，只在缺失很多的生产数据上给出错误的值。

同一个探针对连锁连接同样适用。而要扫整个代码库时，分两步收窄。

--- same probe on the three-table chain ---
  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              3                3
  rows: 1

--- grep patterns for a code review sweep ---
# every LEFT JOIN in the repository, with the ten lines that follow it
grep -rn -A 10 -i 'left join' --include='*.sql' --include='*.py' .

# LEFT JOIN and WHERE in the same statement, single-line queries
grep -rn -iE 'left[[:space:]]+(outer[[:space:]]+)?join.*where' .

--- what to look at once you have the hits ---
# 1. does the WHERE mention an alias that is introduced by a LEFT JOIN?
# 2. if yes, is the predicate an IS NULL check? then it is intentional.
# 3. anything else -> run probe 3 above and compare the two numbers.

整理成步骤是这样。

要确认的事方法判定
WHERE 有没有提到右侧的别名读查询原文提到了就是候选
那个条件是不是 IS NULL看条件的形态是的话就是有意的反连接
连接刚结束时的行数删掉 WHERE 再 COUNT(*)基准值
应用 WHERE 之后的行数按原文 COUNT(*)减少量就是缺失的规模
改写成 INNER 的行数删掉 LEFT 再 COUNT(*)和 WHERE 的结果相同即确认
  • 第 1 步。看 WHERE 子句有没有提到由 LEFT JOIN 引入的别名。没提到就不是这个缺陷
  • 第 2 步。提到了就看那个条件是不是 IS NULL。是的话，很可能是有意的反连接
  • 第 3 步。其余情况就跑探针 3，比较 rows_with_where 和 rows_if_inner。相等即可确认
  • 把缺失比例一起记下来。0% 的环境里复现不了，所以验证要在接近生产的数据上做
  • 修的时候要在两者中选一个: 把条件挪进 ON，或者去掉 LEFT 明写成 INNER。含糊地留着最糟

15. 判断表 - 从意图出发

结论不是「把条件写进 ON」。两个子句做的事不同，所以各自都有正确的位置。决定的不是语法而是意图。先把想说的话写成一句，再挑能表达那句话的子句。

想说的话写在哪个子句本例的行数如何验证
只看符合条件的WHERE + 明写 INNER JOIN4结果里不应有 NULL 的右侧行

把用表时的判断标准压成一行是这样。

  • 「也想把没有的按 0 显示」就用 ON。结果行数应当等于左表行数
  • 「只看存在的」就用 WHERE。但那时要去掉 LEFT，写成 INNER JOIN。意图就留在代码里了
  • 「只看没有符合条件的对象的那一侧」就用 ON + WHERE ... IS NULL。这是两个子句一起用的、唯一常见的情形
  • 收窄左表的条件就原样放在 WHERE 里。它和 LEFT JOIN 的性质不冲突
  • 拿不准就两个版本都跑一遍，比行数。看数字就知道自己问的是哪个问题

16. 检查清单, 以及不要做的事

这是用于评审和自查的清单。

  • 对每段报表查询，确认了WHERE 子句提到的别名是从哪个连接来的
  • 对用了 LEFT JOIN 的查询，数过一次结果行数是否等于左表行数
  • 用缺失比例不为 0 的数据做了验证，没有只靠种子数据放行
  • 没有把 COUNT(*) 直接用作计数指标，而是数了右表的列
  • 对 SUM 的结果判断过一次要不要套 COALESCE，没有把 NULL 放进上层聚合
  • 决定把条件放 WHERE 的地方，去掉了 LEFT 写成 INNER，让下一个人不会误读

反过来，不要做的事。

  • 在 LEFT JOIN 下面用 WHERE 加右表条件 - 如果是有意的，就写 INNER
  • 读成「是 LEFT JOIN，左边都会出来」就放过去 - 先看它下面的 WHERE
  • 用没有缺失的种子数据验证报表查询 - 那个环境里复现不了
  • 不数行数就报告「好像少了」 - 把两个数字并排写出来
  • 把 OR ... IS NULL 当成和 ON 一样 - 8 行和 10 行是不同的结果
  • 想给用 USING 写的连接加条件 - 没有语法位置，改写成 ON

# LEFT JOIN + WHERE 的坑 — 判断表, 诊断 SQL, 复现数据

> 来源: braindetox.kr — 给 LEFT JOIN 加上 WHERE 就变成了 INNER JOIN
> 验证环境: Windows 10 / SQLite 3.49.1 (CPython 3.13.3 sqlite3, Node.js v22.16.0 node:sqlite)
> 把这份文件原样贴给 AI，写上「按这些标准检查我们的报表查询」就能用。
> ⚠ 这个缺陷不会报错。只有行数变少，而且在缺失很少的开发库上复现不出来。

## 0. 一句话总结

**ON 决定「把什么配成一行」，WHERE 决定「配好之后留下什么」。**
连接先发生并造出 NULL 行，WHERE 再去检查那些 NULL 并抹掉整行。所以把右表列的条件放进 WHERE，LEFT JOIN 就变成了 INNER JOIN。

## 1. 判断表 — 从意图出发

| 想说的话 | 写在哪个子句 | 本例行数 | 如何验证 |
|---|---|---|---|
| 只看符合条件的 | `WHERE` + 明写 `INNER JOIN` | 4 | 结果里不应有 NULL 的右侧行 |
| 也想把没有的按 0 显示 | `ON ... AND` | 10 | 结果行数 = 左表行数 |
| 只看没有符合条件的对象的一侧 | `ON` + `WHERE ... IS NULL` | 6 | 右侧的列应全为 NULL |
| 只看完全没有对象的一侧 | `WHERE ... IS NULL` | 4 | 行数与 `NOT EXISTS` 相同 |
| 收窄左表 | `WHERE`(左表的列) | 3 | NULL 的右侧行应原样保留 |
| 条件太长不好读 | 拆到子查询或 CTE 里 | 10 | 行数与取值和 ON 版本一致 |

## 2. 两个子句各自做的事

| 项目 | `ON` | `WHERE` |
|---|---|---|
| 求值时机 | 正在构造连接的过程中 | 连接结束之后 |
| 决定什么 | 把什么配成一行 | 配好之后留下什么 |
| 没有对象的左行 | 用 NULL 填满右侧后保留 | 不满足条件就丢掉 |
| 内连接里的差别 | 没有 | 没有 |
| 执行计划 | `LEFT-JOIN` 标记还在 | 标记消失 |

## 4. 四种写法与真实行数(已验证)

```sql
-- 10 行
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id;

-- 4 行  <- LEFT 在这里失效
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid';

-- 10 行 <- 符合本意
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c LEFT JOIN orders o
  ON c.customer_id = o.customer_id AND o.status = 'paid';

-- 6 行  <- 一条已付款订单都没有的客户
SELECT c.customer_id, c.name
FROM customers c LEFT JOIN orders o
  ON c.customer_id = o.customer_id AND o.status = 'paid'
WHERE o.order_id IS NULL;
```

## 5. 诊断 SQL — 判定已经上线的查询

```sql
-- 探针 1. 连接刚结束 / 应用 WHERE 之后 / 改写成 INNER 的三个行数一次取出
SELECT
  (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
     ON c.customer_id = o.customer_id)                          AS rows_join_only,
  (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
     ON c.customer_id = o.customer_id WHERE o.status = 'paid')  AS rows_with_where,
  (SELECT COUNT(*) FROM customers c JOIN      orders o
     ON c.customer_id = o.customer_id WHERE o.status = 'paid')  AS rows_if_inner;
-- 验证结果: 10 / 4 / 4
-- rows_with_where = rows_if_inner，说明那段查询里的 LEFT 就是装饰。
```

```sql
-- 探针 2. 缺失比例(为 0 时该环境里复现不出来)
SELECT COUNT(*)                                                  AS joined_rows,
       SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)       AS unmatched_rows,
       ROUND(100.0 * SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)
             / COUNT(*), 1)                                      AS unmatched_pct
FROM customers c LEFT JOIN orders o ON c.customer_id = o.customer_id;
-- 验证结果: 10 / 4 / 40.0
```

```sql
-- 探针 3. 优化器是不是已经当成内连接在处理
EXPLAIN QUERY PLAN
SELECT c.name, o.order_id FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id WHERE o.status = 'paid';
-- 计划里 LEFT-JOIN 标记消失, 驱动表反转到右侧, 即可确认。

```

## 6. 聚合速查表 — 没有配上的分组的取值

| 表达式 | 取值 | 实际后果 |
|---|---|---|
| `COUNT(*)` | **1** | 0 条订单被报成 1 条 |
| `COUNT(o.order_id)` | **0** | 通常想要的值 |
| `SUM(o.amount)` | **NULL** | 不是 0。会扩散到上层计算 |
| `COALESCE(SUM(o.amount), 0)` | **0** | 推荐的位置 |
| `AVG(o.amount)` | **NULL** | 上层平均的分母变小而被抬高 |

已验证的案例: 同一份数据上两边的合计都是 815，只有平均值分成了 135.83 和 81.50。**只核对合计抓不到这个错误。**

## 7. 可以直接用在代码评审里的句子

- 「这个 WHERE 提到的别名是从哪个连接来的? 如果是 LEFT JOIN，请数一下结果行数是否等于左表行数。」
- 「如果条件确实该放 WHERE，请去掉 LEFT 写成 INNER JOIN，否则下一个人会误读意图。」
- 「你验证这张报表用的数据，缺失比例是多少? 如果是 0，这段查询等于没验证。」
- 「这里是不是该数右表的列而不是 COUNT(\*)? 没有配上的分组正被报成 1。」
- 「这个 SUM 可能以 NULL 的形式流出去。请判断要不要给聚合结果套 COALESCE。」
- 「时间段条件在右表上。本月没有活动的对象会整块从报表里消失。」

## 8. 检查清单

- [ ] 确认了 WHERE 提到的别名来自哪个连接
- [ ] 把 LEFT JOIN 查询的结果行数和左表行数比较过
- [ ] 用缺失比例不为 0 的数据做了验证
- [ ] 计数指标数的是右表的列，而不是 `COUNT(*)`
- [ ] 对 `SUM` 的结果判断过一次要不要套 `COALESCE`
- [ ] 把条件留在 WHERE 的地方都明写成了 `INNER JOIN`
- [ ] 连锁连接里逐层数了行数，定位到是哪一层掉的
- [ ] `USING` 连接加不上条件时改写成了 `ON`

## 9. 不要做的事

- ❌ 在 LEFT JOIN 下面用 WHERE 加右表条件 — 如果是有意的就写 INNER
- ❌ 读成「是 LEFT JOIN，左边都会出来」就放过去 — 先看它下面的 WHERE
- ❌ 用没有缺失的种子数据验证报表查询 — 那个环境里复现不了
- ❌ 不数行数就报告「好像少了」 — 把两个数字并排写出来
- ❌ 把 `OR ... IS NULL` 当成和 ON 一样 — 实测是 8 行对 10 行
- ❌ 核对完合计就结束验证 — 这个缺陷只在计数指标上显现
