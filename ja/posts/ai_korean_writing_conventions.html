AIが書いた韓国語はどこでずれるのか

1,058万字で測った翻訳調と緩衝表現と文体の揺れ、そして検査ではどうしても届かない層

2026年8月11日 IT・技術

はじめに - 校正ツールは通るのに読めば分かる

初稿を受け取った瞬間に何かが引っかかる。誤字はない。助詞も合っている。それでも三段落ほど読むと、これは人が書いた文章ではないという感覚が来る。どこが変かと聞かれると答えが出てこない。

その感覚の正体はたいてい統語構造だ。語彙は現地語なのに、節を組み立てる順序と述語の立て方が英語文書のものになっている。校正ツールはこの種の文を通す。規範違反ではないからだ。だから「AIっぽい」という指摘は出るのに、直す項目の一覧は出てこない。

一覧を作るには、ずれている場所を名前で呼べるようにする必要がある。以下は韓国語の技術文書1,260本、およそ1,058万字に検査規則19個をかけて得た分布だ。標本はすべて大規模言語モデルが書いた後に人が整えた文章で、コードブロックは集計から外している。

この記事の範囲 — ずれる場所の一覧、それを規約として明文化する形式、そしてその規約を生成時点と出力後の二か所で強制する方法。形態素解析器の導入や文体変換モデルの学習は扱わない。日本語の翻訳調とです・ます体の揺れにもそのまま重なる話として読める。

1. 翻訳調は単語ではなく統語構造だ

翻訳調を単語リストとして扱うと捕まらない。特定の受身標識を禁止語にしても、同じ構造が別の助詞に移るだけだ。実際に問題なのは英語の文の骨格が現地語の語彙をまとって残ることだ。骨格は五か所で表に出る。

1.1 無生物主語が人の座に立つ

英語は事物を主語に立てて能動で述べることにほぼ制約がない。韓国語も日本語もその座はずっと狭い。This tool allows you to deploy automaticallyを語彙どおりに移すと、道具が主語で述語が可能にするという文になる。自然な配置は人か動作を主語に戻す側で、結果として一段短くなる。

1.2 動作主を副詞句に入れて述語を受身にする

英語のby句が着地する場所だ。行為者がはっきりしているときは能動が基本で、受身は行為者を隠す理由があるときに使う。사용자에 의해 호출된다は사용자가 호출한다に戻る。日本語の「〜によって呼び出される」がそのまま同じ位置にある。

1.3 動詞を名詞に押し込んで助詞でつなぐ

名詞化は五つの中で最も広く出る。review of performanceが성능에 대한 검토になり、検討するで終わるはずの文が検討を実施するに伸びる。文は長くなるのに情報は変わらない。日本語なら「〜についての検討を行う」が同じ形だ。

1.4 have系が一つの動詞に固まる

翻訳者がhaveを見て手に取る動詞は、手で握るという意味に近い。属性を述べるときは存在動詞か形容詞述語が自然だ。캐시를 가지고 있다は캐시가 있다に、高い精度を持つは精度が高いになる。

1.5 副詞を作ろうとして接尾辞を足す

basically、generally、effectivelyが漢語の副詞形に自動変換され、文の頭に毎回つく。ほとんどは消しても意味が変わらない。消せない場所だけ残す。

3. 教科書が警告する場所と実際に壊れる場所は違う

翻訳調の矯正資料が真っ先に挙げる例は二重受身とby句の受身だ。標本で二重受身は1,058万字に6件。by句系は141件、1万字あたり0.1件だ。最もよく指摘される綴りの取り違えは0件、数詞と単位の間の分かち書きが揺れた箇所も0件だった。

代わりに上位を占めたのは三つの系統だ。

  • 緩衝表現 — 可能を表す言い回しが1万字あたり14.1件。10万字の原稿に140回出る計算になる。
  • 表記慣習 — 引用符の形、コロン、ダッシュのように英文組版で固まった癖が1万字あたり31.0件、13.0件、8.3件。
  • 名詞化 — 名詞化の連結が1万字あたり3.1件。翻訳調系統で唯一上位に入っている。

まとめると規範を破る間違いはほとんどなく、規範が扱わない選択がずっとずれ続けている。これは校正ツールが見る層がすでに綺麗だという意味でもある。残った問題はツールの上の層にあり、その層を扱う道具が文体規約だ。

4. 緩衝表現 - 1万字に14回の「〜できます」

可能や推量や当為を表す標識が文ごとに付くと、文章は何も主張しなくなる。設定を変えられますという文はたいてい設定を変えますか変えてくださいで終わるはずだった。エラーの可能性がありますは、条件が抜けた場所に貼り付く。

緩衝を全部消せという話ではない。判断が本当に条件付きなら緩衝は誠実な表現だ。規約に使える基準は三行で足りる。

  • 確認された事実は言い切る。根拠があるなら根拠を付けて緩衝は外す。
  • 条件で変わるなら緩衝ではなく条件を書く。遅くなる可能性がありますではなく、同時接続が200を超えると遅くなりますと書く。
  • 可能を示す必要が本当にある場所だけ残し、一段落あたり1回を上限にする。

三つ目が検査に移しやすい形だ。個々の文の正否を問わず密度で測るからだ。当為の言い回しが1万字あたり3.4件なのも同じやり方で上限を置ける。

5. 文体の揺れ - 五本に一本が文末を混ぜる

韓国語は文末が文書の格式を決める。英語は語彙選択で格式を調整するが、韓国語と日本語は文末の二、三文字が毎回あらためて宣言する。だから文末が混ざると即座に目に付く。

文末  丁寧体 47,096 · 常体 105,496 · 会話体 4,095
少数派の文末が10%を超えた文書: 237 / 1260 = 18.8%
上位5本の少数派比率: 49%, 46%, 42%, 40%, 38%

上位五本は二つの文体が事実上半々だ。一段落が丁寧体で終わり次の段落が常体で終わる文章は、読者に語り手との距離を計算し直させる。内容が正しくても初稿のように読まれる最大の原因がここにある。日本語のです・ます体とである体の混在がまさに同じ現象だ。

文体代表的な文末標本での頻度使う場所

規約に入れる項目は四行で足りる。

  • 文書種別ごとに文末を一つ指定する。報告書は常体、利用者向け案内は丁寧体というふうに釘を打つ。
  • 表のセルと箇条書きは体言止めで終える。本文の文末と混ざらないようにする最も安い方法だ。
  • 引用文の中の文末は原文に従い、検査対象から外す。
  • 見出しには文末表現を使わない。

公文書なら指定ではなく遵守事項になる。韓国の国立国語院は公共言語の書き方手引き(2022年改訂版)を公開しており、起案文・報道資料・報告書の種別ごとの原則に加えて、改善対象の行政用語100語と日本語由来の用語50語の一覧を付録に載せている。日本では文化庁の公用文作成の考え方がこれに対応する位置にある。

6. 助詞と分かち書き - 表層文字列では最後まで判定できない層

チェッカーを作るときに一番大きくやけどする場所がここだ。韓国語の正書法第42項は依存名詞を分けて書くと定め、第43項は単位を表す名詞を分けて書くと定める。規範は明確だ。問題は同じ音節が依存名詞でもあり語尾の一部でもあることだ。

直前の音節の終声と次の音節だけを見て規則を組むとこうなる。

補正前 339件 → 補正後 38件 (1万字あたり 0.04)

· 다른 조건이 같다면 추출수 온도가 높을수록  ← 比較の接続語尾、正しい

339件すべてが依存名詞ではなく比較の接続語尾だった。それを例外に抜いて38件まで減らしても、残ったものはすべて疑問の接続語尾だった。本物の誤りは一件も出なかった。1,058万字をなめて得た正解率がゼロだ。

この規則は形態素解析なしには成立しない。そして解析器を入れないのなら、規則そのものを外すのが正しい。誤検知しか出さない規則が一つあることの代償は、見逃しよりも大きい。

6.1 規則を組む側が二度滑る場所

ハングルは初声・中声・終声があらかじめ合成された一文字として保存される。だから語幹だけ書いた規則は活用形を捕まえられない。二重受身を捕まえようとして語幹보여지をかけると보여진다が抜ける。終声が音節に融合して別の文字になるからだ。

もっと静かに失敗するのは連体形語尾だ。可能の言い回しを捕まえようと/[을ㄹ]\s*수/と書くと一件も引っかからない。その音節の終声は独立した文字ではないからだ。読むにはコードポイントを分解する必要がある。

// 音節 = 0xAC00 + (初声*21 + 中声)*28 + 終声。流音の終声インデックスは8。
function jong(ch) {
  const c = ch.codePointAt(0);
  if (c < 0xAC00 || c > 0xD7A3) return -1;
  return (c - 0xAC00) % 28;
}

// 実行結果
終声の罠 - /[을ㄹ]\s*수/ 適中0件、コードポイント判定 適中2件
音節の罠 - /아니/ 適中0件、/아[니닙]/ 適中1件

同じ罠を語尾ごとの安全パターンと正規化・シェル境界まで広げて扱った記事がハングル正規表現の罠にある。日本語でも濁点付き文字や異体字で似た滑り方をするので、最初のチェッカーを書く前に目を通す価値がある。

7. 箇条書き・表・見出し - 英文書の慣習がそのまま流れ込む場所

ここで出た数字が最も実務的だ。規範ではなく慣習の問題であり、慣習は文書の中で一貫してさえいればよいのに、まさにその一貫性が崩れる。

7.1 引用符は規定がすでに整理している

2014年12月に告示され2015年1月から施行された句読点規定の改正は、縦書き専用だった隅付き括弧を横書きでも使えるように用法を変えた。書名や新聞名には二重隅付き括弧か二重山括弧を使い、二重引用符で代えてもよく、小見出し・作品名・商号・法令名には一重山括弧を使う。規約には一行書けば済む。どちらを選んでも文書全体で一つに揃える。

8. 規約をプロンプトに入れる方法とその限界

規約を強制する地点は二つある。生成時点と出力後だ。プロンプトは前者を担う。

8.1 プロンプトに入れるときの形

  • 禁止リストではなく置換ペアで書く。この形を使うなという書き方より、AによってBされる→AがBするという対応の方がはるかによく効く。代替形を与えないと別の翻訳調に移るだけだ。
  • 文末を判定可能な文で釘付けする。すべての文は常体で終える、表のセルと箇条書きは体言止めで終える、というふうに書く。
  • 例文を3〜5個付ける。規則の説明より、誤った文と直した文の対の方が効率が高い。
  • 数を決める。緩衝表現は一段落あたり1回以下という書き方は数えられる。控えめにという書き方は数えられない。
  • 規則数は20個以内に保つ。規則が増えるほど後ろの規則が薄まる。

8.2 プロンプトでは届かないこと

  • 文書単位の一貫性。箇条書きの句点混在40.9パーセントがその証拠だ。規則を知らないのではなく、前の選択が保持されない。
  • 長い出力の後半。出力が長くなるほど、最初に守った文末が後ろで揺れる。
  • 規則同士の衝突。簡潔にと根拠を付けろは頻繁にぶつかり、どちらが勝つかはプロンプトに書かれていない。
  • 検証。プロンプトは守られたかどうかを教えてくれない。守られたか知る唯一の方法は出力を測ることだ。

規則を増やして統制しようとする試みがどこで頭打ちになるかは長い方針文書ではエージェントは統制できないで別に扱った。

9. 出力後の検査で強制する - ブロック・警告・報告の三分

チェッカーを作るときの最も多い失敗はすべての規則を同じ等級でかけることだ。誤検知の多い規則が一つ付くと、人はすぐ報告全体を無視する。等級を三つに分けるとその事故が起きない。

警告等級に閾値を置くには基準値が要る。この標本の値をそのまま使うと今の状態が基準になるので意味がない。よく書けていると思う文書を十本選んで同じ規則で測り、その値を上限にする方がよい。

検査層を構文・実行時・意味に分ける一般論と誤検知の管理はAI成果物の検収体制を作るにまとめてある。ここで足すことは一つだ。現地語のチェッカーは誤検知率を規則ごとに別々に測る必要がある。上で見たように、一つの規則の正解率がゼロなのに他の規則は健全という事態が実際に起きる。

10. 規約文書の形式 - 禁止リストではなく置換表で書く

規約を文書にするとき、表が一つあればだいたい終わる。列は五つだ。

  • 対象 — 引っかかる形。チェッカーが探すパターンと同じ書き方で記す。
  • 代替 — 代わりに書く形。空欄にすると規則は守られない。
  • 例外 — 一致しても通す場合。この欄が空の規則は必ず誤検知を出す。
  • 等級 — ブロック・警告・報告のいずれか。
  • 基準 — 警告等級なら1万字あたり何件か。

ここに文書全体にかかる項目を数行足す。

  • 文末の指定と、表・箇条書きの体言止め規則。
  • 用語表記の統一 — 現地語表記を正本とし、初出時のみ英語を括弧で併記する。標本ではこの併記が1万字あたり8.0件あり、同じ用語を二度三度併記すればそこからは冗長になる。
  • 数値表記 — 桁区切りの位置、万単位表記の可否、小数点以下の桁数。
  • 数値に付ける状態表示 — 実測か推定か未測定か。これを規約に入れると根拠のない数字が目に見えて減る。
  • 文の長さの上限 — 60字を超えたら分けるという機械的な基準一つで足りる。

公共部門の文書なら規範の根拠を添える。国立国語院は正書法本文と併せて分かりやすい公文書の書き方手引きを公開し、公共言語の支援窓口も運営している。

11. この方法でも届かないことと確認できなかったこと

  • 形態素解析なしには助詞・分かち書きの規則が成立しない。上で見たとおり正解率がゼロになる。この層を本当に押さえるには解析器が要り、それはこの記事の範囲外だ。
  • 密度の基準値には根拠がない。1万字あたり何件が正常かを示す公表された基準は見つからなかった。上の表の数値は一標本の分布であって推奨値ではない。
  • 標本が偏っている。1,260本はすべて韓国語の技術・生活情報記事だ。小説・法律文書・契約書では分布が異なると思われるが確認していない。
  • プロンプト規約と出力後検査の効果を比べた数値がない。同一条件で対照するには統制された生成実験が必要で、その実験は行っていない。
  • 原因は確認できていない。二重受身がほぼ出ないのに緩衝表現が多い理由として学習コーパスや整合手法を挙げる説明はよく見るが、根拠として確認した資料がないのでここでは分布だけを記す。
  • 国立国語院の資料は案内ページまでしか確認していない。手引きの本文PDFを条項単位で突き合わせていないので、そこからの個別の例文は引用していない。
  • D系統の規則には誤検知が混ざっている。英語の括弧併記8.0件は技術文書ではおおむね正当な表記であり、見出し内のコロン6.8パーセントも広く使われる。だからこれらをブロックではなく報告等級に置いた。

結論 - 文体規約は好みではなくインターフェースだ

機械が書いた文章で直すべきものは表記ではない。その層はすでに綺麗だ。残っているのは英語文書の骨格と文書単位の一貫性の二つで、どちらも規範ではなく規約の領域だ。

順序を決めるとこうなる。

  • まず文末を釘付けする。文書種別ごとに文末一つ、表と箇条書きは体言止め。五本に一本で出る文体の揺れがこの一行で消える。
  • 次に一貫性の項目を検査にかける。箇条書きの句点混在は判定に解釈が要らず、十本に四本で出る。投入に対する回収が最も大きい場所だ。
  • 翻訳調は置換ペアでプロンプトに入れ、密度で測る。禁止語リストでは捕まらない。
  • 分かち書きの規則は解析器を入れるまで加えない。加えるとチェッカー全体の信頼を先に失う。

規約を文書に残す理由は文を綺麗にするためではない。人と機械が同じ基準で同じ文書を判定できるようにするためだ。基準が文として書かれていなければ、AIっぽいという指摘は毎回感想で終わり、次の初稿も同じものが出てくる。
