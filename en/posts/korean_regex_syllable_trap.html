The Korean Regex Trap - There Is No 아니 Inside 아닙니다

Syllable arithmetic, safe patterns per ending, NFC and NFD, shell escaping, the limits of 가-힣, and regression tests, all backed by executed output

Jul 29, 2026 Tech & IT

Introduction: The Checker Returned No Issues for Two Months

There was a checker whose job was to confirm that a disclaimer appeared in a document. The rule was simple. If the pattern /자문이 아니/ was found, pass. If not, warn. It ran every day and every day it was quiet. Since no warning had ever fired, the natural conclusion was that every document carried its disclaimer.

The truth was the exact opposite. That rule had never matched anything at all. The site body text was written in the formal polite style throughout, meaning 자문이 아닙니다. The 아니 the rule was looking for does not exist inside 아닙니다. The checker was faithfully reading every document, faithfully running the rule, faithfully finding nothing, and faithfully reporting no issues.

What makes this incident dangerous is that the outcome wore the shape of success rather than failure. No exception, exit code zero, clean logs. Nothing anywhere signalled that the checker was broken. This is what a silent failure looks like, and in code that handles Korean text it happens unusually often.

There is a single root cause. Habits formed in English collapse completely in Korean. Searching for advis in English catches advise, advisor and advisory in one shot, because inflection appends and the stem always survives as a substring. Korean does not work that way. When an ending attaches, the preceding character itself changes. Adding a terminal ending to 아니 does not produce 아니 plus something. It produces 아 + 닙 + 니 + 다. The second character has been swapped for a different character entirely.

This article covers that mechanism and the five traps that follow from it. It has one distinguishing feature. Every claim is accompanied by output that was actually executed. Reading an explanation invites a shrug of agreement, but seeing the number -1 with your own eyes is hard to forget.

Execution environment. Every output below was produced on Windows 10 Pro with Node.js v22.16.0 (win32) and is reproduced verbatim. All examples were saved as .js files and executed from disk. Section 5 explains why.

What this article does not cover. Differences between regex engines, that is dialects and portability, were covered in Regular Expressions That Work Everywhere. This article digs into the other side, the problem of Hangul as a writing system. The two do not overlap.

1. Why There Is No 아니 Inside 아닙니다 - Syllables Are Precomposed

Start with verification rather than assertion. This is output, not opinion.

node v22.16.0 / win32
--- 1-1. indexOf ---
'아닙니다'.indexOf('아니') = -1
'아닙니다'.includes('아니') = false
'아니다'.indexOf('아니')   = 0
'아니라'.indexOf('아니')   = 0
--- 1-2. code points ---
아닙니다 : 아=U+C544 닙=U+B2D9 니=U+B2C8 다=U+B2E4
아니     : 아=U+C544 니=U+B2C8
아니다   : 아=U+C544 니=U+B2C8 다=U+B2E4

In 아니다 and 아니라 the term is found immediately at position 0. In 아닙니다 the answer is -1. Laying the code points side by side makes the reason obvious.

  • The search term 아니 is U+C544, U+B2C8
  • The target 아닙니다 is U+C544, U+B2D9, U+B2C8, U+B2E4
  • The second position holds U+B2D9, not U+B2C8, so no contiguous subsequence exists

1.1 A final consonant produces a different character

Why did the second position change? The Hangul Syllables block in Unicode, spanning U+AC00 to U+D7A3, is an area where every combination of initial, medial and final component is precomputed arithmetically and laid out in order. The composition formula defined by the Unicode standard is as follows.

syllable code point = 0xAC00 + (initial_index * 21 + medial_index) * 28 + final_index

Running that formula backwards to decompose 니 and 닙 produces this.

--- 1-3. why they differ (syllable arithmetic) ---
니 U+B2C8 {"initial":2,"medial":20,"final":0}
닙 U+B2D9 {"initial":2,"medial":20,"final":17}
attaching a final consonant yields a completely different code point → '니' ≠ '닙'

The initial component ㄴ is identical and the medial component ㅣ is identical. Only the final component differs, and the moment it moves from 0 to 17, which is ㅂ, the code point shifts by 17. To a string matcher these two characters are as unrelated as the letters a and r. The human intuition that says only a small consonant was added has no representation whatsoever in the code point array.

1.2 How this differs from English

Summarized as a contrast, it looks like this. This opposition is the root of the entire article.

  • English inflects by adding characters. advise → advisor. The leading advis survives intact
  • Korean inflects by replacing characters. 아니다 → 아닙니다. The second character is swapped for a different one
  • Therefore the prefix matching strategy that works in English is structurally invalid in Korean
  • For the same reason startsWith, LIKE '아니%' and prefix matching in a search index all step into the same trap

2. Silent Failure - A Stem-Only Rule Never Catches the Formal Polite Style

If section 1 is the mechanism, section 2 is the blast radius. A bad rule and a good rule were run side by side against five inflected forms.

node v22.16.0 / win32
sentence                                        stem only (BAD)   char class (GOOD)  alternation (GOOD)
--------------------------------------------------------------------------------------
이 글은 법률 자문이 아닙니다.                        MISS              HIT               HIT
이 글은 법률 자문이 아니다.                          HIT               HIT               HIT
이 글은 법률 자문이 아니라 정보 제공입니다.             HIT               HIT               HIT
이 글은 법률 자문이 아님을 밝힙니다.                   MISS              HIT               HIT
이 글은 법률 자문이 아녜요.                          MISS              HIT               HIT
--------------------------------------------------------------------------------------
stem only (BAD)           2/5 detected
char class (GOOD)         5/5 detected
alternation (GOOD)        5/5 detected

The three rules used were /자문이 아니/, /자문이 아[니닙님녜냐]/ and /자문이 아(?:니|닙|님|녜|냐)/ respectively.

2.1 Why this is the worst class of failure

A detection rate of two out of five is not a matter of slightly disappointing performance. Looking at how the rule behaved in practice changes its character entirely.

  • Official documents are written overwhelmingly in the formal polite style. The most common real-world form sits precisely on the side that is missed
  • When a rule never fires, the checker reports not no violations found but effectively did not check. The two produce identical output
  • The mere existence of a running checker creates false confidence. Without it a human would have reviewed the text, but because it exists nobody does
  • What makes it worse is that the rate is 40 percent rather than zero. It fires occasionally on plain-style documents, so evidence that the rule works keeps getting produced

2.2 Suspect the checker before you suspect the rule

One practical principle came out of this. If a rule has caught nothing for a long time, that does not mean there are no violations. It more likely means the rule is dead. This applies with particular force to Korean text. Record match counts alongside each rule when building a checker, and add a mechanism that warns about rules sitting at zero for an extended period. That catches incidents like this early. The regression tests in section 8 are the real cure; this is the cheap insurance.

3. Safe Patterns by Ending - What to Open Into a Character Class

So how should it be written? The core idea is to open the slot where the final consonant attaches ahead of time. The positions where inflection occurs in Korean are broadly fixed, so turning those positions into a character class covers most cases.

Expression soughtCommon inflected formsRisky patternSafe pattern
아니다 family (is not) 아닙니다 / 아니다 / 아니라 / 아님 / 아녜요 아니 아[니닙님녜냐]
없다 family (absent) 없습니다 / 없다 / 없어요 / 없음 / 없이 없다 없[다습어음이는]
하다 family (do) 합니다 / 한다 / 해요 / 함 / 하는 하다 (?:합|한|해|함|하)
이다 family (copula) 입니다 / 이다 / 예요 / 임 / 인 이다 (?:입|이|예|임|인)
않다 family (negation) 않습니다 / 않다 / 않아요 / 않음 않다 않[다습아음는]
수 있다 / 없다 (can / cannot) 할 수 있습니다 / 할 수 없다 수 있다 수 (?:있|없)[다습어]

3.1 Do not trust this table as-is

The table above is a starting point, not a finished product. Korean inflection cannot be covered by enumeration. There are limits to remember while using it.

  • Irregular conjugation cannot be covered by a character class. In 돕다 → 도와 and 듣다 → 들어 the stem itself changes
  • Spacing variation punches through the rule. 할 수 있습니다 and 할수 있습니다 are different strings. Space positions must be opened with \s*
  • Particle insertion punches through too. 자문이 아닙니다, 자문은 아닙니다 and 자문이 결코 아닙니다 are all valid sentences
  • Keep widening the class and false positives climb sharply. Unrelated words beginning with 아 start matching

3.2 The point where regex stops being enough

Past a certain point it is better to change the approach itself. A workable order of escalation looks like this.

  1. Step 1 - match only the core nouns that do not inflect. Words like 자문 and 면책 make good anchors precisely because they do not change form
  2. Step 2 - split into sentences around the anchor and decide within that sentence. Do not try to match an entire sentence with one regex
  3. Step 3 - when more accuracy is needed, normalize stems with a morphological analyzer before comparing. Once 아닙니다 and 아니다 normalize to the same stem, the problem disappears
  4. Step 4 - route whatever remains ambiguous into a list for human review. That beats passing it automatically

Attempts to cover every Korean inflected form with regex generally fail. The rule keeps growing until it becomes a single line nobody dares to touch. Use regex to narrow candidates and delegate the decision to another layer and the system lasts longer.

4. NFC and NFD - When Identical-Looking Characters Are Not Equal

The second trap is subtler. The same 한 can be seen by a computer as two different strings. This is the normalization form problem defined by Unicode Standard Annex 15.

node v22.16.0 / win32
--- 3-1. length and code points ---
'한'.length              = 1 | U+D55C
'한'.normalize('NFD').length = 3 | U+1112 U+1161 U+11AB
both render as: 한 / 한

NFC is the composed form, in which 한 is the single character U+D55C. NFD is the decomposed form, splitting into three code points: initial ㅎ (U+1112), medial ㅏ (U+1161) and final ㄴ (U+11AB). On screen both render identically as 한. The eye cannot possibly distinguish them.

4.1 Every comparison fails

--- 3-2. every comparison fails ---
nfc === nfd            : false
'한국'.indexOf(nfd)     : -1
'한국'.normalize('NFD').indexOf('한') : -1
/한/.test(nfd)          : false
/[가-힣]/.test(nfd)      : false
--- 3-3. normalization fixes it ---
nfc.normalize('NFC') === nfd.normalize('NFC') : true
'한국'.normalize('NFC').indexOf(nfd.normalize('NFC')) : 0

Equality comparison, indexOf, regex testing and character class checking all fail. And a single normalization call fixes all of them. It is rare for a problem and its remedy to map onto each other this cleanly.

4.2 Sets and sorting break along with it

--- 3-4. dedup and sorting break too ---
Set([nfc, nfd]).size = 2 ← same character, counted twice
after normalization Set.size = 1
--- 3-5. filename scenario ---
are the two filenames equal : false
NFC length 7 / NFD length 10
filter(f => f.startsWith('보고서')) match count : 1 ← should be 2

Deduplication does not work and a filename filter catches only half the entries. One of two 보고서.txt files was filtered out. When deduplication fails silently it can take days to find the cause, because two strings that look completely identical sit side by side while the program insists they differ.

4.3 Where to normalize

There is one principle. Normalize once at the boundary where text enters the system, and assume the interior is already normalized. Normalizing everywhere wastes cycles and creates gaps where some paths do it and others do not.

PointNormalizeReason
Reading a filesystem listingRequiredDecomposed forms can arrive depending on platform and protocol
Network receipt / API response parsingRequiredYou cannot control which form the sender chooses
Receiving form inputRequiredResults vary by input method and paste path
Just before a database writeRecommendedUnifying at write time simplifies every query condition
Just before comparison or searchSecond bestIt works, but gaps in coverage appear easily
Just before renderingPointlessComparisons have already finished, so it is too late

Which form should be the target? For web and storage layers NFC is generally the safe default. Strings stay shorter, most systems expect composed text, and length calculations align better with human intuition. That said, when building features that operate on jamo, such as initial-consonant search, deliberately using NFD within that specific stretch of code is easier. What matters more than the choice itself is settling on one form across a single system.

5. Passing Through a Shell Kills a Regex Quietly

The third trap arises not from the writing system but at a layer boundary. It still belongs here because the outcome is exactly as quiet as the previous failures.

Suppose you run a one-liner through node -e to strip whitespace. The moment the command is handed to a shell, one layer of backslash is peeled away, and what remains is reinterpreted as a JavaScript string literal. A single backslash gets consumed twice. Here is what actually ran.

$ node -e "console.log(JSON.stringify('\s'))"
"s"

$ node -e "console.log(String(new RegExp('\s+')))"
/s+/

$ node -e "console.log(JSON.stringify('less  space'.replace(new RegExp('\s+','g'),'')))"
"le  pace"

Look at the third line. The input was less space and the result is le pace. The spaces survived intact and every letter s was deleted. Code meant to remove whitespace did precisely the opposite.

The same commands were executed in both Git Bash and Windows PowerShell 5.1, and the output was identical. This is not a quirk of one shell but a general consequence of adding one more layer.

5.1 What exactly happened

The shell is not the only culprit. JavaScript string literal rules are an accomplice. Saving the same code to a file separates the causes.

node v22.16.0 / win32
--- 4-1. regex literal vs string construction ---
literal /\s+/          : /\s+/
new RegExp('\s+')      : /s+/
new RegExp('\\s+')     : /\s+/
--- 4-2. same input, three outcomes ---
input                    : "less  space"
literal (correct)        : "lessspace"
new RegExp('\s+') (broken): "le  pace"
new RegExp('\\s+') (correct): "lessspace"

Summarized, the chain works like this.

  • In a JavaScript string literal '\s' is an unrecognized escape, so the backslash is discarded and it becomes plain 's'
  • Building a regex from that string yields /s+/. The whitespace character class has turned into the letter s
  • A regex literal such as /\s+/ never passes through the string literal stage, so it is safe
  • If it must be built from a string, the backslash has to be doubled: '\\s+'
  • Passing through a shell may require one more layer on top. Each layer adds one

5.2 Why nobody notices

--- 4-3. the same thing happens with Korean ---
input                   : 자문이 아닙니다
new RegExp('\s') removal : "자문이 아닙니다"
literal /\s/ removal     : "자문이아닙니다"
--- 4-4. why it is a silent failure ---
no exception thrown. RegExp construction succeeded : true

In the Korean string the space that should have been removed simply stayed. And the last line is the heart of this section. new RegExp('\s+') throws nothing. A perfectly valid regex object is created. It just happens to be a different regex than the one you intended. With no error the logs stay clean, and without tests it ships.

5.3 Practical rules

  • Do not pass code containing regex and Korean as shell arguments. Save it to a file and run the file
  • If a regex must be built from a string, print the result once and look at it. A single console.log(String(re)) is enough
  • If patterns are read from config files or a database, write the backslash-doubling rule into the documentation
  • When interpolating user input into a pattern, escape the metacharacters. Skipping this moves you from misbehaviour to a performance incident
  • If inline execution is unavoidable, use the shell convention of single quoting, and verify the result even then

6. What [가-힣] Misses and What to Use Instead

The character class [가-힣], reached for almost reflexively when checking Korean, points at the precomposed syllable block only. Everything else falls outside. Nine samples confirm it.

category              char      code points                [가-힣]
------------------------------------------------------------------------
precomposed syllable  한        U+D55C                     O
standalone consonant  ㄱ        U+3131                     X
standalone vowel      ㅏ        U+314F                     X
jamo being composed   ㄱㅏ       U+3131 U+314F              X
NFD decomposed        한        U+1112 U+1161 U+11AB       X
archaic yesieung      ㆁ        U+3181                     X
archaic medial ext.   ힰ        U+D7B0                     X
compatibility jamo    ㅘ        U+3158                     X
halfwidth Hangul     ﾠﾡ        U+FFA0 U+FFA1              X

Apart from the single precomposed syllable, all eight remaining samples pass straight through. In other words, a validator built on [가-힣] to reject non-Korean characters classifies all eight of those as not Korean. This is where incidents like rejected in-progress input or rejected decomposed filenames come from.

6.1 Comparing two alternatives

--- 5-2. wider alternatives ---
category              wide range   \p{Script=Hangul}
----------------------------------------------------
precomposed syllable  O            O
standalone consonant  O            O
standalone vowel      O            O
jamo being composed   O            O
NFD decomposed        O            O
archaic yesieung      O            O
archaic medial ext.   O            O
compatibility jamo    O            O
halfwidth Hangul      X            O

The two patterns compared were as follows.

  • Hand-listed wide range - [ᄀ-ᇿ㄰-㆏ꥠ-꥿가-힣ힰ-퟿], opening jamo, compatibility jamo and extension blocks by hand. It caught eight samples but leaked on halfwidth Hangul
  • Script property - /\p{Script=Hangul}/u. It caught all nine samples. Because it consults the Script property in the Unicode Character Database directly, block boundaries need no manual maintenance
  • Property escapes require the u flag. Omitting it is not a syntax error but a reinterpretation with different meaning, so it fails silently again

6.2 The gap shows up in counting

--- 5-3. counting Korean characters ---
code points in target string : 7
match(/[가-힣]/g)            : 2
match(/\p{Script=Hangul}/gu) : 7

The same string produced 2 and 7. If you are building a metric such as what percentage of this text is Korean, the choice of pattern changes the answer by more than a factor of three.

6.3 Wider is not always right

A balance is needed here. Depending on the purpose, narrow can be correct.

  • For detecting whether Korean has leaked into body text, such as multilingual contamination checks, wide is correct. Missing hits leaves the checker powerless
  • For validating a username field, narrow may be better. Storing a half-composed ㄱㅏ as a name is a problem
  • For search indexing, normalize first and then apply the wide range. Reversing the order drops decomposed text from the index
  • Either way, the order is to write down in a sentence what should pass and then pick the pattern. Picking the pattern first means the intent gets justified after the fact

7. Length Is Not One Number - Traps Outside Regex

Even outside regex, the same root produces problems. The phrase character count has four different answers.

한글            2            2                  6                    2
NFD 한글        6            6                  18                   2

The string 한글 measures 2, 2, 6 and 2 depending on the yardstick. Arriving in decomposed form it becomes 6, 6, 18 and 2. The same two characters jump from 2 to 6 storage units.

7.1 Storage size varies by encoding

--- 6-2. bytes per encoding ---
'한글' utf8 bytes  : 6 (3 bytes per character)
'한글' utf16 bytes : 4

In UTF-8 a Korean character is 3 bytes; in UTF-16 it is 2. In environments where database columns are sized in bytes, how many bytes up to 10 characters means must be computed together with the encoding. Copying a character-based length limit straight into a byte-sized column truncates Korean input.

7.2 Truncation cuts characters in half

--- 6-3. slice cuts a character in half ---
NFD string slice(0,2) : "하" ← only initial+medial remain, broken character
NFC string slice(0,1) : "한"

Slicing a decomposed string severed the final consonant, turning 한 into 하. This happens when generating preview text or cutting summaries. The principle normalize before truncating holds here too. To handle emoji, flags and family sequences safely, cut on grapheme cluster boundaries.

  • Preview and summary truncation → normalize to NFC first, then cut on grapheme clusters
  • Database column design → byte based, with the encoding stated
  • Character limit messages shown to users → grapheme clusters, as users perceive them
  • Hashing and signing targets → fix the normalization form by contract. Otherwise the same character yields different hashes

8. How to Build Regression Tests - The Only Way to Catch a False Pass

Every trap so far is quiet. No exceptions, clean logs. So what catches them? Nothing except testing the checker itself.

The key is splitting test cases into two kinds.

  • MUST_HIT - the rule has to fire on these sentences. Include formal polite, plain declarative, connective and nominalized forms
  • MUST_MISS - a hit here is a false positive. Widening a rule tends to break things right here
  • Either kind alone is only half a test. With MUST_HIT only, a rule of /./ would pass

Two rules were run through the same test suite.

[bad rule] /자문이 아니/
  [FAIL] MUST_HIT  formal      본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  plain       본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  connective  본 글은 법률 자문이 아니라 일반 정보입니다.
  [FAIL] MUST_HIT  nominalized 본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS unrelated   전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS substring   자문위원회가 심의했습니다.
  => pass 4 / fail 2

[good rule] /자문이 아[니닙님녜냐]/
  [PASS] MUST_HIT  formal      본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  plain       본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  connective  본 글은 법률 자문이 아니라 일반 정보입니다.
  [PASS] MUST_HIT  nominalized 본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS unrelated   전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS substring   자문위원회가 심의했습니다.
  => pass 6 / fail 0

=== summary ===
bad rule failures  : 2 ← a regression test would have caught this on day one
good rule failures : 0

A six-line test immediately exposed a defect nobody had noticed for two months. The incident in the introduction would have been blocked on day one by this test alone.

8.1 What must go into the test cases

  1. Formal polite style - endings in ~습니다 and ~ㅂ니다. The most common form in official documents and the one most often missed
  2. Plain declarative style - endings in ~다. The stem often survives intact, so even a bad rule passes. Including only this makes the test meaningless
  3. Connective and nominalized forms - ~라 and ~ㅁ을. These are the positions where the final consonant actually changes
  4. Colloquial and contracted forms - ~예요 and ~네요. Mandatory if you handle user-generated content
  5. Three kinds of false-pass samples - a sentence unrelated to the rule, one where the key word carries a different sense, and one where the anchor word is part of a longer word

8.2 Additional safeguards when building a checker

  • Do not run regression tests inline. If the escaping accident from section 5 happens inside the test code, the test itself starts lying. Always save it to a file
  • Break the rule deliberately and confirm detection. If damaging a rule does not turn the test red, that test is protecting nothing
  • Record match counts per rule. A rule sitting at zero for a long stretch is probably dead
  • Draw sample sentences from real content. Invented sentences do not reflect the actual register
  • Every time a rule is fixed, add the test case first. A newly discovered miss is itself the new test case

9. What This Approach Still Cannot Prevent

For balance, here are the limits. Even applying every prescription above, some problems remain.

  • Irregular conjugation - when the stem changes wholesale, no character class covers it. A morphological analyzer is required
  • Spacing latitude - Korean is forgiving about spacing errors, so real documents contain every possible variation
  • Semantic judgement - 자문이 아닙니다 and 자문이 아니라고 할 수는 없습니다 mean opposite things while looking similar. Regex cannot distinguish them in principle
  • The cost of a morphological analyzer - accuracy rises, but dictionary maintenance, processing speed and deployment size come with it. Whether one checker justifies that is a separate decision
  • Side effects of normalization - rarely, normalization changes the original bytes, so where signature verification or byte preservation is required the pre-normalization original must be stored separately
  • The breadth of the Script property - \p{Script=Hangul} is good because it is wide, but on screens that need narrow validation it is excessive

So the conclusion is not write better regex. It is closer to know the range regex can carry, and switch tools at the point where it stops.

Conclusion: Suspect the Checker Before You Suspect the Rule

This article started with a checker that stayed quiet for two months. The cause was not regex syntax, not a library bug, not an encoding setting. It was a fact explainable in one line: Korean syllables are precomposed single characters. The moment a prefix-matching habit learned in English was carried over to Korean, the rule died, and nothing existed to signal that it had.

Restated, there are six points. First, Korean changes the preceding character when an ending attaches, so stem matching does not hold. Second, open the final-consonant slot with a character class while knowing enumeration will not cover everything. Third, normalize once at the boundary and assume the interior is normalized. Fourth, do not pass regex through a shell, and print the constructed regex to check it. Fifth, [가-힣] is precomposed only, so consider \p{Script=Hangul} depending on purpose. Sixth, freeze all of it into regression tests.

The sixth matters most. The first five are knowledge; the last is the structure that holds when the knowledge is forgotten. People forget without fail. New joiners never knew in the first place. Only the tests remain.

There is something you can do right now. Open the list of rules that inspect Korean text and look for any that have not fired once in three months. If you find one, feed it a single formal-polite sentence and run it. That one line settles whether the silence meant no violations or a dead rule.

# Korean Regex Review Checklist

> Source: braindetox.kr — The Korean Regex Trap: there is no 아니 inside 아닙니다
> Standards: Unicode UAX #15 (normalization), UAX #29 (grapheme clusters), UAX #44 (Script property)
> How to use: scan top to bottom before reviewing any checker, parser, or search code that touches Korean text.
> You can paste this file into an AI assistant and ask it to audit your codebase against it.

## 0. 30-second triage — if any of these apply, work through everything below
- [ ] You match Korean strings with regex or `indexOf`
- [ ] Korean text arrives from user input, filenames, or an external API
- [ ] You count characters or truncate strings
- [ ] Patterns come from config files, environment variables, or CLI arguments

## 1. Pattern authoring — how to open up the inflection slot
- [ ] Any pattern that matches only a bare stem (`아니`, `없다`, `하다`, `이다`, `않다`)
- [ ] The slot where a final consonant attaches is opened with a character class or alternation
- [ ] The formal polite ending (`~ㅂ니다` / `~습니다`) is explicitly covered
- [ ] The nominalized form (`~ㅁ` / `~음`) is covered
- [ ] Colloquial and contracted forms are covered where user-generated content is involved
- [ ] Spacing positions are opened with `\s*` or `\s+` (Korean spacing varies in practice)
- [ ] Particle variation is considered (`이/은/는/가`)
- [ ] False positives were re-measured after widening any class

### Quick reference for inflection slots
| Family | Slot to open | Minimum candidates |
|---|---|---|
| 아니다 (is not) | second syllable | 니 닙 님 녜 냐 |
| 없다 (absent) | second syllable | 다 습 어 음 이 는 |
| 않다 (negation) | second syllable | 다 습 아 음 는 |
| 하다 (do) | first syllable | 합 한 해 함 하 |
| 이다 (copula) | first syllable | 입 이 예 임 인 |

### When regex is no longer the right layer, escalate in this order
1. Anchor on a **non-inflecting noun** instead of a verb form
2. Split into **sentences** around the anchor, then decide within the sentence
3. If more accuracy is needed, normalize stems with a **morphological analyzer**
4. Route remaining ambiguous cases to a **human review list** (never auto-pass them)

## 2. Normalization — pick one boundary and do it once
- [ ] A single normalization form is chosen for the system (NFC is the usual default)
- [ ] Filesystem listings are normalized right after reading
- [ ] Network payloads and API responses are normalized right after parsing
- [ ] Form input is normalized on receipt
- [ ] Values are unified just before database writes
- [ ] Comparison, sorting, and deduplication are guaranteed to see one form
- [ ] Strings are normalized before `slice` / `substring`
- [ ] For hashing or signing, the form is **fixed by contract**
- [ ] Where the original bytes must be preserved, the pre-normalization value is kept separately

## 3. Shells and tooling — count the backslash layers
- [ ] Regex patterns are not passed as shell arguments (`-e`, `--pattern`)
- [ ] If they are, each extra layer requires one more backslash
- [ ] Backslashes are doubled when a regex is built from a string
- [ ] The constructed regex is **printed and eyeballed once**
- [ ] User input interpolated into a pattern is metacharacter-escaped
- [ ] Regression test code is stored in a **file**, not run inline

### One-line self-diagnostic
Log the string form of every regex right after you construct it.
If it differs from what you intended, it shows up immediately. No exception is ever thrown.

## 4. Character ranges — what counts as Korean
- [ ] If you use `[가-힣]`, you know it covers **precomposed syllables only**
- [ ] You have written down, in a sentence, which of these to accept and which to reject
  - [ ] Standalone consonants and vowels (`ㄱ`, `ㅏ`)
  - [ ] Input still being composed
  - [ ] Decomposed (NFD) strings
  - [ ] Archaic Hangul jamo
  - [ ] Compatibility jamo
  - [ ] Halfwidth Hangul
- [ ] Where a wide match is needed, `\p{Script=Hangul}` was considered
- [ ] The `u` flag is present on property escapes (without it the meaning silently changes)
- [ ] For search indexes the order is **normalize, then range-check** (reversed, decomposed text is dropped)

### Recommended width by purpose
| Purpose | Recommended range | Why |
|---|---|---|
| Contamination detection | Wide (`\p{Script=Hangul}`) | Missing hits makes the checker useless |
| Input validation | Narrow (`[가-힣]` etc.) | Blocks storing half-composed jamo |
| Search indexing | Wide, after normalization | Guards against decomposed input |
| Statistics and ratios | Wide | Narrow ranges skew counts several times over |

## 5. Length and truncation — which unit are you counting
- [ ] The unit behind the phrase character count is defined (code unit / code point / byte / grapheme cluster)
- [ ] If a database column is byte-sized, the encoding is stated and the math is done
- [ ] Counts shown to users are in **grapheme clusters**
- [ ] Preview truncation does not strip a trailing consonant off a syllable
- [ ] Emoji and combining sequences are accounted for where they can appear

## 6. Regression tests — test the checker, not just the code
- [ ] MUST_HIT cases exist (sentences the rule has to catch)
  - [ ] Formal polite style
  - [ ] Plain declarative style
  - [ ] Connective form
  - [ ] Nominalized form
  - [ ] Colloquial form (where relevant)
- [ ] At least three MUST_MISS cases exist (a hit here is a false positive)
  - [ ] A sentence unrelated to the rule
  - [ ] The key word used in a different sense
  - [ ] The anchor word appearing inside a larger word
- [ ] Sample sentences are taken from **real content** (invented ones use the wrong register)
- [ ] Breaking the rule on purpose makes the test fail
- [ ] Match counts are recorded per rule
- [ ] Rules with zero matches over a long period raise a warning

### Test skeleton
```
MUST_HIT  = [formal, plain, connective, nominalized, (colloquial)]
MUST_MISS = [unrelated, different sense, substring of another word]
result = all MUST_HIT matched AND no MUST_MISS matched
```

## 7. Final three lines before shipping
- [ ] Does this rule actually catch **one formal-polite sentence**
- [ ] Does this code actually handle **one decomposed input**
- [ ] Did you **print the constructed regex** and look at it
