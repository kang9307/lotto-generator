引言：零违规这个结果，你信到什么程度

你跑了检查器，结果是零违规。在被这个数字安抚之前，有一个问题值得先问。这个零究竟是对象本身干净，还是检查器什么都没看。两种情况打印出来的都是零。

检查别人的代码有一个奇怪的性质。评分器、测试、检查器、静态分析器、审校脚本全都属于这一类。这类代码坏掉时，不会抛异常也不会把界面弄花。它只是让通过变多。而通过是没有人会去翻开的。

最近有一份记录把这个问题呈现得很干净。一个人写了自动评分的代码来评订单处理的答卷，后来把同样的二十九份答卷连同评分标准一起交给一个商用LLM，让两边各自打分。二十七份两边判定相同。分歧的那两份才是关键，翻开一看，错的不是模型，而是他自己写的评分器。

本文要谈的不是这件事本身，而是它背后的问题。检查的一方出错时会发生什么，怎样才能察觉，以及什么时候可以相信自动评分的结果。对于把测试、检查器、审校脚本当作信任依据的人来说，这是同一个话题。

1. 失败很吵，误通过很静

检查器可能犯的错有两个方向：把不存在的问题说成存在的误报，和把存在的问题说成不存在的漏报。两种错误对称地产生，但被发现的概率完全不对称。

误报会立刻摆到人面前。构建变红，发布停下，有人去翻那一行。通常几分钟内就水落石出。漏报则不留任何痕迹。日志不会多出一行，仪表盘上的数字甚至更好看。发现漏报的唯一路径是问题以别的方式爆出来之后往回追，而那时候，以这个检查器为依据做出的几个月的决定已经堆起来了。

这种不对称会带来几个实务上的后果。

  • 改检查器时，压力只朝减少误报的方向施加。没有人会要求你增加漏报，但让它安静一点的要求每周都来
  • 多加一个条件把误报消掉，那个条件切掉的真实违规也会一并消失。这份损失不会显示在屏幕上
  • 用抓到多少件来评价检查器的质量，方向就反了。什么都不抓的检查器最安静，口碑也最好
  • 一条长期误报的规则会让人把整张清单都无视掉，把真实违规掩盖很久

最后一条尤其麻烦。这个站点自己的审校工具上也发生过：某条规则在某个语言版本里总是把同一个项目报成违规，人们习惯性地跳过那条警报，结果混在下面的两处真实缺陷将近两个月没被看到。检查器运行正常。缺陷在于人已经不再信任它。

2. 检查别人的代码出错的四种形态

把检查器的缺陷分成类型，就知道该先看哪里。实际会遇到的形态大致有四种。

类型症状为什么看不见抓法
规则太窄把正确答案的其他形态算成违规，或者完全看不见只有写规则的人知道的形态进了规则与性质不同的第二判定做对照
范围太窄检查对象本身漏掉了，于是出现零输出里没有对象数量，无法与零违规区分始终打印检查了多少个对象
只看形态名字、标签、扩展名对上就放行通过不会留下依据植入阳性样本确认能被检出
标准本身错了检查器跑得很准，但判定标准是错的所有判定者共享同一套标准由人直接给少量样本打标

四种里前三种可以用工具抓。只有第四种工具抓不到。如果标准错了，基于规则的检查器和模型判定者会给出同样的答案，一致率反而会漂亮得很。

3. 规则太窄就会把有报成没有

这是最常见的类型。人写规则时写的是自己见过的形态。问题在于有效的形态有好几种，而规则里只进去了一种。

前面提到的那份评分记录里，分歧的两份中有一份正是这个形态。答卷并不是没处理某个项目，而是反问了尺寸、请求确认，而评分代码只机械地检查那个项目编号在不在已确认列表里。列表里没有，于是算成遗漏。人一读就知道这是明显恰当的回应，读了整份文档的模型也是这么判的。

这个结构不分领域地反复出现。

  • 只认识一种日期格式的解析器，从记法变更那天起开始报告没有数据
  • 假定了语序的正则表达式，在一种语言里刷出误报，在另一种语言里整片抓不到
  • 要求出现否定词的规则，把所有不用否定词却表达同样意思的句子全部漏掉
  • 把合格条件写成精确字符串相等，导致同义词和缩写被判为不合格

第二条和第三条是这个站点在多语言审校中实际遇到过的类型。用临时拼出来的正则去量规模，每种语言会朝不同方向偏，再拿那个数字去跑批量编辑，本来就正常的文档里会被再塞进一遍同样的内容。

下面是用来说明思路的例子。这是未经运行验证的伪代码，并不以直接放进真实评分器为前提。

# 窄规则 - 只看编号在不在已确认列表里
def is_handled_narrow(answer, item_code):
    return item_code in answer.confirmed_codes

# 放宽后的规则 - 反问也算作有效处理
def is_handled(answer, item_code):
    if item_code in answer.confirmed_codes:
        return True
    if answer.has_clarification_request(item_code):
        return True          # 请求确认不等于没处理
    return False

重要的不是代码而是次序。在放宽规则之前，你得先知道它需要放宽。窄规则从来不会自己说自己窄。

4. 看不到的范围等于不存在

就算规则是对的，只要该被规则处理的输入没进来，结果是一样的。检查器的输入边界，就是它盲区的定义。

同一份记录里第二处不一致就属于这一类。答题者把确认请求写在了页边空白而不是指定栏里，而代码评分器被写成只读指定字段，所以根本不知道那条备注存在。模型把整份文档读了一遍，因此看到了它。这不是规则的问题，而是范围的问题。

实务中这个类型藏身的地方是固定的几处。

  • 生成文件清单的模式悄悄漏掉隐藏文件或某个扩展名
  • 只从末尾读固定行数日志的检查，看不到那之前发生的事件
  • 编码不同的文件读取失败，异常被吞掉，最后变成对象数为零
  • 前一级的过滤条件已经筛掉大部分，到检查这一级只剩下几条

对策很简单，简单到常常被忽略。永远把检查过的对象数量打印出来。零违规和零对象是完全不同的两件事，如果输出一模一样就无从分辨。再加上对象数量比昨天变化很大时发出警告，安静的截断基本都能抓住。

5. 只看名字就放行的检查

第三种类型把形态和含义搞混了。类名在就认为样式生效了，模式键在就认为值有效，标签在就认为内容对。这是把存在性检查误当成内容检查。

这个站点的审校工具里有两种类型属于此列。一种是只确认链接是否存在的检查。链接全都活着，所以结果长期干干净净，而真正的问题是英文文档指向了韩文页面。直到另加一条检查语言是否一致的规则，才大批暴露出来。

另一种是用字符串去找标记的规则。标签上多加了一个属性，模式就不再匹配，而检查器没有报错，而是安静地放行。零违规继续打印出来。有却找不到的规则，比没有规则更糟。没有规则至少大家知道那里没人看，而找不到的规则会让人以为已经看过了。

值得记住的一句话。检查器打印通过时，它的意思不是对象是对的，而是这条规则没有命中。这两句话之间的距离，随着规则变窄而变远。

6. 交叉验证 - 当两个不同的判定说法不一致

到这里为止的所有类型都有一个共同点。检查器无法靠自己产生自己错了的信号。所以信号必须从外面引进来，引进的办法就是交叉验证。

但不是随便两个都行。两个判定者不能共享同一个前提。用同一个解析器的两个检查器，复用同一条正则的两条规则，那不是交叉而是重复。它们会在同一个位置一起出错。

评分方式擅长的位置结构性盲区可重现性
基于规则的检查格式、数值、是否存在。快而且便宜把没预料到的有效形态算成违规完全可重现
与参考答案比对正确答案唯一的任务正确答案有多个时完全无力完全可重现
模型判定意图、上下文、整份文档。第二份实现便宜同样的输入可能得不到同样的判定部分可重现
人工打标唯一能检验标准本身是否成立规模上不去，人与人之间也会分歧部分可重现

该从表里读出来的不是每一行的长处，而是盲区彼此不重叠这个事实。基于规则的强在形态、弱在意图，模型判定正好相反。把两者并排，判定就会在一方的盲区区间里分歧，而分歧点就是要调查的清单。

运营规则很简单。一致携带的信息少，不一致才是信息。两份判定相同并不保证两边都对，但两份判定不同时，至少有一边确定是错的。成本也承受得起，因为不必重审全部，只需要人翻开分歧的那几份。

7. 把LLM放在第二评分者的位置能得到什么

交叉验证是个老想法，但实际上几乎没人做。原因很清楚：做第二份实现的成本和第一份差不多。把评分器写两遍这种提议，在任何一次会上都很难通过。

模型判定改变的不是精度，而是这个成本。把评分标准用自然语言整理好交出去，第二份判定就回来了。前面那份记录里发生的正是这件事。没有重写评分器，只是把同样的标准写成句子交给模型，就产生了两份独立的评分结果，而它们的差异指向了缺陷。

模型判定与基于规则的做法明显不同的地方有三处。

  • 范围更宽。它不是只看指定的栏位，而是读整份文档。写在页边空白处的内容也会进入输入
  • 它看的是意图而不是形态。措辞不同但意思相同就给同样的判定，还会承认反问这类规则从来不知道的有效形态
  • 它逼你把标准重新用语言说一遍。写要交给模型的那些句子时，本来隐含在代码里的假设会浮出来

第三条看着像副作用，其实价值很大。把标准用自然语言完整写一遍，你会发现团队自以为达成过共识的项目里，有些其实从来没被真正约定过。

8. LLM评分者的限制 - 非确定性与共享的误解

出于同样的原因，需要提防的地方也很清楚。不要把模型判定放在与基于规则的检查同一个位置上。

第一，它可能不可重现。用同样的标准对同一份答卷评两次，不保证得到同样的结果。直接挂在关卡上，代码一行没改，仅仅重跑一次结果就会翻转。如果非要用在关卡上，就多跑几次取多数，或者干脆只把它用于分歧检测而不是用于判定本身。

第二，标准错了它会跟着一起错。这是更根本的限制。拿到错误评分标准的模型，会忠实于那个标准给出错误的判定，并与用同一标准写出来的规则检查器愉快地一致。一致率高这个事实不是两个判定者都对的证据，也可能是两者共享同一前提的证据。交叉验证抓的是实现的错误，抓不到标准的错误。

第三，一致率受样本构成左右。这也是那份记录的作者自己点出来的限制。二十九份里有二十六份是正确的，两个评分者什么都不做一致率也会很高。要衡量分辨力，样本里必须有足够多的错误案例。全是好答案的样本堆里跑出来的高一致率，什么都证明不了。

第四，评价评分者的问题又回来了。要验证模型判定就需要另一个判定者，而那个判定者也需要被验证。这个后退不会终止在工具上。总得有个人在某处直接读少量样本并打上标签，那些标签就是地板。既然不可能全部人工看，怎么挑出人要看的那部分样本就成了真正的设计问题。

9. 给检查器本身加回归测试

交叉验证是用来找没预料到的形态的装置。反过来还需要另一个装置，守住已知形态是否还在被抓到。那就是给检查器加的回归测试。

方法如其名。把检查器必须抓到的缺陷用手做出来植入样本，跑检查器，断言它们全部命中。同时还要放上绝对不能被命中的正常样本，确认一个都没命中。方向和普通代码的单元测试相反：不是期待正常输入产生正常输出，而是期待异常输入拉响警报。

植入的样本期望判定失败时意味着什么
过去真实发生过的缺陷必须检出同样的事故会再次通过
规则文本的边界值必须检出收紧规则时削掉了检测力
曾经引发误报的正常案例不应检出误报复活了
写法不同但意思相同的正常案例不应检出规则对表层形态过拟合了
对象列表为空的输入报告对象数为零分不清零命中和零个被看

下面是用来传达思路的骨架。这是没有实际运行验证过的例子，框架和写法要按各自的环境调整。

# 检查器自身的回归测试 (概念示例，未经运行验证)
POSITIVE = [                      # 必须命中的样本
    ("case_missing_field", "MISSING"),
    ("case_wrong_order",   "CRITICAL"),
]
NEGATIVE = [                      # 绝对不能命中的样本
    "case_clarification_request",  # 反问属于正常处理
    "case_note_in_margin",         # 页边备注也要读到
]

def test_checker_detects_known_defects():
    for sample, expected in POSITIVE:
        assert run_checker(load(sample)).kind == expected

def test_checker_stays_quiet_on_valid_input():
    for sample in NEGATIVE:
        assert run_checker(load(sample)).violations == []

def test_scope_is_not_silently_empty():
    result = run_checker(load("case_empty_scope"))
    assert result.scanned_count == 0   # 区分零个被看和零个命中

让它在日常中持续活着，有一条规则。每发现一种新形态，就把这种形态加进样本。不断增长的样本集，正是让同一起事故不发生第二次的东西。每次动规则先跑这套测试，检测力被削掉的那一刻就会出现在屏幕上。没有回归测试就去收紧规则，等于闭着眼睛把灵敏度调低。

10. 修好评分器之后旧分数算什么

修掉检查器的缺陷并不只带来好事。对象一点没变，已经公布的分数却变了。前面那份记录里发生的正是这样：模型和答卷都没动，仅仅因为修了评分器，之前公开的结果就不一样了。

由此得出的原则很短。分数不是对象单独的函数，而是对象与评分器版本共同的函数。不注明评分器的分数，等于没有单位的数字。尤其是把多轮排成时间序列去读趋势的那一刻，用不同尺子量出来的值就上了同一张图。

  • 记录分数时，把评分器版本和规则内容的指纹一并留下
  • 修评分器的当天，把历史对象全量重新评分并替换时间序列
  • 如果无法重评，就在图上用竖线标出评分器变更时点，并在发布文里用一行写明这是哪一版量出来的
  • 引用外部分数时也问同一个问题：这个值是用哪个评分器量的

最后一条在读基准测试数字时直接适用。名字相同的评估，评分实现不同，值就会不同。两家机构公布的同名分数并排比较之所以常常不成立，原因就在这里。

11. 信任自动评分之前的检查清单

把上面的内容压缩成可执行的形式就是这些。无论是刚做出来的检查器，还是接手过来在用的检查器，按同样的顺序问一遍即可。

  • 输出里有检查过的对象数量吗。没有的话就无法区分零命中和零个被看
  • 阳性样本真的会被命中吗。在植入已知缺陷跑一遍之前，检测力是未知数
  • 阴性样本不会被命中吗。误报积累起来，人就会开始无视整张清单
  • 每条规则最近有抓到过东西的记录吗。几个月都是零的规则可能已经悄悄死了；如果从未与性质不同的第二判定做过对照，漏报区间就是整片未测量
  • 有没有人直接读过少量样本并打上标签。标准本身的错误只会在这里暴露
  • 样本里有足够多的错误案例吗。全是正确答案的样本跑出来的高一致率没有信息量
  • 评分器版本有跟分数一起记录吗。没有的话，轮次之间的比较不成立
  • 结果分歧时有让人去翻开的流程吗。把不一致自动往一边靠拢，信号就消失了

顺序是有意义的。上面两条一个下午就能加上，光靠它们就能挡住最常见的失败。越往下成本越高，所以按判定的分量决定走到哪一步就行。如果是拦住发布的关卡就要走到底，如果只是参考性的警报，前四条往往就够了。

未能确认的内容

把拿不出依据的项目集中放在一处。

  • 模型判定的可重现性数值。同一输入多次评分时判定会晃动多少，取决于任务、标准和模型。没有确认到可以一般化的数值
  • 哪个模型作为评分者更好的比较。没有依据去判断产品之间的优劣。本文的论点在于并排放两个性质不同的判定这一结构，而不在某个具体模型
  • 交叉验证能抓出的缺陷比例。前面引用的记录是二十九份里两份，但样本小且偏向正确答案，不能当作一般比例来读
  • 加上回归测试后的定量效果。要测漏报减少了多少，就得知道漏报的真值，而知道那个真值的方法本身就是问题的起点
  • 人工打标的合适样本量。要读多少份人才能让标准的错误暴露，取决于任务难度和失败类型的分布

结论：零违规不是结论，而是一个主张

检查器打印出来的零违规看着像事实陈述，实际上是一个主张：用这些规则看这个范围时没有命中任何东西。支撑它的依据压缩起来是三条。

第一，说清楚你看了什么。把检查过的对象数量打印出来的那一行，是最便宜的防御。安静的截断，光靠这一行基本就会暴露。

第二，证明你抓得到。有一套植入已知缺陷并确认检查器能抓到的回归测试，零违规才有依据说它不是什么都没看的结果。这套测试还会在每次动规则时，把检测力被削掉的那一刻推到屏幕上。

第三，和另一双眼睛对一下。并排放一个性质不同的第二判定，只让人翻开分歧的地方。把模型放到第二评分者的位置之所以在当下有价值，不是因为它的判定更准，而是因为做第二份实现的成本降下来了。

最后还有一点。就算这三个装置全都到位，仍然有挡不住的东西：评分标准本身就错的情况。那时基于规则的检查器和模型判定者会一起给出同样的错误答案，一致率反而更好看。标准的错误不靠工具，只有当人直接去读样本时才会暴露。自动化替不了的位置，恰恰就在那里。
