意思決定モデルの登場背景 — テキスト生成から構造化された確率判定へ

生成AIがエンタープライズの基幹システムへ組み込まれるにつれ、従来の自己回帰（autoregressive）型大規模言語モデル（LLM）が抱える構造的課題が、ミリ秒単位の応答が求められるホットパス（hot path）で顕在化してきた。問い合わせチケットの分類、エージェントのツール呼び出し（tool calling）、不正トラフィックの遮断といった処理では、長文のテキストは一切不要である。システムが必要としているのは、明確に型定義された「真/偽」「緊急度レベル」「担当チーム」といった少数の離散的な選択肢と、その確信度スコアである。

しかし汎用LLMは、単純な判定を出力するためであっても全文生成パイプラインを駆動させ、トークンごとに数十ミリ秒のデコード遅延を累積させる。またJSONスキーマで出力を縛ったとしても、構文エラーやハルシネーション（幻覚）のリスクを完全には排除できない。こうした背景から、文章生成を根本から排除し、入力状態と選択肢を受け取って確率分布を直接出力する「意思決定モデル（Decision Model）」と呼ばれる独立したモデル群が急速に注目を集めるようになった。

この分野の進化は、先行モデルを検証したJev実測評価と型安全分類の技術分析やマルチモーダルへの拡張を試みたJevスタイル視覚LLMラッパー実験、推論トークンを付加したPostHog Jeeves意思決定モデルの分析でも継続的に取り上げてきた。2026年10月1日、Cloudflareはこの領域に本格参入し、オープンウェイトの意思決定モデルClefおよびClef-flashを正式公開した。

  • ワークロードのミスマッチ解消: 文章生成向けLLMを高速な分類やルーティング処理に流用する際の遅延とコスト浪費を抑制。
  • 非自己回帰型アーキテクチャ: トークンごとの逐次デコードを撤廃し、すべての候補選択肢を単一フォワードパスで並列評価。
  • 確率スコアの直接出力: テキスト解析を介さず、実数型の確率値（0.0〜1.0）を取得して自動化の閾値判定に直結。
  • エージェント実行基盤との連携: Cloudflare cf CLIエージェント設計等と連動するエッジ実行パイプラインの確立。
  • オープンウェイト方針: ベンダーロックインを回避するため、Apache-2.0ライセンスによる重み公開とWorkers AI提供を両立。

ClefとClef-flashのモデル諸元と非自己回帰型並列評価の仕組み

Cloudflareが投入したClefシリーズは、処理要件に応じて2つのモデルで構成される。複雑な複数ラベル分類や高度なツール選択を担うフラッグシップのClefはQwen3.8-27Bをベースとし、超低遅延が要求されるエージェントループやリアルタイム処理向けのClef-flashはQwen3.5-9Bをベースとしている。いずれのモデルも大規模な事前学習バックボーンの重みは凍結し、専用のルーティングヘッドとLoRA（Low-Rank Adaptation）層を集中的に追加学習させている。

Clefの最大の特徴は、テキストを生成しない非自己回帰（non-autoregressive）の並列評価機構にある。入力を読み取る単一のプレフィル（prefill）処理の後、モデル内部の隠れ状態（hidden states）空間において、与えられた選択肢を2段階のアテンション層で処理する。第1段階で各選択肢が入力テキストの関連箇所を個別に参照し、第2段階で質問間の相関関係と入力全体を統合して最終的なスコアを計算する。

{
                      "messages": [
                        { "role": "user", "content": "Payment failed for all customers over the past hour. DB connection pool exhausted." }
                      ],
                      "questions": [
                        { "id": "urgency", "type": "choice", "options": ["low", "medium", "critical"] },
                        { "id": "assignee", "type": "choice", "options": ["billing_team", "infra_team", "support"] },
                        { "id": "customer_impact", "type": "boolean" }
                      ]
                    }

このリクエスト構造が示す通り、1つのコンテキストに対して複数の判定質問（選択式、真偽値、数値スコア）を単一のリクエストでまとめて渡すことができる。Clefは各項目についてトークンを順番に出力していくのではなく、すべての選択肢の条件付き確率を一括で算出する。これにより、出力トークン数が増えるにつれて応答時間が悪化する自己回帰モデル特有の遅延スパイクが発生しない。

  • Clef（27Bパラメータ）: Qwen3.8-27Bベース。複雑な業務ロジックの判定や高度な関数呼び出しの選定に最適化。
  • Clef-flash（9Bパラメータ）: Qwen3.5-9Bベース。エッジ環境での50ミリ秒未満の分岐判定やボット検出に最適化。
  • 2段階アテンションルーティング: 選択肢と文脈の照合、および複数質問間の相互依存性解決を分離して処理。
  • 凍結バックボーン構成: 基底モデルが持つ広範な世界知識を維持しつつ、判定ヘッドのみを高精度に調整。
  • 並列判定処理能力: 単一の文脈に対して多数の分類項目を同時に照会しても、推論時間が線形に増加しない設計。

Cloudflare自社測定ベンチマークと応答遅延の読み解き方

Cloudflareは自社のエッジGPUインフラ上で実施した各種ベンチマークの測定結果を公表した。ツール呼び出し精度を測るBFCL（Berkeley Function-Calling Leaderboard）において、Clefは98.47%、Clef-flashは98.76%の一致率を記録し、比較対象のJev（95.75%）を上回ったと報告されている。またAPI-BankベンチマークでもClef 91.93%、Clef-flash 93.11%となり、Jevの88.19%を上回る数値を発表した。

一方で、あらゆる評価でClefが一貫して優勢だったわけではない。ツールを「呼び出すべきでない状況」を正しく見極めるWhen2Callベンチマークでは、Jevが80.97%を記録したのに対し、Clefは72.37%、Clef-flashは65.58%にとどまった。Cloudflare自身も、When2CallやBRIGHT評価ではJevの方が優れた精度を示したことを公式発表で明記している。これは、ツールの積極的な選択能力と、呼び出しを差し控える抑制力との間に、モデル設計上のトレードオフが存在することを示している。

応答時間に関してCloudflareは、43のベンチマークを横断した統合遅延統計を示している。Clef-flashの中央値遅延は38.8msと報告され、比較対象のJev（524.1ms）に対して大幅に短い時間を達成したとしている。またテールレイテンシを示すp95においてもClef-flashは122.4msを記録し、比較対象の中で最も低い分散を示したとされる。ただしこれらの数値はCloudflareが管理する特定のエッジGPUインフラにおける自社測定であり、第三者機関による独立した検証データではない点に留意が必要である。

  • 自社測定値の帰属: すべてのベンチマーク精度および遅延数値は、Cloudflareが公式発表で自社測定として公表した結果。
  • Clef-flashの中央値38.8ms: 9B軽量モデルと非自己回帰アプローチにより実現されたエッジ実行性能。
  • タスクによる得手不得手: BFCL等のツール選定ではClef系が優勢、When2Call等の抑制判断ではJevが優位。
  • 実運用パイプラインの所要時間: ブラウザレンダリング（Browser Run）を伴うWeb分類実験全体では2.2秒を要したと報告。
  • Layaモデルとの比較: 発表では超小型モデルLayaの中央値5.8msに言及しつつ、p95の安定性ではClef-flashが勝ると説明。

マルチモーダル64KコンテキストとJev API互換性

Clefにおける顕著な技術的拡張点として、テキストにとどまらないマルチモーダル対応と、64Kトークンに達する広大なコンテキストウィンドウが挙げられる。先行するJevモデルはテキスト専用かつ32Kコンテキストの制約を持っていたが、Clefは高解像度画像と長大なテキスト状態を同時に処理できる。これにより、Webサイトのスクリーンショットに基づく安全分類、請求書画像のOCR分類、UI認識エージェントなど、視覚情報が絡む意思決定へ直接適用できる。

またCloudflareは既存エコシステムとの円滑な接続を狙い、Jev APIとの上位互換性を持たせている。既存のJevクライアントやSDKを利用している開発者は、データ構造を変更することなく、接続先エンドポイントをWorkers AIへ切り替えるだけで移行できる。返却されるレスポンスも、選択肢ごとの正規化スコアと確率値を含む標準的なJSON形式で統一されている。

{
                      "decisions": {
                        "urgency": {
                          "selected": "critical",
                          "probabilities": { "low": 0.012, "medium": 0.045, "critical": 0.943 }
                        },
                        "assignee": {
                          "selected": "infra_team",
                          "probabilities": { "billing_team": 0.021, "infra_team": 0.965, "support": 0.014 }
                        },
                        "customer_impact": {
                          "selected": true,
                          "probability": 0.988
                        }
                      }
                    }

この決定論的なJSON出力により、アプリケーション側での複雑な正規表現パースやJSONスキーマの修復処理が不要となる。エージェント開発者は、返された確率値（例えばcriticalの確率が0.90以上）に基づいて即座にアラートを発報し、閾値未満の場合は人間の確認キューに回すといった確実な安全マージン設計を実装できる。

  • 64Kコンテキスト対応: 巨大なAPI定義ドキュメントや過去の長い対話ログを一度に入力可能。
  • 画像入力のネイティブサポート: Webサイトのキャプチャ画像や図面を含む分類タスクへの直接対応。
  • Jev APIドロップイン互換: 既存のJev連携コードを最小限のエンドポイント変更のみでそのまま流用可能。
  • 決定論的JSONレスポンス: 出力形式の破綻や構文エラーを物理的に排除した安全な戻り値設計。
  • エンタープライズプライバシー規約: 微調整契約を結んだ場合を除き、入力および出力データを保持・学習に利用しないと明記。

RLCD確率補正と専任微調整サービスおよび基盤ロードマップ

実運用の意思決定システムにおいて、正解率と同等に重要なのが確率の統計的補正（キャリブレーション）である。モデルが「確率80%」と判定した事象は、実際に100回中80回正解でなければならない。一般的なLLMは過剰な自信（overconfident）を持ちがちで、誤った判断に対しても99%の確信度を提示することが頻発する。Cloudflareはこの問題を解決するため、補助的な学習目標としてRLCD（Reinforcement Learning for Calibrated Decisions）を導入した。

RLCDは、順序性のある選択肢（低・中・高など）において正解に近い選択肢にも部分的な報酬を与え、さらに1つのリクエストに含まれる複数の判定項目をすべて正しく揃えた場合にボーナス報酬を付与する。これにより、出力される確率スコアが実際の統計的正答率と正確に一致するよう誘導され、開発者が確率数値をそのまま自動化システムの信頼指標として扱えるようになる。

ビジネス展開の面では、Cloudflareは現在専任の現場エンジニアリング（FDE）チームを通じてエンタープライズ向け微調整を提供している。将来的には社内基盤を統合したセルフサービス型RLプラットフォームへと拡大する計画を公表した。この構想には、AI Gatewayによるデータ収集、Workers AIによる推論履歴生成、Containersによるエージェント評価サンドボックス、新設のTrainerによる自動再学習が含まれる。ただし発表では、セルフサービス基盤は現在開発中であり、現時点で利用できるのはモデル本体とFDE支援のみであることが明確に区別されている。

  • RLCDによる確率補正: 出力される確率値が現実の正答率と統計的に一致するよう誘導する強化学習手法。
  • 部分点と複合報酬の導入: 選択肢の順序誤差を考慮し、複数項目の同時正解に対して重み付け評価を実施。
  • モデル公開と基盤計画の切り分け: モデル重みは即座に利用可能だが、セルフサービス微調整基盤は現在開発中。
  • FDEによる個別微調整支援: 不正検知やカスタマーサポート分類に特化したモデル構築をパートナー向けに先行提供。
  • Cloudflareエッジ基盤の統合構想: AI Gateway、Containers、Workers AIを連携させた継続的学習ループの展望。

意思決定モデル系列の勢力図 — Jev、Luna、Jeevesとの共通点と差異

意思決定モデルの台頭は、AIアーキテクチャにおける明確な分業化の潮流を表している。この分野の草分けとなったのはTypeSafe社のJev System Oneであり、ポインターヘッドを用いた分類特化モデルが汎用LLMを圧倒する処理効率を持つことを実証した。詳細はJev実測評価の分析に詳しい。

その後、この系列は2つの方向へ分化していった。1つはOpenAI Luna Decision APIの分析で取り上げたような、プロプライエタリなクラウドAPIによる簡潔なルーティングの追求である。もう1つはオープンソース側のアプローチであり、PostHogが公開したJeeves意思決定モデルのように、判定直前に軽量な思考トークン（reasoning）を生成して難問の正解率を引き上げる試みである。

Cloudflare Clefの立ち位置は、これらの中にあって「エッジ分散インフラ」と「マルチモーダル64K」を両立させたオープンウェイトモデルとして位置づけられる。Jeevesが思考トークン生成のために数秒単位の遅延を受け入れるのに対し、Clefは非自己回帰を貫くことで数十ミリ秒の応答性を担保した。またJevの独自ホスティング環境に対し、Apache-2.0ライセンスによる自由なローカル実行と、Workers AIでの極めて安価な入力従量課金（Clef $0.24、Clef-flash $0.09）を武器に差別化を図っている。

  • Jevとの関係性: API互換性を保ちつつ、コンテキスト長を32Kから64Kへ拡大し、画像入力をネイティブサポート。
  • OpenAI Decision APIとの差異: 閉じたSaaS APIへの依存を避け、社内サーバーへ重みを配備できるオープン性。
  • PostHog Jeevesとの対比: Jeevesが思考過程による推論精度を重視する一方、Clefはミリ秒単位のホットパス速度に特化。
  • エッジ環境との親和性: Cloudflare Python Workers GAなど自社エッジ基盤上での低遅延呼び出し。
  • 適材適所の切り分け: 複雑な因果推論にはJeeves等の汎用LLMを、高速なトラフィック分岐にはClefを採用する構成。

閉域網環境でのデータ保護およびオンプレミスGPUでの自社運用 Clefオープン重み（Apache-2.0） Hugging Faceから重みを取得し社内クラスタへ外部送信なしで配備
既存のJev SDKで構築されたマイクロサービスのコスト削減 Workers AI Clefエンドポイント Jev API完全互換により、クライアントコードを変更せず移行可能

導入にあたっては、対象タスクが「文章作成を必要とするのか」それとも「選択肢の確率判定で済むのか」を明確に切り分ける必要がある。対話や要約は汎用LLMに任せ、内部的なルーティングや状態判定をClefに委譲するハイブリッド構成が最も費用対効果が高い。

  • タスク責務の明確な分離: 生成が必要な文章と離散的な判定を単一モデルで混用しない設計。
  • 確率閾値に基づく制御: RLCDで補正された確率値を活用し、確実性の高い自動分岐ルールを定義。
  • Workers AIでの事前検証: @cf/cloudflare/clefを用いて素早くプロトタイプを構築・検証。
  • 自社ホスティングの検討: レイテンシ要件が極めて厳しい環境では社内GPUでのローカル運用を評価。
  • プラットフォーム計画の現状認識: セルフサービス基盤は開発中であるため、初期は基本モデルの検証に注力。

  • Cloudflareが38.8ms（Clef-flash）および524.1ms（Jev）を記録したベンチマーク環境の具体的なGPU型番（A100、H100、L40S等）やネットワーク構成。公式ブログには記載されていない。

  • 64Kコンテキスト上限付近まで高解像度画像と長文テキストを詰め込んだ際の、推論遅延の具体的な悪化率。
  • 計画中のセルフサービス型RL微調整プラットフォームの正式公開時期および一般開発者向け料金体系。
  • 公開されたApache-2.0重みをvLLMやTensorRT-LLM等の主要サービング基盤で直ちに動かすための公式コンフィグの提供状況。
