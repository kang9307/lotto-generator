zip の中のファイル名が壊れる地点 - 誰がどの符号化で書いたのか

ファイル名はバイト列である。それをどう読むかはフラグ 1 ビットと道具の推測に委ねられている

2026-07-30 開発/インフラ

序論: 受け取った書庫を展開したら名前が全部壊れていた

取引先から届いた zip を落として展開した。ファイルは全部出てきたのに、名前が ║╕░φ╝¡.txt や 1║╨▒Γ ╕┼├Γ.xlsx のようなものに変わっている。相手に尋ねると 「こちらでは正常に見える」 と言う。逆の状況もよくある。自分が圧縮して送ったファイルを相手が展開したら名前が壊れていたと連絡が来る。自分の機械では何の問題もない。

この会話が果てしなく繰り返される理由は、双方とも間違ったことをしていないからである。ここでよく出る助言は 「UTF-8 で圧縮してください」 だが、これは半分しか当たっていない。zip 書庫の中でファイル名はただのバイト列として保存される。そのバイトをどの符号化で読むべきかを伝える手段はフラグ 1 ビットだけで、そのビットが落ちているとき何で読むべきかは仕様が定めていない。

だからこの記事は設定を変える話ではない。書庫をバイトに分解し、ファイル名欄とフラグを直接読む話である。その二つの値を見れば壊れた理由は即座に確定し、戻せるかどうかもその場で分かれる。以下の出力はすべて実際に走らせて得たものだ。

実行環境。 書庫は struct でバイトを直接組み立てて作り、読むときも標準ライブラリに任せずセントラルディレクトリを手で解析した。スクリプトはすべてファイルに保存してから実行した。非 ASCII 文字と逆スラッシュが混じったコードをシェル引数として渡すと静かに変形するからである。作業パスは \work\demo のような仮の表記に置き換えた。

この記事が扱わないもの。 ファイル内容の符号化誤変換とその診断法は cp949 と UTF-8、二種類の符号化エラー で扱った。Unicode 正規化の原理は NFC と NFD にある。ここでは zip 書庫の中のファイル名欄という一点だけを見る。

1. 仕様が定めなかったもの

zip 形式の規格は PKWARE の APPNOTE 文書である。ファイル名の符号化に関する記述は驚くほど短い。汎用目的ビットフラグのビット 11 についての一文が事実上すべてだ。

Bit 11: Language encoding flag (EFS). If this bit is set, the filename and comment fields for this file MUST be encoded using UTF-8.

この一文はビットが立っているときだけを語る。落ちているときはどうなのか。付録 D の記述が答えだ。zip 形式は歴史的に元の IBM PC 文字符号化集合のみを支援してきたというのである。ビット 11 がなかった時代の既定値は DOS 時代のコードページであり、それ以外の符号化を使っていると宣言する方法がない。

  • ファイル名欄は長さとバイト列しか持たない。符号化の名前が入る場所がない
  • ビット 11 は立っているときだけ意味がある。落ちているのは 「UTF-8 ではない」 ではなく 「宣言していない」 である
  • だから宣言なし UTF-8 の書庫が存在しうる。仕様違反でもない。立てろと強制されていないからだ
  • 同じ文書の 4.4.17 はパス区切りについて必ず順方向スラッシュを使えと記す。こちらは強制である。後でこの規則を破る道具に出会う
  • 結論。ファイル名が壊れるのは誰の落ち度でもなく仕様の空白である。その空白を道具たちがそれぞれの推測で埋めている

この構造が分かると次の問いが変わる。「符号化は何か」 ではなく 「ビット 11 が立っているか、そしてそのバイトは何か」 になる。どちらも書庫を開けば即座に答えが出る。

2. ファイル名欄をバイトに分解する

まず材料を作った。同じ名前を二つの符号化で書くとバイトはこれだけ違う。

--- 2-1. one name, two encodings ---
name : 보고서.txt
  utf-8 bytes : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74   (13 B)
  cp949 bytes : BA B8 B0 ED BC AD 2E 74 78 74            (10 B)

name : 1분기 매출.xlsx
  utf-8 bytes : 31 EB B6 84 EA B8 B0 20 EB A7 A4 EC B6 9C 2E 78 6C 73 78   (19 B)
  cp949 bytes : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78               (15 B)

韓国語の 1 文字が UTF-8 では 3 バイト、cp949 では 2 バイトになる。だから同じ名前が 13 バイトのものと 10 バイトのものの二種類存在する。この二つのバイト列をそれぞれ書庫に入れ、セントラルディレクトリを手で解析した。まずは古い道具が作る形である。

=== A_legacy_cp949.zip  (258 B) ===
EOCD  entries=2  cd_offset=119  cd_size=117
--- entry 1 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 10 bytes
  name field hex   : BA B8 B0 ED BC AD 2E 74 78 74
  as utf-8         : <UnicodeDecodeError>
  as cp949         : [보고서.txt]
  as cp437         : [║╕░φ╝¡.txt]
  extra len        : 0 bytes  (no extra field)
--- entry 2 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 15 bytes
  name field hex   : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78
  as utf-8         : <UnicodeDecodeError>
  as cp949         : [1분기 매출.xlsx]
  as cp437         : [1║╨▒Γ ╕┼├Γ.xlsx]
  extra len        : 0 bytes  (no extra field)

この出力が診断のすべてである。三行だけ見ればよい。

  • フラグが 0x0000 である。ビット 11 が落ちているのでこの書庫は符号化を宣言していない
  • 名前のバイトが BA B8 B0 ED BC AD である。UTF-8 で復号すると例外が出て cp949 では綺麗に読める。バイトが符号化を語っている
  • 拡張フィールドがない。名前をもう一度載せておく場所もない
  • 判定は確定的だ。宣言なし cp949 の書庫である。韓国語 Windows では正常に見え、それ以外では壊れる

ここで注目すべきは as cp437 の行だ。ファイル名のバイトを DOS 時代の既定コードページで読むと ║╕░φ╝¡.txt になる。序論で見たあの文字列である。つまりこの記事の最初の症状は 「宣言なし cp949 の書庫を仕様の既定値どおりに読んだ結果」 だった。

3. ビット 11 という唯一の宣言

同じ名前を UTF-8 のバイトで入れ、ビット 11 を立てた書庫を作って対照した。

=== B_utf8_flagged.zip  (272 B) ===
EOCD  entries=2  cd_offset=126  cd_size=124
--- entry 1 ---
  gp flag raw      : 0x0800   bin 0000100000000000
  bit 11 (UTF-8)   : SET
  name field len   : 13 bytes
  name field hex   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  as utf-8         : [보고서.txt]
  as cp949         : <UnicodeDecodeError>
  as cp437         : [δ│┤Ω│á∞ä£.txt]
  extra len        : 0 bytes  (no extra field)
--- entry 2 ---
  gp flag raw      : 0x0800   bin 0000100000000000
  bit 11 (UTF-8)   : SET
  name field len   : 19 bytes
  name field hex   : 31 EB B6 84 EA B8 B0 20 EB A7 A4 EC B6 9C 2E 78 6C 73 78
  as utf-8         : [1분기 매출.xlsx]
  as cp949         : [1遺꾧린 留ㅼ텧.xlsx]
  as cp437         : [1δ╢äΩ╕░ δºñ∞╢£.xlsx]

フラグが 0x0800 である。二進数で書くと 0000100000000000 で、右から 12 番目の桁が一つ立っただけがすべてだ。この 1 ビットが 「この名前は UTF-8 である」 という宣言であり、zip 形式で符号化を伝えられる唯一の手段である。

3.1 宣言しなかった UTF-8 という罠

三番目の場合がある。バイトは UTF-8 なのにビット 11 を立てなかった書庫だ。これも仕様違反ではない。

=== C_utf8_noflag.zip  (141 B) ===
EOCD  entries=1  cd_offset=60  cd_size=59
--- entry 1 ---
  gp flag raw      : 0x0000   bin 0000000000000000
  bit 11 (UTF-8)   : not set
  name field len   : 13 bytes
  name field hex   : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  as utf-8         : [보고서.txt]
  as cp949         : <UnicodeDecodeError>
  as cp437         : [δ│┤Ω│á∞ä£.txt]
  extra len        : 0 bytes  (no extra field)
  • A と C はフラグの値が同じである。どちらも 0x0000 だ
  • ところが名前のバイトが違う。A は cp949 でのみ読め、C は UTF-8 でのみ読める
  • つまりフラグだけでは足りない。フラグが落ちているときはバイトの妥当性も併せて見ることで初めてどちらかが分かれる
  • C はむしろ韓国語 Windows で壊れる。システムのコードページが 949 なので UTF-8 のバイトを 949 として読んでしまう
  • A と C が互いに逆方向の事故を起こすのがこの問題の厄介なところだ。一方を直す措置がもう一方を作る

  • ������ のように置換文字が連続すれば cp949 のバイトを UTF-8 で読んだということだ。cp949 の組み合わせはほとんど UTF-8 の規則に合わない

  • 壊れた標本にギリシャ文字やアラビア文字が混じって現れるのは正常である。元とは何の関係もなく、誤って適用されたコードページのその位置にその文字があっただけだ

4.1 拡張子が消える理由

上の標本のうち 蹂닿퀬�꽌.txt は点が生きている。ところが実際に書庫を展開してディスクに残った名前は 蹂닿퀬__txt だった。拡張子が消えている。なぜかバイトを二つずつ束ねて見た。

--- 4-3. why the extension disappears ---
utf-8 bytes of the name : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74  (13 B)
cp949 reads two at a time:
  EB B3 -> [蹂] U+8E42
  B4 EA -> [닿] U+B2FF
  B3 A0 -> [퀬] U+D02C
  EC 84 -> <UnicodeDecodeError>
  9C 2E -> <UnicodeDecodeError>
  74 -> [t] single byte
  78 -> [x] single byte
  74 -> [t] single byte

the pair that eats the dot:
  9C 2E   the byte 2E is the '.' of .txt
          a cp949 lead byte 9C swallowed it

what the platform decoder returned for the same bytes:
  [蹂닿퀬??txt]
  U+8E42 U+B2FF U+D02C U+003F U+003F U+0074 U+0078 U+0074   (8 chars)
  chars illegal in a Windows file name : U+003F U+003F
  the extractor replaced them with underscores -> [蹂닿퀬__txt]

連鎖はまさにこうだ。UTF-8 の名前を 2 バイト単位で読んだために先頭バイト 9C が点を相方として引き込んだ。その対は有効な文字ではないので疑問符になり、疑問符は Windows のファイル名に使えないので展開する道具が下線に置き換えた。結果として拡張子が消える。

  • 「名前だけ壊れた」 のではない。拡張子がなくなって関連付けが消え、二回叩いても開かない
  • 点が食われる条件は名前の最後の非 ASCII 文字の三番目のバイトが cp949 の先頭バイト区間に入るときである。名前によってなったりならなかったりする
  • だから 「あるファイルは拡張子が残り、あるファイルは消える」 という現象が同じ書庫の中で同時に現れる
  • 拡張子の有無で壊れを判断するスクリプトはここで静かに誤判定する

5. 戻せるか - バイトが残ったかがすべて

壊れた名前を見ると復旧したくなる。できる場合とできない場合を実行で分けた。まずできる側だ。

--- 5-1. bytes preserved in the archive -> reversible ---
  as reported by reader : [║╕░φ╝¡.txt]
  codepoints            : U+2551 U+2555 U+2591 U+03C6 U+255D U+00A1 U+002E U+0074 U+0078 U+0074
  re-encode cp437       : BA B8 B0 ED BC AD 2E 74 78 74
  decode cp949          : [보고서.txt]
  round trip ok         : True

  as reported by reader : [1║╨▒Γ ╕┼├Γ.xlsx]
  codepoints            : U+0031 U+2551 U+2568 U+2592 U+0393 U+0020 U+2555 U+253C U+251C U+0393 U+002E U+0078 U+006C U+0073 U+0078
  re-encode cp437       : 31 BA D0 B1 E2 20 B8 C5 C3 E2 2E 78 6C 73 78
  decode cp949          : [1분기 매출.xlsx]
  round trip ok         : True

手順は二段階だ。読む道具が適用した符号化で再び符号化して元のバイトを取り戻し、そのバイトを正しい符号化で復号する。ここでは道具が cp437 を適用したので cp437 で戻し cp949 で読んだ。バイトが元と完全に一致したことが成功の証拠である。

二つの失敗は性格が違う。

  • 5-2 は道具がバイトを挽いてしまった場合だ。ある展開道具は名前を自分なりの文字集合に書き写してディスクに書く。BA B8 が A6 A9 になってしまった。元のバイトを取り戻す符号化が存在しない
  • 5-3 は置換文字が食った場合である。置換文字はどのバイトの代わりだったかの情報を一つも持たない。10 バイトが 22 バイトに増えたのは情報が増えたのではなく同じ値が六回繰り返されただけだ
  • だから判断の順序が重要である。ディスクに展開された名前で判断せず、書庫の中のバイトをまず見よ。書庫が無事なら別の道具で展開し直せばよく、すでに変な名前で展開してしまったファイル群は消してやり直すのが速い
  • 元の書庫ファイルを消さずに保管するのが第一の防御だ。書庫があればいつでも戻せる

三行目がこの記事で最も実用的な発見である。今日の Windows 10 に標準で付属する tar コマンドがファイル名を cp949 のバイトで書き、ビット 11 を立てない。古い道具をわざわざ探して使ったのではなく、OS に付いてきた標準の道具がそう動く。zip コマンドがない環境で tar -a -c -f out.zip は自然な選択であり、そうして作った書庫は同じコードページ環境の外では必ず壊れる。

一行目にも罠が一つ隠れている。Python の zipfile は名前に非 ASCII 文字があるときだけビット 11 を立てる。readme.txt のフラグは 0x0000 だった。同じ書庫の中で項目ごとにフラグが違うということであり、最初の項目だけを検査する判別スクリプトはここで間違う。

7. 読む側 - 同じ書庫を四つの道具で

今度は方向を逆にする。先に作った A (cp949、ビットなし)、B (UTF-8、ビット立て)、C (宣言なし UTF-8) をそれぞれ四つの道具で展開し、ディスクに残った名前のバイトを読んだ。

  • 対応は比較する前に両側を同じ形式に正規化することである。最後の行で正規化後には一致した

10. Unicode パス拡張フィールド 0x7075

仕様には迂回路がもう一つある。ビット 11 を立てずに名前を UTF-8 でもう一度載せておく拡張フィールドだ。APPNOTE 4.6.9 が定義する Unicode パス拡張フィールドであり、ヘッダ識別子は 0x7075 である。このフィールドを含む書庫を作って読んでみた。

  • フィールドの構造は版 1 バイト + ヘッダ名の CRC 4 バイト + UTF-8 の名前である。CRC があるので、別の道具がヘッダの名前を書き換えた場合にこのフィールドが古いことを検知できる
  • Python の zipfile はこのフィールドを読むとヘッダの名前を上書きする。だから 5 節の cp437 復旧手順が不要になる
  • ただし確認した三つの道具のうちこのフィールドを書く道具は一つもなかった。読みは広く支援されているのに書きは稀である
  • APPNOTE 自身もビット 11 を使えばこの拡張フィールドは不要だと記す。新しく作る書庫はビット 11 で行くのが正しい
  • このフィールドの実用的な意味は診断にある。受け取った書庫にこれがあれば元の名前を推測なしに知ることができる

12. 名前と内容は別物である

一つの書庫の中で名前は UTF-8、内容は cp949 という項目をわざと作った。この組み合わせが規格上まったく問題ないことを確認する節である。内容の符号化の診断法は cp949 と UTF-8、二種類の符号化エラー で扱ったので、ここでは二つの層が互いに無関係であるという事実だけを押さえる。

--- 12-1. name layer and content layer disagree, on purpose ---
  entry name         : [보고서.txt]  bit11=SET
  name bytes (utf-8) : EB B3 B4 EA B3 A0 EC 84 9C 2E 74 78 74
  content bytes      : C7 D1 B1 DB 20 B5 A5 C0 CC C5 CD 0A
  content as utf-8   : '�ѱ� ������\n'

  internal_attr = 0x0000     (bit 0 is a text/binary hint only)

  • ビット 11 はファイル名と注釈にのみ適用される。仕様がそう明記している。ファイルの内容は対象外だ
  • 項目が持つフィールドを全部並べても内容の符号化を書く場所がない。テキストかバイナリかを示唆するビット一つがすべてである
  • だから 「名前がよく見えるから内容も大丈夫だろう」 には根拠がない。二つの層は何の情報も共有していない
  • 逆も成り立つ。名前が壊れた書庫の内容は無事でありうる。展開は名前と無関係にバイトをそのまま復元する
  • 実務では二つの層を別々に確認しなければならない。名前はセントラルディレクトリで、内容は展開したバイトで

13. 診断手順 - 受け取った書庫はどの場合か

これまでの判別を一度に走らせる検査器を書いた。セントラルディレクトリのフラグ、名前バイトの妥当性、拡張フィールドの有無という三つだけで分類が終わる。

archive                    bit11    ascii  utf8ok 949ok  0x7075 verdict
--------------------------------------------------------------------------------------

順序を整理するとこうなる。

  1. 展開せずに一覧だけ見る。誤った名前でディスクに書いてしまうと 5 節の復旧不可事例に移りうる
  2. セントラルディレクトリからビット 11 を読む。立っていれば名前は UTF-8 であり、それでも壊れて見えるなら原因は書庫ではなく読む道具だ
  3. 落ちていれば名前バイトの妥当性を見る。UTF-8 でのみ有効か、cp949 でのみ有効か、両方か
  4. 拡張フィールド 0x7075 を探す。あれば推測の必要がない。その中に UTF-8 の名前が入っている
  5. 項目を一つだけ見ない。ASCII の名前はフラグが落ちており、一つの書庫に二つの符号化が混ざりうる
  6. 判定が済んでから展開し、元の書庫は消さない。書庫があればやり直せる

両方で有効な場合が実際にある。あるバイト列は UTF-8 でも cp949 でも例外なく読める。ASCII だけの名前が最もよくある例で、それ以外にも重なる区間が存在する。このときはバイトだけでは確定できない。妥当性検査は候補を減らす道具であって結論を出してくれない。だから最後の判断は人が名前を読んで意味が通るかを見ることになる。

表を使うときの注意がある。ディスクに展開された名前に表を当てはめると遅い。表の 「復旧」 欄はほとんどが元の書庫が残っている前提で成り立つ。だから順序は常に書庫が先、ディスクが後である。

15. 配布するときに決めること

今度は逆の立場だ。自分が書庫を作って配布するなら何を決めておくべきか。上の実測を根拠に四項目が出る。

決定項目選択肢確認された根拠推奨
作る道具ビット 11 を立てる / 立てないPython の zipfile と Compress-Archive は立て、Windows の tar.exe は立てなかったビット 11 を立てる道具に固定し文書に記す
名前の文字範囲ASCII のみ / 非 ASCII 許可ASCII の名前はフラグと無関係にどこでも同じに読めた対外配布は ASCII 推奨、社内は規則を明示
正規化形式合成形 / 分解形同じ名前が 13 バイトと 22 バイトに分かれ文字列比較が失敗した合成形に統一し作る時点で正規化する
パス区切り2F / 5CAPPNOTE 4.4.17 は順方向スラッシュを要求するのに一つの道具が 5C を書いた作った書庫の区切りバイトを検査に入れる
受け渡し方法名前に意味 / マニフェスト分離名前が壊れるとどのファイルが何なのか分からなくなる一覧ファイルを同梱し名前依存を減らす
検証目視 / 自動検査最初の項目だけ見るとフラグ混在を見逃す配布前にすべての項目のフラグを機械で確認
  • 最も安い措置は作るコマンドを一つに固定することだ。書庫を作るスクリプトを一つ置き、人が道具を選ばないようにする
  • 二つ目は配布前の検査である。13 節の三つの値を読み 「ビット 11 が落ちた項目が一つでもあれば失敗」 として扱えば事故が原理的に止まる
  • 受け取る側が古い道具を使うと確実なら名前を ASCII に変えてマニフェストに元の名前を記す方がよい。拡張フィールドに頼るより確実である
  • すでに配布した書庫を直せるなら作り直すのが正解だ。名前欄だけ手直しする編集はローカルヘッダとセントラルディレクトリの両方を合わせる必要があり、オフセットがずれやすい
  • 社内規格文書に記す文は短い。「書庫のファイル名は UTF-8 とし汎用フラグのビット 11 を設定する。パス区切りは順方向スラッシュを使う。名前は合成形に正規化する。」 三文でこの記事のすべての事故が止まる

結び: 仕様の空白を規則で覆う

「UTF-8 で圧縮してください」 は助言として半分しか当たっていない。半分当たっている理由はビット 11 を立てる道具を使えば大半が解決するからで、半分外れている理由は zip がファイル名の符号化を強制しないという事実を隠すからである。隠せば次の事故を診断できない。

実行して確認したことを改めて整理するとこうだ。書庫の中のファイル名は長さとバイト列だけである。符号化を伝える手段はビット一つであり、そのビットが落ちているとき何で読むべきかは仕様が定めていない。だから道具たちがそれぞれ推測するのだが、Windows の道具はシステムのコードページを適用し Python は DOS の既定値を適用し古い unzip は独自の変換表を適用する。三つの推測がすべて仕様に反していない。

そしてこれが韓国で特に頻発する理由もここにある。cp949 時代のファイルと慣行がまだ流通し、システムのコードページが 949 の環境同士でやり取りしている間は何も表面化しない。問題は受け取る側が別の環境であるときにだけ現れるので、作った側は自分の書庫が壊れるという事実を知る術がない。今日の Windows に標準で付属する tar がそういう書庫を作ると確認できたことが、この記事の最も実用的な結論である。

今すぐできることが一つある。最近対外に送った書庫を一つ開いてビット 11 を読んでみよ。立っていれば安心してよい。落ちていて名前に非 ASCII 文字があるなら、それを受け取った人は今まさに壊れた名前を見ている可能性が高く、あなたに言っていないだけである。

# zip ファイル名符号化 判別シート

## 0. 一行で

zip はファイル名の符号化を仕様で強制しない。名前はバイト列であり、宣言手段は汎用目的フラグの **ビット 11** だけである。ビットが落ちているとき何で読むかは道具ごとに違う。

## 1. まず見る三つ (展開する前に)

| 見るもの | 位置 | 意味 |
|---|---|---|
| 汎用目的ビットフラグ ビット 11 | セントラルディレクトリヘッダ +8、2 バイトリトルエンディアン | `0x0800` なら UTF-8 宣言 |
| ファイル名欄の生バイト | ヘッダ +46 から名前の長さ分 | UTF-8 / cp949 妥当性の判定 |
| 拡張フィールド `0x7075` | 名前欄の後ろ | あれば UTF-8 の名前がもう一度入っている |

## 2. 壊れた見た目の判別表

| 見える名前 | 標本 | 原因 | 復旧 |
|---|---|---|---|
| 罫線・ギリシャ文字 | `║╕░φ╝¡.txt` | cp949 の名前を cp437 で読んだ | 可能 (cp437 再符号化後 cp949) |
| 小文字ギリシャ・記号 | `δ│┤Ω│á∞ä£.txt` | UTF-8 の名前を cp437 で読んだ | 可能 (cp437 再符号化後 UTF-8) |
| 漢字とハングルの混在 | `1遺꾧린 留ㅼ텧.xlsx` | UTF-8 の名前を cp949 で読んだ | 可能 (cp949 再符号化後 UTF-8) |
| 漢字混在 + 拡張子消失 | `蹂닿퀬__txt` | 同じ。点が先頭バイトに食われた | 書庫から展開し直す |
| 置換文字の連続 | `������.txt` | cp949 の名前を UTF-8 で読んだ | 保存前なら可能 |
| ラテン + アラビア文字 | `٦¦ۦáýä£.txt` | 古い道具が独自の変換表を適用 | 不可。別の道具で展開 |
| 文字数が増える | `º¸°í¼­.txt` | 単一バイトコードページ。不可視文字を含む | 可能 (latin-1 再符号化後 cp949) |
| 正常なのに探すとない | `보고서.txt` | 字母分解の状態で保存された名前 | 可能。比較前に正規化 |
| 展開が例外で中断 | (ファイルなし) | 宣言なし UTF-8 + コードページ解釈 | 別の道具で展開 |

## 3. バイト確認コマンド

```
# 一覧だけ (展開しない)
```

## 4. 道具別の動作対照 (Windows 10 / ANSI 949 で実測)

### 作る側

| 道具 | 名前のバイト | ビット 11 | 区切り | 判定 |
|---|---|---|---|---|
| Python 3.13.3 `zipfile` | UTF-8 | 立てる (ASCII は立てない) | `2F` | 安全 |
| PowerShell 5.1 `Compress-Archive` | UTF-8 | 立てる | `5C` 規格違反 | 名前は安全 |
| Windows `tar.exe` (bsdtar 3.5.2) | cp949 | **立てない** | `2F` | 外で壊れる |
| Node.js v22 | コアに zip 書庫 API なし | 該当なし | 該当なし | 該当なし |
| Info-ZIP `zip` / 7-Zip | この環境になく未確認 | 未確認 | 未確認 | 未確認 |

### 読む側

| 道具 | cp949 + ビットなし | UTF-8 + ビット立て | UTF-8 + ビットなし | `0x7075` |
|---|---|---|---|---|
| Python `zipfile` | cp437 適用 → 壊れる | 正常 | 壊れる | 尊重 |
| Windows `tar.exe` | 正常 | 正常 | 拡張子消失 | 尊重 |
| `Expand-Archive` | 正常 | 正常 | 例外、未展開 | 尊重 |
| UnZip 6.00 | 壊れる | **壊れる (ビット無視)** | 壊れる | 尊重 |

## 5. 配布時の決定項目

- [ ] 作る道具を **ビット 11 を立てるものに固定**した
- [ ] 書庫の生成をスクリプト一つにまとめ人が道具を選ばないようにした
- [ ] 対外配布用の名前を **ASCII に制限**したか、非 ASCII 許可なら規則を文書に記した
- [ ] 名前を **合成形に正規化**して入れた
- [ ] パス区切りが `2F` であることを確認した
- [ ] **すべての項目**のフラグを検査した (最初の項目だけを見ない)
- [ ] 一覧ファイルやマニフェストを同梱し名前依存を減らした
- [ ] 元の書庫を保管する (やり直せる唯一の経路)

## 6. してはいけないこと

- 判定前に **展開すること** — 誤った名前でディスクに書くと復旧経路が狭まる
- **最初の項目だけを検査**すること — ASCII 名はフラグが落ちており項目ごとの混在が可能
- **拡張子の有無で壊れを判定**すること — 点が先頭バイトに食われて消えうる
- 名前欄だけを **バイト編集**で直すこと — ローカルヘッダとセントラルディレクトリ、オフセットがずれる
- 「例外が出なかったからこの符号化だ」 — 両方の符号化で有効なバイト列が存在する
- 古い道具を使う相手に **拡張フィールドを頼ること** — 選択肢一つで無視される
- 名前がよく見えることを根拠に **内容も大丈夫と推定**すること — 二つの層は無関係
