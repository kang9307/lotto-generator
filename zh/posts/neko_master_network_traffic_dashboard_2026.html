neko-master 流量可视化面板 - 与 ntopng 有何不同

不是又一块面板，而是先想清楚这类工具在什么时候才真正需要

2026年7月27日 开发/基础设施

引言：找出占用带宽的元凶，这个老问题

家庭或小型办公网络变慢时，处理者遇到的困境总是一样的：知道它慢了，却不知道是谁、为什么在占用。打开路由器管理页面，大多只能看到收发总量，至于哪台设备正往哪个目标发送多少，并没有答案。凌晨上行突然飙升时，无从判断那是备份软件、云同步、自动更新，还是一台被入侵的智能设备。

试图填补这块空白的工具已经出现过好几代。新面板仍然不断涌现并引发讨论，原因在于这个问题没有唯一正解。从哪里取数，直接决定了什么看得见、什么看不见，以及要付出什么代价。2026 年 7 月在 GeekNews 当日登顶的 neko-master 也属于这一脉络，但它的采集位置本身就与人们通常想象的流量监控工具不同。而这一点几乎决定了它的全部价值与全部局限。

本文只把仓库中能实际确认的内容当作事实，再在其上叠加家庭实验室与小型网络监控的通行经验，来判断这类工具何时确有必要、何时属于过度配置。目标不是功能罗列，而是建立判断标准。文中同时会衡量记录流量这一行为本身所承载的隐私分量，以及在住宅环境中最容易绊住人的那些条件。

1. neko-master 实际做了什么 - 可确认的部分

先从能够确认的事实说起。以下内容出自公开仓库的说明文档，文档中没有的项目随后会单独标出。

1.1 数据从哪里来

这是最关键的一点。neko-master 不直接抓包，也不接收流导出，而是连接网关的控制接口取数。按文档所述，Clash、Mihomo 一类网关走 WebSocket 实时采集，Surge v5 及以上走 HTTP 轮询，在 WebSocket 不可用时回退到轮询。这一类网关为了管理基于规则的路由，本就通过外部控制接口暴露连接列表与流量统计，而 neko-master 处在消费这些输出的一侧。

这一句话决定了其余全部特性。采集负担轻、部署简单是因为它，后文将要谈到的那些致命盲区同样源于它。

1.2 文档中明示的功能

  • 实时监控 —— 基于 WebSocket 的采集，宣称毫秒级延迟
  • 趋势分析 —— 30 分钟 / 1 小时 / 24 小时区间的流量走势
  • 域名分析 —— 按域名的流量、关联 IP、连接数
  • IP 分析 —— 自治系统号、地理位置、关联域名
  • 代理节点统计 —— 按节点的流量分布
  • 多后端 —— 在一块屏幕上观察多个网关实例
  • Agent 模式 —— 由 agent 在网关附近取数并上报面板，面板不直接连接网关
  • 其他 —— PWA 安装、暗色模式、多语言（英文与中文）

值得留意的是 Agent 模式。面板不直连网关、由 agent 中转的设计，读起来像是既要在一块屏幕上看多个站点，又不愿把网关控制接口直接暴露出去。控制接口往往不只支持查询，还能改配置，把它原样开放到外网是危险的。加一层中转是合理的取舍。

文档中没有写明的项目同样需要讲清楚。最低内存与 CPU 要求、默认数据保留期、每秒可处理的连接数，这些数值在文档里查不到。因此下文谈负载与容量时，依据的不是这个项目的实测值，而是同类结构工具的通行表现。

还有一点。仓库明确表示本项目不提供任何网络接入服务、订阅或跨网连通能力，数据仅采自用户自己的网络环境。这条边界恰好与后文的隐私讨论对上。

2. 最大的误解 - 它不是 ntopng 的替代品

2.1 看不见的部分

读取网关控制接口，意味着只有经过该网关的连接才可见。在家庭网络里，这个差别绝不细微。以下流量在这种结构下原理上就抓不到。

  • 绕过网关的直连流量 —— 被规则送进旁路的连接不会进入统计
  • 局域网内部结束的通信 —— 访问 NAS、本地影音播放、打印机、备份等不出门的流量
  • 被配置为不走网关的设备 —— 游戏主机、智能电视以及相当一部分智能家居设备都落在这里
  • 走独立路径的广播与影音流量 —— 机顶盒一类往往走另一条通路
  • 设备自身的资源状态 —— 系统负载、磁盘、温度这类主机指标本就不在范围内

所以家里网络为什么慢这个问题，单靠这个工具很难回答。它能回答的是经过我这台网关的流量流向哪里、量有多大这个更窄也更具体的问题。若模糊了这层区分就上手，就会反复陷入盯着数据也找不到原因的处境。

2.2 换来的东西 - 域名归属的准确度

不过这种结构有一项基于抓包的工具难以企及的优势，而这大概就是它存在的理由：它准确知道目标域名。

如今的流量绝大多数已加密，翻看数据包也很难稳定判定目标主机。早期还能读取握手初期暴露的服务器名称信息，但标准一直在朝着把这一段也加密的方向演进。于是抓包类工具不断向 IP 与端口层面退守，一旦只剩 IP，大型内容分发网络背后叠着数百个服务，实质上已无法做出有意义的归属判断。

反过来看，基于规则的网关为了判断某个目标该走哪条路，必须事先知道域名。也就是说域名信息不是副产品，而是该系统的必需输入。neko-master 取用的正是这份已经确立的事实，因此它呈现的不是推断，而是网关判定结果本身。按域名的流量、关联 IP、连接数这组功能之所以能够成立，根据就在这里。

概括来说，这个工具把窄区间看得很准。它与那些把宽区间看得模糊的工具并非竞争关系，而更接近互补关系。

3. 采集流量的四种方式与各自的代价

要做像样的比较，得先立起采集方式这条轴。在罗列工具名称之前，先区分数据从何而来，要有用得多。以下属于通行认识。

采集方式能获得的信息负载隐私暴露典型代表
接口计数器仅收发总字节与包数几乎为零非常低（无内容、无目标）vnStat、SNMP 轮询
流导出（NetFlow、sFlow、IPFIX）源与目标的 IP 和端口、协议、字节与包数、时间低到中（sFlow 采样，低且可预测）中（留下谁与谁通信，无内容）路由器导出加采集器
抓包与深度分析完整报文头，必要时含载荷高（随线速陡增）高（保存原始数据时最敏感）ntopng 一类的深度模式
消费控制面接口网关已掌握的连接、域名与路径信息低（只接收汇总结果）中到高（留下域名历史）neko-master、DNS 层工具

这张表要读出三点。

  • 信息量与负载大体成正比。 想看得更细就要处理得更多，而且线路越快，这份成本上升得越陡。
  • 信息量与隐私风险同步上升。 只看计数器几乎不含个人信息，而域名历史本身就是敏感信息。
  • 采样并不免费。 采样方式负载低且可预测，代价是更容易漏掉偶发的异常流量。用来看带宽排名足够，用来抓间歇性征兆则偏弱。

再补一点：消费控制面这种方式的特殊之处，在于它是负载低而隐私暴露高的组合。廉价获得的信息就必定不敏感，这种直觉在这里失效。做落地判断时，这两条轴必须分开看。

4. 与既有方案的对比

把处理同一问题的工具放到上述轴线上，性格差异就清楚了。以下评价是各项目通行特征的归纳，具体数值会随配置与线速大幅变化。

工具采集方式资源占用上手难度可视化程度长处
vnStat接口计数器非常轻非常容易基础（总量走势）数月长期总量追踪，几乎无负担
Netdata以主机指标为主，兼有网络指标轻到中容易高（实时下钻）服务器状态与网络同屏定位原因
Grafana + Prometheus取决于采集器的搭配中（随配置增长）较难非常高（完全自由）长期留存、告警与多源汇聚
ntopng抓包观察加流接收中到高中高（深度分析）观察经过某段链路的全部流量
Pi-holeDNS 查询（控制面）轻容易中（查询日志与拦截统计）掌握各设备查询的域名并兼具拦截
neko-master网关控制接口轻（推测）容易（前提是已有网关）高（域名、IP、节点）对网关流量做出域名级的准确归属

4.1 与 Pi-hole 的关系最耐人寻味

表中与 neko-master 性格最接近的不是 ntopng，而是 Pi-hole。两者都不观察流量本身，而是读取控制层早已掌握的事实，属于同一类。但有一处决定性差别。

  • Pi-hole 知道名字，不知道分量。 查询了哪个域名它记得准确，但那条连接实际搬运了多少字节它无从得知。一次查询可能是 1KB，也可能是 10GB。
  • neko-master 同时看到名字与分量，因为网关在按连接计数传输量。对于找出带宽元凶这个原始问题，它更直接。
  • 但 Pi-hole 的覆盖面宽得多。 只要把 DNS 指过去，任何设备都被纳入，而 neko-master 只限于经过其网关的流量。

实践中最现实的是两级组合：在 DNS 层勾出整体轮廓，再到网关统计里确认真实容量。想用其中一种把事情全解决，通常都会失败。

4.2 不要小看 vnStat

看惯了华丽面板容易忘记，在真实的家庭实验室里，活得最久的往往是最简单的那个。只读接口计数器的工具几乎不占资源，实质上不保存个人数据，却能留下好几年的月度总量。若目的是管理套餐上限或判断是否该升级线路，它已经足够，甚至更合适。关键在于：它长寿不是因为功能少，而是因为记录得少。

5. 家庭实验室的现实 - 跑在小设备上会发生什么

5.1 瓶颈出在存储层而非 CPU

接收连接摘要再落库的结构，不像抓包那样让 CPU 直接随线速攀升，因此在小型板卡上跑起来本身通常无碍。问题在别处：连接记录是事件清单而不是统计量，它按连接发生的频次而非线路速度堆积。

现代应用和网页光是打开一个页面就会建立几十条连接。再加上智能家居设备定时叩击服务器的流量，就常常出现带宽微不足道、记录条数却暴涨的局面。真正构成压力的不是一个大文件，而是数万条细碎连接。

5.2 先定好保留期再开始

从仓库文档看，实时窗口在内存中保留 180 分钟，7 天以上的长区间汇总则可另选数据库。这个设计本身就承认长期留存是另一个问题。在家庭实验室里，按下面的顺序推进更稳妥。

  1. 从目的倒推期限。 若目的是排查带宽，几天就够。说不出为什么需要数月的域名历史，那这份数据就不该留下。
  2. 把数据路径挪出存储卡。 microSD 不擅长持续写入。把数据库文件迁到外置固态硬盘或独立卷，对寿命和稳定性都更有利。
  3. 先跑一天实测增量。 24 小时后量一下数据文件大小，立刻就能推算出一个月的用量，比拍脑袋准确得多。
  4. 长期只保留降采样的汇总。 用按日、按域名的合计取代逐条连接记录，既不影响看趋势，又同时降低容量与隐私风险。

另外常被忽略的是备份。监控系统的数据库很容易被排除在备份计划之外，而一旦纳入，每天就有数 GB 的敏感历史被复制到备份存储中。决定不备份，同样是一个必须明确做出的决定。

5.3 面板本身就是新的攻击面

这一点在家庭实验室里尤其容易被忽视。流量面板是整张网络里最敏感的数据汇聚之处，却常常为了方便而对外敞开。

  • 面板原则上只允许内网访问，确需外部访问时通过 VPN 或带认证的隧道
  • 不要把网关控制接口直接暴露到公网 —— 它可能不止能查询，还能改配置
  • 前面提到的 Agent 模式在这个角度上很有用，面板不直连网关，暴露面随之缩小
  • 即使用容器部署，也要核对端口映射范围，绑定到全部网络接口可能在无意中对外开放
  • 把监控数据外发到第三方服务的开关，启用之前先确认到底有什么会流出去

6. 隐私 - 记录家庭流量这件事的分量

6.1 一份域名清单说出的比想象中多

技术文档大多轻描淡写地带过这一点，但在落地判断中它其实是最重的一条。即使不看内容，仅凭目标清单也能了解一个人很多事情。

某种疾病的资讯站点、能暴露宗教或政治倾向的社区、求职网站、心理咨询服务、交友应用的服务器域名，光凭名字就已经在报告这个人的处境。再叠上时间信息，生活作息乃至是否在家都能被还原出来。更麻烦的是这类记录事后极难抹除，今天看着无害的日志，几个月后在家庭矛盾或纠纷场景中可能具有完全不同的意味。

所以原则很简单：只在自己拥有管理权限的网络上运行。 若这张网络还有其他人共用，就告诉他们记录了什么。未经当事人同意窃听或记录他人通信，在许多法域都可能构成法律问题，身处同一屋檐下并不自动豁免。即便理由是保护子女，偷偷记录与先约定规则再使用工具，结果也完全不同。

6.2 按目的所需的最小数据

务实的做法是从目的出发，只采集所需的最小限度。下面梳理了常见目的实际需要的数据层级。

目的所需的最小数据是否需要域名历史建议保留期
管理套餐上限线路收发总量不需要数月（仅总量）
排查速度下降各设备实时用量排名基本不需要数小时到数天
核查某台设备的异常流量该设备的连接目标与频次需要（仅限该设备）数天
判断是否升级线路分时段峰值用量走势不需要数月（汇总值）
盘点智能设备的通信对象各设备的目标域名需要（仅在盘点期间）盘点后删除

从表中可以看出，最常见的两个目的根本不需要域名历史。想知道为什么慢，和想知道谁访问了哪里，是完全不同的两个问题。开工具之前不把这两者分开，就会把不必要的数据存上不必要的时长。

6.3 地理位置查询的陷阱

还有一个附带但值得点出的地方。如果 IP 的地理位置或自治系统号是通过外部查询服务获得的，那么家中流量的目标清单就交到了那家服务手里。为保护隐私而自建的工具，反倒把目标信息漏了出去，这是个实实在在的悖论。neko-master 把基于本地 MMDB 文件的查询列为可选项，可以看作对这一问题的回应，也是挑选任何自建工具时都值得核对的通用项。

7. 落地前要先核对的环境约束

7.1 前提条件本身很可能不成立

最现实的门槛不是功能，而是前提。这个工具要求已经存在 Clash、Mihomo 或 Surge 一类网关，并且控制接口处于开启状态。而许多家庭直接使用运营商提供的路由器，那种环境中根本不存在这类网关。文档标注的界面语言是英文与中文。

换句话说，对多数用户而言装面板这件事，远比搭好它前面那一段要小。得先另立一台路由器或服务器并配好路由，这块屏幕才有意义。若本来就在运行这样的网关，它是很好的补充；但为了用这块面板而专门引入一套网关，则是把决策顺序搞反了。

7.2 双重路由与端口转发

住宅线路的另一个特点是运营商设备与个人路由器叠在一起的双层结构很常见，由此会反复出现一些问题。

  • 端口转发要做两遍 —— 上层设备与下层路由器都配好，外部访问才成立
  • 上层设备直接封掉端口的情况 —— 下层怎么配都开不了，白白耗掉大量排查时间
  • 私有地址被分配两次 —— 设备清单按层级割裂，弄不清该看哪一块界面
  • 切换桥接模式 —— 常用做法是把运营商设备转为桥接、让个人路由器做主路由，但方法随设备与套餐而异

从监控角度看，要点在于测量点放在哪里，结果就会不同。在下层路由器上测，挂在上层的设备流量就看不见。数值反常时，与其怀疑工具，不如先确认自己究竟在测哪一个位置，这样更快。

7.3 宽带与电视融合的线路

宽带与电视捆绑的套餐在许多市场都很普遍，它对监控有两方面影响。其一，电视流量常常走与普通上网流量不同的路径，因而可能不出现在面板数值里，或者反过来被异常放大。解读统计时不把这部分剥离，就会得出离谱的结论。

其二，更实际的问题是随意改动布线或路由器设置会让电视断掉。为了加监控而改网络结构、结果客厅电视看不了，在家庭实验室里并不罕见。改结构之前先准备好回退手段，可能的话优先考虑不触碰既有路径的观测点，会更稳妥。

8. 那么什么时候用它 - 按场景选择

  • 已经在运行基于规则的网关 → neko-master 很合适。不必新建基础设施，只是把既有接口输出变成界面，投入产出比高
  • 只需要看线路总量与套餐上限 → 接口计数器类工具就是正解，用更复杂的反而吃亏
  • 想判断服务器慢是网络还是磁盘 → 要用能同时展示主机指标的工具，只看流量得不出原因
  • 想全面了解各设备都在连什么 → DNS 层工具的覆盖面最广
  • 需要深入看清经过某段链路的全部流量 → 必须用抓包类工具，代价是资源与隐私开销
  • 想长期留存多种指标并配上告警 → 指标采集器加可视化的组合最合适，搭建成本最高，上限也最高

反复出现的结论只有一个：先挑工具再往上套问题，多半会失败。 正确的顺序是先把想回答的问题写成一句话，再挑出回答它所需的最小采集方式。

9. 落地前该自问的三件事

每见到一块新面板，界面漂亮就想先搭起来看看，这是人之常情。留下三个问题来过滤这份冲动。

  1. 我要回答的问题能写成一句话吗？ 想把网络看清楚，这不算问题。每晚十一点上行飙升的原因是什么，才算具体。写不成一句话，面板搭起来也没有打开它的理由，两个月后就会关着落灰。
  2. 这个工具真的在看答案所在的位置吗？ 采集方式就等于视野。如果元凶是绕过网关的设备，读取网关接口的工具永远找不到它。上手前花十分钟确认自己关心的对象是否落在这个工具的视野内，就能省下好几天。
  3. 这份记录泄露了我能承受吗？ 流量面板是家中最敏感数据的汇聚点。没定好访问控制、保留期与备份策略就开起来，等于为解决一个问题而制造一个更大的问题。若这个答案让人不安，把采集粒度降一级才是对的选择。

结语

neko-master 是一个做得不错的工具。它选中网关控制接口这个本就存在的准确数据源，因而不必费力解析报文，也能拼出域名级别的清晰画面。MIT 许可、容器化部署、减少网关暴露的 Agent 模式，乃至用本地地理信息文件替代外部查询的选项，这些设计取舍大体都站得住脚。

但准确地称呼这个工具很重要。它不是网络监控工具，而是网关流量面板。视野被限定在经过该网关的流量，这是设计而非缺陷，而在这段窄范围内，它给出的准确度是其他方式难以企及的。理解了这条边界再用，它很有用；误解了，则只是多出一块看着数据也答不出问题的界面。

落地之前，先核对前提条件与线路结构。已经有网关的话，接上去的理由很充分；没有的话，从总量类工具或 DNS 层工具起步要合理得多。无论最终选哪一个，最后的原则都一样：只观测自己拥有管理权限的网络，只采集目的所需的最小限度，只保留必要的时长。 为了抓住占用带宽的元凶，就把同住之人的一整天完整记录下来，那不是解决问题，只是把问题挪了个位置。
