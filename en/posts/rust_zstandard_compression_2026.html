Introduction: Why Rewrite a Compression Library in Rust?

The Zstandard-in-Rust announcement that trended on GeekNews (news.hada.io) in early June 2026 was Trifecta Tech Foundation's "Announcing Zstandard in Rust," published on 2026-06-01. The project behind it is libzstd-rs-sys, which translated the zstd C reference implementation into Rust with c2rust and is cleaning the result up step by step. Rewriting a compression library that has worked well in C for years is not a matter of language taste. It is one scene in a much larger movement: systems software that parses untrusted external input is migrating to memory-safe languages.

Compression libraries are invisible to most users, yet they run behind nearly every system. They are called when a web server compresses a response, when a database writes data to disk, when a container registry ships an image, and when a backup tool archives files. And these codecs almost always decompress data you cannot control, received over the network or from a file. A single memory bug in the decompression path lets an attacker take over a server with one maliciously crafted compressed file.

This article covers (1) what Zstandard is, (2) why Rust specifically, (3) the vulnerability history of C compression libraries, (4) five benefits of a Rust rewrite, (5) a gzip vs lz4 vs zstd vs brotli comparison, (6) why zstd is popular, (7) the three kinds of zstd implementations in Rust, (8) the Rust vs C performance trade-off, (9) five production scenarios, (10) adoption in real engineering teams, and (11) a conclusion with three immediately actionable steps. Crate versions, implementation status, and benchmark figures were checked against each project's repository, crates.io, and README as of 2026-09-29.

1. What Is Zstandard - An Overview of the zstd Algorithm

Zstandard (zstd for short) is a general-purpose lossless compression algorithm developed by Facebook, now Meta, and released in 2016. The reference implementation lives at github.com/facebook/zstd and is dual-licensed under BSD or GPLv2. The format is stable and documented in RFC 8878, and as of 2026-09-29 the latest release of the reference implementation is v1.5.7 (2025-02-19). The README describes zstd as "a fast lossless compression algorithm, targeting real-time compression scenarios at zlib-level and better compression ratios."

Three traits set zstd apart. First, the range of compression levels. The Rust zstd crate documents regular levels as 1 to 22, and negative levels set with --fast=# trade ratio for even faster compression and decompression. Raising the level trades compression speed for ratio, while, per the README, decompression speed stays roughly the same at all settings. Second, dictionary training. The README notes that small data is the hardest to compress and that a dictionary trained on samples improves the ratio on small data dramatically. Third, a clean streaming API lets you process large files without loading them entirely into memory.

Internally, zstd layers LZ77-style matching on top of a very fast entropy stage built from Huff0 and FSE (Finite State Entropy). Without diving into the theory, the point worth stressing is that zstd has become the de facto compression standard of the 2020s. The Linux kernel, RocksDB, Parquet, ZFS, btrfs, and several package managers have adopted it.

2. Why Reimplement in Rust - The Value of Memory Safety

The reason for rewriting a perfectly functional C library in Rust compresses down to one word: memory safety.

C and C++ are powerful and fast, but they manage memory by hand. Pointer arithmetic, manual allocation and freeing, and the absence of bounds checking lead directly to buffer overflows, use-after-free, double free, and integer overflow. These are not mere bugs; they are security vulnerabilities. Statistics published by Microsoft and Google indicate that roughly 70 percent of their security vulnerabilities stem from memory-safety issues.

Rust checks this class of problems at compile time with ownership and the borrow checker, statically verifying memory access in safe code with no garbage collector and no runtime overhead. Rewriting a codec like zstd in safe Rust therefore structurally reduces the category of CVEs where parsing untrusted input corrupts memory. The effect only applies outside unsafe blocks, though. Code translated with c2rust starts out full of unsafe, so the real value of a rewrite is decided by how much of that unsafe has been removed (section 7).

Key point - Compression libraries almost always decompress uncontrollable, externally supplied data. That is exactly where a memory-safe language delivers the most value.

3. The Risk of C Implementations - A History of Codec Vulnerabilities

This is not an abstract risk. Compression libraries have repeatedly produced serious problems. Here are the representative patterns.

3-1) zlib and Decompression Bombs

The ubiquitous zlib has been refined for decades, yet the many wrappers and parsers built on top of it keep surfacing decompression-related vulnerabilities. Attacks like the zip bomb, where a tiny compressed file expands to enormous memory on decompression, remain effective today, and a memory-safe language does not stop them. The pure-Rust decoder ruzstd warns in its README that decoded frames can be very large and advises checking the frame size or decoding in a streaming fashion; its 0.9.0 source sets a default maximum window size of 100MB (1024×1024×100 bytes) and rejects frames that declare a larger window. That limit bounds allocation, not the total size of the decoded output, so the caller still has to cap the output size.

3-2) Integer Overflow and Heap Corruption

Compression formats handle length and offset fields. In C, multiplying or adding these values without validation triggers integer overflow, which then allocates a heap buffer of the wrong size and leads to heap corruption. This is a textbook pattern reported repeatedly across codecs.

3-3) The XZ Utils Backdoor (2024)

The XZ Utils (liblzma) backdoor discovered in 2024 was a shocking demonstration that compression libraries can be the target of supply-chain attacks. This is a different dimension from memory safety, concerning trust and the supply chain, but it seared one lesson into everyone: compression libraries are embedded so deep in the system that a single breach causes widespread damage.

The conclusion is this. A codec is not in the "it works, do not touch it" category; it is a security-critical component that deserves memory safety before almost anything else. The Rust rewrite is the natural consequence of that realization.

4. Five Benefits of the Rust Rewrite

Here are five practical benefits of reimplementing a compression library in Rust.

4-1) Memory Safety

The biggest benefit. In safe Rust code, the compiler blocks buffer overflows, use-after-free, and double free. But the benefit does not come from the language choice alone. As of 2026-09-29, the libzstd-rs-sys README itself says the encoder "is functional, but still mostly just the raw c2rust translation and hence full of unsafe code." How much unsafe has been removed is the measure of how much safety you actually get.

4-2) Safe Concurrency

Rust's ownership model prevents data races at compile time. Compression is naturally parallelizable at the block level, and in Rust it is easy to implement safe multithreaded compression with a library like rayon.

4-3) Ease of Integration

A Rust crate is added as a dependency in a single cargo line. The Trifecta announcement points out that today's zstd crate compiles C code from source and therefore needs a C toolchain, and that a pure-Rust implementation removes that requirement, which helps on platforms such as Windows and WebAssembly.

4-4) Maintainability

Rust's strong type system and pattern matching make stateful code like a compression-format parser safer and more readable. With more correctness enforced by the compiler, the cost of refactoring drops.

4-5) Trust

The four points above add up to trust. As evidence accumulates for the claim that "this library will not corrupt memory even on malicious input," adoption decisions in security-sensitive infrastructure move faster. libzstd-rs-sys running fuzzing and Miri on top of the reference implementation's test suite is part of building that trust.

6. Why Zstandard Is Popular - The Speed and Ratio Balance

Here is why zstd became a de facto standard so quickly.

6-1) Balance

As the table in section 5 shows, even at the fastest settings zstd -1 beats zlib -1 on ratio (2.896 vs 2.743) while compressing about 5 times and decompressing about 4 times faster, and it compresses far better than lz4. Most workloads need "reasonably good ratio and reasonably good speed," and zstd lands exactly on that spot.

6-2) Freedom to Tune Levels

A single level dial covers real-time (levels 1 to 3, or negative levels) through archival (levels 19 to 22) with one tool. You can change only the level in production to adjust the speed-versus-size trade-off, and the fact that decompression speed barely depends on the level is its most practical strength.

6-3) Dictionary Training

Dictionary training pays off most where huge volumes of small messages are compressed, such as JSON between microservices or IoT sensor data. In a measurement published in the ruzstd README, the github-users sample (7,484,607 bytes; about 10K records of roughly 1KB each, per the zstd README) compressed to 34.99% of the original without a dictionary, and to 16.16% of that size with a dictionary built by the reference implementation. The zstd README explains that a dictionary works best when it is specific to one type of data and that the gains come mostly in the first few KB.

6-4) Ecosystem Adoption

The Linux kernel (initramfs and module compression), the ZFS and btrfs filesystems, RocksDB and Parquet, the Arch and Fedora package managers, and many container registries adopt zstd as a default or an option. A virtuous cycle of adoption breeding more adoption has taken hold.

7. Zstd in the Rust Ecosystem

As of 2026-09-29 there are three ways to use zstd from Rust: bindings to the C reference implementation, a pure-Rust implementation written from scratch, and an implementation that translates the C code into Rust and cleans it up.

7-1) What Was Announced - libzstd-rs-sys

Trifecta Tech Foundation's libzstd-rs-sys translates the reference implementation with c2rust and then cleans it up. At the time of the announcement (2026-06-01) the version was v0.0.1-prerelease.2; cleanup of decompression and the dictionary builder was complete, while most of the cleanup for compression was still ahead. Decompression work was funded by Chainguard, Astral, and the NLnet Foundation, the dictionary builder by the Sovereign Tech Agency, and funding for the compression part is still being sought. As of 2026-09-29 the README describes the state as follows: the decoder has undergone significant cleanup and is mostly safe, the dictionary builder has some lingering unsafe when calling into the encoder, and the encoder is functional but mostly the raw c2rust translation. The decoder is "ready for experimental use, but is not yet battle-tested."

It is also used differently from a typical crate. The README's primary usage is building a static library to link into C projects (cargo build --features=export-symbols -p libzstd-rs-sys --release --lib), and hooking into the zstd crate (zstd-rs) for convenient use from Rust is a future goal. The announcement mentions an in-house fork that uses libzstd-rs-sys, but the feature flags of zstd 0.14.0, released on 2026-09-04, include no option to select it as a backend. As of 2026-09-29 the latest GitHub release and crates.io version is still 0.0.1-prerelease.2, the repository is active with changes pushed the same day, and the license is BSD-3-Clause.

Watch the names - Two repositories are called "zstd-rs." gyscos/zstd-rs hosts the C-binding crate zstd, and KillingSpark/zstd-rs hosts the pure-Rust crate ruzstd. The Rust implementation in this announcement is a third project (libzstd-rs-sys). What cargo add zstd gives you is the C binding, not the Rust rewrite.

7-2) Adding the cargo Dependency

The most widely used zstd crate is a binding to the C reference implementation. As of 2026-09-29 the latest is 0.14.0 (2026-09-04), and zstd-sys 2.1.0+zstd.1.5.7, released the same day, carries the C library version 1.5.7 in its version name. In crates.io metadata the license field changed from MIT in 0.13.3 to BSD-3-Clause in 0.14.0. The pure-Rust ruzstd is at 0.9.0 (2026-07-26, MIT, minimum Rust 1.87). Per its README, decompression implements the full standard, while compression is usable but does not yet reach the speed, ratio, or configurability of the original library. In the 0.9.0 source only the Uncompressed and Fastest (roughly level 1) compression levels are implemented; Default, Better, and Best are marked "UNIMPLEMENTED."

[dependencies]
# C binding (the most mature choice, 0.14.0 as of 2026-09-29)
zstd = "0.14"

# Or a pure-Rust implementation (full decompression, compression up to Fastest)
# ruzstd = "0.9"

7-3) Basic Compress and Decompress

The code below matches the encode_all(source, level) and Decoder::new(reader) signatures in the zstd 0.14.0 source.

use std::io::Read;

fn main() -> std::io::Result<()> {
    let data = b"Hello, Zstandard in Rust! ".repeat(1000);

    // Compress (level 3 = balanced, 19+ = archival)
    let compressed = zstd::encode_all(&data[..], 3)?;
    println!("{} bytes -> {} bytes", data.len(), compressed.len());

    // Decompress
    let mut decompressed = Vec::new();
    zstd::Decoder::new(&compressed[..])?.read_to_end(&mut decompressed)?;
    assert_eq!(data, decompressed);
    Ok(())
}

Here is the same round trip with the pure-Rust ruzstd 0.9.0. The function names compress_to_vec and StreamingDecoder are taken as-is from its README and source.

use ruzstd::decoding::StreamingDecoder;
use ruzstd::encoding::{compress_to_vec, CompressionLevel};
use ruzstd::io::Read;

fn main() {
    let data = b"Hello, pure-Rust zstd! ".repeat(1000);

    // Compress: only Uncompressed and Fastest are implemented in 0.9.0
    let compressed = compress_to_vec(&data[..], CompressionLevel::Fastest);

    // Decompress
    let mut decoder = StreamingDecoder::new(&compressed[..]).unwrap();
    let mut out = Vec::new();
    decoder.read_to_end(&mut out).unwrap();
    assert_eq!(data, out);
}

7-4) Its Place in Systems Programming

Storage engines, log collectors, and network proxies written in Rust commonly use zstd. Once pure-Rust decoders mature, you can keep the entire decompression path memory-safe without an FFI boundary (the C binding), which is the biggest appeal. For the broader migration story, see the Go to Rust migration guide 2026.

8. Performance - The Rust vs C Trade-off

The most common question is, "Is the Rust rewrite slower than C?" The answer depends heavily on how the implementation was built.

8-1) The Theoretical Ceiling Is the Same

Rust generates native code on par with C and C++ through the LLVM backend. With no garbage collector and no runtime overhead, the theoretical performance ceiling is identical to C.

8-2) The Real Gap Depends on the Approach

The C reference implementation has been optimized to the limit over years. libzstd-rs-sys, which translates and cleans up that code, reports in its announcement that decompression is a few percent slower than C by default and matches C performance with the experimental feature flag unsafe-performance-experimental, which, as its name says, is an experimental feature that uses unsafe. ruzstd, written from scratch, is about 3.5 times slower than C when decoding enwik9.zst and about 1.4 times slower on less compressible data such as an Ubuntu installation iso, per its README (measured with the time utility). The gap reflects optimization time and design approach, not a language limitation. The same dynamic appears with allocators in the mimalloc deep dive 2026.

8-3) Ways to Narrow the Gap

Rust can use SIMD through core::arch intrinsics, and safe parallelism makes multicore gains easier to capture. libzstd-rs-sys tracks its performance on a public benchmark page (trifectatechfoundation.github.io/libzstd-rs-sys-bench), so you can watch the gap change yourself.

Caution - The figures above were measured by each project under its own conditions and vary widely with workload, level, and data. Do not treat a single benchmark number as absolute; measure with your own data.

The conclusion: a performance trade-off of a few percent is more than offset by the security value of "no memory corruption even on malicious input." For an implementation that is slower by a multiple, though, you need to check workload by workload whether the exchange still holds.

9. Five Production Scenarios

Here are five scenarios where adopting zstd is justified.

9-1) Log Collection and Storage

Logs are voluminous with strong repeating patterns, so the ratio is excellent. zstd's good ratio cuts storage cost, and fast decompression keeps log search and analysis snappy. Tools like Elasticsearch and Loki support zstd.

9-2) Backup and Archival

For long-term backups, ratio equals cost. zstd's high levels (19 to 22) trade compression speed for a higher ratio, while decompression speed stays nearly independent of the level. Short restore time matters especially for archives.

9-3) Network Transport

For API responses, message queues, and streaming, low-level (1 to 3) zstd saves bandwidth while preserving real-time behavior. Combined with dictionary training, the ratio for small JSON messages improves substantially.

9-4) Storage and Databases

RocksDB, Parquet, ClickHouse, ZFS, and btrfs adopt zstd as default or recommended compression. Where disk I/O is the bottleneck, compression is effectively a performance boost, because there are fewer bytes to read and write. For object and blob layers, this pairs well with the patterns in the Files SDK unified blob storage guide 2026.

9-5) Container Images and Packages

Container registries and package managers (Arch, Fedora, and others) use zstd to cut transfer time and storage at once. Faster image pulls lighten the entire deployment pipeline.

10. Adoption in Real Engineering Teams

Here is how teams can approach zstd and the Rust rewrite in practice.

10-1) Cost-Reduction Effect

Storage and transfer costs are non-trivial on every major cloud. Switching log, backup, and database compression from gzip to zstd can reduce storage usage and transfer volume and lower bills. The savings vary by data, so measure with your real data first.

10-2) Meeting Security Requirements

Finance and public-sector systems carry strong security demands. Evidence that "parsing untrusted input cannot corrupt memory" is a persuasive adoption argument for teams that face heavy security review and vulnerability assessment. To avoid overstating it, security review documents should also state the unsafe cleanup status and release stage of the implementation you plan to use (for example, libzstd-rs-sys is a pre-release as of 2026-09-29).

10-3) An Incremental Rollout Strategy

A safe approach is not to switch everything at once but to start with new log pipelines or new backup jobs on zstd. Keep existing gzip assets for compatibility, but make zstd the default for anything you build new. That accumulates the upside while keeping risk low.

11. Conclusion + Three Steps You Can Take Today

To summarize Zstandard in Rust in one sentence: an evolution in progress that adds the security value of memory safety to the well-balanced standard compressor that is zstd. Here are three patterns you can apply right away.

11-1) Step 1: Make zstd the Default for New Compression

For new log, backup, and transport paths, default to zstd level 3 (balanced) unless you have a reason not to. Even comparing the fastest settings in the README benchmark table, it is faster than zlib and compresses better.

11-2) Step 2: Pick the Optimal Level by Measurement

Start real-time paths at levels 1 to 3 (or negative levels) and archives at levels 19 to 22, then measure ratio and speed on your real data to find the sweet spot. If you compress repetitive small messages, be sure to test dictionary training.

11-3) Step 3: Prefer a Memory-Safe Decoder in Rust Projects

If your Rust code decompresses untrusted input, evaluate ruzstd, a pure-Rust decoder that implements the full standard, first to shrink the FFI boundary. If decompression speed matters, use the C binding (the zstd crate) but abstract the interface so it is easy to switch when libzstd-rs-sys gets a stable release or is wired into the zstd crate. On the compression side, pure-Rust options are still narrow as of 2026-09-29 (ruzstd stops at the Fastest level), so the C binding is the realistic choice.

The closing message is this. Compression is both an invisible cost-reduction lever and an invisible security surface. zstd offers the most balanced cost-reduction lever, and the Rust rewrite is steadily shrinking that security surface. If you are designing a new system in 2026, this combination is worth a serious evaluation.
