Introduction: two false assumptions

The list of web application flaws is long. Step back one pace from that list, though, and most entries turn out to start in the same place. They carry different names and sit in different checklist rows, but the root is two sentences.

Assumption ① - the client cannot be changed. The value placed in a form, the data- attribute in the markup, the cookie, the request body, the request headers. Not one of them is beyond the user's reach.
Assumption ② - the attacker cannot guess. Reset tokens, session values, internal identifiers. A predictable value is not a secret.

These two sentences matter because they let you decide while reading the code instead of memorising a catalogue of flaws. When you see code that treats an arriving value as necessarily the value it sent, that is ①. When you see a value treated as a secret while the function that produced it uses a clock or a counter as its raw material, that is ②.

This article works through fourteen concrete places. When a cookie is actually attached to a request, what becomes possible when two individually medium findings overlap, why a design in which the server accepts a client-computed amount does not hold, and what a log can and cannot prove once identification controls have broken down. Every section puts the vulnerable code next to the safe code, and closes by naming which of the two assumptions the flaw grew from.

If you want the cookie transmission rules broken down request type by request type, SameSite Lax, Strict, None - Which Requests Drop Your Cookie covers that separately. The problem of interpreting headers that arrive more than once is handled in When the Same Header Arrives Twice.

Scope of this article. It covers why something is dangerous and how to stop it, and nothing beyond that. There is no working exploit code, no bypass technique, and no tooling walkthrough. The review method in the last section is limited to a site you operate or have explicit authorisation for. Every path and filename in the code examples is an invented placeholder used for explanation.

1. When does the browser send the cookie - what the three SameSite values actually do

Read enough server code and you find one premise sitting underneath it unspoken: the session cookie is attached, therefore this request came from our own screen. Whether that premise holds is not decided by the server. It is decided by when the browser attaches the cookie, and the attribute that tunes that rule is SameSite.

The definitions are on the MDN Set-Cookie page. SameSite=Strict sends the cookie only for requests originating from the same site that set the cookie. SameSite=Lax sends the cookie for same-site requests, and for cross-site requests only when the request is both a top-level navigation and one that uses a safe method. The same page describes a top-level navigation as a request that causes the URL in the address bar to change, and names POST, PUT and DELETE as excluded from safe methods. SameSite=None sends the cookie with both cross-site and same-site requests, and the Secure attribute must also be set when using this value.

# Vulnerable: no attributes at all. A script can read it, it goes out in cleartext,
#             and whether it rides along on cross-site requests is left to a default.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/

# Vulnerable: cross-site transmission has been opened explicitly.
#             Often this was turned on for an embed and simply stayed.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; SameSite=None; Secure

# Safe: the baseline shape for a session cookie.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

# Safe: use Lax when arriving from an external link must keep the user logged in.
#       With Strict, that first request looks like a logout to the user.
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Lax

1.2 Why leaning on the default is a mistake

The MDN Set-Cookie page writes that «some browsers use Lax as the default value if SameSite is not specified». The word «some» is the point. And the Lax applied as a default is not the same as the Lax you set explicitly. The same page notes that when Lax is applied as a default, a more permissive version is used, and in that version cookies are also included in POST requests as long as they were set no more than two minutes before the request was made.

If the cookie transmission condition is not stated, the decision is delegated to a browser default, and a default is a value that can differ by browser and by version.

  • A default is weak ground for a code review argument of the form «the default is Lax, so we are fine», because the basis sits outside your own code
  • The two-minute window of the permissive default Lax overlaps precisely with the flow that follows a login
  • A cookie that sets None without Secure is rejected by the browser. The result is not «slightly weaker security» but «no cookie at all», which usually surfaces as a functional outage first
  • SameSite is evaluated against the registrable domain, not the origin. A different host under the same domain counts as same-site
  • The OWASP Session Management Cheat Sheet states that session cookies must explicitly set SameSite=Strict as the preferred value, or Lax

Which assumption - ①. «Only requests from our own screen arrive here» delegates the question of origin to conditions on the client side.

2. What a CSRF token stops and what it does not

CSRF is, per the definition in the OWASP Cross-Site Request Forgery Prevention Cheat Sheet, an attack that occurs when a malicious web site, email, blog, instant message, or program tricks an authenticated user's web browser into performing an unwanted action on a trusted site. The same document summarises the enabling condition in one line: browser requests automatically include all cookies including session cookies, so this attack works unless proper authorization is used.

«Proper authorization» here does not mean checking whether the user is logged in. They are already logged in. What is needed is evidence that this request began on our own screen, and that evidence has to be a value the browser does not attach on its own.

The job of a CSRF token is to prove the origin of a request. That is why it has to be a value the browser does not attach automatically, and why a cookie that is attached automatically cannot take its place.

2.1 Synchronizer token - a value the server remembers

In the synchronizer token pattern described by the OWASP Cross-Site Request Forgery Prevention Cheat Sheet, the token is generated on the server side, either once per user session or once per request. The server checks that the token carried by the request matches the value it stored against the session. Because the browser never attaches it automatically, a request built on another site cannot contain it.

<!-- Vulnerable: a state-changing form authenticated only by a value the browser attaches by itself -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">Delete</button>
</form>

<!-- Safe: the form carries a value the server stored against the session -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="csrf_token" value="PLACEHOLDER_TOKEN_FROM_SESSION">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">Delete</button>
</form>
// Vulnerable: only login state is checked. Where the request began is not.
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();
  deleteItem(req.body.item_id);
  res.status(200).end();
}

// Safe: compare the session-held token with the request token in constant time.
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();

  const expected = req.session.csrfToken;         // the value the server remembers
  const provided = req.body.csrf_token;           // the value the request brought
  if (!expected || !provided || !timingSafeEqual(expected, provided)) {
    return res.status(403).end();                 // a failed check is a refusal, not a pass
  }
  deleteItem(req.body.item_id);
  res.status(200).end();
}

2.2 Double submit cookie and its limits

Where the server cannot easily hold state, the double submit pattern is used: put the same value in a cookie and in the request body, and have the server check only that they match. The problem is that the server never remembers the value. The OWASP Cross-Site Request Forgery Prevention Cheat Sheet states that the naive form is bypassable by an attacker who can write cookies on the target domain, and names the routes: a vulnerable sibling subdomain, DNS takeover, or plaintext-HTTP cookie injection. The recommendation in the same document is the signed double submit, binding the token to session data with an HMAC under a server-side secret.

// Vulnerable: only checks that the two values match.
//             Where they came from is never established.
function verifyCsrf(req) {
  return req.cookies.csrf === req.body.csrf_token;
}

// Safe: sign a session-bound value with a server secret.
//       Being able to write cookies is no longer enough to forge a valid token.
function issueCsrf(session) {
  const nonce = randomTokenHex(32);                       // cryptographic randomness
  const mac   = hmacSha256(SERVER_SECRET, session.id + '.' + nonce);
  return nonce + '.' + mac;
}
function verifyCsrf(req) {
  const [nonce, mac] = String(req.body.csrf_token || '').split('.');
  if (!nonce || !mac) return false;
  const expected = hmacSha256(SERVER_SECRET, req.session.id + '.' + nonce);
  return timingSafeEqual(expected, mac);                  // also proves it belongs to this session
}

It is worth being just as clear about what the token cannot stop. The OWASP Cross-Site Request Forgery Prevention Cheat Sheet puts it in capitals: cross-site scripting can defeat all CSRF mitigation techniques. If attacker code is executing inside the page, that code can read the token out of the DOM and attach it. A token filters out «a request built by another site». It does not filter out «a request built inside our own page».

  • The default behaviour on a failed token check must be refusal. An implementation that logs and lets the request through is equivalent to having no control
  • The custom header approach is also valid. The same OWASP document explains that all modern browsers designate requests carrying custom headers as ones to be preflighted, so a server that verifies the header knows a browser-originated request must have been preflighted
  • That approach collapses if Access-Control-Allow-Origin is loose. A wildcard origin nullifies the defense
  • Putting the token in a GET query string leaves it in logs, referrers and browser history. Do not expose state changes over GET
  • One token per session and a fresh token per request are both valid. The per-request variant needs a design for parallel tabs, where the earlier token is invalidated

Which assumption - ①. «This request was built by our form» is the assumption in this section. Without a value that proves origin, that sentence remains an unverified guess.

3. When two findings overlap - medium each, critical together

Taken one at a time, neither of these looks especially serious.

  • Finding A - a state-changing endpoint has no CSRF token check. On its own this rates as medium. Browser defaults have moved toward not attaching cookies to cross-site POST requests, and that default acts as a de facto mitigation
  • Finding B - the session cookie carries SameSite=None; Secure. On its own this is classed as a configuration item. The value is legitimate, and for a service that needs to be embedded it may be the correct choice

Put both in the same system and the character changes. B explicitly switches off the browser-side mitigation, so the session cookie now rides along on cross-site requests. And because of A, the server retains no means whatsoever of judging where a request came from. What the server sees is a single state-changing request carrying a valid session cookie, with no basis for distinguishing one that began on its own screen from one that began elsewhere.

An item-by-item checklist rates items, but the real risk arises from the relationships between items, and an item-scored sheet has no column for relationships.

  • The same shape recurs elsewhere: a predictable identifier plus a missing ownership check, a session that survives login plus a route by which a session value can be planted, a permissive Access-Control-Allow-Origin plus credentialed requests
  • To see combinations you have to follow one request all the way through instead of counting items. What does the browser attach, what does the server verify, and what does it not verify
  • Even for a low-rated item, recording «what is currently mitigating this» surfaces the combination. If A's mitigation was a browser default, then any setting that disables that default becomes an immediate thing to look for
  • It also changes remediation order. Removing either A or B breaks the path. If the embed is not genuinely required, reverting B is usually the cheaper move

Which assumption - ①. A and B both rest on the same assumption, that client-side conditions will report where a request came from. That is why they amplify each other instead of cancelling out.

4. What happens when the user identifier lives in a cookie

There is a shape that feels convenient while you are writing it. Put the user number in a cookie at login, then read that value on later requests to decide whose request this is. It saves one lookup.

# Vulnerable: the user number sits in the cookie in plain form.
Set-Cookie: uid=1042; Path=/
Set-Cookie: role=member; Path=/

# Vulnerable: a session value that carries identity in human-readable form.
Set-Cookie: session=user-1042-member; Path=/; HttpOnly

# Safe: the value means nothing by itself; identity is what the server looks up with it.
Set-Cookie: session=PLACEHOLDER_OPAQUE_128BIT_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

The OWASP Session Management Cheat Sheet is direct. The session ID content must be meaningless to prevent information disclosure attacks, the session ID must simply be an identifier on the client side, and its value must never include sensitive information or personally identifiable information. The same document states the entropy requirement alongside: session identifiers must have at least 64 bits of entropy to prevent brute-force guessing, and with hexadecimal encoding that means at least 16 characters.

IDOR is, per the definition in the OWASP Insecure Direct Object Reference Prevention Cheat Sheet, a vulnerability in which attackers can access or modify objects by manipulating identifiers used in a web application's URLs or parameters. The same document frames the flaw as requiring three components: an object, a reference to that object, and a missing object-level authorization check.

// Vulnerable: queries by the user number the request supplied.
//             Nobody checks that the requester owns what is returned.
function getOrder(req, res) {
  const uid = req.cookies.uid;                    // a value the client chose
  const order = db.findOrder(req.params.orderId);
  res.json(order);                                // no ownership check
}

// Safe: identity comes only from the server session, and ownership is part of the query.
function getOrder(req, res) {
  const uid = req.session.userId;                 // a value the server remembers
  if (!uid) return res.status(401).end();

  // Instead of finding then comparing, only ever find what is mine.
  const order = db.findOrderOwnedBy(req.params.orderId, uid);
  if (!order) return res.status(404).end();       // do not leak existence either
  res.json(order);
}

Difficulty of guessing is not access control. The OWASP Insecure Direct Object Reference Prevention Cheat Sheet states that even with complex identifiers, access control checks are essential, and that if attackers obtain URLs for unauthorized objects the application should still block their access attempts.

  • Per the same page, when both Expires and Max-Age are set, Max-Age takes precedence, and a zero or negative value expires the cookie immediately

  • The same document says not to store authentication tokens, session IDs, JWTs, refresh tokens or any credential in localStorage or sessionStorage

5. Predictable reset tokens - a predictable value is not a secret

The token in a password reset link is a stand-in for the authentication credential for as long as it is valid. Whoever holds a valid token changes the account password. Its quality therefore belongs at the same level of scrutiny as the login password itself.

CWE gives this flaw its own number. CWE-640 names the state in which «the product contains a mechanism for users to recover or change their passwords without knowing the original password, but the mechanism is weak» as Weak Password Recovery Mechanism for Forgotten Password. Its parents are CWE-1390 Weak Authentication and CWE-287 Improper Authentication. In other words this is classified as an authentication flaw. It is not a problem with an auxiliary feature; it is a second authentication path, and the weaker one.

5.1 The source of the randomness is the whole story

MDN places a note at the top of the Math.random() page: «Math.random() does not provide cryptographically secure random numbers. Do not use them for anything related to security. Use the Web Crypto API instead, and more precisely the Crypto.getRandomValues() method.» The same page adds that «the implementation selects the initial seed to the random number generation algorithm; it cannot be chosen or reset by the user». Not being able to control the seed does not mean it is safe. It means there is no guarantee about what the value is made from.

A predictable value is not a secret. When the code that treats a value as secret and the code that produces it rest on different premises, what is being treated as secret is not the value but a belief about the function that made it.

// Vulnerable: built from a clock and a user number. Both can be narrowed from outside.
function makeResetToken(userId) {
  return md5(Date.now() + '-' + userId);
}

// Vulnerable: a random function, but not a cryptographic source.
function makeResetToken() {
  return Math.random().toString(36).slice(2, 12);
}

// Vulnerable: a counter. One issued value reveals the shape of its neighbours.
function makeResetToken(seq) {
  return 'reset' + String(seq).padStart(8, '0');
}

// Safe: drawn from a cryptographic source at sufficient length.
function makeResetToken() {
  const buf = new Uint8Array(32);                 // 256 bits
  crypto.getRandomValues(buf);
  return [...buf].map(b => b.toString(16).padStart(2, '0')).join('');
}

5.2 One good token is not enough

The OWASP Forgot Password Cheat Sheet asks for more than randomness quality. Tokens must be generated using a cryptographically secure random number generator, must be long enough to protect against brute-force attacks, and must be invalidated after they have been used. The same document also requires enumeration prevention: return a consistent message for both existent and non-existent accounts, and ensure that responses return in a consistent amount of time to prevent an attacker enumerating which accounts exist. For the page the link opens, the guidance is to add the Referrer Policy tag with the noreferrer value in order to avoid referrer leakage, and when building the reset URL, do not rely on the Host header - hard-code it or validate it against a list of trusted domains. For existing sessions the advice is to ask the user whether to invalidate all of their existing sessions, or invalidate them automatically.

// Vulnerable: token stored in the clear, no expiry, no single-use handling,
//             and old login sessions survive the reset untouched.
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (!user) return { ok: false, message: 'That email is not registered' };  // leaks existence
  const token = makeResetToken(user.id);
  await db.saveResetToken(user.id, token);
  await sendMail(email, 'https://example.com/reset?token=' + token);
  return { ok: true };
}

// Safe: stored hashed, given an expiry, single use, and an identical response either way.
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (user) {
    const token = makeResetToken();                       // cryptographic randomness
    await db.saveResetToken({
      userId:    user.id,
      tokenHash: sha256(token),                           // never store the original
      expiresAt: Date.now() + RESET_TTL_MS,               // short expiry
      usedAt:    null                                     // single-use marker
    });
    await sendMail(email, RESET_BASE_URL + '?token=' + token);  // not from the Host header
  }
  await constantDelay();                                  // even out the response time
  return { ok: true, message: 'If that address exists, instructions have been sent' };
}
// Safe: the completing half of the flow.
async function completeReset(token, newPassword) {
  const row = await db.findResetByHash(sha256(token));
  if (!row) return fail();
  if (row.usedAt) return fail();                    // already consumed
  if (row.expiresAt < Date.now()) return fail();    // expired

  await db.markResetUsed(row.id);                   // consume first
  await db.updatePassword(row.userId, hashPassword(newPassword));
  await db.invalidateAllSessions(row.userId);       // drop every existing session
  await db.invalidateOtherResetTokens(row.userId);  // clean up any other live tokens
  await notifyPasswordChanged(row.userId);          // tell the account owner
  return ok();
}
  • Storing the token in the database in the clear hands anyone who can read that store an immediate account takeover primitive. Hash it for the same reason you hash passwords
  • Carrying the token in a URL query is common, and it creates four side channels at once: server access logs, proxy logs, browser history, and the referrer
  • Without rate limiting on the request itself, the endpoint becomes a channel for enumeration and bulk attempts. CWE-640 names a lack of throttling on reset attempts as one of the flaw shapes
  • «That email is not registered» is a helpful message and also a direct answer about whether an account exists. You need wording that helps without answering that question
  • Leaving old sessions alive after a reset achieves half the purpose of the reset. That is particularly true when the reason for resetting was a suspicion that somebody else is already inside

Which assumption - ②. «The attacker cannot guess» is this section's assumption. Clocks, counters and general-purpose random functions are all materials that lean on it.

6. The real reason eval() is banned - when parsing a number becomes code execution

«eval() is bad» is widely repeated, and the reason is often remembered as «because it is slow». The actual reason is different. The MDN eval() page classifies the function as an injection sink: the argument passed to it is dynamically parsed and executed as JavaScript, and such APIs are potentially a vector for cross-site scripting attacks. Under the heading «Never use direct eval()», the same page states the first reason as «eval() executes the code it is passed with the privileges of the caller.»

A line written to turn a string into a number becomes an arbitrary code execution point, depending on what the string contains. That code can do anything a logged-in user's screen can do.

// Vulnerable: using eval to turn input into a number.
//             If the input is not a number, its contents run as code.
const qty = eval(document.getElementById('qty').value);

// Vulnerable: a server-provided string is trusted as data and evaluated as code.
const data = eval('(' + responseText + ')');

// Vulnerable: passing a string to setTimeout triggers the same evaluation internally.
setTimeout('refreshPanel(' + panelId + ')', 1000);

// Safe: turn numbers into numbers.
const raw = document.getElementById('qty').value;
const qty = Number.parseInt(raw, 10);
if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
  return showError('Quantity is not valid');
}

// Safe: read JSON with a JSON parser.
const data = JSON.parse(responseText);

// Safe: pass a function as a callback.
setTimeout(() => refreshPanel(panelId), 1000);

The same reasoning rules out assembling a string to reach a property by name. The alternative given on the MDN eval() page is bracket notation: write obj[name] rather than eval('obj.' + name). Where the name originates from a user, pair that with validating the name against an allowlist.

6.1 How CSP addresses this

The MDN Content-Security-Policy page describes unsafe-eval like this: «by default, if a CSP contains a default-src or a script-src directive, then JavaScript functions which evaluate their arguments as JavaScript are disabled. This includes eval(), the code argument to setTimeout(), or the Function() constructor.» It then notes that the unsafe-eval keyword undoes that protection, and warns: «developers should avoid 'unsafe-eval', because it defeats much of the purpose of having a CSP.»

  • Removing eval() from the code and removing unsafe-eval from the policy have an order. Tighten the policy while the calls remain and functionality breaks
  • Even where you never call it directly, a third-party library may evaluate strings internally. Tightening the policy is what surfaces those points, as console errors
  • The MDN eval() page describes reducing the risk by passing trusted type objects instead of strings and enforcing that with the require-trusted-types-for CSP directive
  • The server side has sinks of the same kind. Any point that assembles a string and evaluates it as code or as a query has the same property, in any language

Which assumption - ①. «This string is a number we produced» is the assumption here. If the string came from an input field, a URL or a response body, its contents are decided on the client side.

7. Building HTML by string concatenation - encoding per context

The most common misconception about output encoding is that one escaping function, applied everywhere, is enough. The OWASP Cross Site Scripting Prevention Cheat Sheet disagrees: «using the wrong encoding method may introduce weaknesses or harm the functionality of your application.» Change the place the value lands and the encoding it needs changes with it.

The unit of output escaping is not the value but the position the value lands in. The same value requires different encoding in HTML body, attribute, JavaScript, URL and CSS contexts.

img.setAttribute('src', imgPath);
img.setAttribute('alt', 'profile');

The OWASP Cross Site Scripting Prevention Cheat Sheet enumerates the safe sinks separately: elem.textContent, elem.insertAdjacentText(), elem.setAttribute(safeName, value), formfield.value and document.createTextNode(). The instruction is direct: «try to refactor your code to remove references to unsafe sinks like innerHTML, and instead use textContent or value.» Only when the HTML structure itself has to come from a user value do you route it through a vetted HTML sanitizer.

// Vulnerable: an unvalidated URL placed into a link attribute.
//             Without scheme control, the value can become something that runs on click.
a.href = profile.website;

// Safe: filter by a scheme allowlist first.
function safeHttpUrl(raw) {
  let u;
  try { u = new URL(raw, location.origin); } catch { return null; }
  return (u.protocol === 'https:' || u.protocol === 'http:') ? u.href : null;
}
const href = safeHttpUrl(profile.website);
if (href) { a.href = href; } else { a.removeAttribute('href'); }
  • Even a value the server escaped is mis-encoded if the client then feeds it back through innerHTML. The OWASP Cross Site Scripting Prevention Cheat Sheet notes that server-side encoding is not effective against DOM-based flaws
  • A template engine's automatic escaping generally targets the HTML body context. Putting the same value inside a script block or an href needs separate handling
  • Quoting attribute values alone shrinks the set of characters that must be encoded. The same document calls this out explicitly
  • «This value came from our database, so it is safe» does not hold. Whatever put the value in the database was, usually, also a client
  • Escaping on write means encoding without knowing the display context. Escape at output time, in the manner that position requires

Which assumption - ①. «This value is one we control» is the assumption here. When the content can be decided on the client, what you control is not the value but the position you place it in.

8. Why the client must not compute the price - defining the trust boundary

Order screens tend to grow one particular structure. Selecting options updates the amount on screen, and pressing pay puts the displayed total into the request. The value the user sees and the value that is processed agree, which feels right.

// Vulnerable: every input to the amount calculation is read from the DOM.
function buildOrder() {
  const unit  = Number(document.querySelector('#unit-price').dataset.price);
  const qty   = Number(document.querySelector('#qty').value);
  const disc  = Number(document.querySelector('#discount').dataset.rate);
  const total = Math.round(unit * qty * (1 - disc));

  return { itemId: currentItemId, qty, unitPrice: unit, discount: disc, total };
}

// Server: stores what it received, as received.
function createOrder(req, res) {
  const o = req.body;
  db.insertOrder({ itemId: o.itemId, qty: o.qty, total: o.total });  // no recalculation
  res.json({ ok: true });
}

In this structure the amount the server stores is not the amount the server computed but the amount the request reported. unitPrice, discount and total all arrived from the client, and there is no code on the server confirming that they match its own pricing policy. The only basis is a belief that the screen computed it, so it must be right.

// Safe: the client sends what is being bought. The server produces the amount.
function buildOrder() {
  return {
    itemId:    currentItemId,
    optionIds: selectedOptionIds,        // the chosen option IDs
    qty:       Number(document.querySelector('#qty').value),
    displayedTotal: shownTotal           // shown price, for comparison, never as the basis
  };
}

// Server: recomputes from its own price table.
function createOrder(req, res) {
  const uid = req.session.userId;
  if (!uid) return res.status(401).end();

  const qty = Number.parseInt(req.body.qty, 10);
  if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
    return res.status(400).json({ error: 'INVALID_QTY' });
  }

  const item    = db.findSellableItem(req.body.itemId);          // and that it is sellable
  if (!item) return res.status(400).json({ error: 'INVALID_ITEM' });

  const options = db.findOptionsOf(item.id, req.body.optionIds); // and that they belong to it
  if (options.length !== req.body.optionIds.length) {
    return res.status(400).json({ error: 'INVALID_OPTION' });
  }

  const rate  = pricing.discountRateFor(uid, item);              // the server decides
  const total = pricing.total(item, options, qty, rate);         // the server computes

  if (req.body.displayedTotal !== total) {                       // if the shown price differs
    return res.status(409).json({ error: 'PRICE_CHANGED', total });  // ask for confirmation
  }

  db.insertOrder({ itemId: item.id, qty, total, userId: uid });
  res.json({ ok: true, total });
}

8.1 What a trust boundary is

The standard definition sits in CWE. Per the explanation in CWE-501 Trust Boundary Violation, a trust boundary can be thought of as a line drawn through a program: on one side of the line data is untrusted, and on the other side data is assumed to be trustworthy. The same document defines the purpose of validation logic as enabling data to safely cross the trust boundary, moving from untrusted to trusted.

This article narrows that definition to web applications. On the web the trust boundary sits between the browser and the server. Every value produced on the browser side is on the untrusted side; the moment such a value crosses the network and reaches the server is the moment it crosses the boundary; and data that crosses the boundary is, without exception, subject to validation. The values drawn on screen, the results a script computed and the fields packed into the request are all outside the boundary.

The client sends intent and the server produces the result. «This item, these options, this many» is intent; «therefore this amount» is a result, and a result can only be produced on the inner side of the boundary.

Three working rules follow from that definition.

  1. The client sends intent; the server produces the result. Amounts, privileges and state transitions all belong to the result
  2. Removed from the screen is not removed. Hiding a button and marking a field read-only is a usability improvement, not a control. The control belongs where the request is processed
  3. Client validation is guidance; server validation is control. Both are needed, but their roles differ. A field validated only on the client is an unvalidated field

Three questions are enough to classify any value at the boundary.

  • Is this a value the server produced, or a value the request brought?
  • If the request brought it, does the server confirm its valid range against its own data?
  • If it does, does it do so on every entry path?
  • This is not only about money. Privilege level, seller identifier, shipping cost, points applied, coupon eligibility - any value that server policy should decide that appears in the request body has the same shape
  • State transitions too. Whether «mark as delivered» is a permitted transition is decided by the server's state machine, not the screen
  • Even with server recalculation, the absence of a comparison against the shown price creates user confusion. The example above returns 409 not for security reasons but to prevent the displayed price and the charged price from diverging
  • Where there are several entry paths - a mobile app, an external integration - the recalculation logic has to live in a shared layer. Duplicated per path, it becomes the problem in the next section

Which assumption - ①. This is its purest form. In the sentence «the screen computed it, so it is right», the thing doing the computing is the client.

9. Asymmetry inside one codebase - an inconsistent control is no control

Open a real codebase and a clean split between «has the control» and «lacks it» is rare. Far more common is present on some endpoints and absent on others. The screen built recently has token validation; the admin screen built years ago does not. The list query checks ownership; the download does not.

// Vulnerable: applied per route. Forget to attach it and the route is simply open.
app.post('/api/items/create', requireCsrf, requireAuth, createItem);
app.post('/api/items/update', requireCsrf, requireAuth, updateItem);
app.post('/api/items/delete',              requireAuth, deleteItem);  // missing
app.post('/api/admin/purge',                            purgeItems);  // both missing

// Safe: deny by default, then state the exceptions.
//       Add a new route and do nothing, and it is protected.
const CSRF_EXEMPT = new Set([
  'POST /api/webhooks/inbound'   // only routes that use no session cookie; note the reason
]);

app.use((req, res, next) => {
  if (SAFE_METHODS.has(req.method)) return next();
  if (CSRF_EXEMPT.has(req.method + ' ' + req.path)) return next();
  return requireCsrf(req, res, next);
});
app.use(requireAuth);   // same shape for authentication, with public routes as exceptions

The effectiveness of a control is set by its minimum, not its average, because the defending side has to hold every path while the other side needs one.

  • Asymmetry usually comes from time. Code written before the control was introduced lacks it; code written after has it. The introduction date splits the codebase into two strata
  • It also comes from people. Knowing the same rule does not produce the same habit. When a rule lives only in a document and is not enforced by code, the variance stays
  • The «internal only, so it is fine» exception survives longest. Admin screens, batch endpoints and temporary diagnostic routes are where it lives
  • The direction of the fix is to invert opt-in into opt-out. Instead of attaching the control per route, apply it globally and enumerate exceptions. Then forgetting means being protected
  • The exception list has to live in code to be reviewable. In a config file or a document, changes bypass review
  • The same principle applies to output encoding. A template setup that escapes by default and marks exceptions explicitly has less variance than one that calls a function at each position

Which assumption - both ① and ②. The very existence of the control ends up depending on which path the client arrives through. At that moment another ① is created: «we decide which path they come in by».

10. What does this log prove - non-repudiation

Everything so far has broadly been about what to block. This section asks a different question. When something was not blocked, what can the surviving record actually say?

Non-repudiation is, per the definition the NIST glossary cites from SP 800-53 Rev. 5, protection against an individual who falsely denies having performed a certain action, providing the capability to determine whether an individual took a certain action, such as creating information, sending a message, approving information, or receiving a message. CNSSI 4009-2015, also cited in the same glossary, says the same in substance, and NISTIR 4734 puts it shorter still: «the inability to deny responsibility for performing a specific act.»

Split the definition in two and the practical meaning appears. The first half is protection against denial. The second half is the capability to determine whether an individual took the action. Without the second half the first does not exist.

The evidential weight of a log holds only to the degree the identification controls are sound. «User X deleted this» is a completely different sentence depending on where that X came from.

A user identifier written in a log line does not by itself mean that user performed the action. The meaning of the sentence depends on where that identifier came from.

The reason to press further on the third row is session fixation. Session fixation is, per the definition in the OWASP Session Management Cheat Sheet, an attack in which the attacker sets the session ID on the victim user's web browser instead of gathering the victim's session ID. The same document states the remedy as mandatory: «the session ID must be renewed or regenerated by the web application after any privilege level change within the associated user session», and «the session ID regeneration is mandatory to prevent session fixation attacks». Privilege level change includes the login moment, when the user goes from unauthenticated to authenticated.

// Vulnerable: the session identifier is unchanged by login.
//             A value created before authentication stays valid after it.
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();
  req.session.userId = user.id;                // only fills in a field
  res.json({ ok: true });
}

// Safe: mint a new session identifier at the moment authentication succeeds.
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();

  regenerateSessionId(req, () => {             // the previous identifier is discarded
    req.session.userId = user.id;
    req.session.authAt = Date.now();
    res.json({ ok: true });
  });
}

The fourth row is the point most often skipped. Without a CSRF defense, even «a request went out under X's session» does not mean X intended it. CSRF is by definition an attack in which a request occurs without the user's intent. The definition in the OWASP Cross-Site Request Forgery Prevention Cheat Sheet carries that conclusion: an authenticated user's browser is tricked into performing an unwanted action. The session was genuine and the request really did leave that browser, but the party who decided to perform the action was not the user.

10.2 What to record and what not to

The OWASP Logging Cheat Sheet organises what to record around when, where, who and what. Under who the fields are «source address, e.g. user's device or machine identifier, user's IP address» and «user identity (if authenticated or otherwise known)». The conditional in the parentheses is this whole section in miniature: only if known.

The same document is careful about the relationship between logs and non-repudiation. Logs support «non-repudiation controls (note that the trait non-repudiation is hard to achieve for logs because their trustworthiness is often just based on the logging party being audited properly)». Treating a log as evidence therefore requires the integrity of the log first, which is why the same document asks you to «build in tamper detection so you know if a record has been modified or deleted» and to «store or copy log data to read-only media as soon as possible».

// Vulnerable: the actor is taken from the request body. The log copies the claim.
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  logger.info('record deleted', {
    actor:    req.body.userId,        // a value the client chose
    recordId: req.body.recordId
  });
  res.status(200).end();
}

// Safe: the actor comes only from the server session, with the basis recorded alongside.
function deleteRecord(req, res) {
  const actor = req.session.userId;                   // a value the server knows
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);
  if (!rec) return res.status(404).end();             // ownership check

  removeRecord(rec.id);
  logger.info('record deleted', {
    at:          new Date().toISOString(),            // when
    service:     SERVICE_ID,                          // where
    actor:       actor,                               // who, per the session
    sessionRef:  hash(req.sessionID),                 // never the raw session value
    sourceIp:    req.ip,
    userAgent:   req.get('user-agent'),
    action:      'record.delete',                     // what
    target:      rec.id,
    outcome:     'success',
    csrfChecked: true,                                // which checks it passed
    authMethod:  req.session.authMethod
  });
  res.status(200).end();
}

What must not be recorded is stated as well. The OWASP Logging Cheat Sheet lists authentication passwords, session identification values (a hashed replacement may be used), access tokens, encryption keys and other primary secrets, bank account or payment card holder data, and sensitive personal data. That is why the example above logs a hash rather than the session ID. Events from one session can still be grouped, while anyone who can read the log cannot reuse the session.

10.3 Who this control is for

Put together: in a system where non-repudiation has broken down, the logs cannot identify the actor. That is not a sentence about whose fault anything is. It is a technical statement about what is and is not possible in that state. When identification comes from the client, the who in a log is a claim; without origin verification, even a session-based who does not imply intent; and without session regeneration, the attribution of the session itself is unstable.

  • This is protection for users. When an action they did not take is recorded against their account, the limits of that record need to be explainable in technical terms
  • It is equally protection for operators. Being able to attribute responsibility accurately is what keeps an operator out of disputes with no basis. The party that knows what its own logs prove and do not prove is in the stronger position
  • So the control in this section differs in character from «controls that prevent incidents». It is a control that decides in advance what you will be able to say when something happens
  • The order for raising evidential weight matches the earlier sections: server session identification, then session regeneration, then origin verification, then log integrity. Start at the end and the earlier items stay open
  • Time is part of that weight too. The OWASP Logging Cheat Sheet asks for log date and time in an international format. If clocks drift between servers, the sequence of events cannot be reconstructed

Which assumption - both ① and ②. When identification leans on ①, the who degrades into a claim; when the session value leans on ②, that who may be somebody else.

11. CSP and SRI - the last line

If the earlier sections were about where to draw the boundary, this one is about how far to contain the damage once the boundary is crossed. The order matters: this layer does not substitute for the controls above it.

CSP is, per the definition on the MDN Content-Security-Policy page, an HTTP response header that allows website administrators to control the resources the user agent is allowed to load for a given page, and it helps guard against cross-site scripting attacks. The same page writes about inline scripts: «by default, if a CSP contains a default-src or a script-src directive, then inline JavaScript is not allowed to execute. This includes inline <script> tags, inline event handler attributes, and javascript: URLs.» The unsafe-inline keyword undoes that protection, and the same page warns: «developers should avoid 'unsafe-inline', because it defeats much of the purpose of having a CSP.»

The existence of a policy and what the policy blocks are separate questions. A policy containing unsafe-inline and unsafe-eval is a state in which the header is present while the protection is largely gone.

# Vulnerable: a policy exists, but two keywords undo the protection.
Content-Security-Policy: default-src *; script-src * 'unsafe-inline' 'unsafe-eval'

# Safe: issue a fresh nonce per request and run only scripts carrying it.
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';

# Rollout stage: collect violation reports first to see what would break.
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST';
  report-to csp-endpoint
  • The nonce must be issued fresh per request. A fixed nonce is not far from having no policy
  • The MDN Content-Security-Policy page notes that if a directive contains a nonce or a hash, the browser ignores unsafe-inline. That is why both can be listed together for older-browser compatibility
  • Per the same page, the hash algorithm identifier must be one of sha256, sha384 or sha512
  • strict-dynamic extends the trust conferred by a nonce or hash to scripts that the trusted script loads dynamically. When it is present, host sources, scheme sources, 'self' and 'unsafe-inline' are all ignored
  • frame-ancestors restricts which parents may embed the page with <iframe> and similar. It is the modern form of clickjacking defense
  • Start with Content-Security-Policy-Report-Only. The same page describes it as the approach used during testing to report violations without blocking code from executing

11.1 What SRI blocks and what it does not

Subresource integrity is, per the definition on the MDN Subresource Integrity page, a security feature that enables browsers to verify that resources they fetch are delivered without unexpected manipulation, and it works by letting you provide a cryptographic hash that a fetched resource must match. The same page frames the threat as a supply chain attack, specifically an attacker who gains control of a third-party host and injects malicious content into its files or replaces them outright. The mechanism is simple: the browser computes the hash of what it received and compares it with the specified values, and if it matches it loads the resource, otherwise it refuses to load it and returns a network error.

<!-- Vulnerable: a script from an external host runs with no verification.
     If that file changes, the changed code runs inside our page. -->
<script src="https://cdn.example.com/widget.js"></script>

<!-- Safe: runs only when the hash matches.
     Cross-origin requests using SRI must use CORS, so crossorigin is required. -->
<script src="https://cdn.example.com/widget.js"
        integrity="sha384-PLACEHOLDER_BASE64_HASH_VALUE"
        crossorigin="anonymous"></script>

The same page also explains why crossorigin="anonymous" is needed. Resources load in no-cors mode by default, and if integrity checks were permitted there, an attacker could derive information about a subresource's content by testing hash values. To prevent that information-leakage attack browsers do not allow no-cors requests to use subresource integrity, and a request without crossorigin will always fail.

  • What SRI verifies is only whether the content matches the stated hash. Logic the original author put there from the start matches its hash and passes
  • The hash has to be updated on every version change. If that update is automated so that new hashes are accepted with no review, the check loses much of its value
  • It is impractical for scripts whose content changes constantly. For those, moving to self-hosting is the alternative
  • CSP operates inside the browser only. It has no effect on a missing authorization check, on a checkout that stores a client-supplied amount, or on a predictable reset token
  • Both features are layers that act after the other defenses have failed. Deferring the earlier controls because this layer exists inverts the order

Which assumption - this section fixes neither. CSP and SRI narrow the blast radius once ① and ② have already failed.

12. Why known flaws stay unfixed

Little of what is above is new. The documents cited have been public for a long time and are widely referenced. So one question remains: why do known flaws persist? There is a structure in which things go unfixed even when they are known, and it is separate from ignorance.

  • Turning it on breaks things. Applying CSRF protection globally to an old codebase causes every existing form and async request without a token to be rejected. It is an outage the user sees immediately, and enabling the control becomes an act that carries regression risk
  • The weight of touching working code. The thinner the automated test suite, the heavier this becomes. If you cannot bound the blast radius of a change, fixing looks riskier than leaving
  • Security debt costs nothing visible until an incident. Unlike performance problems or functional defects, it does not show up in any metric while it sits there. An item whose cost reads as zero loses prioritisation meetings
  • Without an owner, intake does not become remediation. A channel for receiving reports can exist while nobody is designated to convert a report into a code change, and then only intake records accumulate. This arises from a gap in role definition
  • Competition with feature work. The same people do both, and only one of the two has a name on the schedule
  • The scope is unknown. Open the code to fix one instance, find the same pattern in an uncountable number of places, and starting gets postponed. This item leads directly into the next section

That this structure shows up in outcomes is visible in public data. In a mid-year summary published on 30 June 2022, Project Zero wrote: «as of June 15, 2022, there have been 18 0-days detected and disclosed as exploited in-the-wild in 2022.» And: «at least nine of the 0-days are variants of previously patched vulnerabilities.» The conclusion of that post reads: «at least half of the 0-days we have seen in the first six months of 2022 could have been prevented with more comprehensive patching and regression tests.» On how quickly variants return, it adds: «four of the 2022 0-days are variants of 2021 in-the-wild 0-days. Just 12 months from the original in-the-wild 0-day being patched, attackers came back with a variant of the original bug.»

Why deadlines exist at all can be read in the same light. The Project Zero Vulnerability Disclosure Policy gives a vendor 90 days after notification to make a patch available to users, and publicly discloses details 30 days after the patch has been made available. Where a patch is not possible in 90 days but is possible within an additional 14, a grace period may be granted; where there is evidence of active exploitation in the wild, a 7-day policy replaces the 90-day policy, with a 3-day grace period.

The fact that deadlines were written down at all encodes an empirical judgement: without one, fixes are delayed.

13. Fixed on paper, unchanged in practice - incomplete patches

Sometimes a fix is made and the same path survives it. The problem comes from how the scope of the fix gets decided, and there are roughly four shapes.

  1. Treating the symptom, leaving the cause. A value is confirmed to render unescaped on one screen, so escaping is added on that screen. Other screens rendering the same value, and other responses carrying the same field, go untouched
  2. No variant analysis. Nobody counts how many more instances of the pattern exist in the codebase. Fix the one reported and the rest remain, and the rest become the next report
  3. Fixing the client and leaving the server. Hide the button, make the field read-only, add screen-side validation. The code that processes the request is unchanged
  4. Closing one route while another stays open. A field is removed from one response, while another endpoint, an error message, a cached response or a download carries the same information

From the trust boundary perspective, a client-side fix is not a defense. Removing a button from a screen makes the request harder to send; it does not reject the request when it arrives.

// Before: a delete request is processed even for an unauthorised user.
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  res.status(200).end();
}

// Incomplete fix: the button was hidden on the screen.
// The server code above is unchanged. The boundary is where it was.
if (!currentUser.isOwner) {
  document.querySelector('#delete-btn').style.display = 'none';
  document.querySelector('#delete-btn').disabled = true;
}

// Complete fix: the decision is made where the request is processed.
function deleteRecord(req, res) {
  const actor = req.session.userId;
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);   // ownership check
  if (!rec) return res.status(404).end();

  removeRecord(rec.id);
  res.status(200).end();
}
// Keeping the hidden button is fine. It is usability, not a control.

For the second shape, the figures cited in the previous section serve directly as evidence. That Project Zero recorded at least nine of eighteen in the first half of 2022 as variants of previously patched vulnerabilities and concluded that at least half could have been prevented with more comprehensive patching and regression tests shows this is a recurring pattern rather than an exceptional case. It is why searching the whole codebase for the same pattern and counting the instances belongs inside the fix, not after it.

13.1 The verification gap in the process

Separately from the technical shapes, the same kind of gap appears in the process that confirms a fix. The structure is simple. A finding is received, passed to the party that develops the software, that party replies that it has been fixed, and the case is closed on that reply. This flow has no step that verifies the statement.

  • This is not about whether the reply is truthful. A reply can be entirely sincere and still fall into one of the four shapes above. Concluding that the fix is complete while a variant remains is the most common case
  • Without re-verification, closure is not a state; it is the end of a procedure. Yet a closed marker creates the impression that things are now safe. An item that has left the list is no longer in anybody's queue
  • Re-verification usually costs less than the original confirmation, because you already know where to look. Even so, if the process has no step for it, it is not performed
  • Verification has to look at two places: the reported instance and other instances of the same pattern. Look only at the first and the second shape passes straight through

One more distinction is worth drawing. An acknowledgement is not evidence of a fix. Being listed on a security acknowledgements page or a contributors list is evidence of receipt and awareness. It records that the flaw became known, not that the flaw was removed. There is an asymmetry underneath. Awareness costs almost nothing; fixing costs something. So awareness is marked quickly and remediation proceeds slowly. Read the two indicators as the same thing and you will estimate the real state as better than it is.

Which assumption - ①. The third shape is exactly ①. A fix that changes the screen leaves «the client cannot be changed» in place and adds one more layer on top of it.

14. How to review your own site in thirty minutes

This section applies only to a site you operate or have explicit authorisation for. Reviewing somebody else's service without permission can create legal problems. Everything below stays at the level of reading your own site's responses in browser developer tools. Nothing here involves manipulating requests or repeating attempts.

What these thirty minutes answer is not a list of flaws but the question «which assumption is our system currently standing on?»

14.1 Five minutes - cookie attributes

Open Cookies under the Application (or Storage) tab in developer tools. On the session cookie row there are four things to look at.

  • Is the HttpOnly column marked? If not, a script can read the value
  • Is the Secure column marked?
  • What is in the SameSite column? Empty means it is left to a browser default. None means you should be able to explain why that cookie has to travel cross-site
  • Is the session cookie's value human-readable? A user number, an email address or a role name visible there is the state described in section 4

14.2 Ten minutes - response headers

In the Network tab, select the document request (the top-level HTML response) and read Response Headers.

  • Is Content-Security-Policy present? If not, the layer from section 11 is simply absent
  • If present, does it contain 'unsafe-inline' or 'unsafe-eval'? That is the state MDN warns about
  • Do the attributes on the Set-Cookie lines match what you saw in 14.1? Different cookies being set with different attributes is common
  • Does the session cookie value change across login? This is where you can see with your own eyes whether the session regeneration from section 10 is happening

14.3 Ten minutes - external scripts

Count where the page fetches code from. Below is a read-only snippet to run in the console on your own site. It changes nothing and only prints a list.

// Read-only: list scripts from external hosts that carry no integrity attribute.
[...document.querySelectorAll('script[src]')]
  .filter(s => new URL(s.src, location.href).origin !== location.origin)
  .map(s => ({
    src:       s.src,
    integrity: s.integrity || '(none)',
    crossorigin: s.crossOrigin || '(none)'
  }))
  .forEach(row => console.log(row));

// Read-only: check whether a CSP is applied through a meta tag.
console.log(
  document.querySelector('meta[http-equiv="Content-Security-Policy"]')?.content
  ?? '(no meta CSP - check the response headers instead)'
);
  • If the list of external hosts is longer than you expected, each of them is a party that can execute code inside your page
  • Entries without integrity will run whatever that file becomes if it changes
  • Where content changes too often for SRI to apply, put moving it to self-hosting on the list of things to evaluate

14.4 Five minutes - the shape of a reset token

Request a password reset for your own account and open the link. What matters is the token's shape and its lifetime.

  • Is it long enough, and what character set does it use? If it is a hexadecimal string, does it exceed the minimum length implied in section 5?
  • Request twice in a row - is there visible regularity between the two values? If the leading portion is identical or only the tail shifts slightly, a clock or a counter may be part of the recipe
  • What happens if you open an already-used link again? If the reset screen simply appears, single-use handling is absent
  • After completing the reset, does an existing login left open in another browser stay signed in?
  • Is the response to a reset request for a non-existent address the same as for an existing one?

Which assumption - ① and ②. If any of the four items leans on conditions on the client side, that point is ①; if the reset token shows regularity, that point is ②.

What could not be confirmed

What follows was left out of the body. Where the basis could not be confirmed, it was not included.

  • A concrete expiry time for reset tokens. The OWASP Forgot Password Cheat Sheet requires invalidation after use but gives no concrete figure in minutes or hours. That is why the body says only «a short expiry»
  • A shortened deadline for incomplete fixes. The Project Zero Vulnerability Disclosure Policy and Vulnerability Disclosure FAQ contain no separate shortened-deadline clause for incomplete fixes. What is verifiable is the 90-day deadline, disclosure 30 days after a patch, the 14-day grace period, and the 7-day deadline with a 3-day grace period for in-the-wild exploitation. What can be cited about incomplete fixes is not policy but the counts on variant re-exploitation
  • Per-browser SameSite default status. The MDN Set-Cookie page says only that «some browsers use Lax as the default». Which browser applies what from which version has to be checked against your own target environment
  • Industry-wide median patch delay and unpatched rates. Public sources differ in sample and definition, so no single figure is cited. The numbers used in sections 12 and 13 are those Project Zero published for its own tracked set, and do not generalise beyond that scope
  • An official list of what SRI does not protect against. The MDN Subresource Integrity page does not explicitly enumerate what SRI fails to cover. The limits described in the body extend only as far as follows from the definition of how SRI operates
  • A NIST glossary entry for trust boundary. No such entry could be located in the NIST glossary. The standard definition in section 8 therefore cites the explanation in CWE-501, and the web-specific narrowing is stated as this article's working definition
  • The code examples in this article. They are written for explanation and were not verified in any particular runtime. Function names and paths are all invented, and in practice it is better to use the facilities your own framework provides

Frequently asked questions

Q1. The user number is visible in my cookie - is that a problem?

A cookie is issued by the server but stored by the client. The value can be edited in developer tools and sent back, so if any server code queries data using that number, the relationship between the owner of the result and the requester is left unverified. The OWASP Insecure Direct Object Reference Prevention Cheat Sheet describes this flaw as requiring three components: an object, a reference to that object, and a missing object-level authorization check. The OWASP Session Management Cheat Sheet requires that the session ID content be meaningless to prevent information disclosure and that it never include sensitive information or personally identifiable information, and it states that session identifiers must have at least 64 bits of entropy to resist brute-force guessing. Two changes follow. First, keep only a meaningless session identifier in the cookie and have the server look up the identity from it. Second, put the ownership condition into the query itself so the code only ever finds what belongs to the current user. Switching to identifiers that are hard to guess is not a substitute. The same OWASP document states that even with complex identifiers, access control checks are essential.

Q2. If I switch SameSite to Strict, can I drop the CSRF token?

The OWASP Cross-Site Request Forgery Prevention Cheat Sheet states that SameSite should be treated as a defense-in-depth layer rather than relied on alone, and it gives three reasons. First, Lax only blocks unsafe methods, so a state-changing action reachable over GET passes straight through. Second, the scope of SameSite is the registrable domain rather than the origin, so a different host under the same domain counts as same-site. Third, defaults differ between browsers. The MDN Set-Cookie page says only that some browsers use Lax as the default when SameSite is not specified, and explains that the Lax applied as a default is a more permissive version in which cookies are also included in POST requests as long as they were set no more than two minutes before. Strict resolves much of the first and third points, but the second remains. So even with Strict on the session cookie, the recommended configuration keeps a synchronizer token or a signed double-submit token on state-changing requests.

Q3. I set HttpOnly, so why is XSS still described as a problem?

HttpOnly blocks exactly one thing: a script reading that cookie value through document.cookie. The MDN Set-Cookie page states that a cookie created with HttpOnly is still sent with JavaScript-initiated requests. So if code is executing inside the page, it does not need to read the cookie at all; it can simply issue requests that carry it. Using the value replaces stealing the value. For the same reason the OWASP Cross-Site Request Forgery Prevention Cheat Sheet emphasises that cross-site scripting can defeat all CSRF mitigation techniques. Code running inside the page holds the same privileges as the legitimate screen, so it can read a token out of the DOM and attach it to a request. In short, HttpOnly is a worthwhile control that narrows one exfiltration path, and the remedy for XSS itself is output encoding. The OWASP Cross Site Scripting Prevention Cheat Sheet recommends refactoring code to remove references to unsafe sinks such as innerHTML and using textContent or value instead.

Q4. My password reset link still opens after it has been used - is that all right?

The OWASP Forgot Password Cheat Sheet states that reset tokens must be invalidated after they have been used. If a link that was already used opens the reset screen again, that requirement is not implemented. Why it matters comes down to what the token is. While it is valid, a reset token stands in for the authentication credential, and CWE-640 names this flaw Weak Password Recovery Mechanism for Forgotten Password with CWE-1390 Weak Authentication and CWE-287 Improper Authentication as its parents. In other words it is classified as an authentication flaw. The link can persist in a mailbox, in browser history, in server access logs, in proxy logs and in the referrer, so if it remains reusable, each of those residues becomes an account takeover path. Three more things are worth checking together: whether the token has an expiry, whether the store keeps a hash rather than the original value, and what happens to existing login sessions once the reset completes. The same document recommends asking the user whether to invalidate all existing sessions, or invalidating them automatically.

Q5. If a user ID appears in the log, can I conclude that person did it?

It depends on where that ID came from. If the value arrived in the request body or in a cookie the client can modify, what the record means extends only as far as the request having claimed to be that user. If the value came from a server session lookup, it extends as far as the session having belonged to that user. Two more things are needed from there. The OWASP Session Management Cheat Sheet defines session fixation as an attacker setting the session ID on the victim's browser rather than obtaining the victim's session ID, and states that session ID regeneration is mandatory to prevent session fixation attacks. Without it the attribution of the session itself is unstable. And without a CSRF defense, a genuine session still does not mean the request expressed the user's intent, because CSRF is by definition an attack in which a request occurs without the user intending it. The definition of non-repudiation that the NIST glossary cites from SP 800-53 Rev. 5 includes the capability to determine whether an individual took a certain action. That capability holds only to the degree the identification controls are sound.

Conclusion: the four claims this article makes

Closing with claims rather than a summary. This article argues four things, and each is listed with the sections that support it.

  1. Code that uses a client-supplied value as its basis is unvalidated, whatever that value happens to be. Form values, data- attributes, cookies, request bodies and request headers all fall under this. Support: section 4 (user identifiers in cookies), section 8 (the trust boundary definition and server-side recalculation), section 13 (fixes applied only on the client).
  2. A predictable value is not a secret. Treating a value as secret holds only once the randomness source that produced it has been checked. Support: section 5 (reset tokens, CWE-640, MDN's explicit statement about Math.random()), section 10 (attribution of session values).
  3. Individually low-rated findings create new paths when combined, and item-by-item checklists do not catch those paths. Support: section 3 (a missing CSRF token combined with SameSite=None), section 9 (asymmetry inside one codebase).
  4. In a system where identification controls have broken down, the logs cannot identify the actor. This protects users and operators alike. Support: section 10 (the definition of non-repudiation, what a logged identifier proves by source, and the effect of session fixation and CSRF on evidential weight).
