πFS - 把数据存进圆周率π而非硬盘的文件系统

无数据文件系统的发想、它为何毫无意义，以及这个玩笑所教的严肃信息论

2026-06-12 IT/技术

引言：一个不保存数据的文件系统的玩笑

2026年6月在news.hada.io再次成为热门话题的题目之一，便是πFS（圆周率文件系统）。它的提议令人心动：不要把你的文件写入硬盘，而只记录该文件在圆周率π的数字中某处已经出现的位置（偏移量）。数据本身无需保存在任何地方，因为π是无限的。

初听之下像是天才级的无限压缩——把任何数据都换成一个数，即位置值。但稍加推敲就会发现它行不通。而为何行不通，恰恰是这个玩笑的真正价值。πFS由Philip Langdale创造，是一个被刻意做成毫无用处的文件系统，同时也是一则一次性讲透信息论、数论与压缩极限的教育寓言。

本文不只是介绍。我将通过12个H2讲解：(1) πFS的发想；(2) 运作机制；(3) 什么是正规数；(4) 为何π的正规性仍未被证明；(5) 与无限猴子定理的联系；(6) 偏移量为何大于数据；(7) 检索成本的天文规模；(8) 柯尔莫哥洛夫复杂度；(9) 压缩的信息论极限与鸽笼原理；(10) 类似的玩笑（魔法压缩等）；(11) 开发者的洞见；(12) 结论。我的原则始终是：保留幽默，但把数学事实讲准确。

一句话总结 - πFS把数据换成π中的一个位置，但这个位置值与数据一样大，因此毫无节省。信息不会因为换了表示而消失。

1. πFS的发想 - 所有数据已经在π里

发想的起点是一句话：「如果π是正规数，那么π的无限数字中必然出现一切有限的数字串。」你的照片、电影、小说，任何文件归根结底都是0和1（或0到9）的有限排列。既然如此，这个排列必然会在π的某个位置原样出现。

这一观察本身并不新鲜。「π是无限的，所以我的生日、甚至莎士比亚全集都在里面」的说法早已流传。πFS的巧妙在于，它把这一观察当真（以玩笑口吻）实现为一个文件系统设计：不存数据，而存数据的地址——就像不复印整本书，而只记下图书馆的索书号。

问题在这个比喻里已经显现。如果图书馆里真的摆着所有书，索书号就很短。但π这座图书馆是无限的，要从中找到某段数据，索书号（偏移量）就会和数据一样长，甚至更长。πFS的一切玩笑都收敛于这一点。

2. 运作机制 - 偏移量与元数据

真实的πFS实现如何运作？以Philip Langdale的原版为准，流程如下。

  • 分解：把文件拆成字节（或更小的单位）。
  • 检索：对每个单位，找到它在π数字展开（用BBP公式等直接计算位数）中首次出现的位置。
  • 记录：把该位置（偏移量）与文件结构存入真实磁盘上的元数据目录。
  • 还原：读取时根据存下的偏移量重新计算π的相应位数，恢复原始字节。

核心矛盾正在于此。数据本身不写入磁盘，但指向它的元数据却写入磁盘。而这份元数据的体积比原始数据更大。也就是说，「不存数据」的说法只在形式上成立，实际磁盘占用反而增加。连原版README都不主张省空间，而是把这个矛盾当作玩笑的核心。

# 概念性伪代码（说明实际上毫无节省）
file = [0x48, 0x49]              # "HI"，2字节 = 16比特
offset_H = 0x48在π中首次出现的位置   # 天文级别的大整数
offset_I = 0x49在π中首次出现的位置   # 同样是巨大整数
metadata = [offset_H, offset_I] # 两个巨大整数 → 比原文更大
# 结果：为了消去2字节，却要存几十到几百字节的偏移量

3. 什么是正规数（normal number）

要理解πFS的前提，需要正规数的概念。一个实数在某进制（base）下是正规（normal）的，意味着在该进制展开中，每个数字以及任意长度的数字组合都以均匀频率出现。例如在十进制中，0到9各以1/10的频率出现，00到99各以1/100的频率出现。

正规数的一个关键性质是析取性（disjunctive）。在所有进制下都正规的数（绝对正规数）会把一切有限数字串包含为子串。也就是说，若一个数是正规数，「我想要的任何数据都在它某处」便在数学上为真。πFS的前提恰恰就是「π是正规数」。

注意 - 仅仅「无限且不循环（无理数）」并不保证包含一切数列。例如0.1010010001000010...是无理数，却根本没有数字2。「包含一切数列」来自的不是无理性，而是正规性（至少是析取性）。

4. π的正规性尚未被证明

这里要把最重要的事实讲清楚：π是正规数这一点截至2026年仍未被证明，只是推测（conjecture）。

数学家相信π、e、√2这类大多数「自然」的无理数都是正规数，但要证明某个具体数的正规性却异常困难。就π而言，计算到数万亿位的统计与正规性吻合得很好，但无论检验多少有限位数都不构成正规性的证明。更令人震惊的是，连0到9每个数字是否在π中无限次出现都尚未被证明。

因此准确的表述是：「π被推测为正规数，若如此则一切有限数据都会出现在其中——但这个前提本身未被证明。」πFS不仅无法运作，连它得以运作所需的数学前提都还只是假设，处在双重极限之上。这是本文最想强调的更正点。

5. 与无限猴子定理的联系

正规数的直觉与著名的无限猴子定理同根同源：猴子在打字机前无限随机地敲键，几乎必然（almost surely）终会敲出莎士比亚全集。

数学上可这样表述：若从有限字母表中独立且均匀地随机抽取每个字符以构成无限数列，则任何给定的有限字符串几乎必然作为该数列的子串出现。这依赖于一切有限字符串的集合是可数（countable）的事实。它与正规数包含一切数列的性质本质上是同一直觉。

但有一个陷阱：「几乎必然」意味着概率为1，而非迅速或实用。猴子敲出「Hamlet」这六个字母的期望时间，就已远超宇宙年龄。πFS亦然：你的数据「存在」于π中，与你能「找到并使用」它，是完全不同的两个问题。把存在性与实用性混为一谈，正是πFS这个玩笑的精确命门。

6. 偏移量大于数据的原因 - 没有节省

现在定量地看πFS毫无意义的核心原因。结论先行：数据在π中出现的位置（偏移量）几乎总是比数据本身更大。

直觉很简单。把π当作随机数列，长度为N比特的某个特定模式首次出现的位置大约在2的N次方位附近。而表示一个约2^N的位置值又需要约N比特。也就是说，消去N比特数据的代价是新存一个N比特的位置值。净节省为零，甚至更糟。

存储方式数据比特索引/偏移比特实际效果
直接存入磁盘N0基准线
πFS（存偏移量）0约N（或更多）无节省
再把偏移量存进π0需要索引的索引无限递归

最后一行是致命一击。你或许会想「偏移量大，那就把偏移量也用πFS存呗」，但那样就需要索引的索引、索引的索引的索引……永无止境。任何一步信息量都没有减少。这正是信息论所说「没有免费的压缩」的具体形态。

7. 检索成本的天文规模

即便忽略存储空间问题，在π中「找到」想要的数据的成本又是另一堵墙。

确实存在BBP（Bailey–Borwein–Plouffe）公式之类可以直接计算π任意一位的方法。但πFS要做的是反方向：找出给定字节模式在π中首次出现的位置——这是在无限数列中的检索，模式越长，其首次出现的位置就指数级地越远。一旦超过寥寥数字节，检索便在现实中不可能。

因此真实的πFS实现通常一次只找1字节（或更少）并累积偏移量。这降低了检索成本，却把第6节的偏移量爆炸问题正面唤回。降低检索成本则存储成本爆炸，为省存储而拉长模式则检索不可能，这是一个两难权衡——无论走哪条路都是死胡同。正是这种两面夹击，使πFS成为一个「完美无用」的设计。

8. 柯尔莫哥洛夫复杂度 - 数据的本质信息量

为何换成任何表示信息都不会减少？答案是柯尔莫哥洛夫复杂度（Kolmogorov complexity）。

柯尔莫哥洛夫复杂度C(x)定义为输出字符串x的最短程序的长度。这就是数据的「本质信息量」。规律的数据（如「010101…」一万次）由短程序生成，复杂度低；接近随机的数据没有比把自己整段写出来更短的程序，复杂度高。

从πFS的角度看很有意思。「把数据表示为π的偏移量」等于写一个生成它的程序（「从π的第i位起输出k位」）。可那个程序的长度由偏移量i的大小主导，而i如前所见与数据一样大。也就是说，πFS的表示并不能降低数据的柯尔莫哥洛夫复杂度。接近随机的数据无法被任何巧妙表示压缩这一事实，πFS用一条迂回路再次予以确认。

9. 压缩的极限 - 鸽笼原理

「无法造出能缩小所有数据的完美压缩器」这一命题，用鸽笼原理（pigeonhole principle）可以干净地证明。

长度为N比特的字符串共有2^N个。假设某个无损压缩器把它们全部缩短到N比特以下。但比N比特短的不同字符串只有2^N − 1个。把2^N个东西放进2^N−1个鸽笼，必有至少两个落入同一个笼。那么一个压缩结果就对应两个不同的原文，导致无法还原——与无损压缩的定义矛盾。

因此能缩小所有输入的完美无损压缩器在数学上不可能。事实上，长度为N的字符串中能被缩短c比特以上的比例至多为2^(−c)，绝大多数字符串几乎压不动（这类字符串被称为「不可压缩」或柯尔莫哥洛夫随机）。πFS看似违反这一极限，实则只是把信息原封不动搬进偏移量，并未违反。πFS的失败正是压缩极限定理的又一证明。

误解提醒 - 实用压缩器（zip、zstd等）之所以有效，是因为它们处理的是「现实中有结构的数据」，而非「一切数据」。文本、图像、日志充满重复与模式，柯尔莫哥洛夫复杂度低。压缩不是魔法，而是对结构的发现。

10. 类似的玩笑 - 魔法压缩及其同伴

πFS属于「不可能压缩」幽默谱系的一支。还有几个类似的思想实验。

10-1) 魔法/自指压缩

「我的压缩器能把任何文件缩成1字节」之类的主张，用鸽笼原理立刻反驳：1字节（256种）无法区分257个以上的不同文件。「反复应用以实现无限压缩」的变体也犯同样错误，因为信息终究藏在某处（如压缩次数，或解压器本身）。

10-2) 收纳一切书的图书馆（博尔赫斯的巴别图书馆）

在收纳一切可能之书的图书馆里，「找到你想要的书」的成本远超写出这本书的成本。这与πFS的偏移量问题结构完全一致。存在不等于可达。

10-3) 把哈希误当数据

「只存文件的哈希值不就行了？」也是常见误解。哈希是单向的，无法还原原文（且存在碰撞），要反推实际上又需要原文信息。这同样是「没有免费的信息」的变奏。

11. 开发者的洞见

从这个玩笑中，实务开发者应当带走的教训如下。

11-1) 信息不因换表示而消失

把数据搬进索引、哈希、偏移量或另一套坐标系，都不会降低其本质信息量（柯尔莫哥洛夫复杂度）。一旦遇到「它已经在某处，所以只存位置」这类设计，先掂量那个位置值的大小。

11-2) 不要把存在性与实用性混为一谈

「理论上可能」与「现实中可用」是两回事。无限、正规性、概率为1这类数学性质很强大，但若忽略检索成本与时间复杂度，就会得出与实用性相反的结论。

11-3) 压缩是对结构的发现

现实数据之所以可压缩，是因为重复与模式，即较低的柯尔莫哥洛夫复杂度。想提高压缩率就要理解数据结构，靠换表示的把戏越不过极限。

11-4) 认真验证玩笑里的数学

即便像πFS这样「显然是玩笑」的设计，也只有把正规数、鸽笼、柯尔莫哥洛夫这些真数学讲准确，才能真正理解。我推荐的习惯是：遇到貌似成立的主张，先用信息论的守恒律验算一遍。

12. 结论 - 无法运作却完美的思想实验

用一句话总结πFS：「一个刻意无用的文件系统，它成功地把数据变成π中的一个位置，但那个位置和数据一样大，因此什么也省不下。」

然而无用恰是这个项目的价值。πFS一次性教会我们：(1) π的正规性仍是未被证明的假设；(2) 「几乎必然存在」与「实用可用」并不相同；(3) 偏移量与检索的两面夹击使节省不可能；(4) 柯尔莫哥洛夫复杂度与鸽笼原理禁止完美压缩。一行无法运作的代码，压缩了整整一学期的信息论——这倒是真正有效的压缩。

我想留下的讯息是：遇到奇巧的无限存储点子时尽管一笑，但要用信息守恒律验算。压缩与存储不是魔法，而是关于结构与极限的科学。πFS用最有趣的方式，教会我们这一真理。
