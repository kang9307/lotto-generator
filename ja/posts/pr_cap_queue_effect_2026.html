「PRは3件まで」ではレビュー待ちは減らない - 上限ルールとキューの動力学

上限3・5・10・20を900日のキューモデルに掛け、遮断率と待ち時間の裾を実測した

2026-07-31 開発・インフラ

序章: 「3件まで」に変えたのに待ち行列はそのまま

あるリポジトリのレビュー待ちが200件を超えたとしよう。会議で出る結論はたいてい見慣れた形をしている。「1人が同時に開けるのは3件までにしよう。」ルールが入り、1か月が過ぎ、待ち行列の長さはそのままだ。

こうなると反応はふつう二つに分かれる。ルールが緩かったと見て上限をさらに締めるか、こういうルールは元々こんなものだと言って無かったことにするかだ。この記事は三つ目の可能性を扱う。上限を掛けたその地点が、そもそも隘路ではなかった可能性である。

出発点は2026年7月30日にnews.hada.ioに投稿されたトピックだった。見出しはPR件数の制限が実際のキューでは2〜13%しか遮断しないというものだ。私はその報告を書き写す代わりに、同じ問いを自分の手で回してみることにした。特定の製品が内部で何をどう判定しているかは外からは分からないので、この記事は一般的な待ち行列モデルを一つ立て、その内部でのみ語る。以下のすべての数値は「このモデルでは」という但し書きとともに読む必要がある。

結論から書く。遮断率が低く出るのはルールが緩いからではない。待ち行列が長くなるのは到着が多いからではなく処理が遅いからであり、上限は到着の時点を遅らせるだけで処理を速くはしない。だから上限を締めても待ちは減らない。ただし上限が常に無用というわけではない。ある条件下では確かに効く。その条件も数値で特定した。

この記事はPRの開き方やレビューの作法を改めて説明しない。そちらが必要ならPull Requestとコードレビューにまとめてある。ここで扱うのは待ち行列の動力学である。

1. モデル - 何を立てたのか

モデルは意図的に単純にした。そうすればどの数字がどこから出たのかを最後まで追える。

  • 作成者40名がいる。それぞれ作業を作って共用の待ち行列に入れる
  • 新規作業は1日平均9.6件入ってくる。ポアソン分布を使った
  • 誰がその作業を出したかはジップ分布(s=1.0)で引く。少数が多く開く偏りを現実に合わせて作るためだ
  • レビュー側は同時に30件を抱えられ、1件は平均3.0日スロットを占める。幾何分布を使った
  • したがって処理率は1日10.0件(30割る3.0)、利用率は0.96(9.6割る10.0)である
  • 上限は「1人の作成者が同時に開いておける最大件数」と定義した。この地点以外のどこでも働かない
  • 900日回して先頭の300日は予熱として捨てる。残り600日だけを数える
// sim.js - node v22.16.0 / win32. fixed seed, so every number below reproduces.
const SEED = 20260731;

function mulberry32(a) {                        // deterministic PRNG
  return function () {
    a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
function poisson(rng, lambda) {                 // Knuth
  const L = Math.exp(-lambda); let k = 0, p = 1;
  do { k++; p *= rng(); } while (p > L);
  return k - 1;
}
function geom(rng, p) {                         // support 1,2,3,... mean 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

// A       how many authors
// lambda  new items per day          R  concurrent review slots
// S       mean days one review occupies a slot   =>  service rate mu = R / S
// cap     how many items one author may have open at the same time
function simulate({ A = 40, s = 1.0, lambda = 9.6, R = 30, S = 3.0,
                    days = 900, warmup = 300, cap = Infinity,
                    retry = false, seed = SEED }) {
  const rng = mulberry32(seed), cum = zipfCum(A, s), p = 1 / S;
  const open = new Int32Array(A);
  let queue = [], active = [], deferred = [];

  for (let d = 0; d < days; d++) {

    // 1. reviews whose duration has elapsed give their slot back
    const still = [];
    for (const it of active) {
      if (it.endsAt <= d) { open[it.author]--; record(it, d); }
      else still.push(it);
    }
    active = still;

    // 2. today's items, plus anything blocked earlier if retry is on.
    //    author and review duration are drawn HERE and never re-drawn, so
    //    changing cap does not shift the random stream.
    const todays = retry ? deferred.splice(0) : [];
    for (let i = 0, n = poisson(rng, lambda); i < n; i++)
      todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

    // 3. the cap is applied here and nowhere else
    for (const ev of todays) {
      if (open[ev.author] >= cap) {             // blocked
        ev.tries++;
        if (retry) deferred.push(ev);           // comes back tomorrow
        continue;                               // otherwise dropped
      }
      open[ev.author]++;
      ev.opened = d;
      queue.push(ev);
    }

    // 4. free review slots pull from the head of the shared FIFO
    while (active.length < R && queue.length) {
      const it = queue.shift();
      it.started = d;
      it.endsAt = d + it.dur;
      active.push(it);
    }
  }
}

[3, 5, 10, 20, Infinity].forEach(cap => report(simulate({ cap })));

設計で一つ特に気を配った点がある。上限値を変えても到着列とレビュー所要日数がずれないようにしたことだ。作業が作られる瞬間に作成者とレビュー所要日数を一緒に引いておけば、その後に上限がその作業を遮断しようが通そうが乱数の消費量は変わらない。こうしないと上限値ごとに別々の世界を比較することになり、差が上限のせいなのか偶然のせいなのか区別できない。実際に最初の版でこの誤りを犯し、上限を変えるたびに総到着件数が5,645から5,793の間で揺れるのを見て気づいた。

実行環境。以下のすべての出力はWindows 10 Pro (10.0.19045)上でNode.js v22.16.0 (win32)により実際に実行した結果である。乱数生成器はmulberry32で、シードは20260731に固定した。同じシードで回し直せば同じ数字が出る。スクリプトはシェル引数やヒアドキュメントではなくファイルに保存して実行した。

この記事が主張しないこと。このモデルはいかなる製品の実装でもない。特定のサービスがどの条件で何を遮断するのか、上限を誰に適用するのかはここでは扱わない。扱うのは「作成者ごとの同時オープン上限」という形のルールが一般的な待ち行列でどう振る舞うかだけである。

これが低い遮断率の正体である。ルールが緩いのではなく、ルールが届く対象が少ないのだ。全体比で報告するとこの事実が「効果が微々たるもの」と翻訳されるが、正確には「効果の及ぶ母集団が狭い」が正しい。そしてその狭い母集団が処理量のかなりの部分を作っているという点が、後で問題になる。

4. 偏りを極端まで押してみると

ここで自然に出る反論がある。「うちのチームはもっと偏っている」というものだ。ジップ指数を0.4から2.4まで変えて確認した。

偏りを大きくすれば遮断率は確かに上がる。しかし上がる区間を見てほしい。遮断率が30%を超えるには1人が全作業の40%以上を出さなければならない。40名の組織で1人が全体の40%を出すなら、それは待ち行列の設計問題ではなく別の問題だ。現実的な偏りの区間、つまり1位が6〜25%を出す範囲では遮断率は1〜12%に留まる。

そしてp90の列が逆方向に動くのが興味深い。偏りが大きくなるほどp90は3から1へ下がる。仕事が1人に集まるほど残りの大半は0件に留まるからだ。平均的な作成者は上限からさらに遠ざかり、1人だけが毎日ぶつかる。全体の遮断率はその母集団を平均した値なので、「1人が毎日壁にぶつかる状況」と「全員が少しずつ不便な状況」を同じ数字に潰してしまう。上限を論じるとき全体比だけを見てはいけない理由がここにある。

同じ罠を指標の側で扱ったのが複数台のp99を平均する誤りだ。分布の異なる集団を一つの数字に畳むと情報が消えるという点で構造が同じである。

三つの行を並べて見る必要がある。

  • 上限20: 13件が一度でも遮断され、完了は5,699件だ。上限が無いときとまったく同じ数字である。待ち行列はこのルールが存在することに気づかなかった
  • 上限10: 628件が遮断されたのに完了は5,695件だ。基準線と4件差である。ところが開始から完了までの平均が4.05日から3.80日へ良くなった。同じ実行の終端遅延は4.05日から4.06日、つまり事実上そのままだ
  • 上限3: 完了が4,450件に落ち、終端遅延の平均は31.66日になった

上限10の行がこの節の核心だ。開始から完了までの時間は良くなったのに終端遅延は動いていない。上限がしたことは「作業が開いている状態として計算される区間」を短くしただけである。時計の開始ボタンを遅く押したのであって、ゴールが近づいたのではない。ところがほとんどのダッシュボードは開始から完了までを測る。このルールは何も変えずに指標を改善する。

ここにはもっと厄介な含意がある。このモデルで1位の作成者は1日2.34件を作り、レビューは平均3日かかる。上限が3ならこの人が通せる最大値は1日1件だ。必要な速度より上限が低いと、その人の個人待ち行列は永久に伸びる。上限3で完了が22%落ちたのはこのためである。これは「減らした」のではなく「飢えさせた」のだ。

6. キューを支配するのは到着率対処理率だ

では待ち行列の長さを実際に決めるのは何か。上限を外して到着率だけを変えてみた。

見えるキューが1,323件から50件に減ったのに処理量はそのままだ。むしろ29件増えている。減った1,273件は「外側保留」列の1,244件とほぼ正確に対応する。ダッシュボードは劇的に改善され、実際には何も変わっていない。終端遅延の平均が87.9日から37.8日へ良くなったように見えるのも、完了したものだけを数える統計に外側に留め置かれてまだ完了していない1,244件が含まれないからである。

利用率が1を超えた状態で上限は処方ではない。症状を画面の外へ移す装置である。

4行目が重要だ。上限が人の行動を変える効果はこのモデルでは測定できない。このモデルの作成者は上限に掛かっても作業を小さく分けない。ただ翌日に同じものを再試行するだけだ。実際の組織で上限が「一つ終えてから次を開こう」という規律として働くなら、それはこのシミュレーションが捉えられない本物の効果である。ただしその効果を期待して上限を掛けるなら、目的を待ち行列の短縮と書いてはならない。

規則の文書を増やすことと強制点を増やすことが違うという話は長い方針文書だけではエージェントを制御できないで別に扱った。

10. 何を測るべきか

上限値をいくつにするか論争する代わりに以下を測れば論争そのものが消える。

指標定義このモデルの値なぜ測るか
処理率単位時間あたりレビューが終わる件数1日10.0件キュー長を決めるのはこちら側だ
到着率単位時間あたり新たに開く件数1日9.6件処理率を超えるとキューは無限に伸びる
利用率到着率割る処理率0.960.9を超えると待ちが非線形に跳ねる
待ち時間の裾開始から完了までのp90とp998日と13日平均は最悪の事例を隠す
終端遅延準備できた時点から完了まで基準線4.05日、上限3で31.66日上限が押し出した時間も含む
同時オープン分布作成者ごとのp50 / p90 / p990 / 3 / 10上限が届く母集団の大きさを教える
キュー長の推移週単位の傾き利用率1.04で右肩上がり単一のスナップショットでは発散が見えない

チェックリストに移すとこうなる。

  • 上限を論じる前に処理率と利用率を先に測った
  • 作成者ごとの同時オープン数のp90を把握し、上限がその下にあるか確認した
  • キュー長を週単位の傾きで見る。スナップショット1枚で判断しない
  • 待ち時間を平均ではなくp90とp99で見る
  • 開始から完了までと終端遅延を分けて測る。上限は前者だけを良くする
  • 上限に掛かった作業がどこに積み上がるかが見える画面がある
  • 利用率が0.9を超えたら処理能力の増強を先に検討する
  • 上限の目的がキュー短縮なのか集中の強制なのかを文書に書いた

11. このモデルが再現していないもの

モデルの限界を書かなければ上の数値が実際より強く読まれる。再現していないものをそのまま並べる。

  • レビュアーの割り当てと専門領域。ここでは単一の共用先入れ先出しキューだ。特定領域を見られる人が1人しかいないために生じる隘路は再現されていない
  • 優先度と緊急処理。割り込みが無い。実際には急ぎが前へ行き、残りの裾がさらに長くなる
  • レビュー後の修正と再レビュー。手戻りループが無い。これがあると実効処理率が下がり利用率が上がる
  • 作業サイズの違い。全件が同じ分布から所要日数を引く。大きい作業と小さい作業が混ざる効果は無い
  • 上限が人の行動を変える効果。このモデルの作成者は上限に掛かっても作業を小さく分けない。上限の最も説得力のある利点がここから抜けている
  • 長く開いた作業が自ら遅くなる効果。衝突、基準の変化、文脈の喪失が無い。実際には長く開いているほど完了が難しくなる
  • 曜日の周期と休暇。到着と処理がすべての日に同じ分布で起きる

このうち三つ目と五つ目は結論に逆方向へ作用しうる。手戻りループは処理率を下げて上限の必要性を高め、行動変化の効果はこの記事が上限の利得を過小評価する原因になる。だからこの記事の結論は「上限は悪い」ではない。「上限は待ち行列の長さを減らす道具ではなく、その目的で使えば指標だけが良くなる」である。

# 上限ルールとキュー — 何を測り、何を直すか

> 出典: braindetox.kr — 「PRは3件まで」ではレビュー待ちは減らない
> 検証: node v22.16.0 / win32、固定シード 20260731、900日シミュレーション(先頭300日は破棄、600日を計測)
> ここの数値はすべてこのモデルの内部でのみ成立する。特定製品の内部動作についての主張ではない。

## 1. モデルの要約

```
作成者40名 · 新規作業 Poisson(9.6件/日) · 作成者の選択 Zipf(s=1.0)
レビュー側は同時に30件を保持 · 1件あたり Geometric(平均3.0日)
処理率 mu = 30 / 3.0 = 10.0件/日 · 利用率 rho = 9.6 / 10.0 = 0.96
上限(cap) = 1人の作成者が同時に開いておける最大件数
```

## 2. 再現コード(中核ループ)

```js
const SEED = 20260731;

function geom(rng, p) {                  // 台は1,2,3... 平均 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

for (let d = 0; d < days; d++) {
  // 1. 期間が終わったレビューがスロットを返す
  const still = [];
  for (const it of active) {
    if (it.endsAt <= d) { open[it.author]--; record(it, d); }
    else still.push(it);
  }
  active = still;

  // 2. 本日の新規作業。作成者とレビュー所要日数はここで一度だけ引く。
  //    そうすれば cap を変えても乱数列がずれない。
  const todays = retry ? deferred.splice(0) : [];
  for (let i = 0, n = poisson(rng, lambda); i < n; i++)
    todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

  // 3. 上限が働くのはここだけ
  for (const ev of todays) {
    if (open[ev.author] >= cap) {         // 遮断
      ev.tries++;
      if (retry) deferred.push(ev);       // 翌日に再試行
      continue;                           // でなければ破棄
    }
    open[ev.author]++;
    ev.opened = d;
    queue.push(ev);
  }

  // 4. 空いたレビュースロットが共用FIFOの先頭から取り出す
  while (active.length < R && queue.length) {
    const it = queue.shift();
    it.started = d; it.endsAt = d + it.dur;
    active.push(it);
  }
}
```

## 6. 上限が実際に効く条件

| 設定 | p50 オープン | p90 オープン | 上限3の遮断率 | 上限5の遮断率 |
|---|---|---|---|---|
| 40名, rho 0.96 | 0 | 3 | 22.62% | 11.57% |
| 40名, rho 0.80 | 0 | 2 | 18.51% | 8.19% |
| 12名, rho 0.96 | 2 | 8 | 38.32% | 22.10% |
| 6名, rho 0.96 | 4 | 15 | 53.42% | 34.21% |
| 40名, レビュー9日 | 1 | 6 | 45.65% | 32.03% |
| 40名, レビュー18日 | 2 | 10 | 60.55% | 46.83% |

**規則: 上限は作成者ごとの同時オープン数のp90より下にあるときだけ効く。** それより上なら形式にすぎない。

## 7. 上限値を議論する代わりに測るもの

| 指標 | 定義 | なぜ測るか |
|---|---|---|
| 処理率 mu | 単位時間あたりレビューが終わる件数 | キュー長を決める側 |
| 到着率 lambda | 単位時間あたり新たに開く件数 | mu を超えるとキューは無限に伸びる |
| 利用率 rho | lambda / mu | 0.9 を超えると待ちが非線形に跳ねる |
| 待ち時間の裾 | 開始から完了の p90 / p99 | 平均は異常を隠す |
| 終端遅延 | 準備できた時点から完了まで | 上限が押し出した時間も含む |
| 作成者別オープン分布 | p50 / p90 / p99 | 上限が届く母集団の規模 |
| キュー長の推移 | 週単位の傾き | 右肩上がりなら rho が1を超えた |

## 8. 点検リスト

- [ ] 上限を論じる前に**処理率(mu)と利用率(rho)**を測った
- [ ] 作成者別の同時オープン数の**p90**を把握し、上限がその下にあるか確認した
- [ ] キュー長を**週単位の傾き**で見る(単一のスナップショットで判断しない)
- [ ] 待ち時間を**平均ではなく p90 / p99**で見る
- [ ] **開始から完了**と**終端遅延**を別々に測る(上限は前者だけを良く見せる)
- [ ] 遮断された作業が**どこに積み上がるか**が見える
- [ ] 利用率が0.9を超えたら**処理能力の増強**を先に検討する
- [ ] 上限の目的が**キュー短縮**なのか**集中の強制**なのかを文書に書いた

## 9. やってはいけないこと

- キューが長いというだけで上限を掛ける — キュー長は到着ではなく処理が決める
- 遮断率が低いから上限をさらに締める — 低いのはそこが隘路ではないから
- **開始から完了の時間だけを見て改善したと報告する** — 時計の起点が動いただけかもしれない
- 利用率が1を超えた状態で上限で対応する — 見えるキューだけが縮み総量は変わらない
- 上限を少数の多作な作成者への罰として使う — その人が処理量の相当部分を作っている

## 10. このモデルが再現していないもの

- レビュアーの割り当てと専門領域(ここでは単一の共用FIFO)
- 優先度、緊急処理、割り込み
- レビュー後の修正と再レビュー(手戻りループ)
- 作業サイズの違い(全件が同じ分布から所要日数を引く)
- 上限が人の行動を変える効果(小さく分割する、文脈切替が減る)
- 長く開いた案件が自ら遅くなる効果(衝突、基準の変化)
- 曜日の周期と休暇
