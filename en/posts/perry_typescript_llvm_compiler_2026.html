Perry - The Native TypeScript Compiler That Lowers TS Straight to LLVM Machine Code

No Transpile, No JIT - From TypeScript Straight to a Native Binary

Jun 9, 2026 Tech & IT

Introduction: Was TypeScript Really a "Slow Language"?

If you have ever shipped a CLI tool written in TypeScript, you remember a particular friction. Even a program that prints a single greeting has to drag along tens of megabytes of Node.js runtime, and the moment the process starts, the V8 engine wakes up to parse, interpret, and gradually optimize your code. When we say "TypeScript is slow," what is actually slow is not the type system but the execution model. The types are erased once compilation finishes, and the remaining JavaScript is interpreted all over again on top of a large virtual machine.

In June 2026, a project called Perry made the rounds on GeekNews (news.hada.io) by flipping that premise on its head. Perry does not transpile TypeScript to JavaScript, nor does it run on a heavy JIT runtime like V8. Instead, it compiles TypeScript straight to native machine code through LLVM. According to the project, Perry is written in Rust, uses SWC for parsing and LLVM for code generation, and emits a single executable that runs with no Node.js, Electron, or browser engine. This article walks through how it works and why it is technically interesting.

1. The Three-Stage Pipeline of Running TypeScript Today

To understand what Perry solves, we first need an accurate picture of how TypeScript runs today. The traditional path takes roughly three stages.

TypeScript source (.ts)
   │   (1) type check + transpile (tsc / swc / esbuild)
   ▼
JavaScript source (.js)   <- all type information is erased here
   │   (2) parse + bytecode generation (V8 / JavaScriptCore)
   ▼
bytecode interpreter
   │   (3) detect hot code -> JIT compile -> machine code
   ▼
native machine code (produced only while running)

Two costs appear here. First, loss of type information. In stage (1), TypeScript's static types are used only for checking and then completely erased from the emitted JavaScript. As a result, the engine in stages (2) and (3) must start by assuming every value is a "dynamic value of unknown type." Second, JIT warm-up. V8 initially runs slowly through an interpreter, then observes which code runs often and only then compiles it to machine code. Startup is slow, reaching peak speed takes time, and the process itself consumes memory and CPU.

This model is reasonable for an environment like the browser, where the code cannot be known in advance. But a CLI or server that we write and deploy ourselves has all of its code fixed before it ever runs. So why defer optimization to runtime at all? That question is exactly the starting point of AOT compilation.

2. AOT vs JIT - Moving the Moment of Optimization

The difference between JIT (Just-In-Time) and AOT (Ahead-Of-Time) compresses into one sentence: when do you produce the machine code?

Dimension JIT (V8/Node.js) AOT (Perry)
When machine code is made While running (runtime) Before running (build time)
Startup speed Needs warm-up, slow Instant (near 0 ms)
Runtime dependency Engine + runtime required Single binary, none
Source of optimization Types observed at runtime Static types at compile time
Dynamic code (eval) Naturally supported Structurally hard

JIT's strength is that it optimizes by "watching which types actually flow." AOT, by contrast, never sees execution, but in exchange it does not have to care about compile speed. The build happens once and the program runs countless times, so it can apply heavy static analysis and aggressive optimization the way C++ and Rust do. That is precisely Perry's target. TypeScript already carries rich static types, so rather than throwing them away, use them as fuel for compile-time optimization.

JIT says, "I will figure out the types as I run." AOT says, "I already know the types, so I will optimize ahead of time." For a language with explicit types like TypeScript, the latter is a natural option.

3. What Is LLVM, and Why Use It?

Perry's code-generation backend is LLVM. In one sentence, LLVM is an industry-standard compiler foundation that sits between the frontends of many languages and the backends of many CPUs, taking charge of powerful optimization. Clang (C/C++), Rust, and Swift all run on top of LLVM.

The heart of LLVM is an intermediate representation called LLVM IR. A language frontend (TypeScript, in Perry's case) only has to lower its source into LLVM IR; from there, LLVM handles dozens of optimization passes - inlining, constant propagation, loop vectorization, dead-code elimination - and machine-code generation for targets like x86, ARM, and WebAssembly. When you build a new language, you do not have to write an optimizer and code generator from scratch; you stand on a proven backend.

Interestingly, Perry did not use LLVM from the start. According to the project blog, it first used Cranelift (a fast single-tier compiler, mostly used in the WebAssembly world) and later switched to LLVM. There were two reasons. First, Cranelift is intentionally a fast single-tier optimizer, which is the wrong trade-off for an AOT compiler where runtime performance is paramount. Second, LLVM has broader target support - for instance arm64_32 for the Apple Watch, which Cranelift lacked.

Key point
Choosing LLVM meant choosing "optimize more deeply even if it is slower." At the cost of a slightly slower build, the executable receives the level of optimization that C and Rust enjoy.

4. Perry's Compilation Pipeline

Here is how Perry turns a .ts file into an executable, as described by the project.

TypeScript source
   │   parse with SWC -> AST
   ▼
lower AST -> HIR (high-level IR) + type inference
   │   IR transform / optimization passes
   ▼
emit LLVM IR (codegen)
   │   LLVM optimization + target machine code
   ▼
link with runtime library -> single native executable

Let us touch each stage. SWC is a blazing-fast TypeScript/JavaScript parser written in Rust; Perry uses it as its frontend to turn source into an abstract syntax tree (AST). It then lowers the AST into a high-level intermediate representation (HIR) while inferring types, runs several transform passes, and generates LLVM IR. Finally, it links with a runtime library that Perry implements natively to produce a single dependency-free binary. According to the project, a "hello world" output is on the order of a few hundred kilobytes, while an app using the standard library heavily can grow to tens of megabytes.

5. Optimization Driven by Type Information

Perry's real charm comes from "not throwing the types away." The information a typical JavaScript engine must work hard to infer at runtime is something TypeScript already tells the compiler. The project describes using that information for optimizations such as:

  • NaN-boxing: representing numeric values without pointers or boxing, reducing the overhead of numeric operations.
  • Inline object allocation: allocating objects inline via bump allocators to lower memory-access cost.
  • i32 loop counters: using 32-bit integer counters instead of generic floats for integer-valued loops, making them faster.
  • Shape-cached objects: caching an object's shape so fields are accessed directly without dynamic lookup.
  • Fast-math flags: allowing fast-math on floating-point ops to widen the room for loop vectorization.

What these have in common is that they are only possible on the premise of "knowing the type of a value." A JavaScript engine cannot be sure whether x + y is integer addition or string concatenation until it runs, but when TypeScript declares x: number, the compiler can lower it straight to integer/float instructions. Static types become optimization information.

This way of thinking - compile-time optimization driven by types - rhymes with the design of lossless compression and memory allocators in systems languages. Just as compression shrinks data more when it understands the data's structure, a compiler shrinks code more when it understands a value's structure. For that context, see our separate pieces on Zstandard rewritten in Rust and the mimalloc high-performance allocator.

6. The Paradox: "Switching to LLVM Made It 70x Slower"

Perry's backend transition carries an instructive anecdote. According to the project blog, when it first cut over from Cranelift to LLVM, some benchmarks actually ran 70x slower. Why would moving to a more powerful backend make things slower?

The cause was "boundaries." The initial LLVM version routed most operations through opaque runtime helper calls, and from LLVM's point of view the inside of those calls was an unreadable black box. Cross-boundary optimizations such as inlining and constant propagation were blocked, so no matter how powerful the optimizer was, it had nothing to do. The Perry team explains that only after deliberately inlining hot paths to tear down those boundaries did the true value of LLVM emerge.

Bolting on a powerful optimizer does not make things faster by itself. You must unfold the code so the optimizer can "see" it before its power takes effect. This is a general principle of all compiler design.

7. So How Much Faster - The Context of the Benchmarks

After the optimization work, Perry reports meaningful speedups. In benchmarks from one published release, the following results are cited versus Node.js.

  • Recursive factorial: about 24.6x faster
  • Method calls: about 11x faster
  • Loop overhead: about 4.4x faster
  • Math-intensive work: about 3.5x faster

These numbers should be read with care, though. The items above are mostly micro-benchmarks with clear types and tight loops - exactly the territory where AOT and static typing shine most. Real applications mix in I/O waits, memory allocation, and library calls, so the felt difference can be smaller. And V8 is a world-class JIT refined over many years, so it remains formidable on code full of dynamic patterns. It is more accurate to read this as "AOT and static types make a big difference on favorable workloads" than "Perry is always N times faster."

8. Prior Art - Perry Is Not the First

Attempts to compile TypeScript/JavaScript to native or WebAssembly did not start with Perry. Understanding the lineage clarifies where Perry sits.

8.1 AssemblyScript

AssemblyScript compiles a subset of TypeScript to WebAssembly. The syntax resembles TypeScript, but it is really closer to a separate language: it does not accept arbitrary TypeScript and requires its own rules, such as explicit integer types. Its backend is not LLVM but Binaryen, a WebAssembly toolchain. The approach is "constrain the types strictly to get close to native."

8.2 Static Hermes

Meta's Static Hermes is the next generation of the Hermes engine for React Native. It aims to AOT-compile soundly typed JavaScript - annotated with TypeScript or Flow types - to native code at build time, reducing the JIT's guesswork via static typing for faster and smaller output. According to public materials, however, its TypeScript support is experimental and incomplete. It is the closest to Perry in philosophy (types for AOT), but Static Hermes has a clear stage: the React Native ecosystem.

8.3 Porffor

Built by Oliver Medhurst, Porffor is an experimental engine that AOT-compiles JavaScript/TypeScript to WebAssembly and native binaries. Because it compiles the code itself instead of bundling an interpreter, the project says its output is far smaller (citing cases of binaries up to 1000x smaller) and faster than existing "JS to Wasm" projects. Porffor has a broad goal of standards conformance (Test262) across JavaScript in general, not only TypeScript.

Project Input Backend Main target
Perry TypeScript LLVM Native binary
AssemblyScript TS subset Binaryen WebAssembly
Static Hermes Typed JS/TS Own + LLVM-family Native (RN)
Porffor JS/TS Own -> Wasm/native Wasm / native

Perry's distinction is the directness of "take ordinary TypeScript and produce a native executable straight through LLVM," together with a standard library and packages reimplemented in Rust.

9. The Reality of the Standard Library and npm Compatibility

The trickiest problem for a native compiler is not the language but the ecosystem. TypeScript's power comes from hundreds of thousands of npm packages, most of which assume the Node.js runtime API (fs, http, net, and so on). Because Perry does not carry V8/Node, it must reimplement those APIs itself.

According to the project, Perry ships a high-performance standard library written in Rust, providing console, fs, path, process, JSON, Math, Date, crypto, Buffer, Map/Set, worker_threads, and more natively. It also includes drop-in native implementations for popular packages such as fastify, axios, PostgreSQL, MySQL, Redis, bcrypt, and JWT. In other words, it is not "any npm package just works," but rather "code runs within the scope Perry has reimplemented natively."

// Conceptual example per the project: an HTTP server that builds to a single binary with no separate runtime
import { createServer } from "http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("Hello from a native TypeScript binary");
});

server.listen(8080, () => {
  console.log("listening on :8080"); // a binary that runs without Node.js
});

10. Limits - Dynamic Features and the Ecosystem Wall

For balance, let us be explicit about the limits. AOT native compilation is not free, and it fundamentally clashes with the most dynamic parts of JavaScript.

  • Dynamic evaluation: eval and new Function, which execute strings as code at runtime, collide head-on with the AOT premise of "compile all code before running." This is the hardest territory for a static compiler.
  • Unsupported features: per the project docs, decorators are currently listed as unsupported. The vast corners of the standard are being filled in gradually.
  • Ecosystem compatibility: only code that does not depend on native runtime APIs, or packages Perry has reimplemented, will run. Lifting an existing large app with a deep npm dependency tree as-is is hard.
  • Maturity: per the project, the version is in the 0.5.x range - an early stage under active development. Validation on suitable workloads should come before any wholesale production adoption.

In short, it is more accurate to see Perry not as "a Node.js replacement for every TypeScript app" but as "a tool that lets you use TypeScript like a systems language for specific workloads."

11. Where It Fits - Usage Scenarios

So where does Perry's strength shine? Follow the character of AOT, single binary, and instant startup, and the answers fall out.

  • CLI tools: a dependency-free single binary is simple to distribute and starts instantly. Users do not need to install Node.
  • Serverless and edge: where cold start is cost and latency, instant startup with no warm-up is a clear advantage.
  • Embedded and constrained environments: small binaries and low memory use favor devices with tight resources.
  • Performance-sensitive workloads: for work with clear types and heavy numeric computation, you can aim for near-native performance.

This overlaps with systems-language choices like "Go to Rust." It is the same question of which language/toolchain to pick when you want faster execution, smaller binaries, and predictable performance. For that context, continue with our Go to Rust migration guide.

12. Conclusion - TypeScript's "Second Life"

Perry's message is clear: TypeScript's types are not merely a developer-convenience tool but optimization information a compiler can use. Instead of erasing types via transpilation and re-inferring them on a heavy JIT, if you hand those types straight to LLVM and lower them to native machine code, TypeScript can gain performance and deployment convenience close to a systems language.

Of course Perry is still early, and the formidable walls of dynamic features and the vast npm ecosystem remain. Not every app will compile to native tomorrow. But together with Static Hermes, Porffor, and AssemblyScript, the larger picture Perry sketches is sharp: the identity of JavaScript/TypeScript as "a dynamic language born in the browser" is expanding, through the new path of AOT compilation, into "a language that can also reach into systems territory." If you enjoy writing TypeScript, this is a trend worth watching.
