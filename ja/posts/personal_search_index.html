きっかけ - 個人検索エンジンという範疇

2026 年 9 月初め、韓国の開発者コミュニティにオープンソースのプロジェクトが一つ紹介された。訪問したウェブページとローカルファイルの本文全体をインデックスしておき、あとでその中から探すというのが要旨だった。興味深いのはこの道具の完成度ではなく、なぜこの範疇が今になって別に生まれたのかの側である。ブラウザにはすでに閲覧履歴があり、OS にはファイル検索があり、ノートアプリはあふれている。それでも毎年同じ席に新しい道具が出てくる。

この記事はその空席の形を見る。まずこの問題がウェブ検索とどこで分かれるかを見て、プライバシーの問題を前に置いたうえで、その上で保存と検索と費用を話す。順序をこうする理由は単純である。技術の選択を先に決めてプライバシーを後から付けると、たいてい付かない。

  • 扱うこと — なぜこれが順位の問題ではないのか、何を保存すれば見つかるのか、その保存が作る危険の性質、長く使ったときに来るもの
  • 扱わないこと — 導入と設定、製品の比較と推奨、他人の記録を収集するあらゆる方法
  • 引用の原則 — リポジトリの数値と製品文書は時点を付けて記し、確認できなかった数値は書かない

公開ウェブ検索とは違う問題である

公開ウェブ検索は数十億の文書から上位十件を選ぶ問題である。個人の記録検索は自分が見たもの数千から数万件のなかで一つを取りこぼさない問題である。ここで順位の値打ちがひっくり返る。ウェブ検索で一位と四十位の差は決定的だが、自分の記録のなかでは四十位でも目で追えばよい。代わりに一覧にまったく出てこなければそれで終わりである。重要なのは精度ではなく再現である。

クエリの性格も違う。ウェブ検索はこれについて知りたいであり、個人の検索はあれをもう一度見たいである。後者には利用者が答えの存在をすでに知っているという特異な性質がある。だからウェブ検索が失敗すればないのだろうと終わるが、個人の検索が失敗すると、あるのに見つからない状態で残って人を長く捕まえる。

順位を付ける材料もない。公開ウェブはリンクとクリックと引用で文書の重さを量るが、自分の記録にはそうした信号がない。代わりに別の信号がある。いつ見たか、どれだけとどまったか、どこから来たか、また開いたか。

項目公開ウェブ検索自分の記録の検索
対象の規模数十億の文書。インデックス自体がインフラの問題である数千から数万。ノートパソコン一台に収まる
核心の指標精度。上位十件がすべてである再現。一覧にありさえすれば目で見つける
クエリの意味これについて知りたいあれをもう一度見たい。あることを知っている
順位の材料リンク、クリック、引用などの外部信号訪問時刻、滞在、流入経路、再訪
失敗の形ないのだろうと思って終わるあるのに見つからない状態で残る
データの性格公開文書。流出という概念がないすべて自分に関するもの。一ファイルが profile である
  • 規模が小さいというのは技術的に易しいという意味であって、甘く見てよいという意味ではない。難しさが検索アルゴリズムからデータ管理へ移っただけである
  • 再現を優先すると結果が雑然とする。その雑然さを耐えられる形にすることがこの分野の実際の UI 課題である
  • 時間が強力な軸になる。ウェブ検索で日付フィルタは付加機能だが、ここでは一次のソート基準になることが多い
  • 最後の行が残り全部を規定する。このインデックスは公開文書の集まりではなく自分に関する記録である

この問題の中心はプライバシーである

訪問したページの本文までインデックスするというのは機能を一つ入れることではなく、散らばっていたものを一か所に集める仕事である。それまでその情報はブラウザのなかに、各サイトのサーバに、あるいはどこにも残らないまま分かれていた。危険の大きさは、そのファイル一つが外へ出たとき何が漏れるかを思い描けばすぐ見当がつく。

何が入っているかは法がすでに一覧にしている。韓国の個人情報保護法第23条と同法施行令第18条は、思想・信条、労働組合や政党への加入と脱退、政治的見解、健康、性生活に関する情報、遺伝情報、犯罪経歴資料、特定の個人を識別する目的で作られた身体・生理・行動の特徴に関する情報、人種・民族に関する情報を機微情報として別枠にしている。ふつうの一か月分の閲覧履歴は、この一覧の半分以上と重なる。

だから設計の問いは三つになる。どこに置くか、何を外すか、どう消すか。一つめが残りを支配する。ローカルにあれば危険の最大の大きさが機器一台に縛られ、その境界は自分の知っている境界である。外へ出た瞬間その境界は事業者の寿命、方針変更、法的管轄、侵害事故にまで伸び、戻せない。一度送ったものは、消したという言葉を信じる以外に確かめる方法がない。

このデータがどんな扱いを要求するかは、大きな会社が同じ問題を解くときどこまで行ったかを見ればわかる。マイクロソフトが Recall のドキュメントに記した条件がその基準線である。スナップショットは機器にだけ保存されマイクロソフトへは送られない。開くには Windows Hello で本人確認をしなければならない。スナップショットとそれに付くベクトルデータベースは常に暗号化され、鍵は TPM で保護される。機能そのものもオプトインなので、管理者が代わりに入れることはできない。学ぶべきは製品ではなく要求水準である。

除外ルールも同じ文書にある。機微情報のフィルタリングが既定で有効になっており、対応ブラウザのプライベートブラウジングは既定で除かれ、DRM の掛かったコンテンツは保存しない。だが限界も記されている。フィルタしたサイトでも埋め込みコンテンツ、ブラウザの履歴、前面にない開いたタブの形で一部が残りうるということである。除外ルールは確率を下げるのであって、保証を作るのではない。

  • インデックスファイルがどこにあり、何で施錠されているか。認証なしで開くインデックスは実質的に平文のファイル一つである
  • 既定の除外一覧に何が入っているか。プライベートブラウジング、金融・医療のドメイン、社内システムが最初から外れているかどうかが性格を分ける
  • 消去が本当に全部を消すか。本文は消えたのにベクトルが残る、インデックスは空にしたのにスナップショットのファイルが残るという例はよくある
  • 外へ出る経路が既定値か選択か。埋め込みを外部 API へ送る設定が既定なら、それは別の種類の製品である
  • 機器を分け合う状況を想定しているか。共用のノートパソコンや、一つのアカウントを複数人で使う環境で分離がどうなるか

ブラウザの履歴ではなぜ足りないのか

ブラウザが何を残すかは拡張 API のドキュメントに正確に書かれている。Chrome の history API で HistoryItem は id、url、title、lastVisitTime、visitCount、typedCount の六つのフィールドである。個別の訪問を表す VisitItem には id、visitId、referringVisitId、visitTime、transition、isLocal がある。Firefox 側の定義も同じ六つである。

この一覧に本文を入れる場所がない。ないものは検索できない。だからブラウザの履歴はタイトルを覚えているときにだけ働くが、人が実際に覚えているのはたいてい本文である。タイトルは読む瞬間に通り過ぎ、本文はとどまる。

ブラウザの履歴に残るもの
  HistoryItem : id · url · title · lastVisitTime · visitCount · typedCount
  VisitItem   : id · visitId · referringVisitId · visitTime · transition · isLocal

記憶が投げる問いとその結果
  「読み込み遅延がキャッシュのせいだと言っていた段落」  -> 本文フィールドがない。検索不可
  「先月のある夜に読んでいたあの文書」                  -> lastVisitTime で絞れるが候補は数百件
  「ある記事からリンクをたどって行ったページ」          -> referringVisitId で追跡できる
  「タイトルにスケジューラが入っていた記事」            -> title で検索できる

範囲の制約もある。Chrome のヘルプは履歴が直近 90 日分であり、内部ページとシークレットモードで見たページ、利用者が消したページは保存しないと記している。もう一度探したくなる文書はたいてい 90 日より古い。ブックマークは別の形で足りない。ブックマークが求めるのは容量ではなく判断であり、実際にもう一度探すことになるページは、見たときには重要そうに見えなかったページである。判断の時点と必要の時点がずれているので、構造的に取りこぼす。

  • ブラウザの履歴は移動を助けるために作られたデータ構造である。アドレスバーの補完が目的であって、想起が目的ではなかった
  • だから本文がないのは欠陥ではなく設計である。本文を保存すれば保管庫が大きくなり危険が生じるのに、その代価を既定で払う理由がなかった
  • ブックマークは判断を前もって求め、履歴は判断を求めない代わりに本文を捨てる。二つのあいだが空いている
  • 記憶がつかむ手がかりは文だけではない。画面の位置、隣にあった図、その日していた仕事も手がかりだが、テキストだけではこちらが拾えない

何を保存すれば見つけられるのか

保存する項目を増やせば答えられる問いが増える。ただし項目ごとに答える問いが違い、払う代価も違う。全部保存しようという結論へ行く前に、この対応関係を広げておくほうがよい。

保存する項目これが答える問い払う代価
アドレスとタイトルあのサイトの名前は何だったかほとんどない。ブラウザがすでにやっている
本文テキストあの文があったページはどこかインデックスの容量。そして繊細な本文が丸ごと入る
訪問時刻と順序先週の火曜の夜に見ていたもの小さい。ただし生活のパターンがそのまま現れる
流入経路どの記事からリンクをたどったか小さい。関心のつながりが profile になる
滞在時間とスクロール位置最後まで読んだものだけ見たい小さい。読み方の癖が記録として残る
画面スナップショットあのとき画面にあったそのまま最も大きい。画像・レイアウト・ログイン状態まで残る

ここで見るべきは一覧ではなく傾きである。上へ行くほど安く無害で見つかりにくい。下へ行くほど見つかりやすく高く危険である。見つけられることと安全であることは同じ軸の両端である。よい実装で消せる衝突ではなくどこに立つかを選ぶ問題であり、自分がその軸のどこにいるか知らないまま入れておくことが最も悪い。

  • スナップショットは性格の違う項目である。テキストは結果に断片だけ見えるが、スナップショットは開いた瞬間に全部が見える
  • 滞在時間とスクロール位置は容量をほとんど食わずに順位を大きく改善する。費用対効果が最もよい項目はたいていここである
  • 本文の保存は効果が最も大きく危険も最も大きい。だからこの項目だけドメイン別の除外ルールを別に置く設計が多い

語を覚えているときと意味だけ覚えているとき

保存の次は取り出し方である。よくキーワード検索とセマンティック検索と呼ばれる二つの分かれ道の違いを正確に言えば、記憶の形によって答える側が違うということである。

全文検索は文書をトークンに割って転置索引を作る。エラーメッセージ、製品名、関数名のように綴りが決まっているものに強い。表現力も思ったより広く、SQLite の FTS5 のドキュメントを基準にすると、フレーズ・前方一致・近接の検索と列指定、ブール結合がすべてクエリ構文のなかにある。

全文検索が表現できる形 (SQLite FTS5 の構文を基準に)

  writeback cache               二つの語が両方入った文書
  「write-back cache」           この順序そのままの句
  writeb*                       こう始まる語
  NEAR(cache latency, 10)       二つの語が 10 トークン以内に一緒にある所
  title : scheduler             タイトル列にだけあるもの
  cache NOT redis               前はあって後ろはない文書

セマンティック検索は文書の断片とクエリをそれぞれベクトルに変えて近いものを選ぶ。語が一つも重ならなくても意味が近ければ引っかかるので、意味だけが残った記憶に答える。ただし制約が二つある。一つは入力の長さである。広く使われる小型の文埋め込みモデルの公開モデルカードは、出力が 384 次元、パラメータが 2,270 万個であり、既定で 256 word piece を超える入力は切り捨てられると明記している。だから長いページは割らねばならず、割り方が検索の品質を決めてしまう。覚えている文がよりによって二つの断片の境目にまたがっていれば、その文を手がかりにしても出てこない。

もう一つは失敗の形である。セマンティック検索はないと言えない。つねに最も近いものをいくつか返すからである。全文検索はなければ 0 件であり、0 件はそれ自体が情報である。見当違いの五件にはそうした合図がない。だから実務では両方を併用する側へ収束する。ベクトル検索を何の上に載せるかはベクトル検索を何の上に載せるかの側で別に扱った。

記憶に残った形どちらが答えるか失敗するときの形
正確な語やエラー文全文検索綴りが少し違えば 0 件になる
意味だけ残り表現は消えたセマンティック検索近いが違うものが五つ出る
おおよその時期時刻フィルタ覚えた時期が違えば範囲の外へ出る
どこから来たか流入経路の追跡途中の経由地が記録されないと切れる
画面の印象だけ残ったスナップショットの流し見量が多いと流し見自体が不可能になる
  • 二つを併用すると再現は上がるが結果は雑然とする。だから結果を混ぜる規則が実際の品質を決める
  • セマンティック検索は最初の数日は印象がよく、あとで失望を与える。正確な語を知っている状態で見当違いの結果を受けると信頼が速く崩れる
  • 全文検索だけ置けば長くよく持つが、肝心の「どこかで見た」という形のクエリには失敗し続ける
  • どちらか一つを選ぶなら全文検索が先である。安く、0 件という合図をくれ、結果を説明できるからである

ローカルで回す代金

常時回るインデックスの負担は保存と計算に分かれる。保存の側には見当をつけられる公開の計測値がある。SQLite FTS5 のドキュメントにはディスク上 1,636 MiB のメール群をインデックスした試験が載っており、FTS インデックスだけで detail=full が 743 MiB、detail=column が 340 MiB、detail=none が 134 MiB だった。同じ資料なのに何を記録するかで五倍以上に振れる。位置情報を捨てれば小さくなるが、フレーズ検索と近接検索を一緒に失う。

ここに原文の写しが加わる。FTS5 は既定の設定で元の行の写しを一緒に保存する。インデックスだけ置く方式もあるが、そうすると結果に本文の断片を見せられない。結果の断片はほぼ必須なので、実際には本文とインデックスの両方を持つことになる。

埋め込みの保存の負担はむしろ小さい。384 次元の浮動小数点ベクトル一つは単純計算で 1,536 バイトであり、一万ページを五つずつ割っても算術では数十メガバイトである。問題は計算である。全文インデックスが文書を一度なぞる仕事なら、埋め込みは断片ごとにモデルを一度ずつ回す仕事であり、ブラウジングの最中に実時間でやればファンが回るのが体感される。だから実際の設計は先送りする。保存はすぐ、全文インデックスはまもなく、埋め込みは電源がつながったときにまとめて。副作用はさっき見たページがセマンティック検索にはまだないことである。

画面スナップショット方式は代金が一段上である。マイクロソフトが Recall に求める最小仕様がその大きさを示す。Secured-core の基準を満たす Copilot+ PC、40 TOPS の NPU、16 GB の RAM、論理プロセッサ 8 個、256 GB のストレージ。有効にするには空き容量が最低 50 GB 必要で、25 GB を下回ると保存が止まる。割り当ては 256 GB の機器に 25 GB、512 GB に 75 GB、1 TB 以上に 150 GB であり、上限に達すると古いものから消える。

  • インデックスの大きさは文書の量よりも何を記録すると決めたかに大きく左右される。位置情報を残すかどうかが数倍を分ける
  • 埋め込みは保存ではなく計算が隘路である。バッテリーで回る機器ではこの負担がそのまま体感される
  • 先送りすれば負荷は減るが、最新の文書が検索から抜ける区間ができる。この区間の長さが体感の品質を決める
  • スナップショットは別の範疇である。保存容量、演算装置、電力の要求がすべて一段上へ上がる

保存できないものと保存してはいけないもの

すべてのページが保存できるわけではなく、保存できるもの全部が保存してよいものでもない。この二つが重なる場所が、この問題の最も居心地の悪い部分である。

まず保存が成り立たない側。検索結果の画面、無限スクロールの一覧、実時間のダッシュボードは、アドレスが同じでも開くたびに中身が違う。こうしたページにはもう一度探すという言葉自体が成り立たない。保存されたのはアドレスではなくあのときのあの画面である。だからここがスナップショットの要る地点であり、同時に最も危険な地点になる。ダッシュボードにはたいてい見てはいけないものが一緒に出ている。

次に保存してはいけない側。メールボックス、口座照会、診療記録、社内システムはたいてい最ももう一度探したいものであり最も保存してはいけないものである。ここにはもう一層ある。ログインの後ろのページには自分の情報だけがあるのではない。受け取ったメールには送り主の文があり、社内文書には同僚の名前と判断がある。自分の記録をインデックスするという言葉が、実際には他人の情報を自分の機器に複写する仕事になる地点がここである。

だから除外一覧は付加機能ではなく前提になる。ただし除外は完全ではない。同じ Recall のドキュメントは、フィルタリングがそのサイトに接続したという事実そのものをブラウザや通信事業者、サイト、組織が知ることは防げないと明記している。ローカルのインデックスから外したことと、痕跡がないことは別の話である。

  • アドレスが同じでも中身が違うページは想起の単位がアドレスではなく時刻になる。時間軸が一次のソートになる理由がここにもある
  • ログインの後ろのコンテンツは価値と危険が同じ方向に大きくなる。この重なりは設定では分離されない
  • 他人の情報が混ざって入る問題は好みではない。共用の機器や業務の環境では範囲を決める問題になる
  • 除外一覧はドメイン単位で置くほうが実効がある。ページ単位の除外は管理が続かず、たいてい最初の一週間しか保たない
  • 最も実用的な判断はこれである。外すかどうか迷ったら外す。あとで入れる費用のほうが、あとで抜き出す費用よりずっと安い

既存の道具が空けている席

この席がなぜ空いているかは、既存の道具がそれぞれ何をして何をしないかを並べれば見える。

道具本文を保管するか扱う範囲空いている所
ブラウザの閲覧履歴保管しない訪問したウェブページ、直近 90 日本文がなく文では見つけられない
ブックマークアドレスだけ残す自分がそのとき選んだもの選ぶ時点では何が重要になるかわからない
ノートアプリ書き写したものだけ自分が手で残したもの書き写さなかったものは存在しない
デスクトップ検索ファイルの中身はインデックスする自分の機器のファイルウェブで見たものは対象ではない
ウェブアーカイブ保管する公開されたページ自分が見たものではなく誰かが保存したものである

デスクトップ検索から見ると境界がはっきりしている。Windows の検索は既定のクラシックモードでドキュメント・ピクチャ・ミュージックのフォルダとデスクトップを、拡張モードで PC 全体をインデックスする。ファイル名と完全なパスを含む属性をインデックスし、テキストのあるファイルは中身までインデックスするが、形式ごとに属性だけをインデックスするよう変えるとインデックスは小さくなる代わりに中身の検索を失う。前節の保存量と検索力の取引が OS の設定にもそのまま入っているわけである。

macOS は除外を明示的な機能として置く。システム設定の Spotlight のなかに検索プライバシーの一覧があり、フォルダやディスクを入れればその場所は検索されない。アップルの文書は代価も記している。特定のファイルとフォルダを除外すると一部のアプリの更新通知を受け取れないことがあり、内部ディスク全体を除外するといかなる更新通知も受け取れないということである。何かを外す決定には、思わぬ所で代価が付いてくる。

どちらもウェブで見たものは扱わない。ブラウザ側はこの空席を知っている。Chrome には AI による履歴検索があり、ヘルプを基準にすると有効にした場合訪問したサイトのページ内容が機器に保存され暗号化される。ただし自分で入れるオプトインであり、米国で英語で使う必要があり、結果はサイトが変わっていても訪問当時の内容を使う。本文を保存しないと想起にならないという結論はブラウザを作る側も同じで、それでも提供の範囲は狭い。別の道具が生まれ続ける席がこの隙間である。

ノートアプリは性格が違う。ノートアプリが持つのは自分が書き写すと決めたものだけであり、決心の時点がずれるという問題はブックマークと同じである。この腐りが組織の単位で起きるとどうなるかは社内ナレッジベースは静かに腐るの側に記した。

  • 既存の道具はそれぞれ別の目的で作られており、想起はどちらの目的でもなかった。空席は失敗ではなく境界である
  • OS のファイル検索とブラウザの閲覧履歴のあいだにウェブの本文という枠が空いている。この枠がこの範疇の存在理由である
  • ブラウザがこの枠を埋め始めたことは、別の道具の寿命が長くないかもしれないという信号としても読める

長く使うほど出てくる問題

この種の道具の本当の試験は入れた最初の一週間ではなく二年目である。第一に、大きくなる。大きさ自体より大きくなる速度が問題である。一日 200 ページなら一年で七万ページ台であり、ある時点からインデックスの再構築が一晩回す作業になる。そこからスキーマを直すことが事実上不可能になる。直すには再構築が要るのに、再構築が一日仕事だからである。

第二に、古びる。保存されたのは訪問当時の内容であり、そのあいだにページは直されたか消えたかもしれない。これは欠陥ではなく性質であり、原本が消えたあとはむしろ自分の写しが唯一の記録になる。ただしその写しを根拠にしてよいかは別である。検証されておらず自分だけが持つ写しである。

第三に、重複する。同じ文書が別のアドレスで、別の時点に、印刷用とモバイルと翻訳のページの形で何度も入ってくる。上位十行が同じ文書の十種の版になれば、その検索は失敗している。重複の除去は何を同じと見るかを先に決めねばならないのに、その基準が自明ではない。

第四に、使わなくなる。これが最もよくある結末である。インデックスがあることを忘れてただウェブ検索をやり直す。個人の道具が死ぬ形は故障ではなく忘却であり、理由もある。道具を開く摩擦が検索窓に打つより少しでも大きければ、急ぐときはいつも後者を選ぶことになる。

  • スキーマは再構築がまだ安いうちに決めねばならない。大きくなったあとは事実上凍結される
  • 古びることは欠陥であり同時に値打ちである。ただし消えた原本の写しを根拠に使うときは、その事実を明かさねばならない
  • 重複除去の基準は道具が代わりに決めてくれない。決めなければ上位の結果が同じ文書で埋まる
  • 最もよくある終わりは忘却である。だからこの道具は既存の習慣のなかへ入る設計が性能より重要なことが多い

作るのか使うのか

ふつうの助言は明確である。自作せず既存のものを使え。費用が最初の版ではなく維持から出るからである。ところがこの領域ではその助言が一段揺れる。データが繊細なほど他人のサービスに載せる費用が非線形に大きくなるからである。ふつうはサービスが閉じれば不便な程度だが、ここでは閉じ方によって自分の記録全体の行方が変わる。

だからといって自作する側がロマンチックなわけでもない。最初の版は本当に週末でできる。長いのはその先である。スキーマを直すたびに再構築が回り、ブラウザが更新されると拡張が壊れ、バックアップなしで回していてインデックスのファイルを一つ飛ばせば数年分が消える。

基準は三つに絞れる。保存場所が自分の管理下にあるか。外へ出るものがあるならそれは既定値か選択か。やめるときにデータを持ち出せるか。三つめが特によく抜ける。入る道だけあって出る道のない設計は、数年後にそのインデックスの人質になる。そしてオープンソースだという事実が一つめの条件を自動的に作ってくれるわけでもない。セルフホストできることと既定の設定がローカルであることは別の話である。ライセンスも保証ではない。ライセンスはコードがどこへ行けるかを決めるのであって、データがどこへ行くかを決めない。

  • 自作するときの本当の費用は最初の実装ではなくスキーマ変更と再構築である。この二つを先に設計すれば残りは付いてくる
  • 他人の道具を使うときは既定値を見る。文書に何ができると書いてあるかではなく、何も設定しないとき何が起きるかを見る
  • 出る道、すなわち書き出しと完全な削除があるかを最初に確かめる。あとになると確かめる余裕がない
  • オープンソースは検証可能性であって検証の結果ではない。そしてライセンスはデータの行方について何も言わない

きっかけになった道具は今どのあたりか

きっかけになったプロジェクトの公開の数値を 2026 年 9 月初め時点で記しておく。リポジトリが作られた日は 2026 年 1 月 4 日で、スターは 3,526 個、フォークは 161 個、開いている issue は 56 個である。最新のリリースは 2026 年 8 月 23 日の v0.18.0、最後のコード反映は 9 月 1 日である。言語は Go、ライセンスは AGPL-3.0 である。

この数字が言うことは二つである。一つ、活発である。八か月のあいだにリリースが十八回を超え、今もコミットが入っている。二つ、八か月であり、まだ 0.x である。スターの数は関心の指標であって安定性の指標ではない。人が好きだということと、三年後にも自分のインデックスを読めるということは別の話であり、個人の記録を載せる器ではこの区別が特に重い。

機能の一覧に記されているのは、全文インデックス、ブラウザの自動インデックス、クエリ機能、選択的なセマンティック検索、クローラとブラウザからの取り込み、ウェブ・ターミナル・MCP のクライアント、多人数利用である。

より重要なのは文書が自ら明かした境界である。既定ではテレメトリとクラウド同期がなく、ブラウザ拡張はインデックスしたページの内容を利用者が指定したサーバへだけ送り、選択的なセマンティック検索を有効にすると文書のテキストが利用者が選んだ埋め込みエンドポイントへ出ていく。最後の一文が第 3 節の分かれ道とちょうど同じ地点である。ローカルが既定で外部への送信が選択という配置は何を保証するわけでもないが、何を問うべきかは教えてくれる。

  • 成熟度を見るときスターの数より有用なのはリポジトリの年齢、リリースの間隔、開いている issue の性格である。前の二つは数値からすぐ見える
  • 0.x というのは保存の形式が変わりうるという意味である。長く積むデータでは、この一行がどの機能より重い
  • 機能の一覧より既定値と境界を明かした文のほうが多くを語る。その文がまったくない道具が最も判断しにくい

まとめ

自分が見たものを探し直す仕事は、ウェブ検索を縮めた問題ではない。対象が数十億ではなく数万なので順位より再現が重要になり、クエリも知りたいことではなくもう一度見たいことである。ブラウザの履歴がこの仕事をできない理由も単純である。タイトルとアドレスはあって本文がないのに、人が覚えているのは本文だからである。

だから本文を保存する方向へ行くことになり、その瞬間に問題の性質が変わる。散らばっていたものがファイル一つにまとまり、そのなかには法が機微情報として別枠にした項目のかなりの部分が入る。ローカルに置く設計と外へ送る設計の違いは利便性ではなく、危険の境界がどこまで伸びるかの違いである。

残るのは一つの軸である。よく見つかるようにするあらゆる措置は、同時に危険を大きくする。本文を入れれば文で探せるようになり、繊細な本文が丸ごと入る。スナップショットを入れれば画面がそのまま蘇り、ログイン状態まで残る。この軸をなくす方法はなく、自分がその上のどこに立っているかを知っていることができるすべてである。

確認できなかったこと

  • きっかけになったプロジェクトが内部でどのインデックスエンジンと保管庫を使うのかは公開の説明から確認できなかった。この記事のインデックスの大きさの議論は、そのプロジェクトではなく SQLite FTS5 のドキュメントの公開計測値を根拠に記した
  • ローカルの埋め込みの実際の所要時間と電力消費は、信頼できる計測値を確認できなかったので数値なしで記した。計算が隘路だという記述は方式の違いから出たものであって、計測から出たものではない
  • Chrome の AI による履歴検索がシークレットモードや特定のサイトを自動的に除外するのか、保存されたページの内容を別に消せるのかは、当該のヘルプから確認できなかった
  • 個人が自分の記録を自分の機器に保存する行為に個人情報保護法のどの条文がどう適用されるのかは確認できなかった。第23条の機微情報の一覧は危険の大きさを測る参考としてのみ引用しており、法的な判断はしていない
  • この範疇の道具の利用者の規模や一年後の継続利用率についての公開資料は見つからなかった。忘却で終わるという記述は観察であって統計ではない
