Filtering Out Whitespace-Only Diffs - So the Real Change Is Not Buried

What -w and -b actually differ on, and how to drop a formatting commit out of blame entirely

2026-09-01 Dev & Infra

A review request comes in. Three files, 51 insertions and 51 deletions. Open it and the indentation has gone from tabs to spaces, trailing whitespace has been cleaned up, and somewhere in the middle a single option has been added. The reviewer's job is to find that one place, and the screen presents the other hundred lines in exactly the same red and green.

What people do at that point is usually one of two things. They scroll, scan with their eyes and miss it, or they just press approve. Neither is review. And this is not a question of how conscientious the reviewer is. It is a question of who handed a human being a screen with a signal-to-noise ratio of one to fifty.

The good news is that tooling solves almost all of it. Git can recompute a diff with whitespace differences excluded, and it can drop a whole formatting commit out of line-by-line history tracking. This article walks through those features using output from throwaway repositories created and run for the purpose.

Every command and every block of output below was run directly in a fresh throwaway repository, in the environment recorded in §2. The pasted output is what actually appeared. Anything I could not run is collected separately in §20. All example paths are arbitrary names.

How one line gets buried under a hundred

Whitespace noise is rarely created on purpose. A formatter that runs automatically on save, different tab-width settings across the team, and a mixture of people who do and do not have trim-on-save enabled. With those three alone, opening a file and closing it is enough to make the whole thing a modification.

The consequence follows from how diff works. Comparison happens line by line, so a single invisible byte changing anywhere in a line renders that line as a deletion plus an addition. Reindent a forty-line function and you get forty deletions and forty additions: eighty lines filling the screen. If a real edit sits among them, nothing distinguishes it visually from the other seventy-nine.

Two responses come up often, and both are only partly right. The first is to stop using formatters, which brings back the different category of review waste that formatters removed. The second is for reviewers to look more carefully, which is asking human attention to pay off a debt that tooling can settle, and it does not last. The answer that actually works is the third: take whitespace differences out of the calculation before the diff reaches the screen.

There are five kinds of whitespace change

Treating whitespace change as one thing makes it impossible to pick an option, because git's ignore options each ignore something different. Five kinds turn up in practice, and each arrives by a different route.

KindHow it appearsVisible?Effect on the diff
Trailing whitespaceSpaces and tabs left behind while editing. They all vanish at once when someone with trim-on-save opens the fileNoThe whole line is marked as changed
Indentation conversionTabs to spaces or back. Formatters, or differing editor settingsBarelyEvery indented line is marked as changed
Amount of inner whitespacePadding added or removed around an equals sign to line things upYesThat line is marked as changed
Blank lines added or removedA formatter's blank-line rules, or personal paragraphing habitsYesAdded and deleted lines appear and hunk ranges widen
Final newlineA tool that saves the last line without a terminating newlineNoThe last line is shown as a deletion plus an addition

There is a sixth: the line-ending character itself. CRLF versus LF behaves a little differently, so §13 handles it separately. For another case of an invisible byte contaminating a file, there is the three-byte BOM at the front of a file, which tends to break execution rather than diffs.

Putting all five into one file

Before explaining any option, build something to compare against. Take a six-line config file, put all five kinds into it, and hide exactly one real change in the middle. The real change is a single timeout value going from 30 to 60. Everything else is whitespace.

$ cat -A app.conf          # the committed original. ^I is a tab, $ is end of line
server {$
^Ilisten 8080;$
^Iretries = 3;$
^Itimeout = 30;$
log_level = info;$
}$

$ cat -A app.conf          # after editing
server {   $               <- three trailing spaces
    listen 8080;$          <- tab became four spaces
^Iretries  =  3;$          <- amount of inner whitespace changed
^Itimeout = 60;$           <- the real change (30 -> 60)
$                          <- blank line added
    log_level = info;$     <- indentation where there was none
}                          <- final newline removed (no $ here)

Running git diff with no options against that state gives the following. A six-line file becomes six deletions and seven additions. One number changed, and the entire file splits.

$ git diff
diff --git a/app.conf b/app.conf
index bd81bfd..d0ea0b8 100644
--- a/app.conf
+++ b/app.conf
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
-}
+server {
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
+}
\ No newline at end of file

To find the timeout line here, a reviewer has to compare twelve lines by eye. That is feasible in a six-line file and impossible in a four-hundred-line one.

Applying the ignore options one at a time

Now the same file, one option at a time. Reading the three in sequence shows exactly how far each of them reaches.

$ git diff --ignore-space-at-eol      # trailing whitespace only
@@ -1,6 +1,7 @@
 server {                             <- dropped down to a context line
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
 }
\ No newline at end of file

$ git diff -b                         # --ignore-space-change
@@ -1,6 +1,7 @@
 server {
     listen 8080;                     <- tab -> spaces swallowed too
 	retries  =  3;                   <- inner whitespace amount swallowed
-	timeout = 30;
-log_level = info;
+	timeout = 60;
+
+    log_level = info;                <- new indentation survives
 }
\ No newline at end of file

$ git diff -w                         # --ignore-all-space
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;                    <- what is left is the real change
+
     log_level = info;                <- and the added blank line
 }
\ No newline at end of file

Line up the three outputs and the split between -b and -w lands on exactly one line. log_level = info; is the line that originally had no indentation and gained four spaces. -b treats runs of one or more whitespace characters as equivalent to each other, so zero and four are not equal. -w treats whitespace as absent entirely, so it swallows that too.

  • --ignore-space-at-eol looks only at line ends. Indentation conversion survives it, so it is weak against formatter noise
  • -b ignores trailing whitespace as well, which makes it a strict superset of --ignore-space-at-eol
  • -w is a superset of -b. The three form a containment chain
  • None of them removes an added blank line. Blank lines belong to a separate option, and that one has conditions attached
  • One more thing worth noticing. Under --ignore-space-at-eol, the final } dropped to a context line, meaning the presence or absence of a final newline is also treated as end-of-line whitespace

--ignore-blank-lines decides per hunk

In the last run of §5, an added blank line survived -w. The natural next thought is to add --ignore-blank-lines, and the natural next thought turns out to be wrong.

$ git diff --ignore-blank-lines       # on that same file from §4
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
...                                   # nothing was suppressed at all

$ git diff -w --ignore-blank-lines    # even combined with -w
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;
+                                     <- the blank line is still here
     log_level = info;
 }

# yet on a file where only blank lines changed, it works completely
$ git diff blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta

$ git diff --ignore-blank-lines blanks.txt
                                      # no output. fully suppressed

$ git diff -w blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta                                # -w cannot remove blank lines

The rule works out like this. --ignore-blank-lines judges per hunk, not per line. If every change in a hunk is a blank line, the hunk is discarded whole; if even one substantive change is mixed in, the entire hunk is emitted as is. That makes it perfect on a commit that only tidied blank lines, and useless on a commit where blank lines and logic changed in the same place.

  • When reviewing a commit where a formatter only touched blank-line rules, --ignore-blank-lines is the strongest tool there is. Everywhere else, lower your expectations
  • -w and --ignore-blank-lines cover non-overlapping territory, so pairing them can reasonably be treated as the default
  • The same per-hunk rule applies to GNU diff's -B. §16 confirms the identical behaviour

Deciding numerically whether a change is mostly formatting

What you usually want to know before starting a review is one thing: how many lines of real change are actually in here. That takes two commands and no eyeballing, because the stat options honour -w faithfully.

# three files: a.js is pure reformat, b.js is reformat + 1 real line, c.js is real only
$ git diff --shortstat
 3 files changed, 51 insertions(+), 51 deletions(-)

$ git diff -w --shortstat
 2 files changed, 2 insertions(+), 2 deletions(-)

# per file
$ git diff --numstat
30	30	a.js
20	20	b.js
1	1	c.js

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # a.js dropped off the list

$ git diff -w --stat
 b.js | 2 +-
 c.js | 2 +-
 2 files changed, 2 insertions(+), 2 deletions(-)

Fifty-one lines against two. That ratio alone decides how the change should be handled. But there is a trap here. --name-only ignores -w. That is what catches people who wanted a file list for automation.

$ git diff -w --name-only
a.js
b.js
c.js                                  # a.js shows up despite being whitespace only

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # this one is accurate

# to classify files reliably, use the exit code
$ git diff --quiet -w -- a.js; echo $?
0                                     # 0 = nothing but whitespace changed
$ git diff --quiet    -- a.js; echo $?
1                                     # 1 = bytes did change
$ git diff --quiet -w -- c.js; echo $?
1                                     # there is a real change

$ for f in $(git diff --name-only); do
>   if git diff --quiet -w -- "$f"; then echo "  whitespace : $f"; else echo "  real       : $f"; fi
> done
  whitespace : a.js
  real       : b.js
  real       : c.js

That last form, --quiet combined with -w, is the most useful one in practice. The answer arrives as an exit code, which means a hook or a CI job can filter out whitespace-only files automatically. When a file list is what you need, take the third column of git diff -w --numstat.

git blame -w - when a formatter eats the history

The second casualty of whitespace change is not the diff but blame. If you run blame to work out why a line ended up the way it did, and every line points at a formatter commit from six months ago, that history has effectively been erased.

To check, build a repository with three commits. Alice writes the logic, Bob runs the formatter, Carol fixes an actual bug. Bob's commit does nothing but convert tabs to four spaces and single quotes to double quotes. Not one bit of behaviour changes.

$ git log --oneline
db3b770 fix: include zero total          <- Carol
007e2a5 style: run formatter over the repo   <- Bob
5c720df feat: aggregate rows             <- Alice

$ git blame --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
007e2a59 (Bob   2026-02-02 2)     total = 0
007e2a59 (Bob   2026-02-02 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# five of seven lines now belong to Bob, who touched no logic at all.

$ git blame -w --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# three lines came back to Alice; the three with changed quotes are still Bob's.

The limit of -w shows up exactly here. -w ignores whitespace and nothing else. Lines that were only reindented came back, but lines where a quote character changed in the same commit are not whitespace changes, so they stay with Bob. And real formatters almost always change whitespace and non-whitespace together: quote style, line-wrap position, trailing commas, bracket alignment.

Which means -w cannot erase a formatter commit. A half-cleaned blame is arguably worse, because the lines that did come back convince you the job is done. The real answer lives somewhere else.

.git-blame-ignore-revs - dropping a commit from blame

Git can skip specific commits entirely when computing blame. Lines the skipped commit produced are attributed back to the commit before it. By convention the repository root holds a file named .git-blame-ignore-revs listing the SHAs to skip.

$ cat .git-blame-ignore-revs
# 2026-02-02 repo-wide formatter run (tabs -> 4 spaces, quote style)
# no behaviour change; skip when running blame
007e2a5974bd7a4c76aba4ee206b690c1410c23d

# option 1. one-off - hand it the path directly
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
^5c720df (Alice 2026-01-10 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
^5c720df (Alice 2026-01-10 6)         return {"total": total}
^5c720df (Alice 2026-01-10 7)     return {"total": 0}

# option 2. permanent - put it in the config
$ git config blame.ignoreRevsFile .git-blame-ignore-revs
$ git blame --date=short report.py
                                      # output identical to the above

# option 3. a single commit, no file
$ git blame --ignore-rev 007e2a5974bd7a4c76aba4ee206b690c1410c23d --date=short report.py
                                      # again, the same output

Where -w left three lines with Bob, this time all seven found their proper owner. Six to Alice, one to Carol for the line she actually fixed. That is the true history of the file.

Comparisongit blame -w.git-blame-ignore-revs
What it ignoresWhitespace differencesEntire named commits

Being committed alongside the repository is the biggest practical win. One person adds a SHA and the whole team's blame is fixed at once. GitHub stated in its changelog of 24 March 2022 that the blame view recognises a .git-blame-ignore-revs file in the repository root. So this single file cleans up both the local CLI and the web view.

What trips people up with ignore-revs

The feature itself is simple, but a few things catch you the first time. All of these were reproduced directly.

# 1. the SHA must be all 40 characters
$ git rev-parse --short HEAD~1
007e2a5
$ echo 007e2a5 > short-revs
$ git blame --ignore-revs-file=short-revs report.py
fatal: invalid object name: 007e2a5
                                      # an abbreviated hash kills blame outright

# 2. you can mark the skipped lines
$ git config blame.markIgnoredLines   true
$ git config blame.markUnblamableLines true
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df  (Alice 2026-01-10 1) def load(rows):
^?5c720d  (Alice 2026-01-10 2)     total = 0
^?5c720d  (Alice 2026-01-10 3)     for r in rows:
^?5c720d  (Alice 2026-01-10 4)         total += r["amount"]
db3b770e  (Carol 2026-03-05 5)     if total >= 0:
^?5c720d  (Alice 2026-01-10 6)         return {"total": total}
^?5c720d  (Alice 2026-01-10 7)     return {"total": 0}
                                      # a question mark = line inferred past an ignored commit

# 3. how to judge which commits belong on the list
$ git show --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 12 ++++++------
 1 file changed, 6 insertions(+), 6 deletions(-)

$ git show -w --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 6 +++---
 1 file changed, 3 insertions(+), 3 deletions(-)
                                      # if -w halves it, whitespace dominates that commit

The first one catches people most often. Paste a commit SHA out of habit as an abbreviated hash and blame simply refuses to run. Pull the full SHA with git rev-parse HEAD and paste that instead.

  • Comments go on lines starting with #. Without a note explaining why a commit is on the list, nobody will dare touch the file months later
  • Before adding anything, confirm the commit really is formatting only. That is what git show -w --stat in item 3 is for. If the line count does not shrink under -w, that commit contains real changes
  • Listing a commit that contains real changes hides the author of those changes forever. That is worse than a polluted blame
  • Turning on blame.markIgnoredLines makes it visible which lines are inferred. It is worth enabling when introducing the file to a team, since it makes the explanation easier
  • The file only affects blame. git log and git diff are untouched, so no history is being removed

Final newlines and No newline at end of file

The last line of the §4 output was \ No newline at end of file. That marker means the final byte of the file is not a newline. It is a statement of fact, not an error.

It exists because of how a text file is defined. POSIX defines a line as a sequence of zero or more characters terminated by a newline, and a text file as a series of such lines. Under that definition, a trailing fragment with no newline is strictly not a line. That is why wc -l can count one fewer, and why concatenating two files can weld the last line of one onto the first line of the next.

$ git show HEAD:eof.txt | tail -c 12 | xxd
00000000: 650a 7477 6f0a 7468 7265 650a            e.two.three.
$ tail -c 12 eof.txt | xxd
00000000: 6e65 0a74 776f 0a74 6872 6565            ne.two.three
                                      # one trailing 0a is gone. that is the whole change

$ git diff
@@ -1,3 +1,3 @@
 one
 two
-three
+three
\ No newline at end of file
                                      # an identical-looking line as a delete plus an add

$ git diff --ignore-space-at-eol; echo "exit $?"
exit 0                                # hidden completely
$ git diff -w
                                      # -w gives no output either
$ git diff --check; echo "exit $?"
exit 0                                # --check does not treat this as an error

Those last two lines matter. git diff --check catches trailing whitespace but does not catch a missing final newline. So do not assume a commit hook running only --check covers this case. This one belongs to editor configuration.

Line endings flip the entire diff

When line endings switch between CRLF and LF, every line in the file becomes a modification, because an invisible byte is added to or removed from each one. Why CRLF and LF diverged in the first place, and how to pin them down with .gitattributes, is covered in the article on line endings. Here we look only at how they contaminate a diff.

$ cat -A notes.txt                    # whole file converted to CRLF, one word edited
line one^M$
line two^M$
line THREE^M$                         <- the only real change is here
line four^M$

$ git diff --stat
 notes.txt | 8 ++++----
 1 file changed, 4 insertions(+), 4 deletions(-)
                                      # a four-line file is reported as entirely rewritten

$ git diff
@@ -1,4 +1,4 @@
-line one
-line two
-line three
-line four
+line one
+line two
+line THREE
+line four
                                      # nothing on screen tells you which line is real

$ git diff --ignore-cr-at-eol
@@ -1,4 +1,4 @@
 line one
 line two
-line three
+line THREE
 line four                            # down to a single line

$ git diff -w
                                      # -w does the same. CR is a whitespace character
  • Git has --ignore-cr-at-eol for precisely this case. Narrower than -w, and therefore safer
  • GNU diff has --strip-trailing-cr for the same purpose. §16 shows it in action
  • The real fix is to nail down line endings for the repository in .gitattributes. These options relieve the symptom, not the cause

Stopping the noise at the source

Everything so far removes noise that already exists from the screen. The better move is to keep it out of commits in the first place. There are three layers, each intercepting at a different point.

The first layer is the editor. Put an .editorconfig in the repository root and editors that support it clean up on save. Support varies by editor, so this is a convention rather than an enforcement.

$ cat .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = 4
trim_trailing_whitespace = true       # strip trailing whitespace
insert_final_newline = true           # guarantee a final newline

[Makefile]
indent_style = tab                    # here the tab is syntax

[*.md]
trim_trailing_whitespace = false      # two trailing spaces mean a line break

The second layer is a pre-commit check. git diff --check works with no configuration and exits with status 2 when it finds a problem, which makes it drop straight into a hook or a CI job.

$ cat -A ws.txt
ok line$
trailing spaces here   $
trailing tab here^I$
 ^Ispace before tab$
$
$

$ git diff --check
ws.txt:2: trailing whitespace.
+trailing spaces here
ws.txt:3: trailing whitespace.
+trailing tab here
ws.txt:4: space before tab in indent.
+ 	space before tab
ws.txt:5: new blank line at EOF.
$ echo $?
2                                     # an exit code a hook can use as is

$ git config --get core.whitespace
                                      # empty = the built-in defaults apply
                                      # blank-at-eol, space-before-tab, blank-at-eof

The third layer is correction at apply time. When someone sends a patch carrying trailing whitespace, git apply --whitespace=fix strips it while applying.

$ tail -3 patch.diff | cat -A
 ok line$
 clean tail$
+new line with trailing ws   $        <- the patch carries trailing whitespace

$ git apply --whitespace=fix patch.diff
patch.diff:8: trailing whitespace.
new line with trailing ws
warning: 1 line applied after fixing whitespace errors.

$ cat -A ws.txt
ok line$
clean tail$
new line with trailing ws$            <- applied with the whitespace removed

The habit of separating formatting commits

Even knowing every option above, the thing with the largest effect is not a tool but the habit of splitting commits. The reason is simple. An option has to be remembered and typed by every reviewer every time; a commit that was already split requires remembering nothing.

The rule is one sentence. A formatter run goes into a commit that contains nothing else. It does not share a commit with logic changes. Doing that solves three problems at once: reviewers can skip the formatting commit without opening it, blame needs only that one SHA in .git-blame-ignore-revs, and if something goes wrong the scope of the revert is unambiguous.

# recovering when the formatter already ran and got mixed with logic changes
$ git stash                           # set the current work aside
$ prettier --write .                  # run the formatter across the repository
$ git commit -am "style: run formatter (no behaviour change)"
$ git rev-parse HEAD >> .git-blame-ignore-revs
$ git stash pop                       # bring the logic changes back
$ git commit -am "fix: the actual change"

# one line to confirm a staged commit really is formatting only
$ git diff --cached --quiet -w && echo "whitespace only" || echo "contains real changes"
  • When adopting a formatter, run it over the whole repository at once. Doing it file by file produces dozens of formatting commits and makes the ignore list unmanageable
  • State in the commit message that behaviour did not change. For whoever judges that commit months later, that one sentence is all there is
  • Splitting commits is not a courtesy to reviewers; it is leaving the history in a readable state. Review lasts a few days and history lasts years

Where git is not available - GNU diff

Plenty of situations are outside a git repository, such as comparing two copies of a config file on a deployment server. GNU diff has the same options under nearly the same names. The per-hunk behaviour of -B matches git exactly too, so that gets checked here as well.

  • If CRLF is involved, add --strip-trailing-cr. Without it every line reads as different
  • When judging by exit code, use -q. Output collapses to one line, which is easier to handle in a script

Where whitespace carries meaning

After applying everything in this article, one risk remains. Making -w a habit means missing real changes in files where whitespace is syntax. This is not hypothetical; it reproduces.

$ git diff                            # one line moved out of a loop in a Python file
@@ -2,7 +2,7 @@ def total(rows):
     s = 0
     for r in rows:
         s += r
-        print(s)
+    print(s)
     return s

$ git diff -w
                                      # no output. -w says nothing changed

$ git diff -w --stat
                                      # empty here too

# yet the actual behaviour differs like this
$ python total.py                     # before
1
3
6
$ python total.py                     # after
6

The output went from three lines to one. Program behaviour changed unmistakably, and git diff -w reports that nothing changed at all. In Python, indentation is not formatting; it is the block structure itself.

TargetWhat whitespace meansUnder -wRecommendation
PythonIndentation depth is block structureHides block moves entirelyNo -w. Use --ignore-space-at-eol if needed
MakefileA recipe line must start with a tabHides a tab turning into spacesNo -w
YAMLIndentation is the nesting structureHides a key moving under a different parentNo -w
MarkdownTwo trailing spaces = a line breakHides a lost line breakEven --ignore-space-at-eol is risky
Go, Java, C familyWhitespace is only a separatorSafe-w is fine as a default
String literals, test fixturesWhitespace is part of the dataHides changed expectationsHandle as per-file exceptions

A workable rule for practice looks like this. Use -w only to clear noise when starting a review, and take one more pass with no options before approving. The first pass decides where to look; the second confirms nothing was missed. The moment those two passes are collapsed into one, every risk in the table above comes back to life.

Handling bulk formatting in review

Most review tools have a whitespace-ignoring view, and turning it on cleans up the screen. But something remains. Line comments are usually anchored to original line numbers, so when formatting shifts lines, older comments end up in the wrong place. And as §9 showed, blame pollution is not fixed by a display option.

So when bulk formatting arrives welded to logic changes, asking for a split is the better move. Making the request with numbers rather than feelings or taste keeps the conversation short. The commands in §8 produce those numbers.

  • Paste the two lines from git diff --shortstat and git diff -w --shortstat. A contrast like 51 lines against 2 needs no explanation
  • Include the list of whitespace-only files from git diff -w --numstat. Those files have nothing to review
  • Frame the request as splitting the commit, not reverting it. Read as an argument against formatters, it moves the discussion off the point
  • Include, in the same request, adding the separated formatting commit's SHA to .git-blame-ignore-revs. Otherwise the blame problem stays
  • Conversely, approve pure formatting commits fast. Asking for a split and then sitting on the result teaches everyone not to bother splitting next time
  • If the formatter config is committed and CI checks it, the contents of a formatting commit are not for humans to review at all. The only thing to review is whether the config file changed

Summary

The whitespace noise problem splits into two layers: removing what already exists from the screen, and preventing it from being created. The first is nearly finished by four options. Line ends only, --ignore-space-at-eol; indentation conversion as well, -b; newly introduced indentation on top of that, -w; and for blank-line cleanup commits, --ignore-blank-lines. The first three nest inside each other and only the last one has a different character.

Blame is a separate problem. §9 established that -w cannot erase a formatter commit. The actual answer is to write the commit's full 40-character SHA into .git-blame-ignore-revs and set blame.ignoreRevsFile. Because the file is committed with the repository, adding it once fixes it for the whole team.

And the second layer, prevention, ends up mattering more. Clean up at save time with .editorconfig, put git diff --check in a commit hook, and ship formatter output as a commit containing nothing else. With those three in place, there is rarely any need to remember the options at all. One caveat survives all of it: in front of Python, YAML and Makefiles, put -w down. There, whitespace is not formatting. It is code.
