「公式サポート対象プラットフォーム」が実際に約束していること - ティア制度で読むサポートの大きさ

動くということと、壊れたらリリースを止めるということは別の約束だ

2026年8月31日 開発・インフラ

はじめに: 「サポートする」の一言に押し込められているもの

新しいアーキテクチャの機材が一台届いた、社内の標準イメージに新しいプラットフォームを入れるか検討している、あるいはリリースノートで「これより公式サポート」の一行を読んだ。その次に確認すべきは「動くか動かないか」ではない。壊れたとき誰が直すことになっていて、その失敗はリリースを止めるのかである。

この二つの答えはプロジェクトごとに文書に書かれている。問題は、その文書を開かずに「公式サポート」という言葉だけを読んだときに起きる。実際この言葉は少なくとも三つの異なる大きさで使われている。リリースを止めるほど強い約束のこともあれば、24時間以内に直すという中間の約束のこともあり、buildbot を回してあるので壊れれば見えはするという約束のこともある。三つ目も「公式サポート」と呼ばれる。

ここで扱うのはその大きさの違いだ。どのアーキテクチャが優れているという話も、どのメーカーがどうという話もしない。サポートティアという制度が何のために存在し、各ティアの文言が実際に何を約束し、その約束がどこで終わるのかが軸である。

今回決まったこと - 確認できた範囲

まず契機を正確な大きさに切り出す。CPython が64ビット RISC-V Linux を Tier 3 のサポート対象に引き上げた。確認できる範囲は次までだ。

  • 対象 — PEP 11 の Tier 3 一覧に riscv64-unknown-linux-gnu(glibc, clang/gcc)が載っている
  • 担当者 — 同じ一覧に Stan Ulbrych、Emma Smith の二名が連絡先として記載されている
  • 機材 — 発表文によれば RISE Project が CPython のために RISC-V マシンを複数台提供した
  • 発表 — Python Insider、2026年8月24日、Stan Ulbrych による。執筆者の作業は Sovereign Tech Agency のフェローシップの支援を受けたと記されている
  • 次の段階として書かれていること — RISE のランナーを通じて CI に直接統合すること、長期的には Tier 2 への昇格、そしてアーキテクチャ固有の最適化

ここまでが文書に書かれていることだ。発表文自身も最後に範囲を絞っている。CPython は Python エコシステムの一部にすぎず、パッケージ・コンパイラ・ツール・インフラが一緒に付いてこなければならない、という一文である。この一行がこの記事の後半の主題でもある。

なぜティアが存在するのか

ティア制度は官僚的な仕組みに見えるが、実は算数の問題に対する答えだ。サポートすべき組み合わせは掛け算で増える。命令セット × libc 実装 × コンパイラ × カーネル版 × ビルドオプションである。一方それを直せる人は足し算でもなかなか増えない。

PEP 11 が自ら述べる背景も同じ場所にある。時間が経つにつれ CPython のソースには、ある時点で特定のプラットフォームで使うために必要だと判断されたプラットフォーム固有のコード片が蓄積してきた、というものだ。問題は、そのコードがまだ必要なのか、まだ動くのか、誰が見ているのかを誰も知らない状態になることにある。

ティアを分けないと、失敗は二方向に同時に起きる。

  • 過剰な約束 — 「すべてサポートする」と書けば、誰も直せないプラットフォームのバグ報告が積み上がり、応答できない issue が信頼を削っていく
  • 過少な約束 — 何も書かなければ、実際にはよく動くプラットフォームでさえ「使ってよいか」を判断する根拠がなく導入が止まる
  • 整理できない — 何を捨ててよいかの基準がなければ、古いプラットフォームのコードが永久に残りすべてのリファクタリングの費用を押し上げる

そこで PEP 11 はサポートをティアに分け、各ティアはそれぞれ異なる要件を持ち、そこから異なる約束が生まれると書く。この文の向きが重要だ。要件が先で約束はその結果である。 人と機材をどれだけ確保したかが約束の大きさを決めるのであって、先に約束をして後から人を探す構造ではない。

各ティアが実際に約束していること

文言のまま書き写すとこうなる。注目すべきは最後の二列だ。応答期限とリリース阻止がティアの実質を決めている。

ティア要求される検証体制誰が責任を負うか応答期限リリース阻止
Tier 1 CI。CI の失敗がリリースを止める コア開発者全員が main を、したがってこれらのプラットフォームを動く状態に保つ責任を負う main を壊す変更はマージ自体が許されず、壊れたものは即座に修正または差し戻す 止める
Tier 2 信頼できる buildbot が必要 コア開発者2名以上がサポートを引き受けると登録 壊した変更は24時間以内に修正または差し戻す 止める
Tier 3 信頼できる buildbot が必要 コア開発者1名以上がサポートを引き受けると登録 失敗に対する応答期限はない 止めない
非サポート なし コアチームはサポートしない 該当なし 該当なし

先に一つ正しておく。ティアは四段階ではない。 PEP 11 が定義するティアは三つで、上の三つの一覧にないすべてのプラットフォームはコアチームがサポートしない状態に分類される。非サポートは排除とは違い、該当プラットフォーム向けのコードもコアチームに最小限の保守負担しか課さず、寄稿者本人よりはるかに多くの人に利益をもたらすときには受け入れられる。ただしそれは約束ではなく受け入れ条件だ。

検証体制の列も見過ごせない。Tier 1 に書かれているのは CI で、Tier 2・3 に書かれているのは buildbot だが、この二つは回る時点が違う。 Tier 1 の条項がmain を壊す変更はマージが許されないと書けるのは、検査がマージの前に回るからだ。一方 buildbot はマージされた後の枝を定期的にビルドして結果を報告する装置である。だから同じ「自動で検査する」でも、前者は門であり後者はアラームだ。今回の発表文が CI への直接統合を今後の課題として別に挙げているのも、この違いによる。

表を縦に読むと、ティア間の間隔が均等でないことも見えてくる。Tier 1 と Tier 2 は「リリースを止める」を共有し、担当範囲と期限だけが違う。一方Tier 2 と Tier 3 の間では約束の種類そのものが変わる。 期限が24時間から48時間に延びるのではなく期限が消え、リリース阻止が弱まるのではなくなくなる。ここが実際の境界線だ。

Tier 3 が意味しないこと

この記事の本論だ。「公式サポート対象プラットフォームとして追加された」という文は、たいてい下の左の欄のように読まれる。規定が定めたのは右の欄である。

「公式サポート」が与える印象Tier 3 条項が実際に定めたこと
リリース前にこのプラットフォームで試験が通らなければならないこのプラットフォームの失敗はリリースを止めない
壊れればすぐ直される失敗に対する応答期限はない
コアチーム全体がこのプラットフォームを見ている登録された担当者が1名以上いれば要件を満たす
マージ前にこのアーキテクチャで検査が回る要求されるのは buildbot だ。発表文が CI 統合を今後の課題として挙げた理由がここにある
このプラットフォーム向けの配布物が一緒に出るティア文書は配布物を扱っていない

誤解を生む箇所は語ひとつだ。「サポート」が「保証」として読まれる。 しかし Tier 3 が要求したのは検証装置と連絡先であって結果ではない。このティアが実際に生み出す変化はこの三つである。

  • 回帰が静かに積み上がらない — buildbot が回っていれば、壊れた時点とコミットが記録として残る。半年後に「いつから駄目だったのか分からない」にはならない
  • 報告先ができる — 名前の載った担当者がいるということは、issue が持ち主のいないまま漂わないということだ
  • プラットフォームコードが整理対象から外れる — 非サポートの状態では関連コードはいつでも削除候補だが、一覧に載ればその根拠が消える

したがって正確な要約はこうだ。Tier 3 は「動くだろう」ではなく「壊れれば見えるだろう」を約束している。 小さくない約束だが、本番導入の判断根拠として使うには扱っている層が違う。

ティアは上がりも下がりもする

ティアをコードの属性だと誤解すると、次の事実が理解できなくなる。ソースが一行も変わらなくてもティアは下がりうる。 要件が人と機材だからだ。

  • 降格の条件 — 現在のティアの要件が相当期間満たされなくなったとき、リリースマネージャーまたはステアリングカウンシルの判断で下位ティアに落とす
  • 実質的な引き金 — 担当者がプロジェクトを離れる、buildbot の機材が止まる、結果が赤のまま残る、の三つだ。いずれもコード品質と直接の関係はない
  • ティアから完全に外れるとき — システム名、もはやサポートしない最初のリリース番号、過去のサポートコードを実際に削除する最初のリリースを文書に残すよう定められている
  • 利用者への知らせ方 — 当該プラットフォームにインストールを試みるとビルドが警告を出すよう変更し、configure にも非サポートのプラットフォームである旨の警告を出させる

昇格も対称だ。Tier 3 から Tier 2 に上がるには、担当するコア開発者が1名から2名になり、24時間以内に修正または差し戻すという約束が付き、buildbot が信頼できる状態で維持されなければならない。いずれも人の時間を要求する条件であり、だから昇格は技術的成熟よりも継続的な人員確保の問題に近い。

この構造が分かれば、今回の知らせを読む正しい時制も決まる。「このプラットフォームはもう安定している」ではなく、「現在、登録した人と回っている機材がある」が正しい。前者は未来を語り、後者は現在を語る。ティア制度が保証するのは後者だけだ。

使う側が確認すること - 言語が動けばエコシステムが動くわけではない

ここが最もよく食い違う。インタープリタのティア文書はインタープリタの移植性だけを扱う。 PEP 11 の管轄は CPython 自体であり、配布パッケージやサードパーティのツールはその範囲外だ。発表文がわざわざ「CPython はエコシステムの一部」と付け加えたのもそのためである。

実際に詰まるのは言語ではなくネイティブ拡張だ。純粋な Python コードはアーキテクチャをほとんど気にしないが、C・C++・Rust で書かれた拡張モジュールはコンパイルと配布の両方を通過しなければならない。確認はこの順序でやると抜けが出にくい。

  • 依存関係の全体を展開する — 直接依存だけでなく推移的依存まで。問題はたいてい二段下にある
  • ネイティブ拡張を選り分ける — 配布物のファイル名が純粋 Python 向けかプラットフォーム指定かで一次分類ができる
  • それぞれに対象プラットフォーム向けの成果物があるか見る — なければインストールはソースビルドに落ちる
  • ソースビルドが成立するか確認する — コンパイラ版、ヘッダ、そして数値演算ライブラリのようにアーキテクチャ別の実装を要するシステム依存があるか
  • 実行時の経路を見る — 暗号・圧縮・直列化のライブラリはアーキテクチャ別の高速化経路を別に持つことが多い。その経路がなければ動きはするが性能特性が変わる
  • CI ランナーを確保できるか見る — なければエミュレーションで回ることになりビルド時間が数倍になる。これは開発速度の問題なので静かに蓄積する
  • コンテナのベースイメージと運用ツールを見る — 基盤イメージ、エージェント、プロファイラがそのアーキテクチャで配布されるかまで見て初めて配備パイプラインが閉じる

整理すると判断の順序はこうだ。言語のサポートティアは必要条件であって出発点ではない。 言語が動かなければ残りを見る必要がない、という意味でのみ先に来る。逆に言語が動くからといって、その下の四つの層が付いてくるわけではない。

あらかじめ作られたものと、ソースからビルドされるもの

新しいアーキテクチャで特に痛むのがここだ。規格側の事情を見ると、ボトルネックは以前ほどではない。

  • 旧方式の Linux 配布物タグはアーキテクチャを文書に列挙していた。公式規格文書が記す manylinux2014 の一覧は x86_64、i686、aarch64、armv7l、ppc64、ppc64le、s390x で、riscv64 はここにない
  • PEP 600 がこの構造を変えた。タグは manylinux_${GLIBCMAJOR}_${GLIBCMINOR}_${ARCH} 形式で、${ARCH} は Python が自ら報告するプラットフォーム値をそのまま使う
  • その結果、新しいアーキテクチャのために新しい PEP を書く必要がなくなった。 PEP 600 自身がこれを設計目標として書いている。旧方式ではアーキテクチャを一つ追加するたびに新しい PEP を書き、PyPI と pip のコードベースが新しいタグを認識するよう直し、新しい pip が利用者に行き渡るのを待つという、かなり手間のかかる過程を経る必要があった

つまり規格はすでに開いている。残ったボトルネックは文書ではなく誰がその配布物を作って上げるのかだ。そのためには各パッケージの保守者が自分の CI にそのアーキテクチャのランナーを付けねばならず、それはまた機材と人の問題に戻る。ティア制度がぶつかるのと同じ壁である。

配布物がなくソースビルドに落ちたとき、実際に変わることはこうだ。

  • インストール時間の単位が変わる — 秒単位だったものが分や時間の単位になる。コンテナを頻繁に作るパイプラインでは、この費用が毎回発生する
  • イメージにビルドツールが入る — コンパイラとヘッダが最終イメージに残れば、サイズと点検対象がともに増える
  • 失敗する箇所が増える — ヘッダの欠落、コンパイラ版の不一致、ビルド中のメモリ不足は、配布物を受け取って使うときには存在しない失敗の型だ
  • 再現性が弱まる — あらかじめ作られた配布物はハッシュで固定されるが、ソースビルドの結果はビルド環境に左右される。同じロックファイルが二台で別のバイナリを作りうる
  • 閉域網では特に痛い — 内部ミラーにソースだけあって配布物がなければ、ビルド依存まですべてミラーリングしなければならない

他のプロジェクトは違う分け方をした

同じ問題を前に他の言語プロジェクトもティアを置いているが、何をティアの軸に選んだかが互いに違う。 優劣の問題ではなく、各自が最もよく質問されることの違いとして読むほうが正確だ。公開文書で確認できる範囲で三つだけ並べる。

プロジェクト最上位ティアが約束すること中間ティア最下位ティアティアを分ける軸
CPython CI の失敗がリリースを止め、コア開発者全員が維持の責任を負う buildbot + 担当者2名 + 24時間以内の修正。失敗はリリースを止める buildbot + 担当者1名。期限がなくリリースを止めない 応答期限とリリース阻止
Rust 動作が保証されると考えてよいティア。公式バイナリを配布し、変更のたびにビルドと試験通過を自動で検証する ビルドが保証される。標準ライブラリの公式バイナリを出し自動ビルドを回すが、試験は常に走るわけではないので動作するビルドが保証されるわけではない コードにサポートが入っているだけで、プロジェクトが自動でビルドも試験もしないため動くかもしれないし動かないかもしれない。公式ビルドは提供されない 自動化がビルドまでか試験までか
Go 壊れたビルドがリリースを止める。寄稿者全員が事実上の責任を負い(壊したなら直すか直せる人を見つける)、ビルダー機材を Go チームが所有することを要求する それ以外のポートは、壊した変更が必ずしも差し戻されるとは限らない。1.N で壊れたままなら 1.N+1 で削除を選ぶことができる リリース阻止とビルダー機材の所有

三つの文書を重ねると、表現は違っても同じ場所に収束するものが三つある。

  • 機材が前提だ。 三者とも自動検証の装置を要求し、Go はそもそもビルダーマシンの所有主体まで要件に書いている
  • 名前の付いた人が必要だ。 Go は新しいポートにポート維持者2名とビルダー維持者1名を指名し同意を得るよう求め、CPython はティアごとに担当コア開発者の人数を定める
  • 最下位ティアは動作を約束しない。 表現が違うだけで「動くかもしれないし動かないかもしれない」が共通の文言だ

この知らせをどう読むか

誇張と貶め、どちらも原文から遠ざかる方向だ。まず誇張側の誤読は「これで本番に使ってよい」に移すことである。Tier 3 の条項にそのような意味はない。応答期限がなくリリースを止めないという二つの文が、その大きさを自ら語っている。

逆に貶め側の誤読は「ティアが低いから意味がない」だ。これも違う。一覧になかった状態とある状態の間には実質的な差があり、その差は上で見た三つ(buildbot・担当者・整理対象からの除外)である。非サポートの状態では、回帰がいつ生じたのかさえ分からない。

実際に変わることと変わらないことを分けておくとこうなる。

  • 変わること — 回帰の発見時点が早まり、issue に受け手ができ、プラットフォームコードが削除候補から外れ、他のプロジェクトが参照できる先例が一つできる
  • 変わらないこと — リリースゲート、応答期限、配布物の入手性、コンテナとツールチェーン、そして性能だ。アーキテクチャ固有の最適化は発表文自身が今後の課題として挙げている
  • 時制を守ること — ティアは現在確保されている人と機材の状態であって、未来への約束ではない

もう一つ。この種の知らせはたいてい決定ではなく過程の中間地点だ。ティア一覧に名前が載るのは、誰かが機材を調達しビルドを付け失敗を一つずつ直した後に起きることであって、その逆ではない。だから「いつから使えるのか」と問う代わりに「今何が確保され何が残っているのか」に読み替えると判断が楽になる。今回、確保されたのは機材と担当者と一覧掲載であり、残りとして発表文自身が挙げたのは CI 統合と上位ティアと最適化である。残りが文書に書かれていること自体が信頼できる合図でもある。すべて済んだと書かれた発表文よりはよい。

実務で使う基準を一つだけ残すならこれだ。今後「公式サポート」の一行を読んだら、そのプロジェクトのティア文書を開いて二行だけ探せ。「失敗はリリースを止めるか」と「応答期限はあるか」である。たいていこの二行の中にそのサポートの実際の大きさが全部入っており、残りの説明はその二行の脚注だ。

確認できなかったこと

本文に入れなかったものをここにまとめておく。空欄を推測で埋めるのが最も悪い。

  • ステアリングカウンシルの承認日と一覧反映日 - 複数の要約に8月20日と22日が出回っているが、その日付を記した一次文書を開けなかったので書かなかった。本文の日付は発表文の掲載日である
  • buildbot の台数・仕様・稼働率 - 何台がどんな構成でどう回っているかを特定できる資料を確認できなかった
  • 当該アーキテクチャ向けパッケージ配布物の実際の普及率 - パッケージごとに異なり全体を見られる公開集計が見つからなかったため数値を書かなかった
  • Tier 2 昇格の時期 - 発表文は目標としてのみ記しており、要件充足の計画や日程は書かれていない
  • 性能 - アーキテクチャ間の比較数値は書いていない。同一条件で測定された公開資料を確認できず、確認していない性能比較は作り話と変わらない

結論: 三つの文に縮めると

第一に、ティアはコードの状態ではなく人の約束を書いたものだ。 要件が buildbot と担当者である以上、ソースがそのままでも人が抜ければティアは下がる。第二に、Tier 3 が定めたのは「動く」ではなく「壊れれば見える」だ。 応答期限がないこととリリースを止めないことという二つの文言が、その境界を正確に引いている。第三に、使う側の判断は言語ではなく依存関係から始まる。 インタープリタが動くことと自分のスタックが動くことは別の問題で、ティア文書は前者だけを管轄する。

一つだけ実行するならこれを勧める。いま運用中のサービスの依存関係一覧を開き、ネイティブ拡張を持つパッケージだけを選んで数えてみることだ。その数が新しいアーキテクチャへ移すときに実際に検討すべき項目の数であり、言語のサポートティアはその一覧の先頭に付く一行にすぎない。
