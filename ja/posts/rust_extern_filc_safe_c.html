extern C の一行が消す保証 - Rust FFI 境界を埋める方法とその代償

ラッパーもバインディング生成器も契約を検査できない、ならば境界そのものを縮められるのか

2026年8月16日 開発・インフラ

序論: コンパイルは通ったが、何が切れたのか分からないとき

画像デコーダにせよ暗号ライブラリにせよ、成熟した C 実装がすでにある機能を Rust プロジェクトに組み込むとき、実際に手を動かすコードは十行ほどだ。extern ブロックに関数シグネチャを書き、ビルドスクリプトでリンクし、薄いラッパーをかぶせれば終わる。コンパイルも通るしテストも通る。

しかしその瞬間にプロジェクトの性質が変わる。それまで Rust コンパイラがコード全体にかけていた保証 — 解放済みメモリを読まない、同じデータへの可変参照が二つできない、データ競合が起きない — はコンパイラが見えるコードに限って成り立つ。リンクされた C オブジェクトはその範囲の外側にある。

この記事では、その境界で正確に何が切れるのか、これまでその隙間を埋めるために使われてきた手法がそれぞれ何を防ぎ何を防げないのか、そして2026年8月に出てきた extern "fil-c" 提案がその問題をどう違う形で切ろうとしているのかを扱う。先に断っておくと、その提案はまだ採用された機能ではない — 段階は後段で正確に示す。

この記事が扱わないことも明確にしておく。「C を Rust で書き直すのか、C をそのままにして強化するのか」という路線論争は メモリ安全性の絶対主義者たち - Rust と Fil-C の論争、何が現実的か ですでに扱った。ここではその勝敗ではなく、二つの世界が出会う地点そのものを見る。

1. FFI における unsafe の意味 - コンパイラが検査をやめる地点

1.1 宣言は検査されるコードではなく人間の主張である

Rust の安全性が成り立つ根拠は単純だ。コンパイラが所有権と寿命とエイリアス規則をコード全体に対して検査するということである。この検査は検査対象をすべて見られるときだけ意味を持つ。

extern ブロックはその前提が崩れる場所だ。そこに書いたシグネチャはコンパイラが確認した事実ではなく開発者が行う主張である。引数の個数も整数幅も構造体のフィールド順も検証されない。間違っていればそのままコンパイルされそのまま実行され、問題ははるか後で見当違いの場所で表面化する。

Rust 2024 エディションが extern ブロック自体に unsafe を付けるよう文法を変えたのも、この性質を文法に見せるためだ。RFC 3484 でまとめられ、2024 以降のエディションでは unsafe extern が必須になっている。ブロック内の個別項目には safe 修飾子を付けて安全に呼べると示せる — ただしその表示もまた人間が責任を負う主張であり、機械が確認した結果ではない。

// 概念例。動作を確認したコードではない。
unsafe extern "C" {
    // このシグネチャがヘッダと一致するかコンパイラは知らない
    fn img_open(path: *const c_char) -> *mut ImgCtx;

    // safe を付けると呼び出し側に unsafe ブロックが要らなくなる。
    // 検査が生まれるのではなく、責任をここで負うという表示だ。
    safe fn img_version() -> u32;
}

1.2 境界で実際に切れる保証

「メモリ安全性が壊れる」という言い方は大づかみすぎる。具体的に何が検査対象から外れるのかを分けると、対策も分かれる。

  • 寿命 — C が返したポインタがいつまで有効か。次の呼び出しまでなのか、コンテキストが生きている間なのか、静的なのかは関数シグネチャにない。
  • 所有権と解放責任 — 返されたバッファを Rust が解放すべきか、専用の解放関数を呼ぶべきか、まったく触ってはいけないのか。
  • 可変排他性 — C ライブラリが内部で同じバッファのエイリアスを保持していると、Rust 側で &mut を作った瞬間に言語規則がすでに壊れている。最適化器はその規則を信じてコードを並べ替える。
  • null 許容と整列と初期化状態 — 返却ポインタが null になりうるか、返されたメモリが初期化されているか。
  • スレッド安全性 — グローバル状態を使うか、再入可能か、特定のスレッドからのみ呼ぶべきか。Send と Sync を手で実装した瞬間、その判断は全面的に人間のものになる。
  • パニックと巻き戻し — Rust のコールバックが C フレームを越えてパニックすると未定義動作になる。コールバック境界で捕まえて飲み込む処理が要る。
  • ABI レイアウト — #[repr(C)] を忘れた構造体を渡すとフィールド配置が違いうる。列挙型の値域、ビットフィールド、パディングも同類だ。
  • エラー規約 — 負値の返却か errno か最終エラー取得関数か。規約を読み違えると失敗を成功として扱って進んでしまう。

八つのうちコンパイラが一つでも検査してくれる項目はない。だから FFI の unsafe は「危険なコード」という警告というより、検査器の管轄がここで終わるという境界標識に近い。

2. これまでの対応 - ラッパーとバインディング生成器と段階的書き直し

2.1 安全ラッパー: 契約を型に書き写す

Rust エコシステムの標準的な慣行は二層構造だ。下層に生の宣言だけを収めた -sys クレートを置き、上層に安全なインターフェースを公開するクレートを置く。上層は RAII で解放責任を型に結び付け、寿命パラメータで有効区間を表現し、null 可能性を Option で表に出す。

この方式は実際にうまく機能する。よくできたラッパーの利用者は unsafe を一度も書かない。危険が消えたのではなく一か所に集まったのであり、監査対象を減らす正当な戦略だ。

限界は二か所にある。ラッパーが正しいという保証は依然として人間が与えるので、契約を読み違えればその誤読が安全なインターフェースという名前で包装されて伝播する。そして契約は変わる — C ライブラリがマイナーバージョンを上げて「このポインタは以後、次の呼び出しまでのみ有効」に動作を変えても、ラッパーはそのままコンパイルされる。

2.2 バインディング生成器: 書き写しの誤りは減るが契約はヘッダにない

bindgen のような道具は C ヘッダを解析して宣言を自動生成する。誤字、整数幅の勘違い、構造体フィールドの漏れが大きく減り、プラットフォームごとにサイズの異なる型もビルド時に取り直すのでクロスコンパイルで特に有用だ。

ただし生成器が読むのはヘッダだけであり、前節の八項目のうちヘッダに書かれているものはほとんどない。char* が null 終端文字列なのか長さを別に受け取るバッファなのか、返却ポインタを誰が解放するのかは文書にあってコンパイル可能な形にはない。生成器は正確な宣言を与えるだけで、安全なインターフェースを与えるわけではない。

2.3 段階的書き直し: 境界は消えず移動する

末端モジュールから Rust へ移す戦略は広く使われ、おおむね妥当だ。ただしこの戦略の会計は正確に見る必要がある。書き直しの途中では境界が減らずに増える。一つだった接点が移したモジュールの数だけ生まれ、接点ごとに前述の八項目が新たに発生する。

  • 移しやすいモジュールはたいてい純粋な計算コードで、もともと危険が少ない。得られる安全性に対して費やす労力が見合わない。
  • 本当に危険なコード — パーサ、プロトコル処理、古い状態機械 — は契約が文書の外にあり、それゆえ最も移しにくい。
  • 書き直しは機能凍結を要求するか、さもなくば二つの実装をしばらく併存させる。どちらにせよ組織が費用を払う。
  • 書き直しが終わるまで安全性の主張はできない。九割を移しても残り一割が同じアドレス空間にあれば、全体はその一割の安全性を持つ。

2.4 動的検査ツール: 実行した経路しか見ない

AddressSanitizer や Valgrind は実際に多くを捕まえる。ただし性格が違う。これらは実行された経路でのみ違反を見つけるので、カバレッジがそのまま保証の範囲になる。リリースビルドで有効にしておくには費用が大きく、Rust 側のインタプリタである Miri は原理的に FFI の向こうを見られない。

2.5 対応方式の比較

方式実際に防ぐもの防げないもの費用の性格
安全ラッパー(二層構造)利用側の誤用、解放漏れ、null 処理漏れ契約の誤読、上流ライブラリの動作変更、C 内部のバグ初期設計の時間 + 上流追跡の負担

表を縦に読むと共通点が見える。どの欄も「C 側のコードが規則を守る」を保証しない。すべて境界で防御するか、境界を動かすか、事後に発見する方法である。

3. Fil-C が狙う位置 - 境界を動かさずに縮める

ここで発想が一度ひっくり返る。境界で防御する代わりに境界の内側を安全にすれば境界で失うものが減る。Fil-C が立っているのはその位置だ。

Fil-C は Filip Pizlo 氏が Clang と LLVM をフォークして作った C・C++ コンパイラで、ソースを直さずに再コンパイルして実行時メモリ安全性を与える。核は三つある。

  • InvisiCaps — ポインタは見た目は64ビット値だが、実際には信頼される権能(capability)と信頼されない番地に分離されている。権能情報は別領域に保持され、アクセスのたびに範囲内かを検査する。
  • 並行ガベージコレクタ — 解放後使用を根本からなくすため、寿命管理を実行時が引き受ける。
  • 逃げ道がない — リポジトリの説明によれば Fil-C には保護を切る unsafe キーワードがない。これは利便性の不足ではなく設計上の宣言だ。

違反が発生すると、悪用可能な状態へ流れる代わりにパニックで終了する。つまり Fil-C が変えるのは「バグがなくなる」ではなく「バグの結果が任意コード実行からプロセス終了へ下がる」だ。この区別は脅威モデルを立てるとき決定的になる — 可用性は依然として攻撃対象だが、機密性と完全性は守られる。

そしてここから本題に直結する性質が一つ出てくる。Fil-C はソース互換だが ABI 互換は意図的に違う。ポインタ表現が異なるからだ。だから普通のコンパイラで作ったオブジェクトとリンクできず、プログラムとその依存関係全体を Fil-C で再コンパイルしなければならない。Fil-C 側の用語では普通の C ABI は Yolo-C と呼ばれる — Rust の extern "C" が話すのはまさにその Yolo-C だ。

4. extern fil-c 提案の現在の段階 - 何が提案され何がまだないのか

2026年8月13日、Domen Kožar 氏が自身のブログに I want extern fil-c という記事を公開した。要旨は一文に縮む — Fil-C の ABI で話す Rust FFI があってほしい、ということだ。

現在の段階を正確に書いておく。2026年8月16日の確認時点でこれは個人ブログの記事であり、rust-lang リポジトリに提出された RFC ではない。番号の付いた RFC もトラッキングイシューも実装ブランチもない。記事は仕様書ではなく呼びかけに近く、実際に来年の OceanSprint で Rust・Fil-C・Zig・Nix の関係者が集まって一緒に作ろうという提案で締めくくられている。Fil-C を Nix のクロスコンパイル基盤として整える filnix を作った Mikael Brockman 氏は参加の意思を示している。

提案が描く第一版の範囲は意図的に狭い。

  • スカラー値、コピーされた文字列とスライス、不透明ハンドル — この三つから始める。複雑なポインタグラフをそのまま渡すことは最初から扱わない。
  • 安全な Rust ラッパーを生成する。人間が契約を書き写す段階をなくすのが狙いだ。
  • C の依存グラフ全体を Fil-C でコンパイルする。部分適用は成り立たない。
  • 普通の unsafe な C へ戻る逃げ道を置かない。著者の表現では Yolo 型の穴を静かに開けないことが要点だ。

新しい ABI 文字列が必要な理由もここで明らかになる。extern "…" の文字列は呼び出し規約を選ぶスイッチだが、Fil-C はポインタ表現から違うので extern "C" では会話が成り立たない。文法の好みではなく、違う世界に話しかけるための最小の装置である。

// 仮の文法。確定したものではなく動作も確認していない。
// 提案の方向を概念として写しただけである。
extern "fil-c" {
    // Fil-C 側のポインタには権能が付いているので、
    // 範囲外アクセスは呼ばれた側でパニックとして終わる。
    fn parse_config(text: &str) -> Result<ConfigHandle, ParseError>;
}

著者自身が認める難所も明確だ。境界が難しい部分であること、そして Fil-C が普通の C との相互運用をそもそも目標に据えていないことである。Rust 側の橋がやるべきことは単に関数を呼ぶことではなく、Fil-C がプログラム全体にかけた保証を橋を架ける過程で損なわないことだ。

5. 代償その一 - 性能とメモリ、そして数字の読み方

実行時検査とガベージコレクションが付けば無料ではありえない。ただし引用される数字ごとに条件が違うので、一つにまとめると誤解が生じる。確認できたものを条件とともに書く。

出典と時点条件数値
LWN 記事 (2025-10-28)Fil-C ドキュメント基準、一般的なプログラム約4倍遅い。ポインタ使用が多いほどオーバーヘッド増
LWN 記事 (2025-10-28)ポインタを含む構造体メモリ使用量が約2倍
LWN 記事 (2025-10-28)bash 5.2.32 を Fil-C でビルドして使用性能差を体感しなかった
Zig 提案イシュー (2026-07-20)方式導入の議論中に言及された範囲1倍から6倍
extern fil-c 提案記事 (2026-08-13)具体的なベンチマーク提示なし数値なし — 検査が静的になれば税金が消えるという方向のみ記述

表をそのまま読むと、幅が大きいこと自体が情報である。検査費用はポインタをどれだけ頻繁に追うかに比例する。だから次のように分かれる。

  • 数値計算、信号処理、圧縮の内部ループのように配列インデックス中心のコードは相対的に損が少ない。
  • 連結リスト、木、グラフ走査のようにポインタを追い続けるデータ構造は大きく損をする。
  • プロセス寿命が短く I/O 待ちが支配的な道具 — シェル、ビルドスクリプト、CLI ユーティリティ — は体感差がほとんどないことがある。bash の事例がその類だ。
  • メモリ増加はスループットより先にコンテナ上限と集約密度に影響する。ノードあたり何個載せられるかが変わる。
  • ガベージコレクタが入ると平均遅延よりテール遅延の分布が変わる。実時間要求のある経路ならこの項目は別に測るべきだ。

だから判断の軸は「4倍を耐えられるか」ではなく「自分のホットパスに C があるか」だ。サムネイル生成器のデコーダが4倍遅くなっても大半のサービスでは問題にならない。同じ倍率がリクエスト経路の真ん中にあれば容量計画が丸ごと変わる。

6. 代償その二 - ビルドとエコシステムと道具の成熟度

実務でより頻繁に足を取られるのは性能ではなくこちら側だ。

6.1 全体再コンパイルが前提であることの重み

ABI が違うのでディストリビューションが提供する .so をそのまま使えない。libc を含む依存ツリー全体を Fil-C でビルドしなければならない。これは単なるビルド時間の問題ではなくサプライチェーンの構成自体が変わる問題だ。パッケージマネージャが与えていたセキュリティ更新の経路を自前のビルドパイプラインで置き換える必要がある。

filnix が意味を持つのはこの地点だ。Fil-C を Nix のクロスコンパイル基盤として整え、再現可能なツールチェーンとパッケージ世界を提供しており、百を超える nixpkgs パッケージが移植されている。言い換えれば全体再コンパイルという要求を吸収する基盤を先に立てたプロジェクトであり、それなしにはこの手法自体が実験室を出にくい。

6.2 プラットフォームと成熟度

  • リポジトリの案内によれば Fil-C は Linux/x86_64 と Linux/ARM64 でのみ動作する。かつて対応していた Darwin/ARM64 と FreeBSD は現在の対象ではない。
  • Windows 対応はない。デスクトップアプリケーションやクロスプラットフォームのライブラリなら、この一行で候補から外れる。
  • バージョン番号は1.0に達しておらず、LWN 記事によれば2023年に始まった比較的新しいプロジェクトで、事実上一人が牽引している。
  • ライセンスが複数層に分かれる。コンパイラ側とランタイム側、そして musl または glibc 基盤の配布物ごとに異なる条件が適用される。社内展開前に法務確認が要る項目だ。
  • デバッガ・プロファイラ・コアダンプ解析・静的解析器が新しいポインタ表現をどこまで理解するかは別途確認が要る。障害時にスタックを読めなければ安全性の利得が相殺される。

まとめると、この方式の参入費用はコードではなくビルド基盤と運用の道具立てに偏っている。コンテナイメージを自前でビルドし再現可能なツールチェーンをすでに備えた組織なら距離が近く、ベンダー提供のバイナリに依存する組織なら遠い。

7. Zig も同じ方向へ - 発想が一つの声ではないということ

同じ発想が別の言語からも出たという事実はそれ自体が情報だ。2026年7月20日、Zig の Andrew Kelley 氏が Fil-C から着想を得た完全メモリ安全コンパイルモードを提案した。イシューには accepted ラベルと今後のマイルストーンが付いているが実装はされていない。ここでも時点と状態を併せて読む必要がある。

  • 既存の最適化モードを保ったまま fil という選択的 ABI を追加する形だ。
  • Invisicaps 方式とシステムコールのラップを Zig コンパイラに独立して実装する方向である。
  • x86_64-linux から始め、他のプラットフォームへ広げる順序を取っている。
  • Rust との対比を明示的に掲げる — unsafe の逃げ道を置かず、C・C++ の依存ツリー全体に適用する。
  • Fil-C の作者もイシューの議論に参加し、アロケータのインターフェースやアーキテクチャ互換性といった技術的争点を扱っている。

二つの提案を並べると共通構造が見える。どちらも「安全な言語で書き直す」ではなく「安全でない側を安全にして境界をなくす」と問題を切った。そしてどちらもまだ提案段階だ。どちらも今日プロダクションで入れられるスイッチではない。

8. 何を選ぶか - 条件別の判定表

選択肢は互いに排他的ではない。同じ組織の中でもコードごとに答えが違うのが普通だ。下の表は決定を代行するものではなく、どの軸を先に見るべきかを整理したものである。

条件先に見るもの現実的な選択
寿命が3年以下で代替計画があるコード投資回収期間既存ラッパーを維持し境界にファジング。大きな転換はしない
10年以上生きており今後も生きるコード契約が文書化されているか境界の一覧化と契約の明文化を先に。その結果がどの転換にも入力になる
信頼できない入力が C パーサに直接届く違反の結果が何かファジングを常時化。実行時安全化を試す第一候補

9. 確認できなかったこと

以下はこの記事を書く時点で確定した答えを見つけられなかった項目だ。断定しない。

  • extern "fil-c" がその後、正式な RFC として提出されたか、担当チームの反応がどうだったかは確認できない。判断に必要なら rust-lang の RFC リポジトリと Internals フォーラムを直接見るべきだ。
  • Rust と Fil-C を実際につないで動かした公開事例は見つからなかった。提案が描く第一版の範囲も実装物ではなく設計意図である。
  • 同一条件で再現可能な公開ベンチマーク一式は確認できなかった。上表の数値はそれぞれ異なる条件から出たもので、直接比較できない。
  • Fil-C の Windows・macOS 対応計画と時期は公開されたものを確認できなかった。
  • 調達や金融分野のセキュリティ要件がメモリ安全性をどんな文言で要求するか — 言語を指定するのか属性を指定するのか — はこの記事の調査範囲外である。
  • Zig の fil ABI がどのリリースを目標にするかは定まっていない。

よくある質問(FAQ)

extern fil-c はすでに Rust に入っている機能なのか?

違う。2026年8月16日時点で個人ブログの記事から出た提案であり、番号の付いた RFC もトラッキングイシューも実装もない。記事の締めくくりが来年のスプリントで一緒に作ろうという誘いである点が性格をよく示している。今この提案が与える実質は機能ではなく問題を切る方法だ。

unsafe ブロックをきちんと使えば FFI も安全になるのでは?

unsafe は検査を通すキーワードではなく検査を人間が肩代わりするという宣言だ。返却ポインタの寿命、解放責任、スレッド安全性はヘッダにないのでコンパイラには見えない。うまく使うとはその契約を正確に読んでラッパーへ移したという意味であり、上流がバージョンを上げて契約を変えれば、その書き写しはコンパイルされたまま間違いになる。

Fil-C でコンパイルすると性能はどれくらい落ちるのか?

条件による。ドキュメント基準で約4倍という値が引用されるが、同じ記事で bash は体感差がなく、Zig 側の議論では1倍から6倍の範囲が言及される。検査費用がポインタ追跡の頻度に比例するからだ。自分のワークロードで測るまでは一つの数字で語れない。

なぜ extern C ではだめで新しい ABI 文字列が必要なのか?

Fil-C はソース互換だが ABI は意図的に異なる。ポインタが権能と番地に分離された表現だからだ。Rust の extern "C" が話すのは普通の C ABI、Fil-C の用語では Yolo-C である。二つの世界は同じ文字列で会話できないので別の文字列が要る。

今すぐ実務でできることは?

三つが提案の採否と無関係に利益になる。プロジェクトの FFI 境界を一覧にし、各境界関数の契約(寿命・解放責任・スレッド安全性・null 許容)をラッパーのコメントに明文化し、信頼できない入力が届く境界にファジングを付けることだ。どの転換を選ぶにせよ、この三つは入力として使われる。

結論: 採用されなくても残るもの

extern "fil-c" が実際に Rust に入るかは分からない。確率だけで見れば個人ブログから始まった発想が言語機能になる例は多くない。それでもこの提案に値打ちがあるのは問題を定義し直したからだ。

これまで FFI の安全性の議論はおおむね「境界でどれだけうまく防ぐか」だった。よりよいラッパー、より賢い生成器、より緻密な検査ツール — すべて必要だが、すべて同じ前提を共有する。向こう側はどうせ信じられないという前提だ。この提案はその前提に触れる。

今日実際に使えるものに縮めると三つだ。

  • 自分のプロジェクトの FFI 境界を数えてみる。いくつあり、それぞれどんな契約を前提にしているか分からなければ、どの選択肢も比較できない。
  • 境界ごとに違反の結果を書き留める。任意コード実行かプロセス終了かで対応の優先順位が完全に変わる。
  • 提案段階と採用段階を区別して読む習慣を保つ。この分野は面白い発想が頻繁に出て、そのかなりの部分は長く発想のまま残る。

言語の優劣を決める問題ではない。C には四十年分の検証された実装が積み上がっており、Rust にはコンパイル時に確認される規則がある。二つの資産を同じアドレス空間に置く限り境界は存在し、その境界をどう扱うかが実務の答えるべき問いだ。提案が採用されようとされまいと、その問いは残る。
