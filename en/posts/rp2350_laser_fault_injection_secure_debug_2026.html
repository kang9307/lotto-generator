1. Hardware Trust Boundaries and Context of Physical Fault Injection

In modern embedded systems and Internet of Things (IoT) devices, hardware security serves as the ultimate anchor for software integrity. Even if an operating system or firmware is compromised, cryptographic keys and one-time programmable (OTP) memory regions physically provisioned inside silicon dies must remain securely protected against external attackers according to modern microcontroller design principles. However, when an attacker gains physical access to a device and applies precision fault injection techniques, repeatedly documented cases show that transistor operating states can be forcefully perturbed to break logical barriers.

Published on September 18, 2026 on the Ledger Donjon blog, an article by Antoine Plin demonstrated that photon-emission-guided laser fault injection (LFI) against Raspberry Pi's RP2350 dual-core microcontroller could re-enable a permanently disabled Secure debug interface. The research experimentally showed that even when hardware fuses permanently severed debug access, precision laser pulses directed at the physical silicon layer could restore Secure debug functionality.

This investigation was conducted in a controlled environment requiring destructive decapsulation and laboratory equipment valued at approximately $250,000. The primary source states that this vulnerability was disclosed to Raspberry Pi on July 28, 2026. The author concludes that security evaluations must encompass the entire enforcement pathway, from immutable OTP configurations to mutable control registers and reset behaviors.

2. The RP2350 Multi-Layered Security Model — OTP, TrustZone, and Permanent Debug Disabling

According to the primary source, the RP2350 is a dual-core microcontroller offering boot-time selection between Arm Cortex-M33 and RISC-V Hazard3 cores per processor socket, equipped with the following security features:

  • Secure Boot: Cryptographically validates the integrity of signed firmware during the boot ROM stage against public key fingerprints provisioned in One-Time Programmable (OTP) memory.
  • Armv8-M TrustZone: Enforces strict logical isolation between Secure and Non-secure domains for memory and peripherals.
  • Permanent Debug Disabling: Setting the CRIT1.DEBUG_DISABLE flag in OTP during manufacturing permanently disables external debugger access to system buses.
  • Hardware Glitch Detectors: Intended to detect timing disturbances caused by clock or power supply manipulation.

According to the primary source, critical security flags are encoded using a 3-of-8 vote across eight consecutive OTP rows, and lock bits employ majority-voting triple redundancy. Each bit in OTP memory can physically transition from 0 to 1 only once, making reversion to a prior state impossible.

External debuggers communicate via the Serial Wire Debug (SWD) interface. External requests pass through the Serial Wire Debug Port (SW-DP) to the Memory Access Port (Mem-AP) of each core. This Mem-AP must be active to access the system bus and peripherals. Under normal secure operation, writing the CRIT1.DEBUG_DISABLE flag holds the Mem-AP enable signals of both cores at zero, permanently preventing arbitrary memory inspection and control by external debuggers.

3. Structural Cause of the Vulnerability — Absence of Documented Redundant Encoding in the DEBUGEN Register

Contrasting with the redundant encoding of OTP security fields, the primary source points out that the datasheet does not document bit redundancy, parity, or majority voting for DEBUGEN. In normal operation, the memory-mapped DEBUGEN register provides an override pathway allowing trusted Secure software to re-enable per-core Mem-AP access when required.

  • Disparity in Documented Protections: While OTP security fields are encoded with majority voting and similar protections, the primary source notes that the datasheet specifies no equivalent protection for DEBUGEN.
  • The Research Question: The primary source consequently set out to test whether laser pulses could set DEBUGEN bits on a protected device.
  • Prerequisites for Secure Debug: Secure debug on a core requires both the bit enabling its Mem-AP and the bit permitting Secure access through that Mem-AP.

In the words of the primary source, there was a difference between the redundant encoding used for OTP security fields and the documented protections for DEBUGEN, and that difference served as the starting point for this evaluation.

4. Silicon Register Localization via Photon Emission Microscopy (PEM)

The primary source explains that PEM was first employed to narrow down the target location. Photon Emission Microscopy is a failure analysis technique that captures the faint near-infrared (NIR) photons emitted when semiconductor transistors switch states using high-sensitivity cameras.

The spatial localization procedure described in the research proceeded as follows:

  • Differential Photon Emission Measurement: After backside decapsulation exposed the silicon substrate, two averaged image stacks were subtracted to cancel static background, sensor offset, thermal emission, and unrelated switching activity.
  • Small areas associated with DEBUGEN bits 0–3 were identified across three regions within the camera field of view (the source also notes that two locations were separated by a few micrometers).
  • PEM results provided the spatial clues for laser targeting. In the words of the primary source, differential PEM first identified bit-dependent DEBUGEN activity, and guided LFI converted those spatial clues into persistent Secure debug access.

The techniques described in this section were performed after backside decapsulation exposed the silicon. The primary source notes that backside decapsulation permanently alters the package and leaves the die exposed.

5. 980 nm Laser Fault Injection (LFI) and the 4-Stage Secret Extraction Procedure

Once the register coordinates were identified, the researchers executed physical fault injection using a 980 nm pulsed laser system. The laser penetrated the exposed backside silicon substrate to forcefully set the register state. The laser parameters deployed in the experiment consisted of approximately 40% of maximum optical power (yielding about 1.2 W) with a 100 ns pulse width focused through a 50x objective lens.

The four-stage secret extraction procedure described in the primary source is as follows:

  1. Rescue reset: Setting CTRL.RESCUE_RESTART to 1 and back to 0 via RP-AP. The primary source explains that a rescue reset is a whole-system reset signaling the boot ROM to pause before executing user software, leaving both cores in the boot ROM wait path.
  2. DEBUGEN to 0xc: While both cores are in the boot ROM wait path, a laser pulse sets PROC1 (bit 2) and PROC1_SECURE (bit 3). In the primary source, the DEBUGEN value read via Core 1's Mem-AP was 0xc.
  3. Core 1 halt: Halting Core 1 via its Debug Halting Control and Status Register (DHCSR).
  4. Secret extraction: Reading the secret (128 bits, Page 48) at OTP rows 0xc08–0xc0f using the restored Secure debug access.

The primary source reports that the 128-bit challenge secret stored in OTP Page 48 of a revision A4 test device was successfully read through this pathway.

6. Technical Analysis of Bypassing DEBUGEN_LOCK and Runtime Locks

According to the source, DEBUGEN_LOCK blocks software writes to the corresponding DEBUGEN bits, and a lock bit cannot be cleared once set. The research team tested whether this lock also holds against laser fault injection.

Experimental validation showed that DEBUGEN_LOCK does not prevent laser-induced register state changes. The technical limitations analyzed in the study include:

  • Lock Bits: The primary source explains that the laser pulse altered DEBUGEN despite DEBUGEN_LOCK, and lock bits set by the pulse could prevent firmware from restoring the inactive value.
  • Bypass of Permanent Lock Configurations (PAGE48_LOCK1): The tested configuration had permanent OTP locks configured as PAGE48_LOCK1 = 0x3c3c3c, strictly prohibiting Non-secure access while preserving Secure read and write privileges. Because the laser-restored debug interface acquired Secure attribution, it passed this lock check normally.
  • Volatility of Runtime Soft Locks: Dynamic soft locks configured by firmware at runtime are cleared upon reset. Because the researchers used a rescue reset to freeze the cores early in the boot ROM sequence, runtime soft locks never had an opportunity to execute.

The primary source concludes that while each software-visible mechanism performed its documented function, their interaction combined with laser faults opened Secure debug access.

7. Comparison of Security Mechanism Intent vs. Fault Injection Results

To accurately contextualize the findings of this research, it is essential to systematically compare the theoretical design intentions of the RP2350 security blocks against their observed behavior under laser fault injection. The table below summarizes the operational outcomes across all five critical security components evaluated in the study.

Security Mechanism Design Intent Fault Injection Study Result
One-Time Programmable (OTP) Memory Critical flags are encoded with a 3-of-8 vote across 8 consecutive rows; lock bits use triple redundancy with majority voting. The primary source does not report alterations to OTP bits. With debug access opened, the 128-bit challenge secret in Page 48 was read.
Permanent Debug Disable (CRIT1.DEBUG_DISABLE) Permanently forces Mem-AP enable signals to zero, physically blocking external debuggers from system buses and memory. Override bits in the DEBUGEN register were forcefully set by laser pulses, re-enabling debug bus transactions.
DEBUGEN Register (Per-Core Debug Override) Provides an override pathway enabling trusted Secure software to re-enable per-core Mem-AP access when needed. Laser pulses set DEBUGEN bits for which the datasheet does not document redundancy, parity, or majority voting.
DEBUGEN_LOCK (Register Write Suppression) Prevents runtime tampering with the DEBUGEN register by asserting lock flags. Once register values were changed by the laser, asserting lock flags could not revert the active debug state back to disabled.
Hardware Glitch Detectors A feature intended to detect timing disturbances caused by clock or supply manipulation. The researchers tested with glitch detectors set to maximum sensitivity; the primary source does not state whether detectors responded during laser irradiation.

The primary source concludes that security depends on the entire pathway spanning OTP configuration, mutable control registers, and reset behaviors, rather than isolated individual mechanisms.

8. Boundaries Between Laboratory Attack Conditions and General Threat Models

In security engineering, evaluating any attack technique requires examining it through the lens of a realistic threat model. Interpreting these research findings as meaning that "all RP2350 devices are easily hacked" is an obvious overreach, and the primary source makes no such claim. The table below outlines the prerequisites for this attack alongside general threat environments, with the third column representing this article's analytical interpretation rather than the primary source.

Attack Requirement Primary Source Statement Interpretation in this Article
Physical Device Possession Primary source: Physical access is required Interpretation: Requirements fundamentally differ from remote intrusion
Destructive Package Decapsulation Primary source: Backside decapsulation permanently alters the package and leaves the die exposed Interpretation: Alters device appearance, making covert execution extremely difficult
Laboratory Equipment PEM, 980 nm pulsed laser, 50x objective, and related lab gear valued at approximately $250,000 (primary source) Interpretation: Not accessible to standard consumer or casual threat actors
Hardware Security Expertise The primary source does not separately quantify required expertise; procedures involve differential PEM, laser positioning, and reset/halt control Interpretation: Demands multi-disciplinary coordination of advanced techniques
Disclosure Process Notified Raspberry Pi on July 28, 2026 (primary source) Interpretation: Provides clear timeline when the vendor received the vulnerability details

The primary source does not discuss risk levels or threat models for other RP2350 devices. From the interpretation of this article, given the prerequisites (physical access, destructive preparation, ~$250,000 equipment), this is read as a laboratory physical attack rather than a remote vector. Actual risk must be weighed within each organization's specific threat model.

9. Defensive and Mitigation Perspectives for Embedded Hardware Designers

The following summarizes the mitigations discussed in the primary source's "Limits of software-based mitigations" section alongside this article's analytical interpretation:

  • Runtime mitigation 1 from primary source: Firmware can restrict debugger access to sensitive targets via ACCESSCTRL and assert the debugger bit in ACCESSCTRL.LOCK to prevent debugger transactions from re-opening those permissions.
  • Runtime mitigation 2 from primary source: Secure firmware can periodically inspect DEBUGEN and, upon detecting an unexpected value, trigger a fail-safe reset that clears the processor-cold reset domain.
  • Limitations identified in primary source: These mitigations are best-effort. An active debugger can halt the core before the next check, and a rescue reset halts execution before firmware can configure ACCESSCTRL or launch monitors, leaving the demonstrated pre-firmware secret extraction unmitigated.
  • Interpretation in this article (not from source): System designers can determine whether a $250,000-class physical attack is realistic for their operational threat models and choose proportionate security tiers.

The primary source also concludes that while the RP2350 encodes critical debug-disable flags in OTP using redundant voting, DEBUGEN can override that effect without equivalent datasheet-documented protections.
