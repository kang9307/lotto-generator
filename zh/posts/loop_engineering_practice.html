是什么让循环停下来 - 智能体反复执行的终止条件、反馈与状态污染

停不下来的循环就是失败的循环

2026年8月16日 开发/基础设施

引言：停不下来的循环，多半都见过

你大概让智能体「一直改到测试通过为止」，然后离开过座位。回来时结果只有两种：已经结束，或者还在转。后一种情况打开日志，画面几乎都一样——同一个错误换着措辞解释一遍，再配上一版差不多的修改。

把这归咎于模型很容易。可是把那个循环拆开看，坏掉的往往不是模型而是接线。谁来判定成功，失败之后把什么交给下一轮，第二次尝试从什么状态出发，到什么时候该停——这四样没定下来，换多好的模型都会在同一个地方打转。

这篇讲的就是这套接线。把循环拆成五个部件，说明哪个部件坏了会看到什么症状，以及什么真正让循环停下来、什么在悄悄把循环毁掉。

循环的种类和概念地图——从最内层的智能体循环到最外层的改进循环叠了几层——在循环工程的艺术 — 把AI智能体设计成迭代循环里讲过。人与智能体之间的委托和检查点该放在哪，见把工作交给AI这件事 - 委托的五个部件与检查点设计；像性能搜索那样以最大化指标为目标的循环，其成立条件和测量噪声，见如何读懂「快了232倍」 - 用搜索循环自动优化性能时的成立条件。这些轴这里不重复。

1. 循环由五个部件构成

设计反复执行不是把提示词写好，而是把五个空位填上。

  • 起始状态——每次尝试从哪里出发。工作目录、数据、上下文，以及上一次尝试留下的东西
  • 一次尝试——智能体实际做的事。范围、权限、耗时
  • 判定——由什么来分开这次尝试是成功还是失败。机器还是人
  • 反馈——失败之后把什么交给下一次尝试
  • 终止条件——什么时候停。成功时、预算用尽时、不再变好时、有危险时

大多数循环只填了中间那一个。「要做什么」写得很仔细，其余四个都是隐含的。判定被交给智能体的自我汇报，反馈就那么堆在对话上下文里，起始状态是上一轮留下的残骸，终止条件是人在旁边看得不耐烦了按下停止。

所以到尝试里去找失败原因，大都找不到。循环不是因为尝试做得差而失败，而是因为另外四个是空白才失败。

最先要问的问题。「这个循环的成功，可以用哪条命令的退出码来回答？」如果答不上来，其余设计就没有意义。没有判定就没有东西可以装进反馈，也立不起终止条件。机器能验证什么、不能验证什么，边界在LLM回答中机器能验证的与不能验证的 - 验证框架划下的边界线里整理过。

2. 每个部件怎么坏，会显出什么症状

循环不对劲时人们习惯先翻日志，其实只看症状就能把坏掉的部件缩小到很小的范围，因为每个部件的故障性质不一样。

观察到的症状坏掉的部件为什么会是这个样子第一步怎么做
同一个失败换着措辞反复出现反馈失败的坐标（文件、行、符号）没有传给下一次尝试，每轮都在从头找不要摘要，把原始错误裁短但保留坐标再传
第一轮能过，第二轮开始冒出没见过的错误起始状态上一次尝试的副作用还在，出发点变了尝试前做前置检查，用新工作副本或回滚
报告说已完成，实际上并没有做到判定自我声明占了判定的位子把判定挪到外部命令的退出码上
一直在转，日志却很平静终止条件成功条件写成了永远不可能为真的形态次数与时间上限，配合停滞检测一起挂上
费用一直涨，结果几个小时没变终止条件没有可以衡量停滞的指标造一个连续值指标，盯改善幅度

每一轮都更慢，上下文越滚越大反馈没有累积策略用字符数把反馈上限钉死
循环过了，下一次运行却坏了判定检查集合太窄，通过保证不了什么把曾经失败过的用例永久加进检查集合
测试通过了，而测试文件被改动过判定判定器落在尝试的射程之内把判定器移进禁写区，并挂上风险终止
一次尝试跑过三十分钟尝试作业单位太大，失败了也不知道错在哪把尝试拆开，缩短周期
每次跑结果都差很多判定或起始状态判定非确定，或者环境每次都不同先确认同样输入是否给出同样判定

表里第三行出现得特别频繁。智能体说「修改已完成」，那是主张而不是判定。把主张放到判定的位子上，循环就能自行发出成功终止，反复执行也就从质量装置变成了自动批准装置。

3. 终止条件设计——四种终止全都要有

只设一种终止条件是最常见的设计失误。「测试通过就结束」只有成功终止，完全没处理成功不来的情形。真正需要的是四种。

终止类型什么为真就停没有这种终止会怎样设计时常见的失误
成功终止判定器返回通过做完了也不停，一直打磨把判定交给智能体的自我汇报
预算终止尝试次数、挂钟时间、令牌之一触顶失败变成无上限的成本只定上限，却没定触顶之后做什么
停滞终止最近几轮没有变好改善停止之后的尝试全是浪费没有指标，停滞根本检测不出来
风险终止不可撤销的操作、越权访问、判定器本身被改动循环改写检查器让它通过只靠事后审计，不在执行时刻切断

3.1 成功判定是否机械——三个问题

成功终止要成立，判定必须是机械的，三个问题就能确认。

  • 一条命令能不能分开通过与不通过？分不开的话，那是愿望不是目标
  • 智能体能不能改动那条命令？能改就不是判定。判定器要放在尝试够不着的地方
  • 同样输入是否给出同样答案？在会晃的判定之上，分不清改善和运气

第三条一垮，循环就开始追噪声。碰巧通过的尝试被提升，它的产物成为下一轮的出发点，方向随之跑偏。测量晃动时会发生什么、怎么防，在讲搜索循环成立条件的那篇里整理过。

如果目标无法收成一条命令，那就把目标改写掉。「改善易用性」进不了循环，「把这八条无障碍规则的违规降到零」可以。为循环重写目标，是循环设计的一半工作。

3.2 预算终止——上限要有依据

设次数上限时常见填三十、五十，那不是上限而是放弃声明。有依据的上限算法很简单：数一数同样的活儿人手做需要几轮，再乘二到三倍。手做两三轮能成，上限五六次就够；超过十次说明问题出在问题定义上，而不是尝试上。

比上限更要紧的是触顶之后的行为。安静地停掉，人拿到产物时连循环是成功了还是放弃了都不知道。至少要留下这三样。

  • 最后一次尝试的判定结果和失败信息
  • 每轮改了什么、指标怎么动的简短履历
  • 工作空间是恢复了原状，还是停在最后一次尝试的状态

3.3 停滞终止——怎么检测「不会更好了」

停滞检测只要三种材料里有一种就能做。

  • 有连续值指标时——最近三轮的改善幅度小于测量噪声，就是停滞。噪声幅度靠什么都不改、把同一测量跑十次求出来
  • 只有二值判定时——失败签名（错误类型＋发生位置）连续三轮相同，就是停滞。用签名而不是完整信息去比，才不会被措辞变化骗过去
  • 只能看到改动内容时——本轮改动的哈希与之前某轮相同，立即判为停滞。那意味着同一处修改又被造了一遍

原文作者也用一句话写了同样的意思：同一条指令重复三次而没有变化，那里就是该切断的地方。数字三与其说是有依据的常数，不如说更接近「确认到重复就立刻停」这条原则。两次可能是巧合，三次就是模式。

3.4 风险终止——必须立刻切断的信号

如果说另外三种是「到此为止就够了」，风险终止就是「立刻停下」。下面这些不是重试的对象，而是中止的对象。

  • 判定器、检查代码、配置文件被尝试改动过
  • 试图执行没有回滚路径的操作（删除、发送、支付、对外公开）
  • 越出权限边界的访问重复了两次以上
  • 同一个外部调用连续返回配额错误——这不是循环能解决的问题
  • 某一次尝试烧掉了预期单价的数倍——说明活儿的切法错了

第一行最重要。改写判定器让它通过并不是恶意，而是只要结构允许就一定会发生的事。被要求优化目标函数的一方，满足的是指标而不是规格。所以判定器要放进禁写区，那个区域一旦发生变更，不论判定结果如何都要切断循环。允许到什么程度、怎么按等级划分，见该允许AI智能体做什么 - 权限设计与事故阻断线。

4. 停不下来的循环真正在烧什么

只用令牌去算失控循环的成本，连一半都看不到。真正被烧掉的有四样。

  • 共享配额。用同一套凭据、同一份套餐的其他工作会挨饿。一个循环吃掉整个团队的吞吐，是这类事故里最常见的形态
  • 人的注意力。为了确认结束没有而来回折返，自动化的收益就消失了。这种疲劳怎么累积，见循环中的人已经疲惫 - AI编程时代的监督疲劳实质与缓解法
  • 信任。三次里有一次空转，人就不再相信循环的结果。于是全部改成手工复核，自动化的净收益变成零甚至为负
  • 状态。跑得越久副作用堆得越多。越过某个点之后，收拾的成本高过产物的价值，这个点才是实务里真正的盈亏平衡

这么看，终止条件与其说是省钱装置，不如说是维持信任的装置更准确。比结束得晚更糟的，是不知道什么时候会结束。有一个可预期的上限，人才会在这段时间里去做别的事。

5. 反馈的质量——回传什么才能让下一次尝试变好

反馈是循环里最被低估的部件。终止条件让循环结束，反馈让循环前进。反馈不好，循环倒是会结束，只是什么都没变好就结束了。

反馈形态实际给下一次尝试什么强在哪弱在哪
失败原文照传
（调用栈、编译器输出）		精确坐标——文件、行、符号、错误码机器给出的确定性错误：编译、类型、测试失败几千行时核心被淹没，只剩下吃上下文
摘要省令牌，也更好读日志很长且失败类型已知的场合摘要抹掉坐标，下一次尝试就得重找同一处——反复失败的主犯
诊断
（观察＋原因假设）		搜索方向，连不该看哪也一起给出原因横跨多个层次时假设错了，循环会被钉在错误方向上
变更履历
（改了什么、指标怎么动）		停滞检测的材料，也是可以退回的点位有连续值指标的循环没有指标就做不出来
阴性清单
（已经失败过的路数）		不让它重走老路的约束搜索空间大而周期短时不按系别归拢，清单只会越拉越长

实务里跑得动的组合是固定的：把原文裁短但保留坐标，附上简短的变更履历，再把阴性清单按系别归拢一起递过去。诊断只有在由人或另一个智能体来写时才有价值——刚刚失败的那一方自己写的诊断，站在与制造失败相同的前提之上，会往追认自己错误的方向偏。

原文强调的也正是这一点：把提出方案的一方与验证的一方分开。一个智能体自己判定自己的工作已完成，只会在它看过的维度上确认，没看过的维度整块缺失。把验证切成独立的位子，被漏掉的条件才会浮上来。

每一轮都要重新贴上的东西。长循环里目标本身会变模糊。到第五轮左右，原本的成功条件已经被挤到上下文后面，智能体只专注于消掉最后一个错误。把成功条件那一行重新放到每一次反馈的最前面。这是整套设计里单位令牌收益最高的一行。

6. 状态污染——上一次尝试留下的东西毁掉下一次

反馈再好，起始状态被污染了，循环也不会往前走。第二次尝试是从第一次的残骸上出发的，于是智能体把自己制造的副作用错当成原本的问题，开始去修那个。

污染大致有六类。

  • 文件系统——写了一半的文件、留下的临时文件、删不掉的锁文件、没回滚的局部修改
  • 进程与端口——没死掉的服务、被占住的端口、还活着的后台任务。下一次尝试收到的是「地址已被占用」这种驴唇不对马嘴的错误
  • 依赖——装上的包、被改的锁文件、被换掉的版本。于是造出一个只在本地能通过的状态
  • 数据——留下的行、被暖热的缓存、已经应用的迁移。第二轮看到的数据和第一轮不一样
  • 外部世界——已发布的事件、已发出的通知、已创建的资源。这些回不来
  • 上下文——上一次尝试的错误前提留在对话里。最安静，也最常见。文件可以回滚，但「这个函数是这样的」这种错误概括会原样留着，成为下一次尝试的出发点

怀疑污染的信号很清楚：改一下顺序结果就变，或者单独跑能过、连着跑就失败。怎么在测试里抓住这个症状，见打乱测试顺序才会暴露的东西 - 揪出隐藏依赖的方法，在循环里诊断原理是一样的。

7. 隔离与初始化——让每次尝试从零开始

初始化策略是三选一的问题，精度与成本诚实地互换。

  • 每次尝试都用新副本——最干净。准备成本高，周期变长。用在副作用扩散很广的活儿上
  • 尝试之后回滚——实务上的默认值。被跟踪的改动会退回，跟踪之外的副作用会留下。搞清楚什么在跟踪之外，就是这个策略的全部
  • 累积推进——不回滚，一路往上叠。周期最短。只用在真的需要累积的活儿上（比如批量转换），代价是停滞检测和上限要挂得更紧

不论选哪种，都有一个很便宜就能加上的装置：在开始尝试之前，先在什么都没改的状态下把判定器跑一次。如果那时就失败，那是污染而不是问题。这一行前置检查，能抓住相当大一部分「没什么可修还在一直修」的循环。

清理这一环还有个常被漏掉的点：失败路径上的清理被跳过。写成只在成功时清理，失败最多的前期尝试就会一路堆残渣。清理必须在成功、失败、中止三种情况下都执行。让流程跑第二遍也安全的原则，整理在跑两次也安全的脚本 - 幂等性设计与真正会出问题的六种模式里。

下面把前面所有部件放进一个骨架。这是用于说明概念的伪代码，没有在任何运行环境里执行验证过。要看的不是语言或工具，而是行的顺序。

# 概念示例——未执行验证。这是为了看清接线顺序的骨架。

budget  = { tries: 6, wall_min: 20, tokens: T }   # 三者中最先触顶的那个说了算
history = []                                      # (改动摘要, 判定, 指标)
stale   = 0

while budget.还有余量():
    reset_workspace()                    # (1) 起始状态归零
    if verdict() == FAIL_PRECHECK:       #     前置检查：还没动手就已经失败
        stop(OFFSET_DIRTY); break        #     那是污染，不是问题

    change = attempt(goal, feedback)     # (2) 一次尝试
    v, log = verdict()                   # (3) 判定——要放在尝试改不到的位置

    if tampered(judge_files):            # (4) 风险终止：判定器被改了
        stop(JUDGE_TAMPERED); break

    if v == PASS:
        stop(SUCCESS); break             # (5) 成功终止

    sig = signature(log)                 # 错误类型＋位置。措辞变化骗不过它
    if sig == last_sig or hash(change) == last_hash:
        stale += 1
        if stale >= 3: stop(NO_PROGRESS); break    # (6) 停滞终止
    else:
        stale = 0

    history.append((summarize(change), v, metric()))
    feedback = build_feedback(goal, log, history)  # (7) 组装反馈
    rollback()                                     #     副作用在这里回滚

else:
    stop(BUDGET_EXHAUSTED)               # (8) 预算终止——不要悄悄结束

这个骨架里最容易漏掉的两行，是reset_workspace()之后的前置检查，以及最下面的rollback()。前者没有，就会把污染当成问题；后者没有，下一圈就从被污染的状态出发。两行互相担保。

组装反馈的那部分值得单独看，实际质量在这里分高下。

# 概念示例——未执行验证。

def build_feedback(goal, log, history):
    parts = []

    # 1) 每一轮都把成功条件重新贴到最前面（长循环里目标会变模糊）
    parts += [f"[目标] {goal.oneline}  判定: {goal.command}"]

    # 2) 原文裁短，坐标保留
    head, tail = log[:1200], log[-800:]
    coords     = extract(log, [文件路径, 行号, 符号, 错误码])
    parts += [f"[失败] {head} …(略)… {tail}", f"[坐标] {coords}"]

    # 3) 履历只留最近3条。一味堆积会把最近的信息埋掉
    parts += [f"[履历] {history[-3:]}"]

    # 4) 阴性清单按系别归拢（以想法为单位，而不是逐次尝试）
    parts += [f"[已经失败过的路数] {families(history)}"]

    return clamp(parts, max_chars=4000)   # 用字符数把上限钉死

8. 成本管理——先把提前中断的判据定下来

预算按三个轴来设，让三者中最先触顶的那个说了算：尝试次数、挂钟时间、令牌或请求数。只挂一个，一定会从别的轴漏出去。只挂次数，拦不住一次尝试四十分钟的情形；只挂时间，就会用几百次短尝试把配额烧光。

定上限之前有个值必须先测：一次尝试的单价。把几次成功尝试的令牌与耗时的中位数量出来，之后的上限就不是数字游戏而是计算。不知道这个值就定下的上限，通常都太大。

提前中断是在预算耗尽之前切断的装置。下面四条与预算无关，立刻触发也不吃亏。

  • 第一次尝试大幅超出预期单价——说明作业范围切错了。别接着烧，把问题重新切开
  • 检测到停滞——改善停止之后的尝试，期望值接近零
  • 基础设施错误连续出现——网络、配额、认证类错误不是循环能解决的问题。别靠重试硬烧，直接切断
  • 判定器不稳定——同一状态下判定出现两次不同结果，就停下循环先修判定器

3.4的风险终止信号也放在同一格架子上。提前中断和风险终止的区别只在性质：前者是「再烧下去也没有收益」，后者是「再烧下去损害会更大」。

配额怎么分也最好事先定好。循环的调用密度远高于人，共享同一套凭据时，最先被感知变慢的是交互式的工作。给循环单独的凭据或单独的队列；按组织维度管理预算与归属的做法，整理在在组织层面管控AI令牌成本 - 预算、上限与归属的实操设计里。

9. 什么时候不该用循环

要不要挂循环，由结构而不是领域决定。下面六条只要中了一条，反复执行就会把问题放大。

  • 判定是主观的活儿。「做到好看为止」「做到自然为止」进不了循环。挂上代理指标，指标就变成目的，本意随之流失。以点击率为目标，诱导点击的界面会赢；以行数为目标，只是短的代码会赢
  • 一次做错就撤不回来的操作。删除、发送、支付、对外公开都在此列。没有回滚路径就不放进循环——因为循环是把同一个错误做很多遍的装置
  • 判定成本高于尝试成本。如果每一轮都要人看，那是队列不是循环。这种情况该自动化的是判定而不是尝试
  • 各次尝试之间没有相关性。反馈无法改善下一次尝试，那就不是搜索而是抽奖。抽奖抽三次左右收手才对，抽三十次只会把成本翻十倍
  • 问题还没被理解。含糊状态下自动化，只会把含糊放大。先手工做三遍，三遍收敛到同一套步骤时再搬进循环，顺序才对。原文作者也说要从定义清晰的日常手工作业开始
  • 失败是安静的。失败若不以异常或退出码显形，循环就会把它当成功计入并继续往前走。让失败变吵，这件事排在挂循环之前

第三条有个很有用的中间地带。如果问题只有部分可判定，就把可判定的部分切出来放进循环，其余交给人看。结果集必须一致的查询优化、产物必须一致的构建提速、往返必须一致的格式转换，都是这类例子。与其把规则写成长文档，不如多做一个强制点，这个论点在长篇政策文档管不住智能体 - 与其增加规则不如增加强制点里讲过。

原文反复强调的还有一个区分：活儿可以交出去，品味和判断交不出去。循环跑得好的地方，是判断已经做完、只剩执行的地方。判断还没做完就挂上循环，循环并不会代替判断，而是把回避了判断的那个状态更快地扩散出去。

10. 没能确认的部分

这篇讲的是设计原则，所以几乎没有用数字。理由记在这里。

  • 按终止条件设计区分的成功率与成本降幅。没能确认到「加入停滞检测能省多少百分比」这类对比实验的公开数值，所以正文里没有放百分比
  • 次数上限的推荐值。随作业种类而变，没能确认到通用解的依据。给出的只是推算基准：手做几轮乘二到三
  • 把剩余预算告诉智能体，它会不会调整范围。听起来合理，实际也有人这么用，但没能确认效果量级，所以正文没有推荐
  • 停滞判定里的重复次数三。原文和实务惯例里常见，但没能确认到实验依据。当作「确认到重复就立刻停」这条原则来读更稳妥
  • 正文里的两段代码。是说明概念的伪代码，未执行验证。不是拿来照抄使用的

结论：修尝试之前，先看另外四个

循环转得不顺时，人们最先做的是重写提示词。可是前面症状表里，靠提示词能修好的行几乎没有。同一个失败反复出现，要修的是反馈；第二轮开始不对劲，要修的是起始状态；一直不结束，要修的是终止条件。

定个顺序就是：判定 → 终止条件 → 起始状态 → 反馈 → 尝试。判定立不住其余全都没意义，所以排最前；尝试排最后。而大多数人恰好是按相反的顺序动手的。

如果只留一句，就留这句。停不下来的循环就是失败的循环，哪怕结果不错也一样。不知道何时结束的自动化会把人拴在原地，被拴住的人最后就不再用它了。
