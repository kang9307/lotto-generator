git bisect - Finding the Commit That Introduced a Bug by Binary Search

1,000 commits in 10 test runs. Automating with bisect run, the exit code contract, skip, terms and merge histories, all with real output

2026-09-01 Dev & Infra

It used to work and now it does not. A problem that starts with that sentence is not one where the cause is unknown; it is one where you do not know where to look. Something changed somewhere, and that somewhere sits among hundreds of commits. git bisect is the command that cuts that range in half, then in half again.

The idea of binary search itself has been covered separately — that is the subject of how a hard kernel bug gets narrowed down. This piece narrows to the command git actually ships. What arguments it takes, what it prints, and where it gets things wrong.

Every output below was produced by actually running the commands on git 2.48.1.windows.1, Windows 10 Pro (10.0.19045), Git Bash (GNU bash 5.2.37, MSYS2), as of September 2026. All experiments ran in freshly created repositories under a temporary directory, and /tmp/demo in the text is a neutral stand-in for that location. Anything that may differ on other platforms or shells is flagged where it comes up.

What problem the tool solves

git bisect answers exactly one question. If it fails now and succeeded before, which commit in between changed it? Give it one commit that was fine and one that is broken, and git checks out a commit in the middle, a person or a script judges it, and the range halves again.

The important part is that you do not need to know anything about the guilty commit. You only need a criterion. A performance regression, a log line that stopped appearing, a file that stops being produced — anything that can be phrased as a test with a yes or no answer qualifies. That makes this a fundamentally different activity from reading code and reasoning about causes. It is not inference. It is measurement.

  • Three things you need — a broken commit (usually HEAD), a commit that was fine (a tag, a release, a commit from a few months back), and a test that reproduces
  • One thing you do not need — a hypothesis about the cause. Having one tends to make you look only there and miss the rest
  • The search space is whole commits, not file diffs, which is why problems caused by the interaction of several files are still found
  • The result is a single commit. If that commit is large you still have narrowing to do, but going from an entire history to one commit usually changes the shape of the problem

Building a repository to experiment on

Descriptions only go so far, so the starting point is a repository built for the purpose: twenty commits. total.sh adds up the numbers it is given as arguments, and check.sh exits 0 when the result is right and 1 when it is wrong. The thirteenth commit rewrites total.sh to iterate by index and, in doing so, drops the last argument. Seven more unrelated commits pile on top of it.

# inside /tmp/demo

cat > total.sh <<'EOF'
#!/bin/bash
sum=0
for n in "$@"; do
  sum=$(( sum + n ))
done
echo "$sum"

cat > check.sh <<'EOF'
#!/bin/bash
out=$(bash ./total.sh 1 2 3 4)
if [ "$out" = "10" ]; then
  exit 0

There are four moves. Open a session with bisect start, say that the present is broken with bisect bad, name a commit that was fine with bisect good. Git then checks out a commit in the middle. Test, answer good or bad, repeat, and leave with bisect reset.

Is 1,000 commits really 10 tests?

The arithmetic gets quoted often enough that it is worth measuring. A fresh repository of 1,000 commits, a configuration value broken at commit 674, and an automatic search across the entire history from the root commit to HEAD. Counting how many times the judgement script ran settles it.

$ git rev-list --count HEAD
1000

$ git bisect start HEAD $(git rev-list --max-parents=0 HEAD)
$ git bisect run bash /tmp/bigtest.sh
Bisecting: 249 revisions left to test after this (roughly 8 steps)
Bisecting: 124 revisions left to test after this (roughly 7 steps)
Bisecting: 62 revisions left to test after this (roughly 6 steps)
...
fe0dcdad953018ee006623208fdde398e98ea338 is the first bad commit
    c0674
bisect found first bad commit

# number of times the judgement script ran
10

Exactly ten. The root commit was the good endpoint, so there were 999 candidates, and halving 999 repeatedly drops below one on the tenth step. The property that matters is not the absolute count but the rate of growth. Doubling the commits adds precisely one test.

Candidate commitsTests neededNote
184Measured on the 20-commit repository above
99910Measured on the 1,000-commit repository
2,00011Twice the commits, one more test
100,00017Even a large repository stays under twenty

The bottom two rows are not measurements; they extend the same rule. The point is that the commit count is almost never the bottleneck.

The length of one test decides the total

So what is the bottleneck? The same 1,000-commit search was run twice: once with a test that finishes instantly, once with sleep 2 added to make it deliberately slow. The answer was identical and so was the number of tests.

--- instant test, 999 commits
tests run: 10
wall time: 3693 ms

--- same search, two seconds per test
tests run: 10
wall time: 24018 ms

same answer? fe0dcdad... / fe0dcdad...

The 20.3 second gap is 2 seconds x 10 runs. Git itself spent 3.7 seconds, the cost of ten checkouts. Almost all of the elapsed time is test time, and the formula is plain: total time is roughly one test duration multiplied by log₂ of the candidate count.

That is why shrinking the test before starting a bisect pays more than anything else. A full suite that takes five minutes costs fifty minutes over ten runs; a minimal case that reproduces the problem in thirty seconds costs five. Build the minimal reproduction first is not a matter of taste, it is a tenfold arithmetic difference.

  • Run the one failing test instead of the whole suite. Most frameworks accept a single case by name
  • If a build is required, make it incremental. A full rebuild each round multiplies straight through by ten
  • Cut out anything that depends on the network or external services. Slow is one problem, but intermittent failure gives a wrong answer
  • Narrow the range where you can. Going from 999 candidates to 60 takes the run count from 10 down to 6

What happens if you forget bisect reset

Leave the state alone after finding the culprit and you sit on a detached HEAD, standing on the last commit tested and attached to no branch. Git does say so, clearly.

$ git status
HEAD detached at 4d711a9
You are currently bisecting, started from branch 'main'.
  (use "git bisect reset" to get back to the original branch)

nothing to commit, working tree clean

$ ls .git | grep -i bisect
BISECT_ANCESTORS_OK
BISECT_EXPECTED_REV
BISECT_LOG
BISECT_NAMES
BISECT_START
BISECT_TERMS

$ ls .git/refs/bisect
bad
good-d6e191c941eb0f49e6ad6b88f546215ef538eecf

Absent-mindedly editing and committing here produces a commit that belongs to no branch. It can be recovered later through reflog, but there is no reason to go through that. The fastest way to tell whether a session is still live is to look for those BISECT_* files inside .git, and reset removes every one of them.

$ git bisect reset
Previous HEAD position was 4d711a9 c12: unrelated note 12
Switched to branch 'main'

# when you want to stay on the culprit commit
$ git bisect reset refs/bisect/bad
HEAD is now at f1fec3f c13: refactor total.sh to index-based loop

# clean up the session without moving off the current commit
$ git bisect reset HEAD

One more thing: a dirty working tree will not let the session start. Files you are editing have to be committed or stashed. This is how it actually ends.

$ git status --short
 M total.sh

$ git bisect start f2ee06a d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
error: Your local changes to the following files would be overwritten by checkout:
	total.sh
Please commit your changes or stash them before you switch branches.
Aborting

bisect run, no human in the loop

This is where the command earns its place. Hand the judgement to a script and git bisect run repeats the checkout, the judgement and the next choice on its own. On exactly the repository from before, with no human involvement, it finishes in one line.

The exit code contract

Automation lives or dies on the exit code. Get the contract wrong and the search quietly names the wrong commit. Pinning a script to each code in turn and running the search produces this.

Exit codeHow git reads itWhat actually happened
0good / oldEverything marked good, so the bad endpoint itself was named the culprit
1–124, 126, 127bad / new1, 2 and 124 behaved identically, naming the oldest candidate
125cannot judge, skipSkipping everything gives We cannot bisect more! then bisect run cannot continue any more
126 and 127 (first round)script suspected unrunnableRetried on a good commit, then stopped with bogus exit code 127 for good revision
128 and aboveabort the searchbisect run failed: exit code 128 ... is < 0 or >= 128

The documented contract is: zero is good, 1 to 127 except 125 is bad, and anything else aborts. Run 126 and 127 for real, though, and there is a layer the contract does not mention. Those two values are what POSIX shells use for found but not executable and command not found, so git — on the first round only — checks out a known good commit and runs the same command once more. If the same code comes back, it treats the script itself as broken and stops.

$ git bisect run bash /tmp/rc.sh      # script always exits 127
running 'bash' '/tmp/rc.sh'
[d6e191c941eb0f49e6ad6b88f546215ef538eecf] c02: add check.sh
running 'bash' '/tmp/rc.sh'
error: bogus exit code 127 for good revision
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

The middle lines show the detour to good commit c02 and the return. This guard is why a typo in the script path rarely marks the whole range as broken. Conversely, when that message appears, do not start suspecting the code; check whether the script can be executed at all.

The genuinely dangerous value is 124. It is what you get when a test is cut short by a timeout, and the contract reads it as bad.

$ timeout 1 sleep 5 ; echo $?
124

In other words, a commit that was merely slow is indistinguishable from one that genuinely failed. If you use a timeout, translating that value into cannot-judge is the accurate thing to do.

Writing a judgement script that works

The first rule is that the test must reproduce. Binary search treats every judgement as truth and discards half the range on the strength of it. A single wrong answer can put the culprit in the discarded half, and the search will not report an error when that happens. It hands you one plausible commit, confidently.

To see that, a test that reports a false failure 30% of the time was run five times on the same repository. The correct answer is c13 (f1fec3f).

--- intermittently failing test, 5 rounds
round 1  f1fec3f...  (correct)
round 2  f1fec3f...  (correct)
round 3  f1fec3f...  (correct)
round 4  f1fec3f...  (correct)
round 5  9dc5458...  (c08 - wrong)

--- deterministic test, 3 rounds
f1fec3f...  f1fec3f...  f1fec3f...

One round in five named an unrelated commit, and nothing in that output marks it as wrong. Where intermittent failure is suspected, it is better to repeat the judgement and treat a single failure among the repeats as bad.

The second rule is cleaning up side effects. Bisect only moves between commits, so untracked files survive. A stale build artefact left behind contaminates the next judgement.

$ echo "stale artifact" > build.out    # untracked artefact
$ git bisect good                       # move to a different commit
$ cat build.out
stale artifact

A usable skeleton looks like this. A failed build exits 125, a timeout also exits 125, and everything else passes the test result straight through.

#!/bin/bash
# /tmp/judge.sh - keep it outside the repository
set -u

rm -rf ./build            # clear the previous round's artefacts
make clean >/dev/null 2>&1

if ! make >/dev/null 2>&1; then
  exit 125                # cannot build - skip instead of judging
fi

timeout 60 ./run_one_test.sh
rc=$?
if [ "$rc" -eq 124 ]; then
  exit 125                # do not let a timeout masquerade as a failure
fi
exit "$rc"
  • Keep the script outside the repository. Older commits do not contain it
  • Handle the exit code explicitly. Letting the last command's code leak through rarely matches what you meant
  • Clear artefacts, caches and temporary files every round. Anything left behind contaminates the next judgement
  • Trim the output, but keep one line explaining the failure. Later you will only have the log to go on
  • Run it by hand on both endpoints first. The search is only valid if it fails on the bad end and passes on the good end

bisect skip, commits that cannot be judged

When a commit inside the range does not build, there is nothing to judge. git bisect skip asks git to pick a nearby commit instead, and during an automatic run a script that exits 125 means the same thing.

The catch is that if the skipped commits cluster around the answer, the result never narrows to one. Here is what happens when the four commits around the defect (c11 to c14) are all made unjudgeable.

$ git bisect run bash /tmp/skipper.sh
...
There are only 'skip'ped commits left to test.
The first bad commit could be any of:
4d711a957c98da7528cf727b1db40974a3f9d199
f1fec3fe55804001fae21aaf7b18a6914483662a
71ed7e0a93f0b4029ba06d2d3cb95e019f141bb1
f9194e697f22b03a4aae2ef437dfc2497846eb63
d21c4cae515e9a7c0cfcacc38374c8b127273674
We cannot bisect more!
error: bisect run cannot continue any more

That is not a failure. Eighteen commits became five candidates, and five is a readable number. If you know in advance which stretch is unusable, range notation removes it in one go.

$ git bisect skip c10..c14
Bisecting: 8 revisions left to test after this (roughly 3 steps)

$ git bisect log | grep skip
git bisect skip 71ed7e0a...   # c14
git bisect skip f1fec3fe...   # c13
git bisect skip 4d711a95...   # c12
git bisect skip f9194e69...   # c11

The easy thing to get wrong here: c10..c14 means everything after c10 up to and including c14. The starting point itself is excluded. To exclude it as well, name it separately, as in git bisect skip c10 c10..c14.

bisect terms, when good and bad do not fit

What you are looking for is not always a bug. When you want the point where performance improved, or where a feature first appeared, calling one end the bad commit muddles the direction. The vocabulary can be changed. There are built-in aliases old and new, and you can also invent your own.

$ git bisect start --term-old=works --term-new=broken
status: waiting for both good and bad commits

$ git bisect broken f2ee06a
status: waiting for good commit(s), bad commit known

$ git bisect works d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

$ git bisect terms
Your current terms are works for the old state
and broken for the new state.

$ git bisect run bash ./check.sh
...
f1fec3fe55804001fae21aaf7b18a6914483662a is the first broken commit
bisect found first bad commit

The result line changed to first broken commit. Only the closing summary line still says first bad commit, which is worth knowing if you intend to parse the output in a script. If you lose track of the current vocabulary mid-session, git bisect terms reports it.

  • Hunting a bug — the default good and bad are fine
  • Finding where a fix landed — old and new, with nothing called a bad commit
  • Performance regression — something like --term-old=fast --term-new=slow keeps the judgements straight
  • Changing the terms does not change the algorithm. Only the words move

Histories with merge commits

By default, bisect treats merge commits and commits inside side branches as candidates too. To check that, here is a history where the defect landed inside a feature branch that was merged later.

$ git log --oneline --graph --all
* 1f5a5ab m7: mainline work
* dc8284c m6: mainline work
*   36edf65 m5: merge feature
|\
| * fa26dce f4: feature polish
| * 9c3c4da f3: rewrite total.sh (THE BUG)
| * 13a2a60 f2: feature work
| * efe0833 f1: feature start
* | 0481885 m4: mainline work
|/
* 87b692a m3: mainline work
* 2606564 m2: mainline work
* 342914a m1: base

Searching the same repository two ways gives two different answers. Both are correct; they answer different questions.

--- default: walks into the side branch
running 'bash' './check.sh'   (3 runs)
9c3c4da9ba2ed3715032525e3699eeae971e583e is the first bad commit
    f3: rewrite total.sh (THE BUG)

--- --first-parent: mainline only
$ git bisect start --first-parent HEAD 2606564
running 'bash' './check.sh'   (3 runs)
36edf65d0bd276c62c3fbae15ccab5a28196c39d is the first bad commit
Merge: 0481885 fa26dce
    m5: merge feature

The default search named f3, the commit that wrote the defect, while --first-parent named the merge commit m5, the point where the defect entered the mainline. Fixing the offending code needs the former; knowing which release first carried the problem needs the latter.

There is a second case where --first-parent earns its keep: repositories where intermediate commits on side branches do not even build. If the habit is to commit broken work in progress and tidy up before merging, the default search keeps stalling on those commits. Restricted to the mainline, each commit is generally intact.

After you have the culprit

One commit in hand is half the work done. Start by looking at what it changed.

$ git show --stat f1fec3f
 total.sh | 8 ++++++--
 1 file changed, 6 insertions(+), 2 deletions(-)

$ git log -p -1 f1fec3f
diff --git a/total.sh b/total.sh
@@ -1,7 +1,11 @@
 #!/bin/bash
+# refactor: iterate by index
 sum=0
-for n in "$@"; do
-  sum=$(( sum + n ))
+i=1
+while [ "$i" -lt "$#" ]; do
+  eval "v=\${$i}"
+  sum=$(( sum + v ))
+  i=$(( i + 1 ))
 done
 echo "$sum"

Here it is visible at a glance: the comparison should have been -le rather than -lt, which is why the last argument fell off. Real culprits are rarely that small, though. When the answer is a commit touching dozens of files, you have to narrow inside it. Bisect works in whole commits and cannot descend further, so start from the parent and add the changed files back one at a time.

$ git show --stat HEAD
 alpha.conf | 1 +
 beta.conf  | 1 +
 delta.conf | 1 +
 gamma.conf | 2 +-
 4 files changed, 4 insertions(+), 1 deletion(-)

$ git checkout HEAD~1            # move to the parent
$ for f in alpha.conf beta.conf delta.conf gamma.conf; do
>   git checkout main -- "$f"
>   bash ./check.sh; echo "  + $f -> $?"
> done
  + alpha.conf -> 0
  + beta.conf -> 0
  + delta.conf -> 0
  + gamma.conf -> 1        <-- breaks here

Down to a single file, and only that file's diff is left to read. If the file itself is large, the same trick applies at hunk level through git checkout -p. And when you want to work directly on the culprit, the git bisect reset refs/bisect/bad from earlier puts you there.

How this differs from git blame

Both look like they answer when did this happen, but the questions differ. blame names the commit that last touched a line; bisect names the point where behaviour changed. They usually agree, and they diverge often enough to matter.

Here is a repository where the defect landed in b3 and a later commit b5 changed only the indentation of the same file. Behaviour has been identical since b3.

$ git blame -- total.sh
^4ff6d88 ... 2) sum=0
75a65371 ... 3) i=1
75a65371 ... 4) while [ "$i" -lt "$#" ]; do
b44df25c ... 5)     eval "v=\${$i}"      <-- b5 (formatting only)
b44df25c ... 6)     sum=$(( sum + v ))
b44df25c ... 7)     i=$(( i + 1 ))

$ git bisect run bash ./check.sh
75a65371be49176fd1a34827c369875cd78e8a1e is the first bad commit
    b3: switch to an index loop

blame attributed the three key lines to the formatting commit b5, while bisect named b3, which changed the logic. Blame can be corrected with whitespace-ignoring (-w) or by excluding a commit (--ignore-rev), and both options do restore b3 here. Those neighbouring options are covered separately in the git history commands that deserve more love.

SituationRight toolWhy
You want to know why a line was written this waygit blameGives the commit and message per line immediately
You do not know when the behaviour changedgit bisectYou do not need to know which line is at fault
The problem is a combination of several filesgit bisectBlame can only answer one line at a time
You want to find when a string disappearedgit log -SFilters commits by change in content
You have the culprit and want to look insidegit show, log -pPicks up where bisect left off

When bisect is the wrong tool

It does not fit every regression. Several conditions rule it out fairly clearly.

  • Repositories that do not build commit by commit — too many skips leave you with several candidates. Restrict to the mainline with --first-parent, or narrow between release tags first and search precisely inside that range
  • Environment-dependent bugs — a problem caused by a library version, kernel or container image is not in the code history at all. What needs bisecting there is the environment, not the code
  • Data-dependent bugs — if it only reproduces on particular records, that data has to be pinned first so the test reproduces. Running against live data makes the judgements wobble
  • Problems that degraded gradually — if performance dropped one percent per commit, there is no single commit where it changed. Forcing a bisect with a threshold only means the threshold picks the answer
  • Problems whose cause you already know — when a stack trace points at a file and a line, blame is far quicker. Bisect is the tool for when there is no thread to pull
  • Ranges whose history was rewritten by a rebase — if the commits were never actually built in that order, intermediate commits may not work in the first place

There is also a trap specific to Windows. Bisect creates a reference with a long name, refs/bisect/good-<40 hex digits>. If the repository path is deep, that path crosses the 260-character limit and the session refuses to start. Varying only the path length gives this.

root=181  refpath=244  -> fine
root=192  refpath=255  -> fine
root=203  refpath=266  -> error: update_ref failed for ref
   'refs/bisect/good-27fe9984...': couldn't set
   'refs/bisect/good-27fe9984...'

The message never mentions path length, which makes the cause hard to find. Turning on core.longpaths=true did not help for this reference. Moving the repository to a shallower path was the reliable fix. The problem does not occur on Linux or macOS.

Summary

There is not much to memorise for daily use. Name the bad commit and the good commit, hand the judgement to a script, and reset when it is done. Three lines.

$ git bisect start <bad commit> <good commit>
$ git bisect run /tmp/judge.sh
$ git bisect reset

Everything else rides on the quality of the judgement script. A test that does not reproduce gives a wrong answer; a slow test multiplies that duration by ten; a carelessly leaked exit code turns a timeout into a defect. The search algorithm is finished work and needs nothing from you. The one thing a person has to prepare is a test that says worked or did not work without ever being wrong.

So the real order of learning this command is not syntax. When a problem shows up, confirm both endpoints by hand, shrink the test to a minimal reproduction, and only then start run. Follow that order and most regressions come down to a single commit inside the time it takes to drink a coffee.

What I could not verify

  • Every output came from a single environment, Windows plus Git Bash. Whether the wording of the messages or the propagation of exit codes is the same on Linux and macOS, or under other shells such as dash and zsh, was not checked
  • The value git bisect run itself returns to the shell on an abort was not consistent. A script exiting 128 produced 128, while one exiting 129 produced 127, and no rule for that was established. Judging by the message rather than by that exit code is the safer habit
  • The re-check behaviour for 126 and 127 is written up purely from observed output. The corresponding handling in the git source was not read
  • The 1,000-commit measurement used a synthetic repository. In a large repository with tens of thousands of files, checkout costs rise and git's own share of the time may shift
  • git bisect visualize requires gitk and was not run. --no-checkout was confirmed to work, but its behaviour in a bare repository was not tested
  • Why core.longpaths fails to help with the long path problem could not be determined, nor whether the reference file or the lock file is the one that trips the limit
