起因 - 不是「每45分钟」，而是「在0分和45分」

GeekNews介绍的cron.withuse.io那篇文章，标题就是结论：cron的*/45不是45分钟间隔。据GeekNews的摘要，这个表达式运行时45分钟与15分钟的间隔交替出现，不会形成稳定的45分钟周期。该网站的FAQ里有一句话概括了这个原理：step作用于斜杠前面的范围，而不是作用于时钟。

这个陷阱之所以长期存在，是因为表达式的样子与读者的直觉恰好相反。既然*/5是每五分钟、*/15是每十五分钟，就会推想*/45是每四十五分钟。前两种情况成立，只是因为5和15恰好能整除60，并不是因为cron承诺了「每N分钟」。本文剥掉这层巧合，直接写出规则本身。掌握规则之后，不只是*/45，像*/7、0 */5、0 0 */10这样结构相同的陷阱，光看表达式就能挑出来。

语法教程不是本文的目的。要讲的有三件事：step实际做什么的定义，执行该定义进行核算的结果，以及真正需要45分钟间隔时可用的方法。

step做什么 - 在字段内选取起始值的倍数

cronie文档(crontab(5))这样定义step：在范围后加斜杠和数字，表示在该范围内按这个数跳着走。示例是小时字段的0-23/2，即每两小时一次。紧接着就是本文主题的那句话：step只在其所应用的字段之内计算。文档的示例是小时字段的*/23，意思是在一个日历日内于0时和23时运行。同一文档还举了分钟字段的*/35：它不是35分钟间隔，而是每小时的0分和35分运行。

把这个定义拆开来看如下。

  • 范围在先。星号表示该字段的整个范围(分钟为0到59，小时为0到23)，step从起始值开始在这个范围内跳着走。
  • 计算在字段内结束。分钟字段的step不会跨过小时边界继续，而是每个小时的0分重新开始。
  • 结果是起始值的倍数。起始值为0时，只保留0、N、2N……中落在范围内的值。不是「每N分钟」，而是「在N的倍数时刻」。
  • 剩下的值在边界处被切断。如果范围长度不是N的倍数，从最后一个值到下一个范围起始值的间隔就会比N短。

第四条就是*/45的真面目。在分钟范围0到59内每隔45跳一次，剩下0和45，下一个是90，超出范围。时钟进入下一个小时、0分到来时，计算又从头开始。所以从0分到45分是45分钟，从45分到下一小时的0分是15分钟，这两种间隔交替出现。systemd.time文档也有同样结构的定义：在值后加斜杠和重复值，则该值本身以及该值加上重复值的各倍数都匹配。加在范围上时，从起始值出发、不超过终止值的各倍数匹配。写法不同，但「范围内以起始值为基准的倍数」这一定义是相同的。

执行验证 - 用Python展开范围的结果

定义是否成立，手算也能验证，但表达式一多就容易出错。下面的脚本不碰crontab，用range展开各字段范围，计算相邻运行时刻的间隔。它在Python 3.13上运行，没有负载。最后两个部分核算*/45一整天的时刻表，以及生成精确45分钟间隔的四行方案(第7节)。

import calendar
                    
                    # 在单个字段范围内展开step (不访问crontab)
                    def expand(lo, hi, step):
                        return list(range(lo, hi + 1, step))
                    
                    # 相邻运行的间隔，包含跨入下一个周期的区间
                    def gaps(vals, period):
                        g = [b - a for a, b in zip(vals, vals[1:])]
                        g.append(vals[0] + period - vals[-1])
                        return g
                    
                    cases = [("*/15 * * * *", 0, 59, 60, 15), ("*/20 * * * *", 0, 59, 60, 20),
                             ("*/45 * * * *", 0, 59, 60, 45), ("*/40 * * * *", 0, 59, 60, 40),
                             ("*/25 * * * *", 0, 59, 60, 25), ("*/7 * * * *", 0, 59, 60, 7),
                             ("0 */8 * * *", 0, 23, 24, 8), ("0 */5 * * *", 0, 23, 24, 5),
                             ("0 */7 * * *", 0, 23, 24, 7)]
                    for expr, lo, hi, period, step in cases:
                        v = expand(lo, hi, step)
                        print(expr, v, sorted(set(gaps(v, period))))
                    
                    # */45一整天: 时刻、间隔、每日运行次数
                    mins = [h * 60 + m for h in range(24) for m in expand(0, 59, 45)]
                    print([f"{t // 60:02d}:{t % 60:02d}" for t in mins[:6]],
                          sorted(set(b - a for a, b in zip(mins, mins[1:]))), len(mins), 1440 // 45)
                    
                    # 日字段: 2026年4月、5月、2月的0 0 */10
                    days = expand(1, 31, 10)
                    for m in (4, 5, 2):
                        n = calendar.monthrange(2026, m)[1]
                        d = [x for x in days if x <= n]
                        print(m, d, d[0] + n - d[-1])
                    
                    # 用四行得到精确的45分钟间隔 (3小时周期，含跨午夜区间)
                    lines = [(0, (0, 21, 3)), (45, (0, 21, 3)), (30, (1, 22, 3)), (15, (2, 23, 3))]
                    t = sorted(h * 60 + m for m, (a, b, s) in lines for h in expand(a, b, s))
                    print(sorted(set(y - x for x, y in zip(t, t[1:] + [t[0] + 1440]))), len(t))

从结果中可以读出以下几点。

  • 第三行是*/45。分钟值只有0和45，间隔集合是{15, 45}。这意味着45分钟不是单一种类的间隔。
  • 第十行是一整天。时刻表为00:00、00:45、01:00、01:45……，每天运行48次。真正的45分钟周期应是1,440分钟除以45得32次，所以实际上多运行了一半。
  • cronie文档举的小时字段*/23，用同一函数展开得到[0, 23]。文档的描述与脚本的规则并不矛盾。

一般规则 - step能整除与不能整除时

把上面的结果一般化，判别式归结为一条：字段的取值个数(分钟60、小时24)能被step整除，则跨越边界后间隔保持不变；不能整除，则边界处会插入一次较短的间隔。表格是同一脚本的展开结果按表达式整理而成。间隔取两个以上值时，按顺序列出。

*/20 * * * *每小时0、20、40分固定20分钟—
*/45 * * * *每小时0、45分45分钟与15分钟交替有

从表中可以看出三条规则。

  • 分钟字段中安全的step是60的约数：1、2、3、4、5、6、10、12、15、20、30。这些值在任何时刻都给出相同的间隔。
  • 小时字段中安全的step是24的约数：1、2、3、4、6、8、12。5或7看起来像整小时单位，但在一天结束处会插入较短的间隔。
  • 非约数的值不能读作「每隔多少分钟」，而要读作「在一天(或一小时)内N的倍数的时刻」。养成这种读法，光看表达式就能认出陷阱。

step相对范围长度越大，偏差越突出。45分钟接近60分钟，剩下的碎片长达15分钟，结果不是「偶尔插入一次短间隔」，而是每日运行次数从32次升到48次，增加到1.5倍。

在小时和日字段中偏差更明显

分钟字段的偏差在一个小时内就结束，不易察觉。小时字段和日字段则不同。0 */5 * * *在0、5、10、15、20时运行，20时之后的下一次是次日0时，所以只有最后一个间隔是4小时。相信「每5小时运行一次」的运维人员，会在20时运行4小时后的午夜遇到意料之外的运行。

日字段还有一个特点。日字段的范围1到31，实际长度因月份而异。0 0 */10 * *选取1、11、21、31日，但当月没有31日时，21日之后的下一次运行就是下个月1日。上面脚本对2026年三个月计算出的值如下。

2026年的月份运行的日期从最后一次运行到下月第一次运行
4月(30天)1、11、21日10天
5月(31天)1、11、21、31日1天
2月(28天)1、11、21日8天

5月份，31日运行后仅隔一天，6月1日又会运行。也就是说，期望「每十天一次」的任务，可能在月末连续两天运行。月份字段的*/5同样在范围1到12内只剩1月、6月、11月，11月之后是下一年的1月，因此会插入两个月的间隔。

所以替代方案不在于继续改写表达式，而在于采用字段内倍数计算之外的其他基准(第7节)。

需要精确的45分钟间隔时

需要真正的45分钟周期时可用的方法，按依据的种类分为三种。

1. systemd timer的相对定时器(文档已确认)。在systemd.timer文档中，OnUnitActiveSec=是以定时器所激活的单元上次被激活的时刻为基准的定时器。写成OnUnitActiveSec=45min，则与时钟时刻无关，上次运行45分钟后就会进行下一次运行。文档同时定义了OnUnitInactiveSec=，它以单元上次被停用的时刻为基准。运行所花的时间是否计入间隔，是两个选项的区别，用哪一个取决于任务耗时是否有波动。与决定首次运行时点的其他选项的组合，本文没有验证。

2. 只用cron写四行(计算验证)。45分钟与24小时的最小公倍数是180分钟，即3小时。3小时周期内有四个运行时刻(0:00、0:45、1:30、2:15)，分成四行写出即可。

  • 0 0-21/3 * * * — 0时、3时、……、21时的0分
  • 45 0-21/3 * * * — 0时、3时、……、21时的45分
  • 30 1-22/3 * * * — 1时、4时、……、22时的30分
  • 15 2-23/3 * * * — 2时、5时、……、23时的15分

上面脚本的最后一段展开了这四行所产生的时刻，并计算了包含跨午夜区间(23:15到00:00)在内的相邻间隔。结果是间隔集合只有{45}一个值，每天32次。这种方法是与时间边界咬合的时钟基准调度，因此没有验证有夏令时的时区以及时刻发生跳变的环境。

3. 在任务内部检查时间(一般设计，没有文档依据)。以较短的周期(例如每分钟)唤醒脚本，脚本把上次成功时间记录在文件中，若尚未过45分钟就立即退出。本文引用的文档中没有写这种方式。它的特点是在任何调度器下都能用，保证间隔的责任从表达式转移到了脚本。

三种方法的选择标准很简单。在systemd环境中，第一种最直接。在只能使用表达式的环境中，不执着于45分钟而改成60的约数(30分钟或60分钟)最安全；如果确实需要45分钟间隔的含义，则使用第二种或第三种。

在现有crontab中查找陷阱的只读检查

已在运行的服务器的crontab里，可能还留有同样的陷阱。下面的检查全部是只读的，没有负载。

  • 用crontab -l仅输出当前用户的登记内容。不使用编辑选项(-e)。
  • 收集*/N形式的表达式，看N在分钟字段中是否为60的约数、在小时字段中是否为24的约数。
  • 对非约数的表达式，按上面表格的方法展开实际运行时刻，并与任务意图(要精确间隔，还是只要大致频率)对比。
  • 日字段或月字段的*/N无论是否为约数，间隔在月末、年末都会波动，因此另行标记。
  • 如果展开结果与意图不同，先确定该任务是否需要精确间隔，再决定是否改写表达式。不需要的话，改成60的约数就够了。
