Introduction: the sentence to read first

Agent platform announcements mostly wear the same face. There is a chat surface, it connects to internal data, and it automates things. This one looks no different on the outside. What is different is a single sentence attached to it: server code runs in a Dynamic Worker with global outbound networking disabled.

That one line is where a placement decision starts, not a product tour. Outbound being closed by default is a security statement, but it is simultaneously a statement that the shape of acceptable work has already been fixed. Code that needs arbitrary external calls simply does not run here. And what fills that gap is Gatekeeper.

Cloudflare open sourced Cloudflare OS on August 5, 2026, during Agents Week. It is a rebuild of the tool the company had been running internally, the license is Apache-2.0, and you can deploy it into your own Cloudflare account with your own Access policies and AI Gateway configuration.

This article does not walk the feature list. It lands on one question instead: is there a reason to put my workload here? What got bundled, what the execution model forces, which work fits and which work is structurally excluded, and why production adoption is premature right now.

Do not confuse this with the opposite-facing product from the same company. Cloudflare also ships technology for detecting AI agents that arrive at your site. That side is covered in Precursor Arrives - Why Cloudflare Reads Whole Sessions to Catch AI Agents. This article is the opposite axis: the runtime that runs agents. That the same company shipped both in the same week says something about where this market currently sits.

1. The three parts Cloudflare OS actually bundles

The name invites a misreading. It is not a new operating system and not a new infrastructure layer. Getting its nature right keeps the evaluation pointed in the right direction.

1.1 New product, or reorganization?

Neither. Cloudflare rebuilt the application it had been running internally and released it as open source. The announcement puts it plainly, 「Today, we are open sourcing a new version of Cloudflare OS」, and the first version was an internal tool opened to every employee in May of the same year. Cloudflare states that people outside engineering started using it to draft documents, build slides, and automate repeatable work.

  • It is an application you place inside a Cloudflare account, not a cloud you subscribe to
  • So the opening question shifts from whether to adopt a new vendor to whether to put this inside the account you already have
  • If you already run Workers and Access, evaluation cost is markedly lower. If you do not, account setup and Access policy design become prerequisite work
  • The internal track record carries weight as evidence. This is a rebuild of something thousands of people used every day, not a demo assembled for a launch

1.2 Broken into three parts

The announcement describes it as the combination of three parts. These are not independently valuable pieces. They stack in an order where each one needs the one before it.

  • An agent workspace. Preloaded with the curated context and skills the company has collected, with an isolated runtime attached where agents can write and run code
  • A security and governance framework. The layer for reaching internal data and services safely. The starting point is that every agent and app begins with access to nothing
  • A platform for personal, modifiable apps. The execution base for apps people build, share, and keep changing
  • The first part alone becomes dangerous the moment it touches internal data. The second alone has nothing to do. The third only produces work that persists when the first two exist
  • Research and questions use code execution to search and analyze instead of loading whole datasets into the model's context window. The design deliberately decouples context budget from data size
  • Generated documents and spreadsheets stay connected to their live sources and update as the underlying data changes. They can still be exported to familiar formats

2. The agent execution model - every app is a Worker

Compressed to one sentence: every app the agent builds is a Worker. Everything else follows from that.

2.1 Client code and server code are generated together

Ask the workspace to build an app and the agent writes two parts. Client code that renders the UI in the browser, and server code that stores state and implements behavior. The server side is loaded on demand as a Dynamic Worker and instantiated as a Durable Object Facet. Each app gets its own SQLite database, separate from the Cloudflare OS runtime managing it.

Browser
  └─ Client code (sandboxed frame)
        │  Cap'n Web RPC
        ▼
Dynamic Worker  ← loaded on demand
  └─ Durable Object Facet
        └─ App-owned SQLite  (separate from runtime store)

The only way out is a capability a Gatekeeper handed over

Calling the server from the client does not look like a remote call. The shape shown in the announcement is this.

const issues = await app.listIssues({
  status: "done",
});
  • The browser client talks to the server over Cap'n Web, Cloudflare's open source object-capability RPC system
  • That makes the interface humans build and the interface agents call the same object. No separate agent-only API is needed
  • Because databases are per app, a schema accident in one app does not spread to another
  • Conversely, sharing data between apps means building that path explicitly. The design chose isolation over convenience

2.2 What closed-by-default egress really means

This is the constraint that most determines the platform's character. Server code runs in a Dynamic Worker with global outbound networking disabled, and client code runs in a sandboxed frame in the browser. Both reach external systems only through capabilities that were explicitly provided.

  • Code the agent generated cannot ship data to an arbitrary address. Even if prompt injection poisons that code, the exfiltration path itself does not exist
  • At the same time, code that calls any external API it likes does not run here. Every connection you need has to be built as a Gatekeeper first
  • Which exposes the true adoption cost. Deploying the platform is the small part; writing a Gatekeeper per service you connect is the real workload
  • The public repository notes it is still refining tooling for configuring external services, adding that many service providers intentionally do not make this easy

2.3 How far does the code-running runtime go

In the same week Cloudflare also released @cloudflare/computer, an agent runtime, as an early preview. It is an open source runtime that picks between isolates and containers depending on the task, running light work in Dynamic Worker isolates and work needing native binaries or specific system tools in containers. State moves between the two through a virtual filesystem backed by SQLite. Cloudflare states the goal that containers are required for less than 10 percent of the work.

But do not glue these two together. Neither the Cloudflare OS announcement nor the @cloudflare/computer announcement states that they are the same thing or that one is a component of the other. They are separate announcements released in the same week. Designing on the assumption that containers come attached anyway is not supported by either.

3. Gatekeeper - granting access without handing over credentials

With egress closed, a door has to be cut somewhere. That door is called a Gatekeeper.

3.1 The credential never reaches the agent

A Gatekeeper is a service-specific Worker that sits between Cloudflare OS and an external service. It handles OAuth, holds the credential, enforces policy, and records what was read. What the agent's generated code receives is not a secret but a typed binding.

const issues = await env.PROJECT.listIssues({
  teamId: "ENG",
  state: "open",
});
  • The announcement explicitly notes that handing API keys to people and agents is dangerous. Keys cannot be scoped down and leave no trace when revoked
  • A Gatekeeper can grant access to a single repository, and allow reading issues while denying source code
  • Every agent and app starts with access to nothing. Resources are requested as needed
  • Actions with external side effects also pass through this layer. So the record of who did what lives in the permission layer rather than in application logs

3.2 Observations constrain sharing

This is where it diverges most from familiar permission models. Cloudflare OS records every resource agents observe, and those observations remain attached to the agent and its work. When another person tries to open the workspace, interact with the agent, or view what it produced, Gatekeepers verify that person's access to the observed resources.

  • The stated goal is that sharing a dashboard must not become a way to share the underlying table with people who could not access it directly
  • A read of sensitive data can also prevent the agent from writing to certain destinations. Read history narrows subsequent write permission
  • This property collides head-on with convenience. The organization has to understand up front that sharing something the recipient cannot open is correct behavior, not a bug
  • An organization without a data classification scheme will end up building one the moment this layer is turned on. That is closer to a precondition than a side effect

3.3 Why MCP alone is not enough

Cloudflare OS supports existing Model Context Protocol servers your organization already uses via MCP Server Portals. Yet the announcement is explicit about why another layer sits on top without replacing MCP: MCP alone does not tell us which underlying resources an agent has observed.

  • MCP is a protocol for exposing tools. What a tool returned and which source that data came from sit outside the protocol
  • So the question of who is allowed to view this output cannot be answered at the MCP layer. Observation records have to be accumulated separately
  • If you already operate several MCP servers, not having to discard that investment lowers the adoption cost meaningfully
  • If you operate none, defining tools for every system you intend to connect comes before turning this platform on

4. Two places where it diverges from ordinary serverless

Sitting on Workers, it inherits serverless properties wholesale. Two places are clearly different.

4.1 The deployment unit disappears

Ordinary serverless deploys functions. Change the code and the pipeline runs again, a version appears, a rollback target appears. Cloudflare OS apps do not pass through that, because they are loaded at request time as Dynamic Workers.

  • Which is why someone outside engineering can modify their own app with AI instead of filing a feature request. That is the point the announcement emphasizes
  • There are two sharing modes. Share the app itself for real-time collaboration, or share a blueprint so others create independent copies
  • A blueprint copy contains the original code but has independent state and connected resources. Good for taking someone else's tool and running it on your own data
  • Something is lost in exchange. No deployment pipeline means no place to attach code review or an approval gate. If internal policy requires deployment approval, that property is the first thing to negotiate

4.2 State lives with the app

Function-style serverless assumes statelessness and pushes state to external stores. Here it is reversed. Each app has a Durable Object Facet and SQLite attached, so state lives in the same place as execution.

  • Building a small internal tool requires no separate database provisioning. Startup cost drops sharply
  • Concurrent editing comes naturally. Multiple teammates working inside the same app at once is a design assumption
  • At scale the property inverts. Because state is bound to the execution unit, the horizontal scaling axis is fixed at the app boundary
  • Deterministic workflows sit on the same axis. They run on demand, on a schedule, or when an external event triggers them

5. What the numeric limits have already decided

This is the first thing to look at in a placement decision. The Cloudflare OS announcement carries no limit figures of its own. But since every app is a Worker, the Workers platform limits become the app limits verbatim.

5.2 The work these limits actually cut

Reading the table is simple. Run your work down it from the top, and if it trips on even one line, that work does not belong here.

  • Long-running GPU training and self-hosted large model serving. A different class of compute entirely. Inference here exits through AI Gateway to an external model; it does not run in place
  • Analysis holding gigabytes in memory. The 128MB cap blocks it directly. Either stream it in pieces or run it somewhere else
  • Fan-out aggregation hitting dozens of backends at once. Six simultaneous outgoing connections per request cuts parallelism at that line
  • Single batches running tens of minutes. The Cron family stops at 15 minutes, so splitting and chaining work becomes mandatory design
  • Toolchains depending on native binaries. They do not run in a V8 isolate. If containers are required, the work sits outside this platform's app model
  • Conversely, lookup-and-tidy work finishing inside a few hundred milliseconds clears every one of these limits comfortably. And a large share of internal business automation genuinely lives there

6. Data locality - the fork for regulated workloads

For a platform handling internal data, where the data sits decides whether adoption is possible at all. App state goes into Durable Objects, and the location rules for Durable Objects are already documented.

6.1 Jurisdictions and location hints are different things

  • Jurisdictions force an object to run and store data only within a region for regulatory compliance. Three are offered: eu, us, and fedramp
  • Location hints guide initial placement when jurisdictional enforcement is not required. Available values are wnam, enam, sam, weur, eeur, apac, apac-ne, apac-se, oc, afr, and me
  • Do not mix the two. Hints are best effort and not a guarantee. The documentation states an object will not necessarily be instantiated in the hinted location
  • Once created, a Durable Object does not relocate to another data center. Only the first get() call participates in placement
  • The identifier is logged outside the specified jurisdiction for billing and debugging purposes. If the identifier itself is sensitive in your design, review that first

6.2 What to check under a national residency requirement

Many countries are absent from the jurisdiction list. If you carry a requirement to keep domestic data domestic, that axis has to be settled before anything else.

  • Absence from the jurisdiction list is not the same as absence of local data centers. But the fact that no enforcement mechanism is offered stands regardless
  • A location hint such as apac-ne only steers toward a broad region; it is not a country-level guarantee and cannot serve as a compliance basis
  • Inference requests exit through AI Gateway to external model providers. Where the provider processes that data becomes a separate review item
  • The observation records Gatekeepers keep are data too. A list of what was read is an audit asset and simultaneously something that needs a retention policy

7. Where the cost actually comes from

One thing needs stating up front: the announcement carries no pricing for Cloudflare OS itself. It is open source and deployed into your own account, so cost arrives not as a software fee but as resource consumption inside that account.

7.1 At least three billing axes

  • Compute and state. Workers execution plus Durable Objects storage and requests. As app count grows, Durable Object count grows, and this axis grows with it
  • Model inference. Every inference request crossing AI Gateway. In practice this axis usually moves the invoice most
  • Identity. Entry is controlled by Cloudflare Access, so user population sets this axis
  • A fourth axis is invisible on any invoice: the human time spent writing and maintaining Gatekeepers. Every new connection adds code, and that code sits in the permission layer, so it cannot be left open to everyone

7.2 What the announcement does say about cost control

There is no price list, but the control mechanism is described clearly. Because all inference calls route through AI Gateway, an organization chooses which models are available and can track spending, set budgets, and enforce rate limits by person or by team. Every request is attributed to the person, team, or workspace that made it.

  • Per-request attribution means cost can be pushed back to a department. In an internal rollout that property is political, not technical
  • Organizational control over model selection sits in the same logic. Pinning an appropriate model per task structurally prevents an expensive model from attaching itself to trivial work
  • What happens on budget overrun, whether to reject or downgrade to a cheaper model, is not in the announcement. That is an operational policy you write yourself

What to read in this table is not superiority but the exchange. Cloudflare OS gives up execution time, memory, and outbound freedom, and takes back permission decomposition, startup speed, and non-engineer editability. Whether that exchange is a gain depends entirely on how much of your internal work sits on the winning side.

8.3 Reducing the decision to three questions

  1. Does this work fit inside 128MB and 5 minutes of CPU? If not, the rest of the discussion is moot
  2. How many external systems must be connected, and is there someone to write a Gatekeeper for each? That number is the real adoption cost
  3. Can the organization accept output being blocked by permissions when shared? If not, you will turn off the platform's central mechanism, and little remains after that

9. Why it should not go into production yet

The public repository says this about itself. Skipping this part throws the whole evaluation off.

  • The repository states that v2 is very capable but still has many rough edges and describes a state of heavy development. That is not a production-ready declaration
  • Self-hosted deployment is marked as coming soon. The path available today runs through a Cloudflare account
  • Tooling for configuring external service connections is also described as still being refined. The more systems you connect, the more of that unfinished stretch you fill in yourself
  • The license is Apache-2.0. Internal modification and redistribution are unobstructed, but an open license and production readiness are separate matters
  • So what is worth doing right now narrows to three things. Deploy a pilot and see whether Access and AI Gateway configuration line up with internal rules, write one or two Gatekeepers to find the right permission granularity, and measure whether your real work fits inside the limits

10. Decisions to settle before adopting it

  • Build a data classification scheme first. Observation-based sharing restriction cannot be switched on without one. That is organizational agreement, not platform configuration
  • Name an owner for Gatekeepers. This is permission-layer code and cannot be open to everyone. It should be the one code path that never deploys without review
  • Write down the model allow-list and the budget-overrun behavior. Reject or downgrade is not in the announcement, so the organization decides
  • Set an app retirement policy from day one. Every app carries a Durable Object and SQLite, so abandoned apps persist as both cost and data
  • Decide the retention period for observation records. They are an audit asset and sensitive material at once. Do not make one table serve both operational and audit retention
  • Teach the difference between sharing a blueprint and sharing an app. One is a copy with separate state, the other is real-time collaboration. Confusing them mixes data
  • Resolve the conflict with deployment approval policy first. The absence of a deployment unit is not negotiable later. Either change the policy or narrow this platform's scope
  • Confirm the exit path. There has to be a way to pull data out of per-app SQLite. Being open source does not automatically guarantee portability

11. What could not be confirmed

Collecting in one place the items for which no basis was secured.

  • Pricing for Cloudflare OS itself. The announcement carries none. Only the structure, billing through account resource consumption, is confirmed
  • Official release stage labeling. The announcement says it is available today and the repository says it has many rough edges. No formal beta or GA label was confirmed
  • Individual limits for Dynamic Workers and Durable Object Facets. The limits table here follows the Workers platform documentation; whether these two features carry separate limits was not confirmed
  • Concurrent app counts and per-workspace ceilings. No figures appear in either the announcement or the repository
  • Concrete internal deployment scale. Only the phrasing that thousands of people across every function use it daily; exact headcount and app counts are not public
  • SLA and support structure. How far incident response responsibility extends in an open source distribution was not confirmed
  • Processing location on the model provider side. What happens after AI Gateway is a per-provider contractual matter and outside this announcement's scope
  • Relationship to R2, D1, Containers, and Workers AI. None of these appear as components in this announcement. Whether they integrate was not confirmed

12. Frequently asked questions

Is Cloudflare OS a new product or a repackaging of existing ones?

Neither. Cloudflare rebuilt the application it had been running internally and released it as open source. The announcement puts it plainly, 「Today, we are open sourcing a new version of Cloudflare OS」, and the first version was an internal tool opened to every employee in May of the same year. So no new infrastructure layer appeared. What opened is an application sitting on top of existing pieces such as Workers, Durable Objects, Access, and AI Gateway, together with the delegation model that application requires, named Gatekeeper. That changes the first question of any evaluation. It is not whether to adopt a new cloud, it is whether to place this application inside the Cloudflare account you already have.

How does an agent-built app run, and where does its state live?

Every app is a Worker. The agent writes client code that renders the interface in the browser and server code that stores state and implements behavior. The server is loaded on demand as a Dynamic Worker and instantiated as a Durable Object Facet. Each app gets its own SQLite database, separate from the Cloudflare OS runtime managing it. The browser client talks to the server over Cap'n Web, an object-capability RPC system. The important property here is that there is no separate deployment unit. Because changing an app does not pass through a deployment pipeline, someone outside engineering can modify their own app instead of filing a feature request and waiting for a developer.

How is Gatekeeper different from handing out API keys?

The credential never reaches the agent. A Gatekeeper is a service-specific Worker sitting between Cloudflare OS and an external service. It handles OAuth, holds the credential, enforces policy, and records what was read. Code the agent generates receives typed bindings rather than secrets. That lets access be scoped to a single repository, or to reading issues but not source code. On top of that sits the observation record. Every resource the agent observes stays attached to the agent and its work, and when another person tries to open that work, Gatekeepers verify that person's access to the observed resources. A read of sensitive data can also prevent the agent from writing to certain destinations.

Which workloads fit this platform and which do not?

What fits is short, distributed execution. Pulling from several internal systems and summarizing, repeatable procedures where a human judges at only a few points, small team-scale internal tools. What does not fit splits three ways. First, long-running GPU training or serving a large model yourself. Second, large state, because a Workers isolate caps JavaScript heap and WebAssembly allocations together at 128MB, so holding big datasets in memory is out from the start. Third, anything needing arbitrary outbound calls, because server code runs in a Dynamic Worker with global outbound networking disabled, and every external path has to be handed over explicitly as a capability.

Can it go into production inside a company right now?

It is early for production. The public repository states that v2 is very capable but still has many rough edges and describes a state of heavy development. Self-hosted deployment tooling is marked as coming soon. The license is Apache-2.0, so internal modification and redistribution are unobstructed, but an open license and production readiness are separate matters. Three approaches are worth the time right now. One, deploy it into your own Cloudflare account as a pilot and see whether Access policies and AI Gateway configuration line up with internal rules. Two, write one or two Gatekeepers yourself to find the right granularity for permission decomposition. Three, measure whether your actual work fits inside 128MB and the CPU limits.

Conclusion: three things to take today

First, this platform's character is set by its constraints, not its feature list. Egress closed by default and 128MB per isolate; those two lines sort almost everything into what can enter and what cannot. Running your own work against those two lines is far faster than reading the glossy parts of the announcement.

Second, the adoption cost is the number of Gatekeepers, not the deployment. Deploying needs one account, but every external system you connect needs a permission-brokering Worker written and maintained. And that code lives in the permission layer, so not everyone can touch it. Counting your connection targets is what reveals the real size of the project.

Third, observation-based sharing restriction is an organizational decision, not a technical one. The platform's core only works if you can accept that sharing output the recipient cannot open is correct behavior. If you cannot accept it, you will switch that mechanism off, and what remains is just another internal chatbot.

One closing note. What lasts from this announcement is not the name Cloudflare OS. It is the direction: give agents capabilities instead of credentials, and make what they have read an input to permission decisions. That direction resurfaces in any internal agent design regardless of which platform you pick. Whether it is usable today or not, the design principle is worth reading now.
