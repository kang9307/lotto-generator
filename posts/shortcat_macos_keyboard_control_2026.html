Shortcat - 마우스 없이 키보드만으로 macOS 전체 제어 2026

UI 요소를 색인하는 커맨드 팔레트로 손을 키보드에 묶어 두기

2026-06-09 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 마우스로 가는 그 짧은 왕복이 쌓이면

코드를 한참 작성하다가 사이드바의 파일 하나를 클릭하기 위해 오른손을 키보드에서 떼 트랙패드로 옮깁니다. 클릭하고, 다시 키보드로 돌아옵니다. 단 1초도 안 되는 동작입니다. 그런데 이 짧은 왕복을 하루에 수백 번, 한 달에 수천 번 반복한다고 생각해 보면 이야기가 달라집니다. 손목의 미세한 피로가 쌓이고, 작업 흐름은 매번 잘게 끊깁니다. Shortcat은 바로 이 '마우스로 가는 짧은 왕복'을 없애려는 macOS 도구입니다. 2026년 6월 8일 GeekNews(news.hada.io)에서 1위를 차지하며 다시 주목받았습니다.

핵심 아이디어는 단순하면서도 강력합니다. 화면에 떠 있는 모든 UI 요소 - 버튼, 링크, 메뉴 항목, 텍스트 필드, 창 - 를 접근성 API로 색인한 뒤, 커맨드 팔레트에서 이름이나 힌트 라벨로 검색해 키보드만으로 실행하는 것입니다. 마우스 커서를 특정 좌표로 끌고 가는 대신, 원하는 요소의 이름을 타이핑하면 됩니다. 이 글에서는 Shortcat이 푸는 문제, 접근성 API 기반의 작동 원리, 키보드 우선 워크플로의 생산성, Vimium·Homerow·Vimac·Keyboard Maestro 같은 유사 도구 비교, 설정과 활용 팁, 그리고 솔직한 한계까지 차분히 정리하겠습니다.

1. Shortcat이 푸는 문제 - 마우스 왕복, RSI, 접근성

Shortcat을 이해하려면 먼저 그것이 '무엇을 위한 해결책인가'를 봐야 합니다. 표면적으로는 생산성 도구지만, 그 아래에는 세 가지 서로 다른 문제가 깔려 있습니다.

  • 마우스 왕복의 비효율: 키보드로 입력하다가 마우스로 손을 옮기고, 목표를 조준해 클릭하고, 다시 키보드로 돌아오는 '호밍(homing)' 동작은 측정 가능한 시간 손실입니다. 개별로는 미미해도 누적되면 상당합니다.
  • RSI(반복 긴장성 손상): 마우스를 끊임없이 쓰는 작업은 손목과 팔에 부담을 줍니다. RSI 예방 자료들은 한결같이 단축키·매크로·핫키 같은 키보드 기반 도구를 마우스 사용을 줄이는 핵심 수단으로 권합니다.
  • 접근성: Shortcat이 의존하는 기술 자체가 시각 장애 사용자를 위한 스크린 리더 기반 위에 서 있습니다. 키보드 우선 제어는 본질적으로 더 포용적인 인터페이스를 만드는 방향과 맞닿아 있습니다.

즉 Shortcat은 단순히 '빨라지는 도구'가 아니라, 입력 효율·건강·접근성이라는 세 축을 동시에 건드리는 도구입니다. 이 점이 단순 단축키 확장 프로그램과의 결정적 차이입니다.

2. Shortcat이란 무엇인가 - 한 문장 정의

공식 소개에 따르면 Shortcat은 "Mac을 위한 범용 커맨드 팔레트(universal command palette)"입니다. 버튼을 클릭하고, 텍스트 필드에 포커스를 주고, 메뉴 명령을 실행하고, 창을 전환하는 일을 - 마우스 없이 - 키보드만으로 처리합니다. Finder든 Spotify든 거의 모든 앱의 UI 요소에 키보드로 접근할 수 있게 해 주는 백그라운드 유틸리티입니다.

여기서 '커맨드 팔레트'라는 표현이 중요합니다. VS Code나 다른 에디터를 써 본 사람이라면 익숙할 텐데, 단축키로 검색창을 띄우고 명령 이름을 입력해 실행하는 그 패턴을 운영체제 전체로 확장한 것이 Shortcat의 본질입니다. 특정 앱의 명령에 국한되지 않고, 화면에 보이는 모든 클릭 가능한 요소가 검색 대상이 됩니다.

마우스가 '어디를 가리킬까'를 묻는다면, Shortcat은 '무엇을 실행할까'를 묻는다. 좌표 대신 이름으로 인터페이스를 다루는 전환이다.

3. 작동 원리 - 접근성 API로 UI를 읽는다

Shortcat의 마법은 macOS의 접근성(Accessibility) API에 있습니다. 이 API는 원래 VoiceOver 같은 스크린 리더가 화면의 내용을 시각 장애 사용자에게 읽어 주기 위해 만들어졌습니다. 운영체제는 이 API를 통해 각 앱의 버튼·라벨·메뉴·창 같은 UI 요소를 구조화된 트리로 노출합니다.

Shortcat은 바로 이 트리를 읽습니다. 작동 흐름을 단계로 풀면 다음과 같습니다.

1. 단축키 입력      Shortcat 팔레트 호출 (예: ⌘ + Space 류의 핫키)
   │
   ▼
2. UI 요소 색인     접근성 API로 현재 화면의 클릭 가능한 요소 수집
   │
   ▼
3. 힌트/검색        요소에 힌트 라벨 오버레이 + 이름 퍼지 검색
   │
   ▼
4. 키보드 실행      라벨 입력 또는 이름 검색 후 Enter → 클릭/메뉴 실행

핵심은 Shortcat이 화면을 '픽셀'로 보지 않는다는 점입니다. 이미지 인식이나 OCR이 아니라, 앱이 접근성 API에 스스로 신고한 구조적 정보를 읽습니다. 그래서 정확하고 빠르며, 동시에 '앱이 접근성 API에 정보를 잘 노출하느냐'에 정확도가 좌우된다는 한계도 여기서 나옵니다. 잘 만들어진 네이티브 앱일수록 Shortcat이 잘 작동합니다.

4. 힌트 모드와 검색 모드

Shortcat이 요소를 다루는 방식은 크게 두 가지입니다. 사용 상황에 따라 골라 쓰면 됩니다.

4.1 힌트(라벨) 모드

팔레트를 띄우면 화면의 클릭 가능한 요소 위에 짧은 문자 라벨이 겹쳐 표시됩니다. 원하는 요소의 라벨 문자를 입력하면 그 요소가 즉시 실행됩니다. 화면에 요소가 많지 않을 때, 또는 이름을 모르는 아이콘 버튼을 빠르게 누를 때 유용합니다. Vimium의 'f' 힌트와 같은 발상입니다.

4.2 검색(타이핑) 모드

요소의 이름이나 라벨 텍스트를 직접 타이핑하면 퍼지 검색으로 후보가 좁혀집니다. 예를 들어 '저장' 버튼을 찾고 싶으면 그 일부만 입력해도 매칭됩니다. 이름을 아는 버튼·링크를 누를 때, 특히 화면에 같은 종류 요소가 잔뜩 있을 때 강력합니다. Shortcat은 힌트와 타이핑을 모두 지원한다는 점에서, 힌트 위주인 일부 경쟁 도구와 차별화됩니다.

5. 메뉴 퍼지 검색 - 숨은 강점

Shortcat의 진가는 메뉴바 명령을 다룰 때 드러납니다. macOS 앱은 메뉴바에 수십·수백 개의 명령을 품고 있지만, 단축키가 할당된 것은 일부뿐이고 나머지는 마우스로 메뉴를 헤집어야 찾을 수 있습니다.

Shortcat은 현재 앱의 메뉴 항목을 번개처럼 빠른 퍼지 검색으로 노출합니다. 더 영리한 점은 동의어(synonym)를 지원한다는 것입니다. 소개에 따르면 'Delete item'이라는 명령을 'delete'뿐 아니라 'remove', 'clear', 'destroy' 같은 단어로도 찾을 수 있습니다. 명령의 정확한 이름을 기억하지 못해도 의미만 알면 도달할 수 있다는 뜻입니다. 이 메뉴 검색만으로도 많은 사용자가 Shortcat을 상시 켜 둘 이유를 찾습니다.

6. 키보드 우선 워크플로의 생산성

키보드만으로 컴퓨터를 다루는 것이 정말 더 생산적일까요? 답은 '경우에 따라, 그리고 시간이 지날수록'입니다.

RSI·생산성 관련 자료들은 핵심을 일관되게 말합니다. 단축키와 핫키, 매크로 같은 키보드 기반 흐름은 마우스/트랙패드 부담을 줄이고, CLI 같은 키보드 중심 작업은 1~3년의 숙련을 거치면 GUI·마우스 기반 흐름의 생산성에 도달하거나 그것을 넘어선다는 것입니다. 즉 즉효약이 아니라 복리로 쌓이는 투자입니다.

키보드 우선 워크플로의 이점을 정리하면 다음과 같습니다.

  • 맥락 전환 감소: 손이 홈 포지션을 떠나지 않으니 입력 흐름이 끊기지 않습니다.
  • 조준 부담 제거: 작은 버튼을 마우스로 정밀 조준하는 인지·근육 부담이 사라집니다.
  • 일관된 멘탈 모델: '이름으로 실행한다'는 한 가지 패턴이 거의 모든 앱에 동일하게 적용됩니다.
  • RSI 완화: 마우스 의존을 줄여 손목·팔의 누적 부담을 분산합니다.

물론 이 모든 이점은 학습 곡선이라는 비용을 먼저 치러야 얻어집니다. 비슷한 '도구가 흐름을 바꾸는' 사례는 터미널 성능과 개발자 생산성에서도 다룬 바 있습니다.

7. 유사 도구 비교 - Vimium, Homerow, Vimac, Keyboard Maestro

Shortcat은 키보드 우선 제어라는 넓은 생태계의 일부입니다. 자주 비교되는 도구들을 정리하면 선택이 쉬워집니다.

도구 범위 방식 비용/상태
Shortcat macOS 전체 힌트 + 타이핑 검색, 메뉴 퍼지 무료 / 최근 유지보수 활발하지 않음
Homerow macOS 전체 힌트 라벨, 키보드 스크롤 유료 / Vimac의 후속, 활발
Vimac macOS 전체 힌트, HJKL 스크롤 모드 무료 / 개발 중단(Homerow로 이전)
Vimium 브라우저 한정 힌트, Vim 키 내비게이션 무료 / 브라우저 확장
Keyboard Maestro macOS 전체 매크로/자동화 중심 유료 / 성격이 다른 자동화 도구

해석을 덧붙이면, Vimium은 브라우저 안에서만 동작하므로 Shortcat과 직접 대체 관계는 아닙니다. Vimac은 사실상 단종되어 개발이 유료 앱 Homerow로 이전했습니다. Homerow는 Vimac의 더 빠르고 세련된 후속으로, Shortcat에 없는 키보드 스크롤 같은 기능을 갖추고 있습니다. Keyboard Maestro는 결이 다른데, UI 요소 색인보다는 매크로·자동화 워크플로를 만드는 도구라 Shortcat과 보완적으로 함께 쓰는 경우가 많습니다.

여러 정리 글의 공통된 권고는 명확합니다. 처음 시작한다면 Shortcat입니다. 무료이고, 더 많은 앱과 호환되며, 입문 장벽이 가장 낮기 때문입니다. 그 후 키보드 스크롤 같은 기능이 절실해지면 Homerow로 넘어가는 경로가 자연스럽습니다.

8. 설치와 권한 설정

Shortcat을 쓰려면 두 가지가 필요합니다. 적절한 macOS 버전과 접근성 권한입니다.

  • 요구 사양: macOS 13 이상이 필요하며, 최신 macOS에서 동작이 확인됩니다. 공식 사이트에서 무료로 내려받을 수 있고, 2025년 7월 기준 0.12.2 버전이 배포되어 있습니다.
  • 접근성 권한: Shortcat이 UI 요소를 읽고 제어하려면 시스템 설정 > 개인정보 보호 및 보안 > 손쉬운 사용(Accessibility)에서 Shortcat을 허용해야 합니다. 이 권한 없이는 화면 요소를 색인할 수 없습니다.

접근성 권한은 강력한 권한이므로, 신뢰할 수 있는 출처(공식 사이트)에서 받은 것인지 확인하고 부여하는 습관이 중요합니다. macOS의 권한 모델 전반은 2026년 개발자들이 실제로 쓰는 도구 글에서 짚은 '도구 위생'과도 통하는 맥락입니다.

9. 활용 팁 - Shortcat을 손에 익히는 법

도구를 깔았다고 생산성이 바로 오르지는 않습니다. 다음 순서로 길들이는 것을 권합니다.

  1. 한 가지 동작부터: 처음에는 '메뉴 명령 실행'만 Shortcat으로 해 보세요. 가장 효과가 크고 마우스 대비 우위가 분명한 영역입니다.
  2. 힌트보다 검색 먼저: 이름을 아는 버튼은 타이핑 검색이 빠릅니다. 이름을 모르는 아이콘일 때만 힌트 모드로 전환하세요.
  3. 동의어를 신뢰하라: 명령 이름이 가물가물하면 의미를 입력하세요(remove, clear 등). 정확한 이름을 외우려 애쓸 필요가 없습니다.
  4. 마우스를 의도적으로 멀리: 일주일만 의식적으로 트랙패드 사용을 줄여 보면 손이 패턴을 기억하기 시작합니다.
  5. 보완 도구와 조합: 창 관리나 매크로가 필요하면 Keyboard Maestro 같은 도구와 역할을 나눠 쓰세요.

10. 한계와 솔직한 단점

균형을 위해 약점을 분명히 짚겠습니다. Shortcat은 만능이 아닙니다.

  • 접근성 API에 종속: 앱이 접근성 정보를 노출하지 않으면 색인이 안 됩니다. 커스텀 캔버스로 그리는 그래픽 앱, 일부 Electron/웹앱, 게임 등은 제어가 어렵거나 불가능합니다.
  • 학습 곡선: 처음 며칠은 오히려 느립니다. 손이 패턴을 익히기 전까지 마우스가 더 빠르게 느껴지는 구간이 반드시 있습니다.
  • 유지보수 우려: Shortcat은 몇 년째 활발히 유지보수되지 않는다는 지적이 있습니다. 무료라는 큰 장점과 맞바꾼 부분으로, 최신 기능이나 빠른 버그 수정이 필요하면 약점이 됩니다.
  • 기능 공백: 키보드 기반 스크롤 같은 일부 기능은 Shortcat에 없고 Homerow에 있습니다.

이 한계들은 대부분 '접근성 API 기반'이라는 설계 선택의 그림자입니다. 정확성과 가벼움을 얻는 대가로, API가 닿지 않는 영역에서는 무력해집니다.

11. 누구에게 권할 만한가

그렇다면 Shortcat은 누구를 위한 도구일까요? 정리하면 다음과 같습니다.

  • 키보드 중심 개발자: 이미 Vim·터미널·단축키에 익숙하고 손을 키보드에 묶어 두고 싶은 사람.
  • RSI를 관리하는 사용자: 마우스 사용을 의학적·예방적으로 줄여야 하는 사람.
  • 접근성이 필요한 사용자: 키보드 우선 제어가 단순한 선호가 아니라 필요인 사람.
  • 메뉴 헌터: 단축키 없는 깊은 메뉴 명령을 자주 쓰는 디자이너·파워유저.

반대로 그래픽 위주 앱이나 게임을 주로 다루거나, 새 도구 학습에 시간을 들이기 어려운 사람이라면 효용이 제한적일 수 있습니다. 새 도구를 고를 때 '내 워크플로에 맞는가'를 먼저 따지는 자세는 Claude Code 숨은 설정에서 강조한 도구 선택의 원칙과도 닿아 있습니다.

12. 결론 + 오늘 바로 해 볼 3가지

Shortcat은 '마우스로 가는 짧은 왕복'이라는, 작지만 끊임없이 반복되는 비효율을 정조준한 도구입니다. 접근성 API로 UI 요소를 색인해 키보드만으로 클릭·메뉴·창 전환을 가능하게 함으로써, 입력 효율·건강·접근성이라는 세 축을 동시에 건드립니다. 무료이고 진입 장벽이 낮아, 키보드 우선 워크플로를 처음 시도하는 사람에게 이상적인 출발점입니다. 다만 접근성 API에 종속된다는 구조적 한계와 유지보수 우려는 분명히 인지하고 써야 합니다.

오늘 바로 해 볼 수 있는 세 가지로 마무리합니다.

  1. 설치하고 접근성 권한부터 켜라. 공식 사이트에서 받아 설치하고, 시스템 설정의 손쉬운 사용에서 권한을 허용하는 것이 모든 것의 출발점입니다.
  2. 메뉴 검색 하나만 일주일 써 보라. 단축키 없는 메뉴 명령을 Shortcat 퍼지 검색으로 실행하는 습관부터 들이면 효용을 가장 빨리 체감합니다.
  3. Homerow와 비교해 보라. 키보드 스크롤이 절실하다면 유료 Homerow를 함께 시험해, 무료의 Shortcat과 자신의 워크플로에 맞는 쪽을 고르세요.
