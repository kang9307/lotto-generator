Putting Static Types on the BEAM

What the Erlang VM already guarantees, and what strains at the message boundary once you add a type system on top

Aug 23, 2026 Dev & Infra

Introduction: a world where you pick the runtime first and the language second

Most language decisions start with syntax and ecosystem. In the BEAM world the order flips. You first decide that you want to run on the Erlang virtual machine, and only then choose which language on top of it. The runtime gives you more than the language does.

One of the options in that slot is Gleam. The official site calls it a friendly language for building type-safe systems that scale, and places a type system, functional expressiveness and the reliability of the Erlang runtime side by side in a single sentence. Version 1.0 landed on 4 March 2024, and as of August 2026 the latest release is 1.18.0, from 29 July.

This article is not a syntax tour. It is one question. When you put static types on a runtime that has been dynamically typed for decades, which boundaries move over to the compiler and which ones stay exactly where they were? Once that has an answer, whether the language fits your problem tends to answer itself as well. The broader swing back to static typing was covered in The Rise of Static Typing - Why It Has Been Back Since the Mid-2010s, and the question of bringing functional languages into an organisation in Why H-E-B Runs Its Supply Chain on 1 Million Lines of Haskell. What is different here is the condition attached: the runtime already provides strong guarantees.

What Gleam is - the confirmed picture as of August 2026

The facts first, briefly. Everything below is stated on the official site and in the official documentation, checked in August 2026.

  • Execution targets - it runs on the Erlang virtual machine and additionally compiles to JavaScript. For consumption from the JavaScript side it also generates TypeScript definitions.
  • Type system - no null values and no exceptions. Absence is Option, failure is Result.
  • Immutability - every data structure is immutable and uses structural sharing for efficiency. Mutable storage means reaching for something external such as Erlang term storage.
  • Toolchain - compiler, build tool, formatter, editor integrations and package manager all ship in one distribution.
  • Stability commitment - the 1.0 announcement made maintaining backwards compatibility a priority and limited the exceptions to security and soundness issues.
  • Recent release direction - 1.16.0 (24 Apr 2026) headlined JavaScript source maps, 1.17.0 (2 Jun 2026) single-file programs via escript, and 1.18.0 (29 Jul 2026) language server work.

If only one line survives from that list, it is the first. Running on the BEAM is the premise for everything else, which is why the runtime has to be established before the types.

What the BEAM gives you already - processes that share nothing

The Erlang documentation summarises the character of this runtime in one sentence: threads of execution share no data, which is why they are called processes rather than threads. The naming is itself a design statement.

Three properties follow from it.

  • Memory is partitioned - when one process corrupts its state it cannot touch another process's memory. With no sharing there is no data race to lose sleep over.
  • Each holds its own mailbox - every process has an input queue and matches received messages one at a time. If no pattern matches, the message stays in the queue and the next one is tried.
  • Messages are values - what travels between processes is simply a valid Erlang term. Lists, tuples, integers, atoms, process identifiers: it makes no difference.

The way the official site frames the runtime points the same way: multi-core actor-based concurrency running millions of concurrent green threads, fast immutable data structures, and a concurrent garbage collector that never stops the world. That last item is the most operationally relevant. Because heaps are per process, collection happens per process too.

The BEAM's guarantee, in short, is not correctness but isolation and continuity. This runtime does not stop your code from being wrong. It narrows how far the damage travels when it is.

Supervision trees - restore rather than repair

Isolation is only half of it. Something has to bring dead processes back, and that is the supervisor. The Erlang documentation states the basic idea as keeping child processes alive by restarting them when necessary.

There are four restart strategies, and the choice among them is the design of your blast radius.

  • one_for_one - only the terminated child restarts. Used when children are independent of one another.
  • one_for_all - when one dies, all are terminated and restarted together. Used when children assume shared state.
  • rest_for_one - the failed child and every child started after it restart. Used when start order carries dependencies.
  • simple_one_for_one - a simplified form for children of one kind added and removed dynamically.

On top sits restart intensity. If more restarts than the configured count occur within the configured window, the supervisor terminates all children and then itself. It prevents runaway restart loops while escalating the problem to the supervisor above. The documentation points out that in a multi-level tree the total number of restarts becomes the product of every layer's intensity, and advises tuning those values carefully.

Where this parts ways with exception handling is clear. Exception handling attempts recovery at the point of failure, so the recovery code must know the cause and branches multiply along every failure path. A supervision tree does the opposite. Instead of repairing broken state it discards it and restores a known initial state. Not needing to know the cause is the practical gain.

Code on the BEAM therefore settled into writing few defensive checks. That this culture actually suited dynamic typing rather well is where the next section starts.

Static types on a dynamic culture - the real issue in this article

What a type system checks is, ultimately, the function call boundary: whether the arguments fit and whether the return value is handled. That check holds inside a compilation unit.

But the central boundary of an actor system is not a function call. It is message passing, and message passing behaves differently. Sender and receiver may not be in the same compilation unit, may not be in the same language, and in principle need not even be on the same node. As we saw, the mailbox is built to accept any valid term. That is about the least convenient shape a static type system can be handed.

Gleam's answer is to put a type on the channel. The actor library provides a typed conduit, Subject(message), and send and call through it are checked for message type at compile time. The repository lists three goals for itself: full type safety of actors and messages, compatibility with Erlang's OTP actor framework, and fault tolerance and self-healing through supervisors. Supervisors come in a static form and a dynamic child-creation form.

So far so tidy. The problem is outside the channel.

There is a short but decisive sentence in the actor documentation. If a message arrives that the actor's selector does not pick up, the actor discards it and logs a warning. That one line says everything this section is about. The compiler did not stop that message. It arrived, and the runtime dealt with it. The type system checked the messages my Gleam code constructs and sends; it did not lock the mailbox.

There is a cost on the other side too. The same repository states that not all Erlang and OTP functionality is included, because of type-safety constraints. Some OTP system messages and some supervision strategies are not mapped yet, and users are pointed at Erlang APIs directly when they need them. Features really were left out in order to keep the types honest.

Is that a defect, then? It reads more accurately as a relocation of boundaries. On the dynamically typed BEAM the contract between processes lived in documentation, convention and discipline. Gleam moved a substantial part of that contract somewhere the compiler can read it. What did not move stays unmoved, and the fact that the unmoved parts are documented is the honest half of this design.

Boundary by boundary, it splits like this.

BoundaryWhat the runtime givesWhat the type system givesWhat remains yours
Function calls inside the codebaseNot applicableFull compile-time checkingAlmost nothing
Messages sent through a typed channelIsolation, arrival orderType checking at send timeCompleteness of receiver branches
Messages reaching the mailbox off-channelIsolationCannot checkDiscarded, left as a warning log
Calls into another languageNot applicableOnly the call site is checkedReturn type and existence unverified
External input and interop dataNot applicableArrives as DynamicNarrowing it with a decoder

The last two rows are what you hit most often in practice. External functions are declared with the @external attribute, and the official guide spells out its limits.

@external(erlang, "lists", "reverse")
pub fn reverse_list(list: List(element)) -> List(element)

Of this declaration the guide says the compiler will ensure that all uses of the function are correct for the annotated types, but it cannot verify that the function implemented in the other language returns the specified types, or even that it exists. The same document therefore advises using externals sparingly and writing more unit tests than usual when you do. It lists the drawbacks as well: external code cannot be analysed or type-checked, the language server offers no assistance with it, and it complicates cross-target compilation.

Values coming in from outside are the same story. The standard library's Dynamic means data whose type is not known yet, and the docs name the sources as interop with Erlang and IO with the outside world. To use such a value you must narrow it through a separate decode module. Every boundary therefore carries an explicit decoding cost.

What you gain - failures pulled to the left

The costs came first, so let the benefits be equally concrete.

  • Absence and failure live inside the types - this is exactly what the write-up that prompted this discussion singled out: Option and Result in place of exceptions and null. Failure paths show up in the signature, so a caller has a hard time walking past them.
  • Changing a message type becomes a compile error - add one variant to what an actor accepts and every place that does not handle it surfaces in the build. Dynamically, that check waits for runtime, and in the worst case for the moment a particular request arrives.
  • Editor support is standard equipment - the language server ships with the toolchain, and the headline of 1.18.0 was language server work. With type information available, rename and find-references behave differently.
  • The tooling arrives as one piece - build tool, formatter and package manager are not separate decisions, which removes a class of per-team bikeshedding.
  • There is a public compatibility promise - the 1.0 announcement said every effort would be made not to introduce breaking changes, with exceptions limited to security and soundness.
  • Paths in from other languages are mapped - the documentation carries cheat sheets for Elixir, Erlang, Elm, Rust, Python and PHP users.

The second item is the one that pays. A large share of bugs in actor systems come from a message contract that drifted. Pulling that drift into the build step is the core of what this language sells.

What you pay - the ecosystem in numbers, and the boundary tax

The cost arrives in four parts.

  • Ecosystem size - checked on 23 August 2026, the official package index reported 1,618 packages. Hex as a whole listed 26,117 at the same moment. The two numbers should not simply be subtracted, though, because packages from other BEAM languages can be used from Gleam.
  • Interop cost - the moment you do that, the @external and Dynamic costs from the previous section attach. What you actually pay is therefore not the gap in package counts but the boundary work added each time you borrow someone else's ecosystem. That is the accurate arithmetic.
  • Macros do not come across - the FAQ says the build tool can compile Elixir dependencies and source files, while stating that Elixir macros cannot be called from outside Elixir. Libraries whose shape is built from macro-defined syntax do not port over as they are.
  • There are two things to learn - not just the language. Processes, supervision trees and restart strategies are a runtime model you have to absorb, with immutability and pattern matching layered on top. Needing external storage whenever mutable state is required also takes getting used to.

That fourth item is not the language's fault; it is the price of choosing the runtime. Erlang, Elixir and Gleam all pay it equally. Mistaking it for a language-selection cost skews the whole decision.

Two backends - what opens and what closes

Compiling the same source to both the BEAM and JavaScript is this language's most visible trait. It does not, however, mean the same code can do the same things in both places.

AspectErlang (BEAM) targetJavaScript target
Concurrency modelProcesses, actors, supervision treesWhatever the host runtime provides
Distribution formSingle-file escript support (1.17.0)Browsers and anywhere JavaScript runs
External function targetsErlang and Elixir modulesJavaScript modules
Exporting type informationNot applicableTypeScript definitions generated
Debugging affordancesOTP tracing and debugging featuresSource map support (1.16.0)

The first row matters most. Half the appeal of this language comes from actors and supervision trees, and those are what the BEAM gives, not what the language gives. Code compiled to JavaScript has no BEAM under it.

In practice the two targets split like this.

  • What opens - server and browser can share the same type definitions and the same domain logic. The purer the part, such as data models and validation rules, the bigger the sharing win.
  • What closes - target support varies library by library. The official guide notes that because Gleam can run in constrained environments such as embedded systems or browsers, some functionality is not included in the standard library. Committing to both targets narrows your dependency choices.
  • Distribution diverges - escript is a feature of the Erlang runtime, so it is BEAM-target only. If single-file distribution is the goal, the target is effectively decided first.

The two backends, then, are a way to work in two worlds with one language, not a way to make the two worlds one. Plans line up better when the scope of shared code is drawn tightly around pure logic.

What actually decides the choice

The axis that decides real projects is not syntax preference. The table below lists, by situation, the axis to check first. It is not a verdict on which language is better.

Layering onto an existing Elixir codebaseBoundary costMacro-based libraries and Dynamic decoding become the actual workload

Using it is simple: pick the two or three rows that match your situation and measure those axes first.

The other side, honestly - when staying dynamic is the right call

It helps to drop the premise that static typing is always a net gain. In the following situations, staying with the existing language is the reasonable choice.

  • A team already fluent in that ecosystem - losing familiar tools and idioms can cost more than the bugs types would have caught, and the smaller the team the more that holds.
  • A codebase tied deeply to macro-centric frameworks - as noted, macros cannot be called from outside. When a framework is the axis of code generation, porting turns into a rewrite in all but name.
  • Needed OTP features that are not wrapped yet - calling Erlang APIs directly is available, but the more often you take that road the less the types are giving you.
  • Systems that are mostly boundary - if the work is relaying external systems and transforming data, a large share of the code becomes a decoding layer. Types pay off where internal logic is thick.
  • Wanting types does not require changing language - the Gleam FAQ itself mentions Elixir's type system, saying the two are as different as two type systems can be and offer different programming experiences. In other words the option set is larger than one.
  • Migration cost scales with codebase size - types pay the most in large codebases, and large codebases are exactly where moving is most expensive. Plans that ignore this paradox tend to slip.

For a small new service the arithmetic changes. There is no code to move, so migration cost is zero, and boundary cost can be designed in from the start.

What could not be confirmed

The items below are ones public material did not answer. They are gaps that matter to the decision, so they are listed together rather than sprinkled through the text.

  • Adopting organisations - the official FAQ carries nothing on organisational adoption or ecosystem maturity. Where the official site mentions WhatsApp and Ericsson, that is about the track record of the BEAM as a runtime, not adoption of this language.
  • Performance comparisons - no throughput or latency figures against other BEAM languages were found in official documentation, nor any public benchmark characterising the compiled output.
  • The concrete list of unmapped OTP features - the repository says only that some system messages and some supervision strategies remain. A full inventory of what does and does not work was not found.
  • Hot code loading and operational practice - how live code replacement, a staple of BEAM operations, is handled under static typing was not explicitly described in official documentation.
  • Concurrency on the JavaScript target - how far actors and supervision trees hold on that target was not confirmed from official documentation.
  • The hiring market - no public statistics were found on the size of the talent pool or hiring difficulty, so this article offers no figures on the subject.
  • What the package count means - 1,618 is what the index displayed. What share of those is actively maintained was not confirmed.

What can be recommended now, and what cannot

This article does not recommend production adoption. Not as a verdict on language quality, but because the list directly above is empty where it should not be. The project itself says in its FAQ that it is ready for production, adding that the Erlang and JavaScript runtimes it targets are extremely mature and battle-tested. That statement is worth noting, but a maker's self-assessment and a basis for adoption are different things.

What is reasonable at this stage looks roughly like this.

  • Start with the browser-based official tour and look only at the syntax - no installation needed to see the shape of the language. Most of the fit question is settled right there.
  • Attach it to a small piece with clean boundaries - internal tooling or a non-critical batch job, somewhere failure is cheap to undo.
  • Deliberately go through interop once - pick one existing library you would need and wire it up through @external and decoding. The boundary cost described above then turns into a number for your team, and that number is what the decision should rest on.
  • Schedule runtime learning separately from language learning - the OTP model is required whichever BEAM language you pick. Folding it into the language rollout muddies any later analysis of what went well.

One framing is worth keeping. The BEAM narrows the radius of failure; static typing pulls failure forward to compile time. The two do not conflict, because they handle different kinds of failure: types catch violated contracts, supervision trees catch unforeseen state collapse. Whether this combination succeeds will be judged by how much of the remaining boundary shrinks.
