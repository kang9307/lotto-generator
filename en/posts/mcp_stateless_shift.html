MCP Dropped Sessions - What the Stateless Shift Changes in Server Operations

What to put in the space left by sticky routing and resumable streams

Aug 16, 2026 Dev & Infra

Introduction: The MCP server that stalls at the ingress config

When you put an MCP server on an internal cluster, the place your hands stop is usually not the code but the ingress configuration. The moment you scale to two pods, half the requests land on the wrong instance and come back with no such session. So you enable session affinity, and then every deploy severs the connections that were in flight. You move the state into a shared store to stop that, and now that store is a single point of failure. It is a familiar loop.

The 2026-07-28 revision of the MCP specification cut the root of that loop. Protocol-level sessions are gone, and so is the initialize handshake that opened a connection. Every request now carries, by itself, which protocol version it speaks and what the client is capable of. The server has no obligation to remember the previous request, and from the infrastructure side MCP traffic is handled like ordinary HTTP traffic.

It is not free. The things sessions were holding up — multi-step work in progress, the server speaking first, resumption of a broken stream — did not disappear. They moved somewhere else, or became the operator's problem outright. This article is about the content of that trade.

If MCP itself is new to you, Complete Guide to MCP (Model Context Protocol): The New Standard for AI Agents covers the concepts, and How to Choose MCP Servers for Claude Code - Six Axes Instead of a List covers picking servers from the client side. This piece takes the other side: building and running the server.

Everything cited here is from the 2026-07-28 revision, checked on 16 August 2026. MCP versions are date stamps and the number does not advance while changes stay backwards compatible, so if you are reading this six months later, start by confirming which revision is current.

1. What sessions actually cost in operations

From 2025-03-26 through 2025-11-25, Streamable HTTP had the server mint a session through the Mcp-Session-Id header, with the client echoing that value on subsequent requests. An HTTP DELETE ended the session, a GET opened a separate SSE stream for server-initiated messages, and a broken stream was resumed with Last-Event-ID.

As a design it is elegant. The problem is that all three of those impose constraints on the infrastructure layer.

  • Sticky routing becomes effectively mandatory. If session state lives in instance memory, follow-up requests for that session must reach the same pod. On an L4 front end without cookie-based affinity, you end up writing header-based hashing yourself.
  • Horizontal scaling is uneven. A new pod only receives new sessions, so load stays on the existing ones. Adding instances has no immediate effect, and removing them means delaying eviction while sessions are still alive.
  • Deploying means severing. When a rolling update replaces a pod, the sessions it held are destroyed. Clients get told there is no session and reconnect from scratch. This is the classic spot where a supposedly zero-downtime deploy interrupts real user work.
  • A session store only relocates the problem. Pushing state into an external cache frees routing but makes that cache's availability, serialisation cost and expiry policy new operational items. For how session revocation breaks at scale, see Why Logout Is Not Instant - Where Session Revocation Breaks at Scale.
  • Intermediaries are blind. To a proxy, every request is an identically shaped POST to the same endpoint. Finding out which tool is being called means parsing the body, and tearing open JSON at the gateway is unwelcome for both performance and security reasons.

The real cost, then, was never sessions as such. It was the location pinning that sessions demand. A system where a request may go anywhere and one where it must go to a specific instance are a full step apart in operational difficulty.

2. What the 2026-07-28 revision actually removed

The change is broad enough that the phrase it went stateless does not convey much. Narrowed to what touches operations directly, it looks like this.

First, there is no handshake. initialize and notifications/initialized were removed, and every request carries the protocol version and client capabilities inside _meta. The keys are reverse-domain named: io.modelcontextprotocol/protocolVersion, io.modelcontextprotocol/clientCapabilities, io.modelcontextprotocol/clientInfo. Servers put their own identity in the _meta of each result. If the version does not match, the server returns an UnsupportedProtocolVersionError listing the versions it does support, and the client retries with one of them. This is not a negotiation round trip; it is rejection and retry.

Second, there is no session header. Mcp-Session-Id and protocol-level sessions were removed together. One consequence is easy to miss: tools/list, resources/list and prompts/list can no longer vary per connection. If your server showed a different tool list per connection, that design has to change first. Where state is needed across calls, the specification points to explicit, server-minted handles passed as ordinary tool arguments.

Third, the server cannot send requests first. Previously a server could push JSON-RPC requests such as roots/list, sampling/createMessage or elicitation/create onto an SSE stream. Now it returns the need for input inside the result itself. Every result carries a resultType field, and when the value is input_required, the inputRequests field says what is needed. The client fills it in and resends the original request under a new request ID together with inputResponses. This pattern is called Multi Round-Trip Requests (MRTR).

Fourth, there is no GET stream. To receive change notifications you POST a subscriptions/listen request, and its response stream becomes the long-lived channel. The client explicitly opts in to the notification types it wants. Request-scoped notifications such as notifications/progress still flow only on the response stream of the request they belong to. The two streams now have separate jobs.

Fifth, there is no resumption. Last-Event-ID and SSE event IDs were removed. If a response stream breaks, the in-flight request is lost and the client must reissue it as a new request with a new ID. That single line is the starting point for the idempotency discussion further down.

One more change weighs heavily in operations. Mcp-Method and Mcp-Name headers are now required on Streamable HTTP POSTs. They mirror the method name and target name from the body, and the purpose is explicit: to let intermediaries route and inspect without parsing the body. List and read results gained ttlMs and cacheScope, making the caching contract explicit, while ping and logging/setLevel were removed.

Looking at the shape of a single request makes the character of the shift obvious. The whole self-introduction is inside the request.

  "jsonrpc": "2.0",

Seeing the same value twice, in a header and in the body, may look redundant, but it is a contract. The specification requires the server to reject a mismatch with 400 and a HeaderMismatch error. The reason is clear: if the load balancer routes on the header while the server executes on the body, the moment those two believe different truths is an attack surface.

4. What you gain - deploys and scaling become unremarkable

Most of the benefit of the stateless shift comes from no longer having to treat MCP as a special case.

  • You can switch off session affinity. If you only face modern clients, requests may land anywhere. Round robin, least connections, whatever policy you already use applies unchanged.
  • The blast radius of a rolling deploy shrinks to one request. Replacing a pod used to wipe out whole sessions. Now what is affected is the individual request in flight at that moment, recovered by a retry. Long-lived notification streams are the exception, covered in the next section.
  • Autoscaling takes effect immediately. A new instance starts sharing load from the very next request. Scaling down only requires waiting for in-flight requests to drain, not for sessions to expire.
  • Intermediaries get smarter. With Mcp-Method and Mcp-Name in headers you can rate-limit per tool, route heavy tools to a dedicated pool, and split metrics by method without touching the body. The x-mcp-header annotation, which mirrors tool parameters into headers, lets you route on values like tenant or region too.
  • Caching became a contract. List and read results carry ttlMs and cacheScope. Because the server states whether a shared intermediary may store the response, the justification for reducing polling comes from the response itself rather than guesswork.

There is one more gain worth adding. Because list results can no longer vary per connection, client-side prompt cache hit rates go up. That is also why the specification recommends returning tools/list in a deterministic order. This is not an infrastructure win but a token cost win.

5. What you lose - where in-flight work, subscriptions and resumption went

This is the real crux of the shift. Sessions going away does not mean the work sessions were doing went away. Split into three, each landed somewhere different.

5.1 In-flight work - from core to extension

The experimental Tasks feature that expressed long-running work left the core for the official io.modelcontextprotocol/tasks extension. Instead of a call that blocks waiting for a result, status is polled, and support is advertised through the extensions field in capability negotiation. A server that implements only the core simply does not have this, so if long-running work is the essence of your service, adopting the extension is itself a design decision.

5.2 The server speaking first - inverted into MRTR

When a server needed user confirmation or a model completion, it used to send a request to the client. Now the server returns a request. The direction is inverted. Two differences matter in practice.

  • The server does not have to hold a waiting state. The connection that stayed open while waiting for input, and the memory pinned to it, are gone. When the retry arrives, any instance can handle it.
  • The context has to be resent instead. The client resends the original parameters plus the responses. If the server needs to correlate something across several round trips, it encodes its own identifier in requestState and manages it. The cost is real: the longer the round trips run, the larger the payload that travels back and forth.

5.3 Subscriptions and resumption - one survives, one does not

Change notifications survive as the long-lived response stream of subscriptions/listen. It is not a rename but a change of character — no longer an always-open GET channel, but a request that explicitly opens with a chosen set of notification types. Servers are encouraged to emit periodic SSE comment lines as keep-alives so intermediaries do not close quiet streams. Reverse proxies buffering SSE, which makes notifications arrive in clumps, is handled with the X-Accel-Buffering: no header.

Resumption did not survive. A broken stream never rewinds. That decision follows logically from statelessness: to resume, something has to remember which instance sent how far, and that memory is exactly the state being removed. So a rolling deploy recovers lost requests through retries but definitively breaks open notification streams. If the client does not resubscribe on its own, that screen quietly stops updating.

  • Cancellation differs by transport too. On HTTP, the client closing the response stream is the cancellation signal; on stdio, a separate cancellation notification is sent.
  • The notification stream is still a connection pinned to one instance. Removing session affinity and keeping streams unbroken are separate problems.
  • Progress notifications and change notifications now flow on different streams, so a client implementation that merged both into one handler has to split them.

6. Where does what lived in the session go?

The hard part of migration is not editing code but discovery. What you piled onto the session object is usually undocumented, and the older the server, the more scattered it is. The technique is simple.

  • List every object created at connection setup that request handlers reference. The constructor arguments are your session state inventory.
  • Find variables inside handlers that are populated without arriving as arguments. Those are traces left by earlier requests.
  • Sweep the paths written to instance-local disk or temp directories. Upload buffers and intermediate artefacts hide there.
  • Check whether the code that builds the tool list branches on user or connection. If it branches, that design does not hold in the current revision.

There are three destinations. Carried in the request (opaque cursors, server-minted handles, the requestState of MRTR), derived from the token (user identity, tenant, scopes), and kept in shared storage (work progress, large intermediate artefacts). The criterion is one question: is this value safe to entrust to the client? If forging it would hand over privilege, it does not go in the request unless the server signs it or revalidates it against storage.

Turning a session cursor into a handle looks roughly like this conceptually. The snippet below is not any SDK's API but pseudocode meant to show the structure.

// Before: the connection object remembered the cursor
session.cursor = result.nextCursor
handleNext(session)          // only works on the same instance

// After: a server-minted opaque handle travels as an argument
{ "method": "tools/call",
  "params": { "name": "list_rows",
              "arguments": { "cursor": "<string signed and issued by the server>" } } }
// whichever instance receives it can continue by decoding the cursor alone

If you must accept legacy clients, make the server dual-era. The specification allows serving both eras on the same endpoint, and the server decides from how the request arrives — per-request _meta means stateless handling, an initialize selects legacy semantics. When a modern-only server receives legacy traffic, the specification's guidance is to answer GET and DELETE with 405 and to ignore Mcp-Session-Id and Last-Event-ID while not minting or echoing session IDs.

It is also worth remembering that era determination is a property of the server as a target, not of an individual request. Clients cache that verdict per server process or origin. So on the day you upgrade a server, a client that remembers it as legacy will keep taking the wrong path for a while.

8. Idempotency and retries - a broken stream never rewinds

The price of losing resumption shows up immediately as duplicate execution risk. The scenario is very concrete. A client calls a payment tool. The server opens an SSE stream and starts working. The network drops midway. Having received no final response, the client resends under a new request ID. The server may or may not have already committed the first attempt. The protocol guarantees nothing here.

Previously the resumption mechanism partially covered this hole. Now whoever wrote the tool has to cover it. There are three standard moves.

  • Take an idempotency key as an argument on tools with side effects. Have the client attach the same key to the same logical attempt, and record results per key so the second call returns the stored result. Request IDs change on every retry, so they cannot serve as the key.
  • Do not mistake cancellation for completion. On HTTP the client closing the stream is the cancellation signal, so the server should stop work as soon as practical and send nothing further. The catch is that side effects already dispatched to external systems are not cancelled. Whether the cancellation path needs a compensating transaction is a per-tool judgement.
  • Do not hang long work off a stream. Since a broken response stream loses the work, anything measured in minutes is better served by returning a handle immediately and letting status be queried separately. That is exactly the shape the Tasks extension standardises.
  • Do not leave retry storms to the client alone. Stream breakage is usually an infrastructure event, so it hits many clients at once. Assume retries arrive in a wave and prepare server-side rate limiting and backoff signalling.

To summarise: statelessness simplifies the server but not the tools. The share the protocol used to cover came down into tool implementations, and that share concentrates on tools with side effects.

9. When authorization moves down to the request

In the session era, authentication felt psychologically like connecting. Pass once, and the connection was treated as authenticated. Statelessness has no such place. On HTTP transports the authorization header must be included in every request from client to server, and putting tokens in the URI query string is forbidden.

The server's duty repeats per request as well. Acting as an OAuth 2.1 resource server, an MCP server validates the token and confirms it was issued with itself as the intended audience. Accepting a token issued for use elsewhere, or passing one on to another service, is forbidden. That single rule blocks a large share of confused deputy attacks.

  • The failure surface widens. An auth error that used to appear once at connection setup now appears on arbitrary calls. Token expiry can land mid-operation, so clients need a path that refreshes and retries on 401.
  • Insufficient scope is handled separately. When the token is valid but the scope falls short, the server answers 403 and names the required scopes in a response header. The client must re-authorize with the union of its existing scopes and the new ones. Requesting only the new scope loses permissions it already had.
  • Finish re-authorization in one round trip. The specification recommends that servers emit all scopes needed for the current operation in a single challenge. Revealing missing scopes one at a time makes the user face repeated consent screens.
  • Always specify the token's target. Clients must name the target resource in both the authorization request and the token request, and the value must be the canonical URI of the MCP server. The requirement is to send it regardless of whether the authorization server supports the parameter.
  • stdio sits outside this spec. stdio implementations do not follow the authorization specification and take credentials from the environment. The privilege boundary of a local server is still the user account that launched the process.

What actually weighs on operations is validation cost. Tokens must be checked per request, and you cannot hit the authorization server every time. If the format validates by signature, caching public keys is enough; if opaque tokens require introspection, that layer becomes a new bottleneck and single point of failure — to avoid a token introspection cache inheriting the seat you just cleared of the session store, prefer self-validating tokens from the outset.

10. Observability - what to record so you can reproduce a fault

Moving to stateless removes one thing from debugging: the session ID as a free correlation key. Grouping logs by session ID used to lay out one user's whole flow. The protocol no longer hands you that axis.

What the specification did prepare instead is distributed tracing. Conventions for propagating trace context in _meta are documented, and the logging feature itself was classified as deprecated with standard error output on stdio and OpenTelemetry named as migration paths. It reads as a declaration that the era of the protocol carrying logs is over and observability belongs to the ordinary observability stack. To keep logs reproducible, gathering the axes below onto one line is practical. The field names are not specified anywhere; read them as the axes worth recording.

ts=2026-08-16T09:14:22Z  instance=mcp-7d9c-4kqp
mcp.version=2026-07-28   mcp.method=tools/call   mcp.name=run_query
req.id=1                 result.type=complete    dur_ms=812
trace=00-4bf92f...-00f067aa0ba902b7-01
auth.sub=u_8391          tenant=acme             scope=files:read
retry.key=6f1c9a2e       stream=closed_by_client
  • Always record the protocol version. A dual-era server takes both kinds of traffic on the same endpoint. Without a version axis you will never separate a bug that only occurs on the legacy path.
  • Record method and target name pulled from the headers. Logging the same values in gateway access logs lets you cross-reference application logs without ever seeing the body.
  • Record the result type. If you do not separate responses that ended in an input request from completed ones, MRTR round trips get counted as failures, or an endless round trip looks healthy.
  • Distinguish why a stream ended. Client closed, server closed, and intermediary severed are completely different events. If cancellations and faults land in the same metric you cannot measure deploy impact.
  • Have the application mint a key that groups retries. Request IDs change per retry, so they cannot reconstruct one logical attempt on their own. An idempotency key or trace ID has to take that role.

Two new metrics deserve attention. Early stream termination rate mixes deploys, proxy timeouts and client cancellations, so read it alongside the reason breakdown above, and the distribution of MRTR round trips ties directly to cost because payloads grow with each trip.

11. What this article did not verify

The factual claims here come from the 2026-07-28 revision documents. The following sits outside that scope and is not asserted.

  • When each language SDK formally supports this revision, and from which version, was not verified. Check the release notes in each SDK repository directly.
  • Adoption timing for major clients and host applications, and how long they intend to stay dual-era, was not verified against any published schedule.
  • Which revision will actually remove the deprecated features is not fixed. What the policy guarantees is a minimum twelve-month window, or a minimum of ninety days under the expedited-removal exception.
  • No public benchmark was found for the measured effect of the stateless shift — throughput per instance, tail latency, cost change. The operational statements here are derived from what the specification requires or permits, not from measurements.
  • Stability grade and version for extensions such as Tasks and Apps move separately from the core. Check each extension repository's status before adopting.

Frequently asked questions

If MCP is stateless, how is it different from a REST API?

What changed is the connection model, not the reason the protocol exists. MCP standardises the description format for tools, resources and prompts, not the way bytes move. You can still ask any server, in the same way, what tools it has and what the input schema is. This revision only removed the connection state layered on top. The debate over MCP's value is covered separately in Is MCP Dead? 2026 - The Limits of Model Context Protocol and What Comes Next.

Do I have to rewrite my existing MCP server right now?

Not immediately. The specification allows a dual-era implementation supporting both the legacy handshake and the modern per-request model. There are combinations that simply fail, though: a modern client against a legacy-only server, and the reverse. So the practical order is make the server dual-era first, then retire the legacy path as client adoption catches up.

Sessions are gone, so how do multi-step operations survive?

The instruction is not to remove state but to move it out of the protocol. Where state is needed across calls, use explicit server-minted handles passed as ordinary tool arguments. The store is shared storage rather than a session object, and its lifetime and cleanup policy are the server designer's decision.

Can I turn off sticky sessions on the load balancer?

If you only serve modern clients, per-request routing is the premise and affinity is unnecessary. Check two things first. Legacy clients still reaching you still use connection-bound sessions. And the long-lived notification stream is still a connection open against one instance, and it is not resumable. Removing affinity and expecting uninterrupted streams are separate questions.

What actually changes about authorization under a stateless model?

There is no longer a place to authenticate once and pin the result to a connection. The authorization header must ride on every request, and the server must confirm on each one that the token names it as the intended audience. What changes in practice is validation cost and where failures land — an auth error that used to surface at setup can now surface on any call, so clients need a retry path that separates expiry from insufficient scope.

Conclusion: three decisions to make today

Reduced to a sentence, this revision is the end of using the connection as a unit of trust. That habit was convenient, but it pinned requests to specific instances, and that pinning was setting the difficulty of deploys, scaling and incident response. In the space where the knot came loose, the gains infrastructure collects and the responsibility that dropped into tool implementations both remain.

  • Start by inventorying what your server hangs on the connection. Discovery comes before deciding whether to migrate. In particular, if you serve a different tool list per connection, that design does not hold in the current revision.
  • Add idempotency keys to tools with side effects. Resumption is gone, so retries increase. This is worth doing now regardless of whether you adopt the revision.
  • Rebuild your observability axes around version, method, result type and stream termination reason. Without an axis to replace what the session ID correlated, you will not be able to reproduce faults right after migration.

The remaining judgement is timing. Weigh the cost of making the server dual-era against the cost of holding on the legacy path while clients move first. Deprecated features carry a minimum twelve-month window, so there is no emergency. What is clear is that removing session dependence is a win independent of this revision.
