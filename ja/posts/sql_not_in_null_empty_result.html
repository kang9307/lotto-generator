NOT IN のリストに NULL が一つ混ざると結果が丸ごと空になる - エラーなしで0行になる SQL 三値論理

0行と8行を分けたのはリスト内の NULL 一つだった。SQLite と DuckDB で実際に実行した出力から

2026-07-30 開発・インフラ

症状: 検索結果が空なのに、データは確かにあった

運用中のサービスに「一度も返金を要求していない顧客」の一覧を取り出すクエリがあった。昨日までは出ていた。今日実行すると0行である。顧客テーブルには依然として数万件が入っており、返金要求テーブルも問題ない。クエリは成功した。エラーメッセージが一行も出ていない。

この状況で人が最初に思い付く結論はたいてい同じである。「条件に合うデータが無いのだろう」。そしてその結論は、何も表示されないダッシュボード、誰にも届かない配信バッチ、0 で埋まったレポートとなって何日も放置される。失敗したのではなく成功したまま空になっているため、通知も鳴らない。

犯人はたいていこの一行である。

SELECT id, name FROM customers
WHERE id NOT IN (SELECT customer_id FROM refund_requests);

そして refund_requests.customer_id に NULL がちょうど一行入っている。それだけで終わりである。残りの一万件がどれだけ正常でも結果は0行になる。

この記事は「NOT IN を使うな」と言うためのものではない。なぜそう設計されたのか、そしていつ何を使うべきかを扱う。結論から言えば、この挙動はバグではなく論理的に正しい結果である。その正しさがよりによってエラーなく静かに現れるために事故になるのだ。

実行環境。以下のすべての出力は Windows 10 Pro (10.0.19045) で実際に実行した結果である。エンジンは SQLite 3.49.1（Python 3.13.3 の sqlite3 ドライバ経由）と DuckDB 1.5.5（PostgreSQL 系の SQL 方言）の二つを使った。同じスクリプトを両方で走らせ、一致する点と分かれる点を区別している。仕様に関する記述は SQLite と PostgreSQL の公式文書だけと照合しており、開いて確認していないエンジン（MySQL、Oracle、SQL Server など）については断定しない。

例題スキーマ。customers が10行（id は 1 から 10 まで）、refund_requests が4行である。要求4件のうち 1件だけ customer_id が NULL になっている。すべて架空のテーブルであり、そのままコピーして自分の DB で再現できる。

この記事が扱わないもの。SQL 自体が初めてなら、まず SQL 入門ガイド を見てほしい。ここでは NULL の三値論理という一点だけを掘り下げる。結合における ON と WHERE の境界はこの記事の主題ではなく、6節と7節の NOT EXISTS・LEFT JOIN は 反結合の代替手段としてのみ扱う。

3. NULL は「無い」ではなく「分からない」である

ほとんどの人は NULL を「値が空である」と理解している。だから NULL = NULL が真になりそうに思え、1 <> NULL も真になりそうに思える。実際に実行するとそうではない。

--- 3-1. comparisons against NULL ---
  eq | neq | null_eq_null | null_neq_null | gt | is_null | one_is_null
  NULL | NULL | NULL | NULL | NULL | 1 | 0

読み方はこうである。1 = NULL は NULL、1 <> NULL も NULL、NULL = NULL も NULL、1 > NULL も NULL である。確定値を返したのは IS NULL だけだった（NULL IS NULL が 1、1 IS NULL が 0）。

ここでの NULL は「結果が空だ」という意味ではなく、三つ目の論理値 UNKNOWN である。型を出力すればはっきりする。

--- 3-2. typeof() of each result - NULL is a value, not an error ---
  t_eq | t_true | t_false | t_nn
  null | integer | integer | null

真と偽は integer であり、NULL との比較結果は null 型である。エラーではなく値なのだ。だからこそ何の音もなく計算に紛れ込む。

3.1 なぜこう定義したのか

NULL を「分からない値」と読むと、すべてが自然になる。

  • ある人の年齢が分からない。その年齢は 30 か。分からない。偽ではなく分からないのである。よって age = 30 は UNKNOWN
  • その年齢は 30 ではないのか。これも分からない。よって age <> 30 も UNKNOWN
  • 二人の年齢がどちらも分からない。二人は同い年か。分からない。よって NULL = NULL も UNKNOWN

「値が空」と読むと三つ目が奇妙に見えるが、「分からない」と読めば当然の結論である。分からない値二つが等しいかどうかを、どうやって断定するというのか。

3.2 UNKNOWN が AND と OR を通る仕方

--- 3-3. NOT of unknown is still unknown ---
  not_unknown | unknown_or_true | unknown_or_false | unknown_and_true | unknown_and_false
  NULL | 1 | NULL | NULL | 0

この一行を表に展開するとこうなる。

式結果なぜ
UNKNOWN OR TRUETRUEOR は真が一つあれば確定する
UNKNOWN OR FALSEUNKNOWN分からないものが真かもしれず確定できない
UNKNOWN AND TRUEUNKNOWN分からないものが偽かもしれず確定できない
UNKNOWN AND FALSEFALSEAND は偽が一つあれば確定する
NOT UNKNOWNUNKNOWN分からないものの反対も分からない

規則は一つである。結論を確定できるときだけ確定し、それ以外では分からないが伝染する。そして NOT UNKNOWN が依然として UNKNOWN であることが、NOT IN を殺した決め手である。

3.3 WHERE は TRUE だけを通す

最後の一片である。三つの論理値が絞り込みでどう扱われるかを直接数えてみた。

--- 3-4. what WHERE does with each of the three values ---
  WHERE TRUE     -> 1 row(s)
  WHERE FALSE    -> 0 row(s)
  WHERE UNKNOWN  -> 0 row(s)
WHERE 句の値その行実行確認
TRUE通過1行
FALSE脱落0行
UNKNOWN脱落0行

ここで罠が完成する。UNKNOWN は絞り込みの段階で FALSE と区別されない。「分からない」と「そうではない」が同じ扱いを受ける。論理式の中では三つを区別しておきながら、結果を出すときには二つに畳んでしまうのだ。

3.4 ここで NOT IN を読み直す

x NOT IN (1, 2, NULL) はこう展開される。

x NOT IN (1, 2, NULL)
  = NOT (x IN (1, 2, NULL))
  = NOT (x = 1 OR x = 2 OR x = NULL)

x = 1  -->  NOT (TRUE  OR FALSE OR UNKNOWN) = NOT TRUE    = FALSE    -- dropped
x = 7  -->  NOT (FALSE OR FALSE OR UNKNOWN) = NOT UNKNOWN = UNKNOWN  -- dropped

どの経路をたどっても TRUE が出ない。リストにあれば FALSE、リストに無ければ UNKNOWN。WHERE は TRUE だけを通すので結果は0行である。先ほどの 2-3 の出力に 1 が一つも無かった理由がこれだ。

逆に IN は生き残る。x = 1 の行で TRUE OR FALSE OR UNKNOWN = TRUE になるからである。OR は真が一つあれば確定するので、NULL が混じっても真を作る経路は塞がれない。

PostgreSQL の公式文書もこの挙動を明示的に規定している。左辺が null であるか、等しい右辺の値が無くかつ右辺の行のいずれかが null を返す場合、NOT IN の結果は真ではなく null になり、これは null に対する SQL の通常の論理結合規則に沿ったものだと書かれている。つまり仕様がそう定めているのである。

4. 実務での本当の事故現場 - NOT IN (SELECT ...)

リテラルのリストに NULL を直接書き込む人はまずいない。事故は副問い合わせで起きる。リストがコードに見えないからである。

--- 0-1. refund_requests contents ---
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | 1200

4行のうちたった1行の customer_id が NULL である。この状態で「返金を要求したことのない顧客」を取り出す。

--- 4-1. customers who never requested a refund - the naive query ---
  SQL: SELECT id, name FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
  rows returned: 0
  id | name

--- 4-2. how many NULLs are in that subquery column ---
  total | non_null | nulls
  4 | 3 | 1

--- 4-3. same query after deleting the single NULL row ---
  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  ...
  10 | juno

--- 4-4. one NULL row is enough - inserting it back ---
  rows in rr_clean before insert : 3
  rows in rr_clean after insert  : 4
  NOT IN result now              : 0 rows
  after removing it again        : 8 rows

NULL の行を消せば8行、戻せば0行、また消せばまた8行である。スイッチのように動作する。

4.1 規模はまったく関係ない

「うちのテーブルは一万件なのだから NULL 一つくらい」という直感が通用しないことを数字で確認した。

=== B. one NULL among ten thousand rows ===
  blocklist rows                  : 10000   (values 1001..11000, none overlap customers)
  NULLs in blocklist.v            : 0
  SELECT id FROM customers WHERE id NOT IN (SELECT v FROM blocklist)
  rows returned                   : 10

  -- one single NULL row inserted --
  blocklist rows                  : 10001
  NULLs in blocklist.v            : 1
  NULL share of the table         : 1 / 10001 = 0.00999 percent
  rows returned                   : 0

  NOT EXISTS on the same table    : 10 rows
  LEFT JOIN / IS NULL             : 10 rows

一万行中 NULL が1行、割合にして 0.01 パーセント。結果は10行から0行になった。効くのは割合ではなく存在するかどうかである。一つで十分であり、一万個あっても結果は同じだ。

4.2 副問い合わせの WHERE が偶然 NULL を隠すとき

もっと厄介な場合がある。副問い合わせに付いた別の目的のフィルタが偶然 NULL を取り除くと、クエリは問題なく動く。そしてそのフィルタに手を入れた瞬間に壊れる。

=== B-2. a WHERE clause in the subquery can hide the NULL by accident ===
  NOT IN (SELECT v FROM blocklist)                             -> 0 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000)              -> 10 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v IS NULL) -> 0 rows

  the middle query works only because v > 5000 is UNKNOWN for the NULL row
  and therefore drops it. Change the filter and the query breaks again:
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v <= 5000)  -> 10 rows

真ん中のクエリが10行を出したのは、v > 5000 が NULL の行で UNKNOWN になり、その行が副問い合わせの結果から既に脱落していたからである。つまり NULL が二度作用して偶然相殺された。この種のクエリは条件を一つ変えただけで原因不明のまま0行になる。

4.3 外側の列が NULL の場合もある

ここまではリスト側の NULL だけを見てきた。比較される側の列が NULL でもその行は消える。リストに NULL が一つも無くてもそうなる。

=== D. SQLite: when the OUTER value is NULL ===
  rows: 3, one of them region = NULL
  WHERE region NOT IN ('seoul')  -> 1 rows
  id | region
  2 | busan
  the NULL-region row disappeared even though the list has no NULL
  WHERE region NOT IN ('seoul') OR region IS NULL -> 2 rows

3行のうち region が NULL の行が一つあったが、「ソウル以外の地域」を取り出したところ1行しか出なかった。地域が分からない顧客について「ソウルではない」と断定できないので UNKNOWN になり脱落したのである。含めたければ OR region IS NULL を明示する必要があり、そうすると2行になる。DuckDB でも数字は同じだった。

5. なぜ誰も気付かないのか

この不具合の本当の恐ろしさは論理ではなく発見できないことにある。三重に隠れる。

  • エラーが出ない。例外も、警告も、スロークエリログも無い。監視が捉えるべき信号そのものが存在しない
  • 0行は正常な結果に見える。「条件に合うデータが無い」と区別が付かない
  • 開発 DB では通ってしまう。手で作ったフィクスチャには NULL が無い
  • コードには何の問題も見えない。クエリ文だけを読めば論理は正確である。結果を変えるのはコードではなくその瞬間テーブルに入っている値だ
  • 再現が間欠的である。NULL を作った行が消えるとクエリはまた正常に動くので、報告を受けて確認する頃には既に問題が見えないことがある

三つ目を数字にしてみた。

=== B-3. the dev-versus-prod illusion ===
  dev fixture  (3 rows, hand-written, no NULL)       -> 10 rows   test PASSES
  prod data    (4 rows, one NULL from an old import) -> 0 rows    silently empty

テストは通る。開発者が手で書いたフィクスチャに NULL を入れる理由が無いからである。一方、運用 DB の NULL はたいてい以前のマイグレーション、中断したバッチ、外部連携の失敗が残した痕跡だ。コードレビューでも見えない。副問い合わせが何を返すかはコードではなくデータが決めるからである。

この不具合に関しては、NULL を含むフィクスチャを単体テストに一行足すことのほうが、コードレビュー十回よりも効く。

6. 代替その一 - NOT EXISTS は死なない

同じ意図を NOT EXISTS で書くとどうなるかを、同じデータで走らせた。

--- 5-1. the same intent written with NOT EXISTS ---
  SELECT c.id, c.name FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)

  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  5 | echo
  6 | flux
  7 | gale
  8 | hive
  9 | iris
  10 | juno

8行である。データはそのままで NULL もそのままなのに結果が出る。理由は判定の基準が違うからだ。

  • NOT IN は値を比較して論理値を作る。だから三値論理の支配を受ける
  • NOT EXISTS は内側の問い合わせが行を一つでも出したかだけを見る。「ある/ない」の二値であり UNKNOWN が入る余地が無い

NULL の行がどうなるかを直接数えてみた。

--- 5-3. why - the NULL row never matches r.customer_id = c.id ---
  id | matching_rows
  1 | 2
  2 | 1
  3 | 0
  4 | 0
  5 | 0
  6 | 0
  7 | 0
  8 | 0
  9 | 0
  10 | 0

customer_id が NULL の 103 番の要求はどの顧客にも結び付かなかった。NULL = 3 が UNKNOWN なので一致せず、一致しなければその副問い合わせが0行を返すだけである。NULL は結論を汚染できず、その場で止まる。

DuckDB でも同じだった。両エンジンとも NOT EXISTS は8行である。

7. 代替その二 - LEFT JOIN のあとに IS NULL

三つ目の書き方である。結合して一致に失敗した行だけを残す。

--- 6-1. anti-join written as LEFT JOIN + IS NULL ---
  SELECT c.id, c.name FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL

  rows returned: 8

--- 6-2. the three forms side by side, same table, same intent ---
  NOT IN (subquery)     -> 0 rows
  NOT EXISTS            -> 8 rows
  LEFT JOIN / IS NULL   -> 8 rows

この三行がこの記事の要約である。同じデータ、同じ意図、同じ正解。それなのに最初の一つだけが0行だ。

7.1 この書き方にも罠がある

IS NULL をどの列に適用するかが正解と誤答を分ける。値が NULL になり得る通常の列に適用すると静かに間違う。要求 104 番の amount を NULL にして再実行してみた。

=== A. SQLite: the LEFT JOIN trap, done properly ===
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | NULL

  WHERE r.req_id IS NULL  (primary key, never NULL in a matched row) -> 8 rows
  WHERE r.amount IS NULL  (nullable column - WRONG choice)           -> 9 rows

  the wrong version leaked customer 1, who DID request a refund:
  id | name | req_id | amount
  1 | aria | 104 | NULL
  3 | cedar | NULL | NULL
  4 | delta | NULL | NULL
  ...
  10 | juno | NULL | NULL

8行であるべきものが9行になり、返金を実際に要求した顧客 1 番が「要求したことのない顧客」の一覧に紛れ込んだ。一致には成功したのに、その行の amount がたまたま NULL だったからである。

規則は明快だ。IS NULL の検査は、結合キーや主キーのように NULL が絶対に入り得ない列にだけ適用する。一致した行でも NULL になり得る列を使うと、「一致に失敗した」と「一致したが値が空だった」を区別できなくなる。

8. 防御策 - IS NOT NULL を入れれば済むのでは

最も手軽な対応は副問い合わせにガードを入れることである。実際に動く。

--- 7-1. the defensive rewrite ---
  SELECT id, name FROM customers
  WHERE id NOT IN (SELECT customer_id FROM refund_requests WHERE customer_id IS NOT NULL)

  rows returned: 8

8行が出る。しかしこれを根本的な解決と呼んではいけない理由が三つある。

  • 繰り返す必要がある。NOT IN が使われているすべての箇所に漏れなく付ける必要があり、一箇所抜ければそのクエリは静かに0行になる。人が毎回覚えていなければならない防御はいつか失敗する
  • 見えない。外側のクエリだけを読む人にこのガードは見えない。なぜ付いているのか分からないのでリファクタリングで消されやすい
  • 意味を変える。その NULL が情報だったなら、消した瞬間に事実が消える

三つ目が特に重要である。例題でその NULL が何だったかを見てみよう。

--- 7-3. what the NULL actually meant here ---
  req_id | customer_id | amount
  103 | NULL | 7000
  a 7000 refund with no customer attached - dropping it hides a data bug

顧客が結び付いていない金額 7000 の返金要求。これは無視してよい雑音ではなく、どこかで参照整合性が壊れたという証拠である。IS NOT NULL で濾し取った瞬間、その事実は永久にレポートから消える。

だから順序はこうなる。

  1. その NULL がなぜそこにあるのかをまず見る。SELECT * FROM t WHERE col IS NULL
  2. 入ってはいけない値なら列に NOT NULL と外部キー制約を付けて源流で遮断する
  3. 入り得る値なら書き方を NOT EXISTS に変えて NULL の影響圏の外に出る
  4. IS NOT NULL のガードは急場をしのぐときだけ使い、なぜ捨ててよいのかコメントを残す

9. NULL が隠れる他の場所その一 - 集計関数

問題は NOT IN だけではない。同じ三値論理が集計では別の形で現れる。customers.credit の10行のうち4行が NULL の状態である。

--- 8-1. COUNT(*) vs COUNT(col) on customers.credit ---
  count_star | count_credit | count_distinct_credit | sum_credit | avg_credit | min_credit | max_credit
  10 | 6 | 6 | 1230 | 205.0 | 60 | 420

COUNT(*) は 10、COUNT(credit) は 6 である。前者は行を数え、後者は値があるものだけを数える。そして平均の分母がどちらなのかが実務で問題になり続ける。

--- 8-2. AVG denominator - it divides by the non-null count, not the row count ---
  s | n_nonnull | n_all | avg_builtin | s_div_nonnull | s_div_all
  1230 | 6 | 10 | 205.0 | 205.0 | 123.0

--- 8-3. COALESCE changes the answer, and that is the point ---
  avg_ignoring_nulls | avg_nulls_as_zero
  205.0 | 123.0

205.0 と 123.0。同じデータから出た二つの「平均」である。AVG(credit) は 1230 を 6 で割り、AVG(COALESCE(credit, 0)) は 1230 を 10 で割る。

どちらが正しいかは NULL の意味による。「限度額をまだ審査していない」なら分母から外すのが正しく、「限度額が 0 である」なら入れるのが正しい。どちらも SQL が代わりに決めてくれるわけではない。これが COALESCE の乱用が危険な理由だ。目の前の NULL を消す代わりに、測定対象そのものを変えてしまう。

空集合ではまた違う。

--- 8-4. aggregates over an empty set ---
  c | s | a | m
  0 | NULL | NULL | NULL
  COUNT returns 0, SUM/AVG/MAX return NULL - a SUM of nothing is not 0

COUNT は 0 を返すが SUM は NULL を返す。「何も無いものの合計は 0」が常識のようだが SQL はそうしない。だから集計結果をそのままアプリケーションの整数型に入れると、その地点で null 参照が起きる。防ぐには COALESCE(SUM(x), 0) を意識的に書く必要がある。DuckDB でも同一だった。

式NULL の扱い実行確認値

SUM / MIN / MAXNULL を無視1230 / 60 / 420
AVG(col)分母が非 NULL の個数205.0

10. NULL が隠れる他の場所その二 - UNIQUE 制約

「この列は UNIQUE だから重複は無い」という文が NULL の前では成立しない。

--- 9-1. inserting several NULLs into a UNIQUE column ---
  insert 'A' -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert 'A' again -> IntegrityError: UNIQUE constraint failed: u_test.code
  rows now: 4
  id | code
  1 | A
  2 | NULL
  3 | NULL
  4 | NULL

NULL が三つとも入った。一方、同じ文字列 'A' を二度目に入れるときは正確に拒否された。一意制約が NULL を互いに異なる値と見なすからである。NULL = NULL が UNKNOWN なので、「重複である」と判定する根拠が無いのだ。

複合 UNIQUE でも同様である。

--- 9-2. same thing on a multi-column UNIQUE ---
  insert ('x', 'y') -> OK
  insert ('x', NULL) -> OK
  insert ('x', NULL) -> OK
  insert (NULL, NULL) -> OK
  insert (NULL, NULL) -> OK
  rows now: 5

('x', NULL) が二回、(NULL, NULL) が二回入った。計5行すべて挿入成功である。DuckDB 1.5.5 でも NULL 三つが入り、'A' の重複だけが拒否された。つまり両エンジンとも同じである。

SQLite の公式文書はこの非一貫性を自ら認めている。UNIQUE 列では NULL が互いに区別されるが SELECT DISTINCT と UNION では区別されないと明記し、これはやや恣意的だが Oracle・PostgreSQL・DB2 と同じ挙動に合わせるための決定だったと記している。同じエンジンの中で規則が逆であることが意図された状態なのだ。

実務上の含意。「事業者番号は UNIQUE だから安心」と書いたのに、その列が NULL を許容しているなら、事業者番号が空の行は無制限に入る。重複を本当に防ぎたければ UNIQUE と NOT NULL を一緒に付ける必要がある。なお PostgreSQL 15 からは UNIQUE で NULL を同じ値として扱う選択肢が加わったとされるが、この記事では実行して確認していないので断定しない。

11. NULL が隠れる他の場所その三 - GROUP BY と DISTINCT

SQLite は昇順で NULL を先頭に、降順で末尾に置く。NULL をすべての値より小さいもののように扱っているのだ。DuckDB は違う。

  9 | 60
  6 | 90
  3 | 150
  8 | 210

ちなみに並べ替えと MIN・MAX は互いに違う振る舞いをする。これも確認した。

=== C. SQLite: where NULL sorts, and what MIN/MAX think ===
  ORDER BY v ASC  -> NULL 1 5 9
  ORDER BY v DESC -> 9 5 1 NULL
  min_v | max_v | n | n_nonnull
  1 | 9 | 4 | 3
  so NULL sorts as if smaller than every value, yet MIN() skips it entirely

並べ替えでは NULL が最も小さい値のように先頭に来るのに、MIN() はそれをまったく無視して 1 を返す。「並べ替えて最初の行を取り出すこと」と MIN() は同じではない。

13. 診断法 - 既にあるクエリからこの危険を見つけ出す

原理が分かったので、次は既に運用中のクエリを点検する番である。順序がある。

13.1 第1段階 - 30秒で判定する SQL

疑わしい副問い合わせの列に対して、これ一つを走らせればよい。

SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;

例題のテーブルに走らせた結果である。

--- 12-1. does this subquery column contain NULL at all ---
  total_rows | non_null | null_rows | verdict
  4 | 3 | 1 | DANGEROUS - NOT IN will return 0 rows

--- 12-2. the same check on a NULL-free column ---
  total_rows | non_null | verdict
  4 | 4 | SAFE for NOT IN

判定基準は単純だ。COUNT(*) と COUNT(列) の数字が違えば、その列に対するすべての NOT IN は既に壊れている。この判定は DuckDB でも同じ結果を出した。

13.2 第2段階 - スキーマが保証しているか確認する

今 NULL が0件であることと、スキーマが NULL を禁じていることはまったく別の話である。前者は明日壊れる。

--- 12-3. is the column even declared NOT NULL - read the schema ---
  name | type | notnull | pk
  req_id | INTEGER | 0 | 1
  customer_id | INTEGER | 0 | 0
  amount | INTEGER | 0 | 0

customer_id の notnull が 0 である。つまりスキーマ上 NULL が許容されている。今日 NULL が無くても安全とは言えない。PostgreSQL 系では次で同じものを見る。

SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';

13.3 第3段階 - その NULL が何だったのかを見る

消す前に必ずこれを先にやる。

SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;

8節で見たように、その NULL がデータ不整合の証拠である場合が多い。症状を消す前に原因を見る。

13.4 第4段階 - 三つの書き方を並べて数字を比べる

最も確実な確認法である。同じ意図を三通りに書いて数字が食い違うか見る。食い違えば NOT IN が犯人だ。

  step 1  SELECT COUNT(*) FROM t;                 -- 4
  step 2  SELECT COUNT(col) FROM t;               -- 3
  if the two numbers differ, every NOT IN against that column is already broken

13.5 第5段階 - 実行計画もヒントをくれる

三つの書き方の計画がどう違うかを出力してみた。

--- 13-7. query plan of the three anti-join forms (SQLite) ---
  NOT IN     : SCAN customers / USING INDEX ix_rr_cust FOR IN-OPERATOR
  NOT EXISTS : SCAN c / CORRELATED SCALAR SUBQUERY 1
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?)
  LEFT JOIN  : SCAN c
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?) LEFT-JOIN

三つともインデックスを使っている。つまり NOT EXISTS に変えることは性能を犠牲にする選択ではない。この例題の規模では計画の形が違うだけでインデックスの活用は同等だった。ちなみに IS NULL の条件もインデックスで処理された。

--- 13-6. index scan still finds NULLs - IS NULL is indexable here ---
  WHERE customer_id IS NULL : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)
  WHERE customer_id = 1     : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)

14. その他の罠 - CHECK、CASE、文字列、空集合

同じ原理が現れる場所をいくつか追加で確認した。

14.1 CHECK 制約は UNKNOWN を通す

--- 13-2. CHECK constraint passes when the result is UNKNOWN ---
  insert qty=5 -> OK
  insert qty=NULL -> OK
  insert qty=-1 -> IntegrityError: CHECK constraint failed: qty > 0
  rows now: 2

CHECK (qty > 0) を付けたのに NULL が通った。-1 は正確に拒否された。NULL > 0 が UNKNOWN であり、制約は偽のときだけ拒否するからである。DuckDB でも同じだった。数量が必ず正でなければならないなら CHECK だけでは足りず、NOT NULL を別途付ける必要がある。

14.2 CASE WHEN col = NULL は決して発火しない

--- 13-1. CASE WHEN col = NULL never fires ---
  id | credit | branch
  1 | 300 | has-value
  2 | NULL | matched-is
  10 | NULL | matched-is

WHEN credit = NULL THEN 'matched-eq' の枝は一度も選ばれなかった。NULL の行ですら次の枝である WHEN credit IS NULL に流れた。= NULL は構文エラーではないため、静かに死んだコードになる。コードレビューでこのパターンを見たら必ず指摘すべき理由がこれだ。

14.3 文字列結合一つが全体を消す

--- 13-3. string concatenation with NULL ---
  concat_result | with_coalesce
  NULL | fallback

'total: ' || NULL の結果は 'total: ' ではなく全体が NULL である。レポート文字列を組み立てていて列が一つ空になると、文全体が消える。ここが COALESCE を正当に使う代表的な場面である。

14.4 空のリストでは NOT IN が全部を返す

--- 13-5. an empty subquery makes NOT IN return everything ---
  NOT IN (SELECT customer_id FROM refund_requests WHERE 1=0) -> 10 rows
  NOT EXISTS on the same empty set                           -> 10 rows

副問い合わせが0行なら NOT IN は全10行を返す。論理的には正しい（何も無いリストに属さないものは全部である）。それでも0行と全行という両極端の間に NULL 一つがスイッチとして置かれていることは覚えておく価値がある。削除バッチや権限フィルタでは、この二つの極端はまったく性格の違う事故を生む。

14.5 左辺が NULL なら IN も NOT IN も UNKNOWN

--- 13-4. NOT IN with NULL on the LEFT side ---
  left_null_notin | left_null_in
  NULL | NULL

4.3 節で見たものの要約である。NULL NOT IN (1,2) も NULL IN (1,2) もどちらも UNKNOWN だ。リストに NULL が無くても左辺が NULL ならその行はどちらにも通過できない。

14.6 null 安全な比較演算子

NULL 同士を等しいと判定したいときに使える演算子がある。SQLite 3.49.1 で確認した。

--- 3-5. null-safe comparison operators available here ---
  is_ | is_not | isnd | isnd2 | isd
  1 | 0 | 0 | 1 | 1
  • NULL IS NULL は 1（真）。SQLite では IS が null 安全な等号の役割を果たす
  • NULL IS NOT DISTINCT FROM NULL は 1（真）。NULL 同士を等しいと見なす
  • 1 IS NOT DISTINCT FROM NULL は 0（偽）。UNKNOWN ではなく確定した偽である
  • 1 IS DISTINCT FROM NULL は 1（真）

DuckDB でも同じ結果だった（false、true、true）。IS DISTINCT FROM 系は結果が決して UNKNOWN にならない。二つの値が「分からない」を含んでいても、真か偽のどちらかに確定する。二つの列を比較しつつ両方の NULL を「同じ」として扱う必要がある変更検知のロジックで有用である。

15. 判断表 - いつ何を使うか

ここまでの実行結果を一つの表に畳む。この表が実務で使う最終成果物である。

意図使うもの理由と注意点
副問い合わせの結果に無い行を探す（最も多い場合） NOT EXISTS NULL と無関係に動作する。意図が文として読め、確認した実行計画でもインデックスをそのまま使う。既定にすること
反結合しつつ相手側の列も SELECT する LEFT JOIN ... IS NULL 結合結果をそのまま使える。IS NULL は必ず主キーか結合キーに — 通常の列に適用すると8行が9行になった
ハードコードした少数のリテラルを除外する NOT IN ('a','b') リストに NULL が無いことが目で確認できる。この場合に限り安全である
副問い合わせの列が NOT NULL で宣言されている NOT IN も可 スキーマが保証する。ただしスキーマ変更一回で壊れる。依存をコメントで残すこと
NULL の行も結果に含めたい ... OR col IS NULL を明示 外側の列が NULL ならその行も脱落する。1行が2行になる違い
二つの値を NULL 込みで等しい/違うと判定する IS NOT DISTINCT FROM 結果が UNKNOWN にならない。変更検知や比較のロジックに適する
急場をしのぐ WHERE col IS NOT NULL のガード 安全網であって解決ではない。すべての箇所で繰り返す必要があり、NULL が情報だったなら事実が消える

一行に縮めるとこうなる。集合に無いものを探すときは NOT EXISTS を既定とし、NOT IN はリストがリテラルの場合か、列が NOT NULL で宣言されている場合にだけ使う。

16. まとめ - これはバグではない

この記事で確認したことをもう一度数えてみる。

  • リストに NULL 一つで 0行。除けば 8行。どちらのクエリもエラーなく成功
  • 同じリストで IN は 2行と正常に動作
  • 行ごとの条件式の値に 1 が一つも無い。偽が2個、残り8個はすべて UNKNOWN
  • 一万行中 NULL 1行（0.01 パーセント）だけで10行が0行になった
  • NOT EXISTS 8行、LEFT JOIN IS NULL 8行、NOT IN だけ 0行
  • LEFT JOIN で検査する列を誤ると 9行になり誤答が混ざる
  • 開発フィクスチャは 10行で通過、運用データは 0行 — テストでは捕まえられない
  • 平均が 205.0 と 123.0 の二つ、空集合の SUM は NULL
  • UNIQUE 列に NULL 3個の挿入に成功、CHECK (qty > 0) に NULL の挿入に成功
  • ORDER BY の NULL の位置が 三つのエンジンで互いに異なる

このすべてが一つの定義から出てくる。NULL は「値が無い」ではなく「分からない」である。分からない値がリストの中にあるか無いかは断定できないので UNKNOWN であり、WHERE は TRUE だけを通すので0行になる。SQL は間違った答えを出すくらいなら何も答えないことを選んだのだ。それがこの設計の一貫性である。

問題はその一貫性がエラーなしで現れる点にある。型の誤りならコンパイルで捕まり、構文の誤りなら実行で捕まる。ところがこれは成功したまま空になっている。だから人が「データが無いのだろう」で片付けてしまう。

対応は二行で終わる。第一に、集合に無いものを探すときは NOT EXISTS を既定にする。第二に、テストのフィクスチャに NULL を一行入れる。二つ目が特に安上がりで強力だ。この記事のすべての失敗例は、NULL を含むフィクスチャ一行があれば配備前に捕まっていた。

よくある質問

Q. NOT IN の結果が0行なのにエラーが出ない。なぜか。

リストまたは副問い合わせの結果に NULL が一つでもあればそうなる。確認したところ、10行のテーブルで id NOT IN (1, 2, NULL) は 0行、NULL だけを除いた id NOT IN (1, 2) は 8行であり、どちらも正常終了した。SQL の論理値が真・偽の二つではなく真・偽・不明の三つだからである。NULL との比較はすべて不明になり、NOT 不明 も依然として不明であり、WHERE は真だけを通す。構文エラーではなく定義どおりに計算した結果なのでエラーが出ない。

Q. IN は動くのに NOT IN だけ動かない理由は。

一致する行で真が出るかどうかで分かれる。IN (1, 2, NULL) は 2行、NULL を除いたものも 2行で同じだった。IN は等号比較を OR でつないだものであり、OR は真が一つあれば残りが不明でも真に確定する。逆に NOT IN ではどの行も真になれない。行ごとの値を出力すると id 1 と 2 で 0、残りの8行はすべて NULL だった。真が一つも無かったのである。

Q. NOT EXISTS に書き換えれば本当に解決するのか。

解決する。同じデータで NOT IN は 0行、NOT EXISTS は 8行、LEFT JOIN IS NULL は 8行だった。NOT EXISTS は値の比較ではなく行の存在の有無だけを見るので UNKNOWN が入る余地が無い。参照列が NULL の行は等号を満たせず単に一致しないだけで、実際に顧客ごとの一致数を数えるとその行はどの顧客にも結び付かなかった。ただし LEFT JOIN の形式には別の罠があり、IS NULL を主キーではない通常の列に適用したところ 9行になり誤答が混ざった。

Q. 副問い合わせに IS NOT NULL を入れれば済むのではないか。

動きはする（8行）。しかし安全網であって解決ではない。第一に NOT IN が使われているすべての箇所で繰り返す必要があり、一箇所抜ければそのクエリは静かに0行になる。第二に外側のクエリだけを読む人には見えず、リファクタリングで消されやすい。第三にその NULL が情報だったなら意味が変わる。例題でその行は顧客が結び付いていない金額 7000 の要求、つまり参照整合性が壊れた証拠だった。根本的な対策は NOT NULL 制約を付けるか、書き方を NOT EXISTS に変えることである。

Q. NULL のせいで静かに間違う場所は他にどこか。

少なくとも五箇所を実行で確認した。集計では COUNT(*) が 10 なのに COUNT(credit) は 6 であり、平均が 205.0 と 123.0 に分かれた。空集合では COUNT が 0 でも SUM・AVG・MAX は NULL だった。UNIQUE 制約には NULL が 3個も入った。GROUP BY では = で等しくない NULL 同士が一つのグループになった。ORDER BY では SQLite が NULL を昇順の先頭に、DuckDB が末尾に置き、エンジンごとに答えが違った。

# NOT IN と NULL — 真理値表・代替構文の比較・診断SQL

> 出典: braindetox.kr — NOT IN のリストに NULL が一つ混ざると結果が丸ごと空になる
> 根拠: SQLite 3.49.1 / DuckDB 1.5.5 / Windows 10 での実行検証、PostgreSQL 公式マニュアルとの照合
> このファイルをそのまま AI に貼り、「この基準で我々のクエリを点検してほしい」と書けば使えます。
> 要点は一行です。**NULL は「値が無い」ではなく「分からない」です。** 分からない値がリストに無いと断定できないので UNKNOWN になり、WHERE は TRUE だけを通すので 0 行になります。

## 0. 症状カード — このファイルが必要な状況

- クエリは成功した。**エラーは出ていない。**
- しかし結果が **0 行**である。
- 昨日までは出ていた。あるいは開発用 DB では出る。
- クエリの中に `NOT IN (SELECT ...)` がある。

→ §3 の診断 SQL を回す。30 秒で終わる。

## 1. 三値論理の真理値表

SQL の論理値は TRUE / FALSE の二つではなく、**TRUE / FALSE / UNKNOWN の三つ**である。

### 1-1. 比較演算子が NULL に出会うと

| 式 | 結果 | 備考 |
|---|---|---|
| `1 = 1` | TRUE | |
| `1 = 2` | FALSE | |
| `1 = NULL` | **UNKNOWN** | FALSE ではない |
| `1 <> NULL` | **UNKNOWN** | TRUE ではない |
| `NULL = NULL` | **UNKNOWN** | 等しくないとも言えない |
| `1 > NULL` | **UNKNOWN** | すべての比較演算子で同じ |
| `NULL IS NULL` | TRUE | `IS` だけが確定値を返す |
| `1 IS NULL` | FALSE | |

### 1-2. AND / OR / NOT

| 式 | 結果 |
|---|---|
| `UNKNOWN OR TRUE` | **TRUE** |
| `UNKNOWN OR FALSE` | UNKNOWN |
| `UNKNOWN AND TRUE` | UNKNOWN |
| `UNKNOWN AND FALSE` | **FALSE** |
| `NOT UNKNOWN` | **UNKNOWN** |

読み方はこうである。OR は TRUE が一つあれば確定する。AND は FALSE が一つあれば確定する。**それ以外では「分からない」が伝染する。**

### 1-3. WHERE は TRUE だけを通す

| WHERE 句の値 | その行 |
|---|---|
| TRUE | 通過 |
| FALSE | 脱落 |
| **UNKNOWN** | **脱落** |

UNKNOWN が絞り込みの段で FALSE と同じ扱いになる。この一つの規則が、この種の不具合すべての出口である。

### 1-4. だから IN は生きて NOT IN は死ぬ

`x IN (a, b, c)` は `x = a OR x = b OR x = c` に展開される。

| 場合 | `IN (1, 2, NULL)` | `NOT IN (1, 2, NULL)` |
|---|---|---|
| x = 1 (リストにある) | `TRUE OR ... OR UNKNOWN` = **TRUE** → 通過 | `NOT TRUE` = **FALSE** → 脱落 |
| x = 7 (リストに無い) | `FALSE OR FALSE OR UNKNOWN` = **UNKNOWN** → 脱落 | `NOT UNKNOWN` = **UNKNOWN** → 脱落 |

- `IN` は一致する行で TRUE が出るので**正常に動く**。
- `NOT IN` はどの行でも TRUE が出ない。一致すれば FALSE、不一致なら UNKNOWN。**だから常に 0 行になる。**

## 2. 三つの反結合の比較表

「A にあって B に無いもの」を求める三つの書き方。同一データ（顧客 10 行、要求 4 行のうち参照列が NULL の行が 1 行）での実行結果である。

| 書き方 | 結果 | NULL 安全 | 判定の基準 | 注意点 |
|---|---|---|---|---|
| `NOT IN (SELECT col FROM t)` | **0 行** | 不可 | 三値論理 | col に NULL が一つでもあれば全滅。エラーは出ない |
| `NOT EXISTS (SELECT 1 FROM t WHERE t.col = a.id)` | **8 行** | 可 | 行が存在するか | NULL の行は `=` を満たさず単に一致しないだけ |
| `LEFT JOIN t ON t.col = a.id WHERE t.pk IS NULL` | **8 行** | 可 | 一致に失敗した行 | **`IS NULL` の検査は必ず NOT NULL 列（主キー）に** |

`NOT IN` だけが違う答えを出した。残りの二つは一致している。

### 2-1. LEFT JOIN 形式に潜む罠

`WHERE` で検査する列を誤ると、静かに間違う。

| 検査した列 | 結果 | 判定 |
|---|---|---|
| `r.req_id IS NULL`（主キー。一致した行なら絶対に NULL ではない） | 8 行 | 正解 |
| `r.amount IS NULL`（値が NULL になり得る通常の列） | **9 行** | 誤り — 実際に要求した顧客が混ざった |

**規則: LEFT JOIN による反結合の `IS NULL` は、結合キーまたは主キーにのみ適用する。**

### 2-2. 意図別の判断表

| したいこと | 使うもの | 理由 |
|---|---|---|
| 副問い合わせの結果に無い行を探す | **`NOT EXISTS`** | NULL の影響を受けず、意図が文として読める |
| 反結合しつつ相手側の列も SELECT する必要がある | **`LEFT JOIN ... IS NULL`** | 結合結果をそのまま利用できる |
| ハードコードした少数のリテラルを除外する | `NOT IN ('a','b')` | リストに NULL が無いことが目で確認できる |
| 副問い合わせの列が **`NOT NULL` で宣言されている** | `NOT IN` も可 | ただしスキーマ変更でいつでも壊れる |
| 「値が NULL の行も結果に含める」が意図 | `... OR col IS NULL` を**明示** | 外側の列が NULL ならその行も脱落する |

## 3. 診断 SQL — そのまま貼って使う

### 3-1. この列は NOT IN に安全か（30 秒）

```sql
SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;
```

`COUNT(*)` と `COUNT(列)` の数字が**違えば、その列に対するすべての `NOT IN` は既に壊れている。**

### 3-2. スキーマが NOT NULL を保証しているか

```sql
-- SQLite
SELECT name, type, "notnull", pk FROM pragma_table_info('the_table');

-- PostgreSQL 系
SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';
```

`is_nullable = 'NO'`（または SQLite の `notnull = 1`）でなければ、**今 NULL が 0 件でも安全ではない。**明日入ってくる。

### 3-3. その NULL が実際に何を意味していたか見る

```sql
SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;
```

消す前にこれを見る。NULL が**データ不整合の証拠**である場合が非常に多い。例題では顧客が紐付いていない返金要求だった。

### 3-4. 三つとも走らせて数字を比べる

```sql
SELECT 'not_in'     AS form, COUNT(*) AS n FROM (
  SELECT id FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
)
UNION ALL
SELECT 'not_exists', COUNT(*) FROM (
  SELECT c.id FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)
)
UNION ALL
SELECT 'left_join', COUNT(*) FROM (
  SELECT c.id FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL
);
```

三つの数字が食い違えば、最初のものが犯人である。

### 3-5. 外側の列も忘れないこと

リストに NULL が無くても、**比較される側の列**が NULL ならその行は脱落する。

```sql
-- region が NULL の行はこの条件から消える
SELECT * FROM t WHERE region NOT IN ('seoul');

-- 含めたいなら明示する必要がある
SELECT * FROM t WHERE region NOT IN ('seoul') OR region IS NULL;
```

## 4. NULL が隠れる他の場所 — 要約表

| 場所 | 挙動 | 実測値（10 行・NULL 4 個） |
|---|---|---|
| `COUNT(*)` | 行を数える | 10 |
| `COUNT(col)` | **NULL を除く** | 6 |
| `SUM` / `AVG` / `MIN` / `MAX` | **NULL を無視する** | AVG = 205.0 |
| `AVG(COALESCE(col, 0))` | NULL を 0 として数える | **123.0** — 答えが変わる |
| 空集合の `SUM` / `AVG` / `MAX` | **NULL を返す**（0 ではない） | NULL |
| `UNIQUE` 制約 | **NULL は複数許容される** | NULL 3 個の挿入に成功 |
| `GROUP BY` | **NULL 同士が一つのグループ** | NULL グループ 1 個（2 行） |
| `SELECT DISTINCT` / `UNION` | **NULL を重複排除する** | distinct 3 個 |
| `CHECK` 制約 | 結果が UNKNOWN なら**通過** | `CHECK (qty > 0)` に NULL の挿入が成功 |
| `CASE WHEN col = NULL` | **決して発火しない** | 必ず `IS NULL` を使う |
| 文字列結合 `'a' \|\| NULL` | **NULL** | 全体が消える |

`UNIQUE` は NULL を互いに異なるとみなし、`DISTINCT` は同じとみなす。**同一エンジンの中で規則が逆である。**

## 5. ORDER BY における NULL の位置 — エンジンごとに違う

| エンジン | `ORDER BY col ASC` | `ORDER BY col DESC` | 根拠 |
|---|---|---|---|
| SQLite 3.49.1 | **NULL が先** | NULL が後 | 実行確認 |
| DuckDB 1.5.5（既定設定） | NULL が後 | **NULL が後** | 実行確認 |
| PostgreSQL | NULL が後 | **NULL が先** | 公式マニュアル |

三つのエンジンが互いに異なる。**`ORDER BY` の結果を前後で切り取るコード（LIMIT、ページネーション、最新 1 件）は、エンジンを移した瞬間に静かに答えが変わる。**

移植可能な解:

```sql
-- NULLS FIRST / NULLS LAST を明示する（SQLite 3.30+、PostgreSQL、DuckDB が対応）
SELECT * FROM t ORDER BY col ASC NULLS LAST;

-- 句が使えないエンジンでの回避
SELECT * FROM t ORDER BY (col IS NULL) ASC, col ASC;
```

## 6. コードレビュー点検文 — レビューコメントにそのまま貼る

- [ ] **この `NOT IN` の副問い合わせ列が `NOT NULL` で宣言されているか、スキーマで確認しましたか。** 今 NULL が無いことと、スキーマが禁じていることは別です。
- [ ] **この `NOT IN (SELECT ...)` を `NOT EXISTS` に書き換えられますか。** 書き換えられるなら書き換えるべきです。性能も概ね同等か良好です。
- [ ] **副問い合わせに `WHERE col IS NOT NULL` のガードを足したなら、その NULL を捨ててよい理由がコメントにありますか。** ガードは症状を隠すもので、原因を直すものではありません。
- [ ] **LEFT JOIN 反結合の `IS NULL` は主キーか結合キーに掛かっていますか。** NULL になり得る通常の列に掛けると、一致した行が結果に混ざります。
- [ ] **比較される外側の列が NULL になり得ますか。** その場合、その行が結果から抜けることが意図か確認し、違うなら `OR col IS NULL` を明示してください。
- [ ] **`= NULL` または `<> NULL` と書いた条件はありませんか。** 常に UNKNOWN です。`IS NULL` / `IS NOT NULL` に変えてください。
- [ ] **`COUNT(col)` と `COUNT(*)` のうち、意図した方を使いましたか。** 前者は NULL を除いて数えます。
- [ ] **`AVG` の分母は全行数であるべきですか、NULL を除いた数であるべきですか。** 既定は後者です。前者が欲しければ `COALESCE` で明示してください。
- [ ] **`ORDER BY` の結果を `LIMIT` で切っているなら、`NULLS FIRST/LAST` を明示しましたか。** エンジンの既定値は互いに異なります。
- [ ] **テストのフィクスチャに NULL は入っていますか。** 手で書いたフィクスチャには大抵 NULL が無いため、この不具合はテストを通過し、本番でだけ発火します。
- [ ] **`UNIQUE` で重複を防いだと書いたなら、その列が NULL のときも防げていますか。** 多くのエンジンで NULL は複数入ります。
- [ ] **`CHECK` 制約が NULL も弾いてくれると仮定していませんか。** 条件が UNKNOWN なら通過します。`NOT NULL` を別途付けてください。

## 7. 一段落の要約

`NOT IN` は壊れた機能ではない。NULL は「分からない」という定義を最後まで貫いた結果である。**分からない値がリストの中にあるか無いかは断定できないので答えは UNKNOWN であり、WHERE は TRUE だけを通すので 0 行になる。**論理的に正しい。問題は、その正しさが**エラーを伴わずに**現れるため、「データが無いのだろう」で片付けられてしまうことである。だから規則は一つだけである。**集合に無いものを探すときは `NOT EXISTS` を既定とし、`NOT IN` はリストがリテラルの場合か、列が `NOT NULL` で宣言されている場合にだけ使う。**
