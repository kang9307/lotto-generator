让LLM画图表时到底哪里出错 - 语义驱动规范的价值与代价

坐标轴类型误判、整数日期、配色滥用，以及「只改这一处」永远落不准的规范

2026年8月3日 IT技术

引言：「只把柱子改成蓝色」却重画了整张图

你给模型发去一行字。「柱子改成蓝色系就行」。回来的图确实变蓝了。但昨天手工调好的画布宽度退回了原值，坐标轴刻度间隔变了，几个标签开始互相压盖。你用一个修正换来了三个没被察觉的回归。

这不是运气问题，这正是本文的起点。出错的位置固定得令人吃惊。坐标轴该当连续量还是分类，算一处；看起来像日期的整数该怎么读，算一处；配色用到几种，算一处；还有「只改这一处」这句话究竟落在规范的哪一行，再算一处。

这四处都不是因为模型不够聪明。它们出自一个事实：需要模型填的格子太多，而且这些格子彼此纠缠。一张做得好的Vega-Lite图里，比例尺定义域、时间单位、标记宽度、画布宽度、标签角度、配色方案、图例位置全部是手工钉死的。改动其中一个，另外六个就会失准。人来做也会失准，何况每一轮都从头重写的模型。

2026年7月，微软研究院公开了Flint。你只需声明每个字段的含义，解析、坐标轴、格式、配色和布局由编译器推导——这是一种中间语言。本文的目的不是介绍Flint，而是看清它究竟在解决什么问题，以及这种做法放弃了什么。工具会换，这个问题不会走。

先给结论。语义驱动的规范可靠地带来的不是「更漂亮的图」，而是「简短且可修改的图表定义」。质量提升被测出来了，但幅度不大，而且有意思的是模型越强，这份收益越小。相反，规范变短的效果与模型无关。引入决策就在这里分岔。

1. 出错的位置是固定的 - 五种故障

把图表交给LLM画过的人，看下面这份清单不会陌生。无论语法是Vega-Lite、ECharts还是Matplotlib，这五种几乎以同样的形态反复出现。

故障在规范的什么地方产生屏幕上表现为人能发现吗
坐标轴类型误判在定量、有序、名义之间选错比例尺连续量散成二十根柱子，或者分类被折线连起来通常能发现
时间解析失败把整数或字符串日期直接送上时间轴全部飞到1970年代某处，或者顺序被打乱难以发现
非可加值堆叠把比率、平均值、排名做成堆叠柱合计超过百分之百，或者高度毫无意义几乎发现不了
配色误用与滥用发散型字段用了顺序色带，二十个分类上彩虹零落在非中性的颜色上，图例吃掉画布滥用看得见，误用看不见
修改指令落错属性一个诉求散落在多个属性里变的不是你要改的那一项立刻可见，原因不可见

其中第三和第四最糟糕，因为成品看上去是好的。坐标轴坏掉的图重画一次就行，但把比率堆起来的柱状图会原样进入会议材料。可视化的价值不来自美观，而来自察觉异常所需的时间，而这两种故障把那个时间推向无穷。至于到底要看什么异常才会显形，我在数据库观测工具那篇里单独讨论过。

第五种性质不同。前四种是第一次生成时的问题，这一种是修改时的问题。而在LLM工作流里，一次就把图做完的情况几乎不存在。对话总是延续为「挺好，就是这一处」。

2. 一个叫202001的列，会分出三条路

抽象说法难以落地，那就取一个具体场景。Flint论文用的例子与此相同，而且这在企业数据仓库里几乎天天遇到：月度指标表的期间列，存的是202001、202002这样的六位整数。

人一眼读成2020年1月。模型也这么读。问题在于模型把读到的东西写进规范的那一刻，路就分成了三条。

模型的选择写进规范的东西结果为何如此
直接当时间轴字段类型指定为时间型年份塌缩，或坐标轴打结把202001当成UNIX秒或年份值来解释
退回分类型字段类型指定为名义型出现七十二个格子，标签互相压盖六年就是七十二个月，每个月成为独立分类
手工解析计算变换、时间单位、标记宽度、画布宽度、标签角度结果正确五个值必须彼此吻合才成立

第三条是正解，而正解的形状本身就是问题。在Vega-Lite里认真写出来大致是这样。

{
  "transform": [
    { "calculate": "datetime(floor(datum.Period/100), datum.Period%100-1)",
      "as": "PeriodDate" }
  ],
  "mark": { "type": "bar", "width": { "band": 0.9 } },
  "encoding": {
    "x": {
      "field": "PeriodDate", "type": "temporal", "timeUnit": "yearmonth",
      "axis": { "format": "%Y-%m", "labelAngle": -45, "labelOverlap": "greedy" }
    },
    "y": { "field": "Users", "type": "quantitative", "aggregate": "sum",
           "scale": { "zero": true } }
  },
  "width": 504
}

数一数这段里模型可能出错的位置。除法与取模的组合、月份索引从0还是从1开始、时间单位字符串、格式字符串、标签角度、防重叠策略、带宽比例、画布宽度。八个。而且其中相当一部分互相依赖。把画布宽度加到720，标签角度就可以退回0，带宽比例也得重新看。

关键在这里。模型本来就知道这是2020年1月。失准发生在把已知的东西翻译成八个低层参数的过程里。那就别让它翻译，让它直接写下它知道的东西——这正是语义驱动规范的出发点。

3. 写短了不好看，写长了会坏

可视化语法有一个由来已久的两难，而Flint论文和官方博客的问题意识正是从这里开始的。

  • 短规范依赖系统默认值。三行就能出图，但坐标轴格式寡淡，标签压盖，配色是库自带的调色板。
  • 长规范能给出想要的结果。代价是冗长、易碎，而且人打开后很难读出每个选择的理由。
  • 人是靠反复修改在这两者之间来回的。画出来，不对就改一行，再看。
  • 模型不擅长这种循环。因为每轮都重写整体，所以不收敛，而是震荡。

上面还压着一件事：长规范吃令牌。一张图每轮都整体重写六十行JSON的流水线，对话越长成本越是线性上升。而重写的这六十行里，真正改变的只有一行。

把结构压缩后再交给模型，这个思路在代码侧已经先验证过。把代码库变成可查询图谱的做法瞄准的其实是同一件事：不要把一切都丢给模型，而是给它只保留了它必须判断的部分的表示。

4. 语义类型替你决定什么 - 三层体系

Flint的规范分成两块：声明字段是什么的部分，和声明用什么图画在哪些通道的部分。仓库给出的最小形态是这样。

import { assembleVegaLite } from 'flint-chart';

const spec = assembleVegaLite({
  data: { values: myData },
  semantic_types: { weight: 'Quantity', mpg: 'Quantity', origin: 'Country' },
  chart_spec: {
    chartType: 'Scatter Plot',
    encodings: { x: { field: 'weight' }, y: { field: 'mpg' },
                 color: { field: 'origin' } },
    baseSize: { width: 400, height: 300 },
  },
});

把origin声明为Country，一连串决定就跟着来了：它是分类的、无序的、基数有限的、用颜色区分最自然的、图例里应直接写名称的、不该套用顺序色带的。一个词顶替六项低层设置。

这套类型体系不是扁平的，而是三层。论文给出的结构如下。

层次决定什么数量示例
第一层 · 领域解析策略。这个值最初该被读成什么6时间型、分类型、度量值、离散值、标识符、地理
第二层 · 族可聚合性、零值的含义、定义域结构15日期时间、时长、实体、分箱、总量、比例、评分、排名、坐标
第三层 · 类型呈现。格式、排序、默认配色系44年月、月份、百分比、营收、利润、纬度、状态、方向

分层之所以重要，是因为继承。新增一个类型时不必从零定义解析和聚合规则，继承父级行为后只收窄呈现方式即可。对已有指标字典的组织来说，这也意味着这套结构很好对应。

为什么会有两个数字。仓库文档写语义类型七十种以上，论文写第三层四十四种。两者统计的层次不同。把族和别名一起算就是前一个数，只算末端类型就是后一个数。引用时不注明依据哪一种口径，看上去就会互相矛盾。

第二层是实务上最值钱的一层。区分总量与比例，意味着能否使用堆叠柱在类型阶段就已决定。前面标为「几乎发现不了」的非可加值堆叠故障，在这里被结构性地堵住了。本来要靠人工评审去抓的东西，改由类型来抓。

5. 编译器做的事 - 三个阶段

从声明到真正的图表规范要走三个阶段。知道这个结构，结果不满意时该怀疑哪一阶段就有了答案。

  1. 语义解析。结合语义类型与原始数据确定字段性质，解析方式、比例尺种类、格式和聚合函数在这里产生。
  2. 优化。以约束方式求解布局。坐标轴长度、条目步长、留白、分面配置，都是在数据基数与画布上限的共同约束下决定的。
  3. 代码生成。把与库无关的属性集合按后端模板打出去：Vega-Lite、ECharts、Chart.js、Plotly，以及通过Office.js生成的Excel原生图表。

第二阶段是这套设计里最少被讨论的部分。论文把每条坐标轴、每个分组、每块分面面板都视作「可压缩的容器」，设定期望尺寸和最小可读阈值：离散布局通过伸缩条目来满足约束，连续布局通过拉伸画布来降低重叠。在全局层面则用倾角四十五度的原则调整纵横比，并平衡分面换行。

关键在这里。七十二个月的坐标轴之所以不压盖，不是因为模型恰好选中了504像素的画布宽度，而是因为优化器从最小可读宽度反推了出来。模型不需要知道那个数字。反过来说，当我们自己想定那个数字时该如何介入，就成了下一节的主题。

后端有多个这一点，在实务中比听上去更重要。同一份规范在网页上作为ECharts输出、在交付报告时作为Excel原生图表输出，意味着「给您截图还是给源文件」这种每次都要来一遍的拉扯消失了。Excel那侧生成的是可编辑的原生图表，不是图片。

6. 能局部修改的规范 - 这才是真正的分水岭

这是本文的核心主张。在LLM工作流里，规范设计的价值不来自「首次生成质量」，而来自「第二条指令落在哪里」。

理由很简单：没有一次对话能一轮做完一张图。真实对话是这样走的。

  • 「改成按月」 - 时间单位变更
  • 「y轴从0开始」 - 比例尺基准
  • 「图例挪到下面」 - 布局位置
  • 「只突出这个地区」 - 颜色通道条件
  • 「横过来放」 - 通道互换

在低层语法里，这五条各自会同时触碰规范的两三个不同位置。光是「y轴从0开始」就会一起牵动比例尺定义域、坐标轴刻度配置，有时还有画布高度。模型无法把它当作局部编辑处理，只能整体重写。一重写，此前四次修改就会按概率丢失。

区分使用者与模型直接写的编译器决定的
字段语义类型、固定取值范围、基准值解析规则、比例尺种类、格式、排序
图表图表种类、通道绑定、聚合函数标记属性、坐标轴刻度、图例构成
布局基准尺寸轴长、步长、留白、分面排布、纵横比
配色（通过语义类型间接影响）配色系、定义域映射、中性值位置

左列就是修改表面积。表面积小，「只改这个」才能落到一行上，其余原封不动。论文给出的规范长度比后端原生代码平均短百分之八十五，讲的不是省空间，而是在测量这块表面积的大小。

但削掉多少，失去的也恰好在同一处。右列同时也意味着我们碰不到的那一列。

7. 交出控制权的代价

自动决策不是免费的。实务中的账单以三种形态到来。

7.1 默认值与意图不符时

编译器判定某字段是比例，于是从0到100，可你实际要展示的是92到98之间的细微差别。这种诉求不是错的，它来自上下文。规范的模式里确实有编码层面的覆写项，也有直接指定取值范围和基准值的可选字段，但覆写开放到什么程度，文档写得很薄。在这里卡住，就只能把编译结果取出来手工修改，而那一刻局部修改的优势就消失了。

7.2 呈现本身就是需求时

在设计系统把色值、字号和栅格间距钉成规范的组织里，自动决策本身就是违规。「你看着弄好看点」在这里不是价值而是成本。这类团队继续用低层语法才对。像把字体轴直接绑到数据上的可变字体可视化实验那样、呈现本身就是主题的工作，也属于同一侧。

7.3 类型推断出错时

整套设计都站在「字段会被贴上正确语义类型」这个前提上。可贴这个类型的，说到底还是模型。一个叫score的列，是评分、是测量值还是排名，光看列名分不出来。贴错了，故障并不会消失，只是上移了一层。

不过这个上移本身有价值。八个低层参数失准的状态很难定位原因，而「这个列的类型错了」是一行能定位、一行能修好的。不是减少失败的数量，而是把失败收拢成可诊断的形状——这才是中间语言设计真正在卖的东西。

论文自己也写明，它假设字段与语义类型一一对应，而对含义模糊的字段这个假设并不充分。

8. 数字该怎么读 - 41%到45%胜率意味着什么

评测结果是公开的，照原样搬过来是这样。从TidyTuesday 2025数据集的六十三张表（行数中位数952，列8）出发，查询生成智能体造出三百一十五个查询，Flint路径与后端直接生成路径各自出图，再由视觉语言模型给渲染结果打分。评分项为相关性、图表错误、清晰度、设计质量四项，各5分，合计20分。

模型Flint胜平局直接生成胜显著性水平平均分（满分20）
GPT-5.1129 (41%)65 (21%)118 (38%)0.0516.27 对 15.91
GPT-5-mini140 (45%)65 (21%)106 (34%)0.00116.16 对 15.60
GPT-4.1135 (43%)70 (23%)106 (34%)0.00415.91 对 15.34

怎么读这张表，决定了引入与否。三点。

  • 差异存在，但很小。平均分差在满分20下是0.36到0.57分，折合百分之二到四。「图表质量出现飞跃」这种说法，这些数字撑不住。
  • 模型越强，差距越窄。GPT-5.1的显著性水平最弱（0.05），胜负也最接近（129对118）；而GPT-5-mini与GPT-4.1分别是0.001和0.004，相当明确。模型越好，中间语言带来的质量收益越小，这样读最自然。
  • 最稳固的数字是长度，不是质量。短百分之八十五这件事与模型能力无关，并且直接连着令牌成本和局部修改的可能性。

所以把它当作「获得更漂亮图表的方法」引入，期待一定会落空。当作「用五分之一长度的定义维持同等质量，并让这份定义成为人能打开修改的东西」来引入，数字和期待才对得上。

测量方式本身也有边界。评分者是视觉语言模型，因此模型偏好的图与人觉得有用的图之间的岔口，这个分数抓不到。「看得见」与「弄得懂」是两个问题，这在观测工具领域是反复出现的格局。

9. 没能确认的事

以下是公开资料里没有答案的条目。若要评估引入，这份清单就是你的前置验证项。

  • 中日韩标签的宽度计算。布局优化以最小可读宽度为前提，但这些文字的实际宽度如何取值没有确认到。同样字数下它们比拉丁字母宽。
  • 本地化数字格式。万、亿这类单位缩写和货币符号，是标准语义类型已覆盖，还是必须通过覆写补上。
  • 覆写的开放范围。模式中存在编码层面的覆写项可以确认，但哪些属性开放、哪些封闭的清单没有确认到。
  • 语义类型推断的准确率。最终图表质量被评测过，但类型推断这一步本身的准确率没有单独的数字。
  • 无障碍默认值。自动选择的配色是否满足色觉障碍对比标准，采用的是哪一套标准。
  • 编译开销。约束优化在高基数下要花多久，这个延迟能否放进服务端渲染流水线。
  • 人工评测。自动评分结果已公开，但采用人类评审员的独立结果没有找到。
  • 生产案例。首次发布是2026年7月，尚无公开的生产环境落地案例。

10. 引入判断 - 何时用，何时留在既有语法

版本是0.4.0，首个版本发布于2026年7月。要把「尚未到1.0」作为判断的前提。接口会变，一变就得重写规范。许可证是MIT，这一侧没有约束。

情形判断理由
智能体或聊天机器人生成图表、人在后面修改用局部修改表面积小，本身就是价值
同一指标既要上网页又要出Excel用单一规范产出各后端的原生结果
希望把图表定义纳入代码评审用六十行JSON评审不动，十行可以
已有指标字典，字段含义稳定用语义类型映射一次做完
刷选、缩放、联动筛选是硬需求不用论文明确交互目前不是一等目标
多图层与注释是核心不用同样理由，属于范围之外
设计系统的像素规格属于合同条款不用自动决策在这里是成本而非价值
数据流水线以Python为主暂缓Python包仍是源码预览阶段
只做一两张图的一次性任务不用加依赖的成本大于收益

要试的话，顺序这样排更好。

  1. 挑一张实际在用的表。带有类似日期的整数键的表最能把差异放大。
  2. 和现有语法产出的规范并排放，数行数和令牌数。
  3. 连发五条「只改这个」，看到第几条时先前的修改开始丢失。这才是真正的判断依据。
  4. 确认公司常用的格式是否已在标准语义类型里，或者是否可以用覆写解决。
  5. 包用npm install flint-chart装，智能体环境里用npx -y flint-chart-mcp接上MCP服务。

结论：规范设计替代模型能力的那一段区间

归拢起来是这样。把图表交给LLM时，出错的位置是固定的，而其中相当一部分发生在把模型早已知道的东西翻译成低层参数的过程里。语义驱动的规范把这段翻译搬进了编译器。你得到的是简短的定义和支持局部修改的表面积，失去的是对自动决定值的直接控制权。

数字说的也很清楚。质量提升真实存在但幅度不大，而且模型越强越小。相反，规范缩到五分之一这件事与模型无关。因此这条路线的寿命分成「模型变好后会变得多余的部分」和「模型变好后依然留下的部分」。前者是质量校正，后者是可编辑的表示。

用今天就能落地的三件事收尾。

  • 先在你现在用的提示词里写清字段含义。不必换工具。「Period是YYYYMM整数，Users是可加计数，Ratio是比例因此禁止堆叠」这一行，就能挡掉相当一部分坐标轴类型误判和非可加堆叠。
  • 连发五条图表修改指令试试。你现在的流水线在第几条上丢掉先前的修改，那就是可改进空间的大小。
  • 把「弄好看点」从需求里分离出来。能否使用自动决策就在这里分岔。呈现若是合同，自动化就是成本。
