界面找不到哪一格填错了 - 给校验错误加上字段路径

亲手实现并运行点号表示法、JSON Pointer 与方括号：转义、数组下标，以及表示法为何是契约

2026-08-01 开发/基础设施

引子：红框画到了整张表单上

提交订单后，服务端连同 422 返回了一句「输入不合法」。界面拿这句话决定不了该做什么，最后给十四个输入框全部加上了红框。用户连同八个完全没问题的格子一起重新检查一遍。服务端明明知道恰好有六处出错，而这个信息没能穿过响应。

把这种情况总结成「错误提示不够友好」就抓错了重点。友好是次要的。核心在于真正消费校验错误响应的是界面，不是人。用户从不阅读响应体。阅读它的是代码，而这段代码只有一件事要做：决定把标记加到哪个输入元素上。

要让这个决定成为可能，每条错误都必须带着一个「在哪」。而这个「在哪」不能是人读的句子，必须是界面能拿去和自己的输入元素比对的机器坐标。表示法的问题从这里开始。同一个位置可以写成 items.2.qty，也可以写成 /items/2/qty，还可以写成 items[2].qty。在人眼里三者读起来一样。可对解析代码来说它们是三样不同的东西，而在某些字段名面前，三者中有两个会悄悄崩塌。

本文讨论的就是这个位置。我亲手实现了一个结构校验器，把嵌套三层且混有数组的请求送进去，将得到的错误用三种表示法打印出来，再解析回去和原始分段比对。转义崩溃的地方、数组下标错位导致红框画到别的格子上的地方、把字段名塞进提示语后翻译崩掉的地方，全部通过运行确认。先说结论：表示法不是品味问题，而是契约。

运行环境。以下所有输出都是在 Windows 10 Pro (10.0.19045) 上实际执行的结果。运行时为 Node.js v22.16.0 (win32)，shell 为 GNU bash 5.2.37 (MSYS2/MinGW64)。校验器和实验脚本全部保存为文件后执行，只在仓库之外的临时工作目录里运行。用 heredoc 传代码会让引号和反斜杠悄悄变形。

例子全是虚构的。文中出现的订单 API、字段名、商品编码、条目标识符都是为讲解而编造的。本文不挑选也不评价任何校验库。这里用的校验器是为凸显论点而自写的 200 行玩具，本文的前提是无论用什么工具，不会改变的是响应的形状。

本文不涉及的内容。错误码本身如何命名、如何扩充，在设计一套错误码里讲过。这里假定错误码已经存在，只专注于「在哪」。列表响应的坐标问题，也就是翻页时条目错位的话题，在偏移量分页在结构上做不到的事里。

1. 复现 - 一句「输入不合法」给界面留下了什么

首先要把问题变成数字。我构造了一个嵌套三层、数组套两重的订单请求体，送进自写的校验器。这个请求体里刻意埋了六处问题。

node v22.16.0 / win32

--- 1-1. the request body (3 levels deep, arrays inside arrays) ---
{
 "orderId": "ORD-12",
 "customer": {
  "name": "",
  "contact": {
   "email": "no-at-sign",
   "phone": "010-1234-5678"

--- 1-2. response style A: one sentence, no location ---

36 字节的响应在带宽上堪称完美。可是界面能指向的输入框是 0 个。界面只剩两个选项：什么都不标，或者全部标上。全部标上会把精确率压到 0.43，八个无辜的格子被连坐指责。用户要逐个检查这八个格子，把时间花在上面。

给同样这六处失败加上位置，界面的行为就完全变了。

--- 1-3. response style B: same failures, each carrying a location ---
{
 "ok": false,
 "error": "validation_failed",
 "errors": [
  { "path": "orderId",                 "rule": "pattern" },

  { "path": "customer.contact.email",  "rule": "pattern" },

--- 1-4. does the path actually point at a real place in the body? ---
  orderId                    resolves = true   depth = 1
  customer.name              resolves = true   depth = 2
  customer.contact.email     resolves = true   depth = 3
  items.2.sku                resolves = true   depth = 3
  items.2.qty                resolves = true   depth = 3
  items.2.options.0.value    resolves = false   depth = 5

响应从 36 字节涨到 313 字节。多出的 277 字节买到的是精确率从 0.43 到 1.00，以及误报从 8 条到 0 条。和用户一次往返所消耗的资源相比，这笔账根本不需要算。

1-4 里有一个值得留意的地方。items.2.options.0.value 从请求体里取值会得到 undefined，因为这个必填字段压根不存在。也就是说即使路径指向的地方没有值，路径本身依然有效。路径不是值的地址，而是位置的地址。忽略这个区别，客户端就会造出「在请求体里找不到的路径就丢掉」这种规则，从而整批吞掉必填缺失类错误。

  • 服务端早就知道失败的规则和位置。问题不在计算，而在传递
  • 没有路径时界面能做的最好选择是全部标出，从可用性上讲这几乎等同于什么都不标
  • 深度为 5 的路径确实会出现。数组里的对象里的数组里的对象不是什么奇特结构，就是一张普通订单表
  • 校验器把失败收集为分段数组而不是字符串。打印被推迟到最后一步，因此更换表示法不需要改动校验逻辑

2. 同一条错误的三种表示法

把分段数组变成字符串的方式大致有三种。我把同样这六处失败同时用三种方式打印了出来。

--- 2-1. the same six failures, printed three ways ---
rule       dot                      json pointer               bracket
------------------------------------------------------------------------------------------------
pattern    orderId                  /orderId                   orderId
minLength  customer.name            /customer/name             customer.name
pattern    customer.contact.email   /customer/contact/email    customer.contact.email
minLength  items.2.sku              /items/2/sku               items[2].sku
min        items.2.qty              /items/2/qty               items[2].qty
required   items.2.options.0.value  /items/2/options/0/value   items[2].options[0].value

--- 2-2. size of the whole response in each notation ---
  dot      302 B    longest path = 23
  pointer  308 B    longest path = 24
  bracket  306 B    longest path = 25

--- 2-3. how much code does the CLIENT need to read it back ---
  dot      chars 154   needs a tokenizer loop: no
  pointer  chars 302   needs a tokenizer loop: no
  bracket  chars 472   needs a tokenizer loop: yes

体积差异可以忽略：整份响应差 6 字节，不到百分之二。有意义的差别在解析这一侧。点号表示法的解析器一行 split 就结束，JSON Pointer 的解析器多两次还原转义的替换。只有方括号表示法需要逐字符扫描的分词循环，因为遇到左括号要去找配对的右括号，点号与括号交界的位置还得自己处理。

在普通路径上三者都没问题。打印后再解析回来与原始分段比对，全部通过。

--- 2-4. round trip on the ordinary paths: print then parse then compare ---
segments                        dot     pointer  bracket
------------------------------------------------------------
["orderId"]                     true    true     true
["customer","name"]             true    true     true
["customer","contact","email"]  true    true     true
["items",2,"sku"]               true    true     true
["items",2,"qty"]               true    true     true
["items",2,"options",0,"value"] true    true     true

--- 2-5. same path, resolved against the body through each notation ---
  dot      items.2.qty          -> ["items",2,"qty"] -> value 0
  pointer  /items/2/qty         -> ["items",2,"qty"] -> value 0
  bracket  items[2].qty         -> ["items",2,"qty"] -> value 0

--- 2-6. is the notation self describing? a lone path with no schema at hand ---
  dot      items.2.options.0.value    array steps are invisible, 2 could be a key
  pointer  /items/2/options/0/value   array steps are invisible, 2 could be a key
  bracket  items[2].options[0].value  array steps are marked by brackets

  none of the three can prove 2 is an index without the schema;
  bracket only records what the SERVER believed when it printed.

2-6 澄清了一个常见的误解。方括号表示法确实有数组层级可见这个优点。人工读日志时，items[2] 比 items.2 理解得更快。可这个信息只是服务端打印时自己如此相信的一份记录而已。客户端无法凭这个标记去反向确认那一步确实是数组。数字究竟是下标还是键，最终判断永远归结构定义所有，表示法不会替你做这个判断。

3. 转义陷阱 - 当名字里含有点号、斜杠或方括号

这里才是表示法选择真正分野的地方。JSON 对象的键几乎什么字符都能放，而实际业务的请求体里这类键很常见：以版本字符串为键的配置映射、直接以头部名称为键的字典、用户输入的标签名、以年份为键的汇总结果等等。我造了九个案例，用三种表示法打印后再解析回去。

--- 3-1. print each key with all three notations ---
case                        dot                       pointer                     bracket
--------------------------------------------------------------------------------------------------------
plain key                   meta.source               /meta/source                meta.source
dot in key                  meta.app.version          /meta/app.version           meta.app.version
slash in key                headers.x-forwarded/for    /headers/x-forwarded~1for   headers.x-forwarded/for
bracket in key              tags.group[a]             /tags/group[a]              tags.group[a]
tilde in key                tags.draft~2              /tags/draft~02              tags.draft~2
digits as key               byYear.2024.total         /byYear/2024/total          byYear.2024.total
empty key                   tags.                     /tags/                      tags.
dot plus index              rows.3.unit.price         /rows/3/unit.price          rows[3].unit.price
key that looks like a path  fields.items.0.qty        /fields/items.0.qty         fields.items.0.qty

--- 3-2. now parse them back and compare with the original segments ---
case                        dot     pointer  bracket
--------------------------------------------------------
plain key                   true    true     true
dot in key                  false   true     false
slash in key                true    true     true
bracket in key              true    true     false
tilde in key                true    true     true

点号 5 例、方括号 4 例、JSON Pointer 8 例。差距的根源不是能力，而是有没有规则。点号和方括号根本没有规定分隔符出现在名字内部时该如何书写。于是信息在打印阶段就消失了，解析阶段再没有还原的办法。

看看崩塌时客户端实际拿到了什么，严重性就一目了然。

--- 3-3. what the client actually receives when a notation collapses ---
  dot in key
    server meant : ["meta","app.version"]
    printed as   : meta.app.version
    client reads : ["meta","app","version"]
    segments     : 2 -> 3
  digits as key
    server meant : ["byYear","2024","total"]
    printed as   : byYear.2024.total
    client reads : ["byYear",2024,"total"]
    segments     : 3 -> 3
  dot plus index
    server meant : ["rows",3,"unit.price"]
    printed as   : rows.3.unit.price
    client reads : ["rows",3,"unit","price"]
    segments     : 3 -> 4
  key that looks like a path
    server meant : ["fields","items.0.qty"]
    printed as   : fields.items.0.qty
    client reads : ["fields","items",0,"qty"]
    segments     : 2 -> 4

--- 3-4. bracket notation on a key that contains a bracket ---
  server meant : ["tags","group[a]"]
  printed as   : tags.group[a]
  client reads : ["tags","group",null]
  the printer has no escape rule for ] at all, so the string is not recoverable

分段数从 2 涨到 4 的那个案例最糟。客户端连自己读错了这件事都无从知晓。fields.items.0.qty 看上去是一条语法完美的路径，解析成功，也不抛异常。它只是指向一个不存在的位置而已。3-4 的方括号案例更露骨：解析器碰到名字内部的右括号，吐出了一个 null 分段。因为打印器根本没有转义规则，这个字符串本身就变得无法还原。

JSON Pointer 在这里表现不同，因为规则写进了文档。

--- 3-5. the only notation with a written escape rule ---
  key "x-forwarded/for"    pointer /headers/x-forwarded~1for  back "x-forwarded/for"    equal true
  key "draft~2"            pointer /tags/draft~02             back "draft~2"            equal true
  key "a~/b"               pointer /tags/a~0~1b               back "a~/b"               equal true

--- 3-6. and the one it still cannot settle by itself ---
  object with a numeric KEY : {"byYear":{"2024":{"total":0}}}
  pointer                   : /byYear/2024/total
  parsed with number guess  : ["byYear",2024,"total"]
  parsed as pure strings    : ["byYear","2024","total"]
  RFC 6901 says: try the string key first, treat it as an index only for arrays.
  a client that guesses by shape alone will mislabel numeric object keys.

斜杠变成 ~1，波浪号变成 ~0。第三行体现了规则的精细：a~/b 变成 a~0~1b 并且准确地还原了回来。还原时顺序很重要。先把 ~1 换回斜杠，然后再把 ~0 换回波浪号。顺序颠倒，遇到 ~01 这样的输入结果就不同。这正是 RFC 6901 要明确这个顺序的原因。

即便如此，JSON Pointer 单靠自己仍然解决不了一件事：数字形式的对象键。在以年份为键的汇总对象里收到 /byYear/2024/total 的客户端，如果判断「长得像数字所以是下标」就错了。RFC 6901 的规定很明确：目标是对象时把这个字符串当成成员名，只有目标是数组时才解释为下标。也就是说判断依据不是字符串的长相，而是那个位置上值的类型。

4. 数组下标的寿命 - 当一个条目消失

解决了转义，数组还剩另一类问题：下标是只对请求发出那一刻的数组状态有效的坐标。我构造了四行购物车，在第三行埋了问题，复现了响应在路上时用户删除第二行的场景。

--- 4-1. the cart as sent, and the errors that came back ---
  [0] ln_7742  sku="SKU-A1"  qty=2
  [1] ln_9310  sku="SKU-B7"  qty=1
  [2] ln_5518  sku=""        qty=0
  [3] ln_2064  sku="SKU-D3"  qty=5

  items.2.sku     rule=required  lineId=ln_5518
  items.2.qty     rule=min       lineId=ln_5518

--- 4-2. the user removes row 1 while the response is in flight ---
  [0] ln_7742  sku="SKU-A1"  qty=2
  [1] ln_5518  sku=""        qty=0
  [2] ln_2064  sku="SKU-D3"  qty=5

--- 4-3. apply the index paths to the cart as it is NOW ---
path from server  index  row now at that index correct row
----------------------------------------------------------------------
items.2.sku       2      ln_2064 (SKU-D3)      NO  should be ln_5518
items.2.qty       2      ln_2064 (SKU-D3)      NO  should be ln_5518

  misplaced marks : 2 of 2

--- 4-4. what the screen shows after the shift ---
  items.2.sku       -> marks ln_2064.sku     value "SKU-D3"  a red line on a VALID field
  items.2.qty       -> marks ln_2064.qty     value 5         a red line on a VALID field

两条错误全都落到了别的行上。而落点上的值是 SKU-D3 和 5，完全正常。从用户角度发生的事情是：没问题的那一行被标红，真正出错的那一行毫无标记。用户把正常的值删掉重填、反复提交，服务端每次都返回同样的错误。在这种状态下用户没有办法弄清原因。

这看起来像时序事故，其实不是。根因是下标不携带身份。给每个条目配一个客户端生成的唯一标识符随请求发出，服务端再把它回填到错误里，问题就消失了。

--- 4-5. same errors carried by a stable id instead ---
  ln_5518.sku       row still present, mark it
  ln_5518.qty       row still present, mark it
  misplaced marks : 0 of 2

--- 4-6. the response that carries both ---
{
 "error": "validation_failed",
 "errors": [
  {
   "path": "items.2.sku",
   "keyPath": "items[lineId=ln_5518].sku",
   "rule": "required"
  },
  {
   "path": "items.2.qty",
   "keyPath": "items[lineId=ln_5518].qty",
   "rule": "min"
  }
 ]
}

  bytes index only  : 117
  bytes both        : 193

--- 4-7. does the server even know the client id? only if the client sent it ---
  body the client sent : {"sku":"","qty":0}
  fields the server can echo back : sku, qty
  stable handle available : no
  so the id has to be part of the REQUEST schema, not invented in the response.

换成稳定标识符后，错位从 2 条降到 0 条。如果条目已被删除，那这条错误无处可挂就变得一目了然，于是悄悄丢弃也是安全的。下标做不出这个判断。下标永远指向「某个人」，而无从知晓那个人是不是原来的目标。

4-7 是最常被忽略的前提。服务端无法回填客户端没有发送过的标识符。请求体里只有 sku 和 qty，服务端能回显的也就只有这两个。也就是说，稳定标识符不是响应设计的问题，而是请求结构设计的问题。决定把它放进错误响应的那一刻，请求侧的契约也随之改变。

  • 下标路径不要丢掉，一起发送。在日志和服务端调试里下标依然更方便
  • 同时携带两种坐标会让响应从 117 字节涨到 193 字节，每条错误 38 字节
  • 标识符可以是服务端生成的，也可以是客户端造的临时值。只要在请求与响应之间不变就行
  • 客户端新增条目时会出现同样的问题。这不是只要小心删除就够了的问题
  • 如果界面允许用户拖动排序，那下标从一开始就不能用

5. 在第一条错误处停下，还是全部收集

决定加上位置之后，下一个决定是数量。第一处失败就立刻返回，还是全部收集起来一次给出。我把同一个请求体用两种方式处理了一遍：面对只返回第一条错误的服务端，让用户只修改被指出的那一格，把这个过程原样跑了一遍。

--- 5-1. stop at the first failure: how many round trips to a clean form ---
  trip 1  server says: orderId                   (pattern)
  trip 2  server says: customer.name             (minLength)
  trip 3  server says: customer.contact.email    (pattern)
  trip 4  server says: items.2.sku               (minLength)
  trip 5  server says: items.2.qty               (min)
  trip 6  server says: items.2.options.0.value   (required)
  total round trips : 6

--- 5-2. collect everything: one round trip ---
  errors returned   : 6
  total round trips : 1

--- 5-3. three response shapes for the same six failures ---
  flat path list      302 B    client walk = one loop
  plus params         459 B    client walk = one loop
  plus english text   859 B    client walk = one loop
  nested tree         217 B    client walk = recursive

  the nested tree, printed:
{"orderId":["pattern"],"customer":{"name":["minLength"],"contact":{"email":["pattern"]}},"items":{"2":{"sku":["minLength"],"qty":["min"],"options":{"0":{"value":["required"]}}}}}
  note: to find a leaf the client must recurse, and array levels look like objects.

六次对一次。从用户角度这是六次提交和六次等待。这是表单越长流失率越高的典型形态，从服务端看请求量也是六倍。只要校验没有副作用，收集起来一次给出几乎总是更好。

5-3 里的嵌套树形式是个有意思的陷阱。217 字节最小，结构乍看也漂亮。可是数组层级看起来像对象。"items":{"2":{...}} 里的 2 明明是下标，却被序列化成了键。第 3 节的数字键问题在这里原样重演。加上客户端为了找到叶子还得递归。扁平列表在体积上稍吃亏，换来的是一个循环就结束。

决定收集起来给出之后，就要确认体积会长到多大。

--- 5-4. how big does collect-all get on a bulk request ---
  items   errors  flat B    with params B  with text B
  ------------------------------------------------------
  1       2       118       172            296
  10      20      820       1360           2600
  100     200     8020      13420          26000
  1000    2000    81820     135820         263600

--- 5-5. capping the list, and saying so ---
  total failures     : 2000
  returned           : 50
  truncated flag     : true
  bytes uncapped     : 81820
  bytes capped       : 2056
  without the flag the screen believes it has the whole list and clears the rest.

--- 5-6. two failures on ONE field: does the list keep both ---
  orderId       minLength {"min":10,"got":1}
  orderId       pattern   {"hint":"ORD-000000"}
  items.0.qty   max       {"max":99,"got":500}
  grouped by path : {"orderId":["minLength","pattern"],"items.0.qty":["max"]}
  a map keyed by path (path -> one message) would silently drop the loser.

一千个条目的批量请求会产生两千条错误，再加上供人阅读的句子，响应会达到 263 千字节。界面反正也只显示前面几条。所以设上限是对的，但必须告知你截断过。不知道列表被截断的界面会判断「列表里没有所以已经解决了」，从而清掉剩下的标记。

5-6 给出了选择响应形态的一个决定性理由：同一个字段上可能同时有两条规则失败。这里 orderId 既长度不够、格式也不对。如果把错误做成以路径为键的映射，后来的会覆盖先前的，于是丢掉一条。用户改完长度重新提交，这时才被告知格式错误。这就是必须用列表而不是映射的理由。

6. 把人读的文案和机器读的路径分开

这里会冒出一个常见的折中方案：「把字段名放进提示语，用户能看懂、界面也能比对，不是挺好？」实际运行一下，两个期待都会落空。

--- 6-1. the server bakes the label into the sentence, one language only ---
  response : [{"message":"Quantity must be at least 1."}]

  a screen in another language now has three bad options:
    1. show the English sentence to a non English reader
    2. translate the sentence at runtime, per request
    3. match the sentence text to decide which box to mark

--- 6-2. option 3 in practice: matching on the sentence ---
  screen locale en   label on screen Quantity     found in the sentence: true
  screen locale de   label on screen Menge        found in the sentence: false
  screen locale es   label on screen Cantidad     found in the sentence: false
  screen locale pt   label on screen Quantidade   found in the sentence: false
  labels matched : 1 of 4
  the only locale that matches is the one the server happened to be written in.

--- 6-3. the same sentence after a harmless copy edit on the server ---
  before : Quantity must be at least 1.   -> client match on "Quantity" = true
  after  : The quantity must be at least 1.   -> client match on "Quantity" = false
  a wording change is a breaking change once the screen parses the wording.

四个语言环境里只有一个比对成功，而这一个正是写服务端代码那个人的语言。剩下三个都在句子里找不到自己界面上的字段名。可更危险的是 6-3：仅仅在句首加一个冠词这种微小改动，比对就立刻失败了。界面开始解析文案的那一刻，改文案就等于破坏兼容性。而且这种破坏任何测试都抓不到，因为在服务端那边只是润色了一句话而已。

解法是拆开。位置、规则码和参数由服务端给，供人阅读的句子由界面造。

--- 6-4. split it: path and rule stay, wording moves to the client ---
{"error":"validation_failed","errors":[{"path":"orderId","rule":"pattern","params":{"hint":"ORD-000000"}},{"path":"customer.name","rule":"minLength","params":{"min":1,"got":0}},{"path":"customer.contact.email","rule":"pattern","params":{"hint":"name at host"}},{"path":"items.2.sku","rule":"minLength","params":{"min":1,"got":0}},{"path":"items.2.qty","rule":"min","params":{"min":1,"got":0}},{"path":"items.2.options.0.value","rule":"required","params":{}}]}

  bytes : 459

--- 6-5. one response, rendered by four screens ---
  path                      locale  what the user reads
  ------------------------------------------------------------------------------
  items.2.qty               en      Quantity must be at least 1.
  items.2.qty               de      Menge muss mindestens 1 betragen.
  items.2.qty               es      El campo Cantidad debe ser al menos 1.
  items.2.qty               pt      O campo Quantidade deve ser no minimo 1.
  items.2.options.0.value   en      Option value is required.
  items.2.options.0.value   de      Optionswert wird benoetigt.
  items.2.options.0.value   es      El campo Valor de opcion es obligatorio.
  items.2.options.0.value   pt      O campo Valor da opcao e obrigatorio.

--- 6-6. sentence length across the four, same path every time ---
  en   chars 28   Quantity must be at least 1.
  de   chars 33   Menge muss mindestens 1 betragen.
  es   chars 38   El campo Cantidad debe ser al menos 1.
  pt   chars 40   O campo Quantidade deve ser no minimo 1.
  path is 11 chars in all four : items.2.qty

--- 6-7. the fallback the server still owes you ---
  rule from server : skuBlockedForRegion
  client knows it  : false
  with no fallback : the box is marked red with an empty tooltip
  with a fallback  : the server also ships a plain default sentence
  {"path":"items.0.sku","rule":"skuBlockedForRegion","params":{"region":"KR"},"message":"This item cannot be shipped to the selected region."}
  the message is a LAST RESORT for unknown rules, never the thing the screen parses.

6-6 就是这一节的总结。句子从 28 个字符到 40 个字符参差不齐，而路径四次都是 11 个字符。文案因语言而异、随时间变化，而路径只要结构不变就不动。把会变的和不会变的混进同一个字符串，不该变的那一半就会被会变的那一半拖着走。

不过完全去掉句子也不是答案，6-7 说明了原因。服务端新增了一个规则码，而界面的文案词典里还没有这个码时，就会出现格子被涂红、说明却是空白的状态。所以服务端必须附上面向未知规则的默认句子。关键是这句话的定位：它是最后手段，不是界面拿去解析的对象。界面认识的规则就用自己的文案，只有不认识时才原样展示服务端的句子。

  • 服务端生产三样东西：路径、规则码、参数。参数原样携带要嵌进句子的数值和提示
  • 界面生产两样：字段名和句子。字段名词典的键是去掉下标后的路径，因此整个数组的条目共用一条
  • 规则码必须稳定。改规则码名字，和改路径是同等分量的变更
  • 服务端的默认句子一种语言就够了。反正界面认识的规则用不上它
  • 让翻译文件里缺失的规则码留下警告，服务端新增规则这件事就不会在发布后悄悄埋没

7. 界面把路径绑定到输入元素的代码

最后一块拼图。响应做得再好，界面如果不能把路径绑定到自己的输入元素，什么也不会发生。我搭了一个有 14 个输入元素和 6 个区域容器的界面，把响应原样送了进去。

--- 7-1. the widgets this screen actually has ---

  customer.name
  customer.contact.email
  customer.contact.phone
  items.0.sku

  items.1.sku

绑定本身很简单：把输入元素的 name 属性设成和路径一样，一次查询就完事。关键是不要手写这些名字。构造请求体的代码和构造输入元素名字的代码如果不共用同一个函数，两者必然错位，数组下标尤其如此。

  ["customer","contact","email"]  <input name="customer.contact.email">
  ["items",2,"qty"]               <input name="items.2.qty">
  ["items",2,"options",0,"value"] <input name="items.2.options.0.value">

  the row index in the widget name has to come from the same counter the
  request body was built with, or the two drift apart on the first insert.

真正的问题在 7-2。响应里的六条路径中，有三条在这个界面上没有对应的输入元素。原因各不相同：billing.taxId 是这一步界面里压根没有的字段，items.9.sku 是界面上不存在的第九个条目，而空路径指的是整个请求体，属于跨字段错误。这不是例外情况，而是常态。服务端和界面不会以同样的速度发布。

8. 遇到界面不认识的路径时

有三个选项：丢掉、提升到顶部横幅、或者沿路径向前截断去寻找上级区域再挂上去。我把三种策略应用到同一份响应上。

--- 7-3. three policies for the paths with no widget ---
  policy ignore   marked=3   promoted=0   banner=1   dropped=2
    banner lines : ["This combination is not allowed."]
  policy banner   marked=3   promoted=0   banner=3   dropped=0
    banner lines : ["Required. (billing.taxId)","Required. (items.9.sku)","This combination is not allowed."]
  policy prefix   marked=3   promoted=1   banner=2   dropped=0
    banner lines : ["Required. (billing.taxId)","This combination is not allowed."]

--- 7-4. what the user sees under each policy, field by field ---
  ignore   3 marked
      customer.name [Too short.]
      items.2.qty [Too small.]
      items.2.options.0.value [Required.]
  banner   3 marked
      customer.name [Too short.]

      items.2.qty [Too small.]
      items.2.options.0.value [Required.]
      items (container) [Required.]

--- 7-5. the failure mode of ignore ---
  http status the client saw : 422
  errors in the body         : 6
  errors shown anywhere      : 4
  errors silently dropped    : 2
  result: the submit button fails, and nothing on the page says why.

--- 7-6. the invariant a client should assert ---
  ignore   shown 4 of 6   invariant holds: false
  banner   shown 6 of 6   invariant holds: true
  prefix   shown 6 of 6   invariant holds: true

忽略策略的结果就摆在 7-5 里：提交失败了，而页面上没有任何地方说明原因。用户再按一次按钮，同样的事情重复发生。这就是「校验错误响应明明做好了，客服工单却不见减少」的典型原因。服务端好好地告知了，界面悄悄地丢掉了。

7-6 是这一节的行动项：在界面这一侧立一条不变式。响应里包含的错误条数与页面上某处显示出来的条数必须相等。哪怕只是在开发构建里把它作为警告抛出来，也能在发布前抓住服务端新增字段时界面吞掉错误的事故。

前缀提升策略更体贴一些。对 items.9.sku 先试 items.9，没找到再试 items，结果把标记挂到了整个购物车区域上。用户至少知道该看哪一块。这个策略也有极限：billing.taxId 连上级的 billing 在界面上都不存在，最终还是进了横幅。

策略显示出的错误用户看到的风险

横幅6 条中 6 条顶部原样露出路径内部字段名被用户看到
前缀提升6 条中 6 条相关区域标记、其余进横幅提升范围过宽会引起误解
空路径整个请求体表单顶部的汇总约定不写进文档界面就会无视

9. 用 linter 检查响应结构

我把到目前为止的要求写成规则，对五种响应形态实际跑了一遍。这不是检查请求的校验器，而是检查契约的 linter。

--- 8-1. lint five candidate response shapes against the contract ---
  rule                                      A   B   C   D   E
  --------------------------------------------------------------
  R1 every error carries a path field       no  no  ok  ok  ok
  R2 one notation across the whole body     no  no  no  ok  ok
  R3 machine readable rule code present     no  no  no  ok  ok
  R4 wording is not the only carrier        no  no  no  ok  ok
  R5 params separated from the sentence     no  no  ok  ok  ok
  R6 array rows have a stable handle        no  no  no  no  ok
  R7 whole body errors have a defined path  no  no  ok  ok  ok
  R8 truncation is announced                no  no  ok  ok  ok
  R9 two failures on one field survive      no  no  ok  ok  ok
  --------------------------------------------------------------
  passed                                    0   0   5   8   9

  A sentence only     25 B
  B path keyed map    206 B
  C mixed notations   394 B
  D path plus rule    459 B
  E full contract     978 B

--- 8-2. why the path keyed map (candidate B) loses information ---
  errors in            : 2
  keys in the map      : 1
  map                  : {"orderId":"pattern"}
  the first rule is overwritten and never reaches the screen.

候选 C 只拿到 5 分的原因，恰好说明了这个 linter 存在的意义。C 有路径、体积也小，但在同一份响应里混用了表示法。奇数条错误用 JSON Pointer，偶数条用点号。现实中确实有产生这种响应的路径：框架自带校验器生成的错误和人工写的领域校验错误混在同一个数组里发出去的时候。从界面看，每条错误都得猜表示法，而猜错的那一刻，第 3 节的事故就重演了。

候选 B 是 0 分。以路径为键的映射结构本身就在丢信息，8-2 展示了这一点：放进去两条错误，出来只剩一个键。

字段谁在用没有它会怎样

10. 设计规则与检查清单

把运行确认过的东西整理成规则，一共五条。每条规则背后的依据都是前面的输出。

  • 选定一种表示法并写进文档。只要字段名有一点可能包含特殊字符，就是 JSON Pointer。它是往返测试中 9 例通过 8 例的唯一表示法，转义规则也写在标准文档里
  • 不要在同一份响应里混用表示法。如果框架生成的错误和领域校验错误会进同一个数组，就在发出去之前的某一处统一表示法
  • 数组条目要同时给出下标和稳定标识符。为此标识符必须先存在于请求结构里。这是唯一一条光改响应解决不了的规则
  • 错误用列表返回，不要用映射。同一个字段上可能同时有两条规则失败，而映射会悄悄丢掉其中一条
  • 文案由界面生成，但服务端留一句默认句子。这是界面遇到未知规则码时唯一的安全网

最常被跳过的一项。决定用哪种表示法的会议会开，而决定「遇到不认识的路径怎么办」的会议不会开。可实测中，响应里有一半是界面上没有对应元素的路径。没有这条规则，各个界面就各自处理，而大多数会选择悄悄丢掉。服务端好好告知的错误有三分之一到不了用户手里，就是这样造成的。

检查清单如下。每一项都是前面章节里真的制造过失败的东西。

  • 错误响应的表示法已写进规格文档
  • 用含有点号、斜杠、方括号的字段名样本通过了往返测试
  • 确认过数字形式的对象键不会被误当成下标
  • 数组条目的错误同时携带稳定标识符
  • 这个标识符在请求结构里也有定义
  • 错误是列表，同一个字段上可以挂两条
  • 列表有上限，并且随附截断标志
  • 界面不解析句子
  • 每个规则码在界面侧都有文案条目，缺失时会留下警告
  • 空路径表示整个请求体这一约定写进了文档
  • 界面上有显示条数不变式
  • 输入元素名和请求体路径出自同一个函数
  • 未知路径的处理策略在每个界面上都相同

11. 本文未能验证的部分

  • 真实浏览器里的无障碍衔接。把路径绑定到输入元素这一步验证过了，但这些标记如何传递给辅助技术不在本次实验范围内
  • 嵌套表单组件的状态管理。界面在增删和排序条目时如何让路径与组件状态保持同步，各框架做法不同
  • 部分成功的响应。批量请求只有一部分失败时，如何把成功条目和失败条目装进同一份响应，是另一个设计问题
  • 异步校验。像重复性检查这类需要服务端往返的规则，错误是在输入途中而不是提交时抵达的。那时路径的有效期与本文的数组问题相似但并不相同
  • 真实业务规模下的响应体积。第 5 节的数字来自合成数据，真实的字段名更长，参数也更多

结论：错误响应的接收方不是人，而是界面

从「把校验错误给好一点」出发，结论就会滑向「把提示语写得更友好」。可实际运行确认到的东西指向相反的方向。友好的句子可以在界面上造出来，但哪一格出错只有服务端知道。服务端该发的不是句子，而是坐标。

一旦决定发坐标，表示法的问题就立刻跟了上来。而表示法与外表相反，不属于品味的范畴。字段名里只多一个点号，两个分段就变成了三个，客户端连自己读错了都无从知晓。方括号表示法为名字里的一个右括号吐出了 null 分段。转义规则写在文档里的表示法和没写的表示法，差距体现为往返测试的 5 例对 8 例。

数组是另一个问题。下标没有身份，所以一个条目消失后两条错误全落到了别的行上，形成没问题的格子被标红、真正出错的行毫无标记的状态。换成稳定标识符后降到了 0 条，可为此必须先改请求结构。这不是光改响应就能解决的问题。

所以结论是这样的：表示法是契约。服务端打印时用的规则和界面解析时用的规则必须一致，这条规则必须写在某个地方，并且在同一份响应里不能摇摆。契约立住了，错误响应才开始有价值。

有一件事现在就能确认。打开你手头这个界面里处理校验错误的代码，看看有没有一行在比较响应里的错误条数和页面上实际显示的条数。如果没有，那这个界面很可能正在悄悄丢弃服务端好好告知的错误。而这件事，无论错误响应做得多好都不会暴露出来。

# 校验错误的字段路径 — 可直接粘贴的表示法对照表与响应结构

> 来源: braindetox.kr — 界面找不到哪一格填错了
> 依据: 在 Windows 10 / Node.js 22.16 (win32) / bash 5.2.37 (MSYS2) 上运行自写校验器实测
> 把这个文件原样贴给 AI 并写上「按这个标准检查我们的错误响应」即可。
> 原则: 错误响应的接收方不是人而是界面。只有界面能把路径绑定到输入元素，它才有价值。

## 1. 三种表示法对比 (往返测试实测)

| 项目 | 点号 `items.2.qty` | JSON Pointer `/items/2/qty` | 方括号 `items[2].qty` |
|---|---|---|---|
| 解析器体量 | 154 字符 | 302 字符 | **472 字符** |
| 分词循环 | 不需要 | 不需要 | **需要** |
| 转义规则 | **没有** | 波浪号 `~0` · 斜杠 `~1` | **没有** |
| 数组层级可见 | 不可见 | 不可见 | 可见(服务端主张) |
| 标准文档 | 惯例 | **RFC 6901** | 惯例 |
| 指代整个请求体 | 需要约定 | 空字符串 | 需要约定 |
| 刁钻键 9 例往返 | 5 例 | **8 例** | 4 例 |

**结论: 字段名有可能含特殊字符就用 JSON Pointer。**

## 2. 转义崩溃的位置

| 键里含有的字符 | 点号 | Pointer | 方括号 | 症状 |
|---|---|---|---|---|
| 点号 `app.version` | 崩塌 | 通过 | 崩塌 | 分段 2 → 3 |
| 斜杠 `x-forwarded/for` | 通过 | 通过 | 通过 | 点号碰巧安全 |
| 方括号 `group[a]` | 通过 | 通过 | 崩塌 | 解析器返回 null 分段 |
| 波浪号 `draft~2` | 通过 | 通过 | 通过 | 转义规则准确还原 |
| 数字键 `2024` | 崩塌 | 崩塌 | 通过 | 把键误当成下标 |
| 空字符串键 | 通过 | 通过 | 崩塌 | 分段悄悄消失 |
| 长得像路径的键 | 崩塌 | 通过 | 崩塌 | 2 → 4，指向不存在的位置 |

- 还原顺序要注意: 先 `~1` → 斜杠，然后 `~0` → 波浪号
- 数字键的判断依据不是表示法，而是 **那个位置上值的类型** (对象则为名字，数组则为下标)

## 3. 数组下标的寿命

- 下标是只对 **请求发出那一刻的数组状态** 有效的坐标
- 删掉一个条目，错误就会顺移到下一行 → 没问题的格子被标红，出错的行无标记
- 实测: 错位 2/2 → 换成稳定标识符后 0/2
- **标识符必须先存在于请求结构里。** 客户端没发送的值服务端回填不了
- 新增和排序也会出现同样的问题，不是只小心删除就够了

## 4. 响应结构

```
{
  "error": "validation_failed",
  "truncated": false,
  "totalErrors": 6,
  "errors": [
    {
      "path": "items.2.qty",
      "keyPath": "items[ln_5518].qty",
      "rule": "min",
      "params": { "min": 1, "got": 0 },
      "message": "仅在规则未知时使用的默认句子"
    }
  ]
}
```

| 字段 | 谁在用 | 没有它 |
|---|---|---|
| `path` | 界面与日志 | 无法决定给哪一格上色 |
| `keyPath` | 界面(数组) | 条目错位后标记落到别的行 |
| `rule` | 界面(挑选文案) | 只能解析句子，改文案即破坏 |
| `params` | 界面(组装文案) | 「至少 1」里的 1 进不了句子 |
| `message` | 界面(仅未知规则) | 没有说明的红格子 |
| `truncated` | 界面(列表) | 把截断的列表当成全部 |
| `totalErrors` | 界面与监控 | 无法告知被截掉多少条 |

- **用列表而不是映射。** 同一字段上可能同时有两条规则失败
- 只给第一条错误实测往返 6 次，全部收集只需 1 次
- 1,000 个条目的批量请求 = 2,000 条错误 = 含句子时 263 KB → 上限 + `truncated` 必备

## 5. 客户端映射

```
function applyErrors(resp, form) {
  let shown = 0;
  for (const e of resp.errors) {
    const el = form.querySelector('[name="' + cssEscape(e.path) + '"]');
    if (el) { markField(el, textFor(e.rule, e.params)); shown++; continue; }
    if (e.path === '') { banner(textFor(e.rule, e.params)); shown++; continue; }
    // 未知路径: 截断前缀去寻找上级区域
    const segs = parsePath(e.path);
    let box = null;
    for (let n = segs.length - 1; n > 0; n--) {
      if (box) break;
      box = form.querySelector('[data-scope="' + printPath(segs.slice(0, n)) + '"]');
    }
    if (box) { markScope(box, textFor(e.rule, e.params)); shown++; }
    else { banner(fallbackText(e)); shown++; }
  }
  // 不变式: 响应里的条数与页面上显示的条数必须相等
  if (shown !== resp.errors.length) warnInDev(resp.errors.length - shown);
}
```

| 策略 | 显示 | 用户看到的 | 风险 |
|---|---|---|---|
| 忽略 | 4/6 | 提交失败、没有说明 | **不变式被破坏，禁止设为默认** |
| 横幅 | 6/6 | 顶部露出路径 | 内部字段名被用户看到 |
| 前缀提升 | 6/6 | 相关区域标记 + 其余进横幅 | 提升范围过宽会引起误解 |

## 6. 人读的文案与机器读的路径

- 服务端生产: **路径 · 规则码 · 参数**
- 界面生产: **字段名 · 句子**
- 实测: 靠服务端英文句子定位格子的做法，四个语言环境只成功一个
- 只加一个冠词的文案修改就让比对立刻失败 → **改文案 = 破坏兼容性**
- 句子长度 28~40 字符参差不齐，路径四次都是 11 字符
- 服务端留一句 **面向未知规则的默认句子** (最后手段，不是解析对象)

## 7. 检查清单

- [ ] 错误响应的 **表示法已写进规格文档**
- [ ] 用含点号、斜杠、方括号的字段名通过了 **往返测试**
- [ ] 确认过数字形式的 **对象键** 不会被误当成下标
- [ ] 数组条目的错误同时携带 **稳定标识符**
- [ ] 这个标识符在 **请求结构** 里也有定义
- [ ] 错误是 **列表**，同一字段上可以挂两条
- [ ] 列表有 **上限**，并且随附截断标志
- [ ] 界面 **不解析句子**
- [ ] 每个规则码都有 **文案条目**，缺失时留下警告
- [ ] **空路径** 表示整个请求体这一约定写进了文档
- [ ] 界面上有 **显示条数不变式**
- [ ] 输入元素名与请求体路径出自 **同一个函数**
- [ ] 未知路径的处理策略在 **每个界面上都相同**

## 8. 不要做的事

- ❌ 在同一份响应里 **混用表示法** — 框架错误与领域错误交汇之处
- ❌ 用 **以路径为键的映射** 返回错误 — 同一字段两条规则会丢一条
- ❌ **只用下标** 指向数组错误 — 删除、新增、排序都会让它错位
- ❌ 让界面 **解析服务端句子** — 改文案立刻变成故障
- ❌ **悄悄丢弃** 未知路径 — 提交失败且没有说明
- ❌ **不声不响地截断列表** — 界面会把其余当成已解决
- ❌ **手写输入元素名** — 第一次插入条目就会与请求体路径错开
