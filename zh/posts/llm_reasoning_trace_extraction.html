LLM 隐藏的推理为何会泄露

提供方封印后回传的中间产物到底是什么，以及调用 API 的团队今天该检查什么

2026年8月16日 IT/技术

把隐藏之物交给客户端的设计

凡是把推理模型接进 API 的人，都见过响应里混着的那一团读不懂的东西。名字因提供方而异：有的叫加密推理项，有的叫思维签名，有的干脆叫思考块。共同点有两条：人读不了，而且必须原样送回下一次请求，对话才接得上。

这个设计不是偷懒的结果。请求响应式 API 把不在服务器保留对话状态当作默认或首选项。OpenAI 文档写明，在无状态模式下——store 为假，或组织启用零数据保留（ZDR）——响应中的推理项默认带有 encrypted_content 属性。Google 的 Gemini 文档把思维签名定义为模型内部推理状态的加密表示，并要求无状态使用时把收到的思考块一个不落地原样送回。Anthropic 文档同样要求把思考块不加改动地传入下一轮。

归纳起来是这样：服务器什么都不留，又要在下一轮接续此前的推理，那就只能把中间产物封印后交给客户端再取回。为满足数据最小化要求而做的选择，结果把秘密的物理位置搬到了信任边界之外。Web 安全里被反复讲了很多年的道理在这里重新开始——为什么不能信任客户端在 LLM API 上同样成立。

本文只在原理层面讨论这个结构，不写可复现的步骤，也不给请求格式。要回答的只有三个问题：是什么性质导致信息泄露、提供方能改什么、调用 API 的一方今天能检查什么。

为什么要隐藏推理过程——成本、安全、竞争

隐藏中间推理背后叠着三种不同的动机。先拆开，后面读缓解措施的代价时会容易得多。

  • 竞争。原始思维过程是蒸馏（distillation）的顶级教材。只有最终答案，竞争者能模仿的仅是结果；有了通往答案的路径，用少得多的数据就能迁移推理能力。提供方最想守住的资产在这里。
  • 安全。即使最终回答拒绝了请求，中间过程里也可能留下审视该请求时写下的表述。安全判定通常挂在最终输出上，把中间产物原样暴露，判定点就被绕开了。
  • 产品一致性。未经打磨的推理会误导用户。模型一度考虑又放弃的假设被读成已定结论，这类事故并不罕见。所以多数提供方展示的是摘要而非原文。
  • 成本与延迟。推理 token 计费，却常常没必要展示给用户。只回传摘要能省下带宽和渲染开销。

隐藏对使用方也有代价。审计、调试、合规应对都会变难；在必须解释模型为何得出该结论的业务里，不透明本身就是采用门槛。这层张力到本文结尾也不会消失。

从部分信息缩小内部状态的原理及其对策

旁路信道在密码实现里是个老题目。智能卡的功耗或运算时间若是密钥的函数，不必直接读密钥也能排除候选。对策同样古老——把功耗抹平、把时间做成常数、掺入噪声。

这条原理在 LLM 场景下变得更锋利，原因有两个。

  • 部分信息本身就是可用形态。密码分析要攒够密钥比特才有意义，而推理轨迹泄露一半，人已经能读懂。复原的门槛很低。
  • 观测信道是作为产品功能公开的。token 用量报告、延迟、摘要展示、缓存命中率，全是为开发者准备的。删掉它们，产品就变差。

因此实务上真正要紧的区分是完全复原与候选收缩。多数旁路信道只是缩小候选，但在某些场景下这个程度作为竞争情报已经够用。反过来，封印块若不绑定上下文，那就不是收缩而是直接搬运。防御设计里把两者放进同一格，优先级一定排错。

封印应具备的性质有三条：让内容无法读取的机密性、能发现篡改的完整性，以及让它只在这个组织、这次对话、这个模型上有效的绑定。教科书上的前两项通常落实得不错，真正的事故出在第三项。

研究实际证明了什么——范围与前提

Alexander Panfilov 等八位作者的《Stealing Reasoning Traces from Proprietary LLM APIs》（arXiv 2608.09867）于 2026 年 8 月 10 日公开。作者在摘要中描述的结构性缺陷可以压缩成一句话：这些加密块在同一提供方的生态内跨会话、跨用户、跨模型完全兼容且可互换。正因为这种兼容性，存在一条不必直接攻击更强模型也能拿到其轨迹明文的路径，这是论文的核心主张。

作者列出的影响有四条。

  • 绕过反蒸馏机制。靠隐藏来阻止蒸馏的防御不再成立。论文记载在 Anthropic、OpenAI、Google 三家上演示了这一条。
  • 大规模私密数据暴露。前提是开发者公开会话日志时并不清楚封印块里有什么。作者报告称，对从公开仓库抓取的 315,320 个推理块进行解码，复原出 367 项个人可识别信息产物与 182 项凭据。
  • 危险信息的绕行暴露。即便最终回答已经安全拒绝了恶意请求，留在推理过程中的内容仍可能显现。
  • 看不见的提示注入。把载荷整个塞进封印块，污染公开的智能体运行记录。人眼看不到任何异常。

补三条框架。其一，这不是把模型打穿的故事，而是封印令牌绑定的故事——不是密码学薄弱，而是从未确定封印绑在什么上。其二，第二条影响的规模是提供方设计与使用方公开日志的习惯相乘的结果，任何一侧改动都会缩小它。其三，演示范围就是论文所写的范围，本文不给提供方排名；凡是采用同一设计模式的一方，都会面对同一个问题。

作者表示已履行负责任披露流程，并提出了用于保护客户端侧推理的密码学与系统层面缓解措施。

研究没有证明的东西

把范围切准，比夸大有用得多。

  • 这不是关于获取模型权重或训练数据的主张，拿到的是推理轨迹。
  • 也不是关于随意读取任意第三方对话的主张。数据复原那条线针对的是已经公开的日志。
  • 各提供方在何时改了什么，不在摘要范围内。提出缓解措施与实际部署是两回事。
  • 摘要里没有攻击成本与成功率数字，所以本文也不写这类数值。
  • 安全研究的结论永远是某个时点的快照。同样的性质今天是否还在，取决于各提供方当下的实现。

因此从业者该带走的问题不是「现在能不能被打穿」，而是「我们的系统是否被设计成不依赖封印块的这些性质」。无论提供方已经修了什么，这个问题都有效。

值得盯住的是第三行。服务端保存是最可靠的防御，但客户端往返这一设计当初诞生的理由，恰恰是不要在服务器上留任何东西的要求。为安全增加保留，隐私承诺就破了；为隐私减少保留，秘密就跑到客户端。这一权衡在原理上不会消失，所以现实的解法压在前两行——把封印绑到上下文并把寿命做短。

第五行的归一化常被低估。把 token 用量按区间取整、给延迟加填充，表 1 上面三行就模糊了不少。代价是开发者难以预估费用，因此把实时值给粗、把结算值给准的分离做法更现实。

这张表看着是给提供方的，对使用方同样有用：这些格子你改不了，但可以挑。在采购与合同评审阶段问一句前两行是否存在——封印绑定到什么范围、有没有有效期——候选提供方之间的实质差别就显出来了。文档里给不出答案，本身就是答案；此时应把它读作一个信号：下面那些使用方措施得铺得更厚。

使用方：输入敏感内容时该立的前提

提供方的缓解措施只能等。而使用方能改的多数事项，今天就能改，成本也低。起点是四条前提。

  • 你输入的内容不只留在最终回答里。它也留在中间产物里。只对最终输出做掩码，等于只遮了一半。
  • 中间产物会经过你自己的流程。也就是你的日志、你的链路追踪、你的工单系统、你的截图。暴露面是你这边的存储，不是提供方的基础设施。
  • 读不了不等于不存在。封印既不消除保存义务，也不消除泄露风险。
  • 摘要看着安全不代表原文安全。屏幕上的摘要是过滤后的结果，而你送回去的块是过滤之前的。

由此得出的措施，基本都属于日志卫生。

  • 不要把整个响应对象序列化写进应用日志或 APM。封印块字段在写入前剥除，或只留长度。
  • 把会话转储从工单与缺陷报告模板的默认附件里拿掉。人出错的地方通常就是模板的默认值。
  • 不要把对话历史上传到公开仓库、公开议题和演示笔记本。密钥扫描器匹配的是明文模式，封印块内部的凭据不会被拦下。
  • 把智能体运行记录分享到团队之外时，剥除封印块或替换成占位值。
  • 不要写把封印块复用到另一次对话的代码。检查缓存键设计是否让对话片段漏进了全局作用域。
  • 不要把来自不可信来源的对话历史直接拼接。若提示注入检查点只覆盖人可读的文本，封印块就会径直穿过检查网。
  • 准入标准本身应写成单独规程。什么可以送进去，已在企业内部数据能否输入 LLM 中以分级与路径指定的形式讨论过，本文默认那份规程已经存在。

实现层面如果只挑一件事，那就是掩码放在哪里。把封印块的剥除散落到每个调用点，下一批新代码一定会再捅穿。放在响应必经的单一位置——SDK 包装层或日志中间件——再用静态检查挡住绕过该点的直接调用，这样才撑得久。如果内部已经在跑数据分级表，给封印块明确一个等级也很便宜。分级表里没有名字的数据没人管，没人管的数据最后就留在日志里。

如果已经留在外面——检测与事后处置

检查表跑一遍，通常会命中几条。很多团队在这里把顺序搞错了。最常见的失误是先去删已经公开的东西。已公开的仓库或议题必须假定被复制过，删除并不能把暴露收回来。能收回来的只有凭据。

  • 先划定范围。弄清是哪个仓库、哪段时间、哪个工作负载的记录流出去了。响应中开始包含封印块的时间点，就是排查区间的起点。
  • 轮换先于删除。如果难以确定里面到底有什么，直接把该工作负载能触及的全部密钥纳入范围，反而更快。
  • 把防复发放进同一周。只做事后清理而不动流水线，下周还会发生同样的事。补上掩码点属于同一份工作。
  • 把判断依据留成记录。是否负有通知义务由法务与个人信息负责人判断，而该判断需要「什么、从何时起、在哪里」的记录。

检测这一侧也值得补一句。多数组织会监控明文密钥被推上仓库，却不监控封印块被推上仓库。只要字段形态固定，这个形态本身就能做成检测规则。不读内容也能判定「这里出现了不该出现的东西」，而事后处置的大部分工作，只要有这个判定就能启动。放规则的地方也是现成的——提交钩子、CI 的密钥扫描阶段、仓库扫描器，三者选其一即可，不必三处都加。

合同与条款里真正要确认的事

有些问题在技术措施之前，先由合同文本给出答案，而提供方文档在这一块写得相对明确。Google 的 Gemini API 附加条款把免费服务与付费服务的数据处理分开规定，并设有地区例外。OpenAI 的数据管理文档分别说明 API 输入输出的训练排除、保留期限，以及零保留适用的范围。两者均为 2026 年 8 月口径，此类文档修订频繁，采用时重新打开一遍更稳妥。

合同评审中真正该问的条目如下。

  • 中间产物（推理 token、思考块）是否落在条款对输出的定义之内。落不落进去，决定训练排除条文的适用范围。
  • 启用零保留时中间产物如何处理。别忘了客户端往返设计本身就是零保留要求的产物。
  • 思考摘要的保留期限与查阅权限。摘要有时与原文享受不同待遇。
  • 禁止对推理轨迹做逆向工程的条文。大多数条款都有，也是下文争点的起点。
  • 中间产物泄露时通知义务的主体与时限。如果是从你这边的日志漏出去的，通知主体就不是提供方。
  • 模型停用或更换时，已积累的对话历史如何迁移。这条线直接连到摆脱 AI 供应商锁定里讨论过的架构问题。

把合同评审与技术团队分开跑，这六条通常会整块漏掉，因为它们正好落在法务单独判断不了、工程师单独读不懂的位置上。在引入评估文档里加一行叫中间产物，让两边看同一行，光这一点就能大幅减少遗漏。复查周期也写在那一行上——这类文档改得很安静，通常没人会来通知你。

知识蒸馏与模型抽取——争点在哪里

从这里开始不是法律意见，本文也不给结论。但争议沿哪些轴展开，是可以梳理的。

  • 合同违约。主要提供方的条款普遍禁止用输出训练竞品模型。实务中最先处理的就是这一轴。
  • 著作权。模型输出本身是否构成作品在各法域仍有争议，没有统一构成。轨迹是否算输出的一部分，也一并成为争点。
  • 商业秘密。分水岭在于提供方是否被认定为采取了合理的保密措施。隐藏动作本身的存在，可能被援引为这种努力的证据。
  • 信息访问相关法律。违反条款是否等同于未经授权访问，各法域判断不一。同一事实在不同国家可能得到不同评价。
  • 个人信息。只要轨迹中含有个人信息，无论它此前是否被隐藏，处理者义务都会产生。与前四轴不同，这一轴争议空间很小。

这份清单里实务上确定的只有一条：「藏起来了所以受保护」这套逻辑在技术上和法律上都很弱。技术侧要封印绑定上下文才成立，法律侧真正的防线是合同文本写了什么。隐藏替代不了这两道防线。

未能确认的部分

把本文没有作为数值或事实主张的条目集中放在一处。

  • 各提供方处置的时间与内容。论文表示履行了负责任披露并提出缓解措施，但哪家在何时改了什么，摘要中无从确认。
  • 凭据的类型分布。二次摘要中提到的按类型计数（密钥、口令、令牌等）不在摘要范围内，未予引用。
  • 当下的可复现性。同样的性质现在是否还在，取决于各提供方当前的实现，本文未做验证。
  • 攻击成本与成功率。摘要中没有数值，因此未写下任何数字。
  • 本地案例。未确认到中国或韩国企业环境中出现同类暴露的公开报道。
  • 旁路信道的定量贡献。表 1 中每条信道实际能缩小多少候选因系统而异，未见可推广的测量值。

常见问题

加密的推理块为什么由客户端持有而不是服务器?

多数推理模型 API 把不在服务器保留对话状态的无状态模式作为默认或可选项。服务器上什么都不存，而下一轮又要接续此前的推理，就只能把中间产物交给客户端再取回。为满足零保留与数据最小化要求而做的选择，结果把秘密的物理位置搬到了信任边界之外。

既然已经封印，不就读不到了吗?

封印需要三个性质：机密性、完整性，以及让它只在这次对话、这个用户、这个模型上有效的绑定。只有前两者而缺第三者，块就不再是上下文，而是可搬运的数据。arXiv 2608.09867 指出的正是这种绑定缺失，问题不在密码学薄弱。

论文实际证明到了什么程度?

按摘要口径共四条：绕过反蒸馏机制、从已公开的会话日志里复原私密数据、在最终回答已安全拒绝时仍暴露留在推理过程中的危险内容，以及把载荷整个藏进封印块的提示注入。作者报告称对 315,320 个来自公开仓库的推理块解码，复原出 367 项个人可识别信息产物与 182 项凭据。这既不是关于获取模型权重的主张，也不是关于任意读取第三方对话的主张。

调用 API 的一方今天能做什么?

最便宜的措施是日志卫生。不要把整个响应对象序列化写进日志，写入前先剥除或掩码封印块。把会话转储从工单与缺陷报告模板的默认附件中拿掉，不要把对话历史上传到公开仓库和演示笔记本。密钥扫描器匹配明文模式，封印块内部的凭据不会被拦下。

用推理轨迹去训练另一个模型在法律上会怎样?

本文不是法律意见，也不给结论。但争点清楚：禁止训练竞品模型条款下的合同违约、模型输出的可著作权性、商业秘密的认定要件、违反条款是否构成未经授权访问，以及轨迹含有个人信息时的处理者义务。除最后一项外，其余在不同法域都不会得出相同结论。

结论：隐藏与保护是两回事

把这件事要带走的东西压到三条。

  1. 问题出在绑定层，不在密码学。把封印状态交给客户端的设计本身有正当理由，失败发生在没人决定封印绑到哪个上下文的时候。处理自家系统的会话令牌或签名 Cookie 时，也该问同一个问题。
  2. 影响范围由使用方的日志习惯决定。从公开仓库能做批量复原，是因为封印块以「读不了」为由未经审查就被公开。这一半今天就能改，不必等谁，代价也不过是改一处日志流水线。
  3. 不要把检查点只放在人可读的文本上。无论是提示注入防御还是密钥扫描，把不透明的块排除在检查范围外，那块就会变成通道。

读安全研究时常见的失误，是只看「哪里被打穿了」，漏掉「原本依赖的是什么」。这项研究动摇的不是某个具体产品，而是隐藏即保护的前提。数一数自家系统里有多少道防御建在这个前提之上，比等提供方发公告更该先做。
