Kubernetes를 브라우저로 포팅하다 — WASM이 여는 새로운 실험

ngrok의 Webernetes는 사실 WASM을 쓰지 않았다 — 그 반전에서 읽는 브라우저 런타임의 진짜 흐름

2026-07-03 개발/인프라

서론: "쿠버네티스가 브라우저에서 돈다"는 말이 낯선 이유

Kubernetes는 애초에 서버 클러스터를 위해 만들어진 물건이다. 수십에서 수천 대 머신에 걸쳐 컨테이너를 스케줄링하고, 네트워크를 붙이고, 죽은 노드를 감지해 파드를 재배치하는 것이 본업이다. 그런 것을 "브라우저 탭 안에서 돌린다"는 문장은 직관적으로 이상하게 들린다. 브라우저 안에는 여러 대의 서버도, 진짜 리눅스 커널도, 실제 컨테이너 런타임도 없기 때문이다.

2026년 6월, ngrok 엔지니어링 팀이 정확히 이 문장을 현실로 만든 프로젝트 Webernetes를 공개하면서 개발자 커뮤니티에서 화제가 됐다. GeekNews에도 이 소식이 소개되며 짧지만 흥미로운 토론이 오갔다. 이 글에서 필자가 하려는 것은 두 가지다. 첫째, 이 프로젝트가 정확히 무엇을 했고 무엇을 하지 않았는지를 과장 없이 풀어내는 것. 둘째, "WASM이 여는 새로운 실험"이라는 프레임이 이 사례에 얼마나 들어맞고 얼마나 안 맞는지를 짚어, 브라우저가 범용 런타임으로 진화하는 더 큰 흐름 속에 이 실험을 정확히 자리매김시키는 것이다. 2026년 7월 기준으로 이 실험이 어디까지 와 있고, 무엇이 아직 검증되지 않았는지를 정리한다.

1. Webernetes란 무엇인가 - ngrok의 실험

Webernetes는 쿠버네티스의 핵심 개념 — 파드, 노드, 스케줄러, ReplicaSet·Deployment 컨트롤러, Service, kube-proxy에 해당하는 로직 — 을 TypeScript로 다시 구현해 브라우저 안에서 그대로 돌아가게 만든 프로젝트다. 노드 3개가 고정된 가상 클러스터를 브라우저 메모리 안에 만들고, 그 위에서 실제 쿠버네티스처럼 파드를 스케줄링하고 서비스로 트래픽을 라우팅하는 과정을 시각적으로 보여준다.

규모도 작지 않다. 약 10만 줄 코드가 두 달에 걸쳐 만들어졌고, 동작의 정확성을 검증하기 위해 실제 k3s 클러스터와 비교하는 통합 테스트 204개와 단위 테스트 1,855개를 붙였다. kubernetes-client 자바스크립트 라이브러리와 호환되는 API를 제공해, 기존 쿠버네티스 도구 지식을 그대로 써먹을 수 있게 설계했다는 점도 특징이다. 목적은 명확히 인터랙티브한 쿠버네티스 교육 콘텐츠 제작이며, ngrok은 공식 데모 사이트로 결과물을 공개했다.

2. 반전 - 이것은 WASM 포팅이 아니다

여기서부터가 이 글의 핵심이다. "Kubernetes를 브라우저로 포팅했다"는 제목만 보면 누구나 WebAssembly로 실제 바이너리를 컴파일한 결과물을 떠올린다. 필자도 처음엔 그렇게 짐작했다. 하지만 원문을 직접 확인한 결과는 달랐다.

2.1 저자가 직접 밝힌 대답

ngrok 블로그 원문에는 "Did you compile Kubernetes to WebAssembly?"라는 질문에 저자가 스스로 "답은 '아니오'다"라고 명시한 대목이 있다. 쿠버네티스의 실제 Go 바이너리(kube-apiserver, kubelet, scheduler 등)를 WASM으로 컴파일한 것이 아니라, Go 코드베이스의 동작 방식을 참고해 TypeScript로 선택적으로 재구현한 것이다.

2.2 왜 WASM을 버렸나 - 파일 크기라는 현실적 이유

이유는 낭만적이지 않고 실용적이다. 저자가 직접 실험해 본 결과, 아무 기능도 없는 hello world 수준의 WASM 빌드조차 약 540KiB에 달했다. 반면 TypeScript로 직접 짠 Webernetes 전체는 약 140KiB에 그쳤다. 브라우저에서 즉시, 가볍게 로드되는 결과물을 원했던 저자에게 WASM 컴파일 경로는 이번 프로젝트의 목적(인터랙티브 데모, 빠른 로딩)에 맞지 않는 선택이었다.

2.3 그렇다면 무엇을 한 것인가 - Go의 동시성을 자바스크립트로

대신 저자는 Go 특유의 채널, 뮤텍스, select 문 같은 동시성 패턴을 자바스크립트 위에서 흉내 내는 런타임 계층을 직접 만들었다. Kubelet 바이너리의 일부, Pod 스케줄러, 네임스페이스 컨트롤러, kube-proxy에 해당하는 로직, 그리고 브라우저 안에서 동작하는 가상 CNI(컨테이너 네트워크 인터페이스)와 가상 컨테이너 런타임까지 전부 이 방식으로 다시 짰다. 결과물은 "쿠버네티스를 WASM으로 옮긴 것"이 아니라, "쿠버네티스의 동작 모델을 자바스크립트 세계로 이식한 것"에 가깝다.

3. 그래도 이 실험이 "브라우저 런타임" 흐름의 일부인 이유

Webernetes 자체가 WASM을 쓰지 않았다고 해서, 이 프로젝트를 "브라우저가 범용 런타임이 되어가는 트렌드"와 무관하다고 보는 것은 성급하다. 오히려 이 사례는 그 흐름의 폭이 얼마나 넓은지를 보여준다.

3.1 진짜 WASM 사례들 - 브라우저는 이미 무거운 일을 하고 있다

Chrome 사용 통계 기준으로 2026년 초 WASM은 전체 페이지 로드의 약 5.5%에서 쓰이는 것으로 보고된다. Figma의 렌더링 엔진, 웹용 포토샵, 웹용 AutoCAD, 구글 미트의 일부 영상 처리가 실제로 WASM 위에서 돈다. 필자가 예전에 다룬 포켓몬 에메랄드를 브라우저에서 10만 FPS로 돌린 WASM 재컴파일 프로젝트도 같은 계보다. 더 직접적인 비교 대상은 StackBlitz의 WebContainers다. 이쪽은 실제로 WASM 기반 가상 OS를 만들어, 파일시스템과 가상 TCP 네트워크까지 흉내 내며 Node.js 서버를 브라우저 안에서 통째로 구동한다. Webernetes가 "됐다, WASM 없이도 충분하다"고 판단한 지점에서, WebContainers는 "제대로 된 OS 추상화를 위해 WASM이 필요하다"고 판단한 셈이다. 같은 목표(브라우저에서 서버 소프트웨어 구동)에 대한 서로 다른 답인 셈이다.

3.2 서버 쪽 WASM+쿠버네티스 - 정반대 방향의 흐름

흥미롭게도 "WASM"과 "쿠버네티스"라는 단어가 함께 쓰이는 더 흔한 맥락은 사실 정반대 방향이다. SpinKube, Kube-Wasm 같은 프로젝트는 WASM 워크로드를 쿠버네티스 클러스터 안에서 네이티브 워크로드처럼 스케줄링하는 것을 목표로 한다. 즉 "쿠버네티스를 브라우저로 가져가는" Webernetes와, "WASM을 쿠버네티스 클러스터로 가져가는" SpinKube류는 방향이 완전히 반대다. 다만 두 흐름 모두 결국 같은 질문에서 출발한다. 컨테이너라는 무거운 격리 단위 대신, 더 가볍고 이식성 높은 실행 단위로 무엇을 쓸 수 있는가라는 질문이다.

3.3 두 흐름이 만나는 지점

필자의 해석은 이렇다. Webernetes는 WASM 기술 자체의 산물은 아니지만, WASM이 지난 몇 년간 증명해 온 전제 — "브라우저는 이제 진짜 실행 환경이지, 문서 뷰어가 아니다" — 위에서만 시도될 수 있는 실험이다. 브라우저의 자바스크립트 엔진이 충분히 빨라지고, 메모리 모델이 충분히 유연해졌기 때문에 Go의 동시성 모델까지 순수 TypeScript로 흉내 낼 엄두를 낼 수 있었던 것이다. 그런 의미에서 "WASM이 여는 새로운 실험"이라는 제목은, Webernetes가 WASM을 직접 썼다는 뜻이 아니라 WASM이 이끈 "브라우저=범용 런타임" 시대가 이런 실험까지 가능하게 만들었다는 뜻으로 읽는 것이 정확하다.

4. 교육·데모·로컬 개발에서의 실제 가치

4.1 기존 브라우저 기반 K8s 학습 도구와 무엇이 다른가

쿠버네티스를 브라우저로 배우는 방법은 원래도 있었다. Killercoda나 Docker의 Play with Kubernetes 같은 서비스는 브라우저에서 접속해 로그인 60분 안에 실제 리눅스·쿠버네티스 환경을 무료로 써볼 수 있게 해준다. 다만 이들은 "브라우저로 접속"만 할 뿐, 실제로는 원격 VM이나 컨테이너가 뒤에서 동작하는 방식이다. 반면 Webernetes는 서버가 전혀 없다. 브라우저 탭을 닫으면 클러스터도 함께 사라지고, 백엔드 비용도 0이다. 이 차이는 사소하지 않다. 대규모 트래픽이 몰려도 서버 확장을 걱정할 필요가 없고, 문서 페이지나 블로그 글 안에 그대로 임베드해 넣을 수 있다.

4.2 어디에 쓸 수 있나

가장 잘 맞는 용도는 세 가지로 정리된다. 첫째, 신규 입사자 온보딩 교육에서 "파드가 어떻게 스케줄링되는지"를 클릭 몇 번으로 눈으로 보여주는 인터랙티브 자료. 둘째, 기술 문서나 콘퍼런스 발표에서 실습 코드를 그대로 embed해 청중이 즉석에서 만져보게 하는 데모. 셋째, 로컬에 minikube나 kind조차 설치하기 부담스러운 초심자가 개념만 빠르게 익히는 입문 도구다. 반대로 실제 애플리케이션 배포, 성능 테스트, 네트워크 정책 검증 같은 작업에는 애초에 맞지 않는다.

Webernetes를 "쿠버네티스 대체품"으로 오해하지 않도록 한계를 분명히 정리한다.

6. LLM으로 짠 코드, 사람이 전부 검토하다

이 프로젝트에서 필자가 개인적으로 가장 흥미롭게 본 대목은 기술 자체보다 개발 과정이다. 저자는 코드 대부분을 LLM이 작성했다고 밝히면서도, 모든 줄을 사람이 직접 검토했다는 점을 강조한다. 반복적으로 발견된 LLM의 문제 패턴은 익숙하다. 제대로 된 자료구조(LRU 캐시 등) 대신 단순 Map으로 축약해버리기, 원본 Go 코드에는 없던 헬퍼 함수를 임의로 추가하기, 테스트 케이스를 슬쩍 생략하기 같은 것들이다. 저자의 결론은 명확하다. "리뷰와 테스트를 함께 적용해야만 LLM 생성 코드를 신뢰할 수 있다."

이는 필자가 AI 코딩 도구 비교 글에서도 반복해서 짚은 지점과 정확히 일치한다. 10만 줄 규모의 프로젝트를 두 달 만에 완성했다는 속도는 인상적이지만, 그 속도가 가능했던 이유는 LLM이 알아서 잘 짰기 때문이 아니라 204개 통합 테스트와 1,855개 단위 테스트, 그리고 100% 수동 코드 리뷰라는 검증 인프라를 동시에 갖췄기 때문이다. "LLM이 짰다"는 사실보다 "어떻게 검증했는가"가 이 프로젝트의 진짜 교훈이다.

7. 한국 개발자 관점 - 어디에 써볼 만한가

한국에서도 쿠버네티스 입문 교육 수요는 꾸준하다. 사내 온보딩, 부트캠프, 콘퍼런스 워크숍에서 흔히 minikube나 kind를 로컬에 설치시키는데, 사내 보안 정책상 Docker 설치 자체가 막혀 있거나 노트북 사양이 부족한 경우가 적지 않다. Webernetes류의 브라우저 시뮬레이터는 이런 상황에서 설치 장벽을 완전히 없앤다는 점에서 매력적이다. 다만 국내 팀이 유사한 것을 직접 만들려 한다면, 이 프로젝트가 증명한 "10만 줄, 2개월"이라는 숫자를 액면 그대로 믿기보다, 그 뒤에 붙은 2,000개 가까운 테스트와 전수 코드 리뷰 비용까지 함께 계산에 넣어야 한다. LLM이 초안 작성 시간을 줄여준 것은 맞지만, 검증 비용까지 줄여준 것은 아니다.

결론: 브라우저가 서버를 흉내 내는 실험에서 무엇을 배울 것인가

Webernetes는 "WASM으로 쿠버네티스를 브라우저로 옮겼다"는 소문과 달리, WASM을 의도적으로 배제한 TypeScript 재구현이다. 이 반전은 흠이 아니라 오히려 더 유용한 교훈을 준다. 브라우저를 범용 런타임으로 쓰는 길이 하나가 아니라는 것이다. WebContainers처럼 WASM으로 진짜 OS를 흉내 내는 길도 있고, Webernetes처럼 필요한 동작만 가벼운 언어로 재구현하는 길도 있다. 두 길 모두 "브라우저는 이제 무엇이든 돌릴 수 있는 곳"이라는 2026년의 전제를 공유한다. 다음에 "OO를 브라우저로 포팅했다"는 소식을 만나면, 그것이 실제로 무엇을 컴파일한 것인지 — 진짜 바이너리인지, 재구현인지 — 를 한 번 더 확인하는 습관을 권한다. 그 디테일 안에 훨씬 흥미로운 이야기가 있다.
