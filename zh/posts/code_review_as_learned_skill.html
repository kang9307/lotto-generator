代码评审不会自己变好

阅读顺序与五个镜头、区分阻断·建议·偏好的意见标注，以及有意识培养评审者的装置

2026年8月16日 开发/基础设施

引言：审批更快了，同一个地方又炸了

一个变更请求三十分钟就通过了。上面挂着三条意见，全是变量名和换行。两周后出故障，原因是那个变更里的一个条件。评审并没有缺席，只是什么都没拦住。

这种事反复出现的团队，给出的诊断通常是「大家再仔细一点」。但仔细不是一个可以往上加的量。能加的是看什么、按什么顺序看，那是流程而不是性格。评审里拦得住东西的人不是更认真，而是读的顺序不同。顺序是可以教的。

这个观点最近又被讨论起来。八月挂上GeekNews的一篇文章把评审定位成一门可以学的技术，并举了最新模型漏掉的三个真实缺陷作为依据。三个案例里代码本身都没问题。一处是文件锁设计中性能与稳定性的取舍，一处是新用的命令行参数在部署环境的版本里到底存不存在，还有一处是校验和与主体分开上传、中途断掉之后还剩下什么。三件事都要记住屏幕之外的上下文才看得见。

本文不讨论评审的目的，也不讨论工具选型。目的在把评审看作可维护性检查里写过，工具版图在智能体代码评审里单独写过。这里只谈如何有意识地把一个人的评审能力练起来。

1. 把评审当作「自然就会」之后出现的症状

1.1 只剩风格，设计一路通过

把一个没有任何训练机制的团队的评审意见收集起来，分布是明显偏的。命名、格式、有没有注释占了大头，几乎没有人问「这条边界为什么划在这里」。

这不是懒，而是成本结构。风格意见几乎是免费的：只看一行就够，不会说错，对方也难以反驳。设计意见则要理解整个变更，说错了很丢脸，而且通常会引发争论。两个选项的价格差这么大，评审自然会往便宜的一侧流。一项交给个人自觉的活动为什么会随时间变差，原因就在这里。

1.2 审批变慢，拦住的缺陷反而变少

评审一旦沦为过场，评审者面对大变更就会往后拖。等待时间一长，作者就把更多东西攒进一次变更里。反正都要等，不如一次性发过去，这在个人层面是合理的。于是下一次评审更难读，也就拖得更久。

这个环一转起来，就出现最糟的组合：审批更慢，而拦住的缺陷更少。上限规则这类处方为什么不太管用，在评审队列的动力学里单独算过。要点是到达率与处理率决定结果，规则本身决定不了。

1.3 每个评审者看的地方不同，于是留下窟窿

有人先打开测试，有人从命名看起。两个人评审同一个变更，重叠的部分被看了两遍，没人看的部分原样留着。增加评审人数并不能补上这个窟窿。没有规范的时候，覆盖面不是由人数决定的，而是由互不重叠的视角数量决定的。

Google公开的评审者指南把检查项按顺序固定下来，正是为了堵住这个窟窿：设计、功能、复杂度、测试、命名、注释、风格、一致性、文档。九项依次排列，风格排在第七位。

2. 阅读顺序 — 从意图到书写形式

九项每次都想起来太难。压缩成实务里好用的五个阶段就是下面这张表。这个排列不是口味，而是获取信息的顺序。有了前一阶段的答案，后一阶段的判断才成立。

阶段确认什么看什么材料这里能拦住的这里拦不住的
1. 变更意图改什么、为什么改、有没有别的做法说明、需求单、决策记录问题定义错误、不必要的变更全部实现缺陷
2. 接口跨越边界的东西形状变成了什么样schema、签名、对外类型兼容性破坏、职责放错位置内部逻辑
3. 数据流向值从哪里进、往哪里出、谁拥有它调用路径、存储访问状态不一致、信任边界越界、泄漏书写形式问题
4. 边界情况边界值、错误、并发、重试测试、异常处理、加锁线上故障的绝大多数可读性
5. 书写形式命名、注释、格式风格指南、静态检查理解成本其余全部

2.1 为什么意图排在最前

不知道意图就打开代码，所有判断都会缩成「实现对不对」。把一个定义错了的问题解得很完美的代码，在这种状态下会顺利通过。语法没错，测试是绿的，找不到拦下来的理由。

还有一个更实际的理由。最有价值的意见「这个变更有必要吗」实际上只出现在最初五分钟。读了二十分钟之后，评审者自己已经在这段代码上投入了时间，很难再开口说掉头。所以确认意图不只是顺序上靠前，而是应该在打开代码之前就完成。说明里找不到答案，当场退回就是一个正当的评审结论。

2.2 为什么书写形式排在最后

书写形式是自动化的对象。格式化工具和静态检查能抓的东西，人用眼睛去看，就等于少看了别的。总时间是固定的。

更糟的是锚定效应。第一屏的变量名不顺眼，接下来二十分钟就变成关于命名的对话，设计问题在这期间悄悄溜过去。Google指南把不在风格指南里的纯风格问题定义为个人偏好，并要求加上Nit:，正是为了把这条车道从主干上摘出去。同一份文档明确写着软件设计从来不是纯粹风格或个人偏好的问题。意思是，设计和偏好不能放在同一个分量上。

2.3 守住顺序之后真正会变的东西

  • 时间分配会变。原本把一半时间花在第五阶段的人挪到第四阶段，抓到的缺陷种类就变了
  • 出现了中止点。在第一阶段卡住就不读代码直接退回。这是流程，不是不负责
  • 意见不再重叠。两个人按同一顺序读，会停在不同深度，视线自然分散
  • 评审时长变得可预测。每个阶段能给出大致预算，往后拖的理由就少了

有一点要分清楚。这个顺序是建立理解的顺序，不是风险分类的顺序。没时间全读时先看什么是另一条轴，那条轴按契约、不变式、权限的次序整理在把控制点移到代码之外里。两者混在一起，既训练不了也分类不了。

3. 看什么 — 五个镜头

清单一长就死。二十项没人用，五项会变成习惯。下面五个是按真实故障反复出现的位置挑的。

3.1 边界值

  • 0条、1条、最大值、超出。列表为空时、正好一条时、正好等于分页大小时
  • 空字符串和null不是一回事。当成一回事，总会在某处分叉
  • 数值的符号与取整位数。金额尤其如此，一位之差会一路走进账目
  • 时间的边界 — 零点、月末、夏令时切换，以及时区是挂在存储时刻还是展示时刻
  • 排序不稳定时相同键之间的次序。翻页时条目会重复或者消失
  • 长度按字节算还是按字符算。中文和表情符号上立刻分岔

3.2 错误路径

  • 成功路径有测试，失败路径通常没有。这个不对称正是评审者的阵地
  • 吞掉异常的代码。catch里是空的，或者只记一行日志就继续往下走
  • 部分失败 — 三个里成功了两个，剩下什么、消失了什么
  • 有没有超时值，以及这个值是否短于上游调用方的超时
  • 重试是否安全。同一个请求发两次结果相同，才谈得上重试
  • 错误消息里会不会把内部路径或标识符带出去

3.3 并发

  • 先读后写的区间。中间插进另一个请求时，什么会被覆盖
  • 事务边界有没有把外部调用包在里面。包住了，连接就被别人的响应时间占着
  • 缓存失效是在写之前还是写之后。一个顺序之差就把旧值钉死了
  • 获取锁的顺序在所有代码路径上是否一致
  • 批处理与在线请求有没有在同一时段碰同一批行
  • 这个镜头测试几乎抓不住，所以人去看仍然是最便宜的办法

3.4 能否回退

  • 发布之后出问题怎么退回去。答案写不成一行，本身就是一条意见
  • 混进了schema变更，只退代码是不够的。前后兼容能不能在一次发布期间保持住
  • 删数据或者改数据形状的变更退不回去。需要的是向前修复流程，而不是回滚
  • 已经发出去的东西收不回来：邮件、支付、对外通知
  • 能用特性开关包住的话，评审负担本身就降下来了。顺便问清开关什么时候摘掉

3.5 能否观测

  • 跑错了谁会怎么知道。答案如果是「客户告诉我们」，那本身就是缺陷
  • 新出现的失败模式背后有没有对应的日志或指标
  • 日志里会不会进个人信息。写下去一次的日志是收不回来的
  • 指标的基数。把用户标识当标签用，几个月后账单会炸
  • 失败后留下的痕迹够不够定位原因，请求标识是否贯穿整条链路

把五个镜头按顺序过一遍成为习惯之后，花的时间反而会减少，因为不必每次重新想一遍。还没形成习惯之前，把清单放在屏幕旁边更实际。

4. 反馈怎么写 — 区分阻断、建议、偏好

评审最常崩掉的地方不是读而是写。十条语气一致的意见摆在面前，作者看不出哪些必须改。于是要么全改，要么全争，要么一声不吭全部照办，然后暗自开始讨厌评审。

解法很简单。给每条意见前面加一个等级。不需要工具，也不需要制度文档，一个前缀就够了。

等级标注含义与批准的关系句式
阻断Blocking:就这样合入不行未解决不予批准什么 + 在哪种输入或状态下 + 造成什么结果
建议Suggestion:我认为有更好的做法作者判断，有依据可保留备选 + 它更好的理由 + 决定权交给作者
偏好Nit:不改也行与批准无关一行写完
提问Question:为了弄明白而问回答即可关闭写清自己不明白什么
标记Praise:把做得好的地方留下来无关好在哪里、为什么好

Nit:不是杜撰的惯例，而是Google指南里写明的标注。对不在风格指南里的改进建议加上它，好让开发者知道这不是强制项。其余四个是同一原理的延伸。

4.1 附上依据的句式

阻断意见的最小形态有三个部件：什么 / 在哪种输入或状态下 / 造成什么结果。缺任何一个，作者都无法复现，从那里开始就变成争论。

  • 坏例子 — 这块看着有点危险
  • 好例子 — Blocking: 列表为空时引用了第一个元素，新用户首次进入会全部失败
  • 建议的好例子 — Suggestion: 把这个分支提到查询侧，每次调用的查询数会降到一次。当前量级不急，决定权交给你
  • 依据的层级是 故障历史 > 规格与文档 > 原则 > 个人经验 > 偏好。越往上争论结束得越快
  • 写出自己的确信程度。「我确定」和「我只是猜测，麻烦确认」是两条不同的意见

4.2 提问句式并不总是对的

「说得委婉一点」的建议流传很广，但把提问句式用在阻断事项上是有害的。「这样做怎么样」会被读成一个选项，作者完全正当地不采纳。然后故障之后只剩下一句「我当时说过」。那句话帮不了任何人。

反过来，本该核实事实的地方用了断定句式，就成了误判，重复两次之后这位评审者的所有阻断意见都会失去分量。判断标准不是语气而是确信程度。知道答案就断定并附上依据，不知道就用提问句式讲清自己不明白什么。指向代码而不是指向人，这条原则不变。「你为什么要这么做」和「这条路径失败之后还剩下什么」是完全不同的两句话。在以MR为中心、并且内部有成文研发规范的团队里，规范文档常常已经替这些等级预留了位置，问题往往不在于没有规范，而在于规范只写了必须做什么，没有写清哪一类意见可以拦住合入。

4.3 团队用一句话约定批准标准

Google指南把批准标准定在明显改善整体代码健康度的状态，并配上一句：世上没有完美的代码，只有更好的代码。缺了这一行的团队里，评审者个人的完美主义会直接变成团队的速度。

分歧收不拢时的处理方式也值得先定下来。同一份指南说先尝试达成共识，不行就转成对话，还不行就往上升级，但不要让决定悬着。实务中最贵的状态，是既没被驳回也没被批准地拖过三天。

5. 培养评审者的装置

从这里开始才是正题。前面的顺序和标注今天读明天就能用。但知道什么看起来危险的那种感觉无法搬进文档。它待在经历过故障的人脑子里，要取出来就得有装置。下面四个按成本排列。

5.1 结对评审 — 把意见对照一遍

  • 两个人各自看同一个变更，然后把意见摆在一起对照。没有重叠的部分就是教材
  • 资深的一方不能先说。先听到答案，后面就只剩确认动作，自己的视角出不来
  • 时间要花两倍，所以钉死在每周一个变更，而不是每个变更都做。这是训练预算，不是运行流程
  • 共享屏幕并把「我现在为什么要打开这个文件」说出声，顺序就原样传过去了
  • 对象要挑普通的变更，不要挑难的。难的变更结论只有一个，看不出注意力的差别

5.2 缺陷复盘与险些出事的分享

  • 出了故障之后只问一个问题：这个缺陷本该在评审里拦住吗，如果是，在哪个阶段
  • 这是找阶段的问题，不是找人的问题。这条界限一垮，下一次复盘就没人说话了
  • 「这类东西评审拦不住」也是正当结论。那就把它挪到测试或者卡点上，而不是塞进清单
  • 更有价值的材料是没有炸掉的那些：评审里拦住的缺陷、发布前一刻发现的东西。原文作者也提议把每个迭代中发现的缺陷各留一份简短记录，在团队里传阅
  • 记录固定成三行：是什么 / 为什么没看见 / 看什么就能看见。写长了就没人写了

5.3 有意识地打散评审分配

  • 同一个人只评审同一个目录，那个目录会变安全，其余会变危险。而且那个人一走，就没人知道了
  • 把负责人一名 + 轮岗一名写进分配规则。第二个位子就是训练位
  • 对轮岗评审者要有不同的期待：不是「这段代码对不对」，而是「读不读得懂」。仅仅指出读不懂的地方就已经有价值
  • Google出的那本书写道，其内部评审绝大多数是由恰好一名评审者处理的。批准被拆成正确性、归属权、语言熟练度三条轴，而通常由一个人同时担着这三条
  • 也就是说，增加评审人数不是答案。这套设计建立在一个人的水平就是评审质量这个前提上，所以钱才要花在训练上

5.4 把最会拦的人的隐性知识挖出来

  • 团队里总有一个格外能拦住东西的人。问他「你是怎么看的」，回答通常是「就是看得出来」。这就是隐性知识
  • 挖出来的办法是追问注意力为什么转移，而不是追问结论。一起打开一个真实变更，让他出声读，在每个停顿处问他为什么停
  • 原文作者把这件事称作苏格拉底式对话和对熟手的认知分析。形式不同，要点一样
  • 挖出来的东西整理成问题清单比整理成检查清单活得久。「这条路径失败之后还剩下什么」这样的句子比一个勾选项更容易被反复用上
  • 一个季度一小时就够，但必须写下来，否则那个人走了就什么都不剩

6. AI开始写代码之后变了什么

6.1 表面质量上升，验证意图的负担变重

生成的代码命名工整、带着注释、格式统一。站在评审者的位置上，这意味着过去在第一阶段和第五阶段亮起的信号消失了。以前凌乱的代码是危险信号：缠成一团说明作者自己也糊涂，往周边挖一般都能挖出东西。现在这个相关性弱了，干净但是错误的代码变得常见。

所以时间分配必须往前挪。原本花在书写形式上的时间挪到意图和数据流向上。原文作者举的三个案例正是这一类。代码本身语法和结构都没问题，错的是部署环境的版本、事务边界、设计上的取舍。三样都在屏幕之外。

6.2 没有人可以问了

人写的代码，问一句「为什么这么写」就有回答。生成的代码，作者往往没有那个答案。评审有一半原本是对话，现在这一半空了。

应对办法是把要求挪个位置。让变更说明写清决策和被放弃的备选，没有就不读代码。评审对象从代码转向决策这条脉络，在控制点的移动里写得更细。压缩成一条实务规则就是：作者解释不了的代码不予批准。这不是禁止工具的规则，而是钉住责任位置的规则。

6.3 训练路径被切断

评审能力原本是靠自己写的代码挨批评长起来的。写得少了，这条路就窄了。与此同时要读的量在变大。还没学会就被推上裁判位，这不是个人勤奋能解决的形状。

所以第五节的装置不能指望自然长出来，要拨预算引入。再补一句：理解低一层抽象的能力仍然保值。要判断生成器造出了什么，就得知道它下面在发生什么。理解成为瓶颈的那个观察，在培养评审者这件事上表现得最尖锐。

7. 组织指标 — 测什么会让评审变差

7.1 容易数的东西通常也容易操纵

想管理评审的组织通常从容易数的东西开始数。可是容易数的指标几乎无一例外都可以靠行为操纵。而在质量就是全部的活动里，扭曲来得特别快。

指标本意实际诱导出的行为留下的结果
批准数量提高评审参与扫一眼就批准，只留一行意见评审变成形式
压缩评审耗时消除瓶颈躲开难的变更，只挑容易的危险的变更处理得最晚
意见条数衡量认真程度批量生产偏好类意见信噪比变差
最小化往返次数减少摩擦把没把握的意见咽回去缺陷顺利通过
评审覆盖率100%防止遗漏用形式批准填满指标是绿的，实质是空的

7.2 那么该看什么

  • 等待时间当成分布看，不要当成目标。看尾部而不是中位数 — 放着超过三天的变更有多少件
  • Google出的那本书把工作时间内24小时给出首次反馈写成期待值。这条更适合当作越过就不对劲的界线，而不是要达成的目标
  • 变更规模的分布。同一本书写道其内部变更约35%只涉及单个文件。大变更是例外，评审才成立。怎么拆分整理在把变更叠成层里
  • 返工率 — 合入之后短时间内又去改同一批文件的比例。这是评审漏掉了什么的间接信号
  • 缺陷被拦住的阶段分布。评审里拦住的与发布后才发现的比例
  • 比任何数字都有价值的是复盘问题。上个季度的故障里，有几件本来可以在评审中拦住，为什么没拦住

7.3 不要按人统计

只守一条的话就守这条。评审指标一旦进入个人绩效，评审就变成政治。难以反驳的意见会变多，难的变更会被躲开，还会开始挑对谁提意见。按人统计缺陷检出率崩得最快，因为接手难代码的人天然吃亏。

指标只用在团队层面，给个人的不是评分而是训练资源。一小时结对评审加三行复盘记录，比一张个人考核表便宜得多，效果也大得多。

8. 九十天训练计划

8.1 个人

  • 第1~2周 — 把阅读顺序写在屏幕旁边，每次评审都照做。书写形式类意见只放在最后五分钟
  • 第3~4周 — 给每条意见加上等级前缀。自己一直以来在提什么，那一周就看得清清楚楚
  • 第5~8周 — 从五个镜头里挑最弱的一个，通常是并发或者可观测性。只把那个镜头每次都有意识地用上
  • 第9~12周 — 回看自己批准过的变更里跑出来的缺陷，标出是在哪个阶段漏掉的。这是个人训练里收益最高的一步
  • 持续 — 按时间顺序翻最会拦的那个人的意见。浮出来的不是结论，而是他先打开了什么

8.2 团队

  • 第1个月 — 把三个等级前缀写进规范。不需要配置工具，一行约定就够
  • 第1个月 — 用一句话定下批准标准。「明显改善整体代码健康度就批准」这种程度就足够
  • 第2个月 — 把每周一次的结对评审放进日程。交给自觉就不会发生
  • 第2个月 — 建一个用三行记录险些出事的渠道。格式固定下来才维持得住
  • 第3个月 — 在分配规则里加一个轮岗评审者的位子
  • 第3个月 — 按路径挂清单。不要做一份全局清单
  • 每季度 — 把「评审本来能不能拦住」作为常设项写进故障复盘

9. 没能确认的事

  • 代码评审能拦住百分之多少的缺陷，这类数字本文没有写。二手资料里流传的「评审过的代码缺陷少20~30%」之类的说法，未能在一手来源核实
  • Google的内部评审案例研究(ICSE 2018)与Microsoft的评审期待与结果研究(ICSE 2013)未能打开论文正文，因此没有引用意见类型分布或等待时间中位数之类的数字。本文中与Google相关的叙述都在公开的评审指南与Google出版的书籍范围之内
  • 「拉取请求控制在400行以内」这类被广泛引用的阈值同样未能确认一手来源，因此没有写入
  • 没有找到把评审者训练项目与对照组作比较的效果测量研究。第五节的装置是有依据的设计，而不是被测量过的处方
  • 也没有确认到比较韩国、日本、中国开发团队评审惯例的权威调查。本文提到惯例的地方是判断，不是统计

结论：评审是流程，不是性格

能拦住东西的人和拦不住的人，差别不在认真。他们有顺序，有镜头，给意见分等级，并且回看自己漏掉的东西。四件事都能学也都能教。所以评审糟糕的团队，问题不在人，而在没有流程。

组织要做的不是喊一句「仔细点」，而是把这四件事变成流程并配上预算。每周一小时结对评审、每次险些出事三行记录、一个轮岗评审位。成本就这些，在多数团队里比一个例会还便宜。

生成代码变多之后，这笔投资的价值反而涨了。要读的量变大了，表面信号消失了，靠自己代码挨批评来学习的那条路也变窄了。剩下的只有有意识的训练。

如果明天只改一件事，就改这个：下一次评审给每条意见前面加上阻断、建议、偏好之一。不需要工具也不需要约定，自己的评审一直偏向哪一侧，当场就看得见。
