定位韩文乱码发生的那一点 - cp949 与 UTF-8，两种编码错误

从乱码的形态倒推原因，并区分可复原的损伤与不可复原的损伤

2026-07-30 开发/基础设施

引言: 「乱码了」不是诊断结论

打开客户发来的 CSV，韩文全变成了奇怪的字符。这时大多数人的反应有两种：把编码设置换来换去试一遍，或者请对方重新发一次。两种都不算错，但顺序颠倒了。首先要弄清的是这个文件还能不能修。

编码错误只有两种。说这个区分就是本文的全部，也不算夸张。

  • ① 字节没错，只是解释错了。文件里原始字节完好无损，只是读取的一方套用了不相干的编码，仅在屏幕上显示得奇怪。可以完全复原。
  • ② 转换过程中信息已经消失。有人把读错的结果存了下来，或者把目标编码里没有的字符换成了问号。原文回不来了。

只看外表，两者都是「字乱了」。可是 ① 一行命令就结束，② 除了重新拿原件之外无路可走。不先判断是哪一种，就会抱着一个已经死掉的文件耗掉一整天。

本文讲的就是这个判断方法。不会说「请用 UTF-8」这种话。这条建议对已经坐在乱码屏幕前的人毫无帮助，也改变不了政府机关与银行仍然用 cp949 发文件的现实。取而代之的是一张从乱码形态倒推原因的表，而这张表的每一格都是我亲手执行填出来的。

执行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际执行的结果。shell 为 GNU bash 5.2.37 (MSYS2/MinGW64)，工具为 Node.js v22.16.0 (win32)、Python 3.13.3、GNU libiconv 1.18。系统 ANSI/OEM 代码页都是 949，shell 区域设置里 LANG 为空值，LC_CTYPE=C.UTF-8。

所有脚本都保存成文件再执行。把混有韩文与反斜杠的代码作为 shell 参数或 heredoc 传过去，会被静静改变。想了解引用规则本身，去看shell 引用规则。示例路径已改写为 /tmp/demo、~/work 这样的占位符。

本文不涉及的内容。同一个字在 Unicode 内部变成两串码点的规范化问题，在NFC 与 NFD里讲过。本文只深挖Unicode 与遗留编码之间的转换。把韩文音节当作正则范围来处理的算术在韩文正则的陷阱里，文件名里混入空格与换行导致管道崩掉的问题在find 与 xargs 的空白陷阱里。这里对文件名只看编码这一面。

可是到了「똠」就分道扬镳。这个字在 euc-kr 的基本 2,350 字之外，cp949 用 8C 63 两字节表示。而这个环境里 Python 的 euc_kr 编解码器把同一个字做成了八字节，用的是把组合用字母一个个排开的老办法。这个差异在实务里会引出什么事故，第 10 节还会再看。

1.1 cp949 根本装不下的东西

--- 1-4. what cp949 cannot hold at all ---
simplified Chinese            U+7B80 U+4F53           UnicodeEncodeError: illegal multibyte sequence
Japanese kana                 U+3042                  AA A2
NFD-decomposed 한 (3 jamo)    U+1112 U+1161 U+11AB    UnicodeEncodeError: illegal multibyte sequence
emoji U+1F600                 U+1F600                 UnicodeEncodeError: illegal multibyte sequence
euro sign U+20AC              U+20AC                  A2 E6
  • 日文假名装得下。cp949 里有日文假名区，所以 U+3042 被转换成了 AA A2。把 cp949 当成「韩文专用」就想错了
  • 欧元符号也装得下。是 A2 E6。也就是说转换失败并不是因为「不是韩国的字符」
  • 简体中文装不下。cp949 的汉字属于繁体一系，所以「简体」被拒绝了
  • 表情符号装不下。它是 Unicode 基本多文种平面之外的字符，根本没有表示方式
  • 拆成字母的韩文也装不下。只有预合成音节，组合用字母区没有映射。想把NFD 状态的字符串输出成 cp949，就会在这一点上炸掉

2. 乱码是有方向的 - 四张面孔

现在进入核心。「编码错了」不是一种情况。把哪种字节用哪种编码去读，决定了屏幕上出现的字符种类完全不同。而这个种类就在告诉你原因。

  • 方向 A（把 cp949 当 UTF-8）。cp949 的两字节组合大多不符合 UTF-8 的规则。UTF-8 要求首字节声明长度、后续字节落在特定范围内，而 cp949 的字节不守这个规则。所以大部分都变成了替换字符。九个字里有六个是替换字符
  • 方向 B（把 UTF-8 当 cp949）。cp949 是两字节两字节地切着读，所以对按三字节写下的东西会一直错位取值。而那些组合相当多会碰巧映射到有效的汉字或韩文。于是就出现像「湲덉븸」这样看着能读却没有意思的结果

这种不对称对诊断是决定性的。替换字符成堆就是方向 A，汉字与韩文混杂就是方向 B。

准确地看这两块的差别。3-1 里重新编码得到的字节与原文完全一致（True）。字节原封不动，所以只要用正确的编码再读一次，原文就回来了。

3-2 里11 字节膨胀成了 27 字节。因为一个替换字符存成 UTF-8 时要占 EF BF BD 三个字节。而决定性的一点是，这三个字节里没有任何关于它替掉了哪个字节的信息。所有失败都被抹成同一个值。所以复原在原理上不可能。

实务规则。看见替换字符是没关系的。它只是在屏幕上晃了一下，文件本身还好。危险的是把那个状态存下来。把读错的结果再写回去的那一刻，① 就变成了 ②，原件在那一刻死掉。所以对编码可疑的文件，以只读方式打开，在有把握之前不要按保存，这是第一道防线。

第三个例子很有教育意义。欧元符号在 cp949 里有，所以原样活了下来。也就是说「非韩国的字符都会坏掉」这种猜测是错的。到底什么行什么不行，必须确认才知道。

  • ignore 什么痕迹都不留。最危险。「가격 100 확정」在语法上看起来完美无缺，没人会怀疑

5. 「占쏙옙」的真身 - 双重损伤的证据

在韩国遇过编码事故的人都见过这几个字。我按步骤重现了它是从哪里来的。

--- 3-6. where the infamous string comes from ---
step 1. real cp949 text
  한글 -> cp949 C7 D1 B1 DB
step 2. some layer decodes it as UTF-8 with replacement
  -> [�ѱ�]   U+FFFD U+0471 U+FFFD
step 3. that string is saved as UTF-8
  -> EF BF BD D1 B1 EF BF BD
step 4. a later reader opens those bytes as cp949
  -> [占싼깍옙]

the replacement char alone, put through the same two steps:
  U+FFFD as utf-8 : EF BF BD
  x2              : EF BF BD EF BF BD -> [占쏙옙]
  x3              : EF BF BD EF BF BD EF BF BD -> [占쏙옙占�]
  x4              : [占쏙옙占쏙옙]
  odd counts leave a dangling byte: cp949 eats 2 at a time, UTF-8 wrote 3

结构很清楚。两个替换字符存成 UTF-8 就是 EF BF BD EF BF BD 六个字节。cp949 两字节两字节地读，于是被切成 EF BF、BD EF、BF BD 三对。按三字节为单位写下的东西被按两字节为单位读了，所以出来三个字。6 与 3 的最小公倍数是 6，所以这个模式会精确地重复。

实务上的结论很重要。看到这串字就该停止复原尝试。它是损伤叠加了两次的证据，而在第一步原始字节就已经消失。就算把第二次误读纠正过来，出来的也只是替换字符。

--- 3-7. how to tell single damage from double damage ---
what you see          U+FFFD present  recoverable   meaning
------------------------------------------------------------------------------
ÇÑ±Û                  False           True          misread only, bytes intact
replacement run       True            False         bytes already destroyed
the infamous one      False           False         bytes already destroyed

第三行里有陷阱。双重损伤的字符串里已经不剩替换字符了。因为在第二次误读的过程中，它们被映射成了正常的汉字与韩文。所以「没有替换字符所以没事」这个判断是错的。替换字符不存在，不是平安无事的证据。必须另外去识别那个特定的模式。

BOM 加上去并不是就结束了。即使正确地按 UTF-8 读，问题仍然留着。

  header[0] codepoints      : U+FEFF U+C774 U+B984

  • 打日志也看不见。必须把码点打印出来才会露出来

7.1 试着把 cp949 字节放进文件名

我想用 C7 D1 B1 DB 这串 cp949 字节创建文件，可是留在磁盘上的名字字节是 C3 87 D1 B1 C3 9B。请求的字节没有被原样存下来。把发生的事拆开来看是这样。

  • C7 是 UTF-8 双字节的起始字节，可紧跟其后的 D1 不是有效的后续字节。于是只有 C7 一个字节被当成了一个字符
  • 剩下的 D1 B1 碰巧是有效的 UTF-8 双字节组合，于是被捆成了一个字符
  • 最后的 DB 也被单独处理。结果是一个三字的名字，它又被重新编码成 UTF-8 存成了六个字节
  • 也就是说在这个环境里根本不存在所谓「cp949 文件名」。文件名一定会在边界上被重新编码

这就是文件名与文件内容的根本差别。文件内容按字节原样保存，而文件名会被操作系统改成自己的格式再存。所以内容即使用错的编码也能安全往返，名字却不行。

  • 在文件内容混着用的仓库里，同一个检索要用两种编码跑两遍才算全查
  • 根本的解决办法不是检索选项，而是把仓库统一到一种编码
  • 通配符也是同样的道理。只按扩展名找时两个都会命中，用韩文前缀找就只命中一个

8.1 PYTHONIOENCODING 改变什么、不改变什么

[PYTHONIOENCODING=cp949]

--- 6-5. what PYTHONIOENCODING does NOT change ---

[PYTHONIOENCODING=cp949]

[PYTHONUTF8=1]

需要准确的区分。PYTHONIOENCODING 只改变标准输出的编码。它不碰打开文件时的默认编码。在确认过的环境里那个值是 cp949。

  • 屏幕输出乱码的问题，可以用 PYTHONIOENCODING 修好
  • 如果问题在读写文件的编码，这个变量毫无效果。只看症状就去动这个变量是浪费时间
  • 想把文件那一侧也一起对齐到 UTF-8，需要 PYTHONUTF8=1。实跑可以看到 open() 的默认值变成了 utf-8
  • 最靠得住的办法是不依赖环境变量，在打开文件的代码里显式写明编码。环境变量会随部署环境而变

8.3 LANG 与 LC_ALL 改变什么

--- 6-6. LANG / LC_ALL effect on this toolchain ---

LC_ALL=[ko_KR.eucKR]  3  chars   /   sort:

  • 在 C 区域设置下数的是字节。UTF-8 是六个字节，所以出来 6
  • 只有在 ko_KR.UTF-8 下才按字符计数，得到 2
  • ko_KR.eucKR 把 UTF-8 字节解释成双字节字符，给出了 3 这个离谱的答案。而排序连输出都没能给出
  • 也就是说区域设置决定工具把字节捆成字符的方式。字符数、排序、大小写转换全挂在这上面

10. 在边界上只转换一次

与遗留编码共存的现实办法只有一个。在文件进来的那一点转换一次，其内侧全部假定为 UTF-8。问题在于这唯一的一次转换可能会静静地失败。

=== 9-1. plain UTF-8 to CP949, one file at a time ===
emoji.txt    FAILED: iconv: emoji.txt:1:7: cannot convert
euro.txt     OK
ext.txt      OK
zh.txt       FAILED: iconv: zh.txt:1:7: cannot convert

=== 9-2. exit codes matter. a silent pipeline loses this ===
exit code             : 1
bytes actually written:  ba b8 b0 ed bc ad 20
what got through     : 보고서
iconv stopped at the offending char and kept the prefix. truncation, not an empty file

这是最危险的行为。转换失败了，可是输出文件已经被造出来了。里面只有失败点之前的那一段。文件存在、内容也读得正常，所以能察觉它被截断的线索只有退出码。

  • 把转换自动化的流水线如果不检查退出码，就会静静地丢掉一部分数据
  • 截断发生在文件末尾，所以只打开前面看一眼的验收绝对抓不到它
  • 用管道串起来的情况下，中间命令的失败可能被掩盖。这与退出码与管道里讲的问题结构完全相同

10.1 绕过失败的三种办法

=== 9-3. the three escape hatches ===
-c           rc=1  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
//TRANSLIT   rc=0  result=[보고서 :-D]  bytes= ba b8 b0 ed bc ad 20 3a 2d 44 0a
//IGNORE     rc=0  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
-c drops it, //TRANSLIT approximates or drops, //IGNORE drops and still reports failure

//TRANSLIT 的结果很有意思。表情符号被近似写成了三个 ASCII 字符。人能读，但那不是原文。

方式失败时的行为实测退出码数据状态适用场合
不加选项在失败点中断1后面全部丢失没有。必须检查退出码
-c只丢掉搬不过去的字符1只丢那个字符明知会失败仍要推进时
//IGNORE丢掉0只丢那个字符不推荐。它把失败藏起来
//TRANSLIT换成近似写法0不是原文，但能读给人看的日志一类

最危险的组合是//IGNORE 加上不检查退出码。字符消失了却被报告为成功。反过来不加选项跑，它会告知失败，但留下的是一个已经被截断的文件。两边都不安全，所以必须另外加上验证。

  • 一边拒绝转换。理由是这个字不在基本 2,350 字里
  • 另一边转换成了八个字节。用的是在一个填充字符后面排开三个组合用字母的老办法。倒回去读能得到原文，所以没有损失
  • 问题在于字节数是四倍。流到有列长限制的地方，就会在那里被截断
  • 因此不能只把编码名字对上就安心。必须拿流水线里实际使用的工具去过一遍样本
编码名这个环境的 PythonGNU libiconv扩展音节的处理实务判断
cp949转换成两个字节转换成功按扩展区处理韩语就用这个
euc-kr转换成八字节的组合型拒绝各工具不同不要只看名字就相信
johab转换成两个字节转换成功另一套字节体系几乎不用
utf-8转换成三个字节转换成功全部都能处理拿它当内部标准

10.3 验证转换的方法

结论很简单。把转换过的东西再转回来，比较字节是否与原文相同就行。

after round trip  : f765f0504efec35848a3c116a1c98d10

这个检查几行就写完，判定也明确。在所有把转换自动化的地方都挂上这个检查，是阻止静默数据丢失的唯一办法。

12.1 与遗留编码共处之道

政府机关与银行发来的文件，今后也会是 cp949。在这个现实里要守的原则整理如下。

  1. 转换只在边界上做一次。在接收文件的那一点换成 UTF-8 存下来，之后所有代码都不知道编码这回事。一旦开始出现追问「这里是 cp949 吗」的代码，设计就已经塌了
  2. 不要在删掉原件之后才验证。把转换后的文件与原件放在一起，通过往返检查之后再清理
  3. 往外发时用对方的编码。对方期待 cp949，就在发出的边界上再转换一次。这时可能混进 cp949 里没有的字符，所以往返检查更重要
  4. 内部绝对不混用。仓库里两种编码共存，就会像第 7 节看到的那样，检索只匹配到一半
  5. 提防表情符号与简体中文。用户输入里混进这些，往 cp949 输出时一定会有损失。在输入端就拦下来并告知，比事后发现问号要好
  6. 把编码写进文档。像 6.4 节看到的，光靠字节无法确定。在收发规格里写明，才是唯一的根本解决办法

13. 本文未能确认的部分

把没确认的事写成确认过的，这篇文章就会误导下一个人。我把局限说清楚。

  • 电子表格软件的实际行为。第 6 节里用「遗留读取器」表述的东西，是我直接重现了按 cp949 解码这个行为，并不是跑某个具体的电子表格产品确认的。随产品、版本与地区设置可能不同
  • 浏览器的文档渲染。第 9 节的结果是关于脚本获取正文这条路径的。meta charset 与 HTTP 头的优先级、浏览器猜测编码的行为，没有用执行验证，所以我不下断言
  • 数据库边界。列字符集与连接字符集错开时到底存进去什么，没有确认。本文的原则（在边界转换一次、做往返验证）照样适用，但具体行为要在自己用的产品上确认
  • 压缩文件的名字编码。zip 条目名用哪种编码存储，据说各工具不同，但本文没有执行
  • 其他操作系统。第 7 节文件名被重新编码的结果，可能是这个环境特有的。在把文件名当字节串处理的系统上，结果看来会不同，但我没有确认
  • 邮件头与附件文件名。那是有另一套编码规则的领域，本文没有涉及
  • 编码自动检测库的准确度。6.4 节展示了原理上的局限，但实际工具在统计上猜得多准，我没有测量

不过这些未能确认的事项有一个共同点：全都是关于「对面那侧怎么做」的问题。而本文的诊断法并不需要知道对面的行为才能成立。直接去看字节的方法，在任何环境里都是一样的。这就是我说不要猜、去看字节的理由。

结论: 该先问的是「还能不能修」

看到乱码的屏幕，人就想先去动编码设置。可是顺序错了。第一个问题是这个文件还能不能修。答案不同，要做的事完全不同。

把执行确认到的东西总结一下。字节完好的误读全部复原了。就算已经把 cp949 字节当 latin-1 读过，只要重新编码、确认字节与原文一致，再用正确的编码读一遍，原文就原封不动地回来了。屏幕看起来再难看也一样。

相反，替换字符一旦介入，复原在原理上就不可能了。11 字节膨胀成 27 字节，而膨胀出来的字节里没有关于原值的信息。而把那个状态再读错一次，就会出现那个特定的三字模式，看到它就只有一个答案：放弃复原，重新去拿原件。为了做这个判断，从字节里数 EF BF BD 就是诊断的第五步。

所以结论不是「全都换成 UTF-8」。那行不通。对面不会变，而且光靠有效性检查也无法确定编码。现实的结论是定下一个转换点，用往返验证确认那次转换没有损失，并让其内侧不知道编码这回事。而最重要的是在猜测之前先看字节。

现在马上就能做一件事。找出转换编码的代码或脚本，看它有没有在检查那次转换的退出码。如果没有检查，那条流水线到现在为止可能一直在静静地截断数据。而这个事实，靠只打开文件前面看一眼的验收绝对暴露不出来。

# cp949 与 UTF-8 乱码诊断 — 判定表与可直接复制的命令

> 来源: braindetox.kr — 定位韩文在哪里崩掉
> 验证环境: Windows 10 / bash 5.2.37 (MSYS2) / Python 3.13.3 / Node 22.16 / GNU libiconv 1.18
> 把这个文件整份贴给 AI，然后写「按这个标准检查我们的流水线」就能用。
> ⚠ 编码可疑的文件请**以只读方式打开，没有把握之前不要保存。**一保存，可恢复的损坏就变成不可恢复的。

## 0. 前提 — 编码错误只有两种

| 种类 | 发生了什么 | 恢复 |
|---|---|---|
| **① 误读** | 字节完好，只是读取方套用了错误的编码 | **完全可以** |
| **② 丢失** | 把误读的结果保存了，或者目标编码里没有的字符被替换掉了 | **不可以** |

**先判定是哪一种。**对着第②种文件反复改编码设置是在浪费时间。

## 1. 30秒判定 — 在用编辑器打开之前先看字节

```bash
FILE=./suspect.csv

od -An -tx1 -N 16 "$FILE"                                  # 前16个字节
iconv -f UTF-8 -t UTF-8 "$FILE" >/dev/null 2>&1; echo "utf8  ok=$?"
iconv -f CP949 -t UTF-8 "$FILE" >/dev/null 2>&1; echo "cp949 ok=$?"

# 里面埋了多少个替换字符(不可恢复的信号)
od -An -tx1 "$FILE" | tr -d ' \n' | grep -o efbfbd | wc -l
```

- `ok=0` 表示按该编码是有效的
- 前三个字节是 `EF BB BF` 就是 **UTF-8 BOM** — 编码由此确定(唯一的积极信号)
- 最后一行**大于零，这个文件就已经死了。**去重新索取原始文件

## 2. 乱码的样子 → 反查原因

| 屏幕上看到的 | 例子 | 原因 | 确认方法 | 恢复 |
|---|---|---|---|---|
| 带问号的菱形连成一串 | `�ѱ� ���ڵ�` | cp949 字节被当作 UTF-8 读 | `iconv -f CP949 -t UTF-8` | 只是显示则**可以** |
| 大写带音符拉丁字母加符号 | `ÇÑ±Û ÀÎÄÚµù` | cp949 字节被当作 latin-1 一类读 | 用 latin-1 重新编码再按 cp949 解码 | **可以** |
| 小写带音符拉丁字母 | `ê¸ˆì•¡` | UTF-8 字节被当作 latin-1 一类读 | 用 latin-1 重新编码再按 UTF-8 解码 | **可以** |

| 首个单元格前多出三个杂字 | `ï»¿이름` | UTF-8 BOM 被当作 latin-1 一类读 | 前三个字节 | **可以**(只需去掉 BOM) |

| 完全没有输出 | (空行加异常) | 输出编码无法表示该字符，进程崩溃 | 退出码、标准错误 | 数据**完好** |

**大小写告诉你方向。**小写带音符拉丁字母 → 原文是 UTF-8。大写带音符拉丁字母 → 原文是 cp949。

## 3. 恢复 — 只发生了误读的情况

```python
# repair.py — 把显示错误的字符串还原成原文
import sys

seen = sys.argv[1]              # 你看到的那个错误字符串
raw = seen.encode('latin-1')    # 把字节原样复活
print(raw.decode('cp949'))      # 用正确的编码重新读
```

```bash
python repair.py "ÇÑ±Û ÀÎÄÚµù"      # -> 한글 인코딩
```

- **一定要用 `latin-1`。**它能让全部 256 个字节值往返无损
- `cp1252` 有五个字节(`81 8D 8F 90 9D`)没有定义字符，**在恢复过程中反而会丢数据**
- 如果乱掉的是 UTF-8 字节，把最后一行改成 `decode('utf-8')`
- 整个文件的话，先用 `iconv -f ISO-8859-1 -t UTF-8` 还原，然后重新判定

## 4. 判定为不可恢复 — 到此为止

```bash
# 只要替换字符被保存过，原始字节就已经消失了
od -An -tx1 "$FILE" | tr -d ' \n' | grep -c efbfbd

# 双重损坏的痕迹(替换字符又被按 cp949 读了一遍)
grep -c '占쏙옙' "$FILE"
```

任意一条命中，就**不要再尝试恢复。**原因：

- 替换字符保存时变成 `EF BF BD` 三个字节，而这三个字节**不带任何关于原始字节的信息**
- 所有不同的失败都被压成同一个值。实测中 11 字节的原文膨胀成了 27 字节
- `占쏙옙` 这一类里**已经没有替换字符了** — 第二次误读把它们映射成了正常的字，所以**没有替换字符并不等于文件没事**

## 5. 只在边界转换一次 — 一种不会截断的写法

```bash
# 坏写法: 失败了文件照样会生成(只含前半部分的截断文件)
iconv -f CP949 -t UTF-8 in.csv > out.csv

# 好写法: 失败就不留下产物
set -Eeuo pipefail
TMP=$(mktemp)
if iconv -f CP949 -t UTF-8 in.csv > "$TMP"; then
  mv "$TMP" out.csv
else
  rm -f "$TMP"
  echo "转换失败 — 请检查原始文件" >&2
  exit 1
fi
```

**不检查退出码，数据就会静悄悄地消失。**截断发生在文件末尾，只看开头几行的抽查永远发现不了。

| 方式 | 失败时 | 实测退出码 | 数据 | 判断 |
|---|---|---|---|---|
| 不加选项 | 在失败处中断 | 1 | **后面的全部丢失** | 必须检查退出码 |
| `-c` | 丢掉转不了的字符 | 1 | 只丢那个字符 | 明知情况仍要继续时 |
| `//IGNORE` | 丢掉 | 0 | 只丢那个字符 | **不推荐**(它隐藏了失败) |
| `//TRANSLIT` | 换成近似写法 | 0 | 不是原文 | 仅限给人看的日志 |

## 6. 往返校验 — 凡是做转换的地方都加上

```bash
# 确认这次转换是无损的
roundtrip_ok() {
  local src="$1"
  iconv -f UTF-8 -t CP949 "$src" 2>/dev/null | iconv -f CP949 -t UTF-8 | cmp -s - "$src"
}

if roundtrip_ok data.csv; then
  echo "无损 — 可以发出去"
else
  echo "有损 — 去查清哪些字符会消失" >&2
  iconv -c -f UTF-8 -t CP949 data.csv | iconv -f CP949 -t UTF-8 | diff - data.csv
fi
```

导出成 cp949 时**必然消失的**：表情符号、简体中文、被拆成字母的韩文。
**出乎意料能活下来的**：欧元符号(`A2 E6`)、日语假名。「凡是非韩国的字符都会乱」这种猜测是错的。

## 7. CSV 与 BOM

```bash
# 加上 BOM(告诉表格程序这是 UTF-8)
printf '\xEF\xBB\xBF' | cat - body.csv > with_bom.csv

# 去掉 BOM
sed '1s/^\xEF\xBB\xBF//' with_bom.csv > no_bom.csv

# 查看前三个字节
od -An -tx1 -N 3 with_bom.csv
```

```python
# 防止 BOM 以 U+FEFF 的形式粘在第一个列名上
import csv

with open('report.csv', encoding='utf-8-sig', newline='') as f:   # sig 是关键
    for row in csv.DictReader(f):
        print(row['이름'])        # 用 utf-8 打开时这个取值会返回 None
```

- BOM 是 **UTF-8 的标记**。加在 cp949 文件前面，这个文件就既不是有效的 UTF-8 也不是有效的 cp949
- 即使正确地按 UTF-8 解码，BOM 仍会作为 `U+FEFF` 字符**留在第一个列名前面**
- 症状**只出现在第一列**。第二、第三列都正常，因此很难找到原因
- `U+FEFF` 不属于空白字符，所以**去掉首尾空格是抓不到它的**

## 8. 只靠有效性检查无法确定编码

有 **345** 个韩文音节，它们的 cp949 字节序列同时也是有效的 UTF-8。你确实可以构造出在两种编码下都能无错读出的文本。

```
징 -> cp949 C2 A1   同样的字节按 UTF-8 读得到 U+00A1
징짖짙짚 -> C2 A1 C2 A2 C2 A3 C2 A4   (utf-8 有效 · cp949 有效 · 两者都是)
```

→ 「先试 UTF-8，失败就退回 cp949」是**猜测**，不是判定程序。没有 BOM，剩下的就只是概率。**把编码写进交换规范才是唯一的根本解法。**

## 9. 每个边界由谁决定编码

| 边界 | 由谁决定 | 陷阱 |
|---|---|---|
| 写文件 | 写入的程序 | 同一台机器上 Python 写成 cp949，Node 写成 UTF-8 |
| 文件名 | 操作系统 | 名字在边界上会**被重新编码。**不像文件内容那样保留字节 |
| Shell 输出 | 代码页加程序 | 代码页和区域设置可能在同一台机器上互相矛盾 |
| **管道** | **没有人决定** | **根本没有地方声明。**只能把两端的约定写进代码 |
| HTTP 头 | 服务器声明 | 客户端**可以无视它。**把正文按字节接收，自己解码 |
| CSV 开头 | 写入方 | BOM 是唯一的信号 |
| 转换工具 | 具体实现 | **同一个名字行为不同**(见下) |

## 10. 不要相信编码的名字

| 名字 | Python | GNU libiconv | 判断 |
|---|---|---|---|
| `cp949` | 扩展音节用 2 字节 | 成功 | **韩文就用这个** |
| `euc-kr` | 扩展音节用 **8 字节**的组合形式 | **拒绝** | 别只看名字就相信 |
| `johab` | 2 字节，另一套体系 | 成功 | 几乎不用 |
| `utf-8` | 3 字节 | 成功 | **把它定为内部标准** |

同样叫「EUC-KR」，一边拒绝转换，另一边转成了 8 字节。虽然没有丢失，但**字节数是四倍**，在有列长限制的地方就会被截断。**应该拿样本走一遍流水线里真正使用的那个工具。**

## 11. Shell 与输出编码

| 设置 | 改变的 | 不改变的 |
|---|---|---|
| `PYTHONIOENCODING` | 只改标准输出的编码 | **打开文件时的默认编码** |
| `PYTHONUTF8=1` | 输出加上 `open()` 的默认值 | — |
| `LC_ALL` / `LANG` | 工具把字节组合成字符的方式(字数、排序) | 文件内容 |
| `chcp` | 控制台代码页 | 管道里流动的字节的含义 |

- 只是屏幕输出乱，就用 `PYTHONIOENCODING`；如果问题在文件读写上，**这个变量毫无作用**
- 最可靠的做法是不依赖环境变量，**在打开文件的代码里明确写出编码**
- 指定一个无法表示该文本的输出编码，结果不是乱码而是**进程直接死掉。**退出码非零且输出为空，说明**数据是完好的**
- Node 没有这种开关，一直按 UTF-8 写 → 用管道把它接到 Python，那里就是事故点

## 12. 检查清单

- [ ] 收到坏文件时，**先开 `od` 而不是编辑器**
- [ ] 数了 `efbfbd` 的个数，**先判定能不能恢复**
- [ ] 恢复时用的是 **`latin-1`** 而不是 `cp1252`
- [ ] 可疑文件是**以只读方式**打开的，没有把误读的状态保存下来
- [ ] 转换脚本会**检查退出码**
- [ ] 转换加了**往返校验**，失败时不留下产物
- [ ] 删掉原始文件之前先通过了校验
- [ ] 读 CSV 时指定了**能去掉 BOM 的编解码器**
- [ ] 仓库里**不混用两种编码**(否则搜索只能命中一半)
- [ ] 在导出 cp949 之前，先筛出用户输入里的**表情符号和简体中文**并给出提示
- [ ] 交换规范文档里**写明了编码**
- [ ] 把文件名的编码和文件内容的编码当作**两个独立问题**处理

## 13. 不要这样做

- ❌ 看到乱码就**先去改编码设置** — 先判定还能不能修
- ❌ 把可疑文件在编辑器里打开然后**保存** — 第①种会变成第②种
- ❌ `//IGNORE` 配上**不检查退出码** — 字符都丢了却报告成功
- ❌ 「没抛异常所以是 UTF-8」 — 在那 345 个音节的区间里会静静地判错
- ❌ 只把编码名字对上，却**不验证工具的实际行为**
- ❌ **只看文件开头**的抽查 — 截断发生在末尾
- ❌ 在已判定不可恢复的文件上耗时间 — 去重新索取原始文件
