원격 URL에 토큰이 박혀 있다 - git 자격증명이 새는 자리

파일만 지우면 되는 문제가 아니다. 여섯 자리를 실제 출력으로 확인하고 사고 뒤의 순서를 정한다

2026-09-01 개발/인프라

자격증명 유출 이야기는 대개 커밋된 파일에서 시작해서 커밋된 파일에서 끝난다. .env 를 실수로 넣었다, 히스토리에서 빼냈다, 끝. 그런데 실무에서 토큰이 밖으로 나가는 경로를 세어 보면 파일은 여섯 개 중 하나일 뿐이다. 나머지 다섯은 파일 관리를 아무리 잘해도 걸리지 않는다.

가장 자주 걸리는 자리는 원격 URL 이다. 한 번 급해서 https://사용자:토큰@호스트/... 형태로 클론해 두면 그 문자열은 저장소의 설정 파일에 평문으로 눌러앉고, 그 뒤로 git remote -v 를 칠 때마다 화면에 다시 나온다. 화면 공유 중에도 나오고, 붙여 넣은 로그에도 나온다.

여기서는 그 여섯 자리를 하나씩 짚고, 각각을 실제로 실행해 확인한 출력을 붙인다. 그리고 마지막에 가장 중요한 것을 정리한다. 이미 새 버린 뒤의 순서다. 그 순서에서 파일을 지우는 일은 1번이 아니다.

이 글의 모든 예제는 명백히 가짜인 값과 존재하지 않는 호스트(.invalid)만 쓴다. 실습은 임시 디렉터리에서 HOME 을 따로 잡아 격리한 채 돌렸고, 붙인 출력에서는 홈 경로만 ~ 로 줄였다. 공격 방법이 아니라 자기 환경을 점검하는 방법을 다룬다.

새는 자리는 파일만이 아니다

먼저 지도를 그려 둔다. 아래 여섯 자리는 성격이 서로 다르다. 어떤 것은 저장소 안에 있고 어떤 것은 저장소 밖에 있으며, 어떤 것은 내 손으로 지울 수 있고 어떤 것은 남의 서버에 있다. 막는 방법이 자리마다 다르다는 것이 이 표의 요점이다.

새는 자리어디에 남는가내 손으로 지울 수 있는가막는 법
커밋된 파일커밋 객체. 클론한 모든 사본재작성해도 남의 사본은 불가커밋 전에 막는다. 무시 규칙을 먼저 둔다
원격 URL 의 토큰.git/config. 화면 출력마다가능. 값이 통째로 교체된다set-url 로 자격증명 없는 URL
.git/config작업 디렉터리 안 평문 파일가능헬퍼에 맡기고 URL 에는 넣지 않는다
셸 히스토리홈 디렉터리 히스토리 파일가능. 다만 잊기 쉽다명령줄에 비밀을 두지 않는다
CI 로그CI 제공자의 서버보존 정책에 따라 다르다추적 출력을 켜지 않는다
커밋 메시지·이슈커밋 객체, reflog, 이슈 서버reflog 는 가능. 서버는 별개붙여 넣기 전에 한 번 읽는다

이 글은 두 번째와 세 번째 줄에 가장 많은 지면을 쓴다. 첫 번째 줄, 즉 이미 추적되고 있는 파일을 빼내는 절차는 무시 규칙을 나중에 추가해도 이미 추적 중인 파일은 빠지지 않는다는 이야기에서 따로 다뤘다. 그 글의 결론이 여기의 출발점이다. 빼내도 히스토리에는 남고, 그래서 키 교체가 먼저다.

확인한 환경

아래 출력은 전부 실제로 실행해 나온 것이다. 지어낸 줄은 없다. 다만 가짜 토큰과 존재하지 않는 호스트를 썼기 때문에 네트워크가 필요한 명령은 이름 해석 단계에서 멈춘다. 그 점이 오히려 편해서, 자격증명이 접속 전에 이미 어디에 기록되는지만 깨끗하게 볼 수 있다.

  • git — 2.48.1.windows.1
  • 셸 — GNU bash 5.2.37(1)-release, Git Bash
  • 플랫폼 — MINGW64_NT-10.0-19045 (Windows 10 위의 MSYS 환경)
  • 시점 — 2026년 9월
  • 격리 — 임시 디렉터리에 새 저장소를 만들고 HOME 을 그 안으로 돌려서, 실제 홈의 설정과 자격증명 파일을 건드리지 않았다

플랫폼이 리눅스나 macOS 면 다르게 나오는 대목이 두 군데 있다. 파일 권한 표시와 OpenSSH 의 개인키 권한 검사다. 해당 절에서 각각 짚는다.

git remote -v 가 토큰을 그대로 보여준다

가장 흔한 시작은 이렇다. 대화형 인증이 귀찮거나 자동화 스크립트에서 붙어야 해서, 토큰을 URL 안에 넣어 클론한다. 동작은 한다. 문제는 그 값이 어디에 남는지다.

$ git remote add origin "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (fetch)
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (push)

$ cat .git/config
[core]
        repositoryformatversion = 0
        filemode = false
        bare = false
        logallrefupdates = true
[remote "origin"]
        url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

$ git config --get remote.origin.url
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

세 가지가 한꺼번에 드러난다. 첫째, remote -v 는 토큰을 가리지 않는다. fetch 줄과 push 줄에 두 번 나온다. 둘째, .git/config 는 암호화되지 않은 텍스트 파일이고 그 안에 토큰이 그대로 들어간다. 셋째, git config --get 같은 평범한 조회 명령도 같은 값을 뱉는다.

위험은 명령 자체가 아니라 그 명령이 실행되는 상황에 있다. git remote -v 는 문제가 생겼을 때 가장 먼저 치는 명령 중 하나다. 즉 도움을 청하는 순간, 화면을 공유하는 순간, 이슈에 로그를 붙이는 순간에 실행된다. 토큰이 밖으로 나가기 좋은 조건이 정확히 그때 갖춰진다.

  • 같은 값이 백업과 동기화 폴더에도 따라간다. 작업 디렉터리를 통째로 백업하면 .git/config 도 같이 간다
  • 여러 원격을 등록해 두면 잊은 쪽에 남는다. upstream 이나 오래된 backup 원격이 흔한 자리다
  • 편집기와 IDE 의 저장소 정보 화면도 같은 값을 읽어 표시한다

원격 URL 을 고치는 법

고치는 명령 자체는 한 줄이다. git remote set-url 로 자격증명이 없는 URL 을 다시 넣으면 된다. 확인해 볼 값어치가 있는 것은 옛 값이 정말 사라지는가 쪽이다. 설정 파일을 손으로 고치다 보면 옛 줄이 주석으로 남거나 다른 키에 복사되는 일이 있어서다.

$ git remote set-url origin "https://git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://git.example.invalid/demo/demo.git (fetch)
origin  https://git.example.invalid/demo/demo.git (push)

$ cat .git/config
[remote "origin"]
        url = https://git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

# .git 디렉터리 전체에 옛 값이 남아 있는지 확인
# (원격 추가와 set-url 만 한 깨끗한 저장소에서)
$ grep -rl 'ghp_EXAMPLE' .git/
(출력 없음)

깨끗하게 교체된다. set-url 은 url 값을 통째로 갈아 끼우기 때문에 옛 문자열이 남지 않고, 커밋 객체와도 무관하다. 원격을 추가한 직후에 검색하면 .git/config 한 건이 잡히고, set-url 이후에는 한 건도 잡히지 않는다.

다만 여기서 안심하면 안 된다. 저장소 안이 깨끗해진 것이지 그 토큰이 깨끗해진 것이 아니다. 그 URL 을 명령줄에 쳤다면 셸 히스토리에 있고, CI 에서 썼다면 로그에 있을 수 있다. 값이 어디까지 갔는지 확신할 수 없다면 정리보다 폐기가 먼저다.

  • 원격이 여럿이면 전부 확인한다. git remote -v 는 등록된 모든 원격을 보여 준다
  • 서브모듈이 있으면 각 서브모듈의 설정도 별도다. .gitmodules 와 각 서브모듈 디렉터리를 같이 본다
  • 바꾼 뒤에는 인증을 어떻게 할지 정해 둬야 한다. 헬퍼에 맡기는 것이 기본이고, 자동화라면 SSH 키 쪽이 낫다

자격증명 헬퍼가 어디에 무엇을 남기는가

URL 에 토큰을 넣지 않으면 git 은 자격증명 헬퍼에게 묻는다. 여기서 선택이 갈린다. 공식 문서 기준으로 git 이 직접 들고 다니는 헬퍼는 둘이고, 나머지는 운영체제 쪽 보안 저장소와 연동되는 것들이다.

헬퍼어디에 두는가지속평문인가어울리는 자리
store홈의 .git-credentials 파일지울 때까지그렇다권할 자리가 거의 없다
cache메모리. 보조 프로세스가 들고 있다지정한 시간디스크에 안 씀공유 장비, 짧은 작업
OS 키체인 연동운영체제의 보안 저장소계정에 묶임아니다개인 작업 장비의 기본
URL 에 직접.git/config지울 때까지그렇다없다. 이 글의 주제

store 가 정확히 무엇을 남기는지는 직접 넣어 보면 분명해진다. 헬퍼는 표준 입력으로 키와 값을 받는 단순한 규약이라, 네트워크에 붙지 않고도 저장과 조회를 그대로 재현할 수 있다.

$ git config --global credential.helper store

# 헬퍼 규약대로 가짜 자격증명을 한 건 넣는다 (네트워크 접속 없음)
$ printf 'protocol=https\nhost=git.example.invalid\nusername=demo-user\npassword=ghp_EXAMPLE0000000000000000000000000000\n\n' \
    | git credential-store store

$ stat -c '%a %n' ~/.git-credentials
644 ~/.git-credentials

$ cat ~/.git-credentials
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid

# 되읽기도 그대로 된다
$ printf 'protocol=https\nhost=git.example.invalid\n\n' | git credential-store get
username=demo-user
password=ghp_EXAMPLE0000000000000000000000000000

파일 한 줄이 곧 https://사용자:비밀번호@호스트 형태다. 즉 원격 URL 에 토큰을 박아 두는 것과 저장 형식이 사실상 같다. 다른 점은 위치뿐이다. git 공식 문서도 이 헬퍼에 대해 비밀번호를 암호화하지 않은 채 디스크에 저장하며 파일 시스템 권한으로만 보호된다고 적고, 그것이 받아들일 수 없는 절충이면 cache 를 쓰거나 운영체제의 보안 저장소와 연동되는 헬퍼를 찾으라고 권한다.

권한 숫자에는 주의가 필요하다. 위 출력의 644 는 이 Windows·MSYS 환경에서 stat 이 그렇게 보고한 값이다. 공식 문서는 이 파일의 권한이 다른 사용자가 읽지 못하도록 설정된다고만 적고 구체적인 숫자를 명시하지 않는다. 리눅스에서 같은 값이 나오는지는 확인하지 않았다. 어느 쪽이든 결론은 바뀌지 않는다. 파일을 읽을 수 있는 주체에게는 토큰이 그대로 보인다.

  • 저장 위치는 홈의 .git-credentials 가 우선이고, 없으면 설정 디렉터리 아래의 git/credentials 도 쓰인다. 백업 대상에서 빼 두는 편이 낫다
  • 지울 때는 파일을 손으로 여는 대신 헬퍼에 erase 를 넘기면 해당 항목만 빠진다
  • Git for Windows 는 시스템 설정에 manager 가 기본으로 잡혀 있다. 이 환경에 함께 설치된 헬퍼는 cache, store, manager, 그리고 선택기 하나였다
  • 여러 헬퍼를 겹쳐 지정하면 git 은 답을 얻을 때까지 차례로 물어본다. 옛 store 설정이 남아 있으면 그쪽이 먼저 답할 수 있다

SSH 키 쪽에서 갈리는 것

SSH 로 붙으면 URL 에 토큰을 넣을 일이 없어서 앞의 문제 대부분이 사라진다. 대신 다른 자리가 생긴다. 개인키 파일 그 자체다. 여기서 갈리는 것은 딱 하나, 패스프레이즈가 있느냐다.

# 패스프레이즈 없이 열리는가 (-y 는 개인키에서 공개키를 유도한다)
$ ssh-keygen -y -P "" -f ~/.ssh/id_nopass >/dev/null 2>&1 \
    && echo "패스프레이즈 없음" || echo "패스프레이즈 필요"
패스프레이즈 없음

$ ssh-keygen -y -P "" -f ~/.ssh/id_pass >/dev/null 2>&1 \
    && echo "패스프레이즈 없음" || echo "패스프레이즈 필요"
패스프레이즈 필요

# 이 호스트에 실제로 어떤 키가 쓰이는지 (설정을 해석한 결과)
$ ssh -G demo | grep -E '^(hostname|user|identityfile)'
user git
hostname git.example.invalid
identityfile ~/.ssh/id_demo

패스프레이즈가 없는 키는 파일을 손에 넣은 쪽이 곧바로 쓸 수 있고, 있는 키는 한 겹이 더 있다. 이 차이는 노트북 분실이나 백업 유출처럼 파일이 통째로 넘어가는 상황에서만 드러나는데, 그것이 실제로 일어나는 상황이다. 매번 입력하는 것이 부담이면 에이전트에 한 번 올려 두면 된다.

두 번째 명령이 더 실용적이다. ssh -G 는 설정 파일을 해석한 최종 결과를 보여 준다. 키가 여러 개일 때 어떤 호스트에 어떤 키가 쓰이는지는 추측하지 말고 이렇게 확인하는 편이 빠르다.

권한도 하나 짚어 둔다. 이 환경에서 개인키를 644 로 바꾸고 접속을 시도했을 때 OpenSSH 는 권한을 문제 삼지 않고 곧장 호스트 이름 해석 실패로 넘어갔다. MSYS 가 권한을 흉내 내는 탓으로 보이며, 리눅스나 macOS 의 동작은 확인하지 않았다. 어느 쪽이든 개인키를 다른 사용자가 읽을 수 있게 두는 것은 좋을 것이 없다.

자격증명범위기본 권한수명쓰는 자리
개인 SSH 키그 사용자가 닿는 모든 저장소사용자 권한 전부직접 지울 때까지사람의 작업 장비
배포 키저장소 하나읽기 전용이 기본. 쓰기 부여 가능직접 지울 때까지서버 한 대, 저장소 하나
세분화된 토큰사용자 또는 조직 하나, 지정한 저장소항목별로 지정기본 30일, 최대 366일 또는 없음자동화, 외부 연동
고전 토큰닿는 조직의 모든 저장소넓은 범주 단위선택. 1년 미사용 시 자동 제거줄여 나갈 자리

배포 키가 유용한 이유가 이 표에 있다. 개인 키는 그 사람이 닿는 모든 저장소로 열리는 반면, 배포 키는 저장소 하나에 붙고 기본이 읽기 전용이다. 서버 한 대가 저장소 하나를 내려받기만 하면 되는 흔한 배포 구성에서, 개인 키를 복사해 넣는 것과 배포 키를 만드는 것은 사고가 났을 때 피해 범위가 다르다.

토큰의 수명과 범위

여기까지가 새지 않게 하는 이야기였다면, 이 절은 새더라도 작게 만드는 이야기다. 유출 사고의 크기를 정하는 것은 대개 유출 그 자체가 아니라 그 자격증명이 무엇을 할 수 있었느냐와 언제까지 유효하냐다. 이 둘은 토큰을 만드는 화면에서 이미 정해진다.

2026년 9월 기준 GitHub 문서를 보면 세분화된 개인 액세스 토큰은 사용자 또는 조직 하나가 소유한 자원으로 한정되고, 그 안에서도 지정한 저장소에만 닿으며, 권한을 항목 단위로 준다. 반면 고전 토큰은 넓은 범주 단위로 동작해서 그 사용자가 닿는 조직의 모든 저장소로 열린다. 같은 문서가 만료 설정을 강력히 권장한다고 적고 있고, 세분화된 토큰은 기본이 30일에 최대 366일 또는 만료 없음까지 고를 수 있다. 고전 토큰도 만료는 선택이지만 1년 동안 쓰이지 않은 토큰은 자동으로 제거된다.

조직 단위로 보면 다른 층이 하나 더 있다. 조직 소유자는 세분화된 토큰이 조직 자원에 접근할 때 승인을 받도록 요구할 수 있고, 고전 토큰의 조직 접근을 제한할 수 있으며, 최대 수명 정책을 걸고, 조직에 걸린 토큰을 검토하고 폐기할 수 있다. 개인이 만든 토큰이 개인 안에서 끝나지 않는다는 뜻이고, 조직 쪽에서 보면 이것이 사고 대응의 유일한 지렛대인 경우가 많다.

  • 만료 없음은 편의가 아니라 부채다. 지금 편한 대신 폐기 시점을 영원히 미룬다
  • 권한은 지금 필요한 것만 준다. 미리 넓게 주면 줄일 계기가 생기지 않는다
  • 용도마다 토큰을 나눈다. 하나를 여기저기 쓰면 폐기할 때 무엇이 같이 멈추는지 알 수 없어 폐기를 미루게 된다
  • 토큰에 용도를 알 수 있는 이름을 붙인다. 사고가 났을 때 목록에서 골라내는 속도가 달라진다
  • 사람이 쓰는 자격증명과 자동화가 쓰는 자격증명을 섞지 않는다. 사람이 퇴사하면 자동화가 같이 멈춘다

CI 에서 새는 방식

CI 는 자격증명이 가장 많이 지나다니면서 출력이 자동으로 보관되는 곳이다. 이 조합이 위험하다. 로컬이면 스크롤을 올려야 보이는 것이 CI 에서는 링크 하나로 남는다.

가장 흔한 사고는 디버깅하려고 추적 옵션을 켜 두는 것이다. 셸의 set -x 는 실행 직전의 명령을 변수를 펼친 채로 찍는다.

$ cat ci_demo.sh
#!/bin/bash
set -x
TOKEN="ghp_EXAMPLE0000000000000000000000000000"
git ls-remote "https://x-access-token:${TOKEN}@git.example.invalid/demo/demo.git"

$ bash ci_demo.sh
+ TOKEN=ghp_EXAMPLE0000000000000000000000000000
+ git ls-remote https://x-access-token:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

대입하는 줄에서 한 번, 쓰는 줄에서 또 한 번 찍힌다. 변수에 담아 뒀다고 가려지지 않는다. set -x 의 목적 자체가 펼쳐진 값을 보여 주는 것이기 때문이다.

git 자신의 출력은 어떤가. 여기서 결과가 갈린다. 오류 메시지는 자격증명을 지우고 보여 주는데, 추적 출력은 그렇지 않다.

# git 자신의 오류 메시지는 자격증명 부분을 지운다
$ git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
fatal: unable to access 'https://git.example.invalid/demo/demo.git/': Could not resolve host: git.example.invalid

# 그러나 GIT_TRACE 는 지우지 않는다
$ GIT_TRACE=1 git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
trace: built-in: git ls-remote https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
trace: run_command: GIT_DIR=.git git remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...
trace: exec: git-remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...

오류 메시지에서 demo-user:ghp_...@ 부분이 통째로 빠진 것을 볼 수 있다. 반대로 추적을 켜면 같은 URL 이 여러 줄에 걸쳐 온전히 나온다. 문제가 안 풀려서 추적을 켜는 순간이 대개 급한 순간이고, 급한 순간의 출력이 그대로 CI 기록에 남는다.

CI 제공자의 마스킹이 있으니 괜찮다고 생각하기 쉬운데, 그 기능에는 경계가 있다. GitHub 문서는 시크릿이 아닌 민감한 값은 별도의 지시자로 직접 가려야 한다고 적고, 큰 시크릿을 파일로 다루는 우회 방법을 설명하는 대목에서는 로그에 출력된 시크릿은 가려 주지 않는다고 명시한다. 명령줄로 시크릿을 전달하는 방식도 프로세스 목록에 보일 수 있다고 경고한다.

  • 마스킹은 등록된 문자열과 정확히 일치할 때 작동한다. 값을 잘라 쓰거나 인코딩하면 같은 값이라도 다른 문자열이 된다
  • 그래서 마스킹은 안전망이지 설계가 아니다. 애초에 찍지 않는 쪽이 먼저다
  • 추적 옵션은 필요한 구간에만 켠다. 스크립트 맨 위에 두면 전체가 대상이 된다
  • 자격증명은 명령줄 인자 대신 환경변수나 표준 입력으로 넘긴다
  • 실패한 실행의 로그가 더 위험하다. 성공한 로그는 잘 안 열어 보지만 실패 로그는 여기저기 붙여 공유된다
  • 포크에서 온 실행에는 시크릿이 전달되지 않는 것이 기본이다. 이 제약을 우회하려는 설정이 사고로 이어진다

셸 히스토리와 프로세스 목록

토큰이 들어간 명령을 한 번이라도 치면 그 줄은 히스토리 파일로 간다. 이 자리가 잘 잊히는 이유는 저장소 밖이기 때문이다. 저장소를 아무리 깨끗이 정리해도 홈 디렉터리의 히스토리 파일은 그대로 남는다.

이 환경의 Git Bash 에서 HISTCONTROL 은 설정되어 있지 않았다. 이 변수에 ignorespace 가 들어 있으면 공백으로 시작하는 명령은 히스토리에 남지 않는데, 기본값으로 기대할 동작은 아니라는 뜻이다. 셸과 배포판마다 다르므로 자기 환경에서 확인하는 편이 낫다.

  • 토큰을 명령줄에 직접 치는 대신 파일이나 표준 입력으로 넘긴다. 히스토리와 프로세스 목록 양쪽을 한 번에 피한다
  • 이미 쳤다면 히스토리에서 그 줄을 지운다. 다만 지우는 것은 두 번째 일이고, 폐기가 첫 번째 일이다
  • 원격 접속 도구가 세션 로그를 파일로 남기도록 설정되어 있으면 그쪽에도 같은 줄이 있다. 터미널 기록은 흔히 잊는 자리다

커밋 메시지 - reflog 라는 두 번째 사본

파일이 아니라 커밋 메시지에 값을 적는 경우가 있다. 임시로 무엇을 시험했는지 적어 두다가 값을 그대로 옮기는 식이다. 파일 검사기는 이것을 보지 못한다. 메시지는 파일이 아니라 커밋 객체의 일부이기 때문이다.

여기서 한 겹이 더 있다. reflog 다. git 은 참조가 움직인 이력을 .git/logs/ 아래에 따로 기록하는데, 그 기록에 커밋 메시지의 첫 줄이 같이 들어간다. 즉 커밋을 다시 쓰거나 되돌려도 사본이 하나 더 남아 있다.

$ git commit --allow-empty -m "oops ghp_EXAMPLE0000000000000000000000000000"

$ grep -rl 'ghp_EXAMPLE' .git/
.git/logs/HEAD
.git/logs/refs/heads/main

$ git reflog --format='%gd %gs' | head -2
HEAD@{0} commit: oops ghp_EXAMPLE0000000000000000000000000000
HEAD@{1} commit (initial): init

# reflog 를 만료시키고 정리를 돌린 뒤
$ git reflog expire --expire=now --all
$ git gc --prune=now
$ grep -rl 'ghp_EXAMPLE' .git/
(출력 없음)

두 파일에 남아 있다가, 만료와 정리를 거치면 사라진다. 이 실험에서 배울 것은 reflog 를 지우는 방법이 아니라 그 반대다. 커밋을 다듬어 로그가 깨끗해 보여도 저장소 안에 사본이 남을 수 있다는 사실이다. 그리고 이 정리는 내 저장소에서만 유효하다. 이미 푸시했다면 서버와 다른 사람의 사본에는 그대로 있다.

  • 같은 이유로 이슈·풀 리퀘스트 본문과 댓글, 채팅에 붙인 로그도 각각 별개의 사본이다. 편집해도 편집 이력이 남는 서비스가 많다
  • 메시지에 값을 적어야 할 상황은 사실상 없다. 무엇을 했는지는 적고 무슨 값을 썼는지는 적지 않는다
  • 정리 명령은 되돌릴 수 없다. reflog 는 사고 복구의 마지막 수단이기도 하므로 급하지 않다면 함부로 만료시키지 않는다

커밋 전에 잡는 법

지금까지의 모든 대응은 이미 벌어진 뒤의 이야기다. 비용이 훨씬 싼 쪽은 들어가기 전에 막는 것이다. 순서는 셋이다. 무시 규칙을 먼저 두고, 훅으로 스테이지를 검사하고, 자동 검사에 맡긴다.

훅은 생각보다 짧다. 아래는 스테이지에 올라온 추가 줄만 보고 자격증명이 들어간 URL 형태와 개인키 머리글을 찾으면 커밋을 중단하는 예다.

$ cat .git/hooks/pre-commit
#!/bin/sh
if git diff --cached -U0 \
   | grep -nE '^\+.*(://[^/@[:space:]]+:[^/@[:space:]]+@|-----BEGIN [A-Z ]*PRIVATE KEY-----)'; then
  echo "pre-commit: 자격증명으로 보이는 문자열이 스테이지에 있다. 중단한다." >&2
  exit 1
fi
exit 0

$ git add deploy.conf && git commit -m "add deploy conf"
7:+url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
pre-commit: 자격증명으로 보이는 문자열이 스테이지에 있다. 중단한다.
$ echo $?
1

# 같은 파일에서 자격증명만 뺀 경우
$ git add deploy.conf && git commit -m "add deploy conf"
committed OK

걸리는 줄을 번호와 함께 보여 주고 종료 코드 1 로 커밋을 막는다. 자격증명을 뺀 같은 파일은 통과한다.

다만 한계는 분명하다. 훅은 저장소마다 따로 두는 것이라 클론하면 따라오지 않고, 우회할 수 있으며, 패턴에 없는 형태는 놓친다. 실수를 줄이는 장치이지 보증이 아니다. 조직 단위로는 서버 쪽에서 푸시를 검사하는 기능과 전용 시크릿 스캐너를 함께 쓰는 것이 일반적이고, 그런 도구는 제공자별 토큰 형태를 알고 있어 손으로 쓴 패턴보다 폭이 넓다.

  • 무시 규칙은 파일을 만들기 전에 둔다. 만든 뒤에 추가하면 이미 추적 중인 파일은 빠지지 않는다
  • 설정 파일은 예시본만 커밋한다. 실제 값이 들어가는 파일은 처음부터 무시 대상으로 둔다
  • 훅이 잡아 줬다면 파일만 고치고 넘어가지 않는다. 그 값이 어디서 왔는지 같이 본다
  • 훅을 강제로 건너뛰는 선택지가 있다는 것을 팀이 알고 있어야 한다. 몰래 막는 장치는 몰래 우회된다
  • 에이전트나 자동화 도구에 저장소를 맡길 때는 시크릿을 아예 넘기지 않는 구성이 훅보다 앞선다

새 버린 뒤의 순서

이 절이 이 글에서 가장 중요하다. 유출을 발견한 순간 사람들이 가장 먼저 하는 일은 대개 파일을 지우는 것이다. 그게 눈에 보이는 문제이기 때문이다. 그런데 그것은 1번이 아니다.

GitHub 문서도 같은 순서를 명시한다. 지워야 할 민감 데이터가 비밀번호나 토큰 같은 비밀이라면 첫 단계로 그것을 폐기하거나 교체해야 한다고 적고, 폐기하고 나면 더 이상 접근에 쓸 수 없으므로 그것만으로 문제가 해결될 수도 있다고 덧붙인다. 이유는 간단하다. 히스토리 정리는 몇 시간이 걸릴 수 있고, 그동안 그 토큰은 계속 유효하다.

순서무엇을왜 이 순서인가미루면 생기는 일
1해당 키·토큰을 즉시 폐기하고 새로 발급폐기되면 그 값은 더 이상 열쇠가 아니다정리하는 동안 계속 유효하다
2그 자격증명으로 무엇이 가능했는지 범위 확인대응의 크기를 정한다어디를 봐야 할지 모른 채 로그를 뒤진다
3접근 로그와 활동 기록 확인실제로 쓰였는지가 갈린다보존 기한이 지나면 못 본다
4다른 자리에도 같은 값이 있는지 점검같은 토큰을 여러 곳에 넣어 둔 경우가 흔하다한 곳만 고치고 끝냈다고 믿는다
5그다음에야 히스토리 정리협업자 전원에게 영향을 준다급하게 해서 다른 것을 깨뜨린다

2번을 건너뛰기 쉬운데, 이것이 대응의 크기를 정한다. 읽기 전용 배포 키 하나가 샌 것과 조직 전체에 쓰기 권한이 있는 토큰이 샌 것은 이후 할 일이 완전히 다르다. 앞 절에서 범위를 좁혀 두라고 한 이유가 여기서 드러난다.

  • 폐기가 서비스를 멈출까 걱정되어 미루게 되는데, 그 걱정 자체가 하나의 토큰을 여러 곳에 쓴 결과다
  • 새 토큰은 옛 토큰과 같은 권한으로 만들지 않는다. 사고를 계기로 범위를 좁힌다
  • 기록을 남긴다. 언제 무엇이 어디로 샜고 무엇을 폐기했는지
  • 혼자 판단하지 않는다. 조직의 자격증명이면 정해진 보고 경로가 있고, 늦게 알리는 것이 대개 더 나쁘다

왜 히스토리 정리만으로 부족한가

히스토리 재작성은 눈에 보이는 결과가 확실해서 해결한 느낌을 준다. 로그를 열어 보면 그 커밋이 없다. 하지만 그 커밋은 이미 여러 곳에 복제되어 있을 수 있다.

GitHub 문서는 히스토리만 다시 쓰고 강제 푸시할 경우 민감 데이터가 담긴 커밋이 여전히 접근 가능한 자리를 셋으로 든다. 저장소의 클론과 포크, SHA-1 해시로 직접 접근되는 캐시된 화면, 그리고 그 커밋을 참조하는 풀 리퀘스트다. 포크에 남은 것은 포크 소유자와 따로 조율해야 한다고도 적혀 있다.

더 현실적인 위험은 되오염이다. 같은 문서가 이렇게 적는다. 동료가 재작성 이전의 클론을 가지고 있다가 재작성 이후에 그냥 pull 하고 push 하면 민감 데이터가 되돌아온다. 정리를 끝낸 뒤에도 팀원 한 사람의 습관적인 동작으로 원래대로 돌아갈 수 있다는 뜻이다.

  • 공개 저장소라면 크롤링과 미러가 더해진다. 공개 시점부터 정리 시점 사이에 무엇이 가져갔는지는 알 방법이 없다
  • 사내 저장소도 백업 스냅샷과 검색 색인에 사본이 남는다. 보존 정책을 확인하지 않으면 지웠다고 말할 수 없다
  • 그래서 히스토리 정리는 위생 작업이지 복구가 아니다. 복구는 1번에서 이미 끝났어야 한다

개인 저장소라도 지켜야 하는 이유

혼자 쓰는 비공개 저장소라면 굳이 신경 쓸 필요가 있느냐는 반문이 자연스럽고, 실제로 위험의 크기는 다르다. 다만 비공개라는 상태가 영구적이지 않다는 것이 문제다.

  • 공개 설정은 바뀐다. 오픈소스로 전환하거나 포트폴리오로 공개하는 순간 히스토리 전체가 같이 공개된다. 그때 과거 커밋을 하나씩 살피는 사람은 드물다
  • 협업자가 추가된다. 한 명을 초대하는 순간 그 사람은 히스토리 전체를 받는다. 최근 커밋만 주는 방법은 없다
  • 백업이 다른 곳으로 간다. 저장소를 통째로 압축해 클라우드에 올리거나 다른 장비로 옮기면 .git 도 같이 간다
  • 계정이 위험해질 수 있다. 계정 하나가 뚫리면 그 계정의 모든 비공개 저장소가 한꺼번에 열린다. 비공개는 계정 보안에 얹혀 있는 상태다
  • 장비가 바뀐다. 노트북 교체나 분실 시 작업 디렉터리와 홈의 자격증명 파일이 같이 움직인다
  • 도구가 읽는다. 편집기 확장, 분석 도구, 에이전트가 작업 디렉터리를 읽는다. 무엇이 어디로 가는지는 도구마다 다르다

정리하면 비공개 저장소의 안전은 지금 이 순간의 설정에 기대고 있고, 그 설정은 몇 년에 걸쳐 여러 번 바뀐다. 반면 히스토리에 들어간 값은 그대로 남는다. 시간이 한쪽 편만 든다.

예방 습관 목록

새로운 도구를 도입하지 않고도 지킬 수 있는 것들만 모았다. 순서는 효과가 큰 것부터다.

  • 원격 URL 에 자격증명을 넣지 않는다. 인증은 헬퍼나 SSH 키에 맡긴다. 이 하나로 세 자리가 동시에 막힌다
  • 토큰에 만료를 건다. 만료 없음을 고르지 않는 것만으로 사고의 유효기간이 생긴다
  • 권한을 지금 필요한 만큼만 준다. 나중에 늘리는 편이 낫다. 넓게 준 권한은 줄일 계기가 없다
  • 용도마다 자격증명을 나눈다. 폐기할 때 무엇이 멈추는지 알 수 있어야 실제로 폐기하게 된다
  • 서버에는 배포 키를 쓴다. 개인 키를 복사해 넣지 않는다. 읽기만 필요하면 읽기 전용으로 둔다
  • 개인키에 패스프레이즈를 건다. 파일이 통째로 넘어가는 상황에서 유일하게 남는 겹이다
  • 평문 저장 헬퍼를 기본으로 쓰지 않는다. 운영체제의 보안 저장소와 연동되는 쪽을 고른다
  • 추적 옵션을 상시로 켜 두지 않는다. 필요한 구간에만, 끝나면 끈다
  • 무시 규칙을 파일보다 먼저 만든다. 순서가 뒤집히면 추적이 이미 시작된다
  • 훅으로 스테이지를 검사한다. 완벽하지 않아도 가장 흔한 실수를 잡는다
  • 화면을 공유하기 전에 원격 URL 을 확인한다. 몇 초면 된다
  • 정기적으로 토큰 목록을 열어 본다. 쓰지 않는 것을 지운다

마지막으로 자기 점검용 세 줄을 둔다. 저장소 안에서 그대로 붙여 넣어 돌리면 된다. 세 가지 자리를 한 번에 본다.

# ① 원격 URL 에 자격증명이 박혀 있는가
git remote -v | grep -E '://[^/@]+@' && echo "원격 URL 에 자격증명이 있다"

# ② 히스토리의 변경 내용에 같은 형태가 있는가
git log --all -p | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

# ③ 커밋 메시지에 있는가
git log --all --format='%B' | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

②와 ③은 개수를 센다. 0 이면 그 형태는 없다는 뜻이다. 이 검사는 사용자명과 비밀번호가 붙은 URL 형태만 본다. 파일 안에 따로 적힌 키나 제공자별 토큰 형태는 잡지 못하므로, 그쪽은 전용 스캐너에 맡기는 편이 낫다. 큰 저장소에서 ②는 시간이 걸린다.

정리

자격증명이 새는 자리는 커밋된 파일 하나가 아니라 여섯이고, 그중 가장 자주 걸리는 것은 원격 URL 에 박힌 토큰이다. 그 값은 .git/config 에 평문으로 앉아 있다가 git remote -v 를 칠 때마다 화면에 다시 나온다. 고치는 것은 git remote set-url 한 줄이다.

새더라도 작게 만드는 쪽은 토큰을 만드는 화면에서 정해진다. 만료를 걸고, 범위를 좁히고, 용도마다 나눈다.

이미 새 버렸다면 순서가 전부다. 폐기, 범위 확인, 로그 확인, 그다음에 히스토리 정리. 파일을 지우는 일은 네 번째나 다섯 번째다. 히스토리를 아무리 깔끔하게 다시 써도 클론과 포크와 캐시에 남은 사본은 회수되지 않고, 재작성 이전의 클론을 가진 동료 한 사람이 pull 하고 push 하면 되돌아온다. 정리는 뒤처리이지 해결이 아니다. 해결은 첫 줄에서 끝난다.

확인하지 못한 것

  • .git-credentials 파일의 권한은 이 Windows·MSYS 환경에서 stat 이 644 로 보고한 값이다. 공식 문서는 다른 사용자가 읽지 못하도록 권한이 설정된다고만 적고 숫자를 명시하지 않으며, 리눅스에서 실제로 어떤 값이 되는지는 확인하지 않았다
  • 개인키를 644 로 두고 접속을 시도했을 때 이 환경의 OpenSSH 는 권한을 문제 삼지 않았다. MSYS 가 권한을 흉내 내는 탓으로 보이지만, 리눅스·macOS 에서 같은 상태가 어떻게 처리되는지는 확인하지 않았다
  • 오류 메시지에서 자격증명이 지워진 것은 이름 해석 실패 단계에서 git 이 직접 낸 메시지에 대한 관찰이다. 실제 서버가 인증 실패로 돌려주는 응답 본문이 무엇을 담는지는 확인하지 않았다
  • 추적 출력 중 HTTP 통신 계층의 헤더 가림 동작은 실제 접속을 하지 않아 관찰하지 못했다. 위 출력은 GIT_TRACE 의 명령 실행 기록에 한정된다
  • 시크릿 스캐너 제품들의 실제 탐지율과 오탐률은 시험하지 않았다. 도구가 있다는 사실만 적었고 특정 제품을 평가하지 않았다
  • GitHub 외 다른 호스팅 서비스의 토큰 만료 기본값과 조직 정책은 확인하지 않았다. 위 수치는 2026년 9월 기준 GitHub 문서에 한정된다
