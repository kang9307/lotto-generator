ローカルでモデルを動かし学習させるという選択 - 何を要求し何を返すのか

推論は30分で終わり、学習はデータで止まる

2026-08-16 開発・インフラ

序論: インストールまで30分、その先が問題だ

GPUが1枚刺さった機材を前にしてアプリを一つ入れれば、30分以内にモデルが答え始める。ここまでは本当に簡単になった。数年前まではPythonのバージョンとCUDAツールキットとドライバが互いに噛み合わずに壊れていた場所に、今はインストーラが一つ置かれている。

問題はその次だ。「自社のデータで学習させて自社のやり方で答えさせよう」という言葉が出た瞬間、難易度は一桁ではなく二桁ほど上がる。そしてその上昇分の大半はGPUではなくデータから来る。

最近、ローカル実行と学習、エージェント接続までを一つのアプリにまとめたツールが目に見えて増えた。その一つが2026年8月初めに公開されたUnsloth Desktopで、この記事の出発点もそこにある。ただし以下で扱うのは特定アプリの機能一覧ではない。モデルを自分の機材に移すという判断が実際に請求する費用と、その対価として返ってくるものだ。ツールは変わるが、この計算は変わらない。

実行スタックの選び方とGGUF量子化フォーマットの選択はローカルLLM実行ガイド2026で、機材を新しく買うときのマトリクスはローカルLLMハードウェア選定完全ガイドで既に扱った。ここでは繰り返さず、実行から学習に移るときに新しく生じる要求事項に集中する。

1. ローカルに移す理由三つ - 重みは状況が決める

ローカルを勧める文章はたいてい三つを並べる。データが外に出ない、呼び出し単価がない、回線が切れても動く。三つとも事実だ。しかし三つの重みは全く同じではなく、状況によって一つだけが決定的で残り二つはおまけである場合が大半だ。

  • データ持ち出し禁止 — 契約書や規制が明示的に禁じているときにのみ、この軸が圧倒的に重くなる。この場合は他の条件がどれだけ悪くてもローカルが唯一の答えだ。逆に禁止条項がないのに何となく気持ち悪くて選ぶ場合も多いが、それも選択であるにせよそのとき支払うのはインフラ運用の負担だと分かって始めるべきである
  • 呼び出し単価 — 機材を回し続けるときにのみ優位が生じる。一日数回使う用途ならGPU1枚の値段と電気代がそのまま損失だ
  • オフライン — 閉域網の事業所、船舶、現場機器のように回線が実際に存在しない場所でのみ決定的になる。オフィスでインターネットがたまに切れる程度はこの軸に該当しない

よく抜け落ちる四つ目の軸が遅延時間だ。ネットワークの往復が消える代わりに自分の機材の処理速度がそのまま上限になる。コンシューマGPUで大きなモデルを回せばAPIより遅くなる区間が明確に存在し、それを知らずに移して戻す事例も少なくない。

整理するとこうなる。持ち出し禁止条項があれば他の計算は不要だ。なければ、残りの軸は稼働率がどれだけ出るかという一つの問いに収束する。社内データを外部モデルに入れてよいかという判断基準そのものは社内データをLLMに入れてよいかで別途整理した。

2. VRAMが上限を決める - 推論と学習は計算式が違う

ローカルで何が可能かは、大半がメモリ容量という一つの数字で決まる。ところがここでよく食い違う期待がある。推論できるモデルだからといって学習もできるわけではない。計算に入る項目そのものが違うからだ。

推論は重みをメモリに載せて読むだけだ。だから重みの容量がほぼ全てで、そこにコンテキスト長に比例するKVキャッシュが付く。学習はその上に勾配とオプティマイザ状態が乗る。パラメータごとに値が何組も生じる構造なので、同じモデルでも必要メモリが数倍に跳ね上がる。

用途パラメータあたり概算8Bモデル換算追加で乗るもの
推論(4ビット級)約0.5バイト約4GBKVキャッシュ(コンテキスト比例)
推論(8ビット級)約1バイト約8GBKVキャッシュ
推論(16ビット)約2バイト約16GBKVキャッシュ
アダプタ学習(4ビットベース)ベース0.5+アダプタ分おおよそ6~12GB台活性化バッファ(バッチ・長さ比例)
全体ファインチューニング(混合精度Adam)16バイト前後128GB規模活性化バッファ、マスター重み

表の最後の2行がこの記事の核心的な分かれ道だ。全体ファインチューニングの16バイトは重み4+勾配4+Adamモーメント2組で8を足した通常の算術で、実際には活性化バッファが別途乗ってさらに大きくなる。8Bモデルに128GBという数字が意味するところは明白だ。コンシューマGPU1枚で全体ファインチューニングをするという計画は算術の段階で既に終わっている。

# 概念例 - 候補を絞り込むための算術である。特定バージョンでの実測値ではない。
def rough_bytes(params_b, mode):
    per_param = {
        "infer_4bit": 0.5,
        "infer_16bit": 2.0,
        "full_finetune_adam": 16.0,   # 重み+勾配+オプティマイザ状態
    }[mode]
    return params_b * 1e9 * per_param / (1024 ** 3)   # GiB

print(rough_bytes(8, "infer_4bit"))          # およそ4
print(rough_bytes(8, "full_finetune_adam"))  # およそ119

算術は候補を絞る用途であって確定ではない。バッチサイズとシーケンス長が活性化バッファを通じて実使用量を大きく揺らす。上の計算で明らかに不可能な組み合わせを先に消し、残った候補は実際に1ステップ回して確定する順序が正しい。算術で通ったのに実行で落ちることはよくあるが、算術で詰まった組み合わせが実行で通ることはない。

3. 量子化が変える三つ - そして学習で変わる点

量子化は重みをより少ないビットで表現する作業だ。変わるのは三つだが、三つの軸が同じ方向に動かないという点が要領の全てである。

  • メモリと速度 — どちらも予測可能に良くなる。メモリはビット幅にほぼ比例して減り、LLMのデコードはトークンごとに重みをなぞるメモリ帯域支配的な作業なので、読むバイト数が減ればその分速くなる。ただしカーネルがそのビット幅に最適化されていて初めて速度の利得が実際に出る
  • 品質 — ここだけが逆方向に動き、どれだけ悪くなるかが作業ごとに違う。雑談と要約はよく耐える一方、長い推論の連鎖、コード生成、正確な数値の引用が先に崩れる
ビット幅メモリ品質の体感どこに使うか学習ベースとして
16ビット基準基準品質比較の基準線、アダプタ統合後の配布可能だがメモリが耐えられない
8ビット級半分おおむね区別が難しい品質を守りつつ一段下げるとき可能
4ビット級1/4作業によって分かれる日常会話、要約、分類。ローカルの実質標準アダプタ学習の標準的な組み合わせ
3ビット以下1/5以下目に見えて揺れる大きなモデルを無理に載せる必要があるときのみ推奨しない

学習で変わる点が一つある。推論において量子化は品質を少し差し出してメモリを得る取引だが、学習ではそもそも不可能だったことを可能にする装置に近い。ベース重みを4ビットで凍結し、その上に小さな学習可能行列を載せる構成がそれだ。QLoRA論文はこの方式で65Bパラメータのモデルを48GBのGPU1枚でファインチューニングし、16ビット全体ファインチューニング水準の作業性能を維持したと報告している。ここで使われた要素は4ビットNormalFloatというデータ型、量子化定数まで再度量子化する二重量子化、メモリ急増を管理するページドオプティマイザの三つだ。

注意すべきは、この値がその論文のモデルと設定で出た値だという点である。バッチサイズとシーケンス長を変えればそのまま移らない。他人の数字を見るときはモデルサイズ・量子化方式・シーケンス長・バッチサイズが併記されているかをまず確かめ、書かれていなければ方向だけ取って大きさは捨てるのが正しい。

4. CPUだけでできる範囲とできない範囲

GPUがなくても済むかという問いには用途を分けて答えなければならない。ボトルネックがどこかによって結論が正反対に分かれる。

4.1 CPUで実用的なもの

  • 小さいモデルの対話利用 — 3B級以下を4ビットで載せればシステムメモリで賄える。応答は遅いが使えないほどではない
  • 埋め込み生成と急ぎでないバッチ処理 — モデルが小さくバッチにまとめやすいのでCPUが相対的に不利になりにくい。夜に回しておいて朝に結果を見る形なら速度は二次的な問題になる
  • データ準備の全工程 — 収集、整形、フォーマット変換、重複除去。ここがファインチューニング作業時間の大半なのにGPUが全く要らない

4.2 CPUでは事実上不可能なもの

  • 中大型モデルの対話応答と長いコンテキスト — メモリ帯域の差がそのまま毎秒トークン数の差として現れる。容量ではなく帯域が壁であり、プロンプトを読み込む段階から体感できるほど遅くなる
  • 学習 — 可能ではあるが所要時間が数日から数週間の単位に広がり、実務上の選択肢にならない

ここから実務的に有用な結論が一つ出る。GPUを買う前にデータ準備からやってみろということ。その段階は今あるノートPCで全部できるし、たいていその段階でプロジェクトの成否が既に決まる。

5. 推論は簡単だ - ファインチューニングはデータ準備が8割

実行と学習が同じアプリの中に並んでいると難易度も似て見える。実際には全く異なる種類の作業だ。

推論は決まった答えのある問題である。モデルファイルを受け取り、機材に合う量子化を選び、実行する。詰まっても原因は有限で大半は検索で解ける。半日で終わる。

ファインチューニングは違う。学習を回すコマンドは一行で、最近のツールはその一行すらボタンに置き換えたが、そのボタンを押すまでが全てだ。

  • 収集と選別 — 学習に使う事例がチケットシステム、ウィキ、メッセンジャー、担当者の頭の中に散らばっている。そしてすべての過去事例が良い事例ではない。悪い応対を学習させれば悪い応対を上手にするモデルができる
  • 非識別化 — 個人情報と契約上の秘密を除かねばならない。ローカルに移した理由がデータ保護だったなら、この段階を飛ばした瞬間に大義名分が消える
  • 整列と分割 — 入力と出力が一対で噛み合う必要があるが、実務の記録はたいていその形ではない。その後、学習セットと評価セットを重ならないよう分ける。重なればスコアだけ上がって実性能はそのままだ
  • 評価セットの作成 — これが本当の成果物だ。この話は下でもう一度する
// 概念例 - 指示と応答の対の典型的な形である。
// 実際のフィールド名とスキーマはツールごとに異なるため、使うツールの文書に従うこと。
{"messages": [
  {"role": "system",    "content": "あなたは社内インフラ運用の担当者だ。"},
  {"role": "user",      "content": "夜間バッチが3時に失敗した。どこから見る?"},
  {"role": "assistant", "content": "1) ジョブログの終了コード 2) 先行ジョブの完了有無 3) ..."}
]}

本当に重要なのは最後の項目だ。評価セットを先に作れ。学習を終えた後に良くなったか悪くなったか判定する手段がなければ、そのファインチューニングは結果を確認できない実験になる。そして評価用の50問を作る途中で詰まるなら、その作業はまだファインチューニングする段階ではない。何が良い答えなのかを自分で定義できていない状態だからだ。ファインチューニングの損益分岐と総費用の構造は500ドルの微調整がフロンティアモデルを上回ったという話で別途整理した。

6. LoRAが解く問題と解けない問題

ローカル学習が現実的に可能になった理由は、全部を学習しない方式が定着したからだ。LoRAは元の重みを凍結したまま、低ランク分解で作った更新行列2つだけを学習する。トランスフォーマーでは通常アテンションブロックにのみ付け、ランクrがその行列の大きさを決める。学習が終わればアダプタ重みを元に統合して一つのモデルにでき、統合してしまえば推論の遅延は増えない。

6.1 うまくいくもの - どう話すか

  • 出力形式の固定 — 常に特定のJSONスキーマで、常に決まった項目順で答えさせる作業。分類・抽出のように狭く反復的な作業を大きなモデルを呼ばずに終える構成もここから生まれる
  • 文体と用語の適応 — 社内文書のトーン、顧客応対の話法、業界で実際に使われる表現。一貫性がそのまま品質になる領域全体が該当する
  • 拒否境界の調整 — どこまで答えてどこで担当者に渡すかの基準を体に覚えさせる作業

6.2 うまくいかないもの - 何を知っているか

  • 事実知識の注入 — 社内規定100件を覚えさせようとする試み。できたとしてもどこまで覚えたか確認する方法がなく、学習された知識は出典を指し示すこともできない
  • 頻繁に変わる情報 — 価格表、在庫、組織図。変わるたびに再学習が必要という時点で既に設計が誤っている
  • 根本的な推論能力の向上 — ベースモデルが解けない問題をアダプタが解けるようにすることはできない

判断基準は一行に縮む。変えたいのがどう話すかなら学習、何を知っているかなら検索だ。そしてこの二つは排他的ではない。形式はアダプタで固定し事実は検索で付ける組み合わせが、たいてい最もよく機能する。

アダプタのあまり知られていない利点が一つ。アダプタはベースに比べて非常に小さいので複数用意して差し替えられる。チームごと、作業ごとに別のアダプタを持ち同じベースを共有する構成が可能だ。全体ファインチューニングは作業ごとにモデル一式が丸ごと複製されるためこの構成が成立しない。ローカルのようにストレージとメモリが逼迫する環境で、この差は思ったより大きく効く。

7. 一箱にまとめられたツール - 得るものと隠れるもの

実行・学習・データ準備・エージェント接続・APIサービングが一つのアプリに入っているのは明らかに良い。ただし抽象化はタダではなく、何を隠しているか分かって使うのと分からずに使うのとでは結果が違う。

7.1 得るもの

  • バージョン地獄の解消 — ドライバ・ランタイム・ライブラリの組み合わせを合わせるのに何日も費やしていた問題が消える。これだけでも参入障壁が大きく下がる
  • 最初の成功までの時間 — できるかできないかを早く知れる。うまくいかないプロジェクトを早く畳むのも利得だ。学習したモデルをそのままサービングして評価する流れが既に繋がっていることもここに寄与する
  • デフォルト値の質 — よくできたツールの既定ハイパーパラメータは、初心者が手で選んだ値よりおおむね良い

7.2 隠れるもの

  • 実際にどんな値が使われたか — ランク、学習率、スケジュール、対象モジュール。結果がおかしいときにこれらの値が見えなければ原因を絞れない
  • どこで落ちたか — 統合ツールのエラーメッセージはたいてい一段上で捕まり、下位層の本当の原因を隠す。ボタン一つで学習が始まると、それが何時間かかる作業なのかの感覚もつかめない
  • 移植性 — そのツールの中でのみ成立する設定で結果を作ると、別の環境へ移すとき一からやり直しになる

だから実用的な基準はこうだ。成果物が標準フォーマットで出るか確認せよ。学習結果がGGUFやsafetensorsのようにツールの外でも読める形で落ちるなら、そのツールは牢獄ではなく利便層である。逆に成果物がそのアプリ専用の形式なら今節約した時間を後で利子まで付けて返すことになる。そして一度は下の層を直接触ってみる方がよい。毎回そうする必要はないが、何が自動化されたのか分からない状態では、自動化が誤ったときに気づくことができない。

8. オープンウェイトはオープンソースではない

この節は技術ではなく法務の話だが、ローカルのプロジェクトで最も遅く発見され最も戻しにくい問題がここから出る。重みをダウンロードできることと自由に使ってよいことは完全に別の話だ。

代表例がLlama系である。コミュニティライセンスは次を要求する。

  • 直前の月の月間アクティブユーザーが7億人を超える製品・サービスは、別途商用ライセンスをMetaに申請しなければならない
  • ウェブサイト・UI・文書などにBuilt with Llamaを目立つように表示しなければならない
  • 派生モデルを配布する際は名称をLlamaで始める必要があり、著作権表示を維持し、別途の利用ポリシーを遵守しなければならない

Open Source Initiativeはこれらの条件についてオープンソースの定義を満たさないと明示的に述べている。指摘された項目は、どんな目的にも使う自由を制限する点、利用者を差別する点、利用分野を制限する点だ。OSIはこうした表記をオープンウォッシングと呼ぶ。

もちろんすべてのオープンウェイトモデルがこうではない。Apache 2.0やMITで配布される系統もあり、そちらは条件がはるかに緩い。要点は系統ごとに完全に異なるということ、だから毎回確認しなければならないということだ。この差の技術的側面はオープンウェイトLLMとクローズドLLMの差で扱った。

8.1 確認すべき三層

  1. ツールのライセンス — 実行・学習フレームワーク自体の条件。複数のライセンスを混ぜて使う場合が多く、どの構成要素を使うかによって適用される条項が変わる
  2. モデル重みのライセンス — 商用利用、派生モデルの配布、表記義務、利用分野の制限。ツールが緩いからといってモデルが付いてくることはない
  3. 学習データの権利 — ファインチューニングに入れる社内文書と顧客記録に対する処理の根拠。データを外に出さないからといって、そのデータを学習に使う権利が自動的に生じるわけではない

特に三つ目はローカルだという理由で丸ごと飛ばされやすい。自分のサーバーの中で起きることだから大丈夫だという感覚は法的根拠ではない。

9. ローカルが答えでない場合

ここまで読めば判断軸が整理される。下の表は条件から結論に至る経路だ。

状況勧める側理由
契約・規制がデータ持ち出しを禁止ローカル他の条件が悪くても選択肢がない
回線が実際に存在しない現場ローカル代替が成立しない
狭く反復的な作業+高い稼働率ローカル+アダプタ単価優位が実際に現れる唯一の組み合わせ
最新最高の性能が結果を左右API公開重みは遅れて出て差をローカルで埋められない
使用量が不規則で少ないAPI機材の減価償却と電気代がそのまま損失
運用担当者が決まっていないAPI半年後に誰も触れないサーバーが残る
要求が変わり続ける初期探索段階APIを先に何を作るか決まる前のローカル投資は埋没費用になりやすい
ローカルを選んだ理由を一文で書けないAPI理由がなければ残るのは運用負担だけだ

表に入らない軸がもう一つある。運用負担は時間が経つほど大きくなる。最初はモデル一つ回せばよいが、半年後にはドライバ更新、モデル交換、アダプタ再学習、ディスク整理、アクセス制御がすべて誰かの仕事になる。導入時点の費用比較にはこの項目がたいてい抜けている。

10. 今のツールの状態、そして確認できなかったもの

2026年8月16日時点で状態を書いておく。この分野は表記がよく変わるので、時点と併せて読む必要がある。

  • この記事の出発点となったUnsloth Desktopは公式文書にベータ(Beta)と表記されている。リポジトリに表示されているバージョン文字列も0.1.800-betaでベータ段階だ
  • 対応プラットフォームとしてmacOS、Windows、Linux、WSLが案内され、Docker経路もある。ハードウェアはNVIDIA、AMD、Intel GPUとApple Siliconが言及され、CPUは会話とデータ処理の用途として書かれている。学習結果はGGUFと16ビットsafetensorsに書き出せると案内している。前節の移植性基準を満たす構造だ
  • ライセンスは二重構造だ。中核パッケージはApache 2.0、スタジオUIと一部の選択構成要素はAGPL-3.0である。AGPL構成要素をサービスとして提供する計画なら条項を直接確認する必要がある

確認できなかったものは下にまとめる。本文のどこにもこれらの項目を根拠にした文はない。

  • ベンダーが提示した性能数値 — 2倍速い学習、VRAM 70%削減、MoE最大12倍、20Bモデルの50万コンテキスト学習といった値が公開されているが、比較対象の基準線、モデル、シーケンス長、バッチサイズが併記されていない。そのため本文の表と算術には一切反映していない
  • ベータ段階の安定性とプラットフォーム別の機能差 — 長期運用での信頼性は検証しておらず、文書にもプラットフォーム別の制約が明示されていない。Apple SiliconとAMD環境で学習機能がNVIDIAと同一に動作するかは確認していない
  • 表のアダプタ学習メモリ範囲 — 6~12GB台はよく引用される概算であって実測ではない。バッチと長さによって外れる

結論: 順序を逆にするな

ローカルに移すプロジェクトが失敗する仕方はたいてい一つだ。機材を先に買ってデータを後で見る。そうするとGPUは遊び、人はデータ整形にかかりきりになり、半年ほど経つと誰も手を付けないサーバーが一つ残る。

順序は逆であるべきだ。

  1. ローカルを選ぶ理由を一文で書く。持ち出し禁止条項か、稼働率か、オフラインか。三つとも違うならここで止めるのが得だ
  2. 評価用の50問を先に作る。これが作れなければ何が良い答えなのかまだ定義されておらず、その状態で学習しても結果を判定できない
  3. 学習の前にプロンプトと検索で先に試す。ここで十分ならファインチューニングは不要だ。相当数がここで終わる
  4. 算術で候補を絞る。全体ファインチューニングはたいてい算術の段階で消え、残るのは4ビットベースの上のアダプタ学習だ
  5. ライセンス三層を確認する。ツール、重み、学習データ。これはコードを書く前に終えるべき作業だ

ツールが良くなったおかげで1番から4番までの参入障壁が大きく下がったのは事実だ。ただし下がったのは実行の障壁であって判断の障壁ではない。何を学習させるか、それがうまくいったかをどう知るかは依然として人が決めるべきことで、その部分はどんなアプリを入れても代わりにやってはくれない。
