MCP 扔掉了会话 - 无状态转型在服务器运维上改变了什么

粘性路由和可恢复流消失之后，那个位置该放什么

2026年8月16日 开发/基础设施

引言: 卡在 Ingress 配置前的 MCP 服务器

把 MCP 服务器放到内部集群上时，手停下来的地方通常不是代码，而是 Ingress 配置。Pod 一扩到两个，一半请求就落到别的实例上，回来一句「没有这个会话」。于是打开会话亲和性，结果每次发布都把进行中的连接整片切断。为了避免这一点把会话放进共享存储，这下那个存储又成了单点故障。是个很熟悉的循环。

MCP 规范的 2026-07-28 修订版把这个循环的根切断了。协议级会话消失了，打开连接的 initialize 握手也没有了。现在每一个请求自己携带：它用哪个协议版本说话，客户端能做什么。对服务器来说，它没有义务记住上一个请求；对基础设施来说，MCP 流量被当成普通 HTTP 流量对待。

这不是免费的。会话撑着的那些东西 — 进行中的多步骤任务、服务器先开口的结构、断流之后的恢复 — 并没有消失，而是挪到了别处，或者干脆变成运维的活。这篇文章讲的就是这笔交易的具体内容。

如果你刚接触 MCP，MCP(Model Context Protocol)完全指南：AI智能体的新标准讲概念，Claude Code 该选哪些 MCP 服务器 - 不看清单，看六条判断轴讲从客户端一侧挑服务器的视角。这里只谈另一侧，也就是做服务器、跑服务器的那一边。

本文引用的规范全部来自 2026-07-28 修订版，确认时点是 2026 年 8 月 16 日。MCP 规范以日期戳作版本号，只要保持向后兼容号就不会往上走，所以半年后再读的话，先确认当前修订版是哪一个更稳妥。

1. 会话造成的运维负担 - 真正贵的是什么

从 2025-03-26 到 2025-11-25 的 Streamable HTTP，是服务器通过 Mcp-Session-Id 头签发会话，客户端在后续请求里一直带着这个值。HTTP DELETE 结束会话，GET 另开一条 SSE 流接收服务器主动发来的消息，流断了就用 Last-Event-ID 恢复。

作为设计它很优雅。问题在于这三件事全都给基础设施层加了约束。

  • 粘性路由事实上被强制。 会话状态在实例内存里，同一会话的后续请求就必须落到同一个 Pod。前面是没有 cookie 亲和性的 L4，你就得自己写基于头的哈希。
  • 水平扩展不均匀。 新 Pod 只接新会话，负载留在旧 Pod 上。自动扩容加了实例也不会立刻见效，缩容时又要因为还活着的会话而推迟驱逐。
  • 发布就等于断连。 滚动更新替换 Pod，它持有的会话随之消亡。客户端收到「没有会话」，从头重连。这正是号称不停机发布、实际上用户工作被打断的典型位置。
  • 引入会话存储只是把问题挪走。 把状态放到外部缓存，路由自由了，但这个缓存的可用性、序列化成本、过期策略又成了新的运维项目。会话撤销在规模上如何崩掉，在退出登录为何不能立刻生效 - 会话撤销在规模上崩掉的地方里详细讲过。
  • 中间设备看不懂内容。 在代理眼里所有请求都是发往同一端点、形状相同的 POST。想知道调的是哪个工具就得解析请求体，而在网关上拆 JSON 无论从性能还是安全角度都不受欢迎。

归结起来，成本的真身不是会话本身，而是会话所要求的位置固定。请求可以去任何地方的系统，和请求必须去某个特定实例的系统，运维难度差一个档次。

2. 2026-07-28 修订版实际拿掉了什么

改动面很宽，「变成无状态了」这一句话读不出手感。只挑直接触及运维的项目，是这些。

首先，没有握手了。 initialize 和 notifications/initialized 被删除，所有请求把协议版本和客户端能力放进 _meta 发送。键名是反向域名形式：io.modelcontextprotocol/protocolVersion、io.modelcontextprotocol/clientCapabilities、io.modelcontextprotocol/clientInfo。服务器把自身信息放进每个结果的 _meta 里应答。版本对不上，服务器返回 UnsupportedProtocolVersionError 并附上自己支持的版本列表，客户端挑一个重试。这不是协商往返，而是拒绝加重试。

其次，没有会话头了。 Mcp-Session-Id 和协议级会话一起被删除。这里带出一个容易漏掉的结果 — tools/list、resources/list、prompts/list 不能再按连接变化。如果你的服务器按连接展示不同的工具列表，那个设计得先改。跨调用需要状态的话，规范指出的方向是使用服务器签发的显式句柄，作为普通工具参数来回传递。

第三，服务器不能先发请求了。 以前服务器可以往 SSE 流上推 roots/list、sampling/createMessage、elicitation/create 这类 JSON-RPC 请求。现在把「还需要输入」这个信号放进结果本身返回。所有结果都带 resultType 字段，值为 input_required 时，inputRequests 里说明需要什么。客户端填好之后连同 inputResponses 用新的请求 ID 重发原请求。这个模式叫多轮往返请求(MRTR)。

第四，没有 GET 流了。 要接收服务器推送的变更通知，用 POST 调 subscriptions/listen，它的响应流成为长生命周期通道。客户端明确选择想要的通知类型。而像 notifications/progress 这种绑定在特定请求上的通知，仍然只在那个请求的响应流上流动。两条流的职责分开了。

第五，没有恢复了。 Last-Event-ID 和 SSE 事件 ID 被删除。响应流一断，进行中的请求就算丢了，客户端必须用新的请求 ID 从头重发。这一行就是后面幂等性话题的起点。

还有一个对运维影响很大的改动。Streamable HTTP 的 POST 上 Mcp-Method 和 Mcp-Name 头成为必填。它们把请求体里的方法名和目标名镜像到头上，目的很明确 — 让中间设备不解析请求体也能路由和观测。列表与读取类结果加上了 ttlMs 和 cacheScope，缓存契约被显式化，而 ping 和 logging/setLevel 被删除。

3. 传输方式的变迁 - 三者预设了不同的世界

把传输方式排开看像是一次进化，但实际上每一个都是按不同的部署形态设计出来的。知道各自的前提，就能看懂为什么现在是这个样子。

(继续保留)		 客户端拉起的子进程标准输入输出，按行分隔的 JSON-RPC 进程生命周期就是边界 当前修订版中作为输入请求装在结果里 不适用 根本没有扩展的概念。一个用户一个进程

表里该读的是最后一列。stdio 本来就是没考虑扩展的传输，给跑在自己笔记本上的进程引入会话这个概念没有理由。HTTP+SSE 把浏览器时代的习惯直接搬了过来，两个端点要成对维护，代理配置因此变得脏。中间那版 Streamable HTTP 把端点合成一个却留下了会话，于是单一端点的好处没能在路由上兑现。当前修订版解开的就是最后这个结。

看一个请求长什么样，转型的性质就清楚了。自我介绍全都在请求内部。

POST /mcp HTTP/1.1
Accept: application/json, text/event-stream
Authorization: Bearer <access-token>
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: run_query

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "run_query",
    "arguments": { "sql": "select 1" },
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": { "name": "example-client", "version": "1.0.0" },
      "io.modelcontextprotocol/clientCapabilities": {}
    }
  }
}

同一个值在头和体里出现两次，看着像冗余，其实是契约。规范要求：头里的值和体里的值不一致时，服务器必须以 400 加 HeaderMismatch 错误拒绝。理由很清楚 — 负载均衡器看头做路由而服务器看体做执行，这两者相信不同真相的那一刻就是攻击面。

4. 得到的 - 发布和扩展变得平平无奇

无状态转型的收益，大半来自不用再把 MCP 当特例对待。

  • 可以关掉会话亲和性。 只面向新世代客户端的话，请求落到哪个实例都行。轮询也好、最少连接也好，现有策略照用。
  • 滚动发布的波及缩小到一个请求。 以前换 Pod 会把整个会话打掉。现在受影响的是那一刻正在处理的单个请求，靠重试收回。不过长生命周期的通知流是例外，下一节讲。
  • 自动扩缩立刻生效。 新实例起来，从下一个请求开始就分担负载。缩容时只需等进行中的请求排空，不必等会话过期。
  • 中间设备变聪明了。 Mcp-Method 和 Mcp-Name 在头里，不拆请求体就能做按工具的限流、把重工具路由到专用池、按方法拆分指标。用把工具参数镜像到头上的 x-mcp-header 注解，还能按租户或区域这类值来路由。
  • 缓存成了契约。 列表和读取结果带上 ttlMs 与 cacheScope。共享的中间缓存能不能存这个响应由服务器明示，于是减少轮询的依据来自响应本身而不是猜测。

还要补一条收益。列表结果不能再按连接变化之后，客户端一侧的提示词缓存命中率会上升。规范建议 tools/list 以确定性顺序返回，也是同一个理由。这不是基础设施收益，而是token 成本收益。

5. 失去的 - 进行中的任务、订阅和恢复去哪了

这里才是这次转型真正的论点。会话没了，并不意味着会话做的活也没了。分成三块看，它们各自落在了不同的地方。

5.1 进行中的任务 - 从核心到扩展

表达长时间任务的实验性 Tasks 从核心里退出，移到了官方扩展 io.modelcontextprotocol/tasks。等结果而阻塞的调用换成了轮询查状态，是否支持通过能力协商的 extensions 字段交换。只实现核心的服务器压根没有这个功能，所以如果长时间任务是服务的本质，采不采用扩展本身就是设计决策。

5.2 服务器先开口 - 被 MRTR 反转

需要向用户确认，或者需要模型补全的时刻，以前是服务器给客户端发请求。现在是服务器返回请求。方向反了过来。实务上重要的差别有两点。

  • 服务器不必持有等待状态。 等输入期间开着的连接、以及绑在上面的内存都没有了。重试进来时，任何实例都能处理。
  • 代价是要把上下文重新发一遍。 客户端在原请求参数上加上响应重发。服务器若要跨多次往返关联什么，就得把自己的标识符放进 requestState 自行管理。往返越长，来回搬运的载荷越大，这个代价是实打实的。

5.3 订阅与恢复 - 一个留下一个没有

变更通知以 subscriptions/listen 这条长生命周期响应流的形式留了下来。不是改了名字，而是性质变了 — 不再是永远开着的 GET 通道，而是挑好通知类型明确打开的一个请求。为了在安静时段不被中间设备掐断，建议服务器周期性地发 SSE 注释行做保活。反向代理缓冲 SSE 导致通知成堆到达的问题，用 X-Accel-Buffering: no 头处理。

恢复没有留下。断掉的流不会回卷。 这个决定和无状态在逻辑上是咬合的 — 要恢复就得有人记住哪个实例发到了哪里，而那份记忆恰恰就是要拿掉的状态。所以滚动发布用重试收回丢失的请求，却确定地切断开着的通知流。客户端若不自己重新订阅，那个界面就会悄无声息地停止更新。

  • 取消方式也因传输而异。HTTP 上客户端关闭响应流就是取消信号，stdio 上则另发一条取消通知。
  • 通知流依然是钉在某一个实例上的连接。去掉会话固定和让流不中断是两个问题。
  • 进度通知和变更通知走不同的流，所以客户端实现里如果把两条路径合进了一个处理器，需要拆开。

6. 原先放在会话里的东西挪到哪

迁移最难的部分不是改代码，而是发现。往会话对象上堆了什么，通常没有文档，服务器越老散得越开。找的窍门很简单。

  • 把连接建立时创建、且被请求处理器引用的对象全部列出来。构造函数的入参就是会话状态清单。
  • 找处理器里那些没有作为参数传进来却已经有值的变量。那就是上一个请求留下的痕迹。
  • 把写到实例本地磁盘或临时目录的路径捋一遍。上传缓冲和中间产物藏在这里。
  • 看构建工具列表的代码是否按用户或连接分支。有分支的话，那个设计在当前修订版下不成立。

去处大致有三个。装在请求里发送的(不透明游标、服务器签发的句柄、MRTR 的 requestState)、从令牌里取出的(用户身份、租户、权限范围)、放进共享存储的(任务进度、大的中间产物)。判断标准只有一条 — 这个值交给客户端是否安全。 如果伪造它就等于交出权限，那就不能装进请求，除非服务器对它签名或者回存储重新校验。

把会话里的游标换成句柄，概念上就是这点差别。下面不是某个 SDK 的 API，而是为了展示结构的伪代码。

// 之前: 连接对象记着游标
session.cursor = result.nextCursor
handleNext(session)          // 必须是同一个实例才能工作

// 之后: 服务器签发的不透明句柄作为参数来回传
{ "method": "tools/call",
  "params": { "name": "list_rows",
              "arguments": { "cursor": "<由服务器签名并签发的字符串>" } } }
// 哪个实例收到都能解出游标继续处理

如果必须接收旧世代客户端，就把服务器做成双世代。规范允许在同一端点上同时服务两个世代，服务器按请求进来的形状判断 — 带着按请求的 _meta 就按无状态处理，以 initialize 开头就选旧世代语义。反过来，只支持新世代的服务器收到旧世代流量时，规范的指引是：GET 和 DELETE 回 405，忽略 Mcp-Session-Id 和 Last-Event-ID，同时不要新建或回显会话 ID。

还有一点值得记住：世代判定是服务器这个对象的性质，不是单个请求的性质。客户端会按服务器进程或源来缓存这个判定。也就是说，你把服务器升到新世代的那天，记着它是旧世代的客户端还会走错一阵子路。

8. 幂等性与重试 - 断掉的流不会回卷

失去恢复的代价，立刻表现为重复执行风险。场景非常具体。客户端调一个支付工具。服务器打开 SSE 流开始处理。中途网络断了。客户端没拿到最终响应，于是用新的请求 ID 重发。服务器可能已经提交了上一次，也可能没有。协议在这里什么都不保证。

以前恢复机制部分地盖住了这个洞。现在得由写工具的人自己去盖。 常规做法有三条。

  • 有副作用的工具接受一个幂等键作为参数。 让客户端为同一次逻辑尝试附上同一个键，服务器按键记录结果，第二次调用返回已保存的结果。请求 ID 每次重试都变，所以不能拿来当幂等键。
  • 不要把取消误当成完成。 HTTP 上客户端关闭流就是取消信号，服务器应尽快停止工作、之后不再发送任何消息。麻烦在于已经发往外部系统的副作用不会被取消。取消路径要不要补偿事务，得按工具逐个判断。
  • 不要把长任务挂在流上。 响应流一断就丢，所以以分钟计的任务更适合立刻返回一个句柄、让状态另行查询。Tasks 扩展标准化的正是这个形态。
  • 不要把重试风暴只交给客户端。 流中断通常是基础设施事件，会同时打到很多客户端。要预设重试会一起涌来，在服务器侧准备好限流和退避引导。

总结一句：无状态让服务器变简单，但没有让工具变简单。 协议原先兜住的那部分落到了工具实现这边，而且这部分大多集中在有副作用的工具上。

9. 认证与授权下沉到请求粒度时

有会话的年代，认证在心理上更接近「接入」。通过一次，这条连接就被当作已认证。无状态里没有这样的位置。HTTP 传输上授权头必须包含在客户端发往服务器的每一个请求里。把令牌放进 URI 查询字符串是被禁止的。

服务器一侧的义务也逐请求重复。MCP 服务器作为 OAuth 2.1 资源服务器校验令牌，并确认这个令牌是以自己为受众签发的。接收签发给别处的令牌并放行、或者转发给其他服务，都是被禁止的。仅这一条规则就挡住了相当一部分混淆代理人攻击。

  • 失败点变宽了。 过去只在连接开始时出现一次的鉴权错误，现在会在任意调用上出现。令牌过期可能发生在任务中途，所以客户端遇到 401 要有刷新后重试的路径。
  • 权限不足另行处理。 令牌有效但范围不够时，服务器回 403 并在响应头里告知所需范围。客户端必须用已有范围与新范围的并集重新授权。只请求新范围会丢掉原先已有的权限。
  • 重新授权要一次走完。 规范建议服务器把一次操作所需的范围汇总在一次挑战里发出。一次告知一个缺失范围，会让用户反复看到同意界面。
  • 务必指定令牌的目标。 客户端必须在授权请求和令牌请求两边都写明目标资源，且该值必须是 MCP 服务器的规范 URI。要求是无论授权服务器是否支持这个参数都要发送。
  • stdio 在这套规格之外。 stdio 传输的实现不遵循这份授权规范，而是从环境里取凭据。也就是说本地服务器的权限边界依然是启动进程的那个用户账号。

运维上真正的负担是校验成本。每个请求都要验令牌，却不能每次都去打授权服务器。如果是靠签名就能验的格式，缓存公钥即可；若是不透明令牌需要内省，那个内省层就成了新的瓶颈和单点故障 — 想避免刚拆掉会话存储、令牌内省缓存就接管了那个位置的局面，一开始就用可自校验的令牌更好。

10. 可观测性 - 留下什么才能复现问题

转到无状态，调试里会少掉一样东西：会话 ID 这个白送的关联键。以前把日志按会话 ID 一聚，一个用户的整条流程就出来了。现在协议不给你这根轴了。

规范准备的替代位置是分布式追踪。在 _meta 里携带并传播追踪上下文的约定被文档化了，而日志功能本身被归类为待废弃，迁移路径给的是 stdio 的标准错误输出和 OpenTelemetry。这更接近一个宣告：协议搬运日志的时代结束了，可观测性回归通用观测栈。想留下可复现的日志，把下面这些轴汇到一行是实用的做法。字段名不是规范定的，把它读成该留这些轴的意思即可。

ts=2026-08-16T09:14:22Z  instance=mcp-7d9c-4kqp
mcp.version=2026-07-28   mcp.method=tools/call   mcp.name=run_query
req.id=1                 result.type=complete    dur_ms=812
trace=00-4bf92f...-00f067aa0ba902b7-01
auth.sub=u_8391          tenant=acme             scope=files:read
retry.key=6f1c9a2e       stream=closed_by_client
  • 协议版本一定要留。 双世代服务器上，两种流量混在同一个端点进来。没有版本这根轴，只在旧世代路径上出现的 bug 永远分不出来。
  • 从头里取出方法名和目标名留下。 网关访问日志里也留同样的值，就能在不看请求体的情况下和应用日志对上。
  • 留下结果类型。 不区分以输入请求收尾的响应和已完成的响应，MRTR 的往返会被统计成失败，或者反过来，无限往返看上去很正常。
  • 区分流结束的原因。 客户端关的、服务器关的、中间设备掐的，是完全不同的事件。取消和故障混进同一个指标，就没法衡量发布的影响。
  • 把重试串起来的键由应用来造。 请求 ID 每次重试都变，光靠它复原不了一次逻辑尝试。得由幂等键或追踪 ID 来担这个角色。

指标上新增两个要看的。流早期终止率混着发布、代理超时和客户端取消，要和上面的原因分类一起看；MRTR 往返次数分布则因为往返越多载荷越大，直接关联到成本指标。

11. 没有确认的事项

本文的事实陈述来自 2026-07-28 修订版文档，以下超出这个范围，不作断言。

  • 各语言 SDK 何时正式支持这个修订版、从哪个版本开始，未做确认。请直接查看各 SDK 仓库的发布说明。
  • 主要客户端与宿主应用的采用时点、以及打算把双世代维持多久，没有找到公开的时间表。
  • 被归为待废弃的功能究竟会在哪个修订版里被移除，尚未确定。策略保证的只是至少 12 个月的缓冲期，符合快速移除例外的情况则至少 90 天。
  • 无状态转型的实测效果 — 单实例吞吐、尾延迟、成本变化 — 没有找到公开基准。本文的运维叙述是从规范要求或允许的行为推导出来的，不是测量值。
  • 扩展(Tasks、Apps 等)的稳定性等级和版本与核心分开演进。采用前需要单独确认各扩展仓库的状态。

常见问题(FAQ)

MCP 变成无状态之后，和 REST API 到底有什么区别?

变的是连接模型，不是协议存在的理由。MCP 标准化的从来不是通信方式，而是工具、资源、提示词的描述格式。有哪些工具、输入 schema 是什么，仍然可以用同一种方式向任何服务器询问。这个修订版只是把叠在上面的连接状态拿掉了。关于 MCP 价值的争论本身，在MCP已死? - Model Context Protocol的局限与2026年AI智能体集成的未来里另作讨论。

现有的 MCP 服务器需要马上改写吗?

不需要马上改。规范允许同时支持旧世代握手方式与新世代按请求方式的双世代实现。不过有些组合是注定失败的：新世代客户端连到只支持旧世代的服务器，或者反过来。所以实务上的顺序是先把服务器做成双世代，再看客户端采用情况逐步撤掉旧世代路径。

会话没有了，多步骤的操作怎么维持?

意思不是消除状态，而是把状态挪到协议之外。跨调用需要状态时，使用服务器签发的显式句柄，作为普通工具参数来回传递。存放处不再是会话对象而是共享存储，其生命周期与清理策略由服务器设计者决定。

负载均衡器上的粘性会话配置可以关掉吗?

只面向新世代的话，按请求路由是前提，不需要固定。但有两点要先看。还在接收旧世代客户端的话，那条路径仍然使用绑定连接的会话。另外长生命周期的通知流依然是开在某一个实例上的连接，而且不可恢复。去掉会话固定和期待流不中断是两个不同的问题。

转向无状态之后鉴权有什么变化?

一次认证然后绑到连接上的那个位置消失了。授权头必须出现在每一个请求里，服务器也必须每次确认令牌是以自己为受众签发的。实务上真正变化的是校验成本和失败点 — 过去只在连接建立时出现一次的鉴权错误，现在会出现在任何一次调用上，所以客户端需要一条能区分过期和权限不足的重试路径。

结论: 今天要做的三个判断

把这个修订版压缩成一句话，就是「把连接当作信任单位这个惯例的终结」。这个惯例很省事，但它把请求绑在特定实例上，而这种绑定决定着发布、扩展和故障处理的难度。结解开之后留下的位置上，基础设施拿走的收益和落到工具实现上的责任同时存在。

  • 先给自己的服务器挂在连接上的东西列个清单。 决定要不要迁移之前，发现在先。特别是如果你按连接给出不同的工具列表，那个设计在当前修订版下不成立。
  • 给有副作用的工具加上幂等键。 恢复没有了，重试就会变多。这件事和采不采用新修订版无关，现在做也不亏。
  • 把可观测性的轴重整为版本、方法、结果类型和流结束原因。 不提前造出替代会话 ID 做关联的轴，迁移之后的故障就复现不了。

剩下的判断是时机。把服务器做成双世代的成本，和守着旧世代、客户端却先迁走的成本，比一比就有答案。待废弃的功能带着至少 12 个月的缓冲期，并不紧迫。不过拆掉会话依赖这件事本身，和这个修订版无关也是划算的，这一点很清楚。
