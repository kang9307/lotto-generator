引言:比红色流水线更可怕的东西

大规模故障来临时,屏幕通常一片红。失败的作业、重试按钮、卡在队列里不动的任务。然而2026 年 8 月 6 日 GitHub Actions 故障中最贵的损失,并不是那些红色标记。而是压根没出现在列表里的那些运行。

GitHub 在关闭事故时公告,包括 push 与 pull request 在内的部分工作流触发事件未被处理,且无法自动重放。失败看得见,缺席看不见。检查列表为空的提交,在界面上很难和通过检查的提交区分开。而一旦这样的提交被合并,故障结束了,结果却留了下来。

本文不是故障播报。事件本身简短带过,重点落在把整条部署路径押在一家公司身上,这个决定实际上要付出什么账单。什么会停、什么照常运转,状态页显示正常而只有自己出问题时如何切分,以及为什么兴趣站去搭多云是净亏。

本文不是 Actions 使用教程。工作流语法、触发类型、job 与 step 的组织这些基础,已经在GitHub Actions与CI/CD - Git & GitHub 协作精通第5篇里讲过。这里只处理当那些工作流所依托的平台停摆时的判断。

事后报道和社区总结在时刻上略有出入。下面只取 GitHub 状态页事故更新里留下的内容。时间全部为 UTC,北京时间在此基础上加八小时。

  • 事故开启:2026 年 8 月 6 日 15 时 22 分 UTC。首条措辞是正在调查 Actions 性能降级的报告
  • 影响等级:critical。记录的组件为 Actions 与 Pages 两个
  • 宣布缓解:8 月 7 日 00 时 05 分 UTC。紧接其前的 00 时 01 分有一条更新称系统级队列已排空、新作业开始被处理

1.3 恢复曲线说明了什么

成功率从 30~40% 爬到 65%,再到 97% 与 99%,说明这不是把开关重新打开就能恢复的那一类。它是一边排空队列一边把正常处理比例往上抬的过程,所以中间时段每个用户的体感基本靠运气。

  • 恢复阶段 GitHub 主动限制了 Webhook 吞吐。这是为帮助恢复而采取的措施,有一条更新提到吞吐一度只有正常的约 15%
  • 在 Webhook 被限流期间,push 与 pull request 并不会产生新的工作流运行
  • 恢复阶段被点名的其他受影响项还包括 Copilot 代码评审、Copilot 编码智能体、托管 Runner、自托管 Runner、Webhook 投递,以及使用 GitHub Enterprise Importer 的迁移
  • 另有一条提示说,使用自托管 Runner 的客户在 Runner 注册时可能遇到错误或限流。这一句就说明,把 Runner 放到自己这边并不能消除对控制面的依赖

2. Actions 与 Pages 停摆时实际会停的东西

要设计任何备份措施,首先得把影响边界划准。这里常见的误判分两个方向。一个是认定 GitHub 一挂全都挂,另一个是认定静态站毫无关系。两个都不对。

2.1 会停的

  • 新部署。如果 Pages 部署走 Actions 工作流,那部署就是 CI。Actions 一停,新文章和新版本都上不去
  • 合并门禁。设了必需状态检查的仓库,在检查跑不起来期间无法合并。这其实是安全装置正常工作的结果
  • 发布自动化。打标签后构建、签名、附加产物的那条链路整条停掉
  • 定时任务。按 cron 跑的清理、备份、报表工作流,那个时间窗的执行就这么没了,不会排队等着以后补跑
  • 依赖 Actions API 的监控工具。通过 API 读取运行状态画看板的东西开始收到错误
  • 容器镜像的构建与推送链路。镜像仓库活着也没用,因为负责构建并推送的是 Actions

2.2 不会停的

  • 已部署并由别处提供访问的产物。构建产物若放在自有服务器或另一家 CDN 上,那条访问路径与 Actions 无关,照常运转
  • 本地开发。在已克隆的仓库里开分支、提交、跑测试全都能在本地完成。Git 本来就是分布式版本控制
  • 已经拉好的依赖。有锁文件和缓存,只要外部仓库还活着,构建本身在本机就能复现
  • 挂在其他 CI 上的流水线。仓库放在 GitHub 但构建跑在别的 Runner 上,只要能访问源码就能继续

2.3 这次没有分清的那条边界

最想知道的那一点,恰恰是公开记录分不出来的。Pages 显示降级,究竟只是新部署被卡住,还是已发布站点的访问也受了影响?状态页措辞没有区分这两种情况。社区帖里的报告压倒性地集中在部署失败,但那只是用户报告的分布,不是访问未受影响的证据。

在实务里,这个区分会整个改变备份措施的设计。下表把两种情况分开。

维度只有部署被卡住访问也受影响
用户体感站点打得开,内容是旧的站点打不开或间歇报错
损失性质新鲜度损失,通常可以补回收入与信任损失,补不回来
合理措施留产物加重试就够了访问路径双活才有正当理由
成本量级基本为零DNS、证书、同步都要花钱
判断标准这些内容能不能等半天一小时打不开会不会漏钱

结论是这样。在访问确实受影响这一点被证实之前,不要按访问会挂的前提去花预算。相反,把系统做到能扛住半天部署停摆,几乎不花钱。

3. 这次故障真正的账单 - 消失的触发

失败了十几个小时的流水线,重跑一遍就行。真正的成本在那之后。

3.1 Webhook 限流造成的静默失败

工作流不会自己跑起来,是 push 或 pull request 这样的事件把它拉起来的。那条投递路径为了帮助恢复被限流,而限流期间发生的相当一部分事件并没有堆进队列等着稍后投递,而是干脆没被处理。

由此产生的后果是这样的。

  • 提交完好地进了仓库,一行代码都没丢
  • 但挂在这个提交上的检查列表是空的。不是失败,是缺席
  • 没设必需检查的仓库,就以这个状态合并了。评审者看不到红色标记,自然察觉不到问题
  • 一个完全跳过 lint、测试与安全扫描的提交进入了默认分支
  • 几天后 CI 因为别的原因跑起来,那个提交的问题爆出来,锅却扣在毫不相干的最新改动上

GitHub 的指引很明确:推一个新提交、更新 pull request,或者在可行时手动重新运行工作流,把触发动作本身再做一遍。无法自动重放这句话就紧挨在旁边。

3.2 故障结束后必须过一遍的清单

事故关闭不等于事情做完了。下面是关闭之后需要人工确认的清单。

  • 落在故障窗口内的提交列表。把时钟对到 UTC,把那段时间的默认分支提交拉出来
  • 检查列表为空的提交。要找的不是失败的,而是什么都没挂上的。这是核心
  • 那段时间被合并的 pull request。人工审批做了,自动检查可能压根没跑
  • 定时工作流的缺号。看看每天跑的备份或清理是不是少了一天。这一项连失败通知都不会有
  • 部署状态与实际访问内容是否一致。确认最后一次成功部署带的确实是最新源码
  • 中途取消或强杀的作业的善后。锁文件、临时资源、传到一半的产物都可能还留着

最省事的做法,是在故障窗口刚过时往默认分支推一个空提交,把全套工作流跑一遍。这样至少能确认当前 HEAD 能通过检查。不过中途夹进去被合并的单个提交的问题,这招抓不到,上面那份清单还得单独过。

4. 状态页是绿的,只有自己的流水线在挂

像这次一样等级升到 critical,判断就容易了。难的是状态页显示正常而只有自己这边不动的情形。实务中这一类反而常见得多。

4.1 按顺序收敛

  • 第一步。看这条工作流最近有没有成功过。从没成功过,大概率是自己的改动
  • 第二步。在另一个仓库跑一条不相干的工作流。那个也不行,问题就在账号或组织层面
  • 第三步。分清失败发生在作业启动前还是启动后。之前是 Runner 分配与排队,之后是自己的脚本
  • 第四步。把同样的命令在本地跑一遍。本地能复现,那就不是基础设施故障
  • 第五步。走到这里还找不出原因,才去看状态页和社区的事故帖

这样排序的理由很简单。状态页永远是滞后的。这次同样如此,用户症状与首条调查公告之间有时差,等级升到最终水平又用了一个多小时。状态页是绿的,这不是没出故障的证据,而是还没有被统计进去的信息。

4.2 原因在自己这边时的信号

  • 失败只集中在某一个 job 或某一个 step
  • 报错很具体,比如找不到模块、没有权限之类
  • 把同一个提交重跑,仍然在同一处以同样的信息挂掉
  • 最近改过 action 版本、Runner 镜像、依赖锁文件三者之一
  • 其他仓库的工作流跑得好好的

4.3 原因在服务方时的信号

  • 作业根本没启动就在队列里待很久
  • 报错含糊,常见的是 Runner 没能领到作业这一类措辞
  • 每次重跑挂的位置都不一样。非确定性是很强的线索
  • 与自己代码毫无关系的工作流也一起失败
  • 网页界面或 API 响应比平时慢,或者间歇性报错

故障期间会让情况更糟的动作。一失败就条件反射地反复全量重跑。在恢复呈阶梯推进的阶段,大量重试会把队列重新撑起来,连自己的恢复也拖慢。这次恢复正是靠排空队列、把成功率往上抬完成的。重试更适合等成功率明显回升之后再集中做。

5. 你的部署路径上到底有几个单点

从这里开始才是正题。把部署押在 GitHub 上不是坏决定。但这个决定实际上把几个格子塞进了同一家公司,是要数一数的。

5.1 拆成四格

部署路径大体分成这四格。

  • 源码保管。代码住的地方,远端仓库
  • 触发。把事件变成运行的那一层,Webhook 与调度器
  • 算力。真正跑构建和测试的机器,Runner
  • 分发。把做好的产物送到用户面前的地方,托管与 CDN

看看典型配置里这四格是怎么摆的,就能立刻明白为什么一家公司的故障会把整条部署停掉。

  • 源码保管 = GitHub
  • 触发 = GitHub Webhook
  • 算力 = GitHub 托管 Runner
  • 分发 = GitHub Pages
  • 四格同属一家。这种配置下单点的数量不是 1,是 4

5.2 自托管 Runner 究竟能减掉哪一格

把 Runner 挪到自有基础设施上,看起来能把算力那一格抽掉,而这次事件恰好把这个期待反驳得干干净净。自托管这边同样报告了 Runner 注册时的错误与限流,跑在自建 Kubernetes 集群上的 Actions Runner Controller Runner 卡在空闲状态,需要人去删 Pod 或重新部署应用。

  • 即便 Runner 在自己的基础设施上,分配作业的控制面仍然是 GitHub
  • 所以自托管是把算力的容量和环境拿到自己手里的手段,不是切断控制面依赖的手段
  • 它反而在故障时多出一样要恢复的东西。清理卡死的 Runner Pod 是自己的活
  • 自托管的正当理由是安全边界、内网访问、特殊硬件和成本。可用性不在这份清单上

6. 各项备份措施的成本与效果

备份措施不是全做或全不做。从几乎零成本到相当昂贵有很多层,而多数情况下前三行就结束了。

6.1 从便宜的开始

措施成本对这一类故障的实际效果推荐对象
把构建产物留成 artifact近乎为零,工作流几行高。不用重建就能手动上传所有人
保持同一条命令在本地可构建低,靠纪律高。没有 CI 也能做出产物所有人
订阅状态页通知零中。缩短判断原因的时间所有人
强制必需状态检查零,设置一次高。挡住无检查提交的合并所有人
把故障后提交排查流程写成文档低高。抓回消失触发的唯一办法团队及以上
把部署脚本从 CI 里剥离中,一次重构中到高。人工也能做同样的部署有收入的服务
保持工作流可迁到别的 CI中,双份维护中。切换要时间,当天故障来不及团队及以上
分发路径双活(另一家托管常驻待命)高,DNS、证书、同步只在访问真的挂掉时有用可用性即收入的场合
仓库本身常态镜像高,权限、钩子、Issue 同步低到中。对这一类几乎无效有合规或合同要求的场合

6.2 这张表要读出的那一行

表格上面四行成本基本为零,效果却很高。下面两行成本很大,对这一类故障效果有限。可是故障刚过,大家开始讨论的通常是下面两行。顺序反了。

  • 留 artifact 就是在工作流里加一个上传步骤。故障期间,最后一次成功构建的产物就在手上
  • 本地构建的可复现性不是工具,是习惯。不去造那种只在 CI 里才跑得通的魔法流程,它自然就保住了
  • 必需状态检查从结构上挡住了这次故障造成的核心损失,也就是无检查提交。检查跑不了就合不进去,人自然会发现
  • 把部署脚本从 CI 专有语法里抽出来,同一份脚本就能在笔记本上执行,应付紧急发布

7. 从哪里开始算过度 - 按规模划线

大型故障之后总会跟着过度反应。多云在绝大多数情况下是净亏。把亏在哪里说准,讨论才能结束。

7.1 兴趣站与个人站

  • 部署晚半天什么也不损失。损失本身接近零,却往备份措施里投钱投时间,那就是净亏
  • 长期维持双托管会让这套结构本身变成新的故障源。DNS 切换、两套证书、重定向规则、同步脚本越堆越多
  • 实际上多数事故出在这些零件上,而不是服务方。用不上的备用路径会悄悄烂掉
  • 这里合理的上限是三件事:留产物、保持本地能构建、订阅状态通知。全都免费,全都今天就能做完
  • 非要再加一件,那就把静态产物压缩后定期丢到另一个仓库或云存储里

7.2 有收入的小规模服务

  • 标准变了。要把部署被卡住和服务打不开分开定价
  • 部署延迟通常扛得住。一个功能晚半天上线就让公司动摇的情况很少见
  • 访问中断是另一回事,这时双活才有正当理由。但要保的是托管与 DNS,不是 CI
  • 也就是说即便到了这个规模,给 CI 做双活通常仍是浪费。钱该花在访问路径上
  • 真正划算的是把部署脚本从 CI 语法里分离出来,故障期间人也能执行同一套流程

7.3 团队与公司规模

  • 从这里开始,损失按小时算。开发人数乘以小时数就是成本
  • 即便如此,第一笔投入也是流程而不是双活。事先定好谁来判断、按什么顺序排查,损失的大头就下来了
  • 给发布排期留余量,比做双活更便宜也更可靠
  • 真要评估 CI 双活,现实的形态是只让一条核心路径也能在别的 Runner 上跑,而不是复制整条流水线
  • 双活的路径必须定期真的跑起来。从不运行的备用路径,在故障当天一定会失败

8. 自建 Runner 能解决问题吗

前面已经提过一次,但这次的证据太干净,值得单列一节。这次故障中,用自托管 Runner 的那批人并没有更轻松。

  • Runner 注册阶段报告了错误和限流。Runner 进程在自己服务器上,但注册仍然要和 GitHub 通信
  • 在 Kubernetes 上通过 Actions Runner Controller 跑 Runner 的,遇到了 Pod 卡在空闲状态的现象
  • GitHub 的指引是用 kubectl 删掉这些 Pod,或者重新部署 ARC 应用,之后替换的 Runner 会自动创建
  • 换句话说,在恢复的最后一段,需要动手的恰恰是拥有自建集群的那一方
  • 只用托管 Runner 的,等队列排空就行了

这个对比不是在说自托管不好,而是在说把可用性从自托管的理由清单里划掉。需要访问内网资源、需要特定 GPU、长时任务成本吃紧、合规上必须掌控构建环境,这些理由下自托管是对的。出问题的是因为这些理由引入之后,还顺带期待可用性也跟着变好。

9. 给发布排期留余量的实操

最便宜的备份不是技术,是排期。而这跟周五不发布那类话题是两码事。

9.1 重试预算这个概念

  • 在发布计划里明确写上假定部署第一次会失败所留的余量时间。几个小时就够
  • 有余量,故障期间就不会冒出硬推的决定。硬推的决定大多是因为没余量
  • 绑了对外公告的发布,要把部署完成和公告时刻分开。部署提前做,公开切换放后面
  • 静态站的自然做法是先把产物做好,发布动作留到后面
  • 发布规模越大,流水线重试次数越多。余量按规模等比例留

9.2 故障期间不该做的决定

  • 临时关掉检查。因为着急就解除必需状态检查,等于亲手制造这次故障造成的那种损失
  • 给流水线做大手术。故障期间大改工作流,事后就分不清原因究竟出在哪
  • 临时迁到别的 CI。毫无准备的迁移当天做不完,做完也只剩一条没验证过的流水线
  • 大量重跑。会在恢复阶段把队列重新撑起来
  • 手动部署不留痕。如果情急之下手动上线了,一定要记录部署了什么、来自哪个提交。下一次自动部署可能把它覆盖掉

10. 未能确认的部分

把没有确凿依据的条目集中放在这里。

  • 根因。GitHub 在 15 时 45 分 UTC 的更新里说已定位到造成中断的来源,但直到事故关闭都没有公开那个来源是什么
  • 恢复阶段那些说法的定位。被分配失效作业的 Runner、卡在空闲的 ARC Pod,是作为症状与缓解对象被提到的,没有被确认为对原因的描述
  • 已发布 Pages 站点的访问是否受影响。究竟只是部署被卡住还是访问也受影响,从公开措辞里分不出来
  • 社区流传的原因解释。把负载增长或基础设施迁移指为原因的说法,来源不是 GitHub。本文不当作事实处理
  • 影响规模的绝对数字。有多少仓库、多少次运行受影响,没有确认到公开数字
  • SLA 是否补偿。这次事故如何适用信用额度政策,公开记录里未能确认
  • 事后详细报告是否发布及时间。成文时尚未见到,之后可能会更新
  • Webhook 限流区间的确切起止时刻。15% 这个数字出现在恢复阶段的更新里,但开始限流与完全解除的时刻没有精确到分钟

11. 常见问题

这次 GitHub 故障什么时候开始、什么时候结束?

按 GitHub 状态页记录,事故于 2026 年 8 月 6 日 15 时 22 分 UTC 开启,8 月 7 日 02 时 04 分 UTC 关闭,整个窗口为 10 小时 42 分。但这个数字不能直接当成停机时长。中间另有缓解完成的时点:8 月 7 日 00 时 05 分 UTC 的更新称系统级队列已排空、降级已缓解。之后约两个小时用于收尾,处理 Actions Runner Controller Runner 恢复滞后的尾巴。换算成北京时间,事故于 8 月 6 日 23 时 22 分开启,8 月 7 日上午 10 时 04 分关闭。

GitHub 公开根因了吗?

没有。状态页 15 时 45 分 UTC 的更新称已定位到造成中断的来源并正在实施缓解,但那个来源究竟是什么,直到事故关闭都没有写出来。恢复阶段出现的说法,比如 Runner 不断被分配已经失效的作业,或者 Actions Runner Controller 的 Pod 卡在空闲状态,描述的是症状与缓解对象,而不是根因陈述。网上流传的几种解释来自社区推测而非 GitHub,不宜当作事实转述。

故障期间推送的提交没跑 CI 会怎样?

不会自动回来。GitHub 在最后一条更新中说明,包括 push 与 pull request 在内的部分工作流触发事件在事故期间未被处理,且无法自动重放。补救办法是重复触发动作本身:推一个新提交、更新 pull request,或者在可行时手动重新运行工作流。实务中真正危险的不是失败的流水线,而是根本没出现在列表里的那一条。红色标记很显眼,而一次运行都没有的提交在界面上不留痕迹,看起来和通过检查的提交没有区别。

已经发布的 GitHub Pages 站点还在正常访问吗?

这一点公开记录分不出来。Pages 被列为受影响组件,并在降级与正常之间来回切换,但公开措辞始终没有区分两种截然不同的情况:新部署被卡住,以及已发布站点的访问受影响。社区帖子里报告的症状绝大多数是部署失败。但那只是用户报告的分布,并不能证明访问没有受影响。因此本文不做任何以访问正常为前提的判断,而是把这个问题单独归入未能确认的条目。

个人博客也需要提前准备第二家托管吗?

多数情况下不需要。兴趣站和个人站长期维持双托管,这套结构本身就会变成新的故障源。DNS 切换、两套证书、重定向规则、同步脚本越堆越多,通常先出问题的是这些零件而不是服务商。如果部署晚半天并不造成损失,三件事就够了。第一,把构建产物留成 artifact,不必从头重建。第二,偶尔确认同一条命令在本地仍能构建。第三,订阅状态页通知,缩短判断是故障还是自己失误的时间。

结论:今天带走三件事

第一,这次故障的损失是缺席,不是失败。红了十几个小时的流水线重跑一遍就行。问题出在触发本身没被处理、运行列表里什么都没留下的那些提交,而它们不会自动回来。故障结束后有没有一套让人去排查那段提交的流程,才决定了实际损失。

第二,单点的数量按格子数,不按公司数。源码、触发、算力、分发四格都在一家公司手里,那家的故障就会把整条部署停掉。而只把 Runner 挪到自有基础设施,触发和控制面依旧原封不动。这次拥有自建集群的一方反而要手动清理 Pod,就是证据。

第三,别把备份措施的性价比顺序倒过来。留产物、本地可复现构建、必需状态检查、故障后排查流程,这四件事实上免费,却能挡住这一类损失的绝大部分。相反,分发路径双活和仓库镜像既贵,对这次这种部署被卡住的类型效果又有限。可故障之后的会上,先被提出来的永远是贵的那一边。

最后一句。状态页上的绿灯不是一切正常的证据,而是还没被统计进去的信息。这次同样如此,用户症状与公告之间、公告与等级上调之间都有时差。所以切分永远该从自己这边开始。把同一条命令在本地跑一遍花的那几分钟,胜过刷别人状态页耗掉的一小时。
