1. 経緯と背景 — バージョン2.1.277で伝えられたAGENTS.md対応の実態

一般的に、コーディングアシスタント環境ではプロジェクト全般の開発指針を標準的なMarkdownファイルとして伝達し、モデルの一貫した応答を促す方式が活用されています。

Claude Code環境では従来、CLAUDE.mdというファイル名がプロジェクト指示書の標準規格として機能してきました。2026年9月、バージョン2.1.277のリリースとともに情報が公開されました。Xの投稿として伝えられた文面によると、Thariqは「We're adding support for AGENTS.md to Claude Code. Starting today in version 2.1.277, if there is no CLAUDE.md in a folder, Claude will check for and use AGENTS.md. You can toggle this behavior in /config.」と表明しました。

GeekNewsによる二次要約では、この機能がClaude Codeの新たな拡張機構であるMods上に構築されたbuilt-in mod（内蔵モジュール）であり、ソースコード全体がリポジトリで公開されている旨が報じられました。要約では「個別のCLAUDE.mdを複製したりシンボリックリンクで接続したりする必要がなくなった」と整理されています。技術コミュニティの反応においても「待望の対応」といった歓迎のコメントが確認されました。

一次情報源であるリポジトリ内のREADME文書は、本プラグインの役割を端的に記述しています。READMEには「The agents-md mod allows Claude Code to read AGENTS.md files as instruction files, similar to how it reads CLAUDE.md files.」と説明されています。この文章の解釈としては、既定設定ではCLAUDE.mdが存在しない場合にのみAGENTS.mdが読み込まれるため、既存リポジトリのファイル構成に応じてモデルへ伝達される指示内容が変化します。

2. 基本動作原理 — 統合ではなく代替（claude-md-or-agents-md）の境界条件

公式READMEに記載されている標準のオプション値はclaude-md-or-agents-mdです。READMEに記述された実際の規則によると、プロジェクト固有の指示ファイルが存在しないプロジェクトに限り、CLAUDE.mdが読み込まれるべき位置にAGENTS.mdを代わりに読み込むと規定されています。

READMEでは「プロジェクト固有の指示ファイル（of its own）」の判定基準を次のように定義しています：

  • プロジェクトのルートディレクトリから現在の作業ディレクトリに至る探索経路上において、CLAUDE.md、.claude/CLAUDE.md、またはCLAUDE.local.mdのいずれかをエンジンがコンテキスト向けに読み込んだ場合。
  • 上記3つの指示ファイルのいずれか1つでも検出された場合、プロジェクト全体の指示書処理は既存エンジンに完全に委ねられ、プラグインはコンテキストに一切介入せず停止状態を保ちます（leaves the whole project to the engine, and the plugin stays out）。
  • 一方で、組織が集中管理する管理ファイル、ユーザーのホームディレクトリにある~/.claude/CLAUDE.md、.claude/rulesファイル、および--add-dirで追加されたディレクトリ内のCLAUDE.mdは、ネスト探索の走査対象外であるため、プロジェクト自身のファイルとしてはカウントされません。
  • 経路上に独自の指示ファイルが一切存在しない場合にのみ、その探索経路上にあるすべてのAGENTS.mdおよび.claude/AGENTS.mdがエンジンによって指示ファイル一覧へ結合されます。

単一ディレクトリ内における優先度判定も明確です。同一フォルダ内にCLAUDE.mdとAGENTS.mdが併存している場合、CLAUDE.mdがそのディレクトリの指示権を占有し、AGENTS.mdは完全に無視されます。既定の設定では、既存リポジトリにCLAUDE.mdが残っている限り、追加配置されたAGENTS.mdはモデルへ伝達されません。

この文章の解釈としては、既定値ではCLAUDE.mdが1つでもあればAGENTS.mdは読み込まれないため、両ファイルを併用するにはマージモードを明示的に選択する必要があります。

3. 4つのinstructionFilesオプションと読込ポリシーの比較

READMEによると、この内蔵プラグインはinstructionFilesという単一のオプション設定によって制御され、4つの排他的なモードを提供します。各モードはエンジンの標準ローダーとプラグイン間のファイル注入動作を切り替えます。

公式仕様に記載された4つのオプションの定義は以下の通りです：

  • claude-md: エンジンが従来通りCLAUDE.mdのみを読み込み、プラグインはコンテキストへ何も追加しません。
  • claude-md-or-agents-md: プラグインの既定値です。プロジェクト固有の指示ファイルが存在しない場合に限り、AGENTS.mdファイルを代わりに注入します。
  • claude-md-and-agents-md: ディレクトリツリー全体のすべてのAGENTS.mdをCLAUDE.mdと並行して読み込みます。すでにインポートやリンクされているファイルは重複排除されます。
  • managed-only: プロジェクトのリポジトリ内指示ファイル、ローカル非公開ファイル、ユーザー個人設定ファイルをすべてコンテキストから除外除外し、組織管理の指示書とエンジンメモリのみを残します。

以下の表は、READMEの記述に基づき、4つのモードにおける読み込み対象ファイルと適用条件を整理して比較したものです。

オプション設定値 モデルのコンテキストに読み込まれる対象 既定値の有無および動作適用条件
claude-md エンジンが探索する標準のCLAUDE.mdのみ 非既定値。プラグインは何の追加も行わずエンジン単独動作となる
claude-md-or-agents-md 独自のCLAUDE.mdが存在しない場合のみAGENTS.md 既定値（default）。リポジトリに独自指示書があればプラグインは除外される
claude-md-and-agents-md ツリー全体のCLAUDE.mdとAGENTS.mdを同時マージ 非既定値。両体系を共存させ、パスと内容の二段階比較により重複排除を行う
managed-only 組織管理下のCLAUDE.mdおよびエンジンセッションメモリのみ 非既定値。プロジェクトローカルやユーザー個人の指示書をコンテキストから明示的に排除する

READMEでは、これらのファイルがモデルへ伝達される内部アーキテクチャについても詳述されています。ファイル伝達の最終責務はプラグインではなくエンジン側にあります。フックprompt.contextがclaudeMdの配下にある指示ファイル群（オブジェクト構造{ path, kind, content, parent? }、種別はmanaged、user, project, local, memoryの順序）をプラグインへ渡し、フックが変更後の一覧を返却します。エンジンは返却されたファイルを独自の前文とフレーミングで描画し、ファイル名をコンソールへ通知した上で、指示書を省略するサブエージェント（Explore、Plan、またはomitClaudeMd付きエージェント）向けにはmanagedファイルのみを保持します。

この文章の解釈としては、4つのオプションによりプロジェクト指示書の取り込み有無と読込範囲が決定論的に分岐します。

4. 状況別の探索規則 — 同一ディレクトリ、サブディレクトリRead、シンボリックリンク

プロジェクトの構成が階層化するにつれ、どのディレクトリ階層にある指示ファイルがどの契機で読み込まれるかを把握することが重要となります。READMEにはファイル探索に関する挙動が規定されています。

サブディレクトリに配置されたAGENTS.mdの読込タイミングについて、READMEには次の一文が明記されています：「Nested AGENTS.md files attach on text Read operations only」。エージェントがテキストのReadツールを用いて特定ソースコードを閲覧した際に、プロジェクトルートと対象ファイルの中間に位置するディレクトリを遡り、経路上に存在するAGENTS.mdがそのターンのコンテキストへ添付されます。この走査時においても、対象ディレクトリにCLAUDE.mdが存在していればそちらが優先権を獲得し、AGENTS.mdは添付されません。

以下の表は、開発現場で遭遇しやすい具体的なファイル構成パターンと各モードでの読み込み結果を示したものです。

想定シナリオとディレクトリ構成 適用設定モード 実際の読み込み結果と動作
ルートにCLAUDE.mdとAGENTS.mdが共存 claude-md-or-agents-md（既定値） CLAUDE.mdが優先され、AGENTS.mdは完全に無視される
リポジトリ全体でCLAUDE.mdがなくAGENTS.mdのみ存在 claude-md-or-agents-md（既定値） CLAUDE.mdが読み込まれるスロットにAGENTS.mdが代替注入される
ルートにCLAUDE.md、配下パッケージにAGENTS.md claude-md-or-agents-md（既定値） ルートに独自指示書があるため、配下のAGENTS.mdも一切読み込まれない
ルートにCLAUDE.md、配下パッケージにAGENTS.md claude-md-and-agents-md（マージ） 配下ファイルをテキストReadで読んだ際に該当パスのAGENTS.mdが添付される
AGENTS.mdからCLAUDE.mdへのシンボリックリンク claude-md-and-agents-md（マージ） パス文字列比較および内容比較により同一性が検知され、二重読込が防止される

シンボリックリンクの取り扱いに関しても仕様が存在します。READMEによると、プラグインはパスの重複判定において、エンジンのようにシンボリックエイリアスを実体パスへ解決することはせず、パス文字列の綴り（spelling）に基づいて直接比較を行います。ファイルシステムでパス表記が異なって渡された場合、エンジンのファイル探索とプラグインの重複判定に差異が生じる可能性があります。

この文章の解釈としては、サブディレクトリのAGENTS.mdはテキストRead操作前の通常の対話段階ではコンテキストへ含まれません。

5. @インポート承認と重複防止 — claude-md-and-agents-mdマージモードの挙動

両方の規格を同時に読み込むclaude-md-and-agents-mdモードを有効化した場合、@構文による外部指示ファイルの取り扱いが重要となります。

READMEには、重複を防止するためのプロトコルが記述されています：

  • CLAUDE.mdがすでに@構文によってインポートしているファイル、またはリンク先となっているファイルは、二重に読み込まれることはありません。
  • 重複判定のアルゴリズムは、まずファイルパスの文字列を比較し、パスが異なる場合にはファイルの内容（content）を直接比較する二段階の手順を踏みます。
  • AGENTS.md内部で使用された@インポート構文についても即座に挿入されることはなく、CLAUDE.mdと全く同一の外部インポート承認（approval）手続きを通過する必要があります。
  • ユーザーによって明示的に承認されていない外部ファイルは、プロンプトフレームから安全に除外されます。

この文章の解釈としては、パスが異なっていても内容が同一であれば重複読み込みが防止され、外部ファイルインポートは承認を経たもののみが反映されます。

6. 組織ガバナンスとmanaged-onlyモードによるコンテキスト隔離

組織環境では、個別のリポジトリ指示書を統制する要求が生じます。managed-onlyオプションは、ガバナンスのための隔離設定です。

READMEによると、managed-onlyモードが適用された際の挙動は以下の通りです：

  • リポジトリにコミットされた指示ファイル（CLAUDE.md、AGENTS.md）、ローカル個別ファイル（CLAUDE.local.md）、およびユーザー個人ファイル（~/.claude/CLAUDE.md）がコンテキストから除外されます。
  • 組織の中央リポジトリ等から配信される管理型CLAUDE.mdおよびエンジン自体のセッションメモリのみがコンテキストに残留します。
  • エンジンが標準提供するclaudeMdExcludes除外設定も引き続き有効に機能し、本プラグインが読み取るAGENTS.md群にも同一ルールが適用されます。
  • 組織レベルでprompt.contextの先頭に事前挿入されたプラグインは本プラグインより上位に配置され、最終的な指示ファイル群に対する決定権限を維持します。

ただし、READMEには細部として、テキストRead時にエンジンが内部的に行うネストされたCLAUDE.mdの動的添付処理については、現時点でフックイベント化されていないため、managed-onlyモード下であっても依然として到達しうる（still arrive）という仕様が明記されています。ソースコードのregister.tsでも、Files.DROPPED_KINDSに該当するファイルをFiles.isKeptWithoutInstructions関数によってフィルタリングするフックが登録されていることを確認できます。

この文章の解釈としては、managed-onlyモードではリポジトリ内部の指示ファイルが除外され、組織管理ファイルとエンジンメモリのみが残存します。

7. 設定手順と下位互換性 — /config、JSON設定、旧キーの移行

本プラグインの設定インターフェースは、対話型CLIコマンドおよび静的設定ファイルの双方から利用可能です。公式READMEには設定項目名や記述形式が示されています。

ターミナル上の対話操作では、/configコマンドを実行して表示される設定一覧のうち、「Project instructions」の行を選択します。READMEの説明によると、この項目は4つの値を切り替えるセレクター（picker）として機能し、各選択肢の解説が画面上に表示されます。

設定ファイルを手動編集する場合は、ユーザー設定ファイル（~/.claude/settings.json）、CLI起動時の--settings引数で渡す設定ファイル、または組織の管理プロファイル内に以下のJSONブロックを追記します。READMEに記載された設定JSONは以下の通りです：

{
  "pluginConfigs": {
    "agents-md@builtin": {
      "options": { "instructionFiles": "claude-md-and-agents-md" }
    }
  }
}

個別プロジェクト直下の.claude/settings.jsonファイルはプラグインオプションの読込対象外となっています。READMEには、プラグイン設定はユーザー共通設定または管理型設定からのみ認識されると記されています。設定を変更するとモジュールが即時再読み込みされ、次ターンの応答、新規セッションの開始、/clear実行、またはコンテキスト圧縮（compaction）のタイミングから新たな設定モードが反映されます。

手動設定で規定の4値以外の不正な文字列が入力された場合は、セッションログ（トランスクリプト）に1度だけ警告が出力され、自動的に既定値であるclaude-md-or-agents-mdとして処理されます。また、/plugin一覧にも内蔵プラグインとして表示され、ユーザーが手動で無効化することも可能です。プラグインをオフにした場合、エンジンは従来通りCLAUDE.mdのみを読み込みます。

設定キーの移行互換性についてもドキュメントに記されています。当初この設定キーはprojectInstructionsと呼ばれており、取りうる値はclaude、agents-fallback、both、noneでした。READMEおよびregister.tsの実装によると、旧キーが設定に残っている場合、instructionFilesが既定値のままである間に限り、以下のようにマッピングされて解釈されます：

  • none → managed-only
  • claude → claude-md
  • agents-fallback → claude-md-or-agents-md
  • both → claude-md-and-agents-md

その他の値は安全側に倒して何も追加しないclaude-mdとしてマッピングされます。セッション開始時のsession.startイベントにおいて、旧キーがどのように読み取られたかが記録されます。その後、新キーであるinstructionFilesに明示的な値が設定されると旧キーは完全に無視されるようになり、設定ファイルから旧キーを削除するよう促すメッセージが表示されます。

8. 実務上の検証手順と留意点 — テスト実行コマンドと設計トレードオフ

公式リポジトリのディレクトリ構成を確認すると、本モジュールは.claude-pluginマニフェスト、フック処理を含むhooks/（エントリーポイントregister.tsを含む）、動作テスト群を含むtests/、およびREADME.mdから構成されています。プラグインの単体テストは、READMEに示されている以下の公式コマンドで実行できます：

claude plugin test mods/agents-md

実務のエンジニアリング現場でこの新機能を適用するにあたり、設計上留意すべき事項は以下の通りです：

  • 指示書のサイレント無視リスク: 既定値のclaude-md-or-agents-mdでは、ルートにCLAUDE.mdが存在するだけで配下のAGENTS.mdが読み込まれません。AGENTS.mdを反映させるには設定をclaude-md-and-agents-mdへ切り替える必要があります（この文章の解釈）。
  • モノレポでの動的読込タイミング: サブパッケージの指示書は対象ファイルをテキストReadで読んだ瞬間にのみ添付されます。そのため、ファイル閲覧前の全体計画段階では下位ルールがモデルへ伝達されていません（この文章の解釈）。
  • シンボリックリンクの表記揺れ: パス判定が文字列の完全一致で行われるため、相対パス表記が異なると重複排除ロジックが適用されない場合があります（この文章の解釈）。
  • チーム内での設定乖離: プラグイン設定はプロジェクト内の.claude/settings.jsonではなくユーザー個別設定に保存されます。そのため、メンバー間で設定値が異なると同一リポジトリでも読み込まれる指示ファイルに差異が生じます（この文章の解釈）。

この文章の解釈としては、既定動作が自動統合ではなく条件付き代替であるため、プロジェクトのファイル構成に合わせてinstructionFilesモードを明示的に設定する必要があります。
