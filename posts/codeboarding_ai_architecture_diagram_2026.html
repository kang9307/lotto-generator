1. 서론: 아키텍처 다이어그램은 왜 항상 낡아있는가

2026년 5월 29일 news.hada.io 신규 글 목록에 CodeBoarding이 22점으로 올라왔다. 한 줄 설명은 "정적 분석과 LLM 추론으로 인터랙티브 아키텍처 다이어그램을 생성한다"였다. 짧은 소개였지만 나는 이 토픽을 보자마자 지난 10년간 모든 개발팀이 조용히 포기해온 한 가지 문제를 정면으로 겨냥하고 있다고 느꼈다. 바로 아키텍처 다이어그램은 그려지는 순간부터 낡기 시작한다는 문제다.

현장에서 일해본 사람이라면 누구나 안다. 새 프로젝트가 시작될 때 누군가 정성껏 박스와 화살표로 시스템 구조를 그린다. 위키에 올라가고 온보딩 문서에 박힌다. 그리고 6개월이 지나면 그 그림은 거짓말이 된다. 코드는 리팩토링되고 모듈은 쪼개지고 새 서비스가 끼어들지만, 다이어그램은 아무도 손대지 않는다. 그림을 수정하는 일이 코드를 수정하는 일과 완전히 분리되어 있기 때문이다. 결국 신입 개발자는 낡은 그림을 믿었다가 헤매고, 시니어는 "그 그림 보지 말고 나한테 물어봐"라고 말하게 된다.

나는 이 현상을 다이어그램 부채(diagram debt)라고 부른다. 기술 부채의 사촌이지만 더 교묘하다. 코드 부채는 빌드가 깨지거나 버그로 드러나지만, 낡은 다이어그램은 아무 경고 없이 사람의 머릿속에 잘못된 지도를 심는다. CodeBoarding이 던지는 제안은 단순하다. 그림을 사람이 그리지 말고 코드에서 자동으로 뽑아내자는 것이다. 코드가 진실의 원천(source of truth)이라면, 그 코드를 읽어 그림을 만들면 그림은 영원히 코드와 동기화된다. 이 글에서는 CodeBoarding의 작동 원리, 기존 도구와의 결정적 차이, 코드 지식 그래프 인프라와의 관계, 그리고 한국의 대규모 레거시 환경에 어떻게 적용할지를 13개 챕터에 걸쳐 운영자의 시각으로 풀어본다. 2. CodeBoarding이란 - 정적 분석과 LLM의 결합

CodeBoarding을 한 문장으로 정의하면 코드베이스를 입력으로 받아 인터랙티브 아키텍처 다이어그램을 출력으로 내놓는 자동화 도구다. 핵심은 두 가지 기술을 결합했다는 점에 있다. 하나는 정적 분석(static analysis)이고 다른 하나는 LLM 추론이다. 이 둘의 분업이 CodeBoarding을 기존 도구와 구분 짓는 결정적 차이다.

정적 분석은 코드를 실행하지 않고 소스 자체를 파싱해 구조 정보를 뽑아내는 기술이다. tree-sitter 계열 파서로 추상 구문 트리(AST)를 만들고, 어떤 함수가 어떤 함수를 호출하는지, 어떤 모듈이 무엇을 import 하는지, 클래스 상속 관계가 어떤지를 사실 그대로 추출한다. 이 단계는 거짓말을 하지 않는다. 코드에 적힌 그대로다. 문제는 이 정보가 너무 저수준이라는 점이다. 함수 5천 개와 호출 엣지 3만 개를 그대로 그리면 사람은 아무것도 읽을 수 없다.

여기서 LLM이 등장한다. LLM은 그 거대한 그래프를 보고 사람의 언어로 의미를 부여한다. "이 함수 묶음은 사실 인증 컴포넌트야", "이쪽 모듈들은 데이터 접근 계층이고 저쪽은 API 계층이야", "이 세 클래스가 결제 도메인을 이룬다"처럼 묶고 이름 붙이고 계층을 나눈다. 정적 분석이 사실(fact)을 제공하고 LLM이 의미(meaning)를 부여하는 구조다. 이 분업이 중요한 이유는 명확하다. LLM 혼자 코드를 읽으면 환각으로 없는 의존성을 지어내고, 정적 분석 혼자 그리면 사람이 읽을 수 없는 스파게티가 나온다. 둘을 합쳐야 정확하면서도 읽을 수 있는 그림이 된다.

3. 어떻게 작동하는가 - AST에서 인터랙티브 다이어그램까지

CodeBoarding의 파이프라인을 직접 돌려보며 정리한 네 단계는 다음과 같다.

3-1) AST 파싱 - 코드를 노드로

첫 단계는 소스 코드를 파싱해 추상 구문 트리를 만드는 것이다. tree-sitter는 30개 이상 언어를 지원하므로 Python, Java, TypeScript, Go 등 대부분의 실무 언어를 다룰 수 있다. 이 단계에서 함수, 클래스, 메서드, 모듈이 각각 하나의 노드가 된다. 100만 줄 규모 프로젝트면 수십만 개의 노드가 생긴다.

3-2) 의존성 그래프 구성 - 노드를 엣지로 연결

두 번째는 노드 사이의 관계를 엣지로 연결하는 단계다. A 함수가 B 함수를 호출하면 call 엣지, 모듈 X가 모듈 Y를 import 하면 import 엣지, 클래스가 다른 클래스를 상속하면 inherits 엣지가 생긴다. 이렇게 의존성 그래프(dependency graph)가 완성된다. 이 그래프가 코드의 골격이다.

3-3) LLM 의미 해석 - 그래프를 컴포넌트로

세 번째가 CodeBoarding의 진짜 차별점이다. LLM이 의존성 그래프를 입력으로 받아 어떤 노드 묶음이 하나의 논리적 컴포넌트인지 판단한다. 호출 밀도가 높은 노드들을 묶고, 의미 있는 이름을 붙이고, 계층 관계를 추론한다. 사람이 화이트보드 앞에서 하는 일을 LLM이 대신하는 셈이다. 이 단계 덕분에 결과물이 "함수 호출 그래프"가 아니라 "아키텍처 그림"이 된다.

3-4) 인터랙티브 다이어그램 렌더링

마지막은 해석 결과를 클릭 가능한 인터랙티브 다이어그램으로 그리는 단계다. 컴포넌트를 클릭하면 내부 모듈로 드릴다운하고, 엣지를 따라가면 실제 코드 위치로 점프한다. 정적인 PNG 그림이 아니라 코드를 탐색하는 지도가 된다. 결과물을 Mermaid 코드나 HTML로 내보내 위키나 PR에 붙일 수도 있다.

4. 기존 다이어그램 도구와의 차이 - 수동 대 자동

아키텍처 다이어그램 도구는 새로운 게 아니다. Mermaid, PlantUML, draw.io는 이미 널리 쓰인다. 그런데 CodeBoarding은 근본적으로 다른 범주에 속한다. 핵심 차이를 표로 정리했다.

도구방식코드 동기화장점약점
Mermaid텍스트 수동 작성없음 (사람이 갱신)가볍고 Git 친화적코드와 즉시 낡음
PlantUML텍스트 수동 작성없음표현력 풍부학습 곡선, 수동 갱신
draw.ioGUI 수동 드로잉없음자유로운 시각화완전 수작업, 가장 빨리 낡음
CodeBoarding코드에서 자동 생성유지 (코드가 입력)항상 최신, 온보딩 즉시대규모 분할 필요, 인덱스 지연

표의 핵심은 코드 동기화 열에 있다. Mermaid, PlantUML, draw.io는 모두 사람이 그림을 그린다. 그래서 코드가 바뀌면 누군가 손으로 그림을 고쳐야 하고, 거의 항상 그 일은 미뤄진다. CodeBoarding은 코드를 입력으로 받아 그림을 출력하므로 사람의 손이 들어가지 않는다. 코드가 바뀌면 다시 돌려서 새 그림을 뽑으면 끝이다. 다만 둘을 대립으로 볼 필요는 없다. CodeBoarding이 만든 결과를 Mermaid 코드로 내보내면 기존 Git 기반 문서 워크플로에 그대로 얹을 수 있다. 나는 이 둘을 대체가 아니라 보완으로 본다.

5. 자동 아키텍처 매핑의 5가지 활용

CodeBoarding 같은 자동 매핑이 가장 빛나는 다섯 가지 실무 시나리오를 본인 경험 기준으로 정리했다.

  1. 온보딩 - 신입이 입사 첫날 코드베이스 전체 구조를 한눈에 본다. "이 함수는 어디서 호출되나요"를 시니어에게 묻지 않고 그림에서 클릭으로 확인한다. 첫 PR까지 걸리는 시간이 절반으로 준 팀을 본 적 있다.
  2. 리팩토링 - 모듈을 쪼개기 전에 현재 의존성 구조를 정확히 본다. 어떤 컴포넌트가 너무 많은 곳에 연결되어 있는지(높은 결합도) 그림으로 즉시 드러난다.
  3. 문서화 - 항상 최신인 아키텍처 문서가 자동으로 생긴다. 위키의 낡은 그림을 손으로 갱신하던 노동이 사라진다.
  4. 코드 리뷰 - 큰 PR이 들어올 때 변경이 전체 구조의 어디를 건드리는지 그림으로 본다. "이 변경이 무엇에 영향을 주는가"를 파악하는 리뷰어의 가장 무거운 작업이 가벼워진다.
  5. 레거시 분석 - 문서도 없고 원작자도 떠난 10년 묵은 코드를 해부할 때, 자동 생성 그림이 유일하게 믿을 수 있는 지도가 된다.

6. CodeGraph 등 코드 지식 그래프와의 관계

CodeBoarding을 제대로 이해하려면 2026년 코드 컨텍스트 인프라의 큰 흐름 속에 놓아야 한다. 며칠 전 다룬 CodeGraph 같은 코드 지식 그래프와의 관계가 특히 중요하다.

둘은 같은 기반을 공유한다. 코드를 텍스트 덩어리가 아니라 노드와 엣지의 그래프로 표현한다는 점이다. 그러나 출구가 다르다. CodeGraph는 그 그래프를 AI 코딩 에이전트의 컨텍스트 최적화에 쓴다. Claude Code나 Cursor가 정확한 노드만 가져가 토큰 비용을 줄이도록 돕는 백엔드 인프라다. 반면 CodeBoarding은 같은 그래프를 사람이 보는 시각적 아키텍처 문서로 출력한다. 기계가 읽는 그래프냐 사람이 읽는 그래프냐의 차이다.

2026년의 큰 그림은 분명하다. 코드를 그래프로 인덱싱하는 공통 레이어 위에 두 개의 출구가 자라고 있다. 하나는 에이전트용(CodeGraph 방향), 다른 하나는 사람용(CodeBoarding 방향)이다. 같은 인덱스를 양쪽이 공유하는 구조가 표준이 되어간다. 한 번 코드를 그래프로 만들어두면 에이전트도 쓰고 신입 개발자도 쓰는 셈이다. 이것이 내가 코드 지식 그래프를 차세대 인프라로 보는 이유다.

7. AI 에이전트와의 결합 - 에이전트가 아키텍처를 이해하면

여기서 한 발 더 나아간 질문이 생긴다. Claude Code나 Cursor 같은 AI 에이전트가 아키텍처 그림 자체를 이해하면 어떻게 될까?

지금까지 AI 코딩 에이전트의 약점은 구조 맹시(structural blindness)였다. 함수 단위로는 똑똑하게 코드를 짜지만, 시스템 전체의 큰 그림은 잘 못 본다. "이 변경이 결제 도메인 전체에 어떤 파급을 주는가" 같은 질문에 약하다. 그런데 CodeBoarding이 만든 컴포넌트 단위 아키텍처를 에이전트가 컨텍스트로 받으면, 에이전트는 비로소 높은 추상 수준에서 코드를 이해하게 된다.

구체적으로는 이런 시나리오다. 에이전트에게 "인증 컴포넌트에 OAuth를 추가해줘"라고 시키면, 아키텍처를 이해하는 에이전트는 인증 컴포넌트가 어떤 모듈로 구성되고 어디와 연결되는지 먼저 파악한 뒤 영향 범위를 좁혀 작업한다. 무작정 비슷한 코드를 긁어모으는 게 아니라 구조적으로 접근한다. 이것이 CodeBoarding의 아키텍처 출력과 CodeGraph의 에이전트 컨텍스트가 한 인덱스에서 만날 때 나오는 시너지다. 다이어그램은 사람만을 위한 것이 아니라 에이전트의 지도가 되기도 한다.

8. 실무 도입 시나리오와 한계

실제로 도입한다면 어떤 순서로, 어떤 함정을 조심해야 할까. 직접 검토한 도입 경로와 한계를 정리한다.

도입 경로. 먼저 중간 규모(10만~50만 줄)의 단일 서비스를 골라 한 번 돌려본다. 결과 그림을 시니어 두세 명에게 보여 "이게 실제 구조와 맞느냐"를 검증한다. 맞으면 CI 파이프라인에 점진적 인덱싱을 묶어 PR 머지마다 그림이 자동 갱신되도록 한다. 그 다음 위키나 PR 템플릿에 자동 생성 다이어그램 링크를 박는다. 이 순서를 지키면 "한 번 그리고 방치되는" 함정을 피할 수 있다.

한계 1 - 인덱스 동기화. 큰 PR이 머지된 직후 점진적 인덱싱이 따라잡지 못하면 다이어그램이 잠시 낡은 상태가 된다. 인덱싱을 머지 파이프라인에 강제로 묶어야 한다.

한계 2 - 대규모 모노레포. 수백만 줄 모노레포를 한 장에 담으면 아무도 못 읽는다. 패키지·도메인 단위로 잘라 계층적으로 그려야 한다. 한 장의 전체 그림은 환상이다. 현실은 여러 장의 도메인별 그림이다.

한계 3 - LLM 해석 오류. LLM이 컴포넌트 경계를 잘못 묶을 수 있다. 정적 분석이 제공하는 사실은 정확하지만, 의미 부여 단계는 확률적이다. 그래서 자동 생성 그림은 초안으로 보고 사람이 한 번 검수하는 단계가 여전히 필요하다.

9. 한국 IT 환경 적용 - 대규모 레거시와 SI 코드베이스

한국 IT 환경에서 CodeBoarding이 특히 가치 있는 이유가 셋 있다.

첫째, 대규모 레거시 모놀리스다. 네이버, 카카오, 쿠팡, 그리고 수많은 금융권 시스템은 10년 넘은 Java 모놀리스를 운영한다. 문서는 부실하고 원작자는 대부분 퇴사했다. 이런 코드베이스에 신입이 투입되면 구조 파악에만 몇 달이 걸린다. 자동 아키텍처 매핑은 이 온보딩 비용을 극적으로 줄인다.

둘째, SI 코드베이스의 인수인계다. 한국 SI 산업은 프로젝트가 끝나면 코드가 발주처로 넘어간다. 인수받은 측은 만든 사람도 문서도 없는 코드를 떠안는다. 이때 자동 생성 아키텍처 그림은 인수인계 품질을 좌우하는 핵심 자료가 된다. 발주 계약서에 "자동 생성 아키텍처 문서 납품"을 명시하는 흐름이 곧 올 것이라 본다.

셋째, 폐쇄망 환경이다. 금융·공공은 외부 LLM 직접 호출을 막는다. 다행히 CodeBoarding의 정적 분석 단계는 외부 호출이 필요 없고, 의미 해석 단계만 온프레미스 LLM(HyperCLOVA X, KT Mi:dm 등)으로 대체하면 폐쇄망에서도 돌릴 수 있다. 정적 분석과 LLM의 분업 구조가 폐쇄망 적용에 유리하게 작용하는 셈이다.

10. 개발자가 알아야 할 5가지 - 2026 코드 시각화 트렌드

CodeBoarding을 넘어 코드 시각화 카테고리 전체에서 2026년 하반기까지 주목할 다섯 가지 흐름을 정리한다.

  1. 다이어그램은 산출물이 아니라 함수가 된다. "그린다"에서 "코드에서 뽑는다"로 패러다임이 바뀐다. 다이어그램 = f(코드).
  2. 정적 분석과 LLM의 분업이 표준이 된다. 사실은 파서가, 의미는 LLM이. 어느 한쪽만으로는 부족하다는 합의가 굳어진다.
  3. 코드 그래프 위에 다중 출구가 자란다. 한 번 인덱싱한 그래프를 에이전트도, 사람도, 문서 도구도 함께 쓴다.
  4. 온보딩이 가장 큰 ROI 영역이 된다. 시니어가 인간 grep 역할에서 해방되는 효과가 가장 측정하기 쉽고 크다.
  5. 아키텍처가 에이전트의 입력이 된다. 그림이 사람만의 것이 아니라 AI 에이전트의 구조적 지도가 된다.

11. 위험과 한계

객관적으로 짚어야 할 한계를 다섯 가지로 정리한다. 모두 자동 매핑 도구 범주 전반의 한계이지 CodeBoarding만의 문제는 아니다.

  • 의미 해석의 확률성 - LLM이 컴포넌트 경계를 잘못 묶을 수 있다. 자동 그림은 초안이며 사람 검수가 필요하다.
  • 동적 코드의 한계 - 리플렉션, 메타프로그래밍, 동적 디스패치는 정적 분석으로 완전히 잡히지 않는다. Spring DI나 Rails처럼 동적 의존성이 많은 프레임워크에서 정확도가 떨어진다.
  • 대규모 가독성 - 수백만 줄을 한 장에 담으면 못 읽는다. 분할 전략이 필수다.
  • 인덱스 지연 - 점진적 인덱싱이 큰 변경을 못 따라가면 잠시 낡은 그림이 나온다.
  • 과신 위험 - 자동 생성이라는 이유로 무조건 믿으면 위험하다. 정적 분석의 정확성과 LLM 해석의 불확실성을 구분해 읽어야 한다.

이 다섯은 PoC 체크리스트에 반드시 올려야 한다. 기대치를 관리하지 않고 도입하면 경영진이 실망하는 가장 빠른 길이 된다.

12. 결론 + 즉시 적용 가능한 3가지

이 글을 한 문장으로 요약하면 이렇다. 아키텍처 다이어그램은 더 이상 사람이 손으로 그리는 산출물이 아니라 코드에서 자동으로 뽑아내는 함수가 되어가고 있으며, CodeBoarding은 정적 분석과 LLM 추론을 결합한 가장 또렷한 후보다. 다이어그램 부채라는 오랜 문제에 처음으로 자동화 해법이 등장한 것이다. 표준이 자리잡는 동안 개발자가 이번 주에 할 수 있는 세 가지를 제시한다.

  1. 가장 문서가 부실한 서비스 하나에 CodeBoarding을 돌려보라. 결과 그림을 시니어에게 보여 정확도를 검증하는 데 하루면 충분하다.
  2. 온보딩 문서의 손으로 그린 그림을 자동 생성 그림으로 교체하라. 갱신 노동이 사라지고 신입의 첫날이 달라진다.
  3. 코드를 그래프로 인덱싱하는 것을 표준으로 삼아라. CodeBoarding을 채택하지 않더라도, 그래프 인덱스는 에이전트용·문서용 양쪽에 재사용되는 가장 싼 보험이다.

함께 읽으면 좋은 글: CodeGraph - AI 코딩 에이전트를 위한 코드 지식 그래프, Flue - TypeScript 샌드박스 에이전트 프레임워크, 프로그래밍은 이론 구축이다 - AI 시대의 재해석. 코드 컨텍스트, 실행 환경, 그리고 프로그래밍의 본질이라는 세 각도를 함께 보면 헤드리스 에이전트 시대의 그림이 완성된다.
