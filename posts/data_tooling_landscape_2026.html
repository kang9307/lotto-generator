2026년 데이터 도구 지형

무엇이 있는가가 아니라, 무엇이 바뀌어서 선택 기준이 달라졌는가

2026-07-29 IT/기술

서론: 「일단 분산 처리부터」가 기본값이 아니게 된 이유

데이터 스택을 새로 짜야 할 때 가장 많이 던져지는 질문은 「요즘은 뭘 쓰나요」다. 이 질문에 도구 이름을 나열해 답하면 6개월 뒤 그 목록은 대부분 틀린 목록이 된다. 버전이 바뀌고, 프로젝트가 재단으로 옮겨가고, 어제까지 별개였던 두 도구가 같은 규약을 구현하기 시작한다. 목록은 낡지만 판단 기준은 덜 낡는다. 그래서 이 글은 카탈로그가 아니라 기준을 다룬다.

지난 몇 년 사이 데이터 처리·분석 스택에서 실제로 이동한 것은 세 가지다. 첫째, 단일 노드에서 처리 가능한 구간이 크게 넓어졌다. 둘째, 저장 포맷과 카탈로그가 엔진보다 상위 결정이 됐다. 셋째, 메모리 표현과 전송 규약이 표준화되면서 도구를 갈아 끼우는 비용이 구간별로 달라졌다. 이 세 이동이 「무엇을 고를 것인가」의 문법을 바꿨다.

먼저 원칙 하나를 못 박고 시작한다. 이 글에 적힌 사실은 전부 각 프로젝트의 공식 문서·공식 저장소에서 2026년 7월 29일에 직접 확인한 것이고, 확인하지 못한 항목은 아예 뺐다. 버전 번호는 확인 시점을 병기하며, 이 분야의 버전은 몇 주 단위로 바뀌므로 독자가 읽는 시점에는 달라져 있을 수 있다. 그리고 이 글은 특정 상용 제품을 권하지 않는다. 오픈소스 프로젝트와 상용 서비스는 구분해 표기한다.

1. 실제로 바뀐 것 - 공식 문서에서 확인된 사실만

변화를 체감으로 말하면 반박이 불가능한 주장이 된다. 그래서 먼저 확인 가능한 사실만 늘어놓는다.

  • 인프로세스 분석 엔진의 성숙 — DuckDB 공식 문서는 이 엔진이 별도 프로세스로 돌지 않고 호스트 프로세스 안에 완전히 임베드되며, 설치·갱신·유지할 DBMS 서버 소프트웨어가 없다고 밝힌다. 대상 워크로드는 OLAP, 즉 저장된 데이터셋의 상당 부분을 훑는 비교적 오래 걸리는 복잡한 질의다.
  • 단일 노드의 상한이 올라갔다 — 같은 문서는 자원이 제한된 엣지 장비부터 100개 이상의 CPU 코어를 가진 수 테라바이트 메모리 서버까지를 대상으로 하며, 지원하는 레이크하우스 포맷을 통해 페타바이트 규모까지 확장될 수 있다고 서술한다.
  • 램보다 큰 데이터가 곧 분산은 아니다 — Polars 공식 문서는 스트리밍 API가 모든 데이터를 동시에 메모리에 두지 않고 결과를 처리하게 하며 가용 램보다 훨씬 큰 데이터셋을 다룬다고 적는다. 엔진 자체는 Rust로 작성됐고 별도 설정 없이 가용 CPU 코어에 작업을 분배한다.
  • 테이블 포맷 명세가 세대를 넘겼다 — Apache Iceberg 명세는 버전 1(분석 데이터 테이블), 2(행 단위 삭제), 3(확장 타입과 기능)이 완료·채택 상태이고, 버전 4(메타데이터 구조와 표현)는 활발히 개발 중이며 아직 정식 채택되지 않았다고 기록한다.
  • 포맷 사이 번역 계층이 생겼다 — Delta Lake 공식 문서의 Universal Format, 그리고 Apache 인큐베이팅 프로젝트인 XTable이 각각 다른 방식으로 포맷 간 메타데이터 변환을 다룬다. 뒤에서 차이를 표로 정리한다.
  • 카탈로그가 공용 규약이 됐다 — Apache Polaris는 Iceberg의 REST API를 구현해 Apache Doris, Flink, Spark, Dremio OSS, StarRocks, Trino 등 여러 플랫폼 사이의 다중 엔진 상호운용을 가능하게 한다고 밝힌다.
  • 변환 도구의 코어가 다시 쓰였다 — dbt 공식 문서는 Fusion 엔진이 Rust로 작성됐고 여러 엔진 방언에 걸쳐 SQL을 네이티브하게 이해하며, 잘못된 SQL을 웨어하우스에 닿기 전에 잡는다고 설명한다. 해당 문서 페이지의 최종 갱신일은 2026년 7월 25일이다.
  • 오케스트레이터가 메이저 세대를 바꿨다 — Apache Airflow 릴리스 노트는 3.0.0이 2025년 4월 22일에 나왔고 태스크 실행 API와 Task SDK, React 기반 UI 재작성, DAG 버저닝, 자산 기반 스케줄링을 담았다고 적는다. 문서상 최신은 3.3.0(2026년 7월 6일)이다.

이 목록에서 이름보다 중요한 것은 방향이다. 계산은 더 작은 단위로 내려왔고, 저장과 메타데이터는 더 공용 규약 쪽으로 올라갔다. 아래부터는 이 방향이 실무 결정을 어떻게 바꾸는지를 순서대로 다룬다.

2. 데이터 크기의 현실 - 갈림길은 어디에 있나

이 글의 핵심 축은 여기다. 대부분의 조직이 실제로 다루는 데이터는 분산 처리가 필요한 규모가 아니다. 그런데 스택 설계는 여전히 「나중에 커질 테니까」를 근거로 가장 무거운 선택지에서 출발하는 일이 많다. 이 출발점은 두 가지 비용을 즉시 발생시킨다. 클러스터를 돌보는 사람의 시간, 그리고 개발 반복 속도의 저하다.

규모를 이야기할 때 흔한 오해가 하나 있다. 「데이터가 램보다 크다」를 분산의 근거로 삼는 것이다. 위에서 인용했듯 Polars 문서는 스트리밍 API로 램보다 큰 데이터셋을 다룬다고 명시하고, DuckDB 문서는 레이크하우스 포맷을 통해 페타바이트 규모로 확장될 수 있다고 적는다. 즉 크기 하나만으로는 갈림길이 되지 않는다. 실제로 갈리는 지점은 다음 표처럼 크기 외의 축에 있다.

표의 마지막 두 행이 실무에서 가장 자주 잘못 읽힌다. 분산이 필요한 진짜 이유는 데이터 크기가 아니라 실패 반경과 동시성인 경우가 많다. 잡 하나가 여섯 시간을 돌다 5시간 30분 지점에서 실패하면, 문제는 처리량이 아니라 재시도 단위다. 이 상황은 엔진을 바꿔서가 아니라 작업을 쪼개서 해결되는 경우가 훨씬 많다.

판단을 단순화할 질문 하나를 제안한다. 「이 작업을 장비 한 대에서 돌려본 적이 있는가」. 없다면 그 답을 먼저 만들어야 한다. 대표 워크로드 하나를 단일 노드에서 끝까지 돌려 실측한 뒤에야 분산이 필요한지 아닌지가 사실로 확정된다. 이 실측 없이 내리는 결정은 전부 추정이다.

3. 단일 노드 엔진이 실제로 커버하는 구간

단일 노드 접근이 넓어진 이유는 하드웨어와 소프트웨어 양쪽에 있다. 한 대에 담기는 코어와 메모리가 늘었고, 엔진이 그것을 쓰는 방식이 좋아졌다. 여기서 중요한 것은 두 엔진의 성격이 서로 다르다는 점이다.

DuckDB는 SQL 인터페이스를 가진 인프로세스 OLAP 엔진이다. 공식 문서는 설치·갱신·유지할 서버 소프트웨어가 없고 주요 운영체제와 CPU 아키텍처 전부로 컴파일된다고 밝힌다. 실무에서 이 성질이 주는 이득은 배포 단위가 라이브러리 하나로 끝난다는 것이다. 오브젝트 스토리지의 파일을 그대로 질의하는 형태가 가장 흔한 사용법이다.

-- 오브젝트 스토리지의 컬럼 파일을 그대로 질의한다
-- 파티션 경로를 조건으로 좁히는 것이 성능의 대부분을 결정한다
SELECT category,
       count(*)     AS n,
       sum(amount)  AS total
FROM 's3://bucket/events/year=2026/month=07/*.parquet'
WHERE amount > 0
GROUP BY category
ORDER BY total DESC
LIMIT 20;

Polars는 데이터프레임 API를 가진 엔진이다. 공식 문서 기준으로 Rust로 작성됐으며, 별도 설정 없이 가용 코어에 작업을 나누고, 스트리밍 API로 메모리보다 큰 데이터를 처리한다. Arrow 데이터를 대체로 무복사로 소비·생산하지만 내부 계산과 버퍼 구현은 자체적이라고 문서가 분명히 적어 둔다. 이 구분은 중요하다. Arrow와 상호운용된다는 말이 Arrow 구현체 위에 올라가 있다는 뜻은 아니다.

import polars as pl

# 스캔은 즉시 읽지 않는다. 조건과 컬럼 선택이 파일 읽기 단계까지 밀려 내려간다
q = (
    pl.scan_parquet("events/*.parquet")
      .filter(pl.col("amount") > 0)
      .group_by("category")
      .agg(
          pl.len().alias("n"),
          pl.col("amount").sum().alias("total"),
      )
      .sort("total", descending=True)
)

df = q.collect()      # 실행은 여기서 처음 일어난다
print(df.head(20))

두 코드의 공통점을 보자. 둘 다 읽을 파일을 좁히는 일이 성능의 대부분을 결정한다. 엔진 선택이 아니라 파티션 설계와 컬럼 선택이 먼저다. 이 사실은 뒤에서 다룰 「포맷이 먼저」라는 결론과 정확히 같은 곳을 가리킨다.

선택 기준을 정리하면 이렇다. SQL이 팀의 공용어이고 산출물이 테이블이면 SQL 엔진 쪽이, 파이프라인이 파이썬 코드 안에 있고 중간 단계에 파이썬 로직이 섞이면 데이터프레임 쪽이 마찰이 적다. 둘을 같이 쓰는 것도 정상이다. 다만 같은 변환을 두 곳에 중복 구현하는 순간 정합성 사고가 예약된다.

4. 포맷은 엔진보다 오래 산다

스택에서 수명이 가장 긴 결정은 데이터를 어떤 형태로 남기느냐다. 엔진은 프로세스다. 마음에 안 들면 다른 프로세스를 띄우면 된다. 반면 저장 포맷을 바꾸는 일은 보관된 데이터 전체를 다시 쓰는 작업이고, 카탈로그를 바꾸는 일은 그 데이터를 가리키는 모든 참조를 다시 쓰는 작업이다. 그래서 결정 순서는 포맷, 카탈로그, 엔진이어야 한다.

테이블 포맷이 파일 포맷과 다른 점부터 짚자. 컬럼 파일은 「이 파일 안에 무엇이 들었는가」만 안다. 테이블 포맷은 「이 테이블은 지금 어떤 파일들의 집합인가」를 원자적으로 관리한다. 여기서 스냅숏, 시간여행, 스키마 진화, 동시 쓰기 제어가 나온다.

세대 변화를 가장 명확히 문서화한 쪽은 Iceberg다. 명세는 각 버전을 이름과 상태로 구분한다. 버전 1은 분석 데이터 테이블, 버전 2는 행 단위 삭제, 버전 3은 확장 타입과 기능이며 셋 다 완료·채택 상태다. 버전 3이 추가한 항목으로 명세는 나노초 타임스탬프, unknown·variant·geometry·geography 타입, 컬럼 기본값, 다중 인자 파티션·정렬 변환, 행 계보 추적, 이진 삭제 벡터, 테이블 암호화 키를 든다. 버전 4는 메타데이터 구조와 표현을 다루며 아직 정식 채택되지 않은 개발 중 상태다.

이 목록을 실무 언어로 옮기면 이렇다. 삭제와 갱신이 싸졌고, 변형되는 반정형 데이터와 공간 데이터가 1급 시민이 됐고, 행 단위 추적과 암호화가 명세 안으로 들어왔다. 예전에는 애플리케이션이 떠안던 문제들이 포맷 계층으로 내려온 것이다. 그래서 「테이블 포맷을 쓸 것인가」는 이제 규모 질문이 아니라 운영 요구 질문이다. 감사 추적이 필요한가, 잘못 쓴 배치를 되돌려야 하는가, 스키마가 바뀌는가. 하나라도 예이면 이미 대상이다.

  • 버전 번호는 라이브러리와 명세가 다르다 — 명세 버전 3과 구현체 릴리스 번호는 별개다. 문서에서 어느 쪽을 말하는지 확인하지 않으면 호환성 판단이 어긋난다.
  • 쓰기 쪽이 항상 뒤따라온다 — 어떤 엔진이 새 명세를 「지원」한다고 할 때 읽기만인지 쓰기까지인지 확인해야 한다. 이 차이가 실제 이주 계획을 좌우한다.
  • 파티션 설계는 포맷이 대신해주지 않는다 — 잘못 잡은 파티션은 어떤 포맷에서도 전체 스캔을 유발한다. 가장 자주 쓰는 필터를 기준으로 잡는다.
  • 작은 파일 문제는 남는다 — 잦은 커밋은 파일 수를 늘린다. 압축·병합 작업을 운영 항목으로 세워두지 않으면 몇 달 뒤 질의가 느려진다.
  • 포맷을 정한 뒤에 엔진을 고른다 — 반대로 하면 엔진이 지원하는 포맷 목록이 조직의 저장 전략을 대신 결정한다.

5. 포맷 수렴은 어떤 형태로 일어나고 있나

「포맷 전쟁의 승자」식 서술은 대개 벤더 자료에서 나온다. 공식 자료만으로 말할 수 있는 것은 더 조심스럽지만 더 유용하다. 단일 포맷으로 통일되는 대신, 포맷 사이를 오가는 계층이 먼저 정착하고 있다. 확인된 접근은 두 가지로 성격이 다르다.

접근공식 문서가 밝히는 내용방향성실무상 제약
Delta Lake Universal FormatDelta 테이블을 Iceberg·Hudi 클라이언트로 읽게 하며, Delta 커밋 이후 비동기로 메타데이터를 생성Delta에서 다른 포맷으로 나가는 단방향Iceberg·Hudi 관점에서는 읽기 전용. 컬럼 매핑 활성화 등 전제 조건이 있음
Apache XTable (인큐베이팅)새 포맷이 아니라 레이크하우스 테이블 포맷 메타데이터를 번역하는 추상화와 도구Delta·Hudi·Iceberg 사이 전방향인큐베이팅 단계. 원본 포맷의 쓰기 주체는 여전히 하나로 정해야 함
Iceberg 명세 자체의 세대 진화v1·v2·v3 채택 완료, v4는 개발 중·미채택포맷 내부에서의 기능 흡수엔진별 지원 시점이 제각각. 읽기·쓰기 지원 범위를 개별 확인해야 함
DuckLake (MIT, DuckDB 재단)데이터는 Parquet, 카탈로그는 ACID와 기본 키를 지원하는 SQL 데이터베이스에 두는 레이크하우스 포맷. v1.0을 2026년 4월에 공개메타데이터를 파일이 아닌 DB로 옮기는 별도 노선데이터 파일은 Parquet만 지원. v1.1은 2026년 9월 예정으로 안내

표를 읽는 방법은 이렇다. 지금 시점에서 「하나만 고르면 안전하다」는 조건은 성립하지 않는다. 대신 「내 데이터가 다른 포맷의 독자에게 읽힐 경로가 있는가」가 실질적인 안전판이다. 단방향 변환만 있는 구성이라면 그 방향이 조직의 미래 선택지를 정한다. 전방향 번역 계층을 쓰더라도 쓰기 주체는 하나여야 한다는 원칙은 변하지 않는다. 두 시스템이 같은 테이블에 동시에 쓰기 시작하면 어떤 번역 계층도 정합성을 보장하지 못한다.

DuckLake는 다른 축의 사례로 볼 만하다. 메타데이터를 파일 트리가 아니라 SQL 데이터베이스에 두는 접근이며, 공식 FAQ는 이를 Unity Catalog와 함께 쓰는 Delta Lake, 또는 Lakekeeper·Polaris와 함께 쓰는 Iceberg와 비슷한 구성이라고 설명한다. 여기서 확인할 수 있는 것은 특정 제품의 우열이 아니라, 카탈로그가 별도 결정 항목으로 분리됐다는 사실이다.

6. 카탈로그가 새로운 결정 지점이 됐다

몇 년 전만 해도 카탈로그는 「메타스토어를 뭘 쓰지」 정도의 부차적 질문이었다. 지금은 다르다. 여러 엔진이 같은 테이블을 공유하는 구조에서 카탈로그는 접근 제어와 트랜잭션 경계가 만나는 지점이다. 그리고 이 지점이 표준화되고 있다.

공식 자료로 확인되는 대표 사례가 Apache Polaris다. 이 프로젝트는 스스로를 Apache Iceberg를 위한 오픈소스 카탈로그라고 소개하며, Iceberg의 REST API를 구현해 Apache Doris, Apache Flink, Apache Spark, Dremio OSS, StarRocks, Trino를 포함한 여러 플랫폼 사이의 다중 엔진 상호운용을 가능하게 한다고 밝힌다. 여기서 중요한 것은 제품명이 아니라 구조다. 카탈로그가 REST 규약으로 노출되면 엔진은 그 규약의 클라이언트가 되고, 클라이언트는 교체 가능한 부품이 된다.

반대 구조를 상상해 보면 왜 이것이 결정 지점인지 분명해진다. 카탈로그가 특정 플랫폼 내부에만 존재하면, 새 엔진을 붙일 때마다 그 플랫폼이 그 엔진을 지원하느냐를 물어야 한다. 선택권이 조직에서 공급자로 넘어간다. 이 이동은 비용 청구서에 항목으로 나타나지 않기 때문에 눈치채기 어렵다.

  • 카탈로그는 권한의 경계다 — 테이블 목록을 아는 주체가 곧 접근을 통제하는 주체다. 스토리지 권한만으로는 세밀한 통제가 어렵다.
  • 규약 기반인지 먼저 확인한다 — 공개된 API 규약을 구현하는가, 아니면 전용 SDK로만 접근 가능한가. 이 답이 나중의 이주 비용을 절반 이상 결정한다.
  • 엔진 지원 목록은 시점 정보다 — 오늘 지원 목록에 없는 엔진이 내년에 들어올 수 있다. 반대도 마찬가지다. 목록보다 규약을 본다.
  • 이름 공간 설계를 미루지 않는다 — 네임스페이스와 테이블 명명 규칙은 나중에 바꾸면 모든 참조를 건드려야 한다. 초기에 정한다.
  • 테이블 유지보수 작업의 주체를 정한다 — 스냅숏 만료, 고아 파일 정리, 파일 병합을 누가 언제 하는지 정하지 않으면 비용과 성능이 동시에 나빠진다.

7. Arrow가 접착제가 된 이유

도구가 늘어나면 보통 통합 비용이 폭증한다. 그런데 지난 몇 년의 데이터 스택은 도구가 늘었는데도 조합 비용이 오히려 줄어든 구간이 있다. 그 이유의 상당 부분이 메모리 표현의 표준화다.

Apache Arrow 공식 명세는 이 포맷이 언어 비의존 인메모리 데이터 구조 명세와 메타데이터 직렬화, 그리고 직렬화·범용 데이터 전송 프로토콜을 포함한다고 규정한다. 설계 목표로는 순차 접근을 위한 데이터 인접성, 상수 시간 임의 접근, SIMD와 벡터화 친화성, 그리고 포인터 스위즐링 없이 재배치 가능해 공유 메모리에서 진정한 무복사 접근이 가능하다는 점을 든다. 대가도 명시돼 있다. 분석 성능과 데이터 지역성을 얻는 대신 변형 연산이 상대적으로 비싸다.

이 명세가 왜 접착제인지는 그 위에 얹힌 두 규약을 보면 분명해진다.

  • ADBC — 공식 문서는 이를 빠른 Arrow 네이티브 데이터베이스 접근을 위한 표준 API·라이브러리 모음으로 소개한다. 결과를 Arrow 컬럼 형식으로 직접 돌려주어 복사와 변환을 없앤다고 밝히며, C/C++, C#, Go, Java, JavaScript, Python, R, Ruby, Rust를 지원 언어로 든다. 드라이버로는 Flight SQL, PostgreSQL, SQLite 등이 문서화돼 있다.
  • Arrow Flight SQL — 공식 문서는 이를 Arrow 인메모리 형식과 Flight RPC 프레임워크로 SQL 데이터베이스와 상호작용하는 프로토콜로 정의한다. Flight의 기존 RPC 메서드를 재사용하고 Protobuf로 정의된 요청·응답 메시지를 짝지어 명령을 제공한다. 문서는 JDBC·ODBC 등 기존 드라이버와의 호환을 위해 서버 구현이 옵션 값의 문자열 표현을 받아들이기를 강력히 권고한다고 적는다.
import adbc_driver_postgresql.dbapi as pg

# 결과를 행 단위 객체로 풀었다 다시 묶지 않고 컬럼 형태로 그대로 받는다
with pg.connect("postgresql://localhost:5432/analytics") as conn:
    with conn.cursor() as cur:
        cur.execute(
            "SELECT category, amount FROM events WHERE amount > 0"
        )
        table = cur.fetch_arrow_table()

print(table.num_rows, table.schema)

실무에서 이 표준화가 만드는 차이는 「조합의 자유도」다. 저장은 컬럼 파일, 계산은 단일 노드 엔진, 전달은 Arrow, 시각화는 다른 언어의 라이브러리 같은 구성이 각 경계에서 데이터를 다시 만들지 않고 이어진다. ADBC 자체와 그 위에 올라온 도구를 더 깊게 다룬 글은 ADBC 기반 질의 도구 쪽에 따로 정리해 두었다. Arrow가 왜 이런 형태로 설계됐는지에 대한 만든 사람의 시각은 Arrow·Pandas 창시자의 전망에서 다뤘다.

8. 엔진을 바꿔도 살아남는 코드 - API 계층의 수렴

엔진 교체 비용을 낮추려는 시도는 오래됐지만, 지금은 실제로 쓰이는 형태로 좁혀졌다. 공식 저장소에서 확인되는 두 갈래가 있다.

Ibis는 스스로를 포터블 파이썬 데이터프레임 라이브러리로 소개하며, 20개 이상의 백엔드에 같은 데이터프레임 API를 사용하고 한 줄만 바꿔 로컬에서 반복하고 원격에 배포할 수 있다고 밝힌다. 기본 로컬 실행은 DuckDB를 통해 이뤄지고, 지연 표현식과 대화형 모드를 제공한다. 저장소가 나열하는 백엔드에는 DataFusion, Druid, Flink, Impala, PySpark, Athena, BigQuery, ClickHouse, Databricks, DuckDB, Exasol, Materialize, MySQL/MariaDB, Oracle, Polars, PostgreSQL, RisingWave, SingleStoreDB, SQL Server, SQLite, Snowflake, Trino가 포함된다.

Narwhals는 성격이 다르다. 저장소는 이를 데이터프레임 라이브러리 사이의 극도로 가볍고 확장 가능한 호환 계층이라고 설명하고, 의존성이 0이며 사용자가 넘긴 것만 사용해 라이브러리를 가볍게 유지한다고 밝힌다. 전체 API를 지원하는 백엔드로 cuDF, Modin, pandas, Polars, PyArrow를, 지연 전용으로 Daft, Dask, DuckDB, Ibis, PySpark, SQLFrame을 든다. 사용처로는 scikit-learn, Plotly, Bokeh, Altair, LightGBM, py-shiny 등이 나열된다.

import narwhals as nw

# 들어온 객체가 어느 라이브러리의 데이터프레임이든 같은 코드로 처리하고
# 같은 타입으로 돌려준다. 라이브러리를 만드는 쪽에서 특히 유용하다
def summarize(df_native):
    df = nw.from_native(df_native)
    out = (
        df.filter(nw.col("amount") > 0)
          .group_by("category")
          .agg(nw.col("amount").sum())
    )
    return nw.to_native(out)

선택 기준은 내가 무엇을 만들고 있느냐로 갈린다. 라이브러리나 재사용 도구를 만든다면 사용자가 어떤 데이터프레임을 넘길지 모르므로 호환 계층 쪽이 맞는다. 의존성을 늘리지 않는다는 성질이 여기서 결정적이다. 분석 파이프라인을 만들고 실행 위치를 바꾸고 싶다면 여러 백엔드로 컴파일되는 표현식 계층 쪽이 맞는다.

  • 추상화는 공짜가 아니다 — 백엔드마다 지원 범위가 다르다. 공통 부분집합 밖으로 나가는 순간 이식성은 사라진다.
  • 성능 튜닝은 결국 엔진 고유 영역 — 힌트, 파티션 전략, 통계는 추상 계층이 가려주지 않는다.
  • 테스트는 실제 백엔드로 해야 한다 — 로컬에서 통과한 표현식이 원격 엔진에서 다른 SQL로 번역될 수 있다.
  • 추상화를 쓰는 이유를 문서에 남긴다 — 「언젠가 바꿀지 몰라서」는 이유가 아니다. 바꿀 계획이 있거나 사용자가 다양한 경우에만 값을 한다.

9. 오케스트레이션과 변환 - 무게중심의 이동

파이프라인을 「무엇을 언제 실행할까」로 보던 시각이 「어떤 데이터 자산이 최신인가」로 옮겨가는 흐름이 공식 문서에서도 읽힌다.

Apache Airflow의 릴리스 노트는 3.0.0(2025년 4월 22일)에서 태스크 실행 API와 Task SDK, React 기반 UI 재작성, DAG 버저닝, 자산 기반 스케줄링, Edge Executor, 스케줄러가 관리하는 백필이 도입됐다고 적는다. 문서상 최신 버전은 3.3.0(2026년 7월 6일)이다. 여기서 실무적으로 큰 항목은 DAG 버저닝이다. 파이프라인 정의가 바뀌었을 때 과거 실행이 어떤 정의로 돌았는지가 추적되지 않으면 사고 원인 분석이 추정에 의존하게 된다.

Dagster 공식 문서는 스스로를 데이터 엔지니어를 위해 만들어진, 계보와 관측성이 통합되고 선언적 프로그래밍 모델과 최상급 테스트 용이성을 갖춘 데이터 오케스트레이터로 소개하며, 자산 중심 사고를 전면에 둔다. 태스크가 아니라 산출물을 선언하고 그 사이의 의존을 기술하는 방식이다.

dbt 쪽 변화는 코어의 재작성이다. 공식 문서는 Fusion 엔진이 Rust로 작성됐고 여러 엔진 방언에 걸쳐 SQL을 네이티브하게 이해하며, 모델의 잘못된 SQL을 웨어하우스에 도달하기 전에 즉시 잡아낸다고 설명한다. 자동완성, 호버 정보, 입력 중 인라인 오류 같은 편집기 기능과 프로젝트 전반에 걸친 모델·컬럼 정의 추적도 명시돼 있다. 문서는 Fusion이 dbt 설치 시 기본 경험이며 무료로 사용 가능하고 Apache 2.0 런타임을 기반으로 한다고 적는다. 해당 페이지의 최종 갱신일은 2026년 7월 25일이다.

세 변화의 공통점은 실행 이전으로 검증을 당기는 것이다. 파이프라인이 깨지는 지점을 런타임에서 컴파일 시점으로 옮기려는 시도이며, 같은 문제의식을 타입 시스템 쪽에서 접근한 사례는 타입 검사로 스키마 드리프트를 막는 접근에서, 의미 계층 쪽에서 접근한 사례는 관계를 선언하는 모델링 언어에서 각각 다뤘다.

  • 오케스트레이터를 두 개 쓰지 않는다 — 팀마다 다른 오케스트레이터를 쓰면 실패 알림과 재시도 정책이 갈라지고, 장애 시 어디를 봐야 할지 모르게 된다.
  • 스케줄이 아니라 의존을 선언한다 — 시각으로 묶은 파이프라인은 상류가 늦어지면 조용히 낡은 데이터를 만든다.
  • 백필 경로를 먼저 만든다 — 과거 구간 재처리는 예외 상황이 아니라 정기 작업이다. 초기에 설계하지 않으면 매번 수작업이 된다.
  • 정의의 버전과 데이터의 버전을 함께 남긴다 — 어떤 코드가 어떤 스냅숏을 만들었는지 이어지지 않으면 재현이 불가능하다.
  • 검증을 파이프라인 밖에 두지 않는다 — 별도 스크립트로 도는 품질 검사는 가장 먼저 유지보수에서 탈락한다.

10. 잠금은 어디에 생기고, 벗어나는 비용은 얼마인가

잠금을 하나의 덩어리로 이야기하면 논의가 감정적으로 흐른다. 계층마다 벗어나는 비용이 다르다는 사실을 인정하고 나면 훨씬 현실적인 대화가 된다. 아래 표는 계층별로 이주가 실제로 무엇을 요구하는지를 정리한 것이다.

잠금이 생기는 계층벗어날 때 실제로 하는 일상대 비용비용을 낮추는 사전 조치
컴퓨트 엔진같은 데이터를 읽는 다른 프로세스를 띄우고 성능을 재조정낮음엔진 고유 기능을 파이프라인 전반에 흩뿌리지 않는다
SQL 방언함수·타입·윈도 문법 차이를 전수 수정하고 결과를 대조중간방언 의존 구문을 한 곳에 모으거나 이식 가능한 계층을 쓴다
오케스트레이션DAG·자산 정의, 재시도·알림 정책, 백필 절차를 다시 작성중간비즈니스 로직을 오케스트레이터 API 밖에 둔다
저장 포맷보관된 데이터 전체를 다시 쓰고 그동안 양쪽을 병행 운영높음공개 명세 기반 포맷을 쓰고 변환 경로를 미리 확인한다
카탈로그테이블·권한·계보 참조를 전부 옮기고 모든 소비자를 재접속높음공개 API 규약을 구현하는 카탈로그를 고른다
독점 저장 계층내보내기 경로가 제한되면 이주 자체가 협상 대상이 됨가장 높음계약 단계에서 대량 내보내기 방식과 비용을 문서로 확인한다

표에서 얻을 결론은 단순하다. 비용이 낮은 계층에서는 마음껏 고르고, 비용이 높은 계층에서는 공개 규약을 고른다. 엔진은 취향으로 골라도 되지만 포맷과 카탈로그는 취향으로 고르면 안 된다. 그리고 가장 높은 비용은 기술이 아니라 계약에서 발생한다. 데이터를 대량으로 내보내는 경로가 없거나 비용이 비대칭이면, 그 시스템에서 나오는 결정은 기술 결정이 아니라 협상이 된다.

한 가지 균형도 적어 둔다. 잠금 회피를 최우선 가치로 두면 그 자체가 비용이다. 모든 계층을 교체 가능하게 만들려는 설계는 추상화가 두꺼워지고, 어느 엔진의 장점도 제대로 쓰지 못하는 결과로 끝나기 쉽다. 실무의 균형점은 이주 비용이 높은 계층만 공개 규약으로 묶고, 나머지는 지금 가장 잘 맞는 것을 쓰는 것이다.

11. 도입하지 말아야 할 신호

「어떤 도구가 최고인가」라는 질문에는 답이 없다. 대신 「우리 상황에서 무엇이 과잉인가」에는 꽤 정확한 답이 가능하다. 아래는 실무에서 반복적으로 확인되는 과잉 신호와 그 처방이다.

관찰되는 신호실제로 벌어지고 있는 일먼저 해볼 조치
클러스터가 하루 대부분 유휴 상태대기 자원이 계산 자원보다 비싸진 상태단일 노드에서 대표 잡을 끝까지 실행해 실측
스트리밍인데 소비자는 하루 한 번 조회요구되지 않은 신선도에 운영 부담을 지불SLA 문서의 숫자를 원문으로 확인
도구 담당이 사실상 한 명그 구성 요소가 단일 장애점인원이 늘지 않으면 구성 요소를 줄인다
파이프라인 수보다 도구 수가 빠르게 증가통합 비용이 산출물 가치를 넘어서는 중같은 역할의 도구를 하나로 합친다
같은 변환이 두 언어로 중복 구현정합성 사고가 예약된 상태단일 정의 지점을 정하고 나머지는 참조
도입 근거가 지난 분기 사고가 아닌 예측겪지 않은 문제를 위한 선투자실제 발생한 장애 목록으로 우선순위 재작성

여기서 가장 중요한 행은 세 번째다. 도구의 적정 수는 데이터 크기가 아니라 인원 수로 정해진다. 각 구성 요소는 업그레이드, 보안 패치, 장애 대응, 사용법 문서화를 요구한다. 이 부담의 총합이 팀 역량을 넘어서면 스택은 조용히 낡기 시작하고, 낡은 스택은 어느 날 갱신할 수 없는 상태로 발견된다.

반대로 도입을 정당화하는 신호도 정리해 둔다. 지난 분기에 같은 유형의 장애가 반복해서 발생했고, 그 원인이 현재 구성의 구조적 한계로 설명되며, 새 구성 요소를 상시로 돌볼 인원이 두 명 이상 확보돼 있고, 실패했을 때 되돌릴 경로가 문서로 존재할 때다. 넷 중 하나라도 없으면 도입 시점을 미루는 편이 대체로 옳다.

12. 결정 순서 - 실행 가능한 절차

지금까지의 내용을 순서로 압축한다. 이 순서를 지키면 대부분의 논쟁이 3단계나 4단계에서 정리된다.

  1. 대표 워크로드를 하나 고정한다 — 실제 운영에서 뜬 것이어야 한다. 합성 데이터는 결론을 낙관적으로 만든다.
  2. 단일 장비에서 끝까지 돌려 실측한다 — 소요 시간, 최대 메모리, 실패 지점을 기록한다. 이 수치가 없는 규모 논쟁은 전부 추정이다.
  3. 요구되는 신선도를 문서에서 확인한다 — 계약이나 합의 문서에 적힌 숫자를 본다. 관행으로 굳은 초 단위 기대치는 근거가 아니다.
  4. 저장 포맷을 먼저 정한다 — 공개 명세가 있고, 다른 포맷으로 나가는 경로가 확인되는 것을 고른다.
  5. 카탈로그를 그다음에 정한다 — 공개 API 규약을 구현하는지, 엔진이 클라이언트로 붙을 수 있는지를 본다.
  6. 엔진은 마지막에 고른다 — 이 시점에서 엔진은 교체 가능한 부품이므로 팀의 언어와 운영 역량으로 고르면 된다.
  7. 파티션과 파일 크기 정책을 함께 정한다 — 포맷을 정하는 자리에서 같이 결정한다. 나중에 바꾸면 전체 재작성이다.
  8. 테이블 유지보수를 운영 항목으로 등록한다 — 스냅숏 만료, 고아 파일 정리, 파일 병합의 주기와 담당을 명시한다.
  9. 변환 정의를 한 곳에 모은다 — 같은 지표가 두 곳에서 계산되지 않도록 단일 정의 지점을 만든다.
  10. 오케스트레이션은 의존 기반으로 선언한다 — 시각이 아니라 상류 자산의 갱신을 기준으로 트리거한다.
  11. 되돌림 경로를 만들고 실제로 시험한다 — 이전 스냅숏으로 복귀하는 절차를 릴리스마다 한 번은 돌려 본다.
  12. 분기마다 스택 구성 요소 수를 센다 — 늘었다면 그만큼 담당이 늘었는지 함께 확인한다. 아니라면 줄일 시점이다.

결론: 도구 목록은 낡고, 순서는 남는다

2026년의 데이터 도구 지형을 한 문장으로 줄이면 이렇다. 계산은 더 작은 단위로 내려왔고, 저장과 메타데이터는 더 공용 규약 쪽으로 올라갔다. 그 결과 실무자가 답해야 할 질문이 바뀌었다. 예전에는 「이 규모를 감당할 만큼 큰 것을 골랐는가」였다면, 지금은 「이 규모에 비해 과한 것을 고르고 있지 않은가」다.

이 글이 반복한 판단 규칙은 세 개다. 첫째, 규모 논쟁은 단일 노드 실측 이후에 시작한다. 둘째, 결정 순서는 포맷, 카탈로그, 엔진이다. 셋째, 이주 비용이 높은 계층만 공개 규약으로 묶고 나머지는 지금 가장 잘 맞는 것을 쓴다. 이 세 규칙은 특정 도구의 흥망과 무관하게 유지된다.

마지막으로 이 글의 유통기한을 밝혀 둔다. 여기 적힌 버전 번호와 상태는 2026년 7월 29일에 각 프로젝트의 공식 문서에서 확인한 것이고, 이 분야에서 그 값들은 빠르게 바뀐다. 그러니 도구 이름과 숫자는 확인용으로만 쓰고, 가져갈 것은 순서와 기준으로 삼는 편이 좋다. 도구는 계속 바뀌지만, 벗어나기 어려운 것을 먼저 정하고 벗어나기 쉬운 것을 나중에 정한다는 원칙은 잘 바뀌지 않는다.
