CRLF와 LF - 윈도우와 리눅스를 오갈 때 실제로 깨지는 것들 2026

보이지 않는 1바이트가 셰뱅과 변수 비교와 git 인덱스에서 하는 일, 그리고 되돌리는 순서

2026-09-01 IT/기술

윈도우에서 편집한 배포 스크립트를 서버에 올렸더니 bad interpreter 한 줄을 남기고 죽는다. 파일을 열어 보면 아무 이상이 없다. 첫 줄은 분명히 #!/bin/bash 이고, 오타도 없고, 권한도 맞다. 그런데 실행이 안 된다. 이 상황에서 사람들이 가장 많이 하는 일은 스크립트를 처음부터 다시 타이핑하는 것이고, 그러면 대개 해결된다. 무엇이 문제였는지는 끝내 모르는 채로.

문제는 줄 끝에 있는, 편집기가 보여 주지 않는 1바이트다. 이 글은 그 1바이트가 어디서 붙고, 붙으면 셸과 변수와 git 인덱스에서 각각 무엇이 벌어지며, 어떤 순서로 되돌려야 하는지를 정리한다. 설명만 하지 않고 전부 직접 돌려서 나온 출력을 붙였다.

세 가지가 있다 - 바이트로 직접 본다

줄바꿈 방식은 셋이다. 유닉스 계열이 쓰는 LF 는 0x0A 한 바이트, 윈도우가 쓰는 CRLF 는 0x0D 0x0A 두 바이트, 그리고 클래식 맥 오에스가 쓰던 단독 CR 은 0x0D 한 바이트다. 세 번째는 지금 새로 만들어지는 일이 거의 없지만, 오래된 자료를 넘겨받을 때 여전히 나온다. 말로 외우는 것보다 바이트를 한 번 보는 편이 빠르다.

$ printf 'hello\nworld\n'     > lf.txt
$ printf 'hello\r\nworld\r\n' > crlf.txt
$ printf 'hello\rworld\r'     > cr.txt

$ xxd lf.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.
$ xxd crlf.txt
00000000: 6865 6c6c 6f0d 0a77 6f72 6c64 0d0a       hello..world..
$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ file lf.txt crlf.txt cr.txt
lf.txt:   ASCII text
crlf.txt: ASCII text, with CRLF line terminators
cr.txt:   ASCII text, with CR line terminators

xxd 오른쪽의 점은 인쇄할 수 없는 문자를 대신 찍은 것이다. LF 파일에서 hello 뒤에 점이 하나인데 CRLF 파일에서는 둘이다. 그 차이가 이 글의 전부다. 눈으로 보이는 텍스트는 완전히 같고, 파일 크기만 줄 수만큼 커진다. 세 줄짜리 파일이라면 17바이트와 20바이트의 차이다.

이름바이트이스케이프주로 쓰는 곳지금 만나는 상황
LF0x0A\n리눅스, 유닉스, 현대 맥, 웹, 대부분의 프로그래밍 언어 소스기본값. 특별한 이유가 없으면 이쪽
CRLF0x0D 0x0A\r\n윈도우 메모장과 배치 파일, 다수의 네트워크 프로토콜윈도우 편집기가 새 파일에 자주 넣는다
CR0x0D\r2001년 이전 클래식 맥 오에스오래된 자료를 넘겨받을 때. 새로 생기지는 않는다

왜 하필 둘로 갈렸나

두 문자의 이름이 유래를 담고 있다. CR 은 carriage return, 인쇄 헤드를 줄 맨 앞으로 되돌리는 동작이고 LF 는 line feed, 종이를 한 줄 밀어 올리는 동작이다. 기계식 인쇄 장치에서는 둘이 별개였다. 한쪽 계열은 이 관습을 파일 형식에 남겼고, 다른 쪽은 줄 하나에 문자 하나면 충분하다고 보았다.

유닉스 쪽 선택은 규격에 적혀 있다. POSIX 는 줄을 「개행 문자가 아닌 문자 0개 이상에 종료용 개행 문자 하나를 더한 것」으로 정의한다. 여기서 개행 문자는 \n 하나이고, CR 은 그냥 데이터에 포함되는 보통 문자다. 그래서 CRLF 파일을 유닉스 도구에 넣으면 CR 이 줄의 마지막 글자로 취급된다. 없어져야 할 제어 문자가 아니라 값의 일부로 딸려 들어간다. 뒤에 나오는 사고는 전부 이 한 문장에서 파생된다.

  • CRLF 파일의 각 줄은 유닉스 관점에서 「내용 + CR」 이다. CR 은 줄 구분자가 아니라 내용의 끝 글자다
  • 그래서 "prod" 를 읽었다고 생각한 변수에 실제로는 "prod\r" 이 들어간다
  • 비교, 경로 조합, 숫자 변환, 해시 계산이 전부 어긋난다. 그런데 화면에는 티가 나지 않는다
  • 반대 방향, 즉 LF 파일을 윈도우 도구에 넣는 쪽은 훨씬 관대하다. 요즘 윈도우 도구는 대부분 LF 를 그대로 읽는다

셸 스크립트가 죽는 방식

가장 유명한 증상부터 본다. 첫 줄이 #!/bin/bash 인 스크립트를 CRLF 로 저장하면 첫 줄의 실제 바이트는 #!/bin/bash\r\n 이 된다. 커널이 셰뱅을 해석할 때 인터프리터 경로는 개행 직전까지를 취하므로, 실행하려는 프로그램의 이름이 /bin/bash 가 아니라 /bin/bash 뒤에 CR 한 글자가 더 붙은 이름이 된다. 그런 파일은 없으니 실패한다.

바이트를 보면 의심의 여지가 없다.

$ printf '#!/bin/bash\r\necho "hi"\r\n' > crlf.sh
$ chmod +x crlf.sh
$ head -c 24 crlf.sh | xxd
00000000: 2321 2f62 696e 2f62 6173 680d 0a65 6368  #!/bin/bash..ech
00000010: 6f20 2268 6922 0d0a                      o "hi"..

6173 68 이 ash 이고 그 다음이 0d 0a 다. 경로 문자열 /bin/bash 바로 뒤에 0x0D 가 붙어 있다. 이 상태로 실행하면 인터프리터를 못 찾는다는 에러가 난다. 그 메커니즘은 셰뱅을 거치지 않고도 그대로 재현된다. 경로 끝에 CR 을 직접 붙여 호출하면 된다.

$ "/bin/bash$(printf '\r')" -c 'echo hi' 2>err.txt
$ cat -A err.txt
/usr/bin/bash: line 1: /bin/bash^M: No such file or directory$

$ xxd err.txt
00000000: 2f75 7372 2f62 696e 2f62 6173 683a 206c  /usr/bin/bash: l
00000010: 696e 6520 313a 202f 6269 6e2f 6261 7368  ine 1: /bin/bash
00000020: 0d3a 204e 6f20 7375 6368 2066 696c 6520  .: No such file
00000030: 6f72 2064 6972 6563 746f 7279 0a         or directory.

오프셋 0x20 의 0d 가 핵심이다. 에러 메시지 안에 진짜 CR 바이트가 들어 있다. cat -A 가 그것을 ^M 으로 표시해 준다. 흔히 보는 bad interpreter: /bin/bash^M 의 ^M 이 바로 이 바이트이고, 없는 문자를 셸이 지어낸 것이 아니다.

셰뱅에 env 를 쓰는 경우에는 에러 모양이 조금 다르다. env 가 인자를 그대로 인용해 보여 주기 때문에 오히려 더 친절하다.

$ env "bash$(printf '\r')" --version
env: 'bash\r': No such file or directory

여기서는 \r 이 아예 글자 그대로 찍힌다. env 로 시작하는 셰뱅을 쓰는 습관이 디버깅에는 유리한 셈이다.

Git Bash 에서는 이 버그가 보이지 않는다

여기서 이 문제가 왜 그렇게 오래 살아남는지가 드러난다. 위에서 만든 crlf.sh 를 Git Bash 에서 그냥 실행하면 아무 일도 일어나지 않는다. 정상 동작한다.

$ ./crlf.sh
hi

$ printf '#!/usr/bin/cat\r\nhello\r\n' > catshebang.sh
$ chmod +x catshebang.sh
$ ./catshebang.sh | cat -A
#!/usr/bin/cat^M$
hello^M$

두 번째 예시가 증거다. 셰뱅을 /usr/bin/cat 으로 두고 실행했더니 cat 이 실제로 실행되어 파일 내용을 뱉었다. 즉 MSYS2 의 실행 계층이 셰뱅 줄 끝의 CR 을 알아서 떼어 내고 인터프리터를 찾아 준다. 파일 안의 CR 은 그대로 남아 있다는 것도 같은 출력에서 확인된다. 내용 줄은 ^M 을 달고 있다.

결과적으로 개발자 노트북에서는 스크립트가 잘 돈다. 커밋도 되고, 리뷰도 통과하고, 배포 파이프라인에 들어간다. 그리고 리눅스 서버에서 처음으로 죽는다. 이것이 이 버그가 코드 리뷰를 통과하는 이유다. CR 을 무시하게 하는 igncr 셸 옵션을 가진 bash 빌드도 있다고 알려져 있는데, 적어도 이 환경의 bash 5.2.37 에는 없다.

$ shopt igncr
/usr/bin/bash: line 1: shopt: igncr: invalid shell option name

그러니 「내 로컬에서는 되는데」 라는 말은 이 주제에서는 정보가 아니다. 로컬이 윈도우라면 원래 된다.

진짜 고약한 것은 변수 값 끝의 CR

셰뱅 문제는 그래도 시끄럽게 죽으니 나은 편이다. 훨씬 오래 사람을 붙잡는 것은 설정 파일을 읽어 변수에 담을 때 생긴다. 스크립트 자체는 LF 인데 읽어 들이는 .env 나 설정 파일만 CRLF 인 경우가 흔하다. 이때는 죽지도 않고, 그냥 조건문이 틀린다.

$ printf 'ENV=prod\r\nPORT=8080\r\n' > app.conf

$ cat readconf.sh
#!/bin/bash
while IFS='=' read -r k v; do
  export "$k=$v"
done < app.conf
echo "ENV=[$ENV]"
if [ "$ENV" = "prod" ]; then echo "MATCH"; else echo "NO MATCH"; fi
echo "length=${#ENV}"

$ bash readconf.sh
ENV=[prod]
NO MATCH
length=5

화면에는 ENV=[prod] 라고 찍혀 있다. 대괄호 안에 prod 네 글자가 보인다. 그런데 prod 와 같지 않다고 하고, 길이는 5라고 한다. 이 세 줄이 동시에 참인 상황을 눈으로만 이해하려고 하면 몇 시간을 쓴다. cat -A 로 보면 즉시 끝난다.

$ bash readconf.sh | cat -A
ENV=[prod^M]$
NO MATCH$
length=5$

값은 prod 가 아니라 prod 뒤에 CR 이 붙은 다섯 글자다. 여기서 한 가지 미묘한 차이를 짚어 둘 필요가 있다. 읽는 방식에 따라 CR 이 남기도 하고 사라지기도 한다.

$ printf 'v2.4.1\r\n' > version.txt

$ read -r VER2 < version.txt
$ echo "len2=${#VER2}"
len2=7
$ printf '%s' "$VER2" | xxd
00000000: 7632 2e34 2e31 0d                        v2.4.1.

$ VER=$(cat version.txt)
$ echo "len=${#VER}"
len=6
$ printf '%s' "$VER" | xxd
00000000: 7632 2e34 2e31                           v2.4.1

read 로 읽으면 CR 이 남아 7글자, 명령 치환으로 읽으면 6글자다. 이 환경의 bash 는 명령 치환에서 끝의 개행을 떼면서 CR 까지 같이 떼어 낸다. 다만 이것도 윈도우에서만 조용한 쪽이다. 파이프는 CR 을 그대로 흘려보낸다.

$ printf 'a\r\nb\r\n' | xxd
00000000: 610d 0a62 0d0a                           a..b..

즉 같은 파일이라도 while read 로 돌리느냐, $(...) 로 받느냐, 파이프로 넘기느냐에 따라 CR 이 남는 자리가 달라진다. 그래서 어떤 줄에서는 되고 어떤 줄에서는 안 되는 스크립트가 만들어진다. 이 비일관성이 원인 추적을 가장 방해한다.

에러 메시지가 이상하게 잘리는 이유

CR 이 값에 섞이면 출력하는 순간 터미널이 반응한다. CR 은 원래 커서를 줄 맨 앞으로 보내라는 제어 문자이기 때문이다. 메시지 중간에 CR 이 들어가면 뒤에 오는 글자들이 앞부분을 덮어쓴다. 지워진 것이 아니라 가려진 것이다.

로그에 deploy failed: version v2.4.1 not supported 를 찍으려 했는데 버전 값 끝에 CR 이 있으면, 터미널은 v2.4.1 까지 그리고 커서를 줄 맨 앞으로 보낸 다음 not supported 를 덧그린다. 남는 것은 앞뒤가 뒤섞인 짧은 한 줄이고 원문은 어디에도 없어 보인다. 파일로 리다이렉트해 cat -A 로 열면 온전한 원문이 그대로 있다.

  • 메시지가 중간이 잘린 것처럼 보이면 CR 을 의심한다. 로깅 코드의 버그가 아닌 경우가 많다
  • 같은 이유로 진행률 표시가 이상해지고, 프롬프트가 겹쳐 보이고, grep 결과가 짧게 나온 것처럼 착각하게 된다
  • 확인은 항상 파일로 받아서 한다. 터미널이 그리는 화면은 원본이 아니다
  • CI 로그 뷰어는 CR 을 처리하는 방식이 도구마다 달라, 같은 로그가 로컬과 웹에서 다르게 보이기도 한다

찾는 법 - grep 이 0을 돌려주는 함정

확인 명령은 네 가지면 충분하다. file 은 한눈에, cat -A 는 줄 단위로, xxd 는 바이트로, dos2unix -i 는 개수로 알려 준다. 섞여 있는 파일을 하나 만들어 넷을 나란히 돌려 본다.

$ printf 'first\r\nsecond\nthird\r\n' > mixed.txt

$ file mixed.txt
mixed.txt: ASCII text, with CRLF, LF line terminators

$ cat -A mixed.txt
first^M$
second$
third^M$

$ dos2unix -i mixed.txt lf.txt crlf.txt cr.txt
       2       1       0  no_bom    text    mixed.txt
       0       2       0  no_bom    text    lf.txt
       2       0       0  no_bom    text    crlf.txt
       0       0       2  no_bom    text    cr.txt

dos2unix -i 의 세 숫자는 왼쪽부터 CRLF, LF, 단독 CR 의 개수다. mixed.txt 가 2 1 0 인 것이 앞에서 만든 대로다. 네 번째 칸은 BOM 유무, 다섯 번째는 텍스트인지 바이너리로 판정했는지다. 여러 파일 중 CRLF 가 섞인 것만 골라내려면 -ic 를 쓴다. 이름만 나온다.

그런데 가장 널리 추천되는 방법이 이 환경에서는 거짓 음성을 낸다.

$ grep -c $'\r' mixed.txt
0

$ grep -Uc $'\r' mixed.txt
2

$ awk '/\r$/{n++} END{print n+0}' mixed.txt
0

$ awk -v BINMODE=3 '/\r$/{n++} END{print n+0}' mixed.txt
2

CRLF 가 두 줄 들어 있는 파일에 grep -c $'\r' 이 0 을 돌려준다. 이 환경의 GNU grep 3.0 은 파일을 텍스트 모드로 읽으면서 줄 끝 CR 을 먼저 떼어 내기 때문이다. -U 를 붙여 바이너리 모드로 읽게 하면 제대로 2가 나온다. gawk 도 같아서 -v BINMODE=3 이 필요하다. 리눅스에서는 이런 전처리가 없어 -U 없이도 잡히지만, 윈도우에서 확인했다는 말은 그래서 신뢰할 수 없다. 검사 스크립트를 짤 때 이 한 글자를 빠뜨리면 검사기가 늘 통과를 반환한다.

file 파일CRLF · LF · CR 종류를 이름으로섞여 있으면 둘 다 나열한다
cat -A 파일줄마다 ^M 과 끝 표시 $가장 직관적. 탭은 ^I 로 나온다
xxd 파일 | head실제 바이트. 0d0a 를 눈으로긴 파일은 head 로 잘라 본다

고치는 법 세 가지, 그리고 각각이 망가뜨리는 것

변환 방법은 셋이 널리 쓰인다. 평범한 CRLF 텍스트 파일이라면 셋 다 같은 결과를 낸다.

$ dos2unix -q mixed.txt
$ sed -i 's/\r$//' mixed.txt
$ tr -d '\r' < mixed.txt > out.txt

$ cat -A mixed.txt
first$
second$
third$

문제는 평범하지 않은 파일에서 갈린다. tr -d '\r' 은 줄 끝인지 아닌지를 전혀 구분하지 않는다. 파일 안의 0x0D 를 남김없이 지운다. 진행률을 CR 로 덮어쓰며 출력한 로그를 예로 들면 이렇게 된다.

$ printf 'progress: 10%%\r progress: 100%%\rdone\n' > prog.log
$ xxd prog.log
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

$ tr -d '\r' < prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 2520 7072  progress: 10% pr
00000010: 6f67 7265 7373 3a20 3130 3025 646f 6e65  ogress: 100%done
00000020: 0a                                       .

$ sed 's/\r$//' prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

tr 을 거친 쪽은 세 단계의 진행 표시가 한 줄에 이어 붙어 원래 의도가 사라졌다. sed 's/\r$//' 은 줄 끝에 있는 CR 만 노리므로 이 파일을 건드리지 않았다. 그런데 sed 도 만능은 아니다. 옛 맥 형식의 단독 CR 파일에는 거의 손을 대지 못한다. 그 파일은 유닉스 도구에게 줄 하나로 보이기 때문이다.

$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ sed 's/\r$//' cr.txt | xxd
00000000: 6865 6c6c 6f0d 776f 726c 64              hello.world

$ tr -d '\r' < cr.txt | xxd
00000000: 6865 6c6c 6f77 6f72 6c64                 helloworld

$ dos2unix -q -c mac cr.txt
$ xxd cr.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.

sed 는 맨 끝 CR 하나만 떼고 중간 CR 은 남겼다. tr 은 두 줄을 helloworld 한 덩어리로 붙여 버렸다. dos2unix -c mac 만 CR 을 LF 로 바꿔 두 줄을 살렸다. 데이터 손실 여부가 명령 선택 하나에 달려 있다.

바이너리 파일에서는 차이가 더 극적이다. dos2unix 는 기본으로 바이너리를 건너뛴다.

$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ dos2unix bin.dat
dos2unix: Binary symbol 0x00 found at line 1
dos2unix: Skipping binary file bin.dat
$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ tr -d '\r' < bin.dat | xxd
00000000: 504e 4789 000a 1a0a ffd8                 PNG.......

tr 을 통과한 파일은 1바이트가 사라졌다. 이미지든 압축 파일이든 이 시점에서 못 쓰게 된다. 그리고 아무 경고도 없다. find 와 조합해 저장소 전체에 tr 을 돌리는 스크립트가 위험한 이유가 이것이다.

도구줄 끝 CRLF줄 중간 CR단독 CR 파일바이너리BOM
dos2unix변환보존-c mac 으로 변환기본으로 건너뜀기본으로 제거
sed -i 's/\r$//'변환보존거의 손대지 못함손댈 수 있음그대로 둠
tr -d '\r'변환같이 삭제줄이 합쳐짐손상시킴그대로 둠

표의 오른쪽 끝 칸은 뜻밖의 부작용이라 따로 확인해 둘 만하다. dos2unix 는 옵션을 주지 않으면 파일 앞의 BOM 을 같이 지운다.

$ printf '\xef\xbb\xbfname,qty\r\nsalt,2\r\n' > bomcrlf.csv
$ xxd bomcrlf.csv
00000000: efbb bf6e 616d 652c 7174 790d 0a73 616c  ...name,qty..sal
00000010: 742c 320d 0a                             t,2..

$ dos2unix -q bomcrlf.csv
$ xxd bomcrlf.csv
00000000: 6e61 6d65 2c71 7479 0a73 616c 742c 320a  name,qty.salt,2.

앞 3바이트 efbbbf 가 사라졌다. 엑셀에 넘길 CSV 처럼 BOM 이 있어야 하는 파일이면 -b 를 붙여 유지해야 한다. 줄바꿈만 고치려다 다른 것을 같이 고쳐 버리는 대표적인 자리다.

git 이 개입하는 두 지점 - core.autocrlf

git 은 줄바꿈을 두 지점에서 손댈 수 있다. 커밋할 때(작업 디렉터리에서 인덱스로) 와 체크아웃할 때(인덱스에서 작업 디렉터리로) 다. core.autocrlf 의 세 값은 이 두 지점을 각각 다르게 건드린다. 임시 저장소를 만들어 확인하면 헷갈릴 여지가 없다.

먼저 체크아웃 쪽이다. LF 로 커밋된 저장소를 세 가지 설정으로 각각 복제한다.

$ cd /tmp/demo/src
$ git ls-files --eol
i/lf    w/lf    attr/                   src.txt

$ git -c core.autocrlf=true  clone -q /tmp/demo/src /tmp/demo/w-true
$ git -c core.autocrlf=input clone -q /tmp/demo/src /tmp/demo/w-input
$ git -c core.autocrlf=false clone -q /tmp/demo/src /tmp/demo/w-false

$ xxd /tmp/demo/w-true/src.txt
00000000: 6c69 6e65 310d 0a6c 696e 6532 0d0a       line1..line2..
$ xxd /tmp/demo/w-input/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.
$ xxd /tmp/demo/w-false/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.

true 만 작업 디렉터리 파일을 CRLF 로 바꿔 놓았다. 이번에는 커밋 쪽이다. 세 저장소 각각에 CRLF 파일을 만들어 커밋하고 인덱스 상태를 본다.

$ printf 'new1\r\nnew2\r\n' > added.txt
$ git add added.txt
$ git commit -qm add
$ git ls-files --eol -- added.txt

# core.autocrlf=true
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=input
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=false
i/crlf  w/crlf  attr/                   added.txt

true 와 input 은 인덱스에 LF 로 넣었고, false 는 CRLF 를 그대로 넣었다. 즉 두 값의 차이는 커밋이 아니라 체크아웃에만 있다. 이 표가 결론이다.

core.autocrlf커밋할 때 (작업 → 인덱스)체크아웃할 때 (인덱스 → 작업)어떤 사람에게 맞나
trueCRLF 를 LF 로 바꿔 저장LF 를 CRLF 로 바꿔 내려 줌윈도우 전용 편집기를 쓰는 사람. 저장소는 깨끗해진다
inputCRLF 를 LF 로 바꿔 저장변환하지 않음. LF 그대로윈도우에서 리눅스용 스크립트를 다루는 사람
false변환하지 않음. 있는 그대로변환하지 않음줄바꿈을 .gitattributes 로만 관리하는 저장소

여기에 core.eol 이 하나 더 있다. 값은 lf, crlf, native 이고 기본은 플랫폼의 관행을 따르는 native 다. 그리고 core.safecrlf 를 true 나 warn 으로 두면 변환이 되돌릴 수 없는 경우에 경고하거나 막아 준다.

  • core.autocrlf 는 개인 설정이다. 저장소를 받는 사람마다 값이 다를 수 있다
  • 그래서 팀 전체에 같은 값을 쓰라고 공지하는 방식은 새로 합류한 사람에게서 반드시 한 번 깨진다
  • 공식 문서는 core.autocrlf=true 를 「모든 파일에 text=auto 를 설정하고 core.eol 을 crlf 로 두는 것과 같다」고 설명한다
  • 즉 autocrlf 는 .gitattributes 의 축약형에 가깝다. 그렇다면 축약형 대신 원본을 쓰는 편이 낫다

.gitattributes 가 더 나은 이유

차이는 하나다. core.autocrlf 는 사람에게 붙고 .gitattributes 는 저장소에 붙는다. 후자는 커밋되어 함께 배포되므로 협업자의 설정과 무관하게 같은 규칙이 걸린다. 새로 들어온 사람이 아무 설정도 하지 않아도 규칙이 작동한다는 점이 실질적인 차이다.

# .gitattributes
* text=auto

*.sh   text eol=lf
*.py   text eol=lf
*.yml  text eol=lf
*.yaml text eol=lf

*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf

*.png binary
*.jpg binary
*.pdf binary

속성의 뜻은 이렇다. text 를 지정하면 체크인할 때마다 인덱스의 줄바꿈을 LF 로 정규화한다. text=auto 는 git 이 텍스트인지 바이너리인지 스스로 판단하게 맡긴다. eol=lf 는 체크아웃할 때 인덱스와 같은 줄바꿈을 쓰라는 뜻이고, eol=crlf 는 작업 디렉터리 파일을 CRLF 로 바꾸라는 뜻이다. binary 는 -text -diff 의 별칭으로, 어떤 변환도 하지 말라는 표시다.

여기서 놓치기 쉬운 대목이 있다. * text=auto 만으로는 작업 디렉터리가 LF 가 되지 않는다. 문서에 따르면 eol 이 지정되지 않고 core.autocrlf 도 core.eol 도 설정되지 않았다면 기본값은 윈도우에서 eol=crlf, 다른 플랫폼에서 eol=lf 다. 실제로 새로 복제해 보면 그대로 나온다.

$ git clone -q /tmp/demo/repo /tmp/demo/fresh
$ cd /tmp/demo/fresh
$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          .gitattributes
i/-text w/-text attr/text=auto          blob.bin
i/lf    w/lf    attr/text eol=lf        deploy.sh
i/lf    w/crlf  attr/text=auto          notes.md

$ xxd notes.md
00000000: 610d 0a62 0d0a                           a..b..
$ xxd deploy.sh
00000000: 2321 2f62 696e 2f62 6173 680a 6563 686f  #!/bin/bash.echo
00000010: 2068 690a                                 hi.

같은 저장소에서 notes.md 는 CRLF 로 내려왔고 deploy.sh 는 LF 로 내려왔다. 차이는 *.sh text eol=lf 한 줄뿐이다. 리눅스에서 실행될 파일에는 eol=lf 를 명시해야 하는 이유가 이것이다. text=auto 만 믿으면 윈도우 작업 트리에서 셸 스크립트가 CRLF 로 살아난다.

출력 형식도 익혀 둘 만하다. git ls-files --eol 은 세 칸을 보여 준다.

칸뜻나올 수 있는 값
i/인덱스에 저장된 블롭의 줄바꿈lf, crlf, mixed, -text(바이너리)
w/지금 작업 디렉터리 파일의 줄바꿈같은 값들. i/ 와 달라도 정상인 경우가 있다
attr/이 경로에 적용 중인 속성text=auto, text eol=lf, 빈칸 등

.gitattributes 는 과거를 고치지 않는다

이 절이 이 글에서 가장 자주 쓰이게 될 부분이다. .gitattributes 를 추가하면 문제가 끝났다고 생각하기 쉬운데, 규칙을 넣기 전에 이미 커밋된 블롭은 그대로 남는다. 규칙은 앞으로의 변환에만 걸린다.

CRLF 파일을 core.autocrlf=false 로 커밋해 둔 저장소에 .gitattributes 를 넣고 상태를 보면 이렇게 나온다.

$ git ls-files --eol
i/crlf  w/crlf  attr/                   deploy.sh
i/lf    w/lf    attr/                   notes.md

$ printf '* text=auto\n*.sh text eol=lf\n*.bat text eol=crlf\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm "add gitattributes"

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text eol=lf        deploy.sh
i/lf    w/lf    attr/text=auto          notes.md

$ git check-attr text eol -- deploy.sh
deploy.sh: text: set
deploy.sh: eol: lf

attr/ 칸에는 새 규칙이 제대로 붙어 있다. check-attr 도 eol: lf 라고 답한다. 그런데 i/ 칸은 여전히 crlf 다. 규칙은 걸렸는데 데이터는 예전 그대로인 상태다. 이 저장소를 리눅스 서버에 배포하면 스크립트는 여전히 죽는다.

더 헷갈리는 경우는 * text=auto 만 넣은 쪽이다. 문서는 이 값에 대해 「텍스트이고 그 파일이 이미 CRLF 로 git 에 들어가 있지 않았다면 줄바꿈을 변환한다」고 적고 있다. 그러면 그 파일을 수정해서 다시 커밋하면 정리될까. 확인해 보면 아니다.

$ git ls-files --eol
i/crlf  w/crlf  attr/                   legacy.txt

$ printf '* text=auto\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm attrs

$ printf 'one\r\ntwo\r\nthree\r\n' > legacy.txt
$ git add legacy.txt
$ git commit -qm edit

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650d 0a74 776f 0d0a 7468 7265 650d  one..two..three.
00000010: 0a                                       .

수정하고 다시 커밋했는데도 인덱스 블롭은 CRLF 그대로다. text=auto 는 한 번 CRLF 로 들어간 파일을 계속 예외로 대우한다. 규칙을 넣고 몇 달이 지나도 저절로 정리되지 않는다는 뜻이다.

정리하려면 명시적인 재정규화가 필요하다. 공식 문서가 안내하는 순서 그대로다. 작업 트리가 깨끗한 상태에서 실행한다.

$ git add --renormalize .
$ git status --short
M  legacy.txt
$ git commit -qm "normalize line endings"

$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650a 7477 6f0a 7468 7265 650a       one.two.three.

인덱스는 이제 LF 다. 그런데 w/ 칸은 아직 crlf 다. 재정규화는 인덱스만 바꾸고 작업 디렉터리 파일은 그대로 두기 때문이다. 작업 트리까지 맞추려면 그 파일을 지우고 다시 받으면 된다.

$ rm deploy.sh
$ git checkout -- deploy.sh
$ git ls-files --eol
i/lf    w/lf    attr/text eol=lf        deploy.sh
  • 재정규화 커밋은 내용 변경이 아닌데 거의 모든 줄이 바뀐 것처럼 보인다. 다른 작업과 섞지 말고 단독 커밋으로 남긴다
  • 진행 중인 브랜치가 있으면 병합 충돌이 크게 난다. 병합할 것을 먼저 병합하고 나서 정규화하는 편이 낫다
  • git status 에 예상하지 않은 파일이 올라오면 그 파일은 -text 로 제외한 뒤 다시 돌린다
  • 정규화 이후에도 i/crlf 가 남아 있다면 그 경로는 규칙에서 빠져 있는 것이다. git check-attr 로 확인한다

어떤 파일은 CRLF 여야 하는가

전부 LF 로 통일하자는 조언이 흔한데, 윈도우 전용 파일까지 그렇게 하면 곤란하다는 말도 그만큼 흔하다. 실제로 얼마나 곤란한지 확인해 봤다. LF 로만 만든 배치 파일에 라벨과 goto, for 반복, if else 블록, call 서브루틴, 마지막 줄에 개행이 없는 경우까지 넣고 cmd.exe 로 돌렸다.

C:\> cmd /c lf2.bat
item 1
item 2
item 3
yes
SUB

C:\> powershell -NoProfile -ExecutionPolicy Bypass -File lf.ps1
ps LF ok
block ok

전부 정상 동작했다. Windows 10 빌드 19045.6466 의 cmd.exe 와 PowerShell 5.1 에서는 LF 배치 파일이 실행됐다. 반드시 CRLF 여야 한다는 이야기는 적어도 이 구성에서는 재현되지 않았다.

그렇다고 배치 파일을 LF 로 두자는 뜻은 아니다. 판단의 근거는 성공 여부가 아니라 위험의 비대칭에 있다. 윈도우 전용 파일을 CRLF 로 두어서 잃는 것은 없다. 리눅스에서 실행될 일이 없기 때문이다. 반대로 리눅스에서 돌 파일을 CRLF 로 두면 확실히 깨진다. 그러니 규칙은 간단해진다. 어디서 실행되는지로 정한다.

파일권장이유
.sh, .bash, .py, .pl, .rbLF셰뱅이 CR 을 인터프리터 경로에 포함시킨다
Makefile, systemd 유닛, cron 파일LF값 끝에 CR 이 붙어 경로와 명령이 어긋난다
.env, .conf, .yml, .jsonLF파서에 따라 값 끝의 CR 이 그대로 들어간다
SSH 공개키, authorized_keysLF키 문자열이 달라져 인증이 조용히 실패한다
.bat, .cmdCRLF이 환경에서는 LF 도 동작했지만, 윈도우 전용이라 CRLF 로 두어 잃을 것이 없다
.ps1어느 쪽이든LF 로 정상 동작했다. 이쪽은 BOM 여부가 더 자주 문제가 된다
이미지, 압축 파일, 폰트변환 금지.gitattributes 에 binary 로 지정한다

에디터와 CI 에서 막는 법

고치는 것보다 안 생기게 하는 편이 싸다. 층은 셋이다. 편집기에서 한 번, 저장소에서 한 번, 파이프라인에서 한 번 막는다. 편집기 층은 .editorconfig 가 맡는다. 규격상 end_of_line 은 lf, cr, crlf 를 받고 값은 대소문자를 가리지 않는다.

# .editorconfig
root = true

[*]
end_of_line = lf
insert_final_newline = true
charset = utf-8
trim_trailing_whitespace = true

[*.{bat,cmd}]
end_of_line = crlf

[*.md]
trim_trailing_whitespace = false

두 파일은 역할이 겹치지 않는다. 앞의 것은 편집기가 저장할 때, 뒤의 것은 git 이 커밋과 체크아웃을 할 때 작동한다. 둘 다 두되 확장자 목록을 맞춘다. 어긋나면 저장할 때와 커밋할 때 값이 달라 매번 변경이 생긴다.

마지막 층은 검사다. 저장소 인덱스에 CRLF 로 들어간 텍스트 파일이 있는지 한 줄로 확인할 수 있다.

$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
$ echo $?
1

# 오염된 저장소에서는
$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
i/crlf  w/crlf  attr/                   added.txt
$ echo $?
0

깨끗하면 아무것도 출력하지 않고 종료 코드 1을, 문제가 있으면 목록과 함께 0을 준다. CI 스텝에서는 앞에 ! 를 붙여 찾으면 실패로 뒤집으면 된다. 파일을 직접 훑는 방식보다 이 방법이 나은 이유가 셋 있다. 바이너리는 i/-text 로 나와 자동으로 빠지고, .gitattributes 로 CRLF 를 허용한 파일은 정규화된 뒤 i/lf 로 나오며, 무엇보다 앞에서 본 grep 의 텍스트 모드 함정을 피한다.

덧붙여, 줄바꿈이 섞이면 코드 리뷰가 먼저 무너진다. 내용이 같아도 전부 바뀐 것으로 나오기 때문이다.

$ diff a_lf.txt a_crlf.txt
1,3c1,3
< alpha
< beta
< gamma
---
> alpha
> beta
> gamma

$ diff --strip-trailing-cr a_lf.txt a_crlf.txt
$ echo $?
0

보이는 글자는 완전히 같은데 세 줄 모두 다르다고 한다. 리뷰어가 실제 변경을 찾을 수 없게 되고, 이 상태로 며칠 지나면 저장소 전체가 섞인다. --strip-trailing-cr 은 급할 때 쓰는 임시방편이지 해결책이 아니다.

마지막으로, 왜 어떤 코드는 멀쩡한지도 알아 둘 만하다. 언어 런타임이 읽는 단계에서 이미 변환해 주는 경우가 있다.

$ python nl.py
default  : 'ENV=prod\n'
newline='': 'ENV=prod\r\n'
binary   : b'ENV=prod\r\n'
split    : ['ENV', 'prod']
split raw: ['ENV', 'prod\r']

파이썬은 텍스트 모드로 열면 기본으로 줄바꿈을 \n 하나로 통일해 준다. 그래서 파이썬 코드는 CRLF 파일을 읽어도 대체로 무사하다. 반대로 newline="" 이나 바이너리 모드로 열면 CR 이 그대로 들어오고, 그 값을 split 하면 'prod\r' 이 나온다. 같은 파일을 두 코드가 다르게 읽는 상황이 실제로 만들어진다는 뜻이다.

줄바꿈과 BOM 은 다른 문제다

이 둘은 자주 같이 묶여 이야기되는데, 원인도 위치도 해법도 다르다. 줄바꿈은 모든 줄의 끝에 있고, BOM 은 파일의 맨 앞에 한 번 있다. 증상이 겹쳐 보이는 이유는 둘 다 「눈에 안 보이는 바이트가 값에 섞인다」는 형태를 공유하기 때문이지, 같은 원인에서 나오는 것이 아니다.

  • 줄바꿈은 0x0D 0x0A, BOM 은 UTF-8 기준 0xEF 0xBB 0xBF 다. 겹치는 바이트가 없다
  • 고치는 도구도 다르다. 다만 dos2unix 는 기본으로 둘 다 손댄다. 앞 절에서 확인한 대로다
  • 셰뱅이 깨지는 증상은 둘 다 만든다. 첫 줄 앞에 BOM 이 있어도, 첫 줄 끝에 CR 이 있어도 인터프리터를 못 찾는다
  • 구분은 xxd 파일 | head -1 한 줄로 끝난다. 맨 앞 efbbbf 인지 줄 끝 0d0a 인지만 보면 된다

BOM 쪽의 세부는 BOM이 만드는 버그 - 보이지 않는 3바이트가 셸과 JSON과 CSV를 깨뜨리는 자리에 따로 정리해 두었다. 한글이 네모나 물음표로 보이는 문제는 또 다른 층인데, 그쪽은 한글이 깨지는 지점을 특정하는 법 - cp949와 UTF-8, 두 종류의 인코딩 오류에 있다. 세 문제가 겹쳐 있을 때는 인코딩 → BOM → 줄바꿈 순서로 하나씩 걷어 내는 편이 빠르다.

정리 - 순서대로

당장 깨진 파일이 있다면 순서는 짧다. file 로 종류를 확인하고, dos2unix 로 바꾸고, 다시 실행한다. 여기까지가 5분이다. 문제는 그 다음이다. 같은 일이 다음 주에 또 생긴다면 파일이 아니라 파이프라인을 고쳐야 한다.

  1. 진단. file 파일 과 xxd 파일 | head -1. 줄 끝 0d0a 인지, 맨 앞 efbbbf 인지 구분한다
  2. 변환. dos2unix 파일. CSV 처럼 BOM 이 필요하면 -b, 옛 맥 파일이면 -c mac. tr -d '\r' 은 쓰지 않는다
  3. 저장소 규칙. .gitattributes 에 * text=auto 와 실행 파일 확장자별 eol=lf. 윈도우 전용은 eol=crlf
  4. 과거 정리. 깨끗한 작업 트리에서 git add --renormalize . 후 단독 커밋. 이것을 하지 않으면 규칙은 장식이다
  5. 편집기. .editorconfig 에 end_of_line = lf. 확장자 목록을 .gitattributes 와 맞춘다
  6. 검사. CI 에 ! git ls-files --eol | grep -E '^i/(crlf|mixed)' 한 줄

가장 중요한 것은 4번이다. 이 글에서 실행으로 확인한 것 중 실무에 가장 자주 걸리는 사실이 규칙을 넣어도 과거는 그대로라는 것이었다. * text=auto 아래에서 그 파일을 수정해 다시 커밋해도 인덱스는 CRLF 였다. 재정규화는 저절로 일어나지 않는다.

윈도우에서 확인했다는 말은 근거가 아니다. 이 글에서 확인한 것만 세 가지다. Git Bash 는 CRLF 셰뱅을 알아서 처리해 스크립트를 정상 실행하고, grep -c $'\r' 은 CRLF 파일에서 0을 돌려주며, 명령 치환은 값 끝의 CR 을 떼어 낸다. 세 가지 모두 문제를 가려 준다. 검증은 실제로 배포될 환경에서, 최소한 git ls-files --eol 처럼 플랫폼을 타지 않는 방법으로 한다.

확인하지 못한 것

  • 리눅스 실기에서 bad interpreter: /bin/bash^M 원문 메시지를 직접 찍어 보지 못했다. 이 PC 에는 리눅스 배포판이 설치돼 있지 않다. 본문에 붙인 것은 같은 메커니즘을 실행 계층에서 재현한 것이며, 메시지 문구는 셸과 배포판에 따라 다를 수 있다
  • 같은 이유로, 이 환경의 bash 가 명령 치환에서 CR 을 떼어 낸다는 것은 확인했지만 리눅스 bash 에서는 CR 이 남는다는 대비를 실행으로 확인하지는 못했다
  • MS-DOS 가 CRLF 를 택하고 유닉스가 LF 를 택한 경위를 담은 1차 자료는 확인하지 못했다. 본문에는 두 제어 문자의 이름이 가리키는 동작과 POSIX 의 줄 정의까지만 적었다
  • 레지스트리 파일이나 일부 윈도우 도구가 CRLF 를 요구한다는 이야기는 검증할 방법이 안전하지 않아 시험하지 않았고, 따라서 본문에 쓰지 않았다
  • 배치 파일 시험은 이 한 대의 Windows 10 빌드 19045.6466 에서만 했다. 다른 윈도우 버전, 다른 배치 구문에서 LF 가 문제를 일으킬 가능성은 배제하지 못했다
  • dos2unix 의 최신 배포본은 7.5.7(2026-08-27)이지만 이 환경의 빌드는 7.5.2 다. 새 버전에서 달라진 동작은 확인하지 못했다
  • git 공식 문서 중 git-config 페이지는 접속 시 본문이 중간에서 잘려 core.autocrlf 항목이 읽히지 않았다. 그래서 kernel.org 미러의 같은 문서로 확인했고, 참고 자료에는 실제로 읽은 쪽을 달았다

참고 자료

  • gitattributes (Git 공식 문서) — text, text=auto, eol=lf, eol=crlf 의 정의. eol 미지정 시 기본이 윈도우에서 crlf, 그 외에서 lf 라는 서술과 git add --renormalize . 안내가 여기에 있다
  • git-config (kernel.org 미러) — core.autocrlf 의 세 값, core.eol 의 lf/crlf/native, core.safecrlf 의 true/warn/false 설명
  • EditorConfig Specification — end_of_line 이 lf/cr/crlf 를 받고 대소문자를 가리지 않는다는 규격. insert_final_newline, charset 등 다른 속성도 여기 있다
  • dos2unix 프로젝트 홈페이지 — DOS·맥·유닉스 줄바꿈 상호 변환, BOM 처리, 바이너리 자동 건너뛰기. 2026년 9월 기준 최신 배포본은 7.5.7(2026-08-27)
  • POSIX.1-2024 Definitions (The Open Group) — 3.185 Line 의 정의. 「개행이 아닌 문자 0개 이상에 종료용 개행 문자 하나를 더한 것」. 이 글의 모든 증상이 여기서 출발한다
