コードは開いていても名前は開いていない - オープンソースライセンスが決めない商標・ドメイン・リリース権限

ライセンスはコードの利用条件を決める。プロジェクトが誰のものかはライセンスの外側で決まる

2026-09-12 開発・インフラ

どんなオープンソースプロジェクトにも、リポジトリの一番上にライセンスファイルが一枚置かれている。その一枚を読めば、このコードを複製してよいか、改変してよいか、改変したものを再び外に出してよいか、出すときに何を添えねばならないかが決まる。ところが、その一枚をどれだけ読んでも最後まで答えの出ない問いが一つある。このプロジェクトは誰のものか。

分けるべきものは一つだ。ライセンスはコードという著作物の利用条件を定める文書であって、プロジェクトという組織とそれに付随する資産の帰属を定める文書ではない。これは抽象的な話ではなく、複数の財団がすでに公開方針文書に一文で書き込んでいることである。Linux Foundation の商標使用ガイドラインはこう書く。A copyright license, even an open source copyright license, does not include an implied right or license to use a trademark that may be related to the project developing the licensed software.

だからフォークは最初から半分だ。コードは丸ごと持って行けるのに、名前は付いてこない。ドメインも、パッケージを取りに行くあの住所も、更新を届けていたチャネルも付いてこない。ライセンスをどれだけ正確に読んでもこの一覧は出てこない。ライセンスが扱う領域ではないからだ。

以下で根拠に用いるのは、ライセンス本文二件とオープンソースの定義、四つの公開商標方針、そして Python パッケージインデックスの名前保持規定である。引用はそれらの文書に書かれている範囲に限る。例として挙げるプロジェクトは公開された方針文書を持つところから選んでおり、進行中の争いの当事者やその是非は扱わない。特定の案件を判定することはここでの仕事ではなく、構造を見るのに必要な分だけ文書を引く。

きっかけ - 誰のものかという問いが生まれる場所

きっかけになったのは、広く使われているあるオープンソースプロジェクトについてこのプロジェクトは誰のものかを問う公開記事である。その記事が並べる項目を見ると一つのことが目につく。コードの所有はそもそも争点ではない。争点として上がるものはすべてコードの外側の資産だ。商標がどの法人にあるのか、公式サイトの基盤を誰が運用しているのか、拡張機能が利用者に届く通路を誰が開け閉めするのか、理事会を誰が決めるのか。

その案件自体は複数の手続きが進行中であり、判断が残っている部分もある。その判断を代わりに下すことはここでやろうとしていることではない。持ってくるのは一つ、問いの形だけだ。

問いの形はこうだ。ライセンスはすでに答えを出した。コードは誰でも複製し、改変し、再頒布できる。ところがその答えを出した後にも答えの出ていない枠が六つほど残る。その枠はライセンスファイルのどこにもなく、それぞれ別の法と契約とアカウントに結びついている。

重要なのは、この形が特定のプロジェクトだけのものではないという点だ。財団を置くプロジェクトも、一社が貢献の大半を作るプロジェクトも、一人が週末に維持するプロジェクトもまったく同じ六つの枠を持つ。違うのは各枠に書かれる名前であり、その名前が文書として公開されているかどうかだけである。

ライセンスが実際に決めること

ライセンスのする仕事は狭く明確だ。著作権という排他的権利を持つ側が、その権利のうち一部をどんな条件で他人に許すかという宣言である。許諾の対象は四つのあたりで決まる。

  • 複製 — 写しを作ってよいか。オープンソースライセンスはすべてここに是と答える。
  • 改変 — 直してよいか。そして直したものを再び外に出してよいか。
  • 頒布 — 原本でも改変版でも他人に渡してよいか。渡すときに何を添えねばならないか。
  • 条件 — 表示を維持すること、告知ファイルを同梱すること、コピーレフトなら受け取った人にソースを提供すること、特許許諾が付くかどうか。

ここまでが全部である。オープンソースの定義の十項目にも、商標・ガバナンス・所有主体に当たる条項はない。その文書は頒布と利用の権利だけを扱う。

ただし名前に関する一文がオープンソースの定義の第4項の末尾に付いており、その向きが面白い。The license may require derived works to carry a different name or version number from the original software. ライセンスが名前を与える条項ではなく、派生物に別の名前を付けるよう要求できるようにする条項だ。オープンソースの定義でさえ、名前は付いて行かない側を想定している。

項目ライセンスが決めるか決めないならどこで決まるか
コードを複製・改変・頒布できるか決める—
頒布時に添えねばならない告知決める—
ソース提供義務が生じる条件決める—
特許許諾が一緒に来るか決める—
プロジェクト名とロゴを使えるか決めない商標法と商標権者の公開商標方針
公式ドメインとサイトを誰が運用するか決めないレジストラとの契約と登録名義
パッケージレジストリのその名前の枠決めないレジストリの規約と名前の保持・移転方針
マージ・リリース・署名の権限が誰にあるか決めないホスティングアカウントの組織設定とプロジェクトのガバナンス
資産を保有する法人と理事会の構成決めない定款と理事会規程
フォーラム・イシュー・文書サイトの運用主体決めない費用を払い契約を結んだ側

ライセンス本文が商標を切り離す仕方

ライセンスが商標を扱わない、という言い方は不正確だ。複数のライセンスが商標を明示的に切り離している。沈黙ではなく排除である。

Apache License 2.0 第6条は見出しからして商標だ。This License does not grant permission to use the trade names, trademarks, service marks, or product names of the Licensor, except as required for reasonable and customary use in describing the origin of the Work and reproducing the content of the NOTICE file. 例外として残るのは二つだけである。著作物の出所を説明する通常の範囲と、告知ファイルの内容をそのまま再現する場合だ。

MPL 2.0 第2.3項も同じ場所を突く。This License does not grant any rights in the trademarks, service marks, or logos of any Contributor. ここでも例外は告知要件を守るのに必要な範囲に限られる。

注目すべきは告知を維持せよという要求と、商標を使ってよいという許諾が同じものではないという点だ。Apache License 2.0 第4条は、再頒布の際に著作権・特許・商標・帰属の告知をソースに維持し、告知ファイルがあればその内容を含めるよう求める。これは残せという義務であって使ってよいという許諾ではない。二つの文をつなげて読むと向きがそっくり逆になる。

短い許容型ライセンスの中には商標条項がそもそもないものもある。条項がないという事実は許諾を意味しない。商標は著作権とは別の根拠で生じる権利であるから、著作権ライセンスの沈黙はその権利に何の影響も与えない。Linux Foundation の方針文書は同じ論旨をもう一段押し進める。オープンソースライセンスは著作物の改変を制限なく許し、財団もその権利を妨げるつもりはないが、特定の商標を使う権利は、そのソフトウェアをオープンソースライセンスで受け取ったという事実では決まらないと書く。

文書商標について書くこと残る例外
Apache License 2.0 第6条ライセンサーの商号・商標・サービスマーク・製品名を使う許諾を与えない出所説明の通常の範囲、告知ファイルの再現
Apache License 2.0 第4条再頒布時に商標告知をソースに維持し、告知ファイルの内容を含めること維持義務であって使用許諾ではない
MPL 2.0 第2.3項いかなる貢献者の商標・サービスマーク・ロゴについても権利を与えない告知要件の遵守に必要な範囲
商標条項のない短いライセンス商標について何も述べない沈黙は許諾ではない。権利の根拠が異なる
オープンソースの定義 第4項派生著作物に別の名前やバージョン番号を要求することを許す名前は付いて行かない側が既定に近い

ライセンスが決めない六つの枠

ライセンスの外側に残る枠を集めると六つになる。それぞれをつなぎとめている根拠が全部違うという点が肝だ。

  • 商標と名前 — 商標法と、商標権者が公開した商標方針が決める。コードとはまったく別の法領域である。
  • ドメインと公式サイト — レジストラとの契約、そして登録名義が決める。契約が終われば枠も終わる。
  • パッケージレジストリのアカウントと配布チャネル — そのレジストリの規約と名前の保持・移転方針、そしてアカウント所有者の一覧が決める。
  • リポジトリの管理権限 — ホスティングアカウントの組織設定が決める。マージ権限、タグ生成、リリース資産のアップロード、パイプラインの秘密値がここにぶら下がる。
  • 財団と法人構造 — 定款と理事会規程が決める。どの資産が法人のもので誰が理事を決めるかがこの枠の中身だ。
  • コミュニティ基盤 — フォーラム、イシュートラッカー、文書サイト、翻訳プラットフォーム、メーリングリスト。おおむね費用を払う側に結びつく。

六つの枠には共通点が一つある。すべて一つのアカウントか一つの法人に結びついており、コードのようには複製されない。リポジトリは数秒で写しができるが、ドメインには写しができない。レジストリのその名前の枠も一つきりだ。だからこれらの枠は分かれた瞬間ただちに排他的な選択になる。

各枠に誰が座っていて、その席が実際にどんな力を持つのかを一つの表にまとめるとこうなる。最後の列が最も実務的だ。その席を取れなかったときに何が起きるか。

資産通常の保有主体保有者にできること取れなかったときに起きること

商標 - コードをフォークしても名前は持って行けない

六つの枠のうち最も頻繁に誤解されるのが商標だ。コードが自由に流れるのだから名前もそうだろうという推測が付くからである。公開された商標方針は正反対を書いている。

Apache Software Foundation の商標方針はこう始まる。The Apache Software Foundation (ASF) owns all ASF-related trademarks, service marks, and graphic logos on behalf of our project communities, and the names of all ASF projects are trademarks of the ASF. プロジェクト名そのものが財団の商標だという宣言であり、保有の名分はコミュニティに代わってである。

Python Software Foundation は、登録商標である言語名とロゴ、複数のイベント名を保有すると書く。そして一文で整理する。All trademarks, even those that apply to open source software, must be used according to certain legal requirements. ただし方針は禁止だけをするのではない。その言語と共に使う、あるいはその言語に適することを指す製品名の形は許すと、例を挙げて書いてある。会社名に使うには事前の書面許可が必要だという条件は別に付く。

WordPress Foundation の方針は、名前とロゴの商標を財団が保有・監督すると書き、イベント名に当たる別の商標は財団の子会社法人が保有すると明かす。商業利用を望む場合には独占的な商業ライセンスを持つ先に問い合わせるよう案内が付いている。この配置が示すのは、商標の保有と商業的活用の権限が別の主体に分かれうるという事実だ。

Linux Foundation の方針は前の三つと違って原理を先に書く。著作権ライセンスはオープンソースライセンスであっても関連商標を使う黙示の権利を含まない、という一文がそれだ。そして登録の試みに対する禁止が明示的である。財団の商標を商標・商号・ドメイン名・屋号として登録しようとするな、と書く。

公開商標方針保有主体について書くことドメインについて書くこと
Apache Software Foundation財団がコミュニティに代わってすべての商標を保有し、プロジェクト名がそのまま財団の商標である混同を招くドメイン使用を禁じ、製品名を二次ドメインとして使うことを認めない
Python Software Foundation言語名は登録商標であり、ロゴとイベント名も財団が保有する会社名に使うには事前の書面許可を求める
WordPress Foundation名前とロゴの商標を財団が保有・監督し、イベント商標は子会社法人が保有するドメイン名や最上位ドメインの一部として使うことを認めない
The Linux Foundation財団法人が商標とロゴを保有し、ライセンスは商標権を与えないという原理を書く商標をドメイン名やその一部として使わないこと、商標・商号・ドメイン・屋号として登録しないこと

四つの文書は配置が互いに違うが同じ枠を埋めている。そして四つとも、ドメインの話を別に書く。理由は次の節にある。

ドメイン - 既定の経路を握る枠

ドメインが重要な理由は検索順位ではない。既定の経路だという点である。インストール案内の一行目、文書のリンク、更新確認の要求が向かう住所、信頼ストアが指す先が、すべて一つのドメインに向かう。公式サイトがダウンロードと文書と拡張機能一覧を兼ねると、一つのドメインが同時に三つの役割を担う。

ドメインは所有ではなく登録である。レジストラとの契約で維持され、登録名義に結びつき、その名義は一つのアカウントの中にある。コードのように分かれない。この席を握る側は、どのソフトウェアがその住所から出て行くかを決められるし、既存のインストール済みの版がその住所を参照し続けるなら、その関係はかなり長く続く。

商標方針がドメインを別に書くのもこのためだ。名前がドメインに入ると、名前の使用であると同時に経路の占有になる。二つのことが一つの文字列に重なっているので、方針はおおむね重ならないようにする側で定まる。

パッケージレジストリの名前の枠

利用者が実際にソフトウェアを受け取る経路は、リポジトリではなくレジストリである場合が多い。設定ファイルに名前が一行書かれていて、ビルドが回るたびにその名前が解決される。だからレジストリのその名前の枠は配布経路の実体だ。

その枠はアカウントに結びつく。名前一つに所有者の一覧が付き、所有者だけが新しい版を公開し、所有者だけが権限を譲る。そして名前をめぐる争いが生じたときにレジストリがどう処理するかは、公開方針文書に書かれている。

Python パッケージインデックスの名前保持規定が代表的だ。その規定は活動中のプロジェクトと放置されたプロジェクトをまず分ける。放置された場合にのみ、そして列挙された条件をすべて満たすときにのみ名前が移転する。一方、活動中のプロジェクトについては一文で線を引く。The maintainers of the Package Index are not arbiters in disputes around active projects.

判断の経路も段階式だ。一次はインデックスの維持者、次はパッケージングワーキンググループであり、そのワーキンググループがこの文書の扱う争いについて最終的な判断を持つ。商標はここで再び登場する。同じ文書は知的財産権侵害の節で、第三者の商標を名目的使用やフェアユースの範囲を超えて使う場合を扱い、通報窓口を別に置いている。

ここから出る結論は単純だ。レジストリの名前は技術では解けず、手続きで解ける。そしてその手続きの敷居はおおむね高い。新しい名前で新しい枠を作るほうが手続きを踏むより速い場合が多く、だから実際のフォークはほぼ常に新しい名前を使う。その代わり、既存の名前を書いてあるすべての設定ファイルは新しい枠を知らない。消された名前と残った参照がどうずれるかは削除されたパッケージ名に要求が届き続ける理由で層ごとに扱ったことがある。

リポジトリ管理権限とリリース署名

リポジトリは複製される。しかしリポジトリを取り巻く権限は複製されない。ここにぶら下がるものを並べると次のとおりだ。

  • マージ権限 — どの変更が本流に入るかを決める。フォークには履歴が付いてくるが、今後のマージ地点は付いてこない。
  • タグとリリース — バージョン番号を付け、配布物を上げる場所。下流の自動化がこの場所を参照する。
  • パイプラインの秘密値 — レジストリ公開トークン、署名鍵、配布先の資格情報。リポジトリの中身ではなく設定に入っている。
  • セキュリティ通報窓口 — 非公開の通報を受ける経路と、その経路を読む人の一覧。
  • 組織オーナーのアカウント — 上の全部を巻き戻せる上位の席。たいてい人数が最も少ない。

このうちリリース署名鍵は性格が少し違う。他の席は移せばよいが、署名鍵は検証する側の信頼がその鍵に結びついている。ディストリビューションのパッケージャーと社内ミラーとロックファイルの検証設定がその鍵を知っている。新しい鍵で署名すればそのすべての場所に新しい起点を植えねばならず、その作業はコードを複製する仕事とは比べものにならないほど手がかかる。

ホスティング自体を移すときに何が付いてきて何が残るかはコードホスティングを移せる状態にしておくで項目ごとに整理したことがある。所有構造が分かれる状況は、その一覧が選択ではなく条件として降りかかる場合に近い。

財団という語が指す三つの構造

財団があるという事実だけで答えが出るわけではない。公開文書を並べて置くと、同じ語が互いに違う配置を指していることがすぐ見える。

  • コミュニティに代わって保有する形 — 財団がすべての商標を保有しつつ、名分をプロジェクトコミュニティに置く。Apache Software Foundation の方針文書がこの文を使う。
  • 保有と商業活用が分かれた形 — 財団が商標を保有し、商業利用は別の独占ライセンスを持つ先を経る。一部のイベント商標は子会社法人が別に保有することもある。
  • プロジェクトごとに別の法人格を置く形 — 上位の財団の下に個別プロジェクトを LLC のシリーズとして置く。Terraform のフォークとして出発した OpenTofu がこの形で運営されていると自らの文書に書かれている。

だから財団の有無より先に問うべきものは三つだ。どの資産をその法人が保有するか。理事会を誰が決めるか。その法人と主たる商業主体がどんな契約でつながっているか。公開方針文書はおおむね一つ目にしか答えない。二つ目と三つ目は定款や別の規程にあり、公開されていない場合も多い。

答えが公開されていないという事実自体は欠陥ではない。ただし判断の材料がないという事実はそのまま残る。依存を決める場面では、この区別が実質的な差を生む。

コミュニティ基盤 - フォーラムとイシューと文書

最後の枠は目につきにくい。フォーラムのアーカイブ、イシュートラッカーの過去の記録、文書サイト、翻訳プラットフォーム、メーリングリスト、チャットの場。これらの席は商標でもなく契約の目的物でもないが、プロジェクトの記憶が保存された場所である。

この席をつなぎとめているのはおおむね費用だ。ホスティング料金を払う側、管理者アカウントを握る側が存続と閲覧範囲を決める。そして移した瞬間にほとんどのリンクが切れる。切れたリンクは検索結果から静かに消え、その決定がなぜ下されたのかを説明していた議論も一緒に消える。

実務に及ぼす影響は思ったより大きい。古いイシュー番号がコミットメッセージやコメントに埋まっているからだ。その番号が指していた先が空けば、コードに残った参照は意味を失う。

フォークが持って行けるものと行けないもの

これまでの枠をフォークの観点で並べ直すと、境界が鮮明になる。

区分項目根拠
持って行けるソースコード、コミット履歴、ブランチとタグの中身ライセンスが複製と改変と頒布を許す
持って行けるドキュメント本文、テスト、ビルド設定、サンプル同じリポジトリに著作物として入っている
持って行ける貢献者が積み上げた文脈 — ただし人が付いてくるときだけ人は契約の目的物ではない
持って行けないプロジェクト名とロゴ商標は別の権利であり、ライセンスは与えない
持って行けない公式ドメインと、その住所を指す既存のインストール済みの版登録名義に結びついている
持って行けないパッケージレジストリのその名前の枠アカウント所有とレジストリの名前方針が決める
持って行けないリリース署名鍵と、その鍵を信頼する下流の設定検証の起点が鍵に結びついている
持って行けないフォーラム・イシュー・文書の記録とそのリンクホスティング主体に結びついている
持って行けない利用者の習慣 — インストールコマンド、検索語、ブックマークどこにも記録されていないが、最も遅く変わる

表の下半分がフォークの実際の費用だ。コードを複製するのにかかる費用は事実上ゼロに近く、費用は全部下半分で発生する。そして下半分の項目は金ですぐに解決しない。時間が要るものがほとんどである。

フォークが根を張るために付いてこねばならないもの

フォークが技術的に成り立つことと、生態系で根を張ることは別の問題だ。根を張るにはコード以外に付いてこねばならないものがある。

  • 文脈を持つメンテナー — コミット権限ではなく、そのコードがなぜそうなっているかを知る人である。この資産は移り動くが複製はされない。
  • 配布経路 — レジストリの新しい名前、コンテナイメージのタグ、ダウンロード住所。利用者が手を動かさなくても届く経路であってこそ意味がある。
  • 下流のパッケージャー — ディストリビューションの管理者と社内ミラーの運用者。彼らが新しい名前を採用してこそ大多数の利用者へ自動的に届く。オープンソースで最も過小評価される席だ。
  • 互換の経路 — 既存の設定ファイルがそのまま読めるか、拡張機能のインターフェースが維持されるか、移行案内の文書があるか。ここで摩擦が大きいと利用者は動かない。
  • 費用を負担する主体 — 基盤の料金、商標登録、最小限の法務確認。初年度にこれがなければ、次の分かれ道で同じことが繰り返される。
  • 安定性の証拠 — 決まった周期で出るリリースとセキュリティ修正。約束ではなく記録が信頼を作る。

六つのうちコードに関わるものは事実上一つもない。フォークの難度はコードの難度ではなく生態系の難度だ。誰が維持するのかという別の軸は誰がインフラを維持するのかで別に扱ったことがある。所有と維持は重なるが同じ問いではない。

使う側が依存する前に見ること

ここまでが構造だとすれば、実務で使える形に縮めると次の表になる。ライセンスファイルを見た後に見るものだ。

見るものどこにあるか何を読み取るか
商標方針の文書プロジェクトサイトまたはリポジトリのルート名前とロゴを誰が保有し、どこまで許すか。文書自体がなければそれも情報だ
ガバナンス文書リポジトリのルートまたはコミュニティ文書決定がどう下され、その手続きがどう変わるか
リリース権限者の人数メンテナー一覧、レジストリの所有者表示一人なら、その一人が単一障害点であり単一決定点でもある
資産を保有する法人サイト下部の表記、商標方針、財団のページ資産が個人名義か法人名義か
貢献の条件貢献案内の文書貢献者ライセンス契約か原作者証明の署名か。権利が集まるか散るか
配布チャネルの数インストール案内経路が一つだけなら、その一つが塞がるとき代替がない
依存を切るときの代替どこにも書かれていない。自分で立てるしかない差し替えられる実装があるか、データを取り出せるか

最後の行が最も頻繁に空いている。代替がないというのは、この依存が切れる日から選択肢を作り始めることになるという意味であり、その時点の作業は平時よりはるかに高くつく。代替を先に書いておく費用は文章数行だ。

リポジトリを開いたときにまず探すファイル名は、おおむね決まっている。

LICENSE            利用条件 — ここまでがライセンスの領域だ
TRADEMARK.md       名前とロゴを誰が保有し、何を許すか
GOVERNANCE.md      決定を誰が下し、その手続きをどう変えるか
MAINTAINERS  OWNERS  マージとリリースの権限を持つ人の一覧
CONTRIBUTING.md    貢献の条件 — 契約の署名か原作者証明か
SECURITY.md        通報窓口とリリースの検証方法

作る側が先に決めておくこと

反対側から見ると、同じ一覧が設計項目になる。そしてこれらの項目は後で決めると遅い。決める必要が生じる時点はたいてい利害がすでに分かれた後であり、そのときは同じ文を前にしても合意にならない。

決めること選択肢後で決めると難しくなる理由
名前とロゴの保有主体個人名義、会社名義、別法人名前に価値が付いた後は移転そのものが交渉の対象になる
貢献者の合意方式貢献者ライセンス契約、原作者証明の署名、どちらもなし遡って適用するには過去の貢献者全員の同意が必要になる
リリース権限の分散一人、少人数のグループ、署名鍵の分離保管引き継ぎなく一人が消えると配布が止まる
ドメインとレジストリアカウントの名義個人アカウント、共用アカウント、法人アカウント個人アカウントはその人と共にアクセス手段が消える
ガバナンス文書の有無なし、簡単な原則、手続きまで明文化争いが起きた後に作る規則は当事者向けの規則として読まれる
商業利用の許容範囲全面許可、条件付き、別ライセンスすでに使っている先ができた後では条件を付けにくい
フォークへの態度沈黙、名称変更の要求、友好的な表記の許可決めておかないと商標法の一般規則が代わりに答える

この表で最も安い枠は一行目と五行目だ。名前を選ぶ日に保有主体を一緒に決める費用は事実上ない。ガバナンス文書も初期には一枚もので十分である。書かれていない合意は、人が変われば残らない。

ライセンス自体を変える決定はまた別の軸であり、すでに出た版との非対称のために別の計算が要る。その計算はライセンスを変えると何が変わるのかに別途まとめてある。

反対側も - 集中が常に悪い配置とは限らない

資産が一か所に集まっているという事実だけで悪い構造だとは言えない。商標を一つの主体が保有する配置には、公開文書が書いている目的がある。WordPress Foundation の方針文書はその趣旨をこう書く。コードと伝統的な知的財産がどちらも開かれているプロジェクトにおいて、品質と信頼の目印として皆が頼れるのは商標の使用が許される場所だ、と。

この論旨は利用者の側から見ると実用的である。名前がどこにでも付けられるなら、その名前は何も保証しない。商標方針があってこそ公式の配布物とそうでないものを分けられる。

分散にも代価がある。リリース権限を広げれば配布が止まる危険は減るが、供給網に開く扉は増える。署名鍵を複数の場所に置けば一か所が消えても済むが、管理地点はその分増える。ガバナンス手続きを細かくすれば恣意的な決定は減るが、決定の速度も一緒に落ちる。

だから問うべきものは集中か分散かではない。どこまでが文書に書かれており、その文書を変える手続きが何か。この二つが書かれていればどんな配置でも予測でき、書かれていなければどんな配置でも予測できない。

まとめ - 五つの文

ここまでを五つの文に縮めるとこうなる。

  • ライセンスはコードの利用を定め、プロジェクトの所有は定めない。複数のライセンス本文が商標を明示的に排除しており、オープンソースの定義にも所有とガバナンスの条項はない。
  • 残る枠は六つで、それぞれ別の根拠に結びついている。商標は商標法、ドメインは登録契約、レジストリの枠はそのレジストリの方針、リポジトリの権限はアカウント設定、資産は法人、コミュニティ基盤は費用を払う側だ。
  • フォークは著作物を全部持って行き、アカウントと登録に結びついたものは一つも持って行けない。名前、ドメイン、レジストリの枠、署名鍵、記録のリンク、利用者の習慣が残る側である。
  • 依存する前に見るものは、ライセンスの次の五つの文書だ。商標方針、ガバナンス文書、リリース権限者の一覧、資産を保有する法人、そして切らねばならないときの代替。
  • 作る側で最も安い瞬間は名前を選ぶ日だ。その日に決めておかなければ、その後のどの日にもより安くはならない。

実務に移すと文が一つ残る。依存一覧にライセンスの列しかないなら、列が一つ足りない。その隣に商標方針とガバナンス文書の有無を書く枠をもう一つ置くことが、ここで挙げた中で最も安い措置である。

確認できなかったこと

以下の項目は今回の範囲内で一次資料から結論を出せなかった。根拠が揃うまで断定しない。

  • 進行中の案件の事実関係と判断 — きっかけになった記事が扱う案件は手続きが進行中である。各主張の真偽や責任の所在は公開方針文書で判定できる種類のものではなく、ここでの対象でもない。本文はその案件から問いの形だけを持ってきた。
  • Terraform のフォークの以前の名称 — OpenTofu が初期に別の名前を使っていて変えたという記述が複数の場所にあるが、プロジェクトの公開文書にその経緯を書いた一文は見当たらなかった。そこで本文には現在の名前と運営形態だけを書いた。
  • Linux Foundation 系プロジェクトの個別商標方針の本文 — プロジェクトの文書が方針集の住所を指しているが、その文書自体は今回開いていない。本文の Linux Foundation の引用は、財団の商標使用方針一件に限られる。
  • 他の言語生態系の名前争いの処理手続き — JavaScript・Rust・Java 側のレジストリが活動中のプロジェクトの名前争いをどう処理するかは今回の範囲に入れていない。本文の手続きの説明は Python パッケージインデックス一か所の規定である。
  • 貢献者の合意方式と商標帰属の関係 — 貢献者ライセンス契約が著作権のほかに商標まで扱う事例があるかは一次文書で確かめていない。本文は二つを別々の項目としてのみ扱った。
  • 韓国法における適用 — オープンソースのプロジェクト名の国内商標登録状況や国内の紛争処理手続きは今回の調査範囲の外だ。本文に引いた方針文書は各財団が自ら定めた使用条件であり、特定の法域の法解釈ではない。
