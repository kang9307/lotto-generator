Why Deleted Package Names Keep Getting Requests - The Code Is Gone, the References Are Not

Removal does not empty a name. What it fails to cut is every file that still spells that name out

2026-09-11 Dev & Infra

A package is judged malicious and taken off the registry. And yet install requests for that name keep arriving, several hundred of them every week. If that sentence sounds like it contradicts itself, the thing that has not been separated yet is what removal actually cuts and what it can never cut, no matter how firmly the announcement is worded.

There is only one separation to make. Removal cuts the path along which new code travels under that name. It does not go into anybody's files and edit the place where the name is written down. The code disappears and the reference stays. The reference that stays sends the same request again at its next scheduled moment. That request lands in a counter, and the counter turns into the sentence that comes back around as 「people are still installing it」.

One more thing splits here. Is the vacated slot actually empty? On npm at least, it is not left empty. The handling procedure that follows a malware finding contains, in the public documentation, a step that plants a security marker in that very slot. So the accurate name for this problem is not 「an empty name is dangerous」 but 「references that were never cut are still pointing at that name」.

The material relied on below is two npm public policy documents, the npm explanation of how download counts are produced, and the list document in the repository that prompted all this. The real names of packages judged malicious are not written here. Writing them out only steers searches toward those names. No assessment of any particular company or registry operator is offered either, and every command shown in the body is read-only.

The trigger - a list of removed names that still draw requests

What set this off is a list posted in a public repository, together with the tool that generates it. The way the list is built decides how far its conclusions reach, so the method comes first.

Take 240 widely used npm packages as seeds. Apply, mechanically, five of the ways package names commonly get mangled: drop the scope, swap a dot for a hyphen or the reverse, drop the hyphen entirely, drop a plugin prefix, and append a short suffix. That produced 773 candidate names on the npm side, of which 263 turned out to actually exist in the registry. The tool returned its danger verdict for 130 of them, and of those, 50 were published in the list. The remaining 80 were withheld.

The publication bar being narrow matters here. The list document says it considers only danger verdicts, and that within those it publishes an entry only when the evidence is one of two kinds. One is a security placeholder that npm itself put up. The other is a deprecation notice that names the real package outright. That is why the 50 published entries break down into 36 with a placeholder standing in the slot and 14 carrying a deprecation notice.

The list also carries a generation timestamp. The date printed on the document is 2026-09-10, and it states that the list is regenerated weekly. The headline of the post that carried this around said 35, while the rows in that section number 36. Neither figure is wrong; the natural reading is that they are values from two different weeks. Quote a number out of a weekly regenerated list as though it were a fixed fact, and it starts drifting from that moment on.

What that number actually counted

Before quoting a figure it is safer to establish what the figure did not count, because the survey population is drawn narrowly by construction.

  • What it did not count — the total number of packages ever pulled from the registry for malicious content. The population consists of candidates derived from 240 seeds, so any name that the derivation rules do not produce was never a candidate in the first place. This is not the result of an exhaustive survey, and it was never presented as one.
  • What it did count — within that candidate population, the number of names that actually exist in the registry, that drew a danger verdict from the tool, and whose evidence is a security placeholder npm itself put up. It is the intersection of three conditions holding at once.
  • Why it moves — the list is rebuilt every week and the install figure on each row is re-queried at the same time. A new marker going up pushes the count one way, and a change in the tool's verdict rules pushes it another. A number produced this way is a reading, not a constant.

Read precisely, then, the list says this. Among candidate names produced by the common ways package names get mangled, there are some three dozen that npm pulled for security reasons and marked, and requests are still arriving for them. That is a different sentence from 「35 malicious packages are still circulating」, and the difference is not a quibble. One describes leftover plumbing; the other describes active infection.

What happens to the name when a package is removed

This is where the article turns. The procedure npm documents for handling a malware report has three steps.

  • Remove the package from the registry.
  • Publish a security placeholder for the package, standing in the slot the removed code used to occupy.
  • Publish a security advisory alerting the community.

The second step corrects the premise this article opened with. The vacated slot is not empty. What stands there is a marker whose meaning is roughly 「what used to be here came down for security reasons」. The name is not open, and something still answers at that coordinate.

The consequence splits in two directions. Seen from the side that sent the request, the install mostly fails, or if it succeeds a package with no functionality lands in the tree. Seen from the registry side, that same request is one request that was answered normally. The whole statistics discussion later in this article turns on exactly that point: the count of requests that arrived and the count of times risk was realised are not the same number, and on these particular names they are very far apart.

So the framing 「deletion empties a name」 does not hold, at least not on this registry. What actually remains as a problem is not a vacant slot but the references that keep pointing at it. Half of the sections that follow are about those references.

The rules that stop the same coordinate from being reused

The unpublish policy treats names and versions as separate things, and that separation connects directly to what a lockfile is holding onto.

  • A name and version pair is never reused. Once that combination has been used it can never be used again, and even after an unpublish a new version number is required. That is the policy document's own wording, not an inference from behaviour.
  • Unpublishing everything brings a waiting period. If every version of a package is unpublished, no new version may be published under that name until 24 hours have passed.
  • The conditions for unpublishing at all are narrow. Within the first 72 hours of publishing, a package can be unpublished as long as nothing else in the public registry depends on it. After 72 hours, three conditions have to hold together: nothing depends on it, it had fewer than 300 downloads over the last week, and it has a single owner.

All of these rules point the same way. They stop different content from moving into a coordinate that has already been handed out. The coordinate a lockfile holds is the combination of name, version, resolved address and integrity hash, and once the name-and-version part of that is frozen at the registry level, the route by which 「the same coordinate, different content」 could happen narrows sharply.

That said, these are rules about reuse of a coordinate, not rules that force cleanup of a reference. Nothing on the registry side changes the fact that a lockfile in your repository still points at that coordinate. The case for carrying fewer dependencies in the first place is a separate argument, made in the choice to reuse less software; this article stays with the references that are already inside.

Other registries settled it differently

The same situation gets handled differently elsewhere, and the comparison makes it clearer why 「empty slot」 is the wrong picture.

  • Name retention comes first. The Python package index states in its public documentation that projects are never removed from the index solely on the basis of abandonment. The reason given is that artifacts uploaded to the index hold inherent historical value, which is a claim about the archive rather than about any individual maintainer.
  • Filenames cannot be reused either. The documentation states that a filename may not be reused even once a project has been deleted and recreated. The direction matches npm's rule about name and version pairs, arrived at through a different mechanism.
  • Malware reports were handled another way. The published note explains that the one tool administrators previously had was complete removal of the project from the database, and that this was often coupled with prohibiting the project name from being reused afterwards. The problem identified with that approach was that removals are pretty much irrevocable.

That is what quarantine was introduced for: an intermediate state. A quarantined project drops out of the installable index and cannot be installed, but if it turns out to have been misclassified it can be brought back. Where the only available action had been permanent destruction, a step that can be undone now exists between the two.

Set the two registries side by side and an axis appears. One plants a marker in the slot; the other clears the slot and locks it. The mechanics are close to opposite, and yet they share one property. On neither side is the name left open for anyone to take. The centre of gravity of the risk sits on the reference side, not the name side, and that is true regardless of which registry is doing the handling.

Why the requests keep coming - the references are still there

A single install request does not mean somebody just typed that name. Most of the time it means a name that was already written somewhere got read back exactly as written. What generates the request is the contents of a file, not a decision by a person.

Once that distinction is in place, the question 「why is this still being installed」 changes shape. What has to be answered is not carelessness on somebody's part but which files are holding that name, and why those files do not get updated. There is usually a reason, and quite often the reason is technically sound. A tag is supposed to be immutable by definition. Reproducing an old build requires that the old copies still exist. Neither of those is negligence.

What removal cannot fix is precisely this being-written-down. Whatever the registry does, the one line in your lockfile stays as it is. So the location of the countermeasure shifts as well. Instead of chasing what the registry took away, the first move becomes counting the references left on your own side — and that turns out to be a job you can do entirely by reading.

Where references survive, and why each layer goes unrefreshed

References do not survive in one place. The reason a layer goes unrefreshed differs from layer to layer, and where the reason differs, the right response differs too.

The layers machines read

The first five layers generate requests on their own without anyone touching them. It is reasonable to assume these produce the bulk of what shows up in the counters, because they run on schedules rather than on human attention.

The layers people read

The last three layers do not generate requests directly, but they keep producing new references. A line left in a document gets read by somebody who then writes the same line into a fresh repository. If the first group produces this week's requests, the second group produces next quarter's.

Read the table down its third column and a rule emerges. Half of the reasons a layer goes unrefreshed are design, not defect. Tags do not change and proxies hold their copies because reproducibility was built that way on purpose. Treat all of these layers as mess to be swept up and you end up breaking reproducibility in the name of hygiene. Each layer needs its own judgement, and the judgement is rarely 「delete it」.

What a weekly install figure actually counts

The definition npm gives when explaining its download counts is short. A download is a count of the HTTP 200 responses served that were tarball files. It does not count people, and it does not count whether an install succeeded. It counts responses.

The same document says what else is swept into that total: requests from automated build servers, requests from mirrors synchronising, and requests from robots that download every package for analysis. It also explains why none of that is filtered out. Detecting automated traffic accurately is genuinely hard, and for some packages — build tooling above all — automated requests are the real usage. And then the document nails it down: these are not absolute numbers, and they are definitely not the same as the number of users of a package. It adds a rough floor as well, noting that below roughly 50 downloads a day a figure is hard to tell apart from background noise.

Nature of the requestCounted?A human install?Which way it pushes the figure here

The last two rows are the point of the table. This figure does not err in one direction only. It inflates because of automated traffic and simultaneously deflates because installs served from cache never reach the counter. With neither error term measured, there is no direction in which to correct. Saying 「the true number is surely lower」 is as unfounded as saying 「the true number is surely higher」, and both sentences get written far too easily.

What the number can tell you and what it cannot

None of which makes the figure useless. Whether it answers depends entirely on the question put to it, so it is worth writing out both lists.

What it can tell you:

  • It is not zero. That much is solid. Whatever the value, the fact that some path toward that name is still alive holds regardless of how much noise is mixed into the total.
  • The trend among figures counted the same way. If last week and this week were counted by the same method, whether it is rising or falling comes through. The absolute value is untrustworthy while the slope is readable.
  • Differences in order of magnitude. A few hits a week and a few thousand hits a week are different states. Even a factor of two in error does not flip an order of magnitude.

What it cannot tell you:

  • How many people were exposed. There is no conversion factor from response counts to human beings, and inventing one is where most of the bad reporting on this topic starts.
  • How many organisations are affected. One organisation can generate thousands of hits, while hundreds of organisations sitting behind caches can generate none at all.
  • How many of those requests actually ran code. On these particular names a security marker already stands in the slot, so what the requests carried away was a marker rather than malicious code.

That third item changes the character of the number entirely. The figure is therefore best read not as 「how many people are being infected right now」 but as a proxy for 「how many paths are still pointing at that name」. Its value as a warning signal survives that reclassification intact. The path that carries away a marker today is the same kind of path that could carry away real code from some other name tomorrow, and that is the reason to care about it at all.

This is not the same problem as typosquatting

These two get discussed as one topic all the time, but they aim at opposite places. Merging them leaves the countermeasures on both sides loose.

A typo lure goes after a name nobody has written down yet. It targets the spots where a hand slips during typing, and its precondition is that somebody makes a fresh mistake. That is exactly why similarity checks and name lists work well against it. The situation in this article runs the other way: the name is already spelled out correctly, and the place it is spelled simply never gets updated. No new typo has to occur anywhere for the requests to keep going out.

A further axis has attached itself to this recently. Coding assistants produce package names that do not exist. The figures cited by the repository that prompted this article put 19.7% of generated package names in the hallucinated category, with 43% of those coming back identically when the same request was run again. What matters on this axis is not the percentage but the repeatability. If a different invented name came out every time, that would be closer to noise; when the same name keeps reappearing, that name has effectively become a fixed address.

The place where the middle column meets the right-hand one is precisely where this list stands. A name invented by a tool can collide with a name that was already pulled for security reasons. That is why the survey method was 「generate candidates with name-mangling rules and compare them against the registry」, and why the result ran into security markers rather than into empty space.

Where a name blocklist leaks

Building a list of dangerous names and blocking them is the first idea anyone has, but against this particular problem the ground it stands on is narrow. There are four places it leaks.

  • A list is retrospective by nature. Only names already known go into it. From the moment a new marker goes up, that name sits outside the list, and the refresh interval is exactly how wide the window stays open.
  • A list matches exact strings. A scope present or absent, a case difference, one separator changed, and the check is bypassed. Given that the candidate names in this problem were generated by precisely those kinds of variation, the aim is off in a fairly fundamental way.
  • A list usually sweeps direct dependencies only. It sees the names written into the manifest but tends to miss names pulled in indirectly from deep inside a lockfile, and a good share of the surviving references live down there.
  • A list looks at names, not at content. Where a different version arrives under the same name, matching on the name alone lets it through without a second look.

So name-based defense belongs in the supporting role. The load-bearing work sits elsewhere: pinning what arrives by its content rather than by its name. The layer below that question — where a chain of trust actually begins — is treated separately in where bootstrap trust breaks.

Every measure has a place where it holds and a place where it gives. Written out as a table, it becomes visible which two need to be layered together.

Read the table down its columns and one rule falls out. Every measure that looks at names goes limp against 「a name already inside the list」, and every measure that pins content goes limp against 「content that was malicious from the start」. That is the whole reason the two kinds have to be layered. Either one on its own leaves the opposite side wide open, and the gap is not a narrow one.

Worth adding: postponing updates is itself a choice with a price. The judgement about what to upgrade and when is covered in how to read release notes. Holding a version still is the safe side of this particular problem and the dangerous side of a different one, which is why it cannot be turned into a standing rule.

Auditing your own repository with reads only

From here on it is a procedure. Everything needed for a verdict comes out of reading. No installing, no deleting, no publishing.

The three things to read out of a lockfile

A single lockfile entry carries three things, and a verdict only stands when all three are read together. Which version did it freeze on, where is it fetched from, and what value verifies that what arrived is what was expected.

# The three things inside one package-lock.json entry
"node_modules/<name>": {
  "version":   "1.2.3",                        # which version it froze on
  "resolved":  "https://registry.example/...", # where it is fetched from
  "integrity": "sha512-..."                    # the value verifying what arrived
}

# Read the installed tree - nothing is modified
npm ls --all              # real names and versions across the whole tree
npm ls <name>             # where in the tree that name is attached
npm explain <name>        # who pulled it in, shown as a path

Counting references across the whole repository

Reading one lockfile only shows the state of the branch currently checked out. Surviving references are frequently somewhere else entirely, which is why the second pass widens to every ref.

# References left in the working tree
grep -rn '"<name>"' --include=package.json .
grep -rn '"<name>"' --include=package-lock.json .

# Unmerged branches and tags too - nothing is downloaded, only names are read
git grep -n '<name>' -- '*.json'
git grep -n '<name>' $(git for-each-ref --format='%(refname:short)' refs/heads)

# What stands in the registry slot - metadata only
npm view <name> --json    # nothing is installed. metadata is all this fetches
npm view <name> versions
StepWhat you doWhat decides itWhen to stop here
1Check whether the lockfile is committed to the repositoryThe file's existence and when it was last updatedWithout it everything after is meaningless. Committing a lockfile comes first
2Search the lockfile for that name stringWhether a matching entry existsAbsence is not the end. Go back through the tree for indirect dependencies

Not one of those eight steps changes any state. And the output of the procedure is not a verdict of 「safe」 but an inventory of the places where references survive. Once the inventory exists, the layer-by-layer decisions start: tags can be left alone while only the documentation is corrected, a proxy cache can be kept while new builds are blocked from reaching it. Those are different decisions and they deserve to be made separately.

In four sentences

Everything above compresses to four sentences.

  • Removal cuts the code and leaves the reference. Whatever happens at the registry, the one line in your lockfile stays exactly where it is.
  • On npm at least, a removed name is not empty. The documented procedure includes a step that plants a marker in that slot, which changes what a request to that name actually retrieves.
  • A weekly figure is a count of responses, not of people. It inflates through automated traffic and deflates through caches, so it cannot be carried straight over into an estimate of exposure.
  • Measures that look at names and measures that pin content leak in different places. Which is why they get layered rather than chosen between.

Translated into practice, one sentence survives. The cheapest thing available is to keep the lockfile committed and read the resolved addresses and integrity hashes inside it once. It comes before extending any name list, and the cost is not remotely comparable.

What could not be confirmed

The items below were not settled from primary sources within the research scope of this article. Nothing is asserted about them until the basis is in hand.

  • Whether a security marker is permanent — the npm public documentation goes as far as the step of publishing a placeholder on a malware finding. A sentence covering whether that placeholder is kept indefinitely, or under what conditions another party could take the name over, was not found in the policy documents. The body therefore treats 「the name is not left empty」 as the extent of what is established.
  • Which window the install figures in the list were counted over — the list document carries the column heading and no sentence naming a source. The tool's own documentation says it uses the npm download query and holds a six-hour cache, but that does not connect through to which period each value in the list covers, so it stays unsettled.
  • The primary source behind 19.7% and 43% — both figures are quoted by the repository that prompted this article. The underlying study's text and measurement conditions were outside this research scope and were not opened, so which models and which prompt set produced them remains unverified here.
  • Which week the headline's 35 belongs to against the document's 36 — the list is regenerated weekly and the document retains no history of earlier editions, so the two could not be reconciled. The body treats them as values from two different weeks.
  • How other language ecosystems handle it — removal and name handling policy for the Rust, Ruby and Go registries is not covered by the tool that prompted this and was not brought into scope. The comparison in this article is limited to the two registries named.
  • Which layer inside a given organisation actually generates the requests — this is not a question public documents can answer. It falls out only from that organisation's own proxy access records and build history, and the layer breakdown in the body is an order of investigation rather than an estimate of proportions.
