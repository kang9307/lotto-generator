JVMはコンテナの上限をどう見ているか - KubernetesのRequestとLimitがヒープ・GC・遅延を決める場所 2026

-Xmxをlimitと同じにするとなぜ死ぬのか、availableProcessorsひとつがGCスレッドと並列度まで決める経路

2026年9月2日 開発・インフラ

Podスペックに limits.memory: 1Gi と書けば、そのコンテナは実際にその線を越えられない。問題は中で動くJVMがその数字をどう読むかだ。JVMは上限を守るプログラムではなく、上限を見て自分の計画を立てるプログラムであり、計画が狂ったとき上限を守るのはカーネルである。カーネルが守るやり方はプロセスを殺すことだ。

CPU側はもっと静かに狂う。平均使用率は低いのにp99だけが跳ねる。その間JVMの中では、コレクタの選択とスレッドプールの大きさがPodスペックの数字ひとつに従って変わっている。

基準はJava 21の java man page、Java 25のGCチューニングガイド、OpenJDKのソースとバグデータベース、2026年9月時点のKubernetes公式文書だ。Linuxコンテナで直接実行して確認できなかったためコマンド出力は載せていない。本文の既定値と挙動はすべて上記の文書で確認したものである。

きっかけ - 上限を設けてもずれる場所

2026年9月初め、韓国の開発者コミュニティにKubernetes上のJava JVMのCPU・メモリRequestとLimitを扱った記事が紹介された。論旨はひとつだった。コンテナ内のJavaプロセスにはメモリの境界が二つある。ヒープの境界とコンテナの境界であり、この二つを同じものとして扱った瞬間に事故が起きる。

同じ構造がCPU側にもある。PodスペックのCPUの数字はスケジューラへの申告であると同時にJVMが自分の並列度を計算する入力でもあるのに、ダッシュボードには片方しか出てこない。コンテナがなぜ OOMKilled で終わったのかという一般的な診断は別記事に、障害中に管制画面が答えを出せない理由はあの記事にある。ここではJVM固有の問題だけを扱う。

JVMはもともとホストを見ていた

根はJVMが自分のヒープサイズを自分で決めるところにある。OracleのGCチューニングガイドが記す既定の選択はこうだ。初期ヒープは物理メモリの64分の1、最大ヒープは4分の1、コレクタはサーバークラスのマシンではG1、それ以外ではSerialである。サーバークラスの定義も注記されている。プロセッサ2個以上かつ物理メモリ1792MB以上のときだ。

ここで「物理メモリ」が問題になる。コンテナ認識がなかった頃のJVMにとって、それはホスト全体だった。64GBのノードにlimit 512MiのPodを載せると、中のJVMは最大ヒープを16GBとして計画した。計画が間違っているのでGCはまだ余裕があると見て回収を先送りし、その間にコンテナは512Miを超えてカーネルに殺される。

直された時点ははっきりしている。JDK 10リリースノートの JDK-8146115 の項目だ。JVMはコンテナ内で動いていることを認識するよう修正され、オペレーティングシステムに問う代わりにコンテナ固有の設定情報を取り出す。取り出すのは割り当てられたCPU数と総メモリである。Linuxでのみ動作し、既定で有効で、-XX:-UseContainerSupport で無効にできる。

  • 同じ変更で -XX:ActiveProcessorCount が追加された。リリースノートはこの値がJVMの他のすべてのCPU自動検出ロジックを上書きすると記す
  • 同じ箇所の JDK-8186248 で InitialRAMPercentage・MaxRAMPercentage・MinRAMPercentage が追加された。従来の Fraction 形式を置き換えるものだ
  • この項目はOracle JDK 8u191のリリースノートにも同じ内容で載っている。JDK 8系列も8u191以上ならコンテナ認識が入っている
  • 言い換えれば8u190以下とJDK 9にはない。そうしたイメージを使っているなら、昔ながらに -Xmx を手で打ち込むしかない

コンテナ認識が実際に読む値

メモリ側の経路は -XX:MaxRAM の文書にそのまま書かれている。既定値は「JVMプロセスが使える最大メモリまたは128GBのうち小さいほう」で、次の一文が肝心だ。その最大メモリとはマシンの物理メモリと環境(例えばコンテナ)が課した制約のうち小さいほうである。コンテナのmemory limitがここに入り、その上に比率のフラグが乗る。

CPU側のアルゴリズムはman pageではなくOpenJDKのソースコメントにある。cgroupSubsystem_linux.cpp の active_processor_count の説明は三行だ。sched_getaffinity で使えるCPU数を求める。quotaが指定されていればquotaをperiodで割る。そして除算の結果はすべて次の整数へ切り上げる。結果は活性プロセッサ数を超えない。

切り上げが実際には大きい。CPU limitが 500m なら0.5が上がって1、1500m なら2だ。1 CPU未満を与えてもJVMは最低1個として見る。逆に 2100m のような値は3になり、実際に使えるより多いスレッドを作らせる。

見落としやすいのはlimitがないときだ。quotaがなければ上のアルゴリズムはシステムの活性プロセッサ数をそのまま使う。96コアのノードに requests.cpu: 500m のPodだけを載せると、そのJVMは96コアの計画を立てる。

-Xmxではなく比率で与える理由

絶対値と比率の違いは好みではなく管理点の数だ。-Xmx2g はPodスペックとは別に生きている数字である。limitを3Giに上げてJVM引数を直さなければ増やしたメモリが遊び、1Giに下げて直さなければそのPodはデプロイ直後から死ぬ。比率で与えれば直す場所はひとつだ。

フラグ何を決めるかJava 21 man page基準の既定値注意
-XX:InitialRAMPercentage初期ヒープ1.5625パーセント起動直後のヒープが非常に小さい。増える間GCが頻繁に回る
-XX:MaxRAMPercentage最大ヒープ25パーセント指定しなければ1Giのコンテナで最大ヒープが約256Miになる
-XX:MinRAMPercentage小さいヒープでの最大ヒープ50パーセント最小値ではない。文書は「約125MB以下の小さいヒープ」に適用されると記す
-XX:MaxRAM上の比率の分母利用可能メモリと128GBのうち小さいほうここでの利用可能メモリがコンテナのlimitだ

既定値25パーセントが実務でいちばん多く事故を起こす。コンテナに4Giを与えたのにヒープは1Giしか取られず、残りの3Giは誰も使わない。「メモリを増やしたのになぜまだGCがひどいのか」の半分はここから出てくる。MaxRAMPercentageはコンテナでは事実上の必須指定項目だ。

名前の罠もひとつある。MinRAMPercentage は「最低何パーセントはヒープに与える」ではなく小さいヒープ区間での最大比率である。250Miのサイドカー Javaプロセスで MaxRAMPercentage だけを触って、なぜ効かないのかと言う場合がこれに当たる。

resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    memory: 1Gi          # 比率の分母になる値
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=70.0
      -XX:InitialRAMPercentage=70.0
      -XX:+ExitOnOutOfMemoryError

70という数字に根拠はない。公式文書のどこにも「ヒープはlimitの何パーセント」という推奨はない。きっかけになった記事は50から75の間で始めて検証せよと記しており、その程度が正直な表現だ。残りの分が何に使われるのかは次の節が説明する。

ヒープだけがメモリではない

この節ひとつだけ持ち帰ってもよい。-Xmx をコンテナのlimitと同じにすると、そのPodは必ず死ぬ。ヒープの外にもJVMが使うメモリがいくつもあり、それらは -Xmx に入らないままコンテナの使用量にはそのまま入るからだ。

領域何が決めるか公式文書上の既定値コンテナ使用量に含まれる
Javaヒープ-Xmx / MaxRAMPercentageMaxRAMの25パーセント含まれる
メタスペース-XX:MaxMetaspaceSizeサイズが制限されない含まれる
JITコードキャッシュ-XX:ReservedCodeCacheSize240MB、階層コンパイルを切ると48MB含まれる
スレッドスタック-Xss × スレッド数Linux x64はスレッドあたり1024KB含まれる
ダイレクトバッファ(NIO)-XX:MaxDirectMemorySize未指定ならJVMが自動で決める含まれる
GC内部構造・JVM自体・ネイティブライブラリフラグなし文書化された固定値なし含まれる

表で目を引くのはメタスペースが既定で無制限だという点だ。クラスを大量に作るフレームワークでこの値が増えると、ヒープは健全なのにコンテナだけが上限に達する。ただし予約と実際のコミットは別物だ。表の数字は上限であって常時の占有量ではない。

死に方が違う点のほうが重要だ。ヒープが足りなければJVMが OutOfMemoryError を投げ、スタックトレースとヒープダンプが残る。一方コンテナの上限を超えると、Kubernetesの文書の表現どおりmemory limitはカーネルのOOM killで強制される。例外もダンプもない。同じ文書は、この終了がカーネルがメモリ圧迫を検知したときにだけ起きるため上限を超えたコンテナがすぐには殺されない場合があると付け加える。同じコード、同じ負荷なのに死ぬ時点が違う理由だ。

ヒープの外がどこへ行ったのかを知るJVM内蔵の手段はネイティブメモリトラッキングだ。-XX:NativeMemoryTracking の既定値は off で、summary にすればサブシステム別の使用量を追跡する。

# ヒープ外メモリの内訳 (追跡を有効にして起動したプロセスでのみ有効)
jcmd 1 VM.native_memory summary

# JVMがコンテナをどう認識したかの最大ロギング
java -Xlog:os+container=trace -XX:MaxRAMPercentage=70 -version

# 最終的に確定したフラグ値の確認
java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|ActiveProcessorCount'

availableProcessorsひとつが決めるもの

Runtime.availableProcessors() のjavadocは短い。JVMが使用できるプロセッサ数を返し、この値は実行中に変わり得て、1より小さくならない。コンテナでこの値は前節の切り上げ計算の結果だ。この数字ひとつが以下を連鎖的に決める。

コレクタの選択とGCスレッド数

サーバークラス判定の条件がここに掛かる。プロセッサ2個未満またはメモリ1792MB未満ならサーバークラスではなく、既定のコレクタはG1ではなくSerialになる。CPU limitが 500m のコンテナはプロセッサ1個として計算されるので、この条件に掛かる。その状態でG1専用のチューニングフラグを付けても何も起きない。

サーバークラスを通過してもGCワーカー数はプロセッサ数に従う。ガイドは「最大GCスレッド数はヒープサイズと利用可能なCPU資源によって制限される」とだけ記し、算式は明かさない。それでも方向ははっきりしている。プロセッサを少なく見ればGCも遅く回る。

ActiveProcessorCountで上書きする

man pageがこのフラグの範囲を教えてくれる。「VMがガベージコレクションやForkJoinPoolのような作業に使うスレッドプールのサイズを計算するときに使うCPU数を上書きする」。「UseContainerSupport が有効でなくても尊重される」という但し書きと、複数のJavaプロセスをコンテナで動かすときCPU資源を分けるのに有用だという用途まで書かれている。

  • このフラグはJVMが見る値だけを変える。cgroupのquotaはそのままだ。1に下げてもコンテナは依然としてlimit分だけ使える
  • だから低く取ればGCワーカーと並列処理が減るのに、肝心のスロットリングは減らない。スロットリングの解決策ではない
  • 逆に高く取ればスレッドだけ増えてquotaはそのままなのでスロットリングが悪化する。「コアを増やしたことにする」は成り立たない
  • 正しく使える場所はひとつのPodにJavaプロセスが二つ以上あるときだ。それぞれがPod全体を自分のものとして計算するのを防ぐ

並列ストリームも同じ値に縛られる。ForkJoinPool のjavadocは、引数なしのコンストラクタが Runtime.availableProcessors() と同じ並列度でプールを作ると記し、共通プールの並列度は java.util.concurrent.ForkJoinPool.common.parallelism プロパティで指定できると案内する。CPU limitを変えることはアプリケーションコードの並列度を変えることでもある。

CPU Limitはなぜ遅延を作るのか

Kubernetes文書の一文が明確だ。cpu limitはCPUスロットリングで強制され、コンテナがlimitに近づくとカーネルがその分までCPUへのアクセスを制限する。カーネルが強制するハードリミットである。メモリのように「超えたら死ぬ」ではなく「超えようとすると止まる」だ。

止まる単位が肝心だ。kubeletは既定でCFS quotaによってPodのCPU limitを強制し、周期値を定めるオプション --cpu-cfs-quota-period の既定値は100ms である。スロットリングは秒単位で滑らかに起きるのではなく、100msの窓の中で割り当てを使い切ればその窓が終わるまで止まるという形で起きる。

ここで平均の罠が出る。CPU limitが1でスレッドが4個なら、100ms分が25msで尽き、残りの75msの間そのコンテナのすべてのスレッドが止まる。1秒で平均すれば使用率は100パーセント未満なのでグラフは穏やかだ。その1秒の中に最大75msの停止が何度も入っているのにそうなる。平均使用率が低いのにp99だけ跳ねる現象の正体はたいていこれだ。

GCと重なるともっと悪くなる。stop-the-worldの区間で割り当てが尽きるとGCスレッドも一緒に止まり、次の周期が開かないと再開しない。短かったはずの停止が周期の境界まで伸びる。GCログの停止時間とスロットリング指標を並べて見なければならない理由だ。

CPU limitを設定するか、しないか

この話題は結論が割れる。双方が別のものを最適化していて、双方に文書で裏づけられる根拠がある。並べて置くほうが正確だ。

設定しない側根拠設定する側根拠
スロットリングが実際の遅延を作るカーネルが強制するハードリミットで周期の既定値が100msだGuaranteed QoSの条件だすべてのコンテナのCPU limitがrequestと等しくなければならない
CPUが足りなくてもPodは死なない退避シグナルはメモリ・ファイルシステム・pidだけでCPUがない退避順で後ろに回る退避はBestEffort、Burstable、Guaranteedの順だ
ノードが空いていれば余りを使える資源が余ればrequest以上を使うことが許されるCPU固定を使うには必須だstaticポリシーの専用CPUはGuaranteed Podかつ整数requestにだけ割り当てられる
requestだけでも配置は決まるrequestはスケジューラが配置を決めるのに使われる隣人の遅延が予測可能になる文書上の根拠ではなく運用方針に近い理由だ

まとめると遅延が重要な少数のサービスと密度が重要な多数のバッチ作業が違う答えを出す。前者はスロットリングを避けるためlimitを外すか大きく取り、後者は予測可能性と退避順位のために設定する。判断基準は好みではなく指標だ。スロットリング指標が実際に上がっているかをまず見る。

ひとつはっきり区別しなければならない。メモリlimitを外すことはCPU limitを外すことと同じ性質の決定ではない。CPUは足りなければ遅くなるだけだが、メモリは圧縮されない。メモリlimitがなければそのPodはノード全体を危険にさらし、JVMはノードのメモリを基準にヒープを計画する。

RequestとLimitは別の仕事をする

Kubernetes文書の定義は短い。requestを指定するとkube-schedulerがその情報でPodをどのノードに置くかを決める。limitを指定するとkubeletがそれを強制して実行中のコンテナがそれ以上使えないようにする。ひとつは配置段階の数字、もうひとつは実行段階の数字だ。

JVMの観点で決定的なのはJVMがrequestを見ないという点だ。MaxRAM が参照するのは「環境が課した制約」、すなわちcgroupのlimitである。requestだけ大きく取ってlimitを空けたPodは、スケジューラの目には余裕をもって配置されたPodなのに、中のJVMはありもしないメモリを前提に動く。

QoSクラス条件退避順JVMの観点での意味
GuaranteedすべてのコンテナがCPU・メモリのlimitとrequestを持ち、二つの値が等しい最も遅く退避されるヒープ比率の分母が確定的だ。ずれる余地が最も少ない
BurstableGuaranteedの条件を満たさず、コンテナのどれかにrequestかlimitがあるBestEffortの次limitがあればそれが分母。なければノードのメモリが分母だ
BestEffortどのコンテナにもCPU・メモリのrequestとlimitがない最も先に退避されるJVMがノード全体を自分のものとして計算する。Javaには事実上禁止

文書が付け加える条件も知っておく価値がある。資源圧迫による退避のとき候補になるのはrequestを超えて使っているPodだ。requestを現実的に取っておくことが単なる書類作業ではない理由である。

JITウォームアップがreadinessを崩す場所

HotSpotは既定でC1とC2を併用する階層コンパイラで起動する。コンパイル自体がCPUを使う。だからJavaアプリケーションのCPU使用量は起動直後が最も高く定常状態で下がる。ところがCPU limitはたいてい定常状態を基準に取られる。最もCPUが必要な区間が最も強くスロットリングされる。

次は決まった手順だ。起動が遅れるとreadiness probeが失敗し、文書の表現どおりkubeletがコンテナを準備できていないと表示すると、エンドポイントコントローラがそのPodのIPを一致するすべてのサービスエンドポイントから取り除く。ここまでは正常動作だ。問題はliveness probeまで同じ閾値で設定した場合である。livenessが失敗すると再起動ポリシーに従ってコンテナが死に、再び起動して同じ区間をまた通る。再起動ループができる。

公式の処方はstartup probeだ。文書はこのプローブが起動の遅いコンテナを保護し、通常のliveness・readinessに影響を与えずに起動専用の成功基準を定義できるようにすると記す。推奨の形まで案内する。livenessと同じ検査を使いつつ失敗閾値だけ高く取ることだ。liveness自体を緩めれば本当の故障を捕まえられなくなる。

  • 起動区間だけCPUを多く与えることは標準のrequest・limitだけではできない。startup probeで時間を稼ぐか、limitを上げる方向に行く
  • limitを上げたくないなら、クラスデータ共有や事前コンパイルのような起動最適化が次の選択肢だ。その効果はこの記事では確認していない
  • 起動が遅くて最初の要求が遅いことと、スロットリングのせいで常時p99が高いことは別の問題だ。起動区間と定常区間を分けて見なければ混ざる

何を見て決めるのか

最もよくある間違いは数字ひとつで決めることだ。ヒープ使用量のグラフひとつでlimitを決めたり、CPU使用率ひとつでスロットリングの有無を判断したりする。以下の五つは別のことを言っている。

  • GC直後のヒープ使用量 — ヒープサイズ算定の根拠だ。鋸歯グラフの頂点は「必要な大きさ」ではなく「回収直前のゴミ込みの大きさ」である
  • コミット済みヒープ — JVMが実際に確保した大きさ。コレクタによっては使わない部分をオペレーティングシステムに返すこともある
  • プロセスRSS — 物理メモリに載っている量。ここからヒープを引けばヒープ外がどれくらいか大まかに見える
  • コンテナのメモリ使用量 — cgroupが見る値でOOM判断の基準だ。ページキャッシュが混ざる
  • CPUスロットリング指標 — 使用率ではなくスロットリングされた周期数と時間を見る。使用率はスロットリングを隠す

順序は単純だ。limitを決め、比率でヒープを与え、実際のトラフィックで上の五つを一緒に見て、戻って直す。特に合成負荷だけではヒープ外のメモリがよく現れない。クラスローディングとコードキャッシュは実際のコード経路が多様に踏まれてこそ増える。

よくある失敗の五つ

同じ失敗が繰り返される理由は、症状が原因から遠く離れて現れるからだ。

失敗実際に起きること症状何を見るか
limitをまったく設定していないJVMがノードのメモリとノードのCPU数で計画するノードが圧迫を受け、無関係なPodが退避されるQoSクラスとノードの退避イベント
-Xmx をlimitと同じにしたヒープ外の分が0になる例外なしの OOMKilled、ダンプもないRSSとヒープの差、ネイティブメモリトラッキング
requestだけあってlimitがないBurstableになり、JVMはノード基準で計画する配置は余裕なのに実行中に死ぬrequestとlimitを並べて確認
CPU limitが低すぎるプロセッサ1個と計算されサーバークラス判定に届かないGC停止が長くなりチューニングフラグが効かない選ばれたコレクタ、GC停止時間、スロットリング指標
複数コンテナのPodで合算を忘れたサイドカーが同じ上限を分け合うサイドカーを入れてから死ぬようになるPod内すべてのコンテナのrequest・limit合計

四つ目には逆方向の罠もある。-XX:ActiveProcessorCount でプロセッサ数だけ上げて取ると、コレクタの選択は変わるがquotaはそのままだ。スレッドが増えた分だけスロットリングが悪化する。コレクタを変えたいならプロセッサ数を偽る代わりに -XX:+UseG1GC のように直接指定するほうが正直だ。

どのバージョンを基準にした話か

この領域はバージョンによって挙動が実際に違う。古い記事をそのまま持ち込んで適用してずれる代表的な場所なので、基準を明かしておく。

  • JDK 8u190以下とJDK 9 — コンテナ認識がない。ホスト基準でヒープとプロセッサ数を決めるので、-Xmx を手で打ち込むしかない
  • JDK 8u191以上とJDK 10以上 — UseContainerSupport が既定で有効で、RAMPercentageの三つのフラグと ActiveProcessorCount が使える
  • JDK 19 — OpenJDKのバグ JDK-8281181「Do not use CPU Shares to compute active processor count」がこのバージョンに入った。それ以前はquotaがないときcpu sharesでプロセッサ数を計算しており、Kubernetesでcpu sharesはCPU requestから来る。古いJDKではrequestがJVMの並列度に影響したという意味だ
  • 本文のフラグ既定値 — Java 21の java man page基準だ。コレクタの選択とサーバークラス判定はJava 25のGCチューニングガイド基準である
  • Kubernetes側 — 2026年9月時点の公式文書だ。cgroup v1とv2の違いは扱っていない

三つ目が特に厄介だ。ランタイムを上げながらCPU設定をそのままにしたのに並列度が変わることが起こり得る。フラグをそのままにすること自体が変更であり得るという意味だ。

まとめ

骨格は一文だ。Podスペックの数字はコンテナを制約する値であると同時に、JVMが自分の計画を立てる入力である。メモリlimitはヒープ比率の分母になり、CPU limitはプロセッサ数になってコレクタの選択とスレッドプールの大きさを決める。

実務的に残るのは三つだ。-Xmx をlimitと同じにしない。ヒープ外の分を残さなければカーネルが静かに殺す。比率で与える。管理する数字がひとつに減り、既定値25パーセントはたいてい小さすぎる。CPU limitは遅延予算と一緒に決める。100msの周期の中の停止は秒単位の平均に現れない。そしてどの比率も他人が決めてはくれない。ヒープ外のメモリはフレームワークとスレッド数によってサービスごとに違う。測って決め、ランタイムを上げるたびに見直す。

確認できなかったこと

  • Linuxコンテナで直接実行して検証していない。本文のコマンドは文書に基づいて書いたもので、実行出力はひとつも載せていない
  • ForkJoinPool 共通プールの既定並列度の算式はjavadocにない。引数なしのコンストラクタが availableProcessors() と同じであることだけを確認した
  • -XX:ParallelGCThreads と -XX:ConcGCThreads の既定の算式もman pageにない。ガイドは「ヒープサイズと利用可能なCPU資源によって制限される」とだけ記す
  • JDK-8281181 のバックポートの有無は確認できなかった。バグデータベースに記録された修正バージョンは19ひとつだった
  • cgroup v1とv2の違いが上の計算に及ぼす影響は扱っていない。ファイル名と単位が異なる
  • Podの資源を再起動なしで変える機能と、その際JVMが値を読み直すかどうかは確認範囲の外だ
  • 起動最適化の技法がスロットリング区間でどれだけ役に立つかは測定していない
