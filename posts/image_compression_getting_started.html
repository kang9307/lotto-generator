이미지 파일 용량을 결정하는 세 가지 축

이미지 파일의 크기는 저장 공간 문제에 그치지 않고 웹 페이지가 뜨는 속도와 전송량에 직접 영향을 준다. web.dev 의 Learn Images 과정은 이미지가 웹에서 전체 전송 용량과 요청 수 모두에서 가장 큰 자산이라고 설명하며, 2022년 6월 기준 웹 페이지 전송 용량의 중앙값이 약 2MB이고 이미지가 그중 절반에 가깝다고 적는다.

용량을 줄이는 수단은 서로 독립된 세 가지로 나뉜다. 첫째는 해상도를 줄여 픽셀 수 자체를 줄이는 것이고, 둘째는 손실 압축의 품질 값을 조절해 저장하는 정보량을 줄이는 것이며, 셋째는 압축 방식이 다른 파일 형식으로 바꾸는 것이다. 세 가지는 서로 배타적이지 않아 함께 쓸 수 있다. 「계산」이라고 표시한 부분은 공식 문서의 서술이 아니라 단순 산술이고, 「web.dev 서술」「MDN 서술」처럼 출처를 적은 부분만 문서의 문장이다.

방법 동작 원리 용량에 미치는 영향 주의점 근거 문서
해상도 축소 가로·세로 픽셀 수를 줄인다 화소 수가 줄어든다. 가로·세로를 절반으로 줄이면 화소 수는 4분의 1이다(계산). 용량은 압축 후 이미지 내용에 따라 달라진다 과도하게 줄이면 선명도가 떨어지고, 다시 키워도 세부는 돌아오지 않는다 Apple 지원(미리보기), Microsoft 그림판 도움말, web.dev
품질 값 조절 손실 압축에서 눈에 덜 띄는 정보를 더 많이 버린다 값이 낮을수록 파일이 작아진다. 줄어드는 폭은 이미지 내용에 따라 달라진다 너무 낮추면 압축 흔적이 눈에 띈다. 같은 값도 도구마다 다르게 해석된다 web.dev(JPEG·WebP 문서)
포맷 변환 JPEG, PNG, WebP 등 압축 방식이 다른 형식으로 바꾼다 web.dev 서술: 같은 사진이 JPEG 로는 수백 KB, PNG 로는 수 MB 일 수 있다 투명도 지원 여부와 브라우저 지원 범위를 따져야 한다 MDN(이미지 형식 가이드), web.dev

무엇을 먼저 쓸지는 이미지가 쓰일 최종 환경에 달려 있다. web.dev 는 이미지를 화면에 더 빨리 보여 주는 유일한 방법이 전송 크기를 줄이는 것이라고 서술한다. 세 수단 가운데 해상도 축소는 픽셀 수 자체를 바꾸므로 나머지 둘의 출발 조건이 되고, 품질 값과 형식은 같은 픽셀을 어떻게 적느냐를 바꾼다.

해상도 조절 — 픽셀 수를 줄여 파일 크기를 줄이는 원리

해상도는 이미지를 이루는 가로와 세로 픽셀의 개수다. web.dev 는 래스터 이미지를 격자의 칸마다 색을 지정하는 지시문의 묶음으로 설명한다. 칸의 수가 줄면 설명할 칸이 줄어드는 셈이다. 가로 4000픽셀, 세로 3000픽셀인 사진의 칸은 1200만 개이고(계산), 가로와 세로를 각각 절반으로 줄이면 칸은 300만 개, 곧 4분의 1이 된다(계산). 다만 압축된 형식에서 파일 용량은 이미지 내용에 따라 달라지므로, 화소 수가 줄어든 비율이 곧 용량이 줄어든 비율은 아니다.

  • Apple 지원 문서는 미리보기에서 이미지 크기를 바꿀 때 너비와 높이에 새 값을 넣거나 팝업 메뉴에서 「퍼센트」를 고를 수 있다고 안내한다. 원본 비율을 지키려면 「비율을 유지하여 크기 조절」을 선택하며, 그러면 너비나 높이 하나를 바꿀 때 나머지가 따라서 바뀐다.
  • 같은 문서의 「이미지 파일 크기 줄이기」 절차는 [도구] > [크기 조절]을 고르고 「이미지 리샘플」을 선택한 뒤 해상도 필드에 더 작은 값을 넣는 것이다. 새 크기가 대화상자 하단에 나타난다. 반대로 「이미지 리샘플」을 해제하면 세부사항을 잃지 않고 크기 값만 바뀐다고 안내한다.
  • web.dev 는 래스터 이미지를 원래 크기보다 크게 늘리면 왜곡되거나 블록처럼 보이거나 흐려진다고 설명한다. 줄이기 전의 큰 원본이 나중에 필요할 수 있으므로 원본은 따로 두는 편이 안전하다. web.dev PNG 문서도 편집을 다시 하거나 다른 형식으로 저장할 때를 대비해 원본(canonical) 버전을 로컬이나 저장소에 보관하는 방식을 소개한다.
  • web.dev 는 이미지를 표시될 크기에 맞춰 제공하는 반응형 이미지를 Learn Images 과정의 별도 주제로 다룬다. 해상도 조절은 이 반응형 이미지의 출발점, 곧 필요한 크기보다 큰 이미지를 내려받게 하지 않는 일과 이어진다.

Apple 지원 문서는 이미지 크기 조절의 목적을 「파일 크기를 줄여 디스크 용량을 절약하거나 이미지를 더 빠르게 다운로드할 수도 있다」고 소개한다. 대화상자 하단에 새 크기가 바로 표시되므로 값을 바꿔 가며 결과 크기를 가늠할 수 있다.

압축 방식과 품질 값 — 손실 압축과 무손실 압축의 차이

web.dev 는 무손실 압축을 같은 정보를 더 적은 바이트로 적는 방식으로 설명한다. 「1행 1열부터 3열까지 파랑」처럼 반복을 묶어 적는 런 렝스 인코딩이 그 비유로 나온다. 시각 정보는 그대로이므로 화질은 변하지 않는다. 손실 압축은 사람이 지각하는 세부 수준과 전송하는 데이터량 사이의 균형을 찾는 일이며, 그 균형은 원본 이미지의 내용이 정한다고 web.dev 는 서술한다. MDN 은 손실 압축은 이미지 데이터를 버려 훨씬 작은 파일을 얻는 방식이고 무손실은 원본을 정확히 재현하는 방식이라고 정리한다.

  • 품질 값: web.dev 는 JPEG 의 복잡한 내부 사항이 0에서 100 사이의 정수 하나인 「quality」 설정으로 드러난다고 설명한다. 0은 가장 작은 파일과 가장 나쁜 화질이고, 올라갈수록 화질과 파일 크기가 함께 커진다. 이 설정은 주관적이어서 도구마다 같은 75를 같게 해석하지 않으며, 지각되는 품질도 이미지 내용에 따라 달라진다.
  • JPEG 의 구조: web.dev 는 JPEG 가 픽셀 하나하나가 아니라 8x8 픽셀 블록을 단위로 이미지를 기술한다고 설명한다. 이산 코사인 변환으로 이미지를 밝기(luma)와 색(chroma) 성분으로 나누고, 사람 눈이 색 차이보다 밝기 차이에 더 민감하다는 점을 이용해 색 성분을 더 많이 줄인다. 색 성분을 낮은 해상도로 저장하는 서브샘플링도 그 방법이다.
  • 과하게 압축했을 때: web.dev 는 JPEG 압축을 지나치게 하면 사람의 지각이 무시하던 수준을 넘어서 세부가 사라진 것이 드러나고, JPEG 가 블록 단위로 작동하므로 블록 사이의 이음매가 보이기 시작한다고 서술한다. 같은 문서의 Squoosh 예시에서는 품질을 60으로 둔 사진이 79% 줄었다. 이는 그 사진과 그 도구에서의 결과이며 일반 수치가 아니다.
  • 점진적(progressive) JPEG: web.dev 는 점진적 JPEG 가 흐릿한 전체 이미지를 먼저 보여 주고 점점 선명해지게 한다고 설명한다. 아주 작은 이미지를 제외하면 기본(baseline) JPEG 보다 파일이 조금 더 작은 경우가 많지만 디코딩은 조금 더 복잡해진다고 덧붙인다.

web.dev 는 품질 눈금 대부분의 구간에서 화질 차이를 사람 눈으로 가려내기 어렵다고도 서술한다. 그러니 품질 값은 낮출수록 좋은 값이 아니라, 이미지 내용에 따라 달라지는 균형점을 찾는 값이다. 그 지점 아래로 내려가면 앞서 본 블록 이음매와 세부 손실이 먼저 눈에 띄기 시작한다.

포맷 변환 — JPEG, PNG, WebP의 특성과 선택 기준

MDN 의 이미지 형식 가이드는 형식을 고르는 기준으로 압축 방식, 화질, 브라우저 지원의 폭과 깊이, 투명도나 애니메이션 같은 기능의 필요 여부를 든다. 같은 문서는 스크린샷, 도표, 로고, 선화처럼 글자와 날카로운 경계가 있는 이미지에는 무손실 인코딩을 선호하라고 하고, 사진 같은 연속 톤 이미지는 버려진 세부가 잘 보이지 않아 대체로 손실 압축을 견딘다고 서술한다.

JPEG — 사진에 맞는 손실 압축

MDN 은 JPEG 가 정지 이미지에 쓰는 손실 압축 형식 중 가장 널리 쓰이며 특히 사진에 유용하다고 설명한다. 이산 코사인 변환에 기반한 손실 압축이고, 알파 채널(투명도)을 지원하지 않는다. 같은 문서는 도표나 차트처럼 선명함이 필요한 내용에 손실 압축을 적용하면 만족스럽지 않은 결과가 나올 수 있다고 경고한다. 최대 크기는 65,535×65,535 픽셀이다. 더 정밀한 재현이 필요하면 PNG 를, 더 나은 재현과 높은 압축이 모두 필요하면 WebP 나 AVIF 를 택하라는 것이 MDN 의 안내다.

PNG — 투명도와 도표에 맞는 무손실 압축

MDN 은 PNG 가 무손실 압축을 쓰며 완전한 알파 투명도를 지원하고, 원본을 더 정밀하게 재현해야 하거나 투명도가 필요할 때 JPEG 보다 낫다고 설명한다. web.dev 는 PNG 가 화질 저하를 일으키지 않지만 현대적인 형식에 비해 파일이 거의 언제나 지나치게 크므로 사진에는 거의 맞지 않는다고 서술한다. 그림자가 있는 로고처럼 반투명이 필요한 단순한 그림이라면 고려할 수 있으나, 반투명을 지원하는 WebP 와 신중히 비교하라고 한다. 같은 사진이 JPEG 로는 수백 킬로바이트이고 PNG 로는 수 메가바이트일 수 있다는 서술도 web.dev 의 래스터 이미지 문서에 있다. PNG 는 나중에 다시 편집할 원본 버전을 보관하는 용도로는 합리적이라고도 한다.

WebP — 손실·무손실·투명도를 모두 다루는 형식

MDN 은 WebP 가 VP8 비디오 코덱에 기반한 손실 압축과 반복 데이터를 치환하는 무손실 압축을 모두 지원하며, 투명도와 애니메이션도 다룬다고 설명한다. 같은 문서의 서술로는 손실 WebP 이미지는 시각적으로 비슷한 압축 수준의 JPEG 보다 평균 25~35% 작고, 무손실 WebP 이미지는 같은 이미지의 PNG 보다 일반적으로 26% 작다. 최대 크기는 16,383×16,383 픽셀이다. WebP 는 주요 브라우저 최신 버전에서 폭넓게 지원되지만 오래된 환경에는 JPEG 나 PNG 폴백을 두라는 것이 MDN 의 안내이고, macOS 의 Safari 에서는 Safari 14 이상과 macOS Big Sur(11) 이상이 모두 필요하다는 주의도 붙어 있다.

MDN 은 AVIF 도 소개한다. 손실 AVIF 가 JPEG 보다 약 50% 작은 예가 있다고 적으면서도, 점진적 렌더링을 지원하지 않아 파일을 모두 받아야 표시되고 파일이 클수록 영향이 커질 수 있다고 알린다. AVIF 사용 시에는 picture 요소로 폴백을 두라는 안내가 있다. web.dev 는 AVIF 지원이 Chrome 과 Opera 에서 2020년, Firefox 에서 2021년, Safari 에서 2022년에 시작됐다고 적는다. 문서들의 공통된 방향은 사진은 JPEG 나 WebP, 반투명이 필요한 도표나 로고는 PNG 나 WebP 를 검토하되 브라우저와 환경의 지원 범위를 함께 따지는 것이다.

Windows 기본 도구로 줄이기 — 그림판과 사진 앱

Microsoft 의 그림판 도움말은 그림판이 간단한 이미지 자르기, 크기 조정, 그리기, 도형과 텍스트 추가에 적합하다고 소개한다. 같은 문서의 영문 안내에서 크기 조정은 Home 탭의 Resize 옵션이며, 새 크기를 픽셀 또는 원본 대비 백분율로 지정할 수 있다. 우리말 메뉴에서는 「크기 조정 및 기울이기」로 보이는 기능이다. 아래는 Windows 11 기준 문서가 안내하는 범위다.

  • 그림판의 해상도 줄이기: 이미지를 그림판으로 열고 크기 조정 기능에서 단위를 백분율 또는 픽셀로 골라 값을 입력한다. 예컨대 백분율 50을 넣으면 가로와 세로가 절반이 되고 화소 수는 4분의 1이 된다(계산).
  • 그림판의 크기 조정 옵션: Home 탭의 Resize 에서 새 크기를 픽셀 또는 원본 대비 백분율로 정한다. 픽셀로 정하면 결과 해상도를 정확히 맞출 수 있고, 백분율로 정하면 원본 대비 비율만 지정하면 된다.
  • 사진 앱의 범위: Microsoft 의 사진 앱 편집 문서는 자르기, 뒤집기, 회전, 조명과 색 조정, 그리기 같은 기능을 안내한다. 이 문서가 다루는 편집은 이미지의 모양과 색을 고치는 작업이다.
  • Office 문서의 이미지: Office 프로그램에 삽입된 그림의 용량은 해당 프로그램의 그림 압축 기능이 따로 다루며, 이미지 파일 자체를 줄이는 위 방법과는 작업 대상이 다르다.

Windows 에서 해상도를 줄이는 방법으로 문서가 안내하는 것은 그림판의 크기 조정 기능이다. 사진 앱은 자르기와 회전, 색 조정처럼 이미지의 모양과 색을 고치는 편집 기능이 중심이다.

macOS 기본 도구로 줄이기 — 미리보기의 크기 조절과 내보내기

Apple 지원의 미리보기 사용 설명서는 이미지 크기 조절과 파일 형식 변환을 모두 다룬다. 크기 조절 문서(prvw2015)에서 확인한 내용은 다음과 같다.

  • 크기 바꾸기: 이미지를 미리보기로 열고 [도구] > [크기 조절]을 고른다. 너비와 높이에 새 값을 입력하거나 「다음에 맞게 크기 조절」 팝업 메뉴에서 크기를 고른다. 「다음에 맞게 크기 조절」에서 크기를 고르면 비율을 지키기 위해 너비나 높이가 선택한 크기보다 작아질 수 있다고 안내한다.
  • 용량 줄이기: [도구] > [크기 조절]에서 「이미지 리샘플」을 선택하고 해상도 필드에 더 작은 값을 입력하면 새 크기가 하단에 나타난다. 단위는 퍼센트로 바꿀 수 있고, 비율은 「비율을 유지하여 크기 조절」로 고정한다.
  • 세부사항 유지: 세부사항을 잃지 않고 크기를 더 작게 조절하려면 너비나 높이를 바꾸기 전에 「이미지 리샘플」을 해제하라고 안내한다.
  • 내보내기와 형식: [파일] > [내보내기]에서 이름과 위치를 정한 뒤 포맷 팝업 메뉴에서 이미지 형식(예: PNG)을 고른다. 시작 페이지는 미리보기가 지원하는 형식을 HEIC, JPEG, JPEG 2000, OpenEXR, PDF, PNG, TIFF 로 안내한다.

여러 이미지를 한 번에 줄이려면 같은 윈도우에 이미지를 띄우고 사이드바에서 선택한 뒤 [도구] > [크기 조절]을 고르라는 것이 Apple 문서의 설명이다. 내보내기에서는 이름과 위치를 정하고 형식을 고르는 것까지가 문서의 안내 범위이며, 형식은 시작 페이지가 열거한 목록 안에서 고른다.

용도별 판단 기준 — 메일 첨부, 웹 게시, 문서 삽입, 증빙 제출

MDN 과 web.dev 는 용도별로 몇 픽셀, 몇 퍼센트로 맞추라는 숫자 대신 형식과 전송 크기를 따지는 판단 기준을 제시한다. 이 절은 그 기준을 용도별로 묶어 정리한다. 수치 기준이 필요하면 수신 서비스나 제출처가 안내하는 사양이 우선이다. 메일·웹·문서·증빙은 각각 먼저 따질 대상이 서비스 한도, 표시 크기, 이미지 종류, 접수 사양으로 갈린다.

  • 메일 첨부: 한도는 메일 서비스와 받는 쪽 설정마다 달라 서비스 안내가 기준이다. 한도를 넘으면 앞서 본 세 가지 수단 중 해상도 축소를 먼저 쓰고, 그래도 크면 품질 값을 조절한다.
  • 웹 게시: web.dev 는 이미지가 웹에서 가장 큰 자산이므로 최적화가 가장 큰 성능 개선일 수 있다고 서술한다. MDN 은 래스터 이미지에 WebP 나 AVIF 를 권하고, 지원하지 않는 브라우저를 위해 picture 요소로 PNG 나 JPEG 폴백을 제공하라고 안내한다.
  • 문서 삽입: MDN 의 구분을 빌리면 도표와 스크린샷은 무손실, 사진은 손실 압축이 맞다. 삽입 후 문서 전체의 크기는 프로그램의 그림 처리 방식에 따라 달라진다.
  • 증빙 제출: 접수 시스템이 형식과 용량을 정해 두었다면 그것이 우선이다. 글자와 직인이 뭉개지지 않는 선에서만 손실 압축을 쓰고, 용량이 부족하면 품질을 낮추는 대신 해상도를 줄이는 쪽부터 시도하는 순서를 고려한다.

메타데이터와 위치 정보 — 공유 전에 확인할 것

이미지 용량을 줄이는 작업과 별개로, 공유하기 전에 살펴볼 것이 있다. Apple 지원 문서는 사진이 GPS 정보를 포함하면 미리보기에서 [도구] > [위치 정보 보기]를 선택해 세계 지도와 거리 지도에서 사진이 찍힌 위치를 볼 수 있다고 안내한다. 메뉴가 회색으로 나타나면 그 이미지에 위치 정보가 없다는 뜻이라고도 설명한다. 이 회색 메뉴는 위치 정보 유무를 가르는 신호다.

  • 위치 정보의 존재: 위 Apple 문서에 따르면 사진 파일은 촬영 위치의 GPS 정보를 담을 수 있다. 공개 게시판이나 중고 거래 같은 곳에 올릴 사진이라면 올리기 전에 이런 정보가 있는지 확인하는 것이 안전하다.
  • 확인 방법: macOS 에서는 앞서 본 [도구] > [위치 정보 보기]가 활성화되는지로 확인할 수 있다. 메뉴가 회색이면 그 이미지에는 위치 정보가 없다.
  • 도구의 처리 방식: Squoosh 의 GitHub README 는 이미지를 서버로 보내지 않고 모든 압축을 로컬에서 처리한다고 밝힌다. 같은 문서는 방문자 기본 정보, 압축 전후 이미지 크기 값, PWA 설치 정보를 Google Analytics 로 수집한다고 함께 적는다.
  • 변환 후 메타데이터: 위치 정보는 사진 파일 안에 담긴 값이므로, 크기 조절이나 형식 변환을 거친 파일도 같은 메뉴가 활성화되는지 보면 남아 있는지 알 수 있다.

공유용 사본은 별도 파일로 만들고 위치 정보가 담긴 원본은 따로 보관하면, 원본이 밖으로 나가는 일을 피할 수 있다.

확인하지 못한 것

  • Windows 11 사진 앱의 이미지 크기 조정 메뉴 이름과 위치, 품질 슬라이더와 권장 값, 그림판의 가로 세로 비율 유지 체크박스 정확한 이름, 그림판에서 JPEG 로 저장하는 절차. Microsoft 문서에 해당 서술이 없다.
  • macOS 미리보기 내보내기 화면의 품질 슬라이더, 알파 체크박스, 예상 파일 크기 표시. Apple 페이지에는 내보내기 형식 목록과 [파일] > [내보내기] 경로만 있었다.
  • 메일, 웹, 문서, 증빙 제출별 권장 해상도·품질 값과 메일 서비스의 첨부 한도. 공식 기준이 없어 상황별로 정해야 한다.
  • 해상도를 절반으로 줄이거나 품질 값을 바꿨을 때 파일 용량이 실제로 몇 퍼센트 줄어드는지에 대한 일반 수치. 이미지 내용마다 달라 문서가 말하지 않는다.
  • 크기 조절·변환 후 위치 정보 같은 메타데이터가 남는지, 메신저와 사진 앱이 이를 지우는지, Office 의 자동 압축이 어떻게 동작하는지.
