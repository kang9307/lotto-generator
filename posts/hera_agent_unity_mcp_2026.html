2026-06-16 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: AI는 게임 엔진을 모른 채 코드를 쓴다

AI 코딩 에이전트에게 Unity 작업을 시키면 묘한 일이 벌어진다. 모델은 자신만만하게 코드를 써 내려가지만, 그 코드는 당신의 프로젝트가 아니라 모델이 기억하는 어떤 Unity를 향한다. 학습 시점의 옛 API, 컨텍스트에 없는 씬 구조, 실제로는 설치되지 않은 패키지를 그럴듯하게 가정한다. 게임 엔진은 버전마다 API가 바뀌고 씬·컴포넌트 상태가 런타임에 결정되므로, 이 추측은 곧장 컴파일 에러나 미묘하게 어긋난 동작으로 이어진다.

2026년 6월 기준, 이 문제를 정면으로 겨눈 도구가 GeekNews 등에서 주목을 받았다. hera-agent-unity다. 원문 저장소의 표현을 30자 이내로 빌리면 "추측은 비싸고, 측정이 명령이다(Guessing is expensive. Measurement is the command)"라는 한 문장이 이 도구의 철학을 압축한다. 이 글은 저장소 README나 GeekNews 토론을 옮기는 대신, 이 도구가 제시하는 설계상의 선택이 무엇을 뜻하는지, 그리고 게임 개발에서 AI 에이전트를 실제로 쓰려는 사람에게 어떤 실무 시사점이 있는지를 본인 관점에서 풀어 본다.

먼저 단서를 분명히 한다. 여기 나오는 도구 사양은 공개된 저장소 문서와 GeekNews 소개를 기준으로 한 것이며, 본인이 직접 모든 명령을 프로덕션에서 장기 검증한 결과는 아니다. 따라서 "무엇을 주장하는가"와 "그것이 왜 합리적인가/어디서 흔들릴 수 있는가"를 구분해 서술한다.

1. 문제의 정체 - 환각이 아니라 컨텍스트 결핍

흔히 AI가 틀린 코드를 쓰면 "환각(hallucination)"이라 부른다. 하지만 Unity 같은 환경에서 더 정확한 진단은 컨텍스트 결핍이다.

1.1 모델은 무엇을 모르는가

대형 언어 모델이 잘못된 API 호출을 지어내는 이유는, 진짜 API를 알 만큼 충분한 예시를 보지 못했기 때문이다. 게임 개발에서는 이 문제가 특히 심하다. Unity API는 버전마다 바뀌고, 같은 기능도 메이저 업데이트에서 시그니처가 달라진다. 모델이 학습한 시점과 당신이 쓰는 버전이 어긋나면, 모델은 "그 시절의 Unity"에 맞는 코드를 쓴다. 더 근본적으로, 어떤 씬이 열려 있고 어떤 GameObject에 어떤 컴포넌트가 붙어 있는지는 프로젝트의 런타임 상태이지 일반 지식이 아니다. 모델은 이를 알 길이 없으므로 가정한다.

1.2 컨텍스트는 잘려 있고 오차는 누적된다

대부분의 코드베이스는 컨텍스트 윈도에 다 들어가지 않는다. 그래서 에이전트는 코드의 일부만, 종종 오해를 부르는 단면만 본다. 그 위에서 발생한 작은 오차들은 에이전트의 긴 실행 시간 동안 복리처럼 쌓이고, 끝에 가서는 그 실수가 코드에 박힌다. Unity처럼 "씬 상태 → 컴포넌트 → 코드"가 서로 얽힌 환경에서는 한 군데 잘못된 가정이 연쇄적으로 번진다.

1.3 해법의 방향 - 질의 가능하게 만들기

해결의 핵심은 분명하다. 에이전트가 프로젝트를 추측하지 않고 질의하게 만드는 것이다. 어떤 씬이 활성인지, 어떤 GameObject가 존재하는지, 어떤 컴포넌트가 붙어 있는지, 어떤 패키지가 설치됐는지를 직접 물어볼 수 있으면 환각이 줄고 토큰도 절약된다. 모델이 "참이라고 가정"하는 대신 "참인지 확인"하기 때문이다. hera-agent-unity가 하려는 일이 바로 이것이다.

2. hera-agent-unity란 - 단일 바이너리로 Unity를 운전하기

이 도구의 구조는 의도적으로 미니멀하다. 한 줄로 요약하면, AI 에이전트가 살아있는 Unity 에디터를 CLI로 제어하게 해주는 다리다.

2.1 핵심 구성

클라이언트 쪽은 단일 Go 바이너리, Unity 쪽은 C# UPM 패키지 하나다. 둘은 로컬 HTTP로 통신한다. Unity를 열면 커넥터가 자동으로 기동해 localhost의 한 포트(문서 기준 8090 이상)에서 대기한다. 저장소 문서의 표현을 빌리면 "Go CLI 하나, C# UPM 패키지 하나, 런타임 의존성 0, MIT"가 전부다. Python도, WebSocket 릴레이도, 상주 미들웨어 프로세스도, JSON-RPC 데몬도 없다.

2.2 무엇을 할 수 있나

제공 명령은 폭이 넓다. 본인이 정리한 주요 범주는 다음과 같다.

  • 에디터·런타임: 플레이/일시정지/리프레시, 임의의 C# 실행, 콘솔 접근
  • 씬·게임오브젝트: 씬 로드, 오브젝트 생성/삭제, 컴포넌트 관리, 이름·태그·레이어·컴포넌트로 필터
  • 에셋·머티리얼: 머티리얼 생성, 셰이더 점검, 임포트 설정 관리
  • 패키지: Unity 패키지 나열·추가·제거·임베드(도메인 리로드를 가로지르는 비동기 작업 추적 포함)
  • uGUI·UI: 살아있는 UI 계층을 JSON 중간표현(IR)으로 내보내고, IR로 UI를 빌드하고, 렌더링해 레퍼런스 이미지와 시각 비교
  • 인트로스펙션: 타입 설명, 어셈블리 전역 메서드 검색, 오프라인 Unity 문서 조회
  • 배치·프로파일러: JSON으로 여러 단계 명령을 묶어 CI 자동화, 프레임 계층 읽기

2.3 측정을 명령으로

철학은 일관된다. AI가 플레이 모드 결과를 가정하기 전에 도구가 실제로 플레이 모드에 들어가 기다린다. 당신의 Unity 버전에 어떤 API가 있다고 가정하기 전에 살아있는 어셈블리를 리플렉션으로 들여다본다. UI 앵커 수치를 추측하기 전에 빌드된 결과를 레퍼런스 이미지와 비교해 보정한다. 추측을 측정으로 대체하는 이 루프가 도구의 정체성이다.

3. MCP와의 비교 - 무엇을 버리고 무엇을 얻나

이 도구를 이해하는 가장 좋은 방법은 같은 목적의 표준 접근인 MCP(Model Context Protocol)와 나란히 두는 것이다.

3.1 Unity와 MCP의 현재

2026년 기준 Unity 생태계에는 이미 여러 MCP 서버가 존재한다. Unity가 공식 Assistant 패키지에서 MCP 통합을 제공하고, CoplayDev/unity-mcp, CoderGamester/mcp-unity 같은 커뮤니티 구현이 Claude·Cursor·Codex 등과 에디터를 잇는다. 발상은 같다. Unity를 MCP 뒤에 두면 에이전트는 프로젝트를 환각하지 않고 질의할 수 있다. 어떤 씬이 활성인지, 어떤 오브젝트·컴포넌트·패키지가 있는지를 물어 환각을 줄이고 토큰을 아낀다. hera-agent-unity와 목적은 동일하다.

3.2 다른 것은 전달 방식이다

차이는 "어떻게 그 컨텍스트를 전달하느냐"에 있다. MCP 서버는 대개 Python 런타임, FastMCP류 프레임워크, 상주 프로세스나 릴레이, 클라이언트별 설정 파일을 요구한다. hera-agent-unity는 이 미들웨어 층을 통째로 없애고 단일 바이너리와 상태 없는 HTTP만 남긴다. 본인이 읽은 대조표는 다음과 같다(공개 문서 기준).

항목hera-agent-unity (CLI)일반 Unity MCP

호출 주체셸을 쓰는 어떤 에이전트·스크립트주로 MCP 클라이언트
도메인 리로드파일시스템 버스로 무상태 처리재연결 로직 필요

3.3 무상태가 푸는 까다로운 문제

주목할 설계 하나는 도메인 리로드 내성이다. Unity는 스크립트를 다시 컴파일할 때 도메인을 리로드하며, 이때 HTTP 서버 같은 메모리 상태가 통째로 날아간다. MCP 방식은 이 순간 연결이 끊겨 재연결 로직이 복잡해진다. hera-agent-unity는 하트비트 파일과 결과 파일 같은 파일시스템 기반 프로세스 간 버스로 이 문제를 우회한다. 서버가 파괴돼도 파일은 살아남고, 에디터 초기화 훅이 감시자를 다시 붙인다. 상태를 메모리가 아니라 파일에 두는 선택이 컴파일마다 죽고 살아나는 Unity 에디터의 생리와 잘 맞물린다. 본인은 이것을 이 도구에서 가장 영리한 부분으로 본다.

4. 측정 기반 UI - ui_doc 파이프라인

AI가 가장 자주 헛다리를 짚는 영역이 UI다. 앵커, 피벗, 색상, 간격은 코드만 봐서는 결과를 알 수 없다. hera-agent-unity의 ui_doc 파이프라인은 이 지점을 측정으로 정면 돌파한다.

4.1 추측을 없애는 루프

흐름은 이렇다. 살아있는 UI를 JSON 중간표현으로 내보내고(export), 그 IR을 부모 아래에 적용해(apply) 빌드하고, PNG로 렌더링(capture)하고, 레퍼런스 이미지에서 실제 16진 색상을 샘플링(sample)하고, 외부 의존 없이 절차적 스프라이트를 생성(gen_sprite)한다. 에이전트는 실제 프로젝트 구조 위에 디자인을 세우고, 자기가 빌드한 것을 그대로 렌더링하고, 목표 이미지와 차이를 비교해 스스로 보정한다.

4.2 왜 중요한가

이 루프의 의미는 "AI가 만든 UI를 사람이 매번 눈으로 확인하고 고쳐주는" 작업을 에이전트의 자기 교정 루프로 바꾼다는 데 있다. 스크린샷이 놓치는 오버레이 캔버스까지 렌더링하고, 색상을 추측이 아니라 측정된 픽셀값에서 가져온다. 게임 UI처럼 픽셀 단위 정확도가 중요한 영역에서, "보고 고친다"를 코드 호출 한 번으로 만든 점은 실용적이다. 다만 시각 비교의 품질은 레퍼런스 이미지와 비교 알고리즘에 좌우되므로, 만능은 아니라는 점도 함께 적어 둔다.

5. 토큰 경제와 커스텀 도구

에이전트 도구의 실용성은 결국 비용으로 수렴한다. 두 가지 설계 선택이 눈에 띈다.

5.1 응답을 가볍게

공개 문서의 스모크 테스트 기준, 호출당 평균 약 26토큰 수준이며 비용의 88%는 응답이 아니라 에이전트가 작성한 코드에서 나온다고 한다. 이는 도구가 장황한 응답으로 컨텍스트를 잡아먹지 않도록 설계됐음을 시사한다. 에이전트 루프에서 도구 응답이 비대하면 매 스텝 컨텍스트가 오염되고 비용이 불어나므로, 응답을 콤팩트하게 유지하는 것은 합리적 우선순위다. (이 수치는 벤더가 제시한 것이므로 본인 워크로드에서 직접 재 보는 것이 안전하다.)

5.2 코드 한 줄로 도구 확장

또 하나는 확장성이다. [HeraTool] 어트리뷰트를 붙인 C# 클래스는 자동으로 발견돼 호출 가능해진다. 코드 생성도, 별도 등록도 필요 없다. 프로젝트마다 고유한 워크플로를 가진 게임 개발에서, 팀이 자기 도구를 즉석에서 추가할 수 있다는 점은 도구의 수명을 늘린다. 표준 명령만으로는 닿지 않는 사내 파이프라인을 에이전트에게 노출하는 통로가 되기 때문이다.

6. 실제 사례 - AI가 운전한 인디 게임

도구의 신뢰도를 보는 한 가지 단서는 만든 사람이 그것으로 무엇을 만들었느냐다. 저장소에 따르면 저자는 NoMoreRolls라는 솔로 인디 게임을 주로 이 도구로 개발했다고 밝힌다. 3티어 아키텍처와 다수의 전투 시스템을 갖춘 프로젝트에서, AI 에이전트가 블라인드 코드 생성이 아니라 살아있는 에디터를 직접 운전했다는 것이다. 씬 구성, 컴포넌트 와이어링, 플레이 모드 반복이 그 예다.

본인 해석은 이렇다. 이 사례의 가치는 "AI가 게임을 만들었다"는 마케팅이 아니라, 측정 기반 루프가 인디 규모에서 실제로 굴러갔다는 증거에 있다. 인디·소규모 개발은 거버넌스보다 마찰 없는 속도가 중요하고, 단일 개발자가 에이전트와 빠르게 반복하는 환경이다. CLI 기반 무의존성 접근이 이 결을 정확히 노린다.

7. 한계와 주의점

장점만 적는 것은 정직하지 않다. CLI 접근이 MCP를 모든 면에서 이기는 것은 아니다.

7.1 표준화와 거버넌스의 공백

MCP는 단지 전송 방식이 아니라 표준화된 도구 디스커버리·권한 모델·생태계 호환을 함께 제공한다. 2026년 Unity는 연결성·권한·기업 안전을 사후가 아니라 설계 단계에서 다루는 공식 AI Gateway를 내놓는 흐름이다. 다중 클라이언트 승인, 감사, 조직 단위 통제가 중요한 팀이라면 직접 CLI 호출보다 표준 경로가 안전하다. hera-agent-unity의 단순함은 동시에 이런 거버넌스 장치의 부재를 뜻한다.

7.2 임의 C# 실행의 양면성

임의의 C#을 실행할 수 있다는 것은 강력하지만 동시에 권한 경계가 넓다는 뜻이다. 에이전트가 에디터에서 무엇이든 실행할 수 있다면, 잘못된 명령 하나가 프로젝트 상태를 망가뜨릴 수 있다. 버전 관리와 백업, 그리고 위험한 작업 전 사람의 확인 같은 안전장치를 운영 측에서 직접 마련해야 한다. 표준 권한 모델이 없는 만큼 책임이 사용자에게 더 실린다.

7.3 검증의 한계

이 글의 기술 묘사는 공개 문서와 소개 기준이다. 토큰 수치, 도메인 리로드 내성, 시각 비교 정확도 같은 주장은 방향을 시사하지만, 당신의 프로젝트·Unity 버전·에이전트 조합에서의 신뢰성은 직접 확인해야 한다. 신생 오픈소스인 만큼 생태계 성숙도와 장기 유지보수도 미지수다.

8. 결론 - 게임 개발 AI에 주는 시사점

hera-agent-unity가 던지는 메시지는 도구 하나를 넘어선다. 2026년 6월 기준 AI 코딩 에이전트의 진짜 병목은 모델의 지능이 아니라 모델이 보는 현실의 정확도라는 점을 또렷이 보여준다. 게임 엔진처럼 상태가 런타임에 결정되는 환경일수록, 에이전트에게 "추측하지 말고 측정하라"고 강제하는 통로가 결과 품질을 가른다.

본인이 정리한 실무 시사점 셋이다.

8.1 에이전트에게 측정 통로를 줘라

Unity든 다른 환경이든, AI 에이전트를 붙일 때 가장 먼저 할 일은 모델이 프로젝트의 실제 상태를 질의할 수 있게 하는 것이다. MCP든 CLI든 수단은 부차적이다. 핵심은 환각을 줄이는 측정 경로의 유무다. 이것이 없으면 더 똑똑한 모델도 옛 Unity를 향해 코드를 쓴다.

8.2 워크로드로 MCP와 CLI를 가려 써라

단일 개발자나 소규모 인디라면, 마찰 없는 무의존성 CLI 접근이 빠른 반복에 유리하다. 반대로 다중 클라이언트·권한 관리·감사가 중요한 팀이라면 표준 MCP나 공식 게이트웨이가 안전하다. 정답은 단일 방식이 아니라 워크로드별 배치다. 둘은 경쟁이라기보다 다른 마찰 구간을 겨냥한 선택지다.

8.3 자동화에 안전장치를 함께 설계하라

에이전트가 에디터를 직접 운전할수록 잘못된 한 수의 파급도 커진다. 버전 관리, 자주 커밋, 위험 작업 전 확인, 배치 자동화의 드라이런 같은 안전장치를 도구 도입과 같은 무게로 설계해야 한다. 측정 기반 접근이 정확도를 높여 주더라도, 권한 경계는 여전히 사람의 몫이다. 관련 흐름은 Claude Code 동적 워크플로 분석과 함께 보면 입체적이다.
