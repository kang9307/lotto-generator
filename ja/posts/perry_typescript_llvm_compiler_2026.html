Perry - TypeScriptをLLVM機械語へ直接コンパイルするネイティブコンパイラ

トランスパイルもJITもなしに、TypeScriptを直接ネイティブバイナリへ

2026年6月9日 IT・技術

はじめに: TypeScriptは本当に「遅い言語」だったのか

TypeScriptで書いたCLIツールを配布したことがあれば、ある不便さを覚えているはずです。たった一行の挨拶を出力するプログラムでさえ、数十MBのNode.jsランタイムを携える必要があり、プロセスが立ち上がった瞬間にV8エンジンが目覚めてコードを解釈し最適化し始めます。私たちが「TypeScriptは遅い」と言うとき、実際に遅いのは型システムではなく実行モデルです。型はコンパイルが終われば消え、残ったJavaScriptは巨大な仮想マシンの上でもう一度解釈されます。

2026年6月、GeekNews(news.hada.io)で話題になったPerryは、この前提を真っ向から覆します。PerryはTypeScriptをJavaScriptへトランスパイルもせず、V8のような重いJITランタイムにも載せず、LLVMを通じて直接ネイティブ機械語へコンパイルします。プロジェクトの紹介によればPerryはRustで書かれ、パースにSWC、コード生成にLLVMを用い、Node.js・Electron・ブラウザエンジンなしで動く単一実行ファイルを生み出します。本稿ではその仕組みと、なぜそれが技術的に興味深いのかを丁寧に解きほぐします。

1. 従来のTypeScript実行の三段構造

Perryが何を解くのかを理解するには、まず「これまでどう実行してきたか」を正確に描く必要があります。従来のTypeScript実行はおおよそ三段階を踏みます。

TypeScriptソース (.ts)
   │   (1) 型検査 + トランスパイル (tsc / swc / esbuild)
   ▼
JavaScriptソース (.js)   ← 型情報はここで全て消える
   │   (2) パース + バイトコード生成 (V8 / JavaScriptCore)
   ▼
バイトコードインタプリタ実行
   │   (3) ホットコード検出 → JITコンパイル → 機械語
   ▼
ネイティブ機械語 (実行中にようやく生成)

ここで二つのコストが生じます。第一に型情報の喪失です。(1)の段階でTypeScriptの静的型は検証だけに使われ、出力JavaScriptからは完全に消えます。その結果、(2)(3)のエンジンはすべての値を「型の分からない動的な値」と仮定して出発せざるを得ません。第二にJITのウォームアップです。V8は最初インタプリタで遅く実行し、頻繁に回るコードを実行時に観測してから初めて機械語にコンパイルします。起動は遅く、速くなるまで時間がかかり、その過程自体がメモリとCPUを食います。

このモデルはブラウザのように「コードを事前に知り得ない」環境では合理的です。しかし、私たちが自分で書いて配布するCLIやサーバーは、実行前にコードが全て決まっています。ならば、わざわざ最適化を実行時まで先延ばしにする理由があるでしょうか。まさにこの問いがAOTコンパイルの出発点です。

2. AOT vs JIT - 最適化の時点を移す

JIT(Just-In-Time)とAOT(Ahead-Of-Time)の違いは一文に凝縮されます。いつ機械語を作るかです。

区分 JIT (V8/Node.js) AOT (Perry)
機械語生成の時点 実行中 (ランタイム) 実行前 (ビルド時)
起動速度 ウォームアップ必要、遅い 即時 (0msに近い)
ランタイム依存 エンジン+ランタイム必要 単一バイナリ、依存なし
最適化の情報源 実行中に観測した型 コンパイル時の静的型
動的コード(eval) 自然に対応 構造的に困難

JITの強みは「実際にどの型が流れるかを見て」最適化する点にあります。逆にAOTは実行を見られない代わりに、コンパイル速度を気にする必要がありません。ビルドは一度きり、実行は無数に繰り返されるので、C++やRustがするように重い静的解析と積極的な最適化を存分に適用できます。Perryが狙うのはまさにここです。TypeScriptはすでに豊かな静的型を持つのだから、それを捨てずにコンパイル時最適化の燃料にしよう、というわけです。

JITは「実行しながら型を突き止める」。AOTは「型はもう分かっているから先に最適化する」。TypeScriptのように型が明示された言語では、後者は自然な選択肢だ。

3. LLVMとは何で、なぜ使うのか

Perryのコード生成バックエンドはLLVMです。LLVMを一文で言えば、多くの言語のフロントエンドと多くのCPUのバックエンドの間に挟まり、強力な最適化を担う業界標準のコンパイラ基盤です。Clang(C/C++)、Rust、Swiftはすべてその上で動きます。

LLVMの核心はLLVM IRという中間表現です。言語フロントエンド(Perryの場合はTypeScript)はソースをLLVM IRへ落とし込む(lower)だけでよく、その先のインライン化・定数伝播・ループのベクトル化・デッドコード除去といった数十の最適化パスと、x86・ARM・WebAssemblyなど多様なターゲットへの機械語生成はLLVMが引き受けます。新しい言語を作るとき、最適化器とコード生成器を一から書く必要がなく、実証されたバックエンドに乗れるのです。

興味深いことに、Perryは最初からLLVMを使っていたわけではありません。プロジェクトのブログによれば、当初はCranelift(WebAssembly陣営で主に使われる高速な単一ティアコンパイラ)をバックエンドにしていましたが、LLVMへ移りました。理由は二つ。第一に、Craneliftは意図的に「速くコンパイルする」単一ティアの最適化器であり、これは実行性能が最優先のAOTコンパイラには誤ったトレードオフだということ。第二に、Apple Watch向けのarm64_32のように、LLVMはターゲット対応の幅が広いことです。

要点
LLVMを選んだのは「遅くても、より深く最適化する」側を選んだということです。ビルドが少し遅くなる代償に、実行ファイルはC・Rustが享受する水準の最適化を受けます。

4. Perryのコンパイルパイプライン

Perryが.tsファイルを実行ファイルへ変える過程を、プロジェクトの説明に基づき整理すると次のようになります。

TypeScriptソース
   │   SWCでパース → AST
   ▼
AST → HIR(高水準IR)へ落とす + 型推論
   │   IR変換・最適化パス
   ▼
LLVM IR生成 (codegen)
   │   LLVM最適化 + ターゲット機械語生成
   ▼
ランタイムライブラリとリンク → 単一ネイティブ実行ファイル

各段階を見ましょう。SWCはRust製の超高速なTypeScript/JavaScriptパーサで、Perryはこれをフロントエンドとして用い、ソースを抽象構文木(AST)にします。続いてASTを高水準中間表現(HIR)へ落としつつ型を推論し、いくつかの変換パスを経てLLVM IRを生成します。最後にPerryがネイティブ実装したランタイムライブラリとリンクし、依存のない一つのバイナリを取り出します。プロジェクトの紹介によれば「hello world」程度の出力は数百KB規模、標準ライブラリを多用するアプリは数十MBにまで膨らみます。

5. 型情報を活かした最適化

Perryの真の妙味は「型を捨てない」点から生まれます。一般的なJavaScriptエンジンが実行時に苦労して推論しなければならない情報を、TypeScriptはコンパイル時にすでに教えてくれます。Perryはその情報で次のような最適化を行うと紹介されています。

  • NaN-boxing: 数値をポインタやボックス化なしで表現する手法で、数値演算のオーバーヘッドを減らします。
  • インラインオブジェクト割り当て: オブジェクトをbumpアロケータでインライン割り当てし、メモリアクセスのコストを下げます。
  • i32ループカウンタ: 整数値で回るループでは一般の浮動小数ではなく32ビット整数カウンタを使い、ループを高速化します。
  • shapeキャッシュのオブジェクト: オブジェクトの形状をキャッシュし、動的探索なしにフィールドへ直接アクセスします。
  • fast-mathフラグ: 浮動小数演算にfast-mathを許し、ループのベクトル化の余地を広げます。

これらの共通点は、すべて「値の型を知っている」という前提の上でのみ可能だということです。JavaScriptエンジンはx + yが整数加算なのか文字列連結なのか実行してみるまで確信できませんが、TypeScriptでx: numberと宣言されていれば、コンパイラは直ちに整数/浮動小数の命令へ落とせます。静的型がそのまま最適化情報になるわけです。

こうした「型を活かしたコンパイル最適化」の発想は、システム言語の可逆圧縮やメモリ割り当ての設計とも通じます。圧縮がデータの構造を知るほど縮められるように、コンパイラも値の構造を知るほど縮められます。この文脈は別記事Rustで書き直したZstandardとmimalloc高性能アロケータでより深く扱います。

6.「LLVMへ移したら70倍遅くなった」という逆説

Perryのバックエンド移行期には教訓的な逸話があります。プロジェクトのブログによれば、CraneliftからLLVMへ最初に切り替えたとき、一部のベンチマークはむしろ70倍遅くなりました。より強力なバックエンドへ移したのに、なぜ遅くなったのでしょうか。

原因は「境界」でした。初期のLLVM版はほとんどの演算を不透明なランタイムヘルパー関数呼び出しで処理し、LLVMから見るとその呼び出しの内側は覗けないブラックボックスでした。関数境界をまたぐ最適化(インライン化、定数伝播)が塞がれるため、最適化器がいくら強力でもやることがなかったのです。Perryチームは、ホットパスを意図的にインライン化して境界を取り払う作業を経て初めて、LLVMの真価を引き出せたと説明します。

強力な最適化器を付けるだけでは速くならない。最適化器が「見えるように」コードを展開して初めて、その力が発揮される。これはあらゆるコンパイラ設計の一般原理だ。

7. では、どれだけ速くなるのか - ベンチマークの文脈

最適化を終えたPerryは意味のある性能向上を報告します。プロジェクトが公開したあるリリースのベンチマークでは、Node.js比で次の結果が引用されます。

  • 再帰の階乗: 約24.6倍速い
  • メソッド呼び出し: 約11倍速い
  • ループのオーバーヘッド: 約4.4倍速い
  • 数値集約的な処理: 約3.5倍速い

ただしこれらの数値は慎重に読むべきです。上の項目は多くが型が明確で反復の多いマイクロベンチマークで、AOTと静的型が最も有利な領域です。実際のアプリはI/O待ち、メモリ割り当て、ライブラリ呼び出しが入り混じるため、体感差は小さくなり得ます。またV8は長年磨かれた世界最高水準のJITで、動的なパターンが多いコードでは依然として強力です。「Perryが常にN倍速い」ではなく、「静的型とAOTが有利なワークロードで大きく差が出る」と理解する方が正確です。

8. 既存の試み - Perryは最初ではない

TypeScript/JavaScriptをネイティブやWebAssemblyへコンパイルしようとする試みはPerryが最初ではありません。系譜を理解するとPerryの立ち位置が鮮明になります。

8.1 AssemblyScript

AssemblyScriptはTypeScriptの部分集合(subset)をWebAssemblyへコンパイルします。構文はTypeScriptに似ますが、実際には別の言語に近く、任意のTypeScriptを受け付けず、明示的な整数型など独自の規則に従う必要があります。バックエンドはLLVMではなくBinaryen(WebAssemblyツールチェーン)です。「型を厳しく制限してネイティブに近づける」アプローチです。

8.2 Static Hermes

Meta(Facebook)のStatic HermesはReact Native向けHermesエンジンの次世代版で、TypeScript/Flowの型注釈が付いた「健全に型付けされた」JavaScriptを、ビルド時にネイティブへAOTコンパイルすることを目指します。静的型でJITの推測を減らし、より速く小さい成果物を狙います。ただし公開資料ではTypeScript対応は実験的で不完全と明記されています。Perryと哲学(型でAOT)が最も近いものの、Static HermesはReact Nativeという明確な舞台を持ちます。

8.3 Porffor

Oliver Medhurstが作るPorfforは、JavaScript/TypeScriptをAOTでWebAssemblyとネイティブバイナリへコンパイルする実験的エンジンです。インタプリタをバンドルする代わりにコード自体をコンパイルするため、紹介によれば成果物は既存の「JS→Wasm」比でずっと小さく(バイナリが最大1000倍小さくなった例を引用)、速いとされます。PorfforはTypeScriptだけでなくJavaScript全般の標準適合性(Test262)を追求する広い目標を持ちます。

プロジェクト 入力 バックエンド 主ターゲット
Perry TypeScript LLVM ネイティブバイナリ
AssemblyScript TS部分集合 Binaryen WebAssembly
Static Hermes 型付きJS/TS 独自+LLVM系 ネイティブ(RN)
Porffor JS/TS 独自→Wasm/ネイティブ Wasm・ネイティブ

Perryの差別点は「普通に書いたTypeScriptを受け取り、LLVMで直接ネイティブ実行ファイルを作る」直接性と、Rustで再実装した標準ライブラリ・パッケージを併せて提供する点にあります。

9. 標準ライブラリとnpm互換の現実

ネイティブコンパイラで最も厄介なのは言語ではなくエコシステムです。TypeScriptの力は数十万のnpmパッケージから生まれますが、その多くはNode.jsランタイムAPI(fs, http, netなど)を前提とします。PerryはV8/Nodeを携えないため、これらのAPIを自前で再実装しなければなりません。

プロジェクトの紹介によれば、PerryはRust製の高性能な標準ライブラリを備え、console・fs・path・process・JSON・Math・Date・crypto・Buffer・Map/Set・worker_threadsなどをネイティブで提供します。さらにfastify・axios・PostgreSQL・MySQL・Redis・bcrypt・JWTといった人気パッケージのドロップイン実装も多数含むとされます。つまり「どんなnpmパッケージでもそのまま動く」のではなく、Perryがネイティブで再実装した範囲内で動くモデルです。

// 紹介に基づく概念例: 別ランタイムなしで単一バイナリにビルドされるHTTPサーバー
import { createServer } from "http";

const server = createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "text/plain" });
  res.end("Hello from a native TypeScript binary");
});

server.listen(8080, () => {
  console.log("listening on :8080"); // Node.jsなしで実行されるバイナリ
});

10. 限界 - 動的機能とエコシステムの壁

バランスのため限界を明確に押さえます。AOTネイティブコンパイルは無料ではなく、JavaScriptの最も動的な部分と本質的に衝突します。

  • 動的評価: 文字列を実行時にコードとして実行するevalやnew Functionは、「実行前に全コードをコンパイルする」というAOTの前提と真っ向から衝突します。静的コンパイラが扱うのが最も難しい領域です。
  • 未対応機能: プロジェクトの文書ではデコレータは現在未対応と明記されています。標準の広大な隅々が段階的に埋められている途上です。
  • エコシステム互換: ネイティブランタイムAPIに依存しないか、Perryが再実装したパッケージのみ動きます。深いnpm依存ツリーを持つ既存の大型アプリをそのまま移すのは困難です。
  • 成熟度: 紹介ベースでバージョンは0.5.x台、活発に開発中の初期段階です。本番への全面導入より、適したワークロードでの検証が先です。

要するにPerryは「すべてのTypeScriptアプリのNode.js代替」ではなく、「特定のワークロードでTypeScriptをシステム言語のように使わせてくれる道具」と見る方が正確です。

11. どこに向いているか - 活用シナリオ

ではPerryの強みが輝くのはどこでしょうか。AOT・単一バイナリ・即時起動という性格をそのまま辿れば答えが出ます。

  • CLIツール: ランタイム依存のない単一バイナリは配布が単純で起動が即時です。ユーザーはNodeを入れる必要がありません。
  • サーバーレス・エッジ: コールドスタートがコスト・遅延に直結する環境で、ウォームアップなしの即時起動は明確な利点です。
  • 組込み・制約環境: 小さなバイナリと低いメモリ使用は、資源の乏しいデバイスに有利です。
  • 性能に敏感なワークロード: 型が明確で数値演算の多い処理で、ネイティブに近い性能を狙えます。

これは「GoからRustへ」のようなシステム言語選択の議論とも重なります。より速い実行と小さなバイナリ、予測可能な性能を求めるとき、どの言語/ツールチェーンを選ぶかという問題だからです。この文脈はGoからRustへの移行ガイドでさらに続きます。

12. 結論 - TypeScriptの「第二の人生」

Perryが投げかけるメッセージは明快です。TypeScriptの型は単なる開発の便利機能ではなく、コンパイラが使える最適化情報だということです。トランスパイルで型を消し、重いJITの上で再び推論させる代わりに、その型をLLVMへそのまま渡してネイティブ機械語へ落とせば、TypeScriptはシステム言語に近い性能と配布の手軽さを得られます。

もちろんPerryはまだ初期段階で、動的機能と巨大なnpmエコシステムという手強い壁が残ります。すべてのアプリが明日すぐネイティブにコンパイルされるわけではありません。しかしStatic Hermes、Porffor、AssemblyScriptと並んでPerryが描く大きな絵は鮮明です。「ブラウザで生まれた動的言語」というJavaScript/TypeScriptのアイデンティティが、AOTコンパイルという新しい道を通じて「システム領域にも踏み込める言語」へと拡張されつつある、ということです。TypeScriptを好んで使う開発者なら、この流れは見守る価値があります。
