Seeing Network Traffic

The capture method decides which questions you can ask - full capture, sampling, and the gateway API fork in the road

Jul 30, 2026 Tech & IT

Introduction: more dashboards, but are we noticing faster?

Traffic visualisation tools surface every few months, and they are consumed the same way each time. The screen looks good, someone spins it up, and within a week nobody opens it. That cycle repeats not because the tools are bad, but because they get attached without anyone checking which question the screen is built to answer.

This article asks one thing. What does seeing network traffic actually solve? The short answer is that visualisation solves nothing. The capture method solves it. The screen merely displays what was already decided beneath it, and information absent from the input will not emerge from any chart.

Let me fix the yardstick first. Throughout this piece, the value of observation is measured only by which questions it can answer. Aesthetic polish is not value. And every technical statement here is bounded by what I verified on 30 July 2026 in the IPFIX specification, the sFlow specification, the official tcpdump manual, the relevant TLS RFCs, and the project repository in question. Where I could not verify something, I say so in the body rather than inventing it.

One more disclosure. Every address and domain in this article is reserved for documentation use. Addresses come from 192.0.2.0/24 and the only domain used is example.com. No specific organisation's network layout is used as material here.

1. Settled first: the tool that got attention does not capture packets

The starting point was neko-master, whose public repository is github.com/foru17/neko-master, released under the MIT licence. And the crucial fact is not the screen but the input.

Here is what reading the repository documentation established. This project does not capture packets. It uses neither pcap, nor eBPF, nor NetFlow. Instead it receives data from the control APIs of proxy gateway software. For the Clash and Mihomo family it performs real time collection over WebSocket; for Surge it polls the HTTP remote API. Storage is SQLite by default, with ClickHouse as an option for larger datasets. The implementation pairs a Next.js, React and Recharts front end with a Node.js, Fastify and WebSocket back end.

Consequently the unit this tool handles is not the packet but the connection. The features stated in the repository are traffic distribution and connection counts per node, traffic, associated IPs and connection counts per domain, and ASN, geolocation and associated domains per IP. On privacy it states that all data is collected from the user's own network environment, and the documentation lists no separate root or CAP_NET_RAW requirement. As a service that calls gateway APIs, it structurally does not need those privileges.

That paragraph sets the direction for everything that follows. If the input is a connection list, the output is confined to the nature of connections. Laid out plainly:

  • Questions it answers well - which domain consumed how much yesterday, how much flowed through which node, which ASN an IP belongs to, whether any domain's connection count suddenly spiked.
  • Questions it cannot answer in principle - what the TCP retransmission rate is, which segment saw round trip latency grow, whether a forty millisecond burst occurred, what broke in the third packet.
  • Why not - that information is not in the input. The gateway hands over connection level aggregates, and packet header sequence numbers or timestamps are not part of those aggregates.
  • Is that a defect - no, it is a design decision. Because it does not capture packets, it needs fewer privileges and stores far less. It simply gave up a class of questions in exchange for not paying that price.
  • Maturity - the repository carried no experimental labelling, and container based deployment and a change history were in place. That said, this article did not independently verify operational stability.

For the record, this article does not cover installing or configuring a proxy gateway. The subject of interest is the nature of the data such a gateway hands out.

2. The line between visible and knowable

Arguments about visualisation slide into matters of taste. The way to stop that is to make the yardstick a question rather than a number. Three questions should be asked of any screen.

  1. Can you write, in one sentence, the question this screen answers? If you cannot, the screen is decoration.
  2. Is the information needed to answer that question actually present in the input? If not, the chart is drawing something that is not there.
  3. Which decision does that answer change? If no decision changes, there is no reason to notice either.

Of the three, the second is the core of this article. The first and the third are general problems of visualisation, already covered in what it means to make a database visible, so I will not repeat them. That piece dealt with internal database state; this one deals with network traffic. Networks carry one problem databases do not: you must choose physically where to read values, and that choice already splits what can and cannot be seen.

Query a statistics view in a database and you get values for the whole instance. Networks do not work that way. Where you stand determines what you see. Which is why, in network observation, choosing the point comes before choosing the tool.

4. What the word flow actually means in the spec

Flow is the most loosely used word in this field, so start with the specification. In the terminology section of RFC 7011, the IPFIX protocol specification, a Flow is defined as a set of packets or frames passing an Observation Point in the network during a certain time interval, and it states that all packets belonging to a particular Flow have a set of common properties.

Three words in that definition decide everything.

  • Observation Point - the same spec defines it as a location in the network where packets can be observed, giving as examples a line to which a probe is attached, a shared medium such as an Ethernet based LAN, a single port of a router, and a set of physical or logical interfaces of a router. A flow is therefore dependent on the point. Traffic that never crossed the point is traffic that does not exist.
  • Time interval - a flow is a creature of an interval, not an instant. The moment you fix the interval, the distribution inside it is erased.
  • Set - a collection, not individual packets. What gets exported is a record summarising that collection.

A more consequential sentence follows. The same section states that the set of packets represented by a Flow may be empty, and that since sampling is a Packet Treatment, this definition includes packets selected by a sampling mechanism. On the Metering Process it says the process consists of a set of functions that includes packet header capturing, timestamping, sampling, classifying, and maintaining Flow Records.

In other words the specification itself embraces sampling as a normal component. This is where practice most often goes wrong. The fact that you received flow records tells you nothing about whether they are exhaustive or sample based. To read a dashboard figure as total traffic, you must first confirm the sampling rate. Read without that confirmation, the number is not a total but an estimate scaled by a rate.

5. Sampling - what one in N erases

RFC 3176, the sFlow specification, describes itself as statistical packet based sampling of switched flows. The mechanism is simple. As the spec puts it, there is a counter that is decremented with each packet, and when the counter reaches zero a sample is taken. Setting the rate to N means sampling one in N of the packets in the monitored flows, and the spec states the goal that over time total packets divided by total samples converges on the configured rate.

The spec also states the boundaries. A sampling rate of one counts all packets, and a rate of zero disables sampling. On lost samples it notes that the net effect is a slight reduction in the effective sampling rate. That sentence is understated but its implication is large. Sampling treats loss not as an error but as absorbed variation in a ratio, because it was never an instrument for counting exactly.

So what gets missed

What sampling misses is not the small but the rare. That distinction is the one most often confused in practice.

Event you want to seeVisible under sampling?Why
Top conversation rankings, protocol mixClearly visibleMade of many packets, so they recur in the samples
A sustained upward bandwidth trendVisibleThe interval is long enough for sufficient samples
A burst lasting tens of millisecondsAlmost invisibleThe window is so short that the expected sample count falls below one
A scan or probe that ends in a few packetsInvisibleRare events not appearing in samples is correct behaviour
Whether a particular connection retransmittedInvisibleThe unit is a sampled packet, so one connection has no continuity

Here is the first way a dashboard deceives. A sample based chart draws absent events as a flat line. The screen looks normal and the viewer feels they have confirmed normality. In reality they felt they confirmed something that could not be confirmed. A screen does not distinguish drawing nothing from drawing not seen.

Reducing this trap is not a technical matter. It is printing the sampling rate on the screen. With the rate attached, viewers compute the resolution limit themselves. Without it, they read every chart as an exhaustive count.

6. Full capture - the price tag attached to accuracy

The opposite extreme is full packet capture. It is accurate. It is also expensive. I will stay inside what the official tcpdump manual states.

First, privilege. The manual states that reading packets from a network interface may require that you have special privileges, and points to the pcap documentation for details. What that single line means in practice is plain: turning on permanent capture is a decision to widen the privilege boundary, and softening privileges for the sake of one screen is a bad trade.

Second, snapshot length. The manual states that the -s option makes it snarf the specified number of bytes from each packet rather than the default of 262144 bytes. And it names the penalty clearly: taking smaller snapshots will discard data from protocols above the transport layer, which loses information that may be important. Snapshot reduction is therefore a dial that trades information for storage.

Third, silent loss. The manual states that on finishing a capture the tool reports packets dropped by kernel, defining this as the number of packets dropped, due to a lack of buffer space, by the packet capture mechanism in the operating system on which tcpdump is running. If that number is not zero, the capture file has holes. Yet a file with holes still opens, and charts still render. Looking only at the screen, you cannot see the holes.

Fourth, the moment you write to a file it becomes an asset management problem. Per the manual, -w writes raw packets to a file to be read later with -r. Put plainly, a capture file is a verbatim copy of communications at that moment. More on that later.

So how do you use it - narrow, and briefly

Where full capture earns its keep in practice is investigation, not permanent monitoring. Two rules: narrow by condition, cut by time.

# Narrow by host and port, and take header level only
# (addresses come from the documentation range 192.0.2.0/24)
tcpdump -i eth0 -s 96 -c 5000 -w /var/tmp/probe.pcap \
  'host 192.0.2.10 and tcp port 443'

# Size conditions - where the angle brackets appear
tcpdump -i eth0 'len < 128'
tcpdump -i eth0 'ip[2:2] > 1400'

# Flag conditions - connection setup and teardown only
tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

Note that a filter is not merely a device for reducing storage. A filter is a record of what you decided not to look at. Later, when that capture yields no answer, the first possibility to examine is not that no answer exists but that the filter threw it away. Which is why the filter string is worth preserving alongside the capture file.

7. Observation is itself load - points, mirroring, storage

This is the most operational section of the article. Looking has value, and value has a price. On networks that price is physical.

The second row is especially dangerous. Traffic discarded because a mirror port overflowed appears on screen as having gone away. And a picture of falling traffic is usually read as reassuring. A sign inversion happens right there, where overload looks like calm. Which is why an observation layer needs metrics about itself. Kernel drop counts, mirror port utilisation and sampling rate have to live somewhere on the screen.

Note too that the choice of storage layer is part of the capture method. The project above splitting SQLite and ClickHouse comes down to retention window and query shape. That axis was covered separately in why ClickHouse is winning the observability war, so I will not repeat it.

8. Encrypted traffic - what shows and what does not

The most common misconception splits in two directions. With TLS you see nothing and capture it and you see everything. Both are wrong. Only the verified range follows.

RFC 8744, which covers requirements for encrypting Server Name Indication, states that the SNI TLS extension that multiplexed servers rely on is transmitted in cleartext, and specifies that the extension is carried in cleartext in the TLS ClientHello message. The same document describes how this value is used for filtering, blocking, quality of service and surveillance. It also notes that from TLS 1.0 through 1.2 servers send certificates in cleartext, so there would be limited benefit in hiding the SNI, adding that even where TLS 1.3 encrypts certificates, encryption alone is insufficient to protect server certificates. On IP addresses it observes that looking up what netblock an address belongs to reveals little in CDN environments.

RFC 8446, the TLS 1.3 specification, states its own limits too. In describing confidentiality goals it says TLS does not hide the length of the data it transmits, though endpoints are able to pad TLS records. Its protocol overview states that everything after the key exchange phase is encrypted. The ClientHello sits before that.

ItemIn encrypted trafficBasis
Server name being reachedMay be revealed - the extension travels in cleartextRFC 8744

The practical implications run two ways. One is encouraging. A surprising number of questions can be answered from names, sizes and timings alone. Which counterparties are being contacted, when load concentrates, whether an unusual peer has appeared - all of these admit judgement without opening any payload. Not capturing content is therefore not the same as being powerless.

The other is cause for caution. Invert the same fact and a person's behaviour is substantially revealed even without content. A record of who reached which name and when is sensitive in itself. We are not capturing content so it is fine does not hold. That is the subject of the next section.

9. Privacy and legal boundaries - where to stop

First, what I could not verify. While writing this I was unable to open the primary text of the relevant national statutes. Accordingly I cite no article numbers and no penalties. Quoting an unverified legal provision produces either false comfort or false alarm. Instead I set out only the operating principles that are not in dispute.

  • Only on a network where you hold administrative authority. This is the first and most important line. Capture is technically easy, and easy has nothing to do with permitted.
  • Do not go looking for ways to capture other people's traffic. This article does not cover that. Placing a point on a public network, someone else's circuit, or a segment you have no authority over is out of scope.
  • In an organisation, get approval before starting. Do not switch on capture without prior sign off from legal and security. Explaining afterwards is not approval. Check as well whether internal policy or employment rules address employee monitoring.
  • Take the minimum. If there is no reason to see content, narrow the snapshot to header level. If the goal is usage accounting, there was never a need to capture packets at all.
  • Decide the retention period first. Collection without a deletion rule only grows riskier over time. Configure automatic deletion before you switch it on.
  • Treat capture files as sensitive assets. Separate access rights, and record purpose and recipient when moving them outside. Dropping them in a shared folder for analytical convenience is the most common route to an incident.
  • Do not use it to identify people. Observation for troubleshooting and tracking individual behaviour have different purposes, and the moment the purpose shifts, the justification evaporates.
  • If you are unsure, do not capture. A problem created by observing is far harder to clean up than something missed by not observing.

There is a reason this section sits in the body rather than an appendix. Choosing a capture method looks like a technical decision, but it is really a decision about how far you have the right to see. Among the cases where sampled flows beat full capture, a fair number win on authority rather than cost. A design that does not see what it need not see is not thrift but a safety mechanism.

10. Three ways visualisation hides the limits of capture

Back to the opening question. The routes by which visible gets mistaken for knowable are broadly three.

10-1. It erases resolution

A line drawn from one in a thousand sampling and a line drawn from exhaustive counting are indistinguishable on screen. Both are smooth. Yet one carries events and the other cannot. A chart that does not display its resolution hides its own limits. As noted, the fix is simple: print the sampling rate and the collection interval on the screen.

10-2. It draws absent and unseen in the same shape

Flat because nothing happened and flat because nothing was observed are entirely different facts rendered as identical pixels. A window where a mirror port overflowed, a window where capture hit kernel drops, a window where the collector briefly disconnected - all appear as empty, and people read that as nothing wrong. Hence the need for the observation layer to report on itself.

10-3. It hides the unit of aggregation

Different things travel under the single word traffic. Connection level aggregates, the byte sum of flow records, an estimate obtained by multiplying samples by a rate. The moment two screens state different numbers under the same name, the tool stops being help and becomes an argument during an incident. Which is why aligning metric definitions comes before adding a tool.

The general ways visualisation distorts are set out in the earlier article, so here I have written only the three that are specific to networks. They share one trait: all three are problems of input, not of drawing.

11. Axes this article does not cover - logs and protocol layers

To keep the scope clear, two adjacent subjects are not the axis of this piece.

  • Log collection and anomaly detection - the axis of gathering and correlating records systems wrote about themselves. Because the input is a record, it differs in nature from traffic observation. That axis was handled in network security monitoring and log analysis.
  • Protocol layers - what gets decided at which layer is useful background for choosing a capture method, but explaining the layers themselves is a textbook axis. See understanding the OSI model and TCP/IP.

The relationship between those axes and this article comes out like this. Logs are what the system told you; traffic is what the system did not tell you. So they are not substitutes. Traffic remains when logs are silent, and logs remain when traffic is encrypted.

Read the whole table and you arrive at the same conclusion. Until the left column is filled in, the right column is undetermined. Pick the tool first and the question bends to fit the tool. That is why the number of dashboards grows while the time to notice does not shrink.

Conclusion: the work of deciding the question first

The traffic dashboard that drew attention is a well made tool. And it wrote plainly in its repository what its input is: connection information received from gateway APIs, with data collected from the user's own network environment. Drawing that line is a virtue. The problem lies not in the tool but in the usage that skips reading the line and throws packet layer questions at a connection layer screen.

Three things for practitioners to take away.

  1. Write down the questions you are failing to answer. That list decides the capture method. If the list is empty, you do not need a new screen.
  2. Confirm the unit of the input. Packet, sample, flow or connection. A question beyond the unit is not solved by a chart. And print the sampling rate and collection interval on the screen.
  3. Record what you chose not to see. Filters, snapshot length, retention period, privilege scope. These four are not cost savings but safety mechanisms. A design that does not see what it need not see lasts longest.

In the end, seeing traffic is not the act of turning on a chart but the act of deciding what to ask. Once the question is settled, a single table often finishes the job; and if it is not settled, you can hang up several live streaming screens and still know nothing.
