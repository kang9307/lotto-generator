人間が保守するかのようにコードを書け

コードベースがAIの学習コンテキストになる時代、悪いパターンをマージすると次の生成コードがそれをプロジェクトのルールとして学ぶ

2026-07-12 開発・インフラ

序論: AIがコードを代わりに書く時代、なぜより気を使って書くべきか

コーディングエージェントが1日に数百行を生成する今、逆説的に「どう書くべきか」という規律はむしろ緩む傾向がある。どうせAIが後で直してくれるという前提のもと、その場しのぎで条件文を一つ追加し、似たロジックをコピー&ペーストし、TODOコメントだけ残して次の作業に移ることが珍しくなくなった。2026年7月現在、GeekNews(news.hada.io)で紹介されたunstack.ioの記事一つが、この流れに正面から反論する主張を投げかけた。AIが書くコードは結局今あるコードベースを参照して作られるため、人間が適当にマージした悪いパターンが次にAIが生成するコードの基準線になるというものだ。

本人はこの主張が単なるクリーンコード論ではなく、AIコーディングツールが実務に深く浸透した2026年現在、あらゆる開発チームが向き合うべき構造的な問題だと考える。この記事では、なぜコードベースが事実上AIのプロンプトとして機能するのか、実際のデータが示すコード品質の崩壊はどの程度か、そしてこの悪循環を断ち切るためにチームが実際に何を変えるべきかを本人の分析で解き明かす。この記事は前回取り上げたコードレビューの本当の目的 — 保守しにくいコードを見つける仕事と繋がるが、角度が異なる。あちらは個々のPR単位で「このコードは保守しやすいか」を問うのに対し、こちらは「このコードがマージされると次のAI生成コードにどんな先例になるか」というコードベース全体・時間軸の視点を扱う。

1. 核心的な洞察 — コードベースは今やAIのプロンプトだ

人間だけがコードを書いていた時代、悪い習慣の代償は概ねその本人が払っていた。自分が書いた乱雑な関数は自分が再び開いて苦労するか、せいぜい同じチームの数人が不便を被る程度だった。しかしコーディングエージェントが毎日コードを生成する今は計算が変わる。

1.1 LLMはスポンジだ — 既にあるパターンをそのまま吸収する

unstack.ioはこの現象を簡潔に指摘した。原文の表現を借りれば、モデルは'LLMs are sponges'(出典: unstack.io)だ。新機能を依頼されたコーディングエージェントは理想的な設計を白紙から想像しない。今開かれているファイル、直近のコミット、リポジトリに既に存在する似たコードを先に参照し、そのスタイルをそのまま踏襲する。つまりコードベースに何が入っているかが、次の生成コードの実質的なプロンプトとして機能する。コードベースにマージされたすべての近道は「ここではこうする」という信号としてモデルに刻まれる。

1.2 5つ目のコピー — 重複が「うちのスタイル」として定着する瞬間

この仕組みが実際に問題になるのは反復の場面だ。例えば権限チェックのロジックを含むAPIエンドポイントを一つずつ追加していく際、毎回同じ条件文の塊を共通関数に切り出さずコピー&ペーストしたとしよう。3つ目、4つ目までは些細な近道に見える。ところが5つ目のエンドポイントをAIに依頼すると、モデルは理想的な解法ではなく、リポジトリに既にある4つのコピーを参照点として5つ目のコピーを作り出す。さらに悪いことに、その後リファクタリングを依頼しても、モデルは5つを一つに統合するより、今のコードベースのパターンがそうなっているという理由で5つをそのまま保存しようとする傾向を見せる。一度の近道がいつの間にか「うちのプロジェクトのスタイル」に昇格するのだ。

2. データで見る崩壊 — リファクタリングは減り、コピペは増えた

この主張が感覚的な懸念にとどまらないことは、最近の大規模なコード変更データで確認できる。本人が照合した主要な数値を整理する。

2.1 リファクタリング比率は半減、コピペは増加

コード品質分析企業GitClearが2億1千万行以上のコード変更を分析した2025年のレポートによれば、全変更行のうちリファクタリングに分類される割合は2021年の約25%から2024年には10%未満に落ち、同期間にコピー&ペーストに分類される行の割合は8.3%から12.3%に増えた。また2024年の1年間だけで重複コードブロックの発生頻度は8倍に増加したという。コード再利用のための構造化作業が減り、既存コードをコピーして新しい要求に合わせるやり方が急速に増えていることを意味する。

2.2 AI生成PRは欠陥が多く、負債は生き残る

810万件以上のプルリクエストと4,800以上のエンジニアリングチームを分析した2026年の研究はより直接的な数値を示す。AI生成コードを含むPRは人間が書いたPRより1件あたりの欠陥が約1.7倍多く(10.83件対6.45件)、AIツール導入後1年以内に技術的負債が30~41%増加した。さらに懸念されるのは、AIが持ち込んだと追跡された欠陥のうち22.7%が依然としてHEAD(現在のコード)に生き残っているという点だ。つまり近道としてマージされた問題の相当部分は自然に消えず、コードベースに蓄積される。

2.3 複利で積み上がる保守コスト

業界分析は、こうして放置されたAI技術的負債が管理されなければ、2年目には保守コストが初期比で約4倍まで膨らみうると警告する。リファクタリングが減りコピペが増える流れと、PRあたりの欠陥が増えその欠陥が長く生き残る流れが重なると、これは一度の悪い習慣ではなく自己強化的に積み上がる負債構造として見るべきだ。

3. なぜ新しい問題なのか — 「ゴミを入れればゴミが出る」のコードベース版

「Garbage in, garbage out(GIGO)」はもともとモデルを学習させる大規模データセットの品質問題を指す言葉だった。汚染された学習データが汚染された出力を生むということだ。しかしコーディングエージェントがリポジトリのコンテキストをリアルタイムで読み取って答えを作る今、本人はこの原則がはるかに即時的で個人的な形で再び現れると見ている。

従来のGIGOは、モデルを学習させる組織だけが気にすればよい、一段階隔たった問題だった。一方で今は、今日マージしたPR一つが明日同じリポジトリでAIが参照するコンテキストに即座に組み込まれる。学習データのキュレーションのような別段階を経ることなく、マージボタンを押す瞬間がそのまま次世代の学習信号を登録する瞬間になるのだ。この即時性と個人化されたフィードバックループが、この問題を「AIがいつか良くなれば解決すること」ではなく「毎日の習慣が毎日複利で積み上がること」に変える。チームの規約が弱いリポジトリほど、そしてコードレビューが形式的であるほど、このループはより速く回る。

4. 人間が読んで直せるコードを書く規律

この悪循環を断ち切る出発点は結局、基本に立ち返ることだ。ただしAI時代には、その基本に「自分が後で楽をするため」に加えて「次の生成コードがこれを標準として学ばないため」という理由がもう一つ加わる。

4.1 明確な名前と小さな関数

名前が意図を表し関数が一つのことだけをすれば、人間であれAIであれ、そのコードを参照点にしたとき正しいパターンを学ぶ。逆にdata、temp2のような名前と200行の関数は、人間にもAIにも「このリポジトリは元々こうまとめて書く」という誤ったシグナルを送る。

4.2 一貫性 — 同じ問題には同じ解法を一つだけ

同じ問題を解決する方法がリポジトリ内に3通りに散らばっていれば、AIはそのうちどれに従うべきか分からず4つ目の方法を新たに作り出す。逆に解法が一つに収束していれば、次の生成コードもその一つのパターンを強く踏襲する確率が高い。一貫性は美学ではなく、AIが参照するシグナルを絞り込み精度を高める実用的な装置だ。

4.3 その場しのぎはその場で整理せよ — TODOの負債には利子がつく

「後でリファクタリングする」というTODOコメントは、人間だけがコードを書いていた時代でもあまり守られなかったが、AI時代にはリスクがもう一つ加わる。後でAIに「このTODOを整理して」と依頼しても、モデルがリポジトリ全体を漏れなく調べてすべてのコピーを見つけ出す保証はない。実際にリファクタリングを依頼されたモデルが既存パターンを慎重に保存しようとするあまり、一部のコピーを見落とす事例も報告されている。重複や近道はそれが発生したPRの中でその場で整理する方が、後で一括整理を試みるよりはるかに安全だ。

5. コードレビュー・リンター・規約の役割がAI時代に大きくなる理由

ここに興味深い逆転がある。AIがコードをより多く書くほど、逆説的に「遅い」人間の仕組み — コードレビューやリンター — の重要性は下がるどころかむしろ上がる。

5.1 AIはドキュメントは無視してもCIのリントエラーは無視できない

コーディングエージェントは規約文書に書かれた推奨事項をしばしば読み飛ばす。しかしCIパイプラインでリンターがビルドを失敗させると、その失敗は無視できない強制信号になる。つまり「こう書いてください」という文書より、違反すれば実際に失敗する自動化されたルールの方が、AIの挙動を統制するはるかに強力な手段だ。レイヤーを跨ぐ依存関係や禁止パターンの使用といったアーキテクチャ違反まで検出する静的解析ルールを備えたチームは、そうでないチームよりAI生成コードの一貫性をはるかによく保っている。

5.2 リポジトリ標準文書の台頭 — AGENTS.md

2025年8月、OpenAI主導で複数のAIコーディングツールが共同で策定したAGENTS.md規格は、リポジトリのルートにAIエージェント向けの標準指針を置く慣例を作った。2025年12月時点で6万を超えるオープンソースプロジェクトがこの形式を採用し、20種類以上のAIコーディングツールがこれをサポートしている。これはチーム規約を人間だけが見るwikiドキュメントから、AIが実際に参照するリポジトリ標準へと格上げしようとする流れを示している。

5.3 コードレビューは今や「次世代学習データのゲートキーパー」だ

前回取り上げたコードレビューの本当の目的は、個々のPRが保守しやすいかを見る視点だった。ここにAI時代の視点をもう一つ加える必要がある。レビュアーが今承認する近道は、そのPR一つの問題では終わらず、次のAI生成コードの参照点として登録される。つまりコードレビューは「このコードが今正しいか」だけでなく、「このコードがマージされると今後このリポジトリでどんなパターンが標準として定着するか」まで併せて判断する仕事になった。AIレビューツールがセキュリティ脆弱性やスタイル違反のような機械的パターンを一次的に選別してくれる今、人間のレビュアーが集中すべき部分はむしろこの長期的な先例判断へと絞られつつある。

6. 実務チェックリスト — 今日から適用できること

本人がチームに勧める具体的な実践5つ。

  • 重複を発見したらすぐに切り出せ。 似たロジックを3回目にコピーしようとする瞬間が、共通関数として切り出す合図だ。「後で」は大抵来ない。
  • 可能な限りドキュメントではなくリンターで強制せよ。 アーキテクチャの境界、禁止パターン、命名規則をCIに組み込み、AIも人間も違反できないようにせよ。
  • AGENTS.mdまたは同等のリポジトリ標準ファイルを置け。 チームの規約をAIが実際に参照する場所に明示せよ。
  • レビューコメントに「これが次のAI生成コードの先例になるか」という問いを加えよ。 機能が正しくてもパターンが悪ければ指摘の根拠になる。
  • AI生成PRを別途追跡せよ。 導入初期はAI生成コードにより厳格なレビュー・品質ゲートを適用し、品質指標(欠陥率・差し戻し頻度)を人間作成コードと分けて観察せよ。

結論

AIがコードを代わりに書いてくれる時代であるほど、人間がコードに気を配って書く理由は減るどころかむしろ増える。コードベースはもはや人間だけが読む成果物ではなく、次のAI生成コードを作り出す生きたプロンプトだからだ。マージした近道一つが5つ目のコピーになり、そのコピーがプロジェクトのスタイルとして定着する過程は既にデータで確認されている。リファクタリング比率が減りコピペが増え、AI生成PRの欠陥が長く生き残る流れは自然には止まらない。明確な名前、小さな関数、一つに収束した解法、その場で整理する規律、そしてドキュメントではなく強制されるリンターとレビュー。この5つが結局、AI時代でもコードベースを健全に保つ最も古く、そして最も確実な方法だ。
