Slumber - 基于配方的终端 HTTP/REST 客户端，Postman 替代品 2026

用 YAML 定义请求、在终端执行：轻量且对 Git 友好的 API 客户端

2026-06-11 IT/技术

引言：与 API 打交道的另一种方式

调用 API 的工具早已数不胜数。有重量级 GUI 平台 Postman 与 Insomnia，有一行命令之王 curl，还有以人性化输出广受喜爱的 HTTPie。然而在 2026 年 6 月，开发者社区里又有一个选项成了热点：Slumber。它是一款用 Rust 编写的终端 HTTP/REST 客户端，最大特点是把请求定义为 YAML 配方（recipe）。

「为什么还需要又一个 HTTP 客户端」是个合理的问题。本文将冷静地指出 Slumber 填补的空白在哪里。先说结论：Slumber 的核心价值不是「速度」或「漂亮的输出」，而是把请求当作代码来对待的工作流。它瞄准的是中间地带——既不被困在 GUI 里，也不必每次手动拼接冗长的 curl 命令。据官方介绍，Slumber 的目标是成为一款「易用、可配置、可共享」的 HTTP 客户端。

1. 什么是终端 HTTP 客户端

进入正文前先理清术语。终端 HTTP 客户端指的是用键盘和文本来构造并发送 HTTP 请求的工具，而非用鼠标点击的图形界面。大体分两类：

  • CLI（命令行界面）： 用一行命令发送请求，如 curl https://api.example.com/users。擅长脚本与自动化。
  • TUI（终端用户界面）： 在终端内呈现带菜单、面板、列表的交互画面，兼顾 GUI 的便利与终端的轻量。

Slumber 有趣之处在于二者兼备。交互式探索请求、查看响应时用 TUI；在脚本或 CI 中自动调用时用 CLI。它甚至以 Python 包的形式提供，可在代码里直接调用。一个集合（请求的组合）由三种界面共享——这一设计正是 Slumber 的身份标识。

2. Slumber 的核心概念 - 集合、配方、profile

理解 Slumber 最快的路径是抓住三个概念。

  • 集合（Collection）： 通常装在一个 slumber.yml 文件里的请求配方的集合，是与项目仓库一起提交的单位。
  • 配方（Recipe）： 单个待执行请求的模板，定义方法、URL、请求头、请求体和查询。每个请求——「列出用户」「创建订单」——就是一个配方。
  • profile（环境配置）： 按环境划分的变量集合，让你在本地、预发布、生产等主机或令牌不同的环境间轻松切换。

这三者咬合后，你只需写一套配方，仅切换 profile 即可在多个环境复用同样的请求。GUI 工具里靠界面管理环境变量的工作，Slumber 用文本文件来处理。

3. 创建第一个集合 - slumber.yml 示例

百闻不如一见。下面是基于官方文档的一个简单集合，处理一个虚构的「鱼」API。

# slumber.yml
profiles:
  local:
    data:
      host: http://localhost:5000
  production:
    data:
      host: https://myfishes.fish

requests:
  list_fish:
    method: GET
    url: "{{ host }}/fishes"
    query:
      big: true

  create_fish:
    method: POST
    url: "{{ host }}/fishes"
    body:
      type: json
      data: { "kind": "barracuda", "name": "Jimmy" }

读一遍意图就很清楚。profiles 下的 local 与 production 各自把 host 变量定义为不同的值；requests 下的配方通过 {{ host }} 模板引用该变量。只要切换 profile，同一个 list_fish 请求就在本地与生产之间往返。与请求头冗长、引号转义凌乱的一行 curl 相比，结构一目了然。

4. TUI 与 CLI - 两种使用方式

建好集合后就该执行了。Slumber 提供两种方式。

4.1 TUI：交互式探索

在含有集合的目录中运行 slumber 即可启动 TUI。在一个交互画面里——通常左侧是配方列表、中间是请求详情、右侧是响应——你用键盘选中请求并发送，随即查看响应。响应浏览内置 JSONPath 选择器，可像 jq 一样从庞大的 JSON 响应中只挑出想要的字段。

4.2 CLI：脚本与自动化

无需交互时，直接用 CLI 执行，例如非交互地发送某个配方。

# 生成新集合
slumber new

# 启动 TUI（使用当前目录的 slumber.yml）
slumber

# 用 CLI 执行特定配方（指定 profile）
slumber request list_fish --profile production

得益于 CLI 模式，你可以把 Slumber 请求嵌入 Shell 脚本或 CI 步骤。把响应通过标准输出接住再管道给其他命令，这种典型的 Unix 式组合也能实现。（命令名与选项的确切形式可能随版本而异，请用 slumber --help 确认。）

5. 动态请求 - 模板、文件、Shell、上一个响应

Slumber 超越单纯「静态请求仓库」的地方，正是动态请求构造。据介绍，Slumber 从以下来源动态组装请求。

  • 模板变量： 像 {{ host }} 那样注入 profile 数据。
  • 文件： 把外部文件内容读入请求体或请求头，对大负载或证书之类的值很有用。
  • Shell 命令： 把 Shell 命令的输出当作值。例如调用令牌生成器，把结果放进请求头。
  • 上一个响应： 从前一个请求的响应中取值，传给下一个请求。登录 → 取得令牌 → 带认证请求这样的链式调用因此成为可能。
  • 交互提示： 在执行时向用户询问取值。

这种「从上一个响应取值」的能力在实战中尤其强大。处理需要认证的 API 时，你可以把「从登录响应中提取令牌、自动放入后续请求头」的流程固化进配方。过去在 Postman 里用「环境变量 + 测试脚本」组合完成的事，Slumber 以声明式配置来表达。

6. 对 Git 友好 - 把配置当作代码

Slumber 的理念可用一句话概括：「源优先（source-first）的配置」。由于所有配置与数据都以本地纯文本 YAML 存在，自然带来以下好处。

  • 版本管理： 把 slumber.yml 提交到 Git，API 请求的变更历史便与代码历史一同留存，用 git blame 即可追溯谁在何时改了某个端点。
  • 代码评审： 新增端点或修改请求可作为 PR 的 diff 评审——这是 GUI 点击做不到的。
  • 共享： 克隆仓库的同事无需另设账户或云同步，立刻就能用上同一个集合。
  • 复用： 在项目之间复制或引用配方，复用标准请求。
当 API 客户端的配置位于仓库之内、而非云端账户之后时，这份配置才真正成为代码库的一部分。

这一点正面解决了使用重量级 GUI 工具时那种微妙的不便——配置被困在工具内部、无法与团队同步的问题。

7. 从其他格式导入 - Insomnia、OpenAPI 等

若你已有用其他工具做好的集合，不必从头再来。据介绍，Slumber 支持导入多种外部格式。

  • Insomnia 集合
  • OpenAPI 规范
  • VSCode .rest 文件
  • JetBrains .http 集合

其中 OpenAPI 导入意义尤大。若有定义良好的 API 规范，便能以它为起点生成 Slumber 配方，从而在不丢弃既有资产的情况下迁移到新的工作流。

8. 与 Postman、Insomnia、curl、HTTPie 的比较

现在进入正式比较。把 Slumber 放在其他工具之间掂量一下它的位置。

工具 界面 配置方式 优势 劣势
Slumber TUI + CLI YAML 文件 轻量、对 Git 友好、环境切换 相对较新、无 GUI 协作
Postman GUI 云端/账户 协作、测试、监控功能丰富 较重、依赖账户、版本管理弱
Insomnia GUI GUI/文件 界面清爽、有插件 仍以 GUI 为中心
curl CLI 命令参数 无处不在、临时调用 反复与结构化时繁琐
HTTPie CLI 命令参数 输出对人友好 集合/环境管理较弱

从表中可见，竞争并非一对一。Slumber 不会完全取代 curl——对于发一次就完事的临时请求，curl 仍然更快。它也不取代 Postman 的团队协作、监控、Mock 服务器等平台功能。Slumber 精准瞄准的位置是这样一类开发者的日常工作流：反复处理多个端点，却不想背负 GUI 平台的重量。

9. curl 命令与配方的关系

值得注意的是，Slumber 配方与 curl 命令是互补而非对立的。把同一请求用两种方式写出来，差异便很鲜明。

# 一行 curl（适合临时调用）
curl -X POST https://myfishes.fish/fishes \
  -H "Content-Type: application/json" \
  -d '{"kind":"barracuda","name":"Jimmy"}'

上面的 curl 命令很快，但一旦请求头增多、环境变成好几个，手动管理就变得繁琐。把同一请求固化成 Slumber 配方后，环境切换与重新执行都更清爽。实际上，可以先用我们站点的curl 命令生成器之类工具快速拼出一次性请求，再把需要反复使用的请求迁入 Slumber 集合加以整理：临时拼装交给生成器和 curl，反复与结构化交给 Slumber。

10. 应用场景 - API 测试、CI、文档化

下面整理 Slumber 真正发光的场景。

10.1 日常 API 调试

调试开发中的 API 时，在 TUI 里挑选配方定义好的请求发送，并用 JSONPath 查看响应。比 curl 更友好，比 Postman 更轻量。

10.2 CI 回归与冒烟测试

在 CI 中用 CLI 执行同一份 YAML 集合，做部署后确认关键端点是否存活的冒烟测试。把开发时用的请求定义原样复用于验证，是一大优势。

10.3 活的 API 文档

slumber.yml 本身就成了「如何调用这个 API」的可执行文档。与 README 里被定格的 curl 示例不同，仓库里的配方会被真正执行，因此不易过时。

10.4 脚本集成

在 Shell 脚本中调用 slumber request，把请求结果交给后续处理。结合动态请求功能，令牌签发、链式调用等复杂流程也能在脚本里自动化。

11. 局限与注意事项

为求平衡，也要把阴影说清楚。Slumber 并非万能。

  • 成熟度： 据官方说明，Slumber 是一款相对较新的工具，功能尚未完全齐备。命令与配置的细节可能随版本变化，应以官方文档为准。
  • 缺少 GUI 协作： 没有 Postman 式的团队工作区、Mock 服务器、监控、可视化测试运行器。若需与非开发岗协作或向非技术干系人共享，GUI 工具更合适。
  • 学习曲线： 若不熟悉 YAML 与终端，初期上手可能比 GUI 更陡。但一旦掌握，便能在反复工作中收回成本。
  • 合适的定位： 临时的一行调用，curl/HTTPie 更佳；庞大的协作平台，Postman 更佳。Slumber 最适合居于其间——「像代码一样对待的反复 API 工作流」。

12. 结论 + 立即可试的三件事

用一句话概括 Slumber：「把请求定义为 YAML 配方、用 Git 管理、以 TUI 和 CLI 执行的轻量、可共享的终端 HTTP 客户端」。若你需要丰富的 GUI 协作，Postman 更好；若只是一行临时调用，curl 更好；但若想在二者之间把反复的 API 工作流当作代码来对待，Slumber 是非常合理的选择。

以三件可立即尝试的事收尾。

  1. 把常用的三个请求迁入配方。 从每次手敲的 curl 命令里挑出复用度最高的三个，写进 slumber.yml。一个小小的集合就能改变工作流的体感。
  2. 用 profile 区分环境。 把本地、预发布、生产的主机分到不同 profile，可从结构上避免「弄错环境、把请求发到错误服务器」的失误。
  3. 把集合提交到仓库。 将 slumber.yml 与代码一起提交，调用 API 的方式便成为活文档，同事仅靠克隆即可立即重现同样的请求。

最后想强调一句：好工具往往不是叠加新功能，而是把散落的工作挪到正确的位置。 Slumber 把长期困在 GUI 里的 API 请求配置，归还到仓库——也就是代码所在之处。若你享受终端、想把配置当作代码来对待，它值得认真一试。
