Memory Safety Absolutists - The Rust vs Fil-C Debate

Full rewrite or incremental hardening, and how to decide by threat model and code lifespan

Jul 27, 2026 Dev & Infra

Introduction: A Purity Contest Over Safety

The memory safety debate has drifted somewhere strange. It began as an entirely practical question: why do the same classes of vulnerability keep recurring in C and C++ code after thirty years? The argument now playing out in the community has a different character. Because Rust ships an escape hatch called unsafe, the claim goes, it is not truly a safe language, and therefore only an implementation like Fil-C, which catches every violation at runtime, deserves the label. The recent essay titled Memory Safety Absolutists takes direct aim at that posture. Its point is simple: if you savage Rust's escape hatch while extending no comparable criticism to ordinary C and C++ that compiles with no checks at all, then your standard is not about safety. It is about allegiance.

This piece works through where that criticism lands and where it falls short, starting from numbers rather than impressions. How large is the memory safety problem in measured terms? What exactly does Fil-C trade away to buy safety? How much unsafe actually exists in the Rust ecosystem? How far has the C++ committee's profiles approach come? After establishing those facts from public sources, we look at what is genuinely achievable in industries with unusually thick legacy C layers, using the embedded, telecom, and financial core systems of the Korean market as a concrete case. The conclusion up front: the answer is not a language name, but what inputs your code receives and how many more years it will live.

1. Numbers Before Arguments - How Big Is the Problem Really

The figure cited most often in this debate is 70 percent. It is not a vibe. It comes from two companies' own tallies, arriving at similar values independently, which is what makes it credible.

1.1 The Published Statistics

  • Microsoft: roughly 70 percent of the security vulnerabilities it assigns a CVE and patches are memory safety issues, tallied across more than a decade of security updates.
  • Google Chromium: an analysis of 912 high and critical severity bugs fixed in the stable channel since 2015 found about 70 percent were memory management and safety bugs, and roughly half of those were use-after-free.
  • Android: the share of memory safety vulnerabilities fell from 76 percent in 2019 to about 24 percent in 2024, and has since been reported below 20 percent.
  • Android's Rust code: across roughly 5 million lines, vulnerability density was estimated at 0.2 per million lines. Against the same organization's historical C and C++ density of about 1,000 per million lines, that is a gap of more than 1000x.
  • Side effects: the same reporting noted Rust changes had a 4x lower rollback rate and spent 25 percent less time in code review - the opposite of the assumption that safety slows delivery.

1.2 What These Numbers Do and Do Not Say

One caution is warranted. The 0.2 versus 1,000 comparison is not a controlled experiment. The Rust code is mostly new functionality; the C and C++ side is old code that has absorbed decades of concentrated attacker attention. Under-discovery in newer code, differences in module risk, and uneven research effort are all mixed in. Even so, a three-order-of-magnitude ratio is hard to explain by measurement bias alone. And Android's trend line from 76 percent to under 20 percent demonstrates something important: the share collapsed without rewriting the existing code. That single fact underwrites most of the practical strategy discussed below.

2. What Fil-C Is - Making C Safe Without Leaving C

2.1 How It Works: InvisiCaps and a Concurrent GC

Fil-C describes itself as a fanatically compatible memory-safe implementation of C and C++. The core is a pointer model called InvisiCaps. A pointer is split into an address the program can see and a capability it cannot, with bounds and lifetime information kept in separate metadata. The program can still perform all the usual bit-twiddling on pointer values, but at dereference time the hidden capability is checked, and an out-of-range access halts the program with a panic. Lifetime is handled by a concurrent, parallel garbage collector that reclaims backing memory only after every pointer to an object is gone, which makes use-after-free structurally impossible. Threads stop only at safe points such as backward control-flow edges, and signal handlers also run at safe points so they never collide with collection.

This is not a toy. The project's site lists ports including CPython, OpenSSH, GNU Emacs, and Wayland, plus Pizlix, an entire Linux userland built with Fil-C. Version 0.681 was published in early July 2026, so development is active. That the version number still starts with zero is also worth reading.

2.2 What It Costs

Safety is not free, and Fil-C's costs are specific enough to determine exactly where it fits.

  • Execution speed: roughly 1x to 6x slowdown for pointer-chasing code, around 4x in bad cases. Conversely, a shell (Bash 5.2.32) built with Fil-C reportedly showed no noticeable difference. In other words, workload variance is enormous.
  • Memory footprint: structures containing pointers carry capability metadata and effectively use double the space. On memory-constrained embedded targets that alone can disqualify it.
  • ABI incompatibility: output does not link with objects from ordinary compilers, so the entire dependency tree must be rebuilt. A single binary-only commercial library blocks the path.
  • Cross-language linking: linking with Rust is not currently supported, which complicates boundary design in mixed stacks.
  • The GC itself: for hard real-time work, kernels and drivers, and signal paths with jitter budgets, the presence of a garbage collector is itself disqualifying.

Put plainly, Fil-C is designed to preserve existing code and pay in runtime resources. There are domains where that exchange clearly works, and domains where it clearly does not.

3. Rust's Safety Model and the Reality of unsafe

3.1 Ownership and the Borrow Checker

Rust attacks the problem from the opposite direction. Every value has exactly one owner, and references may be either one mutable or many shared but never both, enforced at compile time. Those rules eliminate use-after-free, double free, and data races before the program runs. No runtime checks or GC are required, so performance stays close to C. The cost is instead paid by people. The freewheeling aliasing habits of existing C code do not transfer, so migration frequently means redesigning data structures rather than translating statements.

3.2 One Bug, Three Endings

Watching a single use-after-free play out three ways makes the difference concrete.

/* Standard C: compiles, usually runs, and is an attack surface */
char *buf = malloc(16);
free(buf);
strcpy(buf, "hi");   /* write to freed memory - can escalate to code execution */
/* Fil-C: identical source. Halted at runtime with a panic. */
/* The compiler checks the pointer's capability and blocks the invalid access. */
// Rust: it simply does not compile
let buf = vec![0u8; 16];
drop(buf);
// buf[0] = 1;  // error[E0382]: borrow of moved value: `buf`

The difference among the three endings is when you pay. C defers payment and settles the full bill when an incident occurs. Fil-C pays a little on every execution. Rust pays once, up front, during development. Which is preferable depends on how often the software runs, how much performance headroom exists, and how long it will live. That is precisely why this is a situational judgment rather than a ranking of languages.

3.3 Is unsafe a Hole or an Audit Surface?

The absolutists' main line of attack is unsafe, and it is not entirely wrong. Research does show that incorrect code inside unsafe can produce bugs that manifest in safe code, and surveys of prominent crates have catalogued numerous advisories and CVEs. But scale matters. Rust Foundation reporting puts the share of crates.io crates that use the unsafe keyword at about 20 percent, with much of that usage devoted to C interoperability, and the share by code volume estimated at roughly 1 percent.

The practical benefit here is not the presence or absence of safety but the size of the audit surface. In a C codebase, every line is potentially unsafe. In Rust, the places requiring scrutiny are syntactically marked and narrow. Reviewing ten thousand lines out of a million is an organizationally different task from reviewing all million. The argument that an escape hatch renders the whole thing meaningless is weak precisely because it erases that distinction.

4. The Absolutist Critique - Is a Total Rewrite Realistic?

The original author's criticism reads along two tracks. The first is the double standard: treating Rust's unsafe as a fatal defect while sparing plain C and C++, which compiles with no checks whatsoever, is a standard about membership rather than safety. The second is the asymmetry of the alternative: to nominate Fil-C as the single correct answer, you must say what fills the territory Fil-C cannot cover - places that cannot host a GC, cannot change ABI, and cannot absorb a 4x slowdown. Rust is what currently fills exactly that territory.

I largely agree, with one addition. Absolutism is not confined to the anti-Rust camp. The demand that all C must be rewritten in Rust is the same species of absolutism. Rewriting millions of lines of battle-tested code is not merely a question of learning a language; it means discarding decades of field-hardened edge case handling and undocumented requirements in one motion. A rewrite can trade memory bugs away and import fresh logic bugs in return. Notably, what Android actually achieved came from a rule of new code in a safe language, not from a rewrite campaign. The drop from 76 percent to under 20 percent is a curve produced by cutting off the source of newly introduced vulnerabilities, not by erasing the old code.

5. Rust Rewrite vs Fil-C Hardening - Cost and Risk

Comparing the two paths on the same axes makes the decision criteria far sharper. Below is a breakdown by the line items an organization actually pays.

The table reveals that the two options solve non-overlapping problems. Fil-C's greatest strength is not performance but continuity of people and assets: your C developers stay, your code stays, and the risk grade drops. Rust's greatest strength is that safety is nearly free at runtime - pay once and no cost attaches to each execution afterward. So the arithmetic favors Rust for core components that will live long and run constantly, and favors Fil-C for code with a short remaining lifespan or generous performance headroom.

6. The C/C++ Rebuttal - Safety Profiles and C++26

Rather than abandoning the language, the C++ standards community chose safety profiles. A Safe C++ proposal for a separate safe dialect competed with a Profiles proposal applicable incrementally to existing code, and in committee polling Profiles drew 19 in favor to Safe C++'s 9, with 11 favoring both and 6 neutral, so Profiles moved forward. Technical work on C++26 concluded at the March 2026 meeting in London Croydon, bringing reflection and contracts alongside safety hardening applied without rewrites. Work on further reducing undefined behavior and on additional profile papers continues, targeting C++29. Apple's hardening of more than 4 million lines of WebKit using a subset-of-superset approach has been cited as evidence the method scales.

The limits deserve equal honesty. Profiles are strongest on spatial safety - bounds checking - while temporal safety, the domain of use-after-free, remains a far harder problem. Google's published position states explicitly that it does not see a realistic path for C++ to evolve into a language with rigorous memory safety including temporal safety. Layered against the Chromium statistic that half of memory bugs were use-after-free, that means the territory profiles cannot cover may be the more painful half. Even so, profiles have a decisive advantage: you can apply them to existing code today. Switching on a measure that blocks half the problem now generally beats starting a plan that blocks all of it five years from now.

7. Regulation as a Variable - Guidance Turning Into Procurement Terms

This is no longer purely a matter of taste. In February 2024 the US Office of the National Cyber Director identified the programming language itself as a foundational security building block in its report Back to the Building Blocks. The Cybersecurity and Infrastructure Security Agency followed its 2023 joint guide The Case for Memory Safe Roadmaps with product security guidance urging software manufacturers to:

  • Publish a memory safety roadmap by January 1, 2026 - a date now past, meaning the current phase is verification of compliance.
  • Address high-priority components first, such as network-facing code and cryptographic operations.
  • Demonstrate that the roadmap produces a significant, prioritized reduction in vulnerabilities rather than a declaration.
  • Note that products with an announced end-of-support date before January 1, 2030 are out of scope.
  • Acknowledge, in CISA's own words, that migration takes significant time and resources, and pair short-term mitigation with long-term elimination.

The last two points are the striking ones. Even the regulator does not demand a total rewrite. It demands priorities and deadlines. The regulatory text is, if anything, more pragmatic than either pole of the community debate. Nor is this remote for exporters: telecom equipment, security appliances, automotive components, and industrial control software sold into US public sector and critical infrastructure will increasingly be asked in procurement whether such a roadmap exists. For organizations already operating under MISRA C, ISO 26262, or IEC 62443, a memory safety roadmap is not hard to layer onto the documentation system that already exists.

8. A Legacy-Heavy Market in Practice - The Korean Case

8.1 Three Different Battlefields

In Korean industry, C and C++ code is stacked thickest in roughly three places. Their constraints differ completely, so a single prescription guarantees failure.

  • Embedded and automotive: hundreds of kilobytes to a few megabytes of memory, hard real-time constraints, functional safety certification burden. The moment a GC appears the certification argument wobbles, so Fil-C is effectively excluded. The realistic path is stronger MISRA-class rules, wider static analysis, and Rust confined to new modules.
  • Telecom equipment and network software: packet parsers and protocol state machines take fully untrusted input directly, giving them the highest threat exposure of the three. Performance requirements vary widely, though: control-plane code is well worth rewriting in a safe language, while data-plane hot paths remain difficult.
  • Financial core and reconciliation: heavy on message parsing and batch processing, and extremely rewrite-averse because ledger integrity is at stake. Yet nightly batch windows carry relatively generous headroom. This is where a Fil-C style approach fits best in principle - and also where dependency on binary-only commercial libraries most often blocks it on ABI grounds.

8.2 Staffing Is the Real Bottleneck

What actually stalls organizations is people, not feasibility. The pool of systems programmers is already thin, and the pool that handles Rust at production level is thinner still. In markets where system integration and contract development dominate, there is also the hard reality that a feature freeze during a rewrite is unacceptable to the client. Seen this way, the appeal of an approach like Fil-C is not performance but that you do not have to replace your people. Conversely, if you commit to Rust, the lowest-failure pattern is not wholesale conversion but picking one new module and having two or three engineers spend six months learning and shipping at once. It is worth remembering that the 4x lower rollback rate and 25 percent shorter review time cited earlier are metrics that appear after the learning curve, not during it.

9. How Much Overhead Can You Actually Absorb?

The sentence four times slower is not by itself a basis for a decision, because places where 4x is fatal and places where it is irrelevant coexist inside one organization. Splitting tolerance by domain narrows the choice automatically.

What deserves attention here is that high threat exposure and generous performance headroom overlap substantially. Code that chews on external data directly - file parsers, image and document converters, log processors - is usually not on the hot path. That intersection is the optimal entry point for a Fil-C style approach. Recompiling that intersection is a far more productive first step than debating wholesale adoption.

10. A Decision Frame Instead of a Verdict

Compressed into an operational decision, everything above reduces to four questions. The language name comes afterward.

  1. Does this code receive untrusted input directly? If so, it is the top priority. Build the list in order of network boundaries, file parsers, cryptographic operations, and user upload handling.
  2. How many more years will this code live? If it is scheduled for retirement within three years, a rewrite investment will never be recovered; hardening flags and isolation are the rational play. If it will live ten years or more, the rewrite arithmetic starts to work.
  3. How much performance and memory headroom exists? If you have 2x or more and can obtain every dependency as source, a Fil-C style approach is the cheapest safety available. If you have none, delete that option from the list.
  4. Can you change your people? If the team has no capacity to learn Rust and no hiring runway, a full conversion plan will live only in a document. In that case a pilot narrowed to a single new module is the only shape that functions.

Answer those four and most organizations converge on a similar conclusion: write new code in a safe language, recompile or isolate the old code that is exposed, and leave the rest alone under monitoring. Android's path from 76 percent to under 20 percent had exactly that shape.

Conclusion: Purity Is Not a Metric

The double standard identified in Memory Safety Absolutists is real. Disqualifying Rust on account of unsafe while tolerating C and C++ that runs with no checks at all is a standard about belonging, not safety. At the same time, absolutism in the other direction - rewrite all C in Rust immediately - does not function in the field either. Both camps share the same error: treating safety as binary and ignoring the conditions the code actually operates under.

The useful posture for practitioners is much drier. Fil-C is a tool that buys both temporal and spatial safety by spending runtime resources while keeping existing assets and staff, and it is powerful wherever an ABI rebuild and a GC are affordable. Rust is a tool that front-loads the cost at development time and leaves runtime clear, and it wins where code lives long, runs constantly, and has no performance slack. C++ profiles are half a defense you can switch on today, and half is vastly better than zero. The three are less rivals than equipment for different constraint sets. As of July 2026, even regulators speak of priorities and deadlines rather than total rewrites. Time spent choosing a flag would be better spent listing which of your components take untrusted input and how many years each has left - that list will remove more vulnerabilities than participation in any argument.
