チャートライブラリなしにCSS font-variation-settings一行でKPIを描く方法

2026-05-20 IT・技術

はじめに:フォントがチャートになる瞬間

2026年5月、GeekNews(hada.ioトピック)に興味深い記事が投稿されました。Frank Tisellanoが制作したDatatypeというバリアブルフォントです。発想はシンプルですが新鮮です。「データを棒グラフではなくフォントの太さで表現しよう」。売上が伸びれば数字が太くなり、減れば細くなります。チャートライブラリもキャンバスもありません。ただのテキストです。

本記事はDatatypeそのものの紹介ではありません。Datatypeが示した発想を出発点に、バリアブルフォント(Variable Fonts)が2026年のデータ可視化にどのような可能性を持つかを技術的に分析します。要点は、フォント標準そのものがすでに強力な可視化ツールであり、私たちはその可能性を見落としてきたという事実です。

1. バリアブルフォント(Variable Fonts)とは何か

バリアブルフォントは2016年のOpenType 1.8で導入されたOpenType Font Variations規格に由来します。従来のフォントはRegular、Bold、Lightといった太さごとに別ファイル(通常8〜16個)を持っていました。バリアブルフォントはそれらを1ファイルに圧縮し、その間の無限の中間値を補間(interpolation)で生成します。

その補間を可能にするのが軸(Axis)の概念です。規格が定義する5つの登録軸は次の通りです。

  • wght(Weight):100(Thin)〜900(Black)の太さ
  • wdth(Width):狭い〜広い字幅
  • slnt(Slant):傾き(イタリック)
  • ital(Italic):イタリック有効/無効
  • opsz(Optical Size):本文/見出しの最適化

これ以外にフォント制作者は独自のカスタム軸を定義できます。Datatypeが活用するのはまさにこの領域です。

1.1. 通常のフォントとの違い

実務で最も実感する違いはファイルサイズと柔軟性です。

項目通常フォント(静的)バリアブルフォント
ファイル構成太さごと8〜16個の.woff2単一の.woff2
合計容量(ラテン)200〜400KB(複数)80〜150KB
合計容量(CJK)3〜6MB(複数)800KB〜1.5MB
中間太さ不可(450は存在しない)1単位で自由調整
アニメーション切替時にちらつく滑らかなトランジション

1.2. ブラウザ互換性

2018年からChrome、Safari、Firefox、Edgeがすべてバリアブルフォントをサポートしています。2026年時点ではIE11を除けば事実上100%サポートで、モバイルSafariやAndroid Chromeも安定動作します。重要なAPIはfont-variation-settingsプロパティとfont-weight: 1 9999のレンジ指定の2つです。

2. Datatypeの発想 - 「データをフォント軸に」

通常、バリアブルフォントのwght軸はデザイナーが事前に決めた値(例:400、700)を使います。Datatypeの洞察はその値をデータで動的に制御しようという点です。CSS変数1つあれば実現できます。

.chart-value {
  font-family: "DataTypeVariable", sans-serif;
  font-variation-settings: 'wght' var(--value);
  transition: font-variation-settings 0.3s ease;
}

HTMLでデータを直接マッピングできます。

<span class="chart-value" style="--value: 850">1,250</span>  <!-- 大きい売上 → 太く -->
<span class="chart-value" style="--value: 320">430</span>     <!-- 小さい売上 → 細く -->
<span class="chart-value" style="--value: 600">780</span>     <!-- 中間 → 中間 -->

チャートライブラリ(D3.js、Chart.js、ECharts)を一切呼んでいません。キャンバスもSVGもありません。それでも読者は一目で「どの数字が大きいか」を把握します。可視化の本質がデータを視覚属性にマッピングすることだとすれば、フォントの太さは最も自然な視覚属性の一つです。

2.1. アクセシビリティという無料ボーナス

この手法の隠れた強みはアクセシビリティです。キャンバスで描画したチャートはスクリーンリーダーが読めません。SVGはARIA属性を一つひとつ付ける必要があります。しかしバリアブルフォントの可視化は単なるテキストです。NVDA、JAWS、VoiceOverがそのまま「850、430、780」と読み上げてくれます。視覚障害ユーザーにもデータが伝わる、真の意味でのユニバーサルな可視化です。

3. 実務活用5シナリオ

発想が魅力的でも実務での適用先がなければ意味がありません。バリアブルフォント可視化が即効性を発揮する5つのシナリオです。

シナリオ1:ダッシュボードKPIカード

月間売上、新規登録数、コンバージョン率など、単一の数値が大きな視覚的重みを持つ場面に最適です。数字自体が太さで変動を示すため、別途チャートウィジェットが不要です。Vue・Reactではpropsでweight値を渡すだけで済みます。

シナリオ2:データテーブルのセル強調

1,000行の売上テーブルで値の大きい行を強調したいとき、色は色覚多様性に弱く、棒グラフは行ごとに余分なスペースを要します。バリアブルフォントの太さは同じ行内で即座に差を示します。

td.amount {
  font-variation-settings: 'wght' calc(300 + (attr(data-value number) / 1000) * 600);
}

(2026年5月時点でattr() typeは一部ブラウザに限定されるため、本番ではJSでCSS変数を注入する方が安全です。)

シナリオ3:インフォグラフィック・印刷媒体

バリアブルフォントは印刷でも太さがそのまま保たれます。雑誌・年次報告書・プレゼンテーションで棒グラフをテキストに置き換えれば、紙の上でもデータが息づくデザインになります。新聞の見出し太さを記事の重要度に自動マッピングする実験も可能です。

シナリオ4:リアルタイム監視パネル

サーバーCPU使用率や取引銘柄の変動率をバリアブルフォントの太さで表現すれば、点滅するゲージウィジェットより視線負担が少ないです。transitionプロパティで滑らかな補間を与えればデータが「呼吸する」感覚になります。

シナリオ5:CJKバリアブルフォント - 日本語環境での活用

日本語環境ではAdobeとGoogleのSource Han Sans Variable(源ノ角ゴシック)が代表的です。Noto Sans JP Variableも同等で、無料で商用利用可能です。韓国環境のPretendard Variable、中国環境のAlibaba PuHuiTi VFと同じパターンで適用できます。

@font-face {
  font-family: "Noto Sans JP Variable";
  src: url("/fonts/NotoSansJP-VF.woff2") format("woff2-variations");
  font-weight: 100 900;
}

.kpi-number {
  font-family: "Noto Sans JP Variable", sans-serif;
  font-variation-settings: 'wght' var(--data-weight);
}

4. D3.js / Chart.jsとの定量比較

バリアブルフォント可視化は万能ではありません。どの領域で強くどの領域で弱いか、定量的に比較しましょう。

基準バリアブルフォント方式Chart.js / D3.js
初期ロードサイズフォントファイル80〜150KBライブラリ200〜500KB
スクリーンリーダー対応ネイティブテキスト(優秀)ARIA別途作業が必要
インタラクションCSS hover・transitionのみズーム・ツールチップ豊富
学習曲線非常に低い(CSS一行)中〜急
チャート表現力単一値・テキスト中心scatter、heatmap等豊富
印刷互換性完璧(テキストのまま)ラスタライズが必要
SEO本文テキストとして索引キャンバスは索引不可

まとめるとバリアブルフォント可視化は単一値の強調とテキスト優先環境で強く、複雑な多次元チャートとインタラクティブダッシュボードでは弱い。両者は代替ではなく補完関係と捉えるのが正確です。

5. 日本語環境での現実 - CJKフォントが大きい理由

日本語のバリアブルフォントはラテンに比べてファイルが大きくなります。理由は単純です。ラテンアルファベットはグリフが200〜300字程度ですが、日本語はJIS第一水準・第二水準を合わせて約6,355字、漢字・仮名・記号を含めると更に増えます。加えてバリアブルフォントはすべてのグリフに対して補間データを別途保持しなければなりません。

そのため実務では次の2つの最適化が必須です。

  • サブセット(Subset):サイトで実際に使用する文字だけを抽出。pyftsubsetなどのツールで1.5MB → 300KB程度まで削減できます。
  • 分割ロード(unicode-range):CSSの@font-faceにunicode-rangeを明示し、必要なブロックだけダウンロード。
@font-face {
  font-family: "Noto Sans JP Variable";
  font-weight: 100 900;
  font-style: normal;
  font-display: swap;
  src: url("/fonts/noto-sans-jp-var.woff2") format("woff2-variations");
  unicode-range: U+3040-309F, U+30A0-30FF, U+4E00-9FFF;  /* かな・常用漢字 */
}

6. 限界と注意点

バリアブルフォント可視化を実務に導入する前に次を点検すべきです。

6.1. 表現可能なチャート形式の制限

本質的にバリアブルフォントは1次元の値を1つの視覚属性にマッピングする用途に最適化されています。scatter plot(2軸)、heatmap(2次元)、line chart(時系列推移)のような多次元・時系列表現には不向きです。この場合は依然としてD3・ECharts・Vega-Liteが正解です。

6.2. フォント読込前のFOUT対策

バリアブルフォントが読み込まれる前はシステムフォントがフォールバック表示され、その間はweightマッピングが効かずデータが全て同じ太さに見えます。font-display: swapと<link rel="preload">を併用してFOUT時間を最小化するか、フォント読込完了前は可視化エリアにローディングスピナーを置くのが安全です。

6.3. 印刷媒体でのweight精度

モニターで補間されたweight 350と印刷出力のweight 350は微妙に異なる場合があります。RIP(ラスターイメージプロセッサ)によって補間アルゴリズムが異なるためです。精密印刷が必要な媒体では100、300、500、700、900のような整数単位weightのみ使用することを推奨します。

6.4. デザインシステムとの整合

既存のデザインシステムがRegular/Boldの2種類しか定義していない場合、バリアブルフォント可視化はその間を自由に使います。先にデザインシステムガイドを「バリアブル親和」に更新しなければ、デザイナーと開発者の間で衝突が起きます。

7. 誰に推奨し、誰に不適合か

本記事の分析を総合すると、バリアブルフォント可視化の適合度は明確に分かれます。

8. 結論 - バリアブルフォントは可視化パラダイムの静かな拡張

Datatypeは大仰なライブラリではありません。一人のデザイナーが作った小さなフォント一つです。しかしそれが示した発想は本質的です。チャートはキャンバスの上に描かれる絵ではなく、データに視覚属性をマッピングするすべての行為であるという事実を改めて思い出させてくれました。

2026年のウェブはますます軽く、アクセシブルで、印刷フレンドリーな方向へ進化しています。バリアブルフォントはその流れに正確に重なります。チャートライブラリ200KBを呼ぶ前に、フォントファイル100KBの中に既に答えがあるかもしれません。本記事がその可能性をもう一度見直すきっかけになれば幸いです。
