계기 — 벡터 중심 구조의 한계와 v3 아키텍처 발표

2026년 9월 30일, 검색 엔진 인프라 기업 turbopuffer는 공식 엔지니어링 블로그를 통해 「RIP, vector database」라는 제목의 기술 문서를 공개했다. 초기 서버리스 벡터 데이터베이스로 출범했던 turbopuffer가 데이터 저장 계층의 근본적인 재설계를 단행하며 버전 3(v3) 아키텍처로 이행하고 있다는 소식이다. 이 발표의 핵심은 도발적인 표제가 풍기는 벡터 검색의 폐기나 퇴출이 아니다. 시스템의 뼈대였던 근사 최근접 이웃(ANN, Approximate Nearest Neighbor) 벡터 인덱스를 기본 저장 키(primary index)에서 내려놓고, 속성 인덱스와 동등한 세컨더리 인덱스(secondary index)로 전환한다는 구조적 결단이다.

turbopuffer는 클라우드 객체 스토리지를 원본 데이터(source of truth)로 삼고 NVMe SSD와 메모리 캐시를 계층화하여 비용 효율성과 검색 지연 시간을 양립시키는 방식으로 Cursor와 Notion 등 주요 기술 기업의 프로덕션 워크로드를 지원해 왔다. 그러나 텍스트 검색, 정규식 검색, 속성 필터링, 대규모 집계(aggregation) 등 비벡터 쿼리 요구가 급증하면서, 모든 데이터가 벡터 인덱스의 물리적 배치에 종속되어 있던 초기 설계는 저장 증폭, 쓰기 증폭, 쿼리 엔진의 벡터화 제한이라는 세 가지 물리적 장벽에 부딪혔다. 공식 기술 문서에 명시된 주요 해결 목표는 다음과 같다.

  • 벡터 인덱스에 결속되어 있던 문서 저장 구조를 분리하여 다중 벡터 데이터의 물리적 중복 제거
  • 백그라운드 벡터 클러스터링 조정 시 발생하는 수백 개 역색인과 속성의 연쇄 이동 차단
  • ANN 클러스터 크기에 갇혀 있던 분석 쿼리의 블록 크기를 풀어내어 현대적 벡터화 실행 파이프라인 가속
  • 벡터 검색뿐만 아니라 복합 SQL 쿼리와 대규모 스캔 쿼리를 turbopuffer 엔진 위로 이전하여 고속 처리

결국 이번 v3 전환은 단순한 성능 개선 패치가 아니라, 벡터 데이터베이스라는 단일 목적의 특수 데이터베이스 범주에서 벗어나 벡터·전문·구조화 데이터를 단일 엔진에서 통합 서빙하는 멀티 검색 엔진(multi-search query engine)으로의 체급 전환을 의미한다.

v1 아키텍처 — 객체 스토리지와 계층형 클러스터링의 결합

turbopuffer v1의 설계 목표는 매우 저렴하면서도 실용적인 응답 속도를 제공하는 서버리스 벡터 데이터베이스의 완성이었다. 시스템 런칭 당시 업계의 표준적인 선택지는 HNSW(Hierarchical Navigable Small World)와 같은 그래프 기반 벡터 인덱스였다. 그러나 그래프 기반 방식은 노드 간 임의 메모리 포인터 추적이 빈번하게 발생하여, 네트워크 레이턴시가 높고 대용량 연속 블록 읽기에 최적화된 클라우드 객체 스토리지 환경에는 구조적으로 적합하지 않았다. turbopuffer는 그래프 인덱스 대신 객체 스토리지의 특성에 부합하는 계층적 클러스터링(hierarchical clustering) 인덱스를 채택했다.

초기 구현에는 마이크로소프트의 SPANN 알고리즘을 사용했으나, 실시간 데이터 추가와 변경에 대응하기 위해 증분 인덱싱(incremental indexing)을 지원하는 SPFresh 알고리즘으로 전환했다. 벡터들을 특정 개수의 그룹으로 묶고, 각 그룹의 중심점(centroid)을 다시 상위 계층에서 클러스터링하는 과정을 단일 루트 트리가 형성될 때까지 반복하는 방식이다. 데이터 저장 계층은 정렬된 고유 키를 제공하는 키-값 맵 위에 구축되었다. 각 클러스터에는 ClusterId가 부여되고, 클러스터 내부의 개별 벡터에는 조밀한 번호인 LocalId가 매겨졌다. 이 두 식별자를 결합한 C0L1과 같은 형태의 식별자를 ANN 주소(ANN address)라고 부른다.

// turbopuffer v1: ANN 주소를 키로 사용하는 정렬된 키-값 저장 방식
                    // 단일 리프 클러스터 C0 내부의 벡터 데이터와 원본 문서 ID
                    K::Vector(C0L0) = vec![0.45, 0.32, ...];
                    K::Id(C0L0)     = 7;
                    
                    K::Vector(C0L1) = vec![-0.28, 0.96, ...];
                    K::Id(C0L1)     = 13;
                    
                    // 상위 트리 레벨에서 C0 클러스터의 중심점 벡터를 인덱싱
                    K::Vector(C1L4) = vec![0.64, -0.48, ...];
                    K::Id(C1L4)     = C0; // 하위 클러스터 식별자를 가리킴

v1 아키텍처의 구체적인 설계 원칙과 물리적 동작 특성은 다음 네 가지로 요약된다.

  • 객체 스토리지를 단일 원본 저장소로 삼아 디스크 유지 비용을 최소화하고 계층형 로컬 NVMe 캐시로 지연 시간 방어
  • 임의 포인터 추적을 배제하고 클러스터 단위의 대용량 순차 블록 읽기가 가능한 계층형 트리 클러스터 구조 채택
  • 정렬된 키-값 맵 상에서 ClusterId와 LocalId를 조합한 ANN 주소를 레코드의 유일한 물리적 주소로 사용
  • 상위 클러스터 중심점이 하위 클러스터를 가리키는 방식으로 트리 탐색 범위를 축소하여 최소한의 네트워크 I/O 달성

위 코드 예시에서 볼 수 있듯이, 벡터 값뿐만 아니라 원본 문서 ID까지 모두 ClusterId와 LocalId로 결합된 ANN 주소를 물리적 저장 키로 삼았다. 즉, 데이터베이스 엔진 내에서 데이터의 위치를 결정하는 절대적 기준(primary index)이 곧 벡터 인덱스였던 셈이다. 이 구조는 객체 스토리지에서 필요한 벡터 클러스터 블록만을 최소한의 I/O로 읽어 들이는 데에는 극도로 최적화되어 있었다.

v2 확장 — 역색인 속성 필터링과 BM25 전문 검색의 결합

벡터 데이터베이스의 실제 사용처가 단순 코사인 유사도 검색을 넘어 실제 비즈니스 시스템으로 확장되면서, 메타데이터 속성 필터링과 텍스트 전문 검색(FTS, Full-Text Search) 쿼리 플랜이 필수 요구사항으로 대두되었다. turbopuffer는 비공식적으로 v2로 불리는 단계에서 속성 인덱스와 BM25 역색인(inverted index)을 엔진에 통합했다. 검색 필터링을 고속으로 수행하고 높은 재현율(recall)을 보장하기 위해, 속성 인덱스는 특정 속성값을 해당 값이 포함된 문서들의 ANN 주소 목록으로 매핑하도록 구성되었다.

예를 들어 조류 분류 데이터에서 특정 과(family)나 속(genus)을 필터링할 때, 엔진은 해당 속성 키에 연결된 ANN 주소 리스트를 즉시 반환하여 벡터 검색 공간을 한정한다. 또한 include_attributes 매개변수를 통해 검색 결과와 함께 원본 속성 데이터를 반환해야 하므로, 각 문서의 메타데이터 속성 역시 벡터 및 ID와 마찬가지로 동일한 ANN 주소 하위에 물리적으로 함께 저장되었다.

// turbopuffer v2: 속성 역색인 및 BM25 전문 검색 인덱스 구조
                    // 속성값을 문서들의 ANN 주소 리스트에 매핑
                    K::AttrIndex("family", "Alcidae")    -> vec![C0L3, C1L2, C1L3, ...];
                    K::AttrIndex("genus", "Fratercula")  -> vec![C0L3, C1L2, C1L9, ...];
                    
                    // include_attributes 프로젝션을 위해 ANN 주소 하위에 메타데이터 속성 병치
                    K::Vector(C0L0)          = vec![0.45, 0.32, ...];
                    K::Id(C0L0)              = 7;
                    K::Attr(C0L0, "family")  = "Alcidae";
                    K::Attr(C0L0, "genus")   = "Fratercula";
                    
                    // BM25 전문 검색 포스팅 리스트: ANN 주소와 함께 출현 빈도 및 문서 길이 보관
                    K::FTS("description", "Atlantic")    -> vec![(C0L0, 2, 37), (C9L4, 1, 42), ...];
                    K::Attr(C0L0, "description")         = "A sharply dressed seabird with a multicolored bill...";

이후 turbopuffer는 벡터 검색 외에도 다양한 사용자 요구를 수용하기 위해 여러 가지 쿼리 엔진과 인덱스 구조를 지속적으로 출시했다. 대표적으로 확인된 확장 기능은 다음과 같다.

  • 속성값 기준 필터링: 역색인을 통해 속성 조건을 만족하는 ANN 주소 집합을 신속하게 추출
  • BM25 전문 검색: 검색어별 포스팅 목록에 출현 빈도와 문서 길이를 결합하여 연관도 채점 지원
  • 정규식 및 퍼지 매칭: 정형화되지 않은 텍스트 패턴 탐색과 오타 교정을 위한 유연한 문자열 매칭
  • 희소 벡터 검색: SPLADE 등 단어 가중치 기반의 희소 벡터와 밀집 벡터의 하이브리드 검색 지원
  • 속성 기준 정렬 및 집계: 특정 숫자나 날짜 필드를 기준으로 한 정렬과 기초 통계 집계 플랜 제공

이러한 확장을 거치며 turbopuffer는 이슈 트래커 Linear의 델타 동기화 엔진(delta sync read path)처럼 검색 이외의 정밀 데이터 동기화 백엔드로도 채택되었다. 그러나 이러한 수많은 기능적 확장에도 불구하고, 시스템 기저의 저장 구조는 여전히 벡터 클러스터 기반의 ANN 주소를 기준 삼는 벡터 우선 저장 체계에 묶여 있었다.

구조적 병목 ① — 다중 벡터 표현에 따른 저장 공간 증폭

모든 데이터가 벡터 인덱스의 ANN 주소에 종속된 구조는 문서당 정확히 하나의 임베딩 벡터만 존재하는 환경에서는 큰 문제를 드러내지 않았다. 문서 하나가 하나의 ANN 주소를 갖고, 그 주소 아래에 속성과 텍스트가 한 번만 저장되기 때문이다. 그러나 현대적인 RAG(Retrieval-Augmented Generation) 및 정보 검색 시스템이 발전하면서 문서 하나를 단일 벡터로만 표현하는 방식의 한계가 명확해졌다.

긴 문서를 단락별로 나누어 인덱싱하는 문서 중첩(document nesting) 기법이나, 토큰 단위의 다중 임베딩을 유지하여 검색 품질을 비약적으로 끌어올리는 후기 상호작용(late interaction, 대표적으로 ColBERT 계열 모델) 기법이 널리 도입되었다. 이러한 기법들은 한 문서에 여러 개의 벡터를 부여한다. 그러나 turbopuffer의 v1/v2 구조에서는 각 벡터가 서로 다른 클러스터에 할당되어 독립적인 ANN 주소를 부여받게 된다. 그 결과 다음과 같은 심각한 비효율이 발생했다.

  • 단일 문서에 10개의 벡터가 생성되면, 동일한 비벡터 메타데이터 및 텍스트 본문이 10개의 서로 다른 ANN 주소 아래에 10번 중복 저장된다.
  • 문서 본문과 속성의 용량이 큰 워크로드일수록 벡터 자체의 크기보다 중복 복사된 문서 데이터의 크기가 저장소를 압도하게 된다.
  • 저장 공간의 팽창은 곧바로 객체 스토리지 I/O 비용과 로컬 NVMe 캐시의 조기 소진으로 이어졌다.
  • 캐시 적중률 저하는 네트워크 대역폭 포화를 유발하여 동시 쿼리 처리 용량을 심각하게 갉아먹었다.
  • 이로 인해 turbopuffer는 네임스페이스당 벡터 열(vector columns)의 최대 개수를 인위적으로 엄격하게 제한해야만 하는 운영상의 제약을 안게 되었다.

구조적 병목 ② — SPFresh 재균형화가 유발하는 쓰기 증폭

두 번째 치명적인 병목은 데이터의 변경(삽입, 갱신, 삭제) 과정에서 발생하는 쓰기 증폭(write amplification)이다. 계층형 클러스터링 인덱스에서 데이터가 지속적으로 유입되거나 삭제되면 클러스터 간의 균형이 무너져 검색 재현율이 급격히 저하될 위험이 있다. 이를 방지하기 위해 turbopuffer의 SPFresh 알고리즘은 백그라운드에서 주기적으로 벡터들을 재배치하는 재균형화(rebalancing)를 수행한다.

문제는 문서의 모든 속성과 인덱스가 ANN 주소를 키로 삼고 있었다는 점이다. 특정 벡터가 클러스터 A에서 클러스터 B로 이동하여 새로운 ANN 주소(예: C0L3에서 C2L8)를 부여받으면, 해당 벡터 값만 이동하는 것으로 끝나지 않는다. 해당 주소에 종속되어 있던 모든 메타데이터 속성, 본문 데이터, 그리고 그 문서의 주소를 가리키고 있던 수백 개의 속성 역색인(Attribute Index)과 BM25 전문 검색 포스팅 목록까지 전부 연쇄적으로 갱신되어야 했다.

  • 단 하나의 벡터 위치가 재조정될 때 수백 개의 속성 및 색인 엔트리가 물리적으로 함께 이동하는 연쇄 이동(cascading move)이 발생했다.
  • 문서 갱신 빈도가 높은 동적 환경에서는 실제 데이터 유입량 대비 수십 배에서 수백 배에 달하는 디스크 및 객체 스토리지 쓰기 부하가 유발되었다.
  • 인덱싱 처리량(indexing throughput)을 끌어올리기 위한 엔지니어링 튜닝 작업이 점차 한계 효용 체감(diminishing returns)에 직면하게 되었다.
  • 쓰기 I/O의 과부하는 백그라운드 컴팩션 속도를 저하시키고 실시간 쿼리 레이턴시의 스파이크를 초래하는 주요 원인으로 작용했다.
  • 결과적으로 데이터 수집 파이프라인의 처리 속도가 저하되고 시스템 전반의 운영 비용이 급격히 증가했다.

구조적 병목 ③ — 쿼리별 최적 블록 크기와 벡터화 실행 제약

세 번째 문제는 현대 데이터 분석 및 검색 엔진의 핵심 성능 동력인 벡터화 실행(vectorized execution)의 제한이다. 분석 엔진은 SIMD 명령어와 CPU 파이프라인의 처리량을 극대화하기 위해 데이터를 연속된 블록 단위로 묶어 타이트 루프(tight loop) 안에서 처리한다. 그러나 최적의 성능을 발휘하는 블록 크기는 워크로드의 유형에 따라 완전히 다르다.

엔진 및 쿼리 플랜최적의 처리 블록 크기처리 특성 및 하드웨어 정렬 목표

위 표에서 보듯이, turbopuffer의 ANN 인덱스는 클러스터당 100~200개의 문서가 묶여 있을 때 객체 스토리지 환경에서 최적의 성능과 재현율을 달성한다. 그러나 문서 저장소가 이 클러스터 단위에 고정되어 있었기 때문에, 수천 개 이상의 연속된 행을 한꺼번에 스캔하여 처리해야 하는 집계(GROUP BY, SUM, COUNT)나 전체 테이블 스캔 쿼리도 100~200개 문서 크기의 작은 블록에 갇혀 실행되어야 했다.

블록 크기의 중요성은 이미 turbopuffer가 전문 검색 엔진을 v1에서 v2로 개편할 때 명백히 증명된 바 있다. FTS v1 시절에는 포스팅 리스트를 ANN 클러스터 경계를 따라 잘라 저장했기 때문에, 블록당 중간값이 고작 1.5개의 포스팅에 불과했다. FTS v2에서 포스팅 리스트를 ANN 클러스터와 분리하여 약 256개 문서 크기의 고정 블록으로 재구성하자, 인덱스 크기는 10분의 1로 줄어들고 쿼리 속도는 최대 20배 빨라졌다. 포스팅 리스트는 문서의 위치만 참조하면 되므로 클러스터 경계에서 벗어날 수 있었지만, 문서 본문 자체를 읽어야 하는 분석 및 집계 쿼리는 여전히 클러스터 크기에 발이 묶여 있었다.

v3의 해결책 — 프라이머리 인덱스 분리와 세컨더리 체계 전환

이 세 가지 병목을 근본적으로 해소하기 위한 turbopuffer v3의 설계 원칙은 명료하다. 문서의 기본 저장 키로 ANN 주소를 사용하지 않는 것이다. v3에서는 문서의 물리적 저장 배치와 컴팩션(compaction), 조회를 벡터 인덱스의 물리적 트리와 완전히 디커플링(decoupling)했다. 이를 통해 달성된 핵심 아키텍처 변화는 다음과 같다.

  • 문서 저장 계층의 독립: 문서는 벡터 클러스터의 경계와 무관하게 고유한 문서 식별자를 기준으로 최적의 컬럼 블록 크기로 묶여 저장된다. 이를 통해 다중 벡터가 존재하더라도 본문은 단 한 번만 저장되어 저장 증폭이 완전히 제거된다.
  • ANN 인덱스의 세컨더리화: 벡터 인덱스는 시스템의 유일한 중심 축이 아니라, 역색인이나 속성 인덱스와 동등한 하나의 「세컨더리 인덱스」로 재배치된다.
  • 쓰기 연쇄 차단: SPFresh 알고리즘이 벡터 클러스터를 재배치하더라도, 변경되는 것은 벡터 인덱스 내부의 포인터뿐이다. 문서 본문과 수백 개의 속성 역색인은 제자리에 유지되므로 쓰기 증폭이 크게 줄어든다.
  • 분석 쿼리의 벡터화 해방: 집계 및 필터 스캔 엔진은 ANN 클러스터 크기(100~200)의 제약에서 벗어나, 하드웨어 파이프라인을 포화시킬 수 있는 수천 행 단위의 최적 블록 크기로 데이터를 읽을 수 있다.
  • 엔진의 범용 SQL 확장: 문서 저장이 정규화됨에 따라 단순 벡터 유사도 검색을 넘어 훨씬 더 많은 유형의 SQL 분석 쿼리를 turbopuffer 엔진으로 가져와 초고속으로 실행할 수 있는 아키텍처 기반이 마련되었다.
  • 컴팩션 독립성 확보: 문서 데이터의 압축 병합 작업과 벡터 트리의 최적화 작업이 서로 다른 스케줄과 주기로 독립 실행되어 시스템 안정성이 향상된다.

현재 turbopuffer가 공식적으로 밝힌 운영 스케일은 전체 시스템 기준 1조 개 이상의 문서(1T+ documents)를 호스팅하고 있으며, 초당 1,000만 건 이상의 쓰기(10M+ writes/s)와 초당 25,000건 이상의 쿼리(25k+ queries/s)를 처리하고 있다. 또한 단일 인덱스에서 1,000억 개 이상의 벡터(100B+ vectors)를 운용하면서 초당 1,000건 이상의 QPS에서 99백분위(p99) 읽기 레이턴시 200ms를 유지하고 있다.

발표에 따르면 v3는 2026년 9월 초 기준으로 100%의 자동화 테스트(CI)를 통과하여 데이터 정합성과 정확성(correctness)을 먼저 입증했다. turbopuffer 엔지니어링 팀은 성능 격차를 좁히고 기존 v2 이상의 속도를 달성하기 위해 벤치마크 테스트를 진행하고 있으며, 수치 검증이 완료되는 대로 프로덕션 환경에 v3를 점진 배포할 계획이다.

확인하지 못한 것

  • v3에서 도입된 새로운 독립 문서 저장소의 구체적인 파일 포맷(예: Apache Parquet, 자체 컬럼 바이너리 포맷 등)에 대한 세부 명세. 공식 블로그에는 저장 구조의 분리 원칙만 언급되었고 구체적인 온디스크 파일 포맷은 명시되지 않았다.
  • v3 프로덕션 배포 시점의 확정 날짜. 블로그는 CI 100% 통과 후 공개 벤치마크를 진행 중이라고만 밝혔으며 구체적인 정식 릴리스 일정을 공표하지 않았다.
  • 기존 v2 인덱스에서 v3 독립 스토리지로의 온라인 마이그레이션 절차와 다운타임 유무.
  • v3 아키텍처 환경에서 측정된 집계(GROUP BY) 쿼리의 구체적인 레이턴시 개선 백분율 수치. (블로그 본문에서 언급된 10배 축소 및 20배 가속은 v2 FTS 개선 당시의 실측치임)
  • 현재 공개된 고객사(Cursor, Notion, Linear) 외에 v3 알파/베타 테스트에 참여 중인 엔터프라이즈 레퍼런스 목록.
  • v3에서 세컨더리 인덱스로 분리된 ANN 벡터 인덱스가 사용하는 노드 간 내부 캐싱 정책 및 추가 메모리 오버헤드.
