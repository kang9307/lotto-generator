引言:为什么2026年又开始关注本地LLM

直到2024年,"AI属于云端"仍是主流认知。ChatGPT、Claude、Gemini已经足够,似乎没有理由把笨重的模型搬到自己的电脑上。然而经过2025年,氛围明显变了。随用量线性累积的API费用,以及把个人代码和工作文档整批送到外部API所带来的安全与法务负担,开始全面浮出水面。同期Meta的Llama 3.x、阿里的Qwen 2.5、微软的Phi-3.5等7B到70B参数的开源权重模型快速进步,2026年又迎来了Qwen3.6、Gemma 4、gpt-oss等新一代。中等硬件也能得到实用的输出了。

GeekNews上一个叫whichllm的CLI工具引发小规模讨论。它做的事很简单:分析你的电脑配置,告诉你"这个模型能跑,那个模型跑不动",却引来了热烈讨论。这说明"我的电脑到底能跑哪个模型"是大家共同的困惑。本文不是工具介绍,而是依据公开的模型文件大小与厂商官方规格,整理出硬件-模型对照表+量化指南+运行时对比,提供一套实战决策标准。

1. 本地LLM再次走红的4个原因

1-1. 随用量增长的云端API费用

前沿模型API按token计费,每天处理数十万token的开发工作流(代码评审、文档生成、翻译)账单会随用量同步增长。单价的走向不能一概而论。按Anthropic官方价格表,Opus 4.5及之后模型的token单价低于Opus 4和4.1;另一方面,官方也写明Claude 4.7及之后的模型使用新分词器,同样的文本会多产生约30%的token(2026-09-29确认)。所以关键不在单价而在总量。只要把部分重复性工作交给本地7B到14B模型,原本随用量增长的成本曲线就会改变。

1-2. 隐私与机密泄露顾虑

"这段代码能发往外部API吗?"已成为企业法务的日常问题。叠加欧盟AI法案与各国隐私法收紧,把含有客户数据或内部代码的提示词发送到外部LLM提供商本身就构成合规风险。本地推理从根本上去掉了"外部传输"这条路径。不过部署模型的服务器仍需单独做好访问控制与日志管理。

1-3. 离线与隔离网环境需求

金融、医疗、军政、工厂OT网络等切断外网的环境,云端LLM根本不是选项。在这类环境中,把开源权重模型直接部署到内部GPU服务器上自托管是现实可行的路径,本地模型实际上是"唯一选择"。

1-4. 7B-70B开源模型的快速进步

2024年初普遍认为"7B模型只是玩具"。发布本文时(2026年5月),常见的说法是Llama 3.2 3B达到GPT-3.5级别、Qwen 2.5 14B在部分基准上达到GPT-4级别。这类比较随基准与任务差异很大,本文不作定论。可以确定的是换代速度。根据Hugging Face官方仓库,Qwen3.6(27B、35B-A3B)于2026年4月、Gemma 4(E2B、E4B、12B、26B-A4B、31B)自2026年3月起陆续上线,OpenAI的开源权重模型gpt-oss(20b、120b)则于2025年8月发布。只要硬件跟得上,可选模型会越来越多。

2. 按硬件等级的推荐模型对照表

本节是全文核心。各模型的内存需求按Hugging Face公开的GGUF文件大小(2026-09-29确认)校准。实际需要比文件大小更多的余量,因为随上下文长度增长的KV缓存以及运行时本身都会占用内存。VRAM不够时会溢出到系统RAM,此时速度会大幅下降。因此"文件大小加上余量能放进VRAM"是实用性的基准线。

12GB显存可以留有余量地放下Qwen 2.5 14B Q4_K_M(8.99GB),8GB则以7B到8B级的Q4-Q5为现实上限。同一型号也可能有不同显存版本。根据NVIDIA官方对比表,RTX 3060有12GB和8GB两种,RTX 5060 Ti有16GB和8GB两种,购买前务必确认显存容量。价格因地区和时间波动很大,本文不作讨论。

3. 运行时对比:用什么跑

同一个模型文件,用不同运行时加载,性能与易用性差别巨大。个人和小团队常选的代表性方案有以下四种。

运行时 界面 主要格式 优势 适合人群
Ollama CLI + REST API GGUF 一行安装、模型仓库经过整理、Docker友好 入门到中级开发者、RAG后端
LM Studio GUI GGUF 图形界面搜索Hugging Face、内置聊天UI 非开发者、快速试用
llama.cpp CLI(原生) GGUF 最底层构建、可极限调优、Metal/CUDA/ROCm/Vulkan 高级用户、嵌入式、需要性能调优的人
vLLM REST API HF Safetensors 多GPU、PagedAttention、大量并发 生产服务运维者

实战决策标准

  • 个人电脑初次尝试:Ollama或LM Studio。两者安装后都能马上拿到首条回复。
  • 集成到RAG或应用:Ollama。官方文档显示它在http://localhost:11434/v1/下提供/v1/chat/completions、/v1/embeddings、/v1/responses等OpenAI兼容端点(2026-09-29确认),现有代码几乎可以照搬。
  • Mac追求极致性能:llama.cpp(Metal构建)或Ollama,均启用Metal加速。
  • 多用户同时服务:vLLM。基于PagedAttention,擅长处理大量并发请求。

4. 量化指南:Q4、Q5、Q8什么时候用

量化(Quantization)是把模型权重从16位浮点压缩到约4、5、8位精度的技术。用少量质量损失换取大幅内存与速度节省。最常用的是GGUF格式的K-quants系列,常见变体如下。内存节省比例按Qwen官方仓库中Qwen2.5-7B-Instruct GGUF的文件大小(FP16为15.24GB)计算。

量化 内存节省(对比FP16,7B文件大小) 质量损失(相对顺序) 速度 推荐任务
Q4_K_M 约69%(4.68GB) 四者中最大 最快 普通对话、简单摘要、聊天机器人
Q5_K_M 约64%(5.44GB) 小 快 翻译、代码补全、RAG
Q6_K 约59%(6.25GB) 更小 中等 长文代码生成、推理链
Q8_0 约47%(8.10GB) 几乎可忽略 较慢 质量优先任务、基准测试

按任务匹配量化

  • 日常对话、摘要:Q4_K_M足矣。同样VRAM下放更大模型(如14B Q4)通常被认为优于7B Q8。
  • 编码助手:建议Q5_K_M及以上。代码token差一个字符就编译失败,对损失敏感。
  • 翻译:Q5_K_M是平衡点。Q4容易在微妙语义上累积偏差,Q8则速度代价过大。
  • 法律、医疗文档:Q6_K及以上。单词含义关键,优先质量。
"同样VRAM下,更大模型+更强量化通常胜出"

例如12GB VRAM既可以装Qwen 2.5 7B Q8_0(8.10GB),也可以装Qwen 2.5 14B Q4_K_M(8.99GB)。两者文件大小几乎相同,但因为参数量对输出质量的贡献大于量化带来的损失,多数评价认为后者更好(因任务而异)。所以"在我的VRAM里留足余量、塞下最大模型并使用Q4"是普通用户合理的起点。

5. 自动推荐工具的意义与边界

whichllm这类工具理念非常简单:输入电脑配置就给出推荐模型。与其当成"严肃工具",不如读作一个信号——开源LLM生态已经复杂到形成了真实的入门门槛。新模型不断出现,量化变体也很多。Qwen官方GGUF仓库仅Qwen2.5-7B就有含FP16在内的9种变体,某个社区仓库仅Llama 3.3 70B就上传了约30种GGUF变体。同一模型在不同运行时下内存占用还不一样。在这迷宫里迷路的人很多。

这类工具的局限同样明显。第一,真实推理速度并非仅由模型大小与量化决定,还涉及分词器效率、KV缓存大小、上下文长度、并发数、内存带宽等众多变量。第二,质量满意度因用户任务千差万别,自动工具无法评估。第三,中文性能需要单独看,不能等同于英文基准分数,但多数自动工具只按英文打分。

所以把它们当作"一级过滤"用,再用自己的任务实际跑两三个候选做最终决定。本文的对照表就是这"一级过滤"的角色。

6. 中文用户的特别考量(全球通用)

6-1. 语言支持先看模型卡

并非所有开源LLM都能同等处理中文。请先确认各模型卡写明的支持语言(2026-09-29确认)。

  1. Qwen 2.5(7B/14B/32B/72B):模型卡写明"支持29种以上语言",列出的语言中包含中文(以及日语、韩语)。
  2. Llama 3.1/3.3:官方支持语言为英语、德语、法语、意大利语、葡萄牙语、印地语、西班牙语、泰语共8种,不含中文。模型卡允许在遵守许可证的前提下针对其他语言微调,Hugging Face上可以找到中文微调版本。
  3. Phi-3.5 mini、gpt-oss等其他模型:先在模型卡确认支持语言与中文质量,再用自己的任务比较两三个,更稳妥。

6-2. Apple Silicon:装得下和跑得快是两回事

Apple Silicon采用统一内存,GPU与系统共享大部分RAM,因此能装下比同等显存的独立显卡更大的模型。不过发布时写的"24GB MacBook能跑70B Q3、64GB MacBook能跑70B Q8"与文件大小不符,在此更正。Llama 3.3 70B Q3_K_M为34.27GB,Q8_0为74.98GB,分别装不进24GB和64GB。扣除系统与其他应用占用后,70B Q4_K_M(42.52GB)以64GB、Q8_0以128GB配置为现实起点。速度则很大程度取决于内存带宽。官方规格中的带宽为:M5 153GB/s、M5 Pro 307GB/s、M5 Max 460-614GB/s、RTX 5090 1,792GB/s(2026-09-29确认)。能装下大模型与能跑得快是两个不同的问题。

6-3. Hugging Face下载

下载速度因线路、时段与模型大小差异很大(Llama 3.3 70B Q8_0单个文件就有74.98GB)。发布时介绍的hf_transfer(HF_HUB_ENABLE_HF_TRANSFER)已在Hugging Face官方文档中标为弃用(deprecated)。Hub的文件传输已改由Xet后端(hf-xet)完成,hf_transfer不再被使用,高性能模式改用HF_XET_HIGH_PERFORMANCE开启。CLI命令也改为hf(2026-09-29确认)。Ollama从自己的模型仓库拉取模型。

# Hugging Face CLI 下载(依据官方文档,2026-09-29)
pip install -U huggingface_hub
export HF_XET_HIGH_PERFORMANCE=1
hf download Qwen/Qwen2.5-14B-Instruct-GGUF --include "*q4_k_m*.gguf" --local-dir ./models
# 若文件被拆分为多个分片(-00001-of-0000N),需全部下载

6-4. 24小时推理服务器的电费

假设RTX 4090全天以50%推理负载运行、平均功耗200W,则200W × 24小时 × 30天 = 每月144kWh。按发布时采用的居民电价折算(2026年5月时点,未重新确认),中国大陆约80-100元,日本约4,300日元(约30日元/kWh),韩国按累进最高档约285韩元/kWh计算约为41,000韩元的额外电费。发布时韩国写作"约30,000韩元"属计算错误,在此更正。实际电费取决于原有用电量与阶梯档位。用量大时可能比云端API便宜,但不是"零成本",这一点要提前预算。

7. 结论:2026年向谁推荐什么

用户类型 首选推荐 理由
普通用户(摘要、翻译、聊天) Llama 3.2 3B Q4_K_M / Qwen 2.5 7B Q4 显存8GB以上或统一内存16GB以上即可,入门门槛最低。
开发者(编码助手) Qwen 2.5-Coder 7B Q5或14B Q4 代码专项训练,便于本地接入Continue/Cursor。
RAG/内部聊天机器人运维 Llama 3.1 8B Q5_K_M + Ollama OpenAI兼容API,LangChain、LlamaIndex开箱即用。
研究者/实验者 Qwen 2.5 32B Q4-Q5或Llama 3.3 70B Q4 32B需要24GB以上显存,70B Q4_K_M(42.52GB)以64GB以上统一内存或溢出到RAM为前提。
企业服务运营者 vLLM + Llama 3.3 70B FP16(多GPU) 仅FP16权重就约141GB,需要多GPU。适合并发请求、日志、鉴权、配额管理。

本地LLM已经不再是"业余爱好"。发布时常见的看法是7B级可替代GPT-3.5、14B-32B可覆盖GPT-4的大部分场景,但这种比较因任务差异很大,请用自己的工作验证。只要记住一条简单原则——"用文件大小加余量能塞进我的VRAM的最大模型,选Q4_K_M"——就能大幅减少试错成本。

# 本地LLM硬件检查表 - 挑选装得进你内存的模型

基准日: 2026-09-29。文件大小依据Hugging Face公开的GGUF文件,硬件数值依据NVIDIA、Apple官方规格。
不讨论价格(随地区和时间波动很大)。

---

## 1. 先做三步

- [ ] 确认显卡的**显存容量**(Mac则看统一内存容量)。同名产品可能有不同容量:RTX 3060有12GB和8GB,RTX 5060 Ti有16GB和8GB
- [ ] 确认要用的模型的**GGUF文件大小**(见下表)
- [ ] 看**文件大小+余量**(随上下文长度增长的KV缓存、运行时占用)能否放进显存。溢出到内存后速度会大幅下降

Mac需从统一内存中扣除系统和其他应用占用的部分再计算。

---

## 2. GGUF文件大小参照表

| 模型 | Q4_K_M | Q5_K_M | Q6_K | Q8_0 | FP16 |
|---|---|---|---|---|---|
| Qwen 2.5 7B | 4.68GB | 5.44GB | 6.25GB | 8.10GB | 15.24GB |
| Qwen 2.5 14B | 8.99GB | 10.51GB | 12.12GB | 15.70GB | 29.55GB |
| Qwen 2.5 32B | 19.85GB | 23.26GB | 26.89GB | 34.82GB | 65.54GB |
| Qwen 2.5 72B | 44.01GB | 51.67GB | 59.86GB | 77.53GB | 145.93GB |
| Llama 3.3 70B(社区量化) | 42.52GB | 49.95GB | 57.89GB | 74.98GB | 141.12GB |

- gpt-oss-20b:模型卡写明"可在16GB内存内运行"
- Llama 3.3 70B Q3_K_M为34.27GB — 放不进24GB、36GB内存

---

## 3. 按内存容量的决策表

| 你的内存 | 现实上限 | 不要硬塞的 |
|---|---|---|
| 显存 8GB | 7B-8B的Q4-Q5(Qwen 2.5 7B Q4_K_M 4.68GB) | 14B Q4_K_M(8.99GB)及以上 |
| 显存 12GB | Qwen 2.5 14B Q4_K_M(8.99GB) | 14B Q8_0(15.70GB) |
| 显存 16GB | Qwen 2.5 14B Q5_K_M(10.51GB)、gpt-oss-20b | 32B Q4_K_M(19.85GB) |
| 显存 24GB | Qwen 2.5 32B Q4_K_M(19.85GB) | 32B Q8_0(34.82GB)、70B Q4_K_M(42.52GB) |
| 显存 32GB | Qwen 2.5 32B Q6_K(26.89GB) | 70B Q4_K_M(42.52GB) |
| 统一内存 36GB | Qwen 2.5 32B Q4_K_M(19.85GB) | 70B Q3_K_M(34.27GB) |
| 统一内存 64GB | Llama 3.3 70B Q4_K_M(42.52GB) | 70B Q8_0(74.98GB) |
| 统一内存 128GB | Llama 3.3 70B Q8_0(74.98GB) | 405B Q4(约240GB以上,计算值) |

超出显存的模型靠溢出到内存"能跑",但很慢。实用标准是放在显存之内。

---

## 4. 量化选择

| 量化 | 对比FP16节省(按Qwen 2.5 7B文件) | 质量损失(相对顺序) | 用途 |
|---|---|---|---|
| Q4_K_M | 约69% | 四者中最大 | 普通对话、摘要 |
| Q5_K_M | 约64% | 小 | 翻译、代码补全、RAG |
| Q6_K | 约59% | 更小 | 长代码、推理链、法律医疗文档 |
| Q8_0 | 约47% | 几乎可忽略 | 质量优先、基准测试 |

- [ ] 同样显存下先试"更大模型+Q4"(例:12GB上用14B Q4_K_M 8.99GB代替7B Q8_0 8.10GB)
- [ ] 编程从Q5_K_M及以上开始

---

## 5. 速度看内存带宽

| 硬件 | 内存 | 带宽(官方规格) |
|---|---|---|
| RTX 5090 | 32GB | 1,792GB/s |
| RTX 5080 | 16GB | 960GB/s |
| RTX 5070 | 12GB | 672GB/s |
| M5 Max | 最高128GB | 460-614GB/s |
| M5 Pro | - | 307GB/s |
| M5 | 最高32GB | 153GB/s |

装得下和跑得快是两回事。

---

## 6. 运行时选择

- [ ] 初次尝试 → Ollama或LM Studio
- [ ] 应用、RAG集成 → Ollama(`http://localhost:11434/v1/` 下的 `/v1/chat/completions`、`/v1/embeddings`、`/v1/responses`)
- [ ] Mac追求极致性能 → llama.cpp(Metal构建)或Ollama
- [ ] 多用户同时服务 → vLLM(70B FP16权重就约141GB,需多GPU)

---

## 7. 下载命令(依据2026-09-29官方文档)

```
pip install -U huggingface_hub
export HF_XET_HIGH_PERFORMANCE=1
hf download Qwen/Qwen2.5-14B-Instruct-GGUF --include "*q4_k_m*.gguf" --local-dir ./models
```

- `hf_transfer`、`HF_HUB_ENABLE_HF_TRANSFER` 已弃用。高性能模式用 `HF_XET_HIGH_PERFORMANCE`
- 用 `hf` 代替 `huggingface-cli`
- llama.cpp仓库为 `github.com/ggml-org/llama.cpp`

---

## 8. 中文支持(依据模型卡)

- Qwen 2.5:支持29种以上语言,列表中写明中文
- Llama 3.1/3.3:官方支持的8种语言中没有中文。可找微调版本
- 其他模型:先看模型卡,再用自己的任务比较两三个

---

## 9. 电费计算式

月用电量(kWh) = 平均功耗(W) × 24 × 30 ÷ 1000
例:假设200W → 144kWh。144kWh × 电价 = 每月额外电费。
电价按自己的电价方案与阶梯档位填写。
