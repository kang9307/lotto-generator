ハングルが字母に分解される瞬間 - NFCとNFD、境界で壊れるもの

ファイル名・grep・並び替え・長さ検証・圧縮がそれぞれどこで崩れるか、実行した出力で

2026-07-30 IT・技術

序論: 同じ名前のファイルが2つ、1つのフォルダにあった

ファイル一覧を出力したら同じ名前が2回現れた。사진.pngと사진.png。一文字も違わず、余分な空白もなく、拡張子も同じだ。画面を拡大しても区別できない。それなのにOSは2つを別のファイルとして扱っていて、実際に中身も違っていた。

ファイル名をバイトで表示すると答えが出る。一方は19バイト、もう一方は10バイトだ。同じ3文字の名前なのに保存されたバイト数が2倍近く違う。一方はハングル音節をあらかじめ合成された1文字として保存し、もう一方は初声・中声・終声を別々に保存した。Unicodeは両方を許している。画面に描かれるときだけ同じ形になる。

これがUnicode正規化の問題だ。そしてこの問題の実体は「正規化をしなかった」ではない。どこで誰が正規化するのか誰も決めなかったということだ。Webフォームからサーバへ、サーバからデータベースへ、データベースからファイルシステムへ、ファイルシステムから圧縮ファイルへ、圧縮ファイルから別のOSへ。文字列はこの境界を何度も越える。各境界で形式が保たれるのか変わるのか、誰が統一するのかが決まっていなければ、どこかで必ず壊れる。

この記事はその境界を一つずつ越えながら何が壊れるかを実際に実行して確認した出力で示す。結論を先に言うとこうだ。保存はおおむね安全だ。危険なのは境界だ。そして韓国語サービスで最も頻繁に起きる事故はファイル名ではなく[가-힣]正規表現だ。

実行環境。以下のすべての出力はWindows 10 Pro (10.0.19045) / NTFSで実際に実行した結果だ。ツールはNode.js v22.16.0 (win32)、Python 3.13.3、GNU bash 5.2.37 (MSYS2/MinGW64)、GNU tar 1.35、Windows PowerShell 5.1である。例示パスは/tmp/demoのようなプレースホルダに置き換えた。

スクリプトはすべてファイルに保存して実行した。ハングルとバックスラッシュが混ざったコードをシェル引数で渡すと静かに変形する。その罠はハングル正規表現の罠で扱った。

この記事が扱わないもの。語尾が付くと前の文字が変わる音節合成の算術と語尾別の安全パターンは上の記事で扱った。ファイル名に空白や改行が混ざってパイプラインが壊れる問題はfindとxargsの空白の罠で扱った。この記事は同じ名前が互いに違うバイト列になる問題だけを掘る。正規表現の方言と移植性はどこでも動く正規表現にある。

1. 同じに見える2つの文字列が違う - 「文字数」に答えが3つ

まず事実確認だ。「한」を合成形と分解形で作り、3つの長さを並べて測った。

대상            .length  [...s].length  utf8 byte
-------------------------------------------------
NFC 한                1              1          3
NFD 한                3              3          9
NFC 한글              2              2          6
NFD 한글              6              6         18
NFC 대한민국          4              4         12
NFD 대한민국         11             11         33

NFC 가 : U+AC00   (종성 없음)
NFD 가 : U+1100 U+1161   (2 코드포인트)

読み方はこうだ。NFCの「한」はU+D55C一つだ。NFDの「한」は初声ヒウ(U+1112)、中声ア(U+1161)、終声ニウン(U+11AB)の3つだ。だからバイト長が3と9に分かれる。

  • 終声のない「가」は分解しても2コードポイントだ。つまり膨張率は文字ごとに違う。2倍のこともあり3倍のこともある
  • 「대한민국」は4から11になった。4文字のうち終声があるものが3つなので4かける3ではない
  • したがって「文字数かける3」のような概算は通用しない。実際に測るしかない
  • UTF-8では合成済み音節も分解形字母もすべて1文字あたり3バイトだ。膨張はコードポイント数から来る

1.1 比較演算子がすべて違うと答える

--- 1-4. 비교 ---
nfc === nfd                : false
nfc == nfd                 : false
Object.is(nfc, nfd)        : false
nfc.localeCompare(nfd)     : 0
JSON.stringify 동일        : false
Set([nfc,nfd]).size        : 2
Map 키 충돌하는가          : false

注目すべき行は4番目だ。===はfalseなのにlocaleCompareは0、つまり「同じ」を返す。2つの関数が互いに違う答えを出しているのだ。

この不一致が実務でどう働くかが重要だ。並び替えは正常に見えるのに重複除去が失敗する。一覧をlocaleCompareで並べると「한」2つが隣り合う。人が見れば重複が目に入る。ところがSetやデータベースのユニークインデックスはバイトを見るので2つを別物として通す。「並べてみると隣り合っているのに重複除去ができない」という現象がここから出る。

1.2 Unicode標準はこれをどう定義しているか

Unicode標準附属書15が4つの正規化形式を定義している。定義をそのまま写すとこうだ。

形式標準の定義ハングルでの結果主に使う場所
NFC正規分解の後に正規合成音節1コードポイント保存・比較・転送の既定値
NFD正規分解字母に分離初声検索など字母単位の処理
NFKC互換分解の後に正規合成互換字母を組み合わせ用へ、全角を半角へ検索インデックスの正規化
NFKD互換分解上と同じで分解状態を維持まれに、特殊なインデックス

標準の中でハングルに直接関わる一文がある。ハングル音節の分解と合成は表参照ではなく算術アルゴリズムだ。実装が参照表を保存せずコードで計算できるようにした設計である。実務的な意味は明確だ。例外がない。特定の文字だけが問題になるのではなくすべてのハングル音節が例外なく分解可能だ。英語圏で正規化がアクセント付きの数文字の問題であるのとは性質が違う。韓国語はテキスト全体が対象になる。

ここまでは易しい。問題はnormalizeをどの行に書くかだ。これがこの記事の本論である。よくある失敗は2つの方向で現れる。

  • どこでもやらない - 最も多い。開発環境では一度も分解形が入ってこないので問題が表に出ない。特定のユーザ、特定の端末、特定のアップロード経路でだけ再現する
  • あちこちでやる - 問題が起きた後に急いで対応するとこうなる。比較の直前ごとにnormalizeを付けるのだ。動作はするが付け忘れた一箇所が残り、その一箇所を見つけるのに数週間かかる
  • 正規化の有無が層ごとに違う - もっと悪い場合だ。保存は合成形なのにキャッシュキーは原本、検索インデックスはまた別の形式になる。3箇所が互いに合わない
  • 正規化したと信じているができていない場合 - normalize()は新しい文字列を返す関数だ。戻り値を使わず呼び出しだけすると何も起きない。この間違いはコードレビューで見えにくい

標準附属書15が提示する戦略も同じ方向だ。各構成要素が正規化された入出力を保つようシステム境界で形式を保証せよということだ。つまり正規化は散発的な防御ではなく境界の契約であるべきだ。以下の節はその境界を一つずつ実際に越えてみた記録である。

  2. エラーメッセージが名前を判読できない形で表示する。シェルがマッチに失敗したバイトをエスケープして出すので人が原因を推測しにくい。「名前を打ち間違えたか」と誤解して何度もタイプし直すことになる

3.2 ではmacOSはどうか

ここに一つの通説がある。macOSのファイルシステムが分解形系で名前を保存し、そのためmacOSで作った圧縮ファイルを別のOSで展開すると名前が壊れるという話だ。

この記事では確認できなかった。確認環境がWindowsとNTFSだけなのでmacOSの挙動を実行で検証する方法がなかった。だから断定しない。ファイルシステムの種類やOSのバージョンによって挙動が違う可能性があるので使う環境で直接確認する必要がある。確認方法は上と同じだ。分解形の名前でファイルを作り、一覧を読んで返ってきた名前のコードポイントを表示すればよい。3行で終わる。

確認していないことを文書に書き残せば、それが次の人の根拠になる。この問題で実際に危険なのは「どのOSがどうするか」という知識ではなく自分のコードがどちらでも耐えるかだ。耐えさせる方法は一つだ。一覧を読むその行で正規化することである。

4. 検索の境界 - [가-힣]は分解形ハングルを1文字も捕まえられない

ここがこの記事で最も実用的な部分だ。ファイル名の問題は当たる人が限られているが、この問題は韓国語を扱うほぼすべてのコードにある。

node v22.16.0 / win32
--- 5-1. [가-힣]가 NFD를 못 잡는다 ---
대상            [가-힣] test    개수   Script=Hangul
----------------------------------------------------
NFC 한글              O 잡힘       2               2
NFD 한글              X 놓침       0               6
NFC 서울시            O 잡힘       3               3
NFD 서울시            X 놓침       0               7
--- 5-5. 정규식 문자 클래스 전수 비교 ---
패턴                       NFC 개수   NFD 개수
----------------------------------------------
[가-힣]                           3          0
[ㄱ-ㅎㅏ-ㅣ가-힣]                 3          0
\p{Script=Hangul}/u               3          9
[ᄀ-ᇿ]                   0          9

[가-힣]のマッチが2から0、3から0になる。部分的に少なく捕まるのではなく完全に0だ。理由は範囲そのものだ。[가-힣]は合成済み音節領域のU+AC00からU+D7A3までしか指さないのに、分解形字母はU+1100帯にあり範囲の外だ。

3行目がもう一つの罠を見せてくれる。字母を入れて範囲を広げた[ㄱ-ㅎㅏ-ㅣ가-힣]も0だ。「字母まで開いたから分解形も捕まるだろう」という期待が間違っている。なぜ間違っているかは9節で扱う。今必要な結論は一つだ。字母を追加しても解決しない。

4.1 検証器が両方向に静かに間違う

--- 5-2. 검증기가 조용히 통과한다 ---
NFC 사용자이름  ^[가-힣]+$ 통과 : true    | 한글 섞임 탐지 : true
NFD 사용자이름  ^[가-힣]+$ 통과 : false   | 한글 섞임 탐지 : false

2行が互いに反対方向の事故だ。同じ名前で形式だけが違う。

  • 「ハングルのみ許可」検証器 - 分解形の名前を拒否する。ユーザは正常なハングルの名前を入れたのに「ハングルのみ入力してください」というエラーを受け取る。画面に見えるのは明らかにハングルなのでユーザは何が問題か分からない。問い合わせが来ても再現しない
  • 「ハングル混入検知」フィルタ - 分解形ハングルを捕まえられない。多言語ページに韓国語が混ざったか検査するツール、禁止語フィルタ、言語判別器がここに引っかかる。検査器は「異常なし」を返し誰も疑わない
  • 後者のほうがはるかに危険だ。前者はユーザが抗議するのでいつか発見されるが、後者は抗議する人がいない。結果が失敗ではなく成功の形をしている
  • 同じ根から禁止語フィルタの回避が出る。ふるい落とすべき単語を分解形で入れれば合成形基準のフィルタをそのまま通過する。画面にはその単語がそのまま見える

同じ1行が37バイトと79バイトだ。そして合成形の検索語では分解形のファイルから何も見つけられない。ログ検索、ソースコード検索、バッチフィルタがすべてこの地点を通る。「そのログにその文字列はない」という結論が、実際には「形式が違った」である可能性がある。

4.3 grepの文字クラスにはもう一つの罠がある

実行中に予想しなかった数字が出た。正直に書き残す。

--- 5-13. C 로케일 grep -o [가-힣] (바이트로 해석된다) ---
LC_ALL=C  nfc.txt : 30
LC_ALL=C  nfd.txt : 72

本文のハングルは10文字なのにgrep -o "[가-힣]"が30を数えた。30はその10文字のUTF-8バイト数だ。つまりこのgrepは角括弧の範囲を文字の範囲ではなくバイトの範囲として解釈していた。72も同じやり方で出た分解形側のバイト数だ。

  • したがってこの数字はハングルの文字数として読んではいけない。ロケール設定によってツールがマルチバイト文字を文字と見ることもバイトと見ることもある
  • 文字数を数える目的ならシェルツールに頼らずUnicodeを理解するランタイムで数えるのが安全だ。上の出力でNode基準の値が10と0で明確だ
  • 固定文字列検索(-F)はロケールと無関係にバイト比較だ。だから形式が違えば必ず見つけられない。こちらはむしろ予測可能だ
  • 教訓は「ツールがハングルを1文字として数えるか確認して使う」だ。確認方法は既知の個数の標本を入れて結果を照合することである

6.2 切り取りは戻せない損傷を作る

--- 6-4. 자르기가 글자를 반토막 낸다 ---

「한」が「하」になった。終声ニウンが切り落とされたのだ。そして2行目が重要だ。切った後に正規化しても復元されない。正規化は失われた終声を蘇らせられない。これがこの記事の他の罠と性質が違う理由だ。

  • 比較・検索・並び替えの失敗は後で正規化すれば直る。データが残っているからだ
  • 切り取りはデータを捨てる。後から直せない。プレビューテキスト、要約、通知メッセージ、ログの切断がすべて該当する
  • だから順序が決まる。正規化が先、切り取りが後だ。この順序は交渉の対象ではない
  • 絵文字・国旗・結合文字まで安全に扱うには書記素クラスタ単位で切る必要がある。Intl.Segmenterがそれだ

6.3 データベースカラムの計算

--- 6-6. DB 컬럼 바이트 계산 ---

7文字が21バイトと54バイトだ。カラムをバイト基準で取る環境でVARCHAR(30)なら合成形は余裕があり分解形は溢れる。データベースが投げるエラーは「データが長すぎます」だけで、正規化を指さない。7文字の名前が30バイトを超えたというエラーを受け取ったら正規化を疑う根拠になる。

  • 最も広く開く方法は\p{Script=Hangul}だ。4節の表で唯一両側を捕まえた

そして2番目の表を見るとNFKCがどれだけ多くのものを一緒に変えるかが分かる。囲み文字の「㈜」が3文字の(주)になり、単位の「㎉」がkcalになる。戻す方法はない。標準附属書15もこの点を明記している。互換正規化形式を任意のテキストに無闇に適用してはならないということだ。多くの書式上の区別を消してしまうからである。

  • NFKCは検索インデックス用には有用だ。全角で入力した検索語が半角の本文に引っかかるようにしてくれる
  • ところが保存・表示用の原本には使わない。会社名の「㈜」が(주)に変わって保存されると戻せない
  • 実務の構成は原本はNFCで保存し、インデックスだけNFKCで別途生成することだ。2つの値を併せ持つ
  • つまり正規化形式は層ごとに違ってよい。ただし各層でどの形式なのかが明示されている必要がある

9.2 ハングルだけの問題ではない

--- 9-6. 이모지·결합 문자도 같은 문제 ---
구분                      .length  코드포인트   자소
é 합성형 (U+00E9)               1           1      1
é 분해형 (e + U+0301)           2           2      1
가족 이모지                     8           5      1

「é」も同じ構造だ。合成形の1コードポイントと、eにアクセント記号を付けた2コードポイントがある。画面には同じに見えて===はfalseだ。この記事のすべての処方がそのまま適用される。

絵文字のほうは少し違う。家族の絵文字はコード単位8、コードポイント5、書記素クラスタ1だ。こちらは正規化で統一される問題ではなくもともと複数のコードポイントからなる1文字だ。だからIntl.Segmenterが必要な理由が正規化とは別にもう一つ生まれる。「人に見える文字数」を数える唯一安全な方法が書記素クラスタだという結論は両方から同じだ。

10. 境界の判断表 - どこで一度だけ正規化するか

ここまで越えてきた境界を1つの表にまとめた。この記事から持ち帰るものが1つなら、この表だ。

外部API受信送信側の形式を制御できないパース直後にNFC

10.1 なぜ「一度だけ」なのか

複数箇所で正規化すると何が問題なのか。動作自体はするのに勧めない理由がある。

  1. 漏れる地点が必ずできる。比較する場所ごとに正規化を付ける方式は新しいコードが追加されるたびに付け直さなければならない。1箇所を落とせばその1箇所だけが静かに間違う
  2. 不変条件を言えなくなる。境界で一度正規化すれば「この内側の文字列はすべて合成形」という一文を書ける。あちこちでやるとそんな一文は書けず、コードを読む人が毎回追跡することになる
  3. 正規化の有無そのものが条件分岐になる。「ここは正規化されているか」を問うコードが生まれ始めたら設計はすでに崩れている
  4. 原本保存が必要な場所と衝突する。署名検証や原本再現が必要なら正規化前の値を別に保管する必要がある。正規化地点が1つなら「その前が原本」と言える
  5. コストは実際には問題ではない。正規化は冪等で、すでに正規化された文字列に再度かけても結果は同じだ。だから理由は性能ではなく責任の所在である

10.2 診断の順序

実際に疑わしい状況が起きたときの順序はこうだ。上から下へ3段階でおおむね判明する。

  1. バイトを表示する。文字列やファイル名をodで見るかコードポイントを出力する。e1 84で始まる3バイトの塊が続けば分解形だ。ecやedで始まれば合成形だ
  2. 長さを3通りで数える。コード単位、コードポイント、書記素クラスタが食い違うか見る。前の2つが書記素の数より大きければ分解形だ
  3. 両側を正規化して比較する。正規化後に同じになれば原因が確定する。この1行が診断の終わりだ
  4. 原因が確定したら直す位置は上の表から選ぶ。症状が出た場所ではなくその値が入ってきた境界を直す

11. この記事で確認できなかったこと

バランスのために限界を明かす。確認していないことを確認したように書けば、この記事が次の人を誤らせる。

  • macOSや他のファイルシステムの挙動。確認環境がWindowsとNTFSだけだった。macOSが分解形系で保存するという通説は検証できなかったので断定しない。3.2節の方法で各自確認するのが正しい
  • Linuxの各種ファイルシステム。確認していない。一般にファイル名をバイト列として扱うと言われているが実行で確認したことはない
  • zipコマンドの挙動。この環境にzipがなくPowerShellで代替した。zipやunzipの実装ごとに名前のエンコーディング処理が違う可能性がある
  • データベースごとの挙動。特定のデータベースが書き込み時点で正規化するかは確認していない。照合順序の設定によって違う可能性があるので使う製品で確認する必要がある
  • ブラウザの入力メソッドごとの挙動。どの入力経路が分解形を作るかは実行で確認していない。ただしどちらが来ても耐えるようにすることが処方なので実務的には知る必要が少ない
  • 正規化の性能。大量テキストで正規化のコストが有意かは測定していない。測定せずに性能を理由に正規化を省くことは勧めない

ただし確認できなかったものには共通点が1つある。すべて「あちら側がどうするか」に関する問いだ。そしてこの記事の処方はあちら側の挙動を知らなければ成立しないものではない。境界で正規化すればあちら側がどの形式を送っても関係なくなる。それが境界の契約を書く理由である。

結論: 問題は保存ではなく境界だ

この記事の出発点は1つのフォルダにあった同じ名前のファイル2つだった。原因はエンコーディング設定でも、ファイルシステムのバグでも、特定ツールの欠陥でもなかった。Unicodeが同じ文字を2通りで表現できるように許し、誰もどこで統一するか決めなかったことだった。

実行して確認したことを整理するとこうだ。保存の層はおおむね忠実だ。JSONも、ファイル入出力も、tarも、zipも形式をそのまま運ぶ。何も壊さない。だから分解形は一度入ってくるとシステムの外に出るまで生き残る。事故はそれが合成形を期待するコードと出会う地点で起きる。ファイルを探す行、正規表現を回す行、長さを数える行、ハッシュを作る行だ。

そのうち韓国語サービスで圧倒的に頻繁に起きるのは[가-힣]が分解形を1文字も捕まえられないことだ。2から0、3から0だ。字母を入れて範囲を広げても依然として0だ。そしてこの失敗は例外を投げない。検証器は通し、フィルタは捕まえられず、検査器は「異常なし」を返す。結果が失敗ではなく成功の形をしている。

だから結論は「正規化しよう」ではない。正規化地点を1つ決めて、その地点を文書に書けに近い。比較の直前ごとに防御する方式は必ず1箇所を落とす。境界で一度統一すればその内側について「この中の文字列はすべて合成形だ」という一文を書ける。その一文があるコードとないコードの差がこの問題のすべてだ。

今すぐできることが1つある。韓国語の文字列を[가-힣]で検査するコードをリポジトリから探し、その場所に分解形の標本を1つ入れて回してみよ。通るべきものが拒否されたり、引っかかるべきものが通ったりすれば、その検証器は今まで半分しか働いていなかったのだ。そして直す場所はその正規表現ではなく、その文字列が入ってきた境界である。

## 1. 核心の事実3行

1. 同じ「한」がコードポイント1個(U+D55C)のことも3個(U+1112 U+1161 U+11AB)のこともある
2. 画面出力は完全に同じ。目では絶対に区別できない

## 4. 正規化位置の決定ルール

- [ ] 正規化形式を**一つに決めたか**(一般的にはNFC)
- [ ] その形式を**文書に書いたか**(口頭の合意は忘れられる)
- [ ] 正規化地点が**境界にあるか**(比較の直前ではなく)
- [ ] 「この内側の文字列はすべてNFC」という**一文を書けるか**
- [ ] 正規化前の原本を保管すべき場所があるか(署名・原本再現)
- [ ] `normalize()` の**戻り値を使っているか**(呼び出しだけでは何も起きない)
- [ ] 検索インデックスにNFKCが必要なら**原本はNFCで別に**置いたか

### なぜ一度だけなのか

1. 比較の場所ごとに付けると**新しいコードが増えるたびに漏れる危険**が生じる
2. 境界で行えば**不変条件を文として書ける**
3. 「ここは正規化されているか」を問うコードが生まれたら設計はすでに崩れている
4. 正規化地点が一つなら「その前が原本」と言える
5. 正規化は冪等なのでコストは問題ではない。理由は**責任の所在**だ

## 5. よく壊れるパターンと矯正

| 症状 | 原因 | 矯正 |
|---|---|---|
| 同じ名前のファイルが2つ見える | 2つの形式でそれぞれ生成された | パス組み立て前にNFCで統一 |
| あるファイルをないと言う (ENOENT) | 分解形で保存、合成形で照会 | readdirの結果をそのまま使う |
| `[가-힣]` 検証が正常な名前を拒否 | 入力が分解形 | 検証前にNFC正規化 |
| ハングル混入フィルタが捕まえられない | 対象が分解形で `[가-힣]` が無力 | 正規化後に検査、またはScript属性 |
| 禁止語フィルタが抜かれる | 回避入力が分解形 | 入力境界でNFC |
| grepでログが引っかからない | 本文とパターンの形式が不一致 | 両側を同じ形式に |
| 重複除去ができない | Setやユニークインデックスはバイト比較 | キーをNFCに正規化 |
| 並び替えで数項目だけ最上部へ | 分解形初声がU+1100帯 | 並び替え前にNFC |
| 「10文字以内」が正常な名前を拒否 | コード単位で数えると3倍 | 書記素クラスタで数える |
| 「3文字以上」に1文字が通過 | 分解形1文字の長さが3 | 書記素クラスタで数える |
| プレビューの文字が壊れる | 終声が切れた | 正規化が先、切り取りが後 |
| 設定を入れたのに適用されない | オブジェクトキーが2形式に分かれた | キーをNFCに正規化 |
| 同じファイルなのにハッシュが違う | 形式が違う | 署名前にNFC、規約を明示 |
| 同じ検索語が指標に2行 | URLが2つ | リンク生成前にNFC |
| 7文字の名前がカラムを溢れる | 分解形のバイトが3倍 | 保存前にNFC、カラムはバイト基準で計算 |

## 6. 正規化形式の選択

| 形式 | すること | 使う場所 | 注意 |
|---|---|---|---|
| NFC | 正規分解の後に正規合成 | 保存・比較・転送の既定値 | 大半はこれで統一 |
| NFD | 正規分解 | 初声検索など字母単位 | その区間だけ限定使用 |
| NFKC | 互換分解の後に正規合成 | 検索インデックス | **戻せない**、原本には使わない |
| NFKD | 互換分解 | まれ | 上と同じ注意 |

- `[가-힣]` は**合成済み音節のみ**を捕まえる。分解形のマッチは0だ
- `[ㄱ-ㅎㅏ-ㅣ]` は**互換字母**の範囲だ。分解形とは無関係でやはり0だ
- 分解形字母は `U+1100`~`U+11FF` 帯にある
- 最も広く開くならScript属性エスケープを使い、`u` フラグを必ず付ける
- 広く開くのが常に正解ではない。**何を通すか先に決める**
