序論: ドキュメントの先にあるClaude Code

Claude Codeをインストールしたばかりの人と、数か月使い込んだ人の最大の違いは何でしょうか。私は迷わず設定ファイルをどれだけ手なずけたかだと考えます。多くのユーザーはツールをインストールしたまま、つまりデフォルトのまま使います。毎回同じ確認プロンプトでエンターを押し、同じフォーマッタを手で走らせ、繰り返しの作業を繰り返したままにしておく。その間、ツールが提供する設定の半分も触れていません。

このタイトルにある隠れたという言葉は誤解を招きかねないので、先にはっきりさせておきます。私は何か秘密のバックドアキーを暴こうとしているのではありません。ほとんどは公式ドキュメントに確かに存在しますが、前面に大きく出ていないために多くの人が見過ごす領域を指します。settings.jsonの奥深い隅、hooksによる自動化、MCPサーバー接続、権限の細かな制御といったものです。

この記事はhada.ioに上がったClaude Code設定分析のトピックから主題を見つけましたが、原文を翻訳したり要約したりはしません。代わりに私が実際に整理し活用してきた視点から、一般に知られている設定カテゴリを韓国の開発者に役立つ形でひもときます。重要な前提が一つあります。Claude Codeは速く更新されるツールなので、特定バージョンの動作を断定せず、一般的な活用原則を中心に述べます。適用前には必ず自分が使うバージョンの公式ドキュメントを併せて確認することをおすすめします。

1. settings.jsonの構造 - 知っておくべき核心領域

すべての道はsettings.jsonに通じます。Claude Codeの動作を変えたいなら、結局このJSONファイルを扱うことになります。まず理解すべきは設定が複数の階層に分かれているという点です。一般にユーザーグローバル設定(多くはホームディレクトリの~/.claude/settings.json)、プロジェクト設定(リポジトリの.claude/settings.json)、そして個人ローカル設定(.claude/settings.local.json)が一緒に動作すると言われています。

この階層構造がなぜ重要なのでしょうか。同じ設定キーでも、どのファイルに置くかによって適用範囲と共有の有無が完全に変わるからです。グローバル設定は自分のすべてのプロジェクトに影響し、プロジェクト設定はそのリポジトリをクローンする全チームメンバーに適用され、ローカル設定は自分だけに適用されます。この違いを知らないと、チームに強制してはいけない個人の好みを共有ファイルに入れたり、逆に全員が使うべきルールを自分のローカルだけに入れたりするミスをします。

settings.jsonでよく扱う核心領域はおおむね次のとおりです。

  • permissions: どのコマンドを自動許可または遮断するかを決める領域
  • env: Claude Codeセッションに注入する環境変数
  • model: デフォルトで使うモデルの指定
  • hooks: 特定のイベントにシェルコマンドを結びつける自動化
  • statusLine: 下部のステータスラインをカスタマイズする設定

構造を把握する最も安全な方法は、空のファイルからキーを一つずつ追加して動作を確認することです。JSONは文法に厳格で、カンマ一つ抜けても全体が無視されることがあるので、小さな変更のあとすぐ検証する習慣をつけるのがよいでしょう。

2. あまり知られていない便利な設定7つ

では実際に手に取れる設定を見ましょう。以下の7つはすべて一般に公開された機能ですが、深く活用している人は意外と少ない領域です。

2.1 permissions allowで繰り返しプロンプトを減らす

最も体感の大きい設定です。git statusやlsのように明らかに安全な読み取り専用コマンドをallowリストに入れると、毎回確認を押す摩擦が消えます。ただし削除や外部送信のような危険なコマンドは決して広く許可しないでください。

2.2 envでプロジェクトごとの環境変数を注入

特定のプロジェクトでだけ必要な環境変数をenvに定義すると、セッションごとに手でexportする手間が省けます。ただしトークンのような機微な値は共有ファイルではなくローカル設定に置くのが原則です。

2.3 modelで作業の性格に合うモデルを固定

プロジェクトの性格に応じてデフォルトモデルを指定しておくと、毎回モデルを切り替える煩わしさが減ります。重い推論が必要なリポジトリと軽い編集中心のリポジトリを別々に設定する具合です。

2.4 hooksでフォーマッタを自動化

ファイル修正後に自動でフォーマッタを走らせるようhookを掛けると、コードスタイルが人の手を経ずとも一貫して保たれます。自動化の核心なので後で別途扱います。

2.5 statusLineでコンテキストを可視化

ステータスラインをカスタマイズして現在のブランチ、モデル、ディレクトリといった情報を常に見えるようにすると、コンテキスト切り替えのコストが減ると言われています。

2.6 スラッシュコマンドで繰り返しプロンプトをテンプレート化

よく使う指示をスラッシュコマンドに保存すると、長いプロンプトを毎回タイプしなくて済みます。チーム共用コマンドにすると作業のやり方が標準化されます。

2.7 出力スタイルで応答のトーンを調整

出力スタイルを活用すると、応答の形式とトーンを自分の好みに合わせて調整できます。簡潔さを好むか、説明を好むかで体験が変わります。

3. Hooksの活用 - 自動化の核心

私がClaude Code設定の中で最も強力だと見ているのが、まさにhooksです。hooksは特定のイベントが発生する時点であらかじめ定めたシェルコマンドを自動実行する機能として知られています。ツール実行の前後、セッション開始といった時点にスクリプトを結びつけ、人が毎回気にしていた作業をツールに任せるのです。

代表的な活用シナリオは次のとおりです。

  • 自動フォーマット: ファイルが修正されたらフォーマッタを走らせてスタイルを一貫させる
  • ロギングと監査: 特定のコマンドが実行されるとき記録を残し追跡性を確保
  • 通知: 長い作業が終わるとデスクトップ通知やメッセージを送る
  • ガードレール: 危険なパターンを事前に点検する安全装置

ただしhooksは実際のシェルコマンドを実行する点で諸刃の剣です。意図しないコマンドや信頼できない入力をそのまま入れると危険になりかねません。そこで私がすすめるのは小さく始めることです。最初は単純なechoやフォーマッタ実行のような安全な動作を一つだけ掛けておき、意図どおりにトリガーされるか確認してから段階的に拡張してください。正確なイベント名や入力形式はバージョンによって異なることがあるので、公式ドキュメントのhooks項目を基準にするのが安全です。

4. MCPサーバー設定 - ツールの接続

MCP(Model Context Protocol)は、Claude Codeが外部ツールやデータソースとつながる通路の役割をします。MCPサーバーを設定に登録すると、モデルがファイルシステムの先の資源にアクセスしたり、特定サービスの機能を呼び出したりできるようになると言われています。データベース照会、課題トラッカー連携、社内文書検索といった作業をツール内で処理しようとする試みがすべてここに当たります。

MCP設定で私が強調したいのは接続範囲を慎重に決めることです。MCPサーバーは強力なだけに、何にアクセスさせるかを明確に制御しなければなりません。信頼できるサーバーだけを登録し、機微な資源へのアクセスは必要な範囲に限定するのが安全です。

実務ではMCPをすべてのプロジェクトにグローバルでオンにするより、必要なプロジェクトにだけ選択的に接続する方式をすすめます。たとえば社内データにアクセスするMCPサーバーは該当業務リポジトリでだけ有効化し、個人の実験プロジェクトには接続しない具合です。具体的なサーバー登録方法や設定キーはバージョンとサーバーの種類によって異なるので、各MCPサーバーの案内と公式ドキュメントを併せて参照してください。

5. スラッシュコマンド・Skillsのカスタマイズ

繰り返しの長いプロンプトを毎回タイプするほど非効率なこともありません。スラッシュコマンドはこの問題に正面から取り組みます。よく使う指示をファイルに保存しておけば、短いコマンド一行でその長いプロンプトを呼び出せます。

私が特に有用だと見る活用はチーム共用コマンドです。コードレビューのチェックリスト、コミットメッセージの規則、デプロイ前の点検手順といった繰り返し作業をスラッシュコマンドで標準化すると、チーム全員が同じやり方で作業するようになります。人によってばらついていた品質がツールのレベルで揃う効果があります。

さらにSkillsのような拡張メカニズムを活用すると、単純なプロンプトを超えて特定の作業フロー全体をパッケージ化できます。レポート生成や特定形式の文書作成のように手順が決まった作業を、再利用可能な単位にしておくのです。コマンドとSkillsの正確な登録場所と形式はバージョンによって差があり得るので、実際の適用時には現在のバージョンの案内を確認してください。

6. 権限(permissions)の細かな制御 - allow/denyパターン

権限設定は生産性と安全性が正面から衝突する地点です。確認プロンプトが多すぎると流れが切れ、許可が広すぎると事故を招きます。その間のバランスを取ることがpermissionsの核心です。

一般に権限はsettings.jsonのpermissions領域でallowとdenyのリストによって制御します。allowに入れたパターンは確認なしで実行され、denyに入れたパターンは遮断されます。私がすすめる原則は保守的なスタートです。

  • 安全な読み取り専用から: git status、git diff、ディレクトリ照会のように明らかに安全なコマンドだけをまずallowに追加してください。
  • 危険な動作は除外: ファイル削除、強制プッシュ、外部へデータを送るコマンドは自動許可の対象から外すのが安全です。
  • パターンは狭く: 広すぎるワイルドカード許可は意図しない実行を招くおそれがあるので、できるだけ具体的に指定してください。

このように段階的にallowリストを整えると、繰り返しプロンプトは減りつつ、危険な動作への制御は保たれます。パターン文法の細部ルールや優先順位は、バージョン別の公式ドキュメントを確認するのが正確です。

7. 生産性のコツ7つ

設定そのものを超えて、私が実際に効果を見た活用のコツを整理します。これは私の経験に基づく推奨であり、絶対的なルールではありません。

  1. 安全なコマンドからallowする: 最もよく出くわす読み取り専用プロンプトをまず無くすと体感効果が大きいです。
  2. スラッシュコマンドでルーティンをまとめる: 繰り返す指示はすぐコマンドにして再利用しましょう。
  3. hookは小さく始める: 検証していない自動化を一度に掛けず、一つずつ確認しながら増やしましょう。
  4. プロジェクトごとの設定を分離: リポジトリごとに.claudeディレクトリに合わせた設定を置くとコンテキストが自動で揃います。
  5. 機微な値はローカル設定に: トークンと個人のパスは絶対に共有ファイルに入れないでください。
  6. 定期的な設定点検: ツールが更新されたら設定も一度見直し、廃止されたキーがないか確認しましょう。
  7. 設定もバージョン管理する: 共有可能な設定はリポジトリにコミットして変更履歴を残すと、問題が起きたとき戻しやすくなります。

8. チーム設定の共有 - settings.json vs settings.local.json

一人で使うツールなら設定ファイルが一つでも二つでも構いません。しかしチームで使う瞬間、二つのファイルを区別することが協業の核心的な規律になります。

区別の基準は単純です。共有すべきか、そうでないかです。

  • settings.json(共有): チーム共通のルール、標準の権限ポリシー、共用hooks、共用スラッシュコマンド。バージョン管理に含め、全員がクローンと同時に適用されるようにします。
  • settings.local.json(個人): 個人のAPIトークン、ローカルパス、実験的設定。通常.gitignore処理してコミットしません。

この分離がもたらす利点は明確です。協力者がリポジトリをクローンした瞬間にチーム標準が自動で適用される一方で、各自のローカルの好みが衝突したり機微情報が誤ってコミットされたりするのを防げます。私が見た最もよくある事故は、個人トークンを共有settings.jsonに入れてそのままコミットするケースです。最初から二つのファイルの役割を明確に分けておけば、こうしたミスを構造的に遮断できます。

9. 韓国の開発環境への適用 - 韓国語入力、社内網、プロキシ

海外のツールを韓国の環境で使うときは、いつもローカライズの変数がついて回ります。Claude Codeも例外ではありません。私が特に気をつけるよう勧める三つを整理します。

9.1 韓国語入力とエンコーディング

韓国語のコメントや韓国語のファイル名が混じるリポジトリでは、エンコーディングの一貫性が重要です。UTF-8を基本に統一し、ターミナルとエディタのエンコーディング設定を揃えておくと、文字化けの問題を減らせます。

9.2 社内網とセキュリティポリシー

金融や公共のようにセキュリティが厳しい社内網では、外部接続が制限される場合が多いです。このときはMCPサーバーや外部ツール連携のアクセス範囲を社内ポリシーに合わせて狭め、機微データが外部に出ないよう権限と接続を保守的に設定すべきです。

9.3 プロキシ環境

社内プロキシを経由しなければならない環境なら、プロキシ関連の環境変数を正しく設定することが最初のボタンです。一般にHTTP_PROXY、HTTPS_PROXYといった標準の環境変数を活用しますが、具体的な適用方法はツールのバージョンや社内ネットワーク構成によって異なる場合があるので、インフラ担当者と一緒に確認するのが安全です。

10. 注意 - バージョンごとの差異と公式ドキュメント確認の推奨

ここまで読まれたなら一つだけ覚えておいてください。Claude Codeは速く進化するツールだという点です。設定キー名、hooksのイベント名、権限のパターン文法は、バージョンによって追加・変更・廃止され得ます。

ですから私はこの記事のすべての内容を一般的な活用原則として読んでいただくようお願いします。特定バージョンで正確にこう動作すると断定するより、こうしたカテゴリの設定が存在し、こういうふうに活用できるという方向性をつかむための用途です。実際の適用段階では必ず次を確認してください。

  • 自分がインストールしたバージョンの公式ドキュメント
  • ツール内のヘルプのスラッシュコマンドで見る現在バージョンの案内
  • 設定変更後の小さな単位での動作検証

ブログやコミュニティの記事はアイデアを得るのに優れた出発点ですが、特定バージョンの動作を断定する内容は公式ドキュメントで相互検証するのが安全です。この記事もその出発点の一つとして活用していただければと思います。

11. 結論 + すぐ適用できる3つ

Claude Codeの本当の力は、モデルそのものだけでなく、そのモデルを自分のワークフローに合わせて手なずける設定から生まれます。隠れた設定という表現は秘密を意味するのではなく、すでに存在するが多くの人が見過ごす領域を自分のものにしようという招待に近いものです。今日すぐ適用できる三つを整理します。

  • 安全なコマンドをallowに追加する: 最もよく出くわす読み取り専用プロンプトから無くすと、摩擦がすぐ減ります。
  • 繰り返しプロンプトをスラッシュコマンドにする: 毎回タイプしていた長い指示を一行コマンドに変えると、作業速度と一貫性が同時に上がります。
  • 共有設定とローカル設定を分離する: settings.jsonとsettings.local.jsonの役割を最初から分けておくと、協業の事故と機微情報の流出を構造的に防げます。

設定は一度作って終わりではなく、ツールとともに育つ生きた資産です。小さく始めて検証しながら増やしていく習慣が、結局はドキュメントの先にあるClaude Codeを自分のものにする最も確実な道です。
