gh-attachで見るGitHub添付APIの空白 - CLI自動化の回避策とその限界

ブラウザセッションを借りてIssue・PRにファイルを添付するCLIツールは何を回避し、どこまで信頼できるのか

2026年7月9日 開発・インフラ

序論: ドラッグ&ドロップだけが入口の機能

GitHubのIssueやPRにスクリーンショットを1枚貼るだけの何が難しいのかと思うかもしれない。ブラウザで画像ファイルをコメント欄に放り込めばそれで終わりだからだ。しかし、その「ドラッグして落とす」という行為が事実上この機能への唯一の正面玄関だとしたら話は変わる。2026年7月時点で、GitHubはIssue・PR・コメントにファイルを添付する公式のREST・GraphQL APIを依然として提供していない。人間がブラウザの前に座りマウスで操作しなければ開かない扉だ。

CLIでIssueを作成し、ボットがデプロイログをコメントとして残し、AIエージェントが自らPRを開く現在、この扉は明らかなボトルネックである。gh-attachはこのボトルネックを正面突破する代わりに、脇道から回避したツールだ。GeekNewsでも紹介され「まさに必要だった」という反応を得た。本稿はその反応をなぞるのではなく、このツールが実際に何を回避しているのか、自動化ワークフローでどんな価値を持つのか、そしてどこまで信頼して使えるのかを直接検討する。

1. 問題の実体 - なぜ添付APIが無いのか

1.1 ドラッグ&ドロップが実際に行っていること

ブラウザでIssueやPRのコメント入力欄に画像を放り込むと、フロントエンドのコードが即座にgithub.com/upload/policies/assetsへリクエストを送る。このリクエストが通るにはuser_sessionクッキー、つまりログイン済みのブラウザセッションが必要だ。発行されたアップロードポリシーでファイルを内部アセットパイプライン(ストレージ+CDN)に上げ、完了するとgithub.com/user-attachments/assets/{uuid}形式のリンクがコメント本文に挿入される。Issueでよく見るあの画像リンクは、まさにこの過程の結果物である。

1.2 6年近く繰り返されてきた要望

問題は、この流れが最初から最後までセッションクッキー方式だという点だ。個人アクセストークンやOAuthで認証するREST・GraphQL APIには、これに対応するエンドポイントが無い。GitHub Communityの議論には「コメントに画像をアップロードするAPIが欲しい」という要望が繰り返し投稿され、gh CLIリポジトリのあるIssueはこの空白を「エージェンティックなワークフローに決定的」という表現で再提起し、「エージェントが完璧な本文を書いても、それを裏付けるスクリーンショットは添付できない」という趣旨の事例を挙げた。この要望の系譜は2020~2021年まで遡り、当該Issue自体はさらに古い重複Issueとしてクローズされた。つまりほぼ6年間同じ要望が繰り返されているが、公式APIはまだ存在しない。

2. gh-attachは何を回避しているのか

2.1 ブラウザが既に持つセッションを借りる

sudosubin/gh-attach(Goで作成、MITライセンス)の核心アイデアはシンプルだ。ブラウザが既に持っているログインセッションをCLIが借りて使う。まずgh apiで現在認証されているGitHubアカウントと対象リポジトリを確認する。次にローカルにインストールされたChrome系・Firefox系・Safariのクッキーストアを調べ、dotcom_userクッキーの値がそのアカウントと一致するセッションを探す。

2.2 アップロードはブラウザがしていた通りに

セッションを確保すると、そのクッキーを使って/upload/policies/assetsにアップロードポリシーを要求し、ファイルのバイナリをアップロードした後アセットを確定する。ブラウザがドラッグ&ドロップの際に行う手順を、コードでそのまま再現したものだ。

2.3 結果物はWebで直接貼ったものと同一

結果として得られるURLはgithub.com/user-attachments/assets/{uuid}形式で、人が直接ドラッグしてアップロードした画像とまったく同じ種類のリンクだ。gh attach ./image.png -R owner/repoの一行でURLを受け取り、そのままIssue・PR本文に貼り付けられる。--jsonオプションでスクリプトからパースしたり、--templateで他のコマンドと連携させることもできる。ブラウザ・プロファイルの指定は~/.config/gh/attach.yml設定ファイルに保存しておけば、毎回繰り返す必要がない。

3. CLI・自動化ワークフローでの価値

3.1 スクリーンショット・ログを自動で貼るボット

最も直接的な活用法は、デプロイ失敗ログ、ビジュアルリグレッションテストのスクリーンショット、パフォーマンスグラフを人手を介さずIssue・PRに残すボットだ。これまではCIがログをアーティファクトとして残し、人間が改めて開いてキャプチャして貼るという2段階だったが、gh-attachはその間の手作業を無くす。

3.2 エージェントが自らPRを開くとき

AIコーディングエージェントがファイルを修正し自らPRを開く流れが一般的になるにつれ、そのPRに何が変わったかを示すスクリーンショットやダイアグラムを一緒に残したいという要求が生まれる。実際、gh-attachの作者もエージェントがダイアグラム・スクリーンショットを自動で添付できるようにしたくてこのツールを作ったと述べている。テキストだけのPR説明と、実際に何が変わったかを目で示すPR説明は、レビュアーにとってまったく異なる体験だ。

3.3 gh CLI拡張エコシステムの中での位置づけ

gh-attachはgh extension install owner/repoの一行でインストールされるgh CLI拡張だ。GitHubはこの拡張システムを公式ドキュメントでサポートしており、誰でもgh-で始まるリポジトリを作って配布できる。興味深いのは、同じ問題を解く拡張がgh-attach一つではないという点だ。名前まで重なる複数の独立した実装(例: enthus-appdev/gh-attach、MCPサーバーも兼ねるAddono/gh-attach)が同時に存在する。これはこのボトルネックが複数の開発者がそれぞれ突き当たるほど一般的である証拠であり、同時にまだ業界の「標準」が無いことも意味する。

4. 非公式エンドポイント依存のリスク

4.1 自動化用ツールなのに自動化環境には合わないという逆説

まず指摘すべき限界はこれだ。gh-attachは「エージェント・ボット自動化」を前面に押し出しているが、実際の動作原理はログイン済みのブラウザセッションを前提としている。ところがCIランナーやエージェントのサンドボックスの大半には、そもそもそうしたセッションが無い。自動化パイプラインでそのまま使うには、あらかじめ認証済みのブラウザプロファイルをその環境に用意しておくか、ヘッドレスブラウザにセッションをコピーしておく別途の準備が必要だ。「ボットが勝手にスクリーンショットを貼ってくれる」という絵は、この準備を終えて初めて成立し、これはこのツールを「完全自動化」ツールと誤解した際に真っ先につまずくポイントである。

4.2 いつでも壊れうる契約

/upload/policies/assetsはGitHubが公式に文書化しバージョンを保証したAPIではなく、Webフロントエンド内部用のエンドポイントだ。GitHubがアップロードの流れを変更すれば、予告なく動作が止まる可能性がある。これはスクレイピング型ツールが共通して抱える負債であり、関連する議論でもこうした回避方法は「一時しのぎ」と位置づけられ、公式API確保が長期目標として残されている。

4.3 クッキーを読み取るということの重み

ローカルブラウザのクッキーストアを読み取ることは軽い話ではない。一部のOSはキーチェーン・資格情報マネージャーへのアクセス権限を要求し、ブラウザ自体もクッキーをOSレベルで暗号化する場合がある。信頼するオープンソースツールであっても、ログインセッションのクッキーにアクセスするCLIをインストールすること自体が、セキュリティ面の露出を広げる選択であるという点ははっきり認識すべきだ。

5. 公式的な代替手段との比較

GitHub CLIコミュニティもこの問題を認識している。gh-attach式のセッション回避のほかに、トークン認証だけで済む代替案が2つ議論されてきた。

方式認証結果URL長所短所
gh-attach(セッション回避)ブラウザクッキーuser-attachments/assetsリンクWeb UIと同一の結果、即座に使用可能非公式エンドポイント、CIには別途準備が必要
gh release uploadPAT/トークンリリースアセットのダウンロードリンク公式API、トークンのみでCI動作リリース一覧が煩雑化、一時的な添付には過剰
orphanブランチ+rawリンクPAT/トークンraw.githubusercontent.comリンク公式API、リリース汚染なしファイルが履歴に恒久的に残存、自動整理されない

個人的な判断はこうだ。人が一時的に使う手動添付ならgh-attachが最も自然だ。常時稼働するCIボットが習慣的にログを残す用途なら、セッション管理の負担が無いリリースアセットの方が運用上安全だ。orphanブランチ方式は、その両方の条件を満たせない場合の折衷案程度に見ている。

結論: gh-attachは一時しのぎであり最終解ではない

gh-attachは優れた一時しのぎだ。GitHubがIssue・PR添付用の公式APIを出すまでは、この種のセッション回避ツールが出続けるほかない構造であり、名前まで重なる複数の独立実装が存在すること自体がその需要を証明している。今すぐCLIでスクリーンショットを1枚貼りたいなら、gh-attachで十分だ。

ただし、CIやエージェントのパイプラインに組み込むにはセッション準備という宿題が残っている点、そしてこのツールが依拠するエンドポイントがGitHubの意向次第でいつでも消えうる非公式な契約だという点は常に念頭に置くべきだ。本当の解決策はGitHubがトークン認証だけで済む公式アップロードAPIを出すことであり、それまではgh-attachをその空白を埋める複数の実験の一つと見るのが正確だ。
