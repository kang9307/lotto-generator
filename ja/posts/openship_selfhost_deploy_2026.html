デプロイ基盤を自分のサーバーに載せるという選択

消える費用と新たに生まれる費用は同じ通貨ではない - そしてデプロイ道具自身の復帰経路

2026-07-30 開発・インフラ

序論: 「デプロイまで自分のサーバーで」という決定は何を買うことなのか

セルフホストのデプロイ基盤を初めて見ると、たいてい同じ反応が出る。「これなら管理型を使わなくてもよさそうだ。」 画面にはリポジトリをつなげばスタックを自動的に判別し、イメージを作り、ドメインと証明書まで付けてくれる流れがある。その流れが自分のサーバーの中で回ると聞けば、魅力的に見えるのは当然である。

ところがこの決定の実際の中身は、費用をなくすことではなく費用の種類を変えることである。消える側は利用量に連動した反復支出と、特定事業者の規約への依存である。新たに生まれる側は運用責任である。OSのパッチ、バックアップとその復旧試験、証明書の更新、ビルドキャッシュが食うディスク、侵害対応、そしてほとんど言及されない項目が一つ — デプロイ基盤自体が停止したとき何でデプロイするのか。

この記事は道具の紹介ではない。順位も付けず価格も書かない。料金は頻繁に変わるので、確認した日を過ぎればすぐに誤情報になるからである。代わりに「自分のサーバーに載せる」という一文に付いてくる条件を項目として書く。出発点は最近公開されたオープンソースのプロジェクト一つである。事実確認は公式リポジトリと各構成要素の公式文書で2026年7月30日に直接行い、確認できなかった数値は書かなかった。例示ドメインはexample.com、例示アドレスは192.0.2.1で統一した。

なおどのホスティング形態を選ぶかはこの記事の範囲ではない。静的・共有・VPS・PaaSのどれを使うか分ける決定木はウェブホスティングを選ぶ基準で既に扱った。この記事はその決定がすでに「サーバーを使う」で終わった後、そこにデプロイの自動化まで載せるかどうかを扱う。

1. 出発点 - 公式リポジトリで確認されたものだけ

対象はOpenshipである。公式リポジトリはgithub.com/oblien/openshipで、自らを内蔵CI/CDを備えたオープンソースのセルフホスト可能なデプロイ基盤と紹介している。ライセンスはApache License 2.0である。ここで重要な点は、このプロジェクトがPaaSとCIのどちらか一つではなく両方を同時に置き換えようとしていることである。コードが入ってイメージになり、コンテナとして動き、外部に公開される経路と証明書までが一つのシステムの中で処理される。

リポジトリが説明する動作は五段階である。検出 → ビルド → 実行 → ルーティングと保護 → プッシュデプロイ。検出段階ではpackage.jsonとフレームワーク設定、ロックファイル、そして任意でdocker-compose.ymlやopenship.jsonを読んでスタックとビルドコマンドを判断すると書かれている。ビルド段階ではDockerイメージあるいは対象サーバー上のいわゆるベアリリースとして作り、実行段階ではコンテナまたは監督されるホストプロセスとして動かす。ルーティング段階ではOpenRestyエッジがリバースプロキシの仮想ホストを作りLet's Encryptの証明書を発行する。最後の段階はGitHubのWebhookで、追跡中のブランチにプッシュが入るとパイプラインを再実行する。

項目公式リポジトリに書かれている内容この記事で問題になる地点

確認できなかったことも明確に書いておく。公式リポジトリの文書には最小メモリ・CPU・ディスクといった要求仕様が明記されていなかった。最新リリース版の表記も見つからなかった。したがってこの記事には仕様の数値を書かない。導入を検討するなら、その値は推定ではなく自分のワークロードで直接測定すべき項目である。ビルドは特に瞬間的なメモリ使用が跳ねる作業なので、サービスが動くサーバーで一緒に動かすとき最初に問題になる資源はメモリとディスクである。

もう一つ。リポジトリはロードマップに多ノードクラスタ、ロードバランシングUI、プライベートネットワーキング、高度な監視、視覚的なCI/CDパイプラインを今後来る機能として記している。ロードマップにある項目は今はない項目という意味である。複数ノードにまたがるデプロイと精緻な監視を前提に設計を組もうとするなら、その前提がまだ道具の外にあるという事実を計算に入れる必要がある。

2. 消える費用と新たに生まれる費用は同じ通貨ではない

セルフホストの議論がよく空回りする理由は、二種類の費用を同じ単位で比べるからである。一方は毎月数字で届く請求書であり、他方は人の時間と障害のリスクである。後者は平時にはゼロに見え、障害が起きた日にまとめて請求される。

区分消えるか減るもの新たに生まれるものこの項目が現れる時点

依存基盤固有の規約への依存自分の構成への依存(自作の囲い込み)担当が変わるか文書がないとき
上限ビルド回数・帯域のような計測上限物理資源の上限(ディスク・メモリ・IOPS)ビルドが集中する時刻に突然

表の右側の列がこの記事の実質的な主題である。そして右側の列には規模に比例しない項目が多い。サービスが一つでも十でもOSのパッチは同じ周期で回ってくるし、証明書の更新も同じ周期で回ってくる。だから小さな規模でのセルフホストは単位あたりの運用費が最も悪い形になりやすい。この構造はセルフホスト自体を否定する根拠ではなく、どの規模から有利になるかを計算すべきだという根拠である。

3. 新たに生まれる運用項目 - 請求書が来ない側

以下はデプロイ基盤を自分のサーバーに載せたとき、その日から自分の業務になる一覧である。各項目は「誰がやるのか」と「失敗をどう知るのか」を併せて決めて初めて完結する。二つのうち一つでも空いていれば、その項目はまだ存在しない。

  • OSとランタイムのパッチ — コンテナランタイム、データベース、エッジプロキシがそれぞれの保安更新周期を持つ。自動更新を入れれば予告なしの再起動を受け入れ、切れば溜まったパッチを受け入れることになる。どちらにしても定期的に見る仕事が残る。
  • ディスクの余裕 — デプロイ基盤はイメージ、ビルドキャッシュ、ログ、データベースを同時に積み上げる。ディスクが満杯になる瞬間、ビルドだけが失敗するのではなくデータベースの書き込みまで塞がれる。後で個別に扱う。
  • バックアップと復旧試験 — バックアップ機能があることと復旧ができることは別の事実である。一度も戻したことのないバックアップは、障害当日に初めて実行する未検証の手順である。
  • シークレット管理 — 環境変数とデプロイ鍵が基盤の中だけにあると、基盤が止まったときデプロイに必要な値も一緒に閉じ込められる。別保管が必要である。
  • 証明書更新と失敗検知 — 自動更新を仕込むことと更新の失敗を知ることは別個の作業である。両方あって初めて体制が完成する。
  • Webhook受信点の保護 — 外部から入る要求でビルドが動くということは、その経路が実行のトリガであるという意味である。
  • ビルド実行の隔離 — ビルドはリポジトリのコードと依存関係のインストールスクリプトを実行する。それがどの権限でどこで動くかがそのままリスクの大きさである。
  • 監視と夜間通知 — プロセスが止まったのに誰も知らない状態が最も多い長期障害である。外部から接続を確認する監視が別途必要である。
  • ログの保存と回転 — ログがなければ原因が分からず、放置すればディスクを埋める。保存期間と回転周期を数字で決める必要がある。
  • 侵害対応の手順 — ビルドサーバーが他人の道具として使われ始めたとき何から切るかを事前に決めていなければ、その夜の判断はたいてい最悪になる。
  • 変更履歴 — 基盤の設定とサービス定義がどこに記録されるか。画面だけで変えた設定は再構築のとき存在しないのと同じである。
  • ブートストラップ手順 — この一覧で最も頻繁に抜ける項目であり、次章の主題である。

この一覧を読んで「それでもほとんど自動化すればよいのでは」と思うなら半分は正しい。自動化は可能だが、自動化が失敗したときそれを知る仕掛けがなければ、自動化はむしろリスクを大きくする。静かに失敗するバックアップが、まったくないバックアップより悪い理由と同じである。

4. 最も抜け落ちるもの - デプロイ道具自身の復帰経路

ここがこの記事の核である。管理型の基盤を使うときはデプロイ基盤が止まる状況を想像する必要がない。止まれば事業者が直す。セルフホストに移った瞬間その状況は実在するシナリオになり、よりによってサービスに緊急修正が必要な瞬間と重なる確率が低くない。ディスクが満杯の状態でビルドが失敗し、そのためロールバックもデプロイもできない状態が典型的な形である。

構成要素ごとに「止まれば何が止まるのか」と「何で復帰させるのか」を事前に分けておけば、このシナリオはずっと危険が小さくなる。Openshipのリポジトリが明かしたセルフホストのスタック構成要素を基準に整理するとこうなる。

構成要素止まれば何が止まるのか復帰の手段事前に用意しておくもの
エッジプロキシ(80・443)外部からサービスに届く経路のすべて最小のリバースプロキシを自分で立てて迂回仮想ホスト設定と証明書ファイルの控えの置き場所
基盤のAPI・ダッシュボード新規デプロイとロールバックの操作コンテナをランタイムのコマンドで直接実行現在稼働中のイメージタグの一覧
メタデータのデータベースサービス定義・履歴・設定の参照バックアップから復元、または定義をコードから再生成サービス定義をリポジトリにも残しておくこと
キャッシュ層キューやセッションに依存するパイプラインの動作再起動後に再試行、必要ならキャッシュを初期化キャッシュ喪失がデータ喪失でないかの確認
コンテナランタイムすべてのコンテナ、つまり基盤とサービスが同時にランタイムの復旧後、再起動方針に従って自動起動再起動方針を構成要素ごとに明記
ホストのディスクビルド・ログ・DB書き込みのすべて整理して再起動、または別ホストへ移設空き容量のしきい値通知と整理コマンドの一覧

表の最後の列が実際に用意すべきものである。そしてこの用意物はほとんどが基盤の外にあって初めて意味がある。デプロイ基盤が止まった状況で必要な情報がデプロイ基盤の中だけにあれば、その情報はないのと同じである。

再起動方針は特に細部が結果を変える。Docker公式文書は四つの再起動方針を定義する。noは自動再起動をしない既定値であり、on-failureはゼロでない終了コードで終わったとき再起動するがデーモンが再起動してもコンテナを再起動しないと書かれている。alwaysは止まれば常に再起動するが、人が直接止めた場合はデーモンが再起動するときあるいは人が再び起動するときにだけ復活する。unless-stoppedはalwaysと似ているが、止まったコンテナはデーモンが再起動した後でも復活しない。同じ文書は再起動方針を使い、ホストレベルのプロセス管理器でコンテナを起動する方式は避けるよう勧め、二つを併用すると衝突が生じると記している。また再起動方針はコンテナが正常に起動して少なくとも10秒以上上がっていて初めて効力が生じると明かしている。

この違いがなぜ重要なのか。点検のために人が止めておいたコンテナがサーバー再起動後に自動で復活することを期待していたのか、それとも復活しないことを期待していたのかによって正解が違うからである。デプロイ基盤のデータベースとエッジは再起動後に必ず上がるべき側であり、実験用に立てておいたコンテナはそうではない。この区別を方針として書いておかなければ、再起動一回がそのまま障害になる。

# ブートストラップの手順書に書いておくこと - 値はすべて例である
# 1) 復帰させる対象と最小情報
EDGE_HOST=192.0.2.1
APP_DOMAIN=example.com
CURRENT_IMAGE=<現在の本番イメージタグ>

# 2) デプロイ基盤なしでサービスだけを直接起動する最小経路
docker run -d --restart unless-stopped \
  --name fallback-app -p 8080:8080 \
  --env-file /root-of-secrets/<サービス名>.env \
  "$CURRENT_IMAGE"

# 3) エッジの代わりになる最小プロキシ規則 (山括弧は実際の値に置換)
#    https://<サービスのドメイン>/  =>  http://<内部アドレス>:8080
#
# 4) この手順を実際に実行した日付をここに書く。
#    書かれていなければそれは計画ではなく願望である。

ブートストラップ手順で最もよくある抜けはシークレットである。上の例で--env-fileが指す値が基盤のデータベースの中だけにあったなら、そのファイルを作れず手順が一行目で止まる。だからシークレットはデプロイ基盤と別の場所にもう一部なければならない。これは利便性の問題ではなくブートストラップの前提条件である。

5. 再起動方針を構成要素ごとに書く

前章の原則を構成に移すと、結局宣言ファイルに方針が書かれているかの問題になる。画面で一度押しておいた設定は再構築のとき消え、ファイルに書かれた方針は残る。Composeの形でスタックを上げる場合なら次の程度が最小線である。Compose自体の使い方はDocker Composeの回で個別に扱った。

# デプロイ基盤の構成要素ごとに再起動方針を明記する - 値は例である
services:
  api:
    image: <基盤のAPIイメージ>
    restart: unless-stopped
  db:
    image: postgres:<バージョン>
    restart: unless-stopped
    volumes:
      - <データボリューム>:/var/lib/postgresql/data
  cache:
    image: redis:<バージョン>
    restart: unless-stopped
  edge:
    image: <エッジのイメージ>
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - <証明書ボリューム>:/etc/letsencrypt

# 確認事項
# - 証明書ボリュームがホストのバックアップ対象に入っているか
# - dbボリュームがバックアップ対象で、復元を試したことがあるか
# - 人が止めたコンテナが再起動後に復活すべきかを決めたか

ここでもう一つ。証明書ボリュームはバックアップ対象の一覧からよく抜ける。データベースは誰でもバックアップ対象として思い浮かべるが、証明書とエッジの設定は「どうせ再発行すればよい」と流しやすい。ところが障害当日に発行手順を最初からやり直すのは、復旧時間を延ばす最も確実な方法である。発行の手順自体は無料SSL証明書の発行と適用で段階別に扱った。

6. ビルドキャッシュとディスク - 静かに育つ障害原因

セルフホストのデプロイ基盤で最も多い最初の障害は侵害ではなくディスクである。理由は単純である。ビルドはキャッシュを残し、キャッシュは速くなるために存在するので、基本的に消えない方向で設計される。そして同じホストにデータベースがあれば、ディスクが満杯になる瞬間ビルド失敗で終わらずデータ書き込みの失敗に広がる。

Docker公式文書はビルドキャッシュの整理について具体的に記している。BuildKitデーモンはキャッシュの大きさが大きすぎるかキャッシュの寿命が過ぎるとビルドキャッシュを整理するという記述とともに、既定の方針が順に評価されると説明している。方針は四つである。容易に再生成できるキャッシュを48時間以上使っていなければ除去し、ビルドに60日以上使われていないキャッシュを除去し、共有されていないキャッシュが大きさの上限を超えれば除去し、最後に大きさの上限を超えるビルドキャッシュを除去する。Dockerドライバの場合defaultKeepStorageの既定値は20GBと書かれている。

BuildKitの設定側の既定値も同じ文書に出てくる。reservedSpaceは全体ディスクの10パーセントまたは10GBのうち小さい値、maxUsedSpaceは全体ディスクの60パーセントまたは100GBのうち小さい値、minFreeSpaceは20GBである。そして二つの値が併せて設定されると、整理後のキャッシュの大きさがその二つのしきい値の間に置かれると説明している。

ここで実務的に読むべきことは数値そのものではなく比率ベースの既定値が小さなディスクでどう働くかである。全体ディスクの60パーセントまでキャッシュが育ちうるという規則は余裕のあるディスクでは合理的だが、サービスとデータベースが同じボリュームを使う小さなサーバーでは他のプロセスが使う領域を予約しておかないという意味にもなる。だからデプロイ基盤をサービスと同じディスクに載せるときは二つのうち一つが必要である。ビルドキャッシュの上限を明示的に下げるか、ビルド用のボリュームを分離することである。

  • 空き容量のしきい値を先に決める — 何パーセントではなく何GBで決めるほうが安全である。パーセントはディスクが大きくなると意味が薄れる。
  • 通知を人につなぐ — しきい値を超えたという事実をダッシュボードだけで見せると、そのダッシュボードが開かない状況では役に立たない。
  • 整理コマンドを事前に決めておく — 障害当日に何を消してよいか判断しようとすると、必ず消してはいけないものを消す。
  • ビルドのボリュームを分離する — データベースとビルドキャッシュが同じボリュームを共有しないようにするのが最も確実な防御である。
  • ログも同じ問題を作る — コンテナのログとビルドのログの保存期間を決めなければ、キャッシュよりログが先にディスクを埋める場合もある。
  • イメージのタグが積もる — デプロイごとに新しいタグができるとイメージの保存領域が線形に増える。保管する世代数を決める必要がある。

# ビルドキャッシュだけを見て、48時間以上使われていないものから整理する
docker buildx du
docker builder prune --filter until=48h

# ホスト側でどこが埋まっているかを上位の経路から絞る

7. Webhookとビルド実行が作る新しい攻撃面

プッシュすると自動でデプロイされる流れは便利だが、構造をもう一度見ると外部から入った信号で自分のサーバーでコードが実行される経路である。この一文をそのまま読めば、なぜ慎重であるべきかがすぐ見える。

このリスクはセルフホストのデプロイ基盤だけの問題ではなく、自分のインフラでビルドを回すすべての構成が共有する問題である。GitHub公式文書はセルフホストのランナーについて明確な警告を記している。セルフホストのランナーは非公開リポジトリでのみ使うことを勧めるというもので、理由は公開リポジトリのフォークがワークフローでコードを実行するプルリクエストを作り、セルフホストのランナーマシンで危険なコードを実行しうるからと述べている。同じ論理が自作のビルドシステムにも当てはまる。ビルドがリポジトリのスクリプトを実行する限り、そのリポジトリにコードを入れられる人は自分のサーバーでコマンドを実行できる人である。

  • 公開リポジトリと自作ビルドを混ぜない — 外部の貢献を受けるリポジトリのビルドを自分のサーバーで回す構成は、特別な隔離なしでは危険である。
  • ビルドごとにきれいな環境を与える — 前のビルドが残したファイルが次のビルドに影響すると、一度の汚染がずっと続く。
  • ビルドの権限を最小に下げる — ビルドがホスト全体を見られる権限で動けば、ビルドスクリプト一つがそのままホストの権限である。
  • Webhookには署名の検証を要求する — 受信点がインターネットに開いているなら、送った側が本物か確認する手順なしにパイプラインを回してはならない。
  • 制御プレーンを公開露出から外す — Openshipのリポジトリがデスクトップアプリのモードを制御プレーンがローカルであり公開露出がないと説明するように、管理画面をインターネットに置かない構成が可能ならそちらのほうが面が小さい。
  • 脆弱性の届け出経路を確認する — 同じリポジトリは脆弱性を公開のissueやPRではなく非公開で届けてほしいと求め、セキュリティ勧告の機能を優先経路として案内している。道具を導入するときこうした手続きが整っているかは成熟度の合図として読む価値がある。
  • ビルドログにシークレットを残さない — リアルタイムのログを見せる機能は便利だが、そのログを見られる人の範囲がそのままシークレットの露出範囲になる。
# 何が外部に開いているかをまず数える
ss -ltnp | grep -E ':(80|443)\b'

# ビルドがどのユーザー権限で動くか確認する

docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}'

# 管理画面が公開アドレスで応答するか自分で叩いてみる
curl -sS -o /dev/null -w '%{http_code}\n' https://example.com/<管理の経路>/

8. 証明書とエッジ - 自動化の失敗を検知する層

デプロイ基盤が証明書を自動で発行してくれることは大きな利便である。ただしその利便は発行についてのものであり、運用で問題になるのは更新である。Let's Encrypt公式FAQは既定の証明書が90日間有効であると明かし、6日間の短期証明書を選べると記している。更新の勧めは90日の証明書は60日ごと、6日の証明書は3日ごとである。そしてこの有効期間を調整する方法はなく例外もないと断言している。同じ文書はACMEクライアントが決まった時刻ではなく無作為の時刻に定期更新を行うと説明している。

これらの事実をセルフホストの文脈に移すと結論は一つである。更新は自動でなければならず、自動更新の失敗は人に届かなければならない。管理型の基盤では後半が事業者の担当だったが、いまは自分の担当である。そして更新の失敗は静かに起きる。失敗した日には何も起きず、数日後に満了する日に全面障害として現れる。

失敗の型表に見える症状よく見落とす理由検知の方法
更新の処理そのものが動かなかった満了日まで何の症状もない成功ログだけ確認し不在は確認しない最後の更新時刻が基準より古ければ失敗として扱う
検証が失敗したログにだけエラー、サービスは正常通知がダッシュボードの中にだけ残る更新処理の終了コードを外部通知へ渡す
新しい証明書が反映されなかったファイルは更新されたのに応答は古い証明書エッジの再読込の段階を個別に確認しない実際に応答する証明書の満了日を外部から確認
証明書のボリュームがバックアップにない復旧後に証明書だけが消えるデータベースだけをバックアップ対象と考える復旧試験の項目に証明書の確認を含める
ドメイン変更とすれ違った一部のホストだけ証明書エラー仮想ホストの一覧と証明書の一覧が別に管理されるサービスのドメイン一覧を基準に一括点検

9. やってよい条件とやめるべき合図

「よい道具か」は答えにくい問いであり、「我々がいまこれを担えるか」は答えられる問いである。以下の条件は道具の品質ではなく組織の準備状態についてのものである。

  • サービス停止の許容時間が決まっている — 何分まで大丈夫か数字で答えられる必要がある。答えがなければ復旧設計の基準もない。
  • 夜間と週末の対応経路がある — 通知が誰の携帯に行き、その人が接続できないとき次が誰かが決まっている必要がある。
  • 運用できる人が二人以上いる — 一人だけならその人の休暇と離職がそのまま可用性のリスクになる。
  • バックアップから復旧を実際にやってみた — 時点を記録として残せる必要がある。「機能はあります」は答えではない。
  • ブートストラップ手順を実行してみた — 基盤なしでサービスを上げる経路を一度は踏んでいる必要がある。
  • ビルドがサービスと資源を争わない — 同じホストに置くのか、ボリュームを分けるのかが設計段階で決まっている必要がある。
  • 設定がファイルとして残る — 画面操作だけで維持される構成は再構築が不可能な構成である。

逆に以下の合図が見えるならいまではない。この合図は道具を変えて解決するものではなく、準備状態を変えて解決するものである。

  • 運用担当が一人である — デプロイ基盤が止まる日にその人が接続不能なら代案がない。
  • バックアップ復旧を一度も試していない — この状態でのセルフホストはバックアップがないのと実質的に同じである。
  • 夜間障害を認知する経路がない — 朝に知る障害は夜通し続いた障害である。
  • ディスクの余裕を誰も見ていない — 前に見たとおり最初の障害はたいていここから来る。
  • 公開リポジトリのビルドを自分のサーバーで回す計画である — 隔離の設計がなければこの組み合わせは避けるべきである。
  • シークレットが基盤の中だけにある — ブートストラップが構造的に不可能な状態である。
  • 導入理由が費用削減だけである — 削減額が運用時間の価値より小さければ計算はすでに合っていない。

ここで一つ誤解を整理しておく必要がある。セルフホストが高いという主張ではない。規模と準備状態によって有利な地点が違うという主張である。セルフホストの費用構造を別種のワークロードで検討した事例はセルフホストのAIワークスペース側で扱ったが、そこでも結論の形は同じだった。実際の費用は料金表ではなく資源と人の時間から出る。

10. 移行コスト - ここから出るとき何が縛られているのか

導入を検討するときほとんど誰も計算しない項目が出て行く費用である。そしてこの費用はオープンソースだという事実だけでゼロにはならない。ライセンスが自由であることと移行が容易であることは別の問題である。

縛られる地点移行が難しくなる理由事前に減らす方法
ビルド設定基盤が自動検出した規則が文書化されていない仕様になるビルドコマンドと成果物の定義をリポジトリ内のファイルに明記
シークレット値が基盤の保管領域にだけあり一覧すら再現できない鍵の名前一覧と値の保管場所を基盤の外に二重化
ドメインと証明書発行・更新の自動化がエッジに縛られている発行方式を標準のACMEで維持し切替前にキャッシュ時間を下げる
データ書き出し形式と再投入の時間がそのまま停止時間標準形式の定期書き出しと復元試験を周期化
サービス定義ダッシュボードだけで作った設定はコードにないサービス一覧・ポート・ボリューム・環境を宣言ファイルで管理
イメージの保存場所基盤の内部保管領域にだけイメージがある標準のレジストリにも併せて押しておく

表から確認できる規則は一つである。囲い込みは契約書ではなく設計から生まれる。利便機能を多く使うほど、その利便が代わりに下してくれた決定が文書から消え、出るときにその決定を人が改めて下すことになる。だから自動検出のような機能は使うが結果をファイルに固定するほうが安全である。成果物が標準のコンテナイメージである点は確かに有利な条件だが、イメージだけがあってそのイメージをどう起動したかの記録がなければ、移行は依然として書き直しになる。

データベースのバックアップと復旧を個別の主題として扱った記事もある。バックアップの対象と周期、復旧試験をセルフホスト環境でどう設計するかはセルフホストのデータベースバックアップ側を併せて見るとよい。

11. 判断表 - 状況から選択へ

ここまでの内容を一つの表に圧縮する。左で自分の状況に最も近い行を探し、右のまず確認することまで併せて読むのがこの表の使い方である。どちらが優れているという判定はない。

状況傾けてみる方向まず確認すること
文書・ブログのようにサーバー側ロジックがないサイト静的ホスティングサーバーで実行されなければならないコードが本当にないか
一人で作るサイドプロジェクト、夜間対応なし管理型停止の許容時間を数字で決められるか
運用担当1名、バックアップ復旧の経験なし管理型復旧を一度試したうえで改めて判断すること
サービス数が増えデプロイの頻度が高くなった管理型またはセルフホストビルドがサービスの資源を侵さない構成か
データの所在を自分の統制下に置く必要があるセルフホストバックアップの場所と保存期間、復旧時間の目標
すでにサーバーを運用し当直体制があるセルフホストブートストラップ手順を実際に実行してみたか
公開リポジトリで外部の貢献を受ける管理型または隔離されたビルドフォークのコードが自分のホストで実行されないか
サービスの等級が高く停止がそのまま損害であるセルフホストは冗長化が前提単一ノード構成が許容できるリスクか
デプロイの自動化だけ必要でサーバー運用は避けたい管理型CI + 管理型の実行環境二つのシステム間のシークレットの受け渡し経路
内部網でだけ使う道具をデプロイするセルフホスト制御プレーンを公開露出から外せるか
費用削減が唯一の導入理由である判断を保留削減額と運用時間の価値を同じ表に書いて比較

表で「セルフホスト」が推奨として出た行をもう一度見ると共通点がある。すでにサーバー運用をしている組織か、データの所在のように金で買えない要求がある場合である。逆に「管理型」が出た行の共通点は人の時間と対応体制が足りない場合である。道具の品質ではなくこの条件が結論を分ける。

結論: セルフホストは節約ではなく交換である

デプロイ基盤を自分のサーバーに載せる決定は悪い決定ではない。ただしそれが何と何を交換する取引なのかを正確に知って行うべきである。

  • 消えるのは利用料とベンダー依存である — 計測上限に合わせて設計する必要が減り、成果物が標準のコンテナなら移動の可能性も残る。
  • 新たに生まれるのは運用責任である — パッチ、ディスク、バックアップと復旧試験、証明書更新の失敗検知、Webhookとビルド実行の隔離、侵害対応が一束で来る。
  • 最もよく抜ける項目はブートストラップである — デプロイ基盤が止まったとき何で復帰させるかに答えがなければ、利便のために導入した道具が単一障害点になる。
  • 判断の基準は道具ではなく準備状態である — 停止の許容時間、当直体制、復旧試験の経験。この三つが答えを決める。

最後に姿勢をもう一度書く。セルフホストを無条件に勧める記事も、無条件に危険だと脅す記事も助けにならない。必要なのは各選択に付いてくる項目を漏らさず数える仕事である。だからこの記事には金額を書かず、要求仕様のように公式文書で確認できなかった数値はまったく使わず、数値を書いた場所には根拠の文書を併せて残した。その文書は変わる。導入を決める日には自分で改めて開くこと以外に安全な方法はない。
