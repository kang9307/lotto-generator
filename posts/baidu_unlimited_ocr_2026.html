페이지 단위 한계를 넘어, 40페이지+ 문서를 단일 패스로 파싱하는 R-SWA 아키텍처의 의미와 실무 활용 분석

2026-06-25 IT/기술

서론: 왜 OCR은 항상 페이지 단위였나

2026년 6월, Baidu가 Unlimited OCR을 공개했다. 제목이 다소 마케팅적으로 들릴 수 있지만, 기술적으로 이 모델이 해결하려는 문제는 꽤 구체적이고 오래된 것이다. OCR(광학 문자 인식)이 왜 항상 "페이지 단위"로 쪼개서 처리해야 했는지, 그리고 그 한계를 어떻게 아키텍처 수준에서 건드렸는지가 이 발표의 핵심이다.

문서 AI가 실무에서 쓰이는 방식을 생각해보면 문제가 금방 보인다. 계약서, 논문, 재무 보고서를 AI로 처리할 때 가장 먼저 하는 작업이 OCR이다. 그런데 이 단계에서 이미 손실이 생긴다. 기존 LLM 기반 OCR 모델들은 문서를 페이지 단위로 잘라 처리하고 나중에 이어 붙이는데, 바로 이 "이어 붙이는 지점"에서 오류가 누적된다. 표가 페이지 경계에 걸쳐 있으면 깨지고, 다단 레이아웃은 순서가 뒤섞이고, 문맥이 이어지는 문단은 둘로 잘린다. Unlimited OCR은 이 이어 붙이기 자체를 없애는 방향을 택했다. 2026년 6월 기준, 이 접근이 어디까지 유효한지 정직하게 분석한다.

1. 기존 OCR의 구조적 한계 — KV 캐시 선형 증가 문제

최근 OCR 트렌드는 규칙 기반 엔진에서 LLM 기반 end-to-end 모델로 이동했다. DeepSeek OCR 같은 모델이 그 흐름을 대표한다. 이미지를 입력하면 텍스트를 바로 생성하는 방식으로, 레이아웃·수식·표까지 함께 처리할 수 있다는 장점이 있다.

그런데 LLM 기반 디코더에는 구조적 비용이 있다. 텍스트를 생성할수록 이전 토큰들에 대한 KV 캐시(Key-Value Cache)가 쌓인다. 이 캐시가 메모리를 차지하고, 각 생성 단계에서 점점 더 많은 연산이 필요해진다. 짧은 문서라면 문제없지만, 수십 페이지짜리 보고서를 한 번에 넣으면 메모리가 급증하고 생성 속도가 급락한다. 논문의 측정에 따르면 6,000토큰 출력 기준에서 기존 방식은 약 35%의 처리량 저하를 보인다.

이 문제의 전통적 해법은 문서를 잘라서 처리하는 것이었다. 페이지별로 나누거나 고정 토큰 수 단위로 슬라이딩 윈도우를 적용한다. 그런데 이 방식은 "조각을 나눠 처리한 뒤 결과를 합칠 때" 반드시 오류가 생긴다. 페이지 경계에 걸린 표, 이어지는 문단, 각주와 본문의 연결이 모두 취약 지점이다. Unlimited OCR은 이 구조 자체를 다시 설계하는 길을 선택했다.

2. R-SWA — KV 캐시를 상수로 만드는 아이디어

Reference Sliding Window Attention(R-SWA)이 Unlimited OCR의 핵심 기술이다. 사람이 책을 필사할 때의 작업 방식을 모방한 설계라고 논문은 설명한다. 사람은 원본 텍스트를 눈으로 보면서, 방금 쓴 몇 글자만 기억하고, 훨씬 앞에서 쓴 내용은 흘려보낸다. 필요할 때 원본을 다시 보면 되니까.

R-SWA는 이 방식을 어텐션 메커니즘으로 구현한다. 각 생성 단계에서 모델은 두 가지를 참조한다. 첫째는 시각 토큰 전체(입력 이미지를 인코딩한 참조 집합)이고, 둘째는 직전 128개 출력 토큰만이다. 시각 토큰은 전체 디코딩 과정에서 항상 접근 가능하고, 출력 어텐션 창은 슬라이딩하며 뒤로 밀려난 토큰은 점진적으로 "잊힌다". 이 덕분에 KV 캐시 크기가 출력 길이에 따라 커지지 않고 상수로 유지된다.

중요한 설계 선택이 하나 더 있다. 논문은 기존 DeepSeek OCR의 시각 인코더를 그대로 동결(freeze)하고 언어 디코더의 어텐션 레이어만 R-SWA로 교체했다고 밝혔다. 이는 처음부터 새로 훈련하는 것이 아니라 기존 강력한 시각 인코딩 능력을 보존하면서 디코더 부분만 수술한 전략이다. 논문 표현을 빌리면 "표준 어텐션 전체를 R-SWA로 교체하는 것이 효과적이고 손실이 없다"고 한다.

2.1 모델 사양

2026년 6월 공개 기준 사양은 다음과 같다. 파라미터는 3B 총량, 500M 활성의 MoE(Mixture of Experts) 구조다. 최대 컨텍스트는 32,768 토큰이며, 추론 해상도는 gundam(640, 속도 우선)과 base(1024, 레이아웃 정밀도 우선) 두 가지를 지원한다. 라이선스는 MIT로 완전 무료·상업 활용 가능이다.

2.2 성능 수치

OmniDocBench v1.6에서 93.92%를 달성해 end-to-end SOTA를 기록했다. 비교 기준인 DeepSeek OCR의 87.01%(v1.5 기준)보다 6%p 이상 높다. 40페이지 이상 문서에서 편집 거리(edit distance)를 0.11 미만으로 유지했다는 수치도 제시됐다. 단, OmniDocBench의 버전 차이(v1.5/v1.6)를 직접 비교할 때는 주의가 필요하다. 벤치마크 자체가 업데이트됐기 때문이다. 여기선 수치를 방향 지표로 읽는 것이 적절하다.

3. 기존 OCR과 무엇이 달라지나 — 표·레이아웃·다단 문서

기술적 메커니즘보다 실무자에게 중요한 질문은 "그래서 실제로 무엇이 달라지냐"이다.

3.1 표(Table) 처리

표는 기존 OCR의 고질적 약점이었다. 페이지 단위 처리에서 표가 두 페이지에 걸쳐 있으면, 각 페이지의 결과를 합쳐도 원래 표 구조가 복원되지 않는다. Unlimited OCR은 문서 전체를 단일 컨텍스트 안에서 처리하므로, 페이지 경계를 넘어 연속하는 표를 하나의 구조체로 인식할 수 있다. 수식 추출에서도 6%p+ 향상이 보고됐다.

3.2 다단 레이아웃

학술 논문처럼 두 단(column) 레이아웃은 OCR에서 읽기 순서가 자주 뒤섞인다. 왼쪽 단 첫 문단 다음에 오른쪽 단 첫 문단이 와야 하는데, 좌우 위치만 보고 순서를 결정하면 오른쪽 단 내용이 왼쪽 단 사이에 끼어들기도 한다. Unlimited OCR은 전체 페이지 구조를 시각적으로 파악하며 디코딩하므로 이 문제가 개선된다. 단, 모든 레이아웃 유형에서 완벽하다는 독립 검증은 아직 없으므로 본인 문서 유형으로 직접 검증하는 것이 필요하다.

3.3 반복 억제

장문 생성의 고질적 문제 중 하나가 헤더·바닥글·표 행 같은 반복 요소에서 모델이 루프에 빠지는 것이다. Unlimited OCR은 DeepSeek OCR로부터 상속한 ngram 기반 반복 억제 메커니즘을 강화해, 슬라이딩 윈도우 전체에 걸쳐 제약을 적용한다. 수백 페이지 문서에서 이 메커니즘이 특히 중요해진다고 논문은 지적한다.

4. 중국어 처리 강점 — Baidu라는 배경

이 모델이 중국어 문서에서 강점을 가질 것이라고 보는 이유는 단순히 중국 기업이 만들었기 때문이 아니다. Baidu는 중국 최대 검색 엔진으로, 수십 년간 중국어 문서를 처리해 온 인프라와 데이터 역량을 보유한다. 이 배경이 학습 데이터와 모델 설계에 반영될 가능성이 높다.

중국어 문서는 OCR 관점에서 특수한 도전이 있다. 한자 자체의 복잡도, 간체·번체 혼재, 세로쓰기, 한자-알파벳 혼용 표기, 중국어 특유의 표 구성 방식이 그것이다. OmniDocBench는 중국어·영어 혼합 문서를 포함한 벤치마크이며, 여기서 SOTA를 기록한 것은 중국어 문서 파싱 능력의 간접적 지표다. 다만 특정 도메인(예: 법률 한자어, 고문)에서의 성능은 별도로 검증해야 한다.

또 하나 주목할 점은 모델의 적용 범위다. 논문은 R-SWA를 "범용 파싱 어텐션 메커니즘"으로 설계했다고 밝힌다. OCR 외에도 음성 인식(ASR), 번역, 멀티모달 처리 등 "원본 참조를 유지하면서 긴 출력을 생성해야 하는" 모든 작업에 적용 가능하다. 이는 단순 OCR 도구가 아니라 문서 AI 인프라 레이어가 될 수 있다는 시사다.

5. RAG 파이프라인에서의 위치 — 데이터 품질의 기초

RAG(Retrieval-Augmented Generation)가 기업 AI 도입의 핵심 패턴이 된 지금, 문서 전처리 품질이 전체 시스템 성능을 좌우한다. LLM이 아무리 강력해도 입력 텍스트가 엉망이면 답변도 엉망이 된다. 여기서 Unlimited OCR의 위치가 분명해진다.

5.1 파싱 단계 오류가 미치는 영향

기존 파이프라인에서 OCR 결과의 오류는 뒤 단계로 그대로 전파된다. 표가 평탄화되면 청킹(chunking) 단계에서 표 셀 하나가 독립된 청크로 떨어져 나간다. 레이아웃 순서가 뒤섞이면 임베딩된 의미가 왜곡된다. 이렇게 오염된 청크가 인덱싱되면 검색 결과도 오염된다. Unlimited OCR이 파싱 단계에서 구조를 더 잘 보존한다면, 이 오류 전파를 줄일 수 있다.

5.2 자체 호스팅의 이점

RAG 파이프라인에 유입되는 문서는 대부분 내부 기밀 자료다. 계약서, 재무 보고서, 연구 자료를 외부 API로 보내는 것에는 데이터 보안 부담이 따른다. Unlimited OCR은 MIT 라이선스 오픈소스로 내부 인프라에서 완전히 자체 호스팅이 가능하다. 문서가 외부로 나가지 않으면서도 SOTA급 파싱 품질을 얻을 수 있다는 점이 기업 도입의 핵심 유인이다.

5.3 파이프라인 통합 방식

실무 통합 경로는 두 가지다. HuggingFace Transformers 방식은 Python에서 직접 호출하는 가장 단순한 형태이고, SGLang 서버 방식은 OpenAI 호환 API를 제공해 기존 LLM 클라이언트를 그대로 재활용할 수 있다. PDF 입력은 PyMuPDF로 300DPI 이미지로 변환 후 처리한다. 배치 처리(infer_multi())도 지원해 대량 문서 처리에도 적용 가능하다.

6. 경쟁 지형 — Document AI의 현주소

Unlimited OCR이 등장한 시장에는 이미 여러 경쟁자가 있다. 직접 비교를 위한 표를 정리한다. 단, 벤치마크 버전 차이와 측정 조건 차이가 있어 수치는 방향 지표로만 참고할 것을 권한다.

7. 한계와 솔직한 유보

장점만 나열하는 것은 부정직하다. 솔직히 짚어야 할 한계가 있다.

7.1 "AI OCR의 지어낸 결과물" 문제

LLM 기반 OCR의 공통 위험은 모델이 이미지에 실제로 없는 텍스트를 생성할 수 있다는 점이다. 기존 규칙 기반 OCR은 "있는 것을 인식하지 못할" 수는 있어도 "없는 것을 만들어내지"는 않는다. LLM 기반은 반대로 확률적 생성 과정에서 환각이 섞일 수 있다. 특히 저화질 이미지나 손상된 문서에서 이 위험이 커진다. GeekNews 토론에서도 실사용자들이 이 점을 지적했다. 프로덕션 환경에서는 신뢰도 임계값 설정이나 이중 검증이 필요하다.

7.2 32K 토큰 한계

최대 컨텍스트가 32,768 토큰이라는 점은 "Unlimited"라는 이름과 다소 어색하다. 이는 40페이지+ 수준을 충분히 커버하지만, 수백 페이지짜리 두꺼운 보고서나 법률 서류는 여전히 분할 처리가 필요할 수 있다. 이름이 시사하는 것처럼 진짜로 무제한은 아니며, 실제 문서 규모에 맞는 적용 범위 확인이 필요하다.

7.3 하드웨어 요구와 최적화 성숙도

CUDA 12.9 등 최신 환경이 요구되고, 1024 해상도(base 모드)에서 긴 문서를 처리하면 GPU 메모리 요구가 상당하다. 2026년 6월 현재 이제 막 공개된 모델로, 커뮤니티 최적화(양자화, 경량화)가 아직 축적되지 않았다. 실제 배포 전에 본인 하드웨어 스펙에 맞는 성능 테스트가 필수다.

8. 의미 — Document AI의 방향 신호

Unlimited OCR이 보여주는 것은 단순히 "OCR 성능이 좋아졌다"가 아니다. 문서를 처리하는 단위의 철학이 바뀌고 있다는 신호다.

기존 파이프라인에서 문서는 항상 페이지나 청크 단위로 쪼개졌다. 이는 인프라 제약에서 비롯된 설계였지, 문서의 의미론적 구조에서 나온 선택이 아니었다. 문서는 본래 전체로서 의미를 가진다. 표는 맥락이 필요하고, 레이아웃은 논리 구조를 담고, 절(section) 간의 참조는 전체를 봐야 이해된다. R-SWA는 그 인프라 제약을 완화하는 한 가지 해법이다.

이 방향은 RAG 파이프라인, 기업 문서 자동화, 규제 문서 처리 등 문서가 핵심인 AI 활용 전반에 영향을 준다. 파싱 단계의 품질이 올라가면 그 위에서 동작하는 LLM의 답변 품질도 따라 올라간다. 데이터 파이프라인은 가장 취약한 연결고리의 품질에 의해 결정된다는 원칙 그대로다.

9. 오늘 할 수 있는 것 세 가지

분석을 구체적 행동으로 마친다.

9.1 본인 문서 유형으로 직접 테스트하라

HuggingFace에서 모델을 내려받아 본인이 실제로 처리하는 문서 유형(계약서, 논문, 재무 보고서 등)으로 10-20개 샘플을 테스트하라. 특히 페이지 경계에 걸친 표, 다단 레이아웃, 수식이 있는 문서를 포함시킬 것. 벤치마크 수치보다 본인 도메인 결과가 더 신뢰할 수 있는 근거다.

9.2 RAG 파이프라인에서 파싱 단계를 교체해보라

기존 OCR 또는 PDF 파서(pdfplumber, pymupdf 텍스트 추출 등)를 쓰고 있다면, Unlimited OCR로 교체한 전후의 다운스트림 LLM 응답 품질을 비교하라. 파싱 품질이 올라갔을 때 실제로 LLM 답변이 개선되는지를 골든 셋으로 측정하면 도입 가치를 수치화할 수 있다.

9.3 데이터 보안 관점에서 자체 호스팅을 평가하라

외부 OCR API를 사용 중이면서 처리 문서에 기밀 정보가 포함된다면, MIT 라이선스 자체 호스팅 방식의 보안적 이점을 검토하라. GPU 비용과 운영 부담을 계산해 API 비용 대비 총소유비용(TCO)을 비교하면 의사결정이 명확해진다.
