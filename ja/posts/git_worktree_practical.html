一つのリポジトリを複数フォルダに同時展開する - 何が共有され、何がブロックされ、どう片付けるか

2026-09-29 開発・インフラ

機能開発の途中で緊急のバグ修正が発生した場合、多くの開発者は作業内容を git stash に退避させてブランチを切り替えます。しかし、依存関係が肥大化したプロジェクトではブランチを切り替えると変更されたファイルが書き直され、再ビルドが必要になることがあります。かといって別ディレクトリにリポジトリ全体を再クローンすると、大きなリポジトリではオブジェクトデータベースが重複してディスクを消費します。

git worktree はこのジレンマを解決する強力な機能です。単一の .git ディレクトリを共有したまま、複数のブランチを独立した別フォルダへ同時にチェックアウトして並行作業を行えます。ただし、この利便性の裏には厳密な境界が存在します。どの範囲まで設定や退避データが共有されるのか、同一ブランチへのアクセスがどう制限されるのか、作業完了後にどう片付ければ参照破壊を防げるのかを正しく把握しなければ、予期せぬ混乱に見舞われます。

本稿では抽象的なブランチ戦略論は扱いません。独立したテスト環境で実際にコマンドを実行し収集したコンソール出力を基に、一つのリポジトリを複数フォルダに展開した際に何が共有され、何が遮断され、どのように安全に片付けるべきかを実測データ中心に解説します。基礎的なブランチの運用方法はGitブランチ協業ガイドを、変更の復旧手順はgit取り消し決定表を参照してください。

1. 背景と前提 - 一つのリポジトリを複数フォルダに展開すること

1.1 なぜブランチ切り替えではなくワークツリーなのか

単一の作業ディレクトリ環境では、ファイルシステム上に同時に存在できるブランチは一つだけです。緊急修正を行うには作業中ファイルをコミットまたはstashする必要があり、書き直されたファイルが再ビルドを招くこともあります。

これに対し、git worktree を利用すれば現在の作業状態に一切触れることなく、隣のディレクトリへ目的のブランチを即座に展開できます。別クローンを作成する場合と比較して以下の明確な利点があります。

  • ディスク消費の抑制: コミット履歴やツリーオブジェクトを格納する .git は一つだけ維持されるため、ストレージの重複消費が発生しません。
  • 即時のコミット共有: あるフォルダで作成したコミットは、ネットワーク経由のpushやpullを行わずとも他の全ワークツリーから即座に参照可能です。
  • 作業ファイルの保存: p1 の作業ファイルはそのままにして、隣のフォルダでホットフィックスを修正できました（7.1）。

1.2 検証環境と表記基準

本検証では、初期コミット（c54568b init）を持つ main ブランチのリポジトリ p を作成し、検証用の hotfix ブランチをあらかじめ分岐させました。記載されたコマンドはすべて通常の開発者がターミナルで実行する標準形式です。

Windows環境においてディレクトリの階層が極端に深くなると、git内部プロセスがパス長制限によりファイル作成に失敗する事例が確認されています。安定運用のために、基準リポジトリは浅いパスに配置することを推奨します。

2. 核心機構 - worktree add、listと.gitファイルの正体

2.1 新規ブランチと既存ブランチの展開

ワークツリーを追加する基本コマンドは git worktree add です。新しいブランチを作成しながら展開する場合は -b オプションを付け、既存のブランチを取り出す場合はパスの後ろにブランチ名を指定します。

git branch hotfix
git worktree add -b feature …/tech_lab/p1
git worktree add …/tech_lab/p2 hotfix
git worktree list

上記を実行した際の実際のターミナル出力は以下の通りです。

Preparing worktree (new branch 'feature')
HEAD is now at c54568b init
Preparing worktree (checking out 'hotfix')
HEAD is now at c54568b init
…/tech_lab/p  c54568b [main]
…/tech_lab/p1 c54568b [feature]
…/tech_lab/p2 c54568b [hotfix]

git worktree list を確認すると、メインの p は main を、新規フォルダ p1 と p2 はそれぞれ feature と hotfix をチェックアウトしていることが分かります。単一リポジトリ内で3つのブランチがファイルとして同時に展開されています。

2.2 ワークツリーの.gitはフォルダではなくファイルである

展開されたワークツリーの内部構造を確認すると、通常のリポジトリとは大きく異なる設計が確認できます。メイン側の .git は通常のディレクトリですが、追加されたツリーの .git はテキストファイルです。

ls -ld p/.git p1/.git
cat p1/.git
ls p/.git/worktrees/p1
cat p/.git/worktrees/p1/commondir

出力結果は以下の通りです。

drwxr-xr-x 1 …   0 Sep 29 07:48 p/.git
-rw-r--r-- 1 … 257 Sep 29 07:48 p1/.git
gitdir: …/tech_lab/p/.git/worktrees/p1
HEAD
ORIG_HEAD
commondir
gitdir
index
logs
refs
../..

実測の通り p1/.git はわずか257バイトの通常ファイルであり、内部にはメイン側の管理先を示す gitdir: …/tech_lab/p/.git/worktrees/p1 が記述されています。メイン側の管理フォルダ内には以下の構造的特徴があります。

  • 個別メタデータの維持: 各ワークツリー専用の HEAD、index（ステージング）、logs が個別ディレクトリに分離保管されます。
  • commondirによる親参照: commondir ファイル内の ../.. 相対パスを通じて、大元の .git ディレクトリを参照します。
  • 共有される部分: rev-parse --git-path で見ると、hooks・config・refs/stash はメインの .git のパスを指していました（4 章）。

3. 衝突防止機構 - 同一ブランチの重複チェックアウト遮断

3.1 使用中ブランチを取り出そうとする際のfatalエラー

あるワークツリーがチェックアウトしているブランチを、別のフォルダで再度チェックアウトしようとすると何が起きるでしょうか。p1 が feature を開いている状態で、p3 に同一ブランチを追加してみました。

git worktree add …/tech_lab/p3 feature

git は次の fatal エラーを出して止まりました（exit=128）。

Preparing worktree (checking out 'feature')
fatal: 'feature' is already used by worktree at '…/tech_lab/p1'

ドキュメントも、ブランチが既に別のワークツリーでチェックアウトされている場合、add はデフォルトで新しいワークツリーの作成を拒否すると記しています。

3.2 メインツリーでのswitch拒否と-f強制指定の危険性

この拒否はワークツリー作成時だけではありません。メインの作業ツリーで git checkout feature を実行しても、同じ fatal: 'feature' is already used by worktree at '…/tech_lab/p1' で拒否されました（exit=128）。別の実験リポジトリでは、メイン側の git switch hotfix も同じ形式のエラーを出しました。

強制フラグ（-f）を付けると事情が変わります。git worktree add -f …/tech_lab/p3 feature は警告なしに Preparing worktree (checking out 'feature')・HEAD is now at c54568b init を出力し、git worktree list では p1 と p3 がどちらも [feature] と表示されました。

  • 防止機構を切る操作: -f は同じブランチの重複を防ぐ仕組みを切ります。ドキュメントもこのオプションがそうした安全装置を上書きすると記しています。
  • 後片付け: こうして作った p3 はクリーンだったため、git worktree remove …/tech_lab/p3 はメッセージなしで終わりました（exit=0）。
  • 正しい解決策: 重複して開くのではなく、必ず別の作業用ブランチ（-b）を作成して作業すべきです。

4. 共有範囲の実測 - 何が共有され何が隔離されるのか

4.1 共有リソースと隔離リソースの検証対照表

ワークツリー運用で最も注意すべき点は、リソースごとの共有境界です。実測実験を通じて、コミット、stash、設定値、フック、HEAD・index のパスを一つずつ確認しました。

ワークツリー p1 でファイルを変更してコミットすると、メインリポジトリの git log --oneline --all --graph に 99a62e7 feature work がすぐに現れました。一方 rev-parse --git-path で見ると、HEAD・index・logs/HEAD は worktrees/p1/… 以下のワークツリー別のパスを指していました。

リソース項目 共有されるか 実測根拠（コマンドおよび確認結果）
コミットおよびブランチ 共有 p1 でのコミットがメインの log --all に即時表示される
stash 一覧 共有（単一レファレンス） p1 で作成した stash がメインおよび p2 の stash list に現れる
標準 git config 共有 p2 で config lab.flag fromN2 を設定するとメイン側で読める
git config --worktree ツリー別に隔離 extensions.worktreeConfig true 有効時に専用ファイルへ保存
hooks スクリプト 共有 メインの .git/hooks/post-commit が p1、p2 コミット時に共通実行
HEAD / index / logs ツリー別に隔離 rev-parse --git-path で各ツリー固有のパスを返す

4.2 stashが一つという落とし穴と他ブランチ適用の競合

実測で最も警戒すべき事実として判明したのは、stashストレージがリポジトリ全体で一つしかない点です。p1 で git stash push -m "wip-in-p1" を実行後、メインおよび p2 で git stash list を確認した結果は以下の通りでした。

Saved working directory and index state On feature: wip-in-p1
stash@{0}: On feature: wip-in-p1          # メインリポジトリでの表示
stash@{0}: On feature: wip-in-p1          # p2(hotfix)での表示

この stash を別ブランチ（hotfix）のワークツリーで適用するとどうなるかも別に試しました。結果は次のとおりコンフリクトでした。

Auto-merging app.txt
CONFLICT (content): Merge conflict in app.txt
On branch hotfix
…
exit=1
  • 単一の退避スタック: 退避された変更は各ツリーに閉じず、リポジトリ全体で一元管理されます。
  • ブランチラベルの確認義務: git stash list 出力の On feature: ... 表示を必ず確認してから取り出す必要があります。
  • ツリー削除後の保持: ワークツリーディレクトリを削除しても、そこで作成された stash は失われず残存します。

4.3 --worktree による個別設定とフックの実行パス

通常、git config で設定した項目はメインの .git/config に書き込まれ全ツリーへ波及します。特定ツリー専用の設定を設けるには、設定拡張を有効化する必要があります。

git config --worktree lab.only fromP2
# extensions.worktreeConfig が必要というエラーで失敗
git config extensions.worktreeConfig true
git config --worktree lab.only fromP2

拡張を有効にした後に --worktree で登録した値はメインの .git/worktrees/p2/config.worktree に記録され、p2 では fromP2 が読めましたが、メインと p1 からは読み取れませんでした（exit=1）。

一方で、コミット検証などを司る .git/hooks はリポジトリ全体で共有されます。メイン側に配置した post-commit フックは、どのワークツリーからコミットしても実行され、その際の作業ディレクトリ（pwd）は実行元のツリー位置を正確に指し示しました。

  • フックの一元管理: チーム共有の検証スクリプトをツリーごとに配置し直す手間が省けます。
  • 相対パスへの配慮: フック内で相対パスを扱う場合は、メイン以外のツリーから呼び出される可能性を考慮して記述します。
  • ワークツリー別設定は有効化が必要: extensions.worktreeConfig なしで --worktree を使うと fatal（exit=128）で拒否されました。

5. 整理手順 - worktree removeの拒否条件とpruneの必要性

5.1 変更や未追跡ファイルが存在する際の削除拒否

役目を終えたワークツリーを片付けるコマンドは git worktree remove です。しかし、対象ディレクトリ内に未コミットの変更や、追跡されていない新規ファイルが1つでも残っている場合、git は削除を拒否します。

# ファイル変更を残したまま削除を試みる
git worktree remove …/tech_lab/p2
# 出力: fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it

# 変更をstashし、未追跡ファイル(untracked.txt)のみが存在する状態で試みる
git worktree remove …/tech_lab/p2
# 出力: fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it

実測結果が示す通り、未追跡ファイル（?? untracked.txt）が1つあるだけでも同じ fatal エラーになります。ドキュメントも、未追跡ファイルも追跡ファイルの変更もないクリーンなワークツリーだけが削除できると記しています。完全に破棄して問題ない作業であれば、--force フラグを指定して強制消去できます。

  • 正規削除の条件: 追跡・未追跡を問わず作業ツリーが完全にクリーンでなければ削除できません。
  • 強制削除: --force を付けると、変更ファイル・新規ファイルごとフォルダが削除されました（ls: cannot access 'p2': No such file or directory）。
  • ブランチの実体は残る: フォルダが消去されても、ブランチ（hotfix）自体はリポジトリ内に保持されます。

5.2 手動削除で生じるprunable状態とブランチロック

git worktree remove の代わりにエクスプローラーや rm -rf でワークツリーのフォルダを直接消すとどうなるかを見ました。p4（ブランチ tmpbr）を作成した後、フォルダを別の場所へ移動させて「消えた」状態を作りました。

git worktree list
git worktree list --porcelain

git はフォルダが消滅しても管理情報を自動削除せず、以下のように prunable として保持し続けます。

…/tech_lab/p   c54568b [main]
…/tech_lab/p4  c54568b [tmpbr] prunable
worktree …/tech_lab/p4
HEAD c54568b49c4cf9ce2c99ccc5dff022eb0bc00495
branch refs/heads/tmpbr
prunable gitdir file points to non-existent location

この状態では、存在しないフォルダがブランチを占有し続けます。同じ方法で p5（ブランチ tmp2）を作ってフォルダを移動した後、git worktree add …/tech_lab/p6 tmp2 を実行すると次のエラーになりました（exit=128）。

fatal: 'tmp2' is already used by worktree at '…/tech_lab/p5'

5.3 worktree prune による幽霊レコードの掃除

手動削除によって孤立した参照メタデータは、git worktree prune で解放します。実行前に -n（ドライラン）と -v（詳細表示）を付けて削除対象を確認するのが安全です。

git worktree prune -n -v
# 出力: Removing worktrees/p4: gitdir file points to non-existent location
git worktree prune -v
# 出力: Removing worktrees/p4: gitdir file points to non-existent location

prune の後は git worktree list にメインだけが残り、同じブランチを再び展開する git worktree add …/tech_lab/p4 tmpbr が Preparing worktree (checking out 'tmpbr') で成功しました。tmp2 も git worktree prune の後に p6 へ展開できました。

6. 外部ストレージと一時保管 - lockとunlock

6.1 lock 設定による誤った自動 prune の防止

ドキュメントは、ワークツリーが常にはマウントされていない可搬デバイスやネットワーク共有上にある場合、管理ファイルが自動で prune されないようロックするよう記しています。この機能が git worktree lock です。

git worktree lock --reason "on USB disk" …/tech_lab/p4
git worktree list --porcelain

ロックを設定すると、一覧に locked on USB disk と表示されます。この状態であればフォルダが見当たらない状態でも git worktree prune -v は削除をスキップします。

6.2 ロックされたツリーの安全な解除と削除

ロック中のワークツリーは git worktree remove でも削除できませんでした（exit=128）。

fatal: cannot remove a locked working tree, lock reason: on USB disk
use 'remove -f -f' to override or unlock first

メッセージのとおり先に git worktree unlock …/tech_lab/p4 でロックを解除すると、フォルダのないこのワークツリーは git worktree prune -v で Removing worktrees/p4: gitdir file points to non-existent location とともに片付きました。メッセージとドキュメントは -f を2回付ける方法（remove -f -f）も記していますが、この実験では unlock で片付けました。

7. 実務適用指針 - 活用すべき場面と注意すべき場面

7.1 緊急ホットフィックスと並行作業

実行結果からそのまま導ける使い方は次のとおりです。

  • 緊急修正ブランチを隣のフォルダに: 既存の hotfix ブランチを git worktree add …/tech_lab/p2 hotfix で展開すると、p1（feature）の作業ファイルはそのままに隣のフォルダで修正できました。p2 でのコミットでも共有フックが実行されました。
  • 終わったら remove で片付ける: クリーンなワークツリーはメッセージなしで削除され、削除後もブランチと stash は残りました。不要なら別途整理します。
  • フォルダを手で消さない: 手で消したフォルダは prune までブランチを占有し、同じブランチを別の場所に展開できませんでした。

7.2 並列AIコーディングエージェントとワークツリー隔離

複数の AI コーディングセッションが一つのリポジトリを共有するときの問題は AIエージェント複数運用の実態で扱いました。ワークツリーを使う場合、本稿の実行結果から押さえておく点は次のとおりです。

  • HEAD・index はワークツリー別: rev-parse --git-path の結果のとおり、ワークツリーごとに HEAD・index のパスが別になります。
  • stash は一つ: あるワークツリーで stash pop すると、別のワークツリーが退避した stash を取り出してしまうことがあります。stash list の「On ブランチ」表示を確認します。
  • 片付けは remove・prune: 作業が終わったワークツリーは git worktree remove で削除し、手で消したフォルダがあれば git worktree prune でブランチの占有を解きます。

7.3 状況別コマンドおよびエラーメッセージ決定表

日常の開発で遭遇する主なエラー出力と、それに対する正しい対処手順をまとめました。

発生状況 原因および出力メッセージ（実測） 推奨される対処

変更・未追跡が残るツリーの削除 fatal: '…' contains modified or untracked files, use --force to delete it 変更をコミットまたは退避後に再実行。未追跡ファイルが1つでもあれば拒否される

リムーバブルメディア上のツリー保護 list に locked / remove 時 fatal: cannot remove a locked working tree, lock reason: on USB disk git worktree lock --reason "理由" で保護（フォルダがなくても prune が触れない）。削除時は unlock 後に片付けるか remove -f -f

確認できなかった事項

  • LinuxおよびmacOS専用ファイルシステムの挙動: 本検証はWindows 10のNTFS環境で実施したため、Linux ext4やmacOS APFS環境でのファイルパーミッション挙動は実測比較できていません。
  • ネットワークファイルシステム（NFS/SMB）上のロック競合: リモートマウントされた共有ストレージ上にツリーを展開した際の、複数クライアント間でのファイルロック競合や遅延挙動は検証範囲外です。
  • 内部一時リファレンスのライフサイクル: refs/bisect や refs/rewritten など、git内部の特殊操作時に生成される非共有リファレンスの詳細な挙動は、bisect実験を行っていないため確認できていません。

# git worktree 実践チェックリスト - ブランチ並行作業と隔離

検証環境: Windows 10 Pro 10.0.19045、Git Bash (GNU sed 4.9、GNU Awk 5.0.0)、curl 8.12.1 (Schannel)、git 2.48.1.windows.1、Windows PowerShell 5.1、Python 3.13.3、Node 22.16.0 (管理者権限なし)。
以下の値はこの環境で実際に実行して確認した出力に基づいています。ただし、ロックしたワークツリーの `remove -f -f` は git のメッセージと文書が示す方法で、実行していません（ロックは `unlock` で解除して片付けました）。パスは `…/tech_lab/` に短縮しました。

---

## 1. ワークツリー間の共有範囲対照表（実測確認）

| 項目 | 共有されるか | 実測根拠（コマンドと出力） | 実務への影響 |
|---|---|---|---|
| コミット・ブランチ | 共有 | ワークツリー p1 のコミットがメインの `log --all` にすぐ表示される | どのフォルダでコミットしても他のワークツリーからすぐ見える |
| stash 一覧 | **共有（一つ）** | p1 で退避した stash がメインと p2 の `stash list` にそのまま現れ、ワークツリー削除後も残る | 別のワークツリーの `stash pop` が他人の作業を取り出しうる（別ブランチで適用すると CONFLICT を実測） |
| git config（標準） | 共有 | p2 で設定したキー（`lab.flag`）をメインで読める | リポジトリ単位の設定変更は全ワークツリーに適用される |
| git config --worktree | ワークツリー別 | `extensions.worktreeConfig true` を有効にした後だけ使える（なければ fatal）。値はメインの `.git/worktrees/p2/config.worktree` に記録 | ワークツリー別の設定が必要なときだけ有効にする |
| hooks スクリプト | 共有 | メインの `.git/hooks/post-commit` が p1・p2 のコミットで実行される | フックはメインの一か所に置けばよい |
| HEAD / index / logs | ワークツリー別 | `rev-parse --git-path` が `worktrees/p1/...` のパスを返す | HEAD・index のパスはワークツリーごとに別 |

---

## 2. 状況別のコマンドと git の応答（実測メッセージ）

| 状況 | 実行コマンド例 | git の出力メッセージ（実測） | 対処法 |
|---|---|---|---|
| 別のワークツリーが使うブランチを展開 | `git worktree add …/tech_lab/p3 feature` | `fatal: 'feature' is already used by worktree at '…/tech_lab/p1'` | 新しいブランチ（`-b`）で展開する。`-f` は防止機構を切る操作 |
| 変更・新規ファイルが残ったままの削除 | `git worktree remove …/tech_lab/p2` | `fatal: '…\tech_lab\p2' contains modified or untracked files, use --force to delete it` | stash かコミットの後に remove。未追跡ファイルが1つでも拒否される |
| フォルダを手で消した後のブランチ再利用 | `git worktree add …/tech_lab/p6 tmp2` | `fatal: 'tmp2' is already used by worktree at '…/tech_lab/p5'` | `git worktree prune -n -v` で確認してから `git worktree prune` を実行 |
| ロックしたワークツリーの削除 | `git worktree remove …/tech_lab/p4` | `fatal: cannot remove a locked working tree, lock reason: on USB disk` | `git worktree unlock` の後に片付けるか `remove -f -f`。ロックは `lock --reason "on USB disk"` で掛け、`list --porcelain` に `locked on USB disk` と表示される |

## 3. 作業前後のチェックリスト

- [ ] **フォルダ削除ではなく正規コマンドを使う**: エクスプローラーや `rm -rf` で消さず、`git worktree remove <パス>` で削除する。
- [ ] **削除後に残るブランチ・stash を確認**: ワークツリーのフォルダを消してもブランチと stash は残るので、不要なものは別途整理する。
- [ ] **stash pop の前にブランチ表示を確認**: stash は一つなので、`git stash list` の `On <ブランチ名>` を確認してから取り出す。
- [ ] **未追跡ファイルを確認**: `worktree remove` は未追跡の新規ファイル（`??`）が1つあるだけでも削除を拒否する。
- [ ] **Windows の長いパスに注意**: パスが非常に長いフォルダでは git が `.git` 内に書き込めず失敗することがあるため、リポジトリは短いパスに置く。
- [ ] **手で消した・移動した後は prune**: フォルダがなくなったワークツリーは `git worktree prune -n -v` で確認し、`git worktree prune` で片付ける。
