마스킹은 출력에서 하면 늦다 - 민감 정보를 발생 지점에서 막는 구조

출력에서 가리는 방식은 아는 형식만 막는다. 그때는 이미 사본이 늘어난 뒤다

2026-08-01 개발/인프라

서론: 로그에서는 지웠는데 백업에는 남아 있었다

가장 흔한 순서는 이렇다. 누군가 로그를 보다가 있으면 안 될 값이 찍혀 있는 것을 발견한다. 급히 마스킹 규칙을 넣고 배포한다. 다음 날 로그 화면은 깨끗하다. 그리고 한 달쯤 뒤, 장애 조사를 하려고 예전 백업을 풀어 본 사람이 같은 값을 다시 발견한다.

이 이야기에서 마스킹 규칙은 제 일을 했다. 문제는 규칙이 작동하기 시작한 시점이다. 그 값은 이미 표준 출력으로 나갔고, 파일에 쓰였고, 수집기로 전송됐고, 로테이션됐고, 백업에 들어갔다. 출력 단계에서 가린다는 것은 이미 여러 벌 복제된 뒤에 그중 한 벌을 고치는 것이다.

그래서 이 글의 논지는 「마스킹하자」가 아니다. 마스킹은 마지막 방어선이고, 진짜 해법은 애초에 그 값이 로그 경로에 들어가지 않게 하는 것이다. 그리고 그렇게 하려면 규칙의 방향을 뒤집어야 한다. 뺄 것을 고르지 말고 넣을 것을 골라야 한다.

  • 출력에서 가리는 방식은 패턴을 아는 것만 막는다. 형식이 조금만 달라지면 그대로 통과하고, 아무것도 실패하지 않는다
  • 객체를 통째로 넣으면 나중에 생긴 필드가 자동으로 따라온다. 로그 코드는 한 줄도 안 바뀌었는데 새는 항목이 늘어난다
  • 고치기로 결정한 시점에는 이미 사본이 여러 벌이다. 어느 사본이 남아 있는지 아는 사람이 없다
  • 값을 감싸 두면 실수해도 원본이 안 나온다. 문자열 결합에 넣어도, 로그에 넣어도 마찬가지다

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 Node.js v22.16.0 (win32)으로 실제로 실행한 결과다. 스크립트는 전부 파일로 저장해 실행했고, 임시 디렉터리 안에서만 파일을 만들었다.

★예시 값은 전부 형식만 맞춘 가짜다. 자릿수만 맞추고 숫자는 모두 0으로 채웠으며(000000-0000000, 0000-0000-0000-0000, 010-0000-0000), 이메일은 실제로 배달될 수 없는 예약 도메인을 썼다. 실존하는 개인정보가 아니다. 이 글은 값이 어떻게 새는지의 구조만 다루며, 우회나 추출 방법은 다루지 않는다.

이 글이 다루지 않는 것. 어떤 데이터를 어디까지 외부 도구에 넣어도 되는가 하는 판단 기준과 사내 규정은 사내 데이터를 LLM에 넣어도 되는가 쪽 이야기다. 무엇을 어느 레벨로 찍을 것인가 하는 레벨 규약은 WARN이 쓰레기통이 되는 이유에서 다뤘으니 여기서는 다시 설명하지 않는다. 허용 목록으로 뒤집는 일반 절차는 금지 목록은 항상 뒤늦다에 있다. 이 글은 그 원리를 로그 경로 한 점에 적용한 구현이다.

법령에 관하여. 개인정보를 다루는 조직에는 수집·보관·파기에 관한 의무가 있다. 다만 이 글은 조문이나 금액을 인용하지 않는다. 적용 범위와 보존 기간은 사업 형태와 국가에 따라 달라지므로, 관련 법령과 사내 정책을 확인해 정하라. 이 글이 다루는 것은 기술적 구현뿐이다.

1. 객체를 통째로 넣으면, 나중에 생긴 필드가 따라온다

먼저 가장 중요한 재현이다. 이것 하나만 이해해도 이 글의 절반이다. 문제는 「민감한 값을 로그에 찍었다」가 아니라 「로그에 찍히는 범위를 아무도 고정해 두지 않았다」는 것이다.

객체를 통째로 직렬화해 찍는 코드를 하나 두고, 시간이 지나 다른 팀이 다른 기능을 위해 필드를 추가하는 상황을 만들었다. 로그 호출은 손대지 않았다.

node v22.16.0 / win32
--- 1-1. release v1: the object has 3 fields ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z"}

--- 1-2. release v2: product adds fields. the log call is UNCHANGED ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","cardNumber":"0000-0000-0000-0000","nationalId":"000000-0000000"}

--- 1-3. diff: what the log gained without a code change ---
fields logged in v1 : 3  id,nickname,createdAt
fields logged in v2 : 6  id,nickname,createdAt,phone,cardNumber,nationalId
newly leaking        : phone,cardNumber,nationalId
lines of code changed to cause this : 0

마지막 줄이 이 글 전체의 요약이다. 이 변화를 만들기 위해 바뀐 코드 줄 수는 0이다. 필드를 추가한 사람은 로그 코드를 읽은 적이 없고, 로그 코드를 쓴 사람은 그 필드가 생긴 줄 모른다. 둘 다 잘못한 게 없는데 값이 샌다.

이런 종류의 결함은 코드 리뷰로 잡히지 않는다. 리뷰어가 보는 것은 「필드 세 개를 추가했다」는 변경뿐이고, 그 변경만 놓고 보면 아무 문제가 없기 때문이다. 문제는 두 변경 사이의 거리에 있다.

1.1 전개와 중첩도 똑같다

「객체를 그대로 넣지만 않으면 되겠지」라는 생각이 자연스럽다. 그런데 흔히 쓰는 두 가지 우회가 전혀 우회가 아니다.

--- 1-4. the same happens through spread, nesting and ORM rows ---
spread into context  : {"requestId":"r-0001","id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","card ...
nested one level     : nationalId still present
depth does not help  : JSON.stringify walks the whole tree
  • 전개 연산자로 컨텍스트에 합치는 것은 필드를 고른 것이 아니다. 그냥 같은 필드가 한 단계 위로 올라온 것이다
  • 한 단계 감싸는 것도 소용없다. 직렬화 함수는 트리 전체를 훑기 때문에 깊이는 방어가 아니다
  • 데이터베이스 행 객체를 그대로 넘기는 것이 가장 위험하다. 열이 늘어나면 로그도 같이 늘어나고, 열 추가는 로그와 무관한 사람이 한다
  • 요청 본문 전체를 컨텍스트에 붙이는 것도 같은 구조다. 클라이언트가 무엇을 보낼지 서버 코드가 정하지 않는다
  • 공통점은 하나다. 범위를 정하는 주체가 로그를 쓰는 사람이 아니다. 그것이 결함의 정의다

2. 출력에서 가리는 방식은 아는 형식만 막는다

가장 먼저 떠오르는 대응은 출력 직전에 정규식으로 가리는 것이다. 실제로 흔히 쓴다. 이 방식이 어디서 무너지는지 무해한 값으로만 확인했다. 전화번호 모양과 사번 모양이고, 숫자는 전부 0이다.

아홉 개 중 일곱 개가 그대로 통과했다. 그리고 통과한 이유들이 하나같이 사소하다.

  • 구분자가 하이픈에서 공백이나 점으로 바뀌었다. 상류 시스템이 정규화 방식을 바꾸면 그날부터 규칙이 놀게 된다
  • 구분자가 아예 없다. 데이터베이스에 저장할 때 흔히 지우는 형태다
  • 국가 번호가 앞에 붙었다. 국제 표기로 정규화하는 계층을 하나 지나면 이렇게 된다
  • 대소문자가 다르다. 정규식에 플래그 하나 빠진 것이 전부다
  • 사번 자릿수가 하나 늘었다. 채번 정책이 바뀌었을 뿐인데 규칙이 빗나갔다
  • 공통점은 아무것도 실패하지 않는다는 것이다. 마스킹이 안 됐다고 알려 주는 신호가 없다

2.1 반대 방향으로도 틀린다

덜 알려진 실패 모드가 하나 더 있다. 규칙이 지우면 안 될 것을 지우는 경우다.

--- 2-2. why the rule cannot be finished ---
the masker matches shapes. the data is defined by MEANING.
every upstream format change is a silent hole, and nothing fails loudly.

--- 2-3. and the rule can be too greedy in the other direction ---
order 010-0000-0000 shipped           order 010-****-**** shipped   <- masked, but this was not personal data
build EMP-000000 finished             build EMP-****** finished   <- masked, but this was not personal data

a pattern rule has two failure modes at once: it misses, and it destroys.

주문 코드와 빌드 태그가 우연히 그 형식에 맞았다. 이 경우 마스킹은 민감하지 않은 값을 지워 디버깅을 방해한다. 그러면 사람들은 규칙을 느슨하게 만들고, 느슨해진 규칙은 다시 놓치기 시작한다. 이 진자 운동에는 끝이 없다.

근본 이유는 한 문장으로 정리된다. 정규식은 형식을 맞히고, 민감 정보는 의미로 정의된다. 같은 열한 자리 숫자가 어떤 맥락에서는 개인정보이고 어떤 맥락에서는 주문 번호다. 그 차이는 값 안에 들어 있지 않다.

막는 지점무엇을 막나새 필드가 생기면사본에 미치는 범위되돌리기
발생 지점 (래퍼 타입)값 자체가 문자열로 존재하지 않음영향 없음 (감싼 값만 취급)새 사본이 만들어지지 않음코드 되돌리기
이벤트 조립 (허용 목록)넣기로 정한 필드 외 전부자동으로 제외로거 아래 전 구간코드 되돌리기
로거 직렬화기이름을 아는 필드이름을 모르면 통과그 로거를 쓰는 곳만설정 되돌리기
수집기 규칙패턴이 맞는 값패턴이 다르면 통과즉시 전역, 단 기존 사본 제외즉시
출력 후 일괄 세척찾아낸 것만모름손댄 사본 하나불가 (원본 소실)

3. 고치기로 결정한 시점에는 이미 여러 벌이다

이제 세 번째 축이다. 앞의 두 절이 「무엇을 놓치는가」였다면 이 절은 「언제 놓치는가」다. 로그 한 줄이 태어나서 겪는 평범한 일생을 실행으로 따라가 봤다.

아홉 벌 중 여덟 벌에 원본이 남아 있다. 고친 것은 한 벌이다. 그리고 이 여덟 벌의 보존 기간을 정하는 사람이 각각 다르다.

  • 로테이션 파일은 서버 설정이 정한다. 보통 애플리케이션 팀이 아니라 인프라 쪽이다
  • 수집기 세그먼트는 수집기 정책이 정한다. 인덱스가 만들어져 있으면 검색으로도 나온다
  • 백업은 백업 정책이 정한다. 대개 가장 길고, 되돌려 쓰기가 가장 어렵다
  • 장애 스냅샷과 티켓 첨부는 아무도 정하지 않는다. 만든 사람이 잊으면 영원히 남는다
  • 그래서 「지웠다」고 말하려면 이 목록을 먼저 만들어야 한다. 대부분의 조직에 그 목록이 없다

여기서 나오는 결론이 이 글의 핵심 논지다. 사본을 쫓아다니는 싸움은 이길 수 없다. 값이 태어나는 순간 사본은 이미 예정되어 있고, 그 뒤의 모든 조치는 예정된 사본 중 일부만 건드린다. 싸움을 옮겨야 한다. 값이 그 경로에 들어가기 전으로.

4. 에러 객체가 값을 실어 나른다

로그 호출을 아무리 잘 정리해도 남는 경로가 하나 있다. 예외다. 예외는 「로그를 찍자」고 결정한 사람이 없어도 출력된다.

node v22.16.0 / win32
--- 4-1. route A: the value goes into the message ---
e.message           : invalid nationalId: 000000-0000000
first stack line    : Error: invalid nationalId: 000000-0000000

--- 4-2. route B: the value rides on a property ---
e2.message          : payment declined   (clean)
JSON of e2.context  : {"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}

--- 4-3. what each common serializer emits ---
JSON.stringify(e2)            : {"name":"AppError","context":{"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}}
  -> CONTAINS nationalId
String(e2)                    : AppError: payment declined
  -> clean
util.inspect(e2) contains     : CONTAINS nationalId
console.error path uses inspect, so the terminal shows it too

두 경로가 성격이 다르다.

  • 경로 A는 눈에 보인다. 검증 실패 메시지에 값을 넣는 것은 친절한 습관이라 아주 흔하고, 그래서 아주 흔하게 샌다. 메시지에 넣는 순간 스택 첫 줄에도 들어간다
  • 경로 B는 눈에 안 보인다. 메시지는 깨끗한데 컨텍스트 속성에 요청 전체가 붙어 있다. 그리고 이 습관은 권장되는 습관이라 더 널리 퍼져 있다
  • 메시지만 보고 판단하면 틀린다. 직렬화기가 무엇을 훑는지가 실제로 나가는 내용을 결정한다
  • 터미널 출력도 같은 검사 경로를 쓰므로 화면에도 그대로 나온다

--- 4-5. why JSON.stringify(err) looks safe and is not ---
JSON.stringify(new Error(payload.phone)) : {}
message and stack are non-enumerable, so plain JSON drops them,
which is exactly why teams add a custom error serializer,
and the custom serializer is what puts message, stack and context back in.

--- 4-6. an unhandled rejection prints it with no logging code at all ---
uncaught handler saw : AppError: payment declined
full text contains   : CONTAINS nationalId

nobody called a logger here. the runtime did.

4-5가 특히 교훈적이다. 기본 직렬화는 에러를 빈 객체로 만든다. 메시지와 스택이 열거되지 않는 속성이기 때문이다. 그래서 팀들은 「에러가 로그에 안 찍힌다」는 불편을 겪고 전용 에러 직렬화기를 붙인다. 그 직렬화기가 메시지와 스택과 컨텍스트를 다시 집어넣는다. 안전해 보이던 기본값을 스스로 걷어내는 셈이다.

  • 원인 체인으로 감싼 바깥 에러는 메시지가 깨끗해 더 안심된다. 그런데 안쪽 컨텍스트를 그대로 끌고 간다
  • 미처리 예외는 아무도 로거를 부르지 않아도 런타임이 출력한다. 로그 호출을 감사해도 이 경로는 목록에 없다
  • 따라서 에러 컨텍스트에는 식별자만 넣는 규칙이 필요하다. 요청 아이디, 사용자 아이디, 주문 아이디 같은 것들이다
  • 검증 실패 메시지에는 값이 아니라 무엇이 틀렸는지를 쓴다. 「형식이 맞지 않음, 필드 이름 nationalId」로 충분하다
  • 이 규칙은 5절의 래퍼가 있으면 저절로 지켜진다. 감싼 값을 메시지에 넣어도 원본이 나오지 않기 때문이다

5. 발생 지점에서 막는다 - 꺼내야만 나오는 래퍼

이제 해법이다. 발상은 단순하다. 민감한 값을 문자열로 들고 다니지 않는다. 대신 꺼내는 호출을 명시적으로 해야만 원본이 나오는 타입으로 감싼다. 감싸는 순간부터 실수는 값을 노출하지 않고 자리표시자를 노출한다.

const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // 명시적이고 검색 가능한, 유일한 출구
  expose() { return this[RAW]; }
  // 암묵적 경로는 전부 같은 자리표시자를 돌려준다
  toString() { return '[' + this.label + ' redacted]'; }
  toJSON()   { return '[' + this.label + ' redacted]'; }
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }
}

const phone = new Secret('010-0000-0000', 'phone');

네 개의 훅을 함께 덮는 것이 핵심이다. 하나라도 빠지면 그 구멍으로 다 나간다. 실수가 일어날 수 있는 경로를 열세 가지 골라 전부 통과시켜 봤다.

--- 5-7. the wrapper does not survive the network boundary ---

  • 문자열 변환만 구현한 래퍼는 화면에서는 가려지지만 직렬화와 검사 출력에서 원본을 그대로 뱉었다. 그리고 이쪽이 실제 로그 경로다
  • 절반짜리 래퍼는 없는 것보다 위험하다. 코드를 읽는 사람이 「이건 감싸져 있으니 안전하다」고 판단하기 때문이다
  • 엄격한 변형은 문자열로 쓰려 하면 예외를 던진다. 테스트에서 실수를 즉시 잡는 대신 운영에서 새 사고를 만들 수 있다
  • 흔한 절충은 개발과 테스트에서는 던지고 운영에서는 자리표시자로 대체하는 것이다. 직렬화 훅은 양쪽 모두 대체를 유지해 로그가 죽지 않게 한다
  • 래퍼는 경계를 넘지 못한다. 직렬화해 보내면 상대는 자리표시자 문자열을 받는다. 받는 쪽에서 다시 감싸야 하므로, 이 방식은 서비스마다 각자 세워야 한다
  • 덧붙여 타입 시스템이 있으면 더 강해진다. 문자열을 요구하는 자리에 감싼 값을 넣으면 컴파일 단계에서 걸린다

6. 뺄 필드가 아니라 넣을 필드를 정한다

래퍼는 값을 지킨다. 그런데 1절의 문제는 값이 아니라 범위였다. 그 범위를 고정하는 것이 이 절이다. 여기서는 「민감 필드를 어떻게 뺄까」 한 가지만 본다.

// 방향 1. 뺄 필드를 정한다
const DENY = ['phone', 'cardNumber', 'nationalId'];
function denylist(obj) {
  const out = { ...obj };
  for (const k of DENY) delete out[k];
  return out;
}

// 방향 2. 넣을 필드를 정한다
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];
function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

두 함수는 처음 작성된 스키마에서 구별이 안 된다. 그것이 이 결함이 오래 살아남는 이유다.

--- 6-1. both rules look fine on the schema they were written for ---
  denylist (v2)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}
  allowlist(v2)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}

--- 6-2. now the schema moves. neither rule is edited ---
  denylist (v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","national_id":"000000-0000000","backupPhone":"010-0000-0000","kyc":{"documentNo":"D-000000000"}}
  allowlist(v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}

  sensitive values present in denylist output  : id-shaped value, phone-shaped value, document-shaped value
  sensitive values present in allowlist output : none

스키마를 세 방향으로 움직였다. 같은 데이터가 다른 표기법의 이름으로 들어왔고, 아무도 알려주지 않은 새 필드가 붙었고, 한 단계 중첩된 구조가 생겼다. 뺄 필드 목록은 셋 다 통과시켰고, 넣을 필드 목록은 셋 다 막았다. 1절과 정확히 대조된다. 1절에서 자동으로 새던 것이 여기서 자동으로 막힌다.

--- 6-3. the asymmetry, stated plainly ---
  denylist  fails OPEN : an unknown field is emitted
  allowlist fails CLOSED: an unknown field is dropped
  a new field is added by someone who has never read the logging code.
  so the rule has to be safe when nobody updates it.

--- 6-4. what you lose, and how to notice ---
  fields dropped from the log : phone, cardNumber, nationalId, national_id, backupPhone, kyc
  a field you needed for debugging is now missing, and that is the cost.
  make it visible instead of silent:
  {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","_dropped":6}
  the count tells you the schema moved, without telling you what moved.

--- 6-5. the allowlist has to be applied at build time, not at write time ---
  event object keys : ["id","nickname","createdAt","plan"]
  the wide object never reaches the logger, so no later stage can widen it.
  narrowing inside the logger is one layer too late: everything upstream
  of the logger, including error handlers, still sees the wide object.
  • 실패 방향이 반대다. 뺄 목록은 모르는 필드를 내보내고, 넣을 목록은 모르는 필드를 버린다. 아무도 규칙을 갱신하지 않는 상태에서 안전해야 하므로 후자가 맞다
  • 대가가 있다. 디버깅에 필요했던 필드가 조용히 사라진다. 이것이 허용 목록의 실제 비용이고, 숨기면 안 된다
  • 대가를 조용하지 않게 만드는 값싼 방법이 6-4에 있다. 버린 필드의 개수만 함께 남기는 것이다. 무엇이 바뀌었는지는 말하지 않으면서 스키마가 움직였다는 사실은 알려 준다
  • 그 숫자가 어느 날 갑자기 커지면 상류에 변경이 있었다는 신호다. 허용 목록을 갱신할지 검토하는 계기가 된다
  • ★적용 지점이 결정적이다. 로거 내부에서 좁히면 한 층 늦다. 로거보다 위에 있는 모든 것, 특히 에러 처리기는 여전히 넓은 객체를 본다
  • 그래서 좁히는 일은 이벤트 객체를 만드는 순간에 해야 한다. 넓은 객체가 로거에 도달하지 않으면, 뒤의 어떤 단계도 그것을 다시 넓힐 수 없다

7. 뒤 4자리만 보여줘야 할 때, 어디서 자르는가

현실에는 부분 표시 요구가 있다. 상담 화면에서 카드 뒤 4자리를 확인해야 본인 여부를 물어볼 수 있다. 이 요구 자체는 정당하다. 문제는 어디서 자르느냐다.

--- 7-1. the requirement: a support screen shows the last 4 digits ---
  requested display value : ****-****-****-0000

--- 7-2. attempt A: keep both on the same record ---
  record  : {"userId":"u-0001","cardNumber":"0000-0000-0000-0000","cardLast4":"0000"}

  record  : {"userId":"u-0001","cardLast4":"0000","card":"[card redacted]"}

7-2가 아주 흔한 실수다. 자른 값과 원본을 같은 객체에 나란히 둔다. 화면은 자른 값을 쓰니 요구는 충족된다. 그런데 이 객체가 통째로 로그에 들어가는 순간 원본도 같이 간다. 부분 표시가 줄인 것은 아무것도 없고, 필드가 하나 늘었을 뿐이다.

7-3이 답이다. 경계에서 한 번 잘라 파생값만 남기고, 원본은 감싼 채로 둔다. 그러면 화면도 로거도 자른 값만 받는다.

--- 7-5. cutting late produces drift ---
  input                : "0000 0000 0000 0000"
  last4  (digits only) : 0000
  last4v2(naive slice) : "0000"
  same field name, two values, depending on which layer computed it.
  cutting once at the boundary makes the answer single-valued.

--- 7-6. a partial value is still personal data ---
  one record may hold several partials : {"u-0001":["0000","010-0000","a***@example.invalid"]}
  each is harmless alone. joined on the same subject they narrow the set.
  so a partial is a display format, not a declassification.
  keep the same retention and access rules on it.
  • 7-5는 늦게 자를 때 생기는 두 번째 문제다. 자르는 코드가 여러 계층에 생기면 같은 필드 이름에 다른 값이 담긴다. 한쪽은 숫자만 남기고 자르고, 다른 쪽은 문자열 끝을 그냥 잘랐다
  • 공백이 섞인 입력에서 두 결과가 갈렸다. 하나는 숫자 네 자리, 하나는 공백을 포함한 네 글자다. 화면에 따라 다르게 보이는 값이 생기고, 그것이 문의로 돌아온다
  • 경계에서 한 번만 자르면 이 문제가 정의상 사라진다. 파생값을 만드는 곳이 하나뿐이기 때문이다
  • 7-6이 마지막 주의다. 부분 값도 여전히 개인정보다. 하나만 보면 무해하지만 같은 주체에 여러 부분 값이 붙으면 범위가 좁아진다
  • 따라서 부분 표시는 표시 형식이지 등급 해제가 아니다. 보존 기간과 접근 권한을 원본과 같은 기준으로 두라
  • 구체적인 자릿수와 표시 범위는 업종과 계약에 따라 다르다. 관련 법령과 사내 정책, 그리고 결제망 규정을 확인해 정하라

8. 이미 쌓인 로그에서 위험 지점 찾기와 도입 순서

여기까지가 「앞으로 어떻게 할까」였다면, 이 절은 「이미 쌓인 것을 어떻게 할까」다. 진단은 두 번 훑는다.

--- 8-1. build a sample log tree ---

--- 8-2. pass 1: key names, not value shapes ---
  file          lines   risky keys found

1차 통과는 값의 모양이 아니라 키 이름으로 찾는다. 2절에서 봤듯 값의 형식은 상류에 따라 달라지지만, 키 이름은 비교적 안정적이다. 중첩된 키도 경로째로 잡아야 한다. context.cardNumber가 그렇게 걸렸다.

그런데 2차 통과가 더 중요하다. 위험 키 목록에 걸리지 않은 나머지 키를 전부 나열해 사람이 한 번 읽는 것이다. 표본에서 서로 다른 키가 열네 개였고 그중 일곱 개가 목록 밖이었다. 이 목록은 유한하다. 한 번 읽으면 끝난다. 그리고 값 형식만 훑는 방식으로는 애초에 만들 수 없는 목록이다.

--- 8-4. rank by blast radius, not by count ---
  file          keys   retain   copies   score
  ----------------------------------------------------------
  batch.log     3      365d     3        3285
  auth.log      2      365d     4        2920
  api.log       2      90d      4        720
  worker.log    0      14d      1        0
  score = risky keys x retention days x number of destinations.
  a low-volume line kept for a year in four places outranks a noisy one kept for two weeks.

--- 8-5. order of work, by how hard each step is to undo ---
  # action                                cost      undo                  buys you
  ------------------------------------------------------------------------------------------------------------
  1   collector-side drop rule              minutes   fully reversible      stops NEW copies today
  2   shorten retention on the worst file   minutes   reversible            shrinks the window
  3   purge existing copies                 days      NOT reversible        needs an owner list first
  4   allowlist the event builders          weeks     reversible by revert  the actual fix
  5   wrapper type on the fields            weeks     reversible by revert  makes step 4 hold
  6   remove the collector rule             minutes   reversible            only after 4 and 5 are verified

우선순위를 건수가 아니라 파급 범위로 매긴 것이 8-4다. 위험 키 수와 보존 일수와 사본 목적지 수를 곱했다. 그러자 조용하지만 일 년 보관되며 세 곳에 복제되는 로그가 시끄럽지만 삼 개월만 남는 로그보다 위로 올라왔다. 건수로 정렬했다면 순서가 반대였을 것이다.

도입 순서에서 논쟁이 되는 지점은 하나다. 수집기부터인가 코드부터인가. 8-5의 답은 수집기부터이고, 이유는 「그게 더 나은 해결책이라서」가 아니다.

단계효과 범위걸리는 시간되돌리기한계
1. 수집기 차단 규칙즉시 전역분완전히 되돌림2절의 패턴 한계 그대로
2. 보존 기간 단축해당 로그분되돌림이미 만들어진 사본은 그대로
3. 기존 사본 파기파기한 것만일불가소유자 목록이 먼저 있어야 함
4. 이벤트 조립 허용 목록배포된 서비스주코드 되돌리기서비스마다 따로
5. 래퍼 타입 적용감싼 필드주코드 되돌리기경계를 넘지 못함
6. 수집기 규칙 제거즉시 전역분되돌림4·5 검증 전에는 금지
  • 수집기 규칙이 먼저인 이유는 지혈대이기 때문이다. 배포 없이 즉시 전역에 적용되고, 틀렸으면 즉시 뗄 수 있다
  • 동시에 지혈대는 치료가 아니다. 이미 만들어진 사본에는 아무 효과가 없고, 그 자체가 2절에서 불완전하다고 확인한 패턴 매칭이다
  • 파기를 서두르면 안 된다. 되돌릴 수 없는 유일한 단계이고, 소유자 목록 없이 실행하면 「지웠다」고 말할 수 없다
  • 코드 수정을 4번과 5번 순서로 두는 이유는, 허용 목록이 범위를 고정하고 래퍼가 그 고정을 유지시키기 때문이다. 반대로 하면 감싸지 않은 새 필드가 계속 들어온다
  • 마지막 6번은 검증 후에만 한다. 검증 방법은 간단하다. 수집기 규칙을 끄고 스테이징에서 같은 스캔을 돌려 위험 키가 0인지 본다
  • 새 서비스에는 순서가 반대다. 처음부터 4·5만 하면 되고 수집기 규칙은 필요 없다

8.1 점검 목록

  • 로그 호출에 객체를 통째로 넘기는 곳이 있는지 찾았다 (전개·중첩·데이터베이스 행·요청 본문 포함)
  • 이벤트 객체를 만드는 지점에서 넣을 필드를 명시했다. 뺄 필드를 지정하지 않았다
  • 허용 목록을 로거 안이 아니라 이벤트 조립 시점에 적용했다
  • 버린 필드 개수를 함께 남겨 스키마 변경을 감지할 수 있게 했다
  • 민감 필드에 래퍼 타입을 적용했고, 네 개 훅을 전부 구현했다
  • 래퍼의 꺼내기 호출을 코드 검색해 사용처를 전부 확인했다
  • 에러 컨텍스트에 식별자만 넣도록 규칙을 세웠다
  • 검증 실패 메시지에 값 대신 필드 이름을 쓴다
  • 전용 에러 직렬화기가 무엇을 훑는지 확인했다
  • 부분 표시는 경계에서 한 번만 자르고, 원본과 같은 객체에 두지 않았다
  • 부분 값에도 원본과 같은 보존·접근 기준을 적용했다
  • 기존 로그를 키 이름 기준으로 훑고, 목록 밖 키 전부를 사람이 읽었다
  • 우선순위를 키 수 × 보존 일수 × 목적지 수로 매겼다
  • 로그 사본의 목적지 목록과 소유자를 문서로 만들었다
  • 개인정보 취급 범위와 보존 기간을 관련 법령과 사내 정책에 맞춰 확인했다

결론: 뺄 것을 고르지 말고 넣을 것을 골라라

실행해서 확인한 것을 한 줄씩 다시 놓으면 이렇게 된다. 객체를 통째로 넣는 코드는 코드 0줄 변경으로 새는 필드가 세 개 늘었다. 출력 단계 정규식은 무해한 형식 변형 아홉 개 중 일곱 개를 놓쳤고 동시에 민감하지 않은 값 두 개를 지웠다. 로그 한 줄은 평범한 운영만으로 아홉 벌이 됐고 마스킹이 고친 것은 그중 한 벌이었다.

반대편도 실행으로 확인했다. 네 개 훅을 덮은 래퍼는 실수 경로 열세 개에서 유출 0이었다. 넣을 필드를 정한 직렬화는 스키마가 세 방향으로 움직여도 아무것도 통과시키지 않았다. 같은 상황에서 뺄 필드를 정한 쪽은 셋 다 통과시켰다.

그래서 결론은 「마스킹을 더 잘하자」가 아니다. 마스킹은 마지막 방어선이다. 출력에서 가리는 방식은 패턴을 아는 것만 막고, 그 시점에는 이미 복제가 끝나 있다. 진짜 해법은 그 값이 로그 경로에 들어가기 전에 있고, 그 자리에서 쓸 규칙은 하나다. 뺄 것을 고르지 말고 넣을 것을 골라라. 모르는 필드를 만났을 때 버리는 쪽으로 기울어 있어야, 아무도 규칙을 갱신하지 않는 몇 년 동안 버틴다.

지금 당장 할 수 있는 일이 하나 있다. 로그 코드에서 객체를 통째로 넘기는 호출을 하나만 찾아, 그 객체의 필드 목록을 지금 출력해 보라. 그 목록을 마지막으로 확인한 것이 언제였는지 기억나지 않는다면, 그 사이에 무엇이 늘었는지도 모르고 있는 것이다. 8절의 2차 통과는 그 확인을 한 번에 끝내기 위한 절차다.

# 민감 정보를 발생 지점에서 막기 — 래퍼·허용 목록·진단 절차

> 출처: braindetox.kr — 마스킹은 출력에서 하면 늦다
> 근거: Windows 10 / Node.js v22.16.0 실행 검증
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 로그 경로를 점검해줘」라고 쓰면 됩니다.
> 아래 예시 값은 형식만 맞춘 가짜입니다. 자릿수만 맞추고 숫자는 전부 0입니다.
> 개인정보 취급 범위와 보존 기간은 관련 법령과 사내 정책을 확인해 정하세요.

## 0. 한 줄 원칙

마스킹은 마지막 방어선이다. 진짜 해법은 그 값이 로그 경로에 들어가지 않게 하는 것이고,
그 자리에서 쓸 규칙은 하나다. **뺄 것을 고르지 말고 넣을 것을 골라라.**

| 방식 | 모르는 필드를 만나면 | 판단 |
|---|---|---|
| 뺄 필드 목록 | 내보낸다 (fail open) | 스키마가 움직이면 샌다 |
| 넣을 필드 목록 | 버린다 (fail closed) | **이쪽을 쓴다** |
| 출력 정규식 | 형식이 다르면 통과 | 지혈대. 해결책 아님 |

## 1. 래퍼 타입 — 꺼내야만 원본이 나온다

네 개 훅을 **전부** 덮어야 한다. 하나라도 빠지면 그 구멍으로 다 나간다.

```js
const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // 유일한 출구. 이름이 있으므로 코드 검색으로 사용처를 전부 나열할 수 있다
  expose() { return this[RAW]; }

  toString() { return '[' + this.label + ' redacted]'; }   // 템플릿·결합
  toJSON()   { return '[' + this.label + ' redacted]'; }   // 직렬화
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }  // console.log
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }   // 암묵 변환
}
```

검증한 경로 13가지에서 유출 0:
템플릿 문자열 / 문자열 결합 / String() / 배열 join / JSON.stringify /
중첩 JSON / util.inspect / 중첩 inspect / format %s / format %j /
format %o / String.prototype.concat / + 연산자

주의:
- **절반만 구현하면 없느니만 못하다.** toString만 두면 직렬화·검사 출력에서 그대로 샌다
- 개발·테스트에서는 던지고 운영에서는 대체하는 절충이 흔하다. toJSON은 양쪽 다 대체 유지
- **경계를 넘지 못한다.** 직렬화해 보내면 상대는 자리표시자를 받는다. 받는 쪽에서 다시 감쌀 것

## 2. 허용 목록 직렬화 — 이벤트를 만드는 순간에 좁힌다

```js
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];

function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

// 좁히는 위치가 결정적이다. 로거 안이 아니라 여기.
function buildEvent(user) {
  const picked = allowlist(user);
  const droppedCount = Object.keys(user).length - Object.keys(picked).length;
  return { event: 'signup', user: picked, _dropped: droppedCount };
}
```

- 로거 안에서 좁히면 한 층 늦다. 에러 처리기 등 로거 위쪽은 여전히 넓은 객체를 본다
- 버린 개수를 남기면 **무엇이 바뀌었는지 말하지 않으면서** 스키마 변경을 알 수 있다
- 그 숫자가 갑자기 커지면 상류 변경 신호. 허용 목록 갱신을 검토

## 3. 에러 컨텍스트 규칙

- 검증 실패 메시지에 **값을 넣지 않는다.** 「형식 불일치, 필드 nationalId」로 충분
- 에러 컨텍스트에는 **식별자만**: 요청 아이디, 사용자 아이디, 주문 아이디
- 원인 체인으로 감싼 바깥 에러는 메시지가 깨끗해 보여도 **안쪽 컨텍스트를 끌고 간다**
- 미처리 예외는 **로거를 부르지 않아도** 런타임이 출력한다. 로그 호출 감사로는 안 잡힌다
- 기본 직렬화가 에러를 빈 객체로 만든다고 안심하지 말 것. **전용 직렬화기가 다시 집어넣는다**

## 4. 진단 절차 — 두 번 훑는다

1) **1차: 키 이름으로 훑는다** (값 모양이 아니라)
   - 중첩 키는 경로째로: context.cardNumber
   - 값 형식은 상류에 따라 달라지지만 키 이름은 비교적 안정적이다
2) **2차: 목록 밖 키를 전부 나열해 사람이 읽는다**
   - 이 목록은 유한하다. 한 번 읽으면 끝난다
   - 값 형식 스캔으로는 애초에 만들 수 없는 목록이다
3) **우선순위 = 위험 키 수 × 보존 일수 × 사본 목적지 수**
   - 건수로 정렬하지 말 것. 조용하지만 오래·널리 남는 로그가 위다

## 5. 도입 순서 — 되돌리기 어려운 순으로

| # | 단계 | 시간 | 되돌리기 | 얻는 것 |
|---|---|---|---|---|
| 1 | 수집기 차단 규칙 | 분 | **완전히 되돌림** | 오늘부터 새 사본 차단 |
| 2 | 보존 기간 단축 | 분 | 되돌림 | 노출 창을 줄임 |
| 3 | 기존 사본 파기 | 일 | **불가** | 소유자 목록이 먼저 |
| 4 | 이벤트 조립 허용 목록 | 주 | 코드 되돌리기 | **실제 해결** |
| 5 | 래퍼 타입 적용 | 주 | 코드 되돌리기 | 4를 유지시킴 |
| 6 | 수집기 규칙 제거 | 분 | 되돌림 | 4·5 검증 후에만 |

- 수집기부터인 이유는 더 나은 해법이라서가 아니라 **지혈대**이기 때문이다
- 신규 서비스는 순서가 반대다. 4·5만 하면 되고 수집기 규칙은 필요 없다

## 6. 점검 목록

- [ ] 로그 호출에 **객체를 통째로 넘기는 곳**을 찾았다 (전개·중첩·DB 행·요청 본문 포함)
- [ ] 이벤트 조립 지점에서 **넣을 필드를 명시**했다 (뺄 필드 지정 아님)
- [ ] 허용 목록을 **로거 안이 아니라 이벤트 조립 시점**에 적용했다
- [ ] 버린 필드 **개수**를 함께 남겼다
- [ ] 민감 필드에 래퍼를 적용하고 **네 개 훅을 전부** 구현했다
- [ ] 꺼내기 호출을 코드 검색해 **사용처를 전부** 확인했다
- [ ] 에러 컨텍스트에 **식별자만** 넣는 규칙을 세웠다
- [ ] 검증 실패 메시지에 **값 대신 필드 이름**을 쓴다
- [ ] 전용 에러 직렬화기가 **무엇을 훑는지** 확인했다
- [ ] 부분 표시는 **경계에서 한 번만** 자르고 원본과 같은 객체에 두지 않았다
- [ ] 부분 값에도 **원본과 같은 보존·접근 기준**을 적용했다
- [ ] 기존 로그를 **키 이름 기준**으로 훑고 **목록 밖 키 전부**를 읽었다
- [ ] 우선순위를 **키 수 × 보존 일수 × 목적지 수**로 매겼다
- [ ] 로그 사본의 **목적지 목록과 소유자**를 문서로 만들었다
- [ ] 취급 범위·보존 기간을 **관련 법령과 사내 정책**에 맞춰 확인했다

## 7. 하지 말 것

- ❌ 객체·DB 행·요청 본문을 **통째로** 로그에 넘기는 것 — 새 필드가 코드 0줄로 따라온다
- ❌ 출력 정규식 마스킹을 **해결책으로** 여기는 것 — 형식 변형에 뚫리고 무해한 값을 지운다
- ❌ 자른 값과 **원본을 같은 객체에** 두는 것 — 통째 로그 한 번에 둘 다 나간다
- ❌ 검증 실패 메시지에 **값을 넣는 것** — 스택 첫 줄에도 같이 들어간다
- ❌ 소유자 목록 없이 **파기부터** 하는 것 — 되돌릴 수 없는 유일한 단계다
- ❌ 수집기 규칙만 넣고 **끝났다고 하는 것** — 이미 만들어진 사본에는 효과가 없다
- ❌ 래퍼를 **절반만** 구현하는 것 — 안전해 보여서 더 위험하다
