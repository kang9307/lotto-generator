A Shell Command Does Not Decide What It Will Do Until It Runs - The Line Between Readable Structure and Unreadable Results

Parsing can be the first filter in a safety decision, but it can never be the security boundary

2026-09-10 Dev & Infra

Can you read a single line of shell and say what it will do? Most people assume they can. Yet put echo *.json in front of them and ask how many arguments this command receives, and no answer comes. The count is not inside those eleven characters. At the top of one repository that line expands into 43 words, and one directory below it expands into 1. Same text, different argument vector.

That property defines what kind of language the shell is. Shell source is not a program in itself so much as a set of directives that build a program at run time. The argument array that finally reaches execve is assembled not from text alone but from the file system at that instant, the environment, the output of preceding commands, and the state of shell options. Pinning that array down from text alone is impossible in principle.

None of which makes static analysis useless. Results are unreadable, but structure is readable. How many stages a pipeline has, which file descriptor a redirection binds, what sits in the command slot, where a subshell begins and ends are all settled by the text alone. The trouble starts when those two things are used without being distinguished. And one place they meet head-on is the gate that approves or refuses the shell commands an AI agent wants to run.

The occasion is unbash, a TypeScript parser that turns bash source into a position-annotated syntax tree without running it. The interesting part is the line the repository draws around itself. It does not execute code, does not perform shell expansion, does not provide a sandbox, and does not decide whether a command is safe. Those four clauses are the summary of this entire piece.

Every example below is read-only. The output came from GNU bash 5.2.37(1)-release (x86_64-pc-msys), and no example creates or deletes a file. None of these lines is written on the assumption that a reader will copy and run it — they are minimal examples meant to expose a property of the grammar. Destructive commands have been replaced with neutral ones throughout.

What analysing without executing precisely means

That phrase reads two ways. One is knowing what will happen without running it, and the other is reading only the structure of the text without running it. In a shell only the second is achievable.

The distinction looks minor and the consequences are opposite. Build a gate on the first reading and that gate reports having checked things it never checked. Build it on the second and the gate knows what it does not know, and hands anything unknown to the next line of defence. Two teams can use the identical parser and diverge exactly here.

Obtaining a syntax tree means breaking text into grammatical elements. This word is a command name, that word is an argument, this symbol is a pipe, that block is a subshell. Attach the start and end offsets in the original source to every element and an editor can put a marker on the exact line and column, and even a truncated input can return the partial tree built so far plus the position where it broke. These are facts about the text, and every one of them is true.

But they are not facts about execution. That the command slot contains the two characters ls is true. What those two characters become at run time is a separate question, and the answer lives not in the text but in that shell instance's alias table, function table, and PATH. The parser hands over the first kind of fact, and people routinely expect the second.

The line the parser draws around itself

The unbash README separates what it does from what it does not do. Tools that write down their own boundary are rare, and when one exists it is worth quoting directly.

Listed under grammar it handles: commands, control flow, pipelines, redirections and assignments; compound commands; parameter and word expansions; process substitution and nested substitution; coproc; here-documents and here-strings; C-style for; select; array assignment; extended globs; the case fall-through operators (;& and ;;&); and the bash 5.3 command substitution form. In short, most of bash grammar is covered.

Listed under what it does not do are four items. It does not execute code, does not perform shell expansion, does not provide a sandbox, and does not decide whether a command is safe. Beyond that, PowerShell and cmd.exe are explicitly out of scope, and it is explicitly not the thing to reach for when parsing process arguments. Recovery has a stated limit too — error recovery is bounded for deeply nested parameter and arithmetic expansions.

The security sentence is unusually honest. The README places a requirement on the caller: a security-sensitive consumer must inspect the word parts, the nested scripts, and the error list of every parsed script. Invert that sentence and it says this. The mere fact that a parser returned a tree approves nothing. Whoever receives the tree has to build decision rules on top of it, and the quality of those rules is the quality of the gate.

Size and performance are stated as well. It is a zero-dependency synchronous API, 80KB minified and 19KB gzipped, under the ISC licence. Throughput figures and a speed multiple against another parser appear in the README too, but those were measured in the repository's own environment and are not numbers to carry around without their conditions.

Five reasons the shell resists static analysis

This is the heart of the piece. What makes the shell hard to analyse statically is not that its grammar is complicated. It is that the grammar is deliberately designed to pull run-time state into the meaning of a line. It splits five ways.

1. A glob is decided by the directory at that instant

How many words a pattern expands into is not in the pattern. It is in the file system. And the behaviour when nothing matches forks three ways depending on shell option state.

# Same text, different directory - different word count
$ echo *.json          # repository top level
PHASE2_STAGES.json _h2_index.json ... package.json trend_topics.json   # 43 words

$ echo *.json          # the posts directory below it
index.json                                                             # 1 word

# When nothing matches - the default leaves the pattern in place
$ echo zzz*.nosuch
zzz*.nosuch

$ ( shopt -s nullglob; echo "[" zzz*.nosuch "]" )
[ ]                                              # the word disappears

$ ( shopt -s failglob; echo zzz*.nosuch )
bash: no match: zzz*.nosuch                      # the command never runs

All three lines carry the identical pattern. The outcomes fork into one word, zero words, and no execution at all. Which one you get depends on the options that shell instance has enabled, and that state is nowhere in the text.

So what static analysis can say is roughly this. There is a pattern in this position. This word has a variable argument count. The lower bound is zero and the upper bound is undetermined. What it cannot say is the count and every one of the values. How glob syntax itself differs from regular expressions is handled separately in Globs Are Not Regex - When the Asterisk Means Two Different Things.

2. Variable expansion and command substitution need execution to settle

The value of $VAR lives in the environment, and the value of $(...) or a backtick pair only appears once the command inside has actually run. The latter is particularly awkward because the value is not even deterministic. Evaluate the same text twice and different values commonly come back.

# Command substitution - the inside must run before a value exists
$ echo "$(echo one two)"
one two

# Same text, a different value each time
$ echo $RANDOM; echo $RANDOM
11194
27279

# Expansion results are not reparsed - they never become operators
$ v='echo a; echo b'; $v
a; echo b

$ v='echo a | tr a-z A-Z'; $v
a | tr a-z A-Z

Those last two matter. Put a ; or a | inside a variable and they do not become operators; they stay ordinary arguments. That property is why the skeleton static analysis produces mostly holds. Expansion does not conjure new structure.

What static analysis can say is that a substitution exists and what the nested script inside it looks like. The inside of $(...) is shell grammar too, so the command names and pipeline structure in there are lexically readable. That is exactly why the README demands that nested scripts be inspected. What it cannot say is the value, and how that value will move the argument boundaries of the enclosing command.

3. The same name points at different things

What the word in the command slot executes is decided by name resolution rules: alias first, then function, then builtin, and finally a walk of PATH. The same name can exist at all four levels simultaneously.

# Four candidates coexisting under one name
$ type -a echo
echo is aliased to `echo A'
echo is a function
echo is a shell builtin
echo is /usr/bin/echo

# A function shadows an external command
$ printf() { builtin printf "FUNC:%s\n" "$*"; }; printf hello
FUNC:hello

# Narrow PATH and what resolved a moment ago no longer resolves
$ type -p node
/c/Program Files/nodejs/node
$ PATH=/usr/bin; type -p node || echo "not found"
not found

# Aliases even have timing - define and use on one line and it does not apply
$ shopt -s expand_aliases; alias hi="echo ok"; hi
bash: hi: command not found          # same line

$ shopt -s expand_aliases
$ alias hi="echo ok"
$ hi
ok                                    # next line

That last example shows the limit most sharply. Alias expansion happens while the shell reads a line, and the alias table at that moment is that shell's run-time state. In other words, execution state intrudes as early as the parsing stage. Feed the same text to a different shell instance and even the parse can differ.

What static analysis can say stops at there is this text in the command slot. What that text resolves to at run time is out of reach. Keeping that distinction makes gate verdicts precise. Write not this command is ls but the word in this command slot is ls.

4. eval turns a string back into code

Point 2 said expansion results are not reparsed. eval is the exception to that rule. It reads the string it receives back in as shell source.

# Expansion alone yields a single command
$ v='echo a; echo b'; $v
a; echo b

# eval turns the same string into two commands
$ v='echo a; echo b'; eval "$v"
a
b

# The string can carry assignments and arithmetic expansion too
$ s='a=1; echo $((a+1))'; echo "$s"
a=1; echo $((a+1))
$ eval "$s"
2

The instant eval appears, a syntax tree is born at run time. Static analysis can say a new script comes into being here and no more, and since the content of that script is a string value, you are back in the problem from point 2. . and source have the same character. They pull the contents of another file into the current shell, so what that file holds is outside the text.

5. Word splitting and quoting move argument boundaries

How many arguments an expanded value becomes is decided by whether it was quoted and by the IFS variable. An unquoted expansion result is split, a quoted one is not, and what counts as a separator is set by a single run-time variable.

$ x='a b c'

$ set -- $x;   echo "argc=$#"      # unquoted - split into three
argc=3
$ set -- "$x"; echo "argc=$#"      # quoted - stays one
argc=1

# An empty value vanishes entirely if it is not quoted
$ e=''
$ set -- a $e b;   echo "argc=$#"
argc=2
$ set -- a "$e" b; echo "argc=$#"
argc=3

# The separator is decided by a run-time variable
$ y='a:b:c'
$ ( IFS=:; for w in $y; do printf ' [%s]' "$w"; done; echo )
 [a] [b] [c]

The second example bites gate design directly. An argument can disappear wholesale. The text carries three words, and what runs is a two-element argument vector. Any rule that decides by counting positions goes wrong right here.

What static analysis can say is the possibility verdict this word is unquoted and therefore may be split. Since quoting itself is entirely lexical, that verdict is precise. The count is still unreadable. Which quote turns off which expansion is laid out in Shell Quoting Rules - What Each Quote Actually Blocks.

The jurisdiction set by expansion order

The five branches look unrelated, and they are bound together by one specification. The GNU Bash manual fixes the order of expansions like this: brace expansion; then tilde expansion, parameter and variable expansion, arithmetic expansion and command substitution (left to right); then word splitting; then filename expansion; and finally quote removal.

Only brace expansion, word splitting, and filename expansion can increase the number of words; the other expansions expand a single word to a single word.

That single line draws the jurisdiction of static analysis exactly. Two of the three stages that can change the word count depend on run-time state. Word splitting depends on IFS and on expanded values; filename expansion depends on directory contents and shell options. That is why the argument vector is not statically determined.

The remaining one, brace expansion, is purely lexical. It consults neither the file system nor the environment. It is the sole exception, and therefore the only expansion whose result a parser can state exactly.

# Brace expansion never looks at the file system
$ echo {a,b}.txt
a.txt b.txt

$ echo /nonexistent/{p,q}/r          # expands even for a path that does not exist
/nonexistent/p/r /nonexistent/q/r

$ set -- {a,b,c}.txt; echo "argc=$#"  # the word count is statically settled
argc=3

# Quote it and the expansion does not happen - also a lexical verdict
$ echo "{a,b}.txt"
{a,b}.txt

The POSIX shell specification writes the order slightly differently. Tilde expansion, parameter expansion, command substitution and arithmetic expansion come first; then field splitting; then pathname expansion (unless set -f is in effect); and quote removal, if performed, is always last. Brace expansion is absent from that list.

StageOrder in the bash manualOrder in the POSIX specResult statically settled

The last column of that table is half of this article. The two settled rows are stages where the grammar closes over itself; everything else drags in outside state. What the parser sees is the top of this ladder, and what execution sees is the bottom. In between, words multiply, shrink, and disappear.

What is settled before execution anyway

Everything so far was the side that does not work. From here on is the side that does, and the list is longer than people expect.

# Pipeline structure is lexically settled
$ echo hi | tr a-z A-Z
HI

# A redirection may precede the command name - first word is the command is wrong
$ 2>/dev/null echo redir-first-ok
redir-first-ok

# Whether a leading word is an assignment or a command is also lexical
$ A=1 B=2 env | grep -E '^(A|B)=' | sort
A=1
B=2

# Subshell boundary - parentheses make a new shell, braces do not
$ x=1; ( x=2; echo "inner=$x" ); echo "outer=$x"
inner=2
outer=1
$ x=1; { x=2; echo "brace=$x"; }; echo "after=$x"
brace=2
after=2

The fact that a redirection may sit before the command name has a large practical consequence. Any checker built on the rule that the first word of a line is the command name breaks immediately on this form. A structural parser splits it correctly into one redirection and one command. Conversely there are statements holding only assignments and no command at all, and the emptiness of the command slot in that case is also statically settled.

That subshell boundaries are settled means you can say which assignments leak outward and which stay trapped without running anything. The practical accidents that boundary causes are covered in Why Variables Vanish Inside a Piped while Loop - Subshells 2026.

# Flow operators - candidates settle, execution is decided by exit status
$ true && echo ran-A; false && echo ran-B; echo always-C
ran-A
always-C

# Whether a here-document body expands is a lexical verdict on the delimiter
$ v=VALUE; cat <<EOF
plain: $v
EOF
plain: VALUE

$ v=VALUE; cat <<"EOF"
quoted: $v
EOF
quoted: $v

What flow operators settle is the upper-bound set of commands that could run. Which one actually runs depends on exit status and is unsettled, but the upper bound alone is enough for an allowlist verdict. If every command in that upper bound is on the allowlist, the safety condition holds whichever branch is taken. What exit status genuinely catches and misses is set out in Shell Exit Codes and set -e - What It Catches and What It Misses.

The here-document side is clean as well. Look only at whether the delimiter is quoted and you know whether expansion happens inside the body. A quoted delimiter makes the body pure text, so a string that looks like a command in there is not a command. An unquoted delimiter keeps substitution alive inside, so the body has to be counted as a nested script. That verdict is lexical and exact. Using here-documents themselves is covered in Here-Documents in Practice - Turning Expansion Off and On, and the Indentation Trap.

Compress all of it into one sentence and you get this. Structure is readable and results are not.

The last row is the one most often forgotten. Some arguments are themselves programs written in another language: the script body handed to a pattern-processing tool, the command string handed to a remote shell, everything trailing a tool that assembles other commands from its input. To the shell parser those are a single quoted word. Even a flawless shell AST has no jurisdiction inside them.

What leaks when you filter by string matching

Implement block the dangerous commands with string matching and what you manufacture is false reassurance. There are three layers of reason.

  • The set of spellings is open. The shell offers several routes to the same word. This piece does not enumerate them — the point is not the length of the list but the property that the list does not close. A rule that blocks by enumeration collapses on the one form that was not enumerated.
  • What is inspected is pre-expansion text. The argument vector that actually runs is assembled after descending the whole ladder from section 4. String matching only ever looks at the top rung. What a harmless-looking word up there becomes down below was never inspected.
  • There are no boundaries. A regular expression does not tell a command slot from an argument slot, from the inside of a string, or from the inside of a comment. So false passes and false blocks arrive together. Mistaking a word inside a here-document body for a command and blocking a legitimate script, and missing a form where a leading redirection means the first word is not the command, come from one cause.

The third is especially awkward because the failure runs both ways. A checker that fails in one direction can be tuned: too permissive, tighten the rules; too strict, carve exceptions. A checker that fails in both directions blocks legitimate work as you tighten and loosens the verdict as you relax. The two dials are bolted to the same axis.

And in practice the false blocks bite first. When legitimate commands keep getting refused, people look for ways around the gate or loosen the rules wholesale. Accumulated false blocks end in false reassurance. That is the path by which a string-matching gate gets worse over time.

What structural analysis catches and still misses

Start with what changes once you hold a syntax tree.

  • Slots are distinguished. Command slot, argument slot, and string interior are different nodes. Words inside strings are never counted as commands, which cuts false blocks sharply.
  • Every pipeline stage is counted. Passing something because you only looked at the front or only at the tail becomes structurally impossible.
  • Nested scripts are counted as separate sets. Commands inside command substitutions, process substitutions and unquoted here-document bodies each get their own nodes.
  • Redirection placement stops mattering. Before or after the command name, it reads as the same structure.
  • Parse failure becomes a signal. The rule reject input that does not form valid syntax becomes available. String matching has no such axis.
  • Position data records the reasoning. When the log says which node at which line and column caused the refusal, the rule can be fixed.

And yet things remain out of reach, and that list maps exactly onto section 3.

  • Expansion results. What a glob expands into and what a substitution returns are not in the tree.
  • Name resolution. Whether the command-slot word is an alias, a function or an executable is that shell's state.
  • Code born after eval or source. The tree only says a new tree appears here.
  • Argument semantics. Another language embedded in an argument string sits outside shell grammar.
  • The magnitude of side effects. The same command has a completely different blast radius depending on the directory it runs in, and the working directory is execution state.
Inspection methodWhat it seesFalse passesFalse blocksActs on expansion results
String and regex matchingPre-expansion text, no slot distinctionMany - the spelling set is openMany - counts words in strings and commentsNo
Structural verdictsSyntax tree with slots distinguishedFewer but present - name resolution and expansionSharply reducedNo

The last column of that table sets the ordering. The first three rows all look at text; only the last looks at outcomes. Trying to settle by text what is not settleable in principle can raise accuracy but never manufacture a guarantee.

Isolation, allowlist, blocklist - in that order

The strength of the three defences is set by what each one acts upon.

  • Isolation acts on outcomes. Whatever a command expands into, if file system reach, network reach and privileges are capped from outside, the damage has an upper bound. That bound holds without reading a single character of the text.
  • An allowlist acts on the complement. Only enumerated things pass, so everything unenumerated is stopped. The freedom of spelling flips from an attack surface into a reason for refusal. Meet an unknown form and refusal is the default.
  • A blocklist acts only on what was enumerated. It stops the known. One new spelling outside the list is one hole.

Hence the order: isolation, then allowlist, then blocklist. This is not to say blocklists are useless. They catch obvious mistakes early and tell a person about them. What matters is that the moment a blocklist becomes the first line of defence, it becomes false reassurance.

Implement the allowlist through structural parsing and it takes this shape. It is not filtering out dangerous things; it is defining the subset of the grammar you are willing to accept.

  • Refuse if parsing failed or the error list is not empty.
  • Refuse if any construct falls outside the permitted node types. eval, source, process substitution, coproc and nested command substitution are safer placed on the unknown side.
  • Refuse if the command-slot word is off the allowlist. Apply the same rule to every pipeline stage and every command in every nested script.
  • Refuse an unquoted expansion in an argument, or admit it only with isolation strength raised a notch.
  • Treat a redirection target that contains an expansion the same way.
  • Run whatever passes inside isolation anyway. Clearing the gate does not exempt anything from isolation.

What matters in that list is that every verdict tilts toward refusal. All of static analysis's uncertainty has to be loaded onto the refusal side. Load the unsettled onto the pass side and that uncertainty becomes risk verbatim.

Where it earns its keep and where it cannot

There are clear places a shell parser earns its keep, and they share a trait. They are places where a failed verdict does not itself become an incident.

The fourth row, log normalisation, is less discussed and is where static analysis fits most cleanly. Aggregate executed command strings verbatim and cardinality explodes because every argument differs. Parse them structurally, keep only the command name and option shape, and replace argument values with placeholders, and commands of the same shape collapse into one bucket. Here, not knowing the expansion result is an advantage: what you want is the shape, not the value.

The last two rows, by contrast, do not improve with a better parser. It is not a question of parser maturity but that the question itself cannot be answered from text. Dialect - which shell are you parsing

One axis remains. Fail to confirm which dialect the parser targets and the verdicts drift.

The POSIX shell specification and bash overlap heavily without being the same. Arrays are absent from the POSIX spec, and so is process substitution. The current edition lists [[ and ]] among words that an implementation may recognise as reserved without specifying their meaning. The dollar-prefixed single-quote form, on the other hand, has a section of its own in the current edition. Some things match on both sides, such as turning off pathname expansion with set -f, and some exist on one side only, such as brace expansion.

On top of that comes the mismatch between a name and its referent. In the environment that produced the output above, sh is not a separate implementation; it is bash. sh -c 'echo $BASH_VERSION' returns 5.2.37(1)-release. In other words, testing with sh in that environment is not testing POSIX. Point 3 of section 3, the same name points at different things, applies to the shell itself.

How does that drift show up in a gate? Run a script beginning with #!/bin/sh through a bash-grammar parser and you can admit something that will be a syntax error in the real execution environment. The reverse exists too. Check a script that uses bash extensions against a POSIX-only grammar and it fails to parse, and in a gate that treats parse failure as refusal, a perfectly good script is blocked.

That last row is also the scope unbash states for itself. Windows-family shells are out. If one gate accepts commands from several platforms, each dialect needs its own parser and its own allowlist. That different shells differ from the quoting rules of the same string upward is shown through name handling in Why the Same Filename Looks Different in Each Shell - Where Git Bash and PowerShell Disagree.

Wiring order for a command gate

Translate all of the above into actual wiring and the order comes out like this.

  1. Stand up isolation first. Before attaching a parser, create the state in which the blast radius is fixed no matter what a command does. Without this step every later step is best-effort only.
  2. Pin the dialect. Make which shell will execute and which grammar will inspect the same thing. If they differ, the verdict and the execution are reading different languages.
  3. Treat parse failure as refusal. If the error list is not empty, nothing passes.
  4. Narrow to a grammar subset. Refuse anything outside the permitted node types. When new grammar becomes necessary, widen the rule explicitly.
  5. Apply the command-name allowlist. Apply it without exception to every pipeline stage and every command in every nested script.
  6. Demote anything with expansion left in it. An unquoted expansion or a glob is refused, or sent to tighter isolation.
  7. Record the reasoning. Log which node at which position caused the refusal. Refusals without reasoning end with someone switching the rule off entirely.

Keep that order and the parser's role falls naturally into place. The parser is not the gate's guard; it is the gate's front desk. It checks that the form is filled in correctly, sends back anything it does not recognise, and passes what clears through to the real boundary inside.

Return to the opening sentence and it resolves like this. Reading one line of shell and saying what it will do is impossible. But saying what shape it has is possible, and deciding whether that shape falls inside a defined set is possible too. Changing the question a gate has to answer from the first to the second — that is what static analysis actually does.

What could not be confirmed

  • The filename expansion page of the GNU Bash manual — the page returned HTTP 429 on both attempts. That an unmatched pattern is left in place, and the effects of nullglob and failglob, rest only on the execution output above and were not cross-checked against the manual clause. The expansion order clause was quoted from the manual directly.
