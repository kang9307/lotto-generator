계기 — AI 에이전트와 오디오 편집기의 접점

소프트웨어 엔지니어링 영역에서 거대언어모델(LLM) 기반의 코딩 에이전트는 터미널 CLI와 편집기 인터페이스를 통해 자율적인 코드 수정과 빌드, 테스트를 수행하는 단계에 도달했다. 그러나 멀티미디어 도메인, 특히 오디오 신호 처리와 타임라인 기반의 멀티트랙 편집 작업은 대용량 바이너리 스트림과 마이크로초 단위의 샘플 타이밍 정밀도를 요구하기 때문에 텍스트 중심의 에이전트가 직접 제어하기 어려운 영역으로 여겨져 왔다.

전통적인 디지털 오디오 워크스테이션(DAW)은 수많은 가상 악기, VST/AU 플러그인 체인, 복잡한 믹서 라우팅을 중심으로 설계되어 있다. 이러한 복잡성은 팟캐스트 녹음이나 음악 트랙의 특정 구간을 자르고 재배치하며 불필요한 노이즈를 제거하는 일상적인 편집 작업에서조차 과도한 인지적 부담을 발생시킨다. 또한 대부분의 상용 DAW는 외부 프로세스가 프로젝트 내부 구조에 프로그래밍 방식으로 안전하게 접근할 수 있는 개방형 인터페이스를 제공하지 않는다.

Audionaut는 이러한 배경 속에서 음악, 팟캐스트, 멀티채널 녹음 작업을 위한 무료 오픈소스 멀티트랙 오디오 편집기로 공개되었다. 전체 제작 환경을 포괄하는 무거운 DAW를 지향하는 대신, 타임라인에서 클립을 정밀하게 분할하고 조합하는 핵심 편집 작업에 집중한다. 특히 주목할 부분은 모델 컨텍스트 프로토콜(Model Context Protocol, MCP)을 통해 Claude와 같은 외부 AI 에이전트가 실행 중인 편집 세션을 직접 제어할 수 있도록 설계된 아키텍처다.

AI 에이전트에게 오디오 편집 권한을 부여할 때 시스템 관리자와 사용자가 가장 먼저 검토해야 하는 기술적 과제는 명확하다. 첫째, 수 기가바이트에 달하는 사용자의 오디오 자산이 외부 클라우드 서비스로 전송되는지 여부다. 둘째, 에이전트가 비결정론적으로 내린 편집 명령이 기존 작업물을 파괴하지 않고 안전하게 되돌려질 수 있는가 하는 점이다. 셋째, 실시간으로 재생되거나 녹음 중인 타임라인 상태와 에이전트 명령 간의 경합을 어떻게 제어하는가이다. 이 글에서는 Audionaut의 공개 명세를 바탕으로 이러한 안전장치와 아키텍처 설계를 분석한다.

오디오 처리 위치와 보안 — 업로드 없는 로컬 파이프라인

기업 및 개인 작업 환경에서 음성 녹음 데이터와 미발표 음악 음원은 민감한 개인정보이자 독점적 지식재산에 해당한다. 최근 클라우드 기반 생성형 AI 오디오 서비스의 확산으로 인해 오디오 편집 자동화 도구가 내부 데이터를 외부 서버로 업로드하는 것이 아닌가 하는 보안상 우려가 빈번하게 제기된다.

Audionaut 공식 명세서(docs/features.md)는 음원 분리 및 오디오 처리 파이프라인에 대해 다음과 같이 명시하고 있다: 「htdemucs via demucs.cpp, running locally. Nothing is uploaded.」 즉, 모든 오디오 신호 연산과 분리, 분석은 사용자의 로컬 컴퓨터 내부에서 네이티브 바이너리로 실행되며, 오디오 샘플이나 파형 데이터가 네트워크 외부로 전송되지 않는다.

AI 에이전트와의 상호작용 역시 오디오 파일 자체를 모델의 프롬프트 컨텍스트에 삽입하는 방식이 아니다. 외부 LLM 에이전트는 타임라인의 구조적 메타데이터(트랙 목록, 리전 시작점 및 종료점, 클립 배치 시간, 페이드 곡선 정보)만을 텍스트 JSON 형태로 수신하고, 실행하고자 하는 편집 동사(verb)를 명령으로 전달한다. 실제 오디오 파일의 디코딩, 파형 절단, 리샘플링, 믹싱 연산은 로컬 머신에 상주하는 C++ 애플리케이션 코어가 직접 수행한다.

또한 프로젝트의 원격 원격 측정(telemetry) 및 익명 사용 통계 전송과 관련하여, 소프트웨어는 사용자가 명시적으로 동의(opt-in)한 경우에만 제한적으로 전송하도록 설계되어 있다. 헤드리스 환경에서 실행되는 CLI 도구에서도 환경 설정이나 인수를 통해 사용 통계 전송을 완전히 비활성화할 수 있어 격리된 망 환경에서도 안전한 운용이 가능하다.

MCP 연동 아키텍처 — live state와 파일 직접 수정의 분리

AI 에이전트가 Audionaut를 조작하는 인터페이스는 표준 모델 컨텍스트 프로토콜(MCP) 서버인 audionaut-mcp 패키지를 통해 제공된다. 사용자는 Node.js 18 이상이 설치된 환경에서 다음 명령어로 Claude Code 또는 호환 클라이언트에 MCP 도구를 등록할 수 있다.

claude mcp add audionaut -- npx -y audionaut-mcp

Audionaut의 헤드리스 실행 아키텍처는 두 가지 진입점을 가진다. 하나는 테스트 및 스크립트 빌드 환경에서 제공되는 독립형 콘솔 바이너리인 audionaut-cli이며, 다른 하나는 GUI 애플리케이션 바이너리 자체다. GUI 바이너리는 동사 인수를 전달받으면 헤드리스 모드로 명령을 처리하고 종료할 수 있도록 구현되어 있다.

프로젝트가 데스크톱 GUI 앱에 열려 있는지 여부에 따라 에이전트 명령의 전달 경로와 실행 대상은 엄격하게 이원화된다. 이 구조는 파일 손상과 상태 불일치를 원천적으로 방지하기 위한 핵심 설계다.

  • GUI 앱에 프로젝트가 열려 있는 경우: 에이전트가 audionaut-mcp를 통해 호출한 명령은 디스크 상의 프로젝트 파일로 직접 향하지 않는다. 대신 실행 중인 Audionaut GUI 프로세스로 명령이 직접 인계(hand over)된다.
  • 라이브 상태(live state) 복사본 실행: 명령은 사용자가 화면에서 보고 있는 미저장 변경사항이 포함된 현재 메모리 상태의 복사본 위에서 평가된다.
  • 디스크 쓰기 우회: 에이전트 명령이 실행되더라도 프로젝트 메타데이터 파일인 Project.json에는 즉각적인 쓰기가 발생하지 않는다. 디스크에 영구 저장하는 권한과 책임은 온전히 인간 사용자에게 남겨진다.
  • GUI 미실행 상태: 데스크톱 앱에서 프로젝트가 열려 있지 않은 독립 실행 상태에서는 CLI 바이너리가 Project.json 파일을 직접 읽고 수정한 뒤 디스크에 기록한다.
  • 연결 실패 시 안전 차단: 앱이 특정 프로젝트를 열어 점유하고 있는 상태에서 에이전트 명령이 통신 장애 등으로 앱 프로세스에 도달하지 못할 경우, 시스템은 디스크 파일로 폴백(fallback)하여 덮어쓰지 않고 즉시 실패(fail)를 반환한다. 이는 미저장 작업이 실수로 유실되는 것을 방지하기 위함이며, 의도적으로 디스크 파일을 직접 수정하려면 AUDIONAUT_AGENT_ROUTING=0 환경변수를 설정해야 한다.

프로젝트 패키지 내부에는 애플리케이션의 비정상 종료 시 복구를 위한 스냅숏인 Autosave.json과 어떤 프로세스가 현재 프로젝트를 점유하고 있는지 식별하는 마커인 Host.json 파일이 존재하며, 외부 도구가 이 내부 상태 파일을 임의로 변조하지 못하도록 보호한다.

안전 제어와 충돌 방지 — 사용자 우선권과 개별 Undo

비동기적으로 동작하는 자율 에이전트가 오디오 타임라인을 조작할 때 발생할 수 있는 가장 심각한 위험은 사용자의 수동 편집 작업과의 충돌이다. 사용자가 특정 트랙의 클립을 미세 조정하고 있는 도중에 백그라운드 에이전트가 트랙 전체를 재정렬한다면 작업 흐름이 완전히 붕괴될 수 있다.

Audionaut는 사용자 우선권(User Precedence) 원칙을 아키텍처 수준에서 강제한다. 에이전트 명령이 처리되는 도중에 사용자가 마우스나 키보드로 프로젝트 상태를 변경하면, 시스템은 진행 중이던 에이전트 명령의 실행 결과를 즉시 폐기(drop)한다. 그리고 에이전트 측에는 작업이 취소되었음을 알리고 변경된 최신 상태를 바탕으로 명령을 다시 시도하도록 응답을 반환한다.

또한 타임라인의 실시간 상태에 따른 작업 거부 정책이 마련되어 있다. 사용자가 오디오 인터페이스를 통해 새로운 트랙을 실시간 녹음(recording) 중일 때에는 모든 외부 에이전트 명령이 거부된다. 마찬가지로 오디오 전송부(transport)가 재생(playing) 중일 때에는 내보내기(export) 명령이 거부되어 버퍼 언더런이나 불완전한 렌더링을 차단한다.

에이전트가 성공적으로 수행한 모든 변경 작업은 GUI 상에서 완전한 가시성과 통제권을 제공받는다. 주요 제어 메커니즘은 다음과 같다.

  • 개별 Undo 단계 생성: 에이전트의 단일 도구 호출은 사용자의 실행 취소 내역(Undo history)에 정확히 하나의 독립된 단계로 기록된다.
  • 동사 기반 라벨링: 실행 취소 목록에는 에이전트가 호출한 명령 동사의 이름이 명시적으로 라벨링되어 어떤 작업이 수행되었는지 식별할 수 있다.
  • 창 제목 시각 경고: 에이전트에 의해 프로젝트 내용이 수정되면 윈도우 제목 표시줄에 「Edited By Agent」라는 시각적 표기가 활성화된다.
  • 단축키 기반 원복: 사용자는 표준 실행 취소 단축키(macOS 기준 ⌘Z)를 한 번 누르는 것만으로 에이전트의 수정을 즉각 이전 상태로 되돌릴 수 있다.
  • 디스크 원복(Revert to Saved): 세션 전체의 변경 사항을 디스크에 저장된 마지막 커밋 시점으로 완전히 되돌리는 기능도 기본 지원된다.

음원 분리와 분석 엔진 — Demucs와 Essentia의 로컬 구동

Audionaut는 복잡한 오디오 편집을 자동화하기 위해 두 가지 핵심 오디오 인텔리전스 라이브러리를 서브모듈 형태로 내장하고 있다. 오디오 신호 분석을 담당하는 Essentia와 딥러닝 기반 음원 분리를 담당하는 Demucs다.

음원 분리 기능은 Meta의 Demucs 아키텍처를 C++ 환경으로 포팅한 demucs.cpp 서브모듈을 통해 구현되었다. 사용자가 특정 오디오 클립에 대해 음원 분리를 실행하면 하나의 클립이 드럼(Drums), 베이스(Bass), 보컬(Vocals), 기타/나머지 소리(Other)의 4개 독립 트랙으로 분할된다. 이 처리에 필요한 htdemucs 모델 가중치는 약 80MB 크기이며, 기능이 처음 호출될 때 단 한 번 로컬로 다운로드된다. 다운로드된 가중치는 사용자의 컴퓨터에 저장되며 연구 목적(research use only) 라이선스가 적용된다.

음악 분석 및 자동 편집(Auto Edit) 기능은 UPF(Universitat Pompeu Fabra)의 오픈소스 오디오 분석 라이브러리인 Essentia의 정적 빌드에 연결되어 구동된다. Essentia 엔진이 제공하는 주요 기능은 다음과 같다.

  • 세그먼트 경계 감지(SBic): 베이지안 정보 기준(BIC)을 활용하여 오디오 스트림 내에서 음악적 구성이나 음향적 특성이 변화하는 구간 경계를 자동으로 식별한다.
  • 소리 시작 지점(Onset) 및 박자 추적: 두 가지 독립된 알고리즘을 통해 퍼커션 어택이나 음의 시작점을 감지하고 전체 트랙의 템포 및 비트 그리드를 추적한다.
  • 프로젝트 캐싱 및 시각 오버레이: 분석된 세그먼트와 비트 위치는 프로젝트 내부에 캐싱되어 반복 연산 없이 타임라인 트랙 상에 시각 오버레이로 즉시 표시된다.
  • 자동 분할(Create Segments): 분석된 음악적 경계점에 맞춰 클립을 자동으로 분할하며, 분할 접합부마다 부드러운 전환을 위한 자동 크로스페이드(crossfade) 옵션을 적용할 수 있다.
  • 자동 재조합(Assemble): 트랙 내에 생성된 리전들을 지정된 길이에 맞춰 순차적으로 또는 무작위(shuffled)로 재배치하여 새로운 편곡 구성을 자동으로 생성한다.

Essentia 빌드는 선택 사항(optional)으로 구성되어 있어, C++ 빌드 환경에 해당 종속성이 없더라도 ESSENTIA_ENABLED 플래그가 비활성화된 상태로 기본 편집 기능과 음원 분리 기능만 포함된 컴파일이 가능하다.

플랫폼 제약과 macOS 샌드박스 경계

Audionaut는 Windows, macOS, Linux 환경에서 네이티브로 실행되는 크로스 플랫폼 애플리케이션이다. 그러나 운영체제별 보안 모델의 차이로 인해 AI 에이전트 및 CLI 환경을 구성할 때 반드시 준수해야 하는 파일 경로 제약이 존재한다.

macOS 환경에서 배포되는 공식 GUI 애플리케이션은 Apple의 앱 샌드박스(App Sandbox) 정책 하에서 실행된다. 이로 인해 앱 자체뿐만 아니라 앱이 서브프로세스로 기동하는 모든 헤드리스 명령 역시 샌드박스 격리 규칙을 엄격히 적용받는다. 샌드박스 내에서 앱이 접근 권한을 가지는 표준 디렉터리는 사용자의 음악 폴더(~/Music)로 한정된다.

따라서 macOS 환경에서 Claude Desktop이나 Claude Code와 같은 AI 에이전트를 연동할 때, 작업 대상인 .audium 프로젝트 파일과 가져올(import) 원본 오디오, 그리고 내보낼(export) 대상 디렉터리는 반드시 ~/Music(예: ~/Music/Audionaut) 경로 하위에 위치해야 한다. 만약 에이전트가 다른 디렉터리에 위치한 파일 경로를 지정하여 명령을 실행할 경우, audionaut-mcp 서버는 실행 전에 이를 감지하고 sandbox_denied 에러를 반환하며 작업을 거부한다.

반면 사용자가 소스 코드에서 직접 빌드한 개발자용 콘솔 바이너리 audionaut-cli는 이러한 샌드박스 제한을 받지 않으며, Windows(Audionaut.exe) 및 Linux(.deb 또는 AppImage) 네이티브 바이너리 역시 운영체제 파일 권한 내에서 자유로운 경로 접근이 허용된다.

  • macOS 공식 GUI 앱: Apple App Sandbox 제약으로 인해 ~/Music 디렉터리 하위 경로에만 접근 가능
  • macOS 개발자 CLI: 소스에서 직접 빌드한 audionaut-cli 콘솔 바이너리는 샌드박스 제한 없이 동작
  • Windows 환경: Audionaut.exe 바이너리는 샌드박스 제약 없이 표준 사용자 파일시스템 권한 내에서 동작
  • Linux 배포판: 데비안 패키지(.deb) 및 AppImage 실행 환경에서 임의 경로 접근 허용

오디오 편집 기능 자체의 명세를 살펴보면, Audionaut는 비파괴(non-destructive) 리전 기반 타임라인을 채택하고 있다. 원본 소스 파일에서 정의된 명명된 리전(Named regions)은 오디오 데이터를 복제하지 않고 타임라인 클립으로 배치되며, 하나의 리전을 여러 번 재사용할 수 있다.

클립 속도는 0.25배속에서 4배속까지 조절 가능하며, 피치가 함께 변하는 바리스피드(varispeed) 모드와 피치를 유지하는 타임 스트레치(Rubber Band R3 라이브러리 기반) 모드를 지원한다. 템포 락(Tempo lock) 기능을 켜면 클립이 프로젝트의 기준 템포에 맞춰 자동으로 정렬된다. 분할(Cmd+E), 채널별 클립 게인 조정, 이퀄 파워(equal-power) 페이드 커브, 클립 경계를 넘어서는 오버랩 기반 크로스페이드 등이 모두 비파괴 방식으로 동작한다.

브라우저 편집기와의 차이 — AudioMass 비교와 네이티브 메모리 관리

웹 기술의 발전으로 브라우저 환경에서도 Web Audio API를 활용한 오픈소스 오디오 편집기가 다수 등장했다. 대표적인 사례인 AudioMass의 경우 별도의 설치 과정 없이 웹 브라우저 탭 안에서 즉시 단일 파형을 자르고 이펙트를 적용할 수 있는 편의성을 제공한다. 그러나 프로덕션 환경의 복잡한 멀티트랙 작업과 AI 에이전트 연동 측면에서 브라우저 기반 도구와 Audionaut와 같은 네이티브 C++ 데스크톱 애플리케이션 사이에는 명확한 아키텍처적 간극이 존재한다.

첫째, 메모리 할당 및 버퍼 관리 방식의 차이다. 브라우저 기반 편집기는 자바스크립트 가비지 컬렉터와 브라우저 탭의 메모리 제한(일반적으로 32비트 힙 한계 또는 2~4GB 수준) 내에서 작동하므로, 작업 대상 오디오 샘플 전체를 메모리 배열에 로드해야 한다. 이로 인해 고해상도(96kHz/24bit 등) 멀티채널 세션이나 수 시간에 달하는 팟캐스트 녹음본을 다룰 때 탭 충돌이 발생할 위험이 높다. 반면 JUCE 기반의 네이티브 데스크톱 앱인 Audionaut는 OS 파일 시스템 버퍼와 디스크 캐시를 직접 제어하므로 메모리 한계를 초과하는 긴 타임라인 세션도 안정적으로 스트리밍 처리할 수 있다.

둘째, 에이전트 제어 루프의 격리 수준이다. 브라우저 편집기를 외부 에이전트가 제어하려면 웹소켓이나 헤드리스 브라우저 조작(Puppeteer 등)이 필요하여 실행 오버헤드가 크고 상태 검증이 까다롭다. Audionaut는 OS 레벨의 로컬 프로세스 간 통신과 표준화된 MCP 서버, 그리고 헤드리스 CLI 바이너리를 통해 명령을 1회 단위로 직렬화하여 실행하므로 에이전트 자동화의 신뢰성이 높다.

셋째, 비파괴 편집과 프로젝트 구조의 차이다. 단순 파형 편집기가 원본 샘플 버퍼를 직접 수정(destructive)하는 것과 달리, Audionaut는 원본 미디어 파일은 보존한 채 메타데이터 단위로 구간을 참조하는 비파괴 리전 방식을 채택한다. 따라서 에이전트가 수십 차례 자동 절단과 재배치를 수행하더라도 원본 오디오는 물리적으로 훼손되지 않는다.

확인하지 못한 것

  • 대규모 멀티트랙 세션에서의 실측 재생 지연 시간(latency) 및 CPU 벤치마크. 원문 저장소와 커뮤니티 토론에서 저자는 아직 공식 재생 성능 벤치마크를 수행하지 않았다고 명시했다.
  • 레이블(Label) 가져오기 및 내보내기 기능. 기능 목록과 사용자 매뉴얼에서 영역(Region) 기능은 지원되나 레이블 기능은 아직 미지원 상태(개발 대기 목록)로 확인되었다.
  • VST/AU 등 서드파티 오디오 플러그인 호스팅 지원 여부. 저자의 설명에 따르면 플러그인 호스팅 및 딜레이 보정 기능은 개발 대기 목록에 포함되어 있으며 현재 빌드에는 탑재되지 않았다.
  • Demucs 음원 분리 실행 시 NVIDIA/Metal GPU 하드웨어 가속 지원 범위. demucs.cpp C++ 포팅 코드가 CPU 전용인지 GPU 가속을 활용하는지는 문서에서 확인하지 못했다.
  • 프로젝트가 데스크톱 앱에 열려 있지 않은 상태에서 동시에 여러 CLI 프로세스가 동일한 Project.json 파일을 수정할 때의 동시성 락(file lock) 제어 메커니즘.
