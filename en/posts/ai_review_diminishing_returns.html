How Many Times Should You Run an AI Code Review

Why the same code and the same tool surface different findings every run, and where to stop

Aug 30, 2026 Tech & IT

Review the same code ten times and you get ten different answers

You open a pull request, run the AI review once, get three findings, fix them, and merge. For most teams, that is what using AI code review actually looks like. But run it a second time without changing a single line and something odd happens. Different findings come back. The third pass differs again.

A recently published experiment counted this properly. A 359-line C firmware module was reviewed ten times independently with no modification between passes. Only the single file was supplied, repository access was blocked, and two different coding agents were used. The result was 61 findings. Clustered into equivalence groups, 14 distinct groups remained. An average pass produced 6.1 findings — but the composition of those 6.1 changed from run to run.

One number in that write-up is easy to misread. The 400 in its title does not mean one pull request was reviewed 400 times. The author's own definition is that roughly 400 LLM calls occurred across the entire study, and that this counts neither review calls alone nor the number of experiment runs. The core of the repeated-review experiment is ten passes over a single file; the remaining calls were spread across two separate Python tasks, review-fix loops, and reruns.

The character of the study is worth stating too. It is a designed experiment — acceptance criteria were frozen before implementation, conditions (file-only versus repository access) were split for comparison, and the clustering procedure was validated separately. It is also small. Two Python tasks where frozen contracts and tests settle the verdict, one C module where a human adjudicated truth, two models, at most three loop rounds. The author says as much in the limitations section, adding that only three of the findings were reconfirmed under a different condition or a different model. So the numbers below are a record of one condition, not a law.

Why a different thing catches each time — variance is not a fault

The cause splits into two layers. The lower one is a property of the model; the upper one is a property of review as a task. The upper layer matters far more.

Start below. A language model samples the next token from a probability distribution. Turning the temperature down toward zero still does not guarantee exact reproduction, because slight differences in batching or floating-point accumulation order can flip the ranking of two near-tied candidates. In most work that is negligible noise. Review, though, is the kind of task where one early flip changes the whole result. Which function gets picked up in the opening paragraph sets the direction of everything after it.

The upper layer is the real story. Those 359 lines held at least fourteen things worth flagging, while a single response carried about six. This is not a task with a right answer to hit; it is a task of selecting and ranking candidates. When there are more candidates than slots, very small conditions decide which ones get picked.

  • There is no defined answer set — a test suite has pass and fail, but the question of how many problems a piece of code contains has no answer key.
  • The response has limited room — if there is no space to list fourteen, six get chosen. The moment they are chosen, the other eight did not exist in that run.
  • Earlier sentences drag the later ones — catch one race condition early and the rest leans toward concurrency. Same code, different lens.
  • One word in the prompt shifts the center of gravity — find bugs and point out what is risky produce different lists.

So the variance is not a defect awaiting a fix. It is a property of the tool, and in fact it is exactly why repetition pays at all. A reviewer that always returns the identical list may not be stable — it may be looking at only one place. Keeping a nondeterministic tool under control is a broader problem, covered separately in the grammar of controlling nondeterminism.

What you miss by calling one pass a review

A single run is one sample. Under this experiment's conditions, one pass covered 44 percent of the fourteen distinct groups. Excluding the four false positives and using only the ten confirmed defects as the denominator, it covered 34 percent.

Independent review passesAgainst 14 distinct groupsAgainst 10 confirmed defects (4 false positives removed)
1 pass44%34%
3 passes71%61%
5 passes83%76%

The table has to be read with its conditions attached: one 359-line C module, file-only context, cumulative averages over ten independent passes. It is a record of that condition, not a general curve.

The more awkward case is a pass that returns zero findings. Silence is not proof of completion. Zero is one of three outwardly indistinguishable situations — the code really is clean, nothing was drawn in this particular sample, or context was too thin to see anything in the first place. In this experiment one model stayed silent under a condition where the other found distinct failure modes.

  • You are claiming the six findings from this pass are all there is.
  • You are claiming that what did not appear does not exist — yet going to three passes surfaces another 27 percentage points.
  • You are claiming that what this tool can see defines the scope of review. Without context, some things cannot be seen at all.
  • A green review badge does not distinguish between these three.

Where new findings thin out — but conditions draw the curve

Read the table again: going from one pass to three adds 27 percentage points, and three to five adds 12. The increment itself shrinks. That much is what the table says.

Here is what must not be done with it: turning that shape into a law and extracting a sentence like three passes is the right number. It does not hold, because four variables draw the curve.

  • Total candidate pool — fourteen in 359 lines. A 3,000-line change multiplies the candidates while the number carried per pass barely moves. The curve flattens considerably.
  • How much context was given — this was file-only. Supply related files and call paths and first-pass coverage rises, which shrinks the marginal value of repeating.
  • The nature of the code — firmware tangled with concurrency and a ring buffer is the kind that cannot be seen at once. A straightforward block of data handling yields most of its findings on the first pass and the curve lies down early.
  • The prompt — asking with the identical sentence every time is drawing from the same distribution again. Overlap is unavoidable.

What transfers, then, is the shape rather than the numbers: most of it arrives in the first few passes, and the rest flattens. Which pass it flattens at is decided by your code. And that is measurable. Take a representative pull request, run it five times without touching it, and count from which pass onward no new kind of finding appears. Each team only needs to do this once.

Is a repeated finding a trustworthy signal?

Intuition says a finding that shows up in eight of ten passes must be real. This experiment produced the exact opposite. Four of the five most frequently reported findings were false positives. Under file-only context the false-positive rate was 4 of 14 groups, or 29 percent.

It looks strange until you look at the structure. Whatever produced the false positive is present identically in every run. Give the model one file and no run can know that the initialization lives elsewhere, so this is never initialized comes back all ten times. Genuine defects, meanwhile, are hard to reach, and hard things surface occasionally. Frequency ends up measuring how easy a finding is to arrive at, not whether the defect exists.

One decisive observation follows. When repository access was granted, those four false positives disappeared in both models. It is one of the few results the author lists as reconfirmed across conditions. The false positives were not a shortcoming of the models but a product of missing context.

  • Sorting by frequency and fixing from the top is dangerous — that ordering can put false positives at the head of the queue.
  • Read a recurring finding as a place that keeps producing the same conclusion, not as a confirmed defect — the two look identical from outside.
  • The first move on a recurring finding is to supply context and ask again, not to fix it — it may be the kind that vanishes once a few related files are attached.
  • Adding context is often cheaper than adding passes — one call that removes four false positives versus ten passes that make you read the same four ten times.

The three budgets repetition spends — money, latency, attention

This is the real bottleneck. Ten passes produced 61 findings and 14 distinct groups. But a person has to read 61 of them, because deduplication is not done for you. Deciding that two differently worded findings describe the same defect is itself a judgment, and judgment stays with the human.

When you repeatAcross 10 passesWhat sets it
Findings a person must read61Grows roughly linearly
Defects you actually learn about14 groups, 10 of them realMost arrive early, then flattens
False positives4 of 14 groups (29%)Set by context volume; passes do not reduce it
Model call costAbout 10xProportional to tokens and code size
Wall-clock wait10x if serial, nearly flat if parallelExecution strategy

The whole point of the table is that the first two rows grow at different speeds. What you must read rises linearly; what you learn flattens. Money and latency can be pushed back with budget and parallel execution, but the third budget — human attention — cannot be pushed.

  • Attention is not uniform across 61 items. It degrades toward the end of the list, and a genuine defect sitting at the bottom is effectively absent.
  • After three or four false positives in a row, the rest start looking like false positives too. That is when a real one slips through.
  • Claiming full coverage means adjudicating all 61. The moment that adjudication costs more than the human review it was meant to relieve, the reason for adopting the tool is gone.
  • So the practical ceiling on passes is set not by model pricing but by the time a person can spend adjudicating.

Adding passes and splitting perspectives are different moves

Running the identical prompt ten times is drawing from the same distribution ten times. Overlap is unavoidable, and that overlap is what flattens the curve. Change the angle of the question and the distribution itself moves, which leaves room for something new.

  • Repeating the same question — relies on sampling randomness. It pays, but the payoff shrinks quickly.
  • Splitting by where to look — boundary conditions, concurrency, resource release, input validation. Separate axes have little reason to overlap.
  • Varying the context — file only, related files, full call path. The same question sees different things. This is the axis that removed the false positives.
  • Reversing the direction — asking whether there is any reason to revert this change produces a different list than asking what is wrong with it.

Splitting perspectives is not free either. Four axes means four calls and four piles to read. The difference is that for the same budget, four different questions yield more new information than four identical ones, because they overlap less — and that holds without relying on the luck of the draw.

A workable way to choose axes is to use the failure types that actually bit you recently. If resource leaks took you down twice last quarter, that is axis one. What AI review is generally good and bad at catching is laid out in the state of agentic code review.

Fixes create new code — change size decides the outcome

This is the most operationally useful part of the experiment. Repeated review and the review-fix loop are different activities. Reviewing without modifying pushed coverage from 34 to 76 percent. In the loop — review, fix, review again — compliance against the frozen acceptance criteria did not improve further, while code size grew between 24 and 152 percent depending on condition. Under one condition it actually shrank. What the loop reliably produced was not compliance but code.

The reason is simple. A fix can remove the problem, or it can bolt on defensive code — and the second is far easier. Add one more check where the finding pointed and the finding goes away. The trouble is that the code added that way has never been reviewed.

  • Each loop round creates new code, and the next round sees that new code for the first time. So we reviewed it N times loses its meaning; each pass looked at different code.
  • Whether a re-review is needed is decided by the size of the modification, not the round counter. A large fix is not a repeat review — it is the first review of new code.
  • Even 359 lines yielded only six findings per pass. At 3,000 lines the ratio gets worse. That is why review collapses on large pull requests: candidates multiply while the per-pass yield does not.
  • Hence the prescription: review many times, fix once. Run independent passes, pool the findings, have a person adjudicate, and apply the fixes together.

One practical judgment falls out of this. When torn between adding passes and splitting the pull request, splitting is usually better. Splitting raises the fraction a single pass covers, cuts the pile a human must read, and narrows the blast radius when fixing. Repetition is a way to reduce residual uncertainty, not a way to absorb a large lump. Why keeping change units small matters so much to review quality is examined from another angle in code review seen through maintainability.

Decide the stopping rule before you start

Judge after the fact and you will keep running. The reasoning this pass turned up something new, so one more is always available, because repetition keeps producing new findings — that is the nature of the method. So the rule has to be set before the results are visible.

Stopping ruleWhen it fitsWhere it breaks
Round cap (say, three)Small changes of a familiar kindFar too early on large changes with many candidates
No new distinct finding for two passesWhen someone is available to adjudicate clustersDeciding what counts as distinct costs human time
Churn converging to zeroWhen contracts and tests are tightWith loose contracts it does not converge; one condition here kept climbing
Perspective list exhaustedTeams that fixed their axes in advanceAnything not on the list never gets looked at
Cap on adjudication timeAlmost always worth running alongsideMechanical, so it leaves remaining defects in place

One rule is deliberately absent from the table. Stop when nothing is reported cannot serve as a criterion. Silence is not proof of completion, and restructuring the same code differently can expose new problems. Zero is closer to an absence of information than to information.

  • Set two ceilings together — a round cap and a time cap, stopping at whichever is reached first.
  • Write the perspective list first and let its length set the pass count — four axes means four passes.
  • Fix once, at the end — and after fixing, stop continuing the round count and restart as the first review of new code.
  • When false positives recur, add context rather than passes — supplying the related files once is cheaper than reading the same false positive five more times.
  • Measure your team's curve once — one representative pull request, five passes, and note where new groups stop appearing.

What passes cannot fill in

One sentence from the limitations section is the starting point here. Design appropriateness, clarity of intent, and accuracy of naming were not measured. Those three are precisely what human code review normally treats as its priorities. So what this experiment measured is not review in full but the part a machine can count.

The reasons differ in each case.

  • Intent — what the change was trying to do lives outside the code: requirements, what was said in a meeting, the point where users actually struggled. A hundred passes over the code will not recover it.
  • Design judgment — whether this capability belongs here is not right versus wrong but a choice, and choices need knowledge of the organization's situation and its plans.
  • Understandability — what will confuse the person opening this file in six months is judged by someone who knows the team's idioms and history.
  • What was decided against — alternatives considered and dropped leave no trace in the code, and there is no way to flag an absence. Filling that gap is what a comment is actually for.

So the range repeated review genuinely covers is narrow: a first-pass filter for easily missed defects. That alone is worth having, because the time saved can go to the four items above. Get the direction backwards, though, and it turns costly. Spend all of a person's attention pushing machine-countable coverage to 90 percent and the places the machine cannot see get merged untouched. Review quality can fall while coverage rises. Missing what a metric fails to measure shows up in the same shape in the blind spots of evaluation.

What could not be verified

  • Whether the raw materials of the experiment — run logs, the basis for clustering findings — are published could not be confirmed. The figures here follow the tables and narrative the author released.
  • No replication showing the same curve shape on codebases of a different size or language was located. The sample is two Python tasks, one C module, two models, at most three loop rounds.
  • The author states that only three of the findings were reconfirmed under a different condition or model. The rest were observed once, so it is safer to carry the direction than the individual numbers.
  • The denominator of coverage is known defects, not existing ones. A defect that has never surfaced in any run is not in the denominator, so the percentages read generously. The author notes the reported figures are lower bounds.
  • The cost of repeated runs varies widely with model, token count, and code size, so no dollar figures are given here.
  • How many passes commercial review services run internally, and how they deduplicate, could not be found in public material.

In short — look many times, fix once

Three sentences remain. The same tool on the same code catches different things each run — not a fault, but a sign that there are more candidates than slots. So calling one pass a review amounts to claiming that whatever this sample drew is all there is. And repetition grows what you must read far faster than what you come to know — the real bottleneck is not the bill but the time a person spends adjudicating 61 items.

Practice, then, is closer to an ordering than a count. Write the axes first, run that many independent passes, pool the findings for a person to adjudicate, and fix in one go. If the fix was large, stop continuing the round count and restart as the first review of new code.

There is no universal answer to how many passes are right, because change size, the nature of the code, the context supplied, and the prompt each draw a different curve. But your own curve only needs measuring once. One representative pull request, five passes, and a note of where new kinds of findings stop. It takes half a day, and that half day buys a far more accurate answer than borrowing someone else's table.
