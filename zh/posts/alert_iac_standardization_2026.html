将告警(Alert)系统标准化并以 IaC 方式运维

从在 UI 上一条条手搭的告警,到用代码定义、版本管理、部署的告警 - 标准化、SLO 与自动化实践分析

2026-07-05 开发/基础设施

引言: 为什么现在也该用代码来管理告警

告警常被当作「随手就能搭好的东西」。在 Grafana 控制台里点一条规则、指定一个 Slack 频道,就算完事。这套办法在告警只有五条、十条时毫无问题,但一旦超过五十条、上百条,必然崩溃。没人记得这条告警是谁、何时、依据什么标准建的;同一个指标,不同团队用着不同的阈值;负责人一换,告警的归属就悬空了。

GeekNews 上最近的一个话题「将告警系统标准化并以 IaC 方式运维」,又把这个老问题摆上了台面。本文以此为契机,从我自己的角度分析Alerting as Code这种做法: 不再在 UI 里一条条手搭告警,而是用代码去定义、版本管理、部署它们。文章会讲清楚告警标准化为何重要、如何从结构上减少 alert fatigue(告警疲劳)、基于 SLO 的告警与传统阈值告警有何不同、用 Terraform、Grafana、Prometheus 把告警代码化能带来哪些实际收益,以及一套可落地的采用策略——内容截至2026年7月整理。参考的原文与 GeekNews 链接列在文末。

1. 什么是告警疲劳(Alert Fatigue),它为何发生

1.1 发生机制

告警疲劳是当告警数量超出人能有意义处理的范围时产生的一种感觉麻木。值班工程师一天收到几十条告警,大脑会启动防御机制,不再认真读取内容,而是反射性地按下确认键。问题在于,这种麻木状态会连带削弱区分「真正紧急」与「噪音」的能力。告警疲劳不只是烦人,它是事故响应失败的直接原因。

1.2 实践中常见的模式

告警疲劳通常由三个原因叠加而成。第一是碎片化: Grafana、CloudWatch、EventBridge、基于 Lambda 的自定义告警各自生成通知,值班人员不得不为每一种告警记住不同的格式和不同的处理流程。第二是责任人不清: 告警触发时该谁去确认、这条告警本身归哪个团队所有,一旦模糊,响应就会延迟,责任也会被互相推来推去。第三是无法采取行动的告警: 触发了却没有具体可做的事,最终只会教会所有人忽略它。三者叠加后,值班人员会彻底不再信任告警,而这最终会固化为一种「连真正的故障也反应迟缓」的组织习惯。

2. 什么是 Alerting as Code - 把 IaC 应用到告警上

2.1 定义与四项承诺

Alerting as Code 把用代码管理基础设施的 IaC 原则,原样应用到告警规则上。告警条件、严重级别、路由对象、Runbook 链接不再靠 UI 点击设置,而是用 YAML 或 HCL 之类的声明式文件定义,交给 Git 仓库做版本管理,再用 Terraform 这类工具部署到 Grafana 或 Prometheus Alertmanager。核心承诺有四项: 版本管理(记录谁在何时改了什么)、可评审性(变更先经 Pull Request 审阅)、可复现性(同一份代码在任何环境下都得到相同结果)、可回滚性(出问题立即回退到上一次提交)。

2.2 为什么是现在

不可否认,UI 点击方式在小规模下确实方便。问题是这种方便不会线性扩展。告警越多,在 UI 里维持一致性的成本就呈指数级增长。反过来,把告警当代码管理,无论是 100 条还是 1000 条,都能走同一套模板和校验流程。在我看来,真正的转折点不是某个具体的告警数量,而是当组织自问「能不能说清这条告警存在的依据」时,答案开始变得含糊的那一刻。

3. 标准化的四根支柱 - 命名、严重级别、路由、Runbook

3.1 命名规则与目录结构

让告警的名称和存放位置本身就成为元数据,在实践中更省心。比如用 {大类}/{子类}/{严重级别}/{名称}.yml 这样的层级结构,光看文件路径就能立刻判断这条告警属于哪个领域、有多严重。韩国电商 SaaS 公司 AB180 的工程博客介绍的告警标准化案例中,正是采用了类似的层级结构,并把它作为将告警重新定义为「连接预防与响应的运维接口」的起点——而不只是一条通知。一个目录结构,不需要额外文档就能说明这条告警的性质。

3.2 定义严重级别与路由

严重级别至少要清晰划分为两档(Warning、Critical)以上,并且提前固定每一档流向哪个渠道。Critical 直接通过 PagerDuty 之类的值班工具立即呼叫,Warning 则堆在 Slack 频道里,留到工作时间处理。如果这套映射因告警而异,值班人员每次都得自己判断「这条告警现在值不值得把人叫醒」,而这个判断过程本身就是延迟和失误的根源。

3.3 强制附带 Runbook 链接

在告警定义中把 Runbook(处理流程文档)链接设为必填字段,告警一旦触发,值班人员无需另外搜索就能直接跳转到该做什么。甚至可以考虑一条策略: 没有 Runbook 的告警一律不允许注册。因为没有处理流程的告警,最终大多会滑向「先观察一下」这种无所作为。

3.4 两种方式对比

项目UI 点击方式Alerting as Code
定义位置分散在各工具控制台统一在一个 Git 仓库
变更历史难以追溯通过 Git 日志完整追溯
评审无,即时生效Pull Request 事先评审

回滚手动重新配置立即回退到上一次提交

4. 基于 SLO 的告警 - 从阈值到错误预算

4.1 传统阈值告警的局限

像「CPU 超过 90% 就告警」这样的静态阈值容易设置,却有两个陷阱。在流量本就波动较大的服务上,即便处于正常范围也会频繁跨越阈值造成误报;反过来,在阈值以下缓慢恶化的问题又很容易被漏掉。结果是要不断花时间去调阈值,而这本身又是告警疲劳的另一个源头。

4.2 多窗口、多燃烧率方法

SRE 领域已经沉淀出的替代方案,是以 SLO(服务级别目标)和错误预算消耗速度(burn rate)为基准来告警。同时检查一个短窗口(比如 5 分钟)和一个长窗口(比如 1 小时),只有当两个窗口都显示错误预算消耗过快时才触发告警。只看短窗口会被瞬时抖动误报,只看长窗口又会响应迟缓,所以用 AND 条件把两个窗口叠加起来才是关键。这一模式在 Google SRE 团队的工作手册中有清晰的整理,已广为人知。

4.3 SLO 告警与标准化的交汇点

基于 SLO 的告警,如果最终没有被定义为代码,同样会沦为标准化之外的一块「飞地」。只有把错误预算的计算公式、窗口大小、燃烧率阈值明确留在告警代码里,日后才不需要有人再去反推「这条告警为何在这种条件下触发」。在我看来,SLO 告警恰恰是 Alerting as Code 优势体现得最明显的领域——计算公式越复杂,靠 UI 点击就越难复现,也就越需要留在代码里才能被验证和复用。

5. 用 Terraform、Grafana、Prometheus 将告警代码化的好处

5.1 可复现性与跨环境一致性

用 Terraform 定义 Grafana Alerting 或 Prometheus Alertmanager 资源,可以在开发、预发布、生产环境中无误地复制同一套告警规则。若靠 UI 逐个环境手动配置,迟早会出现某个环境漏配的事故。

5.2 评审与审计轨迹

把告警变更纳入 Pull Request 流程,就能避免有人悄悄放宽阈值或关掉某条告警而完全不经代码评审的情况。谁在何时、出于什么原因改动了这条告警,一份 Git 日志就能说清楚。事后复盘时如果要追问「这条告警当初为什么被关掉了」,这份审计轨迹的价值尤其突出。

5.3 Alertmanager 与 Grafana Alerting 该如何选择

如果指标来源统一为 Prometheus 一种,PromQL 就足够用,选择 Alertmanager 走简单路线是合理的。而如果需要把 Loki 日志、CloudWatch 指标、数据库查询这类多个来源整合进同一套告警体系,Grafana 的统一告警(Unified Alerting)会更有优势。我观察到,数据源越多的组织,往往最终都会收敛到 Grafana 上,因为只有把告警评估引擎统一为一个,下游(Slack、PagerDuty)的体验才能保持一致。正如我此前分析的Sentry、PostHog 免费观测策略一样,工具选择从来不是绝对的优劣之争,而取决于组织自身数据源的多样性。

6. 从结构上减少告警疲劳的技巧

6.1 分组

当同一条规则下多个实例同时触发(比如 5 个 pod 同时异常)时,把这些消息合并成一条分组消息,而不是发 5 条独立消息,就能大幅降低频道里的感知噪音。分组内部仍需持续追踪每个实例各自的状态变化,才能知道是否只有某个实例已恢复。

6.2 模板与矩阵

如果为每个队列、每个服务都手动复制相似的告警,改一处就得不漏地把其余全部改一遍,负担很重。把共同条件定义为一个模板,只用矩阵展开队列名、阈值这类会变化的值,就能实现声明式复用,降低维护成本。

6.3 可执行告警原则

应当立下一条准则: 触发后如果没有人能采取的具体行动,这条告警一开始就不应该存在。把这条原则明确写进告警注册的评审标准里,那些容易创建却没人能处理的告警就会在源头被过滤掉。

6.4 抑制与去重

当上游资源故障级联触发下游资源的一连串告警时,把依赖关系告知告警系统,就能自动抑制下游告警。同时用去重窗口压住同一条告警在短时间内的重复触发,可以避免同一起事故引发几十次告警轰炸。

7. 元监控 - 告警系统本身也需要被监视

7.1 Deadman switch 的概念

告警系统保持安静,并不必然意味着「一切正常」——这与告警管道本身挂掉、什么都发不出去的情况完全无法区分。防范这一点的经典手法是 Deadman switch: 系统正常运行期间,通过另一条独立路径持续、周期性地发送「存活」信号(heartbeat),一旦这个信号中断,中断本身就被当作一次告警来处理。

7.2 依赖异构基础设施以规避单点故障

设计元监控时常见的错误,是把监视体系搭在与被监视对象相同的基础设施之上。如果告警评估引擎挂了,而检测这一状态的逻辑又恰好跑在同一个集群上,那就会一起挂掉。监视链条的最后一环,必须依赖与被监视对象在物理上分离的基础设施(比如另一个云服务),这样一方倒下时,另一方仍能拉响警报。

8. 落地策略 - 从哪里开始

8.1 分阶段迁移

试图一次性把所有既有的 UI 告警迁移为代码,必然会让团队疲惫不堪。更现实的做法是,对新增告警先应用「代码优先」原则,既有告警则在每次发生事故或需要修改时再逐步迁移为代码。

8.2 组织层面的课题 - 所有权

在告警代码仓库里用 CODEOWNERS 之类的机制明确各团队的所有权,谁来批准、谁来维护某条告警的模糊地带就会消失。这是组织共识问题,而非技术问题,而且往往比引入工具本身更耗时。

8.3 度量指标

标准化之后,必须开始留存指标。记录每条告警的确认(Ack)耗时、解决耗时,以及同一条告警的重复触发次数,日后就能用数据而非直觉去判断「这条告警只是反复触发却没有任何互动,毫无意义」。标准化初期往往缺少这类 As-Is 基线数据,即便如此,从现在开始收集本身就是收益。

9. 局限与注意事项

Alerting as Code 并非万能。第一,采用初期搭建代码、评审、流水线反而更费时间。原本能在 UI 上三分钟搭出一条紧急告警的团队,一旦要走 PR 和评审流程,可能会感觉变慢了。第二,如果为了处理告警代码强行造出新的 DSL 或过度抽象,反而会拉高学习曲线;更好的做法是尽量原样把既有告警引擎的payload结构搬进 YAML,采取最小侵入式的方案。第三,基于 SLO 的告警在低流量服务上信号本就稀薄,多窗口方法可能效果不佳,这种情况下应辅以静态阈值和绝对值告警作为补充。

10. 结论 - 今天就能落地的三件事

把告警标准化并以 IaC 方式运维,不是一次浩大的重写,而是一种态度的转变: 不再把告警当成几次 UI 点击的副产品,而是当作一份经过版本管理、评审、可回滚的小型运维软件来对待。

10.1 从新增告警开始强制命名、严重级别、Runbook 规则

从最小化模板做起,每新建一条告警就要求填写目录结构、严重级别、Runbook 链接这几个必填项。不必推倒重来既有的全部告警。

10.2 裁剪不可执行的告警

不妨拉一份「反复触发却没人处理」的告警清单出来看看。用「无可执行动作的告警不应存在」这条原则果断清理,告警疲劳就会肉眼可见地下降。

10.3 建一个监视告警系统本身的 Deadman switch

哪怕只是最简单的一条 heartbeat,走一条独立路径发出去,也足以防止最危险的错觉——把「没收到告警」误当成「一切正常」。
