계기 — 컴파일 대기 시간 단축을 향한 실험적 시도 headstart

저장소의 README 는 문제를 한 문장으로 요약한다. 모든 크레이트는 자신이 의존하는 크레이트가 함수 본문까지 완전히 검사될 때까지 기다렸다가 시작한다. 그런데 그 본문은 자기 타입 검사에 필요하지 않다. 의존하는 쪽이 보는 것은 의존 크레이트의 인터페이스, 곧 .rmeta 파일의 메타데이터이기 때문이다. headstart 는 인터페이스 검사가 끝나는 즉시 rustc 가 초기 메타데이터 파일을 쓰게 하고, cargo 가 그것을 신호로 후속 크레이트를 시작하게 한다. 그러면 각 크레이트의 본문은 하류 크레이트가 이미 컴파일되는 동안 검사된다.

저장소는 2026년 9월 27일에 만들어졌고 마지막 push 는 10월 4일이다. Hacker News 에는 10월 4일에 올라왔으며(스레드 제목은 메타데이터를 일찍 내보내면 Rust 빌드와 검사가 최대 두 배 빨라진다는 취지), GeekNews 에는 10월 5일에 소개되었다. 그러므로 이 글이 다루는 것은 만든 지 열흘이 안 된 프로토타입이다.

이 글에서 가장 조심해야 할 것은 수치의 분모다. README 의 「최대 54%」와 「최대 42%」는 13개 실제 프로젝트의 16코어 클린 빌드 가운데 최댓값이고, results 문서의 표를 보면 그 둘은 모두 rust-analyzer 한 프로젝트의 값이다. check 는 90.1초에서 41.5초, build 는 137.9초에서 79.9초이다. 같은 표에서 가장 작은 값은 zola 의 check 2%, build 0% 이다. 이하의 모든 수치는 이렇게 어느 프로젝트의 어느 시스템 값인지를 붙여서 읽어야 한다.

기존 Cargo 파이프라이닝 컴파일의 구조와 한계

의존 크레이트가 끝나기 전에 후속 크레이트를 시작하는 방식 자체는 새로운 것이 아니다. Rust 릴리스 노트에 따르면 파이프라이닝 컴파일은 Rust 1.38.0(2019-09-26)에서 rustc 와 cargo 양쪽에 추가되었다. 릴리스 노트는 이것이 경우에 따라 컴파일 시간을 개선한다고만 적는다. design.md 는 cargo 가 이미 cargo build 의 라이브러리를 metadata 알림 시점에 파이프라이닝하고 있다고 설명한다.

한계는 그 메타데이터가 쓰이는 시점이다. design.md 에 따르면 rustc 는 모든 함수 본문의 타입 검사와 차용 검사가 끝난 뒤에야 메타데이터를 쓴다. 메타데이터에는 항목의 시그니처와 타입, 트레이트 구현, 그리고 하류가 컴파일 시간에 평가하거나 인라인하거나 인스턴스화할 수 있는 것의 MIR 이 들어 있는데, 하류가 필요로 하지 않는 본문의 검사 결과까지 기다려야 하는 셈이다. 또한 design.md 는 cargo check 는 cargo 가 애초에 파이프라이닝하지 않았다고 적는다.

같은 발상을 시도한 선행 작업도 문서에 나온다. design.md 에 따르면 2019년에 Nicholas Nethercote 가 rust-lang/rust#64112 에서 메타데이터 기록을 타입 검사와 차용 검사 앞으로 옮겼다. 그의 방식은 하류가 코드 생성에 쓸 MIR 까지 담은 단일 메타데이터 파일이라 이른 기록이 분석의 대부분을 여전히 강제했고, 최대 1.07배의 개선을 보고 포기했다고 한다(그가 밝힌 이유는 큰 이득이 아니고 오류 메시지 방출을 조금 늦춘다는 것, 인용은 design.md 가 가리키는 블로그 글). headstart 는 두 가지가 다르다고 한다. 초기 메타데이터를 분석에 필요한 것만 담은 별도 파일로 두고 하류는 코드 생성 직전에만 전체 파일을 기다리며, cargo check 까지 대상으로 한다.

인터페이스 분석과 함수 본문 검사의 분리 메커니즘

design.md 가 설명하는 실행 순서는 이렇다. 새 쿼리 analysis_interfaces 가 항목 인터페이스 검사(well-formedness, coherence)까지를 실행하고, 기존 analysis 는 그것을 먼저 돌린 뒤 모든 본문을 검사한다. 드라이버는 둘 사이에서 초기 메타데이터를 쓴다.

  • 신규 쿼리: analysis_interfaces 가 분석을 항목 인터페이스와 함수 본문으로 나눈다.
  • 초기 메타데이터 기록: 두 단계 사이에서 드라이버가 .early-rmeta 를 쓰고 early-metadata 아티팩트 알림을 낸다. 아무도 의존할 수 없는 바이너리는 쓰지 않는다.
  • 하류 즉시 시작: cargo 는 그 알림에 맞춰 후속 유닛을 시작한다. check·build·test 모드의 모든 rustc 유닛이 대상이며 바이너리·테스트·proc macro·빌드 스크립트도 포함된다. 다만 proc macro 와 dylib 의존은 여전히 전체 빌드를 기다린다.
  • 본문 검사의 중첩: 상류가 함수 본문을 검사하는 동안 하류는 초기 메타데이터로 자기 분석을 진행한다.
  • 전체 메타데이터로 교체: 코드 생성 전에 rustc 는 의존 크레이트의 전체 메타데이터로 바꿔 끼운다. 파일이 아직 없으면 생산자가 쥐고 있는 락이 풀리기를 기다린다. 기다리는 동안 컴파일은 wait-metadata 알림을 내어 cargo 가 그 작업 슬롯을 다른 일에 쓰게 하고, 끝나면 resume 을 낸다.

메타데이터가 정확하려면 초기 파일 쓰기 전에 본문에서 나오는 것들을 미리 계산해야 한다. design.md 는 그것을 인터페이스 본문(interface bodies)이라 부른다. opaque 타입(impl Trait 의 숨은 타입), 상수와 const fn 과 배열 길이의 MIR, static 의 평가, 그리고 async 의 코루틴이 그에 해당한다. 반대로 함수의 최적화된 MIR 과 추론된 매개변수 속성, 내보낸 심볼, 크로스 크레이트 인라인 가능성, 패닉 전략은 코드 생성에서만 읽히므로 초기 메타데이터에 넣지 않는다. 두 파일은 같은 크레이트 해시(SVH)를 갖는다. 이 해시는 초기 메타데이터의 바이트와 HIR 해시 및 추적 옵션의 보충분에서 한 번 계산되고 전체 메타데이터가 같은 값을 싣는다. 본문 하나가 바뀌면 해시가 바뀌므로 증분 컴파일의 판단은 유지된다고 문서는 설명한다.

cargo check 에서 하류는 초기 메타데이터만으로 끝까지 실행된다. cargo build 에서는 분석까지 초기 메타데이터로 진행하고 코드 생성 직전에 전체 메타데이터를 기다린다. 링크하는 크레이트는 링크 직전에 rlib 도 기다린다. 이 기다림은 락으로 구현되어 있다. 상류가 실패하거나 죽으면 운영체제가 락을 풀어 주고, 기다리던 쪽은 파일이 없는 채로 락을 얻어 오류로 멈춘다. 의존 그래프에 순환이 없으므로 기다림이 교착으로 이어지지 않는다고 문서는 적는다.

rustc 및 Cargo 패치 구성과 동작 흐름

patches/README.md 에 따르면 이 저장소는 커밋 시리즈로, rust-lang/rust 용 6개와 rust-lang/cargo 용 3개다. 각 커밋은 단독으로 빌드되고 저장소 자체 검사(fmt, tidy)를 통과한다. 아래 표는 그 문서의 요약이다.

검증 스크립트scripts/sweep.sh 외rustc-perf 컴파일 벤치마크 53개를 헤드스타트 끔·켬으로 빌드하고 -Zearly-metadata-verify 로 점검한다.results 문서에서는 52개가 양쪽 모두 통과하고 stm32f4 는 장치 기능이 필요해 양쪽 모두 실패한다.

직접 써 보려면 README 의 순서를 따른다. 먼저 rustc 와 cargo 를 받아 패치를 적용하고 둘 다 빌드하는 스크립트를 돌린다.

scripts/setup.sh    # check out rustc + cargo, apply the patches, build both

그 다음 아무 Rust 프로젝트에서 패치된 rustc 와 cargo 를 지정해 실행한다.

RUSTC=/path/to/headstart/rustc/build/host/stage1/bin/rustc \
                      /path/to/headstart/cargo/target/release/cargo check -Zheadstart   # or build

CARGO_UNSTABLE_HEADSTART=true 나 .cargo/config.toml 의 [unstable] headstart = true 로도 켠다. 켜지 않으면 패치된 cargo 는 업스트림처럼 동작하므로 같은 바이너리로 공정한 비교 기준선을 얻는다고 README 는 설명한다. 한 가지 주의할 점은 results 문서가 적은 대로 sccache 처럼 rustc 출력을 끝날 때까지 버퍼링하는 rustc-wrapper 는 초기 메타데이터 알림을 cargo 에서 가려 아무것도 일찍 시작되지 않게 만든다는 것이다.

16코어와 4코어 벤치마크 측정 결과 분석

results 문서의 측정 조건은 이렇다. 클린 빌드를 scripts/bench.sh 로 재고, 같은 패치된 rustc·cargo 로 끔과 켬을 번갈아 돌려 중앙값을 적는다. 16코어는 AMD EPYC 9554P 에 16 jobs 이고 실제 프로젝트 13종은 3회씩이다. 4코어는 Claude Code 컨테이너의 4 jobs 이다. 측정 중 다른 사용자의 작업으로 VM 부하가 3~5 정도였다고 문서가 밝히며, 끔과 켬이 부하를 같이 받으므로 절감률은 비교할 수 있어도 절대 시간은 조금 높을 수 있다고 한다.

4코어, codex-rs (57a38c1)14% (475.92초에서 409.11초)측정 불가컨테이너 메모리 15GB 에서 headstart 없이도 codex-core 의 rustc 가 13.7GB 에서 OOM 으로 종료

16코어 기본 프런트엔드의 13개 프로젝트에서는 README 의 말대로 느려진 프로젝트가 없었다. 이것은 기본 프런트엔드에 한정한 말이다. 병렬 프런트엔드(-Zthreads=8)를 함께 켠 표에는 위에서 본 세 건의 -1~-2% 가 있다. results 문서는 이 셋을 실행 범위가 겹치는 오차 범위의 무승부로 본다. 병렬 프런트엔드가 headstart 와 겹치는 영역을 이미 처리하기 때문이다. 실제로 rust-analyzer 의 check 는 둘 중 하나만 켜도 90초에서 40~42초가 되고 둘을 함께 켜면 30초가 된다.

README 가 codex-rs 에서 든 37% 는 16코어에서 cratebank 로 기록한 클린 빌드 한 번씩의 값이다. results 문서는 samply 로 프로파일링한 이 기록에서 빌드가 511초와 323초였다고 적는다(약 37%). 같은 절의 3회 중앙값 38% 와 별개의 측정이다. 4코어의 codex-rs check 14% 도 다른 시스템과 커밋(57a38c1)의 값이므로 이들을 한 행에 섞을 수 없다. 이득의 크기는 빌드가 남겨 두던 유휴 코어에 비례한다. rust-analyzer 와 polars 는 headstart 없이 16 슬롯 중 평균 약 3개 컴파일이 동시에 돌았고 headstart 를 켜면 6~7개가 돌았다. 반대로 마지막에 큰 크레이트 하나로 끝나는 넓은 빌드(zola 의 minify_html_common 은 생성된 표 때문에 81초)는 이득이 작다. headstart 는 크레이트를 일찍 시작시킬 수는 있어도 쪼갤 수는 없기 때문이다.

rustc-perf 의 다중 크레이트 벤치마크 21개(16코어, 5회, 현재 버전)에서 cargo build 의 절감률은 serde_derive-1.0.219 의 37%, eza-0.21.2 의 35%, ripgrep-14.1.1 의 34% 에서 encoding 의 6% 까지 나뉜다. results 문서는 proc macro 연쇄(serde_derive, clap_derive)와 의존 그래프 끝의 바이너리가 모든 rlib 이 끝나기를 기다리지 않게 된 것을 build 이득의 주된 자리로 설명한다.

조기 실행에 따르는 위험과 자원 비용

design.md 의 위험 절과 results 문서가 말하는 비용은 다음과 같다.

  • 오류가 조금 늦게 나온다: 크레이트 자신의 본문 오류는 초기 기록 뒤에 나온다. cargo-0.87.1 빌드에서 초기 기록을 하는 280개 크레이트의 지연은 중앙값 4ms, p90 34ms, p99 249ms, 최댓값 532ms 였다. 이는 첫 번째 check 전용 버전에서 잰 값으로 이후 변경 뒤에는 다시 재지 않았다. 이 지연이 2019년 시도(rust-lang/rust#64112)가 멈춘 두 이유 중 하나라고 문서는 적는다.
  • 버려지는 작업과 출력: 크레이트가 실패하면 일찍 시작한 하류의 작업은 버려진다. cargo 는 의존이 모두 깨끗이 끝난 뒤에만 유닛의 출력을 내보내고 하나라도 실패하면 버리므로, 진단과 종료 상태는 기존과 같다. 달라질 수 있는 것은 진행 줄과 크레이트 사이 JSON 메시지 순서처럼 원래 타이밍에 따르던 출력이다.
  • 메모리: 컴파일러가 동시에 더 많이 살아 있고 일시 정지된 것도 상주한다. cargo 는 정지된 컴파일러 수를 아직 제한하지 않는다. 피크 메모리는 첫 번째 check 전용 버전에서만 재었고 -4%에서 +39%(nalgebra, 0.76GB에서 1.05GB)까지였다.
  • 작업 슬롯 경합: 재개된 컴파일은 빈 작업 슬롯을 기다리지 않는다. 기다리게 했더니 대신 시작된 작업과 토큰을 다투며 임계 경로가 굶었기 때문이다. headstart 가 더 많은 컴파일을 동시에 돌리므로 포화된 머신에서는 임계 경로가 느려질 수 있고, cargo 가 이를 위한 스케줄링 조정은 아직 하지 않는다고 문서는 적는다. 4코어의 bevy 와 typst 에서는 rustc CPU 시간이 3~7% 늘었다고 readiness 문서는 적는다.
  • 증분 컴파일: 하나의 함수 본문을 고친 뒤의 증분 cargo check 에서 codex-rs 는 16% 단축(codex-core 28.8초에서 24.2초, codex-protocol 61.4초에서 51.6초)이었고 첫 check 전용 버전에서 잰 cargo 자체 워크스페이스는 6~8% 였다. 클린 빌드보다 작지만 모든 편집에 적용된다.
  • 알려진 버그: 같은 크레이트의 두 번째 증분 세션이 early and full metadata disagree on the SVH 라는 오류로 패닉할 수 있고 zed 의 util 크레이트에서 발견되었으며 아직 고치지 못했다.

results 문서는 실제 프로젝트 빌드가 rustc-perf 스윕이 지나친 세 가지 버그를 드러냈고 모두 고쳤다고 적는다. 최적화된 의존(typst 는 의존을 opt-level 2, zed 는 proc macro 를 3 으로 빌드)에서 missing optimized MIR 로 실패한 것, -Zthreads=8 의 zola 가 headstart 로 80% 느려진 것(초기 기록 전 단계가 static 평가를 순차 루프로 돌린 탓이며 병렬 루프로 바꾸자 bevy·helix·lldap 의 작은 손실이 이득이 되고 typst 의 이득이 4%에서 22%가 되었다), cargo check --release 가 초기 크레이트에 MIR 을 요구한 것(-Zearly-metadata-verify 가 2,819건 보고)이다.

이 목록에서 results 문서가 직접 강조하는 것은 도움이 되지 않는 경우다. CPU 가 이미 꽉 찬 빌드(첫 버전은 12코어 맥에서 cargo-0.87.1 을 1% 줄이는 데 그쳤다), 빌드 스크립트와 그 안의 C 코드, proc macro, 의존 크레이트가 없는 단일 크레이트에서는 이득이 없거나 거의 없다.

공식 컴파일러 정식 반영까지 남은 과제와 현 단계 평가

README 는 이 패치들이 커밋 시리즈이며 각 커밋에 메시지와 테스트가 있고 업스트림 풀 리퀘스트가 되기 위한 것(meant to become upstream pull requests)이라고 적는다. readiness.md 의 결론은 한 줄이다. 디자인 논의와 함께 보여 줄 초안 PR 을 낼 준비는 되었으나(Ready for the design conversation), 아직 머지할 준비는 되지 않았다(Not yet ready to merge).

  • 컴파일러 쪽 절차: readiness 문서는 rustc 쪽 2~6번 커밋에 컴파일러 MCP 가 필요하다고 적는다. -Zearly-metadata 가 새 불안정 플래그이고 --json=artifacts 에 알림 세 종류가 늘기 때문이다. 문서는 MCP 에 교체 불변식(코드 생성 전에 초기 메타데이터로 로드된 의존에게 전체 메타데이터에서만 달라지는 질문을 하면 안 된다는 규칙)과 알림 프로토콜, 락 파일을 적어야 한다고 말한다.
  • 불변식이 강제되지 않음: 그 불변식은 손으로 관리하는 쿼리 목록으로, 그것도 -Zearly-metadata-verify 아래서만 검사된다. -Zvalidate-mir 가 걸린 구멍이 하나 알려져 있다.
  • cargo 만 구동할 수 있음: 로더는 rlib 이 .rmeta 옆에 있다고 가정하고 기다림은 의존 크레이트의 컴파일이 같은 머신에서 나란히 돈다고 가정한다. Bazel 과 Buck2 는 rmeta 액션을 샌드박스나 원격에서 돌리므로 이 부분의 설명이 필요하다고 문서는 쓴다.
  • jobserver: 재개된 컴파일이 토큰 없이 돌아 빌드가 한도를 한 작업 초과할 수 있다. make -j 안에서는 cargo 의 집계를 넘어 jobserver 의 계약을 깬다. 의도한 선택이지만 옹호하거나 상한을 두어야 한다고 문서는 쓴다.
  • 측정과 플랫폼: 16코어와 8코어 머신에서 현재 시리즈로 다시 재야 하고 메모리와 오류 지연도 현재 버전으로 다시 재야 한다. 락은 std 의 파일 잠금을 쓰지만 Windows 에서는 돌려 본 적이 없고 macOS 에서도 락이 폴링을 대체한 뒤로는 돌려 본 적이 없다. Linux 에서만 돌렸다.

HN 스레드에서는 게시자인 knuckleheads 가 이 변경 세트 자체는 들어가지 않을 것(LLM written, little to no thinking through of the broader design)이라고 쓰면서도 비슷한 것이 언젠가 나오기를 바란다고 덧붙였다. 이는 커뮤니티 게시판에 남은 한 사람의 말이고 컴파일러 팀의 입장이 아니다. 또 이 시리즈의 정확성 근거로 문서가 내세우는 것은 53개 벤치마크 중 52개의 양 모드 통과, 실제 프로젝트 312회 빌드의 동일한 진단, 그리고 -Zearly-metadata 를 모든 UI 테스트에 강제로 켠 실행에서 22,168개 통과와 4개 실패(타이밍에 따라 달라지는 출력만 다름)이다.

확인하지 못한 것

  • 컴파일러 팀·cargo 팀의 공식 반응과 MCP 의 제출 여부. HN 스레드의 게시자는 Rust Zulip 에 올린 글을 옮겨 적었다고 하지만 그 글과 팀의 응답은 확인하지 못했다.
  • 현재 버전에서의 피크 메모리와 오류 지연 수치. 문서가 인용하는 값은 첫 check 전용 버전의 것이다.
  • 16코어와 8코어에서 현재 시리즈로 다시 잰 헤드라인 수치. 16코어 수치는 마지막 수정 이전의 것이라고 readiness 문서가 적는다.
  • Windows 와 macOS 에서의 현재 락 구현 동작. 문서에 따르면 Linux 에서만 돌렸다.
  • 컴파일러 팀이 이 설계를 실제로 어떻게 평가했는지.
