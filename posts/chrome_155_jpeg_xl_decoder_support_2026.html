발표의 골자 — Chrome 155부터 JPEG XL 디코딩

Chrome 개발자 블로그는 Chrome 이 Chrome 155 부터 JPEG XL(.jxl) 이미지 포맷의 디코딩 지원을 배포한다고 발표했다. 블로그는 JPEG XL 을 현대 웹 개발자와 사진 작업자의 요구를 겨냥해 설계된 차세대 이미지 포맷으로 소개하고, JPEG 보다 30-50% 더 나은 압축, 무손실 압축, 내장 HDR 지원, 무손실 JPEG 트랜스코딩 등을 제공한다고 적었다.

블로그가 개발자에게 건넨 권고는 한 문장으로 요약된다. 최선의 결과를 얻으려면 AVIF 와 JPEG XL 을 둘 다 시험해 보라는 것이다. 이어서 Chrome 팀은 JPEG XL 이 고충실도 또는 무손실 압축, 특히 사진 이미지에서, 그리고 세밀한 점진적 디코딩(fine-grained progressive decoding)이 선호되는 경우에 가장 유용할 것으로 기대한다고 적었다. 「기대한다」는 표현이므로 측정 결과가 아닌 Chrome 팀의 전망이다.

글의 구성도 블로그가 밝혔다. 왜 JPEG XL 을 Chrome 에 들여왔는지, 메모리 안전성을 먼저 확보하기 위해 Rust 를 어떻게 썼는지, 빠르게 만든 성능 작업, 그리고 개발자 피드백과 웹 표준 생태계가 말해 주는 교훈이 순서대로 다뤄진다. 맺음 대목에서 블로그는 개발자, 콘텐츠 제작자, 플랫폼 운영자에게 파이프라인에서 .jxl 이미지와 애니메이션을 쓰기 시작하라고 권하며, 문제는 버그로 제보해 달라고 요청한다.

「155부터」의 범위 — 일정표와 지원 표기가 말하는 것

「Chrome 155 부터」가 어떤 날짜와 어떤 환경을 가리키는지는 블로그 본문만으로 정해지지 않는다. 본문은 버전 번호만 적고 날짜, 플래그 여부, 플랫폼별 범위를 적지 않는다. 이를 보완하는 공개 자료는 두 가지다.

  • Chromium Dash 마일스톤 일정. 155 의 branch_point 는 2026-09-14, earliest_beta 는 2026-09-16, early_stable 은 2026-09-23, stable_date 는 2026-10-06, 다음 stable_refresh 는 2026-10-13 으로 표기된다. 직전 154 의 stable_date 는 2026-09-22 이다. 따라서 일정표상 안정 채널 날짜는 블로그 게시일과 같다.
  • Can I use 의 Chrome 열. Chrome 152, 153, 154 는 「기본 꺼짐(d)」과 함께 chrome://flags/#enable-jxl-image-format 플래그로 켤 수 있다는 주석이 붙어 있고, 155 부터 지원(y)으로 표기된다. 즉 이전 버전에서는 플래그 뒤에 있던 기능이 155 에서 플래그 없이 지원되는 것으로 표기된다.
  • MDN 의 서술. MDN 이미지 형식 문서는 Chrome 145 이상이 #enable-jxl-image-format 플래그 뒤에서 JPEG XL 을 지원한다고 적는다. 이 문장은 155 발표 이전 시점의 기재이므로 현재 상태를 말하는 것으로 읽으면 안 된다.
  • Android 범위. 블로그는 플랫폼을 구분하지 않는다. Can I use 의 Chrome for Android 열은 154 까지만 있고 「미지원, 기본 꺼짐」으로 표기되어 155 항목이 없다. 데스크톱과 Android 의 동시 적용 여부는 이 자료들로 판정되지 않는다.

JPEG XL 의 특성 — 블로그 주장과 MDN 기재

JPEG XL 의 성능 수치는 Chrome 블로그의 한 문장에 담겨 있다. 「JPEG 대비 30-50% 더 나은 압축」은 Chrome 개발자 블로그가 적은 문장이며, 이미지 유형·품질 지표·측정 방식 같은 비교 조건은 블로그에 제시되어 있지 않다. 이 수치는 조건 없이 일반화하지 않고 블로그의 주장으로 읽는 것이 맞다.

반면 포맷의 기능 범위는 MDN 이 별도로 정리한다. MDN 은 JPEG XL 을 ISO/IEC 18181 로 표준화된 로열티 없는 래스터 이미지 포맷이라고 설명하며, 손실·무손실 압축, 점진적 디코딩, 높은 비트 심도, 넓은 색 영역, HDR, 투명도, 애니메이션을 지원하고 기존 JPEG 를 원본 복원이 가능하도록 무손실로 트랜스코딩할 수 있다고 적는다.

표의 내용은 포맷끼리 압축 효율을 수치로 비교한 것이 아니다. MDN 이 포맷마다 적은 설명을 같은 칸에 옮긴 것이며, 칸이 비어 있는 곳은 해당 문서에 그 항목에 대한 기재가 없다는 뜻이다. 압축 효율의 순위는 이 표로 정해지지 않는다.

  • 블로그의 위치 지정. Chrome 팀은 JPEG XL 이 JPEG 의 대체 하나가 아니라 AVIF 와 나란히 시험해 볼 선택지라고 쓴다. AVIF 보다 우월하다는 서술은 블로그에 없다.
  • MDN 의 일반 권고. MDN 은 래스터 이미지에 WebP 나 AVIF 를 우선 권하고, 크고 해상도가 높은 래스터 이미지에는 JPEG XL 도 고려하라고 적는다.
  • 용도 구분. MDN 은 스크린샷·다이어그램·로고·선화에는 무손실 인코딩을, 사진처럼 연속 톤 이미지에는 손실 압축을 권한다. 이는 포맷이 아닌 이미지 유형에 대한 일반 지침이다.

Rust 디코더 jxl-rs — 안전을 먼저 둔 설계

블로그의 두 번째 절 제목은 「Safety first: Reimplementing the decoder in Rust (jxl-rs)」이다. 블로그는 이미지 디코더를 모든 현대 브라우저에서 가장 중요하고 가장 많이 노려지는 공격 표면 중 하나로 규정한다. 디코더는 네트워크에서 온 복잡하고 신뢰할 수 없는 이진 구조를 렌더러 프로세스 안에서 곧바로 처리하며, 과거에 C++ 같은 메모리 비안전 언어로 쓴 디코더에서 경계 밖 읽기, 힙 오버플로, use-after-free 같은 취약점이 흔했다고 적는다.

  • 보안 모델. 블로그에 따르면 Chrome 의 보안 모델은 샌드박싱과 심층 방어(defense-in-depth)에 의존하며 rule of two 의 안내를 받는다. 그러나 샌드박싱은 이차 방어층이라고 블로그는 쓴다.
  • 선택. 그런 위험을 근원에서 없애기 위해 JPEG XL 디코더의 순수 Rust 구현인 jxl-rs 를 통합했다고 블로그는 밝혔다.
  • Rule of 2 의 내용. 블로그가 링크한 Chromium 문서는 신뢰할 수 없는 입력 처리, 안전하지 않은 구현 언어, 높은 권한의 세 가지 중 둘까지만 고르라는 규칙이라고 설명한다. 이미지 디코더는 입력이 신뢰할 수 없으므로 나머지 둘 중 하나를 피해야 한다는 해석이 된다.
  • 검증. 블로그는 퍼징과 코드에 대한 AI 검토를 포함한 여러 최신 기법으로 jxl-rs 를 검증했고 전체 구현 이력에서 메모리 안전성 버그를 찾지 못했다고 밝혔다. 이는 Chrome 팀의 자체 보고이며 제3자 감사 결과는 아니다.

속도 설계 — target_feature_11 과 jxl_simd

블로그는 안전만으로는 채택이 어렵다는 입장을 분명히 한다. 최고의 비안전 대안과 거의 같은 속도를 내는 메모리 안전 디코더는 성능 타협이 큰 선택지보다 훨씬 분명한 선택이라는 서술이다. 이 문장은 설계 원칙의 표명이며, 블로그 본문에는 jxl-rs 의 속도를 libjxl 과 비교한 수치가 제시되어 있지 않다.

  • SIMD 의 안전한 사용. 현대 코덱 성능의 근본 요소는 SIMD 하드웨어를 최대한 쓰는 것이며, 이를 안전하게 하려고 Rust 의 target_feature_11 기능이 안정화되어야 했다고 블로그는 적는다. 이 기능으로 unsafe 코드 없이 SIMD 명령을 쓸 수 있게 되었다는 설명이다.
  • Rust 쪽 기록. 블로그가 링크한 rust-lang/rust 의 풀 리퀘스트 134090 은 제목이 「Stabilize target_feature_11」이며 2025-02-13 에 닫힌 것으로 GitHub 에 표시된다.
  • jxl_simd. 다음 단계로 C++ Highway 라이브러리에서 영감을 받은 SIMD 추상화 계층 jxl_simd 를 만들었다. Highway 는 원래 libjxl, 곧 JPEG XL 의 C++ 참조 구현을 위해 개발된 라이브러리라고 블로그는 설명한다.
  • 결과. 두 가지가 합쳐져 SIMD 성능 최적화를 포기하지 않는 다중 플랫폼 라이브러리를 작성하면서 unsafe 연산을 소수의 철저히 검토된 지점으로 제한할 수 있었다고 블로그는 쓴다.
  • libjxl 계승. jxl-rs 의 성능 최적화는 libjxl 의 것을 기반으로 한다. 영역 경계를 넘는 단계를 위한 일반 처리 파이프라인과 데이터 복사를 최소화하는 설계가 여기에 포함된다.
  • 추적. 서로 다른 하드웨어 플랫폼에서의 Rust 재구현 성능은 jxl-rs performance dashboard 에서 추적해 왔다고 블로그는 적는다.

개발자 피드백과 Interop 2026 JPEG XL Investigation

블로그의 마지막 본문 절은 결정의 근거를 다룬다. Chrome 팀은 버그, 설문, Developer Signals Project, Interop Project 등 여러 경로로 웹 개발자 피드백을 고려한다고 밝혔다. JPEG XL 을 배포하기로 한 결정은 웹 개발자의 일관된 피드백과 요청에 근거했고, 그것이 가장 뚜렷하게 나타난 곳은 2026년과 그 이전 여러 해에 인기 있는 제안이었던 Interop 프로세스였다고 블로그는 적었다.

상호운용을 위해 Chrome 팀은 Interop 2026 JPEG XL Investigation 에 참여했다고 블로그는 쓴다. 목적은 브라우저에서 JPEG XL 의 모든 기능에 대한 테스트 범위가 마련되고 그 테스트가 Chrome 에서 통과되도록 하는 것이다. 이 조사의 저장소(web-platform-tests/interop-jpegxl)는 범위를 다음 항목으로 적어 둔다.

  • 색과 비트 심도. 8·10·12·16비트 심도, Display P3·Adobe RGB·Rec.2020·ProPhoto RGB 등 넓은 색 영역, ICC 프로파일의 드문 사용, CMYK 변환을 시험 대상으로 든다.
  • HDR. 톤 매핑(PQ/HLG)과 게인 맵(ISO 21496-1)을 시험한다고 적혀 있다.
  • 부호화 방식. VarDCT 의 가장 큰·작은 블록 크기, Modular 모드의 손실·무손실, 알파 채널을 VarDCT 와 Modular 양쪽에서 시험한다.
  • 점진적 렌더링. DC 데이터만 그릴 때의 렌더링 방식, 그리고 더 낮게 다운샘플된 progressive_dc 를 지원할지에 대한 정렬을 다룬다.
  • 그 밖. 무손실 트랜스코딩된 JPEG, 방향(코드스트림의 orientation 을 따르고 EXIF 방향은 무시), 애니메이션, 레이어, 최소 JPEG XL 파일로 만드는 JPEG XL art 도 범위에 있다.
  • 웹 통합 지점. img·picture·source, video poster, input type=image, embed·object·iframe, link rel=preload as=image, SVG image, CSS 의 background-image·content·image-set()·list-style-image 를 시험한다고 적혀 있다.

MDN 의 이미지 형식 문서도 비슷한 맥락으로 Safari 17 이상이 JPEG XL 을 지원하고, Safari 는 JPEG XL 파일의 점진적 다운로드를 지원하지 않아 전체를 받은 뒤에야 그린다고 적는다. 두 출처 모두 Safari 에서 점진적 디코딩이 되지 않는다고 일치하게 기재한다. 블로그가 내세운 「세밀한 점진적 디코딩」의 이점이 브라우저에 따라 다르게 나타날 수 있다는 뜻이다.

웹 개발자의 폴백 마크업과 도입 전 확인 사항

MDN 은 JPEG XL 을 쓸 때 AVIF, WebP, JPEG 같은 대체 포맷을 picture 요소로 함께 제공하라고 적고, 일반 img 요소는 호환성 폴백을 지원하지 않지만 picture 요소는 지원한다고 설명한다. 아래는 MDN 이미지 형식 문서의 「Providing image fallbacks」 예시 그대로이다. 이 예시는 SVG 를 우선하고 WebP, PNG, GIF 순으로 내려가는 구조이며, source 를 몇 개 두어도 되지만 보통 2-3개면 충분하다는 설명이 붙는다.

<picture>
                      <source srcset="diagram.svg" type="image/svg+xml" />
                      <source srcset="diagram.webp" type="image/webp" />
                      <source srcset="diagram.png" type="image/png" />
                      <img
                        src="diagram.gif"
                        width="620"
                        height="540"
                        alt="Diagram showing the data channels" />
                    </picture>

이 구조를 JPEG XL 에 적용하는 방법은 해석이다. 위 예시에서 가장 앞의 source 가 가장 우선이므로, JPEG XL 을 먼저 시도하게 하려면 type 이 image/jxl 인 source 를 맨 앞에 두면 된다는 점은 MDN 이 설명한 구조에서 도출된다. MDN 문서에 JPEG XL 을 넣은 예시 코드가 있는 것은 아니다.

  • 폴백 순서. picture 안의 source 는 위에서 아래로 평가되므로 이미지 포맷의 우선순위를 어떻게 둘지는 서비스 목적에 따라 정한다. 블로그는 AVIF 와 JPEG XL 을 둘 다 시험하라고만 권한다.
  • 이미지 유형. 블로그가 JPEG XL 이 유용하다고 본 조건은 고충실도 또는 무손실 압축과 세밀한 점진적 디코딩이 필요한 사진이다. 다른 유형에서의 우열은 블로그에 없다.
  • 기초 개념. 해상도·압축 품질·포맷 변환의 기본은 이미지 압축 입문 글에서 다뤘으므로 여기서 반복하지 않는다.

확인하지 못한 것

  • 비교 조건. 「JPEG 대비 30-50% 더 나은 압축」의 이미지 유형, 품질 지표, 측정 방식은 블로그에 없다.
  • Android 의 상태. Chrome 155 의 Android 판에서 JPEG XL 이 기본 활성화되는지는 블로그와 Can I use 로 판정되지 않는다.
  • 속도 수치. jxl-rs 의 속도를 libjxl 이나 다른 포맷과 비교한 수치는 블로그 본문에 없고 성능 대시보드 링크만 있다.
  • 인코딩 계획. 브라우저 내장 인코딩이나 Canvas·WebCodecs 를 통한 .jxl 생성에 관한 서술은 블로그에 없다.
  • Firefox 158 의 출시일. Can I use 가 Firefox 158 을 지원으로 표기하지만 그 버전의 안정 출시 날짜는 이 자료들로 판정되지 않는다.
  • 이전 지원 이력. Chrome 의 과거 JPEG XL 지원 이력은 블로그에 서술이 없어 다루지 않는다.
