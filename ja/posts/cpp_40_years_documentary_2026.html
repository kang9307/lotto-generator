C++ 40年史 - ベル研究所から現在まで、ドキュメンタリーがたどった旅

一つの言語はいかにして死なず、再び成長したか

2026年6月7日 IT・技術

序論: 40年を耐えた言語と、一本のドキュメンタリー

2026年6月、一本のドキュメンタリーが公開され、開発者コミュニティがざわつきました。タイトルはシンプルです。「C++: The Documentary」。1979年、ベル研究所の小さな実験から始まり、ゲームエンジンや金融取引システム、CERNの素粒子物理実験、そして世界中の数百万人の開発者の指先まで広がった一つの言語の40年を描いた作品です。このドキュメンタリーには、言語を作ったBjarne Stroustrup(ビャーネ・ストロヴストルップ)、標準化を率いたHerb Sutter、STLを設計したAlexander Stepanov、そしてDoomとQuakeを作ったJohn Romeroまで登場します。

興味深いのは、このドキュメンタリーが「思い出語り」ではないという点です。公開時に引用された統計によれば、C++は2025年第3四半期時点で上位4プログラミング言語の中で最も速く成長しており、直近3.5年でユーザーが90%以上増えたとされます。かつて「レガシー」と扱われた言語が、再び成長曲線を描いているのです。本稿では、ドキュメンタリーがたどった流れに沿って、C++がどこで生まれ、いかにして標準となり、なぜ今も使われ、現代C++は何が変わり、そしてRustの時代にどんな意味を持つのかを落ち着いて整理します。

1. 誕生: ベル研究所と「C with Classes」(1979)

物語は1979年、デンマーク出身の若き計算機科学者Bjarne StroustrupがAT&Tベル研究所に加わったことから始まります。彼は博士課程で分散システムを研究する中で、一つのジレンマに直面しました。シミュレーションに優れたSimula(シミュラ)はクラスのような強力な抽象化を提供しましたが実務には遅すぎ、逆にBCPLは速いものの大規模ソフトウェアを扱うには低水準すぎたのです。

Stroustrupの結論は明快でした。「Cの速度にSimulaの抽象化を載せよう」。1979年10月、彼はCコードにSimula風のクラスを加える前処理系Cpreを作り、これが「C with Classes」の始まりでした。この時期に加わった機能 - クラス、派生クラス、強い型検査、インライン関数、デフォルト引数 - は、今日のC++の骨格をそのまま決定づけました。重要な哲学はこのときすでに根づいていました。「抽象化の代価を実行時に払わない(ゼロオーバーヘッド抽象化)」。使わない機能には費用がかからず、使う機能も手書きのコードと同じだけしか高くつかない、という原則です。

2. 名前が変わる: C++の誕生(1982〜1985)

1982年、Stroustrupは「C with Classes」の後継を開発し始め、新しい名前を考えました。いくつもの候補の末に選ばれたのがC++です。C言語のインクリメント演算子++から取り、「Cを一段引き上げる」という意味を込めました。命名自体にプログラマーのウィットが滲んでいます。

1983年にはCfrontというコンパイラが登場しました。Cfrontの肝は、C++コードを一旦Cコードに変換し、既存のCコンパイラでコンパイルする方式でした。この巧妙な戦略のおかげで、C++は当時ほぼすべてのプラットフォームに存在したCのツール群の上に乗ることができました。そして1985年、C++は初の商用リリースとともに正式に世に出て、同年Stroustrupの著書『The C++ Programming Language』初版が出版されました。まだ公式標準がなかった時代、この本自体が事実上の標準の役割を果たしました。

C++の設計哲学は一文に集約されます。「プログラマーを信じよ。ただし抽象化の代価は実行時ではなくコンパイル時に払わせよ」。

3. 標準化の時代: C++98への道

1980年代後半、C++は急速に広まりましたが、同時に危険も増しました。コンパイラごとに挙動が少しずつ異なり、一冊の本に依存する非公式標準では大規模な産業採用を支えきれませんでした。そこで1990年代初頭、ISOとANSIの委員会が組まれ、本格的な標準化作業が始まりました。

その結実が1998年のC++98(ISO/IEC 14882:1998)です。C++初の公式国際標準であり、この過程で最も重要な出来事は、Alexander Stepanovが設計したSTL(Standard Template Library)の統合でした。vector、map、set、listといったコンテナとアルゴリズムが、テンプレートベースのジェネリックプログラミングとして標準ライブラリに入りました。STLは単なるデータ構造の集まりではなく、「コンテナ・イテレータ・アルゴリズム」を分離して組み合わせる考え方そのものをC++に刻んだ出来事でした。2003年には、C++98のバグと曖昧さを正した小規模修正版C++03が出ました。

4. 停滞と「C++の冬」

C++98以降、C++はしばらく停滞期に入ります。ドキュメンタリーでも「2000年代初頭のC++の冬」という表現でこの時期を扱います。JavaやC#のようにガベージコレクションを備えた言語が台頭し、「C++は複雑すぎて危険だ」という批判が噴出しました。ポインタの誤った扱いから生じるメモリリークやクラッシュは、C++の代表的な弱点と名指しされました。

2003年以降、実に8年間も新しい標準が出なかったという事実は、この停滞を象徴的に示しています。多くの人がC++の全盛期は終わったと考えました。しかしこの沈黙の時期は、実は次の飛躍のための準備期間でした。委員会は言語を根本から現代化する大きな絵を描いていたのです。

5. 復活: C++11と「現代C++」の始まり

2011年、8年の沈黙を破って発表されたC++11はゲームチェンジャーでした。あまりに多くが変わったため、人々はこの時点からを「現代C++(Modern C++)」と呼び始めました。Stroustrup本人も「C++11はまるで新しい言語のように感じる」と表現しています。主要な追加機能を整理すると次の通りです。

  • スマートポインタ(unique_ptr、shared_ptr): 手動のnew/deleteなしで資源の寿命を自動管理します。メモリリークの主因を構造的に取り除きます。
  • ムーブセマンティクス: 不要なコピーの代わりに資源の所有権を「移動」させ、性能を引き上げます。大きなオブジェクトの返却・受け渡しの費用を劇的に減らしました。
  • auto型推論: 冗長な型宣言をコンパイラに推論させ、コードを簡潔にします。
  • ラムダ式: 匿名関数をコードの流れの中に直接書けるようになりました。
  • constexpr: コンパイル時計算を明示的に支援します。

これらの変化に共通する方向は明確です。「危険な手作業を減らし、コンパイラにより多くの仕事をさせる」。とりわけスマートポインタとムーブセマンティクスは、C++の持病だったメモリ問題を大きく緩和しつつ、ガベージコレクタの実行時費用は避けました。

6. 3年周期の進化: C++14 / 17 / 20

C++11以降、委員会は3年周期で標準を出す規則的なリズムを定着させました。この予測可能性そのものが、産業の信頼回復に大きく寄与しました。

  • C++14 (2014): C++11の隙間を埋める小規模な拡張です。ジェネリックラムダや変数テンプレートなど使い勝手を整えました。
  • C++17 (2017): 標準ファイルシステムライブラリ(<filesystem>)と並列STLが代表機能です。構造化束縛、std::optional、std::string_view、if constexprなど実用的な道具が多数追加されました。
  • C++20 (2020): C++11に匹敵する大変革です。よく「ビッグ4」と呼ばれる四機能 - コンセプト(Concepts)、レンジ(Ranges)、コルーチン(Coroutines)、モジュール(Modules) - が核心です。

とりわけC++20のビッグ4は、言語の表現方法そのものを変えました。コンセプトはテンプレートに制約を明示し、難解だったエラーメッセージを読めるものにしました。レンジはコレクション処理を宣言的につなげられるようにしました。コルーチンは非同期・遅延評価のコードを自然に書けるようにし、モジュールは数十年来のヘッダファイル方式による遅いコンパイルとマクロ汚染を根本的に改善する道を開きました。

7. コードで見る変化: 旧C++ vs 現代C++

言葉だけでは抽象的なので、同じ作業を二つの時代のスタイルで比較してみましょう。メモリを直接扱う旧来の方式と、スマートポインタ・レンジを使う現代の方式の違いです。

// 旧スタイル (C++98) - 手動メモリ管理、リークの危険
#include <iostream>

void old_style() {
    int* arr = new int[3];          // 手動割り当て
    arr[0] = 1; arr[1] = 2; arr[2] = 3;

    int sum = 0;
    for (int i = 0; i < 3; ++i) {    // インデックス基準ループ
        sum += arr[i];
    }
    std::cout << sum << std::endl;

    delete[] arr;                    // 忘れれば即メモリリーク
}
// 現代スタイル (C++20) - RAII、標準アルゴリズム、安全な推論
#include <vector>
#include <numeric>
#include <iostream>

void modern_style() {
    // スタック上で自動管理されるコンテナ - delete不要
    std::vector<int> nums{1, 2, 3};

    // 標準アルゴリズムで意図を宣言的に表現
    auto sum = std::accumulate(nums.begin(), nums.end(), 0);

    std::cout << sum << std::endl;
}   // numsはスコープを抜けると自動解放 (RAII)

核心の違いはdeleteが消えたことです。現代C++のRAII(Resource Acquisition Is Initialization、資源獲得は初期化)原則は、資源の寿命をオブジェクトの寿命に結びつけます。オブジェクトがスコープを抜けると資源が自動的に返されるため、「deleteを忘れて生じたリーク」という古典的なバグが構造的に消えます。スマートポインタはまさにこのRAIIをポインタに適用した例です。

8. なぜ今もC++なのか: 性能こそアイデンティティ

2026年もC++が健在な理由は、一語に集約されます。性能です。より正確には、「ガベージコレクタなしでハードウェアに近い制御を提供しつつ、高水準の抽象化を使える」という独特の位置です。この特性が輝く分野は明確です。

分野 なぜC++か 代表例
ゲームエンジン フレーム単位のミリ秒制御、予測可能な遅延 Unreal Engine、主要AAAゲーム
OS・ブラウザ 低水準ハードウェアアクセス、極限の最適化 Windowsの中核、Chrome/V8
金融取引 ナノ秒単位の遅延がそのまま利益 高頻度取引(HFT)システム
組み込み・自動車 限られた資源、リアルタイム制御 車両制御、航空・宇宙
科学計算 大規模数値演算のスループット CERN素粒子物理解析(ROOT)

あるベンチマーク報告によれば、遅延が核心の一部アプリケーションではC++がRustより15〜20%速く動くこともあります。これはRustが安全のために加える一部の実行時検査がないためです。毎サイクルが重要なゲームエンジンや組み込みでは、こうした微差が採用の根拠になります。ある研究では、組み込み開発者の73%がリアルタイムシステムにC++を使うと答えました。

9. 挑戦者Rust: 競争ではなく共存

現代C++の話題でRustは外せません。Rustは所有権(ownership)と借用検査(borrow checker)を通じて、ダングリングポインタ、use-after-free、データ競合をコンパイル時に遮断します。メモリ安全が命の自動車・組み込み分野で強力な魅力です。一時は「RustがC++に取って代わる」という見通しが流行しました。

しかし2026年の現実は「置き換え」よりも「共存」に近いです。その理由は次の通りです。

  • 膨大な既存コードベース: ゲームエンジン、OS、金融システムに積み上がった数十年分のC++コードを一晩で書き直すことはできません。
  • エコシステムと道具の成熟度: ライブラリ、デバッガ、プロファイラなどC++エコシステムの深さは圧倒的です。
  • C++自身の進化: C++26はstd::vector・std::stringの境界検査を強めた「ハードン化された標準ライブラリ」で安全性の差を縮めています。

実際の産業の選択は明確です。既存資産と極限性能が必要な領域はC++が守り、新規に始める安全重視のプロジェクトはRustが取る、という分業です。両言語を一つのシステム内で混ぜて使う事例も増えています。Rustへの段階的移行に関心があればGoからRustへの移行ガイドを、メモリ安全と性能の均衡についてはRustで実装したZstandardの分析を併せて読むと、この流れがより鮮明になります。

10. ドキュメンタリーが投げかけるメッセージ

「C++: The Documentary」はCultRepoが制作し、金融分野の後援を受けて作られました。単なる技術紹介を超え、一つの言語が40年間どう生き残り、再び成長したかというより大きな問いを扱います。ドキュメンタリーが示すメッセージを整理すると三つです。

第一に、持続の力です。C++は一度も「最もトレンディな言語」だったことはありませんが、黙々と進化し続け、消えませんでした。第二に、後方互換性の重みです。数十年前のコードが今日もコンパイルされねばならないという制約は言語を複雑にしますが、同時に巨大な産業が安心して寄りかかれる土台になります。第三に、コミュニティと委員会の献身です。標準を巡る果てしない議論と妥協こそが、C++を生かし続けた原動力でした。

11. C++を学ぼうとする人へ

この歴史がどれほど興味深くても、結局は実用的な問いが残ります。「今C++を学ぶべきか、学ぶならどう学ぶか」。ドキュメンタリーの流れと現代C++の方向を踏まえると、次の通りです。

  1. 現代C++から始めよ。 古い教材のnew/delete中心スタイルではなく、C++17/20以降のスマートポインタとRAIIを最初から身につけましょう。同じ言語でも安全性と生産性が全く違います。
  2. STLとアルゴリズムに慣れよ。 vector、map、そして標準アルゴリズムは現代C++の日常語です。自前で実装する前に標準を先に探す習慣が重要です。
  3. なぜC++かを明確にせよ。 ゲーム、組み込み、高性能システムのようにC++が輝く分野を目標にすれば学習動機が明確になります。単純なWebバックエンドなら他の選択がよいこともあります。
  4. 道具も一緒に学べ。 コンパイラ警告を最大に上げ、静的解析器とサニタイザ(アドレス・メモリ検査ツール)を習慣化すれば、C++の危険を大きく減らせます。

12. 結論 + 今すぐ適用できる3つ

C++の40年は一文に集約されます。「性能を諦めずに、絶えずより安全で表現力豊かに進化した言語」。ベル研究所の小さな前処理系から始まり、標準化の道と「冬」を越え、C++11の復活とC++20の大変革を経て、今やC++26を前に再び最も速く成長する言語になりました。Rustの挑戦さえ、C++を終わらせるよりも、より安全に進化させる刺激となりました。

今すぐ実践できる三つで締めくくります。

  1. 現代C++として見直せ。 昔C++に触れて離れたなら、C++17/20のスマートポインタ・レンジ・コンセプトを30分だけ眺めてみましょう。「これがあのC++?」と思うほど変わっています。
  2. 手動メモリ管理をRAIIに替えよ。 既存コードに残るnew/deleteをunique_ptr・vectorのようなRAII道具へ段階的に替えれば、最も多いメモリバグが消えます。
  3. ドキュメンタリーを自分で観よ。 「C++: The Documentary」は技術を超え、「一つの技術がいかにして長く生き残るか」への洞察を与えます。言語を問わず、作り手なら一度観る価値があります。
