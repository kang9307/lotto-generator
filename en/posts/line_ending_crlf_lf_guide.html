CRLF and LF - What Actually Breaks When You Move Between Windows and Linux 2026

What one invisible byte does to a shebang, a variable comparison and the git index, and the order in which to undo it

Sep 1, 2026 Tech & IT

You edit a deploy script on Windows, push it to a server, and it dies leaving one line: bad interpreter. You open the file and nothing is wrong. The first line clearly says #!/bin/bash, there is no typo, the permissions are right. It still will not run. What most people do next is retype the script from scratch, which usually works, and they never find out what the problem was.

The problem is one byte at the end of the line that your editor does not show you. This piece covers where that byte comes from, what it does to shells, to variables and to the git index once it is there, and in what order to undo it. Nothing here is described from memory. There are three of them - look at the bytes

There are three line ending conventions. Unix-like systems use LF, one byte 0x0A. Windows uses CRLF, two bytes 0x0D 0x0A. Classic Mac OS used a lone CR, one byte 0x0D. The third one is almost never produced today, but it still shows up in inherited material. Rather than memorise this, look at it once.

$ printf 'hello\nworld\n'     > lf.txt
$ printf 'hello\r\nworld\r\n' > crlf.txt
$ printf 'hello\rworld\r'     > cr.txt

$ xxd lf.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.
$ xxd crlf.txt
00000000: 6865 6c6c 6f0d 0a77 6f72 6c64 0d0a       hello..world..
$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ file lf.txt crlf.txt cr.txt
lf.txt:   ASCII text
crlf.txt: ASCII text, with CRLF line terminators
cr.txt:   ASCII text, with CR line terminators

The dots on the right of xxd stand in for characters that cannot be printed. In the LF file there is one dot after hello; in the CRLF file there are two. That difference is the whole subject of this article. The visible text is identical and only the file size grows, by one byte per line. For a three-line file that is 17 bytes against 20.

NameBytesEscapeWhere it is usedWhen you meet it now
LF0x0A\nLinux, Unix, modern macOS, the web, most language sourcesThe default. Use it unless there is a reason not to
CRLF0x0D 0x0A\r\nWindows Notepad and batch files, many network protocolsWindows editors often put it in new files
CR0x0D\rClassic Mac OS, before 2001In inherited material only. Nothing creates it now

Why it split into two in the first place

The names of the two characters carry the history. CR is carriage return, moving the print head back to the start of the line; LF is line feed, advancing the paper by one line. On mechanical printing devices these were separate motions. One lineage kept that convention in the file format; the other decided one character per line was enough.

The Unix choice is written into the standard. POSIX defines a line as a sequence of zero or more non-newline characters plus a terminating newline character. The newline character there is \n alone, and CR is just an ordinary character that belongs to the data. So when a CRLF file is handed to a Unix tool, the CR is treated as the last character of the line. It is not a control character to be stripped; it comes along as part of the value. Every failure below follows from that one sentence.

  • From a Unix point of view, each line of a CRLF file is content plus a CR. The CR is not a separator, it is the final character of the content
  • So the variable you believe holds "prod" actually holds "prod\r"
  • Comparison, path building, numeric conversion and hashing all go wrong. And the screen shows nothing unusual
  • The other direction, an LF file fed to a Windows tool, is far more forgiving. Most Windows tools today read LF without complaint

How a shell script dies

Start with the famous symptom. Save a script whose first line is #!/bin/bash with CRLF endings and the actual bytes of that line become #!/bin/bash\r\n. When the kernel parses the shebang, the interpreter path runs up to the newline, so the program to be launched is not /bin/bash but /bin/bash with one extra CR character on the end. No such file exists, so it fails.

The bytes leave no room for doubt.

$ printf '#!/bin/bash\r\necho "hi"\r\n' > crlf.sh
$ chmod +x crlf.sh
$ head -c 24 crlf.sh | xxd
00000000: 2321 2f62 696e 2f62 6173 680d 0a65 6368  #!/bin/bash..ech
00000010: 6f20 2268 6922 0d0a                      o "hi"..

6173 68 is ash, and what follows is 0d 0a. The path string /bin/bash is immediately followed by 0x0D. Run it in that state and you get an error saying the interpreter cannot be found. The same mechanism reproduces without a shebang at all: just call an executable whose path has a CR glued to the end.

$ "/bin/bash$(printf '\r')" -c 'echo hi' 2>err.txt
$ cat -A err.txt
/usr/bin/bash: line 1: /bin/bash^M: No such file or directory$

$ xxd err.txt
00000000: 2f75 7372 2f62 696e 2f62 6173 683a 206c  /usr/bin/bash: l
00000010: 696e 6520 313a 202f 6269 6e2f 6261 7368  ine 1: /bin/bash
00000020: 0d3a 204e 6f20 7375 6368 2066 696c 6520  .: No such file
00000030: 6f72 2064 6972 6563 746f 7279 0a         or directory.

The 0d at offset 0x20 is the point. There is a real CR byte inside the error message. cat -A renders it as ^M. The ^M in the familiar bad interpreter: /bin/bash^M is exactly this byte; the shell is not inventing a character that is not there.

When the shebang goes through env the error looks different, and rather more helpful, because env quotes the argument it was given.

$ env "bash$(printf '\r')" --version
env: 'bash\r': No such file or directory

Here the \r is printed literally. Writing shebangs through env turns out to be an advantage when you are debugging this.

Git Bash hides this bug from you

Here is why the problem survives so long. Run the crlf.sh created above inside Git Bash and nothing happens at all. It works.

$ ./crlf.sh
hi

$ printf '#!/usr/bin/cat\r\nhello\r\n' > catshebang.sh
$ chmod +x catshebang.sh
$ ./catshebang.sh | cat -A
#!/usr/bin/cat^M$
hello^M$

The second example is the proof. With the shebang pointing at /usr/bin/cat, cat really did run and printed the file. In other words the MSYS2 exec layer strips the CR from the end of the shebang line and resolves the interpreter for you. The same output also shows that the CR inside the file is untouched: the content line still carries ^M.

The result is that the script runs fine on the developer laptop. It gets committed, reviewed, and shipped into the pipeline. And then it dies for the first time on a Linux server. That is how this bug passes code review. Some bash builds are said to carry an igncr option that tells the shell to ignore CR, but the bash 5.2.37 in this environment does not have it.

$ shopt igncr
/usr/bin/bash: line 1: shopt: igncr: invalid shell option name

So on this topic, it works on my machine is not information. If your machine is Windows, it is supposed to work.

The nastier case is a CR at the end of a value

The shebang case at least fails loudly. What keeps people busy far longer happens when a config file is read into variables. It is common for the script itself to be LF while the .env or config file it reads is CRLF. Nothing dies here. A conditional just quietly returns the wrong answer.

$ printf 'ENV=prod\r\nPORT=8080\r\n' > app.conf

$ cat readconf.sh
#!/bin/bash
while IFS='=' read -r k v; do
  export "$k=$v"
done < app.conf
echo "ENV=[$ENV]"
if [ "$ENV" = "prod" ]; then echo "MATCH"; else echo "NO MATCH"; fi
echo "length=${#ENV}"

$ bash readconf.sh
ENV=[prod]
NO MATCH
length=5

The screen says ENV=[prod]. Four characters, inside brackets. Yet it reports that this is not equal to prod, and that its length is 5. Trying to reconcile those three lines by eye can burn hours. cat -A ends it immediately.

$ bash readconf.sh | cat -A
ENV=[prod^M]$
NO MATCH$
length=5$

The value is not prod but five characters, prod followed by a CR. There is one subtlety worth pinning down here: whether the CR survives depends on how you read the file.

$ printf 'v2.4.1\r\n' > version.txt

$ read -r VER2 < version.txt
$ echo "len2=${#VER2}"
len2=7
$ printf '%s' "$VER2" | xxd
00000000: 7632 2e34 2e31 0d                        v2.4.1.

$ VER=$(cat version.txt)
$ echo "len=${#VER}"
len=6
$ printf '%s' "$VER" | xxd
00000000: 7632 2e34 2e31                           v2.4.1

Read with read and the CR stays, giving 7 characters; read through command substitution and you get 6. The bash in this environment strips the trailing CR along with the trailing newline in command substitution. That too is a place where Windows is quieter than it should be. Pipes, by contrast, pass the CR straight through.

$ printf 'a\r\nb\r\n' | xxd
00000000: 610d 0a62 0d0a                           a..b..

So for the same file, whether the CR survives depends on whether you looped with while read, captured with $(...), or piped it. That is how you end up with a script where some lines work and others do not. This inconsistency is the single biggest obstacle to tracing the cause.

Why error messages come out mangled

Once a CR is inside a value, the terminal reacts the moment you print it, because CR is the control character that means send the cursor back to the start of the line. If a CR lands in the middle of a message, the characters that follow overwrite the beginning of it. Nothing was deleted; it was painted over.

Suppose you meant to log deploy failed: version v2.4.1 not supported and the version value ends with a CR. The terminal draws as far as v2.4.1, sends the cursor back to column zero, and draws not supported on top. What remains is a short line with the front and back mixed together, and the original appears to be nowhere. Redirect it to a file and open it with cat -A and the full text is intact.

  • If a message looks like it was cut off in the middle, suspect a CR. It is often not a bug in the logging code
  • The same cause makes progress indicators misbehave, prompts overlap, and grep output look shorter than it is
  • Always confirm by capturing to a file. What the terminal draws is not the original
  • CI log viewers handle CR differently from one tool to the next, so the same log can look different locally and in the browser

Finding it - and the trap where grep returns 0

Four commands are enough. file tells you at a glance, cat -A tells you line by line, xxd tells you in bytes, and dos2unix -i tells you in counts. Make one file with mixed endings and run all four side by side.

$ printf 'first\r\nsecond\nthird\r\n' > mixed.txt

$ file mixed.txt
mixed.txt: ASCII text, with CRLF, LF line terminators

$ cat -A mixed.txt
first^M$
second$
third^M$

$ dos2unix -i mixed.txt lf.txt crlf.txt cr.txt
       2       1       0  no_bom    text    mixed.txt
       0       2       0  no_bom    text    lf.txt
       2       0       0  no_bom    text    crlf.txt
       0       0       2  no_bom    text    cr.txt

The three numbers from dos2unix -i are, left to right, the counts of CRLF, LF and lone CR. mixed.txt showing 2 1 0 matches how it was built. The fourth column is whether a BOM is present, and the fifth is whether the file was judged text or binary. To list only the files containing CRLF out of many, use -ic, which prints names alone.

But the most widely recommended check produces a false negative in this environment.

$ grep -c $'\r' mixed.txt
0

$ grep -Uc $'\r' mixed.txt
2

$ awk '/\r$/{n++} END{print n+0}' mixed.txt
0

$ awk -v BINMODE=3 '/\r$/{n++} END{print n+0}' mixed.txt
2

On a file with two CRLF lines, grep -c $'\r' returns 0. The GNU grep 3.0 here reads files in text mode and strips the trailing CR before matching. Add -U to force binary mode and it correctly reports 2. gawk behaves the same, so it needs -v BINMODE=3. On Linux there is no such preprocessing and the match works without -U, which means a check performed on Windows cannot be trusted. Leave that one letter out of a validation script and the validator will pass forever.

CommandWhat it tells youCaveat

Three ways to fix it, and what each one destroys

Three conversion methods are in common use. On an ordinary CRLF text file all three give the same result.

$ dos2unix -q mixed.txt
$ sed -i 's/\r$//' mixed.txt
$ tr -d '\r' < mixed.txt > out.txt

$ cat -A mixed.txt
first$
second$
third$

They diverge on files that are not ordinary. tr -d '\r' makes no distinction between a CR at a line end and a CR anywhere else. It deletes every 0x0D in the file. Take a log that prints progress by overwriting with CR and this is what happens.

$ printf 'progress: 10%%\r progress: 100%%\rdone\n' > prog.log
$ xxd prog.log
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

$ tr -d '\r' < prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 2520 7072  progress: 10% pr
00000010: 6f67 7265 7373 3a20 3130 3025 646f 6e65  ogress: 100%done
00000020: 0a                                       .

$ sed 's/\r$//' prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

The tr version has three stages of progress run together on one line and the original intent is gone. sed 's/\r$//' targets only a CR at the end of a line, so it left this file alone. But sed is not universal either. It can barely touch an old Mac lone-CR file, because such a file looks like a single line to Unix tools.

$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ sed 's/\r$//' cr.txt | xxd
00000000: 6865 6c6c 6f0d 776f 726c 64              hello.world

$ tr -d '\r' < cr.txt | xxd
00000000: 6865 6c6c 6f77 6f72 6c64                 helloworld

$ dos2unix -q -c mac cr.txt
$ xxd cr.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.

sed removed only the final CR and left the middle one. tr fused the two lines into helloworld. Only dos2unix -c mac turned the CRs into LFs and preserved both lines. Whether you lose data comes down to which command you picked.

With binary files the gap is starker. dos2unix skips them by default.

$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ dos2unix bin.dat
dos2unix: Binary symbol 0x00 found at line 1
dos2unix: Skipping binary file bin.dat
$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ tr -d '\r' < bin.dat | xxd
00000000: 504e 4789 000a 1a0a ffd8                 PNG.......

The file that went through tr lost a byte. Image or archive, it is unusable from that point, and there is no warning. This is why a script that combines find with tr across a whole repository is dangerous.

ToolCRLF at line endCR mid-lineLone-CR fileBinaryBOM
dos2unixConvertsPreservesConverts with -c macSkipped by defaultRemoved by default
sed -i 's/\r$//'ConvertsPreservesBarely touches itCan damage itLeft alone
tr -d '\r'ConvertsDeletes it tooFuses linesCorrupts itLeft alone

The rightmost column is an unexpected side effect worth confirming separately. Given no options, dos2unix also strips a BOM from the front of the file.

$ printf '\xef\xbb\xbfname,qty\r\nsalt,2\r\n' > bomcrlf.csv
$ xxd bomcrlf.csv
00000000: efbb bf6e 616d 652c 7174 790d 0a73 616c  ...name,qty..sal
00000010: 742c 320d 0a                             t,2..

$ dos2unix -q bomcrlf.csv
$ xxd bomcrlf.csv
00000000: 6e61 6d65 2c71 7479 0a73 616c 742c 320a  name,qty.salt,2.

The leading three bytes efbbbf are gone. For a file that needs its BOM, such as a CSV going into Excel, add -b to keep it. This is the classic case of fixing line endings and silently fixing something else at the same time.

The two points where git intervenes - core.autocrlf

Git can touch line endings at two points: on commit (working directory to index) and on checkout (index to working directory). The three values of core.autocrlf affect those two points differently. Build a throwaway repository and there is nothing left to be confused about.

Checkout first. Clone a repository whose content is committed as LF three times, with a different setting each time.

$ cd /tmp/demo/src
$ git ls-files --eol
i/lf    w/lf    attr/                   src.txt

$ git -c core.autocrlf=true  clone -q /tmp/demo/src /tmp/demo/w-true
$ git -c core.autocrlf=input clone -q /tmp/demo/src /tmp/demo/w-input
$ git -c core.autocrlf=false clone -q /tmp/demo/src /tmp/demo/w-false

$ xxd /tmp/demo/w-true/src.txt
00000000: 6c69 6e65 310d 0a6c 696e 6532 0d0a       line1..line2..
$ xxd /tmp/demo/w-input/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.
$ xxd /tmp/demo/w-false/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.

Only true rewrote the working file as CRLF. Now the commit side. Create a CRLF file in each of the three clones, commit it, and look at the index.

$ printf 'new1\r\nnew2\r\n' > added.txt
$ git add added.txt
$ git commit -qm add
$ git ls-files --eol -- added.txt

# core.autocrlf=true
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=input
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=false
i/crlf  w/crlf  attr/                   added.txt

true and input both stored LF in the index; false stored the CRLF as it was. In other words the difference between the first two is on checkout, not on commit. That table is the conclusion.

core.autocrlfOn commit (work → index)On checkout (index → work)Who it suits
trueStores CRLF as LFHands back LF as CRLFSomeone on Windows-only editors. The repository stays clean
inputStores CRLF as LFNo conversion. LF as-isSomeone on Windows working on Linux scripts
falseNo conversion. Exactly as writtenNo conversionA repository that manages endings purely with .gitattributes

There is also core.eol, whose values are lf, crlf and native, the default being native, which follows the platform convention. And setting core.safecrlf to true or warn makes git warn about, or refuse, a conversion that would not be reversible.

  • core.autocrlf is a per-person setting. Everyone who clones the repository may have a different value
  • So announcing a team-wide value is a policy that will break exactly once for every new joiner
  • The official documentation describes core.autocrlf=true as being the same as setting text=auto on all files and core.eol to crlf
  • Which means autocrlf is close to shorthand for .gitattributes. If so, write the real thing instead of the shorthand

Why .gitattributes is the better answer

The difference is one thing. core.autocrlf attaches to a person; .gitattributes attaches to a repository. The latter is committed and shipped along with the code, so the same rule applies regardless of a collaborator's configuration. That a new joiner gets the rule without configuring anything is the practical difference.

# .gitattributes
* text=auto

*.sh   text eol=lf
*.py   text eol=lf
*.yml  text eol=lf
*.yaml text eol=lf

*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf

*.png binary
*.jpg binary
*.pdf binary

The attributes mean this. Setting text normalises line endings to LF in the index on every check-in. text=auto lets git decide for itself whether a file is text or binary. eol=lf means to use the same endings as the index on checkout, and eol=crlf means to convert the working file to CRLF. binary is an alias for -text -diff, that is, do not convert anything.

There is an easy thing to miss here. * text=auto alone does not give you an LF working directory. The documentation states that when eol is unspecified and neither core.autocrlf nor core.eol is set, the default is eol=crlf on Windows and eol=lf everywhere else. Clone the repository fresh and that is exactly what you see.

$ git clone -q /tmp/demo/repo /tmp/demo/fresh
$ cd /tmp/demo/fresh
$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          .gitattributes
i/-text w/-text attr/text=auto          blob.bin
i/lf    w/lf    attr/text eol=lf        deploy.sh
i/lf    w/crlf  attr/text=auto          notes.md

$ xxd notes.md
00000000: 610d 0a62 0d0a                           a..b..
$ xxd deploy.sh
00000000: 2321 2f62 696e 2f62 6173 680a 6563 686f  #!/bin/bash.echo
00000010: 2068 690a                                 hi.

From the same repository, notes.md arrived as CRLF and deploy.sh as LF. The only difference is the single line *.sh text eol=lf. That is why files destined to run on Linux need an explicit eol=lf. Rely on text=auto alone and your shell scripts come back to life as CRLF in a Windows working tree.

The output format is worth learning too. git ls-files --eol shows three columns.

ColumnMeaningPossible values
i/Endings of the blob stored in the indexlf, crlf, mixed, -text (binary)
w/Endings of the file in the working directory nowThe same values. Differing from i/ can be normal
attr/Attributes currently applied to that pathtext=auto, text eol=lf, blank, and so on

.gitattributes does not fix the past

This is the section that will be needed most often. It is easy to think that adding .gitattributes ends the matter, but blobs committed before the rule existed stay exactly as they were. The rule only applies to future conversions.

Take a repository where a CRLF file was committed under core.autocrlf=false, add .gitattributes, and look at the state.

$ git ls-files --eol
i/crlf  w/crlf  attr/                   deploy.sh
i/lf    w/lf    attr/                   notes.md

$ printf '* text=auto\n*.sh text eol=lf\n*.bat text eol=crlf\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm "add gitattributes"

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text eol=lf        deploy.sh
i/lf    w/lf    attr/text=auto          notes.md

$ git check-attr text eol -- deploy.sh
deploy.sh: text: set
deploy.sh: eol: lf

The attr/ column carries the new rule correctly. check-attr answers eol: lf. And yet i/ still reads crlf. The rule is in force and the data is unchanged. Deploy this repository to a Linux server and the script still dies.

The more confusing case is a bare * text=auto. The documentation says of that value that a file is converted if it is text and was not already in Git with CRLF endings. So does editing the file and committing it again clean it up? Check, and no.

$ git ls-files --eol
i/crlf  w/crlf  attr/                   legacy.txt

$ printf '* text=auto\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm attrs

$ printf 'one\r\ntwo\r\nthree\r\n' > legacy.txt
$ git add legacy.txt
$ git commit -qm edit

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650d 0a74 776f 0d0a 7468 7265 650d  one..two..three.
00000010: 0a                                       .

Edited and re-committed, and the index blob is still CRLF. text=auto keeps treating a file that once went in as CRLF as an exception. Which means it will not sort itself out months after you added the rule.

Cleaning it up takes an explicit renormalisation, exactly the sequence the official documentation gives. Run it from a clean working tree.

$ git add --renormalize .
$ git status --short
M  legacy.txt
$ git commit -qm "normalize line endings"

$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650a 7477 6f0a 7468 7265 650a       one.two.three.

The index is LF now. But the w/ column still reads crlf, because renormalising changes the index and leaves the working file alone. To bring the working tree along, delete the file and check it out again.

$ rm deploy.sh
$ git checkout -- deploy.sh
$ git ls-files --eol
i/lf    w/lf    attr/text eol=lf        deploy.sh
  • A renormalisation commit changes no content yet looks as though nearly every line changed. Keep it as its own commit, not mixed with other work
  • Branches in flight will produce large merge conflicts. Merge what is ready first, then normalise
  • If unexpected files show up in git status, exclude them with -text and run it again
  • If an i/crlf survives the normalisation, that path is not covered by the rule. Check it with git check-attr

Which files should be CRLF

The advice to standardise on LF everywhere is common, and so is the objection that Windows-only files should be exempt. I checked how much of an exemption they actually need. I wrote a batch file with LF only, containing labels and goto, a for loop, an if else block, a call into a subroutine, and no newline on the final line, and ran it under cmd.exe.

C:\> cmd /c lf2.bat
item 1
item 2
item 3
yes
SUB

C:\> powershell -NoProfile -ExecutionPolicy Bypass -File lf.ps1
ps LF ok
block ok

All of it ran correctly. On cmd.exe under Windows 10 build 19045.6466 and on PowerShell 5.1, the LF batch file executed. The claim that it must be CRLF did not reproduce, at least in this configuration.

That is not an argument for keeping batch files as LF. The reasoning rests not on whether it worked but on the asymmetry of the risk. Keeping a Windows-only file as CRLF costs you nothing, because it will never run on Linux. Keeping a Linux-bound file as CRLF breaks it for certain. So the rule becomes simple. Decide by where it runs.

FileRecommendedWhy
.sh, .bash, .py, .pl, .rbLFThe shebang folds the CR into the interpreter path
Makefile, systemd units, cron filesLFA CR at the end of a value throws off paths and commands
.env, .conf, .yml, .jsonLFDepending on the parser, the CR ends up inside the value
SSH public keys, authorized_keysLFThe key string changes and authentication fails silently
.bat, .cmdCRLFLF worked here, but these are Windows-only so CRLF costs nothing
.ps1EitherLF ran fine. For these, the BOM is the more frequent problem
Images, archives, fontsDo not convertMark them binary in .gitattributes

Stopping it in the editor and in CI

Preventing it is cheaper than fixing it. There are three layers: once in the editor, once in the repository, once in the pipeline. The editor layer belongs to .editorconfig. Per the specification, end_of_line accepts lf, cr and crlf, and the values are case-insensitive.

# .editorconfig
root = true

[*]
end_of_line = lf
insert_final_newline = true
charset = utf-8
trim_trailing_whitespace = true

[*.{bat,cmd}]
end_of_line = crlf

[*.md]
trim_trailing_whitespace = false

The two files do not overlap in role. The first acts when the editor saves, the second when git commits and checks out. Keep both, and keep their extension lists aligned. When they disagree, the value on save differs from the value on commit and you get a change every time.

The last layer is the check. One line tells you whether any text file went into the index as CRLF.

$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
$ echo $?
1

# in a contaminated repository
$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
i/crlf  w/crlf  attr/                   added.txt
$ echo $?
0

Clean, it prints nothing and exits 1; dirty, it prints the list and exits 0. In a CI step, put ! in front to invert it so that finding something is a failure. This beats scanning files directly for three reasons. Binaries come out as i/-text and drop out on their own, files you deliberately allow as CRLF show up normalised as i/lf, and above all it avoids the grep text-mode trap seen earlier.

One more thing: mixed endings destroy code review before they destroy anything else, because identical content shows up as entirely changed.

$ diff a_lf.txt a_crlf.txt
1,3c1,3
< alpha
< beta
< gamma
---
> alpha
> beta
> gamma

$ diff --strip-trailing-cr a_lf.txt a_crlf.txt
$ echo $?
0

The visible characters are identical, yet all three lines are reported as different. A reviewer can no longer find the real change, and a few days of this leaves the whole repository mixed. --strip-trailing-cr is a stopgap for an urgent moment, not a solution.

Finally, it is worth knowing why some code is fine. Some language runtimes convert at the point of reading.

$ python nl.py
default  : 'ENV=prod\n'
newline='': 'ENV=prod\r\n'
binary   : b'ENV=prod\r\n'
split    : ['ENV', 'prod']
split raw: ['ENV', 'prod\r']

Opened in text mode, Python normalises line endings to a single \n by default. That is why Python code usually survives a CRLF file. Open the same file with newline="" or in binary mode and the CR comes through, and splitting that value gives you 'prod\r'. Which means two pieces of code can genuinely read the same file differently.

Line endings and the BOM are different problems

These two get discussed together, but they differ in cause, in location and in cure. Line endings sit at the end of every line; a BOM sits once at the very front of the file. The symptoms look alike only because both take the form of an invisible byte entering a value, not because they share a cause.

  • A line ending is 0x0D 0x0A; a UTF-8 BOM is 0xEF 0xBB 0xBF. No byte is shared
  • The tools differ too, except that dos2unix touches both by default, as confirmed in the previous section
  • Both produce a broken shebang. A BOM before the first line and a CR at the end of it each stop the interpreter from being found
  • Telling them apart takes one line, xxd FILE | head -1. Look for efbbbf at the front or 0d0a at a line end

The BOM side is covered separately in The Bug an Invisible Three Bytes Makes - Where the UTF-8 BOM Breaks Shells, JSON and CSV. Text appearing as boxes or question marks is yet another layer, and that one is in Locating Where Hangul Breaks - cp949, UTF-8, and the Two Kinds of Encoding Error. When all three overlap, peeling them off in the order encoding, then BOM, then line endings is faster.

In order - the short version

If you have a broken file right now the sequence is short. Confirm the kind with file, convert with dos2unix, run it again. That is five minutes. The problem is what comes after. If the same thing happens again next week, the thing to fix is not the file but the pipeline.

  1. Diagnose. file FILE and xxd FILE | head -1. Distinguish 0d0a at a line end from efbbbf at the front
  2. Convert. dos2unix FILE. Add -b when a BOM is needed, as in a CSV, and -c mac for old Mac files. Do not reach for tr -d '\r'
  3. Repository rule. * text=auto in .gitattributes, plus eol=lf per executable extension. eol=crlf for Windows-only files
  4. Clean the past. git add --renormalize . from a clean working tree, as its own commit. Skip this and the rule is decoration
  5. Editor. end_of_line = lf in .editorconfig. Align the extension list with .gitattributes
  6. Check. One line in CI: ! git ls-files --eol | grep -E '^i/(crlf|mixed)'

Step four matters most. Of everything verified by running it here, the fact that trips up real work most often is that adding the rule leaves the past untouched. Under * text=auto, editing that file and committing it again still left CRLF in the index. Renormalisation does not happen by itself.

Verified on Windows is not evidence. Three separate things in this article show why. Git Bash handles a CRLF shebang for you and runs the script, grep -c $'\r' returns 0 on a CRLF file, and command substitution strips the CR off the end of a value. All three hide the problem. Verify in the environment the code will actually be deployed to, or at minimum with a method that does not depend on the platform, such as git ls-files --eol.
