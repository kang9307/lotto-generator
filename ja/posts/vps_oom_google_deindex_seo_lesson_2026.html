月6ドルVPSの教訓 - OOM 503エラーが招いたGoogleのインデックス削除

When Out-of-Memory Meets SEO - A Low-Spec VPS Cautionary Tale

2026年6月10日 IT・技術

序論: 6ドルのサーバーが検索から消えた日

月6ドル。コーヒー1〜2杯分で借りた最小スペックのVPS上で、バイブコーディングでさっと作った株式スクリーナーが動いていました。最初の数週間は平和でした。検索にも少しずつ表示され始め、小さなサイトが居場所を見つけつつあるようでした。ところがある日、トラフィックが少し増えるとサイトが断続的に応答しなくなり、ブラウザに503 Service Unavailableが表示され始めます。数日後、Googleの検索結果からページが静かに姿を消しました。インデックス削除です。

本稿は、最近開発者コミュニティで話題になった運用者の体験談 — 低スペックVPSのメモリ不足(OOM)が503の連発を生み、それがGoogleのインデックス削除につながった事例 — を出発点に、なぜこんなことが起きるのかを運用とSEOの2軸で丁寧に解剖します。単に「サーバーを増強しろ」で終わる話ではありません。メモリ・スワップ・OOM killerがどう噛み合うのか、503が検索エンジンにとってなぜそれほど危険な合図なのか、そして同じ6ドルの予算でも事故を避ける設計と事故後の復旧法までを実務の教訓として整理します。小さなサイトほど、この仕組みを知っているかどうかが生存を分けます。

1. 何が起きたか - 事件のタイムライン

まず事件を時系列で再構成します。細部は異なり得ますが、低スペックVPSで繰り返し観察される典型的な崩壊パターンです。

  • 段階1 — リリース: 1 vCPU、1GB前後の最小スペックVPSにアプリを載せます。スワップは未設定、リソース上限も置いていません。
  • 段階2 — 潜伏: トラフィックが少ないうちは正常です。メモリは厳しくても破綻しないため、問題に気づきません。
  • 段階3 — 引き金: 検索表示や外部リンクで同時接続が増えると、アプリがリクエストごとにメモリを多く使い、RAMが上限に達します。
  • 段階4 — OOM: スワップもないためカーネルはメモリを追加できず、OOM killerが最も重いプロセス(多くはWebアプリ)を強制終了します。サーバーは生きていてもアプリは死にます。
  • 段階5 — 503連発: アプリが死んでいる間、リバースプロキシはバックエンドに接続できず503を返します。死と再起動が繰り返され、503が断続的に出続けます。
  • 段階6 — クローラの後退: Googlebotが訪れるたびに503に出くわし、クロール頻度を下げます。
  • 段階7 — インデックス削除: 503が数日以上続くと、Googleは当該URLをアクセス不可と判断してインデックスから削除します。

重要なのは、これが単一原因ではなく連鎖だという点です。メモリ不足というインフラの問題が503というHTTPの合図に翻訳され、その合図が検索エンジンの信頼判断につながります。どこか一つの輪を断つだけで、インデックス削除までは至りません。

2. メモリ不足の解剖 - RAM、スワップ、OOM killer

なぜアプリが「死ぬ」のかを理解するには、Linuxのメモリの扱い方を知る必要があります。資料を総合すると、Linuxの利用可能メモリは3層から成ります。

構成 役割 枯渇時
物理RAM 実際の高速メモリ。アクティブデータを保持 最初に圧迫
ページキャッシュ ファイルベースのデータキャッシュ 回収可能、先に解放
スワップ 非アクティブなページをディスクへ退避する緩衝 ここまで埋まるとOOM間近

スワップは安全網です。瞬間的なメモリ急増やバックグラウンド使用を吸収し、メモリリークや設定ミスに対応する時間を稼いでくれます。問題のVPSにスワップがなかったことが致命的だったのはそのためです。緩衝がまるごと欠けていたのです。

2.1 OOM killerはいつ、何を殺すか

OOM killerは、物理メモリとスワップが共に枯渇して割り当て要求を満たせないときにカーネルが発動する最後の防衛線です。メモリが完全にゼロになるまで待たず、要求を満たせないと判断すると先回りして作動します。対象選定は各プロセスのbadnessスコアで決まります。メモリ使用量、実行時間、権限、nice値、そしてoom_score_adj調整値を総合し、最も高いプロセスを終了させます。

もう一つのルールが「子優先の犠牲(sacrifice child)」です。親と子のプロセスでは子を先に殺し、重要な親を生かします。ワーカーを起動するWebサーバー構成で、メモリ消費の大きいワーカーが標的になる理由がここにあります。運用者は/proc/<pid>/oom_score_adj(-1000は絶対に殺さない、+1000は最初に殺す)で守りたいプロセスをある程度調整できます。

# OOM発生の痕跡を確認 (dmesg)
$ dmesg | grep -i -E "killed process|out of memory"
[12345.678] Out of memory: Killed process 813 (gunicorn) ...

# 現在のメモリ/スワップ状態
$ free -h
              total   used   free  shared  buff/cache  available
Mem:          957Mi  812Mi   72Mi    8Mi       72Mi        41Mi
Swap:            0B     0B     0B   <-- スワップなし: 緩衝が欠如

# 特定プロセスを保護 (例: ほぼ「殺さない」水準)
$ echo -900 > /proc/$(pgrep -o nginx)/oom_score_adj

上のfree -h出力でSwap: 0Bが見えたら、このサーバーはメモリ急増を吸収する緩衝が皆無という意味です。availableが数十MBまで落ちていれば、OOMは時間の問題です。

3. なぜ503はSEOに致命的なのか

ここからインフラから検索へ移ります。興味深いことに、503そのものは悪い応答ではありません。Googleにとって503は「今は無理だから後で来て」という一時的な合図であり、正しく使えばSEOに害はありません。Googlebotは503に出くわしてもページが消えたと断定せず、時間を置いて再びクロールしようとします。合理的な範囲で忍耐強く設計されています。

問題は継続時間と反復です。Googleのサポートコミュニティのガイドを総合すると、おおむね次の閾値が挙げられます。

  • 24時間以内: 一般に安全。10〜15分単位の断続的な503は「長期的」とはみなされません。
  • 1〜7日: 監視していれば危険は最小化されますが、クロール頻度は下がり始めます。
  • 7日超: インデックス削除の危険域。Googleが当該URLを事実上恒久的にアクセス不可とみなし得ます。
503は1日の風邪なら問題ないが、数週間引きずる慢性疾患になると、Googleはそのサイトを「信頼できない場所」と学習する。

とりわけ事例のように不規則に繰り返される503は、単なるメンテナンスより悪質です。クローラにとっては「このサイトはいつ生きているか分からない」という継続的な不安定として読まれ、これはクロール圧力を長期的に下げるよう学習させる最速の道です。その結果は、発見の遅延、更新の遅延、サイト全体の再クロール周期の鈍化へと波及します。

3.1 5xxがインデックスに与える直接的効果

Googleにとって5xxページはそもそもインデックス不可です。検索結果に現れず、頻繁な5xxはサイトが不安定だという合図になり、失敗したリクエストにクロールバジェットが浪費されます。Googlebotは5xxを多く見るとサイトを圧迫しないようクロール頻度を下げます。小さなサイトほどクロールバジェットが厳しいので、503に予算を食われることは正常なページのインデックス機会を失うことと同じです。

4. 決定的な一手 - Retry-Afterヘッダー

同じ503でも、Retry-Afterヘッダーの有無が運命を分けます。サーバーは503応答にRetry-Afterで「いつ準備できるか」を秒数やHTTP日付で伝えられます。これがあればGooglebotはページを消失とみなさず、指定時刻に合わせてクロールを予約し直します。

# 意図したメンテナンス時の正しい503応答 (例: 2分後に再試行を要求)
HTTP/1.1 503 Service Unavailable
Retry-After: 120
Content-Type: text/html

# nginxでメンテページを503 + Retry-Afterで返す例
location / {
    return 503;
}
error_page 503 @maintenance;
location @maintenance {
    add_header Retry-After 120 always;
    try_files /maintenance.html =503;
}

ただし注意すべきは、事例で発生した503が意図したメンテナンスではなくOOMによる異常な503だったことです。この場合、リバースプロキシがRetry-Afterを付ける余裕すらなくバックエンドが死んでいることが多いです。Retry-Afterは計画的メンテナンスには優れた安全装置ですが、根本原因のOOMを解決しない限り万能薬ではありません。

5. 予防策 - 6ドルの予算を守りつつ503をなくす

核心の問いは「サーバーを増強しろ」ではなく「同じ予算でどう安定させるか」です。コスト順に整理します。

5.1 まずはスワップ — 最も安く即効

スワップがないなら、まず無料でできるのがスワップ追加です。1GB RAMなら1〜2GBのスワップが瞬間的な急増を吸収し、OOM killerの発動を遅らせます。ディスクベースで遅いものの、「アプリが死ぬ」より「少し遅い」方がはるかにましです。

# 2GBのスワップファイルを作成・有効化
$ sudo fallocate -l 2G /swapfile
$ sudo chmod 600 /swapfile
$ sudo mkswap /swapfile && sudo swapon /swapfile

# Webワークロード向けにスワップ傾向を調整 (RAM優先、スワップは後)
$ sudo sysctl vm.swappiness=10

ちなみにswappinessはスワップをどれだけ積極的に使うかを決めますが、VPSのWebワークロードでは10〜20程度が推奨されます。RAMを優先し、スワップは後で動員してディスクI/Oの負担を減らします。

5.2 アプリのメモリ上限とワーカー数の制限

二つ目は、アプリがRAMを超えないよう上限を明示することです。1GBのサーバーでワーカーを無制限に起動すると、同時リクエストが増えたときメモリが爆発します。ワーカー数をRAMに合わせて保守的に固定し、コンテナならメモリ上限と再起動ポリシーを置きます。

  • ワーカー数の固定: 1GB RAMならワーカー2〜3個のように、メモリ予算内で上限を設けます。
  • プロセスごとのメモリ上限: リークが累積する前にワーカーを定期的に再起動します(max-requestsなど)。
  • cgroup/コンテナ上限: 一つのプロセスの暴走がシステム全体を引き下げないよう隔離します。

5.3 ヘルスチェックと自動再起動

アプリが死んだとき自力で復活させることが、503の継続時間を縮める鍵です。プロセス管理ツール(systemd、supervisorなど)に自動再起動を設定し、リバースプロキシにヘルスチェックを置いて死んだバックエンドにトラフィックを送らないようにします。死と再起動が速くなるほど、クローラが503に出くわす確率が下がります。

5.4 CDNと静的化 — オリジン負荷を80〜95%吸収

読み取り中心のサイトならCDNキャッシュが最も効果的な盾です。資料によればCDNは読み取りトラフィックの80〜95%まで吸収し、本来なら503を誘発したオリジンサーバーの圧力を大きく減らします。30〜60秒の短いTTLだけでも、トラフィック急増時のバックエンド負荷が劇的に下がります。静的化できるページを事前にビルドしておけば、動的サーバーが揺らいでもCDNが「最後の正常バージョン」を返し続けます。応答性能を引き上げる広い文脈は、UUID主キーとSQLiteの性能のようなデータ層最適化ともつながります。

5.5 503の代わりにグレースフルデグラデーション

最も成熟した解は失敗を優雅に下げる(グレースフルデグラデーション)設計です。動的アプリが過負荷で応答できないとき、503を返す代わりにキャッシュ済みの静的バージョンを読み取り専用で返します。CI/CDが失敗したりオリジンストレージに障害が出ても、CDNが最後の正常スナップショットを生かして「可用性の緩衝」を提供します。ユーザーには少し古いページが見えても、クローラには200が返ります。503を200に変えること — これがインデックス削除を防ぐ最も本質的な転換です。こうした安定運用の考え方は、SREにおけるAIと信頼性運用の原則とも通じます。

6. 復旧方法 - インデックス削除されたサイトを蘇らせる

すでにインデックス削除が起きていたら? 順序が重要です。原因を先に直し、その後Googleに知らせるのです。逆にすると再クロール時にまた503に出くわし、信頼がさらに削られます。

  1. 根本原因の解決: 上の予防策(スワップ・ワーカー制限・ヘルスチェック・CDN)で503をまず止めます。サーバーが安定して200を返すか確認します。
  2. エラークラスタの確認: Search Consoleのインデックス登録レポートで「サーバーエラー(5xx)」にまとめられたURLクラスタを探します。
  3. 主要ページのインデックス登録リクエスト: URL検査ツールで重要なページから登録をリクエストし、再クロールを前倒しします。
  4. 修正の検証: エラークラスタで「修正を検証」を押し、Googleに再クロール・再検証を促します。
  5. 監視: クロールの統計情報で5xx率と応答時間が正常化するか見守ります。検証は通常数日から約2週間、長ければそれ以上かかり、結果はメールで通知されます。

回復は可能ですが即座ではありません。サイトの規模・人気・503が続いた期間によって、再クロールが戻る速度は変わります。長く放置するほど回復も遅いので、異常を早く捉える監視そのものが最善の保険です。

7. 小規模サイト運用者への教訓

この事例が小さなサイトの運用者に残す教訓を整理します。

  • 低スペックは罪ではないが、無防備は罪だ。6ドルVPSもスワップ・ワーカー制限・ヘルスチェックさえあれば十分耐えます。問題はスペックではなく緩衝の欠如でした。
  • インフラ障害はSEO障害に翻訳される。メモリ不足は開発者だけの問題ではありません。503を経て検索可視性へ、ひいてはトラフィックと収益へ直結します。
  • 200を守ることがすべてのSEOの土台だ。コンテンツ・キーワード・被リンク以前に、クローラが訪れたときサイトが生きていなければなりません。グレースフルデグラデーションで503を200に変える設計が最も本質的です。
  • 監視なき運用は目を閉じた運転だ。Search Consoleの通知と簡単な稼働監視があれば、インデックス削除の前に手を打てました。
  • バイブコーディングの死角は運用だ。AIで機能を速く作ることと、それを安定して運用することは別の能力です。データ層の耐久性設計はPostgreSQLによる耐久ワークフローのように別の検討を要します。

結論: 503を200に変える設計がSEOの始まり

月6ドルVPSのインデックス削除事件は、華やかなハッキングやアルゴリズムのペナルティではなく、メモリ1コマ足りずに始まった連鎖の結果でした。RAMが埋まり、スワップがなくOOM killerがアプリを殺し、死んだアプリが503を吐き、繰り返す503がクローラの信頼を削って、ついにインデックスから消えました。幸い、この連鎖はどの輪でも断ち切れます。

最後に、今日すぐ点検すべき3つで締めます。

  1. 今すぐfree -hでスワップを確認せよ。Swap: 0Bなら、最も安く即効の安全網が欠けています。まずスワップを追加しましょう。
  2. 過負荷時に何を返すか決めよ。503を吐くか、キャッシュ済みの静的ページ(200)を返すかを事前に設計しましょう。CDNと静的フォールバックがインデックス削除を防ぐ核心の盾です。
  3. Search Consoleを常時オンに。5xxエラー通知とクロールの統計情報は無料の早期警報です。消えた後に復旧するより、消える前に防ぐ方が比べものにならないほど安いです。
