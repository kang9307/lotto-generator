Cate - 无限画布编程 IDE，抛弃标签页与窗口的工作空间 2026

把编辑器、终端、浏览器与 AI 智能体铺展到同一平面的空间型 IDE 实验

2026年6月14日 IT/技术

引言：为什么此刻重新追问「IDE 该长什么样」

过去二十多年，代码编辑器的外观稳定得惊人。左侧文件树，中间用标签页归拢的编辑器，下方终端，右侧侧边面板。无论是 VS Code 还是 JetBrains 系列，这种在矩形窗口里堆叠矩形面板的网格结构，几乎成了事实标准。然而 2026 年 6 月，一个登上 GeekNews（news.hada.io）榜首的项目，正面动摇了这个前提。它叫 Cate：一款抛开标签页与窗口的隔断，把编辑器、终端、浏览器、文档与 AI 智能体自由排布在可无限缩放画布上的桌面 IDE。

本文以 Cate 这一具体工具为出发点，从开发工具与 UX 的角度，从容地审视一个更大的问题：无限画布能否成为编程的工作空间？我们会依次梳理 Cate 是什么、如何构建，既有 IDE 的标签页与窗口模型有哪些局限，这一发想在贯穿 Figma、tldraw、Muse 的空间 UI 趋势中处于何处，以及空间记忆（spatial memory）如何与生产力相连。最后再均衡地谈谈学习曲线、性能等现实局限，并诚实地问一句：它到底适合谁。

1. Cate 是什么 - 一句话定义

用一句话概括，Cate 就是 「一款把项目所有工具铺展在同一张无限画布上的桌面 IDE」。据官方仓库（0-AI-UG/cate）的说明，Cate 自我介绍为「把编辑器、终端、浏览器、文档与 AI 智能体铺展到自由空间，而非堆叠窗口与标签页」。它的名字本身可读作 Canvas Terminal Editor 的缩写，把核心身份直接亮在表面。

使用方式很直观。打开一个文件夹，它就成为一个工作空间（workspace）。在画布上右键添加面板，用命令面板（Cmd+K）调出工具，把面板拖到停靠区归拢成标签或分屏。面板可以自由悬浮，可以停靠为标签与分屏，也可以拆分到独立的操作系统窗口。再次打开该文件夹时，Cate 会还原整套布局。也就是说，「项目 = 空间」这个等式，就是工作的基本单位。

2. 技术栈与面板构成 - 用什么造出来的

Cate 立足于人们熟悉的 Web 技术。官方文档给出的技术栈如下。

  • 运行时：Electron 41 ＋ React 18 前端。虽是桌面应用，内部却是 Web 渲染。
  • 编辑器：Monaco 0.52（VS Code 的编辑器引擎），提供语法高亮、多光标、diff 与 Markdown 预览。
  • 终端：xterm.js 5.5 ＋ node-pty 1.0，把原生 shell 直接开在画布之中。
  • 样式与状态：Tailwind 3.4、Zustand 5；构建使用 electron-vite、electron-builder、electron-updater。

面板种类也很丰富。除了代码编辑器与终端，还有用于 PDF、DOCX、图片的文档面板，浏览器预览，以及识别 Git 的文件树（暂存、分支、工作树、历史、内联 diff），都作为画布上的面板来处理。许可证为 MIT，提供面向 macOS（DMG、ZIP）、Windows（NSIS、ZIP）、Linux（AppImage、DEB、tar.gz）的预编译版本。可见，发想虽属实验性，实现却建立在一批经过验证的组件之上。

3. 既有 IDE 的局限 - 标签页、窗口与面板这道隔断

要理解 Cate 的前提，先得说清既有 IDE 做不到什么。传统 IDE 的基本隐喻是「堆叠」。标签页把多个文件堆在同一处，一次只显示一个；面板把屏幕切成矩形，往每块里塞进一个工具。这套模型适合深看一样东西，但在需要同时铺开多个上下文、加以比较与探索时，就会制造摩擦。

标签页很会回答「我现在在看什么」，却让你忘掉「它旁边曾经有什么」。隔断在帮助专注的同时，也切断了上下文。

具体的痛点是这样的：要在多处比较同一个文件，就得反复分屏，分得越多每格就越窄；要同时看终端、预览与文档，就得开多个窗口、在操作系统层面排列，而这套摆放往往会随会话结束而消失。更要紧的是，昨天工作时「那套摆放」，今天很难在脑中重新唤起。标签页的顺序与面板的位置极易挥发，几乎不给人的空间记忆留下可抓的锚点。

4. 无限画布这一替代方案 - 从堆叠到铺展

Cate 给出的答案，是把「堆叠」换成「铺展」。它不再把屏幕切成矩形，而是在一个没有边际的平面上按坐标摆放面板。编辑器右边放终端，上方放浏览器预览，一角放 AI 智能体，靠缩放与平移在它们之间穿梭。拉远看，整个项目的地形一览无余；凑近看，又能聚焦于单个文件的细节。

这种方式的核心好处是上下文的共存。想比较的两个文件不必硬塞进狭窄的分屏，可以并排铺开；调试时把日志（终端）、代码（编辑器）、结果（浏览器）放在同一视野里，只需移动视线即可。更妙的是，Cate 会按项目保存并还原这套摆放，于是「昨天的工作景象」原样留存。值得注意的是，Cate 并不试图取代操作系统的窗口管理器，而是只在项目范围内组织空间，划出一条不与操作系统窗口管理冲突的界线。

5. 空间 UI 趋势中的 Cate - Figma、tldraw、Muse 一脉

无限画布并非 Cate 首创。过去几年，在设计、思考与协作工具领域，「无限画布」已自成一个品类。Muse 团队做的介绍站点（infinitecanvas.tools）称它为「一种新的基础性文档类型」，这里的「无限」指的不是广阔的空间，而是「开放与可能性」。

工具 领域 无限画布的用途
Figma / FigJam 设计、白板 多人在同一平面上铺开设计与创意
tldraw 开源 SDK 把无限画布嵌入产品的 React 工具包
Muse 空间型思考与笔记 在 iPad、Mac 上以空间方式排布思考的画布
Cate 编程 IDE 把编辑器、终端、浏览器与 AI 放到同一平面

Cate 的新意不在无限画布本身，而在于它把这个隐喻带进了最保守的领域——编程。它把设计师与产品人率先接受的空间型工作方式，应用到一个有着活终端、真编辑器、还跑着 AI 智能体的开发环境里。这与「IDE 近二十年停滞不前」的观察相互呼应，可看作是重新想象工具形态这一更大实验的一个实例。

6. 集成 AI 智能体的意义 - 人与智能体同处一个平面

Cate 最具时代感的部分，是 AI 智能体成了画布的一等公民。据官方介绍，Cate 内置了一个编程智能体（Pi），并支持 Anthropic、OpenAI、GitHub Copilot、Gemini、OpenRouter、Groq、Mistral、DeepSeek 等多家提供方。重要的不是「用哪个模型」，而是「智能体在哪里」。

在传统 IDE 里，AI 通常被关在侧边面板的聊天框中。智能体触碰的文件、运行的终端、拉起的预览，都散落在不同的格子里，于是人不得不在聊天与代码之间不断往返。Cate 拆掉这道隔断，把智能体面板放在与它所操作的文件、终端、浏览器同一个空间里。智能体在看什么、在改什么，都收进同一片视野。

这一设计连接着一个更大的议题——「AI 智能体的 UI 问题」。当智能体已成为编程循环的一部分，我们或许仍把它硬塞进为人设计的矩形聊天框里。空间型工作空间通过让人的工具与智能体的工作在同一平面共享上下文，为这个问题给出了一种答案。关于以智能体为中心的开发，更广的脉络见Claude Code 的动态工作流与 harness。

7. 空间记忆与生产力 - 用位置去记忆

无限画布拥护论的核心，是空间记忆（spatial memory）这一概念。人对物体在物理空间中的位置记得惊人地好。厨房哪个抽屉里放着剪刀、便签贴在书桌哪个角，我们不假思索就能想起。这种能力在进化上十分古老，它对空间布局的把握，远强于对抽象列表的把握。

无限画布 IDE 的假设是：把工具与文件固定在空间中，就能把这种记忆能力也借给编程。如果用位置去记上下文——「认证逻辑在画布左上，支付流程在右下，日志终端在中间」——那么翻看标签列表去找文件的认知成本就会下降。在调试这类需要同时抓住多个上下文的探索式工作中，好处尤为突出。

不过这里需要一个平衡的砝码。空间记忆只有在布局稳定时才奏效。位置若频繁变动，记忆的锚点就会动摇，反而要四处去找「我放哪儿了」。也就是说，无限画布的生产力，并非来自自由摆放本身，而来自使用者营造有意义的布局、并将其稳定维持的自律。

8. 优点小结 - 哪些地方变好了

把以上讨论压缩为优点，大致如下。

  • 上下文共存：把多个文件与工具并排铺在同一平面，而非塞进狭窄的分屏。
  • 布局持久化：按项目保存并还原布局，「昨天的工作景象」原样留存。
  • 善用空间记忆：用工具的位置记上下文，降低探索式工作的认知成本。
  • 工具与 AI 同居：智能体与其操作对象处于同一空间，减少上下文割裂。
  • 灵活停靠：面板可在自由摆放、标签、分屏与独立窗口之间随意切换。

9. 局限与批评 - 自由的代价

为求均衡，明确摆出另一面。无限画布并非免费午餐，发布之初的讨论中也提出了诸多担忧。

  • 缺乏结构＝认知过载：能自由摆放，也就意味着可能变乱。一位用户表示「没有结构，最终每张画布都会变成一团糟」，并把它比作凌乱的 Miro 白板和臃肿的浏览器标签页。
  • 学习曲线：对习惯了标签页与窗口的手与脑而言，坐标与缩放是新习惯，可能与仅用键盘快速移动的工作流相冲突。
  • 性能与稳定性：早期版本报告过窗口操作响应迟滞、拖拽行为不一致、光标异常等缺陷。打开的面板越多，渲染负担也越重。
  • 重新实现之争：也有批评问道「何必重造终端、编辑器，直接拉起原生应用不行吗」，或认为「不如用一个像样的平铺式窗口管理器」。
  • 缺少远程与无头：对远程、无头运行，大画布内的导航，乃至终端重命名等实用功能的需求接连出现。

这些批评的共同根源只有一个：自由即责任。隔断原本强制施加的整理，如今要由使用者自己来做，于是工具能在多大程度上支撑良好的整理习惯，便决定了成败。

10. 适合谁 - 契合与不契合

那么，像 Cate 这样的无限画布 IDE 究竟为谁而设？工具的价值，在很大程度上取决于工作的类型。

维度 契合的情形 不太契合的情形
工作性质 在众多服务与仓库间穿梭的探索式工作 深度专注于单一文件的工作
思考方式 以空间方式思考、记得布局的人 以列表、键盘为中心快速移动的人
环境 本地桌面，偏好大屏或一个无限平面 以远程、无头、SSH 为主的环境

简言之，Cate 与其说是「面向所有人的下一代 IDE」，不如说是一款强烈契合特定思考方式与工作类型的工具。对于那些同时铺开多个上下文、用视线在其间穿梭工作的人，对于想把 AI 智能体、代码与预览放进同一视野的人，它能带来一种解放感。反过来，对于沉浸于单个文件、或仅凭键盘飞快穿梭的人，它反倒可能成为摩擦。

11. 更大的图景 - IDE 重新开始流动

Cate 的真正意义，不在于它会不会马上取代 VS Code。更重要的信号是这样一个事实本身：停滞近二十年的 IDE 形态，重新成了实验的对象。随着 AI 智能体进入开发循环，「编程」这一行为的构成发生了变化，工作空间的形态也随之被重新审视。

这股潮流不止 Cate 一家。打出为智能体而设的「指挥塔（mission control）」旗号的工具、主打多智能体画布的工具等，发想相近的项目正同时涌现。可以说，整个工具生态正处在为「AI 已成为其中一员的工作」摸索新 UI 的阶段。前端与构建工具的整合脉络见VoidZero 加入 Cloudflare 与 Vite，以智能体为中心的框架脉络见Angular v22 的 AI 智能体流程。

12. 结论 ＋ 可以一试的 3 件事

Cate 是对「抛开标签页与窗口之后会看见什么」这一问题给出的具体而勇敢的一种答案。它把编辑器、终端、浏览器与 AI 智能体铺展在无限画布上，试图把人的空间记忆借给编程。它的长处在于上下文共存、布局持久化，以及工具与 AI 的同居；短处则在于缺乏结构带来的认知过载、学习曲线，以及早期的性能。哪一面更突出，取决于你的工作类型与整理习惯。

若想亲自衡量，给三点建议。

  1. 从一个小项目开始。在一次铺开多个仓库之前，先在单个项目里把编辑器、终端、预览与智能体放到同一画布上，亲身感受空间记忆是否真的会扎根。
  2. 定下有意义的固定布局。无限画布的生产力源自稳定的布局，而非自由本身。先为「什么放在哪里」立下自己的规则，才是关键。
  3. 以工作而非工具来判断。用「我的探索式工作是否真的更快了」作标准，而不是「它酷不酷」。无限画布不是为所有人，而是为某种工作方式而设。
