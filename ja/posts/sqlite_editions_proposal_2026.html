SQLiteにもRust流エディションが必要だ - 安全なデフォルト提案

Rust Editions for SQLite - 古いコードを壊さずに安全なデフォルトへオプトインする方法

2026年7月17日 開発・インフラ

序論: なぜ今SQLiteのデフォルトを語るべきか

2026年7月時点で、SQLiteは世界で最も多くデプロイされているデータベースエンジンだろう。ブラウザ、モバイルアプリ、デスクトップソフト、組み込み機器の中に静かに埋め込まれている。しかしこの成功の根本理由 - 徹底した後方互換性 - が同時に足かせになっている。SQLiteは30年近く積み重なったアプリケーションを絶対に壊さないという約束を守り続け、その代償として今の基準では安全でも速くもないデフォルトをそのまま引きずっている。

最近hada.io(GeekNews)で話題になったmort.coffeeの記事「SQLite should have (Rust-style) editions」は、この問題を正確に突いている。筆者は実務で遭遇したバグ - 文字列'1'が整数列にそのまま書き込まれていた事故、外部キーが強制されず参照整合性が崩れた事例、同時書き込み時にアプリケーションがそのまま落ちるSQLITE_BUSY - を根拠に、Rustの「エディション(edition)」のような仕組みをSQLiteに導入すべきだと提案する。本稿はその提案をそのまま伝えるのではなく、なぜ後方互換性がソフトウェア進化の普遍的な障害なのか、Rustのエディションが実際にどうこの問題を解決するのか、そしてその解法をSQLiteという全く異なる種類のソフトウェアへ移植する際に何が本当に難しいのかを、直接掘り下げる。

1. 後方互換性という普遍的な問題

1.1 ソフトウェアは老いる、しかし変えられない

成熟したソフトウェアはすべて同じジレンマに直面する。設計当初に下した判断が時間とともに誤りだったと分かっても、すでにその判断に依存して動くコードが世に広まっており手を出せない。Cのヌル終端文字列、PHPの緩い比較演算子、JavaScriptの暗黙的型変換はすべて同じ系譜にある。問題と分かっていても直せない理由は単純だ。デフォルトを変えた瞬間、その上に乗った無数のアプリケーションが予告なく壊れるからだ。

1.2 SQLiteが特に難しい理由

SQLiteはこのジレンマを他のソフトウェアより極端な形で抱えている。第一に、SQLiteはサーバーではなくアプリケーションにリンクされるライブラリであり、同時にファイルフォーマットでもある。あるデータベースファイルを作った時点のアプリケーションと、10年後にそのファイルを開くアプリケーションは、まったく異なるバージョンのSQLiteを使っている可能性がある。第二に、SQLite公式プロジェクト自体が「長期サポート(long-term support)」を中核的な設計目標として明示し、ファイルフォーマットの超長寿命を最優先の価値としている。この二つの特性のため、SQLiteでデフォルトを変える決断は一般的なアプリケーションライブラリよりはるかに重い。

2. Rustのエディション機構を分解する

2.1 エディションが変えるものと変えないもの

Rustは1.0リリース時に「1.xでコンパイルされるコードは以後どの1.yでもコンパイルされる」という安定性の約束をした。言語が進化するにつれこの約束と衝突する改善が積み重なると、RustチームはCargo.tomlのeditionフィールド(2015、2018、2021、2024)によるクレート単位のオプトイン機構を導入した。核心の保証はこうだ。あるエディションで一度コンパイルされたコードは、そのエディションの中で永遠にコンパイルされ続ける。既存クレートは開発者が明示的にeditionフィールドを引き上げるまで自動で新ルールを適用されない。移行負担を減らすためcargo fix --editionが機械的に処理可能な変更の大部分を自動適用する。

2.2 同じバイナリの中でエディションが混在できる理由

Rustのエディション設計で最も精巧な部分はエディション間の相互運用性だ。2015エディションで書かれたクレートが2024エディションのクレートに依存することも、その逆も可能だ。これが可能な理由は、エディションの違いがコンパイル時のソース解析・文法解釈にのみ影響し、コンパイルが終わった成果物にはエディションの痕跡が残らないためだ。言い換えれば、エディションはソースコードの読み方についての合意にすぎず、実行時の意味論やバイナリ形式を変えるものではない。この狭く明確なスコープのおかげで、「古いコードと新しいコードが一つのプロジェクトの中で共存する」ことが原理的に保証される。

3. SQLiteの問題あるデフォルト

3.1 緩い型 - 型アフィニティとSTRICTテーブル

SQLiteは列に宣言された型を強制しない。代わりにTEXT、NUMERIC、INTEGER、REAL、BLOBという5つの「型アフィニティ(affinity)」という概念を使う。これは推奨される保存形式にすぎない。INTEGERと宣言された列であっても、無損失変換が不可能なら文字列がそのまま保存される。これは実務で実際に、整数列に文字列'1'と'0'が混在する事故につながる。SQLite 3.37.0(2021-11-27)からはCREATE TABLE ... STRICTでテーブル単位の厳格な型検査を有効にできる。STRICTテーブルはすべての列にINT、INTEGER、REAL、TEXT、BLOB、ANYのいずれかの型指定を要求し、無損失変換ができなければSQLITE_CONSTRAINT_DATATYPEエラーを出す。問題は、これが新規テーブルにのみ選択的に適用される機能だという点だ。既存テーブル、そして何より、この機能の存在を知らない大多数の開発者にとっては、今も緩いデフォルトのままだ。

3.2 foreign_keysが既定でOFF

SQLiteは長年、外部キー構文を解析するだけで強制していなかった。後に実際の強制機能が追加された際、これをデフォルトで有効にすると、以前から緩い参照整合性に依存してきたアプリケーションが見たことのないエラーコードを受け取り壊れる危険があった。そのためPRAGMA foreign_keysは今も既定でOFFであり、これは接続単位の設定なので接続のたびに再度有効化しなければならない。この状態では、親行が削除されても子行が孤児として残り、SQLiteのROWID再利用アルゴリズムと重なると、削除されたユーザーの投稿が後に再利用されたIDを持つ新規ユーザーへ静かに再割り当てされるという、静かなデータ破損にまでつながりうる。

3.3 WALではなくロールバックジャーナル、そしてSQLITE_BUSY

SQLiteのデフォルトの原子的コミット方式は伝統的なロールバックジャーナルだ。後に導入されたWAL(Write-Ahead Logging)モードはPRAGMA journal_mode = WALでオプトインする必要があり、読み書きをはるかによく並行実行させて性能を引き上げる。しかしWALはネットワークファイルシステムでは動作せず、追加の-wal・-shmファイルが付くという制約があるため、デフォルトとして強制されなかった。同時書き込みの状況では、複数の書き込みが集中すると即座にSQLITE_BUSYエラーが返る。PRAGMA busy_timeoutで一定時間再試行させて緩和できるが、ロックエスカレーションの局面ではこれも完全な解決策ではないという指摘が開発者コミュニティで根強く出ている。

4. エディション方式がSQLiteに合う理由

mort.coffeeの提案はシンプルで洗練されている。PRAGMA edition = 2026;のような一行で、その時点の「推奨デフォルトの束」を一度にオプトインしようというものだ。この束にはforeign_keys = ON、合理的なbusy_timeout、journal_mode = WAL、そしてSTRICTテーブルを標準とする変更が含まれうる。この方式の利点は明確だ。既存アプリケーションはエディションを指定しない限り古い挙動をそのまま維持するため、何も壊れない。一方、新規プロジェクトや移行を負担できるチームは、一行で複数の安全装置を一度に有効化できる。個々のPRAGMAを一つずつ覚えて有効化しなければならない今の方式より、「安全なデフォルトの集合」を標準化された名前で呼べること自体が、認知的負担を大きく減らす。

5. 難題 - 組み込み・超互換性の哲学との衝突

5.1 設定のスコープがばらばらだ

Rustのエディションはクレートという明確なコンパイル単位一つに紐づく。しかしSQLiteの安全関連設定はスコープがばらばらだ。foreign_keysは接続単位、journal_modeは事実上データベースファイル単位、STRICTはテーブル単位だ。hada.ioの議論でも指摘された通り、統合PRAGMAをファイル単位に置くか接続単位に置くかをまず決めねばならず、設計を誤ると古いバージョンのライブラリが新しいエディションフラグの付いたファイルを開いた際に誤動作したりファイルを破損させたりする危険が生じる。

5.2 ファイルの可搬性と超互換性哲学の衝突

SQLiteのデータベースファイルは生まれつき、システムやアプリケーションのバージョンを跨いで移動する。これはRustのクレートがコンパイル時点で一度固定されるのとは根本的に異なる。ファイルにエディション情報を刻み込んだ瞬間、そのファイルを開けるSQLiteバージョンの下限が生まれる。古い組み込み機器やレガシーシステムに埋め込まれ数十年生き続けねばならないファイルフォーマットにこのような下限を設けることは、SQLiteがこれまで守ってきた超互換性の原則と正面からぶつかる。

5.3 テストマトリクスと組み合わせ爆発

エディションが複数存在し、各エディションが複数の機能を束ねるなら、SQLiteのコア開発者は事実上「エディション×プラットフォーム×コンパイルオプション」の組み合わせ全体を検証しなければならない。Rustはコンパイラ一つが標準を握っていたためこの負担に耐えられたが、SQLiteは数多くのバインディング(Python、Node.js、各種モバイルSDK)を通じて使われるため、エディション導入がそのバインディングエコシステム全体に波及するテスト・文書化負担を生む。

6. 他の言語・DBのバージョニング戦略との比較

6.1 Pythonの__future__ - 段階的義務化

Pythonはfrom __future__ import 機能構文で将来の言語機能をモジュール単位でオプトインさせ、定められた「義務化リリース」の時点からその機能がデフォルトになるという段階的移行モデルを長く使ってきた。これはRustのエディションのようにオプトインだが、結局ある時点以降は強制的にデフォルトになるという点で、SQLiteのように永遠に古い挙動を保証する方式とは性質が異なる。

6.2 JavaScriptの"use strict"

ES5はスクリプトや関数の先頭に"use strict"を宣言するだけで、より厳格な意味論をオプトインできるようにした。既存のES3コードはこの指示文がなければ全く影響を受けない。スコープがファイル・関数単位で明確という点でRustのエディションに似ているが、バージョンという概念なしに「緩いモード対厳格モード」という二分法一つしか存在しない点でより単純だ。

6.3 MySQLが実際にデフォルトを変えた事例

すべてのDBがSQLiteのようなオプトイン路線を選んだわけではない。MySQLは5.7.5(2015年)からSTRICT_TRANS_TABLESをsql_modeのデフォルトに含め、誤った値を自動型変換したり黙って切り捨てたりする代わりにエラーを出すよう既定動作そのものを変えた。これは強制移行路線だ。新規インストールのMySQLはより安全になったが、以前の緩い挙動に依存してきたアプリケーションはアップグレード時点で実際に壊れ、多くの運用者が移行期間中に明示的にsql_modeを下げて回避せざるを得なかった。SQLite・Rust式のオプトイン戦略と正確に対比される点だ。MySQLは「いずれ全員が新デフォルトへ」、SQLite/Rustは「古いコードには絶対手を触れず、新しいコードだけ新デフォルトへ」を選んだわけだ。

7. 実務への示唆 - 今すぐ使えるもの

7.1 3行のPRAGMAで今すぐ安全に

公式のエディション機構が出る前でも、以下の3つのPRAGMAを接続開始時に毎回実行するだけで、本稿で指摘した問題の大部分を緩和できる。

PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;

一行目は参照整合性を強制し、孤児行と静かなデータ破損を防ぐ。二行目は同時読み書き性能を引き上げる(ただしローカルファイルシステムでのみ有効で、ネットワークドライブでは動作しない点に注意が必要だ)。三行目は同時書き込みの衝突時に即座に失敗する代わりに5秒間再試行させる。

7.2 新規テーブルはSTRICTで

新しく作るテーブルにはSTRICTオプションを付けて型安全性を確保できる。

CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  age INTEGER
) STRICT;

こうすると、age列に文字列'30'を入れようとする試みは黙って保存される代わりに、エラーとして即座に表面化する。

7.3 それでも手作業で担保が必要な限界

これらのPRAGMAはすべてアプリケーションコードが接続のたびに明示的に設定しなければならず、ORMやコネクションプールを挟むと抜け落ちやすい。エディション機構が実際に登場すれば、この繰り返し作業を「一行の宣言」に標準化できるというのがmort.coffeeの提案の核心的価値だ。ただし第5章で述べた通り、その標準化がSQLiteのファイル可搬性の哲学と衝突しないよう設計することは決して簡単ではない。

結論

SQLiteの緩いデフォルトの問題は、SQLite固有の欠陥ではなく、成熟したソフトウェアが例外なく直面する後方互換性のジレンマの一事例だ。Rustのエディションは、このジレンマを「古いコードには絶対に手を触れず、新しいコードだけがオプトインで新ルールを受け取る」という方式で解き、優雅な先例を残した。これをSQLiteにそのまま移植しようというmort.coffeeの提案は方向性としては正しいが、クレート単位できれいに分かれるコンパイル言語とは違い、接続・ファイル・テーブル単位に設定が散らばり、ファイル自体が数十年移動し続けねばならない組み込みデータベースエンジンに移すには、スコープ設計と後方互換性の検証においてはるかに多くの難題を解く必要がある。公式エディションが出るかどうかにかかわらず、今すぐできる最も現実的な対応は、foreign_keys、journal_mode、busy_timeout、STRICTテーブルをプロジェクトの標準として明示的に有効化しておくことだ。
