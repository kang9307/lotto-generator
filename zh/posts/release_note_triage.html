发布说明读不完 - 决定升级时要挑出来的四类信息

安全修复、破坏性变更、废弃预告，以及悄悄改变的行为。机器能做到哪里，从哪里开始要人来看

2026-09-03 开发/基础设施

打开依赖清单，自己亲手写进去的大概只有二十来行，而旁边的锁文件里躺着几百个包。其中活跃的那些每隔几周就发一个新版本。两个数字一乘，每周到达的发布说明的量早已超出一个人能读完并做出判断的范围。可是不读的话，某天部署就会崩，崩了之后再去翻说明，那段内容就明明白白写在那里。

所以现实中发生的通常是两种情况：要么从一开始就没人读，要么一个人全读到精疲力尽，最后还是没人读。这篇文章讲的是中间那段。如果全部读完不可能，那么只挑哪些来读才能决定升级。答案比想象的短，而其中一项是大多数团队压根没在找的。

本文不推荐、不评价任何特定工具或服务，也不涉及安装与配置步骤。文中引用的规范与政策均以2026年9月为准，来自各发布主体的一手文档，此后可能被修订。

缘起 - 一个声称替你筛发布说明的服务

2026年9月初，韩国开发者社区里出现了一个服务，声称能从 CNCF 项目的发布说明中自动抽取安全修复、破坏性变更和待废弃项。覆盖范围据称是 CNCF 毕业与孵化阶段的76个项目。CNCF 的项目页面在2026年9月列出了毕业38个、孵化38个，所以这个数字对得上。

公开的配套仓库是一个用 Go 写的 MCP 服务器。Apache-2.0 许可、102 次提交、最新标签 0.8.0、2 颗星、0 个分叉。这是一个刚起步的个人项目。因此本文既不推荐也不评价这个服务。真正值得注意的是，这种东西被做出来这件事本身就是一个信号，说明读发布说明已经变成人力接不住的活儿。

该服务的网页拒绝访问（HTTP 403），无法直接打开。所以下面谈的不是某个具体工具的行为，而只谈这类工具能替你分担什么，又有什么会一直留在人这一侧。

全部读完早就不可能了

不读发布说明不是因为懒，是算术。自己声明的依赖有三十个，每个再牵进来十个，进入执行路径的包就是几百个。再加上底层平台：容器运行时、编排系统、数据库、反向代理，以及它们之下的发行版。在任何组织里，这都不是一个人能读完并判断的量。

在这之上还叠着三种错觉，把问题彻底固化。

  • 重要的东西反正会显眼 — 最危险的变更往往写在最不起眼的句子里，「调整了默认超时」 这一行就是
  • 只在主版本号变动时看就行 — 后面要讲的 SemVer 规范并没有把这个期待保证到那种程度
  • CI 过了就没事 — 测试只验证我们知道自己在用的行为。碰巧依赖上的行为，本来就不在测试里

所以需要的不是更勤快地读的习惯，而是一条把阅读对象缩小的标准。没有标准，勤快撑不过几周。

要找的只有四类

发布说明里混着性能改进、文档修订、错别字、内部重构和贡献者名单。参与升级判断的只有其中四类，其余的等发布之后再读也不迟。

找什么说明里常用的措辞漏掉会发生什么机器能不能代劳
安全修复Security、CVE-、GHSA-、advisory带着已公开的漏洞继续运行基本可以
破坏性变更Breaking、Removed、no longer部署当场崩掉，好处是当场就知道基本可以
废弃预告Deprecated、will be removed in眼下没事，两个版本之后一起爆部分可以
悄悄改变的行为Changed、Fixed、now defaults to一个错都不报，只有结果不一样了最难

安全修复 - 标注得最好，也漏得最多

安全修复的标注约定是四类里最完备的。会挂上 CVE 或 GHSA 标识符，配一个单独的公告页面，还会被漏洞数据库收录。可还是会漏，原因不在标注，而在到达路径。自己声明的包发安全版本会有通知，可那个包在内部牵进来的东西发安全版本，往往落在通知配置之外。真出事一般都是从那一侧来的。

破坏性变更 - 危险但诚实

破坏性变更听着吓人，实务上却是四类里最好处理的。要么编译失败，要么起不来，要么第一个请求就抛异常。代价大，但检测是免费的。花在这上面的时间是 「修的时间」，不是 「找的时间」。

废弃预告 - 今天的警告，明年的故障

废弃预告今天什么都不会引发，所以读了也就过去了。问题在于这一项是带到期日的债务。当时不立刻登记成工单，几年后就会有好几条在同一周集中到期。

悄悄改变的行为 - 没人给它做标记

第四类和前三类性质不同。它没有标注约定，在发布说明里只是 「Changed」 或 「Fixed」 条目中的一句话。版本号是次版本或修订版，可默认值变了，或者排序变了，或者取整方式变了。部署成功，测试也通过，只是结果不一样了。

为什么第四类最危险

前三类总会在某个时点给出信号。安全修复有公告文档，破坏性变更让部署崩掉，废弃预告在日志里留下警告。只有第四类什么信号都不给。于是发现的时点不是部署之后，而是几周后对账对不上的时候，或者用户提交工单的时候。

这一类怎么产生的，SemVer 规范本身就给了线索。规范规定修订号在 「只引入向后兼容的缺陷修复时」 递增，同时把缺陷修复定义为「修正错误行为的内部变更」。可如果我们的代码正好依赖着那个 「错误行为」，这次修复在定义上是修订版，对我们却是破坏性变更。上游是修好了，下游是坏掉了。这种不对称，规约守得再好也消不掉。

从说明里把这一类挑出来的办法，是对几个词保持怀疑。下表左侧的措辞一出现，哪怕那句话被归在 「性能改进」 条目下，也得重读一遍。

说明里的措辞实际该问的是什么在我们这边核对哪里
默认值现在是 X我们有没有显式写死过那个值在配置文件和代码里搜那个选项名
不再做 Y 了我们是不是把 Y 当成前提在用隐含前提通常不在测试里
把排序稳定化了有没有依赖顺序的逻辑取列表首元素的代码、分页
修正了精度或取整会不会用在金额和数量的计算上已存的历史值和新算出来的值对不上
现在会抛出错误了之前有没有悄悄通过的输入没有异常处理却一路通过的路径

表里最后一行来得特别频繁：原先默默忽略非法输入的库，现在被 「修好」 成会抛异常。而在发布说明里，它被写在 Fixed 下面。

语义化版本承诺了什么，又没承诺什么

Semantic Versioning 2.0.0 规范给三位数字各自赋予了含义。主版本号在出现不兼容的 API 变更时递增，次版本号在新增向后兼容的功能时递增，修订号在做向后兼容的缺陷修复时递增。规范还给次版本号那条加了一句：公共 API 中任何功能被标记为废弃时，必须递增次版本号。也就是说，废弃预告本身就被设计成要体现在版本号上。

承诺到此为止。没有承诺的部分要更多。

SemVer 承诺的没有承诺的
主版本号升了，就一定有不兼容的变更主版本号没升，我们的代码就不会坏
公共 API 的废弃标记会体现在次版本号以上未写进文档的行为、错误消息、日志格式
主版本号递增时，次版本号和修订号归零性能、延迟、内存占用的连续性
0.y.z 事先声明任何东西都可能随时改变传递依赖一起升上去而带来的变化
只对声明遵循该规约的项目成立那个项目把 「公共 API」 的边界划到哪里

右侧第一行在实务上代价最高。规范的 FAQ 直接处理了这种情形：当不小心发出了不兼容的变更、而回退会波及大量用户时，它写道「即使严格来说只算修订版发布，也可能更适合发一个主版本」。也就是说，连制定规范的一方也预设了版本号与实际影响可能对不上。

0.x 的特例也值得照字面读。规范把 0.y.z 定为初始开发阶段，并明确写道任何东西都可能随时改变，不应把公共 API 视为稳定。至于什么时候该发 1.0.0，FAQ 的回答更直白：如果软件已经用在生产环境，那它多半早就该是 1.0.0 了。所以已经进入运维的 0.x 依赖，是规约上什么都不保证的地方。

怎么读安全公告 - 分数不是顺序

找到安全修复之后，下一个问题是 「要不要先修」。这里常见的错误是按 CVSS 分数排队。FIRST 的 CVSS v4.0 用户指南明确堵住了这种用法，原话是「CVSS 基础分是为衡量漏洞的严重程度而设计的，不应单独用来评估风险」。同一份文档补充说，基础分只反映漏洞自身的固有属性，与威胁态势和存在漏洞的系统所处的环境无关，必须用环境指标和威胁指标来补足。

真正改变顺序的是是否正在被实际利用。CISA 的 KEV 目录就是为此运行的。收录标准有三条：漏洞已分配 CVE 标识符、有可靠证据表明它已在野被实际利用、以及存在明确的处置方式（例如厂商提供的更新）。目录页面把自己描述为「在野被利用漏洞的权威来源」，同时写明组织应当把这份目录 「作为漏洞管理优先级框架的输入」 来使用。截至2026年9月，收录条目为 1,694 条。

适用于美国联邦民事行政机构的指令已更新为 2026年6月10日发布的 BOD 26-04。该指令沿用了 KEV 的收录标准，并且不按分数、而按四个二选一的问题来确定处置期限。它对其他国家的企业没有直接约束力，但作为优先级函数的形状是可以直接借鉴的。

问什么为什么要问这个
资产是否对外暴露攻击者能够到达，利用才谈得上成立
是否被列入 KEV理论上的可能和实际的利用是两回事
利用能否自动化一旦自动化，不是目标也会轮到你
是部分控制还是完全接管同样能够到达，后果的量级不同

举指令表格里的例子：对外暴露、列入 KEV、可自动化且导致完全接管的组合，要求在3天内处置并同时做取证分类；同样条件下影响为部分控制则是6天。另一端，不在 KEV、没有对外暴露、影响为部分控制的组合，被归类为「随系统升级时修复」。期限以日历日计，且明确写明事实变化时期限也随之变化。

这里该拿走的是结构而不是数字。与其拿一个分数去对阈值，不如分别去问可达性、实际利用、自动化和影响量级。四个问题里有三个可以靠外部资料回答，只有第一个需要了解自家基础设施的人来答。补丁发布之后留给防守方多少时间，在修复本身就是信号里单独谈过。

为机器留下的那些钩子

自动扫描发布说明的工具并不是在真空里运转的。过去十几年间，在写给人看的文字里埋进机器能勾住的钩子这种惯例已经积了好几层，各自回答的问题并不相同。

格式或数据库回答的问题局限
Keep a Changelog这个版本有没有安全条目项目遵循时才成立
Conventional Commits提交里有没有标注破坏性变更漏标了没办法验证
GitHub Releases API哪个标签在什么时候发的正文是自由格式的 Markdown
OSV这个版本是否落在影响范围内影响范围以包为单位
GitHub Advisory Database哪个版本最先修好的未审阅条目不触发告警
SBOM我们到底装了些什么装了和真的在跑是两回事

Keep a Changelog 在 1.1.0 版把变更类型固定为六种：Added（新功能）、Changed（已有功能的变更）、Deprecated（即将被移除的功能）、Removed（已移除的功能）、Fixed（缺陷修复）、Security（涉及漏洞）。这六种里Security 单独占一个分区，正是这套惯例的实际价值所在，因为上一节的第一个问题靠一个分区名就有了答案。不过同一份文档把 「变更日志是给人看的，不是给机器看的」 放在原则的最前面，并写道拿提交日志的 diff 当变更日志是个糟糕的主意，因为那里面全是噪声。

Conventional Commits 1.0.0 则把钩子挂在提交信息上。结构是这样的。

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

一种写法是在脚注里写大写的 BREAKING CHANGE 加冒号和描述，另一种是在类型或作用域之后、冒号之前紧挨着加一个 !。规范规定用了 ! 就可以省略脚注，此时提交描述本身就是对破坏性变更的说明；并且不论类型为何，带 BREAKING CHANGE 的提交都应当对应到主版本发布。

变更日志那一侧长这个样子。分区名是固定的，所以能被解析，也因此机器可以把前述四类中的三类筛成候选。

## [2.4.0] - 2026-08-14
### Added
### Changed
### Deprecated
### Removed
### Fixed
### Security

采集这一侧常用 GitHub 的发布 REST API。有列出发布、取最新发布、按标签查询的端点，响应里带着 tag_name、body、prerelease、draft、published_at 这些字段。还有一个自动生成发布说明的端点，文档把它的产物描述为 「包含自上次发布以来的变更和贡献者信息的 Markdown 正文」。忽略 prerelease 和 draft，就会把还不算正式的标签也抓进来。标签本身消失时下游会失去什么，在标签消失后下游失去什么里谈过。

漏洞这一侧有两个数据库撑着。OSV 把自己描述为 「面向开源的分布式漏洞数据库」，并说它的模式「以人和机器都能读的格式描述漏洞，并精确对应到开源包的版本或提交哈希」。关键词是 「精确对应」，因为 「1.x 系列里某处有漏洞」 这样的表述没法自动判定。

GitHub Advisory Database 把条目分成三类：经 GitHub 审阅并确认了生态系统与包信息的、从 NVD 数据源自动进来但未经审阅的、以及关于恶意包的。文档明确写道未审阅的条目不会触发 Dependabot 告警。也就是说，没收到告警并不等于不受影响。每个条目都有 GHSA-xxxx-xxxx-xxxx 形式的标识符，同时收录问题存在的已发布版本范围和最早修复的版本。后者在实务里用得更多，因为它直接告诉你要升到哪里。

SBOM 在另一个层面作答。CISA 把 SBOM 定义为 「构成软件组件的配料清单，一份嵌套的清单」，并把它描述为软件供应链风险管理的核心构件。同一页面一并介绍的 VEX 是「一份证明，也是安全公告的一种形式，用来说明某个产品是否受某个已知漏洞的影响」。这正是想由供应方提前回答下一节那个问题，也就是 「那么我们到底受不受影响」 的尝试。

最后，还有一条绕开发布说明拿到答案的路。自 v1.19 起，Kubernetes 对访问已废弃 REST 端点的请求会在响应里加上 Warning 头，在审计事件里留下 k8s.io/deprecated 注解，并把 apiserver_requested_deprecated_apis 这个 gauge 指标置为 1。这个指标上还带着标明将在哪个发行版停止提供的标签。这是不读说明、直接去问正在运行的系统，就废弃这件事而言，这条路准确得多，因为它连我们是不是真的在调用那个 API 都一并告诉你。

自动化能到哪里，又在哪里停下

把前面那些格式全都接上，边界就相当清楚了，一句话就能划出来。信息在上游仓库里，机器能答；信息在我们自己的代码里，机器答不了。

  • 机器能回答的 — 这个版本有没有 Security 分区、提交里有没有破坏性标注、我们锁定的版本是否落在这条公告的影响范围内、哪个版本最先修好的、上次升级之后过去了多少个标签
  • 机器回答不了的 — 我们是不是真的会走到那条代码路径、变掉的默认值我们有没有显式指定过、被移除的函数在我们代码里用什么参数调用、这个变更在我们的数据形态下会不会出问题
  • 卡在中间的 — 我们到底有没有装那个包。SBOM 答到这一步为止，装了和真的在执行之间的空隙仍然留着
  • 供应方试图代答的 — VEX 就是把 「本产品不受该漏洞影响」 写成文档的做法，前提是得有人肯出这份文档
  • 剩下的 — 判断转移不了。自动化能做的到 「生成候选并排好顺序」 为止

所以自动化落地的成败，不该看 「它能捞出多少」，而该看「它把人要看的清单缩到多短」。一天扔过来四十条的工具，和什么都不扔的工具实质上是一样的，因为两者都不会被读。

为什么不能靠摘要决定发布

摘要不是把句子变短的活儿，而是选择丢掉什么的活儿。而在发布说明里最先被丢掉的，偏偏是条件从句和否定词。「只有启用了 A 选项时 B 才会变」 缩成 「B 会变」，就是这么来的。人来摘要也会出这种事故，但以长度为目标的自动摘要在结构上会更频繁地出。

发布说明摘要中反复出现的损失，大致分成五种。

  • 条件脱落 — 只在特定配置、平台或版本组合下才成立的变更，被读成全面性的变更
  • 否定翻转 — 「不做」 变成 「做」，「不受影响」 变成 「受影响」
  • 主体错位 — 服务端的默认值变更被搬到客户端，或者反过来
  • 版本错位 — 有漏洞的版本和带修复的版本混在一起。这一类会把处置方向弄成正好相反
  • 强度失真 — 「建议」 硬化成 「必须」，「没有已知案例」 硬化成 「没有」

所以摘要只该用在挑选要读什么上，发布的判断要回到原文去做。要把这条界线固化下来，三条展示规则就够：摘要旁边永远放上原文链接和标签名；把 「无安全条目」 和 「未核对」 用不同的标记区分开；把摘要所依据的那句话原样引用附上。

在团队里怎么跑起来

规则一重就撑不过两个月。真正能维持下来的形态大致是这样。

  • 先把范围缩小 — 定期核对的对象是自己声明的依赖和底层平台，不是整个锁文件。其余交给漏洞告警
  • 每周巡视一人30分钟 — 轮流承担，产出是 「本周需要人看的 N 条」 这一份清单。读的人不负责下判断
  • 把紧急和例行分开 — 紧急通道的条件事先写成文字。对外暴露的资产、且已确认存在实际利用的漏洞，是常见的基准线。其余全部走例行通道
  • 机器人 PR 的自动合并范围要事先定好 — 修订级别、测试通过、没有破坏性标注，到此为止。之外的由人来看。GitHub 的文档也写道，判断被提议的更新时要查看 PR 摘要中附带的变更日志和发布说明
  • 积压的 PR 要读成政策失败的信号 — 二十条压在那里不是懒，而是说明自动合并的范围太窄，或者对象范围太宽
  • 把放过去的记下来 — 本周搁置的升级要带着期限记成工单。没有记录的搁置，下周就不存在了

处理机器人开的 PR 还有一点要说。自动更新工具的目的是即使依赖没有漏洞也让它保持最新，所以 PR 被开出来这件事本身不是安全事件。把安全 PR 和保鲜 PR 排在同一列里，真正紧急的那条就被埋掉了。无论用标签还是用频道，两条流必须在视觉上不一样。另外这类采集流水线通常随身带着仓库访问令牌，令牌会从哪里漏出去，整理在远程 URL 里嵌着令牌里。

写发布说明的一方能做什么

以上都是读的一方。写的一方能做的事便宜得多，效果也大得多。发布说明是一份关于该做什么、而不是提交了什么的文档。

  • 不要让 Security 分区空着 — 没有就写没有。分区根本不存在和分区是空的，对读的人来说是完全不同的信息
  • 破坏性放在标题行 — 藏在正文第二十行的破坏性等于没有。提交规约里的 ! 标记或脚注就是为它腾出的位置
  • 把默认值变更当作破坏性来对待 — 版本号上是次版本，在下游就是破坏性。前面讲的第四类，大部分就诞生在这里
  • 废弃要把预告和移除时点一起写出来 — 「以后会移除」 不是期限。Kubernetes 的 API 废弃政策就接近这个形状：GA 版本可以标记为废弃，但不得在同一主版本内移除；beta 版本在引入后9个月或3个次版本发布（取较长者）内被废弃，并在废弃之后再经过同样的期限才停止提供；alpha 版本则可以在任何发行版中不经预告直接移除
  • 留下运行时警告 — 这是能触达没读说明的人的唯一路径。前面提到的 Warning 头和废弃 API 调用指标就是例子
  • 迁移指南要用代码写 — 不是 「什么变了」，而是 「把这段代码改成这段代码」。前后对照两行，比十行文字说明读得快

同一份政策文档里还有一条规则值得借鉴：API 元素只能通过递增 API 组的版本来移除。已经进入某个版本的元素，不能从那个版本里拿掉，也不能显著改变其行为。这条规则给下游的，是 「只要还留在这个版本上，脚下就不会动」 这份保证；有了这份保证，升级才能被当成计划来处理。

推迟是要付利息的

推迟升级这个判断本身常常是对的。现在不需要、现在没人腾得出手、现在没有理由制造风险。问题在于推迟期间积累起来的东西不容易看见。

  • 废弃警告整块丢失 — 警告只在实际经过那个版本时才出现。一次跳过三个主版本，中间版本本该发出的警告一次都看不到，而它们想告知的变更会在同一刻全部砸过来。这是被推迟的升级最大的实际代价
  • 迁移指南互相咬不上 — 指南是按一级一级往上爬来写的。跳过三级，各级的前提条件彼此错位，最后没有一份指南能照原样套用
  • 安全修复只进最新分支 — 这种政策很常见。于是落后得越多，就越可能因为一个漏洞被迫做一次计划外的大规模升级
  • 连别的升级也被卡住 — 一个陈旧的包压着上限，和它咬合的那些包就被一起捆住。一行升不上去，十行停在原地

所以实务规则一条就够。把推迟这个决定记录下来，并且给它加上期限。没有期限的搁置不是决定，是遗忘，而遗忘的代价会在以后一次性结账。这张账单送到的时点，通常轮不到我们来挑。

小结

把发布说明全部读完是不可能的，所以目标不是勤快，而是筛选。要挑出来的有四类：安全修复、破坏性变更、废弃预告，以及没有任何标记、只有行为变了的条目。前三类有标注约定，机器可以生成候选；第四类没有约定，只能靠人对特定的词保持怀疑。而事故大多出在第四类。

版本号是信号，不是保证。SemVer 告诉你主版本号升了就一定有不兼容的变更，却不会告诉你主版本号没升就安全。安全这一侧也一样：分数衡量的是严重程度，不是排队的次序，真正改变次序的是实际是否被利用，以及我们的环境暴露到什么程度。

自动化的边界同样清楚。在上游仓库里的信息机器能答，在我们自己代码里的信息机器答不了。「这个版本里有安全修复」 找得到，「我们的代码会受影响」 找不到。所以接入工具时该期待的是清单变短，而不是判断消失。

  • 关于 LLM 摘要丢失否定词或条件从句的频率，没有确认到可以引用数值的一手资料。该节只写成摘要这项工作本身带来的结构性风险，没有主张任何发生率
