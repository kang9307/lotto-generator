LLM을 직접 띄운다는 결정 - 자체 서빙 플랫폼 검토 체크리스트

넷플릭스가 공개한 사내 서빙 구성으로 본 엔진 선택·GPU 산정·배칭 설계·기존 ML 플랫폼 통합의 결정 항목

2026-07-28 개발/인프라
글의 범위 — 이 글은 공개된 기술 문서와 논문을 근거로 정리한 일반적인 정보이며, 특정 벤더나 오픈소스 프로젝트의 도입을 권하는 글이 아닙니다. 서빙 구성의 성능은 모델·하드웨어·요청 분포에 따라 크게 달라지므로, 여기 나온 어떤 구성도 특정 성능을 보장하지 않습니다. 실제 도입 판단은 자사 워크로드로 직접 측정한 결과를 근거로 하시기 바랍니다.

서론: 「우리도 직접 띄워보자」는 말이 나오는 순간

API로 시작한 조직이 어느 시점에 자체 서빙을 검토하게 되는 계기는 대체로 셋 중 하나다. 첫째, 데이터를 외부로 보낼 수 없다는 제약이 뒤늦게 확인된 경우. 둘째, 파인튜닝한 모델을 프로덕션에 올려야 하는데 호스팅 API로는 원하는 형태가 안 나오는 경우. 셋째, 월 청구서가 어느 선을 넘어서면서 재무 쪽에서 질문이 들어온 경우다. 어느 쪽이든 회의실에서 나오는 문장은 비슷하다. 「오픈 웨이트 모델도 좋아졌다는데, 우리가 직접 띄우면 안 되나?」

이 질문 자체는 건강하다. 문제는 그다음에 벌어지는 일이다. 대개 GPU 견적과 모델 벤치마크 점수를 비교하는 회의로 흘러가고, 정작 운영에서 실제로 시간을 잡아먹는 항목들은 검토표에 올라오지도 않는다. 엔진과 서버의 버전 조합, 아티팩트를 어떤 경로로 노드에 내리는지, 모델을 교체할 때 소비자 코드가 어떻게 되는지, 지표가 두 군데로 흩어져 있을 때 기존 대시보드를 쓸 수 있는지 같은 것들이다.

2026년 7월 17일, 넷플릭스 기술 블로그에 사내 LLM 서빙 플랫폼을 설명한 글이 올라왔다. AI 플랫폼 조직의 Model Runtime 팀과 Inference 팀이 함께 쓴 글이다. 이 글이 흥미로운 지점은 자랑이 아니라 실패 지점의 목록이라는 데 있다. 어떤 파라미터가 조용히 버려졌고, 어떤 버전 조합에서 백엔드가 통째로 안 떴고, 어느 지점에서 지연이 CPU에 묶였는지를 구체적으로 적어 놓았다.

이 글은 그 사례를 소개하려는 것이 아니다. 넷플릭스가 만난 문제들은 대부분 구조에서 나오는 문제라서, 규모가 훨씬 작은 조직이 자체 서빙을 시도해도 똑같이 만나게 된다. 그래서 이 글에서는 그 목록을 「자체 LLM 서빙을 검토할 때 결정해야 하는 항목표」로 다시 정리한다. 비용을 어떻게 통제할지는 토큰 비용을 조직 단위로 통제하는 방법에서 별도로 다뤘고, 여러 벤더를 어떻게 오갈지는 벤더 락인과 이탈 전략에서 다뤘다. 여기서는 모델을 직접 띄워 운영하는 쪽의 인프라 문제만 본다.

1. 넷플릭스가 실제로 만든 것 - 공개된 구조에서 읽히는 것

원문에서 확인되는 구조는 세 겹이다. 맨 앞에 JVM 기반 서빙 계층이 있어 라우팅, 피처 조회, 후보 생성, 후처리, 로깅을 담당한다. 그 뒤에 Model Scoring Service(MSS)라는 공용 추론 백엔드가 있고, 그 아래에서 NVIDIA Triton 추론 서버가 모델 로딩·배칭·GPU 스케줄링을 맡는다. 작은 CPU 모델은 서빙 계층 안에서 그대로 돌리고, 큰 모델은 MSS로 원격 호출을 보낸다.

여기서 가장 중요한 설계 결정은 기술 선택이 아니라 배치 위치다. 넷플릭스는 LLM 전용 스택을 새로 세우지 않았다. 원문의 표현을 빌리면 별도의 ML 사일로가 아니라 기존 프로덕션 환경 안에서 전체 스택을 직접 돌린다. MSS는 XGBoost·TensorFlow·PyTorch·LLM을 모두 하나의 인터페이스 뒤에서 지원하고, 어떤 모델이든 같은 gRPC 호출로 점수를 매긴다. 배포·버저닝·헬스체크·오토스케일링·멀티리전 롤아웃을 담당하는 Java 컨트롤 플레인도 그대로 재사용한다.

  • 목표가 「LLM 플랫폼 구축」이 아니다. 목표는 기존 모델 서빙 체계에 LLM을 모델 타입 하나로 추가하는 것이었다.
  • 프론트엔드는 두 개다. 기존 서빙 계층을 위한 gRPC, 새 애플리케이션을 위한 OpenAI 호환 HTTP를 같은 인스턴스에 함께 노출한다.
  • OpenAI 호환을 넣은 이유는 편의가 아니라 이동 경로다. 호스팅 모델로 실험하다가 파인튜닝한 자체 호스팅 모델로 옮길 때 코드 변경을 최소화하기 위해서다.
  • 모델 아티팩트 저장소를 따로 설계했다. 큰 가중치를 오브젝트 스토리지에서 매번 내려받는 대신, 모델 공지 시점에 고성능 파일 시스템으로 미리 물질화해 둔다.
  • 지표는 합쳐서 내보낸다. 추론 엔진과 모델 서버가 각자 내보내는 지표를 하나의 엔드포인트로 병합하는 프록시를 별도로 만들었다.

이 다섯 줄을 뒤집으면 자체 서빙 검토표의 첫 다섯 항목이 나온다. 어디에 붙일 것인가, 어떤 API 표면을 낼 것인가, 어떻게 옮겨 탈 것인가, 가중치를 어떻게 나를 것인가, 지표를 어디서 합칠 것인가.

2. LLM 서빙은 전통 ML 서빙과 어디서 갈라지는가

기존에 ML 플랫폼을 운영해 온 조직일수록 이 부분을 가볍게 보기 쉽다. 「모델 하나 더 얹는 것」으로 보이기 때문이다. 그런데 갈라지는 지점이 생각보다 깊고, 대부분은 출력 길이를 요청 시점에 알 수 없다는 한 가지 성질에서 파생된다.

2.1 프리필과 디코드는 성격이 다른 두 작업이다

요청 하나는 두 단계로 처리된다. 입력 전체를 한 번에 읽어 내부 상태를 만드는 프리필, 그리고 토큰을 하나씩 뽑는 디코드다. 프리필은 입력 토큰 수만큼 병렬 연산이라 연산 유닛이 바쁘다. 디코드는 토큰 하나를 뽑기 위해 모델 가중치 전체를 다시 읽어야 해서 메모리 대역폭에 묶인다. 두 단계의 병목이 다르다는 사실이 배칭 설계 전체를 좌우한다.

2.2 KV 캐시가 용량 계산의 중심이다

디코드 단계에서 앞 토큰들의 키·값을 매번 다시 계산하지 않으려고 저장해 두는 것이 KV 캐시다. 이것이 요청마다, 토큰이 늘어날수록 선형으로 커진다. 전통 ML에는 없던 성질이다. 요청 수가 아니라 살아 있는 토큰의 총량이 메모리를 결정하므로, 「초당 몇 건」이라는 익숙한 용량 지표가 바로 통하지 않는다.

이 문제를 운영체제의 가상 메모리처럼 다루자고 제안한 것이 PagedAttention이다. 캐시를 블록 단위로 쪼개 비연속 물리 공간에 배치해 조각화를 줄이고, 요청 안팎에서 캐시를 공유할 수 있게 한다. 원 논문은 KV 캐시 메모리 낭비가 거의 없는 상태를 목표로 제시했고, 같은 수준의 지연에서 당시 최신 시스템 대비 처리량이 2~4배 개선됐다고 보고했다. 긴 시퀀스, 큰 모델, 복잡한 디코딩일수록 개선 폭이 컸다는 서술도 함께 있다.

2.3 연속 배칭은 배치 크기의 의미를 바꾼다

정적 배칭은 요청 여러 건을 묶어 한 번에 처리하고, 가장 느린 요청이 끝날 때까지 나머지 슬롯이 논다. 출력 길이가 제각각인 LLM에서는 이 낭비가 크다. 연속 배칭은 스케줄링 단위를 배치가 아니라 디코딩 스텝으로 내려서, 끝난 요청을 즉시 빼고 대기 중인 요청을 그 자리에 밀어 넣는다. 그래서 자체 서빙에서는 「배치 크기 32」 같은 고정 값이 의미를 잃고, 대신 스텝당 토큰 예산과 동시 시퀀스 상한이라는 두 개의 손잡이가 등장한다.

3. 엔진 선택 - 성능표가 아니라 운영 적합성으로 갈린다

넷플릭스는 처음에 컴파일 기반 엔진으로 시작했다가, 2025년 여름 워크로드 구성이 넓어진 뒤 다시 벤치마크를 돌려 vLLM을 기본 경로(paved path) 엔진으로 정했다. 원문이 밝힌 선택 이유는 네 가지인데, 눈여겨볼 것은 그중 성능 항목이 하나도 없다는 점이다.

  1. 커스텀 아키텍처를 다단계 컴파일 파이프라인 없이 로드할 수 있다. 비표준 모델에서 반복 속도가 빨라진다.
  2. 커스텀 디코딩 로직을 위한 확장 지점이 있다. 뒤에 나올 제약 디코딩 작업에 필요했다.
  3. 실패와 중간 상태를 들여다보기 쉽다. 당시의 컴파일된 엔진보다 디버깅이 수월했다는 서술이다.
  4. 연구 조직이 이미 쓰고 있었다. 연구에서 프로덕션으로 넘기는 인계 비용이 줄었다.

성능 격차 자체는 2025년 시점에 이미 좁혀졌다는 것이 원문의 판단이다. 즉 이 결정은 「어느 엔진이 더 빠른가」가 아니라 「어느 엔진이 우리 조직의 작업 흐름에 맞는가」로 내려졌다. 특정 도구를 권하려는 것이 아니라, 판단 축이 그쪽이었다는 사실이 중요하다.

접근 방식성격강점이 나오는 상황치러야 하는 대가
컴파일형모델을 하드웨어에 맞춰 미리 엔진으로 빌드모델과 하드웨어가 고정되고 오래 유지될 때빌드 단계가 릴리스 경로에 들어오고, 내부 상태 관찰이 상대적으로 어렵다
런타임형가중치를 그대로 올리고 런타임에 스케줄링모델이 자주 바뀌고 디코딩에 손댈 일이 있을 때스크립트 계층이 핫 패스에 남아 병목이 될 수 있다
모델 서버형여러 백엔드를 얹어 로딩·버저닝·배칭을 관리여러 모델 타입을 한 서버에서 다뤄야 할 때서버와 백엔드 사이에 버전 결합이 생긴다

실무에서 이 표를 쓰는 방법은 간단하다. 아래 네 질문에 답해 보고 답이 몰리는 쪽을 고르면 된다.

  • 우리 모델은 몇 주에 한 번 바뀌는가? 분기에 한 번이라면 빌드 단계를 감당할 수 있다.
  • 디코딩 단계에 개입할 일이 있는가? 출력 형식을 강제해야 한다면 확장 지점이 필요하다.
  • 새벽에 장애가 났을 때 누가 붙는가? 그 사람이 스택 내부를 열어 볼 수 있어야 한다.
  • 연구·분석 조직은 무엇을 쓰고 있는가? 인계 비용은 생각보다 크다.

4. 자체 서빙을 택할 조건과, 택하지 말아야 할 조건

이 판단에서 흔한 실수는 비용부터 계산하는 것이다. 비용은 마지막 조건이다. 앞의 조건이 맞지 않으면 아무리 계산해도 그 숫자는 현실이 되지 않는다. 넷플릭스가 이 길을 갈 수 있었던 전제도 원문에 그대로 드러난다. 이미 공용 추론 백엔드와 Java 컨트롤 플레인이 있었고, 제약 디코딩의 핫 패스를 C++로 다시 구현할 수 있는 인력이 있었다.

변경 주기모델을 오래 고정해서 쓴다더 좋은 모델이 나오면 바로 갈아탄다
지연 요구지연 하한을 스스로 통제해야 한다벤더 SLA로 충분하다
규모한 인스턴스를 꾸준히 채울 만큼 크다인스턴스 하나도 다 못 채운다

표를 보면 오른쪽 열이 하나라도 강하게 해당되면 자체 서빙의 근거가 급격히 약해진다는 것을 알 수 있다. 특히 트래픽 모양은 비용 계산 전체를 뒤집는다. GPU는 놀아도 요금이 나가기 때문에, 피크를 견디도록 맞춰 놓은 인스턴스가 나머지 시간에 비어 있으면 토큰당 원가가 그만큼 올라간다. 이 항목은 뒤의 손익분기 절에서 다시 다룬다.

5. GPU 용량 산정 - 가중치와 KV 캐시를 나눠서 센다

「이 모델 돌리려면 몇 기가 필요해?」라는 질문에 파라미터 수만으로 답하면 절반만 맞는다. 필요한 메모리는 세 덩어리로 나뉜다.

  • 가중치 — 파라미터 수 × 요소 바이트. 16비트 부동소수점이면 파라미터당 2바이트다. 텐서 병렬로 쪼개면 카드 수로 나뉜다.
  • KV 캐시 — 살아 있는 시퀀스의 토큰 수에 비례한다. 실질적으로 동시성을 결정하는 항목이다.
  • 활성값과 프레임워크 오버헤드 — 중간 텐서, 통신 버퍼, 런타임이 잡아 두는 몫이다. 정확히 예측하기 어려우므로 여유로 남긴다.

5.1 토큰당 KV 캐시 바이트를 먼저 구한다

계산식 자체는 단순한 산수다. 키와 값 두 벌을 층마다, KV 헤드마다, 헤드 차원만큼 저장한다.

토큰당 KV 바이트
  = 2 (키와 값)
  × 층수(num_hidden_layers)
  × KV 헤드 수(num_key_value_heads)
  × 헤드 차원(head_dim)
  × 요소 바이트(bf16 = 2)

예) 층 32, KV 헤드 8, 헤드 차원 128, bf16
  = 2 × 32 × 8 × 128 × 2
  = 131,072 바이트 = 128 KiB / 토큰

시퀀스 1개 × 8,000 토큰  ->  약 1.0 GiB
동시 시퀀스 20개          ->  약 20 GiB

여기서 자주 틀리는 지점이 하나 있다. 헤드 수는 어텐션 헤드가 아니라 KV 헤드를 써야 한다. 최근 모델 다수가 그룹 쿼리 어텐션을 쓰기 때문에 KV 헤드 수가 어텐션 헤드 수보다 훨씬 작다. 위 예시에서 어텐션 헤드 32를 잘못 넣으면 필요 메모리를 4배로 과대 계산하게 된다. 값은 반드시 해당 모델의 설정 파일에서 확인해야 한다.

5.2 산정 순서

  1. 카드 총 메모리에서 가중치를 뺀다.
  2. 런타임이 사전 할당하는 비율을 정한다. vLLM은 gpu_memory_utilization 비율만큼 GPU 캐시를 미리 잡아 두며, 이 값을 올리면 KV 공간이 늘어 되돌림(선점)이 줄어든다.
  3. KV로 쓸 수 있는 나머지를 토큰당 바이트 × 목표 컨텍스트 길이로 나눈다. 이것이 동시 시퀀스 상한이다.
  4. 동시 시퀀스 상한과 평균 처리 시간으로 대략의 처리량 상한을 낸다. 이 값은 추정일 뿐이므로 반드시 실측으로 대체한다.
  5. 피크 트래픽을 이 상한으로 나눠 인스턴스 수를 구하고, 여기에 이중화와 배포 겹침 몫을 더한다.
  • 컨텍스트 상한을 2배로 늘리면 시퀀스당 KV가 2배가 되고, 같은 카드에서 동시성은 대략 절반이 된다. 컨텍스트는 공짜가 아니다.
  • 접두사 캐시가 잘 맞으면 실제 사용량은 계산보다 줄지만, 용량 계획은 최악값으로 잡는 편이 안전하다.
  • 양자화는 가중치를 줄이지 KV 캐시를 자동으로 줄이지는 않는다. KV 양자화는 별도 설정이며 품질 영향을 따로 측정해야 한다.
  • 개발·스테이징용 GPU를 빼먹는 경우가 많다. 프로덕션만 세면 실제 청구액과 어긋난다.

6. 배칭과 큐잉 설계에서 실제로 결정해야 하는 항목

연속 배칭을 쓰면 튜닝 손잡이가 몇 개로 정리된다. 문제는 이 손잡이들이 서로 반대 방향으로 움직인다는 것이다. 그래서 「최적값」을 찾는 게 아니라 어떤 지표를 희생할지 먼저 정해야 한다.

결정 항목무엇을 정하는가키우면줄이면
스텝당 토큰 예산한 스텝에 처리할 프리필+디코드 토큰 총량첫 토큰까지의 시간이 좋아진다토큰 사이 간격이 안정된다
동시 시퀀스 상한KV 풀을 몇 갈래로 나눌지처리량이 오르고 되돌림 위험도 오른다되돌림이 줄고 GPU가 놀 수 있다
최대 컨텍스트 길이시퀀스 하나가 점유할 수 있는 상한긴 입력을 수용한다동시성을 확보한다
메모리 사전 할당 비율KV 풀 전체 크기되돌림이 줄어든다메모리 부족 여유가 늘어난다
되돌림 방식재계산할지 스왑할지환경에 따라 다르며, 최근 구현은 재계산을 기본으로 둔다
큐 대기 상한언제 요청을 거절할지거절은 줄고 꼬리 지연이 길어진다꼬리 지연이 짧아지고 거절이 는다
우선순위 분리대화형과 배치 작업을 어떻게 나눌지한 풀에 섞으면 배치 작업이 대화형 지연을 밀어 올린다

6.1 청크 프리필이 기본값이 된 이유

긴 프롬프트 하나가 들어오면 그 프리필이 한 스텝을 통째로 차지해서, 이미 답을 뽑고 있던 요청들의 토큰이 그동안 멈춘다. 사용자 눈에는 글자가 나오다가 뚝 끊기는 현상으로 보인다. 청크 프리필은 긴 프리필을 여러 스텝에 나눠 넣어 이 현상을 완화한다. vLLM 공식 문서는 이 기능이 토큰 간 지연과 디코드를 개선하며, 연산 바운드인 프리필과 메모리 바운드인 디코드를 같은 배치에 섞어 GPU 활용도를 높인다고 설명한다. 최신 아키텍처에서는 가능한 경우 기본으로 켜진다.

튜닝 방향도 문서에 명시돼 있다. 스텝당 토큰 예산을 작게 잡으면(예: 2048) 토큰 간 지연이 좋아지고, 크게 잡으면 첫 토큰까지의 시간이 좋아진다. 처리량을 최대로 뽑으려면 8192보다 크게 두라는 권고도 함께 있는데, 큰 GPU에 작은 모델을 올린 경우에 특히 그렇다고 적혀 있다. 세 목표를 동시에 만족시키는 값은 없으므로, 서비스가 대화형인지 배치인지부터 정하는 것이 순서다.

6.2 되돌림 경고가 뜨기 시작하면

메모리가 모자라면 엔진은 진행 중인 요청의 KV를 회수하고 나중에 다시 스케줄한다. 이 되돌림이 잦아지면 같은 토큰을 두 번 계산하게 되므로 처리량과 꼬리 지연이 함께 나빠진다. vLLM 문서가 제시하는 대응 순서는 다음과 같다.

  1. 메모리 사전 할당 비율을 올려 KV 공간을 넓힌다.
  2. 동시 시퀀스 상한을 낮춰 한 번에 살아 있는 요청 수를 줄인다.
  3. 텐서 병렬 크기를 키운다.
  4. 파이프라인 병렬 크기를 키운다.

6.3 큐잉에서 빠뜨리기 쉬운 것

  • 어드미션 컨트롤이 없으면 꼬리 지연에 상한이 없다. 큐를 무한히 받으면 응답이 늦게라도 오는 대신 사용자는 이미 떠난 뒤다. 대기 시간 상한을 넘기면 거절하는 편이 낫다.
  • 거절은 실패가 아니라 설계다. 429를 받은 클라이언트가 무엇을 할지(대체 모델, 축약 응답, 나중 재시도)까지 같이 정해야 한다.
  • SLO를 첫 토큰과 토큰 간격으로 쪼개 정의한다. 종단 지연 하나로만 정의하면 파라미터를 어느 쪽으로 돌릴지 결정할 수 없다.
  • 재시도 정책이 부하를 증폭한다. 포화 상태에서 자동 재시도가 겹치면 큐가 더 길어진다. 백오프와 재시도 예산을 함께 둔다.
  • 스트리밍 클라이언트의 중단을 서버가 알아채야 한다. 사용자가 창을 닫았는데 토큰을 계속 뽑고 있으면 그만큼이 낭비다.

7. 모델 패키징과 배포 - 인터페이스가 바뀔 때 무엇이 깨지는가

넷플릭스 글에서 실무자가 가장 얻어 갈 만한 부분이 이 대목이다. 같은 모델을 올리는 두 가지 패키징 방식이 있고, 둘의 차이가 성능이 아니라 결합도라는 서술이다.

  • 스크립트 백엔드 방식 — 패키징 시점에 입출력 텐서 스펙을 직접 정의하고, 그 스펙이 아티팩트 안에 고정된다. 프론트엔드가 입출력 스펙을 건드리는 업그레이드를 하면 패키징 코드도 함께 바꿔야 하고, 그러지 않으면 런타임에 요청이 실패한다.
  • 엔진 백엔드 방식 — 아티팩트가 가중치와 토크나이저를 가리키는 설정 파일이고, 스펙은 배포 시점에 동적으로 생성된다. 모델과 프론트엔드가 서로 독립적으로 진화할 수 있어 기본 권장 경로가 됐다.

그런데 두 번째 방식에는 대가가 따라온다. 서버와 엔진 사이의 버전 결합이다. 원문은 구체적인 사례를 들었다. 특정 서버 릴리스가 엔진 쪽에서 이미 제거된 모듈을 가져오려 해서 백엔드가 통째로 뜨지 않았다. 그래서 넷플릭스는 함께 검증한 조합을 짝으로 고정해 배포한다. 커스텀 전처리·후처리, 앙상블 파이프라인, 비표준 토크나이즈가 필요한 모델은 여전히 스크립트 백엔드로 되돌아가야 하며, 이 탈출구는 일부 모델에 계속 필요할 것이라고 적혀 있다.

7.1 배포 전략 두 가지와 그 GPU 비용

전략동작맞는 상황약점
레드-블랙새 버전을 옆에 띄우고 헬스체크 통과 후 트래픽을 단계적으로 이동. 실패 시 원자적 롤백모델 인터페이스가 안정적일 때입출력 스키마가 바뀌면 이동 중 불일치가 발생
버전 병행모델 ID와 버전 쌍마다 독립 배포. 여러 버전이 동시에 서비스파괴적 인터페이스 변경이 불가피할 때겹치는 기간 동안 GPU 비용이 일시적으로 증가

넷플릭스의 권고는 명확하다. 텐서 모양 같은 가변 설정을 모델 안에 넣어 버전에 무관한 인터페이스로 만들고, 값싼 레드-블랙 경로를 쓰라는 것이다. 버전 병행은 파괴적 변경이 불가피한 드문 경우로 남긴다. 실무 언어로 옮기면 이렇다.

  • LLM 배포는 컨테이너 이미지 교체가 아니다. 전환 기간에 GPU가 한동안 두 배로 필요하다는 사실을 용량 계획에 미리 넣어야 한다.
  • 모델 인터페이스에 버전 협상 개념이 없으면, 모델 교체가 곧 소비자 코드 배포와 묶인다. 이 결합을 끊는 것이 배포 전략의 목적이다.
  • 롤백 경로를 먼저 만든다. 새 버전으로 넘어가는 절차보다 되돌아오는 절차가 더 자주 필요하다.
  • 엔진과 서버의 검증된 조합을 목록으로 관리한다. 이 목록이 없으면 업그레이드마다 도박이 된다.

8. 기존 ML 플랫폼에 얹을 때의 충돌 지점 여섯 곳

이미 모델 서빙 체계가 있는 조직이 LLM을 추가할 때 실제로 부딪히는 지점들이다. 넷플릭스가 각각을 어떻게 처리했는지가 공개돼 있어 대조하기 좋다.

  1. 인터페이스 계약 — 기존 플랫폼은 「입력 텐서를 넣으면 출력 텐서가 나온다」를 전제한다. LLM은 스트리밍, 가변 길이, 중도 취소를 요구한다. 넷플릭스는 하나로 통일하는 대신 gRPC와 OpenAI 호환 HTTP 두 프론트엔드를 같은 인스턴스에 병행해 풀었다. 기존 소비자는 그대로 두고 새 소비자만 새 표면을 쓰게 하는 방식이다.
  2. 아티팩트 배포 경로 — 기존 모델은 수 초 만에 올라오지만 LLM 가중치는 수십 기가바이트다. 원문은 오브젝트 스토리지나 모델 허브에서 시작 시점에 직접 내려받으면 콜드 스타트가 스케줄러가 견디는 수준을 넘어선다고 지적하고, 모델 공지 시점에 고성능 파일 시스템으로 미리 물질화하는 방식을 택했다고 밝혔다.
  3. 오토스케일 신호 — 초당 요청 수와 CPU 사용률로 스케일하는 기존 규칙은 LLM에서 늦게 반응한다. 요청 하나가 오래 살아 있기 때문이다. 대기 큐 길이, KV 캐시 사용률, 대기 시간을 신호로 써야 한다.
  4. 관측성 — 추론 엔진과 모델 서버가 서로의 지표를 모른다. 원문에 따르면 서버의 내장 브리지가 엔진 지표 40여 개 중 9개만 노출했고, 토큰 처리량·KV 캐시 사용률·접두사 캐시 적중률처럼 정작 필요한 지표가 빠져 있었다. 넷플릭스는 두 소스를 읽어 하나의 지표 엔드포인트로 합치는 경량 프록시를 만들어, 기존 대시보드와 알람을 수정 없이 그대로 쓸 수 있게 했다.
  5. API 계약의 조용한 누락 — 원문에서 가장 실용적인 경고다. 서버의 OpenAI 호환 프론트엔드가 구조화 출력 지정 필드를 엔진에 닿기 전에 조용히 버렸다. 오류가 나는 것이 아니라 그냥 무시된 것이라 발견이 늦다. 넷플릭스는 해당 프론트엔드를 가져와 패치해서 그 필드를 엔진의 가이드 디코딩 파라미터로 번역하게 만들었다. 여기서 얻을 교훈은 명확하다. 「OpenAI 호환」은 스펙 준수의 보증이 아니다. 실제로 쓰는 필드마다 계약 테스트가 필요하다.
  6. 배포 파이프라인과 노드 풀 — GPU 노드 풀 분리, 이미지 크기, 드라이버 버전, 노드 재기동 시 워밍업 절차가 기존 CI/CD 가정과 어긋난다. 특히 이미지가 커지면 배포 시간이 길어져 앞의 배포 전략 선택에 영향을 준다.

9. 구조화 출력을 강제할 때 생기는 문제

많은 서비스가 LLM 출력을 그대로 쓰지 않고 정해진 형식으로 받아야 한다. 흔한 방법은 생성이 끝난 뒤 검사하고 어긋나면 다시 시키는 것인데, 이 방식은 잘못된 생성의 비용을 이미 지불한 뒤에 고치는 것이다. 넷플릭스는 제약을 디코드 루프 안으로 밀어 넣는 쪽을 택했다. 요청마다 다른 규칙이 적용되므로 요청별로 설정된 처리기가 붙는 구조다.

9.1 왜 지연이 GPU가 아니라 CPU에 묶였나

초기 구현에서 문제가 드러났다. 로짓 처리기가 요청 단위로 돌았기 때문이다. GPU가 배치 전체의 로짓을 만들면 CPU가 그것을 받아 오고, 그다음 제약 로직이 요청마다 차례로 실행됐다. 파이썬의 전역 인터프리터 잠금 때문에 이 작업이 병렬화되지 않아서, 배치가 커질수록 CPU 시간이 선형으로 늘었다. 원문의 서술은 이 상황을 정확히 짚는다. GPU에서 순전파는 효율적으로 배치되는데 종단 지연이 CPU 바운드가 되어 꼬리 지연이 튄다는 것이다.

구조적 해결은 엔진 쪽 세대 교체에서 왔다. 로짓 처리가 배치 레벨로 옮겨졌고, 넷플릭스는 배치 자료구조에 맞춰 처리기를 다시 쓰고 핫 패스를 C++와 멀티스레딩으로 재구현해 잠금을 우회했다. 그 결과 배치가 커져도 로짓 처리 시간이 평평하게 유지됐다. 대가는 API 복잡도다. 배치 구성 변화를 명시적으로 추적해 줘야 해서 이전의 요청별 인터페이스보다 다루기 어렵다.

9.2 프로덕션에서만 드러난 두 가지

벤치마크에서는 보이지 않다가 실제 동시성에서 나온 문제 두 가지가 기록돼 있다. 둘 다 상태 기계의 전제가 깨지는 유형이다.

[문제 1] 부분 프리필
  청크 프리필로 한 요청이 여러 스텝에 걸쳐 프리필된다.
  배치 갱신 정보만으로는 완전 프리필인지 부분 프리필인지 구분되지 않는다.
  -> 내부에 진행 상태를 따로 추적하도록 보강

[문제 2] 되돌림에 의한 상태 리셋
  메모리 압박 시 엔진이 진행 중 요청의 KV 캐시를 회수하고
  나중에 다른 프롬프트와 출력 토큰 목록으로 다시 스케줄한다.
  상태 기계는 출력 토큰 목록이 단조 증가한다고 가정하고 있었다.
  -> 스텝 사이에 토큰 이력이 줄어드는 것을 감지하면
     상태 기계를 리셋하고 새 프롬프트로 재초기화

9.3 그런데 대부분의 조직은 여기까지 갈 필요가 없다

이 대목을 그대로 따라 하려는 판단은 위험하다. 커널 수준까지 내려가는 작업은 잘못된 생성의 비용이 재시도 비용보다 클 때만 정당화된다. 판단 기준은 세 가지로 정리된다.

  • 현재 유효 출력 비율 — 프롬프트와 스키마 지정만으로 몇 퍼센트가 통과하는가. 이 값이 이미 높으면 개선 여지가 작다.
  • 재시도 단가 — 실패 한 건을 다시 시키는 비용과 지연이 얼마인가. 짧은 출력이면 재시도가 싸다.
  • 지연 예산 — 재시도가 SLO 안에 들어오는가. 대화형이면 한 번의 재시도로 예산이 소진될 수 있다.

세 값이 모두 나쁜 쪽일 때만 디코드 개입이 이득이다. 그렇지 않다면 프롬프트 설계, 스키마 지정, 실패 시 재시도라는 평범한 조합이 유지보수 측면에서 더 낫다. 다만 어느 쪽을 택하든 구조화 출력 파라미터가 엔진까지 실제로 도달했는지 검증하는 테스트는 반드시 필요하다. 앞에서 본 조용한 누락 사례가 정확히 이 지점에서 발생했다.

10. 운영 지표 - 무엇을 보고 있어야 하는가

기존 웹 서비스 감각으로 p95 응답 시간 하나만 걸어 두면 LLM 서빙에서는 거의 아무것도 알 수 없다. 출력 길이가 제각각이라 분포가 섞이기 때문이다. 최소한 아래 지표들은 나눠서 봐야 한다.

지표정의무엇을 알려주는가기준을 잡는 법
첫 토큰까지의 시간요청 도착부터 첫 출력 토큰까지큐 대기와 프리필 상태대화형은 사용자 인지 임계로, 배치는 관리하지 않아도 된다
출력 토큰당 시간출력 토큰 사이의 평균 간격디코드 단계의 건강 상태사람이 읽는 속도보다 빠르면 체감 차이가 작다
종단 지연요청부터 완료까지전체 체감출력 길이 구간별로 나눠 본다
인스턴스당 출력 토큰 처리량초당 생성 토큰 수실제 용량배치 크기에 따라 변하므로 부하 수준을 함께 기록
KV 캐시 사용률할당된 KV 풀 중 사용 비율되돌림이 임박했는지지속적으로 고점이면 동시성을 낮추거나 카드를 늘린다
접두사 캐시 적중률재사용된 프리필 비율프롬프트 설계의 효과시스템 프롬프트에 변동 값이 섞이면 급락한다
대기 큐 길이스케줄되지 못한 요청 수포화 여부오토스케일 신호로 쓰기 좋다
되돌림 횟수KV 회수로 되돌려진 요청 수메모리 압박0에 가깝게 유지하는 것을 목표로 한다
GPU 사용률연산 유닛 점유율단독으로는 오해를 부른다디코드는 메모리 대역폭에 묶이므로 다른 지표와 함께 본다
굿풋목표 지연을 만족하며 완료된 초당 요청 수서비스 관점의 실제 능력처리량 대신 이 값으로 용량을 정의한다
  • 처리량 대신 굿풋을 본다. 배치를 키우면 처리량은 오르지만 목표 지연을 놓친 응답이 늘어날 수 있다. 지연 목표를 만족한 것만 세는 편이 서비스 실제 능력에 가깝다.
  • 길이 버킷별로 나눈다. 짧은 응답과 긴 응답을 한 히스토그램에 넣으면 p95가 무엇을 뜻하는지 알 수 없게 된다.
  • 지표는 엔진과 서버 양쪽에서 나온다. 합치는 계층을 만들지 않으면 기존 관측 자산을 그대로 쓸 수 없다는 것이 넷플릭스 사례의 핵심이다.
  • 토큰 회계를 처음부터 남긴다. 요청별 입력·출력 토큰 수를 로그에 남겨 두지 않으면 나중에 원가를 소급 계산할 수 없다.

11. 장애 시나리오와 1차 확인

운영을 시작하면 마주치게 되는 전형적인 상황들이다. 원인 후보를 미리 알고 있으면 대응 시간이 크게 줄어든다.

증상흔한 원인1차 확인재발 방지
배포가 아예 뜨지 않는다서버와 엔진의 버전 조합 불일치기동 로그의 모듈 임포트 오류, 직전 조합으로 롤백검증된 조합을 짝으로 고정
평균은 멀쩡한데 꼬리 지연만 튄다요청별로 순차 실행되는 CPU 단계배치 크기 대비 CPU 처리 시간 곡선배치 레벨 처리로 전환, 핫 패스 분리
처음엔 괜찮다가 서서히 느려진다KV 압박에 따른 되돌림 반복되돌림 카운터와 KV 사용률 추이동시성 상한 하향, 컨텍스트 상한 정비
새 노드가 헬스체크를 못 넘긴다가중치 다운로드로 인한 콜드 스타트기동 단계별 소요 시간, 아티팩트 경로워밍 캐시 또는 전용 파일 시스템 사용
출력 형식이 어긋난다구조화 출력 파라미터가 중간 계층에서 유실엔진 로그에 해당 파라미터가 실제로 도달했는지필드 단위 계약 테스트를 회귀에 포함
특정 요청만 메모리 부족을 낸다긴 컨텍스트 하나가 KV를 독점입력 길이 분포와 최대 컨텍스트 설정입력 길이 상한과 거절 정책 명문화
모델 교체 후 일부 소비자가 실패입출력 스키마 변경변경된 필드와 소비자 버전 대조버전 병행 배포 또는 버전 무관 인터페이스
배포 중 GPU가 모자란다병행 기간에 두 배 용량이 필요전환 기간 겹침 시간과 예약 용량배포 창에 여유 용량을 사전 확보

12. 손익분기를 스스로 계산하는 방법

「월 얼마부터는 자체 서빙이 싸다」거나 「하루 몇 토큰이 분기점이다」 같은 숫자가 여러 곳에 돌아다닌다. 그런데 그 수치들은 대개 가정이 공개되지 않은 채 제시된다. 어떤 GPU를 어떤 계약으로 쓰는지, 활용률을 몇 퍼센트로 뒀는지, 인건비를 포함했는지가 빠져 있으면 그 숫자는 다른 조직에 그대로 옮겨지지 않는다. 그래서 이 글은 특정 손익분기 수치를 인용하지 않고 계산 틀만 둔다.

[호스팅 API 쪽]
  월 비용 = (입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가) × 월 요청 수
           - 프롬프트 캐시 절감 - 배치 할인

[자체 서빙 쪽]
  월 비용 = GPU 시간 단가 × 인스턴스 수 × 730시간
           + 스토리지 + 네트워크 + 로드밸런서
           + 운영 인건비(FTE 환산)
           + 개발/스테이징 GPU
           + 배포 겹침 기간의 추가 용량

[비교 기준]
  토큰당 원가 = 월 비용 ÷ 실제로 처리한 월 토큰 수
  ※ 분모가 핵심이다. 활용률이 절반이면 토큰당 원가는 두 배가 된다.

계산 순서는 이렇게 잡는다.

  1. 시간대별 트래픽 분포부터 그린다. 피크와 평균의 비율이 이 계산의 지배 변수다.
  2. 목표 SLO에서 인스턴스당 굿풋을 실측한다. 벤치마크 없이 추정하면 이후 계산이 전부 흔들린다.
  3. 피크를 견딜 인스턴스 수를 구한다. 여기에 이중화 몫을 더한다.
  4. 그 인스턴스들이 평균 시간대에 얼마나 비는지를 계산해 실효 활용률을 낸다.
  5. 총비용을 월 처리 토큰으로 나눠 토큰당 원가를 낸다.
  6. 여기에 사람 비용을 더한다. 버전 조합 관리, 엔진 이슈 추적, 지표 통합은 일회성이 아니라 상시 업무다.

계산에서 자주 빠지는 항목들을 따로 적어 둔다.

  • 개발·스테이징 환경의 GPU. 프로덕션만 세면 실제 청구액과 어긋난다.
  • 배포 전환 기간에 겹쳐 뜨는 인스턴스 비용.
  • 모델 아티팩트 저장소와 고성능 파일 시스템 비용.
  • 리전 이중화 또는 장애 대비 예비 용량.
  • 벤치마크 자체에 드는 GPU 시간. 튜닝은 한 번으로 끝나지 않는다.
  • 야간·주말 대응 인력. 자체 서빙은 벤더에게 넘길 수 없는 장애가 생긴다.

흔한 오해도 세 가지 정리해 둔다.

  • 「오픈 웨이트라 공짜」 — 가중치가 무료인 것이지 서빙이 무료인 것이 아니다. 비용의 대부분은 GPU 시간과 사람 시간이다.
  • 「GPU 한 대 사면 끝」 — 이중화가 없으면 단일 장애점이 된다. 최소 구성이 한 대인 경우는 실험 환경뿐이다.
  • 「API 대비 절반」 — 이런 비교를 볼 때는 활용률 가정을 먼저 찾아봐야 한다. 100% 가동을 전제한 계산은 현실의 트래픽 분포에서 성립하지 않는다.

토큰 단가 자체를 어떻게 관리할지, 부서별로 어떻게 귀속시킬지는 이 글의 범위를 넘는다. 그 부분은 토큰 비용 통제 설계에서, 여러 모델을 상황에 따라 갈라 보내는 문제는 모델 라우팅에서 따로 다뤘다.

13. 결론: 플랫폼이 아니라 결정 목록을 먼저 만들어라

넷플릭스 사례에서 가져갈 것은 구성도가 아니다. 그 회사의 구성은 이미 있던 공용 추론 백엔드와 JVM 서빙 계층이라는 전제 위에 세워졌고, 그 전제가 없는 조직이 같은 그림을 그대로 그리면 오히려 손해다. 가져갈 것은 그들이 실제로 결정해야 했던 항목의 목록이다.

  1. LLM을 별도 스택으로 둘 것인가, 기존 모델 서빙에 모델 타입으로 편입할 것인가.
  2. 어떤 API 표면을 낼 것인가. 기존 인터페이스와 표준 호환 인터페이스를 병행할 것인가.
  3. 엔진을 성능으로 고를 것인가, 반복 속도와 디버깅 가능성으로 고를 것인가.
  4. 패키징을 어느 쪽으로 둘 것인가. 결합도를 낮추는 대신 버전 고정을 감수할 것인가.
  5. 배포를 레드-블랙으로 갈 것인가, 버전 병행으로 갈 것인가. 그 GPU 비용을 어디에 잡아 둘 것인가.
  6. KV 캐시 예산을 어떻게 나눌 것인가. 컨텍스트 상한과 동시성 중 무엇을 포기할 것인가.
  7. SLO를 첫 토큰과 토큰 간격으로 어떻게 쪼갤 것인가. 큐 대기 상한과 거절 정책은 무엇인가.
  8. 구조화 출력을 디코드 안에서 강제할 것인가, 후처리와 재시도로 감당할 것인가.
  9. 지표를 어디서 합칠 것인가. 기존 대시보드를 그대로 쓸 수 있게 만들 것인가.
  10. 가중치를 어떤 경로로 노드에 내릴 것인가. 콜드 스타트 예산은 얼마인가.

시작 순서를 제안하자면 이렇다. 먼저 자사 요청 분포로 실측 벤치마크를 돌려 인스턴스당 굿풋을 구한다. 그 값으로 SLO를 정의한다. 그다음 모델 하나, 워크로드 하나로 파일럿을 돌리되 지표 통합과 배포 전략을 파일럿 단계에서 같이 만든다. 이 둘을 나중으로 미루면 확장 시점에 되돌아와야 한다.

마지막으로 한 가지만 덧붙인다. 이 글에 나온 어떤 구성도 특정 성능을 보장하지 않는다. 엔진 버전, 모델 구조, 요청 길이 분포, 카드 세대가 조금만 달라져도 숫자가 바뀐다. 공개 사례는 무엇을 결정해야 하는지 알려 줄 뿐, 그 결정의 답을 알려 주지는 않는다. 답은 자사 트래픽으로 직접 재 보는 수밖에 없고, 그 측정 체계를 먼저 갖추는 것이 자체 서빙의 진짜 첫 단계다.
