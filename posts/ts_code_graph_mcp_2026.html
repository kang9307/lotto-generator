TS 컴파일러로 만든 코드 그래프 MCP - Claude Code 토큰을 10배 절감하다

코드를 읽지 않고 그래프를 조회하게 만들면 왜 토큰이 줄어드는가 - 원리와 한계를 분석한다

2026-07-02 개발/인프라

서론: 에이전트가 코드를 "읽는" 방식이 문제였다

GeekNews에 올라온 짧은 글 하나가 눈에 띄었다. TypeScript 컴파일러로 코드 그래프를 만들어 MCP(Model Context Protocol) 서버로 제공했더니, 같은 작업에서 Claude Code의 토큰 소비가 약 10배 줄었다는 내용이다. 포인트는 3점으로 소박했지만, 다루는 문제는 소박하지 않다. AI 코딩 에이전트를 실무에 붙여 본 사람이라면 누구나 한 번은 겪는 일 - 별것 아닌 질문 하나에 파일을 대여섯 개 열어 보고, grep을 몇 번 돌리고, 결국 컨텍스트 절반을 "코드를 찾는 데" 써 버리는 상황 - 을 정면으로 겨냥한 접근이기 때문이다.

본인은 이 글을 단순 요약이 아니라, MCP·컴파일러 API·기존 코드 인덱싱 방식을 실제로 조사하고 교차 확인한 뒤 쓴 자체 분석으로 정리한다. 2026년 7월 기준으로 코드 그래프 MCP류 도구가 이미 여러 개 나와 있고, 접근 방식과 주장하는 절감 폭도 제각각이다. 그 안에서 이 사례가 강조하는 "컴파일러 기반"이라는 선택이 왜 중요한지, 그리고 왜 토큰이 실제로 줄어드는지를 구조적으로 뜯어본다.

1. 코드 그래프와 MCP - 무엇을 하는 도구인가

코드 그래프 MCP를 한 문장으로 정리하면, 코드베이스를 미리 읽고 정리해 둔 지도를 에이전트에게 건네주는 도구다. 두 축으로 나눠 보면 이해가 쉽다.

1.1 코드 그래프 - 구조를 좌표로 바꾸는 작업

코드 그래프는 코드베이스의 심볼(함수·클래스·타입·변수)을 노드로, 그 사이의 호출·상속·임포트·타입 참조 관계를 엣지로 표현한 자료구조다. "이 함수를 누가 호출하는가", "이 타입을 어디서 쓰는가" 같은 질문에 파일을 뒤지지 않고 그래프를 따라가며 답할 수 있다. 핵심은 이 그래프를 실행 시점이 아니라 오프라인 인덱싱 단계에서 미리 만들어 둔다는 점이다. 에이전트가 질문을 받을 때마다 코드를 처음부터 분석하는 게 아니라, 이미 완성된 지도를 조회만 하면 된다.

1.2 MCP - 그 지도를 에이전트에게 건네는 표준 파이프

Model Context Protocol은 Anthropic이 2024년 11월 공개한 개방 표준으로, LLM 기반 에이전트가 외부 도구·데이터 소스와 통신하는 방식을 표준화한다. 코드 그래프를 MCP 서버로 감싸면, Claude Code 같은 에이전트는 정해진 프로토콜로 그래프에 질의를 던지고 구조화된 응답을 받는다. 2026년 현재 MCP는 Claude Code·Cursor·Codex·Windsurf 등 주요 코딩 도구 대부분이 지원하는 사실상 표준으로 자리 잡았다. 코드 그래프 자체는 오래된 아이디어(정적 분석 도구는 수십 년 전부터 있었다)지만, MCP라는 표준 인터페이스가 생기면서 "에이전트가 그래프를 직접 조회한다"는 조합이 비로소 실용적으로 굴러가게 됐다는 것이 본인의 해석이다.

1.3 이번 사례의 핵심 주장

원문이 강조하는 설계는 두 가지다. 첫째, 그래프 응답에 소스 코드 본문을 담지 않고 이름·엣지·시그니처·file:line 범위만 돌려준다. 둘째, 에이전트가 그래프를 무작정 탐색하지 않도록 체계적 추론 순서를 강제하는 장치를 뒀다. 8개 레포지토리와 4개 모델 조합으로 벤치마크한 결과 토큰 사용이 약 10배 줄었고 답변 품질은 유지됐다고 주장한다. 수치는 특정 벤치마크 환경의 결과이므로 절대치로 받아들이기보다 방향성 - "그래프를 매개하면 자릿수 단위 절감이 가능하다" - 로 읽는 게 맞다.

2. 왜 토큰이 절감되는가 - 탐색 비용의 정체

이 부분이 본인이 가장 흥미롭게 본 지점이다. 토큰 절감의 원천은 "생성"이 아니라 "탐색"에 있다.

2.1 에이전트의 탐색 비용은 생각보다 크다

실제로 Claude Code 같은 에이전트가 낯선 코드베이스에서 작업할 때 소모하는 토큰 중 상당 부분은 코드를 "찾는" 데 쓰인다. grep으로 후보를 찾고, glob으로 파일을 나열하고, 그 중 몇 개를 열어 보고, 원하는 게 아니면 다시 찾는 왕복이 반복된다. 이 반복 자체가 컨텍스트를 채운다. 200개 파일 규모의 코드베이스에서 한 시간 작업 중 탐색만으로 상당한 토큰이 소모된다는 관측도 있다 - 이는 "일" 자체가 아니라 "길 찾기"에 쓰이는 비용이다. 코드 그래프가 없다면 에이전트는 매번 이 탐색을 처음부터 반복한다.

2.2 압축된 응답이 만드는 차이

코드 그래프 MCP의 핵심은 파일 전체가 아니라 필요한 부분의 좌표만 돌려준다는 데 있다. "이 함수를 누가 호출하는가"라는 질문에 관련 함수 5개의 이름과 파일 위치만 오면, 에이전트는 그 좌표로 곧장 이동해 필요한 줄만 읽는다. 파일 전체를 여러 번 훑는 것과 정확한 좌표로 한 번에 도달하는 것의 토큰 차이는 코드베이스가 클수록 기하급수적으로 벌어진다. 10배라는 수치가 나온 것도, 대규모 레포에서 탐색 왕복이 애초에 많았기 때문에 그 비효율을 제거한 효과가 크게 나타난 것으로 해석하는 것이 합리적이다.

2.3 강제된 추론 순서의 역할

단순히 그래프를 제공하는 것만으로는 부족하다. 에이전트가 그래프를 받고도 습관적으로 파일 전체를 다시 읽거나, 관련 없는 노드까지 헤매며 탐색하면 절감 효과가 줄어든다. 원문이 언급한 "강제적 체계적 추론"은 에이전트에게 그래프 조회 → 대상 좁히기 → 필요한 지점만 읽기라는 순서를 프롬프트나 도구 설계로 강제하는 장치로 보인다. 이는 별도로 조사한 Chain-of-Thought 관련 연구에서도 확인되는 흐름과 맞닿아 있다 - 구조화되지 않은 추론은 오히려 토큰을 낭비할 수 있고, 정보 추출과 추론 단계를 분리해 구조를 강제하면 토큰을 큰 폭으로 줄이면서 품질을 유지할 수 있다는 결과들이 보고돼 있다. 즉 이 도구의 절감은 그래프라는 데이터 구조와 그것을 쓰는 방식을 강제하는 설계, 두 요소가 함께 작동한 결과로 보는 것이 맞다.

3. 왜 하필 TypeScript 컴파일러 API인가

2026년 현재 코드 그래프류 MCP 도구는 이미 여러 종류가 나와 있다. 조사하면서 확인한 바로는 Tree-sitter 기반 파서로 여러 언어를 지원하는 도구, 벡터 임베딩으로 의미적 유사 코드를 찾는 도구, 그리고 이번 사례처럼 언어별 컴파일러를 직접 쓰는 도구로 갈라진다. 이 갈림에서 컴파일러 API를 택한 이유를 짚어볼 가치가 있다.

3.1 휴리스틱 파서의 한계

Tree-sitter 같은 구문 분석기는 코드의 문법 구조(괄호가 어디서 열리고 닫히는지, 어떤 노드가 함수 선언인지)는 빠르고 정확하게 파악한다. 그러나 "이 변수가 실제로 어떤 타입인지", "이 임포트가 재노출(re-export)을 거쳐 결국 어디서 오는지", "제네릭이 어떻게 구체화되는지" 같은 의미 해석은 별개의 문제다. 문법만으로는 이런 관계를 정확히 풀어낼 수 없고, 휴리스틱을 쌓아 근사할 수밖에 없다. 근사는 필연적으로 오탐과 누락을 남긴다.

3.2 컴파일러는 이미 정답을 갖고 있다

TypeScript 컴파일러는 프로젝트를 실제로 빌드하기 위해 모든 모듈을 해석하고, 모든 타입을 추론하고, 모든 참조를 확정한다. 이 과정을 거친 결과물(타입 체커의 내부 상태)에는 "무엇이 무엇을 정확히 참조하는가"에 대한 답이 이미 들어 있다. 코드 그래프를 컴파일러 API 위에서 만든다는 것은, 이 답을 다시 추정하지 않고 그대로 가져다 쓴다는 뜻이다. 재노출 체인이 몇 단계를 거치든, 타입 별칭이 얼마나 복잡하든, 컴파일러가 이미 풀어낸 관계이므로 그래프의 엣지가 실제 코드 동작과 어긋날 가능성이 낮다. 이는 AutoBE 같은 다른 TypeScript 기반 AI 코딩 도구들이 "컴파일러를 API 레벨에서 임베드해 AI가 생성한 코드를 검증한다"는 방향을 택하는 것과 같은 맥락으로 읽힌다 - 코드에 대한 확정적 판단이 필요한 곳에서는 근사가 아니라 컴파일러의 정답을 쓴다는 원칙이다.

3.3 비용은 인덱싱 시점으로 이동한다

다만 공짜는 아니다. 컴파일러 기반 분석은 Tree-sitter보다 무겁고 느리다. 그러나 이 비용은 에이전트가 매 요청마다 지불하는 게 아니라, 인덱싱 단계에서 한 번(또는 코드 변경 시 증분으로) 지불된다. 즉 무거운 연산을 오프라인으로 미리 끝내 두고, 온라인에서는 가벼운 조회만 남기는 구조다. 이 시점 이동이야말로 코드 그래프 MCP 전반의 설계 철학이라고 본인은 판단한다.

4. 대규모 코드베이스에서의 가치

이 접근의 가치는 코드베이스 규모에 비례해서 커진다. 작은 사이드 프로젝트라면 파일을 몇 개 읽는 것과 그래프를 조회하는 것의 차이가 미미하다. 하지만 실무에서 다루는 코드베이스는 그렇지 않다.

4.1 파일 수가 늘수록 탐색 왕복이 조합적으로 늘어난다

파일이 200개, 2000개로 늘면 "관련 있어 보이는 파일"의 후보 집합도 함께 커진다. grep 한 번에 걸리는 라인 수, 훑어봐야 할 후보 파일 수가 모두 늘어난다. 코드 그래프는 이 조합적 증가를 미리 정리된 엣지 목록으로 흡수한다. 규모가 커질수록 "미리 정리해 둔 것"과 "매번 다시 찾는 것"의 격차가 벌어지므로, 대규모 모노레포·오래된 레거시 코드베이스일수록 절감 효과가 커질 것으로 본인은 예상한다.

4.2 리팩토링·영향 범위 파악에 특히 유효하다

"이 함수를 고치면 어디까지 영향이 가는가" 같은 질문은 본질적으로 그래프 순회 문제다. 코드 그래프가 있으면 이 질문에 파일을 뒤지는 대신 그래프의 역방향 엣지를 따라가며 정확히 답할 수 있다. 이는 앞서 조사한 유사 도구들(코드 리뷰용 그래프 등)이 공통으로 "영향 범위(blast radius) 파악"을 핵심 사용 사례로 내세우는 것과 일치한다. 대규모 리팩토링이나 코드 리뷰처럼 "이 변경이 어디에 닿는가"를 반복해서 물어야 하는 작업에서 그래프의 이득이 가장 뚜렷하게 나타난다.

4.3 온보딩과 문서화되지 않은 코드에서의 활용

문서가 부실하거나 원저자가 떠난 코드베이스에서 신규 합류자(사람이든 에이전트든)가 구조를 파악하는 데 드는 비용은 상당하다. 코드 그래프는 이런 상황에서 암묵적 구조를 명시적 데이터로 바꿔 준다. 사람에게도 유용하지만, 특히 컨텍스트가 제한된 AI 에이전트에게는 "구조를 몸으로 익힐 시간"이 없으므로 그래프가 사실상 대체 기억 역할을 한다.

5. 유사 접근과의 비교 - LSP, 벡터 인덱싱

코드 그래프 MCP가 유일한 해법은 아니다. 조사한 바로는 최소 세 갈래의 접근이 경쟁하고 있고, 각각 트레이드오프가 다르다.

5.1 LSP(Language Server Protocol)와의 차이

LSP는 에디터가 정의로 이동하거나 자동완성을 받기 위해 언어 서버와 통신하는 표준 프로토콜이다. TypeScript의 tsserver도 사실상 이 역할을 한다. 그러나 LSP는 "한 시점에 하나의 질의-응답"을 위해 설계됐다 - 커서가 있는 위치에서 정의가 어디인지, 여기서 쓸 수 있는 자동완성이 무엇인지를 묻는 식이다. 에이전트가 코드베이스 전체 구조를 파악하려면 이런 질의를 수백 번 왕복해야 하고, 그때마다 프로토콜 오버헤드와 왕복 지연이 쌓인다. 코드 그래프 MCP는 이 왕복을 없애고, 애초에 "구조 전체"를 한 번에 조회 가능한 형태로 미리 만들어 둔다는 점에서 다르다. LSP가 대화형 문답이라면 코드 그래프는 미리 만든 지도를 통째로 건네는 쪽에 가깝다.

5.2 벡터 임베딩 기반 인덱싱과의 차이

RAG(검색 증강 생성) 스타일로 코드를 임베딩해 의미적으로 유사한 조각을 찾는 접근도 널리 쓰인다. 이 방식은 "비슷한 걸 찾아줘" 같은 퍼지(fuzzy) 질의에 강하다. 하지만 "이 함수를 정확히 누가 호출하는가"처럼 확정적 관계가 필요한 질문에는 약하다. 임베딩 유사도는 근사치이지 정답이 아니기 때문이다. 코드 그래프는 반대로 확정적 관계에 강하고 퍼지 검색에는 약하다. 실무에서는 두 방식이 경쟁 관계라기보다 상호 보완 관계로 쓰일 가능성이 높다고 본인은 본다 - "비슷한 코드 찾기"는 임베딩에, "정확한 의존 관계 추적"은 그래프에 맡기는 식이다.

5.3 언어 범용성과의 트레이드오프

Tree-sitter 기반 도구들은 여러 언어를 한 프레임워크로 지원한다는 장점이 있다. 반면 컴파일러 API 기반 접근은 정확도는 높지만 언어마다 별도 구현이 필요하다. TypeScript는 컴파일러가 API 레벨로 공개돼 있고 타입 시스템이 강력해 이런 접근에 유독 유리한 언어라는 점도 짚어야 한다. 다른 언어에서 같은 수준의 정확도를 얻으려면 각 언어의 컴파일러·타입 체커를 동등하게 API로 노출해야 하는데, 모든 언어가 그런 인프라를 갖추고 있지는 않다.

결론: 규모가 클수록, 정확도가 중요할수록 볼 만하다

2026년 7월 기준으로 코드 그래프 MCP는 아직 표준이라기보다 빠르게 늘어나는 실험적 생태계에 가깝다. 이번 TypeScript 컴파일러 기반 사례가 흥미로운 이유는 "그래프를 미리 만들어 조회만 하게 한다"는 아이디어 자체보다, 컴파일러가 이미 확정한 정답을 그대로 그래프로 옮긴다는 선택에 있다. 근사가 아니라 확정, 매 요청 재계산이 아니라 오프라인 인덱싱, 이 두 가지 전환이 토큰 절감의 실질적 근거라는 것이 본인의 판단이다.

다만 10배라는 수치를 만능 지표로 받아들이는 것은 경계해야 한다. 벤치마크는 특정 레포·모델 조합의 결과이고, 소규모 프로젝트나 탐색 비용이 애초에 낮은 작업에서는 절감 폭이 훨씬 작을 수 있다. 또한 인덱싱 파이프라인을 추가로 운영해야 하는 부담, 컴파일러 기반 접근의 언어 종속성도 함께 고려해야 한다. 대규모 TypeScript 코드베이스에서 AI 에이전트로 반복적인 리팩토링·영향 분석 작업을 자주 한다면, 이런 코드 그래프 MCP를 직접 붙여 보고 본인 워크플로에서 토큰과 응답 품질을 함께 측정해 보는 것을 권한다. LSP나 임베딩 인덱싱을 이미 쓰고 있다면 대체가 아니라 병행을 검토하는 편이 현실적이다.
