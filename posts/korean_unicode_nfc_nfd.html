서론: 같은 이름 파일 두 개가 한 폴더에 있었다

파일 목록을 출력했더니 같은 이름이 두 번 나왔다. 사진.png와 사진.png. 글자 하나 다르지 않고, 공백도 없고, 확장자도 같다. 화면을 확대해도 구분되지 않는다. 그런데 운영체제는 둘을 서로 다른 파일로 취급하고 있었고, 실제로 내용도 달랐다.

파일 이름을 바이트로 찍어 보면 답이 나온다. 하나는 19바이트, 하나는 10바이트다. 같은 세 글자 이름인데 저장된 바이트 수가 두 배 차이 난다. 하나는 한글 음절을 미리 합성된 한 글자로 저장했고, 다른 하나는 초성·중성·종성을 따로 저장했다. 유니코드는 두 방식을 모두 허용한다. 화면에 그려질 때만 같은 모양이 된다.

이것이 유니코드 정규화 문제다. 그리고 이 문제의 실체는 「정규화를 안 했다」가 아니다. 어디서 누가 정규화할지 아무도 정하지 않았다는 것이다. 웹 폼에서 서버로, 서버에서 데이터베이스로, 데이터베이스에서 파일 시스템으로, 파일 시스템에서 압축 파일로, 압축 파일에서 다른 운영체제로. 문자열은 이 경계를 여러 번 넘는다. 각 경계에서 형식이 보존되는지, 아니면 바뀌는지, 누가 통일하는지가 정해져 있지 않으면 어딘가에서 반드시 깨진다.

이 글은 그 경계를 하나씩 넘어 보며 무엇이 깨지는지 직접 실행해 확인한 출력으로 짚는다. 결론을 미리 말하면 이렇다. 저장은 대체로 안전하다. 위험한 것은 경계다. 그리고 한국어 서비스에서 가장 자주 나는 사고는 파일명이 아니라 [가-힣] 정규식이다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045) / NTFS에서 실제로 실행한 결과다. 도구는 Node.js v22.16.0 (win32), Python 3.13.3, GNU bash 5.2.37 (MSYS2/MinGW64), GNU tar 1.35, Windows PowerShell 5.1이다. 예제 경로는 /tmp/demo 같은 자리표시자로 옮겨 적었다.

스크립트는 모두 파일로 저장해 실행했다. 한글과 역슬래시가 섞인 코드를 셸 인자로 넘기면 조용히 변형된다. 그 함정은 한글 정규식 함정에서 다뤘다.

이 글이 다루지 않는 것. 어미가 붙으면 앞 글자가 바뀌는 음절 합성 산술과 어미별 안전 패턴은 위 글에서 다뤘다. 파일명에 공백·개행이 섞여 파이프라인이 깨지는 문제는 find와 xargs의 공백 함정에서 다뤘다. 이 글은 같은 이름이 서로 다른 바이트열이 되는 문제만 파고든다. 정규식 방언과 이식성은 어디서나 동작하는 정규표현식에 있다.

1. 같아 보이는 두 문자열이 다르다 - 「글자 수」에 답이 세 개

먼저 사실 확인이다. 「한」을 결합형과 분해형으로 만들어 세 가지 길이를 나란히 재 봤다.

읽는 법은 이렇다. NFC의 「한」은 U+D55C 하나다. NFD의 「한」은 초성 히읗(U+1112), 중성 아(U+1161), 종성 니은(U+11AB) 세 개다. 그래서 바이트 길이가 3과 9로 갈린다.

  • 종성이 없는 「가」는 분해해도 2 코드포인트다. 즉 팽창률이 글자마다 다르다. 2배일 때도 있고 3배일 때도 있다
  • 「대한민국」은 4에서 11이 됐다. 네 글자 중 종성이 있는 것이 세 개라 4 곱하기 3이 아니다
  • 따라서 「글자 수 곱하기 3」 같은 어림 계산이 통하지 않는다. 실제로 세야 한다
  • UTF-8에서 결합형 음절과 분해형 자모는 모두 글자당 3바이트다. 팽창은 코드포인트 개수에서 온다

1.1 비교 연산자가 전부 다르다고 답한다

--- 1-4. 비교 ---
nfc === nfd                : false
nfc == nfd                 : false
Object.is(nfc, nfd)        : false
nfc.localeCompare(nfd)     : 0
JSON.stringify 동일        : false
Set([nfc,nfd]).size        : 2
Map 키 충돌하는가          : false

여기서 눈여겨볼 줄은 네 번째다. ===는 false인데 localeCompare는 0, 즉 「같다」를 돌려준다. 두 함수가 서로 다른 답을 하는 것이다.

이 불일치가 실무에서 어떻게 작용하는지가 중요하다. 정렬은 정상으로 보이는데 중복 제거는 실패한다. 목록을 localeCompare로 정렬하면 「한」 두 개가 나란히 붙는다. 사람이 보면 중복이 눈에 보인다. 그런데 Set이나 데이터베이스 유니크 인덱스는 바이트를 보므로 둘을 별개로 통과시킨다. 「정렬해 보면 붙어 있는데 중복 제거가 안 된다」는 현상이 여기서 나온다.

1.2 유니코드 표준은 이것을 어떻게 정의하나

유니코드 표준 부속서 15가 네 가지 정규화 형식을 정의한다. 정의를 그대로 옮기면 이렇다.

형식표준 정의한글에서 결과주로 쓸 곳
NFC정규 분해 후 정규 결합음절 1 코드포인트저장·비교·전송의 기본값
NFD정규 분해자모로 분리초성 검색 등 자모 단위 처리
NFKC호환 분해 후 정규 결합호환 자모를 조합용으로, 전각을 반각으로검색 색인 정규화
NFKD호환 분해위와 같고 분해 상태 유지드물게, 특수 색인

표준에서 한글과 직접 관련된 문장이 하나 있다. 한글 음절의 분해와 결합은 표 조회가 아니라 산술 알고리즘이다. 구현이 조회 표를 저장하지 않고 코드로 계산할 수 있게 만든 설계다. 실무적 함의는 분명하다. 예외가 없다. 특정 글자만 문제가 되는 것이 아니라 모든 한글 음절이 예외 없이 분해 가능하다. 영어권에서 정규화가 악센트 붙은 몇 글자의 문제인 것과 성격이 다르다. 한국어는 텍스트 전체가 대상이다.

코드포인트 이름을 보면 구조가 그대로 드러난다. HANGUL SYLLABLE HAN 하나가 CHOSEONG HIEUH + JUNGSEONG A + JONGSEONG NIEUN 셋으로 갈리는 것이다. Python의 unicodedata.is_normalized는 정규화하지 않고 형식만 판정하므로, 들어온 문자열의 상태를 로그로 남길 때 유용하다.

여기까지는 쉽다. 문제는 normalize를 어느 줄에 쓸 것인가다. 이것이 이 글의 본론이다. 흔한 실패는 두 가지 방향으로 나타난다.

  • 아무 데서도 안 한다 - 가장 흔하다. 개발 환경에서는 한 번도 분해형이 들어오지 않아 문제가 드러나지 않는다. 특정 사용자, 특정 기기, 특정 업로드 경로에서만 재현된다
  • 여기저기서 한다 - 문제가 터진 뒤 급하게 대응하면 이렇게 된다. 비교 직전마다 normalize를 붙이는 것이다. 동작은 하지만 붙이지 않은 한 곳이 남고, 그 한 곳을 찾는 데 몇 주가 걸린다
  • 정규화 여부가 계층마다 다르다 - 더 나쁜 경우다. 저장은 결합형인데 캐시 키는 원본, 검색 색인은 또 다른 형식이 된다. 세 곳이 서로 안 맞는다
  • 정규화했다고 믿지만 안 된 경우 - normalize()는 새 문자열을 돌려주는 함수다. 반환값을 쓰지 않고 호출만 하면 아무 일도 일어나지 않는다. 이 실수는 코드 리뷰에서 잘 안 보인다

표준 부속서 15가 제시하는 전략도 같은 방향이다. 각 구성 요소가 정규화된 입출력을 유지하도록 시스템 경계에서 형식을 보장하라는 것이다. 즉 정규화는 산발적 방어가 아니라 경계 계약이어야 한다. 아래 절들은 그 경계를 하나씩 실제로 넘어 본 기록이다.

  • 파일 시스템은 이름을 정규화하지 않았다. 분해형으로 준 이름이 분해형 그대로 저장되고, 목록 조회도 분해형으로 돌아왔다
  • 결합형 이름으로는 찾을 수 없다. ENOENT, 즉 그런 파일이 없다는 응답이다. 「분명히 있는데 없다고 한다」가 여기서 나온다
  • 같아 보이는 이름 두 개가 한 폴더에 공존한다. 서론의 그 화면이다

3.1 셸 리터럴로는 분해형 이름을 쓸 수 없다

분해형 파일 하나만 있는 디렉터리에서, 셸에 직접 이름을 타이핑해 접근해 봤다.

--- 3-13. 글로브로는 잡힌다 ---

세 줄이 각각 다른 것을 말한다.

  1. 타이핑한 이름은 결합형이 된다. 입력기와 편집기가 결합형을 만들기 때문이다. 그래서 실제 파일과 다른 문자열이 된다
  2. 오류 메시지가 이름을 알아볼 수 없게 표시한다. 셸이 매칭에 실패한 바이트를 이스케이프해 찍으므로 사람이 원인을 짐작하기 어렵다. 「이름을 잘못 쳤나」로 오해하고 몇 번을 다시 타이핑하게 된다
  3. 글로브는 성공한다. 글로브는 사람이 만든 문자열이 아니라 파일 시스템이 준 이름을 그대로 쓰기 때문이다. 정규화 문제가 생겼을 때 글로브가 되는데 직접 지정이 안 된다면 이 문제를 의심할 근거가 된다

메모리 안에서만 벌어지는 절반 실패도 있다. 두 형식이 섞인 목록에 접두 필터를 걸어 봤다.

3.2 그래서 macOS는 어떤가

여기서 통설이 하나 있다. macOS의 파일 시스템이 분해형 계열로 이름을 저장하고, 그래서 macOS에서 만든 압축 파일을 다른 운영체제에서 풀면 이름이 깨진다는 이야기다.

이 글에서는 확인하지 못했다. 확인 환경이 Windows와 NTFS뿐이므로 macOS의 동작을 실행으로 검증할 방법이 없었다. 그러므로 단정하지 않는다. 파일 시스템 종류와 운영체제 버전에 따라 동작이 다를 수 있으니 쓰는 환경에서 직접 확인해야 한다. 확인 방법은 위와 같다. 분해형 이름으로 파일을 만들고, 목록을 읽어 돌아온 이름의 코드포인트를 찍어 보면 된다. 세 줄이면 끝난다.

확인하지 않은 것을 문서에 적어 두면 그것이 다음 사람의 근거가 된다. 이 문제에서 실제로 위험한 것은 「어떤 OS가 어떻게 한다」는 지식이 아니라 내 코드가 어느 쪽이든 견디는가다. 견디게 만드는 방법은 하나다. 목록을 읽는 그 줄에서 정규화하는 것이다.

// 파일 목록을 읽는 경계에서 한 번
const names = fs.readdirSync(dir).map(n => n.normalize('NFC'));
// 이 아래로는 전부 NFC라고 가정하고 쓴다

4. ★검색 경계 - [가-힣]는 분해형 한글을 한 글자도 못 잡는다

여기가 이 글에서 가장 실용적인 부분이다. 파일명 문제는 겪는 사람이 정해져 있지만, 이 문제는 한국어를 다루는 거의 모든 코드에 있다.

[가-힣] 매칭이 2에서 0, 3에서 0이 된다. 부분적으로 덜 잡히는 것이 아니라 완전히 0이다. 이유는 범위 자체다. [가-힣]는 완성형 음절 영역 U+AC00부터 U+D7A3까지만 가리키는데, 분해형 자모는 U+1100 대역에 있어 범위 바깥이다.

세 번째 줄이 함정을 하나 더 보여 준다. 자모를 넣어 범위를 넓힌 [ㄱ-ㅎㅏ-ㅣ가-힣]도 0이다. 「자모까지 열었으니 분해형도 잡힐 것」이라는 기대가 틀렸다. 왜 틀렸는지는 9절에서 다룬다. 지금 필요한 결론은 하나다. 자모를 추가해도 해결되지 않는다.

4.1 검증기가 양방향으로 조용히 틀린다

--- 5-2. 검증기가 조용히 통과한다 ---
NFC 사용자이름  ^[가-힣]+$ 통과 : true    | 한글 섞임 탐지 : true
NFD 사용자이름  ^[가-힣]+$ 통과 : false   | 한글 섞임 탐지 : false

두 줄이 서로 반대 방향의 사고다. 같은 이름인데 형식만 다르다.

  • 「한글만 허용」 검증기 - 분해형 이름을 거부한다. 사용자는 정상적인 한글 이름을 넣었는데 「한글만 입력하세요」라는 오류를 받는다. 화면에 보이는 것은 분명히 한글이므로 사용자는 무엇이 문제인지 알 수 없다. 문의가 들어와도 재현되지 않는다
  • 「한글 혼입 탐지」 필터 - 분해형 한글을 못 잡는다. 다국어 페이지에 한국어가 섞여 들어갔는지 검사하는 도구, 금칙어 필터, 언어 판별기가 여기 걸린다. 검사기는 「이상 없음」을 돌려주고 아무도 의심하지 않는다
  • 후자가 훨씬 위험하다. 전자는 사용자가 항의하므로 언젠가 발견되지만, 후자는 항의할 사람이 없다. 결과가 실패가 아니라 성공의 모양을 하고 있다
  • 같은 뿌리에서 금칙어 필터 우회가 나온다. 걸러야 할 단어를 분해형으로 넣으면 결합형 기준 필터를 그냥 통과한다. 화면에는 그 단어가 그대로 보인다

4.2 검색어와 본문의 형식이 어긋날 때

--- 5-3. NFD 텍스트에서 NFC 패턴으로 검색 ---
본문 형식        : NFD (코드포인트 26개)
검색어 형식      : NFC (코드포인트 3개)
doc.includes(pat)                        : false
new RegExp(pat).test(doc)                : false
doc.indexOf(pat)                         : -1
양쪽 NFC 정규화 후 includes              : true
양쪽 NFD 정규화 후 includes              : true

주목할 것은 마지막 두 줄이다. 양쪽을 결합형으로 맞추든 분해형으로 맞추든 검색은 성공한다. 즉 어떤 형식을 고르느냐는 이 문제의 본질이 아니다. 양쪽이 같은 형식인가가 전부다. 그래서 「NFC가 정답이다」라고 외우는 것보다 「비교하는 두 값이 같은 경계를 지나왔는가」를 묻는 습관이 실질적으로 더 강하다.

명령줄에서도 확인했다. 같은 내용을 두 형식으로 저장한 파일에 grep을 걸었다.

--- 5-6. 두 파일 크기 (같은 내용, 다른 바이트) ---
 37 nfc.txt
 79 nfd.txt
--- 5-7. NFC 패턴으로 grep ---
nfc.txt 에서 grep 강남구 : 찾음
nfd.txt 에서 grep 강남구 : 못 찾음
--- 5-9. 첫 12바이트 비교 ---
nfc.txt 앞 12바이트 :  ec 84 9c ec 9a b8 ec 8b 9c 20 ea b0
nfd.txt 앞 12바이트 :  e1 84 89 e1 85 a5 e1 84 8b e1 85 ae
--- 5-10. 정규화해서 다시 grep ---
nfd_fixed.txt 에서 grep 강남구 : 찾음
--- 5-12. 본문의 실제 한글 글자 수 (Node 기준) ---

같은 한 줄이 37바이트와 79바이트다. 그리고 결합형 검색어로는 분해형 파일에서 아무것도 못 찾는다. 로그 검색, 소스 코드 검색, 배치 필터가 전부 이 지점을 지난다. 「그 로그에 그 문자열이 없다」는 결론이 실제로는 「형식이 달랐다」일 수 있다.

4.3 grep의 문자 클래스에는 함정이 하나 더 있다

실행 중에 예상하지 않은 숫자가 나왔다. 정직하게 적어 둔다.

--- 5-13. C 로케일 grep -o [가-힣] (바이트로 해석된다) ---
LC_ALL=C  nfc.txt : 30
LC_ALL=C  nfd.txt : 72

본문의 한글은 10글자인데 grep -o "[가-힣]"가 30을 셌다. 30은 그 10글자의 UTF-8 바이트 수다. 즉 이 grep은 대괄호 범위를 글자 범위가 아니라 바이트 범위로 해석하고 있었다. 72도 같은 방식으로 나온 분해형 쪽 바이트 수다.

  • 따라서 이 숫자는 한글 글자 수로 읽으면 안 된다. 로케일 설정에 따라 도구가 멀티바이트 문자를 글자로 볼 수도, 바이트로 볼 수도 있다
  • 글자 수를 세는 목적이라면 셸 도구에 의존하지 말고 유니코드를 아는 런타임에서 세는 것이 안전하다. 위 출력에서 Node 기준 값이 10과 0으로 명확하다
  • 고정 문자열 검색(-F)은 로케일과 무관하게 바이트 비교다. 그래서 형식이 다르면 무조건 못 찾는다. 이쪽은 오히려 예측 가능하다
  • 교훈은 「도구가 한글을 한 글자로 세는지 확인하고 쓴다」다. 확인 방법은 아는 개수의 표본을 넣어 결과를 대조하는 것이다

  • 페이지네이션이 어긋난다. 정렬 기준이 흔들리면 커서 기반 페이징에서 항목이 중복되거나 건너뛰어진다
  • localeCompare로 정렬하면 순서는 맞는다. 그래서 정렬만 보고 「문제없다」고 판단하기 쉽다
  • 그런데 순서가 맞는 것과 같은 항목으로 취급하는 것은 다른 문제다. 1절에서 본 Set.size = 2가 그대로 남아 있다

정리하면 비교 계층이 둘로 갈라져 있다. 사람에게 보여 주는 정렬·검색은 정규화를 감안하고, 데이터 무결성을 지키는 동일성 판정은 바이트를 본다. 두 계층이 서로 다른 답을 하는 시스템에서는 「목록에는 하나로 보이는데 저장소에는 둘 있다」는 상태가 정상적으로 유지된다. 중복 계정, 중복 태그, 중복 카테고리가 이렇게 생긴다.

--- 6-3. 「3자 이상」 검증이 NFD를 뚫는다 ---

최소 길이 검증이 한 글자 입력을 통과시켰다. 분해형 「한」의 코드 단위 길이가 3이기 때문이다. 최대 길이 검증은 정상 입력을 거부해 사용자가 항의하지만, 최소 길이 검증은 부적합 입력을 통과시키므로 아무도 항의하지 않는다. 4절의 구조와 같다. 조용한 쪽이 더 위험하다.

--- 6-4. 자르기가 글자를 반토막 낸다 ---
NFD 한국어 slice(0,2)  : "하"  ← 종성이 떨어져 나갔다
NFD 자른 뒤 NFC 정규화 : "하"  ← 정규화해도 복구되지 않는다
--- 6-5. Segmenter 단위로 안전하게 자르기 ---
권장 순서 : NFC 정규화 → Segmenter 로 자르기
정규화 먼저 한 결과 : "한" (코드포인트 1)

「한」이 「하」가 됐다. 종성 니은이 잘려 나간 것이다. 그리고 두 번째 줄이 중요하다. 자른 뒤에 정규화해도 복구되지 않는다. 정규화는 없어진 종성을 되살릴 수 없다. 이것이 이 글의 다른 함정들과 성격이 다른 이유다.

  • 비교·검색·정렬 실패는 나중에 정규화하면 고쳐진다. 데이터가 남아 있기 때문이다
  • 자르기는 데이터를 버린다. 나중에 고칠 수 없다. 미리보기 텍스트, 요약, 알림 메시지, 로그 절단이 모두 여기 해당한다
  • 그래서 순서가 정해진다. 정규화가 먼저, 자르기가 나중이다. 이 순서는 협상 대상이 아니다
  • 이모지·국기·결합 문자까지 안전하게 다루려면 자소 클러스터 단위로 잘라야 한다. Intl.Segmenter가 그것이다

일곱 글자가 21바이트와 54바이트다. 컬럼을 바이트 기준으로 잡는 환경에서 VARCHAR(30)이면 결합형은 넉넉하고 분해형은 넘친다. 데이터베이스가 던지는 오류는 「데이터가 너무 깁니다」일 뿐, 정규화를 지목하지 않는다. 일곱 글자 이름이 30바이트를 넘겼다는 오류를 받으면 정규화를 의심할 근거가 된다.

지금까지 본 것은 깨지는 경계였다. 이제 안 깨지는 경계를 확인할 차례다. 그런데 「안 깨진다」가 좋은 소식이 아니라는 것이 이 절의 요지다.

node v22.16.0 / win32

JSON 직렬화와 파일 입출력은 형식을 그대로 통과시킨다. 분해형으로 넣으면 분해형으로 나온다. 바이트를 직접 확인해도 두 형식이 한 파일 안에 나란히 들어 있다.

이것이 왜 나쁜 소식인가. 왕복 어디에서도 정규화가 일어나지 않는다는 뜻이다. 「저장했다 읽으면 정리될 것」이라는 막연한 기대가 근거 없다는 것이 확인됐다. 분해형은 한 번 들어오면 시스템 밖으로 나갈 때까지 그대로 남는다. 저장소를 거치면서 스스로 통일되는 일은 없다.

7.1 객체 키가 갈리면 값이 묻힌다

--- 7-2. JSON 객체 키가 NFC/NFD로 갈리면 ---
키 개수                    : 2 ← 같은 이름인데 2개
키 목록 코드포인트 수      : 3, 8
parse 후에도 키 2개인가    : true
obj['한국어'] 로 읽으면    : NFC 값 ← NFD 값은 조용히 묻힌다

같은 이름 키가 두 개 만들어졌고, 결합형으로 읽으면 결합형 값만 나온다. 분해형 값은 객체 안에 존재하지만 접근되지 않는다. 설정 파일, 번역 사전, 매핑 테이블, 캐시가 모두 이 구조다. 「설정을 넣었는데 적용이 안 된다」의 원인이 여기일 수 있다. 파일을 열어 봐도 키는 분명히 있으므로 원인 추적이 어렵다.

7.2 URL과 해시는 형식을 그대로 노출한다

--- 7-6. URL 인코딩 ---
NFC URL : %ED%95%9C%EA%B5%AD%EC%96%B4
NFD URL : %E1%84%92%E1%85%A1%E1%86%AB%E1%84%80%E1%85%AE%E1%86%A8%E1%84%8B%E1%85%A5
--- 7-7. 해시가 갈린다 ---
sha256(NFC 한국어) : ea3252281bc3bcec
sha256(NFD 한국어) : 4cbdf1837a1d7592
해시가 같은가      : false
정규화 후 해시 같은가 : true

같은 검색어가 완전히 다른 URL이 된다. 결과가 이어진다.

  • 캐시가 갈린다 - CDN과 애플리케이션 캐시가 두 URL을 별개 자원으로 본다. 적재율이 떨어지고 원인이 안 보인다
  • 분석 지표가 갈린다 - 같은 검색어의 유입이 두 줄로 집계된다. 상위 검색어 목록에서 순위가 내려가고 실제 인기도가 과소평가된다
  • 정규 URL이 흔들린다 - 같은 문서가 두 주소를 갖게 되면 검색 노출이 나뉜다
  • 해시가 갈린다 - 무결성 검증, 서명, 중복 파일 판정이 실패한다. 「같은 파일인데 해시가 다르다」가 된다
  • 해시를 쓰는 자리에서는 형식을 규약으로 고정해야 한다. 「서명 전 NFC로 정규화한다」를 문서에 못 박지 않으면 검증 측과 서명 측이 다른 답을 낸다

결론은 명확하다. 확인한 환경에서 tar도 zip도 이름을 정규화하지 않았다. 분해형 9 코드포인트가 담을 때도 풀 때도 그대로였고, 바이트까지 완전히 일치했다.

그리고 이것이 이 글의 논지를 가장 잘 보여 주는 결과다. 압축 도구는 충실한 운반자다. 아무것도 고치지 않고 아무것도 망가뜨리지 않는다. 그래서 분해형 이름은 손상 없이 목적지까지 도착한다. 사고는 압축에서 나지 않는다. 도착한 그 이름을 결합형 문자열로 찾으려는 다음 소비자에게서 난다.

  • 압축 파일을 받아 푸는 자동화가 있다면, 푼 직후 목록을 읽는 그 줄이 정규화 지점이다
  • 압축 파일을 만드는 쪽이라면 담기 전에 이름을 통일하는 것이 더 낫다. 소비자가 여러 곳이면 한 곳에서 고치는 것이 싸다
  • 목록 출력이 이름을 이스케이프해 보여 줄 수 있다. 실제로 tar -tf 출력에서 분해형 이름이 알아보기 어려운 형태로 표시됐다. 목록 표시가 이상하다고 파일이 깨진 것은 아니다. 위 8-4에서 바이트 일치가 확인됐다
  • 도구와 버전에 따라 동작이 다를 수 있다. 압축 형식에는 이름 인코딩 관련 옵션이 있는 경우도 있으므로 쓰는 도구로 직접 확인하는 것이 맞다. 확인은 위처럼 코드포인트를 찍어 보면 끝난다

9. 자모의 종류와 NFKC - 넓히려다 더 잃는다

4절에서 남긴 질문에 답할 차례다. 자모를 넣어 범위를 넓힌 [ㄱ-ㅎㅏ-ㅣ가-힣]가 왜 분해형을 못 잡았나.

node v22.16.0 / win32
--- 9-1. 세 종류의 「ㄱ」 ---
구분                    출력    [가-힣]   Hangul   utf8
-------------------------------------------------------
호환 자모 (U+3131)      ㄱ            X        O      3
조합용 초성 (U+1100)    ᄀ            X        O      3
조합용 종성 (U+11A8)    ᆨ              X        O      3
--- 9-2. NFD는 호환 자모를 쓰지 않는다 ---
NFD('가') 첫 글자 : U+1100  ← 조합용 초성
호환 자모 ㄱ      : U+3131
둘이 같은가       : false
NFD('가나다') 에서 [ㄱ-ㅎㅏ-ㅣ] 매칭 수 : 0
NFD('가나다') 에서 [ᄀ-ᇿ] 매칭 수 : 6

답이 나왔다. 「ㄱ」이 세 종류다. 키보드로 자음만 눌렀을 때 나오는 것은 호환 자모 U+3131이고, 분해형이 쓰는 것은 조합용 초성 U+1100이며, 종성 자리는 또 다른 U+11A8이다. 셋은 화면에 비슷하게 보이지만 서로 다른 문자다.

  • 정규식에 [ㄱ-ㅎ]를 쓰면 호환 자모 범위를 여는 것이다. 분해형과 무관하다
  • 분해형을 잡으려면 [ᄀ-ᇿ] 대역을 열어야 한다. 위 출력에서 6개를 잡았다
  • 초성과 종성이 다른 코드포인트라는 점도 함정이다. 종성 「ㄱ」을 초성 「ㄱ」으로 검색하면 안 걸린다
  • 가장 넓게 여는 방법은 \p{Script=Hangul}이다. 4절 표에서 유일하게 양쪽을 다 잡았다
  • 다만 넓게 여는 것이 항상 정답은 아니다. 사용자 이름 검증이라면 조합 중인 자모를 거부해야 할 수도 있다. 무엇을 통과시킬지 먼저 정하는 것이 순서다

9.1 NFKC가 추가로 바꾸는 것

「그럼 NFKC로 다 통일하면 되지 않나」라는 생각이 나올 지점이다. 무엇이 바뀌는지 실제로 봐야 한다.

--- 9-3. NFC/NFD는 호환 자모를 건드리지 않는다 ---
입력        NFC       NFD       NFKC      NFKD
U+3131 ㄱ   U+3131    U+3131    U+1100    U+1100
U+3158 ㅘ   U+3158    U+3158    U+116A    U+116A
--- 9-4. NFKC가 추가로 바꾸는 것들 ---
구분                원본    NFC     NFKC      변경됨
----------------------------------------------------
전각 영문 ＡＢＣ    ＡＢＣ  ＡＢＣ  ABC       O
전각 숫자 １２３    １２３  １２３  123       O
로마숫자 Ⅷ          Ⅷ       Ⅷ       VIII      O
원문자 ㈜           ㈜      ㈜      (주)      O
단위 ㎉             ㎉      ㎉      kcal      O
합자 ﬁ              ﬁ       ﬁ       fi        O
--- 9-5. NFKC는 되돌릴 수 없다 ---
'㈜'.normalize('NFKC') = (주)  (코드포인트 3개)
원본으로 되돌릴 방법이 있는가 : 없다 (정보가 손실된다)

첫 표가 중요한 사실을 말한다. NFC와 NFD는 호환 자모를 건드리지 않는다. U+3131은 정규 분해에서 그대로 남는다. 바꾸는 것은 NFKC와 NFKD뿐이다.

그리고 두 번째 표를 보면 NFKC가 얼마나 많은 것을 함께 바꾸는지 알 수 있다. 원문자 「㈜」가 세 글자 (주)가 되고, 단위 「㎉」가 kcal이 된다. 되돌릴 방법은 없다. 표준 부속서 15도 이 점을 명시한다. 호환 정규화 형식을 임의의 텍스트에 무턱대고 적용해서는 안 된다는 것이다. 많은 서식 구분을 지우기 때문이다.

  • NFKC는 검색 색인용으로는 유용하다. 전각으로 입력한 검색어가 반각 본문에 걸리게 해 준다
  • 그런데 저장·표시용 원본에는 쓰지 않는다. 회사명 「㈜」가 (주)로 바뀌어 저장되면 되돌릴 수 없다
  • 실무 구성은 원본은 NFC로 저장하고, 색인만 NFKC로 별도 생성하는 것이다. 두 값을 함께 갖는다
  • 즉 정규화 형식은 계층마다 다를 수 있다. 다만 각 계층에서 어떤 형식인지가 명시돼 있어야 한다

9.2 한글만의 문제가 아니다

--- 9-6. 이모지·결합 문자도 같은 문제 ---

「é」도 같은 구조다. 합성형 한 코드포인트와, e에 악센트 기호를 붙인 두 코드포인트가 있다. 화면에는 같게 보이고 ===는 false다. 이 글의 모든 처방이 그대로 적용된다.

이모지 쪽은 조금 다르다. 가족 이모지는 코드 단위 8, 코드포인트 5, 자소 클러스터 1이다. 이쪽은 정규화로 통일되는 문제가 아니라 애초에 여러 코드포인트로 이뤄진 하나의 글자다. 그래서 Intl.Segmenter가 필요한 이유가 정규화와 별개로 하나 더 생긴다. 「사람에게 보이는 글자 수」를 세는 유일하게 안전한 방법이 자소 클러스터라는 결론은 양쪽에서 같다.

10.1 왜 「한 번만」인가

여러 곳에서 정규화하면 왜 문제인가. 동작 자체는 하는데도 권하지 않는 이유가 있다.

  1. 누락 지점이 반드시 생긴다. 비교하는 자리마다 정규화를 붙이는 방식은 새 코드가 추가될 때마다 다시 붙여야 한다. 한 곳을 빠뜨리면 그 한 곳만 조용히 틀린다
  2. 불변 조건을 말할 수 없게 된다. 경계에서 한 번 정규화하면 「이 안쪽 문자열은 모두 결합형」이라는 문장을 쓸 수 있다. 여기저기서 하면 그런 문장을 쓸 수 없고, 코드를 읽는 사람이 매번 추적해야 한다
  3. 정규화 여부 자체가 조건 분기가 된다. 「여기는 정규화됐나」를 묻는 코드가 생기기 시작하면 이미 설계가 무너진 것이다
  4. 원본 보존이 필요한 자리와 충돌한다. 서명 검증이나 원본 재현이 필요하면 정규화 전 값을 따로 보관해야 한다. 정규화 지점이 하나면 「그 앞이 원본」이라고 말할 수 있다
  5. 비용은 실제로 문제가 아니다. 정규화는 멱등이고, 이미 정규화된 문자열에 다시 걸어도 결과가 같다. 그래서 성능이 아니라 책임 소재가 이유다

10.2 진단 순서

실제로 의심 상황이 생겼을 때 순서는 이렇다. 위에서 아래로 세 단계면 대체로 판명된다.

  1. 바이트를 찍는다. 문자열이나 파일명을 od로 보거나 코드포인트를 출력한다. e1 84로 시작하는 3바이트 묶음이 이어지면 분해형이다. ec·ed로 시작하면 결합형이다
  2. 길이를 세 가지로 센다. 코드 단위, 코드포인트, 자소 클러스터가 갈리는지 본다. 앞 둘이 자소 수보다 크면 분해형이다
  3. 양쪽을 정규화해 비교한다. 정규화 후 같아지면 원인이 확정된다. 이 한 줄이 진단의 끝이다
  4. 원인이 확정되면 고칠 위치는 위 표에서 고른다. 증상이 난 자리가 아니라 그 값이 들어온 경계를 고친다

11. 이 글에서 확인하지 못한 것

균형을 위해 한계를 밝힌다. 확인하지 않은 것을 확인한 것처럼 적으면 이 글이 다음 사람을 잘못 이끈다.

  • macOS와 다른 파일 시스템의 동작. 확인 환경이 Windows와 NTFS뿐이었다. macOS가 분해형 계열로 저장한다는 통설은 검증하지 못했으므로 단정하지 않는다. 3.2절의 방법으로 각자 확인하는 것이 맞다
  • Linux의 여러 파일 시스템. 확인하지 않았다. 일반적으로 파일명을 바이트열로 다룬다고 알려져 있으나 실행으로 확인한 바가 없다
  • zip 명령의 동작. 이 환경에 zip이 없어 PowerShell로 대체했다. zip·unzip 구현마다 이름 인코딩 처리가 다를 수 있다
  • 데이터베이스별 동작. 특정 데이터베이스가 저장 시점에 정규화하는지는 확인하지 않았다. 조합·정렬 규칙 설정에 따라 다를 수 있으므로 쓰는 제품에서 확인해야 한다
  • 브라우저 입력기별 동작. 어떤 입력 경로가 분해형을 만드는지는 실행으로 확인하지 않았다. 다만 어느 쪽이 오든 견디게 만드는 것이 처방이므로 실무적으로는 알 필요가 적다
  • 정규화 성능. 대량 텍스트에서 정규화 비용이 유의미한지는 측정하지 않았다. 측정 없이 성능을 이유로 정규화를 생략하는 것은 권하지 않는다

다만 확인하지 못한 것들의 공통점이 하나 있다. 전부 「저쪽이 어떻게 하는가」에 관한 질문이다. 그리고 이 글의 처방은 저쪽의 동작을 알아야 성립하는 것이 아니다. 경계에서 정규화하면 저쪽이 어느 형식을 보내든 상관없어진다. 그것이 경계 계약을 쓰는 이유다.

결론: 문제는 저장이 아니라 경계다

이 글의 출발점은 한 폴더에 있던 같은 이름 파일 두 개였다. 원인은 인코딩 설정도, 파일 시스템 버그도, 특정 도구의 결함도 아니었다. 유니코드가 같은 글자를 두 가지로 표현할 수 있게 허용하고, 아무도 어디서 통일할지 정하지 않았다는 것이었다.

실행해서 확인한 것을 정리하면 이렇다. 저장 계층은 대체로 충실하다. JSON도, 파일 입출력도, tar도, zip도 형식을 그대로 옮긴다. 아무것도 망가뜨리지 않는다. 그래서 분해형은 한 번 들어오면 시스템 밖으로 나갈 때까지 살아남는다. 사고는 그것이 결합형을 기대하는 코드와 만나는 지점에서 난다. 파일을 찾는 줄, 정규식을 돌리는 줄, 길이를 세는 줄, 해시를 만드는 줄이다.

그중 한국어 서비스에서 압도적으로 자주 나는 것은 [가-힣]가 분해형을 한 글자도 못 잡는 것이다. 2에서 0, 3에서 0이다. 자모를 넣어 범위를 넓혀도 여전히 0이다. 그리고 이 실패는 예외를 던지지 않는다. 검증기는 통과시키고, 필터는 못 잡고, 검사기는 「이상 없음」을 돌려준다. 결과가 실패가 아니라 성공의 모양을 하고 있다.

그래서 결론은 「정규화해라」가 아니다. 정규화 지점을 하나 정하고, 그 지점을 문서에 적어라에 가깝다. 비교 직전마다 방어하는 방식은 반드시 한 곳을 빠뜨린다. 경계에서 한 번 통일하면 그 안쪽에 대해 「이 안의 문자열은 전부 결합형이다」라는 한 문장을 쓸 수 있다. 그 문장이 있는 코드와 없는 코드의 차이가 이 문제의 전부다.

지금 당장 할 수 있는 일이 하나 있다. 한국어 문자열을 [가-힣]로 검사하는 코드를 저장소에서 찾아, 그 자리에 분해형 표본 하나를 넣어 돌려 보라. 통과해야 할 것이 거부되거나, 걸려야 할 것이 통과하면 그 검증기는 지금까지 절반만 일하고 있었던 것이다. 그리고 고칠 자리는 그 정규식이 아니라, 그 문자열이 들어온 경계다.

# 유니코드 정규화 경계 점검표 (NFC·NFD)

> 출처: braindetox.kr — 한글이 자모로 분리되는 순간, NFC와 NFD
> 표준 근거: Unicode UAX #15(정규화 형식), UAX #29(자소 클러스터)
> 쓰는 법: 한글이 지나가는 경로를 위에서 아래로 훑는다. 각 경계에서 「누가 정규화하는가」에 답이 없으면 그 자리가 사고 지점이다.
> 이 파일을 그대로 AI에 붙여 「우리 코드 기준으로 점검해줘」라고 써도 된다.

## 0. 30초 판정 — 하나라도 해당하면 전 항목을 본다

- [ ] 한글 문자열을 비교·검색·정렬한다
- [ ] 사용자 입력·파일명·외부 API에서 한글이 들어온다
- [ ] 「글자 수」를 세거나 문자열을 자른다
- [ ] 파일을 이름으로 찾는다
- [ ] 해시·서명·캐시 키에 한글이 들어간다
- [ ] 압축 파일을 주고받는다

## 1. 핵심 사실 3줄

1. 같은 「한」이 1 코드포인트(U+D55C)일 수도, 3 코드포인트(U+1112 U+1161 U+11AB)일 수도 있다
2. 화면 출력은 완전히 동일하다. 눈으로는 절대 구분할 수 없다
3. 한글 음절의 분해·결합은 산술 알고리즘이라 **예외가 없다**. 모든 음절이 대상이다

## 2. 경계별 판단표 — 어디서 무엇이 깨지나

| 경계 | 무엇이 깨지나 | 정규화 위치 |
|---|---|---|
| 웹 폼 → 서버 | 길이 검증 3배, 정규식 검증 반전 | 서버 수신 직후 NFC |
| 외부 API 수신 | 송신 측 형식을 통제 불가 | 파싱 직후 NFC |
| 파일 목록 읽기 | 목록이 분해형으로 옴, 접두 필터 절반 누락 | readdir 결과 즉시 NFC |
| 파일 쓰기 | 같아 보이는 이름 파일 2개 생성 | 경로 조립 전 NFC |
| 압축 → 해제 | 이름은 보존됨, 다음 소비자에서 깨짐 | 담기 전 NFC 또는 푼 직후 |
| DB 저장 | 유니크 인덱스가 같은 이름을 2개로 봄 | 이미 정규화 가정, 불가하면 저장 직전 |
| 검색 색인 생성 | 분해형 문서가 색인 누락 | 색인 전 NFC |
| URL·쿼리 생성 | 같은 검색어가 다른 URL, 캐시·지표 분산 | 링크 생성 전 NFC |
| 해시·서명 | 같은 글자가 다른 해시 | 규약 고정 후 서명 전 NFC |
| 자르기·요약 | 종성 절단, **복구 불가** | 정규화 먼저, 자르기 나중 |
| 화면 출력 | 아무것도 깨지지 않음 | 하지 말 것 (이미 늦다) |

## 3. 진단 명령 — 바이트와 코드포인트 확인

### 3.1 셸에서 파일명 바이트 보기

```
# 파일명 바이트 확인
for f in *; do printf '%s : ' "$f"; printf '%s' "$f" | od -An -tx1; done

# 판독법
#   e1 84 / e1 85 / e1 86 으로 시작하는 3바이트 묶음 반복 → 분해형(NFD)
#   ec / ed 로 시작하는 3바이트 → 결합형(NFC)
```

### 3.2 문자열 상태 판정 (Node)

```
const cps = s => [...s].map(c => 'U+' + c.codePointAt(0).toString(16).toUpperCase()).join(' ');
console.log(cps(s));
console.log('코드유닛', s.length);
console.log('코드포인트', [...s].length);
console.log('바이트', Buffer.byteLength(s, 'utf8'));
console.log('자소', [...new Intl.Segmenter('ko', {granularity:'grapheme'}).segment(s)].length);
console.log('이미 NFC인가', s === s.normalize('NFC'));
```

### 3.3 문자열 상태 판정 (Python)

```
import unicodedata
print(len(s), len(s.encode('utf-8')))
print(unicodedata.is_normalized('NFC', s))
print([unicodedata.name(ch) for ch in s])
```

### 3.4 파일 목록 형식 확인

```
const fs = require('fs');
for (const f of fs.readdirSync(dir)) {
  console.log(f, [...f].length, f === f.normalize('NFC') ? 'NFC' : 'NFD');
}
```

## 4. 정규화 위치 결정 규칙

- [ ] 정규화 형식을 **하나로 정했는가** (일반적으로 NFC)
- [ ] 그 형식을 **문서에 적었는가** (구두 합의는 잊힌다)
- [ ] 정규화 지점이 **경계에 있는가** (비교 직전이 아니라)
- [ ] 「이 안쪽 문자열은 전부 NFC」라는 **한 문장을 쓸 수 있는가**
- [ ] 정규화 전 원본을 보관해야 하는 자리가 있는가 (서명·원본 재현)
- [ ] `normalize()` 의 **반환값을 쓰고 있는가** (호출만 하면 아무 일도 안 난다)
- [ ] 검색 색인에 NFKC가 필요하면 **원본은 NFC로 따로** 두었는가

### 왜 한 번만인가

1. 비교 자리마다 붙이면 **새 코드가 추가될 때마다 누락 위험**이 생긴다
2. 경계에서 하면 **불변 조건을 문장으로 쓸 수 있다**
3. 「여기는 정규화됐나」를 묻는 코드가 생기면 설계가 이미 무너진 것
4. 정규화 지점이 하나면 「그 앞이 원본」이라고 말할 수 있다
5. 정규화는 멱등이라 비용은 문제가 아니다. **책임 소재**가 이유다

## 5. 자주 깨지는 패턴과 교정

| 증상 | 원인 | 교정 |
|---|---|---|
| 같은 이름 파일이 2개 보인다 | 두 형식으로 각각 생성됨 | 경로 조립 전 NFC 통일 |
| 있는 파일을 없다고 한다 (ENOENT) | 분해형으로 저장, 결합형으로 조회 | readdir 결과를 그대로 쓴다 |
| `[가-힣]` 검증이 정상 이름을 거부 | 입력이 분해형 | 검증 전 NFC 정규화 |
| 한글 혼입 필터가 못 잡는다 | 대상이 분해형, `[가-힣]` 무력 | 정규화 후 검사, 또는 Script 속성 |
| 금칙어 필터가 뚫린다 | 우회 입력이 분해형 | 입력 경계에서 NFC |
| grep으로 로그가 안 잡힌다 | 본문과 패턴 형식 불일치 | 양쪽을 같은 형식으로 |
| 중복 제거가 안 된다 | Set·유니크 인덱스는 바이트 비교 | 키를 NFC로 정규화 |
| 정렬에서 몇 항목만 맨 위로 | 분해형 초성이 U+1100 대역 | 정렬 전 NFC |
| 「10자 이내」가 정상 이름 거부 | 코드유닛으로 세면 3배 | 자소 클러스터로 센다 |
| 「3자 이상」에 1글자가 통과 | 분해형 1글자 길이가 3 | 자소 클러스터로 센다 |
| 미리보기 글자가 깨진다 | 종성이 잘렸다 | 정규화 먼저, 자르기 나중 |
| 설정을 넣었는데 적용 안 됨 | 객체 키가 두 형식으로 갈림 | 키를 NFC로 정규화 |
| 같은 파일인데 해시가 다르다 | 형식이 다름 | 서명 전 NFC, 규약 명시 |
| 같은 검색어가 지표에 두 줄 | URL이 두 개 | 링크 생성 전 NFC |
| 7글자 이름이 컬럼을 넘친다 | 분해형 바이트가 3배 | 저장 전 NFC, 컬럼은 바이트 기준 계산 |

## 6. 정규화 형식 선택

| 형식 | 하는 일 | 쓸 곳 | 주의 |
|---|---|---|---|
| NFC | 정규 분해 후 정규 결합 | 저장·비교·전송 기본값 | 대부분 이것으로 통일 |
| NFD | 정규 분해 | 초성 검색 등 자모 단위 | 그 구간에서만 한정 사용 |
| NFKC | 호환 분해 후 정규 결합 | 검색 색인 | **되돌릴 수 없다**, 원본에 쓰지 말 것 |
| NFKD | 호환 분해 | 드묾 | 위와 같은 주의 |

- `[가-힣]` 는 **완성형 음절만** 잡는다. 분해형 매칭은 0이다
- `[ㄱ-ㅎㅏ-ㅣ]` 는 **호환 자모** 범위다. 분해형과 무관하며 역시 0이다
- 분해형 자모는 `U+1100`~`U+11FF` 대역에 있다
- 가장 넓게 열려면 Script 속성 이스케이프를 쓰되 `u` 플래그를 반드시 붙인다
- 넓게 여는 것이 항상 정답은 아니다. **무엇을 통과시킬지 먼저 정한다**
