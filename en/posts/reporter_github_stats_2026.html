GitHub's 14-Day Traffic Data Limit - Analyzing Repo-rter and Local-First Alternatives

Why does GitHub Insights only show 14 days of data - what a local-first app like Repo-rter offers for tracking open source growth metrics

Jul 13, 2026 Dev & Infra

Introduction: Stars Persist, Traffic Vanishes

Anyone who has maintained even one open source repository has felt this frustration on the GitHub Insights screen. Open the Traffic tab and you get graphs for Views and Clones - but no matter how far you scroll, there are only 14 days of history. Whatever traffic last month's release actually generated, whatever week saw a spike in inbound visitors, is already gone without a trace. Star counts, by contrast, can be graphed years back using external tools like star-history. Why the asymmetry?

In July 2026, GeekNews featured an open source project built to attack this problem head-on: Repo-rter. Its premise is to preserve GitHub Insights' 14-day data permanently through a local desktop app. Rather than promote the tool itself, this piece digs into the question behind it - why does GitHub only show 14 days of traffic, and what does it actually mean to own that data yourself?

1. What Is GitHub Insights' 14-Day Limit?

1.1 What Disappears, and How

According to GitHub's official docs, anyone with write (push) access to a repository can view full clones, unique visitors, and views from the Traffic page of Insights, covering the last 14 days. Clone and visitor counts refresh hourly; popular content and referring sites refresh daily. The issue isn't the refresh cadence - it's retention. All of these figures disappear from the UI, and from the API response covered next, exactly 14 days later.

1.2 Why Calling the API Directly Doesn't Help

You might expect that calling the REST API directly would surface a longer window, but it does not. The /repos/{owner}/{repo}/traffic/views and /repos/{owner}/{repo}/traffic/clones endpoints return the same fixed 14-day range regardless of whether you pass per=day or per=week. Using per=week just groups that same 14 days into two weekly buckets - it doesn't open up a longer history. On top of that, these endpoints require authentication and return 403 Forbidden without write access to the repo. In other words, the API is not "a wider window" - it's just a programmatic way to see the exact same window as the UI. If you want to keep more than 14 days, someone has to read the values while they're still available and store them somewhere else.

2. The Pain Point for Maintainers and Product Teams

2.1 Long-Term Trends Can't Be Reconstructed

The most direct cost is a break in trend analysis. Wanting to know whether views climbed steadily over the past six months, or how much clone counts jumped after a specific release, is unanswerable unless someone manually screenshotted the graph the whole time. When it's time to look back at project growth for a conference talk, a sponsor report, or a hiring post - exactly the moments you need the evidence - it simply isn't there.

2.2 Cause and Effect Can't Be Connected

Validating the impact of marketing or community activity requires comparing traffic before and after an event. You may want to see how traffic responded on the day a blog post went live, the day of a conference talk, or the day of a major release - but once 14 days pass, the comparison baseline itself is gone. As a result, it's hard to verify after the fact which activities actually drove traffic, and planning the next one falls back on gut feeling.

2.3 Documentation Priorities Are Hard to Set With Data

The Popular content metric, showing which doc pages or files were viewed most, is useful for prioritizing documentation work. But because it too is only a 14-day snapshot, it's hard to separate seasonal variance or a temporary traffic spike (say, a post linked from elsewhere) from a genuine long-term pattern. Many maintainers end up editing docs by instinct, spending time on things unrelated to actual reader behavior.

3. Repo-rter - A Local, Permanent-Storage Approach

3.1 What the Tool Does

Repo-rter is a free, open source desktop app (MIT license) built to attack this problem directly. According to its repository, it pairs a Tauri (Rust) backend with a Next.js, React, and TailwindCSS frontend, and it's cross-platform - supporting macOS (Apple Silicon and Intel), Windows, and Linux. It runs in the background from the system tray, periodically calling the GitHub API on a cron schedule to accumulate views, clones, and stars into local storage, and it can export the results as CSV or JSON. In short, it takes periodic snapshots on your behalf before GitHub deletes them, and stacks them up in a local database.

3.2 Why a Local Desktop App, Specifically

There is more than one way to solve this problem (compared in Sections 4 and 5). Choosing a local desktop app specifically implies a few design decisions. It runs without a server or cloud account, so there's no infrastructure to operate, and the collected data never passes through a third-party server - it stays on your machine. The flip side is that collection stops when the machine is off, and sharing the same history across a team means passing files around - real collaboration limits traded for that simplicity.

4. Trade-offs of the Local Desktop App Approach

4.1 API Tokens and Privacy

Every method for collecting traffic and clone data, Repo-rter included, requires without exception a GitHub token with write access to the repository. That's not a risk specific to Repo-rter - it's the permission model of the GitHub Traffic API itself. What differs between tools is where and how that token is stored. GitHub's own guidance recommends using an OS credential manager and avoiding plaintext storage. If you use a local app, it's worth checking directly how it stores the token and how narrow its scope is (ideally a fine-grained PAT limited to what's needed). In exchange, the collected data itself never passes through a third-party SaaS server - a clear privacy advantage.

4.2 The Trade-offs of Automatic Collection

Living in the system tray and syncing on a schedule removes the chronic failure mode of manual approaches - forgetting to run the check and leaving a gap. But an always-on background process does consume a bit of battery and resources, and a fundamental limit remains: leave a laptop off for several days and that window is still missing. Unlike a cron job running on a server (say, GitHub Actions), it's important to understand that collection only happens while your machine is on.

4.3 Other Limitations

Because storage is local, switching devices or reinstalling the app means the history has to move with it, and sharing across a team means manually collecting exported CSV or JSON files. That's a different trade-off from the convenience of a cloud dashboard you can check instantly from any browser.

5. Comparable Alternatives

Beyond a local app, there are several other ways to solve the same problem - catching data before GitHub deletes it.

5.1 GitHub Actions Cron + Commit to the Repo

The most common self-hosted alternative is a daily GitHub Actions workflow that calls the Traffic API and commits the results into the same repo (or a separate data repo). No server is needed, everything stays within GitHub's infrastructure, and the history lives in the git commit log itself, making it easy for a whole team to share. The trade-offs: if the repo is public, the committed traffic data is public too, and you have to verify the action actually ran successfully every day.

5.2 A Custom Cron + Database (+ Grafana)

For organizations already running internal monitoring infrastructure (Prometheus, Grafana, and the like), periodically calling the GitHub API and loading results into an existing database or time-series store, then plugging it into an existing dashboard, is a natural fit. It offers full control and customization, but the build-and-operate burden falls entirely on the organization - heavy for an individual maintainer.

5.3 star-history and Similar - Star-Only Tools

Tools like star-history.com or daily-stars-explorer are fundamentally different from Repo-rter in that they only handle star history. Because GitHub exposes star events through a paginated API, tools like these can retroactively reconstruct historical star counts. Views and clones, however, are only exposed as pre-aggregated summary figures to begin with, and that aggregate itself is discarded after 14 days - retroactive reconstruction simply isn't possible. The assumption that "there's a star tool, so something similar must exist for traffic" doesn't hold.

5.4 OSSInsight and Similar - Hosted Large-Scale Analytics

Platforms like OSSInsight are hosted services that collect and analyze GitHub's public events (stars, PRs, issues, commits) at scale. They work instantly with no installation and are strong for ecosystem comparisons, but because they are built on public events, they don't touch private metrics like views or clones that require repository write access to see in the first place. That is the fundamental line separating local and self-hosted approaches from hosted analytics services.

6. Why and How to Track Open Source Growth Metrics

6.1 Why Track Them

For a maintainer, traffic and clone history serves as evidence for sponsorship pitches, conference talks, and hiring posts, and it's also experimental data for validating the impact of releases, documentation, and marketing activity. Without data, you're stuck with impressions like "it feels like it's grown." With accumulated history, you can talk in concrete numbers instead.

6.2 What to Watch - Clones Over Stars

Stars are the lowest-friction expression of interest (closer to bookmarking), and the community has long pointed out that they correlate weakly with actual usage. Unique clones, by contrast, are a signal closer to the number of people actually pulling and using the code. Watch both, but weight decisions toward behavioral signals like clones and views. Layer in popular/referrers (traffic sources) on top, and you can trace where people are discovering the project in the first place.

6.3 A Practical Workflow

A minimal workflow that applies regardless of project size: first, always move the data somewhere before the 14 days elapse - whether via a local app or Actions, what matters is continuity, not the specific method. Second, log event dates separately - releases, talks, blog posts - so you can later line them up against the traffic graph and infer causation. Third, build a habit of reviewing the history roughly once a month, so you don't miss anomalies like sudden spikes or drop-offs.

Conclusion - A Small Question About Data Ownership

GitHub Insights' 14-day limit looks minor, but dig into it and it leads to a bigger question: who holds the data about your project, where, and for how long? Repo-rter answers that in three words - local, indefinite, open source. There's no single right answer. If you run a small repo solo, a local app that's ready after a single install carries the least overhead; if you're part of a team or organization, plugging into existing CI or monitoring infrastructure is more sustainable. Whichever approach you choose, the core move is the same: move the data out before the 14 days are up - that one small habit is what will end up telling your project's growth story later.
