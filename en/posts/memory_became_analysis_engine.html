Why Building Memory Turns Into a Program Analysis Engine - Choosing What to Store Requires Knowing What It Means

Storing everything is not memory. The work is selection, and selection needs to know what the thing is used for

Aug 31, 2026 Dev & Infra

The whole conversation is stored, and the agent still asks again

If you have pasted the entire session log into an agent and a hypothesis you ruled out yesterday comes back today, the missing piece is not storage. The transcript is right there. It is there and the conclusion still returns, which means nobody is maintaining what is currently true across those stored sentences.

That is exactly where Jordy Zomer starts in Lemmalog: Maintaining LLM State Through Datalog. During long vulnerability investigations the model kept forgetting facts already established and reviving hypotheses already disproven. His diagnosis was that this is not a language understanding problem but a state maintenance problem. As he puts it, he does not just want the model to remember what was said; he wants it to maintain what is currently known.

What came out of that is a Datalog-based deductive database. Instead of parking the conversation somewhere and pulling from it, the system holds facts and rules, and when a premise changes the conclusions that depended on it are invalidated automatically. And having built it, the author noticed what he had built: at some point it became fairly obvious that he had approached the problem like a static analysis engine without meaning to.

The interesting part is that the overlap looks accidental, and what this article is after is why it is not. The two problems were wearing different names while demanding the same thing. If you have already worked through the retrieve-and-paste structure, this piece begins outside it. Before you can decide what to fetch, you have to decide what to keep, and that question is where we are standing.

What memory actually demands - selection, not storage

The word memory borrows a human experience, and the borrowing keeps producing confusion. The model remembers nothing. On every call it sees only the tokens placed in its input. So the engineering question narrows to one: what gets stored, and which part of it re-enters the prompt.

Framed that way, a design that stores everything has not built memory. It has deferred selection to the retrieval step, and that deferral is not free. The prompt budget is finite, similarity is not importance, and discarded sentences remain in the index looking exactly like live ones.

That selection is the substance also shows up in the author's numbers. On MemEval, a conversational memory benchmark of 102 questions, the system supplied roughly 2,700 tokens per question, where feeding the entire conversation for the same questions costs roughly 104,000. On LoCoMo the figures were about 3,400 tokens per question against about 18,900. The overwhelming majority of the material is the part deliberately left out.

More telling is where the score came from. The author writes that the climb from an F1 of 0.226 to 0.463 came almost entirely from fixing the intermediate representation: entity resolution, date representation, retrieval aliases, plural stemming. Not a different model. A different shape for the facts. Few passages state so plainly where the performance of a memory system actually lives.

So building memory breaks into five decisions.

  • What gets promoted to a fact - the line between a sentence you let pass and a claim you keep
  • What shape it is kept in - raw prose, relational tuples, or both side by side
  • When it goes back into the input - every turn, or only when a query pulls it
  • What gets thrown away - a store that only grows collapses back into a transcript
  • What stops being true - deletion and invalidation are not the same operation

The fourth and fifth are hard enough to deserve their own sections later. First, why the first two are hard is the spine of this article.

To choose, you have to know what it means

Is the fact that this function changed worth remembering? You cannot answer from the sentence alone, because the answer depends on what the function is used for.

A signature change in a helper called only from test fixtures and a return-type change in a validator called on the authentication path can have identical diff lengths and completely different worth. Forget the first and usually nothing happens. Forget the second and every conclusion drawn afterwards stands on a false premise. Importance is not a property of the text; it is a property of position.

And position is not written in the sentence. Almost no codebase carries a comment saying this function is used on the authentication path, and where one exists, a single refactor turns it into a lie. Position comes only from relations.

The same trap sits on the conversational side. Suppose a user states a constraint once. Whether that is a standing rule, a condition attached only to that task, or something already overturned by a later remark depends on what the sentence hangs on. As sentences, all three look the same.

  • Similarity-based selection picks what resembles the question - it cannot pick what has reach
  • Recency-based selection picks what was just said - it misses old constraints that still govern everything
  • Frequency-based selection picks what came up often - it is weak on the fact that appeared once and decided the rest
  • Only impact-based selection asks what collapses if this collapses - and it requires knowing the relations

The first three are computable from the surface of the text. That is why they are cheap, and why they are so often wrong. Only the fourth demands meaning, and the moment meaning is demanded the job changes character.

Meaning comes from relations - calls, dependencies, definitions and uses

Knowing what something means, in practice, is being able to answer four questions.

  • Which definition does this name refer to - name resolution
  • What calls this, and what does this call - call relations
  • Where is this value produced and where does it flow - definitions and uses
  • What facts is this conclusion standing on - provenance

All four are the standard queries of program analysis. A compiler front end answers the first, a call graph the second, dataflow analysis the third, provenance tracking the fourth. And a memory system that wants a real answer to what matters here has to ask the same four. It makes no difference that the material is conversation rather than code: you still need to know who refers to whom, and which utterance holds up which conclusion.

This is also why Datalog fits the slot. You supply facts, you write rules, derived facts follow until a fixed point, and when an input fact changes only the dependents are recomputed. The rule the author shows looks like this.

controls_kernel_object(X) :- controls(X, Y), points_to(Y, Z), kernel_object(Z).
viable(primitive_a) [10:14, 12:37)

The first line is a derivation rule: if an attacker controls some object and that object points to a kernel object, the conclusion that the attacker controls a kernel object stands on its own. The second is a fact carrying a validity interval, saying a primitive held from 10:14 until 12:37. It was not deleted; the record of how long it was true remains. Those two lines carry nearly the whole character of the design.

So it is not a coincidence - what the two problems demanded

The author says arriving at a static analysis engine was not intentional. That statement describes the order of discovery, not the reason for the design. The reason sits elsewhere: both problems demanded the same five things.

What a memory system must solveWhat program analysis already solvedMachinery both demand
What is true right nowWhich value is live at this pointState with a timestamp
A premise flips, so conclusions must fallInput facts change, so results must be recomputedIncremental evaluation and retraction
Why the conclusion was reachedWhy this warning firedProvenance tracking
Many expressions naming one thingAliases, re-exports, overloadsEntity resolution
What to include for this questionWhich facts this query needsDemand-driven evaluation

Not one of those five rows belongs only to conversational data or only to code. Both are the problem of keeping derived conclusions coherent over changing inputs, and the solution space for that problem is narrow. Separate facts from rules, record the dependencies, recompute only what moved. There is not much else. Build it seriously and you land in a similar shape.

The implementation list in the repository documentation shows the same landing point. Stratified Datalog with negation as absence, seminaive fixpoint evaluation, per-epoch delta maintenance, annotations carrying confidence and provenance together, queries that return proof trees, magic-set rewriting for point queries. Every one of those found its footing in the static analysis literature first.

Put simply: the overlap is not two people having the same idea. The problem demanded the same things. The only accident was the moment of noticing.

Why text is the wrong handle - same name different thing, different name same thing

Attempts to do selection with string search break in two directions, always.

First, the same name for different things.

  • Two modules each defining a type of the same name - the name matches and the thing does not
  • Overloaded functions - one name, several different contracts
  • A local variable shadowing an outer one - the same spelling pointing at different storage
  • Test doubles against real implementations - the matching name is the entire point of them

Second, different names for the same thing.

  • Aliased imports and re-exports - several paths, one entity
  • Renamed symbols - the names before and after a refactor point at the same thing
  • Pronouns and titles on the conversational side - a name, a nickname and that person are one person

String search cannot separate these, so false positives and false negatives arrive together. It drags in unrelated namesakes while missing the alias you needed. And the two errors hide each other. Something always comes back, so the signal that it was wrong rarely fires.

In code this is already solved. The parser gives structure, name resolution decides which definition, types decide what is the same as what. Drop the text and use syntax and semantics. Conversation has no comparable ground, which is why it is harder, and why Lemmalog handles entity identity with star-shaped aliasing and directional canonical views. The author leaves the remaining hole visible: relations that do not connect lexically, such as a generic term for a kitchen gadget and the product name of one, still slip past retrieval.

What to forget - discarding is the harder rule

Deciding what to keep is easier than deciding what to drop. Get keeping wrong and the store grows a little; get dropping wrong and there is nothing to recover from. Yet without dropping, the store slides back into a transcript and you are at the beginning again.

Reason to dropTestRisk when wrongMitigation
SupersededA new value arrives for the same subject and relationQuestions about the past become unanswerableClose the validity interval instead of deleting
IrrelevantNo rule references this factA rule added later cannot bring it backHold off while the rule set is still growing
StaleThe source changed - hash, commit, revision dateUnchanged parts are lost along with itMatch the invalidation unit to the unit of change
FalseIt rests only on a retracted premiseA conclusion still true by another route is erasedCheck every derivation path before deleting

The last row is the real trap, and the author uses the same example when explaining retraction. When a points-to relation is withdrawn, a conclusion that also followed from a second rule has to survive. Miss that and retraction becomes information loss. Skip retraction entirely and disproven hypotheses keep serving as evidence.

The mitigation for the superseded row is a time axis. The repository documentation keeps three stamps on every fact, valid from, valid to and asserted at, and derives what is true now by comparing against the current time. The same store then answers both the current question and the historical one. Two sentences that looked contradictory turn out to be facts from different intervals.

  • Do not make deletion and invalidation the same operation - the latter only exists if there is a time axis
  • Always ask a drop candidate for its derivation paths first - one support or two changes the verdict
  • Keep a record of what was dropped - if you cannot explain the absence you will re-ingest the same fact later

What you stored goes stale - when to invalidate

Facts extracted from code carry a weakness conversation does not have: the source keeps changing. The note you extracted yesterday saying this function bypasses the cache becomes false with one commit today, and the store has no way of knowing it.

So invalidation belongs on events, not on clocks. Expiry timers produce both errors at once, discarding facts that never changed while keeping facts that already did.

  • Commit boundary - cheapest and coarsest. You know something changed, not how far it spread
  • File content hash - accurate per file, but one changed line throws away every conclusion drawn from that file
  • Symbol signature - the most precise and the most expensive, and it only works with an accurate dependency graph
  • Session turn - the natural unit on the conversation side, recomputing only the dependents of each new utterance

Whichever unit you pick, the principle holds. The invalidation unit has to match the unit in which the source changes, and the blast radius has to follow the dependencies. That is the same point behind the repository note that retraction recomputes only transitive dependents. Full recomputation is always correct and never affordable in a long session.

There is a worse failure than staleness. Explaining the low scores in the multi-session reasoning category, the author points out that the failures came not from connecting facts wrongly but from never extracting them at all. Nothing that failed to enter the database can be recovered by derivation. A stale fact can at least be caught; a missing one is silent.

Cost - analysis is not free

The benefit of structuring is clear and so is the bill. Cost lands in three places: extracting the facts, maintaining the derivations among them, and putting the selected material back into the prompt. The first is usually the largest, because extraction means one more model call per turn or per file.

When you computeWhat you gainWhat you payWhere it fits
At the ingestion boundary - every turn or commitLow query latencyYou compute facts nobody will ask forQueried often, changed rarely
At query time - only when neededLittle wasted workThe first response is slowQueried rarely, changed often
Incrementally - deltas onlyBoth problems softenYou carry the cost of a dependency graphLong sessions with frequent change

The author's figures belong to that third row. On a synthetic scenario of 1,000 turns with 30 people, maintenance latency is reported at 1.5 milliseconds per turn, and per-position secondary index lookups at roughly 100 microseconds at a scale of four million facts. Those are the author's synthetic scenario and repository documentation; what the same numbers look like on a real codebase is not there.

The token side holds a reversal. The author states that richer extraction grows the memory context itself, so the per-query token advantage that sits between four and twelve times narrows to between one and five times on heavy instances. Remembering more does not get cheaper. The rule for forgetting is a cost problem before it is a quality problem.

Where this approach does not fit

There are clear cases where structured state is the wrong answer. Stated plainly.

  • Things whose relations are not crisp - conditional knowledge such as taste and preference loses its exceptions the moment it becomes an unconditional tuple. The author says conditional knowledge loses nuance when flattened, and cites it for the weak scores in the preference category
  • Things that rarely change - a document you read once is cheaper to re-read than to extract and maintain. If nothing is ever invalidated, the entire machine is idling
  • Small subjects - if the whole thing fits in context, structuring never earns back the extraction cost
  • One-shot work - a short session produces nothing to retract and nothing to go stale
  • Places where the fact exists only as prose - when the evidence lives in the nuance of a sentence, tupling it is itself the loss. Keep the original snippet beside the structured state
  • The hope that stricter discipline helps - the author reports that strengthening the instruction to answer only when facts support it made the model treat only literal matches as support, producing refusals on questions that required counting or comparison

That last item is a recurring trap in this field. Tighten the accuracy machinery and the system gets quieter, but quiet and correct are different things.

Where to start small

None of this has to be stood up at once. Keep the order and most of it can wait.

  • Decide what to drop first - a store started without a retention rule turns back into a transcript every time
  • Fix the shape of the facts before anything else - entity resolution, time representation, name normalization. That almost the entire score gain came from here tells you the ordering
  • Pick exactly one invalidation trigger - a single commit boundary beats having none by a wide margin
  • Record provenance from day one - it is the hardest axis to add later, and without tracing which facts produced a conclusion you cannot implement retraction at all
  • Measure on two separate axes - did the fact arrive, and is the conclusion right. That the multi-session failures came from extraction rather than connection is the argument for splitting them

One thing stands out about that order. Not a single item concerns the model. They are all decisions about representation and rules.

In closing

Building memory reads like attaching a storage device, but what actually gets built is a selection rule. Selection demands meaning, meaning demands relations, and machinery for relations has been under construction for decades under the name of program analysis.

That is why the author of Lemmalog arriving at a static analysis engine is not a coincidence. Two problems demanded the same five things, and taking those demands seriously leads to a narrow place. The only accidental part was noticing the overlap.

The practical judgment is simple. When a memory system underperforms, the first suspect is neither the model nor the retriever. It is the shape of the facts and the rule for discarding them. In the work behind this article, those two are exactly what doubled the score.

What could not be confirmed

  • The article puts per-question tokens at about 2,700 while the repository documentation says about 2,300, so the stated reduction differs as 38 times against 45 times. Which conditions produced which figure could not be pinned down from those two documents alone
  • Every benchmark score quoted here is the author measuring and reporting on his own system. No third-party reproduction was found in public
  • The scores come from conversational memory benchmarks; there are no published figures for an evaluation against a codebase. The code-side argument in this article rests on the structural overlap between the two problems, not on those numbers
  • What fact extraction costs in model calls at real repository scale is not stated. Only maintenance latency and index lookup times are public

Frequently asked questions

Cannot I just store the whole conversation and retrieve well?

Store everything and you have a transcript, and retrieval finds passages that resemble the question. Resembling and being currently true are different properties. Yesterday's ruled-out hypothesis is still there as a sentence, and the retriever does not know it was discarded. What is missing is not more storage but a rule for maintaining what currently holds.

Does this mean embedding search is useless?

No. It connects different wordings of the same meaning and recovers prose that structuring dropped. But similarity does not measure blast radius; it will never tell you which conclusions collapse when a fact changes. The two are not substitutes, they play different roles.

Does the same approach work outside code?

As far as the relations are crisp. People and affiliations, events and places move over easily; conditional preferences lose their exceptions when flattened into unconditional tuples. In those domains, keep the original prose beside the structured state.

When should stored facts be invalidated?

On events, not on clocks. For code that means commit boundaries, file hashes or symbol signatures. A coarse unit is safe but discards a whole file's conclusions over one line; a fine unit is cheap but needs an accurate dependency graph. And retraction is not deletion.

Does this structure actually reduce tokens?

In that direction, but not without limit. The author reports far smaller per-question context than full conversations, and in the same breath notes that richer extraction narrows the advantage. Extraction is itself a model call, so input tokens alone misprice the system.
