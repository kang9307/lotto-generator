AI时代韩国公文档HWP无法打开的真正原因与解决方案

30年专有二进制锁定结构的根源、HWPX转换的真实意义，以及开发者现在就能用的实用解法——2026年6月现状

2026-06-21 开发/基础设施

前言：AI读不懂的大韩民国公文档

2026年6月，韩国面临一个奇特的矛盾。这个国家的智能手机普及率跻身世界前列，开发者们快速推出AI原生产品，政府宣布了AI转型战略。然而2025年一项调查显示，政府公文的91.1%以HWP或扫描PDF格式流通。这两种格式与标准AI文本处理流水线根本不相容。

这不是一个「韩国软件落后」的故事，而是关于采购惯性、专有二进制格式和数十年积累文档如何形成结构性锁定的故事。要正确理解它，需要从格式本身的技术设计出发，结合行政采购和政治经济背景一并审视。

1. HWP是什么，为何不兼容

1.1 HWP的技术结构

HWP（Hangul Word Processor）是1989年韩国Hancom公司开发的文字处理器专用文件格式。旧版.hwp（HWP5及以下）是专有二进制格式，基于微软OLE2复合文档文件格式，内部流的排列和编码方式没有公开的国际标准规范。

实际后果：任何想读取HWP文件的软件都必须逆向工程或获得授权。LibreOffice、MS Word和PyMuPDF的韩语文档模块都在没有完整公开规范的情况下构建了部分实现，结果是即使最好的第三方工具在复杂HWP文件上也会产生不完整或布局错乱的输出。对于AI流水线而言，问题是根本性的：没有原生解析器，收到文件也无法提取内容。

1.2 AI为何无法读取

现代AI文档工作流假设文本提取是既定的。RAG（检索增强生成）流水线将文档嵌入向量数据库，这需要原始文本。N8N、Zapier等工作流自动化工具将文档内容传递给LLM，同样需要可读文本。如果提取步骤失败，整个流水线就会失败。HWP恰好在这一提取步骤处卡住，意味着数十年的韩国公共记录对AI系统实际上不可见。

2026年6月时点：ChatGPT于2026年4月宣布正式支持HWP/HWPX，Gemini从2024年下半年起已支持，而Claude和Copilot仍无原生支持。

2. 30年锁定的形成原因

2.1 历史起源：韩文处理的技术优势

1989年推出时，HWP是唯一能正确处理韩语字母拼合与竖排布局的软件。初声、中声、终声的分离输入方式和韩文专用排版引擎是当时的唯一选择。教育部和政府部门基于技术合理性采用了HWP。问题在其后产生：数十年公文以HWP格式积累，打开旧文件需要HWP，用HWP就产生新HWP，循环固化。

2.2 政府采购与标准的悖论

2007年韩国政府将国家标准正式转换为开放文档（KS X ISO IEC 26300 ODF），但行政现场几乎没有变化。Nara系统和各地方政府电子文档系统基于HWP构建，整体替换的成本和阻力过大。Hancom Office许可证成为政府采购目录的固定项，年度续签纳入预算计划。采购惯性，而非技术选择，是锁定持续的核心。

2.3 兼容工具缺失的恶性循环

LibreOffice的HWP读取支持不完整：表格、特殊符号、HWP特有的分栏布局经常错乱。用LibreOffice打开HWP后布局损坏的体验，让用户最终回到Hancom Office。这种失败体验的重复固化了「反正只能用韩文」的认知。兼容工具不完善导致锁定延续，锁定延续导致兼容工具开发的商业激励弱化——典型恶性循环。

3. HWPX是什么，转换为何重要

3.1 HWPX技术结构

HWPX是Hancom从2010年前后开始支持的新格式，2014年被指定为韩国国家标准KS X 6101。内部是遵循OWPML（开放文字处理标记语言）规范的XML文件打包为ZIP容器。将扩展名改为.zip即可用解压工具直接查看内部XML。这与DOCX（ZIP+OOXML）和ODT（ZIP+ODF）在技术上是相同的方法。对开发者而言，这是决定性的区别：任何语言都有XML解析库。python-hwpx（Apache 2.0）无需Hancom Office即可读取、编辑并将HWPX转换为Markdown，正是得益于这种开放结构。

3.2 2026年政府转换政策

自2026年5月18日起，行政安全部Nara系统限制了.hwp文件附件。中央部委和地方政府的Nara系统正在扩展开放文档（hwpx）应用，公务员邮件系统「On-mail」预计在2026年10月前完成hwpx转换。国家AI战略委员会联合行安部和文体部宣布全面义务化。这一政策的核心驱动力是AI应用：HWPX格式的公文可以被AI解析、索引、摘要和检索，应将其视为公共AI基础设施的基础建设。

3.3 HWPX转换的局限

第一，旧版HWP文件的遗留问题。数十年积累的旧HWP文档与转换政策无关继续存在，需要单独的大规模转换项目。

第二，HWPX不是ODF。HWPX是开放XML格式，但OWPML是韩国国家标准而非国际标准。LibreOffice、Google Docs、MS Word不原生支持HWPX，海外开发者解析HWPX仍需专用库。

第三，民间及海外接收方问题。向企业或海外机构发送HWPX文件时，对方可能没有查看工具，问题重现。

4. AI时代HWP兼容性问题更严峻的原因

4.1 RAG流水线与死数据

企业和公共机构正在快速部署RAG（检索增强生成）流水线用于内部文档检索。文档嵌入向量数据库的过程以文本提取为前提。HWP阻断文本提取，意味着数十年公文档在RAG中被完全排除——数据存在，但AI无法使用，成为死数据。

4.2 自动化工作流中断

现代工作流自动化（N8N、Zapier、Make等）将文档作为AI摘要、分类、提取步骤的输入。HWP文件进入流水线时，流水线断裂。尝试构建公共文档处理自动化的开发者首先碰到的就是HWP这堵墙。

4.3 可访问性问题：Mac、Linux和海外用户

Hancom Office以Windows为中心。macOS版存在但功能差距明显，Linux版实际上不存在。使用Mac的开发者、Linux服务器环境和海外合作机构收到HWP文件后都需要额外操作才能打开。在2026年，「打开此文件需要安装特定付费软件」的要求近乎可访问性设计失败。

5. 开发者实用解决方案（2026年6月）

5.1 让Claude读取HWP：HWP-MCP

将HWP-MCP服务器连接到Claude Desktop或Claude Code，一行命令安装即可让Claude直接读取HWP和HWPX文件。无需Hancom许可，支持Mac和Windows，本地运行不将文档发送至外部服务器。基于MCP（Model Context Protocol）标准，在Claude Code、Claude Desktop、Cursor、VS Code Copilot、ChatGPT等支持MCP的环境中均可使用。Claude自动调用hwp_read工具并以表格形式返回结果，用户无需关注转换过程。企业封闭网络环境也可无需外部API即可本地部署。

5.2 Python流水线：pyhwp、python-hwpx、kordoc

  • pyhwp（PyPI，GNU AGPL）：HWP5二进制解析器，可实验性转换为ODT或文本，适合批量处理旧版公文档。
  • python-hwpx（GitHub: airmang/python-hwpx，Apache 2.0）：纯Python的HWPX解析器，支持Markdown转换（普通和格式保留两种模式）、表单填写和模板分析，完全不依赖Hancom Office。
  • kordoc（GitHub: chrisryugj/kordoc）：支持HWP3、HWP、HWPX、HWPML、PDF、XLS、XLSX、DOCX转Markdown的CLI和MCP服务器一体化解析器，另支持新旧对比和自动填表。

基本流水线模式：接收HWP/HWPX文件 → 转换为Markdown → 投入任意LLM → 后处理结果。Markdown对所有LLM均可处理，无模型依赖。

6. 格式对比：HWPX的位置

格式容器公开规范国际标准全球工具支持AI解析
HWP（旧版）OLE2二进制未公开无有限非常困难
HWPXZIP + XMLOWPML（KS X 6101）仅韩国国标有限需要库，可实现
DOCXZIP + XMLOOXML（ISO 29500）国际ISO广泛容易
ODTZIP + XMLODF（ISO 26300）国际ISO广泛容易

HWPX明显优于旧版HWP，但处于国内开放格式与国际认可标准之间的中间阶段。

7. 真正的解决方案

短期（立即）：在AI流水线中加入HWP-MCP、kordoc或python-hwpx解析层，立即获得兼容性。不完美但实用。

中期（HWPX转换完成后）：Nara系统转换完成后，新公文以HWPX流通，python-hwpx级别的流水线可处理大部分文档。但若没有旧版HWP批量转换项目，历史文档仍被排除。

长期（根本解决）：将国际标准格式（DOCX或ODT）指定为公共文档的并行分发和存档标准。HWPX用于内部作成，PDF加DOCX或ODT用于对外分发、长期存档和AI处理。这种双标准政策是已解决类似锁定问题的政府的通行做法。

核心判断：这是采购和政策问题，不是技术问题。HWPX从2014年起技术上就可行，但转换在2026年才发生，源于国家AI战略委员会的政治意志，而非工程突破。最终解决同样需要政策制定者将国际标准兼容性列为强制采购评估标准。

8. 结论：从现在能做的开始

2026年6月，情况比两年前明显改善：政府强制推行HWPX，ChatGPT增加了HWP原生支持，HWP-MCP等开源桥接工具已达到生产可用水平。但结构性问题尚未完全解决——旧版HWP存量、全球工具对HWPX的未支持、与国际标准的差距依然存在。

对开发者：现在就在流水线中加入kordoc或HWP-MCP进行实验。对政策制定者：在巩固HWPX为内部标准的同时，评估DOCX/ODT作为并行外部分发格式。这个问题由30年惯性积累而成，解法从现在开始。
