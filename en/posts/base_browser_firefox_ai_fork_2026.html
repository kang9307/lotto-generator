1. Firefox AI Integrations and the Drive Toward Complete Removal

Modern web browser engines operate on vast codebases spanning tens of millions of lines of source code. Generally, as software ecosystems mature, upstream vendors inevitably integrate secondary business layers, commercial telemetry, and emerging technological trends directly into the runtime framework. Firefox, long considered by many technical communities as a resilient bastion of independent open-source client software, has similarly seen a steady expansion of integrated artificial intelligence submodules, on-device helper routines, and remote workflow integrations into the deeper layers of its rendering and application architecture.

Confronting this developmental shift, security researcher and independent developer Sarah Jamie Lewis published a personal reflection titled "Thoughts on the Future of Web Browsers" on September 19, 2026. The source reflects upon an earlier Mastodon thread initiated by the author in July, asserting that if an independent, non-slop web has any viable future remaining, every existing Firefox fork must commit to working together to maintain a hardfork isolated from Mozilla. The author explicitly characterizes this task as one that is too large to be handled by any single small project alone, yet far too important to leave under the guidance of an organization like Mozilla.

In the source text, the author describes Mozilla's developmental trajectory as a settled and persistent commitment. The author writes: "Mozilla and, by extension, Firefox have laid out the direction they want to go - and have consistently moved in that direction over the last decade. There is no redemption arc there, they are not going to turn the ship around - and every week and month that goes by, Firefox gains more slop and drifts further from the visions that founded it." Under this diagnosis, expecting upstream management to reverse course is considered unrealistic, leaving physical codebase isolation as the only consistent recourse.

In this article's interpretation, passive user resistance through toggling checkboxes in advanced preferences has proven incapable of counterbalancing the structural reconfiguration of the core browser engine. When an upstream organization shifts toward treating the browser window as an interactive staging ground for external agents, basic configuration switches function merely as temporary operational bandages. In this article's estimation, the concept of an isolated hardfork emerged directly from a technical judgment that deep module coupling fundamentally alters the integrity and security perimeter of the underlying web platform.

2. Identity of Base Browser — Stripping Code Rather than Disabling Flags

The discussions originating from the Mastodon thread subsequently took concrete shape as the Base Browser Project hosted on Codeberg. The source describes this project as an attempt to establish a dedicated forum where contributors and maintainers can gather to deliberate on technical directions and shared repository infrastructure. The source provides a concise and explicit definition of the repository's current status: "A set of patches, based around the current Firefox 153 ESR, that strip user hostile features completely out of the code base (as opposed to the common soft-fork approach of disabling these.)"

The foundational distinction here lies in the technical divergence between disabling features via build flags or preference settings and stripping them physically out of the underlying source files. Conventional community forks frequently adopt a soft-fork posture, shipping altered distribution packages where telemetry URLs are blanked out and unwanted integrations are turned off by default. Conversely, Base Browser rejects this passive coexistence, choosing instead to excise the entire physical implementation of submodules designated as user-hostile directly from the code tree.

The source author defends this comprehensive deletion approach as an unavoidable technical necessity. The text states: "I believe that deleting these features entirely is the correct approach for exactly the reasons that make it a pain - these features are large, and increasingly tightly integrated into the core browser. They also account for an increasingly percentage of the total firefox code base and quite frankly: I do not believe that these features should be anywhere near the core base of a web browser". The very difficulty of the excision is cited as empirical proof of why the code cannot safely remain embedded within the engine foundation.

In this article's interpretation, retaining dormant code within an active binary maintains latent attack surface, accidental IPC invocation routes, and tangled compilation dependencies across internal interfaces. In complex multi-process browser environments, disabled features can be inadvertently re-engaged or modified by upstream merge updates. In this article's estimation, opting for complete codebase removal constitutes a deliberate architectural choice to eliminate the risk of latent activation, accepting severe rebasing friction to guarantee structural purity.

3. Scale of the Initial AI Removal Patch and Compression Process

As an initial proof of concept within this initiative, the author undertook the construction of a comprehensive patch designed to remove all artificial intelligence integration subroutines from the browser. The source details the immense physical scale of this initial diff: "a ridiculous patch impacting 1605 files changed with 852297 deletions, totalling 37 megabytes". Removing these features required deleting more than eight hundred and fifty thousand lines of source code distributed across more than sixteen hundred individual files, generating a raw unified diff file of thirty-seven megabytes.

The source carefully clarifies that this massive initial patch reflects the exploratory scope of excising all AI-related code from the repository rather than representing the finalized distribution diff of the Base Browser project itself. Nonetheless, the figure serves as quantitative evidence of how extensively helper frameworks, contextual hooks, and model-dispatch mechanisms have permeated the codebase. Following this initial milestone, the author and a small team of volunteers spent several weeks refining the diff, authoring supplementary patches, and engineering pipeline tooling to manage the changes.

According to the source, contributors cliffmccarthy and gellge provided substantial assistance during this engineering phase, alongside other participants who tested and evaluated the patches. To overcome the logistical difficulty of distributing and applying a 37-megabyte diff, the team developed automated scripts that compressed the patch down to just under a single megabyte. The source explains that this compression was accomplished by leveraging Git's existing irreversible-delete flag combined with custom Python routines to enable clean repatching against target source trees.

When hundreds of source files are deleted outright, conventional text diffs include every deleted line, inflating storage unnecessarily. In this article's estimation, the necessity of creating custom Python scripts illustrates how standard Git patch mechanisms struggle when projects perform wholesale amputations of deeply nested subsystem trees.

4. Contrast with Existing Approaches of Tor Browser and Waterfox

In establishing the strategic justification for Base Browser, the source directly analyzes the engineering postures maintained by prominent existing projects, specifically referencing Tor Browser and Waterfox. The author characterizes their maintenance methodology as follows: "Projects like Tor Browser and Waterfox are painstakingly disabling / patching out the worst - but every release becomes more expensive, and things do slip through." While acknowledging their dedicated efforts, the author highlights the cumulative fragility inherent in ongoing superficial mitigation.

Selective disabling demands an ever-increasing maintenance tax with every upstream ESR or rapid release cycle. When upstream engineers refactor internal components, previously decoupled flags can be bypassed, silently restoring unwanted network transactions or analytics pipelines. The source emphasizes that despite rigorous continuous testing, unwanted code artifacts inevitably slip through the review net when the underlying components remain resident in the binary.

Comparative Analysis of Browser Customization Frameworks
Approach Classification Representative Projects Implementation Mechanism Primary Advantages Architectural Costs and Trade-offs
Soft-Fork / Disabling Mitigations Tor Browser, Waterfox Disabling runtime flags and applying targeted surgical patches Preserves upstream branch alignment; facilitates security updates Compounding verification overhead; risk of upstream regressions
Complete Codebase Deletion Base Browser Physical removal of offending files and symbols from tree Eliminates latent attack surface; prevents submodule activation Severe merge conflict frequency; demands extensive developer labor

The comparative tension between these two engineering paradigms highlighted in the source manifests through several distinct dynamics:

  • Tor Browser and Waterfox prioritize continuous synchronization with upstream security releases, leading to a reliance on flag-level mitigations.
  • The recurring maintenance burden of auditing disabled features grows progressively heavier as upstream integration points multiply across versions.
  • Base Browser adopts a structural amputation strategy, ensuring that excised submodules cannot be inadvertently invoked by auxiliary subsystems.
  • Total deletion maximizes codebase divergence from upstream trunk, exponentially increasing the difficulty of applying recurring security patches.

In this article's interpretation, downstream maintainers historically embraced soft-fork strategies not because they considered them architecturally superior, but because practical resource constraints precluded managing a permanent hardfork. Tracking monthly browser security advisories while maintaining thousands of custom merge resolutions is notoriously labor-intensive. In this article's estimation, Base Browser exposes the painful reality that maintaining genuine code independence requires confronting engineering costs that most volunteer groups cannot sustainably bear alone.

5. Author's Assessment of Browser Direction — Smart Window and AI Agents

The impetus driving the creation of Base Browser stems from a fundamental divergence regarding the long-term roadmap envisioned by browser vendors. The source notes that Firefox is moving far beyond isolated helper buttons or localized autocomplete enhancements. Citing a Mastodon post, the author points toward an emerging paradigm where the entire browser viewport is conceived as a "smartwindow" designed as much for third-party artificial intelligence agents as it is for human operators.

Transforming the browser from a user-directed document viewer into an automated execution surface for third-party agents fundamentally alters its trust architecture. As examined in our previous analysis of What the Mistral-Mozilla Smart Window Partnership Discloses and Conceals — Deconstructing AI Browsing Privacy Promises, feeding page document trees and user browsing context into reasoning models requires extensive internal telemetry, continuous DOM observers, and pervasive runtime integration hooks. Such architectures turn the browser client into a continuous surveillance and dispatch node.

The source author rejects this trajectory unequivocally, stating: "I don't want the web to go in that direction and, frankly, I cannot follow." The text expresses an explicit unwillingness to accommodate a future where agent mediation replaces direct human navigation. While the author openly acknowledges personal limitations—noting that they may not be the ideal figurehead to direct an ecosystem-wide countermeasure—they insist on the moral and technical imperative of attempting a tangible intervention rather than remaining passive.

In this article's interpretation, this confrontation represents a clash over client agency: whether the browser exists to execute the unambiguous commands of its human user or to mediate between the user and commercial automation platforms. Once a browser engine integrates ambient contextual awareness for external models, traditional process boundaries begin to erode. In this article's estimation, Base Browser serves as an early protest against the reconfiguration of the open web into an automated data pipeline for third-party machine learning infrastructure.

6. A Tool for Creation Beyond Consumption — Amaya, Flock, and Alternative Protocols

Beyond defensive code removal, the source articulates an affirmative historical vision for what web software ought to be. The author references pioneering historical browser projects: "I often think about the visions put forth by browsers like Amaya and, much later Flock. That a browser should be a tool for creation as much as consumption." This perspective recalls an era when browser development prioritized decentralized user authoring rather than passive, ad-driven content absorption.

Amaya, developed by W3C and INRIA as a testbed for early standards, unified web browsing with direct WYSIWYG HTML document editing, treating reading and authoring as symmetrical operations. Similarly, Flock explored integrating blogging platforms, distributed tagging, and RSS feeds directly into the client framework during the mid-2000s. The source recalls the early 2000s renaissance catalyzed by Firefox, when community excitement centered on open comments, collaborative feeds, and an expansive definition of web interaction.

The tension between these early ideals and contemporary web standards is characterized in the source by several key historical shifts:

  • The original architectural principle that the web should be equally writable, readable, and shareable by individual participants.
  • The subsequent sanitization and commercial packaging of that collaborative ethos by centralized platform monopolies.
  • The over-saturation of modern web standardization bodies under the overriding priority of corporate commercial interests.
  • The persistent economic tension palpable on every page load between pure open-web philosophy and expected corporate financial returns.

Reflecting this philosophy, the author notes ongoing personal experiments involving custom lightweight clients designed around the Gemini protocol (geminiprotocol.net—explicitly clarifying "the protocol, not the llm") alongside RSS feeds. By exploring protocol environments untainted by the hyper-commercialization of modern browser specifications, the author seeks alternative technical spaces. While acknowledging uncertainty over whether such protocols represent the ultimate destination, the source embraces them as a potential viable path, concluding with the historical rallying cry: "we need new noise".

7. Three Temporary Actions to Reduce Web Reliance

Because constructing and maintaining a fully independent browser base is an arduous, multi-year endeavor, the source outlines three concrete operational strategies currently employed by the author to reduce daily reliance on Firefox and bloated web engines. Rather than waiting passively for an ecosystem shift, these pragmatic measures decentralize information retrieval away from monolithic browser processes.

  1. Moving as much offline as possible: The source describes utilizing openzim readers (such as Kiwix) to relocate general reference lookups away from the live browser. OpenZIM archives leverage a minimal subset of HTML, CSS, and JavaScript, enabling rapid reading inside lightweight standalone viewers without requiring full rendering engine overhead.
  2. Moving to standalone desktop applications where possible: As an operator who spends the majority of daily workflows on desktop computers, the author expresses a strong preference for dedicated native clients over resource-heavy web applications, transitioning platforms like Mastodon to specialized standalone software.
  3. Moving to dedicated feed readers where possible: In parallel with standalone tools, syndication feeds (RSS/Atom) provide a robust, structured mechanism to interact with content pipelines without loading dynamic browser contexts, client-side tracking scripts, or auxiliary AI overlays.

In this article's interpretation, these steps constitute a practical defense strategy against platform bloat and browser surveillance. By substituting dynamic web apps with static offline packages and native feed consumers, users can eliminate exposure to upstream engine churn. In this article's estimation, documenting these three personal coping mechanisms highlights the realistic transition period required while community-driven initiatives like Base Browser work to establish a dependable long-term foundation.

8. Practical Limits of Sustainability and the Need for Collective Effort

The most candid dimension of the source text lies in its unvarnished appraisal of project longevity. The author openly acknowledges the immense structural headwinds facing Base Browser, stating: "Now, I am well prepared to lose this battle. I do not believe that there is enough funding, or enough developer effort to maintain something like this long term. Unless we all pool our efforts into making a base like this possible." Maintaining an independent browser engine requires substantial ongoing engineering capital that informal volunteer teams rarely possess.

Developing modern rendering engines, auditing upstream security patches, and maintaining web standards compliance demands well-funded engineering teams. The source observes that over the past decade, web specifications have expanded so dramatically that maintaining quality assurance requires substantial financial backing or direct reliance on an upstream corporate patron. Yet financial patronage invariably introduces commercial compromises that undermine foundational privacy and independence goals.

The conditions governing the future survival of Base Browser and the author's expectations are encapsulated in the following core observations:

  • The initiative operates upon a foundation of shifting sands due to continuous structural refactoring across upstream Firefox releases.
  • Long-term survival remains mathematically and operationally impossible unless fragmented downstream forks pool developer labor into a shared core.
  • The effort will be considered an unequivocal success if it merely teaches a few independent developers how to compile Firefox from source code.
  • The project team would be ecstatic if any existing community fork ultimately adopts or integrates these clean excision patches into its build pipelines.

In this article's interpretation, Base Browser's primary contribution is not the commercial delivery of an end-user browser product, but the provision of a shared, unencumbered reference baseline for the wider open-source ecosystem. If disparate forks continue to maintain isolated, redundant soft-fork patches, they will each be worn down individually by upstream release velocity. In this article's estimation, the author's open acknowledgment of potential failure serves as an urgent strategic appeal for collective downstream consolidation before the non-Chromium open web is entirely subsumed.

9. What Could Not Be Verified

Based on a meticulous examination of the source text and public project repositories, the following items could not be independently confirmed due to limitations in public documentation:

  • Formal binary release schedules and a concrete roadmap for Base Browser: The source describes a patch set and compression methodology but does not outline a release timetable or packaged binary distributions for end users.
  • Participation or feedback from other Firefox forks such as LibreWolf, Zen, or Floorp: The source solely references Tor Browser and Waterfox as comparative approaches and does not mention whether other community forks intend to collaborate.
  • Detailed directory paths and specific module listings for the 1,605 altered files: The source provides aggregate metrics of 1,605 files and 852,297 deletions but does not publish the complete itemized directory inventory of deleted source files.
  • Source code of the custom Python compression utility: The source mentions using git's irreversible-delete flag alongside custom Python to reduce patch size under a megabyte, but does not include the Python script itself.
