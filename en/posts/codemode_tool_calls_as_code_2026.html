This article summarizes "What is Codemode", which Armin Ronacher wrote on his blog on October 6, 2026. Explanations and code come from that post, and evaluations and forecasts are marked as the author's opinion.

The trigger - a year-old recommendation and Codemode in Pi 1.0

The post is dated "written on October 06, 2026" and the author is Armin Ronacher. He recalls that more than a year ago he wrote a few posts recommending that people not load custom tools, or MCP servers, into the context and instead use more scripts. He singles out "Code Is All You Need" as the most important of them and says he also wrote "MCP needs code". With Pi 1.0, however, the team added MCP support through Codemode. The author writes that this is in some ways a long time coming, yet maybe somewhat surprising to some, and says he wants to share updated thoughts on what it all means.

  • Author and date: Armin Ronacher, October 6, 2026.
  • Tool in question: Pi. The author writes that Pi 1.0 added MCP support via Codemode.
  • This site's Pi 1.0 article covers the features of 1.0 as a whole, while this one follows the author's argument about Codemode.

What tools are and what bash cannot do

The author begins by pinning down what a tool is. When a harness supplies an LLM with tools to call, it supplies tool definitions, and these are translated into some token structure on the server side. Whether a model is encouraged to call a tool is the result of the reinforcement learning process, a subject he says he wrote about before.

He leans strongly toward the CLI and bash for two reasons. Calls are easy to compose, and the model also learns how the file system works while it is trained. When the model invokes something like echo foo > /tmp/test.txt, he explains, it also learns that afterwards there is a file called test.txt in /tmp.

Bash nevertheless has one fundamental limitation: it can only compose programs that run. The author writes that some things are not programs but are native tools to the LLM, and they sort of have to be.

  • read or view_image: when a multimodal model needs to read an image it cannot use cat, because the harness needs to inject the actual image payload into the protocol of the LLM.
  • Sub agents: to spawn and orchestrate them it is tricky to avoid tools provided by the harness. In theory the agent could provide a CLI tool that talks to the outer harness via environment variables and Unix sockets, but the author calls that a rather crude process.
  • Where the code runs: that approach has another issue, which the author unpacks in the next section.

Brains and hands - the harness and the execution environment

The author asks the reader to think about where all the pieces run. There are usually two systems. The first is the brain, the harness: it runs on one machine and is trusted. The second is the hands, often the same machine, where the tools actually execute. Pi now calls this the execution environment, and you can think of it as the target of all the operations.

What matters is that there is a dividing line between the harness brain and the target environment that runs bash and executes the tools. Splitting it in half has important consequences, he writes: the two run on different file systems and have different levels of trust. If you use a sandboxing solution such as Gondolin, for instance, your bash will be sandboxed just fine, but the harness itself will not be.

PartThe author's descriptionTrust and isolation
Brain (harness)Runs on one machineTrusted
Hands (execution environment, target)Often the same machine, but where bash and the tools actually runA different file system and a different level of trust from the harness
With a sandbox such as GondolinThe bash side is sandboxedThe harness itself is not sandboxed

What Codemode does - a harness-side sandbox

The author sums up what Codemode really does: it is a way for the LLM to express and orchestrate complex operations on the harness side, not on the execution-environment side. Codemode runs in the harness, in its own sandbox. In Pi that is QuickJS within a WASM runtime, with intentional limitations.

  • No network.
  • No file system.
  • No timers.
  • Limited RAM.

The only thing code can do inside is call more tools. The author adds that one could imagine Codemode running Scheme or some other language as well. For readers unfamiliar with it he puts it this way: it is basically a way to issue tool calls from within some language, in this case JavaScript. That allows those calls to be composed without necessarily going through the LLM's context. Credit for the name goes, he says, to friends at Cloudflare who coined it.

What changes in the context

The author uses a bash call as the example. If a bash call is issued as a regular tool call, Pi puts only the trailing 2000 lines into the context, and if the agent wants more it has to look at the overflow file itself. If the agent issues the same invocation via Codemode, the Codemode side gets the larger output sent structurally.

Because Codemode is JavaScript, the agent can express concurrent operations and basic workflows. A common pattern the author sees agents use now is to first probe 5-10 items from some tool response to see what it looks like, and then to write a Codemode script that processes the next n items.

Codemode can also put state into the transcript. One Codemode invocation can stash away data that the next call in the session can load again. The author stresses that this is on the harness host, not in the sandbox. In Pi, calls that make no sense in its traditional interface, such as generating images with an image model or classifying text with a one-shot classifier model, are exposed via Codemode but not via regular tools, where they would just waste context.

ItemRegular tool callCodemode (the author's description)
Large bash outputOnly the trailing 2000 lines go into the context and the rest goes to an overflow fileThe Codemode side receives larger output structurally
Concurrency and workflows—Being JavaScript, it can express concurrent operations and basic workflows
Learning the shape of a response—Probe 5-10 items first, then write a script that processes the rest

Three real sessions - images, issue triage, a game loop

The author shows Codemode invocations from recent Pi sessions of his own. He notes that none of this code is human written: it comes from real Pi sessions, just re-indented. The agent starts using Codemode automatically, either because the task is one where the model already naturally picks up that tool or because a user asked for it. In Pi, Codemode is by default only enabled when MCP is enabled, and it can be turned on with "defaultTools": ["+codemode"] in the settings. He adds that you can simply ask Pi to enable it. Generating images

Image generation is a feature Pi supports in the AI SDK core, but it is not a tool the agent can use. In the past the only way to use image models was to write a bespoke extension or to have the agent run node itself and use the internal image APIs. Because Pi exposes quite a few of the internal model APIs within Codemode, the agent can use them now.

const [painter] = await models.getAvailableOfType("image");
                    const result = await models.generateImages(painter, {
                      input: [{ type: "text", text: "A cute little puppy sitting on a grassy " +
                        "lawn, soft natural light, photorealistic" }],
                    });
                    if (result.stopReason !== "stop") return result.errorMessage;
                    for (const block of result.output) {
                      if (block.type === "image") image(block);
                      else text(block.text);
                    }

The call to image() sends the image back as image content to the LLM. On the harness side it feeds the image directly into the agent and also writes it to disk as a temporary artifact, in case the agent wants to pass that image back to bash.

Analyzing GitHub issues with a classifier

Classifier models such as Jev also do not fit well into an agent's workflows through the typical tools. Rather than making a bespoke tool available, Codemode lets the agent reach into the AI SDK and invoke them directly. The code the author shows uses Jev to mass process GitHub issues for a quick sentiment analysis.

const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
                    const r = await tools.bash({
                      command: "gh issue list --state open --limit 100 " +
                        "--json number,title,body,comments",
                    });
                    const issues = JSON.parse(r.output);
                    const results = await Promise.all(issues.map(async (issue) => {
                      const res = await models.classify(jev, {
                        state: {
                          title: issue.title,
                          body: (issue.body || "").slice(0, 4000),
                          comments: issue.comments.slice(-5).map(c => c.body.slice(0, 800)),
                        },
                        questions: {
                          sentiment: {
                            type: "choice",
                            instructions: "What is the overall sentiment of the author towards pi?",
                            criteria: {
                              positive: "Appreciative, happy, constructive praise",
                              neutral: "Matter-of-fact report or request without emotion",
                              negative: "Frustrated, annoyed, upset, or angry",
                            },
                          },
                          // ... frustration (score), kind (choice)
                        },
                      });
                      // ...
                    }));
                    store("sentiment_results", results);
  • It fetches up to 100 open issues (gh issue list with --limit 100).
  • For each issue it sends the body cut to 4000 characters and the last 5 comments cut to 800 characters each.
  • It asks three questions: the author's overall sentiment (a choice of positive, neutral or negative), how frustrated the reporter is (a score), and what kind of issue it is (a choice of bug, feature, question or other).
  • It saves the whole result with store() into the session transcript and returns only the 12 issues with the highest frustration score. The author notes that a later Codemode call can read that result back.
  • Promise.all is fine here, he explains, because Pi limits the total number of concurrent tool executions to four and keeps a queue for the rest.

A game debugging loop

As a more adventurous example the author uses Jev to drive a game engine for debugging. The agent knew his tankctl command and quickly built a minimal harness around it to drive a game loop. It runs a 30-step loop in which each step goes to the game engine for a text dump of what is going on and then to Jev to determine what to do next.

Calling MCP servers and "Codemode in Codemode"

The author writes that Codemode is obviously great for calling MCP servers. Pi does not expose any of the MCP tools to the LLM. Instead the agent first uses provided APIs to issue a tool search within Codemode and discover what it might be able to do with the connected servers. He says this form of progressive discovery makes the whole MCP business work well enough for a lot of use cases today.

In the example, the agent reaches for the Sentry MCP straight away, even without discovering the tools. The author presumes this is because it has already learned during the RL process what the Sentry MCP looks like. It does learn from what Pi injects into the system prompt that the Sentry server is available to begin with, so he adds that it is not completely guessing.

const orgs = await tools.mcp__sentry__find_organizations({});
                    const { organizations } = orgs.structuredContent;
                    const results = await Promise.allSettled(
                      organizations.map(org => tools.mcp__sentry__find_projects({
                        organizationSlug: org.slug,
                        regionUrl: org.regionUrl,
                      }))
                    );

The author says he really does not want to talk too much about MCP here, yet writes that MCP is a protocol that greatly benefits from Codemode. The problem, in part, is that MCP in practice often targets harnesses that do not use Codemode yet. He thinks the tide is shifting. In the meantime a temporary crutch has been to do what Cloudflare did and do Codemode within the MCP server. But now there is Codemode in Codemode, which he calls pretty bad.

  • It means double JSON escaping.
  • It is easy for smaller models to get confused by.
  • The inner code cannot call the outer tools.

So if you use the Cloudflare MCP servers in Pi, the agent needs to write JavaScript and funnel it through more JavaScript. The author writes that this is really not optimal, but that it is also understandable that it is happening.

What is wanted from MCP and what is left open

Asked how well Codemode works with MCP today, the author answers that it does not work amazingly well. MCP servers are not really targeting harnesses that use Codemode yet, though he thinks most harnesses support it by now. He lists four recommendations for making it work well.

ItemProblemThe author's explanation
Structured contentCodemode wants calls to return nicely formatted JSON, and many servers do not do that yetThe outputSchema system in MCP is great for that
Consistent resultsA server that optimizes tokens depending on how many items are in the result set can return inconsistent dataAn initial probe with 5 items can succeed and then fail when the server returns the maximum batch size
Large binary dataMCP does not yet support large binary data, so quite a few interesting use cases do not work well at allAll kinds of weird workarounds appear, such as pre-signed URLs that let file uploads happen through non-MCP channels
Composable tool searchThe MCP server may know better than the client which tool fits a taskThere is no good mechanism for a harness to fan out tool searches across multiple MCP servers, so it is emergent behavior that does not scale to several active servers

Asked whether this reverses what he wrote a year ago when he encouraged CLIs, the author says he does not think so. From his perspective the MCP ecosystem picked up on exactly what he pointed out a year ago works: code. Codemode goes beyond MCP in that it can act as a capable mechanism within the harness to express more freedom for the agent. He writes that some things still need to be figured out.

  • Durability: it is trickier with Codemode, and some ideas from durable workflow engines may have to be adopted to snapshot invocations.
  • Composition language: given its deterministic nature, something like Starlark may be a better language than JavaScript.
  • Images and binary data still have to be fleshed out.
  • The pattern does not work with smaller models.

He closes by writing that it is for sure not a perfect solution yet, but a quite useful pattern that he expects to leverage more.

What could not be confirmed

  • How large the sandbox RAM limit is: the post says only that RAM is limited and gives no figure.
  • Any difference in token counts or time with and without Codemode: the post contains no measurements.
  • Whether data kept with store() survives a session restart and in what format it is stored: the post says only that it goes into the session transcript.
  • How the approach Cloudflare wrote about first differs in detail from Pi's: the two posts were not compared item by item.
  • How well smaller models write Codemode scripts: the post mentions only that this is a limitation and gives no success rate.
