背景 — 为何必须在代码生成前固化需求与架构决策

随着基于大语言模型（LLM）的AI编码智能体快速演进，工程师根据自然语言提示直接生成和修改程序代码的效率获得了突破性提升。然而，仅凭寥寥数语的即兴提示词直接驱动代码生成的做法，在软件工程规模扩大后暴露出致命的缺陷。智能体往往会依据统计概率自行脑补未明确规定的需求细节，并在缺乏宏观架构约束的情况下选择最短视的实现路径，从而忽视长期的非功能性要求与系统权衡。

在缺乏正式前置规范的情况下直接生成代码，通常会在实际项目中诱发以下三大顽疾：

  • 主观脑补造成的需求扭曲：智能体在未说明的边缘场景下擅作主张，导致业务规则被悄然篡改。
  • 非功能性架构约束的全面脱落：实现方案绕过并发控制、幂等性边界与异常恢复通道，仅满足表层功能。
  • 跨工作会话引发的架构退化：新会话由于无法了解前序决策的取舍缘由，极易破坏既有设计的基石。

这种模糊性不仅导致实现阶段的高频回滚，更会在后续不同的智能体工作会话中引发破坏性的架构退化（Regression）。正如先前关于规划模式与正式计划文档的深度分析（plan_mode_planning_vs_plan_document_2026）以及基于代码反向推导架构图的智能体技能（archify_code_to_system_diagram_agent_skill_2026）所强调的，自主智能体编写的软件若要保持长期可维护性，必须建立明确的架构契约与设计记录。

2026年10月在GitHub上以MIT协议开源的alps-writer-plugins正是为了解决这一痛点而设计的插件套件。该工具面向Claude Code与OpenAI Codex环境，强制智能体在动笔写代码之前，先通过结构化问答梳理出清晰的产品需求规范（ALPS PRD），并将架构选型原因沉淀为架构决策记录（ADR）。

核心原则 — 舍弃可复原事实而仅保留可复现条件

该插件设计哲学的核心基石，是一条被称为「保留可复现条件，舍弃可复原事实（preserve reproducible conditions, not recoverable facts）」的法则。传统软件文档最普遍的失败形式，在于将代码中的函数列表、变量名、文件目录等瞬态细节巨细靡遗地抄写在文档中，导致代码稍有变动文档便沦为错误的摆设。

官方README提出了三道严格的判定门禁，用以划定信息的存储边界：

  • 需求门禁（Requirement gate）：若某项事实被抹除，未来智能体重新生成代码时，是否会导致生成的代码违背既定的业务数值、安全权限、状态机迁移、故障保证或边界条件？若存在此风险，则必须在该契约的主管层级（PRD或ADR）予以持久化保存。
  • 代码通读测试（Code-readthrough test）：若该事实并非刚性需求，且智能体通读现有源代码、单元测试或依赖配置文件（如Cargo.toml、package.json）即可完全复原出该信息，则坚决不在文档中重复记载，由代码单独承担。
  • ADR准入门禁（ADR admission gate）：若仅凭阅读源代码无法理解为何在多个备选方案中选中了当前架构，且改变该事实将颠覆整体系统架构设计，则必须将决策结论、选型理由、权衡取舍与前提假设固化在ADR中。

依据该法则，系统各层级的职责划分如下表所示：

系统及文档层级 持久化保留的内容（Persist） 严禁重复保留的内容（Do not persist）
ALPS PRD（产品需求） 用户痛点、可观测结果、业务契约、成功指标、明确排除项（Out of Scope）、长期架构约束 具体代码路径、技术栈细节清单、临时开发计划、复制粘贴的工单与日志
ADR（架构决策记录） 采纳的决策、严谨的需求契约、选型理由、对比过的替代方案、与具体实现无关的验证证据 选用的第三方SDK具体函数签名、数据库字段列表、内部调用时序流程
源码与自动化测试 模块结构、标识符名称、工程依赖、性能调优参数、可执行的验证逻辑 反向引用PRD或ADR文件路径的注释标记
Issue、PR与Commit 特定改动的具体意图、评审讨论记录以及字面版本历史 取代正规PRD或ADR作为架构唯一事实源（Source of Truth）

产物结构 — ALPS PRD、Lite ALPS与ADR的职责分工

插件管理的产物涵盖三种核心文档格式，分别服务于不同的生命周期阶段：

产物格式 README规范描述 使用阶段与触发命令 未确认的技术细节
Full ALPS PRD 专为智能体打造的9小节产品规范，将Out of Scope作为一等小节严格固化 构建完整复杂产品时（/alps-init） 9个小节各自的具体子标题完整清单
Lite ALPS 面向快速PoC的4小节极简格式（问题、C4 Context、核心体验、演示脚本） 快速原型验证与设计演示时（/lite-alps-init） 4个小节以外自定义扩展小节的支持机制
ADR 记录单一决策、选型缘由、需求契约与替代方案的独立Markdown文档 直接撰写（/adr-new）或由PRD移交（/feature-to-adr） 外部ADR可视化渲染工具的元数据规范
.mapping.json 追踪ADR规范键、文件路径、状态与前置依赖（dependsOn）的内部拓扑账本 执行代码实现前校验拓扑依赖时自动查询 超大型Monorepo中分包分区的管理方案
glossary.md 收录专业术语、行业缩写及特定定义的词汇表附录 日常语言无法清晰表达的业务词汇首次出现时 多语言环境下的词汇对照标注规范

产物之间的协同运行细则归纳如下：

  • Full ALPS全量约束：通过9个规范小节和依赖关系图谱（6.3）严格定义端到端业务切片功能。
  • Out of Scope置于核心：明确排除禁止实现的需求范围，避免智能体过度设计。
  • Lite ALPS极速验证：精简为问题定义、C4 Context图、核心体验与演示流程四大要素。
  • .mapping.json拓扑中枢：负责统一核验规范标识符、状态机变迁与dependsOn前置条件。

ALPS（Agentic Lean Product Spec）是专为AI智能体开发量身定制的PRD规范。传统PRD依赖人类工程师的行业常识去脑补细节，而智能体缺乏常识直觉，必须依托无歧义的显式约束才能生成可靠的代码。ALPS颠倒了传统编写流程：智能体主动发起聚焦的技术提问，人类进行裁决确认，未经显式批准的内容绝不落盘。

Lite ALPS则是为产品经理快速推进概念验证（PoC）而精简的4小节规范。人类只需确认核心问题与预期商业回报，智能体即刻草拟最小解决方案、产品级C4 Context上下文图、核心用户体验路径以及一套可直接执行的演示步骤。

ADR（架构决策记录）遵循adr.github.io的经典定义，沉淀针对重要架构需求（ASR）所作出的正当设计决策。决策一旦确立，其唯一键值与依赖链便被记录至.mapping.json中，指导后续的开发进程。

插件架构 — alps-writer向adr-writer的单向契约移交

alps-writer-plugins并未构建为一个臃肿的单体程序，而是拆分为alps-writer与adr-writer两个各自独立的插件系统。

alps-writer（PRD编写工具）
                      │
                      │ /feature-to-adr（单向契约移交）
                      ▼
                    adr-writer （ADR周期管理引擎，完全独立运行）
                      ├── /adr-new, /adr-impl, /adr-impl-refactor, /adr-impl-review
                      ├── /adr-sync（实现漂移修复）
                      ├── /adr-rollup（决策演进链整合）
                      └── SessionStart 钩子（基于.mapping.json恢复会话上下文）

这种解耦的核心优势在于：adr-writer完全不依赖且不读取ALPS规范。在没有PRD的轻量项目中，adr-writer可完全独立运作。两者的唯一纽带是alps-writer内置的单向移交指令/feature-to-adr。

  • adr-writer完全无依赖运行：无需PRD介入，可在任意既有项目中独立承担架构决策全生命周期管理。
  • 单向功能契约移交 (/feature-to-adr)：将ALPS PRD第7节中定义的功能条款完整无遗漏地映射至ADR。
  • 移交后PRD退居历史规划：移交完成后，代码实现的最高准则全权交由ADR接管。

四大接入流程 — 从遗留项目分析到PRD优先开发

该套件支持四种针对不同研发场景的工作流程，在Claude Code中以/skill-name调用，在Codex中以$skill-name调用：

  • 既有项目接入（Existing Project）：调用/adr-import [路径]，智能体利用EventStorming方法梳理现有代码与测试，提炼业务事件与规则边界。最终汇总为单一意图与冲突报告，经确认后批量生成Proposed状态的ADR基线。
  • PoC快速定义（PoC Authoring）：调用/lite-alps-init，通过快速问答确立4小节极简规范与验证演示脚本。
  • PRD优先开发（PRD-First）：通过/alps-init完成9小节详尽PRD，随后通过/feature-to-adr移交契约至ADR，进入标准化实现阶段。
  • 直接编写ADR（ADR-Only）：跳过PRD阶段，直接调用/adr-new [分类]确立单项决策并推进实现。

插件安装无需本地编译或npm繁琐安装，完全通过原生市场指令一键完成：

# 在Claude Code中注册市场并安装
                    /plugin marketplace add haandol/alps-writer-plugins
                    /plugin install alps-writer@alps-writer
                    /plugin install adr-writer@alps-writer
                    
                    # 在Codex中注册市场并安装
                    codex plugin marketplace add haandol/alps-writer-plugins
                    codex plugin add alps-writer@alps-writer
                    codex plugin add adr-writer@alps-writer

环境运行要求为对应的编码CLI工具以及Node.js 24或更高版本。

执行生命周期 — 拓扑依赖门禁与重构评审闭环

当ADR建立并处于Proposed状态后，从文本走向验证代码的整个过程受到严格门禁算法的约束。

最具代表性的是拓扑依赖门禁（Topological Dependency Gate）。当开发者触发/adr-impl [id]时，智能体首先遍历.mapping.json中声明的dependsOn前置列表。只要发现有任何前置依赖项未达到Accepted状态，智能体将拒绝编写当前功能的代码，要求先按拓扑顺序完成前置ADR的实现与验收。

当依赖全部就绪且初版代码编写完成后，系统将执行以下严密的闭环流转：

  • 初步实现与边界测试：智能体编写贯穿UI至数据层的端到端切片代码并运行测试。仅覆盖常规路径（Happy Path）的测试无法通过审核，必须全面覆盖边界异常条件。
  • 保真重构（/adr-impl-refactor）：初测通过后，智能体对代码执行效率、圈复杂度与重复率进行审查。仅允许实施高度可信且不改变既有行为的局部优化，并通过前后测试一致性进行核验。
  • 基于风险的最终评审（/adr-impl-review）：实施完备性审查，全面比对实现代码与ADR契约条款。只有评审通过，ADR的状态才会正式变更为Accepted。
  • 代码漂移修复（/adr-sync）：当人工修改或大规模重构导致代码与文档不一致时，执行/adr-sync进行精准校准。
  • 历史演进归并（/adr-rollup）：当同一逻辑决策因反复修改演化为分散的多篇ADR时，调用/adr-rollup将其整合为紧凑的单链记录。

非侵入式脚手架 — 插件移除后完全保留的标准Markdown体系

在采纳新型AI研发工具时，工程团队最担忧的往往是厂商技术绑定（Vendor Lock-in）。如果工具将核心知识加密或存储于私有格式中，团队将面临巨大的迁移风险。

alps-writer-plugins明确将自身定位为「可随时移除的非侵入式脚手架（A removable, non-invasive harness）」。工具在项目中产出的所有实体，均为标准的Markdown文件（docs/adr/*.md等）、干净的源代码以及通用的JSON文件（.mapping.json）。

此项非侵入设计保障了软件工程资产的三大独立性：

  • 完全标准的开源文件格式：文档纯净，可在GitHub代码仓库中直接渲染呈现。
  • 彻底消除隐式依赖残留：插件即便完全被卸载，也不会导致既有工程发生配置破坏。
  • 跨时代模型的无缝对接：沉淀的架构决策可直接被未来的新一代模型直接读取消费。
