Windows MAX_PATH 260-Character Limit: Tool Discrepancies and Silent Omissions

When paths are long, tools fail differently — suspect silent omission with exit code 0 before assuming a file is missing

2026-09-29 Dev & Infra

Introduction: The File Exists, but Tools Claim It Does Not

In Windows environments, engineers frequently encounter an unsettling anomaly during file-based automation workflows. A file exists on the storage volume, possesses intact data, and can be read by certain applications, yet specific command-line utilities and scripts assert that the file cannot be found or quietly return a false status without raising an error. The instinctive reaction is often to suspect file permissions, network latency, or encoding corruption. However, the root cause frequently lies in the legacy MAX_PATH (260-character) limitation of the Windows operating system, which manifests in wildly divergent failure patterns across different tools and runtimes.

This article is not a generic summary of registry tweaks. Instead, it demonstrates through rigorous empirical testing that different development tools fail in fundamentally inconsistent ways when path lengths exceed 260 characters, with silent omission by standard search utilities representing the most dangerous blind spot. By constructing a real 322-character deep file path on Windows 10, we systematically evaluated PowerShell 5.1, cmd.exe, Python 3.13, Git Bash, Node.js 22, and Git 2.48 to document exact console outputs, error codes, and behavioral discrepancies.

To maintain clear boundaries, foundational concepts regarding Windows batch scripting and PowerShell automation are established in our Windows Automation Guide. Incompatibilities regarding Korean character encoding and shell escaping are detailed in Why Shells Display Korean Filenames Inconsistently. Archive-level bit flag parsing is analyzed in Where Korean Filenames Break Inside Zip Files. The current analysis focuses exclusively on the physical length of filesystem paths.

1. Execution Environment and Real Boundaries of MAX_PATH (260 Characters)

All empirical results documented herein were gathered from direct command execution on a single Windows 10 machine as a standard (non-elevated) user. Each measurement is a single run in this environment.

  • Operating System: Windows 10 Pro (Build 10.0.19045)
  • Command Shells: Windows PowerShell 5.1.19041.6456 (.NET Framework v4.0.30319), cmd.exe
  • Language Runtimes: Python 3.13.3, Node.js v22.16.0
  • POSIX Emulation and Tools: Git for Windows 2.48.1.windows.1, Git Bash (GNU sed 4.9, GNU Awk 5.0.0), curl 8.12.1 (Schannel)
  • Privileges: Standard user (non-elevated)
  • Test Target Path: …/tech_lab/lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
  • Path Metrics: Absolute file path length of 322 characters, directory path length of 294 characters

1.1 The 260-Character Limit Breakdown and 248-Character Directory Threshold

According to official Microsoft technical documentation (Naming Files, Paths, and Namespaces), the traditional maximum path length in the Windows API is governed by the MAX_PATH constant, defined exactly as 260 characters. This allocation encompasses a drive letter (e.g., C:, 2 characters), a backslash separator (\, 1 character), the constituent subdirectories and filename components, and a mandatory terminating null character (\0, 1 character). Consequently, the maximum usable path string is 259 characters.

However, an essential nuance frequently overlooked by software practitioners is that directories face an earlier boundary at 248 characters (MAX_PATH - 12). Microsoft documentation specifies that a directory path cannot exceed MAX_PATH minus 12 characters. This constraint reserves sufficient namespace buffer for creating at least one standard 8.3 filename (8 characters + 1 dot + 3 extension characters = 12 characters) inside that directory. Our empirical tests validate this specification: creating a 231-character directory succeeded without issue, whereas creating a 252-character directory failed immediately with WinError 206.

1.2 Verification of the LongPathsEnabled Registry Setting

Modern editions of Windows 10 and Windows Server provide a registry flag, LongPathsEnabled, intended to lift MAX_PATH restrictions across the OS. Prior to initiating tests, we queried the state of this key via PowerShell and cmd.

reg query "HKLM\SYSTEM\CurrentControlSet\Control\FileSystem" /v LongPathsEnabled
Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' -Name LongPathsEnabled | Select-Object LongPathsEnabled

The console output confirmed the default operating system configuration:

HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\FileSystem
    LongPathsEnabled    REG_DWORD    0x0

LongPathsEnabled
----------------
               0

With LongPathsEnabled set to 0, the legacy 260-character restriction remained fully active across the operating system. All subsequent findings reflect this baseline state.

3. Silent Omission in cmd dir /s: The Hidden Danger of Exit Code 0

The most hazardous finding in our investigation occurred within the Windows Command Prompt (cmd.exe) when executing recursive directory listings via dir /s.

cmd /c "dir `"$d`""            # Standard path single directory
cmd /c "dir `"\\?\$d`""        # Prefixed directory
cmd /c "type `"$f`""
cmd /c "type `"\\?\$f`""
cmd /c "dir /s /b `"$b\lp`""   # Recursive listing
# Exit codes checked via $LASTEXITCODE

The captured output and return codes were as follows:

=== cmd dir plain dir
The system cannot find the path specified.
=== cmd dir prefixed dir
 Volume in drive \\?\C: has no label.
 Directory of \\?\C:\…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb\cccccccccccccccccccc
2026-09-29  ?? 07:38                16 long_file_name_for_test.txt
               1 File(s)             16 bytes
=== cmd dir /s lp
…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa
…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb

dir plain exit=1
dir prefixed exit=0
type plain exit=1
hello long path
type prefixed exit=0
dir /s lp exit=0

3.1 Differences Between Single-Directory dir and Recursive dir /s /b

When executing dir or type directly against a single long path, cmd exits with exit=1 and outputs The system cannot find the path specified. The failure is evident and allows scripts to handle the error.

Conversely, when dir /s /b performed recursive traversal from an upper directory, it listed directories up to 252 characters (aaaaaaaa...) and 273 characters (bbbbbbbb...), but silently dropped the 294-character folder (cccccccc...) and the 322-character test file entirely from the output. Crucially, the command completed with exit code 0.

3.2 Operational Hazards in Search Scripts and Batch Jobs

This behavior is dangerous because a loop like the following (an illustrative pattern, not executed in this article) treats the dir /s /b output as the full work list:

FOR /F "delims=" %%F IN ('dir /s /b "C:\Data\*"') DO (
    call :ProcessFile "%%F"
)

Because dir /s outputs no errors and returns code 0, the batch process assumes the listing is complete. Files under a dropped path, like the cccc… folder in this test, never enter the work list and are skipped silently. Neither the output nor the exit code reveals that anything is missing.

4. Handling Extended Paths with the \\?\ Prefix in Python and PowerShell

When scripts must interact with deep directory structures, developers can use the extended-length path prefix \\?\ accepted by the Unicode Windows API functions.

4.1 The Role of \\?\ and Relative Path Constraints

According to Microsoft documentation, the Unicode Windows API functions accept an extended-length path with the \\?\ prefix, for a maximum total path length of 32,767 characters. The documentation says such a path is passed to the system with minimal modification, so you cannot use forward slashes as separators or . and .. for the current and parent directories.

However, the \\?\ prefix cannot be used with relative paths. The documentation states that because you cannot use the prefix with a relative path, relative paths are always limited to MAX_PATH characters. The prefix must be paired with an absolute path that starts with a drive letter (e.g., \\?\C:\Path\To\File).

4.2 shutil.rmtree Failures and Bottom-Up Cleanup

Cleaning up test trees demonstrated another failure mode when calling Python shutil.rmtree() on deep structures.

# Excerpt from t1_clean.py
shutil.rmtree(targets[0])                 # Standard path removal
os.path.exists(P + targets[0])
for root, dirs, files in os.walk(P + t, topdown=False):
    os.remove(...)
    os.rmdir(...)
os.rmdir(P + t)

The console output showed the failure and subsequent remediation:

plain rmtree lp: OSError winerror= 145 filename_len= 252
still exists (prefixed check): True
prefixed delete lp files= 2 dirs= 4 exists after= False
prefixed delete g\lp files= 1 dirs= 4 exists after= False
prefixed delete gr1\lp files= 1 dirs= 4 exists after= False

Standard shutil.rmtree failed with WinError 145 (The directory is not empty). Because standard APIs could not enumerate or delete the 322-character file inside, the directory remained occupied. In this test, running os.walk(topdown=False) on the \\?\-prefixed path and removing leaf files before parent directories deleted all three trees with nothing left (exists after= False).

5. Git and core.longpaths: Worktree Protection vs. Deep Repository Limits

Version control systems like Git frequently encounter path length issues on Windows. While Git for Windows offers core.longpaths, its practical boundaries must be clearly understood.

5.1 Default Settings and Scope of core.longpaths

We first inspected the origin and default state of Git path settings:

git init -q .
git config --show-origin --show-scope --get-all core.longpaths
git config --system --show-origin --get core.longpaths
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1 git config --get core.longpaths

On this PC the user had set core.longpaths=true in the global config, but the system-level query returned exit code 1, and so did the query with both global and system configs excluded. In other words, long path support is off unless you set it (default false). The bundled Git for Windows documentation says it is disabled by default because long paths are not supported by Windows Explorer, cmd.exe and the Git for Windows tool chain (msys, bash, tcl, perl…).

5.2 Staging and Restoring Long Paths in the Worktree

When a 330-character file exists within the working tree, the effect of core.longpaths is decisive. This run disabled the global config (GIT_CONFIG_GLOBAL=/dev/null) and pointed only the object directory to a short path via GIT_OBJECT_DIRECTORY, isolating the long worktree file:

--- longpaths unset: add long file
warning: could not open directory 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/': Filename too long
fatal: pathspec 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt' did not match any files
exit=128
--- longpaths=true: add long file
exit=0
lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
s.txt
--- restore (checkout) longpaths unset
fatal: cannot create directory at 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb': Filename too long
exit=128
--- restore longpaths=true
exit=0
hi

Without the setting, Git emits a Filename too long warning and fails with fatal: pathspec did not match. Setting -c core.longpaths=true immediately allows staging and checkout restoration to succeed.

5.3 Object Storage Failures When Repository Roots Are Deep

However, core.longpaths=true does not resolve all issues. When the Git repository root itself was located at a deep path (232 characters), git add failed even for short files. This ran with the PC's global core.longpaths=true still in effect:

--- git add (no longpaths)
error: unable to write file .git/objects/45/b983be36b73c0788dc9cbcb76cbb80fc7bb057: No such file or directory
error: lp/…/long_file_name_for_test.txt: failed to insert into database
error: unable to index file 'lp/…/long_file_name_for_test.txt'
fatal: adding files failed
exit=128
--- -c core.longpaths=true add short.txt
error: unable to write file .git/objects/1d/3aaf18909062b31aeeeb3b683f1c2fad3e304e: No such file or directory
error: short.txt: failed to insert into database
error: unable to index file 'short.txt'
fatal: adding files failed
exit=128

Even when adding a 9-character file (short.txt), Git failed with unable to write file .git/objects/...: No such file or directory. With the repository root at 232 characters, the object folder .git/objects/45 was 248 characters and the object file path 291 characters, beyond 260. In this environment (Git 2.48.1.windows.1), setting core.longpaths=true only changed the message from “Filename too long” to “unable to write file … No such file or directory”; the failure remained. In short, core.longpaths rescued worktree files here but not a deep repository's own object writes.

6. Bypassing Length Constraints Using 8.3 Short Paths (ShortPath)

To prove that path length alone caused the Git object failure, we conducted a controlled experiment utilizing Windows 8.3 short paths (ShortPath).

6.1 Principles of 8.3 Short Paths

Folders in this environment had 8.3 short names (like PROGRA~1). Querying the ShortPath property via Scripting.FileSystemObject in PowerShell compressed the 232-character repository root down to approximately 87 characters (C:\Users\<user>\…\tech_lab\ctl).

6.2 Controlled Experiment via GIT_DIR Environment Variables

Simply changing directory (cd) to the 8.3 path was ineffective: git rev-parse --show-toplevel printed the long name again, and git add failed with the same error. It succeeded only when GIT_DIR was passed the short name directly:

# (Scripting.FileSystemObject).GetFolder(...).ShortPath → C:\Users\<user>\…\tech_lab\ctl  (about 87 chars)
$env:GIT_DIR = "$s\.git"; $env:GIT_WORK_TREE = $s
git add a.txt; "exit=$LASTEXITCODE"
git ls-files -s

The console output showed immediate success:

exit=0
100644 b88e8890e5b4d028a6d3849b4f4979cad8b07d3c 0	a.txt

Without modifying Git binaries or altering filesystem contents, shortening the repository pointer path resulted in immediate success (exit 0). This confirmed conclusively that physical path length was the sole point of failure.

7. 5-Step Diagnostic Procedure Before Concluding a File Does Not Exist

When automated processes report missing files or path exceptions on Windows, follow this systematic checklist:

  • Step 1: Count total path length — Before troubleshooting access control or replication, evaluate the absolute path length via PowerShell ($path.Length) or Python (len(path)).
  • Step 2: Scrutinize ambiguous error diagnostics — Messages like does not exist, No such file or directory, The system cannot find the path specified, and WinError 145 (directory not empty) frequently mask path length exhaustion.
  • Step 3: Cross-check recursive enumeration tools — Do not trust exit code 0 from cmd dir /s /b; verify directory contents using Git Bash find or Node.js scripts.
  • Step 4: Use \\?\ prefixes with absolute paths — For one-off inspections or recursive deletions, avoid relative paths and supply canonical \\?\C:\... paths to OS APIs.
  • Step 5: Verify Git repository nesting depth — If core.longpaths=true fails during object staging, check the depth of the repository root and pass 8.3 short paths via GIT_DIR and GIT_WORK_TREE.

7.1 Measuring Path Lengths and Verification Order

Always evaluate path lengths using fully resolved canonical paths rather than relative path fragments. In this test the base folder itself was 228 characters, and that length directly shaped the results (the git repository failures). If your working directory sits deep, log its path length at the start of a job.

7.2 Best Practices for Automated Batch Scripts

Avoid relying on cmd dir /s in mission-critical batch automation on Windows. Cross-check the listing with methods that did list the long path in this test — Get-ChildItem -LiteralPath with the \\?\ prefix (single folder), Python os.listdir with the prefix, Git Bash find, or Node.js fs.readdirSync — before passing it on.

8. Frequently Asked Questions (FAQ)

Here are answers to the most common questions regarding Windows path length constraints:

  • Q1. Do all programs fail on Windows when a path exceeds 260 characters?
    A. No. In our 322-character path test on this machine, cmd, PowerShell, and Python failed, whereas Git Bash (MSYS2) read the file and wrote a new one, and Node.js 22 read the file and listed the directory, all without error. Results differ by tool.
  • Q2. Why is cmd dir /s particularly dangerous with long paths?
    A. In our test, dir /s /b silently dropped the 294-character folder and the 322-character file from the output list (the 273-character folder was still listed) while exiting with return code 0. Scripts relying on this output falsely assume the files do not exist.
  • Q3. Why does git add fail despite setting core.longpaths=true?
    A. The setting only protects working tree files. If the repository root is deeply nested, internal object paths (.git/objects/xx/...) exceed 260 characters, failing loose object creation. Move the repository or use 8.3 short paths.
  • Q4. Can the \\?\ extended path prefix be used with relative paths?
    A. No. According to the official documentation, the \\?\ prefix cannot be used with a relative path, so relative paths are always limited to MAX_PATH (260 characters).
  • Q5. Does enabling LongPathsEnabled in the Windows registry fix all issues?
    A. No. Applications must also declare longPathAware in their manifests, and a reboot might be required. The documentation says the setting only affects applications modified to take advantage of the new feature (we did not switch it on here).

9. Unverified Items

The following items could not be directly verified due to environment constraints:

  • Behavior After Modifying LongPathsEnabled to 1: We did not change this value for this article, so we did not verify behavioral changes across tools following a registry modification and reboot, relying instead on official Microsoft documentation.
  • Git Bash Internal Translation Mechanics: Although Git for Windows documentation states that msys and bash toolchains do not support long paths, Git Bash successfully processed 322-character paths in practice. The precise binary-level mechanism used by MSYS2 was not inspected.
  • Cross-Platform Comparison: Direct empirical comparisons with Linux and macOS were not performed, as testing was conducted on a single Windows 10 environment.

| git `add` (deep repository root) | Failed (exit 128) | — | Even with `core.longpaths=true`, fails on `.git/objects/...: No such file or directory` | Internal storage failure |
| git `add` (8.3 short path injection) | **Succeeded (exit 0)** | — | Passing 8.3 short path (`C:\Users\<user>\…\tech_lab\ctl`) via `GIT_DIR` and `GIT_WORK_TREE` succeeds immediately | Path abbreviation workaround |

## 2. Symptom and Root Cause Comparison Table

| Displayed Symptom | Surface Conclusion by Tool | Actual Underlying Cause | Verification and Mitigation |
|---|---|---|---|
| Returns `False` (no error) | File does not exist | PowerShell and Python treat paths exceeding 260 characters as non-existent | Measure path character length using `$f.Length` or `len(f)` |
| `Cannot find path ... because it does not exist` | Path cannot be found | Plain path exceeds 260 characters (readable with `\\?\`) | Prepend `\\?\` to the absolute path |
| `The system cannot find the path specified` | Path does not exist | Plain path exceeds 260 characters (`dir`/`type` with `\\?\` succeeded) | Use `\\?\` prefix or 8.3 short path |
| **Exit code 0, file missing from list** | Search complete, file not found | cmd `dir /s` silently skips long path items without raising an error | Do not rely solely on exit code 0; cross-check with recursive tools |
| `winerror= 206` (filename or extension too long) | Directory or file name too long | Directory path length exceeds 248 characters (MAX_PATH - 12) | Shorten parent paths or prepend `\\?\` prefix |
| `winerror= 145` (directory not empty) | Cannot delete non-empty folder | Standard API cannot enumerate deep inner files to delete them first | Use `\\?\` prefix with bottom-up deletion (`os.walk(topdown=False)`) |
| `.git/objects/...: No such file or directory` | Git internal object missing | Repository root is too deep; internal 38-char hash path exceeds 260 characters | Move the repository to a short path, or pass an 8.3 short path directly to `GIT_DIR` and `GIT_WORK_TREE` |

## 3. 5-Step Long Path Troubleshooting Checklist

- [ ] **1. Count the path length**: When encountering "file not found" errors or `False` returns, measure the full absolute path length first (`len(path)` or `$path.Length`) before assuming the file is missing.
- [ ] **2. Check the 248-character directory boundary**: As documented in the Windows API, directory paths are constrained at `MAX_PATH - 12` (248 characters) rather than 260 (confirmed by failure at 252 characters).
- [ ] **3. Never trust `dir /s` exit code alone**: cmd `dir /s /b` completed with exit code 0 while silently omitting the 294-char folder and 322-char file from the output list (the 273-char folder was still listed).
- [ ] **4. Use `\\?\` with absolute paths for file operations**: The Windows extended-length prefix `\\?\` allows up to 32,767 characters, but it cannot be used with relative paths.
- [ ] **5. Work around deep Git repositories with 8.3 short names**: Setting `core.longpaths=true` only rescued work tree files; if the repository root itself is deep, keep the repository at a short path, or, as in this test, pass 8.3 short paths directly to `GIT_DIR` and `GIT_WORK_TREE` (`cd` alone failed).
