Every Post Deserves an Exit: 플랫폼 종속을 넘어 마크다운과 MDX로 내 글을 온전히 소유하는 방법

2026-09-14 IT/기술

1. 플랫폼 락인과 블로그 콘텐츠 소유권의 위기

수년간 특정 상용 플랫폼에서 블로그를 운영해온 창작자라면 누구나 한 번쯤 마음속 깊은 불안과 피로감을 느껴보았을 것입니다. 포털 사이트의 검색 알고리즘이 업데이트될 때마다 정성스레 작성한 수백, 수천 편의 글이 검색 상단에서 자취를 감추거나, 플랫폼 운영사의 정책 변경으로 인터페이스, 광고 배치, 모바일 뷰어 서식이 일방적으로 뒤흔들리는 경험은 한국 블로거들에게 결코 낯설지 않습니다. 특히 국내 웹 생태계에서 네이버 블로그와 티스토리는 수많은 개발자, 엔지니어, 전문직 종사자, 기록가들이 지식과 경험을 축적해온 가장 대중적인 핵심 공간이었지만, 역설적으로 그 안에 쌓인 방대한 콘텐츠는 플랫폼의 닫힌 데이터베이스 안에 단단히 결속되어 있습니다.

이러한 현상을 기술적인 관점에서는 플랫폼 종속(Vendor Lock-in)이라고 규정합니다. 글을 쓴 개인은 자신이 창작한 텍스트의 온전한 저작권을 가지고 있다고 믿지만, 플랫폼 제공자가 외부 반출을 위한 공식 API나 기계 가독성(Machine-readable)을 갖춘 표준 내보내기 기능을 지원하지 않는다면 실제로는 데이터의 가공, 백업, 이전, 영구 보존에 관한 실질적 주권을 상실한 것과 다름없습니다. 블로그 서비스를 새로운 정적 사이트나 독립형 CMS로 이전하고 싶어도, 과거에 누적된 방대한 글들을 일일이 수작업으로 복사하여 붙여넣고 이미지를 다시 내려받아 업로드해야 하는 극심한 노동 비용 때문에 대부분의 블로거는 이전을 중도 포기하고 플랫폼의 울타리 안에 머무는 타협을 선택하게 됩니다.

가공과 재활용이 차단된 데이터 고립의 문제

상용 포털 플랫폼에 저장된 글들은 주로 해당 서비스에 특화된 비표준 HTML 태그나 독자적인 에디터 JSON 구조로 렌더링됩니다. 이와 같은 구조는 플랫폼 내부의 뷰어 컴포넌트에서는 매끄럽게 보이지만, 외부 브라우저나 독립 렌더러로 꺼내는 순간 레이아웃이 완전히 깨지고 인라인 스타일이 충돌하며 이미지 경로가 누락되는 심각한 파편화 문제를 야기합니다. 특히 개발자나 기술 문서 작성자의 경우, 자신이 과거에 체계적으로 정리해둔 알고리즘 풀이, 트러블슈팅 기록, 소프트웨어 아키텍처 다이어그램 등을 개인 옵시디언(Obsidian) 지식베이스나 깃허브 기반의 개발 문서 사이트로 통합하려 할 때 데이터 반출의 불가능이라는 거대한 기술적 장벽에 직면하게 됩니다.

결국 진정한 의미의 디지털 콘텐츠 소유권이란 단순히 화면 상단에 내 닉네임이 작성자로 표시되는 정서적 권리를 넘어섭니다. 그것은 본문의 원본 텍스트는 물론이고 본문에 인라인으로 포함된 다양한 이미지 자산, 글의 작성 시점과 카테고리 태그 같은 메타데이터, 그리고 문서 내부에서 다른 글을 참조하는 하이퍼링크 구조까지 완전한 개방형 표준 규격으로 내려받아 자신의 로컬 저장 장치에 안전하게 보관할 수 있는 실질적인 데이터 통제권을 의미합니다. 플랫폼이 내일 당장 서비스를 개편하거나 계정을 제한하더라도 내 기록만큼은 온전히 보전될 수 있어야만 진정한 소유권이 성립하는 것입니다.

탈출구가 필요한 수천 편의 기록들

지식의 가치는 시간이 흐를수록 복리로 축적됩니다. 5년 전, 10년 전에 고민하며 작성했던 개발 삽질기나 아키텍처 분석 글은 오늘날에도 여전히 유효한 통찰을 제공하며, 최근 급부상한 개인 맞춤형 AI 시대에는 로컬 LLM을 위한 검색 증강 생성(RAG) 지식베이스나 파인튜닝 데이터셋으로 재탄생할 수 있는 매우 값진 자산입니다. 하지만 이 귀중한 기록들이 네이버나 카카오의 특정 서버에 갇힌 채 RSS 피드로 최신 50개 정도만 겨우 노출되는 상태에 머물러 있다면, 플랫폼의 운영 축소나 약관 개정이라는 외생적 변수 한 번에 사용자의 수년간 노력이 허공으로 사라질 수 있는 구조적 취약성을 안게 됩니다.

이러한 문제의식을 배경으로 탄생한 오픈소스 프로젝트가 바로 ExitPress입니다. "모든 글은 탈출구를 가질 자격이 있다(Every post deserves an exit)"라는 명확하고 단호한 슬로건을 내건 이 도구는, 폐쇄된 국내 포털 블로그 서비스에 갇혀 있던 글들을 개방형 표준인 마크다운(Markdown)과 최신 웹 표준인 MDX 포맷으로 구출해내는 강력하고 실용적인 마이그레이션 파이프라인을 제시합니다.

2. ExitPress 개요와 개발 배경

ExitPress는 웹상에 공개된 블로그 게시글을 정밀하게 스캔하여 표준 Markdown/MDX, YAML frontmatter, 최적화된 로컬 자산(이미지 파일), 그리고 복구 및 재구성이 가능한 manifest.json 메타데이터 파일 형태로 내보내는 오픈소스 마이그레이션 도구입니다. 중앙 집중형 클라우드 서버에 내 계정 정보를 넘겨주어야 하는 서드파티 상용 SaaS와 달리, 사용자의 로컬 컴퓨터에서 샌드박스 형태로 안전하게 실행되는 구조를 채택하여 개인정보 유출이나 중간 데이터 탈취 위험 없이 투명하게 백업을 완수할 수 있습니다.

이 프로젝트의 시작은 개발자 본인이 오랜 기간 겪었던 매우 현실적이고 절박한 고민에서 비롯되었습니다. ExitPress를 설계하고 개발한 엔지니어 mym0404는 네이버 블로그 플랫폼에 무려 2,000편이 넘는 방대한 글들을 수년에 걸쳐 정성껏 기록해왔습니다. 그러나 글의 편수가 늘어날수록, 플랫폼 내부에서는 자신이 쓴 글들을 일괄적으로 수집하거나 구조화하여 로컬에 백업할 수 있는 수단이 전무하다는 치명적인 한계에 부딪혔습니다. 수년간 쌓아 올린 2,000여 편의 소중한 지식을 외부 저장소로 안전하게 이전하고 싶었지만 신뢰할 만한 도구가 존재하지 않자, 개발자 스스로 문제를 근본적으로 해결하기 위해 직접 도구 구축에 나선 것입니다.

단순 스크래핑을 넘어선 구조적 변환 엔진

과거에도 웹페이지 URL을 입력하면 마크다운 텍스트로 변환해주는 간이 파이썬 스크립트나 크롬 확장 프로그램 형태의 스크래퍼는 존재했습니다. 하지만 네이버 블로그나 티스토리 같은 국내 대형 블로그 플랫폼은 단순한 정적 HTML 페이지가 아니라, 십수 년간 개편을 거듭해온 기형적이고 복잡한 독자 렌더링 계층을 가지고 있습니다. 본문 한 편 안에서도 단순 문단, 이미지 그리드 갤러리, 코드 스니펫 블록, 스티커, 인용구 박스, 링크 미리보기 카드, 지도 첨부 등 수십 종의 독자 컴포넌트가 각양각색의 HTML 클래스와 인라인 스타일로 뒤엉켜 있습니다. 일반적인 범용 HTML-to-MD 변환기로 이를 긁어올 경우, 들여쓰기와 서식이 완전히 무너지고 이미지가 엉뚱한 위치로 이동하거나 코드 블록의 들여쓰기가 깨지는 등 결과물을 도저히 실무에 재활용할 수 없게 됩니다.

ExitPress는 이러한 문제를 원천적으로 해결하기 위해 중간 요소(Block) 추상화 계층이라는 체계적인 컴파일러형 아키텍처를 도입했습니다. 원본 글이 네이버 블로그의 스마트에디터든 티스토리의 커스텀 HTML 컨테이너든 상관없이, 입력단에서 먼저 수백 가지의 마크업 요소를 고유한 의미론적 단위인 '블록(Block)'으로 표준화하여 추출합니다. 그런 다음, 사용자가 지정한 최종 출력 타깃(GFM, Fumadocs, Docusaurus, Nextra)에 맞추어 사전에 정의된 템플릿 문법을 통해 재조합하는 N×M 확장 구조를 확립했습니다. 덕분에 입력 플랫폼과 출력 프레임워크가 서로 독립적으로 확장될 수 있는 견고한 기술적 토대를 마련했습니다.

오픈소스 생태계와 재현 가능한 아카이빙

ExitPress는 수정과 배포가 자유로운 MIT 라이선스로 완전 공개되어 있어, 누구나 소스코드를 자유롭게 열람하고 감사(Audit)하며 자신의 블로그 구조에 맞추어 기능을 확장할 수 있습니다. 특히 내보내기 작업이 완료되었을 때 산출물 디렉터리에 함께 생성되는 manifest.json 파일은 이 도구의 완성도를 보여주는 핵심 요소입니다. 이 파일에는 글의 원본 플랫폼 URL, 고유 글 번호, 수집 시점의 타임스탬프, 카테고리 매핑 계층 구조, 그리고 본문에 포함되었던 이미지 자산들의 원본 URL 및 로컬 파일 경로 매핑 정보가 머신 리더블한 JSON 포맷으로 꼼꼼히 기록됩니다.

이러한 메타데이터 보존 구조 덕분에 ExitPress를 통한 백업은 일회성 텍스트 덤프에 그치지 않습니다. 훗날 사용자가 다른 데이터베이스 시스템으로 글을 적재하거나, 전혀 새로운 정적 사이트 생성기(SSG)나 CMS 엔진으로 콘텐츠를 다시 이전하고자 할 때, 이 manifest.json 파일을 파싱하는 간단한 스크립트만으로 언제든 전체 파이프라인을 무결하게 재현하고 자동화할 수 있는 강력한 데이터 지속성을 확보하게 됩니다.

3. 지원 입력 플랫폼과 핵심 제약 사항

ExitPress는 대한민국 블로그 시장의 압도적인 지분을 차지하고 있는 네이버 블로그와 카카오 티스토리를 정밀하게 지원합니다. 두 플랫폼은 서비스 운영 역사만 20년에 달하는 만큼, 시기별로 에디터 엔진이 수차례 전면 교체되었고 그에 따라 데이터베이스에 저장된 마크업 형태도 완전히 제각각입니다. 따라서 완성도 높은 백업 도구가 되기 위해서는 각 플랫폼의 세대별 마크업 특징을 정확히 식별하고 분기 처리할 수 있어야 합니다.

네이버 블로그의 경우 2000년대부터 널리 사용된 레거시 스마트에디터 2.0(SE2), 모바일 반응형 웹 시대를 겨냥해 출시되었던 스마트에디터 3.0(SE3), 그리고 현재 표준으로 자리 잡은 스마트에디터 ONE(SE4)까지 폭넓게 수집을 지원합니다. 티스토리의 경우 클래식 HTML 모드와 신형 블록 에디터를 포함하여, 웹 브라우저 상에 HTML 기반으로 렌더링되는 모든 공개 글을 파싱 대상으로 삼습니다.

에디터 세대별 마크업 격차 해소

네이버 블로그의 세대별 에디터는 내부 구조가 완전히 다른 소프트웨어라고 보아도 무방할 만큼 큰 구조적 차이를 보입니다. 과거 SE2 시절 작성된 게시글은 <p> 태그와 <font color="...">, 인라인 <span style="..."> 태그가 무질서하게 뒤섞여 있으며, 이미지는 전용 레이아웃 테이블 안에 배치되어 있는 경우가 흔합니다. 반면 SE3와 스마트에디터 ONE은 모바일 뷰어와 반응형 그리드를 염두에 두고 설계되어 se-component와 se-text-paragraph 같은 구조화된 클래스 기반 블록으로 렌더링되며, 캡션과 정렬 속성이 별도의 모듈형 컴포넌트로 분리되어 있습니다.

ExitPress는 이러한 세대별 마크업 격차를 극복하기 위해 각각의 에디터 엔진 전용 파서를 내장하고 있습니다. SE2의 레거시 인라인 스타일 숲에서 의미론적인 헤딩(Heading)과 강조(Bold/Italic)를 정밀하게 복원해내는 한편, SE3와 ONE의 블록형 컴포넌트에서는 불필요한 레이아웃 래퍼(Wrapper) 태그를 깔끔하게 제거하고 순수한 마크다운 제목 계층(H1~H4)과 목록, 인용구 구조로 정규화합니다. 오랜 기간 블로그를 운영하며 에디터가 여러 번 바뀌었던 블로거라도 글 작성 시기에 구애받지 않고 균일한 품질의 마크다운 문서를 얻을 수 있는 이유가 여기에 있습니다.

★반드시 확인해야 할 핵심 제약: 공개 글만 수집 가능

ExitPress를 본격적으로 사용하기 전에 모든 사용자가 반드시 숙지해야 하는 가장 결정적인 기술적 제약 사항이 있습니다. 현재 ExitPress는 웹상에 전체 공개(Public)된 게시글만 스캔하여 수집할 수 있습니다.

이 도구는 사용자의 네이버 아이디나 카카오 계정의 로그인 세션(쿠키, 인증 토큰, 브라우저 세션 스토리지 등)을 탈취하거나 모방하여 비공개 인트라넷 영역으로 접근하는 크래킹 방식이 아닙니다. 일반 웹 사용자가 브라우저를 통해 주소를 입력했을 때 로그인 없이도 즉시 열람할 수 있는 공개 HTTP 페이지를 안전하게 스캔하는 표준 웹 스크래핑 아키텍처를 기반으로 동작합니다. 따라서 다음과 같은 유형의 게시글은 수집 대상에서 완전히 제외됩니다:

  • 네이버 블로그에서 작성자 본인만 볼 수 있도록 설정된 비공개 게시글 및 임시 저장 글
  • 서로이웃 또는 특정 그룹 이웃에게만 열람 권한이 부여된 제한 공개 게시글
  • 티스토리 플랫폼에서 비공개로 설정되었거나 비밀번호를 입력해야 열람할 수 있는 보호 글
  • 포털 계정 로그인 및 성인 본인인증을 통과해야만 본문이 렌더링되는 연령 제한 게시글
  • 비공개 카테고리 내부에 속해 있어 카테고리 목록에서 접근 경로가 차단된 글

만약 일기장, 가계부, 미완성 초고 등 개인적인 비공개 메모를 백업할 목적으로 ExitPress를 구동한다면, 수집 목록에 해당 글들이 전혀 나타나지 않아 당황할 수 있습니다. 비공개 글의 백업이 반드시 필요한 상황이라면, ExitPress로 스캔 작업을 진행하는 동안 일시적으로 글의 공개 범위를 전체 공개로 전환한 뒤 백업이 끝난 즉시 원상복구하거나, 플랫폼에서 제공하는 수동 텍스트 복사 방식을 병행해야 합니다.

4. 4가지 마크다운·MDX 출력 형식 비교와 선택 가이드

블로그 마이그레이션 도구를 사용할 때 흔히 겪는 또 다른 실패 사례는, 추출된 결과물이 특정 형식에 지나치게 치우쳐 있어 새로운 정적 사이트 생성기나 노트 앱에 넣었을 때 파일 경로가 꼬이거나 메타데이터가 인식되지 않는 문제입니다. ExitPress는 이러한 파편화를 방지하기 위해 글로벌 개발자 생태계와 기술 문서 플랫폼에서 가장 널리 쓰이는 4대 표준 출력 어댑터를 완벽히 지원합니다.

사용자는 로컬 웹 대시보드에서 내보내기를 실행할 때 자신의 마이그레이션 목적지에 부합하는 출력 형식을 손쉽게 선택할 수 있으며, 어댑터는 각 프레임워크가 요구하는 파일 명명 규칙, 프론트매터 스키마, 사이드바 구성 파일을 한 번에 빌드해냅니다.

개인 보관을 위한 GFM과 최신 문서 사이트용 MDX

첫 번째 출력 형식인 GFM(GitHub Flavored Markdown)은 표준 마크다운 문법을 따르는 index.md 파일로 글을 저장합니다. 카테고리 폴더 하위에 글 제목 또는 슬러그 폴더를 생성하고 그 안에 index.md와 해당 글에서 사용된 로컬 이미지를 함께 패키징합니다. 이 방식은 복잡한 리액트 컴포넌트나 자바스크립트 빌드 과정이 전혀 필요 없기 때문에, 옵시디언(Obsidian)이나 로그시크(Logseq) 같은 로컬 마크다운 지식베이스 도구, 깃허브 저장소 자체 위키, 혹은 노션(Notion)으로의 대량 가져오기(Import)에 가장 이상적입니다.

반면 나머지 3개 어댑터는 자바스크립트 컴포넌트를 마크다운 내부에서 직접 렌더링할 수 있는 차세대 문서 규격인 MDX(Markdown with JSX)를 채택하고 있습니다. MDX 어댑터들은 단순히 파일 확장자만 .mdx로 바꾸는 것이 아니라, 각 정적 사이트 생성기가 라우팅과 문서 계층 트리를 구성할 때 필수적으로 요구하는 메타데이터 스크립트까지 함께 생성합니다:

  • GFM: 카테고리/글폴더/index.md 형태로 저장되며 순수 텍스트와 프론트매터 보존에 최적화
  • Fumadocs: Next.js 기반 최신 문서 프레임워크로, content/docs/**/index.mdx 경로에 본문을 두고 meta.json 파일로 카테고리와 순서를 자동 구성하며 이미지는 public/에 배치
  • Docusaurus: 메타(Meta)가 주도하는 글로벌 문서 도구로, docs/**/index.mdx 경로와 함께 카테고리 메타데이터인 _category_.json을 생성하고 자산은 static/에 저장
  • Nextra: Next.js 생태계에서 널리 쓰이는 정적 콘텐츠 엔진으로, content/**/index.mdx 경로와 디렉터리 구조를 정의하는 _meta.js 스크립트를 생성하고 이미지는 public/에 분리

프레임워크 덮어쓰기 없는 안전한 폴더 분리

ExitPress의 MDX 어댑터 설계에서 돋보이는 부분은 기존 프로젝트와의 완벽한 공존성입니다. 도구가 임의로 웹 애플리케이션 프레임워크 전체를 스캐폴딩하거나 사용자의 기존 설정 파일(예: docusaurus.config.js, next.config.js)을 덮어쓰지 않습니다. 모든 내보내기 결과물은 프로젝트 하위의 output/ 디렉터리 안에 완벽히 격리된 구조로 생성됩니다.

따라서 사용자가 이미 운영 중인 Docusaurus 블로그나 Nextra 사이트가 있다면, output/ 폴더 아래에 생성된 docs/나 content/ 폴더, 그리고 정적 자산이 담긴 static/이나 public/ 폴더만 복사하여 기존 프로젝트의 해당 위치에 붙여넣기만 하면 즉시 모든 글이 사이트에 통합됩니다. 라우팅 오류를 방지하기 위해 파일 경로와 폴더명은 영문 ASCII 안전 문자로 인코딩될 수 있으나, 화면에 렌더링되는 실제 제목, 카테고리 표시명, 그리고 YAML frontmatter의 메타데이터 필드는 원본 한글 텍스트를 그대로 완벽하게 유지합니다.

5. 자산 보존과 링크 관리: 이미지 처리와 백링크 변환

블로그 마이그레이션을 직접 시도해본 엔지니어들이 가장 뼈아프게 겪는 실패 지점은 텍스트가 아니라 이미지 자산의 유실과 내부 링크의 단절입니다. 마크다운 파일로 본문을 아무리 깔끔하게 변환했더라도, 이미지 주소가 기존 포털 서버의 URL을 그대로 가리키고 있다면 플랫폼이 외부 사이트로부터의 핫링크(Hotlinking) 차단 보안 정책을 활성화하는 순간 모든 이미지가 일제히 엑스박스로 깨지게 됩니다. 또한 글 본문 중간중간에 삽입되어 있던 "지난 연재 글 보러가기" 링크들이 여전히 과거 네이버 블로그 주소로 남아 있다면, 새 블로그로 유입된 독자가 링크를 클릭하자마자 다시 예전 플랫폼으로 튕겨 나가는 어처구니없는 사용자 경험이 발생합니다.

ExitPress는 이러한 마이그레이션 사고를 근본적으로 방지하기 위해 정교하게 설계된 3대 이미지 처리 파이프라인과 스마트 백링크 치환 엔진을 기본 탑재하고 있습니다.

3가지 유연한 이미지 처리 전략

사용자의 개인 서버 인프라 환경과 저장 공간 여유는 저마다 다릅니다. ExitPress는 이러한 현실적 차이를 고려하여 사용자가 직접 선택할 수 있는 3가지 이미지 처리 옵션을 제공합니다:

  1. 원격 주소 유지: 기존 네이버나 티스토리 서버에 올라가 있는 이미지의 절대 URL을 마크다운 본문에 그대로 유지합니다. 로컬 디스크 공간을 거의 차지하지 않고 변환 속도가 가장 빠르지만, 포털 측의 이미지 CDN 접근 제한이 걸리면 이미지가 표시되지 않을 수 있는 위험을 감수해야 합니다.
  2. 로컬 다운로드 및 압축: 본문에 포함된 모든 이미지 파일을 로컬 컴퓨터로 직접 내려받고, 웹 서비스에 적합하도록 압축 최적화를 수행한 뒤, 마크다운 본문의 이미지 경로를 로컬 상대 경로(예: ./assets/image.webp)로 자동 변경합니다. 플랫폼의 서버 상태와 무관하게 100% 완전한 오프라인 영구 보관이 가능해집니다.
  3. PicList 커스텀 업로드: 내려받아 압축된 이미지를 검증된 오픈소스 이미지 관리 엔진인 PicList(PicGo 코어 기반)와 연동하여 사용자의 AWS S3, GitHub 저장소, Cloudflare R2 등 커스텀 클라우드 스토리지로 자동 전송하고, 본문의 이미지 링크를 해당 신규 CDN URL로 일괄 교체합니다.

스마트 이미지 중복 방지와 용량 최적화

장기간 운영된 블로그를 분석해보면, 글 상단에 공통으로 배치하는 블로그 배너, 특정 시리즈물에 반복해서 삽입한 챕터 안내 이미지, 카테고리 대표 썸네일 등 수십에서 수백 개의 글에서 완전히 동일한 이미지가 반복해서 쓰이는 경우가 매우 빈번합니다. 단순한 순차 다운로더를 사용할 경우 2,000편의 글에서 수천 장의 동일한 이미지가 중복으로 다운로드되어 기가바이트 단위의 디스크 용량을 낭비하고 네트워크 트래픽을 불필요하게 소모하게 됩니다.

ExitPress는 이미지를 다운로드하는 과정에서 이미지 바이너리 해시와 크기, 원본 메타데이터를 정밀 대조합니다. 이미 이전에 다운로드되어 로컬에 존재하는 파일과 동일한 이미지임이 확인되면, 중복으로 내려받거나 외부 스토리지에 중복 업로드하지 않고 기존에 저장된 동일 자산의 경로를 영리하게 재참조하도록 링크만 연결합니다. 이 최적화 덕분에 디스크 사용량을 수십 퍼센트 절감하고 전체 백업 시간을 비약적으로 단축할 수 있습니다.

내부 백링크 보존을 통한 링크 그래프 복원

정성스럽게 작성된 기술 블로그일수록 "지난번 1편 글을 먼저 읽고 오시면 이해가 쉽습니다"와 같이 자신의 이전 게시글을 인용하는 내부 링크가 촘촘한 그물망처럼 엮여 있습니다. 네이버 블로그 URL(예: blog.naver.com/아이디/글번호) 형태의 링크를 그대로 방치하면 새 사이트의 링크 그래프가 완전히 망가지게 됩니다.

ExitPress는 전체 게시글을 스캔하는 단계에서 각 글의 고유 식별자, 원본 URL, 제목, 발행 일자를 매핑 테이블로 메모리에 구축합니다. 이를 바탕으로 본문 파싱 시 내부 글을 가리키는 링크가 발견되면, 사용자가 설정한 새로운 도메인 주소(예: https://myblog.dev/docs/...)나 로컬 상대 경로(../category/post-slug.md)로 하이퍼링크를 매끄럽게 자동 치환합니다. 플랫폼을 탈출하더라도 수년간 쌓아 올린 글과 글 사이의 지식 연결망이 단 한 줄도 끊어지지 않고 완벽히 계승되는 것입니다.

6. 설치와 실행 절차: mise부터 로컬 웹 UI까지

ExitPress는 파이썬 기반의 단순 스크립트나 클릭 한 번으로 실행되는 단일 윈도우 실행 파일(.exe)이 아닙니다. 최신 타입스크립트(TypeScript) 기반 모노레포 아키텍처로 구축된 노드(Node.js) 생태계 도구입니다. 따라서 평소 깃(Git)과 터미널 환경을 자주 접해보지 않은 일반 블로거에게는 초기 설치 및 환경 설정 단계에서 약간의 진입장벽이 느껴질 수 있습니다.

그러나 최신 런타임 및 패키지 환경 관리자인 mise를 기반으로 모든 요구사항이 표준화되어 있으므로, 공식 절차를 순서대로 차분히 따라가면 누구나 오류 없이 자신의 로컬 환경에서 백업 서버를 구동할 수 있습니다.

사전 요구사항과 mise 환경 준비

ExitPress를 빌드하고 실행하기 위한 핵심 시스템 요구사항은 개발 도구 버전 관리자인 mise입니다. mise는 프로젝트 루트 디렉터리에 포함된 mise.toml 설정 파일을 읽어 들여, 프로젝트가 필요로 하는 올바른 Node.js 버전과 pnpm 패키지 관리자를 사용자의 시스템에 자동으로 프로비저닝해줍니다.

운영체제의 터미널(Windows의 경우 PowerShell, macOS 및 Linux의 경우 bash/zsh)을 실행한 후 아래 명령어를 순차적으로 입력하여 저장소를 복제하고 빌드 환경을 설정합니다:

git clone https://github.com/mym0404/exitpress.git
cd exitpress
mise trust
mise install
pnpm install

여기서 mise trust는 현재 디렉터리의 mise 설정 파일을 신뢰하도록 시스템에 승인하는 명령이며, mise install을 통해 프로젝트 실행에 필요한 노드 런타임이 격리 설치됩니다. 이후 고성능 패키지 관리자인 pnpm install을 실행하면 모노레포에 정의된 모든 코어 파서, 어댑터, 웹 UI 라이브러리 의존성이 로컬 디스크에 준비됩니다.

로컬 웹 서버 구동과 6단계 사용 순서

환경 설정이 끝났다면 아래의 단일 명령어로 로컬 백업 애플리케이션 서버를 기동합니다:

pnpm start

명령어가 성공적으로 실행되면 터미널에 로컬 서버 구동 안내가 나타납니다. 웹 브라우저(Chrome, Edge, Safari 등)를 열고 http://localhost:4173 주소로 접속하면, 복잡한 CLI 옵션을 일일이 외울 필요가 없는 세련되고 직관적인 웹 대시보드가 브라우저 화면에 펼쳐집니다. 사용자는 화면의 지시에 따라 다음 6단계 순서로 마이그레이션을 진행하게 됩니다:

  1. 블로그 플랫폼 선택: 네이버 블로그(Naver Blog) 또는 티스토리(Tistory) 라디오 버튼을 선택합니다.
  2. 블로그 ID 또는 URL 입력: 백업하려는 대상 블로그의 아이디(네이버 계정명) 또는 전체 블로그 URL을 입력창에 정확히 기입합니다.
  3. 공개 글 스캔: 스캔(Scan) 버튼을 클릭하여 원격 블로그에서 현재 공개되어 있는 게시글 목록과 카테고리 트리 구조를 비동기로 조회합니다.
  4. 카테고리/날짜 범위 선택: 스캔된 결과 중에서 백업하고자 하는 특정 카테고리를 체크하거나 특정 시작일과 종료일을 지정하여 글 범위를 필터링합니다.
  5. 내보내기 실행: 원하는 마크다운 어댑터(GFM, Fumadocs, Docusaurus, Nextra 중 택일)와 이미지 처리 방식, 백링크 옵션을 설정한 뒤 내보내기(Export) 버튼을 누릅니다.
  6. output/ 아래 결과 확인: 변환 작업이 완료되면 프로젝트 디렉터리 내의 output/ 폴더로 이동하여 구조화된 마크다운 파일과 에셋 자산들을 확인합니다.

프로젝트 내부의 문서 페이지나 파서 데모를 자체적으로 확인하고 싶다면 저장소에 명시된 Vite 프리뷰 빌드 명령어를 실행할 수 있습니다:

mise exec -- pnpm --filter @exitpress/web build:pages
mise exec -- pnpm --filter @exitpress/web exec vite preview --config vite.website.config.ts

이처럼 백엔드에서는 복잡한 DOM 트리 탐색과 비동기 다운로드 로직이 돌지만, 사용자 접점은 깔끔한 로컬 웹 GUI로 추상화되어 있어 개발 지식이 깊지 않은 사용자도 직관적으로 작업을 완수할 수 있습니다.

7. Rule-based 파서와 AI 에이전트의 지속적 개선 구조

웹 문서 파서나 스크래퍼를 제작할 때 개발자를 가장 괴롭히는 본질적인 문제는 '현실 웹페이지의 무한한 변칙성'입니다. 블로거마다 사용하는 에디터 서식이 다르고, 수년 전 포털이 실험적으로 도입했다가 조용히 폐기한 구형 컴포넌트 태그, 사용자가 외부 웹사이트에서 복사해 붙여넣은 출처 불명의 인라인 스타일 등 온갖 예외 케이스(Edge Cases)가 곳곳에 숨어 있습니다. 수천 편의 글을 긁어오다가 단 하나의 특이한 블록 때문에 전체 프로세스가 뻗어버리거나 내용이 통째로 증발하는 사고가 발생하는 것이 기존 스크래퍼들의 일상적인 한계였습니다.

ExitPress는 이 난제를 돌파하기 위해 결정론적인 규칙 기반(Rule-based) 파서와 AI 코딩 에이전트의 피드백 루프를 결합한 혁신적인 진화 구조를 구축했습니다.

수백 가지 HTML 파싱 규칙의 정교한 매핑

ExitPress의 파서 코어는 거대 언어 모델(LLM)에 의존해 텍스트를 생성하는 비결정론적 방식이 아니라, 수백 가지의 검증된 HTML 파싱 규칙을 바탕으로 원본 태그를 엄격하게 마크다운으로 매핑하는 순수 규칙 기반 엔진으로 작동합니다. 이는 토큰 비용을 전혀 발생시키지 않으며, 대량의 글을 초당 수십 편씩 초고속으로 처리할 수 있는 결정론적 일관성을 유지합니다.

예를 들어 인용구 블록 하나를 처리하더라도, 단순 따옴표 형태인지, 좌측 컬러 바 형태인지, 포스트잇 형태인지에 따라 최적의 마크다운 블록쿼트(>) 또는 콜아웃 문법으로 정확히 변환합니다. 복잡한 표(Table) 내부의 셀 병합이나 코드 블록 안의 공백 들여쓰기, syntax 언어 식별자까지 손상 없이 안전하게 유지해냅니다.

블록 파싱 실패 시 AI 에이전트를 활용한 기여 워크플로

만약 내 블로그에 포털의 최신 스티커나 비표준 컴포넌트가 포함되어 있어 특정 블록이 마크다운으로 깔끔하게 변환되지 않는다면 어떻게 해야 할까요? ExitPress 저장소는 오픈소스 생태계와 코딩 AI 에이전트가 함께 문제를 해결할 수 있는 독창적인 자동화 워크플로를 README를 통해 안내하고 있습니다:

  1. ExitPress 공식 GitHub 저장소를 자신의 계정으로 포크(fork)합니다.
  2. 로컬 컴퓨터에 초고속 자바스크립트 런타임인 bun을 설치하고 정상 설치 여부를 확인합니다:
bun --version
  1. 코딩 AI 에이전트에게 내 블로그 아이디를 넘겨주며 자동 인제스트 스킬 실행을 요청합니다:
$ingest-blog {내 블로그 id}

이 명령어는 저장소 내의 .agents/skills/ingest-blog에 정의된 전용 에이전트 스킬을 실행합니다. AI 에이전트는 대상 블로그를 탐색하여 기존 파서가 올바르게 해석하지 못한 HTML 블록을 단위별로 찾아내고 구조화합니다. 그런 다음 해당 블록을 완벽히 지원하는 파싱 코드를 스스로 작성하고, 기존의 다른 테스트 케이스들이 깨지지 않는지 픽스처(Fixture) 테스트와 코드 커버리지(Coverage) 검증을 거친 뒤, GitHub에 자동으로 Pull Request(PR)를 제출합니다.

인간 메인테이너는 AI 에이전트가 작성해 올린 PR 목록을 검토하여 옵션을 다듬고 정식 코드베이스에 병합합니다. 사용자가 겪은 개별 파싱 실패 사례가 인공지능과 오픈소스 협업을 통해 시스템 전체의 완성도를 끌어올리는 강력한 집단 지성 파이프라인으로 전환되는 것입니다.

8. 독립형 블로그 마이그레이션 시 주의할 점과 기술적 한계

ExitPress를 사용하여 네이버 블로그나 티스토리의 글들을 완벽한 마크다운과 이미지 자산으로 추출했다고 해서 블로그 마이그레이션의 모든 여정이 끝난 것은 아닙니다. 추출된 마크다운을 들고 새로운 독립 도메인(예: GitHub Pages, Vercel, Netlify, Cloudflare Pages 등)에 블로그를 개설하여 글을 배포할 때, 기술적·운영적 측면에서 반드시 짚고 넘어가야 할 엄중한 현실적 과제들이 존재합니다.

이러한 주의사항을 사전에 고려하지 않고 무작정 수천 편의 글을 새 사이트에 일괄 게시할 경우, 검색 엔진의 페널티를 받거나 기존 독자층과의 연결 고리가 완전히 단절되는 역효과를 초래할 수 있습니다.

검색 엔진의 중복 콘텐츠(Duplicate Content) 페널티 위험

마이그레이션 과정에서 가장 주의를 기울여야 하는 기술적 지점은 바로 검색 엔진의 중복 문서 판정입니다. 기존 네이버 블로그나 티스토리에 수천 편의 글이 여전히 웹상에 발행되어 있는 상태에서, 완전히 동일한 본문 텍스트를 새로운 독립 도메인의 웹사이트에 대량으로 업로드하면 구글이나 네이버의 검색 로봇은 새 사이트를 '타인의 글을 무단으로 복제한 스크랩 사이트' 혹은 '검색 품질을 저해하는 어뷰징 문서'로 오판할 위험이 매우 높습니다.

일반적인 독립 웹사이트 간의 이전이라면 기존 사이트의 HTML 헤더에 <link rel="canonical" href="신규글URL"> 태그를 명시하여 원본 소유권이 새 사이트로 이전되었음을 검색 로봇에 알릴 수 있습니다. 그러나 네이버 블로그는 사용자가 HTML <head> 태그를 임의로 수정할 수 없도록 엄격히 통제되므로 캐노니컬 태그를 활용한 정상적인 SEO 이전 처리가 구조적으로 불가능합니다.

따라서 성공적인 독립 블로그 안착을 위해서는 다음과 같은 현실적이고 단계적인 운영 전략이 권장됩니다:

  • 신규 사이트에 글을 게시한 후 검색 색인이 생성되는 추이를 모니터링하면서, 기존 네이버 블로그의 글 본문을 핵심 요약문 형태로 축소하고 "전체 글은 새 기술 블로그에서 읽으실 수 있습니다"라는 안내 링크를 배치하는 방식
  • 검색 유입이 거의 없는 과거 아카이브 성격의 글부터 순차적으로 마이그레이션하고 원본 글을 비공개로 전환하는 단계별 이전 방식
  • 새 독립 블로그는 개발자 포트폴리오 및 오프라인 기술 위키 용도로 운영하고, 대중적인 포털 검색 유입용 채널로는 기존 블로그를 병행 유지하는 이원화 채널 전략

플랫폼 종속 소셜 데이터의 단절과 한계

ExitPress는 본문 텍스트, 코드 블록, 이미지, 날짜, 카테고리, 내부 링크 등 '콘텐츠 그 자체'는 훌륭하게 추출해내지만, 플랫폼 데이터베이스에 묶여 있는 소셜 상호작용 데이터까지 복원해낼 수는 없습니다. 지난 수년간 독자들이 정성스레 남겨준 댓글과 답글, 공감(좋아요) 수, 스크랩 통계, 누적 방문자 수 등은 포털 서비스의 고유 자산이므로 마크다운 파일로 이전될 수 없습니다.

또한 개발 도구와 웹 호스팅에 익숙하지 않은 일반 블로거에게는 마크다운 파일을 추출한 이후에도 이를 서비스할 호스팅 서버를 세팅하고, 커스텀 도메인을 구매하여 DNS를 연결하며, 댓글 시스템(Giscus, Utterances, Disqus 등)을 직접 붙이는 과정이 상당한 기술적 부담으로 다가올 수 있습니다. 그럼에도 불구하고 플랫폼의 일방적인 정책 변경이나 서비스 종료의 위협으로부터 벗어나, 내가 수년간 흘린 땀과 지식을 내 컴퓨터의 텍스트 파일로 온전히 소유할 수 있다는 사실은 크리에이터의 디지털 주권을 지탱하는 가장 견고한 방패가 되어줍니다.

9. 확인하지 못한 것

본 포스팅에서 다룬 기술 분석과 기능 명세는 ExitPress 공식 GitHub 저장소와 공개된 기술 문서를 엄격히 대조하여 작성되었습니다. 그러나 다음 항목들은 공식 문서에 구체적인 근거 자료나 통계 수치가 명시되어 있지 않아 최종적으로 확인하지 못했습니다:

  • 비공개 및 서로이웃 글 지원 로드맵: 공식 저장소 README에는 "현재는 공개 글만 수집할 수 있습니다"라는 안내 문구만 기재되어 있으며, 향후 세션 쿠키 수동 주입이나 브라우저 자동화(Playwright 등)를 통한 비공개 글 추출 지원 여부 및 구체적인 개발 계획은 공식 문서에서 확인하지 못했습니다.
  • PicList 외부 스토리지 세부 프로바이더 지원 목록: PicList(PicGo 엔진)를 통해 커스텀 Provider에 업로드할 수 있다고 명시되어 있으나, AWS S3와 GitHub 외에 공식적으로 사전 테스트를 통과한 상용 오브젝트 스토리지(Cloudflare R2, Supabase Storage, MinIO 등)의 전체 목록은 공식 자료에 나열되어 있지 않아 확인하지 못했습니다.
  • 스마트에디터 ONE의 신규 컴포넌트 파싱 완전성: 네이버 블로그의 장소(지도) 첨부 모듈, 네이버 폼 투표, 글감(책/영화) 링크 카드 등 최근 추가된 세부 컴포넌트들에 대한 파싱 지원율 및 누락 여부에 대한 구체적인 백분율 통계는 공식 자료에서 확인하지 못했습니다.
