이 글은 gg582 가 oborona.zip 에 쓴 「SQPOLL은 불안형 여친이다」(2026-09-19)와 Linux man-pages 의 io_uring_setup(2) 를 바탕으로 한다. 블로그 글은 io_uring 의 기본 모드와 SQPOLL 을 애착 유형 비유로 설명하며 sq_thread_idle, NEED_WAKEUP, 커널 버전별 권한 같은 세부는 다루지 않는다. 그 세부는 man 페이지에서 가져왔다. 두 출처가 말하지 않는 부분은 「이 글의 해석」이라고 표시한다.

1. '불안형 여친' 비유로 본 io_uring과 SQPOLL의 등장 배경

io_uring 은 유저 공간과 커널이 링 버퍼를 통해 입출력을 주고받는 리눅스의 비동기 입출력 인터페이스다. 동작 모드 중 SQPOLL(Submission Queue Polling)은 커널 스레드가 제출 큐를 폴링해 시스템 콜 없이 입출력을 제출할 수 있게 하는 대신 CPU 를 쓴다.

최근 국내 기술 커뮤니티 GeekNews 에 소개되며 개발자들의 이목을 끈 oborona.zip 블로그의 글 「SQPOLL은 불안형 여친이다」(gg582)는 이러한 기술을 일상적 비유로 설명했다. 원문은 글의 전개를 「I/O Uring은 대체 뭐야?」, 「기본 모드/인터럽트 주도 모드」, 「SQPOLL이라는게 대체 뭔데 '불안형 여친'이라고 하는건데?」, 그리고 「좀 웃기는 요약」이라는 총 4개의 절로 나누어 구성했다. 저자는 io_uring 의 동작을 애착 유형에 빗대어 설명한다.

블로그는 기본 모드(인터럽트 주도 모드)를 「자기 생활이 있는 안정형 여친」에, SQPOLL 을 「불안형 여친」에 빗댄다. man 페이지에 따르면 SQPOLL 플래그를 지정하면 제출 큐 폴링을 수행하는 커널 스레드가 만들어지고, 애플리케이션은 시스템 콜 없이 입출력을 제출하고 회수할 수 있다. 블로그는 이 상태를 「오빠 지금 어디야 내 마음은 타들어가는데 어디 있어?」라는 말투로 표현한다.

블로그는 IORING_SETUP_SQ_AFF 도 언급하며 「살짝 스토커 성향도 생긴다」, 「CPU는 타 들어간다」 같은 표현을 쓴다. 이 글의 질문은 시스템 콜을 없애는 대신 CPU 코어를 쓰는 선택이 언제 맞는가다.

2. 기본 인터럽트 주도 모드와 폴링 모드의 메커니즘 차이

이 절의 일반 설명은 이 글의 정리이며, 원문 근거는 아래 SQPOLL 문단이다. 일반적으로 기본 모드에서는 애플리케이션이 제출 뒤 io_uring_enter(2) 로 커널에 알리고, 기다리는 동안 CPU 를 다른 일에 쓸 수 있다.

이 글의 정리로는 이 방식은 대기 중에 CPU 를 다른 프로세스가 쓸 수 있어 CPU 효율이 좋다. 블로그의 요약도 「성능보단 CPU를 덜 태우고 싶으면 안정형 여친」이라고 적는다.

man 페이지는 SQPOLL 을 이렇게 설명한다. 「When this flag is specified, a kernel thread is created to perform submission queue polling. An io_uring instance configured in this way enables an application to issue I/O without ever context switching into the kernel. … the application can submit and reap I/Os without doing a single system call.」 시스템 콜 비용이 얼마인지는 두 출처 모두 수치를 제시하지 않는다.

즉 SQPOLL 의 핵심은 커널 스레드가 제출 큐를 폴링해 애플리케이션이 시스템 콜 없이 제출하고 회수할 수 있게 하는 것이다. 이 커널 스레드의 이름은 man 페이지에 나오지 않는다.

3. 공유 링 버퍼 기반의 SQE 제출과 CQE 회수 구조

이 절의 링 구조 설명은 일반적인 io_uring 구조를 이 글이 정리한 것이며 두 출처의 문장이 아니다. io_uring 은 유저 공간과 커널이 공유하는 링 버퍼를 활용하며, 제출 큐(Submission Queue, SQ)와 완료 큐(Completion Queue, CQ)가 있다. 이 구조에서 작업을 처리하는 일반적인 흐름은 다음과 같다.

  • 애플리케이션은 제출 큐(SQ)의 빈 슬롯에 작업 명세인 SQE(Submission Queue Entry)를 채운다.
  • SQE 를 채운 뒤 SQ 링의 tail 을 갱신해 새 작업이 있음을 알린다.
  • SQPOLL 에서는 커널 스레드가 제출 큐를 폴링해 새 SQE 를 처리한다(man 페이지: a kernel thread is created to perform submission queue polling).
  • 작업이 끝나면 결과는 완료 큐(CQ)의 CQE(Completion Queue Entry)로 돌아오고, 애플리케이션은 완료 큐를 지켜본다(man 페이지: watching for completions on the completion queue).

이 글의 정리로는 SQPOLL 에서 제출과 회수가 공유 메모리 조작으로 이루어지므로 시스템 콜을 부르지 않아도 된다. 다만 커널 스레드가 잠든 경우에는 다음 절의 깨우기 절차가 필요하다.

4. sq_thread_idle과 깨우기 핸드셰이크(NEED_WAKEUP)

man 페이지는 커널 스레드가 sq_thread_idle 밀리초보다 오래 유휴이면 struct io_sq_ring 의 flags 필드에 IORING_SQ_NEED_WAKEUP 비트를 설정한다고 설명한다. 이 글의 추론으로는, 이런 유휴 처리가 없다면 폴링 스레드가 빈 큐를 계속 확인하며 CPU 를 쓰게 된다. man 페이지가 유휴 CPU 소비를 직접 다루는 것은 아니다.

sq_thread_idle 은 struct io_uring_params 의 필드이며 밀리초 단위다. man 페이지는 기본값을 적지 않는다.

이 글의 추론으로는, 스레드가 잠들면 애플리케이션이 나중에 SQ 에 항목을 넣어도 스레드가 스스로 알아채지 못하므로 깨우는 절차가 필요하다. man 페이지에 기술된 절차는 다음과 같다.

  • 커널 스레드는 유휴 시간이 sq_thread_idle 밀리초를 넘으면 flags 필드에 IORING_SQ_NEED_WAKEUP 을 설정한다.
  • 애플리케이션은 tail 을 기록한 뒤 flags 를 읽는다. man 페이지는 「Ensure that the wakeup flag is read after the tail pointer has been written」 라며 flags 읽기에 load-acquire 의미를 쓰라고 안내한다.
  • NEED_WAKEUP 이 설정되어 있으면 io_uring_enter(fd, 0, 0, IORING_ENTER_SQ_WAKEUP) 를 호출한다(man 페이지의 코드 예).
  • 이 확인을 빠뜨리면 어떻게 되는지는 man 페이지가 서술하지 않는다. 이 글의 추론으로는 깨우기를 빠뜨리면 제출한 I/O 가 처리되지 않을 수 있다.

man 페이지는 SQPOLL 링에서는 애플리케이션이 io_uring_enter(2) 를 직접 부르지 않으며, 그것은 보통 liburing 의 io_uring_submit(3) 이 처리한다고 적는다.

원시 시스템 콜을 직접 다룰 때는 위 확인을 직접 해야 한다는 것은 이 글의 해석이다.

5. IORING_SETUP_SQ_AFF와 CPU 코어 전소의 대가

man 페이지에 따르면 IORING_SETUP_SQ_AFF 는 폴링 스레드를 struct io_uring_params 의 sq_thread_cpu 로 지정한 CPU 에 묶으며, IORING_SETUP_SQPOLL 과 함께 지정할 때만 의미가 있다. 컨테이너 환경에서 cgroup 의 cpuset.cpus 가 바뀌면 묶인 CPU 세트도 바뀔 수 있다고 man 페이지는 적는다.

이 글의 추론으로는, 폴링 스레드를 특정 코어에 묶으면 그 코어를 다른 일에 쓰기 어려워진다. 블로그는 이 지점을 「CPU는 타 들어간다」고 표현한다.

이 글의 판단으로는, 요청이 드문 서비스에서는 폴링에 코어를 쓰는 비용이 이득을 넘을 수 있다. 두 출처 모두 이를 수치로 보이지 않는다.

6. 리눅스 커널 권한 변천사 — CAP_SYS_NICE에서 비특권 허용까지

man 페이지는 커널 버전에 따라 SQPOLL 사용 조건이 달라졌다고 적는다.

  • 5.11 이전: 애플리케이션은 io_uring_register(2)의 IORING_REGISTER_FILES 로 사용할 파일 집합을 등록해야 하며, 그러지 않으면 제출된 I/O 가 EBADF 로 실패한다. 이 조건이 없는 동작은 IORING_FEAT_SQPOLL_NONFIXED 기능 플래그로 확인할 수 있다.
  • 5.11: 파일 등록이 더 필요 없고, CAP_SYS_NICE 기능을 가진 사용자는 루트가 아니어도 SQPOLL 을 쓸 수 있다.
  • 5.13 이후: 이 요구도 완화되어 새 커널에서는 특별한 권한이 필요 없다. man 페이지는 5.13 보다 오래된 일부 안정(stable) 커널도 비특권 SQPOLL 을 지원할 수 있다고 적는다.

이 글의 해석으로는, 권한 문턱이 낮아진 만큼 도입 여부는 워크로드에 맞춰 신중히 판단할 몫이 사용자에게 있다. 채택 사례나 확산 정도는 두 출처가 다루지 않는다.

7. 기본 모드 vs SQPOLL 핵심 지표 및 설정 플래그 비교

기본 모드와 SQPOLL 모드의 주요 특성을 정리한 비교는 다음과 같다.

8. 아키텍처 관점에서의 선택 기준 — 값을 하는 자리와 못 하는 자리

이 절은 두 출처의 권고가 아니라 이 글의 해석이다. 블로그의 요약은 「성능보단 CPU를 덜 태우고 싶으면 안정형 여친, 죽어도 성능이면 불안형 여친」이다. 이를 CPU 효율이 우선이면 기본 모드를, 성능이 최우선이면 SQPOLL 을 검토한다는 뜻으로 읽을 수 있다.

이 글의 추측으로는, 지연 시간이 가장 중요하고 입출력이 끊이지 않는 워크로드에서 폴링 코어의 비용이 정당화될 수 있다. 특정 업종이나 수치는 두 출처에 없다.

반대로 다음 경우에는 SQPOLL 이 맞지 않을 수 있다(모두 이 글의 추측이다).

  • 요청 사이 유휴가 긴 서비스: 폴링이 CPU 를 쓰고, 스레드가 잠들면 깨우기 절차가 필요해 이득이 줄 수 있다.
  • 코어 수가 적은 환경: 할당된 vCPU 가 적으면 폴링 스레드가 코어를 차지해 다른 스레드가 쓸 CPU 가 줄 수 있다. man 페이지는 컨테이너에서 cpuset.cpus 가 바뀌면 묶인 CPU 세트도 바뀔 수 있다고 적는다.
  • CPU 사용량이 비용에 직결되는 환경: 폴링 스레드의 CPU 사용이 과금이나 자동 확장 지표에 잡힐 수 있다. 두 출처는 클라우드 비용을 다루지 않는다.
  • 전력에 민감한 기기: 지속적인 폴링은 전력 소모를 늘릴 수 있다. man 페이지는 전력을 다루지 않는다.

아래 절차는 두 출처에 있는 것이 아니라 이 글의 제안이다. 블로그에는 벤치마크 수치가 없으므로, 자신의 환경에서 직접 측정해야 한다.

  • 1단계: 베이스라인 인터럽트 모드 프로파일링 — 기본 모드에서 CPU 사용률과 I/O 처리량을 기록해 볼 수 있다.
  • 2단계: SQPOLL 적용 및 sq_thread_idle 튜닝 — IORING_SETUP_SQPOLL 을 적용한 뒤 sq_thread_idle 을 조절하며 NEED_WAKEUP 발생 빈도를 관찰해 볼 수 있다.
  • 3단계: 시스템 콜 호출 빈도 추적 — io_uring_enter(2) 시스템 콜 호출 횟수가 줄어드는지 확인해 볼 수 있다.
  • 4단계: 지연 시간과 코어 영향 평가 — IORING_SETUP_SQ_AFF 로 코어를 묶었을 때 지연 시간과 다른 작업에 미치는 영향을 비교해 볼 수 있다.

10. 확인하지 못한 것

이 글은 블로그 글과 io_uring_setup(2) 두 곳만 읽었다. 확인하지 못한 것은 다음과 같다.

  • 원문 블로그(oborona.zip/post/sqpoll)는 정성적 비유와 구조적 개념만을 다루고 있으며, SQPOLL 모드와 기본 모드 간의 IOPS, 마이크로초 단위 지연 시간, CPU 점유율에 대한 정량적 벤치마크 데이터를 일체 제시하지 않아 원문 수치를 확인하지 못했다.
  • 리눅스 공식 매뉴얼 페이지 io_uring_setup(2)에는 사용자가 sq_thread_idle 필드를 명시적으로 지정하지 않았을 때 커널 내부 기본값으로 적용되는 구체적인 만료 시간(기본 밀리초 값)이 기재되어 있지 않아 확인하지 못했다.
  • man 페이지에서 일부 5.13 이전 안정 커널도 비특권 SQPOLL 을 지원할 수 있다고 적었으나 구체적인 목록은 기술되어 있지 않아 확인하지 못했다. 폴링 커널 스레드의 이름도 man 페이지에 나오지 않는다.
  • 네트워크 소켓 I/O 와 블록 스토리지 I/O 사이에서 sq_thread_idle 매개변수의 차이나 전력 소비량의 정량적 상관관계는 두 출처의 범위를 벗어나 확인하지 못했다.
