Introduction: one space in a filename turns three arguments into five

A cleanup script that ran fine for years starts behaving strangely one day. What changed is not the code but the input. Someone uploaded a file named annual report.pdf. One space. From that moment the three targets the script thought it had become five, and commands run against an annual and a report.pdf that do not exist. If that command is rm, the outcome is not a file listing but an incident report.

This is not a bug, it is the shell's design. The shell expands a variable and then chops the result into words again. That second step is word splitting, and quotes are the switch that turns it off. So far this is widely known. What actually trips people up comes next. "$@" differs from $@, "$*" differs from "$@", "${arr[@]}" differs from ${arr[@]}, and IFS follows different rules when cutting than when joining. Confusing any one of these six breaks argument boundaries.

This article focuses on making those boundaries visible. Every example prints each argument wrapped in brackets with printf '[%s]\n'. How many there are and where the cut happened is right there on screen. The commands and output come from actually running them under GNU bash, version 5.2.37(1)-release and a dash in the same environment.

What each kind of quote blocks was already covered in Shell Quoting Rules, so it is not repeated here. The subject of this article is argument boundaries, not quoting. For values disappearing across process boundaries see Why Variables Vanish Inside a Piped while Loop, and for guaranteeing cleanup no matter how a script ends see Cleaning Up Temp Files With trap.

Read this before the examples. The mistakes in this article delete real files. With files="annual report.pdf", running rm $files hands rm two arguments: annual and report.pdf. If either of those names actually exists, it gets deleted. If the expansion contains a *, the blast radius grows. When editing code that handles file lists, replace the delete command with echo, run it once, look at the target list with your own eyes, then put it back. Add a -- terminator to rm and mv, and hold file lists in an array rather than a string so they expand as "${files[@]}". If names containing newlines have to be handled, use find -print0 with read -d ''. All three are demonstrated by running them below.

1. You passed three, the function received five

Build three arguments and pass them to a function in four different forms, counting each time. The targets are two names containing spaces and one ordinary name.

#!/usr/bin/env bash
show() { printf '  count=%d\n' "$#"; printf '  [%s]\n' "$@"; }

f1() { show "$@"; }
f2() { show $@; }
f3() { show "$*"; }
f4() { show $*; }

set -- "annual report.pdf" "q3 data.csv" plain.txt

echo '--- "$@" ---'; f1 "$@"
echo '--- $@  ---';  f2 "$@"
echo '--- "$*" ---'; f3 "$@"
echo '--- $*  ---';  f4 "$@"
$ bash t1.sh
--- "$@" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- $*  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]

Three went in and the counts that came out were 3, 5, 1, 5. Only the first preserved the original count. The other three each broke the boundaries in their own way.

1.1 What the four combinations do, in one table

FormResulting wordsWord splittingGlobbingWhere to use it
"$@"3 (unchanged)NoNoPassing arguments along. Effectively the only right answer
$@5YesYesAlmost nowhere
"$*"1 (joined)NoNoPrinting arguments on one log line
$*5YesYesAlmost nowhere

In the table $@ and $* produce the same result, and that is no accident. The moment you drop the quotes, the difference between them evaporates. An unquoted expansion gets re-chopped by IFS anyway, so how it was joined stops mattering. Which means arguing about $@ versus $* is only meaningful when they are quoted.

  • "$@" expands to exactly as many words as there are arguments. With zero arguments it produces zero words
  • "$*" is always exactly one word. With zero arguments it is still one empty string
  • $@ and $* give identical results. Both go through IFS splitting and globbing
  • Using "$*" where arguments are being forwarded makes them arrive as a single clumped argument
  • For a human-readable log line, "$*" is actually the right tool: echo "running: $0 $*"
  • $# is the argument count. The 3, 5, 1, 5 printed inside the function above is that value

1.2 The same rules apply in for loops

$ bash t12.sh
--- for loop ---
for x in "$@"
    [annual report.pdf]
    [q3 data.csv]
for x in $*
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
for x in "$*"
    [annual report.pdf q3 data.csv]
a bare "for x" defaults to "$@"
    [annual report.pdf]
    [q3 data.csv]

The last form is worth remembering. Writing for x; do ... done with no list at all makes the shell use "$@". There is no longer any opportunity to forget the quotes.

2. Two things the shell quietly does after expanding

Why this happens becomes clear from the order in which the shell processes a command line. Expanding the variable is only a middle step; two more follow it.

  1. Expansion — things like $var, ${arr[@]} and $(cmd) turn into values
  2. Word splitting — that value is cut on the characters in IFS into multiple words
  3. Filename expansion — any *, ? or [ inside each word turns into real filenames

Wrapping in double quotes skips steps 2 and 3. Step 1 still happens. That is why "$var" retrieves the value while keeping it as one word. That single sentence is the summary of this entire article.

The important detail is that steps 2 and 3 apply only to values that came out of an expansion. Literals written directly in the script are not subject to them.

$ bash -c 'show() { echo "count=$#"; }; show annual report.pdf'
count=2                # two literals. it was two from the start

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show $x'
count=2                # cut apart after coming out of the variable

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show "$x"'
count=1                # the quotes turned step 2 off
  • The middle line is the archetype of the accident. What was one chunk inside the variable arrived at the command as two
  • The result of command substitution $(cmd) goes through steps 2 and 3 identically. So quoting $(...) is the default too
  • Arithmetic expansion $((...)) yields a number, so it rarely bites in practice, but the rule is the same
  • The right side of an assignment is an exception. x=$y is not split even without quotes, because assignment is a context that takes exactly one word
  • The subject of case and the inside of [[ ]] also skip splitting. The old [ ] does not, which is why [ $x = y ] is a syntax error when x is empty

3. IFS is both the knife that cuts and the glue that joins

IFS does two jobs and the rules differ between them. Without knowing this asymmetry you cannot predict the result of changing IFS.

3.1 When joining, only the first character is used

#!/usr/bin/env bash
set -- alpha beta gamma
echo "default IFS  : [$*]"
IFS=,
echo "IFS=,        : [$*]"
IFS=
echo "IFS empty    : [$*]"
unset IFS
echo "IFS unset    : [$*]"
IFS=',;|'
echo "IFS=',;|'    : [$*]"
$ bash t3.sh
default IFS  : [alpha beta gamma]
IFS=,        : [alpha,beta,gamma]
IFS empty    : [alphabetagamma]
IFS unset    : [alpha beta gamma]
IFS=',;|'    : [alpha,beta,gamma]

The last line is the point. Three characters went into IFS but only the first one appears between elements. An empty IFS joins with nothing at all, while unset restores the default of whitespace. Empty and unset are completely different states.

In the same run, "$@" did not budge when IFS was switched to a colon.

with IFS=: in effect, "$@" is untouched:
  [alpha]
  [beta]
  [gamma]

3.2 When cutting, every character in it is used

#!/usr/bin/env bash
line="root:x:0:0:root:/root:/bin/bash"
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- default IFS, unquoted ---'
show $line
echo '--- IFS=: unquoted ---'
IFS=:
show $line
echo '--- IFS=: but quoted ---'
show "$line"
$ bash t4.sh
--- default IFS, unquoted ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]
--- IFS=: unquoted ---
  count=7
  [root]
  [x]
  [0]
  [0]
  [root]
  [/root]
  [/bin/bash]
--- IFS=: but quoted ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]

Here IFS does its field separator job properly, splitting an account record into exactly seven fields. Yet with quotes added in the same state, nothing happens at all. IFS only acts on unquoted expansions.

3.3 Rules for changing IFS

Changing IFS globally affects every unquoted expansion that follows. There is a way to scope it to a single command.

$ bash t13.sh
--- save and restore ---
old_IFS=$IFS; IFS=,; read -r -a parts <<< "alpha,beta,gamma delta"; IFS=$old_IFS
  3 elements
    [alpha]
    [beta]
    [gamma delta]
--- IFS=, read -a : scoped to that one command ---
  3 elements
    [alpha]
    [beta]
    [gamma delta]
  IFS after: $' \t\n'

The second form is better. An assignment written in front of a command, as in IFS=, read -r -a parts, is in effect only while that command runs. Checking IFS afterwards shows the default intact. The save-and-restore approach fails to restore if you leave early via return or an error.

  • The default IFS is three characters: space, tab, newline. The $' \t\n' in the output above is that value
  • Those three get special treatment. Runs of them collapse into one, and leading and trailing ones are discarded
  • Non-whitespace separators such as a colon behave differently: consecutive colons create an empty field
  • So splitting a::b on IFS=: yields three fields with an empty string in the middle
  • This is why reading a file line by line uses while IFS= read -r line. Emptying IFS stops leading and trailing whitespace from being trimmed
  • The -r in read -r stops backslashes being treated as escapes. It is effectively mandatory when reading paths

4. Drop the quotes and a string turns into filenames

Less famous than word splitting but more dangerous is filename expansion. Verified in a directory holding three files.

#!/usr/bin/env bash
# this directory holds report.txt, notes.txt and archive.tar
pattern='*.txt'
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- unquoted $pattern ---'; show $pattern
echo '--- quoted "$pattern" ---'; show "$pattern"
echo '--- with set -f on ---'; set -f; show $pattern; set +f
$ bash t5.sh
files here: archive.tar notes.txt report.txt
--- unquoted $pattern ---
  count=2
  [notes.txt]
  [report.txt]
--- quoted "$pattern" ---
  count=1
  [*.txt]
--- with set -f on ---
  count=1
  [*.txt]

The variable holds *.txt, yet the command received two real files. The string stored in the variable turned into something else just before reaching the command. That conversion depends on the current state of the filesystem, so the same code behaves differently today than it did yesterday.

4.1 A glob inside an array element doubles the damage

$ bash t5.sh
--- array with a glob in an element ---
arr=('*.txt' 'literal name.txt')
  unquoted ${arr[@]}:
  count=4
  [notes.txt]
  [report.txt]
  [literal]
  [name.txt]
  quoted "${arr[@]}":
  count=2
  [*.txt]
  [literal name.txt]

A two-element array became four. The first element became two through globbing and the second became two through word splitting. Because the two stages apply in sequence, the damage multiplies.

  • If a glob matches nothing, bash by default leaves the pattern characters as-is. That is why the problem is discovered late
  • shopt -s nullglob makes the word disappear when nothing matches. That is a different accident: an argument vanishing entirely
  • shopt -s failglob raises an error on no match. Handy interactively, but in a script it creates unexpected aborts
  • set -f disables globbing only and leaves word splitting alone. The [*.txt] surviving as one word above is that result
  • Leaving set -f on for a whole script means globs stop working where you actually want them. Enable it for the needed section and restore with set +f
  • The real fix is quoting. set -f is closer to a stopgap for when you cannot edit someone else's code

5. Counting elements across the four array expansions

The four combinations seen with positional parameters exist for arrays too. Only the notation changes.

#!/usr/bin/env bash
arr=("annual report.pdf" "q3 data.csv" plain.txt)
count() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
count "${arr[@]}"
count ${arr[@]}
count "${arr[*]}"
count ${arr[*]}
echo "element count: ${#arr[@]}"
echo "length of first element: ${#arr[0]}"
$ bash t2.sh
--- "${arr[@]}" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- ${arr[@]}   ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "${arr[*]}" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- ${arr[*]}   ---
  count=5
--- element count: 3 ---
--- length of first element: 17 ---

The table from section 1 applies unchanged. There is exactly one way to use an array as an array: "${arr[@]}". The other three forms turn the array into something that is not an array.

The last two lines are worth noting as well. ${#arr[@]} gives the element count 3, while ${#arr[0]} gives the character length 17 of the first element. What sits inside the brackets changes what # means.

5.1 Using the bare array name gives you the first element

$ bash t11.sh
arr=("a:b" "c d" "e")
  $arr        = [a:b]
  ${arr[0]}   = [a:b]
  ${arr[@]:1} = [c d e]

$arr is not the whole array, it is ${arr[0]}. Since it raises no error, discovery is late. Testing with a single-element array hides this mistake to the very end. Making a habit of putting at least two elements in test data filters out this class of bug.

5.2 IFS acts on unquoted array expansions too

$ bash t11.sh
arr=("a:b" "c d" "e")
--- IFS=: and unquoted ---
  count=4
  [a]
  [b]
  [c d]
  [e]
--- quoted in the same state ---
  count=3
  [a:b]
  [c d]
  [e]
--- "${arr[*]}" joins with the first IFS char ---
  count=1
  [a:b:c d:e]

The first result is interesting. Since IFS is a colon, a:b split in two, while the space in c d is no longer a separator and stayed put. Changing IFS changes wholesale what gets cut.

5.3 Slicing and sparse arrays

$ bash t11.sh
--- "${arr[@]:1:2}" ---
  count=2
  [c d]
  [e]
--- removing an element does not renumber the rest ---
s=(zero one two); unset 's[1]'
  count=2  indices=0 2
  [zero]
  [two]
--- declare -p shows the real shape ---
declare -a s=([0]="zero" [2]="two")
declare -a arr=([0]="a:b" [1]="c d" [2]="e")

unset on a middle element leaves a hole rather than renumbering. ${#s[@]} is 2 while the last valid index is 2. So an index loop like for ((i=0; i<${#s[@]}; i++)) misses elements in an array like this.

  • Iterate with for x in "${arr[@]}" instead of an index loop. It skips the holes for you
  • When you genuinely need indices, get the real list with ${!arr[@]}. The indices=0 2 above is that
  • declare -p shows an array's true shape including indices. It is the first thing to print when an array looks wrong
  • The slice "${arr[@]:1:2}" obeys the same quoting rules. Drop the quotes and it splits again
  • arr+=("new") appends while arr=("new") replaces wholesale. Verified: the former gave 2 elements, the latter 1
  • Associative arrays must be declared with declare -A first. Without it, a string key goes through arithmetic evaluation and lands at index 0

6. Where empty strings and newlines disappear

Build a three-element array whose middle element is an empty string.

$ bash t7.sh
--- array with an empty-string element, ${#arr[@]}=3 ---
  count=3
  [first]
  []
  [third]
--- the same array unquoted ---
  count=2
  [first]
  [third]

The empty element vanished without a trace. Three elements exist but only two reach the command. In a design where an optional setting that may be empty is held in an array and passed on the command line, argument positions shift and the next argument lands in the wrong slot.

$ bash t7.sh
--- element containing a newline, ${#arr2[@]}=2 ---
  count=2
  [line1
line2]
  [tail]
--- unquoted: newline is an IFS char, so it splits ---
  count=3
  [line1]
  [line2]
  [tail]

Newline is one of the three default IFS characters. So a filename containing a newline becomes two filenames in an unquoted expansion. Putting a newline in a filename is not forbidden on Linux filesystems. Code handling user uploads or extracted archives can genuinely meet one.

6.1 Expanding an empty array under set -u

$ bash t6.sh
bash 5.2.37(1)-release
--- "${empty[@]}" under set -u ---
  OK, expanded to nothing: rc=0
--- "${empty[*]}" is different ---
  count=1              # one empty string appears
--- passing "${empty[@]}" to a command ---
  count=0              # no arguments at all
--- the ${empty[@]:-default} idiom ---
  [<default>]

Under bash 5.2.37, expanding an empty array as "${empty[@]}" with set -u raised no error and produced zero arguments. This behaviour changed in bash 4.4; before that, it is documented to have raised an unbound variable error. No older bash was available in this environment, so that was not reproduced. Scripts targeting old distributions still use the "${empty[@]:-}" guard for this reason.

Worth noting in the same output is that "${empty[*]}" gave count=1. The array is empty yet one argument appeared — an empty string. Passed to a command, that is not «no argument» but «an empty argument», and commands behave differently for the two.

7. The right way to put command output into an array

Four approaches compared in a directory holding two files, one of whose names contains a space.

$ bash t8.sh
files: annual report.txt|notes.txt|
--- arr=($(ls)) ---
  3 elements
  [annual]
  [report.txt]
  [notes.txt]
--- mapfile -t arr2 < <(ls) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- readarray -t arr3 < <(ls) ---
  2 elements
--- arr4=(*) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- mapfile -d '' arr5 < <(find . -maxdepth 1 -type f -print0) ---
  2 elements
  [./annual report.txt]
  [./notes.txt]

Only the first is wrong. arr=($(ls)) runs command output straight through word splitting and globbing. The inside of an array assignment's parentheses is a place that cannot be quoted. Writing arr=("$(ls)") instead makes the entire output one element, which destroys the point of the array.

  • mapfile -t reads line by line and -t strips the trailing newline. For a list of lines this is the default form
  • readarray is another name for mapfile. Same builtin, and the verified result was identical
  • There is a reason for < <(cmd) instead of a pipe. Writing cmd | mapfile runs mapfile in a subshell and the array never escapes. Same root cause as the subshell article
  • When the target is filenames, arr=(*) is safest. The shell builds the list itself, so any name lands as exactly one element
  • However arr=(*) yields an array holding the single string * when nothing matches. Pair it with shopt -s nullglob or check [ -e "${arr[0]}" ]
  • To handle names containing newlines, combine mapfile -d '' with find -print0. NUL is the only character that cannot appear in a filename, which makes it a safe delimiter
  • mapfile is a bash 4 feature. It is unavailable in scripts that must fall back to POSIX sh

7.1 Two ways to walk a file list

$ bash t10.sh
--- find -print0 + read -d '' ---
    got [./-rf]
    got [./annual report.pdf]
    got [./keep me.txt]
  total=3
--- for f in $(find . -type f) ---
    got [./-rf]
    got [./annual]
    got [report.pdf]
    got [./keep]
    got [me.txt]
  total=5

Three files became five. Run rm in the lower form and deletion is attempted against a nonexistent report.pdf and ./keep; if files by those names do exist, they go. The actual code for the upper form is this.

while IFS= read -r -d '' f; do
    echo "processing: [$f]"
done < <(find . -maxdepth 1 -type f -print0)

All three pieces are required: IFS= to empty it, -r to disable backslash handling, and -d '' to switch the delimiter to NUL. Leave any one out and it breaks on some name.

8. Arrays do not reach functions by value

Try to pass an array to a function and what arrives is not an array but several arguments.

$ bash t9.sh
--- an array cannot be passed by value; it flattens into arguments ---
arr=("annual report.pdf" "q3 data.csv")
takes "${arr[@]}"
  inside: $1=[annual report.pdf]  $#=2
--- rebuilding the array inside the function ---
h() { local -a mine=("$@"); echo "  mine=${#mine[@]}"; }
  mine=2
--- passing the name and receiving it as a nameref (bash 4.3+) ---
byref() { local -n ref=$1; echo "  ${#ref[@]} elements, first=[${ref[0]}]"; }
byref arr
  2 elements, first=[annual report.pdf]
--- local -a does not pollute the global namespace ---
  inner has 2
  inner outside: [<unset>]
--- set -- "${arr[@]}" swaps it into the positional parameters ---
  $#=2
  [annual report.pdf]
  [q3 data.csv]

Three approaches, each with its own place.

  • Receive as arguments and rebuild. One line does it: local -a mine=("$@"). Simplest, and the most portable
  • The drawback is that only one array can be passed. Two requires a workaround such as inserting a separator argument
  • Pass only the name and receive it as a nameref. local -n ref=$1 points at the original, so modifications inside the function are visible outside
  • Namerefs need bash 4.3 or later. If the parameter name matches the array name passed in, you get a circular reference error, hence the convention of prefixing instead of using a common name like ref
  • Swap into the positional parameters. After set -- "${arr[@]}", "$@" is that array. It is the only approach that also works in POSIX sh
  • It does overwrite whatever positional parameters were there. Stash them in another array first if you still need them
  • An array declared with local -a is invisible outside the function. The <unset> printed above confirms it
  • Creating an array inside a function without local makes it global. It collides silently with any other function using the same name

8.1 A wrapper that forwards its arguments

$ bash t13.sh
good: wrapper_good() { inner "$@"; }
  inner sees 2 arg(s):
    [annual report.pdf]
    [q3 data.csv]
bad:  wrapper_bad()  { inner $@; }
  inner sees 4 arg(s):
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
--- prepending an option while forwarding ---
wrapper_opt() { inner --dry-run "$@"; }
  inner sees 2 arg(s):
    [--dry-run]
    [annual report.pdf]

Wrapper scripts are where this mistake shows up most. When you build a thin wrapper that prepends a couple of options to docker or kubectl, forgetting the quotes on the final "$@" means it breaks silently the moment an argument containing a space goes through. Everyday testing never surfaces it because test arguments have no spaces.

9. Assembling a command line whose options come and go

When building a command whose options vary by condition, assembling it as a string always breaks. Arrays exist for exactly this problem.

#!/usr/bin/env bash
opts=()
verbose=1
outfile="my output.log"
[ "$verbose" = 1 ] && opts+=(--verbose)
opts+=(--output "$outfile")
echo "${#opts[@]} args:"; printf '  [%s]\n' "${opts[@]}"
$ bash t12.sh
--- assembled as an array ---
  3 args:
    [--verbose]
    [--output]
    [my output.log]
--- assembled as a string ---
optstr="--verbose --output $outfile"
  what the command sees:
    [--verbose]
    [--output]
    [my]
    [output.log]

On the string side the filename became two fragments. The command reads --output my and takes output.log as a separate positional argument. An error message would be the lucky outcome; usually a file named my gets created instead.

9.1 The empty-argument trap in conditional options

$ bash t12.sh
flag=""
probe "$flag" other           ->  got 2 arg(s)
probe ${flag:+"$flag"} other  ->  got 1 arg(s)

"$flag" creates one empty argument even when the value is empty. To pass no argument at all, use an expansion that only fires when a value exists, like ${flag:+"$flag"}, or add to the array conditionally in the first place, which reads better.

args=()
[ -n "$flag" ] && args+=("$flag")
cmd "${args[@]}" other

9.2 Names starting with a dash, and the terminator

$ ls -1
-rf
annual report.pdf
keep me.txt

$ ls -1 -rf          # reads -rf as options
.
..

$ ls -1 -- -rf       # after -- everything is a filename
-rf

A file whose name starts with a dash gets read as an option. Quoting cannot stop this. Quotes only prevent a word from being split; the fact that the unsplit word looks like an option remains. In the run above, ls -1 -rf was interpreted as the -r and -f options and listed the current directory instead of the file.

  • The fix is the -- terminator. Everything after it is treated as a non-option
  • Add it by habit to irreversible commands: rm -- "$file", mv -- "$src" "$dst"
  • The other approach is making the path start with ./. ./-rf no longer begins with a dash
  • This is why it is convenient that find emits paths starting with ./. The [./-rf] in the section 7 output is an example
  • Some commands do not support --. There the ./ approach is the only alternative
  • Anywhere user input goes straight into a command, treat the terminator as mandatory rather than optional

10. Shells without arrays can still pass arguments safely

A script with a #!/bin/sh shebang running under dash in production is common. If /bin/sh points at bash on your development machine, the difference is invisible.

$ dash -c 'arr=(a b c); echo "$arr"'
dash: 1: Syntax error: "(" unexpected

The array syntax itself does not exist. Positional parameters do, however, and the quoting rules match bash.

$ dash tp.sh
--- "$@" in POSIX sh ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@ in POSIX sh ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" in POSIX sh ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]

Exactly the same results as bash. So even without arrays, one list can be handled safely: put it in the positional parameters and expand with "$@".

set -- "annual report.pdf" "q3 data.csv"
set -- "$@" "newly added file.txt"     # appending
for f in "$@"; do
    echo "processing: [$f]"
done
  • set -- "$@" "new item" is the equivalent of appending to an array. You can accumulate elements one at a time
  • $# gives the element count, the same role as ${#arr[@]}
  • shift pops from the front one at a time, which is the queue pattern
  • If you need two or more lists, this approach runs out. That is the point at which to name bash in the shebang
  • local is a non-POSIX extension, but it was confirmed to work in dash. It is not standard, so it is not guaranteed across every sh
  • mapfile, readarray, local -n and declare -p are all bash extensions. Avoid all four when portability matters
  • Writing #!/usr/bin/env bash is the minimum requirement for a script that uses arrays. Leave it as #!/bin/sh and it will die with a syntax error on some other machine eventually

Everything so far, paired as safe and unsafe forms.

11.1 Checklist

  • Quote expansions by default. Dropping them is the exception, and when you do, leave the reason in a comment
  • Hold lists in arrays, not strings. The moment it becomes a string, the boundary information is gone
  • Use only "${arr[@]}" for array expansion. Reserve the star form for log output
  • Use mapfile -t to turn command output into an array. Never command substitution inside the parentheses
  • When the target is filenames, use the shell's own glob. Do not parse ls output
  • Add the -- terminator to delete, move and copy commands
  • After changing logic, swap the delete line for echo, run it once, and look at the target list
  • Always put one name containing a space in your test data. Every defect in this article surfaced from that one thing
  • Where possible, test with at least two elements. One element never reveals the $arr mistake
  • When IFS must change, scope it to the command with the IFS=, read ... form
  • Read files line by line with the while IFS= read -r line form exactly as written
  • Name bash explicitly in the shebang of any script that uses arrays
  • When an array looks wrong, print it with declare -p including indices. Faster than guessing
  • A static checker catches most of the mistakes in this article before commit. Unquoted expansion is one of its headline rules

12. What was not verified

Everything stated from documentation rather than confirmed by running it, collected in one place.

  • The set -u behaviour of bash before 4.4. The claim that expanding an empty array as "${arr[@]}" raised an error rests on the change history; no old bash existed here to reproduce it. The guard idiom recommended in 6.1 rests on the same source
  • Array behaviour in zsh and ksh. zsh follows different rules entirely, for instance not performing word splitting on unquoted expansions, but no runnable environment was available. Do not transfer this article's conclusions to zsh unchanged
  • busybox ash. A common shell in minimal container images, not verified. Whether the POSIX conclusion in section 10 holds there is worth one run on the target
  • A Linux glibc environment. The environment here is bash 5.2.37 built for x86_64-pc-msys plus a dash in the same environment. Quoting and splitting are shell-internal and independent of the filesystem, so divergence is unlikely, but the filename examples are worth reproducing on the target
  • Limits on very long arrays. Argument count and total length have kernel-side ceilings. How "${arr[@]}" fails at that boundary was not measured
  • Iteration order of associative arrays. Key order for a declare -A array is documented as unspecified, but this article did not exercise it
  • Glob character ranges under different locales. Range patterns such as [a-z] behaving differently by locale is outside this article's scope and was not checked

FAQ

Q1. Can I just quote every expansion?

Almost. Places where quotes must come off are rare in practice. The case for removing them is deliberately splitting one string into several arguments, and in that situation an array is the better tool anyway. A few contexts are safe without quotes: the right side of an assignment x=$y, the inside of [[ ]], and the subject of case. The shell guarantees no word splitting there. Even so, quoting consistently is the recommendation. The cost of remembering the exceptions exceeds the cost of typing two more characters. And in code review, confirming «they are all quoted» is faster than verifying «this one is safe here» every single time.

Q2. When should I use "$*"?

When building one string for a human to read. Writing a log line saying «this command ran with these arguments» is the archetype. Running it confirms "$*" always produces exactly one word, with elements joined by the first character of IFS. Conversely, never use it where arguments are forwarded to another command. Three arguments go in and one arrives. One more caution: even for logging, whether the original arguments contained spaces is indistinguishable in the joined string. If you want the boundaries preserved exactly, printing each argument wrapped, as in printf '[%s] ' "$@", is better.

Q3. What does it mean that array assignment cannot be quoted?

It means there is no way to wrap the whole parenthesised group in arr=($(cmd)). Writing arr="($(cmd))" gives a string containing parentheses rather than an array, and arr=("$(cmd)") makes the entire output one element. The inside of an array assignment's parentheses is structurally a place that goes through word splitting. So the fix is not to use that syntax. For a list of lines use mapfile -t; for a list of files use a glob directly, as in arr=(*). There is an exception: if the output is certainly whitespace-free tokens with no chance of glob characters, it is fine. What makes it the archetypal accident is that the certainty gets invalidated later.

Q4. Can I just turn set -f on for the whole script?

It is half a solution, because it disables globbing while leaving word splitting in place. The filename-with-space problem remains untouched. Worse, lines that genuinely need a glob, such as for f in *.log, stop working. Running it confirms that under set -f, *.txt survived as one word with the pattern characters intact. It is not entirely useless: when you cannot immediately fix someone else's code but must stop globbing accidents, or for a short section handling user input where you enable set -f and restore with set +f afterwards, it earns its place. The real fix is quoting and arrays.

Q5. Do filenames with newlines actually happen?

Yes. The only characters that cannot appear in a Linux filename are NUL and slash; newline is not on the banned list. Code that unpacks user-uploaded archives or handles data moved from another system can genuinely encounter one. Checking confirms an element containing a newline splits into two under unquoted expansion, because newline is one of the three default IFS characters. Handling it requires switching the delimiter to NUL: build the list with find -print0 and receive it with read -d '' or mapfile -d ''. Because NUL is the only character that cannot appear in a filename, it is the only viable delimiter.

Conclusion: three things to change today

First, stop holding lists in strings. The moment several filenames go into one string the boundary information is gone, and from then on the shell guesses it back using IFS. The accident is the moment the guess is wrong. Put lists in arrays and expand with "${arr[@]}". In a shell without arrays, put them in the positional parameters and expand with "$@". Verified: those two forms are the only ones that preserved the original count.

Second, do not use command substitution inside array-assignment parentheses. In a directory with two files, arr=($(ls)) produced a three-element array while mapfile -t produced exactly two. When the target is filenames, using the shell's own glob as in arr=(*) is better still, because the parsing step disappears entirely.

Third, add -- to delete and move commands, and run once with echo after changing logic. A file whose name starts with a dash cannot be protected by quoting, and ls -1 -rf was confirmed to read it as options rather than a file. Deletion is irreversible. Eyeballing the target list costs a few seconds.

One last thing. Every defect in this article surfaced from nothing more than putting one space-containing name in the test data. Next time you write code that handles file lists, add a single touch "annual report.pdf" to the test. Where the code that currently looks fine falls apart becomes visible on the spot.
