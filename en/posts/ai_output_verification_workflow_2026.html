Building a Verification Pipeline for AI Output - What Syntax Checks Never Catch

Designing syntax, runtime and semantic layers, managing false positives, and the traps of batch editing

Jul 27, 2026 Dev & Infra

Introduction: a passing check is not the same as being correct

Having AI draft documents, produce configuration files and handle translation has become routine. The real bottleneck in that workflow is not generation but verification. When you produced one artifact a day by hand you could read all of it before shipping. When dozens land every day, reading everything is physically impossible. So you bolt on a checker. node --check passes, the JSON parses, the open and close tag counts match, and a green light comes on.

The problem is that green-lit artifacts break in production. The cause is usually not a bug in the checker. The defect simply landed in territory the checker never looks at. A passing check does not mean nothing is wrong; it means nothing is wrong within what that check looks at. We keep reading those two sentences as if they were the same.

This is not a tooling quality problem but a limit of principle. Rice's theorem states that every non-trivial semantic property of a program is undecidable. A question about behaviour, such as whether a program halts on all inputs, is fundamentally different from a question about form, such as whether it contains an if-else statement. No tool can decide correctness in general by reading code alone. Real tools sidestep that wall. A sound analyzer over-approximates, accepting false positives to eliminate false negatives. A complete analyzer under-approximates, accepting false negatives to eliminate false positives. Heuristic tools such as ESLint and SonarQube give up both guarantees and pick usefulness instead. In other words, the checkers we use every day are built so that they will necessarily miss something.

What a practitioner should do, then, is not hunt for the perfect checker but learn what each checker cannot see and design a pipeline where another layer covers the blind spot. This article covers that pipeline for artifacts in general — documents, translations, configuration files and data. It is a different axis from evaluating model performance or automating code review. What is discussed here is the process that filters an already-produced artifact before it ships.

1. Checking has layers - syntax, runtime, semantics

Treating verification as one undifferentiated blob makes it impossible to design. Split it into three layers and you can finally say what each layer is responsible for.

  • Layer 1, syntax — the question is does it parse. It looks only at whether a string conforms to a structural grammar. Cheapest, fastest and shallowest.
  • Layer 2, runtime — the question is does it actually become a value and run. You evaluate, execute or render the parsed result and observe it alive.
  • Layer 3, semantics — the question is is the content correct. Does the value match reality, does the document make sense, does the translation say the same thing as the source.

Their properties compare as follows.

LayerCore questionTypical meansCatches wellCannot catch in principleCost
SyntaxDoes it parsenode --check, JSON parsers, XML schemas, lintersUnclosed tags, broken JSON, misspelled keywordsBehaviour that only appears at run time, plausibility of valuesVery low, seconds
RuntimeDoes it evaluate and runReal parsing and evaluation, headless rendering, unit testsUnbounded recursion, exceptions, elements under the wrong parent, broken referencesDefects off the executed path, factual accuracyMedium, minutes
SemanticsIs the content correctHuman review, cross-source checking, LLM judgment, proxy metricsFactual errors, omitted or added information, awkward phrasing, lost contextEverything outside the sample, and it is vulnerable to judge biasHigh, human hours

The most important property here is that the three layers are serial, not parallel. Adding a hundred syntax checks removes exactly zero runtime defects. As you move up, cost rises and automation rate falls, and a lower layer never substitutes for a higher one. The classic way a verification system collapses is to build a dense syntax layer and then believe that having checks is enough.

2. Four failures the syntax layer can never catch

Abstractions do not land, so here are four failure shapes that occur often in practice. All four pass a syntax check with a perfect score.

2.1 Grammatically perfect, dies on unbounded recursion

To a parser, the function below is flawless. Parentheses balance, keywords are valid, semicolons are in place.

function resolveRoot(node) {
  // Intent: walk up to the topmost node
  return resolveRoot(node.parent || node);
}

The moment node.parent becomes null, the node passes itself back in, there is no termination condition, and the stack blows up. A syntax check can never see this. It surfaces only when executed. That is the simplest possible argument for a runtime layer.

2.2 Tags balance but the element sits under the wrong parent

In the fragment below every opening tag has a matching close. A checker that counts tags waves it through.

<table>
  <li>First item</li>
  <li>Second item</li>
</table>

But li must be a child of ul or ol. The browser HTML parser drags these elements outside the table, a behaviour known as foster parenting. The result is a page whose layout has quietly collapsed. The check is green while the screen is broken. Counting matched pairs and knowing parent-child rules are entirely different products.

2.3 The number format is valid but the value is wrong

{"unitPrice": 1200} is a perfect integer as far as a JSON schema is concerned. The check passes whether the real price is 12,000, whether the unit is a different currency, or whether the product does not exist at all. A format validator says nothing about the plausibility of a value. This is especially dangerous in AI-generated configuration files, where the structure comes out flawlessly in the learned pattern while the numbers inside it may have no basis whatsoever.

2.4 The translation is grammatically perfect but invents content

Look at the MQM (Multidimensional Quality Metrics) error typology, effectively the reference standard for translation quality. Under the Accuracy dimension it defines Addition (target content that is not present in the source), Omission (content missing from the translation that is present in the source) and Mistranslation (which itself contains machine translation hallucination as a distinct subtype) as separate error categories. In other words, a large axis of translation failure is not grammar but a mismatch in information content. Research on over- and under-translation reports that current neural systems still erroneously add and omit target words, and that omission occurs more often than addition.

Feed such a sentence to a grammar checker and nothing is wrong. It surfaces only by comparing against the source, or by comparing the sets of numbers in source and target.

Failure shapeSyntaxRuntimeSemanticsCheapest detection
Unbounded recursion or loopMissesCatchesNot neededReal execution under a timeout
Element under the wrong parentMissesCatchesNot neededParent-rule check after DOM parsing
Valid format, wrong valueMissesUsually missesCatchesRange invariants plus cross-source checking
Added or omitted translation contentMissesMissesCatchesSet comparison of numbers, URLs, proper nouns
Broken linksMissesCatchesNot neededExhaustive HTTP status check
A whole table missing in one language editionMissesUsually missesCatchesCross-language structural count invariants

3. Designing the runtime layer - what only execution reveals

The runtime layer is where you separate 'it parses' from 'it becomes a value'. Five techniques carry most of the weight in practice.

  • Round-trip re-serialisation — parse, serialise back to a string, and compare the structure with the original. Whatever the parser quietly fixed for you shows up as a difference. The more lenient the parser, the more this technique is worth.
  • Structural rule checks — parent-child relationships, required fields, mutually exclusive fields, that is, rules beyond grammar rather than format. This is where the failure in section 2.2 gets caught.
  • Count invariants — rules such as 'the four language editions of the same document must have identical counts of h2 headings, tables and list items'. Without verifying a single fact, they catch wholesale omission.
  • Isolated execution — actually run it with a timeout and a memory ceiling. Unbounded recursion is caught here and nowhere else. Always run in a separate process so the harness does not die with it.
  • Post-render checks — draw the page in a headless browser and read the DOM back. This is the last net for cases that looked right in source but render differently.

Writing one command per layer makes the difference obvious.

# Layer 1, syntax - does it parse
node --check build/report.js

# Layer 2, runtime - does it become a value, evaluated for real under a timeout
timeout 10 node -e "JSON.parse(require('fs').readFileSync('data/config.json','utf8'))"

# Layer 2, runtime - check invariants at the same time
node -e "const d=require('./data/config.json');
         if (!(d.retries >= 0 && d.retries <= 10)) throw new Error('retries out of range: '+d.retries);
         if (!d.endpoint.startsWith('https://')) throw new Error('insecure endpoint: '+d.endpoint);"

The parent-rule check from section 2.2 looks like this. Instead of counting tags, you walk the tree the parser accepted.

const { JSDOM } = require('jsdom');
const doc = new JSDOM(html).window.document;

// li must be a direct child of ul or ol
for (const li of doc.querySelectorAll('li')) {
  const parent = li.parentElement.tagName;
  if (parent !== 'UL' && parent !== 'OL') {
    throw new Error(`li sits inside ${parent}: ${li.textContent.slice(0, 30)}`);
  }
}

// every row of a table must have the same number of columns
for (const table of doc.querySelectorAll('table')) {
  const widths = [...table.querySelectorAll('tr')].map(tr => tr.children.length);
  if (new Set(widths).size > 1) throw new Error('column count mismatch: ' + widths.join(','));
}

What matters is that all of these are mechanical judgments. No human opinion is involved, so exhaustive automation is possible and false positives are rare. Verification budget should be spent here first.

4. The semantic layer - dividing work between humans, cross-sources and LLMs

The semantic layer has three judges and all three are flawed. Load everything onto any one of them and it will be breached.

4.1 Cross-source checking

Confirming the same fact in two independent sources. Of all semantic checks this is the closest to automatable. There is one trap: if both sources cite the same original, they are not independent. Two news articles repeating the same press release are one piece of information seen twice, not a cross-check. You have to descend to the institutional original or primary record for the cross to be real.

4.2 The limits of LLM-as-judge

Cheap and fast, but biased. The study 'Judging the Judges' examined 15 LLM judges across two benchmarks, MT-Bench and DevBench, covering 22 tasks and roughly 40 solution-generating models, producing over 150,000 evaluation instances. Its conclusion is that position bias is systematic rather than random and varies substantially by judge and by task. Prompt length had weak influence, whereas a larger quality gap between candidates produced stronger bias. Separate work reports self-preference bias, the tendency of a model to overrate its own output. Verbosity bias, a preference for longer answers, is also documented.

That does not make the tool unusable. Know the limits and change the design.

  • Ask twice with the order reversed. Accept only cases where both answers agree. This single measure filters out a large share of position bias.
  • Separate the generating model from the judging model. The simplest defence against self-preference bias.
  • Use checklists instead of scores. 'Is there a sentence not present in the source: yes or no' is far more reproducible than 'rate this out of ten'.
  • Use the judge only for ordering. Not as a pass-fail gate but as a way to rank what a human should look at first. The goal is to reach a state where reviewing the top twenty is enough.
  • Re-check the judge on a sample. The judge is also subject to review. Have a human re-inspect a random sample of its verdicts and record the agreement rate.

4.3 Human review

The most accurate, the most expensive, and above all blind whenever the sample is small. That limit can be stated as arithmetic rather than intuition, as section 9 shows. Human time is a finite resource, so designing where to spend it is half of any verification system.

5. False positives kill the checker - the structure of alert fatigue

Static analysis literature summarises that roughly 35 to 91 percent of warnings reported as bugs are in fact unactionable. That the range is this wide is itself the point: outcomes vary enormously by tool, project and configuration, which conversely means configuration is what decides the result.

The real cost of a false positive is not the minutes spent confirming it. It is alert fatigue — frequent warnings desensitise people, and real warnings end up ignored along with the noise. A checker that has cried wolf ten times will not stop the eleventh, genuine wolf. Multiple studies have observed developers ignoring or suppressing warnings under time pressure or warning fatigue, and the number of suppressions in a project has been observed to keep rising over its lifetime.

A case I lived through. A multilingual site validator carried a rule that 'every language edition must contain a certain sharing SDK'. But that SDK was, by policy, only ever added to the Korean pages. So every run produced the same warning for the other three languages. Because it always appeared, nobody read it, and a genuine error printed on the same line — a wrong CSS path — stayed buried for two months. Narrowing the rule to 'required on the Korean edition only' made the real error visible the same day. A checker that is permanently amber is not a checker, it is background noise.

Comparing the four responses teams typically choose makes it clear which one is worst.

ResponseShort-term effectEffect on detection powerVerdict
Switch the rule offWarnings disappearThat defect class is never caught againWorst. Nothing will ever prompt a reversal
Loosen the thresholdWarnings decreaseBorderline defects pass silentlyBad. Nobody knows how much is now missed
Just ignore the warningsNoneAlert fatigue deepens, real warnings buriedBad. The checker itself is neutralised
Narrow the scope preciselyOnly warnings for that condition disappearDetection preserved, signal-to-noise improvedCorrect, though working out the condition takes effort

The principle fits in one sentence. The fix for a false positive is not switching the rule off but stating precisely the condition under which the rule is true. 'Check A produces false positives' usually means 'the premise of check A is scoped more broadly than reality'.

6. After narrowing a rule, put a regression test on it

Narrowing introduces the opposite risk. Narrow too far and you stop catching the real thing. If you have no way to tell whether the checker went quiet because there are no defects or because the checker died, narrowing is functionally identical to switching it off.

Software testing already solved this. Mutation testing seeds artificial defects, called mutants, into source and checks whether the test suite catches, or kills, them, thereby measuring the fault-detection power of the tests themselves. The proportion killed is the mutation score, and it is reported to correlate with real fault-detection ability more strongly than code coverage does. Coverage says only 'this code ran'; a mutation score says 'when I broke it, something failed'.

The same idea transfers directly to a verification pipeline. Call it regression testing by seeding defects.

#!/usr/bin/env bash
# Confirm the checker is alive - seed a defect on purpose and see if it is caught
set -euo pipefail

WORK=$(mktemp -d)                       # always work on a copy
cp posts/sample.html "$WORK/sample.html"

# Defect 1: remove one closing tag
node -e "const fs=require('fs'); const p=process.argv[1];
         fs.writeFileSync(p, fs.readFileSync(p,'utf8').replace('</ul>',''));" "$WORK/sample.html"

if node validate.js "$WORK/sample.html"; then
  echo "FAIL: the checker did not catch the seeded defect"
  exit 1
else
  echo "OK: detected as expected"
fi

rm -rf "$WORK"                          # the original was never touched

The list of defects worth seeding differs by team, but this makes a usable starting point.

  • Remove one closing tag — the syntax layer should catch it
  • Remove the closing quote of an attribute value — syntax layer
  • Add a trailing comma after the last element of a JSON array — syntax layer
  • Move a list item inside a table — runtime layer, structural rules
  • Delete the termination condition of a recursive function — runtime layer, isolated execution
  • Delete a required meta tag — syntax layer or rule check
  • Introduce a single-character typo in a link domain — runtime layer, HTTP check
  • Change one digit of a number — semantic layer, only partially caught by range invariants
  • Delete an entire table from one language edition — runtime layer, count invariants
  • Add one sentence to a translation that is not in the source — semantic layer

Run this list at two moments: on a schedule, monthly, and every time you touch a rule. Anything that goes uncaught is precisely the hole that will be breached next. It helps to agree with the team in advance that finding an uncaught item is the success condition of this exercise. Otherwise nobody will want to run it.

Safety rule. Always seed defects into a copy. Seeding into the original and restoring afterwards becomes an incident the moment the restore fails. Copy into a temporary directory, run there, and delete the whole thing when finished. Do not relax because the files are under version control — a failed restore that coincides with a commit leaves the defect in history.

7. Golden files and snapshots - the layer that catches 'it changed'

Everything so far asked 'is this a rule violation'. You can add one more question: 'is this different from before'. You store a reference artifact and compare later artifacts against it. The technique has several names.

  • Golden master — borrowed from audio mastering, meaning the reference original.
  • Snapshot test — the name popularised by Jest, where the file generated on first run becomes the approved version.
  • Characterization test — Michael Feathers' term from Working Effectively with Legacy Code, defined as documenting the system's actual behaviour, not the behaviour you wish it had.
  • Approval test — Llewellyn Falco's name for essentially the same thing, differing in that a human approves the snapshot before it is used.

The four names point at effectively one technique with one goal: to have tests that fail if the system behaves differently. For AI output review it is particularly useful for catching 'the structure changed since last time for the same input'.

It has a well-known weakness, though: it is fragile. Intended changes make it fail too, so the reference file has to be updated constantly, and once updating becomes a habit you reach the state of updating without reading the failure. At that moment the test becomes meaningless. Mitigations are as follows.

  • Treat snapshots as code. Put them in code review and do not wave update commits through. Literature names this the most important practice.
  • Narrow what you snapshot. Storing whole HTML breaks on a single space. Store a normalised structural digest instead.
  • Take automatic updating out of the default. Follow the approval-test model and require an explicit act to update.
  • Attach a description to each snapshot. One line about what this file guarantees lets you decide later whether a break means update or fix.

A structural digest looks like this. It does not break when a sentence is edited, but it always breaks when a table disappears or a section goes missing.

// store the structure rather than the whole body
function structureDigest(doc) {
  return {
    h2: [...doc.querySelectorAll('h2')].map(el => el.textContent.trim()),
    tables: doc.querySelectorAll('table').length,
    listItems: doc.querySelectorAll('li').length,
    codeBlocks: doc.querySelectorAll('pre code').length,
    links: [...doc.querySelectorAll('a[href]')].map(a => a.getAttribute('href')).sort()
  };
}

8. The danger of batch processing - contamination from range-based replacement

Automating verification breeds the next ambition: you want to automate correction too. This is where the biggest accidents happen. A badly written checker merely gets noisy; a badly written batch corrector silently contaminates hundreds of files.

8.1 The most common failure - bounding the range by character offset

// Bad: only replace within the first 2000 characters
const head = html.slice(0, 2000).replace(/2025/g, '2026');
html = head + html.slice(2000);

The 2000-character boundary has nothing to do with document structure. In one file the body starts inside it, in another an external script URL sits there, and in a third the head runs past 2000 so the actual target falls outside the range. Process hundreds of files this way and exceptions are guaranteed, and those exceptions persist silently as wrong values. Worse still, the result remains grammatically perfect. Both the syntax and runtime layers pass it.

8.2 The second failure - a regular expression with no boundary

Omit boundaries from a word-level replacement and it will match part of a different word. In practice I ran a dictionary replacement over multilingual documents to convert certain Sino-Korean terms into plain Korean, and because the pattern had no boundary it struck inside unrelated words, producing several hundred strings in which two different writing systems were fused into a single word. The HTML was fine, it parsed, it rendered. It only looked wrong to a human reader. Afterwards this class of defect was converted into a standing mechanical proxy check: 'are two different writing systems mixed inside one word'. When you cannot check meaning directly, find a mechanical signal that correlates with it — the principle that section 10 builds on.

8.3 How to run a batch job safely

// Better: target a specific tag and attribute, with explicit boundaries
html = html.replace(
  /(<meta property="article:published_time" content=")[^"]*(")/,
  '$12026-07-27$2'
);

// always count before you run
const hits = [...html.matchAll(/<meta property="article:published_time"[^>]*>/g)];
if (hits.length !== 1) throw new Error(`expected 1, found ${hits.length} - aborting`);

The safety rules for batch work, in table form. This table works as a checklist as it stands.

RuleConcrete methodFailure it prevents
Target nodes, not offsetsAddress tags, attributes and paragraphs rather than character positionsContamination outside the intended range
Put boundaries in the patternFence attribute values with quote boundaries, words with word boundariesMatching inside a different word
Count firstPrint the number of pending changes and abort when it differs from the expectationMisjudged scope
Eyeball one casePrint 40 characters either side of the first match, confirm, then run the restA mis-designed rule
Make it idempotentRun twice; if the second run changes anything, the rule is wrongDouble application and cumulative damage
Keep it reversibleCommit separately before the job or keep a copyUnrecoverable state
Re-run all three layersIn particular, redo the semantic random-sample reviewNew defects introduced by the correction

9. The statistical limit of sample review - if twenty look fine, is it clean?

'I checked twenty and found nothing' is routinely used as grounds for reassurance. Run the numbers and it is weaker than it sounds.

For a population with defect rate p, the probability that a random sample of n contains at least one defect is 1 − (1 − p)n. The table below is that formula computed directly.

Actual defect rateSample of 5Sample of 20Sample of 50Sample of 100
10% (one in ten)41.0%87.8%99.5%99.99%
5% (one in twenty)22.6%64.2%92.3%99.4%
1% (one in a hundred)4.9%18.2%39.5%63.4%
0.5% (one in two hundred)2.5%9.5%22.2%39.4%

How to read it.

  • At a 10% defect rate, twenty samples catch it about 88% of the time. Common defects are adequately caught by small samples.
  • At a 1% rate, twenty samples catch it 18% of the time. Four times out of five it sails through. Rare defects are effectively invisible to sample review.
  • Confirming a 1% rate at the 95% level takes roughly 300 items. This is the so-called rule of three, where the required sample is about 3 divided by the defect rate.
  • The habit of 'looking at the first five' is not a sample at all. Without randomness the arithmetic above does not hold. Early artifacts are usually made with more care, which skews the result optimistic.

From here the conclusion forks in two.

  • Rare but critical items — public URLs, monetary amounts, legal wording, exposed personal data, out-of-date contact numbers — should not rely on sample review. Build exhaustive automated checks. Fortunately these items tend to have mechanical criteria, so automating them is comparatively easy.
  • Frequent but non-critical items — tone, naturalness of phrasing, the feel of a headline — are adequately covered by random sampling. Attaching exhaustive checks here costs a lot and returns little.

Manufacturing quality control has long since tabulated this balance. The AQL tables of ISO 2859-1, known in the United States as ANSI/ASQ Z1.4, specify how many units to sample per lot size and how many defects are acceptable. They do not transfer verbatim to software artifacts, but the mindset that fixing the sample size also fixes the detection power transfers perfectly. Choosing a sample size first and asking about detection power afterwards is the wrong order.

10. What to automate and what to look at with your own eyes

The automation decision splits on two axes: is the criterion mechanical, and does it repeat.

Low repetitionHigh repetition
Mechanical criterionHandle with a throwaway script and discard itTop automation priority. Spend budget here first
Subjective criterionLook at it yourself. Attempting automation is wasteProxy metrics plus checklists plus random sampling

Some items are routinely left out of the cost calculation.

  • Maintenance costs more than construction. When the artifact format changes, rules go stale immediately, and a rule that has not kept up becomes a false-positive factory.
  • Multiply out the cost of a single false positive. Thirty per day at two minutes each is one hour per day, plus the real defects that leak through the alert fatigue it creates.
  • Put the cost of a single miss in too. One wrong public URL or one wrong amount can cost more than a hundred false positives. Comparing those two magnitudes is what justifies a threshold.
  • If automation is hard, change the target. 'Is the translation accurate' is hard to automate; 'do the lists of numbers in source and target match' is easy.

That last item pays for itself most often. When you cannot check meaning directly, find a mechanical proxy that correlates with it. Useful proxies include the following.

  • Set comparison of numbers, URLs and proper nouns — extract from source and target and compare as sets. Catches added and omitted information cheaply.
  • Matching structural counts — check that section, table and list-item counts agree across language editions. Strong at detecting wholesale omission.
  • Length ratio outliers — flag when a per-language length ratio leaves its usual band. Because density differs by language, compare against the usual ratio rather than absolute length.
  • Exhaustive link status checks — broken links have an entirely mechanical criterion, which puts them among the highest-yield automations available.
  • Writing-system mixing checks — detect whether two different scripts appear inside a single word. Catches replacement accidents and translation accidents at once.
  • Forbidden and retired value checks — maintain a list of renamed schemes and discontinued contact numbers, the 'once correct' values. This is the one part of fact-checking that automates cheaply.

11. The order in which to assemble the pipeline

Trying to build all three layers at once usually fails. There is an order.

  1. Start with an incident list. Write down the defects that actually shipped in the last three months. A checker should first block defects that really happened, not defects you imagined. Without this list there is no basis for prioritising rules.
  2. Assign each incident to a layer. Split into what the syntax layer catches, what needs the runtime layer, and what is semantic only. The table in section 2 works as is.
  3. Automate the syntax and runtime layers exhaustively first. They are cheap, fast and low in false positives. Whatever they catch should never reach a human.
  4. Build the semantic layer from proxies plus random sampling. Exhaustive for critical items, sampled for the rest, with the arithmetic in section 9 as the basis for sample size.
  5. Put regression testing on the calendar. Monthly, and on every rule change. Skip this and the four steps above quietly rot over time.

A few rules apply once you are operating.

  • Report three values, not two. Pass, fail and needs review. Treating 'needs review' as a failure is what makes people want to switch rules off.
  • Introduce new rules as warnings first. Promote to blocking only after confirming the false-positive rate is low enough. A rule that blocks from day one gets deleted at its first false positive.
  • Record a reason whenever you suppress. An unexplained suppression becomes a mine nobody dares touch. A steadily rising suppression count is itself a signal that the rule needs work.
  • Record which layers ran, on the artifact itself. When something goes wrong, 'we never checked' and 'we checked and missed it' call for completely different responses, and only the latter leads to rule improvement.
  • Version-control the checker. A history of when and how a rule was narrowed is what lets you trace the cause of a miss discovered much later.

Conclusion: a checker is an instrument, not a rubber stamp

Use a checker as a rubber stamp and you will lose. A stamp says 'this is fine'; a checker has no capacity to say that. All a checker can say is 'nothing was wrong within what I look at', and that sentence is only useful when what it looks at is written down.

So treat the checker as an instrument. An instrument's datasheet states its measurement range and its error. A verification system needs the same: which layer sees what, what each layer cannot see, what covers the blind spot, and how you confirm the instrument has not broken. That last item is regression testing, and it is usually the first thing omitted.

To summarise: the syntax layer is cheap, so turn all of it on. The runtime layer is the only place a large share of failure shapes can be caught, so build it. The semantic layer gives up exhaustiveness and instead splits into exhaustive checks for critical items, random sampling for the rest, and mechanical proxy metrics. When a false positive appears, narrow the condition instead of switching the rule off. After narrowing, seed a defect to confirm detection still works. Batch corrections should target nodes rather than offsets, count before running, stay idempotent, and remain reversible.

The volume of AI-produced artifacts keeps rising. The bottleneck always forms on the verification side, and making checks shallower to relieve it only devalues the green light. Ten layered checks beat a hundred shallow ones. As of July 2026, what separates teams that run smoothly from teams that keep having incidents is often not their choice of model but the design of this pipeline.
