GitHub スタックPR パブリックプレビュー - 大きな変更を積み上げて分けると何が変わるか

層を積むのは易しい。下が変わったとき上を合わせ直すのが難しい

2026-08-01 開発/インフラ

序論: ファイル40個のPRの前でレビューが止まる

PR一つにファイルが40個入った。スキーマ変更、そのスキーマを使う照会層、その層を呼ぶAPIエンドポイント、そしてついでに整理した設定ファイルまで一塊だ。レビュアーが開いて閉じた。三日目、承認がない。急かすと「明日見る」と返ってくる。その間に作者はこのブランチの上に次の作業を載せ始める。この時点で問題はレビュアーの真面目さではなく、レビュー不可能な形で仕事が届いたということだ。

2026年7月30日、GitHub がスタックPRをパブリックプレビューで公開した。大きな変更を層に積み上げ、層ごとに別々にレビューを受けさせる機能だ。ところがこの記事の関心は「新機能が出た」ではない。ブランチを繋ぐ作業は元々ローカル git でできたことであり、実際に下で自分の手で作って見せる。発表されたのは概念ではなく、その概念を維持するのにかかる反復作業をプラットフォームが肩代わりするという部分だ。

だからこの記事が投げる問いは一つだ。大きな変更を分ける費用を道具がどれだけ減らしてくれるのか。積み上げの本当の難しさは層を作ることにはない。下が変わるたびに上を合わせ直す作業にある。その作業をローカル git でそのまま回して、どこが痛くて何が自動化されるのかを出力で見せる。

実行環境。以下の git 出力はすべて Windows 10 Pro (10.0.19045) で実際に実行した結果だ。git 2.48.1.windows.1、シェルは GNU bash 5.2.37 (MSYS2/MinGW64)。コマンドはヒアドキュメントではなくファイルに保存して実行し、例のリポジトリは一時ディレクトリに新しく作ったものだ。ブランチ名もファイル名もすべて架空の例である。

この記事が扱わないこと。PRの開き方とレビューの基本はPull Requestとコードレビューにある。「オープンPRの数に上限を掛ければ待ちが減るのか」というキューの動力学の問題はPR上限とキューの動力学でシミュレーションとして扱った。この記事は一件の大きさを分ける方法だけを見る。ブランチ戦略そのものはブランチ戦略にある。

1. 何が発表されたのか - 確認した範囲の事実だけ

公式文書とチェンジログを直接開いて確認した内容だけを書く。要約記事やコミュニティの投稿で機能を断定してはいない。

  • 発表日と状態。GitHub チェンジログの2026年7月30日付の項目がスタックPRのパブリックプレビューを告知した。全リポジトリへの展開は「数日かけて」進むと書かれている
  • 定義。チェンジログの文は「大きな変更を小さくレビュー可能なPRたちに割る」であり、「変更の焦点の定まった層をそれぞれ担う順序付きのPRの束」と説明する
  • 構造の規則。文書は一番下のPRが既定ブランチを向き、その上の各PRがすぐ下のブランチを向くと書いた。そして「ある層のコードが別の層のコードに依存するなら、その依存対象は同じブランチかより下のブランチになければならない」という原則を提示する
  • 扱える場所。github.com、GitHub CLI、モバイルアプリだ。CLI 拡張は gh extension install github/gh-stack で入れ、文書に登場する下位コマンドは gh stack init、gh stack add、gh stack submit、gh stack rebase、gh stack push である
  • web で作る方法。各PRの基準ブランチをすぐ下のPRのブランチに指定した上でスタック作成の項目を選ぶ方式も文書にある
  • 制約。すべてのブランチが同じリポジトリになければならず、フォークをまたぐスタックは非対応だ。GitHub Desktop では非対応。自動マージは非対応。スタックのブランチ同士に完全な線形履歴が要る
  • マージキュー。文書はスタックがマージキューを完全に対応し正しい順序でキューに入ると書き、スタックを一塊に保つためにマージグループが設定された最大サイズを最大50パーセントまで超えることを許すと明かした。その余裕でも足りなければ連続するマージグループに分割される。ただしチェンジログはマージキュー対応が「数週間かけて」順次適用されると述べたので、この部分はリポジトリごとに到達時期が異なり得る

プレビュー時点の明示。文書に「この機能はパブリックプレビューであり変更され得る」という文言がそのまま書かれている。この記事は2026年8月1日時点で確認した内容だ。画面構成、下位コマンド名、制約の一覧は正式リリース前に変わり得るので、導入を決める前に必ず原文を確認し直してほしい。

開けなかったもの / 開かなかったもの。検索結果に出たコミュニティの議論、ロードマップの課題、gh-stack リポジトリのページ、クイックスタート文書、組織向け展開チュートリアルは開いていない。だからそれらの文書にしかない内容はこの記事にない。下の「参考資料」には実際に開いて読んだ五箇所だけを書いた。

2. なぜ大きなPRが問題なのか - 数値ではなく構造で

「大きなPRはレビューされない」という言葉はよく聞くが、その理由を統計で説明しようとすると大抵は他人の数字を写すことになる。ここでは数字を使わず構造だけで見る。レビューは読み、文脈を頭に保ち、判断する三段階だ。PRが大きくなるときこの三つが同じ速さでは大きくならない。

  • 読む量は線形に増える。ファイルが二倍なら読む時間も概ね二倍だ。ここまでは耐えられる
  • 保つべき文脈はそれより速く増える。40個目のファイルを見るときレビュアーは前の39個が何を変えたか覚えていなければならない。「この関数の署名が変わったのは正しいか」を確かめるには上にスクロールして探し直す必要があり、その往復がファイル数につれて増える
  • 判断の単位は逆に大きくなる。レビュー承認はPR単位でしかできない。40個のうち39個が完璧で一つが怪しければ全部が待ち状態になる。良い部分が悪い部分に人質に取られる
  • 修正が入ればすべて見直す。作者が指摘を反映して押すと、レビュアーは「何が変わったか」を探し直さねばならない。PRが大きいほどその再確認の費用が大きく、だから二度目のレビューが緩くなる
  • 巻き戻しの単位がレビューの単位と同じだ。リリース後に問題が出たとき戻せる最小単位はそのPR全体になる。スキーマ変更のせいでAPIエンドポイントまで一緒に消える
  • CIが全部か無かで動く。40ファイルのうち一箇所のリント違反が全パイプラインを赤くする。残り39個が通ったという事実には何の力もない

まとめると大きなPRの問題はレビューの最小単位と変更の最小単位が強制的に同じになることだ。積み上げはこの二つを引き離そうとする試みである。変更は大きくやりつつ、レビューと承認と巻き戻しは層単位でやる。

一つははっきりさせておこう。分けることはレビュー容量を増やさない。一週間にチームが消化できる変更の総量を決めるのはレビュアーの時間であって、PRを切る方式ではない。上限ルールが待ちを減らせない理由を前の記事でキューとして扱ったが、ここでも同じ線が保たれる。スタックが変えるのは総量ではなく一件あたりの時間と部分的な通過の可能性だ。

3. 積み上げとは何か - ローカルgitで自分の手で作る

定義は一行だ。ブランチの基準をトランクではなくすぐ下のブランチに取ること。そうすると各ブランチの差分画面には下が既にやったことが除かれ、その層が新たにやったことだけが残る。特別な道具なしに作れる。

$ git switch -c stack/1-db   main          # 1層目: DB接続プール設定
$ git switch -c stack/2-repo stack/1-db    # 2層目: 照会層 (1層目の上に)
$ git switch -c stack/3-api  stack/2-repo  # 3層目: APIエンドポイント (2層目の上に)

こうして作ったリポジトリを覗くとこうなる。

git version 2.48.1.windows.1 / MINGW64_NT-10.0-19045

=== 1-2. the stack as one line of history ===
* 3f0f26a (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 50bdde2 (stack/2-repo)          feat(repo): order lookup, raise pool size
* cb5f977 (stack/1-db)            feat(db): add connection pool config

=== 1-3. what each branch points at ===
main          78b0629  chore: bootstrap trunk
stack/1-db    cb5f977  feat(db): add connection pool config
stack/2-repo  50bdde2  feat(repo): order lookup, raise pool size
stack/3-api   3f0f26a  feat(api): GET /orders/:id

三つのブランチが一本の線の上の別々の地点を指している。これがスタックのすべてだ。枝分かれした枝ではなく一本の線に打たれた目盛りである。では各層のレビュー単位を見よう。

=== 1-4. the REVIEW UNIT of each layer (diff vs the layer below) ===
--- base=main          head=stack/1-db
 db.yml | 3 +++
 1 file changed, 3 insertions(+)
--- base=stack/1-db    head=stack/2-repo
 db.yml  | 2 +-
 repo.py | 2 ++
 2 files changed, 3 insertions(+), 1 deletion(-)
--- base=stack/2-repo  head=stack/3-api
 api.py | 2 ++
 1 file changed, 2 insertions(+)

=== 1-5. what ONE big PR would have looked like (main..top) ===
 api.py  | 2 ++
 db.yml  | 3 +++
 repo.py | 2 ++
 3 files changed, 7 insertions(+)

同じ作業だ。統合して見ればファイル3個に7行追加であり、層で見ればファイル1個、2個、1個に分かれる。例なので規模は小さいが比率はそのまま大きくなる。ファイル40個のものが12個、20個、8個に分かれれば三人が並行して見られるし、1層目は今日承認され得る。

3.1 層をどこで切るか - これだけは道具にできない

文書の依存の原則を読み直すと切る基準が出てくる。ある層のコードが依存する対象は同じ層かより下になければならない。この条件を満たすように切る作業が積み上げの唯一の創作部分であり、道具が代わりにやってくれない。

  • 技術方向に切る。リポジトリ層 → サービス層 → コントローラのように呼び出し方向が下から上へ向くように置く。上が下を呼び、下は上を知らない
  • 「準備」と「本作業」を分ける。名前変更、ファイル移動、整形のように挙動が変わらない変更を一番下の層に抜く。この層は読みやすいので早く承認される
  • 機能フラグを一番上に。スイッチを入れるコミットを最後の層に置けば、下の層たちは無害な状態で先にリリースできる
  • 互いを参照する二つの塊は切らない。AがBを呼びBもAを呼ぶなら順序を決められない。こういうものは一つの層に置く
  • テストはその層に付ける。テストを最後の層に寄せると下の層のCIが意味を失う
  • 層の数は少なく。層が増えるほど下が揺れたとき合わせ直す対象が増える。次の節がその費用を見せる

4. 下が変われば上が揺れる - リベースと衝突、そして巻き戻し

ここが積み上げの実際の費用だ。レビュアーが1層目に指摘を一つ残したとしよう。接続プールが小さすぎるという指摘で、作者は1層目にコミットを一つ足す。その瞬間に何が起きるか見よう。

=== 2-1. reviewer asks the bottom layer to change: pool size 5 -> 10 ===
stack/1-db moved: cb5f977 -> 63509a2

=== 2-2. the layers above are now stale ===
* 63509a2 (HEAD -> stack/1-db)  fix(db): pool size 5 -> 10 per review
| * 3f0f26a (stack/3-api)        feat(api): GET /orders/:id
| * 50bdde2 (stack/2-repo)       feat(repo): order lookup, raise pool size
|/
* cb5f977                        feat(db): add connection pool config

一本だった履歴が分岐した。2層目と3層目は依然として古い1層目にぶら下がっている。この状態のままだと2層目のPR画面には下でたった今直した内容が反映されず、CIも古い基準で回る。上の層たちを新しい1層目の上に動かさねばならない。

4.1 すぐ上の層を動かすときに衝突する地点

$ git switch stack/2-repo
$ git rebase stack/1-db
Auto-merging db.yml
CONFLICT (content): Merge conflict in db.yml
error: could not apply 50bdde2... feat(repo): order lookup, raise pool size
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
rebase exit code: 1

--- status while stopped ---
UU db.yml
A  repo.py

--- the conflicted file ---
pool:
<<<<<<< HEAD
  size: 10
=======
  size: 20
>>>>>>> 50bdde2 (feat(repo): order lookup, raise pool size)
  timeout: 30

衝突した。なぜ起きたかが重要だ。1層目がその行を5から10に直し、2層目も元々同じ行を5から20に直すコミットだった。リベースは2層目のコミットを新しい1層目の上に適用し直そうとするのだが、基準となる行が既に変わっていて自動で決められない。

  • 衝突は層が同じファイルの同じ行を触ったときだけ起きる。層を技術方向にうまく切ってあれば大半のリベースは静かに終わる
  • 衝突表示で HEAD 側が新しい基準 (下の層) であり、下側が今適用中のコミット (上の層) だ。普段のマージと上下が逆に感じられる地点なのでよく間違える
  • 止まっている間リポジトリは中間状態だ。.git/rebase-merge ディレクトリが存在するかで確認できる
  • 層が三つならこの作業が最大二回起きる。層の数がそのまま反復回数だ

4.2 巻き戻しの方法 - 三つの脱出口

衝突の前で慌てる必要がないのは巻き戻しが完全に保証されているからだ。実際に戻してみた。

=== 2-4. escape hatch: abort puts everything back ===
$ git rebase --abort
after abort, stack/2-repo = 50bdde2
db.yml on stack/2-repo:
pool:
  size: 20
  timeout: 30

=== 2-9. undoing a FINISHED rebase (reflog) ===
a4f0a88 stack/3-api@{0}: rebase (finish): refs/heads/stack/3-api onto 8e137ce
3f0f26a stack/3-api@{1}: commit: feat(api): GET /orders/:id
50bdde2 stack/3-api@{2}: branch: Created from stack/2-repo

$ git reset --hard stack/3-api@{1}    # リベース直前の状態に正確に復帰

三つを区別しておけばよい。

  • 進行中なら git rebase --abort。ブランチが開始地点に正確に戻る。上の出力では 50bdde2 に復帰し、ファイルの中身も元通りだった
  • 既に終わっていれば git reflog。リベース前の位置が @{1} に残っている。git reset --hard でその地点に戻す
  • ORIG_HEAD も同じ用途だ。リベース直前の位置を指すので git reset --hard ORIG_HEAD が短い形で使える。ただし他のコマンドが上書きするのでリフログの方が安全だ
  • 重要な前提。この巻き戻しはローカルでだけ無害だ。既にリモートへ強制プッシュしていれば他人が取得した履歴とずれる。スタックのブランチは本人だけが押すという合意が要る

4.3 その上の層は開始点を自分で指定する必要がある

2層目を動かした後は3層目が問題だ。3層目は古い2層目を指しているので、単純なリベースでは見当違いのコミットまで引っ張ってくる。

=== 2-6. layer 3 still points at the OLD layer 2 ===
layer3 does NOT contain the new layer2 -> must rebase too

=== 2-7. rebase layer 3 with --onto (old base -> new base) ===
$ git rebase --onto stack/2-repo 50bdde2 stack/3-api
Successfully rebased and updated refs/heads/stack/3-api.

=== 2-8. the stack is one line again ===
* a4f0a88 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 8e137ce (stack/2-repo)          feat(repo): order lookup, raise pool size
* 63509a2 (stack/1-db)            fix(db): pool size 5 -> 10 per review
* cb5f977                         feat(db): add connection pool config

git rebase --onto 新基準 旧基準 対象 の三つの引数がそれぞれどこへ、どこから、何をだ。古い2層目のコミットハッシュを手で書き入れねばならない点に注目してほしい。層が五つならこの手作業が四回で、ハッシュを一つ書き間違えるとコミットが消えるか重複する。ここが人が間違える場所であり、道具が狙う場所だ。

5. スタック全体を一度に動かす - update-refs

git 自体にもこの反復を減らす仕掛けがある。git rebase -h が「リベース対象のコミットを指すブランチも一緒に更新する」と説明する --update-refs だ。ない場合とある場合を同じ状況で回して比べた。状況はトランクが前に進んだ場合、つまり他人のPRが先にマージされたよくある状況である。

=== 3-1. WITHOUT --update-refs ===
before:  main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6d241f4
$ git switch stack/3-api
$ git rebase main
after:   main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6204587

* 6204587 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 483c62e                        feat(repo): order lookup
* b422809                        feat(db): add connection pool config
* 5ea68a0 (main)                 chore: bump trunk
| * a08d522 (stack/2-repo)       feat(repo): order lookup
| * 9b331dc (stack/1-db)         feat(db): add connection pool config
|/
* c2562b8                        chore: bootstrap trunk

これがスタックが静かに壊れる姿だ。3層目は新しいトランクの上にうまく動いたのに1層目と2層目のブランチは古いトランクにそのまま残った。この状態で押せば1層目のPRと2層目のPRは古いコードをレビューすることになり、3層目のPRの差分画面には下の層が既にやったことが再び登場する。層を分けた意味が消える。

=== 3-2. WITH --update-refs, same situation ===
before:  main ebfef49   1-db 7862785   2-repo d8b3ddc   3-api 79b45bc
$ git rebase --update-refs main
Rebasing (1/5)(2/5)(3/5)(4/5)(5/5)
Successfully rebased and updated refs/heads/stack/3-api.
Updated the following refs with --update-refs:
    refs/heads/stack/1-db
    refs/heads/stack/2-repo
after:   main ebfef49   1-db 469e32a   2-repo cd35dca   3-api a807932

* a807932 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* cd35dca (stack/2-repo)          feat(repo): order lookup
* 469e32a (stack/1-db)            feat(db): add connection pool config
* ebfef49 (main)                  chore: bump trunk
* 153d615                         chore: bootstrap trunk

=== 3-3. make it the default for this repo ===
$ git config rebase.updateRefs true
plain 'git rebase main' now moves every layer   exit code: 0

一本の線が保たれ中間の層のブランチも一緒に動いた。git が「次の参照を更新した」と自分で知らせてくれる。rebase.updateRefs を真にすれば普通の git rebase main にも同じ動作が適用される。

この節がこの記事の核心だ。積み上げの概念は3節で既に終わっている。コマンド三行で作れる。ところが4節で見た手作業 — 古いハッシュを探して --onto に入れる作業 — が層の数だけ繰り返される。道具の価値は概念を提供することにあるのではなく、この反復を無くすことにある。--update-refs がローカルでその仕事をし、プラットフォーム機能はそこにレビュー画面と承認ルールとマージ順序を繋げることを足す。だから道具があってもどこで切るかを決める判断は依然として人の役目だ。

既にリモートへ押した強制プッシュが必要他人が取得済みなら危険リモートのリフログはない

6. マージ順 - 下からでなければならない理由

文書は「スタックPRはトランクに最も近い下から上へマージされる」と書き、「中間のPRを単独でマージすることはできず、その下のPRが常に一緒にマージされる」と明示した。規則だけ読むと方針のように見えるが、ローカルでやってみると履歴の性質から出てくる物理的な制約であることが明らかになる。

=== 4-2. merge the MIDDLE first: what actually lands ===
commits layer2 would bring in:
  fc9279e feat(repo): order lookup
  6c5b822 feat(db): add connection pool config     <-- 1層目のコミットが付いてくる

$ git switch main
$ git merge --no-ff stack/2-repo

files now on main:
  README.md  app.yml  db.yml  repo.py            <-- db.yml も一緒に入った

what is LEFT in the bottom PR (main..stack/1-db):
  commits: 0
   repo.py | 2 --
  -> the bottom PR is now EMPTY

2層目だけを選んでマージしたところ1層目のコミットが一緒にトランクに入った。当然だ。2層目の履歴の中に1層目のコミットが既に入っているからだ。その結果が最後の行である。1層目のPRに残ったコミット数が0になった。

  • 1層目は自分の名前でレビューされないままトランクに入った。承認ルールを層ごとに掛けていたなら、そのルールが静かに迂回される
  • 1層目のPR画面はもう「変更なし」に見える。レビュアーは何があったのか知るすべがない
  • 差分が負の値で出たことにも注目してほしい。トランクが1層目より進んでいるので、1層目を基準に見ると repo.py が削除されたように見える
  • だからプラットフォームが中間の単独マージを防ぐのは制限ではなく保護だ。下を一緒にマージしてこの状況を根本から遮断する

6.1 スカッシュマージという罠

多くのチームがスカッシュマージを既定に使う。コミット一つに押し潰してトランクの履歴を綺麗に保とうとするのだ。ところがスカッシュは内容は同じでコミットハッシュは違う新しいコミットを作る。スタックと出会うとどうなるか二つの場合に分けて回した。

=== 4-3. bottom squash-merged, then the stack rebased (誰も触らなかった場合) ===
$ git merge --squash stack/1-db
$ git commit -m "feat(db): add connection pool config (#1)"
same content, different commit id:
  main:db.yml        c7c0b78
  stack/1-db:db.yml  c7c0b78      <-- 中身(blob)は同一

$ git switch stack/2-repo
$ git rebase main
warning: skipped previously applied commit 8fd3e84
hint: use --reapply-cherry-picks to include skipped commits
Successfully rebased and updated refs/heads/stack/2-repo.
layer 2 review unit:
 repo.py | 2 ++                                   <-- 綺麗に整理された

=== 4-4. same, but the maintainer edited one line while squashing ===
$ git rebase main
Auto-merging db.yml
CONFLICT (add/add): Merge conflict in db.yml
error: could not apply 1cb43a1... feat(db): add connection pool config
  AA db.yml
pool:
<<<<<<< HEAD
  size: 8
=======
  size: 5
>>>>>>> 1cb43a1 (feat(db): add connection pool config)
  timeout: 30
rebase exit code: 1

二つの結果が分かれた。誰も触らずにスカッシュしたときは git が「既に適用されたコミットを飛ばす」と知らせて自分で整理し、2層目のレビュー単位は綺麗に repo.py 一つになった。ところが管理者がマージしながら一行でも直すと同じファイルが両側で新しく生まれたものとして扱われ add/add 衝突が起きた。

  • 「スカッシュマージを使うとスタックが壊れる」という話は半分だけ正しい。内容がそのままなら git が自分で飛ばす
  • 壊れるのはマージ時点で内容が変わるときだ。web エディタで誤字を直す習慣、自動整形器が付くパイプライン、リリースノートをコミットに挟む慣習が全部ここに当たる
  • 文書が求める完全な線形履歴の条件も同じ話だ。下のブランチにプッシュが入るかトランクが前に進むとその条件が揺らぐと文書が直接書いている
  • 導入前にチームの既定マージ方式でスタックを一度通してみる以外に確かめる方法はない

7. 三つの方式の対照 - 大きなPR、独立PR、積んだPR

同じ作業を三通りで出せる。どれかが優れているのではなく費用をどこに置くかが違う。

基準一つの大きなPR複数の独立PR積んだPR
レビュー単位全体が一塊PRごとに独立層ごとに独立、下の内容は除かれる
依存の表現なし(一塊なので不要)表現できない。説明欄に文で書くだけ基準ブランチとして履歴に刻まれる
重複した変更なし重なるファイルがあれば両方に現れるなし。下のものは上で見えない
巻き戻し全部か無かPR単位、ただし順序は守る必要上から層単位
部分的な通過不可可能下からのみ可能
CI費用1回分、失敗すれば全体を再実行PR数だけ、互いに無関係層数だけ + 下が変われば上が全部再実行
マージ順制約なし制約なし(衝突は各自解決)下から強制
作者の負担低い中程度(衝突を手で解決)高い。下が変わるたびリベース
レビュアーの負担非常に高い低い、ただし全体像が見えない低い + スタック地図で全体を把握
必要な道具なしなしローカルgitで可能、プラットフォーム対応があれば楽

表から読むべきは積んだPRの費用が作者に寄るという点だ。レビュアーが楽になる分だけ作者がリベースを引き受ける。だから一人で使うチームでは利得がなく、レビューが実際にボトルネックであるチームでのみ価値が生まれる。

8. 実際の現場での姿 - 人数、承認ルール、リリースブランチ

ここでは特定の組織の話をしない。開発組織でよく見られる構造的な条件三つとスタックがどう噛み合うかだけを見る。

8.1 レビュアーが少ないとき

  • スタックはレビューの「件数」を増やす。層が三つなら通知が三つ来る。レビュアーが一人だけなら同じ人が三回開くことになる
  • 合計時間が減るかは層がうまく切れたかにかかっている。うまく切れていれば各層が短くて合計が減り、間違って切っていれば文脈を三回取り直すせいでかえって増える
  • 得るものは確実に一つある。下半分を先に通せる。作者は承認された下の層の上で次の作業を続けられ、巻き戻しの危険が減る
  • 逆にレビュアーが一人でその人が席を外すとスタック全体が丸ごと止まる。下が詰まれば上はマージできないので単一障害点が強くなる

8.2 承認ルールが掛かっているとき

  • 必須承認人数やコードオーナーの規則があると層ごとにその規則を通過せねばならない。文書も下のPRがすべて要求条件を満たさねばマージされないと書いた
  • 承認イベントが層の数だけ必要という意味だ。必須承認が二人で層が四つなら承認行為が八回起きる
  • だから承認ルールが厳しい組織ほど層を三つ四つ以下に保つ方が現実的だ
  • コードオーナーが層ごとに違えばむしろ有利だ。DB担当が1層目を、API担当が3層目を並行して見れば合計の待ち時間が実際に減る。大きなPRでは二人が同じ40ファイルをそれぞれ眺めねばならなかった
  • 自動マージが非対応という文書上の制約もここで体感される。承認が全部揃っても人がマージボタンを押さねばならない

8.3 リリースブランチ戦略と噛み合うとき

  • スタックの底がトランクではなくリリースブランチを向くと、そのブランチにホットフィックスが入るたびスタック全体が揺れる。5節の --update-refs が事実上必須になる
  • リリースが凍結される期間にスタックが跨っていると下は今回のリリース、上は次のリリースになる状況が生まれる。このとき上の層の基準を次のリリースブランチに移す必要があり、それがまたリベースだ
  • チェリーピックでリリースに反映する慣習があれば6.1節の内容は同じでハッシュは違う問題がそのまま再現する
  • フォーク経由で貢献を受けるリポジトリならそもそも使えない。文書がフォークをまたぐスタックは非対応と明示した
  • 実務的にはスタックの寿命をリリース周期より短く保つことが唯一の解法だ。層がリリースの境界を越え始めると管理費用が急激に上がる

9. 導入の判断 - いつ価値があり、いつ過剰か

結論から書くとこうだ。スタックはレビュー容量を増やす道具ではない。一週間に処理される変更の総量は依然としてレビュアーの時間が決める。スタックが変えるのは一件あたりのレビュー時間と下半分を先に通せる可能性、この二つだけだ。だから判断基準も狭くなる。

状況積み上げが合うか理由
変更が階層方向に自然に割れる合う依存の向きが一方向なので順序を決められる
名前変更や移動のような無害な準備作業が大きい合う一番下の層に抜けば早く承認される
下の層だけ先に出しても意味がある合う部分的な通過の利得が実際に発生する
コードオーナーが層ごとに違う合う並行レビューで合計の待ちが減る
二つの塊が互いを参照する合わない順序を決められない。一つの層に置く
層が五つを超える合わない更新費用が利得を食う
下の層が毎日変わる合わない上の層を毎日リベースすることになる
PRが既にファイル5個ほどだ合わない分けるものがない。オーバーヘッドだけ増える
フォークから貢献を受ける不可文書が非対応と明示
スカッシュマージ + マージ時点の編集の慣習まず試験6.1節の衝突が再現し得る

9.1 道具なしにローカルgitだけでできることとできないこと

  • できる。層を作ること。git switch -c 上の層 下の層 三行で終わりだ
  • できる。各層のレビュー単位を確認すること。git diff --stat 下の層..上の層 ならその層が新たにやったことだけが出る
  • できる。下が変わったとき上を動かすこと。--onto と --update-refs がこの仕事をする
  • できる。巻き戻し。--abort、リフログ、ORIG_HEAD
  • できる。PRを開くことまでも。各PRの基準ブランチを手で下の層に指定すればレビュー画面は同じようにその層だけを見せる
  • できない。下がマージされたとき上のPRの基準を自動で変えること。手でやると毎回忘れる
  • できない。レビュアーにこの層が全体のどこかを見せること。説明欄に一覧を書いておくしかなく、すぐ古くなる
  • できない。下からマージされるように強制すること。規律に頼ることになり6節の事故が起きる
  • できない。複数の層を一度の操作でマージすること
  • つまりプラットフォーム機能が埋める場所は正確にこの四つだ。残りは既に git にある

9.2 導入前のチェックリスト

  • 今のPRが実際に大きいか。ファイル数と待ち日数をまず測れ。小さいのに導入すれば損だ
  • ボトルネックがレビューか、それともリリースやQAか。レビューでなければスタックは何も直せない
  • チームの既定マージ方式は何か。スカッシュなら6.1節の試験を先にやれ
  • スタックのブランチを本人だけが押すという合意があるか。強制プッシュが行き交えば履歴がずれる
  • git のバージョンが2.38 以上か。--update-refs がなければ手作業が層の数だけ残る
  • 層を三つ四つ以下に保つ規則があるか
  • リリースブランチがスタックの底になることがあるか。あるなら寿命をリリース周期より短く取れ
  • フォーク経由の貢献があるか。あるならその経路はスタックを使えない
  • CI費用を負担できるか。下が変われば上が全部走り直す
  • プレビューだという事実をチームが知っているか。画面もコマンドも変わり得る

最後にこの記事全体の線を引き直す。スタックPRは大きな変更を分ける反復作業の費用を下げる道具だ。それ以上でもそれ以下でもない。どこで切るか、何を下に置くか、この変更を分ける価値があるか — この判断は道具が代わりにやってくれない。そして分けた後も処理量を決めるのは依然としてレビュー容量だ。層を増やしてもレビュアーの一日が長くなるわけではない。

# スタックPR — 積み上げの再現コマンドと導入チェックリスト

> 出典: braindetox.kr — GitHub スタックPR パブリックプレビュー
> 根拠: git 2.48.1.windows.1 / GNU bash 5.2.37 (MSYS2) / Windows 10 Pro で実行検証
> 時点: 2026-08-01。GitHub のスタックPRはパブリックプレビューであり、画面もコマンドも変わり得ます。
> このファイルをそのままAIに貼り、「この基準で自分たちのリポジトリを点検して」と書けば使えます。

## 1. スタックを作る (ローカルgitだけで)

```
git switch -c stack/1-db   main          # 1層目
git switch -c stack/2-repo stack/1-db    # 2層目は1層目の上
git switch -c stack/3-api  stack/2-repo  # 3層目は2層目の上
```

確認コマンド:

```
git log --graph --oneline --decorate main..stack/3-api
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads/
git diff --stat stack/1-db..stack/2-repo    # その層のレビュー単位だけ
git diff --stat main..stack/3-api           # 大きなPR一つならこの量
```

## 2. 下が変わったときの上の更新

```
# すぐ上の一層だけ
git switch stack/2-repo
git rebase stack/1-db

# 二つ以上上 (古い基準ハッシュを明示)
git rebase --onto stack/2-repo OLD_HASH stack/3-api

# スタック全体を一度に (git 2.38+)
git switch stack/3-api
git rebase --update-refs main

# 毎回自動で
git config rebase.updateRefs true
```

## 3. 衝突と巻き戻し

```
# 進行中に諦める
git rebase --abort

# 解決して続ける
git add db.yml
git rebase --continue

# 完了済みのリベースを戻す
git reflog stack/3-api
git reset --hard stack/3-api@{1}
git reset --hard ORIG_HEAD          # 短い形
```

- 衝突表示の HEAD 側が新しい基準 (下の層)、反対側が今適用中の上の層のコミット
- `.git/rebase-merge` があれば中間状態
- 巻き戻しが無害なのはローカルだけ。強制プッシュ後は他人が取得した履歴とずれる

## 4. マージ手順

- 下から上へマージする (プラットフォーム文書の規則)
- 中間だけの単独マージは不可 — 下は常に一緒にマージされる
- 中間を無理に先にマージすると下のPRの残りコミットが0になり、レビューなしで通ったことになる
- 下がマージされると上はトランクを基準に取り直される
- 自動マージは非対応 (プレビュー時点)
- スカッシュマージの試験: 内容がそのままならgitが飛ばす。マージ時に一行でも直すと add/add 衝突

## 5. 三つの方式の比較

| 基準 | 大きなPR一つ | 独立したPR複数 | 積み上げたPR |
|---|---|---|---|
| レビュー単位 | 全体が一塊 | PRごとに独立 | 層ごとに独立 |
| 依存の表現 | 不要 | できない | 基準ブランチに刻まれる |
| 巻き戻し | 全部か無か | PR単位 | 上から層単位 |
| 部分的な通過 | 不可 | 可能 | 下からのみ |
| CI費用 | 1回分 | PR数だけ | 層数だけ + 下の変更で全部 |
| マージ順 | 制約なし | 制約なし | 下から強制 |
| 作者の負担 | 低い | 中程度 | 高い (リベース) |

## 6. 導入チェックリスト

- [ ] 今のPRは本当に大きいか (ファイル数・待ち日数をまず測る)
- [ ] ボトルネックはレビューか (デプロイやQAならスタックは効かない)
- [ ] 変更が階層方向に割れるか (互いに参照するなら一層に)
- [ ] 層を三つ四つ以下に保つ規則があるか
- [ ] チームの既定マージ方式はスカッシュか (ならば先に試験)
- [ ] スタックブランチは本人だけが押すという合意があるか
- [ ] git 2.38 以上か (--update-refs が使える)
- [ ] リリースブランチがスタックの底になることがあるか
- [ ] フォーク経由の貢献があるか (あれば使用不可)
- [ ] 下が変わるたび上のCIが全部走り直す費用を払えるか

## 7. やってはいけないこと

- 層が互いを参照するように切ること — 順序を決められない
- 層を五つ以上に増やすこと — 更新費用が利得を食う
- スタックブランチを複数人が押すこと — リベースと衝突する
- 中間の層を先にマージしようとすること — 下がレビューなしで付いてくる
- スタックでレビュー容量が増えると期待すること — 総量はレビュアーの時間が決める
- プレビュー機能の画面やコマンドを固定として文書化すること
