epiq登場 - issueをGitリポジトリに入れてコンテキストスイッチを消す分散型issueトラッカー

端末内でイベントソーシングによりissueを管理するツールが再び投げかける問い - オフライン・分散・可搬性の価値とチーム協業の限界

2026-07-06 開発・インフラ

序論: なぜ再び「issueをGitの中へ」という話が出てくるのか

2026年7月、issueトラッカーを再び議論の的に押し上げたのは派手な新製品ではなく、とても古い問いだった。issueはなぜコードとは別の場所になければならないのか。Gitリポジトリの中にissueをまるごと入れて端末で扱う分散型issueトラッカーepiqが、その問いを再び投げかけた。GitHub IssuesやJiraに慣れた開発者には目新しく聞こえるだろうが、この発想自体は新しくない。2008年前後にも複数のチームが同じ問題意識から似たツールを作ったが、そのほとんどは静かに姿を消した。

本稿はepiqという個別ツールの機能を並べるだけでは終わらない。そのツールが改めて呼び起こした問い - issueトラッカーがコードリポジトリと分離しているときに生じる摩擦、そしてその摩擦をなくすためにissueをGitへ移す接近法の利点と欠点 - を筆者の視点で読み解く。hada(GeekNews)に掲載された紹介記事を出発点にしつつそのまま転載せず、git-appraise、Fossil、git-issueといった類似の試みと並べて、何が繰り返される失敗で、何が2026年に新しく変わったのかを確かめる。

結論を先に言えば、epiqが直面する強みと限界は、10年余り前にticgitやBugs Everywhereが直面したものと大きくは変わらない。ただ一つ、変化した変数がある。リポジトリの中でissueを読み書きする主体が、もはや人間だけではなく、端末で共に働くAIコーディングエージェントでもあるという点だ。

1. epiqとは何か - 端末の中の分散型issueトラッカー

epiqはGitHubリポジトリで公開されているオープンソースプロジェクトで、アカウントもサーバーも使わずローカルのGitリポジトリだけで動作するissueトラッカーを標榜する。

1.1 中核設計 - イベントソーシングとULID

epiqはissueを一つの共有ファイルに繰り返し上書きする代わりに、ユーザーごとに分離されたファイルへ追記専用(append-only)のイベントとして記録する。各イベントは時系列で並べ替え可能な識別子(ULID)と直前のイベントへの参照を併せ持ち、複数人がそれぞれオフラインで作業した後で後からマージしても、イベントが実際に起きた順序を機械的に復元できる。issueデータをGitの通常の3-wayマージにそのまま委ねるとテキスト衝突が起きやすいが、「誰が何をいつ行ったか」をイベントログとして残せば、マージ時の衝突面をかなり縮められるという設計判断として読める。

1.2 二重インターフェースとGit worktreeによる同期

操作面では、vimスタイルのキーバインド(h/j/k/l移動、:コマンドライン、?パレット)を用いる端末UIと、ブラウザGUIの両方を提供する。issueの状態は専用のGitブランチとworktreeに保存され自動的に管理されるため、実際の作業ブランチをチェックアウトしたりリベースしたりする日常の流れとissue同期の手順が互いにぶつからないよう分離されている。過去のissueトラッキングツールがしばしば犯した失敗 - issueのコミットが実際のコード履歴に混ざりログを乱雑にする問題 - をworktreeの分離で避けようとする設計である。

1.3 MCP対応 - AIエージェントのためのissueトラッカー

epiqは専用のMCP(Model Context Protocol)サーバーバイナリを提供し、Claude CodeのようなAIコーディングエージェントがissueを直接読み書きできるようにしている。後段で改めて扱うが、この部分がこのツールを単なる「端末派好みのissueトラッカー」ではなく「エージェンティックコーディング時代のissueトラッカー」として読み直させる核心である。

2. コンテキストスイッチという古い摩擦

epiqが正面から狙った問題から見ていこう。issueトラッカーとコードリポジトリが分離しているときに生じるコストである。

2.1 ブラウザ往復のコスト

issueを一つ確認するためにエディタからブラウザへ行き、また戻ってくる往復は些細に見えて、積み重なると大きい。深い集中が途切れた後に元の集中状態へ戻るまでにおよそ20分かかるとする研究もあり、この切り替えコストを年単位に換算して開発者一人当たり相当な規模の生産性損失と見積もる業界分析もある。正確な数字よりも重要なのは方向性だ。issueを見るためだけにツールを切り替える行為そのものが、すでにコストだということである。

2.2 issueトラッカーがコードと分かれてきた理由

ではそもそも、なぜissueトラッカーはコードリポジトリと分かれたまま発展してきたのか。理由は単純だ。issueトラッカーの中核利用者の少なくない部分は、コードを書かない。PM・QA・デザイナー・カスタマーサポート、時には顧客自身がissueを登録し状態を追う。彼らにGitリポジトリへアクセスしてコミットを作れと求めるのは、そもそも選択肢になり得なかった。そのためissueトラッカーは自然と、誰もがログインしてフォームを埋めるWebサービスとして定着し、その代償としてコードを扱う開発者は毎回もう一つウィンドウを開かねばならない立場になった。epiqがなくそうとしている摩擦は、まさにこの非対称性から生まれている。

3. issueをコードと共にバージョン管理する接近法 - 利点

issueがGitオブジェクトになった瞬間に得られる利益は三つに整理できる。

3.1 オフラインでも途切れない

issueがローカルのGitオブジェクトとして存在すれば、ネットワーク接続の有無にかかわらず読み書きできる。飛行機の中で、通信が不安定な現場で、社内網しか開いていない閉じた環境でも、issueを登録・更新した後、後で一度pushするだけで同期できる。クラウドissueトラッカーが前提とする常時接続を取り払うという点で、これは単なる利便機能ではなく設計思想の違いである。

3.2 リポジトリ一つで持ち運べる

git clone一つでコードとissue履歴がまるごとついてくる。会社のSaaSアカウントがなくても、そのSaaSがサービスを終了してさえも、issueデータはリポジトリの中にそのまま残る。オープンソースプロジェクトをフォークするときにissueまで一緒についてくる経験は、GitHub Issuesでは事実上不可能だが、Gitネイティブのissueトラッカーでは既定の動作である。

3.3 コミットとissueの因果関係が保存される

特定のコミット時点でどのissueが開いていて、どんな議論が交わされていたかを、別途APIを呼ばずその時点のGit履歴だけから再構成できる。古いブランチをcheckoutしたとき当時のissue状態まで一緒についてくるのは、issueとコードが物理的に同じタイムライン上にあるという事実の自然な帰結だ。epiqのtime travel機能もまさにこの点を狙っている。

4. 同じ接近法のトレードオフ - 欠点

利点だけを見るのは公平ではない。同じ設計が生む代償も明らかにある。

4.1 イベントソーシングでも衝突を完全にはなくせない

イベントソーシングはマージ衝突の面を縮小するが、完全にはなくさない。二人がオフライン状態で同じissueを同時に修正すると、多くの実装が採る規則どおり後からマージされたイベントが優先されやすく、その場合先に反映された修正が画面上では静かに後退しうる。元に戻す機能(time travel)があることと、そもそも衝突が起きたという事実をユーザーがすぐに気づけることとは、別の問題である。

4.2 リポジトリが重くなり、通知・検索が弱い

issue履歴が積み重なるほど、リポジトリ自体の容量とcloneコストが増える。別ブランチ・worktreeで分離しても、fetch/pushのトラフィックから完全に自由にはなれない。より根本的には、メール通知、全文検索、担当者の自動割り当て、バーンダウンチャートといったSaaS issueトラッカーの管理機能を、ローカルファーストのツールが同水準で再現するのは容易ではない。通知がないというのは些細に見えるが、issueが開かれたという事実そのものを能動的にpullしなければ誰も気づかないということを意味する。

4.3 配布方式への懸念

epiqはバイナリのインストールスクリプトとnpmパッケージの二経路で配布される。サプライチェーンの信頼が話題になる時期に、インストールスクリプトをそのままパイプ実行したりnpmのグローバルインストールを使ったりすることへの警戒は珍しい反応ではなく、実際に公開後のコミュニティ議論でも配布方式への懸念が挙がった。ツール自体の設計とは別に、ローカルファーストのCLIツールが越えるべき信頼の壁である。

5. 既存の方式(GitHub Issues・Jira)との対比

epiq流の接近法とSaaS issueトラッカーを並べると、トレードオフがはっきりする。

項目GitHub Issues / Jiraepiq(Gitベース)
データの所在中央サーバー(SaaS)ローカルGitリポジトリ
オフラインアクセス事実上不可(Web必須)可能
可搬性サービスに依存git cloneでまるごと移動
非開発者のアクセス性高い(Webフォーム)低い(端末・ローカルGUI)
通知・検索・レポーティング成熟未成熟
協業の可視性中央ダッシュボード各自clone・pullが必要
AIエージェント連携API呼び出し経由ローカルファイル・MCPで直接アクセス

この表が示すのは優劣ではなくトレードオフである。GitHub IssuesとJiraは組織規模の可視性と成熟した周辺エコシステムと引き換えに、常時接続とアカウントへの依存を求める。epiqはその対極に立ち、接続からの独立性と可搬性を得る代わりに組織規模の可視性を差し出している。

6. 系譜 - git-appraise・Fossil・git-issue、そして2010年代の実験たち

epiqを孤立した新製品として見ると多くを見逃す。同じ発想を試みた系譜はすでに長い。

6.1 git-appraise - コードレビューをgit-notesへ

Googleが公開したgit-appraiseはissueではなくコードレビューを対象とするが、思想は同じだ。レビュー要求・コメント・CI結果を別サーバーなしにgit-notes(refs/notes/devtools/*)へ記録し、リポジトリをpush/pullするだけでレビュー履歴も一緒に伝播する。epiqがissueに適用した「サーバーレスの分散保存」を、コードレビュー側で先に証明した事例と見ることができる。

6.2 Fossil - オールインワンだが狭いエコシステム

SQLiteの開発者が作った分散型バージョン管理システムFossilは、当初からチケットシステム・Wiki・フォーラムを一つのバイナリに統合していた。サーバー設定なしにfossilを一つ実行するだけでバージョン管理とissueトラッキングが同時に回るという点は、今見ても印象的だ。しかしメール通知を付けにくく、GitHub式のプルリクエスト・コードレビューの概念がチケットシステムと噛み合わないという指摘は根強い。統合はよくできているが、GitHub Issuesが提供する周辺エコシステム(通知・連携・検索)には及ばないという評価が支配的である。

6.3 git-issue - テキストファイルと双方向同期

dspinellisのgit-issueはissueを普通のテキストファイルとして保存しつつ、GitHub・GitLabと双方向でインポート・エクスポートできるようにした折衷案である。サーバーが不要で、サーバーが落ちてもissueを失わないというローカルファースト原則を守りながら、同時に必要なときに中央プラットフォームと同期する通路を開けている点がepiqとは色合いが異なる。epiqがまだこの程度の双方向同期を前面に押し出していない点は注目に値する。

6.4 ticgit・Bugs Everywhere・Ditz・SD・DisTract - 廃墟となった実験たち

2008年前後、ticgitを皮切りにBugs Everywhere、Ditz、SD、DisTractといったツールがほぼ同時に「issueをバージョン管理システムの中へ」入れようとした。この流れを振り返るある回顧記事は、このエコシステムを塹壕戦の後に残された荒れ地に例えるほど、ほとんどがメンテナを失い放置されたとまとめている。失敗の共通原因は技術ではなく、二つの社会的条件にあった。Webフォームに慣れた非開発者が参加できる入口がなかったこと、そしてチーム全体に同じツールを使わせる手段がなかったことだ。epiqのイベントソーシングとworktreeの分離は、この時代のツールが抱えていた技術的欠陥(衝突・ログ汚染)をかなり改善したが、二つの社会的条件はそのまま残っている。

7. チーム協業の限界 - 非開発者と可視性

本稿の核心的な警告はここにある。epiq流のツールが技術的にどれほど洗練されても、組織レベルの二つの壁はそのまま残る。

7.1 非開発者は端末からissueを登録しない

先の系譜で確認した結論がそのまま繰り返される。Webフォームに慣れた関係者にvimキーバインドとコマンドラインモードを求めた瞬間、その人はissueを登録しないか、別のチャネル(チャット・メール)へ迂回する。epiqはブラウザGUIも併せて提供しこの壁を下げようとするが、そのGUIもアカウントベースの中央サービスではなくローカルリポジトリを覗く窓であるため、関係者それぞれがリポジトリへアクセスできなければならないという前提そのものは変わらない。

7.2 ダッシュボード・レポーティング・エピックがない

Jiraのエピック・スプリント・バーンダウンチャート、GitHub Projectsのカンバンと自動化は、多数のissueを組織単位でまとめて報告するための仕組みだ。ローカルファーストのissueトラッカーは個別のリポジトリの中では強力だが、複数のリポジトリ・複数のチームにまたがる現状を一画面で示す中央集計機能は、設計上どうしても後回しになる。issue数の少ない小規模チームでは体感されないが、組織が大きくなるほどこの空白は早く露わになる。

8. それでも2026年に再び注目される理由 - エージェンティックコーディング

ここまでだけを見ればepiqも結局は過去の実験の焼き直しに読める。しかし筆者がこのツールを違って見ている点が一つある。

8.1 協業の相手がもはや人間だけではない

10年前の失敗の核心的な原因 - 非開発者のアクセス性の欠如 - は今もそのまま有効だ。しかし2026年には新しい変数が一つ入り込んだ。リポジトリの中で共に働く相手が人間だけでなく、Claude CodeのようなAIコーディングエージェントでもあるという点だ。エージェントはvimキーバインドを不便に感じないし、Webログインも必要としない。むしろローカルファイル・Gitオブジェクトとして露出された状態を、API呼び出しよりも安く、即座に読み書きできる。

8.2 MCPが変える計算

epiqが専用のMCPサーバーを提供し、エージェントがissueを直接扱えるようにしたのは、まさにこの点を狙った設計だ。人間の関係者のためにWeb GUIが依然として必要だという結論はそのままにしつつ、エージェントが繰り返しissueを作成し状態を更新するワークフローでは、「端末の中にある」という事実がもはや欠点ではなく、遅延のない直接アクセスという利点になる。issueトラッカーをコードリポジトリの中へ戻そうという議論がコーディングエージェントの時代に再び浮上した理由は、人間のコンテキストスイッチ問題がエージェントのツールアクセス性の問題として書き換えられたからだと筆者は解釈する。これはCode as Agent Harnessの分析で扱った、コードベース自体をエージェントの実行基盤として見る視点ともつながる。

9. 結論 - どこで使うべきか

epiqは本物のシグナルであると同時に、古い限界も一緒に受け継いだツールである。2026年7月時点での筆者の実務的な判断は次の通りだ。

9.1 よく合う場面

一人あるいは少人数の開発チーム、オフライン作業が多い環境、そしてAIコーディングエージェントにissue管理の一部を任せたいワークフローでは、epiqのようなツールがすぐに恩恵をもたらす。特にすでに端末ベースのエージェントツールを使っているなら、issueまで同じリポジトリの中に置く方が断片化を減らせる。

9.2 慎重になるべき場面

非開発者の関係者が実務に関わる組織、メール通知・レポーティング・コンプライアンス追跡が求められる組織であれば、GitHub IssuesやJiraを主力として維持する方が安全である。検証されていない配布経路(npmのグローバルインストールなど)へのセキュリティレビューも導入前に済ませるべきだ。

9.3 ハイブリッドという折衷案

git-issueが示した双方向同期モデルのように、ローカルのissueトラッカーを主として使いつつ必要なissueだけを中央プラットフォームへ書き出す折衷も可能だ。正解は一つのツールではなく、チーム構成と協業の相手(人間かエージェントか)に応じてissueの置き場所を設計し分けることにある。Gitワークフロー自体の変化に関心があればGritのGit Rust再実装分析とre_gentのAIエージェントバージョン管理分析も参考になる。
