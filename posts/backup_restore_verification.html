종료 코드 0 이 관측하는 것과 관측하지 않는 것

논리 백업, 즉 덤프는 서버에 질의를 던져 결과를 SQL 문으로 받아 적는 절차다. MySQL 8.4 문서의 분류를 그대로 옮기면 논리 백업은 서버가 돌아가는 상태에서 수행되고, 데이터베이스에 속하지 않는 로그 파일과 설정 파일은 담기지 않는다. 담기지 않은 것이 무엇인지는 덤프 파일 어디에도 기록되지 않는다.

백업 작업이 성공했다고 말할 때 실제로 관측되는 신호는 셋 정도다. 프로세스 종료 코드, 출력 파일의 크기, 전송 완료 여부. 관측되지 않는 것은 이렇다.

  • 덤프 내용이 어느 한 시점의 일관된 상태를 나타내는가
  • 스키마와 데이터가 서로 짝이 맞는가
  • 대상 환경에 그 덤프를 받을 전제 조건이 갖춰져 있는가
  • 이 파일을 여는 데 필요한 키가 다른 곳에 살아 있는가
  • 복원에 걸리는 시간이 감당 가능한 범위인가

다섯 항목의 공통점이 있다. 전부 백업 시점에는 값을 알 수 없고 복원 시점에만 값이 정해진다. 백업 파이프라인의 초록불이 이 다섯을 대신할 방법은 원리적으로 없다.

성공한 백업이 거짓말하는 여섯 자리

1. 덤프가 도는 동안 스키마가 바뀌면

MySQL 의 --single-transaction 은 InnoDB 테이블을 잠금 없이 온라인으로 뜨게 해 주는 옵션이다. 그런데 문서가 붙여 놓은 조건이 있다. 덤프가 도는 동안 다른 연결이 ALTER TABLE·CREATE TABLE·DROP TABLE·RENAME TABLE·TRUNCATE TABLE 를 쓰지 않아야 올바른 덤프 파일이 나온다는 것이다. 일관된 읽기가 그 문장들로부터 격리되지 않기 때문에, 덤프 대상 테이블에 그런 문장이 걸리면 내용을 잘못 가져오거나 실패할 수 있다.

여기서 눈여겨볼 쪽은 「실패할 수 있다」의 반대편이다. 잘못 가져오는 쪽은 실패가 아니다. 덤프는 정상 종료하고, 파일은 문법적으로 유효한 SQL 이고, 나중에 복원해도 오류가 나지 않는다. 어긋난 것은 내용뿐이다. 스키마 마이그레이션 배포 시각과 야간 백업 창이 겹치는 조직에서 이 조건은 이론이 아니다.

PostgreSQL 쪽은 사정이 다르다. pg_dump 는 동시 사용 중에도 일관된 결과를 만들고, 문서의 표현으로 그 덤프는 pg_dump 가 실행을 시작한 시점의 스냅숏을 나타낸다. 같은 위험을 같은 방식으로 겪지 않는다는 뜻이며, 두 계열을 하나의 사내 절차로 뭉뚱그리면 안 되는 이유이기도 하다.

2. 스키마만, 또는 데이터만

--schema-only 로 뜬 덤프를 복원하면 테이블이 전부 생기고 행은 0 이다. 오류는 나지 않는다. 반대로 --data-only 로 뜬 덤프는 빈 대상에 넣으면 받을 테이블이 없어 실패하고, 이미 스키마가 있는 대상에 넣으면 제약과 적재 순서에서 부분적으로 실패한다.

PostgreSQL 문서는 라지 오브젝트가 데이터로 취급된다고 명시한다. --data-only 에는 포함되고 --schema-only 에는 포함되지 않는다. 스키마 덤프와 데이터 덤프를 따로 떠서 나중에 합치는 운용에서, 두 파일의 시각이 어긋나면 그 사이에 들어온 행은 어느 쪽에도 없다. 그리고 이 누락은 복원 로그에 아무 흔적을 남기지 않는다.

3. 기본으로 담기지 않는 것들

mysqldump 에서 --triggers 는 기본으로 켜져 있어 테이블을 뜰 때 그 테이블의 트리거가 따라온다. 반면 --routines 와 --events 는 기본으로 꺼져 있고 명시해야 담긴다. 저장 프로시저·저장 함수·이벤트 스케줄러 항목이 여기 해당한다.

이 기본값이 만드는 결함의 성질이 특이하다. 복원 시점에 전혀 드러나지 않는다. 테이블은 다 있고 행수도 맞는다. 없는 것은 야간 집계 이벤트와 저장 프로시저이고, 그것들은 각자의 실행 시각이 와야 부재가 알려진다. 행수 대조를 통과하는 결함의 첫 사례가 여기서 나온다.

4. 클러스터 밖에 있는 것들

pg_dump 는 한 데이터베이스만 뜬다. 역할과 테이블스페이스처럼 클러스터 전역에 걸린 객체는 담기지 않으며, 그쪽은 pg_dumpall 의 몫이다. 역할이 없는 대상에 복원하면 소유권을 세우는 문장이 걸린다. pg_restore 는 기본적으로 ALTER OWNER 또는 SET SESSION AUTHORIZATION 을 내보내는데, 문서에 따르면 이 문장들은 최초 접속이 슈퍼유저이거나 모든 객체의 소유자가 아니면 실패한다.

확장도 성질이 같다. 덤프가 담는 것은 확장을 만들라는 지시이지 확장의 구현이 아니다. 대상 호스트에 그 패키지가 깔려 있지 않으면 그 지점에서 끊긴다. 시퀀스는 반대로 조용한 쪽이다. 값이 딸려 오기는 하지만 데이터만 따로 적재하는 운용에서는 시퀀스가 뒤처진 채 복원되고, 그 사실은 다음 삽입이 기본 키 충돌을 낼 때 처음 알려진다.

5. 인코딩과 정렬 - 데이터와 같이 옮겨지지 않는 것

덤프는 기본적으로 원본 데이터베이스의 인코딩으로 만들어진다. 옮겨 가는 것은 바이트와 그 인코딩 선언이지 대상 서버의 설정이 아니다. 그래서 대상 데이터베이스를 만들 때의 인코딩 선택은 복원의 일부이고, 이 선택은 복원 스크립트가 아니라 대상 준비 스크립트에 들어 있기 마련이다.

정렬은 훨씬 조용하다. PostgreSQL 은 콜레이션 객체를 만들 때 그 제공자의 버전을 시스템 카탈로그에 적어 두고, 그 콜레이션을 쓸 때마다 현재 버전과 대조해 어긋나면 경고를 낸다. 문서의 설명은 직설적이다. 콜레이션 정의가 바뀌면 인덱스가 깨지는 등의 문제로 이어질 수 있다. 데이터베이스가 저장된 객체의 정렬 순서를 전제로 동작하기 때문이다.

그리고 이 일은 비정상적인 경로로만 생기지 않는다. 문서가 든 정상적인 사례가 운영체제를 메이저 버전으로 올릴 때, 그리고 더 새로운 ICU 로 링크된 서버 바이너리로 pg_upgrade 할 때다. 복원 대상 호스트가 원본과 다른 배포판인 상황은 재해 복구에서 예외가 아니라 기본값에 가깝다.

함정이 하나 더 있다. 경고를 없애는 ALTER COLLATION ... REFRESH VERSION 은 카탈로그의 버전 기록만 갱신한다. 문서가 못 박아 둔 문장이 있다. 그 명령은 영향받는 모든 객체가 실제로 올바르게 다시 만들어졌는지를 검사하지 않는다. 경고를 지우는 일과 인덱스를 고치는 일은 별개이고, 순서는 REINDEX 가 먼저다.

6. 키와 매체 - 파일은 있는데 못 읽는다

암호화된 백업의 복호화 키가 백업 대상과 같은 시스템에만 있으면, 그 시스템을 잃는 사고에서 백업도 같이 잃는다. 이 결함은 백업 단계에서 절대 보이지 않는다. 암호화는 성공하기 때문이다. 보이는 시점은 복원 시도의 첫 1 분이고, 그나마 나은 축에 든다. 즉시 드러나기 때문이다.

매체 손상은 반대다. PostgreSQL 은 데이터 페이지마다 체크섬을 실어 쓸 때 갱신하고 읽을 때 검증하며, 18 부터는 이것이 기본으로 켜져 있다. 다만 보호 범위가 문서에 명시돼 있다. 데이터 페이지만 보호되고 내부 자료구조와 임시 파일은 아니다. 그리고 이것은 살아 있는 클러스터의 이야기이지, 오브젝트 스토리지에 여섯 달 놓여 있던 덤프 파일의 이야기가 아니다. 그쪽은 저장소가 제공하는 무결성 장치와 백업물 자체의 매니페스트가 맡는다.

지금까지의 항목을 한 표에 놓으면 규칙 하나가 보인다. 백업 단계에서 보이는 실패는 거의 없다. 그래서 백업 쪽 알림을 아무리 촘촘히 걸어도 이 목록은 줄지 않는다.

복원 도구의 기본값은 「계속 진행」이다

표의 마지막에서 두 번째 줄이 가장 자주 놓치는 자리다. 주요 복원 경로의 오류 처리 기본값은 멈추기가 아니라 계속하기다.

pg_restore 의 --exit-on-error 설명문이 그 기본값을 그대로 적는다. 기본은 계속 진행하고 복원이 끝날 때 오류 개수를 표시하는 것이다. 「표시한다」는 말은 사람이 화면을 볼 때 성립한다. 스케줄러가 종료 코드만 읽고 있으면 오류 40 건이 난 복원과 0 건이 난 복원이 같은 신호로 들어온다.

평문 덤프를 psql 로 적재할 때도 같다. 문서의 표현으로 기본적으로 psql 스크립트는 SQL 오류를 만난 뒤에도 실행을 계속한다. ON_ERROR_STOP 변수를 켜면 오류 발생 시 종료 코드 3 으로 빠져나온다. 그리고 문서가 뒤에 붙인 문장이 결론이다. 어느 쪽이든 부분적으로만 복원된 데이터베이스를 갖게 된다. 차이는 그 사실을 아느냐뿐이다.

복원 경로오류를 만났을 때의 기본 동작멈추게 하는 방법판정의 성질
pg_restore · 아카이브 형식계속 진행하고 끝에 오류 개수 표시오류 시 종료 옵션기본값에서는 부분 성공이 성공으로 보인다
pg_restore · 단일 트랜잭션전부 성공하거나 아무것도 반영되지 않음기본으로 오류 시 종료를 포함판정이 이진이 되어 검증에 적합하다
psql · 평문 덤프SQL 오류 뒤에도 계속 실행ON_ERROR_STOP 설정 · 종료 코드 3끄고 켬에 따라 같은 파일이 다르게 판정된다
mysql · 덤프 재적재문서에 기본값이 서술되어 있지 않음계속 진행 옵션의 존재로 역추정문장으로 확정하지 못해 아래 절에 남긴다

단일 트랜잭션 복원이 검증에 맞는 이유가 표의 둘째 줄에 있다. 전부 성공하거나 아무것도 반영되지 않으므로 판정이 이진이 된다. 검증용 복원의 목적은 데이터를 살리는 것이 아니라 참·거짓 하나를 얻는 것이다.

형식에 얽힌 함정도 하나 있다. pg_restore 는 평문 형식 덤프를 복원하지 못한다. 커스텀·디렉터리·tar 형식이어야 한다. 검증 절차를 pg_restore 기준으로 짜 두고 정작 백업은 평문으로 뜨고 있는 조합은, 검증이 한 번도 돈 적 없는 상태로 오래 지낼 수 있다.

복원 검증이 실제로 요구하는 것

격리된 대상과, 원본과 무관한 자원

「복원해 봤다」가 성립하려면 복원 대상이 원본과 분리돼 있어야 한다. 분리는 데이터베이스 이름을 다르게 쓰는 정도로는 부족하다. 같은 서버 프로세스, 같은 디스크, 같은 자격증명, 같은 네트워크 경로를 쓰고 있으면 그 검증은 원본이 살아 있다는 사실에 기대고 있다. 원본이 사라지는 상황을 대비한 절차가 원본에 의존하면 그 절차는 대비가 아니다.

PostgreSQL 문서가 복원 대상에 붙여 놓은 조건도 같은 종류다. template1 에 지역적으로 추가한 것이 있으면 진짜 빈 데이터베이스에 복원해야 하고, 그러려면 template0 에서 복사해 데이터베이스를 만들어야 한다. 대상이 깨끗하지 않으면 성공과 실패가 섞이고, 섞인 결과는 판정을 만들지 못한다.

매번 새 컨테이너를 띄워 복원하는 방식이 널리 쓰이는 이유가 여기 있다. 초기 상태가 항상 같기 때문이다. 다만 컨테이너 자체는 격리의 한 축일 뿐이다. 그 컨테이너가 원본과 같은 호스트, 같은 스토리지, 같은 클라우드 계정 위에 있으면 격리는 프로세스 수준에서 멈춘다. 자원 격리의 정도는 대비하려는 사고의 크기에 맞춰 정하는 것이 맞다.

무엇을 대조하는가

행수는 값싸고 유용하다. 다만 앞에서 본 것처럼 행수가 맞아도 통과하는 결함이 여럿이다. 저장 프로시저 누락, 이벤트 누락, 시퀀스 뒤처짐, 정렬 순서 어긋남이 전부 그렇다.

체크섬은 한 단계 위지만 조건이 붙는다. MySQL 의 CHECKSUM TABLE 은 백업이나 롤백 전후로 내용이 같은지 확인하라고 만들어진 문장이다. 그런데 문서가 붙인 단서가 둘이다. 값이 테이블 행 형식에 의존해서 형식이 바뀌면 체크섬도 바뀌고, 해시 함수가 충돌이 없다고 보장되지 않아 서로 다른 두 테이블이 같은 값을 낼 가능성이 남는다. 실제로 문서는 시간 타입의 저장 형식이 특정 버전 구간에서 바뀌어 업그레이드 시 체크섬이 달라질 수 있다는 예까지 들어 둔다.

결론은 명확하다. 버전을 올리며 복원하는 검증에서 체크섬 불일치는 손상의 증거가 아닐 수 있다. 같은 판본끼리 비교할 때만 신호가 된다. 그래서 대조는 층으로 쌓는 편이 낫다.

  • 1층 · 객체 개수 — 테이블·인덱스·시퀀스·확장·루틴·이벤트·트리거. 기본값 때문에 통째로 빠진 부류를 여기서 잡는다.
  • 2층 · 테이블별 행수 — 부분 적재와 중단된 복원을 잡는다. 값이 싸므로 매번 돌린다.
  • 3층 · 핵심 테이블의 집계값 — 합계·최댓값·최근 시각. 행수는 같은데 내용이 어긋난 경우를 여기서 잡는다.
  • 4층 · 애플리케이션이 실제로 던지는 질의 몇 개 — 조인과 정렬이 걸린 질의를 골라야 인덱스와 콜레이션 문제가 드러난다.

층을 나누는 이유는 비용이 다르기 때문이다. 1·2 층은 매 복원마다 돌릴 만큼 싸고, 4 층은 그렇지 않다. 무엇을 어디에 놓을지는 다음 절의 자동화 경계와 이어진다.

파일이 열린다는 것과 서비스가 산다는 것

이 경계를 가장 분명히 적어 둔 것은 PostgreSQL 의 백업 검증 도구 문서 자신이다. pg_verifybackup 은 pg_basebackup 으로 뜬 백업을 서버가 백업 시점에 만든 매니페스트와 대조해 무결성을 본다. 그리고 문서는 바로 이어 적는다. 이 도구가 수행하는 검증은 돌아가는 서버가 그 백업을 실제로 쓰려 할 때 수행할 모든 검사를 포함하지 않으며, 포함할 수도 없다. 이 도구를 쓰더라도 시험 복원을 수행해 결과 데이터베이스가 기대대로 동작하고 올바른 데이터를 담고 있는 것처럼 보이는지를 봐야 한다.

같은 문서가 한계를 더 좁혀 적기도 한다. 파일 누락이나 내부 체크섬 불일치 같은 명백한 문제를 잡기에는 충분하지만, 복구를 시도할 때 생길 수 있는 모든 문제를 잡을 만큼 넓지는 않다는 것이다. 예로 드는 것은 체크섬은 맞지만 말이 안 되는 동작을 지정하는 로그 레코드다. 형식은 맞는데 뜻이 틀린 경우가 검증기의 사각지대라는 이야기다.

한 발 더 나가면 시험 복원조차 마지막 층이 아니다. 데이터베이스가 뜨는 것과 서비스가 뜨는 것 사이에는 스키마 마이그레이션 버전, 애플리케이션이 기대하는 확장, 접속 계정의 권한, 외부 저장소에 있는 첨부 파일, 캐시에만 있던 세션 같은 것들이 놓여 있다. 이 층을 한 번도 통과해 본 적 없는 복구 계획은 실제 사고에서 그 층에 도달한 다음에야 새 문제를 만난다. 복구 가능성이 사후 노력이 아니라 설계의 산물이라는 이야기는 기기 펌웨어 쪽에서 먼저 정리한 적이 있는데, 데이터베이스라고 다르지 않다.

목표를 숫자로 세운다 - RPO 와 RTO

두 값이 없으면 백업 설계는 시작할 수 없다. 어떤 주기가 충분한지, 어떤 복원 속도가 필요한지를 판단할 기준이 없기 때문이다. 정의는 NIST SP 800-34 Rev. 1 의 것이 가장 널리 인용된다.

용어정의정하는 것정해지지 않으면
RPO · 복구 시점 목표장애 이후 데이터가 복구되어야 하는 시점백업 주기와 쓰기 로그 보관 방식주기 논쟁이 기술 취향 싸움으로 끝난다
RTO · 복구 시간 목표시스템 구성 요소가 임무나 업무 프로세스에 부정적 영향을 주기 전까지 복구 단계에 머물 수 있는 전체 시간백업의 형식과 복원 경로의 구조복원이 며칠 걸려도 규격 위반이 아니게 된다

RPO 가 24 시간이면 야간 덤프로 족하다. RPO 가 5 분이면 덤프로는 닿지 않고 쓰기 로그를 계속 흘려보내는 구성이 필요하다. PostgreSQL 쪽에서는 WAL, MySQL 쪽에서는 바이너리 로그다. MySQL 8.4 는 바이너리 로깅이 기본으로 켜져 있고, 시점 복구의 재료는 전체 백업 이후에 생성된 바이너리 로그 파일들이다. 백업이 끝나면 로그를 정리해 디스크를 비우는 습관이 있으면 RPO 는 서류상의 값으로만 남는다. 바이너리 로그를 되감기 가능한 이력으로 쓰는 발상은 되돌리기 가능한 데이터 타임머신을 다룬 글에서 따로 정리한 적이 있다.

RTO 가 정하는 것은 백업의 형식이다. 여기서 논리 백업의 대가가 드러난다. MySQL 문서는 mysqldump 에 대해 상당한 양의 데이터를 백업하기 위한 빠르거나 확장성 있는 해법으로 의도된 것이 아니다라고 스스로 적고, 데이터가 크면 복원이 매우 느릴 수 있다고 덧붙인다. 이유도 함께 적혀 있다. SQL 문을 재생하는 일에 삽입과 인덱스 생성을 위한 디스크 입출력이 따라붙기 때문이다.

여기서 자주 하는 착오가 있다. 덤프 파일 크기로 RTO 를 추정하면 거의 항상 낙관적으로 틀린다. 덤프를 뜨는 시간과 되돌리는 시간은 비대칭이고, 그 비대칭의 크기는 인덱스 구성에 좌우된다. 복원 시간은 추정이 아니라 측정으로만 알 수 있다.

마지막으로 이 둘이 정해지지 않으면 무슨 일이 벌어지는지가 중요하다. 「백업 주기를 몇 시간으로 할까」는 결론이 나지 않는 기술 논쟁이다. 「이 서비스가 몇 분 치 주문을 잃어도 되는가」로 옮기면 답을 낼 사람이 정해진다. 두 값은 기술 파라미터가 아니라 업무가 감수하기로 한 손실의 크기이고, 그래서 인프라 담당자가 혼자 정할 수 있는 종류의 숫자가 아니다. 이 성격은 작은 팀이 Postgres 를 지키는 방식을 다룰 때도 같은 자리에서 나온다.

3-2-1 은 표준인가 관행인가

3-2-1 은 자주 규칙이나 표준으로 불린다. 사본 3 개, 매체 2 종, 오프사이트 1 개라는 구성이다. 출처를 따라가면 표준 문서가 아니라 사진가 피터 크로그의 저서 『The DAM Book』(오라일리)에서 정리된 경험칙으로 이어진다. 널리 인용되고 대체로 타당하지만, 표준화 기구가 요구 사항으로 발행한 조항은 아니다. 규칙보다 관행으로 부르는 편이 정확하다.

표준 쪽에서 실제로 요구하는 문장은 모양이 다르다. NIST 사이버보안 프레임워크 2.0 의 PR.DS-11 은 「데이터의 백업이 생성·보호·유지·시험된다」이다. 딸린 구현 예시에는 이런 항목들이 있다.

  • 중요한 데이터는 준실시간으로 지속 백업하고, 그 밖의 데이터는 합의된 일정으로 자주 백업한다
  • 모든 종류의 데이터 원본에 대해 최소 연 1 회 백업과 복원을 시험한다
  • 일부 백업은 오프라인·오프사이트에 안전하게 보관해 사고나 재해가 그것을 훼손하지 않게 한다
  • 백업 저장소에 지리적 분리와 위치 제한을 적용한다

읽어 보면 사본의 개수보다 시험과 격리가 앞에 있다. 3-2-1 을 완벽히 지키면서 한 번도 복원해 보지 않은 조직과, 사본이 둘뿐이지만 분기마다 복원 훈련을 하는 조직 중 어느 쪽이 실제 사고에서 살아남을지는 자명하다. 개수는 세기 쉬워서 감사에서 먼저 세어지고, 시험은 세기 어려워서 나중으로 밀린다. 그 순서가 뒤집혀 있다.

덧붙이자면 오프사이트라는 항목의 뜻도 자주 좁게 읽힌다. 물리적 거리만이 아니라 신뢰 경계가 다른가가 핵심이다. 같은 클라우드 계정의 다른 리전은 지리적으로 떨어져 있지만 자격증명 하나가 둘을 함께 지운다. 보관을 남에게 맡길 때 접근권 자체를 잃지 않는 문제는 아카이브 접근권과 벤더 락인 쪽에서 계약 관점으로 정리한 적이 있다.

자동화의 경계 - 매번 할 것과 가끔 할 것

복원 검증에서 자동화할 수 있는 것과 없는 것을 가르는 기준은 하나다. 기준값이 어디에 있는가.

기계 쪽 항목의 공통점은 기준값이 데이터 안에 있다는 것이다. 사람의 판단 없이 참과 거짓이 갈리고, 갈린 결과를 알림으로 바꿀 수 있다. 사람 쪽 항목의 공통점은 기준값이 조직 안에 있다는 것이다. 복구 훈련의 소요가 40 분이라는 사실 자체는 참도 거짓도 아니다. 그것이 RTO 안에 드는지를 업무가 판정해야 의미가 생긴다.

경계에 놓인 항목이 표의 다섯째 줄이다. 복원 소요 시간의 추세는 기계가 재지만, 그 추세가 언제 위험해지는지는 사람이 정한다. 데이터가 커지면 복원 시간은 반드시 늘고, 늘어난 시간이 RTO 를 넘는 날은 아무 알림 없이 온다. 복원 소요를 매번 기록해 두는 일이 값싼 이유가 이것이고, 기록만 쌓고 아무도 안 보는 상태가 되기 쉬운 이유이기도 하다. 모아 두었으나 읽히지 않는 데이터의 문제는 관측 데이터가 왜 안 읽히는가에서 다룬 것과 같은 모양이다.

기계가 대신할 수 없는 것을 억지로 자동화하려는 시도도 흔하다. 검증기가 판정할 수 있는 범위와 없는 범위를 가르는 일반적인 기준은 검증 하네스가 그은 경계선 쪽에 정리해 두었다. 요지는 같다. 기계는 하한을 지킨다. 상한은 사람이 정한다.

셀프 호스팅의 대가 - 그 도구의 백업은 누가 하는가

백업 도구를 직접 띄우면 질문이 하나 늘어난다. 그 도구의 상태는 누가 백업하는가.

백업 도구는 스케줄, 접속 정보, 보존 정책, 저장소 자격증명, 암호화 키, 그리고 실행 이력을 들고 있다. 이 상태를 잃으면 백업 파일이 전부 남아 있어도 복구 절차의 절반이 사라진다. 어떤 파일이 어느 시점의 어느 데이터베이스인지, 어떤 키로 열리는지가 그 도구 안에만 있었다면 더 그렇다.

순환 의존은 여기서 생긴다. 도구가 자기 상태를 자기 저장소에 백업하고, 그 저장소 자격증명이 도구 안에만 있으면 원을 그리는 셈이다. 사고에서 이 원은 한 점만 끊겨도 전체가 멈춘다. 끊는 방법은 특별하지 않다.

  • 도구의 설정을 도구 바깥에 사람이 읽을 수 있는 형식으로 내보내 형상 관리에 둔다. 코드로 관리되면 도구를 새로 세워도 같은 상태가 재현된다.
  • 복호화 키는 백업물과 다른 신뢰 경계에 둔다. 같은 저장소, 같은 계정, 같은 컨테이너 안에 있으면 하나의 사고가 둘을 함께 가져간다.
  • 도구가 없는 상태에서 백업 파일 하나를 여는 절차를 문서로 남기고, 그 절차를 한 번 밟아 본다. 웹 화면 없이 복원할 수 있어야 도구가 단일 실패 지점이 아니게 된다.
  • 백업 목록을 도구 바깥에서도 읽을 수 있게 한다. 저장소 쪽의 파일 이름 규칙과 매니페스트가 그 역할을 한다.

이 대가는 셀프 호스팅을 하지 말라는 근거가 아니다. 관리형 서비스를 쓴다고 질문이 사라지지 않고 공급자에게 옮겨질 뿐이며, 대신 계약과 접근권이라는 다른 층의 질문이 생긴다. 어느 쪽이든 원을 끊는 지점을 자기가 알고 있어야 한다. 배포 플랫폼을 자기 서버에 올릴 때 없어지는 비용과 새로 생기는 비용의 구조는 셀프호스팅 배포 플랫폼을 다룬 글에서 같은 방식으로 갈라 두었다.

읽기만으로 확인해 볼 수 있는 것

아래는 전부 읽기·검사 계열이다. 대상을 바꾸거나 지우는 명령은 넣지 않았다. 호스트·계정·스키마 이름은 자리표시자이므로 각자의 값으로 바꿔 넣으면 된다.

백업물을 복원하지 않고 목차만 본다

# 아카이브 목차. 복원하지 않고 무엇이 들어 있는지만 나열한다.
pg_restore --list /PATH/TO/backup.dump

# 물리 백업을 서버가 만든 매니페스트와 대조한다.
pg_verifybackup /PATH/TO/basebackup

# 페이지 체크섬이 켜져 있는지만 조회한다.
psql -h HOST -U USER -d DBNAME -c 'SHOW data_checksums'

복원본에 무엇이 왔는지 센다

-- 스키마별 테이블 수. 통째로 빠진 부류를 먼저 잡는다.
SELECT table_schema, count(*) AS tables
  FROM information_schema.tables
 WHERE table_schema NOT IN ('pg_catalog', 'information_schema')
 GROUP BY 1 ORDER BY 1;

-- 확장은 만들라는 지시만 덤프에 담긴다. 대상 호스트에 실제로 섰는지 본다.
SELECT extname, extversion FROM pg_extension ORDER BY 1;

-- 시퀀스가 뒤처진 채 복원되면 다음 삽입에서 기본 키 충돌이 난다.
SELECT schemaname, sequencename, last_value
  FROM pg_sequences ORDER BY 1, 2;

정렬 버전이 어긋난 객체를 찾는다

-- PostgreSQL 문서에 실린 질의. 비교 연산자만 != 로 적었다.
SELECT pg_describe_object(refclassid, refobjid, refobjsubid) AS collation_name,
       pg_describe_object(classid, objid, objsubid)          AS object_name
  FROM pg_depend d
  JOIN pg_collation c
    ON refclassid = 'pg_collation'::regclass AND refobjid = c.oid
 WHERE c.collversion != pg_collation_actual_version(c.oid)
 ORDER BY 1, 2;

MySQL 쪽에서 기본값 때문에 빠진 것을 센다

-- 트리거는 기본으로 담기지만 루틴과 이벤트는 아니다. 원본과 복원본에서 각각 센다.
SELECT routine_type, count(*) AS n
  FROM information_schema.routines
 WHERE routine_schema = 'APPDB' GROUP BY routine_type;

SELECT count(*) AS events   FROM information_schema.events
 WHERE event_schema   = 'APPDB';
SELECT count(*) AS triggers FROM information_schema.triggers
 WHERE trigger_schema = 'APPDB';

-- 내용 지문. 값이 행 형식과 판본에 의존하므로 같은 판본끼리만 비교한다.
CHECKSUM TABLE APPDB.ORDERS;

마지막 문장은 읽기 계열이지만 공짜는 아니다. 큰 테이블에서는 전체를 훑으므로 운영 시간대에 원본을 상대로 돌릴 성질의 것이 아니다. 복원본을 상대로 돌리는 것이 맞고, 그래서 격리된 대상이 앞 절의 조건으로 먼저 나왔다.

확인하지 못한 것

  • 계기가 된 도구의 복원 검증이 크기와 테이블별 행수 외에 무엇을 더 대조하는지는 README 서술 범위를 넘어 확인하지 못했다. 제약·인덱스·루틴의 존재까지 보는지, 애플리케이션 계층 점검을 붙일 수 있는지는 여기서 단정하지 않는다.
  • 같은 저장소의 GitHub 설명문은 PostgreSQL 도구라고만 적고 README 는 네 계열을 적는다. 어느 쪽이 최신 의도인지는 확인하지 못했다.
  • mysql 클라이언트가 스크립트를 읽다가 SQL 오류를 만났을 때의 기본 동작은 확정하지 못했다. 옵션 문서에 계속 진행 옵션이 「SQL 오류가 나도 계속한다」로만 적혀 있고 기본값은 명시적으로 서술돼 있지 않다. 반대로 추론할 수는 있으나 문서 문장으로 확정하지 못했다.
  • 3-2-1 을 요구 사항으로 발행한 표준·정부 문서는 찾지 못했다. 널리 인용되는 출처는 저서이고, NIST CSF 2.0 의 PR.DS-11 은 사본 수가 아니라 생성·보호·유지·시험을 요구한다.
  • MariaDB 와 MongoDB 계열의 덤프 기본값은 이 글의 근거에 포함하지 않았다. PostgreSQL 18 과 MySQL 8.4 의 공식 문서만 사용했다.
  • 복원 소요 시간의 일반적인 수치는 제시하지 못한다. 데이터 크기·하드웨어·인덱스 구성에 좌우되므로 RTO 판단은 각자 환경의 실측으로만 가능하다.
