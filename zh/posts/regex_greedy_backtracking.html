正则表达式停不下来 - 贪婪匹配与回溯爆炸

实测输入每多一个字符时间就翻一倍的结构，再用四种办法把它切断

2026-09-01 开发/基础设施

正则给出错误结果时很快就能发现，测试会变红，日志里会留下被截错的值。麻烦的是正则根本不给出结果的情况。既没有异常，也没有错误信息，进程就停在那一行。CPU 一个核占满100%，抓一份栈回溯，指向的是 String.prototype.match 里的某处。

面对这种情况最常见的误判是认为输入太大了。下面要测的例子，输入是31个字节，处理它花了7.8秒。原因不在数据的大小，而在模式的形状。这篇文章要弄清楚那个形状是什么，为什么它会呈指数膨胀，以及怎么切断它，每一条都实际掐着表验证。

本文中的数字，都是在下面「测量环境」所写的那一台机器上实际运行得到的。CPU、运行时版本、其他进程的负载不同，绝对值可以差出很多。要看的不是毫秒的位数，而是输入稍微变长时，时间以什么比例增长。只有这个比例，换一台机器也会呈现同样的形状。

回溯这个结构

大多数编程语言使用的正则引擎是回溯式的。它的动作和名字一致，从左往右读模式并往字符串上套，某处卡住了就退回到最近一个还有选择余地的位置，换一个选择再试。就像在迷宫里每个岔路都做个记号，碰到死路就退回最后一个记号。

这种方式明明可能很慢却仍被广泛使用，是有原因的。有些功能只有在能够退回时才成立。

  • 反向引用 — 像 (\w+)\s+\1 这样要求「和前面捕获到的东西相同」的语法。必须能记住前面那个组捕获了什么并重新尝试，才谈得上成立
  • 环视断言 — (?=...)、(?<=...) 这类位置检查。需要在某一点试着匹配另一个模式，然后回到原来的位置
  • 贪婪量词的回吐 — .* 先吃到底，后面对不上就一个字符一个字符往回吐，这个动作本身就是回退
  • 分支的优先顺序 — (a|ab) 先试左边、失败再走右边这条规则，同样架在回退之上

这些功能超出了形式语言理论所说的正则语言的范围。所以单纯把状态机走一遍是处理不了的，必须搜索。搜索总有最坏情况，而这个最坏情况通常比人们以为的近得多。

复现这场灾难 - 一个字符翻一倍

教科书式的例子是 ^(a+)+$。往里放 n 个 a，末尾再加一个 b。b 永远匹配不上，所以引擎必须把所有可能的分支都试完之后才能宣告失败。测量的代码是这样的。

const CAP_MS = 4000;   // 单次超过4秒就中断

for (let n = 10; n <= 34; n++) {
  const s = 'a'.repeat(n) + 'b';
  const re = new RegExp('^(a+)+$');
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  console.log(n, ms.toFixed(3));
  if (ms > CAP_MS) break;
}

比例那一列全部聚在2附近，这就是指数增长的指纹。一个字符让时间翻倍，也就意味着十个字符是一千倍。把这张表直接延长下去，40个字符是几小时的量级，50个字符是几个月的量级。所以人才会觉得「卡死了」。它其实没有停下，只是结束的时刻跑到了人的时间感之外。

值得注意的是这个区间非常窄。到20个字符为止是6毫秒，任何测试都能顺利通过。25个字符是0.1秒，29个字符是2秒，31个字符是7.8秒。开发时用的短样本永远碰不到，生产环境里稍长一点的值进来，一次就跨过去了。

为什么会爆炸 - 切分方式的数量

这个病的名字叫歧义。在 (a+)+ 里，内层的 a+ 吃掉一个以上的 a，外层的 + 把它重复一次以上。于是把 aaaa 这四个字符套进这个模式的方式就不止一种，有4、3+1、1+3、2+2、2+1+1、1+2+1、1+1+2、1+1+1+1，共八种。一般来说把 n 个字符这样切开的方式有2n-1 种。

匹配成功时，引擎会停在第一个找到的方式上。可是末尾有个 b 让 $ 失败之后，引擎就会判断「换一种切法说不定能成」，于是全部试一遍。切法有 2n-1 种，尝试也就有那么多次。同一段字符串可以用多种方式切分，而且这些结果全都失败，这两个条件重叠的地方就是爆炸点。

验证这个诊断是否正确的办法，是去测量患有同一种病的其他形状。它们外表完全不同，但「切法不止一种」这个性质是一样的。

模式n=20n=24n=28n=29
^(a+)+$6.480 ms109.264 ms2233.649 ms3995.791 ms
^(a|a)*$13.354 ms191.011 ms3368.902 ms6640.935 ms
^(a*)*$12.359 ms242.906 ms3675.270 ms7156.893 ms

三者画出同一条曲线。(a|a)* 的两个分支咬住的是完全相同的东西，选哪一边结果都一样，重复 n 次就产生 2n 条路径，而且全都以同样的方式失败。(a*)* 的内层还能吃掉空字符串，切分的种数进一步增加。语法不同，病却是同一个。

  • 量词里面套着量词，而且内层是可变长度的 — (a+)+、(\w+\s?)*、([a-z]*)+
  • 分支可以咬住同一个字符 — (a|a)*、(\d|\w)*、(x|xy)*
  • 重复里含有能匹配空字符串的元素 — (a*)*、(\s?)*
  • 三种情况的条件可以归结为一句话，只要同一段输入对应到模式上的方式有两种以上，一旦失败就会把它们全部检查一遍

只在失败时才会炸

这个性质在诊断时是决定性的。同一个模式、同样大小的输入，只要匹配成功就什么都不会发生，因为引擎在第一次成功时立刻停下。在同一个 n=26 上把三种情况并排测了一遍。

输入 "a"×26 + "b"   模式 ^(a+)+$    447.897 ms   （失败）
输入 "a"×26 + "b"   模式 ^(a+)+     0.0005 ms    （立刻成功）
输入 "a"×26        模式 ^(a+)+$    0.0002 ms    （立刻成功）

第三行尤其重要。模式还是那个出问题的模式，只是少了一个 b，就变成0.0002毫秒。超过一百万倍的差距，来自输入的最后一个字符。第二行去掉了 $，一旦不再要求匹配到结尾，前面就直接成功并结束。

由此得出一个实务上的结论。只喂有效值的测试永远抓不到这类缺陷。写正则测试时只填成功用例是很常见的习惯，而这一类缺陷恰好藏在那个盲区里。而且生产环境里进来的值，往往是无效的那一侧更加五花八门。

同样的道理，锚点的有无也会改变耗时。没有起始锚点 ^ 时，引擎在第一个字符失败后会从第二个字符重新开始，再从第三个字符重新开始。n=24 时 ^(a+)+$ 是116.532毫秒，而 (a+)+$ 是295.768毫秒，差2.5倍。加锚点消不掉指数，但能消掉前面那个系数。

贪婪、懒惰与占有

量词有三种性格。三者的区别不在于「吃多少」，而在于「吃进去的会不会还回来」。

写法名称行为JS（V8）Python 3.13Perl 5.38
* +贪婪尽量多吃，后面卡住就一个字符一个字符还回去支持支持支持
*? +?懒惰尽量少吃，后面卡住就一个字符一个字符多吃支持支持支持
*+ ++占有尽量多吃，而且绝不还回去不支持支持支持
(?>...)原子组一旦离开这个组，组内的选择就不再回头查看不支持支持支持

先把常见的误解理清楚。改成懒惰量词就会变快这句话只对了一半。懒惰并没有丢掉回退的性质，只是把回退的方向翻了过来。在20万字符的字符串里，目标位于何处会让结果完全分成两边。

模式目标在字符串前部目标在字符串尾部
<h2>(.*)</h2>0.2658 ms0.0350 ms
<h2>(.*?)</h2>0.0003 ms0.0357 ms
<h2>([^<]*)</h2>0.0003 ms0.0356 ms

目标在前面时，懒惰快了将近900倍，因为贪婪要先把20万个字符吃到底再从那里往回退。可是目标在后面时，三个模式基本上是一样的，因为这回轮到懒惰从前面一个字符一个字符地伸展，尝试20万次。懒惰不是性能对策，而是语义上的选择。想要最短匹配时才用它，速度则跟着数据的形状走。

真正的对策是占有量词和原子组。这两者明确地告诉引擎「在这里放弃回退」。a++ 会尽量多吃 a，即使后面失败也不吐回来。没有可吐的选项就不会产生分支，没有分支就没有指数。这是在 Python 3.13.3 和 Perl 5.38.2 上确认的数值。

Python 3.13.3
  ^(a+)+$    n=26        3323.962 ms
  ^(a++)+$   n=100000    0.0398 ms
  ^(?>a+)+$  n=100000    0.0395 ms

Perl 5.38.2
  ^(a++)+$   n=100000    0.0091 ms
  ^(?>a+)+$  n=100000    0.0091 ms

输入大了大约3800倍，时间却只有0.04毫秒。不过有一点要注意，占有量词会改变语义。用在 "[^"]*+" 这种本来就不需要回退的位置是安全的，但直接扣到后面依赖回吐的模式上，会让本来能匹配的东西匹配不上。它应当被当作语义声明，而不是性能开关。

在 JavaScript 里切断回退

JavaScript 没有这套工具。在 Node.js v22.16.0（V8 12.4.254.21-node.26）上，三种写法在编译阶段就被拒绝。

> new RegExp('^(?>a+)+$')
SyntaxError: Invalid regular expression: /^(?>a+)+$/: Invalid group

> new RegExp('^a*+$')
SyntaxError: Invalid regular expression: /^a*+$/: Nothing to repeat

> new RegExp('^a++$')
SyntaxError: Invalid regular expression: /^a++$/: Nothing to repeat

Nothing to repeat 这条消息把情况说得很清楚。V8 不会把 a++ 读成「占有量词」，而是读成「把 + 用 + 再重复一次」这样的语法错误。占有这个概念本身就不存在。

替代方案是一个惯用写法，把分组放进先行断言里，再用反向引用去引它。把 (?>X) 改写成 (?=(X))\1。先行断言在内部一旦确定就不会从外面还回来，所以用反向引用把那个结果原样消费掉，效果就等同于原子组。

// 把 ^(a+)+$ 原子化
const naive  = /^(a+)+$/;
const atomic = /^(?=(a+))\1+$/;

// "a"×26 + "b"
naive.test(s)    →  528.117 ms
atomic.test(s)   →  0.0005 ms

// 同一个 atomic 模式用在大得多的输入上
n=1000     0.0009 ms
n=10000    0.0077 ms
n=100000   0.0771 ms

输入每大100倍，时间大约只大10倍，也就是接近线性。这个写法可读性差是明摆着的缺点，所以要用就一定要留下注释说明为什么这么写。否则以后有人判断它是「多余的先行断言」而顺手清理掉，缺陷就原样回来了。

不到指数也一样慢

指数爆炸很有戏剧性，但并不常见。实际工作中遇到得多得多的是多项式回溯，典型形式就是把 .* 用上好几次，中间用分隔符隔开。日志解析和 CSV 处理里几乎每次都会出现。

给 ^"(.*)" "(.*)" "(.*)"$ 这样的模式喂一行含有多个引号包裹字段的文本，末尾多加一个字符让匹配失败。三个 .* 要做的工作量，正比于选择分隔符位置的组合数。

字段数行长度"(.*)""([^"]*)"
1050 字符0.003 ms0.0001 ms
20110 字符0.024 ms0.0001 ms
40230 字符0.208 ms0.0001 ms
80470 字符1.774 ms0.0001 ms
1601010 字符15.522 ms0.0001 ms

长度增加20倍，时间增加了5000倍。每翻一倍大约是8倍，也就是大致三次方。它不像指数那样一击致命，但要解释「日志行变长之后整个解析器变慢」这件事，这一类才是常见得多的元凶。而右边那一列已经把答案摆在那里了，把 .* 换成 [^"]*，各种规模都会变平。

原因很简单。[^"]* 碰到引号一定会停，停的位置定死成一个，组合就不会产生。.* 连引号也能吃，所以引擎必须去试到底在哪里停。把分隔符从字符类里排除掉，是这一类问题里最便宜的修法。

工作中真正会出现的形状

危险的模式通常并不长得「像是危险的」。没有人会特意写 (a+)+，代码里实际存在的是下面这些形状。

形状实际看到的样子藏在里面的东西
嵌套量词^(\w+\s?)*$ — 检查是不是由空格连接的单词组成的一行\s? 是可选的，\w+ 之间可以直接相连，切分方式就变成了多种
重叠的分支(\d|\w)+ — 数字或字母的重复\d 包含在 \w 里，每一个数字都造出两条路径
点星号连用^(.*) (.*) \[(.*)\] "(.*)"$ — 一行访问日志分隔符位置的组合。字段越长，就以多项式的速度增加
松散的邮箱校验^([\w.-]+)+@([\w-]+\.)+[a-z]{2,}$前半部分和 (X+)+ 是同一个形状，域名一侧也是重复里套着重复
空白整理^(\s*)+$ 或 (\s|\t)*$能吃空字符串的元素在重复。制表符和空格混在一起时就会分岔

第一行实际测了一下。给 ^(\w+\s?)*$ 放 n 个字母，末尾加一个 !。即使字符串里一个空格都没有，\s? 也能吃掉空，足以让切分分岔。

n=20    8.445 ms
n=24    227.832 ms
n=26    697.181 ms
n=28    2268.459 ms
n=29    4564.045 ms   ← 在这里中断

这个模式常见于检查「用户名是否只由单词和空格构成」的输入校验里。而这种校验按定义就位于直接接收用户输入的位置。

ReDoS - 停机性变成可用性问题的地方

到这里为止说的都是性能。用户输入触达这类模式的那一刻，性质就变了。正则表达式拒绝服务（ReDoS）指的是一条很短的输入长时间占住处理线程，把整个服务拖停的情形。既不需要特殊权限，也不需要大流量，这正是这个问题的性质所在。

在单线程事件循环上运行的运行时里，波及面尤其大。一个请求在匹配上花掉7秒，那7秒里同一进程中其他所有请求都在等。健康检查没有响应，实例被替换，替换后的那个再收到同样的请求，就原样重复一遍。

本文不涉及如何构造危险输入。需要的是自己找出哪里有什么形状并把它堵上。

  • 先截断输入长度。在正则拿到数据之前放一句 if (s.length > 200) return false;，最坏情况就被约束成常数。在指数曲线上，上限差几个字符影响非常大
  • 从模式里消掉那个形状。这才是根本性的修改。拆开嵌套量词，让分支不再重叠，把分隔符从字符类里拿掉
  • 在边界上加时间上限。把处理用户输入的匹配挪到单独的工作进程或者带截止时间的路径上。JS 标准正则本身没有超时机制
  • 不要把模式当作数据接收。用用户输入的字符串去构造 new RegExp() 的地方，模式本身就跑到控制之外了，上面所有的检查在这种情况下都没有用
  • 依赖里的模式同样算数。就算自己的代码里没有，只要解析库或校验库里有，结果是一样的

第一条的效果实测了一下。这是同一个脆弱模式在不同上限下的最坏值。

maxLength=16   最坏 0.195 ms
maxLength=20   最坏 3.131 ms
maxLength=24   最坏 51.605 ms
maxLength=28   最坏 849.141 ms

仅仅把上限从28降到16，就少了大约4000倍。不过这是缓解而不是修复。长度上限在以后需求变化时会悄悄往上抬，那时缺陷就会复活。修改模式本身永远是更优先的事。

引擎各不相同

这里出现了一个意料之外的结果。同一个 ^(a+)+$ 在 Perl 5.38.2 上跑，并没有爆炸。n=20 是0.017毫秒，n=34 是0.018毫秒，一路平坦。^(a*)*$ 和 ^(\w+\s?)*$ 也是一样。看起来 Perl 的引擎会记住已经失败过的（位置，模式节点）组合，不再重复同样的工作。

但这并不意味着 Perl 就安全。在同一个 Perl 上，上一节那个多项式模式 ^"(.*)" "(.*)" "(.*)"$ 照样变慢，10个字段时0.011毫秒，80个字段时6.199毫秒，320个字段时是323.276毫秒。也就是说，有些形状能被这项优化接住，有些形状接不住。

另一端是基于自动机的引擎。它不回退，而是同时持有所有可能的状态，把输入只扫一遍。用 GNU grep 3.0 测了同样的模式。

仅 grep 进程启动（1字节的文件）        0.046 ～ 0.052 s

grep -E '^(a+)+$'
  n=20         0.049 s
  n=100        0.053 s
  n=10000      0.050 s
  n=100000     0.059 s
  n=1000000    0.058 s
  n=5000000    0.104 s

启动时间是0.05秒，低于这个数就测不出来。有意义的是最后一行，500万个字符，实际匹配工作大约0.05秒就结束了。正是那个让 Node 在31个字符上花掉7.8秒的模式。曲线本身就不是同一条。

这是有交换代价的。Go 的 regexp 包文档明确写着「本包提供的实现保证在与输入规模成线性的时间内运行（这是大多数开源正则实现并不保证的性质）」。代价是 RE2 的语法文档把反向引用 \1 和环视断言 (?=re)、(?!re)、(?<=re)、(?<!re) 全部标注为不支持。

引擎与版本方式^(a+)+$ 观测占有与原子组备注
Node.js v22.16.0（V8 12.4）回溯31 字符 7798 ms不支持用先行断言加反向引用模拟

这里有一处微妙的对称。上一节里救了 JavaScript 的那个写法 (?=(a+))\1，同时用到了先行断言和反向引用。也就是说，拯救回溯引擎的那件工具，在本来就不会爆炸的自动机引擎里根本不可能存在。线性时间的保证和表达能力，是同一根轴的两端。

修法 - 把前后并排测量

修法有四种，上面已经一个一个出现过了。这里把前后放进同一张表。顺序是越靠上越根本。

拆开嵌套量词

这是最可靠的修改。像 (\w+\s?)* 这样「重复里含有可选元素」的时候，就把那个可选元素挪到重复外面，让切分方式定死成一种。改写成 ^\w+(\s\w+)*$ 之后，必须有空格才能开始下一次重复，切分方式就只剩一种。

收窄字符类

把用作分隔符的字符从字符类里去掉。"(.*)" → "([^"]*)"，(.*) → (\S+) 。停的位置定死成一个，组合就消失了。语义通常也会变得更准确。

让它放弃回退

如果是 Python、Perl 或 PCRE 系，就用占有量词或原子组。如果是 JavaScript，就用先行断言的惯用写法。这一类是保留形状、只压住症状，所以是上面两种办法用不了时的选项。

不用正则

如果只是按分隔符切开，字符串函数更快也更好读。这是把一行602个字符的三字段文本拆解20万次的结果。

修改修改前修改后
^(\w+\s?)*$ → ^\w+(\s\w+)*$n=28 时 2268.459 msn=30 时 0.0003 ms / n=100000 时 0.2574 ms

测量自己模式的最小脚本

靠肉眼判断一个模式，比想象中难。相反，一边加长输入一边计时就不需要用眼睛判断了。线性时比例会停在1附近，指数时比例会一直保持在2附近。

// redos-probe.js
// 用法: node redos-probe.js "<模式>" [重复单元] [尾部]
const [, , src, unit = 'a', tail = 'b'] = process.argv;
const BUDGET_MS = 2000;
const re = new RegExp(src);
let prev = 0;

console.log('n\tms\t相对上一行');
for (let n = 2; n <= 200000; n = n < 40 ? n + 2 : Math.ceil(n * 1.6)) {
  const s = unit.repeat(n) + tail;
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  const ratio = prev > 0.05 ? (ms / prev).toFixed(2) : '-';
  console.log(n + '\t' + ms.toFixed(3) + '\t' + ratio);
  if (ms > BUDGET_MS) {
    console.log('\n判定: 超线性。n=' + n + ' 时 ' + ms.toFixed(0) + ' ms');
    process.exit(2);
  }
  prev = ms;
}
console.log('\n判定: 到 n=200000 为止没有超过 ' + BUDGET_MS + ' ms');

关键在 BUDGET_MS。单次一旦超过这个值就立刻中断。指数曲线上下一档就是两倍，不设上限地跑下去，等于自己把自己的机器卡死。tail 的值必须是会让匹配失败的字符。用能成功的输入什么都显现不出来，这正是前面看到的结果。

两份输出的差别本身就是诊断。上面那份里 n 每加2，时间就变成4倍。下面那份里 n 变成1.6倍，时间也变成1.6倍。要看的不是第二列，而是第三列。绝对时间因机器而异，比例才是模式的性质。

什么时候不该用正则

到这里说的是怎么修，最后是一开始就不该用它的地方。正则能表达的，是除去嵌套深度不确定的结构之后剩下的部分。越过这条边界，模式就会变长，而变长的模式会把上面看到的那些形状一并带进来。

  • HTML 与 XML — 标签可以互相包裹，深度没有限制。正则无法把开标签和闭标签配成对。应当用解析器
  • JSON 与 YAML — 同样的道理。对象里套对象是递归结构，而标准库里早就有解析器
  • 括号配对 — 这是被形式化证明位于正则语言范围之外的典型例子。一边计数一边扫过去的代码才是正解
  • 邮箱地址校验 — 严格遵循规范的正则又长，而且通常含有危险的形状。只看形式即可，大致是有一个 @ 且前后不为空，真正的校验交给确认邮件
  • URL 解析 — 每种语言都有 URL 类或与之等价的东西。自己写的模式在边缘情形上必定会出错
  • 按固定分隔符切开 — 用 split 或 indexOf 就能办到的事改用正则，既慢又难读
  • 查找固定字符串 — 用 includes 或 grep -F。没有理由把本来不是模式的东西塞进模式引擎

正则适用的领域依然很广。在扁平的、长度有限的、结构不递归的文本上，没有哪种工具能像正则这样简短地写出意图。问题在于离开那个领域之后还继续用它。

同一个正则在不同工具里语法不同这个问题，放在正则方言兼容性里说；先行断言的实战用法在先行断言的实务运用里；处理韩文时的音节陷阱在韩文正则的音节陷阱里另行讨论。在 shell 里把通配符和正则搞混的问题，则在shell 通配符与正则的区别里。

未能确认的部分

  • Perl 5.38.2 在 ^(a+)+$ 上没有爆炸的确切机制未能确认。看起来是一种记住失败组合的优化，但这台机器上的 perldoc 无法运行，没能在官方文档里核实它的名称与生效条件。这里只如实记录了测量值
  • Go 和 RE2 没有装在这台机器上，无法运行。表中相应的行不是实测，而是官方文档的表述。线性时间保证以及不支持反向引用与环视，都在文档里确认过，但实际耗时没有测
  • 没有通过源码确认 GNU grep 3.0 的内部实现。「自动机方式」是广为流传的说法，测量结果也与之一致，但本文确认到的只是没有观测到爆炸这一事实
  • grep 的测量被大约0.05秒的进程启动时间掩盖，低于这个区间的实际匹配开销无法分离。500万字符0.104秒这个数字，只是减去启动开销之后的推算
  • Python 的第三方 regex 模块和 re2 绑定在这个环境里没有，因此没有进入对比。只测了标准的 re
  • 其他 JavaScript 引擎（SpiderMonkey、JavaScriptCore）没有测。没有依据认为 V8 上得到的数值在别的引擎上也一样
