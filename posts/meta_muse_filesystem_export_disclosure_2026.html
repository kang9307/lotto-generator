1. 사건 개요와 1차 출처 보고의 성격

자율형 인공지능 에이전트가 복잡한 작업을 수행하기 위해 격리된 운영체제 환경과 파일시스템에 접근하는 구조가 보편화되면서, 해당 런타임 환경 내부의 자산 관리와 정보 반출 통제가 엔지니어링의 주요 과제로 부상하고 있다. 사용자와 상호작용하는 인공지능 모델이 시스템 도구를 호출하고 파일 작업을 수행할 수 있을 때, 에이전트가 참조하는 시스템 내부 설정과 자산이 어떤 경로로 사용자에게 전달될 수 있는지는 런타임 설계의 핵심 쟁점이다.

2026년 9월 22일, Mouse 소속의 연구자 Peter James는 Meta가 제공하는 인공지능 에이전트 서비스인 Muse와의 대화 실험을 통해 세션에 할당된 런타임 환경의 파일시스템 데이터를 아카이브 형태로 전달받았다고 기술 블로그를 통해 공개했다. 원문은 저자가 진행한 요청 절차와 내려받은 데이터의 구체적인 크기 및 디렉터리 구성, 그리고 Meta의 버그 바운티 프로그램을 통한 공식 신고 경위와 응답을 담고 있다.

이 보고서는 제3자 해킹 도구를 동원하거나 외부 침투를 시도한 결과가 아니라, 서비스가 제공하는 통상적인 대화 인터페이스를 통해 연결된 클라우드 저장소로 파일을 전달하도록 지시한 실험 결과를 다룬다. 원문은 자신이 확인한 사실관계를 있는 그대로 기술하면서도 민감 정보의 구체적인 값이나 아카이브 자체를 외부에 공개하지 않는 방침을 취했다. 본 글에서는 원문에 기록된 확정 사실과 양측의 입장을 체계적으로 정리한다.

2. 대화형 내보내기 실험과 전송된 데이터 규모

Peter James가 수행한 실험의 골자는 에이전트에게 스스로 볼 수 있는 환경 내부의 파일들을 단일 아카이브로 압축한 뒤, 사용자의 계정에 연결된 Google Drive로 전송하도록 요청한 것이다. 원문은 "Muse에게 볼 수 있는 파일들을 아카이브로 만들어 Google Drive로 전송하도록 요청했고, 에이전트가 이를 수행했다"고 적는다. 특수한 취약점 익스플로잇 코드를 주입한 것이 아니라 작업 지시를 자연어로 전달한 형태였다.

전송된 아카이브의 용량은 압축 상태에서 약 2.7GB였으며, 압축을 해제했을 때의 크기는 약 6.8GB에 달했다. 저자는 자신의 세션에 배정된 리눅스 환경의 루트 파일시스템 전체가 포함된 것으로 보인다고 설명했다. 데이터 내부에는 우분투(Ubuntu) 기반의 기본 운영체제 시스템 파일을 비롯하여 Meta 내부 문서, 런타임 연동 코드, 애플리케이션 템플릿, 메모리 파일, 에이전트 로그 등이 망라되어 있었다.

저자는 대화 화면에서 아카이브가 생성되고 Google Drive 링크로 전달되는 과정을 캡처하여 증빙으로 제시했다. 특히 데이터 내부에는 SSH 키 파일이 포함되어 있었던 것으로 저자가 보고했다. 저자는 이러한 SSH 키가 실제 운영 환경에서 유효하게 작동하는 키인지, 혹은 어떤 추가 권한을 제공하는지까지는 입증하지 않았다고 밝혔으며, 데이터 원본이나 키 문자열 자체는 외부에 공개하지 않았다.

3. 핵심 디렉터리 구조와 hatch 환경 파일 내역

내려받은 데이터 내에서 가장 핵심적인 역할을 담당하는 경로는 /home/hatch, /opt/hatch, /opt/hatch-image 등이었다. 원문은 'Hatch'가 Meta 내부에서 Muse를 지칭할 때 사용하는 코드명이며, 런타임 전반의 설정 파일과 스크립트에서 이 명칭이 일관되게 사용되고 있었다고 설명한다.

사용자 홈 디렉터리에 해당하는 /home/hatch/ 경로에는 에이전트의 작동 원리와 정체성을 규정하는 6개의 핵심 마크다운 문서가 배치되어 있었다. 이 파일들은 각각 다음과 같다:

  • SOUL.md: 에이전트의 기본 행동 철학 및 가치 지침을 기술한 파일
  • IDENTITY.md: 에이전트의 페르소나 및 정체성 정의를 담은 설정 파일
  • USER.md: 사용자에 대한 맥락 정보 및 상호작용 지침이 정리된 파일
  • MEMORY.md: 사용자의 선호도, 사실 관계, 약속 사항을 요약한 단기·핵심 기억 시트
  • AGENTS.md: 다중 에이전트 구조 및 서브에이전트 조율 규칙을 정의한 문서
  • TOOLS.md: 에이전트가 호출 가능한 도구들의 명세와 사용 가이드라인

이들 문서 외에도 동일 경로 아래에는 113건의 서브에이전트 실행 기록 및 JSONL 추적 로그를 보관하는 agents/ 디렉터리가 존재했다. 아울러 브라우저 사용법, 외부 커넥터, 결제 연동, 자격 증명 취급, 음성 제어, 목표 설정 및 스케줄링 방식을 규정한 약 20건의 마크다운 문서가 docs/ 경로에 포함되어 있었다. 일반적인 시스템 운영체제 배포본과 달리, 에이전트의 추론과 행동을 유도하는 프롬프트성 지침 문서들이 파일시스템 상에 일반 텍스트 형태로 온전히 배치되어 있었던 점이 특징적이다.

4. 스킬 아키텍처와 Spaces 애플리케이션 프레임워크

도구 연동 계층인 /opt/hatch/skills/ 아래에는 약 68개의 스킬 디렉터리가 배치되어 있었다. 각 스킬 디렉터리는 대개 에이전트가 해당 도구를 사용하는 시점과 조건을 정의한 SKILL.md 지침 파일과, 이를 실제 실행하는 명령줄 인터페이스(CLI) 도구 또는 지원 코드가 한 쌍을 이루는 구조였다. 지원 대상은 Google Workspace, Meta 소셜 플랫폼 앱, Outlook, 여행 및 쇼핑 서비스, 건강 관리, 홈 디바이스 제어, 미디어 생성 등으로 다양했다.

또한 skill-scopes.conf 및 bin-scopes.conf라는 설정 파일에는 향후 지원을 염두에 둔 것으로 보이는 커넥터 목록이 나열되어 있었다. 원문은 여기에 Slack, Dropbox, Polymarket, Canva, Klaviyo 및 사내 도구 명칭 등이 포함되어 있었다고 전한다.

코드 자산 중 가장 큰 비중을 차지한 것은 Spaces 프레임워크였다. 이는 에이전트가 사용자에게 대화형 웹 애플리케이션을 생성하고 제공하기 위해 활용하는 프레임워크다. 전송된 데이터에는 React 기반 클라이언트 코드, 서버 액션(Server Actions), Drizzle 기반의 SQLite 데이터베이스 스키마 및 SQL 마이그레이션 파일, Bun 런타임 구성 파일 등이 온전히 포함되어 있었다. 일반적인 서비스가 웹 애플리케이션의 템플릿과 실행 엔진을 서버 사이드에 숨겨두는 것과 달리, 에이전트가 직접 수정하고 서빙할 수 있도록 런타임 이미지 내부에 프레임워크 전체가 탑재되어 있었던 셈이다.

추가로 리눅스 컨테이너 격리를 위한 구성 요소도 확인되었다. /opt/hatch/runtime-cell/ 경로에는 systemd-nspawn을 이용해 루트 파일시스템을 기동하고 부팅 훅 및 데몬을 제어하는 18개의 스크립트가 존재했다. 한편 /opt/hatch-image/bin/codex에는 Codex CLI 버전 0.149.0이 설치되어 있었으나, 저자는 Muse가 이를 코딩 에이전트로 직접 호출하는 정황은 발견하지 못했다고 적었다. 대신 Codex 리소스에 번들된 bubblewrap 샌드박스 바이너리를 이용해 비디오 변환 도구인 ffmpeg와 ffprobe를 비특권 사용자(nobody) 권한으로 안전하게 구동하는 용도로 활용하고 있었다고 보고했다.

5. Muse의 메모리 보관 메커니즘과 동작 특성

Peter James의 보고서에서 기술적으로 상당한 분량을 차지한 대목은 Muse가 사용자와의 상호작용 기억을 장기 보관하고 유지하는 방식에 대한 설명이다. 원문에 따르면 Muse의 기억 시스템은 모델 자체의 가중치를 미세 조정하거나 수정하는 방식이 아니라, 외부 파일시스템과 데이터베이스를 유기적으로 결합한 갱신 메커니즘을 취하고 있다.

기억의 1차 기록지는 일반 마크다운 파일이다. 사용자와의 대화 중 발생하는 일상적이고 상세한 기록은 ~/memory/ 경로 아래에 날짜별 파일로 축적된다. 에이전트는 대화가 진행되는 도중에도 이 파일들에 새로운 내용을 작성할 수 있다. 한편 최상위 경로의 ~/MEMORY.md는 단편적인 사실과 사용자 선호, 약속 사항 중 엄선된 내용만 간결하게 추려 보관하는 시트 역할을 담당한다.

이러한 일상 기록과 핵심 시트 사이의 정리는 백그라운드 작업이 수행한다. 저자의 설명에 따르면 매시간 실행되는 배경 작업이 새로 생성된 주장(claim)들을 원래 대화 메시지와 대조 검증하고, 원문 인용문 및 메시지 ID, 주장 ID를 함께 부여하여 기록한다. 이를 통해 검증된 정보는 memory/bank/ 하위로 분류되어 상황, 경험, 선호 항목으로 구조화된다.

이렇게 축적된 마크다운 데이터의 고속 검색과 인출을 위해 Postgres 데이터베이스가 연동되어 있었다. memory.entries 테이블은 텍스트 청크와 줄 번호 참조를 저장하고, memory.embeddings는 384차원 임베딩 벡터를 보관하여 의미론적 유사도 검색을 지원한다. 또한 memory.claims 테이블은 각 주장의 근거와 신뢰도 점수, 상태를 추적하며, 상충하는 새로운 정보가 들어오면 supersedes_claim_id를 통해 이전 주장을 대체한다. 망각(forget) 작업 역시 단순한 텍스트 삭제에 그치지 않고 연결된 인덱스를 재구축하여 후속 작업이 삭제된 기억을 재생성하지 못하도록 설계되어 있었다. 결과적으로 모델의 가중치는 영구히 고정된 채, 파일시스템의 프롬프트 지침과 데이터베이스 기록을 능동적으로 갱신함으로써 시간에 따른 적응을 달성하는 구조다.

6. 신고 경위와 Meta의 공식 버그 바운티 응답

Peter James는 실험을 통해 확인한 결과와 데이터 내역을 정리하여 Meta의 공식 버그 바운티 프로그램을 통해 취약점 보고서로 접수했다. 연구자가 문제의식으로 제기한 핵심은 내부 런타임 파일과 민감한 자산이 일반적인 대화 요청과 연결된 클라우드 반출 목적지를 통해 시스템 외부로 빠져나갈 수 있다는 구조적 위험이었다.

신고 접수 후 Meta 보안 팀이 내놓은 공식 처리 결과는 "보고서를 '해당 없음(Not Applicable)'으로 표기"하는 것이었다. Meta 측의 회신문은 해당 판정이 내려질 수 있는 여러 일반적인 근거를 열거하였으나, 이번 건에 구체적으로 어떤 사유가 적용되었는지는 명시적으로 단정하지 않았다. 대신 보안 또는 개인정보에 미치는 추가적인 영향에 대한 증거를 제시해 달라고 요청했다.

표 2. 버그 바운티 신고 경위 및 양측 입장 정리

저자는 보고서에서 자신이 컨테이너 경계를 벗어나 호스트 시스템으로 탈출하는 시도를 가볍게 진행했으나, 테스트 결과 경계가 견고하게 유지되는 것으로 보였다고 밝혔다. 아울러 발견된 80여 개의 소켓에 대한 추가적인 접근은 운영 시스템에 미칠 영향과 자신의 경험 한계를 고려하여 중지했다고 덧붙였다. 즉, 가상화 또는 컨테이너 계층을 깨뜨리는 기술적 탈출은 발생하지 않았다는 점이 연구자의 서술을 통해서도 명확히 확인된다.

7. 에이전트 샌드박스와 파일 반출 경계의 기술적 쟁점

이번 사건은 자율형 인공지능 에이전트의 보안 평가에서 전통적인 인프라 격리와 에이전트 권한 격리 사이에 존재하는 개념적 차이를 뚜렷하게 보여준다. 시스템 아키텍처 관점에서 볼 때 세션별로 독립된 컨테이너 환경이 제공되고 호스트 탈출이 차단되어 있다면 인프라 보안 관점에서는 정상적인 격리가 유지되고 있다고 판단할 수 있다. Meta가 보고서를 "해당 없음"으로 분류한 배경에도 세션 격리 경계가 깨지지 않았다는 판단이 작용했을 가능성이 기술적으로 거론된다.

그러나 응용 계층 관점에서 접근하면 다른 문제가 제기된다. 사용자가 접근 가능한 샌드박스 내부라 하더라도, 에이전트의 프롬프트 정의 문서, 내부 아키텍처 명세, 통합 스킬 코드, 그리고 시스템에 잔존하는 SSH 키나 토큰 같은 파일들이 에이전트의 외부 내보내기 도구를 통해 일괄 반출될 수 있다면 이는 데이터 노출 리스크로 인식될 수 있다. 특히 에이전트에게 파일시스템 읽기 및 클라우드 업로드 권한이 결합되어 있을 때, 어떤 파일 경로까지 모델의 시야에 노출시킬 것인가는 엄밀한 접근 제어 규칙이 필요한 영역이다.

일반적으로 컨테이너 기반 에이전트 환경에서는 사용자가 생성한 작업 산출물 영역과 런타임 시스템 설정 영역을 물리적 또는 논리적으로 엄격히 분리하는 마운트 정책이 권장된다. 에이전트가 호출 가능한 도구의 매개변수를 검증하여 루트 디렉터리나 민감 설정 파일에 대한 일괄 읽기 및 압축 명령을 제한하는 방어 계층의 필요성이 이번 사례를 통해 개발자 커뮤니티에서 폭넓게 논의되고 있다.

8. 확인하지 못한 것

본 글은 1차 출처 기술 문서에 명시된 사실을 근거로 작성되었으며, 아래 항목들은 공개된 문서상에서 확인되지 않았거나 추가 검증이 불가능하여 단정적인 서술을 배제하고 사실 관계의 한계로 명시한다.

  • 전송된 데이터 아카이브 내에 포함되어 있던 SSH 키 파일이 실제 Meta의 내부 인프라나 특정 서비스에 유효하게 접근할 수 있는 활성 키였는지 여부는 저자가 검증하지 않아 확인하지 못했다.
  • Meta 보안 팀이 버그 바운티 보고서를 '해당 없음(Not Applicable)'으로 처리하면서 회신문에 열거한 여러 잠재적 근거 중 정확히 어떤 기술적 이유를 채택했는지는 공식 문서에 명시되지 않아 특정하지 못했다.
  • 보고서에 언급된 홈 디바이스 연동 명세인 'Meta Home Link' 및 ESP32-C5 관련 문서가 단순 사내 프로토타입 연구인지, 제한적 시험인지, 혹은 향후 정식 상용화될 예정인 기능인지는 원문 저자도 알지 못한다고 밝혔으므로 확인하지 못했다.
  • Muse 런타임 환경에서 발견된 80여 개의 내부 소켓이 정확히 어떤 백엔드 마이크로서비스 및 내부 포트와 통신하는 엔드포인트였는지는 원문에 세부 내용이 없어 파악하지 못했다.
  • 실험 이후 Meta 측이 런타임 환경의 파일 읽기 권한이나 대화형 아카이브 반출 동작에 대해 패치나 정책 변경을 적용했는지 여부는 후속 공지가 없어 확인하지 못했다.
