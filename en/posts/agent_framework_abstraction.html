What Should an Agent Be in Code - What Classes, Graphs and Config Files Each Hide

Choosing the abstraction also prices debugging, resumption and portability

Sep 1, 2026 Dev & Infra

The first thing you choose when building an agent is neither the model nor the tools. It is what the agent will be called in code. A class, a node in a graph, an entry in a config file, or a single text file holding a prompt. On day one this looks like a matter of syntax taste. Two months later it arrives as an invoice.

The line items on that invoice are predictable. How long it takes to see what actually went to the model. Whether an interrupted job can be picked back up. Whether reading a log means opening the framework docs alongside it. What you throw away when you move. The abstraction quietly decides all four in advance. The repository that prompted this piece is only a good starting point because it pushes one of the four branches further than anyone else, not because introducing that project is the point here.

This piece compares how several agent frameworks are designed but does not rate one above another. The design facts cited were confirmed in each project's official documentation and repository as of early September 2026, and this area changes quickly between releases.

The trigger - when an agent becomes a Python class

The labs-OO-Agents repository under the NVIDIA-NeMo organisation is exactly what its name says. Fields are state, methods are capabilities, docstrings are prompts, and type annotations are contracts. A method whose body is ... gets filled in by the model at run time; a method with real code stays deterministic Python.

from nooa import Agent

class SupportAgent(Agent):
    """You are a support agent."""
    order_db: OrderDB

    def is_refund_eligible(self, order: Order) -> bool:
        return order.delivered and order.days_since_delivery <= 30

    async def triage(self, message: str, order: Order) -> Ticket:
        """Create a typed support ticket."""
        ...

Three things that usually live in three separate places are gathered inside those twelve lines: the system prompt, the tool schema and the callbacks. The method name, its parameters and its docstring are the prompt, so editing the docstring changes the instruction. The model acts by writing Python in a Jupyter-style REPL with access to self and imported modules.

  • The repository was created on 20 July 2026. As of 31 August it shows 1,955 stars, 266 forks and 77 open issues. Those are six-week numbers
  • The published versions of the PyPI package nooa run from 0.0.7 on 30 July to 0.0.9 on 18 August
  • The licence is Apache-2.0 and the LICENSE file carries a copyright notice for NVIDIA CORPORATION & AFFILIATES. This is lab output, not a weekend experiment
  • The documentation calls itself research software. AST checks and module deny-lists are described as defence-in-depth guardrails rather than a containment boundary, and the containment boundary is stated to be OS-level isolation such as a container or a VM
  • A paper of the same name went up on arXiv on 22 July. Fifteen authors, and six model-facing concepts: typed input and output, pass-by-reference over live objects, code as action, programmable loop engineering, explicit object state, and model-callable harness APIs

That is what the repository and the abstract confirm directly. What interests me is what comes next. Why a class in particular, and what is already settled six months after you decide to call it one. Taking apart a single framework is work I did in the piece on a TypeScript sandbox framework, so here the subject is the form of representation itself.

The four branches representations fall into

Lay out what is currently available and the ways of representing an agent collapse into roughly four branches. Each makes a different shape of code natural, and therefore makes something different awkward.

BranchWhat an agent isCode that becomes naturalWhat becomes awkward
ObjectA class instance. Fields are state, methods are capabilityReusing shared behaviour by inheritance, pinning contracts with typesShowing the flow as a single picture
Graph or state machineNodes and edges. State flows through the graphExpressing branching, parallelism and interrupts structurallyAn agent's identity scatters across nodes
Declarative configA YAML or JSON entry listing role, goal and toolsNon-developers can edit it, diffs stay shortConditional logic. It escapes into code eventually
Prompt fileOne Markdown page whose body is the system promptReading the prompt as written and reviewing it by diffTypes, reuse, programmatic composition

Few real implementations stay purely in one branch. But the dominant branch is visible on the first page of the docs. If the first example is a class, it is object-shaped; if it is code registering nodes, it is graph-shaped.

  • Pydantic AI's Agent is a class generic in its dependency and output types. The documentation offers notation such as Agent[Foobar, list[str]] as an example
  • The OpenAI Agents SDK's Agent carries name, instructions, model, tools, handoffs and output type as fields and is generic over a context type. Instructions can also be a function
  • LangGraph centres on a StateGraph parameterised by a user-defined State. Nodes take the state and return an update; edges decide which node comes next
  • CrewAI defines an agent by role, goal and backstory. New projects use a config-first layout with agents/<name>.jsonc, and the older config/agents.yaml remains supported
  • AutoGen's core documentation defines an agent as a software entity that communicates via messages, maintains its own state and acts in response to messages received. Messages are the only point of contact
  • A Claude Code subagent is a Markdown file with YAML frontmatter, and the body is the system prompt as written
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

The class example above and this file are the two ends of the spectrum. One pulls in as much typing and inheritance as it can; the other finishes with a single text file. The point is not which end is right but that each position pays a different price.

What you actually gain by wrapping it in an object

The advantage of the object-oriented side is not elegance in the abstract. It comes from work the tooling does on your behalf.

  • The editor knows. Completion works, a mistyped parameter name is caught at save time, and a rename follows through to every call site. None of that happens when prompts exist only as string constants
  • Types pin the boundary. Declare an output type and a strange model response fails right there. It does not detonate three levels up in some unrelated place
  • Shared behaviour lives in one place. Write retries, budget caps and audit logging once in a base class and every subclass inherits them
  • Test doubles slot in easily. Override only the model-calling method and the rest can be exercised without a model. Whether an agent can run in CI is decided right here
  • Deterministic code and model judgement sit in one file. Refund eligibility goes in Python, triaging the message goes to the model. Scatter them and the line of responsibility blurs

The last item matters most. Whether agent code survives long-term mostly comes down to whether you refused to hand the model something you could have written as a rule. Ask a model whether delivery was within thirty days and it will usually get it right, occasionally not, and the occasional miss becomes a refund incident. The convention that a method with a body is deterministic while a body of ... belongs to the model writes that boundary directly into the syntax.

What wrapping it in an object hides

The cost concentrates in one place. The prompt that actually goes to the model is no longer written down anywhere in the source. It is the sum of the docstring, the signature, whatever the base class appended, and whatever gets injected at run time, so the final shape has to be computed to be known.

This grows in proportion to inheritance depth. Putting one shared instruction line in a base class is reuse, but whoever reads a class three levels down does not know that line is attached. Tool lists go the same way. Once they are registered by decorators, merged by mixins and filtered at run time, you cannot count how many tools are attached by reading the source alone.

Anthropic's post on engineering agents points at the same spot. Frameworks often add layers of abstraction that obscure the underlying prompts and responses and make them harder to debug, and incorrect assumptions about what is under the hood are a common source of error. That is a remark about layering in general, not about any one product.

  • Hiding becomes dangerous thirty minutes into an incident. What you need then is the full text the model received
  • So the thing to check on day one is not the feature list but how to dump the final payload to a file. If that is one line, deep inheritance is survivable
  • Whether tracing is on by default is also a selection criterion. The repository above states that every call is traced by default. On by default and possible to turn on are different things
  • Keeping inheritance shallow helps too. Two levels still reads; from four levels down, nobody reads it
  • Instead of burying shared prompt fragments as strings inside a class, pull them into files and reference them by name so they can at least be searched

What a graph shows and what it scatters

The strength of the graph side is that the flow becomes a data structure. A data structure can be drawn, inspected, and given structural rules about where to stop. Branching scattered through if statements inside an imperative function can do none of the three.

LangGraph's documentation puts the structure plainly. Nodes do the work and edges say what to do next. The state schema is the input schema for every node and edge, and each key gets a reducer. If no reducer is specified, all updates to that key simply override. That default is a regular home for subtle bugs. Set a conversation history that ought to accumulate to override and only the last item survives, and the symptom shows up as lost context, which reads like a prompt problem.

The price a graph pays is identity. Seeing what one agent does means following nodes and edges. The more complex the flow, the more the graph wins; the fatter each individual agent, the more the object wins. How many pieces to split into is covered in the piece on subagent counts.

  • A graph leans toward code holding the flow. Nodes must be registered in advance, so paths that were not defined rarely appear mid-run
  • That property helps reproducibility and hurts on unexpected input. Undefined situations still get routed down one of the defined paths
  • Graph definitions carry a lot of framework-specific vocabulary, which makes them among the hardest assets to move
  • On the other hand, being able to define interrupts structurally is a graph-only advantage. It matters a great deal when human approval sits inside the flow
  • Naming reducers explicitly is cheap and pays well. Write it even where override is correct and the next reader can tell intent from neglect

The ceiling declarative config runs into

The advantage of the config-file approach is social. People who are not developers can open, read and edit it, and the change history stays short and clear enough to argue about in review. In an organisation where a product manager edits prompt wording directly, that advantage outweighs everything else.

The ceiling arrives with conditionals. The moment a requirement reads use that tool only in this case, the config language starts imitating a programming language. From there only two roads exist. Put expression syntax inside the config, or open an escape hatch into code. The first invents a small language with no debugger and no type checker; the second creates a state where you must read both config and code to see the whole.

  • Good to leave in config — values people adjust often that carry no branching. Role descriptions, temperature, model names, tool allow-lists
  • Belongs in code — conditions, loops, computation, lookups against external state. Imitate these in config and it will become unreadable
  • The worst state is one concept split across two places. Half the tool list in a file and half in decorators means nobody knows the whole list
  • A config-first approach that still leaves a road into code is a design that knows about this ceiling

Prompt files - the thinnest abstraction

Making one Markdown page the agent removes one of the problems above entirely. What went to the model stops being a question, because what is in the file is what went. Frontmatter carries the name, the description and the tool allow-list, and the body below becomes the system prompt.

Claude Code's documentation states the boundary explicitly: subagents receive only this system prompt plus basic environment details such as the working directory, not the full Claude Code system prompt. The fact that what does not get included is also written down says a lot about this approach.

The cost shows up in programming. With no types, output shape has to be requested in the prompt; pulling out shared sections requires a text-include feature; and the moment that feature exists you are back in the previous section's problem. How far a role-splitting arrangement actually holds up is covered in the piece on role-division simulation.

  • Where it fits — work people touch often, with a single-track flow and text as the output
  • Where it does not — work whose output feeds another system and must not violate a schema
  • The hidden advantage is how well it pairs with version control. Prompt changes show as diffs and rolling back is rolling back a file
  • The hidden disadvantage is search. The same instruction ends up copied into ten places, and you fix one and believe you fixed it

The biggest fork - who holds the control flow

The four branches so far are differences of representation. What actually determines a system's character is the question underneath. Does code decide what happens next, or does the model? Anthropic separates the two by name. Workflows are systems where LLMs and tools are orchestrated through predefined code paths; agents are systems where LLMs dynamically direct their own processes and tool usage.

Frameworks put this switch in different places, and its position affects outcomes more than the representation does. Even on the same class-based footing, code holding all the flow is close to a workflow, while a model composing its next action in a REPL sits at the opposite end.

Who holds the flowFitting representationWhat worksWhere it breaksSymptom on failure
Code holds all of itGraphs, imperative functionsReproducibility, cost prediction, testingUndefined input arrivesRuns quietly to completion down the wrong path
The model holds all of itPrompt files, a single loopNovel situations, explorationLoops, duplicate calls, budgetCalls the same tool eight times and stalls
Code holds the skeleton, model the stretchesObjects (deterministic plus generation methods)Most real workDeciding where the boundary goesFails only inside badly drawn stretches
The model writes code to build the flowREPL and code executionBranching and looping in one shotWhen isolation is missingThe accident happens outside the sandbox

Using the third and fourth rows together is where current design is heading. Expressiveness goes up, but the execution environment becomes the attack surface. That is why the documentation above insists its AST checks and deny-lists are not a containment boundary. It is a burden shared by everyone who picks the fourth row.

Writing actions as JSON or as code

How a model calls tools also has two branches, and this choice is attached to the fork above. smolagents implements both side by side. CodeAgent generates its tool calls as Python code snippets, while ToolCallingAgent writes them as JSON. The documentation says either approach can be used and notes that web browsing, which requires waiting after each interaction, fits JSON calls well.

  • The code side's advantage — one action can hold loops, conditions and intermediate variables. Sweeping a list of twenty becomes a single round trip
  • The code side's cost — the whole execution environment comes inside the trust boundary. Modules, the file system and the network all become considerations
  • The JSON side's advantage — arguments can be validated against a schema and audit logs stay uniform enough to count and replay
  • The JSON side's cost — round trips multiply. Tokens and latency grow, and so does the chance of context being trimmed
  • The link to representation — exposing objects to a REPL leans toward code, while keeping tools as a list of independent functions leans toward JSON

Acting through code is not inherently smarter. It trades higher expressive density for fewer validation points. The closer a tool is to pure computation, the more the code side wins; the more a tool changes the outside world, the more the JSON side's validation points earn their keep.

State and resumption - what serialization asks back

Any abstraction runs fine on short tasks. What asks the question back is long-running work. A thirty-minute job dies at minute twenty-five: what is left? Each branch answers differently.

The graph side meets this head on. LangGraph lets you specify a checkpointer when compiling, and checkpoints save at superstep boundaries so a run can resume after an interrupt or a failure. Because the flow is a data structure, where it stopped can be expressed as a value.

On the object side the question becomes how to serialise the instance. Passing references over live objects buys expressiveness, but those references do not leave the process. Open sockets and file descriptors are handles, not values. That the package above describes itself in its PyPI summary as a code-generating agent orchestration system with event sourcing and serialized execution reads as a signal that the problem is being handled at design time.

The prompt-file side answers by holding no state at all. The conversation record is the state, and resuming means feeding the record back in. Simple and sturdy, but a long record turns straight into token cost.

  • Is the state a value or a handle? Values are saved, handles are not. If resumption is a requirement, draw that line early
  • Where are the save points? After every tool call or at node boundaries decides the worst-case loss window
  • Is re-execution idempotent? Restarting from a checkpoint must not call the same payment API twice. The framework does not guarantee this for you
  • Does the saved format survive deploys? If it cannot be read, every deployment erases work in progress

There is one way to check. In the first week, kill the process hard after the third tool call. That single experiment tells you more than the documentation does.

Observability - when logs turn into framework dialect

As abstraction layers pile up, logs acquire layers too. A line about a reducer at node 3 is a sentence only to someone who knows that framework's docs, and noise to everyone else. Picture the person paged at four in the morning opening those docs for the first time and the cost is obvious.

Two kinds of log are needed. One is the raw exchange with the model: the final prompt, the full response, the tool arguments, what the tool returned. The other is the framework's execution record. With only the second, debugging becomes guesswork. You asked why this answer appeared and were told which nodes were visited.

  • Good signal — tracing is on by default and calls are retained with parent and child relationships intact. The repository above states this in its docs and opens a viewer from the CLI
  • Signal to watch — a structure where seeing traces requires signing up for an external service. One more path for data to leave, and if the service is down that day's investigation stops
  • Floor — the raw record of a single run should land in a local file. Dashboards come after
  • Something to count — how many framework concepts a single log line requires. Past three, only insiders read it

Attach several agents and this cost multiplies. The cost of coordination itself is covered in the piece on the orchestration tax.

The real size of lock-in

Lock-in is what people worry about most when choosing, and the size of the worry does not match the size of the thing. The cost of moving comes not from lines of code but from whether it is text or a framework-specific format.

AssetDifficulty of movingWhy
Prompt textEasyIt is just text. You paste it
Tool function bodiesEasyUsually ordinary functions. You swap the decorator
Output schemasModerateRiding on a standard type library, they travel. Bespoke types get rewritten
Flow structureHardGraph definitions, inheritance chains and handoff rules are that framework's vocabulary
Saved checkpointsVery hardThe format belongs to the framework. Work in progress gets discarded
Trace and evaluation historyVery hardDifferent schemas. You lose the baseline for comparing regressions
The team's thinking habitsHardestPeople start carving problems into that framework's concepts

The last two rows are the real lock-in. Code can be rewritten, but lose the evaluation baseline and there is no way to prove the new arrangement is better than the old one. After six months people start discussing problems in that framework's concepts, and that cost never appears in a migration document.

  • Keep prompts in files or a constants module rather than as strings inside classes. A large share of the migration cost disappears
  • Write tools as pure functions with no framework decorator and register them in a thin adapter. Only the adapter gets rewritten
  • Keep evaluation datasets and grading criteria in files outside the framework. That erases one of the last two rows

When skipping the framework is the right call

Anthropic's advice is clear. It suggests developers start by using LLM APIs directly and notes that many patterns can be implemented in a few lines of code. It also adds that frameworks can make it tempting to add complexity where a simpler setup would suffice.

messages = [{"role": "user", "content": task}]
while True:
    reply = client.messages.create(model=MODEL, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": reply.content})
    calls = [b for b in reply.content if b.type == "tool_use"]
    if not calls:
        return reply
    results = [run_tool(c) for c in calls]   # from here down it is all my code
    messages.append({"role": "user", "content": results})

Nothing is hidden in these nine lines. What goes out and what comes back is visible in the variable names. In exchange, retries, budget caps, resumption and parallelism all have to be written by hand. The problem is that these nine lines will not still be nine lines in six months.

  • A hand-written loop suffices, one — the flow is a single track and you can count the branches on your fingers
  • Two — there are fewer than ten tools and they share no state with each other
  • Three — the work finishes inside one request, so resumption is not a requirement
  • Four — one or two people are involved, so conventions hold without documentation
  • Five — you want to decide the log format yourself, and have a reason to
  • A framework earns its keep, one — several people each add agents, so shared conventions must be enforced in code
  • Two — resumption and human approval are requirements. Build those yourself and you end up building a framework
  • Three — you swap between several providers and several models
  • Four — traces and evaluations must accumulate uniformly from the start. This is the hardest thing to backfill

In practice the common answer is the middle. Write the loop yourself and use a library only for tracing and evaluation, or adopt a framework but keep prompts and tools in files outside it. Seeing this as an all-or-nothing choice is itself already the framework's vocabulary.

Six questions to answer before choosing

Feature comparison tables do not help, because everything eventually does everything. Spend a few days with a candidate and answer these six instead, and what will hurt in six months becomes visible.

  • How many minutes does it take to dump the full prompt to a file? Past ten and your incident response time grows by the same amount
  • Can you count the tool list by reading the source alone? If not, permission review becomes execution-log review
  • What is left if you kill the process after the third tool call? If nothing is, do not run long jobs on this setup
  • Does code or the model hold the branching, and is the answer written in the docs? If not, the two are mixed, and the mixed spot becomes the incident
  • Can a colleague who does not know the framework read the log and say what went wrong? If not, operations is tied to one person
  • What would you rewrite if you tore this framework out? If the list is prompts and tool functions, the lock-in is shallow; if evaluation history is in it, it is deep

An abstraction is a choice about what to make easy, and what is easy happens a lot. Call it a class and people start sharing through inheritance; call it a graph and they start splitting nodes; call it a file and files multiply. The moment you choose, you have decided what the team will do most often for the next six months. The framework will not decide that answer for you, but what it has made easy is all there in the first example. Read the first page of the documentation as a design statement and you will see more than any comparison table shows.

What I could not verify

  • The repository's commit count shows as 322 on the listing screen, but that is for the default branch and shifts over time. I did not check per-branch or per-tag history
  • The paper's SWE-bench Verified and Terminal-Bench 2.0 results were confirmed only at the abstract level; I did not open the tables in the body. That is why not a single performance figure appears here
  • I could not find material comparing the frameworks named here under identical conditions. That is why this piece does not say which is better
  • The design facts recorded here follow each project's official documentation as of early September 2026. Config file formats have changed recently in at least one case
  • I found no study quantifying what migration actually cost teams that switched frameworks. The difficulty ranking in section 12 is not a measurement
