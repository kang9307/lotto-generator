CTX Explained - A Persistent Memory Tool for Claude Code Sessions

AI coding agents forget everything when a session ends - how CTX tries to close that gap with retrieval-based memory

2026-07-02 Dev & Infra

Introduction: The Fatigue of Explaining Everything Again

Anyone who works with Claude Code all day recognizes a recurring scene. You open a new session, and you have to explain from scratch what was decided last time and why a given file was changed. It's true even for the account running this very blog: this workflow leans on a file called MEMORY.md that summarizes past conversations so the next session can load them back in. As the number of projects grows into the dozens, a single file like that starts to strain under the weight — something I feel in daily practice, not in theory.

CTX is an open-source tool that takes direct aim at this problem. As of early July 2026, when it was featured on GeekNews (news.hada.io), it was a small project with roughly 98 cumulative users and about 2,726 monthly PyPI downloads. But the problem it addresses is one that anyone who uses an AI coding agent daily runs into. This piece lays out, from my own perspective, what CTX actually does, how it differs from Claude Code's built-in CLAUDE.md and Auto Memory, and how it's distinct from MCP memory servers.

1. Why Session Memory Matters

1.1 The Context Window Disappears When the Session Ends

Claude Code and most other AI coding agents only preserve conversational context within a single session. Once the session ends, or once the context window fills up and gets compacted, the fine-grained decisions inside it — why a function was written a particular way, why a library was dropped — vanish unless they were recorded somewhere separately. The next session effectively starts with amnesia.

1.2 The Real Cost of Repeating Yourself

This cost isn't just annoyance. The tokens and time spent re-explaining project structure, conventions, and recent issues at the start of every session are resources that could have gone toward actual work. At team scale, this repetition creates the same kind of inefficiency you'd get from having no handoff documentation between people. This is exactly the point CTX's creator raised: losing prior decisions and context whenever a session breaks is wasteful.

1.3 What Continuity Actually Buys You

Conversely, when continuity across sessions is preserved, an agent can move straight into the next task instead of re-deriving "why does this project use this pattern" every single time. That difference compounds especially on long-running work — a refactor spanning weeks, or debugging that stretches across many sessions.

2. How CTX Actually Works

2.1 Automatic Hook Wiring

CTX (package name ctx-retriever) is installed with pip install ctx-retriever and wires itself automatically into Claude Code's hook system. A UserPromptSubmit hook captures user queries, a PostToolUse hook tracks file changes during the session, and everything is auto-indexed once the session ends. There's no separate server or cloud account involved — it's all processed locally.

2.2 Retrieval Method - Hybrid BM25 + Vector

According to publicly available material, CTX uses a hybrid retrieval approach that blends keyword-based BM25 with vector embeddings roughly 50/50 (α=0.5). Queries are classified into four trigger types, each handled by a different pipeline: direct symbol lookup (EXPLICIT_SYMBOL), keyword-based concept matching (SEMANTIC_CONCEPT), dependency traversal through the import graph (IMPLICIT_CONTEXT), and recent-change history lookup (TEMPORAL_HISTORY). This structure itself signals that CTX isn't "summarizing and storing the whole conversation" but rather acting as a search engine that fetches only the fragments it needs.

2.3 Why No Extra LLM Call Matters

CTX states that it doesn't call an additional LLM during retrieval. That means no extra API cost for summarization or reorganization, and because it's pure algorithmic computation, latency stays in the tens-to-hundreds-of-milliseconds range. Compared with approaches where memory lookup itself becomes a cost-and-latency line item, this is a design choice that stands out in practice.

3. Relationship to CLAUDE.md and Auto Memory

3.1 Claude Code's Built-In Memory System

Claude Code already offers two official memory pathways. One is CLAUDE.md, a static file a person writes by hand to record project rules, build commands, and coding conventions that would otherwise need re-explaining every time. At session start, Claude Code reads any CLAUDE.md or CLAUDE.local.md files it finds, walking up from the current directory toward the root, and injects them into context. The other is Auto Memory, where the model itself writes down things it judges useful during a session — build commands, debugging insights, architecture notes, user corrections — into a MEMORY.md-style file.

3.2 "Writing It Down" vs. "Fetching It on Demand"

The clearest distinction I found while reading through CTX's material is this. CLAUDE.md and Auto Memory are static-file approaches where a human edits or the model summarizes content that gets written down. At session start, the whole file (or its top portion) gets loaded wholesale into context. CTX, by contrast, pre-indexes the conversation log and codebase, then fetches only the most relevant fragments per query. The former puts the maintenance burden on a person; the latter's quality hinges on retrieval accuracy — a genuinely different tradeoff.

3.3 Layers, Not Competitors

My own read is that these two are better understood as different layers rather than substitutes. CLAUDE.md excels at pinning down "rules you should always know," while retrieval-based memory like CTX excels at surfacing "details from a past session you only need occasionally." In fact, the way this very blog is run splits things the same way — top-level rules live in MEMORY.md, while project-specific history lives in separate per-project documents. That's essentially the same direction CTX is trying to automate.

4. Comparison with MCP Memory Servers

4.1 MCP Memory Servers Are a Protocol Layer

One of the official reference implementations of MCP (Model Context Protocol), the memory server, stores knowledge as a knowledge graph through standardized tools like create_entity and search_memories. The key is standardization: any MCP-compatible client (Claude Desktop, Claude Code, Cursor, and others) can access the same memory server through the same protocol, making it highly portable across tools.

4.2 CTX Is Closer to a Local Search Engine

CTX, by comparison, doesn't use the MCP protocol at all — it's a local tool wired directly into Claude Code's hooks. Its storage model isn't a knowledge graph either; it specializes in BM25/vector indexing and import-graph-based code structure search. In other words, while an MCP memory server aims for "a general-purpose fact-and-preference store shared across multiple tools," CTX aims for "search optimized for this specific codebase and these specific sessions." The design philosophies diverge from there.

4.3 A Practical Rule of Thumb

If you're moving across multiple AI tools (Claude Code, Cursor, and others) and want one shared memory, an MCP memory server fits the structure better. If you're working within Claude Code alone and need retrieval that precisely pinpoints code symbols and dependency relationships, a code-structure-specialized engine like CTX offers more concrete value. There's no strong reason you couldn't run both — their purposes don't really overlap.

5. Practical Adoption Scenarios

5.1 Where It Fits Well

For refactors spanning multiple sessions, repeated symbol/dependency lookups in a large single repository, or trying to recall "why did we drop that library last week" — retrieval-based memory like CTX offers a clear time savings. The fact that it processes everything locally without an extra LLM call is also attractive for individuals and small teams sensitive to API costs.

5.2 Where to Be Cautious

Published benchmarks show CTX performs better on queries mixed with code symbols and keywords than on pure natural-language queries, where recall can dip below plain BM25 in some ranges. It's also documented that codebases larger than 2,000 files are automatically excluded from indexing, and that heuristic symbol extraction quality degrades on unfamiliar projects without prior indexing history. Above all, with roughly 98 cumulative users, it remains an early-stage open-source project — which means long-term maintenance and security review deserve careful scrutiny before any production rollout.

5.3 What to Check Before Adopting It

My recommended process is straightforward. First, check whether your project's core rules are already well captured in CLAUDE.md. Then observe how often you actually need to search "cross-session decision history" that CLAUDE.md can't cover. If that need comes up frequently, install CTX on a side project first, measure the real-world benefit on your own codebase, and only then decide whether it's worth rolling out team-wide.

Conclusion: Memory Is Now Infrastructure for AI Coding Workflows

CTX itself is still a small project — about 98 users and 2,726 monthly downloads as of July 2026. But the problem it targets — AI coding agents forgetting everything between sessions — is far from small. Claude Code already addresses part of this with CLAUDE.md and Auto Memory, and MCP memory servers provide a different axis of cross-tool shared memory. Against that backdrop, CTX is trying to carve out a niche as "a third layer specialized in codebase retrieval." None of the three approaches is a complete solution on its own, and each has a different sweet spot. Understanding that and combining them to fit your own workflow feels like the most realistic answer right now. If you use an AI coding agent every day, it may be time to treat memory strategy not as an optional extra, but as base infrastructure — the same way you'd treat a CI pipeline.
