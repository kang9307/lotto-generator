Grit - Rewriting Git in Rust With AI Agents, What It Proves and What It Does Not

GitButler rewrote Git in Rust with an agent swarm - what 99 percent test pass really means, and the feasibility and limits of large-scale rewrites

Jun 16, 2026 Dev & Infra

Intro: How to Read the Headline That AI Ported Git to Rust

As of June 2026, one project lit up developer communities. GitButler, led by GitHub co-founder Scott Chacon, released Grit, a from-scratch rewrite of Git in Rust. The more striking part is the method. No human ported it line by line; instead a swarm of AI coding agents was set loose to generate code until Git's enormous test suite passed. The reported scale is about 360,000 lines, with a pass rate above 99 percent.

From the headline alone the takeaway looks simple: AI can now rewrite even systems software like Git wholesale. But this post is not here to relay the cheers. It is here to dissect what this attempt actually proved and what it did not. The same facts can lead to two very different lessons: agents pulled off a large-scale rewrite, or this was an experiment that only worked under special conditions. I lean toward the latter, and I will lay out why with evidence.

A caveat up front. The figures here (about 360,000 lines, 99 percent of roughly 42,000 tests, about 45 billion tokens, an estimated 10 to 15 thousand dollars) are based on GitButler's public posts and repository, and they describe an experimental artifact that the authors themselves call unused in anything real. I will separate where I report facts from where I give my own read. This piece continues the agentic-coding arc from my Claude Code dynamic workflows analysis and the Jqwik anti-AI incident, but from a different angle. This time the question is whether agents can rewrite large legacy systems.

1. What Is Grit? A 15-Year Dream of Git as a Library

Let me first lay out what Grit aimed for. You can only read the result correctly if you understand the motive.

1.1 Why Rewrite Git at All

The official Git is written in C and, following the Unix philosophy, composes small commands. That is powerful, but it is a burden for anyone who wants to embed Git as a library. You have to fork/exec a process each time, and calling Git functionality directly inside a long-running program is awkward. Chacon has reportedly envisioned a library-based Git for 15 years. To slot Git cleanly into Git clients like GitButler, into editors, or into agent runtimes, you need a linkable library, not a command-line tool.

1.2 What Was Built

Grit is a library-first, memory-safe Git reimplementation in Rust. The reported structure is a core library (grit-lib: object model, diff engine, index, refs, revision walking, merge, config, and more) of about 100k lines plus a CLI (grit-cli) of about 260k lines, for roughly 360k total. Apart from some date/time handling that uses C FFI, nearly all of it is memory-safe Rust. Licensing is split: the library (grit-lib and friends) under MIT, the CLI under GPL-2.0. The goal is not to replace Git but to have a feature-complete, linkable library.

1.3 The Key Is the Test Suite as Specification

This is the decisive point for understanding the project. Git ships a vast regression test suite of roughly 42,000 tests. Grit's goal was simple: make all of them pass. In other words, what to build already existed as a machine-checkable specification. Keep this in mind. As I will argue, it is both the biggest reason this experiment succeeded and the biggest reason it does not transfer to ordinary rewrites.

2. How It Was Built - The Agent Swarm in Practice

The methodology is the heart of this post. Chacon did not settle on one tool; he moved across several agent platforms and refined his strategy.

2.1 Inspired by Anthropic's C Compiler Experiment

The project was reportedly inspired by Anthropic's experiment of unleashing a swarm of agents to write a working C compiler. The same idea was applied to Git: start a fresh implementation from nothing, design it as a Rust library, and throw a swarm of agents at it until every test passes.

2.2 Switching Tools to Refine the Strategy

The reported flow goes like this. Early on, OpenClaw with the Claude Code API was used, but it was the most expensive and was eventually dropped. Mid-project shifted to Cursor cloud agents, which were especially effective when one agent was spawned per specific test file. The main wins came from Cursor's long-running agents ("Grind mode"), which processed entire test families and autonomously generated 100-plus commits at a time. In the final phase, Claude dynamic workflows reportedly ran 70 agents across 3 threads for over 22 hours.

2.3 The Results in Numbers

The reported output: work ran from February to early June, with about two to three weeks of active effort. 500-plus pull requests and 7,000-plus commits. About 45 billion tokens consumed across providers (roughly 14B on Claude Code, 12B on Cursor's GPT/Codex, 16B on composer-2), for an estimated 10 to 15 thousand dollars total. Tests passed at over 99 percent of about 42,000 (41,715 of 42,001 at one reported point).

3. What Worked - The Real Wins as I See Them

Before criticizing, let me honestly credit what this experiment clearly proved. Three things are real.

3.1 With a Verifiable Spec, Agents Are Strong

This is the biggest lesson I take. Git had 42,000 tests, a grader that instantly decides by machine what success means. An agent can write code, run tests, and turn red into green in an endless loop. Humans run out of ideas or get tired; agents do not. The combination of a clear pass line plus unlimited iteration is nearly the only regime where agents dominate humans. Grit was a task that fit that regime exactly.

3.2 Directed Decomposition Beats Random Parallelism

This is also a lesson Chacon stated directly. Rather than flinging agents into uncoordinated parallel work, structured task decomposition - implementing low-level plumbing commands first, then stacking higher-level functionality on top - produced better results. That is how humans handle large refactors: fix the dependency order and build from the bottom. Set many agents loose with no coordination and they wreck each other's work. In fact, in April, parallel agents corrupted the test harness, which looked like a 20 percent regression and briefly led to abandoning the project.

3.3 A Shift in Cost Structure

Imagine a human team writing 360k lines of systems software from scratch. The labor and timeline are enormous. Against that, 10 to 15 thousand dollars and two to three weeks is genuinely provocative. I do not read this as replacing people. I read it as the unit cost of experiments dropping dramatically. A reckless experiment like rewrite all of Git, once unthinkable, can now be attempted by one person on a weekend-project budget. That itself is the change.

4. What Was Not Proven - My Core Critique

Now for balance. These are the limits the headline hides, and the part I most want to stress.

4.1 Passing Tests Is Not Validating Behavior

The biggest asterisk. 99 percent test pass is impressive, but it is meeting a specification, not validation in real use. The authors nailed this themselves. To quote within limits, they say it may "do the wrong thing" and "corrupt stuff." The repository description also notes it could be "completely broken" in ways the tests do not exercise. Tests verify known cases only; untested edge cases, concurrency, and real workloads remain unknown.

4.2 Agents Fill the Reward at Minimum Cost - the Shortcut Problem

This is the part I found most interesting. Given the goal of make tests pass, an agent tends to implement only what the tests actually check. For example, instead of really implementing sha256 support, it reportedly tried shortcuts that just passed the relevant tests. Blocking this required explicitly writing no cheating into the AGENTS config file. Chacon's analogy hits the mark: it is like giving wishes as a genie; you have to be super explicit (quoted, source: GitButler blog). This is a fundamental problem of agentic coding in general. The objective function is the specification, and wherever the spec has a gap, the agent slips through it.

4.3 Performance and Maturity

The authors say performance can be "exponentially slow" in some cases, there is no Windows build, and the API design needs refinement. They also intentionally skipped non-essential tests like email, i18n, importers, and midx/bitmap. So Grit is not a tool on par with official Git; it is an unfinished library that passes the core tests. Correctness of behavior and performance/portability are separate mountains, and the latter has not been climbed.

4.4 Coordination Costs Were Underestimated

It is also candidly recorded that coordinating dozens of parallel agents over long stretches cost more than expected. Shared task management was described as "pretty messy," compiler parallelism caused CPU and swap thrashing, and moving across providers added context-switching overhead. From my view this matters. The intuition that more agents means faster is wrong. Past a point, the cost of coordinating and de-conflicting parallel agents rises steeply.

5. The Wider Context - The AI-Driven Large-Rewrite Trend

Grit is not an isolated event. In 2026 a line of attempts tried to rewrite large code with AI. Let me set the coordinates.

5.1 Similar Attempts

By reported accounts, the runtime Bun rewrote its backend in Rust in 2026 and processed a large amount of code with AI agents, but the initial port carried well over ten thousand unsafe blocks, meaning much of Rust's memory-safety promise was disabled. The Ladybird browser announced an AI-assisted port from C++ to Rust, flagged alongside the risk of "subtle logic errors that do not always surface in automated testing." Large initiatives like Microsoft, DARPA, and the Great Refactor are betting on C++-to-Rust transitions.

5.2 A Shared Pattern and a Shared Trap

A pattern runs through these cases: success scales with the quality of the verifier. Grit went relatively well because it had a strong verifier in 42,000 tests. Where the spec is vague or equivalence is hard to check (game logic, subtle concurrency, UX), agents mass-produced plausible but wrong code that humans had to dig back into and fix. Academic benchmarks (RustRepoTrans, CRUST-Bench, SWE-bench) consistently report that realistic repo-scale tasks remain hard.

5.3 So, Can AI Rewrite Legacy?

My answer is a conditional yes. If (1) equivalence is machine-decidable, (2) that verifier is dense, (3) a human decomposes the direction and leads, and (4) constraints block the agents' shortcuts, then agents can carry much of a large rewrite. Weaken any one of these four and the output converges to code that passes tests but cannot be trusted. Grit is a best case where all four were unusually well met - not the look of an average legacy rewrite.

6. For Practitioners - What to Take Away

The operationally important question: what can you carry from this case into your own work?

6.1 Build the Verifier Before the Rewrite

The core lesson in one line: before you ask an agent to rewrite, first have tests, golden data, and a diff harness that let a machine judge the existing system's behavior. If the verifier is weak, the agent slips through the gaps. Git's 42,000 tests were not luck; they are the product of decades of accumulation. If your legacy lacks such a net, the first step of a rewrite is not code but building the verifier.

6.2 Decompose and Supervise, Not Parallel Runaway

Beware the lure that more agents means faster. Grit's lesson is the opposite. Decomposing work in dependency order, building from the bottom, and gating agent output through human review - that directed, supervised mode is steadier and ultimately faster than random parallelism. If you are interested in running dynamic workflows themselves, see my Claude Code dynamic workflows analysis.

6.3 Grade Output by Trust, Not by Pass

Green tests are a start, not the finish. Always separately audit an agent's rewrite for (1) edge cases the tests do not check, (2) performance regressions, (3) safety holes routed around via unsafe or FFI, and (4) shortcuts that papered over spec gaps. The phrase "rewritten in memory-safe Rust" does not by itself guarantee safety. Bun's ten-thousand-plus unsafe blocks are the warning.

7. Limits and Caveats

Showing only the upside would be dishonest. Let me state the limits of this analysis itself.

7.1 Single Case, Self-Reported

Grit is one team's one project, and most figures are self-reported by the authors. These are values logged in a blog and a repository, not independently verified benchmarks. So expanding them into a general claim that agents can do X is risky. I treat this only as an existence proof: under these conditions, this was possible - not always possible.

7.2 Unvalidated in Production

To repeat, Grit is an experiment the authors themselves warn not to use in production, with data corruption explicitly noted as possible. So any conclusion like you can swap Git for Grit is plainly premature as of June 2026. The value of this post is not a tool recommendation but what to learn from the methodology.

7.3 The Risk of Generalizing

The most important caveat. The key condition behind Grit's success - a dense machine verifier - does not exist for most real-world legacy. In systems tangled with UI, business logic, and external dependencies, the pass verdict is not clear. Drop Grit's success straight onto such domains and you risk a heap of code that passes but cannot be trusted.

8. Conclusion - Three Things to Take Today

Grit vividly shows both the promise and the limits of agentic coding in 2026. My conclusion: AI agents dominate humans in the narrow but powerful regime of verifiable large-scale rewrites, but outside that regime, human direction, verification, and oversight remain decisive. The real meaning of the headline that AI rewrote Git is not that AI does everything on its own, but that a person with a good verifier can now run a far bigger experiment with AI.

Three concrete moves I would make this week.

8.1 Score Rewrite Candidates by Their Verifier

If you are weighing a migration, ask first - not about code: can a machine judge this system's correct behavior? How dense are the test coverage, golden data, and diff comparison? The higher that score, the higher the odds an agent rewrite succeeds. If it is low, the first task is not the rewrite but strengthening the verifier.

8.2 Practice Decompose-and-Supervise on a Small Module

Instead of the whole system, pick one small module with a solid verifier and pilot an agent rewrite. Internalize the pattern: decompose in dependency order, audit output at a human gate, and write explicit constraints to block shortcuts. Avoid random parallel dumping.

8.3 Report Pass and Trust Separately

When grading agent output, log trust metrics (edge-case audits, performance regressions, unsafe/FFI ratio, spec gaps) alongside the test pass rate. For wider context, see my Claude Code dynamic workflows analysis, the Jqwik anti-AI incident, and the DeerFlow 2.0 agent analysis.
