A Code Graph MCP Built on the TypeScript Compiler Cuts Claude Code Tokens 10x

Why querying a pre-built graph instead of reading code collapses token usage - the mechanism, and where it breaks down

2026-07-02 Dev & Infra

Introduction: The Problem Was Never "How to Generate," It Was "How to Look Around"

A short post on GeekNews caught my attention: someone built a code graph from the TypeScript compiler, exposed it as an MCP (Model Context Protocol) server, and reported that Claude Code's token consumption dropped by roughly 10x on the same tasks. The original write-up was terse, but the problem it targets is not small. Anyone who has actually put an AI coding agent to work on a real codebase knows the pattern - a trivial question triggers five file reads, a handful of greps, and half the context budget disappears just "finding the code" before any real work happens.

This piece is not a summary of that source. It is my own analysis, built by independently researching and cross-checking MCP, the TypeScript compiler API, and the landscape of existing code-indexing approaches, then reasoning through why the design choices described actually produce a token reduction. As of July 2026, several code-graph MCP tools already exist, each with different architectures and different claimed savings. Against that backdrop, I want to unpack why "compiler-based" is the load-bearing choice here, and why tokens fall the way they do.

1. What a Code Graph and MCP Actually Do Together

Stripped to one sentence, a code graph MCP is a tool that hands an agent a map of the codebase that has already been read and organized in advance. It helps to separate the two halves.

1.1 The Code Graph - Turning Structure Into Coordinates

A code graph represents a codebase's symbols - functions, classes, types, variables - as nodes, and the calls, inheritance, imports, and type references between them as edges. Questions like "who calls this function" or "where is this type used" can be answered by walking the graph instead of grepping through files. The critical part is that this graph is built ahead of time, during an offline indexing step, not recomputed on every request. The agent is not analyzing the code fresh each time it is asked something - it is querying a map that already exists.

1.2 MCP - The Standard Pipe That Delivers the Map

The Model Context Protocol is an open standard Anthropic released in November 2024 that standardizes how LLM-based agents talk to external tools and data sources. Wrap a code graph in an MCP server, and an agent like Claude Code can query it through a defined protocol and get back a structured response. As of 2026, MCP has become close to a de facto standard - Claude Code, Cursor, Codex, Windsurf, and most other major coding tools support it, and the ecosystem now counts well over 5,000 MCP servers. Code graphs themselves are not a new idea; static analysis tools have existed for decades. What changed is that a standard interface now exists for an agent to query one directly, which is what makes "agent queries graph" a practical workflow rather than a research curiosity.

1.3 The Central Claim of This Particular Tool

Two design choices stand out in the source material. First, responses never include full source text - only names, edges, signatures, and file:line spans. Second, the tool enforces a structured reasoning order so the agent cannot wander through the graph aimlessly. Benchmarked across eight repositories and four models, the report claims roughly a 10x reduction in tokens while holding answer quality steady. That figure belongs to one specific benchmark configuration - it should be read as a directional signal that graph-mediated access can produce order-of-magnitude savings, not as a guaranteed number for any given codebase.

2. Why Tokens Actually Drop - The Real Cost Is Discovery

This is the part I found most interesting. The source of the savings is not generation - it is discovery.

2.1 Agent Discovery Overhead Is Larger Than It Looks

A meaningful share of the tokens an agent like Claude Code burns on an unfamiliar codebase goes toward "finding" the code, not writing it. Grep for candidates, glob to list files, open a few, discover they're not the right ones, search again. That loop, repeated, fills the context window on its own. In a roughly 200-file codebase, navigation overhead alone has been observed to run somewhere in the neighborhood of 80,000 to 150,000 tokens per hour of work - and that is the cost of "finding your way around," not the cost of the actual task. Without a code graph, an agent re-runs this discovery loop from scratch every time.

2.2 What a Compact Response Changes

The core mechanic of a code graph MCP is that it returns coordinates for the relevant slice, not the surrounding file. Ask "who calls this function" and get back five function names and their file locations, and the agent jumps directly to those coordinates and reads only what it needs. The token gap between repeatedly skimming whole files and landing precisely on the right lines widens combinatorially as the codebase grows. It is reasonable to read the reported 10x figure as evidence that, in large repositories where discovery round trips were already expensive, removing that inefficiency produces an outsized effect.

2.3 Why Enforced Reasoning Order Matters Too

Simply exposing a graph is not sufficient on its own. If an agent, even with graph access, falls back into habitually re-reading whole files or wandering into irrelevant nodes, the savings shrink. What the source describes as "enforced systematic reasoning" appears to be a mechanism - built into the prompt or the tool interface - that forces a fixed order: query the graph, narrow the target, read only the necessary span. This echoes a pattern visible in separate chain-of-thought research: unstructured reasoning can waste tokens, while separating information retrieval from reasoning steps and enforcing that structure has been shown to cut generated tokens by roughly 2-3x while preserving quality. In other words, the savings here come from two things working together - the graph as a data structure, and a design that forces the agent to use it in a disciplined way.

3. Why the TypeScript Compiler API Specifically

As of mid-2026, several code-graph-flavored MCP tools already exist. Broadly, they split into Tree-sitter-based parsers supporting many languages, vector-embedding tools for fuzzy semantic search, and - as in this case - tools built directly on a language's own compiler. It's worth examining why the compiler route was chosen here.

3.1 The Limits of Heuristic Parsers

Tree-sitter and similar parsers are fast and accurate at recognizing a code's grammatical structure - where a bracket opens and closes, which node is a function declaration. But questions like "what type does this variable actually resolve to," "where does this import ultimately originate after passing through several re-exports," or "how does this generic get instantiated" are semantic questions, not syntactic ones. Grammar alone cannot answer them precisely; you end up stacking heuristics to approximate the answer, and approximation inevitably produces both false positives and missed edges.

3.2 The Compiler Already Has the Answer

To actually build a project, the TypeScript compiler resolves every module, infers every type, and settles every reference. The result of that process - the internal state of the type checker - already contains the answer to "what precisely references what." Building a code graph on the compiler API means reusing that answer directly instead of re-deriving it. However many hops a re-export chain takes, however tangled the type aliases get, the compiler has already worked it out, so the graph's edges are unlikely to diverge from what the code actually does. This mirrors a philosophy visible in other TypeScript-ecosystem tools - AutoBE, for instance, embeds the compiler at the API level so AI-generated code can be validated against real compiler feedback rather than a guess. The common thread: where a codebase needs a definitive answer, use the compiler's ground truth instead of approximating it.

3.3 The Cost Shifts to Indexing Time

None of this is free. Compiler-based analysis is heavier and slower than Tree-sitter parsing. But that cost is paid once (or incrementally, on code changes) during indexing, not on every single agent request. Heavy computation gets pushed offline; only cheap lookups remain online. I'd argue that time-shift - from per-query cost to one-time indexing cost - is the real design philosophy behind code-graph MCPs in general, not just this one implementation.

4. Where This Pays Off Most - Large Codebases

The value of this approach scales with codebase size. In a small side project, the difference between reading a few files and querying a graph is negligible. Production codebases are a different story.

4.1 Navigation Overhead Grows Combinatorially With File Count

As a codebase grows from 200 files to 2,000, the candidate set of "files that might be relevant" grows with it - more lines per grep hit, more candidate files to skim. A code graph absorbs that combinatorial growth into a pre-computed edge list. The gap between "already mapped out" and "search again every time" widens as scale increases, so I would expect the payoff to be largest in big monorepos and long-lived legacy codebases.

4.2 Especially Strong for Refactoring and Blast-Radius Analysis

"If I change this function, how far does the impact spread?" is fundamentally a graph-traversal question. With a code graph, that question is answered by walking reverse edges instead of grepping through the tree. This lines up with what similar tools claim as their core use case - for example, a separate code-review-oriented graph tool reports roughly a 49x token reduction for review workflows by giving Claude a precise "blast radius" file list with structural metadata instead of asking it to read everything. Tasks that repeatedly need to answer "where does this change reach" - large refactors, code review - are where the graph's advantage is most visible.

4.3 Onboarding and Undocumented Code

In codebases with thin documentation or an original author long gone, the cost of a new contributor - human or agent - building a mental model of the structure is substantial. A code graph turns that implicit structure into explicit data. It helps people too, but it matters more for a context-constrained AI agent, which has no equivalent of "spending a few weeks absorbing the codebase" - the graph effectively substitutes for that accumulated familiarity.

5. How This Compares to LSP and Vector-Embedding Indexing

A code graph MCP is not the only approach on the table. At least three distinct strategies are competing here, each with different tradeoffs.

5.1 The Difference From LSP

The Language Server Protocol is the standard by which editors talk to a language server for things like go-to-definition and autocomplete - TypeScript's own tsserver is effectively this role. But LSP is designed for one query, one response, at a time: where is the definition at this cursor position, what completions are valid here. For an agent to understand a whole codebase's structure through LSP, it has to make hundreds of these round trips, each carrying protocol overhead and latency. A code graph MCP removes that back-and-forth entirely by pre-building the "whole structure" into something queryable in a single call. If LSP is a conversation, a code graph is closer to handing over a finished map all at once.

5.2 The Difference From Vector-Embedding Indexing

RAG-style embedding of code to find semantically similar snippets is also widely used, and it is genuinely strong at fuzzy "find something like this" queries. It is weak, however, at questions that need a definitive answer, such as "who exactly calls this function" - embedding similarity is an approximation, not ground truth. A code graph sits at the opposite end: strong on definitive relationships, weak on fuzzy search. In practice, I'd expect these two approaches to end up complementary rather than competing - embeddings handle "find similar code," graphs handle "trace the exact dependency."

5.3 The Tradeoff Against Language Generality

Tree-sitter-based tools have the advantage of supporting many languages under one framework. Compiler-API-based approaches are more accurate but require a separate implementation per language. It's also worth noting that TypeScript is unusually well-suited to this approach specifically because its compiler is exposed as a public API and its type system is strong. Reaching the same accuracy in another language would require that language's compiler or type checker to expose an equivalent API - and not every language ecosystem has that infrastructure in place.

Conclusion: More Valuable at Scale, More Valuable Where Precision Matters

As of July 2026, code-graph MCPs look less like an established standard and more like a fast-growing experimental space. What makes this particular TypeScript-compiler-based example interesting isn't just "pre-build a graph and query it" as an idea - it's the specific choice to carry the compiler's already-settled answer directly into the graph. Definitive edges instead of approximated ones, and indexing time instead of per-request recomputation: those two shifts are, in my reading, the actual mechanism behind the token reduction, not the graph format itself.

That said, the 10x figure shouldn't be treated as a universal constant. It comes from a specific set of repositories and models; smaller projects, or tasks where discovery overhead was already low, will likely see far smaller gains. There's also the ongoing burden of running an indexing pipeline and the language lock-in that comes with a compiler-based approach. If you're running an AI agent against a large TypeScript codebase for repeated refactoring or impact-analysis work, it's worth wiring up a code graph MCP and measuring both token usage and answer quality on your own workflow before deciding. If you're already using LSP or embedding-based indexing, treating a code graph as a complement rather than a replacement is the more realistic path.
