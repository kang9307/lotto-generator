过滤只改了空白的 diff - 别让真正的改动被埋没

-w 和 -b 到底差在哪，以及怎样把格式化提交整个移出 blame

2026-09-01 开发/基础设施

一个审查请求上来了。三个改动文件，51 行新增、51 行删除。打开一看，缩进从制表符换成了空格，行尾空白被清理过，而在这中间某处多了一个选项。审查者要做的就是找出那一处，可屏幕上其余一百行是同样的红和绿。

这种情况下人通常只会做两件事之一。一边滚动一边用眼睛扫，然后漏掉；或者干脆按下批准。两者都不叫审查。而且这不是审查者够不够认真的问题，是把一块信噪比一比五十的屏幕丢给人的那一方的问题。

好在这个问题几乎可以完全靠工具解决。git 能在排除空白差异的前提下重新计算 diff，也能把一个格式化提交整个从逐行历史追踪里剔除。这篇文章就是用临时建仓库实际跑出来的输出把这些功能整理了一遍。

一行被一百行埋掉的结构

空白噪声大多不是人有意造出来的。每次保存都自动跑的格式化工具、团队里各不相同的编辑器制表符宽度设置、开了保存时去尾部空白的人和没开的人。光是这三样凑在一起，把文件打开再关上就足以让整份文件变成改动对象。

问题出在后面。diff 是按行比较的，所以行里一个看不见的字节变了，那一行也会显示成一删一增。给一个四十行的函数换缩进，就是四十行删除加四十行新增，也就是八十行占满屏幕。哪怕其中夹着一行真正的修改，视觉上也和另外七十九行没有区别。

这时常见的两种应对，都只对了一半。一种是别再用格式化工具，这会让格式化工具本来消掉的另一类审查浪费重新回来。另一种是审查者看仔细点，这等于要人用注意力去偿还本该由工具还的债，撑不了多久。真正管用的是第三种，在把内容送上屏幕之前，先把空白差异从计算里剔出去。

空白改动有五种

把空白改动当成一件事来处理就没法选选项，因为 git 的各个忽略选项忽略的东西并不相同。实际会碰上的有五种，各自的来路也不一样。

种类怎么产生的看得见吗对 diff 的影响
行尾空白编辑时残留的空格和制表符。开了保存清理的人一打开文件就会一次全消失看不见整行都被标成改动
缩进转换制表符和空格互换。格式化工具或编辑器设置的差异几乎看不见所有缩进行都被标成改动
行内空白数量为了对齐而在等号周围增减空白看得见该行被标成改动
空行增减格式化工具的空行规则，或者个人分段的习惯看得见出现增删行，hunk 范围随之变宽
文件末尾换行把最后一行不带换行符保存的工具看不见最后一行显示为先删后增

还有第六种，换行符本身。CRLF 和 LF 的性质稍有不同，放在 §13 单独看。看不见的字节污染文件的另一个例子是文件开头那三个字节的 BOM，不过它坏的不是 diff 而是执行本身。

把五种全塞进一个文件

在讲选项之前先造一个比较对象。拿一个六行的配置文件，把上面五种全塞进去，再在中间藏唯一一处真正的改动。真正的改动只有 timeout 从 30 变成 60 这一处，其余全是空白。

$ cat -A app.conf          # 已提交的原文。^I 是制表符，$ 是行尾
server {$
^Ilisten 8080;$
^Iretries = 3;$
^Itimeout = 30;$
log_level = info;$
}$

$ cat -A app.conf          # 编辑之后
server {   $               <- 三个行尾空格
    listen 8080;$          <- 制表符变成四个空格
^Iretries  =  3;$          <- 行内空白数量变了
^Itimeout = 60;$           <- 真正的改动 (30 -> 60)
$                          <- 加了一个空行
    log_level = info;$     <- 原本没有的缩进冒出来了
}                          <- 删掉了文件末尾换行 (这里没有 $)

在这个状态下不带选项跑 git diff，结果是这样。六行的文件变成六行删除、七行新增。实际变的其实只有一个数字，整个文件却全裂开了。

$ git diff
diff --git a/app.conf b/app.conf
index bd81bfd..d0ea0b8 100644
--- a/app.conf
+++ b/app.conf
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
-}
+server {
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
+}
\ No newline at end of file

审查者想在这里找出 timeout 那一行，就得用眼睛比对十二行。六行的文件还做得到，四百行的文件就不可能了。

逐个加上忽略选项

现在把选项一个一个加到同一个文件上。按顺序看这三个，就能看清每个选项到底吞到哪里为止。

$ git diff --ignore-space-at-eol      # 只忽略行尾空白
@@ -1,6 +1,7 @@
 server {                             <- 降成了上下文行
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
 }
\ No newline at end of file

$ git diff -b                         # --ignore-space-change
@@ -1,6 +1,7 @@
 server {
     listen 8080;                     <- 制表符变空格也吞掉了
 	retries  =  3;                   <- 行内空白数量也吞掉了
-	timeout = 30;
-log_level = info;
+	timeout = 60;
+
+    log_level = info;                <- 原本没有的缩进留下来了
 }
\ No newline at end of file

$ git diff -w                         # --ignore-all-space
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;                    <- 剩下的只有真正的改动
+
     log_level = info;                <- 和那个新增的空行
 }
\ No newline at end of file

把三份输出并排看，-b 和 -w 的差别正好落在一行上。log_level = info; 原本是没有缩进的行，现在多了四个空格。-b 把有一个以上空白的区间彼此视为相同，所以零个和四个并不相同。-w 干脆当空白不存在，于是连这个也一起吞掉。

  • --ignore-space-at-eol 只看行尾。缩进转换会原样留下，所以对付格式化工具的噪声力度不够
  • -b 连行尾空白一起忽略，也就是说它是 --ignore-space-at-eol 的超集
  • -w 又是 -b 的超集。三者可以用包含关系理清
  • 没有任何一个选项能消掉新增的空行。 空行归另一个选项管，而且那个选项还带条件
  • 还有一处值得注意。加上 --ignore-space-at-eol 之后，最后那行 } 降成了上下文行。这说明文件末尾换行的有无也被当作行尾空白处理

--ignore-blank-lines 按 hunk 判断

§5 最后那份输出里，加了 -w 之后新增的空行还留着。于是很容易想到再加上 --ignore-blank-lines 就行了，可实际加上去并非如此。

$ git diff --ignore-blank-lines       # 单独加在 §4 的那个文件上
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
...                                   # 什么都没少

$ git diff -w --ignore-blank-lines    # 和 -w 一起加也一样
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;
+                                     <- 空行原封不动还在
     log_level = info;
 }

# 可是在只改了空行的文件上，它完全生效
$ git diff blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta

$ git diff --ignore-blank-lines blanks.txt
                                      # 没有输出，全部被抑制了

$ git diff -w blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta                                # -w 消不掉空行

规则是这样的。--ignore-blank-lines 不按行判断，而是按 hunk 判断。某个 hunk 的改动全是空行，就把整个 hunk 丢掉；只要混进一处有内容的改动，整个 hunk 就原样输出。所以在只整理了空行的提交上它完美生效，在空行和逻辑改在同一处的提交上则毫无作用。

  • 审查一个格式化工具只动了空行规则的提交时，--ignore-blank-lines 是最强的工具。其余场合要把预期降下来
  • -w 和 --ignore-blank-lines 管的范围不重叠，所以把两个一起加当成默认做法是合理的
  • 这个按 hunk 判断的规则，GNU diff 的 -B 也一样。§16 会确认同样的现象

用数字判定这次改动是不是大半在格式化

开始审查之前想知道的通常就一件事，这次改动里究竟有几行是真的。 这不用靠眼睛数，两条命令就出来了，因为统计类选项会老老实实尊重 -w。

# 三个文件: a.js 纯粹重新格式化，b.js 重新格式化 + 一行真改动，c.js 只有真改动
$ git diff --shortstat
 3 files changed, 51 insertions(+), 51 deletions(-)

$ git diff -w --shortstat
 2 files changed, 2 insertions(+), 2 deletions(-)

# 想按文件看的话
$ git diff --numstat
30	30	a.js
20	20	b.js
1	1	c.js

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # a.js 从列表里消失了

$ git diff -w --stat
 b.js | 2 +-
 c.js | 2 +-
 2 files changed, 2 insertions(+), 2 deletions(-)

51 行对 2 行。光看这个比例就能定下该怎么对待这次改动。不过这里有个坑，--name-only 会忽略 -w。 想只取文件列表拿去做自动化的人，就卡在这儿。

$ git diff -w --name-only
a.js
b.js
c.js                                  # a.js 明明只改了空白也照样出现

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # 这边是准确的

# 要按文件可靠地分类，就用退出码
$ git diff --quiet -w -- a.js; echo $?
0                                     # 0 = 除了空白什么都没变
$ git diff --quiet    -- a.js; echo $?
1                                     # 1 = 字节确实变了
$ git diff --quiet -w -- c.js; echo $?
1                                     # 有真正的改动

$ for f in $(git diff --name-only); do
>   if git diff --quiet -w -- "$f"; then echo "  仅空白 : $f"; else echo "  真改动 : $f"; fi
> done
  仅空白 : a.js
  真改动 : b.js
  真改动 : c.js

最后这种 --quiet 配 -w 的写法在实际工作中最好用。答案以退出码给出，所以钩子或者 CI 里可以自动把只改了空白的文件筛掉。需要文件列表的话，取 git diff -w --numstat 的第三列就行。

git blame -w - 格式化工具吞掉历史的时候

空白改动造成的第二类损害不在 diff，而在 blame。想弄清某一行为什么长成这样才跑的 blame，结果每一行都指向半年前的格式化提交，那份历史等于被抹掉了。

为了验证，建一个三次提交的仓库。Alice 写逻辑，Bob 跑格式化工具，Carol 修一个真正的 bug。Bob 那次提交做的只是把制表符换成四个空格，把单引号换成双引号，行为一点没变。

$ git log --oneline
db3b770 fix: include zero total          <- Carol
007e2a5 style: run formatter over the repo   <- Bob
5c720df feat: aggregate rows             <- Alice

$ git blame --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
007e2a59 (Bob   2026-02-02 2)     total = 0
007e2a59 (Bob   2026-02-02 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# 七行里有五行成了 Bob 的。而 Bob 一个字的逻辑都没碰。

$ git blame -w --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# 三行回到了 Alice 名下，但引号变了的三行依旧是 Bob 的。

-w 的边界在这里显现得很清楚。-w 只忽略空白。 仅仅重新缩进的行救回来了，可同一次提交里引号字符变了的行不属于空白改动，所以还挂在 Bob 名下。而现实中的格式化工具几乎总是把空白和非空白一起改：引号风格、折行位置、尾随逗号、括号对齐都是。

也就是说，-w 抹不掉格式化提交。 只清理了一半的 blame 从某种意义上更糟，因为有一部分行回来了，会让人误以为事情已经办妥。真正的答案在别处。

.git-blame-ignore-revs - 把提交移出 blame

git 有一个功能，可以在计算 blame 时把指定的提交整个跳过。被跳过的提交所产生的行，责任会往前一次提交那边挪。按惯例在仓库根目录放一个叫 .git-blame-ignore-revs 的文件，把要跳过的提交 SHA 写进去。

$ cat .git-blame-ignore-revs
# 2026-02-02 全仓库执行格式化工具 (制表符 -> 四个空格，引号风格)
# 行为没有变化，blame 时跳过
007e2a5974bd7a4c76aba4ee206b690c1410c23d

# 方式一，只用一次 - 直接给出文件路径
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
^5c720df (Alice 2026-01-10 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
^5c720df (Alice 2026-01-10 6)         return {"total": total}
^5c720df (Alice 2026-01-10 7)     return {"total": 0}

# 方式二，长期使用 - 写进配置
$ git config blame.ignoreRevsFile .git-blame-ignore-revs
$ git blame --date=short report.py
                                      # 与上面完全相同的输出

# 方式三，不用文件，只指定一个提交
$ git blame --ignore-rev 007e2a5974bd7a4c76aba4ee206b690c1410c23d --date=short report.py
                                      # 同样是相同的输出

-w 时还有三行挂在 Bob 名下，这一次七行全部各归其位。Alice 六行，Carol 一行，就是她实际修过的那行。这才是这个文件真正的历史。

比较项git blame -w.git-blame-ignore-revs
忽略的对象空白差异指定的整个提交
引号风格、折行位置的改动抹不掉能抹掉
不做配置能否马上用可以用 --ignore-rev 可以
与全队共享各人都得自己加选项文件随仓库一起提交
是否需要人来挑提交不需要需要，SHA 要自己写
写错了会怎样没有影响把含真改动的提交放进去，历史会被扭曲

文件随仓库一起提交，这一点在实际工作中最重要。一个人加了 SHA，全队的 blame 就一起被修好了。GitHub 在 2022 年 3 月 24 日的更新日志里说明，blame 页面会识别仓库根目录下的 .git-blame-ignore-revs。也就是说，这一个文件能把本地 CLI 和网页两边一起理顺。

用 ignore-revs 时会卡住的地方

功能本身很简单，但第一次用会卡住几个点。下面这些都是实际复现确认过的。

# 1. SHA 必须写满 40 位
$ git rev-parse --short HEAD~1
007e2a5
$ echo 007e2a5 > short-revs
$ git blame --ignore-revs-file=short-revs report.py
fatal: invalid object name: 007e2a5
                                      # 缩写哈希会让 blame 直接失败

# 2. 可以给跳过的行留标记
$ git config blame.markIgnoredLines   true
$ git config blame.markUnblamableLines true
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df  (Alice 2026-01-10 1) def load(rows):
^?5c720d  (Alice 2026-01-10 2)     total = 0
^?5c720d  (Alice 2026-01-10 3)     for r in rows:
^?5c720d  (Alice 2026-01-10 4)         total += r["amount"]
db3b770e  (Carol 2026-03-05 5)     if total >= 0:
^?5c720d  (Alice 2026-01-10 6)         return {"total": total}
^?5c720d  (Alice 2026-01-10 7)     return {"total": 0}
                                      # 带问号的行 = 跨过被忽略提交推定出来的行

# 3. 怎样判断该把哪些提交放进去
$ git show --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 12 ++++++------
 1 file changed, 6 insertions(+), 6 deletions(-)

$ git show -w --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 6 +++---
 1 file changed, 3 insertions(+), 3 deletions(-)
                                      # 加了 -w 少掉一半，说明空白占比很大

第一个最常卡住。粘贴提交 SHA 时习惯性用了缩写哈希，blame 就根本跑不起来。用 git rev-parse HEAD 取出完整 SHA 再粘进去才稳妥。

  • 注释写在以 # 开头的行里。不写清楚某个提交为什么在列表里，几个月后就没人敢动这个文件了
  • 放进去之前先确认那个提交真的只有格式化。上面第 3 点的 git show -w --stat 就是用来做这个判断的。加了 -w 行数还是没少，说明那个提交里有真改动
  • 把混了真改动的提交放进列表，那处改动的作者就被永远藏起来了。这比 blame 被污染更糟
  • 打开 blame.markIgnoredLines 就能看出哪些行是推定值。第一次在团队里引入这个文件时打开它，解释起来会轻松很多
  • 这个文件只影响 blame。git log 和 git diff 都不受影响，所以历史并没有消失

文件末尾换行与 No newline at end of file

§4 那份输出的最后一行是 \ No newline at end of file。这个标记的意思是文件的最后一个字节不是换行符。它不是错误，而是在陈述事实。

这个标记之所以存在，根源在文本文件的定义。POSIX 把行定义为以换行符结尾的零个或多个字符，把文本文件定义为这样一串行的排列。照这个定义，没有换行符收尾的末尾片段严格来说不算一行。于是就会出现 wc -l 少数一行，或者把两个文件拼接时前一个的最后一行和后一个的第一行黏成一行的情况。

$ git show HEAD:eof.txt | tail -c 12 | xxd
00000000: 650a 7477 6f0a 7468 7265 650a            e.two.three.
$ tail -c 12 eof.txt | xxd
00000000: 6e65 0a74 776f 0a74 6872 6565            ne.two.three
                                      # 末尾少了一个 0a，就这一点差别

$ git diff
@@ -1,3 +1,3 @@
 one
 two
-three
+three
\ No newline at end of file
                                      # 看起来一模一样的行显示成先删后增

$ git diff --ignore-space-at-eol; echo "退出码 $?"
退出码 0                               # 被完全隐藏了
$ git diff -w
                                      # -w 同样没有输出
$ git diff --check; echo "退出码 $?"
退出码 0                               # --check 不把它当作错误

最后两行很重要。git diff --check 抓行尾空白，却抓不到缺失的文件末尾换行。所以别以为提交钩子里只挂了 --check 就连这个也拦住了。这一项应该交给编辑器配置来防。

换行符会把整个 diff 翻过来

换行符在 CRLF 和 LF 之间变动时，文件的每一行都会变成改动，因为每行都多出或少掉一个看不见的字节。CRLF 和 LF 当初为什么分岔、怎样用 .gitattributes 把它钉死，在讲换行符的那篇文章里另作了整理。这里只看它怎样污染 diff。

$ cat -A notes.txt                    # 整个文件转成 CRLF，只改一个单词
line one^M$
line two^M$
line THREE^M$                         <- 真正的改动只有这一处
line four^M$

$ git diff --stat
 notes.txt | 8 ++++----
 1 file changed, 4 insertions(+), 4 deletions(-)
                                      # 四行的文件被算成整个重写了

$ git diff
@@ -1,4 +1,4 @@
-line one
-line two
-line three
-line four
+line one
+line two
+line THREE
+line four
                                      # 屏幕上分不出哪一行才是真的

$ git diff --ignore-cr-at-eol
@@ -1,4 +1,4 @@
 line one
 line two
-line three
+line THREE
 line four                            # 缩到只剩一行

$ git diff -w
                                      # -w 结果相同，因为 CR 也是空白字符
  • git 有专为这种情况准备的 --ignore-cr-at-eol。范围比 -w 窄，因此更安全
  • GNU diff 那边有目的相同的 --strip-trailing-cr。§16 会实际确认
  • 根本对策是用 .gitattributes 把仓库的换行钉死。选项只是缓解症状，不是解决

从源头上不让它产生

到这里为止讲的都是把已经产生的噪声从屏幕上抹掉。更好的做法是不让噪声进入提交。这里有三层，各自拦截的位置不同。

第一层是编辑器。在仓库根目录放一个 .editorconfig，支持它的编辑器就会在保存时帮忙整理。各家编辑器的支持范围不同，所以这是约定而非强制。

$ cat .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = 4
trim_trailing_whitespace = true       # 去掉行尾空白
insert_final_newline = true           # 保证文件末尾有换行

[Makefile]
indent_style = tab                    # 这里制表符就是语法

[*.md]
trim_trailing_whitespace = false      # 行尾两个空格代表换行

第二层是提交前的检查。git diff --check 不用配置就能工作，发现问题时以退出码 2 结束，所以可以直接塞进钩子或 CI。

$ cat -A ws.txt
ok line$
trailing spaces here   $
trailing tab here^I$
 ^Ispace before tab$
$
$

$ git diff --check
ws.txt:2: trailing whitespace.
+trailing spaces here
ws.txt:3: trailing whitespace.
+trailing tab here
ws.txt:4: space before tab in indent.
+ 	space before tab
ws.txt:5: new blank line at EOF.
$ echo $?
2                                     # 钩子里可以直接用的退出码

$ git config --get core.whitespace
                                      # 为空 = 应用内置默认值
                                      # blank-at-eol, space-before-tab, blank-at-eof

第三层是应用时的纠正。别人发来的补丁带着行尾空白时，git apply --whitespace=fix 会在应用的同时把它去掉。

$ tail -3 patch.diff | cat -A
 ok line$
 clean tail$
+new line with trailing ws   $        <- 补丁里带着行尾空白

$ git apply --whitespace=fix patch.diff
patch.diff:8: trailing whitespace.
new line with trailing ws
warning: 1 line applied after fixing whitespace errors.

$ cat -A ws.txt
ok line$
clean tail$
new line with trailing ws$            <- 应用后空白已被去掉
手段拦截时机行尾空白末尾换行空格后跟制表符强制力
.editorconfig保存时去除保证间接取决于编辑器支持
git diff --check提交前检出检不出检出用退出码 2 在钩子里拦下
git apply --whitespace=fix应用补丁时去除不处理纠正由应用的一方选择
.gitattributes提交与检出时不处理不处理不处理仅对换行符强制

把格式化提交分开的习惯

即便把上面这些选项都记住了，效果最大的仍然不是工具，而是把提交分开的习惯。原因很简单，选项要靠审查者每次记住并加上，而已经分好的提交什么都不用记。

规则只有一句。格式化工具跑出来的结果要放进只装它的那一次提交，不和逻辑修改放在同一次提交里。这样做三件事会同时解决：审查者可以不打开格式化提交就跳过，blame 只需把那一个 SHA 放进 .git-blame-ignore-revs，出问题时要回退的范围也很明确。

# 格式化工具已经跑过并且和逻辑修改混在一起时的补救顺序
$ git stash                           # 先把当前工作放到一边
$ prettier --write .                  # 对整个仓库执行格式化工具
$ git commit -am "style: run formatter (no behaviour change)"
$ git rev-parse HEAD >> .git-blame-ignore-revs
$ git stash pop                       # 把逻辑修改重新取回来
$ git commit -am "fix: 实际的修改内容"

# 提交之前确认这次提交是不是真的只有格式化，一行搞定
$ git diff --cached --quiet -w && echo "仅空白" || echo "含真正的改动"
  • 引入格式化工具时，一次性跑遍整个仓库更好。按文件一点点跑会让格式化提交涨到几十个，忽略列表就没法管理了
  • 格式化提交的信息里要写明行为没有变化。对几个月后判断这次提交的人来说，那一句话就是全部依据
  • 分开提交不是对审查者的体贴，而是把历史留成可读状态的工作。审查几天就结束，历史要留好几年

没有 git 的地方 - GNU diff

像在部署服务器上比较两份配置文件这样，不在 git 仓库里的场合也很多。GNU diff 有同样的选项，名字也几乎一致。不过 -B 按 hunk 判断的行为也和 git 一模一样，这点顺带确认一下。

$ diff -u old.txt new.txt              # 不带选项
@@ -1,6 +1,7 @@
-alpha
-	beta = 1
-epsilon
+alpha
+    beta  =  1
+    epsilon
+

 gamma
-delta
+delta!

$ diff -u -b old.txt new.txt           # 只忽略空白数量的变化
@@ -1,6 +1,7 @@
 alpha
 	beta = 1
-epsilon
+    epsilon                           <- 原本没有的缩进留下来了
+

 gamma
-delta
+delta!

$ diff -u -w old.txt new.txt           # 完全忽略空白
@@ -2,5 +2,6 @@
 	beta = 1
 epsilon                               <- 这次消失了

+
 gamma
-delta
+delta!

$ diff -u -B old.txt new.txt           # 只忽略空行
@@ -1,6 +1,7 @@
-alpha
-	beta = 1
...                                   # 毫无效果。和 git 一样是按 hunk 的规则

$ diff -q -w -B old.txt new.txt; echo $?
Files old.txt and new.txt differ
1                                     # 0 = 相同，1 = 不同，2 = 出错
  • -u 是统一格式输出。会带上三行上下文，既便于人阅读，也能用 patch 应用
  • -b 和 -w 的区别与 git 完全一致，分歧点就在新增了缩进的 epsilon 那一行
  • -B 和 git 的 --ignore-blank-lines 一样按 hunk 判断，一旦和其他改动混在一起就没有效果
  • 如果掺了 CRLF，就把 --strip-trailing-cr 一起加上。不加的话每一行都会显示成不同
  • 要靠退出码判断时用 -q。输出缩成一行，在脚本里更好处理

空白带有含义的地方

把这篇文章的内容全部用上之后，最后还剩一个风险。把 -w 变成习惯，就会在空白即语法的文件里漏掉真正的改动。这不是假设，是能复现的事实。

$ git diff                            # 在 Python 文件里把一行挪到循环外面
@@ -2,7 +2,7 @@ def total(rows):
     s = 0
     for r in rows:
         s += r
-        print(s)
+    print(s)
     return s

$ git diff -w
                                      # 没有输出。-w 说什么都没变

$ git diff -w --stat
                                      # 这里也是空的

# 可实际行为是这样变的
$ python total.py                     # 修改前
1
3
6
$ python total.py                     # 修改后
6

输出从三行变成了一行。程序行为明明变了，git diff -w 却报告说什么都没变。因为在 Python 里缩进不是排版，它本身就是块结构。

对象空白的含义加上 -w 之后建议
Python缩进深度就是块结构把整块的移动全藏起来禁用 -w，需要时用 --ignore-space-at-eol
Makefile配方行开头必须是制表符藏住制表符变成空格的改动禁用 -w
YAML缩进就是嵌套结构藏住键被挪到另一个父节点下禁用 -w
Markdown行尾两个空格 = 换行藏住换行的丢失连 --ignore-space-at-eol 都有风险
Go、Java、C 系空白只是分隔符安全可以把 -w 当默认
字符串字面量、测试数据空白是数据的一部分藏住期望值的变化按文件作例外处理

实际工作中这样定基准比较稳妥。-w 只在开始审查、要清掉噪声时用，批准之前不带选项再看一遍。 第一遍是决定该看哪里，第二遍是确认有没有漏掉。一旦想把这两遍合成一遍，上表里的风险就全活过来了。

审查中怎样处理大批量格式化

大多数审查工具都有忽略空白的视图，打开它屏幕就清爽了，但只靠它还有遗留问题。给特定行加审查意见的功能通常以原始行号为基准，格式化一旦让行位移，之前意见的位置就对不上了。而且正如 §9 所见，blame 被污染不是审查页面的选项能解决的。

所以当大批量格式化和逻辑修改捆成一团上来时，请求拆分更合适。提请求时用数字而不是情绪或喜好作依据，对话会短很多。§8 的那些命令就能造出这些数字。

  • 把 git diff --shortstat 和 git diff -w --shortstat 两行原样贴上去。51 行对 2 行这样的对比不需要解释
  • 用 git diff -w --numstat 取出只改了空白的文件清单一并给出。那些文件的意思是没有东西可审
  • 请求的形式是拆分提交，不是打回重来。被读成不要用格式化工具，论点就跑偏了
  • 把拆出来的格式化提交的 SHA 加进 .git-blame-ignore-revs，这一步也放进同一个请求里。否则 blame 的问题还是留着
  • 反过来，纯格式化的提交要快速批准。既要求拆分又把那次提交压很久，下次就没人愿意拆了
  • 如果仓库里提交了格式化工具的配置并且 CI 会检查它，那么格式化提交的内容本身就不是给人审的。要审的只有配置文件有没有变

总结

空白噪声的问题分成两层：把已经产生的从屏幕上抹掉，和从一开始就不让它产生。前者靠四个选项基本就完事了。只抹行尾用 --ignore-space-at-eol，连缩进转换一起抹用 -b，连原本没有的缩进也抹掉用 -w，整理空行的提交用 --ignore-blank-lines。前三个是包含关系，只有最后一个性质不同。

blame 是另一个问题。§9 已经确认 -w 抹不掉格式化提交。真正的答案是把那次提交的完整 40 位 SHA 写进 .git-blame-ignore-revs，再设置 blame.ignoreRevsFile。因为文件随仓库一起提交，放进去一次全队就一起修好了。

而后一层，也就是从源头预防，最终分量更重。用 .editorconfig 在保存时整理，把 git diff --check 挂进提交钩子，格式化工具的结果用只装它的提交发出去。这三样做到了，前面那些选项基本就不必记了。只是最后还剩一条：在 Python、YAML 和 Makefile 面前必须放下 -w。在那些地方，空白不是排版，是代码。

未能确认的部分

  • --ignore-rev 和 --ignore-revs-file 从 git 哪个版本开始加入，没能通过一手资料确认。好几处写的是 2.23，但我没有直接打开发布说明比对，所以正文里没有写版本号。上面的输出全部出自 2.48.1
  • Makefile 的配方行开头不是制表符时会报的错误，没能直接复现。做实验用的 Git Bash 里没有 make。所以 §17 里 Makefile 那一行只写了规则，没有附上运行输出
  • .editorconfig 的各个键在不同编辑器上实际支持到什么程度没有确认。这个文件不是由 git 解释，而是由编辑器和插件解释的，各家工具的支持范围并不相同
  • 除 GitHub 之外的审查工具对 .git-blame-ignore-revs 的识别程度没有确认。§18 因此没有点名任何具体工具，只写了通用的应对
  • 所有输出都只来自 Windows 上的一套 Git Bash。Linux 或 macOS 上的其他 git 构建，尤其是 BSD 系的 diff，选项名称和输出都可能不同
