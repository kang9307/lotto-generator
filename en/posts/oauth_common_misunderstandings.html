Where OAuth Gets Misread - Delegated Authorization, Not Authentication

Four roles, four flows, and what the latest BCP removed from the list

Aug 24, 2026 Dev & Infra

When someone in a meeting says we added login with OAuth, the next half hour is fairly predictable. One person is cracking open an access token to pull a user identifier out of it. Another has parked that token in browser storage. A third is hiding scopes in the UI and calling it access control. All three are common, and all three grow from the same root.

The root is in the name of the spec. The formal title of OAuth 2.0 is The OAuth 2.0 Authorization Framework, and the word authentication does not appear in it. That is not an accident. The problem this framework set out to solve was never who is this person but how far may this application reach into that resource. Miss that one line and every decision stacked on top of it drifts in order.

What follows walks the places where the drift shows up, in the order the specs lay them out. Each section covers what the norm is and what guarantee is lost when the norm is broken, and stops there. How an attack is carried out is out of scope.

1. The biggest misreading - OAuth is not an authentication protocol

RFC 6749 is a Proposed Standard from October 2012. Its abstract defines what the framework does as enabling a third-party application to obtain limited access to an HTTP service, either on behalf of a resource owner or on the application's own behalf. Either way the output is access. Not proof of identity.

That settles what an access token is. An access token is built to be presented to a resource server, not to be read by the client. Whatever sits inside it is information about how far this request may be honored, not about who is in front of the screen right now. The security considerations of RFC 6749 carry a separate warning about treating access tokens as proof of the resource owner's identity.

If login is the goal, one more layer goes on top. OpenID Connect Core 1.0 describes itself as a simple identity layer on top of the OAuth 2.0 protocol. What that layer introduces is the ID Token, a security token that contains claims about the authentication of an end user. It takes the form of a JWT and requires these claims.

  • iss - issuer identifier for the issuer of the response
  • sub - subject identifier, locally unique within the issuer and never reassigned
  • aud - audience the ID Token is intended for, including the OAuth client identifier
  • exp - expiration time on or after which the ID Token must not be accepted
  • iat - time at which the JWT was issued

The core of this section is that the two tokens have different recipients. The access token goes to the resource server, the ID Token goes to the client. When profile data is needed, OpenID Connect defines the UserInfo endpoint, which is a protected resource that returns authorized information about the end user when presented with an access token. Even reading a profile happens in the grammar of authorization.

How to decide. If what your service needs is permission to put an event on someone's calendar over there, OAuth is the whole answer. If it needs to pin down which account in your service this person is, OpenID Connect is required. When both needs are present, use both layers. The moment one access token is asked to do both jobs is where the trouble starts.

2. There are four roles, and trust does not flow one way

RFC 6749 splits the participants into four. Getting the vocabulary exact here makes every later section easier.

  • Resource owner - an entity capable of granting access to a protected resource
  • Client - an application making protected resource requests on behalf of the resource owner and with its authorization
  • Authorization server - the server issuing access tokens to the client after successfully authenticating the resource owner and obtaining authorization
  • Resource server - the server hosting the protected resources, capable of accepting and responding to protected resource requests using access tokens

What usually gets blurred is the direction of trust. The resource owner trusts exactly one party, the authorization server, and that is the only place a password or a second factor should ever be typed. The client does not trust the resource owner; it trusts what the authorization server handed back. The resource server likewise trusts the validity of a token the authorization server issued, not the client presenting it. The four parties do not trust each other symmetrically, and that asymmetry is the skeleton of the spec.

The other axis is client type. A confidential client can keep its own credentials confidential; a public client cannot. A backend running on a server is the former; a single-page application in a browser or a native app installed on a user device is the latter. Most later norms branch on this axis. Whether the client credentials grant is usable, whether PKCE is required or recommended, whether rotation is demanded of refresh tokens, all of it hangs here.

Native apps get one more norm. RFC 8252 is a Best Current Practice from October 2017, carrying the number BCP 212. The point is that authorization requests from native apps should be made only through external user-agents, primarily the user's browser, rather than embedded ones. Read against the trust direction above, the reason is plain. An embedded web view is a surface the client owns, and the premise that the resource owner only ever gives credentials to the authorization server does not hold on that surface.

3. What actually differs between the flows

Memorizing flows is slower than holding on to the two questions that separate them. First, is the resource owner present right now. Second, can the client keep a secret. The answers pick the flow.

Flow Spec and status Is the resource owner present Client type Where it is used
Authorization code flow RFC 6749 (Proposed Standard, 2012-10) Yes, consenting in a browser Confidential and public Nearly every case where a person is involved
PKCE (extension of the code flow) RFC 7636 (Proposed Standard, 2015-09) Yes Required for public, recommended for confidential Adding defense against code interception and injection
Device authorization grant RFC 8628 (Proposed Standard, 2019-08) Yes, but approving on another device Mostly public Smart TVs, consoles, printers with limited input
Client credentials grant RFC 6749 (Proposed Standard, 2012-10) No, no person involved Confidential clients only Server-to-server calls a service makes in its own name

3.1 Why the authorization code flow has two steps

The first thing that snags people about the authorization code flow is why it splits in two. A browser redirect delivers an authorization code, and that code is then sent back to the authorization server to be exchanged for an access token. Two round trips where one would seem to do.

The reason is that the two round trips run on different channels. The first goes through the user's browser. Redirect URLs appear in the address bar, land in browser history, and pass through several layers. The second is a direct exchange between the client and the authorization server. Keeping the access token on the second path alone means the token itself never becomes a trace on the first path. That separation is why the authorization code flow is the one still standing.

3.2 The device flow and the client credentials flow

The device authorization grant exists for devices that cannot open a browser. The device shows the user a code, and the user completes approval on a separate device such as a smartphone. Meanwhile, rather than requiring two-way communication between the client and the user agent, the device polls the authorization server repeatedly. Instead of making someone type a password with a remote control, the act of authorizing is moved to a different device entirely.

The client credentials grant is a different animal. There is no resource owner here. It is used when the client is reaching resources under its own control, or resources arranged with the authorization server in advance. So the spec nails it down: the client credentials grant type must only be used by confidential clients. The common misuse is pulling user data through this flow. Do that and the party who granted anything disappears from the structure, leaving a single service account in the audit trail.

4. The two flows that came off the list - implicit and password grant

RFC 9700 arrived in January 2025. Its title is Best Current Practice for OAuth 2.0 Security and its status is Best Current Practice, BCP 240. It updates RFC 6749, RFC 6750, and the older threat model document RFC 6819. If you are designing OAuth today, the baseline is that document, not 6749.

The most visible thing it did was take two flows off the list.

4.1 The implicit grant

RFC 9700 states that clients should not (SHOULD NOT) use the implicit grant, and groups other response types that issue access tokens in the authorization response with it, leaving an exception for cases where access token injection into the authorization response is prevented. Two grounds are given.

  • It is vulnerable to access token leakage and access token replay
  • It has no standardized way to sender-constrain the token

The same document gives the alternative in one line: use the code response type. Held against the channel separation above, the reasons overlap. The implicit flow puts the token on the front channel, which re-merges exactly what section 3.1 worked to keep apart.

4.2 The resource owner password credentials grant

The language here is stronger. RFC 9700 says this grant must not (MUST NOT) be used. Four reasons are given.

  • It insecurely exposes the credentials of the resource owner to the client
  • It increases the attack surface
  • It trains users to enter their credentials outside the authorization server
  • It is not designed to work with two-factor authentication

The third reason is the most practical one. Training users is not a technical vulnerability, it is a point about habit. A user who has learned that typing a password into an app screen is normal has lost the basis for telling whose screen it is. The fourth reason is more direct still: a structure that receives a credential pair wholesale leaves no room for a second factor to fit in. That thread continues in the walkthrough of two-factor methods.

For context, work called OAuth 2.1 is in progress. Revision 15 is dated March 2, 2026, its status is Internet-Draft, and it consolidates RFC 6749 and RFC 6750 while leaving both the implicit grant and the password grant unspecified. A draft is not a standard, though. If you need normative footing today, cite RFC 9700.

5. What PKCE prevents - no longer a public-client story

RFC 7636 is titled Proof Key for Code Exchange by OAuth Public Clients. It is a Proposed Standard from September 2015, and its abstract targets one problem: public clients using the authorization code grant are susceptible to authorization code interception attacks.

The mitigation is what the name says. The client creates a dynamically generated cryptographic key per request and uses it to correlate the authorization request with the token request. A value derived from that key rides along with the authorization request, the original value goes with the token request, and the authorization server compares them. The result is that a party holding only the code cannot redeem it for a token.

That much is the old understanding. What changed is the scope of application. RFC 9700 lays it out this way.

  • Public clients must use PKCE (MUST).
  • Use of PKCE is recommended for confidential clients too (RECOMMENDED), because it provides strong protection against misuse and injection of authorization codes.
  • When an attacker attempts to inject a stolen authorization code, the verifier check fails and the exchange does not complete at the token endpoint.
  • The same document notes that PKCE provides protection against CSRF even in the presence of strong attackers.

In one sentence: PKCE moved from being a patch for clients that cannot hold a secret to being a defense against code injection as a threat class. Concluding that a backend does not need PKCE because it guards its client secret well is applying a threat model that is one generation out of date.

The companion norm in this area is redirect URI matching. RFC 9700 requires that the authorization server utilize exact string matching (MUST). The only exception is port numbers in localhost redirect URIs of native apps, and pattern matching was explicitly rejected on grounds of complexity and security issues. When matching is loose, the set of destinations an authorization response can return to grows wider than the client intended.

Clients wired to more than one authorization server pick up one more norm. RFC 9207 is a Proposed Standard from 2022 that defines an iss parameter carrying the authorization server's issuer identifier explicitly in the authorization response, as a countermeasure to mix-up attacks. RFC 9700 requires the client to store the issuer it sent each request to, compare it with the identifier received in the response, and abort the interaction on a mismatch.

6. Where the token goes - browser storage versus cookies

This question has no single right answer, and the specs say so. RFC 10017, published in August 2026 under the title OAuth 2.0 for Browser-Based Applications, is a Best Current Practice sharing the number BCP 212. It sets out three architectures a browser-based application can adopt.

  • Backend-For-Frontend (BFF) - tokens stay server-side and the browser talks to it over a session cookie
  • Token-Mediating Backend - the backend acts as a confidential client but hands the access token down to the browser
  • Browser-Based OAuth 2.0 Client - the code in the browser is the client

The sentence the document attaches while placing all three side by side is the yardstick: each of these architectural patterns offers a different trade-off between security and simplicity. It recommends the BFF for sensitive applications while acknowledging legitimate uses for the others.

One more sentence anchors how to read the trade-off: the malicious JavaScript code has the same privileges as the legitimate application code. Once script execution is compromised, there is no browser-side storage a script cannot read. Difficulty of access does vary, and the document notes that universally accessible storage areas, such as Local Storage, are easier to access from malicious JavaScript than more isolated storage areas.

Storage location When script execution is compromised Sent automatically What comes with it
Local Storage In reach. Classified as an easier area to access No Blocking script injection becomes the only real line
Session Storage In reach. Tab-scoped lifetime is not access control No UX design for the lack of cross-tab sharing
JavaScript in-memory variable In reach. It lives in the same execution context No A re-acquisition path on every reload
HttpOnly and Secure cookie (BFF) Session state cannot be read directly by script Yes, the browser attaches it Cross-site request defense because of that automatic send

The norms on the BFF side are explicit. The BFF must enable the Secure flag and the HttpOnly flag (MUST) for its cookies, and the document explains that HttpOnly cookies prevent the attacker from directly accessing the session state. The cost on the other side is just as clear. Because the browser attaches cookies on its own, a separate axis that asks whether this request originated from our own surface becomes necessary. That calculation is worked through with cookie transmission rules in the piece on trust boundaries and web security controls.

On the token-mediating backend the document writes both sides too. The backend must act as a confidential client (MUST), yet the moment the access token goes down to the browser it becomes vulnerable to token theft by malicious browser-based code. Whichever architecture you pick, the risk is not removed but relocated.

7. Scope and least privilege - where scope is actually enforced

RFC 6749 defines scope as a list of space-delimited, case-sensitive strings. The norm that follows is easy to miss: the authorization server may fully or partially ignore the scope requested by the client, based on its own policy or the resource owner's instructions. And when the issued scope differs from the requested one, the server must include the scope response parameter to inform the client of the actual scope granted.

The conclusion that falls out of that pair matters in practice. Scope is a request, not a guarantee. If client code is written on the assumption that we asked for these three, so we have these three, that assumption stops being true the moment the authorization server trims one. What you read is not the request list but the scope in the response.

Then the more important question: where is scope enforced? At the resource server. RFC 9700 puts it this way: every resource server is obliged to verify, for every request, whether the access token sent with that request was meant to be used for that particular resource server. The same section asks that the token's own reach be narrowed: access tokens should be audience-restricted to a specific resource server (SHOULD) or, if that is not feasible, to a small set of resource servers. Targeting can be expressed through the scope parameter or through the resource parameter of RFC 8707, the document adds.

What breaks here. Reading scopes in the frontend and hiding a button is guidance, not enforcement. If the resource server does not check the token's audience and reach on every request, that endpoint is open whether the button is on screen or not. Without audience restriction, a token issued for a different resource server passes straight through. Least privilege is not about writing shorter scope strings; it is about placing the check at the resource server.

8. Refresh tokens and rotation - what detection really means

Start with the requirement as written. Refresh tokens issued to public clients must be sender-constrained or use refresh token rotation (MUST). One or the other. On the confidential side, RFC 6749 already requires that refresh tokens only be usable by the client they were issued to.

The sender-constraining mechanisms the document names are mutual TLS and DPoP. DPoP is RFC 9449, a Proposed Standard from 2023, which sender-constrains tokens with a proof-of-possession mechanism at the application level. Its abstract states that the mechanism allows for the detection of replay attacks with access and refresh tokens. Why such a device is needed at all becomes clear back at the definition in RFC 6750: a bearer token grants access to associated resources without demonstrating possession of a cryptographic key. Whoever holds it is the authorized party.

The rotation principle is written out in the document. If a refresh token is compromised and subsequently used by both the attacker and the legitimate client, one of them will present an invalidated refresh token, which will inform the authorization server of the breach. The next sentence matters even more in practice: the authorization server cannot determine which party submitted the invalid refresh token, but it will revoke the active refresh token.

Read together, the character of rotation comes through. Rotation does not prevent theft. It detects the moment a stolen token is used and, unable to tell the parties apart, cuts both. Two design obligations follow.

  • The legitimate user is cut off as well. Detection means a re-login is required, and if that experience is not designed, a security control reads as an outage
  • It only holds if the client reliably stores the new token. A client that fails to persist the new refresh token from a refresh response and reuses the old one becomes the party presenting an invalid token. Where several requests may refresh at once, a condition to funnel refreshes through one path is newly attached

The client-side storage problem is dug into from a command-line angle in the piece on designing CLI authentication.

9. Where validation belongs - what a client cannot do for you

Two tokens means two validating parties. Swapping them is where the accidents happen.

9.1 Access tokens are validated by the resource server

The RFC 9700 sentence again: every resource server is obliged to verify, for every request, whether the access token sent with that request was meant to be used for that particular resource server. How that verification is done splits by token format.

  • If it is a JWT - RFC 9068, a Proposed Standard from 2021, defines the required and optional claims and the validation rules for issuing OAuth 2.0 access tokens in JWT format. The profile exists precisely because proprietary JWT token implementations had broken interoperability
  • If it is opaque - RFC 7662, a Proposed Standard from October 2015, defines introspection, where a protected resource asks the authorization server whether a token is active and what metadata it carries. Working regardless of whether information is embedded in the token is the design intent

9.2 ID Tokens are validated by the client

OpenID Connect Core 1.0 enumerates what a client must check in its ID Token validation section.

  • Does the issuer match exactly
  • Does the audience contain this client's own identifier
  • Is the current time before the expiration
  • If a nonce was sent with the authorization request, does the value match
  • Is the signature valid under keys provided by the issuer

9.3 So what a client must not do

There is nothing wrong with code in the browser decoding a token. Checking whether expiry is near so a refresh can be queued, or painting a user's name on screen, are ordinary uses. The problem is using that decoded result as the basis for an authorization decision.

Two reasons. First, the sentence from section 6 holds here too: code running in the browser sits on the same privileges as malicious code, so a signature check that code performed can be neutralized in the same execution context. Second, the server has no way of knowing what the browser verified. What arrives at the resource server is a request and a token, nothing else.

So signature verification, issuer checks, audience checks, and expiry checks belong to whoever hands something over on the strength of that token. For access tokens that is the resource server; for ID Tokens it is the client server that mints a session from them. Decoding in the browser is a display convenience, not a control.

10. Common wrong combinations - what breaks in each

The table below is not a list of prohibitions. It maps each combination to the guarantee it gives up, in the words of the specs.

Combination What breaks in it Governing spec
Using an access token as proof of identity No basis to confirm who it was issued for or after what authentication RFC 6749 security considerations, OpenID Connect Core 1.0
Keeping the implicit flow The token rides in the authorization response with no standard way to sender-constrain it RFC 9700 (SHOULD NOT)
Password grant plus a two-factor requirement The grant itself was not designed to work with two-factor authentication RFC 9700 (MUST NOT)
Public client without PKCE No defense at all against code interception or code injection RFC 7636, RFC 9700 (MUST for public clients)
Allowing partial redirect URI matches The set of destinations an authorization response can reach widens beyond intent RFC 9700 (exact string matching MUST)
Refresh token in the browser without rotation No point at which theft is detected and none at which the sender is bound RFC 9700, RFC 10017
Multiple authorization servers with no issuer check No basis to establish which authorization server a response came from RFC 9207, RFC 9700
Resource server not checking token audience A token issued for another resource server passes straight through RFC 9700 (verification duty on every request)
Authorizing a native app in an embedded web view The premise that credentials go only to the authorization server does not hold RFC 8252 (BCP 212)
Enforcing scope only in the UI If the enforcement point is not the resource server, the endpoint stays open RFC 6749 scope definition, RFC 9700
Reaching user data through the client credentials grant The granting party disappears and audit records collapse to a service account RFC 6749 (confidential clients only, MUST)

What I could not confirm

  • The basis for this article is normative text in the RFCs and in OpenID Connect Core 1.0, and nothing else. How any individual authorization server product or library implemented those norms was not examined, and no claim is made about whether a particular implementation conforms
  • OAuth 2.1 is an Internet-Draft, revision 15, dated March 2, 2026. A draft is not a standard and can change before publication. Only its editorial direction, leaving the implicit and password grants unspecified, is cited here; none of its detailed provisions are
  • The resource parameter of RFC 8707, which RFC 9700 mentions as a targeting mechanism, is referenced only through that citation. The source document was not opened
  • The specification text for mutual-TLS certificate-bound tokens was not opened. What was confirmed is only that RFC 9700 names mutual TLS and DPoP as the two sender-constraining mechanisms
  • No trustworthy public statistics on the actual adoption share of each flow were found, which is why no claim of the form most services do it this way appears anywhere in this article

The order to read the documents in

Reading the specs front to back costs a lot of hours. The order below fixes the vocabulary first, then overwrites it with the current baseline.

  1. The roles and terminology section of RFC 6749, plus the authorization code flow section. This is where the four roles and the parameter names come from. Every other document is written in that vocabulary
  2. RFC 6750. A short check on what a bearer token does not guarantee. Section 8 starts from here
  3. RFC 7636. PKCE. Short, with a crisply stated problem
  4. RFC 9700 (BCP 240). Today's baseline. It updates 6749, 6750, and 6819. Read 6749 first and this second, or you will not see what came off the list. Reversing the order hides the reasoning
  5. Whichever one matches your situation: RFC 10017 for browser apps, RFC 8252 for native apps, RFC 8628 for input-constrained devices
  6. If login is the goal, the ID Token and ID Token validation sections of OpenID Connect Core 1.0
  7. If token format and validation are the issue, whichever of RFC 9068 or RFC 7662 matches your token format
  8. With multiple authorization servers, RFC 9207; to move past bearer tokens, RFC 9449; for endpoint discovery, RFC 8414

Three claims to close on. First, OAuth is a delegated authorization spec and login is a separate layer that sits on top of it; the name of the spec already says so. Second, where you placed the check is what the control actually is; scope and token validation are guidance when done on screen and enforcement only when done at the resource server. Third, the baseline today is RFC 9700, not RFC 6749. Designing from the 2012 document alone means starting out carrying everything that came off the list in the thirteen years since.
