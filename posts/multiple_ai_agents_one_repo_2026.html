이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: AI 에이전트 여러 개를 한 레포에 풀어놨더니 생긴 일

2026년 7월 기준, "코딩 에이전트 하나를 붙여 놓고 지켜본다"는 워크플로우는 이미 낡은 이야기가 됐다. Claude Code, Codex, Cursor 같은 도구들이 여러 세션을 동시에 띄우는 것을 기본 기능으로 지원하면서, 개발자들은 자연스럽게 "에이전트를 여러 개 풀어놓고 병렬로 돌리면 더 빠르지 않을까"라는 질문에 도달했다. 최근 GeekNews에도 이 실험을 직접 해본 사람의 경험담이 올라왔다. 여러 코딩 에이전트를 한 저장소에서 동시에 돌렸더니 브랜치가 서로의 작업을 덮어쓰고, 어디에도 속하지 않는 고아 커밋이 쌓이고, 스테이징 영역이 뒤섞이는 혼란을 겪었다는 내용이다.

이 글은 그 경험담을 그대로 옮기는 대신, 왜 이런 혼란이 구조적으로 발생할 수밖에 없는지, 그리고 실제로 통하는 격리·조율 패턴이 무엇인지를 운영 관점에서 정리한다. 결론부터 말하면 문제는 에이전트의 능력이 아니라 여러 실행 주체가 하나의 가변 상태(워킹 디렉토리)를 공유한다는 아키텍처 자체에 있다. 이는 병렬 프로그래밍에서 수십 년간 반복돼 온 공유 상태 문제와 본질적으로 같다.

1. 병렬 에이전트가 매력적인 이유 - 속도와 분업

1.1 속도: 여러 작업을 동시에 진행한다는 감각

에이전트 하나만 돌리면, 그 에이전트가 계획을 세우고 코드를 쓰고 테스트를 돌리는 동안 개발자는 기다린다. 반면 에이전트 서너 개를 동시에 붙이면 - 하나는 버그 수정, 하나는 리팩토링, 하나는 테스트 보강 - 체감 처리량이 눈에 띄게 늘어난다. 격리 구조를 제대로 갖춘 팀에서는 48GB 메모리의 맥 한 대에서 열두 개 세션을 동시에 돌리며 메인 브랜치에 충돌 없이 병합했다는 사례도 보고된다.

1.2 분업: 관심사를 에이전트 단위로 쪼갠다

두 번째 매력은 분업이다. 사람 팀에서 기능별로 담당자를 나누듯, 에이전트도 모듈·레이어·티켓 단위로 나눠 맡길 수 있다. 프런트엔드 에이전트, 백엔드 에이전트, 테스트 에이전트를 따로 굴리면 작은 팀을 꾸린 듯한 효과를 기대하게 된다.

2. 실제로 부딪히는 문제들

2.1 공유 워킹트리 충돌

가장 먼저 부딪히는 문제는 단순하다. 에이전트 여러 개가 같은 디렉토리에서 파일을 동시에 쓰면, 한 에이전트가 저장한 내용을 다른 에이전트가 덮어쓰거나, 아직 저장 중인 파일을 다른 에이전트가 읽어 반쯤 완성된 코드를 기준으로 다음 작업을 이어간다.

2.2 브랜치·커밋 경합 - 가로채기와 고아 커밋

git은 원래 한 사람이 한 워킹 디렉토리에서 작업한다는 전제로 설계됐다. 에이전트 여러 개가 같은 체크아웃에서 브랜치를 전환하면, 한 에이전트가 A 브랜치에서 작업 중인데 다른 에이전트가 B로 전환해버리는 브랜치 가로채기가 생긴다. 이 상태에서 커밋하면 의도한 브랜치가 아닌 곳에 커밋이 쌓이거나, 심하면 어느 브랜치에도 연결되지 않은 고아 커밋(detached HEAD 상태의 커밋)이 만들어진다.

2.3 스테이징 영역 오염

더 골치 아픈 것은 스테이징(인덱스) 오염이다. 한 에이전트가 git add로 자기 변경 사항을 스테이징해둔 사이, 다른 에이전트가 같은 인덱스에 자신의 임시 파일이나 관련 없는 수정 사항을 함께 add해버리면, 다음 커밋에 의도치 않은 변경이 뒤섞여 들어간다. 리뷰어 입장에서는 하나의 커밋 안에 서로 다른 작업 두세 개가 뒤엉켜 있어 되돌리기(revert)도 어려워진다.

2.4 컨텍스트 간섭과 중복 작업

에이전트는 작업을 시작할 때 현재 코드 상태를 읽어 컨텍스트를 구성한다. 다른 에이전트가 그 순간 파일을 바꾸고 있으면, 이미 지나간 상태를 기준으로 계획을 세우게 된다. 그 결과 두 에이전트가 같은 버그를 각자 다른 방식으로 고치거나, 이미 삭제된 함수를 다시 호출하는 코드를 만드는 등 중복·모순 작업이 발생한다.

2.5 머지 지옥

문제를 방치한 채 병렬 작업을 계속하면, 마지막에는 서로 얽힌 변경 사항 여러 개를 한꺼번에 병합해야 하는 상황에 몰린다. 에이전트별 diff가 겹치는 파일에서 충돌하고, 충돌 해결 자체를 다시 에이전트나 사람이 맡아야 하니 병렬화로 아낀 시간을 병합 단계에서 그대로 반납하는 역설이 벌어진다.

3. 왜 이런 일이 생기나 - 원자성과 격리의 부재

근본 원인은 두 가지로 압축된다. 첫째, 에이전트는 서로의 상태를 모른다. 각 에이전트는 자기 세션 안에서만 계획을 세우고 실행하며, 다른 에이전트가 같은 순간 같은 파일을 만지고 있다는 사실을 알 방법이 없다. 둘째, 파일 시스템과 git 워킹 디렉토리에는 원자성(atomicity)과 격리(isolation)가 기본으로 보장되지 않는다. 데이터베이스라면 트랜잭션이 이 문제를 막아주지만, 로컬 파일과 git 인덱스에는 그런 장치가 없다. 결국 여러 병렬 프로세스가 락 없이 같은 자원에 쓰기 접근을 하는, 동시성 이론에서 이미 오래전에 이름 붙여진 경쟁 상태(race condition) 문제를 코딩 에이전트가 새로운 얼굴로 재현하고 있는 셈이다.

4. 격리·조율 패턴 - 실제로 통하는 것들

4.1 에이전트별 git worktree·브랜치 분리

2026년 현재 가장 널리 자리 잡은 해법은 git worktree다. worktree는 하나의 .git 저장소를 공유하면서도 에이전트마다 완전히 독립된 워킹 디렉토리와 인덱스를 갖게 해준다. Claude Code는 --worktree 플래그로 저장소 루트의 .claude/worktrees/ 아래에 worktree-<n> 브랜치를 자동 생성하는 기능을 제공하고, Codex와 Cursor도 유사한 병렬 세션 격리를 네이티브로 지원한다. 파일 시스템 수준에서 충돌 여지 자체를 없애는 방식이라 가장 먼저 적용해볼 만하다.

4.2 컨테이너·샌드박스 격리

worktree가 파일 충돌을 막아준다면, 컨테이너·샌드박스는 한 걸음 더 나아가 실행 환경 자체를 격리한다. Docker 컨테이너나 devcontainer, 또는 마이크로VM으로 에이전트를 감싸면 파일뿐 아니라 프로세스·네트워크·자격 증명까지 서로 침범하지 못한다. Codex CLI는 기본값으로 네트워크 접근을 막는 OS 수준 샌드박스를 내장한 예다. 보안·권한이 중요한 조직일수록 worktree만으로는 부족하고 이 층이 필요하다.

4.3 작업 큐와 락

파일이나 모듈 단위로 락을 걸어, 한 에이전트가 특정 영역을 작업 중이면 다른 에이전트가 같은 영역에 손대지 못하게 막는 방식이다. 작업 큐에 티켓을 쌓아두고 에이전트가 하나씩 꺼내 처리하게 하면, 동시에 같은 파일을 여러 에이전트가 집는 상황 자체를 줄일 수 있다.

4.4 오케스트레이터 - 허브 앤 스포크

에이전트들이 서로 직접 소통하지 않고, 중앙 오케스트레이터가 작업을 쪼개 배분하고 결과를 취합하는 구조다. 이 방식은 에이전트들이 부분적인 정보만으로 서로 겹치는 변경을 만들어내는 "메시(mesh)" 구조의 위험 - 여러 에이전트가 대등하게 정보를 주고받다가 의미적으로 모순된 코드를 동시에 만들어내는 상황 - 을 피하는 데 유리하다.

4.5 파일 소유권 경계

사람 팀의 코드 오너십처럼, 에이전트별로 건드릴 수 있는 디렉토리·모듈을 명시적으로 나누는 것이다. "이 에이전트는 API 레이어만, 저 에이전트는 프런트엔드 컴포넌트만" 식으로 경계를 미리 그으면 worktree가 없어도 충돌 표면적이 크게 줄어든다.

4.6 PR 단위 통합과 CI 게이트

격리된 브랜치에서 작업이 끝났다고 바로 메인에 합치지 않는다. 각 에이전트의 결과물은 PR로 올라오고, CI가 빌드·테스트·린트를 통과시킨 것만 병합 대상이 된다. 브랜치를 공유 상태로 두지 말고 병합 시점에만 충돌을 해소한다는 원칙은 실시간 동기화보다 훨씬 다루기 쉽다. 여기에 agent/<티켓>-<설명> 같은 브랜치 네이밍 규칙을 더하면, 리뷰어가 diff를 열기 전부터 이것이 에이전트 산출물임을 알고 검토 강도를 조절할 수 있다.

패턴막는 문제도입 비용비고
git worktree/브랜치 분리파일·브랜치·스테이징 충돌낮음가장 먼저 적용할 기본기
컨테이너/샌드박스자격증명·네트워크·프로세스 침범중간보안 민감 작업에 추가
작업 큐·락동시 파일 점유중간대규모 병렬일수록 효과
오케스트레이터(허브앤스포크)메시 구조의 의미적 충돌높음에이전트 수 많을 때
PR 단위 통합 + CI 게이트검증 안 된 코드의 메인 유입낮음모든 조합에 필수

5. 어제 이야기와 연결 - 감독 부담은 병렬화로 더 커진다

이전 글 루프 안의 인간은 지쳤다에서 다룬 감독 피로 문제는 에이전트를 병렬로 늘릴수록 더 날카로워진다. 에이전트 하나를 감독하는 것도 지치는 일인데, 서너 개를 동시에 감독하면 검토해야 할 diff·PR·로그가 그만큼 늘어난다. 격리 패턴은 충돌은 줄여주지만 검토 총량 자체는 줄여주지 못한다. 그래서 병렬화를 늘릴수록 CI 게이트·자동 린트·자동 테스트처럼 사람이 손대지 않아도 되는 1차 필터를 함께 강화해야, 병렬화의 이득이 감독 피로에 잠식되지 않는다.

6. 툴 관점 - worktree 자동화와 오케스트레이션

수작업으로 worktree를 만들고 지우는 것도 금방 번거로워진다. 그래서 2026년 들어 worktree 생성·정리·포트 분리·브랜치 명명까지 자동화해주는 래퍼 도구들이 여럿 나왔다. Claude Code 데스크톱 앱은 새 세션마다 worktree를 자동으로 만들어주고, 일부 오픈소스 도구는 Claude Code·Codex·Gemini를 나란히 각자의 worktree에서 띄워주는 식으로 여러 벤더의 에이전트를 한 화면에서 조율한다. 오케스트레이션 쪽에서는 작업 분배와 PR 취합을 자동화하는 계층이 붙는 추세다. 도구를 고를 때 기준은 하나다. "이 도구가 격리를 대신 강제해주는가, 아니면 격리를 사람이 계속 신경 써야 하는가."

7. 언제 병렬이 득이고 언제 실인가

병렬이 유리한 경우는 작업 단위가 서로 독립적일 때다. 서로 다른 모듈, 서로 다른 파일, 서로 다른 티켓처럼 겹칠 일이 애초에 적은 작업이면 worktree 격리만으로도 충돌이 거의 나지 않는다. 반대로 병렬이 손해인 경우는 여러 에이전트가 같은 핵심 파일(공용 설정, 공유 타입 정의, 진입점)을 동시에 건드려야 하는 작업이다. 이럴 때는 병렬화보다 순차 처리나 단일 에이전트에 넓은 컨텍스트를 주는 편이 오히려 빠르다. 신생 코드베이스나 아키텍처가 자주 바뀌는 초기 단계에서도 병렬은 득보다 실이 크다. 경계가 아직 안 잡혔기 때문이다.

8. 실무 체크리스트

  • 에이전트마다 별도 git worktree·브랜치를 배정했는가
  • 브랜치 네이밍에 에이전트 산출물임을 표시했는가(agent/... 등)
  • 공유 브랜치(main)에 에이전트가 직접 커밋·푸시하지 못하게 막았는가
  • 파일·모듈 단위 소유권 경계를 사전에 문서화했는가
  • 병합은 반드시 PR + CI 게이트를 거치는가
  • 보안·자격 증명이 얽힌 작업은 컨테이너·샌드박스로 한 겹 더 격리했는가
  • 동시에 몇 개까지 돌릴지 상한을 정했는가(무제한 확장은 곧 감독 붕괴로 이어진다)
  • 리뷰 총량이 감당 가능한 수준인지 주기적으로 점검하는가

여러 에이전트를 한 레포에 풀어놓는 것 자체는 틀린 방향이 아니다. 문제는 풀어놓기만 하고 격리는 안 하는 운영이다. git worktree로 파일 충돌을 없애고, 필요하면 컨테이너로 실행 환경까지 나누고, PR과 CI 게이트로 병합 시점의 충돌만 해소하는 구조를 갖추면 병렬 에이전트는 실제로 처리량을 늘려준다. 다만 그 이득은 격리 인프라를 갖추는 수고, 그리고 늘어난 검토 총량을 감당할 체력과 맞바꾸는 것이다. 그 검토 총량을 다뤄낼 판단력은 시니어 개발자 프리미엄에서 다룬 것과 같은 종류의 시스템적 사고에 가깝다. 그 사실을 분명히 알고 시작해야 한다.
