git bisect - 用二分查找定位引入 Bug 的那次提交

1,000个提交只用10次测试。bisect run 自动化与退出码约定，skip、terms、合并历史，全部用实际输出说明

2026年9月1日 开发/基础设施

以前是好的，现在不行了。 以这句话开头的问题，并不是不知道原因，而是不知道该看哪里。代码在某处变了，而那个某处夹在几百次提交之间。git bisect 就是把那个区间一半一半切进去的命令。

二分查找这个想法本身另外写过 — 内核 Bug 是怎样被一步步收窄的讲的就是那件事。这篇只收窄到git 已经实现好的那个命令上。要给什么参数，会打印什么输出，以及在哪里容易出错。

下面的输出全部是在 git 2.48.1.windows.1、Windows 10 Pro (10.0.19045)、Git Bash(GNU bash 5.2.37, MSYS2) 上实际执行得到的，时点为2026年9月。实验一律在临时目录里新建的仓库中进行，正文里的 /tmp/demo 只是指代那个位置的中性名字。在其他平台或其他 shell 上可能不同的地方，都会在出现时标注。

它解决的是什么问题

git bisect 回答的问题只有一个。如果现在失败、以前成功，那么是中间的哪次提交把它改了。 只要告诉它一个当时正常的提交和一个已经坏掉的提交，git 就会检出中间那次提交，由人或脚本判定，然后再砍掉一半。

这里要紧的是不需要知道肇事提交的内容。有判定标准就够了。性能回归也好，某条日志不再打印也好，某个文件不再生成也好，只要是能用是或否回答的测试，就全都适用。所以这个工具和读代码推断原因的做法性质不同。它不是推断，是测量。

  • 需要三样东西 — 坏掉的提交(多半是 HEAD)、当时正常的提交(标签、发布版本、几个月前的提交)、能复现的测试
  • 不需要的东西 — 关于原因的假设。有了假设反而会只盯着那一侧而漏掉
  • 搜索的对象是整个区间的提交，不是文件的差异。所以横跨多个文件的相互作用问题也抓得到
  • 结果是一次提交。那次提交如果很大，还得再往里收窄，但从整段历史缩到一次提交，通常局面就已经变了

造一个用来做实验的仓库

光说不容易有感觉，所以先造一个仓库再开始。是20个提交的。total.sh 把参数里收到的数字相加，check.sh 在结果正确时以0结束、错误时以1结束。在第13次提交里把 total.sh 改成按下标遍历，同时带进一个漏掉最后一个参数的缺陷。之后还会再堆上七个无关的提交。

# 在 /tmp/demo 中
git init -b main

cat > total.sh <<'EOF'
#!/bin/bash
sum=0
for n in "$@"; do
  sum=$(( sum + n ))
done
echo "$sum"
EOF

cat > check.sh <<'EOF'
#!/bin/bash
out=$(bash ./total.sh 1 2 3 4)
if [ "$out" = "10" ]; then
  exit 0
else
  echo "expected 10, got $out"
  exit 1
fi
EOF

基本流程 - 把一个会话走完

顺序有四步。用 bisect start 开一个会话，用 bisect bad 告诉它现在是坏的，再用 bisect good 告诉它当时正常的提交。这样 git 就会替你检出中间那次提交。测试之后反复给 good/bad，结束时用 bisect reset 退出来。

把正常点定为 c02、故障点定为 c20，候选就是从 c03 到 c20 共18个。下面是那个会话的全部，命令和输出一条都没删。

1,000个提交真的只要10次测试吗

常被引用的那个算法，还是量一量比较好。新建一个1,000个提交的仓库，在第674次提交里弄坏一个配置值，然后从第一次提交到 HEAD 让它自动搜索整个区间。数一数判定脚本被执行了多少次就行。

$ git rev-list --count HEAD
1000

$ git bisect start HEAD $(git rev-list --max-parents=0 HEAD)
$ git bisect run bash /tmp/bigtest.sh
Bisecting: 249 revisions left to test after this (roughly 8 steps)
Bisecting: 124 revisions left to test after this (roughly 7 steps)
Bisecting: 62 revisions left to test after this (roughly 6 steps)
...
fe0dcdad953018ee006623208fdde398e98ea338 is the first bad commit
    c0674
bisect found first bad commit

# 判定脚本被执行的次数
10

恰好10次。因为把第一次提交定为正常点，候选是999个，把999不断除以2，10次就落到1以下。这里要紧的性质不是绝对次数，而是增长的速度。提交数翻一倍，测试也只多一次。

候选提交数需要的测试次数备注
184在上面那个20提交的仓库上实测
99910在1,000提交的仓库上实测
2,00011提交翻倍也只多一次
100,00017大型仓库也在二十次以内

表里下面两行不是实测，而是按同一规则往下推的值。要点是提交数几乎不会成为瓶颈。

一次测试的时间决定总时间

那么瓶颈是什么。同样的1,000提交搜索跑了两遍。一遍用判定立刻结束的测试，一遍加上 sleep 2 故意做慢。答案一样，测试次数也一样。

--- 立即结束的测试，999个提交
tests run: 10
wall time: 3693 ms

--- 同一次搜索，每次测试2秒
tests run: 10
wall time: 24018 ms

答案相同? fe0dcdad... / fe0dcdad...

相差的20.3秒就是2秒 × 10次。git 花掉的时间只有10次检出的3.7秒。也就是说总耗时几乎全是测试时间，公式很简单。总时间 ≒ 一次测试的时间 × log₂(候选数)。

所以在挂上 bisect 之前把测试变短，实际收益最大。整套测试要5分钟的话，10次就是50分钟；把复现问题的最小用例做出来缩到30秒，就变成5分钟。先做最小复现这条建议不是定性的劝告，而是十倍差距的算术。

  • 不跑整套，只跑失败的那一个测试。大多数框架都支持指定单个用例
  • 需要构建就让增量构建生效。每次都全量重建，那段时间会原样放大十倍
  • 依赖网络和外部服务的部分要切掉。慢固然是问题，但间歇性失败会让答案是错的
  • 能收窄区间就收窄。把候选从999个减到60个，测试就从10次减到6次

忘了 bisect reset 会发生什么

找到肇事提交之后如果就那么放着，会留在分离头指针状态。站在最后一次检查的提交上，不挂在任何分支下面。好在 git 会好心提醒。

$ git status
HEAD detached at 4d711a9
You are currently bisecting, started from branch 'main'.
  (use "git bisect reset" to get back to the original branch)

nothing to commit, working tree clean

$ ls .git | grep -i bisect
BISECT_ANCESTORS_OK
BISECT_EXPECTED_REV
BISECT_LOG
BISECT_NAMES
BISECT_START
BISECT_TERMS

$ ls .git/refs/bisect
bad
good-d6e191c941eb0f49e6ad6b88f546215ef538eecf

在这里随手改了代码再提交，那次提交不属于任何分支。以后虽然能用 reflog 找回来，但这是没必要经历的事。确认会话是否还活着最快的办法就是像上面那样看 .git 里有没有 BISECT_* 文件，reset 之后它们全都消失。

$ git bisect reset
Previous HEAD position was 4d711a9 c12: unrelated note 12
Switched to branch 'main'

# 想直接停留在肇事提交上时
$ git bisect reset refs/bisect/bad
HEAD is now at f1fec3f c13: refactor total.sh to index-based loop

# 不移动当前提交，只清理会话
$ git bisect reset HEAD

另外补一句，工作树是脏的时候会话根本起不来。 必须把正在改的文件提交掉，或者用 stash 收走。实际上是这样结束的。

$ git status --short
 M total.sh

$ git bisect start f2ee06a d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
error: Your local changes to the following files would be overwritten by checkout:
	total.sh
Please commit your changes or stash them before you switch branches.
Aborting

bisect run - 不用人盯着也能跑完

从这里开始才是这个命令的本体。把判定交给脚本，git bisect run 就会自己反复做检出、判定和下一步的选择。在和前面完全相同的仓库里，不需要人介入，一行就结束。

$ git bisect start f2ee06a d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

$ git bisect run bash ./check.sh
running 'bash' './check.sh'
Bisecting: 4 revisions left to test after this (roughly 2 steps)
[d21c4cae515e9a7c0cfcacc38374c8b127273674] c15: unrelated note 15
running 'bash' './check.sh'
expected 10, got 6
Bisecting: 1 revision left to test after this (roughly 1 step)
[f1fec3fe55804001fae21aaf7b18a6914483662a] c13: refactor total.sh to index-based loop
running 'bash' './check.sh'
expected 10, got 6
Bisecting: 0 revisions left to test after this (roughly 0 steps)
[4d711a957c98da7528cf727b1db40974a3f9d199] c12: unrelated note 12
running 'bash' './check.sh'
f1fec3fe55804001fae21aaf7b18a6914483662a is the first bad commit
commit f1fec3fe55804001fae21aaf7b18a6914483662a
Author: demo <demo@example.invalid>

指出的提交和手动会话完全一样，而人敲的命令只有两行。run 后面可以跟任何命令 — make、npm test、pytest -k some_case、自己写的 shell 脚本都行。带参数也可以，脚本的路径放在被检出的仓库之外更安全。放在仓库里面的话，旧的提交上可能没有那个文件。

退出码约定

自动化的全部就是退出码。约定搞错了，它会悄悄指出错误的提交。把脚本固定成各个码分别跑一遍，结果整理如下。

退出码git 的解释实际出现的情况
0正常(good/old)全部被标为正常，把坏的端点本身指成了肇事提交
1 ~ 124, 126, 127有缺陷(bad/new)1、2、124 行为相同。把区间最前面的提交指为肇事提交
125无法判定 - 跳过全部跳过时先是 We cannot bisect more!，然后是 bisect run cannot continue any more
126 · 127 (第一轮)疑似脚本执行失败在正常提交上重试之后以 bogus exit code 127 for good revision 中断
128 以上中断搜索bisect run failed: exit code 128 ... is < 0 or >= 128

文档上的约定是「0为正常，除125以外的1到127为有缺陷，其余的码中断」。可是把 126、127 真跑一遍，会发现比文档多出一层。这两个值是 POSIX shell 用于无法执行和命令不存在的值，所以 git 只在第一轮会检出一个已知正常的提交，把同样的命令再跑一次。那里也出同样的码，它就认为脚本本身有问题而停下。

$ git bisect run bash /tmp/rc.sh      # 脚本始终以127结束
running 'bash' '/tmp/rc.sh'
[d6e191c941eb0f49e6ad6b88f546215ef538eecf] c02: add check.sh
running 'bash' '/tmp/rc.sh'
error: bogus exit code 127 for good revision
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

中间那行能看出它切到正常提交 c02 之后又切回原位的痕迹。有了这道保险，因为脚本路径打错而把整个区间标成有缺陷的事故大体上能被挡住。反过来，出现这条消息时不该怀疑代码，而要先看脚本能不能执行。

最危险的值是 124。它是给测试加超时时会出现的值，而按约定会被读成有缺陷。

$ timeout 1 sleep 5 ; echo $?
124

也就是说因为慢而被掐断的提交和真正失败的提交分不开。 要用超时的话，把那个值换成无法判定更准确。

把判定脚本写好的办法

第一条规则是必须是能复现的测试。二分查找把每次判定都当成真话，然后整整丢掉一半。判定只要错一次，肇事提交就可能在被丢掉的那一半里，而那时搜索不会报告任何错误。它会自信满满地给出一个看起来很像的提交。

为了确认这一点，做了一个有30%概率给出假失败的测试，在同一个仓库上跑了五遍。正确答案是 c13(f1fec3f)。

--- 间歇性失败的测试，5轮
round 1  f1fec3f...  (正确)
round 2  f1fec3f...  (正确)
round 3  f1fec3f...  (正确)
round 4  f1fec3f...  (正确)
round 5  9dc5458...  (c08 - 错误)

--- 确定性的测试，3轮
f1fec3f...  f1fec3f...  f1fec3f...

五次里有一次指了一个毫不相干的提交。而且只看那份输出，哪里也没有标明它是错的。怀疑有间歇性失败时，更好的做法是把判定重复多次，只要失败一次就当作有缺陷。

第二条是清理副作用。bisect 只是在提交之间来回走，未被跟踪的文件会原样留下。旧的构建产物留着，下一次提交的判定就会被污染。

$ echo "stale artifact" > build.out    # 未被跟踪的产物
$ git bisect good                       # 移动到其他提交
$ cat build.out
stale artifact

实战里能用的骨架是这样。构建失败给 125，超时也给 125，其余把测试结果原样返回。

#!/bin/bash
# /tmp/judge.sh - 放在仓库之外
set -u

rm -rf ./build            # 清理上一轮的产物
make clean >/dev/null 2>&1

if ! make >/dev/null 2>&1; then
  exit 125                # 无法构建 - 不判定，跳过
fi

timeout 60 ./run_one_test.sh
rc=$?
if [ "$rc" -eq 124 ]; then
  exit 125                # 避免把超时误判为缺陷
fi
exit "$rc"
  • 脚本放在仓库之外。旧的提交上没有那个文件
  • 显式地处理退出码。让最后一条命令的码漏出去，就会和本意不同
  • 产物、缓存、临时文件每一轮都清掉。留着会污染下一次判定
  • 标准输出可以少打，但失败原因那一行要留。之后只能靠日志来判断
  • 先在两个端点上手动跑一遍。 坏端点失败、好端点成功，搜索才成立

bisect skip - 无法判定的提交

区间里有构建坏掉的提交就没法判定。这时用 git bisect skip，git 会替你另选附近的提交。如果在自动运行中，脚本以 125 结束就是同样的意思。

只是被跳过的提交要是扎堆在答案附近，结果就收不到一个上。下面是把缺陷前后的四个提交(c11～c14)全部设为跳过之后跑出的结果。

$ git bisect run bash /tmp/skipper.sh
...
There are only 'skip'ped commits left to test.
The first bad commit could be any of:
4d711a957c98da7528cf727b1db40974a3f9d199
f1fec3fe55804001fae21aaf7b18a6914483662a
71ed7e0a93f0b4029ba06d2d3cb95e019f141bb1
f9194e697f22b03a4aae2ef437dfc2497846eb63
d21c4cae515e9a7c0cfcacc38374c8b127273674
We cannot bisect more!
error: bisect run cannot continue any more

这不该当成失败。18个提交减到了5个候选，这五个是能用手看完的量。事先就知道哪一段没法用的话，也可以用范围写法一次性排除。

$ git bisect skip c10..c14
Bisecting: 8 revisions left to test after this (roughly 3 steps)

$ git bisect log | grep skip
git bisect skip 71ed7e0a...   # c14
git bisect skip f1fec3fe...   # c13
git bisect skip 4d711a95...   # c12
git bisect skip f9194e69...   # c11

这里容易绊住的地方 — c10..c14 指的是 c10 之后到 c14 为止。起点本身不包含在内。要连起点一起排除，就得像 git bisect skip c10 c10..c14 这样另外写出来。

bisect terms - good/bad 不合适的时候

要找的东西未必总是 bug。找性能变好的时点，或某个功能最初进来的时点时，「坏的提交」这个说法会把方向搞混。这时可以换掉术语。内置的别名有 old/new，也可以自己起名。

$ git bisect start --term-old=works --term-new=broken
status: waiting for both good and bad commits

$ git bisect broken f2ee06a
status: waiting for good commit(s), bad commit known

$ git bisect works d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

$ git bisect terms
Your current terms are works for the old state
and broken for the new state.

$ git bisect run bash ./check.sh
...
f1fec3fe55804001fae21aaf7b18a6914483662a is the first broken commit
bisect found first bad commit

结果那一行变成了 first broken commit。只有最后的汇总行依然是 first bad commit，如果打算用脚本解析输出，这个差别值得知道。会话中途忘了当前用的是什么术语，就用 git bisect terms 确认。

  • 找 bug 的时候 — 默认的 good/bad 就够
  • 找修复是什么时候进来的 — 用 old/new。不必称之为「坏的提交」
  • 性能回归 — 像 --term-old=fast --term-new=slow 这样起好名字，判定时就不会搞混
  • 换了术语，算法还是一样的。变的只是说法

混有合并提交的历史

在默认行为下，bisect 把合并提交，以及侧分支里的提交，全都当作候选。 造了一个缺陷在功能分支里进来、那个分支之后被合并的历史来确认。

$ git log --oneline --graph --all
* 1f5a5ab m7: mainline work
* dc8284c m6: mainline work
*   36edf65 m5: merge feature
|\
| * fa26dce f4: feature polish
| * 9c3c4da f3: rewrite total.sh (THE BUG)
| * 13a2a60 f2: feature work
| * efe0833 f1: feature start
* | 0481885 m4: mainline work
|/
* 87b692a m3: mainline work
* 2606564 m2: mainline work
* 342914a m1: base

同一个仓库用两种方式搜索，答案不一样。两个都是对的答案，只是问的问题不同。

--- 默认：会进入侧分支内部
running 'bash' './check.sh'   (3次)
9c3c4da9ba2ed3715032525e3699eeae971e583e is the first bad commit
    f3: rewrite total.sh (THE BUG)

--- --first-parent：只看主线
$ git bisect start --first-parent HEAD 2606564
running 'bash' './check.sh'   (3次)
36edf65d0bd276c62c3fbae15ccab5a28196c39d is the first bad commit
Merge: 0481885 fa26dce
    m5: merge feature

默认的搜索指出的是写下缺陷的那次提交 f3，--first-parent 指出的是缺陷进入主线的地点，也就是合并提交 m5。要改原因代码就需要前者，要知道从哪个发布版本开始有问题就需要后者。

--first-parent 还有一种特别有用的场合。侧分支中间的提交连构建都过不了的仓库。如果开发过程中就带着坏的状态提交、临合并前才整理，默认的搜索会在那些坏掉的提交上一直卡住。只看主线的话，每次提交大体上都是完整的。

找到肇事提交之后

得到一次提交，就已经完成了一半。先看那次提交改了什么。

$ git show --stat f1fec3f
 total.sh | 8 ++++++--
 1 file changed, 6 insertions(+), 2 deletions(-)

$ git log -p -1 f1fec3f
diff --git a/total.sh b/total.sh
@@ -1,7 +1,11 @@
 #!/bin/bash
+# refactor: iterate by index
 sum=0
-for n in "$@"; do
-  sum=$(( sum + n ))
+i=1
+while [ "$i" -lt "$#" ]; do
+  eval "v=\${$i}"
+  sum=$(( sum + v ))
+  i=$(( i + 1 ))
 done
 echo "$sum"

这里一眼就看得出来。本该是 -le 的地方写成了 -lt，所以最后一个参数被落下了。可实战中的肇事提交多半没这么小。要是出来一次动了几十个文件的提交，就得在那里面再收窄。bisect 以提交为单位，进不到里面去，所以从父提交开始，把改动过的文件一个个叠上去测试。

$ git show --stat HEAD
 alpha.conf | 1 +
 beta.conf  | 1 +
 delta.conf | 1 +
 gamma.conf | 2 +-
 4 files changed, 4 insertions(+), 1 deletion(-)

$ git checkout HEAD~1            # 移动到父提交
$ for f in alpha.conf beta.conf delta.conf gamma.conf; do
>   git checkout main -- "$f"
>   bash ./check.sh; echo "  + $f -> $?"
> done
  + alpha.conf -> 0
  + beta.conf -> 0
  + delta.conf -> 0
  + gamma.conf -> 1        <-- 这里坏掉

收窄到一个文件，只看那个文件的改动就行。文件本身要是也很大，把同样的办法用 git checkout -p 套到块级别就好。另外，想直接在肇事提交上干活，前面看过的 git bisect reset refs/bisect/bad 会把你带到那个位置。

和 git blame 有什么不同

两个看起来都在回答「什么时候变成这样的」，但问题不同。blame 说的是最后动过这一行的提交，bisect 说的是行为改变的时点。多数时候它们指向同一处，但分岔的情况也很常见。

造了一个仓库，缺陷在 b3 进来，之后 b5 只改了同一个文件的缩进。从 b3 起行为一直没变。

$ git blame -- total.sh
^4ff6d88 ... 2) sum=0
75a65371 ... 3) i=1
75a65371 ... 4) while [ "$i" -lt "$#" ]; do
b44df25c ... 5)     eval "v=\${$i}"      <-- b5(只改了格式的提交)
b44df25c ... 6)     sum=$(( sum + v ))
b44df25c ... 7)     i=$(( i + 1 ))

$ git bisect run bash ./check.sh
75a65371be49176fd1a34827c369875cd78e8a1e is the first bad commit
    b3: switch to an index loop

blame 把关键的三行归给了格式提交 b5，bisect 指出的是改了逻辑的 b3。blame 这边也能用忽略空白(-w)或排除特定提交(--ignore-rev)来修正，实际上这两个选项都能把结果拉回 b3。这一带的选项在被低估的 Git 历史命令那篇里另外讲过。

场景合适的工具理由
想知道这一行为什么这么写git blame按行直接给出提交和提交信息
不知道行为是从什么时候起变了git bisect不需要知道是哪一行有问题
问题出在多个文件的组合上git bisectblame 只能一行一行地回答
要找这个字符串是什么时候消失的git log -S按内容变化筛出提交
已知肇事提交，想看它内部git show · log -p接着 bisect 的结果往下用

bisect 不合适的场合

它并不是所有回归都能用。有几种明确不合适的条件。

  • 按提交粒度构建不过的仓库 — 要跳过的提交太多，最后会剩下好几个候选。可以用 --first-parent 只看主线，或者先在发布标签之间收窄，再对那一段做精细搜索
  • 依赖环境的缺陷 — 库的版本、内核、容器镜像变了而产生的问题，不在代码历史里面。这时要二分查找的不是代码，而是环境
  • 依赖数据的缺陷 — 只在特定记录上复现的话，得先把那份数据固定下来，让测试变得可复现。直接用生产数据，判定会摇摆
  • 逐渐变差的问题 — 性能每次提交差1%的话，根本不存在「变了的那一次提交」。定个阈值硬做二分，也只是那个阈值在决定答案
  • 已经知道原因的问题 — 栈跟踪已经指向文件和行号的话，blame 快得多。bisect 是没有线索时用的工具
  • 历史被 rebase 重写过的区段 — 那些提交实际上从未按那个顺序被构建过，中间的提交可能本来就跑不起来

还有一个只对 Windows 用户成立的坑。bisect 会创建一个叫 refs/bisect/good-<40位哈希> 的长名字引用。仓库路径一深，这个路径就会超过260字符的限制，会话起不来。只改变路径长度做验证，结果是这样。

root=181  refpath=244  -> 正常
root=192  refpath=255  -> 正常
root=203  refpath=266  -> error: update_ref failed for ref
   'refs/bisect/good-27fe9984...': couldn't set
   'refs/bisect/good-27fe9984...'

消息里不会说这是路径的问题，所以原因很难找。打开 core.longpaths=true 对这个引用也不起作用。把仓库挪到浅一点的路径上最稳妥。在 Linux 和 macOS 上不会出现这个问题。

小结

归拢起来，实战中要记的东西不多。给出坏的提交和好的提交，把判定交给脚本，结束后 reset。三行。

$ git bisect start <坏的提交> <好的提交>
$ git bisect run /tmp/judge.sh
$ git bisect reset

其余全都取决于判定脚本的质量。测试不能复现，答案就是错的；测试慢，那段时间会变成十倍；退出码随手一漏，超时就摇身变成缺陷。搜索算法早就做好了，没有可动的地方。人这边要准备的只有一样，一个能把「成了/没成」一次都不说错的测试。

所以真正学会这个命令的顺序不是语法。碰上问题先手动确认两个端点，把测试缩成最小复现，然后才挂上 run。守住这个顺序，大部分回归都能在一杯咖啡的工夫里收窄到一次提交。

未能确认的部分

  • 所有输出都只在 Windows + Git Bash 这一个环境里取得。在 Linux、macOS，以及 dash、zsh 这类其他 shell 上，消息措辞或退出码的传递是否相同，没有确认
  • 搜索中断时 git bisect run 本身返回给 shell 的值并不固定。脚本以128结束时出128，以129结束时出127，规律没能弄清。判断还是靠消息而不是靠退出码更安全
  • 126、127 的重试行为只按观测到的输出写。没有直接到 git 源码里确认对应的处理
  • 1,000个提交的实测用的是合成仓库。在有几万个文件的大型仓库里，检出成本会变大，git 自身耗时的占比可能不同
  • git bisect visualize 需要 gitk，没有运行。--no-checkout 确认过可用，但在裸仓库里的行为没有试
  • 长路径失败时 core.longpaths 为什么不起作用，未能确认原因。 是引用文件的路径还是锁文件卡住了，也没能确定
