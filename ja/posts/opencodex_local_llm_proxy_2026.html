opencodex — Codexで任意のLLMを使えるローカルプロキシ

OpenAI Codex CLIを特定モデルに縛られずローカル・他社LLMへ接続する — ベンダーロックイン回避・コスト削減・プライバシー実用分析

2026-06-22 開発・インフラ

序論：Codexを自由に使いたいなら

OpenAI Codex CLIは2026年6月基準でTerminal-Bench 2.1リーダーボード1位（83.4%）を記録する強力なターミナルAIコーディングエージェントだ。問題はひとつ。OpenAIモデル専用という縛りがある。ChatGPT Plus（月額$20）またはPro（月額$200）のサブスクリプションなしには動かない。Claude、Gemini、DeepSeek、Ollamaといったローカル・オープンソースモデルはCodexと繋がる手段がない。

この問題を解決するのがopencodexだ。GeekNewsに46ポイントで掲載されたこのプロジェクトは一文で説明できる。「Codex CLI・App・SDKで任意のLLMを使えるようにするローカルプロキシ。」本稿はopencodexの動作原理、なぜこのアプローチが技術的に有効か、LiteLLMや他の代替手段と比べてどこに位置づけられるか、そして実際のリスクは何かを自分の視点で分析する。2026年6月基準の情報だ。

1. なぜこの問題が生まれたか — Responses APIという壁

1.1 Responses APIの登場

OpenAIは2025年初頭にResponses APIを導入した。従来のChat Completions APIより、マルチターン会話・ツール呼び出し（tool_calls）・推論トークン（reasoning tokens）・画像処理に最適化されたインターフェースだ。Codex CLIはこのResponses API上で動作するように設計されている。エージェントループでのツール呼び出し、推論過程のトークン処理、ストリーミングレスポンスがResponses APIに最適化されているためだ。

1.2 他社プロバイダーはResponses APIを知らない

問題はAnthropicのClaude、GoogleのGemini、Ollamaなど大半の他社プロバイダーがResponses APIをサポートしていないことだ。それぞれ独自のネイティブAPIを持つ。AnthropicはMessages API、GoogleはGemini API、ローカルモデルはChat Completions互換エンドポイントを使う。Codexは「Responses APIしか話せないクライアント」であり、他社プロバイダーは「Responses APIを理解できないサーバー」だ。このプロトコルギャップをopencodexが埋める。

1.3 コミュニティの声

openai/codexリポジトリのIssue #26「Support for local / other LLMs」は、この需要がいかに強かったかを示す。ベンダーロックインを嫌い、コスト負担を感じ、コードベースを外部APIに送ることを避けたい開発者が最初からこの機能を求めていた。opencodexはOpenAIが公式対応しないこの要求をコミュニティが直接解決した結果だ。

2. opencodexの動作原理 — プロトコル翻訳機

opencodexは構造的にシンプルだ。ローカルで動かす翻訳プロキシだ。

2.1 リクエストフロー

Codex CLI / App / SDK
        │  (Responses APIリクエスト)
        ▼
   opencodex  (ローカルプロキシ)
        │  (プロトコル翻訳)
        ▼
   対象LLMプロバイダー
   (Claude / Gemini / DeepSeek / Ollama 等)

CodexがResponses APIリクエストを送ると、opencodexがそれを傍受し、対象プロバイダーのネイティブプロトコルへ変換して転送する。レスポンスも逆方向に翻訳されてCodexに戻る。Codexの視点では常にResponses APIエンドポイントと通信しているように見える。

2.2 5つのプロトコルアダプター

アダプター名対象カバー範囲
anthropicClaude Messages APIAnthropic全モデル（Claude 3.5/3.7等）
googleGemini APIGemini 2.0/2.5等Googleモデル
azure-openaiAzure OpenAIAzureにデプロイされたモデル
openai-responsesOpenAI ResponsesパススルーOpenAI公式エンドポイント直接
openai-chatChat Completions互換エンドポイントDeepSeek/GLM/Kimi/Qwen/Groq/OpenRouter/Ollama等40以上

openai-chatアダプターが最も広範だ。Chat Completions API互換のエンドポイントを公開するプロバイダーであれば何でも対象になる。OpenRouter経由で指定すれば、数百のモデルをCodexに接続できる。

2.3 双方向フィーチャー変換

opencodexはストリーミング、ツール呼び出し、推論トークン、画像を双方向に変換すると公表している。これはテキストの単純なリレーではなく、プロトコルレベルの翻訳だ。Codexエージェントがファイル編集やターミナルコマンド実行のためにツールを呼び出す際、そのツール呼び出し構造が対象モデルにも正しく伝わる必要がある。

3. インストールと使用 — 3コマンドで完結

前提条件はBun 1.1以上のみ。その後は3つのコマンドで完結する。

npm install -g @bitkyc08/opencodex   # または bun install -g @bitkyc08/opencodex
ocx init    # 対話形式セットアップ: プロバイダー・モデル・APIキー選択
ocx start   # バックグラウンドサービスとしてプロキシ起動

ocx initは対話形式でプロバイダーとモデル、APIキーを設定し、Codex CLI・TUI・App・SDKへ自動インジェクションする。Codex設定ファイルを手動編集する必要はない。ocx startで起動するとバックグラウンドサービスとして動作し、リアルタイムWebダッシュボードでリクエストフローを確認できる。MITライセンスのオープンソース。

4. ベンダーロックイン回避 — なぜ重要か

4.1 Codex CLIの構造的従属

Codex CLIはApache 2.0オープンソースだが、動かすにはOpenAIサブスクリプションが必要だ。ツール自体は開かれていても、そのツールを動かす燃料（モデルAPI）は鍵がかかっている。開発者視点でこの従属は3つの実質問題を生む。①コスト：Proサブスクリプション（月$200）は重度ユーザーにも負担。②コードプライバシー：コードベースがOpenAIサーバーを通過する。③モデル選択権の欠如：特定タスクに優れたモデルがあっても使えない。

4.2 opencodexが開く出口

コスト面では、DeepSeek V3やQwenなど安価なOpenAI互換プロバイダーに切り替えることで、同じCodexインターフェースをより低単価で使える。Ollamaでローカルモデルを繋げばトークンあたりの限界コストがゼロに近づく。プライバシー面ではローカルモデル接続時にコードが外部に出ない。モデル自由度の面では、ocx initでプロバイダーを変更するだけでよく、ワークフローを変える必要がない。

4.3 プロバイダー非依存設計の実用性

opencodexの本質的な価値は「特定モデルより優れている」という主張ではなく、モデル選択が設定パラメーターになるという設計だ。今日はDeepSeekで始め、より良いモデルが出たらocx initでプロバイダーだけ変える。Codexの使い方もワークフローもスクリプトも変えなくてよい。これはLiteLLMがコードレベルで実現したLLM抽象化と同じ哲学をツールレイヤーに適用したものだ。

5. LiteLLMとの比較 — 解決する層が違う

5.1 LiteLLMの役割

LiteLLM（v1.83.8、MIT）は100以上のプロバイダーをOpenAI Chat Completions形式で統一するPython SDKおよびゲートウェイプロキシだ。自分が作るアプリケーションのバックエンドゲートウェイとして使う。コード変更なしにプロバイダーを切り替えられる。これは自分のコードがLLMを呼び出す時の抽象化だ。2026年3月に供給チェーンセキュリティインシデントが発生したが、チームが詳細を公開して対応し、現在も最も広く使われるオープンソースLLMゲートウェイだ。

5.2 opencodexの役割

opencodexは自分のコードではなくCodexという既存ツールがLLMを呼び出す際の抽象化だ。Codexのコードは変更できないが、プロキシを通じてその動作を変えることができる。解く問題の階層が異なる。

5.3 組み合わせシナリオ

両者を組み合わせることもできる。opencodexのopenai-chatアダプターのエンドポイントにLiteLLMプロキシサーバーのアドレスを指定すれば、opencodex → LiteLLM → 100以上のプロバイダーという連鎖が可能だ。Codexから実質的にLiteLLMがサポートする全モデルを使えることになる。

6. 類似プロジェクトとエコシステム

6.1 codex-relay

Rustで書かれた軽量プロキシで、Responses APIをChat Completions APIへ翻訳することに特化する。opencodexより機能が絞られているがRustの性能特性を活かせる。OpenAI互換エンドポイントのみが対象なら、より軽い選択肢だ。

6.2 OpenCode — 別の道

プロキシではない別の選択肢として、2026年6月時点でGitHubスター168,000超のOpenCodeがある。75以上のLLMプロバイダーをネイティブサポートするオープンソースCLIエージェントで、Codex CLIの代替として位置づけられる。Codexインターフェースへの固執がないチームなら、ツール自体を切り替えるほうがシンプルな選択かもしれない。opencodexは「Codexワークフローを維持しつつモデルだけ変えたい」チーム向けだ。

7. リスクと注意点 — 正直に

7.1 利用規約リスク

opencodex著者自身が明示した警告がある。「一部のプロバイダー — 特にAnthropicのClaude — はサードパーティプロキシ経由でAPIトラフィックをルーティングするアカウントを停止または制限する可能性がある。Use at your own risk（自己責任で使用すること）。」各プロバイダーの利用規約を必ず事前確認すること。Claudeをopencodex経由で接続する場合、アカウントリスクを認識する必要がある。

7.2 プロトコル変換の完全性

プロトコル変換は常に完全ではない。Codexが推論トークンや特定のツール呼び出し形式など、対象モデルが同等の概念をサポートしていない機能を要求した場合、変換が不完全になるかフィーチャーが失われる可能性がある。エージェントループの動作を実際のワークロードで検証することが不可欠だ。

7.3 メンテナンスの継続性

コミュニティプロジェクトの宿命として、OpenAIがResponses APIスキーマを変更したりCodexプロトコルを更新したりすると、opencodexのアダプターも更新が必要になる。公式サポートはないため、管理者の活動状況に依存する。本番ワークフローへの採用前にメンテナンス履歴を確認すること。

8. どのような開発者に向いているか

8.1 適している場合

すでにCodex CLIワークフローに投資済みで、モデルだけ変えたいチーム。コードプライバシーが求められる環境（Ollama経由でローカルモデルを繋げばコードが外部に出ない）。ヘビーユーザーでコスト最適化が目標の場合：安価なChat Completions互換プロバイダーでトークン単価を大幅削減できる。

8.2 向いていない場合

Claude Code、Cline、OpenCodeを使っているチーム（Codex以外のワークフローにopencodexは無関係）。AnthropicのClaudeを接続したいが利用規約リスクを避けたい場合。最初からマルチプロバイダー対応を求めるなら、複雑さを増すプロキシより最初からOpenCodeを検討するほうが長期的にすっきりする。

9. 結論 — プロトコル抽象化が自由をもたらす

opencodexは華やかなツールではない。しかしそのシンプルさが核心だ。Codexがリクエストを送りつつ他社プロバイダーがそれを理解できないという間隙に、正確に翻訳機を挿入した。このアイデア自体は新しくない。LiteLLMがコードレイヤーでやったことをツールレイヤーで繰り返したものだ。新しいのは実行だ。3行インストール、5つのアダプター、ダッシュボード、MITライセンス。

2026年6月基準のAIコーディングツール市場の核心的緊張のひとつは、オープンソースツールと商用モデル従属の矛盾だ。Codex CLIはApache 2.0だが実質的にOpenAIサブスクリプションなしでは意味をなさない。opencodexはこの緊張を一段階緩和する。完全には解消しない — 利用規約リスク、変換完全性の限界、メンテナンスの不確実性が残る。しかし「自分たちが使うツールの自由は自分たちが守る」というコミュニティの立場から生まれた成果物の好例だ。
