MCP已死? - Model Context Protocol的局限与2026年AI智能体集成的未来

挑衅标题背后的均衡真相 - 热潮一年后，承诺兑现了吗

2026年6月1日 IT/技术

1. 引言：MCP热潮一年后 - 承诺兑现了吗

2026年5月31日，news.hada.io的热门文章里出现了一个挑衅性话题"Is MCP Dead?(MCP已死?)"。Model Context Protocol，简称MCP，是Anthropic于2024年底发布、随后顶着"AI智能体的USB-C"绰号红火了整个2025年的标准。一篇追问MCP是否"已死"的文章登上热门榜，这本身就在发出信号：一年之间，期待与现实之间的落差已大到被人公开议论。

我先坦白再开始。BrainDetox此前在谈智能体基础设施时多次正面提到过MCP。正因如此，这篇我更想写得客观。"已死"这个标题很刺激，但先把结论说在前面：MCP没死，死的是它无所不能的幻想。本文将均衡地拆解：那个幻想在哪里破裂，而MCP又在哪里依然闪光。

本文以hada.io话题为起点，但不照搬其摘要。我将用13章梳理我亲自搭建MCP服务器并接入客户端使用时遇到的五大局限、与function calling及直接集成的对比、MCP适合与不适合的领域、替代方案，以及在韩国开发环境中的实情。先说结论：是否使用MCP，应当以"是否契合我的集成结构"而非"因为它流行"来判断。

2. MCP曾是什么 - Anthropic的Model Context Protocol概览

MCP是一种开放协议，用于标准化AI模型(准确说是包裹模型的客户端)与外部工具、数据源、系统连接的方式。核心想法很简单：把过去因模型而异、因应用而异、各不相同的工具连接方式统一成一个共同契约。所以常被比作"AI时代的USB-C"。正如任何设备都插进同一个接口，任何模型都通过同一协议插进工具。

架构是客户端-服务器模型。MCP主机(Claude Desktop、Cursor、VS Code等)内嵌一个MCP客户端，该客户端与外部的MCP服务器通信。服务器暴露三样东西：模型可调用的tools(函数)、可读取的resources(文件、数据库记录等上下文)、可复用的prompts(提示模板)。通信在本地用标准输入输出(stdio)，远程用基于HTTP/SSE的传输。

打个比方，MCP服务器就是工具的"适配器"。为GitHub、Slack、本地文件系统、数据库各做一次适配器，任何支持它的客户端都能用上同一个工具。这个"做一次，处处可用"的承诺，正是2025年MCP热潮的核心动力。

3. MCP承诺了什么 - 标准化的工具与上下文连接

MCP问世时，我觉得最有吸引力的承诺有三个。

  • 化解N×M问题 - 把N个模型与M个工具分别相连需要N×M个集成。MCP承诺在中间插入一个标准层，把它降到N+M。工具提供方只做一个MCP服务器，模型提供方只做一个MCP客户端。
  • 可复用的工具生态 - 别人做的GitHub MCP服务器，可以原样插进你的Cursor，也插进同事的Claude Desktop。工具不再依附于应用，而成为生态资产。
  • 上下文供给的标准化 - 不仅是函数调用，还以一致方式向模型注入所需上下文(文件、数据库、文档)。智能体的"能做什么"和"知道什么"在同一契约下处理。

这些承诺如今看仍是正确方向。问题在于：承诺方向正确，与承诺在任何场景都产生成本收益，是完全两码事。现实的局限正是从这里开始。

4. MCP的五大实际局限

这是我实际搭建并运营MCP服务器时撞上的五大局限。这不是别人的摘要，而是实测经验。

4-1) 复杂配置 - 入门门槛

这是最先撞上的墙。为用一个工具就要起一个独立服务器进程，把运行命令、环境变量、认证令牌准确写进客户端配置文件(JSON)。用function calling几行代码搞定的事，到MCP却要经历安装服务器、配置路径、确认运行时依赖等多个步骤。对非开发者几乎无法入门，对开发者也会冒出"为一个工具至于吗"的瞬间。

4-2) 安全 - 攻击面扩大

MCP给模型授予执行外部工具的权限。这有多强大就有多危险。当服务器触及本地文件系统、数据库、内部API，一旦模型被提示注入操纵，那份权限就直接变成攻击面。安装来源不可信的MCP服务器，等于以自己的权限运行第三方代码。把凭据明文写进服务器配置的常见做法，更放大了风险。

4-3) 调试 - 难以追踪

调用链跨越主机 → 客户端 → 服务器 → 外部系统多个进程，出问题时很难追踪在哪儿断了。是模型没调工具，是客户端没起起服务器，还是服务器报了错但消息没传回模型？很难区分。标准化的可观测性与日志仍薄弱，往往只能翻stdio日志做原始调试。

4-4) 标准分裂 - 实现之间不一致

号称"标准"，但各客户端支持范围不同。有的支持resources，有的只支持tools。传输方式(stdio对HTTP/SSE)、认证、权限模型的细节因实现而异。于是"做一次处处可用"在现实中退化为"做完还得逐客户端单独测试"。标准的价值源于一致性，而分裂直接啃食这份价值。

4-5) 性能开销

MCP要经过独立进程与协议往返，因此相比在模型内直接调用同一函数，延迟增加。取工具清单、序列化、做进程间通信、再反序列化拿回结果，这些步骤在每次调用上层层累积。一次性任务感受不大，但在智能体几十次调用工具的长循环里，累积开销就不容忽视了。

五大局限的共同点是"加一层的代价"。一旦插入名为标准的抽象层，配置、安全、调试、兼容、性能的成本便一并到来。这与其说是MCP的缺陷，不如说是所有中间件都背负的本质性权衡。

5. "已死"是夸大吗 - 真实的采用现状

那么真的死了吗？我的回答明确是"没有"。尽管局限明显，MCP的采用曲线依然向上。主流编码智能体与IDE(Claude Desktop、Cursor、VS Code及众多其他)把MCP作为一等集成方式支持，公开的MCP服务器数量一年间迅速增长。工具提供企业推出"官方MCP服务器"已成一种惯例。

"已死"的说法源于混淆了两件事。其一是炒作周期的正常化。按Gartner的炒作周期，MCP正从2025年的"期望膨胀顶点"下行至2026年的"幻灭低谷"。在这一段，"果然也没什么"的声音会变大。但幻灭低谷不是死亡，而是走向成熟的必经仪式。其二是适用范围的误解。以为MCP会取代一切集成的期待过头了，而在它契合的领域，采用照样在增长。

在我看来，死去的不是MCP，而是"单凭MCP就能让智能体集成的一切问题消失"的叙事。技术活着，死的是被夸大的期待。若分不清这点，就会因为风头过去而把一个本可好好使用的工具丢掉。

6. MCP vs Function Calling vs 直接集成 对比

要评价MCP，须把它与替代方案并列来看。下面对比三种做法。

标准Function CallingMCP直接集成(OpenAPI等)
配置难度低高中
复用性依附应用高(多客户端)中
工具生态无共享服务器生态按API各自
安全暴露面小大(独立权限)中
性能(延迟)最快有开销中
适合规模单一应用多客户端既有REST资产

把表格浓缩成一句：function calling对单一应用最简单，MCP在工具被多客户端共享时闪光，直接集成在已有完善REST API资产时合理。三者与其说是对手，不如说处在不同层。若function calling是连接模型与工具的"神经"，MCP便是让这根神经在多个身体上复用的"标准连接器"。

纠正一个常见误解：MCP不取代function calling。恰恰相反，模型调用MCP服务器的工具时，内部用的就是function calling机制。两者不是敌人，而是不同层的协作者。

7. MCP闪光的领域 vs 不适合的领域

下面是我整理的：何时该用MCP，何时不该用。

7-1) MCP闪光的领域

  • IDE与桌面智能体的本地工具连接 - 在Cursor里查询本地数据库或操作文件系统等，把同一工具在多客户端复用时最强。
  • 工具提供方与模型提供方解耦 - 当你只想把工具做好，而把用哪个模型交给用户时。SaaS推出"官方MCP服务器"的模式即属此类。
  • 多个智能体共享的工具池 - 把组织内标准工具集做一次，让全队智能体都能用。

7-2) MCP不适合的领域

  • 单一后端内的简单工具调用 - 一个应用里模型只调两三个函数，MCP的配置与运维成本明显过剩。function calling才是答案。
  • 以超低延迟为核心的任务 - 在每毫秒都重要的实时路径上，协议往返开销是负担。
  • 安全边界极度敏感的环境 - 在不允许外部MCP服务器扩权的封闭网络里，导入门槛极高。

核心判断标准只有一个："这个工具会被多个客户端共享吗?"答案为是就用MCP，为否就用function calling。

8. 替代与补充 - 下一代智能体集成标准

并非只有MCP。我所见的替代与补充版图如下。

  • 原生function calling / 工具API - 各模型提供方提供的最基础最快的集成。对单一应用仍是最佳。
  • 基于OpenAPI的直接集成 - 若REST API已完善定义，把规范交给模型让其直接调用更简单。
  • 框架工具抽象 - LangChain、LlamaIndex等提供自有工具抽象，有时把MCP当作适配器吸纳。
  • 智能体间通信(A2A类)协议 - 若MCP处理"智能体↔工具"，A2A类便瞄准"智能体↔智能体"。两者不竞争，而是填补不同层。

关键洞见在于：这些替代大多是补充而非扼杀MCP。2026年的现实图景不是单一赢家，而是多层结构。应用内用function calling，工具共享层用MCP，智能体协作层用A2A类，各占其位。

9. 开发者现在该用MCP吗 - 坦诚的判断

坦诚回答最常被问的问题："现在该学并导入MCP吗?"

我的回答是"用途契合的话，现在是好时机"。三个理由。其一，主流客户端支持已趋稳定，配置比早期顺畅得多。其二，公开服务器生态壮大，无需从零开始、可直接拿来用的工具变多。其三，处在幻灭低谷，被夸大的期待已散去，资料围绕实际有用性得到了整理。

不过导入方式须谨慎。我的建议是分阶段。先只用MCP包装一两个价值最高的工具并衡量效果。用数据确认配置成本对复用收益是否真的划算，再扩展。一开始就把所有工具都用MCP标准化的大爆炸式做法，是一次性背上第4章五大局限的路。

10. 韩国开发环境中的MCP实情

在韩国开发组织里落地MCP，有三点要权衡。

其一是封闭网络与安全审查。金融、公共、电信对引入外部来源代码与外部扩权审查严格。安装外部MCP服务器易在安全审查中被卡住，收窄为只允许自行验证的内部MCP服务器。在韩国封闭网络里，我建议以"仅可信内部服务器、权限最小化"为基本原则。

其二是与本地部署及国产LLM的结合。在使用HyperCLOVA X、KT Mi:dm等本地部署模型的环境里，MCP客户端是否支持成了变量。由于全球客户端先支持，国产技术栈里MCP采用往往慢半拍跟进。导入前务必确认客户端兼容。

其三是小团队占比高。在多为1~5人开发团队的韩国创业公司与SI现场，搭建并维护MCP服务器的余力不足。这类团队若是单一应用，function calling足矣；只有在工具确实必须跨多处共享的时刻才转向MCP，才更具成本效益。

11. 风险 - 标准之战的不确定性

围绕MCP的最大不确定性不是技术局限，而是标准治理。整理我担忧的三点。

  • 主导权集中风险 - MCP虽开放，实则由Anthropic主导。由特定公司主导的标准，方向可能随该公司战略而摇摆。能否过渡到真正中立的治理，是长期存活的关键。
  • 竞争标准的出现 - 若另一阵营推出替代协议，便会爆发"标准之战"。工具提供方要背上同时支持多个标准的负担，标准化本来的收益被稀释。
  • 版本碎片化 - 若第4章的实现分裂因版本差异恶化，可能走到"是标准却不兼容"的最坏局面。

这些风险并非MCP独有，而是每个新生标准都必须通过的关口。导入时，我建议不要把代码深度绑定到某一标准，而是把工具逻辑与协议适配器层分离，让标准变化时只需更换适配器即可。

12. 结论 + 可立即应用的3点

把正文核心浓缩成一句：MCP没死。死的是以为单凭MCP就能解决所有智能体集成的幻想，而在工具被多客户端共享的领域，MCP依然作为事实标准活着。在此之上给出可立即应用的三点。

  1. 以"是否被多客户端共享"来判断。工具只在一个应用里用就function calling，被多个智能体与客户端共享就MCP。以这一个问题而非潮流来决定。
  2. 用一两个价值最高的工具做试点。不要全面标准化，先只把复用收益最大的工具用MCP包装，衡量配置成本对效果，再扩展。
  3. 把工具逻辑与协议适配器分离。为对冲标准之战的不确定性，别深度绑定MCP，把设计做成只需更换适配器层即可。
