用 is 比较，有的数为真有的数为假 - 整数缓存与同一性比较

测试能通过，只有生产环境的条件对不上 - 优化不是规范

2026-08-01 开发/基础设施

引言：测试通过了，只有生产环境的条件对不上

有一个函数用来判断状态码是不是某个特定值。单元测试全部通过。可是一上生产，那个分支一次都没有进去过。把代码再读一遍，逻辑看不出任何毛病。把值打进日志，明明就是期待的那个数字。但条件就是为假。

原因只是一个比较运算符。本该写 == 的位置写成了 is。而这个错误可怕的地方不在于犯了错，而在于 测试通过了。测试把数字直接写进了源码，生产则是经过套接字和字符串解析拿到同一个值。同一个数字，结果却分道扬镳。

本文的主张不是「不要用 is」。is 是一个正当的运算符，也有非它不可的场合。准确的主张是这样。

  • is 问的是「是不是同一个对象」。 它问的不是「值是不是一样」。这是两个不同的问题
  • 值相同是不是同一个对象，由解释器的优化决定。 复用常用对象是为了速度而做的实现选择，不是语言给出的承诺
  • 优化不是规范，所以不能依赖它的结果。 实现一变，答案就变
  • 在小数上碰巧为真才是危险的地方。 因为碰巧对的答案会让 测试通过

最后一条是核心。总是出错的缺陷马上就会被发现，只是偶尔对的缺陷才会一路活到上线。 下面是我实际跑起来，把这个「偶尔」的边界找出来的记录。

运行环境。 下面所有输出都是在 Windows 10 Pro (10.0.19045) 上真实运行的结果。解释器是 CPython 3.13.3，构建信息为 tags/v3.13.3:6280bb5, Apr 8 2025, 14:47:33 [MSC v.1943 64 bit (AMD64)]。所有脚本都先写成文件再执行。

文中出现的缓存范围数字不是规范。「从哪到哪会被共享」这个值只是 在这台解释器、这个版本上测出来的结果。换成别的实现或别的版本可能不同。本文不是让你背这两个数字，而是要说明 依赖这类数字的代码为什么危险。

本文不涉及的内容。 函数默认参数在什么时候求值，在 默认值求值的时点里讲过。话题不同，但教训是接得上的：不要把代码建立在实现细节上。

2. 用 id 看进去 - 同样的值，不同的地址

接着确认 is 到底在看什么。官方文档把 is 定义为 比较对象的标识，而这个标识由 id() 给出。于是我把 id() 直接打印出来。

--- 2-1. id() of two equal values ---
n        id(a)              id(b)              same  a==b
------------------------------------------------------------------
5        140735027553320    140735027553320    True  True
100      140735027556360    140735027556360    True  True

257      1406444444016      1406444443248      False True
1000     1406444443280      1406444443312      False True
1000000000000 1406444443248      1406444444016      False True

--- 2-2. the same object every time you ask for it ---
distinct ids for the value 7 across 5 builds : 1
distinct ids for the value 777 across 5 builds: 3
  (777 ids can repeat by accident: a freed object's address gets reused)

看地址的位数会发现一个有意思的现象。被缓存的值都挤在以 140735… 开头的一块区域里，缓存之外的值则在以 1406… 开头的另一块区域。 前者从解释器启动就存在，后者是用到时才分配的。

可是 2-2 的最后一行藏着陷阱。把值 777 造了五次，出现的不同地址只有 三个。五次里有两次，新对象坐进了先前对象消失后腾出的位置。下面把这一点做得更极端。

--- 2-3. id reuse makes id() alone untrustworthy ---
id of a dead 999999 : 1406444443312
id of a fresh 888888: 1406444443312
addresses equal     : True  <- equal ids, different values

--- 2-4. keeping a reference changes the answer ---
both alive at once  : id equal = False  a is b = False

--- 2-6. sys.getrefcount on a cached object ---
refcount of 1  : 4294967295
refcount of 777: 1
  a cached object is referenced from everywhere in the process
  • 值为 999999 的对象和值为 888888 的对象报出了同一个地址。 因为第一个对象销毁后，第二个复用了它的位置。官方文档也明确写着 id() 只在 对象的生存期内唯一，而且 生存期不重叠的两个对象可以有相同的值
  • 所以把 id() 的值存起来以后再比较的代码，在原理上就是错的。 存下去的那一刻，对象还活着的保证就没有了
  • 2-4 中把两个对象同时保活，地址就分开了。也就是说 同一段代码，握不握着引用，答案会不一样
  • 最后那块的引用计数很扎眼：被缓存的 1 计数是 四十二亿量级。在这台解释器上长期复用的对象会被标记成不参与回收。而 777 的计数是 1

不过这里冒出一个意料之外的结果。缓存范围 之外的 257，用运算式造出来再比较，居然为真。

--- 2-5. two address regions, and an unexpected True ---
200 + 56 = 256  300 - 44 = 256  x is y = True
200 + 57 = 257  300 - 43 = 257  p is q = True
  the second pair is OUTSIDE the cache yet still True.
  the cache is not the only thing that makes 'is' true - see experiment 3.
  compare with values built at run time:
  make(257) is make(257) = False

同样是 257，写成运算式就为真，放到运行时构造就为假。 光靠缓存解释不通。还有第二个原因。

3. 同样的代码，执行方式不同答案也不同

第二个原因是 编译器对常量的处理。编译代码时如果同一个字面量出现多次，编译器会把它合并成一个对象放进代码对象的常量表。像 200 + 57 这样的表达式也会在编译期算好变成常量。运行时只是把那个常量取出来用，于是两个名字自然指向同一个对象。

--- 3-1. module level, one file, two statements ---
a = 257 ; b = 257   ->  a is b = True

--- 3-2. inside a function, same code object ---
same function body  -> True
two function bodies -> True

--- 3-3. what the compiler stored ---
co_consts of f() : (None, 257)
g1 const id      : 140735026668016
g2 const id      : 140735026668016
same object      : True

bytecode of f():
 13           RESUME                   0

 14           LOAD_CONST               1 (257)
              STORE_FAST               0 (a)

 15           LOAD_CONST               1 (257)
              STORE_FAST               1 (b)

 16           LOAD_FAST_LOAD_FAST      1 (a, b)
              IS_OP                    0
              RETURN_VALUE

字节码把话说尽了。两行都是 LOAD_CONST 1。把常量表的同一个格子读了两次，结果只能是同一个对象。 更进一步，两个不同函数的常量竟然也是同一个对象，因为编译一个模块期间常量是共享的。

那么把编译单元切开会怎样。

--- 3-4. exec: one string vs two strings ---
exec, single string  -> True
exec, three strings  -> False

--- 3-5. compile() separately then exec ---
separate code objects -> False
const in c1 : [257]
const in c2 : [257]
same object : False

--- 3-6. a real REPL, statement by statement (code module) ---
REPL, line by line  -> False
REPL, small number -> True

结果彻底分开了。看 3-5，两个代码对象各自持有一个叫 257 的常量，可 这两个并不是同一个对象。工程上最重要的是 3-6：交互式解释器里一行就是一个编译单元，常量不共享，所以结果为假。

我还跨进程验证了一遍。

--- 3-7. child process: python -c, script file, piped stdin, -i ---
python -c            -> True
script file          -> True
piped stdin (python) -> True
piped stdin (-i)     -> False
  stderr tail of -i  : >>> >>> >>> >>>

--- 3-8. the same test written so the compiler cannot help ---
module level, run-time values -> make(257) is make(257) = False
module level, literal values  -> 257 is 257 (via consts)  = True

把同样两行的结果汇成表就是下面这样。这是本文第二重要的一张表。

执行方式a = 257; b = 257 之后的 a is b原因

工程上的含义很重。交互式里确认的结果，可能和脚本的行为不一致。 如果交互式给了假，你据此判断「果然不能这么写」而改成 ==，那是幸运；反过来如果脚本给了真，你觉得「这不是能用吗」就放过去了，那段代码 会在值的来源改变的那一刻悄悄崩掉。

4. 字符串也是一样

这不只是整数的事。字符串按同样的原理被共享，只是条件略有不同。

--- 4-1. literals in one compilation unit ---
s1 = "total" ; s2 = "total"      -> s1 is s2 = True
with a space in it               -> t1 is t2 = True

--- 4-2. built at run time ---
"to" + "tal"        is base : True   == base : True
parts[0] + parts[1] is base : False   == base : True
"".join(parts)      is base : False   == base : True
percent format      is base : False   == base : True
f-string            is base : False   == base : True

--- 4-3. length matters for run-time strings ---
built            is-literal   len
----------------------------------------
''               True         0
'x'              True         1
'xx'             False        2
'xxx'            False        3
'xxxx'           False        4
'xxxxx'          False        5

4-2 第一行和第二行的差别是关键。字面量之间的相加在编译期就被合成常量，而从列表里取出的片段相加则是在运行时生成新对象。值完全一样，只有同一性判断分开。

4-3 说明只有空字符串和单个字符会被共享。这同样是预先创建常用对象的优化。下面把编译单元切开再看一次。

--- 4-4. identifier-shaped vs not, from a REPL (separate units) ---
  identifier-shaped     -> True
  with a space          -> False
  with a hyphen         -> False
  empty string          -> True
  single ascii char     -> True

--- 4-5. sys.intern forces sharing ---
run-time built, two copies       : False
after sys.intern on both         : True
interned is the literal          : True

--- 4-6. slicing produces new objects ---
name[:] is name       : True    (full slice can return self)
name[0:7] is name     : True
name[1:] is "ser_id"  : False
name[1:] == "ser_id"  : True

4-4 就是「标识符形状的字符串会被驻留」这句话的实体。编译单元明明是分开的，user_id 却为真，而 一旦掺进空格或连字符就变成假。因为只有能当变量名用的那种形状的字符串才会被自动共享。

  • 也就是说 像键名那样标识符形状的字符串，is 碰巧对的概率很高。 这正是把这个缺陷藏得最好的地方
  • 反过来，用户名、句子、带连字符的编码值几乎总是为假。同一段代码会因为数据不同而表现不同
  • 想强制共享就得显式调用驻留函数，4-5 里结果因此翻成了真。但它的目的是 省内存，不是用来做比较的工具
  • 4-6 的第一行也是个坑。整段切片 有可能返回同一个对象。「切片一定是新对象」这个猜测同样不成立

这个问题在工程上会在哪里爆掉，就是最后一块拼图：值 从外部进来的那一刻。

--- 4-7. where this bites: values that came from outside ---
json value  is literal : False   == literal : True
csv  value  is literal : False   == literal : True

--- 4-8. the same for other immutable types ---
() is ()            : True
tuple() is tuple()  : True
(1,2) built vs lit  : False
0.0 is 0.0 (consts) : True
float('0.0') twice  : False

同样的字符串，从序列化格式里取出来的值和字面量是两个对象。 配置文件、接口响应、表格文件、用户输入全都一样。开头那个场景说的正是这件事：测试把值写进了源码，生产是从外面收来的。

5. == 和 is 问的是两个不同的问题

到这里做个归纳。这两个运算符不是替代品，而是 两个不同的问题。

--- 5-1. the two questions are different ---
a == b : True    same value
a is b : False   different objects
a is c : True    same object
after b.append(4)  a = [1, 2, 3]  b = [1, 2, 3, 4]
after c.append(9)  a = [1, 2, 3, 9]  c = [1, 2, 3, 9]   <- c IS a

--- 5-2. equal but not identical, identical but not equal ---
x = float('nan')
  x is x : True    same object
  x == x : False   a value that is not equal to itself
  x in y : True    'in' tries 'is' first, then '=='
  any(v == x for v in y) : False

--- 5-3. __eq__ can say anything; 'is' cannot be overridden ---
p == q : True   __eq__ decides
p is q : False  identity is not overridable
p == 5 : True
p is p : True

--- 5-4. objects that define no __eq__ fall back to identity ---
m == n : False   default __eq__ IS identity
m is n : False

5-2 证明了这两个问题完全独立。存在一个值，它是同一个对象，却不等于它自己。 而判断是否属于某个序列的运算会先看同一性，于是给出真；只用值比较去确认则是假。如果它们是同一个问题，这种事根本不可能发生。

5-4 解释了这个缺陷为什么发现得晚。没有定义相等行为的类，默认行为本身就是同一性比较。 所以在这种类上两个运算符永远给出同样的答案。等到哪天有人给这个类加上相等行为，一直好好运行的同一性比较就突然错了。

运算符所问的问题实现方式类能否改变该用在哪
a == b值是否相同类的相等行为能改所有值比较
a is b是否同一个对象标识比较不能改单例、哨兵、共享判断
a != b值是否不同类的不等行为能改所有值比较
a is not b是否不同对象标识比较不能改单例、哨兵

「不能改」是 is 唯一的长处。而需要这个长处的场合确实存在。

--- 5-5. when 'is' is the right tool: singletons ---
None is None            : True
Ellipsis is Ellipsis    : True
NotImplemented is itself: True
  fetch('a' ) -> None
  fetch('b' ) -> 0
  fetch('c' ) -> ''
  fetch('zz') -> 'MISS'
  note 'a' holds None and 'b' holds 0: a truthiness check would lose both

--- 5-6. the falsy trap that 'is SENTINEL' avoids ---
  bad('a' )   -> 'MISS'
  bad('b' )   -> 'MISS'
  bad('c' )   -> 'MISS'
  bad('zz')   -> 'MISS'
  three stored values were reported as missing

把这两块并排看。面对同一个存储，一个回答得完全准确，另一个丢了三条。 当存进去的值是「无」、是 0、是空字符串时，只看真假的判断会把它们统统判成「没有」。这时需要的是 世上只有一个的标记对象，而确认它的唯一办法就是 is。

6. is None 为什么安全，is True 为什么不是

「比较 None 要用同一性判断」这条规则广为人知。我把理由实际跑出来确认了一遍。

--- 6-1. None is a singleton: try to make a second one ---
type(None)          : <class 'NoneType'>
type(None)() worked : True  <- it returns the same object
copy.copy(None) is None      : True
copy.deepcopy(None) is None  : True
pickle round trip is None    : True
id(None) stable in a loop    : True

--- 6-2. None across a process boundary ---
id(None) here      : 140735026668016
id(None) in child  : 140735026668016

--- 6-3. why 'is None' and not '== None' ---
w == None : True   <- a class talked its way into looking like None
w is None : False  <- identity cannot be talked into anything

a column-style 'missing' object:
  m == None : True
  m is None : False
  if m == None: would take the branch; if m is None: would not
  • 没有办法造出第二个。 直接调用它的类型，回来的还是原来那个对象。拷贝、深拷贝、序列化往返全都是同一个对象
  • 所以 x is None 与解释器的优化完全无关，永远准确。它和第 1 节的缓存故事性质完全不同
  • 6-3 就是不能用等值运算符的理由。类重定义相等行为之后，并非 None 的对象会声称自己等于 None。 处理表格数据的库确实在用这种「缺失值」对象
  • 6-2 很有意思但容易误读。父进程和子进程给出同一个地址，是因为这个对象在可执行文件里有固定的位置。但这不代表可以跨进程比较 id() 的值。 第 2 节已经看到，普通对象的地址是会被复用的

那么真假值也是只有一个的对象，用 is True 是不是就没问题？语法上安全，但 语义是错位的。

--- 6-4. True is a singleton too, but the comparison is still wrong ---
bool(1) is True     : True
True is True        : True

value    type           == True    is True    if value:
--------------------------------------------------------
1        int            True       False      True
1.0      float          True       False      True
True     bool           True       True       True
'1'      str            False      False      True
[1]      list           False      False      True

--- 6-5. a function returning 1 instead of True ---
legacy_flag    -> 1      if v:True    v == True:True    v is True:False
modern_flag    -> True   if v:True    v == True:True    v is True:True

看表的最后一列。五个值全都是真值。 可是同一性判断那一列只有一个为真。也就是说，用 is True 去问「是不是真」，会把绝大多数真值判成假。

6-5 是工程上的场景。一个老函数原本返回 1，后来改成返回真值，或者反过来，真值判断和等值比较都不动，只有同一性那个分支翻了过来。 变更记录上只写着「整理成布尔值」，很难把它和事故联系起来。

现在把开头那个事故原样复现。

--- 6-6. 'is 0' and friends: run-time values break the spell ---
  value 0       v == 0:True   v is zero:True   | v == 257:False  v is big:False
  value 1       v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 256     v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 257     v == 0:False  v is zero:False  | v == 257:True   v is big:False
  value 1000    v == 0:False  v is zero:False  | v == 257:False  v is big:False

--- 6-7. the dangerous shape: a test that passes for the wrong reason ---
status_code_ok(200)          : True   <- literal 200, same const pool
status_code_ok(int('200'))   : True   <- 200 is inside the cache
status_code_ok(199 + 1)      : True
status_code_ok2(500)         : True   <- literal, const pool again
status_code_ok2(int('500'))  : False   <- outside the cache: FALSE
status_code_ok2(499 + 1)     : True

6-7 是整篇文章的浓缩。写成 code is 200 的那个函数 三种调用方式全部通过，因为 200 落在缓存范围里。而写法完全相同的 code is 500 函数，一喂给它从字符串构造的值就变成假。

这里就是本文的核心。 两个函数犯的是 完全相同的错误，可一个通过一个失败。差别只在于状态码那个数字落在缓存范围之内还是之外。

为什么这很危险？用 200 段成功码写的测试全都是绿的。 如果没有测试错误处理路径，就会把只在 400 段、500 段崩掉的缺陷发出去。而失败路径恰恰是测试覆盖最薄的地方，于是这个缺陷 正好藏在最难被发现的位置。

7. 布尔就是整数 - 字典的键会重叠

布尔和整数的关系看上去是另一个话题，根子却是同一个：什么会被当成同一样东西。

--- 7-1. bool is a subclass of int ---
issubclass(bool, int) : True
isinstance(True, int) : True
int(True), int(False) : 1 0
True + True           : 2
sum([True, True, False]): 2

--- 7-2. equality and hashing ---
expression       value    hash
--------------------------------------
True             True     1
1                1        1
1.0              1.0      1
False            False    0
0                0        0
0.0              0.0      0

True == 1     : True
True is 1     : False
False == 0    : True
hash(True) == hash(1) : True

--- 7-3. dict keys collapse ---
d after three assignments : {1: 'float one'}
len(d)                    : 1
type of the surviving key : int
insert True first         : {True: 'int one'}  key type: bool

官方文档把布尔类型定义为整数的子类，不能再被继承，而且 实例只有真和假两个。结果就是 7-2：值相同，哈希也相同，所以在字典里占同一个槽。

7-3 最后两行给出了确切行为：先插入的键留下，只有值被覆盖。 先放整数，键的类型就还是整数；先放布尔，就还是布尔。换句话说，留下来的键是什么类型，取决于插入顺序。

--- 7-4. the same collapse in sets and counters ---
{1, True, 1.0}            : {1}
len({0, False})           : 1
Counter([1, True, 1, True]): Counter({1: 4})

--- 7-5. a config table that quietly loses a row ---
declared 5 entries, got   : 3 -> {0: 'disabled', 1: 'enabled', 2: 'verbose'}
LEVELS[False]             : disabled
LEVELS[0]                 : disabled  <- same slot

--- 7-6. list membership and index ---
True in row               : True
row.index(True)           : 1
False in row              : True
row.count(1)              : 1
[True, 1].count(1)        : 2

7-5 就是事故真正的样子。写了五行，只剩三行。 既不报错也不告警。代码评审时那五行还都好好地摆在那里，所以很难察觉。配置表里一旦把 0 和假一起用上，这件事就会发生。

7-6 的计数结果也值得留意。列表里同时有真值和整数 1 时，1 的个数会被数成 2。 统计逻辑就是在这里出错的。

--- 7-7. so how do you actually distinguish them? ---
  True   -> is-check:bool    type() is bool:True    isinstance int:True
  False  -> is-check:bool    type() is bool:True    isinstance int:True
  1      -> is-check:int     type() is bool:False   isinstance int:True
  0      -> is-check:int     type() is bool:False   isinstance int:True
  1.0    -> is-check:float   type() is bool:False   isinstance int:False

--- 7-8. JSON round trip keeps them apart, dict keys do not ---
json.dumps({'a': True, 'b': 1}) : {"a": true, "b": 1}
json.dumps({True: 'x', 1: 'y'}) : {"true": "y"}

7-7 给出了解法：必须检查类型本身是不是布尔类型。 判断是不是整数的检查会放布尔过去。把「只收数字」的校验写成那样，布尔值就会原封不动地流进来。

7-8 第二行显示了后果：写了两个条目，序列化结果里只剩一个，键还变成了字符串形式的真。 这不是序列化函数的错，在它看到之前，字典里就已经合并完了。

8.2 第二级 - 自己遍历语法树

要补上盲区就得把代码当结构来读。我用标准库的语法树模块做了一个检查器，核心部分如下。

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

class Checker(ast.NodeVisitor):
    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None                       # singleton, fine
            return "LITERAL", "literal comparison"
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "display literal"
        if isinstance(node, ast.BinOp):
            return "EXPR", "arithmetic result"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", "conversion result"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None                       # singleton name, fine
            if node.id in self.consts:
                return "CONSTNAME", "name bound to a literal"
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON", "is True/False"))
        self.generic_visit(node)

要点是先把模块顶层的 名字 = 字面量 赋值收集起来，再拿比较式的两侧去和这份清单对照。跑在样例文件上的结果如下。

类别抓什么解释器告警处理
LITERAL与字面量做 is 比较抓得到立刻换成 ==
EXPR与运算、转换结果比较抓不到立刻换成 ==
CONSTNAME与数字、字符串常量名比较抓不到比值就用 ==，要单例就用标记对象

（正常）is None、is not None不适用原样保留

9. 团队规范与检查清单

工具只能找出代码里已经有的东西。要挡住新进来的，就需要规范。下面只写了从上面的运行结果里直接推得出来的内容。

9.1 规范

  1. is 只用于单例。 None、显式创建的标记对象、枚举成员。看到这三者之外的 is，评审时就要问原因
  2. 值比较一律用 ==，没有例外。 整数、字符串、状态码、配置值都算。「数小所以没事」不构成理由
  3. 不要用真值判断来检测「没有值」。 5-6 已经看到，0 和空字符串会一起消失。造一个标记对象，用 is 去确认
  4. is True 只在问「是不是恰好那个对象」时使用。 若确属此意，请写注释说明为什么。 没有注释的 is True 一律视作失误
  5. 类型判断要直接看类型。 判断是不是整数的检查会放布尔过去（7-7）
  6. 字典和集合的键不要混用 0 与假、1 与真。 会像 7-5 那样悄悄少掉几行
  7. 测试不要只喂字面量。 这一条最重要。用经过字符串解析、序列化往返、真实输入输出的值做同样的验证。理由就是 6-7
  8. 不要保存 id() 的值，也不要跨进程比较它。 2-3 已经看到地址会被复用

9.2 检查清单

  • 已在构建里加入把解释器告警升级成错误的步骤
  • 已在整个仓库跑过一遍语法树检查器，并复核了结果
  • 已把所有 == None 改成同一性判断
  • 残留的 is True 和 is False 全部带有说明理由的注释
  • 没有与常量名做 is 比较的地方（这是解释器告警抓不到的形态）
  • 「没有值」的判定使用标记对象，且该对象没有泄漏到模块之外
  • 每一处整数校验都判断过布尔值通过是否可以接受
  • 字典、集合的键里没有 0 和假同时出现
  • 统计、计数逻辑里不会混入布尔值和整数
  • 测试用 从外部进来的值也验证了同一个分支
  • 不只测成功码，也测 失败码的路径（6-7 的陷阱就在那里）
  • 注释或文档里没有把缓存范围数字当作依据的地方
  • 没有拿交互式里确认的结果当作脚本行为的依据
  • 只有枚举、标记对象这类 有意设计的单例还在用 is

10. 本文没能验证的部分

把没验证过的事情写得像验证过一样，会把下一个人带偏。这里把边界讲清楚。

  • 其他实现。 所有测量都是在一个解释器实现、一个版本、一个操作系统上完成的。本文不主张换个实现也会得到同样的结果。 恰恰相反，本文的主张就是它可能不同
  • 其他版本。 同一个实现，不同版本之间优化也可能改变。2-6 里看到的引用计数行为就是这样一个区域
  • 静态检查工具的实际行为。 8-1 已说明这个环境里一个都没装。这也是文中不引用规则编号的原因
  • 多线程与多解释器环境。 对象共享的方式在那里可能不同，本文没有涉及
  • 性能影响。 同一性判断比等值调用快是事实，但这个差距没有测量。而且 更快地给出错误答案没有任何价值
  • 其他语言的同一性比较。 据说存在类似的陷阱，但本文没有实际运行验证

不过这些没能验证的项目有个共同点：它们全都是关于「实现怎么做」的问题。 而本文的结论并不需要知道实现的行为才成立。无论实现怎么做，值比较用 == 就对了。 这是让你不必了解实现的唯一办法。

结论：能通过的测试才是最危险的

归纳一下。is 问的是「是不是同一个对象」。拿它做值比较，答案对不对由 解释器的优化决定。在这台解释器上测得的共享范围是从 -5 到 256，短字符串和标识符形状的字符串也会被共享。可那个范围是 测量值，不是规格。

而且原因不止一个，这让问题更难缠。缓存是一个，编译单元内的常量共享是另一个。因为后者，同一段代码在脚本里为真，在交互式里为假。 换个验证方式，结论就翻过来了。

最重要的是最后这一点。这个缺陷并不是总是错的，它偶尔是对的。 用 200 状态码写的测试会通过，只有 500 段会崩；把值写进源码的测试会通过，只有从外部收来的值会崩。所以这个缺陷穿过绿色的测试发布出去，然后在最难核查的路径上第一次现身。

规则很短：is 只用在 None、标记对象和枚举成员上。 其余一律用 ==。守住这条规则，你就不需要知道缓存范围从几到几。让人不必了解实现细节，正是一条好规则该有的样子。

现在就能做一件事：在仓库里搜索 is，数一数和 None 之外的东西比较的行。 其中如果有和常量名比较的，解释器告警绝对抓不到。而如果那段代码的测试是绿的，值得确认一下 绿是因为代码对，还是因为数字小。

# `==` 与 `is` — 判断表 / 复现代码 / 检测器 / 检查清单

> 来源: braindetox.kr — 用 is 比较，有的数为真，有的数为假
> 测量环境: Windows 10 Pro (10.0.19045) / CPython 3.13.3 (MSC v.1943 64bit AMD64)
> 把这个文件整篇贴给 AI，写「按这套标准检查我们的代码库」即可使用。
> 下面出现的缓存范围数字是 **在这台解释器上测出来的值**，不是语言规范。换实现、换版本都可能不同。

## 0. 一句话总结

`is` 问的是「是不是同一个对象」，`==` 问的是「值是不是一样」。
想比较值却写成 `is`，答案对不对由 **解释器的优化**决定。
优化不是规范，所以 **不能依赖这个结果。**

## 1. 判断表 — 该用哪一个

| 想做的事 | 该用 | 不该用 | 原因 |
|---|---|---|---|
| 值是否相同 | `a == b` | `a is b` | 值相同不保证是同一个对象 |
| 是不是 None | `x is None` | `x == None` | `__eq__` 可以被任何类重定义 |
| 是不是非 None | `x is not None` | `x != None` | 同上 |
| 是否为真 (一般情况) | `if x:` | `x is True` | `1`、`[1]`、`'a'` 为真，但 `is True` 为假 |
| 是否恰好是 `True` 对象 | `x is True` | — | 如果确实是这个意图就正确。请加注释 |
| 是不是 bool 类型 | `type(x) is bool` | `isinstance(x, int)` | `bool` 是 `int` 的子类 |
| 区分「没有值」 | `x is SENTINEL` | `if not x:` | `0`、`''`、`[]` 会被误判为没有值 |
| 是否共享同一个对象 | `a is b` | `a == b` | 这才是 `is` 的本职 |
| 比较 Enum 成员 | `x is Color.RED` | `x == 'RED'` | Enum 成员是单例 |
| 比较字符串的值 | `s == 'admin'` | `s is 'admin'` | 运行时生成的字符串不会被共享 |

## 2. 复现代码 — 直接粘贴运行

```python
# repro.py
import sys

def make(n):
    """在运行时构造整数，避开编译期常量复用。"""
    return int(str(n))

print(sys.version)

for n in (0, 5, 256, 257, 1000):
    a, b = make(n), make(n)
    print(n, "is:", a is b, " ==:", a == b)

def shared(n):
    return make(n) is make(n)

lo, hi = 0, 1 << 20
while hi - lo > 1:
    mid = (lo + hi) // 2
    if shared(mid):
        lo = mid
    else:
        hi = mid
print("最后一个被共享的值 :", lo)

lo2, hi2 = -(1 << 20), 0
while hi2 - lo2 > 1:
    mid = (lo2 + hi2) // 2
    if shared(mid):
        hi2 = mid
    else:
        lo2 = mid
print("第一个被共享的值   :", hi2)
print("测得的范围         :", hi2, "..", lo)
```

测得结果 (CPython 3.13.3 / Windows): 共享范围 `-5 .. 256`，共 262 个对象。
再强调一次，这是 **测量值**，不是规格。

## 3. 运行方式不同，答案也不同

同样两行，结果不一样。实测:

| 运行方式 | `a = 257; b = 257` 之后的 `a is b` |
|---|---|
| 脚本文件 | `True` |
| `python -c` | `True` |
| 从标准输入喂进去 | `True` |
| `exec()` 传一个字符串 | `True` |
| `exec()` 传三个字符串 | `False` |
| 分两次调用 `compile()` | `False` |
| 交互式解释器 (逐行) | `False` |
| 运行时构造的值 `make(257)` | `False` |

教训: **同一个编译单元内相同的字面量会被合并成一个对象。**
在交互式里确认的结果，可能和脚本的行为不一致。

## 4. 检出危险写法

### 4-1. 只用标准库 — 把编译器警告变成错误

```bash
# 把字面量和 is 放在一起比较时，解释器会给出 SyntaxWarning
python -W error::SyntaxWarning -c "import py_compile,sys; py_compile.compile(sys.argv[1], cfile=None, doraise=True)" target.py
```

- 能抓到: `x is 200`、`x is 'admin'`、`x is ()`
- **抓不到**: `x is CONST`、`flag is True`、`a is b`
- 不依赖任何第三方包就能让构建步骤失败

### 4-2. 用 `ast` 自己走一遍 (`is_lint.py`)

```python
#!/usr/bin/env python3
"""找出危险的 is 用法。发现任何一处即返回退出码 1。"""
import ast, os, sys

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

def module_consts(tree):
    out = {}
    for stmt in tree.body:
        if isinstance(stmt, ast.Assign) and isinstance(stmt.value, ast.Constant):
            v = stmt.value.value
            if isinstance(v, (int, float, str, bytes)) and not isinstance(v, bool):
                for t in stmt.targets:
                    if isinstance(t, ast.Name):
                        out[t.id] = v
    return out

class Checker(ast.NodeVisitor):
    def __init__(self, consts):
        self.consts, self.hits = consts, []

    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None
            return "LITERAL", "%s 字面量 %r" % (type(node.value).__name__, node.value)
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "显示式字面量"
        if isinstance(node, ast.JoinedStr):
            return "LITERAL", "f-string"
        if isinstance(node, ast.BinOp):
            return "EXPR", "运算结果"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", fn + "() 的结果"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None
            if node.id in self.consts:
                return "CONSTNAME", "绑定到字面量的名字 %r" % (self.consts[node.id],)
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON",
                                      "不要写 is %r，用真值判断或 ==" % side.value))
        self.generic_visit(node)

def scan(path):
    src = open(path, encoding="utf-8").read()
    tree = ast.parse(src, filename=path)
    ck = Checker(module_consts(tree))
    ck.visit(tree)
    return sorted(set(ck.hits))

def main(root):
    total = 0
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames
                       if d not in ("__pycache__", ".git", ".venv", "node_modules")]
        for fn in sorted(filenames):
            if not fn.endswith(".py"):
                continue
            p = os.path.join(dirpath, fn)
            try:
                hits = scan(p)
            except SyntaxError as exc:
                print("%s: 解析失败 %s" % (p, exc))
                continue
            for lineno, kind, detail in hits:
                print("%s:%d: %s %s" % (p, lineno, kind, detail))
                total += 1
    print("共 %d 处" % total)
    return 1 if total else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1] if len(sys.argv) > 1 else "."))
```

检出类别:

| 标签 | 含义 | 处理 |
|---|---|---|
| `LITERAL` | 与字面量做 `is` 比较 | 立刻换成 `==` |
| `EXPR` | 与运算或转换结果做 `is` 比较 | 立刻换成 `==` |
| `CONSTNAME` | 与绑定到数字或字符串的名字做 `is` 比较 | 比值就用 `==`，要单例就用 `object()` 哨兵 |
| `BOOLSINGLETON` | `is True` / `is False` | 改成真值判断或 `==`。确属有意则加注释 |

### 4-3. 如果可以用第三方工具

- `flake8` 系: `F632` (与字面量做 is 比较)、`E712` (`== True` 比较)
- `pylint`: `literal-comparison`、`singleton-comparison`
- `ruff`: `F632`、`E711`、`E712`
- 本环境一个都没装，所以用 4-1 和 4-2 代替

## 5. 布尔与整数 — 重叠的地方

| 表达式 | 结果 | 说明 |
|---|---|---|
| `issubclass(bool, int)` | `True` | bool 是 int 的子类 |
| `True == 1` | `True` | 值相同 |
| `True is 1` | `False` | 是两个对象 |
| `hash(True) == hash(1)` | `True` | 在字典里落到同一个槽 |
| `{1: 'a', True: 'b', 1.0: 'c'}` | `{1: 'c'}` | **先插入的键留下，只有值被覆盖** |
| `{1, True, 1.0}` | `{1}` | 集合也一样会塌缩 |
| `sum([True, True, False])` | `2` | 按整数相加 |
| `type(True) is bool` | `True` | 类型判断要这样写 |
| `isinstance(True, int)` | `True` | int 检查挡不住布尔值 |

## 6. 检查清单

- [ ] 没有用 `is` 做值比较的地方 (`is_lint.py` 通过)
- [ ] 已把 `-W error::SyntaxWarning` 加进 CI
- [ ] 已把 `x == None` 改成 `x is None`
- [ ] `x is True` 只保留在确实指「恰好是 True 对象」的地方，并加了注释
- [ ] 判断「没有值」用哨兵 (`object()`)，不用 `if not x:`
- [ ] 所有 `isinstance(x, int)` 的地方，都确认过布尔值通过是否可接受
- [ ] 字典和集合的键没有混用 `0/False`、`1/True`
- [ ] 测试没有只喂字面量，还覆盖了 **经过解析、序列化或套接字**的值
- [ ] 没有任何注释或文档依赖那个缓存范围
- [ ] 不保存 `id()` 的值，也不跨进程比较它
- [ ] 只对 Enum、哨兵这类 **有意设计的单例**使用 `is`
- [ ] 评审规范里写明「`is` 只用于单例」

## 7. 不要做的事

- 把缓存范围数字 **当成语言规范**写进文档 — 那是实现细节
- 拿交互式里看到的 `is` 结果去解释脚本的行为 — 编译单元不一样
- 因为 `id()` 相同就断定是同一个对象 — 生存期不重叠的两个对象可以有相同的 `id()`
- 用 `is True` 去问「是否为真」 — 绝大多数为真的值都会被挡掉
- 想用 `isinstance(x, int)` 排除布尔值 — 它会通过
- 因为测试是绿的就放着 `is` 比较不管 — **也许只是在小数值上侥幸通过了**
