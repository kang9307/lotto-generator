1. 지능의 가격표와 '하네스 세금' — 연구의 문제의식

현대 소프트웨어 개발 생태계에서 자율 코딩 에이전트(Autonomous Coding Agent)는 단순한 자동완성 플러그인을 넘어 개발자의 터미널과 코드베이스를 직접 조작하는 실무 파트너로 안착했다. 수많은 엔지니어링 팀이 에이전트를 도입할 때 던지는 첫 번째 질문은 대개 어떤 파운데이션 모델의 추론 능력이 뛰어난가에 집중된다. 벤치마크 리더보드의 상단을 차지하는 모델을 선택하고, 모델 제공사가 공식 배포하는 커맨드라인 인터페이스(CLI) 도구를 설치하면 최적의 생산성을 얻을 수 있으리라는 믿음이 일반적이다.

그러나 실제 프로덕션 파이프라인에서 에이전트를 대규모로 구동하는 조직들은 기이한 청구서와 마주하게 된다. 동일한 모델 가중치를 기반으로 동일한 소프트웨어 버그 수정 과제를 해결하도록 지시했음에도 불구하고, 어떤 런타임 래퍼를 씌웠는가에 따라 월간 API 호출 비용이 1.5배에서 2배 이상 차이 나는 현상이 빈번하게 관찰된다. 작업의 최종 해결 성공률이나 패치 품질에는 유의미한 차이가 없음에도 불구하고, 에이전트를 구동하는 인터페이스 계층 자체가 막대한 추가 비용을 발생시키는 것이다.

이러한 비용 오버헤드를 소프트웨어 공학 커뮤니티에서는 하네스 세금(Harness Tax)이라고 부른다. 하네스란 언어 모델이 환경과 상호작용할 수 있도록 시스템 프롬프트를 조립하고, 파일 입출력 및 셸 명령 도구를 주입하며, 대화 턴(turn) 사이의 컨텍스트 윈도우를 관리하는 오케스트레이션 프레임워크를 뜻한다. 2026년 4월 Siddharth Sambharia가 Portkey 엔지니어링 블로그에서 개념화한 이 표현은, 모델의 고유 지능 비용 위에 하네스 설계가 덧씌우는 구조적 비효율을 정확히 지적한다.

2026년 9월 16일, UC Berkeley Sky Lab과 모델 평가 플랫폼 Arena의 연구진(Melissa Z. Pan, Shuo Yang, Negar Arabzadeh, Wei-Lin Chiang, Ion Stoica, Matei Zaharia)은 바로 이 하네스 세금의 실체를 정밀하게 계측한 연구 HarnessTax를 공개했다. 연구진은 코딩 에이전트의 최종 성과가 모델 자체의 지능에서 나오는지, 아니면 수천 줄의 시스템 프롬프트와 정교한 툴체인으로 무장한 하네스에서 나오는지를 숫자로 추적했다. 그 결과는 소프트웨어 엔지니어링 업계의 상식을 뒤흔드는 3가지 핵심 발견으로 이어졌다.

2. 실험 설계 — 21개 모델-하네스 조합과 3회 반복 검증 절차

HarnessTax 연구팀은 하네스의 독자적 영향을 분리해 내기 위해 통제된 다차원 평가 환경을 구축했다. 특정 모델과 특정 하네스의 결합에만 유리한 편향을 방지하기 위해 7종의 프론티어 및 오픈 언어 모델과 3종의 대표적 하네스 아키텍처를 교차 결합하여 총 21개 모델-하네스 쌍(model-harness pairs)을 구성했다.

평가 대상에 포함된 7개 언어 모델은 시장의 최첨단 프로덕션 모델부터 경량 및 오픈가중치 모델까지 고르게 망라한다:

  • Claude Fable 5: 복잡한 추론과 코딩 태스크에서 최상위 성능을 대표하는 Anthropic의 플래그십 모델
  • Claude Opus 4.8: 장기적 아키텍처 분석과 방대한 컨텍스트 추론에 특화된 고성능 모델
  • Claude Sonnet 4.6: 엔지니어링 실무 현장에서 비용 대비 처리 효율로 가장 널리 채택되는 주력 모델
  • Claude Haiku 4.5: 빠른 응답 속도와 저지연 처리에 초점을 맞춘 경량 고효율 모델
  • GPT-5.6 Sol: 범용 코딩 및 시스템 조작 벤치마크에서 강력한 실행력을 보여주는 OpenAI의 프론티어 모델
  • GPT-5.6 Luna: 고속 배치 연산 및 실시간 대화형 개발 보조를 겨냥한 최적화 모델
  • Kimi K3: 폐쇄형 상용 API 모델들과 동등한 비교군 역할을 수행하는 오픈웨이트(open-weight) 대표 모델

이들 모델을 감싸는 하네스로는 서로 완전히 다른 설계 철학을 지닌 3종이 선정되었다. 첫째는 Anthropic의 공식 에이전트 CLI인 Claude Code로, 풍부한 시스템 가이드라인과 정교한 린팅, 프로젝트 분석 도구를 내장한 고기능 하네스다. 둘째는 OpenAI 생태계에서 널리 활용되는 Codex CLI로, 터미널 제어와 스크립트 실행에 최적화된 상용급 래퍼다. 셋째는 본 연구에서 비교의 핵심 축으로 동작하는 Pi다. Pi는 특정 하드웨어나 라즈베리 파이와는 전혀 무관한 최소 오픈소스 하네스로, 모델에게 파일 읽기(read), 파일 쓰기(write), 부분 수정(edit), 셸 실행(bash)이라는 단 4개의 원초적 도구 스키마만을 제공한다.

평가 벤치마크로는 소프트웨어 저장소 수준의 실제 버그 패치 능력을 검증하는 SWE-bench Lite와 터미널 환경에서의 시스템 설정 및 스크립트 실행 능력을 평가하는 Terminal-Bench 2.0이 사용되었다. 연구진은 각 벤치마크에서 30개의 과제를 무작위 추출한 뒤, 21개 모델-하네스 조합마다 각 과제를 3회씩 반복 실행하여 총 수천 회의 세션 데이터를 축적함으로써 일시적 생성 요동이나 네트워크 편차를 통계적으로 상쇄했다.

3. 발견 1 — 성공률은 대등하고 비용만 최대 2배 벌어지다

연구진이 확인한 첫 번째 핵심 발견은 충격적이다. 하네스의 복잡성과 도구 세트의 풍부함은 작업 성공률을 끌어올리는 데 거의 기여하지 못하는 반면, 작업을 완수하는 데 들어가는 API 청구 비용에는 막대한 증폭 효과를 미쳤다. 최고 지능 모델인 Claude Fable 5를 기준으로 측정했을 때, SWE-bench Lite에서의 문제 해결 성공률은 세 하네스 모두에서 통계적으로 대등한 수준을 유지했다.

실제 계측치에 따르면 Claude Fable 5의 성공률은 고기능 공식 하네스인 Claude Code에서 97.8%를 기록했고, 타사 도구인 Codex CLI와 최소 하네스인 Pi에서 각각 96.7%를 기록했다. 성공률 격차는 불과 1.1%포인트에 불과해 실질적인 엔지니어링 결과물의 품질 차이는 체감할 수 없는 수준이었다. 그러나 각 과제를 해결하는 데 소모된 평균 비용은 정반대의 양상을 보였다. 과제당 처리 비용에서 Claude Code는 $1.33를 기록한 반면, 최소 도구만을 제공한 Pi는 $0.67에 불과했다. 동일한 모델이 동일한 수준의 정답 코드를 도출했음에도 하네스의 차이만으로 비용이 정확히 2배로 폭증한 것이다.

이러한 현상은 특정 모델에 국한된 예외가 아니었다. 7개 공유 모델 전체의 데이터를 지오메트릭 평균(geometric mean)으로 집계했을 때, SWE-bench Lite에서 Claude Code는 Pi 대비 약 2.0배, Codex CLI 대비 약 1.6배의 비용을 소모했다. 터미널 조작 중심인 Terminal-Bench 2.0에서도 Claude Code는 Pi 대비 약 1.5배의 비용을 꾸준히 기록했다. 반면 하네스로 인해 발생한 작업 성공률의 변동 폭은 SWE-bench Lite에서 ±2% 이내, Terminal-Bench 2.0에서 ±5% 이내로 극히 좁았다. 결국 하네스가 만들어내는 가장 큰 차별점은 에이전트의 문제 해결 능력이 아니라 재정적 청구액의 크기였다.

4. 비용 격차의 해부 — 초기 컨텍스트 10배 차이와 프롬프트 비대화

그렇다면 동일한 모델을 사용하고 유사한 수준의 코드를 작성하는데 왜 2배에 달하는 비용 격차가 발생하는가. 연구진은 그 근본적인 메커니즘을 에이전트 세션이 시작될 때 주입되는 초기 컨텍스트(initial context)의 규모에서 찾아냈다. 평가 대상이 된 7개 모델 전체에서 Claude Code가 매 요청의 서두에 모델에게 전달하는 평균 초기 컨텍스트 길이는 Pi가 주입하는 길이의 10배를 상회했다.

이러한 초기 컨텍스트 팽창은 다음과 같은 구조적 요인들에 기인한다:

  • 방대한 시스템 프롬프트: 에이전트의 역할 규정, 코딩 컨벤션 권고사항, 예외 처리 규칙, 출력 포맷 지침이 수천 단어에 걸쳐 사전 주입됨
  • 상세한 툴 스키마 정의: 단순 bash 실행 외에 파일 뷰어, 디렉터리 리스터, 린트 통합기 등 다수의 전문화된 도구 파라미터 명세가 포함됨
  • 안전 및 제약 가이드라인: 보안 위험 명령 필터링, 시스템 변경 전 사용자 확인 절차 유도 등 엔터프라이즈 거버넌스 규칙 상시 상주
  • 작업 환경 메타데이터: 셸 환경변수, 로컬 깃 저장소 상태, 프로젝트 루트 감지 결과 등이 세션 초기 프롬프트에 자동으로 직렬화됨
  • 컨텍스트 누적 효과: LLM API의 특성상 세션이 다중 턴으로 진행될 때마다 비대한 초기 지시문이 매 턴 입력 토큰으로 재전송되며 비용을 지수적으로 누적

코딩 에이전트는 단 한 번의 프롬프트 호출로 끝나지 않고 평균 15회 이상의 대화 턴을 오가며 디버깅과 컴파일을 반복한다. 비록 현대 클라우드 LLM 제공사들이 프롬프트 캐싱(Prompt Caching) 기술을 통해 반복 토큰에 대해 50%에서 90%에 달하는 단가 할인을 적용하더라도, 기본 입력 베이스라인 자체가 10배 차이 나는 구조에서는 누적 토큰 비용의 절대치가 압도적으로 커질 수밖에 없다. 또한 캐시 미스(cache miss)가 발생하는 턴이나 컨텍스트 윈도우가 재정렬되는 구간에서는 이 10배의 지연과 토큰 소모가 고스란히 정가 청구액으로 전환된다.

5. 발견 2 — 최소 하네스 Pi의 파레토 프론티어 도달과 턴 수의 역설

복잡한 하네스를 옹호하는 진영의 핵심 논리는 구조화된 지침이 에이전트의 방황을 줄여 총 대화 턴(turn) 수를 단축시킬 것이라는 가설이었다. 상세한 툴 설명과 엄격한 코딩 규칙을 주입하면 모델이 헛발질을 적게 하여 더 적은 단계 만에 정답에 도달할 것이고, 턴 수가 줄어들면 턴당 비용이 다소 높더라도 전체 세션 비용은 상쇄될 수 있다는 논리다.

그러나 HarnessTax의 두 번째 발견은 이 가설을 정량적으로 반박한다. 도구 4개만 갖춘 극도로 단순한 하네스 Pi는 SWE-bench Lite와 Terminal-Bench 2.0 두 벤치마크 모두에서 비용 대비 성능의 파레토 프론티어(Pareto Frontier)에 확고하게 도달했다. 파레토 프론티어란 특정 지표를 희생하지 않고서는 다른 지표를 개선할 수 없는 최적의 경계선을 의미한다.

실제 Fable 5 모델의 실행 통계를 대조해 보면, 문제를 해결하기까지 소모된 평균 턴 수는 Pi가 15.4회, Claude Code가 15.3회로 거의 완벽하게 일치했다. 복잡한 시스템 가이드라인과 10배에 달하는 초기 지시문이 모델의 시행착오 횟수를 단 0.1턴도 줄여주지 못한 것이다. 턴 수가 동일한 상태에서 매 턴 입력되는 컨텍스트 크기만 비대해졌기 때문에, Claude Code는 Pi와 정확히 같은 회수의 상호작용을 거치면서도 정확히 2배의 청구 비용을 소모하는 비효율의 함정에 빠졌다.

이는 현대 프론티어 언어 모델의 본질적 역량이 과거와 달라졌음을 시사한다. 모델의 내장 추론 및 코드 이해 지능이 극도로 발전함에 따라, 에이전트는 장황한 행동 수칙을 주입받지 않아도 단 4개의 기본 도구(read, write, edit, bash)만으로 파일 구조를 스스로 탐색하고, 컴파일 오류를 스스로 해석하며, 최적의 수정을 찾아낼 수 있는 자율적 궤적을 그릴 수 있게 되었다.

6. 발견 3 — 자사 모델에 자사 하네스가 항상 최적은 아닌 이유

엔지니어링 현장에서 통용되던 또 다른 정설은 "Anthropic 모델에는 Claude Code를, OpenAI 모델에는 Codex CLI를 사용하는 것이 최상의 시너지를 낸다"는 결합 논리였다. 모델 가중치를 학습시킨 벤더가 자사 모델의 특성과 토크나이저, 지시어 순응도를 가장 잘 이해하고 있을 것이므로, 자사 하네스를 결합했을 때 최상의 성공률을 거둘 것이라는 직관적 기대였다.

연구진이 6개 상용 모델(Anthropic 4종 및 OpenAI 2종)과 2개 벤치마크를 결합한 총 12개의 비교 시나리오를 정밀 대조한 결과, 무려 9건(75%)에서 자사 하네스가 아닌 타사 하네스를 결합했을 때 최고 성공률이 달성되었다. 자사 하네스가 자사 모델의 잠재력을 항상 최대로 이끌어내지 못한다는 세 번째 핵심 발견이다.

구체적인 수치로 살펴보면 실증적 격차는 명확하다. Claude Sonnet 4.6 모델의 경우 SWE-bench Lite 환경에서 자사 하네스인 Claude Code와 결합했을 때 66.7%의 성공률을 기록한 반면, 경쟁사 래퍼인 Codex CLI와 결합했을 때는 68.9%의 성공률을 기록했다. 비용이 대등한 상태에서 타사 하네스가 2.2%포인트 더 높은 작업 완수율을 이끌어낸 것이다.

반대 방향의 조합에서도 동일한 양상이 관찰되었다. OpenAI의 최신 프론티어 모델인 GPT-5.6 Sol은 Terminal-Bench 2.0에서 자사 공식 도구인 Codex CLI와 결합했을 때 78.9%의 성공률과 과제당 $0.76의 비용을 나타냈다. 그러나 최소 하네스인 Pi와 결합하자 성공률은 83.3%로 4.4%포인트 상승했고, 과제당 소모 비용은 $0.42로 거의 절반 수준으로 급감했다. 전용 래퍼의 과도한 제약과 복잡한 프롬프트 구조가 오히려 모델의 유연한 문제 해결 경로를 경직되게 제약했을 가능성을 보여준다.

7. 풍부한 하네스가 주는 대가 — 구조화된 지원의 가치와 오버헤드

이러한 발견들이 복잡한 하네스의 무용론을 의미하는 것은 아니다. 연구진의 데이터는 하네스가 부과하는 '세금'의 크기를 투명하게 드러낸 것이지, 하네스가 제공하는 기능 자체를 무의미하다고 폄하하지 않는다. Claude Code와 같은 풀스펙 하네스가 매 턴 막대한 토큰을 소모하는 데에는 소프트웨어 엔지니어링 실무에서 요구되는 구조화된 안전장치와 개발 편의성이 녹아 있다.

표 2: HarnessTax 3대 핵심 발견과 엔지니어링 분석 요약
연구 발견 구분 실측 데이터 및 관측 지표 구조적 발생 원인 소프트웨어 아키텍처적 함의
발견 1: 비용 대칭 붕괴 Fable 5 기준 성공률 97.8% vs 96.7% (1.1%p 차이), 과제당 비용 $1.33 vs $0.67 (2배 차이). SWE-bench Lite 전체 지오메트릭 평균 Claude Code가 Pi 대비 2.0배 비용 하네스가 주입하는 초기 시스템 프롬프트 및 도구 스키마 길이의 10배 격차 단순 벤치마크 리더보드의 모델 순위만으로 시스템을 설계하면 2배의 추론 비용 낭비 발생
발견 2: 최소 하네스의 파레토 도달 Pi 하네스가 두 벤치마크 모두에서 파레토 최적 경계 달성. Fable 5 기준 평균 턴 수는 Pi 15.4회 vs Claude Code 15.3회로 사실상 동일 모델 고유의 추론 능력이 고도화되어 상세 지시문 없이도 4개 기본 도구로 최적 경로 수렴 풍부한 지침이 에이전트의 턴 수를 단축시키지 못하므로 불필요한 메타데이터 제거가 최선의 최적화
발견 3: 전용 하네스의 비최적성 상용 6개 모델 × 2개 벤치마크 = 12개 비교 중 9건(75%)에서 타사 하네스가 최고 성공률 달성. GPT-5.6 Sol의 Pi 결합 시 성공률 +4.4%p 및 비용 45% 절감 특정 벤더 전용 래퍼의 경직된 프롬프트 제약이 모델의 자율적 탐색 공간을 제한할 가능성 "자사 모델에는 자사 CLI"라는 결합 공식을 맹신하지 말고 파이프라인별 독립 벤치마크 필수

풍부한 하네스가 비용이라는 대가를 치르며 시스템에 제공하는 고유한 가치 요소들은 다음과 같다:

  • 파괴적 명령어 방어: 셸 레벨에서 광범위한 파일 삭제(rm -rf)나 데이터베이스 드롭 명령이 실행되기 전 사용자 인터랙션을 강제하는 안전망 제공
  • 통합 진단 및 린팅 피드백: 정적 코드 분석기와 테스트 러너를 단일 인터페이스로 묶어 개발자가 터미널을 이탈하지 않고 즉시 결과를 검증할 수 있는 개발자 경험(DX) 지원
  • 멀티파일 컨텍스트 동기화: 대규모 모노레포에서 에이전트가 탐색해야 할 의존성 그래프를 백그라운드에서 추적하여 누락 없는 코드 수정을 보장하는 인프라 구축
  • 엔터프라이즈 감사 로그: 기업 보안 표준을 준수하기 위해 에이전트가 수행한 모든 도구 호출과 파일 조작 이력을 구조화된 JSON 포맷으로 로깅하는 준법 계층
  • 초기 진입 장벽 완화: 도구 사용법이나 셸 스크립팅에 미숙한 개발자도 자연어 명령만으로 복잡한 CI/CD 및 배포 작업을 안전하게 조작할 수 있도록 돕는 추상화

결국 엔지니어링 팀이 내려야 할 선택은 "비용을 지불하고 이 모든 구조화된 가이드와 안전장치를 살 것인가, 아니면 최소 하네스를 채택하여 순수한 모델 지능에만 의존하고 절반의 비용으로 운영할 것인가"라는 명확한 트레이드오프로 귀결된다.

8. 하네스 선택의 실무 기준 — 대량 파이프라인과 고난도 단일 작업의 분기

HarnessTax 연구 결과가 현업의 기술 리더와 MLOps 엔지니어에게 던지는 실무적 교훈은 분명하다. 에이전트를 배치하는 워크로드의 성격에 따라 하네스 아키텍처를 이원화해야 한다는 점이다.

첫 번째 영역은 CI/CD 파이프라인, 자동화된 단위 테스트 복구, 회귀 버그 패치 생성 등 대량·반복적 배치 워크로드다. 이러한 환경에서는 매일 수백, 수천 개의 에이전트 세션이 무인 환경에서 트리거된다. 성공률이 97.8%와 96.7%로 사실상 동등한 상태에서 2배의 비용 차이는 월 수천만 원 단위의 인프라 예산 증감으로 직결된다. 이 영역에서는 Claude Code와 같은 중량급 래퍼를 걷어내고, Pi와 같은 최소 4도구 기반의 경량 하네스를 구축하여 불필요한 시스템 프롬프트와 툴 스키마를 철저히 제거하는 것이 절대적으로 유리하다.

두 번째 영역은 소수의 시니어 개발자가 복잡한 분산 아키텍처의 난제를 해결하거나 대규모 레거시 시스템을 리팩토링하는 대화형 고난도 단일 작업이다. 이러한 시나리오에서는 API 비용의 몇 달러 차이보다 개발자의 인지 부하 감소와 작업의 안전성이 훨씬 중요하다. 실수로 프로덕션 DB 마이그레이션 스크립트를 잘못 건드리거나 환경변수를 파괴하는 사고를 방지하기 위해, 풍부한 시스템 가이드라인과 명령 승인 절차를 갖춘 풀스펙 하네스가 충분히 그 값을 해낸다.

하네스 도입 및 개발 시 검토해야 할 실무 의사결정 지침은 다음과 같이 요약된다:

  • 초기 컨텍스트 감사: 사내에서 자체 구축한 에이전트 프레임워크가 매 턴 주입하는 시스템 프롬프트의 토큰 수를 주기적으로 프로파일링하여 불필요한 수식어 제거
  • 도구 스키마 최소화: 모델에게 10개 이상의 특화 도구를 나열해 주는 대신, 범용 bash 도구 하나로 모델이 필요 명령을 스스로 조합하도록 도구 정의 축소
  • 캐시 최적화 설계: 프롬프트 캐싱의 적중률을 극대화하기 위해 동적으로 변하는 메타데이터(타임스탬프, 임의 UUID)를 시스템 프롬프트 상단에서 제거하고 정적 텍스트 블록화
  • 하네스 교차 검증: 새로운 프론티어 모델을 도입할 때 벤더가 제공하는 기본 번들 툴체인에 안주하지 않고, 사내 골든셋 기반으로 최소 하네스와 병행 벤치마크 수행
  • 역할별 하네스 분리: 자동화 배치 봇에는 경량 API 하네스를, 개발자 대화형 터미널에는 안전 가드가 내장된 리치 CLI를 배포하는 이원화 정책 수립

9. 벤치마크 해석의 경계 — 저자들이 밝힌 두 벤치마크의 한계

이러한 정량적 수치를 해석함에 있어, 저자들이 결론 문단에서 강력하게 강조한 방법론적 유보 조건을 간과해서는 안 된다. HarnessTax의 연구진은 본 실험 결과가 지니는 일반화의 경계를 스스로 명확하게 짚었다.

가장 핵심적인 한계는 평가에 사용된 벤치마크가 SWE-bench Lite와 Terminal-Bench 2.0이라는 두 가지 공개 오픈소스 벤치마크에 국한되어 있다는 점이다. 이들 벤치마크에 포함된 리포지토리와 터미널 환경은 인터넷에 오랫동안 공개되어 온 유명 파이썬 프로젝트나 표준 리눅스 유틸리티들이다. 따라서 평가 대상이 된 프론티어 언어 모델들이 사전 학습(pre-training)이나 사후 미세조정 과정에서 해당 코드베이스의 관례와 이슈 해결 패턴을 이미 간접적으로 접했을 가능성을 배제할 수 없다.

공개 데이터셋에서 학습된 모델들은 환경에 대한 사전 지식이 풍부하기 때문에, 하네스가 제공하는 장황한 설명서가 없어도 최소 도구만으로 정답에 직행할 수 있다. 그러나 한 번도 공개된 적 없는 독자적인 엔터프라이즈 사내 프레임워크, 수백만 줄의 사내 독점 모노레포, 사내 규범이 지배하는 도메인 특화 환경에서는 상황이 완전히 달라질 수 있다. 사전 지식이 전혀 없는 미지의 코드베이스에서는 하네스가 사전에 제공하는 아키텍처 가이드라인과 린트 규칙이 모델의 탐색 실패를 방지하는 결정적인 역할을 수행할 여지가 여전히 존재한다.

따라서 엔지니어링 조직은 본 연구의 결과를 "모든 환경에서 최소 하네스가 우월하다"는 절대적 진리로 받아들여서는 안 되며, 자사 고유의 워크로드와 코드베이스 위에서 자체적인 비용-성공률 곡선을 측정하기 위한 엄밀한 기준선으로 삼아야 한다.

10. 확인하지 못한 것

본 기술 분석을 작성하며 1차 연구 자료와 공개 데이터셋을 검토하는 과정에서 명확한 수치나 원시 데이터가 공개되지 않아 본문에 단정적으로 적지 않은 항목은 아래와 같다.

  • 연구진이 논문 각주 및 향후 계획을 통해 공개할 예정이라고 밝힌 전체 21개 모델-하네스 조합의 턴별 토큰 breakdown 및 상세 프로파일링 트레이스(profiling traces) 원시 로그는 공식 저장소에 아직 배포되지 않아 세부 토큰 흐름을 확인하지 못했다.
  • 본 연구에서 평가된 7개 모델 외에, 2026년 하반기 공개된 Llama 4 계열이나 Qwen 계열 등 추가적인 오픈웨이트 모델군에 대한 동일 하네스 3종의 확장 실험 수치는 원문에 수록되지 않아 확인하지 못했다.
  • 실제 기업 프로덕션 환경에서 독자 개발한 내부 툴체인(사내 시맨틱 검색기, 내부 DB 스키마 뷰어 등)을 하네스에 플러그인 형태로 주입했을 때 발생하는 추가적인 토큰 세금의 정량적 가감폭은 공개 벤치마크 범위 밖이므로 확인하지 못했다.
