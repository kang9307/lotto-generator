Semantic Version Control With sem - Diffing Functions, Not Lines

Where line-based diff breaks down, how AST comparison works, sem vs difftastic and GumTree, and why it matters for AI-era code review

Jul 13, 2026 Dev & Infra

Intro: What Git Shows You Isn't Always the Question You're Asking

In July 2026, a CLI tool called sem, built by Ataraxy Labs, showed up on the developer community hada. The one-line pitch is simple: a semantic version control tool that adds function-and-class-level change tracking on top of Git. Instead of comparing lines, it compares code entities - functions, methods, classes - and reports what was added, modified, deleted, moved, or renamed.

That can sound like a minor UX polish at first glance. It isn't. This is a problem software engineering has wrestled with for over a decade. Git's default diff is still, at its core, a line comparison rooted in the Myers algorithm family from the 1970s, and the lineage of attempts to layer semantic understanding on top of it is long: the academic GumTree, GitHub's own semantic library (built, then shelved), the commercial SemanticDiff, and the now widely used difftastic. sem sits at the newest point on that lineage, trying to fold entity-level history management - not just displaying a diff - into the Git workflow itself.

This piece isn't a single-tool review. It walks through exactly where and why line-based diff breaks down, what AST (abstract syntax tree) comparison does at a principled level, where each prior attempt stalled, and why this problem matters again now that AI reads and writes code. It is grounded in publicly available material and academic research verifiable as of July 2026, but the interpretation and judgment throughout are my own.

1. The Structural Limits of Line-Based Diff - What Breaks, and Why

1.1 What diff Actually Compares

git diff's default algorithm is an edit-distance algorithm built on Myers' longest-common-subsequence approach. It treats two files as arrays of lines and computes how many lines must be deleted and added to go from one to the other. The upside is language-agnostic speed and four decades of battle-tested stability. The problem is the premise itself: the meaningful unit of code isn't a line but a structure - a function, a class, an expression - and diff knows nothing about that structure; it only compares text lines.

1.2 Why Refactors, Moves, and Renames Explode Into Noise

This mismatch surfaces the moment code is merely relocated. Move a function further down the file and, even though not a single character of logic changed, diff reports it as N lines deleted plus N lines added. Rename a single variable and every line that references it is flagged as changed. Even unifying indentation or switching line-break style paints a swath of substantively unrelated lines red and green. This is a repeatedly documented problem in the literature: line-based diff only computes additions and deletions, cannot represent other edit actions such as updates and moves, and operates at a coarse granularity - the text line - that is not aligned with source-code structure. That mismatch is the very starting point cited by AST-diff research.

1.3 The Real Cost to Code Review

The cost of that noise isn't abstract. To answer the question of what a PR actually changed, a reviewer has to manually filter genuine logic changes from simple relocation directly on the diff screen. Given that refactors often move code far from its original location, this filtering cost grows with the complexity of the change. The practical result is that reviewers skim large PRs more loosely, or teams impose a discipline that forces refactoring PRs to be split from logic-change PRs. Both responses are humans compensating for a limitation in the diff tool itself, not a real fix.

2. What Semantic Diff Is - The Principle Behind AST Comparison

2.1 Comparing Syntax Trees Instead of Text Lines

Semantic diff (structural diff) swaps the unit of comparison from text lines to the abstract syntax tree (AST). Source code is parsed into a tree where functions, classes, conditionals, and expressions are linked as parent-child nodes; two versions of that tree are then matched against each other to compute which nodes stayed put and which were added, deleted, modified, or moved. Because it looks at tree structure, it can recognize the same function even when the code sits on physically different lines, and changes that don't affect tree structure - like formatting - are filtered out of the comparison from the start.

2.2 GumTree - The Academic Prototype of Semantic Diff

The canonical academic prototype for this approach is GumTree, proposed by Falleri and colleagues in 2014. GumTree matches two ASTs in two phases. A top-down phase first locks in isomorphic subtrees - large, fully identical chunks - shared between the two trees. A bottom-up phase then stitches together the remaining unmatched nodes using surrounding-context similarity. Crucially, it was the first to formally introduce a move operation into edit scripts, letting a relocated code block be represented as a move rather than a delete-plus-add. Its drawback was that optimal tree-edit-distance computation is expensive, so the original GumTree slowed down on large ASTs. Follow-up research in 2024 addressed much of this with a heuristic, reportedly speeding up matching by 50x to as much as 281x while shrinking median edit-script size by half.

2.3 tree-sitter - The Infrastructure That Made Real-World Deployment Possible

If GumTree-style algorithms are the theory, tree-sitter is the infrastructure that let them actually ship in developer tools. tree-sitter is a parser generator built for incremental parsing: when a file changes slightly, it re-parses only the changed portion instead of rebuilding the whole tree. This incremental re-indexing is reported to run roughly 4x faster than full re-indexing, and it has been validated at a scale that handles something like the Linux kernel - 28 million lines across 75,000 files - within minutes. This is why most of the practical structural-diff tools that have emerged recently, difftastic and sem included, ride on tree-sitter's grammar ecosystem instead of building per-language parsers from scratch. Being able to extend language support without the cost of writing a new parser is the core reason this lineage of tools reached production far faster than the academic prototypes before it.

3. What sem Actually Does - Entity-Level Diffing and History Management

3.1 Three-Stage Matching - From Exact ID to Structural Hash to Fuzzy Similarity

sem (built by Ataraxy Labs in Rust, dual-licensed MIT/Apache-2.0) extracts entities such as functions, classes, and methods from source using tree-sitter, then matches entities between two versions in three stages. Exact ID matching first filters out entities that stayed unchanged; what remains goes through structural hash comparison to separate cosmetic changes like formatting from real logic changes. Finally, entities with token overlap above 80% are paired via fuzzy similarity, catching renamed or relocated entities. This three-stage structure can be read as GumTree's top-down/bottom-up two-phase matching with a practical structural-hash filter layered on top. In other words, sem doesn't propose new theory so much as refine a proven approach into a productized tool.

3.2 Command Surface - Beyond Diff to Full History

What makes sem interesting is that it doesn't stop at showing a single diff. sem diff shows entity-level changes with rename detection and word-level highlighting; sem impact analyzes cross-file dependencies to show what else breaks when a given entity changes. sem blame tracks, at the entity rather than the line level, who last made a substantive change to a given function, and sem log shows how a single function evolved across commit history. sem entities lists the functions and classes in a file or directory, and sem context is the LLM context-extraction feature covered later. Taken together, this is less a diff tool than a version-control layer that treats the entity as a first-class citizen.

3.3 How It Integrates With Git

sem doesn't create a separate repository; it works by wrapping git. The sem setup command installs it as git's default diff handler, so a team doesn't need to change tools at all - the output of familiar commands like git diff and git log -p simply becomes semantic. It's also practically important that file formats tree-sitter doesn't support fall back automatically to chunk-based text diffing. Supporting 32 languages doesn't mean everything else stops diffing - it means files sem can't parse quietly fall back to the old way.

4. Comparing sem to Prior Attempts - difftastic, GumTree, github/semantic, SemanticDiff

It's easy to overrate sem as a first attempt with no lineage. In reality, at least three prior branches of effort had to happen first, and each stalled at a different point.

4.1 difftastic - A Great-Looking Structural Diff, but Not History

difftastic, built in Rust by Wilfred Hughes, parses 50-plus languages via tree-sitter and shows only meaningful changes side by side, ignoring formatting differences. It's sem's closest neighbor but serves a different purpose. difftastic is a tool for showing one comparison better; it has no function-level history, impact analysis, or blame - nothing across a time axis. Where difftastic makes this diff more readable, sem also tracks how this function has changed over time.

4.2 GumTree - Accurate, but an Algorithm, Not a Tool

GumTree was never meant to be an end-user tool; it was a research library. The cost of optimal tree-edit-distance computation, combined with the absence of a production-grade CLI or git integration, kept it from mainstream adoption. It's accurate to say that later tools like sem and difftastic are, in effect, GumTree-family ideas - top-down/bottom-up matching, the move operation - wrapped in production-grade engineering.

4.3 The Lesson From github/semantic - Structural Diff Infrastructure Is Expensive to Maintain

The most instructive case is GitHub's own semantic. Written in Haskell and combining Myers' algorithm with RWS-family matching to offer structural diff and analysis across many languages, this library was archived on April 1, 2025. It's reasonable to read this as evidence that even a large platform couldn't sustain the cost of building and maintaining accurate structural parsers and matchers for every language, forever. sem's choice to ride the tree-sitter ecosystem instead of building its own parsers looks like a design that directly absorbed that lesson - delegating language support to a community-maintained grammar repository rather than owning it entirely.

4.4 Where sem Sits - The Next Step on the Lineage

Seen this way, sem's contribution isn't that it was first to attempt AST comparison. It's that it assembled four pieces into one CLI: ① tree-sitter as proven parsing infrastructure, ② the productization of GumTree-style three-stage matching, ③ an entity-centered workflow that bundles impact, blame, and log alongside diff, and ④ low adoption friction from the git-wrapper approach. None of the individual pieces is new, but my read is that the combination and execution here are relatively more polished than elsewhere in this lineage.

5. What AST-Based Comparison Actually Delivers - Review Clarity, Refactor Tracking, Meaningful History

5.1 Review Clarity

The most direct effect for a reviewer is that relocation and logic change are separated on the diff screen. Items flagged as rename or move can be skimmed past, letting review time concentrate on items flagged as genuine modification. This isn't mere convenience - it's a structural shift that moves the earlier-described cost of manually filtering noise from the reviewer to the tool.

5.2 Refactor Tracking

The fact that sem log and sem blame operate at the entity level means how this function changed across the entire commit history can be reconstructed in a way that was effectively impossible with file-level blame. File-level blame loses history the moment a function moves between files or is extracted from or merged into another file. Tracking by entity ID lets you cross that break.

5.3 Meaningful Change History

The net effect is turning a commit log from a record of how many lines changed into a record of why and how this function or class evolved. That ripples into adjacent work beyond code review - onboarding (letting new hires follow the evolution of core logic) and postmortems (tracing which entity change, at what point, introduced a bug).

6. Why Semantic Change Tracking Matters More in the Age of AI Code Review and Agents

6.1 LLM Context Budgets and Diff Noise

As of 2026, a large share of code review is already first-passed by LLM-based agents. The underlying problem is fundamentally the same one humans face, but the cost differs. A human spends time filtering noisy diffs by eye; an LLM consumes that noise directly as tokens. Feeding a diff inflated by relocation straight into a prompt burns context budget unnecessarily and dilutes the attention the model could otherwise devote to changes that actually matter. If what genuinely changed can be compressed down to the entity level, the same context budget carries more real signal.

6.2 sem context and MCP Integration

sem shipping a sem context command for token-budgeted LLM context extraction, along with MCP (Model Context Protocol) integration, targets this problem directly. When an AI coding agent is asked what changed in this PR, receiving an entity-level, refined change list instead of a raw git diff leaves more room to produce an accurate answer within the same token count. This isn't unique to sem - it overlaps with where AI code-review tools have been converging as of 2026. Recent review tools have moved beyond looking only at a PR's diff, building a semantic graph of the whole repository to supply architectural context alongside it. sem's entity graph can be read as an upstream stage that refines the raw material for that graph starting at diff time.

6.3 To an Autonomous Agent, Move and Modify Are Different Signals

If separating relocation from logic change is a convenience for a human reviewer, for an autonomous coding agent that distinction ties directly into action decisions. If a function was simply moved, the agent doesn't need to redesign its tests; if the logic changed, related tests, docs, and dependent code all need updating together. Making an agent infer that judgment from raw diff text versus having the tool tag move and modify from the start makes a meaningful difference in agent-pipeline reliability.

7. Practical Adoption Considerations - Language Support, Performance, Git Integration

7.1 The Reality of Language Support - 32 Languages and What Falls Outside

sem supports 32 languages including TypeScript, Python, Go, Rust, Java, C/C++, JavaScript, Ruby, PHP, Swift, and Kotlin, plus structured formats like JSON, YAML, TOML, CSV, and Markdown. That covers most mainstream backend and frontend stacks, but internal DSLs, niche languages, or languages whose tree-sitter grammar is still immature quietly drop to chunk-based text fallback - worth knowing upfront. The fallback itself is safe (the tool doesn't break), but it's worth remembering that the benefits described in this piece - entity matching, move detection, impact analysis - disappear in that fallback state, and you're back to an ordinary diff.

7.2 Performance - The Trade-off Between Incremental Parsing and Cloud Acceleration

tree-sitter's incremental parsing makes re-parsing individual files fast, but queries that sweep a repository-wide dependency graph, like impact, are a different animal. According to examples published in sem's own docs, an impact query on a large repository (deno-scale) is reported at roughly 573ms when recomputed locally versus roughly 86ms with a cloud cache. That suggests recomputing a large graph query from scratch every time can be burdensome in practice, and that caching and indexing strategy determines real-world performance. Documentation also notes that after sem setup, a resident graph is kept locally to speed up repeated queries. It's safer to measure real latency for impact and log queries, not just diff, at your own repository's scale before adopting.

7.3 Git Integration and Team Adoption Friction

sem's choice to replace git's default diff handler rather than demand a separate repository or workflow is a sensible design for reducing adoption friction. A team doesn't need to learn a new tool at all - existing git diff and git log habits automatically start producing semantic output. That said, if you have CI pipelines, review bots, or internal scripts that parse existing diff output, you'll need separate verification at the point where the output format changes.

8. Limitations and Open Problems

8.1 Limitations Academia Still Flags in AST Diff

Getting swept up in the tools this piece has introduced and painting AST diff as a silver bullet wouldn't be honest. A 2024 study on refactoring-aware AST differencing summarizes five limitations current tools still commonly share: ① lack of multi-mapping support, where one node should correspond to several; ② matching between AST nodes that are semantically incompatible; ③ underuse of language-specific grammar cues during matching; ④ weak ability to recognize refactoring patterns themselves; and ⑤ comparisons that often remain file-scoped rather than commit-scoped. sem's three-stage matching and its impact/log features mitigate some of these - especially history and refactor tracking - but there's no basis to claim it resolves all five.

8.2 The Stability of a New Tool - The Temperature of hada's Reaction

One reaction when sem was introduced on hada was a mix of surprise that this was even possible and a fair question about whether it's stable enough for production. That's a reasonable line to hold. At points where heuristics take over - like the 80% token-overlap threshold for fuzzy similarity in three-stage matching - both false positives (misjudging an unrelated function as a rename) and false negatives (missing a genuine move) can occur, and how noticeable that is will vary by language and coding style. Before rolling this out across a large team, it's safer to reproduce a handful of real refactoring commits from your own codebase through sem diff and check the results directly.

8.3 Fallback for Structured Files and Unsupported Code

Even though sem supports structured formats like JSON, YAML, and TOML, regex-based config files, internal custom formats, and newer languages without a mature tree-sitter grammar quietly fall back to chunk-based text diffing. If your repository is a mix of many languages and formats, it's worth checking upfront that the share of files that actually diff semantically may be lower than expected.

9. Conclusion - Three Things Worth Checking Today

Semantic version control isn't a new idea. GumTree laid the academic groundwork over a decade ago, and GitHub itself tried and shelved its own attempt. What makes sem interesting isn't a new theory - it's that it bundled diff, impact, blame, and log into a single git-native workflow on top of mature tree-sitter infrastructure, and in doing so, squarely targeted a distinctly 2026 problem: how much context an AI agent has to spend. That said, the fundamental limitations academia still flags in AST diff - multi-mapping, semantically mismatched matching, weak refactoring-pattern recognition - are not fully resolved in sem either, and the stability verification that any new tool requires is still ongoing.

9.1 Reproduce It on Your Own Codebase First

Pick five to ten recent refactoring commits and re-view them through sem diff. Confirm that noise actually drops and that moves and renames are caught correctly. How this feels will vary by language and coding style.

9.2 Check Your CI and Review-Bot Touchpoints First

Before swapping the default diff handler with sem setup, check whether any CI scripts or review bots parse existing diff output, and verify in a separate environment first.

9.3 If You Run an AI Agent Pipeline, Measure Context Consumption First

If you're already running LLM agents on code review or refactoring, feed the same PR through a raw diff and through sem context output separately, and compare token consumption and answer quality. That gap is the most concrete basis for deciding whether to adopt.
