コマンドラインでモニター入力を切り替える - DDC/CIとmonitor-input-rs徹底解説

ハードウェアKVMなしで1台のモニターを複数PCで使い回す方法 - DDC/CIプロトコルの仕組みと実践活用

2026年7月22日 開発・インフラ

序論: KVMなしで1台のモニターを複数PCが共有するということ

仕事用PCとゲーム用PCを同じ机に置き、モニターは1台だけという環境を思い浮かべてほしい。2台のPCを行き来するたびにモニターへ手を伸ばし、入力切替ボタンを何度も押してOSD(オンスクリーンメニュー)を辿ってHDMI1からDisplayPortへ切り替えた経験があれば、この面倒さがすぐに理解できるはずだ。ハードウェアKVMスイッチを買えば解決するが、映像信号が経由する機器が一つ増える分、解像度・リフレッシュレートの制限やHDCPの問題が新たに発生することも珍しくない。

GeekNews(hada.io)で紹介されたmonitor-input-rsは、この問題をまったく別のレイヤーで解決する。ハードウェアを追加購入する代わりに、すでにモニターの中に眠っている制御機能をコマンドラインから直接叩く方式だ。本稿では、その土台となるDDC/CIプロトコルが実際に何をしているのか、このツールがなぜ今の形で作られたのか、そしてどこまで期待でき、どこから注意すべきかを整理する。2026年7月時点で確認したリポジトリと関連資料を根拠にしている。

1. DDC/CIとは何か - モニターをソフトウェアで制御する規格

DDC/CI(Display Data Channel/Command Interface)はVESAが制定した規格で、ホストPCとモニターが映像ケーブルの中を一緒に通る補助チャネルを介して対話できるようにする。要点はシンプルだ。モニターの輝度・コントラスト・入力ソースといった設定を、物理ボタンを押さずにソフトウェアコマンドで変更できるという点にある。

1.1 I2Cの上に乗る制御チャネル

DDC/CIはHDMI・DVI・DisplayPortケーブルの中を一緒に通るI2Cバスを物理層として使う。コンピューターがマスター、モニターがスレーブの役割を担い、決められたアドレスで短いコマンド列をやり取りする。画面に描画される映像信号とは完全に別のチャネルなので、DDC/CIコマンドを送っても画面がちらついたり途切れたりすることはない。

1.2 VCPコードとMCCS規格

このチャネル上で実際に何をどう要求するかを定義するのがMCCS(Monitor Control Command Set)だ。MCCSは設定項目ごとにVCP(Virtual Control Panel)機能コードを割り当てる。たとえば輝度はコード0x10、入力ソース選択はコード0x60で扱われる。Linuxのddcutilのようなツールでsetvcp 60 0x0fのように値を指定して入力を切り替えるのも、結局はこの規格の上で行われていることだ。monitor-input-rsは、この低レベルのコードをユーザーが覚える必要がないよう、モニター名や入力名といった人間が読みやすい文字列で包んだツールだと理解すればよい。

2. monitor-input-rsが解決する実際の不便

monitor-input-rsは開発者kojiishi氏が公開したオープンソースプロジェクトで、DDC/CIを使ってモニターの入力ソースをコマンドラインから切り替えることだけを目的としている。派手なGUIもトレイアイコンもない。そのシンプルさこそが、スクリプトやショートカットに組み込みやすい理由でもある。

2.1 物理ボタンの代わりにコマンド一行

モニターのOSDを通じて入力を切り替える手順は、機種ごとにボタン配置もメニューの階層も異なる。一方monitor-input-rsはモニター名=入力値という統一された文法を提供する。一度スクリプトやショートカットに登録しておけば、以降はそのキー操作だけで切り替えが完了する。GeekNewsのコメント欄でも、実際のユーザーがシェルエイリアスでmonのような短いコマンドを作り、WindowsとMacの間を行き来しているという体験が共有されていたが、これがまさにこのツールが狙う使い方だ。

2.2 なぜクロスプラットフォーム・Rustなのか

DDC/CI自体はプラットフォームごとにアクセス方法が異なる。WindowsはOS独自のモニター設定API、macOSはIOKit系のインターフェース、LinuxはI2C-devカーネルモジュールを経由する。monitor-input-rsはこの違いをddc-hiというクレートで吸収し、同じCLI文法が3つのプラットフォームすべてで同じように動くようにしている。Rustで書かれている点にも実用的な理由がある。別途ランタイムを導入する必要がない単一実行ファイルとして配布され、起動遅延がほぼゼロなので、ショートカットや自動化スクリプトに組み込んでも体感の遅延がない。コマンドライン優先の設計であるため、シェル関数・cronジョブ・ホットキーマネージャーなど、どんな自動化ツールにもそのまま組み込めるという点が、GUI専用ツールと最も大きく異なる点だ。

3. 実際の使い方 - 導入とコマンドの考え方

公式リポジトリを基に導入と基本的な使い方を整理すると次のようになる。正確な最新オプションはリポジトリのドキュメントで確認するのが確実だ。

3.1 導入

Rustツールチェーンが導入済みなら、cargo install monitor-inputの一行でcrates.io登録版が導入される。リポジトリから直接ビルドするにはcargo install --git https://github.com/kojiishi/monitor-input-rsを使う。Linuxではlibudevの開発パッケージが事前に必要だ。Windowsでコンソールウィンドウを出さずバックグラウンド実行ファイルとして使いたい場合は、-F winappの機能フラグを付けて導入するとmonitor-inputw.exeが生成され、エラーはコンソールの代わりにWindows通知として表示される。

# crates.ioから導入
cargo install monitor-input

# リポジトリから直接導入
cargo install --git https://github.com/kojiishi/monitor-input-rs

# Windows向けコンソールレス版
cargo install monitor-input -F winapp

3.2 基本コマンド

使い方はモニターを一覧表示し、名前で絞り込み、入力値を指定するという3ステップに集約される。値を複数並べると、実行するたびに次の値へ進むトグル・循環動作も利用できる。

# 接続中のモニターを全て一覧表示
monitor-input

# モニター名に特定の文字列を含むものだけ検索
monitor-input Dell

# 特定モニターの入力をDisplayPort 1に指定
monitor-input U2723=dp1

# hdmi1とusbc2を実行のたびにトグル
monitor-input P3223=hdmi1,usbc2

# hdmi1 → usbc2 → dp1 の順で循環
monitor-input P3223=hdmi1,usbc2,dp1

この文法のポイントは、値をカンマで並べると自動的に循環する点だ。つまりショートカット一つにmonitor-input P3223=hdmi1,usbc2を割り当てておけば、押すたびに2つの入力を行き来するトグルボタンが出来上がる。VCPコードやベンダーごとの値表を自分で調べる必要がないという点が、ddcutilのような低レベルツールに対する最大の使い勝手の差だ。

4. 活用シナリオ - どこに組み込むか

4.1 仕事用PC ↔ ゲーム用PC

最も直感的な使い道だ。業務用ノートPCとゲーム用デスクトップを1台のモニターに繋ぎ、ショートカット一つで行き来する。物理ボタンを押す数秒の摩擦がなくなると、実際に切替の頻度自体が増える経験をするユーザーは多い。手間が減ると行動パターンが変わるというよくあるUXの原則が、ここでもそのまま現れる。

4.2 ホームラボ・複数サーバーのコンソール

複数台のサーバーやミニPCクラスターを1台のモニターで管理するホームラボ環境でも役立つ。専用のコンソールKVMを別途置かず、各マシンをモニターの異なる入力に接続してスクリプトで循環させれば、低コストで似た利便性が得られる。もちろんこの場合、キーボード・マウスの切替は別途解決する必要がある点は後述する。

4.3 会議室・開発環境の分離

会議室のモニターをノートPCと発表用PCの間で行き来させる状況、あるいは開発環境を物理的に分離した別マシンと普段の業務マシンを行き来する構成にも同じパターンが当てはまる。スクリプトにまとめておけば、会議開始マクロに入力切替コマンドを含めることも可能だ。

5. 類似ツールとの比較 - 「ソフトウェアKVM」と混同しないこと

この分野を調べると名前の似たツールが多く、混同しやすい。整理しておこう。

5.1 Linux: ddcutil

ddcutilははるかに古く成熟したLinux向けDDC/CIツールだ。ddcutil detectでモニターを検出し、ddcutil setvcp 60 0x0fのようにVCPコードと16進値を直接指定する。機能は強力だがコード表を自分で調べる必要がある低レベルインターフェースだ。monitor-input-rsは同じ原理を使いつつ名前ベースの人に優しい文法を乗せており、何よりLinux専用ではなく3プラットフォームで同じように使える点が異なる。

5.2 Windows: ControlMyMonitor・ddcswitch系

Windows陣営にはNirSoftのControlMyMonitorをバッチスクリプトで包んで使う方法や、DDC/CI専用に作られたddcswitchのようなWindows専用CLIがある。機能的にはmonitor-input-rsと重なるが、Windowsに限定されるという制約がある。MacとWindowsを併用する人には、プラットフォームごとに別のツールを覚える負担が生じる。

5.3 macOS: Lunarと自動トリガーツール

macOSにはLunarのように輝度と入力をGUIで制御するDDC/CIツールがあり、これに機器の接続を検知して自動的に切替コマンドを発行する補助ツールを組み合わせる事例も報告されている。この組み合わせは、ショートカットを押さなくてもケーブルを挿した瞬間に自動で切り替わるという利点があるが、monitor-input-rs自体には自動検知機能はなく、純粋にコマンドが来たら実行するツールだ。自動トリガーが必要であれば、別途スクリプトやフックで包む必要がある。

5.4 「ソフトウェアKVM」は実は別の問題を解決する

Synergy、Input Director、Barrierのようないわゆるソフトウェアkvmは検索結果によく一緒に出てくるが、実際には別のレイヤーの問題を解決している。これらは複数のコンピューターがそれぞれ自分のモニターを持っている状況で、マウスカーソルを画面の境界を越えて移動させ、キーボード・マウス入力だけを引き渡すツールだ。モニター自体は1台なのに複数PCの映像ケーブルが繋がっていて、そのうち1つだけを画面に表示しなければならない状況では、キーボード・マウスを共有しても画面に表示される内容は変わらない。その画面自体を切り替えるのがDDC/CIとmonitor-input-rsの領域だ。両者の種類のツールはしばしば一緒に使われる。ソフトウェアkvmでキーボード・マウスを引き渡し、monitor-input-rsで映像入力を同じタイミングで切り替えるという具合だ。

6. 限界と注意点

6.1 モニターがDDC/CIをきちんとサポートしている必要がある

DDC/CIは規格だが、実装品質はメーカーと機種によってばらつきが大きい。一部の廉価モニターはDDC/CIをまったくサポートせず、サポートしていても特定のポートでしか動作しないケースがある。たとえば一部の超ワイド・ゲーミングモニターでは、DisplayPortではDDC制御が塞がれておりHDMIでのみ動作するという事例が報告されている。ツールを導入する前に、手持ちのモニターがどのポートでDDC/CIをサポートしているか確認するのが順序だ。

6.2 USB-Cドッキングステーション・マルチストリームハブの落とし穴

USB-Cドッキングステーションやマルチストリーム対応ハブを経由すると、映像信号は正常に出るのにDDC制御チャネルだけが欠落するケースがよくある。ドッキングステーションのファームウェアがDDCパススルーを正しく実装していないことが原因である場合が多く、この場合はモニターをPCに直接ケーブルで繋いで原因を切り分けるのが最も早い診断法だ。ノートPC1台にドッキングステーションまで繋いだ構成では、この点で詰まる事例が実際によく報告されている。

6.3 スリープモード・信号検知・Linuxディストリビューションのばらつき

入力を切り替えた後に該当PCがスリープモードに入ると、モニターが信号を探し続けて意図しない入力に固定されたり、無信号画面を表示したりすることがある。完全な自動化を狙うなら、スリープ状態への移行タイミングまで考慮する必要がある。またGeekNewsのコメント欄では、Ubuntu 24.04で機器が認識されないという互換性の問題も報告されていた。Linuxディストリビューションやカーネルバージョンによってi2c-devモジュールの有効化状況や権限設定が異なり、初回実行ですぐには動かない可能性がある点を踏まえておく必要がある。

結論 - 誰に向いているか

monitor-input-rsは派手な新技術ではなく、すでにほとんどのモニターの中に眠っていたDDC/CIという古い規格を、コマンドライン時代の習慣に合わせて再び引っ張り出したツールに近い。ハードウェアKVMを買う必要がなく、すでに持っているモニターとケーブルだけで問題を解決できる点が、このツールの本当の価値だ。

1台のモニターを仕事用とゲーム用、あるいは複数のホームラボマシンの間で物理ボタンなしに行き来したい人、そしてすでにシェルスクリプトやショートカットマネージャーでワークフローを自動化する習慣がある人に特に向いている。逆にモニターのDDC/CI対応状況が不確実だったり、ドッキングステーションを何層も経由する複雑な配線を使っている場合は、まず引数なしでmonitor-inputを実行し、モニターが認識されるかどうかを確認するのが順序だ。キーボード・マウスも一緒に引き渡したいなら、ソフトウェアkvmと組み合わせる構成を推奨する。
