OAuth 被误解的地方 - 它是委托授权而不是身份认证

四个角色、四种流程，以及最新的 BCP 从清单上拿掉的东西

2026年8月24日 开发/基础设施

会议上只要有人说出「我们用 OAuth 接了登录」，接下来半小时的对话基本就定型了。有人正在拆开访问令牌取出用户标识来用，有人把那枚令牌放进了浏览器存储，还有人只在界面上隐藏作用域，就把它称作权限控制。三种都很常见，而且三种都出自同一个根。

根在规范的名字里。OAuth 2.0 的正式名称是 The OAuth 2.0 Authorization Framework，其中没有 authentication 这个词。这不是偶然。这份规范当初要解决的问题，从来就不是「这个人是谁」，而是「这个应用能伸手到那份资源的哪一步」。漏掉这一行，堆在它上面的判断就会按顺序一起走偏。

下面按照规范本身的顺序，逐个指出这种偏差实际显形的位置。每一节只讲「规范怎么写的」和「违背这条规范时会崩掉什么」，到此为止。攻击如何实施不在讨论范围内。

1. 最大的误解 - OAuth 不是身份认证协议

RFC 6749 是 2012 年 10 月发布的 Proposed Standard。摘要把这个框架做的事定义为让「第三方应用获得对某个 HTTP 服务的有限访问权限」。无论是代表资源所有者，还是应用为自己，产出的始终是访问权限，而不是身份的证明。

这样一来访问令牌的性质也就自然定下了。访问令牌是为了向资源服务器出示而造的东西，不是给客户端读的。里面装着什么都好，那是关于「这次请求可以响应到哪一步」的信息，不是关于「此刻屏幕前的人是谁」的信息。RFC 6749 的安全考量一节里另有一条警告，提醒不要把访问令牌当成资源所有者的身份凭证来用。

如果目标是登录，就得再加一层。OpenID Connect Core 1.0 把自己定义为「架设在 OAuth 2.0 协议之上的一个简单身份层」。这一层带进来的新东西是 ID 令牌。ID 令牌是一枚承载最终用户认证相关声明的安全令牌，采用 JWT 形式，以下声明为必需项。

  • iss - 签发该响应的签发者标识
  • sub - 主体标识，在签发者范围内唯一且永不重新分配
  • aud - 这枚 ID 令牌面向的受众，包含 OAuth 客户端标识
  • exp - 过期时间，到达该时刻之后不得再接受这枚 ID 令牌
  • iat - 该 JWT 的签发时间

本节的核心是两枚令牌的接收方不同。访问令牌由资源服务器接收，ID 令牌由客户端接收。需要用户资料时，OpenID Connect 设有 UserInfo 端点，它是一个受保护资源，出示访问令牌即返回已获授权的最终用户信息。连读取资料这件事，都是用授权的语法完成的。

判断标准。如果自己的服务需要的是「往对方服务里我的日历上添加一个日程的权限」，OAuth 就把事情做完了。如果需要的是「确定这个人对应本服务的哪个账号」，那就需要 OpenID Connect。两种需求混在一起时，两层都用。想让一枚访问令牌把两件事一起干的那一刻，就是事故的起点。

2. 角色有四个，信任的方向不是单向的

RFC 6749 把参与方分成四个。在这里把术语抓准，后面几节会轻松很多。

  • 资源所有者 - 能够授予对受保护资源之访问权限的实体
  • 客户端 - 代表资源所有者、并经其授权而发起受保护资源请求的应用
  • 授权服务器 - 在成功认证资源所有者并取得授权之后，向客户端签发访问令牌的服务器
  • 资源服务器 - 托管受保护资源，能够接受并响应使用访问令牌的受保护资源请求的服务器

这里最容易被糊过去的是信任的方向。资源所有者信任的对象只有一个，就是授权服务器，输入密码或第二因素的地方也只应该在那里。客户端并不信任资源所有者，它信任的是授权服务器交回来的东西。资源服务器同样不信任客户端，它信任的是授权服务器签发的令牌是否有效。四方之间并不是对称信任的结构，这一点就是这份规范的骨架。

另一条分叉的轴是客户端类型。能够把自身凭据保持机密的叫机密客户端，做不到的叫公开客户端。跑在服务器上的后端属于前者，跑在浏览器里的单页应用或装在用户设备上的原生应用属于后者。后面的大部分规范都在这条轴上分叉。能不能用客户端凭据许可、PKCE 是必须还是建议、刷新令牌是否被要求轮换，全都挂在这里。

原生应用还要多加一条规范。RFC 8252 是 2017 年 10 月发布的 Best Current Practice，编号为 BCP 212。核心主张是，来自原生应用的授权请求应当只经由外部用户代理，主要是用户自己的浏览器发起，而不是嵌入式用户代理。用上一段的信任方向再读一遍就很清楚：嵌入式 WebView 是客户端自己拥有的界面，资源所有者只把凭据交给授权服务器这个前提，在那个界面上并不成立。

3. 各流程之间到底有什么不同

与其背流程，不如抓住区分流程的那两个问题。第一，资源所有者此刻在不在场。第二，客户端能不能保住秘密。这两个答案决定了流程。

流程 规范与状态 资源所有者是否在场 客户端类型 使用场合
授权码流程 RFC 6749 (Proposed Standard, 2012-10) 在场，在浏览器里同意 机密与公开都可 几乎所有有人参与的场合
PKCE (授权码流程的扩展) RFC 7636 (Proposed Standard, 2015-09) 在场 公开必须，机密建议 为授权码流程补上对拦截与注入的防御时
设备授权许可 RFC 8628 (Proposed Standard, 2019-08) 在场，但在另一台设备上批准 以公开为主 智能电视、主机、打印机等输入受限的设备
客户端凭据许可 RFC 6749 (Proposed Standard, 2012-10) 不在场，没有人参与 仅限机密客户端 服务以自己名义发起的服务器间调用

3.1 授权码流程为什么分成两步

第一次看授权码流程，卡住人的往往是它为什么要分成两段。先通过浏览器重定向拿到授权码，再把这个码送回授权服务器换成访问令牌。看上去一次就能办完的事，偏要来回两趟。

原因在于这两趟走的是不同的信道。前一趟经过用户的浏览器：重定向 URL 会出现在地址栏，落进浏览器历史，穿过好几层。后一趟是客户端与授权服务器之间的直接往来。把访问令牌只放在后一条路径上往返，令牌本身就不会成为前一条路径上的痕迹。这个分离就是授权码流程能留到今天的理由。

3.2 设备流程与客户端凭据流程

设备授权许可是为打不开浏览器的设备准备的。设备把一个码展示给用户，用户在智能手机这类另一台设备上完成批准。在这期间，设备不要求客户端与用户代理之间的双向通信，而是反复轮询授权服务器。与其让人拿着遥控器敲密码，不如把授权这个行为整个搬到另一台设备上，这就是它的设计。

客户端凭据许可则是完全不同的东西。这里没有资源所有者。它用于客户端访问自己掌控之下的资源，或者事先与授权服务器约定好的资源。所以规范把话钉死：该许可类型只能由机密客户端使用。常见的误用是拿这个流程去取用户数据。这样一来，「是谁许可的」所对应的当事人就从结构里消失了，审计记录里只剩下一个服务账号。

4. 从清单上撤下的两种流程 - 隐式与密码许可

2025 年 1 月 RFC 9700 发布。名称是 Best Current Practice for OAuth 2.0 Security，状态是 Best Current Practice，BCP 240。这份文档更新了 RFC 6749、RFC 6750 以及旧的威胁模型文档 RFC 6819。换句话说，今天设计 OAuth，基准线是这份文档而不是 6749。

它做的事情里最显眼的一件，就是把两种流程从清单上撤了下来。

4.1 隐式许可

RFC 9700 写明客户端不应当使用(SHOULD NOT)隐式许可，其他在授权响应中签发访问令牌的响应类型也被归进同一类，只在授权响应中的访问令牌注入被阻止的情况下留了例外。依据有两条。

  • 对访问令牌的泄露与重放存在脆弱性
  • 这种方式没有标准化的手段施加发送方绑定

同一份文档用一句话给出替代方案：改用 code 响应类型。对照上一节的信道分离，理由是重合的。隐式流程把令牌放上了前信道，于是 3.1 里辛苦分开的东西又合到了一起。

4.2 资源所有者密码凭据许可

这一边的措辞更硬。RFC 9700 写明该许可不得使用(MUST NOT)，理由有四条。

  • 它把资源所有者的凭据以不安全的方式暴露给客户端
  • 它扩大了攻击面
  • 它训练用户在授权服务器之外输入自己的凭据
  • 它并非为配合双因素认证而设计

第三条尤其贴近实务。训练用户这个说法指的不是技术漏洞，而是关于习惯的指摘。一个已经学会「在应用界面里输密码很正常」的用户，也就失去了分辨那是谁家界面的依据。第四条更直接：一个整体接收凭据对的结构，根本没有留下让第二因素插进来的位置。这一点与按方式梳理双因素认证的那篇文章连起来读会更清楚。

顺带一提，名为 OAuth 2.1 的工作正在进行中。2026 年 3 月 2 日的第 15 版已经发布，状态是互联网草案(Internet-Draft)，它在整合 RFC 6749 与 RFC 6750 的同时不再规定隐式许可与密码许可。不过草案不是标准。今天若需要规范性依据，该引的是 RFC 9700。

5. PKCE 防的是什么 - 已经不只是公开客户端的事

RFC 7636 的标题是 Proof Key for Code Exchange by OAuth Public Clients。它是 2015 年 9 月发布的 Proposed Standard，摘要瞄准的问题只有一个：使用授权码许可的公开客户端容易遭受授权码拦截攻击。

缓解方式就如其名。客户端为每次请求动态生成一把密码学密钥，用它把授权请求与令牌请求关联起来。授权请求里带上由该密钥派生的值，令牌请求里送出原始值，由授权服务器比对两者。结果是只拿到码的一方无法把它换成令牌。

以上是旧的理解。变了的是适用范围。RFC 9700 是这样梳理的。

  • 公开客户端必须使用 PKCE(MUST)。
  • 也建议机密客户端使用 PKCE(RECOMMENDED)，因为它对授权码的滥用与注入提供了强有力的保护。
  • 即便攻击者试图注入窃得的授权码，原始值比对不上，在令牌端点上这次交换也无法完成。
  • 同一份文档还写明，即使面对强攻击者，PKCE 也提供对 CSRF 的保护。

把这个变化压成一句话：PKCE 从「给保不住秘密的客户端打的补丁」，挪到了「针对代码注入这一威胁本身的防御」。觉得后端把客户端密钥保管得很好所以不需要 PKCE，这种判断是在用上一代的标准框定防御对象。

本节还要一并看的规范是重定向 URI 的比对。RFC 9700 要求授权服务器必须使用精确字符串匹配(MUST)。唯一的例外是原生应用 localhost 重定向 URI 中的端口号，而模式匹配因复杂度与安全问题被明确否决。比对一旦放宽，授权响应可返回的目的地集合就会比客户端本意更宽。

接了多个授权服务器的客户端还多一条规范。RFC 9207 是 2022 年发布的 Proposed Standard，定义了在授权响应中显式携带授权服务器签发者标识的 iss 参数，目的是应对混合攻击(mix-up attack)。RFC 9700 要求客户端保存每次请求发往的签发者，与响应中收到的标识比对，不一致时必须中止这次交互。

6. 令牌放在哪里 - 浏览器存储与 Cookie 的代价

这个问题没有唯一正解，规范也是这么说的。2026 年 8 月发布的 RFC 10017 标题为 OAuth 2.0 for Browser-Based Applications，是一份 Best Current Practice，共用 BCP 212 这个编号。文档摆出了浏览器应用可以采取的三种架构。

  • 后端代理前端(BFF) - 令牌留在服务端，与浏览器之间用会话 Cookie 对话
  • 令牌中介后端 - 后端以机密客户端的身份运作，但把访问令牌下发给浏览器
  • 浏览器端 OAuth 2.0 客户端 - 浏览器里的代码本身就是客户端

文档在把三者并列时附上的那句话，就是判断的尺子：每一种架构模式都在安全性与简洁性之间给出不同的取舍。它为敏感应用推荐 BFF，同时承认其余两种也有正当用途。

读这份取舍时还有一句话是主轴：恶意 JavaScript 代码拥有与合法应用代码相同的权限。在脚本执行已被攻破的情形下，不存在「脚本读不到的浏览器内存储」。访问难度确有差别，文档写明像本地存储这类随处可访问的存储区域，比更为隔离的区域更容易被恶意 JavaScript 触及。

存放位置 脚本执行被攻破时 浏览器自动发送 随之而来的要求
本地存储 在射程内，被文档归为更易访问的区域 无 阻断脚本注入几乎成了唯一防线
会话存储 在射程内，寿命绑在标签页上并不等于访问控制 无 标签页之间不共享所带来的体验设计
JavaScript 内存变量 在射程内，处在同一个执行上下文里 无 每次刷新都需要一条重新取得的路径
HttpOnly 且 Secure 的 Cookie (BFF) 会话状态无法被脚本直接读取 有，浏览器会带上它 因自动发送而需要的跨站请求防御

BFF 这一侧的规范写得很明确。BFF 必须为自己的 Cookie 打开 Secure 标志与 HttpOnly 标志(MUST)，文档解释说 HttpOnly Cookie 阻止攻击者直接访问会话状态。另一侧的代价同样清楚：Cookie 是浏览器自作主张带上去的，于是需要另设一条轴去确认「这次请求是不是从我们自己的界面发起的」。这笔账连同 Cookie 发送规则，在梳理信任边界与 Web 安全控制的那篇文章里谈得更细。

对于令牌中介后端，文档同样把两面都写了出来。后端必须以机密客户端的身份运作(MUST)，但访问令牌下到浏览器的那一刻，就暴露在浏览器内恶意代码的令牌窃取之下。无论选哪种架构，风险都不是消失，而是转移。

7. 作用域与最小权限 - 真正被强制的位置

作用域在 RFC 6749 里被定义为以空格分隔、区分大小写的字符串列表。紧接着的一条规范很容易被漏掉：授权服务器可以完全或部分地忽略客户端所请求的作用域，依据自身策略或资源所有者的指示。而当签发的作用域与请求的不同时，授权服务器必须在响应中包含 scope 参数，把实际授予的范围告知客户端。

由这一组推出的结论在实务上分量很重：作用域是请求，不是保证。如果客户端代码建立在「我们请求了这三个，所以就有这三个」的前提上，那么授权服务器削掉其中一个的瞬间，这个前提就不再成立。该读的不是请求列表，而是响应里的 scope。

然后是更重要的问题：作用域在哪里被强制？答案是资源服务器。RFC 9700 是这样写的：每一个资源服务器都有义务，对每一次请求，都验证随该请求送来的访问令牌是否本就是为这个资源服务器而准备的。同一节还要求收窄令牌本身的权限：访问令牌应当把受众限定到特定的资源服务器(SHOULD)，若不可行，则限定到少数几个资源服务器构成的集合。文档补充说，指定目标既可以用 scope 参数，也可以用 RFC 8707 的 resource 参数。

这里崩掉的是什么。在前端读作用域然后把按钮藏起来，那是提示而不是强制。只要资源服务器不在每次请求时确认令牌的受众与范围，无论按钮在不在界面上，那个端点都是开着的。不做受众限定，为另一个资源服务器签发的令牌就会直接通过。最小权限不是把作用域字符串写短一点，而是把检查点放在资源服务器上。

8. 刷新令牌与轮换 - 所谓检测究竟指什么

先把 RFC 9700 的要求原样抄下来：签发给公开客户端的刷新令牌必须被发送方绑定，或者使用刷新令牌轮换(MUST)。二选一。机密客户端那边，RFC 6749 早已要求刷新令牌只能由被签发的那个客户端使用。

文档举出的发送方绑定手段是双向 TLS 与 DPoP 两种。DPoP 即 RFC 9449，2023 年发布的 Proposed Standard，通过在应用层附上持有证明来为令牌施加发送方绑定。摘要写明这种机制能够检测针对访问令牌与刷新令牌的重放攻击。为什么还要另外备这样一套装置，回到 RFC 6750 的定义就清楚了：持有者令牌是无需证明持有某把密码学密钥，就允许访问与该令牌关联之资源的东西。谁拿着它，谁就是有权者。

轮换那边的原理，文档里写得原原本本：如果刷新令牌被窃取，攻击者与合法客户端都在使用它，那么其中一方必然会出示一个已经失效的刷新令牌，而这个事实会把泄露告知授权服务器。下一句在实务上更要紧：授权服务器无法判断是哪一方提交了失效令牌，因此会吊销当前有效的刷新令牌。

把这两句连起来读，轮换的性质就显出来了。轮换不是防止窃取的装置，而是在被窃令牌被使用的那一刻检测出来，又因为无法分辨而把两边一起切断的装置。由此带来两项设计负担。

  • 合法用户也会被一并切断。检测触发就意味着需要重新登录，如果没有把这段体验设计好，安全装置会被当成故障
  • 必须客户端确实保存了新令牌才成立。若没能把刷新响应里拿到的新刷新令牌存下来而又用了旧的，这个客户端自己就成了出示失效令牌的一方。同理，在多个请求可能同时发起刷新的结构里，会新添一条把刷新路径收拢成一条的条件

客户端侧的存放问题，从命令行的角度在梳理 CLI 认证设计的那篇文章里挖得更深。

9. 验证该在哪里做 - 客户端替代不了的事

令牌有两枚，验证的一方也就有两个。把这个对应关系搞反，就会出事。

9.1 访问令牌由资源服务器验证

再引一次 RFC 9700 那句话：每一个资源服务器都有义务，对每一次请求，都验证随之送来的访问令牌是否本就是为这个资源服务器而准备的。这项验证按令牌格式分成两路。

  • 若为 JWT 格式 - RFC 9068 是 2021 年发布的 Proposed Standard，规定了以 JWT 形式签发 OAuth 2.0 访问令牌时的必需与可选声明以及验证流程。这份规格出现的缘由，正是各家产品各行其是的 JWT 令牌实现破坏了互操作性
  • 若为不透明令牌 - RFC 7662 是 2015 年 10 月发布的 Proposed Standard，定义了受保护资源向授权服务器询问某枚令牌是否有效及其元数据的内省协议。无论信息是否嵌在令牌内部都能工作，正是这种方式的设计意图

9.2 ID 令牌由客户端验证

OpenID Connect Core 1.0 在 ID 令牌验证一节里列出了客户端必须确认的项目。

  • 签发者是否精确一致
  • 受众中是否包含自己的客户端标识
  • 当前时间是否早于过期时间
  • 若授权请求中送出过 nonce，其值是否一致
  • 用签发者提供的密钥验证签名是否有效

9.3 所以客户端不该做的是什么

浏览器里的代码去解析令牌，这件事本身没有问题。看一眼是否临近过期以便准备刷新，或者把用户名画到界面上，都是正常用法。问题在于把那个解析结果当作权限判定的依据。

理由有两条。第一，第 6 节那句话在这里同样成立：跑在浏览器里的代码与恶意代码处在同一层权限之上，它做的签名校验可以在同一个执行上下文里被架空。第二，服务器无从知道浏览器验证过什么。抵达资源服务器的只有请求和令牌。

所以签名校验、签发者确认、受众确认、过期确认都必须由凭这枚令牌交出东西的那一方来做。访问令牌是资源服务器，ID 令牌则是凭它建立会话的那台客户端服务器。浏览器里的解码是为展示提供的便利，不是控制。

10. 常见的错误组合 - 每种组合里崩掉的是什么

下面这张表不是禁令清单，而是把每种组合会放弃掉哪项保证，对应到规范的原句上。

组合 这个组合里崩掉的东西 对应的规范
把访问令牌当作身份凭证使用 没有依据确认它是为谁、经过何种认证而签发的 RFC 6749 安全考量, OpenID Connect Core 1.0
继续保留隐式流程 令牌随授权响应发出，且没有标准手段施加发送方绑定 RFC 9700 (SHOULD NOT)
密码许可与双因素认证并用 该许可本身就不是为配合双因素认证而设计的 RFC 9700 (MUST NOT)
公开客户端未启用 PKCE 对授权码拦截与代码注入根本没有防御 RFC 7636, RFC 9700 (公开客户端 MUST)
允许重定向 URI 的部分匹配 授权响应可返回的目的地集合比本意更宽 RFC 9700 (精确字符串匹配 MUST)
刷新令牌放在浏览器且未启用轮换 既没有检测窃取的位置，也没有绑定发送方的位置 RFC 9700, RFC 10017
接了多个授权服务器却不校验签发者 没有依据确定响应来自哪一台授权服务器 RFC 9207, RFC 9700
资源服务器不检查令牌受众 为另一个资源服务器签发的令牌会直接通过 RFC 9700 (对每次请求的验证义务)
用嵌入式 WebView 为原生应用授权 凭据只交给授权服务器这个前提不再成立 RFC 8252 (BCP 212)
只在界面上强制作用域 强制点不在资源服务器，端点就一直开着 RFC 6749 作用域定义, RFC 9700
用客户端凭据许可访问用户数据 许可的当事人消失，审计记录收敛为一个服务账号 RFC 6749 (仅限机密客户端, MUST)

未能确认的内容

  • 本文的依据只有 RFC 原文与 OpenID Connect Core 1.0 文档中的规范性表述。各家授权服务器产品或库如何实现这些规范并未查证，对某个具体实现是否合规不作任何主张
  • OAuth 2.1 是 2026 年 3 月 2 日的第 15 版互联网草案。草案不是标准，正式发布前内容可能变化。本文只引用了它不再规定隐式许可与密码许可这一编辑方向，未引用其中的具体条款
  • RFC 9700 提到的目标指定手段 RFC 8707 的 resource 参数，本文仅以引用关系提及，未与其原文核对
  • 基于双向 TLS 的证书绑定令牌的规范原文未曾打开。所确认的只是 RFC 9700 把双向 TLS 与 DPoP 列为两种发送方绑定手段这一事实
  • 未能找到显示各流程实际采用比例的可靠公开统计。因此本文中没有出现「大多数服务都是这么做的」这类表述

该按什么顺序读这些文档

把规范从头顺读会花掉很多时间。下面这个顺序的做法是先把词汇抓住，再用现在的基准线覆盖上去。

  1. RFC 6749 的角色与术语一节，以及授权码流程一节。四个角色和参数名从这里来。其余文档全都是用这套词汇写的
  2. RFC 6750。简短确认一下持有者令牌不保证什么。第 8 节的讨论就从这里出发
  3. RFC 7636。PKCE。篇幅短，问题定义清楚
  4. RFC 9700 (BCP 240)。今天的基准线，更新了 6749、6750 与 6819。先读 6749 再读它，才看得出清单上撤掉了什么。顺序反过来，理由就看不见了
  5. 挑一份对得上自己处境的：浏览器应用看 RFC 10017，原生应用看 RFC 8252，输入受限的设备看 RFC 8628
  6. 如果目标是登录，读 OpenID Connect Core 1.0 的 ID 令牌一节与 ID 令牌验证一节
  7. 如果问题出在令牌格式与验证，读 RFC 9068 或 RFC 7662 中对应自己令牌格式的那一份
  8. 接了多个授权服务器就看 RFC 9207，想从持有者令牌里走出来就看 RFC 9449，需要端点发现就看 RFC 8414

最后把本文的主张收成三条。第一，OAuth 是委托授权的规范，登录是架在它之上的另一层，规范的名字早就这么说了。第二，把检查点放在哪里，才是这项控制的实体；作用域也好令牌验证也好，在界面上做是提示，在资源服务器上做才是强制。第三，今天的基准线是 RFC 9700 而不是 RFC 6749。只读 2012 年那份文档去做设计，等于把此后十三年间被撤下清单的东西原样背在身上起步。
