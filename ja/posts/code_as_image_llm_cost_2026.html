コードを画像化してLLMトークン費用を減らす - pxpipeが突いたビジョン課金の隙

テキストトークンと画像トークンはなぜ違う基準で課金されるのか - 仕組み・精度の限界・プロンプトキャッシュとの比較

2026-07-06 IT・技術

序論: 画像1枚がテキストより安いという奇妙な話

AI APIの費用を減らす最も一般的な方法は、プロンプトを短くするかキャッシュを使うことだ。しかし2026年7月初め、GeekNews(hada)で紹介されたオープンソースプロジェクトpxpipeはまったく違う道を選んだ。コードやログのような容量の大きいテキストコンテキストをPNG画像に変換し、その画像をLLMのビジョン(画像認識)経路に流し込むというものだ。リポジトリの説明は端的に「コンテキストを画像として描画することでトークン使用量を削減する」としている(出典: GitHub)。実測値も小さくない - 実トラフィックで終端コストがかなり削減されたという報告がある。

本稿は発表資料の数字をそのまま転記するのではなく、なぜこのトリックが成立しうるのかをトークン課金の構造という観点から分解し、どこまで信頼できるのか、そしてプロンプトキャッシュやコンテキスト圧縮といった既存の正攻法と比べたときにこの手法を実務でどう位置づけるべきかを、自分自身の分析としてまとめる。2026年7月現在、この手法はまだ実験段階であり、ここで挙げる数値は特定のモデル・特定のワークロードでのみ検証されたものである点を先に断っておく。

1. テキストトークンと画像トークンは、そもそも違う物差しで測られる

この手法を理解する出発点は、二つのモダリティの課金方式が根本的に異なるという事実だ。

1.1 テキストトークン: 文字数に素直に比例する

LLMがテキストを処理する際は、BPE(バイトペアエンコーディング)系のトークナイザが文字列をサブワード単位に分割する。トークン数は事実上、文字・サブワード片の数に比例して増える。コード100行をテキストで送れば、その100行分のトークンが課金される - コードが密であろうと疎であろうと、文字数がそのままコストになる。

1.2 画像トークン: ピクセル面積・タイル数で決まる

画像入力はまったく違うルールに従う。主要プロバイダーは画像トークン数を「中に何が描かれているか」ではなく「画像が何ピクセルで、いくつのタイルに分割されるか」で計算する。

プロバイダー画像トークンの計算方式(公開資料基準、2026年7月時点)
Anthropic(Claude)おおむね(横×縦)/750のピクセル面積に比例
Google(Gemini)384px以下は固定258トークン、それ以上は768×768タイルごとに258トークン
OpenAI(GPT)縮小後にタイル・パッチ単位で分解、タイル・パッチごとの固定トークン+ベースコスト

数値はモデル世代ごとに調整されるため、あくまで方向性として参考にしてほしい。

1.3 核心的な違い: 密度と無関係な課金

画像トークンのコストは、絵の中に文字が密に詰まっていようとほぼ空白であろうと、ピクセルサイズさえ同じなら変わらない。一方テキストトークンのコストは文字数に素直に比例する。この計算方式の違いそのものが、pxpipeが突いた隙間だ。

2. コードを画像に描くとなぜ安くなるのか - メカニズム分析

pxpipeの核心的な洞察は単純だ。コード・JSON・ツール実行ログのように文字が密なテキストを、小さいフォントで1枚の画像に描画すれば、同じ情報量をはるかに少ない画像トークンで運べる。

2.1 テキストの密度をピクセルに詰め込む

プロジェクト側の説明によれば、実トラフィックにおいて密度の高いコード・JSON・ツール出力は画像トークン1個あたり約3.1文字を収めていた一方、テキストトークンは1トークンあたり約1文字だったという。同じテキストを画像として描画して送れば、算術上、約3分の1のトークンで同じ文字数を伝えられるということだ。

2.2 報告されている実測圧縮率

公開されている実測値もこれを裏付ける。約1万3千件の実リクエストを観察した結果、終端コストが約59%(100ドル→約41ドル)削減され、その後の約8,900件の圧縮適用リクエスト区間では約70%まで削減されたという報告がある。ある事例では、テキストなら約2万5千トークンかかる内容が画像では約2,700トークンに縮んだという数字も挙げられている - 概ね9倍の圧縮だ。ただしこれはコーディングエージェントの反復的なコンテキストという特定のワークロードに最適化された結果であり、ワークロードが異なれば削減幅も大きく変わりうる。

2.3 実態は価格体系の隙を突く裁定取引

冷静に見れば、これは圧縮技術そのものの進歩というより、プロバイダーが画像課金体系を設計する際に「写真のように情報密度の低い画像」を前提としていて、「密なモノスペーステキストを描いた画像」までは想定していなかったことから生じる価格体系の隙を突く裁定取引(アービトラージ)に近い。ビジョン入力経路を事実上のテキスト圧縮コーデックへと転用したわけだ。

3. 精度という代償 - ビジョンはOCRではない

ここで必ず区別すべき点がある。画像内の文字をモデルが「読む」ことは、スキャナが文書をOCRすることとは異なる。

3.1 パッチ埋め込みと「もっともらしい確信」

ビジョンエンコーダは画像をパッチ単位に分割して埋め込みに変換し、言語モデルはその埋め込みから「もっともらしい」テキストを復元する。フォントが小さかったり文字が密だったりすると、特定のピクセルパッチが複数の文字候補と曖昧に重なり、モデルは文脈上最もそれらしい文字で埋める。ほとんどの散文やコードロジックではこの「それらしさ」が実際の原文と一致するが、常にそうとは限らない。

3.2 実測: 正確な文字列復元のばらつき

関連するテストでは、無作為な12桁の16進数文字列を画像から復元する課題でモデルごとに大きなばらつきが見られた。あるモデルは15個中13個を正解したのに対し、別のモデルは15個中1個も正確に復元できなかったという。しかも失敗は「わからない」というエラーではなく、もっともらしく見える誤った文字列を自信満々に返す形で現れた - プロジェクト側はこの種の失敗を「静かな作話(silent confabulation)」と呼んでいる。

3.3 圧縮率と精度の曲線

このトレードオフはpxpipe固有の話ではなく、学術的にも定量化されている。2025年末に公開された光学的コンテキスト圧縮の研究(DeepSeek-OCR)は、テキストトークン数が画像トークン数の10倍以内(圧縮率10倍以下)であれば復元精度が約97%まで保たれるが、圧縮率を20倍まで押し上げると精度が約60%程度まで落ちると報告している。圧縮を強くかけるほど、精度は緩やかにではなく急激に崩れるということだ。

3.4 なぜ「静かな」失敗の方が危険なのか

テキストAPIがトークン上限を超えると、明示的なエラーが出るか、切り詰めが目に見える形で現れる。一方、画像から誤読された文字列は、応答の形式上まったく正常に見える - 別途その値を検証しない限り誤りに気づく方法がない。人間が改めて目を通すワークロードなら相対的にリスクは低いが、結果をそのまま自動化パイプラインへ流し込む構造ならリスクは積み上がる。

4. どこに使えて、どこが危険か

この手法の価値は結局のところワークロードの分類にかかっている。

4.1 適した作業

システムプロンプトやツールドキュメントのように概ね固定的で、おおまかな意味さえ伝われば十分な背景コンテキスト、複数ターンにわたって積み重なる会話履歴のうちもはや細かい値が重要でない過去の区間、参考としてざっと目を通すだけの大量のログ・文書のように「要旨」さえつかめればよいコンテンツに向いている。

4.2 危険な作業

ハッシュ値・APIキー・シークレット・正確な行番号・座標・パッチ(diff)のように、一文字違うだけで意味がまったく変わる値、そしてその値が以降の文字列比較や自動適用にそのまま使われるワークロードは、この方式と相性が悪い。pxpipe自体も、直近の会話ターン、ユーザーメッセージ、モデル出力、許可リスト外のモデルについてはテキストのまま残す形でこのリスクを管理している。

4.3 モデル依存というリスク

このトリックの有用性は、特定のモデルが画像内の文字をどれだけ正確に読み取れるかに全面的に依存している。報道によれば、このプロジェクトは基本的に画像読み取りの誤り率が低い一部のモデルにのみ画像化を自動適用し、誤り率が相対的に高い他の最上位モデルはオプトインでのみ開放している。今日あるモデルでうまくいったトリックが、そのモデルの次バージョンや別プロバイダーのモデルでは誤読率が変わり、まったく違う結果になりうる - ベンダーの一度のアップデートで静かに壊れうる最適化ということだ。

5. プロンプト費用最適化の正攻法との比較

画像レンダリングをプロンプトキャッシュ・コンテキスト圧縮と並べてみると、性格の違いがはっきりする。

5.1 プロンプトキャッシュ: 無損失、反復が条件

複数のリクエストが同一のプレフィックス(システムプロンプト、固定文書など)を共有するとき、サーバー側ですでに計算済みのアテンションのキー・バリューを再利用し、その区間の再計算コストをなくす方式だ。主要プロバイダーはいずれもこの機能を支持しており、キャッシュがヒットするとその区間の単価が標準入力価格に比べて大幅に(公開資料基準で通常9割前後)下がるとされる。鍵となる条件は「静的な内容を前、可変な内容を後ろ」に配置してプレフィックスが繰り返されることであり、この過程で原文は一文字も損なわれない。

5.2 コンテキスト・セマンティック圧縮: 制御された損失

要約ベースの圧縮ツールは、「重要度が低い」と判断された文やトークンを意図的に間引いたり別の表現に置き換えたりする。これにも損失はあるが、その損失は「何を捨てるか」を重要度スコアなどの制御された基準で選んだ結果だ。

5.3 画像レンダリング: 制御しにくい損失

前の二つとは性格が異なる。情報を捨てたり要約したりせず同じ内容を維持したまま、それを運ぶモダリティだけをテキストから画像に変える。圧縮は起きるが、損失がどこで発生するかをユーザーが制御しにくい - どの文字が誤読されるかはフォント・レイアウト・その瞬間のモデルの状態に左右され、予測が難しい。一方でキャッシュと違い、繰り返されないコンテンツ(毎回新しいコードやログ)にも適用できるため、キャッシュが届かない領域を狙うものと見るべきだ。

6. 結論 - 実務でどう向き合うか

費用最適化の順序としてはキャッシュ → セマンティック圧縮 → 画像レンダリングが合理的だ。キャッシュと圧縮は無損失または制御された損失であり、検証コストも低い。画像レンダリングはその次に、正確な値が不要な領域に限って実験するのが安全だ。

導入するなら、必ず自分のワークロードでゴールデンセットを作り、画像化前後で実際の値の誤りが増えたかを測定すべきだ。2026年7月現在、この手法をうまく支持するモデルは限られており、ベンダーが異なれば、あるいは同じベンダーの次のモデルであっても誤読率が変わりうることを前提にする必要がある。そして、ハッシュ・シークレット・正確な座標や行番号が行き交う区間は絶対に画像化せず、テキストのまま残すべきだ - 費用を節約しようとして静かに誤った値が下流のシステムへ流れ込むことこそ、この手法の最も現実的なリスクである。
