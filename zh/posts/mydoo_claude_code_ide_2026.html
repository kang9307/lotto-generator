myDoo — 以Claude Code为默认LLM的AI原生IDE

终端智能体与GUI编辑器的融合如何重塑开发体验 — 与Cursor、Windsurf、Kiro的差异及AI原生IDE趋势分析

2026-06-23 IT/技术

引言：将智能体引入编辑器内部

截至2026年6月，AI编程工具市场大致分为两大阵营。一是AI增强编辑器——Cursor和Windsurf等fork VS Code并在其上叠加自有AI层的工具。二是CLI智能体——Claude Code和OpenCode等在终端中自主理解并操作代码库的工具。两者都改变了开发方式，但本质上始终是分离的世界。要使用智能体，就必须打开终端；要使用编辑器，就必须走出智能体的上下文。

开发者Lee Geun-young在GeekNews（hada.io）上发布的myDoo正是弥合这一鸿沟的尝试。项目的核心主张一句话道尽：「在VS Code基础上，以新方式实现了Claude Code的智慧与IDE的便利」。这是一个将Claude Code作为编辑器一等公民的宣言——不是边栏插件，而是编辑器运行的认知层。

本文不是产品介绍，而是分析：这种集成为何有意义、myDoo与现有工具有何不同、这一方向在AI原生IDE大趋势中处于什么位置。由于关于myDoo的公开信息有限，我将明确区分已确认事实与推论。

1. myDoo是什么 — 以Claude Code为IDE引擎

myDoo是以Claude Code为默认LLM的VS Code系AI原生IDE，由独立开发者Lee Geun-young构建，发布于GeekNews的Show GN板块。2026年6月，受到韩国开发者社区的广泛关注。

1.1 核心理念：智能体作为引擎而非插件

关键概念区分在于「插件」与「引擎」。现有的Claude Code VS Code扩展是将Claude Code附加在编辑器旁侧——智能体在终端独立运行，编辑器近似于展示其输出的查看器。myDoo的目标是让Claude Code成为编辑器本身的认知层。打开文件、浏览代码、编辑、执行、审查diff——所有操作都在编辑器与智能体共享的单一上下文中进行。

这看似微小的区别，在开发流程中却是决定性的。如果智能体自动知道「编辑器当前打开的文件」，开发者就无需每次手动复制粘贴上下文。智能体生成diff时，编辑器立即以内联方式展示，开发者无需切换上下文即可审查并接受。

1.2 LLM选择的战略意义

myDoo选择Claude Code作为默认LLM是一个战略判断。截至2026年6月，开发者调查显示Claude Code主力工具采用率达28%，超过Cursor的24%。Anthropic持续改进智能体循环、MCP（模型上下文协议）集成和工具调用可靠性。通过将这个成熟智能体作为引擎而非自行开发LLM层，独立开发者可以快速交付高质量的AI原生IDE。Anthropic每次改进Claude Code——更好的文件编辑、更智能的上下文管理、新的MCP集成——myDoo无需额外开发即可获益。

但这种选择带来真实的依赖风险：Anthropic的API定价、政策决定和可用性。离线或隔离环境是明显的局限。以开发速度和质量换取LLM层自主性——这个权衡需要正视。

2. 终端与GUI融合改变了什么

让我们具体说明这种集成在开发工作流中实际改变了什么。

2.1 消除上下文切换成本

目前同时使用Claude Code和VS Code的最常见方式是两个独立窗口：一侧是编辑器，另一侧是运行智能体的终端。开发者需要将文件路径复制到终端、复制错误信息、切换窗口构建请求、再切换回来查看结果。这种上下文切换成本不仅仅是不便——它打破心流状态，增加手动组装上下文的认知负担，引入出错的空间。

当智能体集成到编辑器中，它已经知道编辑器正在查看什么。打开的文件、光标位置、最近的修改、诊断错误——这些都自动成为智能体上下文的一部分。开发者在当前位置直接提问，智能体以完整的情境感知作答。

2.2 内联diff审查与编码流程的统一

智能体修改代码时最关键的时刻是开发者审查这些变更的时刻。基于终端的智能体以文本输出diff，或将修改推送到文件让开发者在编辑器中检查。这种审查步骤的摩擦不是中性的——许多开发者正是因为上下文切换让彻底审查显得昂贵，才会草草了事或直接跳过。将diff内联展示在编辑器中，使代码审查成为编码流程的自然组成部分，而非中断。这是将智能体集成到编辑器中最具体的价值：让代码所有权从智能体转移给开发者的时刻尽可能无摩擦。

2.3 即时反馈循环

智能体会犯错，尤其是上下文不足或请求模糊时。在终端系统中，智能体犯错后，开发者切换到编辑器查看之前无法发现。在编辑器集成系统中，编辑器的诊断层——编译错误、类型错误、lint警告——在智能体修改后立即反映。智能体可以将这些诊断作为反馈接收，并尝试自我修正，无需开发者手动传递信息。这种反馈循环的缩短是提升智能体编程可靠性的核心。

3. 与Cursor、Windsurf、Kiro的差异

理解myDoo的定位，需要与占据市场的工具进行诚实的比较。

3.1 Cursor — VS Code Fork的最强选手

截至2026年中，Cursor是AI IDE市场最完善的产品。Tab预测补全不仅完成代码行，还能预测整个下一个代码块，准确度领先业界。上下文感知深度强，编辑器集成精细。Cursor构建并维护自有AI层，而非委托给Claude Code这样的外部智能体。myDoo与Cursor的核心差异在于：myDoo将Claude Code的智能体循环本身集成到IDE中。

3.2 Windsurf — 强调自主性的Cascade智能体

Windsurf的Cascade智能体在多文件自主修改方面表现突出，吸引偏好「将整个任务交托给智能体」工作流的开发者。2026年Codeium将Windsurf转型为Devin Desktop，延续了这一自主性方向。与myDoo的区别在于引擎：Windsurf用Cascade，myDoo用Claude Code。哪个更好取决于具体工作负载，在没有直接对比的情况下无法得出确定结论。

3.3 Amazon Kiro — 规格驱动开发与云端深度集成

Kiro是2026年最具特色的新进入者。同样基于VS Code（Code OSS），它引入规格驱动开发：在写代码之前，智能体先生成需求文档、架构计划和测试规格，结构化计划成为实现的支撑。Kiro支持包括Claude在内的多个LLM，但与AWS服务（Lambda、DynamoDB、S3、Bedrock）的深度集成使其明显偏向AWS生态。myDoo以Claude Code保持云中立，与此形成对比。

3.4 myDoo的差异点 — 轻量集成与Claude Code生态系统继承

myDoo与其他三者最重要的区别在于不开发自有AI层。这既是弱点，也是优势。弱点：Claude Code的限制即是myDoo的限制；Anthropic的定价变化直接影响用户。优势：Anthropic每次改进Claude Code，myDoo都零开发成本受益。独立开发者能在AI IDE竞争中对抗资金雄厚的团队，正是因为不必重建Anthropic已经构建的东西。竞争杠杆是真实的；依赖风险同样是真实的。

4. 2026年AI原生IDE市场地形图

myDoo不是孤立的实验，需要放在2026年AI原生IDE市场的大趋势中理解。

4.1 三大阵营

当前市场大致分三个定位。第一，拥有自有AI层的VS Code Fork：Cursor以最完善的功能集领军。第二，云集成规格驱动开发环境：Kiro将开发环境与云生态系统捆绑，在编码前增加结构化规划。第三，封装成熟外部智能体的轻量集成：myDoo，以及某种程度上Zed与Claude Code的搭配，代表这种方式——封装已验证的智能体，而非从头构建AI。每个阵营对「开发者真正需要什么」和「可持续竞争护城河在哪里」有不同判断。

4.2 从「AI植入IDE」到「以智能体为中心」的转变

2025-2026年AI开发工具的核心转变是：从「在IDE中添加AI」转向「围绕智能体构建，让编辑器扮演支撑角色」。Claude Code Desktop将智能体包装成独立应用并支持多会话管理；Google Antigravity以智能体编排器为中心；Kiro将规格作为智能体的起点。myDoo则采取将智能体集成进编辑器的路径，而非将智能体提升为独立平台。这是有效的路径——大多数开发者大部分时间在编辑器中工作，在工作已发生的地方迎接智能体有其真实的用户体验逻辑。

4.3 独立开发者在市场中的角色

myDoo是独立开发者项目这一事实揭示了当下时刻的一个重要特征。Cursor获得了数亿美元风险投资；Kiro是AWS的产品。然而在AI原生IDE领域，单个开发者利用Claude Code（成熟智能体）和VS Code开源扩展API可以快速交付有竞争力的工具。基础模型生态系统已显著降低了开发工具的进入门槛。这不是暂时现象，而是将持续产生来自意想不到之处的有趣工具的结构性转变。

5. 开发体验变化的具体分析

超越抽象分析，从我自己的视角具体整理开发流程发生了什么变化。

5.1 提问的上下文自动构建

目前在终端Claude Code中最频繁的操作之一是「请修复我现在看到的这个文件中的错误」。将这一句话传达给终端，需要复制文件路径、复制错误信息、必要时还要提及相关文件。当智能体集成到编辑器中，所有这些上下文都自动构建。开发者只需输入「帮我修这个」，智能体已经知道编辑器打开的文件、光标位置和诊断错误。提问质量提升，回答准确度随之提高。

5.2 审查流程不与编码流程分离

智能体编程中最危险的时刻是开发者没有充分审查智能体输出就接受的时候。摩擦导致许多开发者草草审查或直接跳过。当智能体的diff内联显示在编辑器中，审查成为编码流程的自然组成部分。不是「将责任委托给智能体」，而是「与智能体协作开发」的范式得以具体化。

5.3 智能体错误即时可见

当上下文不足或请求模糊时智能体会犯错。编辑器集成智能体让错误在诊断层立即反映：编译错误、类型错误、lint警告在智能体修改后即刻显示，智能体可接收这些诊断作为反馈并尝试自我修正。这种反馈循环的缩短是提升智能体编程可靠性的核心。

6. 注意事项与局限

也需要直视myDoo的现实局限。

6.1 信息的局限

myDoo是发布于GeekNews的个人项目，截至2026年6月，公开的技术文档和详细功能列表尚不充分。本文描述的「集成方向」和「带来的体验变化」基于已公开的概念和AI IDE市场的一般趋势，实际实现细节可能有所不同。对未亲自使用过的工具做出确定性判断需要谨慎。

6.2 Claude API依赖

以Claude Code为默认引擎意味着承受Anthropic的API成本结构和政策。对于想使用本地LLM或要求离线环境的团队，这是一个制约。2026年出现了通过非官方代理以本地LLM替代Claude Code的方案，但并非官方支持。

6.3 成熟度与生态系统

Cursor拥有数百万用户，快速发布周期修复漏洞，拥有广泛的社区和文档。myDoo目前处于起点。个人项目成长为成熟产品需要巨大的持续性投入。现阶段将myDoo作为主要开发工具不如视其为探索这一方向可能性的参考项目更为现实。

7. 结论 — AI原生IDE的下一步

myDoo指明的方向是清晰的：打破终端智能体与GUI IDE之间的壁垒，将Claude Code作为编辑器的一等构成要素。若能成功，开发者可以在无需上下文切换的情况下与智能体协作，在编辑器流程内审查智能体输出，将与AI协作编程的体验构建为完整的闭环。

截至2026年6月，AI原生IDE市场的赢家尚未确定。Cursor目前完成度最高，但Kiro、Windsurf、OpenCode、myDoo各自从不同角度撼动格局。这种碎片化是市场仍在探索「哪种方式才是正确的」的信号。myDoo在这场探索中尝试「最大化利用Claude Code生态系统的轻量集成」这一答案。

在终端诞生的智能体进入编辑器内部。编辑器围绕智能体重新构建。这两种运动交汇的地点，正是myDoo所在之处。无论结果如何，这个实验都有助于让AI原生IDE应当意味着什么变得更加清晰。
