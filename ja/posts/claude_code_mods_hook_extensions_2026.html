modの定義とアーキテクチャ — 設定フックと異なるセッション常駐構造

原文はmodを、Claude Codeのセッション内で動作する小さなJavaScriptまたはTypeScriptのファイルと定義する。modはセッションで起きていることを監視でき、Claude Codeの動作を変えることができ、ターミナルでもデスクトップアプリでも独自のUIを描画できる。APIを先に学ぶ必要はない。claudeを起動して欲しいmodを言葉で説明し、ホットリロードを許可するか尋ねられたら許可すれば、ターンの終わりにmodが現れるという。

Claude Codeはすでに、設定、権限ルール(permission rules)、スラッシュコマンド、スキル、ステータスラインによって多くの挙動を変えられる。原文は、modはさらに一歩進み、Claude Codeの動作を書き換えたり置き換えたりでき、独自のUIまで描画できると説明する。内部的にはmodはプラグインに同梱されて配布されるフックであり、各modはセッション中のあらゆるイベントを発生した時点で目にする。

設定フックとの違いは、原文が短い一段落にまとめている。設定フックはイベントごとにシェルコマンドを実行し、stdinとstdoutでJSONを受け渡す。一方、modは一度だけ読み込まれ、セッションに留まる。この構造から、modができることは次の4点に整理できる。

  • 一度読み込み、セッションに留まる: イベントごとにプロセスを起動せず、読み込まれた状態のままセッションの間ずっと存在する。
  • 状態を保つ: 値をモジュール変数ではなくホストが保持する$.stateに置けば、リロードを経ても残る。
  • UIを更新する: イベントが起きるたびに更新されるUIを描画する。
  • コールバック: Claude Codeを呼び返して、paneを開く、プロセスを実行する、スラッシュコマンドを登録する、モデルが呼べるツールを登録する、といった操作を行う。

原文によれば、Claude Code自身もmodを使っている。AGENTS.mdのサポートや、対話の横に出る/diffのpaneなど一部の機能はmodとして作られている。そのソースとテストは公開リポジトリanthropics/claude-codeのmods/以下にあり、チームがmodをどう組んでいるかを読める。

フックチェーンと3大動作パターン — Observe·Rewrite·Answerの仕組み

modはプラグインのフックが連なったチェーンとして動く。モジュールはregister(on, options)をエクスポートし、その内部でon(event, matcher?, hook)によってフックを追加する。すべてのフックは同じ形をしており、原文のコードがその形と3つの引数の意味をコメントで説明している。

on("tool.call", { tool: "Bash" }, async ($, e, next) => {
                      // $    the mods API: ui, session, state, store, fs, process, clock, http, tool, command, model, ...
                      // e    this event's input, as plain data
                      // next passes e to the other plugins and then to Claude Code's own behavior
                      return next(e);
                    });

フックはミドルウェアのように連なる。自分のフックが実行され、next(e)がイベントを次のプラグインへ渡し、最下層でClaude Codeがもともと行うはずだった処理を行う。フックにできることは3つある。まず監視(Observe)は、const r = await next(e);で結果を受け取って確認し、そのまま返す動作で、すべてのファイル編集の記録や毎ターン終了後の値の取得がその例である。次に書き換え(Rewrite)は、return next({ ...e, command: safer })のようにチェーンの残りが目にする入力を変える動作である。最後に直接応答(Answer)は、nextを呼ばずに{ deny: "…" }を返す動作で、ツール呼び出しを拒否したり、コマンドやツールをフックが自分で処理したりする。

パターン区分コード構文原文の例チェーン上の位置
Observe (監視)const r = await next(e); /* look */ return rすべてのファイル編集の記録、毎ターン後の値の取得nextを呼んだ後に結果を見る
Rewrite (書き換え)return next({ ...e, command: safer })チェーンの残りが目にする入力を変えるnextを呼ぶ前に入力を変える
Answer (直接応答)return { deny: "…" } (next未呼出)ツール呼び出しの拒否、コマンドやツールの自前処理チェーンを断ち、フックが代わりに答える

原文が述べるイベントの範囲は、ツール呼び出し、送信されたプロンプト、ターンの開始と終了、セッションの開始と終了、スラッシュコマンド、そして描画されるインターフェースのあらゆる断片を表すui.renderである。本文とコードから名前が確認できるものは次の通りである。

  • tool.call: ツール呼び出し。{ tool: "Bash" }のようにツール名で絞り込める。
  • prompt.submit: 送信されたプロンプト。原文はチームの規約をすべてのプロンプトに加えるフックをアイデアとして挙げている。
  • turn.start · turn.complete: ターンの開始と終了。サブエージェントのターンはe.agentIdで区別する。
  • session.start: セッションの開始。原文はセッションの開始と終了をイベントとして挙げている。
  • command.run: 登録したスラッシュコマンドの実行時。{ command: "replay" }のようにコマンド名で絞り込む。
  • ui.render: インターフェースの断片が描画されるとき。{ component: "AbovePrompt" }のようにコンポーネントで絞り込む。

モジュールは専用のサンドボックスで動作し、DOMもNodeもない。そのため外部に出る処理はすべて$を経由する。原文コードのコメントは、$がui、session、state、store、fs、process、clock、http、tool、command、modelなどを持つと記している。

modプラグインの構成要素 — マニフェスト・型契約・$.state

modは特別な形式ではなく、ごく普通のプラグインフォルダである。原文が示すToken Weatherの構成は次の通りである。

token-weather/
                    ├── .claude-plugin/
                    │   ├── plugin.json
                    │   └── types/            (written by Claude Code when it loads the mod)
                    ├── hooks/
                    │   ├── hooks.json
                    │   └── token-weather.mjs
                    ├── types/
                    │   └── index.d.ts        (added in step 3)
                    └── tests/
                        └── token-weather.test.ts   (added in step 5)

各部分の役割は次の通りである。

  • .claude-plugin/plugin.json: 標準のプラグインマニフェスト。name、version、description、authorを記す。
  • hooks/hooks.json: modulesの下にモジュールをちょうど1つ指定する。原文は「A mod has exactly one」と書いている。
  • types/index.d.ts: $.stateに置く値をPluginStateインターフェースに宣言する型契約。マニフェストに"types": "./types/index.d.ts"を加える必要がある。
  • .claude-plugin/types/: modを読み込むたびにClaude Codeがそのビルドの宣言を書き込むフォルダ。エディタとtsc -pが追加の手順なしにこれを使う。

原文が最も強調する習慣は、ホットリロードを前提に設計することである。モジュール直下のlet readings = []は手軽に見えるが、ホットリロードは新規の読み込みなのでregisterとsession.startが再び実行され、モジュール変数は初期状態に戻る。履歴は$.stateに置くべきで、これは名前付きの値をホスト側に保持するためリロードを経ても残る。値は{ plugin: "token-weather", key: "readings" }のようにpluginとkeyで指し、$.state.getと$.state.setで読み書きする。

宣言を省くと、claude plugin validateが修正箇所を示すエラーで止める。原文が示すエラーは「token-weather.readings is not declared: the manifest's types contract must name it in interface PluginState { … }」である。きちんと宣言した見返りもある。レンダーフックの実行中に行った$.state.getはその描画を購読するため、以降に$.state.setが行われるたびに帯が再描画され、$.ui.invalidateを呼ぶ必要はない。

実装例1: Token Weather — コンテキスト残量と12ターン推移の可視化

原文が空のフォルダから作って見せる最初のmodがToken Weatherである。毎ターンの後にコンテキストウィンドウの埋まり具合を読み取り、プロンプトの真上の帯に1行を描画する。その1行には、天気アイコン、使用率、ウィンドウに対する使用トークン数、直近のターンの小さなグラフ、直前のターンが増やした量が入り、全体で約80行である。原文は、この帯が18%のClear、67%のShowers、81%のStormと埋まっていく様子を示している。

プロンプトの真上の帯はAbovePromptというコンポーネントである。Claude Code自身はここに何も描画しないので、最初の題材に向いていると原文は述べる。このコンポーネントのui.renderイベントにフックを掛け、要素のツリーを返せばよい。原文の第2ステップのコードは次の通りである。

// hooks/token-weather.mjs
                    export function register(on) {
                      on("ui.render", { component: "AbovePrompt" }, ($, e, next) => {
                        const { Box, Text } = $.ui.resolve(e);
                        return Box({
                          paddingX: 1,
                          children: [Text({ color: "yellow", bold: true, children: "☀  Clear skies" })],
                        });
                      });
                    }

要素はグローバルではない。描画先(surface)ごとに対応する要素が少しずつ異なるため、$.ui.resolve(e)がその描画先用のコンストラクタを返す。claude --plugin-dir ./token-weatherでセッションを開くと、プロンプトの上に「☀ Clear skies」が現れ、フォルダは監視されているので、保存するたびに再起動なしでモジュールがその場で再読み込みされる。

数値は$.session.usage()から読む。ステータスラインと同じ数値を返し、context.tokens、context.window、context.percentが含まれる。呼び出しは無料で、内訳を求めたときだけトークン数のリクエストが送られる。フックはsession.startとturn.completeでまずnext(e)を呼んでから観察するだけで、if (!e.agentId)によってサブエージェントのターンを除外し、メインループのターンだけを読む。履歴は直近12件だけを残し、▁▂▃▄▅▆▇█の文字でグラフにする。

原文は、真似する価値のある細部を3つ挙げる。コンポーネントのpropsはe.propsにある。hasSurveyが真なら、アンケートが帯を使いたがっているのでnext(e)で譲り、bodyColumnsは帯の実際の幅で、paneが横に付いているときはターミナルより狭い。このコードは幅が60桁以上のときだけグラフと増減を加える。描画するものがなければnext(e)を返して、帯をClaude Codeや他のmodへ返す。最後に、絵文字ではなく幅が1つの記号を使えば、どのターミナルのフォントでも揃う。

実装例2: Blast Radius — 危険コマンドの保留と影響試算レポート

ClaudeがBashで次のいずれかを呼ぶと、Blast Radiusはその呼び出しを保留する。コマンドが触れる対象を算出したうえで、ProceedとCancelのあるpaneを開く。2を押すとClaudeは理由付きの拒否を受け取り、1を押すとコマンドは書かれたとおりに実行される。

  • rm -rf
  • git reset --hard
  • git clean
  • 強制プッシュ(force push)
  • データベースマイグレーション(database migration)

このmodが使うフックは3つで、Bashに対するtool.callと、PaneおよびAbovePromptに対するui.renderである。核心は先の表にあった直接応答(Answer)であり、原文のコードは次の通りである。

on("tool.call", { tool: "Bash" }, async ($, e, next) => {
                      const risk = classify(String(e.command ?? ""));
                      if (risk === null) return next(e);                 // everything else runs as normal
                      const report = await measure($, risk, await $.session.cwd());  // git status, git clean -n, du, ...
                      held = { command: e.command, risk, report, decision: null };
                      const opened = await $.ui.open({ id: "blast-radius", title: "Blast Radius", focus: true });
                      if (!opened.isPlaced) held.where = "band";         // too narrow for a pane: draw above the prompt
                      while (held.decision === null && !next.signal.aborted) {
                        await $.process.run(["sleep", "0.25"]);          // time inside $ calls doesn't count against the hook's time limit
                      }
                      if (held.decision === "proceed") return next(e);   // let it run
                      return { deny: `Blast Radius held this command: the user pressed Cancel. It would have: ${report.summary}.` };
                    });

原文がこのコードから指摘する点は4つある。第一に、ドライランは$.process.runで行う。レポートはgit status --porcelain、git clean -n、git log HEAD..origin/main、showmigrationsといったツール自身のコマンドから得られ、引数はargv配列として渡すため、パスに含まれるどの文字もシェルコードとして実行されない。第二に、呼び出しの保留である。フックは1回の呼び出しにつき自分の時間として10秒を与えられるが、$呼び出しの中で待つ時間は数えられない。そのため、ボタンのonPressが決定を設定するまで短いsleepプロセスで待ち続け、next.signalが中断されたとき(Escを押したとき)に諦める。

第三に、ボタンにはホットキーを付けられる。Button({ label: "Proceed", hotkey: "1", onPress })は、クリック、TabとEnter、数字キーのいずれでも押せる。第四に、帯への縮退である。ターミナルが十分に広ければpaneを会話の横に付け、$.ui.openがisPlaced: falseと答えたときは、同じレポートをプロンプトの上に描画する。

原文は限界もはっきり書いている。このmodは安全網であって、権限システムではない。コマンドの文字列を読むため、$(…)、エイリアス、rmを呼ぶスクリプトは通り抜ける。確実に止めるには権限ルールを使う。

実装例3: Replay Theater — ターン別ファイル編集差分の段階再生

Replay Theaterは、ターンの実行中にすべてのEditとWriteの呼び出しを記録する。対象はファイルと、書き込み前後のテキストである。ターンが終わるとプロンプトの上にヒントが現れ、rを押すか/replayと入力すると、番号付きのステップの帯とPrev、Next、Closeのボタンを備えたpaneが、編集をdiff1つずつ順に見せる。このmodは編集を止めも変えもせず、観察するだけで、原文のコードは次の通りである。

on("tool.call", async ($, e, next) => {
                      if (EDIT_TOOLS.has(e.tool)) state.pending.push(...(await stepsFor($, e)));  // old/new text → diff
                      return next(e);                                                              // the edit runs untouched
                    });
                    on("turn.start", ($, e, next) => { if (!e.agentId) state.pending = []; return next(e); });
                    on("turn.complete", async ($, e, next) => {
                      const r = await next(e);
                      if (!e.agentId && state.pending.length) state.replay = state.pending;       // one replay per turn
                      return r;
                    });
                    on("session.start", async ($, e, next) => {
                      const r = await next(e);
                      await $.command.register({ name: "replay", description: "Step through the last turn's file edits" });
                      return r;
                    });
                    on("command.run", { command: "replay" }, async ($, e) => ({ text: (await openReplay($)) ? "Replaying" : "No edits" }));

原文が整理する学べる点は4つある。1つ目はイベントの組み合わせで、turn.startとturn.completeが編集を1ターンごとの再生にまとめ、e.agentIdがサブエージェントのターンをまとまりから除く。2つ目はスラッシュコマンドの登録で、session.startで$.command.registerを呼び、command.runで応答する。3つ目はファイルの読み取りで、Writeでは書き込みが反映される直前に$.fs.readで古い内容を読むため、diffは実際のものになる。4つ目は、配置は描画先の役目だという点である。全画面ではpaneが右側に付き、80桁ではプロンプトの上にインラインで開くが、modはどちらの場合も同じツリーを描画する。

modの配布とセキュリティ境界 — ローカル実行権限と出所確認の原則

原文の第5ステップは検証とテストである。claude plugin validateは、マニフェストとモジュールのソースをClaude Codeが読むのと同じ方法で読み、モジュールがどのイベントにフックし、どの$のメソッドを呼ぶかを報告する。claude plugin testは、プラグインの*.test.tsファイルを実際のClaude Codeランタイムに対して実行する。テストがonで登録したフックはチェーン上でmodの後に実行され、Claude Codeが返すはずの答えを代役として返すので、$.session.usage()が返す値を自分で決められる。

claude plugin validate ./token-weather
                    claude plugin test ./token-weather
                    claude --plugin-dir ./token-weather

modはプラグインなので、同じ方法で配布する。.claude-plugin/marketplace.jsonを置いたフォルダがあればマーケットプレイスとして機能し、GitHubリポジトリに置けばそのリポジトリがマーケットプレイスになり、通常のプッシュで更新できる。導入はClaude Codeの中で、/plugin marketplace add your-org/my-mods、/plugin install token-weather@my-mods、/reload-pluginsの3つのコマンドで行う。modはリロード時に始動し、現れなければClaude Codeを再起動する。modを含むプラグインは、Claude directory(claude.ai/directory/manage)へ提出することもできる。

セキュリティについて、原文の中心となる一文は1つである。modは自分のマシン上のClaude Codeの中で、Claude Codeと同じアクセス権で動作するコードであり、書いたのはAnthropicではなく公開者なので、「install mods the way you'd install a package: read the repo first and only install from people you trust」とある。この文の周辺で、原文から確認できる事実は次の通りである。

  • modが持つアクセス範囲は、Claude Codeが持つものと同じである。
  • modの作者は公開者でありAnthropicではない。そのため先にリポジトリを読み、信頼できる人のものだけを入れる。
  • コマンドを実行するまでは何もインストールされない。
  • モジュールはDOMもNodeもないサンドボックスで動作し、外部とのあらゆる接点は$を経由する。原文はこのサンドボックスを権限の分離とは説明していない。
  • フックは1回の呼び出しにつき自分の時間として10秒を与えられ、$呼び出しの中で待つ時間は数えられない。

原文の事例も同じ方向を向いている。Blast Radiusは安全網であって権限システムではないため、確実に止めたいなら権限ルールを使うよう述べている。

  • Claude Code 2.1.286以前でmodを読み込んだときのエラーメッセージや代替動作。
  • $.stateの値が、セッション終了後の再開(resume)時に復元されるか否か(原文はリロードを経て残るとだけ説明している)。
  • ターミナルとデスクトップアプリ以外の、VS Code拡張などの描画先で使える$.uiコンポーネントの全一覧。
  • claude.ai/directory/manageへmodを提出した際の審査基準。
  • フック内部で生成した非同期タイマーやバックグラウンド処理が、セッション終了時にどう後始末されるか。
