Claude Code 该选哪些 MCP 服务器 - 不看清单,看六条判断轴

你得到什么,又交出什么 - 用传输、作用域、权限、信任与上下文代价来决定

2026-08-06 IT/技术

引言:推荐清单半年就过期

给 Claude Code 接一台 MCP 服务器,只需要一行命令。难的从来不是接,而是选。

MCP 服务器的推荐清单早已泛滥:分类盘点文、awesome 列表、官方目录,应有尽有。可清单是有保质期的。早期的参考实现服务器中已有相当一部分被迁进了单独的归档仓库,当年几乎每篇教程都会提到的 @modelcontextprotocol/server-github 包也在其中。照着半年前的清单逐条照搬,等于把无人维护的代码种进自己的开发环境。

比清单更耐用的是标准。而在 MCP 这件事上,标准之所以格外重要,还有第二个理由:接一台 MCP 服务器,不是打开一个便利功能,而是交出一次访问授权。文件系统服务器把磁盘拉进智能体的射程,数据库服务器拉进的是数据,工单系统服务器拉进的是内部工单全文。选错的服务器不是慢,而是危险。

所以本文用六条判断轴取代清单:①到底有没有理由接;②用哪种传输方式接;③写进哪个作用域;④这台服务器让你交出什么;⑤你凭什么信任它;⑥接上之后它吃掉多少上下文。每条轴上有哪些选项、各自付出什么代价,逐一说清。这不是一篇给特定服务器盖安全章的文章,而是一篇让读者能自己判定自己那台服务器的文章。

1. 先判断有没有理由接 - 复制粘贴次数这个朴素信号

1.1 该接的时候

官方文档给出的信号朴素得出人意料:当你发现自己在把另一个工具里的内容复制粘贴进会话窗口时,就是该接的时候。工单正文、监控面板的堆栈跟踪、查询结果表格——这些东西你若在反复搬运,那个系统就是候选。接上之后,智能体不再等你粘贴,而是自己去读、自己动手。

1.2 不该接的时候

把判断反过来会更清楚:你从不复制内容的系统,就没有理由接。

  • 一个月才打开一两次的系统:配置、认证与维护成本高过收益
  • 现有命令行工具已能覆盖的系统:在一行 shell 命令上再叠一层协议,收获有限
  • 每次搬运的内容都一样:那该固定进项目文档,而不是接一台服务器
  • 只需要读,服务器却把写入类工具一并带来:多余的权限跟着进门
  • 需要新签发凭据,却没有办法把这份凭据的范围收窄

1.3 筛掉候选的五句话

  • 过去两周里,你从那个系统搬进会话的内容有五次以上吗?
  • 每次搬的内容都不一样吗?
  • 智能体需要往那个系统写入,还是只读就够?
  • 这台服务器索要的凭据能不能收成只读?
  • 接上再拆掉的成本低吗?低的话,先接上观察再决定也是合理做法

2. MCP 到底标准化了什么 - 不懂规范就选不好

2.1 这套协议的坐标

MCP 是把 AI 应用连接到外部系统的开放标准,常被比作 AI 应用的 USB-C 接口。服务器端把自己能做的事以标准形态暴露出来,任何理解这套形态的客户端都能直接接入,不需要定制的集成代码。Claude Code 与其他多款编辑器、智能体共享同一批服务器。这种互通性是下面所有取舍的前提——它意味着你今天选的服务器不会被焊死在某一个工具上。

2.2 怎么读版本号

MCP 规范用 YYYY-MM-DD 形式的日期字符串标注版本,而这个日期有其特定含义:它指的是最后一次做出破坏向后兼容变更的日期。保持向后兼容的改进不会让版本号前进。当前规范版本是 2026-07-28。如果某台服务器的文档里写的支持版本还停留在远早于此的日期,那就可以读作一个信号:它没有跟上此后的兼容性断裂。

2.3 引入版本协商之后的变化

每个请求都通过 _meta 字段里的 io.modelcontextprotocol/protocolVersion 键声明所用版本,服务器按请求逐个接受或拒绝。在 Streamable HTTP 上,同一个值还会随 MCP-Protocol-Version 请求头一起发送。若服务器不支持所请求的版本,它会返回一个列出自身所支持版本的错误,客户端据此重试。想事先敲定的客户端可以调用一次 server/discover,一并拿到支持的版本、能力与身份。实务上更值得注意的是:规范明确写出了与仍在使用旧握手式版本(2025-11-25 及更早)的服务器之间的兼容路径。老服务器不会一夜之间不可用,但越是无人维护的服务器,越会先在这条边界上出问题。

3. 四种传输方式该走哪一条

3.1 岔路其实只有一个

传输方式的选择归根结底落在服务器代码是跑在你的机器上,还是跑在别人那里。这一个差别就改写了整套信任模型。作为本地进程运行的服务器直接沿用你账号的权限;远程服务器则让你的凭据经过你并不运维的基础设施。

传输方式运行位置认证选它的理由注意事项
stdio你机器上的本地进程环境变量与配置文件文件、本地工具、自己写的脚本以你的账号权限运行。包的来源即执行权限
HTTP(streamable-http)远程服务OAuth 2.0 或请求头令牌云端 SaaS 集成的默认选择,支持面最广JSON 配置里漏掉 type,条目会被当成 stdio 而失败
SSE远程服务OAuth 或请求头仅适用于目前只暴露 SSE 的服务已不推荐的传输方式,有 HTTP 就走 HTTP
WebSocket远程服务仅请求头服务器会主动推送事件的场景不能用 OAuth,列表命令里也看不到它

3.2 真正要敲的命令

远程 HTTP 服务器只需要名字和地址。

claude mcp add --transport http <名称> <地址>

本地 stdio 服务器把运行命令写在 -- 之后。这个双横线很关键:它是分隔符,让客户端不去把后面的参数当成自己的选项,而是原样传给服务器。

claude mcp add --transport stdio <名称> -- npx -y <包名>

添加后,claude mcp list 看状态,claude mcp get <名称> 看详情,claude mcp remove <名称> 移除。会话内的 /mcp 面板会把连接状态、工具数量和待认证项放在同一屏。添加命令并不校验凭据,所以填错了值照样添加成功,只在连接阶段才失败。不要把添加成功当成连接成功,这是第一个实务陷阱。

4. 三种作用域 - 写在哪里,决定了谁持有这份权限

4.1 三者的真实差别

作用域加载范围团队共享适合的场景风险点
local(默认)仅添加它的那个项目,仅你自己否个人实验、带凭据的服务器队友不明白为什么只有你的环境能用
project该项目的所有人是,经由版本控制团队公共工具、可复现的开发环境你授予的权限变成全团队持有
user你的所有项目否随处要用的个人小工具无关的项目里那台服务器也一直活着

4.2 project 作用域藏起来的那个决定

project 作用域写进仓库根目录的 .mcp.json,随仓库一起分发。好处很直白:克隆下来的人自动获得同一套工具。可把同一句话翻到权限那一面,读起来就变了:你选的服务器,将在每一位队友的机器上运行。正因如此,项目作用域的服务器被设计成首次使用前需要批准,并且另有一条命令用来重置这些批准选择。一个克隆下来的仓库无法替你批准自己的服务器,也是同一个道理。

4.3 优先级,以及不会合并这件事

同名服务器定义在多处时,只有一个能存活。顺序是 local → project → user → 插件提供的服务器 → 连接器。容易被忽略的是后半条规则:字段不会合并。优先级高的那一份定义会被整体采用。在 user 作用域放好请求头、指望 project 作用域只覆盖地址,这种预期不成立。另外,三种作用域按名称判定重复,而插件与连接器按端点判定。

4.4 不把凭据带进仓库的做法

用于共享的 .mcp.json 要使用环境变量展开。${VAR} 展开为变量值,${VAR:-默认值} 在变量未设置时回落到默认值。可展开的位置是 command、args、env,以及远程服务器的 url 和 headers。若引用的变量未设置又没有默认值,配置不会整个崩掉:会给出一条警告,并把原文原样保留。写明默认值,才能避免在无声中用错误的值连上去。

{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": { "Authorization": "Bearer ${API_KEY}" }
    }
  }
}

5. 各类服务器交出去的是什么 - 一张按权限画的地图

5.1 把同一张表改写成暴露面

分类推荐通常按「什么变方便了」来写。把同一张表按什么被暴露了重写一遍,选择就会变。

git 与代码托管读取议题与 PR、评审、创建携带仓库权限的令牌令牌范围内所有仓库都可被提交或建议题按仓库签发细粒度令牌,以读为主

5.2 浏览器一类是另一个问题

浏览器控制那一行是这张表里最特殊的格子。其他服务器打开的是某一个具体系统,而浏览器打开的是它里面所有已登录的服务。浏览器厂商在自己推出 MCP 服务器时开始加入仅本地运行、阻断个人数据访问之类的设计,正是因为这种特殊性。想把这一类深挖一层,可以看Safari MCP 服务器分析,那里单独梳理了各厂商的设计差异与信任边界的争点。

5.3 数据库那一格里的官方建议

官方文档有一处在示例里把原则直接说了出来:接数据库服务器时,连接串中要用只读账号。理由也讲得明白——好让智能体执行的查询无法改动数据。这一句压缩了本文的全部原则。选服务器不是在问「能不能信任它」,而是在做「即便信任崩塌,损害也被限定」的安排。

6. 信任一台服务器的依据 - 八个质量信号

6.1 出现在目录里意味着什么,又不意味着什么

这一点误读很多,需要说准。Anthropic 在把连接器收进自家目录之前会按收录标准审核,但文档里写得很清楚:它不对任何 MCP 服务器做安全审计,也不负责管理。也就是说,进目录只是通过了最低限度的形式审核这一信号,不是安全认证。官方注册表同样是一个元注册表,保存的是元数据和安装命令,真正的产物仍留在 npm、PyPI 这类包注册表里。它会验证命名空间的所有权,但不提供访问控制、审计留痕这类治理能力。

6.2 真正值得看的信号

信号怎么查坏兆头
供应方是否对得上是不是服务运营方自己发布的第三方非官方封装,却起了个看起来官方的名字
维护活力近期提交与发布、议题响应数月停滞,或已迁入归档仓库
跟进规范它声明支持的规范版本停留在明显更早的日期
权限说明是否写清所需范围与令牌权限索要全权限令牌且不作解释
工具表面积工具数量,以及有无破坏性工具号称只读,却附带删除或发送类工具
描述质量描述是否是写给人读的句子描述里混着面向模型的指令
分发形态能否固定到某个具体版本只提供永远拉最新的调用方式
安装路径包名与仓库是否对应名字相近的仿冒包、没有仓库链接

6.3 stdio 服务器要多看的一层

远程服务器跑在别人的基础设施上,而 stdio 服务器跑在你的机器上,用你账号的权限。因此挑 stdio 服务器时会多出一层软件供应链视角:由哪个包管理器获取、版本能否固定、这个包在安装时会执行什么,都是判断材料。永远拉最新版的调用方式很省事,但也意味着上游一变,你机器上运行的代码就悄悄跟着变了。

7. 提示注入与工具投毒 - 这件东西特有的风险

7.1 两种风险,两个防守位置

MCP 服务器承担的风险分成两层,混为一谈就会把防守摆错地方。

  • 提示注入:指令藏在服务器取回的数据里。外部人写的工单正文、抓取的网页、用户提交的日志都是通道。防守位置是怀疑数据。
  • 工具投毒:工具定义本身被污染。恶意指令写进工具描述的元数据,模型会读到那段文字,而用户界面上通常只看得到一个工具名。防守位置是怀疑服务器。

后一类之所以更棘手,恰恰在于它看不见。从不向用户渲染的字符串,照样完整落进模型的输入。这也是在客户端侧漏洞分类中,该类型被指为最普遍、影响最大的原因。

7.2 客户端已经替你挡下的部分

下面是 Claude Code 侧已有的缓解措施。有这些并不构成放心的理由,但知道哪些已被覆盖,可以避免重复投入。

  • 权限默认只读,敏感操作需要明确批准
  • 新的 MCP 服务器与首次打开的代码库要经过信任确认(在非交互的 -p 运行中该确认不生效)
  • 从网络抓取内容的 shell 命令默认不被自动批准
  • 网页抓取使用独立的上下文窗口,减少恶意指令渗进主对话
  • 之前放行过的命令,形态可疑时仍会再次要求批准;未命中规则的命令默认走人工批准

7.3 剩下的那一份

官方文档自己也讲明:这些机制只能降低风险,不构成完全免疫。而剩下的那一份,大半落在人这一侧。不要把不可信内容直接用管道灌进去,批准之前先读一遍被提议的命令,涉及外部服务的活儿放进隔离环境里跑。听着老套,但真正被这三条挡下的事故占比最大。

8. 收到最小权限的实际配置

8.1 在凭据这一层收

这是最外面、也是杠杆最大的一层。在这里收,比任何工具规则都可靠。

  • 数据库连接串围绕只读账号来构造
  • 代码托管令牌签发为只覆盖目标仓库的细粒度令牌
  • 走 OAuth 的服务,请求范围里只保留真正需要的那几项
  • 令牌不写进配置文件,改用环境变量展开来引用
  • 优先选有有效期的凭据——就算忘了它也会自己关上

8.2 用按工具的规则收

MCP 工具的名字形如 mcp__服务器名__工具名,权限规则就写在这些名字上。规则语法里有一处不对称值得记住。

  • 拒绝与询问规则可以在工具名位置使用通配符。mcp__* 表示所有服务器的所有 MCP 工具
  • 允许规则不同。通配符只能出现在字面量前缀 mcp__服务器名__ 之后,服务器那一段不能是通配符
  • mcp__服务器名__* 自动批准该服务器的全部工具,mcp__服务器名__get_* 只批准读取形态的那些
  • 没有锚定的允许通配符(例如一个光秃秃的星号)会被警告并跳过,什么也不会自动批准

实务上真正划算的组合是只允许读取形态的工具,其余留给批准。接了服务器不等于要把它整个打开。把真正在重复的读取动作自动化,往返次数就降下来了,而暴露面没有跟着涨。

8.3 在暴露面这一层收

对文件访问类服务器,值得确认它是否尊重客户端告知的工作根目录。规范里有一种请求,服务器可借此询问并把自己限制在允许范围内;Claude Code 会以会话的启动目录加上用户额外授予的目录列表作答,而当这个集合变化时还会发出变更通知。实现了这套流程的服务器,只看得到用户打开的那部分;没实现的服务器,则是它知道多少就看多少。这个区别,是要在服务器文档里逐条核对的。

8.4 批准本身就是目的的工具

服务器作者一侧也有一个机制。把工具的元数据标记为必须由用户交互,该工具即使在自动批准的权限模式下也会每次弹出批准界面,并且不提供「下次不再询问」的选项,允许规则同样绕不过去。它是为授予访问权这类操作而设的——若被自动批准,就等于从来没有人真正同意过。如果你自己在写服务器,给破坏性工具打上这个标记,是你能交给用户的最诚实的一道保险。

9. 上下文代价与响应延迟 - 接得越多越吃亏的地方

9.1 工具定义占掉的位置

每接一台服务器,它的工具定义和服务器说明就会在模型的输入里占位。服务器越多,留给对话的空间越少。Claude Code 为此默认启用工具搜索:会话开始时只载入工具名和服务器说明,真正的定义等需要时再取。所以多接几台服务器对上下文的冲击并不大。它没有固定的每服务器工具数上限,实际的天花板是你的上下文预算。

9.2 可调的旋钮

  • 工具搜索的行为由环境变量控制,可在预先载入、全部延后、按比例阈值自动判断之间选择
  • 每轮都要用的少数服务器可以用「始终载入」选项设为例外,代价是启动时会短暂等待该服务器连上
  • 工具输出超过一万个 token 会触发警告;默认上限为两万五千个 token,可用环境变量调高
  • 服务器说明与工具描述各自在 2KB 处被截断,写服务器就该把要点放在前面
  • 工具调用另有按服务器的时限与空闲时限,空闲默认远程五分钟、本地三十分钟

9.3 需要定期清理的真正理由

比 token 成本更实际的问题是选错工具。名字相近的工具散落在多台服务器上时,模型伸手去拿错的那一个的概率就升高。把三个月前试过一次就搁着的、实验到一半停下的、以及已经不用的服务对应的那台服务器摘掉,既是安全动作,也是准确性动作。打开列表,把最近三十天内实际没被调用过的挑出来,这样的定期巡检就够了。

10. 什么时候不该接,以及替代手段

10.1 MCP 不是答案的场景

并非所有集成都得是服务器。下面这些情况,别的手段更便宜。

  • 已经有好用命令行工具的系统:在一行 shell 命令上再叠协议层,只会增加故障点
  • 步骤固定的重复工作:固化进项目文档或脚本,比每次用自然语言复述更可复现
  • 一次性查询:接上再拆掉的成本高过那一次查询
  • 凭据无法收窄的服务:只能签发全权限令牌的话,暴露面就不可控
  • 输出过大的数据源:每次调用都撞上限,最后还得由人来裁剪

10.2 正式接入前可以先试的事

  • 先用 local 作用域接上用两周,看实际调用频次再决定要不要升到 project 作用域
  • 只把读取类工具设为自动批准,写入留给人工批准,然后观察
  • 先用预发布或只读副本的凭据接,不要一上来就用生产凭据
  • 把工具清单通读一遍,先从名字上认出哪些是破坏性工具
  • 故意让服务器失败一次,看看它的报错长什么样——认证失败与连接失败的处理方式不同

11. 未能确认的部分

把本文因依据不足而没有下断言的条目集中列在这里。

  • 对单个服务器的安全性判定:本文不认定任何第三方服务器是安全的。公开的独立安全审计结果未能确认
  • 工具搜索的实际节省幅度:默认启用这一行为已在文档中确认,但能量化服务器数量与 token 节省关系的公开基准数据未能确认
  • 工具投毒的实际损失规模:有研究指出该风险类型及其普遍性,但统计事故数量或损失规模的可靠公开数据未能确认
  • 各服务器的采用率排名:以下载量或安装量为准的可靠最新榜单未能确认。因此本文没有人气排名
  • 原推荐文中的完整服务器清单:引发本文的那篇文章中的分类与注意事项已确认,但各分类下逐一列出的服务器完整清单未能确认
  • 注册表策略的后续变化:官方注册表是否计划增加治理功能,未能确认

常见问题(FAQ)

Q1. 怎么判断该不该接一台 MCP 服务器?

如果你在反复把另一个工具里的内容复制进会话,那个系统就是候选。反过来,一个月看一两次的系统、现有命令行工具能做的事、内容每次都一样因而可固定进文档的情况,都更适合不接。每接一台服务器,配置、认证、上下文开销和权限暴露都会一并跟来。

Q2. local、project、user 作用域有什么区别?

local 是默认值,只在那个项目里对你自己生效。project 存在仓库的配置文件里由全团队共享,首次使用需经批准。user 在你的所有项目里加载,但仅对你可见。同名冲突时按 local、project、user、插件、连接器的顺序只留一个,且字段不会合并。

Q3. 提示注入和工具投毒有什么不同?

注入是指令藏在服务器取回的数据里,投毒是工具定义本身被污染。前者要你怀疑数据,后者要你怀疑服务器。投毒更麻烦,因为从不向用户渲染的字符串照样完整落进模型的输入。

Q4. 把权限收到最小,实际该怎么做?

分三层收:凭据层用只读账号与细粒度令牌,工具层用指名到具体服务器和工具的规则,暴露层用工作目录限制与环境变量引用。三者之中,凭据层的效果最大。

Q5. 出现在目录或注册表里就等于安全吗?

不等于。按收录标准的审核确实存在,但文档明确写着那不是安全审计。官方注册表也只保存元数据,不提供访问控制、审计留痕这类治理能力。收录是起点,不是结论。

结论 - 今天就能落地的五步

挑 MCP 服务器不是找一份更好清单的问题,而是握住自己标准的问题。清单半年就腐坏,标准会留下来。按今天就能动手的顺序排下来是这样:

  • 第一步——先清点现在接着的。打开列表,把最近没真正用过的标出来。清理既是安全动作,也是准确性动作
  • 第二步——给每台服务器写一句它交出了什么。写不出那一句的服务器,就是你还没弄懂的服务器
  • 第三步——先从凭据开始收。只读账号、细粒度令牌、收窄的 OAuth 范围。在这里收,比用规则收更可靠
  • 第四步——重新挑一遍作用域。把该给全团队的、只该给自己的、只该在这个项目里打开的区分清楚,再各归各位
  • 第五步——新服务器先在 local 作用域试两周。只自动批准读取,观察调用频次,再决定要不要升级

最后要讲清本文没有做的一件事:这里没有任何一条判定说某台服务器是安全的,因为没有哪份清单能替你下这个判定。存在的只是用来判定的那几条轴,而把这些轴放到自己的环境上比一比,终究是接入者自己的分内之事。
