Context - An Interface for Attaching Real-Time Web Search Context to AI Agents

The central limitation of an AI agent built on a large language model (LLM) is that the model was trained on data up to a certain point in time and then frozen. It therefore knows only what existed before its knowledge cutoff, which makes it hard to work with the model on recent events, changing APIs, or fast-moving news. The About page explains what happens next when no search is available: an agent that needs live information usually guesses the URL of a page and fetches it directly, and when the guess is wrong the request returns a 404 Not Found and the agent has to try again.

The Web Search API that Cloudflare introduced in its changelog on October 2, 2026 is available in beta. The changelog describes it as a way for AI agents and applications to search the Internet and ground their responses in live information, instead of guessing URLs or relying on a model's training cutoff. Like a person who starts with a search engine, the agent sends a query and receives a list of relevant, up-to-date results, and the developer injects those results into the model's context so that the response is grounded in live information.

The About page lists the processing order in four steps. First, the request is routed through the AI Gateway that you specify. Second, the query is forwarded to the search provider you choose among Ceramic.ai, Exa, and Linkup, and if you do not set a provider the service uses Ceramic.ai as the default. Third, the provider's response is normalized into a consistent format, with a URL and title for each result and an optional description, image, favicon, and last-modified date. Fourth, the request is recorded in your AI Gateway logs and billed to your account. Four points stand out from this flow, all according to the documentation.

  • First, because Ceramic.ai, Exa, and Linkup are all normalized into the same result format, the documentation says you can switch providers by changing a single parameter.
  • Second, every request goes through AI Gateway, which the documentation describes as the control plane for AI applications, so search requests appear in gateway logs and analytics alongside model inference requests.
  • Third, under Unified Billing the searches draw down from your AI Gateway credit balance at each provider's list API price, with no additional markup.
  • Fourth, the three providers have committed to Cloudflare's verified bot crawling standards, and the About page states that every search result must include a link to the location of the crawled content.

The sections that follow take these points in the same order: the gateway and billing, the providers, the call format, the crawler standards, and the handling of provider keys. Where the changelog and a detail page word the same fact differently, or where a document is silent, the article says so instead of filling the gap with an assumption.

Core Architecture - AI Gateway as a Single Point of Control and Unified Billing

The Web Search API is built on AI Gateway. The How to use page says that both ways of calling it, the REST API from any backend and the AI binding from a Worker, route their requests through an AI Gateway. Every account has a gateway named default, and you can also create a new gateway when you need one. To get started you need a Cloudflare account and an AI Gateway, plus one of two things already in place: AI Gateway credits loaded on your account, or a provider API key stored on your gateway.

The About page summarizes what you get because every search request goes through a gateway, in four points.

  • Observability: search requests appear in the gateway's logs and analytics alongside your model inference requests.
  • Unified Billing: searches draw down from your AI Gateway credit balance, you pay each provider's list API price, and there is no additional markup. The rates are on the Providers page.
  • Bring your own key (BYOK): if you already have an account with a search provider, you can store your provider API key on your gateway, and the provider then bills you directly.
  • Access control: you control which providers your gateway can use and who can send requests.

The Providers page restates the same point as a billing rule. When you pay with AI Gateway credits, each search is billed at the provider's list API price with no additional markup, and if you bring your own key, the provider bills you directly under your own agreement with them.

The gist of the documentation is that the record and the bill for every search call gather in one place, the gateway. How access control is configured, and which fields of a request are kept in the gateway logs, is not explained in these documents. What the documents do confirm is that model inference costs and search costs can be viewed against the same credit balance.

Comparison of Three Search Providers and Zero Data Retention Entries

At the launch of the beta, developers can select from three integrated search providers: Ceramic.ai, Exa, and Linkup. Passing the corresponding string in the provider parameter instantly routes the query to that engine, while omitting the parameter causes the gateway to select Ceramic.ai as the default vendor. The three suppliers differ across index breadth, search approach, the kind of excerpt each result carries, and price, and the Providers page lists each of those properties for every provider. Because the choice is a single string in the request, the cost of trying a different provider is small, but the data retention entry and the per-request price both change with that choice, so they deserve a look before the string is changed.

The following table summarizes the documented technical characteristics and official pricing for each supported provider as detailed in the official developer documentation.

Provider Identifier Web Index and Search Strategy Result Excerpt Format Zero Data Retention Documented Status Official Price per 1,000 Requests
ceramic (default) Independent web index of over 40 billion pages optimized for AI workloads Detailed descriptive summaries spanning up to 8,000 characters Yes (Supported) $0.25 ($0.00025 per request)
exa Hybrid keyword and semantic embedding search utilizing the auto search mode Highly relevant contextual highlights extracted from matched pages No (Listed as No in provider table) $7.00 ($0.007 per request)
linkup Fast search depth returning raw, unsynthesized results from trusted sources Citing source links and text snippets without generated answer synthesis Yes (Supported) $5.00 ($0.005 per request)

Here the official documents disagree. The changelog post dated October 2, 2026 says in its running text that all three providers support Zero Data Retention for requests made through Cloudflare. However, the property table on the Providers page, updated the same day, lists the Zero Data Retention value for Exa as No, while Ceramic.ai and Linkup match as Yes in the table as well. No later correction that resolves which statement is accurate was found, so an environment in which search queries must not remain on a provider's servers can take the table value as its reference and set provider explicitly to Ceramic.ai or Linkup, which is the choice that stays consistent with both documents. Ceramic.ai and Linkup carry Yes in the changelog and in the table alike, so the pin does not depend on which of the two documents is later corrected.

The Providers page introduces each provider as follows. Every statement about what a provider suits is wording that the documentation itself attaches to that provider.

  • Ceramic.ai: it runs its own independent web index of more than 40 billion pages, designed for AI agents and LLM applications, and it focuses on low-latency, low-cost search. The documentation calls it a good fit for agents that run many searches per task, for grounding chatbot answers in current information, and for checking model output against live web sources. Results include long descriptions of each page, up to 8,000 characters, and the price is $0.25 per 1,000 requests.
  • Exa: it is a search engine built for AI, with its own index that combines traditional keyword search with embeddings-based search. Requests use Exa's auto search type, a balanced mode optimized for both result quality and speed, and each result includes highlights, the text snippets most relevant to your query, returned as the result description. The documentation calls Exa a good fit when you want to pass concise, query-relevant excerpts straight into a model's context, and the price is $7.00 per 1,000 requests.
  • Linkup: it provides web search built for AI applications, returning sourced results with text snippets from across the web. Requests use Linkup's fast search depth with raw search results, so no answer is generated. The documentation calls it a good fit for agent tool calls that need quick, cited results from trusted sources, and the price is $5.00 per 1,000 requests.
  • Result format: the About page says every provider returns the same result format, a URL and title plus an optional description, image, favicon, and last-modified date, so a single change of the provider value is enough to switch. Because the description is optional, it is safer not to assume that every provider always fills it in.

The Providers page also gives each provider its own property table, with the provider value, the Zero Data Retention status, and the price, together with links to the provider's own documentation and terms. Terms and data handling are set by the providers themselves, so before a real deployment the terms page of each provider should be opened separately. The table for Exa additionally records the search mode, the auto search type with page highlights returned as the result description, and the table for Linkup records the fast search depth, which matches the request settings described above.

Calling Interfaces - Specifications for REST API and Workers AI Binding

Cloudflare delivers two execution pathways: an authenticated REST API for arbitrary backend environments and an integrated Workers AI runtime binding for serverless applications executing at the network edge. The How to use page puts it as calling the Web Search API from any backend with the REST API, or from a Worker with the AI binding, and it states that both methods route requests through an AI Gateway, so the gateway ID is part of every call whichever pathway is chosen.

The REST API receives requests at the endpoint POST https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/websearch/. Authentication uses a Cloudflare API token that has both of two permissions, the account-level Workers AI > Read and AI Gateway > Read. The page presents these as the permissions the token needs to have, and it names no other scope for the endpoint.

The REST invocation example provided in the official documentation is reproduced below. It sends the query about fun things to do in Salt Lake City as fall approaches to the ceramic provider, asks for 5 results, and names the default gateway in the options object.

curl https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/ai/websearch/ \
                      --request POST \
                      --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
                      --header "Content-Type: application/json" \
                      --data '{
                        "query": "What are some fun things to do in Salt Lake City as fall approaches?",
                        "provider": "ceramic",
                        "limit": 5,
                        "options": { "gateway": { "id": "default" } }
                      }'

In a Workers environment you add an AI binding (ai: { binding: "AI" }) to the Wrangler configuration file and then pass the gateway ID and the query to env.AI.websearch(). The configuration example in the documentation sets compatibility_date to 2026-10-05 and carries a comment telling you to set that value to the current date. websearch() returns a standard Response object, so you read the results with response.json().

export default {
                    	async fetch(request, env): Promise<Response> {
                    		const response = await env.AI.websearch({
                    			gatewayId: "default",
                    			query: "What are some fun things to do in Salt Lake City as fall approaches?",
                    			provider: "exa",
                    			limit: 5,
                    		});
                    
                    		const results = await response.json();
                    		return Response.json(results);
                    	},
                    } satisfies ExportedHandler<Env>;

The request parameters that the documentation lists are as follows. In a REST body the gateway goes into the options object, and in a Worker call it goes into gatewayId.

  • query (required, string): the search query, with a minLength of 1 and a maxLength of 1,024.
  • provider (optional, string): one of ceramic, exa, or linkup, with ceramic as the default.
  • limit (optional, integer): the maximum number of search results to return, with a minimum of 1, a maximum of 10, and a default of 10. The limit on results for a single request is 10.
  • options.gateway.id (REST, required) or gatewayId (Worker, required): the ID of the AI Gateway through which the request is routed. When you use the default gateway, specify default.
  • byokAlias (optional, string): the alias of a provider API key stored on your gateway, matching the pattern ^[A-Za-z0-9_-]{1,64}$. If you set it and that key is not configured, the request fails instead of falling back to AI Gateway credits.

Successful invocations yield a uniform JSON payload housing an array of item records alongside request metadata. The Worker example above selects the exa provider, asks for 5 results, and returns the parsed JSON to the caller, while the response format section of the documentation shows a single item with a url, a title, and a description, and a metadata object whose latencyMs is 612 in the example.

{
                      "items": [
                        {
                          "url": "https://example.com/salt-lake-city-fall-guide",
                          "title": "Fall in Salt Lake City: A Local's Guide",
                          "description": "From scenic drives up Big Cottonwood Canyon to pumpkin patches..."
                        }
                      ],
                      "metadata": {
                        "query": "What are some fun things to do in Salt Lake City as fall approaches?",
                        "requestId": "<REQUEST_ID>",
                        "latencyMs": 612
                      }
                    }

The response body has the same shape for every provider, an items array and a metadata object holding query, requestId, and latencyMs. A result item always carries url and title, while the description, image, favicon, and last-modified date are included only when the provider returns them, and the response format section of the documentation says the same about optional fields.

The How to use page also includes an example of using search as a model tool. A web_search function tool is defined for the model, and when the model calls that tool the code runs the search with websearch() and hands the results back to the model as a message with the tool role. The example calls a Workers AI model and caps the search at 5 results. The limits that the documentation lists are only two, a query length of 1,024 characters and 10 results per request.

Crawler Standards and Source Attribution - The Standards Providers Have Committed To

The Crawler standards section of the About page begins with Cloudflare's own position. Crawlers should be honest and transparent and should respect the rules and preferences that site owners set, and site owners should have meaningful visibility into and control over how their content is used.

The page then states that every Web Search API provider has committed to meet the following standards.

  • Verified bot compliance: the crawler a provider uses must meet Cloudflare's published requirements for verified bots, and those requirements include identifying the crawler and respecting robots.txt.
  • Source attribution: every search result must include a link to the location of the crawled content.
  • The purpose the page summarizes in its closing: when you use the API, your agents consume search results from operators that give site owners transparency, control, and visibility over how their content is crawled.

That is everything the documents say directly. How the commitments are actually checked, and how a site operator identifies and controls the crawler of an individual provider, is not covered in these documents. Reporting the commitment that the changelog describes and the two standards of the About page, without going further, is the scope of this section.

Bring Your Own Key (BYOK) Operations and Secrets Management

According to the How to use page, a developer who already has an account with a search provider can use that provider's API key instead of AI Gateway credits, and the provider then bills the developer directly. The procedure and the rules for choosing a key are as follows.

  • Dashboard registration: in the Cloudflare dashboard, go to the AI Gateway page, select your gateway, and select Provider Keys. Add an API key for Ceramic.ai, Exa, or Linkup and assign it an alias, for example default. If the provider is not listed, select Configure custom providers to add it.
  • Key storage: your API key is never sent in the request. AI Gateway retrieves the key stored on the gateway for the provider and alias, and the stored keys are encrypted with Secrets Store.
  • When an alias is set: if you pass byokAlias, AI Gateway uses the stored key with that alias. If the provider or alias is not configured on the gateway, the request fails with a 400 error instead of falling back to your credits.
  • When the alias is omitted: if the gateway has a stored key with the default alias for the provider, AI Gateway uses that key, and otherwise the search is billed to your AI Gateway credits.

The BYOK example in the documentation is a request with the query What is Cloudflare Workers?, with provider set to exa and byokAlias set to default. The call has the same shape as the credit-based one, plus a single byokAlias line. For further detail on how keys are stored, the How to use page points to the Bring your own keys documentation of AI Gateway.

Comparison Between Documented Statements and Unverified Points

Before relying on any service, it helps to separate what the vendor documentation says from what it leaves unstated. The table below places the specifications stated in the Changelog, About, Providers, and How to use pages next to the points that these pages do not settle, so that a gap in the documents is not mistaken for a guarantee in either direction.

Specification Area Explicitly Documented Statements Unverified Items and Caveats
Data Retention Policy Ceramic.ai and Linkup explicitly list Zero Data Retention as Yes The changelog claims all three support it, yet Exa is marked No in the provider table
Pricing and Markups Charges are deducted from gateway credits at vendor list rates with zero markup Free credit allocations and minimum balance recharge increments are omitted from documentation
Parameter Constraints States a query length of 1 to 1,024 characters and a limit of 1 to 10 results, default 10 Global rate limit thresholds per minute or per day across accounts are not documented
Supported Interfaces REST API endpoint and the Worker AI binding, plus a model tool-calling example Third-party framework connectors such as LangChain, LlamaIndex, or MCP could not be found in these documents

Before deploying mission-critical autonomous workloads against the Web Search API beta, development teams must incorporate the following operational considerations:

  • Because the documentation lists no rate limit per minute or per day and states only the two limits above, a high-concurrency system should confirm its behavior under load before relying on it and should plan retry and backoff handling on its own side.
  • The documented ceiling of 10 results per request means that a task which needs more documents has to issue several queries, and each search is billed as a request at the provider price shown in the Providers table.
  • Due to the documented No status for Exa's Zero Data Retention in the provider table, systems processing sensitive enterprise data should strictly pin requests to Ceramic.ai or Linkup.
  • Local development behavior under wrangler dev is unspecified in the pages that were read, meaning developers should confirm whether local binding calls incur live gateway credit charges or support offline mocks.

What could not be confirmed

  • The true resolution of the contradiction between the changelog claim of universal Zero Data Retention and the Providers table marking Exa as No. No correction or clarification of either statement was found in the pages that were read.
  • Account-level rate limits and concurrency thresholds per minute across Free, Workers Paid, and Enterprise plan tiers. The Limits table of the How to use page lists only query length and results per request.
  • Whether Cloudflare provides a trial quota of free searches upon activating an AI Gateway before credit deduction begins.
  • The exact User-Agent header strings and IP CIDR ranges employed by the underlying provider crawlers when indexing target sites.
  • Whether local Workers execution via wrangler dev mocks search responses or invokes live chargeable API Gateway endpoints.
