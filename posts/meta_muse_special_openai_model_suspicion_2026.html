본 분석은 2026년 9월 25일 피터 제임스(Peter James)가 공개한 가상머신 로그 분석 보고서에 기반한다. 저자는 이전에도 Muse 시스템을 분석한 바 있다. 본문은 공개된 세션 로그와 바이너리 문자열에 기록된 기술적 사실을 중심으로 구성되었으며, 외부 모델 호출에 관한 해석은 저자가 명시적으로 밝힌 정황 증거 및 추론에 근거한다. 특정 기업이나 모델에 대한 주관적 평가는 배제하고 공개된 런타임 아키텍처의 설계적 사실만을 정리한다.

1. 가상머신 세션 로그에서 관찰된 단 하나의 이례적 모델

인공지능 코딩 에이전트 시스템이 사용자의 요청을 받아 소프트웨어를 구축하는 과정에서 어떤 언어 모델을 호출하는가는 시스템의 핵심 아키텍처를 결정하는 중요한 요소다. 일반적으로 대규모 서비스를 지탱하는 에이전트는 다양한 작업 복잡도에 대응하기 위해 내부 라우팅 계층을 운용한다. 메타가 공개한 코딩 에이전트 서비스 Muse는 독자적인 모델 기술을 바탕으로 개발 환경을 자동화하는 플랫폼으로 주목을 받았다. 원문은 저자 피터 제임스가 Muse를 활용해 웹사이트를 제작하던 도중 가상머신 세션 로그를 분석한 기술적 기록을 다룬다.

원문은 저자가 가상머신에 남겨진 에이전트 세션 기록들을 집계한 결과, 거의 모든 세션이 메타의 자체 개발 모델인 아보카도(Avocado)로 라우팅되어 동작하고 있었다고 적는다. 세션 로그 파일들은 에이전트의 대화 내역, 도구 호출, 시스템 프롬프트 등을 상세히 기록하고 있었으며, 대다수의 로그는 일관되게 아보카도 계열의 세부 모델 식별자를 가리키고 있었다.

그러나 전체 세션 로그 중에서 단 하나의 서브에이전트 세션이 완전히 다른 모델 이름을 기록하고 있는 현상이 포착되었다. 원문은 2026년 9월 21일에 실행된 특정 서브에이전트 로그에서 모델 식별자가 azure/muse-special로 기록되어 있었다고 보고한다. 다른 모든 세션이 아보카도 단일 모델 군으로 균일하게 유지되던 환경에서, 외부 클라우드 플랫폼의 경로 형식을 띤 특이한 식별자가 단 한 차례 등장한 것이다. 원문은 저자가 약 5분 분량의 글을 통해 이 특이 세션의 내부 트랜스크립트를 추적하게 된 배경을 이렇게 설명한다.

이 글의 해석으로는, 단 한 번의 호출이라 할지라도 런타임 내부에 azure/muse-special이라는 식별자가 실재하고 실제 작업에 관여했다는 사실은 중요한 기술적 의미를 지닌다. 이는 Muse 에이전트 프레임워크가 순수한 단일 자체 모델에만 고정된 것이 아니라, 조건이나 서버 측 제어에 따라 외부 클라우드 엔드포인트로 작업을 연결할 수 있는 다중 모델 라우팅 체계를 갖추고 있음을 보여주는 실질적 단서이기 때문이다.

2. 서명 체계와 도구 호출 식별자가 가리키는 정황 증거

소프트웨어 아키텍처 역공학이나 런타임 로그 분석에서 호출 대상의 정체를 파악하는 확실한 방법은 프로토콜 수준의 서명 체계와 고유 식별자 생성 규칙을 검증하는 것이다. 일반적으로 대형 언어 모델 공급자들은 각자의 규격에 따라 고유한 응답 서명 형식과 난수 식별자 형식을 유지한다. 원문은 저자가 Cursor 도구를 사용해 Muse 에이전트 저장소 소스코드를 검색하던 중 주목할 만한 설정 주석을 발견했다고 기술한다.

원문에 따르면 코드베이스 내부에서 GPT Responses model client via MAGI native Azure OpenAI lane이라는 설명 문자열이 검색되었다. 이는 마이크로소프트 Azure 클라우드 환경에서 호스팅되는 OpenAI 모델 전용 전송 경로를 직접 언급하고 있는 명시적 단서였다. 더 나아가 런타임 데몬의 모델 카탈로그 목록에서는 azure/muse-special 바로 다음 항목으로 azure/gpt-5.6-sol이라는 명칭이 나란히 등재되어 있는 구조가 확인되었다.

이러한 정황은 실제 세션 트랜스크립트의 세부 필드를 열람했을 때 더욱 구체적인 기술적 증거로 뒷받침되었다. 원문은 문제의 특이 세션 로그에서 두 가지 핵심적인 차이점이 관찰되었다고 밝힌다. 첫째, 응답 서명 태그에 gpt_responses_v1이라는 명칭이 부여되어 있었으며, 그 내부 페이로드는 gAAAAA로 시작하는 암호화된 문자열 형태로 채워져 있었다. 원문은 gAAAAA로 시작하는 이 페이로드 형식이 OpenAI가 내부 추론 및 응답 검증에 널리 사용하는 전형적인 서명 특성이라고 지적한다.

둘째, 에이전트가 외부 도구를 실행할 때 생성하는 고유 식별자(Tool Call ID)의 형식에서도 명확한 차이가 드러났다. 원문에 따르면 azure/muse-special 세션의 도구 호출 식별자는 접두사 call_ 뒤에 24자리의 영문 대소문자 및 숫자가 혼합된 문자열로 구성되어 있었다. 반면 가상머신 내의 다른 모든 일반 아보카도 세션에서는 동일한 call_ 접두사 뒤에 정확히 32자리의 16진수 문자열이 이어지는 규칙을 따르고 있었다.

이 글의 해석으로는, 도구 호출 식별자의 문자열 길이와 문자 집합 규칙은 클라이언트가 임의로 조작하기 어려운 백엔드 인프라의 고유 지문에 해당한다. 24자리의 영숫자 혼합 문자열은 OpenAI의 함수 호출 엔진이 생성하는 표준적인 식별자 포맷과 일치하며, 32자리 16진수는 메타 자체 시스템의 생성 규칙을 반영한다. 이러한 식별자 포맷의 불일치는 서로 다른 생성 엔진이 해당 세션의 백엔드에서 실제로 연산을 수행했음을 시사하는 강력한 정황 증거다. 원문은 저자가 이러한 기술적 단서들을 바탕으로 muse-special 모델이 Azure 환경을 경유하여 제공되는 OpenAI 모델일 가능성이 높다는 판단에 도달했다고 설명한다.

3. 아보카도와 muse-special의 기술적 차이점 비교

아보카도와 muse-special 세션 사이의 차이는 단순히 모델 이름이나 식별자 형식에 그치지 않고, 런타임 데이터 처리 파이프라인 전반에 걸쳐 심층적인 구조적 분리를 보여준다. 일반적으로 엔터프라이즈 환경에서 외부 상용 API를 연동할 때는 프라이버시와 학습 데이터 분리 등의 기술적 요구사항을 충족하기 위해 엄격한 데이터 차단 장치를 마련한다. Muse 시스템 역시 내부 모델과 외부 연계 모델 사이에 명확한 경계선을 설정해 두고 있었다.

아래 표는 원문에 기술된 가상머신 로그 분석 결과와 런타임 바이너리 설정을 바탕으로 아보카도 모델 세션과 muse-special 모델 세션 사이의 핵심적인 기술적 차이점을 정리한 것이다.

원문은 위와 같은 차이점이 드러내는 가장 중요한 구조적 특징으로 추론 데이터의 보관 방식을 꼽는다. 아보카도 모델의 경우 에이전트의 중간 사고 과정이 트랜스크립트에 여과 없이 평문 텍스트로 보존된다. 이는 사용자가 사전에 명시적으로 동의를 해제하지 않는 한, 메타의 인공지능 개발 및 강화학습 파이프라인에서 활용될 수 있는 일반적인 자사 데이터 처리 방식과 일치한다.

반면 muse-special 세션에서는 원시적인 연쇄 사고 텍스트가 메타 환경 내부에서 해독되지 않은 채 암호화된 바이너리 블록으로 격리된다. 메타의 데몬은 이 암호화된 블록을 다음 턴의 문맥 유지를 위해 보관했다가 Azure 엔드포인트로 다시 전송하는 중계 역할만을 수행한다. 이 글의 해석으로는, 이러한 기술적 차이는 메타가 외부 모델을 활용하더라도 그 과정에서 생성되는 원시 사고 논리를 자사 모델의 강화학습용 데이터셋으로 전용하지 못하도록 아키텍처 수준에서 격리벽을 구축해 두었음을 명백히 보여준다.

4. 런타임에 포함된 다중 제공업체 모델 카탈로그와 클라이언트

Muse 가상머신 환경의 심층 조사는 azure/muse-special 단일 모델의 존재를 확인하는 데서 멈추지 않았다. 원문은 저자가 에이전트 데몬과 함께 패키징되어 배포된 전체 모델 카탈로그 명세를 분석한 결과, 메타의 자체 모델 외에도 인공지능 업계의 주요 선도 모델들이 폭넓게 망라되어 있었다고 기술한다. 시스템 런타임은 단일 제공업체에 국한되지 않고 다각적인 외부 공급 경로를 지원할 수 있도록 사전 설계되어 있었다.

원문에 따르면 에이전트 데몬에 내장된 모델 카탈로그에는 메타의 자체 아보카도 모델 약 15종의 버전 외에도 다음과 같은 다양한 외부 제공업체 모델 계열이 포함되어 있었다.

  • 메타 내부에서 개량되어 등록된 약 15종의 다양한 아보카도 세부 모델 버전군
  • 앤스로픽(Anthropic) 계열의 최상위 모델인 클로드 오퍼스(Claude Opus) 4.6, 4.7, 4.8 버전
  • 중간 규모 및 고속 처리를 담당하는 클로드 소넷(Sonnet) 4.6 및 클로드 하이쿠(Haiku) 4.5 버전
  • OpenAI 자체 API, Azure 클라우드, Codex 경로를 통해 주소 지정이 가능한 GPT-5.5 및 GPT-5.6 변형 모델군
  • Fireworks 플랫폼 및 메타 자체 호스팅 경로를 통해 연동되도록 구성된 키미(Kimi) K3 모델군

원문은 저장소 내부에서 Rust 언어로 구현된 앤스로픽 전용 클라이언트 파일들이 발견되었다고 적는다. 구체적으로 요청의 흐름을 제어하는 anthropic/request_flow.rs, 에이전트 프롬프트를 변환하는 anthropic/convert_prompt.rs, 그리고 서버 전송 이벤트 스트림을 파싱하는 anthropic/parse_sse_stream.rs 파일이 런타임에 포함되어 있었다.

또한 시스템 환경변수 파일에는 외부 모델 연동을 제어하는 보안 설정들이 배치되어 있었다. 원문에 따르면 OpenAI와 앤스로픽의 API 키 파일들이 시스템 내에 존재하고 있었으며, 이들 파일에 대한 접근 권한은 inference-proxy 서비스로 한정되어 있었다. 아울러 런타임 환경변수에는 JARVIS_ANTHROPIC_BASE_URL_REVPROXY_OVERRIDE=0이라는 설정 항목이 존재했다. 원문은 소스 주석에서 이 설정을 운영 상황에 따라 즉각적으로 외부 역방향 프록시 연동을 제어할 수 있는 실시간 킬스위치로 규정하고 있었다고 기술한다.

이 글의 해석으로는, 런타임 바이너리와 데몬 패키지에 복수의 외부 상용 모델 카탈로그와 통신 파이프라인이 포함되어 있다는 사실 자체가 상시적인 외부 모델 호출을 의미하는 것은 아니다. 그러나 이는 메타 인프라 팀이 자체 아보카도 모델의 성능 한계나 장애 상황에 대응하여 서버 측의 라우팅 결정만으로 즉각 트래픽을 타사 모델로 우회시키거나 하이브리드로 결합할 수 있는 아키텍처적 유연성을 확보해 두었음을 시사한다.

5. 추론 데이터 암호화와 강화학습 활용 제한의 함의

자체 파운데이션 모델을 보유한 거대 기업이 자사 서비스의 서브에이전트에 외부 선도 모델을 투입했다는 정황이 관찰될 때, 인공지능 업계에서 민감하게 대두되는 질문은 지식 증류의 가능성이다. 일반적으로 타사의 고성능 모델 응답이나 사고 과정을 자사 모델의 학습 데이터셋으로 전용하는 행위는 약관 위반 및 지적재산권 분쟁의 쟁점이 된다. 원문은 저자가 기술적 분석을 통해 이 문제에 대해 명확한 질문을 던지고 직접 답변을 제시했다고 기술한다.

원문은 메타가 타사의 최상위 연구소 모델들로부터 지식을 증류하고 있는가라는 질문에 대해 명확하게 "아니다(No)"라고 결론을 내린다. 저자가 가상머신 바이너리와 트랜스크립트 구조를 분석한 결과, 증류를 목적으로 외부 모델을 호출했다는 증거는 발견되지 않았으며 오히려 이를 원천 차단하는 안전장치가 가동되고 있었다.

원문이 제시하는 기술적 근거는 다음과 같이 요약된다.

  • 원시 사고 과정의 암호화 저장: muse-special 모델이 반환하는 상세 추론 데이터는 gAAAAA로 시작하는 암호화 블록으로 보호되어 있으며 런타임 내부에서 이를 복호화하지 않는다.
  • 강화학습 시스템의 유입 차단: 바이너리 내부 명시에 따르면 암호화된 추론 블록은 강화학습 완료 서버 오버라이드를 사용할 수 없도록 명시되어 있으며 서버는 해당 데이터를 거부한다.
  • 제한된 데이터 가시성: 메타 측 데몬이 접근할 수 있는 정보는 최종 텍스트 회신, 호출된 도구의 명칭과 인자, 그리고 외부 제공자가 명시적으로 반환하는 매우 짧은 추론 요약본에 한정된다.
  • 자체 아보카도 모델과의 처리 분리: 메타 자체 모델인 아보카도는 추론 텍스트를 평문으로 직접 기록하여 사용자 동의 하에 강화학습과 모델 고도화에 투입하지만, 외부 모델 데이터는 이 파이프라인에서 기술적으로 배제된다.

원문은 저자가 메타가 OpenAI나 앤스로픽의 모델 가중치를 복제하거나 추출하고 있다는 어떠한 징후도 찾을 수 없었다고 적는다. 암호화된 페이로드는 오직 다중 턴 대화에서 모델이 이전 단계의 추론 상태를 이어받아 일관된 작업을 지속할 수 있도록 클라이언트 측에 상태 토큰 형태로 보관되었다가 다시 전송되는 본래의 API 운영 목적에 충실하게 사용되고 있었다.

이 글의 해석으로는, 이러한 설계는 상용 인공지능 생태계에서 고려된 규정 준수 아키텍처의 표본이다. 메타는 외부 모델의 우수한 실행 능력을 제한적으로 빌려와 에이전트의 완성도를 높이면서도, 계약상의 약관 위반 소지를 사전에 제거하기 위해 추론 데이터의 자사 학습 시스템 유입을 바이너리 수준에서 철저히 격리한 것이다. 데이터는 시스템을 통과하지만 모델의 가중치로 흡수되지는 않는 엄격한 단방향 실행 구조가 확립되어 있었다.

6. 저자가 제시한 분석 내용과 스스로 밝힌 명시적 유보

기술적 사실을 다루는 엔지니어링 분석에서는 관찰된 물리적 데이터와 그로부터 도출된 추론 및 해석을 명확히 구분해야 한다. 특히 단일 인스턴스에서 수집된 로그는 전체 시스템의 보편적 동작을 완벽히 대변하지 못할 가능성이 상존한다. 원문에서 피터 제임스는 자신의 분석 결과가 지닌 기술적 통찰을 제시하면서도, 자신이 확인하지 못한 한계 지점을 솔직하고 명시적으로 유보해 두었다.

아래 표는 원문에 기술된 객관적인 관찰 사실과 저자가 내린 추정, 그리고 저자 스스로 명확히 밝힌 한계 및 유보 사항을 대조하여 정리한 것이다.

원문은 저자가 본인의 분석에 대해 남긴 명시적 유보를 그대로 담고 있다. 저자는 "파일과 로그는 정확히 어느 GPT 모델인지, 혹은 서브에이전트가 왜 이를 선택했는지 알려주지 않는다"고 기록했다. 즉, muse-special이 특정 상용 모델 중 정확히 어떤 변형에 해당하는지, 그리고 해당 서브에이전트가 코딩 작업의 난이도 때문인지 아니면 무작위 분기 때문인지 어떤 알고리즘으로 외부 경로를 탔는지는 로그의 범위를 벗어난 영역이라는 점을 명확히 짚었다.

또한 원문의 결론부에서 저자는 "내 최선의 추측은 muse-special이 Azure를 통해 제공되는 OpenAI 모델이라는 것"이라고 명시하며, 이 주장이 단정적인 사실 선언이 아니라 확인된 정황 증거들에 기반한 합리적 추론이자 가설임을 스스로 규정했다. 아울러 원문에는 메타 측의 공식적인 해명이나 반론 내용은 포함되어 있지 않다.

이 글의 해석으로는, 이와 같은 저자의 신중한 태도는 독자적인 분석 보고서의 신뢰도를 높여주는 중요한 요소다. 관찰된 서명 규격과 식별자 길이라는 단단한 기술적 사실 위에 서 있되, 서버 내부의 의사결정 로직과 미공개 모델 버전에 대해서는 비약을 경계하며 사실과 추론의 경계선을 엄격하게 유지했기 때문이다.

7. 자사 모델 중심 생태계와 하이브리드 라우팅의 기술적 시사점

이번 가상머신 로그 분석 사례는 현대 자율형 인공지능 에이전트 아키텍처가 직면한 실무적인 엔지니어링 과제와 그 해결 방식을 선명하게 보여준다. 일반적으로 독자적인 인공지능 파운데이션 모델을 보유한 거대 기술 기업이라 할지라도, 사용자의 복잡한 실세계 코딩 요구를 충족하기 위해서는 단일 모델의 역량만으로는 한계에 부딪힐 수 있다. 코드 생성, 도구 조합, 계획 수립 등 다양한 하위 태스크마다 최적의 효율을 내는 모델이 다를 수 있기 때문이다.

원문이 보여주는 Muse 시스템의 런타임 설계는 자사 모델 중심의 생태계를 확고히 유지하면서도 실무적 필요에 따라 외부 최고 수준의 모델을 유연하게 결합하는 하이브리드 라우팅의 전형을 보여준다. 대다수의 일반적인 상호작용은 자체 모델인 아보카도로 처리하여 운영 비용을 절감하고 데이터 주권을 유지하되, 특정 서브에이전트의 작업이나 검증 단계에서는 외부 클라우드 모델을 보완재로 동원할 수 있는 인프라적 여지를 열어둔 것이다.

더욱 주목할 점은 클라이언트 환경에 내장된 다중 제공업체 카탈로그와 역방향 프록시 킬스위치 구조다. 사용자 환경에 배포되는 가상머신 런타임에 앤스로픽, OpenAI, 키미 등 다양한 공급자의 통신 클라이언트를 미리 컴파일해 둠으로써, 서비스 운영팀은 클라이언트 업데이트 없이도 서버 측 정책 변경만으로 유연하게 백엔드 라우팅을 조정할 수 있는 통제권을 확보했다.

이 글의 해석으로는, 이러한 아키텍처는 에이전트 시스템 구축에서 단일 모델 의존성을 탈피하고 서비스 복원력을 극대화하기 위한 현대 소프트웨어 공학의 필연적인 귀결이다. 다만 이러한 하이브리드 운영이 신뢰를 얻기 위해서는 데이터 격리와 라이선스 준수가 아키텍처 수준에서 철저히 보장되어야 한다. Muse 로그에서 확인된 암호화 추론 격리와 강화학습 서버 거부 메커니즘은 외부 모델을 차용하면서도 법적·윤리적 위험을 회피하고자 한 엔지니어링적 고심의 흔적으로 평가할 수 있다. 원문은 저자가 최첨단 에이전트 런타임의 내부 파일시스템을 직접 들여다보는 과정에서 기술의 빠른 진보를 체감했다고 소회를 밝히며 글을 맺는다.

8. 확인하지 못한 것

본 글은 공개된 1차 분석 보고서의 사실 관계를 객관적으로 정리하였으나, 로그와 소스코드의 공개 범위 한계로 인해 규명하지 못한 기술적 사항들은 다음과 같다.

  • 저자의 단일 가상머신 테스트 환경 외에 전체 Meta Muse 사용자 환경에서 azure/muse-special 모델이 호출되는 실제 비율이나 발생 빈도는 공개 통계가 없어 확인하지 못했다.
  • 해당 세션에서 실제로 호출된 구체적인 백엔드 모델 명칭은 로그와 설정 파일에 명시되지 않아 확인하지 못했다.
  • 서브에이전트가 자체 아보카도 모델 대신 외부 모델을 선택하도록 결정한 내부 라우팅 알고리즘의 구체적인 판정 기준이나 매개변수는 확인하지 못했다.
  • 런타임 코드베이스에 포함된 Anthropic 관련 Rust 구현체와 킬스위치 설정이 실제 프로덕션 환경에서 활성화되어 호출된 이력이 있는지 여부는 확인하지 못했다.
  • Peter James의 분석 공개 이후 Meta 측이 발표한 공식적인 기술 입장이나 해명 문서는 확정된 사실에 존재하지 않아 확인하지 못했다.
