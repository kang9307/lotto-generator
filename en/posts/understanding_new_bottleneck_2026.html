Understanding Is the New Bottleneck - Why Comprehension, Not Code Generation, Is Now the Constraint

As AI makes writing code cheap, the weight of verification and maintenance shifts to how fast humans can understand

2026-07-15 Dev & Infra

Introduction: The Bottleneck Moved

Until fairly recently, the software bottleneck was obvious: how fast and how much code a team could produce. AI coding tools have all but removed that constraint. As of July 2026, what's actually happening on the ground is subtly different. Code pours out faster than ever, while the speed at which a human can read, judge, and take responsibility for it hasn't moved at all. Notion design engineer Geoffrey Litt named this mismatch directly in an essay published in early July 2026, "Understanding is the new bottleneck." He splits understanding into two kinds: "understanding to verify" - is this code correct - and "understanding to participate" - having enough of a mental model to propose what should happen next.

This piece takes that distinction as a starting point, looks at data showing why understanding has become the constraint, frames what accumulates when it's neglected as understanding debt, and works through concrete practices for protecting understanding in day-to-day engineering. The essay and its GeekNews discussion are the jumping-off point; the framing and conclusions below are my own.

1. In a World Where Generation Is Cheap, Where Did the Bottleneck Go

The cost of having an AI agent write code has fallen close to zero. But the real bottleneck in software was never actually writing - verification, integration, and maintenance were always heavier. It's just that when writing was slow, that weight stayed hidden behind it. Once AI pushed writing speed to an extreme, the verification and maintenance bottleneck that was always there got fully exposed.

1.1 The Mismatch in Numbers

Per a Faros AI analysis, organizations with high AI adoption saw pull request size grow roughly 51.3% and files touched per PR rise 59.7%. Yet median review time rose 441.5%, bugs per PR rose 54%, and the share of PRs merged without review climbed 31.3%. A separate study found developers using AI performed roughly 100 delete-and-undo actions per month, versus about 7 for developers not using AI. Generation sped up; the process of digesting it got shakier.

1.2 What This Tells Us

The one-line summary: the gap between how fast code is generated and how fast humans can understand it keeps widening. Teams that fail to close that gap end up with review turning into a rubber stamp, or review queues becoming the new bottleneck that eats back the speed gains. Either way, the outcome is the same - productivity looks higher on paper while fewer people actually understand the system underneath it.

2. What Is Understanding - To Verify vs. To Participate

Litt's distinction is simple, but I think its practical implications run deep. Understanding to verify answers a yes/no question: is this code correct. As AI gets better at writing its own tests and catching its own errors, humans have less to do here. Understanding to participate is far deeper - it requires a mental model of why the system is shaped the way it is, so you can propose what should change next and in which direction.

From watching engineering teams, I've noticed these two kinds of understanding get conflated often. Green tests and an approved review make it easy to assume "we understood this." But that's only verification. The real signal that participatory understanding is missing shows up the next sprint, when nobody can confidently say how to extend the code that was just merged. The better AI gets at verification, the more the human's remaining job narrows toward participatory understanding.

3. Understanding Debt - A New Kind of Debt You Can't See

Technical debt is a familiar idea: code written in haste, refactors deferred, accumulating a cost that comes due with interest. I'd place understanding debt alongside it. The code itself is clean and every test passes, but the team's shared understanding of why it was built that way is quietly empty and growing emptier. This overlaps with what researchers discuss as cognitive debt.

3.1 Why It's Invisible

Technical debt tends to smell - duplication, quick-fix comments, tangled dependencies leave traces. Understanding debt leaves none. The code is tidy, the PR is approved, CI is green. But if nobody involved can actually explain why it was done this way, the debt is already accruing. In Litt's phrase, the people involved may simply have "lost the plot."

3.2 When the Bill Arrives

This debt stays invisible day to day, then comes due all at once during an incident or a major migration. Root-causing takes several times longer than usual, and most of that time goes into reconstructing why the code being touched was written that way in the first place. The absence of understanding is most expensive precisely when things are most urgent.

4. The Risk of Merging Without Understanding

A common pattern: an agent produces a large diff in one shot, and a reviewer under time pressure approves it because tests passed. The figures cited above - a 54% rise in bugs per PR and a 75% rise in logic and correctness errors - show this pattern is generating real cost. Separate analysis found AI-generated code looks plausible but actually contains more issues than human-written code.

What worries me more than any single bug is the cumulative effect. Repeating the habit of approving without understanding slowly produces a codebase nobody feels confident touching. That's the same phenomenon as legacy systems of the past, just arriving at a much faster clip. Treating skipped understanding as normal under sprint pressure buys speed today and gets repaid in full during on-call and incident response tomorrow.

5. Practices That Protect Understanding - Small Changes, Explanations, Tests, Docs, Good Abstractions

Litt proposes four techniques: explainer docs, comprehension quizzes, micro-worlds, and shared spaces. I want to recast these as five habits any team can apply immediately.

5.1 Keep Changes Small

Comprehension load doesn't grow linearly with diff size - it grows faster than that. Explicitly instructing an agent to change one concept at a time, and breaking multi-concern refactors into staged requests, is the cheapest way to avoid accumulating understanding debt.

5.2 Ask for the Explanation Before the Raw Diff

Extending Litt's explainer-doc idea, a review process can require a short summary of what changed and why before anyone looks at the raw diff. Going further, requiring a reviewer to pass a brief comprehension check before approving structurally blocks the habit of approving without understanding. Litt calls this kind of mechanism a "speed regulator."

5.3 Accept What Tests Can't Show, But Keep Them as a Floor

Tests show correctness, not intent - accepting that limit keeps a green suite from being mistaken for proof of understanding. Even so, tests remain valuable as a minimum safety net against regressions.

5.4 Turn Complex Logic Into Docs and Small Demos

Like Litt's micro-worlds, wrapping a complex algorithm or migration in a small interactive demo the team can walk through together sharply speeds up comprehension. What's notable is that an agent can build that demo too - using code to help humans understand other code.

5.5 In the End, It's Good Abstraction

The most fundamental fix is designing an architecture with boundaries and names a human can actually follow in the first place. That's exactly the argument in this blog's Write Code Like a Human Will Maintain It. The skill of designing good abstractions isn't replaced in the AI era - if anything, it's the surest investment for lowering the understanding bottleneck.

6. AI Tools: Helping vs. Hurting Understanding

The same AI tool can help or hurt understanding depending on how it's used. Dropping a large diff with no explanation, or running repeated automated refactors with no rationale, hurts understanding. Requiring an agent to produce a doc explaining the background and intent behind a change, and folding a short comprehension check into review, makes the same tool work in understanding's favor.

In my view, the deciding factor is a team's prompting habits and review process, not the tool itself. A team whose default prompt is "just get it done fast" and a team whose default is "explain why you changed it this way" will land in very different places using the exact same model.

7. The Link to the Changing Developer Role

This discussion shares roots with this blog's piece on how the developer role shifts in the AI coding era. As the value of execution - writing code directly - declines, what grows in importance is problem definition and design. Adding this essay's argument, the core of that design capability now includes the ability to design for a team's shared understanding. A senior developer's value is shifting from "someone who writes good code" toward "someone who makes sure the whole team understands the system." The old advice to write maintainable code shares the same root - it's ultimately design for a future understander, whether that understander is human or AI.

Conclusion: Three Things to Try Today

Geoffrey Litt's diagnosis is clear: AI's writing speed has already outpaced human understanding speed. The question is no longer how fast you can write, but how fully you can understand before participating in the next iteration. Splitting understanding into verification and participation makes clear what can be handed to AI and what a human has to keep holding.

Three things worth trying starting today. First, deliberately keep change sizes small. Second, formalize a review step that asks for "what changed and why" before the raw diff. Third, experiment with team rituals that build shared understanding - short demos, short comprehension checks, short docs. If you accept that understanding is the new bottleneck, the next investment isn't a faster generation tool - it's habits and process that produce faster understanding.
