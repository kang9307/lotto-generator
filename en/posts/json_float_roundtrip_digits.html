Introduction - two directions in which a number stops being the same

A double is 64 bits in memory, but inside files, logs, JSON and CSV it is text. The number of digits used between the moment a value is written as text and the moment the text is read back decides whether the value stays identical. A round trip has two directions, and each guarantees a different number of digits.

  • Text to double to text: is a decimal string written by a person restored exactly? The guaranteed digit count is 15.
  • Double to text to double: does a value obtained from a calculation come back with the same bits? The digit count needed is 17.
  • Mixing the two directions and saying that 15 digits are safe makes code that stores calculation results with 15 digits change values silently.

The questions answered here are the following.

  • When text written with 6, 9, 15, 16 and 17 digits is read back, how many values end up with different bits?
  • What does the shortest round-trip notation chosen by Python repr and JavaScript toString guarantee?
  • What does a value that needs 17 digits look like?
  • How many digits do Python, Node, PowerShell 5.1, awk and SQLite print without any setting?
  • When a value changes between tools, does the change arise on the writing side or the reading side?

Section 8 of the JSON number precision article counts 15, 16 and 17 digit failures on a sample of 200,000 values. This article does not repeat that table. It covers the contrast between three sample kinds (bit patterns, arithmetic results and input of at most 15 digits), the 6 and 9 digits of float32, the default output digits of tools, and the separation of variables when values move between tools.

0.1 and 0.1+0.2 seen as bits

The floating-point page of the official Python tutorial states that IEEE 754 binary64 values carry 53 bits of precision and that 0.1 is approximated by 3602879701896397 / 2 ** 55. The same page explains that 0.1, 0.10000000000000001 and 0.1000000000000000055511151231257827021181583404541015625 all point to the same approximation, so any of them could be displayed while preserving the invariant eval(repr(x)) == x. The code below checks that explanation with bits and hexadecimal notation.

The output shows the following.

  • The bits of 0.1+0.2 are 3FD3333333333334 and the bits of 0.3 are 3FD3333333333333. The last bit differs, and the two are different doubles.
  • Writing 0.1+0.2 with %.15g gives the text 0.3, and reading that text back returns the bits of 0.3 (...333), which is not the original value.
  • Writing it with %.17g gives 0.30000000000000004, and reading it back returns the original bits (...334).
  • The neighbouring doubles around 0.3 are 0.29999999999999993, 0.3 and 0.30000000000000004. Seventeen digits are the number needed to tell a value from its neighbours.
  • Writing 0.1 with 17 digits gives 0.10000000000000001, while repr gives 0.1. Both strings go back to the same double.

Round-trip table for 6, 9, 15, 16 and 17 digits - three kinds of samples

The code below builds three kinds of samples, writes each value as %.N g text, reads it back as a float, and compares all 64 bits. A is a finite value from a random 64-bit pattern (the whole exponent range), B is an arithmetic result in an ordinary range (multiplication and division), and C is a value made from decimal text typed with 1 to 15 significant digits. float32 is counted the same way.

import random, struct, math, sys
                    def bits(x): return struct.unpack('<Q', struct.pack('<d', x))[0]
                    def f32(x): return struct.unpack('<f', struct.pack('<f', x))[0]
                    def f32bits(x): return struct.unpack('<I', struct.pack('<f', x))[0]
                    print(sys.version.split()[0], 'float_info.dig =', sys.float_info.dig, ' mant_dig =', sys.float_info.mant_dig)
                    rnd = random.Random(20261006)
                    N = 100000
                    A = []
                    while len(A) < N:
                        x = struct.unpack('<d', struct.pack('<Q', rnd.getrandbits(64)))[0]
                        if math.isfinite(x): A.append(x)
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(N)]
                    C = [float('%.*g' % (rnd.randint(1, 15), rnd.uniform(-1e6, 1e6))) for _ in range(N)]
                    def fails(S, n):
                        return sum(1 for x in S if bits(float('%.*g' % (n, x))) != bits(x))
                    print('double, %d values per set; text = %%.Ng, then float(text), compare all 64 bits' % N)
                    print('%-4s %10s %10s %10s' % ('N', 'A:bitpat', 'B:arith', 'C:<=15dig'))
                    for n in (6, 9, 15, 16, 17):
                        print('%-4d %10d %10d %10d' % (n, fails(A, n), fails(B, n), fails(C, n)))
                    F = [f32(rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000)) for _ in range(N)]
                    def f32fails(n):
                        return sum(1 for x in F if f32bits(f32(float('%.*g' % (n, x)))) != f32bits(x))
                    print('float32, %d values; text = %%.Ng, then back to float32' % N)
                    for n in (6, 7, 8, 9):
                        print('N=%d  failures=%d' % (n, f32fails(n)))

The rules that the table shows are the following.

  • In A and B, 17 digits give 0 failures. About 94 percent of values came back with different bits at 15 digits and about 42 to 45 percent at 16 digits. On the side that writes a double as text, 15 digits are not a safe line.
  • In C, 15, 16 and 17 digits all give 0. This matches the sentence in the Python documentation for sys.float_info.dig, that a decimal string with at most 15 significant digits converted to a float and written back recovers the same decimal value. The same page gives the example of the 16-digit string 9876543211234567, which becomes 9876543211234568 when formatted with .16g.
  • The failures of C at 6 and 9 digits (59411 and 39308) arise because the typed text had up to 15 digits and the value changed the moment it was cut to 6 or 9. If the writing precision is shorter than the original text, nothing is restored in either direction.
  • float32 has 0 failures at 9 digits and 1568 failures at 8 digits. The standard numeric format strings page of Microsoft Learn says to use G17 for Double and G9 for Single, which matches this table.
  • Zero failures in a sample is not a proof for every double. The basis for needing 17 digits is that this sample and the Microsoft Learn recommendation point the same way.

Shortest round-trip notation - what repr and toString do

Writing 17 digits every time turns 0.1 into 0.10000000000000001, which is awkward to read. The Python documentation says that since 3.1 repr picks the shortest string among the candidates, and that when sys.float_repr_style is short, float(repr(x)) == x holds. Number::toString in the ECMAScript specification makes k as small as possible when fixing s, n and k, and MDN says toString uses the fewest significant figures needed to distinguish the output from adjacent number values. The code below counts how many digits this shortest form needs per value.

import random, collections
                    rnd = random.Random(20261006)
                    def need(x):
                        for n in range(1, 18):
                            if float('%.*g' % (n, x)) == x: return n
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(100000)]
                    h = collections.Counter(need(x) for x in B)
                    print('smallest N with float(%.Ng) == x, 100000 arithmetic values:')
                    for n in sorted(h): print('  N=%2d  %6d' % (n, h[n]))
                    print('examples (digits needed, repr):')
                    for x in (0.1, 0.1 + 0.2, 0.1 * 3, 1.1 * 1.1, 0.1 + 0.7, 1 / 3, 2 / 3, 100 * 1.1, 1e23, 5e-324):
                        print('  %2d  %s' % (need(x), repr(x)))

  • The standard numeric format strings page of Microsoft Learn gives the default precision of the G format for Double as the smallest round-trippable number of digits, with G15 as the default in .NET Framework.   • The R entry on the same page recommends G17 for Double. The 17-digit output written by ToString("R") has the same digit count as that recommendation.
  • Python %g, awk print and SQLite CAST AS TEXT are all short outputs meant for people to read, not for restoring values. The awk printf %.17g writes the same value with 17 digits.
  • Node toLocaleString wrote at most 3 decimal places in this PC's locale. Number formatting functions are not a value-preserving serialization path.

Moving between tools - the writer decides the value

Whether a change between tools comes from the writing side or the reading side can only be decided by separating the variables. In the experiment below, Python writes the bit patterns (hexadecimal) of 2000 values to a file, three writing tools write the same values in their own ways into 8 text files, and three reading tools read all 8 files and compare against the original bits. There are 8 writing methods and 3 reading tools, and the data is the same.

What to write and how - selection criteria

The results of the executions, arranged by purpose of writing, are as follows.

PurposeWay of writingEvidence seen in this article
Display for people, no restoration neededShort formats such as %g, G15 and toLocaleStringOutput of section 5. Part of the value is discarded
A double that must be restored (JSON, logs, CSV)Shortest round trip (repr, JSON.stringify) or 17 significant digits (%.17g, G17)Section 3 gives 0 at 17 digits; the table of section 6
float329 significant digits (G9)Section 3 gives 0 at 9 digits; Microsoft Learn recommendation
A double exported to CSV from PowerShell 5.1ToString("G17", InvariantCulture)Section 6: G17 gives 0, the ToString() default gives 1870
Receiving JSON numbers as double in PowerShell 5.1Convert the value to a string and use [double]::Parse(InvariantCulture)Section 7: cast gives 222, Parse gives 0
Checking whether a value changed between toolsRead the same file with two tools and compare the bits (hexadecimal)Setup of section 6
  • When restoration is the purpose, first check whether the notation is a shortest round trip or 17 digits, rather than asking how many digits to use.
  • Fifteen digits is a guarantee for the text to double to text direction, so it suits displaying values typed by a person and does not suit storing calculation results.
  • The default digits of the writing tool differ by tool and by output path. Even inside PowerShell 5.1, interpolation and ConvertTo-Json differ.
  • Compare values by bits, not by text. Python can extract the 64 bits with struct, Node with DataView, and PowerShell with BitConverter.
  • The problem of large integer-like values and 64-bit IDs is separate from the fractional digits treated here and is covered in the JSON number precision article.

What Could Not Be Verified

  • PowerShell 7 and recent .NET. This PC has no pwsh. Microsoft Learn describes the default G digits for Double as the smallest round-trippable number of digits and singles out .NET Framework as G15, but the two could not be compared by execution.
  • The default output digits of other languages such as Java, Go, Rust and C, and of JavaScript engines other than Node.
  • An exhaustive proof that 17 digits restore every double. The samples are three kinds of 100,000 values each.
  • The rule by which ConvertTo-Json writes 15 digits for some values and 17 for others. Only one counterexample and the result on a 2000-value sample exist.
  • The reason the Decimal cast in PowerShell 5.1 ends up one bit off, and the reason double.Parse reads -6667.211341195974 differently.
  • Round trips of infinity, NaN, negative zero and subnormal numbers. Whether sample A contains subnormal numbers was not counted.
  • The digits when ConvertTo-Json receives an object or an array. Only scalar doubles were passed.
  • Behavior on Linux and macOS, and locales that use a comma as the decimal separator. The PowerShell code is fixed to InvariantCulture.
  • The phenomenon that SQLite printf with %.17g did not give 17 digits. It printed 0.3 in execution, but the cause was not investigated.
