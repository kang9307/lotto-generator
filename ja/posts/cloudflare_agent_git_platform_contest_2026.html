きっかけ - エージェントが何千にもなったとき、リポジトリの土台は何か

2026年10月1日、Cloudflare公式ブログにDina Kozlov、Dillon Mulroy、Zebulon Piaseckiの3人による記事が掲載された。内容はコンテストの告知である。CloudflareはWorkersとArtifactsを使って「次のGitプラットフォーム」を作ってみるよう呼びかけた。GeekNewsには2026年10月4日登録の項目として紹介され、要約は締切、賞、そしてArtifactsがオープンベータであることに集中している。

告知の冒頭は、規定より先に前提を述べる。ブログは、GitHubが人間がコードを書き、リポジトリに整理し、ブランチ・コミット・イシュー・プルリクエストで協働する世界のために作られたと書く。そして次の世代のソフトウェアは別の種類の開発者、つまりエージェントによって作られるようになると述べる。ブログがエージェントの仕事として挙げるのは、バグ修正、機能開発、テスト、コードレビュー、依存関係の更新、保守作業である。この前提から告知の中心的な問いが出てくる。何百、場合によっては何千ものエージェントが同じコードベースで同時に働く世界で、土台はどのような姿になるのか。

ブログはこの問いを四つの未解決の問題に広げている。エージェントは他のエージェントの同時作業を知ることができるか。互いに衝突する変更をどう扱うか。エージェントが出した成果物をどう検証するか。なぜそう変更したのかという理由をどう残すか。コンテストはこの四つに答える実装を集める仕組みとして示されている。既存のGitHubにエージェントを付け足す水準を超えて、リポジトリ、ブランチ、プルリクエスト、ワークツリー、コードレビュー、マージ衝突そのものを考え直すことが求められている。

ここで扱う範囲は、告知に書かれた条件を表と箇条書きに整理し、同じ対象を指していても出典によって値が分かれる部分を切り分けておくことである。締切が近く、課金がまもなく始まるサービスなので、日付が正確であってはじめて役に立つ。コンテストの価値判断や参加の推奨は扱わない。同じテーマの背景は、AIネイティブなGitホスティングを扱ったCursorのGitサービスOriginの分析と、エージェントのランタイムを扱ったCloudflare OSの分析にある。以下は、それらが扱っていない今回のコンテストの条件とArtifactsドキュメントの数値に限る。

提出物3点とライセンス条件

ブログが提出物として求めるのは三つである。一つ目は、作ったものを見せる5〜10分の動画である。動画には、何を作ったか、それによってエージェントと開発者が何をできるようになるか、そしてどう動くかの三つを盛り込む必要がある。二つ目はソースコードへのリンクで、寛容なオープンソースライセンスで提供されなければならない。括弧内で例示されたライセンスはMIT、Apache、BSDである。三つ目はプロジェクトを実行または試す方法である。

これらの条件のうち、ライセンスの項目は実務上まず引っかかる部分である。告知は「寛容な」ものに限定しており、例示された三つはいずれも利用・改変・再配布の条件が軽い系統に属する。それ以外のライセンスが認められるのか、たとえば相互主義の条件が強いものやソース公開を制限するものがどう扱われるのかは書かれていない。プロジェクトが外部のコードに依存する場合、そのコードのライセンスと提出ライセンスが衝突しないかも、提出前に確認する項目である。この判断はコンテストの規定ではなく一般的なオープンソースの利用慣行に属し、告知はこの点に触れていない。

  • 動画 - 5分以上10分以下。何を作ったか、エージェントと開発者が何をできるようになるか、どう動くかを見せる用途。
  • ソースリンク - MIT・Apache・BSD系の寛容なライセンスで公開されたもの。
  • 実行方法 - プロジェクトを動かす、または試す方法の案内。
  • 提出様式 - 告知には書かれていない。別のページがあるかは確認できなかった。

賞の構成 - 1位のクレジットと上位3チームの渡航支援

賞は二層に分かれる。上位3プロジェクトは、チームごとに最大2人がサンフランシスコで開かれるCloudflare Connectに参加し、作ったものを紹介する。ブログの文言は「fly up to two members from each team to San Francisco」、つまりチームごとに最大2人を航空で送るというもので、宿泊は書かれていない。1位にはこれに加えて、25,000ドル相当のCloudflareクレジットとConnect月曜夜のVIP登壇者ディナーへの招待がある。ブログの文言は、クレジットとディナーの招待をまとめて1位の取り分として書いている。

この構成から読み取れることと読み取れないことを分けると次のようになる。読み取れるのは、1位の賞が現金ではなくクレジットであること、クレジットの単位がドルであること、航空の支援が上位3チームにかかることである。読み取れないのは、2位と3位にクレジットがあるか、クレジットをどの範囲のCloudflare製品にどの期間使えるか、航空の支援に上限があるか、宿泊など航空以外の費用が支援されるか、メンバー2人という上限がチーム規模の制限を意味するかである。最後の項目には特に注意が要る。「チームごとに最大2人の航空」は支援の規模を述べているだけで、チームの人数制限だと見なす根拠は告知にない。

賞が実際にいくらの価値になるかは、各自が判断することである。クレジットは使い道がCloudflareのサービスに限られる価値であり、ここでは他の単位への換算をしない。Artifactsの料金表は公開されていて、第7節にその料率がある。ただし、その料率で25,000ドルのクレジットがどれだけ持つかは、操作回数や保存量といった使い方によって決まるため、ここでは計算しない。

  • 上位3プロジェクト: チームごとに最大2人、Cloudflare Connect(サンフランシスコ)への航空。宿泊は告知に書かれていない。
  • 1位: 25,000ドル相当のCloudflareクレジット + Connect月曜夜のVIP登壇者ディナーへの招待。
  • 告知にないこと: 2位・3位のクレジット、クレジットの有効期間、航空の支援の上限と宿泊が支援されるか。

Artifactsとは何か - ドキュメントが定義する範囲

コンテストの土台であるArtifactsを、ブログは「Gitを話すバージョン管理型のファイルシステムで、数百万のリポジトリまで拡張できるもの」と定義している。Cloudflare開発者ドキュメントの概要は「Gitを話すバージョン管理ストレージ」と書き、生のblobではなくバージョン付きのファイルツリーを保存すると説明する。変更履歴によれば、2026年4月16日にプライベートベータとして始まり、2026年10月1日にオープンベータとなった。オープンベータの対象はWorkers Paidプランの顧客で、Workers Freeでは使えない。

下の表は、ブログと概要ドキュメントが共通して挙げる機能を整理したものである。どちらの出典もこの水準の記述なので、各機能が内部でどう実装されているかは書かない。

アクセス経路Workersバインディング、REST API、標準のGitクライアントエージェントがGitクライアントで接続する構成が可能だという記述
リポジトリの作成・import・forkプログラムからリポジトリを作成し、既存のものを取り込み、forkする作業ごとに隔離されたコピーを持たせる用途と読める

第3列は告知の文ではなく、読む側の解釈である。ブログは、これらの機能をコンテスト課題にどう使うべきかを指定していない。確認できるのは、ドキュメント概要にある「エージェントのセッションを別のリポジトリやブランチに記録する」「forkと比較とマージで並列に探索する」という記述が、コンテストの問いと同じ方向を向いているという点までである。

  • 定義: ブログは「Gitを話すバージョン管理型ファイルシステムで数百万リポジトリまで拡張」、ドキュメントは「Gitを話すバージョン管理ストレージ」。

  • 対象: Workers Paidプラン。Workers Freeでは使えない。
  • 規模の記述の違い: ブログは数百万、変更履歴は数千万と書く。表現が異なり、上限ドキュメントのリポジトリ数は無制限である。

公式コードサンプル2つを読む - forkとpushイベント

ブログにはコードサンプルが二つある。以下は原文のサンプルをそのまま写したものである。テンプレートリテラルのバッククォートとドル記号はHTMLの文字参照で書いただけで、コードは同じである。ここではコードを実行しておらず、動作の説明はブログがサンプルとして示した範囲にとどめる。

using project = await env.ARTIFACTS.get("my-project");
                    const { defaultBranch } = await project.info();
                    const workspace = await project.fork(`task-${crypto.randomUUID()}`);
                    
                    using repo = await env.ARTIFACTS.get(workspace.name);
                    const instructions = await repo.readFile({
                      ref: defaultBranch,
                      path: "AGENTS.md",
                    });
                    
                    const agentTask = {
                      remote: workspace.remote,
                      token: workspace.token,
                      instructions: instructions ? await instructions.text() : null,
                    };

最初のサンプルが示す流れは四段階である。名前でプロジェクトを取得し、デフォルトブランチを調べ、作業ごとにランダムな名前を付けてforkし、forkされたリポジトリでデフォルトブランチのAGENTS.mdを読む。そしてエージェントに渡すタスクオブジェクトに、リモートのアドレス、トークン、指示のテキストを入れる。目を引くのは、エージェントが使うアクセス情報が、forkされた一つの作業空間に結びついて出てくる点である。元のリポジトリを直接開くのではなく、作業ごとのコピーのリモートとトークンを渡す形になっている。これが複数のエージェントが同時に働くときに衝突を減らす設計の方向だという説明は、サンプルコードから読み取れる解釈であり、ブログがそう述べたわけではない。

export default {
                      async queue(batch, env) {
                        for (const message of batch.messages) {
                          const event = message.body;
                          if (event.type !== "cf.artifacts.repo.pushed") continue;
                    
                          await env.REVIEW_WORKFLOW.create({
                            params: {
                              namespace: event.source.namespace,
                              repo: event.source.repoName,
                              ref: event.payload.ref,
                              commit: event.payload.after,
                            },
                          });
                        }
                      },
                    };

二つ目のサンプルはキューのコンシューマである。メッセージを順に処理し、イベントの種類がpushでなければ読み飛ばし、pushならネームスペース、リポジトリ名、ref、コミットを引数にして、REVIEW_WORKFLOWというバインディングにワークフローのインスタンスを作る。ブログの説明どおりなら、このサンプルはpushに反応してコードレビューの流れを始める構造である。イベント名の形式(cf.artifacts.repo.pushed)とペイロードのフィールド(source.namespace、source.repoName、payload.ref、payload.after)がサンプルにそのまま現れている。

  • どちらのサンプルもWorkersランタイムのバインディング(env.ARTIFACTS、env.REVIEW_WORKFLOW)を使う。
  • 最初のサンプルのusing宣言は、リソースがスコープを抜けると片付けられる構文として使われている。片付けが具体的に何をするかはサンプルに説明がない。
  • サンプルは一部の抜粋で、REVIEW_WORKFLOWの定義とキューの設定は含まれていない。
  • サンプルの指示ファイルはAGENTS.mdで、エージェントへの指示をリポジトリ内のファイルから読む慣行に沿ったものと見られる。

料金と上限 - 課金開始日が二通りに書かれている理由

料金は二つの軸である。ブログは、リポジトリの操作回数と保存されたデータ量に基づくと書く。開発者ドキュメントの料金ページは具体的な値を示している。操作は月の最初の10,000件まで、それ以降は1,000件あたり0.15ドル、保存は月の最初の1GBまで、それ以降はGB月あたり0.50ドルである。GB月は、30日の請求期間にわたる日ごとの最大保存量の平均として決まる。

問題は課金開始日である。ブログは、2026年10月15日からArtifactsの利用に課金を始めると書く。開発者ドキュメントの料金ページは、10月14日から操作と保存に課金を始めると書き、変更履歴の10月1日の項目も10月14日と書いている。一日の差はタイムゾーンの解釈でも生じうる大きさだが、どちらの出典もタイムゾーンを書いていない。原因はここでは確定できない。確かなのは、どちらも10月中旬で、コンテストの締切(10月14日)と同じ週に料金が始まるという点である。したがってコンテストの作品を動かし続ける側は、締切の数日後には課金が始まると見て計算しておくのが安全である。

項目値出典
操作(operations)月の最初の10,000件まで、以降1,000件あたり0.15ドル開発者ドキュメントの料金ページ
保存(storage)月の最初の1GBまで、以降GB月あたり0.50ドル開発者ドキュメントの料金ページ
課金開始日2026-10-15コンテストのブログ
課金開始日2026-10-14ドキュメントの料金ページ・変更履歴
リポジトリ一つの保存上限1GBプラットフォーム上限のドキュメント
ファイル・blob一つの上限32MBプラットフォーム上限のドキュメント
アカウントあたりの保存上限1TB(要請により引き上げ可能)プラットフォーム上限のドキュメント
リクエストレートコントロールプレーンはネームスペース単位、Gitリクエストはリポジトリ単位で10秒に2,000件プラットフォーム上限のドキュメント
リポジトリ・ネームスペースの数無制限プラットフォーム上限のドキュメント

上限のうち設計に直接影響するのは、リポジトリあたり1GBとblobあたり32MBである。エージェントが作業ごとにリポジトリをforkする構成では、リポジトリ数は無制限で保存は合計1TBまでなので、一つのリポジトリの大きさよりも作業空間を片付ける頻度のほうが請求額に直接影響しうる。これは料金表から導いた推論であり、実際の課金方式は請求書で確認する必要がある。

  • 料金ページは操作の例としてcreate・push・pull・cloneのようなリポジトリ操作を挙げている。この例の外のリクエストがどう数えられるかは確認できなかった。
  • ネームスペース名は2〜63文字で、英字または数字で始まり、その後は英字・数字・ピリオド・アンダースコア・ハイフンを使える。
  • 無料枠(操作10,000件、保存1GB)はWorkers Paidアカウント内の値で、Workers Freeには適用されない。

コンテストの問いを設計項目に置き換えると

ブログの問いは、実装項目に置き換えると具体性が出る。下の一覧は、ブログが列挙した問いと、それに対応すると読めるArtifactsの道具を結びつけたものである。この対応は解釈であり、コンテストがこの方向を求めているという意味ではない。ブログが求めた最低条件は、複数のエージェントが変更を同時に扱う姿を見せることである。

  • 同時作業の認知 - あるエージェントが別のエージェントの進行中の変更を知っているか。イベント購読のpushやforkのイベントが材料になりうる。
  • 衝突する変更 - 同じファイルを別の方向に直した変更。作業ごとにforkして隔離し、マージの時点で扱う方式が、サンプル1の構造から読み取れる一つの方向である。
  • 成果物の検証 - サンプル2でpushイベントがワークフローを始める構造は、レビュー自動化の一つの形である。
  • 変更理由の保存 - ブログはエージェントのコンテキストを残す新しい方法に言及している。保存方式は指定されていない。
  • 同時比較と選択 - 複数の変更を同時に比較し、どれを出荷するかを決める段階。ブログが例として挙げている。

このうちどれが必須かは告知に書かれていない。審査基準がないので、どの点を強調する作品が有利かは分からない。確実に言えるのは、告知が個別の機能ではなく土台を考え直すよう求めたという点である。

参加を勧めるための項目ではなく、告知の条件から直接導かれる準備事項を整理したものである。参加するかどうかは各自の判断に属する。

  • プラン - ArtifactsはWorkers Paid専用なので、使うにはそのプランのアカウントが必要である。プランの価格はここで確認した範囲の外である。
  • 締切までの余裕 - 締切の時刻とタイムゾーンが書かれていないので、締切日の前日に提出を終えるのが最も単純な備えである。
  • ライセンスの整合 - ソースはMIT・Apache・BSDのいずれかで公開する必要がある。依存ライブラリのライセンスと合うかを先に確認する。
  • 動画の長さ - 5〜10分の範囲に収める必要がある。5分未満や10分超の場合の扱いは告知にない。
  • 再現性 - 実行方法の案内が提出物なので、環境変数やトークンなどの秘密の値はソースに入れず、設定の案内として分ける。
  • 課金開始後の費用 - 締切後も作品を動かし続ける予定なら、10月14日または15日から操作と保存の料金がかかるアカウントで動くものとして計算する。
  • データの管轄 - Artifactsはデータの保存・処理地域を米国またはEUから選べる。実際のコードをデモに使うなら、どの地域に置くかを決めておく。

確認できなかったこと

  • 締切の時刻とタイムゾーン。ブログには日付だけがある。
  • 審査基準、審査員、結果の発表時期、参加資格、チーム規模の制限。ブログに記述がない。
  • 提出経路と様式。別の提出ページがあるかは確認していない。
  • 2位・3位のクレジットの有無、クレジットの利用範囲と有効期間、航空の支援の上限と宿泊が支援されるか。
  • 課金開始日がブログ(10月15日)とドキュメント(10月14日)で異なって書かれている理由。どちらが基準かは確認できなかった。
  • create・push・pull・clone以外のリクエストが操作一件に当たるか。料金ページが挙げた例の外の範囲は確認できなかった。
  • Workers Paidプランの価格と含まれる内容。この記事の範囲外である。
  • サンプルコードの実行結果。ここではコードを実行しておらず、Artifacts APIの詳細ドキュメントも開いていない。
