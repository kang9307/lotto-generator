HTTP QUERY Method — The New Search Standard Beyond GET and POST

RFC 10008: A Request Body with Safety, Idempotency, and Cacheability — All Three at Once

2026-06-27 Dev & Infra

Introduction: Why Does HTTP Need a New Verb?

For decades, HTTP's GET and POST have handled the web's read and write operations. For simple CRUD APIs, they work well enough. But when modern RESTful APIs need to handle complex search and filtering requests, both methods hit structural walls. GET forces queries into URLs where complexity creates a length problem, while POST accepts flexible bodies but can't signal read-only intent to the HTTP infrastructure.

As of June 2026, RFC 10008 has been officially published, introducing the HTTP QUERY method to fill this gap. The authors are Julian Reschke, James M. Snell (Cloudflare), and Mike Bishop (Akamai). Rather than summarizing the announcement, this post analyzes the structural reasons QUERY was needed, how it should be used in practice, and what real adoption barriers remain.

1. GET's Structural Limits — When the URL Becomes a Prison

RESTful design defaults to GET for retrieval. Simple cases work fine. But imagine a product search API that must carry category, price range, tag arrays, sort conditions, and pagination all in one request — the URL quickly becomes unwieldy.

GET /products?category=electronics&price_min=100&price_max=500&tags[]=wireless&tags[]=bluetooth&tags[]=noise-cancelling&sort=price_asc&page=2 HTTP/1.1

That's still manageable. But real search APIs carry nested filter structures, full-text search expressions, and aggregation conditions. Four distinct problems emerge.

First, URL length limits. The RFC itself sets no URL length cap, but browsers (Chrome ~2MB) and servers (Apache default 8KB, Nginx default 8KB) impose their own. Encoding a complex Elasticsearch query into a URL hits these limits quickly.

Second, non-ASCII encoding overhead. Non-English search terms and special characters require percent-encoding. Readability degrades, and debugging the original query becomes hard.

Third, logging and privacy exposure. URLs appear in web server access logs, CDN logs, and browser history. Sensitive search parameters in URLs are recorded and potentially leaked unintentionally.

Fourth, no standard for arrays and nested objects. Encoding arrays as tags[]=a&tags[]=b or nested objects in URLs varies across libraries, creating client-server interoperability gaps.

2. The POST Workaround's Hidden Costs

To avoid GET's limits, many APIs use POST for complex search requests. GraphQL query execution is the canonical example; Elasticsearch's _search endpoint and OpenSearch APIs do the same for complex queries. Sending JSON in the request body seems like a practical fix.

But this workaround carries invisible costs.

First, semantic pollution. POST signals in HTTP semantics that an operation may modify server state. Using it for read-only searches means the HTTP layer cannot determine whether the request is a read or write. Middleware, proxies, and the entire infrastructure operate without knowing the intent.

Second, no caching. By HTTP spec, POST responses are not cacheable by default. CDNs and reverse proxies cannot reuse responses for identical search queries. Even the most popular search terms hit the origin server on every request. This is a semantics problem — forcing cache headers on POST responses works against the standard.

Third, no automatic retries. On network failure, HTTP clients and load balancers only auto-retry idempotent requests. POST is not idempotent by definition, so retrying risks duplicate side effects. A read-only query never gets automatically retried just because it uses POST.

In short, the POST workaround trades three HTTP guarantees — safety, idempotency, and cacheability — for short-term convenience. The cost returns as infrastructure complexity, unnecessary server load, and debugging difficulty.

3. QUERY's Design — Three Guarantees in One Method

RFC 10008's core definition is concise: allow a request body while guaranteeing safe, idempotent, and cacheable semantics simultaneously.

"A QUERY requests that the request target process the enclosed content in a safe and idempotent manner and then respond with the result of that processing." — RFC 10008

A practical QUERY request looks like this:

QUERY /contacts HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{
  "filter": {
    "country": "US",
    "tags": ["developer", "api"],
    "joined_after": "2025-01-01"
  },
  "sort": { "field": "name", "order": "asc" },
  "limit": 20
}

This may look like POST on the surface. The difference is not the verb name itself but the semantic signal it sends to every layer of the HTTP stack.

3.1 Safety

QUERY explicitly declares it does not modify server state. Middleware, monitoring tools, and API gateways can treat the request as a side-effect-free read operation. Both humans and infrastructure see "this is a search" unambiguously.

3.2 Idempotency

The same QUERY request produces the same result regardless of how many times it's sent. On network failure, HTTP clients and load balancers can automatically retry. Complex search requests that fail due to network instability get retried by the infrastructure without developer intervention.

3.3 Cacheability

QUERY responses can be cached. However, the cache key must include the request body and Content-Type metadata in addition to the URL. Two requests to the same endpoint with different bodies are different queries. CDNs and reverse proxies that include the body in the cache key can serve cached responses for repeated identical queries. Servers can also assign stable URIs to query results via Content-Location headers, enabling subsequent GET requests to retrieve cached results without re-sending the body.

4. Accept-QUERY Header — Query Format Negotiation

RFC 10008 also introduces the Accept-QUERY response header, allowing servers to advertise supported query formats. For example:

Accept-QUERY: application/json, application/x-www-form-urlencoded

Clients read this header to learn which query syntaxes the server accepts, then send QUERY requests in the appropriate format. This standardizes something that was ad-hoc before — different APIs accepted different query syntaxes (JSON filters, FIQL, GraphQL) with no standard way to discover them. With Accept-QUERY, format negotiation is explicit and standard.

6. Practical Use — Where QUERY Fits

QUERY shines in a specific scenario: complex search APIs where both a flexible request body and response caching matter.

6.1 Good Fits

Complex REST search APIs are the primary target — product search, document search, user list filtering with many conditions and complex structures benefit immediately. GraphQL is another candidate: it currently uses a non-standard mix of GET and POST; QUERY would be semantically correct and cacheable for query execution. Elasticsearch and OpenSearch DSL queries sent as POST bodies could switch to QUERY to gain infrastructure-level caching and retry support.

6.2 Where to Stick with GET

Search results that must be shareable via URL or bookmarkable don't fit QUERY — the URL itself is the sharing unit. Simple one- or two-condition filters don't justify QUERY either. Use QUERY where GET genuinely breaks down, not as a blanket replacement.

7. Adoption Status and Real Barriers

An RFC being published doesn't mean QUERY is usable tomorrow. Every layer of the HTTP stack must understand the new method.

7.1 Current Status (June 2026)

API client tool Kreya added QUERY support in version 1.20. Since the RFC's co-authors work at Cloudflare and Akamai, CDN-level support is expected to arrive earlier than framework support. Browser fetch() support requires WHATWG discussion and browser implementation. Major frameworks (Express, FastAPI, Django, Spring), HTTP client libraries (curl, axios), and legacy proxies and firewalls that may block non-standard HTTP methods all need updates. Some corporate firewall policies block methods other than GET/POST/PUT/DELETE outright.

7.2 Long-Term Outlook

IETF standards take time to deploy. HTTP/2 was standardized in RFC 7540 in 2015 but took years for full adoption. QUERY may realistically need 3–5 years to become a standard tool across production stacks. The practical strategy today: experiment with QUERY in new internal APIs where you control both client and server. For public or external-facing endpoints, wait for client library and CDN maturity.

8. Infrastructure: Cache Key Design is the New Challenge

The most interesting infrastructure challenge QUERY introduces is cache key design. Traditional HTTP caches key on URL alone. QUERY requires including the body in the cache key — a new requirement for CDNs and reverse proxies.

RFC 10008 permits implementations to normalize semantically insignificant differences (like JSON key order). A cache can treat two bodies with different key ordering but identical content as the same cache entry. This improves cache efficiency but adds implementation complexity.

The Content-Location pattern is useful here. A server responds to a QUERY with a stable result URI in the Content-Location header. Subsequent requests can GET that URI using normal URL-keyed caching — no need to re-send the complex body or deal with body-inclusive cache keys on the client side.

9. Conclusion — What Proper HTTP Semantics Actually Mean

The problem HTTP QUERY solves isn't technically complex. It's a simple design mismatch that was left unaddressed for too long. Cramming complex searches into GET URLs or sending read-only queries as POST works in the short term but spreads semantic contamination through the entire infrastructure. QUERY eliminates that compromise.

That said, an RFC publication is not the same as "usable today." Full stack support will take time, and body-inclusive cache key design is a real new challenge. But the direction is clear: a standard for expressing complex search API semantics correctly in HTTP now exists, and the signal is already reaching client tools and CDN providers.

Two things worth doing now: list the read-only search endpoints in your API that currently use POST as a workaround — these are QUERY migration candidates. And start including QUERY in routing support for new internal API services, so the team becomes familiar with it before adoption becomes mainstream.
