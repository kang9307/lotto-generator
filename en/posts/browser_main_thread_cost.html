Why the Browser Has Only One Main Thread - What Shares It, and What Can Actually Leave

How scripting and rendering block each other, what each of the three metrics really measures, and where the boundary of the untransferable is drawn

2026-09-05 Dev & Infra

When a web page stutters, the first diagnosis is almost always that the code is slow. So the algorithm gets rewritten, the library gets swapped, the bundle gets trimmed. And yet, surprisingly often, none of that changes how the page feels. The problem was never speed. It was location.

Inside a single browser tab, almost everything related to what you see on screen happens on exactly one thread. JavaScript runs there. Style calculation happens there. Layout happens there, and so does the generation of paint commands. Even the work of deciding which element sits under the coordinates you just tapped happens there. Every item on that list waits for every other item. While one holds the thread, the rest form a queue behind it.

This article is not a list of optimization tips. It looks at what is sharing that single thread, at which metrics actually capture the feeling of slowness, and at where the line is drawn between work that can be moved off the thread and work that is structurally forbidden from leaving it. Knowing where that line runs also tells you which optimizations were never going to work in the first place.

Every metric definition and threshold below is as it stands in the primary sources: web.dev, Chrome for Developers, the W3C draft, MDN, and the WHATWG HTML Standard. Performance thresholds get revised, and the single most common error in performance writing is copying a number out of an older article that copied it from somewhere else. Read the values in the table below together with the date they were cited.

The trigger - the problem is not the speed of the code but its location

In early September 2026 a post titled The browser main thread is expensive circulated in the Korean developer community. The original is written in Korean, and its thesis compresses into a single sentence: the trouble is not that the code is slow, it is that this particular code happens to be holding the main thread. On top of that diagnosis the author stacks seven prescriptions — splitting, batching, prioritizing, deferring, moving work onto the compositor, sending work to a worker, and eliminating the work altogether. The original notes that the last of these usually leaves the biggest margin behind.

A list of prescriptions is useful. What a list does not explain, however, is why each prescription works. Why does splitting improve responsiveness without making anything faster? What is the line that separates work a worker can take from work it cannot? What exactly does moving something onto the compositor skip? Those answers only appear once you look at the structure underneath.

So this article maps structure and boundaries instead of prescriptions. That includes material the original does not cover. Long Animation Frames, OffscreenCanvas and requestIdleCallback do not appear in it. Conversely, content-visibility, INP and TBT do appear in the original, and they appear here too — but with the definitions from the primary documentation attached verbatim. The most common accident in performance writing is re-copying a number someone else already copied.

The actual list of what the main thread carries

The Chromium rendering architecture document enumerates the responsibilities of the main thread inside the render process in a single sentence. It runs scripts, the rendering event loop, the document lifecycle, hit testing, script event dispatching, and the parsing of HTML, CSS and other data formats. The same document also notes that the render process contains a separate compositor thread and several helper threads. In other words, the browser is not single threaded. There is simply one place where the truth of the screen gets computed.

What deserves attention in that list is how completely unrelated the items are to one another, and how they nonetheless stand in the same line. A sorting algorithm, a style recalculation and a click handler invocation have nothing in common — until they share an execution seat, at which point each becomes a cause of the others being late.

The right-hand column is what the user experiences; the left-hand column is what the developer sees in code. Bridging those two columns is the job of the next section.

One at a time - a task runs to completion before it yields the seat

The reason this structure hurts is not that there is one thread. It is that the unit of execution is not preemptible. Once a JavaScript task starts, it runs to the end. Even if something more urgent arrives midway, the browser cannot cut the running task apart and slot the urgent work in. An operating system scheduler would force a context switch when the time slice expires; the event loop has no such mechanism.

So when a 300 millisecond function is running and the user presses a button, that click sits in the queue in a state where it exists but nobody knows about it yet. Dispatching only begins once the function returns, and the rendering update only gets its turn once the handler returns. This waiting stretch is precisely the first segment of INP, the input delay, which we will come back to shortly.

One common misunderstanding is worth settling here. Asynchronous is not parallel. An async function, a promise chain, the handling of a fetch response — all of them eventually come back as a task or a microtask on the main thread. Waiting on the network does release the thread, but parsing the response when it arrives, updating state, and re-rendering the list all happen in the same seat as everything else. Writing something asynchronously does not relocate heavy computation anywhere.

The frame budget - of 16.6 milliseconds, what is actually yours

For the screen to look smooth, frames have to arrive on a regular cadence. The web.dev rendering performance document states that on a 60Hz display the browser has 16.66 milliseconds to produce each frame. It then attaches a caveat immediately: the browser has its own per-frame overhead, so all of your work needs to be completed inside 10 milliseconds.

What matters about this number is the ratio rather than the absolute value. As refresh rate rises, the budget shrinks by the same factor. On a 120Hz display the frame interval halves, and so does the time available. It feels as though higher-end hardware should be more forgiving, but when the refresh rate rises with it, the reality is that the budget gets tighter, not looser.

And those 10 milliseconds are not a JavaScript-only budget. Style calculation, layout and paint command generation all have to fit inside them too. If a script consumes 8 milliseconds, everything else has to finish within 2. Code that redraws a list can look fast on its own and still drop the frame, because the layout cost that follows it pushes the total past the budget.

How they block each other - the dependency chain of five stages

web.dev names five stages in the making of a frame: JavaScript, Style, Layout, Paint and Composite. JavaScript produces the visual change. The style stage matches which CSS rules apply to which elements and computes the final values. Layout works out element dimensions and screen positions, and its defining characteristic is that a change in one element can propagate across the whole tree. Paint turns the result into pixel-filling commands, and composite places the drawn layers onto the screen in the correct order.

That ordering is a dependency chain. You cannot paint without layout results, and you cannot lay out without computed styles. Two consequences follow.

  • The entry point into the pipeline depends on which property you change. Change a width or a position and layout runs again from the top; change only a color and layout is skipped and the work starts at paint
  • Some properties can skip both layout and paint. web.dev states explicitly that if you change a property that requires neither layout nor paint, the browser can jump straight to the compositing step, and calls this the cheapest and most desirable pathway through the pipeline
  • If you interleave reads and writes within the same frame, the browser has to run the calculation early in order to hand back an up-to-date layout value. This is why the habit of doing all reads first and batching all writes afterwards exists
  • That forced calculation is hard to see in code. A single property that asks for an element size or position triggers layout on the spot, and if it sits inside a loop, layout runs once per item

Put differently, the jobs on the main thread do not merely share a seat — they are each other's inputs and outputs. That is why a delay in one place spreads to another, and why a saving in one place rescues something else entirely.

The three metrics that measure slowness, and their thresholds

Once the structure is clear, measurement comes next. The word slow carries no information by itself; unless you fix what is being measured and how, you cannot even tell whether you improved anything. On the web there are three axes in common use.

INP - from the press to the change on screen

Interaction to Next Paint expresses a page's overall responsiveness by observing the latency of every click, tap and keyboard interaction that occurs across the lifespan of a visit. A single interaction breaks into three segments: the input delay before event handlers begin running, the processing duration during which the handler callbacks execute, and the presentation delay from the end of those callbacks until the next frame is painted. Scrolling, hovering and zooming are not counted for INP purposes. INP became a stable Core Web Vital in 2024, replacing FID.

TBT - the total time the main thread was blocked during load

Total Blocking Time measures the total amount of time after First Contentful Paint during which the main thread was blocked for long enough to prevent input responsiveness. The arithmetic is simple enough to memorize. A task that runs on the main thread for more than 50 milliseconds is a long task, and for each long task only the amount beyond 50 milliseconds is added up. A 120 millisecond task contributes 70; a 45 millisecond task contributes zero. TBT is a lab metric. web.dev notes that measuring it in the field is possible but not recommended, because user interaction can swing the value in ways that produce large variance in reports.

LoAF - delay seen per frame, with the culprit attached

Long Animation Frames counts frames rather than tasks. The W3C draft defines a long animation frame as either of two occurrences whose duration exceeds 50 milliseconds: a task after which updating the rendering is not necessary, and a task after which updating the rendering is necessary, up until rendering is actually updated. The entry carries startTime, duration, renderStart, styleAndLayoutStart, blockingDuration, firstUIEventTimestamp, and scripts, an array attributing the frame to the scripts responsible.

The three look at the same phenomenon from different angles. TBT is the total during the loading window, INP is the responsiveness real users experienced, and LoAF tells you which frame went wrong and who did it. Used as a sequence of work, that becomes: find the culprit with LoAF, guard against regressions with TBT, and confirm with INP that the fix reached actual users.

Why long tasks alone were not enough

The Long Tasks API was the default instrument for watching main thread occupancy for a long time. It has a structural blind spot, though: something is recorded only when a single task exceeds 50 milliseconds. Five consecutive 40 millisecond tasks can hold a frame hostage for 200 milliseconds and not a single long task is reported. The user waited 200 milliseconds and the dashboard stayed silent.

LoAF fills that blind spot at frame granularity. The Chrome for Developers document explains that because LoAF examines the whole frame rather than individual tasks, it captures the case where multiple smaller tasks collectively block rendering, and offers considerably better timing breakdowns and script attribution. The way blockingDuration is computed is worth noting. The W3C draft sorts the task durations within the frame in descending order, combines the longest task with the render duration if rendering occurred, and then sums the amount by which each entry exceeds 50 milliseconds. It is the TBT rule relocated to the inside of a frame.

Script attribution is where the practical difference shows up. A PerformanceScriptTiming entry carries invoker and invokerType describing what called it, executionStart for when execution began, sourceURL, sourceFunctionName and sourceCharPosition pointing at the source location, and forcedStyleAndLayoutDuration for the style and layout time that script forced. That last field is where the cost of interleaving reads and writes, described earlier, comes back to you as a number.

Support is narrow, however. It works in Chrome 123 and later and Edge 123 and later, and is absent from Firefox and Safari. So LoAF is a diagnostic instrument, not a dashboard covering your whole audience. Blurring that distinction leads to false reassurance on any service with a substantial Safari share.

Yielding - the craft of letting go and taking the thread back

With no preemption available, the only remaining option is to let go voluntarily. You cut long work into several tasks and leave a gap between the pieces for the browser to step in. One point has to be stated plainly here: yielding does not reduce the total amount of work. Because of task switching overhead the wall-clock total actually gets slightly longer. What you gain is room for input handling and rendering to happen in between. It is a trade that buys responsiveness while doing the same amount of work.

There are several ways to yield and they differ in character. Deferring with setTimeout puts the work at the end of the queue. If plenty of other tasks have piled up in the meantime, your work resumes considerably later. Deep nesting also triggers clamping: the WHATWG HTML Standard specifies that if the nesting level is greater than 5 and the timeout is less than 4, the timeout is set to 4.

scheduler.yield() attacks this problem head on. web.dev explains that it is simply a function returning a promise, and that the continuation of the current task runs before any other similar tasks. In other words you yield without going to the back of the line. Support is Chrome 129 and later, Edge 129 and later, Firefox 142 and later, and it is not supported in Safari.

// Process a long list in chunks, releasing the main thread each frame.
async function processInChunks(items, work) {
  const CHUNK_BUDGET_MS = 5;        // How long to hold the thread (heuristic)
  let start = performance.now();

  for (let i = 0; i < items.length; i++) {
    work(items[i]);

    // Budget not spent yet, so keep holding the thread.
    if (performance.now() - start < CHUNK_BUDGET_MS) continue;

    // Use scheduler.yield when it exists.
    // The continuation returns before other similar tasks.
    if (typeof scheduler !== 'undefined' && 'yield' in scheduler) {
      await scheduler.yield();
    } else {
      // Fallback. Goes to the back of the queue, and deep nesting clamps to 4ms.
      await new Promise((resolve) => setTimeout(resolve, 0));
    }
    start = performance.now();
  }
}

One retired piece of advice deserves flagging. The pattern of using isInputPending() to yield only when input is actually waiting circulated widely for a while. web.dev now states that it no longer recommends using this API, and recommends yielding regardless of whether input is pending or not, citing false negatives and incomplete scope. Code still sitting in older blog posts is better not copied forward.

Attaching priorities to work

Yielding alone is sometimes not enough, because who gets the seat you released is still undecided. The Prioritized Task Scheduling API handles that part. scheduler.postTask() accepts three priority levels, and MDN states that tasks are executed in priority order, and then in declaration order.

PriorityHow it is setWhat kind of work it belongs to
user-blockingStated explicitly in the optionsWork the user is waiting on that is holding up a screen update
user-visibleWhat you get if you omit it (the default)Work that is visible on screen but less immediate
backgroundStated explicitly in the optionsWork nobody is waiting for, such as precomputation or log shipping

If the priority may need to change later, you must not put the value directly in the options. MDN advises that for mutable priority you create a TaskController, pass its signal to the options, and adjust it with setPriority(). Work being computed leisurely in advance that suddenly becomes urgent because the user clicked something is exactly this case.

Nearby sits requestIdleCallback. MDN describes it as queueing a function to be called during the browser's idle periods, which enables background and low priority work on the main thread without impacting latency-critical events such as animation and input response. The callback receives an IdleDeadline, asks how much time is left with timeRemaining(), and checks didTimeout to see whether it was invoked because the timeout expired. Two caveats attach. A timeout option is strongly recommended for required work, and when that timeout elapses the callback is queued even if doing so risks causing a negative performance impact. Availability is not broad: MDN marks it as not Baseline because it does not work in some of the most widely-used browsers. This API does not appear in the original article.

What can leave, part one - computation that goes to a worker

Here is the heart of the matter. Among the jobs on the main thread, what can genuinely leave? The first exit is the web worker.

The worker boundary is drawn with unusual clarity. MDN states that you cannot directly manipulate the DOM from inside a worker, or use some default methods and properties of the window object. The main thing you cannot do in a worker is directly affect the parent page, which includes manipulating the DOM and using that page's objects. Because the global scope is DedicatedWorkerGlobalScope rather than Window, there is no window, no document, no parent. On the other hand fetch, XMLHttpRequest, timers, the standard built-in objects and importScripts() are all available.

The second thing to know is how data crosses the boundary. By default it is copied. In MDN's own words, data passed between the main page and workers is copied rather than shared, objects are serialized as they are handed over and deserialized on the other end, and the page and the worker do not share the same instance, so a duplicate ends up on each side. That is structured cloning. Shuttling a large array back and forth every frame therefore cancels out the benefit of moving to a worker with serialization cost.

Transferable objects solve this. Ownership moves wholesale, so no copy happens. MDN notes that when you transfer an ArrayBuffer to a worker, the original ArrayBuffer is cleared and no longer usable — its contents are, quite literally, transferred.

// main.js - do not copy a large buffer, hand over ownership instead.
const worker = new Worker('./heavy.js');
const pixels = new Uint8ClampedArray(width * height * 4);
// ... fill pixels ...

worker.postMessage(
  { buffer: pixels.buffer, width, height },
  [pixels.buffer]                 // the second argument is the transfer list
);
// After this line pixels.buffer is empty (byteLength === 0)

worker.onmessage = (e) => {
  const out = new ImageData(new Uint8ClampedArray(e.data.buffer), e.data.width);
  ctx.putImageData(out, 0, 0);    // touching the DOM happens here, on the main thread
};

// heavy.js - there is no DOM. Data comes in, data goes out.
self.onmessage = (e) => {
  const { buffer, width, height } = e.data;
  const buf = new Uint8ClampedArray(buffer);
  for (let i = 0; i < buf.length; i += 4) {
    const g = (buf[i] * 0.299 + buf[i + 1] * 0.587 + buf[i + 2] * 0.114) | 0;
    buf[i] = buf[i + 1] = buf[i + 2] = g;
  }
  self.postMessage({ buffer: buf.buffer, width, height }, [buf.buffer]);
};

Canvas has one exceptional doorway through this boundary. OffscreenCanvas decouples the DOM and the Canvas API so that the <canvas> element is no longer entirely dependent on the DOM. MDN explains that rendering operations can be run inside a worker context, allowing heavy work to be kept off the main thread. The mechanism is transferControlToOffscreen(), which detaches control and transfers it to the worker, and workers can even use requestAnimationFrame() with it. It is marked as available across browsers since March 2023. This API also does not appear in the original article.

What can leave, part two - motion that goes to the compositor

The second exit has a different character. You are not relocating code; you are meeting the conditions under which the browser will handle the work on another thread for you.

The Chromium document states that the compositor thread in the render process processes input, performs scrolling and animations, and coordinates image decodes and raster tasks. It then says that separating the main and compositor threads is critically important for performance isolation of animation and scrolling from main thread work. More concretely: animations of visual effects, and scroll, can skip layout, pre-paint and paint, and if those three can be skipped, they can be run entirely on the compositor thread and skip the main thread.

Translated into practice the rule is simple. Build a movement animation out of left and top and layout runs every frame, and that layout belongs to the main thread. Build the same movement out of transform and layout and paint are skipped, leaving only compositing. Opacity behaves the same way. That is the difference between an animation that stays smooth even while the main thread is busy and one that freezes the instant a script runs.

Scrolling follows the same principle, but here there is a common trap in which developers undo the benefit themselves: the passive option on event listeners. MDN explains that setting passive to true declares that the listener will not cancel the default action, so the browser can start the default action immediately without waiting for the listener to finish. Conversely, when a cancelable listener is attached the browser has no way to know whether preventDefault() will be called, so it has to wait. That waiting is scroll latency.

The defaults are worth knowing exactly. MDN states that passive defaults to false if unspecified, except that in browsers other than Safari it defaults to true for wheel, mousewheel, touchstart and touchmove on the document-level nodes Window, Document and Document.body. A touch listener attached to some specific element rather than a document-level node therefore still defaults to false. This is a place where writing { passive: true } explicitly is a habit worth having.

What cannot leave - where the boundary is drawn

Now the other side. Some work cannot leave no matter how you arrange it, and the reason is not performance but definition.

Work that has to touch the DOM

The absence of document in a worker is a design decision, not an unfinished implementation. The DOM is a mutable tree that cannot maintain consistency if multiple threads touch it simultaneously, so access was confined to a single thread. Accept that decision and style calculation and layout come along with it, because both have to read the DOM tree and the stylesheets. That is exactly what the Chromium document means when it lists the document lifecycle as main thread work.

Input that has to remain cancelable

Hit testing and event dispatching are in the same position. Determining which element sits at a coordinate requires up-to-date layout, and layout lives on the main thread. And the mere possibility that a listener might call preventDefault() is enough to make the browser wait. Even when scrolling is being handled on the compositor, the appearance of a cancelable listener forces the decision back to the main thread.

What you are trying to doDoes it leave the main threadWhy
Pure computation such as parsing, compression, sorting or pixel processingYes — Web WorkerIt does not use the DOM and its input and output are data alone
Drawing to a canvasYes — OffscreenCanvas plus a workerThe canvas can be detached from the DOM and its control handed to a worker
transform and opacity animationsYes — the compositor threadLayout, pre-paint and paint can all be skipped
ScrollingUsually — the compositor threadBut a cancelable listener forces the question back to the main thread
Reading and writing the DOMNoA worker has no window, document or parent
Style calculation and layoutNoThe document lifecycle is defined as main thread work
Running input event handlersNoScript event dispatching itself happens on the main thread
Hit testingNoIt has to read up-to-date layout in order to decide

The conclusion this table forces is fairly blunt. The best way to free the main thread is not to relocate work but to reduce it. Only the top four rows can move, and in real web applications the biggest consumers of time are usually in the bottom four.

Reducing the work itself - containment and skipping

The most structural way of reducing work is CSS containment. MDN explains that it enables the isolation of page subtrees from the rest of the DOM, letting the browser improve performance by optimizing the rendering of those independent parts. Each value of the contain property fences off something different. size isolates the element's size calculation from its contents, layout confines layout recalculation to the element and its descendants, style does the same for style recalculation, and paint confines painting to the element's bounds. content is shorthand for layout, style and paint combined, without size. strict adds size on top and is the most restrictive form.

The best-known place where containment turns into real gain is content-visibility. The web.dev document states that an element with content-visibility: auto gains layout, style and paint containment, and if it is off screen it also gains size containment. During that period the browser only styles and lays out the element box itself and stops painting and hit-testing its contents. In the travel blog example in the same document the rendering time dropped from 232 milliseconds to 30 milliseconds, which the document describes as a 7x performance boost.

/* Skip style, layout and paint for off-screen cards */
.feed-card {
  content-visibility: auto;

  /* Placeholder size used while the work is skipped.
     Without it, an off-screen element collapses to zero height
     and the scrollbar length keeps jumping around. */
  contain-intrinsic-size: auto 480px;
}

/* Use strict only where isolating size is also acceptable.
   strict = size + layout + style + paint */
.widget-frame {
  contain: strict;
  width: 320px;
  height: 240px;
}

contain-intrinsic-size specifies the natural size to use if the element is affected by size containment. Without it an off-screen element collapses to zero height and the scrollbar size shifts. web.dev calls this property a placeholder size in lieu of rendered content.

One thing needs care. Content skipped by content-visibility: auto can still be searched for on the page and navigated to, without waiting for it to load. That is both the difference from display: none or visibility: hidden and the advantage. Because of it, though, off-screen landmark elements also appear in the accessibility tree, so the documentation advises adding aria-hidden where that becomes clutter. In other words the performance win comes with a separate obligation to keep the accessibility tree tidy.

Reaching this point explains why the original article said the biggest gains usually come from deleting the work. What can be relocated is little, relocation itself carries cost, and work never performed consumes time on no thread at all.

Where this article diverges from the one that prompted it

The original gives prescriptions. It splits them into seven branches with examples, in a form you can pick up and use immediately, and the first three in particular — splitting, batching and prioritizing — are concrete enough to apply without any framework. The numbers in the original do not conflict with the ones here either: the 16.6 millisecond frame budget, the 50 millisecond long task threshold, and mentions of both INP and TBT are all present.

This article draws boundaries instead. If you settle what belongs where and why before reaching for prescriptions, you can judge for yourself where any new prescription fits when it appears. That is why the following three were brought in from outside the original.

  • Long Animation Frames — not in the original. The long task threshold alone cannot catch small tasks that collectively block a frame, and this API is what fills that blind spot
  • OffscreenCanvas — not in the original. It is the one practical hole in the rule that workers cannot touch the DOM, so a discussion of boundaries cannot omit it
  • requestIdleCallback — not in the original. It is the far end of the priority conversation, the oldest tool for the lowest tier, and its narrow availability has to be read alongside it
  • Conversely, content-visibility does appear in the original, which introduces it briefly as a property that aims for a similar effect in one line of CSS. This article opens up which kinds of containment it gains and which companion property it needs

A note on measurement: the sensation of delay and the number on the dashboard diverge more often than people expect. That gap is the subject of How We Agreed That Software Can Be Slow, while the link between coherent screen state and user trust is covered in Every Frame Perfect. What you lose when rendering moves into a canvas is handled in Drawing HTML Into a Canvas, and a concrete case of surviving huge lists through virtualization is already covered in Trees, a high-performance file tree rendering library, so none of those are re-explained here.

Finally, one ordering suggestion. Before touching code, find out which frame was late and why. Locate the responsible script with LoAF, then check which row of the table above that script's work belongs to. If it is in the top four, relocate it. If it is in the bottom four, reduce it. Getting that single judgement right eliminates time spent on optimizations that were never going to hold.

What could not be verified

  • The minimum delay for nested timers is written differently in different documents. The WHATWG HTML Standard specifies that if the nesting level is greater than 5 and the timeout is less than 4, the timeout is set to 4, while the web.dev long tasks article says 5 milliseconds. The body of this article uses the standard's value, but why the two documents differ could not be established
  • Whether the value returned by IdleDeadline.timeRemaining() has an upper bound such as 50 milliseconds could not be confirmed from the MDN documentation. It is a frequently quoted figure, but the specification sentence was not located directly, so it was left out of the body
  • The exact date on which INP replaced FID could not be confirmed. What was verified is the Core Web Vitals document's statement that INP became a stable metric in 2024, and the fact that the announcement post says only that today is the day
  • Whether the 50 millisecond threshold in Long Animation Frames can be adjusted, and whether there are plans to promote the metric to a Core Web Vital, could not be confirmed
  • Whether OffscreenCanvas supports a WebGPU context could not be confirmed from the MDN overview page, which demonstrates only 2D and WebGL
  • The 5 millisecond per-frame chunk budget proposed in the original is a heuristic rather than a specification. No source or justification for that value is given in the original, so it could not be verified. The code example here marks it as a heuristic
  • Safari's support for requestIdleCallback and scheduler.yield() was verified only as far as MDN's statement that it does not work in some of the most widely-used browsers and web.dev's note that Safari is unsupported; the per-version compatibility tables were not opened directly
  • The ordered substeps of the update the rendering algorithm in the WHATWG HTML Standard could not be confirmed, as the relevant section was truncated when the document was retrieved. The pipeline ordering in the body rests on the descriptions in web.dev and the Chromium architecture document
