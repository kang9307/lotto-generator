経緯 — 機能プレビューからデフォルト画面への移行

GitHub変更履歴（Changelog）の2026年10月1日付の項目「New dashboard experience now the default」は、機能プレビュー（feature preview）として提供されていた新しいダッシュボード体験が、全利用者の既定画面になったと記載している。変更履歴はこの画面を生産性重視（productivity-focused）のダッシュボードと呼び、最も重要な作業に集中でき、次に必要なものを見つけてすぐ着手しやすくなると説明している。項目の分類は改善（Improvement）である。

時系列は2つの出典を並べて初めて見える。コミュニティ告知（#208952）は9月28日に投稿され、すでに新ダッシュボードを全員の既定の体験にすると記載していた。変更履歴はその3日後の10月1日付で、「is now the default」と記載している。変更履歴は既定画面が実際に切り替わった日付を示していないため、10月1日から切り替わったと断定することはできない。

告知によると、GitHubは前年に生産性重視の新ダッシュボードを機能プレビューとして導入し、その後、多くの利用者が新旧両方のダッシュボードについてフィードバックを寄せた。告知はそのフィードバックに基づき、新ダッシュボードを全員の既定にすると記載している。告知が挙げる新ダッシュボードの機能は4つであり、変更履歴は同じ内容を3項目にまとめて記載している。各機能とGitHub Docsの記述は続く節で整理する。確認できなかった項目は、理由とともに「確認できなかった事項」の節にまとめた。

変更履歴に明記された新しいダッシュボードの主要構成

コミュニティ告知は、新ダッシュボードでできることを4項目で列挙している。変更履歴はそのうち1つ目と2つ目を1項目にまとめ、3項目で記載している。

  • 一箇所への集約: アクティブなエージェントセッション（active agent sessions）、Issue、プルリクエスト（pull requests）を一箇所で確認する。
  • フィルターと件数制限: フィルターで各セクションに表示する項目を選び、各リストには最大12件が表示される。
  • 独立したFeedタブ: リポジトリと組織の活動の更新は、独立した「Feed」タブで追う。変更履歴はこれを、フィードを生産性重視のダッシュボードと区別するものと記載している。
  • ダッシュボードからの作業開始: IssueをCopilotコーディングエージェントに割り当てることや、プルリクエストをCopilot Chatで開くことを例に挙げている。

告知は、この画面を現在の作業に集中して見られるようにし、次に何をするか決める助けになるよう設計したと記載している。12件という数字は、どちらの出典でも「各セクションをフィルターし、リストごとに最大12件を表示する」という1文にしか現れない。12件を超える項目の見方は両出典とも記載しておらず、GitHub Docsにあるのはエージェントセッション一覧のView allだけである（次の節）。

エージェントセッションとIssue・PRの統合 — 作業中心インターフェース

変更履歴は、エージェントセッション・Issue・プルリクエストを一箇所で見られるとだけ記載している。各リストに何が載るかは、GitHub Docsの「Personal dashboard」文書のうち「Home dashboard view」の項目が説明している。ただしこの項目は、更新されたホームダッシュボードをpublic previewで変更されうるものと記述し、見るにはまずfeature previewで「New Dashboard Experience」を有効にする必要があると記載している。既定画面になったという変更履歴と記述の時点が異なるため、以下のDocsの記述は既定化より前に書かれた文である可能性がある。

  • エージェントセッション: 実行中または過去のCopilot cloud agentセッションの一覧である。「View all」を押すとagentsタブが開く。
  • プルリクエスト: 自分が作成した、レビューした、メンションされた、またはレビュアーに指名された、直近のプルリクエストの一覧である。
  • Issue: 自分に割り当てられた、または自分が関わる直近のIssueの一覧である。
  • フィルターと12件: 変更履歴と告知の文言であり、Docsのホームダッシュボードの項目にはフィルターも12件という数字も出てこない。

同じDocs文書は、ホームダッシュボードとは別に「Recent activity」セクションも説明している。このセクションは直近2週間の更新を最大4件までプレビュー表示し、開いているIssueやPRが載る条件として、自分が開いた場合、自分が開いたものに他の人がコメントした場合、再オープンされた場合、レビューを依頼された場合、担当者に指定された場合、コミットで参照した場合、自分がコメントした場合を挙げている。「Top repositories」リストは自動生成され、直接編集できない。コミット、Issue・PRの作成やコメントなどのやり取りがあったリポジトリが載り、最後のやり取りから1年後に一覧から外れる。この2つが新ダッシュボードでどう表示されるかは、Docsが新ダッシュボードと結び付けて記述していない。

IssueとPRを扱う協業の考え方は、本ブログの過去記事 Git & GitHub協業マスター第4編：Pull Requestとコードレビュー で扱った。

Feedタブの分離 — ソーシャル・リポジトリ更新と業務領域の切り離し

変更履歴は、更新情報を独立した「Feed」タブで確認する形にして、フィードを生産性重視のダッシュボードと区別していると記載している。どの活動がフィードに載るかは、GitHub Docsの「Personal dashboard」文書の「Feed activity」の項目が列挙している。この項目は、新しいフィード（new feed）もpublic previewで変更されうるものと記載し、フォローしている誰かが挙げられた操作をしたときに更新が表示されると説明している。

  • Feedタブの定義（変更履歴・告知）: 変更履歴は更新をFeedタブで追うと記載し、告知はリポジトリと組織の活動を追う場所と記載している。
  • Docsのフィードイベント (1): フォローしている人がリポジトリにスターを付けたとき、他のユーザーをフォローしたとき、公開リポジトリを作成したとき。
  • Docsのフィードイベント (2): フォローしている人が、自分がウォッチしているリポジトリでhelp wantedまたはgood first issueラベルの付いたIssueやPRを開いたとき、自分がウォッチしているリポジトリにコミットをプッシュしたとき。
  • Docsのフィードイベント (3): フォローしている人が公開リポジトリをフォークしたとき、新しいリリースを公開したとき。「Quickstart」文書は、フィード右上のFilterドロップダウンで表示するイベントの種類を選べると記載している。

変更履歴はFeedタブにどのイベントが載るかを記載していないため、上のDocsの一覧がFeedタブの内容と同じかどうかは、両文書とも明記していない。確認できたのは、変更履歴がフィードを独立したタブにしていることと、Docsがフィードのイベントを上の種類として定義していることである。

ダッシュボード直結アクション — CopilotコーディングエージェントおよびChat連携

変更履歴は、ダッシュボードから直接作業を始める例を2つ挙げ、告知も同じ2例を記載している。GitHub Docsは、ホームダッシュボードのCopilot関連の要素を別に説明している。

  • IssueをCopilotコーディングエージェントに割り当て: 変更履歴は「assigning an issue to Copilot coding agent」を例に挙げている。
  • Copilot Chatでプルリクエストを開く: 変更履歴は「opening a pull request in Copilot Chat」を例に挙げている。
  • DocsのCopilotプロンプトボックス: ホームダッシュボードには、GitHub Copilotにプロンプトを送る、Copilot cloud agentにタスクを割り当てる、Copilotでissueを作成する、GitHub Sparkで構築を始める、ためのプロンプトボックスがあると記載している。
  • Docsクイックスタートのエージェント追跡: ダッシュボードからCopilotに直接プロンプトを送り、自分が起動した最新のエージェントセッションを追跡し、エージェントのログで進捗を確認し、結果のプルリクエストやタスクを管理できると記載している。

変更履歴は「Copilot coding agent」、Docsは「Copilot cloud agent」と記載しており、表記が異なる。ブラウザ上の開発環境の権限の問題は github.dev 1-クリックトークン奪取脆弱性分析 で、エージェントに渡す作業仕様は OpenSpec AIコーディングエージェント仕様 でそれぞれ扱った。

従来のダッシュボードに戻す手順 — Previewドロップダウン

変更履歴は、以前の体験を維持したい場合は「Preview」横のドロップダウンをクリックして、いつでも戻せると記載している。コミュニティ告知も、以前のダッシュボードを好む場合はPreview横のドロップダウンでいつでも戻せると記載している。

  • 操作位置: 「Preview」表記の横にあるドロップダウンをクリックする。
  • 切り替え時期: 変更履歴と告知の双方が「at any time」、つまりいつでもと記載している。
  • フィードバック窓口: 変更履歴は、質問や意見をCommunity discussionにコメントで残すよう案内している。告知は、生産性に役立つこと、妨げになること、最も改善してほしいことをコメントで求めている。
  • 後続の改善: 告知は、ここ数週間で多くの意見を受け取り、最も一貫して聞かれたテーマに基づいて、後続の改善の方向性をいくつか探っていると記載している。

告知は、その改善について今後数週間以内に共有すると記載し、その間（in the meantime）は以前のダッシュボードを好む場合にドロップダウンで切り替えられると案内している。

既存のコラボレーションフローとの関係と読み取り専用の確認

ダッシュボードが既定画面になった後、各項目をどの出典で照合できるかを表に整理し、設定を変更しない確認手順を添える。

リストの絞り込み各セクションに表示する項目をフィルターで選択フィルター条件の種類は出典に記載なし

確認は、設定を変更せずに次の順で行える。

  • ダッシュボードで、アクティブなエージェントセッション、Issue、プルリクエストの各セクションが表示されているか確認する。
  • 自分に割り当てられたIssueやレビューを依頼されたPRのうち、リストごとの12件の上限のためにリストに見えない項目がないか確認する。
  • Feedタブを開き、フォローしている人やウォッチしているリポジトリの活動が、Docsの列挙する種類どおりに表示されるか確認する。
  • 以前の画面が必要なら、「Preview」横のドロップダウンで切り替える。
  • 不便な点や改善案は、Community discussion（#208952）にコメントとして残す。

確認できなかった事項

  • GitHub Docsの2つの文書が既定化の後に更新されたかどうか。2つの文書は開けて、ホームダッシュボードをpublic previewとして、有効化をfeature previewの「New Dashboard Experience」として記述している。変更履歴が既定画面と記載した時点と記述が異なり、Docsには12件の制限、Feedタブの分離、以前の画面への切り戻しの記述がない。
  • 組織（Organization）やエンタープライズ（Enterprise）の管理者が、メンバーのダッシュボードの初期表示を以前の画面に固定できるポリシー制御の有無。どの文書にも記載がない。
  • リストごとの12件という表示件数をユーザー設定で変えられるかどうかと、12件を超えるIssueやPRの見方。DocsにあるのはエージェントセッションのView allのみである。
  • 「Preview」横のドロップダウンで以前の画面に戻せる機能がいつまで続くか。終了予定は記載されていない。
  • 外部の開発者コミュニティにおける非公式な反応や満足度統計。本稿は変更履歴・告知・Docsの文言のみを確認しており、公式文書ではない反応は確認の対象から外した。
