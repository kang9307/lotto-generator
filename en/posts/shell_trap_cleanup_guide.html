Intro: the cleanup is on the last line, and the script never got there

Picture a script that creates a temp directory, piles intermediate artifacts into it, and removes it on the final line. On a normal day nothing goes wrong. The trouble starts on the days that are not normal. An input file is missing so the script bails out with exit 1, CI cancels the job mid-deploy, or someone hits Ctrl+C in a terminal. Every one of those skips the cleanup, because the script never reached that line.

Leftovers accumulate quietly. A few 200MB working directories a day turns into a disk alert a few weeks later. And by then, opening one of those directories tells you almost nothing about which run produced it or when.

trap attacks this head on. It reframes the cleanup from a line to run at the end into code the shell must run when it exits. That sentence comes with a pile of exceptions, though. Some endings are caught and some are not, results diverge between shells, and a careless handler deletes things it should never touch.

Every command and output below was produced on GNU bash, version 5.2.37(1)-release and dash. Every delete ran only against paths created by mktemp under /tmp. If the shell fundamentals are not solid yet, Shell Script Basics and Shell Scripting Advanced come first.

1. One line that cleans up no matter how the script ends

The base form is short. Create the temp file, then register the command that removes it on EXIT.

#!/usr/bin/env bash
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'rm -f "$tmp"' EXIT

EXIT is not a signal. It is a pseudo-name for the moment the shell terminates, so a normal finish, an explicit exit 1, and a failure caught by set -e all pass through it. Here are all three paths, each run for real.

$ bash t1.sh ok
created: /tmp/work.Z8kaai
doing work
[trap] cleaning /tmp/work.Z8kaai
exit=0

$ bash t1.sh fail            # exit 1 in the middle of the script
created: /tmp/work.af0aeI
about to exit 1
[trap] cleaning /tmp/work.af0aeI
exit=1

$ bash t1.sh err             # a command fails while set -e is on
created: /tmp/work.cLzp5n
about to run a failing command
[trap] cleaning /tmp/work.cLzp5n
exit=1

The handler fired in all three cases and the original exit status survived. That much trap gives you unconditionally.

1.1 Single quotes and double quotes produce different results

A trap body gets two chances to be interpreted: once when registered, once when it fires. Which one expands your variables is decided by the quoting.

$ tmp=/tmp/first
$ trap "echo [double] would remove $tmp" EXIT   # double quotes: expands now
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[double] would remove /tmp/first

$ tmp=/tmp/first
$ trap 'echo "[single] would remove $tmp"' EXIT # single quotes: expands when it fires
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[single] would remove /tmp/second

The double-quoted version aims at /tmp/first, the value captured at registration time. In any script where the temp path is decided later or changes inside a loop, that difference is the whole bug.

  • Wrap trap bodies in single quotes by default
  • Once the body outgrows a single line, move it into a function and register just the name with trap cleanup EXIT. The quoting question disappears
  • A function also keeps the registration short, so trap -p output stays readable when you inspect it
  • Reach for double quotes only when you deliberately want a value frozen at registration time, usually while debugging

2. Why a temp file survives when you press Ctrl+C

This is where behavior actually diverges. What happens to a script armed only with EXIT when a signal kills it? I had the script signal itself to find out.

$ cat t4.sh
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'echo "[EXIT trap] rm $tmp"; rm -f "$tmp"' EXIT
kill -"$1" $$
sleep 5
echo "SURVIVED the signal"

$ bash t4.sh INT
pid=1349 tmp=/tmp/work.ZaHJMi  sending SIGINT to self
[EXIT trap] rm /tmp/work.ZaHJMi
exit=130 tmpfile=cleaned

$ bash t4.sh TERM
[EXIT trap] rm /tmp/work.By1Y9n
Terminated
exit=143 tmpfile=cleaned

On bash, an EXIT trap alone fired for SIGINT, SIGTERM and SIGHUP. The exit codes are correct too: 130 and 143, which are 128 plus the signal number.

2.1 But it does not fire under dash

Run the identical script under dash and the result flips.

$ bash /tmp/d2.sh          # EXIT trap only, self-sends SIGTERM
[EXIT] rm /tmp/work.LJpwWB
Terminated
  rc=143
  cleaned

$ dash /tmp/d2.sh
Terminated
  rc=143
  LEFTOVER /tmp/work.skxk0l

dash never ran the handler and left the file in place. Scripts whose shebang is #!/bin/sh are routinely executed by dash in production. If /bin/sh on your workstation is a link to bash, this difference is invisible until the leftovers start piling up on a real host.

2.2 Naming the signals makes dash behave

The fix is to list the signals next to EXIT.

cleanup() { rm -f "$tmp"; }
trap cleanup EXIT
trap 'cleanup; trap - INT;  kill -INT  $$' INT
trap 'cleanup; trap - TERM; kill -TERM $$' TERM
trap 'cleanup; trap - HUP;  kill -HUP  $$' HUP
$ dash /tmp/d3.sh
[cleanup] rm /tmp/work.Gjy9y6
Terminated
  rc=143
  cleaned

The part that matters is that the handler disarms its own trap with trap - INT and then kills itself with the same signal. Ending with a plain exit 0 makes the run look successful to whoever called it.

$ cat /tmp/reraise2.sh
trap 'echo "[INT] cleaning"; exit 0' INT
kill -INT $$

$ bash /tmp/reraise2.sh
[INT] cleaning
rc=0        # aborted, but reported as success

$ bash /tmp/reraise.sh      # cleans up, then re-raises the same signal
pid=587 tmp=/tmp/work.QAJTr9
rc=130      # 128+2, what the caller expects

CI runners and parent scripts use that exit code to tell «cancelled» from «failed» from «succeeded». Doing the cleanup perfectly and then corrupting the exit status defeats the point.

3. Which signals run your handler and which do not

I armed the same script two ways and sent one signal at a time. A registers only trap ... EXIT; B adds INT TERM HUP QUIT on top of EXIT.

SignalNo.A: EXIT onlyB: EXIT + signalsExit codeNote
SIGINT2cleanedcleaned130what Ctrl+C sends
SIGTERM15cleanedcleaned143the default for kill
SIGHUP1cleanedcleaned129terminal disconnect
SIGQUIT3script surviveshandler runs, script continues0ignored by default in non-interactive bash
SIGKILL9leftoversleftovers137cannot be caught

A and B look identical in that table, but this is bash. As section 2 showed, A collapses under dash. Once portability is on the table, B is the baseline.

3.1 SIGQUIT is ignored by default

That is the odd row out. A non-interactive bash script with no trap armed ignores SIGQUIT outright.

$ cat /tmp/q2.sh
echo "no trap armed; sending QUIT to self"
kill -QUIT $$
echo "survived"

$ bash /tmp/q2.sh
no trap armed; sending QUIT to self
survived
rc=0

Arm a trap and the handler does run. It just does not stop the script unless the handler itself calls exit.

$ bash /tmp/q1.sh
armed; sending QUIT to self
[QUIT handler] ran
survived (handler did not abort the script)
rc=0

dash produced the same result. Handling SIGQUIT explicitly is rare in practice, but it is a clean demonstration that the assumption «I trapped it, so the script will stop» can be wrong. The handler running and the script ending are two separate events.

4. Exactly what kill -9 leaves on disk

SIGKILL is never delivered to the process. The kernel removes the process itself, so the shell never gets a chance to execute anything. I interrupted a working directory holding five 64KB files with kill -9 and counted what stayed.

$ bash /tmp/leftover.sh &
$ sleep 1; kill -9 $!
$ du -sh /tmp/work.yURWz1; ls -1 /tmp/work.yURWz1
320K    /tmp/work.yURWz1
    chunk.1
    chunk.2
    chunk.3
    chunk.4
    chunk.5

The traps were armed on EXIT INT TERM HUP, and not one of them ran.

4.1 bash will happily let you trap KILL

This is the real trap. Rejecting it as a syntax error would be helpful. That is not what happens.

$ bash -c 'trap "echo caught" KILL; trap -p'
trap -- 'echo caught' SIGKILL
rc=0

The SIGKILL entry sits right there in the trap -p listing. A line like trap cleanup EXIT INT TERM KILL in code review reads as though KILL is covered, and that slot does absolutely nothing. It manufactures a sense of safety that is not there.

4.2 So the countermeasure lives outside the process

  • Give temp paths a fixed prefix. Creating them with mktemp -d /tmp/myjob.XXXXXX makes leftovers obvious at a glance
  • Have a separate sweeper collect old entries under that prefix. Filtering by last-modified time keeps it from touching live runs
  • For genuinely large artifacts, use a dedicated volume with headroom rather than /tmp, so leftovers cannot take down other services
  • Reduce the paths by which SIGKILL arrives in the first place. Container orchestrators and service managers usually escalate to KILL once the stop grace period expires, so finishing cleanup inside that window means you rarely see KILL at all
  • If cleanup takes tens of seconds, shorten the cleanup. Extending the grace period is the second move, not the first

5. Why only one of your two cleanups runs

Registering two traps for the same signal means the later one replaces the earlier one. They do not accumulate.

$ bash -c 'trap "echo first" EXIT; trap "echo second" EXIT; echo body'
body
second

No error, no warning. If two functions each register their own temp file on EXIT, only the one called later survives and the first cleanup vanishes silently. It bites hardest in codebases where library-style scripts are pulled in with source.

5.1 Stack the cleanup items and run them all at once

_cleanups=()
add_cleanup() { _cleanups+=("$1"); }
_run_cleanups() {
    for ((i=${#_cleanups[@]}-1; i>=0; i--)); do eval "${_cleanups[i]}"; done
}
trap _run_cleanups EXIT

add_cleanup "echo remove file A"
add_cleanup "echo remove dir B"
add_cleanup "echo release lock C"
$ bash /tmp/stack.sh
body
release lock C
remove dir B
remove file A

Running in reverse registration order is the point. If you took the lock first and created the directory afterwards, the release should remove the directory first and drop the lock last.

5.2 Appending to an existing handler

When something else has already armed a trap, you can read it back with trap -p and append.

add_exit() {
    local prev new
    prev=$(trap -p EXIT)
    prev=${prev#trap -- \'}
    prev=${prev%\' EXIT}
    if [ -z "$prev" ]; then new="$1"; else new="$prev; $1"; fi
    trap "$new" EXIT
}
$ bash /tmp/a1.sh
captured: trap -- 'echo first-handler' EXIT
now armed as: trap -- 'echo first-handler; echo second-handler; echo third-handler' EXIT
body
first-handler
second-handler
third-handler

It works, at two costs. First, the string surgery above breaks if the handler body itself contains a single quote. Second, trap -p is a bash extension and is unavailable in dash.

$ dash -c 'trap "echo x" EXIT; trap -p'
dash: 1: trap: Illegal option -p

Bare trap with no arguments does print a listing in dash. Parsing that output and feeding it back is even more delicate on the quoting front, so if portability matters, the array approach from 5.1 is the better answer.

$ bash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' SIGINT

$ dash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' INT

bash writes SIGINT, dash writes INT. Any checker that compares this output mechanically will trip over the difference.

5.3 How to remove a trap

trap - EXIT       # restore the default behaviour
trap '' INT       # ignore it (which is not the same as removing)

The second form has a side effect worth knowing. A signal set to ignored is inherited by child processes, and the child cannot undo it.

$ cat /tmp/ig.sh
trap '' INT
bash -c 'trap "echo child handler" INT; trap -p INT'

$ bash /tmp/ig.sh
trap -- '' SIGINT

The child ran trap "echo child handler" INT and the listing still shows an empty string, meaning ignored. A signal handed down as ignored cannot be re-armed by the child. If your script is a wrapper that runs another command, this inheritance strips that command of its Ctrl+C behavior.

6. How far traps follow into subshells, background jobs and functions

The fact that pipes and parentheses create an extra process is covered in Why Variables Vanish Inside a Piped while Loop. Traps move across that same boundary differently from variables.

6.1 A subshell inherits the trap but does not fire it on its own exit

$ cat /tmp/sub_t.sh
trap 'echo "[EXIT] fired in BASHPID=$BASHPID"' EXIT
echo "parent BASHPID=$BASHPID"
( echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t.sh
parent BASHPID=340
  inside subshell BASHPID=341
subshell rc=3
[EXIT] fired in BASHPID=340

The subshell is a separate process (341) and it terminated with exit 3, yet the handler ran exactly once, in the parent (340). You do not need to worry about the same cleanup executing twice. Conversely, a temp file used only inside a subshell needs its own trap in there.

$ cat /tmp/sub_t2.sh
trap 'echo "[parent EXIT] BASHPID=$BASHPID"' EXIT
( trap 'echo "  [subshell EXIT] BASHPID=$BASHPID"' EXIT
  echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t2.sh
  inside subshell BASHPID=344
  [subshell EXIT] BASHPID=344
subshell rc=3
[parent EXIT] BASHPID=343

A trap registered inside the subshell fires there when the subshell ends, and the parent's trap fires separately when the parent ends. They do not interfere.

6.2 Background jobs behave the same, and pipeline internals stay internal

$ bash /tmp/sub_t3.sh
parent BASHPID=346
  bg BASHPID=347
parent done
[EXIT] fired in BASHPID=346
$ bash /tmp/a2.sh
echo x | { trap 'echo "[inner EXIT]"' EXIT; cat > /dev/null; }
[inner EXIT]
parent continues
parent trap -p EXIT output:
(nothing between the two lines = the parent has no EXIT trap)

A trap set inside a pipeline component fires when that component ends and leaves nothing in the parent. If a trap seems not to be firing, check whether the line that arms it sits to the right of a pipe or inside parentheses.

6.3 A trap armed inside a function outlives the function

$ bash -c 'f() { trap "echo [EXIT] set inside f" EXIT; echo "in f"; }; f; echo "after f"'
in f
after f
[EXIT] set inside f

The EXIT trap is shell-wide state, not function-local. When a function registers its own temp file cleanup on EXIT, that registration stays until the script ends and overwrites whatever another function registered. Same root cause as section 5.

6.4 ERR and RETURN need an option to reach inside

The ERR trap fires when a command fails, but by default it does not descend into functions, subshells or command substitutions.

$ bash -c 'set -e; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
rc=1                       # the handler never ran

$ bash -c 'set -eE; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
[ERR] caught
rc=1

set -E is what makes ERR inherit into functions. For RETURN and DEBUG traps, set -T plays the same role.

$ bash -c 'trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g

$ bash -c 'set -T; trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g
[RETURN]

The firing order is settled too. On a failure, ERR comes first and EXIT second.

$ bash -c 'trap "echo [ERR]  seen" ERR; trap "echo [EXIT] seen" EXIT; set -e; false'
[ERR]  seen
[EXIT] seen
rc=1

Using ERR to record where the failure happened and leaving the actual cleanup on EXIT is the natural split. Note that ERR, RETURN and DEBUG are all bash extensions.

$ dash -c 'trap "echo err" ERR; false; echo done'
trap: ERR: bad trap
done

$ dash -c 'trap "echo ret" RETURN; f(){ :; }; f'
trap: RETURN: bad trap

7. Guards that stop a cleanup from deleting the wrong thing

Read this before the next section. Everything here has to be in place before the examples that follow. A cleanup script written carelessly deletes things it must not touch. Deletion is irreversible, and files removed by a script do not land in any trash bin. Until the three guards below are attached, keep a trap containing rm -rf off any machine holding real data.

7.1 Stop dead when the variable is empty

A trap fires at any point in the script, and the window before the temp path variable is assigned is a real window. If the delete command runs in that state, what it targets is anyone's guess.

cleanup() {
    : "${workdir:?cleanup called with no workdir}"
    ...
}

: is the builtin that does nothing, and ${var:?message} is the expansion that prints the message and stops the shell right there when the variable is empty. Together they form a one-line assertion.

$ bash -c 'cleanup() { : "${workdir:?cleanup called with no workdir}"; echo "would remove $workdir"; }
trap cleanup EXIT
echo body'
body
environment: line 2: workdir: cleanup called with no workdir

It stopped before reaching the delete. What happens without that line is described here, not demonstrated. rm -rf -- "$workdir" with an empty variable passes an empty string and usually just errors out, but the following common shapes behave very differently.

  • rm -rf "$workdir"/* — an empty variable turns this into /*, targeting everything directly under root
  • rm -rf "$base/$sub" — either half being empty leaves a stray slash and takes out one level above what you meant
  • cd "$workdir" && rm -rf . — if cd fails you are still in the current directory. Even with &&, a cd that succeeds into the wrong place proceeds happily
  • rm -rf $workdir — unquoted, a path containing spaces splits into several arguments, and whichever leading fragment happens to exist gets removed

None of these four are things to try out and see. Put the guard in first; write the delete second.

7.2 Pin the path

Being non-empty is not enough. Check that the value has the shape you expect.

cleanup() {
    : "${workdir:?}"
    case "$workdir" in
        /tmp/myjob.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
        *)            echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
    esac
}
$ bash /tmp/guarded.sh
workdir=/tmp/work.nGJBt5
removed /tmp/work.nGJBt5
rc=0

A mismatched prefix produces a warning instead of a deletion. If a later edit accidentally puts a different value in workdir, nothing is removed and the incident leaves a trace in the log.

7.3 Arm the trap first, create second

The reversed order is extremely common.

# fragile order: dying between these lines leaves the file behind
tmp=$(mktemp /tmp/work.XXXXXX)
... 40 lines of setup ...
trap 'rm -f -- "$tmp"' EXIT

The gap may look small, but a signal arriving in it leaves debris. Flip it around.

tmp=
cleanup() { [ -n "$tmp" ] && rm -f -- "$tmp"; echo "[cleanup] handled tmp=[$tmp]"; }
trap cleanup EXIT
tmp=$(mktemp /tmp/work.XXXXXX)
$ bash /tmp/race2.sh
trap armed before anything exists
created /tmp/work.35mmxL
[cleanup] handled tmp=[/tmp/work.35mmxL]

$ bash /tmp/race3.sh        # exits before mktemp
[cleanup] handled tmp=[]
rc=1

Dying before anything is created leaves the handler doing nothing at all, quietly. Pre-declaring with tmp= matters especially under set -u.

$ bash -c 'set -u; cleanup() { echo "rm -rf -- \"$workdir\""; }; trap cleanup EXIT; echo body'
body
environment: line 3: workdir: unbound variable

7.4 The points of no return

  • Interrupting a delete that has started does not help. Pressing Ctrl+C halfway through an rm -rf does not bring back what is already gone
  • A design that moves originals into the temp directory is dangerous. If they got there by move rather than copy, the cleanup trap is a trap that deletes your originals
  • If the target could be a symlink, confirm whether the delete follows it. Removing what you thought was just a link can remove the real data behind it
  • Using a network filesystem or shared volume as scratch space means another process may be using the same path. Put a process identifier in the prefix so they cannot collide
  • After changing the cleanup logic, swap the delete for an echo and run it once. Confirm with your eyes which path gets targeted, then put the delete back
  • The first time it goes on a production host, run it for a few days with mv into a quarantine directory instead of rm. Any unexpected path shows up during that window

8. One directory in, one directory out

When the job creates more than one file, grabbing a directory with mktemp -d and doing everything inside it is the better shape. The cleanup collapses to a single target.

#!/usr/bin/env bash
set -euo pipefail

workdir=
_cleaned=0

cleanup() {
    [ "$_cleaned" -eq 1 ] && return
    _cleaned=1
    trap '' INT TERM HUP
    if [ -n "$workdir" ] && [ -d "$workdir" ]; then
        case "$workdir" in
            /tmp/job.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
            *)          echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
        esac
    else
        echo "[cleanup] nothing to remove"
    fi
}

on_signal() {
    local sig=$1
    echo "[signal] SIG$sig received" >&2
    cleanup
    trap - "$sig" EXIT
    kill -"$sig" "$$"
}

trap cleanup EXIT
for s in INT TERM HUP; do trap "on_signal $s" "$s"; done

workdir=$(mktemp -d /tmp/job.XXXXXX)
echo "workdir=$workdir"

printf 'row1\nrow2\nrow3\n' > "$workdir/input.txt"
wc -l < "$workdir/input.txt"

All three paths were run and verified.

$ bash job.sh ok
workdir=/tmp/job.QoSGZJ
rows: 3
work finished
[cleanup] removed /tmp/job.QoSGZJ
rc=0
verified: /tmp/job.QoSGZJ gone

$ bash job.sh fail
workdir=/tmp/job.aHj3Nw
rows: 3
failing on purpose
[cleanup] removed /tmp/job.aHj3Nw
rc=1
verified: /tmp/job.aHj3Nw gone

$ bash job.sh signal
workdir=/tmp/job.ipwR33
rows: 3
signalling myself
[signal] SIGINT received
[cleanup] removed /tmp/job.ipwR33
rc=130
verified: /tmp/job.ipwR33 gone

Piece by piece, here is what went into that template.

  • workdir= is declared first, the trap is armed, and only then is mktemp -d called (7.3)
  • A _cleaned flag keeps the cleanup from running twice (section 10)
  • trap '' INT TERM HUP at the start of cleanup blocks further signals
  • case verifies the path prefix (7.2)
  • The signal handler cleans up and then re-raises the same signal at itself to preserve the exit status (2.2)
  • local sig=$1 lets one handler take its own argument, so you do not need a separate function per signal

8.1 Clean up child processes too

If you spawned background work, removing the directory is not enough. Orphans keep trying to use a path that no longer exists.

cleanup() {
    echo "[cleanup] killing $(jobs -p | wc -l) background job(s)"
    jobs -p | while read -r p; do kill "$p" 2>/dev/null; done
    : "${workdir:?}"
    rm -rf -- "$workdir"
}
$ bash /tmp/kids.sh
running with 2 children
[cleanup] killing 2 background job(s)
[cleanup] workdir removed
workdir gone: /tmp/work.47Wiqu

Order matters. Kill the children first, then remove the directory. The other way round has them writing into a vanished path and flooding the log with errors.

9. Where set -e and traps disagree

What happens to a trap handler in a script with set -e on? And what happens to the rest of the cleanup if the handler itself fails? That is where I started.

$ bash -c 'trap "echo [EXIT] start; false; echo [EXIT] still running; echo [EXIT] done" EXIT; echo body'
body
[EXIT] start
[EXIT] still running
[EXIT] done
outer rc=0

A failure mid-handler did not stop the rest, and the exit status was untouched. Turn on set -e inside the handler and the story changes.

$ bash -c 'cleanup() { set -e; echo "[cleanup] step 1"; false; echo "[cleanup] step 2 - NOT REACHED"; }
trap cleanup EXIT
echo body'
body
[cleanup] step 1
outer rc=1

Step 2 never ran. If the first delete inside the cleanup function fails, the second delete and the lock release are skipped wholesale. The exit status also flipped to 1, overwriting the original result.

  • Do not enable set -e inside a cleanup function. Cleanup is code that must keep trying even when it fails
  • A top-of-script set -e applies inside functions too, so putting set +e on the first line of the cleanup is sometimes the safe move
  • To absorb individual failures, use options that succeed on absence like rm -f, or append || true
  • To ignore a failure but still record it, use the || echo "..." >&2 shape instead

9.1 An exit inside the handler overwrites the exit status

$ bash -c 'trap "echo [EXIT] handler; exit 99" EXIT; exit 3'
[EXIT] handler
rc=99

$ bash -c 'trap "echo [EXIT] handler" EXIT; exit 3'
[EXIT] handler
rc=3

When the handler does not call exit, the original status is preserved exactly. Reflexively adding exit 0 to a cleanup handler makes failed runs report success. In an automated pipeline there are few worse defects.

9.2 exec does not take the trap with it

$ bash -c 'trap "echo [EXIT] should not print" EXIT; echo before-exec; exec echo after-exec'
before-exec
after-exec

exec replaces the shell process with another program. After the replacement that shell no longer exists, and neither does its EXIT trap. If a container entrypoint script ends by exec-ing the real program, any cleanup trap armed before that line will never run.

10. When a second Ctrl+C arrives mid-cleanup

With a cleanup that takes two seconds, I sent SIGINT three times at one-second intervals. This handler has no guard.

$ bash /tmp/reenter.sh
start (05)
  [cleanup] enter  (06)
  [cleanup] enter  (08)      <-- entered again before the first finished
  [cleanup] leave  (10)
  [cleanup] leave  (10)
end (16)

enter printed twice in a row. The cleanup code re-entered itself. Here is what that actually does.

  • It tries to delete the same directory twice. The second attempt errors because the target is gone
  • If the lock release runs twice, the second release can drop a lock the next run has just acquired
  • Code that rolls back a counter or trims a log gets applied twice and the value drifts
  • If the inner invocation finishes first and calls exit, the outer cleanup disappears halfway through

10.1 Use a flag and signal blocking together

_cleaned=0
cleanup() {
    [ "$_cleaned" -eq 1 ] && { echo "  [cleanup] already done, ignoring"; return; }
    _cleaned=1
    trap '' INT TERM HUP      # ignore signals while we work
    ...
}
$ bash /tmp/reenter2.sh
start (17)
  [cleanup] enter  (18)
  [cleanup] leave  (20)
end (26)

Same three SIGINTs, cleanup ran once. There is a reason for both layers.

  • The _cleaned flag prevents duplication when EXIT and the signal handler both call the same cleanup function
  • trap '' INT TERM HUP stops a fresh signal from invoking the handler again while cleanup is running
  • With only the flag, the second entry does return immediately, but the first cleanup has still taken an interrupt in the meantime
  • With only the blocking, duplication arriving via the EXIT path is unhandled. EXIT is not a signal and cannot be blocked

A long cleanup makes blocking dangerous too. The longer the window in which signals are ignored, the longer Ctrl+C does nothing at all. That ends in someone reaching for kill -9, which puts you right back in section 4. Keeping cleanup short is the best defence there is.

11. When the handler seems to run late

You have probably pressed Ctrl+C and watched nothing happen for several seconds. While the shell waits on a foreground child it defers trap execution. The signal is accepted right away; the handler runs once that child returns. Measured, it looks like this.

$ bash /tmp/measure.sh 5        # sleep 5 in the foreground, SIGINT at t+1s
  signal will arrive at t+1s
  [handler] ran at t+5s
  foreground sleep 5 returned at t+5s

$ bash /tmp/measure2.sh         # sleep 5 & in the background, waited on
  signal will arrive at t+1s
  [handler] ran at t+1s
  wait returned at t+1s

Same five-second wait, but one handler was four seconds late and the other was immediate. The difference is that wait is interruptible by a signal and a foreground sleep is not.

11.1 Making it respond faster

  • Convert long waits into sleep 300 & wait $!. A signal makes wait return immediately
  • Split it if you can. A loop of sleep 0.5 iterations had the handler running at t+1s
  • Backgrounding a long external command and waiting on it gives the same effect. Just remember to take its exit status from the return value of wait "$job"
  • This delay means cleanup is late, not missing. Hammering Ctrl+C out of impatience is what moves you into the re-entrancy problem of section 10
$ bash /tmp/defer5.sh
[04:37] waiting on background sleep 4
  >>> [04:38] TERM handler
rc=143

12. Locks that block a second run, and orphaned locks

The second most common use of a cleanup trap is releasing a lock. mkdir fails if the target exists, and the check and the creation happen as one operation, which makes it usable as a locking primitive.

lockdir=/tmp/myjob.lock
if ! mkdir "$lockdir" 2>/dev/null; then
    echo "another run holds $lockdir - exiting"
    exit 1
fi
trap 'rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
$ bash /tmp/lock.sh &          # first run
1854 holds the lock
$ bash /tmp/lock.sh            # second run, immediately after
another run holds /tmp/myjob.lock - exiting
second run rc=1
[cleanup] released /tmp/myjob.lock
lock released

12.1 A lock left by SIGKILL stays forever

Section 4's conclusion returns here. A kill -9 leaves the lock directory in place and no run can ever start again. That is more urgent than a filling disk. Writing owner information into the lock lets the next run make a judgement.

if mkdir "$lockdir" 2>/dev/null; then
    echo "$$" > "$lockdir/pid"
    trap 'rm -f "$lockdir/pid"; rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
else
    owner=$(cat "$lockdir/pid" 2>/dev/null)
    if [ -n "$owner" ] && kill -0 "$owner" 2>/dev/null; then
        echo "lock held by live pid $owner"
    else
        echo "STALE lock (owner $owner is gone) - safe to break"
    fi
fi
$ bash /tmp/lock2.sh &
acquired by 1862
$ bash /tmp/lock2.sh           # while the owner is alive
lock held by live pid 1862

$ kill -9 1862
$ bash /tmp/lock2.sh           # after the owner is gone
STALE lock (owner 1862 is gone) - safe to break

kill -0 sends no signal and only checks whether that process exists. The judgement has holes, though.

  • PIDs are recycled. If an unrelated process inherited the dead owner's number, you read it as alive
  • When several hosts share one lock on a shared volume, a PID check is meaningless. Record the hostname alongside it
  • Logic that breaks stale locks automatically creates a race of its own. Two runs can decide «stale» at the same moment
  • The safe compromise is not to break it automatically but to warn and exit, letting a human confirm and remove it
  • Recording a start timestamp with the owner makes the staleness judgement far safer

13. So which pattern do you use

Here is what each cleanup pattern catches and misses.

PatternNormal exitexit 1 · errorINT · TERMKILLPortability
rm on the last linecleanedleftoversleftoversleftoversevery shell
trap ... EXITcleanedcleanedcleaned on bash onlyleftoversweak on signals under dash
trap ... EXIT INT TERM HUPcleanedcleanedcleanedleftoversverified on bash and dash
above + re-raise and re-entry guardcleanedcleanedcleaned, status preservedleftoversbash, template in section 8
fixed prefix + external sweeper———cleaned laterthe only thing that covers KILL

That last row is the important one. trap alone cannot cover every case. Row three is the ceiling of what a script can do for itself; above that line the work belongs to machinery outside the script. Running both together is the real answer.

13.1 The minimum checklist

  • Move cleanup into a function and register it with trap cleanup EXIT. The quoting problem disappears
  • List INT TERM HUP next to EXIT. It looks unnecessary on bash and is necessary on dash
  • Signal handlers clean up, disarm with trap - SIG, then re-raise the same signal at themselves
  • The first line of the cleanup function is : "${var:?}". The second is the case path check
  • Pre-declare the variable empty, arm the trap, and only then call mktemp
  • Add a re-entry flag plus trap '' INT TERM HUP
  • Never call exit 0 inside a handler. Preserve the original exit status
  • Give temp paths a fixed prefix and run a separate job that sweeps old leftovers
  • If there are background children, kill them before removing the directory
  • Convert long waits to & wait to keep the script responsive
  • Remember that traps armed before a final exec in an entrypoint script will never run
  • Run it once under the shell you actually deploy with. Producing the tables in this article took a few minutes

14. What I could not verify

Everything in this article that was not verified by execution is collected here.

  • A real Ctrl+C typed at a terminal. All verification was done with non-interactive scripts sending signals to themselves or to a child. The case where a terminal delivers SIGINT to an entire process group, so the shell and its child receive it simultaneously, was not reproduced. Handler ordering could differ under that condition
  • A Linux glibc environment. The runtime here is bash 5.2.37 built for x86_64-pc-msys plus the dash from the same environment. The signal delivery layer is not necessarily identical to Linux. The SIGQUIT ignore behavior and the exit codes in section 3 in particular are worth reproducing once on your deployment target
  • zsh, ksh and busybox ash. No environment was available to run them. That combination is common in minimal container images, so it is a meaningful gap for real-world use
  • Locking based on flock. flock is not installed here, so section 12 was verified only with the mkdir approach. The property that the lock releases automatically when the file descriptor closes was not verified
  • Stop procedures of service managers and container orchestrators. Section 4 cites escalation to SIGKILL after the grace period as the basis for its advice, but no actual service definition was built to reproduce it
  • Delete latency on network filesystems. Section 7.4 warns about shared volumes as scratch space, but no actual latency or partial deletion was measured
  • How long large deletions take. Section 10 says to keep cleanup short without measuring rm -rf duration against file count
  • Older bash versions. Whether trap -p and set -E behave identically on much older releases was not checked

FAQ

Q1. Is one line of trap cleanup EXIT not enough?

If you only ever run under bash, it mostly is. Verified by execution, bash 5.2.37 ran the handler for SIGINT, SIGTERM and SIGHUP with nothing but EXIT armed. The problem shows up when the same script runs under dash: the handler did not run on SIGTERM and the temp file stayed on disk. A shebang of #!/bin/sh can be executed by dash in production, and if /bin/sh on your workstation links to bash you will never see the difference. Listing the signals explicitly costs one line, so just list them.

Q2. Can I end a cleanup handler with exit 0?

No. Verified, an exit 99 inside the handler overwrote an original exit status of 3 with 99. When the handler does not call exit, the original value is preserved. Attaching exit 0 to a cleanup handler makes every failed and every cancelled run report success. CI runners use that code to decide whether to retry, and parent scripts use it to decide whether to continue. Cleaning up perfectly and then corrupting the exit status throws away everything you gained.

Q3. If the trap handler errors, what happens to the rest of the cleanup?

By default it carries on. Injecting a false mid-handler still let every following line run and left the exit status alone. But enabling set -e inside the cleanup function stops it at the first failure. Verified, step 1 printed, step 2 never ran, and the exit status flipped to 1. Cleanup is code that must keep trying even after a failure, so do not enable set -e in it. Use delete options that succeed on absence, and append || true where a failure has to be absorbed.

Q4. Why is it a problem for each function to register its own cleanup on EXIT?

Because traps for the same signal overwrite rather than accumulate. Function A registers, function B registers, only B survives. On top of that, an EXIT trap is shell-wide state and outlives the function that armed it; it is not function-local. The way around it is to push cleanup items onto an array and register a single function on EXIT that walks the array in reverse. Reverse registration order also matches resource release order: if you took the lock first and created the directory second, remove the directory first and drop the lock last.

Q5. How do I clean up a temp file created inside a subshell?

Arm a separate trap inside that subshell. Verified by execution, a subshell inherits the parent's EXIT trap as a listing but does not execute it when it terminates; the handler fires once, in the parent. Conversely, a trap registered inside the subshell fires there when the subshell ends and leaves nothing in the parent. The same applies to traps set inside pipeline components. So when a trap appears not to be firing, the first thing to check is whether that line sits to the right of a pipe or inside parentheses.

Conclusion: three things to change today

First, move the cleanup off the last line and into a trap. Then list INT TERM HUP next to EXIT. It looks redundant on bash and it collapses without them on dash. Signal handlers should clean up, disarm their own trap, and re-raise the same signal at themselves so the exit status survives.

Second, make : "${var:?}" and a path check the first lines of the cleanup function. A trap fires at any point in the script, and the window before the variable is assigned is real. If a delete runs in that state there is no telling what goes, and what goes does not come back. That is why those two lines go before the delete, not after. When you change the logic, swap the delete for an echo and run it once to see the target path with your own eyes.

Third, do not believe trap covers everything. kill -9 is uncatchable, and the measurement left a 320KB working directory entirely intact. Because bash does not reject trap ... KILL as a syntax error and even lists it, reading the code suggests the case is handled. Giving temp paths a fixed prefix and running a separate job that sweeps old leftovers is the only way to fill a hole that can never be closed from inside the script.

One last thing. Every table and every output in this article came from scripts of about ten lines. If you are unsure whether your cleanup runs, stop guessing: create a file with mktemp and kill the thing. It takes thirty seconds.
