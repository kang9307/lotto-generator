gh-attach로 보는 GitHub 첨부 API 공백 - CLI 자동화의 우회로와 그 한계

브라우저 세션을 빌려 이슈·PR에 파일을 붙이는 CLI 도구는 무엇을 우회하고, 어디까지 믿을 수 있는가

2026-07-09 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 드래그 앤 드롭 하나가 전부인 기능

GitHub 이슈나 PR에 스크린샷 한 장 붙이는 일이 뭐가 어렵냐고 물을 수 있다. 웹 브라우저에서 이미지 파일을 끌어다 코멘트 창에 떨어뜨리면 그만이니까. 그런데 그 "드래그해서 떨어뜨리기"가 사실상 이 기능으로 들어가는 유일한 정문이라면 이야기가 달라진다. 2026년 7월 기준, GitHub는 이슈·PR·코멘트에 파일을 첨부하는 공식 REST·GraphQL API를 여전히 제공하지 않는다. 사람이 브라우저 앞에 앉아 마우스로 끌어다 놓아야만 열리는 문이다.

CLI로 이슈를 만들고, 봇이 배포 로그를 코멘트로 남기고, AI 에이전트가 스스로 PR을 여는 지금 이 문은 명백한 병목이다. gh-attach(sudosubin/gh-attach)는 이 병목을 정면 돌파하는 대신 옆으로 파고들어 우회한 도구다. GeekNews에도 소개돼 "필요했다"는 반응을 얻었는데, 이 글은 그 반응을 그대로 옮기는 대신 이 도구가 실제로 무엇을 우회하는지, 자동화 워크플로에서 어떤 값어치가 있는지, 그리고 어디까지 믿고 써도 되는지를 직접 따져본다.

1. 문제의 실체 - 왜 첨부 API가 없는가

1.1 드래그 앤 드롭이 실제로 하는 일

브라우저에서 이슈나 PR 코멘트 입력창에 이미지를 끌어다 놓으면, 프런트엔드 코드가 곧바로 github.com/upload/policies/assets로 요청을 보낸다. 이 요청이 통과하려면 user_session 쿠키, 즉 로그인한 브라우저 세션이 있어야 한다. 발급받은 업로드 정책으로 파일을 내부 자산 파이프라인(스토리지+CDN)에 올리고, 완료되면 github.com/user-attachments/assets/{uuid} 형태의 링크를 코멘트 본문에 끼워 넣는다. 이슈에서 흔히 보는 그 이미지 링크가 바로 이 과정의 결과물이다.

1.2 6년 가까이 반복된 요청

문제는 이 흐름이 처음부터 끝까지 세션 쿠키 기반이라는 점이다. 개인 액세스 토큰이나 OAuth로 인증하는 REST·GraphQL API에는 이에 대응하는 엔드포인트가 없다. GitHub Community 토론 여러 건에는 "코멘트에 이미지를 올리는 API를 달라"는 요청이 되풀이해 올라왔고, gh CLI 저장소의 한 이슈는 이 공백을 "에이전틱 워크플로에 결정적"이라는 표현으로 다시 제기하며 "에이전트가 완벽한 본문은 써도 정작 스크린샷은 못 붙인다"는 취지의 사례를 들었다. 이 요청의 계보는 2020~2021년까지 거슬러 올라가고, 해당 이슈 자체는 더 오래된 중복 이슈로 닫혔다. 즉 거의 6년째 같은 요청이 반복되지만 공식 API는 아직 없다.

2. gh-attach는 무엇을 우회하는가

2.1 브라우저가 이미 가진 세션을 빌려 쓴다

sudosubin/gh-attach(Go로 작성, MIT 라이선스)의 핵심 아이디어는 단순하다. 브라우저가 이미 갖고 있는 로그인 세션을 CLI가 빌려 쓰는 것이다. 먼저 gh api로 현재 인증된 GitHub 계정과 대상 저장소를 확인한다. 그다음 로컬에 설치된 Chrome 계열·Firefox 계열·Safari의 쿠키 저장소를 뒤져 dotcom_user 쿠키 값이 그 계정과 일치하는 세션을 찾는다.

2.2 업로드는 브라우저가 하던 그대로

세션을 확보하면 그 쿠키를 들고 /upload/policies/assets에 업로드 정책을 요청하고, 파일 바이너리를 올린 뒤 자산을 확정한다. 브라우저가 드래그 앤 드롭 때 수행하는 절차를 코드로 그대로 재현한 셈이다.

2.3 결과물은 웹에서 직접 붙인 것과 동일

그 결과로 나오는 URL은 github.com/user-attachments/assets/{uuid} 형태로, 사람이 직접 드래그해서 올린 이미지와 완전히 같은 종류의 링크다. gh attach ./image.png -R owner/repo 한 줄이면 URL을 받아 그대로 이슈·PR 본문에 붙일 수 있고, --json 옵션으로 스크립트에서 파싱하거나 --template으로 다른 명령과 엮을 수도 있다. 브라우저·프로필 지정은 ~/.config/gh/attach.yml 설정 파일에 저장해 매번 반복하지 않아도 된다.

3. CLI·자동화 워크플로에서의 가치

3.1 스크린샷·로그를 자동으로 붙이는 봇

가장 직접적인 활용은 배포 실패 로그, 시각 회귀 테스트의 스크린샷, 성능 그래프를 사람 손 없이 이슈·PR에 남기는 봇이다. 지금까지는 CI가 로그를 아티팩트로 남기고 사람이 다시 열어 캡처해 붙이는 두 단계였다면, gh-attach는 그 사이의 수작업을 없앤다.

3.2 에이전트가 PR을 스스로 열 때

AI 코딩 에이전트가 파일을 고치고 PR을 여는 흐름이 흔해지면서, 그 PR에 무엇이 바뀌었는지 보여주는 스크린샷이나 다이어그램을 함께 남기고 싶은 요구가 생긴다. 실제로 gh-attach 제작자도 에이전트가 다이어그램·스크린샷을 자동으로 첨부하도록 만들고 싶어 이 도구를 만들었다고 밝힌 바 있다. 텍스트만 있는 PR 설명과, 실제로 무엇이 달라졌는지 눈으로 보여주는 PR 설명은 리뷰어 입장에서 완전히 다른 경험이다.

3.3 gh CLI 확장 생태계 속의 위치

gh-attach는 gh extension install owner/repo 한 줄로 설치되는 gh CLI 확장이다. GitHub는 이 확장 시스템을 공식 문서로 지원하며, 누구나 gh-로 시작하는 저장소를 만들어 배포할 수 있다. 흥미로운 점은 같은 문제를 푸는 확장이 gh-attach 하나가 아니라는 것이다. 이름까지 겹치는 여러 독립 구현(예: enthus-appdev/gh-attach, MCP 서버까지 겸하는 Addono/gh-attach)이 동시에 존재한다. 이는 이 병목이 여러 개발자가 각자 부딪힐 만큼 흔하다는 방증이자, 동시에 아직 업계 "표준"이 없다는 뜻이기도 하다.

4. 비공식 엔드포인트 의존의 리스크

4.1 자동화용 도구인데 자동화 환경엔 안 맞는 역설

가장 먼저 짚어야 할 한계는 이것이다. gh-attach는 "에이전트·봇 자동화"를 내세우지만, 정작 동작 원리는 로그인된 브라우저 세션을 전제로 한다. 그런데 CI 러너나 에이전트 샌드박스 대부분에는 애초에 그런 세션이 없다. 자동화 파이프라인에서 그대로 쓰려면 미리 인증된 브라우저 프로필을 그 환경에 심어 두거나, 헤드리스 브라우저에 세션을 복사해 두는 별도 준비가 필요하다. "봇이 알아서 스크린샷을 붙여준다"는 그림은 이 준비를 마친 다음에야 성립하며, 이는 이 도구를 "완전 자동화" 도구로 오해할 때 가장 먼저 걸려 넘어지는 지점이다.

4.2 언제든 깨질 수 있는 계약

/upload/policies/assets는 GitHub가 공식 문서화하거나 버전을 보장한 API가 아니라 웹 프런트엔드 내부용 엔드포인트다. GitHub가 업로드 흐름을 바꾸면 예고 없이 동작이 멈출 수 있다. 이는 스크래핑 기반 도구가 공통으로 지는 부채이며, 관련 논의에서도 이런 우회 방식은 "임시방편"으로 규정되고 공식 API 확보가 장기 목표로 남아 있다.

4.3 쿠키를 읽는다는 것의 무게

로컬 브라우저의 쿠키 저장소를 읽는 것은 가벼운 일이 아니다. 일부 운영체제는 키체인·자격 증명 관리자 접근 권한을 요구하고, 브라우저 자체도 쿠키를 OS 레벨로 암호화하는 경우가 있다. 신뢰하는 오픈소스 도구라 해도, 로그인 세션 쿠키에 접근하는 CLI를 설치한다는 것 자체가 보안 표면을 넓히는 선택이라는 점은 분명히 인지해야 한다.

5. 공식적인 대안과의 비교

GitHub CLI 커뮤니티도 이 문제를 모르지 않는다. gh-attach식 세션 우회 외에, 토큰 인증만으로 되는 대안 두 가지가 함께 논의돼 왔다.

방식인증결과 URL장점단점
gh-attach(세션 우회)브라우저 쿠키user-attachments/assets 링크웹 UI와 동일한 결과, 즉시 사용비공식 엔드포인트, CI엔 별도 준비 필요
gh release uploadPAT/토큰릴리스 자산 다운로드 링크공식 API, 토큰만으로 CI에서 동작릴리스 목록 오염, 임시 첨부엔 과함
orphan branch + raw URLPAT/토큰raw.githubusercontent.com 링크공식 API, 릴리스 오염 없음파일이 히스토리에 영구 잔존, 자동 정리 안 됨

개인적인 판단은 이렇다. 사람이 잠깐 쓰는 수동 첨부라면 gh-attach가 가장 자연스럽다. 항상 켜져 있는 CI 봇이 습관적으로 로그를 남기는 용도라면, 세션 관리 부담이 없는 release asset 쪽이 운영상 더 안전하다. orphan branch 방식은 두 조건을 다 만족 못 시키는 경우의 절충안 정도로 본다.

결론: gh-attach는 임시방편이지 최종 해법이 아니다

gh-attach는 훌륭한 임시방편이다. GitHub가 이슈·PR 첨부용 공식 API를 내놓기 전까지는, 이런 종류의 세션 우회 도구가 계속 나올 수밖에 없는 구조이고, 이름이 겹치는 여러 독립 구현이 존재한다는 사실 자체가 그 수요를 증명한다. 지금 당장 CLI에서 스크린샷 하나 붙이고 싶다면 gh-attach로 충분하다.

다만 CI나 에이전트 파이프라인에 얹으려면 세션 준비라는 숙제가 남아 있다는 점, 그리고 이 도구가 딛고 선 엔드포인트가 GitHub의 뜻에 따라 언제든 사라질 수 있는 비공식 계약이라는 점은 계속 염두에 둬야 한다. 진짜 해법은 GitHub가 토큰 인증만으로 되는 공식 업로드 API를 내놓는 것이고, 그전까지 gh-attach는 그 공백을 메우는 여러 실험 중 하나로 보는 것이 정확하다.
