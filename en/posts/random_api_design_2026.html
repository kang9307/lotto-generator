If I Were to Redesign a Random Number API - Reproducibility, Safety, Consistency

Two families, seeds, ranges, shuffles and global state, measured by running them and turned into design rules

2026-08-01 Development/Infrastructure

Introduction: a failure that would not reproduce, and two functions with the same name

A check driven by generated input tripped once. The log said only that a value did not match. Rerunning it passed. Ten more runs passed. Whichever input broke it disappeared the moment the process exited.

While looking for the cause, something else turned up first. The code producing that input and the code minting the token in a password reset link were calling functions with nearly the same name. One was a statistical generator and the other a security one. From the call site alone there was no way to tell which was which.

The two look like separate accidents but share one root. The hard part of a random number API is naming and defaults, not the algorithm. Which generator to use, whether to accept a seed, how to cut a range: all of it is surface design, and when the surface is vague the calling side is guaranteed to get it wrong.

So it was all run for real. Every number below came from executing it in this runtime. Four things were confirmed.

  • The name hides the family. When both families share a word, the call site tells you nothing
  • Without a seed you cannot see a bug twice. Reproducibility is a precondition for debugging, not a convenience
  • Cutting a range skews the distribution. And that skew is either obvious or permanently invisible depending on the width of the source
  • One global generator holds reproducibility hostage. Even with a fixed seed, changing the consumption order changes the result

Environment. Every output below was produced by actually running it on Windows 10 Pro (10.0.19045) with Node.js v22.16.0 (win32 x64). The statistical generator is a hand-written splitmix32 with 32 bits of state; the security side uses the cryptographic random interface this runtime provides. All scripts were saved to files and executed. Sample sizes are stated per item in the text.

What this post does not cover. How predictability is exploited is not covered. Only the property that a statistical generator is predictable is confirmed; no procedure for using that property is written down. A server that returns deliberately blurred values and the storage cost of using a random identifier as a primary key each have their own post. Whether a check depends on execution order is also out of scope here. This post looks only at the surface of the random API itself.

1. One name, two families

First the random-related calls this runtime offers were laid out and labelled by family. Then a single line of real code was put on its own to see whether the family is visible.

--- 1-1. every one of these has "random" in the name ---
call                          family        seedable  sample output
--------------------------------------------------------------------------------------------
Math.random()                 statistical   no        0.4962049585478472
crypto.randomInt(0, 100)      security      no        57
crypto.randomBytes(4).hex     security      no        16ca5c5e
crypto.getRandomValues(u32)   security      no        4091828560
crypto.randomUUID()           security      no        9ba23fe3-3912-4644-9d45-3025617158a5
seeded splitmix32(42)         statistical   YES       551831576

--- 1-2. can you tell the family from the call site alone? ---
const pick   = Math.random();                           statistical   
const nonce  = crypto.randomInt(0, 1e9);                security-grade
const shard  = Math.random() * 16 | 0;                  statistical   
const token  = crypto.randomBytes(16).toString("hex");  security-grade
const jitter = Math.random() * 200;                     statistical   
const id     = crypto.randomUUID();                     security-grade

Of six call sites, three are statistical and three are security. And all six carry the same word in the name. Skimming these lines in a code review, judging which is which means having memorised the callee list.

  • The seedable column decides everything. Only the statistical family accepts a seed; the security side has no place to put one
  • Yet that property is nowhere in the name. You learn it from the documentation, and without the documentation you do not learn it
  • Whether the variable is called token or jitter is the only hint, and variable names are not enforced
  • Catching it with static analysis means tracing whether the value ever leaves the process, which is hard in the general case

1.1 Why two families exist - throughput measured in this runtime

There is a reason for the split. How large that reason actually is was measured, together with how each family reacts to bad arguments.

--- 1-4. the security call has limits the statistical one does not ---

getRandomValues(Float64Array)     TypeMismatchError: The data argument must be an integer-type TypedArray

The difference is real, but its nature is interesting. Called one word at a time the security path was 175 times slower, and requested 4,096 at a time it came within 1.3 times. Most of the cost was per-call overhead, not the algorithm.

  • The reasoning that the security family is too slow is usually weak. Batched, the gap disappears for most workloads
  • The security call has a ceiling of 65,536 bytes per request and throws past it. That ceiling itself expresses the intent to batch, but not without bound
  • It rejects a non-integer array type outright, and it throws on the spot when the minimum exceeds the maximum
  • The statistical call, by contrast, quietly ignored extra arguments. Passing something that looks like a seed changed nothing. Code that mistook it for a seed will never reproduce

2. A seed is a precondition for debugging, not a convenience

Back to the first symptom. A check driven by generated input tripped and the input is unknown. With a seed that situation does not arise at all.

A function that divides by a span and returns infinity when the span is zero was checked 500 times against generated input, once with the seed recorded in the report and once without.

All three replays pointed at the same iteration and the same input. At that point the failure stops being a random event and becomes a fixed value you can quote. It goes into the fix commit verbatim, and the same value verifies the fix.

--- 2-5. what a seed buys, measured ---
property                              seeded    unseeded
----------------------------------------------------------------------------
can rerun the exact input set         yes       no
failure report is a fixed value       yes       no
fix can be proven against the case    yes       not the same case
unpredictable to an outside party     no        no (both are statistical)
safe for tokens and secrets           no        no

Five runs of the same check put the first failure at iteration 8, 52, 119, 14 and 32. The failure count wandered between 9 and 19. In this state there is no way to prove the fix worked, because a clean run afterwards is indistinguishable from luck.

  • The seed has to be part of the failure report. A seed that is never logged might as well not exist
  • The last two rows of the table matter. Seeded or not, a statistical generator is predictable, and neither form is fit for producing a secret
  • In other words, having a seed is a question on the reproducibility axis, not the safety axis. Mixing the two axes blurs the judgement
  • In practice the seed is often deferred as something to add when needed, but the moment it is needed is already too late

3. Cutting a range skews the distribution

The most common way to move a random value into a range is the modulo operator. A million eight-bit values were taken modulo 100 and the distribution counted. A small range, a die roll, was measured alongside.

--- 3-1. modulo on an 8-bit source, bound = 100 ---
256 = 2 * 100 + 56   -> values 0..55 have 3 preimages, 56..99 have 2
theoretical p(low)  = 1.1719%   p(high) = 0.7813%   ratio = 1.500
measured  mean(0..55) = 11715.7   mean(56..99) = 7816.4   ratio = 1.499
measured  min = 7615  max = 11917  expected if fair = 10000
chi-square (df 99) = 37546   (fair sample lands near 99)
first 8 buckets  : 11623 11596 11859 11710 11869 11676 11634 11520
buckets 56..63   : 7949 7884 7659 7807 7886 7615 7881 7824

--- 3-2. same bug, small bound = 6 (a dice roll) ---
256 = 42 * 6 + 4
face       :         1        2        3        4        5        6
count      :    167301   167670   168621   167747   164466   164195
share      :   16.730%  16.767%  16.862%  16.775%  16.447%  16.419%
expected fair share 16.667% each
chi-square (df 5) = 104.1   (fair sample lands near 5)
theoretical excess of faces 1..4 = 2.38%

The reason is one line of arithmetic. 256 divided by 100 gives a quotient of 2 and a remainder of 56. Values 0 through 55 have three paths and 56 through 99 have two. So the low values appear exactly 1.5 times as often. The measured 1.499 matched the theory.

The die has the same shape. 256 over 6 leaves a remainder of 4, so faces 1 through 4 come up 2.38% more often. By eye that reads as noise, yet the chi-square of 104.1 is more than twenty times what 5 degrees of freedom expects.

3.1 On a wide source the same bug is invisible forever

Here is the core of this section. The identical modulo was applied to a 32-bit value over the same million draws, and the cost of removing the bias was measured alongside.

--- 3-3. same "% 6" on a 32-bit source: bias still there, invisible ---
2^32 = 715827882 * 6 + 4
theoretical excess of faces 1..4 = 1.397 parts per billion
count      :    166645   166580   166318   167237   166273   166947
chi-square (df 5) = 4.1   -> indistinguishable from fair
draws needed to see this bias at all: about 512410 x 10^12

--- 3-4. rejection sampling removes the bias at a measurable cost ---
accept only bytes < 200 (= 256 - 256 % 100), then take % 100
measured  min = 9708  max = 10279  expected = 10000
chi-square (df 99) = 104   (fair sample lands near 99)
rejected 280146 of 1280146 bytes = 21.88%  (theory 21.88%)
worst-case rejection rate for an 8-bit source is just under 50% (bound = 129)

The 32-bit run came out at chi-square 4.1, indistinguishable from a fair sample. The bias did not vanish; at 1.4 parts per billion it simply cannot be seen. Detecting it statistically would take a sample on the order of ten to the seventeenth. It becomes a bug no check will ever catch.

Source widthRangeExcess on low valuesVisible in 1e6 drawsPractical verdict
8-bit62.38%yesshows up at once, easy to fix
8-bit10050%yesthe most dangerous pairing
8-bit1000744 values never appearyesrange wider than the source

Read the table this way. The top rows are bugs that get caught quickly; the bottom rows are bugs that never get caught. Yet the code looks identical on both sides. That is why nothing has gone wrong so far is not evidence.

  • A byte-wide source with a narrow range is the pairing that causes the most accidents. Draws, dice and card picks all live there
  • Rejection sampling accepts only up to the exact multiple of the range and drops the tail. Eight bits with a range of 100 discards 21.88% and buys zero bias
  • On a 32-bit source the rejection cost was 1.00 draws on average and 2.00 at worst, which is not a practical problem
  • The surest fix is for the library to ship this function. When callers rebuild it each time, half get it wrong
// unbiased bounded integers - the code a caller should never have to write again
function intBelow(next, n) {                     // next() returns a uint32
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width (2^32)');
  const limit = 4294967296 - (4294967296 % n);   // largest exact multiple of n
  let v;
  do { v = next(); } while (v >= limit);         // drop the ragged tail
  return v % n;
}

function intBetween(next, lo, hi) {              // closed range, both ends included
  if (!Number.isInteger(lo) || !Number.isInteger(hi)) throw new TypeError('intBetween takes integers');
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}

The rounded distribution stands out. The endpoints sit at 5.01% and the interior at 10.00%, exactly half. Rounding maps 0 and n onto intervals of half the width. Use that idiom in a draw or a tier assignment and only the two end tiers quietly become rare.

  • The interval is half-open. Across five million draws neither an exact 0 nor an exact 1 appeared; the smallest observed was 1.8e-7
  • Truncating with a bitwise operator goes negative past two to the thirty-first. A span of five billion produced -544,967,296
  • A single float carries at most 53 bits. Ask for a wider range and some values can never come out
  • To include both ends, do not round: add one to the bucket count and floor. That is the second row of the table
  • To keep callers from deciding this every time, the API has to state open or closed in the name

5.1 Why the broken shuffle cannot be uniform in principle

--- 5-3. why broken Fisher-Yates cannot be fair, by counting ---
length 3 :       27 equally likely swap paths spread over    6 permutations           27 / 6 = 4.5000  <- not an integer, cannot be uniform
length 4 :      256 equally likely swap paths spread over   24 permutations         256 / 24 = 10.6667  <- not an integer, cannot be uniform
length 5 :     3125 equally likely swap paths spread over  120 permutations       3125 / 120 = 26.0417  <- not an integer, cannot be uniform
length 6 :    46656 equally likely swap paths spread over  720 permutations      46656 / 720 = 64.8000  <- not an integer, cannot be uniform
correct Fisher-Yates draws from 0..i, giving exactly n! paths for n! outcomes

--- 5-4. the comparator version also depends on the sort algorithm and length ---
length   2 : P(element 0 stays at index 0)  comparator   49.84%   Fisher-Yates   50.02%   fair value 50.00%
length   3 : P(element 0 stays at index 0)  comparator   43.62%   Fisher-Yates   33.35%   fair value 33.33%
length   4 : P(element 0 stays at index 0)  comparator   35.96%   Fisher-Yates   25.06%   fair value 25.00%
length   8 : P(element 0 stays at index 0)  comparator   22.13%   Fisher-Yates   12.45%   fair value 12.50%
length  16 : P(element 0 stays at index 0)  comparator   13.26%   Fisher-Yates    6.26%   fair value 6.25%

Counting alone proves it. Drawing the swap partner from the whole array gives n to the power n paths spread over n factorial outcomes. For four elements 256 over 24 is 10.667, not an integer. Equally likely paths cannot be handed out in whole numbers, so uniformity is impossible. The correct form draws the partner only from 0 up to the current index, which yields exactly n factorial paths.

  • The comparator shuffle gets worse as the array grows. At length 16 the first element stayed in place 13.26% of the time, twice the fair 6.25%
  • The same code produces a different distribution depending on the sort implementation, which means the result changes when the runtime does
  • A comparator assumes that comparing the same two elements always gives the same answer, and a random comparator breaks that assumption
  • The conclusion matches section 3. The library has to ship the shuffle. If it does not, the comparator trick will appear

6. Where the security family is required

Now to how the difference between the families shows up in the output. The same token function was placed on top of a statistical generator and a security one.

One thing up front. This section only confirms the property that a statistical generator is predictable. How that property is used, or by what procedure a next value would be derived, is not covered.

--- 6-1. a reset token built on a statistical generator ---

Two services starting from the same seed produced three 24-character tokens that were identical. A statistical generator is its state and nothing more. And this is exactly the property section 2 asked for. The same feature earns opposite verdicts: a virtue where reproduction matters, a defect where a secret is being minted.

What this post withholds. No procedure for exploiting predictability is written here, because the property alone is enough for the decision that matters. The single fact that the value is fixed once the state is fixed is reason enough not to use it as a secret. The opposite kind of safety claim, that something is hard to work out, collapses as techniques improve; the structural fact does not change.

csrf token, nonce, salt         security      security relies on it being fresh
temporary file name             security      a name others can anticipate is a hazard
lottery or prize draw           security      money plus an outside party

one line rule: if a stranger holding the value gains something, it is the security family

The third column carries the decision. Eight hex characters is 32 bits, so 77,000 values already put the collision probability at half. Twenty-two characters from a 62-symbol alphabet is 131 bits, with more headroom than any real system will use. The other thing to notice is that token length is not entropy. A generator with 32 bits of state cannot exceed 32 bits no matter how long the token is.

  • The rule is one line. Does a stranger holding the value gain something? If so, it is the security family
  • When unsure, take the security family. One mistake costs speed; the other cannot be undone
  • Using a universally unique identifier directly as a secret means accounting for the format eating fixed bits: 6 of 128 are pinned by the version and variant fields
  • Temporary file names are on the list because whoever can anticipate the name can occupy the spot first. Unpredictability is the requirement there

7. One global generator breaks reproducibility

Section 2 bought reproducibility with a seed. That reproducibility breaks more easily than expected. A global generator with a fixed seed was shared by two components and only the consumption order was varied three ways.

--- 7-1. one global generator, two consumers, two interleavings ---

------------------------------------------------------------------
A A A B B B           201 652 582           38 515 449
B B B A A A           38 515 449            201 652 582
A B A B A B           201 582 515           652 38 449

same seed, same code, three different results for A: 3 distinct sequences out of 3
the seed pins the stream. it does not pin who draws from it, or when.

Same seed, same code, and component A saw a different sequence in all three. A seed pins the stream but not who draws from it, when, or how many. Handing each component its own generator made all three orders agree.

Two runs differing only in timing produced different results, while the side with its own generator was unchanged by timing. A global generator turns every consumer into a hidden dependency of every other one. One extra draw somewhere changes the result of unrelated code elsewhere.

  • The shape worth adopting is a child generator per unit of work, derived from a parent seed and a work identifier
  • Then the units can run in parallel or in a different order and each unit keeps its own sequence
  • An API that offers a global generator looks convenient, but it trades away all of reproducibility for that one convenience
  • No amount of careful seed management fixes this. It is a structural problem, not a value problem

8. Redesigned - names, seeds, ranges, defaults

A surface that blocks every trap from the previous seven sections was actually built and run. Four rules: put the family in the name, make the seed explicit, ship range helpers, and let the default be the cautious one.

// the family is in the constructor name, and the seed is not optional
function statisticalRng(seed) {
  if (!Number.isInteger(seed)) throw new TypeError('statisticalRng(seed) requires an explicit integer seed');
  const api = core(splitmix32(seed));    // deterministic engine
  api.seed = seed;                       // the value that goes into a failure report
  api.kind = 'statistical';
  return api;                            // an instance, never a module-level singleton
}

const secureRandom = (() => {
  const pool = new Uint32Array(1024);    // batched: per-call overhead was the cost, not the algorithm
  let i = pool.length;
  const u32 = () => { if (i >= pool.length) { crypto.getRandomValues(pool); i = 0; } return pool[i++]; };
  const api = core(u32);
  api.kind = 'security';
  api.token = (chars = 22) => { /* ... */ };     // exists only on this object
  return api;                            // no seed parameter, so none can be passed
})();

// one shared surface, so range and collection helpers read the same on both
function core(u32) {
  return {
    intBelow:     (n) => bounded(u32, n),                      // [0, n)  half-open, the name says below
    intBetween:   (lo, hi) => lo + bounded(u32, hi - lo + 1),  // [lo, hi] closed, the name says between
    unitInterval: () => u32() / 4294967296,                    // [0, 1)  named after its range
    pick:         (arr) => arr[bounded(u32, arr.length)],      // no index arithmetic at the call site
    shuffled:     (arr) => { /* Fisher-Yates on a copy */ },   // past tense: returns a copy
  };
}

The point is that the two constructors have different shapes. The statistical one cannot be built without a seed, and the security one has no place to put one. The surface enforces it without anyone reading the documentation. That surface was then run back through the three earlier traps.

  • Array helpers should return a copy instead of mutating in place. A past-tense name announces that
  • The reproducibility contract belongs in the documentation too. Whether the same seed yields the same sequence across versions is a real promise for deterministic uses
  • Offer a fast path if one is needed, but give it a long and explicit name so it is never chosen by accident

9. In closing - the hard part is names and defaults, not algorithms

Everything measured here reduces to one sentence. What goes wrong with randomness is usually not the generation but the surface that handles the value. The algorithms have settled answers and a library can carry them. What decides how often accidents happen is which names that library exposes and what they expose.

Two things in particular. First, when the statistical and the security family share similar names, the accident is guaranteed. In the measurement six calls split three and three, and names alone did not separate them. That is a defect in the surface, not carelessness in the user.

Second, reproducibility is not nice to have, it is the precondition for debugging. Without a seed a failure cannot be quoted, and what cannot be quoted cannot be proven fixed. Make the seed optional and nobody passes it, which is why it has to be required.

  • Does a stranger holding the value gain something? That one line splits the families
  • Do not cut ranges with the modulo operator. On a narrow source it shows immediately, on a wide one it never shows
  • Do not build integer ranges with rounding. The endpoints end up at half weight
  • Do not shuffle with a comparator. The result depends on the sort implementation and the array length
  • Do not share a global generator. Reproducibility becomes hostage to call order
  • Do not add the seed later. The moment it is needed is already too late

# Random API Checklist — Statistical vs Security, Ranges, Shuffles, Seeds

> Source: braindetox.kr — If I Were to Redesign a Random Number API
> Basis: verified by running on Windows 10 / Node.js v22.16.0 (win32 x64), 2026-08-01

## 1. One question splits everything

**Does a stranger gain something by holding this value?**

- Yes → **security family**. Tokens, sessions, password reset links, invite codes, temp file names, prize draws
- No → **statistical family**. Sampling, jitter, A/B assignment, synthetic check data, visual effects

When unsure, take the security family. Using the security family where the statistical one
would do costs only speed. The mistake in the other direction cannot be undone.

## 2. Which family for which job

| What you are generating | Family | Seed | Why |
|---|---|---|---|
| Session identifier | security | none | the value itself grants access |
| Password reset token | security | none | the value itself grants access |
| API key, invite code | security | none | the value itself grants access |
| CSRF token, nonce, salt | security | none | freshness is the safety property |
| Temp file or directory name | security | none | a name others can anticipate is a hazard |
| Lottery or prize draw | security | none | money plus an outside party |
| Synthetic data for a check | statistical | **required** | the seed goes in the failure report |
| A/B bucket assignment | statistical | **required** | same user, same bucket |
| Log stream sampling | statistical | recommended | makes the sample auditable |
| Retry backoff jitter | statistical | not needed | only has to spread load |
| Animation and particles | statistical | optional | speed is the whole point |

## 3. Ranges — bounded integers without bias

Slicing with `%` skews the distribution, and the narrower the source the worse it gets.
On an 8-bit source, `% 100` makes the 56 lowest values come up **50% more often**
(measured ratio 1.499).

```js
// unbiased [0, n) via rejection
function intBelow(next, n) {
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width');
  const limit = 4294967296 - (4294967296 % n);
  let v;
  do { v = next(); } while (v >= limit);   // next() returns a uint32
  return v % n;
}

// closed range [lo, hi]
function intBetween(next, lo, hi) {
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}
```

- On a 32-bit source the rejection cost measured **1.00 draw** on average, **2.00** in the worst case
- On an 8-bit source, `% 100` rejects 21.88% of bytes and buys zero bias in exchange
- The narrower the source, the larger the bias: 8-bit with `% 6` is 2.38%, 32-bit with `% 6` is 0.00000014%

## 4. The float-to-integer boundary

| Idiom | Actual range | Verdict |
|---|---|---|
| `Math.floor(r * n)` | 0..n-1 uniform | **correct** (half-open) |
| `Math.floor(r * (n + 1))` | 0..n uniform | **correct** (closed) |
| `Math.round(r * n)` | 0..n, endpoints half-weight | **wrong** — measured 5.01% vs 10.00% |
| `Math.ceil(r * n)` | 0..n, 0 almost never | **wrong** |
| `(r * n) \| 0` | goes negative past 2^31 | **wrong** — span 5e9 gave -544967296 |

`[0, 1)` is half-open. Across 5,000,000 draws neither an exact 0 nor an exact 1 came out.
Feeding `floor(r * n)` the largest double below 1 still stops at n-1 for every n up to 2^53.

## 5. Shuffling

```js
// Fisher-Yates: j is drawn from 0..i only
function shuffled(next, arr) {
  const x = arr.slice();
  for (let i = x.length - 1; i > 0; i--) {
    const j = intBelow(next, i + 1);
    const t = x[i]; x[i] = x[j]; x[j] = t;
  }
  return x;
}
```

Four elements, all 24 permutations, 240,000 shuffles each:

| Method | min | max | max/min | chi-square (df 23) |
|---|---|---|---|---|
| `sort(() => Math.random() - 0.5)` | 3,671 | 45,021 | **12.26** | 277,371 |
| broken Fisher-Yates (j over full range) | 7,420 | 13,939 | 1.88 | 6,952 |
| Fisher-Yates (j over 0..i) | 9,782 | 10,197 | 1.04 | **24** |

- The comparator shuffle left the original order in place **11 times** too often (45,021 against an expected 10,000)
- Broken Fisher-Yates spreads n^n paths over n! outcomes. For n=4 that is 256/24 = 10.667, not an integer, so uniformity is **impossible**
- The longer the array, the clearer the skew: at length 16 the first element stayed in place 13.26% of the time (fair value 6.25%)

## 6. Seeds

```js
// the seed is a required argument, not an option
function statisticalRng(seed) {
  if (!Number.isInteger(seed)) throw new TypeError('statisticalRng(seed) requires an explicit integer seed');
  // ...
}
```

- A check driven by generated input must **record the seed in the failure report**
- With a seed the failing input becomes a fixed, quotable value (measured: three replays all hit iteration 92, lo=30 hi=30)
- Without a seed, five runs of the same check told five different stories (first failure at 8, 52, 119, 14, 32)
- **A seed is for reproduction, not for safety.** A seeded generator is predictable by definition

## 7. No global generator

| Layout | Stable alone | Stable in parallel | Stable on reorder | Depends on |
|---|---|---|---|---|
| one global generator | no | no | no | call order and timing |
| one per component | yes | yes | partly | draw count inside the component |
| one per unit of work | yes | yes | yes | nothing |

Same seed, same code: changing only the consumption order gave component A
**three different sequences out of three**. Handing each consumer its own generator made all
three identical. Deriving a child generator per unit of work from `seed + work id` keeps
reproducibility even when the units run in parallel.

## 8. API design checklist

- [ ] The **family is visible in the name** (statistical / secure)
- [ ] The statistical constructor takes a **required seed**. No zero-argument form exists
- [ ] The security object has **no seed parameter at all**
- [ ] The library ships bounded integers (`intBelow`, `intBetween`)
- [ ] Range names **state open or closed** (`below` excludes, `between` includes)
- [ ] The library ships a shuffle, so the comparator trick has nowhere to appear
- [ ] Generators are **instances**. No global singleton is exported
- [ ] Bad arguments **throw**. They never return a quietly wrong number
- [ ] Token generation exists **only on the security object**
- [ ] The cautious option is the default. The fast one has to be chosen on purpose
- [ ] The reproducibility contract is written down (same sequence across versions or not)
- [ ] Array helpers **return a copy instead of mutating** (`shuffled`, past tense)

## 9. What not to do

- Do not guess the family from the name. In the measurement, six call sites split three and three, and all of them contained the word `random`
- Do not build tokens on a statistical generator. Same seed, same token, on any machine
- Do not slice ranges with `%`. On a narrow source it shows immediately; on a wide one it never shows
- Do not build integer ranges with `Math.round`. The endpoints end up at half weight
- Do not truncate with `| 0`. Past 2^31 the result goes negative
- Do not shuffle with a comparator. The outcome depends on the sort algorithm and the array length
- Do not share one global generator across callers. Reproducibility becomes hostage to call order
- Do not defer the seed as something to add later. Reproduction is the precondition for debugging
