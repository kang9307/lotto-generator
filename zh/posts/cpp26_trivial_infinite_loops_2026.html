1. while (true); 曾被归类为未定义行为的背景

通常情况下，编程语言中的循环控制语句是用于维持控制流直至满足退出条件，或有意使执行上下文处于等待状态的基础语法结构。在系统级开发与底层控制中，许多程序员在编写循环体为空的 while (true); 语句时，其初衷都是让程序在到达该点后彻底永久停机。然而原文指出，在C++26之前，没有任何副作用（side effect）的 while (true); 形式循环在语言标准中一直被归类为未定义行为（undefined behaviour）。尽管绝大多数开发者直觉上认为该程序具有完全明确定义的行为（well-defined），但按照原文所述，依据C++26之前的标准条款，这种直觉在法理上是完全错误的。

原文解释道，针对不存在可观测副作用的循环，编译器被赋予了自由假设其最终必然会终止的权力。原文进一步强调，部分优化编译器（特别是Clang）正是在这条标准规定支持下，在优化阶段将整个循环完全消除（optimize away）。原文指出，这种将循环蒸发掉的处理方式引发了极其惊人的后果（spectacular consequences），导致了完全违背开发者字面意图的异常控制流。

根据本文的解读，本次变更是将编译器优化假设与开发者直观代码意图之间的冲突，通过引入明确的语法例外规定加以平息。

原文在此明确划清了界限：本次C++26的修订绝非将所有无限循环无条件变为安全语句。新标准并没有对任意循环结构给予豁免，而是仅针对语法形式极其狭窄、条件完全受限的特定空循环去除了未定义行为的标签。原文写道，只有完全符合简单无限循环的严苛定义，才能免于被编译器判定消除。

2. 向前进展（Forward Progress）假设与编译器循环优化

原文引用了C++11标准正式确立的向前进展（forward progress）规则作为编译器得以消除循环的理论根源。依据原文引述的C++标准 [intro.progress] 节条款，编译器实现可以合法假定任何运行中的线程最终都会执行特定行为之一。原文引述的标准原文为： 「the implementation may assume any thread will eventually do one of the following: terminate, call a library I/O function, access a volatile glvalue, or perform a synchronization or atomic operation」 。换而言之，编译器在法律上有权假定每个线程终将达成以下四种可观测行为之一：

  • 线程正常结束其执行（terminate）。
  • 调用标准输入输出库函数（call a library I/O function）。
  • 访问带有volatile限定符的泛左值内存（access a volatile glvalue）。
  • 执行线程同步操作或原子（atomic）操作（perform a synchronization or atomic operation）。

原文明确指出，仅仅以一个分号结束的 while (true); 循环没有执行上述四种动作中的任何一项。该循环内部既无I/O系统调用，也不触碰volatile修饰的变量，没有任何原子同步动作，更没有正常退出的出口。按照原文的说明，编译器依据向前进展规则，断定该线程不可能在此处无限停滞，推论其必定会走向终止。由于循环体内根本没有任何可观测的外部效应，编译器进而得出执行这段循环纯属多余的结论，最终直接在生成的机器码中将条件检查与回跳指令全盘剥除。

根据本文的解读，当循环完全不执行向前进展规则所列四项可观测行为中的任何一项时，编译器便认定其最终会终止并予以删除。

3. Clang循环消除案例与unreachable代码的异常执行

为了直观展现编译器消除此类循环所带来的真实后果，原文给出了在Clang编译器下能够稳定复现的经典示例代码。原文展示的代码如下：

// https://godbolt.org/z/WYMxxeW1T
#include <iostream>

int main() {
    while (true)
        ;
}

void unreachable() {
    std::cout << "Hello world!" << std::endl;
}

原文指出，在Clang编译器环境下编译并运行这段代码时，控制台居然打印出了 「Hello world!」 字符串。纵观整份源代码，没有任何语句调用过 unreachable() 函数，且 main() 函数内部除了一句空转的 while (true); 之外空无一物。然而，程序却直接越界跨入了未被调用的函数内部，输出信息并退出了系统。

原文对此解释道，编译器认定 while (true); 不含任何副作用而将其从指令序列中彻底剔除，导致 main 函数的代码体变为空白。紧接着，程序的执行流直接穿透了 main 函数的尾部边界，径直坠入（fall through）链接器恰好排布在 main 函数正下方的 unreachable() 函数入口处，触发了该函数的指令执行。

根据本文的解读，由于循环被消除，函数的控制流边界随之瓦解，从而导致执行流直接坠入在物理内存中紧随其后的函数。

4. C++26 P2809R3所定义的「简单无限循环」要件

原文指出，为彻底修复这一未定义行为问题而提交并获得标准采纳的核心提案正是 P2809R3 提案。原文写道，随着该提案被纳入C++26，简单无限循环不再属于未定义行为。但原文反复强调，该提案所建立的保护范围在语法界定上有着极其苛刻的准入条件。

原文全文引述了提案中的规范定义条文： 「The loop must be a trivially empty iteration statement — meaning its body is literally empty (`;` or `{}`). Any non-empty statement in the body, even a meaningless expression statement such as `"a string";`, disqualifies it. The controlling expression must be a constant expression that evaluates to `true`.」 将原文中的技术准则拆解后，受保护的简单无限循环必须严格满足以下四项判定要件：

  • 循环必须属于语法上完全为空的平凡空迭代语句（trivially empty iteration statement）。
  • 允许存在的循环体字面结构仅限于单一分号（;）或完全空白的花括号代码块（{}）。
  • 循环体内如果夹带任何非空语句，哪怕是一条无实际意义的表达式语句（如 "a string";），也会瞬间剥夺其资格。
  • 用于控制循环的条件表达式（controlling expression）必须在编译期求值为 true 的常量表达式。

原文特别说明，循环体必须为空这一规则不容许任何语义层面的宽限。哪怕某条表达式语句在运行时既不写入内存也不占用寄存器，只要它在语法上构成了一条非空语句，就不符合P2809R3定义的简单无限循环标准。因此，这类循环在C++26中仍然继续停留在未定义行为中。

根据本文的解读，该规则的核心在于将保护范围严格限定在可纯粹由语法树字面判定的空循环体形式之内。

5. 各种语法形式在C++26下的受保护状态对照

为了帮助工程师精确分辨各种写法的安全边界，原文列举了常见的无限循环语法形式，并通过明晰的对比表格阐明了各类写法在C++26下的真实待遇。基于原文整理的判定对照表如下所示：

循环语法形式 C++26保护状态 原文给出的判定依据与原因说明
while (true); 受保护 控制表达式为常量true且循环体仅为一个独立分号完全为空
for (;;); 受保护 省略的条件表达式等同于true且循环体完全为空
do {} while (true); 受保护 循环体代码块为空花括号且控制表达式为常量true
constexpr bool go = true; while (go); 受保护 constexpr变量在编译期直接解析为常量true且循环体为空
while (true) { "a string"; } 不受保护 即使字符串字面量无副作用，但循环体存在非空语句故取消资格
while (true) if (done) break; 不受保护 循环体内包含条件分支控制语句，不符合字面完全为空的要求
while (true) if constexpr (false) break; 不受保护 语法层面上存在if constexpr语句，未能满足完全空循环体的硬性指标
bool done = false; while (!done); 不受保护 依赖普通运行期变量判定，控制表达式并非编译期常量表达式

从上述对照清单中可以清晰看出，C++26提供的安全保护范围极其狭窄。原文重点强调的技术特征包括：

  • 三类最典型的传统空循环——while (true);、for (;;);、do {} while (true); 均获得完全保护。
  • 通过外部变量控制循环时，只有加上 constexpr 确保编译期真值锁定时才属于受保护范畴。
  • 在循环体内哪怕仅多写了一句诸如 "a string"; 般的语句，也会立即沦为未定义行为。
  • 依赖运行时动态标志变量的循环（while (!done);）无法获得本次规则修订的保护。

根据本文的解读，正如同表格中将 while (!done); 明确划归为不受保护一样，若控制表达式依赖普通变量且不包含 [intro.progress] 规定的volatile泛左值访问、原子操作或同步操作，编译器优化仍不会受到阻止。

6. 采纳为缺陷报告（Defect Report）与对旧版C++标准的回溯适用

针对P2809R3提案的实际工程落地，原文特别披露了一项极具实操价值的官方决议。原文指出，该提案已被标准委员会正式采纳为缺陷报告（defect report）： 「The mentioned proposal was also accepted as a defect report, so implementations may apply the fix to earlier C++ modes as well.」

原文指出，正因为被定性为缺陷报告，编译器实现团队完全有权将这一修复举措逆向回溯应用到早期C++模式（earlier C++ modes）中。换而言之，只要开发者使用了整合此项修复的新版编译器，即便项目的编译构建选项仍然显式锁定在早期标准模式，编译器也不再强行剥离简单无限循环。标准条款演进与缺陷报告的关系如下表所示：

标准历史阶段 向前进展规则状态 对简单无限循环（while (true);）的处理策略
C++11及以后（向前进展保证引入后） 执行 [intro.progress] 假设 无副作用循环归为未定义行为，编译器有权予以删除
C11 (ISO C) 明文豁免常量控制表达式循环 原文评价「C got this right」: 常量循环在标准中受到严格保护
C++26 (P2809R3) 针对简单无限循环设立显式豁免 满足空循环体与常量true即移出UB范畴，赋予yield协作语义
早期C++模式（回溯） 采纳缺陷报告（DR）修订 编译器实现可自行决定在早期C++模式下也停用循环删除

缺陷报告状态给整个C++生态链带来的切实变革体现为：

  • 在指定早期C++模式编译时，若编译器工具链采纳了此项修复，简单无限循环便有望得以保留。
  • 正如原文所言，向早期模式的移植属于编译器的实现自由，开发者需实际确认不同供应商的具体支持情况。
  • 依赖 while (true); 停机的存量系统项目，无需被迫改变语言模式即可解除循环消除风险。
  • 根据本文的解读，采纳为缺陷报告的核心意义在于为编译器实现向早期C++模式回溯保留简单无限循环提供了规范依据。

原文明确指出编译器有权将修复向早期模式延伸，这提示开发者应主动查证自身所用工具链在早期模式下的实际表现。

7. 嵌入式系统halt-on-error模式与独立式实现中yield的隐忧

原文指出，简单无限循环在嵌入式系统和底层内核领域被广泛运用于停机报错模式（halt-on-error pattern）。按照原文的描述，在没有操作系统可供退出时，程序只能原地停机（原文： 「there's no operating system to exit to, you simply stop」 ）。原文举出硬件初始化失败（例如调用 hardware_init_failed() ）作为具体场景，说明开发者在发生致命错误后会使用空循环来强制冻结执行。

原文解释道，假若优化编译器将该停机语句强行抹除，程序便无法维持预期的停机状态，进而脱离循环继续向下执行。原文说明，P2809R3正是为了满足系统开发的现实诉求而确保空循环得以留存。

但是，原文对标准为该循环设计的底层执行语义表达了担忧，尤其是在独立式（freestanding）实现环境中。按照新规，为使简单无限循环顺应向前进展规则，编译器在语义上将循环体替换为对 std::this_thread::yield() 的调用。原文特别警示道，在独立式环境中存在着限制： 「it is implementation-defined whether the replacement with `std::this_thread::yield()` occurs at all」 。也就是说，在独立式环境下这种替换到底发生与否，完全由实现定义（implementation-defined）。

原文明确对这种语义替换表达了忧虑： 「turning a deliberate halt loop into a cooperative yield could introduce behaviour the programmer never intended」 。原文针对独立式环境提出的重点事实包括：

  • 在独立式实现中，是否替换为 std::this_thread::yield() 属于由实现定义（implementation-defined）事项。
  • 将蓄意的停机（halt）循环转变为协作式让步（yield），可能会引入程序员从未预期的行为。
  • 原文并未罗列协作式让步可能引发的具体故障场景。
  • 根据本文的解读，在独立式环境下针对目标硬件平台核实由实现定义的yield替换行为在工程上十分必要。

原文基于这一顾虑阐明，在独立式系统中使用简单无限循环时，必须审慎关注编译器实现所选定的具体行为。

8. 与C11标准的对比及C++委员会的设计取舍

在探讨如何处理无限循环未定义行为的议题时，原文回顾了C语言早期的标准化处理方案，并评价道 「C got this right」 。早在C11修订版引入向前进展规则时，ISO C标准委员会便明确作出了制度安排：只要控制循环的条件表达式属于常量表达式，便自动享有向前进展豁免权，严禁编译器予以消除。

原文透露，在C++标准委员会内部，直接全盘照搬C11既有规则的提案同样曾被讨论过，但最终遭到了明确否决： 「considered and rejected」 。倘若原样照搬C11规范，只要控制条件恒为常数，即便循环体内部书写了语句，编译器也不得假定其终止。原文解释道，C++委员会之所以弃用该案，是因为这种宽泛的豁免会给C++优化器带来过大的束缚（optimizer constraints）。

正因如此，C++委员会最终通过了一份比C11严格得多的方案。它不仅要求循环条件必须是求值为 true 的常量表达式，更强制要求循环体必须完全为空。两门语言在设计选择上的差异可归纳为：

  • C11对所有包含常量控制条件的无限循环给予了普遍豁免，提供了较宽的保护范围。
  • C++委员会评估了C11规则，但因考虑优化器所受限制而决定将其否决。
  • C++26通过追加循环体必须字面完全为空的约束，选择了尽量减少优化损失的狭窄路径。
  • 根据本文的解读，C++为了维系优化器性能，采取了比C11严苛得多的空循环体规则。

原文强调，C与C++在无限循环的定义上走向了不同的道路，C++26的修订是与C11全面保护截然不同的独立妥协产物。
