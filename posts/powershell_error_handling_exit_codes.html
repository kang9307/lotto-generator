코드는 스크립트 파일로 저장해 powershell.exe -NoProfile -File로 실행했고, 출력은 Windows PowerShell 5.1(5.1.19041.6456)에서 나온 그대로이며 경로만 C:\demo이다. 오류 메시지는 영어로 나오는 환경(Windows PowerShell을 직접 띄운 세션)에서 얻은 영어 원문이다. 같은 PC에서 Git Bash로 powershell.exe를 띄우면 같은 오류가 한국어 메시지로 나오므로, 메시지 문구는 이 환경의 것이다. 항목마다 「코드 → 실제 출력 → 이유」 순서로 적는다. 이유 부분에서 공식 문서를 인용한 곳은 문서 문장임을 밝히고, 실행으로 본 것과 구분한다.

서론 - 실패는 세 곳에서 따로 판정된다

PowerShell 스크립트가 실패했을 때 호출자(작업 스케줄러·CI 러너·다른 스크립트)가 받는 값은 프로세스 종료 코드 하나다. 그런데 그 값이 정해지기까지 PowerShell 안에는 판정 장부가 셋 있다. 첫째는 예외, 곧 terminating 오류와 try/catch다. 둘째는 직전 명령의 성공 여부를 담는 $?다. 셋째는 마지막으로 실행한 네이티브 프로그램의 종료 코드를 담는 $LASTEXITCODE다. 세 장부는 서로 자동으로 이어지지 않는다. 어느 한 장부에 실패가 적혔다고 해서 나머지 둘에도 적히는 것이 아니다.

용어를 먼저 정리한다. cmdlet은 Get-Item처럼 .NET 클래스로 구현된 PowerShell 명령이고, 네이티브 명령은 cmd.exe·git.exe처럼 별도 프로세스로 실행되어 정수 종료 코드를 돌려주는 외부 실행 파일이다. ErrorRecord는 PowerShell이 오류마다 만드는 객체로 예외, 오류 범주, 대상 객체, 스크립트 위치를 담는다. 실패가 예외로 발생했는지 오류 스트림에 기록만 됐는지가 여기서 관찰하는 모든 차이를 가른다.

bash에서는 set -e와 $? 하나로 대부분이 설명된다. PowerShell은 객체로 된 오류 모델 위에 네이티브 프로그램의 정수 종료 코드가 따로 얹혀 있어, 같은 「실패」가 장부마다 다르게 보인다. bash 쪽의 errexit·pipefail 사각지대는 셸 종료 코드와 set -e 글이 실행 출력으로 정리했으므로, 논의는 PowerShell에만 한정한다.

다루는 질문은 다음과 같다.

  • try/catch가 잡는 오류와 잡지 못하는 오류의 경계는 어디인가.
  • $ErrorActionPreference는 어느 범위까지 영향을 주고, -ErrorAction과 부딪히면 어느 쪽이 이기는가.
  • 네이티브 명령이 실패하면 $?·$LASTEXITCODE·예외 중 무엇이 바뀌는가.
  • exit와 return은 프로세스 종료 코드에 어떻게 반영되는가.
  • 같은 스크립트를 -File과 -Command로 호출하면 종료 코드가 어떻게 달라지는가.
  • Write-Error와 throw, 파이프라인 중간의 오류, $Error 컬렉션은 각각 무엇을 남기는가.

terminating 오류와 non-terminating 오류 - try/catch가 보는 것

Microsoft Learn의 about_Try_Catch_Finally는 try/catch가 다루는 대상을 이렇게 정의한다. PowerShell의 terminating 오류는 현재 문장을 멈추는 statement-terminating 오류와 호출 스택 전체를 풀어 버리는 script-terminating 오류 두 종류이고, 둘 다 try/catch로 잡힌다. 여기에 들지 않는 것이 non-terminating 오류다. cmdlet이 오류 스트림에 오류를 쓰고도 다음 항목 처리를 계속하는 경우이며, 문서의 $ErrorActionPreference 항목은 이 기본 동작을 Continue(오류를 표시하고 계속 실행)라고 적는다.

경계를 실행으로 확인한 첫 코드는 존재하지 않는 경로에 Get-Item을 쓰는 것이다.

try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
Get-Item : Cannot find path 'C:\demo\nope.txt' because it does not exist.
                    At C:\demo\e1.ps1:3 char:7
                    + try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught:  ...
                    +       ~~~~~~~~~~~~~~~~~~~~~~~~~
                        + CategoryInfo          : ObjectNotFound: (C:\demo\nope.txt:String) [Get-Item], ItemNotFoundException
                        + FullyQualifiedErrorId : PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
                    
                    after Get-Item

오류 메시지는 화면에 나왔지만 catch 블록은 실행되지 않았고, try 안의 다음 문장 'after Get-Item'이 그대로 실행됐다. 이유는 앞의 정의 그대로다. Get-Item은 이 오류를 non-terminating으로 쓰고 계속 진행했기 때문에 예외가 발생하지 않았다. 같은 코드에 -ErrorAction Stop을 붙이면 결과가 달라진다.

try { Get-Item C:\demo\nope.txt -ErrorAction Stop; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
caught: ItemNotFoundException

이번에는 catch가 실행됐고 'after Get-Item'은 출력되지 않았다. 문서는 $ErrorActionPreference를 Stop으로 두면 non-terminating 오류가 script-terminating 오류로 승격된다고 설명하며, -ErrorAction 공통 매개 변수는 명령 하나에 대해 그 설정을 덮어쓴다고 적는다. 아래 표는 같은 스크립트에서 여러 형태의 실패를 try/catch에 넣어 본 결과다.

try 안의 코드catch 실행catch의 $_.Exception 형식try 안의 다음 문장
Get-Item C:\demo\nope.txt안 됨—실행됨
Get-Item C:\demo\nope.txt -ErrorAction Stop실행ItemNotFoundException실행 안 됨

NonsenseString(없는 명령)실행CommandNotFoundException실행 안 됨

표에서 읽을 수 있는 규칙은 다음과 같다.

  • cmdlet이 스스로 오류 스트림에 쓰는 오류(Get-Item의 경로 없음, Write-Error)는 기본 설정에서 catch에 도달하지 않는다.
  • 언어가 직접 일으키는 오류(0으로 나누기, 형 변환 실패, 없는 명령, throw)는 예외이므로 항상 catch로 들어온다.
  • 같은 cmdlet의 같은 실패가 -ErrorAction Stop 하나로 catch 대상이 된다. 스크립트 전체에 적용하려면 $ErrorActionPreference = 'Stop'을 쓴다.
  • catch 안의 $_는 ErrorRecord이고 $_.Exception의 형식으로 오류 종류를 가를 수 있다. 문서는 PowerShell이 모든 예외를 RuntimeException으로 감싼다고 적는다.

$ErrorActionPreference의 범위와 -ErrorAction

about_Preference_Variables는 $ErrorActionPreference의 값으로 SilentlyContinue·Stop·Continue(기본)·Inquire·Ignore를 나열하고, 설정을 바꾸면 그 범위와 자식 범위에만 적용된다고 적는다. 실행으로 범위를 확인한 코드다.

'start: ' + $ErrorActionPreference
                    function Inner { 'inner sees: ' + $ErrorActionPreference }
                    function SetsStop { $ErrorActionPreference = 'Stop'; 'in SetsStop: ' + $ErrorActionPreference; Inner }
                    SetsStop
                    'after SetsStop: ' + $ErrorActionPreference
start: Continue
                    in SetsStop: Stop
                    inner sees: Stop
                    after SetsStop: Continue

함수 안에서 Stop으로 바꾼 값은 그 함수가 부른 함수(Inner)에는 보이고, 함수가 끝나 호출자로 돌아오면 원래 값 Continue로 돌아간다. 반대 방향도 같다. 호출자가 $ErrorActionPreference = 'SilentlyContinue'로 두고 Inner를 부르면 inner sees: SilentlyContinue가 출력됐다. 즉 이 변수는 호출 체인을 따라 아래로 상속되고 위로는 새지 않는다.

두 설정이 부딪힐 때는 명령 단위의 -ErrorAction이 이긴다.

$ErrorActionPreference = 'Stop'
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    'survived: ' + $?
survived: False

전역 설정이 Stop인데도 스크립트가 다음 줄까지 진행했고, 오류 메시지도 출력되지 않았다. 다만 $?는 False다. 오류를 숨기는 것과 실패가 없었던 것으로 만드는 것은 다르다.

SilentlyContinue와 Ignore는 둘 다 메시지를 숨기지만 $Error에 남기는 방식이 다르다. 문서는 Ignore가 $Error에 오류를 추가하지 않는다고 적는다.

$Error.Clear()
                    Get-Item C:\demo\a.txt -ErrorAction SilentlyContinue
                    'after SilentlyContinue, $Error.Count = ' + $Error.Count
                    Get-Item C:\demo\b.txt -ErrorAction Ignore
                    'after Ignore, $Error.Count = ' + $Error.Count
after SilentlyContinue, $Error.Count = 1
                    after Ignore, $Error.Count = 1

SilentlyContinue 뒤에 1건이 쌓였고 Ignore 뒤에도 1건 그대로다. Ignore는 기록조차 남기지 않으므로 나중에 $Error로 되짚을 단서가 사라진다.

문서는 $ErrorActionPreference의 값으로 Ignore도 나열하지만, 5.1에서 Ignore는 cmdlet의 -ErrorAction 매개 변수 값으로만 쓸 수 있었다. 변수에 대입하는 것 자체는 오류 없이 됐고, 그 상태에서 오류가 발생하는 순간 NotSupportedException이 났다.

$ErrorActionPreference = 'Ignore'
                    'preference set to: ' + $ErrorActionPreference
                    Get-Date | Out-Null
                    'after Get-Date, preference: ' + $ErrorActionPreference
                    try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().FullName; $_.Exception.Message }
                    'preference now: ' + $ErrorActionPreference
preference set to: Ignore
                    after Get-Date, preference: Ignore
                    caught: System.NotSupportedException
                    The value Ignore is not supported for an ActionPreference variable. The provided value should be used only as a value for a preference parameter, and has been replaced by the default value. For more information, see the Help topic, "about_Preference_Variables."
                    preference now: Continue

오류를 내지 않는 Get-Date는 평범하게 실행되어 변수가 Ignore로 남았다. 그러나 Get-Item이 오류를 내자 NotSupportedException이 catch로 들어왔고, 원래의 ItemNotFoundException은 catch에 도달하지 않았다. 메시지는 Ignore를 선호 변수의 값으로 쓸 수 없고 선호 매개 변수의 값으로만 써야 하며, 제공된 값이 기본값으로 교체되었다고 알린다. 실제로 마지막 줄에서 변수는 Continue로 돌아가 있었다. 정리하면 5.1에서 Ignore는 -ErrorAction Ignore처럼 매개 변수에서만 쓸 수 있고, 변수에 Ignore를 두면 오류가 나는 첫 지점에서 이 예외로 바뀐다. 이 동작은 5.1에서 실행한 결과이며 7에서는 실행하지 않았다.

마지막으로 about_Try_Catch_Finally의 Note가 알리는 동작이 있다. $ErrorActionPreference가 SilentlyContinue나 Ignore이면 throw조차 전파되지 않고 다음 문장으로 넘어간다. 이 문장은 문서의 것이고, 아래 실행은 SilentlyContinue로만 했다. Ignore는 위에서 본 대로 변수에 둘 수 없어 확인하지 못했다.

$ErrorActionPreference = 'SilentlyContinue'
                    throw 'boom'
                    'line after throw ran'
line after throw ran

메시지 boom은 출력되지 않았고 다음 줄이 실행됐다. SilentlyContinue에 대해서는 문서의 설명과 일치하는 결과다. 이 설정을 스크립트 상단에 습관적으로 두면 throw로 만든 중단 지점까지 사라진다.

Stop을 쓴 뒤 $Error에 남는 것도 실행으로 보았다.

$Error.Clear()
                    try { Get-Item C:\demo\nope.txt -ErrorAction Stop } catch { }
                    $Error.Count
                    $Error[0].GetType().FullName
                    $Error[0].Exception.GetType().FullName
1
                    System.Management.Automation.ErrorRecord
                    System.Management.Automation.ItemNotFoundException

공식 문서는 Stop이 원래 오류에 더해 ActionPreferenceStopException 객체를 오류 스트림에 낸다고 적는다. 이 실행의 $Error에는 1건이 있었고 그 예외 형식은 ItemNotFoundException이었다. 두 서술의 관계는 이 실행만으로 해석하지 않는다.

$?와 $LASTEXITCODE - 네이티브 명령 실패는 예외가 아니다

about_Automatic_Variables는 $?를 직전 명령의 실행 상태(성공 True, 실패 False)로, $LASTEXITCODE를 마지막으로 실행한 네이티브 프로그램 또는 스크립트의 종료 코드로 정의한다. 네이티브 명령에 대해서는 $LASTEXITCODE가 0이면 $?가 True, 0이 아니면 False라는 문장이 이어진다. 네이티브 명령이 실패했을 때의 세 장부를 실행으로 보았다.

cmd /c exit 3
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = False
                    $LASTEXITCODE = 3

실패는 $?와 $LASTEXITCODE에는 적혔다. 예외 장부는 어떤가. $ErrorActionPreference를 Stop으로 두고 같은 명령을 try 안에서 실행했다.

$ErrorActionPreference = 'Stop'
                    try { cmd /c exit 3; 'next line ran' } catch { 'caught' }
next line ran

catch는 실행되지 않았고 다음 문장이 실행됐다. 네이티브 프로그램의 0이 아닌 종료 코드는 오류가 아니라 값이다. PowerShell이 대신 중단해 주지 않으므로, Stop 설정을 켜 둔 스크립트에서도 네이티브 호출의 실패는 $LASTEXITCODE를 직접 읽어야 알 수 있다. 존재하지 않는 프로그램 이름을 실행하면(nosuchprogram.exe) 이야기가 다르다. 이때는 PowerShell이 명령을 찾지 못한 것이므로 try 안에서 CommandNotFoundException이 잡혔다. 프로그램이 실행된 뒤의 실패와 실행조차 못한 실패는 장부가 다르다.

두 변수의 수명도 다르다. 다음 코드는 네이티브 호출 뒤에 cmdlet을 실행한 경우다.

cmd /c exit 3
                    Get-Date | Out-Null
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = True
                    $LASTEXITCODE = 3
                    $? = False
                    $LASTEXITCODE = 3

성공한 cmdlet 뒤에도, 실패한 cmdlet 뒤에도 $LASTEXITCODE는 3으로 남았다. 이 변수는 네이티브 프로그램이나 스크립트를 실행할 때만 갱신되므로, 몇 줄 위에서 남은 값을 지금 호출의 결과로 읽는 실수가 가능하다. $?는 반대로 수명이 한 문장이다.

Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    $ok = $?
                    '$? read once = ' + $ok
                    '$? read again (after the assignment) = ' + $?
$? read once = False
                    $? read again (after the assignment) = True

$ok = $?라는 대입 자체가 성공한 명령이어서 $?를 다시 읽으면 True다. 판정이 필요하면 실패한 명령 바로 다음 문장에서 변수에 옮겨 둔다. 함수 안에서는 한 겹 더 있다. 문서는 Write-Error가 실행 직후 $?를 False로 만들지만 그 함수를 부른 쪽의 $?는 False로 만들지 않는다고 적으며, 실행도 같았다.

function T { Write-Error 'bad' -ErrorAction SilentlyContinue; 'inside: ' + $? }
                    T
                    'outside: ' + $?
inside: False
                    outside: True

네이티브 stderr를 2>&1로 오류 스트림에 합치면 예외 장부에도 영향이 간다. 같은 명령이 리다이렉트 유무에 따라 Stop 설정에서 다르게 움직였다. 아래에서 cmd /c는 stdout에 한 줄, stderr에 한 줄을 쓰고 종료 코드 2로 끝난다.

$ErrorActionPreference = 'Stop'
                    try {
                      $out = cmd /c "echo to-stdout & echo to-stderr 1>&2 & exit 2" 2>&1
                      'no exception; lines captured: ' + @($out).Count
                    } catch {

exit와 return - 프로세스 종료 코드를 정하는 것

프로세스 종료 코드는 호출 방식에 따라 다른 규칙으로 정해진다. about_PowerShell_exe는 -File에 대해 스크립트가 exit로 끝나면 그 숫자가 프로세스 종료 코드이고 script-terminating 오류가 나면 1이라고 적는다. -Command에 대해서는 마지막 명령의 $?가 True면 0, False면 1이며, 마지막 명령이 0·1 이외의 종료 코드를 설정한 외부 프로그램이나 스크립트이면 그 코드가 1로 변환된다고 적는다. 같은 스크립트를 두 방식으로 호출해 부모 PowerShell에서 $LASTEXITCODE를 읽은 결과다. 스크립트는 한 줄짜리다.

'before'; throw 'boom'; 'after'11before 뒤 중단, after 없음

표에서 이유가 뚜렷한 항목을 풀면 다음과 같다.

  • exit 5는 -File에서 5가 그대로 나오지만 -Command "& 스크립트"에서는 1로 변환된다. 문서가 적은 「0·1이 아닌 코드는 1로 변환」과 같은 결과다.
  • return 5는 종료 코드가 아니라 출력이다. 스크립트 최상위에서 return은 스크립트를 끝낼 뿐이고 값은 출력 스트림으로 나가므로 프로세스 종료 코드는 0이다. 함수 안의 return 7도 같은 이유로 7이 화면에 나온다.
  • 함수 안의 exit 7은 함수가 아니라 프로세스 전체를 끝낸다. 호출자 쪽에서 after가 출력되지 않았다.
  • 스크립트의 마지막 줄이 네이티브 실패(cmd /c exit 3)여도 -File은 0을 돌려준다. 문서가 적은 「스크립트가 정상 완료되면 0」과 같은 결과이고, 값을 전달하려면 exit $LASTEXITCODE가 필요하다.
  • try { exit 4 } finally { ... }에서 finally가 실행됐다. about_Try_Catch_Finally가 catch 안의 exit에 대해 적은 문장과 같은 방향의 결과를 try 안의 exit에서도 얻었다.
  • $ErrorActionPreference = 'Stop'도 네이티브 종료 코드 3을 막지 못해 done이 출력됐다. 앞 절의 결과와 같다.
  • 구문 오류가 있는 스크립트는 첫 줄도 실행되지 않고 종료 코드 1이 된다. 문서는 구문 분석 오류가 $?에 영향을 주지 않는다고 적는데, 이 경우는 스크립트 실행 이전 단계의 실패여서 프로세스 종료 코드가 1로 나왔다.

명령 문자열을 직접 넘기는 -Command는 판정 기준이 마지막 명령의 $?라는 점이 더 노골적으로 드러난다. 부모 PowerShell에서 powershell.exe -NoProfile -Command 뒤에 아래 문자열을 하나씩 넘긴 결과다.

파이프라인 중간에서 난 오류

about_Pipelines는 파이프라인이 객체를 한 번에 하나씩 다음 명령으로 보낸다고 설명한다. 이 때문에 중간 단계의 오류는 이미 지나간 항목에는 영향이 없고 이후 항목이 계속 흐르는지가 쟁점이 된다. 스크립트 블록 안에서 0으로 나누는 경우를 세 방식으로 실행했다.

1,2,0,4 | ForEach-Object { 10 / $_ }
10
                    5
                    Attempted to divide by zero.
                    At C:\demo\e4.ps1:2 char:28
                    + 1,2,0,4 | ForEach-Object { 10 / $_ }
                    +                            ~~~~~~~
                        + CategoryInfo          : NotSpecified: (:) [], RuntimeException
                        + FullyQualifiedErrorId : RuntimeException
                    
                    2.5

0 항목에서 오류가 났지만 4 항목은 처리돼 2.5가 출력됐다. 오류가 그 항목의 문장 하나만 멈추고 파이프라인은 계속 흘렀다. 같은 파이프라인을 try/catch로 감싸면 달라진다.

try { 1,2,0,4 | ForEach-Object { 10 / $_ } } catch { 'caught: ' + $_.Exception.Message }
10
                    5
                    caught: Attempted to divide by zero.

2.5가 출력되지 않았다. catch가 오류를 받는 순간 파이프라인 전체가 중단된 것이다. $ErrorActionPreference = 'Stop' 아래에서도 결과는 같았고, 스크립트 블록 안의 throw(3에서 던지는 경우)도 item 1, item 2 뒤에 caught: three로 끝났다. 따라서 「오류가 나도 나머지 항목은 처리하고 실패만 모은다」는 설계에는 try/catch를 파이프라인 밖에 두면 안 되고, 항목 처리 블록 안에서 항목마다 잡아야 한다.

cmdlet 하나가 여러 입력을 받는 경우는 non-terminating 오류가 결과와 섞여 나온다. 네 경로(둘은 없는 파일)를 한 번에 Get-Item에 넘기고 2>&1로 결과를 변수에 받아 형식을 세었다.

$r = Get-Item C:\demo\e1.ps1, C:\demo\nope1.txt, C:\demo\e2.ps1, C:\demo\nope2.txt 2>&1
                    $r | ForEach-Object { $_.GetType().Name }
FileInfo
                    ErrorRecord
                    FileInfo
                    ErrorRecord

성공 객체와 ErrorRecord가 입력 순서대로 섞여 나왔다. 실패한 항목이 뒤의 항목 처리를 막지 않았다는 뜻이다. 이 구조를 모르면 결과 변수에 오류 객체가 섞여 있는 것을 보고 놀라게 된다.

파이프라인이 끝난 뒤 $?를 읽으면 단계별 동작이 드러난다.

Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue | ForEach-Object { 'x' }
                    '$? = ' + $?
                    Get-Date | ForEach-Object { Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue }
                    '$? = ' + $?
$? = False
                    $? = True

첫 단계 cmdlet이 오류를 쓴 파이프라인은 마지막 단계가 성공했어도 $?가 False였다. 반대로 마지막 단계의 스크립트 블록 안에서 일어난 실패는 $?에 반영되지 않았다. 문서가 $?를 「마지막 명령」의 상태로 정의하는 점은 둘째 결과와 맞지만, 첫째 결과는 그 정의만으로 설명되지 않는다. 어느 쪽이든 파이프라인 뒤의 $?는 실패 감지 수단으로 신뢰하기 어렵다. 단계별 실패는 -ErrorVariable이나 $Error로 수집하는 편이 낫다.

Write-Error의 매개 변수로 오류 분류를 정할 수 있다. 다음 코드는 범주와 식별자를 지정한 뒤 $Error[0]을 읽은 결과다.

try { throw [System.IO.FileNotFoundException]::new('typed') } catch [System.IO.FileNotFoundException] { 'typed catch: ' + $_.Exception.Message }

잡힌 오류도 $Error에 들어간다. 문서가 「try 블록에서 오류가 나면 먼저 $Error에 저장된다」고 적는데, 실행에서도 try { throw 'caught-me' } catch { ... } 뒤 $Error.Count가 1이었다. 다만 catch 안의 $_와 $Error[0]을 ReferenceEquals로 비교하면 False가 나왔다. 같은 오류를 가리키지만 같은 객체 참조로는 확인되지 않았다.

                    Get-Item C:\demo\fourth.txt -ErrorAction SilentlyContinue -ErrorVariable +ev
                    'ev.Count: ' + $ev.Count
ev.Count: 1 / $Error.Count: 1
                    ev.Count: 2

첫 줄은 -ErrorVariable ev로 한 번 실패한 뒤의 값이고, 둘째 줄은 -ErrorVariable +ev(앞에 +)로 한 번 더 실패해 누적한 뒤의 $ev.Count다. +가 없으면 변수가 매번 덮어써진다. 실무에서는 스크립트 상단에서 $Error.Clear()를 한 번 부르고, 종료 직전에 $Error.Count와 $Error | Select-Object -First 5로 삼켜진 오류가 있었는지 감사하는 방식이 쓸 만하다. 앞 절의 SilentlyContinue는 이 감사 대상에 잡히고 Ignore는 잡히지 않는다.

bash와의 대응 - set -e에 해당하는 것과 없는 것

bash에 익숙한 사람이 PowerShell 스크립트를 쓸 때 가장 먼저 하는 질문이 「set -e는 어디 있나」다. 위의 실행 결과로 대응을 짧게 정리한다. 전체 명령 대조는 다른 글의 몫이라 여기서는 오류와 종료 코드에 한정한다.

bashPowerShell 5.1실행으로 확인한 차이
set -e$ErrorActionPreference = 'Stop'cmdlet 오류만 예외로 승격한다. 네이티브 종료 코드 3은 Stop 아래에서도 막지 못했다
$?(직전 종료 상태 정수)$?(True/False)와 $LASTEXITCODE(정수)값이 둘로 갈린다. $LASTEXITCODE는 cmdlet 실행으로 갱신되지 않는다
cmd || exit $?if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }이 형태로 -File에서 종료 코드 3이 전달됐다
trap ... EXITtry/finallyexit 때도 finally가 실행됐다(종료 코드 4)
exit Nexit N함수 안에서 써도 프로세스 전체를 끝낸다. return N은 종료 코드가 아니라 출력이다
스크립트 종료 상태 전달-File 사용 또는 -Command 끝에 exit $LASTEXITCODE-Command는 0·1로 변환하므로 값 전달에 부적합하다

이 표에는 pipefail 행이 없다. 파이프라인 단계별 상태는 6절에서 본 것처럼 단계의 종류에 따라 $?에 다르게 반영됐다. bash의 set -e 예외 규칙과 pipefail의 세부는 bash 쪽 글이 다룬다.

실전 패턴 - 네이티브 호출 래퍼와 종료 코드 전달

위 실행에서 얻은 규칙을 한 스크립트로 합치면 다음과 같다. 상단에서 Stop을 켜 cmdlet 오류를 예외로 만들고, 네이티브 호출은 래퍼가 $LASTEXITCODE를 검사해 throw로 바꾸며, catch에서 호출자가 읽을 종료 코드를 exit로 정하고, finally에서 정리한다.

$ErrorActionPreference = 'Stop'
                    function Invoke-Native {
                        param([scriptblock]$Command)
                        & $Command
                        if ($LASTEXITCODE -ne 0) { throw ('native command failed with exit code ' + $LASTEXITCODE) }
                    }
                    try {
                        'step 1'
                        Invoke-Native { cmd /c exit 0 }
                        'step 2'
                        Invoke-Native { cmd /c exit 3 }
                        'step 3 (not reached)'
                    }
                    catch {
                        'ERROR: ' + $_.Exception.Message
                        exit 3
                    }
                    finally {
                        'cleanup runs'
                    }

이 스크립트를 powershell.exe -NoProfile -File로 실행하고 부모에서 $LASTEXITCODE를 읽은 결과다.

exit code = 3
                    step 1
                    step 2
                    ERROR: native command failed with exit code 3
                    cleanup runs

세 번째 단계는 실행되지 않았고, exit 3 뒤에도 finally의 정리가 실행됐으며, 프로세스 종료 코드는 3이었다. 이 패턴이 의존하는 사실은 모두 앞 절에서 실행으로 본 것이다.

  • 네이티브 실패는 예외가 아니므로 래퍼에서 throw로 승격한다(4절).
  • exit가 있어도 finally는 실행된다(5절).
  • -File은 exit 값을 그대로 돌려준다(5절).

이 패턴을 쓸 때의 점검 항목은 다음과 같다.

  • 스크립트 상단의 $ErrorActionPreference 값이 의도한 것인가. SilentlyContinue로 두면 throw도 삼켜진다.
  • 네이티브 호출 직후에 $LASTEXITCODE를 읽는가. 몇 줄 뒤의 값은 이전 호출의 값일 수 있다.
  • 호출자가 -Command로 부르는 구조라면 문자열 끝의 exit $LASTEXITCODE가 있는가.
  • 래퍼 없이 2>&1로 stderr를 합친 네이티브 호출이 Stop 아래에서 예외로 바뀌지 않는가.
  • 종료 직전에 $Error.Count를 확인해 Ignore가 아닌 SilentlyContinue로 삼켜진 오류를 점검하는가.

확인하지 못한 것

  • $ErrorActionPreference가 Ignore일 때 throw가 전파되지 않는다는 문서 Note의 Ignore 부분. 5.1에서는 변수에 Ignore를 두면 오류가 나는 지점에서 NotSupportedException으로 바뀌어 재현하지 못했고, 확인한 것은 SilentlyContinue뿐이다.
  • PowerShell 7(pwsh)의 동작. 이 PC에는 pwsh가 설치되어 있지 않아 5.1과의 차이를 실행으로 비교하지 못했다. 공식 문서가 5.1 문서 안에서 밝힌 것은 괄호 (...)·$(...)·@(...)로 감싼 문장이 PowerShell 7 이전에는 $?를 항상 True로 되돌렸고 7에서 바뀌었다는 점, 그리고 -File에서 스위치 매개 변수에 명시적 Boolean 값을 줄 수 없다는 제한이 PowerShell 6(pwsh.exe)에서 제거되었다는 점뿐이다.
  • bash의 pipefail에 해당하는 5.1 설정. 열람한 공식 문서 다섯 건에서는 찾지 못했다.
  • Stop이 낸다고 문서가 적은 ActionPreferenceStopException이 오류 스트림 어디에 나타나는지. 이 실행에서는 $Error에 1건만 있었다.
  • cmd.exe·작업 스케줄러·CI 러너가 이 종료 코드를 받는 방식. 종료 코드는 부모 PowerShell에서 $LASTEXITCODE로만 읽었다.
  • Ctrl+C로 중단했을 때의 종료 코드. 문서는 -File에서 0, -Command에서 1이라 적지만 대화형 중단은 자동 실행이 어려워 실행하지 않았다.
  • 스크립트 모듈·바이너리 모듈 안 cmdlet에서의 $ErrorActionPreference 상속, 원격 실행(Invoke-Command)·백그라운드 작업에서의 오류 전파.
  • $LASTEXITCODE의 초기값(네이티브 프로그램을 한 번도 실행하지 않은 세션)과 다른 Windows 빌드에서의 결과.
  • 같은 5.1 안에서도 호스트(콘솔·ISE·VS Code 통합 터미널)에 따라 오류 표시 형식이 다를 수 있는지.
