崩塌点因指标而异 - 选定位宽之前该测什么

先分清把保持与崩塌划开的到底是哪个指标

2026-09-10 IT/技术

想在本地跑模型的人最先撞上的墙不是质量，而是内存。55GB 的权重文件放不进一张消费级显卡。于是把位宽降下来。窄了就小，小了就装得下。

至于降下来之后会怎样，市面上流传的说法大体只有一句：4位还能用，再往下就危险。最近出现了一份用实测支撑这句话的记录，把一个模型分成五种位宽，送过三项基准测试。

可是把这份记录的结论折成「4位保持，1位崩塌」这一句，那次测量展示出来的最有用的东西就消失了。三个指标是在不同的位宽上分开的。指令遵循这一侧一直到2位都没有变化，科学知识与智能体编码这一侧在2位就已经分开了。所谓单一的安全线，从数据里根本没有出现过。

所以这里要抓住的问题不是「几位才安全」，而是把保持与崩塌划开的指标究竟是什么，以及要在自己的工作里找到那个位置，得一并测量什么。变小之后的模型丢掉了什么，已经在平均被守住而长尾先被切掉那篇里另行整理。这里处理的是另一侧：测出损失在哪里显形的设计。

文中的数值与引述来自原始测量文章以及模型与量化分发方的公开文档，查阅时点为2026年9月10日。原文使用的文件中，2位、4位与8位版本已由分发方在2026年8月19日替换，所以当时用的正是那几个文件如今已无法以同名取得。这里不对任何模型或工具作出评价，也不能被读成对性能的任何承诺。各指标的确切分数在原文中以图表呈现，因此没有作为数值搬过来。

缘起 - 把一个模型分成五种位宽来测

测量对象只有 Qwen3.8-27B 一个。模型卡写明它是270亿规模的稠密模型，是能同时处理图像与视频的原生视觉语言模型，并带有调节思考深度的设置。原生上下文写作262,144个词元，扩展时可延伸到100万个词元。

原文把这个模型的 BF16 原版，与分发方制作的五个 GGUF 量化版本并排放在一起。下表按原文所记的标签与容量原样列出。

推理引擎是 llama.cpp，原文说明使用的是2026年8月16日的构建。机器有三种：NVIDIA L40S 48GB、H100 80GB 与 H200 141GB，作者写道在云端 GPU 上花掉了大约三千美元。把一个模型分成五种位宽就要花这么多，这件事本身就解释了为什么这类测量并不常见。

有一条重要的附注。由于分发方在2026年8月19日替换了2位、4位与8位文件，大部分测试所用的正是那几个文件已经不在原处。也就是说，今天以同名取得的文件，没有依据认为它与当时的是同一个。

把保持与崩塌划开的是三个指标

最要紧的地方在这里。原文没有给出一个总分，而是把性质完全不同的三项任务分别列出。

指标看的是什么本次测量的上下文原文记下的结果
GPQA Diamond难度大的科学题最深思考档位下推理词元约8千到4位为止与原版无明显差别。1位掉到随机猜测的水平
IFBench(严格评分)是否遵守了指令与格式约4千词元到2位为止各模型之间没有变化
Terminal-Bench 2.1在终端里运行的智能体编码预留98k上下文4位与原版同水平。2位用同样的回合数解出，但多写约四分之一的词元

把这张表折成一句，就成了「4位保持，1位崩塌」。这不是错误的概括，只是2位落在哪一列会让答案不同这一点消失了。若是只要守住格式的活儿，10.7GB 的版本也没有差别；若是科学知识或智能体编码，同一个文件的数值已经掉下去了。

换句话说，「从几位开始崩塌」这个问题，在没有指明指标之前是没有答案的。原文自己在末尾也是带着条件给建议的：对大多数任务，4位版本应当足够好且没有明显差别；对一些更简单的任务，2位版本应当绰绰有余。那句话的重心落在「大多数」与「更简单」上。

每个指标崩塌的位置都不同

为什么会分开？因为三项任务向模型索取的东西彼此不同。

格式遵循为什么撑得最久

指令遵循任务大体是在查看表层约束有没有守住：字数对上了吗，有没有按规定的段落划分，有没有避开禁用词。这类约束一次判定就结束，而模型用来满足它们的表征不是某项稀有知识，而是遍布全部文本的结构性规律，留存得很厚。权重的表示宽度变窄让概率分布略有晃动，但距离头部候选的次序被翻转还有很大余量。

罕见知识为什么先被抹平

难度大的科学题恰恰相反，它要求精确取出训练数据中很少出现的事实。常见的内容沿多条路径重复留存，罕见的只沿一条路径薄薄留下，而薄的东西在压缩中先消失。这一段与长尾先被切掉的说法同根，那边已作详述。

多步任务为什么以累积的方式崩塌

智能体编码的性质又是另一回事。它不是一次判定，而是几十次选择相连，每一步的输出成为下一步的输入。哪怕单步的正确概率只降低一点点，连着走二十步之后抵达终点的概率也会明显下降。更麻烦的是，中途偏掉的结果会成为下一步的前提，于是误差不会相互抵消，而是带着方向堆叠起来。原文观察到2位版本用同样的回合数却多写约四分之一的词元，正好贴着这个性质。就算到达同一个答案，路上也绕得更多。

平均被守住这句话掩盖了什么

这里把本文的核心主张说清楚。总分相同并不等于给出相同的答案。总分是分布的概括，而概括按定义就会丢掉分布的形状。

同样是100题得80分，得法有很多种。可以在四个类别里各错五题，也可以在某一个类别里集中错掉二十题。两者的分数一样，但把这两个模型放进实务时的体验完全不同。前者是偶尔出错的工具，后者是某一类活儿根本干不了的工具。

量化造成的损失更接近后者。它不是均匀变差，而是在特定条件下成簇变差。因此选择位宽的判断没法靠平均分来做。平均是一个信息太少、不足以据以决断的数字。

原文做得好的正是这一点。它没有拼出一个综合分，而是把性质不同的三根轴分别列出，于是2位处的分岔被看见了。假如把三个值平均成一个头条数字发布，2位区间里发生的最有意思的事就会藏进统计里。概括会造成损失，这并不是模型独有的性质。

同样叫4位的东西并不是同一件事

当两个人都说「4位」时，他们指的是同一个东西的概率比想象中低。位宽这一项信息，远不足以确定一种量化。至少还需要两件事：用在哪里与用什么方法。

作用位置本次测量中减少的是什么先显现的症状
权重分五档变动着测模型文件容量与常驻内存因指标而异。本文正题
KV 缓存固定为 F16。每32k词元约2.3GB与上下文长度成比例的内存长上下文后半段的遗漏
激活值原文未提及计算带宽与中间缓冲离群值大的层上的不稳定
嵌入层与输出层原文未单独说明与词表相关的内存罕见词汇与非英语写法

方法这一侧也有分岔。把多少个权重捆成一组共享缩放系数，是否先送入校准输入去测哪些权重对结果贡献更大再据此调整，是否把离群值单独抽出保留在高精度上，是否给不同层分配不同位宽，这些都是各自独立的选项。在同一个4位标签之下把这些选择组合得不同，结果也就分开。

原文用的组合可以确定下来：llama.cpp 系的 GGUF 文件，属于分发方的动态量化系列，其中2位、4位与8位是该系列的第2版，1位是第3版。KV 缓存则明确写着无论模型位宽如何都置于 F16。因此这是只改变了权重位宽这一条件下的测量。

分发方在每个标签内部如何分配逐层位宽、用什么作校准数据，本文没有作为数值搬过来，理由记在后面一节。不过标签前缀 UD 的存在本身就说明该版本属于与默认方式不同的系列，而这恰恰印证了一点：同样的位宽，因制作者的规则不同，就会成为不同的文件。

KV 缓存 - 这次测量固定住的那根轴

这次测量里有一个值得留意的设计选择：KV 缓存无论模型位宽如何都固定为 F16。原文把它的大小记作每32k词元约2.3GB。

这个选择意味着两件事。第一，这次测量展示的纯粹是权重位宽的效果。若把缓存一并收窄，就无从把某项损失归到某个原因上。作为实验设计，这是正确的取舍。

第二，它与真实部署之间有落差。因为内存不够而降到4位的人，通常也想把 KV 缓存一并减小，上下文取得越长，缓存所占的份额越大。以预留98k上下文的智能体任务来算，仅缓存一项就要7GB 上下。再加上4位权重的17GB，总量落在24GB 左右，这已经超过单张高端消费级显卡的容量。

所以「4位就能装进这么大的卡」这种算法，是只数了权重的算法。在上下文长度定下来之前，没法说出需要多少内存。原文作者也只写道缓存侧的量化尚未测量，以后或许会试。机器侧的判断在本地大模型的硬件选择那边另行处理。

崩塌是以错答之外的面貌到来的

关于1位版本如何失败，有一段描述格外有价值：在最深的思考档位上，1位模型更常一直推理到词元预算耗尽，然后返回一个空答案。

这在分数表上被记作「错答」，但性质与错答完全不同。模型并不是笃定地给出了错误答案，而是没能收尾。这种失败在自动评分器里与其他失分无从分辨。一旦被合成一个数字，因知识不足而答错、与因造不出终止条件而交不出答案，就落进同一个格子。

在实务中这两者的处置方向完全相反。前者的答案是更大的模型或检索增强，后者的答案是削减思考预算、强制输出格式，或把停止条件写明。也就是说，看到同样的分数下滑，可以开出方向相反的两种药方。

因此做测试时，最好在分数之外另设一栏来数失败的种类。把格式违规、空输出、预算耗尽、工具调用参数出错与事实错误分别计数，往下调位宽时就能看出哪一栏先增长。这个视角与查看让同样权重给出不同结果的运行环境与模板那几层时是同一种做法。

读基准测试的人先看的六件事

读别人做出来的表格时，有些东西要排在分数前面。这六项若不同，两张表从一开始就不是可比对象。

  • 是否同一引擎同一构建 - 原文写明了 llama.cpp 2026年8月16日的构建。引擎不同，同一个文件也会给出不同结果
  • 是否同一聊天模板与系统提示 - 模板一旦错位，模型接到的就是并非它自身格式的输入。这属于悄悄变差的那一类
  • 采样设置有没有写下来 - 没有写温度、头部候选截断与随机种子的表格无法复现。原文里也没有这些值
  • 跑了几次、离散程度多大 - 原文说明误差棒画的是 Wilson 95 百分比置信区间，并补充说这对逐次运行的噪声而言非常保守。重复次数本身没有写出来
  • 上下文长度取了多少 - 同一个模型在4千词元的任务与98k的任务上会露出不同的面貌
  • 思考深度设成了什么 - 原文说这个值大幅改变了分数，并补充说默认档位可能偏向想得过多

最后一项在这次测量里分量尤其重。把思考深度调低，1位模型因预算耗尽而交出空答案的情况可能减少，于是同一个文件的分数就会改变。位宽与思考预算不是彼此独立的变量。不固定其中一个而去比较另一个，两种效应就混在了一起。

而且跑一次得到的数值是一个样本，不是排名。不知道同样条件再跑一次会晃动多少，就无法判断两个值之间的差距是不是有意义的差距。基准测试本身看不见什么，在评估的盲区那边写得更多。

该一并测量什么 - 把测量轴拆开

说一个总分不足以支撑判断，等同于说要把轴拆开来测。下表把降低位宽时需要一并观察的东西按轴拆开。

测量轴对什么敏感会在总分里显现吗怎么测
长上下文KV 缓存精度、上下文长度设置几乎不显现。标准任务大多很短把同一个问题分别附在短文档与长文档上，比较答案的一致率
罕见词汇与专有名词权重位宽、嵌入层处理不显现。频率权重偏向常见的一侧做一份内部术语与产品名清单，统计写法的一致率
多步推理权重位宽、思考预算只显现一部分，被最终正确率掩埋在中间步骤设置校验点，记录在哪一步开始分岔
格式与指令遵循相对迟钝，崩得较晚若有专用指标则会显现接上模式校验器，单独统计通过率
非英语输入分词器、罕见写法只用英语任务来测就完全不显现把同一任务做成目标语言版本，并排跑
工具调用与结构化输出格式遵循与参数准确性的结合任务中包含时会显现一部分用模式校验调用参数，按错误类型分别计数
终止行为思考预算、停止的判断不显现，与错答混作一团把空输出与预算耗尽分作两栏来数
输出长度与成本抵达同一答案途中的绕路正确率表格里没有就两者都解出的用例比较消耗词元

这张表的第三列是要点：不在总分里显现的轴超过一半。这些轴不去测就好像不存在，而在没人测过之前就把位宽降下来，损失就会在部署之后由使用者那一侧先发现。

这并不是说八根轴都要测。顺序是先定下自己的工作究竟落在哪根轴上。只做摘要与分类的处理链路，或许有格式遵循与非英语两根轴就够；而调用工具的智能体，多步、工具调用与终止行为才是要害。逐项工作的适配判断，与对什么算够用、在哪里变得危险那边合看会更清楚。

在自己的工作里测量的步骤 - 先测再缩

不把顺序颠倒，就是这一节的全部。内存不够就先降到低位宽，觉得不对再往上调，这种做法起步于一个没有语言去描述「不对」的状态，最后往往止于「总觉得差了点」。

第1步 - 把失败的形状写成句子

自己的工作里失败长什么样？先把这个写下来。是 JSON 坏掉，是工具调用的参数出错，是长文档后面的段落被漏掉，是专有名词的写法被改动，还是没有依据的断言变多。没有失败的定义就做不出测试。

失败定义示例 - 内部文档问答
  F1  引用的段落编号与原文不符
  F2  把文档中没有的事实写进答案
  F3  输出 JSON 缺少必填键
  F4  内部产品名的写法被改动
  F5  只在文档最后30%的部分找不到答案

第2步 - 做一套只捕捉这些失败的测试

三十到一百个用例足以起步。要紧的不是数量而是构成。用容易的用例填满，位宽降下来也照样通过，什么都测不出来。要刻意混入困难用例、长用例、非英语用例与格式苛刻的用例，并且让每个用例记录的不只是通过与否，还有撞上了哪一种失败类型。

第3步 - 在原版位宽上取得基线

先在最宽的档位上跑。在这里就已经失败的用例，问题出在任务或提示上，而不在量化。不把它们筛掉，后面的比较全都会被污染。在同一条件下跑三次以上，把离散程度也一并记下。日后小于这个离散程度的差异，不算作差异。

第4步 - 一档一档往下调，重复同一套测试

固定 - 引擎构建 / 聊天模板 / 系统提示
       温度 / 随机种子 / 上下文长度 / 思考深度设置
改变 - 只改权重位宽这一项

记录 - 按类型的失败件数 / 重复之间的离散 / 消耗词元
       首次响应时间 / 常驻内存

这里常见的失误有两种。一是连着位宽把别的东西也改了：一边降位宽一边缩短上下文又调低思考深度，结果变差时就无从定位原因。二是只记录总分：不留下按类型的件数，哪根轴先折就消失了。

第5步 - 找到折断处，在上一档停住

看清在哪一档离开基线之后，选它正上方的那一档。之所以不恰好停在边界上，是因为实测条件与真实负载不同。测试跑在受控输入上，而真实输入更长也更脏。留一格余量更稳妥。推算模型规模与所需内存的一般脉络，整理在规模这个词所指的四件事那边。

这次测量没有回答的问题

越好的测量，越能说清自己没有测什么。下面记下落在这次测量范围之外的东西。

  • 迁移到其他模型 - 测的是一个系列里的一个规模。把稠密270亿规模上得出的界线原样搬到更小的模型或专家混合架构上，这次测量里没有依据
  • 非英语性能 - 三项任务全是英语。中文输入从哪一档开始写法会晃动，需要另做测试
  • 与困惑度的关系 - 原文没有把困惑度作为测量指标。常被引用的那些困惑度数值与这三项任务的结果如何对应，这次测量说不了
  • 速度与吞吐 - 文件变小通常会变快，但那个值不是这次测量的焦点。不过2位版本多写词元这一观察提示，速度上的收益可能被部分抵消
  • 长期稳定性 - 这是对某一时点文件的测量。分发方更新文件后，同一标签下的结果可能改变，而实际上测试三天之后就发生了替换

结论 - 留下的三点

第一，「从几位开始崩塌」在没有附上指标之前是没有答案的问题。同一个模型、同样的文件、同一套机器上，格式遵循撑到了2位，而科学知识与智能体编码在那一档就已经分开。与其去找一条单一的安全线，不如先定下自己的工作落在哪根轴上。

第二，平均是一个信息不足以据以决断的数字。总分相同，哪一类输入先崩塌也不会留在总分里。长上下文、罕见词汇、多步推理、格式遵循、非英语与终止行为各自对不同的东西敏感，而其中多数不在总分里显现。没测过的轴，会在部署之后由使用者那一侧先发现。

第三，先测再缩。把失败的形状写成句子，做一套只捕捉这些失败的测试，在原版位宽上取得基线与离散程度，然后固定住其他所有条件，只把位宽一档一档往下调并重复同一套测试。找到折断处之后，在上一格停住。守住这个顺序，就把「哪个模型更好」这个没有答案的问题，换成了「这个位宽在我的工作里撑不撑得住」这个有答案的问题。

未能确认的部分

  • 各指标的确切分数 - 原文以柱状图呈现结果，正文里大体以叙述带过。用眼睛从图上读出的值无法保证精度，因此没有作为数值搬进正文，只搬了原文以句子写下的叙述
  • 重复次数、温度、随机种子与样本量 - 原文里没有这些值。只有误差棒为 Wilson 95 百分比置信区间这一标注，也没有写明那个区间是由多少道题算出来的
  • 动态量化系列的内部规则 - 说明校准数据是什么、逐层位宽如何分配、带 UD 前缀与不带前缀的标签有何区别的分发方文档没能打开。文档地址已迁移，两次尝试都没有返回内容，于是按规则中止。因此正文只搬了标签的存在与系列标记，没有描述内部规则
  • K 系与 I 系标签的官方定义 - llama.cpp 仓库里的量化工具文档列出了标签清单与容量表，但没有解释 Q4_K_M 或 IQ1_S 这类名称中每个字母的含义，也没有说明重要性矩阵对哪些标签是必需的
  • UD-IQ1_M 的文件容量 - 原文记下了其他标签的容量，唯独没有记这一个
  • Q8_0 的智能体编码数值 - 原文自己写明跳过了这个组合的运行，数值是插值出来的。因此8位那个点并非实测
  • 把 KV 缓存一并收窄之后的结果 - 原文把缓存固定在 F16，只提到缓存量化以后或许会试。正文中与缓存有关的叙述止于容量计算，对质量的影响说不出数值
  • 与被替换文件的同一性 - 分发方替换2位、4位与8位文件之后，同名的当前文件是否与测试所用的相同，原文也没有下定论。想要复现的一方最先撞上的就是这一点
