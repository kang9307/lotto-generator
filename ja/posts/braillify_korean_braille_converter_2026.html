1. braillifyとは - ツール概要

braillifyは韓国語テキストをUnicode点字パターン(U+2800〜U+28FF)に変換するオープンソースのJavaScriptライブラリです。韓国の開発者コミュニティで作られたこのツールは次のアイデンティティを持ちます。

  • ライセンス:MIT - 商用利用自由
  • 対応規定:2024年改正韓国点字規定を全面反映
  • 検証水準:2,419件のテストケース通過(単体テスト基準)
  • ランタイム:ブラウザ(ES Module)+Node.js同時対応
  • 依存関係:外部パッケージ0個(zero-dependency)

一文で言えば、braillifyは「インストール直後に韓国語を点字へ変換する最軽量ライブラリ」です。従来の点字変換ツールはWindows用デスクトッププログラムか、サーバー設置型の重いソリューションが主流でした。braillifyはこの流れを断ち、静的HTMLの中でも動作するレベルまで単純化しました。

2. 点字(Braille)の基本 - 6点セルの理解

点字を見たことのない読者のために、まず構造を整理します。点字は横2点×縦3点=6点セルを1単位とします。点が浮き出ていれば1、平らなら0なので、1セルが表現できる組み合わせは2の6乗=64通りです。

Unicodeは1999年にU+2800〜U+28FFへ点字パターン256個を割り当てました。これは8点セル(コンピュータ点字)も含むためです。6点モードだけならU+2800〜U+283Fの64個が使われます。

要素説明
セル(Cell)点字1文字の単位(横2×縦3)
点(Dot)1〜6番で識別(左上から縦方向)
略字(Contraction)頻出単語を1〜2セルに圧縮した表記
略語(Abbreviation)長い単語を定型の短い点字に置換
数符(Number Sign)続くセルが数字であることを示す
大文字符(Capital Sign)続くセルが大文字であることを示す

2.1. なぜ6点・2列なのか

1825年にルイ・ブライユが点字を設計した際、基準は指先の触覚分解能でした。人差し指の腹で一度に識別できる範囲は概ね横6mm×縦9mmで、その中に6点が収まれば確実に区別できます。セルがそれより大きいと指を上げ下げする動作が増え、小さいと点同士が融合します。この人体工学的制約が200年経った今も6点セル標準を維持させています。

3. ハングル点字の特殊性

英語点字はアルファベット1文字が点字1セルに対応します。極めて直感的です。しかし韓国語は異なります。ハングルは初声・中声・終声で構成される結合文字だからです。「안녕」という2文字を字母に分解すると「ㅇ + ㅏ + ㄴ + ㄴ + ㅕ + ㅇ」の6字母になります。点字はこの字母一つひとつにセルを割り当てます。

そこに韓国語固有の規則が重なります。

  • 初声・終声の区別:同じ「ㄱ」でも初声と終声で点字パターンが異なります。
  • 略字(Contraction):「그러나」「그리고」など頻出語は単独の1セルに圧縮します。
  • 略語(Abbreviation):「대한민국」のような長い語は予め定められた略語点字に置換します。
  • 外来語処理:英単語が混在すると英語点字モードへの切替表示を挿入する必要があります。
  • 分かち書き規則:点字は通常テキストより多くの分かち書きを要求します。

これらすべての規則を正確に実装するには、単純なマッピングテーブルでは不十分で、形態素解析に近い前処理が必要です。自動化ツールが精度面で苦戦していた理由はここにあります。

4. 2024年韓国点字規定の改正

2024年の改正は、デジタル時代を初めて正面から見据えた韓国点字規定の更新です。それ以前の規定は印刷点字を前提に設計され、自動変換には曖昧な領域が多く残されていました。新規定の主な変更は次の通りです。

領域旧規定2024新規定
外来語表記英文点字切替表示が曖昧切替時点・範囲を明確化
数字処理数符の適用範囲解釈に差連続数字・小数点・コンマを一元化
略字使用一部の略字衝突あり衝突解決ルールを追加
句読点各種引用符・括弧の変形多数標準パターン5種に単純化
デジタル出力印刷のみ想定Unicode出力ガイド明示

特に最後のUnicode出力ガイドの意味は大きいです。それ以前まで点字ツールは出版社用のBRFファイルを生成し、点字プリンタに送るのが一般的でした。新規定はUnicode点字パターン(U+2800〜U+28FF)で直接出力する方式を公式化し、Webブラウザ上での点字表示や、点字ディスプレイ装置への直接送信の道を開きました。braillifyはこの流れを正確になぞります。

5. braillifyの5つの強み

本記事ではbraillifyを以下の5つの観点で評価します。

5.1. 2024新規定への完全対応

2024年新規定で導入された外来語切替表示、数符一元化、略字衝突解決の各ルールが全てコードに実装されています。既存の韓国視覚障害者協会の印刷用ツールが新規定の反映に時間を要する一方、braillifyのGitHubコミットログには改正発表直後の迅速な対応の痕跡が見えます。仕様変更へ機敏に反応できるのはオープンソースプロジェクトの大きな美徳です。

5.2. 2,419件のテストケース検証

韓国語点字変換は、字母分解・略字・外来語・数字が絡み合う「悪魔は細部に宿る」典型分野です。braillifyは単体テストだけで2,419件のケースを保持しています。一般単語、略字適用単語、英文混在、数字混在、句読点、略語、多重略字衝突など、すべての境界条件が回帰テストとして含まれます。「オープンソースだが信頼できる」ことの客観的証拠です。

5.3. JavaScriptライブラリとしての統合容易性

インストールは一行です。npm install braillify。CDN利用者はESM形式で直接importできます。APIは事実上関数1つです。入力は韓国語文字列、出力はUnicode点字文字列。オプションで略字モード、外来語モード、出力形式を切り替えます。学習コストはほぼゼロです。

5.4. オープンソース+MITライセンス

アクセシビリティツールを商用ライセンスで保護することは実は矛盾です。視覚障害者が使う道具が高価なら、アクセシビリティそのものが損なわれます。MITライセンスは誰でも自由に持ち帰り、改造し、再配布できるようにします。企業が自社キオスクに統合してもライセンス料は発生せず、学校が教育アプリに組み込んでも無料です。小さいですが重い決断です。

5.5. ブラウザとNodeの同時対応

同じコードがクライアントとサーバーの両方で動きます。つまり静的サイトのJavaScript、Next.jsのサーバーコンポーネント、AWS Lambda上のどこで実行しても変換結果は同一です。これは点字変換の正確性が環境によってブレないことを意味します。印刷用・Web用・キオスク用など多様な出力先に単一コードベースで対応できます。

7. 開発者統合方法 - 5分クイックスタート

理論は十分です。実際のコードに進みます。

7.1. インストール

npm install braillify
# またはCDN利用
#

7.2. 基本使用

import { toBraille } from 'braillify';

const text = '안녕하세요. 점자 변환 테스트입니다.';
const braille = toBraille(text);
console.log(braille);
// 出力:Unicode点字文字列(U+2800〜U+28FF領域)

7.3. オプション

const result = toBraille(text, {
  contraction: true,       // 略字適用
  abbreviation: true,      // 略語適用
  foreignMode: 'auto',     // 外来語自動切替
  format: 'unicode',       // 'unicode' | 'brf' | 'numeric'
});

7.4. Reactコンポーネント例

import { useState } from 'react';
import { toBraille } from 'braillify';

export function BrailleConverter() {
  const [input, setInput] = useState('');
  const braille = input ? toBraille(input, { contraction: true }) : '';
  return (
    <div>
      <textarea value={input} onChange={(e) => setInput(e.target.value)} />
      <div className="braille-output" aria-label="点字出力">{braille}</div>
    </div>
  );
}

7.5. サーバーサイド(Node.js / Next.js API)

// app/api/braille/route.ts (Next.js App Router)
import { toBraille } from 'braillify';

export async function POST(req) {
  const { text } = await req.json();
  const braille = toBraille(text, { contraction: true });
  return Response.json({ braille });
}

「5分」という表現は誇張ではありません。上記5ステップを踏めば、どの環境でも韓国語点字変換が即座に動作します。

8. 活用シナリオ5選

ツールが魅力的でも適用先が浮かばなければ意味がありません。braillifyが即効性を持つ5つのシナリオを整理します。

シナリオ1:視覚障害学生向け学習資料の自動変換

教科書PDF、教師が作成したプリント、塾の問題集をテキスト抽出後、braillifyで点字変換します。点字プリンタでの紙出力、または点字ディスプレイへの直接表示が可能です。従来は出版社に依頼して数カ月を待ちましたが、現在は分単位で処理できます。特殊教育現場の時間コストが劇的に下がります。

シナリオ2:点字学習アプリ

視覚障害児童の点字学習や、健常者の点字学習において、braillifyは即席変換カードを生成します。「今日の単語」モード、「クイズ」モード、「略字試験」モードなどをReact Nativeで実装すればモバイル点字学習アプリになります。教育部のデジタル教科書事業と連動する可能性もあります。

シナリオ3:公共機関文書のアクセシビリティ自動化

区役所・市役所・住民センターの案内文がPDFで発行されると、同内容の点字PDFを自動で並行生成します。政府のデジタルアクセシビリティ評価で点字提供の有無が大きな項目となりつつあり、この自動化は評価点と直結します。braillifyのBRF出力モードがここで活躍します。

シナリオ4:点字キオスク

地下鉄券売機、病院受付、空港チェックイン端末に点字ディスプレイを結合します。画面のテキストをリアルタイムでbraillifyに通して点字ディスプレイへ出力すれば、視覚障害者は職員の助けなくキオスクを利用できます。2026年以降キオスクのアクセシビリティ義務化の流れにも合致します。

シナリオ5:多言語点字(英語・日本語・中国語との違い)

braillify自体は韓国語専用ですが、同じページに英語・日本語・中国語の点字変換器を並べれば多言語点字サービスになります。英語はliblouis、日本語はBES、中国語はピンイン変換後にliblouisを使う組み合わせが可能です。グローバル観光地の案内キオスクが自然な適用先です。

9. グローバルな視点 - 英語点字 vs ハングル点字 vs 日本語点字 vs 中国語点字

ハングル点字がいかに精緻なシステムかを見るには、他言語との比較が有効です。

言語変換方式略字体系1文字あたり平均セル代表ツール
英語アルファベット1:1マッピングGrade 1 / Grade 21.0〜1.2セルliblouis
韓国語字母分解後マッピング略字・略語多層2.5〜3.0セルbraillify
日本語かな1:1マッピング限定的な略字1.5〜2.0セルBES
中国語漢字→ピンイン→点字ピンイン略字3.0〜4.0セルlibbraille

ハングル点字は「平均セル数」面で英語の約2.5倍の空間を占めます。字母分解のためです。これは点字図書の分量が印刷本よりはるかに厚くなる理由であり、デジタル点字ディスプレイの画面幅が80セル以上推奨される理由でもあります。中国語はさらに難題で、漢字を点字へ直接マッピングできないためピンイン変換が先行し、その過程で同音異義語による情報損失が発生します。韓国語が字母単位で1:1マッピング可能であることは、変換アルゴリズム設計者にとって大きな幸運です。

10. アクセシビリティ領域の未来 - AIと点字

点字は200年の歴史を持つシステムですが、デジタル・AI時代の環境は急変しています。今後5年でアクセシビリティ領域を再編するであろう3つの潮流があります。

  • リアルタイム音声→点字変換:STTで即座にテキスト化し、braillify同類の変換器で点字ディスプレイへ流せば、視覚・聴覚重複障害者もリアルタイム会話を「読む」ことができます。
  • OCR+点字自動発行:紙の本を撮影しOCRで抽出→braillifyで変換→点字PDFで保存するワークフローがモバイルアプリ1つで完結します。
  • 大規模言語モデルとの統合:LLMが要約・翻訳した結果をそのまま点字へ流せれば、視覚障害学習者も一般学習者と同等の情報アクセシビリティを得られます。ただしハルシネーション検証は点字側でも別途必要です。

AI時代のアクセシビリティは「おまけ」ではなく「基本機能」になります。そしてその基本機能を可能にするのは、braillifyのように小さく、速く、正確なツール群です。

12. 結論 - 最小のライブラリ、最大の社会的価値

braillifyは巨大なプロジェクトではありません。依存関係0、MITライセンス、単体テスト2,419件。それ自体は一人の開発者が作ったツールに見えるかもしれません。しかしこの小さなライブラリが扱う領域は、韓国の25万人の視覚障害者、そして彼らの家族・教師・同僚が触れるすべてのデジタルコンテンツです。社会的価値の密度が最も高いライブラリの一つと言えます。

2026年の韓国はアクセシビリティを「付加機能」とする時代を抜け、それを「基本機能」へ引き上げる時期にあります。その転換に必要なのは大仰な政府政策ではなく、braillifyのように小さく堅実なオープンソースツールと、それを即座に自社サービスへ導入する開発者の判断です。本記事がその判断の重みをほんの少しでも軽くできれば幸いです。
