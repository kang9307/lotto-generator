Why Korean Sorts Differently Than You Expect - Locales and Collation

Where the same list lines up differently across tools, and how to pin it down in one place

Aug 4, 2026 IT/Tech

Introduction: one dataset, three different orders

You look at a list of member names in the admin screen. You export the same list to CSV and open it. You check the uploaded attachments on the server with ls. All three are in a different order. The underlying data is identical.

When this happens, most people suspect one of two things: the encoding is broken, or the sorting code has a bug. Far more often it is neither. The three tools are each correctly applying a different sorting rule, and none of them is malfunctioning. What is broken is the assumption that sorting produces the same result wherever you do it.

Here is the conclusion up front. If ordering is a product requirement, do not leave it to shell environment variables or database server settings; state it explicitly as a collator in application code. The rest of this article explains why, and exactly where things drift apart when you do not.

The phenomenon of Hangul decomposing into jamo, and what it breaks in file systems, search and length validation, is covered in When Hangul Falls Apart Into Jamo - NFC and NFD. This article is about order only. If characters are visibly mangled, that is Locating Where Hangul Breaks; if names inside an archive are ruined, that is Where Korean File Names Break Inside a ZIP. Traps in matching Hangul with regular expressions live in The Korean Regex Trap.

Three things to take from this table.

  • The biggest split is whether Hangul comes before or after Latin. ICU's Korean collation puts Hangul first; everything else puts Latin first. Compare just two characters and it is unmistakable: in the Korean collator, compare('가', 'a') is negative, while the English, Japanese and Chinese collators all return positive.
  • _temp jumps around. In code point order the underscore is U+005F, so it lands between uppercase and lowercase letters. In collation it is treated as punctuation and moves to the very front. If your conventions use an underscore prefix for temporary or system entries, that difference shows up directly on screen.
  • In five of the six rows, 10번째 comes before 1번째. No amount of locale tuning fixes this, because numeric comparison is an axis independent of locale.

2. Code point order - why Hangul is "mostly" right

Code point sorting treats characters as numbers and compares magnitudes. It has nothing to do with how humans order things. UTS #10, the Unicode Collation Algorithm, says so in its opening pages:

The position of characters in the Unicode code charts does not specify their sort order.

And yet for Hangul the two line up remarkably well. How well? Take every one of the 11,172 syllables in the Hangul Syllables block from U+AC00 to U+D7A3, sort them by code point and by Korean collation, and compare position by position: there is not a single mismatch. A sample of 3,000 two-syllable strings gives the same answer.

That is not luck. Hangul syllable code points are laid out by the formula 0xAC00 + (initial × 588) + (medial × 28) + final, and the enumeration order of initial, medial and final jamo matches dictionary order. Final consonants follow the same structure. Checked with a Korean collator, 가 < 각, 간 < 갈 and 강 < 개 all give the same answer as raw code point comparison.

Which supports a concrete judgment: if your input contains only precomposed syllables, all in composed form, code point sorting is an exact shortcut to dictionary order. It is also the fastest option available. The question is who guarantees that precondition.

3. Where it breaks - when something else joins the list

There are three ways the precondition falls apart.

3.1 Decomposed Hangul in the list

Composed 가 is a single character, U+AC00. Decomposed 가 is two, U+1100 followed by U+1161. By code point, 0x1100 is far below 0xAC00, so decomposed forms always sort before composed ones. Mix them in a list and every decomposed entry stampedes to the front.

Input: 가방(composed) 나무(composed) 다리(composed)
       각목(decomposed) 남산(decomposed) 대구(decomposed)

Code point sort   → 각목 | 남산 | 대구 | 가방 | 나무 | 다리
Korean collator   → 가방 | 각목 | 나무 | 남산 | 다리 | 대구

The code point result bears no relation to dictionary order. Pull the same input through SQLite's default ORDER BY, or through LC_ALL=C sort, and the decomposed entries lead again. This is not a quirk of one language; it is a property of code point comparison as a rule.

Why decomposed forms enter your data at all, and which boundaries flip the form, is covered in the NFC/NFD article. What belongs here is one fact about ordering: an ICU collator considers the two forms equal. Compare composed 가방 with decomposed 가방 and you get 0, so sorting works fine. Put the same two values in a Set and its size is 2.

The gap where sorting works but deduplication does not
A collator treats the two forms as equivalent, but === and hash-based structures do not. The inference "they sorted next to each other, so duplicates must be gone" fails quietly right here. Deduplication is not the collator's job; it is normalization's.

3.2 Jamo and symbols in the mix

The compatibility jamo ㅏ is U+314F, below the syllable block, so code point sorting places it before 가. A Korean collator sends the same character to the very end of the list. If you use standalone jamo as tags or index keys, the two approaches give you opposite results.

Emoji behave similarly. Their code points are high, so they land at the end under code point ordering, but a Korean collator puts them ahead of digits. In free-form fields such as user nicknames, where anything can arrive, this difference is very visible.

3.3 Mixed case

Code point sorting herds all uppercase to the front: Apple, Banana, then apple, zebra, which nobody reads as alphabetical. Collation keeps identical spellings together and considers case only at the last level. In JavaScript you choose that level with sensitivity.

SettingWhat it distinguishesapple vs Apple
baseBase letters only0 (equal)
accentBase letters + diacritics0 (equal)
caseBase letters + caseDifferent
variant (default)Everything-1 (apple first)
caseFirst: 'upper'Uppercase first+1 (Apple first)

SQLite's NOCASE falls well short of this. The official documentation states that only the 26 ASCII letters are case folded, adding that SQLite does not attempt full UTF case folding because of the table sizes involved. In practice 'A' = 'a' COLLATE NOCASE is true while 'Ä' = 'ä' COLLATE NOCASE is false. Build a name search on NOCASE, then feed it multilingual data, and you have a quiet leak.

4. What a locale changes, and what it does not

The expectation that "setting the locale to Korean gives Korean ordering" is only half right. A locale name is a label pointing at a rule set; the rules themselves belong to whatever library interprets that name. So the same name yields different orders in different environments.

Observations from the measurement environment (see the "Environment and reproduction" section below):

  • LC_ALL=ko_KR.UTF-8 sort and LC_ALL=en_US.UTF-8 sort produce byte-identical output. Naming a Korean locale does not by itself attach Korean sorting rules.
  • Python's locale.strxfrm gives the same result under ko_KR.UTF-8, en_US.UTF-8 and Korean_Korea.949 alike.
  • Only Intl.Collator('ko') on the same machine puts Hangul ahead of Latin. ICU uses a different rule table.
  • locale.setlocale(locale.LC_COLLATE, '') follows the machine's own setting; on the measurement machine it resolved to Korean_Korea.949. If your laptop and your production server have different system locales, the same code produces different orders.

UTS #10 describes exactly this situation. The default table, DUCET, cannot satisfy every language on its own, so the specification notes that "for most languages, some degree of tailoring is required to match user expectations." ICU ships those tailorings. A given C library implementation may or may not.

Python's documentation adds one more warning. The locale is a program-wide property and setlocale() is not thread-safe on most systems. A design that flips the locale per request inside a web server is therefore not available to you.

5. Numeric sorting - file2 and file10

String comparison reaches the digit position in 파일2 and 파일10, weighs 2 against 1, and puts 파일10 first because 1 is smaller. That is the rule working as designed, and changing the locale does not touch it.

Input: 파일1.txt 파일2.txt 파일10.txt 파일20.txt 파일3.txt 파일100.txt

Default sort   → 파일1 · 파일10 · 파일100 · 파일2 · 파일20 · 파일3
Numeric on     → 파일1 · 파일2 · 파일3 · 파일10 · 파일20 · 파일100

Every toolchain has a fix.

  • JavaScript: new Intl.Collator('ko', { numeric: true })
  • GNU sort: sort -V (version sort), which produces exactly the expected order for the list above
  • Python: use a sort key that converts digit runs to int
import re, unicodedata

def natural_key(s):
    s = unicodedata.normalize('NFC', s)
    return [int(t) if t.isdigit() else t
            for t in re.split(r'(\d+)', s)]

sorted(names, key=natural_key)
The trap that comes with numeric comparison - zero padding becomes a tie
With numeric: true, comparing A-007 and A-7 returns 0, a tie, because both read as the number 7. If data written in a zero-padded era shares a table with data that was not, the order will wobble on every render. Normalize the padding, or append a unique secondary sort key.

6. Pinning it down, tool by tool

6.1 Shell - do not trust the locale, nail it down

If the order your script produces ends up in an artifact (checksum lists, manifests, diff dumps), you must fix the locale explicitly. There are two directions.

# 1) When you want reproducible byte order - same result on any machine
LC_ALL=C sort names.txt

# 2) When you want human-readable order - do not do it in the shell
#    (the same locale name can mean different rules on different machines)

The judgment call: if a machine will compare the list, pin it with LC_ALL=C; if a human will read it, do not sort in the shell at all. The worst state is leaving it vaguely at the system default. When your dev machine and your CI container disagree on LANG, the same script emits different files.

6.2 JavaScript - build the collator once and reuse it

// Build once, reuse everywhere
const collator = new Intl.Collator('ko', {
  numeric: true,          // 파일2 < 파일10
  sensitivity: 'variant', // distinguish case and diacritics
  caseFirst: 'false'      // locale default
});

names.sort(collator.compare);

Three things worth remembering.

  • Reuse the collator instance. Calling a.localeCompare(b, 'ko') inside the comparison function reassembles a collator on every call. Sorting 20,000 items, the localeCompare approach is more than twice as slow as a reused collator.
  • Never sort with usage: 'search'. MDN is explicit: "it is inappropriate to use search for sorting/ordering." Concretely, comparing 가 and 까 returns opposite signs under sort and under search. With search, only zero versus non-zero is meaningful.
  • You cannot precompute sort keys. JavaScript exposes no public API equivalent to ICU's sort key extraction, so Python's strxfrm pattern is unavailable. If performance matters, reusing the collator is effectively your only lever.

6.3 Python - between the standard library and ICU

With the standard library alone, the locale module is all there is. strxfrm transforms a string into a comparable form, and the documentation recommends it "when the same string is compared repeatedly, e.g. when collating a sequence of strings."

import locale
locale.setlocale(locale.LC_COLLATE, 'ko_KR.UTF-8')
result = sorted(names, key=locale.strxfrm)

As seen above, though, this hands the result to the machine's C library, and it is not thread-safe. If you need ICU rules, PyICU is the proper answer. If that is out of reach, the pragmatic middle ground is to build a normalization plus natural sort key yourself. It depends on no locale, so it gives the same result everywhere.

import re, unicodedata

def sort_key(s):
    s = unicodedata.normalize('NFC', s)          # decomposed to composed
    parts = re.split(r'(\d+)', s)
    return [(1, int(t), '') if t.isdigit() else (0, 0, t) for t in parts]

For lists containing only precomposed Hangul, that key alone yields exact dictionary order. The exhaustive comparison in section 2 is the evidence.

7. Databases - where you write COLLATE decides the index

There appear to be two ways to fix ordering in a database: attach COLLATE to the query, or put it in the column definition. The results match, but the costs do not.

Create a name column in SQLite, index it, and read the query plans. The difference is stark.

QueryQuery plan
ORDER BY nameSCAN t USING COVERING INDEX idx_name
ORDER BY name COLLATE NFCSCAN t
USE TEMP B-TREE FOR ORDER BY
WHERE name = ?SEARCH t USING COVERING INDEX idx_name (name=?)
WHERE name = ? COLLATE NFCSCAN t
Column declared COLLATE NFC + indexSCAN t USING COVERING INDEX idx (order also correct)

The moment you attach COLLATE to a query, you lose both the sorting index and the lookup index. The index was built under the default collation, so demanding a different rule makes it unusable. You end up building a temporary B-tree on every sort, and equality tests fall back to a full scan.

The place to fix this is the schema.

-- SQLite: declare the collation on the column, index on top of it
CREATE TABLE members (name TEXT COLLATE NOCASE);
CREATE INDEX idx_members_name ON members(name);

-- PostgreSQL: create an ICU collation and attach it to the column
CREATE COLLATION ko_icu (provider = icu, locale = 'ko-KR');
CREATE TABLE members (name text COLLATE ko_icu);

-- MySQL 8.x: pick a utf8mb4 collation on the column
CREATE TABLE members (
  name VARCHAR(100) CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_as_cs
);

Product-specific things worth knowing.

  • SQLite: there are only three built-in collations, BINARY, NOCASE and RTRIM. The default, BINARY, compares with memcmp(), which is code point order. Korean rules require registering a collation from the application.
  • PostgreSQL: two providers exist, libc and ICU. ICU collations are independent of encoding, so there is exactly one collation of a given name in a database. For stable ordering, ICU is the better choice.
  • MySQL 8.x: the Unicode collation list has no Korean-specific collation. Japanese, Chinese, Russian, German and many others are there; Korean is not on the list. The default utf8mb4_0900_ai_ci is based on UCA 9.0.0 and CLDR v30 and is accent-insensitive and case-insensitive. If name ordering must be strict, use an _as_cs variant.
Changing a collation can corrupt indexes
The PostgreSQL documentation puts it plainly: "A change in collation definitions can lead to corrupt indexes and other problems because the database system relies on stored objects having a certain sort order." It adds that this happens in legitimate circumstances, such as upgrading the operating system to a new major version or moving to server binaries linked with a newer version of ICU. The remedy is to REINDEX the affected objects and run ALTER COLLATION ... REFRESH VERSION — though the docs themselves note that this does not actually verify everything was rebuilt correctly.

8. Ties - when sorting finishes without deciding the order

A collation is allowed to declare two values equal. At that moment the final order of those items passes to the sort algorithm. JavaScript's Array.prototype.sort is stable, so input order is preserved. That sounds like a good property, but inverted it means this:

With ignorePunctuation on (compare('한-국', '한국') === 0)

Input [한-국, 한국, 한.국]  →  Output 한-국 | 한국 | 한.국
Input [한.국, 한국, 한-국]  →  Output 한.국 | 한국 | 한-국

Same data, different arrival order, different order on screen. And collation is not the only route to a tie. There are several.

  • sensitivity: 'base' or 'accent' makes values differing only in case tie
  • ignorePunctuation: true makes values differing only in hyphens or periods tie
  • numeric: true makes values differing only in zero padding tie
  • A bare ORDER BY name makes people with the same name tie

There is one fix: append something unique to the sort key. In a database that is ORDER BY name, id; in application code it means comparing by ID when the comparison function returns 0.

What this tie problem destroys when you paginate a list is covered separately in What Offset Pagination Structurally Cannot Do. When the sort key is not unique, items vanish or repeat at page boundaries.

9. Performance - what costs how much

Time to sort 20,000 Korean strings, median of five runs.

MethodTimevs. default
Default sort() (code point)10.1 ms1.0×
Intl.Collator instance reused27.0 ms2.7×
a.localeCompare(b, 'ko') per call59.5 ms5.9×

How to read it.

  • Collation costs 2.7×. Twenty-seven milliseconds for 20,000 items is not a debate on most screens. "We keep code point ordering because collation would be slow" has weak grounds at this scale.
  • The real loss is calling localeCompare directly inside the comparator. Hoisting the collator into a single line outside cuts the time in half, and the results are identical.
  • If you are sorting hundreds of thousands of rows per request, the problem is not the method but the location. Push it down to a database index.

10. The judgment - collation belongs in the application layer

Gathering everything above into one rule of thumb:

SituationWhere to pin itWhy
Lists shown to usersExplicit collator in the application layer
(Intl.Collator · ICU)		Same order regardless of environment. The options stay in code, where they can be reviewed
Paginated queries over large listsColumn collation + indexQuery-level COLLATE kills the index. Pair it with a unique tiebreaker
Scripts and CI artifactsExplicit LC_ALL=CThe goal is reproducibility, not human-readable order
Deduplication and key comparisonNFC normalizationA collator only judges equivalence; it does not merge values
File names and pathsNormalize, then compareMixed decomposed forms wreck code point ordering

The recommendation to keep collation in the application layer rests on four grounds, not taste.

  1. The same locale name does not guarantee the same order. On one machine, ko_KR.UTF-8 and en_US.UTF-8 gave identical shell sort output, while the ICU Korean collator on that same machine gave a completely different order. Environment variables are not a mechanism for pinning order.
  2. Locales are process-global and not thread-safe. A server that needs different rules per request structurally cannot use them.
  3. Database collation is dragged along by infrastructure changes. PostgreSQL warns that indexes may need rebuilding when the OS or ICU version moves. That ties your ordering rules to an infrastructure schedule.
  4. The options stay in the code. How you set numeric, sensitivity and caseFirst is visible in source. Scattered across server environment variables, nobody can explain why the screen is ordered the way it is.

None of this says avoid database sorting. If you are paging through tens of thousands of rows, the index should do the sorting. Even then, declare the collation on the column and build the index on top of it. Attaching COLLATE to the query buys the correct result while paying every cost.

12. What was not verified

The following were not measured here. Where the text rests on official documentation, it is marked as such.

  • How sort handles locales under Linux glibc. The shell measurements above come from the MSYS2 runtime on Windows. glibc may use a different collation table, so do not expect the same result. If shell sort output lands in artifacts on your server, verify it on that server.
  • Actual PyICU output. It is not installed in the measurement environment; only the standard library locale module was measured.
  • Real sorting behavior on PostgreSQL and MySQL servers. The database measurements here were done with SQLite; PostgreSQL and MySQL statements rest on each product's official documentation. The relationship between indexes and collation differs in detail per product, so check the query plan on your target version before adopting anything.
  • The details of how macOS file systems store names. This article covers only what happens to ordering when decomposed forms appear in a list; which file system stores which form and when belongs to the NFC/NFD article.
  • How much the order shifts across ICU versions. Only one version (ICU 77.1) was measured. Collation data is revised between versions, so if ordering is part of a contract, pin the ICU version and keep a regression test.

13. Frequently asked questions

If we only use precomposed Hangul, can we just use the default sort?

Yes. Across all 11,172 syllables, code point order and Korean collation order agree completely. But something in your codebase has to hold up the "only precomposed Hangul" premise. In a list fed by user input, uploaded file names and third-party API responses, that premise will not survive.

Doesn't Intl.Collator differ between browsers?

Details can differ when the bundled ICU and CLDR versions differ. So if a screen requires the same order on server and client, sort in exactly one of them. Having the server sort and the client render as-is is the more stable arrangement.

It's Korean data, so why is Hangul at the end?

Most likely the collator's locale is not ko. Only ICU's Korean collation places Hangul before Latin letters; the English, Japanese and Chinese locales all lead with Latin. If you are passing the browser's language setting straight through, the order changes from user to user.

My ORDER BY result and my screen order disagree. Which do I fix?

Do not try to reconcile them; reduce the number of places that sort to one. If the database sends back a sorted array and the frontend sorts it again, the results will keep diverging as long as the two rules differ. When pagination is needed, unify on the database side and align the column collation.

When should normalization happen?

Once, right before storage, is the cheapest option. Normalizing on every read costs you the index; normalizing only at comparison time lets both forms keep accumulating in storage. If mixed data is already stored, clean it once with a migration and block it at the input path from then on.
