Introduction - one number, four units

Unix time is an integer count of the time elapsed since 1970-01-01T00:00:00Z (the epoch). The Python documentation gives the epoch of the time module as January 1, 1970, 00:00:00 (UTC) on all platforms, and MDN says a JavaScript Date holds the milliseconds since the epoch. The reference instant is the same, but the counting unit splits into seconds, milliseconds, microseconds and nanoseconds. When the unit slips while the same integer passes between a file and an API, the date goes to early 1970 or tens of thousands of years ahead.

  • A value in seconds read as milliseconds lands inside January 1970.
  • A value in milliseconds read as seconds sends the year to the 55,000s.
  • The rule that judges the unit by digit count (10, 13, 16 and 19 digits) holds only in a certain period.
  • A 32-bit integer cannot hold a seconds value in 2038.

The questions answered here are the following.

  • Where does the date go when the same value is read as seconds, milliseconds, microseconds and nanoseconds?
  • In which instants does the digit-count rule hold, and where does it break?
  • When a detection function is written the same way in four tools, does it give the same answer?
  • How many digits do the current-time APIs of Python, Node, PowerShell and date return?
  • Where are the 32-bit boundary and the representable limit of each tool?

Date numbers with a different base date, such as Excel serial values, are covered by the Excel serial number article, changes in time zone rules by the time zone data article, and the difference between wall clocks and monotonic clocks by the monotonic clock article. This article looks only at the unit of integers based on the Unix epoch.

The digit-count rule and where it breaks

The common rule is the digit count. Ten digits are seconds, 13 are milliseconds, 16 are microseconds and 19 are nanoseconds. The instants in which this rule holds were calculated. These are the moments at which each digit count begins.

The digit rule and the threshold rule were applied to 119193 instants at intervals of about 1.01 days from 1970-01-01 to 2300-12-31. The threshold rule takes an absolute value below 1e11 as seconds, below 1e14 as milliseconds, below 1e17 as microseconds and anything above as nanoseconds. First, the dates those thresholds correspond to were calculated.

  • After 5138-11-16, when a seconds value reaches 1e11, the threshold rule also misjudges it as milliseconds. This sample stops at 2300, so that range is not included.

  • The maximum of a signed 32-bit integer, 2147483647, is 2038-01-19 03:14:07 UTC. One second later, 2147483648 is 2038-01-19 03:14:08 UTC as a 64-bit value, but wrapped into 32 bits it becomes -2147483648 and reads as 1901-12-13 20:45:52 UTC.
  • In JavaScript, (2**31)|0 is -2147483648, and the date for that value in seconds is 1901-12-13T20:45:52.000Z. Calculated as a double, the same value is 2038-01-19T03:14:08.000Z, which is correct. The bitwise operator reduces the value to 32 bits.
  • The maximum of an unsigned 32-bit integer, 4294967295, is 2106-02-07 06:28:15 UTC.
  • Milliseconds stored in a signed 32-bit integer overflow at 2147483647 milliseconds (about 24.86 days), which is 1970-01-25 20:31:23. That is 25 days after the epoch, not 2038.
  • The Python documentation says the time module may not handle dates before the epoch or far in the future, that the upper limit is set by the C library, and that on 32-bit systems it is typically in 2038. The Python on this PC converted 3000-12-31 and 3001-01-01, raised OSError for 253402300799, and the same value was represented up to 9999-12-31T23:59:59 with EPOCH + timedelta.
  • The range of a JavaScript Date is plus or minus 8,640,000,000,000,000 milliseconds. 8.64e15 is +275760-09-13T00:00:00.000Z, and adding 1 gives an Invalid Date whose getTime is NaN, so toISOString raises RangeError. This is the same range that MDN states.
  • PowerShell FromUnixTimeSeconds works up to 253402300799 (9999-12-31 23:59:59), and 253402300800 raises ArgumentOutOfRangeException. The int32 maximum and minimum convert to 2038-01-19 03:14:07 and 1901-12-13 20:45:52.
  • GNU date 8.32 converted 2147483648 and -2147483648 normally, and bash 64-bit arithmetic turned 9223372036854775807 plus 1 into -9223372036854775808.

How to fix the unit - selection criteria

Values in milliseconds or smaller before 1973-03-03 may be mixed inBoth the digit rule and the threshold rule can misjudge, so fix the unit with a separate field or nameWindow 1 of section 3 and 86400000 in section 4
Seconds values after 2286, or the threshold boundary after 5138The rule cannot decide or misjudgesWindow 4 of section 3 and 253402300799 in section 4
A conversion failure has to be received as an exceptionThe exception kind differs by tool, so put a range check firstOSError, ArgumentOutOfRange and Invalid Date in section 2
Seconds stored in an integer columnA signed 32-bit integer is limited to 2038-01-19 03:14:07 UTC, so use 64 bitsOutput of section 6
Handling nanosecond and microsecond values in JavaScriptUse BigIntThe Number conversion output of section 4
  • Do not guess the unit from the value alone; write the unit in the field name (for example sec for seconds and ms for milliseconds) or in the schema, because the ranges in which a guessing rule is correct are fixed.
  • If guessing is unavoidable, use the threshold rule but pin down its correct range (1973-03-03 to 5138-11-16) in code comments and tests.
  • When a conversion result lands in January 1970 or beyond the year 5000, suspect a unit error first.
  • When putting an instant into a 32-bit integer column, protocol or file format, 2038 is the limit, and for milliseconds the limit is 25 days.
  • Each tool reacts differently to out-of-range values (OSError, ArgumentOutOfRangeException, Invalid Date), so a value that passes in one tool may fail in another.

What Could Not Be Verified

  • The limit of Python fromtimestamp on Linux and macOS. On this PC's Windows build OSError occurred at 253402300799, but values on other platforms were not run.
  • The behavior of real systems that use a 32-bit time_t. The 2038 boundary was shown only with Python integer arithmetic and ctypes conversion.
  • The effect of leap seconds. The Python documentation says leap seconds are excluded from the seconds since the epoch, but values in a period with a leap second were not run.
  • Local time zones and daylight saving time. All output was fixed to UTC.
  • The exact boundary after 3001 at which Python fromtimestamp starts to raise OSError.
  • The units and ranges of Java, Go, C# and database timestamp types.
  • Formats whose epoch is 1601, such as Windows FILETIME, and unit confusion with Excel serial values.
  • Loss of precision when an instant is expressed as float seconds.
  • The range of FromUnixTimeSeconds in .NET versions other than the one under PowerShell 5.1.
