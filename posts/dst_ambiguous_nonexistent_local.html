서론 - 지역 시각은 한 순간을 가리키지 못하는 날이 있다

지역 시각은 「2026-03-08 02:30」처럼 날짜와 시계 표기만 가진 값이다. 이 값이 하나의 순간(UTC 기준 시각)으로 정해지려면 시간대 규칙이 필요하고, 서머타임이 있는 지역에서는 전환일에 그 대응이 깨진다. 시계를 앞으로 돌리는 날에는 시계가 건너뛰는 구간이 있어 그 안의 표기는 어떤 순간에도 대응하지 않는다. 시계를 뒤로 돌리는 날에는 같은 표기가 두 번 지나가므로 하나의 표기가 두 순간에 대응한다.

이 현상에는 이름이 있다. 존재하지 않는 지역 시각은 영어권 문서에서 gap, nonexistent, invalid time이라 부르고 두 번 오는 시각은 overlap, repeated, ambiguous time이라 부른다. 아래에서는 앞의 것을 「구멍」, 뒤의 것을 「중복 시각」이라 쓴다. 도구마다 이 두 경우에 대한 기본 동작이 다르다는 것이 실행 결과이며, 같은 문자열이 도구에 따라 한 시간씩 다른 UTC로 바뀐다.

시간대 규칙이 데이터이며 갱신되면 과거 시각의 해석도 바뀐다는 점과 전환 구간에서 24시간 뒤와 내일 같은 시각이 다르다는 점은 타임존은 코드가 아니라 데이터다가 Python 출력으로 다뤘다. 여기서는 Python 한 도구의 설명을 넘어, 같은 입력을 Node.js와 PowerShell 5.1이 어떻게 해석하는지, 그리고 그 차이를 막는 저장 규칙을 비교한다.

다루는 질문은 다음과 같다.

  • UTC 순간을 지역 시각으로 바꾸어 나열하면 구멍과 중복은 어떻게 보이는가.
  • Python zoneinfo의 fold는 구멍과 중복에서 각각 무엇을 고르는가.
  • Node.js의 Date 생성자는 구멍과 중복을 어떻게 풀고, 되읽으면 값이 바뀌는가.
  • PowerShell 5.1의 TimeZoneInfo는 두 경우를 어떻게 판별하고 변환하는가.
  • 오프셋을 붙인 문자열과 UTC 저장은 어디까지 모호함을 없애는가.
  • 서머타임이 없는 Asia/Seoul은 이 문제에서 비교 기준으로 어떻게 보이는가.

UTC에서 보면 구멍과 중복이 보인다

지역 시각을 입력으로 받는 쪽에서는 구멍이 보이지 않는다. 반대로 UTC 순간을 30분 간격으로 늘어놓고 각 순간을 America/New_York의 지역 시각으로 표시하면 어디에 구멍이 있고 어디가 겹치는지 한눈에 드러난다. Intl.DateTimeFormat의 formatToParts로 연·월·일·시·분과 약칭을 읽는 코드다.

const f = new Intl.DateTimeFormat('en-CA', {
                      timeZone: 'America/New_York', year: 'numeric', month: '2-digit', day: '2-digit',
                      hour: '2-digit', minute: '2-digit', hourCycle: 'h23', timeZoneName: 'short'
                    });
                    function walk(startIso, n) {
                      let t = Date.parse(startIso);
                      for (let i = 0; i < n; i++, t += 1800000) {
                        const o = {};
                        f.formatToParts(new Date(t)).forEach(p => o[p.type] = p.value);
                        console.log(new Date(t).toISOString().slice(11, 16) + 'Z', '->',
                          o.year + '-' + o.month + '-' + o.day + ' ' + o.hour + ':' + o.minute, o.timeZoneName);
                      }
                    }
                    console.log('node ' + process.version + ' / tz data ' + process.versions.tz);
                    console.log('-- spring');

                    console.log('-- autumn');

봄 구간에서는 06:30Z가 01:30 EST이고 다음 샘플인 07:00Z가 곧바로 03:00 EDT이다. 표시된 지역 시각 중에 02시대가 없다. 가을 구간에서는 05:00Z와 05:30Z가 01:00·01:30 EDT, 06:00Z와 06:30Z가 다시 01:00·01:30 EST이다. 지역 시각 01시대가 한 시간 간격의 두 순간에 한 번씩 나타나고, 둘을 구별하는 것은 약칭(EDT·EST)뿐이다. 약칭이 식별자로 쓸 수 없는 이유는 앞선 글의 약칭 절이 따로 다룬다.

  • 샘플 간격이 30분이라 02:00에서 02:59 사이는 이 출력만으로는 비어 있는 것으로만 보이며, 구간 전체가 비어 있다는 것은 다음 절의 분 단위 판별 출력이 보여 준다.
  • 전환은 UTC 축에서는 연속이다. 06:30Z 다음이 07:00Z이고 그 사이 순간은 모두 존재한다. 어긋나는 것은 지역 시각이라는 표기 쪽이다.
  • 가을의 중복은 지역 시각 문자열이 같고 UTC가 다른 두 순간이다. 문자열을 키로 쓰면 서로 다른 두 순간이 한 키로 합쳐진다.

Python zoneinfo - fold가 고르는 것

Python 3.9 이상의 zoneinfo는 IANA 이름으로 시간대를 만들고, datetime의 fold 속성으로 반복 구간의 두 순간을 구별한다. 공식 문서(datetime 모듈)는 fold를 「반복 구간에서 벽시계 시각을 구별하는 데 쓰는 값」으로 설명하며 「0과 1은 같은 벽시계 표기를 가진 두 순간 중 각각 이른 쪽과 늦은 쪽」이라고 적는다. 아래 코드는 구멍(03-08 02:30)과 중복(11-01 01:30)에 fold 0과 1을 넣고, 이어서 분 단위로 정상·구멍·중복을 판별한다. Windows에서 zoneinfo는 tzdata 패키지가 있어야 동작하며, 이 PC에는 tzdata 2025.3이 설치되어 있다.

import sys
                    from datetime import datetime, timezone
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    UTC = timezone.utc
                    print("python", sys.version.split()[0])
                    
                    
                    def show(naive, fold):
                        dt = naive.replace(tzinfo=ny, fold=fold)
                        u = dt.astimezone(UTC)
                        back = u.astimezone(ny)
                        print(naive.strftime("%Y-%m-%d %H:%M"), "fold=%d" % fold, "offset", dt.strftime("%z"),
                              "-> UTC", u.strftime("%H:%MZ"), "-> back", back.strftime("%H:%M"), back.tzname())
                    
                    
                    show(datetime(2026, 3, 8, 2, 30), 0)
                    show(datetime(2026, 3, 8, 2, 30), 1)
                    show(datetime(2026, 11, 1, 1, 30), 0)
                    show(datetime(2026, 11, 1, 1, 30), 1)
                    print("default fold:", datetime(2026, 11, 1, 1, 30, tzinfo=ny).fold)
                    
                    
                    def classify(naive, tz):
                        a = naive.replace(tzinfo=tz, fold=0)
                        b = naive.replace(tzinfo=tz, fold=1)
                        back = a.astimezone(UTC).astimezone(tz).replace(tzinfo=None)
                        if back != naive:
                            return "nonexistent"
                        return "ambiguous" if a.utcoffset() != b.utcoffset() else "normal"
                    
                    
                    print()
                    for s in ["2026-03-08 01:59", "2026-03-08 02:00", "2026-03-08 02:59", "2026-03-08 03:00",
                              "2026-11-01 00:59", "2026-11-01 01:00", "2026-11-01 01:59", "2026-11-01 02:00"]:
                        print(s, classify(datetime.strptime(s, "%Y-%m-%d %H:%M"), ny))

중복(11-01 01:30)에서는 문서가 말한 그대로다. fold=0은 이른 순간인 EDT(-0400)로 05:30Z, fold=1은 늦은 순간인 EST(-0500)로 06:30Z이고, 두 값을 다시 지역 시각으로 되돌리면 모두 01:30이다. 구멍(03-08 02:30)에서는 출력이 보여 주는 동작이 다음과 같다. fold=0은 전환 전 오프셋 -0500을 적용해 07:30Z가 되고, 이 순간을 지역 시각으로 되돌리면 03:30 EDT이다. fold=1은 전환 후 오프셋 -0400을 적용해 06:30Z가 되며 되돌리면 01:30 EST이다. 구멍 안의 시각은 예외 없이 변환되지만, 되돌린 값이 입력과 다르다.

판별 코드의 원리는 왕복 변환이다. 지역 시각을 UTC로 바꾸었다가 되돌려 값이 달라지면 구멍이고, 같은데 fold 0과 1의 오프셋이 다르면 중복이다. 출력에서 02:00부터 02:59까지가 모두 구멍이고 01:00부터 01:59까지가 모두 중복이며 01:59와 03:00은 정상이다. 기본 fold 값은 0이라고 출력의 마지막 줄 바로 위에서 확인된다. fold를 지정하지 않은 코드는 중복에서 이른 쪽을, 구멍에서 전환 전 오프셋을 조용히 고른다.

같은 tzinfo를 가진 두 aware datetime을 비교하거나 빼면 tzinfo와 fold가 무시된다는 공식 문서 문장이 있다(「the tzinfo and fold attributes are ignored and the base datetimes are compared」). 같은 지역 시각의 fold 0과 1이 == 으로 같다고 나오는 이유이며, 이 비교로는 한 시간 차이를 알 수 없다. 이 문제는 앞선 글의 DST 경계 절이 숫자로 보여 주었으므로 여기서는 비교 대신 UTC로 바꾼 뒤 비교하는 방식만 취한다. 같은 지역 시각의 fold 0과 1을 직접 비교하면 다음과 같다.

from datetime import datetime
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    a = datetime(2026, 11, 1, 1, 30, tzinfo=ny, fold=0)
                    b = datetime(2026, 11, 1, 1, 30, tzinfo=ny, fold=1)
                    print("a == b:", a == b, "| offsets:", a.strftime("%z"), b.strftime("%z"))
a == b: True | offsets: -0400 -0500

비교는 True이지만 두 값의 오프셋은 -0400과 -0500으로 한 시간 차이이다.

JavaScript Date - 구멍은 앞으로, 중복은 먼저

Node.js의 Date는 지역 시각을 필드(연·월·일·시·분)로 받으면 현재 프로세스의 시간대 규칙으로 해석한다. MDN의 Date 문서는 오프셋 전환 구간의 지역 시각을 설정할 때 Temporal의 disambiguation 「compatible」과 같은 동작을 쓴다고 적고, 「지역 시각이 두 순간에 대응하면 이른 쪽을 고르고, 존재하지 않으면(구멍) 구멍의 길이만큼 앞으로 간다」고 설명한다(원문 표현: the earlier one is chosen; ... we go forward by the gap duration). 시간대는 스크립트 안에서 process.env.TZ로 America/New_York을 지정했다. 아래 코드는 입력 필드와 읽어 되돌린 필드를 함께 출력한다.

process.env.TZ = 'America/New_York';
                    const pad = n => String(n).padStart(2, '0');
                    function probe(y, mo, d, h, mi) {
                      const x = new Date(y, mo - 1, d, h, mi);
                      const asked = y + '-' + pad(mo) + '-' + pad(d) + ' ' + pad(h) + ':' + pad(mi);
                      const got = x.getFullYear() + '-' + pad(x.getMonth() + 1) + '-' + pad(x.getDate()) + ' ' + pad(x.getHours()) + ':' + pad(x.getMinutes());
                      console.log(asked, '->', x.toISOString(), 'reads back', got, asked === got ? '(same)' : '(CHANGED)');
                    }
                    probe(2026, 3, 8, 1, 59);
                    probe(2026, 3, 8, 2, 0);
                    probe(2026, 3, 8, 2, 30);
                    probe(2026, 3, 8, 3, 0);
                    probe(2026, 11, 1, 0, 59);
                    probe(2026, 11, 1, 1, 30);
                    probe(2026, 11, 1, 2, 0);
                    console.log(new Date('2026-03-08T02:30:00').toISOString());
                    console.log(new Date('2026-11-01T01:30:00').toISOString());

구멍의 02:00과 02:30은 각각 03:00과 03:30으로 읽혀 돌아온다. 순간으로는 07:00Z와 07:30Z이며, 파이썬 fold=0의 07:30Z와 같다. 구멍 안의 입력이 예외 없이 한 시간 뒤의 값으로 바뀐다. 중복의 01:30은 05:30Z이고 되읽은 값도 01:30이므로 변화가 없다. 그러나 이른 쪽(EDT)을 골랐다는 사실은 필드만 봐서는 알 수 없고 UTC를 찍어야 보인다. 마지막 두 줄이 보여 주듯 오프셋이 없는 ISO 문자열(예: 2026-03-08T02:30:00)도 같은 규칙으로 지역 시각 해석을 거쳐 같은 순간이 된다.

  • Date의 구멍은 이 코드처럼 getXxx로 필드를 읽어 입력과 비교하면 알아낼 수 있다. 02:00과 02:30이 CHANGED로 찍힌 줄이 그 신호다.
  • 중복은 읽어 되돌려도 값이 같아서 이 방식으로 알 수 없다. UTC 값이 두 개일 수 있다는 사실을 코드가 따로 알아야 한다.
  • TZ 환경 변수 방식의 위험(프로세스마다 지역이 달라짐)은 앞선 글의 환경 변수 절이 Node.js 출력으로 보였다.

PowerShell 5.1 - 중복은 표준시, 구멍은 예외

PowerShell에서는 .NET의 TimeZoneInfo를 쓴다. 시간대 이름은 IANA가 아니라 Windows 식별자(Eastern Standard Time)이며, 이 PC의 조회 결과 SupportsDaylightSavingTime은 True이다. 이 API에는 판별 메서드가 있다. 공식 문서는 IsAmbiguousTime을 「한 시각이 둘 이상의 UTC 시각에 대응할 수 있는지 판정」한다고 정의하며, ConvertTimeToUtc에 대해서는 「모호한 시각이면 표준시로 가정하고, 잘못된(invalid) 시각이면 ArgumentException을 던진다」고 적는다.

[System.Threading.Thread]::CurrentThread.CurrentUICulture = [System.Globalization.CultureInfo]::GetCultureInfo('en-US')

UTC에서 지역 시각으로 갈 때도 함정이 있다. 이 PC(로컬 시간대 Korea Standard Time)에서 ConvertTimeFromUtc가 돌려준 DateTime의 Kind는 Unspecified였고 오프셋 정보가 없다. 로컬 시간대가 다른 PC에서는 Kind와 해석이 달라질 수 있다. 아래 코드는 가을 중복의 두 순간(05:30Z와 06:30Z)을 지역 시각으로 바꿨다가 UTC로 되돌리고, 같은 두 순간을 DateTimeOffset으로 바꾼 결과와 비교한다.

같은 시각이 하루에 몇 번 오는가 - 0번, 1번, 2번

매일 02:30에 도는 작업이나 01:30으로 잡은 알림을 생각하면 문제가 선명해진다. 지역 시각 하나가 하루에 나타나는 횟수를 세어 보면 전환일의 값이 평소와 다르다. 다음 코드는 UTC 축을 15분 단위로 훑어 지역 시각이 정확히 그 값인 순간을 모은다.

from datetime import datetime, timedelta, timezone
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    UTC = timezone.utc
                    
                    
                    def occurrences(y, m, d, hh, mm, tz):
                        # UTC instants whose wall clock in tz reads exactly y-m-d hh:mm (15-minute scan, +-14 h)
                        base = datetime(y, m, d, hh, mm, tzinfo=UTC)
                        hits = []
                        for k in range(-14 * 60, 14 * 60 + 1, 15):
                            u = base + timedelta(minutes=k)
                            w = u.astimezone(tz)
                            if (w.year, w.month, w.day, w.hour, w.minute) == (y, m, d, hh, mm):
                                hits.append(u.strftime("%H:%MZ"))
                        return hits
                    
                    
                    for y, m, d, hh, mm in [(2026, 3, 7, 2, 30), (2026, 3, 8, 2, 30), (2026, 3, 9, 2, 30),
                                            (2026, 10, 31, 1, 30), (2026, 11, 1, 1, 30), (2026, 11, 2, 1, 30)]:
                        h = occurrences(y, m, d, hh, mm, ny)
                        print("%d-%02d-%02d %02d:%02d" % (y, m, d, hh, mm), "->", len(h), "time(s)", h)

안전하게 다루는 규칙 - 막을 것과 고를 것

앞의 실행에서 두 가지가 드러났다. 지역 시각 문자열은 구멍에서 값이 없고 중복에서 값이 둘이다. 그리고 도구의 기본 선택은 서로 다르다. 그래서 규칙은 기본 선택에 맡기지 않고 입력 단계에서 정책을 정하는 것이다. 아래 코드는 Python에서 구멍은 예외로 거부하고 중복은 fold가 없으면 거부하며 fold가 있으면 변환하는 함수다.

from datetime import datetime, timezone
                    from zoneinfo import ZoneInfo
                    
                    UTC = timezone.utc
                    
                    
                    def to_utc(naive, tz, fold=None):
                        a = naive.replace(tzinfo=tz, fold=0)
                        b = naive.replace(tzinfo=tz, fold=1)
                        if a.astimezone(UTC).astimezone(tz).replace(tzinfo=None) != naive:
                            raise ValueError("nonexistent local time: " + naive.isoformat(" "))
                        if a.utcoffset() != b.utcoffset():
                            if fold is None:
                                raise ValueError("ambiguous local time: " + naive.isoformat(" ") + " (fold=0 or fold=1 required)")
                            return (b if fold else a).astimezone(UTC)
                        return a.astimezone(UTC)
                    
                    
                    ny = ZoneInfo("America/New_York")
                    for n, f in [(datetime(2026, 3, 8, 2, 30), None), (datetime(2026, 3, 8, 3, 30), None),
                                 (datetime(2026, 11, 1, 1, 30), None), (datetime(2026, 11, 1, 1, 30), 0),
                                 (datetime(2026, 11, 1, 1, 30), 1)]:
                        try:
                            print(n.isoformat(" "), "fold=%s" % f, "->", to_utc(n, ny, f).isoformat())
                        except ValueError as e:
                            print(n.isoformat(" "), "fold=%s" % f, "-> ValueError:", e)

  • 순간을 저장할 때는 UTC 시각(또는 오프셋이 붙은 시각)을 쓴다. 오프셋을 붙여 넘긴 출력(앞의 오프셋 절)에서는 UTC 값이 모든 도구에서 같았고, 오프셋 없이 지역 시각만 넘긴 출력(앞의 비교 표)에서는 도구마다 갈렸다.
  • 사람이 입력한 지역 시각은 시간대 이름과 함께 받는다. 시간대 이름이 없으면 구멍과 중복을 판정할 수 없다.
  • 구멍은 입력 오류로 되돌려 사용자에게 다른 시각을 고르게 한다. 조용히 한 시간 뒤로 보정하는 동작(Node.js)은 사용자가 입력한 값을 바꾼다.
  • 중복은 두 후보(05:30Z와 06:30Z)를 보여 주고 고르게 하거나, 정책(이른 쪽 또는 늦은 쪽)을 코드에 명시한다. 도구의 기본값에 맡기면 PowerShell과 Python이 서로 다른 쪽을 고른다.
  • .NET에서는 UTC에서 지역 시각으로 바꾼 DateTime을 다시 UTC로 돌리지 않는다. DateTimeOffset으로 오프셋을 함께 들고 간다.
  • 오프셋이 붙은 입력도 안심할 수 없다. 앞의 오프셋 절에서 구멍(03-08 02:30)에 -04:00을 붙인 문자열은 06:30Z로 해석됐고, 이는 지역 시각 01:30 EST인 순간이다. 받은 오프셋이 그 시간대에서 가능한 조합인지 따로 검사한다.
  • 시험 데이터에 2026-03-08 02:30과 2026-11-01 01:30처럼 구멍과 중복을 넣고, 지역 시각 문자열을 키로 쓰는 코드를 점검한다.

DB 쪽의 같은 문제, 곧 세션 시간대가 AT TIME ZONE 연산의 결과 타입에 끼어드는 문제는 PostgreSQL AT TIME ZONE 글이 따로 다룬다. 시각과 정수 사이의 변환에서 단위가 갈리는 문제는 타임스탬프 변환 글이 다룬다.

확인하지 못한 것

  • 리눅스·macOS에서의 Node.js·Python·PowerShell 동작. 모든 출력은 이 Windows PC에서 얻은 값이다.
  • PowerShell 7(.NET 8 이후)의 TimeZoneInfo가 IANA 이름을 받는 방식과 구멍·중복 처리. 이 PC에는 pwsh가 설치되어 있지 않다.
  • ECMAScript 사양 본문의 해당 알고리즘. 사양 페이지에서 해당 절을 열지 못해 MDN 문서의 설명만 인용했다.
  • Python에서 구멍의 fold 0·1이 전환 전·후 오프셋을 고르는 동작의 문서 근거. 열어 본 datetime 문서는 fold를 반복 구간 용도로만 설명했고, 구멍의 동작은 출력으로만 확인했다.
  • Windows 시간대 데이터에 1988년 서머타임이 없는 이유, 그리고 다른 Windows 빌드에서의 결과. 조정 규칙 수 0은 이 PC에서 읽은 값이다.
  • 30분 단위 전환이나 자정에 전환이 일어나는 시간대에서의 동작, 그리고 스케줄러(cron·작업 스케줄러)가 전환일에 작업을 0번·2번 실행하는지 여부.
  • Temporal API(이 Node.js 버전에서는 정의되어 있지 않다)의 disambiguation 옵션 동작과 Python의 pytz·dateutil 같은 다른 라이브러리.
