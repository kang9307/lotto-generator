CUDA 커널을 실행하면 GPU 내부에서 벌어지는 일

호스트 런치부터 워프 실행·메모리 계층·점유율까지 — 단계별 완전 분석

2026-07-01 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 단 한 줄이 불러오는 거대한 파이프라인

딥러닝 모델을 학습시키거나, GPU를 이용한 과학 시뮬레이션을 돌리거나, 고성능 그래픽을 렌더링할 때 우리는 CUDA 커널을 실행한다. 코드 상에서는 단 한 줄의 런치 호출이지만, 그 뒤편에서는 호스트 CPU의 드라이버 호출, GPU 커맨드 큐, 수천 개 스레드의 동시 스케줄링, 여러 계층의 메모리 접근이 유기적으로 맞물린다.

이 글은 2026년 6월 기준, 그 파이프라인을 처음부터 끝까지 단계별로 해부한다. 목표는 두 가지다. 하나는 "왜 GPU가 이렇게 동작하는가"에 대한 개발자 수준의 직관을 쌓는 것이고, 다른 하나는 딥러닝과 AI 추론 가속의 토대가 왜 CUDA 내부 구조에 달려 있는지 이해하는 것이다. vectorAdd<<<4096, 256>>>(a, b, c, N); 같은 코드를 처음 쓰는 사람도, GPU 최적화를 공부 중인 ML 엔지니어도 이 글에서 구체적 그림을 얻을 수 있을 것이다.

하나의 전제를 분명히 한다. GPU 마이크로아키텍처의 세부는 세대마다 다르고, 상당 부분은 NVIDIA가 공개하지 않는다. 여기서는 RTX 40 계열과 H100 같은 현 세대 Hopper/Ada 아키텍처를 기준으로 공개된 문서와 역공학 연구를 바탕으로 서술한다. 숫자는 방향을 이해하기 위한 것이지, 벤치마크 데이터가 아님을 감안하고 읽기 바란다.

1단계: 호스트에서 커널을 런치하기까지

1.1 nvcc 컴파일 파이프라인

CUDA 코드는 .cu 파일에서 시작해 nvcc를 거친다. nvcc는 호스트 코드와 디바이스 코드를 분리한 뒤, 디바이스 코드를 두 단계로 컴파일한다. 첫 단계는 PTX(Parallel Thread Execution)라는 가상 ISA(명령 집합 아키텍처)로의 변환이다. PTX는 무한한 가상 레지스터를 가정하고, GPU 마이크로아키텍처로부터 추상화된 이식성 높은 중간 표현이다. 두 번째 단계는 실제 GPU 기계어인 SASS(Shader Assembly)로의 변환이다. RTX 4090은 sm_89 대상의 SASS를 생성한다. 최종 바이너리인 fatbin에는 cubin(기계어)과 PTX가 함께 묶여 실행 파일에 삽입된다. 새 GPU 세대에서 PTX를 통해 JIT 컴파일이 가능한 것은 이 구조 덕분이다.

1.2 호스트 스텁과 드라이버 호출

런타임에 kernelFunc<<>>(args...)를 호출하면, nvcc가 생성한 호스트 스텁(stub)이 실행된다. 스텁은 런타임 등록 테이블에서 커널을 찾는 키 역할을 하고, 인자들을 argument buffer에 정렬한다. 첫 번째 GPU 호출 시에는 libcuda.so가 동적 로드되고 GPU 컨텍스트가 생성된다. 이 초기화 비용은 크지만 이후엔 재사용된다. strace로 추적하면 벡터 덧셈 하나에도 수백 개의 ioctl이 발생하는데, 대부분은 one-time 설정 비용이다.

1.3 QMD, pushbuffer, GPFIFO, doorbell

드라이버는 QMD(Queue Meta Data)를 구성한다. QMD는 커널 런치 디스크립터로, 그리드 크기, 블록 크기, 스레드당 레지스터 수, 공유 메모리 요구량, 프로그램 시작 주소, 커널 인자가 있는 constant bank 주소, 완료 신호 위치를 모두 담는다. 드라이버는 이 QMD를 pushbuffer에 기록하고, GPFIFO 엔트리가 이를 가리킨다. 마지막으로 doorbell MMIO 쓰기로 GPU에 새 작업이 왔음을 알린다. 여기서부터 제어권은 CPU에서 GPU로 넘어간다.

2단계: 그리드·블록·SM 구조 — 작업이 어떻게 분배되나

2.1 그리드와 블록의 계층

CUDA 실행 계층은 그리드 → 블록 → 스레드 3단계다. 그리드는 커널 런치 하나에 대응하는 최상위 단위다. 그리드는 1D·2D·3D 형태로 블록을 배열할 수 있고, 블록도 마찬가지다. 이 다차원 구조는 이미지 처리(2D)나 체적 시뮬레이션(3D) 같은 문제에서 인덱스 계산을 자연스럽게 만들어 준다. 스레드 ID는 다차원 구조를 행 우선(row-major) 순서로 선형화해 계산한다.

2.2 SM에 블록이 할당되는 방식

GPU의 물리적 실행 단위는 SM(스트리밍 멀티프로세서)이다. H100은 144개, RTX 4090은 128개 SM을 갖는다. 커널 그리드의 블록들은 SM에 나뉘어 할당된다. 같은 블록 내 스레드는 반드시 같은 SM에서만 실행된다는 규칙이 핵심이다. 이 덕분에 같은 블록의 스레드는 공유 메모리를 공유하고 __syncthreads()로 동기화할 수 있다. 서로 다른 블록은 독립적이고, 실행 순서를 가정하면 안 된다. SM이 한 번에 수용할 수 있는 블록 수는 레지스터·공유 메모리·하드웨어 제한에 의해 결정된다.

2.3 SM 내부 구조

SM 안에는 CUDA 코어(FP32/INT32 실행 유닛), 특수 함수 유닛(SFU), 텐서 코어(행렬 연산 전용), 워프 스케줄러, 레지스터 파일, L1 캐시/공유 메모리(통합)가 있다. H100 SM 하나에는 128개 FP32 코어와 4개의 워프 스케줄러가 있다. 각 워프 스케줄러는 매 사이클 eligible한 워프에서 명령을 발행할 수 있다. SM이 여러 워프를 동시에 보유하고 교대로 실행하는 것이 GPU 지연 숨기기의 핵심 메커니즘이다.

3단계: 워프와 SIMT 실행 — 32개가 함께 뛴다

3.1 워프란 무엇인가

워프(warp)는 SM이 스케줄링하는 기본 단위로, 32개의 스레드로 구성된다. 블록의 스레드들은 스레드 ID 기준으로 32개씩 묶여 워프가 된다. 256 스레드 블록은 8개 워프로 분할된다. 워프 내 32개 스레드는 동일한 명령을 동일한 클럭 사이클에 실행한다. 이것이 SIMT(Single Instruction Multiple Thread) 모델이다. 각 스레드는 독립적인 레지스터와 프로그램 카운터를 가지지만, 정상 흐름에서는 같은 명령을 함께 실행한다.

3.2 SIMT가 SIMD와 다른 점

CPU의 SIMD는 프로그래머나 컴파일러가 명시적으로 벡터 연산을 지정해야 한다. 반면 SIMT는 스레드마다 스칼라 코드를 작성해도 하드웨어가 32개 스레드를 묶어 병렬 실행한다. 개발자 경험이 훨씬 단순하다. 단, SIMT는 워프 내 모든 스레드가 같은 경로를 실행한다는 가정 위에 성능이 서 있다. 이 가정이 깨지면 워프 다이버전스가 발생한다.

3.3 워프 스케줄링과 지연 숨기기

SM은 동시에 실행 가능한 것보다 훨씬 많은 워프를 보유(in-flight)한다. 한 워프가 글로벌 메모리 접근 대기(수백 사이클 지연)에 들어가면, 스케줄러는 그 워프를 잠시 내려놓고 ready 상태의 다른 워프를 즉시 발행한다. 이 "무오버헤드 컨텍스트 스위칭"이 GPU의 메모리 지연 숨기기 전략이다. CPU처럼 레지스터를 저장하거나 복원하는 비용이 없다. 워프의 레지스터는 전환 중에도 SM 레지스터 파일에 그대로 남아 있기 때문이다. 워프가 eligible 상태가 되려면 scoreboard(변동 지연 명령 대기)와 stall counter(고정 지연 명령 대기) 조건을 모두 통과해야 한다.

4단계: 워프 다이버전스 — 조건문이 성능을 죽이는 이유

4.1 다이버전스가 발생하는 상황

워프 내 32개 스레드가 if·for·switch 등의 조건문에서 서로 다른 분기를 타면 워프 다이버전스가 발생한다. GPU 하드웨어는 SIMT 방식이므로 워프 전체가 같은 명령을 실행해야 한다. 분기가 갈리면 A 경로를 실행할 때 B 경로의 스레드는 마스킹(비활성화)되고, B 경로를 실행할 때 A 경로의 스레드가 마스킹된다. 결국 두 경로를 순차적으로 실행하게 된다. 분기가 두 갈래면 실행 사이클이 최대 2배, N 갈래면 N배로 늘어날 수 있다.

4.2 다이버전스를 줄이는 설계 원칙

핵심 원칙은 같은 워프 내 스레드가 같은 코드 경로를 타도록 데이터를 배열하는 것이다. 예를 들어, 홀짝 스레드가 다른 분기를 타는 코드는 최악이다. 반면 데이터를 정렬하거나 분기 조건이 블록 단위로 균일하도록 하면 다이버전스를 최소화할 수 있다. 불가피한 분기라면, 워프가 처음부터 같은 경로에 있도록 데이터를 미리 파티셔닝하는 것이 낫다. 현대 GPU는 Thread Block Compaction 같은 기법으로 다이버전스를 하드웨어 수준에서 일부 완화한다.

5단계: 메모리 계층 — 레지스터부터 글로벌까지

5.1 레지스터 — 가장 빠르고 가장 비싼

레지스터는 스레드 전용의 가장 빠른 저장 공간이다. 접근 지연은 1사이클에 불과하다. H100 SM 하나당 65,536개의 32비트 레지스터가 있다. 컴파일러는 PTX의 가상 레지스터를 실제 레지스터에 매핑하는데, 스레드당 레지스터 사용량이 많아지면 SM이 동시에 수용할 수 있는 스레드 수(워프 수)가 줄어든다. 레지스터가 넘치면 레지스터 스필(register spill)이 발생해 지역 메모리(실제로는 글로벌 메모리에 적재)로 넘어가고 성능이 크게 떨어진다.

5.2 공유 메모리 — 블록 내 스레드의 협업 공간

공유 메모리(shared memory)는 같은 블록 내 스레드가 공유하는 온칩 메모리다. 접근 지연은 약 25사이클로, 글로벌 메모리(약 350~1000사이클)에 비해 수십 배 빠르다. L1 캐시와 물리적으로 같은 SRAM을 나눠 쓰며, H100의 경우 SM당 최대 228KB를 설정할 수 있다. __shared__ 키워드로 선언한다. 행렬 곱셈의 타일링(tiling) 최적화가 공유 메모리를 활용하는 대표 사례다. 단, 뱅크 충돌(bank conflict)을 주의해야 한다. 공유 메모리는 32개 뱅크로 분할되어 있고, 같은 워프의 여러 스레드가 같은 뱅크에 접근하면 직렬화된다.

5.3 글로벌 메모리 — 광활하지만 느리다

글로벌 메모리(global memory)는 GPU VRAM 전체에 해당하며, 모든 스레드가 접근 가능하다. H100은 HBM3 기반으로 3TB/s의 대역폭을 제공하지만, 레이턴시는 TLB 히트 기준 약 350사이클, 미스 시 1000사이클 이상이다. 이 지연을 숨기려면 충분한 워프를 in-flight 상태로 유지해야 하며, 합착 접근(coalesced access)이 필수다. 워프의 32개 스레드가 연속된 메모리 주소를 접근하면 한 번의 트랜잭션으로 처리되지만, 스트라이드가 크거나 랜덤 접근이면 여러 트랜잭션으로 분해되어 대역폭이 낭비된다.

5.4 L1/L2 캐시와 텍스처 메모리

글로벌 메모리 접근은 L1(SM 내부, 공유 메모리와 공유) → L2(GPU 전체 공유) 캐시 계층을 거친다. RTX 4090은 72MB의 L2 캐시를 갖는다. 캐시에 히트하면 지연이 대폭 줄어든다. 읽기 전용·공간 지역성이 높은 데이터는 텍스처 메모리(텍스처 캐시 경유)를 활용하면 추가 이득을 얻을 수 있다. 메모리 계층 전체를 정리하면 다음과 같다.

메모리 유형범위지연(대략)크기(H100)특징

6단계: 점유율(Occupancy) — 워프를 얼마나 채워야 하나

6.1 점유율의 정의와 제약 인자

점유율(occupancy)은 SM에 실제로 할당된 워프 수를 SM이 지원하는 최대 워프 수로 나눈 비율이다. H100 SM은 최대 64 워프, 2048 스레드, 32 블록을 수용한다. 점유율을 결정하는 세 가지 제약이 있다. 첫째, 레지스터 수: 스레드당 레지스터가 많을수록 한 SM에 넣을 수 있는 스레드가 줄어든다. 둘째, 공유 메모리: 블록이 많은 공유 메모리를 쓸수록 SM에 올릴 수 있는 블록 수가 줄어든다. 셋째, 블록 크기: 블록이 너무 작으면 SM당 최대 블록 수 제한에 걸린다. 예를 들어 블록 크기 32(= 1 워프)이면 SM당 최대 32 블록 → 32 워프로 점유율 50%(H100 기준 64 워프가 최대)가 된다.

6.2 점유율이 항상 높을수록 좋은가

직관과 달리, 점유율 20~40% 이상에서는 추가 워프의 성능 기여가 급격히 줄어드는 경우가 많다. 오히려 높은 점유율을 위해 레지스터를 절약하다 보면 레지스터 스필이 발생해 오히려 느려진다. 공유 메모리를 더 넣어 캐시 히트율을 높이는 것이 워프를 더 넣는 것보다 이득인 경우도 많다. 핵심은 "워프를 교대 실행하며 지연을 숨기기에 충분한 점유율"과 "레지스터·공유 메모리 효율" 사이의 균형이다. CUDA Occupancy Calculator나 Nsight Compute로 실측하는 것이 감으로 맞추는 것보다 훨씬 정확하다.

7단계: 커널 완료와 결과 반환

그리드의 모든 블록이 완료되면 GPU는 completion semaphore를 post한다. 코드에서 cudaDeviceSynchronize()나 스트림 이벤트를 기다리면 CPU가 이 신호를 받는다. 결과 데이터를 호스트로 가져오려면 cudaMemcpy(DtoH)가 실행되는데, 이 시점에 데이터는 GPU의 VRAM에서 PCIe 버스를 통해 호스트 메모리로 이동한다. NVLink가 있는 멀티-GPU 환경에서는 GPU 간 직접 전송도 가능하다.

벡터 덧셈처럼 단순한 커널도 이 전체 파이프라인을 거친다. 72MB 규모의 벡터 덧셈을 Nsight로 실측하면 약 10~11μs가 걸리고, DRAM 활용률이 80% 수준이며, 워프 발행률은 5% 내외에 그친다. 이 커널은 전형적인 메모리 바운드 케이스다. 12바이트 데이터 전송에 FP32 덧셈 1회만 수행하니 산술 집약도(arithmetic intensity)가 극히 낮다.

8단계: 딥러닝 가속의 토대로서 CUDA 내부 구조

8.1 왜 GPU가 딥러닝에 맞는가

딥러닝 학습의 핵심은 행렬 곱셈이다. 수천만 개의 가중치와 배치의 행렬을 반복 곱하는 연산이 GPU의 SIMT 구조와 정확히 맞아떨어진다. 같은 연산을 다른 데이터 위치에 반복 적용하므로, 워프 다이버전스 없이 수백 개 SM이 동시에 달려들 수 있다. H100의 144 SM × 128 FP32 코어 = 18,432개 코어가 이 병렬성을 활용한다. 더 나아가 텐서 코어는 FP16/BF16 행렬 연산을 하드웨어에서 직접 가속해, 같은 사이클에 FP32 코어보다 훨씬 높은 TFLOPS를 낸다.

8.2 FlashAttention과 메모리 계층 인식 커널 설계

트랜스포머의 Attention 연산은 시퀀스 길이의 제곱에 비례하는 메모리 접근이 발생한다. 순진하게 구현하면 글로벌 메모리를 반복 읽어야 해 메모리 바운드가 된다. FlashAttention은 Attention 연산을 타일 단위로 나눠 공유 메모리 내에서 처리하고 글로벌 메모리 접근을 최소화한다. 결과는 같지만 메모리 이동이 훨씬 줄어든다. 이것이 2022년 이후 대형 언어 모델 학습 속도를 수배 끌어올린 이유다. CUDA 내부 구조를 이해하지 않으면 이런 최적화를 설계할 수 없다.

8.3 커스텀 CUDA 커널이 필요한 시점

PyTorch나 JAX 같은 프레임워크는 대부분의 표준 연산에 최적화된 cuBLAS·cuDNN 커널을 쓴다. 그러나 새로운 연산자, 특수한 희소성 패턴, 도메인 특화 융합(kernel fusion)이 필요한 경우에는 커스텀 CUDA 커널을 작성해야 한다. 이때 그리드·블록 크기, 공유 메모리 활용, 합착 접근 여부, 워프 다이버전스 최소화를 직접 설계해야 한다. Nsight Compute로 프로파일링하면 어디서 병목이 발생하는지 SM별, 워프별로 세밀하게 볼 수 있다.

9단계: 일반 개발자를 위한 실전 시사점

GPU를 직접 프로그래밍하지 않더라도, 이 구조를 이해하면 얻는 것이 있다.

9.1 배치 크기와 워프 활용

딥러닝에서 배치 크기가 너무 작으면 SM이 절반도 채워지지 않아 GPU 활용률이 떨어진다. 32의 배수로 배치 크기를 설정하면 워프가 완전히 채워진다. 512나 1024가 일반적 출발점인 이유가 여기 있다. 다만 배치가 너무 크면 글로벌 메모리 요구가 커져 VRAM을 초과한다.

9.2 텐서 크기와 메모리 정렬

행렬 연산에서 행·열 크기가 8이나 16의 배수가 되면 텐서 코어와 합착 접근 패턴을 최대한 활용할 수 있다. 깔끔하지 않은 크기는 패딩이 생기거나 추가 트랜잭션이 발생해 효율이 떨어진다.

9.3 GPU 활용률 프로파일링

느리다고 무조건 더 큰 GPU를 사는 것은 잘못된 접근이다. 먼저 Nsight Compute나 PyTorch Profiler로 현재 커널이 컴퓨트 바운드인지 메모리 바운드인지 확인해야 한다. 메모리 바운드 커널에 더 많은 CUDA 코어를 추가해도 거의 효과가 없다. 반면 합착 접근을 개선하거나 커널 fusion을 적용하면 같은 GPU에서 수배의 속도 향상을 볼 수 있다.

결론: 추상화 아래의 구조를 아는 것의 힘

kernel<<>>(args) 한 줄 뒤에는 컴파일 파이프라인, 드라이버 호출, QMD 구성, pushbuffer 기록, doorbell 신호, SM 블록 할당, 워프 스케줄링, SIMT 실행, 메모리 계층 탐색, completion semaphore까지 이어지는 긴 파이프라인이 있다. 이것을 모르고도 딥러닝 코드를 실행할 수는 있다. 그러나 병목을 찾고, 최적화를 설계하고, 메모리 계층을 의식한 커널을 구현하려면 이 구조가 살아있는 지식이어야 한다.

특히 대형 언어 모델이 단위 시간당 처리하는 토큰 수, Attention 연산의 속도, 추론 비용의 상당 부분은 CUDA 커널이 GPU의 메모리 계층을 얼마나 잘 활용하느냐에 달려 있다. AI 가속의 토대는 추상화된 프레임워크가 아니라, 바로 이 GPU 내부 구조 위에 서 있다. 2026년 6월 기준, 이 구조를 이해하는 것은 ML 엔지니어와 인프라 개발자 모두에게 점점 필수 역량이 되어가고 있다.
