What the page contains - a lab with no install, account or API

MicroLLM Lab is an experiment page where a single browser tab downloads tiny language models, runs them, and compares them on the same problems. The first sentence of the GitHub README sums up its character: no API key, no Python, no CUDA install. Model weights are stored in the browser's IndexedDB per origin, so a model is downloaded once and not fetched again, and the project page states that no prompt or user data ever leaves the device.

This combination draws attention because the threshold for running an LLM has dropped from a server or GPU workstation to a browser tab. The models have shrunk by the same amount. The models covered here have roughly one hundred million parameters, and their 4-bit quantized files run from 15 to 216MB. This article concentrates on two questions. First, what conditions must be met for a browser to become an LLM runtime? Second, what limits do the sources themselves state in that environment?

The hardware end of the same topic was covered in a separate article. The attempt to run a small model on an eight-dollar microcontroller is laid out in the ESP32-S3 on-device LLM article, and this one does not repeat that axis and stays on the browser as an execution layer.

The structure the table shows is simple, and the sizes fall into three groups: two MiniMind2 models in the 20 to 100M range, five models compared in the 120 to 130M range, and one SmolLM2 360M at about 300M. The experimental value of the page is that several models with different makers and training methods sit at nearly the same size. The README also lists makers. PetitGPT is by yangqi0, the SmolLM line by Hugging Face Smol Models Research, L20-Edu by AliceYin, MiniMind2 by jingyaogong, and GPT-2 by OpenAI (Radford et al.). Only GPT-2 is MIT-licensed and the rest are Apache-2.0. The supported architectures are written as two branches, Llama-style (GQA and SwiGLU) and GPT-2 or nanoGPT-style (LayerNorm and GELU), so a small model belonging to either family can be mounted on the same decoders.

The three-tier fallback - from WebGPU down to WASM and JS

The project page states the execution path in one line: prefer WebGPU, fall back to WASM if that fails, and to JS if that fails too. The three paths differ in character.

  • WebGPU. An API that lets the browser use the GPU's compute capability directly. LLM inference, which is mostly matrix multiplication, fits the parallel structure of a GPU. It is the path with the highest reported speed range.
  • WASM (CPU). Code compiled to WebAssembly runs on the CPU. It works even on machines without a GPU or browsers without WebGPU. The reported speed is around one tenth of WebGPU.
  • JS fallback. The last resort when both paths above fail. The sources give no speed for this path.

The meaning of this order is that it trades the range of devices that can run against the speed at which they run. With a fallback, execution still happens in environments where WebGPU is blocked. But when speed drops from single digits to double digits of tokens, the same page can feel like a different tool. That is why a sense of tokens per second matters. The gap between 8 to 20 tokens per second and 100 or more feels as different as a response filling in line by line and a screen scrolling past. That feel varies with tokenization and language, so it is an illustration of feel and not a value the sources report.

Separately, the README says that on Safari it supports a Metal decoder and a WebGPU decoder together. The sources do not give the reason for listing both decoders. Only the fact that the README lists both is reported here.

If this structure is applied to your own screen or service, what to decide first is less the fallback itself than whether to tell the user which path is running. Because speed differs so much by path, expectations must differ even for the same feature. The sources do not say whether MicroLLM Lab does this, and what follows is a list of design questions the three-tier structure raises.

  • Path display. Whether to show on screen which of WebGPU, WASM and JS is running now.
  • Minimum speed threshold. Below what speed to turn the feature off and substitute a notice. At single-digit tokens per second, interactive use is hard.
  • First download. What to show while a 15 to 216MB file is downloading. Because it is stored in IndexedDB, the cost disappears from the second visit.
  • Model size choice. Whether to assign a different model size per path. On the WASM path a smaller model may be realistic.

What it takes for a browser to become the runtime

No install does not mean no conditions. Five conditions can be read from the sources.

  • HTTP serving. The README says modules and workers need an origin, so a local HTTP server is required. Opening the HTML by double-clicking it in a file explorer (a file address) does not meet this condition. The repository also provides a ZIP download, and the premise is to serve the unpacked folder with a static server.
  • Browser version. The GeekNews summary lists Chrome 113 or later, Edge 113 or later, Brave, and Firefox with WebGPU enabled. The README names Safari, Chrome and Edge. Because the two sources list different browsers, actual support has to be judged by whether the page works in your own environment.
  • Storage. Model files are 15 to 216MB and are stored in IndexedDB per origin. Opening the same file from a different origin means downloading it again.
  • Quantization. Models are distributed as Q4. The GeekNews summary says compressing 16-bit floating-point weights to 4 bits cuts memory use by 75%. Going from 16 bits to 4 leaves a quarter of the bits, which matches a 75% reduction arithmetically. But this compression is traded against quality, and the sources give no accuracy difference between an original model and its Q4 version.
  • Architecture support. Only two branches, Llama-style and GPT-2-style, have decoders. A model with any other structure cannot be loaded as is.

Put together, these five conditions say the browser is an environment without install, not an environment without limits. It uses workers and modules inside the security boundary called an origin, and reaches the GPU only through the API the browser allows. For the same reason, the privacy the project page stresses is structural: inference ends inside the browser on the user's device, so there is no path along which input would be sent to a server. The sources do not say where the page downloads model files from, or whether the statistics and certificate-sharing features communicate externally.

Speed - the ranges reported and the conditions behind them

The speed figures are spread across three sources. If source and condition are not kept apart, measurements taken under different conditions are easily misread as one line. The table below makes that separation.

Path or conditionSpeed reportedSource and condition
WebGPU100 to 300+ tokens per secondGeekNews summary. Device and model conditions are not in the summary
WASM (CPU)8 to 20 tokens per secondGeekNews summary. Described as 10 to 20 times slower than WebGPU
JS fallback—No figure given
PetitGPT research-v187ms, 115 tokens per secondREADME. Apple M4, Safari, Metal Q4, greedy decoding, a Say hello prompt
SmolLM2 135M Instruct227ms, 66 tokens per secondREADME. Same conditions as above
First-token latencyA phrase saying under 10msProject page, introducing an autocomplete use. Conditions not stated

Two things stand out. First, the README's M4 measurements split two models in the same size range into 115 and 66 tokens per second. All that can be read from this is that speed differs with structure and details such as embedding size even when parameter counts are similar. Second, the GeekNews summary's 100 to 300+ tokens per second for WebGPU is a range that does not contradict the README's M4 measurement, but the summary does not say on which device and model the value was taken. So the safe course is to quote it as a range the sources report and not carry it over as an expectation for your own environment.

The project page says sustained speed is measured over a continuous 256-token generation. First-token latency for a short response and throughput for a long generation are different values. In a short response such as autocomplete, first-token latency governs the feel, and in a long response such as a summary, sustained speed does. That is why the page shows both metrics side by side.

There is one rule for reading the table: compare values only within the same row, and do not stitch values from different sources into a single trend. If even one of device, browser, model or prompt differs, it is a different measurement. In particular, deriving sustained speed from a first-token latency value, or the reverse, has no basis in the sources, because the two metrics describe different phases of generation and the sources give no formula linking them.

How the benchmark, certificate and custom JS evaluation are built

MicroLLM Lab is not only an execution tool but carries measurement tools with it. The structure the sources describe is as follows.

  • Objective benchmark. The Benchmarks tab on the project page uses objective checks judged by regular expression or exact token match. Because the criterion is mechanical, the same input tends to give the same result.
  • Test count. The GeekNews summary says 21 tests run automatically. The README separates 14 original tests from 20 expanded tests, and says SmolLM2 135M Instruct got 14 of the 20 expanded tests right and PetitGPT 10 of the 14 original tests. The sources alone do not show which README number the value 21 corresponds to.
  • Suite duration. The README says about 1.5 seconds for PetitGPT and about 6 seconds for SmolLM2 on Safari on an M4.
  • 256-token sustained speed. The project page measures sustained speed (Highest Sustained Speed) with a continuous 256-token generation.
  • Performance certificate. A certificate holding the device hardware specification and the peak and sustained speeds can be made, downloaded, or shared to X and LinkedIn. The GeekNews summary says it is generated as a PNG.
  • Custom JS benchmark. If a user writes a benchmark in JavaScript, the project page says it is run with eval() in this origin and checked against the decoded model output.

That decoding is greedy only ties into benchmark design. Greedy picks the highest-probability token at every step, so results tend to reproduce for the same input and model. With sampling, results change from run to run and pass rates are hard to compare. This shows the tool was designed for comparison experiments, and for the same reason it does not suit creative generation or uses that need varied answers.

The custom JS evaluation calls for a caution. eval() executes an input string as code, so code the user wrote runs as is inside this tool's origin. It is no problem as long as you run your own code on your own device, but pasting in a benchmark script someone else gave you is a different matter. This article only reports the behavior the sources describe, and the sources do not say how the page isolates this execution.

Model (README name)Evaluation conditionAccuracy reportedTime reported

The very fact that the README writes original and expanded separately means the test set has been revised, and it shows that only values from the later set should be compared with each other.

Limits - context, decoding, hallucination, and where such models fit

The README states the limits itself. These models hallucinate and must not be used for high-stakes questions, context is capped at 2,048 tokens, and decoding is greedy only.

  • Hallucination. The README says these models hallucinate. Among the Hacker News reactions the GeekNews summary relays are a case where SmolLM2 360M answered a population as both 153 million and 325 million, contradicting itself, and a case where GPT-2 124M gave an off-target answer to a 2+2 question. Both are test reports from particular users and not generalized statistics.
  • 2,048-token context. Feeding a whole long document is outside this tool's range. The sum of input and output handled at once has to fit inside that limit.
  • Greedy decoding. With no temperature or sampling control, output diversity cannot be adjusted. The same question gives the same answer.
  • UI feedback. The reactions the GeekNews summary relays also include screen-improvement requests such as font size and information density.

Where, then, would such models fit? The only use the sources state directly is the instant short response the project page introduces, autocomplete. What follows is an interpretation that follows logically from the limits above and not a use the sources recommend. It holds for work that does not demand accurate facts, has short output, and where a person can filter out a mistake right away. Work with a single correct answer, such as arithmetic and fact checks, is where the cases above show failure. Narrow judgment tasks such as classification or filtering could be candidates, but this tool's test results do not prove it. To use them that way, the pass rate has to be measured directly on your own data, and the custom JS benchmark on this page happens to be the place for that measurement.

In the end, what this page shows is not the skill of small models but how far the conditions for a browser to run inference have come together. A staircase that reaches hundreds of tokens per second with WebGPU and drops to single or double digits without it is open through the fallback structure, and on it models of around 100 million parameters run with no install. Whether such a model can be trusted with a task is a separate matter, and the sources say so themselves. The maturity of the runtime and the reliability of the model are different axes, and neither can stand in for the other: a demo that runs smoothly says nothing yet about whether its answers can be relied on.

What could not be confirmed

  • The exact number of models and tests. The GeekNews summary (7 models, 21 tests) and the README (8 table rows, 14 original plus 20 expanded tests) disagree, and the sources alone cannot show which is more current.
  • On which device and model the WebGPU figure of 100 to 300+ tokens per second and the WASM figure of 8 to 20 were taken. The summary does not state the conditions.
  • How many times slower older GPUs are. No such figure is in the sources consulted.
  • The claim that the models suit edge work such as classification and filtering. The sources do not state it, and it is treated only as interpretation in this article.
  • The real speed and operating conditions of the JS fallback path. The project page gives only the order.
  • How much Q4 quantization lowers accuracy against the original model, how the custom JS execution is isolated, and whether sharing a certificate involves external communication. Not in the sources.
  • The model list in the project page body. The page loads model cards, so no list appeared in the body text.
  • This article did not run the tool to reproduce speeds. Every figure is a value the sources report.
