Why API Docs Always Lag Behind Code - From Excel and PDF Specs to a Machine-Readable Contract

Source of truth placement, breaking change classes, the limits of CI checks, deprecation policy, freshness metrics

Jul 28, 2026 Dev & Infra

Introduction: the docs are not wrong by accident, they were built to be able to go wrong

An email arrives from the integration owner. The attachment is called API_spec_v3_final_final2_revised.xlsx. It has twelve sheets, four of which are still alive; the rest were agreed to be mentally deleted. The partner company writes code against this file. Meanwhile the server renamed one response field two deployments ago, and that fact never made it into the spreadsheet. The integration breaks on the last day of joint testing. And then someone says it in the retrospective: we really should manage our documentation better.

That conclusion is where this article starts, because it is wrong. Nobody was lazy. The incident was caused by leaving in place a structure in which docs and code can diverge, and then trusting individual diligence to keep them aligned. Diligence does not scale. A process that works at thirty endpoints will fail at three hundred, without exception.

API documentation differs from other internal documentation in one crucial way: its readers are not only humans. An API specification is a promise between two programs, and promises are only enforced when a machine can check them. The real problem with Excel and PDF is not that they look old-fashioned but that they are impossible to cross-check. The line orderStatus: string in a spreadsheet is never once compared against what the server actually emits. What cannot be compared can drift unnoticed, and what nobody notices stays broken for months.

So this article is not about how to write better documentation. It is about designing so that divergence surfaces immediately. Three claims:

  • Docs falling behind code is not human negligence but the inevitable result of update triggers being separated.
  • The first move is not buying a tool, it is deciding where the single source of truth lives and demoting everything else to a derived artefact.
  • The boundary between what automation can and cannot catch is sharper than people assume. Miss that boundary and you will buy tooling and still have the same outage.

What this article does not cover. The general problem of internal documents ageing inside a RAG index is covered in Your internal knowledge base rots quietly. This piece drills into one narrow axis of that: the machine-readable API contract. The shared conclusions about owners, expiry and retirement are not repeated here. Protocols between tools themselves are handled by the MCP guide and Is MCP dead, and a public brokerage API case sits in Toss Securities OpenAPI.

1. What Excel and PDF specs really cost you - not the medium, the verifiability

First, remove the sneer. Teams that keep APIs in spreadsheets are not primitive. Excel has a near-zero barrier to entry, free-form table editing and universal readability. Starting there is a rational choice for a young team. The trouble begins when the choice is never revisited as scale grows.

1.1 If it cannot be machine-read, it cannot be verified

The OpenAPI Specification defines itself as a standard, programming language-agnostic interface description for HTTP APIs. The load-bearing words are standard and machine-readable. A standard format means tools exist, and tools existing means three things can go into a pipeline.

  • Syntax and convention checks - is the description itself valid, does it follow in-house naming rules
  • Version diffing - what changed since the last release, and which of those changes break consumers
  • Conformance against the implementation - does the server actually respond the way the description claims

Excel and PDF provide none of the three. More precisely, it is not that they cannot, it is that nobody builds it. Maintaining a parser that reliably extracts field definitions from merged cells and freeform formatting is more expensive than migrating to a standard format.

1.2 Attaching a file is not distribution, it is duplication

The second loss is quieter. The instant a spec is emailed, the canonical copy stops existing and only forks remain. Partner A works from the March file, partner B from the May one. Both believe they hold the latest. The only way to tell which is newer is the filename, and the filename is decided by how many times the word final has been repeated.

Publishing at a URL removes half the problem. One address always points at the current description, and a version-tagged address preserves the past. The other half, whether the content at that URL matches the running server, is what the rest of this article is about.

2. Five paths by which docs drift from code

Drift does not have one cause. Five paths show up repeatedly in practice, and each one is blocked by a different mechanism. Introduce a tool without separating the causes and you will end up defending the wrong path.

2.1 Path 1: separated update triggers

The most common and most damaging. A code change must pass through merge, a forcing event, but a documentation update hangs off no such event. Different repository, different owner, different schedule: lag is not a probability, it is a matter of time. There is only one cure. Put the spec file in the same repository and the same change request as the code. The OpenAPI Initiative learning material likewise says descriptions should be treated as first-class source files versioned alongside production code.

2.2 Path 2: copy proliferation

Covered above. Without a canonical identifier, discovering a mismatch does not tell you which copy to fix. And fixing one leaves the others untouched.

2.3 Path 3: agreements the format cannot hold

This path survives migration to a standard format. Every description language has promises it cannot express. For example:

  • Whether a money field is in major or minor units, and how many decimal places are significant
  • Whether the time zone of a timestamp string is UTC or local, and whether an offset is mandatory
  • How an idempotency key is constructed on retry and how long it is retained
  • Whether list pagination is offset or cursor based, and when a cursor expires
  • Where in the response you read which items succeeded after a partial failure

None of these appear as types in a schema. They are written in prose in a description field, or not written at all and left as a verbal agreement. That is why organisations that adopted a spec still have incidents at this layer. Two mitigations: use a linter to forbid empty description fields, and pin these conventions down in a single organisation-wide rules page that individual APIs reference.

2.4 Path 4: the illusion created by generation

People expect drift to vanish once docs are generated from code annotations. That is half true. What the generator reads is not the code but the annotations, and annotations are maintained by hand. Add a field to a response object, forget the annotation, and the document ships wrong while enjoying more trust because it was generated. That is why it can be more dangerous than a handwritten document.

This outcome is part of why the OpenAPI Initiative favours design-first. Because the range of APIs expressible in code exceeds the range describable in OpenAPI, retrofitting a description onto an existing implementation tends to leave unintuitive and incomplete descriptions.

2.5 Path 5: documents that swell because nothing can be deleted

The last path is created by time. Old endpoints and old fields are never removed while new ones keep accumulating. They are not removed because nobody knows who uses them. Without usage measurement you cannot know what breaks if you delete, and not knowing, you leave it. The description becomes a blend of present and past, and readers cannot tell which parts are alive. No documentation tool blocks this path. It needs a deprecation policy and usage telemetry, covered in sections 8 and 9.

3. What a machine-readable contract is - what OpenAPI standardises and what it does not

The OpenAPI Specification describes the interface of an HTTP API in a language-neutral way: paths and methods, request parameters, request and response body schemas, authentication schemes, error response shapes. What matters just as much is what it does not hold. The meaning of business rules, call ordering, performance characteristics and pricing are out of scope. A spec is a contract about shape, not a contract about meaning.

3.1 The practical difference between 3.0 and 3.1

The decisive difference for practitioners is the schema language. Version 3.0 used a modified subset of JSON Schema, which spawned custom keywords such as nullable and confused tooling. Version 3.1, published in February 2021, is fully aligned with JSON Schema 2020-12, so any valid JSON Schema 2020-12 document is a valid 3.1 schema. Webhook description also arrived properly in 3.1.

The specification itself is versioned major.minor.patch, where major.minor designates the feature set and patch only fixes errors or clarifies wording. In other words 3.1.0 and 3.1.1 are the same feature set. Upgrade without checking whether your toolchain fully supports 3.1 and the tools break first. As of July 2026 support levels still vary between tools, so it is safer to trial the generators, documentation renderers and mock servers you actually use before committing.

3.2 Deprecation markers exist at the schema layer too

OpenAPI puts a boolean deprecated field on the Operation Object to declare an operation deprecated, and consumers should refrain from using it. In 3.1, because schemas follow JSON Schema 2020-12, field-level deprecation can also be expressed. It is worth knowing that the JSON Schema deprecated keyword is an annotation that does not affect validation, so deprecated values still pass. The marker is a signal, not an enforcement.

4. Where to put the single source of truth - a decision table

Before choosing tools, decide where the truth lives. The OpenAPI Initiative guidance is blunt: information should exist in only one place, and duplication guarantees that one copy will diverge. If duplication is unavoidable, it adds, use continuous integration testing to keep them consistent.

There are five candidates. The right answer varies by organisation, so here it is as a table.

CandidateFits whenPrice you payFailure signal
Spec file
(design-first)		 External partners or other teams are consumers, multi-language clients, contract negotiation precedes development Requires spec fluency, slower start, needs a mechanism to keep spec and implementation in step The spec advances while the implementation does not, producing ghost endpoints
Server code annotations
(code-first)		 Internal only, exploratory phase with weekly requirement churn, one team owns both server and client The description is dragged along by implementation shape, missing annotations are undetectable Fields keep growing while the share of items with empty descriptions climbs
An IDL
(proto, SDL and similar)		 Internal traffic is gRPC or GraphQL centric, multi-language stub generation is the core need Mapping rules to an HTTP representation are managed separately, REST consumers get a second-hand artefact Naming rules between the IDL and the public HTTP document start to diverge
A documentation service
(SaaS editor)		 Non-engineers co-edit, the partner portal is effectively the product Edit history lives outside the code repository, tool lock-in The deploy pipeline has no idea what state the docs are in

(status quo)		 A few dozen endpoints at most, effectively one internal consumer team, quarterly change cadence You give up verification, diffing and conformance entirely Integration owners start reading the source code to find out what the API really does

Use the table backwards. Find the failure signal you already observe, and if that row's source of truth differs from where yours lives today, consider migrating. If no signal is present, you do not have to move. That is why the last row is still on the list.

The most common wrong answer is putting the truth in two places. Maintaining both a spec file and annotations means neither is canonical. If you must keep both, declare which one is derived and automate the direction of derivation. A structure where humans reconcile both sides by hand diverges without exception.

5. Classifying changes by blast radius - what actually breaks consumers

Answering is this change safe by intuition produces different verdicts from different people. Published guidance is a better baseline. What follows draws on Google's API design guidance AIP-180 and Stripe's public policy.

ChangeClassBasis and conditions
Adding a new property to a responseUsually compatibleStripe publishes this as backwards-compatible. Strict clients that reject unknown fields will still break
Adding an optional request parameterCompatibleIncluded in Stripe's published list
Reordering response propertiesCompatibleExplicitly listed by Stripe as compatible
Changing length or format of an opaque stringCompatibleObject IDs, error messages and similar, per Stripe. Breaks consumers that assumed a length
Adding a required request parameterBreakingAIP-180 forbids new required fields in request messages and resources
Removing an existing field or methodBreakingAIP-180: existing components must not be removed
Renaming an existing fieldBreakingAIP-180 treats a rename as semantically equivalent to remove and add
Changing the type of an existing fieldBreakingAIP-180: prohibited even when the new type is wire-compatible
Changing a field default valueBreakingAIP-180: static default values on resources must not change
Changing how defaults are serialisedBreakingAIP-180 includes whether default-valued fields appear in JSON output
Renaming a resourceBreakingAIP-180 forbids this even across major versions
Adding a value to a response enumConditionalSafe only if consumers tolerate unknown values. AIP-180 distinguishes request-only enums, to which values may be added freely
Changing the error code taxonomyConditionalBreaking if used for branching. Wording-only changes are usually compatible
Tightening authentication scopesBreakingCalls that used to pass with existing credentials are rejected, which is effectively removal

5.1 What to actually take from the table

The value here is not memorising rows but internalising two principles.

  • Adding is usually safe, removing and changing are usually dangerous. That is why mature APIs keep accumulating fields instead of deleting them, and clean up through a deprecation process instead.
  • Safety depends on consumer tolerance, not on the server. The claim that additions are safe only holds for clients that ignore unknown fields and survive unknown enum values. So that tolerance rule has to be written into the consumer-facing document too.

5.2 The lesson in Stripe's date-based versions

Stripe publishes that only major releases carry incompatible changes while monthly releases contain compatible changes exclusively. Its engineering blog describes maintaining old versions through small, isolated transformation modules that downgrade new responses into the old shape. The cost is obvious: the transformation layer accumulates forever. For most organisations that is overkill, but the transferable principle is simple. Do not let incompatible changes trickle out whenever, gather them at one point.

6. What contract testing guarantees and what it does not

Even with a spec, whether the server responds according to it is a separate question. The best-known approach for closing that gap is consumer-driven contract testing.

6.1 Start from the precise definition

The Pact documentation defines contract testing as a technique for testing an integration point by checking each application in isolation to ensure the messages it sends or receives conform to a shared understanding documented in a contract. Interactions exchanged with a test double during the consumer test run are recorded into a contract, and the provider side replays that contract to verify. The headline benefit is being able to test the integration without standing both services up together.

6.2 Draw the boundary clearly

The same documentation is equally clear about limits, and this is the part most often misread in practice.

  • A contract is not a schema describing all possible states. It is enforced by executing a collection of concrete request and response pairs.
  • Therefore only the parts consumers actually use are checked. A field nobody calls is not in any contract, and what is not in a contract is not protected.
  • Provider-side contract testing alone does not assure that consumers are calling the provider correctly.
  • It requires consumer participation. It is hard to apply as-is to a public API whose consumers are unknown.

In short, contract testing does not replace spec linting or breaking change detection. They occupy different layers. A spec covers broad and shallow, a contract covers narrow and deep. With neither, nothing is covered; with only one, only that side is.

7. What CI can verify automatically and what it cannot

This section is the practical core of the article. Miss this boundary and you will adopt tools and still ship the same incident. Item by item:

7.1 What a linter catches and what it misses

Spectral describes itself as an API style guide enforcer and a flexible JSON and YAML linter. It has built-in support for OpenAPI 2.0, 3.0 and 3.1, AsyncAPI 2.x and Arazzo 1.0, and you enforce in-house conventions by defining rulesets. Built-in functions cover pattern checks, parameter checks, alphabetical ordering, character counts and verifying that given keys are present, and custom functions can be written when needed.

Now the decisive limitation. A linter only sees the description document. It has no idea what the server responds with. You can score full marks on lint while the spec disagrees with reality. Unless that is spelled out to the team, passing lint gets consumed as if it were proof of correctness, which is a dangerous illusion.

7.2 Diffing and conformance

oasdiff produces a machine-readable diff between two specs and flags changes likely to break consumers using a rule library. The project states it identifies 506 distinct breaking and non-breaking changes, and it returns exit code 1 when breaking changes are found so a CI step can fail automatically. Its GitHub Action compares the pull request branch against the base branch and leaves inline annotations.

Schemathesis runs in the other direction. It generates test cases from an OpenAPI or GraphQL schema, actually issues the calls, and checks whether responses conform to the schema. The point of this approach is catching the slow drift where the code returns a field the schema never documented, or returns null where the schema promised a string.

# Illustrative pipeline - exact command forms vary by tool version, check the official docs

# 1) Syntax and in-house style checks
spectral lint openapi.yaml --ruleset .spectral.yaml

# 2) Detect breaking changes against the base branch (exit code 1 when found)
oasdiff breaking base/openapi.yaml head/openapi.yaml

# 3) Verify the staging server responds according to the spec
schemathesis run openapi.yaml --url https://staging.example.com

7.3 Get the rollout order wrong and you only buy resentment

Turn all three on as blocking conditions at once and hundreds of findings pour out of the existing spec, at which point the team responds by turning rules off. The order that works in practice looks like this.

  • Week 1: only syntax validation blocks. Everything else emits warnings only
  • Weeks 2 to 4: apply linter rules to newly changed parts only. Freeze existing violations as a baseline list and pay them down gradually
  • Week 5 onward: make breaking change detection blocking, but build an approval path at the same time so intentional incompatible changes can proceed
  • Start conformance checking and contract testing with a handful of the most important endpoints

8. What a deprecation policy must contain

A retirement process is the only mechanism that stops documents from swelling. Here are the items a policy document needs, grounded in public examples and standards.

  • Where it is declared - deprecation is marked inside the spec. Zalando's public guidelines require setting deprecated: true on an endpoint, input argument, object or property and adding an explanation in the description.
  • Minimum notice period - there is no industry standard number. The Google Cloud Platform Terms of Service state at least 12 months notice before discontinuing a service or making a materially backwards-incompatible change to a customer-facing API, and Microsoft Graph documentation states that a generally available API is declared deprecated at least 24 months before removal. Set your own number to match your consumers.
  • Response header signals - use the Deprecation header defined by RFC 9745 together with the Sunset header defined by RFC 8594. The Sunset timestamp must not be earlier than the Deprecation timestamp.
  • Guidance links - both RFCs define link relation types. Attach the policy and migration documents through rel values.
  • Named replacement - state what to move to and how the fields map. The Zalando guidelines likewise require documenting in detail what consumers should use instead and how to migrate.
  • Usage telemetry - the same guidelines require API owners to observe migration progress so that ongoing consumers are not broken uncontrollably. Without per-consumer residual traffic you cannot pick a shutdown date.
  • Agreement with external consumers - where external partners exist, define the post-deprecation maintenance window and obtain their consent.
  • Shutdown mechanics - decide in advance whether you cut it off one day, block it briefly to signal remaining consumers, or raise error rates in stages.
  • Exception clause - state that the window may shorten for security vulnerabilities or legal compliance. The Google Cloud terms carry the same carve-out.

8.1 How it looks in the spec and on the wire

# openapi.yaml - operation-level deprecation marker
paths:
  /v1/orders/{orderId}:
    get:
      operationId: getOrderV1
      deprecated: true
      summary: Fetch order detail (scheduled for removal)
      description: |
        Shutting down on 2026-09-01. Replacement path is GET /v2/orders/{orderId}.
        The marketing_agree field moved to consents[].marketing.
        Migration guide: https://api.example.com/docs/migrate/orders-v2
      responses:
        '200':
          description: Order detail
HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1785196800
Sunset: Tue, 01 Sep 2026 00:00:00 GMT
Link: <https://api.example.com/docs/migrate/orders-v2>; rel="deprecation"

The Deprecation header value is a structured field date, so an integer number of seconds follows @. The Sunset header value uses the HTTP-date format. RFC 8594 explicitly says Sunset timestamps should be treated as hints and availability until that time is not guaranteed. In other words the header is a signal, not a promise. The promise comes from the policy document and the agreement.

9. Documentation freshness metrics - what to measure to make drift visible

Drift causes no outage. No alarm fires. Which means if you do not measure it, you will never see it. Most of the metrics below can be computed from the repository and access logs you already have.

MetricComputationHow to read it
Spec lagLast change date of the handler code minus last change date of that path in the specLong positive stretches mean drift. Track the per-path maximum weekly
Ghost pathsPaths present in the spec but absent from the routing tableAnything above zero means consumers who trusted the doc are broken
Undocumented pathsPaths present in routing but absent from the specAlso surfaces internal ad-hoc routes accidentally exposed externally
Description gap rateOperations and fields with empty descriptions divided by the totalProduce it daily with the linter. The trend alone is informative
Example coverageShare of operations carrying request and response examplesCorrelates well with partner onboarding question volume
Contract test coveragePaths with a consumer contract divided by externally exposed pathsThe uncovered remainder is where incidents actually happen
Residual deprecated trafficDaily calls per consumer on paths marked deprecatedIf it is not converging toward zero, push the shutdown date back
Days since deprecationDays elapsed since declaration crossed with residual trafficShutting down purely because the window elapsed causes incidents
Diff alert countBreaking changes detected per change requestA sudden rise signals that design agreement is breaking down

You do not need all of them. Two are enough to start: ghost paths and undocumented paths. Both are computable from a routing table dump plus the spec file, and the moment either is non-zero it demonstrates, beyond argument, that the current document is wrong. They are also the most effective numbers for winning priority in a planning meeting.

10. A migration order for organisations still on Excel and PDF

The most common failure is attempting the whole estate at once. A team tries to move 200 endpoints, stalls after three months and returns to spreadsheets. Reorder the work and it goes differently.

10.1 Step 0 - pick one canonical copy (a few days)

  • Gather the circulating copies, designate one current canonical document and mark the rest as retired. Deletion comes later.
  • Use access logs to extract the top 20 paths by actual call volume. Those 20 are the migration scope.
  • Build a consumer list, split into internal teams, external partners and unidentified callers.

10.2 Step 1 - describe only those 20 (two to three weeks)

  • Compare the existing document against real traffic and write what the system actually does. Where the spreadsheet disagrees with reality, reality wins.
  • Put the spec file in the same repository as the server code. This single move blocks path 1.
  • Whether to start on 3.0 or go to 3.1 should be decided by what your tools support. Newest is not automatically right.

10.3 Step 2 - put it in the pipeline (two weeks)

  • Make syntax validation a blocking merge condition.
  • Run the linter in warning mode only. Blocking at this point invites pushback.
  • Generate a documentation page from the spec and publish it at a URL. From this point, stop attaching spreadsheets.

10.4 Step 3 - change control (three to four weeks)

  • Run a diff against the base branch on every change request and flag breaking changes.
  • Create an approval path for incompatible changes. Nothing passes without it, but keep the path short.
  • Post the classification table from section 5 on the team wiki so verdict criteria are shared.

10.5 Step 4 - conformance and contracts (four weeks or more)

  • Attach schema conformance checks in staging to compare real responses with the spec.
  • Pilot contract testing with your single most cooperative consumer team. Broad rollout comes after.
  • Document the deprecation policy and attach header signals. Start measuring residual traffic at the same time.

10.6 What not to do

  • Choosing tools first. Until the source of truth is fixed, no tool finds its place.
  • Migrating every path simultaneously. The top 20 percent of traffic generally produces most of the incidents.
  • Blocking everything from week one. A culture of switching rules off is hard to reverse.
  • Keeping the spreadsheet alive in parallel. Two sources of truth always diverge. Once you migrate, lock the old file read-only.

11. What this system cannot prevent

Without overstating it: doing everything above will not eliminate divergence. What changes is how fast and how cheaply divergence surfaces. The remaining holes:

  • Meaning is still guarded by people. A spec is a contract about shape. Promises written in prose, such as money units, time zones and idempotency conventions, are beyond any checker.
  • Design-first is not always right. The OpenAPI Initiative itself concedes code-first is easier to start with. Fixing a spec early in a volatile phase means spending all your time editing the spec.
  • Generation faithfully documents an inaccurate implementation. Being generated does not imply being correct.
  • Contract testing needs participants. A public API with unknown consumers needs a different approach.
  • Passing lint is not proof of correctness. It only looks at style.
  • Without an owner, tooling is inert. An alert with nobody to receive it is just noise.

So setting the goal at zero divergence guarantees failure. The realistic goal is this: make drift surface at deploy time, and make fixing it far cheaper than discovering it on the last day of joint testing.

Conclusion: hand the job to structure instead of diligence

What a spreadsheet-driven organisation needs is not a lecture. The people involved are already diligent enough. The problem is that diligence is the only line of defence. When there is one line, it falls on the day that line takes a break.

Only three things need to change. First, pin the source of truth to one place and demote everything else to a derived artefact. Second, put that source inside the same change request as the code so update triggers merge into one. Third, switch to a format a machine can cross-check so divergence surfaces automatically. Do those three and linting, diffing and contract testing are things you simply layer on top. Invert the order and buy tooling first, and the same incident recurs in a more expensive form.

One sentence to keep from all of this: documents going wrong is not an accident, it is the result of a design. Leave a structure in which they can diverge and one day they will. Build a structure where divergence surfaces immediately and the system holds even when people are careless. Documentation management is not a question of diligence, it is a question of structure.

There is one thing to do on Monday. Dump the routing table, compare it against the current description and count the paths missing from either side. If that number is not zero, the answer is already in front of you.

# API Deprecation Policy Checklist

> Source: braindetox.kr — Why API docs always lag the code
> Standards: RFC 8594 (Sunset header), RFC 9745 (Deprecation header)
> Paste this into your AI assistant and ask it to fill in your service's values.

## 1. Nail these down in the policy document
- [ ] Notice period (e.g. GA at least __ months / preview at least __ weeks)
- [ ] When the clock starts (announcement date, or the date docs are updated)
- [ ] The boundary between compatible and breaking changes (agree via table 2)
- [ ] Exceptions — may a security fix shorten the notice period
- [ ] Response after sunset (410 Gone, or keep returning 200)
- [ ] Official channel (header / changelog / email / dashboard — which one is binding)

## 2. Change classification — settle this or argue every time
| Change | Class | Deprecation process |
|---|---|---|
| Add optional field | Compatible | Not required |
| Remove field | Breaking | Required |
| Change field type | Breaking | Required |
| Add enum value | **Contested** | Breaking if consumers parse strictly |
| Add required parameter | Breaking | Required |
| Add error code | **Contested** | Breaking if consumers branch on codes |
| Change ordering | **Contested** | Compatible only if never documented as guaranteed |

## 3. Machine-readable signals (a human announcement is not enough)
- [ ] `Deprecation` response header — RFC 9745
- [ ] `Sunset` response header — RFC 8594, the actual cut-off time
- [ ] `Link` header with `rel="deprecation"` pointing at the notice
- [ ] `deprecated: true` in the OpenAPI document
- [ ] CI check that the three above **do not disagree on the date**

## 4. Before you switch it off
- [ ] Remaining calls in the last 30 days (if not zero, do not switch off)
- [ ] Can you identify the remaining callers (API key / User-Agent / contract)
- [ ] Internal systems still calling it — this is usually where it breaks
- [ ] Does the replacement offer **equivalent** capability (partial parity blocks removal)
- [ ] Rollback path — can you bring it back after switching off

## 5. Common failures
- Docs say unsupported but no header is sent → nobody finds out
- Notice given, but the team **never counted remaining calls** before switching off
- A replacement exists but **there is no migration guide**
- The sunset date is written in several places and they disagree
