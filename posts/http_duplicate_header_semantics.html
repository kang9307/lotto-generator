같은 헤더가 두 번 오면 - 합쳐도 되는 것과 절대 안 되는 것

필드마다 다른 「여러 개」의 의미, 그리고 런타임이 대신 정해 버리는 것

2026-08-01 개발/인프라

서론: 쿠키를 두 개 내려보냈는데 하나만 저장됐다

로그인 응답에서 세션 쿠키와 테마 쿠키를 함께 내려보냈다. 서버 로그에는 둘 다 찍혔다. 그런데 브라우저에는 세션 쿠키 하나만 남아 있다. 코드를 열어 보면 쿠키를 만드는 부분에 실수가 없다. 그래서 대개는 브라우저 설정이나 도메인 문제를 의심하며 반나절을 쓴다.

이 증상의 상당수는 훨씬 앞쪽에서 결정된다. 어딘가에서 두 줄이던 헤더가 한 줄로 합쳐진 것이다. 그리고 그 합침은 대개 잘못이 아니다. 오히려 대부분의 필드에서는 합치는 것이 규격이 정한 올바른 동작이다. 문제는 규격이 그렇게 정하지 않은 필드에까지 같은 처리를 했을 때 일어난다.

그래서 이 글의 주제는 「중복 헤더를 막자」가 아니다. 막을 수도 없고 막을 이유도 없다. 진짜 질문은 이것이다.

  • 같은 이름이 두 번 왔다는 것이 그 필드에서는 무슨 뜻인가. 목록이 늘어난 것인가, 값이 두 개인 것인가, 있어서는 안 되는 상태인가
  • 합칠지 말지를 누가 정하는가. 개발자가 정하는 게 아니라 런타임이 먼저 정해 버리는 경우가 많다
  • 내 코드가 보는 것은 도착한 것인가, 이미 가공된 것인가. 문자열 하나를 받아 든 시점에는 정보가 이미 사라졌을 수 있다

세 질문 모두 실행해서 답을 냈다. 같은 바이트를 서로 다른 런타임에 밀어 넣고, 받은 쪽이 무엇을 손에 쥐는지 찍었다. 결과는 한 문장으로 요약된다. 필드마다 「여러 개」의 의미가 다르고, 런타임마다 그 의미를 다르게 처리한다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 런타임은 Node.js v22.16.0 (win32)과 Python 3.13.3 (win32)이고, 서버는 각 언어의 기본 HTTP 서버 모듈로 직접 띄웠다. 요청은 원시 소켓으로 바이트를 직접 써 넣었다. 클라이언트 라이브러리가 전송 전에 헤더를 정규화하는 것을 피하기 위해서다. 사용한 포트는 18090~18094이며 측정이 끝난 뒤 전부 종료했다.

이 글은 특정 제품의 동작을 단정하지 않는다. 7절에 나오는 중계는 이 글을 위해 직접 짠 스무 줄짜리 최소 구현이고, 상용 프록시나 로드밸런서, 웹 서버 제품의 동작을 대표하지 않는다. 각 제품이 어떻게 처리하는지는 여러분의 환경에서 직접 측정해야 한다. 이 글이 제공하는 것은 결론이 아니라 측정 방법과 판단 기준이다.

이 글이 다루지 않는 것. 헤더 이름의 대소문자가 만드는 별개의 함정은 이름은 대소문자를 안 가리는데 코드는 가린다에서 다뤘다. 여기서는 이름이 완전히 같을 때만 본다. 쿠키 속성의 의미는 SameSite Lax·Strict·None에 있다. 3절에서는 속성이 아니라 줄을 합치면 값이 부서진다는 한 가지만 본다.

1. 같은 이름을 두 번 보내면 무엇이 도착하는가

먼저 가장 기본적인 재현이다. 이름이 같은 헤더를 두 줄씩 담은 요청 하나를 만들어, 그 똑같은 바이트를 두 서버에 각각 보냈다. 보낸 것은 다음과 같다.

GET /dup HTTP/1.1
Host: shop.example.test
X-Trace-Id: aaa-111
X-Trace-Id: bbb-222
Accept: text/html
Accept: application/json
X-Forwarded-For: 203.0.113.9
X-Forwarded-For: 198.51.100.4
Cookie: sid=A1
Cookie: theme=dark
Connection: close

받은 쪽이 무엇을 쥐고 있는지 세 가지 API로 각각 찍었다. 먼저 Node다.

1-A. Node.js v22.16.0 / win32
status : HTTP/1.1 200 OK

  req.headers[x-trace-id      ] = 'aaa-111, bbb-222'
  req.headers[accept          ] = 'text/html, application/json'
  req.headers[x-forwarded-for ] = '203.0.113.9, 198.51.100.4'
  req.headers[cookie          ] = 'sid=A1; theme=dark'

  req.headersDistinct[x-trace-id      ] = ['aaa-111', 'bbb-222']
  req.headersDistinct[accept          ] = ['text/html', 'application/json']
  req.headersDistinct[x-forwarded-for ] = ['203.0.113.9', '198.51.100.4']
  req.headersDistinct[cookie          ] = ['sid=A1', 'theme=dark']

  req.rawHeaders (flat, order kept):
    [0] Host: shop.example.test
    [1] X-Trace-Id: aaa-111
    [2] X-Trace-Id: bbb-222
    [3] Accept: text/html
    [4] Accept: application/json
    [5] X-Forwarded-For: 203.0.113.9
    [6] X-Forwarded-For: 198.51.100.4

    [8] Cookie: theme=dark
    [9] Connection: close

세 API가 같은 요청에 대해 서로 다른 그림을 준다. 가장 널리 쓰이는 첫 번째 API는 두 줄을 쉼표와 공백으로 이어 붙인 문자열 하나를 준다. 두 번째와 세 번째는 줄을 그대로 보존한다. 그리고 Cookie만 쉼표가 아니라 세미콜론으로 이어졌다는 점을 눈여겨보자. 이 필드는 원래 세미콜론으로 구분된 목록이기 때문에 런타임이 필드마다 다른 규칙을 적용한 것이다.

이제 같은 바이트를 Python 서버에 보냈다.

1-B. Python 3.13.3 / win32
status : HTTP/1.1 200 OK

  headers.get(x-trace-id      )     = 'aaa-111'
  headers.get(accept          )     = 'text/html'
  headers.get(x-forwarded-for )     = '203.0.113.9'
  headers.get(cookie          )     = 'sid=A1'

  headers.get_all(x-trace-id      ) = ['aaa-111', 'bbb-222']

  headers.get_all(x-forwarded-for ) = ['203.0.113.9', '198.51.100.4']

    Host: shop.example.test
    X-Trace-Id: aaa-111
    X-Trace-Id: bbb-222
    Accept: text/html

    X-Forwarded-For: 203.0.113.9
    X-Forwarded-For: 198.51.100.4

    Cookie: theme=dark

여기서 이 글의 첫 번째 핵심이 드러난다. 같은 바이트인데 문자열 API가 주는 답이 두 런타임에서 다르다.

  • 한쪽은 두 줄을 이어 붙인다. 정보는 남지만 경계가 사라진다
  • 다른 쪽은 첫 줄만 준다. 두 번째 줄은 조용히 버려진다. 예외도 경고도 없다
  • 두 런타임 모두 모든 줄을 배열로 주는 별도의 API를 갖고 있다. 이름만 다를 뿐 존재는 같다
  • 어느 쪽도 오류를 내지 않았다. 중복 헤더 자체는 프로토콜 위반이 아니다
  • 그래서 「중복 헤더가 오면 어떻게 되나」라는 질문은 서버 하나만 보고 답할 수 없다

실무에서 이 차이가 무섭게 나타나는 지점이 있다. 어떤 팀이 문자열 API를 쓰는 언어로 앞단을 짜고, 다른 팀이 다른 언어로 뒷단을 짰다고 하자. 같은 요청을 두고 앞단은 「값이 두 개 이어진 문자열」을 보고, 뒷단은 「첫 번째 값 하나」를 본다. 둘 다 정상 동작이고 둘 다 로그에 아무 흔적을 남기지 않는다.

2. 목록형 필드는 합치는 것이 규격이다

합치는 것이 늘 잘못이라는 인상을 주고 싶지 않다. 오히려 반대다. 상당수 필드는 합쳐야 맞다. RFC 9110 5.2절은 이렇게 정의한다.

한 섹션 안에서 필드 이름이 반복되면, 그 결합 필드 값은 해당 섹션 안의 필드 라인 값들을 순서대로 이어 붙이되 각 값을 쉼표로 구분한 목록으로 구성된다. (RFC 9110, 5.2절)

그러니까 「두 줄로 보내기」와 「한 줄에 쉼표로 넣기」는 목록형 필드에서는 같은 뜻이어야 한다. 정말 그런지 확인했다. 같은 세 필드를 두 방식으로 보내고 결과를 비교했다.

EXP 2. list-based fields: two lines vs one comma line

 [Node.js v22.16.0]
   accept          via req.headers
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     parsed two lines : ['text/html', 'application/json']
     parsed one line  : ['text/html', 'application/json']
     SAME MEANING     : True
   cache-control   via req.headers
     two lines -> 'no-cache, max-age=0'
     one line  -> 'no-cache, max-age=0'
     parsed two lines : ['no-cache', 'max-age=0']
     parsed one line  : ['no-cache', 'max-age=0']
     SAME MEANING     : True
   accept-encoding via req.headers
     two lines -> 'gzip, br'
     one line  -> 'gzip, br'
     SAME MEANING     : True

 [Python 3.13.3]
   accept          via join(get_all())
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     SAME MEANING     : True
   cache-control   via join(get_all())
     SAME MEANING     : True
   accept-encoding via join(get_all())
     SAME MEANING     : True

두 런타임 모두, 세 필드 모두 같은 목록으로 갈라졌다. 목록형 필드에서는 줄로 나뉘어 왔든 한 줄에 쉼표로 왔든 최종 의미가 동일하다는 뜻이다. 그래서 여기서는 합치는 것이 손실이 아니다.

다만 여기에는 전제가 있다. 같은 5.3절이 이렇게 못박는다.

그 필드의 정의가 여러 필드 라인 값을 쉼표로 구분된 목록으로 재결합하는 것을 허용하지 않는 한, 송신자는 한 메시지 안에서 같은 이름의 필드 라인을 여러 개 만들거나 이미 같은 이름의 필드 라인이 있는데 또 붙여서는 안 된다. (RFC 9110, 5.3절)

즉 합쳐도 되는 것은 규격이 목록으로 정의한 필드뿐이고, 그 밖의 필드를 이름이 같다는 이유로 합치는 것은 규격이 금지한 쪽에 가깝다. 순서에 대해서도 같은 절이 분명히 적어 두었다.

따라서 같은 이름의 필드 라인이 수신되는 순서는 필드 값의 해석에 유의미하며, 프록시는 메시지를 전달할 때 이 필드 라인 값들의 순서를 바꾸어서는 안 된다. (RFC 9110, 5.3절)

순서가 의미를 갖는다는 것은 실무에서 자주 무시된다. 값을 정렬하거나 집합으로 만들어 중복을 제거하는 코드가 흔한데, 목록형 필드에서 그것은 우선순위 정보를 버리는 일이다.

2.1 한 줄에 여러 개, 여러 줄에 여러 개가 섞여 올 때

실전에서는 둘이 섞인다. 두 줄로 오는데 그중 한 줄에 쉼표가 또 들어 있는 경우다. 이때 줄만 세면 개수를 틀린다.

request sent:
  > Accept: text/html
  > Accept: application/json, text/plain

readList(accept) = ["text/html","application/json","text/plain"]
  note: 2 field lines, 3 members.

필드 라인은 둘인데 목록 구성원은 셋이다. 그러므로 목록형 필드를 읽는 올바른 절차는 두 단계다. 먼저 배열 API로 모든 줄을 받고, 그다음 각 줄을 쉼표로 나눠 하나로 펼친다. 줄만 세는 코드나 문자열 한 줄만 나누는 코드는 둘 다 반쪽이다.

3. Set-Cookie는 합치면 값이 부서진다

이제 예외다. 그리고 이 예외는 사소하지 않다. 서론의 증상이 바로 여기서 나온다.

쿠키 두 개를 정상적으로 각각 한 줄씩 내려보내면 이렇게 도착한다.

3-A. server sent TWO Set-Cookie lines (correct)
 res.headers["set-cookie"] type : Array
 value:
   [0] sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly
   [1] theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 cookies the client will store : ["sid=A1","theme=dark"]
 count = 2

쿠키 두 개가 그대로 저장된다. 이제 완전히 같은 두 쿠키를 쉼표와 공백으로 이어 붙여 한 줄로 만들었다. 목록형 필드였다면 아무 문제 없었을 처리다.

3-B. the SAME two cookies glued with ", " into one line
 raw value on the wire:
   sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly, theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 now split it back on "," the way a list-based field is split:
   [0] sid=A1; Path=/; Expires=Wed
   [1] 20 Aug 2026 10:00:00 GMT; HttpOnly
   [2] theme=dark; Path=/; Expires=Fri
   [3] 22 Aug 2026 10:00:00 GMT
 pieces = 4   (we started with 2 cookies)
 cookies the client would store : ["sid=A1","20 Aug 2026 10:00:00 GMT","theme=dark","22 Aug 2026 10:00:00 GMT"]

쿠키 두 개가 조각 네 개로 부서졌다. 원인은 명확하다. 만료 시각 표기가 요일 뒤에 쉼표를 갖고 있어서, 쉼표를 구분자로 삼는 순간 쿠키 하나가 그 안에서 둘로 잘린다. 그리고 잘린 뒷조각이 새로운 쿠키인 것처럼 보인다.

RFC 9110은 이 상황을 예견하고 5.5절에 이렇게 적었다.

날짜나 URI 참조 요소처럼 구성원 안에 쉼표를 담을 것으로 예상되는 필드는, 그 데이터 안의 쉼표를 잠재적인 목록 구분자와 구별할 수 있도록 해당 요소 주위에 구분 기호를 두고 정의되어야 한다. (RFC 9110, 5.5절)

쿠키 필드는 그렇게 정의되어 있지 않다. 만료 시각의 쉼표를 감싸는 따옴표가 없다. 그래서 쉼표만 보고는 어느 것이 구분자이고 어느 것이 데이터인지 판별할 방법이 원리적으로 없다. 같은 문서 5.3절은 이 필드를 이름을 들어 예외로 명시한다.

실제로 Set-Cookie 헤더 필드는 응답 메시지에서 여러 필드 라인에 걸쳐 나타나는 경우가 많고 목록 문법을 사용하지 않으므로, 같은 필드 이름의 여러 필드 라인에 대한 위 요구사항을 위반한다. (RFC 9110, 5.3절)

3.1 만료 시각이 없어도 안전하지 않다

「그럼 만료 속성을 안 쓰면 되는 것 아닌가」라고 생각할 수 있다. 확인해 보면 그쪽이 더 나쁘다.

3-D. even without Expires, joining loses a cookie boundary
 two lines  -> ["sid=A1; Path=/","theme=dark; Path=/"]
   stored   -> ["sid=A1","theme=dark"]  count=2
 one line   -> "sid=A1; Path=/, theme=dark; Path=/"
   a cookie parser reads ONE cookie from ONE line:
     name/value = sid=A1
     attributes = ["Path=/, theme=dark","Path=/"]
   -> "theme=dark" arrived as an ATTRIBUTE of sid, not as a cookie.
   -> stored cookies = ["sid=A1"]   count=1   (one cookie silently vanished)

여기서 서론의 증상이 정확히 재현된다. 쿠키를 두 개 내려보냈는데 하나만 저장됐다. 두 번째 쿠키가 사라진 게 아니라 첫 번째 쿠키의 속성으로 흡수됐다. 파서 입장에서 한 줄은 쿠키 하나이고, 세미콜론 뒤는 전부 속성이다. 인식하지 못하는 속성은 무시되므로 오류도 나지 않는다.

  • 서버 로그에는 쿠키 두 개를 만든 기록이 남는다. 그래서 서버 쪽을 아무리 봐도 원인이 안 보인다
  • 브라우저 개발자 도구의 저장소 탭에는 쿠키 하나만 보인다. 응답 헤더 탭에는 긴 한 줄이 보인다
  • 사라지는 것은 항상 뒤쪽 쿠키다. 그래서 「마지막에 넣은 쿠키만 안 된다」는 형태로 신고가 들어온다
  • 만료 속성이 있으면 정체불명의 쿠키가 생기기도 한다. 잘린 날짜 조각이 쿠키 이름처럼 보이기 때문이다
  • 쿠키 속성 자체의 의미는 이 문제와 별개다. 그쪽은 SameSite 동작에서 다뤘다

3.2 문자열로 바꾸는 순간 되돌아온다

이 필드를 배열로 잘 받아 놓고도 마지막에 망치는 경로가 있다.

3-E. what the array API vs the string API report
 res.headers["set-cookie"]         = Array(2)
 res.headersDistinct["set-cookie"] = Array(2)
 res.rawHeaders set-cookie lines   = 2
 String(res.headers["set-cookie"]) = "sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly,theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT"
   <- the moment you coerce it to a string, the "," is back and the damage is done

배열은 문자열로 변환되는 순간 쉼표로 이어 붙은 하나의 문자열이 된다. 로그에 찍거나, 템플릿 문자열에 넣거나, 다른 응답으로 그대로 복사하는 코드가 여기에 해당한다. 이 필드만큼은 배열인 채로 끝까지 다뤄야 한다.

4. Host가 두 개일 때 - 누가 어느 쪽을 믿느냐

이제 목록이 아닌 필드다. Host는 요청이 어느 대상을 향하는지를 정하는 단일값 필드다. 두 줄을 보내면 어떻게 되는지 측정했다.

EXP 4-A. two Host lines, different authorities
  > GET /who HTTP/1.1
  > Host: front.example.test
  > Host: back.example.test
  > Connection: close

 Node.js v22.16.0:
  status : HTTP/1.1 200 OK
    req.headers[host]         = 'front.example.test'
    req.headersDistinct[host] = ['front.example.test', 'back.example.test']

 Python 3.13.3:
  status : HTTP/1.1 200 OK
    headers.get(host)     = 'front.example.test'
    headers.get_all(host) = ['front.example.test', 'back.example.test']

측정 결과는 이렇다. 두 서버 모두 거부하지 않았다. 둘 다 200을 돌려줬고, 문자열 API로 물으면 첫 번째 값을 준다. 그리고 둘 다 배열 API로 물으면 두 값이 모두 남아 있다.

여기서 흥미로운 것은 Node의 동작이다. 1절에서 X-Trace-Id는 쉼표로 이어 붙였는데, Host는 이어 붙이지 않고 첫 값만 줬다. 같은 런타임이 필드에 따라 다른 규칙을 쓴다는 뜻이다. 어느 필드가 그런 취급을 받는지 더 넓게 확인했다.

EXP 4-B. single-value fields sent twice
  > Authorization: Bearer FIRST
  > Authorization: Bearer SECOND
  > Content-Type: application/json
  > Content-Type: text/plain
  > User-Agent: agent-one
  > User-Agent: agent-two
  > X-Trace-Id: aaa
  > X-Trace-Id: bbb

 Node.js v22.16.0:
    req.headers[authorization]         = 'Bearer FIRST'
    req.headersDistinct[authorization] = ['Bearer FIRST', 'Bearer SECOND']
    req.headers[content-type]          = 'application/json'
    req.headersDistinct[content-type]  = ['application/json', 'text/plain']
    req.headers[user-agent]            = 'agent-one'
    req.headersDistinct[user-agent]    = ['agent-one', 'agent-two']
    req.headers[x-trace-id]            = 'aaa, bbb'
    req.headersDistinct[x-trace-id]    = ['aaa', 'bbb']

 Python 3.13.3:
    headers.get(authorization)     = 'Bearer FIRST'
    headers.get_all(authorization) = ['Bearer FIRST', 'Bearer SECOND']
    headers.get(x-trace-id)        = 'aaa'
    headers.get_all(x-trace-id)    = ['aaa', 'bbb']

Node는 단일값으로 알려진 필드 목록을 내부에 갖고 있고, 그 목록에 든 필드는 이어 붙이지 않고 첫 값만 남긴다. 그래서 인증 토큰 두 개가 왔을 때 문자열 API는 첫 번째만 보여준다. 두 번째 토큰은 코드가 실행되기 전에 이미 시야에서 사라진 상태다.

4.1 왜 위험한가 - 판단하는 층이 둘 이상일 때

이 상황이 위험한 이유는 값이 이상해서가 아니다. 구조 때문이다. 요청 하나를 여러 층이 차례로 판단하는 구성을 생각해 보자. 앞단이 무언가를 보고 결정을 내리고, 뒷단이 다시 같은 것을 보고 결정을 내린다.

  • 같은 이름이 두 줄 왔을 때 어느 쪽이 진짜인지는 규격이 아니라 구현이 정한다. 위 측정에서 두 런타임은 우연히 둘 다 첫 값을 골랐지만, 그것을 모든 구현이 그렇다는 근거로 쓸 수는 없다
  • 앞단이 첫 값을 믿고 뒷단이 마지막 값을 믿는 조합이 성립하면, 두 층이 서로 다른 대상에 대해 판단하게 된다. 어느 쪽도 오류를 내지 않는다
  • 앞단이 합쳐서 넘기고 뒷단이 합쳐진 문자열 전체를 하나의 값으로 취급하는 조합도 있다. 이때 뒷단이 보는 값은 앞단이 판단한 값과 문자열 자체가 다르다
  • 이 어긋남은 로그로 추적하기 어렵다. 각 층의 로그에는 그 층이 고른 값 하나만 찍히기 때문이다. 두 로그를 나란히 놓기 전에는 차이가 보이지 않는다
  • 그러므로 대응은 값을 잘 고르는 것이 아니라 고를 일이 생기지 않게 하는 것이다. 즉 경계에서 정규화하거나 거절한다

실무 규칙은 단순하다. 대상을 결정하는 필드가 두 줄 이상 왔다면 그 요청은 이미 정상이 아니다. 어느 값이 맞는지 고민할 것이 아니라, 가장 바깥 경계에서 줄 수를 세어 하나가 아니면 거절하거나 하나로 정규화하고, 그 뒤 층들이 다시 판단하지 않게 만들어야 한다. 뒤에서 각자 판단하게 두는 순간 층마다 다른 답이 나올 여지가 생긴다.

5. Content-Length 중복 - 여기서는 거절이 정답이다

Content-Length는 본문이 어디서 끝나는지를 정하는 필드다. 이 값이 애매해지면 메시지의 경계 자체가 애매해진다. 값이 다를 때와 같을 때를 나눠 측정했다.

EXP 5. duplicate Content-Length, measured

 Node.js v22.16.0 http server
  baseline: one Content-Length             -> HTTP/1.1 200 OK    headers['content-length']='5'  headersDistinct=['5']
  two Content-Length, SAME value           -> HTTP/1.1 400 Bad Request
  two Content-Length, DIFFERENT values     -> HTTP/1.1 400 Bad Request
  one Content-Length holding a comma list  -> HTTP/1.1 400 Bad Request

 Python 3.13.3 http.server
  baseline: one Content-Length             -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5']
  two Content-Length, SAME value           -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '5']
  two Content-Length, DIFFERENT values     -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '7']
  one Content-Length holding a comma list  -> HTTP/1.1 200 OK    get('content-length')='5, 5'   get_all=['5, 5']

 --- node server error log ---
 [clientError] code=HPE_UNEXPECTED_CONTENT_LENGTH msg=Parse Error: Duplicate Content-Length
 [clientError] code=HPE_UNEXPECTED_CONTENT_LENGTH msg=Parse Error: Duplicate Content-Length
 [clientError] code=HPE_INVALID_CONTENT_LENGTH   msg=Parse Error: Invalid character in Content-Length

두 런타임의 태도가 정반대다. 정리하면 이렇다.

  • Node는 값이 완전히 같아도 거절한다. 5와 5가 왔는데도 400이다. 「모순이 없으니 통과」가 아니라 「중복 자체가 오류」라는 태도다
  • 거절은 애플리케이션 코드에 도달하기 전에 파서 단계에서 일어난다. 요청 핸들러는 아예 호출되지 않았다
  • 한 줄에 쉼표 목록으로 넣은 경우는 다른 오류 코드로 거절됐다. 값에 쉼표가 들어간 것 자체를 문제 삼은 것이다
  • Python 표준 라이브러리 서버는 네 경우 모두 통과시켰고, 흔히 쓰는 조회 메서드는 5만 돌려줬다. 두 번째 값이 7이든 5든 코드는 차이를 볼 수 없다
  • 즉 같은 요청이 한 런타임에서는 400이고 다른 런타임에서는 200이다. 이 필드에 관해서는 「일반적인 서버 동작」이라는 것이 존재하지 않는다

규격은 값에 쉼표가 들어가는 것에 대해 분명하다.

송신자는 쉼표를 포함하는 필드 값을 가진 Content-Length 헤더 필드를 생성해서는 안 된다. (RFC 9110, 8.6절)

여기서 얻을 실무 지침은 하나다. 본문 경계를 정하는 필드는 조용히 하나를 고르면 안 된다. 값이 같아 보여도 마찬가지다. 값이 같다는 확인 자체가 배열 API를 써야 가능한 일이고, 문자열 API만 쓰는 코드는 값이 같은지 다른지조차 알 수 없다. 이 필드에 관해서는 엄격한 쪽이 옳다.

6. 런타임이 주는 자료구조 - 문자열이 도착하면 이미 늦었다

지금까지의 관찰을 하나로 묶으면 이렇게 된다. 합칠지 말지를 런타임이 대신 정해 버리면, 개발자는 이미 결정된 결과만 본다. 이것이 왜 되돌릴 수 없는 결정인지 증명했다.

6-B. the proof: a joined string cannot tell you what arrived
 case A: two lines  -> ["aaa-111","bbb-222"]
 case B: one line   -> ["aaa-111, bbb-222"]
 joined A           = "aaa-111, bbb-222"
 joined B           = "aaa-111, bbb-222"
 joinA === joinB    : true
 -> two different wire shapes collapse to the same string.

줄이 두 개였던 경우와 줄이 하나인데 그 안에 쉼표가 있던 경우가 완전히 같은 문자열이 됐다. 이 문자열을 받은 코드는 원래 몇 줄이 왔는지 알 방법이 없다. 정보가 숨겨진 것이 아니라 사라진 것이다. 나중에 아무리 정교하게 파싱해도 복원되지 않는다.

같은 함정이 값 자체에 쉼표가 들어 있을 때 반대 방향으로도 생긴다.

6-C. a value that legitimately contains a comma
 one line whose value has a comma : ["Wed, 20 Aug 2026 10:00:00 GMT"]
 joined                           : "Wed, 20 Aug 2026 10:00:00 GMT"
 naive split(",")                 : ["Wed","20 Aug 2026 10:00:00 GMT"]
 pieces = 2  from 1 original line(s)

한 줄짜리 값이 쉼표 분리로 두 조각이 됐다. 그래서 쉼표로 나누는 것은 그 필드의 문법이 목록이라고 정의했을 때만 유효하다. 모든 헤더에 일괄로 적용하는 유틸리티 함수는 이 지점에서 조용히 틀린다.

6.1 브라우저와 서버가 공유하는 헤더 객체

웹 표준 헤더 객체는 브라우저와 서버 양쪽에서 쓰인다. 이 객체가 무엇을 주는지도 확인했다.

6-A. WHATWG Headers (the fetch API object)
 h.get("x-trace-id")      = "aaa-111, bbb-222"
   typeof                 = string
 h.get("set-cookie")      = "sid=A1; Path=/, theme=dark; Path=/"
   typeof                 = string
 h.getSetCookie()         = ["sid=A1; Path=/","theme=dark; Path=/"]
   length                 = 2
 [...h.entries()]         = [["set-cookie","sid=A1; Path=/"],["set-cookie","theme=dark; Path=/"],["x-trace-id","aaa-111, bbb-222"]]

중요한 것은 두 번째 줄이다. 일반 조회 메서드는 쿠키 필드에 대해서도 이어 붙인 문자열 하나를 준다. 3절에서 부서지는 것을 봤던 바로 그 형태다. 그래서 이 객체에는 쿠키 전용 배열 조회 메서드가 따로 있다. 그 메서드를 쓰지 않으면 3절의 파괴가 그대로 일어난다.

반면 항목 순회는 쿠키 필드를 두 개의 항목으로 따로 내놓았다. 같은 객체 안에서도 어느 접근자를 쓰느냐에 따라 답이 다르다는 것이 요점이다.

6.2 API 대조표

지금까지 실행으로 확인한 것을 정리했다. 이 표에서 「손실」이라고 적힌 API로 판정을 내리면 안 된다.

API반환중복 필드는 어떻게 되나쿠키 필드판정
Node req.headers[name]문자열쉼표와 공백으로 이어 붙임 (단일값 필드는 첫 값만)배열 (예외)손실
Node req.headersDistinct[name]배열줄마다 한 항목배열무손실
Node req.rawHeaders평탄 배열이름과 값의 쌍, 순서 보존쌍으로 보존무손실 + 순서 + 원래 표기
표준 Headers.get(name)문자열쉼표와 공백으로 이어 붙임이어 붙임 (파괴)손실
표준 Headers.getSetCookie()배열해당 없음줄마다 한 항목무손실 (쿠키 전용)
Python headers.get(name)문자열첫 줄만, 나머지 폐기첫 줄만손실
Python headers.get_all(name)리스트줄마다 한 항목줄마다 한 항목무손실

표를 읽는 법은 이렇다. 모든 런타임이 무손실 API를 이미 갖고 있다. 부족한 것은 기능이 아니라 습관이다. 손실 API 쪽이 이름이 짧고 예제에 먼저 나오기 때문에 기본값처럼 쓰일 뿐이다.

7. 자작 중계 한 홉 - 읽는 API가 뒷단이 보는 것을 정한다

앞 절의 「정보가 사라진다」가 한 프로세스 안의 문제로 끝나지 않는다는 것을 보이려면 홉을 하나 더 두어야 한다. 그래서 스무 줄짜리 중계를 두 벌 만들었다. 두 중계는 헤더를 읽는 API 하나만 다르고 나머지는 동일하다.

이 절의 중계는 이 글을 위해 직접 짠 최소 구현이다. 어떤 상용 프록시, 로드밸런서, API 게이트웨이, 웹 서버의 동작도 대표하지 않으며 그것들이 이렇게 동작한다는 근거로 쓸 수 없다. 여기서 보이려는 것은 제품의 동작이 아니라 「중계가 헤더를 어떤 API로 읽느냐가 뒷단이 보는 것을 정한다」는 인과 구조 하나다. 여러분이 쓰는 제품이 어떻게 처리하는지는 이 글의 방법으로 직접 측정하면 된다.

=== EXP 7. one hop through a hand-written relay ===
client sends (same bytes in every case):
  > GET /through HTTP/1.1
  > Host: shop.example.test
  > X-Trace-Id: aaa-111
  > X-Trace-Id: bbb-222
  > Accept: text/html
  > Accept: application/json
  > X-Note: first
  > X-Note: second

7-A. NO relay: straight to the origin
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2
   x-note     lines at origin : 2

7-B. relay reading req.headers (the string API)
   origin saw  x-trace-id: aaa-111, bbb-222
   origin saw  accept: text/html, application/json
   origin saw  x-note: first, second
   x-trace-id lines at origin : 1   value="aaa-111, bbb-222"
   x-note     lines at origin : 1   value="first, second"

7-C. relay reading req.rawHeaders (the array API)
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2   value="aaa-111, bbb-222"
   x-note     lines at origin : 2   value="first, second"

결과를 정리하면 이렇다.

  • 중계를 거치지 않으면 두 줄이 두 줄로 도착한다. 원본 상태다
  • 문자열 API로 읽는 중계를 거치면 두 줄이 한 줄로 도착한다. 중계가 값을 바꾼 것이 아니다. 중계는 자기가 갖지 않은 것을 전달할 수 없었을 뿐이다. 읽는 순간 이미 문자열 하나였다
  • 배열 API로 읽는 중계를 거치면 줄 수가 끝까지 보존된다. 같은 중계, API 하나 차이다
  • 주목할 점은 7-C의 마지막 두 줄이다. 뒷단에서 줄은 둘인데 문자열 API로 물으면 여전히 이어 붙은 하나다. 즉 앞단이 잘 전달해도 뒷단이 어떤 API로 읽느냐에 따라 다시 손실이 일어난다
  • 그래서 양쪽 층이 모두 배열 API를 쓸 때만 두 층이 같은 것을 본다. 한쪽만 고쳐서는 부족하다

여기서 나오는 결론이 이 글의 핵심 중 하나다. 「우리 앞단은 헤더를 안 건드린다」는 말은 대개 값을 수정하지 않는다는 뜻이다. 그런데 값을 수정하지 않아도 줄의 구조는 읽는 방식만으로 바뀐다. 아무도 손대지 않았는데 모양이 달라져 있는 것이 이 문제의 성질이다.

8. 설계 규칙 - 무엇을 합치고 무엇을 나눌 것인가

지금까지의 측정을 실무 규칙으로 바꿨다. 먼저 필드를 세 부류로 나눈다. 이 분류가 모든 판단의 출발점이다.

부류예여러 줄이 왔다는 뜻읽는 법여러 줄로 보내도 되나
목록형Accept, Cache-Control, Accept-Encoding, Vary, Via목록 구성원이 늘어난 것배열로 모든 줄을 받고 각 줄을 쉼표로 다시 펼침된다. 한 줄에 쉼표로 넣은 것과 같은 뜻
단일값Host, Content-Length, Content-Type, Authorization, Location있어서는 안 되는 상태배열로 받아 줄 수를 세고, 1이 아니면 거절하거나 정규화안 된다. 합치는 것도 답이 아니다
절대 합치지 않음Set-Cookie정상. 항목이 여러 개인 것배열 전용 접근자로 받아 배열인 채로 끝까지 다룸된다. 오히려 여러 줄이 정상이고 합치면 파괴됨
사설 헤더직접 만든 X- 계열정의한 사람이 정해야 함정의를 문서에 적고 양쪽 코드가 같은 정의를 참조정한 대로. 정하지 않았으면 그것이 문제

이 분류를 코드로 옮긴 뒤, 실제 요청에 돌려 봤다. 아래는 목록형과 단일값이 섞여 오고 사설 헤더까지 있는 요청에 대한 결과다.

8.1 안전하게 읽는 세 가지 함수

실제로 쓴 구현은 짧다. 부류별로 하나씩이면 충분하다.

// 목록형: 모든 줄을 받고, 각 줄을 다시 쉼표로 펼친다 (2단계)
function readList(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  return lines.flatMap(v => v.split(',').map(s => s.trim())).filter(Boolean);
}

// 단일값: 줄이 하나가 아니면 값을 주지 않고 거절한다
function readSingleton(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  if (lines.length === 0) return { ok: true, value: null };
  if (lines.length > 1)   return { ok: false, reason: 'arrived ' + lines.length + ' times', lines };
  if (lines[0].includes(',')) return { ok: false, reason: 'single line contains a comma', lines };
  return { ok: true, value: lines[0] };
}

// 절대 합치지 않음: 배열 그대로, 문자열로 만들지 않는다
function readCookies(distinct) {
  return (distinct['set-cookie'] || []).slice();
}

파이썬 쪽도 구조가 같다. 조회 메서드를 바꾸는 것이 전부다.

# 손실: 첫 줄만 온다
value = headers.get('x-trace-id')

# 무손실: 모든 줄이 온다
lines = headers.get_all('x-trace-id') or []

# 목록형은 두 단계
members = [p.strip() for line in lines for p in line.split(',') if p.strip()]

# 단일값은 줄 수를 먼저 본다
if len(lines) != 1:
    raise ValueError('singleton field arrived %d times' % len(lines))

8.2 앞단과 뒷단이 같은 값을 보게 하는 법

7절에서 봤듯이 한쪽만 고쳐서는 부족하다. 순서대로 적으면 이렇다.

  • 가장 바깥 경계에서 한 번만 정규화한다. 단일값 필드가 두 줄 이상이면 그 자리에서 거절하거나 하나로 줄인다. 안쪽 층들은 이미 정리된 것을 받는다고 가정할 수 있어야 한다
  • 안쪽에서 다시 판단하지 않는다. 같은 필드를 여러 층이 각자 해석하는 구성이 어긋남의 원인이다. 판단은 한 곳에서만 한다
  • 판단에 쓰는 값은 반드시 배열 API로 읽는다. 값을 쓰는 것이 아니라 몇 줄이 왔는지를 함께 보기 위해서다. 줄 수를 모르면 정규화도 거절도 할 수 없다
  • 중계 코드는 읽은 그대로 전달한다. 문자열로 받아 문자열로 넘기는 순간 뒷단의 선택지가 사라진다
  • 사설 헤더는 부류를 문서에 적는다. 목록형인지 단일값인지 정의가 없으면 층마다 다르게 해석하는 것이 당연하다
  • 줄 수를 로그에 남긴다. 값만 찍는 로그는 두 줄이 온 사실 자체를 기록하지 못한다. 이름과 줄 수를 함께 남기면 사후 추적이 가능해진다
  • 쿠키 필드는 배열인 채로 끝까지 옮긴다. 응답을 복사하거나 다시 조립하는 코드가 있다면 그 지점을 특히 확인한다

8.3 점검 목록

  • 헤더를 읽는 코드를 전부 찾아, 문자열 API를 쓰는 곳과 배열 API를 쓰는 곳을 나눠 적었다
  • 인증·대상·본문 길이처럼 판단에 쓰이는 필드는 전부 배열 API로 바꿨다
  • 단일값 필드가 두 줄 이상 왔을 때 조용히 통과하지 않는다는 것을 테스트로 확인했다
  • 목록형 필드를 읽을 때 줄 배열과 쉼표 분리를 둘 다 했다 (한쪽만 하면 개수를 틀린다)
  • 쿠키 필드를 문자열로 변환하는 코드가 없다. 로그·템플릿·응답 복사 지점을 모두 확인했다
  • 중계나 복사 코드가 헤더를 읽은 형태 그대로 넘긴다
  • 사설 헤더의 부류가 문서에 적혀 있고 앞단과 뒷단이 같은 문서를 본다
  • 중복이 감지됐을 때 이름과 줄 수가 로그에 남는다
  • 운영 환경에서 쓰는 각 구성요소가 중복 필드를 어떻게 처리하는지 직접 측정해 기록했다 (제품 문서나 추측이 아니라)
  • 헤더 이름의 대소문자는 별개 문제이므로 그쪽 점검도 따로 했다

## 1. 필드 유형별 판단표

| 유형 | 예 | 여러 줄 = 무슨 뜻 | 읽는 법 | 합쳐도 되나 |
|---|---|---|---|---|
| 목록형 | Accept, Accept-Encoding, Accept-Language, Cache-Control, Vary, Via, TE, Content-Encoding | 목록 구성원이 늘어남 | 배열로 전부 받고 각 줄을 쉼표로 다시 분리 | 된다 (규격) |
| 단일값 | Host, Content-Length, Content-Type, Authorization, Location, Date, ETag, Retry-After | 있어서는 안 되는 상태 | 배열로 받아 줄 수를 세고 1이 아니면 거절 | 안 된다 |
| 절대 합치지 않음 | Set-Cookie | 정상, 항목이 여러 개 | 배열 전용 접근자, 배열인 채로 유지 | 절대 안 된다 (파괴됨) |
| 사설 헤더 | 직접 만든 X- 계열 | 정의한 사람이 정해야 함 | 정의를 문서화하고 양쪽이 같은 정의 참조 | 정한 대로 |

## 2. 런타임 동작 대조 (실측)

| API | 반환 | 중복이 오면 | 판정 |
|---|---|---|---|
| Node req.headers[name] | 문자열 | 쉼표+공백 결합 / 단일값 필드는 첫 값만 | 손실 |
| Node req.headersDistinct[name] | 배열 | 줄마다 한 항목 | 무손실 |
| Node req.rawHeaders | 평탄 배열 | 이름·값 쌍, 순서·표기 보존 | 무손실 |
| Headers.get(name) | 문자열 | 쉼표+공백 결합 (쿠키도 결합됨) | 손실 |
| Headers.getSetCookie() | 배열 | 줄마다 한 항목 | 무손실 (쿠키 전용) |
| Python headers.get(name) | 문자열 | 첫 줄만, 나머지 폐기 | 손실 |
| Python headers.get_all(name) | 리스트 | 줄마다 한 항목 | 무손실 |

## 3. 실측 요약

- 같은 요청 바이트, 두 런타임: 한쪽은 두 줄을 결합, 다른 쪽은 첫 줄만 반환. 둘 다 오류 없음
- 목록형 3종(Accept / Cache-Control / Accept-Encoding): 두 줄 = 한 줄 쉼표. 의미 동일 확인
- Set-Cookie 2개를 쉼표 결합 후 재분리: 조각 4개 (만료 시각의 쉼표가 쿠키를 반으로 자름)
- 만료 속성 없는 단순 쿠키 2개를 결합: 저장 쿠키 1개. 둘째 쿠키가 첫째의 속성으로 흡수됨
- Host 2줄: 두 런타임 모두 200, 문자열 API는 첫 값. 배열 API에는 둘 다 남아 있음
- Content-Length 2줄: 한 런타임은 값이 같아도 400 (파서 단계), 다른 런타임은 4가지 경우 전부 200
- 결합된 문자열은 원래 줄 수를 복원할 수 없음 (두 줄 vs 한 줄+쉼표가 동일 문자열)
- 자작 중계 1홉: 문자열 API로 읽으면 2줄이 1줄로, 배열 API로 읽으면 2줄 유지

## 6. 점검 목록

- [ ] 헤더를 읽는 모든 지점을 **문자열 API / 배열 API**로 분류해 목록화했다
- [ ] 인증·대상·본문 길이 등 **판단에 쓰이는 필드**는 전부 배열 API로 읽는다
- [ ] 단일값 필드가 2줄 이상일 때 **조용히 통과하지 않는다** (테스트로 확인)
- [ ] 목록형은 **줄 배열 + 쉼표 분리 2단계**로 읽는다 (한쪽만 하면 개수 오류)
- [ ] **Set-Cookie를 문자열로 변환하는 코드가 없다** (로그·템플릿·응답 복사 전부 확인)
- [ ] 중계·복사 코드가 헤더를 **읽은 형태 그대로** 넘긴다
- [ ] 사설 헤더의 **유형이 문서에 적혀 있고** 앞단·뒷단이 같은 문서를 참조한다
- [ ] 중복 감지 시 **필드명과 줄 수**가 로그에 남는다
- [ ] 정규화는 **가장 바깥 경계에서 한 번만**, 안쪽은 재판단하지 않는다
- [ ] 운영 구성요소별 중복 처리 동작을 **직접 측정해 기록**했다 (문서·추측 아님)

## 7. 하지 말 것

- ❌ 모든 헤더에 일괄로 쉼표 분리를 적용하는 유틸리티 — 값 안의 쉼표를 자른다
- ❌ Set-Cookie를 문자열로 이어 붙이기 — 쿠키가 조각나거나 통째로 사라진다
- ❌ 단일값 필드에서 조용히 첫 값 채택 — 층마다 다른 값을 볼 여지를 만든다
- ❌ 「우리 앞단은 헤더를 안 건드린다」는 가정 — 값을 안 바꿔도 줄 구조는 바뀐다
- ❌ 목록형에서 정렬·중복 제거 — 도착 순서가 해석에 유의미하다
- ❌ 제품 문서만 읽고 동작 단정 — 버전·설정마다 다르다. 측정하라
- ❌ 값만 남기는 로그 — 두 줄이 온 사실 자체가 기록되지 않는다

자주 묻는 질문

중복 헤더 자체를 막으면 되지 않나?

막을 수 없고 막을 이유도 없다. 목록형 필드에서는 여러 줄이 정상적인 표현이고, 쿠키 필드는 오히려 여러 줄이 기본이다. 전면 차단은 정상 요청을 깨뜨린다. 필요한 것은 차단이 아니라 필드별로 다른 처리다. 8절의 세 부류 분류가 그 출발점이다.

배열 API로 바꾸면 코드가 복잡해지지 않나?

모든 곳을 바꿀 필요는 없다. 판단에 쓰이는 필드만 바꾸면 된다. 로그에 찍거나 화면에 보여주는 용도라면 문자열 API로도 충분하다. 반면 인증, 대상 결정, 본문 길이, 접근 제어처럼 그 값으로 분기하는 자리는 반드시 줄 수를 함께 봐야 한다. 실무에서 이런 자리는 대개 손에 꼽을 정도다.

순서를 정렬하거나 중복을 제거해도 되나?

목록형 필드에서는 안 된다. RFC 9110 5.3절이 같은 이름의 필드 라인이 수신된 순서가 해석에 유의미하다고 명시하고, 중계자가 전달할 때 그 순서를 바꾸면 안 된다고 규정한다. 선호도나 우선순위를 담는 필드에서 정렬은 의미를 바꾸는 행위다. 집합으로 만들어 중복을 없애는 것도 같은 이유로 위험하다.

제품 문서에 적힌 동작을 믿어도 되나?

출발점으로는 쓸 수 있지만 결론으로 쓸 수는 없다. 이 글에서 확인한 것만 봐도 같은 요청이 한 런타임에서는 400이고 다른 런타임에서는 200이었다. 버전과 설정에 따라서도 달라진다. 그래서 권하는 것은 이 글의 방법을 그대로 쓰는 것이다. 원시 소켓으로 바이트를 직접 써 넣고, 받은 쪽에서 배열 API로 줄 수를 세어 보라. 스무 줄이면 된다.

이 글의 결과를 우리 인프라에 그대로 적용해도 되나?

안 된다. 이 글의 수치는 명시한 두 런타임의 특정 버전에서 측정한 것이고, 다른 제품이나 다른 버전을 대표하지 않는다. 특히 7절의 중계는 이 글을 위해 직접 짠 스무 줄짜리 구현이라 어떤 상용 제품의 동작과도 무관하다. 가져갈 것은 수치가 아니라 방법과 분류다. 여러분의 구성요소에 대해 같은 측정을 하고, 8절의 표에 여러분의 결과를 채워 넣으면 된다.
