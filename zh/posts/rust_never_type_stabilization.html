为什么需要一个没有任何值的类型

给发散的表达式一个类型，以及改动类型推断默认值这件事的分量

2026-08-28 开发/基础设施

引言：那个说是拖了很久的特性，其实早就在用了

只要用 Rust 写过东西，多半写过这样的函数。

fn bail(msg: &str) -> ! {
    eprintln!("{msg}");
    std::process::exit(1)
}

返回类型的位置上只有一个感叹号。这种写法很早以前就能在稳定通道里直接用。可是 2026 年 8 月末，never 类型历经十余年终于稳定化的消息传开了。已经在用的东西，现在才稳定化，这话是什么意思。

答案有两层。第一，到目前为止稳定通道里能用的，只有写在返回位置上的 !。像 let x: !、Result<u32, !>、作为泛型参数的 ! 这样放在普通类型位置上的用法，一直是 nightly 专属。第二，而且这一层才是真正的原因——绊住脚的不是语法，而是类型推断最终决定不了时会落到哪里这一个默认值。

本文讲的就是这个默认值。一个没有任何值的类型为什么有用，以及在一门已经发布出去的语言里改动默认值为什么如此昂贵。它与从 unsafe 一侧讨论 Rust 安全模型的 从 iddqd 看 Rust 的 unsafe 封装 - borrow-from-value 与自引用结构的陷阱，以及讨论事后给语言加类型所产生的边界成本的 在 BEAM 上加载静态类型这一选择 - Gleam 挪动的边界与留下的边界属于同一条脉络。

稳定化的是什么、什么时候到手 — 以 2026 年 8 月为准

先把时间点说准。稳定通道里还没有。

  • 稳定化 PR rust-lang/rust#155499（标题就是 stabilize never type）已于 2026 年 8 月 24 日合入。里程碑是 1.100.0。
  • 按 releases.rs 的时间表，1.100.0 将在 2026 年 9 月 25 日从 master 分支，并于 2026 年 11 月 12 日进入稳定通道。
  • 写作本文时的稳定版本是 1.98.0，下一个 1.99.0 的预定日期是 2026 年 10 月 1 日。

所谓已经稳定化的标题，指的是合入的时间点。如果不用 nightly，真正到手是 11 月，最终范围也要等发布说明出来才算定下。

这个 PR 打包处理的事情有四件。

  • 把 ! 稳定化为正式类型 — 返回位置之外也能写了
  • 把类型推断的回退在所有版次上统一为 !
  • 把 std::convert::Infallible 转为 ! 的类型别名
  • 移除为预告而开启的 dependency_on_unit_never_type_fallback lint

再说十余年这个说法的依据。RFC 1216（bang type）的 Start Date 是 2015-07-19。到合入那天，走了 11 年 1 个月。标题里的十年是取整的说法，而且中间这段时间并不是空白。后面会看到，它曾经稳定化过一次，随后被回退。

一个没有任何值的类型这一想法

把类型看成值的集合，账就好算了。bool 有两个值，u8 有 256 个，() 只有一个。那么值有 0 个的类型是什么。

值有 0 个，就造不出这个类型的值。既然造不出，那么往这个类型的变量里塞东西的代码就不可能被执行到。这里翻转了一次——没有值被翻译成了执行不会到达这里。一句关于值的个数的话，变成了一句关于控制流的话。Rust Reference 把 ! 写作没有值的类型，用来表示永远不会完成的计算的结果。

为什么需要这种东西。类型检查器要求每个表达式都有类型，才能把计算接下去。可程序里有一大堆不返回值就结束的表达式。

  • panic!("...") — 无论是展开还是直接中止，后面都接不下去
  • loop {} — 没有 break 的无限循环
  • std::process::exit(1) — 进程本身消失了
  • return — 控制流走出函数，所以这个位置不会留下值
  • break 与 continue — 控制流去了别处
  • ? 运算符的失败路径 — 提前返回，所以没有后续

在 RFC 1216 之前，Rust 给这类表达式安的是 ()。这样一来，就等于说在执行根本到不了的地方有一个值。从编译器的角度看，这个谎言不是免费的。死代码的判定会变模糊，分支汇合处的类型计算里会混进多余的东西。

RFC 的表述很简洁。! 的行为像一个空枚举，但可以被隐式转换成任何别的类型。前半句说的是它没有值这个事实，后半句才是让这个类型真正有用的性质。

它会流向所有类型 — 当分支的一侧走到头时

! 的核心性质只有一条。! 类型的表达式会被强制转换成其他所有类型。Reference 就是这么写的。

这为什么是安全的。因为要转换的那个值根本不存在。连转换规则都不需要定义。把这条逻辑摆得最直白的是 Haskell 的 Data.Void，那里有一个 absurd :: Void -> a 函数，文档解释说它就是从假可以推出任何东西这条逻辑原则的实现。既然是一个调用不到的函数，那么承诺返回什么都不算撒谎。

在实务中，这条性质最显眼的地方是分支的一侧走到头时。

let port: u16 = match std::env::var("PORT") {
    Ok(v)  => v.parse().unwrap_or(8080),
    Err(_) => {
        eprintln!("PORT is required");
        std::process::exit(1)   // 这一分支的类型是 !
    }
};

match 的所有分支类型必须相同。上面那支是 u16，下面那支是 !。因为 ! 会流向 u16 一侧，两者就对上了。程序员不必编造一个毫无意义的占位值。在没有这个类型的世界里，下面那支得写上一个 0 之类的东西，而那个 0 会给读代码的人留下一个错误的疑问：这个值有可能被用到吗。

一旦写进函数签名，信息的方向又变了一次。

fn bail(msg: &str) -> ! { eprintln!("{msg}"); std::process::exit(1) }

let cfg = load_config().unwrap_or_else(|_| bail("config missing"));
//        即使闭包给出 !，cfg 的类型也不会动摇

如果这里的 bail 声明为返回 ()，上面的代码就会因为类型对不上而编译不过。一旦声明为 !，三件事会同时成立。

  • 调用处的类型对得上 — 可以直接放在需要返回值的位置上
  • 后面的代码被判定为不可达 — 未初始化变量的诊断和死代码警告都会更准
  • 实现一旦改动，编译就会拦住 — 以后谁在 bail 里不小心返回了，当场就会报错

最后一条正是它与注释分道扬镳的地方。写一行// 这个函数不会返回的注释，在实现改动之后什么也不做。

空枚举与 ! — 自己造一个没有值的类型

读到这里，自然会冒出一个念头。自己写一个没有变体的枚举不就行了吗。

enum Never {}          // 没有变体，所以造不出值

实际上大家就是这么用的。标准库的 std::convert::Infallible 正是这件东西，文档把它写作为永远不可能发生的错误准备的错误类型，并说因为这个枚举没有变体，所以这个类型的值实际上不可能存在。RFC 1216 也承认，用户自定义的空类型能覆盖前面说的全部用途。

那么区别在哪里。有三点。

  • 强制转换 — ! 会自动流向任何类型。空枚举不会，得用 match x {} 这样的形式亲手消去
  • 返回位置的表达力 — -> ! 说的是不会返回。-> Never 在语法上读作给出一个 Never 值，而那个值不可能存在这件事藏在一层之后
  • 对推断的影响 — 空枚举是普通的用户类型，不会牵扯推断默认值的争论。! 是语言内置的，所以会牵扯

第三点就是本文余下的全部内容。而 Infallible 的命运，文档里早就写好了——计划是等 ! 稳定化之后把 Infallible 变成它的类型别名，并最终废弃 Infallible。这次的 PR 实际执行了这项别名转换。

同一份文档也自己点出了一个陷阱。给 fn() -> ! 和 fn() -> Infallible 分别挂上 trait 实现的代码，在两者变成同一个类型的那一刻，实现就重叠了。这意味着做一个别名这件事，可能在别人的代码里制造冲突，而连这种事都得数清楚，才是稳定化工作的真实体量。

为什么拖了这么久 — 当推断决定不了时

现在进入正题。把 ! 认定为类型的语法并不难。难的是类型推断最终什么都决定不了的那个位置。

有时候一个泛型类型变量会一路不受任何约束地留到最后。编译器不能就这么放弃，于是填进一个默认值。这就是回退（fallback）。Rust 历史上把那个值定为 ()。

版次指南的表述精准地点住了问题。历史上回退类型是 ()。正因如此，即使在没有回退时编译器本不会推断出 () 的位置上，! 也会自动被强制转换成 ()。这既令人困惑，也一直挡着 ! 类型的稳定化。

换句话说，一边说要把 ! 当成真正的类型对待，一边在决定不了的位置上把它按倒成 ()，这前后是不通的。可是一改这个默认值，原本能编译的代码就编译不过了。看看版次指南举的例子。

fn outer<T>(x: T) -> Result<T, ()> {
    fn f<T: Default>() -> Result<T, ()> { Ok(T::default()) }
    f()?;        // 以前：T = ()  /  现在：T = !
    Ok(x)
}

f()? 的成功值被丢掉了，所以 T 没有任何约束。以前它落到 ()，而 () 实现了 Default，于是通过。现在它落到 !，而 ! 没有实现 Default，于是报错。修法只有一种，就是由人把意图钉死，写成 f::<()>()?; 这样。

这种程度虽然麻烦，但是安全的。编译错误会大声告诉你。真正的问题在于语义悄无声息地改变的那一侧。编译器的 lint 文档举的例子就是这个。

if true {
    return
} else {
    unsafe { std::mem::zeroed() }   // 回退是 () 则健全，是 ! 则立即 UB
};

mem::zeroed 的返回类型由调用处决定。回退是 () 的时候，它造出来的是一个 ()，这完全健全。回退变成 ! 之后，就变成了造出了一个值不可能存在的类型的值，当场就是未定义行为。代码原封不动，语义却变了。而且编译能通过。

这个风险当年被多认真地对待过，在履历里留着痕迹。never 类型曾在 1.26 中与 TryFrom 一起稳定化，又在 2018 年 4 月被回退（PR #50121），原因就是随之而来的回退语义变化。此后跟踪议题 #58184 提出了一种部分稳定化的思路：不动推断，只稳定类型。最后终究还是得动推断，但在这段时间里，预告用的装置一层层堆了起来。

改动一个默认值所需要的装置

在一门已经稳定的语言里改动默认值，意味着改动已经发布到世界上的代码的语义。Rust 为这件事动用的装置有三样，而且三样都能原样搬到别的语言、别的项目上去。

第一，版次。先在 2024 版次里把回退改成 !。旧的 crate 按旧版次的规则编译，与新的 crate 链接起来毫无问题。不过版次是过渡的通道，不是永久的分岔。如果规则永远随版次而异，语言事实上就变成了好几门，所以最后的目标一直是所有版次统一，而这次的 PR 做的正是这件事。

第二，警告的阶梯。按允许、警告、拒绝的顺序往上抬。在 1.92 里把两条 lint 抬成默认拒绝时，预计约 500 个 crate 会受影响，即便如此也还是留了 #[allow] 这条退路。发布说明把这项举措定性为不是兼容性变更，而是为将来 never 类型的稳定化铺路。在文档里把破坏和预告分开来称呼的态度，就在这里。

第三，crater。这是把整个公开生态实际重新构建一遍的实验。这次 PR 的运行结果是 9,024 项中有 3,277 项回归，其中 1,149 项被判定为无意的噪声，建议重跑。读这些数字时有一点要留意。

  • crater 的回归数不是坏掉的 crate 数，而是需要人去读的清单的长度
  • 同一个原因可能被算成几百项，而且混着基础设施问题带来的噪声
  • 反过来，不在公开仓库里的内部代码根本不会被算进去 — 这一侧其实更要紧
  • 所以 crater 应当被读作抽样调查，而不是安全保证

还有一点。版次指南明确写着，虽然没有自动修复，但对于会被版次变更破坏的代码，有自动检测。cargo fix 不替你改的理由很清楚。正确的修法是由人来决定这里究竟想要哪个类型，而这不是工具能代为决定的那一类事。

这里留下一条通用的教训。默认值就是 API 表面。哪怕文档里没写，哪怕使用者从未明确选择过，人们还是会把代码架在它上面。配置文件的默认值也好，库的默认行为也好，都是一样的。

别的语言是怎么填这个位置的

这个概念的通用名称是底类型（bottom type）。它没有值，位于所有类型的下方。好几门语言都有对应物，而下面这张表不是排名。差别不来自好坏，而来自什么时候引入，以及那时背着怎样的兼容性包袱。

语言名称提供方式查阅的文档
Rust!语言内置类型，外加向所有类型的强制转换。推断回退也由语言规定Reference · RFC 1216
KotlinNothing语言内置。所有类型的子类型。throw 表达式的类型Kotlin 官方文档
ScalaNothing语言内置。所有类型的子类型。表示异常、终止与无限循环Scala 官方导览
TypeScriptnever语言内置。联合类型穷尽之后剩下的东西，用于穷尽性检查TypeScript 手册
PythonNever · NoReturn标准库 typing。给静态检查器看的标注Python typing 文档
HaskellVoid库里的数据类型，外加 absurd 函数Data.Void

把这张表横着读，能看出两条分野。

  • 在库里还是在语言核心里 — Haskell 的 Void 与 Python 的 Never 在库这一侧。嵌进核心，就能影响子类型关系和推断，代价是想改就难了
  • 靠子类型还是靠强制转换 — Kotlin 与 Scala 把它处理成所有类型的子类型。Rust 只在生命周期上用子类型，所以用强制转换取得同样的效果。结果相近，规则住的地方不同
  • 运行时会不会检查 — Python 的 Never 是说给静态检查器听的，解释器并不强制。名字一样，把关的主体却不同

Python 文档一边说明 Never 与 NoReturn 在类型系统里含义相同、静态检查器把两者同等对待，一边把两个名字都留了下来，这一点值得留意。NoReturn 在 3.6.2 进来，Never 在 3.11 进来。不替换名字而是叠加，同样是维护兼容性的一种方式，也正是 Rust 打算把 Infallible 留作别名的理由。

实务中会碰上这个类型的地方

这个类型听着抽象，但在真实代码里露脸的地方相当具体。

用签名说出绝不会失败

标准库里有这样一处实现。

  • impl<T, U: Into<T>> TryFrom<U> for T 的关联类型是 type Error = Infallible;
  • 它一边使用转换可能失败的 TryFrom 接口，一边用类型说出在这种情况下失败变体并不存在这个事实
  • 等到 ! 能写在普通类型位置上，就可以直接写 Result<T, !>，再多造一个专用错误类型的理由也就少了
  • 在读代码的一侧，这个 API 会不会失败，只看签名就定了 — 不必再去翻文档

不会返回的函数

  • 服务器的主循环、进程退出的包装函数、致命错误处理器都是典型
  • 一旦声明为 -> !，编译器就知道调用处之后不可达 — 未初始化诊断与死代码警告的准确度会提高
  • 在 FFI 边界上也会用到。Reference 举了 unsafe extern "C" { pub safe fn no_return_extern_func() -> !; } 这种形式作为例子。这是把 C 那边的不会返回标注搬进 Rust 签名的位置
  • 关于边界本身的讨论，在 试图减少 Rust FFI 中 unsafe 的尝试 - extern fil-c 提案瞄准的位置与付出的代价里另外讲过

把泛型参数钉死为没有

  • 状态机里尚且到不了的状态，不发送事件的通道的消息类型，都是这样的位置
  • 比留一个占位结构体更准确地传达意图 — 占位的东西以后可能被人塞进值，而没有值的类型做不到
  • 不过这种设计在库这一侧价值大，放进应用代码里容易过头

穷尽性检查

  • 在 TypeScript 里，never 被广泛用作确认联合类型是否已被处理干净的惯用写法
  • Rust 本来就强制 match 的穷尽性，所以同一套惯用写法的必要性没那么强 — 这是同一件工具在不同语言里分量不同的例子
  • 在模式里省略空变体的功能不在本次稳定化范围内，仍留在另一个开关后面

可以不知道的人，与知道了划算的时点

老实说，绝大多数代码不会直接用到这个类型。panic! 和 process::exit 照写就是，! 由编译器在背后装上又卸下。写应用代码时亲手敲出 ! 的机会，几个月未必有一次。

如果下面这些条件全部成立，本文的内容忘掉也无妨。

  • 是单个 crate 的应用，不做公开的库
  • 不做把错误类型以泛型形式暴露出去的 API 设计
  • 没有 unsafe 块
  • 用的是最新版次，工具链也一直在跟着升
  • 出了编译错误再读消息去改就行 — 实际上真的可以这样

反过来，如果下面任何一条沾上了边，现在就弄明白反而更省。

  • 在 unsafe 里调用返回类型由调用处决定的函数 — 也就是 mem::zeroed 这一类。这里冒出来的警告不能用 #[allow] 盖过去。编译错误以后再改也行，未定义行为却没有以后。把这条 lint 抬到拒绝等级的理由，正是这个
  • 在做库，并且把错误类型作为泛型参数暴露出去 — 这正是 Infallible 的别名转换可能在别人代码里制造实现冲突的地方
  • 维护着停留在旧版次上的大型代码库 — 从 1.100.0 起，版次边界不再挡着了。现在冒出来的警告，就是那时候的工作量
  • 大量使用宏 — 宏生成的表达式里回退会落到哪里，光看源码是看不出来的
  • 曾被错误消息里冒出来的 ! 弄懵过 — 本文第三、第四节就是答案

类型能当文档的条件与不能的条件

-> ! 是把这个函数不会返回这句话刻进代码里。用类型写下的句子胜过注释，理由只有一个，而这一个是决定性的。编译器会强制这项主张。实现一改，真的返回了，构建当场就停。注释则会悄悄变成谎言。

类型真正尽到文档职责的条件，大体是这样。

  • 编译器会强制它 — 一旦对不上，构建就失败
  • 它会改变调用方代码的形状 — Result<T, !> 干脆让错误处理的代码消失
  • 写法短，而且惯用写法只有一种 — 好几种并存的话，读的人每次都得解释一遍

反过来，类型说不出口的话也很清楚。知道这一侧反而更实用。

  • 它说不出为什么 — -> ! 只说了不会返回这个事实。退出码是多少、会不会留日志、是展开还是直接中止，它一概沉默
  • 它分不出不可能的种类 — 一个没有值的类型，不会告诉你这件事是协议上永远不可能，还是只是尚未实现，抑或只在这套构建配置里没有
  • 没写下来的默认值不是文档 — 回退正是这样的东西。源码里哪儿也没写着 ()，可代码的语义就吊在那上面。整篇文章就是这个案例

所以结论不是把一切都写进类型里。类型强制什么是不可能的，散文留下为什么会这样。这就是 -> ! 旁边至今仍需要一行注释的理由。

没能确认的事

  • 1.100.0 的发布说明还没出。最终的稳定化范围是否与合入时点一致，要等发布时再确认
  • crater 的 3,277 项回归里实际需要修改的 crate 有多少个 — 处在噪声判定与建议重跑的状态，没有确定的数字
  • Infallible 的废弃时点 — 文档只写了最终会废弃
  • 模式里省略空变体（另有开关）的稳定化时间表 — 仍在讨论中，不在本次范围内
  • 1.92 里预计的约 500 个 crate 实际呈现出什么结果的事后统计
  • 内部与非公开代码受影响的规模 — crater 只扫公开仓库，所以结构上就无从得知

小结

缩成三句话就是这样。一个没有任何值的类型，是用类型说出执行不会到达这里的装置。它之所以有用，是因为它会流向任何类型，于是分支的一侧走到头时不必再编造占位值。而它之所以走了十余年，不是因为语法，而是因为改动推断决定不了的位置上的默认值，会动到已经发布出去的代码的语义。

只留三样带走的东西。

  • 默认值就是 API。世界上的代码架在谁也没有明确选过的值上面。想改，就需要版次、警告阶梯、生态实验这样的装置，而造出这些装置所花的时间，正是所谓拖了很久的理由
  • 编译错误与语义变化的分量不同。前者可以以后再改，后者不行。Rust 只把与 unsafe 纠缠的那条 lint 抬到拒绝等级，这个判断把这条分界原样摆了出来
  • 告诉人们大多数人可以不知道，本身也是信息。亲手用到这个类型的机会很少。但只要 unsafe、公开的库、旧版次这三样沾上一样，现在就把警告读掉，会比 11 月再读便宜
