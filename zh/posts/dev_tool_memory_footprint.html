开发工具为什么吃内存 - 语言服务器内存的原理与代价

为了让补全即时响应必须放进内存的东西，以及削减它之后失去的东西

2026年8月23日 开发/基础设施

引言：一行代码都没敲，风扇却在转

编辑器开着，你去倒杯咖啡回来，笔记本已经发烫。再开一个视频会议窗口，刚才还很利落的补全就慢了半拍。切换分支之后，整个编辑器会僵住三十秒左右。这三个场景来自同一个地方：窗口背后运行的语言服务器，正在把整个项目读进去、重新绘制它自己的那张地图。

2026 年 8 月，一个 Rust 的替代语言服务器以内存少用一百倍的标题出现在开发者社区。这篇文章既不是那个工具的介绍，也不是推荐。它要处理的是那个标题触到的真问题：开发工具的内存从哪里长出来，长出来的内存究竟破坏了什么。以及当我们动手去削减它时，悄悄让出去的又是什么。

先把已发布的内容连同可核实的条件简短交代，然后就离开具体工具、回到原理。

1. 发布了什么 - 以及一百倍是什么比什么

引起讨论的项目是一个名为 Rust Glancer 的 Rust 语言服务器实现。项目站点把自己描述为与 rust-analyzer 不同的路线：不是把一切放在内存里动态重算，而是使用冻结的工作区，并且可以把它卸载到文件系统上。以承受一定性能损失换取极致的内存效率与瞬时重启，这是项目自己的总结，开发时间写的是大约四个月。

在照搬标题里的倍数之前，必须先把比较的两端拆开。文档中真正能确认的内容如下。

  • 内存那一侧的数字是目标值。文档写的是在规模合理的项目上以低于 100MB 为目标，而所谓合理规模指的是什么，并没有交代。
  • 比较对象那一侧的数字是作者的轶事：在用同一个编辑器的两份实例同时打开多个项目的状态下，rust-analyzer 占了 16GB。那是整套配置的合计，而不是单个实例的常驻量。
  • 项目公开的并列对比表里没有内存这一列。表里只有索引耗时。
  • 因此一百倍更接近于用 100MB 的目标去除以 16GB 的轶事。把同一个仓库在同一台机器上用两个服务器分别打开、并列测量常驻内存的公开数据并不存在。

公开的时间对比表如下。它始终是索引时间而不是内存，并且带着在两台 MacBook 上测量的条件。

  • MacBook Pro M4 Max 36GB：Glancer 基础 5 秒、完整 8 秒，rust-analyzer 基础 6 秒、完整 13 秒
  • MacBook Pro M1 8GB：Glancer 基础 6 秒、完整 9 秒，rust-analyzer 基础 7 秒、完整 14 秒

代价也写在文档里。新写的 import、结构体与 trait 在保存文档之前不会被索引。输入过程中只对当前函数体做浅层分析并复用之前的索引。需要真正执行构建脚本或过程宏才能得到的信息、以及 nightly 专属特性，都明确标注为暂不支持。这些句子不是缺陷而是信号。倍数只有附上条件才有意义，而要理解条件，就得先知道为什么一开始需要那么多内存。

2. 语言服务器为什么花内存 - 即时性的价格

语言服务器协议的存在，是为了把乘法问题变成除法。与其为 M 种语言和 N 个编辑器的每一种组合分别实现语言支持，不如每种语言配一个服务器，编辑器用标准协议对话。补全、定义跳转、查找引用、重命名、诊断，全都变成服务器这一侧的职责。

这里会产生一个误解：以为吃内存的是源代码。rust-analyzer 的架构文档把这一点写得很清楚：分析器把全部输入数据放在内存里而不做任何 IO，因为输入就是源代码，而源代码顶多也就几十兆字节，全部拿着完全没问题。造出 GB 级占用的不是源代码，而是从源代码里推导出来的那些东西。

放进内存的东西有了它才能做的事没有它会怎样
语法树判断光标所在位置的语法上下文补全退化成字符串匹配
名称解析结果与模块作用域表确定这个标识符指向哪个定义定义跳转与重命名变成猜测
类型推断结果计算点号之后可以接什么方法候选不准确或者干脆为空
符号索引与反向引用索引查找引用、工作区全局搜索每次查询都要重扫整个项目
依赖图判断变更之后要重算哪些部分改一个字符就要全量重新分析
记忆化的中间结果同一个查询不算第二遍每次敲键都在重复同样的工作

最后一行尤其重要。现代语言服务器是增量计算引擎。rust-analyzer 为此使用 Salsa，其设计的核心不变式是在函数体内部输入不会让全局派生数据失效。为了守住这个承诺，它给每个文件单独维护一份与函数体改动无关的摘要结构、把模块作用域索引成另一张表，语法树则只在需要时才解析。

结构切得越细，需要重算的范围就越窄，而这些碎片与碎片的缓存正是内存。这一领域最根本的交易就在这里显形：为了买到快速重算而支付内存。补全能一眨眼就弹出来，说明做出那个答案所需的材料大多早已备在 RAM 里。

3. 精确度与内存的交换 - 本文的核心

全都装进内存，既准又快。问题在于精确度、延迟、内存这三样不可能同时拉满。轻量工具不是变了魔术，而是把三样中的一样放下了，放下的是哪一样决定了这个工具的性格。

3.1 放下的是什么

  • 惰性加载 — 需要时才计算。总内存下降，但第一次查询变慢。只在第一次要等三秒这种现象几乎不会体现在平均响应时间的统计里，而人恰恰记住的就是那三秒。
  • 部分索引 — 工作区精确分析，依赖库只留摘要。在大型仓库上省下的最多，但进入库内部的定义跳转会在某个深度断掉。
  • 磁盘缓存 — 把结果写成文件，需要时再载入。重启速度提升极其明显，代价是需要判断缓存何时过期的规则；规则保守就总在重建，规则松散就会给出错误答案。
  • 快照冻结 — 输入时只看浅层，保存时才跑完整分析。省下的幅度最大，但会出现刚写好的东西还不存在的状态。

3.2 让出去的多半是时间轴

把这四样并排看，共同点就浮出来了。轻量工具真正让出去的往往不是功能清单，而是此刻的精确度。代码在两次保存之间一直在变，索引却停在上一次保存的时刻，这个间隔越大，工具就越是在回答关于过去那份代码的问题。

新定义一个结构体，不保存就切到别的文件敲它的名字，候选里不会出现。因为按下保存就立刻消失，所以也没人会把它报成缺陷。于是这笔成本不会出现在基准测试里，而且体感完全取决于习惯。对每写两三行就保存的人来说几乎不存在，对写一大段之后再保存的人来说是每天都要撞的墙。

3.3 现实的答案是把层次分开

C/C++ 的语言服务器 clangd 所选的结构是这种折中的好例子。它不把索引做成一整块，而是叠几层再呈现为一个。最上面是负责当前正在编辑文件的动态索引，下面是扫描整个项目的后台索引。设计文档说明，得益于这个结构，即使后台索引尚未完成，你正在处理的那些文件的交叉引用也可以使用。

值得学的是原则而不是具体实现。一旦区分出必须保持最新的部分与不必如此的部分，什么该留在内存、什么该放到磁盘就自然分开了。光标所在的文件必须精确到毫秒级的最新，半年没碰过的 vendor 目录则不必。想把所有东西维持在同样的新鲜度时，内存就会炸开。

4. 开发机内存不够时实际发生的事

内存占用数字大本身不会伤到任何人。有害的是这个数字超过可用量之后开始的连锁反应，而它是有顺序的。

  • 回收与换出 — 内核先把用得少的页赶出去。第一个陷阱就在这里。ps 手册把 RSS 定义为未被换出的物理内存，所以内存越紧张，进程的 RSS 反而显得越小。
  • 压缩 — macOS 在换出之前先做内存压缩。Activity Monitor 里的 Compressed 就是为了腾出更多 RAM 而压缩掉的量。被压缩的页每次触碰都要花 CPU，于是内存问题伪装成 CPU 占用率出现。
  • 工作集缩减 — Windows 会从进程的工作集里削掉页面。工作集是虚拟地址空间中当前驻留在物理内存里的那些页，被削掉的页一旦再被触碰就会产生硬缺页，必须从后备存储读回来。这就是一次补全变成一次磁盘读取的那一刻。
  • 工具之间的竞争 — 编辑器本体与扩展宿主、类型检查器、打包器的监视进程、容器运行时，还有开着四十个标签页的浏览器，共用同一块 RAM。它们会互相挤掉对方攒下的页缓存，所以减掉其中一个，另一个往往就变快了。
  • 容器上限 — 开发容器和 CI 里由 cgroup v2 立起围墙。越过 memory.high 时进程会被节流并承受强烈的回收压力，而内核文档明确写着越过 high 这条线并不会触发 OOM killer。只有当 memory.max 已达上限且无法再减少用量时，该组内才会真的触发 OOM killer。
  • 发热与续航 — 压缩、回收、重建索引全都是 CPU 的活。内存问题在笔记本上会被翻译成散热问题，选笔记本时先看内存容量这条建议正是从这里来的。

如果在 CI 里遇到过语言服务器或类型检查器毫无理由地消失，那么有个地方比日志更该先看。cgroup v2 的 memory.events 文件带着 low、high、max、oom、oom_kill 这几个计数器，oom_kill 在涨，案子就算结了。

还有直接度量压力本身的指标。Linux 的 PSI 在系统层面暴露为 /proc/pressure/memory，在 cgroup 层面暴露为 memory.pressure。some 行是至少有一部分任务因该资源而停滞的时间占比，full 行是所有非空闲任务同时停滞的时间占比。full 在上涨，那就不是慢，而是抖动。10 秒、60 秒、300 秒的平均值一起给出，所以瞬时尖峰与持续趋势可以在一屏之内分辨开。

5. 单一大仓库与大型代码库 - 规模不是线性增长

文件翻倍，内存看上去也该翻倍，实际却涨得更陡。原因在数据结构的性质里。

  • 引用关系更接近符号的两两配对。符号数量与文件数成正比，但要让查找引用与安全重命名即时可用，就需要一份谁在用谁的反向索引，而这份索引比文件数长得快。
  • 失效范围会变宽。依赖图越深，改动一个公共类型时需要重算的下游范围就越大。所以仓库越大，越会想把缓存开得更大。
  • 生成代码会插进来。宏展开、代码生成、由 schema 派生的类型都不在源码里。分析对象的真实体量开始与仓库的表面体量脱节。
  • 实例会被乘起来。rust-analyzer 的文档写着一个进程可以服务多个项目，但要是每个项目单开一个编辑器窗口，这个优势就没了，服务器数量也随窗口数增加。第 1 节里的 16GB 轶事正是这种配置。

这个量级上会发生什么，clangd 的设计文档写得很平实：大型项目的后台索引通常要花好几个小时并消耗数 GB 的 RAM。所以 clangd 提供了挂载预先构建好的静态索引这一选项，而远程索引功能正是为了把全局索引带来的巨大内存开销挪到另一台机器上而设计的。

规模的答案由此浮现。仓库超过某个体量之后，在个人机器上靠调优硬撑的阶段就结束了，把索引挪到开发机之外成为剩下的方向。一台索引服务器最终会比给全体成员加内存更便宜，而这笔账在内存价格大幅上涨的行情里又会再度动摇。

6. 怎么量 - 该看哪个数字

关于内存的讨论多半会错位，原因是不同的数字被叫了同一个名字。定义不同，同样的情形就会得出不同的结论。

指标定义在哪里看注意什么
RSS未被换出的、该任务实际用掉的物理内存ps、top、/proc 状态文件换出的部分不计入；共享库会按进程重复计入
VSZ进程的虚拟内存大小，不含设备映射ps是预留而不是使用。映射大文件会让它虚高
PSS该进程在这块映射上的按比例份额smaps、smaps_rollup适合对多进程求和；只看单个进程会低估
Private_Dirty只有该进程持有并且已被修改的页smaps最接近进程退出时真正能收回来的量
Swap本应是匿名内存但已被换到 swap 上的量smaps与 RSS 一起看才能看出真实用量
available无需换出即可启动新程序的内存估计值free真正的余量是这一列而不是 free 列
memory.current该 cgroup 及其子组当前使用的总量cgroup v2在容器与 CI 里这才是基准线

Compressed为腾出更多 RAM 而压缩掉的内存量macOS Activity Monitor这个值大，说明已经处在压力之下

读这些数字是有顺序的，守住顺序就能消掉大部分误诊。

  • 先看系统余量 — Linux 看 available，macOS 看内存压力曲线。这里宽裕的话，某个进程用掉 2GB 不是问题而是设计。
  • 没有余量就分份额 — 用 PSS 的合计看谁占了多少。把 RSS 简单相加会因为共享部分重复而得出超过物理内存的数值。
  • 锁定进程之后 RSS 与 Swap 一起看 — 只看其中一个，在紧张状态下会读得恰好相反。
  • 先找工具自带的度量 — Go 的语言服务器 gopls 在用量超过 1GB 时会自动把内存调试信息写到临时目录，启动调试服务器还能在浏览器里查看性能分析与内存状况。

如果接下来还要把编辑器卡住的时刻与系统日志里的回收记录对齐，那时用到的工具与Linux 日志分析命令那一侧完全重合。

7. 削减的各种做法与各自付出的代价

削减内存的方法早已被整理成好几条路子，没有一条是免费的。每一条都在拿精确度、延迟、运维复杂度中的某一样去换内存。

做法做什么得到什么付出什么
卸载到磁盘把分析结果放成文件，需要时才载入常驻内存下降、重启时间缩短首次访问的延迟、缓存失效规则的复杂度、磁盘写入
保存时索引输入时浅层处理，保存时做完整分析内存与 CPU 的节省幅度最大保存之前的新条目工具看不见
部分索引与惰性索引工作区精确，依赖只留摘要在大型仓库上效果显著进入库内部的探索会在某个深度断掉
紧凑表示驻留化、位打包、字符串池没有精确度损失实现复杂度、每次访问的少量 CPU
进程分离把索引隔离到编辑器之外的进程编辑器变轻、故障不会蔓延进程间通信开销、多一个要管的部件

实务上排顺序的话，最后一行排在最前。范围排除一行配置就完事，通常剔掉的是 node_modules、target 这类本来就不需要分析的东西。其次是进程分离与设定上限。紧凑表示和索引结构改造是造工具那一方的事，不是用工具这一方的选项。

8. 也要诚实地看另一面 - 那些内存买到了什么

如果轻就是无条件更好，那我们现在还在用文本搜索找定义。过去十年开发工具的内存占用上涨，是功能增加的结果而不是谁偷懒的结果。

  • 基于类型的补全 — 不是罗列名字相近的候选，而是只显示在那个位置上真正成立的东西。必须有类型推断结果驻留内存才做得到。
  • 安全的重命名 — 字符串替换会连注释和字面量一起改坏。基于引用图的重命名要有反向索引才成立。
  • 保存前的诊断 — 不跑构建就在输入过程中报错，靠的是增量计算缓存。
  • 结构性导航 — 查找引用、调用层级、查找实现，没有项目级全局索引就根本不存在。
  • 重构自动化 — 提取方法、内联、修改签名，只有同时知道类型与引用才安全。

所以判断标准不是用量的绝对值。只有当你看不出这些内存买到了什么，它才成为问题。在 8GB 内存的机器上占 2GB 的语言服务器等于拿走了半台机器，而在 64GB 的机器上同样的 2GB 是笔好交易。补一句，轻的工具也未必总是更快。缓存持有得少，重复查询就要重算，还要加上从磁盘载入的时间。索引时间、响应时间与内存是各自独立的轴，改善其中一条必然存在让另一条变差的区间。

9. 选工具时真正该看的东西

把宣传话术剥掉之后，剩下的判断材料并不多。下面六条就够了。

  • 看条件而不是倍数 — 哪个仓库、哪台机器、哪套配置下测的。没有条件的倍数不是信息而是印象。
  • 区分目标值与实测值 — 目标 100MB 与实测 100MB 是两句话。文档要是把两者混着写，这本身就是信息。
  • 精确度的边界是否写在文档里 — 肯说明什么东西在什么时候之前不会被索引的项目值得信任，遮着掩着的那一方危险得多。
  • 与自己的工作习惯是否合拍 — 保存时索引的体感，在频繁保存的人与总是拖着的人身上恰好相反。别人的评测不如自己的习惯更能预测结果。
  • 看最坏的时刻而不是平均值 — 首次索引期间、大批量切换分支之后、更新依赖之后的那些尖峰。
  • 有没有退路 — 能否排除索引范围、能否设置内存上限、重启成本是多少。能设上限的工具在糟糕的日子里也能保住机器。

换工具之前，先把共用这块 RAM 的其他东西数一遍通常更快。二十个编辑器扩展、三四个常驻监视进程，还有浏览器。比起换掉语言服务器省下 1GB，从这边掏出 3GB 才是更常见的情况。

  • 把同一个仓库在同一台机器上用两个 Rust 语言服务器分别打开、并列测量常驻内存的公开表格。已公开的并列对比只有索引耗时。
  • 目标值所预设的规模合理的项目究竟指什么。行数、crate 数、依赖数，哪一项都没有给出定义。
  • 关于 rust-analyzer 典型常驻内存的官方数值。其文档的故障排查页面根本没有内存这一项。
  • 实际测量仓库规模与内存增长曲线关系的公开基准。第 5 节中不是线性增长的说法是从数据结构性质推出的论点，不是实测值。
  • macOS Activity Monitor 里按进程显示的内存这一列究竟读的是哪个账本。苹果的支持文档只定义了系统层面的项目。

结论：内存是预算而不是分数

把语言服务器的内存占用当成越低越赢的记分牌来读，判断就会出错。那个数字不是分数而是预算。预算大的工具用这笔钱买了即时性与精确度，预算小的工具则决定其中一部分不买。哪一边更对，取决于机器的内存容量、仓库的体量，以及那个按下保存键的人的个人习惯。

今天能做的有三件。用RSS 与 swap 一起确认现在这个工具到底用了多少；用 available 或内存压力判断系统余量是不是真的不够；如果真不够，就从排除索引范围这种几乎没有代价的做法开始动手。换工具是这之后的选项。

而每当一个新工具带着惊人的倍数出现，问同样的三个问题就好。是什么比什么、在什么条件下测的、作为交换又放弃了什么。三个问题都能在文档里给出答案的项目大体可信，一个都不答的项目，无论数字多大，都还处在没有材料可供判断的状态。
