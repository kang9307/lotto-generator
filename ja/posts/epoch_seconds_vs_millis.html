はじめに - 数字は1つなのに単位は4つある

Unix時刻は、1970-01-01T00:00:00Z(エポック)から経過した時間を整数で数えた値である。Pythonドキュメントはtimeモジュールのエポックをすべてのプラットフォームで1970年1月1日00:00:00(UTC)と書き、MDNはJavaScriptのDateがエポックからのミリ秒を持つと書いている。基準の時点は同じだが、数える単位は秒・ミリ秒・マイクロ秒・ナノ秒に分かれる。そのため同じ整数がファイルとAPIの間を通るときに単位がずれると、日付が1970年の初めや数万年後に飛ぶ。

  • 秒の値をミリ秒として読むと、日付が1970年1月の中に入る。
  • ミリ秒の値を秒として読むと、年が5万年台に行く。
  • 桁数(10・13・16・19桁)で単位を判別する規則は、特定の期間でしか合わない。
  • 32ビット整数は2038年に秒の値を入れられない。

扱う問いは次のとおりである。

  • 同じ値を秒・ミリ秒・マイクロ秒・ナノ秒として読むと、日付はそれぞれどこに行くか。
  • 桁数による判別規則は、どの時刻の範囲で合い、どこで崩れるか。
  • 判別関数を4つのツールで同じ方法で書くと、同じ答えが出るか。
  • Python・Node・PowerShell・dateの現在時刻APIは、それぞれ何桁を返すか。
  • 32ビットの境界と各ツールの表現の限界はどこか。

Excelのシリアル値のように基準日が違う日付の数字はExcelシリアル値の記事が、タイムゾーン規則の変化はタイムゾーンデータの記事が、壁時計と単調時計の区別は単調時計の記事が扱う。この記事はUnixエポック基準の整数の単位だけを見る。

同じ数字を秒とミリ秒として読むと

1700000000(10桁)と1700000000000(13桁)を、4つのツールで秒とミリ秒として読んだ。Pythonはtimezone.utcを指定したfromtimestamp、Nodeはnew DateとtoISOString、PowerShellはDateTimeOffsetのFromUnixTimeSecondsとFromUnixTimeMilliseconds、bashはGNU dateの-d @である。

                    print('ms value read as seconds, year by arithmetic: about', int(1970 + ms / 31556952))

  • 1700000000000を秒として読んだ結果はツールごとに違う。GNU dateは55840-11-08T22:13:20Zを、Nodeは+055840-11-08T22:13:20.000Zを出力した。PythonはOSError: [Errno 22]を、PowerShellはArgumentOutOfRangeExceptionを出した。
  • Pythonドキュメントは、fromtimestampがプラットフォームのC言語ライブラリのlocaltime()またはgmtime()の範囲を超えるとOverflowErrorを、その関数が失敗するとOSErrorを出すことがあり、通常1970〜2038年に制限されると書いている。このWindowsビルドでOSErrorが出たのは、この文と同じ方向である。
  • Microsoft LearnはFromUnixTimeSecondsの有効範囲を-62,135,596,800以上253,402,300,799以下と書き、外れるとArgumentOutOfRangeExceptionだと書いている。出力のメッセージと同じ範囲である。
  • マイクロ秒の値1700000000000000を秒として読むと、NodeではgetTimeがNaNのInvalid Dateになり、toISOStringはRangeErrorを出す。GNU dateは53872825-06-17T22:13:20Zを出力した。

4つの単位を互いに読み替えた全体の表を計算した。同じ瞬間の1700000000秒を各単位で書いた整数が行で、読む単位が列である。

from datetime import datetime, timezone, timedelta
                    EPOCH = datetime(1970, 1, 1, tzinfo=timezone.utc)
                    SCALE = {'s': 1, 'ms': 10**3, 'us': 10**6, 'ns': 10**9}
                    base = 1700000000  # 2023-11-14T22:13:20Z in seconds
                    def read_as(value, unit):
                        sec = value // SCALE[unit]
                        if sec < 253402300800:
                            return (EPOCH + timedelta(seconds=sec)).strftime('%Y-%m-%d %H:%M:%S')
                        return 'year ~%d' % (1970 + value / SCALE[unit] / 31556952)
                    print('%-28s' % 'value (written as)' + ''.join('%-24s' % ('read as ' + u) for u in SCALE))
                    for u, k in SCALE.items():
                        v = base * k
                        print('%-28s' % ('%d (%s)' % (v, u)) + ''.join('%-24s' % read_as(v, r) for r in SCALE))

桁数による判別規則と、その規則が崩れる境界

よくある規則は桁数である。10桁なら秒、13桁ならミリ秒、16桁ならマイクロ秒、19桁ならナノ秒とみなす。この規則が合う時刻の範囲を計算した。各桁数が始まる瞬間である。

判別関数 - 4つのツールで同じ答えが出るか

しきい値の規則を4つのツールで実装し、同じ8個の入力を与えた。入力は0、-1、86400000、1700000000、1700000000123、1700000000123456、1700000000123456789、253402300799である。Nodeは19桁の値を正確に扱うためBigIntを使い、PowerShellはInt64、bashは64ビット算術を使う。

  • 変換結果が1970年1月や5000年以降になったら、まず単位の誤りを疑う。
  • 32ビット整数のカラム・プロトコル・ファイル形式に時刻を入れるときは2038年が限界で、ミリ秒なら25日が限界である。
  • 範囲外の値への反応がツールごとに違うので(OSError、ArgumentOutOfRangeException、Invalid Date)、あるツールで通った値が別のツールで失敗することがある。

確認できなかったこと

  • LinuxとmacOSでのPython fromtimestampの限界。このPCのWindowsビルドでは253402300799でOSErrorが出たが、他のプラットフォームの値は実行できなかった。
  • 32ビットのtime_tを使う実際のシステムの動作。2038年の境界はPythonの整数計算とctypesの変換でのみ示した。
  • うるう秒の影響。Pythonドキュメントはエポックからの秒にうるう秒が含まれないと書くが、うるう秒がある期間の値は実行していない。
  • 地域のタイムゾーンと夏時間。出力はすべてUTCに固定した。
  • Python fromtimestampが3001年以降のどの値からOSErrorを出すかの正確な境界。
  • Java・Go・C#・データベースのタイムスタンプ型の単位と範囲。
  • Windows FILETIMEのようにエポックが1601年の形式と、Excelシリアル値との単位の混同。
  • 小数点付きの秒(float)で表した時刻の精度の損失。
  • PowerShell 5.1以外の.NETでのFromUnixTimeSecondsの範囲。
