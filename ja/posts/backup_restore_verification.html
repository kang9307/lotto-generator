バックアップのダッシュボードが緑なら、たいていその日の仕事は終わったものとして扱われる。ジョブは終了コード 0 で終わり、ファイルは想定どおりの大きさでストレージに上がり、通知も届いた。だがその緑が保証している命題はひとつだけである。ダンププログラムが自分の仕事を終えたということだ。

「復元できる」はそれとは別の命題である。受け取る空のデータベースが要る。そこにスキーマが立たねばならない。データが制約を通って入らねばならない。シーケンスと権限と拡張が所定の場所になければならない。並び順がインデックスの前提と合っていなければならない。そして最後に、アプリケーションがその上で立ち上がらねばならない。この鎖のどの環も、バックアップジョブは検査していない。

二つの命題のあいだの距離は、事故が起きるまで誰も測らない。そして測る方法はひとつしかない。実際に復元してみることである。問題は、「復元してみた」が成立する条件が見た目より厳しい点にある。ここではその条件を層に分けて並べる。

当該プロジェクトの README が記す手順はこうである。バックアップが終わるたび、あるいは時・日・週・月単位や cron 式で決めた周期で、データベースのコンテナを立ち上げ、その中で復元を走らせ、復元後の大きさをバックアップと照合し、すべてのテーブルを行数付きで並べた報告を出す。失敗だけを選んで通知する選択肢もある。

終了コード 0 が観測することと、しないこと

論理バックアップ、つまりダンプは、サーバに問い合わせを投げて結果を SQL 文として書き取る手順である。MySQL 8.4 の分類をそのまま移すと、論理バックアップはサーバが動いている状態で行われ、データベースに属さないログファイルや設定ファイルは含まれない。なにが含まれなかったかは、ダンプファイルのどこにも記録されない。

バックアップジョブが成功したというとき、実際に観測されている信号は三つほどである。プロセスの終了コード、出力ファイルの大きさ、転送の完了。観測されていないのは次のものだ。

  • ダンプの内容がある一時点の一貫した状態を表しているか
  • スキーマとデータが互いに噛み合っているか
  • 対象環境にそのダンプを受け取る前提条件が揃っているか
  • このファイルを開くのに要る鍵が別の場所で生きているか
  • 復元にかかる時間が耐えられる範囲か

五つには共通点がある。いずれもバックアップ時点では値が定まらず、復元時点で初めて値が決まる。バックアップパイプラインの緑がこの五つを代わりに示す方法は、原理的に存在しない。

成功したバックアップが嘘をつく六つの場所

1. ダンプが走っているあいだにスキーマが変わると

MySQL の --single-transaction は、InnoDB のテーブルをロックなしでオンラインで取れるようにするオプションである。ところが文書には条件が付いている。ダンプが走っているあいだ、他の接続が ALTER TABLE・CREATE TABLE・DROP TABLE・RENAME TABLE・TRUNCATE TABLE を使わないことが、正しいダンプファイルの条件だという。一貫読み取りがそれらの文から隔離されないため、ダンプ対象のテーブルにそうした文が当たると、内容を誤って取得するか失敗しうる。

目を留めるべきは「失敗しうる」の反対側である。誤って取得する側は失敗ではない。ダンプは正常終了し、ファイルは構文的に妥当な SQL であり、後で復元してもエラーは出ない。ずれているのは内容だけだ。スキーマ移行の配備時刻と夜間バックアップの枠が重なる組織で、この条件は理論ではない。

PostgreSQL 側は事情が違う。pg_dump は同時利用中でも一貫した結果を作り、文書の表現ではそのダンプはpg_dump が実行を開始した時点のスナップショットを表す。同じ危険を同じ形で被らないという意味であり、二つの系統をひとつの社内手順にまとめてはいけない理由でもある。

2. スキーマだけ、あるいはデータだけ

--schema-only で取ったダンプを復元すると、テーブルがすべて生成され行は 0 になる。エラーは出ない。逆に --data-only で取ったダンプは、空の対象に入れれば受け取るテーブルがなくて失敗し、既にスキーマのある対象に入れれば制約と投入順序で部分的に失敗する。

PostgreSQL の文書はラージオブジェクトがデータとして扱われると明記している。--data-only には含まれ、--schema-only には含まれない。スキーマのダンプとデータのダンプを別々に取って後で合わせる運用では、二つのファイルの時刻がずれると、そのあいだに入った行はどちらにも存在しない。しかもこの欠落は復元ログになんの痕跡も残さない。

3. 既定では含まれないもの

mysqldump では --triggers が既定で有効なので、テーブルを取ればそのテーブルのトリガが付いてくる。一方 --routines と --events は既定で無効であり、明示しなければ含まれない。ストアドプロシージャ、ストアドファンクション、イベントスケジューラの項目がここに当たる。

この既定値が作る欠陥は性質が独特だ。復元時点でまったく表に出ない。テーブルは揃っており行数も合う。ないのは夜間集計のイベントとストアドプロシージャであり、それらはそれぞれの実行時刻が来て初めて不在が知られる。行数の照合を通過する欠陥の最初の例がここで出てくる。以降も繰り返し出てくる。

4. データベースの外にあるもの

pg_dump は一つのデータベースだけを取る。ロールやテーブルスペースのようにクラスタ全体にまたがるオブジェクトは含まれず、そちらは pg_dumpall の担当である。ロールのない対象に復元すると、所有権を立てる文が引っかかる。pg_restore は既定で ALTER OWNER または SET SESSION AUTHORIZATION を出力するが、文書によればこれらの文は最初の接続がスーパーユーザか、全オブジェクトの所有者本人でなければ失敗する。

拡張も性質は同じだ。ダンプが運ぶのは拡張を作れという指示であって、拡張の実装ではない。対象ホストにそのパッケージが入っていなければ、そこで止まる。シーケンスは逆に静かな側である。値は付いてくるが、データだけを別に投入する運用ではシーケンスが遅れたまま復元され、その事実は次の挿入が主キー衝突を起こしたときに初めて知られる。

5. 文字コードと照合順序 - データと一緒には運ばれないもの

ダンプは既定で原本データベースの文字コードで作られる。運ばれるのはバイト列とその文字コード宣言であって、対象サーバの設定ではない。だから対象データベースを作るときの文字コード選択は復元の一部であり、その選択は復元スクリプトではなく対象準備スクリプトに入っているのが常で、そのために持ち主が曖昧になる。

照合順序ははるかに静かだ。PostgreSQL は照合順序オブジェクトを作るとき、その提供元の版をシステムカタログに記録し、使うたびに現在の版と照合して食い違えば警告を出す。文書の説明は率直である。照合順序の定義が変わるとインデックスが壊れるなどの問題につながりうる。データベースが、保存されたオブジェクトが一定の並び順を持つことを前提に動いているからだ。

しかもこれは異常な経路でだけ起きるのではない。文書が挙げる正常な事例が、OS をメジャーバージョンに上げるとき、そしてより新しい ICU でリンクされたサーババイナリへ pg_upgrade するときである。復元先のホストが原本と別のディストリビューションである状況は、災害復旧では例外ではなく既定に近い。

その上に罠がもうひとつ重なる。警告を消す ALTER COLLATION ... REFRESH VERSION は、カタログの版の記録だけを更新する。文書が釘を刺した一文がある。そのコマンドは、影響を受ける全オブジェクトが実際に正しく作り直されたかを検査しない。警告を消すことと、インデックスを直すことは別の作業であり、順序は REINDEX が先だ。

6. 鍵と媒体 - ファイルはあるのに読めない

暗号化したバックアップの復号鍵が、バックアップ元と同じシステムにしかなければ、そのシステムを失う事故でバックアップも一緒に失われる。この欠陥はバックアップ段階では絶対に見えない。暗号化は成功するからだ。見える時点は復元試行の最初の 1 分であり、これはむしろ良いほうに入る。即座に表に出るからだ。

媒体の損傷は逆である。PostgreSQL はデータページごとにチェックサムを載せ、書くときに更新し読むときに検証する。18 からはこれが既定で有効になった。ただし保護の範囲は文書に明記されている。データページだけが保護され、内部のデータ構造や一時ファイルは対象外である。さらに言えば、これは生きているクラスタの話であって、オブジェクトストレージに半年置かれたダンプファイルの話ではない。そちらはストレージ側の整合性機構と、バックアップ成果物そのもののマニフェストが担う。

復元ツールの既定値は「続行」である

表の最後から二番目の行が、最も頻繁に見落とされる場所だ。主要な復元経路のエラー処理の既定値は止まることではなく続けることである。

pg_restore の --exit-on-error の説明文が、その既定値をそのまま書いている。既定は続行し、復元の最後にエラー件数を表示することだ。「表示する」は人が画面を見ているときに成り立つ命題である。スケジューラが終了状態だけを読んでいれば、エラー 40 件の復元と 0 件の復元は同じ信号として届く。

平文ダンプを psql で投入するときも同じだ。文書の表現では、既定で psql のスクリプトは SQL エラーに遭ったあとも実行を続ける。ON_ERROR_STOP 変数を立てるとエラー時に終了コード 3 で抜ける。そして文書が後ろに付けた一文が結論である。どちらにせよ部分的にしか復元されていないデータベースを手にする。違いはその事実を知っているかどうかだけだ。

単一トランザクション復元が検証に向く理由は表の二行目にある。全部成功するかなにも反映されないかなので、判定が二値になる。検証用復元の目的はデータを救うことではなく、真偽をひとつ得ることだからだ。

形式に絡む罠もひとつある。pg_restore は平文形式のダンプを復元できない。カスタム・ディレクトリ・tar のいずれかの形式である必要がある。検証手順を pg_restore 前提で組んでおきながら、実際のバックアップは平文で取っているという組み合わせは、検証が一度も走っていない状態で長く過ごしうる。

復元検証が実際に要求するもの

隔離された対象と、原本に依存しない資源

「復元してみた」が成立するには、復元対象が原本から分離されていなければならない。分離はデータベース名を変える程度では足りない。同じサーバプロセス、同じディスク、同じ資格情報、同じネットワーク経路を使っていれば、その検証は原本が生きているという事実に寄りかかっている。原本が消える状況に備えた手順が原本に依存しているなら、その手順は備えではない。

PostgreSQL の文書が復元先に付けている条件も同じ種類だ。template1 にローカルな追加があるなら、本当に空のデータベースへ復元しなければならず、そのためには template0 を雛形にして作る必要がある。対象が清潔でなければ成功と失敗が混ざり、混ざった結果は判定を作れない。

毎回新しいコンテナを立てて復元する方式が広く使われる理由はここにある。初期状態が常に同じだからだ。ただしコンテナは隔離の一軸にすぎない。そのコンテナが原本と同じホスト、同じストレージ、同じクラウドアカウントの上にあれば、隔離はプロセス水準で止まる。資源隔離の程度は、備えようとしている事故の大きさに合わせて決めるのが筋である。

なにを照合するのか

行数は安価で有用だ。ただし前に見たとおり行数が合っていても素通りする欠陥がいくつもある。ストアドルーチンの欠落、イベントの欠落、シーケンスの遅れ、並び順の食い違いがすべてそうだ。

チェックサムは一段上だが条件が付く。MySQL の CHECKSUM TABLE は、バックアップやロールバックの前後で内容が同じかを確かめるために用意された文である。ところが文書が付けた但し書きが二つある。値がテーブルの行フォーマットに依存するので、行フォーマットが変われば値も変わる。そしてハッシュ関数は衝突しないと保証されていないので、同一でない二つのテーブルが同じ値を出す可能性が残る。文書は、時刻型の格納形式がある版の境界で変わったため、アップグレードしたテーブルのチェックサムが変わりうるという例まで挙げている。

結論は明確だ。版を上げながら復元する検証では、チェックサムの不一致が損傷の証拠とは限らない。同じ版どうしで比べるときにだけ信号になる。だから照合は層に積むほうがよい。

  • 第 1 層 · オブジェクト数 — テーブル・インデックス・シーケンス・拡張・ルーチン・イベント・トリガ。既定値のせいで丸ごと抜けた分類をここで捕らえる。
  • 第 2 層 · テーブル別の行数 — 部分投入と中断された復元を捕らえる。安いので毎回回す。
  • 第 3 層 · 主要テーブルの集計値 — 合計・最大・直近の時刻。行数は同じなのに内容がずれた場合をここで捕らえる。
  • 第 4 層 · アプリケーションが実際に投げるクエリを数本 — 結合と並べ替えを含むものを選ばないと、インデックスと照合順序の問題は表に出ない。

層に分けるのは費用が違うからだ。第 1・2 層は毎回の復元で回せるほど安く、第 4 層はそうではない。なにをどこに置くかは、次節の自動化の境界につながる。

ファイルが開くことと、サービスが生きること

この境界を最も明確に書いているのは、PostgreSQL 自身のバックアップ検証ツールの文書である。pg_verifybackup は pg_basebackup で取ったバックアップを、サーバがバックアップ時に生成したマニフェストと照合して整合性を見る。そして文書はすぐ続けて書く。この道具が行う検証は動作中のサーバがそのバックアップを実際に使おうとするときに行うすべての検査を含まないし、含みようもない。この道具を使ってもなお、試験復元を行い、結果のデータベースが期待どおり動作し正しいデータを含んでいるように見えるかを確かめるべきである。

同じ頁は限界をさらに絞っても書く。この水準の検証はファイルの欠落や内部チェックサムの不一致といった明白な問題を捕らえるには十分だが、復旧を試みるときに起こりうるあらゆる問題を捕らえるほど広くはない。例として挙げられているのは、チェックサムは正しいが意味をなさない動作を指定するログレコードである。形式は正しく意味が誤っている場合が、検証器の死角だという話だ。

もう一歩進めば、試験復元ですら最後の層ではない。データベースが立ち上がることとサービスが立ち上がることのあいだには、スキーマ移行の版、アプリケーションが期待する拡張、接続アカウントの権限、外部ストレージにある添付ファイル、キャッシュにしかなかったセッションといったものが横たわっている。この層を一度も通ったことのない復旧計画は、実際の事故でその層に到達したあとに新しい問題と出会う。復旧可能性が事後の努力ではなく設計の産物であるという話は機器のファームウェア側で先に整理したが、データベースでも変わらない。

目標を数値で立てる - RPO と RTO

この二つの値がなければバックアップ設計は始められない。どの周期が十分か、どの復元速度が要るかを判断する基準がないからだ。定義は NIST SP 800-34 Rev. 1 のものが最も広く引かれる。

用語定義定めるもの定まっていないと
RPO · 目標復旧時点障害後にデータが復旧されなければならない時点バックアップの周期と書き込みログの保管方式周期の議論が技術的な好みの争いで終わる
RTO · 目標復旧時間システムの構成要素が組織の任務や業務プロセスに悪影響を与える前に復旧段階に留まりうる全体の時間バックアップの形式と復元経路の構造復元に数日かかっても規格違反にならない

RPO が 24 時間なら夜間ダンプで足りる。RPO が 5 分ならダンプでは届かず、書き込みログを流し続ける構成が要る。PostgreSQL 側では WAL、MySQL 側ではバイナリログである。MySQL 8.4 はバイナリロギングが既定で有効であり、時点復旧の材料はフルバックアップのあとに生成されたバイナリログのファイル群だ。バックアップが終わるとログを整理してディスクを空ける習慣があると、RPO は書類上の値としてだけ残る。バイナリログを巻き戻せる履歴として使う発想は巻き戻せるデータのタイムマシンを扱った記事で別途整理した。

RTO が定めるのはバックアップの形式である。ここで論理バックアップの代価が表に出る。MySQL の文書は mysqldump について相当量のデータをバックアップするための高速あるいは拡張性のある解法として意図されたものではないと自ら書き、データが大きいと復元が非常に遅くなりうると付け加える。理由も併記されている。SQL 文を再生する作業に、挿入とインデックス作成のためのディスク入出力が伴うからだ。

ここでよくある誤りがある。ダンプファイルの大きさから RTO を推定すると、ほぼ必ず楽観的に外れる。ダンプを取る時間と戻す時間は非対称であり、その非対称の大きさはインデックス構成に左右される。復元時間は推定ではなく測定でしか分からない。

最後に、この二つが定まっていないとなにが起きるかが重要である。「バックアップ周期を何時間にするか」は結論の出ない技術論争だ。「このサービスは何分ぶんの注文を失ってよいか」に移せば、答えを出せる人が決まる。二つの値は技術パラメータではなく業務が引き受けると決めた損失の大きさであり、だからインフラ担当が一人で決められる種類の数字ではない。この性格は小さなチームが Postgres を守る方法を扱うときにも同じ場所で出てくる。

3-2-1 は標準か慣行か

3-2-1 はしばしば規則や標準と呼ばれる。複製 3 つ、媒体 2 種、オフサイト 1 つという構成だ。出典をたどると標準文書ではなく、写真家ピーター・クログの著書『The DAM Book』(オライリー)で整理された経験則に行き着く。広く引用され概ね妥当だが、標準化団体が要求事項として発行した条項ではない。規則より慣行と呼ぶほうが正確である。

標準の側が実際に要求している文はかたちが違う。NIST サイバーセキュリティフレームワーク 2.0 のサブカテゴリ PR.DS-11 は「データのバックアップが作成・保護・維持・試験される」である。付随する実装例には次のような項目がある。

  • 重要なデータはほぼリアルタイムで継続的にバックアップし、その他のデータは合意された日程で頻繁にバックアップする
  • あらゆる種類のデータソースについて少なくとも年 1 回、バックアップと復元を試験する
  • 一部のバックアップはオフラインかつオフサイトに安全に保管し、事故や災害がそれを損なわないようにする
  • バックアップの保管に地理的分離と所在地の制限を適用する

読めば複製の数より試験と隔離が先に来ている。3-2-1 を完璧に守りながら一度も復元してみたことのない組織と、複製は二つだけだが四半期ごとに復元訓練をする組織と、実際の事故でどちらが生き残るかは自明である。数は数えやすいので監査で先に数えられ、試験は数えにくいので後回しになる。その順序が逆さまなのだ。

付け加えると、オフサイトという項目の意味もしばしば狭く読まれる。物理的な距離だけでなく信頼境界が違うかが要点である。同じクラウドアカウントの別リージョンは地理的に離れているが、資格情報ひとつが両方を消す。保管を他者に委ねるときにアクセス権自体を失わない問題はアーカイブのアクセス権とベンダーロックインの側で契約の観点から整理した。

自動化の境界 - 毎回やることと、たまにやること

復元検証で自動化できるものとできないものを分ける基準はひとつだ。基準値がどこにあるか。

項目担い手頻度基準値のある場所
復元がエラーなく終わったか機械毎バックアップ終了状態 · 単一トランザクションの判定
オブジェクト数が前回と同じか機械毎バックアップ直前の成功した復元の値
テーブル別の行数が想定範囲か機械毎バックアップ原本の同時刻の集計
アプリケーションが起動しヘルスチェックに応答するか機械週 1 回以上ヘルスチェックのエンドポイント
復元所要時間の趨勢機械が測定 · 人が判定毎回記録 · 四半期に検討測定は自動 · 閾値は RTO
全体復旧訓練人四半期または半期業務が定めた RTO と RPO
手順書の現行性人構成変更のたび現在の構成と文書の差
担当者不在時の手順人半期組織図と権限委任の規定
保存期間と規制要件の整合人年 1 回契約と法令

機械側の項目の共通点は、基準値がデータの中にあることだ。人の判断なしに真と偽が分かれ、分かれた結果を通知に変えられる。人側の項目の共通点は、基準値が組織の中にあることだ。復旧訓練の所要が 40 分だという事実そのものは真でも偽でもない。それが RTO に収まるかを業務が判定して初めて意味が生じる。

境界に置かれているのが表の五行目である。復元所要時間の趨勢は機械が測るが、その趨勢がいつ危険になるかは人が決める。データが大きくなれば復元時間は必ず伸び、伸びた時間が RTO を超える日はなんの通知もなく来る。復元所要を毎回記録しておくことが安価な理由がこれであり、記録だけ溜まって誰も見ない状態になりやすい理由でもある。集めたが読まれないデータの問題は集めた観測データがなぜ読まれないのかで扱ったものと同じかたちだ。

機械が代われないものを無理に自動化しようとする試みもよくある。検証器が判定できる範囲とできない範囲を分ける一般的な基準は検証ハーネスが引いた境界線の側に整理してある。要旨は同じだ。機械は下限を守る。上限は人が決める。

セルフホスティングの代価 - その道具のバックアップは誰がするのか

バックアップの道具を自分で立てると、問いがひとつ増える。その道具の状態は誰がバックアップするのか。

バックアップの道具は、スケジュール、接続情報、保存方針、ストレージの資格情報、暗号鍵、そして実行履歴を抱えている。この状態を失えば、バックアップファイルが全部残っていても復旧手順の半分が消える。どのファイルがいつのどのデータベースなのか、どの鍵で開くのかがその道具の中にしかなかったなら、なおさらだ。

循環依存はここで生じる。道具が自分の状態を自分のストレージにバックアップし、そのストレージの資格情報が道具の中にしかなければ、円を描くことになる。事故のとき、円は一点が切れただけで全体が止まる。切る方法は特別なものではない。

  • 道具の設定を道具の外に人が読める形式で書き出し、構成管理に置く。コードとして管理されていれば、道具を新しく立てても同じ状態が再現される。
  • 復号鍵はバックアップ成果物と別の信頼境界に置く。同じストレージ、同じアカウント、同じコンテナの中にあれば、ひとつの事故が両方を持っていく。
  • 道具のない状態でバックアップファイルをひとつ開く手順を文書に残し、その手順を一度踏んでみる。ウェブ画面なしで復元できて初めて、その道具は単一障害点でなくなる。
  • バックアップの一覧を道具の外からも読めるようにする。ストレージ側のファイル命名規則とマニフェストがその役を果たす。

この代価はセルフホスティングをやめる根拠ではない。マネージドサービスを使っても問いは消えず提供者に移るだけであり、代わりに契約とアクセス権という別の層の問いが生じる。どちらにせよ、円を切る地点を自分で分かっている必要がある。配備プラットフォームを自分のサーバに載せるときに消える費用と新たに生じる費用の構造はセルフホスティングの配備プラットフォームを扱った記事で同じやり方で分けてある。

読み取りだけで確かめられること

以下はすべて読み取り・検査の系統である。対象を変えたり消したりする命令は入れていない。ホスト・アカウント・スキーマ名はプレースホルダなので、各自の値に置き換えればよい。

バックアップを復元せずに目次だけ見る

# アーカイブの目次。復元せずに、なにが入っているかだけを並べる。
pg_restore --list /PATH/TO/backup.dump

# 物理バックアップを、サーバが生成したマニフェストと照合する。
pg_verifybackup /PATH/TO/basebackup

# ページチェックサムが有効かどうかだけを参照する。
psql -h HOST -U USER -d DBNAME -c 'SHOW data_checksums'

復元先になにが来たかを数える

-- スキーマ別のテーブル数。丸ごと抜けた分類をまず捕らえる。
SELECT table_schema, count(*) AS tables
  FROM information_schema.tables
 WHERE table_schema NOT IN ('pg_catalog', 'information_schema')
 GROUP BY 1 ORDER BY 1;

-- 拡張は作れという指示だけがダンプに入る。対象ホストで実際に立ったかを見る。
SELECT extname, extversion FROM pg_extension ORDER BY 1;

-- シーケンスが遅れたまま復元されると、次の挿入で主キー衝突が起きる。
SELECT schemaname, sequencename, last_value
  FROM pg_sequences ORDER BY 1, 2;

照合順序の版が食い違うオブジェクトを探す

-- PostgreSQL の文書に載っているクエリ。比較演算子だけを != で書いた。
SELECT pg_describe_object(refclassid, refobjid, refobjsubid) AS collation_name,
       pg_describe_object(classid, objid, objsubid)          AS object_name
  FROM pg_depend d
  JOIN pg_collation c
    ON refclassid = 'pg_collation'::regclass AND refobjid = c.oid
 WHERE c.collversion != pg_collation_actual_version(c.oid)
 ORDER BY 1, 2;

MySQL 側で既定値のせいで抜けたものを数える

-- トリガは既定で入るが、ルーチンとイベントは入らない。原本と復元先で別々に数える。
SELECT routine_type, count(*) AS n
  FROM information_schema.routines
 WHERE routine_schema = 'APPDB' GROUP BY routine_type;

SELECT count(*) AS events   FROM information_schema.events
 WHERE event_schema   = 'APPDB';
SELECT count(*) AS triggers FROM information_schema.triggers
 WHERE trigger_schema = 'APPDB';

-- 内容の指紋。値が行フォーマットと版に依存するので、同じ版どうしでだけ比べる。
CHECKSUM TABLE APPDB.ORDERS;

最後の文は読み取り系統だがただではない。大きなテーブルでは全体を走査するので、営業時間帯に原本へ向けて回す性質のものではない。復元先に向けて回すのが筋であり、だからこそ隔離された対象が前節の条件として先に出てきたのである。

確認できなかったこと

  • きっかけとなった道具の復元検証が、大きさとテーブル別行数のほかになにを照合するのかは、README の記述範囲を超えて確認できなかった。制約・インデックス・ルーチンの存在まで見るのか、アプリケーション層の点検を付けられるのかは、ここでは断定しない。
  • 同じリポジトリの GitHub 説明文は PostgreSQL の道具とだけ書き、README は四つの系統を挙げる。どちらが最新の意図なのかは確認できなかった。
  • mysql クライアントがスクリプトを読んでいて SQL エラーに遭ったときの既定の挙動は確定できなかった。オプション文書には続行オプションが「SQL エラーが起きても続ける」とだけ記され、既定値は明示的に記述されていない。逆から推論はできるが、文書の文としては確定できなかった。
  • 3-2-1 を要求事項として発行した標準・政府文書は見つからなかった。広く引かれる出典は著書であり、NIST CSF 2.0 の PR.DS-11 は複製の数ではなく作成・保護・維持・試験を要求している。
  • MariaDB と MongoDB 系統のダンプの既定値は、この記事の根拠に含めていない。PostgreSQL 18 と MySQL 8.4 の公式文書だけを用いた。
  • 復元所要時間の一般的な数値は提示できない。データの大きさ・ハードウェア・インデックス構成に左右されるため、RTO の判断は各自の環境の実測でのみ可能である。
