引言：请求变慢时用具体数值切分瓶颈

当针对特定 API 或 Web 服务的 HTTP 请求出现明显延迟时，工程师面临的首要难题是难以准确定位延迟属于哪一层网络交互。究竟是域名解析消耗了时间，还是跨越中间路由与防火墙的 TCP 三次握手受阻，亦或是 TLS 证书校验与密码套件协商较慢，还是服务端应用程序处理复杂导致等待首字节（TTFB）时间过长，仅凭直觉推测无法得出结论。

终端工具 curl 是以明确数值厘清上述疑问的利器。然而，仅仅运行 curl https://example.com/ 或使用系统的 time 命令封装，只能得到请求往返总耗时这一个笼统的数字。唯有合理搭配 curl 的诊断标志 -w（--write-out）与 -v（--verbose），方能将整体延迟拆解为毫秒级的各个独立阶段。

本文并非罗列参数的手册，而是专注于请求变慢或失败时，如何通过数值准确切分各阶段耗时。我们将剖析格式文件中实际换行符被忽略的内部原理、自增累计时间指标的差值计算公式、Windows Schannel 环境下的日志特征，以及如何在自动化脚本中准确捕获退出码 28、6 和 22。

关于各层网络协议的基础理论，站点其他文章已作详细梳理。关于递归 DNS 缓存层次，请参阅DNS 缓存给我们的启示；关于 TLS 协议协商演进，请参阅在 SSL 中学到的知识如今为何失效；关于 Shell 退出码捕获，请参阅Shell 退出码与 set -e；关于终端 REST 交互工具，请参阅Slumber 终端 HTTP 客户端。

2. 格式文件换行陷阱 - 丢弃实际换行符的 curl

curl 的 -w 选项允许在传输结束后按自定义模板输出指标。当监测指标较多时，官方文档推荐使用 @filename 语法从外部文件读取格式定义。

2.1 使用物理换行时的单行拼接现象

初次编写格式文件时，开发者通常会在每个变量后直接回车换行。以下是实际创建包含 9 行内容的 curl-format.txt 并调用的测试：

printf 'namelookup:    %%{time_namelookup}\nconnect:       %%{time_connect}\n…remote_ip:     %%{remote_ip}\n' > curl-format.txt
cat curl-format.txt
curl -s -o /dev/null -w @curl-format.txt https://example.com/

虽然文件中存在 9 行文本，终端输出却将所有内容压缩成了一行：

namelookup:    %{time_namelookup}
connect:       %{time_connect}
…(文件中共有 9 行)
=== run 1
namelookup:    0.023826connect:       0.150990appconnect:    0.571661pretransfer:   0.571741starttransfer: 0.711580total:         0.734726http_code:     200size_download: 713remote_ip:     172.66.147.243=== run 2

文件中的所有物理换行符均被丢弃，输出内容粘连在一起，导致按行解析的下游逻辑失效。

2.2 必须写入字面量 \n 的源码原因

这一现象源于 curl 本身的代码实现。查阅 curl 8.12.1 源码中 src/tool_paramhlp.c 的 file2string() 函数可以明确其机理。

该函数在读取文件到内存时调用了 memcrlf()。代码注释指出：countcrlf FALSE - return number of bytes from the start that DO NOT include any CR or LF or NULL。换言之，加载格式模板时，curl 会自动跳过文件内的 CR 与 LF 字符。

因此，若要在输出中保留换行，必须在文件内写入反斜杠加字母 n 的字面量字符串 \n。Everything curl 文档中亦有明确说明：You can also output a newline by using \n, a carriage return with \r and a tab space with \t。

修正后的 curl-format2.txt 内容如下：

namelookup:    %{time_namelookup}\n
connect:       %{time_connect}\n
appconnect:    %{time_appconnect}\n
pretransfer:   %{time_pretransfer}\n
starttransfer: %{time_starttransfer}\n
total:         %{time_total}\n
http_code:     %{http_code}\n
size_download: %{size_download}\n
remote_ip:     %{remote_ip}\n

经 od -c 检查，确认文件中物理写入了 \ 和 n 两个字符。

3. -w 时间变量的本质 - 累计数值与差值计算

使用修正后的 curl-format2.txt 对 https://example.com/ 进行了两次测试：

for i in 1 2; do echo "=== run $i"; curl -s -o /dev/null -w @curl-format2.txt https://example.com/; done

输出得到了整齐的分行记录：

=== run 1
namelookup:    0.016839
connect:       0.148093
appconnect:    0.476784
pretransfer:   0.476995
starttransfer: 0.619743
total:         0.619873
http_code:     200
size_download: 713
remote_ip:     172.66.147.243
=== run 2
namelookup:    0.016120
connect:       0.143699
appconnect:    0.463794
pretransfer:   0.463936
starttransfer: 0.600572
total:         0.603125
http_code:     200
size_download: 713
remote_ip:     172.66.147.243

3.1 六个时间指标描绘的请求生命周期

观察各项数值可知，数字自上而下呈现单调递增趋势。run 1 中 namelookup 约为 0.017 秒，connect 约为 0.148 秒，appconnect 约为 0.477 秒，total 约为 0.620 秒。

这说明：curl 的 time_* 变量并非代表某一阶段的独立耗时，而是自请求发起（0.000 秒）至该阶段结束时的「累计时刻」。例如 time_connect 的 0.148093 秒包含此前 DNS 解析的时间，而非单纯的 TCP 建连耗时。

3.2 获取各阶段耗时的差值减法公式

要获取各阶段实际消耗的毫秒数，必须进行相邻累计指标的差值计算。以 run 1 为例换算为毫秒（ms）：

  • DNS 解析耗时: time_namelookup = 16.8 ms (run 2: 16.1 ms)
  • TCP 握手耗时: time_connect - time_namelookup = 148.1 - 16.8 = 131.3 ms (run 2: 127.6 ms)
  • TLS 协商耗时: time_appconnect - time_connect = 476.8 - 148.1 = 328.7 ms (run 2: 320.1 ms)
  • 请求准备耗时: time_pretransfer - time_appconnect = 477.0 - 476.8 = 0.2 ms (run 2: 0.1 ms)
  • 等待服务端响应（TTFB）: time_starttransfer - time_pretransfer = 619.7 - 477.0 = 142.7 ms (run 2: 136.6 ms)
  • 响应体下载传输: time_total - time_starttransfer = 619.87 - 619.74 = 0.1 ms (run 2: 2.6 ms)

在总计约 0.62 秒的耗时中，TLS 握手阶段耗费约 328.7 ms，占比超过一半。在初次实验中，appconnect - connect 三次测量均在 0.30 至 0.42 秒之间，每次都是最长的阶段。该数值为特定环境单次测试所得，并非通用固定指标。

4. 分阶段耗时拆解与瓶颈排查表

通过表格梳理时间差值计算，可迅速将延迟对应到相关技术层。下表结合 run 1 实测值列出各阶段耗时异常时的常见背景原因：

异常偏高阶段 计算公式（累计值差） 本次实测（run 1，单次测量） 出现延迟时应怀疑的背景因素
DNS 解析 namelookup 16.8 ms 本地解析器缓存失效、上游 DNS 服务器拥塞或丢包
TCP 握手 connect - namelookup 131.3 ms 物理网络距离（RTT）、中间防火墙过滤延迟、SYN 包重传
TLS 握手 appconnect - connect 328.7 ms 大体积证书链校验、多轮往返密码套件协商、OCSP 查询挂起
服务处理响应 starttransfer - pretransfer 142.7 ms 服务端业务逻辑与数据库慢查询、反向代理缓存未命中
响应体下载 total - starttransfer 0.1 ms (713 B) 响应数据包体积过大、网络出口带宽饱和、TCP 接收窗口限制

通过这套公式，可将总计 620ms 的请求清晰拆分为「DNS 17ms、TCP 131ms、TLS 329ms、服务端首字节等待 143ms」（本环境单次测量），为运维与开发协同提供明确数据支撑。

5. -v 详细日志解读与 Schannel 环境的局限

除 -w 提供的量化数据外，-v（--verbose）展示了底层协议交互的详细文本。

5.1 依据前缀符号（*、>、<、{）梳理交互

运行 curl -v -o /dev/null https://example.com/ 2>&1 输出的关键日志如下（已省略进度条；原输出中没有 Cookie 或跟踪头）：

行首符号定义明确：

  • *: curl 内部诊断信息（DNS 解析、IP 选取、连接状态与 SSL 初始化）
  • >: 客户端发送至服务端的 HTTP 请求头
  • <: 服务端返回的 HTTP 响应头
  • {: 接收到的数据量（本输出中为 { [725 bytes data]）

5.2 --trace-time 时间戳与阶段边界解析

附加 --trace-time 后的带时间戳日志：

07:43:32.016000 * Host example.com:443 was resolved.
07:43:32.018000 * IPv6: (none)
07:43:32.018000 * IPv4: 172.66.147.243, 104.20.23.154
07:43:32.018000 *   Trying 172.66.147.243:443...
07:43:32.146000 * schannel: disabled automatic use of client certificate
07:43:32.450000 * Connected to example.com (172.66.147.243) port 443
07:43:32.450000 * using HTTP/1.x
07:43:32.450000 > GET / HTTP/1.1

此处反映出两个特点。首先，秒后小数部分末尾均为 000，表明 Windows 构建版本的时间分辨率仅到毫秒级。

其次，注意 Connected to 的打印时机。TCP 尝试发起于 .018，Schannel 日志输出于 .146，而 Connected to 打印在 TLS 基本就绪的 .450。由此看来，在该 Schannel 构建中，连接日志是在 TLS 结束后才输出的。因此，不应仅凭详细日志行距估算阶段，使用 -w 的 time_connect 与 time_appconnect 才能获得准确边界。

此外，该 Windows Schannel 版本在 -v 下未输出协商的密码套件和证书过期详情，即使指定 --trace-config tls,dns 亦无额外输出，Linux、macOS 上常用的 OpenSSL 构建的 -v 输出未在本环境中确认，只需注意不同构建的输出可能不同。

6. 两种超时机制（--connect-timeout vs -m）与退出码

在脚本自动化中合理控制超时是防止进程假死的关键。curl 提供了限定建连耗时的 --connect-timeout 与限定全局周期的 -m（--max-time）。

6.1 仅约束建连过程的 --connect-timeout

对无响应的私有 IP 10.255.255.1 施加 --connect-timeout 2：

time curl -sS --connect-timeout 2 -o /dev/null http://10.255.255.1/; echo "exit=$?"
curl: (28) Connection timed out after 2011 milliseconds
real	0m2.122s
exit=28

历时 2.011 秒后建连中断，返回退出码 28。该参数仅限制建连阶段，一旦 TCP 握手完成便不再干预后续传输。

6.2 约束全程的 -m (--max-time) 及其优先级

而 -m 约束全程耗时。测试二者同时传入时的优先级表现：

curl -sS --connect-timeout 5 -m 0.2 -o /dev/null https://example.com/; echo "exit=$?"
curl: (28) Connection timed out after 204 milliseconds
exit=28

即使建连超时预设为 5 秒，较短的 -m 0.2 仍在 204 毫秒时率先动作。当 -m 短于 --connect-timeout 时，即使处于建连期亦由 -m 优先终止。

同为退出码 28，报错文本随中断阶段而不同：

  • 建连未成时超时：curl: (28) Connection timed out after 204 milliseconds
  • 建连后等待数据时超时（-m 0.5）：curl: (28) Operation timed out after 514 milliseconds with 0 bytes received（此时 http_code 为 000）

若将限额放宽至 -m 0.58（足以覆盖 0.578 秒传输），则正常返回退出码 0 与 HTTP 200。

7. 脚本集成实践：-sS、-f 与 JSON 结构化输出

在自动化部署或巡检中，默认行为极易掩盖真实的异常。

7.1 保留错误的 -sS 与拦截异常状态的 -f

查询不存在的域名 nonexistent.invalid：

curl -sS -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl -s  -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl: (6) Could not resolve host: nonexistent.invalid
exit=6
=== -s alone hides error
exit=6

单独使用 -s 会抹去错误信息。脚本中务必使用 -sS（--silent --show-error），在关闭进度条的同时保留 stderr 报错。域名解析失败返回退出码 6。

更为隐蔽的是 HTTP 404 等服务端响应：

curl -s  -o /dev/null -w '%{http_code}\n' https://example.com/no-such-page; echo "exit(no -f)=$?"
curl -sf -o /dev/null https://example.com/no-such-page; echo "exit(-f)=$?"
404
exit(no -f)=0
exit(-f)=22

本次实验中收到 404 时，未带 -f 的 curl 仍返回退出码 0。只有附加 -f（--fail），才能在遇到 HTTP 400 及以上响应时抛出退出码 22。仅检查响应头可用 -I，追踪重定向需搭配 -L。

实测验证的退出码速查表如下：

测试场景 调用参数 退出码 实际输出的错误提示
连接无响应的私有 IP --connect-timeout 2 28 Connection timed out after 2011 milliseconds
握手阶段全局超时生效 -m 0.2 28 Connection timed out after 204 milliseconds
响应等待阶段全局超时生效 -m 0.5 28 Operation timed out after 514 milliseconds with 0 bytes received
域名无法解析 -sS（仅用 -s 时无文字，退出码仍为 6） 6 Could not resolve host: nonexistent.invalid
收到 HTTP 404 响应 未指定 -f 0 （无报错，视为传输成功正常结束）
收到 HTTP 404 响应 指定 -f 22 —（被 -s 隐藏，无输出）

7.2 curl 8.12 的 %{json} 与 %{header_json} 实战

无需管理外部文件即可直接获取结构化数据时，可以使用在 curl 8.12.1 中确认可用的 JSON 导出：

curl -s -o /dev/null -w '%{json}' https://example.com/ | python -c "…输出键数量与部分键…"
curl -s -o /dev/null -w '%{header_json}' https://example.com/ | head -c 120

解析确认输出了 67 个属性键：

keys: 67
http_code = 200
time_namelookup = 0.016632
time_connect = 0.144654
time_appconnect = 0.431361
time_starttransfer = 0.568338
time_total = 0.568422
remote_ip = 172.66.147.243
http_version = 1.1
scheme = https
exitcode = 0
errormsg = None
curl_version = libcurl/8.12.1 Schannel zlib/1.3.1 brotli/1.1.0 zstd/1.5.6 libidn2/2.3.7 libpsl/0.21.5 libssh2/1.11.1
=== -w %{header_json} support
{"date":["Mon, 28 Sep 2026 22:43:41 GMT"],
"content-type":["text/html; charset=utf-8"],
"transfer-encoding":["chunked"

-w '%{json}' 集中导出了耗时、exitcode 与 remote_ip，便于 Python 或 jq 直接处理，%{header_json} 也以 JSON 形式输出了响应头（仅确认前 120 字节）。

常见场景推荐标志组合如下：

诊断场景目标 推荐参数搭配 预期收益与分析优势 使用时的关键注意事项
各阶段延迟毫秒级分析 -s -o /dev/null -w @curl-format2.txt 拆解 DNS、TCP、TLS 与首字节耗时 格式文件中换行符必须使用字面量 \n
交互式通信过程追踪 -sv --trace-time -o /dev/null 带时间戳记录首部传输全过程 该 Schannel 构建未输出 TLS 详细行（OpenSSL 构建未验证）
健壮的脚本自动化调用 -sS -f --connect-timeout 3 -m 10 建连与总耗时分离，400 及以上返回退出码 22（依文档，已用 404 实测） 缺少 -f 时 404 响应仍将以 exit 0 退出

未能确认的事项

本指南以实机命令执行与官方规范为准，但受当前测试环境所限，以下内容未直接验证：

  • OpenSSL 构建下的 TLS 详细日志: 本次验证仅基于使用 Schannel 后端的 curl 8.12.1（x86_64-w64-mingw32 构建）。Linux 或 macOS 上常见的 OpenSSL 构建在 -v 下如何输出 TLS 相关行，未能在当前环境中确认。
  • libcurl 官方手册中 time_* 的定义原文: 尽管查阅了 Everything curl 及命令手册，但未能确认 libcurl C API 的 CURLINFO_* 原文定义，文中所述减法计算基于实验 2 的累计实测归纳得出。
  • HTTP/2 多路复用时的累计耗时行为: 由于测试使用的 curl 构建未启用 HTTP/2（回退至 using HTTP/1.x），单连接多流请求时的指标记录特性未作测量。

# curl 诊断标志与延迟阶段拆解 - 实战速查表

验证环境: Windows 10 Pro 10.0.19045, curl 8.12.1 (Schannel), Git Bash, Python 3.13.3.
表中数值与信息均在本环境实际运行确认（耗时为单次测量）。第 4 节的第 3 条命令为示例，该组合本身未实际运行。

---

## 1. 瓶颈阶段判定 — 通过差值计算

curl 的 `time_*` 变量均为自请求发起起的**累计时刻**。各阶段耗时需通过与上一阶段累计值相减得出。

| 异常耗时阶段 | 计算公式（累计值之差） | 本机实测值（单次） | 延迟时优先排查方向（通用背景） |
|---|---|---|---|
| DNS 解析 | `time_namelookup` | 16.8 ms | 本地缓存失效、递归解析器响应过慢 |
| TCP 建连 | `time_connect - time_namelookup` | 131.3 ms | 网络往返时间（RTT）、防火墙过滤或丢包 |
| TLS 握手 | `time_appconnect - time_connect` | 328.7 ms | 证书链校验耗时、密码套件协商往返（占比最大） |
| 服务端响应等待（TTFB） | `time_starttransfer - time_pretransfer` | 142.7 ms | 业务计算负载、数据库慢查询、反向代理穿透 |
| 响应体传输 | `time_total - time_starttransfer` | 0.1 ms (713 B) | 响应数据包体积、出口网络带宽限制 |

## 2. 退出码实测速查表

| 测试场景 | 指定选项 | 退出码 | 实际返回的错误信息 |
|---|---|---|---|
| 连接无响应的私有 IP | `--connect-timeout 2` | 28 | `Connection timed out after 2011 milliseconds` |
| 握手阶段全局超时生效 | `-m 0.2` | 28 | `Connection timed out after 204 milliseconds` |
| 响应等待阶段全局超时生效 | `-m 0.5` | 28 | `Operation timed out after 514 milliseconds with 0 bytes received` |
| 域名无法解析 | `-sS`（仅用 `-s` 时无文字，退出码仍为 6） | 6 | `Could not resolve host: nonexistent.invalid` |
| 接收到 HTTP 404 响应 | （无，未指定 `-f`） | 0 | （无报错，视为传输成功正常退出） |
| 接收到 HTTP 404 响应 | `-f` (`--fail`) | 22 | —（被 `-s` 隐藏，无输出） |

## 3. 实战排查清单

- [ ] **格式文件换行符陷阱**: 格式文件（`@curl-format.txt`）内部必须写入字面量 `\n`，而非物理回车换行（物理换行会被 curl 内部的 `file2string()` 自动忽略）。
- [ ] **脚本基础参数**: 脚本自动化中务必使用 `-sS`（`--silent --show-error`），在关闭进度条的同时保留 stderr 报错。
- [ ] **捕获 HTTP 状态异常**: 未指定 `-f`（`--fail`）时，404 响应仍返回了退出码 0（文档：`-f` 在 400 及以上返回 22），必须添加 `-f` 或检查 `%{http_code}`。
- [ ] **超时优先级判断**: 同时指定 `--connect-timeout` 与 `-m` 时，若 `-m` 更短，即使在建连期间也由 `-m` 先终止。
- [ ] **Schannel 构建特性**: 本环境的 Schannel 构建（curl 8.12.1，x86_64-w64-mingw32）的 `-v` 不输出 TLS 版本、密码套件与证书详情，评估 TLS 耗时应使用 `-w` 的 `time_appconnect`。
- [ ] **协议特性核对**: 各平台构建特性不同，排查前应先执行 `curl -V` 确认 HTTP2 等特性的支持情况。

## 4. 推荐诊断模板

### 毫秒级耗时格式文件 (`curl-format.txt`)
```text
namelookup:    %{time_namelookup}\n
connect:       %{time_connect}\n
appconnect:    %{time_appconnect}\n
pretransfer:   %{time_pretransfer}\n
starttransfer: %{time_starttransfer}\n
total:         %{time_total}\n
http_code:     %{http_code}\n
size_download: %{size_download}\n
remote_ip:     %{remote_ip}\n
```

### 命令示例
```bash
# 1. 精确获取分阶段耗时（毫秒级）
curl -s -o /dev/null -w @curl-format.txt https://example.com/

# 2. 导出完整 JSON 统计（已在 curl 8.12.1 中确认）
curl -s -o /dev/null -w '%{json}' https://example.com/

# 3. 健壮的脚本调用示例（3 与 10 为示例值，该组合本身未实际运行）
curl -sS -f --connect-timeout 3 -m 10 -o output.dat https://example.com/
```

复制后可直接粘贴到笔记应用或 AI 工具中。
