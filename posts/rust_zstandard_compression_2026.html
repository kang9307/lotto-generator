서론: 압축 라이브러리를 Rust로 다시 쓰는 이유

2026년 6월 초 GeekNews(news.hada.io)에서 화제가 된 Rust로 구현한 Zstandard 발표는 Trifecta Tech Foundation이 2026-06-01 공개한 「Announcing Zstandard in Rust」입니다. 대상 프로젝트는 libzstd-rs-sys로, zstd 레퍼런스 C 구현을 c2rust로 Rust로 옮긴 뒤 코드를 정리해 가는 방식입니다. 이미 수년째 C로 잘 동작하는 압축 라이브러리를 굳이 다시 쓰는 이 작업은 언어 취향의 문제가 아니라, 신뢰할 수 없는 외부 입력을 파싱하는 시스템 소프트웨어가 메모리 안전 언어로 옮겨 가는 큰 흐름의 한 장면입니다.

압축 라이브러리는 우리 눈에 잘 띄지 않지만 거의 모든 시스템의 뒤편에서 동작합니다. 웹 서버가 응답을 압축할 때, 데이터베이스가 디스크에 데이터를 쓸 때, 컨테이너 레지스트리가 이미지를 전송할 때, 백업 도구가 파일을 아카이브할 때 모두 압축 코덱이 호출됩니다. 그리고 이 코덱들은 대부분 네트워크나 파일로 받은, 통제할 수 없는 데이터를 해제합니다. 해제 과정에서 메모리 버그가 하나라도 있으면 공격자는 악의적으로 조작한 압축 파일 하나로 서버를 장악할 수 있습니다.

이 글은 (1) Zstandard가 무엇인지, (2) 왜 하필 Rust인지, (3) C 압축 라이브러리의 취약점 역사, (4) Rust 재구현의 5가지 이점, (5) gzip·lz4·zstd·brotli 비교, (6) zstd가 인기 있는 이유, (7) Rust 생태계의 세 갈래 구현, (8) Rust vs C 성능, (9) 5가지 실무 시나리오, (10) 한국 개발 환경 적용, (11) 결론과 즉시 적용 3가지를 다룹니다. 크레이트 버전·구현 상태·벤치마크 수치는 2026-09-29 기준 각 프로젝트의 저장소·crates.io·README와 대조했습니다.

1. Zstandard란 - zstd 압축 알고리즘 개요

Zstandard(줄여서 zstd)는 Facebook, 현재의 Meta가 개발해 2016년에 공개한 범용 무손실 압축 알고리즘입니다. 레퍼런스 구현 저장소는 github.com/facebook/zstd이고, 라이선스는 BSD 또는 GPLv2 중 하나를 고르는 이중 라이선스입니다. 포맷은 안정화되어 RFC 8878로 문서화되어 있고, 2026-09-29 기준 레퍼런스 구현의 최신 릴리스는 v1.5.7(2025-02-19)입니다. README는 zstd를 「zlib 수준 이상의 압축률에서 실시간 압축 시나리오를 겨냥한 빠른 무손실 압축 알고리즘」이라고 소개합니다.

zstd가 다른 알고리즘과 구별되는 특징은 세 가지입니다. 첫째, 압축 레벨의 폭입니다. Rust zstd 크레이트 문서 기준 일반 레벨은 1~22이고, --fast=#로 지정하는 음수 레벨은 압축률을 내주고 압축·해제 속도를 더 끌어올립니다. 레벨을 올리면 압축 속도를 내주고 압축률을 얻는데, README에 따르면 해제 속도는 어느 설정에서나 거의 같습니다. 둘째, 사전(dictionary) 학습입니다. README는 작은 데이터일수록 압축이 어렵다는 점을 짚고, 샘플로 학습한 사전을 쓰면 작은 데이터의 압축률이 극적으로 좋아진다고 설명합니다. 셋째, 스트리밍 API가 깔끔해서 대용량 파일을 메모리에 다 올리지 않고 처리할 수 있습니다.

내부적으로 zstd는 Huff0과 FSE(Finite State Entropy)로 이루어진 빠른 엔트로피 단계 위에 LZ77 계열의 매칭을 얹은 구조입니다. 깊은 이론까지 들어가지 않아도 강조할 점은 zstd가 2020년대 압축의 사실상 표준이 되었다는 사실입니다. Linux 커널, RocksDB, Parquet, ZFS, btrfs, 그리고 여러 패키지 매니저가 zstd를 채택했습니다.

2. 왜 Rust로 재구현하나 - 메모리 안전성의 가치

잘 동작하는 C 라이브러리를 굳이 Rust로 다시 쓰는 이유는 단 하나로 압축됩니다. 메모리 안전성입니다.

C와 C++은 강력하고 빠르지만, 메모리를 수동으로 관리합니다. 포인터 산술, 수동 할당·해제, 경계 검사 부재는 곧 버퍼 오버플로, use-after-free, double free, 정수 오버플로로 이어집니다. 이들은 단순한 버그가 아니라 보안 취약점입니다. 마이크로소프트와 구글이 공개한 통계에 따르면 자사 보안 취약점의 약 70%가 메모리 안전 문제에서 비롯됩니다.

Rust는 소유권(ownership)과 빌림 검사(borrow checker)로 이 문제를 컴파일 시점에 검사합니다. 가비지 컬렉터 없이, 런타임 오버헤드 없이 안전한 코드의 메모리 접근을 정적으로 검증합니다. 그래서 zstd 같은 코덱을 안전한 Rust로 다시 쓰면 "신뢰할 수 없는 입력을 파싱하다 메모리 손상이 일어나는" 부류의 CVE를 구조적으로 줄일 수 있습니다. 단, 이 효과는 unsafe 블록 밖의 코드에만 해당합니다. c2rust로 옮긴 코드는 unsafe로 가득한 상태에서 출발하므로, 재구현의 실제 가치는 그 unsafe를 얼마나 걷어 냈느냐로 판가름 납니다(7절).

핵심 - 압축 라이브러리는 거의 항상 "외부에서 받은 통제 불가능한 데이터"를 해제합니다. 이 지점이 바로 메모리 안전 언어가 가장 큰 가치를 발휘하는 영역입니다.

3. C 구현의 위험 - 압축 라이브러리의 보안 취약점 역사

추상적인 위험이 아닙니다. 압축 라이브러리는 실제로 심각한 문제를 반복해 왔습니다. 대표적인 유형을 정리합니다.

3-1) zlib와 압축 해제 폭탄

가장 널리 쓰이는 zlib는 수십 년간 다듬어졌지만, 그 위에서 동작하는 수많은 래퍼와 파서에서 압축 해제 관련 취약점이 끊임없이 발견됐습니다. "압축 폭탄(zip bomb)"처럼 작은 압축 파일이 해제 시 거대한 메모리를 차지하게 만드는 공격은 지금도 유효하고, 이것은 메모리 안전 언어로도 막히지 않습니다. 순수 Rust 디코더 ruzstd도 README에서 해제 결과가 매우 커질 수 있으니 프레임 크기를 확인하거나 스트리밍으로 받으라고 권하고, 0.9.0 소스에서는 창(window) 크기 상한을 기본 100MB(1024×1024×100바이트)로 두어 그보다 큰 창을 선언한 프레임을 거부합니다. 이 상한은 할당을 묶는 장치이지 해제 결과 전체의 크기 제한은 아니므로, 출력 크기 제한은 호출하는 쪽이 따로 걸어야 합니다.

3-2) 정수 오버플로와 힙 손상

압축 포맷은 길이·오프셋 필드를 다룹니다. C에서 이 값을 검증 없이 곱하거나 더하면 정수 오버플로가 발생하고, 그 결과로 힙 버퍼가 잘못된 크기로 할당되어 힙 손상으로 이어집니다. 압축 코덱 류에서 반복적으로 보고된 전형적 패턴입니다.

3-3) XZ Utils 백도어 사건(2024)

2024년 발견된 XZ Utils(liblzma) 백도어 사건은 압축 라이브러리가 공급망 공격의 표적이 될 수 있음을 충격적으로 보여줬습니다. 이것은 메모리 안전과 다른 차원의 문제(공급망·신뢰)이지만, 압축 라이브러리가 시스템 깊숙이 박혀 있어 한 번 뚫리면 피해가 광범위하다는 점을 모두에게 각인시켰습니다.

결론은 이것입니다. 압축 코덱은 "잘 동작하니 건드리지 말자"의 영역이 아니라, 가장 우선적으로 메모리 안전성을 확보해야 하는 보안 핵심 컴포넌트입니다. Rust 재구현은 이 인식의 자연스러운 귀결입니다.

4. Rust 재구현의 5가지 이점

압축 라이브러리를 Rust로 재구현했을 때의 다섯 가지 실질적 이점입니다.

4-1) 메모리 안전

가장 큰 이점입니다. 안전한 Rust 코드에서는 버퍼 오버플로·use-after-free·double free를 컴파일러가 막습니다. 다만 이 이점은 Rust로 썼다는 사실만으로 생기지 않습니다. libzstd-rs-sys README는 2026-09-29 기준 인코더를 「대부분 c2rust가 옮긴 그대로라 unsafe 코드로 가득하다」고 스스로 적고 있습니다. unsafe를 얼마나 줄였는지가 곧 안전성의 크기입니다.

4-2) 안전한 동시성

Rust의 소유권 모델은 데이터 레이스를 컴파일 시점에 막습니다. 압축은 블록 단위 병렬화가 자연스러운 작업인데, Rust에서는 rayon 같은 라이브러리로 안전하게 멀티 스레드 압축을 구현하기 쉽습니다.

4-3) 통합 용이성

Rust 크레이트는 cargo 한 줄로 의존성을 추가합니다. Trifecta 발표문은 현재의 zstd 크레이트가 C 코드를 소스에서 컴파일하므로 C 툴체인이 필요하다는 점을 짚고, 순수 Rust 구현이면 그 요구가 사라져 Windows와 WebAssembly 같은 환경에서 편해진다고 설명합니다.

4-4) 유지보수성

Rust의 강한 타입 시스템과 패턴 매칭은 압축 포맷 파서처럼 상태가 복잡한 코드를 더 안전하고 읽기 쉽게 만듭니다. 컴파일러가 잡아주는 영역이 넓어 리팩터링 부담이 줄어듭니다.

4-5) 신뢰

위 네 가지가 합쳐져 결국 신뢰가 됩니다. "이 라이브러리는 악의적 입력을 받아도 메모리 손상이 없다"는 주장을 뒷받침할 근거가 쌓이면, 보안이 중요한 인프라에서 채택 결정이 빨라집니다. libzstd-rs-sys가 레퍼런스 구현의 테스트 모음에 더해 퍼징과 Miri 검사를 쓰는 것도 이 신뢰를 쌓는 과정입니다.

5. 압축 알고리즘 비교 - gzip / lz4 / zstd / brotli

주요 압축 알고리즘 네 가지를 한 표로 정리합니다. 왼쪽 세 열은 각 알고리즘의 높은 레벨까지 포함한 일반적 경향이고, 오른쪽 열은 facebook/zstd README 벤치마크 표(Core i7-9700K, Ubuntu 24.04, lzbench, Silesia 코퍼스)에서 가져온 가장 빠른 설정끼리의 수치입니다(압축률 · 압축 속도 · 해제 속도).

알고리즘압축률속도적합 용도README 표 (빠른 설정)
gzip보통보통범용, 레거시 호환zlib 1.3.1 -1: 2.743 · 105 MB/s · 390 MB/s
lz4낮음매우 빠름실시간 처리lz4 1.10.0: 2.101 · 675 MB/s · 3850 MB/s
zstd높음빠름균형 (대세)zstd 1.5.7 -1: 2.896 · 510 MB/s · 1550 MB/s
brotli매우 높음느림웹 정적 자원brotli 1.1.0 -1: 2.883 · 290 MB/s · 425 MB/s

선택 기준은 단순합니다. 특별한 이유가 없으면 zstd를 기본값으로 두고, 극단적 속도가 필요하면 lz4, 한 번 압축해 여러 번 전송하는 웹 정적 자원은 brotli, 오래된 시스템과의 호환이 필요하면 gzip입니다. 네 알고리즘 중 어느 하나가 모든 상황에서 최고는 아니며, zstd의 강점은 "가장 넓은 영역에서 무난하게 1등"이라는 균형감입니다. 같은 README 표에서 zstd의 음수 레벨 --fast=4는 2.146 · 665 MB/s · 2050 MB/s로, 압축 속도는 lz4에 가깝고 해제 속도는 lz4에 못 미칩니다.

6. Zstandard가 인기 있는 이유 - 속도와 압축률 균형

zstd가 짧은 시간에 사실상 표준이 된 이유를 정리합니다.

6-1) 균형감

5절 표에서 보듯 가장 빠른 설정끼리 비교해도 zstd -1은 zlib -1보다 압축률이 높고(2.896 대 2.743) 압축은 약 5배, 해제는 약 4배 빠르며, lz4보다 압축률이 한참 높습니다. 대부분의 워크로드는 "압축률도 속도도 적당히 좋아야" 하는데, zstd가 정확히 그 자리를 차지합니다.

6-2) 레벨 튜닝의 자유

레벨 하나로 실시간(레벨 1~3 또는 음수 레벨)부터 아카이브(레벨 19~22)까지 한 도구로 커버됩니다. 운영 중에 레벨만 바꿔 속도·용량 트레이드오프를 조정할 수 있고, 해제 속도가 레벨과 거의 무관하다는 점이 가장 실용적인 강점입니다.

6-3) 사전 학습

작은 메시지를 대량으로 압축하는 환경(예: 마이크로서비스 간 JSON 메시지, IoT 센서 데이터)에서 사전 학습의 효과가 큽니다. ruzstd README에 실린 측정에서는 github-users 샘플(7,484,607바이트, zstd README 설명으로 약 1KB 레코드 약 1만 개)을 사전 없이 압축하면 원본의 34.99%가 되고, 공식 구현이 만든 사전을 쓰면 그 결과의 16.16% 크기까지 줄었습니다. zstd README는 사전이 데이터 종류마다 따로 있어야 효과가 크고, 이득은 주로 처음 몇 KB에서 난다고 설명합니다.

6-4) 생태계 채택

Linux 커널(initramfs·모듈 압축), ZFS·btrfs 파일시스템, RocksDB·Parquet, Arch·Fedora 패키지 매니저, 여러 컨테이너 레지스트리가 zstd를 기본 또는 선택지로 채택했습니다. 채택이 채택을 부르는 선순환이 자리 잡았습니다.

7. Rust 생태계에서의 활용

Rust에서 zstd를 쓰는 길은 2026-09-29 기준 세 갈래입니다. C 레퍼런스 구현에 대한 바인딩, 처음부터 새로 쓴 순수 Rust 구현, 그리고 C 코드를 Rust로 옮겨 정리해 가는 구현입니다.

7-1) 발표의 실체 - libzstd-rs-sys

Trifecta Tech Foundation의 libzstd-rs-sys는 레퍼런스 구현을 c2rust로 옮긴 뒤 정리하는 방식입니다. 발표 시점(2026-06-01)의 버전은 v0.0.1-prerelease.2이고, 해제(decompression)와 사전 생성기는 정리를 마쳤으며 압축 쪽은 정리 작업 대부분이 남아 있다고 밝혔습니다. 해제 작업은 Chainguard·Astral·NLnet Foundation이, 사전 생성기는 Sovereign Tech Agency가 지원했고, 압축 부분은 자금을 찾는 중입니다. 2026-09-29 기준 README는 현재 상태를 이렇게 적습니다. 디코더는 정리가 상당히 진행되어 대부분 안전하고, 사전 생성기는 인코더를 부르는 곳에 unsafe가 남아 있으며, 인코더는 동작하지만 대부분 c2rust 번역 그대로입니다. 디코더는 「실험적 사용은 가능하지만 아직 실전 검증을 거치지 않았다」는 단계입니다.

쓰는 방식도 일반 크레이트와 다릅니다. README가 제시하는 주된 사용법은 C 프로젝트에 링크하는 정적 라이브러리로 빌드하는 것이고(cargo build --features=export-symbols -p libzstd-rs-sys --release --lib), Rust에서 편하게 쓰도록 zstd 크레이트(zstd-rs)에 연결하는 것은 앞으로의 목표입니다. 발표문은 libzstd-rs-sys를 쓰는 자체 포크를 두고 있다고 밝혔지만, 2026-09-04에 나온 zstd 0.14.0의 기능 플래그 목록에는 이 구현을 백엔드로 고르는 항목이 없습니다. 2026-09-29 기준 GitHub 릴리스와 crates.io 최신 버전은 여전히 0.0.1-prerelease.2이고, 저장소는 같은 날에도 변경이 올라오는 활성 상태이며 라이선스는 BSD-3-Clause입니다.

이름 혼동 주의 - 「zstd-rs」라는 저장소 이름이 둘입니다. gyscos/zstd-rs는 C 바인딩 크레이트 zstd의 저장소이고, KillingSpark/zstd-rs는 순수 Rust 크레이트 ruzstd의 저장소입니다. 이번 발표의 Rust 구현은 이 둘과 다른 세 번째 프로젝트(libzstd-rs-sys)입니다. cargo add zstd로 받는 것은 Rust 재구현이 아니라 C 바인딩입니다.

7-2) cargo 의존성 추가

가장 널리 쓰이는 zstd 크레이트는 C 레퍼런스 구현에 대한 바인딩으로, 2026-09-29 기준 최신 0.14.0(2026-09-04)이며 같은 날 나온 zstd-sys 2.1.0+zstd.1.5.7은 버전 이름에 C 라이브러리 1.5.7을 표기합니다. crates.io 메타데이터상 라이선스 표기는 0.13.3의 MIT에서 0.14.0의 BSD-3-Clause로 바뀌었습니다. 순수 Rust 구현 ruzstd는 최신 0.9.0(2026-07-26, MIT, 최소 Rust 1.87)입니다. README에 따르면 해제는 표준 전체를 구현했고, 압축은 쓸 수 있지만 속도·압축률·설정 폭이 원본에 미치지 못합니다. 0.9.0 소스에서 구현된 압축 레벨은 Uncompressed와 Fastest(레벨 1 수준)뿐이고, Default·Better·Best는 「UNIMPLEMENTED」로 표시되어 있습니다.

[dependencies]
# C 바인딩(가장 성숙한 선택, 2026-09-29 기준 0.14.0)
zstd = "0.14"

# 또는 순수 Rust 구현(해제는 완전, 압축은 Fastest 레벨까지)
# ruzstd = "0.9"

7-3) 기본 압축·해제 코드

아래 코드는 zstd 0.14.0 소스의 encode_all(source, level)과 Decoder::new(reader) 시그니처에 맞춘 것입니다.

use std::io::Read;

fn main() -> std::io::Result<()> {
    let data = b"Hello, Zstandard in Rust! ".repeat(1000);

    // 압축 (레벨 3 = 균형, 19+ = 아카이브)
    let compressed = zstd::encode_all(&data[..], 3)?;
    println!("원본 {} bytes -> 압축 {} bytes", data.len(), compressed.len());

    // 해제
    let mut decompressed = Vec::new();
    zstd::Decoder::new(&compressed[..])?.read_to_end(&mut decompressed)?;
    assert_eq!(data, decompressed);
    Ok(())
}

같은 일을 순수 Rust ruzstd 0.9.0으로 하면 다음과 같습니다. 함수 이름은 README와 소스의 compress_to_vec·StreamingDecoder를 그대로 썼습니다.

use ruzstd::decoding::StreamingDecoder;
use ruzstd::encoding::{compress_to_vec, CompressionLevel};
use ruzstd::io::Read;

fn main() {
    let data = b"Hello, pure-Rust zstd! ".repeat(1000);

    // 압축: 0.9.0에서 구현된 레벨은 Uncompressed와 Fastest뿐
    let compressed = compress_to_vec(&data[..], CompressionLevel::Fastest);

    // 해제
    let mut decoder = StreamingDecoder::new(&compressed[..]).unwrap();
    let mut out = Vec::new();
    decoder.read_to_end(&mut out).unwrap();
    assert_eq!(data, out);
}

7-4) 시스템 프로그래밍에서의 위치

Rust로 작성된 스토리지 엔진, 로그 수집기, 네트워크 프록시는 zstd를 흔히 압축 방식으로 씁니다. 순수 Rust 디코더가 성숙하면 FFI 경계(C 바인딩) 없이 해제 경로 전체를 메모리 안전하게 유지할 수 있다는 점이 가장 큰 매력입니다.

8. 성능 - Rust vs C 구현 트레이드오프

가장 자주 나오는 질문은 "Rust 재구현이 C보다 느리지 않냐"입니다. 답은 구현 방식에 따라 크게 갈립니다.

8-1) 이론상 천장은 같다

Rust는 LLVM 백엔드로 C/C++과 동급의 네이티브 코드를 생성합니다. 가비지 컬렉터가 없고 런타임 오버헤드가 없으므로 이론적 성능 천장은 C와 동일합니다.

8-2) 실제 격차는 구현 방식에 달렸다

C 레퍼런스 구현은 수년간 극한까지 최적화되어 있습니다. 그 코드를 옮겨 정리하는 libzstd-rs-sys는 발표문 기준 해제 성능이 기본 설정에서 C보다 몇 퍼센트 느리고, 실험적 기능 플래그 unsafe-performance-experimental을 켜면 C와 같은 성능을 낸다고 밝혔습니다. 플래그 이름 그대로 unsafe를 쓰는 실험 기능입니다. 반면 처음부터 새로 쓴 ruzstd는 README 기준으로 enwik9.zst 해제에서 C보다 약 3.5배, 압축이 덜 되는 데이터(Ubuntu 설치 iso 같은)에서는 약 1.4배 느립니다(time 유틸리티로 측정). 격차는 언어가 아니라 최적화에 쏟은 시간과 설계 방식에서 나옵니다.

8-3) 격차를 좁히는 수단

Rust에서도 core::arch intrinsics로 SIMD를 쓸 수 있고, 안전한 병렬화로 멀티코어 이득을 얻기 쉽습니다. libzstd-rs-sys는 성능을 공개 벤치마크 페이지(trifectatechfoundation.github.io/libzstd-rs-sys-bench)로 추적하고 있어, 격차의 변화를 직접 확인할 수 있습니다.

주의 - 위 수치는 각 프로젝트가 자기 조건에서 잰 값이고, 워크로드·레벨·데이터에 따라 크게 달라집니다. 단일 벤치마크 숫자를 절대화하지 말고, 실제 데이터로 직접 측정하십시오.

결론은 이렇습니다. 몇 퍼센트 수준의 성능 트레이드오프라면 "악의적 입력에도 메모리 손상이 없다"는 보안 가치로 충분히 상쇄됩니다. 다만 배수 단위로 느린 구현이라면 이 교환이 성립하는지 워크로드별로 따져 봐야 합니다.

9. 실무 활용 시나리오 5가지

zstd 적용이 정당화되는 다섯 가지 시나리오입니다.

9-1) 로그 수집·저장

로그는 양이 많고 반복 패턴이 강해 압축률이 잘 나옵니다. zstd는 압축률이 좋아 스토리지 비용을 줄이고, 해제가 빨라 로그 검색·분석 시 지연이 작습니다. Elasticsearch·Loki 같은 도구가 zstd를 지원합니다.

9-2) 백업·아카이브

장기 보관 백업은 압축률이 곧 비용입니다. zstd의 높은 레벨(19~22)은 압축 속도를 내주는 대신 압축률을 끌어올리고, 해제 속도는 레벨과 거의 무관하게 유지됩니다. 복원 시간이 짧다는 점이 아카이브에서 특히 중요합니다.

9-3) 네트워크 전송

API 응답·메시지 큐·스트리밍에서 낮은 레벨(1~3)의 zstd는 실시간성을 유지하면서 대역폭을 절약합니다. 사전 학습을 결합하면 작은 JSON 메시지의 압축률이 크게 좋아집니다.

9-4) 스토리지·데이터베이스

RocksDB, Parquet, ClickHouse, ZFS, btrfs가 zstd를 기본 또는 권장 압축으로 채택합니다. 디스크 I/O가 병목인 환경에서 압축은 사실상 성능 향상 수단입니다 - 읽고 쓸 바이트가 줄기 때문입니다.

9-5) 컨테이너 이미지·패키지

컨테이너 레지스트리와 패키지 매니저(Arch·Fedora 등)는 zstd로 전송 시간과 저장 공간을 동시에 줄입니다. 이미지 풀 속도가 빨라져 배포 파이프라인 전체가 가벼워집니다.

10. 한국 개발 환경 적용

한국 개발자 관점에서 zstd와 Rust 재구현이 갖는 의미를 정리합니다.

10-1) 비용 절감 효과

국내 클라우드(네이버 클라우드, KT 클라우드)와 AWS·GCP 한국 리전 모두 스토리지·전송 비용이 무시할 수 없습니다. 로그·백업·DB 압축을 gzip에서 zstd로 바꾸면 스토리지 사용량과 전송량이 줄어 비용 절감으로 이어질 수 있습니다. 절감 폭은 데이터마다 다르므로 실제 데이터로 먼저 재 보십시오.

10-2) 보안 규제 대응

금융·공공 부문은 보안 요구가 강합니다. "신뢰할 수 없는 입력을 파싱해도 메모리 손상이 없다"는 근거는 보안 심사·취약점 점검 부담이 큰 한국 환경에서 설득력 있는 채택 근거가 됩니다. 다만 심사 자료에는 쓰려는 구현의 unsafe 정리 상태와 릴리스 단계(예: libzstd-rs-sys는 2026-09-29 기준 사전 릴리스)를 함께 적어야 과장이 되지 않습니다.

10-3) 점진적 도입 전략

한 번에 전부 바꾸지 말고, 신규 로그 파이프라인이나 신규 백업 작업부터 zstd로 시작하는 점진적 도입이 무난합니다. 기존 gzip 자산은 호환성 때문에 유지하되, 새로 만드는 부분에 zstd를 기본값으로 두면 위험을 낮추면서 이득을 쌓을 수 있습니다.

11. 결론 + 즉시 적용 가능한 3가지

Rust로 구현한 Zstandard를 한 문장으로 요약하면 이것입니다. "균형감 좋은 표준 압축 zstd에, 메모리 안전이라는 보안 가치를 더해 가는 진행 중인 진화"입니다. 바로 적용할 수 있는 세 가지 패턴입니다.

11-1) 즉시 적용 1: 신규 압축은 zstd를 기본값으로

새로 만드는 로그·백업·전송 경로는 특별한 이유가 없으면 zstd 레벨 3(균형)을 기본값으로 두십시오. README 벤치마크 표에서 가장 빠른 설정끼리 비교해도 zlib보다 빠르고 더 잘 압축됩니다.

11-2) 즉시 적용 2: 데이터별 최적 레벨을 측정으로 결정

실시간 경로는 레벨 1~3(또는 음수 레벨), 아카이브는 레벨 19~22로 시작하되, 실제 데이터로 압축률·속도를 측정해 최적점을 잡으십시오. 반복되는 작은 메시지라면 사전 학습을 반드시 시험해 보십시오.

11-3) 즉시 적용 3: Rust 프로젝트는 메모리 안전 디코더를 우선 검토

Rust로 신뢰할 수 없는 입력을 해제한다면, 표준 전체를 구현한 순수 Rust 디코더 ruzstd를 우선 검토해 FFI 경계를 줄이십시오. 해제 속도가 중요하면 C 바인딩(zstd 크레이트)을 쓰되, 인터페이스를 추상화해 두면 libzstd-rs-sys가 정식 릴리스되거나 zstd 크레이트에 연결될 때 옮기기 쉽습니다. 압축 쪽은 2026-09-29 기준 순수 Rust 선택지가 아직 좁으므로(ruzstd는 Fastest 레벨까지) C 바인딩이 현실적입니다.

마지막으로 강조할 메시지는 이것입니다. 압축은 "보이지 않는 비용 절감 지렛대"이자 "보이지 않는 보안 표면"입니다. zstd는 비용 절감 지렛대를 가장 균형 있게 제공하고, Rust 재구현은 그 보안 표면을 줄여 가는 중입니다. 2026년 신규 시스템 설계자라면 이 조합은 한 번쯤 진지하게 평가할 가치가 있습니다.

# Rust에서 zstd 고르기 - 구현 선택표와 도입 점검표

기준일: 2026-09-29. 버전·상태는 각 프로젝트의 저장소·crates.io·README 기준이다.

---

## 1. Rust용 zstd 구현 세 갈래

| 크레이트 | 저장소 | 방식 | 버전(기준일) | 해제 | 압축 | 라이선스 |
|---|---|---|---|---|---|---|
| `zstd` | gyscos/zstd-rs | C 레퍼런스 구현 바인딩 | 0.14.0 (2026-09-04) | 완전 | 레벨 1~22 | BSD-3-Clause (0.13.3까지 MIT) |
| `ruzstd` | KillingSpark/zstd-rs | 처음부터 새로 쓴 순수 Rust | 0.9.0 (2026-07-26) | 표준 전체 구현 | `Uncompressed`·`Fastest`만 | MIT |
| `libzstd-rs-sys` | trifectatechfoundation/libzstd-rs-sys | C 코드를 c2rust로 옮겨 정리 | 0.0.1-prerelease.2 (2026-06-01) | 대부분 안전, 실험적 사용 단계 | 동작하지만 대부분 unsafe | BSD-3-Clause |

- 「zstd-rs」라는 저장소 이름이 둘이다. `cargo add zstd` 는 C 바인딩을 설치한다.
- `libzstd-rs-sys` 의 주된 사용법은 C 프로젝트에 링크하는 정적 라이브러리다. `zstd` 0.14.0 에는 이것을 백엔드로 고르는 기능 플래그가 없다.

---

## 2. 무엇을 쓸까 - 결정표

| 상황 | 권하는 선택 | 이유 |
|---|---|---|
| 신뢰할 수 없는 입력을 해제, FFI 경계를 줄이고 싶다 | `ruzstd` | 해제는 표준 전체 구현, 순수 Rust |
| 해제 속도가 중요하다 | `zstd` | ruzstd 해제는 README 기준 C보다 약 1.4~3.5배 느림 |
| 레벨 3 이상으로 압축해야 한다 | `zstd` | ruzstd 는 `Default`·`Better`·`Best` 미구현 |
| C 프로젝트에서 C 라이브러리를 Rust 구현으로 바꿔 보고 싶다 | `libzstd-rs-sys`(실험) | 정적 라이브러리 빌드가 주된 사용법, 사전 릴리스 |
| 나중에 구현을 바꿀 가능성이 있다 | 어느 쪽이든 인터페이스를 추상화 | libzstd-rs-sys 정식 릴리스·zstd 크레이트 연결 대비 |

---

## 3. 도입 전 점검표

- [ ] 쓰려는 크레이트의 저장소 URL이 기대한 프로젝트인가 (crates.io 페이지의 repository 확인)
- [ ] 버전을 기준일 이후 다시 확인했는가 (`zstd` 0.14, `ruzstd` 0.9)
- [ ] 해제 결과 크기에 상한을 걸었는가 (메모리 안전 언어로도 압축 폭탄은 막히지 않는다)
- [ ] ruzstd 를 쓴다면 창 크기 기본 상한 100MB 를 알고 있는가 (이를 높이면 큰 할당 위험이 돌아온다)
- [ ] 레벨을 실제 데이터로 측정해 정했는가 (실시간 1~3 또는 음수 레벨, 아카이브 19~22)
- [ ] 작은 메시지가 많다면 데이터 종류별 사전을 시험했는가
- [ ] 보안 심사 자료에 구현의 unsafe 정리 상태와 릴리스 단계를 적었는가
- [ ] 성능 수치를 인용할 때 측정 조건(프로젝트·데이터·설정)을 함께 적었는가
