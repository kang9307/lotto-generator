TypeScript 7.0 RC — Goネイティブコンパイラで10倍高速化、Project Corsaを徹底分析

ビルド78秒を7.5秒に変えたProject Corsaの選択と、JSツーリングのネイティブ化が意味するもの

2026-06-25 IT・技術

はじめに: コンパイラが自分の言語を捨てた

2026年6月18日、MicrosoftはTypeScript 7.0 RCを発表した。単なるバージョンアップではない。TypeScriptコンパイラは、これまで自分自身がTypeScriptで記述されたセルフホスト型コードベースだったが、Goへと移植された。コードネームProject Corsaと呼ばれてきたこの作業は約1年かけて進められ、RC段階でnpmから即インストールできる形で公開された。

見出しの数値は「多くの場合、約10倍高速なビルド」だ。VS Codeコードベース(約150万行のTypeScript)のビルド時間が約78秒から約7.5秒に短縮された。言語サーバーではコマンド失敗がTypeScript 6.0比で20倍以上減少した。数字だけ見ると宣伝文句のように聞こえるかもしれないが、どんな構造的選択がその数字を生み出したか、そしてTypeScriptユーザーとJS生態系全体にとって何を意味するかこそが興味深い問いだ。2026年6月時点の公式発表事実を基に、過大解釈なく分析する。

1. 移植と再作成の違い — 重要な区別

Microsoftはこの作業を正確に表現している。「ゼロから書き直したのではなく、既存の実装から方法論的に移植した(methodically ported from our existing implementation rather than rewritten from scratch)」。この区別は意味論的な細かい話ではない。

1.1 移植が保証するもの

再作成とは設計判断、アルゴリズム、データ構造をゼロから再定義することだ。移植は異なる。既存のTypeScriptコードベースをファイル単位でGoコードに置き換えながら、同じアルゴリズムとデータ構造を維持した。公式発表によれば、型チェックロジックはTypeScript 6.0と構造的に同一だ。核心的な互換性保証として、TypeScript 6.0でstableTypeOrderingを有効にし廃止済みフラグなしでクリーンにコンパイルされるコードは、7.0でも同一にコンパイルされるべきとされている。

これは信頼性を先に確保するアプローチだ。再作成では微妙な型推論の差異が生じる可能性がある。移植は、10年以上蓄積されたテストスイートを使って新旧コンパイラを並列実行することで動作等価性を検証できる。MicrosoftはBloomberg、Canva、Figma、Google、Slack、Vercelなどの外部企業がプレリリース版をテストしたと報告した。

1.2 Goコードベースの現状

現在GoコードベースはTypeScriptコンパイラ全体の約85%を占める。RCでは、以前のプレビュー段階で使われていた別実行ファイル名tsgoは使わなくなった。通常のTypeScriptパッケージとしてインストールし、tscをそのまま実行すれば良い。

2. なぜGoか — RustでもC++でもない理由

言語の選択は単純な好みではない。Microsoftが公開している理由を分析すると、3つの構造的根拠が見えてくる。

2.1 既存コードベース構造との整合性

最も実用的な理由だ。Goのプログラミングモデルが既存のTypeScriptコードベース構造に近く、論理を保存しながら移植するのに適していた。「Goが好きだから」という感情的選択ではなく、移植方式を採用した場合に実装の忠実度を保ちやすい言語がGoだったという技術的判断だ。

2.2 AST走査とグラフ操作

コンパイラの核心は抽象構文木(AST)を走査して型情報を伝播する作業だ。Goは複雑なツリーとグラフを走査するのに人間工学的なサポートを提供する。Rustはオーナーシップモデルにより木の再帰走査が大幅に煩雑になる。C++は細かい制御が可能だが、この規模の移植作業では生産性コストが大きい。Goは「JITオーバーヘッドを完全に排除できるほど速く」かつ「大規模コードベースを方法論的に移植できるほど人間工学的」という交差点にある。

2.3 共有メモリ並列性

これがJavaScriptが構造的に持てない優位点だ。Goは共有メモリ並列性(shared memory parallelism)をネイティブにサポートする。TypeScript 7.0はデフォルト4つの型チェックワーカーで並列検査をサポートし、--checkersフラグでその数を調整できる。モノレポ環境では--buildersフラグでプロジェクト単位の並列ビルドも可能だ。JavaScriptランタイムは構造上この共有メモリ並列性を持てない。Goはこれをネイティブにサポートするという点で、JSランタイムとは根本的に異なる出発点にある。

3. 10倍性能の実際の体感 — ビルドとエディタ

数値は数値だ。重要なのはその数値がどのような文脈で出たか、どう解釈すべきかだ。

3.1 ビルド速度

公式発表の数値: VS Codeコードベース(約150万行TypeScript)ビルド時間が約78秒から約7.5秒に短縮。Microsoftの公式表現は「多くの場合、約10倍高速(often about 10 times faster)」だ。「多くの場合」という言葉に注目してほしい。10倍は保証された下限ではなく、大規模コードベースで観測された範囲の代表値だ。

ファイル監視(--watch)モードも再実装された。ParcelバンドラーのC++ファイルウォッチャーをGoに移植して使用する。以前のNode.jsベースのウォッチャーは一部の設定でポーリングを使用したり、OS APIのプラットフォーム差異による不安定性があった。新しいウォッチャーは「大幅なリソース改善」と安定したクロスプラットフォームサポートを提供するとされる。

3.2 エディタ応答性

言語サーバー(LSP)面でのコマンド失敗がTypeScript 6.0比20倍以上減少した。エディタ体験はビルド速度と異なる次元で影響を与える。ビルド速度はCIパイプラインとデプロイ待ち時間に直結する。エディタ応答性は開発者がコードを書いている瞬間の体験を変える。自動補完、型エラー表示、リファクタリング提案が目に見えて速くなれば、開発フロー自体が変わる。大規模モノレポでVS Codeが遅い原因の多くがTypeScript言語サーバーの負荷だったことを考えると、この改善の実用的価値は大きい。

3.3 コードベース規模に比例する恩恵

小さなプロジェクト(数千行規模)なら既にビルドが数秒で終わっており、10倍改善が体感上意味を持たない場合もある。しかし数十万〜数百万行規模の大型プロジェクト、そして複数パッケージで構成されるモノレポでは差が顕著になる。78秒のビルドを7.5秒に短縮することは、CIが待つ時間の問題ではなく、開発者がフィードバックを受けるまでのループ全体が変わる問題だ。

4. 何が変わり、何が変わらないか — 互換性と主な変更点

4.1 型システムは同一

繰り返しになるが、これが核心的な保証だ。型チェックロジックはTypeScript 6.0と構造的に同一だ。新しい型演算子や言語構文の追加はなく、既存の型システムをより速い実行環境に移したものだ。

4.2 デフォルト値の変更とハードエラー

TypeScript 7.0はTypeScript 6.0の新しいデフォルト値を採用し、6.0で廃止予定とされたフラグや構文に対する警告をエラーに格上げする。エラーになる主な項目は以下の通りだ。

  • target: es5 — ES5ダウンコンパイルのサポート終了
  • moduleResolution: node / node10
  • module: amd, umd, systemjs, none
  • baseUrl(代わりにpathsを使用)
  • esModuleInterop: false, allowSyntheticDefaultImports: false

新しいデフォルト値はstrict: true、module: esnext、target: current(現行安定ECMAScript)、noUncheckedSideEffectImports: true、stableTypeOrdering: trueなどだ。特にstableTypeOrderingは無効化不可であることに注意が必要だ。

4.3 RCで未対応: プログラマティックAPI

安定したプログラマティックAPIはTypeScript 7.0 RCに含まれておらず、TypeScript 7.1で提供予定だ。TypeScriptをライブラリとして呼び出すビルドツールプラグイン、カスタムトランスフォーマー、特殊な言語サーバー統合は7.0で互換性の問題が生じる可能性がある。ツールチェーンにこれらの依存がある場合、事前に確認が必要だ。

5. マイグレーション経路 — 段階的アプローチ

5.1 TypeScript 6.0が前提条件

TypeScript 6.0は7.0への橋渡しとして意図的に設計された。6.0は7.0でエラーになる機能に対して事前に警告を表示する。6.0で警告なしにビルドされる状態をまず確保すれば、7.0へのアップグレード時の想定外エラーを大幅に減らせる。

5.2 並列比較テスト

typescript@npm:@typescript/typescript6でTypeScript 6.0をインストールしてtsc6バイナリを維持しながら、TypeScript 7.0 RC(npm install -D typescript@rc)と並べてCIで実行し結果を比較できる。2つのコンパイラを並列実行してアップグレード前に動作差異を把握するのが推奨パターンだ。

5.3 並列ワーカーの活用

--checkers 8のようにワーカー数を増やすことで、マルチコア環境での型チェック並列性を高められる。大規模モノレポなら--buildersフラグでプロジェクト単位の並列ビルドも試す価値がある。ただし、ワーカーが多ければ必ず速くなるわけではなく、I/Oボトルネックや依存順序によって最適値が異なる。

6. 生態系への影響 — JSツーリングのネイティブ化の流れ

6.1 esbuild、SWC、Bunの先例

esbuild(Go)、SWC(Rust)、Bun(Zig/C++)はすでにネイティブコンパイル型ツーリングがJavaScript実装ツールを大幅に上回れることを示した。esbuildはwebpack相当のバンドルをミリ秒単位で実現し、SWCはNext.jsなどでBabelを置き換えた。この流れの共通認識は「JavaScriptでJavaScriptツールを作ることに構造的な限界がある」というものだ。

6.2 TypeScript 7.0がこの流れに持つ意味

esbuildとSWCがビルドパイプラインをネイティブ化した一方で、TypeScript型チェック自体はJavaScriptベースのままだった。TypeScript 7.0がその最後のギャップを埋める。型チェッカー自体がネイティブになる。これはビルド速度を超えた意味を持つ。TypeScriptの型情報を消費するすべてのツール — エディタ、リンター、コードレビュー自動化、リファクタリングエンジン — がこの変化の下流にある。長期的には、型チェストのコストが下がることで、より野心的な静的解析、より精密なリファクタリング、よりインテリジェントなIDE機能が実現可能になる。

6.3 生態系の適応課題

楽観的になりすぎてはいけない。TypeScript生態系にはTypeScript APIに直接依存するツールが多くある。ts-jest、ts-node、TypeScript ESLintプラグイン、社内コード生成パイプラインなどだ。TypeScript 7.1でプログラマティックAPIが安定化するまで、これらのツールは7.0を完全サポートしにくい。この依存がある複雑なツールチェーンは移行ウィンドウが長くなることを見込んでおく必要がある。

7. 私の見解 — この変化をどう読むか

7.1 10倍はゴールではなく結果だ

Microsoftが「10倍の速度達成」を目標に設定してGoを選んだのではない。移植方式で型システムの等価性を保証しながらネイティブ並列実行を可能にする最善の選択がGoだったという判断であり、10倍はその選択の結果だ。この区別はなぜRustでもC++でもなくGoを選んだかを理解する上で重要だ。速さよりも移植の忠実度と開発生産性が先行する制約だった。

7.2 型チェストコストが下がることで何が開くか

型チェストが速くなることは単に「CIが少し速くなる」話ではない。コストが下がれば型チェストをより頻繁に、より多くの場所で、より密接に使えるようになる。全プロジェクトの型チェストが数秒で完了するなら、現在は「保存後に数十秒待って端末で手動実行」していた方式がIDEネイティブに統合される可能性がある。これは開発ループの性質自体を変える。

7.3 移行を急ぐ必要はない

RCはまだプロダクション推奨ではない。廃止済みフラグを多用している場合、プログラマティックAPIに依存するツールがある場合、または7.0対応を確認できていないビルドツールに依存している場合は、直接アップグレードは時期尚早だ。Microsoftは安定版リリースをRCから約1ヶ月後と発表している。その期間にエコシステムの7.0対応状況を観測しながら、並列比較テストをCIで先行して準備するのが合理的だ。

8. まとめ — JSツーリングのネイティブ化の節目

TypeScript 7.0 RCは、TypeScriptコンパイラが自分の言語であるTypeScriptを実装言語として使う時代を終わらせる変化だ。Project Corsaが約1年でRCに到達したことは、Microsoftが移植の忠実度を検証しながらも意味のある速度でこの作業を完了させたことを示している。

2026年6月時点での実用的なまとめは3点だ。大規模コードベースのビルドとエディタ応答性が実質的に速くなる。型システムは同一なので型安全性の保証は変わらない。プログラマティックAPIの安定化(7.1)まで生態系全体の対応には時間がかかる。esbuildからSWC、そしてこの瞬間に至るJSツーリングのネイティブ化の流れの中で、TypeScriptコンパイラ自体がその流れに合流したことが、この変化の位置づけだ。
