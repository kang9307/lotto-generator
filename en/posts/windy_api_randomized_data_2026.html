When a Free API Gives You Wrong Data on Purpose - The Windy Surf Forecast Case

What Windy's officially randomized trial API reveals about freemium data degradation and how developers should verify API trust

2026-07-03 Dev & Infra

Introduction: Can You Trust a Free API Enough to Build On It?

As of July 2026, a developer's comparison of free surf forecast APIs has been quietly making the rounds in developer circles. While benchmarking several free surf and weather forecast APIs side by side, the author re-confirmed something startling: Windy's API Trial key doesn't return real observation or model data at all - it returns randomly generated values. What makes this notable isn't that it's a hidden trap; Windy's own staff have confirmed it openly on the company's official community forum.

This piece uses that one case as a starting point to look at three things: how common it actually is for free API tiers to deliberately degrade data quality, what risks developers face when they unknowingly depend on such an API, and what to actually check before adopting a new one. This isn't meant to single out one vendor - it's meant to unpack the structural problem the case exposes.

1. What Was Found - Windy's Trial API Officially Admits to "Random Data"

1.1 How It Came to Light

The trigger was simple. While actually testing several free surf forecast APIs side by side, the author noticed that values returned by Windy's Point Forecast API under a free Trial key didn't follow any physically plausible pattern over time. Checking Windy's official community forum confirmed it: Windy staff had already answered a related question with the line "it generates random data" (Windy Community, staff member Suty). In other words, this wasn't a bug - it was designed behavior.

1.2 Trial vs. Professional - What Actually Differs

Windy's API splits into two tiers: Trial and Professional (paid). The Trial key isn't just rate-limited; in the staff's own words it exists "for testing purposes" only, and returns randomized data. The Professional plan, by contrast, serves real observation and forecast values from actual weather models such as ECMWF and GFS. The common assumption that "free just means fewer requests, but the values themselves are real" doesn't hold here.

2. This Isn't Your Typical "Free Tier Limit" - It's a Silent Failure

2.1 Rate Limits vs. Data Distortion

Rate limits and reduced resolution are constraints developers notice immediately. A 429 error or a coarse grid tells you right away: "this is as far as free goes." Randomized values behave differently. The response arrives as a normal 200 OK, and the numbers sit within a plausible range. It isn't a failure - it's a silent wrong answer.

2.2 The Danger of Fake Data That Passes Tests

When developers test an integration, they usually check whether the request succeeds and whether the response schema is correct. Rarely do they cross-check every value against real-world observations. As a result, a prototype built on a Trial key can look like it's working perfectly while the numbers inside were meaningless from day one. If a side project quietly graduates into production, or a free key is left in test code, the problem only surfaces after deployment.

3. Data Degradation to Drive Premium Upgrades - A Pattern Across the Industry

3.1 Three Ways to Make a Free Tier Worse

There are broadly three ways vendors intentionally make free tiers less attractive. First, usage caps (request counts, call frequency). Second, feature locks (disabling specific endpoints, filters, or batch processing). Third, degrading the data quality itself (lower resolution, delayed delivery, or, as with Windy, replacing the values outright). The first two are widely accepted, normal freemium strategies. The third, especially swapping in entirely different values, is far rarer and far more contentious.

3.2 Watermarking, Delays, and Resolution Cuts - Similar Cases Elsewhere

Similar practices show up in other industries. Financial data APIs commonly give free-tier users 15-20 minute delayed quotes instead of real-time ones. Map and image APIs often watermark free requests or serve only low-resolution tiles. These cases tend to degrade in ways users notice immediately - "it's delayed," "it's blurry." What makes Windy's approach unusual is that it isn't degradation, it's substitution. The values aren't late or fuzzy; they're unrelated to any real observation from the start.

4. The Real Problem Is Where Transparency Lives

4.1 Windy Didn't Actually Hide It

To be clear, this isn't an attempt to vilify Windy. Windy never denied this policy. Staff answered community questions directly, and the fact that Trial exists "for testing purposes" has been stated more than once. It also makes business sense: giving away accurate, production-ready data for free and without limits would remove any reason to buy the paid Professional plan.

4.2 The Gap Between "It's in the Docs" and "Developers Actually See It"

The real issue is where this disclosure lives. This information wasn't placed prominently in the main API documentation - it was buried in a community forum reply thread. A developer integrating the API for the first time is unlikely to encounter a line like "this response contains randomized test data" anywhere near the response headers, field descriptions, or even the request URL itself. Technically disclosed, yes - but the people who actually reach that information are usually the small subset who already hit a problem and went searching. Having disclosed something and having made it discoverable are not the same thing.

5. The Risk of Relying on Free APIs

5.1 The Moment a Prototype Becomes Production

The most common failure path looks like this: a side project or MVP gets built quickly on a Trial key, and once it gets traction, it ships to real users as-is. If nobody revisits the paid upgrade at that point, the service keeps looking functional on the surface while the numbers underneath stay untrustworthy. In domains like surfing or weather, where users act on those numbers - deciding whether to actually paddle out - a silent wrong answer can translate into real-world harm.

5.2 Personal Tools and Internal Dashboards Aren't Exempt

Personal tools and internal dashboards carry the same risk. It's easy to keep using a free key because "only I'm looking at this," until that tool's output starts informing real decisions - inventory, scheduling, operations. If a free API is going to be used for anything beyond a throwaway prototype, verifying whether the data is actually real should happen from day one.

6. A Practical Way to Verify API Reliability

6.1 Cross-Check Against at Least One Authoritative Source

The most reliable method is cross-verification. Compare values for the same timestamp and location against a trusted independent source - a government weather agency or a NOAA buoy station that publishes raw observational data - at least once. If there's no correlation, that API isn't ready for production.

6.2 Search Forums and Issue Trackers, Not Just Docs

Don't stop at official documentation. Search support forums, GitHub issues, and community boards for the API's name alongside words like "trial," "sample," "demo," "random," or "test data." As with the Windy case, vendors often quietly acknowledge these limitations somewhere other than their main landing page - support threads tend to surface it first.

6.3 Separate Quantitative Limits From Qualitative Language

Read pricing pages with an eye for whether the wording is quantitative or qualitative. Numeric limits like "1,000 requests/month" or "10 calls/minute" are predictable and easy to verify. Qualitative phrases like "for testing purposes," "sample data," or "limited accuracy" don't tell you what they actually mean until you check the real response values in code. The moment you spot qualitative language, treat the actual response as something that needs verification.

7. What to Look For When Choosing an Alternative API

7.1 The Open-Meteo Case - A Provider That States Its License and Model Source

Open-Meteo comes up frequently as an alternative in this discussion. It's free for non-commercial use up to 10,000 daily calls with no API key required, and it serves real model data straight from national weather services - GFS, ECMWF, DWD ICON, and others. The data is licensed under CC BY 4.0, and the server code itself is open source under AGPLv3, meaning you can self-host it for unlimited use if needed. The key point: the free tier's limit is a numeric call cap, not the authenticity of the values themselves.

7.2 Prioritize Providers That Are Explicit About "What You Get, and How Much"

Generalizing from this case, a few criteria hold up: favor providers that state their data source (which model, which observation network) explicitly; favor providers where the free-vs-paid difference is described numerically rather than vaguely; favor providers with clear licensing and redistribution terms. Conversely, if a free tier's accuracy or data nature is only described in vague terms, it's safer not to treat that API as a trust baseline until you've verified the actual values yourself.

Conclusion: Free Doesn't Mean Verified

The fact that Windy's Trial API returns random data isn't, by itself, dishonest. Windy never denied it, and it's a defensible business decision. What this piece really wants to highlight is something else: degrading data quality is a common freemium strategy, but when that degradation happens quietly and only lives deep inside documentation, developers end up building services on top of fake data without realizing it.

As of July 2026, the free API ecosystem keeps expanding, and cases like this are likely to become more common, not less. The takeaway is simple: don't equate the word "free" with "verified data." Cross-check at least once against an authoritative source before you put any API on your trust baseline.
