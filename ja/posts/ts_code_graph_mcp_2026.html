TypeScriptコンパイラで作ったコードグラフMCP - Claude Codeのトークンを10倍削減する

コードを読ませずグラフに問い合わせるだけにすると、なぜトークンが減るのか - その仕組みと限界を分析する

2026年7月2日 開発・インフラ

はじめに: エージェントが「コードを読む」やり方そのものが問題だった

GeekNewsに投稿されていた短い記事が目に留まった。TypeScriptコンパイラでコードグラフを構築し、それをMCP(Model Context Protocol)サーバーとして提供したところ、同じ作業でClaude Codeのトークン消費がおよそ10倍減ったという内容だ。要旨自体は数行の簡潔なものだが、扱っている課題は決して小さくない。AIコーディングエージェントを実務で使ったことがある人なら誰もが一度は経験する状況 - ちょっとした質問に答えるためだけにファイルを5つも6つも開かせ、grepを何度も走らせ、結局コンテキストの半分を「コードを探すこと」に費やしてしまう - を正面から狙い撃ちしたアプローチだからである。

本稿は元記事の要約ではなく、MCP・コンパイラAPI・既存のコードインデックス手法を独自に調査・照合したうえでの自己分析としてまとめる。2026年7月時点で、コードグラフMCPに類するツールはすでに複数登場しており、採用しているアプローチや主張するトークン削減幅もそれぞれ異なる。その中で今回の事例が強調する「コンパイラベース」という選択がなぜ重要なのか、そしてなぜ実際にトークンが減るのかを構造的に掘り下げる。

1. コードグラフとMCP - 何をするツールなのか

コードグラフMCPを一言でまとめると、コードベースを事前に読み込んで整理した地図をエージェントに手渡すツールである。二つの軸に分けて考えると理解しやすい。

1.1 コードグラフ - 構造を座標に変換する作業

コードグラフとは、コードベース内のシンボル(関数・クラス・型・変数)をノードとし、それらの間の呼び出し・継承・インポート・型参照関係をエッジとして表現したデータ構造である。「この関数を誰が呼んでいるか」「この型はどこで使われているか」といった問いに、ファイルを漁らずグラフをたどるだけで答えられる。重要なのは、このグラフを実行時ではなくオフラインのインデックス構築段階で事前に作っておくという点だ。エージェントは質問を受けるたびにコードを一から解析するのではなく、すでに完成した地図を照会するだけでよい。

1.2 MCP - その地図をエージェントに渡す標準パイプ

Model Context Protocolは、Anthropicが2024年11月に公開した開放標準で、LLMベースのエージェントが外部ツールやデータソースと通信する方法を標準化するものだ。コードグラフをMCPサーバーとしてラップすれば、Claude Codeのようなエージェントは定められたプロトコルでグラフに問い合わせを送り、構造化された応答を受け取れる。2026年現在、MCPはClaude Code・Cursor・Codex・Windsurfをはじめとする主要なコーディングツールのほとんどが対応する事実上の標準になっている。コードグラフというアイデア自体は古くから存在する(静的解析ツールは数十年前から存在した)が、MCPという標準インターフェースが登場したことで「エージェントがグラフを直接問い合わせる」という組み合わせが初めて実用段階に乗ったというのが筆者の見立てだ。

1.3 今回の事例が主張する核心

元記事が強調する設計は二つある。第一に、グラフの応答にソースコード本文を含めず、名前・エッジ・シグネチャ・file:line範囲のみを返す。第二に、エージェントがグラフを無秩序に探索しないよう体系的な推論順序を強制する仕組みを備えている。8つのリポジトリと4つのモデルの組み合わせでベンチマークした結果、トークン使用量が約10倍減り、回答品質は維持されたと主張している。この数値は特定のベンチマーク環境で得られた結果であり、絶対値としてではなく「グラフを介在させれば桁違いの削減が可能になる」という方向性として読むのが妥当だろう。

2. なぜトークンが削減されるのか - 探索コストの正体

この点が筆者にとって最も興味深かった部分だ。トークン削減の源泉は「生成」ではなく「探索」にある。

2.1 エージェントの探索コストは想像以上に大きい

実際、Claude Codeのようなエージェントが未知のコードベースで作業する際に消費するトークンのかなりの部分は、コードを「探す」ことに使われている。grepで候補を探し、globでファイルを列挙し、そのうちいくつかを開いてみて、目的のものでなければまた探し直す、という往復が繰り返される。この繰り返し自体がコンテキストを埋め尽くす。200ファイル規模のコードベースでは、1時間の作業のうち探索だけでおよそ8万から15万トークン程度が費やされるという観測もある - これは「作業」そのものではなく「道を探す」ためのコストだ。コードグラフがなければ、エージェントはこの探索を毎回ゼロからやり直すことになる。

2.2 圧縮された応答が生む差

コードグラフMCPの核心は、ファイル全体ではなく必要な箇所の座標だけを返す点にある。「この関数を誰が呼んでいるか」という問いに対し、関連する関数5個の名前とファイル位置だけが返ってくれば、エージェントはその座標に直行して必要な行だけを読めばよい。ファイル全体を何度も読み返すのと、正確な座標に一度で到達するのとでは、コードベースが大きくなるほどトークンの差が指数関数的に開いていく。10倍という数値が出たのも、大規模リポジトリではもともと探索の往復が多かったため、その非効率を取り除いた効果が際立って現れたと解釈するのが合理的である。

2.3 強制された推論順序の役割

グラフを提供するだけでは十分ではない。エージエントがグラフを受け取っても習慣的にファイル全体を読み直したり、無関係なノードまで彷徨いながら探索したりすれば、削減効果は薄れてしまう。元記事が言及する「強制的な体系的推論」とは、グラフへの問い合わせ→対象の絞り込み→必要な箇所だけを読む、という順序をプロンプトやツール設計で強制する仕組みだと考えられる。これは別途調査したChain-of-Thought関連の研究とも符合する流れだ - 構造化されていない推論はかえってトークンを浪費しうる一方、情報検索と推論のステップを分離して構造を強制すると、品質を保ちながらトークンを大幅(2〜3倍程度)に削減できるという報告(Focused Chain-of-Thoughtなど)がある。つまりこのツールの削減効果は、グラフというデータ構造と、それを使う手順を強制する設計、この二つが揃って初めて機能した結果だと見るべきだろう。

3. なぜTypeScriptコンパイラAPIなのか

2026年現在、コードグラフ系のMCPツールはすでに複数登場している。調査した限りでは、Tree-sitterベースのパーサーで多言語対応する系統、ベクトル埋め込みで意味的に類似したコードを探す系統、そして今回のように言語別のコンパイラを直接利用する系統に分かれる。この分岐において、コンパイラAPIを選んだ理由を掘り下げる価値がある。

3.1 ヒューリスティックパーサーの限界

Tree-sitterのような構文解析器は、コードの文法構造(括弧がどこで開いてどこで閉じるか、どのノードが関数宣言か)を高速かつ正確に把握できる。しかし「この変数は実際にはどの型か」「このインポートはre-exportを経て最終的にどこから来ているのか」「ジェネリクスがどう具体化されるか」といった意味解釈は別の問題だ。文法情報だけではこうした関係を正確に解けず、ヒューリスティックを積み重ねて近似するほかない。近似である以上、誤検知や見落としが必然的に残る。

3.2 コンパイラはすでに正解を持っている

TypeScriptコンパイラはプロジェクトを実際にビルドするために、すべてのモジュールを解決し、すべての型を推論し、すべての参照を確定させる。この過程を経た結果(型チェッカーの内部状態)には、「何が何を正確に参照しているか」という答えがすでに含まれている。コードグラフをコンパイラAPIの上に構築するということは、この答えを改めて推定するのではなく、そのまま利用するということを意味する。re-exportの連鎖が何段階を経ようと、型エイリアスがどれほど複雑であろうと、コンパイラがすでに解決済みの関係であるため、グラフのエッジが実際のコードの挙動とずれる可能性は低い。これはAutoBEのような別のTypeScriptベースAIコーディングツールが「コンパイラをAPIレベルで組み込み、AIが生成したコードを実際のコンパイラのフィードバックで検証する」という方向を選んでいるのと同じ思想の延長線上にあると読める - コードについて確定的な判断が必要な場面では、近似ではなくコンパイラの正解を使うという原則だ。

3.3 コストはインデックス構築時に移動する

ただし、これはタダではない。コンパイラベースの解析はTree-sitterより重く遅い。しかしこのコストはエージェントがリクエストのたびに支払うものではなく、インデックス構築段階で一度(あるいはコード変更時に差分として)支払われるものだ。つまり重い演算をオフラインで事前に済ませておき、オンラインでは軽い照会だけを残す構造になっている。この「コストの時点移動」こそが、コードグラフMCP全体を貫く設計思想だと筆者は考える。

4. 大規模コードベースにおける価値

このアプローチの価値は、コードベースの規模に比例して大きくなる。小さな個人プロジェクトであれば、ファイルを数個読むこととグラフに問い合わせることの差はごくわずかだ。しかし実務で扱うコードベースはそうではない。

4.1 ファイル数が増えるほど探索の往復が組み合わせ的に増える

ファイルが200個、2000個と増えれば、「関連しそうなファイル」の候補集合も同時に膨らむ。grep一回でヒットする行数、目を通すべき候補ファイル数もすべて増加する。コードグラフはこの組み合わせ的な増加を、あらかじめ整理されたエッジのリストとして吸収する。規模が大きくなるほど「事前に整理しておいたもの」と「毎回改めて探すもの」の差が開いていくため、大規模なモノレポや古いレガシーコードベースほど削減効果は大きくなると筆者は予想する。

4.2 リファクタリングと影響範囲の把握に特に有効

「この関数を変更するとどこまで影響が及ぶか」という問いは、本質的にグラフ走査の問題である。コードグラフがあれば、この問いにファイルを漁ることなく、グラフの逆方向エッジをたどって正確に答えられる。これは、調査した類似ツール(コードレビュー用グラフなど)が共通して「影響範囲(blast radius)の把握」を主要な利用シーンに掲げていることとも一致する。大規模なリファクタリングやコードレビューのように「この変更がどこに波及するか」を繰り返し問う作業において、グラフの利点が最も明確に現れる。

4.3 オンボーディングと未文書化コードでの活用

ドキュメントが不十分だったり、元の作成者がすでに離れたコードベースで、新しく加わったメンバー(人間であれエージェントであれ)が構造を把握するコストは大きい。コードグラフはこうした状況で、暗黙の構造を明示的なデータへと変換してくれる。人間にとっても有用だが、特にコンテキストが制限されるAIエージェントにとっては「構造を体で覚える時間」がないため、グラフが事実上の代替記憶として機能する。

5. 類似アプローチとの比較 - LSP、ベクトル埋め込み

コードグラフMCPが唯一の解決策というわけではない。調査した範囲では、少なくとも三つの系統のアプローチが競合しており、それぞれトレードオフが異なる。

5.1 LSP(Language Server Protocol)との違い

LSPは、エディタが定義へジャンプしたり補完を受け取ったりするために言語サーバーと通信する標準プロトコルである。TypeScriptのtsserverも実質的にこの役割を担う。しかしLSPは「ある時点で一つの質問と応答」を前提に設計されている - カーソル位置の定義がどこにあるか、ここで使える補完は何か、を一つずつ尋ねる形だ。エージェントがコードベース全体の構造を把握しようとすると、こうした問い合わせを数百回往復させる必要があり、そのたびにプロトコルのオーバーヘッドと往復遅延が積み重なる。コードグラフMCPはこの往復をなくし、そもそも「構造全体」を一度に照会可能な形であらかじめ用意しておく点で異なる。LSPが対話的な一問一答だとすれば、コードグラフは事前に作った地図をまるごと手渡すことに近い。

5.2 ベクトル埋め込み型インデックスとの違い

RAG(検索拡張生成)スタイルでコードを埋め込み、意味的に類似した断片を探すアプローチも広く使われている。この方式は「似たようなものを探して」といったファジー(fuzzy)な問い合わせに強い。しかし「この関数を正確に誰が呼んでいるか」のような確定的な関係が必要な問いには弱い。埋め込みの類似度はあくまで近似であって正解ではないからだ。コードグラフはその逆で、確定的な関係には強いがファジー検索には弱い。実務では両者が競合関係というより、相互補完的に使われる可能性が高いと筆者は見る - 「似たコードを探す」は埋め込みに、「正確な依存関係を追跡する」はグラフに任せるといった使い分けだ。

5.3 言語汎用性とのトレードオフ

Tree-sitterベースのツールは、複数言語を一つのフレームワークで扱える点が強みだ。一方でコンパイラAPIベースのアプローチは精度は高いが、言語ごとに個別実装が必要になる。TypeScriptはコンパイラがAPIレベルで公開されており型システムも強力なため、このようなアプローチに特に有利な言語であるという点も押さえておくべきだ。他の言語で同水準の精度を得るには、それぞれの言語のコンパイラや型チェッカーを同等にAPIとして公開する必要があるが、すべての言語がそのようなインフラを備えているわけではない。

結論: 規模が大きいほど、精度が重要なほど見る価値がある

2026年7月時点で、コードグラフMCPはまだ標準と呼べる段階ではなく、急速に増えつつある実験的なエコシステムに近い。今回のTypeScriptコンパイラベースの事例が興味深いのは、「グラフを事前に作って照会だけさせる」というアイデアそのものよりも、コンパイラがすでに確定させた正解をそのままグラフに写し取るという選択にある。近似ではなく確定、毎回の再計算ではなくオフラインインデックス構築、この二つの転換こそがトークン削減の実質的な根拠だというのが筆者の判断だ。

ただし、10倍という数値を万能の指標として受け止めるのは避けるべきだ。ベンチマークは特定のリポジトリとモデルの組み合わせで得られた結果であり、小規模プロジェクトや、もともと探索コストが低い作業では削減幅ははるかに小さくなりうる。また、インデックスパイプラインを追加で運用する負担、コンパイラベースのアプローチが持つ言語依存性も併せて考慮すべきだ。大規模なTypeScriptコードベースでAIエージェントによるリファクタリングや影響範囲分析を頻繁に行うのであれば、こうしたコードグラフMCPを実際に導入し、自分のワークフローでトークンと応答品質の両方を測定してみることを勧める。すでにLSPや埋め込みインデックスを使っているなら、置き換えではなく併用を検討するのが現実的だろう。
