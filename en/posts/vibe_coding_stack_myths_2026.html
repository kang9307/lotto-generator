Where AI-Generated Next.js + Supabase Breaks Later

Keys leaking across the boundary, RLS that is on but wide open, and the places the bill spikes, in the order you should check them

Aug 3, 2026 Development/Infrastructure

Intro: Code that runs and code that is safe are different states

Every screen renders. Login works, posts save, the deploy is green. Getting here took an amount of time that would not have made sense a few years ago. That is exactly why Next.js paired with Supabase has become the default when someone wants to build something quickly with AI assistance. Auth, database, storage, realtime and deployment arrive as one bundle, and generative models have seen more code in this shape than in almost any other.

The problem is not that the stack is bad. It is a genuinely good choice. The problem is that a few pieces of convenient abstraction hide how the thing actually works, and those few pieces happen to be exactly where incidents come from. How far a key travels. How the badge that says a policy is enabled differs from the state where access is actually blocked. What server rendering does with a session. How many connections exist under load. None of that has anything to do with whether the screen renders, which is why none of it shows up right after deployment. It shows up when traffic grows, or when someone opens the browser devtools.

What follows walks through those places one at a time. Each item gives the shape generators usually produce, why it breaks later, and how to check it in your own project and what to change it to. Everything is written as self-inspection rather than as attack technique. For how to choose the stack itself in the first place, I covered that separately in Choose Boring Technology Revisited.

1. One boundary changes the whole bundle

The shape AI produces

A component needs interactivity, so 'use client' goes at the top of the file, and the data-access utility is imported directly into that same file. Inside the utility is code that reads the project URL and a key. It works, so it stays.

Why it breaks later

'use client' is not a marker that changes the nature of one file. The Next.js documentation describes the directive as declaring a boundary between the server and client module graphs. The moment a file carries it, all of its imports and the components it directly renders are included in the client bundle. You did not move one component to the client. You moved the entire module graph hanging beneath it.

There is one safety net that saves most projects here, and it is the environment variable rule. The docs state that only variables prefixed with NEXT_PUBLIC_ end up in the client bundle, and that unprefixed variables are replaced with an empty string. So even when a server-only utility gets dragged clientward by accident, the secret value itself does not get baked into the bundle. The function simply stops working, quietly.

The real incident happens when a human works around that rule. The classic version: something reads undefined locally, so the fix is to add NEXT_PUBLIC_ to the front of the name. That single edit bakes a secret key into the build output as a plain string. Paste the error message into an assistant and this fix gets suggested more often than you would like.

Two less obvious traps sit next to it.

  • Public variables freeze at build time. The docs say that after being built, the app no longer responds to changes in these environment variables. If you promote a single image across environments, every environment carries whatever the value was at build. Rotate a key and the old one keeps shipping until you rebuild.
  • Dynamic lookups are not inlined. Building the variable name from a string, or reading through const env = process.env, takes the reference out of inlining range. Tidying up your config into a lookup table is a very ordinary refactor that makes the value disappear at runtime.

Checking and fixing

The reliable check is to search the build output directly. Code review misses import chains three levels deep.

# After a build, look for the secret value in the client bundle
npm run build
grep -rF "$SUPABASE_SECRET_KEY" .next/static/ && echo "LEAK" || echo "clean"

# Is anything that should stay private declared with the public prefix?
grep -rn "NEXT_PUBLIC_.*\(SECRET\|SERVICE_ROLE\|PRIVATE\)" .env* next.config.*

The fix is to put a marker inside server-only modules. Importing the server-only package makes any attempt to pull that module into a client component fail at build time. Instead of silently receiving an empty string at runtime, the build stops, which means the mistake surfaces before deployment rather than after.

// lib/supabase/admin.ts
import 'server-only'
import { createClient } from '@supabase/supabase-js'

// This client bypasses RLS. It must never leave the server.
export function createAdminClient() {
  return createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_SECRET_KEY!, // no public prefix
    { auth: { persistSession: false } }
  )
}

There is also a structural answer. Let a server component wrap the client component, read the data on the server, and pass down only serializable props. The children slot pattern the docs describe belongs here: a server component handed to a client component as children never enters the client module graph, and only its rendered output is passed along.

2. Enabling RLS is not the end of it

The shape AI produces

Right after the statement that creates the table and enables RLS, a read policy arrives. The name is usually something like enable read access for all users, and the condition is using (true).

alter table public.posts enable row level security;

create policy "Enable read access for all users"
  on public.posts for select
  using (true);

Why it breaks later

Enabling RLS means nothing is returned until a policy exists. The documentation states that once RLS is on, no data is accessible through the API with a publishable key until you create policies. That is a safe default. The trouble is the policy that follows. using (true) is a policy that re-opens the table completely while RLS remains on. In the dashboard the RLS badge reads enabled. In reality the anonymous role reads every row. Enabled and blocked are different states that look identical at a glance.

Several other places routinely go wrong when writing policies.

  • Policies attach per command. A read policy alone leaves writes blocked. Conversely, an update policy alone does not work: the docs state that to perform an update, a corresponding select policy is required. When a feature works locally but fails only in production, check this combination first.
  • USING and WITH CHECK look at different things. USING decides whether an existing row is visible and applies to select, update and delete. WITH CHECK validates the resulting row on insert and update. An insert policy written as with check (true) does not stop someone from creating a row with somebody else's owner value. On any table with an owner column, this is the most common hole.
  • auth.uid() is null for unauthenticated requests. The docs explain that the condition then silently evaluates false and access is denied, and recommend checking authentication explicitly. It fails safe, so it is not dangerous, but this is usually the source of the mysterious empty list.
  • Never authorize on user metadata. The documentation names this directly as a common mistake. User metadata is user-updatable, so a policy that reads a role value out of it becomes a privilege escalation path, and the docs point to app metadata as the alternative.
  • Views bypass policies by default. Unless specified at creation, a view runs with definer privileges and skips the RLS on the tables beneath it. The Supabase Security Advisor classifies this as an error-level lint. Projects that created one view in the dashboard to make a list screen fast end up here.

Checking and fixing

Do not check this by hand. Run the advisors. The Supabase dashboard exposes a Security Advisor and a Performance Advisor under the database section, and you can rerun them after fixing things. The lints that intersect with this article are below.

LintWhat it catchesLevel
0013_rls_disabled_in_publicA public schema table with RLS off. Anyone who knows the project URL can read, edit and delete all dataError
0010_security_definer_viewA view running with definer privileges, bypassing policies on the underlying tablesError
0002_auth_users_exposedA view exposing the auth users table to the publicError
0007_policy_exists_rls_disabledPolicies exist but RLS is not enabled on the tableInfo
0008_rls_enabled_no_policyRLS enabled with no policies, so all API access is blockedInfo
0015 familyPolicies relying on user-editable metadata-

The fix is to split policies per command around an owner condition. One performance measure rides along with it: the docs report that wrapping auth.uid() as (select auth.uid()) lets Postgres cache the result per statement and improved benchmark times by roughly 95 percent. They also recommend indexing the columns policies read and narrowing target roles with the TO clause.

-- Split per command, and pin the owner condition in both directions
create policy "owner reads own rows"
  on public.posts for select to authenticated
  using ((select auth.uid()) = user_id);

create policy "owner inserts own rows"
  on public.posts for insert to authenticated
  with check ((select auth.uid()) = user_id);

create policy "owner updates own rows"
  on public.posts for update to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);

create policy "owner deletes own rows"
  on public.posts for delete to authenticated
  using ((select auth.uid()) = user_id);

-- Index the column the policy reads
create index if not exists posts_user_id_idx on public.posts (user_id);

-- If you use a view, run it with invoker privileges
create view public.post_summaries with (security_invoker = on) as
  select id, user_id, title, created_at from public.posts;

Some tables genuinely need public reads. Announcement lists and public profiles do. Even then, before reaching for using (true), ask whether that table also holds columns that must not be public. If an email address or an internal status value lives in the same table, the answer is to split the table, not to write a cleverer policy. Policies filter rows. They do not hide columns.

3. What the anon key can actually do

The shape AI produces

The project URL and the publishable key are declared with the NEXT_PUBLIC_ prefix and a client is created in the browser. This is correct code. The problem is treating it as evidence that key management is done.

Why it breaks later

The documentation does say publishable keys are safe to expose online. The reasoning matters, though. The reason given is that key retrieval is always possible from a public component. Hiding it was never the defense line, which is not the same as the key being harmless. A request carrying that key runs as the anonymous role, or as the authenticated role once a user token is attached. What becomes visible after that is decided entirely by your RLS policies and schema privileges.

So the summary is this. A leaked publishable key is not an incident. A publishable key combined with a table that has no RLS is. That is precisely what the error-level advisor lint describes when it says anyone with your project URL can read, edit and delete all data.

The secret key on the other side is a different kind of object. The docs explain that it carries the attribute that bypasses RLS and grants full access to project data, and they say not to add it to web pages, source code or executables and not to send it over chat or email. Used from a browser it returns 401, but the docs attach a caveat right there: that does not prevent an attacker from using it elsewhere. The 401 is a mistake-catcher, not a defense. If it has been exposed, the guidance is to delete it immediately and rotate.

AspectPublishable / anon keySecret / service role key
Where it belongsBrowsers, mobile apps, CLIs and other public componentsServers and edge functions only
Role it runs asAnonymous when signed out, authenticated when signed inA role with the RLS bypass attribute
Subject to RLSYes, and that is the only defense lineNo, it bypasses
If exposedAssumed by design, but an incident if RLS is emptyDelete and rotate immediately
Next.js env varCarries the NEXT_PUBLIC_ prefixNo prefix

Checking and fixing

  • Confirm the key used in the browser really is the publishable one. The API section of project settings distinguishes the key types.
  • Review which schemas are exposed to the Data API. The default is the public schema. Tables that never need to be reachable over REST should move to a separate schema and come off the exposed list. Then the API path itself stops existing regardless of keys.
  • If you wrote a function that elevates privileges, check where it lives. The docs explicitly warn never to create definer-privilege functions in an exposed schema.
  • After rotating a key, rebuild the client bundle. Public variables are baked at build time, so the old key keeps shipping until you redeploy.

4. Where the session meets server rendering

The shape AI produces

A server component or middleware reads the session and redirects to login when there is none. It is the client-side call moved verbatim to the server.

// Do not do this on the server
const { data: { session } } = await supabase.auth.getSession()
if (!session) redirect('/login')

Why it breaks later

The Supabase server-side auth guide for Next.js puts a danger marker exactly here. The first sentence is that the server gets the user session from cookies and that those cookies can be spoofed by anyone. The second is never to trust getSession() inside server code. The reason is stated too: the call is not guaranteed to revalidate the auth token. The current guide points to getClaims() for protecting pages and user data, and that call verifies the JWT signature against published public keys on every invocation. getUser(), which asks the auth server directly, serves the same purpose.

That is not the end of it. When sessions meet server rendering, three more traps appear.

  • Server components cannot write cookies. That is why a middleware layer has to own token refresh and propagation. The guide describes that layer doing three things: refreshing the auth token, passing the refreshed token to server components, and passing it back to the browser. Without it, sessions expire quietly and users get logged out for no visible reason. This class of bug is nearly impossible to capture in a report.
  • Caching hands the session to the next person. A page rendered while signed in, cached at a CDN, gets served to whoever comes next. That is why the cookie-setting code in the guide carries cache-related headers and insists they be applied to the response. Keeping static caching off personalized pages is a rendering concern, not an auth concern.
  • Route protection is not data protection. Blocking a path in middleware does nothing to the Data API, which is open independently of your routes. So that one path missing from the matcher list, or the new route someone forgot to register, does not become a leak only if the data side is blocked again by RLS. This is why items 2 and 4 are separate checks.

Checking and fixing

// app/dashboard/page.tsx
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export default async function DashboardPage() {
  const supabase = await createClient()

  // Use a call that asks the server to verify
  const { data: { user }, error } = await supabase.auth.getUser()
  if (error || !user) redirect('/login')

  // RLS applies again here. Keep both layers.
  const { data: posts } = await supabase
    .from('posts')
    .select('id, title, created_at')
    .order('created_at', { ascending: false })

  return <PostList posts={posts ?? []} />
}
  • Request a protected path while signed out and confirm you get a redirect rather than a 200. Use curl, not a browser. Client-side redirects hide what the server actually returned.
  • Read the cache headers on that same response. If a personalized page carries a shared cache directive, fix that first.
  • Put the middleware matcher list and the actual route list side by side. A hand-maintained list will drift. Writing the matcher so protection is the default and exclusion is explicit means a forgotten route fails safe.
  • Search the codebase for getSession calls in server files and review each one.

5. Connections leak differently under serverless

The shape AI produces

The connection string copied from the dashboard goes into DATABASE_URL and an ORM is attached. Port 5432. It runs locally and it runs in production, for as long as traffic stays small.

Why it breaks later

In serverless environments instances multiply as requests arrive. Each instance carries its own pool, so a hundred concurrent requests become a hundred connections. The database has a connection ceiling, and once you reach it new requests wait or fail. The application log shows timeouts, which does not make it obvious that the database is the cause. Connection exhaustion as a phenomenon, and pooler theory in general, I covered in A Startup's PostgreSQL Survival Guide, so here I stay on the choice that only exists where Supabase and serverless overlap.

The three paths the documentation lays out serve different purposes.

PathPortFitsConstraint
Direct connection5432Long-lived VMs, containers, persistent serversIPv6 by default; IPv4 requires the add-on
Pooler, session mode5432Standing in for a direct connection on IPv4-only networksThe docs recommend it only for that case
Pooler, transaction mode6543Serverless and edge functions with many short connectionsNo prepared statement support

The docs call transaction mode ideal for serverless or edge functions that require many transient connections, then immediately attach the constraint: the mode does not support prepared statements, so to avoid errors you must turn them off in your connection library. Skip that switch and nothing happens at low load, then intermittent errors begin exactly when connections start getting reused. This is the archetype of the bug that will not reproduce.

Address family is another silent failure mode. Direct connections are IPv6 by default, and the shared pooler is IPv4-only on every tier. If the deployment target cannot egress over IPv6, the direct connection string fails at connect time. Nothing in the generated code reveals that condition, and since it works locally, it is more confusing than it should be.

Checking and fixing

  • Check the port in the deployed connection string. A serverless function dialing 5432 is itself the finding.
  • If you are on transaction mode, verify that prepared statements are off in the library. The switch has a different name in each one. Prisma uses pgbouncer=true in the connection string; postgres.js uses prepare: false.
  • Separate the migration connection. Schema tools sometimes rely on session-level state and sit poorly with transaction mode. Application traffic on transaction mode and migrations on a direct or session connection is the safer split.
  • Create the client once at module scope and reuse it. Code that builds a fresh pool inside every request handler makes a single instance hold several connections.
  • Watch connection counts and wait states as metrics. What to look at before anomalies become visible is in Making a Database Visible.

6. Migrations and schema drift

The shape AI produces

A block of SQL arrives in the chat answer, ready to paste into the dashboard SQL editor. Paste, run, done. Nothing is written to a file.

Why it breaks later

The real schema in production and the migration files in the repository diverge. Four consequences follow.

  • You cannot create a new environment. Spin up staging and the SQL that gets you there exists nowhere.
  • You have no basis for rollback. What changed, when and why lives only in a chat log.
  • There is no review. Schema changes are harder to undo than application code, and they are the ones skipping approval.
  • Your security configuration sits outside version control. RLS policies are part of the schema. If policies are not in migration files, there is no way to find out who added using (true) and when, and a fresh environment comes up with tables and no policies.

That last point connects back. However carefully you write policies in item 2, if they do not exist as code they disappear at the next deployment.

Checking and fixing

The check is to extract the difference. What comes out is the SQL gap between the remote schema and your local migrations. Empty output is the passing state.

# Link the project
supabase link --project-ref <project-ref>

# Check for drift. Output should be empty
supabase db diff --linked

# Recover changes that were already made by hand
supabase db diff --linked -f recover_manual_changes

# From here on, the file comes first
supabase migration new add_posts_rls
supabase db reset          # replay locally from scratch to prove reproducibility
supabase db push           # apply to remote
  • Put the diff check in CI and fail the build when the output is not empty. Drift is cheap to recover on the day it appears.
  • Put policies, indexes and functions in migration files too. Table definitions alone means half the schema is managed.
  • Make local replay a habit. A migration set that does not produce the same result when run from scratch will fail in a new environment.
  • Split large schema changes instead of shipping them at once. Splitting as a technique is in GitHub Stacked Pull Requests in Public Preview, and how locks behave during zero-downtime changes is in the PostgreSQL survival guide.

7. Where the bill spikes

The shape AI produces

Queries select every column. select('*') shows up as though it were the default. Images are the original uploads dropped straight into an img tag. Realtime subscriptions open inside a component with no teardown.

Why it breaks later

The bill rarely spikes on database size. It spikes on outbound egress. As of August 2026 the public pricing page lays out the following.

Line itemFree ($0)Pro ($25/mo)Pro overage
Monthly active users50,000100,000$0.00325 per user
Database size500 MB8 GB$0.125 per GB
Egress5 GB250 GB$0.09 per GB
File storage1 GB100 GB$0.0213 per GB
ComputeShared (500 MB RAM)$10 monthly creditAdditional projects billed separately

What matters here is not the absolute figures but what the billing unit is. Egress is billed per GB, so if a single list screen ships an entire large text column or JSON column on every render, the screen stays fine while the invoice grows. Images behave the same way. Put a full-resolution file where a list thumbnail belongs and one page view costs several megabytes.

Two operational conditions are worth confirming as well. On the Free plan, projects are paused after a week of inactivity and you get two active projects. If a project created for a quick test became production, that condition eventually shows up as an outage. On Pro, spend caps are on by default and you have to turn them off to spend past the plan limits. Leaving the cap on means the bill will not spike but service gets restricted at the limit; turning it off inverts that. Either choice is fine. Not knowing which one you are on is the bad state.

Checking and fixing

  • Read the usage screen in the dashboard line by line. If egress is larger than expected, find which requests are heavy first.
  • Name your columns in queries. A list screen usually needs three or four.
  • Transform images or store multiple sizes, and attach cache headers. Not re-sending the same file on every view cuts egress substantially on its own.
  • Unsubscribe realtime channels in the cleanup function. Subscriptions that accumulate as users navigate grow both connections and transfer.
  • Check your spend cap setting and make sure the team agrees on which way it should be set.
// Only the columns the list screen needs
const { data } = await supabase
  .from('posts')
  .select('id, title, thumbnail_url, created_at')
  .order('created_at', { ascending: false })
  .range(0, 19)
As of August 2026. Line items and unit prices change. The table above reflects the public pricing page at the time of writing; confirm on the official pricing page before making a billing decision.

8. The pass to run before you ship

The order carries meaning, because each item is a precondition for the ones below it. Route protection cannot help if no policy exists, and fixing a policy accomplishes nothing if the policy is not in a migration and reverts on the next deploy.

#What to checkHowPassing state
1RLS on public schema tablesRun the Security AdvisorZero error-level lints
2using (true) policiesRead the policy list and its tablesOnly on tables meant to be public
3Insert and update conditions on owner columnsInspect the WITH CHECK clausesOwner condition present in both directions
4Secret key in the bundleSearch the build output for the valueZero matches
5Session checks in server codeSearch for getSession callsNone used for authorization
6Cache headers on protected routescurl while signed outNo shared cache on personalized pages
7Serverless connection port and optionsInspect deployment environment variablesPrepared statements off if on transaction mode
8Schema driftsupabase db diff --linkedEmpty output
9Heaviest egress requestsCompare usage screen against query codeNo select-all in list queries
10Plan and spend capCheck billing settingsThe team knows which state it is in

These ten lines are not meant to be done in one sitting. Items 1 through 4 are urgent; the rest can wait until users start arriving. Item 4 is worth doing today, though. If a key is already out there, the cost of recovery only grows with time.

What I could not confirm

  • Line items, included quotas and overage prices reflect the public pricing page as of August 2026. Plan structures change, so re-check at the moment you make a billing decision. The specific throttling behavior when you exceed a limit varies by plan and settings, so I did not generalize it.
  • The return shape of getClaims() and whether asymmetric key verification applies depend on project settings and library version. The examples use getUser(), whose shape is stable.
  • Advisor lint numbers and levels can be revised. Judge by the description the dashboard shows rather than by the number.
  • Which AI coding tool emits which default template varies by tool and version. The shapes described here are not attributed to any specific product; they are the patterns that recur in this stack.
  • Prepared statement options differ per connection library, and the library documentation takes precedence. Combinations beyond the two named here need checking in their own docs.

Conclusion: the places to peel back the abstraction are finite

None of this argues against the stack. The opposite. What makes this combination good is that auth, database and policy sit in one place, which means there are few points to check, and the ten lines above are the list of those few points. Assemble the same capabilities yourself and verifying the same properties means looking in far more places.

The issue with AI-written code is not code quality either. Generative models are optimized to produce code that runs, and they are good at it. But running, being safe and being cheap are three different objectives, and the last two do not appear on screen. So verification stays with the person.

If one criterion survives, let it be this. If you cannot say in one sentence what a piece of code is blocking, assume it is blocking nothing yet. The fact that RLS is enabled is not a sentence. Which role, under which condition, reaches which rows is a sentence. Getting to where you can write that sentence takes about half a day. Postponing it costs an amount nobody can predict.
