병렬 코딩 에이전트는 어디까지 이득인가 - Orca가 연 ADE와 한계선

워크트리 격리·충돌 비용·리뷰 병목으로 가르는, 에이전트를 여러 개 돌려도 되는 작업과 안 되는 작업

2026-08-09 IT/기술

서론: 에이전트를 다섯 개 돌린다는 말

Orca 저장소는 자신을 이렇게 소개한다. 「병렬 에이전트 무리와 함께 일하기 위한 ADE」. 한 문장에 전제가 다 들어 있다. 에이전트는 하나가 아니라 여럿이고, 낱개가 아니라 무리로 다뤄야 하며, 그러려면 편집기와는 다른 종류의 환경이 필요하다는 것.

README의 표현은 더 직접적이다. 「하나의 프롬프트를 다섯 에이전트에 펼치고, 각각을 자기만의 격리된 git 워크트리에 두고, 결과를 비교해 승자를 병합한다」. 도구가 무엇을 하는지는 이 문장 하나로 끝난다. 남는 질문은 그다음이다. 그래서 그게 언제 이득인가.

이 질문이 중요한 이유는 병렬 실행이 직관을 배신하는 영역이기 때문이다. 소프트웨어에서 작업 다섯 개를 동시에 돌린다는 것은 다섯 배 빨라진다는 뜻이 아니다. 작업들이 서로 독립적이어야 하고, 합치는 비용이 나누는 이득보다 작아야 하며, 결과를 판정할 사람이나 기계가 그 속도를 따라가야 한다. 이 세 조건 중 하나만 깨져도 병렬은 손해로 뒤집힌다. 코딩 에이전트라고 예외일 이유가 없다.

그래서 이 글은 도구 소개에서 멈추지 않는다. Orca가 실제로 하는 일과 함께 등장한 Paseo의 차이를 정리한 뒤, 병렬화가 먹히는 작업과 먹히지 않는 작업을 가르는 기준, 충돌과 중복이 실제로 물리는 비용, 그리고 리뷰 부담이 어디로 옮겨 가는지를 따진다. 결론을 미리 말하면 이렇다. 병렬 에이전트는 배속 장치가 아니라 분업 장치다. 분업이 성립하지 않는 일에 분업 도구를 대면 관리 비용만 남는다.

1. ADE라는 말이 실제로 가리키는 것

1.1 용어의 좌표

ADE는 Agentic Development Environment의 약자로 쓰인다. InfoWorld는 이 부류를 「여러 코딩 에이전트가 한 저장소의 여러 브랜치에서 여러 이슈를 작업할 때 벌어져야 하는 모든 일을 조정하고 관리하는」 도구로 정의한다. 같은 기사에 인용된 GitKraken CEO 매트 존스턴의 문장이 대비를 가장 짧게 요약한다. 「IDE는 한 사람이 타이핑하던 시대를 위해 만들어졌다. ADE는 사람이 에이전트 무리를 지휘하는 시대를 위해 만들어졌다.」

1.2 IDE와 어긋나는 축

이름이 비슷해서 IDE의 확장판처럼 읽히지만, 설계의 중심축이 다르다.

  • 화면의 주인공: IDE는 에디터 버퍼가 중심이고, ADE는 실행 중인 작업 목록과 각 작업의 변경분이 중심이다
  • 동시성 단위: IDE는 파일과 탭을, ADE는 브랜치와 작업 디렉터리를 동시에 연다
  • 사람의 역할: IDE에서 사람은 작성자이고, ADE에서 사람은 분배자이자 판정자다
  • 완료의 정의: IDE는 저장이 완료의 단위이고, ADE는 리뷰 가능한 변경 묶음이 완료의 단위다

1.3 이 이름을 쓰는 쪽이 늘고 있다

ADE가 한 회사의 마케팅 용어에 그치지 않는다는 신호는 저장소 메타데이터에서도 보인다. Orca와 Paseo 두 저장소 모두 GitHub 토픽에 ade를 달고 있고, Orca 쪽 토픽에는 parallel-agents·worktrees·agent-ide가 함께 붙어 있다. 범주 이름이 자리를 잡는 중이라는 뜻이다. 다만 범주가 생겼다는 것과 그 범주의 도구가 모든 작업에 이롭다는 것은 완전히 다른 명제다.

2. Orca가 하는 일 - 워크트리 격리와 프롬프트 팬아웃

2.1 격리 수단은 컨테이너가 아니다

Orca가 택한 격리 단위는 git 워크트리다. 워크트리는 같은 저장소의 여러 브랜치를 하나의 git 데이터베이스에서 서로 다른 디렉터리로 체크아웃하는 기능이다. 저장소를 통째로 복제하지 않고도 작업 디렉터리를 여러 개 만들 수 있다는 것이 요점이다. 에이전트 다섯 개가 각자의 디렉터리에서 파일을 고치면, 적어도 파일 트리 차원에서는 서로 밟지 않는다.

이 선택은 가볍고 빠르지만 경계가 어디까지인지는 분명히 해 둬야 한다. 워크트리는 파일 트리의 분리이지 프로세스나 시스템 자원의 분리가 아니다. 컨테이너나 가상 머신처럼 네트워크·포트·프로세스 공간을 갈라 주지 않는다. 이 차이가 실제로 어디서 터지는지는 뒤에서 표로 정리한다.

2.2 팬아웃과 「승자 병합」

Orca가 전면에 내세우는 사용법은 두 가지로 읽힌다. 하나는 서로 다른 작업 N개를 N개 에이전트에 나누는 분업이고, 다른 하나는 같은 작업 하나를 N개 에이전트에 똑같이 던져 결과를 비교하는 팬아웃이다. README가 예로 드는 「하나의 프롬프트를 다섯 에이전트에 펼치고 승자를 병합한다」는 후자다.

이 둘은 겉보기에 같은 병렬이지만 경제학이 정반대다. 분업은 N개의 산출물을 모두 쓰려는 것이고, 팬아웃은 N개 중 N-1개를 버리려고 돌리는 것이다. 버리는 쪽이 낭비라는 뜻은 아니다. 정답이 하나로 정해져 있지 않고 어느 접근이 맞는지 미리 알기 어려운 문제에서는, 여러 시도를 병렬로 뽑아 비교하는 편이 한 시도를 붙잡고 고쳐 쓰는 것보다 나을 수 있다. 다만 비용이 N배로 나가고 판정 부담도 N배로 나간다는 사실은 계산에 넣어야 한다.

2.3 문서가 밝히는 나머지 기능

Orca가 스스로 설명하는 기능 중 병렬 운영과 직접 얽히는 것들은 다음과 같다.

  • 터미널 다중 분할과 영속 스크롤백: 실행 중인 에이전트 여러 개를 한 화면에서 지켜보게 하는 부분
  • 모바일 동반 앱: 자리를 떠난 뒤에도 진행 상황을 확인하고 개입하는 용도(iOS·Android)
  • SSH 원격 실행: 워크트리를 로컬이 아닌 원격 장비에 두고 돌리는 구성
  • GitHub·Linear 연동: 이슈와 변경분을 도구 안에서 연결
  • 변경분 주석: 커밋 전에 사람이 diff에 코멘트를 남기는 검토 단계
  • CLI 스크립팅: orca worktree create처럼 워크트리 생성을 명령으로 자동화

지원 에이전트 범위는 넓게 잡혀 있다. 태그라인이 직접 이름을 대는 것은 Codex·Claude Code·OpenCode·Pi이고, 저장소 토픽에는 cursor-agent도 함께 올라 있다. 기준은 모델 종류가 아니라 터미널에서 도는 CLI 에이전트인가다. 그리고 구독은 사용자 몫이다. Orca는 실행 환경을 제공할 뿐 모델 접근을 제공하지 않는다.

3. Orca와 Paseo - 같은 문제를 다른 무게중심으로 푼다

3.1 두 도구를 나란히 놓으면

같은 시기에 함께 회자된 Paseo는 자신을 「Claude Code·Codex·Copilot·OpenCode·Pi 에이전트를 위한 하나의 인터페이스」로 소개한다. 겨냥하는 문제는 Orca와 같지만 강조점이 다르다.

3.2 라이선스 차이가 실제로 뜻하는 것

표에서 도입 판단에 가장 크게 걸리는 칸은 라이선스다. Orca는 MIT를 명시한다. Paseo는 README에 AGPL-3.0으로 적혀 있는데, GitHub의 라이선스 자동 판별 필드는 이를 특정 라이선스로 분류하지 않는다. 사내 도입을 검토한다면 이 한 칸은 저장소의 라이선스 파일을 직접 열어 확인해야 하는 항목이다. AGPL 계열은 네트워크 너머로 서비스를 제공하는 형태까지 배포로 보기 때문에, 사내에서 개조해 팀에 웹으로 열어 주는 사용 방식이라면 판단이 달라질 수 있다.

3.3 두 도구가 공유하는 전제

차이보다 중요한 것은 둘이 같은 전제 위에 서 있다는 점이다.

  • 모델을 팔지 않는다: 두 도구 모두 에이전트 CLI를 대신 제공하지 않는다. 사용자가 자기 구독과 자격증명으로 미리 설치해 둬야 한다
  • 실행은 사용자 기계에서: 클라우드 샌드박스가 아니라 내 개발 환경이 그대로 무대다. 그래서 로컬 환경의 상태가 결과에 그대로 반영된다
  • 격리는 git에 기댄다: 브랜치와 워크트리라는 이미 있는 메커니즘을 재활용한다. 새 격리 기술을 만들지 않았다
  • 판정은 사람 몫으로 남긴다: 둘 다 결과를 자동으로 채택하지 않는다. 비교와 병합 결정은 사용자에게 돌아온다

즉 이 도구들이 파는 것은 모델 성능이 아니라 실행과 조정의 계층이다. 판단에 쓸 잣대도 그 계층에 맞춰야 한다. 「어느 쪽이 코드를 더 잘 짜나」는 잘못된 질문이다. 코드는 어차피 붙인 에이전트가 짠다.

4. git 워크트리가 나눠 주는 것과 나눠 주지 않는 것

4.1 나눠 주는 것

워크트리 격리가 확실하게 해결하는 문제는 세 가지다.

  • 작업 디렉터리 충돌: 에이전트 A가 고치는 중인 파일을 에이전트 B가 동시에 덮어쓰는 사고가 사라진다
  • 브랜치 전환 경합: 한 디렉터리에서 브랜치를 오가며 생기는 스태시·체크아웃 꼬임이 없어진다
  • 복제 비용: 저장소를 N번 클론하지 않으므로 디스크와 시간이 절약된다

4.2 나눠 주지 않는 것

문제는 개발 작업이 파일만 건드리지 않는다는 데 있다. 에이전트는 빌드를 돌리고 테스트를 띄우고 서버를 실행한다. 그 순간 워크트리 밖의 공용 자원이 등장한다.

자원워크트리로 분리되나부딪히면 생기는 일대처
소스 파일·브랜치분리됨-기본 동작으로 충분
개발 서버 포트분리 안 됨두 번째 에이전트의 서버 기동 실패, 테스트가 남의 서버를 때림워크트리별 포트 오프셋을 환경 변수로 주입

의존성 디렉터리분리는 되나 공유 안 됨워크트리마다 재설치로 디스크와 시간 낭비패키지 매니저의 전역 캐시·스토어 활용

비추적 설정 파일분리되지만 복사 안 됨새 워크트리에서 환경 변수 파일이 없어 즉시 실패생성 시 부트스트랩 스크립트로 배치
외부 API 사용량·요금분리 안 됨동시 실행이 한도에 먼저 부딪힘동시 실행 수 상한을 정해 둠
사람의 주의력분리 안 됨결과가 쌓이는 속도가 검수 속도를 추월진행 중 작업 수를 제한

표의 아래 두 줄이 핵심이다. 앞의 항목들은 설정으로 풀리지만 사용량 한도와 사람의 주의력은 설정으로 풀리지 않는다. 병렬 폭의 실질적 상한은 대개 이 두 줄에서 결정된다.

5. 병렬화가 먹히는 작업과 먹히지 않는 작업

5.1 가르는 기준 세 가지

작업 목록을 늘어놓기 전에 판별 기준부터 세우는 편이 재활용에 좋다. 병렬 적합도는 결국 세 질문으로 갈린다.

  • 경계: 이 작업이 건드릴 파일과 인터페이스를 미리 그을 수 있는가. 그을 수 없으면 다른 작업과 겹친다
  • 검증: 결과가 맞는지 기계가 판정해 주는가. 사람만이 판정할 수 있다면 병렬 폭은 사람 수에 묶인다
  • 되돌림: 틀린 결과를 버리는 비용이 싼가. 버리기 어려운 작업일수록 시도를 늘리는 전략이 손해다

셋 다 예면 병렬이 이득이고, 셋 다 아니오면 병렬은 관리 비용만 남긴다. 대부분의 작업은 그 사이 어딘가에 있다.

5.2 작업 유형별 판정

작업 유형병렬 적합도이유권장 방식
독립 모듈의 테스트 추가높음경계가 파일 단위로 명확하고 통과 여부를 기계가 판정모듈별로 작업 분배
다국어 문서·문자열 갱신높음언어별로 완전히 독립, 원문이 정답 역할언어별 분배
겹치지 않는 의존성 업그레이드높음패키지 단위로 분리되고 빌드가 검증패키지별 분배 후 순차 병합
정형화된 보일러플레이트 생성높음패턴이 고정돼 판정 기준이 명확대상별 분배
린트·포매팅 규칙 일괄 적용중간기계 검증은 쉬우나 전 파일을 건드려 병합이 커짐병렬보다 단일 실행이 대체로 유리
같은 버그의 서로 다른 수정안중간팬아웃에 적합하나 N-1을 버리는 비용을 지불원인이 확정된 뒤 접근만 비교
성능 최적화 시도중간측정으로 판정 가능하나 상호 간섭 여지가 큼측정 환경을 분리해 팬아웃
원인이 불명확한 버그 추적낮음중간 발견이 다음 단계의 전제라 분할 불가단일 에이전트로 순차 진행
공용 인터페이스를 흔드는 리팩터링낮음모든 작업이 같은 경계를 동시에 건드림인터페이스 확정 후에 분배
아키텍처·설계 결정낮음정답이 하나로 수렴하지 않고 판정이 사람 몫병렬은 초안 수집까지만, 결정은 단일
데이터 스키마 마이그레이션낮음순서 의존과 되돌림 비용이 모두 큼병렬 금지, 단일 경로 유지
보안·인증 관련 수정낮음기계 검증이 부분적이고 실수 비용이 비대칭단일 진행 후 별도 검토

5.3 표를 관통하는 규칙 하나

위 표를 다시 읽으면 규칙이 하나로 정리된다. 병렬이 잘 되는 작업은 「이미 결정이 끝난 작업」이다. 무엇을 만들지가 확정돼 있고 남은 것이 실행뿐일 때 에이전트를 늘리면 실행이 병렬로 처리된다. 반대로 결정 자체가 남아 있는 작업에 에이전트를 늘리면, 서로 다른 전제 위에 선 결과물이 늘어날 뿐이다. 병렬화의 선행 조건은 도구가 아니라 설계가 어디까지 확정됐는가다.

6. 충돌과 중복 - 병렬이 실제로 지불하는 비용

6.1 텍스트 충돌은 오히려 싼 편이다

같은 파일의 같은 줄을 두 에이전트가 고치면 병합 충돌이 난다. 이건 시끄럽지만 싸다. 도구가 알려 주고, 위치가 특정되고, 해결하면 끝난다. 병렬 에이전트에서 사람들이 가장 먼저 걱정하는 것이 이 유형인데, 실제로는 가장 다루기 쉬운 축에 속한다.

6.2 진짜 비용은 조용한 충돌이다

비싼 쪽은 텍스트로는 충돌하지 않는데 의미로는 충돌하는 경우다. 에이전트 A가 어떤 함수의 반환 규약을 바꾸고, 에이전트 B가 그 함수를 옛 규약대로 호출하는 코드를 새로 쓴다. 두 변경은 다른 파일에 있으므로 병합은 조용히 성공한다. 깨지는 것은 실행 시점이다.

이 유형이 병렬 에이전트에서 특히 잘 생기는 이유가 있다. 각 에이전트는 자기 워크트리 안의 코드만 본다. 다른 워크트리에서 지금 무슨 일이 벌어지는지는 서로 모른다. 사람 팀이라면 대화로 메워지는 부분이 여기서는 메워지지 않는다. Orca와 Paseo가 공통으로 워크트리 격리를 택했다는 사실은, 뒤집어 말하면 에이전트 간 상호 인지는 설계상 없다는 뜻이기도 하다. 격리는 안전장치인 동시에 정보 차단벽이다.

6.3 중복 작업이 무는 비용

충돌 다음으로 큰 손실은 중복이다. 같은 문제를 두 에이전트가 각자 발견해 각자 고치는 상황은 병렬 실행에서 자주 나온다.

  • 토큰 비용의 이중 지출: 같은 코드를 두 번 읽고 두 번 고치는 만큼 요금이 나간다
  • 리뷰 비용의 이중 지출: 사람은 두 변경분을 각각 읽고 나서야 같은 일임을 알게 된다
  • 병합 순서 의존: 먼저 들어간 쪽 기준으로 나중 것이 무효화되거나 충돌한다
  • 판단 왜곡: 두 결과가 미묘하게 다르면 어느 쪽이 옳은지 판정하는 일이 새로 생긴다

중복을 줄이는 방법은 도구가 아니라 작업 분해에 있다. 작업 지시에 「건드려도 되는 범위」와 「건드리지 말 것」을 명시하면 중복은 눈에 띄게 줄어든다. 병렬 에이전트에서 프롬프트의 절반이 경계 선언에 쓰이는 것은 낭비가 아니라 필수 지출이다.

7. 리뷰 부담은 사라지지 않고 자리를 옮긴다

7.1 병목의 이동

병렬 에이전트가 확실하게 해내는 일은 변경분을 만드는 속도를 올리는 것이다. 그런데 소프트웨어 전달 과정에서 작성은 여러 단계 중 하나일 뿐이다. 작성이 빨라지면 그 뒤 단계에 대기열이 쌓인다. 이건 새로운 현상이 아니라 어떤 공정에서든 병목 앞 구간을 가속했을 때 나타나는 결과다. 바뀐 것은 병목의 위치다. 키보드에서 사람의 판단으로 옮겨 갔다.

7.2 리뷰가 무너지고 있다는 신호

  • 변경분을 열어 놓고 무엇을 확인해야 하는지 떠올리는 데 시간이 걸린다
  • 테스트가 통과했다는 사실만으로 승인하는 횟수가 늘어난다
  • 병합 후에야 두 변경이 서로 어긋난다는 것을 알게 되는 일이 반복된다
  • 어떤 결정이 왜 그렇게 내려졌는지 설명할 수 있는 사람이 없어진다

마지막 항목이 가장 위험하다. 코드는 남는데 결정의 근거가 남지 않는 상태는 시간이 지나야 청구서가 도착한다.

7.3 도구가 겨냥하는 지점과 남는 몫

Orca가 커밋 전 변경분 주석 기능을 넣은 것은 이 문제를 인식했다는 신호로 읽힌다. 결과를 자동 채택하지 않고 사람이 diff에 코멘트를 남기는 단계를 넣었다는 뜻이기 때문이다. 다만 이런 기능은 검토를 편하게 할 뿐 검토량을 줄이지는 않는다. 다섯 개 워크트리에서 나온 다섯 벌의 변경분은 여전히 다섯 벌이다.

7.4 병렬 폭을 실제로 넓히는 것

사람 판정에 의존하는 몫을 기계로 옮기지 않으면 병렬 폭은 늘지 않는다. 순서대로 두면 이렇다.

  • 테스트: 에이전트가 스스로 실패를 발견하고 고치게 만드는 1차 방어선. 커버리지가 낮은 저장소에서 병렬 에이전트는 위험만 늘린다
  • 타입·정적 분석: 조용한 충돌 상당수를 병합 전에 잡아내는 저비용 장치
  • 계약 검사: 모듈 경계의 규약을 코드로 못 박아 두면 에이전트가 서로의 전제를 어겼는지 기계가 판정한다
  • 변경 크기 제한: 한 작업의 변경분이 사람이 한 번에 읽을 수 있는 크기를 넘지 않게 분해한다

정리하면 병렬 에이전트 도구의 도입 준비도는 검증 자동화 수준으로 측정된다. 도구를 먼저 깔고 테스트를 나중에 붙이는 순서는 대체로 역효과를 낸다.

8. 병렬 에이전트를 돌리기 전에 갖춰야 할 것

8.1 저장소 쪽 준비

  • 새 워크트리에서 설치와 빌드가 명령 한 줄로 끝나는가
  • 비추적 설정 파일이 새 워크트리에 자동으로 배치되는가
  • 포트·데이터베이스 이름이 환경 변수로 바깥에서 주입되는가
  • 테스트가 워크트리와 무관하게 독립적으로 도는가
  • 빌드 캐시 경로가 워크트리별로 분리되는가

8.2 작업 분해 쪽 준비

  • 작업마다 건드릴 파일 범위를 지시문에 적을 수 있는가
  • 작업 사이에 순서 의존이 없는지 확인했는가
  • 공용 인터페이스 변경이 필요한 작업을 미리 분리해 뒀는가
  • 각 작업의 완료 조건이 기계로 판정 가능한 형태인가
  • 실패했을 때 통째로 버려도 되는 크기로 잘랐는가

8.3 운영 규칙 쪽 준비

  • 동시에 돌릴 에이전트 수의 상한을 정했는가
  • 병합 순서를 누가 어떤 기준으로 정하는지 합의했는가
  • 버려진 워크트리를 정리하는 절차가 있는가
  • 비용 한도와 사용량 경고를 걸어 뒀는가
  • 하루에 검수할 수 있는 변경분 총량을 기준으로 작업 수를 정하는가

Paseo의 CLI는 이런 운영을 명령 한 줄로 표현하는 형태를 보여 준다. 워크트리 지정이 실행 옵션 자리에 들어와 있다는 점이 이 부류 도구의 성격을 드러낸다.

paseo run --provider <에이전트/모델> --worktree <작업이름> "작업 지시"

9. 다섯 배로 돌리면 다섯 배로 쓴다

9.1 선형으로 늘어나는 것과 늘어나지 않는 것

병렬 실행에서 확실하게 N배로 늘어나는 것은 비용이다. 에이전트 다섯 개가 각자 저장소를 읽고 각자 고치면 토큰 사용량도 다섯 몫이다. 반면 확실하게 N배로 줄어드는 것은 없다. 실행 시간은 작업 간 의존이 없을 때만 줄고, 그마저도 병합과 검수 시간은 줄지 않는다.

여기에 한 겹 더 있다. 구독제 에이전트에는 대개 사용량 한도가 걸려 있다. 다섯 개를 동시에 돌린다는 것은 한도에 다섯 배 빨리 도달한다는 뜻이다. 팬아웃 전략이 매력적으로 보일수록 이 계산을 먼저 해야 한다. 다섯 벌을 만들어 넷을 버리는 방식은 정확히 다섯 몫의 사용량을 쓴다.

9.2 비용을 낮추는 현실적 선택

  • 팬아웃은 좁게: 접근이 갈릴 여지가 큰 문제에만 쓰고, 답이 정해진 작업에는 쓰지 않는다
  • 분업은 넓게: 서로 다른 작업을 나누는 쪽은 산출물을 전부 쓰므로 낭비가 없다
  • 탐색과 실행을 분리: 무엇을 할지 정하는 단계는 단일 에이전트로, 정해진 뒤 실행만 병렬로 돌린다
  • 동시 실행 수에 상한: 검수 가능한 양을 기준으로 정한다. 기계 성능이 아니라 사람 기준이다

10. 이 도구를 지금 도입할지 판단하는 기준

10.1 도입해도 좋은 신호

  • 테스트 커버리지가 이미 쓸 만해서 기계가 1차 판정을 해 준다
  • 작업 대기열에 서로 독립적인 항목이 꾸준히 쌓인다
  • 새 워크트리 부트스트랩이 명령 한 줄로 끝난다
  • 브랜치를 오가며 스태시를 반복하는 일이 잦다 — 워크트리만으로도 이득이 나는 상태다
  • 변경분을 읽고 판정할 사람이 실제로 확보돼 있다

10.2 미루는 편이 나은 신호

  • 테스트가 부족해 결과 판정을 전적으로 사람이 한다
  • 지금 하는 일이 대부분 설계 결정과 원인 규명이다
  • 로컬 환경 구축이 복잡해 워크트리마다 손이 많이 간다
  • 에이전트 하나를 돌릴 때도 결과를 다 못 읽고 있다
  • 사용량 한도에 이미 자주 부딪히고 있다

두 목록을 합치면 판단이 단순해진다. 에이전트 하나를 제대로 못 쓰는 상태에서 다섯 개를 돌리면, 잘 안 되던 일이 다섯 배로 잘 안 된다. 병렬은 잘 돌아가는 공정을 넓히는 장치이지 안 돌아가는 공정을 고치는 장치가 아니다.

11. 확인하지 못한 것

근거를 확보하지 못해 이 글에서 단정하지 않은 항목을 한자리에 모은다.

  • Orca의 충돌 처리 동작: 저장소 문서는 결과를 비교해 승자를 병합한다고 설명할 뿐, 여러 에이전트가 같은 파일을 건드렸을 때 도구가 자동으로 무엇을 해 주는지(자동 병합·충돌 표시·리베이스 전략)는 확인하지 못했다. 이 글의 충돌 논의는 도구 동작이 아니라 병렬 브랜치 운영 일반의 성질에 근거한다
  • 컨테이너 격리 옵션 유무: 워크트리 외에 컨테이너나 샌드박스 수준의 격리를 선택할 수 있는지는 확인하지 못했다
  • 성숙도 표기: 알파·베타·정식 같은 명시적 단계 표기를 찾지 못했다. 저장소 개설이 2026년 3월이고 열린 이슈·PR이 3천 건대라는 사실만 남긴다
  • Paseo 라이선스의 최종 확정: README는 AGPL-3.0으로 밝히지만 GitHub의 자동 판별은 특정 라이선스로 분류하지 않는다. 어느 쪽이 최종인지는 확인하지 못했다
  • 병렬 에이전트의 실측 효과: 에이전트 수를 늘렸을 때 완료 시간이나 결함률이 어떻게 변하는지 보여 주는 공개 벤치마크는 확인하지 못했다. 이 글의 적합·부적합 판정은 측정 결과가 아니라 작업의 의존 구조에서 끌어낸 추론이다
  • 모바일·원격 실행의 보안 모델: 모바일 앱과 SSH 원격 워크트리가 어떤 권한 경계를 갖는지는 확인하지 못했다. 원격 실행을 붙이려면 별도 검토가 필요하다

자주 묻는 질문(FAQ)

Q1. ADE는 IDE와 무엇이 다른가?

IDE는 한 사람이 한 파일을 편집하는 상황을 중심에 놓고 설계됐고, ADE는 여러 에이전트가 한 저장소의 여러 브랜치에서 동시에 작업하는 상황을 조정한다. 화면의 주인공이 에디터 버퍼에서 작업 목록과 변경분으로 옮겨 가고, 사람의 역할도 작성자에서 분배자이자 판정자로 바뀐다.

Q2. Orca는 에이전트를 어떤 방식으로 격리하나?

컨테이너가 아니라 git 워크트리다. 각 에이전트가 자기 디렉터리에서 자기 브랜치를 다루므로 저장소를 복제하지 않고도 파일 충돌을 피한다. 다만 이것은 파일 트리의 분리일 뿐이어서 포트·로컬 데이터베이스·외부 API 사용량 같은 공용 자원은 여전히 공유된다.

Q3. 병렬 에이전트가 실제로 이득인 작업은?

경계가 분명하고 검증이 자동화돼 있으며 실패를 싸게 버릴 수 있는 작업이다. 독립 모듈의 테스트 추가, 겹치지 않는 의존성 업그레이드, 다국어 문서 갱신 같은 것이 해당한다. 반대로 설계 결정, 공용 인터페이스를 흔드는 리팩터링, 원인이 불명확한 버그 추적은 병렬이 손해다.

Q4. 에이전트를 늘리면 리뷰 부담은 어떻게 되나?

사라지지 않고 자리를 옮긴다. 작성이 빨라진 만큼 검수 대기열이 길어지고 병목이 사람의 판단으로 이동한다. 그래서 병렬 폭의 실질적 상한은 모델 성능이 아니라 하루에 제대로 읽을 수 있는 변경분의 양이며, 테스트와 정적 검사로 기계가 먼저 거를 몫을 늘리는 것이 폭을 넓히는 유일한 방법이다.

Q5. Orca와 Paseo 중 무엇을 골라야 하나?

둘 다 에이전트 CLI를 대신 제공하지 않고 실행과 조정만 담당하므로 코드 품질로는 갈리지 않는다. 워크트리 병렬과 결과 비교가 목적이면 Orca가, 데몬 중심 자체 호스팅과 여러 클라이언트 접근이 목적이면 Paseo가 결이 맞는다. 사내 도입이라면 라이선스를 저장소에서 직접 확인하는 편이 안전하다.

결론 - 병렬은 배속이 아니라 분업이다

Orca와 Paseo가 만든 것은 새로운 코딩 능력이 아니라 여러 실행을 나란히 두고 관리하는 계층이다. 이 계층은 실행이 병목일 때만 이득을 낸다. 그리고 실제 개발에서 병목이 실행인 구간은 생각보다 좁다. 결정이 끝나고 남은 것이 타이핑뿐인 구간, 딱 거기다.

오늘 적용할 수 있는 순서로 정리하면 이렇다.

  • 1단계 — 대기열을 두 무더기로 나눈다. 결정이 끝난 작업과 결정이 남은 작업. 병렬은 앞쪽에만 쓴다
  • 2단계 — 워크트리 부트스트랩을 먼저 고친다. 새 디렉터리에서 설치·빌드·테스트가 명령 한 줄로 되지 않으면 병렬은 시작 단계에서 막힌다
  • 3단계 — 공용 자원부터 바깥으로 뺀다. 포트와 데이터베이스 이름을 환경 변수로 옮기는 작업이 도구 도입보다 먼저다
  • 4단계 — 동시 실행 수를 사람 기준으로 정한다. 기계가 감당하는 수가 아니라 하루에 검수 가능한 변경분 수가 상한이다
  • 5단계 — 팬아웃은 마지막에 꺼낸다. 접근이 갈릴 여지가 큰 문제에만 쓰고, 답이 정해진 작업에는 쓰지 않는다

마지막으로 이 글이 하지 않은 일을 분명히 해 둔다. 여기에는 어떤 도구가 더 낫다는 판정이 없다. 병렬 에이전트의 성패는 도구 선택보다 저장소가 병렬을 받아들일 준비가 됐는지에 훨씬 크게 좌우되기 때문이다. 테스트가 얇고 환경 구축이 복잡한 저장소에서는 어떤 ADE를 깔아도 결과가 같다. 준비는 도구 바깥에 있다.
