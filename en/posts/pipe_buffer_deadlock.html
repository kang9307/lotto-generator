Why Your Child Process Hangs - Deadlock From a Full Pipe Buffer

It passes on small inputs and hangs only on real data - a record of measuring the boundary byte by byte

2026-07-30 Development/Infrastructure

Opening: it was stopped, with no message at all

You leave a nightly batch running and in the morning the script is stopped somewhere. No error message. No stack trace. The process is still in the list and CPU usage is zero percent. The last line of the log carries a timestamp from hours ago. Run it again and it stops in the same place. Yet yesterday, with a short sample, it finished in five seconds.

In this situation most of the time is spent in the wrong place. You reread the logic, add more logging, and start suspecting locks or the network. But there is nothing wrong with the code. The cause is not the code, it is the size of the pipe buffer — a number written nowhere in your source. That is why reading the source never reveals it.

This article is a record of measuring that number directly and confirming, byte by byte, the boundary it creates. The conclusion fits in three sentences.

  • A pipe is a finite buffer. Not an unlimited channel but a box of fixed size, and in this environment it was 4096 bytes
  • When it fills, the writer waits. That is not a bug, that is flow control. A slow downstream still lets the pipeline complete. Waiting itself is normal
  • A deadlock appears when the party who should read is already waiting for something else. The shape of the problem is always both sides waiting for each other

And the truly dangerous part is the last one. If the output is smaller than the buffer, nothing at all happens. The samples a unit test uses are almost always smaller than the buffer. So this defect passes every test and shows up only on the first day it meets production data.

Environment. Every output below was produced by actually running the code on Windows 10 Pro (10.0.19045). The shell is GNU bash 5.2.37 (MSYS2 / MINGW64), and the runtimes are Python 3.13.3 (win32) and Node.js v22.16.0 (win32). Every script was saved to a file before running, and because these experiments reproduce deadlocks, every run carried a timeout of ten seconds or less. Anything that hit the timeout is recorded as a confirmed deadlock.

★Buffer capacity differs per environment. The numbers below are measurements from this environment, and other operating systems, shells and runtimes will produce different values. In fact three different values appeared on this one machine depending on the path. So this article does not ask you to memorise numbers, it shows you how to measure. Example paths are written as placeholders such as /tmp/demo.

What this article does not cover. Pipeline exit codes, the status array, and how to notice a failing pipe were already covered in exit codes and pipes. Here I stay on the single point of deadlock caused by a full buffer. Filenames with spaces breaking a pipeline are in the whitespace trap in find and xargs, and quoting rules are in shell quoting rules.

1. A pipe is a finite buffer - 4096 bytes here

The capacity has to be measured first. I created a pipe and kept writing while never touching the read end. Wherever the write stops returning is the capacity. To avoid hanging forever the writing ran on a separate thread and the state was checked after five seconds.

python 3.13.3 / win32
--- 1-1. raw os.pipe() capacity: write until it blocks ---
  writer thread is STILL BLOCKED after 5.0s  <- pipe is full
  bytes accepted before blocking : 4096

--- 1-2. same measurement, 1 byte at a time (exact) ---
  blocked after exactly 4096 bytes

--- 1-3. drain the pipe, does the writer resume? ---
  read 4608 bytes from the read end
  writer counter is now 8704 (was 8704)

--- 1-4. subprocess stdin pipe: child never reads ---
  parent is BLOCKED writing to a child that never reads
  bytes accepted : 4096
  child killed, test over

Three things to read here. First, it is exactly 4096 bytes. Measuring in 512-byte units gave 4096 and measuring one byte at a time gave 4096. Not a rough figure but an exact one. Second, the writing thread did not die, it waited. That it is a wait and not an error is the key. Third, once 4608 bytes were pulled out from the read end, writing simply resumed. The counter climbed to 8704.

That last observation establishes the premise of this article. A writer waiting on a full pipe is not a fault. It continues by itself once room appears. The POSIX text says the same thing. Where the non-blocking flag is clear it records that a write request may cause the thread to block, but that on normal completion it returns the number of bytes requested. In other words it is designed behaviour.

Item 1-4 is the same experiment with the direction reversed. A child process was started with its standard input piped, and the child read nothing. The amount the parent could write was the same 4096 bytes. A pipe is the same box whichever way you write into it.

1.1 Three different values on one machine

There is a caution here. That value of 4096 came out of this path only. Measuring other paths on the same machine gave entirely different numbers.

LayerMeasured hereHow it was measuredNature

The last two rows matter most. The Node stall boundary of 131073 bytes is neither the operating system pipe capacity nor the stream high water mark. It is not the plain sum of the two either. It is the result of several layers stacked together, and I could not verify the internal accounting exactly. So I present that number strictly as a measurement and do not generalise it into a formula.

  • The value in your environment may differ from every number written here. Linux versus Windows, the kind of shell, and the runtime version are all variables
  • So what is useful in practice is not the number but the procedure for measuring it. The experiment in 1-1 reproduces in ten lines
  • More important is that development and production may hold different values. That is the second reason something passes in development and hangs only in production
  • Inside and outside a container, local versus CI, running through a shell versus running directly are all different paths. Passing on one guarantees nothing about another

2. Reproducing the deadlock - between 4096 and 4097

Now for the real accident shape. The most common wrong code follows this order. Start the child, wait first, then read the output. Having waited before reading is the entire trap.

python 3.13.3 / win32

--- 2-1. parent calls wait() first: small vs large output ---
  child writes     1024 B -> wait(3s) : finished (0.10s)
  child writes     4096 B -> wait(3s) : finished (0.10s)
  child writes     4097 B -> wait(3s) : DEADLOCK (2.01s)
  child writes     8192 B -> wait(3s) : DEADLOCK (2.02s)
  child writes    65536 B -> wait(3s) : DEADLOCK (2.01s)
  child writes  1048576 B -> wait(3s) : DEADLOCK (2.01s)

--- 2-2. bisect the exact boundary ---
  largest output that does NOT deadlock : 4096 bytes
  smallest output that DOES deadlock    : 4097 bytes
  probes                                : 13

This table is the heart of the article. 4096 bytes finishes in 0.10 seconds and 4097 bytes waits forever. The code does not differ by a single character. Only the number of bytes the child writes went up by one.

The DEADLOCK marker means the run hit its timeout. The wait call carried a two-second ceiling and anything past it was judged a deadlock. Without a ceiling the experiment itself never ends. Experiments about deadlocks must always carry a timeout — that is the first practical lesson.

Thirteen bisection probes pinned the boundary. The largest passing value is 4096, the smallest hanging value is 4097. That is exactly the pipe capacity measured in section 1. Not a coincidence, but evidence of the cause.

2.1 Why it stops, in two sentences

The structure is simple. The child waits for room in the pipe. The parent waits for the child to finish. The only party who could make room is the parent, and the parent is waiting. The only thing that could finish the child is completing the write, and that is blocked. The circle in which each waits for the other next move has closed.

  • At 4096 bytes or less the child writes everything and simply exits. Data may remain in the pipe but the child is already gone, so the wait returns at once
  • At 4097 bytes the last byte cannot be written, so the child cannot exit. The wait never returns
  • This difference is logged nowhere. No exception, no error code. Two processes quietly wait for one another
  • So the symptom is a hang. Not a failure but nothing happening at all, and that is what makes it hard to diagnose

The Python documentation states the risk explicitly. The description of the wait call reads that it will deadlock when using a pipe for standard output or standard error and the child generates enough output to block waiting for the operating system pipe buffer to accept more data. What the document describes is exactly what the measurement reproduced.

3. Why the tests pass

The boundary from section 2 determines the character of this defect. 4096 bytes is nothing at all. As text that is roughly 4000 characters, as logs about 40 to 50 lines. Samples placed in unit tests are rarely larger.

a day with many errorsseveral MBblocked on standard errorwaits forever

The last row is especially nasty in practice. A batch that normally runs fine stops on exactly the day when many errors occurred. Warning logs grew and standard error crossed the buffer, yet from the outside it reads as if a failure took the batch down with it. The investigation begins with cause and effect reversed.

  • This defect is easy to reproduce. Enlarge the sample and it reproduces every time. The problem is that nobody tries
  • Conversely it never reproduces with a small sample. Which is how the phrase it works on my machine becomes true
  • So putting one sample larger than the buffer into the test set is the cheapest defence. Measure capacity by the method in section 1 and build a sample above it
  • Better still is to restructure the code so that it is safe regardless of size. That is what section 4 onwards is about

4. Fix one - read first, wait afterwards

The simplest fix reverses the order. Read all the output to empty the pipe, then wait.

--- 2-3. FIX A: read the output first, then wait ---
  read 1048576 bytes, then wait() returned 0 in 0.09s

--- 2-4. FIX A': communicate() does the same thing for you ---
  communicate() -> 1048576 bytes, rc=0, 0.10s

The same 1048576 bytes that hung forever in section 2 finished in 0.09 seconds. All that changed was the order of two lines. The pipe keeps emptying while you read, so the child never blocks, and once the child exits the stream closes and the read ends.

Item 2-4 uses the standard function that does this for you. The Python documentation advises using the combined call rather than writing and reading the streams yourself, in order to avoid deadlocks due to any of the other operating system pipe buffers filling up and blocking the child. But the document also records the price: the data read is buffered in memory, so do not use this method if the data size is large or unlimited. Running it makes that price visible.

--- 9-4. streaming a huge output line by line: constant memory ---
  streamed 200000 lines in 0.31s, largest object held = 12 chars

--- 9-5. the same data via communicate(): held entirely in memory ---
  communicate() -> one object of 2600000 bytes (2.5 MB) in 0.53s

The same 200000 lines were taken two ways. Streaming line by line held a single 12-character object at any moment. The combined call puts one 2.5 megabyte object into memory. And 200000 lines is on the small side. For a child with no output ceiling this approach eventually blows up on memory.

  • If the output ceiling is known and small, the combined call is the safest and shortest. Recording that ceiling in a comment is better still
  • If there is no ceiling, take it by streaming or into a file. The combined call prevents the deadlock but leaves a memory problem
  • Streaming is structurally superior because its memory ceiling is one line. 200000 lines were handled in 0.31 seconds
  • However, streaming is affected by the output buffering of the child. Section 9 covers that

5. The trap that catches people most - two pipes, one reader

So far there has been one pipe. Real code usually opens both standard output and standard error as pipes, which is natural since you want the error messages too. But the reading code is usually singular. Here you get two pipes and one reader.

--- 2-5. the classic trap: stdout AND stderr piped, only stdout read ---
  stdout.read() has NOT returned after 4.0s -> DEADLOCK
  child alive : True   (it is blocked writing stderr)

The child writes 200000 bytes to standard error and only 10 bytes to standard output. The parent reads standard output only. Even though standard output holds just 10 bytes, the read never finished. It had not returned after four seconds and the child was alive.

What makes this case vicious is that there is nothing wrong with the stream I am reading. Standard output is 10 bytes, one four-hundredth of the buffer. However long you stare at the code, no picture of an oversized output appears. The blockage is in the other pipe, the one I opened and never look at.

Node reproduced the same thing. And Node has one more layer, so the boundary is much larger.

node v22.16.0 / win32 / 10.0.19045

--- 4-1. spawn, never touch child.stdout, wait for close ---
  child writes     1024 B: close fired, code=0 (93 ms)
  child writes     4096 B: close fired, code=0 (92 ms)
  child writes    65536 B: close fired, code=0 (95 ms)
  child writes  1048576 B: TIMEOUT after 2500 ms -> DEADLOCK

--- 4-2. exact boundary for the paused-stream case (bisect) ---
  largest output that does NOT hang : 131072 B
  smallest output that DOES hang    : 131073 B
  probes: 18

--- 4-5. stdout AND stderr piped, only stdout consumed ---
  only stdout consumed: TIMEOUT after 3000 ms -> DEADLOCK

Note that 65536 bytes passed. In Python that size would have blocked long before. Node holds data read from the operating system pipe in its own stream buffer, so it survives longer. Which means in Node this defect surfaces later and only on larger data. That is not good news. It means the chance of finding it during development is that much lower.

The Node documentation describes the situation precisely. It states that by default pipes for standard input, output and error are established between the parent process and the spawned subprocess, that these pipes have limited and platform-specific capacity, and that if the subprocess writes beyond that limit without the output being captured, the subprocess blocks waiting for the pipe buffer to accept more data. The phrase platform-specific capacity is exactly what the table in section 1 shows.

6. Fix two, three and four - read together, use files, or merge

The two-pipe problem has three directions of fix. All three were run and confirmed.

--- 2-6. FIX B: read stderr concurrently in a thread ---
  stdout 10 B, stderr 200000 B, rc=0, 0.10s -> no deadlock

--- 2-7. FIX B': communicate() reads both streams at once ---
  communicate() -> stdout 10 B, stderr 200000 B, rc=0, 0.20s

--- 2-8. FIX C: give the child a real file instead of a pipe ---
  wait() first with files: rc=0 in 0.10s
  out.tmp 10 B, err.tmp 200000 B

--- 2-9. FIX D: merge stderr into stdout (one pipe, one reader) ---
  merged read 200010 B, rc=0, 0.09s
  first 4 bytes b'EEEE'  last 4 bytes b'OOOO'
  count O=10  E=200000

Fix two, read together. A separate thread read standard error while the main thread read standard output. What had not finished after four seconds finished in 0.10 seconds. In an asynchronous runtime a concurrent await does the same job. The principle is single: there must be as many readers as there are streams opened as pipes.

Fix three, take it into a file. Item 2-8 is interesting. When the output lands in a temporary file, waiting first is safe. That is the very order which produced an endless wait in section 2, yet this time it finished in 0.10 seconds. The reason is clear. A regular file has no such state as full. A pipe is a fixed-size box while a file grows as far as the disk allows. There is no reason for the writer to wait, so the very premise of the deadlock disappears.

Fix four, merge them. Merging standard error into standard output leaves one pipe, so one reader suffices. All 200010 bytes arrived in 0.09 seconds. But the first four bytes of the result are EEEE and the last four are OOOO. The child wrote standard output first, yet standard error came first in the result. The ordering flipped.

6.1 The price of merging - ordering scrambles

I confirmed the effect again with a short example, making the child alternate three writes to each stream.

--- 2-10. the price of merging: ordering gets scrambled ---
  merged (default buffering):
    ERR-0
    ERR-1
    ERR-2
    OUT-0
    OUT-1
    OUT-2
  merged (PYTHONUNBUFFERED=1):
    OUT-0
    ERR-0
    OUT-1
    ERR-1
    OUT-2
    ERR-2
  same bytes? False

The real order the child wrote is OUT-0, ERR-0, OUT-1, ERR-1, OUT-2, ERR-2. Merged with default settings, three standard error lines came first and three standard output lines afterwards. It reads as a completely different story.

The cause is not the pipe but the program own output buffer. Standard error is usually unbuffered and goes out immediately, while standard output switches to block buffering when attached to a pipe and leaves all at once at exit. That is what rearranges the time order. Turning on the unbuffered switch restored the real order exactly.

  • Do not merge logs whose order matters. Where progress and errors must be read chronologically this is fatal
  • Merging is convenient when you do not look at the order. Storing the whole output as one blob on failure is perfectly fine
  • To keep both the ordering and the single pipe, run the child unbuffered. The second block above is exactly that
  • Picking out just the error lines later is impossible. Merging destroys the origin information

The Node side fixes were confirmed symmetrically.

--- 4-3. FIX: consume the stream (data listener) ---
  4 MB with a data listener: close code=0, read 4194304 B (100 ms)

--- 4-4. FIX: resume() alone is enough (discard the data) ---
  4 MB with resume() only: close code=0 (101 ms)

--- 4-6. FIX: consume both streams ---
  both consumed: close code=0, stdout 10 B, stderr 400000 B (91 ms)

--- 4-9. FIX: stream straight to a file, no memory, no pipe limit ---
  4 MB to a file descriptor: close code=0, file 4194304 B (91 ms)

--- 4-7. spawnSync reads both for you: no deadlock, but memory ---
  spawnSync 4 MB : status=0, stdout 4194304 B, 116 ms
  maxBuffer 1024 : status=null, error=ENOBUFS

--- 4-8. execFile has a default maxBuffer ---
  execFile 4 MB default maxBuffer -> error code=ERR_CHILD_PROCESS_STDIO_MAXBUFFER

Item 4-4 is interesting. Merely discarding the data breaks the deadlock. Even if you will not use the content, letting the stream flow keeps the child unblocked. Of course if you never intended to look at the output, not creating the pipe is the right answer. The Node documentation says plainly to use the ignore option if the output will not be consumed.

Items 4-7 and 4-8 show the character of bounded approaches. The default ceiling of the file-executing helper is documented as one megabyte, and going over it produces an error instead of a hang. The child is terminated and the output truncated. That is far better than a deadlock. Failing loudly always beats stopping quietly.

7. Shell pipelines - flow control is not a bug

The same principle operates in the shell, yet there it is usually not a problem. Understanding why gives you the criterion that separates deadlock from flow control.

bash 5.2.37(1)-release on Msys / MINGW64_NT-10.0-19045

--- 3-1. capacity of a SHELL pipe: writer pushes, reader sleeps ---
  bytes the writer got in before it blocked : 65536 (128 B granularity)

--- 3-2. same probe, 16 B granularity ---
  bytes accepted : 65536

--- 3-3. flow control is NOT a bug: slow reader only slows the writer ---
  pipeline exit=0  elapsed=2455 ms  (reader slept 2s, still COMPLETED)

--- 3-4. reader closes early: writer gets SIGPIPE (the opposite problem) ---
row
row
  PIPESTATUS = 141 0

Item 3-1 is the second row of the table in section 1. The shell pipe capacity is 65536 bytes, sixteen times larger than the native pipe on the same machine. Measuring at two different granularities gave the same value.

Item 3-3 is the point of this section. The downstream end was made to read nothing for two seconds. The upstream end filled 65536 bytes and waited. Yet the pipeline completed normally in 2455 milliseconds with exit code zero. The downstream woke after two seconds, started reading, and the upstream resumed and ran to the end.

This is flow control. A pipe automatically matches the speed of a fast producer to a slow consumer. The producer waiting is not waste but a design that avoids unbounded memory use. Without this device a producer would eat all memory in front of a slow consumer.

AspectFlow control (normal)Deadlock (an incident)
state of the writerwaitingwaiting (identical)
state of the readerwill read eventuallyis waiting for something else
as time passesprogress resumesstays that way forever
measured hereexit code 0 after 2455 msno change until the timeout
how to tell them apartsample progress twice and compare. Moving means flow control, frozen means deadlock

The first two rows are the key. Looking only at the writer, the two are indistinguishable. Both are waiting on a write to a pipe. The difference lies with the reader. So diagnosis must always look at both sides together.

Item 3-4 is the opposite accident. When the reader finishes first, the writer is signalled rather than made to wait. The first status slot showing 141 is the trace of that. The meaning of that value and the exit code conventions of pipelines were covered in exit codes and pipes, so here I only note the direction. A deadlock happens because the reader does not read, this happens because the reader left first.

One more observation is worth adding. With a native Windows program as the upstream in the same situation, a write error appeared instead of a signal. The exit code was 1 and the message indicated an invalid argument. So even the way the fact that the reader is gone gets delivered depends on the environment. To identify a cause from an exit code you must check your own environment first.

8. The buffer is not one layer

So far only the pipe buffer has been discussed, but there is one more layer: the program own output buffer. The two are entirely separate, and mixing them up misdirects diagnosis.

--- 5-1. what Python says about its own stdout buffering ---
  plain          : isatty=False line_buffering=False
  into a pipe    : isatty=False line_buffering=False
  with -u        : isatty=False line_buffering=False write_through=True
  buffer size    : io.DEFAULT_BUFFER_SIZE = 8192

--- 5-6. two independent layers: how many bytes arrive per read ---
  default buffering  : chunk sizes [8268, 212]
                       2 chunks, 8480 bytes total
  PYTHONUNBUFFERED=1 : first 10 chunk sizes [212, 4240, 4028]
                       3 chunks, 8480 bytes total
  one line is 210 bytes; the default run hands them over in 8192 B blocks

The child writes forty lines of 210 bytes, 8480 bytes in total. With default settings the parent received just two chunks, of 8268 and 212 bytes. Forty writes arrived in two deliveries. The program output buffer size of 8192 decided that unit.

The difference between the two layers needs to be set out.

LayerValue hereWhen it fillsHow to change itSymptom

This table matters in diagnosis because the two layers produce different symptoms. The output buffer creates delay and the pipe buffer creates a stop. Logs arriving late and the process being stuck are different problems with different fixes.

On the writing side Node made another choice. That was measured too.

node v22.16.0
--- 8-1. Node adds its OWN buffer on top of the OS pipe ---
  child.stdout.readableHighWaterMark : 16384
  child.stderr.readableHighWaterMark : 16384
  child.stdin.writableHighWaterMark  : 16384

--- 8-3. write() return value tells you the buffer is full ---
  bytes handed to write()            : 1048576
  write() first returned false at    : 16384 B
  socket.writableLength (queued)     : 1048576
  -> Node queues in memory instead of blocking; the queue is unbounded

1048576 bytes were pushed into the child standard input. The write function started returning false at the 16384-byte mark, signalling that the buffer was full. Yet it did not block. All 1048576 bytes handed over piled into a memory queue.

  • Node converted the write-side deadlock into memory growth. Instead of stopping, the queue grows without bound
  • Ignore the return value and you get memory exhaustion instead of deadlock. Only the symptom changes, the problem stays
  • Conversely the read side still deadlocks. The 131073 bytes in section 5 is that
  • So a different runtime turns the same cause into a different symptom. The judgement that we are fine because we use Node is only half right

9. Why progress output never appears

This is the representative symptom created by the output buffer of section 8. Progress logs do not appear in real time. I measured arrival times of the same program under three conditions, a program that prints six lines at 0.3 second intervals.

--- 5-2. six lines through a pipe, DEFAULT buffering (arrival times) ---
    +2019 ms  progress 0/6
    +2074 ms  progress 1/6
    +2125 ms  progress 2/6
    +2177 ms  progress 3/6
    +2237 ms  progress 4/6
    +2294 ms  progress 5/6

--- 5-3. the same program with PYTHONUNBUFFERED=1 ---
    + 200 ms  progress 0/6
    + 504 ms  progress 1/6
    + 812 ms  progress 2/6
    +1108 ms  progress 3/6
    +1413 ms  progress 4/6
    +1702 ms  progress 5/6

--- 5-5. does stdbuf help a Python child? ---
    +2223 ms  progress 0/6
    +2276 ms  progress 1/6
    +2328 ms  progress 2/6
    +2384 ms  progress 3/6
    +2439 ms  progress 4/6

With default settings all six lines arrived at once, after 2019 milliseconds — after the program had finished. To someone expecting one line every 0.3 seconds it looks like two seconds of no progress at all. With the unbuffered switch on, the arrivals were 200, 504, 812, 1108, 1413 and 1702 milliseconds, the expected spacing.

Item 5-5 is the trap. I prefixed an external buffering-control tool and it had no effect at all. Clumping from 2223 milliseconds onward is the same as the default. That tool adjusts the buffering of the C standard library, while this runtime uses its own buffer. When a tool is applied and nothing changes, the tool may not reach that layer.

  • Most missing progress output is not a slow program but data pooling in a buffer. The programs in 5-2 and 5-3 are completely identical
  • What gets fixed is the producer side. The reader can do nothing. Data that never entered the pipe cannot be read
  • Use the switch that matches the runtime. The environment variable and the command option gave nearly identical results here (200 versus 210 milliseconds)
  • This delay is unrelated to deadlock. Confusing the two makes you fix the wrong thing

★What I could not reproduce. The standard explanation of this symptom is that output is line buffered when attached to a terminal and switches to block buffering when attached to a pipe. But a comparison against a real terminal could not be reproduced in this environment. The runs are non-interactive, so the terminal test never returned true on any path, and attaching a pseudo terminal tool only produced a message refusing because standard input is not a terminal. So all output above is the pipe case, and the terminal behaviour was not measured. What is confirmed stops at this: with a pipe attached, turning on the buffering switch restores the arrival spacing.

10. Both sides waiting for each other - the two-way deadlock

So far only the output direction. When you must also feed a large input to the child, the deadlock appears in its purest form: the parent writes all the input, then reads the output. And here an unexpected result came out.

--- 6-1. child A (reads all, then writes) - like sort ---
  payload     4096 B -> ok         (wrote 4096 B, echoed 4096 B, 0.09s)
  payload    65536 B -> ok         (wrote 65536 B, echoed 65536 B, 0.09s)
  payload  1048576 B -> ok         (wrote 1048576 B, echoed 1048576 B, 0.10s)
  payload  4194304 B -> ok         (wrote 4194304 B, echoed 4194304 B, 0.14s)

--- 6-2. child B (streaming filter) - like cat / grep / sed ---
  payload     1024 B -> ok         (wrote 1024 B before stopping, 0.10s)
  payload     4096 B -> ok         (wrote 4096 B before stopping, 0.10s)
  payload     8192 B -> ok         (wrote 8192 B before stopping, 0.09s)
  payload    16384 B -> DEADLOCK   (wrote 10240 B before stopping, 3.01s)
  payload    65536 B -> DEADLOCK   (wrote 10240 B before stopping, 3.01s)
  payload  1048576 B -> DEADLOCK   (wrote 10240 B before stopping, 3.01s)

--- 6-3. verify the bracket, then bisect the streaming case ---
  bracket check: 1 B hangs=False   65536 B hangs=True
  largest payload that survives : 9216 B
  smallest payload that hangs   : 9217 B
  probes : 16

The result split completely according to what kind of child it was. This is the most practical finding of the whole experiment.

  • A child that reads everything before writing (the sorting-tool family) did not deadlock even at four megabytes. The child keeps reading so the parent write never blocks, and by the time writing is done the parent has moved on to reading
  • A streaming filter that writes while reading (the search and substitute family) deadlocked from 9217 bytes. When the child blocks on its output pipe it stops reading, and then the parent write blocks too
  • So the same parent code passes or hangs depending on the other side. This is where the accident of swapping one tool in a pipeline and suddenly hanging comes from
  • Which means you cannot judge from the parent code alone. You have to know whether the child streams or not

Decompose the boundary of 9216 bytes and the structure becomes visible. 4096 plus 4096 plus 1024 equals 9216. The child output pipe fills with 4096 bytes, the parent input pipe fills with 4096 bytes, and with a final 1024-byte chunk in flight the circle closes. The sum of the two pipe capacities appeared directly as the boundary. That is the arithmetic evidence of both sides waiting for each other.

--- 6-4. FIX: feed and drain at the same time ---
  communicate() 4 MB in -> 4194304 B out, rc=0, 0.12s

--- 6-5. FIX: writer thread + reader in the main thread ---
  writer thread + main-thread reader -> 4194304 B, rc=0, 0.12s

There is only one fix. Do the feeding and the draining at the same time. Whether you hand it to the combined call or move the writing to a separate thread, four megabytes finished in 0.12 seconds. Separate the order and it deadlocks, overlap it and it resolves.

11. A procedure for diagnosing a hang

Now the practical situation. A hung process sits in front of you and you must decide whether this is the problem. Five steps, no special tooling. I created a deadlock deliberately and walked the procedure.

--- 7-1. start a pipeline that is stuck on purpose, then look at it ---
  step 1: are both ends still alive?
          372     369     365      22220  ?         197609 13:40:40 /usr/bin/sleep
          373     370     370       7504  ?         197609 13:40:40 .../python      

  step 2: is the writer making progress? (sample the counter twice)
    bytes written at t=2s : 65536
    bytes written at t=4s : 65536
    -> FROZEN at the same byte count

  step 3: is it burning CPU (a loop) or waiting (blocked)?
    CPU seconds sample 1 : 0.109375
    CPU seconds sample 2 : 0.109375
    -> equal CPU time + alive process = BLOCKED, not looping

  step 4: the decisive test - shrink the payload
     65536 B payload -> writer exit=0  (0 = finished on its own)
    400000 B payload -> writer exit=124  (124 = still blocked when timeout killed it)
    got 65536 B in before blocking
    same code, only the size changed -> the cause is the pipe buffer

Reading the four steps in order narrows the verdict.

  • Step 1, confirm life. Both appear in the process list. Nothing crashed, they are alive and waiting. That alone erases the crash hypothesis
  • Step 2, confirm progress. Bytes written read 65536 at both the two-second and four-second marks. Frozen. That is the criterion from the table in section 7
  • Step 3, confirm CPU. Cumulative CPU time held at 0.109375 then 0.109375. A spin loop would raise that value. It did not rise, so this is waiting rather than computing
  • Step 4, the decisive test. The same code ran twice with only the size changed. 65536 bytes exited normally with code 0, while 400000 bytes was killed while still blocked and left 124. The amount that got in was exactly 65536 bytes, the shell pipe capacity
  • Step 5, read the code. Check whether a wait call sits before the read, and whether any stream is opened as a pipe and left unconsumed. If the four previous steps hold, the cause is certainly here

It is worth stressing why step 4 is decisive. Nothing but the size was changed. Same code, same environment, same input content. Yet the results diverged. No clearer evidence exists. And this test requires no special tooling whatsoever.

ObservationVerdictNext action

A word on tools. In this environment only listing processes and reading CPU time were available. There was no tool for open files and no debugger, and while a system call tracer existed it could not attach to an already running native process. So the procedure above is deliberately built from things that work anywhere. Progress sampling and the shrink test work in an environment with no tools at all.

12. Timeouts, streaming, and when the parent dies

Three more things that catch people in practice. The first is the timeout trap.

--- 9-1. wait(timeout=) does NOT kill the child; run(timeout=) does ---
  Popen.wait(1.5) raised TimeoutExpired
  child alive right after the exception : True
  after an explicit kill(), alive        : False

--- 9-2. run(timeout=) on a big output: does it survive? ---
  run(capture_output=True, timeout=5) -> rc=0, 2097152 B, 1.23s

--- 9-3. the trap: check_output on a child that also writes stderr ---
  check_output, stderr NOT a pipe (DEVNULL) -> 10 B, 0.38s
  check_output(stderr=PIPE)  -> 10 B, 1.15s

Item 9-1 matters. A ceiling was placed on the wait call and the exception arrived, yet the child was still alive. A timeout means I stop waiting, not I end the other party. It disappeared only after an explicit kill.

  • Set a timeout without killing and orphan processes accumulate. In an environment where the batch runs repeatedly, that quietly eats resources
  • The place that catches the exception must call the kill. And it must reap the process afterwards
  • As 9-2 and 9-3 show, the high-level calls handle this for you. A two megabyte output completed inside the ceiling, and opening standard error as a pipe did not deadlock
  • So unless there is a reason to assemble it yourself, using the high-level call is safer. Most deadlocks come out of hand-assembled code

The second is when the parent dies first. I checked what becomes of the child in two varieties.

--- 10-1. orphan that keeps WRITING to the dead parent's pipe ---
  1.5s after the parent exited, still running : False
  -> its next write failed, so it terminated on its own

--- 10-2. orphan that is NOT writing (just sleeping) ---
  1.5s after the parent exited, still running : True
  -> nothing ever tells it the parent is gone; it just keeps sleeping
  had to be killed explicitly

The results split. A child that keeps writing died by itself, because its next write failed. Meanwhile a child that waits without writing survived, because nothing gives it an occasion to learn that the parent is gone. It disappeared only after an explicit kill.

  • The expectation that children get cleaned up when the parent dies is only half right. It holds only for children that keep writing
  • A pipe informs you of the absence of the other side only when you write. A process that reads or sleeps receives no signal at all
  • So code that spawns children needs handling that cleans them up on the parent exit path. It must exist on the exception path as well as the normal one
  • This can behave differently depending on the operating system and process group settings. The results above are measurements from this environment

The measurements so far, compressed into practical decisions. Three things decide it: output size, whether standard error is used, and whether order matters.

14. Checklist and things not to do

Arranged so you can use it directly in a code review.

  • Count whether every stream opened as a pipe has code consuming it. Streams and readers must match in number
  • Check that the wait call comes after the read. If it comes before, that alone is a defect
  • Check that every wait call has a timeout. Without one you cannot even investigate during an incident
  • Check that the child is killed explicitly after a timeout. Catching the exception does not kill it
  • Check that children with an unclear output ceiling are taken into a file or streamed
  • Check that some test sample is larger than the buffer capacity. Without one this path has never been verified
  • Check that writing and reading run together where a large input is fed
  • Check that logs whose order matters have not been merged. Merging breaks the chronology
  • Check that children which must show progress run unbuffered
  • Check that no pipe is being created where the output is never used
  • Check that the parent exit path has child cleanup. A sleeping child does not die by itself
  • Check that the production buffer capacity was measured directly. It may differ from development

And the things not to do.

  • ❌ A stream opened as a pipe and never consumed — overwhelmingly the most common cause in practice, and usually standard error
  • ❌ Wait first, read later — code that only passes up to 4096 bytes
  • ❌ Assuming the child also died because the wait failed — measured, it was still alive
  • ❌ Passing a review on small samples only — the boundary is crossed only by real data
  • ❌ Assuming a buffer capacity from another environment — one machine gave 4096, 65536 and 131072
  • ❌ Misdiagnosing a delayed progress log as a slow program — it is only pooled in a buffer and the cause is different
  • ❌ Merging two streams and then trusting the order — measured, the order flipped completely
  • ❌ Waiting without a timeout — it makes the reproduction experiment itself impossible. Every experiment here ran under a ceiling
  • ❌ Judging the code safe from the parent alone — as in section 10, the kind of child changes the result

# Pipe Buffer Deadlock — Child Process Review Sheet

> Source: braindetox.kr — The Real Reason Your Child Process Hangs
> Evidence: measured on Windows 10 / bash 5.2.37 (MSYS2) / Python 3.13.3 / Node.js 22.16.0
> Paste this file into an AI assistant and say: review our code against these rules.
> ⚠ Buffer capacity differs per OS, shell and runtime. The numbers below are measurements from the environment above. Measure yours again.

## 0. The principle in one line

A pipe is a **finite buffer**. When it is full the writer waits — that is not a bug, that is **flow control**.
The problem appears when the person who should read is already waiting. That is when **both sides wait for each other**.

## 1. Measured capacity per layer (reference)

| Layer | Measured | Meaning |
|---|---|---|
| Native Windows anonymous pipe | 4096 B | Python os.pipe and subprocess PIPE |
| MSYS2 shell pipe | 65536 B | the bash cmd1 pipe cmd2 form |
| Node stream highWaterMark | 16384 B | a userland buffer stacked on the OS pipe |
| Node unconsumed stdout stall boundary | 131073 B | measured; not the plain sum of the two above |
| Python stdio buffer | 8192 B | io.DEFAULT_BUFFER_SIZE, a separate layer from the pipe |

## 2. Measured deadlock boundaries

| Pattern | Passes | Deadlocks | Reading of the boundary |
|---|---|---|---|
| Python: wait first, child writes to stdout | up to 4096 B | 4097 B and above | the pipe capacity itself |
| Node: no data listener, waiting for close | up to 131072 B | 131073 B and above | stream buffer plus libuv read-ahead |
| Parent writes all input, reads later (streaming filter child) | up to 9216 B | 9217 B and above | 4096 plus 4096 plus 1024 |
| Parent writes all input, reads later (slurping child) | 4 MB still passes | — | the child keeps draining, so nothing blocks |

## 3. Choosing how to run a child

| Situation | Choose | Watch out for |
|---|---|---|
| Output is small with a known ceiling | one high-level call (run, check_output, spawnSync) | everything is held in memory. Document the ceiling in code |
| Output is large or unbounded | redirect to a file descriptor | you own temp-file cleanup and disk headroom |
| Output must be handled live | consume line by line | the child stdio buffer delays it. Run the child unbuffered |
| You also need stderr | consume both streams at once (thread, async, or a high-level call) | reading only one side always deadlocks |
| You only need stderr text and order is irrelevant | merge stderr into stdout | the two streams buffer differently, so ordering scrambles |
| The child also takes a large input | write and read at the same time (separate thread or a combined API) | writing everything and reading later is a two-way deadlock |
| Output is discarded entirely | point it at the null device | opening a PIPE and ignoring it is the worst case |

## 4. Safe call patterns

### Python

```python
import subprocess

# (1) small output: take it all at once. Both streams are drained for you
r = subprocess.run(cmd, capture_output=True, timeout=60)

# (2) large output: land it in files, and only then is wait-first safe
with open("/tmp/demo/out.log", "wb") as fo, open("/tmp/demo/err.log", "wb") as fe:
    p = subprocess.Popen(cmd, stdout=fo, stderr=fe)
    rc = p.wait(timeout=600)

# (3) live handling: consume line by line, holding one line at a time
p = subprocess.Popen(cmd, stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
                     text=True, bufsize=1)
for line in p.stdout:
    handle(line)
p.wait(timeout=600)

# (4) large input plus large output: let one call do the feeding and draining
out, err = p2.communicate(payload, timeout=600)
```

**Forbidden patterns**

```python
p = subprocess.Popen(cmd, stdout=subprocess.PIPE)
p.wait()                 # waits forever once the output exceeds the buffer
out = p.stdout.read()    # this line is never reached

p = subprocess.Popen(cmd, stdout=subprocess.PIPE, stderr=subprocess.PIPE)
out = p.stdout.read()    # a full stderr stops the child, so this read never ends
```

### Node.js

```javascript
const { spawn, execFile } = require("child_process");

// (1) small output: the 1 MB default ceiling reports an error instead of hanging
execFile(cmd, args, { maxBuffer: 4 * 1024 * 1024, timeout: 60000 }, cb);

// (2) large output: stream it straight into a file descriptor
const fd = fs.openSync("/tmp/demo/out.log", "w");
const child = spawn(cmd, args, { stdio: ["ignore", fd, "inherit"] });

// (3) consume both streams
const c = spawn(cmd, args, { stdio: ["ignore", "pipe", "pipe"] });
c.stdout.on("data", onOut);
c.stderr.on("data", onErr);      // without this line a full stderr stalls everything
c.on("close", onDone);

// (4) if you will not look at the output, do not create the pipe
spawn(cmd, args, { stdio: "ignore" });
```

**Forbidden pattern**

```javascript
const c = spawn(cmd, args, { stdio: ["ignore", "pipe", "pipe"] });
c.on("close", done);   // nobody consumes stdout or stderr, so close never fires
```

### Shell

```bash
# flow control is normal. A slow consumer only slows the producer down
producer | consumer

# break large intermediate results with a file
producer > /tmp/demo/stage1.tsv
consumer < /tmp/demo/stage1.tsv

# if the reader finishes first the producer is signalled. Check the codes
producer | head -n 100
echo "${PIPESTATUS[0]} ${PIPESTATUS[1]}"

# if progress logs arrive in clumps, run the producer unbuffered
PYTHONUNBUFFERED=1 producer.py | tee /tmp/demo/run.log
```

## 5. Diagnosing a hang, in five steps

1. **Confirm it is alive.** If both parent and child appear in the process list, nothing died — they are waiting.
2. **Sample CPU time twice.** An unchanged value means a **block**, not a spin loop. Measured example: 0.109375 then 0.109375.
3. **Sample progress twice.** Bytes written, output file size, last log line — check whether any of them moves.
4. **The decisive test: shrink the input.** If the same code stops hanging below a size, the cause is the **buffer**, not your logic.
   - Measured example: 65536 B exited normally (0), 400000 B was still blocked when killed (124), having accepted 65536 B.
5. **Read the order in the code.** Does a wait call come before the read? Is any piped stream left unconsumed?

| Observation | Verdict |
|---|---|
| Alive and CPU time frozen | blocked on a pipe (or some other I O wait) |
| Alive and CPU time climbing | a spin loop. Not a pipe problem |
| Passes when you shrink the size | **pipe buffer deadlock confirmed** |
| Hangs regardless of size | not a pipe problem. Suspect locks, network, or input |
| Child finished but parent did not | the parent never closed or never consumed a stream |

## 6. Review sentences you can paste

- What is the ceiling on this child output? If there is none, switch to a file or to streaming.
- stderr is opened as a pipe but I see no code consuming it. Reading one side only is a deadlock.
- The wait call sits before the read. Swap the order, or move to a combined API.
- You write the whole input before reading output. Against a streaming filter that is a two-way deadlock.
- There is no timeout. Every wait needs a ceiling, and the child needs an explicit kill after it.
- The test input is small, so this path has never been exercised. Add a sample larger than the buffer.
- Progress logs arrive in clumps. Attaching a pipe switches to block buffering. Run the producer unbuffered.

## 7. Checklist

- [ ] every stream opened as a pipe has **code consuming it**
- [ ] the wait call comes **after** the read (or a combined API is used)
- [ ] every wait call has a **timeout**
- [ ] the child is **killed explicitly** after a timeout (a failed wait does not mean it died)
- [ ] children with an unclear output ceiling go to a **file or a stream**
- [ ] the test sample is **larger than the buffer capacity**
- [ ] when feeding a large input, **writing and reading run together**
- [ ] logs whose order matters are **not merged** (merging scrambles them)
- [ ] children that must show progress run **unbuffered**
- [ ] if the output is unused, **no pipe is created**
- [ ] there is a path that **cleans up children** when the parent dies
- [ ] the production buffer capacity was **measured directly** (it may differ from development)

## 8. Do not

- ❌ leave a piped stream **unconsumed** — the most common cause by far
- ❌ **wait first, read later** — it only passes on small output
- ❌ **assume the child died** because the wait failed — measured: it was still alive
- ❌ pass a review on small samples only — the boundary is crossed only by real data
- ❌ **assume a buffer size from another environment** — one machine gave 4096, 65536 and 131072
- ❌ **misread a delayed progress log as a slow program** — it is only pooled in a buffer
- ❌ merge two order-sensitive streams and then **trust the ordering**
- ❌ wait without a timeout — it makes even the reproduction experiment impossible
