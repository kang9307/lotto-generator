한 글자의 폭은 1이 아니다 - 동아시아 폭 속성과 터미널 표가 어긋나는 자리

문자 수, 바이트 수, 표시 폭은 서로 다른 세 숫자이고 정렬은 그중 폭에 달렸다

2026-07-31 개발/인프라

서론: 표가 한글 줄에서만 어긋났다

운영 스크립트가 찍는 재고 표를 열었더니 영문 줄은 칸이 딱 맞는데 한글이 든 줄에서만 오른쪽으로 밀려 있었다. 코드를 봐도 이상한 곳이 없다. 모든 셀에 같은 함수를 쓰고, 같은 폭 값을 넘긴다. 그런데 화면에서는 어긋난다.

이 증상의 원인은 하나다. 패딩 함수가 세는 숫자와 터미널이 세는 숫자가 다르다. 파이썬의 ljust도, 자바스크립트의 padEnd도 「몇 글자인가」를 기준으로 공백을 채운다. 그런데 터미널은 「몇 칸을 차지하는가」로 그린다. 한글과 한자와 가나는 한 글자가 두 칸을 쓰므로, 글자 수를 맞추면 칸 수가 어긋난다.

여기서 다섯 번째 숫자가 등장한다. 하나의 문자열에 붙는 숫자는 이미 넷이었다. 바이트 수, 코드 유닛 수, 코드포인트 수, 그리고 사람이 한 글자로 인식하는 그래핌 수다. 그 넷의 차이는 이모지 하나가 11글자로 세지는 이야기에서 다뤘다. 이 글은 그 위에 얹히는 다섯 번째 숫자, 표시 폭만 다룬다.

  • 표시 폭은 앞의 네 숫자 어느 것으로도 유도되지 않는다. 뒤에서 보겠지만 3바이트짜리 문자 중에 폭 1도 있고 폭 2도 있다
  • 표시 폭은 문자의 성질만으로 결정되지도 않는다. 유니코드가 「애매함」이라고 못 박아 둔 부류가 따로 있고, 그 폭은 환경이 정한다
  • 그래서 이 글의 결론은 「폭 2로 세세요」가 아니다. 폭을 세야 하는 자리와 글자 수를 세야 하는 자리를 가르는 것, 그리고 어긋나도 읽히게 만드는 것이 현실적인 목표다

실행 환경. 아래 모든 숫자는 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. Python 3.13.3 (win32)의 내장 unicodedata(유니코드 데이터 15.1.0)와 Node.js v22.16.0 (win32)를 썼다. 표준 출력 인코딩은 UTF-8로 고정했다.

없는 라이브러리는 없다고 적는다. 이 환경에는 파이썬 wcwidth 패키지가 설치되어 있지 않고, Node의 string-width 패키지도 없다. 그래서 아래 모든 폭 값은 스크립트 안에서 직접 계산한 것이다. 외부 구현의 판단이 아니라 유니코드 속성 값에서 바로 나온 숫자라는 뜻이다.

★렌더링에 의존하지 않았다. 이 글의 판단은 전부 코드포인트와 폭 속성 값으로 했다. 「내 터미널에서 이렇게 보인다」는 근거로 쓰지 않았고, 문자는 전부 U+XXXX로 병기했다. 실제 화면에 몇 칸으로 그려지는가는 폰트와 터미널이 정하는 별개의 문제이며, 그 경계를 이 글의 3절에서 따로 다룬다.

이 글이 다루지 않는 것. 바이트와 코드 유닛과 그래핌의 차이는 ZWJ 시퀀스와 길이 검증에 있다. 같은 글자가 두 가지 코드포인트열이 되는 정규화 원리는 NFC와 NFD에 있고, 여기서는 4절에서 정규화가 폭에 미치는 영향만 본다. 인코딩을 잘못 읽어 글자가 깨지는 것은 cp949와 UTF-8 쪽이며 이 글과 무관하다.

1. 글자 수는 같은데 폭이 다르다

먼저 증상을 그대로 재현했다. 품목·담당·수량 세 칸짜리 표를 str.ljust로 그린 것이다. 어긋난 출력을 손대지 않고 그대로 싣는다.

첫 두 줄이 이 글 전체의 요약이다. kim과 김철수는 둘 다 3글자다. 그런데 바이트는 3과 9로 다르고, 칸 수는 3과 6으로 다르다. ljust(8)은 양쪽에 똑같이 5칸의 공백을 넣었다. 함수는 공정하게 일했는데 결과가 3칸 어긋난다.

  • 문자 수는 같은데 폭이 다르다. 그래서 문자 수로 만든 패딩은 반드시 어긋난다
  • 바이트 수로 세도 틀린다. 김철수는 9바이트인데 폭은 6칸이다. 3바이트가 2칸이므로 비율조차 정수가 아니다
  • 어긋나는 크기는 그 셀에 든 넓은 문자 개수와 정확히 같다. 김철수의 넓은 문자는 3개이고 어긋난 크기도 3칸이다
  • 영문만 있는 표는 영원히 문제가 없다. 아스키 구간에서는 세 숫자가 전부 일치하기 때문이다. 사고는 한글이 한 칸 들어가는 순간 시작된다

2. 폭 속성 여섯 가지 - W, F, H, Na, A, N

유니코드 표준 부속서 11번(UAX #11)이 정의하는 값은 여섯 개다. 각각에 해당하는 문자를 하나씩 골라 unicodedata.east_asian_width로 실측했다.

  • W와 F의 차이는 유래다. W는 원래부터 넓은 문자이고, F는 좁은 문자에 대응하는 전각 형태로 따로 만들어진 문자다. 결과는 둘 다 2칸으로 같다
  • H는 반대 방향이다. 넓은 문자에 대응하는 반각 형태이고 1칸이다. 반각 가타카나가 여기 속한다
  • 원화 기호 U+20A9이 H라는 점이 눈에 띈다. 통화 기호인데 반각으로 분류돼 있다. 4절에서 이 값이 왜 중요한지 나온다
  • N은 「모르는 문자」가 아니라 「동아시아 레거시 인코딩에 없던 문자」다. 아랍 문자나 그림문자가 여기 들어간다. 실용적으로는 1칸으로 다룬다
  • A는 값이 하나 더 있는 게 아니라 값이 결정되지 않은 상태다. 이 부류가 이 글의 절반이다
  • UAX #11은 이 속성이 렌더링 폭이 아니라고 명시한다. 표준 문서의 표현으로 실제 글리프의 표시 폭은 폰트가 정하고 레이아웃이 다시 조정한다. 폭 속성은 고정폭 문맥에서의 관례를 정리한 것이지 화면 측정치가 아니다

3. 애매폭(A)이 진짜 문제다

UAX #11은 애매폭에 대해 문자 코드에 담기지 않은 추가 정보가 있어야 폭이 정해진다고 적고 있다. 언어 태그, 스크립트 식별, 연결된 폰트, 데이터의 출처, 명시적 마크업 같은 맥락을 쓰라는 것이고, 맥락을 알 수 없으면 기본적으로 좁게 처리하라고 권한다. 즉 폭이 문자의 성질만으로 결정되지 않는 유일한 부류다.

어느 문자가 여기 속하는지가 관건이다. 일상적으로 쓰는 문자 39개를 골라 실측했다.

39개 중 33개가 애매폭이었다. 이 목록을 읽으면 왜 이것이 진짜 문제인지 바로 보인다.

  • 그리스 문자와 키릴 문자 전체가 애매폭이다. 수식이 든 리포트, 통계 출력, 러시아어 데이터가 전부 여기 걸린다
  • 따옴표와 말줄임표가 애매폭이다. U+201C, U+201D, U+2026은 워드프로세서가 자동으로 넣어 주는 문자라 사용자 입력에 무심코 섞인다
  • 상자 그리기 문자가 통째로 애매폭이다. U+2500, U+2502, U+250C. 테두리를 두른 표를 그리면 내용이 아니라 테두리부터 환경에 따라 갈린다
  • 바로 옆 문자가 다른 값인 경우가 있다. U+2588(full block)은 A인데 U+2591(light shade)은 N이다. 진행 막대를 이 둘로 그리면 같은 줄 안에서 규칙이 섞인다
  • 통화 기호도 갈린다. 유로 U+20AC은 A인데 파운드 U+00A3은 Na다. 「기호는 다 애매폭」이라는 어림짐작은 틀린다

그래서 같은 문자열이 환경에 따라 다른 폭이 된다. 애매폭을 1로 볼 때와 2로 볼 때를 나란히 계산했다.

  • U+2400 구간에 159자. 원문자 번호 U+2460 계열. 목록 표시에 자주 쓴다
  • U+0300 구간에 160자. 그리스 문자와 결합 부호가 섞여 있다. 결합 부호는 6절에서 따로 다룬다
  • U+2100 구간에 53자. 섭씨 U+2103, 번호 U+2116 같은 단위 기호가 여기 있다
  • 합쳐서 1,271자라는 것은 「드문 문자」가 아니라는 뜻이다. 사무 문서와 리포트에서 매일 쓰는 것들이 여기 몰려 있다

여기서 이 글의 두 번째 논지가 나온다. 폭은 문자의 성질만으로 결정되지 않는다. 1,271자에 대해서는 유니코드가 답을 주지 않고 환경에 위임한다. 그러므로 모든 터미널·모든 폰트에서 동일한 정렬은 원리적으로 불가능하다.

4. 전각과 반각 - 같은 A가 두 개의 코드포인트

2절의 F와 H가 실무에서 어떻게 나타나는지 본다. 알파벳 A처럼 보이는 문자가 유니코드에 두 개 있다.

이 결과가 실무에서 두 가지 사고를 낸다.

  • 글자 수는 같은데 폭이 두 배다. 전각으로 입력된 주문번호는 8글자 그대로인데 16칸을 먹는다. 문자 수 기준 검증은 전부 통과하고 표만 어긋난다
  • 문자열 비교가 실패한다. INV-2026과 전각으로 친 같은 값이 같지 않다. 일본어·중국어 입력기에서 전각 모드로 친 값이 그대로 들어오면 조회가 안 된다
  • NFC는 이것을 고치지 못한다. 전각을 아스키로 접는 것은 호환 정규화(NFKC)이고, 일반적으로 쓰는 NFC는 U+FF21을 그대로 둔다. 두 정규화의 차이는 NFC와 NFD 글에 있다
  • NFKC를 걸면 폭이 16에서 8로 반이 된다. 즉 정규화 지점을 어디에 두느냐에 따라 같은 입력의 폭이 달라진다

반대 방향인 반각도 본다. 반각 가타카나와 반각 원화 기호다.

  • 반각 가타카나는 4글자·12바이트·4칸이다. 아스키가 아닌데 폭은 1이다. 「비아스키는 폭 2」라는 가정이 여기서 깨진다
  • NFKC를 걸면 폭이 4에서 8로 두 배가 된다. 4-2와 반대 방향이다. 즉 정규화는 폭을 줄이기도 하고 늘리기도 한다
  • 탁점이 붙은 반각 가나는 코드포인트가 두 개다. U+FF8A과 U+FF9E이고, NFKC를 걸면 U+30D0 하나가 된다. 글자 수와 폭이 동시에 바뀐다
  • 원화 기호 U+20A9이 폭 1이라는 점은 금액 열을 그릴 때 직접 영향을 준다. 통화 기호라고 2칸을 잡아 두면 그만큼 어긋난다

5. 폭 기준으로 세는 함수

이제 고친다. 필요한 것은 문자 수가 아니라 폭 합계로 공백을 계산하는 함수다. 외부 패키지가 없는 환경이므로 표준 라이브러리만으로 직접 만들었다.

# width_util.py   (Python 3.13.3, unicodedata 15.1.0)
import unicodedata

ZERO_CATS = ("Mn", "Me", "Cf")     # combining, enclosing, format

def char_width(ch, ambiguous=1):
    if unicodedata.category(ch) in ZERO_CATS:
        return 0                            # gate 1: advances nothing
    e = unicodedata.east_asian_width(ch)
    if e in ("W", "F"):
        return 2                            # gate 2: always two columns
    if e == "A":
        return ambiguous                    # gate 3: the environment decides
    return 1

def str_width(s, ambiguous=1):
    return sum(char_width(c, ambiguous) for c in s)

def pad(s, n, ambiguous=1, align="l", fill=" "):
    gap = n - str_width(s, ambiguous)
    if gap <= 0:
        return s
    if align == "l":
        return s + fill * gap
    if align == "r":
        return fill * gap + s
    left = gap // 2
    return fill * left + s + fill * (gap - left)

def trunc(s, n, ambiguous=1, ellipsis="..."):
    if str_width(s, ambiguous) <= n:
        return s
    room = n - str_width(ellipsis, ambiguous)
    out, acc = [], 0
    for ch in s:
        cw = char_width(ch, ambiguous)
        if acc + cw > room:
            break
        out.append(ch)
        acc += cw
    return "".join(out) + ellipsis

ambiguous가 인자로 노출돼 있는 것이 요점이다. 애매폭을 함수 안에 박아 넣지 않고 호출하는 쪽이 결정하게 만들었다. 3절에서 본 대로 그 값은 환경이 정하는 것이지 함수가 아는 값이 아니기 때문이다. 이 함수로 1절의 표를 다시 그렸다.

  • 말줄임표 자체의 폭도 예산에 넣어야 한다. 위 함수는 ...의 폭을 먼저 빼고 남은 자리를 채운다
  • 넓은 문자 경계에서 반 칸이 남는 경우가 있다. 남은 자리가 1칸인데 다음 문자가 2칸이면 넣을 수 없다. 위 구현은 그 자리를 공백으로 남긴다
  • 검증은 눈이 아니라 함수로 한다. 완성된 줄을 다시 str_width에 넣어 전부 같은지 보는 것이 유일하게 믿을 수 있는 확인이다

6. 조합 문자와 0폭 - 단순 합산이 또 틀리는 자리

5절 함수에 관문이 세 개였다. 그중 첫 번째 관문이 왜 필요한가가 이 절이다. 폭 속성 값이 실제 칸 수와 어긋나는 문자들이 있다.

  • 0폭을 아는 함수는 8과 8로 같은 값을 낸다. 범주가 Mn인 U+030A과 U+0308을 0으로 처리했기 때문이다
  • 이 차이는 눈에 보이지 않는다. 화면에는 같은 단어가 보이는데 표만 어긋난다

그래서 폭 함수의 관문 순서가 고정된다.

  • 관문 1: 일반 범주가 Mn, Me, Cf이면 0. 폭 속성이 무엇이든 무시한다
  • 관문 2: 폭 속성이 W 또는 F이면 2. 여기까지가 확정된 부분이다
  • 관문 3: 폭 속성이 A이면 호출자가 넘긴 값. 함수가 정하지 않는다
  • 그 밖에는 1. H, Na, N이 모두 여기 들어간다
  • 관문 1이 반드시 먼저여야 한다. U+302A이 관문 2에 먼저 걸리면 2가 되어 두 칸을 과다 계산한다

    U+2524  [┤]  eaw=A
  every one of them is A. the frame itself is undecided, not the content.

이것이 가장 지독한 경우다. 테두리 문자 열한 개가 전부 애매폭이다. 위 표는 애매폭을 1로 가정해 그린 것이므로, 애매폭을 2로 처리하는 환경에서는 내용이 아니라 테두리부터 두 배로 늘어나 무너진다. 내용 셀을 아무리 정확히 계산해도 프레임이 흔들리면 소용이 없다.

  • 상자 문자로 그린 표는 이식성이 없다. 같은 출력이 어떤 환경에서는 맞고 어떤 환경에서는 두 배로 벌어진다
  • 대안은 아스키 테두리다. -, |, +는 전부 Na라 흔들리지 않는다. 모양은 투박해도 폭은 확정이다
  • 진행 막대도 같은 문제다. U+2588은 A이고 U+2591은 N이라 한 막대 안에서 규칙이 섞인다
  • 표 라이브러리를 쓸 때도 이 값을 확인해야 한다. 라이브러리가 어떤 관례를 쓰는지 모르면 결과를 예측할 수 없다

8-4에서 한글만 든 셀은 안정으로 나오고 café가 불안정으로 나온 것이 이 판정의 핵심이다. 한글 음절은 전부 W라 폭이 확정이고, é는 A라 환경에 달렸다. 「한글이 문제」라는 통념과 결과가 반대다.

  • 애매폭이 든 셀만 표시하면 된다. 전수 검사가 아니라 폭 속성이 A인 문자와 범주가 Mn·Me·Cf인 문자만 찾으면 된다
  • 인용 부호 「」는 안정이다. U+300C 계열은 W로 확정돼 있다. 반면 U+201C 계열은 A다
  • 가장 싼 해결은 공백 정렬을 버리는 것이다. 탭이나 등호로 구분하면 폭 계산 자체가 필요 없다
  • 구분자 방식은 기계가 읽기에도 낫다. 공백 정렬된 표는 파싱할 때 열 경계를 다시 추측해야 한다
  • 정말 표가 필요하면 애매폭을 표에서 몰아낸다. 테두리를 아스키로 바꾸고, 원문자 번호를 괄호 숫자로 바꾸면 흔들림이 사라진다
  • 완벽한 정렬은 목표가 아니다. 어긋나도 읽히게 만드는 것이 목표다. 열이 한 칸 밀린 표는 읽을 수 있지만, 열이 뒤섞인 표는 못 읽는다

파이썬은 unicodedata.east_asian_width가 표준 라이브러리에 있어서 속성 값을 바로 물어볼 수 있다. Node에는 그런 API가 없다. Intl.Segmenter는 있지만 그것은 그래핌 경계를 나누는 도구이지 폭을 알려주지 않는다. 그래서 범위 표를 직접 들고 다녀야 하고, 직접 만든 표에는 애매폭 분류가 아예 빠지기 쉽다. 위 표는 U+03B1과 U+2500을 조용히 1칸으로 처리한다.

  • 범위 표는 유니코드 버전에 묶인다. 이 글의 파이썬은 유니코드 데이터 15.1.0을 쓰는데, 유니코드가 공개한 속성 파일의 최신판은 17.0.0이다. 새 문자가 추가되면 손으로 만든 표는 그만큼 뒤처진다
  • 미할당 코드포인트의 기본값도 알아야 한다. 속성 파일은 기본을 N으로 두되 U+3400..U+4DBF, U+4E00..U+9FFF, U+F900..U+FAFF과 2·3면의 미지정 영역은 W로 기본값을 준다. 범위 표를 만들 때 이 규칙을 빠뜨리면 미래 한자가 1칸이 된다
  • 양쪽 런타임이 섞인 파이프라인이 가장 위험하다. 파이썬이 폭으로 정렬한 것을 Node가 코드 유닛으로 다시 자르면 결과는 어느 쪽 기준도 아니게 된다
  • 구현을 고를 때는 애매폭을 어떻게 다루는지부터 확인한다. 옵션이 없는 구현은 이미 한쪽으로 결정을 내려 둔 것이다

점검 목록. ① 패딩과 자르기가 문자 수가 아니라 폭 합계를 쓰는가. ② 폭 함수가 범주 Mn·Me·Cf를 0으로 먼저 거르는가. ③ 애매폭 값이 호출자에게 노출돼 있는가, 아니면 함수 안에 박혀 있는가. ④ 표 테두리에 U+2500 계열을 쓰고 있지는 않은가. ⑤ 전각 입력(U+FF01~U+FF60)을 경계에서 NFKC로 접는가. ⑥ 완성된 줄을 다시 폭 함수에 넣어 전부 같은지 검증하는가. ⑦ 정렬이 정말 필요한 자리인가, 구분자로 바꿀 수 있는 자리인가.

눈으로 확인하지 않은 것. 이 글의 모든 판단은 속성 값과 코드포인트로 했다. 애매폭 문자가 특정 터미널에서 실제로 몇 칸으로 그려지는가, 반각 가타카나가 어떤 폰트에서 어떻게 보이는가, 이모지가 두 칸으로 그려지는가는 확인하지 않았고 확인할 수도 없다. 환경마다 다르기 때문이다. 그것이 바로 이 글의 결론이다. 렌더링은 별개의 문제이고, 코드가 할 수 있는 최선은 속성 값에 근거한 예측을 내놓는 것까지다.

# 표시 폭 정렬 — 복붙용 대조표와 패딩 함수

> 출처: braindetox.kr — 한 글자의 폭은 1이 아니다
> 근거: Windows 10 / Python 3.13.3 (unicodedata 15.1.0) / Node.js v22.16.0 실행 검증
> wcwidth, string-width 미설치 환경에서 표준 라이브러리만으로 계산

## 1. 한 문자열에 붙는 다섯 숫자

| 숫자 | 무엇을 세나 | 예: 김철수 | 예: café (U+00E9) |
|---|---|---|---|
| UTF-8 바이트 | 전송·저장 크기 | 9 | 5 |
| UTF-16 코드 유닛 | JS 문자열 길이 | 3 | 4 |
| 코드포인트 | 유니코드 문자 개수 | 3 | 4 |
| 그래핌 | 사람이 세는 글자 | 3 | 4 |
| **표시 폭** | **터미널 칸 수** | **6** | **1 또는 2 (환경)** |

## 2. 동아시아 폭 속성 6종 대조표

| 값 | 이름 | 칸 수 | 실측 예 |
|---|---|---|---|
| `W` | Wide | 2 | U+4E00, U+D55C, U+3042 |
| `F` | Fullwidth | 2 | U+FF21, U+FF10 |
| `H` | Halfwidth | 1 | U+FF76, U+20A9 |
| `Na` | Narrow | 1 | U+0041, U+0024 |
| `A` | Ambiguous | **환경이 정함** | U+03B1, U+00B1 |
| `N` | Neutral | 1 | U+0627, U+2603 |

- 2칸을 뜻하는 값은 `W`와 `F` 둘뿐
- `A`는 값이 아니라 **미결정 상태**. UAX #11은 맥락이 없으면 좁게 처리하라고 권고
- 전체 코드포인트 스캔: W 182,417 / F 104 / H 123 / Na 111 / A 138,739 / N 790,570
- A 중 실제 할당 문자는 **1,271자** (나머지는 사용자 정의 영역)

## 3. 폭 기준 패딩 함수 (Python, 의존성 없음)

```python
import unicodedata

ZERO_CATS = ("Mn", "Me", "Cf")

def char_width(ch, ambiguous=1):
    if unicodedata.category(ch) in ZERO_CATS:
        return 0                          # 관문 1: 반드시 먼저
    e = unicodedata.east_asian_width(ch)
    if e in ("W", "F"):
        return 2                          # 관문 2
    if e == "A":
        return ambiguous                  # 관문 3: 호출자가 결정
    return 1

def str_width(s, ambiguous=1):
    return sum(char_width(c, ambiguous) for c in s)

def pad(s, n, ambiguous=1, align="l", fill=" "):
    gap = n - str_width(s, ambiguous)
    if gap <= 0:
        return s
    if align == "l":
        return s + fill * gap
    if align == "r":
        return fill * gap + s
    left = gap // 2
    return fill * left + s + fill * (gap - left)

def trunc(s, n, ambiguous=1, ellipsis="..."):
    if str_width(s, ambiguous) <= n:
        return s
    room = n - str_width(ellipsis, ambiguous)
    out, acc = [], 0
    for ch in s:
        cw = char_width(ch, ambiguous)
        if acc + cw > room:
            break
        out.append(ch)
        acc += cw
    return "".join(out) + ellipsis
```

|---|---|---|---|
| U+0301 결합 악센트 | A | Mn | **0** |
| U+302A 성조 부호 | **W** | Mn | **0** |
| U+FE0F 변이 선택자 | A | Mn | **0** |
| U+200B 0폭 공백 | N | Cf | **0** |
| U+200D 결합자 | N | Cf | **0** |

- 폭 속성만 더하면 U+302A에 2가 붙어 **두 칸 과다 계산**
- 그래서 범주 검사(관문 1)가 폭 속성 검사보다 **먼저** 와야 함
- UAX #11도 결합 부호는 폭 속성을 문자 진행폭과 연결할 수 없다고 명시

## 6. 전각·반각 요약

| 문자 | 코드포인트 | 폭 속성 | UTF-8 | 칸 |
|---|---|---|---|---|
| A | U+0041 | Na | 1 B | 1 |
| Ａ | U+FF21 | F | 3 B | 2 |
| ｶ | U+FF76 | H | 3 B | 1 |
| ₩ | U+20A9 | H | 3 B | 1 |
| 一 | U+4E00 | W | 3 B | 2 |

- 같은 3바이트인데 폭이 1과 2로 갈림 → **바이트로 폭을 유도할 수 없음**
- NFKC는 전각을 아스키로 접어 폭을 절반으로(16→8), 반각 가나는 정상형으로 펴 폭을 두 배로(4→8)
- NFC는 U+FF21을 그대로 둠. 전각 문제는 NFC로 안 풀림

## 8. 점검 목록

- [ ] 패딩·자르기가 문자 수가 아니라 **폭 합계**를 쓴다
- [ ] 폭 함수가 범주 `Mn`/`Me`/`Cf`를 **0으로 먼저** 거른다
- [ ] 애매폭 값이 **호출자에게 노출**돼 있다 (함수 안에 박혀 있지 않다)
- [ ] 표 테두리에 U+2500 계열 대신 아스키 `-` `|` `+`를 쓴다
- [ ] 전각 입력을 경계에서 NFKC로 접는다
- [ ] 완성된 줄을 **다시 폭 함수에 넣어** 전부 같은지 검증한다
- [ ] 정렬이 꼭 필요한 자리인지, 탭·등호 구분자로 바꿀 수 있는지 확인했다
- [ ] 범위 표를 손으로 만들었다면 미할당 기본값(N, 단 CJK 구간은 W)을 반영했다
- [ ] 파이썬과 Node가 섞인 파이프라인에서 양쪽 기준이 같은지 확인했다

## 9. 하지 말 것

- 표시 폭을 **바이트 수에서 유도**하는 것 — 3바이트에 폭 1도 있고 2도 있다
- 애매폭을 **함수 안에 상수로** 박는 것 — 환경이 정할 몫이다
- 상자 그리기 문자로 **이식성 있는 표**를 그리려는 것 — 테두리 11자가 전부 A다
- 범주 검사 없이 **폭 속성만 합산**하는 것 — U+302A가 2칸으로 세어진다
- 「완벽한 정렬」을 목표로 삼는 것 — 어긋나도 읽히게 만드는 것이 현실적이다
- 눈으로 보고 **다 맞았다고 판정**하는 것 — 내 터미널의 애매폭 관례일 뿐이다
