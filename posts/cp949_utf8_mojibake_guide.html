한글이 깨지는 지점을 특정하는 법 - cp949와 UTF-8, 두 종류의 인코딩 오류

깨진 모양으로 원인을 역추적하고, 복구 가능한 손상과 불가능한 손상을 가르는 법

2026-07-30 개발/인프라

서론: 「깨졌다」는 진단이 아니다

거래처에서 받은 CSV를 열었더니 한글이 전부 이상한 글자로 보인다. 이때 대부분의 대응은 두 가지다. 인코딩 설정을 이것저것 바꿔 보거나, 상대에게 다시 보내 달라고 한다. 둘 다 틀린 방법은 아니지만 순서가 뒤바뀌었다. 먼저 알아야 할 것은 이 파일이 고칠 수 있는 상태인지 아닌지다.

인코딩 오류는 두 종류뿐이다. 이 구분이 이 글의 전부라고 해도 좋다.

  • ① 바이트는 맞는데 해석을 틀린 것. 파일 안에는 원본 바이트가 온전히 들어 있고, 읽는 쪽이 엉뚱한 인코딩을 적용해 화면에만 이상하게 보이는 상태다. 완전히 복구된다.
  • ② 변환 과정에서 정보가 사라진 것. 누군가 이미 잘못 읽은 결과를 저장했거나, 대상 인코딩에 없는 문자를 물음표로 바꿔 버렸다. 원문은 돌아오지 않는다.

겉모습만 보면 둘 다 「글자가 깨졌다」로 똑같다. 그런데 ①은 명령 한 줄로 끝나고, ②는 원본을 다시 받는 것 말고 방법이 없다. 어느 쪽인지 먼저 판별하지 않으면, 이미 죽은 파일을 붙들고 하루를 보내게 된다.

이 글은 그 판별법을 다룬다. 「UTF-8을 쓰세요」 같은 이야기는 하지 않는다. 그 조언은 이미 깨진 화면 앞에 앉은 사람에게 아무 도움이 안 되고, 관공서와 은행이 여전히 cp949로 파일을 보내는 현실도 바꾸지 못한다. 대신 깨진 모양을 보고 원인을 역추적하는 표를 만들고, 그 표의 모든 칸을 직접 실행해 채웠다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 셸은 GNU bash 5.2.37 (MSYS2/MinGW64), 도구는 Node.js v22.16.0 (win32), Python 3.13.3, GNU libiconv 1.18이다. 시스템 ANSI/OEM 코드페이지는 둘 다 949이고, 셸 로케일은 LANG이 빈 값에 LC_CTYPE=C.UTF-8이다.

스크립트는 모두 파일로 저장해 실행했다. 한글과 역슬래시가 섞인 코드를 셸 인자나 히어독으로 넘기면 조용히 변형된다. 인용 규칙 자체가 궁금하면 셸 인용 규칙을 보라. 예제 경로는 /tmp/demo, ~/work 같은 자리표시자로 옮겨 적었다.

이 글이 다루지 않는 것. 같은 글자가 유니코드 안에서 두 가지 코드포인트열이 되는 정규화 문제는 NFC와 NFD에서 다뤘다. 이 글은 유니코드와 레거시 인코딩 사이의 변환만 파고든다. 한글 음절을 정규식 범위로 다루는 산술은 한글 정규식 함정에, 파일명에 공백과 개행이 섞여 파이프라인이 깨지는 문제는 find와 xargs의 공백 함정에 있다. 여기서 파일명은 인코딩 측면만 본다.

1. 같은 글자, 다른 바이트 - 3바이트와 2바이트

모든 문제의 출발점은 단순하다. 같은 「한글」이 인코딩에 따라 다른 바이트가 된다. 나란히 찍어 봤다.

읽는 법은 이렇다. UTF-8은 한글 한 글자를 3바이트로, cp949는 2바이트로 쓴다. 아스키 문자는 양쪽 모두 1바이트이고 값도 같다. 그래서 영문과 숫자만 있는 파일은 인코딩을 틀려도 아무 일이 없다. 사고는 한글이 들어간 순간부터 시작된다.

여기서 중요한 사실이 하나 나온다. 「한」과 「가」는 euc-kr과 cp949에서 바이트가 완전히 같다. cp949는 euc-kr을 확장한 것이라 겹치는 영역이 대부분이다. 그래서 두 이름을 섞어 써도 대체로 문제가 없다.

그런데 「똠」에서 갈린다. 이 글자는 euc-kr의 기본 2,350자 밖에 있고, cp949는 8C 63 2바이트로 표현한다. 반면 이 환경의 Python euc_kr 코덱은 같은 글자를 8바이트로 만들었다. 조합용 자모를 늘어놓는 옛 방식을 쓴 것이다. 이 차이가 실무에서 어떤 사고를 내는지는 10절에서 다시 본다.

1.1 cp949가 아예 담지 못하는 것

  • 유로 기호도 들어간다. A2 E6이다. 즉 변환 실패는 「한국 문자가 아니라서」 생기는 게 아니다
  • 간체 중국어는 못 담는다. cp949의 한자는 번체 계열이라 「简体」가 거부됐다
  • 이모지는 못 담는다. 유니코드 기본 다국어 평면 밖의 문자라 표현 자체가 없다
  • 자모로 분해된 한글도 못 담는다. 완성형 음절만 있고 조합용 자모 영역은 매핑이 없다. NFD 상태의 문자열을 cp949로 내보내려 하면 이 지점에서 터진다

두 방향이 전혀 다르게 생겼다. 이유는 1절의 3바이트 대 2바이트에 있다.

  • 방향 A (cp949를 UTF-8로). cp949의 2바이트 조합은 대부분 UTF-8 규칙에 맞지 않는다. UTF-8은 첫 바이트가 길이를 선언하고 뒤따르는 바이트가 특정 범위에 있어야 하는데, cp949 바이트는 그 규칙을 지키지 않기 때문이다. 그래서 대부분이 대체문자로 바뀐다. 9글자 중 6개가 대체문자였다
  • 방향 B (UTF-8을 cp949로). cp949는 2바이트씩 잘라 읽으므로 3바이트 단위로 쓰인 것을 계속 어긋나게 집어 든다. 그런데 그 조합이 우연히 유효한 한자나 한글로 매핑되는 경우가 많다. 그래서 「湲덉븸」처럼 읽을 수 있는 글자로 보이는데 뜻이 없는 결과가 나온다

이 비대칭이 진단에 결정적이다. 대체문자가 우글거리면 방향 A, 한자와 한글이 뒤섞여 있으면 방향 B다.

두 블록의 차이를 정확히 보자. 3-1에서는 재인코딩한 바이트가 원본과 완전히 일치했다(True). 바이트가 그대로였으니 올바른 인코딩으로 다시 읽는 것만으로 원문이 돌아왔다.

3-2에서는 11바이트가 27바이트로 늘어났다. 대체문자 하나가 UTF-8로 저장될 때 EF BF BD 3바이트를 차지하기 때문이다. 그리고 결정적으로, 이 3바이트에는 원래 어떤 바이트를 대신했는지에 대한 정보가 없다. 모든 실패가 같은 값으로 뭉개진다. 그래서 복구가 원리적으로 불가능하다.

실무 규칙. 대체문자를 보는 것은 괜찮다. 화면에 잠깐 나타난 것뿐이고 파일은 멀쩡하다. 위험한 것은 그 상태를 저장하는 것이다. 잘못 읽은 결과를 다시 쓰는 순간 ①이 ②로 바뀌고, 그 시점에 원본은 죽는다. 그래서 인코딩이 의심스러운 파일은 읽기 전용으로 열고, 확신이 서기 전에는 저장 버튼을 누르지 않는 것이 첫 번째 방어다.

  • ignore는 아무 흔적도 남기지 않는다. 가장 위험하다. 「가격 100 확정」은 문법적으로 완벽해 보여서 아무도 의심하지 않는다
  • xmlcharrefreplace는 숫자 참조로 바꿔 정보를 보존한다. HTML로 흘러가는 경로라면 이 방식이 손실을 막는다
  • 어느 쪽이든 대상 인코딩이 그 문자를 모른다는 사실 자체는 바뀌지 않는다. 근본 해결은 변환하지 않는 것이다

5. 「占쏙옙」의 정체 - 이중 손상의 증거

한국에서 인코딩 사고를 겪어 본 사람이라면 이 글자를 본 적이 있다. 이것이 어디서 오는지 단계별로 재현했다.

--- 3-6. where the infamous string comes from ---
step 1. real cp949 text
  한글 -> cp949 C7 D1 B1 DB
step 2. some layer decodes it as UTF-8 with replacement
  -> [�ѱ�]   U+FFFD U+0471 U+FFFD
step 3. that string is saved as UTF-8
  -> EF BF BD D1 B1 EF BF BD
step 4. a later reader opens those bytes as cp949
  -> [占싼깍옙]

the replacement char alone, put through the same two steps:
  U+FFFD as utf-8 : EF BF BD
  x2              : EF BF BD EF BF BD -> [占쏙옙]
  x3              : EF BF BD EF BF BD EF BF BD -> [占쏙옙占�]
  x4              : [占쏙옙占쏙옙]
  odd counts leave a dangling byte: cp949 eats 2 at a time, UTF-8 wrote 3

구조가 명확하다. 대체문자 두 개가 UTF-8로 저장되면 EF BF BD EF BF BD 6바이트가 된다. cp949는 두 바이트씩 읽으므로 EF BF, BD EF, BF BD 세 쌍으로 잘린다. 3바이트 단위로 쓴 것을 2바이트 단위로 읽었기 때문에 세 글자가 나온다. 6과 3의 최소공배수가 6이라 이 패턴이 정확히 반복된다.

실무적 결론이 중요하다. 이 문자열을 봤다면 복구 시도를 멈춰야 한다. 이것은 손상이 두 번 겹쳤다는 증거이고, 첫 번째 단계에서 이미 원본 바이트가 사라졌다. 두 번째 오독을 바로잡아도 나오는 것은 대체문자일 뿐이다.

--- 3-7. how to tell single damage from double damage ---
what you see          U+FFFD present  recoverable   meaning
------------------------------------------------------------------------------
ÇÑ±Û                  False           True          misread only, bytes intact
replacement run       True            False         bytes already destroyed
the infamous one      False           False         bytes already destroyed

세 번째 줄에 함정이 있다. 이중 손상된 문자열에는 대체문자가 남아 있지 않다. 두 번째 오독 과정에서 정상 한자와 한글로 매핑됐기 때문이다. 그래서 「대체문자가 없으니 괜찮다」는 판단이 틀린다. 대체문자의 부재는 무사함의 증거가 아니다. 특정 패턴을 따로 알아봐야 한다.

  • 남은 D1 B1은 우연히 유효한 UTF-8 2바이트 조합이라 문자 하나로 묶였다

  • 파일 내용을 섞어 쓰는 저장소에서는 같은 검색을 두 인코딩으로 두 번 돌려야 전수 조사가 된다
  • 근본 해결은 검색 옵션이 아니라 저장소를 한 인코딩으로 통일하는 것이다
  • 글롭 패턴도 같은 원리다. 확장자만으로 찾을 때는 둘 다 걸리지만, 한글 접두사로 찾으면 하나만 걸린다

여기서 배울 것은 파이프에는 인코딩 정보가 흐르지 않는다는 것이다. 파일에는 BOM을 붙일 수 있고 HTTP에는 헤더가 있지만, 파이프는 바이트만 전달한다. 양쪽이 각자 자기 기본값을 쓴다. 이 환경에서 시스템 코드페이지는 949인데 셸 로케일은 C.UTF-8이라, 한 기계 안에서 두 기본값이 충돌하고 있다.

8.1 PYTHONIOENCODING이 바꾸는 것과 바꾸지 않는 것

--- 6-3. PYTHONIOENCODING changes stdout encoding, nothing else ---

sys.getfilesystemencoding() = utf-8
[PYTHONIOENCODING=utf-8]
stdout.encoding = utf-8
[PYTHONIOENCODING=cp949]
stdout.encoding = cp949
[PYTHONIOENCODING=ascii]

--- 6-5. what PYTHONIOENCODING does NOT change ---
[unset]
locale.getpreferredencoding(False) = cp949
open() default encoding            = cp949
[PYTHONIOENCODING=cp949]
locale.getpreferredencoding(False) = cp949
open() default encoding            = cp949
[PYTHONUTF8=1]
locale.getpreferredencoding(False) = utf-8
open() default encoding            = utf-8

정확한 구분이 필요하다. PYTHONIOENCODING은 표준 출력의 인코딩만 바꾼다. 파일을 열 때의 기본 인코딩은 건드리지 않는다. 확인한 환경에서 그 값은 cp949였다.

  • 화면 출력이 깨지는 문제는 PYTHONIOENCODING으로 고쳐진다
  • 파일을 읽고 쓰는 인코딩이 문제라면 이 변수는 아무 효과가 없다. 증상만 보고 이 변수를 만지면 시간을 버린다
  • 파일 쪽까지 한꺼번에 UTF-8로 맞추려면 PYTHONUTF8=1이 필요하다. 실행해 보면 open() 기본값이 utf-8로 바뀌었다
  • 가장 확실한 방법은 환경 변수에 기대지 않고 파일을 여는 코드에서 인코딩을 명시하는 것이다. 환경 변수는 배포 환경마다 달라진다

이 구분이 3절 표의 마지막 행이다. 출력이 아예 없고 종료 코드가 0이 아니면 데이터는 무사하다. 인코딩 단계에 도달하기 전에 멈췄기 때문이다. 반대로 replace 처리를 붙이면 프로그램은 살지만 물음표만 남는다. 죽는 쪽이 데이터에는 더 안전하다.

Node는 다르다. 이 환경에서 항상 UTF-8로 썼고, 코드페이지가 949인데도 영향을 받지 않았다. 즉 같은 기계에서 Python과 Node의 출력 바이트가 다르다. 두 도구를 파이프로 엮으면 여기가 사고 지점이 된다.

8.3 LANG과 LC_ALL은 무엇을 바꾸나

--- 6-6. LANG / LC_ALL effect on this toolchain ---
LC_ALL=[]             6  chars   /   sort: A 한글
LC_ALL=[C]            6  chars   /   sort: A 한글
LC_ALL=[ko_KR.UTF-8]  2  chars   /   sort: A 한글
LC_ALL=[ko_KR.eucKR]  3  chars   /   sort:

「한글」의 글자 수를 세게 했더니 로케일에 따라 6, 6, 2, 3이 나왔다. 정답은 2다.

  • C 로케일에서는 바이트를 센다. UTF-8 6바이트라 6이 나왔다
  • ko_KR.UTF-8에서만 문자 단위로 세어 2가 나왔다
  • ko_KR.eucKR은 UTF-8 바이트를 2바이트 문자로 해석해 3이라는 엉뚱한 답을 냈다. 그리고 정렬은 출력을 내지 못했다
  • 즉 로케일은 도구가 바이트를 문자로 묶는 방식을 정한다. 글자 수, 정렬, 대소문자 변환이 모두 여기에 걸린다

결과가 분명하다. 이 클라이언트의 text()는 선언된 charset을 전혀 보지 않았다. euc-kr이라고 정확히 알려줘도 UTF-8로 디코드했고, 세 경우의 코드포인트가 완전히 같았다.

더 눈여겨볼 것은 마지막 줄이다. charset=euc-kr이라고 거짓으로 선언한 UTF-8 본문은 정상으로 읽혔다. 즉 이 경로에서 charset 헤더는 아무 역할도 하지 않는다. 헤더를 고쳐서 해결하려는 시도가 실패하는 이유가 여기 있다.

  • euc-kr과 windows-949 두 이름이 같은 결과를 냈다. 확장 음절까지 처리하는 같은 디코더로 연결된다
  • 엄격 모드는 유효성 검사 도구로 쓸 수 있다. 맞는 인코딩에서는 통과하고 틀린 인코딩에서는 예외를 던졌다. 4개 조합 전부 예상대로였다
  • 다만 6.4절에서 봤듯 유효성만으로 확정할 수는 없다. 후보를 좁히는 데 쓰고 최종 판단은 합의된 규격으로 해야 한다
  • Node에는 cp949로 인코딩하는 기능이 내장돼 있지 않다. 디코드는 되고 인코드는 안 된다. cp949 파일을 만들어 내보내야 하는 요구가 있으면 별도 방법이 필요하다

확인하지 못한 것도 분명히 적어 둔다. 브라우저가 HTML 문서를 렌더링할 때 charset 헤더와 meta charset을 어떤 우선순위로 쓰는지는 이 글에서 실행으로 검증하지 않았다. 위 결과는 스크립트에서 본문을 가져오는 경로에 대한 것이고, 문서 렌더링 경로와는 다른 규칙이 적용될 수 있다.

10. 경계에서 한 번만 변환하기

레거시와 사는 현실적인 방법은 하나다. 파일이 들어오는 지점에서 한 번 변환하고, 그 안쪽은 전부 UTF-8이라고 가정하는 것. 문제는 그 한 번의 변환이 조용히 실패할 수 있다는 점이다.

=== 9-1. plain UTF-8 to CP949, one file at a time ===
emoji.txt    FAILED: iconv: emoji.txt:1:7: cannot convert
euro.txt     OK
ext.txt      OK
zh.txt       FAILED: iconv: zh.txt:1:7: cannot convert

=== 9-2. exit codes matter. a silent pipeline loses this ===
exit code             : 1
bytes actually written:  ba b8 b0 ed bc ad 20
what got through     : 보고서
iconv stopped at the offending char and kept the prefix. truncation, not an empty file

이것이 가장 위험한 동작이다. 변환이 실패했는데 출력 파일은 이미 만들어져 있다. 그 안에는 실패 지점 앞부분만 들어 있다. 파일이 존재하고 내용도 정상으로 읽히니 절단됐다는 사실을 알아차릴 단서가 종료 코드뿐이다.

  • 변환을 자동화한 파이프라인이 종료 코드를 확인하지 않으면 데이터 일부가 조용히 사라진다
  • 절단은 파일 끝에서 일어나므로 앞부분만 열어 보는 검수는 이것을 절대 못 잡는다
  • 파이프로 엮은 경우 중간 명령의 실패가 가려질 수 있다. 종료 코드와 파이프에서 다룬 문제와 정확히 같은 구조다

10.1 실패를 넘기는 세 가지 방법

=== 9-3. the three escape hatches ===
-c           rc=1  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
//TRANSLIT   rc=0  result=[보고서 :-D]  bytes= ba b8 b0 ed bc ad 20 3a 2d 44 0a
//IGNORE     rc=0  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
-c drops it, //TRANSLIT approximates or drops, //IGNORE drops and still reports failure

//TRANSLIT 결과가 인상적이다. 이모지가 아스키 세 글자로 근사 표기됐다. 사람이 읽을 수는 있지만 원본이 아니다.

방식실패 시 동작측정된 종료 코드데이터 상태쓸 만한 상황
옵션 없음실패 지점에서 중단1뒷부분 전체 소실없음. 반드시 종료 코드 확인
-c못 옮기는 문자만 버림1그 문자만 소실실패를 알면서 진행할 때
//IGNORE버림0그 문자만 소실권하지 않음. 실패를 숨긴다
//TRANSLIT근사 표기로 치환0원본 아님, 읽을 수는 있음사람이 읽을 로그류

가장 위험한 조합은 //IGNORE와 종료 코드 미확인이다. 문자가 사라졌는데 성공으로 보고된다. 반대로 옵션 없이 돌리면 실패를 알려주지만 이미 절단된 파일이 남는다. 어느 쪽도 안전하지 않으므로 검증을 따로 붙여야 한다.

  • 다른 쪽은 8바이트로 변환했다. 채움 문자 하나에 조합용 자모 셋을 늘어놓는 옛 방식이다. 되돌려 읽으면 원문이 나오므로 손실은 없다
  • 문제는 바이트 수가 4배라는 것이다. 컬럼 길이 제한이 있는 곳으로 흘러가면 여기서 잘린다
  • 따라서 인코딩 이름만 맞춰 놓고 안심하면 안 된다. 파이프라인에 실제로 쓰이는 도구로 표본을 통과시켜 봐야 한다

10.3 변환을 검증하는 방법

결론은 단순하다. 변환한 것을 되돌려 변환해서 원본과 바이트가 같은지 비교하면 된다.

=== 9-6. round trip integrity check you can run in CI ===
original md5      : f765f0504efec35848a3c116a1c98d10
after round trip  : f765f0504efec35848a3c116a1c98d10
VERDICT: lossless

now the same check on a file that cannot survive:
original md5      : 4db91275cca0367a7fe3823751f802e8
after round trip  : 918226859d33c495cb4acde0bafc7e30
VERDICT: LOSSY - do not ship
diff             : 1c1 < 보고서 😀 --- > 보고서

첫 번째 파일에는 유로 기호가 들어 있었는데 해시가 완전히 일치했다. cp949에 유로 기호가 있으니 손실이 없다. 두 번째는 이모지가 있어 해시가 달라졌고, 차이를 출력해 보니 정확히 그 문자만 사라졌다.

이 검사는 몇 줄로 끝나고 판정이 명확하다. 변환을 자동화하는 모든 곳에 이 검사를 붙이는 것이 조용한 데이터 손실을 막는 유일한 방법이다.

12.1 레거시와 사는 법

관공서와 은행이 보내는 파일은 앞으로도 cp949일 것이다. 그 현실에서 지킬 원칙을 정리하면 이렇다.

  1. 변환은 경계에서 한 번만. 파일을 받는 지점에서 UTF-8로 바꿔 저장하고, 그 뒤 모든 코드는 인코딩을 모르게 만든다. 「여기는 cp949인가」를 묻는 코드가 생기기 시작하면 설계가 무너진 것이다
  2. 원본을 지운 뒤에 검증하지 않는다. 변환한 파일과 원본을 함께 두고 왕복 검사를 통과한 다음에 정리한다
  3. 내보낼 때는 상대의 인코딩으로. 상대가 cp949를 기대하면 내보내는 경계에서 다시 변환한다. 이때 cp949에 없는 문자가 섞여 들어갈 수 있으므로 왕복 검사가 더 중요하다
  4. 내부에서는 절대 섞지 않는다. 저장소 안에 두 인코딩이 공존하면 7절에서 본 것처럼 검색이 반쪽만 걸린다
  5. 이모지와 간체 중국어를 경계한다. 사용자 입력에 이것이 섞이면 cp949로 내보낼 때 반드시 손실이 난다. 입력 단에서 걸러 알려주는 것이 나중에 물음표를 발견하는 것보다 낫다
  6. 인코딩을 문서에 적는다. 6.4절에서 봤듯 바이트만으로는 확정할 수 없다. 주고받는 규격에 명시하는 것이 유일한 근본 해결이다

13. 이 글에서 확인하지 못한 것

확인하지 않은 것을 확인한 것처럼 적으면 이 글이 다음 사람을 잘못 이끈다. 한계를 명확히 밝힌다.

  • 스프레드시트 프로그램의 실제 동작. 6절에서 「레거시 리더」로 표현한 것은 cp949로 디코드하는 동작을 직접 재현한 것이고, 특정 스프레드시트 제품을 실행해 확인한 것이 아니다. 제품과 버전, 지역 설정에 따라 다를 수 있다
  • 브라우저의 문서 렌더링. 9절 결과는 스크립트가 본문을 가져오는 경로에 대한 것이다. meta charset과 HTTP 헤더의 우선순위, 브라우저의 인코딩 추측 동작은 실행으로 검증하지 않았으므로 단정하지 않는다
  • 데이터베이스 경계. 컬럼 문자셋과 커넥션 문자셋이 어긋날 때 무엇이 저장되는지는 확인하지 않았다. 이 글의 원칙(경계에서 한 번 변환, 왕복 검증)은 그대로 적용되지만, 구체적 동작은 쓰는 제품에서 확인해야 한다
  • 압축 파일의 이름 인코딩. zip 항목 이름을 어느 인코딩으로 저장하는지는 도구마다 다르다고 알려져 있으나 이 글에서 실행하지 않았다
  • 다른 운영체제. 7절의 파일명 재인코딩 결과는 이 환경 고유의 것일 수 있다. 파일명을 바이트열로 다루는 시스템에서는 결과가 다를 것으로 보이지만 확인하지 않았다
  • 메일 헤더와 첨부 파일명. 별도 인코딩 규칙이 있는 영역이고 다루지 않았다
  • 인코딩 자동 감지 라이브러리의 정확도. 6.4절에서 원리적 한계를 보였지만, 실제 도구들이 통계적으로 얼마나 잘 맞히는지는 측정하지 않았다

다만 확인하지 못한 것들에는 공통점이 있다. 전부 「저쪽이 어떻게 하는가」에 관한 질문이다. 그리고 이 글의 진단법은 저쪽의 동작을 알아야 성립하는 것이 아니다. 바이트를 직접 보는 방법은 어느 환경에서나 같다. 그것이 추측 대신 바이트를 보라고 하는 이유다.

결론: 먼저 물어야 할 것은 「고칠 수 있나」다

깨진 화면을 보면 인코딩 설정부터 만지고 싶어진다. 그런데 순서가 틀렸다. 첫 질문은 이 파일이 고칠 수 있는 상태인가다. 그 답에 따라 할 일이 완전히 달라진다.

실행해서 확인한 것을 요약하면 이렇다. 바이트가 온전한 오독은 전부 복구됐다. cp949 바이트를 latin-1로 읽어 놓았어도, 다시 인코딩해 바이트가 원본과 일치하는 것을 확인하고 올바른 인코딩으로 읽으면 원문이 그대로 돌아왔다. 화면이 아무리 흉하게 보여도 그렇다.

반면 대체문자가 개입한 순간 복구는 원리적으로 불가능해진다. 11바이트가 27바이트로 늘어나고, 늘어난 바이트에는 원래 값에 대한 정보가 없다. 그리고 그 상태를 다시 잘못 읽으면 특정 세 글자 패턴이 나오는데, 그것을 봤다면 복구 시도를 접고 원본을 다시 받는 것이 유일한 답이다. 그 판별을 위해 바이트에서 EF BF BD를 세는 것이 진단의 다섯 번째 단계였다.

그래서 결론은 「전부 UTF-8로 바꾸자」가 아니다. 그건 안 된다. 상대는 바뀌지 않고, 유효성 검사만으로는 인코딩을 확정할 수도 없다. 현실적인 결론은 변환 지점을 하나 정하고, 그 변환이 손실 없이 끝났는지 왕복으로 검증하고, 그 안쪽은 인코딩을 모르게 만드는 것이다. 그리고 무엇보다 추측하기 전에 바이트를 보는 것이다.

지금 당장 할 수 있는 일이 하나 있다. 인코딩을 변환하는 코드나 스크립트를 찾아, 그 변환의 종료 코드를 확인하고 있는지 보라. 확인하지 않고 있다면 그 파이프라인은 지금까지 조용히 데이터를 잘라 왔을 가능성이 있다. 그리고 그 사실은 파일 앞부분만 열어 보는 검수로는 절대 드러나지 않는다.

## 0. 대전제 — 인코딩 오류는 두 종류다

| 종류 | 무슨 일이 일어났나 | 복구 |
|---|---|---|
| **① 오독** | 바이트는 온전한데 읽는 쪽이 엉뚱한 인코딩을 적용 | **완전히 가능** |
| **② 소실** | 잘못 읽은 결과를 저장했거나, 대상 인코딩에 없는 문자를 치환 | **불가** |

**어느 쪽인지 먼저 판별한다.** ②를 붙들고 인코딩 설정을 바꾸는 것은 시간 낭비다.

## 1. 30초 판별 — 편집기로 열기 전에 바이트를 본다

```bash
FILE=./suspect.csv

od -An -tx1 -N 16 "$FILE"                                  # 앞 16바이트
iconv -f UTF-8 -t UTF-8 "$FILE" >/dev/null 2>&1; echo "utf8  ok=$?"
iconv -f CP949 -t UTF-8 "$FILE" >/dev/null 2>&1; echo "cp949 ok=$?"

# 대체문자(복구 불가 신호)가 몇 개 박혀 있나
od -An -tx1 "$FILE" | tr -d ' \n' | grep -o efbfbd | wc -l
```

- `ok=0` 이면 그 인코딩으로 유효하다
- 앞 3바이트가 `EF BB BF` 면 **UTF-8 BOM** — 인코딩이 확정된다(유일한 적극적 신호)
- 마지막 줄이 **0보다 크면 그 파일은 이미 죽었다.** 원본을 다시 받는다

| 첫 셀 앞 잡음 세 글자 | `ï»¿이름` | UTF-8 BOM을 latin-1 계열로 읽음 | 앞 3바이트 | **가능** (BOM만 제거) |
| 첫 셀 앞 한자 하나 | `癤우` | UTF-8 BOM을 cp949로 읽음 | 앞 3바이트 | **가능** |
| 아스키 물음표 박힘 | `보고서 ?? 첨부` | **인코딩** 단계에서 대상에 없는 문자 치환 | 물음표가 `3F` 인지 | **불가** |
| 출력이 아예 없음 | (빈 줄 + 예외) | 출력 인코딩이 문자를 표현 못 해 크래시 | 종료 코드, 표준 오류 | 데이터는 **온전** |

**대소문자 규칙이 방향을 알려준다.** 소문자 악센트 라틴 → 원본은 UTF-8. 대문자 악센트 라틴 → 원본은 cp949.

## 3. 복구 — 오독만 일어난 경우

```python
# repair.py — 화면에 잘못 보이는 문자열을 원문으로 되돌린다
import sys

seen = sys.argv[1]              # 잘못 보이는 문자열
raw = seen.encode('latin-1')    # 바이트를 그대로 되살린다
print(raw.decode('cp949'))      # 올바른 인코딩으로 다시 읽는다
```

```bash
python repair.py "ÇÑ±Û ÀÎÄÚµù"      # -> 한글 인코딩
```

- **반드시 `latin-1`을 쓴다.** 256개 바이트 값 전부를 왕복시킨다
- `cp1252`는 5개 바이트(`81 8D 8F 90 9D`)에 정의된 문자가 없어 **복구 중에 오히려 잃는다**
- UTF-8 바이트가 잘못 보인 경우는 마지막 줄을 `decode('utf-8')`로 바꾼다
- 파일 단위라면 `iconv -f ISO-8859-1 -t UTF-8` 로 되살린 뒤 다시 판정한다

## 4. 복구 불가 판정 — 여기서 멈춘다

```bash
# 대체문자가 저장되어 있으면 원본 바이트는 이미 사라졌다
od -An -tx1 "$FILE" | tr -d ' \n' | grep -c efbfbd

# 이중 손상의 흔적 (대체문자가 cp949로 다시 읽힌 결과)
grep -c '占쏙옙' "$FILE"
```

하나라도 걸리면 **복구를 시도하지 않는다.** 이유:

- 대체문자는 저장될 때 `EF BF BD` 3바이트가 되는데, **원래 어떤 바이트였는지 정보가 없다**
- 모든 실패가 같은 값으로 뭉개진다. 11바이트 원본이 27바이트로 늘어난 사례를 확인했다
- `占쏙옙` 계열에는 대체문자가 **남아 있지 않다.** 두 번째 오독에서 정상 글자로 매핑됐기 때문이다 → **대체문자의 부재는 무사함의 증거가 아니다**

## 5. 경계에서 한 번만 변환 — 절단을 막는 형태

```bash
# 나쁜 예: 실패해도 파일은 만들어진다 (앞부분만 든 절단 파일)
iconv -f CP949 -t UTF-8 in.csv > out.csv

# 좋은 예: 실패하면 결과물을 남기지 않는다
set -Eeuo pipefail
TMP=$(mktemp)
if iconv -f CP949 -t UTF-8 in.csv > "$TMP"; then
  mv "$TMP" out.csv
else
  rm -f "$TMP"
  echo "변환 실패 — 원본을 확인하세요" >&2
  exit 1
fi
```

**종료 코드를 확인하지 않으면 데이터가 조용히 사라진다.** 절단은 파일 끝에서 일어나므로 앞부분만 열어 보는 검수로는 절대 안 잡힌다.

| 방식 | 실패 시 | 종료 코드 | 데이터 | 판단 |
|---|---|---|---|---|
| 옵션 없음 | 실패 지점에서 중단 | 1 | **뒷부분 전체 소실** | 종료 코드 확인 필수 |
| `-c` | 못 옮기는 문자 버림 | 1 | 그 문자만 소실 | 알면서 진행할 때 |
| `//IGNORE` | 버림 | 0 | 그 문자만 소실 | **권하지 않음** (실패를 숨긴다) |
| `//TRANSLIT` | 근사 표기로 치환 | 0 | 원본 아님 | 사람이 읽을 로그류 |

## 6. 왕복 검증 — 변환하는 모든 곳에 붙인다

```bash
# 변환이 손실 없이 끝났는지 확인한다
roundtrip_ok() {
  local src="$1"
  iconv -f UTF-8 -t CP949 "$src" 2>/dev/null | iconv -f CP949 -t UTF-8 | cmp -s - "$src"
}

if roundtrip_ok data.csv; then
  echo "무손실 — 내보내도 된다"
else
  echo "손실 발생 — 어떤 문자가 사라지는지 확인하라" >&2
  iconv -c -f UTF-8 -t CP949 data.csv | iconv -f CP949 -t UTF-8 | diff - data.csv
fi
```

cp949로 내보낼 때 **반드시 사라지는 것**: 이모지, 간체 중국어, 자모로 분해된 한글.
**의외로 살아남는 것**: 유로 기호(`A2 E6`), 일본어 가나. 「비한국 문자는 다 깨진다」는 어림짐작은 틀렸다.

## 7. CSV와 BOM

```bash
# BOM 붙이기 (스프레드시트에 UTF-8임을 알린다)
printf '\xEF\xBB\xBF' | cat - body.csv > with_bom.csv

# BOM 떼기
sed '1s/^\xEF\xBB\xBF//' with_bom.csv > no_bom.csv

# 앞 3바이트 확인
od -An -tx1 -N 3 with_bom.csv
```

```python
# BOM이 첫 열 이름에 U+FEFF로 붙는 사고를 막는다
import csv

with open('report.csv', encoding='utf-8-sig', newline='') as f:   # sig 가 핵심
    for row in csv.DictReader(f):
        print(row['이름'])        # utf-8 로 열면 이 조회가 None 을 돌려준다
```

- BOM은 **UTF-8 표식**이다. cp949 파일에 붙이면 UTF-8로도 cp949로도 유효하지 않은 파일이 된다
- 올바르게 UTF-8로 읽어도 BOM은 `U+FEFF` 문자로 **첫 열 이름 앞에 남는다**
- 증상이 **첫 번째 열에서만** 난다. 둘째·셋째 열은 정상이라 원인을 찾기 어렵다
- `U+FEFF`는 공백류가 아니라 **앞뒤 공백 제거로는 안 잡힌다**

## 8. 유효성 검사만으로는 인코딩을 확정할 수 없다

한글 음절 **345자**는 cp949 바이트열이 그대로 유효한 UTF-8이다. 두 인코딩 어느 쪽으로도 예외 없이 읽히는 텍스트를 실제로 만들 수 있다.

```
징 -> cp949 C2 A1   같은 바이트를 UTF-8로 읽으면 U+00A1
징짖짙짚 -> C2 A1 C2 A2 C2 A3 C2 A4   (utf-8 유효 · cp949 유효 · 둘 다)
```

→ 「UTF-8로 시도하고 실패하면 cp949로」는 **추측**이다. BOM이 없으면 나머지는 확률이다. **주고받는 규격에 인코딩을 명시하는 것이 유일한 근본 해결이다.**

## 9. 경계별 책임 — 누가 인코딩을 정하나

| 경계 | 누가 정하나 | 함정 |
|---|---|---|
| 파일 저장 | 쓰는 프로그램 | 같은 기계에서 Python은 cp949, Node는 UTF-8로 쓴다 |
| 파일명 | 운영체제 | 이름은 경계에서 **재인코딩된다.** 내용처럼 바이트 보존이 안 된다 |
| 셸 출력 | 코드페이지 + 프로그램 | 코드페이지와 로케일이 한 기계에서 충돌할 수 있다 |
| **파이프** | **아무도 정하지 않음** | **선언할 자리가 없다.** 양쪽 합의를 코드에 박아야 한다 |
| HTTP 헤더 | 서버가 선언 | 클라이언트가 **무시할 수 있다.** 본문을 바이트로 받아 직접 디코드 |
| CSV 선두 | 쓰는 쪽 | BOM이 유일한 신호 |
| 변환 도구 | 도구 구현 | **같은 이름이 다르게 동작한다** (아래) |

## 10. 인코딩 이름을 믿지 말 것

| 이름 | Python | GNU libiconv | 판단 |
|---|---|---|---|
| `cp949` | 확장 음절을 2바이트로 | 성공 | **한국어에 이것을 쓴다** |
| `euc-kr` | 확장 음절을 **8바이트** 조합형으로 | **거부** | 이름만 보고 믿지 말 것 |
| `johab` | 2바이트, 다른 체계 | 성공 | 거의 안 쓰임 |
| `utf-8` | 3바이트 | 성공 | **내부 표준으로 삼을 것** |

같은 「EUC-KR」을 두고 한쪽은 거부하고 한쪽은 8바이트로 변환한다. 손실은 없지만 **바이트 수가 4배**라 컬럼 길이 제한이 있는 곳에서 잘린다. **파이프라인에 실제로 쓰이는 도구로 표본을 통과시켜 봐야 한다.**

## 11. 셸·출력 인코딩

| 설정 | 바꾸는 것 | 바꾸지 않는 것 |
|---|---|---|
| `PYTHONIOENCODING` | 표준 출력 인코딩만 | **파일을 열 때의 기본 인코딩** |
| `PYTHONUTF8=1` | 출력 + `open()` 기본값 | — |
| `LC_ALL` / `LANG` | 도구가 바이트를 문자로 묶는 방식 (글자 수, 정렬) | 파일 내용 |
| `chcp` | 콘솔 코드페이지 | 파이프로 흐르는 바이트의 의미 |

- 화면 출력만 깨지면 `PYTHONIOENCODING`, 파일 읽기·쓰기가 문제면 **이 변수는 효과가 없다**
- 가장 확실한 것은 환경 변수에 기대지 않고 **파일을 여는 코드에서 인코딩을 명시**하는 것
- 표현 불가한 출력 인코딩을 지정하면 깨지는 게 아니라 **프로그램이 죽는다.** 종료 코드가 0이 아니고 출력이 비었으면 **데이터는 온전하다**
- Node는 이 스위치가 없고 항상 UTF-8로 쓴다 → Python과 파이프로 엮으면 여기가 사고 지점

## 12. 체크리스트

- [ ] 깨진 파일을 받으면 **편집기보다 `od`를 먼저** 열었다
- [ ] `efbfbd` 개수를 세어 **복구 가능 여부를 먼저 판정**했다
- [ ] 복구에 `cp1252`가 아니라 **`latin-1`**을 썼다
- [ ] 의심 파일을 **읽기 전용으로** 열었고, 잘못 읽은 상태를 저장하지 않았다
- [ ] 변환 스크립트가 **종료 코드를 확인**한다
- [ ] 변환에 **왕복 검증**을 붙였고, 실패 시 결과물을 남기지 않는다
- [ ] 원본을 지우기 전에 검증을 통과시켰다
- [ ] CSV를 읽을 때 **BOM을 걷어내는 코덱**을 지정했다
- [ ] 저장소 안에 **두 인코딩을 섞지 않는다** (검색이 반쪽만 걸린다)
- [ ] 사용자 입력의 **이모지·간체 중국어**를 cp949 내보내기 전에 걸러 알린다
- [ ] 주고받는 규격 문서에 **인코딩을 적었다**
- [ ] 파일명과 파일 내용의 인코딩을 **별개 문제로** 다뤘다
