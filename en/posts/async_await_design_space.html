Why the Same Async Code Ends Differently on Each Runtime - Nine Design Axes and What Each Choice Bills You

Not a tutorial but a map of choices. There are many ways to put asynchrony into a language, and each one makes something easy at the price of making something else hard

Sep 11, 2026 Dev & Infra

Here is a piece of code that writes one log line in the background. It spawns a task and returns without waiting for it. You would think reading the code tells you what gets printed, but in practice the answer depends on which runtime it runs on. Not the timing. The observable result.

Gavin Gray of the Cognitive Engineering Lab at Brown University published a post on 8 September 2026 titled 「A Design Space Exploration of Async/Await」 that organises this divergence into nine design dimensions. In the post's own framing, a program whose entire job is to write a log line in the background produces four different answers. A paper sits behind the post, and the divergence is explained by a formal semantics over a core calculus of asynchronous programs.

What follows is not a guide to using async/await. It is about the several different ways asynchrony gets built into a language, and what each of those ways makes easy at the cost of making something else hard. Closer to a map of choices than a tutorial. The post's classification serves as the skeleton, and any axis that is not in the post is flagged as such and raised separately.

The trigger - one log line ends four different ways

The post starts from a very small program. It spawns a task that simulates a slow log write, and the enclosing function returns without awaiting it. Outside, the program sleeps briefly and prints one more marker. The string that comes out splits into four groups across seven runtimes.

The interesting part is not which answer is correct. This program has no race condition, no shared resource, and no second thread. If the answers still diverge, the cause is not in the program but in what the runtime underneath has decided to make its default. That is exactly why the post needs nine axes.

The post cuts the life of a task into three segments and places the axes accordingly: how a task begins, how it ends, and how it is cancelled. And for each axis it states flatly that there are trade-offs of performance, memory usage, ergonomics, and semantics, with no right or wrong answers. Every language has its own design rationale.

Catching concurrency defects from outside the code, by enumerating orderings and sweeping the reachable state space, is a separate topic covered in what a specification catches that tests do not. What follows is the other side of the same coin: the shape a language gives to asynchrony.

Colored functions - why the marker spreads up the call chain

The first wall anyone hits with asynchrony is neither cancellation nor exceptions. It is that calling one async function requires the caller to be async, and then the caller above that, until the marker has climbed all the way to the entry point. This is commonly called function coloring.

Where the stack lives

The spread is not a matter of syntactic taste. It is forced by the implementation strategy. An ordinary call pushes its locals and return address onto the machine call stack, and that stack is owned by an operating system thread. So when a synchronous function waits, the whole thread stops. With the stack pinned to the thread there is nothing else it could do.

A suspendable function breaks that premise. It must stop midway, hand control back to its caller, and later resume at exactly that point. To do that, whatever has to survive across the await must be stored off the stack. What must survive is a fixed list.

  • Locals still used after the await — their values must exist after the stack frame is gone
  • The resume point — a marker naming where in the body execution should pick up again
  • Cleanup obligations — open resources, locks to release, and the position of finally blocks that still owe a run

The compiler builds an object to hold those three, then chops the function body at every await point and rearranges it into resumable pieces. This transformation happens only when the function carries the marker. That is the mechanism behind the MDN description of an async function body being split at its await points.

And so it climbs

An unmarked ordinary function has no such storage. So using the result of a suspendable function leaves exactly two options: block a whole thread and wait, or take the same transformation yourself. The first throws away the reason for going asynchronous; the second moves the marker one level up. That is why it spreads through the entire call chain.

The spread only exists in designs where the marker appears in the signature. The lightweight thread family covered further down chooses instead to detach the stack from the thread and give one to each task, so any function can suspend and no marker is needed.

Is the spread a defect or information?

Judgement genuinely splits here. One side reads it as contagion. One library turns asynchronous and every piece of code above it has to be rewritten, leaving a synchronous edition and an asynchronous edition of the same functionality maintained side by side.

The other side reads it as intended type information. A marker in the signature says this call may suspend, and that fact turns out to be useful.

  • It shows where invariants become observable — when a suspension happens, another task can interleave and see shared state. The marker labels the window
  • It makes suspend-while-holding-a-lock findable by eye — an await inside a lock region is visible right there in the body, not buried in a signature
  • It shows where cancellation can arrive — cooperative cancellation is usually delivered at suspension points
  • It separates calls with different cost profiles — a call that returns immediately and one that hides a wait are told apart by the signature

This is not the place to declare a winner. The same property counts as a defect when it is priced as cost of change, and as a feature when it is priced as information you read. If the codebase is already large and deeply entangled with synchronous libraries, the first price is high. If a lot of code touches shared state and interleaving points have to be controlled, the second value is high.

Two axes at the start - eagerness and suspension

Eagerness decides whether work begins the moment an async function is called. On the lazy side, the call merely constructs an object and nothing happens. The Python standard library documentation states that simply calling a coroutine will not schedule it to be executed, and shows the call evaluating to a coroutine object. The Rust standard library Future documentation puts it more forcefully: futures alone are inert, and they must be actively polled for the underlying computation to make progress.

The eager side is the opposite. The C# documentation describes an async method suspending at its first await, returning a task to the caller, and that task representing ongoing work. It is already running by the time you hold it.

The suspension axis is subtler. It asks whether you may assume that because there is an await here, control yields at least once. MDN is explicit for JavaScript: even when the promise used is already fulfilled, execution of the async function still pauses until the next tick, and this happens even if the awaited value is not a promise, because execution does not return to the function until all other already-scheduled microtasks are processed.

// await yields to the next tick even when the operand is not a promise
async function step(name) {
  console.log(name, 'start');
  await console.log(name, 'middle');
  console.log(name, 'end');
}

step('first');
step('second');
// first start / first middle / second start / second middle / first end / second end

C# gives a different answer in the same place. The Microsoft documentation notes that if the awaited operation completes before the await is reached, control remains in the method, and gives the reason alongside: the expense of suspending and returning would be wasted. The same word await guarantees a yield on one side and does not on the other.

  • Static suspension makes interleaving points countable from the source. The price is one tick even for values already at hand
  • Dynamic suspension saves the round trip when the value is ready. The price is that identical code runs in different orders under different load
  • Lazy start allows composition to be layered on afterwards — retry, timeout, and so on. The price is that forgetting to drive it produces silence

Four axes at the end - extent, reference, destruction, propagation

Extent fixes how long a spawned task is allowed to live. On the indefinite side a task may outlive the function that created it; on the dynamic side it is cleaned up before its creating scope exits. The Swift concurrency proposal states the latter rule in one sentence: a function that creates a child task must wait for it to end before returning. Trio takes the same shape. Its documentation says the block does not exit until all tasks have completed, and adds that you cannot start a child task unless you are prepared to be a responsible parent.

Reference strength is the axis that bites most quietly in production. The Python asyncio documentation attaches a warning to create_task: the event loop only keeps weak references to tasks, and a task that is not referenced elsewhere may get garbage collected at any time, even before it is done. So the documentation tells you to gather background tasks in a collection to create a strong reference, and to have each task remove its own reference on completion.

import asyncio

background = set()

async def main():
    task = asyncio.create_task(write_log())
    background.add(task)                       # create a strong reference
    task.add_done_callback(background.discard) # drop it when the task finishes
    await asyncio.sleep(1)

Destruction is the disposal that happens the instant the extent ends. Some designs await what remains, some cancel it so it can clean up, some simply cut it off. This is the axis that decides whether cleanup code runs at all. One condition in the C# documentation captures the character of the axis nicely: suspension at an await does not constitute an exit from the method, and finally blocks do not run at that moment. The cleanup code of a task that is never resumed is therefore left unexecuted.

Propagation handles a task that nobody awaited and that failed. The Python documentation says that with the never-awaited approach, if a task fails its exception is never retrieved and asyncio logs a message about a task exception that was never retrieved when the task is garbage collected. Trio sits at the other end: unhandled exceptions are re-raised inside the parent task, grouped into a single exception group.

  • Indefinite extent makes background work easy. The price is that nobody knows what is still alive at shutdown
  • Dynamic extent guarantees that nothing is left once the scope is exited. The price is hand-building a separate scope for anything long-running
  • Weak references structurally reduce reference leaks. The price is that an unheld background task can vanish
  • Keeping exceptions inside the task stops one failure from dragging its neighbours down. The price is that a failure survives only as a log line

Three axes for cancellation - awareness, direction, persistence

Cancellation is the only family to which the post assigns three separate axes. That is a measure of how many branches it has.

Awareness asks whether a task can respond to being cancelled. Where it can, cancellation becomes cooperative. The Swift proposal states that cancellation is fully cooperative and synchronous, and that it has no effect at all unless something checks for cancellation. The Python documentation describes the same property differently: Task.cancel merely arranges for a cancellation exception to be thrown into the wrapped coroutine on the next cycle of the event loop, and the coroutine gets a chance to clean up or even deny the request by suppressing the exception. The documentation adds that suppressing it is actively discouraged.

Direction asks which way cancellation travels through the graph. The Swift proposal says that when a parent task exits with an error its child tasks are implicitly cancelled. Python's TaskGroup has a different shape: the first time any task in the group fails with an exception other than a cancellation, the remaining tasks in the group are cancelled, and if the body of the statement is still active the task containing it is cancelled too. The failures are combined into an exception group and raised at the end.

async def main():
    try:
        async with asyncio.TaskGroup() as tg:   # the scope holds its children
            tg.create_task(write_log())
            tg.create_task(fetch_config())      # one failure cancels the rest
    except* OSError:                            # remaining failures arrive grouped
        handle_failure()

async def write_log():
    try:
        await asyncio.sleep(2)
    except asyncio.CancelledError:
        raise                                   # re-raise instead of swallowing
    finally:
        close_handle()

Persistence asks how long a cancellation stays in force. The Trio documentation explains its own behaviour with the phrase level triggered: once a block has been cancelled, all cancellable operations in that block keep raising the cancellation exception. Swift points the same way, its proposal noting that once the cancellation flag is set it is never cleared. Python leaves room on the other side: code that catches and suppresses the cancellation exception must call Task.uncancel to remove the cancellation state, and doing so can rescind a cancellation that had been arranged but not yet thrown.

  • Persistent cancellation prevents a cancellation from quietly lapsing mid-cleanup and letting work continue. The price is that any wait inside cleanup needs its own shielded region
  • Transient cancellation leaves room to carry on with post-processing after a cancellation. The price is that any code that swallows a cancellation breaks the deadline
  • Unaware cancellation asks nothing of the target code. The price is that whatever was half-finished at the stopping point must be handled separately

Axes not in the post - who resumes, and where the stack lives

The nine axes in the post separate the observable semantics of a task. Choosing in practice needs two more axes underneath them, and neither is in the post's classification. They are raised separately here, distinct from the post's own axes.

The first is who resumes execution. Some designs ship an executor with the language; others define only the suspendable pieces and leave the executor to be picked as a library. The Rust Future documentation describes the latter directly: when using a future you generally do not call poll yourself but .await the value, and the executor is responsible for repeatedly calling poll on futures when they are ready to make progress. Readiness comes back through a Waker. When polling returns Poll::Pending, a clone of the waker from the current context is stored, and it is woken once the future can proceed.

The second is where the stack lives. The state machine transformation covered earlier is one answer; attaching a separate stack to each task is the other. The Java virtual threads proposal specifies the latter implementation: the stacks of virtual threads are stored in Java's garbage-collected heap as stack chunk objects, and they grow and shrink as the application runs.

  • Runtime-provided executor — one standard makes library compatibility easy. The price is narrow room to change scheduling policy
  • Choosable executor — the executor can be swapped to match the workload. The price is that libraries assuming different executors do not mix
  • State machine transformation — per-task memory is only as large as it needs to be. The price is stack traces that no longer line up with the original call chain
  • Separate stacks — the call chain survives, so tracing and debugging carry through. The price is somewhere to keep the stacks themselves

Designs that remove the coloring - what they buy and what they sell

There is a way to reach the same goal without any marker: make threads cheap enough that you write blocking code as usual while the carrier thread is released during the block. Java virtual threads are the case documented in most detail. The proposal defines a virtual thread as an instance of java.lang.Thread that is not tied to a particular OS thread, and states that a virtual thread runs Java code on an underlying OS thread but does not capture that thread for the code's entire lifetime.

What it buys back

What the proposal says about asynchronous style is exactly the list of what gets bought back. Asynchronous style forces developers to break request-handling logic into small stages and to forsake the language's basic sequential composition operators, such as loops and try-catch blocks. On observability the wording is more direct still: stack traces provide no usable context, debuggers cannot step through request-handling logic, and profilers cannot associate an operation's cost with its caller.

// The colorless side: blocking calls stay, and each task gets a thread
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var request : requests) {
        executor.submit(() -> {
            var body = httpClient.send(request, ofString()); // blocking is fine
            return store.save(body);                         // loops and try still work
        });
    }
}

What it sells

There is a price. First, the visibility of suspension points. Nothing in a signature says which call can stop, so code that suspends while holding a lock, or a window in which a broken invariant is observable to another thread, cannot be found by reading signatures. Second, the boundary conditions. The proposal names two cases where a virtual thread cannot be unmounted because it is pinned to its carrier: when it executes inside a synchronized block or method, and when it executes a native method or a foreign function.

The line the proposal draws around itself matters too: virtual threads are not faster threads, they do not run code any faster than platform threads, and they exist to provide scale rather than speed. The applicability condition is stated alongside — throughput improves when the number of concurrent tasks is high, more than a few thousand, and the workload is not CPU-bound.

This is not the place to declare a winner either. If the work is dominated by computation, neither side has much waiting to reclaim. If the existing code is full of blocking calls and those libraries have no asynchronous edition, moving to the colored side is expensive. Conversely, if a lot of code touches shared state and interleaving points must be controlled, a marker in the signature earns its keep.

Where this actually bites in production

Work that survives a cancellation that never reached it

The cause is simple: no channel for the cancellation reaches that work. Such a channel takes one of three forms — a signal passed as an argument, a scope that holds its children, or disposal. Spawn a task using none of them and it becomes nobody's child.

  • The signal-passing form — the Go standard library documentation prescribes not storing contexts inside a struct type and instead passing a context explicitly to each function that needs it. The channel is cut in whatever stretch skips it
  • The scope-holding form — the Swift proposal states that neither unstructured tasks nor detached tasks respect the parent-child completion constraint. A task that escapes the scope does not end with it
  • The broken-reference form — this is the Python weak reference warning. An unheld background task can disappear before it finishes

Paths where exceptions disappear

When a task nobody awaited fails, there is nobody to receive the exception. The Python documentation describes that state through the log message about a task exception that was never retrieved, and notes that the message appears when the task is garbage collected. In other words there is a gap in time between the failure and the log.

  • When the return type cannot carry an exception — the C# documentation states that an async method with a void return type cannot be awaited and that the caller cannot catch any exceptions that the method throws
  • When nobody retrieves the result — the Python documentation tells you to avoid this path with TaskGroup, which keeps a strong reference to each task, awaits them, and propagates their exceptions
  • When the design keeps exceptions inside the task — this is the never side of the post's propagation axis. On the other side, Trio-style designs re-raise in the parent

One blocking call that stalls the whole runtime

The cause lies in the fact that the executor thread is currently running your code. Under the state machine strategy, resume fragments run on executor threads. If a fragment makes a call that blocks at the operating system level, that thread runs no other task's fragment for the duration. When the executor is single-threaded, the entire runtime is stopped for that time.

  • A long stretch of computation — the result is the same without any blocking call. With no yield point, nothing else advances
  • A synchronous library call — file I/O, name resolution, and cryptographic work are the usual examples where no asynchronous edition exists
  • The matching phenomenon on the lightweight thread side — this is where the Java pinning conditions live. Inside a synchronized block or a native function, the carrier thread cannot be released

Two parties waiting on each other while neither advances is not unique to asynchrony. A concrete case of a single shared resource stalling both sides is written up in deadlock from a full pipe buffer.

Code that assumes an ordering nothing guarantees

This is the suspension axis showing up directly as a defect. Either the assumption that control yields here, so the other side will run in the gap, or the assumption that this finishes immediately, so it will not suspend, gets baked into the code. The two are opposites, and which one the runtime guarantees can only be learned from its documentation.

  • Moving code that assumes static suspension onto a dynamic runtime — scheduled follow-up work runs later than expected
  • Moving code that assumes dynamic suspension onto a static runtime — interleaving appears in a stretch believed to be atomic
  • Mistaking lazy start for eager start — a coroutine that was constructed but never driven quietly does nothing at all

Where code that assumes an order quietly breaks

Of all defects in asynchronous code, ordering assumptions are the hardest to reproduce. Three causes stack on top of each other.

First, whether suspension is guaranteed differs by runtime. On a side that always yields, like JavaScript, the code after an await is always pushed to the next tick, even for a value already available. On a side that stays put for ready values, like C#, the same code continues right there. Move structurally identical code between the two and the order changes.

Second, the moment a task starts differs. On the lazy side, constructing and driving are separate steps; on the eager side, calling starts it. If a constructed coroutine only begins when it is later awaited, ordering assumptions built around the interval in between fall apart.

Third, completion order differs from submission order. Spawn several at once and external factors decide who finishes first. Yet code frequently assumes results arrive in the order they were launched.

  • Move it into an expression of order — if order matters, write it with events, queues, or locks that state the order explicitly, rather than relying on side effects at wait points
  • Bind it with a scope — express a stretch that spawns several and needs all of them finished with a group API. The fact that the scope exited is itself the guarantee
  • Pin the assumption with a test — where an ordering assumption must remain, add a test that exercises it, so it reproduces by logic rather than by load

Conclusion - you chose a failure mode, not a syntax

The observation that one program ends four different ways across seven runtimes exposes the fact that asynchrony is not a pair of keywords but nine or more independent decisions. Those decisions are scattered across documentation, and they usually get read only after an incident.

  • The spread of the marker is a consequence of where the stack lives — not a matter of taste. Removing it means giving each task its own stack, and that sells the visibility of suspension points
  • Cancellation is a channel, not a feature — decide first whether it will be built from signals, scopes, or disposal, and nothing is left behind later
  • Reading the defaults is half the work — extent, reference strength, and propagation take the runtime's default whenever nobody states otherwise

Adopting asynchrony is therefore a decision about which failure mode you are willing to carry. That is the same reason the post records trade-offs on every axis and no right or wrong answers.
