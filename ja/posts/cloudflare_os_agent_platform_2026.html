序論: 発表文で最初に読むべき一文

エージェントプラットフォームの発表はだいたい同じ顔をしている。チャット画面があり、社内データにつながり、自動化ができるという話だ。今回も見た目は変わらない。ただしCloudflare OSには別の一文が付いている。サーバーコードがグローバルな外向きネットワークを無効にしたDynamic Workerで動く、という一文だ。

この一行が製品紹介ではなく配置の判断の出発点になる。外向きが既定で閉じているというのはセキュリティの説明でもあるが、同時にこのプラットフォームが受け入れられる仕事の形をすでに決めてしまったという意味でもある。任意の外部呼び出しが必要なコードはここでは単純に動かない。そしてその穴を埋めるために出てきたのがGatekeeperだ。

Cloudflareは2026年8月5日、Agents Weekの期間中にCloudflare OSをオープンソースとして公開した。社内で使っていたツールを作り直して出したもので、ライセンスはApache-2.0、自分のCloudflareアカウントに直接配置して自前のAccessポリシーとAI Gateway設定で動かせる。

この記事は機能一覧を追わない。代わりに「自分のワークロードをここに置く理由はあるか」の一点に着地する。何が束ねられたのか、実行モデルが何を強制するのか、どんな作業が合ってどんな作業が構造的に合わないのか、そしていまの時点で本番に載せてはいけない理由までいく。

同じ会社の、逆方向の製品と混同しないこと。Cloudflareはサイトに入ってくるAIエージェントを見分ける側の技術も別に出している。そちらはPrecursor登場 - Cloudflareがセッション全体の行動でAIエージェントを見抜く理由で扱った。この記事は正反対の軸、つまりエージェントを走らせる側のランタイムの話だ。同じ会社が同じ週に両方を出したという事実自体が、この市場のいまの状態を示している。

1. Cloudflare OSが実際に束ねた三つの塊

名前がOSなので誤解しやすいが、新しいオペレーティングシステムでも新しいインフラ層でもない。性格を正確につかんでおかないと検討の方向がずれる。

1.1 新製品か、再編か

どちらでもない。Cloudflareが社内で使っていたアプリケーションを作り直してオープンソース化したものだ。発表文の表現そのままに「本日、我々はCloudflare OSの新バージョンをオープンソース化する」であり、最初のバージョンは同じ年の5月に全社員へ開放された社内ツールだった。エンジニアリング以外の人たちが文書を書き、スライドを作り、反復業務を自動化するのに使い始めたとCloudflareは述べている。

  • Cloudflareアカウントの中に配置するアプリケーションであって、新たに契約するクラウドではない
  • だから検討の最初の問いが、新しいベンダーを使うかではなく、いまあるアカウントの中にこれを置くか、に変わる
  • すでにWorkersとAccessを使っているなら検討コストは明確に低く、使っていないならアカウント開設からAccessポリシー設計までがすべて先行作業になる
  • 社内配備の実績があるという点は根拠として価値がある。デモ用に作ったものではなく、数千人が毎日使っていたものを作り直した結果物だ

1.2 三つの塊に分けて見ると

発表はこれを三つの部分の結合として説明している。この三つは独立に価値を持つのではなく、前のものが後のものを必要とする順に積み上がっている。

  • エージェント作業空間。会社がキュレーションした文脈とスキルがあらかじめ載っており、エージェントがコードを書いて実行できる隔離ランタイムが付いている
  • セキュリティとガバナンスの枠組み。社内データやサービスへ安全に届くための層だ。すべてのエージェントとアプリがアクセス権ゼロで始まることが出発点になる
  • 個人が直せるアプリのプラットフォーム。人が作り、共有し、直し続けられるアプリのための実行基盤だ
  • 最初の塊だけあると社内データに触れた瞬間に危険になり、二番目だけあると使い道がない。三番目は前の二つがあって初めて成果物が残る形になる
  • 調査と質問は、データ全体をモデルのコンテキストウィンドウへ流し込む代わりにコード実行で検索し分析する方式を使うとしている。コンテキスト予算と資源規模を切り離す設計だ
  • 生成された文書やスプレッドシートは元データに接続されたまま残り、元が変われば一緒に更新される。必要なら見慣れた形式に書き出すこともできる

1.3 構成要素と各自の役割

発表に実際に登場した構成要素だけを整理する。この表にない製品は、この発表では言及されていない。

2. エージェント実行モデル - アプリ一つがWorker一つ

実行モデルを一文に縮めるとこうなる。エージェントが作ったアプリはすべてWorkerだ。この一文から残りが全部ついてくる。

2.1 クライアントコードとサーバーコードが一緒に生成される

作業空間にアプリを作ってくれと頼むと、エージェントは二つの部分を書く。ブラウザで画面を描くクライアントコードと、状態を保存して振る舞いを実装するサーバーコードだ。サーバー側は必要なときにDynamic Workerとして読み込まれ、Durable Object Facetとしてインスタンス化される。各アプリは自分のSQLiteデータベースを持ち、それはアプリを管理するCloudflare OSランタイムと分離されている。

ブラウザ
  └─ クライアントコード (サンドボックスフレーム)
        │  Cap'n Web RPC
        ▼
Dynamic Worker  ← 要求時に読み込み
  └─ Durable Object Facet
        └─ アプリ専用SQLite  (ランタイム保存領域と分離)

外へ出る道はGatekeeperが渡したケーパビリティだけ

クライアントからサーバーを呼ぶ形は遠隔呼び出しに見えない。発表に載った例はこの形だ。

const issues = await app.listIssues({
  status: "done",
});
  • ブラウザのクライアントはCap'n Webでサーバーと話す。Cloudflareが公開したオブジェクトケーパビリティ方式のRPCだ
  • おかげで人が作るインターフェースとエージェントが呼ぶインターフェースが同じものになる。エージェント専用APIを別に作る必要がない
  • アプリごとにデータベースが分離されているので、あるアプリのスキーマ事故が別のアプリへ広がらない
  • 逆にアプリ間でデータを共有するにはその経路を明示的に作らなければならない。利便性ではなく隔離を選んだ設計だ

2.2 外向きが既定で閉じているという意味

このプラットフォームの性格を最も大きく決める制約だ。サーバーコードはグローバルな外向きネットワークが無効化されたDynamic Workerで動き、クライアントコードはブラウザのサンドボックスフレームで動く。どちらも明示的に提供されたケーパビリティを通してのみ外部システムに届く。

  • エージェントが作ったコードが任意のアドレスへデータを送れない。プロンプトインジェクションで生成コードが汚染されても流出経路そのものが存在しない
  • 同時に、どんな外部APIでも呼ぶコードはここでは動かない。必要な接続はすべて先にGatekeeperとして作っておく必要がある
  • だから導入コストの実体が見えてくる。プラットフォームを配置することより、接続するサービスごとにGatekeeperを書くことが本当の作業量だ
  • 公開リポジトリの案内文も外部サービス設定のツールを整備中だと記しつつ、多くのサービス提供者がこの過程を意図的に容易にしていないと併記している

2.3 コードを実行するランタイムはどこまでか

同じ週にCloudflareは@cloudflare/computerというエージェントランタイムもアーリープレビューとして公開した。隔離とコンテナを状況に応じて選ぶオープンソースのランタイムで、軽い作業はDynamic Workerの隔離で、ネイティブバイナリや特定のシステムツールが必要な作業はコンテナで動かす。状態はSQLiteに裏打ちされた仮想ファイルシステムで両者の間を行き来する。Cloudflareはコンテナが必要な作業を全体の10パーセント未満にすることを目標に据えたと述べている。

ただしこの二つをくっつけて読まないこと。Cloudflare OSの発表文にも@cloudflare/computerの発表文にも、両者が同じものだとか一方が他方の構成要素だという記述はない。同じ週に出た別々の発表だ。「コンテナまで勝手に付いてくるだろう」と仮定して設計してはいけないという意味である。

3. Gatekeeper - 認証情報を渡さずに権限だけ渡す方法

外向きを閉じた以上、どこかに扉を作らねばならない。その扉の名前がGatekeeperだ。

3.1 認証情報はエージェントに渡らない

GatekeeperはCloudflare OSと外部サービスの間に置かれるサービス別のWorkerだ。OAuthを処理し、認証情報を保持し、ポリシーを執行し、何を読んだかを記録する。エージェントが生成したコードが受け取るのは認証情報ではなく型の付いたバインディングである。

const issues = await env.PROJECT.listIssues({
  teamId: "ENG",
  state: "open",
});
  • 発表は、人やエージェントにAPIキーを渡すのが危険だと明示的に指摘している。キーは範囲を絞れず、回収の痕跡も残らない
  • Gatekeeperはリポジトリ一つ単位で権限を与えられ、イシューは読めるがソースコードは読めないように分けられる
  • すべてのエージェントとアプリはアクセス権が何もない状態から始まる。必要な資源をその都度要求する構造だ
  • 外部に副作用を起こす動作もすべてこの層を通る。だから「誰が何をしたか」がアプリケーションログではなく権限層に記録として残る

3.2 観測記録が共有を制限する

ここが従来の権限モデルと最も大きく分かれる地点だ。Cloudflare OSはエージェントが観測したすべての資源を記録し、その観測記録はエージェントと成果物に付いて回る。別の人がその作業空間を開いたり、エージェントとやり取りしたり、成果物を見ようとすると、Gatekeeperがその人が観測された資源にアクセスできるかを確認する。

  • ダッシュボードの共有が、その中に入った元テーブルを共有する迂回路になってはならないというのが設計目標だ
  • 機微なデータを読んだ後は特定の宛先への書き込みが止められることもある。読み取り履歴がその後の書き込み権限を狭める方向に働く
  • この性質は利便性と正面からぶつかる。成果物を共有したのに相手が見られない状況がバグではなく正常動作だと、組織が先に理解しておく必要がある
  • 社内データの等級体系がない組織なら、この層を入れた瞬間に等級体系を作ることになる。導入の副作用ではなく導入の前提に近い

3.3 MCPだけではなぜ足りないのか

Cloudflare OSは組織がすでに使っているMCPサーバーをMCP Server Portalsで接続して使える。ところが発表は、MCPを置き換えないままその上に層を一つ重ねた理由をはっきり書いている。MCPだけではエージェントがどの基底資源を観測したのか分からないということだ。

  • MCPはツールを公開する規格だ。ツールが何を返したか、そのデータがどの元から来たかは規格の外にある
  • だから「この成果物を見てよい人は誰か」をMCP層では答えられない。観測記録は別に積む必要がある
  • すでにMCPサーバーを複数運用しているなら、その資産を捨てなくてよい点は導入コストを下げる要素だ
  • 逆にMCPサーバーが一つもない組織なら、このプラットフォームを入れる前に接続対象ごとのツール定義を作る作業が先に来る

4. 既存のサーバーレスと分かれる二つの地点

Workersの上に載っているのでサーバーレスの性質をそのまま受け継ぐ。ただし二箇所ではっきり違う。

4.1 デプロイ単位が消える

普通のサーバーレスは関数をデプロイする。コードを直せばパイプラインを回し直し、バージョンができ、ロールバック対象ができる。Cloudflare OSのアプリはその手順を通らない。Dynamic Workerとして要求時点で読み込まれるからだ。

  • おかげでエンジニアでない人が機能要望を書く代わりに自分のアプリをAIで直接直せる。発表が強調する地点がここだ
  • 共有の方式が二つある。アプリ自体を共有してリアルタイムで一緒に使うか、設計図を共有して各自が独立した複製を作るかだ
  • 設計図の複製は元のコードを持つが、状態と接続された資源は独立している。他人のツールを持ってきて自分のデータで動かすのに向く
  • 代わりに失うものがある。デプロイパイプラインがないということはコードレビューや承認ゲートを挟む地点もないという意味だ。社内規程がデプロイ承認を求めるなら、この性質から協議対象になる

4.2 状態がアプリにくっついている

一般的な関数型サーバーレスは無状態を前提に、状態を外部ストアへ押し出す。ここは逆だ。アプリごとにDurable Object FacetとSQLiteが付いており、状態が実行単位と同じ場所に住む。

  • 小さな内部ツールを作るのに別途データベースをプロビジョニングしなくてよい。着手コストが大きく下がる
  • 同時編集が自然だ。チームの複数人が同じアプリの中で同時に作業する形を前提に設計されている
  • 代わりに規模が大きくなると問題が裏返る。状態が実行単位に縛られているので水平拡張の軸がアプリ単位に固定される
  • 決定的ワークフローも同じ軸の上にある。要求があるとき、決まったスケジュールで、あるいは外部イベントが発生したときに実行される形を支える

5. 数値の上限がすでに決めてしまったこと

ここが配置の判断で最初に見るべき場所だ。Cloudflare OSの発表文には固有の上限値がない。ところがアプリがすべてWorkerなので、Workersのプラットフォーム上限がそのままアプリの上限になる。

5.2 この上限が実際に切り落とす作業

表の読み方は単純だ。上から自分の作業を当ててみて、一つでも引っかかればその作業はここに載せるものではない。

  • 長時間のGPU学習と大型モデルの自前配信。そもそも計算資源の種類が違う。推論はAI Gatewayを通って外部モデルへ出る構造であって、ここで動くものではない
  • 数GBのデータをメモリに載せる分析。128MBの上限が正面から塞ぐ。ストリーミングで刻むか、最初から別の場所で動かすかだ
  • 数十のバックエンドを同時に叩くファンアウト集計。同時外向き接続がリクエストあたり6本なので並列性がその線で切れる
  • 数十分かかる単一バッチ。Cron系が15分で切れるので、作業を刻んでつなぐ設計が必須になる
  • ネイティブバイナリに依存するツールチェーン。V8隔離では動かない。コンテナが必要な作業ならこのプラットフォームのアプリモデルの外だ
  • 逆に数百ミリ秒で終わる照会と整理の作業は、この上限のすべてを余裕で通過する。そして社内業務自動化の相当部分が実際にここに入る

6. データ所在地 - 規制のかかったワークロードの分岐

社内データを扱うプラットフォームなので、データがどこに座るかが導入の可否を分ける。アプリの状態はDurable Objectに入り、Durable Objectの位置規則はすでに文書化されている。

6.1 管轄と位置ヒントは別物だ

  • 管轄(jurisdiction)は規制順守のため特定地域の中でのみ実行し保存するよう強制する仕掛けだ。eu、us、fedrampの三つが提供される
  • 位置ヒント(location hint)は管轄の強制が要らないときに初期配置の位置を誘導する値だ。wnam、enam、sam、weur、eeur、apac、apac-ne、apac-se、oc、afr、meがある
  • この二つを混ぜてはいけない。ヒントは最善の努力であって保証ではない。ヒントした位置に必ず作られるわけではないと文書が明示している
  • Durable Objectは一度作られると別のデータセンターへ移らない。最初のget()呼び出しだけが位置決定に関与する
  • 識別子は課金とデバッグの目的で、指定した管轄の外にも記録される。識別子そのものが機微情報になる設計なら、この点を先に検討する必要がある

6.2 国内保存要件がある場合に確認すること

提供される管轄の一覧に多くの国は入っていない。だから国内データを国内にのみ置く要件がかかっているなら、この軸から整理しなければならない。

  • 管轄一覧にないことと国内データセンターがないことは別の話だ。ただし強制の仕掛けとして提供されていないという事実はそのまま残る
  • 位置ヒントapac-neはアジア北東地域を誘導するだけで国単位の保証ではない。規制対応の根拠には使えない
  • 推論リクエストはAI Gatewayを通って外部のモデル提供者へ出る。モデル提供者側のデータ処理位置が別途の検討対象になる
  • Gatekeeperが残す観測記録もデータだ。何を読んだかの一覧が残るということは監査資産であると同時に保管方針が必要な対象だという意味である

7. コストはどこで発生するか

先にはっきりさせておくことがある。Cloudflare OS自体の価格体系は発表にない。オープンソースとして公開され自分のアカウントに配置する形なので、コストはソフトウェア使用料ではなくそのアカウントで消費する資源から出る。

7.1 課金の軸は少なくとも三つに分かれる

  • 計算と状態。Workersの実行とDurable Objectsの保存・リクエストがここに入る。アプリ数が増えればDurable Object数が増え、その軸も一緒に伸びる
  • モデル推論。AI Gatewayを通るすべての推論リクエストだ。実際の請求はだいたいこの軸が最も大きく動く
  • アイデンティティ。Cloudflare Accessで入口を統制するので、利用者規模がこの軸を決める
  • ここに目に見えない四つ目がある。Gatekeeperを書いて維持する人の時間だ。接続対象が増えるたびにコードが増え、そのコードは権限層なので誰にでも触らせるわけにいかない

7.2 発表がコスト統制について実際に述べたこと

価格表はないが統制の仕掛けは明確に説明されている。すべての推論呼び出しがAI Gatewayを通るので、組織はどのモデルを使えるようにするかを選び、人単位やチーム単位で支出を追跡し、予算と速度制限をかけられる。すべてのリクエストは、それを出した人、チーム、作業空間に帰属する。

  • 帰属がリクエスト単位で行われるということはコストを部署単位へ戻せるという意味だ。社内導入においてこの性質は技術仕様ではなく政治仕様である
  • モデル選択権が組織にある点も同じ文脈だ。作業の性格に合うモデルを指定しておけば、高価なモデルが些細な作業に付く状況を構造的に防ぐ
  • ただし予算超過時の動作、つまり拒否するのか安いモデルへ落とすのかは発表にない。運用方針として決めておく項目だ

8.3 判断を三つの問いに縮めると

  1. この作業は128MBとCPU5分の中に入るか。入らないなら残りの議論に意味がない
  2. 接続すべき外部システムはいくつで、それぞれにGatekeeperを書く人がいるか。この数字が実際の導入コストだ
  3. 成果物の共有が権限で塞がれる状況を組織が受け入れられるか。受け入れられないならこのプラットフォームの中核装置を切ることになり、そうすると残るものが大してない

9. いま本番に載せてはいけない理由

公開リポジトリの案内文が自ら明かしている内容だ。この部分を飛ばして検討すると判断が丸ごとずれる。

  • 案内文はv2が相当使えるがまだ粗い部分が多いと記し、活発な開発状態だと表現している。本番準備完了の宣言ではない
  • セルフホスト配備の方式は準備中と表示されている。いま配置できる経路はCloudflareアカウントを使う側だ
  • 外部サービス接続の設定ツールも整備中だと書かれている。接続対象が多い組織ほど、この未完成の区間を自分で埋めることになる
  • ライセンスはApache-2.0だ。社内改造と再配布に障害はないが、ライセンスが開いていることと本番に載せる準備ができていることは別の問題である
  • だからいま価値のある取り組みは三つに絞られる。試験アカウントに配置してAccessとAI Gatewayの設定が社内規程と噛み合うか見ること、Gatekeeperを一つ二つ自分で書いて権限分解の粒度をつかむこと、自分たちの実際の作業が上限内に入るか測ることだ

10. 導入するなら先に決めておくこと

  • データ等級体系を先に作ること。観測記録に基づく共有制限は等級がないと入れられない。これはプラットフォーム設定ではなく組織の合意だ
  • Gatekeeperの所有者を指名すること。権限層のコードなので誰にでも触らせてはいけない。レビューなしにデプロイされない唯一のコード経路であるべきだ
  • モデル許可リストと予算超過時の動作を文書に書くこと。拒否か安いモデルへの切り下げかは発表にないので組織が決める
  • アプリの廃棄方針を最初から置くこと。アプリごとにDurable ObjectとSQLiteが付くので、放置されたアプリがそのままコストとデータとして残る
  • 観測記録の保管期間を決めること。監査資産であると同時にそれ自体が機微情報だ。運用データと監査記録の保存方針を兼用しないこと
  • 設計図の共有とアプリの共有を区別して教育すること。前者は状態が分離した複製で、後者はリアルタイムの共同作業だ。この違いを知らないとデータが混ざる
  • デプロイ承認規程との衝突を先に解消すること。デプロイ単位がないという性質は後から協議できない。規程を直すかこのプラットフォームの適用範囲を狭めるかの二択だ
  • 脱出経路を確認しておくこと。アプリ別SQLiteに溜まったデータを外へ出す経路が必要だ。オープンソースという事実が移行可能性を自動的に保証はしない

11. 確認できなかったこと

根拠を確保できなかった項目を一箇所にまとめる。

  • Cloudflare OS自体の価格。発表に価格情報がない。アカウント資源の消費で請求される構造だけが確認できる
  • 正式リリース段階の表記。発表は本日利用可能と書き、リポジトリは粗い部分が多いと書いている。ベータやGAといった公式の段階表記は確認できなかった
  • Dynamic WorkersとDurable Object Facetsの個別上限。この記事の上限表はWorkersプラットフォーム文書に基づくもので、この二つの機能に別途上限があるかは確認できなかった
  • 同時実行アプリ数と作業空間あたりの上限。発表にもリポジトリの案内文にも数値がない
  • 社内配備規模の具体値。あらゆる職能にわたって数千人が毎日使うという表現だけがあり、正確な人数とアプリ数は公開されていない
  • SLAと支援体制。オープンソース配布の形態で障害対応の責任がどこまでかは確認できなかった
  • モデル提供者側のデータ処理位置。AI Gatewayを通った後の処理地域は提供者ごとの契約事項であり、この発表の範囲外だ
  • R2・D1・Containers・Workers AIとの関係。この発表文にはこれらの製品が構成要素として登場しない。連携の可否は確認できなかった

12. よくある質問

Cloudflare OSは新製品か、それとも既存製品群の再編か?

どちらでもない。Cloudflareが社内で使っていたアプリケーションを作り直し、オープンソースとして公開したものだ。発表文の表現そのままに「本日、我々はCloudflare OSの新バージョンをオープンソース化する」であり、最初のバージョンは同じ年の5月に全社員へ開放されていた社内ツールだった。したがって新しいインフラ層が生まれたわけではない。Workers、Durable Objects、Access、AI Gatewayといった既存の構成要素の上に載るアプリケーションが一つ開かれ、そのアプリケーションが必要とする権限委譲の仕組みがGatekeeperという名前で一緒に出てきた。だから検討の最初の問いも、新しいクラウドを使うかではなく、既にあるCloudflareアカウントの中にこれを置くか、に変わる。

エージェントが作ったアプリはどう実行され、状態はどこに残るのか?

アプリ一つがWorker一つだ。エージェントはブラウザで画面を描くクライアントコードと、状態を保存して振る舞いを実装するサーバーコードを一緒に書く。サーバー側は必要なときにDynamic Workerとして読み込まれ、Durable Object Facetとしてインスタンス化される。各アプリは自分のSQLiteデータベースを持ち、それはアプリを管理するCloudflare OSランタイムの保存領域とは分離されている。ブラウザのクライアントとサーバーの通信はCap'n Webというオブジェクトケーパビリティ方式のRPCで行われる。ここで重要な性質はデプロイ単位が別に存在しないことだ。アプリを直すのにデプロイ手順が挟まらないので、エンジニアでない人も機能要望を書く代わりに自分のアプリを直接直せる。

Gatekeeperは従来のAPIキー方式と何が違うのか?

認証情報がエージェント側へ渡らない点が違う。GatekeeperはCloudflare OSと外部サービスの間に置かれるサービス別のWorkerで、OAuthを処理し、認証情報を保持し、ポリシーを執行し、何を読んだかを記録する。エージェントが生成したコードが受け取るのは認証情報ではなく型の付いたバインディングだ。だから権限をリポジトリ一つ単位、イシューは読めるがソースは読めない単位に分割できる。さらに観測記録が付く。エージェントが見た資源はそのエージェントと成果物に付いて回り、別の人がその成果物を開こうとすると、Gatekeeperがその人の観測資源へのアクセス権を確認する。機微なデータを読んだ後は特定の宛先への書き込みが止められることもある。

どんなワークロードがこのプラットフォームに合い、どれが合わないのか?

合うのは短く分散した実行だ。社内システムを複数まわって照会し整理する作業、人が数箇所でだけ判断すればよい反復手順、チーム単位で使う小さな内部ツールがここに入る。合わない方は三つに分かれる。第一に長時間のGPU学習や大型モデルの自前配信。第二に大容量の状態だ。Workersの隔離はJavaScriptヒープとWebAssemblyの割り当てを合わせて128MBなので、大きなデータをメモリに載せる方式は最初から入らない。第三に任意の外向き通信が必要な作業。サーバーコードはグローバルな外向きネットワークが無効な状態で動くため、外に出るにはその経路をケーパビリティとして明示しておく必要がある。

今すぐ社内の本番に入れてよいか?

本番投入は早い。公開リポジトリの案内文自体が、v2は相当使えるがまだ粗い部分が多く、活発な開発の最中だと書いている。セルフホスト配備のツールも準備中と表示されている。ライセンスはApache-2.0なので社内改造や再配布に障害はないが、ライセンスが開いていることと本番に載せる準備ができていることは別の話だ。今の時点で価値のある取り組みは三つ。一つ、自分のCloudflareアカウントに試験配置して、AccessポリシーとAI Gatewayの設定が社内規程と噛み合うか見る。二つ、Gatekeeperを一つ二つ自分で書いて権限分解の粒度をつかむ。三つ、128MBとCPUの上限に自分たちの作業が実際に入るか測る。

結論: 今日持ち帰る三つ

第一に、このプラットフォームの性格は機能一覧ではなく制約が決める。外向き既定遮断と隔離あたり128MB、この二行があれば、どんな作業がここに入りどんな作業が入れないかがほぼ全部整理される。発表文の華やかな部分より、この二行を先に自分の作業へ当ててみる方がずっと速い。

第二に、導入コストはプラットフォームの配置ではなくGatekeeperの個数だ。配置はアカウント一つで済むが、接続する外部システムごとに権限仲介Workerを書いて維持しなければならない。そしてそのコードは権限層なので誰にでも触らせるわけにいかない。接続対象の一覧を先に数えてみれば、導入規模の実体が出てくる。

第三に、観測記録に基づく共有制限は技術ではなく組織の決定だ。成果物を共有したのに相手が見られない状況が正常動作だと受け入れられて初めて、このプラットフォームの中核が働く。受け入れられなければその装置を切ることになり、そうなればただの社内チャットボットがもう一つ増えるだけである。

最後に一つ。今回の発表で長く残るのはCloudflare OSという名前ではない。エージェントに認証情報を渡す代わりにケーパビリティを渡し、何を読んだかを権限判断の入力にするという方向だ。この方向はどのプラットフォームを選んでも社内エージェント設計で再び出会うことになる。いま使えるかどうかとは別に、その設計原則だけは今読んでおく価値がある。
