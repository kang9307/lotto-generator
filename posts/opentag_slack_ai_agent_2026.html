OpenTag 출시 - Slack 스레드를 읽고 도구를 부르는 셀프호스팅 AI 에이전트

상용 Slack AI 태그 도구의 오픈소스·락인 없는 대안 - 셀프호스팅이 주는 것과 잃는 것

2026-07-07 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 협업 툴 안으로 들어오는 AI 에이전트

지난 몇 년 AI 어시스턴트의 이동 경로는 뚜렷하다. 독립된 챗봇 창에서 시작해 IDE 안의 코딩 에이전트로 옮겨갔고, 이제는 팀이 실제로 하루 종일 살고 있는 협업 툴 안으로 들어오고 있다. 결정과 질문 대부분이 Slack 스레드에서 벌어지는 조직이라면, "Slack을 떠나지 않고 AI에게 물어보고 시키는" 방향은 자연스러운 다음 단계다. 이 흐름의 최근 사례가 CopilotKit이 공개한 오픈소스 프로젝트 OpenTag다. Slack 스레드를 읽고, 질문에 답하고, 필요하면 등록된 도구를 호출해 그 결과를 표·차트 같은 형태로 대화창 안에 그려 넣는다.

겉모습만 보면 이미 여러 회사가 파는 "Slack에 Claude 태그하기"류 상용 앱과 크게 다르지 않다. 그러나 결정적 차이가 하나 있다. OpenTag는 코드 전체를 오픈소스로 공개하고, 벤더의 클라우드가 아니라 직접 운영하는 서버에서 돌리는 셀프호스팅 모델을 전제로 한다. 이 글은 hada.io에 소개된 GitHub 저장소(CopilotKit/OpenTag)와 공개 문서를 출발점으로 삼되, 그 소개를 그대로 옮기지 않는다. 실무에서 이런 도구를 실제로 붙인다면 무엇을 얻고 무엇을 떠안게 되는지, 셀프호스팅·오픈소스라는 선택이 정확히 무엇을 사고 무엇을 파는 거래인지 짚는다. 내용은 2026년 7월 기준으로 공개된 저장소 설명과 문서를 근거로 정리했다.

1. OpenTag란 무엇인가 - Slack 스레드 안에서 도구를 부르는 에이전트

1.1 스레드 컨텍스트를 읽고 답하는 봇

사용자가 Slack 채널이나 스레드에서 OpenTag를 멘션하면, 에이전트는 그 스레드의 이전 메시지와 참여자 맥락을 함께 읽고 응답한다. 단발 텍스트 답변에 그치지 않는다는 점이 핵심이다. 질문에 답이 필요하면 등록된 도구 - 사내 API 조회, 문서 검색, 티켓 시스템 연동 같은 - 를 실제로 호출하고, 그 결과를 다시 같은 스레드에 이어 붙인다. 즉 OpenTag는 "질문에 답하는 챗봇"이 아니라 "스레드 안에서 작업을 수행하는 에이전트"에 가깝다.

1.2 제너러티브 UI와 휴먼인더루프 승인 게이트

저장소가 강조하는 두 특징이 있다. 하나는 도구 호출 결과를 항목별 분해, 표, 막대그래프 같은 구조화된 형태로 Slack Block Kit 위에 렌더링하는 제너러티브 UI다. 텍스트 뭉치로 답하는 대신 사람이 바로 읽을 수 있는 형태로 바꿔 준다는 뜻이다. 둘째는 실제로 상태를 바꾸는 동작 - 예컨대 티켓을 생성하는 것 - 앞에 사람이 "승인" 버튼을 눌러야 실행되는 휴먼인더루프 게이트다. 채팅창에 도구 호출 권한을 쥔 에이전트를 붙일 때 가장 먼저 걱정되는 지점, 즉 "에이전트가 멋대로 뭔가를 저지르면 어떡하나"를 설계 단계에서부터 다루려 한 흔적으로 읽힌다. 다만 이 게이트가 안전을 완전히 보장하는 건 아니라는 점은 5장에서 다시 짚는다.

1.3 Slack 전용이 아니다 - 크로스플랫폼 봇 엔진

OpenTag의 코드 기반은 CopilotKit이 만든 오픈 SDK @copilotkit/bot이다. Slack이 1순위 타깃이지만, 같은 코드가 Discord·Telegram·WhatsApp에서도 동작한다. 플랫폼마다 렌더링 방식이 다른데(Slack Block Kit, Discord Components V2, Telegram HTML), 이 차이는 크로스플랫폼 JSX 레이어가 흡수한다. 운영 관점에서 저장소가 밝힌 최소 구성은 프로세스 두 개 - LLM을 호출하는 "에이전트"와 Slack 연결을 담당하는 "봇" - 와 시크릿 세 개다. 다만 기본값은 인메모리 스레드 상태이므로, 재시작 후에도 대화 맥락이 살아남게 하려면 별도의 영속 저장소를 직접 붙여야 한다. 이 부분이 "직접 운영"이 요구하는 첫 번째 숨은 숙제다.

2. 셀프호스팅·오픈소스가 주는 것 - 데이터 주권과 모델 선택

2.1 데이터 주권 - 프롬프트가 어디서 처리되는가

코드를 자체 서버에서 실행한다는 것은, Slack 메시지와 첨부, 그리고 그 위에서 호출하는 사내 API 응답이 외부 벤더의 클라우드를 거치지 않는다는 뜻이다. 2026년은 이 지점이 취향의 문제에서 규제의 문제로 넘어간 해다. EU AI Act의 여러 의무 조항이 2026년 8월부터 본격 적용되고, 고위험 시스템에는 로그 기록 의무(제12조)까지 걸린다. 여기서 놓치기 쉬운 함정 하나: "EU 리전에 호스팅된 SaaS"라고 해서 데이터 주권 문제가 자동으로 해결되는 건 아니다. 그 SaaS를 운영하는 회사가 미국 기업이면 미국 CLOUD Act의 관할을 받을 수 있다는 지적이 계속 나온다. 자체 인프라에서 도는 오픈소스 봇은 적어도 이 질문에서만큼은 "데이터가 어디로 나가는가"라는 변수 자체를 없앤다.

2.2 모델 선택의 자유와 락인 회피

상용 Slack AI 통합 다수는 특정 모델, 혹은 한 벤더의 모델 라인업에 사실상 고정된다. OpenTag는 "어떤 모델, 어떤 에이전트 하네스와도" 동작하도록 설계됐다고 밝힌다. 이는 가격이 오르거나 정책이 바뀌거나 더 나은 모델이 나왔을 때, 봇 전체를 새로 만들 필요 없이 백엔드만 교체하는 선택지를 준다. 이미 온프레미스 K8s나 자체 GPU, 사내 LLM 게이트웨이를 운영하는 팀에는 이게 추상적 장점이 아니라 실제로 실행 가능한 전환 경로다.

2.3 비용 구조의 전환

상용 도구는 대개 좌석당 월 구독료로 과금된다. OpenTag는 라이선스 비용이 없는 대신 인프라와 운영 시간이 비용이 된다. 사용자가 늘어도 좌석당 과금이 붙지 않는다는 점은 분명 매력적이다. 다만 이건 "공짜"가 아니라 비용의 성격이 구독료에서 인건비·인프라비로 옮겨가는 것뿐이라는 점을, 다음 장에서 정직하게 짚는다.

3. 관리형 서비스의 편의 - 잃는 것도 있다

3.1 셀프호스팅의 진짜 비용은 라이선스가 아니라 운영

OpenTag를 붙이는 순간 팀은 다음을 스스로 떠안는다. 봇·에이전트 프로세스의 상시 가동, Slack API 변경에 대한 대응, 시크릿 로테이션, 영속 저장소 구성과 백업, 도구별 권한 스코프 설계와 감사, 그리고 LLM API 요금·레이트리밋 관리다. 흥미롭게도 CopilotKit 스스로도 이를 인지한 듯 "매니지드 서비스가 곧 나온다(coming soon)"고 예고했다. 이는 뒤집어 보면 "직접 운영은 이만큼 손이 간다"는 사실을, 만든 회사 스스로 인정한 셈이기도 하다.

3.2 Slack 네이티브 AI·Dust·Glean과 비교

Slack 자체도 Business+/Enterprise+ 요금제에 채널·스레드 요약, AI 검색, 일일 리캡 같은 네이티브 AI 기능을 번들로 제공한다. 설정이 거의 필요 없고 SSO·권한 체계가 이미 Slack 안에 통합돼 있지만, 모델 선택권이 없고 Slack 요금제에 종속된다. Dust.tt는 MIT 라이선스로 코드를 공개하면서도 실제 사용자 대부분은 관리형 SaaS로 이용하며(좌석당 약 29달러부터), 멀티모델 지원과 100개 이상의 커넥터를 관리형으로 제공한다. Glean은 폐쇄형 엔터프라이즈 검색 제품(좌석당 50달러 이상)으로, 조직 지식 그래프 기반의 읽기 중심 어시스턴트에 강하지만 도구를 실행해 상태를 바꾸는 액션은 제한적이다. 이 셋과 나란히 놓으면 OpenTag의 위치가 뚜렷해진다 - "누가 대신 관리해 주지 않는 대신, 무엇을 어떻게 할지 전부 내가 정한다."

4. 실무 도입 시나리오 - 어떤 워크로드에 맞는가

4.1 잘 맞는 곳

이미 서버·컨테이너·CI를 운영해 본 개발/인프라 팀의 사내 봇으로는 자연스러운 선택이다. 온콜 런북 조회, 배포 상태 질의, 로그 요약, 티켓 초안 작성 같은 작업이 대표적이다. 승인 게이트가 있으니 "티켓을 만들어라"까지는 자동화하되, 실제 실행 직전에는 사람이 확인하는 안전판을 둘 수 있다. 사내 코드·배포 로그·내부 API 응답을 외부로 내보내고 싶지 않은 팀, 이미 자체 LLM 게이트웨이나 온프레미스 모델을 굴리고 있는 팀에도 잘 맞는다.

4.2 신중해야 할 곳

봇 프로세스를 직접 운영할 엔지니어링 리소스가 없는 비개발 조직에는 오히려 관리형 도구가 더 안전하다. 고객 대응처럼 24시간 무중단이 중요한 워크로드, 혹은 조달 규정상 벤더 SLA·지원 계약이 필수인 규제 산업도 셀프호스팅보다 관리형 쪽이 유리하다. 또한 "능동적으로 뭔가를 실행"하기보다 "이미 있는 사내 지식을 찾아내는" 것이 핵심 니즈라면, 지식 그래프 기반 검색에 특화된 Glean류 도구가 더 적합할 수 있다.

5. 보안 - 협업 툴에 도구 호출 권한을 주는 위험

5.1 프롬프트 인젝션과 스레드 컨텍스트

Slack 스레드 전체를 컨텍스트로 읽는다는 것은, 스레드에 누군가(악의적이든 실수든) 심어 넣은 텍스트가 곧바로 에이전트의 입력이 된다는 뜻이다. 도구 호출 권한을 가진 에이전트에서 프롬프트 인젝션은 단순한 오답을 넘어 원치 않는 액션 실행으로 이어질 위험이 있다. 승인 게이트는 이 위험을 줄이는 핵심 장치지만, 만능은 아니다. 게이트를 우회하도록 설계됐거나 실수로 그렇게 구성된 도구가 하나라도 있다면 이 안전판은 무력화된다.

5.2 권한 스코프 설계

실제 배포 전에 점검할 목록은 명확하다. 봇에 등록하는 각 도구가 최소 권한 원칙을 지키는지, Slack 앱의 OAuth 스코프가 필요 이상으로 넓지 않은지, 시크릿(Slack 토큰·LLM API 키)이 어디에 어떻게 저장되는지, 그리고 승인 게이트가 "되돌릴 수 없는" 동작 앞에 예외 없이 서 있는지다. 이는 OpenTag만의 문제가 아니라, 협업 툴에 도구 호출형 에이전트를 붙이는 모든 설계가 마주치는 공통 숙제다.

6. 데이터 거버넌스 큰 그림 - 2026년 규제 환경

2026년 들어 규제 환경은 "어디에 데이터를 두느냐"를 아키텍처 결정의 상위 항목으로 끌어올렸다. EU AI Act의 로그·감사 의무가 시행되기 시작했고, 규제 업계에서는 자체 인프라에서 프롬프트·응답·로그가 한 발짝도 나가지 않는 구성만이 거주지 요건을 계약이 아니라 사실로 증명한다는 지적이 나온다. 실무에서 관찰되는 절충안은 하이브리드다. 게이트웨이와 메모리 저장소는 자체 운영하되, 모델 자체는 특정 리전에 고정된 관리형 엔드포인트를 쓰는 구조다. OpenTag처럼 봇·에이전트 코드를 셀프호스팅하면서 LLM 백엔드만 리전이 고정된 API로 붙이는 조합도 이 절충안의 한 형태로 볼 수 있다. 완전 셀프호스팅(오픈웨이트 모델까지 자체 GPU에서)과 완전 관리형 사이에서, 팀의 규제 부담과 운영 역량에 맞는 지점을 고르는 것이 실제 과제다.

8. 결론 - 어떤 팀에 적합한가, 오늘 할 수 있는 일

OpenTag는 "상용 Slack AI 도구가 편한 건 알겠는데 데이터가 벤더로 나가는 게 걸린다", 혹은 "특정 모델·벤더에 묶이고 싶지 않다"는 팀을 위한 정직한 거래다. 라이선스 비용 대신 운영 부담을 지불하는 구조이며, 그 부담을 감당할 엔지니어링 역량이 있는 개발/인프라 팀에 가장 잘 맞는다. 반대로 그런 역량이 없거나 벤더 SLA·지원이 필요한 조직에는 Dust·Glean·Slack 네이티브 AI 같은 관리형 옵션이 여전히 합리적이다.

8.1 저위험 워크로드부터 파일럿하라

로그 요약, 온콜 런북 조회처럼 실패해도 피해가 작은 사내 워크로드 하나를 골라, 승인 게이트를 반드시 켠 채로 먼저 붙여 보라. 실제로 상태를 바꾸는 도구는 파일럿 단계에서 아예 빼도 좋다.

8.2 권한 스코프와 시크릿 관리를 먼저 문서화하라

도구별 최소 권한 스코프, Slack OAuth 스코프, 시크릿 로테이션 주기를 코드보다 먼저 문서로 정리하라. 프롬프트 인젝션은 완전히 막을 수 없어도, 권한 범위를 좁히면 피해 반경은 줄일 수 있다.

8.3 영속 저장소 없이 인메모리로 굴리지 마라

재시작 한 번에 스레드 맥락이 사라지는 구성으로 파일럿을 시작하면 신뢰를 잃기 쉽다. 영속 저장소를 먼저 붙이고, 재시작 후에도 맥락이 살아남는지 확인한 다음 실사용자에게 공개하라.
