LiteLLM을 2,900줄로 줄인 litelm - 라우팅만 남기고 무엇을 버렸나

10만 줄의 거대 프록시에서 호출 경로와 변환 계층만 추출한 경량화 아키텍처, 19개 제공자 라우팅과 AI 개발 투명성 고지의 실무적 의미

2026-09-13 개발/인프라

현대 생성형 AI 애플리케이션 개발에서 다양한 대규모 언어 모델 공급자를 단일 인터페이스로 추상화하는 작업은 선택이 아닌 필수가 되었다. OpenAI, Anthropic, Groq, Mistral 등 각 공급자마다 엔드포인트 규격, 파라미터 네이밍, 도구 호출 스키마, 오류 응답 형식이 제각각이기 때문이다. 이러한 이기종 공급자들의 파편화를 해결하기 위해 가장 널리 쓰여 온 파이썬 도구가 바로 BerriAI의 LiteLLM이다. 개발자는 completion(model="anthropic/claude-3-5-sonnet", messages=[...])과 같이 친숙한 OpenAI 포맷으로 다채로운 모델을 손쉽게 호출할 수 있었다.

그러나 프로젝트가 오랜 기간 진화하면서 LiteLLM은 단순한 클라이언트 변환 라이브러리를 넘어섰다. 독립 프록시 서버, Redis 기반 캐싱, 조직 단위 예산 관리 및 비용 추적 계층, 자체 가드레일, 에이전트 스케줄러, 멀티모달 처리기 등 수많은 기능이 추가되면서 코드베이스의 크기는 10만 줄(100k+ LOC) 이상으로 비대해졌다. 수많은 엔지니어링 조직에서 정작 필요로 하는 기능은 오직 「모델 라우팅과 메시지 규격 변환」이라는 핵심 실행 경로뿐인데도, 전체 패키지를 설치함에 따라 수십 개의 전이 의존성과 무거운 런타임 오버헤드를 함께 떠안아야 하는 상황이 벌어진 것이다.

오픈소스 개발자 Kenneth Wolters가 공개한 litelm(l이 하나 빠진 이름)은 바로 이 딜레마에 정면으로 도전하는 프로젝트다. 원작인 LiteLLM을 경쟁 상대로 대체하려는 것이 아니라, 그 방대한 코드베이스 밑바닥에 묻혀 있던 핵심 호출 경로만을 정밀하게 발라내어 약 2,900줄의 코드와 단 2개의 의존성(openai, httpx)으로 재구현한 최소주의적 부분집합(subset)이다. 이 글은 거대 프레임워크의 비대화가 실무 시스템에 미치는 영향, litelm이 의도적으로 버린 것과 남긴 것, 지원 제공자의 검증 현실, DSPy 통합 및 AI 보조 개발 투명성 고지가 제시하는 소프트웨어 엔지니어링의 새로운 표준을 심층 분석한다.

10만 줄의 프레임워크와 2,900줄의 코어 — litelm의 등장 배경

소프트웨어 라이브러리가 사용자층을 넓혀가는 과정에서 기능 추가(Feature Creep)가 누적되는 현상은 매우 자연스럽다. LiteLLM 역시 초기에는 「모든 LLM을 OpenAI 규격으로 호출한다」는 간결한 목표로 출발했으나, 엔터프라이즈 도입 기업들의 요구사항을 흡수하면서 구조가 급격히 팽창했다. 중앙화된 AI 게이트웨이 역할을 수행하기 위한 고성능 프록시 서버 데몬, 사용자별 API 키 발급 및 할당량 통제, SQLite와 Redis를 아우르는 캐시 백엔드, 오디오 전사, OCR, 이미지 생성, 파인튜닝 관리 파이프라인 등이 단일 리포지토리 안에 통합된 것이다.

하지만 마이크로서비스 내부나 단일 책임 원칙을 따르는 자율 코딩 에이전트, 가벼운 CLI 도구를 구축하는 개발자 관점에서 이러한 기능 확장은 적지 않은 기술 부채를 유발한다. 구체적으로 다음과 같은 네 가지 구조적 마찰이 발생한다.

  • 의존성 지옥과 공급망 위험: 프레임워크가 수많은 서드파티 공급자 SDK와 보조 유틸리티를 직간접적으로 참조함에 따라, 패키지 설치 용량이 커지고 종속성 충돌(Dependency Conflict)을 해결하기 위한 환경 설정 시간이 길어진다.
  • 보안 감사 및 취약점 대응 비용: 기업 내 보안 정책상 라이브러리에 포함된 모든 코드 라인은 정기적인 정적 분석(SAST)과 취약점(CVE) 스캔의 대상이 된다. 10만 줄에 달하는 방대한 코드베이스는 사용하지도 않는 컴포넌트에서 발생한 경고 때문에 배포 파이프라인이 차단되는 문제를 빈번하게 야기한다.
  • 런타임 메모리와 임포트 지연: 수많은 모듈을 탐색하고 임포트하는 과정에서 파이썬 프로세스의 시작 시간(Cold Start)이 늘어나며, 서버리스 함수(AWS Lambda, Cloudflare Workers 등) 환경에서 응답 지연의 원인이 된다.
  • 디버깅과 동작 예측의 난해함: 공급자 API 호출 도중 예기치 않은 오류가 발생했을 때, 요청이 내부 프록시 인터셉터, 캐시 핸들러, 비용 추적 훅 중 어디를 거치다 왜곡되었는지 추적하기가 매우 까다롭다.

litelm의 제작자 Kenneth Wolters는 바로 이 지점에 주목했다. 대다수 애플리케이션 개발자가 LiteLLM에 기대하는 핵심 가치는 오직 provider/model 형식으로 엔드포인트를 지정하고, 상이한 메시지 포맷을 자동으로 변환해 주는 호출 경로(call path) 그 자체라는 점이다. litelm은 거대한 부가 기능들을 완전히 털어내고, 라우팅과 메시지 변환 로직만을 약 2,900줄로 정갈하게 추출했다. 기본 의존성 또한 openai SDK와 비동기 HTTP 통신을 위한 httpx 단 2개로 압축하여 공급망 복잡도를 극소화했다.

무엇을 남기고 무엇을 버렸나 — 기능 포함 및 제외 비교

프레임워크의 크기를 10만 줄에서 2,900줄로 30분의 1 이하로 축소했다는 것은 그만큼 명확한 절단선(Cut-off)을 그었음을 의미한다. litelm은 단순히 코드를 압축한 것이 아니라, 프로덕션 애플리케이션의 핵심 런타임에 불필요하다고 판단된 아키텍처적 레이어를 과감하게 걷어냈다. 원문 README가 규정한 포함 기능과 제외 기능의 대비는 아래 표와 같다.

이 기능 대비표가 시사하는 바는 명확하다. litelm이 배제한 영역들은 결코 기술적 완성도가 떨어져서 빠진 것이 아니라, 클라이언트 라이브러리의 책임 범위를 벗어난 것들을 의도적으로 분리해 낸 결과다.

  • Router 클래스 배제: 공급자 간 로드밸런싱이나 오류 시 자동 폴백(Fallback)은 외부 API 게이트웨이나 상위 오케스트레이터가 담당해야 할 영역이지, 단일 프로세스 내 SDK가 쥐고 있을 필요가 없다는 판단이다.
  • 프록시 서버 배제: 백엔드 서버 데몬 프로세스를 제거함으로써 패키지를 순수한 인프로세스(In-process) 파이썬 라이브러리로 유지한다.
  • 캐싱과 비용 추적 배제: 데이터베이스 커넥션이나 캐시 만료 정책, 토큰 단가 테이블을 SDK 안에 내장하면 라이브러리 업데이트마다 단가 테이블 불일치가 발생한다. 이를 과감히 생략했다.
  • 토큰 카운팅 생략: 벤더마다 제각각인 토크나이저(Tiktoken 등) 바이너리를 라이브러리에 강제 결합하지 않고, 모델이 반환하는 원본 usage 객체 처리에 집중한다.
  • 멀티모달 및 파인튜닝 제외: 텍스트 생성과 임베딩이라는 주류 텍스트 LLM 워크플로에만 집중하여 코드 표면적을 극도로 좁혔다.
  • 가드레일 및 에이전트 추상화 제거: 비즈니스 로직에 깊게 얽히는 정책 필터링이나 에이전트 상태 관리를 상위 프레임워크의 자율에 맡긴다.

19개 제공자 라우팅과 검증 현황 — 실무 프로덕션의 경계선

litelm은 provider/model-name 문법을 통해 총 19개 제공자로의 라우팅을 지원한다. 또한 OpenAI 규격을 준수하는 모든 커스텀 또는 로컬 엔드포인트는 api_base 매개변수를 통해 제한 없이 연결할 수 있다. 하지만 여기서 엔지니어가 가장 냉정하게 직시해야 하는 사실은 지원(Supported)과 검증(Verified)의 차이다.

원문 README는 지원하는 제공자 목록과 함께, 실제로 동작을 신뢰할 수 있는지 나타내는 검증 여부를 투명하게 공개하고 있다. 아래 표는 litelm이 정의한 19개 제공자의 핸들러 방식 및 공식 검증 상태를 요약한 것이다.

이 검증 매트릭스는 실무 개발팀에게 매우 구체적인 지침을 제공한다. 현재 litelm이 자체 테스트 및 라이브 호출을 거쳐 신뢰성을 공식 확인(Verified: Yes)한 공급자는 OpenAI, Anthropic, Groq, Mistral, xAI, OpenRouter, Azure의 7곳이다. 이 7개 제공자를 주력으로 사용하는 시스템이라면 litelm은 즉시 높은 안정성으로 투입될 수 있다.

반면 AWS Bedrock, Cloudflare, DeepSeek, Together, Fireworks 및 로컬 서빙 도구(Ollama, vLLM, LM Studio)를 포함한 나머지 12개 공급자는 아직 미검증(Verified: No) 상태다. 이 공급자들의 경우 코드 레벨의 라우팅과 변환 핸들러는 작성되어 있으나, 업스트림 벤더의 최신 API 스키마 변경이나 세부 스트리밍 청크 구조와의 100% 호환성이 보장되지 않았음을 뜻한다. 따라서 프로덕션 도입 시에는 다음 네 가지 실무적 경계선을 반드시 준수해야 한다.

  • 검증 7개 공급자 중심의 1차 마이그레이션: 상용 클라우드에서 가장 호출 비중이 높은 OpenAI, Anthropic, Azure 및 초저지연 추론 벤더(Groq)를 대상으로 먼저 전환을 시도한다.
  • 미검증 제공자 사용 시 사전 통합 테스트 필수: DeepSeek이나 Bedrock을 litelm으로 호출하고자 할 경우, 사내 스테이징 환경에서 도구 호출과 스트리밍 동작을 반드시 직접 검증해야 한다.
  • 로컬 vLLM/Ollama 연동 시 호환성 확인: api_base를 통한 프라이빗 호스팅 환경 연동은 OpenAI 호환 인터페이스를 따르므로, 서빙 프레임워크의 엔드포인트 버전 호환성을 미리 체크해야 한다.
  • 패키지 버전 고정: 현재 프로젝트가 Alpha 상태이므로, 예상치 못한 릴리스 파손을 방지하기 위해 pyproject.toml 또는 requirements.txt에서 정확한 버전을 고정(Pinning)하여 운영해야 한다.

코드 변경을 최소화하는 드롭인 호환성 — 기본 호출부터 비동기·스트리밍까지

litelm이 설계상 가장 강력하게 내세우는 장점 중 하나는 기존 LiteLLM 코드와의 드롭인(Drop-in) 호환성이다. 기존에 LiteLLM을 사용하던 프로젝트라면, 애플리케이션 로직을 한 줄도 바꿀 필요 없이 임포트 문에서 s/litellm/litelm/ 치환만 수행하면 전환이 완료된다. 함수 시그니처, 매개변수 명세, 반환 객체의 형태가 완벽하게 동일하기 때문이다.

설치는 필요한 공급자 SDK에 맞추어 선택적으로 구성할 수 있다. 기본 설치 시에는 오직 openai와 httpx만 포함되며, 특정 클라우드 벤더의 공식 SDK가 필요한 경우 엑스트라 옵션을 통해 설치한다.

pip install litelm                # openai + httpx
pip install litelm[anthropic]     # + anthropic SDK
pip install litelm[bedrock]       # + boto3
pip install litelm[all]           # everything

기본적인 호출 흐름은 단일 완성(Completion), 스트리밍, 그리고 텍스트 임베딩으로 구성된다. 아래는 README 원문에 명시된 표준 사용 예제다.

import litelm

# 기본 완성 (Basic completion)
response = litelm.completion("openai/gpt-4o", messages=[{"role": "user", "content": "Hello!"}])
print(response.choices[0].message.content)

# 스트리밍 (Streaming)
for chunk in litelm.completion("groq/llama-3.1-70b-versatile", messages=[{"role": "user", "content": "Hello!"}], stream=True):
    print(chunk.choices[0].delta.content or "", end="")

# 임베딩 (Embeddings)
response = litelm.embedding("openai/text-embedding-3-small", input=["hello world"])

비동기 프로그래밍 환경을 위해 모든 주요 함수는 비동기 변형(Async variant)을 기본 제공한다. README에 명시된 비동기 함수는 acompletion, aembedding, aresponses, atext_completion의 네 가지다. 고성능 FastAPI 서버나 자율 에이전트 루프에서 I/O 블로킹 없이 동시 요청을 처리할 수 있다.

또한 이기종 공급자마다 제각각인 예외 응답을 통일된 계층 구조로 정규화해 주는 예외 처리 메커니즘을 제공한다. 공급자별로 다른 원본 HTTP 오류 코드를 분석할 필요 없이, litelm이 노출하는 표준 예외 클래스를 통해 일관된 장애 복구 로직을 작성할 수 있다.

from litelm import ContextWindowExceededError, RateLimitError, AuthenticationError

try:
    response = litelm.completion("openai/gpt-4o", messages=[{"role": "user", "content": "Hello!"}])
except ContextWindowExceededError:
    # 프롬프트 길이 초과 시 자르고 재시도 (prompt too long — truncate and retry)
    pass
except RateLimitError:
    # 속도 제한 시 지수 백오프 적용 (back off)
    pass
except AuthenticationError:
    # 유효하지 않은 API 키 처리 (bad API key)
    pass

에이전트 구현의 핵심인 도구 호출(Function Calling) 역시 표준 OpenAI 스키마를 그대로 따르며, 대상 공급자의 규격에 맞게 인수를 자동으로 직렬화한다.

tools = [{"type": "function", "function": { "name": "get_weather", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}}, }}]

response = litelm.completion(
    "openai/gpt-4o",
    messages=[{"role": "user", "content": "Weather in Paris?"}],
    tools=tools,
    tool_choice="required",
)

tool_call = response.choices[0].message.tool_calls[0]
print(tool_call.function.name, tool_call.function.arguments)

사내 인프라에 배포된 자체 호스팅 모델이나 개발용 로컬 런타임의 경우, api_base 매개변수를 넘겨주는 것만으로 손쉽게 라우팅할 수 있다.

# vLLM 연동
litelm.completion("openai/my-model", messages=[{"role": "user", "content": "Hello"}], api_base="http://localhost:8000/v1")

# Ollama 연동
litelm.completion("ollama/llama3", messages=[{"role": "user", "content": "Hello"}], api_base="http://localhost:11434/v1")

# LM Studio 연동
litelm.completion("openai/local-model", messages=[{"role": "user", "content": "Hello"}], api_base="http://localhost:1234/v1")

DSPy 연동과 업스트림 커밋 감사 — Alpha 단계의 안정성 검증

새로운 오픈소스 라이브러리가 등장했을 때 가장 우려되는 지점은 「실제 복잡한 LLM 오케스트레이션 프레임워크와 결합했을 때 미묘한 스키마 결함으로 깨지지 않는가」이다. litelm은 현재 Alpha 상태이지만, 이 호환성 검증을 위해 두 가지 엄격한 엔지니어링 절차를 거쳤음을 문서화하고 있다.

첫째는 스탠퍼드 대학교의 선언형 LLM 프레임워크인 DSPy와의 완전한 드롭인 연동 검증이다. DSPy는 프롬프트를 함수형 프로그램처럼 최적화하는 특성상 모델 호출 규격에 매우 민감하다. litelm은 다음 7개 실행 경로 전체를 실제 라이브 환경에서 통과시켰다.

  • Predict: 가장 기본적인 단일 입출력 예측 모듈 경로
  • CoT (Chain of Thought): 단계별 사고 과정을 생성하는 다단계 추론 경로
  • Typed Signatures: Pydantic 기반 타입 정의를 갖춘 엄격한 입출력 서명 경로
  • Streaming: 점진적 토큰 생성을 처리하는 스트리밍 파이프라인 경로
  • Embeddings: 벡터 유사도 계산을 위한 텍스트 임베딩 생성 경로
  • Tool Use: 외부 도구 및 파이썬 함수를 호출하고 결과를 재반영하는 경로
  • Multi-output: 다중 후보군 출력 및 구조화된 복수 필드 생성 경로

둘째는 업스트림 LiteLLM 커밋에 대한 정밀 감사(Attestation)다. 2026년 9월 11일 유지보수자 감사 보고에 따르면, LiteLLM의 라우팅 및 포맷팅 관련 변경 사항을 커밋 649eb2d부터 9a715df2까지 대조 검토했다. 이 과정에서 핵심 경로 커밋 360개를 선별하여 업스트림 테스트 케이스를 분석하고, 발견된 호환성 격차를 테스트 우선(Test-first) 방식으로 수정했다.

현재 litelm의 테스트 스위트는 로컬 스코프 테스트에서 262개 통과(262 passed, 55 skipped)를 기록하고 있으며, LiteLLM으로부터 이식된 계약 테스트(Ported tests) 75개 또한 전부 통과했다. 여기에 더해 실제 API 키를 사용하는 제공자 라이브 테스트 45개와 DSPy 스모크 테스트 10개 역시 현행 디펜던시 락 기준 전체 통과 상태다. 테스트 실행 명령어는 아래와 같다.

# 로컬 비-라이브 테스트 (262개 통과)
uv run --extra all pytest tests/ -x --ignore=tests/ported --timeout=10

# 업스트림 빠른 계약 테스트 (49개)
bash scripts/ported_contract.sh

# 제공자 라이브 테스트 (45개)
uv run --extra all pytest tests/test_live.py -m live --timeout=30

# DSPy 통합 스모크 테스트 (10개)
uv run pytest tests/test_dspy_smoke.py -m live --timeout=60

AI 보조 개발과 투명성 고지 — Claude와 GPT-5.5가 작성한 오픈소스의 의미

litelm의 README에서 기술적으로 가장 흥미롭고 선구적인 대목 중 하나는 개발 방식의 투명성 고지(Development transparency) 섹션이다. 저자는 자신이 만든 소프트웨어가 어떻게 작성되었는지를 숨기지 않고 명시적인 사실로 공개했다.

"litelm is human-directed, AI-assisted software. Much of the code was written with Claude Code using Claude Opus 4.6/4.7. Code written from 2026-05-14 onward is written through Pi using GPT-5.5. Compatibility claims are based on tests and maintainer review, not AI authorship."

이 고지문은 현대 오픈소스 생태계에서 AI 코딩 에이전트의 역할과 엔지니어링 윤리에 대해 세 가지 중요한 사실을 전달한다.

  • 인간 주도와 AI 보조의 명확한 선언: 아키텍처 설계와 기능 절단선 결정은 인간 엔지니어의 방향 설정(Human-directed) 하에 이루어졌으며, 코드 생성 과정에 Claude Code 및 Claude Opus 4.6/4.7 모델이 활용되었음을 구체적으로 명시했다.
  • 도구 진화의 타임라인 기록: 2026년 5월 14일 이후 작성된 코드부터는 Pi(도구)와 GPT-5.5를 통해 개발 도구를 전환했음을 날짜 단위로 투명하게 기록했다. 이는 소프트웨어 개발 역사에서 모델 세대교체의 흔적을 남긴 드문 사례다.
  • 품질 보증의 본질적 근거 확립: 가장 중요한 지점은 "호환성 주장의 근거는 AI가 작성했다는 사실 자체가 아니라, 철저한 테스트 스위트와 유지보수자의 코드 검토에 있다"고 명시한 점이다. AI가 코드를 작성했든 사람이 작성했든, 소프트웨어의 신뢰성은 엄격한 테스트 통과와 인간의 책임 있는 검토로 증명된다는 원칙을 분명히 한 것이다.

AI 코딩 에이전트가 소프트웨어 개발의 주류 도구로 자리 잡은 시점에서, 어떤 AI 모델과 프롬프트 도구로 작성되었는지를 문서 상단에 투명하게 공개하는 이러한 관행은 향후 오픈소스 생태계의 신뢰 구축 모델에 있어 매우 긍정적인 선례를 제시한다.

클라이언트 SDK 최소화와 프록시 라우터의 차이 — 아키텍처 선택 기준

LLM 라우팅 기술을 검토할 때 엔지니어들이 종종 혼동하는 대목은 「인프로세스 클라이언트 라이브러리」와 「독립 프로세스 프록시 라우터」의 차이다. 본 블로그의 선행 분석인 모든 요청을 비싼 모델에 맡기지 않는다 - API를 그대로 두고 모델만 바꿔 끼우는 LLM 라우터와 Switchyard 글에서 다룬 NVIDIA NeMo Switchyard가 네트워크 계층에서 동작하는 프록시 라우터라면, litelm은 애플리케이션 프로세스 안에서 직접 링크되는 가벼운 클라이언트 SDK다.

이 두 접근법은 상호 배타적인 것이 아니며, 시스템 아키텍처의 요구 조건에 따라 선택의 축이 완전히 달라진다. 엔지니어링 팀은 다음 네 가지 기준에 따라 적절한 도구를 선택해야 한다.

  • 단일 파이썬 프로세스 vs 다중 언어 분산 환경: 순수 파이썬 환경에서 빠른 임베딩과 호출 변환만 필요하다면 litelm과 같은 인프로세스 경량 SDK가 네트워크 지연시간과 서버 운영비 없이 최적의 성능을 낸다. 반면 Go, Java, Node.js 등 다양한 언어로 작성된 마이크로서비스들이 단일 AI 관문을 공유해야 한다면 Switchyard나 LiteLLM Proxy 같은 외부 게이트웨이가 필수적이다.
  • 정적 호출 라우팅 vs 런타임 실패 신호 기반 라우팅: provider/model 규격에 따라 요청을 적절한 공급자로 전달하는 것이 목적이라면 litelm으로 충분하다. 하지만 에이전트가 도구 실행 도중 에러를 냈을 때 상위 모델로 동적 에스컬레이션(Stage Router)하는 런타임 적응형 제어가 필요하다면 Switchyard와 같은 지능형 라우팅 계층이 요구된다.
  • 운영 복잡도와 공격 표면적 최소화: 컨테이너 이미지 크기를 줄이고, 불필요한 데몬 프로세스 없이 서버리스 환경에 배포하고자 할 때는 2,900줄의 litelm이 압도적인 유지보수성 우위를 점한다.
  • 캐싱과 중앙 통제 필요성: 전사적인 토큰 쿼터 제어, Redis 프롬프트 캐시 공유, 감사 로그 저장이 반드시 필요한 중앙 플랫폼 팀의 경우, 거대한 기능을 갖춘 원작 LiteLLM이나 전용 API 게이트웨이를 선택하는 것이 자연스럽다.

결국 litelm의 가치는 거대 프레임워크를 맹목적으로 추종하기보다, 자신의 시스템이 진정으로 필요로 하는 최소한의 코드와 의존성만을 취사선택할 수 있는 엔지니어링 선택권을 회복시켜 준 데 있다.

확인하지 못한 것

공개된 소스 코드와 기술 문서의 범위 제한으로 인해 본 분석 과정에서 독립적으로 검증하지 못한 사항들은 다음과 같다.

  • 대규모 동시성 비동기 루프에서의 성능 및 메모리 실측 벤치마크: 초당 수천 건 이상의 동시 요청이 발생하는 고부하 asyncio 환경에서 litelm과 원작 LiteLLM 간의 P99 응답 지연시간 및 메모리 점유율 차이를 직접 측정한 공식 벤치마크 데이터는 공개되어 있지 않다.
  • Alpha 탈피 및 정식 v1.0.0 출시 로드맵: 현재 패키지가 Alpha 상태로 명시되어 있으나, 하위 호환성을 보장하고 안정적인 엔터프라이즈 지원을 약속하는 v1.0.0 정식 릴리스 일정은 문서에 명시되지 않았다.
  • 미검증 제공자(Bedrock, DeepSeek 등)의 세부 엣지 케이스 동작: 12개 미검증 공급자에 대한 단위 테스트 케이스의 존재 여부와 실제 라이브 API 호출 시 스트리밍 청크 누락이나 비표준 오류 반환 여부는 직접 검증하지 못했다.
  • 대규모 상용 저장소에서의 실전 마이그레이션 회귀 사례: LiteLLM에서 litelm으로 전환한 실제 프로덕션 서비스에서 발생한 예상치 못한 버그나 역호환성 결함에 대한 엔지니어링 사례 보고는 아직 보고되지 않았다.
