The Process Died Without a Word - How to Read the OOM Killer

When the application log is empty, the order in which you pick the culprit out of what the kernel left behind

2026-09-02 Dev & Infra

The process is gone. The last line of the application log is an ordinary record of a request being handled, and after it there is nothing. No exception stack, no parting message from a shutdown hook. The monitoring tool tells you only that the process no longer exists.

The time most often wasted here goes into digging through the application log more carefully. It is not there. It cannot be there. SIGKILL is not a signal the process receives and handles but an operation that ends the process where it stands, so at that moment the application never gets the chance to write a single character. The first move, then, is not to dig deeper into the log but to change the hypothesis. It did not die. It was killed.

The environment this article was written in is Windows 10 with Git Bash (MSYS2, GNU bash 5.2.37(1)-release). There is no Linux kernel, no cgroup and no dmesg here, so every kernel behavior, field definition and file path below was confirmed against the official kernel.org documentation and the kernel source. No OOM log was reproduced and pasted in. The only thing actually executed and confirmed in this environment is the exit code rule, and that output appears verbatim in the body. The line between what was verified and what was not is collected in the second-to-last section.

Why the application log says nothing

The kernel memory management documentation describes the OOM killer this way. It is possible that on a loaded machine memory will be exhausted and the kernel will be unable to reclaim enough memory to continue to operate, and in order to save the rest of the system it invokes the OOM killer. And it goes on to say that the OOM killer selects a task to sacrifice for the sake of the overall system health. The important word is selects. The choice happens on the kernel side, and the one selected is never notified.

So everything the application normally leaves behind drops out at once. An exception stack requires an exception, and no exception occurred. A shutdown hook needs a catchable signal, and SIGKILL cannot be caught. Log lines still sitting in a buffer disappear without being flushed. The fact that the last log line looks ordinary is itself the signal, not evidence that there is no information.

  • What is not left behind — exception stacks, traces of shutdown hooks running, unflushed log buffers, the exit code the application records for itself
  • What is left behind — the OOM record in the kernel ring buffer, the exit status the parent process received, the termination reason attached by the container runtime, the last value the metrics collector scraped
  • The order is inverted — normally the application log is the primary source and the kernel log is secondary. In this incident it is the other way around
  • The point where metrics stop is a hint — with a 15-second scrape interval there is no value for the last 15 seconds before death. Even if the final point looks calm, there may have been a spike in between

It did not die, it was killed - 137 and OOMKilled

The basis for switching hypotheses is the exit code. When a command terminates on a fatal signal, the shell reports 128 plus the signal number as the exit status. That rule behaves the same way for the same shell even outside Linux, so it could be confirmed directly in the Git Bash this article was written in.

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ bash -c 'kill -9 $$'; echo "exit=$?"
/usr/bin/bash: line 1:  1419 Killed                  bash -c 'kill -9 $$'
exit=137

$ bash -c 'kill -15 $$'; echo "term_exit=$?"
Terminated
term_exit=143

Signal 9 is SIGKILL, so 128 plus 9 is 137, and signal 15 is SIGTERM, so 143. What deserves attention is that 137 tells you less than people assume. It says only that the process was force-terminated. Who sent the SIGKILL is not contained in it. It could be the kernel OOM killer, it could be an orchestrator finishing up after the grace period expired, it could be a batch script.

SignalNumberExit code the shell reportsWhat this code tells you
SIGTERM15143There was a chance to clean up. What it did is in the application log
SIGKILL9137Terminated immediately. Who sent it can only be learned by cross-checking the kernel log
SIGSEGV11139Invalid memory access. A different event from running out of memory
SIGABRT6134The runtime itself gave up. Seen in implementations that treat allocation failure as abort
Normal exit-0 ~ 125A value the application chose. Not a forced termination

Signal numbers follow the platform's signal table. The 6, 9, 11 and 15 above are stable across Linux, but not every number is. In the MSYS environment this article was written in, kill -l prints signal 7 as SIGEMT, while on Linux x86 signal 7 is SIGBUS. Printing that system's own table once is safer than memorizing numbers.

In containers there is one more label. The runtime records the termination reason as OOMKilled and the orchestrator exposes it in the pod status. That is more explicit than an exit code, but it still does not tell you which kind of OOM it was. A node running out entirely and a container hitting its own limit come back wearing the same label.

The Kubernetes documentation adds that memory limits are enforced reactively. When a container uses more than its memory limit the kernel may terminate it, but terminations only happen when the kernel detects memory pressure, so a container that over allocates memory may not be immediately killed. That is the answer to it was over the limit yesterday too, so why did it die today.

Where to look

The kernel writes to one place, but there are several windows onto it and each window keeps records for a different length of time. That difference is why the conclusion there is no record is so often wrong.

# 1) Kernel ring buffer - fastest, but does not stay long
dmesg -T | grep -i -E 'out of memory|oom-killer|killed process'

# 2) Journal - kernel messages only, narrowed to a time range
journalctl -k --since '2 hours ago' | grep -i -E 'oom|killed process'

# 3) If a reboot happened in between, walk back by boot
journalctl --list-boots
journalctl -k -b -1 | grep -i 'killed process'

# 4) When the ring buffer has already rolled - the path differs by distribution
grep -i -E 'oom-killer|killed process' /var/log/messages
grep -i -E 'oom-killer|killed process' /var/log/syslog

The ring buffer dmesg reads is fixed in size, so new messages push the oldest ones out. On a node where storage or network messages are printed several lines per second, an OOM record from a few hours ago is already gone. The conclusion it is not in dmesg, so it was not OOM only holds once you have confirmed the ring buffer did not roll. The journal disappears with a reboot too if its storage is volatile. How far back logs survive is a subject of its own, and the traps that rotation settings create are covered separately in where log rotation quietly goes wrong.

The container-side windows are held by the runtime and the orchestrator. You often work without permission to reach the kernel log, so these are the ones within reach first.

# Kubernetes - the reason and code of the previous termination
kubectl describe pod <pod> | sed -n '/Last State/,/Restart Count/p'
kubectl get pod <pod> -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\t"}{.lastState.terminated.reason}{"\t"}{.lastState.terminated.exitCode}{"\n"}{end}'

# Docker - the OOMKilled flag and the exit code on one line
docker inspect --format '{{.Name}} oom={{.State.OOMKilled}} exit={{.State.ExitCode}}' <container>

# If you can get onto the node, line the timestamps up with the kernel side
journalctl -k --since '2026-09-02 09:00' --until '2026-09-02 10:00'

This is where the first fork appears. If the container status is OOMKilled but the node's kernel log has no system OOM record, the node was fine and the incident belongs to the cgroup limit. Conversely, if several pods died at the same moment and the kernel log holds a dump of node-wide memory state, it is the node. Raising a limit or adding a node before passing this fork is a coin flip.

How to read the table the kernel prints

When the kernel performs an OOM killing it dumps the task list as a table, and that behavior is switched on and off with a sysctl. The kernel sysctl documentation says oom_dump_tasks enables a system-wide task dump excluding kernel threads that includes such information as pid, uid, tgid, vm size, rss, pgtables_bytes, swapents, oom_score_adj score and name. The kernel source's header-printing function shows the same thing plainly: the dump is gated on that sysctl value.

The strings that reach the log come in three chunks. Below are the format strings copied straight from the kernel source; actual values are filled into the %s and %d positions when printed.

# (1) Who invoked the OOM killer - dump_header()
%s invoked oom-killer: gfp_mask=%#x(%pGg), order=%d, oom_score_adj=%d

# (2) Column names of the candidate list - dump_tasks()
[  pid  ]   uid  tgid total_vm      rss rss_anon rss_file rss_shmem pgtables_bytes swapents oom_score_adj name

# (3) The conclusion - __oom_kill_process()
%s: Killed process %d (%s) total-vm:%lukB, anon-rss:%lukB, file-rss:%lukB, shmem-rss:%lukB, UID:%u pgtables:%lukB oom_score_adj:%d

Most people read (3) and stop. But (3) is the conclusion, and the list of candidate causes is in the table that follows (2). Without reading the table you cannot answer why that process, and if you cannot answer it the same thing happens again next time.

ColumnUnitWhat it isIts use in picking the culprit
total_vmpagesSize of the virtual address spaceLow. It includes regions that were only reserved and never used
rsspagesTotal amount resident in physical memoryStart here. Sorting descending narrows the candidates
rss_anonpagesThe part with no file backing. Heap and stackFirst suspect for a leak. Swap is the only way to reclaim it
rss_filepagesMapped file pagesMostly reclaimable. A process large only in this column is likely not the culprit
rss_shmempagestmpfs and shared memory/dev/shm usage. Looks like files but is not reclaimed
pgtables_bytesbytesMemory the page tables themselves useGrows with many threads or with finely fragmented mappings
swapentspagesNumber of pages swapped outWith swap, rss looks smaller than reality. Read both together
oom_score_adjnoneThe weight applied to the selectionIf the process that died is not first by rss, the answer is in this column
namenoneExecutable nameTruncated if long. With duplicate names, match by pid

Two things are easy to get wrong while reading. One is that the unit is pages. Only pgtables_bytes, which carries _bytes in its name, is in bytes; the remaining memory columns are page counts. Page size varies with architecture and configuration, so confirm that system's value before multiplying. The other is that the column layout differs by kernel version. The list in the sysctl documentation above and the header string in the current source already disagree (the source has rss_anon, rss_file and rss_shmem in addition). Read the header line in your own log first and line the columns up against it.

# Pull just the table out of a saved log
# Column numbers differ per kernel version, so always print the header line with it
awk '/\[ *pid *\]/{print; f=1; next} f && /^\[/{print} f && !/^\[/{f=0}' oom.log | head -40

# Count which position rss occupies in the header, then sort (below assumes the 4th)
awk '/^\[/{print $4, $NF, $0}' oom.log | sort -nr | head -20

Why that particular process died

The kernel scores each candidate for badness and picks the highest. In the current source that calculation starts from adding RSS, the number of swap entries, and the page table size converted into pages. It is an estimate of how many pages come back if this process ends right now. Then oom_score_adj is added, and not raw: it is multiplied by total pages divided by 1000 before being added.

That multiplication is what matters in practice. One point of oom_score_adj converts to the page count of 0.1 percent of total memory, so a process with this value raised to 100 is treated as though it were using an extra 10 percent of total memory. On a 128GiB node that is an extra 13GiB. This is the arithmetic reason the process using the most memory dies is not always true.

Per the kernel documentation the range of this value is -1000 to +1000. The documentation says of the lowest value, -1000, that it is equivalent to disabling OOM killing entirely for that task, because it will always report a badness score of 0. It also notes that the value exposed through /proc/<pid>/oom_score already includes this weight, making its effective range 0 to 2000.

# The current score and weight for one process
cat /proc/<pid>/oom_score
cat /proc/<pid>/oom_score_adj

# Sweep for processes whose weight is not 0 (find out who has been touching it)
for p in /proc/[0-9]*; do
  a=$(cat "$p/oom_score_adj" 2>/dev/null) || continue
  [ "$a" = "0" ] && continue
  printf '%s\t%s\t%s\n' "${p#/proc/}" "$a" "$(tr -d '\0' < "$p/comm")"
done
  • The kernel works in units of the thread group, not a single thread. That is why the table has a tgid column
  • Monitoring agents and sidecars usually score low because they use little memory. So the one that dies is the main process, and after it dies the agent lives on to report process not found
  • The reverse also happens: a weight raised on a sidecar and then forgotten. If something using far less memory dies first, suspect this column
  • Orchestrators sometimes set this value according to workload class. It can be non-zero even if you never touched it
Risk note. Lowering oom_score_adj to -1000 removes that process from the candidate pool; it does not give it more memory. The shortage remains and something else dies instead. Exempt the database and the monitoring agent next to it dies, and then nobody tells you about the incident. An exemption is not a fix but a reordering of who dies, so it is a value to touch only after deciding what is acceptable to lose in its place.

A system OOM and a cgroup OOM are different events

The kernel source contains the point where these two diverge in a single line. When it calls the OOM handling function it picks the message string with a ternary operator, passing "Out of memory" when it is not a memory cgroup OOM and "Memory cgroup out of memory" when it is. That string goes into the leading %s of format (3) from the previous section. The first word of the log tells you which kind of event it was.

AspectSystem (node) OOMcgroup OOM
TriggerReclaim failed across the whole nodeThat cgroup reached its own limit
Log prefixOut of memory: Killed process ...Memory cgroup out of memory: Killed process ...
Candidate scopeEvery process on the nodeThat cgroup and its descendants
Free memory on the nodeNone. That is why this happenedCan be plentiful. The dashboard looks calm
What dies alongsideUnrelated workloads get shaken tooOnly that container dies
Common misdiagnosisBlaming an application leakAdding nodes
Where to look first/proc/meminfo, the memory dump in the kernel logmemory.events, memory.max, memory.current

The kernel cgroup v2 documentation defines memory.max as the memory usage hard limit and says that if a cgroup's memory usage reaches this limit and cannot be reduced, the OOM killer is invoked in the cgroup. memory.high is different. If usage goes over the high boundary the processes of the cgroup are throttled and put under heavy reclaim pressure, but going over the high limit never invokes the OOM killer, the same document says. high is a brake; max is a wall.

# From inside the container - cgroup v2
cat /sys/fs/cgroup/memory.max        # the wall. max means no limit
cat /sys/fs/cgroup/memory.high       # the brake
cat /sys/fs/cgroup/memory.current    # how much is in use right now
cat /sys/fs/cgroup/memory.events     # read low/high/max/oom/oom_kill here
cat /sys/fs/cgroup/memory.stat | head -20

# When pointing at a specific cgroup path from the node
cat /sys/fs/cgroup/kubepods.slice/.../memory.events

The two values in memory.events mean different things, and that difference works as a forecast. The documentation defines oom as the number of times the cgroup's memory usage reached the limit and allocation was about to fail, and oom_kill as the number of processes belonging to this cgroup killed by any kind of OOM killer. So if oom is climbing while oom_kill is 0, nobody has died yet, and that is an advance notice of dying at the next deployment or the next peak. Alert on this value and you can act before the fact rather than after it.

The same document has memory.oom.group. It determines whether the OOM killer should treat this cgroup as an indivisible workload, and when set, all tasks in the cgroup and its descendants are killed together or not at all. It is the switch that prevents one process dying while the rest keep running at half capacity.

How the runtime itself perceives the memory limit is another layer. Runtimes that infer heap size from the container limit, like the JVM, have traps of their own, and that is covered separately in when the JVM inside a container misreads the limit. This article stays with the kernel and cgroup generalities.

What changes between cgroup v1 and v2

The same memory limit 512Mi can mean different things in the two versions. The file names differ to begin with, and so does the way swap is counted.

# Which version is running - cgroup2fs alone means v2 only
stat -fc %T /sys/fs/cgroup
mount | grep -E 'cgroup|cgroup2'

# The files you read on the v1 side
cat /sys/fs/cgroup/memory/memory.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.usage_in_bytes
cat /sys/fs/cgroup/memory/memory.failcnt
cat /sys/fs/cgroup/memory/memory.memsw.limit_in_bytes
cat /sys/fs/cgroup/memory/memory.oom_control
grep -E '^(cache|rss|mapped_file) ' /sys/fs/cgroup/memory/memory.stat
  • How swap is counted. v1 sets the limit on memory and swap combined through memory.memsw.limit_in_bytes. v2 sets swap separately through memory.swap.max. This is the classic place where the same number means something different
  • Accuracy of the usage value. The v1 documentation admits that memory.usage_in_bytes does not show an exact value, and directs you to RSS plus CACHE (plus SWAP) in memory.stat for a more precise reading
  • The failure counter. v1's memory.failcnt counts how many times the limit was hit. What takes its place in v2 is memory.events
  • The procedure on hitting the limit has the same skeleton. The v1 documentation says that when a cgroup goes over its limit the kernel first tries to reclaim memory from the cgroup, and if the reclaim is unsuccessful an OOM routine is invoked to select and kill the bulkiest task
  • The switch that disables OOM killing. v1's memory.oom_control has oom_kill_disable and under_oom. The documentation says that when under_oom is 1 the memory cgroup is under OOM and tasks may be stopped
Risk note. Turning on v1's oom_kill_disable means the process does not die but stops instead. It is alive in the process list and may even pass a health check depending on its type, while handling no requests at all. Dying and being restarted is often the better outcome, so consider this value only when you have a separate way to detect that state.

Overcommit - why you die even though malloc succeeded

Linux promises more memory than it actually has by default, because doing so pays off in most cases. A process that calls exec right after fork barely touches the address space it copied, and code that reserves a large array up front and uses only the beginning is common. Physical pages are attached on the first write to that address.

So the failure arrives late. The allocation function succeeds in obtaining address space, and death comes at the moment of the first write to that address. In the code it looks like dying on the line after a successful allocation. That is why no matter how carefully you write allocation-failure handling, control never reaches that path.

vm.overcommit_memoryWhat the kernel documentation saysWhat actually happensSide effect
0 (default)The kernel compares the userspace memory request size against total memory plus swap and rejects obvious overcommitsMost requests get throughFailure shows up as an OOM at use time rather than at allocation time
1The kernel pretends there is always enough memory until it actually runs outNearly every request succeedsThe allocation-failure signal disappears and every problem converges on OOM
2The kernel uses a never overcommit policy that attempts to prevent any overcommit of memoryCommits beyond CommitLimit are refused outrightAllocations that used to succeed start failing

The overcommit accounting documentation describes the limit in mode 2 as swap plus a configurable amount of physical RAM, defaulting to 50 percent. That percentage is set with vm.overcommit_ratio and the absolute value with vm.overcommit_kbytes, and both take effect only in mode 2. It also states that the current limit and the amount committed are viewable in /proc/meminfo as CommitLimit and Committed_AS.

sysctl vm.overcommit_memory vm.overcommit_ratio vm.overcommit_kbytes

# How much has been promised - see how close Committed_AS sits to CommitLimit
grep -E '^(MemTotal|SwapTotal|CommitLimit|Committed_AS):' /proc/meminfo

Per the documentation Committed_AS is the amount of memory presently allocated on the system, a sum of all memory allocated by processes, with the caveat that it counts even memory that has not been used by them as of yet. So this value comfortably exceeding MemTotal is normal and is evidence that overcommit is working. It is not a value to treat as a problem.

Risk note. Changing vm.overcommit_memory to 2 replaces OOM with allocation failure. Processes that reserve large and use little may not even start. Changing it immediately with sysctl on a production node shakes every service at once, so first measure the normal trend of Committed_AS against CommitLimit for several days and confirm startup in staging before doing it.

What swap changes

With swap, the kernel gains one more place to reclaim from. Anonymous pages can be pushed out to the storage device and their frames reused, so OOM arrives later. In exchange that stretch is slow. Whether that slowness is better than dying depends on the nature of the service.

The kernel PSI documentation splits this state into two lines. some is the share of time in which at least some tasks are stalled on a given resource, and full is the share of time in which all non-idle tasks are stalled on a given resource simultaneously. The document describes the full state as wasteful CPU cycles and says it indicates thrashing. If full is climbing, the node simply has not died yet; it is already not working.

swapon --show
free -h
grep -E '^(SwapTotal|SwapFree|SwapCached):' /proc/meminfo

# The share of time currently stalled - read some and full separately
cat /proc/pressure/memory
cat /sys/fs/cgroup/memory.pressure

# Which processes are sitting in swap
grep -H VmSwap /proc/[0-9]*/status | sort -t: -k3 -n -r | head -10

The practice of disabling swap in container environments has this behind it: for some services, response latency is worse than dying. A response that takes 30 seconds has already failed, but the process is alive and passes the health check, so traffic keeps arriving and the state gets worse. In that case dying fast and restarting fast is better for overall availability.

  • The Kubernetes documentation states that by default the kubelet will not start on a Linux node that has swap enabled. To make it start you must set failSwapOn: false explicitly
  • Swap behavior is set with memorySwap.swapBehavior. Under the default NoSwap, workloads running as pods on that node do not and cannot use swap; under LimitedSwap they can
  • The same document carries a clue worth noting. Even with NoSwap and swap tolerated, processes outside of Kubernetes-managed containers, such as systemd services and even the kubelet itself, can utilize swap. Non-zero swap usage on a node does not mean the pods are using it
  • The kubelet directs the container runtime through the runtime API, and the example the document gives for the cgroup v2 case is memory.swap.max. It connects straight back to the file from the previous section
  • If you decide to enable swap, decide first how much latency is acceptable. Without that decision, a permanent state of not dying but always slow sets in, and that state rarely triggers an alert
Risk note. On a production node, swapoff -a reads every swapped-out page back into physical memory. If free physical memory at that moment is smaller than swap usage, it invokes an OOM on the spot. Before disabling, check that SwapTotal minus SwapFree fits inside MemAvailable, and turn devices off one at a time during a low-traffic window.

RSS is not the whole story

The value most often misread when looking at memory is the free column of free. The free manual defines free as unused memory only, and computes used as total minus available. On the kernel side the counterpart of that available is MemAvailable in /proc/meminfo, which the kernel documentation defines as an estimate of how much memory is available for starting new applications, without swapping, calculated from MemFree, SReclaimable, the size of the file LRU lists and the low watermarks in each zone. The value to read is available, not free.

free -h
grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|Cached|Shmem|Slab|SReclaimable|SUnreclaim):' /proc/meminfo

# The breakdown for one process - VmRSS is the sum of the three below
grep -E '^(VmRSS|RssAnon|RssFile|RssShmem|VmSwap):' /proc/<pid>/status

# The place that looks like files but is memory
df -h /dev/shm
  • Page cache is not locked memory. It is reclaimed when needed. A large cache making free look small is normal, and reporting that state as a memory shortage sends you to fix the wrong thing
  • Shared memory and tmpfs are different. What piles up in /dev/shm looks like files but is memory and is not reclaimed the way cache is. The kernel documentation defines Shmem as the total memory used by shared memory and tmpfs
  • Kernel slab uses memory too. SReclaimable is the part that might be reclaimed and SUnreclaim is the part that cannot be reclaimed under memory pressure. If the latter has grown large, no amount of digging through userspace produces an answer
  • Do not sum RSS. Per the kernel documentation VmRSS comprises RssAnon, RssFile and RssShmem, and pages shared between processes such as shared libraries are counted once per process. Estimating node usage by adding per-process RSS gives a number larger than reality
  • Processes holding files count as memory as well. How to find a process holding a deleted-but-open file or a large mapping is laid out in which process is holding this file

OOM is a symptom, not a cause

An OOM kill tells you memory ran out, not why it ran out. And the why is not in the snapshot of the moment of death but in the shape of the stretch before it. At the moment of death everything has already grown, so cause and effect are indistinguishable. In that one symptom has many causes and you must separate them in a fixed order, it is the same kind of problem as No space left on device while the disk is not full.

  • Leak — rises in proportion to time. After a restart it rises again at the same slope. If it rises overnight with no traffic, it is close to confirmed
  • Traffic surge — rises in steps and lines up in time with the traffic graph. It comes back down after the peak. If it does not come down, a surge and a leak are overlapping
  • A misconfigured limit — starts right after a deployment. Putting the previous deployment's manifest side by side settles it in minutes, so it goes early in the order
  • An unbounded cache — the hit rate keeps improving and memory keeps climbing. Invisible at low load, it blows up all at once when load rises. Check first whether a maximum entry count or maximum byte size is set
  • A growing result set — queries without pagination, lists inflated by re-reading related data per row. This is usually the category behind code that did not change but blew up one day, and its slope is gentle enough to miss
  • Concurrency numbers — buffer size per request times concurrent requests. It blows up the day after someone raises worker count or connection pool size. Look for it in the configuration change history, not the deployment history
  • The neighbors — a system OOM in which our process happened to be selected. The cause is another workload on the same node and ours was merely large, so no amount of reading our code turns anything up
  • Other consumers on the node — non-container things like log shipping daemons, backup agents, kernel slab. If the sum of pod usage and node usage diverge widely, it is this

If you had to pick one thing most useful for separating them, it is the shape of the slope. Straight, stepped or sawtooth: that alone removes half the candidates. Which is why the first thing to secure in a post-mortem is not logs but the memory time series for the hours before death. Without it the investigation becomes guesswork.

How to prevent it - limits, requests and the restart loop

Setting a limit is necessary but not sufficient. The scheduler decides placement by looking at requests, so if requests are missing or much smaller than reality, pods get packed onto one node. Then the per-container limits hold while the node as a whole falls over first. The Kubernetes documentation says that when a node runs out of resources Kubernetes evicts BestEffort pods first, followed by Burstable and finally Guaranteed. How you wrote requests and limits sets the eviction order.

  • Set limits and requests together. With only a limit the scheduler does not know real consumption; with only a request nothing stops a runaway
  • Start from requests at normal usage and limits at peak plus headroom. Setting them equal raises the class but lowers node utilization
  • Raising a limit buys time. If it is a leak, only the interval lengthens. If you buy time, write in the ticket how long you are buying. If you do not, that limit becomes permanent
  • Without readiness the moments after a restart are dangerous. Traffic enters an instance still warming up, and that load pushes memory back up
  • An overly aggressive liveness probe mixes in deaths that are not OOM. A brief stall gets read as death and triggers a restart, and that path is SIGTERM, so the code is 143. If 137 and 143 are mixed together, you are treating two events as one
  • Exceeding the grace period turns 143 into 137. Even for the same 137, if the kernel log has no OOM record at that timestamp, this is what happened
  • Adding replicas cuts both ways. If requests spread out it helps, but if the structure gives each instance one more cache of the same size, node-wide totals go up instead
  • For multi-process containers, consider memory.oom.group. If one dies and the rest remain, the container is alive while the function is half-broken, and that state is not cleared by a restart either

The path into a restart loop usually runs like this. It dies. It restarts. During warm-up it takes the queued requests all at once. It dies again. The orchestrator widens the restart interval progressively, so the first few minutes are back-to-back deaths and after that they turn intermittent. The moment you call that later half an intermittent fault you move away from the cause. Checking whether the restart interval widens exponentially settles immediately whether it is the same event.

Risk note. Removing the memory limit altogether does not remove the problem; it promotes a cgroup OOM into a system OOM. With a limit in place the victim is confined to that container, but without one the kernel picks candidates across the whole node. What gets picked is then out of your hands, and unrelated workloads get shaken along with it.

The order of investigation

The reason for fixing an order is that each step narrows the next. Skip an earlier step and the later ones cannot be interpreted.

  1. Confirm it really died. Is the exit code 137, 143, or somewhere between 0 and 125? For a container, read the reason and code of the previous termination together. If 143 or a normal exit turns up, close the OOM investigation
  2. Confirm the kernel killed it. Is there an OOM record in the kernel log at that timestamp? If not, first check whether the ring buffer rolled, and if it did not, it was not the kernel but an orchestrator, a watchdog or a person
  3. Separate system from cgroup. Is the log prefix Out of memory or Memory cgroup out of memory? On the container side, check whether oom_kill in memory.events went up. The direction of the response splits completely here
  4. See who grew. Sort the table the kernel left behind by rss. If the process that died is not first, read the oom_score_adj column; if it is first, look at the split between rss_anon and rss_shmem
  5. See when it started growing. Secure the time series for the hours before death. Straight, stepped or sawtooth is decided here
  6. Cross-check why it grew. Overlay deployment times, configuration change history, the traffic graph and data growth on that time series. One overlap is almost the answer; none means going a layer down to cache bounds, result set size and concurrency
  7. Decide what to change. Raising the limit is the last option. Ahead of it are cache bounds, page size, worker count and connection pool. If you do raise it, write down how long it stays that way

Summary

An empty application log does not mean there is no information; it means the author of the record changed. SIGKILL cannot be caught, so the application can write nothing and the event is left on the kernel side. That is why the investigation starts by checking the exit code and moving to the kernel log rather than digging further into the application log.

After that move there is one fork. Did the node run out, or did something hit its limit? The first word of the log tells you, and the response diverges completely from there. Touching limits for a node problem or adding nodes for a limit problem both change nothing. And either way, OOM itself is not the cause. The cause is inside the slope of the hours before death, and that slope cannot be recovered once the incident is over. So what to keep is not a list of commands but an order. Did it die, did the kernel kill it, system or cgroup, who grew, since when, and why. Pass those six in order and the last question usually has only one answer left.

What I could not verify

  • The environment this article was written in is Windows 10 with Git Bash (MSYS2, GNU bash 5.2.37(1)-release), and there is no Linux kernel. No actual output from dmesg, journalctl, /proc/meminfo or /sys/fs/cgroup was reproduced and pasted in. The commands in the body were written on the basis of official documentation and kernel source
  • Exactly three things were executed and confirmed: the exit status of bash -c 'kill -9 $$' is 137, kill -15 gives 143, and the shell version is GNU bash 5.2.37(1)-release. Only those three appear in the body as real output
  • The kernel documentation on docs.kernel.org was opened directly, but the kernel source itself could not be opened because git.kernel.org returned 403. The format strings and the badness calculation were therefore confirmed on the master branch of the official mirror at raw.githubusercontent.com/torvalds/linux. It is not the code of any particular distribution kernel
  • The column layout of dump_tasks differs by kernel version. The list in the sysctl documentation and the header string in the master source already disagree. You have to check the header line of your own kernel directly
  • The function names used in the badness calculation have changed across versions. So the names were not carried over, only the composition and the way oom_score_adj is scaled. Implementation details need checking per kernel version
  • Log file paths differ by distribution and log daemon configuration. Which of /var/log/messages and /var/log/syslog is used was not verified
  • The exact rule by which a container runtime attaches exit code 137 could not be confirmed in official documentation. 128 plus the signal number is the shell's rule, confirmed here, and no documentary basis was found for runtimes following the same rule. The corresponding clause in the Bash manual could not be opened either, as gnu.org refused the request with a rate limit
  • The Kubernetes QoS documentation explains only the eviction order and says nothing about how oom_score_adj is set per class. That is why the body says no more than orchestrators sometimes set it. Userspace OOM managers such as systemd-oomd are also out of scope here
