웹 기술로 데스크톱 앱 만들기

시스템 웹뷰와 번들 런타임이 갈리는 지점, 그리고 그 선택이 청구하는 것

2026-08-16 개발/인프라

서론: 프레임워크 이름을 비교하기 시작하면 답이 안 나온다

사내 도구를 데스크톱으로 내려야 하는 상황을 가정해 보자. 웹 인력은 있고 네이티브 인력은 없다. 이때 대부분 후보 프레임워크 이름을 표에 늘어놓고 별점을 매기기 시작한다. 그 표는 끝까지 가도 결론이 나오지 않는다. 축이 잘못 잡혔기 때문이다.

웹 기술로 데스크톱 앱을 만들 때 실제로 고르는 것은 네 가지다. 렌더링 엔진을 앱과 함께 배포할 것인가, 백엔드 로직을 어떤 언어로 둘 것인가, 배포물을 어떤 형식으로 서명하고 갱신할 것인가, OS 기능과 얼마나 깊이 붙을 것인가. 이 중 나머지 셋의 난이도를 한꺼번에 정하는 것이 첫 번째다. 엔진을 실을지 말지가 정해지면 앱 용량의 자릿수가 정해지고, 렌더링 회귀를 언제 겪을지가 정해지고, 보안 패치를 누가 실어 나를지가 정해진다.

이 글은 그 첫 번째 축을 세로로 세우고 나머지를 배치한다. 2026년 8월 베타에 들어선 Wails v3을 예로 쓰지만, 특정 프레임워크를 권하는 글이 아니다. 어떤 도구를 쓰든 남는 교환 관계를 보이는 것이 목적이다.

1. 웹뷰 방식이 해결하는 것과 그대로 남기는 것

웹뷰 방식이 실제로 해결하는 문제는 인력과 자산의 문제다. 화면 코드를 세 벌 쓰지 않아도 되고, 이미 사내에 쌓인 컴포넌트와 디자인 시스템을 그대로 가져올 수 있다. 반복 주기도 짧다. 저장하면 바로 반영되는 개발 경험은 네이티브 툴킷에서 흔한 것이 아니다.

남는 것은 이쪽이다.

  • 번들 크기 — 엔진을 내장하면 앱 하나가 브라우저 한 벌을 통째로 들고 다닌다. 사내 배포에서는 초기 다운로드보다 갱신할 때마다 반복되는 전송량이 먼저 문제가 된다.
  • 메모리 — 브라우저 엔진은 다중 프로세스 구조다. 렌더러와 GPU 프로세스가 따로 뜨는 구조를 창 하나짜리 앱에 그대로 얹으면 예상보다 무겁다.
  • 시작 시간 — 엔진 초기화와 프런트엔드 자산 파싱이 순서대로 일어난다. 웹에서는 첫 렌더까지의 시간이 지표였지만, 데스크톱 앱에서는 아이콘을 눌러 창이 뜰 때까지의 체감이 곧 품질 평가가 된다.
  • 네이티브 통합 — 메뉴 막대, 트레이 아이콘, 파일 연결, 시스템 알림, 창 밖에서 끌어다 놓기, 접근성 트리는 웹 표준 밖에 있다. 프레임워크가 어디까지 감싸 주는지가 실제 차이를 만든다. 창 상태 복원과 다중 모니터 배율, 자동 시작 등록처럼 OS별 창 관리와 권한 모델에 걸린 항목도 웹뷰를 쓴다고 사라지지 않고 플랫폼별로 따로 붙는다.

이 항목들의 숫자는 앱 구성과 빌드 옵션에 따라 자릿수가 달라진다. 그래서 프레임워크별 MB와 밀리초를 하나로 말할 수 없다. 그러나 자릿수를 실제로 바꾸는 결정은 하나다.

2. 갈림길 — 런타임을 내장하는가, 시스템 것을 빌리는가

두 전략이 있다.

2.1 런타임 내장

브라우저 엔진과 런타임을 앱에 담아 배포한다. Electron 계열이 이 자리에 선다. 이득은 명확하다. 개발자가 시험한 엔진 버전이 사용자 기기에서 그대로 돈다. CSS 한 줄이 어느 기기에서만 다르게 그려지는 상황이 구조적으로 생기지 않는다. 브라우저 지원 표를 볼 일도 없다.

대가도 명확하다. 앱마다 엔진 한 벌이 붙는다. 그리고 엔진의 보안 패치를 앱 릴리스로 실어 나를 책임이 개발 팀에 남는다. 크로미움에 취약점이 공개되면 그 수정본을 담은 앱 버전을 내고 사용자에게 갱신시켜야 한다. 이 책임은 프레임워크가 대신 져 주지 않는다.

2.2 시스템 웹뷰 사용

OS가 이미 제공하는 엔진을 호출한다. Wails와 Tauri 계열이 이쪽이다. Wails 저장소 안내문은 이 입장을 네이티브 렌더링 엔진을 쓰며 내장 브라우저가 없다는 한 줄로 못 박는다. 배포물에서 엔진이 빠지고, 엔진 패치는 OS나 런타임 갱신 경로가 담당한다.

대가는 다양성이다. 사용자 기기마다 엔진 버전이 다르고, 지원되는 웹 기능도 다르다. 최신 CSS 문법 하나를 쓰기 전에 지원 하한을 정해야 한다는 뜻이다.

2.3 중간 지대가 있다

이 교환이 프레임워크 사이에만 있는 것이 아니라는 점이 중요하다. 같은 플랫폼 안에도 있다. 윈도우의 WebView2는 두 가지 배포 모드를 제공하는데, 자동 갱신되는 상시 최신 모드와 특정 버전 바이너리를 앱과 함께 싣는 고정 버전 모드다. 마이크로소프트 배포 문서는 고정 버전 바이너리가 250MB를 넘으며 앱 패키지가 그만큼 커진다고 적는다. 반대로 상시 최신 모드에서는 필요할 때 내려받는 부트스트래퍼가 약 2MB다.

정리하면 이렇다. 렌더링 일관성과 배포 용량은 같은 다이얼의 양 끝이다. 어느 프레임워크를 고르든 이 다이얼은 남고, 어느 위치에 놓을지는 제품이 정해야 한다.

4. 윈도우 — WebView2와 두 가지 배포 모드

윈도우의 시스템 웹뷰는 엣지와 같은 크로미움 계열 엔진을 쓰는 WebView2다. 실무에서 알아야 할 것은 다음과 같다.

  • 상시 최신 런타임은 윈도우 11 운영체제에 포함된다. 윈도우 10은 대다수 기기에 이미 설치돼 있지만 전부는 아니다. 그래서 앱 설치나 기동 시점에 존재를 확인하는 절차가 권고되는데, 방법은 레지스트리에서 런타임 항목의 버전 값을 읽거나 사용 가능한 브라우저 버전 문자열을 반환하는 API 결과가 비어 있는지 보는 두 가지다.
  • 없을 때는 약 2MB짜리 부트스트래퍼를 내려받아 설치하거나, 오프라인 환경이면 전체 설치본을 배포물에 동봉한다.
  • 모든 상시 최신 앱이 기기에 설치된 한 벌을 공유한다. 조건이 맞으면 엣지 바이너리와 하드링크로 묶여 디스크와 메모리를 아낀다는 설명도 문서에 있다.
  • 운영상 함정이 하나 있다. 런타임이 갱신돼도 실행 중인 앱은 이전 버전을 계속 쓴다. 새 버전으로 넘어가려면 앱을 재시작하거나 기존 환경 객체 참조를 놓아야 한다. 오래 켜 두는 앱이 외부 콘텐츠를 렌더한다면 이건 보안 사안이 된다. 새 브라우저 버전 알림 이벤트를 받아 재시작을 유도하는 처리가 이래서 필요하다.
  • 고정 버전 모드에는 별도 제약이 붙는다. 문서상 알려진 문제로 네트워크 경로에서 실행할 수 없고, 윈도우 10에서 특정 버전 이후로는 패키지되지 않은 데스크톱 앱이 권한 부여 명령을 추가로 실행해야 한다.
  • 프로덕션 앱은 엣지 브라우저의 안정 채널을 백엔드 플랫폼으로 쓸 수 없다. 앱이 브라우저 설치 여부에 의존하지 않게 하려는 설계다.

판단 기준은 이렇게 잡는다. 사내 전 PC에 배포하고 렌더링 회귀를 절대 받을 수 없는 조직, 특히 인터넷이 막힌 망에 배포하는 경우라면 고정 버전 모드가 검토 대상이다. 그 외에는 상시 최신 모드에 설치 시점 확인 절차를 붙이는 쪽이 용량과 패치 부담 모두에서 낫다.

5. macOS와 리눅스 — 같은 시스템 웹뷰인데 성질이 다르다

macOS는 단순한 편이다. 시스템 웹뷰가 WKWebView 하나이고 OS 업데이트와 함께 움직인다. 배포 대상 OS 하한이 곧 엔진 하한이 되므로, 지원 범위를 정하는 일이 곧 웹 기능 지원 범위를 정하는 일이다. 빌드에는 Xcode 명령줄 도구가 필요하다.

리눅스가 진짜 변수다. 배포판마다 GTK 세대와 WebKitGTK 버전이 다르고, 같은 배포판이라도 릴리스에 따라 개발 패키지 이름이 바뀐다. Wails v2 설치 문서는 GTK3와 WebKit2GTK를 요구하면서, 최신 우분투처럼 4.0 개발 패키지가 없는 환경에서는 4.1을 설치하고 빌드 태그를 붙이라고 안내한다. 이 안내가 문서에 명시적으로 들어가 있다는 사실 자체가 상황을 말해 준다.

v3이 리눅스 스택을 GTK4와 WebKitGTK 6.0으로 올린 것은 방향을 보여 준다. 예전 GTK3 계열은 별도 빌드 태그로 남되 v3.1까지라고 못 박혀 있다. 그리고 v3 지원 플랫폼 표기가 우분투 24.04를 명시하고 다른 리눅스는 될 수도 있다고 적는 방식이 현실을 그대로 반영한다.

그래서 리눅스를 1급 타깃으로 삼는다면 순서를 이렇게 잡는다. 어느 배포판 어느 버전까지 책임질지 먼저 못 박는다. 그 결정이 GTK 세대와 빌드 태그를 정하고, 그게 다시 CI 이미지와 패키지 형식을 정한다. 이 순서를 뒤집으면 배포 직전에 스택 전체를 다시 고르게 된다.

6. Wails가 취한 입장, 그리고 v3에서 달라진 것

Wails의 입장은 두 문장으로 요약된다. 백엔드는 Go로 두고, 화면은 OS의 네이티브 렌더링 엔진에 그린다. 서버를 띄우고 브라우저를 여는 방식을 피하면서 Go 프로그램에 웹 프런트엔드를 붙이려는 사람이 대상이다. 앞 절의 분류로는 시스템 웹뷰 쪽에 선다.

6.1 버전 상태 — 2026년 8월 16일 확인 기준

  • 저장소 안내는 두 갈래를 명시한다. v2는 Stable, v3은 Beta다. 설치 명령도 각각 wails와 wails3로 따로 있다.
  • 릴리스 목록에서 v2.14.0이 2026년 8월 10일 정식 릴리스로 올라 있다.
  • v3 계열 최신은 v3.0.0-beta.8로 2026년 8월 12일 프리릴리스다. 첫 베타 태그인 v3.0.0-beta.0이 8월 2일이고 그 직전까지는 알파 계열이었다. 열흘 사이에 베타 태그가 아홉 번 나간 셈이다. 수정이 빠르다는 뜻이면서, 버전을 고정하지 않으면 빌드가 흔들린다는 뜻이기도 하다.
  • 베타는 베타다. 프로덕션 기준 안정 채널은 여전히 v2다.

6.2 v3에서 달라진 것

발표된 변경과 저장소에서 확인되는 흔적을 함께 놓으면 다음과 같다.

  • 명시적 객체 수명주기 — 암묵적인 컨텍스트 중심 구성에서 Application·Window·Service라는 명시적 객체 구성으로 바뀌었다.
  • 다중 창 기본 지원 — 편집기나 검사 도구처럼 창을 여러 개 띄우는 앱에서 우회 구현이 필요 없어졌다.
  • Go 서비스 패턴 — 기존 바인딩 자리를 서비스가 대체하면서 백엔드 기능과 프런트엔드 API 사이 경계가 명시된다.
  • 정적 분석 기반 타입 정의 생성 — 매개변수 이름과 주석을 보존한 형태로 프런트엔드용 타입 정의가 나온다.
  • 빌드 과정 공개 — 프레임워크 내부에 숨기지 않고 Taskfile 형식으로 드러낸다. 저장소에 해당 파일이 있고, 설치 문서도 패키지 관리자를 바꾸려면 프로젝트 Taskfile을 고치라고 안내한다.
  • 서버 빌드 옵션 — 데스크톱 UI와 백엔드 로직을 분리해 돌릴 수 있는 형태가 가이드로 들어와 있다.
  • 실험적 모바일 — 저장소 v3 디렉터리에 iOS·안드로이드 문서 파일이 있다. 실험 단계로 표기된다.
  • 툴체인 요구 상승과 설정 마법사 — Go 1.24 이상을 요구한다. v2가 1.21 이상이었던 것과 대비된다. npm은 v3에서 선택으로 내려갔지만 기본 템플릿 대부분이 필요로 한다. wails3 setup이 플랫폼 의존성 점검과 프로젝트 기본값, 서명 설정을 한 번에 다루는데, 문서에 새 기능이며 주로 리눅스에서 시험됐다는 주의가 붙어 있다.

마이그레이션 관점에서 중요한 것은 이 목록의 첫 세 항목이다. API 이름이 바뀐 수준이 아니라 앱을 구성하는 모델 자체가 달라졌다. 진행 중인 제품이 있다면 정식 배포 전까지는 새 프로젝트에서 시험하는 편이 되돌리기 쉽다.

7. 경계를 코드로 보면 — 개념 예시

아래는 구조를 보이기 위한 축약 예시이며 실행해 확인하지 않았다. 실제 API 시그니처와 등록 방식은 사용하는 버전의 문서를 따라야 한다.

웹뷰 방식에서 백엔드와 프런트엔드의 경계는 함수 시그니처 몇 개로 좁혀진다. Go 쪽에 이런 타입이 있다고 하자.

// 개념 예시 — 동작 미확인
type Vault struct {
    root string
}

// 프런트엔드에 노출되는 것은 이 메서드 하나다.
func (v *Vault) List(prefix string) ([]string, error) {
    // 파일 시스템 접근은 Go 쪽에만 존재한다.
    // prefix 를 그대로 경로에 붙이지 않고 정규화·검증을 거친다.
    if strings.ContainsAny(prefix, "/\\.") {
        return nil, errors.New("invalid prefix")
    }
    return filepath.Glob(filepath.Join(v.root, prefix+"*"))
}

프런트엔드는 생성된 타입 정의를 통해 이 메서드만 본다.

// 개념 예시 — 동작 미확인
const files = await Vault.List('report-');
render(files);

이 그림이 왜 중요한지는 두 가지다.

  • 웹뷰 안에서 도는 코드는 신뢰 경계 바깥이다. 렌더러에 로드된 스크립트가 무엇이든 호출할 수 있는 것은 노출된 메서드뿐이고, 그 목록이 곧 공격면이다. 편의를 위해 파일 경로를 그대로 받는 범용 메서드를 열어 두면 그 순간 임의 경로 접근이 가능해진다. 검증은 반드시 Go 쪽에서 한다.
  • 경계를 좁히면 문서가 따라온다. 정적 분석으로 타입 정의를 생성하면 프런트엔드 쪽 코드에서 함수 이름과 매개변수 이름, 주석까지 보인다. 손으로 유지하던 인터페이스 문서가 사라진다는 뜻이다.

이 구조가 강제하는 규율도 있다. 상태 변화는 이벤트로 흘리고 명령은 메서드로 보내는 형태가 결국 표준이 된다.

8. 배포·서명·자동 업데이트 — 데스크톱에서 시간을 먹는 구간

화면을 만드는 일이 끝나면 진짜 일정이 시작된다. 이 구간을 얕게 잡으면 출시가 밀린다.

8.1 서명과 공증

Wails v3의 서명 가이드가 정리한 교차 서명 관계는 실무 판단에 그대로 쓸 수 있다.

  • 윈도우 실행 파일과 설치 패키지는 윈도우·macOS·리눅스 어느 호스트에서든 서명할 수 있다.
  • 리눅스 DEB·RPM 패키지도 PGP 키로 어느 호스트에서든 서명할 수 있다.
  • macOS 앱 번들 서명과 공증만 macOS에서만 가능하다. 애플 도구 체계 때문이다.
  • 서명 백엔드는 네이티브 플랫폼에서 각 OS 표준 도구를 쓰고 교차 컴파일 시에는 내장 구현을 쓴다. v3의 설정 마법사는 서명 설정을 사용자 설정 파일에 쓰고 비밀번호는 OS 자격 증명 저장소에 넣는다. 빌드 스크립트에 평문으로 남기지 않는다는 뜻이다.

세 번째 항목이 예산에 바로 반영된다. 맥을 배포 대상에 넣는 순간 CI에 맥 러너가 필요하다. 그리고 인증서 발급과 갱신, 공증 대기, 서명 키를 CI에 안전하게 주입하는 일은 코드가 아니라 절차이고, 절차는 일정에서 압축되지 않는다.

8.2 자동 업데이트

웹은 새로고침이 배포다. 데스크톱은 아니다. 내려받고, 검증하고, 실행 중인 바이너리를 바꾸고, 재시작을 유도해야 한다. 직접 만들 때 빠지면 안 되는 것은 네 가지다.

  • 서명 검증 — 내려받은 것이 우리가 낸 것인지 공개키로 확인한다. 전송 구간 암호화만으로는 부족하다.
  • 원자적 교체 — 부분 다운로드나 중단이 실행 파일을 깨뜨리지 않아야 한다. 임시 위치에 받아 검증 후 교체하는 순서가 기본이다.
  • 롤백 경로 — 새 버전이 기동에 실패했을 때 이전 버전으로 돌아갈 방법이 없으면 원격 지원이 전화 안내가 된다.
  • 강제 업데이트 정책 — 보안 수정에는 건너뛰기를 허용하지 않는 등급이 필요하다.

Wails v3은 이 부분을 프레임워크 기능으로 올렸다. 업데이터가 애플리케이션 객체에 붙고, 배포처 제공자를 꽂아 쓰는 구조다. 가이드에는 깃허브 릴리스, 상용 배포 서비스, Sparkle 계열 매니페스트, 자체 매니페스트 규약, 직접 구현이 열거된다. 내려받은 파일은 설정한 공개키로 검증하고, 바이너리를 안전하게 교체하며, 상태 전이는 프레임워크 이벤트 버스로 흐른다. 상태는 미설정·대기·확인 중·최신·업데이트 있음 같은 값으로 정의돼 있고 기본 업데이트 창 UI도 제공되며 교체할 수 있다.

여기서 4절의 함정을 다시 겹쳐 봐야 한다. 시스템 웹뷰를 쓰면 엔진 패치는 앱 업데이트와 별개 경로로 온다. 그건 이득이다. 하지만 앱을 며칠씩 켜 두는 사용 패턴이라면 그 앱은 옛 엔진을 계속 쓴다. 앱 자동 업데이트와 별개로, 재시작을 유도하는 장치가 있어야 실제로 패치가 적용된다.

9. 선택 판정표 — 요구사항별로 무엇을 먼저 보나

표를 쓰는 법은 위에서 아래로 읽는 것이 아니다. 우리 제품에서 양보 불가능한 항목 하나를 찾아 그 행부터 고정하고, 나머지 행의 대가를 감수 가능한 범위로 맞춘다. 양보 불가능한 항목이 두 개 이상이면 대개 그중 하나는 진짜 요구사항이 아니다.

10. 확인하지 못한 것

  • v3 발표 원문 페이지 — 공식 사이트의 베타 발표 글은 접근이 403으로 막혀 열리지 않았다. 6절의 변경 목록은 저장소의 문서 원본과 파일 구성, 그리고 그 발표를 요약한 국내 기술 토픽에 근거한다.
  • 프레임워크별 번들 크기·메모리·시작 시간 — 동일 조건에서 측정한 공개 수치를 확인하지 못했다. 이 글에 프레임워크별 MB와 밀리초가 없는 이유다. 사용한 유일한 수치인 고정 버전 250MB 이상과 부트스트래퍼 약 2MB는 마이크로소프트 배포 문서의 값이다.
  • v3.0 정식 배포 시점 — 공개된 일정을 확인하지 못했다.
  • v3 모바일 지원 범위 — 저장소에 iOS·안드로이드 문서 파일이 있으나 실험 단계이며 어디까지 동작하는지는 확인하지 못했다.
  • Electron·Tauri의 최신 릴리스별 세부 동작 — 이 글의 비교는 엔진을 내장하는가라는 구조 차이까지다. 각 프레임워크의 최신 기능은 해당 공식 문서를 봐야 한다.
  • 7절 코드 — 개념을 보이기 위한 축약이며 실행해 확인하지 않았다. 실제 시그니처와 등록 방식은 사용하는 버전의 문서를 따라야 한다.

결론: 착수 전에 정할 세 가지

프레임워크 비교표를 만들기 전에 답해야 할 질문은 셋이다.

  1. 렌더링 일관성을 얼마나 살 것인가. 값은 배포 용량과 엔진 패치 책임으로 치른다. 이 값이 정해지면 후보는 절반으로 준다.
  2. 지원 하한을 어디에 그을 것인가. 윈도우 10을 어디까지, macOS를 몇 버전까지, 리눅스를 어느 배포판까지. 리눅스 답이 가장 비싸다.
  3. 서명과 업데이트 파이프라인을 누가 언제 만드는가. 맥이 대상이면 맥 러너가 필요하고, 자동 업데이트에는 공개키 검증·원자적 교체·롤백·강제 정책이 최소로 들어간다.

Wails는 이 구도에서 시스템 웹뷰 쪽에 서고 백엔드를 Go로 두는 선택지다. v3은 앱 구성 모델을 다시 짠 큰 변경이고, 2026년 8월 16일 확인 기준으로 베타다. 안정 채널은 v2다. 시험은 새 프로젝트에서 하고, 납품은 안정 채널로 하는 편이 지금 시점의 안전한 배치다.

마지막으로 하나. 웹뷰 방식이 만드는 착시가 있다. 화면이 웹으로 빨리 나오니 앱이 거의 다 된 것처럼 보인다. 실제로 남은 일은 설치기, 서명, 공증, 업데이트, 크래시 수집, 자동 시작, 다중 모니터다. 이 목록을 일정에 먼저 넣고 시작하면 나중에 밀리지 않는다.
