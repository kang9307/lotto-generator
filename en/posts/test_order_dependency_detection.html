What Shuffling Test Order Reveals - Finding the Hidden Dependency

Passing did not mean correct. It meant correct in this order.

2026-07-31 Dev & Infra

The symptom: red in CI, green on my machine

Monday morning, CI is red. You open the log and one test that was fine on Friday has failed. You copy its name and run it locally. It passes. You run it again. It passes again. You read the code and nothing is wrong with it. So you hit the retry button, green comes back, and you move on.

Most teams file this under «flaky test» and walk away. But that label explains nothing about the cause. This article covers exactly one of those causes: execution order.

Order dependency behaves differently from the other sources of instability. Something that wobbles because of timing or concurrency can produce different results under identical conditions, while order dependency is completely deterministic. Run the same order and you get the same result every time. Nobody was watching when the order changed, that is all.

So the thesis here is not «isolate your tests». That is a conclusion, not a diagnosis. The claim is this.

When state survives between tests, order is an input. A green run then means not «this is correct» but «this is correct in this order». And that input has never been validated by anyone.

Seen that way, shuffling the order stops being fastidiousness or personal taste. It is widening the range of inputs you test. Running a single order is like feeding a function one value and declaring the function correct.

Environment. Every output below was actually executed on Windows 10 Pro (10.0.19045). The tools are the standard library unittest on Python 3.13.3 (win32, MSC v.1943 64bit) and node:test on Node.js v22.16.0 (win32 x64), with GNU bash 5.2.37 (MSYS2) as the shell.

What I could not run. This environment has no pytest installed (No module named pytest). Python 3.11 gave the same answer, and nose2 was absent too. So ordering behaviour in the pytest family, and its plugins, was not measured directly. Wherever this article mentions pytest, the statement rests on documentation and is flagged as not measured.

Every script was saved to a file and executed. All examples and paths below are fictional code rewritten onto placeholders such as /tmp/order-demo.

1. The four tests under study

Start with the subject. It is an extremely ordinary shape: one module holds a global dictionary and the tests share it.

# /tmp/order-demo/store.py
CONNECTIONS = {}          # module-level global, imported once per process

# /tmp/order-demo/tests_shared.py
import unittest
import store

class SessionTests(unittest.TestCase):
    # deliberately defined in the order d, b, a, c
    def test_d_close_all(self):
        store.CONNECTIONS.clear()
        self.assertEqual(store.CONNECTIONS, {})

    def test_b_query_uses_connection(self):
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_a_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"
        self.assertEqual(len(store.CONNECTIONS), 1)

    def test_c_registry_has_one_entry(self):
        self.assertEqual(len(store.CONNECTIONS), 1)

All four read naturally on their own. Open a connection, query it, count the entries, close it. Nowhere does it say «an earlier test will have opened the connection». But that is exactly what has been arranged.

2.1 If order is an input, how large is the input space?

Two data points could be dismissed as bad luck. So I ran all 24 permutations, each in a fresh process.

    d a b c

RED   (20):
    a b d c   a c d b   a d b c   a d c b   b a c d   b a d c
    b c a d   b c d a   b d a c   b d c a   c a b d   c a d b

A 17 percent pass rate. And there is a second, decisive fact. This tool's default order, a b c d, is the first of the four green ones. The developer was seeing green every day, and could have lived for months one small reshuffle away from red.

  • The four green permutations share a shape: a comes before b and c, and d comes after b and c
  • That constraint is written down nowhere in the code. The alphabetical order of the names happened to satisfy it
  • The moment someone renames test_a_open_connection to test_setup_connection, it turns red. The refactor did not break the test; it revealed a dependency that was already there
  • Adding one test is enough to shift positions. The new test is blameless and a different test goes red

3. The default order differs by tool

Here is the most common misconception to clear up: «tests run top to bottom». That is true in some tools and false in others. So do not generalise it, measure it in the tool you use. Below are the values measured in this environment.

Name order, not definition order. True for methods and for classes alike. The documentation states it too: the order is determined by sorting the test method names with respect to the built-in ordering for strings.

Measuring is easy: write a few tests whose definition order deliberately disagrees with their name order, then watch which way they actually run.

4. The five places state survives

For order to become an input, something has to survive between tests. I split those places into five and ran each one. Every run starts in a fresh process; fwd is name order and rev is its reverse.

4.1 Module-level global

case 1  module-level global       order=fwd
  run : a_open_connection -> b_query_uses_connection -> c_close_all
  ==> ALL PASS   (3/3 passed)

case 1  module-level global       order=rev
  run : c_close_all -> b_query_uses_connection -> a_open_connection
  ==> 1 FAILED   (2/3 passed)
      red: b_query_uses_connection
      KeyError: 'main'

The most common place by far. A module is imported once per process, so the variables inside it stay alive for the whole test session. Splitting files does not help. The moment two files import the same module, they share the same object.

4.2 Class attribute

class FeatureFlags:
    enabled = set()          # class attribute: every instance shares this one set

    def on(self, name):
        self.enabled.add(name)     # mutates the class-level set, not the instance

case 2  class attribute           order=fwd
  run : a_enable_beta -> b_fresh_object_has_no_flags
  ==> 1 FAILED   (1/2 passed)
      red: b_fresh_object_has_no_flags
      AssertionError: Items in the first set but not the second: 'beta'

case 2  class attribute           order=rev
  run : b_fresh_object_has_no_flags -> a_enable_beta
  ==> ALL PASS   (2/2 passed)

The direction flips here. It fails in the default order and passes reversed. self.enabled.add(...) looks like it creates an instance attribute, but it actually walks up to the set on the class and adds there. So an object freshly built with FeatureFlags() already carries the earlier value.

4.3 Cache and memoization

USERS = {}

@functools.lru_cache(maxsize=None)
def find_user(uid):
    return USERS.get(uid)

case 3  cache / memoization       order=fwd
  run : a_created_user_is_found -> b_lookup_again -> c_unknown_user_is_none
  ==> ALL PASS   (3/3 passed)

case 3  cache / memoization       order=rev
  run : c_unknown_user_is_none -> b_lookup_again -> a_created_user_is_found
  ==> 2 FAILED   (1/3 passed)
      red: b_lookup_again              AssertionError: None != 'kim'
      red: a_created_user_is_found     AssertionError: None != 'kim'

This is the nastiest of the five. Look again at the body of test_a_created_user_is_found.

def test_a_created_user_is_found(self):
    USERS[7] = "kim"                          # inserts the data correctly
    self.assertEqual(find_user(7), "kim")     # looks it up correctly  -> and still fails

There is nothing wrong with this test. Yet reversed, it goes red. The earlier test_b_lookup_again called find_user(7) while the data was still absent, and the resulting None was baked into the cache. A cache remembers the answer «not found» just as faithfully as any other.

  • A function with a cache attached is effectively a global variable, just one that sits out of sight
  • Restoring a config value in a fixture is not enough: if you do not clear the cache, the old answer comes right back
  • Caching negative results (not found, not permitted, empty) is especially dangerous. The test that later sets things up correctly is the one that breaks
  • It is not only your own caches. Caches inside imported libraries, compiled regex caches and connection pools all occupy the same place

4.4 Temp files and directories

case 4  temp file / directory residue  order=fwd
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty
      AssertionError: Lists differ: ['report.csv'] != []

case 4  temp file / directory residue  order=rev
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> ALL PASS   (2/2 passed)

So far this matches the earlier cases. But this place has a property the other four lack. Drop the cleanup and run twice in a row to see it.

$ python -c "remove the residue"
residue cleared

--- run 1: cleanup omitted, fwd order ---
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

--- run 2: brand new process, rev order (ALL PASS a moment ago) ---
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

The reversed order that was ALL PASS a moment ago is now red, in a brand new process. State left on the file system crosses the process boundary. In other words, the role of «the earlier test» is now played by the entire previous run.

  • So this type shows up as «it works on a fresh clone but not in my working copy»
  • If CI uses a clean container each time, you get the mirror image: green in CI and red locally
  • The moment you use a fixed path, parallel runs trample each other too
  • Databases, cache servers and message queues share this property. Restarting the process does not clear them

4.5 Unrestored monkeypatch

def test_a_invoice_with_frozen_clock(self):
    clock.now = lambda: 1700000000.0      # swapped in and never put back
    ...

case 5  monkeypatch that is never undone  order=fwd
  run : a_invoice_with_frozen_clock -> b_invoice_uses_real_clock
  ==> 1 FAILED   (1/2 passed)
      red: b_invoice_uses_real_clock
      AssertionError: 85445231.48900342 not less than 5.0 : clock is off by 85445231 seconds

case 5  monkeypatch that is never undone  order=rev
  run : b_invoice_uses_real_clock -> a_invoice_with_frozen_clock
  ==> ALL PASS   (2/2 passed)

The drift is 85.4 million seconds, about two years and eight months. Freezing the clock is a perfectly legitimate technique; the problem is not putting it back. Random seeds, environment variables, stubbed network calls and logging configuration all live in this same place.

5. Telling the cause types apart

Here are those five arranged for practical use. If you take one thing from this article, take this table.

TypeWhere it survivesTypical symptomHow to confirmHow to undo
Module-level globalThe imported module objectA later test reads what an earlier one filled inPrint the module variable before and after each testReset in setUp plus a registered cleanup
Class attributeThe class object itselfA fresh instance already carries old valuesCheck whether it is per-instance or per-classMove the mutable default into the constructor
Cache and memoizationThe cache attached to the functionWhoever runs first defines the answer, the rest disagreePrint cache hit statisticsClear the cache in setUp
Temp files and directoriesThe file systemReproduces in a brand new processDiff the directory listing before and afterA fresh temp directory per test, auto-removed
Unrestored monkeypatchThe patched module attributeClock, randomness or network returns nonsenseCompare the current attribute against the originalRegister the restore before patching

A sense of direction helps when using the table. Globals, caches and monkeypatches generally have the earlier test polluting the later one; class attributes accumulate, so they often fail early in the default order; and temp files have the previous run polluting this one.

6. Who polluted, and who broke

The most frequent diagnostic mistake is treating the red test as the culprit. To see it plainly, I printed the shared state before and after every test.

order=fwd
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  b_query_uses_connection    state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  c_registry_has_one_entry   state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  d_close_all                state {'main': 'pg://demo'}  -> {}                     CHANGED
  red tests : (none)

order=rev
  d_close_all                state {}                     -> {}                       --
  c_registry_has_one_entry   state {}                     -> {}                       --
  b_query_uses_connection    state {}                     -> {}                       --
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  red tests : b_query_uses_connection, c_registry_has_one_entry
  who mutated shared state : a_open_connection, d_close_all

Read the last two lines together. The red tests, b and c, did not change a single character of the shared state (the -- marker). The two that did change it, a and d, are both green.

  • The point of failure and the point of cause are completely separate. That is why the stack trace in the failure log does not point at the culprit
  • In the reversed run the real cause is d_close_all emptying the dictionary at the front. And because d passed its own assertion, it emitted no signal at all
  • This structure is what produces defensive patches on the victim. The red goes away and the source of pollution stays
  • The place to fix is whichever test changed state and did not put it back

7. Bisecting down to the culprit

With four tests you can eyeball it. With several hundred you cannot, so you need a procedure: halve the set of tests placed before the victim.

I built a 17-test example. Most are ordinary arithmetic checks and one of them quietly changes shared config. The last test checks a total including tax.

CONFIG = {"tax_rate": 0.10, "currency": "KRW"}

    def test_09_tax_exempt_customer(self):
        # the culprit: sets the rate for an exemption check and never puts it back
        CONFIG["tax_rate"] = 0.0
        self.assertEqual(CONFIG["tax_rate"], 0.0)

    def test_zz_total_includes_tax(self):
        # the victim: perfectly correct on its own
        self.assertAlmostEqual(10000 * (1 + CONFIG["tax_rate"]), 11000.0)

Now pretend the culprit is unknown and follow the procedure. Every trial is a fresh process.

suite size      : 17 tests (16 candidates + 1 victim)
victim          : zz_total_includes_tax

step 0 -- pin both endpoints first
  trial 1   before=16 [01_amount_is_positive..16_due_date_offset]        -> RED
  trial 2   before=0  [nothing]                                          -> GREEN

step 1 -- halve toward whichever side stays RED
  trial 3   before=8  [01_amount_is_positive..08_empty_cart_total]       -> GREEN
  trial 4   before=8  [09_tax_exempt_customer..16_due_date_offset]       -> RED
  trial 5   before=4  [09_tax_exempt_customer..12_zero_quantity_skipped] -> RED
  trial 6   before=2  [09_tax_exempt_customer..10_max_line_items]        -> RED
  trial 7   before=1  [09_tax_exempt_customer..09_tax_exempt_customer]   -> RED

minimal reproducing pair : 09_tax_exempt_customer  then  zz_total_includes_tax
subprocess runs used     : 7
brute force would need   : 16 (one run per candidate)

Seven runs. Trying candidates one at a time would take sixteen, and the gap widens as the suite grows. With 1,000 candidates brute force needs 1,000 runs while this procedure needs about twenty.

  • Do not skip step 0. «Whole prefix plus victim is red» and «victim alone is green» must both hold for this to be order dependency. If the victim is red on its own, it is simply a broken test
  • Every trial in a fresh process. Chaining trials inside one process lets them pollute each other and flips the verdicts
  • If neither half is red, more than one culprit is involved, meaning two tests together create the condition. In that case narrow by removing halves instead
  • Keep the minimal pair you found as a regression test. A dedicated test that runs those two in that order stops the same incident from returning
  • Fix the culprit side. Defensive code on the victim is first aid

8. The illusion that isolation creates

Let us reproduce «it works on my machine» exactly. Take that same 17-test example and run only the victim.

zz_total_includes_tax  run alone            GREEN
all 17 tests (name order)                  RED

That is all it takes. A developer who reads the failure log, copies the test name and runs it locally will always see green. So the conclusion drifts to «environment problem» and the retry button takes it from there.

But doing the same thing with the earlier four-test example gives a different answer.

a_open_connection                PASS
b_query_uses_connection          FAIL
c_registry_has_one_entry         FAIL
d_close_all                      PASS

Here b and c fail even on their own. That difference matters enormously for diagnosis. Order dependency comes in two kinds.

KindAloneIn the suiteCharacterHow hard to find
Needs a predecessorFailsPasses in some ordersNever a self-contained test. It uses an earlier test as its setup stepLow. Running it alone exposes it immediately
Victim of pollutionPassesFails in some ordersThe test itself is correct. It merely stepped on state an earlier test leftHigh. This is where «works on my machine» comes from

The second row is what eats your week. Passing in isolation is not evidence that the test is fine; it is a symptom that you are looking at the second kind. Isolation is where diagnosis starts, never where it concludes.

9. Random order and a fixed seed

If order is an input, the answer is obvious: feed it more than one value. But do not just switch randomness on, because a red build you cannot reproduce cannot be diagnosed. Fixing the seed buys you randomness and reproducibility at once.

seeds tried : 1..40   (order = random.Random(seed).shuffle)
green seeds : 10  -> [1, 3, 9, 11, 12, 13, 17, 26, 27, 33]
red   seeds : 30  -> [2, 4, 5, 6, 7, 8, 10, 14, 15, 16, 18, 19] ...

Thirty of forty seeds were red. Now pick one and pin it. The fixed seed used throughout this article is 20260731. Anyone who supplies that seed gets the same order.

$ python ci_shuffle.py 20260731
==============================================================
TEST ORDER SEED : 20260731      replay with: ci_shuffle.py 20260731
==============================================================
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

$ python ci_shuffle.py 20260731          # same seed again
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

The two runs are identical in order and in outcome. That is the one condition that makes random ordering usable in practice.

  • Print the seed and the replay command at the very top of the failure log. Whoever receives the log should be able to copy that one line and reproduce it
  • Draw the seed from randomness, not from the clock. Clock-based seeds make two runs in the same minute take the same order, narrowing your search
  • The Python standard library is enough. Take the list of names, shuffle it with a fixed seed and assemble the suite in that order
  • The pytest ecosystem has plugins that shuffle order, along with options to disable their registration. However pytest is absent here, so I could not verify that directly

10. Rules for putting state back

Now the fix. I changed only the fixtures of the four-test suite, leaving every assertion alone.

class SessionTestsFixed(unittest.TestCase):
    def setUp(self):
        # 1. arrive at a known state instead of inheriting one
        store.CONNECTIONS.clear()
        # 2. register the undo up front, so it runs even if the test raises
        self.addCleanup(store.CONNECTIONS.clear)

    def given_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"      # build your own precondition

    def test_b_query_uses_connection(self):
        self.given_open_connection()
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_c_registry_has_one_entry(self):
        self.given_open_connection()
        self.assertEqual(len(store.CONNECTIONS), 1)

Only two things changed: reset the state on arrival, and build your own preconditions. Here is the result.

  red   : 0  []
  pass rate : 24/24 = 100%

  b                          PASS
  c                          PASS
  d                          PASS

case 5 fixed  monkeypatch: register the restore before you patch    order=rev  ==> ALL PASS

10.1 Eight rules

  • Never outsource your arrange step. A test builds the preconditions it needs. This one rule removes most order dependency
  • setUp means arriving at a known state, not a place to inspect whatever you inherited
  • Register the undo before you patch. Restoration must still run when the test body is cut short by an exception
  • Cleanup functions run in reverse order of registration. Resources are released opposite to how they were acquired, so dependencies hold naturally
  • Do not put cleanup at the end of the test body. A failed assertion never reaches that line. This is what «one broke and ten broke after it» really is
  • A cache is a global. If you restored the setting, clear the cache too
  • Create temp files fresh per test and let them remove themselves. Never share a hardcoded path
  • Class-scoped fixtures are not the default. Use them only when speed forces it, and keep them read-only

10.2 Safe to share and never to share

Safe to shareNever share
Immutable constants, frozen config valuesMutable containers: dicts, lists, sets
Pure functionsFunctions with a cache attached
Read-only fixture dataDatabases and files that get written to
A temp directory created per testA working directory at a fixed path
Helper methods on the test classMutable defaults held as class attributes
A copy of a precomputed valueA reference to the value itself

The criterion reduces to one question. Does the test write to it? If yes, do not share it. If it only reads, sharing is fine, but verify that «only reads» really means only reads. Sorting a list is a write. So is a dictionary lookup that fills in a default.

11. What to wire into CI

Translating all of the above into a pipeline gives this.

  • Keep the main job on a fixed order. If the order wobbles on every commit you cannot tell whether a red build came from the code or the order
  • Split random ordering into a separate job and print the seed. That job going red means «there is order dependency»; the main job going red means «the code is wrong». The signals never mix
  • Add one reverse-order run to the nightly job. It is cheaper than randomisation and, as this article shows, detects a great deal. Being deterministic, it reproduces automatically
  • Pin every newly found minimal pair as its own test. Leaving a test that runs those two in that order keeps the same incident from coming back
  • Add a step that checks for leftover files in the temp directory after a run. That alone catches most of the type in section 4.4
  • Remove order dependency before enabling parallel execution. Parallelism not only shakes the order harder, it adds concurrent access on top. Going parallel with an order problem gives you two layers of cause

A suggested rollout. Switching on order randomisation all at once typically buries the team in red and ends with the job being disabled. Start with a single reverse-order run instead. It is deterministic and therefore easy to reproduce, and you can narrow each red down to a minimal pair and fix it one at a time. Turn on randomisation once that backlog is clear.

12. Checklist

  • I ran the newly added test on its own
  • I ran the suite in reverse once
  • I ran a random order at least once with a pinned seed
  • No leftover files remain in the temp directory after a run
  • Every monkeypatch has a registered restore
  • Fixtures for code that uses a cache include cache clearing
  • No mutable defaults sit on class attributes
  • No test assumes another test's name or position
  • Cleanup lives in the fixture, not at the end of the body
  • The CI log prints the order seed

12.1 What not to do

  • Adding defensive code to the failing test first - you fix the victim and lose the culprit
  • Numbering test names to lock the order in - that hides the dependency instead of removing it, and it fails outright if your tool does not run by name
  • Retrying a red build - it only went green because the order happened to change
  • Turning on random order without a seed - what cannot be reproduced cannot be diagnosed
  • Stopping at «it works on my machine» - as section 8 showed, passing alone is a symptom, not evidence
  • Making shared fixtures the default for speed - an untrustworthy test costs more than a slow one
  • Enabling parallel execution while order dependency remains

13. Summary

Collecting what was actually executed here:

  • Of the 24 permutations of four tests sharing state, four were green. A 17 percent pass rate, and the tool's default order was one of those four
  • The default execution order differs by tool. Measured, unittest went by name and node:test by definition order. Logically identical tests all passed under one and failed under the other
  • There are five places state survives, and only temp files cross the process boundary
  • The tests that went red had not changed the shared state at all. The culprits were green
  • From 16 candidates, bisection reached the minimal reproducing pair in seven runs
  • The victim passed when run alone. That is precisely what «it works on my machine» is
  • Pinning seed 20260731 reproduced the order and the failure exactly
  • Changing only the fixtures, leaving assertions untouched, produced 24 out of 24 passing

The conclusion is the thesis stated at the start. Order dependency is not a moral failing about neglecting isolation; it is the fact that one more unvalidated input exists. That input is called order.

So the closing question changes. Not «does this test pass» but «in which orders does it pass». Running it reversed once takes a few seconds, and those seconds move Monday morning's red build to right here, right now.

# Test Order Dependency Checklist

When state survives between tests, **order becomes an input**.
A green run then means not «this is correct» but «this is correct in this order».

---

## 0. The 30-second verdict

| Question | Yes | No |
|---|---|---|
| Does the test pass when run alone? | **Order dependency confirmed** (see section 1) | Genuine defect, or it needs a predecessor |
| Does reversing the order break a different test? | **Order dependency confirmed** | Look elsewhere |
| Does the failing test itself mutate shared state? | It is also a suspect | **The culprit runs earlier** |
| Does it reproduce in a brand new process? | State lives **outside** the process (files, DB) | State lives in process memory |

The point: **a failing test is usually the victim, not the culprit.**

---

## 1. Cause types and how to tell them apart

| Type | Where it survives | Typical symptom | How to confirm | How to undo |
|---|---|---|---|---|
| Module-level global | The imported module object | A later test reads what an earlier one filled in | Print the module variable before and after each test | Reset in setUp, register an undo with addCleanup |
| Class attribute | The class object itself | A freshly built instance already carries old values | Check whether the attribute is per-instance or per-class | Move the mutable default into the constructor |
| Cache / memoization | The cache attached to the function | **Whoever runs first defines the answer**, the rest disagree | Print cache statistics or hit counts | Clear the cache in setUp, treat it as any other global |
| Temp files and directories | The file system | **Reproduces even in a brand new process** | Diff the directory listing before and after the run | One temp directory per test, removed automatically |
| Unrestored monkeypatch | The patched module attribute | Clock, randomness or network returns nonsense | Compare the current attribute against the original | **Register the restore before you patch** |

### Directional instincts

- Globals, caches, monkeypatches: usually **earlier pollutes later**
- Class attributes: often **fail early in the default order**, because they accumulate
- Temp files: **the previous run pollutes this one**, crossing the process boundary
- When a cache stores a **negative** result, the test that later inserts the data correctly is the one that goes red

---

## 2. Finding the minimal reproducing pair

Goal: find the A in «B breaks when it runs after A».

### Procedure

1. **Pin both endpoints first**
   - Confirm that the whole prefix plus the victim is RED
   - Confirm that the victim alone is GREEN
   - Order dependency requires both
2. **Cut the prefix in half**
   - Run the first half plus the victim
   - RED means keep the first half; GREEN means keep the second half
3. **Repeat step 2 until one test remains**
4. What remains is the **culprit**, and it plus the victim is the **minimal reproducing pair**

### Rules

- Run **every trial in a fresh process**, otherwise the trials pollute each other
- If neither half is RED on its own, **more than one test is involved**. Narrow down by removing halves instead
- With N candidates this takes roughly **2 times log2(N)** runs. Sixteen candidates land around seven runs, against sixteen for brute force

### After you find it

- **Keep the minimal pair as a regression test**
- Fix the culprit. Adding defensive code to the victim is first aid, not treatment

---

## 3. Fixture rules

1. **Never outsource your arrange step.** A test builds the preconditions it needs
2. **setUp means arriving at a known state,** not inheriting whatever was left behind
3. **Register the undo before you patch,** so restoration still runs when the test raises
4. **Cleanup functions run in reverse order of registration.** Resources are released in the opposite order they were acquired
5. **Class-scoped fixtures are not the default.** Use them only when speed forces it, and keep them read-only
6. **A cache is a global.** If you restored the setting, clear the cache too
7. **Temp files: new per test, self-removing.** Never share a hardcoded path
8. **Do not put cleanup at the end of the test body.** A failure never reaches that line

---

## 4. Safe to share vs never share

| Safe to share | Never share |
|---|---|
| Immutable constants, frozen config values | **Mutable** containers: dicts, lists, sets |
| Pure functions | Functions with a cache attached |
| Read-only fixture data | Databases and files that get written to |
| A temp directory created per test | A working directory at a fixed path |
| Helper methods on the test class | Mutable defaults held as class attributes |
| A **copy** of a precomputed value | A reference to the value **itself** |

One test decides it: **does the test write to it?** If yes, do not share it.

---

## 5. What to wire into CI

- **Shuffle the order, but print the seed.** Without the seed a red build cannot be reproduced
- Put the **seed and the replay command** at the very top of the failure log
- Add one **reverse-order run** to the nightly job. It is the cheapest reliable detector there is
- Keep the main pipeline on a **fixed order** and put randomization in a separate job, so a red build immediately tells you whether the code or the order caused it
- **Pin each newly found minimal pair** as its own test
- Remove order dependency before enabling parallel execution. Parallelism only shakes the order harder

---

## 6. Checklist

- [ ] I ran the new test **on its own**
- [ ] I ran the suite **in reverse** once
- [ ] I ran a random order at least once **with a pinned seed**
- [ ] **No leftover files** remain in the temp directory after a run
- [ ] Every monkeypatch has a **registered restore**
- [ ] Code that uses a cache has **cache clearing** in its fixture
- [ ] No **mutable defaults** sit on class attributes
- [ ] No test assumes **another test's name or position**
- [ ] Cleanup lives **in the fixture, not at the end of the body**
- [ ] The CI log prints the **order seed**

---

## 7. What not to do

- **Adding defensive code to the failing test first** — you patch the victim and lose the culprit
- **Numbering test names to lock the order in** — that hides the dependency rather than removing it
- **Retrying a red build** — a green retry only means the order happened to change
- **Turning on random order without a seed** — what cannot be reproduced cannot be diagnosed
- **Stopping at «it works on my machine»** — passing in isolation is the symptom, not the evidence
- **Making shared fixtures the default for speed** — an untrustworthy test costs more than a slow one
- **Enabling parallel execution before fixing order dependency**
