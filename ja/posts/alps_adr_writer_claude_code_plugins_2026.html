契機 — コード生成前に要件と設計判断を確定させる理由

大規模言語モデル（LLM）に基づくコーディングエージェントの普及に伴い、自然言語による指示からプログラムコードを直接生成・修正する速度は飛躍的に向上した。しかし、数行のプロンプトから直ちにコード生成を開始する手法は、システムの規模拡大とともに深刻な破綻を引き起こす。エージェントは指定されていない仕様の空白を自身の推論で勝手に補完し、アーキテクチャ上のトレードオフや非機能要件を考慮せずに場当たり的な実装を選択しやすい。

事前仕様を策定せずにコード生成を行う場合、実務開発において以下の3つの欠陥が頻発する。

  • 推論の独断による仕様の歪曲: エージェントが境界値や例外処理を自己判断で簡略化し、業務ルールを逸脱する。
  • 非機能的制約の脱落: 並行処理モデル、冪等性保証、エラーハンドリングの境界条件を無視し、表層の動作のみを満たす。
  • 別セッションにおけるデグレード: 以前の設計理由を知らない新しいエージェントが既存コードを変更する際に致命的な先祖返りを引き起こす。

このような曖昧さは実装の頻繁な手戻りを招き、さらに後のセッションで別のエージェントがコードを触る際に、なぜ以前の実装がその設計を選択したのかを理解できず、構造を破壊するデグレード（Regression）を誘発する。以前の記事で検証した計画モードとドキュメントの関係（plan_mode_planning_vs_plan_document_2026）やコードからの構造逆引き（archify_code_to_system_diagram_agent_skill_2026）が示した通り、エージェント生成コードが持続性を保つには明確な設計契約が残されていなければならない。

2026年10月にGitHub上でMITライセンスとして公開されたalps-writer-pluginsは、Claude CodeおよびOpenAI Codex環境においてこの課題を解決するために開発された。エージェントがコードを書く前に、対話型インタビューを通じて製品要件仕様（ALPS PRD）を確定させ、設計判断の根拠をアーキテクチャ決定記録（ADR）として固定化することを強制する。

中核原則 — 復元可能な事実を捨て再現条件のみを保存する

このプラグインの設計哲学の根幹をなす規則は、「復元可能な事実を排除し、再現可能な条件のみを保存する（preserve reproducible conditions, not recoverable facts）」という原則である。旧来のソフトウェア文書化が失敗する最大の要因は、関数一覧や変数名、ファイル配置といった実装の細部を文書に二重管理し、コードの変更とともに文書が陳腐化することにあった。

公式READMEは、記録すべき情報の境界を判定する厳格な3段階テストを定めている。

  • 要件ゲート（Requirement gate）: その事実が消失した場合、将来エージェントがコードを再生成した際に、必須のビジネス値、権限ルール、状態遷移、失敗保証、境界条件に違反する恐れがあるか？もしそうなら、契約を所有するレイヤー（PRDまたはADR）に必ず保存する。
  • コード読解テスト（Code-readthrough test）: その事実が必須要件ではなく、エージェントがコード、テスト、パッケージ設定（Cargo.toml等）を読めば確実に把握できる情報であるか？そうであれば文書からは排除し、コードとテストにのみ委ねる。
  • ADR承認ゲート（ADR admission gate）: なぜ他の選択肢を退けてその設計を採用したのかという理由（Rationale）がコード単体から読み取れず、その事実が変わると設計判断自体が変化するか？そうであれば決定内容、根拠、トレードオフ、前提条件をADRに記録する。

この原則によるシステム階層ごとの情報境界は以下の通りである。

文書・システム階層 保存する情報（Persist） 保存しない情報（Do not persist）
ALPS PRD（製品仕様） ユーザーの課題、観測可能な成果、ビジネス契約、成功条件、対象外範囲（Out of Scope）、長期的制約 具体的なコードパス、ライブラリ一覧、一時的なタスク計画、チケットやログの転記
ADR（アーキテクチャ決定） 承認された決定、厳格な要件契約、選択の根拠、比較検討した代替案、実装非依存の検証証拠 個別SDKのシグネチャ、DBテーブルの詳細カラム、内部関数呼び出しフロー
コードおよび自動テスト 実装構造、識別子名、外部依存関係、チューニング値、実行可能な検証ロジック PRDやADRファイルへの逆参照コメント
Issue、PR、Commit 個別変更の意図、レビュー経緯、変更履歴の記録 製品やアーキテクチャの正本（Single Source of Truth）を代替する記述

成果物構造 — ALPS PRD・Lite ALPS・ADRの役割分担

プラグインが扱う主要な成果物は3種類の文書形式に分かれており、それぞれ固有の責務を担う。

成果物フォーマット READMEの仕様説明 利用フェーズと開始コマンド 未確認の境界
Full ALPS PRD エージェント専用の9セクション要件定義書。Out of Scopeを1級節として包含 新規の包括的プロダクト要件定義時（/alps-init） 全9セクションの個別サブ見出し一覧
Lite ALPS 最小PoCのための4節構成（課題、C4 Context、体験、デモシナリオ） 迅速な概念実証やモックアップ開発時（/lite-alps-init） 4節以外の独自カスタム節追加機能の有無
ADR 単一の設計決定、根拠、契約、代替案を記録する独立ファイル 個別決定作成（/adr-new）またはPRD連携（/feature-to-adr） 外部ADR可視化ツール向けMarkdownメタデータ仕様
.mapping.json ADRの識別キー、ステータス、要約、依存関係（dependsOn）を追跡する内部台帳 実装承認およびトポロジカル依存判定時に自動参照 大規模モノレポにおける分割管理の正式仕様
glossary.md 文書内で登場する専門用語や略語の定義を集約する用語集付録 平易な言葉で説明できないドメイン用語の初回登場時 多言語ドメイン環境における対訳併記の標準指針

成果物間の協調動作を支える細部規則は以下の通りである。

  • Full ALPSの9節厳格性: 垂直スライス機能を明示し、依存関係グラフ（6.3）を通じて各機能の実行境界を定義する。
  • Out of Scope節の最優先: 実装してはならない境界を1級節として独立させ、エージェントの不要な肥大化を防ぐ。
  • Lite ALPSのPoC特化: 課題、C4 Context、主要体験、デモ手順のみに絞り、迅速な検証を可能にする。
  • .mapping.jsonによる依存追跡: ADRの正規キー、ファイルパス、状態、およびdependsOnを機械的に監査する。

ALPS（Agentic Lean Product Spec）は、AIエージェントによる開発を前提に最適化されたPRD規格である。人間の読者とは異なり、エージェントは暗黙の了解を解釈できないため、信頼性の高いコードを生成するには曖昧さを徹底的に排除した仕様が必要となる。エージェントがユーザーに焦点を絞った質問を投げかけ、ユーザーの明示的な承認なしには一切ディスクへ保存されない対話型作成フローを採用している。

Lite ALPSは、迅速なPoC作成を支援する4セクションの要件定義書である。課題と期待ビジネス効果の承認後、エージェントが最小限の解決策、C4 Context図、コア体験、実行可能なデモ手順を提案し、合意を形成する。

ADR（Architecture Decision Record）はadr.github.ioの提唱する原則に基づき、設計の決定事項と選択の理由を記録する。承認された決定は.mapping.jsonに登録され、後続の実装フローを統制する。

プラグイン構成 — alps-writerとadr-writerの単方向連携

本プラグインは単一の巨大ツールではなく、alps-writerとadr-writerという2つの独立プラグインに分離されている。

alps-writer (PRD作成ツール)
                      │
                      │ /feature-to-adr (単方向の契約移譲)
                      ▼
                    adr-writer  (ADR管理エンジン、完全独立稼働)
                      ├── /adr-new, /adr-impl, /adr-impl-refactor, /adr-impl-review
                      ├── /adr-sync (実装乖離の修復)
                      ├── /adr-rollup (分散した決定履歴の集約)
                      └── SessionStart フック (.mapping.jsonによる文脈復元)

この分離における重要なポイントは、adr-writer側はALPSを一切参照しない点にある。PRDを持たないプロジェクトでもadr-writer単体で完全に動作する。唯一の結合点は、alps-writerから呼び出される単方向コマンド/feature-to-adrのみである。

  • adr-writerの独立稼働: PRDを持たない軽量プロジェクトでも、独立した決定管理ツールとして動作する。
  • 単方向の契約移譲 (/feature-to-adr): ALPS PRDセクション7の機能要件を漏れなくADRへ引き渡す。
  • 引き渡し後のPRDの役割: 移譲完了後のPRDは過去の計画文書となり、実装の権威は完全にADRへ移行する。

4つの開始フロー — 既存プロジェクト分析からPRD先行開発まで

プラグインは状況に応じて4つの独立したワークフローを提供する。Claude Codeでは/skill-name、Codexでは$skill-nameとして呼び出される。

  • 既存プロジェクトへの導入（Existing Project）: /adr-import [パス]を実行すると、エージェントが既存のソースやテストを読み取り、EventStorming手法によりビジネスルールを抽出する。分析結果を意図・衝突レポートとして提示し、確認を経てProposed状態のADR群を生成する。
  • PoC仕様作成（PoC Authoring）: /lite-alps-initを実行し、4つの必須節からなる最小PoC仕様とデモシナリオを対話的に作成する。
  • PRD先行開発（PRD-First）: /alps-initで完全なALPSを作成し、/feature-to-adrでADRへ移譲した後に実装フェーズへ移行する。
  • ADR直接作成（ADR-Only）: PRDを介さず、/adr-new [カテゴリ]により直接ADRを作成して実装を開始する。

プラグインのインストールはマーケットプレイスコマンドのみで完結する。

# Claude Codeでのマーケットプレイス登録と導入
                    /plugin marketplace add haandol/alps-writer-plugins
                    /plugin install alps-writer@alps-writer
                    /plugin install adr-writer@alps-writer
                    
                    # Codexでのマーケットプレイス登録と導入
                    codex plugin marketplace add haandol/alps-writer-plugins
                    codex plugin add alps-writer@alps-writer
                    codex plugin add adr-writer@alps-writer

動作要件として、各CLIエージェントとNode.js 24以上が必要である。

実行ライフサイクル — トポロジカル依存ゲートとリファクタ・レビュー循環

ADRが作成されProposedとなった後、コードが実装されて承認されるまでの工程は厳密な自動ゲートによって保護される。

最も重要なゲートがトポロジカル依存関係ゲート（Topological Dependency Gate）である。開発者が/adr-impl [id]を実行すると、エージェントは.mapping.json内のdependsOnを走査する。依存先に1つでもAcceptedになっていないProposedのADRが存在する場合、実装は即座に拒否され、依存元の実装を先に行うよう促される。

前提条件が揃いコードが作成された後は、以下の検証サイクルが実行される。

  • 初期実装とテスト実行: バーティカルスライス（UIからAPI、DBまで）を実装し、テストを実行する。単なる正常系だけでなく、境界条件や異常系の網羅が必須であり、正常系のみのテストではゲートを通過できない。
  • 検証付きリファクタリング（/adr-impl-refactor）: テスト成功後、実行効率、結合度、重複度を検証する。動作を変更しない安全な改善のみが適用され、前後のテスト実行によって品質が担保される。
  • リスク基準の完了レビュー（/adr-impl-review）: コードがADRの契約を満たしているかを最終判定する監査ゲートである。レビューを合格して初めてADRのステータスがAcceptedへと遷移する。
  • 実装乖離の修復（/adr-sync）: 手動編集や大幅な改修により文書とコードにズレが生じた場合、差分を修復する。
  • 決定履歴の統合（/adr-rollup）: 1つの論理的決定が複数のADRに分散して進化した際、履歴を1つの決定連鎖へと整理統合する。

非侵襲ハーネス — プラグイン削除後も標準Markdownとして存続する設計

AIツールの導入において最も警戒すべきリスクは、特定ベンダーの独自仕様へのロックインである。ツール専用の独自バイナリ形式に依存すると、将来の移行が困難になる。

alps-writer-pluginsは自らを「除去可能な非侵襲ハーネス（A removable, non-invasive harness）」と定義している。生成される成果物はすべて標準的なMarkdownファイル（docs/adr/*.md等）とソースコード、そして簡潔なJSON（.mapping.json）のみで構成される。

この非侵襲構造が保証する持続可能性の3大メリットは以下の通りである。

  • 標準ファイル形式の担保: すべての仕様はGitHubウェブ上で直ちに表示可能なMarkdownファイルとして永続化される。
  • 隠蔽された独自状態の排除: プラグインを削除しても設定破損や孤立化が起きず、成果物がそのまま残る。
  • 将来モデルとの完全な互換性: 今後別の新しいAIモデルを投入しても、追加の変換処理なしに既存仕様を理解できる。

確認できなかったこと

  • 開発速度の向上やバグ削減効果に関する客観的な定量的ベンチマーク測定値。公式READMEには運用の原則のみが記載されており、数値統計は含まれていない。
  • Claude CodeおよびCodex以外の開発環境（Cursor、Windsurf、GitHub Copilot等）に対する公式サポート計画。
  • 巨大なモノレポにおいて.mapping.jsonをパッケージ単位で分割統括する正式なマルチプロジェクト運用規約。
  • Full ALPS PRDの全9セクションの詳細な項目名と標準テンプレートの全文。
  • SessionStartフックに対応していない古いCLI環境での手動コンテキスト注入手順。
