SameSite Lax・Strict・None - どのリクエストでクッキーが消えるか

決済から戻ったらログアウトしていた理由を、リクエスト種別ごとの判定表で

2026-07-31 開発/インフラ

症状: 決済が終わって戻ったらログアウトしていた

利用者がカートで決済ボタンを押す。外部決済事業者の画面に移り、カード情報を入れて承認を受ける。そして自社サイトに戻ってくる。ところがログインが切れている。決済は正常に処理されたのに、肝心の注文履歴画面に入れない。

この種の申告はたいてい、セッションの有効期限を延ばすか、決済事業者に問い合わせるか、再現しないという理由で静かに閉じられる。だがサーバーのログを見れば答えがすでに出ていることが多い。戻ってきたリクエストのCookieヘッダーにセッション名がそもそも無い。認証に失敗したのではなく、クッキーが最初から載っていない。

クッキーを送るかどうかを決めるのはサーバーではなくクライアントだ。その判断に使われる属性がSameSiteであり、値は三つしかない。ところがこの三つは「強い・中くらい・弱い」の一直線ではない。リクエストの種類ごとに分かれ方が違う。

  • Strictは別サイト起点のリクエストには一律に付かない。利用者が自分でリンクを押して入ってきても付かない
  • Laxはアドレスバーが変わる遷移でありかつ安全なメソッドのときだけ例外的に付ける。この二条件が本稿の核心だ
  • Noneはすべてに付ける。その代わりSecureが無ければクッキーは保存すらされない

本稿は「ではNoneにしましょう」で終わらせない。それは原因を見ずに扉を開けておくことだ。代わりにどのリクエストでこのクッキーが必要かを先に一覧に書く手順を作る。一覧が決まれば値は自ずと決まる。

実行環境。以下の出力はWindows 10 Pro (10.0.19045)上でNode.js v22.16.0 (win32)により実際に実行した結果だ。ローカルサーバー2台を任意の高番号ポート(18081、18082)に立てて確認し、実験終了後にすべて停止した。規格の根拠はRFC 6265bis (draft-ietf-httpbis-rfc6265bis-22, 2025-12-01)とMDNである。スクリプトはシェル引数やヒアドキュメントではなくすべてファイルに保存して実行した。

★本稿が直接確認できなかったこと。ブラウザを起動してクッキーストアを観察してはいない。したがって「このリクエストにクッキーが付く・付かない」という判定は規格の文言をコードとして実装し計算した値であり、実ブラウザの挙動を観測した値ではない。下の表ではどの行が規格根拠でどの行が実測かを専用の列を設けて明示した。導入前に対象ブラウザで再確認することを勧める。

本稿が扱わないこと。Webセキュリティ一般やCSRF対策の全体像はWebセキュリティ基礎とIDSとIPSで扱った。ここではSameSiteの値の挙動という一点だけを掘る。登場するドメイン・ポート・クッキー名はすべて架空である。

1. 三つの値は実際に何を分けているのか

規格の文は短い。RFC 6265bisはStrictを「同一サイトのリクエストにのみ送る」、Laxを「同一サイトのリクエストと、クロスサイトのトップレベル遷移に送る」、Noneを「同一サイトとクロスサイトの両方に送る」と定義する。問題はこの三文だけでは自分のページのどの要素がどれに当たるのかが分からないことだ。画像タグはトップレベル遷移なのか。formの送信は。iframeは。

そこで規格の判定規則をそのままコードに移し、ページが作り得るリクエストの形をすべて通した。

node v22.16.0 / win32
cookie set by https://app.example.com , request initiated from https://portal.other-site.com

cross-site link click             no       YES      YES      YES
cross-site image load             no       no       YES      no
cross-site script/css load        no       no       YES      no
cross-site form GET               no       YES      YES      YES
cross-site form POST              no       no       YES      no
cross-site fetch / XHR            no       no       YES      no

表を縦に読むと「Noneが一番寛容だ」しか分からない。横に読んで初めて役に立つ。各値がどこで分かれるかだけを抜き出した。

--- 3-2. the same table, but only the differences that matter ---
  shapes where Strict and Lax disagree:
    - cross-site link click
    - cross-site form GET
    - cross-site 302 landing as GET
  shapes where Lax and None disagree:
    - cross-site image load
    - cross-site script/css load
    - cross-site form POST
    - cross-site fetch / XHR
    - cross-site iframe load
    - cross-site 307 landing as POST
  • StrictとLaxが分かれるのは三行だけだ。リンククリック、form GET、そして302で戻ってGETで着地する場合。三つともアドレスバーが変わる遷移という共通点を持つ
  • LaxとNoneが分かれるのは残り全部だ。画像、スクリプト、fetch、iframe、そしてPOST
  • つまりLaxは「副リソースには付かない」に要約される。他人のページがこちらのサーバーの画像を読み込んでも、こちらのセッションは載らない。これがLaxが既定値になった理由でもある
  • 同一サイト内では三つの値がすべて同じように動く。だから自社サイトだけを押して回るテストでは差が永遠に現れない

1.1 この表のどれが実測でどれが文書か

ここは正直に分けなければならない。本稿はブラウザを起動してクッキーストアを直接観察していない。上の判定は規格の文言をコードに移して計算した値である。一方サーバーが実際に何を送り出し何を受け取るか、そしてリダイレクトがメソッドを書き換えるかはローカルサーバー2台を立てて直接測定した。その区別を表の最終列に書いた。

別サイトによるスクリプト・CSSの読み込み付かない付かない付く付かない規格
別サイトからの form GET付かない付く付く付く規格
別サイトからの form POST付かない付かない付く付かない規格
別サイトからのfetch・XHR付かない付かない付く付かない規格

最後の二行だけが「規格 + 実測」である。リダイレクトがメソッドを書き換えるかどうかはこの機械上でHTTPにより直接測定し、その出力は6節にある。他の行の判定は規格の解釈なので、実装ごとに異なりうるという前提で対象ブラウザにて確認するほうが安全だ。

2. 値を書かないと何になるのか

最も多い事故はここから始まる。SameSiteをまったく書いていないクッキーは「制限なし」ではない。RFC 6265bisは属性がないか値が認識できないとき「Laxに相当する既定の施行モード」を適用すると記す。MDNも「SameSite属性が設定されていなければクッキーは既定でLaxとして扱われる」と同じことを述べる。

だからコードを一行も直していないのにある日決済復帰が壊れることが起きる。サーバー側はそのままなのに、そのクッキーを解釈する側の既定方針が変わったからだ。値を書かないのは判断をしなかったのではなく判断を他人に委ねたことである。

さらに悪いのは書いたのに書かれていない場合だ。値に打ち間違いがあるとどうなるかをパーサーを作って確認した。

--- 2-3. the silent-typo trap, side by side ---
  SameSite=Strict     -> Strict
  SameSite=strict     -> Strict
  SameSite=Strick     -> Default(Lax)   <- NOT what the author typed
  Samesite=Strict     -> Strict
  SameSite =Strict    -> Strict
  • SameSite=Strickはエラーではない。認識できない値なので既定の施行モード、つまりLaxへ静かに落ちる
  • 一方で属性名の大文字小文字と等号まわりの空白は無害だ。SamesiteもSameSite =Strictも正常に処理される
  • つまり危険なのは値の打ち間違い一つだけであり、それだけが何の警告もなく方針を変える
  • ゆえに値の文字列を定数に置き、コードレビューで目視確認するのが実質的な防御になる。構文チェッカーはこの打ち間違いを捕まえてくれない

既定値にはもう一つ条件が付く。規格は「Lax-allowing-unsafe」という任意の互換モードを許容する。明示的にSameSiteを書いていないクッキーに限り、作られて間もない場合はクロスサイトのPOSTにも付けてよいというものだ。規格は「2分以下が妥当な限界に見える」と記す。

--- 3-3. the 2-minute window applied to a cross-site POST ---
  cookie age   10s  ->  maybe*   (explicit Lax would be: no)
  cookie age  119s  ->  maybe*   (explicit Lax would be: no)
  cookie age  121s  ->  no   (explicit Lax would be: no)
  cookie age 3600s  ->  no   (explicit Lax would be: no)
  a cookie that works in testing and fails in production may simply be older.

これが「自分の環境では動くのですが」の正体である場合が多い。開発者はログインしてすぐ決済を押す。クッキーができたてだ。実際の利用者はログインしたまましばらく経ってから決済する。同じコードが時間によって違う挙動に見える。このモードは任意なので、動けば幸運というだけで設計の根拠にはできない。

3. Noneを使ってSecureを落とすとクッキーは捨てられる

症状だけを見てSameSite=Noneに変える対処はよくある。だがここには罠があり、この罠は何のエラーも出さない。RFC 6265bisの保存アルゴリズムにこういう一文がある。クッキーのsame-siteフラグがNoneのとき、secure-onlyフラグが真でない限りアルゴリズムを中断してクッキーを完全に無視する。

サーバーがそのヘッダーを実際に送り出すのか、そしてそのとき応答がどう見えるのかを直接確認した。

node v22.16.0 / win32   server 127.0.0.1:18081

--- 7-1. server emits it, the jar decides ---
recipe             HTTP status   what left the server                    jar verdict
-----------------------------------------------------------------------------------------------
None, no Secure    200 OK        sid=abc; SameSite=None                  REJECTED  (None without Secure)
None + Secure      200 OK        sid=abc; SameSite=None; Secure          stored  (None + Secure)
Lax, no Secure     200 OK        sid=abc; SameSite=Lax                   stored  (Lax)
Strict + Secure    200 OK        sid=abc; SameSite=Strict; Secure        stored  (Strict + Secure)
none + secure      200 OK        sid=abc; samesite=none; secure          stored  (None + Secure)
None; Secure=1     200 OK        sid=abc; SameSite=None; Secure=1        stored  (None + Secure)

  every row returned 200. the server never objects.
  row 1 is thrown away before it is ever stored, so no request will carry it.
  row 6 shows Secure is a valueless flag: Secure=1 still reads as present.

六行すべてが200 OKだ。サーバーはこの組み合わせに何の不満もない。サーバーがすることは文字列をヘッダーに載せて送ることだけであり、捨てるかどうかの判定は反対側で起きる。

--- 7-2. the failure you will actually observe ---
  HTTP/1.1 200 OK
  Set-Cookie: sid=abc; SameSite=None
  Date: Thu, 30 Jul 2026 20:33:11 GMT
  Connection: close
  Content-Length: 3

  response looks perfect. no 4xx, no log line, no exception.
  the symptom surfaces one request later, as a missing session,
  in a completely different part of the code. that is why it costs a day.

--- 7-3. why the rule exists, in one line ---
  SameSite=None means: send me on requests I did not initiate.
  Secure means: only over a protected transport.
  the spec refuses to let a cookie be maximally exposed and unprotected at once.
  • 失敗が応答に現れない。ステータスコードは200で、ログにも例外にも何も残らない
  • 症状は一リクエスト後に、まったく別のコード領域で「セッションなし」として現れる。だから原因追跡が一日を食う
  • Secureは値を持たない印だ。上の五行目・六行目のように小文字で書いてもSecure=1のように値を付けても「あり」と読まれる
  • 規則自体は単純な論理だ。Noneは「自分が始めていないリクエストにも自分を送れ」という意味でありSecureは「保護された経路でのみ」という意味なので、規格は最も広く露出しながら保護がない状態を許さない

実務では順序が大事だ。Noneはhttpsが前提である。社内ツールがまだ平文で提供されているならNoneは選択肢ではなく先に解決すべき前提条件だ。そして__Host-接頭辞を使えばSecureとPath=/、Domain未指定を強制できるので、間違いを構造的に防げる。

4. Set-Cookie文字列はどう読まれるのか

Set-Cookie一行がどう解釈されるかが分かれば、上の罠がなぜ静かなのかが理解できる。規格の解析手順をそのまま実装し、十種類の文字列を通した。

node v22.16.0 / win32

--- 2-1. parsing ten Set-Cookie strings ---
input                                                              -> SameSite      Secure  note
---------------------------------------------------------------------------------------------------------
[sid=abc123; Path=/; HttpOnly; SameSite=Lax]                       -> Lax           false
[sid=abc123; path=/; httponly; samesite=lAx]                       -> Lax           false
[sid=abc123;SameSite=Strict;Path=/]                                -> Strict        false
[sid=abc123;    SameSite   =   None   ;   Secure  ]                -> None          true
[sid=abc123; SameSite=None]                                        -> None          false   DISCARDED (None without Secure)
[sid=abc123; SameSite=Loose; Path=/]                               -> Default(Lax)  false
[sid=abc123; SameSite; Path=/]                                     -> Default(Lax)  false
[sid=abc123; SameSite=Strict; SameSite=None; Secure]               -> None          true
[sid=abc123; Path=/; Flavour=vanilla; Priority=High; SameSite=Lax] -> Lax           false   ignored attrs: Flavour=vanilla, Priority=High
[sid=; Path=/; Max-Age=0]                                          -> Default(Lax)  false

--- 2-2. what the parser proved ---
  case of attribute name and value is irrelevant : true
  attribute order is irrelevant                  : true
  surrounding whitespace is stripped             : true
  unknown attribute drops the ATTRIBUTE only     : true  (ignored: Flavour=vanilla)
  duplicate attribute: last one wins             : None
  typo in the VALUE is not an error, it degrades : Default(Lax)   <- raw was [Loose]
  • 属性名は大文字小文字を問わない。規格が直接「CamelCaseで表記しているがどの大小文字も受け入れる」と記している
  • 順序は無関係だ。Secureを前に書いても後ろに書いても結果は同じ
  • 空白は除去される。名前と値の前後の空白を取り除くことが手順に明記されている
  • 未知の属性はその属性だけ捨てる。Flavour=vanillaのようなものが混ざってもクッキー自体は生き残る。だから新しい属性が標準に追加されても古いクライアントが壊れない
  • 同じ属性が二度出れば最後が勝つ。八行目はStrictが先に出ているのに結果がNoneだ。ミドルウェア二か所が同じクッキーを触るときここで事故が起きる
  • 認識できない値はエラーではなく降格だ。六行目と七行目がそれで、2節の打ち間違いの罠はここから来る

最後の行も見る価値がある。sid=; Max-Age=0はクッキーを消す慣用的な方法だが、このときもSameSiteが既定値に落ちる。削除用のSet-Cookieに元のクッキーと同じ属性の組み合わせを合わせないと削除が効かない現象がここで生まれる。ログアウトできない不具合のよくある原因だ。

5. Domain・Path、そして「サイト」の基準

SameSiteだけを見ても半分だ。どのリクエストにクッキーが付くかは三つのフィルターをすべて通過して決まる。ドメインが合い、パスが合い、その次にSameSiteの判定が来る。前の二つを先に確認した。

node v22.16.0 / win32

--- 5-1. host-only cookie vs Domain cookie ---
request host              no Domain attr   Domain=example.com
---------------------------------------------------------------
example.com               true             true
www.example.com           false            true
api.a.example.com         false            true
notexample.com            false            false
example.com.evil.net      false            false
  omitting Domain is the TIGHTER setting. adding it widens the blast radius.

--- 5-2. Path matching ---
Path=/app   request path        match
------------------------------------------
            /app                true
            /app/               true
            /app/orders         true
            /application        false
            /                   false
            /x/app              false
  /application does not match /app. the boundary is a slash, not a prefix.
  • Domainを省くほうが狭い。省けばクッキーを配ったホストにしか行かない。「既定は緩いだろう」という直感とちょうど逆だ
  • Domain=example.comと書けばすべてのサブドメインに行く。api.a.example.comのように数段下でも同じだ
  • 似た名前は引っかからない。notexample.comもexample.com.evil.netも一致しない。接尾辞比較の前に点の境界が必要だからだ
  • Pathの境界はスラッシュだ。Path=/appは/applicationに一致しない。ただしMDNが明言する通りPathはセキュリティ機構ではない

そして「サイト」という語が問題になる。日常語では「うちのサービス」程度だが、ここではスキーム + 登録可能ドメインという正確な意味を持つ。よく一緒に使われる「オリジン」とは違う。

--- 5-4. what "same site" actually compares ---
A                              B                              same site?
---------------------------------------------------------------------------
https://app.example.com/       https://api.example.com/       YES
https://app.example.com/       https://example.com/           YES
https://app.example.com:443/   https://app.example.com:8443/  YES
https://app.example.com/       http://app.example.com/        no
https://app.example.com/       https://app.example.net/       no
https://shop.example.co.kr/    https://pay.example.co.kr/     YES
https://a.github.io/           https://b.github.io/           no
http://localhost:18081/        http://localhost:18082/        YES
http://localhost:18081/        http://127.0.0.1:18082/        no

--- 5-5. site vs origin, side by side ---
  URL    : https://app.example.com:8443/orders?x=1
  origin : https://app.example.com:8443        <- scheme + host + PORT
  site   : https://example.com     <- scheme + registrable domain, no port
  these two words are not interchangeable, and cookies use the second one.
  • ポートが違っても同一サイトだ。クッキーはオリジン単位ではない。8443に立てた開発サーバーが本番とクッキーを共有してしまうのはこのためだ
  • スキームが違えば別サイトだ。httpとhttpsが分かれる
  • 公開接尾辞の下では一段多く消費される。shop.example.co.krとpay.example.co.krは同一サイトだが、a.github.ioとb.github.ioは別サイトだ。静的ページホスティングで隣のクッキーが読めない理由がこれである
  • localhostと127.0.0.1は別サイトだ。ローカルでクロスサイトを模すときこの二つを混ぜると意図せずクロスサイトになり、逆にポートだけ変えてもクロスサイトの再現に失敗する

設計への影響が一つある。サブドメインを分けることはSameSiteの観点では何の隔離も生まない。決済ドメインを切り離しても同じ登録可能ドメインの下なら依然として同一サイトであり、その間の遷移にはStrictのクッキーまでそのまま付く。隔離を望むならドメイン自体を分けるかDomain属性を外すほうを見るべきだ。

6. ログインが切れる経路を段階ごとに

ここで冒頭の症状に戻る。外部決済事業者や認証提供者へ出て戻ってくる流れで、正確にどの地点でクッキーが消えるのかが核心だ。分岐点はただ一つ、戻るときのメソッドである。

この部分は規則ではなく実測だ。ローカルにサーバーを2台立てて片方がもう片方へリダイレクトするようにし、POSTで出たときどのメソッドで着地するかをステータスコードごとに測定した。

node v22.16.0 / win32
provider 127.0.0.1:18082  ->  app 127.0.0.1:18081/return

--- 4-1. we POST to the provider; it redirects us back. which method lands? ---
redirect status   we sent   we landed with   Lax cookie would ride?
---------------------------------------------------------------------------
301               POST      GET              yes - safe method
302               POST      GET              yes - safe method
303               POST      GET              yes - safe method
307               POST      POST             NO  - unsafe method
308               POST      POST             NO  - unsafe method

  measured with an HTTP client on this machine, not with a browser.
  the method rewrite on 301/302/303 is the whole ballgame:
  307 and 308 preserve POST, and a Lax cookie is withheld on arrival.
  • 301・302・303はメソッドをGETに書き換えて着地させる。するとLaxの二条件(トップレベル遷移 + 安全なメソッド)を両方満たしてクッキーが付く
  • 307・308はPOSTをそのまま保つ。着地リクエストがクロスサイトのPOSTになり、Laxではクッキーが付かない
  • この差はこちらのコードではなく相手の設定画面の数字ひとつだ。こちらが変わらなくても相手が変えれば症状が出たり消えたりする
  • Strictならメソッドと無関係に付かない。302でGET着地しても同じだ
  • formを自動送信して結果をPOSTで返す方式も結果は同じだ。見た目がリダイレクトでないだけでクロスサイトのPOSTである点は変わらない
--- 4-2. the redirect chain, step by step ---
  step 1  POST http://127.0.0.1:18082/go?code=307
          <- 307 Location: http://127.0.0.1:18081/return?via=307
  step 2  the client repeats the request at the new URL
          this second request is cross-site AND it is a POST
          -> Strict: withheld.  Lax: withheld.  None+Secure: sent.

--- 4-3. same chain, but the provider returns us with 303 ---
  landed method : GET   (the body was dropped)
  -> Strict: still withheld (cross-site).  Lax: sent.  None+Secure: sent.
  one number in the provider config moves the session between present and absent.

--- 4-4. and the second hop, once we are back on our own site ---
  same-site GET landed with method GET
  this is why the bug looks intermittent: reload the page after landing
  and the next request IS same-site, so Strict starts working again.

6.1 六段階に区切ってみる

  1. 利用者が自社サイトで決済ボタンを押す。ここまではすべて同一サイトであり三つの値すべてが正常に動く
  2. 決済事業者のドメインへ移動する。この区間にこちらのクッキーは関与しない
  3. 決済事業者が承認結果をこちらの復帰URLへ戻す。このリクエストがクロスサイトだ
  4. 戻し方がGETならLaxのクッキーが付いてログイン状態が保たれる
  5. 戻し方がPOSTならLaxのクッキーが付かない。サーバーは未ログイン利用者のリクエストと見なしログイン画面を出す
  6. 利用者がその画面で何かを押せばそこからは同一サイトなのでクッキーがまた付く。だから「更新したら直りましたけど」という報告が続き、再現不能としてチケットが閉じられる

対処の順序もここから出る。値をNoneに緩めるのは最後の手段だ。まず復帰地点をGETで受ける薄いエンドポイントに変えることを検討する。決済結果の本文が必要ならその本文はサーバー間通知で受け取り、利用者のブラウザはGETだけで戻せばよい。こうすればクッキーの方針を広げずに症状が消える。

7. サイズと個数、天井は二つある

セッションが消えるもう一つの経路がある。クッキーが大きすぎて保存されないことだ。規格の文は明快である。名前と値の長さの合計が4096オクテットを超えるとアルゴリズムを中断しSet-Cookie文字列を丸ごと無視する。

node v22.16.0 / win32
max HTTP header size this runtime accepts: 16384 bytes

--- 6-1. the 4096-octet line, name + value together ---
name len   value len   sum     jar keeps it?
-----------------------------------------------
3          4093        4096    true
3          4094        4097    false
3          4095        4098    false
500        3596        4096    true
500        3597        4097    false
  the limit counts the NAME too. renaming session_identifier to sid buys you bytes.

--- 6-2. an oversized cookie is dropped whole, not truncated ---
  value length          : 5000
  jar keeps it          : false
  what the app receives : nothing at all
  no error, no warning, no half-value. the next request simply has no session.
  • 名前も長さに含まれる。session_identifierをsidに縮めれば値に使えるバイトがその分増える
  • 切り詰めではなく丸ごと捨てられる。前半だけ残るのではなく、まったく無いことになる
  • だから症状が「値がおかしい」ではなく「クッキーがない」として現れる。サイズを疑うまでに時間がかかる理由がこれだ
  • 非ASCII文字や絵文字が入ると計算がまた変わる。オクテット単位なので文字数ではなくエンコード後のバイト数を数える必要がある

天井は一つではない。クッキーストアの限界の上にHTTPヘッダーのサイズという別の限界がある。こちらは実際のサーバーに当ててみた。

--- 6-3. many cookies at once, measured against a real server ---
count   Cookie header bytes   server response
-------------------------------------------------------
10      856                   200 OK  cookies=10 bytes=848
50      4296                  200 OK  cookies=50 bytes=4288
100     8596                  200 OK  cookies=100 bytes=8588
180     15556                 200 OK  cookies=180 bytes=15548
300     25996                 431 Request Header Fields Too Large
  past the runtime header budget the request dies before your code runs.
  the cookie jar has its own per-domain cap on top of this. two ceilings, not one.

--- 6-4. every cookie rides on EVERY matching request ---
  one 1.2 KB cookie             : 1204 bytes per request
  60 requests to render a page  : 72240 bytes uploaded, per page view
  and Domain=example.com sends it to the image host and the API host too.
  this is the real argument for keeping an identifier in the cookie and state on the server.

180個(15,556バイト)までは通り、300個(25,996バイト)で431が返った。ここで重要なのはアプリケーションのコードが実行されなかったという点だ。こちらのログも、こちらの例外処理も、こちらのエラーページも出ない。だから「特定の利用者だけサイト全体が使えない」という申告になり、その利用者のクッキーを消せば直る。MDNが「クッキーはすべてのリクエストとともに送られるため性能を悪化させうる」と記したのはまさにこの話である。

8. サーバーはなぜ理由を知り得ないのか

診断が難しいことには構造的な理由がある。サーバーが送るものと受け取るものが対称ではない。

node v22.16.0 / win32
server A 127.0.0.1:18081   server B 127.0.0.1:18082

--- 1-1. exact Set-Cookie bytes the server puts on the wire ---
recipe            Set-Cookie line as received
---------------------------------------------------------------------------
no-attr          Set-Cookie: sid=abc123; Path=/; HttpOnly
lax-explicit     Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Lax
strict           Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Strict
none-no-secure   Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None
none-secure      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None; Secure
bogus-value      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Loose
weird-case       Set-Cookie: sid=abc123; path=/; httponly; samesite=lAx

--- 1-3. what the server sees when a client sends a Cookie header ---
  with Cookie header : cookie-header-seen: sid=abc123; theme=dark
  without            : cookie-header-seen: (none)
  the server cannot tell WHY a cookie is missing. absent == never-sent == blocked.

--- 1-4. no SameSite attribute survives into the Cookie header ---
  cookie-header-seen: sid=abc123
  Cookie: carries name=value only. no Path, no Domain, no SameSite.
  the server gets no evidence of which policy was applied.
  • Set-Cookieには属性がすべて載る。Path、HttpOnly、SameSiteまでそのまま出ていく
  • 戻ってくるCookieヘッダーには名前と値しかない。どの方針で保存されたかに関する情報が一つもない
  • だからサーバーはクッキーが無い理由を区別できない。ログアウトした利用者なのか、SameSiteに阻まれたのか、サイズ超過で保存されなかったのか、利用者が自分で消したのかがすべて同じ形に見える
  • 結局リクエスト側の情報から推定するしかない。OriginとRefererでどこから来たかを見て、メソッドが何かを見て、その組み合わせがこちらの方針でクッキーを許すかを1節の表と突き合わせるのだ

だから実用的な対策はログだ。セッション無しで到着したリクエストについてメソッド・Origin・Refererを併せて記録しておけば、判定表と突き合わせるだけで原因が大きく絞られる。このログ一行がなければ再現の試みに何日も費やすことになる。

9. 何をどこに入れ、値をどう選ぶか

ここまで来ると問いが変わる。「どの値が良いか」ではなく「何をクッキーに入れるか」が先だ。

原則は二行である。クッキーには識別子だけを入れる。状態はサーバーに置く。7節の二つの天井がその根拠であり、そうすればサイズの問題と帯域の問題が同時に消える。次にその識別子がどのリクエストに載るべきかを一覧に書けば、値は一覧から自動的に出てくる。

クッキーの中身クロスサイトで必要か推奨値併せて付けるもの
ログインセッション識別子(一般的なWebアプリ)不要LaxSecure HttpOnly Path=/
ログインセッション + 外部決済・OAuth復帰復帰地点のみLax + 復帰をGETにSecure HttpOnly
管理コンソール・社内ツール不要StrictSecure HttpOnly __Host-接頭辞
CSRFトークン(二重送信方式)不要StrictまたはLaxSecure、HttpOnlyなし
他社ページに埋めるウィジェット・SSO iframe必要NoneSecure必須 + Partitionedを検討
広告・分析用の識別子必要NoneSecure、ブロックされる前提で設計
言語・テーマなど表示設定不要LaxSecure、ローカルストレージも検討
  1. このクッキーが別サイト起点のリクエストに付く必要がある場合をすべて書き出す。無ければ無いと書く
  2. 一覧が空ならLaxを使う。トップレベル遷移でも不要だと確信できるならStrictまで狭める
  3. 一覧が空でないときだけNoneを使い、そのときはSecureも併記する。そしてその一覧をコメントか文書に残す。次の人が理由を知らずにまた広げるのを防ぐ

最後に線をはっきり引く。SameSiteはCSRFの緩和策であってCSRF対策のすべてではない。MDNも「クロスサイトリクエストフォージェリ攻撃に対してある程度の保護を提供する」と記すのであって、解決すると書いてはいない。値が何であれ状態を変えるリクエストには別途のトークン検証が必要だ。Webセキュリティ全体の骨格はWebセキュリティ基礎に、検知層はIDSとIPSに整理してある。

値一行の定義典型的な症状
Strict同一サイトのリクエストにのみ付く外部リンクから入った最初の画面がログアウト状態
Lax同一サイト + トップレベル遷移の安全なメソッド決済・OAuthがPOSTで返すとセッションが消える
Noneすべてのリクエストに付くSecureを外すとクッキー自体が保存されない
(値なし)Laxと同じ扱い「コードを触っていないのにある日壊れた」

表の「典型的な症状」列が実戦では最も役に立つ。症状を先に見て値を逆算するほうが、値を変えながら配って試すよりはるかに速い。

10. 点検リスト

  • セッションクッキーのSameSite値を明示した(既定値に頼らない)
  • Noneを使うクッキーにSecureが付いている
  • Noneを選んだ理由をリクエストの一覧として書ける
  • 外部決済・OAuthの復帰地点のステータスコードとメソッドを確認した
  • 復帰地点がPOSTなら薄いGETエンドポイントを別に用意した
  • Domain属性は本当に必要なときだけ付けた(省略のほうが狭い)
  • サブドメインが同一サイトとして束ねられることを設計に反映した
  • ローカル検証でlocalhostと127.0.0.1を意図せず混ぜていない
  • クッキー一つの名前+値が4096オクテット未満である
  • ドメインあたりのクッキー個数と総バイト数を実際に測った
  • SameSiteの値の文字列に打ち間違いがない(打ち間違いは静かに既定値になる)
  • セッション無しで到着したリクエストのメソッド・Origin・Refererをログに残す

11. 誤解とやってはいけないこと

  • ❌ 症状が出た瞬間にNoneへ変えること — どのリクエストで必要かを先に一覧で決める
  • ❌ Noneを使いながらSecureを落とすこと — 保存の段階でクッキーが捨てられる
  • ❌ 既定値に依存すること — 明示しないクッキーは解釈する側の既定方針に従う
  • ❌ localhostだけで確認して終えること — ポートだけ変えたローカル環境はクロスサイト条件を再現できない
  • ❌ サブドメイン分離で隔離できたと信じること — 同じ登録可能ドメインの下は同一サイトだ
  • ❌ SameSiteをCSRF対策のすべてとして扱うこと — 緩和策であって防御の全部ではない
  • ❌ セッションの状態をクッキーに丸ごと入れること — 4096オクテットの上限と毎リクエストの帯域を同時に払う

最後に一つ。ブラウザのバージョン別挙動を断定しないこと。既定値の適用範囲、「Lax-allowing-unsafe」の採否、分割ストレージの扱いは実装ごとに異なりうるし時間とともに変わる。規格は何が許されるかを定めるだけで、すべての実装が同じように動くとは保証しない。導入前に対象ブラウザで直接確認する手順を入れることが唯一老いない対策である。

# SameSite クッキー — 値の選択判断表とリクエスト種別ごとの判定表

> 出典: braindetox.kr — SameSite Lax・Strict・None、どのリクエストでクッキーが消えるか
> 根拠: RFC 6265bis (draft-ietf-httpbis-rfc6265bis-22, 2025-12-01) + MDN
> 実行環境: Windows 10 Pro 10.0.19045 / Node.js v22.16.0 (win32) / ローカルサーバー2台
> **限界の明示**: ブラウザのクッキーストアの実挙動は本書では直接確認していない。
> 以下の判定欄は**規格の文言をコードとして実装し計算した値**である。導入前に対象ブラウザで再確認すること。

## 1. リクエスト種別ごとの判定表

クッキーを置いた側: `https://app.example.com`
リクエストを開始した側: `https://portal.other-site.com`

| リクエスト種別 | Strict | Lax | None+Secure | 値なし | 根拠 |
|---|---|---|---|---|---|
| 同一サイト内のページ移動 | 付く | 付く | 付く | 付く | 規格 |
| 別サイトからのリンククリック | **付かない** | 付く | 付く | 付く | 規格 |
| 別サイトによる画像の読み込み | 付かない | 付かない | 付く | 付かない | 規格 |
| 別サイトによるスクリプト・CSSの読み込み | 付かない | 付かない | 付く | 付かない | 規格 |
| 別サイトからの form GET | **付かない** | 付く | 付く | 付く | 規格 |
| 別サイトからの form POST | 付かない | **付かない** | 付く | 付かない | 規格 |
| 別サイトからの fetch・XHR | 付かない | 付かない | 付く | 付かない | 規格 |
| iframe 内での読み込み | 付かない | 付かない | 付く | 付かない | 規格 |
| 同一サイトの fetch | 付く | 付く | 付く | 付く | 規格 |
| 302 で戻り GET で着地 | **付かない** | 付く | 付く | 付く | 規格 + 着地メソッドは実測 |
| 307 で戻り POST で着地 | 付かない | **付かない** | 付く | 付かない | 規格 + 着地メソッドは実測 |

読み方は二行で足りる。

- **Strict と Lax が分かれるのは「トップレベル遷移かつ安全なメソッド」の三行だけ。**
- **Lax と None が分かれるのは副リソースと POST、つまり残り全部。**

## 2. 値の選択判断表

| クッキーの中身 | 別サイトからのリクエストで必要か | 推奨値 | 併せて付けるもの |
|---|---|---|---|
| ログインセッション識別子（一般的なWebアプリ） | 不要 | `Lax` | `Secure` `HttpOnly` `Path=/` |
| ログインセッション + 外部決済・OAuth からの復帰あり | 復帰地点のみ | `Lax` + 復帰を **GET** にする | `Secure` `HttpOnly` |
| 管理コンソール・社内ツール | 不要 | `Strict` | `Secure` `HttpOnly` `__Host-` 接頭辞 |
| CSRF トークン（二重送信方式） | 不要 | `Strict` または `Lax` | `Secure`、`HttpOnly` は付けない |
| 他社ページに埋めるウィジェット・SSO iframe | 必要 | `None` | **`Secure` 必須** + `Partitioned` を検討 |
| 広告・分析用の識別子 | 必要 | `None` | `Secure`、ブロックされる前提で設計 |
| 言語・テーマなど表示設定 | 不要 | `Lax` | `Secure`、ローカルストレージも検討 |

**選択手順は三文で終わる。**

1. このクッキーが**別サイト起点のリクエスト**に付く必要があるかを一覧に書く。
2. 一覧が空なら `Lax`。トップレベル遷移でも不要なら `Strict`。
3. 一覧が空でないときだけ `None` を使い、そのときは `Secure` が**必須**。

## 3. 三つの値のまとめ

| 値 | 一行の定義 | 典型的な症状 |
|---|---|---|
| `Strict` | 同一サイトのリクエストにのみ付く | 外部リンクから入った最初の画面がログアウト状態 |
| `Lax` | 同一サイト + **トップレベル遷移の安全なメソッド**に付く | 決済・OAuth が POST で返すとセッションが消える |
| `None` | すべてのリクエストに付く | `Secure` を外すとクッキー自体が保存されない |
| （値なし） | `Lax` と同じ扱い | 「コードを触っていないのにある日壊れた」 |

## 4. Set-Cookie の書き方（パーサーで確認したこと）

- 属性の**名前と値の大文字小文字は無視**される。`samesite=lax` も `SameSite=Lax` と同じ
- 属性の**順序は無関係**。`Secure; SameSite=Lax` と `SameSite=Lax; Secure` は同一
- 等号まわりの**空白は除去**される。`SameSite = None` も解析できる
- **未知の属性はその属性だけ捨てられる。** クッキー全体は死なない
- **同じ属性が二度あれば最後が勝つ**
- **値の打ち間違いはエラーにならない。** `SameSite=Strick` は静かに既定値（Lax）になる
- `Set-Cookie` はサーバーからクライアントへ、`Cookie` はクライアントからサーバーへ。**`Cookie` ヘッダーには名前=値しか載らない。** サーバーはどの方針が適用されたかを知る術がない

## 5. ログインが切れるときの診断順序

1. 失敗したリクエストの **`Cookie` ヘッダーにセッション名があるか**をサーバーログで確認する。無ければ認証ではなくクッキーの問題
2. そのリクエストが**別サイト起点か**を確認する。同一サイトなら SameSite は犯人ではない
3. そのリクエストの**メソッド**を確認する。`POST` なら `Lax` で付かないのは正常動作
4. 外部サービスが**何番のステータスコードで戻すか**を確認する。301・302・303 は GET で着地し、**307・308 は POST を保つ**
5. 着地地点を **GET で受ける薄いエンドポイント**に変える。値を `None` に緩めるより先にこれ
6. それでも駄目なら着地ページから**同一サイトのリクエストをもう一度**投げてセッションを確認する

## 6. サイズと個数の上限（実測）

- クッキー一つの上限は**名前の長さ + 値の長さが 4096 オクテット以下**。名前も勘定に入る
- 超えると切り詰めではなく**丸ごと破棄**される。エラーも警告も出ない
- 実行環境の HTTP ヘッダー予算は **16384 バイト**で、クッキー300個（25996 バイト）で **431 応答**になった。アプリケーションのコードは動いていない
- クッキーは**一致するすべてのリクエストに毎回載る。** 1.2 KB のクッキー一つでページあたり60リクエストなら、一回あたり約 72 KB を送り出す
- ゆえに原則は一つ。**クッキーには識別子だけ、状態はサーバーに。**

## 7. 点検リスト

- [ ] セッションクッキーの `SameSite` 値を**明示**した（既定値に頼らない）
- [ ] `None` を使うクッキーに**`Secure` が付いている**
- [ ] `None` を選んだ理由を**リクエストの一覧として**書ける
- [ ] 外部決済・OAuth の**復帰地点のステータスコードとメソッド**を確認した
- [ ] 復帰地点が `POST` なら薄い **GET エンドポイント**を別に用意した
- [ ] `Domain` 属性は**必要な場合だけ**付けた（省略のほうが狭い）
- [ ] サブドメインが**同一サイトとして束ねられる**ことを設計に反映した
- [ ] ローカル検証で `localhost` と `127.0.0.1` を**混ぜていない**（別サイトである）
- [ ] スキームが違えば別サイトであることを確認した（http と https）
- [ ] クッキー一つの**名前+値が 4096 オクテット未満**である
- [ ] ドメインあたりのクッキー**個数と総バイト数**を測った
- [ ] `SameSite` の値の文字列に**打ち間違いがない**（打ち間違いは静かに既定値になる）
- [ ] セッションクッキーに `HttpOnly` を付けた
- [ ] CSRF 対策を **SameSite だけに**頼っていない

## 8. やってはいけないこと

- ❌ 症状が出た瞬間に **`None` へ変える**こと — どのリクエストで必要かを先に決める
- ❌ `None` を使いながら **`Secure` を落とす**こと — 保存の段階でクッキーが捨てられる
- ❌ **既定値に依存する**こと — 明示しないクッキーは実装の既定方針に従う
- ❌ **`localhost` だけで確認**して終えること — ローカルは越境条件を再現できない
- ❌ **ブラウザのバージョン別挙動を断定する**こと — 実装ごとに異なりうるので対象で確認する
- ❌ SameSite を **CSRF 対策のすべて**として扱うこと — 緩和策であって防御の全部ではない
- ❌ セッションの状態を**クッキーに丸ごと**入れること — サイズ上限と帯域を同時に払う
