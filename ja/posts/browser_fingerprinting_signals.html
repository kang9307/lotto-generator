クッキーを消したのに同じ人として扱われる理由

保存ではなく照合である — 画面・フォント・キャンバス・音声が端末ごとにずれる原理、そして完全には塞げない理由

2026年8月21日 IT/技術

序論: 消す対象が存在しない追跡

ブラウザのデータをすべて消した。クッキー、サイトデータ、キャッシュまで。プライベートウィンドウで開き直し、ログインもしていない。それなのに数日前にちらりと見た商品が最初の画面に並んでいる。別のサイトでは新しいアカウントを作ろうとすると、すでに登録履歴のある端末だとして追加認証を求められる。

ここでよく出る反応は「まだ何か残っているのだろう」である。だからもっと消す。そして結果は変わらない。残っているものがないから、そうなっている。あらかじめ植えられた目印が見つかったのではなく、ブラウザが質問に答える仕方が前回と同じだったために同一端末と判定されたのだ。

この記事はその判定がどんな材料で組み立てられるのかを信号単位で解きほぐす。画面・フォント・描画結果・音の計算がなぜ端末ごとに微妙にずれるのか、そのずれがどうして識別情報になるのか、そしてブラウザと標準が何を防ぎ何を防げないのかまで見る。作り方は扱わない。

1. 保存する追跡と見分ける追跡は別の作業である

クッキーは構造が単純だ。サーバーが値を一つ渡し、ブラウザがそれを保管し、次の要求に添えて送り返す。値があるから見られるし、見られるから消せる。ブラウザの設定に削除ボタンがあるのも、規制が比較的早く整ったのも、対象が目に見える物だからである。クッキー自体の挙動が気になるなら、SameSite の値によってどの要求でクッキーが落ちるかを整理した記事が別にある。

フィンガープリンティングは物を作らない。ページを普通に描画する過程ですでに外へ表れる値を集め、一本の文字列に圧縮するだけだ。その文字列はサーバーに残り、こちらの端末には残らない。自分の側に消せるものが存在しない。

W3C が仕様策定者向けに出した文書は、これを「設定値やその他の観測可能な特性を通じて訪問中の利用者・ユーザーエージェント・端末を識別または再識別する能力」と定義する。定義に再識別が入っている点が重要だ。初めて見分けることより、一度切れた結び付きを繋ぎ直す方が実際の使いどころである。

同じ文書はこの能力を四つに分ける。防御を設計するときに実際に分かれるのがこの分類だ。

  • 受動型 — 要求を送るだけでサーバーが知る類い。ヘッダーの構成と順序、ネットワーク層の特性がここに入る。ページ上でコードが動かなくても成立し、外からは収集の有無を観測する方法がない。
  • 能動型 — スクリプトやスタイルがブラウザに何かを尋ねて初めて得られるもの。ウィンドウの大きさ、利用可能なフォント、センサー値が代表例だ。コードが実行されるので原理的には検知しうる。
  • 瞬間相関 — 保存値なしに、異なるオリジンでほぼ同時に起きるハードウェア・環境イベントを突き合わせ、同じ端末だと推定する方式。
  • クッキー類似型 — どこかに状態を残して後で読み直すもの。名前がクッキーでないだけで性質は保存であり、だから削除で切れる。

利用者にとって最も厄介なのは受動型だ。切るスイッチがブラウザの中になく、どのサイトがそうしているかを知る手立てもほとんどない。逆に防御が最も効くのは能動型である。尋ねる行為があって初めて答えが出るので、答えを均したり問いを止めたりする余地が生まれる。

2. どのような信号が使われるのか

よく挙げられる材料を性質ごとにまとめるとこうなる。各項目がなぜ端末ごとに割れるのかも併記した。

信号何が見えるのかなぜ端末ごとに違うのか
画面とウィンドウ解像度、色深度、拡大率、タスクバーやドックを除いた実使用領域モニター構成と OS の拡大率設定が人によって違い、タスクバーの位置・大きさまで反映されると値の種類が大きく増える
フォント一覧どのフォントが導入され描画に使えるかOS の既定セットの上に事務用ソフト・デザインツール・ゲーム・言語パックがそれぞれ別の束を載せる。導入履歴がそのまま組み合わせになる
キャンバスの描画結果同じ文字列と図形を描いたときに出るピクセル値グラフィックス装置とドライバー、アンチエイリアスの方式、フォントラスタライザーが違えば境界ピクセルが一段二段ずれる
グラフィックス装置の情報報告されるベンダー・レンダラー文字列、対応拡張の一覧、シェーダー精度の上限GPU 世代とドライバー版がそのまま表れる。拡張一覧は順序まで組み合わせになる
音声処理の結果既知の波形を通したときに出る数値列浮動小数点の丸め位置、ベクトル化の有無、リサンプラー実装、既定のサンプリング周波数が環境ごとに割れる
端末の等級論理コア数、おおよそのメモリ容量、タッチポイント数、ポインターの種類普及機・上位機・デスクトップ・タブレットが別々の区間に落ちる。値自体は粗いが他の信号と掛け合わさるとよく分かれる
地域と言語タイムゾーン、優先言語の一覧、数値・日付の表記規則居住地と設定の癖を反映する。言語を二つ三つ並べている利用者はそれだけで希少になる
メディア対応構成再生可能なコーデックとコンテナの組み合わせ、保護コンテンツの再生能力OS とブラウザのビルド、追加導入されたコーデック、ハードウェアデコーダーの有無で割れる

一つひとつはありふれているのに、なぜ組み合わせは稀なのか

ここで誤解がよく生じる。「自分の解像度は一番ありふれた値なのに、どうして特定できるのか」という反問だ。前提は正しいが結論が違う。識別は項目一つで行うのではなく、複数の項目を掛け合わせて行う。

最もありふれた解像度を使う人が全体の四分の一だとしても、そこにタイムゾーンと言語構成が乗り、フォントの組み合わせが乗り、グラフィックス装置の文字列が乗れば、残る人数は急激に減る。情報理論ではこの「各項目がどれだけ人を分けるか」をエントロピーと呼び、実務では残った集団の大きさを匿名集合と呼ぶ。防御の目標は自分の値を消すことではなく、自分が属する匿名集合を大きく保つことである。

この見方が重要なのは、後で扱う結論に直結するからだ。値を無作為に変える道具は匿名集合を大きくしない。むしろ世界に自分ひとつだけの組み合わせを作り出しかねない。

3. なぜ端末ごとに微妙にずれるのか

表に書いた「なぜ違うのか」をもう一段下りると、ずれは三つの層でそれぞれ生じている。

  • ハードウェア層 — 演算ユニットの構成と実行順序が違えば浮動小数点結果の末尾が割れる。同じ式でもどの順に足すかで値が変わるのは浮動小数点の正常な動作であり、不具合ではない。
  • システムソフトウェア層 — グラフィックスドライバー、フォントラスタライザー、オーディオスタックはそれぞれ版があり、それぞれ最適化を行う。同じブラウザでもこの層が違えば結果が割れる。
  • 設定層 — 画面の拡大率、言語の順序、アクセシビリティ設定、配色の好みのように人が直接触った値。この層は利用者自身が特異にしている場合が多い。

では、なぜ標準はこれを放置するのか。ほとんどのウェブ仕様は結果が見た目に同じであることを求め、ビット単位で同じであることまでは求めない。求めるならハードウェアアクセラレーションを諦めるか、すべての実装に同一の描画・演算経路を強いる必要があり、それは性能と移植性をまとめて捨てる選択になる。その許された誤差がそのまま識別情報になるのがこの問題の構造的性質だ。

だからこれは「どこかの会社が悪い API を作った」ではなく「速く多様な実装を許した代償」に近い。直すには性能か機能のどちらかを差し出さねばならない。後で見るブラウザの防御がどれも折衷で終わるのはそのためである。

4. 音声信号が実際に測っているもの

音声由来の信号は名前のせいで誤解を招きやすい。マイクで何かを聴いているのではない。権限の要求も出ない。

構造はキャンバスと同じだ。既知の入力を入れ、既知の処理をさせ、出てきた数値を見る。のこぎり波のように成分の豊かな波形を作って処理経路に流すと、その先で配列が一つ出てくる。理屈の上ではどの端末でも同じはずの値だが、実際には小数点以下のどこかで割れる。割れる理由は前節の三層そのままだ — 丸め位置、ベクトル化の方式、リサンプラー実装、そしてシステムが取った既定のサンプリング周波数。

ここで重要な事実が一つある。Web Audio の仕様には実際の出力装置へ送らず計算だけを行うレンダリングモードが定義されている。仕様は通常のコンテキストを「出力先ノードがリアルタイム出力装置へ経路づけられたオーディオグラフ」と説明し、オフラインレンダリングはその装置出力なしに処理する。だからスピーカーが繋がっていなくても、システムがミュートでも、イヤホンを抜いていても値は出る。

仕様自体がこの危険を知らないわけではない。レンダー単位の大きさを選ぶ項目にはホストに関する情報を露出しフィンガープリンティングに使われうるという趣旨の注記が付いており、プライバシー・セキュリティの考慮に関する節も別に用意されている。つまりこれは隠れた脆弱性ではなく、文書に記されたまま残っている折衷である。

5. 無音の計算が装置を掴み続けうる理由

前節の二つのモードの区別が、ここで実際の副作用につながる。

計算だけで済ませるつもりならオフラインレンダリングを使えばよい。ところがリアルタイムのコンテキストを作って出力先まで接続し、最終段の音量だけを 0 にする構成も可能だ。この場合、人の耳には何も聞こえないが、ブラウザから見れば出力経路は生きたままの状態である。仕様はコンテキストが作られたら再生する音がなくなるかページが消えるまで続くと記し、資源を手放すには明示的な一時停止が必要だと説明している。

この差が目に見える場所が Bluetooth だ。二台に同時接続するマルチポイント対応ヘッドセットは、どちらが実際に音声を出しているかを根拠に切り替えを判断する。ホストがストリームを維持していれば使用中に見え、携帯側へ自然に移らない。タブのミュートボタンが効かない場合もあるが、そのボタンはおおむねページ内のメディア要素を基準に動くからである。メディア要素がなくグラフだけが生きていれば引っかからない。

2026 年 8 月、ある大手ショッピングサイトを開いたままにすると Bluetooth ヘッドセットが携帯へ移らないという観察が個人ブログに掲載された。筆者はページ上で動くスクリプトが無音のオーディオグラフを維持していることを原因として挙げ、同じスクリプトが描画結果・グラフィックス装置情報・画面の大きさ・端末等級といった値も併せて集めていると分析した。

この事例をどこまで事実と見るか。上記は第三者が観察し分析して公開した主張である。当該サイト側の説明は確認されておらず、なぜそうした構成になったのか — 意図なのか副作用なのか — は外から分かる問題ではない。この記事が事実として扱う範囲はWeb Audio の仕様上そうした構造が原理的に可能であるところまでだ。

一般化するとこうなる。画面に何も見えない機能がシステム資源を掴みうる。これはフィンガープリンティング固有の性質というよりリアルタイムメディア API 全般の性質であり、カメラやマイクと違って音声出力側には権限のダイアログも表示灯もない。利用者が気づく通路がほとんどないという点がこの件の本当の重みだ。

6. 同じ技術のもう一方 — 不正検知とボット対策

ここまで読むと、この技術が追跡のためだけに存在するように読める。そうではない。実際に最も広く使われている場所は決済とログインだ。

用途何を判断するのか利用者が得るもの問題になる地点
不正決済の検知盗難カードが普段とまったく違う端末構成で使われているか本人が知らないうちに通る決済が減る正常な利用者が端末を替えたときに誤検知で止められる
アカウント乗っ取り防止これまで見たことのない端末からのログインか新端末の通知と追加認証で乗っ取りを遅らせるブラウザを初期化した本人も新端末として扱われる
自動化・スクレイピング対策人が使うブラウザと違う痕跡があるか在庫の買い占めやチケットのマクロが減るプライバシー設定を強くした人がボットと誤認される
不正利用の抑制同じ端末がアカウントを替えながら特典を繰り返し受け取っているか一人一回の特典が実際に一人一回になる家族共用の端末が一つにまとめられる
サイト横断の広告プロファイル複数のサイトで見た人が同一人物か利用者が得るものが明確でない目的が拡張し保存期間が延びる典型的な場所

表を横に読むと見えてくるものがある。技術はすべて同じで、割れるのは目的・保存期間・共有範囲だ。同じ値一つが危険判定にも使われ、プロファイルの蓄積にも使われる。だから「フィンガープリンティングを禁じよう」という整理は実務でうまく働かない。禁止対象が技術なら決済のセキュリティも一緒に崩れ、禁止対象が目的なら外から検証する手立てがほとんどない。

利用者側が体感する逆説もここから出る。防御を強くするほどボットのように見える。値を隠したり珍しい組み合わせを作ったりすると危険度が上がり、その結果キャプチャが頻繁に出て決済がもう一度止まる。これは不当な扱いというより、危険判定モデルがもともとそう動くということだ。遮断強度を上げると何が壊れるかは遮断強度ごとの代償を整理した記事で別に扱った。

7. ブラウザが実際に行っている防御

ブラウザが使う手立てはおおむね四つで、それぞれ性質が違う。

  • 標準化 — 同じ状況では全員が同じ値を答えるようにする。W3C の指針が仕様策定者に勧める第一の方向だ。値が揃えばその項目のエントロピーは 0 に近づく。
  • エントロピーの削り取り — 精度を切り落とすか、連続値をいくつかの区間に減らすか、いっそ可否の二値に縮める。機能は保ったまま識別力だけを落とす方式だ。
  • 一覧に基づく遮断 — 既知のフィンガープリンティングスクリプトを名前で止める。確実だが一覧にないものは素通りする。
  • 値の正規化 — 特定の項目だけ無難な値に置き換えて答える。どの項目に手を入れるかがそのまま互換性の費用になる。
  • ストレージの区画化 — サイトごとに保存領域を分ける。クッキー類似型にはよく効き、保存を使わない能動型の信号には直接の効果がない。

実際の適用例を見ると折衷の形が見える。Mozilla は Firefox のフィンガープリンティング保護がグラフィックスハードウェアの詳細、端末のフォント情報、プロセッサのコア数、タッチ対応の有無、ドックやタスクバーの寸法、数値演算の微細な差などを制限すると述べ、固有に見える利用者の割合がほぼ半分に減ったと説明する。同時により積極的に遮断すれば正常なサイト機能が壊れるのは確実だという趣旨で限界も併記している。カレンダーのように正常な機能に必要なタイムゾーンなどの値は意図的に残すという説明も付いている。

ここで一つ方向をはっきりさせておく必要がある。無作為化より標準化の方がよい。W3C の文書は仕様を標準化して規格に従うブラウザ同士の匿名集合を大きくするよう勧める。毎回違う値を答える戦略はそれ自体が特異な振る舞いなので、かえって目立ち、サイトの機能も一緒に揺らぐ。

そして W3C は結論で退かない。広く配備された技術的手段だけで本気の相手のフィンガープリンティング能力を完全に取り除くことは蓋然性が低いと明記する。代わりに達成可能な目標として、表面の縮小、匿名集合の拡大、検知可能性の確保、状態の削除可能性の四つを挙げる。

8. 利用者にできることと、その限界

完全遮断が不可能だという前提の上で、実際に残る選択肢は次のとおりだ。

手段実際に行うこと代償と限界
ブラウザ内蔵の保護モード既知のスクリプトを止め、一部の項目を正規化する項目ごとに残す値があり、強いモードは一部のサイトが壊れる
プライベートウィンドウセッション終了時に保存された状態を消す信号自体は変わらない。クッキー類似型にだけ効く
トラッキング遮断の拡張機能要求の段階で既知の収集先を切る拡張の組み合わせが特異だとそれ自体が新しい信号になりうる
値の偽装ツール一部の項目に偽の値を答える匿名集合を大きくできず、辻褄の合わない組み合わせはより見分けやすい
VPN・プロキシネットワークのアドレスを替える受動型の信号の一部を隠すだけ。能動型には影響しない
ブラウザと OS を最新に保つ新たに入った緩和策をそのまま受け取る最も費用の低い手段だが効果は漸進的だ
端末と設定を無難に保つ匿名集合の大きい構成の中に留まる好みやアクセシビリティ設定を諦めねばならない場合がある

まとめると、目標を変えるのが先だ。見えなくすることは達成しうる目標ではない。達成しうるのは目立たなくなることで、その方向はおおむねあまり手を入れない側にある。道具を何重にも積む構成より、内蔵の保護を有効にして更新を先延ばしにしない方が匿名集合の観点では有利な場合が多い。

自分のブラウザがどれだけ目立つかは公開の診断ツールで直接確認できる。電子フロンティア財団が運営する Cover Your Tracks は MDN の文書でも参考資料として案内されている。ただし、どの道具も結果を保証するものではなく、特定の拡張機能やブラウザを使えば安全になると言える状況ではないという点ははっきりさせておく。

9. 制度はこの問題をどう扱っているか

免責 — この節は公開資料に基づく一般的な説明であり法的助言ではない。具体的な事案の判断は管轄と事実関係によって変わるため、必要であれば専門家の検討を受けるのが望ましい。

欧州側の議論は比較的古い。第 29 条作業部会が 2014 年 11 月に出した意見書は、値を保存せず読み取るだけでも端末機器の情報にアクセスする行為とみなしうるため、クッキーに適用される同意要件が併せてかかりうるという解釈を示した。保存していないのだから規制はないという主張を明示的に退けたのがこの文書の核心である。その後、欧州データ保護会議は e プライバシー指令第 5 条 3 項の技術的範囲を整理し直したガイドライン 2/2023 を出し、最終版は 2024 年 10 月に採択された。

他の法域は出発点が異なる。たとえば韓国の個人情報保護法第 2 条第 1 号は、個人情報を生存する個人に関する情報であって個人を識別できるもの、そしてその情報だけでは識別できなくても他の情報と容易に結合して識別できるものと定義する。容易に結合できるかは、他の情報の入手可能性や識別に要する時間・費用・技術を合理的に考慮して判断することとされている。

この構造の下では、ブラウザのフィンガープリントが個人情報にあたるかは一律に答えられる問いではない。その値だけを見れば誰なのか分からないが、同じ事業者がアカウント・決済・注文履歴を併せ持っているなら結合可能性の性質が変わる。つまり判断は値そのものではなくその値が置かれた場所から出てくる。この記事が結論を断定しない理由はそこにある。利用者視点のプライバシー議論をさらに追いたい向きには、欧州のメッセージスキャン立法をめぐる論争を整理した記事が参考になる。

10. ウェブ標準が向かっている方向

標準側の対応は「悪い API をなくそう」というより、新しい API を設計する時点でどれだけ漏れるかをあらかじめ計算しように近い。W3C の指針が仕様策定者に求める項目を絞るとこうなる。

  • 受動型の表面を増やさないこと — 検知もできず回避もできない種類なので費用が最も大きい
  • 機能に必要な範囲まで露出を狭めること
  • 無作為化ではなく標準化で匿名集合を大きくすること
  • 精度の制限・列挙型・二値化でエントロピーを減らすこと
  • サーバーが明示的に要求して初めて値が出るようにし、検知可能性を確保すること
  • 保存手段の削除時点を揃え、状態を実際に消せるようにすること
  • クッキー削除後も残る恒久的な識別子を作らないこと
  • 新機能を提案する際に増える表面を設計文書に併記すること — 仕様策定のあらゆる段階で考慮すべき問題として扱われている

残る緊張ははっきりしている。性能のためにハードウェア情報を知らせる API、アクセシビリティのために利用者設定を知らせる API、メディア品質のためにコーデック対応を知らせる API は今後も出てくる。そのたびに同じ天秤が再び載る。この問題は解決される種類ではなく、管理される種類だ。

実務者の視点からすぐ使える基準もそこから出る。新しい機能を足すとき「これは何をさらに漏らすのか」を一行でも書き残すこと、そしてリアルタイム資源は必要な間だけ掴み、終わったら明示的に手放すこと。前節の音声事例が教えるのは華々しい脆弱性ではなく、この平凡な衛生規則の方である。

確認できなかったこと

この記事で確定的に述べなかったものを一か所にまとめておく。

  • 先述のショッピングサイトの事例で、その挙動が意図なのか副作用なのか — 事業者側の説明が確認されていない
  • 収集された値がサーバーでどれだけ保存され他のサービスと結び付けられるのか — クライアントの外からは観測できない領域だ
  • 当該現象がどのブラウザ・OS・ヘッドセットの組み合わせで再現するのかの範囲 — 再現条件を整理した独立検証の資料を確認できなかった
  • 各ブラウザの防御効果を第三者が独立に測定した最新の数値 — 本文に引いたほぼ半減は当該ブラウザ提供元自身の説明である
  • 特定の法域でブラウザのフィンガープリントを個人情報と判断した確定した事例 — 確認できなかった

結論: 何を基準に見るか

整理すると三つの軸が残る。

第一に、消せる目印があるかないか。この区別がクッキーとフィンガープリンティングを分け、そのまま利用者が取れる手段の範囲を分ける。プライベートウィンドウが期待ほど効かない理由もここにある。

第二に、技術ではなく目的・保存・共有を見る。決済の乗っ取りを止める判定と広告プロファイルの蓄積は同じ材料を使う。二つを一語でくくると、どちらもまともに扱えない。

第三に、目標は消えることではなく目立たなくなることだ。標準化は無作為化に勝り、道具を積むより内蔵の保護と最新維持の方がおおむね良い。完全な遮断を約束する説明があれば、その一文で一度立ち止まる理由がある。

そして開発者側にはもう一行が付く。画面に見えない機能だからといって費用がかからないわけではない。リアルタイム資源は掴んだら手放さねばならない。
