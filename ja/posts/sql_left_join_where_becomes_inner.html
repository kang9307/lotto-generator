LEFT JOIN に WHERE を付けると INNER JOIN になる - ON と WHERE の境界

エラーも出ないまま 10 行が 4 行になるバグを SQLite で実際に再現し、どちらの句が正しいかを見分ける

2026-07-30 開発・インフラ

症状: 毎月レポートの件数が少しだけ少なかった

地域別の月次レポートがあった。売上合計は経理の数字と一致していた。ところが集計対象の顧客数だけがいつも少し少なかった。エラーログは空で、そのクエリは数か月だれも触っていない場所にあった。ある月には一つの地域が表からまるごと消えていたが、その地域は売上が 0 だったので、だれも不審に思わなかった。

原因は一行だった。LEFT JOIN で顧客全体を引いてきたあと、その下に WHERE o.status = 'paid' を足したこと。この一行がLEFT JOIN を INNER JOIN に変えてしまう。構文エラーではない。警告も出ない。実行時間はむしろ速くなる。減るのは行数だけだ。

こういうバグが数か月生き延びるのには理由がある。

  • エラーが出ない。構文も型も問題がないので、どのツールも警告しない
  • 開発データベースでは再現しない。シードデータは関係が密で欠損がほとんどない。欠損がなければ LEFT と INNER の結果は同じだ
  • 減った側が「ないデータ」だ。画面から消えたのは値が 0 か空だった行なので、見た目には差が出ない
  • 合計は合う。金額を足す指標はそのままで、件数を数える指標だけが誤るので、経理照合では引っかからない

この記事は結合の種類を説明し直さない。SQLite に表を三つ作り、同じクエリを少しずつ変えながら行数を一件ずつ数えた。以下に出てくる数字と出力はすべて、そのとき画面に表示されたそのままだ。

実行環境。以下のすべての出力はWindows 10 Pro (10.0.19045)で実際に実行した結果だ。エンジンはSQLite 3.49.1で、二つの経路から触った。一つはCPython 3.13.3の sqlite3 モジュール、もう一つはNode.js v22.16.0に内蔵された node:sqlite だ。二つの結果を 14 節で照合した。

スクリプトはすべてファイルに保存して実行した。クエリと出力をシェル引数で受け渡すと引用符が静かに変形する。表とデータはすべて架空の customers、orders、shipments だ。

この記事が扱わないこと。結合の種類そのものの概論と基本構文はSQL 入門のまとめにある。索引・ロック・N+1 のような性能の話題は運用データベース生存のまとめで扱った。ここではON と WHERE の境界という一点だけを掘る。

そこに要求が入る。「決済済みの注文だけ見たい」。もっとも自然な手つきは、クエリのいちばん下に一行足すことだ。

10 行が 4 行になった。そしてすぐ下に INNER JOIN で書き直したクエリがまったく同じ 4 行を返す。二つのクエリは結果が同じだ。つまり上のクエリで LEFT という単語は何もしていない。

消えた 6 行を分けると、性格が違う二種類になる。

  • 2 行は意図した除去だ。5 番の pending、6 番の cancelled 注文。決済済みだけ見ると言ったのだからこれは正しい
  • 4 行は意図しない除去だ。7 番から 10 番の顧客。この人たちは決済済み注文がないのではなく注文そのものがない
  • 要求は「決済済み注文だけ」であって「顧客を外せ」ではなかった。ところがクエリは顧客まで外した
  • LEFT という単語はクエリにそのまま残っている。レビューでは「LEFT JOIN だから顧客全体が出るだろう」と読まれて通される
  • 開発 DB に注文のない顧客がいなければ、二つのクエリは永遠に同じ結果を出す。テストでは捕まえられない

2. 同じ条件を ON に移すと

同じ条件を WHERE ではなく ON の後ろに AND で付けるとどうなるか見る。文字数は似ていて条件式も同じだ。

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o
       ON c.customer_id = o.customer_id
      AND o.status = 'paid'
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  1            Ada   101       paid
  2            Ben   102       paid
  3            Cara  103       paid
  4            Dan   104       paid
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 10

また 10 行だ。ただし 1 節の最初の出力とは中身が違う。5 番の pending 注文と 6 番の cancelled 注文が消えたのではなく NULL に変わった。顧客は残り、条件に合わない注文だけが落ちた。

行数と NULL の個数を並べて数えると、三つのクエリの違いが一目で見える。

--- row counts, five spellings of nearly the same query ---
  LEFT JOIN, no filter           : 10 rows
  LEFT JOIN + WHERE status=paid  :  4 rows
  LEFT JOIN + ON   status=paid   : 10 rows
  INNER JOIN + WHERE status=paid :  4 rows
  INNER JOIN + ON   status=paid  :  4 rows

--- how many NULL order_id survive in each ---
  LEFT JOIN, no filter          : 10 rows, 4 NULL order_id
  LEFT JOIN + WHERE status=paid :  4 rows, 0 NULL order_id
  LEFT JOIN + ON   status=paid  : 10 rows, 6 NULL order_id
  • WHERE 版は4 行、NULL の右側行 0 個。決済済み注文がある顧客だけが残った
  • ON 版は10 行、NULL の右側行 6 個。顧客全体が残り、条件に合う注文だけが付いた
  • NULL 行が 4 個から 6 個に増えたことが核心だ。条件に合わない注文 2 件が除去ではなくNULL 処理された
  • どちらが正しいかはクエリが答えられない。レポートが何を数えようとしていたかが決める

最後の二行が重要だ。INNER JOIN では ON と WHERE の結果が同じになる。だから「条件は ON に書くほうがよい」という助言を内部結合で覚えた人には、違いを体験する機会がない。違いは外部結合でしか現れない。

3. なぜそうなるか - 結合が先、WHERE が後

理由は順序ひとつで説明できる。結合が先に起きて中間結果を作り、WHERE はその中間結果にかかる。その中間結果をそのまま出力し、各行が WHERE を通るかどうかを横に書いてみた。

--- the intermediate result, right after the join, before WHERE ---
  cid  name  order_id  status     -> does WHERE o.status=paid keep it?
  ---  ----  --------  ---------  --------------------------------------
  1    Ada   101       paid       KEEP
  2    Ben   102       paid       KEEP
  3    Cara  103       paid       KEEP
  4    Dan   104       paid       KEEP
  5    Eve   105       pending    DROP (not paid)
  6    Finn  106       cancelled  DROP (not paid)
  7    Gus   NULL      NULL       DROP (NULL = paid is NULL, not true)
  8    Hana  NULL      NULL       DROP (NULL = paid is NULL, not true)
  9    Ivan  NULL      NULL       DROP (NULL = paid is NULL, not true)
  10   Joy   NULL      NULL       DROP (NULL = paid is NULL, not true)
  join produced 10 rows, WHERE kept 4

NULL で埋められた四行がどう死ぬかが最後の列に書かれている。結合が作り出した NULL が、次の段の WHERE に引っかかってその行を消す。LEFT JOIN がわざわざ残した行を、WHERE が捨て直す構造だ。

その判定をしているのは三値論理だ。比較式そのものを出力するとこうなる。

SELECT NULL = 'paid'            AS null_eq_paid,
       NULL <> 'paid'           AS null_ne_paid,
       NULL IS NULL             AS null_is_null,
       (NULL = 'paid') IS NULL  AS comparison_is_null;

  null_eq_paid  null_ne_paid  null_is_null  comparison_is_null
  ------------  ------------  ------------  ------------------
  NULL          NULL          1             1
  rows: 1

-- a row survives WHERE only when the predicate evaluates to TRUE (1).
-- NULL = 'paid' is neither TRUE nor FALSE. It is NULL. So the row goes away.
-- NULL <> 'paid' does not rescue it either: that is NULL too.

NULL = 'paid' は偽ではなくNULLだ。WHERE は結果が真の行だけを残すので、真でも偽でもない行は残らない。ここでよくある誤解が一つ分かれる。NULL <> 'paid' に書き換えても救われない。それも NULL だ。

二つの句がしている仕事を項目ごとに分けるとこうなる。この表がこの記事の骨だ。

項目ONWHERE
評価の時点結合を作っている途中結合が終わったあと
決めること何を組み合わせるか組み合わせた後で何を残すか
相手のない左行NULL で埋めて残す条件を満たさなければ捨てる
この例の結果行数104
内部結合での違いないない
実行計画LEFT-JOIN の表示が残る表示が消える
  • ON は組み合わせの規則だ。どの左行とどの右行を一行にまとめるかを決める
  • LEFT は救済の規則だ。相手が見つからなかった左行を NULL で埋めて残す
  • WHERE は選別の規則だ。上の二つが終わったあと、残った行のうち条件を満たすものだけを通す
  • だから WHERE に右表の列の条件を書くとLEFT がいま救済した行をまた消す。二つの規則が正面からぶつかる
  • 左表の列の条件ならぶつからない。WHERE c.region = 'north' は LEFT JOIN の性質をそのままにして左側だけを絞る

PostgreSQL の公式文書もこの順序を明記している。7.2.1.1 Joined Tables の節は、ON 句に置かれた制約は結合の前に処理され、WHERE 句に置かれた制約は結合の後に処理される。この違いは内部結合では問題にならないが、外部結合では大きく問題になると書いている。つまりこれは特定製品の癖ではなく、結合の定義そのものだ。

4. IS NULL という例外 - 同じ WHERE なのに結果が逆になる

ここで自然な反論が出る。「では WHERE o.order_id IS NULL も全部飛ぶのでは?」実際には逆で、注文がない顧客だけが残る。三つを並べて実行した。

-- 1. customers with no order at all
SELECT c.customer_id, c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id
  -----------  ----  --------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

-- 2. ON filter + IS NULL = customers with no PAID order
SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'
WHERE o.order_id IS NULL
ORDER BY c.customer_id;

  customer_id  name  order_id  status
  -----------  ----  --------  ------
  5            Eve   NULL      NULL
  6            Finn  NULL      NULL
  7            Gus   NULL      NULL
  8            Hana  NULL      NULL
  9            Ivan  NULL      NULL
  10           Joy   NULL      NULL
  rows: 6

-- 3. orders.status is declared NOT NULL, yet IS NULL matches 4 rows
SELECT c.customer_id, c.name, o.status
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status IS NULL
ORDER BY c.customer_id;

  customer_id  name  status
  -----------  ----  ------
  7            Gus   NULL
  8            Hana  NULL
  9            Ivan  NULL
  10           Joy   NULL
  rows: 4

一つ目が4 行だ。原理は前とまったく同じ。IS NULL はNULL に真を返す唯一の種類の条件だ。だから結合が作った NULL 行が WHERE を通り、逆に一致した行が落ちる。これがアンチジョインと呼ばれる定型句だ。

二つ目のほうがずっと役に立つ。条件を ON に、IS NULL を WHERE に置くと、決済済み注文が一件もない顧客 6 人が出る。前の 4 人とは違う集合だ。5 番と 6 番は注文はあるが決済済みがないので、ここに入る。

三つ目の出力は別に覚えておく価値がある。

  • IS NULL はNULL に真を返す条件だ。ほかの比較演算子はすべて NULL を返す
  • だからこれは結合が作った NULL 行を選び出すのに使う。定型句であって例外ではない
  • ON に条件を置いて WHERE ... IS NULL を付けると「その条件に合う相手がいない左行」が出る。この例では 6 行
  • ON に条件を置かなければ「相手がまったくいない左行」が出る。4 行。二つの質問は違う
  • NOT NULL と宣言された列に IS NULL をかけても引っかかる。その NULL は表に保存された値ではなく、結合が作り出したものだ

5. 集計と出会うと - COUNT(o.order_id) と COUNT(*)

集計が付くと同じ罠が別の顔で現れる。結合結果に GROUP BY をかけ、二種類の COUNT を並べて出した。

SELECT c.customer_id, c.name,
       COUNT(*)          AS count_star,
       COUNT(o.order_id) AS count_order_id
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  count_star  count_order_id
  -----------  ----  ----------  --------------
  1            Ada   1           1
  2            Ben   1           1
  3            Cara  1           1
  4            Dan   1           1
  5            Eve   1           1
  6            Finn  1           1
  7            Gus   1           0
  8            Hana  1           0
  9            Ivan  1           0
  10           Joy   1           0
  rows: 10

-- grand totals over exactly the same join
  count_star  count_order_id  count_status
  ----------  --------------  ------------
  10          6               6
  rows: 1

7 番から 10 番の顧客で二つの値が分かれる。COUNT(*) は 1、COUNT(o.order_id) は 0 だ。注文が一件もない顧客の注文件数が1 と報告されることがこの節の事故だ。理由は単純で、NULL で埋められた行もれっきとした一行であり、COUNT(*) は行を数える。

合計行でも同じ差が出る。全体の COUNT(*) は 10、COUNT(o.order_id) は 6 だ。10 は顧客数で、6 は注文数だ。どちらも正しい数字だが、レポートの見出しが「注文件数」なら 10 は誤りだ。

集計関数ごとに、一致がないグループで何が出るかを整理した。

式一致がないグループの値なぜ実務での結果
COUNT(*)1NULL で埋められた行も一行だ注文 0 件が 1 件と報告される
COUNT(o.order_id)0NULL の引数は数えないたいてい欲しい値
SUM(o.amount)NULL足す値が一つもない0 ではない。上位の計算に広がる
COALESCE(SUM(...), 0)0集計結果を置き換える推奨される位置
AVG(o.amount)NULL分母が 0 だ上位の平均の分母が減って膨らむ
  • COUNT(*) は行を数える。NULL で埋められた行も一行なので、一致がないグループでは 1 になる
  • COUNT(o.order_id) はNULL でない値を数える。一致がなければ 0 で、たいてい欲しいのはこちらだ
  • どの列を数えるかも重要だ。COUNT(o.status) も 6 になった。右表のどの NOT NULL 列でもよい
  • COUNT(DISTINCT c.customer_id) はまた別の値だ。12 節のレポートでこの関数が地域ごとに違う答えを出した

6. SUM が 0 ではなく NULL になること

金額のほうは症状がもっと静かだ。同じ列を四通りで合計してみた。

SELECT c.customer_id, c.name,
       SUM(o.amount)              AS sum_raw,
       COALESCE(SUM(o.amount), 0) AS coalesce_outside,
       SUM(COALESCE(o.amount, 0)) AS coalesce_inside,
       TOTAL(o.amount)            AS sqlite_total
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

  customer_id  name  sum_raw  coalesce_outside  coalesce_inside  sqlite_total
  -----------  ----  -------  ----------------  ---------------  ------------
  1            Ada   120      120               120              120
  2            Ben   80       80                80               80
  3            Cara  45       45                45               45
  4            Dan   300      300               300              300
  5            Eve   60       60                60               60
  6            Finn  210      210               210              210
  7            Gus   NULL     0                 0                0
  8            Hana  NULL     0                 0                0
  9            Ivan  NULL     0                 0                0
  10           Joy   NULL     0                 0                0
  rows: 10

-- what those NULLs do one layer further out
  from SUM(o.amount)             : sum=815  avg=135.83  count=6
  from COALESCE(SUM(o.amount),0) : sum=815  avg= 81.50  count=10
-- the totals agree, the averages do not: AVG skipped the four NULL groups.

一致がなければ SUM は 0 ではなく NULL だ。足す値が一つもないからだ。この NULL はその場では害がなさそうに見える。問題は一段外に出るときに起きる。

同じデータなのに平均が 135.83 と 81.50 に分かれた。合計はどちらも 815 で同じだ。AVG が NULL のグループを数えないので、分母が 6 と 10 に変わった。「顧客あたり平均購入額」のような指標が、まさにこの地点で静かに膨らむ。

COALESCE をどこに掛けるかも実際に確認した。

  • COALESCE(SUM(o.amount), 0) - 集計結果に掛ける。グループ全体が空のときに 0 を作る。たいていはこれが正しい位置だ
  • SUM(COALESCE(o.amount, 0)) - 集計の前に掛ける。このデータでは同じ答えだが意味が違う。NULL の金額が実際に保存されている場合に分かれる
  • SQLite には TOTAL() があり、空のグループにも 0 を返す。ほかのエンジンにはない関数なので移植性のあるクエリには使わない
  • NULL をそのまま外に出すと上位の集計が静かに誤る。合計は合っていて平均だけが誤る組み合わせがとくに危ない
  • レポートの列ごとに「この値は NULL になりうるか」を一度問うだけで大半は止まる

7. 三つの結合をつなぐと - 中間の条件が後ろまで殺す

表が三つになると罠も伝播する。顧客から注文へ、注文から配送へと二回 LEFT JOIN する。

SELECT c.customer_id, c.name, o.order_id, o.status, s.carrier
FROM customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id
LEFT JOIN shipments s ON o.order_id    = s.order_id
ORDER BY c.customer_id;

中間の表に条件を置くと4 行だ。ただしこちらには別の損失が一つ加わる。6 番の顧客のキャンセル注文には配送記録があったのに、注文が絞られたことでその配送記録まで結果から消えた。条件をかけていない表のデータが失われたのだ。

  • 条件は自分の層にだけ置く。後ろの表の条件を WHERE に置くと、手前の LEFT JOIN まで一緒に無効化される
  • 連鎖が長くなれば被害も大きくなる。三表結合で最後の表の条件一つが 10 行を 3 行にした
  • 条件をかけていない表のデータまで消える。中間の表を絞ると、その表にぶら下がる後ろの行も一緒に消える
  • ON に移せば層ごとに独立する。4 番の顧客のように前の層は通り、後の層でだけ NULLになる行が出る
  • 連鎖結合ではプローブを層ごとに回す。どの層で行が減ったかを層別の COUNT で絞るのが速い

8. RIGHT JOIN と FULL OUTER JOIN - 向きだけ変えた同じ罠

向きを変えても同じことが起きるか確認した。SQLite は RIGHT JOIN と FULL OUTER JOIN を 3.39.0(2022 年 6 月 25 日リリース)で追加しており、この環境は 3.49.1 なのでどちらも動く。

顧客表に存在しない顧客番号を持つ注文を一件入れて、向きごとの違いをはっきりさせた。

--- SQLite 3.49.1, same data ---
  RIGHT JOIN, no filter        : 10 rows
  RIGHT JOIN + WHERE           :  4 rows
  FULL OUTER JOIN, no filter   : 10 rows
  FULL OUTER JOIN + WHERE      :  4 rows

--- now insert one orphan order (customer_id 99 does not exist) ---
INSERT INTO orders VALUES (107, 99, 'paid', 500.0, '2026-07-25');

  LEFT JOIN             : 10 rows   <- orphan invisible
  RIGHT JOIN            :  7 rows   <- 6 orders + orphan, customers 7-10 gone
  FULL OUTER JOIN       : 11 rows   <- 10 customers + orphan
  FULL OUTER + WHERE o  :  5 rows   <- WHERE on the right table
  FULL OUTER + WHERE c  :  3 rows   <- WHERE on the LEFT table also collapses it

FULL OUTER JOIN ではどちらの側の条件でも崩壊が起きる。右表の条件を WHERE に置くと 11 行が 5 行、左表の条件を置くと 11 行が 3 行になった。両側を保存する結合なので両側とも脆い。

向きごとに整理するとこうなる。

結合保存される側右表の条件を WHERE に置くとこの環境での対応
LEFT [OUTER] JOIN左内部結合になる (10 → 4)全バージョン
RIGHT [OUTER] JOIN右内部結合になる (10 → 4)3.39.0(2022-06-25)以降
FULL OUTER JOIN両側どちらの条件でも崩壊 (11 → 5, 11 → 3)3.39.0 以降
INNER JOINなし何も起きない全バージョン
  • RIGHT JOIN は向きだけが逆だ。右表を保存し、左表の列の条件を WHERE に置くと同じ崩壊が起きる
  • FULL OUTER JOIN は両側とも脆い。どちらの表の列でも WHERE に来ればその側の保存が壊れる
  • 孤児の行を一件入れると向きごとの違いがはっきりする。LEFT は 10 行で孤児が見えず、RIGHT は 7 行で顧客 4 人が見えない
  • SQLite でこの二つの結合は3.39.0 以降でしか使えない。古いビルドが混ざる環境ならまずバージョンを確認する

9. 実行計画が教えてくれること

オプティマイザが実際にこの変換をしているのかを EXPLAIN QUERY PLAN で確認した。

EXPLAIN QUERY PLAN <query>;

-- 1. LEFT JOIN, no filter
   SCAN c
   BLOOM FILTER ON o (customer_id=?)
   SEARCH o USING AUTOMATIC COVERING INDEX (customer_id=?) LEFT-JOIN

-- 2. LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- 3. LEFT JOIN + ON ... AND o.status = 'paid'
   SCAN c
   BLOOM FILTER ON o (status=? AND customer_id=?)
   SEARCH o USING AUTOMATIC PARTIAL COVERING INDEX (status=? AND customer_id=?) LEFT-JOIN

-- 4. INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

2 番と 4 番の計画が完全に同じだ。LEFT JOIN に WHERE を付けたものと、最初から INNER JOIN で書いたものが文字単位で同一の実行計画を作った。そして決定的に、1 番と 3 番にあった LEFT-JOIN の表示が 2 番では消えている。

駆動順も逆になった。1 番と 3 番は SCAN c で顧客から走るが、2 番と 4 番は SCAN o で注文から走る。顧客全体を保存するという制約がなくなったので、小さい表から回るほうが有利だと判断したのだ。索引を作っても結論は同じだった。

CREATE INDEX idx_orders_customer ON orders(customer_id);

-- LEFT JOIN, no filter
   SCAN c
   SEARCH o USING COVERING INDEX idx_orders_customer (customer_id=?) LEFT-JOIN

-- LEFT JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

-- INNER JOIN + WHERE o.status = 'paid'
   SCAN o
   SEARCH c USING INTEGER PRIMARY KEY (rowid=?)

実務でこの出力を使う方法は単純だ。

  • LEFT-JOIN の表示が計画に残っているかを見る。消えていれば、オプティマイザはすでに内部結合として扱っている
  • 駆動表が変わったかを見る。左表から走っていた計画が右表から走るように反転したら、保存の制約が消えた合図だ
  • INNER JOIN に書き直したクエリの計画と比べる。二つの計画が同じなら、二つのクエリは同じクエリだ
  • この確認はデータに触らないので本番データベースでも安全に回せる

10. OUTER キーワード、USING、そして定数条件

周辺の構文も一緒に確認した。まず OUTER キーワードは何を変えるのか。

--- does the OUTER keyword change anything ---
  LEFT JOIN       rows: 10
  LEFT OUTER JOIN rows: 10
  result sets identical : True
  query plans identical : True

--- the inner-join spellings, same data ---
  JOIN        :  6 rows
  INNER JOIN  :  6 rows
  CROSS JOIN  :  6 rows   (SQLite accepts ON after CROSS JOIN)
  comma join  :  6 rows   (FROM customers c, orders o WHERE c.customer_id=o.customer_id)

何も変えない。結果集合が同じで、実行計画の文字列まで同じだった。OUTER は省略可能で、LEFT JOIN はすでに外部結合だ。逆に JOIN、INNER JOIN、カンマ結合はすべて 6 行で同じだった。

USING 句も同じ罠をそのまま持っている。

SELECT customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN orders o USING (customer_id)
ORDER BY customer_id;
  rows: 10

-- append the filter to WHERE and the same collapse happens
LEFT JOIN orders o USING (customer_id) WHERE o.status = 'paid'
  rows: 4

-- there is no place to put an extra predicate inside USING
LEFT JOIN orders o USING (customer_id) AND o.status = 'paid'
  ERROR: near "AND": syntax error

-- which side does the merged column come from on an unmatched row?
SELECT customer_id, c.customer_id AS from_left, o.customer_id AS from_right
FROM customers c LEFT JOIN orders o USING (customer_id)
WHERE o.order_id IS NULL;

  customer_id  from_left  from_right
  -----------  ---------  ----------
  7            7          NULL
  8            8          NULL
  9            9          NULL
  10           10         NULL
  rows: 4

二つ目につく。一つは WHERE を付けたときやはり 4 行に減ったこと。もう一つはUSING には追加条件を受け取る文法上の場所がないことだ。AND を付けると構文エラーになる。つまりUSING を書いた瞬間に「条件を ON に移す」という選択肢が消える。条件を生かすには ON に書き換えるか、サブクエリに出すしかない。

二つの句の役割の違いをもっとも鮮明に見せるのは定数条件だ。

--- constant predicates, to isolate what each clause does ---
  ON c.customer_id=o.customer_id AND 1=1  : 10 rows
  ON c.customer_id=o.customer_id AND 1=0  : 10 rows   <- still 10
  ON 1=1 (no join key at all)             : 60 rows   <- 10 x 6 cartesian
  WHERE 1=1                               : 10 rows
  WHERE 1=0                               :  0 rows   <- everything gone
  WHERE c.region='north' (LEFT table!)    :  3 rows

--- ON ... AND 1=0 keeps every left row and nulls the right side ---
  customer_id  name  order_id
  -----------  ----  --------
  1            Ada   NULL
  2            Ben   NULL
  3            Cara  NULL
  ...
  10           Joy   NULL
  rows: 10

ON ... AND 1=0 は10 行をそのまま保つ。組み合わせが一つも成立しないのに、左の行は全部残って右だけが NULL になる。一方 WHERE 1=0 は0 行だ。同じ偽の条件が、一方では「組むな」と読まれ、他方では「全部捨てろ」と読まれる。

  • OUTER はあってもなくても同じだ。結果集合と実行計画がどちらも同一だった
  • JOIN、INNER JOIN、カンマ結合はすべて同じ 6 行。SQLite では CROSS JOIN にも ON を付けられ、結果は同じだった
  • USING は追加条件を受け取る文法上の場所がない。条件を ON に移す逃げ道が閉じるので、条件が付く結合には最初から ON を使うほうがよい
  • USING で統合された列は、一致がない行では左側の値を返した。だからその列で欠損判定はできない。欠損判定には右表の別の列を使う
  • ON ... AND 1=0 と WHERE 1=0 の差が二つの句の役割の違いをそのまま見せる。10 行と 0 行だ

11. サブクエリと CTE で先に絞る

条件が長くなると ON 句は読みにくくなる。代替は条件をサブクエリや CTE の中に入れ、その結果を結合することだ。

SELECT c.customer_id, c.name, o.order_id, o.status
FROM customers c
LEFT JOIN (SELECT * FROM orders WHERE status = 'paid') o
       ON c.customer_id = o.customer_id
ORDER BY c.customer_id;
  rows: 10

--- three spellings that must agree, and do ---
  ON       : 10 rows
  subquery : 10 rows
  CTE      : 10 rows
  all three identical : True

--- and four that are not the same thing ---
  WHERE o.status='paid'                        :  4 rows
  WHERE o.status='paid' OR o.order_id IS NULL  :  8 rows
  EXISTS (paid order)                          :  4 rows
  NOT EXISTS (paid order)                      :  6 rows

三つの書き方がすべて 10 行で、値まで同じだった。スクリプトで結果集合を直接比べて同一と判定した。条件が複数あるときや、サブクエリの中で集計まで必要なときは、この形が読みやすい。

下の四行は互いに別の質問だという点をはっきりさせておく。

  • ON、サブクエリ、CTE の三つの書き方の結果が同じだ。読みやすいほうを選べばよい
  • 条件が三つ以上あるとき、あるいはサブクエリの中で集計まで必要なときはCTE が圧倒的に読みやすい
  • WHERE ... OR ... IS NULL はON に移したのと同じではない。8 行が出た。条件に合わない相手を持つ行が復活する
  • 「あるかどうかだけ分かればよい」なら EXISTS のほうが正確だ。結合は行を増やしうるが EXISTS は増やさない

12. 日付範囲の条件でとくに多い理由

このバグがとくに多く出る場所がある。日付範囲の条件だ。月次や週次のレポートはほぼ例外なく期間条件を持ち、その条件が付く表はほぼ必ず右側の表だ。

--- a date range is the most common way to trip this ---
  no filter                                     : 10 rows
  WHERE o.ordered_at >= '2026-07-01'            :  5 rows
  ON ... AND o.ordered_at >= '2026-07-01'       : 10 rows
  WHERE o.ordered_at BETWEEN Jul01 AND Jul31    :  5 rows
  WHERE (o.ordered_at >= Jul01 OR o.id IS NULL) :  9 rows

-- the WHERE version drops two different populations at once:
--   the 4 customers with no order, and the 1 customer whose only order is from June.
-- the OR ... IS NULL version brings back the 4 but still hides the June customer.

WHERE 版は二種類の行をまとめて捨てる。注文がまったくない顧客 4 人と、唯一の注文が 6 月で範囲外になった顧客 1 人だ。前の 4 人はまだ気づく余地があるが、後の 1 人は「今月活動がなかった顧客」なので発見がはるかに難しい。

よく使われる回避策の OR ... IS NULL も半分しか効かない。9 行が出た。注文がない 4 人は戻ったが、6 月注文の顧客はまだ抜けている。条件を ON に移すのと同じではない。

実際のレポートの形にして二つの版を並べて実行した。冒頭で述べた症状がここでそのまま再現する。

-- the report, WHERE version
SELECT c.region,
       COUNT(DISTINCT c.customer_id) AS customers_in_report,
       COALESCE(SUM(o.amount), 0)    AS revenue
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.region ORDER BY c.region;

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    1                    300
  north   2                    165
  south   1                    80
  rows: 3

-- the report, ON version
LEFT JOIN orders o ON c.customer_id = o.customer_id AND o.status = 'paid'

  region  customers_in_report  revenue
  ------  -------------------  -------
  east    2                    300
  north   3                    165
  south   3                    80
  west    2                    0
  rows: 4

-- revenue per region is identical. the customer counts are not,
-- and the whole 'west' region is missing from the first report.

地域別の売上は二つの版で完全に同じだ。だから経理照合を通る。違うのは顧客数だ。north が 2 と 3、south が 1 と 3 に分かれる。そしてwest 地域は WHERE 版では表にまったくない。売上 0 の地域が消えたことを、レポートを見る人が気づくのは難しい。

  • 期間条件はほぼ必ず右側の表にある。顧客に期間はなく、注文にはある。だからレポートのクエリは構造的にこの罠にさらされる
  • なくなる側が二種類だ。相手がまったくない行と、相手はいるが期間の外にある行。後者のほうがはるかに見つけにくい
  • OR ... IS NULL は部分的な回避だ。相手がない行は戻すが、期間外の行はやはり隠す
  • 金額の合計は二つの版で同じだ。だから経理照合を通る。分かれるのは件数の指標だけだ
  • 売上 0 の分類が表からまるごと抜ける。この例では west 地域が消えた。ない行に気づく人はまれだ

13. 診断法 - すでに動いているクエリから見つける

ここから逆方向だ。すでに動いているクエリからこのバグを見つける。三段階に分けた。

--- probe 1. how many rows does the WHERE remove? ---
  driving table rows       : 10
  after LEFT JOIN          : 10
  after WHERE              : 4
  lost by the WHERE clause : 6  (60%)

--- probe 2. unmatched ratio, straight from the join ---
SELECT COUNT(*)                                           AS joined_rows,
       SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END) AS unmatched_rows,
       ROUND(100.0 * SUM(CASE WHEN o.order_id IS NULL THEN 1 ELSE 0 END)
             / COUNT(*), 1)                               AS unmatched_pct
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id;

  joined_rows  unmatched_rows  unmatched_pct
  -----------  --------------  -------------
  10           4               40
  rows: 1

--- probe 3. the one that settles it ---
SELECT (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id)                        AS rows_join_only,
       (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_with_where,
       (SELECT COUNT(*) FROM customers c JOIN      orders o
          ON c.customer_id=o.customer_id WHERE o.status='paid')  AS rows_if_inner;

  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              4                4
  rows: 1

-- rows_with_where equals rows_if_inner -> the word LEFT is doing nothing.

三つ目のプローブが判定を終わらせる。rows_with_where と rows_if_inner が同じなら、そのクエリの LEFT は飾りだ。同じ値が出たということは、左の表を保存しようという意図が実行されていないという意味だ。

二つ目のプローブの unmatched_pct も一緒に見る。この例では 40 パーセントだった。開発データベースでこの値が 0 なら、そこではバグは絶対に再現しない。欠損の少ないデータで検証したから通ったクエリが、欠損の多い本番データでだけ誤った値を出す。

連鎖結合にも同じプローブがそのまま通る。そしてコードベース全体を洗うときは二段階で絞る。

--- same probe on the three-table chain ---
  rows_join_only  rows_with_where  rows_if_inner
  --------------  ---------------  -------------
  10              3                3
  rows: 1

--- grep patterns for a code review sweep ---

grep -rn -A 10 -i 'left join' --include='*.sql' --include='*.py' .

# LEFT JOIN and WHERE in the same statement, single-line queries
grep -rn -iE 'left[[:space:]]+(outer[[:space:]]+)?join.*where' .

--- what to look at once you have the hits ---
# 1. does the WHERE mention an alias that is introduced by a LEFT JOIN?
# 2. if yes, is the predicate an IS NULL check? then it is intentional.
# 3. anything else -> run probe 3 above and compare the two numbers.

手順にするとこうなる。

確認すること方法判定
WHERE が右側の別名に触れているかクエリの本文を読む触れていれば候補

  • 第 2 段。触れているなら、その条件が IS NULL かを見る。IS NULL なら意図したアンチジョインの可能性が高い
  • 第 3 段。それ以外ならプローブ 3 を回して rows_with_where と rows_if_inner を比べる。同じなら確定だ
  • 欠損の比率も一緒に記録する。0 パーセントの環境では再現しないので、検証は本番に近いデータでやる
  • 直すときは二つのうち一つを選ぶことだ。条件を ON に移すか、LEFT を消して INNER と明記するか。曖昧に残すのが最悪だ

  • SQLite 固有の機能はそう表示した。TOTAL() 関数、CROSS JOIN に ON を付けられる点、EXPLAIN QUERY PLAN の出力形式がそれだ
  • 実行計画の文字列はエンジンごとにまったく違う。9 節の判断法(保存の表示が消えたか、駆動表が反転したか)は移せるが、出力の形はそのまま移らない

15. 判断表 - 意図から始める

結論は「条件は ON に書け」ではない。二つの句は仕事が違い、だからそれぞれ正しい置き場所がある。決めるのは構文ではなく意図だ。言いたいことをまず文にして、その文に合う句を選べばよい。

表を使うときの基準を一行に縮めるとこうなる。

  • 「ないものも 0 として見たい」なら ON だ。結果の行数が左表の行数と同じになるはずだ
  • 「あるものだけ見る」なら WHERE だ。ただしそのときは LEFT を消して INNER JOIN と書く。意図がコードに残る
  • 「条件に合う相手がいない側だけ見る」なら ON + WHERE ... IS NULL だ。二つの句を一緒に使う、唯一よくある場合だ
  • 左表を絞る条件は WHERE にそのまま置く。LEFT JOIN の性質と衝突しない
  • どちらか分からなければ二つの版を回して行数を比べる。数字を見れば何を訊いたのかが分かる

16. チェックリストと、やらないこと

レビューと自己点検に使う一覧だ。

  • レポートのクエリごとにWHERE 句が触れる別名がどの結合から来たかを確認した
  • LEFT JOIN を使ったクエリで結果の行数が左表の行数と同じかを一度数えた
  • 欠損比率が 0 でないデータで検証した。シードデータだけで通していない
  • COUNT(*) を件数の指標にそのまま使わなかった。右表の列を数えた
  • SUM の結果にCOALESCE を掛けるかを一度判断した。上位の集計に NULL を流さなかった
  • 条件を WHERE に置くと決めたならLEFT を消して INNER と書いた。次の人が誤解しないようにした

逆に、やらないこと。

  • LEFT JOIN の下に右表の条件を WHERE で足すこと - 意図があるなら INNER と書く
  • 「LEFT JOIN だから左は全部出る」と読んで通すこと - 下の WHERE を先に見る
  • 欠損のないシードデータでレポートのクエリを検証すること - その環境では再現しない
  • 行数を数えずに「減ったようだ」と報告すること - 数字を二つ並べて書く
  • OR ... IS NULL を ON と同じものとして扱うこと - 8 行と 10 行は違う結果だ
  • USING で書いた結合に条件を付けようとすること - 文法上の場所がない。ON に書き換える

# LEFT JOIN + WHERE の罠 — 判断表・診断 SQL・再現データ

> 出典: braindetox.kr — LEFT JOIN に WHERE を付けると INNER JOIN になる
> 検証環境: Windows 10 / SQLite 3.49.1 (CPython 3.13.3 sqlite3, Node.js v22.16.0 node:sqlite)
> このファイルをそのまま AI に貼って「この基準でうちのレポートのクエリを点検して」と書けば使えます。
> ⚠ このバグはエラーを出しません。行数だけが減り、欠損の少ない開発 DB では再現しません。

## 0. 一文でいうと

**ON は「何を組み合わせるか」、WHERE は「組み合わせた後で何を残すか」。**
結合が先に起きて NULL の行を作り、WHERE がその NULL を検査して行を消す。だから右表の列の条件を WHERE に置くと、LEFT JOIN が INNER JOIN になる。

## 1. 判断表 — 意図から始める

| 言いたいこと | どの句に書くか | 例の行数 | 確認方法 |
|---|---|---|---|
| 条件に合うものだけ見る | `WHERE` + `INNER JOIN` と明記 | 4 | 結果に NULL の右側行がないこと |
| ないものも 0 として見たい | `ON ... AND` | 10 | 結果の行数 = 左表の行数 |
| 条件に合う相手がいない側だけ | `ON` + `WHERE ... IS NULL` | 6 | 右側の列がすべて NULL |
| 相手がまったくない側だけ | `WHERE ... IS NULL` | 4 | `NOT EXISTS` と行数が同じ |
| 左表を絞る | `WHERE`(左表の列) | 3 | NULL の右側行がそのまま残る |
| 条件が長くて読みにくい | サブクエリまたは CTE に分ける | 10 | ON 版と行数・値が一致 |

## 2. 二つの句がしている仕事

| 項目 | `ON` | `WHERE` |
|---|---|---|
| 評価の時点 | 結合を作っている途中 | 結合が終わったあと |
| 決めること | 何を組み合わせるか | 組み合わせた後で何を残すか |
| 相手のない左行 | NULL で埋めて残す | 条件を満たさなければ捨てる |
| 内部結合での違い | ない | ない |
| 実行計画 | `LEFT-JOIN` の表示が残る | 表示が消える |

## 5. 診断 SQL — すでに動いているクエリの判定

```sql
-- プローブ 1. 結合直後 / WHERE 適用後 / INNER に書き換えたときの三つの行数を一度に
SELECT
  (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
     ON c.customer_id = o.customer_id)                          AS rows_join_only,
  (SELECT COUNT(*) FROM customers c LEFT JOIN orders o
     ON c.customer_id = o.customer_id WHERE o.status = 'paid')  AS rows_with_where,
  (SELECT COUNT(*) FROM customers c JOIN      orders o
     ON c.customer_id = o.customer_id WHERE o.status = 'paid')  AS rows_if_inner;
-- 検証結果: 10 / 4 / 4
```

## 6. 集計チートシート — 一致がないグループの値

| 式 | 値 | 実務での結果 |
|---|---|---|
| `COUNT(*)` | **1** | 注文 0 件が 1 件と報告される |
| `COUNT(o.order_id)` | **0** | たいてい欲しい値 |
| `SUM(o.amount)` | **NULL** | 0 ではない。上位の計算に広がる |
| `COALESCE(SUM(o.amount), 0)` | **0** | 推奨される位置 |
| `AVG(o.amount)` | **NULL** | 上位の平均の分母が減って膨らむ |

検証された事例: 同じデータで合計はどちらも 815 で同じ、平均だけが 135.83 と 81.50 に分かれた。**合計の照合だけではこの誤りを捕まえられない。**

## 9. やらないこと

- ❌ LEFT JOIN の下に右表の条件を WHERE で足すこと — 意図があるなら INNER と書く
- ❌ 「LEFT JOIN だから左は全部出る」と読んで通すこと — 下の WHERE を先に見る
- ❌ 欠損のないシードデータでレポートのクエリを検証すること — その環境では再現しない
- ❌ 行数を数えずに「減ったようだ」と報告すること — 数字を二つ並べて書く
- ❌ `OR ... IS NULL` を ON と同じものとして扱うこと — 検証では 8 行と 10 行で違った
- ❌ 合計だけを照合して検証を終えること — このバグは件数の指標にしか現れない
