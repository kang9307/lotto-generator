AIが書いたNext.js + Supabase、あとで壊れる場所

境界から漏れる鍵、有効なのに開いたままのRLS、料金が跳ねる区間までをデプロイ前に確認する順序

2026年8月3日 開発/インフラ

序論: 動くコードと安全なコードは別の状態だ

画面はすべて出る。ログインもできるし投稿も保存されるし、デプロイも通った。ここまでにかかった時間は、少し前の基準では説明がつかないほど短い。Next.jsとSupabaseの組み合わせが、AIで何かを速く作るときの事実上の既定値になった理由がそれだ。認証、データベース、ストレージ、リアルタイム、デプロイまでが一つの束で届き、生成モデルはこの組み合わせのコードを最も多く見ている。

問題はこのスタックが悪いということではない。実際に良い選択肢だ。問題は便利な抽象化が隠している動作原理がいくつかあり、そのいくつかがよりによって事故の起きる場所だという点にある。鍵がどこまで出ていくのか。ポリシーが有効という表示と、実際に遮断されている状態がどう違うのか。サーバーレンダリングがセッションをどう扱うのか。接続が何本まで増えるのか。こうしたことは画面がきれいに出ることとまったく関係がないので、デプロイ直後には表に出ない。表に出るのは利用者が増えたとき、あるいは誰かがブラウザの開発者ツールを開いたときだ。

以下はその場所を一つずつ押さえたものだ。項目ごとに生成ツールがよく出す形、それがなぜ後で壊れるのか、自分のプロジェクトでどう確認し何に変えるのかを付けた。攻撃手法ではなく自分のプロジェクトを点検する方向でのみ書いている。スタックの選定自体をどの基準で行うかは退屈な技術を選べ、再考で別に扱った。

1. 境界が一つ変わるとバンドル全体が変わる

AIが出す形

相互作用が必要なコンポーネントに'use client'を付け、そのファイルでデータアクセス用のユーティリティをそのままimportする。ユーティリティの中にはプロジェクトURLと鍵を読むコードが入っている。問題なく動くのでそのまま残る。

なぜ後で壊れるのか

'use client'はファイル一つの性格を変える印ではない。Next.js公式ドキュメントはこのディレクティブを、サーバーとクライアントのモジュールグラフの間に境界を宣言するものだと説明している。ファイルにこの印が付いた瞬間、そのファイルがimportしたものと直接レンダリングするコンポーネントがすべてクライアントバンドルに含まれる。コンポーネント一つをクライアントに回したのではなく、その下にぶら下がるモジュールグラフ全体をクライアントに移したことになる。

ここで救ってくれる安全装置が一つある。環境変数の規則だ。ドキュメントはNEXT_PUBLIC_接頭辞の付いた変数だけがクライアントバンドルに含まれ、接頭辞のない変数は空文字列に置換されると記している。だからサーバー専用のユーティリティが誤ってクライアント側に引きずられても、シークレット鍵の値そのものがバンドルに焼き込まれることはない。代わりにその関数は静かに動作しなくなる。

本当の事故はこの規則を人間が迂回したときに起きる。ローカルでundefinedが出たので名前の前にNEXT_PUBLIC_を付けて解決した、という場合が代表的だ。この一度の修正でシークレット鍵がビルド成果物に文字列として焼き込まれる。エラーメッセージをそのままAIに渡すと、この修正が提案されることは珍しくない。

あまり知られていない罠がもう二つある。

  • 公開変数はビルド時点で凍結される。 ドキュメントは、ビルドが終わった後はアプリがこの環境変数の変更に反応しないと記している。一つのイメージを複数の環境に上げる構成なら、どの環境もビルド時の値をそのまま使う。鍵をローテーションしても再ビルドまでは古い値が出ていく。
  • 動的な参照は置換されない。 process.env[varName]のように変数で鍵名を作ったり、const env = process.envで受けてからアクセスするとインライン化の対象外になる。設定をきれいに整理するという理由でこうしたリファクタリングを行うと、実行時に値が消える。

確認と修正

確認はビルド成果物を直接探すのが最も確実だ。コードレビューではimportの連鎖を三段目で見落とす。

# ビルド後、クライアントバンドルにシークレット鍵の値が入っていないか
npm run build
grep -rF "$SUPABASE_SECRET_KEY" .next/static/ && echo "LEAK" || echo "clean"

# 公開してはならない変数が公開接頭辞で宣言されていないか
grep -rn "NEXT_PUBLIC_.*\(SECRET\|SERVICE_ROLE\|PRIVATE\)" .env* next.config.*

修正はサーバー専用モジュールに印を打っておく方向だ。server-onlyパッケージをimportすると、クライアントコンポーネントからそのモジュールを引いてきた瞬間にビルド時エラーになる。実行時に静かに空の値になる代わりにビルドが止まるので、事故がデプロイ前に表面化する。

// lib/supabase/admin.ts
import 'server-only'
import { createClient } from '@supabase/supabase-js'

// このクライアントはRLSを迂回する。サーバーの外に出してはならない。
export function createAdminClient() {
  return createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_SECRET_KEY!, // 公開接頭辞を付けない
    { auth: { persistSession: false } }
  )
}

構造で解く方法もある。クライアントコンポーネントをサーバーコンポーネントが包み、データはサーバーで読んで直列化可能なpropsだけを下ろす形だ。ドキュメントが紹介するchildrenスロットのパターンがここに当たる。クライアントコンポーネントにchildrenとして渡したサーバーコンポーネントはクライアントのモジュールグラフに入らず、サーバーでレンダリングされた結果だけが渡される。

2. RLSは有効にしただけでは終わらない

AIが出す形

テーブルを作りRLSを有効にする文のすぐ後に、読み取りポリシーが一つ付いてくる。名前はたいてい全ユーザーに読み取りを許可といったもので、条件はusing (true)だ。

alter table public.posts enable row level security;

create policy "Enable read access for all users"
  on public.posts for select
  using (true);

なぜ後で壊れるのか

RLSを有効にするとポリシーを作るまでは何も出ていかない。公式ドキュメントは、RLSを有効にした後ポリシーを作るまでは公開用の鍵でAPIを通じてどのデータにもアクセスできないと記している。安全な既定値だ。問題はその後に付くポリシーの方だ。using (true)はRLSを有効にしたままテーブルを再び全部開くポリシーだ。ダッシュボードでRLSのバッジは有効に見え、実際には匿名ロールが全行を読む。有効と遮断は別の状態なのに、見た目は同じだ。

ポリシーを書くときに食い違いやすい箇所が他にもいくつかある。

  • コマンドごとに個別に掛かる。 読み取りポリシーだけあれば書き込みは遮断される。逆に更新ポリシーだけ作ると更新が動作しないが、ドキュメントは更新を実行するには対応する読み取りポリシーが必要だと明記している。ローカルで動いていた機能が本番だけで失敗するなら、この組み合わせをまず見る。
  • USINGとWITH CHECKは見る対象が違う。 USINGは既存の行が見えるかを決め、読み取り・更新・削除に適用される。WITH CHECKは挿入・更新の結果の行が条件を守っているかを見る。挿入ポリシーにwith check (true)を書くと、他人の所有者値を入れた行を作ることを防げない。所有者カラムのあるテーブルでは、ここが最もよくある穴だ。
  • 未ログインのリクエストではauth.uid()がnullになる。 ドキュメントはこの場合に条件が静かに偽となりアクセスが遮断されると説明し、認証の有無を明示的に確認する形を勧めている。遮断される側なので危険ではないが、原因のわからない空の一覧の正体はたいていこれだ。
  • ユーザーメタデータを権限判断に使ってはならない。 ドキュメントがよくある誤りとして直接名指ししている項目だ。ユーザーメタデータは利用者が更新できるので、そこに入った役割の値を見て管理者かどうかを決めるポリシーは権限昇格の経路になる。代替としてアプリメタデータを使うようドキュメントが明記している。
  • ビューは既定でポリシーを迂回する。 ビューは作成時に指定しなければ定義者の権限で動作し、基となるテーブルのRLSを飛ばす。SupabaseのSecurity Advisorはこの項目をエラー等級のリントとして分類している。ダッシュボードでビューを一つ作って一覧画面を手早く処理したプロジェクトがここに引っかかる。

確認と修正

確認は手作業ではなくAdvisorを回す。Supabaseのダッシュボードのデータベース項目にSecurity AdvisorとPerformance Advisorがあり、問題を直した後に再実行できる。以下はこの記事の主題と直接絡むリントだ。

リント何を捕まえるか等級
0013_rls_disabled_in_public公開スキーマのテーブルでRLSが無効。プロジェクトURLを知る人が全データを読み・変更し・削除できる状態エラー
0010_security_definer_viewビューが定義者権限で動作し、基となるテーブルのポリシーを迂回するエラー
0002_auth_users_exposed認証ユーザーテーブルの内容を公開に露出するビューエラー
0007_policy_exists_rls_disabledポリシーは作られているのにテーブルのRLSが無効情報
0008_rls_enabled_no_policyRLSは有効なのにポリシーがなくAPIアクセスが全部遮断される情報
0015系利用者が変更できるメタデータに依存するポリシー-

修正は所有者を基準にコマンド別へポリシーを分ける形が基本だ。ここに性能上の措置が一つ付く。ドキュメントはauth.uid()を(select auth.uid())で包むとPostgresが文単位で結果をキャッシュし、ベンチマーク基準で約95パーセントの改善があったと記している。ポリシーが使うカラムにインデックスを張ることと、TO句で対象ロールを絞ることも併せて勧めている。

-- コマンド別に分け、所有者条件を両方向に掛ける
create policy "owner reads own rows"
  on public.posts for select to authenticated
  using ((select auth.uid()) = user_id);

create policy "owner inserts own rows"
  on public.posts for insert to authenticated
  with check ((select auth.uid()) = user_id);

create policy "owner updates own rows"
  on public.posts for update to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);

create policy "owner deletes own rows"
  on public.posts for delete to authenticated
  using ((select auth.uid()) = user_id);

-- ポリシーが見るカラムにはインデックスを張る
create index if not exists posts_user_id_idx on public.posts (user_id);

-- ビューを使うなら呼び出し元の権限で動かす
create view public.post_summaries with (security_invoker = on) as
  select id, user_id, title, created_at from public.posts;

公開読み取りが実際に必要なテーブルはもちろんある。お知らせ一覧や公開プロフィールがそうだ。そのときもusing (true)を使う前に、そのテーブルに公開してはならないカラムが混ざっていないかをまず見る。メールアドレスや内部状態の値が同じテーブルにあるなら、答えはポリシーではなくテーブルを分けることだ。ポリシーは行単位でしか掛からず、カラムを隠してはくれない。

3. anon keyでできることの正確な範囲

AIが出す形

プロジェクトURLと公開鍵をNEXT_PUBLIC_接頭辞で宣言し、ブラウザでクライアントを作る。これは正しいコードだ。問題はこのコードを根拠に鍵の管理が終わったと考える方にある。

なぜ後で壊れるのか

公式ドキュメントは公開用の鍵をオンラインで公開しても安全だと記している。ただしその根拠が重要だ。ドキュメントが挙げる理由は公開コンポーネントからは鍵の取得が常に可能だという点である。隠すことを防御線にしていないという意味であって、その鍵で何もできないという意味ではない。この鍵を持つリクエストは匿名ロールとして、ログイン利用者のトークンが付けば認証ロールとして動作する。その先で何が見えるかは完全にRLSポリシーとスキーマ権限が決める。

だから整理するとこうなる。公開鍵の露出は事故ではない。公開鍵とRLSのないテーブルの組み合わせが事故だ。Advisorのエラー等級リントがこの状態を指して、プロジェクトURLを知る人が全データを読み・変更し・削除できると記している理由がそれだ。

反対側のシークレット鍵は性格が違う。ドキュメントはこの鍵がRLSを迂回する属性を持ちプロジェクトのデータに完全なアクセス権を与えると説明し、Webページやソースコードや実行ファイルに入れず、チャットやメールで送らないよう記している。ブラウザで使うと401が返るが、ドキュメントはここに但し書きを付ける。それは攻撃者が他の場所でその鍵を使うことを防ぐわけではない。401は防御ではなく取り違え防止の装置だ。流出したなら直ちに削除してローテーションするというのがドキュメントの案内である。

区分公開鍵(publishable / anon)シークレット鍵(secret / service_role)
置く場所ブラウザ、モバイルアプリ、CLIなど公開コンポーネントサーバー、エッジ関数など非公開コンポーネントのみ
動作ロール未ログインは匿名ロール、ログイン時は認証ロールRLS迂回属性を持つロール
RLS適用受ける。これが唯一の防御線迂回する
露出したとき設計上の前提。ただしRLSが空ならそのまま事故直ちに削除してローテーション
Next.js環境変数NEXT_PUBLIC_接頭辞を付ける接頭辞を付けない

確認と修正

  • ブラウザで使う鍵が公開鍵で合っているか確認する。プロジェクト設定のAPI項目で鍵の種類を区別して表示してくれる。
  • Data APIに露出しているスキーマの一覧を見る。既定は公開スキーマだ。RESTで出ていく必要のないテーブルは別スキーマに移して露出一覧から外す。鍵があってもAPIの経路そのものがなくなる。
  • 権限昇格用の関数を作ったなら、その関数が露出スキーマにあるかを見る。ドキュメントは定義者権限の関数を露出スキーマに作らないよう明示的に警告している。
  • 鍵をローテーションしたならクライアントバンドルも再ビルドする。公開変数はビルド時点で焼き込まれるので、再デプロイまでは古い鍵が出ていく。

4. セッションがサーバーレンダリングと出会う場所

AIが出す形

サーバーコンポーネントやミドルウェアでセッションを読み、なければログインページへ送る。クライアントで使っていた呼び出しをそのままサーバーへ移した形だ。

// サーバーでこう書いてはいけない
const { data: { session } } = await supabase.auth.getSession()
if (!session) redirect('/login')

なぜ後で壊れるのか

SupabaseのNext.js向けサーバーサイド認証ガイドは、この地点に危険表示を付けている。サーバーはクッキーからセッションを取得するがそのクッキーは誰でも偽造できるというのが最初の一文で、サーバーコードでgetSession()を絶対に信頼するなというのが二つ目だ。理由も併記されている。この呼び出しは認証トークンの再検証を保証しない。現行のガイドはページとユーザーデータを保護する際にgetClaims()を使うよう案内しており、この呼び出しは公開された公開鍵でJWT署名を毎回検証する。認証サーバーに直接問い合わせるgetUser()も同じ目的に使える。

ここで終わりではない。サーバーレンダリングとセッションが出会うと罠がもう三つ生まれる。

  • サーバーコンポーネントはクッキーを書けない。 だからトークンの更新と伝達を担うミドルウェア層が必要になる。ガイドはこの層が、認証トークンを更新し、更新されたトークンをサーバーコンポーネント側とブラウザ側にそれぞれ渡す三つの仕事をすると説明している。この層が抜けるとセッションが静かに期限切れになり、利用者は理由もなくログアウトされる体験をする。再現が難しくバグ報告として捕まえにくい種類だ。
  • キャッシュがセッションを渡してしまう。 ログイン状態でレンダリングされたページがCDNにキャッシュされると、次の人がその画面を受け取る。ガイドのクッキー設定コードがキャッシュ関連のヘッダーを併せて渡し、そのヘッダーを必ずレスポンスに適用せよという理由がこれだ。個別化されたページに静的キャッシュが付かないようにするのは認証設定ではなくレンダリング設定側の仕事である。
  • ルート保護はデータ保護ではない。 ミドルウェアで経路を遮断してもData APIはその経路と無関係に開いている。マッチャーの一覧から漏れた経路が一つ、新しく追加して登録を忘れた経路が一つあっても、それがそのままデータ流出にならないためにはデータ側をRLSが再び遮断している必要がある。これが2番と4番を別々に点検すべき理由だ。

確認と修正

// app/dashboard/page.tsx
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export default async function DashboardPage() {
  const supabase = await createClient()

  // サーバーに確認を要求する呼び出しを使う
  const { data: { user }, error } = await supabase.auth.getUser()
  if (error || !user) redirect('/login')

  // ここでもRLSが再び掛かる。二重にしておく。
  const { data: posts } = await supabase
    .from('posts')
    .select('id, title, created_at')
    .order('created_at', { ascending: false })

  return <PostList posts={posts ?? []} />
}
  • ログアウト状態で保護経路にリクエストを送り、200ではなくリダイレクトが返るか見る。ブラウザではなくcurlで見る。クライアント側のリダイレクトはサーバーの応答を隠してしまう。
  • 同じリクエストのレスポンスヘッダーでキャッシュ関連の値を確認する。個別化されたページに共用キャッシュが付いていたら、そこから直す。
  • ミドルウェアのマッチャー一覧と実際のルート一覧を並べて比較する。手動の一覧は必ずずれる。保護を既定にして公開を例外とする方向でマッチャーを組めば、新しい経路を忘れても安全な側に倒れる。
  • コードベースでサーバーファイルのgetSession呼び出しをすべて探して確認する。

5. 接続はサーバーレスで違う漏れ方をする

AIが出す形

ダッシュボードからコピーした接続文字列をDATABASE_URLに入れてORMを付ける。ポートは5432だ。ローカルでよく回り、デプロイしてもよく回る。利用者が少ない間は。

なぜ後で壊れるのか

サーバーレス環境はリクエストが増えるとインスタンスが増える。インスタンスごとに自分の接続プールを持つので、同時リクエスト100件はそのまま接続100本になる。データベースには接続数の上限があり、上限に達すると新しいリクエストは接続を得られず待つか失敗する。アプリケーションのログにはタイムアウトだけが残るので、原因がデータベースだということも見えにくい。コネクション枯渇という現象自体とプーラーの一般論はスタートアップのPostgres生存ガイドで扱ったので、ここではSupabaseとサーバーレスが重なったときだけ生じる選択の問題を見る。

公式ドキュメントが示す三つの経路は目的が違う。

経路ポート合う場所制約
直接接続5432長く生きるVM・コンテナなど常駐サーバー既定はIPv6。IPv4はアドオンが必要
プーラー セッションモード5432IPv4専用網で直接接続の代わりにするときドキュメントはその場合に限り勧める
プーラー トランザクションモード6543サーバーレス・エッジ関数など短い接続が多い場所プリペアドステートメント非対応

ドキュメントはトランザクションモードについて、多数の一時的な接続を必要とするサーバーレスやエッジ関数に理想的だと記したうえで、すぐに制約を付ける。このモードはプリペアドステートメントに対応していないので、エラーを避けるには接続ライブラリでその機能を無効にする必要があるというものだ。このスイッチを切らないと負荷が低いうちは何も起きず、接続が再利用され始める地点から断続的なエラーが出る。再現しないエラーの典型的な出どころだ。

アドレス系統も静かな失敗要因だ。直接接続は既定がIPv6で、共有プーラーは全プランでIPv4専用である。デプロイ対象の環境がIPv6で出られないと直接接続の文字列は接続段階で失敗する。生成されたコードだけでは判断できない条件であり、ローカルではうまくいくのでさらに紛らわしい。

確認と修正

  • デプロイ環境の接続文字列のポートを確認する。サーバーレス関数が5432で出ているなら、それ自体が点検対象だ。
  • トランザクションモードを使うならライブラリのプリペアドステートメントのスイッチを切ったか確認する。スイッチ名はライブラリごとに違う。Prismaは接続文字列のpgbouncer=true、postgres.jsはprepare: falseがその位置だ。
  • マイグレーションの接続は分ける。スキーマ変更ツールはセッションレベルの状態を使う場合があり、トランザクションモードと相性が悪い。アプリケーションはトランザクションモード、マイグレーションは直接接続かセッションモードに置く方が安全だ。
  • モジュールの最上位でクライアントを一度だけ作って再利用する。リクエストハンドラの中で毎回新しいプールを作るコードは、インスタンス一つに接続を複数掴ませる。
  • 接続数と待機状態を指標として見る。何を見れば異常が見えるのかはデータベースを「見える」ようにするということで整理した。

6. マイグレーションとスキーマドリフト

AIが出す形

ダッシュボードのSQLエディタに貼り付けるSQLブロックがチャットの回答として出てくる。貼って実行すればすぐ通る。ファイルには何も残らない。

なぜ後で壊れるのか

本番データベースの実際のスキーマとリポジトリのマイグレーションファイルが分かれていく。この状態が生む結果は四つだ。

  • 新しい環境を作れない。ステージングを一つ立てようとすると、そこまで到達するSQLがどこにもない。
  • 戻す根拠がない。何をいつなぜ変えたのかの記録がチャットログにしかない。
  • レビューがない。スキーマ変更はアプリケーションコードより戻しにくいのに、承認手続きを通らないのはこちらだ。
  • セキュリティ設定がバージョン管理の外にある。RLSポリシーはスキーマの一部だ。ポリシーがマイグレーションファイルになければ、誰がいつusing (true)を入れたのか確認する方法がなく、新しい環境にはポリシーなしでテーブルだけができる。

最後の項目がこの記事の他の項目とつながる。2番でポリシーをどれだけ丁寧に組んでも、そのポリシーがコードとして残っていなければ次のデプロイで消える。

確認と修正

確認は差分を取り出すことだ。リモートのスキーマとローカルのマイグレーションの差がSQLとして出てくる。結果が空であれば正常だ。

# プロジェクトを接続
supabase link --project-ref <project-ref>

# ドリフト確認。出力が空であるべき
supabase db diff --linked

# すでに手で変えてしまったものをファイルに回収する
supabase db diff --linked -f recover_manual_changes

# 以降はファイルが先
supabase migration new add_posts_rls
supabase db reset          # ローカルで最初から再生し再現性を確認
supabase db push           # リモートに適用
  • CIに差分確認を入れて出力が空でなければ失敗させる。ドリフトは生じた日に捕まえれば回収が楽だ。
  • ポリシーとインデックスと関数もマイグレーションファイルに入れる。テーブル定義だけ入れるのは半分だけ管理していることになる。
  • ローカル再生を習慣にする。最初から回し直して同じ結果にならないマイグレーションは、新しい環境で必ず失敗する。
  • 大きなスキーマ変更は一度に上げず刻む。分けて上げる方式自体はGitHub スタックPR パブリックプレビューで扱い、無停止変更でロックがどう掛かるかはPostgres生存ガイドの方だ。

7. 料金が跳ねる区間

AIが出す形

取得は全カラムだ。select('*')が既定値のように出てくる。画像はストレージに上げた元ファイルをそのままimgタグに掛ける。リアルタイム購読はコンポーネントの中で開き、後始末のコードはない。

なぜ後で壊れるのか

料金が跳ねる場所はたいていデータベースの容量ではない。送信量だ。2026年8月時点の公開料金表を整理するとこうなる。

項目Free($0)Pro($25/月)Pro超過単価
月間アクティブユーザー50,000100,0001人あたり$0.00325
データベース容量500MB8GB1GBあたり$0.125
送信量5GB250GB1GBあたり$0.09
ファイルストレージ1GB100GB1GBあたり$0.0213
コンピュート共有(RAM 500MB)月$10クレジット追加プロジェクトは別課金

ここで読むべきは絶対額ではなく何が課金単位なのかだ。送信量がGB単位で課金されるのに、一覧画面が一つ大きなテキストカラムやJSONカラムを丸ごと下ろしているなら、画面は問題ないまま請求書だけが育つ。画像も同じだ。元解像度のファイルを一覧のサムネイル位置にそのまま掛けると、一回の訪問で数MBが出ていく。

運用条件も二つ確認しておく。Freeプランは1週間活動がないとプロジェクトが一時停止され、アクティブなプロジェクトは2つまでだ。検証用に作ったプロジェクトをそのまま本番に上げた構成なら、この条件がある日サービス停止として現れる。Proプランは支出上限が既定で有効で、上限を超えて使うには自分で解除する必要がある。上限を有効にしたままなら料金は跳ねない代わりに限度でサービスが制限され、解除すれば逆になる。どちらでもよいが、知らないままでいる状態が一番悪い。

確認と修正

  • ダッシュボードの使用量画面で項目別に見る。送信量が想定より大きいなら、どのリクエストが重いのかから探す。
  • 取得でカラムを明示する。一覧画面に必要なカラムはたいてい三つか四つだ。
  • 画像は変換を通すかサイズを分けて保存し、キャッシュヘッダーを付ける。同じファイルを毎回新しく下ろさないようにするだけで送信量が大きく減る。
  • リアルタイム購読は後始末の関数で必ず解除する。画面を行き来するたびに購読が積み上がると、接続と送信量が一緒に増える。
  • 支出上限の設定を確認し、どちらに倒すことにしたのかをチームで合意しておく。
// 一覧画面で必要なカラムだけ
const { data } = await supabase
  .from('posts')
  .select('id, title, thumbnail_url, created_at')
  .order('created_at', { ascending: false })
  .range(0, 19)
2026年8月時点。料金項目と単価は変わる。上の表は確認時点の公開料金ページの値であり、支払いの判断は必ず公式の料金ページで再確認する。

8. デプロイ前に一度ずつ回す順序

順序に意味がある。上の項目が下の項目の前提だからだ。ポリシーがない状態でルート保護をどれだけ精緻にしても意味がなく、マイグレーションにポリシーがなければポリシーを直しても次のデプロイで戻る。

順序確認すること見る方法合格基準
1公開スキーマのテーブルのRLSSecurity Advisorを実行エラー等級のリント0件
2using (true)ポリシーポリシー一覧を読み対象テーブルを確認公開が意図されたテーブルにのみ存在
3所有者カラムの挿入・更新条件WITH CHECK句を確認両方向に所有者条件が掛かっている
4シークレット鍵のバンドル混入ビルド後の成果物を文字列検索一致0件
5サーバーコードのセッション判断getSessionの呼び出しを検索権限判断の位置にない
6保護経路のキャッシュヘッダーログアウト状態でcurlリクエスト個別化ページに共用キャッシュなし
7サーバーレスの接続ポートとオプションデプロイ環境変数を確認トランザクションモードならプリペアド無効
8スキーマドリフトsupabase db diff --linked出力が空
9送信量の上位リクエスト使用量画面と取得コードを対照一覧取得に全カラム取得がない
10プランと支出上限決済設定を確認選んだ状態をチームが把握している

この10行は一度に全部やるために作ったものではない。1番から4番までが急ぎで、残りは利用者が付き始めてからでも遅くない。ただし4番は今日やる方がよい。鍵がすでに出ているなら、時間が経つほど回収コストだけが大きくなる。

確認できなかったこと

  • 料金項目・含有量・超過単価は2026年8月時点の公開料金ページの値だ。プラン構成は変わるので、支払い判断の時点で再確認する必要がある。限度を超えたときの具体的な制限動作はプランと設定によって異なるため一般化しなかった。
  • getClaims()の戻り値の構造と非対称鍵検証の適用可否は、プロジェクト設定とライブラリのバージョンによって変わる。本文の例には形が安定しているgetUser()を使った。
  • Advisorのリント番号と等級は一覧が更新されうる。番号ではなくダッシュボードが表示する説明を基準に判断する。
  • どのAIコーディングツールがどの既定テンプレートを出すかは、ツールとバージョンごとに違う。本文の「AIが出す形」は特定の製品の出力を指したものではなく、このスタックで繰り返し観察される形を整理したものだ。
  • 接続ライブラリごとのプリペアドステートメントのオプションは、各ライブラリのドキュメントが優先する。本文に記した二つの例以外の組み合わせは、それぞれのドキュメントで確認する必要がある。

結論: 抽象化を剥がすべき地点は決まっている

このスタックを使うなという話ではない。逆だ。この組み合わせが良い理由は、認証とデータベースとポリシーが一か所に集まっていて確認すべき地点が少ないことであり、上の10行がその少ない地点の一覧だ。自前で組み立てたなら、同じことを確認するためにはるかに多くの場所を見なければならない。

AIが書いたコードの問題もコード品質ではない。生成モデルは動くコードを作るよう最適化されており、実際に上手に作る。ただし動くことと安全なことと安いことは互いに別の目標であり、後ろの二つは画面に現れない。だから確認は人の側に残る。

基準を一つだけ残すならこれだ。このコードが何を遮断しているのかを一文で言えないなら、まだ何も遮断していないと考える。RLSを有効にしたという事実は文ではない。どのロールがどの条件でどの行にアクセスするのかが文だ。その文を書けるようになるまでにかかる時間は半日ほどで、それを先送りしたときにかかる時間は予測できない。
