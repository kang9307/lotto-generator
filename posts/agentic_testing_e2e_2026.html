에이전틱 테스팅 — E2E 테스트 스택에서 AI 에이전트의 역할

셀렉터 자동복구·시나리오 생성·플레이키 테스트 진단에서 에이전트가 실제로 무엇을 하고, 어디서 멈추는가

2026-06-24 개발/인프라

서론: E2E 테스트는 왜 이렇게 자주 깨지는가

2026년 6월 기준, 소프트웨어 엔지니어링에서 가장 불편한 진실 중 하나는 E2E(End-to-End) 테스트가 유지보수 비용 대비 효용이 낮다는 것이다. CI 파이프라인에서 테스트가 이유 없이 실패하고, 개발자가 버그인지 환경 문제인지 구분하는 데 몇 시간을 쓰며, 소소한 UI 변경 하나가 수십 개의 테스트를 깨뜨린다. Slack 엔지니어링팀은 한때 플레이키 테스트 비율이 57%에 달했다고 고백했다. 세 번 중 두 번은 무작위로 실패하는 테스트 스위트라면, 테스트가 신뢰를 주는 것이 아니라 노이즈를 생산하는 것이다.

이 문제에 AI 에이전트가 등장했다. Slack 엔지니어링팀이 공개한 실험 결과가 GeekNews에서 주목받으면서, "에이전틱 테스팅(agentic testing)"이라는 개념이 현실적으로 논의되기 시작했다. 이 글은 그 실험 데이터를 교차 검증하고, 에이전트가 실제로 무엇을 하는지, 어디서 멈추는지, 그리고 지금 당장 어디에 쓸 수 있는지를 본인 관점으로 분석한다.

미리 결론을 밝힌다. 에이전틱 테스팅은 기존 E2E 테스트의 대체가 아니다. 테스트 피라미드 최상단에 별도 레이어를 더하는 것이다. 그리고 그 레이어가 유용한 범위와 쓸 수 없는 범위를 분명히 이해하지 않으면, 또 다른 형태의 기술 부채를 만든다.

1. 전통적 E2E 테스트의 구조적 취약점

에이전트가 무엇을 해결하려는지 이해하려면 전통적 E2E 테스트가 왜 깨지기 쉬운지 먼저 짚어야 한다.

1.1 셀렉터 의존성: 가장 빈번한 파손 경로

전통적 E2E 테스트의 핵심은 DOM 셀렉터다. document.querySelector('.checkout-btn')나 XPath로 특정 요소를 찾아 클릭한다. 문제는 이 셀렉터가 UI 구현 세부사항에 묶여 있다는 것이다. 디자이너가 클래스명을 바꾸거나, 개발자가 컴포넌트를 리팩터링하거나, 마케팅팀이 버튼 위치를 옮기면 셀렉터가 깨진다. 기능은 전혀 바뀌지 않았는데도.

Playwright는 role-based locator(getByRole, getByLabel)와 auto-waiting으로 이 문제를 상당 부분 완화했다. 그러나 DOM 변화의 근본적 취약성은 남는다. 현실에서 대형 프론트엔드 코드베이스는 끊임없이 리팩터링되고, 테스트 팀은 그 속도를 좇아 셀렉터를 업데이트해야 한다.

1.2 플레이키 테스트: 비결정론의 늪

플레이키 테스트(flaky test)는 코드가 바뀌지 않았는데 통과와 실패를 오가는 테스트다. E2E가 특히 취약한 이유는 세 가지다. 첫째, 비동기 타이밍: API 응답이 느릴 때 테스트가 아직 오지 않은 데이터를 검사하려다 실패한다. 둘째, 옵티미스틱 UI 트랩: UI가 먼저 렌더링되고 데이터가 나중에 채워지는 패턴에서, auto-waiting이 DOM 준비를 확인해도 비즈니스 상태가 아직 미완이다. Slack은 이 문제를 "optimistic-UI-rendering trap"으로 부르며, 전담 안정화 작업으로 57%에서 4% 미만으로 낮추는 데 상당한 시간을 투자했다. 셋째, 환경 불안정성: 테스트 워크스페이스, 인증 세션, 네트워크 상태가 예측 불가능하게 변한다.

1.3 유지보수 부담의 복리 효과

기능이 추가될수록 E2E 테스트는 선형이 아니라 복리로 늘어나는 경향이 있다. 시나리오 수가 늘면 각 시나리오를 작성하고 유지보수하는 비용도 함께 늘고, 파이프라인 실행 시간도 길어진다. 많은 팀이 E2E 테스트를 쓰기로 결정하고, 유지보수 부담에 지쳐 점점 업데이트를 미루다가, 결국 수백 개의 깨진 테스트를 방치한 채 사실상 E2E 커버리지를 포기하는 패턴으로 빠진다.

2. 에이전틱 테스팅: 여정이 아닌 목표를 검증한다

Slack 엔지니어링팀이 내린 에이전틱 테스팅의 핵심 정의는 단 한 문장으로 압축된다.

"Tests enforce journeys. Agents verify goals." — Slack Engineering

전통적 테스트가 "버튼을 클릭하고, 입력창에 타이핑하고, 결과를 확인하는" 여정을 순서대로 실행한다면, 에이전트는 "스레드 메시지를 보내라"는 목표를 제시받아 스스로 경로를 찾는다. 200회 이상의 실험에서 동일한 목표에 도달하는 행동 시퀀스의 약 80%가 실행마다 달랐다. 에이전트는 같은 목표에 다른 입력 방식, 다른 메뉴 순서, 다른 UI 요소 선택으로 도달한다.

이것이 셀렉터 문제를 해결하는 방식이다. 에이전트는 특정 DOM 구조에 묶이지 않는다. 접근성 트리(accessibility tree) 스냅샷을 읽고, 화면 상태를 해석하고, 의미적으로 다음 행동을 결정한다. UI가 리팩터링되어 클래스명이 바뀌어도, 에이전트는 "로그인 버튼"을 다시 찾아낸다. 하드코딩된 셀렉터가 아니라 의미 기반으로 탐색하기 때문이다.

3. Slack 실험 데이터: 무엇이 실제로 작동하고 무엇이 작동하지 않는가

Slack 엔지니어링팀은 Playwright MCP, Playwright CLI, 그리고 에이전트 생성(generated) 테스트 세 가지 방식으로 200회 이상의 실험을 진행했다. 핵심 데이터를 정리하면 다음과 같다.

3.1 신뢰성

방식단순 시나리오 실패율복잡 시나리오 실패율
Playwright MCP0%약 12%
Playwright CLI약 12%약 20%
에이전트 생성 테스트약 8%약 48%

MCP 방식이 가장 안정적이다. CLI 방식의 실패 원인 다수는 모델 추론이 아니라 인증 처리, 탐색 타이밍, 세션 불안정성 같은 실행 환경 문제였다. 에이전트 생성 테스트는 단순 흐름에서는 나쁘지 않지만 복잡한 워크플로우에서 실패율이 급등하는 것이 핵심 약점이다.

3.2 비용

에이전틱 테스팅의 가장 큰 현실적 장벽은 비용이다. 실행당 $15~30이라는 수치는 전통적 E2E 테스트와 비교해 몇 자릿수 차이가 난다. CLI 방식은 약 85턴에 걸쳐 약 600만 토큰을 소비했고, MCP 방식도 약 40턴에 350만 토큰이었다. 왜 이렇게 비싼가? 매 턴마다 전체 시스템 프롬프트와 대화 이력이 재전송되기 때문이다. 컨텍스트가 누적될수록 토큰 소비가 급증한다.

프롬프트 캐싱, 컨텍스트 압축 같은 기술로 이 비용을 줄일 여지는 있다. 그러나 2026년 6월 기준, "에이전틱 테스팅을 CI 파이프라인의 표준 실행 레이어로 돌린다"는 것은 현재 비용 구조에서 대부분의 팀에 비현실적이다.

3.3 속도

아이러니하게도 에이전트 생성 테스트는 생성 시간이 약 3분으로 가장 빠르다. MCP 방식은 5~8분, CLI 방식은 9~11분이다. 그러나 한 번 생성된 결정론적 Playwright 테스트가 32초 만에 실행되는 것과 비교하면, 에이전트 방식은 매번 추론을 새로 시작하므로 반복 실행 비용이 단계적으로 쌓인다.

4. 에이전트가 실제로 기여하는 세 가지 영역

실험 결과를 바탕으로, 에이전트가 현재 실질적으로 기여할 수 있는 영역은 세 가지다.

4.1 셀렉터 자동복구(Self-Healing)

Playwright의 내장 Healer 에이전트는 테스트 실행 중 셀렉터 실패를 감지하면 접근성 트리 스냅샷을 분석해 대체 로케이터를 생성하고 테스트를 자동으로 재실행한다. 셀렉터 관련 실패의 75% 이상에서 자동 복구가 가능하다는 보고가 있다. 이것은 UI 리팩터링이 잦은 프로젝트에서 유지보수 부담을 크게 줄여준다. 단, 로직 버그나 백엔드 변경으로 인한 실패는 에이전트가 셀렉터를 고치는 것으로 해결할 수 없다. 여기서 자동복구는 작동하지 않는다.

4.2 시나리오 자동 생성

Playwright의 Planner + Generator 에이전트 체인은 앱을 탐색해 마크다운 테스트 플랜을 만들고, 이를 Playwright 테스트 파일로 변환한다. 아무도 테스트 케이스를 처음부터 작성하지 않아도 된다. 이것은 두 가지 상황에서 유용하다. 새 기능의 첫 테스트 커버리지를 빠르게 만들 때, 그리고 어떤 시나리오가 존재하는지 탐색할 때. 그러나 생성된 테스트는 반드시 사람이 검토해야 한다. 표면적으로 통과하지만 중간 경로가 잘못된 경우를 에이전트 스스로 감지하지 못할 수 있기 때문이다.

4.3 플레이키 테스트 진단과 버그 재현

이것이 본인이 가장 높게 평가하는 영역이다. 에이전트는 "이 워크플로우가 간헐적으로 실패한다"는 상황에서 목표만 주고 여러 번 반복 실행해 실패 패턴을 찾아내는 데 적합하다. 결정론적 테스트라면 정해진 경로만 실행하지만, 에이전트는 다양한 경로로 목표에 접근하면서 특정 경로에서만 발생하는 비결정론적 실패를 잡아낼 가능성이 높다. 또한 프로덕션에서 재현하기 어려운 버그를, 목표 기반 지시로 재현 시나리오를 만드는 데도 유용하다.

5. 에이전틱 테스팅의 한계와 신뢰 경계

기술의 가치는 그 한계를 명확히 알 때 제대로 쓸 수 있다. 에이전틱 테스팅의 한계를 솔직하게 정리한다.

5.1 비결정론은 이점이자 취약점이다

에이전트가 다양한 경로로 목표에 도달한다는 것은 유연성이지만, 동시에 CI 파이프라인의 확정적 검증에 쓸 수 없다는 이유가 된다. 같은 테스트가 매번 다른 경로를 밟으면, 어느 날 실패했을 때 "이번 실패가 기능 회귀인가, 에이전트가 다른 경로를 택해서인가"를 구분하기 어렵다. 신뢰할 수 있는 CI는 결정론적이어야 한다.

5.2 복잡도가 오르면 실패율이 급등한다

Slack 실험에서 단순 시나리오의 실패율이 0~12%인 반면, 복잡 시나리오에서는 에이전트 생성 테스트의 실패율이 48%까지 치솟았다. 크로스워크스페이스 플로우, 다중 브라우저 창, 복잡한 인증 시퀀스 같은 시나리오에서 에이전트의 신뢰성은 현재 수준에서 CI 기준을 충족하지 못한다.

5.3 프롬프트 자체가 테스트 로직이다

에이전틱 테스팅에서 목표를 기술하는 프롬프트는 전통적 테스트의 코드와 동등한 위상이다. "빠르게 체크아웃을 완료하라"는 지시는 "체크아웃을 완료하라"와 다른 행동을 유도할 수 있다. 프롬프트를 업데이트하면 에이전트의 행동이 바뀌고, 그 결과 테스트 결과가 달라진다. 이는 프롬프트 버전 관리와 리뷰가 코드 리뷰만큼 중요하다는 것을 의미한다. 많은 팀이 이 점을 간과한다.

5.4 데이터 보안: 숨겨진 리스크

AI 보조 테스트 생성과 자동복구는 LLM에 DOM 스냅샷, 코드 스니펫, 셀렉터 문자열을 전송한다. 테스트 픽스처에 실제 사용자 데이터나 PII가 포함되어 있다면, 외부 API로 전송되는 순간 데이터 유출 리스크가 생긴다. 자체 호스팅 테스트 플랫폼과 온프레미스 LLM 엔드포인트를 쓰면 이 위험을 줄일 수 있지만, 그만큼 운영 부담이 늘어난다. 규제 산업이나 보안 민감 제품이라면 이 선택이 필수다.

6. 에이전틱 테스팅을 테스트 피라미드에 어떻게 배치할 것인가

Slack 엔지니어링팀의 결론은 명확하다. 에이전틱 테스팅은 기존 테스트 피라미드를 대체하지 않고, 그 위에 별도 레이어를 더한다.

6.1 각 레이어의 역할 재정의

유닛 테스트는 빠르고 비용이 낮으며 결정론적이다. 함수 단위의 로직을 검증한다. 통합 테스트는 서비스 간 인터페이스와 데이터 흐름을 검증한다. 결정론적 E2E 테스트는 중요 사용자 여정을 코드로 고정하고 CI에서 매 커밋마다 실행한다. 에이전틱 테스팅은 이 세 레이어가 잡지 못하는 것, 즉 복잡한 UI 동작 탐색, flaky 워크플로우 디버깅, 프로덕션 버그 재현에 투입된다.

6.2 실용적 배치 전략

본인이 권하는 배치는 이렇다. 에이전틱 테스팅을 CI 필수 게이트로 쓰지 마라. 비용과 비결정론이 현재 수준에서 그것을 허용하지 않는다. 대신 두 가지 상황에 집중하라. 첫째, 새 기능 출시 전 탐색적 검증: 에이전트에게 목표를 주고 예상하지 못한 경로와 에지케이스를 찾게 한다. 둘째, 간헐적 실패 진단: 결정론적 테스트가 간헐적으로 실패할 때, 에이전트로 다양한 경로를 반복 실행해 패턴을 찾는다. 여기서 에이전트의 비결정론이 오히려 장점이 된다.

6.3 비용 관리

에이전틱 테스팅 비용을 통제하려면 세 가지가 필요하다. 프롬프트 캐싱으로 반복되는 시스템 프롬프트를 재사용한다. 컨텍스트 압축으로 긴 대화 이력이 토큰을 불필요하게 소비하는 것을 막는다. 실행 빈도를 통제한다. 매 커밋이 아니라 PR 병합이나 릴리스 전 단계에서만 돌린다. 이것만으로도 비용을 상당히 낮출 수 있다.

7. 2026년 현재의 정직한 평가

에이전틱 테스팅은 과장된 기대와 무시 사이 어딘가에 있다. 본인이 정직하게 평가하는 현재 상태는 이렇다.

작동하는 것: 단순 시나리오의 목표 기반 검증, 셀렉터 자동복구, 탐색적 테스팅, 간헐적 실패 패턴 발견. 이 영역에서 에이전트는 사람이 수동으로 하던 일을 상당 부분 자동화한다.

아직 작동하지 않는 것: 고빈도 CI 파이프라인의 표준 게이트, 복잡한 크로스워크스페이스 시나리오, 비용 효율적인 전체 E2E 커버리지. 이 영역에서 에이전트를 억지로 쓰면 현재 기술로는 돈을 쓰고 신뢰성을 잃는다.

빠르게 나아지고 있는 것: 토큰 비용, 컨텍스트 관리, MCP 프로토콜의 안정성. 1~2년 뒤에는 지금의 한계 중 상당수가 해소될 것이다. 단 그 시점에 써야지, 지금 당장 전면 도입을 서두를 필요는 없다.

가장 중요한 경고는 이것이다. 에이전트가 "통과"를 보고했다고 해서 테스트가 올바른 것을 검증했다고 신뢰해서는 안 된다. 최종 결과뿐 아니라 에이전트가 택한 경로, 즉 실행 궤적을 사람이 직접 확인하는 프로세스가 있어야 한다. 에이전틱 테스팅을 블랙박스로 신뢰하는 것은 테스트를 없애는 것만큼 위험할 수 있다.

결론: 지금 할 수 있는 세 가지

에이전틱 테스팅은 진짜 신호다. 그러나 E2E 테스트의 모든 문제를 해결하는 마법이 아니다. 2026년 6월 기준, 지금 실질적으로 할 수 있는 세 가지를 제안한다.

첫째, Playwright의 Healer 에이전트를 기존 테스트에 적용해 셀렉터 유지보수 부담을 줄여라. 이것은 가장 낮은 비용으로 가장 빠른 효과를 낸다. 둘째, 결정론적 테스트가 간헐적으로 실패하는 워크플로우를 하나 골라 에이전트로 진단해 봐라. 비용을 한 번의 실험으로 한정하고, 실제로 패턴을 찾아내는지 확인하라. 셋째, 새 기능의 첫 테스트 커버리지를 Planner + Generator로 생성한 뒤, 사람이 검토해 CI에 편입하는 워크플로우를 만들어라. 에이전트가 초안을 쓰고 사람이 감수하는 구조다.

에이전틱 테스팅이 E2E 테스트 피라미드의 최상단 레이어가 되는 것은 불가피해 보인다. 다만 그 레이어가 언제, 어디서, 어떤 비용으로 쓰일지를 지금부터 조심스럽게 실험하고 배우는 것이 현명하다.
