はじめに:Codex Goals とは何か、今どこまで来たか

Codex Goals は、Codex に「作業が終わったときに成り立っているべき状態」を一度決めて渡すと、その目標をスレッドに保存し、複数のターンにわたって作業を続けさせる機能です。始まりは /goal コマンドひとつです。最初に入ったのは 2026年4月30日公開の Codex CLI 0.128.0(当時は実験的機能)で、2026年5月21日の 0.133.0 で既定で有効になり、実験的機能の表示が外れました。この記事の初出(2026年5月20日)はその間でした。韓国の開発者コミュニティ GeekNews(news.hada.io)でもすぐに話題になり、goal-setter のような外部ラッパーも紹介され、「実務で本当に使えるのか」という実用的な問いが出てきました。

本記事は OpenAI 公式ドキュメントをそのまま訳したガイドではありません。Codex Goals がどんな作業に役立ち、どこで空回りしやすく、Claude Code の作業の進め方と何が違うのかを実務の観点から整理した分析です。2026-09-29 の更新では、動作の説明を OpenAI 公式ドキュメントと GitHub リリースノートに合わせて書き直しました。結論を先に言えば、完了条件をテストや測定値で判定できる移行・リファクタリングにはよく合い、「何をもって終わりとするか」を言えない作業には合いません。

1. Codex Goals 登場の背景 - 単発生成の限界

2023〜2024年の GPT-4 時代のコーディングアシスタントは、本質的に「関数をひとつずつ書いてくれる友人」でした。「JWT デコーダ関数を作って」と頼めばきれいな Python を返してくれますが、その関数が自分のリポジトリの認証ミドルウェアのどこに入り、既存のセッション処理コードとどう衝突するかは知りません。結局、ユーザーが毎回コンテキストを説明し直す必要がありました。

2025年に Cursor・Windsurf・Claude Code のようなツールが広まり、リポジトリ全体をコンテキストとして扱う能力は大きく向上しました。しかし依然として、ユーザーが「これをやって、次はあれを」と段階ごとに指示しなければなりませんでした。この段階的指示のコストが積み重なると、AI を使う時間のほうが自分で書く時間より長くなる逆説が生じます。

Codex Goals はこの限界に、「目標と完了条件を一度決めておけば、次の一手は Codex が進み具合を見て決める」という方式で向き合います。OpenAI Cookbook は、ゴールラインは明確だがそこまでの道筋が不確かなときに Goals を使うよう案内しています。例として挙がるのは、プロファイリング、パッチ適用、ベンチマーク、不安定なテストの再現など、次の一手が前の段階で分かったことによって変わる作業です。

2. Goals 機能の動作(公式ドキュメント基準)

初出時、この節は「目標入力 → チェックリスト形式の自動サブタスク分解(4〜10個)→ 一定回数失敗するとエスカレーションする検証ループ → 振り返りレポート」の4段階で説明していました。2026-09-29 に OpenAI 公式ドキュメントと照合したところ、チェックリスト形式の自動分解、失敗回数に基づくエスカレーション、振り返りレポートは公式ドキュメントで確認できませんでした。公式ドキュメントが説明する流れは次のとおりです。

  1. 目標の設定:/goal <目標> で目標を決めます。公式の例は /goal Finish the migration and keep tests green です。
  2. 状態確認と操作:/goal だけを入力すると現在の目標が表示され、/goal pause・/goal resume・/goal clear で一時停止・再開・解除します。
  3. ターンをまたいで継続:目標はスレッドに保存され、複数のターンにわたって保持されます。ただし、別のターンが進行中のとき、ユーザー入力が待機中のとき、スレッドの他の作業が残っているときは続行しません。
  4. 止まる条件:成功、一時停止、解除、中断、予算上限、ユーザー入力が必要な行き詰まりのいずれかに至ると止まります。
  5. 有効化:0.133.0 から既定で有効です。スラッシュコマンドの一覧に /goal が見えない場合は、config.toml に features.goals = true を入れるか、codex features enable goals を実行するよう公式ドキュメントが案内しています。

要は検証基準を誰が決めるかです。公式 Cookbook は、良い目標に含める要素として6つを挙げます。終わったときに成り立っているべき結果(Outcome)、それを証明するテスト・ベンチマーク・レポートなどの検証手段(Verification surface)、作業中に後退してはならない制約(Constraints)、使ってよいファイル・ツール・リポジトリの範囲(Boundaries)、各試行の後に次の試行を決める方針(Iteration policy)、打つ手がなくなったときに止まって報告する条件(Blocked stop condition)です。つまり検証ループはシステムが自動で作ってくれるものではなく、ユーザーが目標の文に書き込むものです。

ChatGPT デスクトップアプリのスラッシュコマンドのドキュメントは、/goal を持続的な目標を設定するコマンドとして説明し、先に /plan で目標を練るよう案内しています。目標の実行中は、入力欄の上に進捗と、一時停止・再開・編集・解除のボタンが表示されます。先に計画を立てるやり方の長所と短所は 計画モードは死んだのか で別途扱いました。

3. 実戦シナリオ 3 つ(自前で構成した例)

以下は OpenAI 公式の例ではなく、韓国の SI・スタートアップ・サイドプロジェクトでよく見られるパターンを想定して作った例です。初出時は「予想されるサブタスク分解」として紹介しましたが、Codex が目標をこのようなリストに分けて見せるという公式の説明はありません。以下のリストは人が作業順序をあらかじめ描いたもので、目標の文には完了条件と検証手段を併せて書きました。

シナリオ A. レガシー REST API v1 → v2 移行

目標:「v1 REST API を v2 に移行。既存の v1 クライアントは 6 か月間互換を維持。既存の統合テストが v1・v2 の両方で通れば完了。」

作業の流れの例(想定):

  1. 既存 v1 エンドポイントの全数スキャン(routes/v1/*.py などのファイル一覧を抽出)
  2. v1 と v2 の差分マトリクスを作成(リクエスト・レスポンススキーマ比較表)
  3. v2 ルーターのスキャフォールディング生成(FastAPI prefix=/v2)
  4. v1→v2 アダプタ層の作成(旧クライアントが v1 を呼ぶと内部的に v2 を呼ぶ)
  5. 互換性テストケースの追加(既存の統合テストを v2 prefix で複製)
  6. 移行ガイドを Markdown で作成

注意:アダプタ層に誤ったマッピングが入ると本番障害に直結するため、この部分だけは別途人がコードレビューする必要があります。

シナリオ B. JWT 認証 → セッションベース認証への切り替え

目標:「ユーザー認証を JWT トークン方式からセッション Cookie 方式に切り替え。Redis セッションストアを使用。ログイン・ログアウトの統合テストが通れば完了。」

作業の流れの例(想定):

  1. 現在の JWT 発行・検証コードの位置を特定
  2. Redis クライアントモジュールの追加と接続設定
  3. セッション ID の生成・保存・検証ロジックを実装
  4. 既存の JWT 検証ミドルウェアをセッション検証ミドルウェアに置き換え
  5. ログイン・ログアウトのエンドポイントを修正(トークン応答 → Set-Cookie)
  6. フロントエンド呼び出し側の修正事項を整理(Authorization ヘッダー削除 + credentials オプション)
  7. 移行戦略ドキュメント(段階的移行と一括移行の比較)

注意:この作業はセキュリティ事故のリスクが大きいため、自動テストの通過だけでは不十分です。別途セキュリティレビューが必要な領域まで目標に入れて任せないでください。

シナリオ C. 型安全性を 95% 以上に引き上げる

目標:「TypeScript の型カバレッジを 60% から 95% 以上へ。any 型の除去を優先。type-coverage の結果が 95% 以上で、既存テストが引き続き通れば完了。」

作業の流れの例(想定):

  1. type-coverage ツールの実行結果を分析(現在のカバレッジを測定)
  2. any 使用箇所の優先順位付け(ライブラリ境界 > コアビジネスロジック > テストコード)
  3. 外部ライブラリの型定義を補強(@types の追加または ambient 宣言)
  4. ユーティリティ関数のシグネチャを明示(ジェネリクスを導入できる箇所を抽出)
  5. strict モードを段階的に有効化(noImplicitAny → strictNullChecks → strict 全体)
  6. 最終カバレッジの測定と未解決 any 一覧の報告

このシナリオは Goals の設計と最もよく合う種類の作業です。完了条件を数値で書けるため、止めるときと続けるときを判定しやすくなります。

5. 実務導入時の注意点

Codex Goals を初めて使うときによく陥る落とし穴を4つ挙げます。

  • 目標を広く取りすぎる:「コードベース全体をきれいにせよ」のような目標は終わりを判定する方法がなく、止まる根拠もありません。公式ドキュメントも、始める前に「完了とは何か」を決めるよう求めています。1回の Goal は完了をテストや測定値で言える単位に絞るのが安全です。
  • 検証手段なしで任せる:テストのないリポジトリでは目標を達成したか確かめる方法がなく、誤った方向に進み続けるおそれがあります。導入前に最低限の統合テストか測定コマンドが必要です。
  • 機密情報の漏えいリスク:API キーや DB パスワードが平文でコードに埋め込まれたリポジトリでは、作業中にその値が外部モデルへ送信されるリスクがあります。.gitignore と環境変数の使い方を先に点検してから導入してください。
  • ロールバック計画の欠如:長い作業の結果が気に入らなかったとき、専用ブランチで作業していなければ元に戻すのは困難です。必ず新しいブランチを作ってから始め、触ってよい範囲(Boundaries)を目標の文に書いておきましょう。
推奨ワークフロー:小さく始める → 結果を検証 → 段階的に拡大。最初の導入は「テストコードの追加」のようにリスクが低く完了条件が明確な作業から始めると、学習曲線がなだらかになります。

6. 韓国開発者のシナリオ別適合性

6.1 政府・公共 SI プロジェクト

外部 AI サービスの利用はセキュリティポリシー上ブロックされることが多くあります。ネットワーク分離環境で Codex Goals をそのまま使うのは難しく、オンプレミスの代替(例:ローカル LLM ベースの自前エージェント)を検討する必要があります。ただし RFP 作成や技術仕様の草案のような非コード作業では部分的に役立つ可能性があります。

6.2 スタートアップ・B2B SaaS

効果が出やすい領域です。シニア1人の時間を節約する価値が大きいためです。ただし「開発速度そのものよりコード品質の一貫性」が重要になった時点で導入するのが効果的です。MVP の段階では過剰なこともあり、技術的負債を整理する段階で有用性が高まります。

6.3 サイドプロジェクト・個人開発

コストパフォーマンスは使い方次第です。Codex は ChatGPT のプランに含まれる形で使うのが基本で、初出時に書いた「Goal 単位の追加費用」は公式ドキュメントで確認できませんでした。ただし公式ドキュメントは止まる条件のひとつに予算上限を挙げているため、長い目標をかける前に、その作業に使う予算を先に決めておくほうが安全です。すでに使っているツールがあるなら、完了条件が明確な大きな作業でだけ Goals を試すやり方が負担の少ない選択です。

7. goal-setter のような外部ラッパーと選択肢

コミュニティが作った goal-setter のようなラッパーは、初出当時 GeekNews で紹介されました。本記事は当初これを「OpenAI API の直接呼び出しと Codex Goals の間の抽象化レイヤー」と説明しましたが、今回の更新ではそのツールの現在の状態と機能を確認できませんでした。代わりに、公式ドキュメントで確認できる事実を基準に選択肢を整理し直します。

目標駆動の作業を回す方法は次の3つに分けられます。

  • API の直接呼び出し:目標の保持・反復・停止判断のロジックを自前で実装する必要があります。ツールを作るのに時間がかかります。
  • Codex Goals:目標の保存、ターンをまたいだ継続、一時停止・再開・解除が Codex に組み込まれているため、すぐに始められます。検証基準は引き続きユーザーが目標の文に書く必要があります。
  • ラッパーツール:目標の文の作成やコスト見積もりを助ける補助ツールです。使う前に、どの権限で何を実行するのかをリポジトリで直接確認してください。

外部ツールを Codex につなぐ公式の経路は MCP です。Codex は config.toml の [mcp_servers.名前] テーブルと codex mcp コマンドで MCP サーバーに接続するよう文書化されており、Claude Code の MCP エコシステムと同じ標準の上で比較できます。

8. 結論 - 誰が使い、誰が見送るべきか

よく合う人:

  • 移行・大規模リファクタリングの頻度が高いシニア開発者
  • レガシーコードベースをモダンに移行する必要があるチームリード
  • 一人で複数のリポジトリを管理するインフラ運用者

当面は見送る人:

  • 単発の関数作成が中心のジュニア(過剰なツール・学習機会の減少)
  • テストコードがほとんどないリポジトリ(完了を判定する手段がない)
  • ネットワーク分離・セキュリティ規制で外部 AI の利用が遮断された環境

当時の見通し(2026年5月):Codex Goals と Claude Code task の機能差は次第に縮まり、選択の決め手は「機能」より「価格ポリシーの安定性」になる可能性が高いと見ていました。2026-09-29 時点で見ると、Goals は5月21日に既定の機能となり、Codex アプリは ChatGPT デスクトップアプリに統合されました。Codex も ChatGPT のプランに含まれる形で使うのが基本であり、当時書いた「定額制対従量制」という構図は正確ではありませんでした。

最後に、どのツールを選ぶにしても「検証基準を自分で設計できる力」が最も重要です。公式ドキュメントが良い目標の要素として結果・検証手段・制約・範囲を先に挙げているのも同じ理由です。ツールが自律的に動くほど、人の役割は「指示」から「完了基準の設計」へ移っていきます。モデルを切り替えるときに既存の指示文がそのまま通用しない問題は 設定をそのまま引き継ぐと起きること で別途扱いました。

  • 予算上限の設定方法や目標数の制限が公式ドキュメントに記載されたとき
  • Codex を使える ChatGPT のプラン構成が変わったとき
  • ChatGPT デスクトップアプリや Codex の製品名が再び変わるか統合されたとき

# Codex Goals チェックリスト - 目標をかける前に確認すること

基準日:2026-09-29。
以下の値は OpenAI 公式ドキュメント(Cookbook「Using Goals in Codex」、「Follow a goal」、ChatGPT デスクトップアプリのスラッシュコマンドドキュメント、Codex MCP ドキュメント)と openai/codex GitHub リリースノート・README で確認したものです。価格は記載していません。

## 1. コマンドと設定

| やりたいこと | コマンド・設定 | 備考 |
|---|---|---|
| 目標を設定 | `/goal <目標>` | 公式の例:`/goal Finish the migration and keep tests green` |
| 現在の目標を表示 | `/goal` | |
| 一時停止 / 再開 / 解除 | `/goal pause` / `/goal resume` / `/goal clear` | |
| `/goal` が一覧にないとき | `config.toml` に `features.goals = true`、または `codex features enable goals` | 0.133.0 から既定で有効 |
| 外部ツールの接続 | `config.toml` の `[mcp_servers.名前]` テーブル、`codex mcp` コマンド | MCP |

## 2. バージョンと提供環境

| 項目 | 確認できた内容 |
|---|---|

## 3. 目標の文のチェックリスト(公式推奨の6要素)

- [ ] **結果(Outcome)**:終わったときに何が成り立っているべきかを一文で書いた
- [ ] **検証手段(Verification surface)**:それを証明するテスト・ベンチマーク・コマンド出力・レポートを指定した
- [ ] **制約(Constraints)**:作業中に後退してはならないもの(既存テストの通過など)を書いた
- [ ] **範囲(Boundaries)**:使ってよいファイル・ツール・リポジトリを書いた
- [ ] **反復方針(Iteration policy)**:各試行の後に次の試行をどう決めるかを書いた
- [ ] **行き詰まり時の停止条件(Blocked stop condition)**:打つ手がなくなったら止まって報告するよう書いた

## 4. 始める前の点検

- [ ] リポジトリに最低限の統合テストか測定コマンドがある(なければ完了を判定できない)
- [ ] 新しいブランチで始める
- [ ] API キーや DB パスワードがコードに平文で入っていない(.gitignore・環境変数を確認)
- [ ] セキュリティレビューが必要な部分は目標から外した
- [ ] この作業に使う予算を先に決めた(予算上限は公式ドキュメントが挙げる停止条件のひとつ)

## 5. 止まる条件(公式ドキュメント)

| 条件 | 意味 |
|---|---|
| 成功 | 目標を達成 |
| 一時停止 / 解除 | ユーザーが `/goal pause` または `/goal clear` |
| 中断 | 実行が中断された |
| 予算上限 | 決められた予算に到達 |
| 行き詰まり | ユーザー入力が必要な状況 |

別のターンが進行中のとき、ユーザー入力が待機中のとき、スレッドの他の作業が残っているときは続行しません。

## 6. 合う作業 / 合わない作業

| 合う作業 | 合わない作業 |
|---|---|
| ゴールラインは明確で道筋が不確かな作業 | 「何をもって終わりとするか」を言えない作業 |
| レガシー API の移行、型カバレッジの引き上げ | 「コードベース全体をきれいに」のような広い目標 |
| 性能改善、不安定なテストの再現 | テストがほとんどないリポジトリ |
