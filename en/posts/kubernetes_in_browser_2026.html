Porting Kubernetes to the Browser — What the "WASM Experiment" Really Reveals

ngrok's Webernetes actually skipped WASM — what that twist tells us about where browser runtimes really stand

Jul 3, 2026 Dev & Infra

Introduction: Why "Kubernetes running in a browser" sounds so strange

Kubernetes was built for server clusters, full stop. Its job is scheduling containers across dozens to thousands of machines, wiring up networking, and detecting dead nodes so it can reschedule pods elsewhere. So the sentence "it runs inside a browser tab" sounds intuitively wrong - a browser has no fleet of machines, no real Linux kernel, no actual container runtime.

In June 2026, ngrok's engineering team made exactly that sentence real with a project called Webernetes, and it made the rounds in developer circles - including a short but interesting thread on GeekNews. This piece has two goals. First, lay out precisely what the project did and did not do, without the hype. Second, weigh how well the framing "a new WASM experiment" actually fits this case, and place it accurately within the bigger trend of browsers becoming universal runtimes. As of July 2026, here's where that experiment actually stands, and what remains unproven.

1. What Webernetes actually is - ngrok's experiment

Webernetes reimplements Kubernetes' core concepts - pods, nodes, the scheduler, ReplicaSet/Deployment controllers, Services, and kube-proxy-equivalent logic - in TypeScript so they run entirely in the browser. It spins up a fixed three-node virtual cluster in browser memory and visually shows pods being scheduled and traffic being routed through services, just like the real thing conceptually behaves.

The scale is not trivial. Roughly 100,000 lines of code were written over two months, validated with 204 integration tests that compare behavior against a real k3s cluster plus 1,855 unit tests. It also exposes an API compatible with the kubernetes-client JavaScript library, so existing tooling knowledge carries over. The stated purpose is explicitly interactive Kubernetes education content, and ngrok shipped a public demo site alongside the code.

2. The twist - this is not a WASM port

This is the core of the piece. A headline like "ported Kubernetes to the browser" makes almost everyone assume real binaries were compiled to WebAssembly. That was my first assumption too. Checking the primary source told a different story.

2.1 The author answers this directly

The original ngrok blog post literally poses the question "Did you compile Kubernetes to WebAssembly?" and answers it: "The answer is no." Webernetes did not compile Kubernetes' real Go binaries (kube-apiserver, kubelet, the scheduler, and so on) to WASM. It selectively reimplemented the Go codebase's behavior in TypeScript instead.

2.2 Why WASM got dropped - a plain bundle-size problem

The reason is unromantic and practical. According to the author's own experiment, even a bare hello-world WASM build weighed about 540KiB, while the entire TypeScript-based Webernetes came in around 140KiB. Wanting something that loads instantly and stays lightweight in the browser, WASM compilation simply didn't fit the project's actual goals - interactive demos, fast loads.

2.3 So what did they actually build? Go concurrency, reimplemented in JavaScript

Instead, the author built a runtime layer that mimics Go-specific concurrency patterns - channels, mutexes, select statements - on top of JavaScript. A portion of the kubelet binary, the pod scheduler, the namespace controller, kube-proxy-equivalent logic, and even a browser-native virtual CNI (container network interface) and container runtime were all rewritten this way. The result is less "Kubernetes moved to WASM" and more "Kubernetes' behavioral model ported into the JavaScript world."

3. Why this experiment still belongs to the "browser runtime" trend

Just because Webernetes itself skips WASM doesn't mean it's disconnected from the trend of browsers becoming universal runtimes. If anything, this case shows how wide that trend actually is.

3.1 Real WASM examples - the browser is already doing heavy lifting

Chrome usage data put WASM at roughly 5.5% of page loads in early 2026. Figma's rendering engine, web Photoshop, web AutoCAD, and parts of Google Meet's video processing genuinely run on WASM today. I covered a similar lineage previously in a WASM recompilation project that ran Pokémon Emerald at 100,000 FPS in the browser. The more direct comparison is StackBlitz's WebContainers, which actually build a WASM-based virtual OS - complete with a filesystem and a virtualized TCP stack - to run a full Node.js server inside the browser. Where Webernetes decided "we don't need WASM for this," WebContainers decided "we need WASM for a proper OS abstraction." Two different answers to essentially the same goal: running server software in the browser.

3.2 WASM plus Kubernetes on the server side - the opposite direction

Interestingly, the more common context where "WASM" and "Kubernetes" appear together runs in the opposite direction. Projects like SpinKube and Kube-Wasm aim to schedule WASM workloads natively inside Kubernetes clusters, on servers. So "bringing Kubernetes to the browser" (Webernetes) and "bringing WASM to Kubernetes clusters" (SpinKube-style projects) point in completely opposite directions. Both, however, start from the same underlying question: what lighter, more portable execution unit can replace the heavy isolation boundary of a container?

3.3 Where the two currents actually meet

My read is this: Webernetes isn't a product of WASM technology itself, but it's an experiment that could only be attempted on top of a premise WASM has spent years proving - that the browser is now a genuine execution environment, not a document viewer. Only because JavaScript engines got fast enough and memory models flexible enough could someone even attempt to fake Go's concurrency model in pure TypeScript. Read that way, "a new WASM experiment" doesn't mean Webernetes used WASM directly - it means the "browser as universal runtime" era that WASM helped usher in is what made this kind of experiment thinkable at all.

4. Real value in education, demos, and local development

4.1 How it differs from existing browser-based K8s learning tools

Learning Kubernetes through a browser wasn't new. Services like Killercoda or Docker's Play with Kubernetes let you log in and get a free, real Linux/Kubernetes environment for about 60 minutes. But those only let you "connect" through the browser - a remote VM or container does the actual work behind the scenes. Webernetes has no server at all. Close the tab and the cluster is gone; backend cost is zero. That difference matters: there's no server scaling to worry about no matter how much traffic hits the page, and it can be embedded directly into docs or blog posts.

4.2 Where it actually fits

Three use cases fit best. First, onboarding training where new hires can watch "how does a pod get scheduled" happen with a few clicks rather than reading a diagram. Second, embedding a live, interactive demo directly in technical docs or a conference talk so the audience can poke at it on the spot. Third, a zero-install entry point for beginners who don't want the friction of installing minikube or kind just to grasp the concepts. It's clearly the wrong tool for deploying real applications, load testing, or validating network policies.

To avoid anyone mistaking Webernetes for a Kubernetes replacement, here's the boundary spelled out plainly.

To sum up: Webernetes never runs real container images, and it lacks ConfigMaps, Secrets, persistent volumes, init/ephemeral containers, and affinity rules. Service types are limited to ClusterIP and NodePort; LoadBalancer and ExternalName are absent. Nodes are fixed at three virtual nodes. It's a visualization tool for how Kubernetes concepts behave, not a deployment platform that replaces Kubernetes. Blurring that line invites disappointment when a teaching tool is held to production expectations.

6. LLM-written code, reviewed line by line by a human

The part of this project I personally found most interesting isn't the technology - it's the development process. The author states most of the code was written by an LLM, while stressing that every single line was manually reviewed. The recurring failure patterns will sound familiar: collapsing a proper data structure (like an LRU cache) into a plain Map, inventing helper functions that don't exist in the original Go code, and quietly dropping test cases. The author's conclusion is blunt: "you can only trust LLM-generated code if you pair it with review and tests."

This lines up almost exactly with a point I keep making in my comparison of AI coding tools. Finishing a 100,000-line project in two months is impressive, but the speed didn't come from the LLM simply writing good code on its own - it came from pairing that generation with 204 integration tests, 1,855 unit tests, and 100% manual code review as verification infrastructure running in parallel. The real lesson here isn't "an LLM wrote it" - it's "how rigorously it was verified."

7. A practitioner's angle - where this is actually worth trying

Demand for introductory Kubernetes training isn't going away anywhere, and installing minikube or kind locally for onboarding, bootcamps, or workshop sessions frequently runs into corporate security policies that block Docker installs, or laptops that simply can't handle it. Browser simulators in the Webernetes vein remove that installation barrier entirely, which is genuinely attractive. That said, if a team is considering building something similar, take the "100,000 lines, two months" headline with a grain of salt and factor in the nearly 2,000 tests and full manual review that made it trustworthy. An LLM cutting drafting time is real; it does not cut verification cost.

Conclusion: what to take from a browser experiment that imitates a server

Contrary to the "ported Kubernetes to the browser with WASM" impression a headline might give, Webernetes is a TypeScript reimplementation that deliberately skips WASM. That twist isn't a flaw - it's a more useful lesson than a straightforward WASM port would have been. There is more than one path to using the browser as a universal runtime. WebContainers takes the path of faking a real OS with WASM; Webernetes takes the path of reimplementing only what's needed in a lightweight language. Both share the same 2026 premise: the browser can now run essentially anything. The next time you see a headline claiming "X ported to the browser," it's worth checking exactly what got compiled - a real binary, or a reimplementation. That detail is usually where the more interesting story lives.
