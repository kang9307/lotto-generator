Slumber - 레시피 기반 터미널 HTTP/REST 클라이언트, Postman 대안 2026

YAML로 요청을 정의하고 터미널에서 실행하는, 가볍고 Git 친화적인 API 클라이언트

2026-06-11 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: API를 다루는 또 하나의 방식

API를 호출하는 도구는 이미 차고 넘칩니다. 무거운 GUI 플랫폼인 Postman과 Insomnia, 한 줄짜리 명령의 왕인 curl, 사람이 읽기 좋은 출력으로 사랑받는 HTTPie까지. 그런데 2026년 6월 개발자 커뮤니티에서 또 하나의 선택지가 화제가 되었습니다. 바로 Slumber입니다. Rust로 작성된 터미널 기반 HTTP/REST 클라이언트로, 요청을 YAML 레시피(recipe)로 정의한다는 점이 가장 큰 특징입니다.

"또 하나의 HTTP 클라이언트가 왜 필요한가"라는 질문은 정당합니다. 이 글은 Slumber가 메우는 빈틈이 어디인지를 차분히 짚습니다. 결론을 먼저 말하면, Slumber의 핵심 가치는 '속도'나 '예쁜 출력'이 아니라 요청을 코드처럼 다루는 워크플로에 있습니다. GUI에 갇히지 않고, 그렇다고 매번 긴 curl 명령을 손으로 조립하지도 않는, 그 중간 지대를 노리는 도구입니다. 공식 소개에 따르면 Slumber의 목표는 "쓰기 쉽고, 설정 가능하며, 공유 가능한" HTTP 클라이언트입니다.

1. 터미널 HTTP 클라이언트란 무엇인가

본론에 앞서 용어를 정리하겠습니다. 터미널 HTTP 클라이언트는 마우스로 클릭하는 그래픽 화면 대신, 키보드와 텍스트로 HTTP 요청을 만들고 보내는 도구를 말합니다. 크게 두 갈래가 있습니다.

  • CLI(명령줄 인터페이스): curl https://api.example.com/users처럼 한 줄 명령으로 요청을 보냅니다. 스크립트·자동화에 강합니다.
  • TUI(터미널 사용자 인터페이스): 터미널 안에서 메뉴·패널·목록이 있는 대화형 화면을 띄웁니다. GUI의 편의성과 터미널의 가벼움을 절충합니다.

Slumber가 흥미로운 이유는 이 둘을 모두 제공한다는 점입니다. 대화형으로 요청을 탐색하고 응답을 살필 때는 TUI를, 스크립트나 CI에서 자동으로 호출할 때는 CLI를 씁니다. 게다가 Python 패키지로도 제공되어 코드 안에서 직접 호출할 수도 있습니다. 하나의 컬렉션(요청 모음)을 세 가지 인터페이스가 공유한다는 설계가 Slumber의 정체성입니다.

2. Slumber의 핵심 개념 - 컬렉션, 레시피, 프로파일

Slumber를 이해하는 가장 빠른 길은 세 가지 개념을 잡는 것입니다.

  • 컬렉션(Collection): 보통 slumber.yml 파일 하나에 담기는, 요청 레시피들의 묶음입니다. 프로젝트 리포지토리에 함께 커밋하는 단위입니다.
  • 레시피(Recipe): 실행할 개별 요청의 템플릿입니다. 메서드·URL·헤더·바디·쿼리를 정의합니다. '사용자 목록 조회', '주문 생성' 같은 요청 하나하나가 레시피입니다.
  • 프로파일(Profile): 환경별 변수 집합입니다. 로컬·스테이징·운영처럼 호스트나 토큰이 다른 환경을 손쉽게 전환하게 해 줍니다.

이 세 개념이 맞물리면, 한 벌의 레시피를 작성해 두고 프로파일만 바꿔 가며 여러 환경에서 같은 요청을 재사용할 수 있습니다. GUI 도구에서 환경 변수를 화면으로 관리하던 일을, Slumber는 텍스트 파일에서 처리합니다.

3. 첫 컬렉션 만들기 - slumber.yml 예시

백문이 불여일견입니다. 공식 문서의 예시를 바탕으로 한 간단한 컬렉션을 보겠습니다. 가상의 '물고기' API를 다루는 컬렉션입니다.

# slumber.yml
profiles:
  local:
    data:
      host: http://localhost:5000
  production:
    data:
      host: https://myfishes.fish

requests:
  list_fish:
    method: GET
    url: "{{ host }}/fishes"
    query:
      big: true

  create_fish:
    method: POST
    url: "{{ host }}/fishes"
    body:
      type: json
      data: { "kind": "barracuda", "name": "Jimmy" }

읽어 보면 의도가 명확합니다. profiles 아래 local과 production이 각각 host 변수를 다르게 정의합니다. requests 아래의 레시피들은 {{ host }} 템플릿으로 그 변수를 참조합니다. 프로파일만 바꾸면 같은 list_fish 요청이 로컬과 운영을 오갑니다. 헤더가 길고 따옴표 탈출이 지저분한 curl 한 줄과 비교하면, 구조가 한눈에 들어옵니다.

4. TUI와 CLI - 두 가지 사용 방식

컬렉션을 만들었다면 실행할 차례입니다. Slumber는 두 가지 방식을 제공합니다.

4.1 TUI: 대화형 탐색

컬렉션이 있는 디렉터리에서 slumber를 실행하면 TUI가 뜹니다. 왼쪽에 레시피 목록, 가운데에 요청 상세, 오른쪽에 응답이 배치되는 식의 대화형 화면에서 키보드로 요청을 골라 보내고, 응답을 바로 살펴봅니다. 응답 탐색에는 JSONPath 셀렉터가 내장되어 있어, jq처럼 큰 JSON 응답에서 원하는 필드만 골라 볼 수 있습니다.

4.2 CLI: 스크립트와 자동화

대화형이 필요 없을 때는 CLI로 곧장 실행합니다. 예를 들어 특정 레시피를 비대화형으로 보내는 식입니다.

# 새 컬렉션 생성
slumber new

# TUI 실행 (현재 디렉터리의 slumber.yml 사용)
slumber

# 특정 레시피를 CLI로 실행 (프로파일 지정)
slumber request list_fish --profile production

CLI 모드 덕분에 Slumber 요청을 셸 스크립트나 CI 단계에 끼워 넣을 수 있습니다. 응답을 표준 출력으로 받아 다른 명령에 파이프하는, 전형적인 유닉스식 조합이 가능합니다. (명령 이름·옵션의 정확한 형태는 버전에 따라 다를 수 있으니 slumber --help로 확인하시기 바랍니다.)

5. 동적 요청 - 템플릿, 파일, 셸, 이전 응답

Slumber가 단순한 '정적 요청 저장소'를 넘어서는 지점이 바로 동적 요청 구성입니다. 소개에 따르면 Slumber는 요청을 다음 소스들로부터 동적으로 조립합니다.

  • 템플릿 변수: 프로파일 데이터를 {{ host }}처럼 끼워 넣습니다.
  • 파일: 외부 파일 내용을 바디나 헤더로 불러옵니다. 큰 페이로드나 인증서 같은 값에 유용합니다.
  • 셸 명령: 셸 명령의 출력을 값으로 씁니다. 예컨대 토큰 생성기를 호출해 그 결과를 헤더에 넣습니다.
  • 이전 응답: 앞선 요청의 응답에서 값을 뽑아 다음 요청에 넘깁니다. 로그인 → 토큰 획득 → 인증 요청 같은 체인이 가능합니다.
  • 프롬프트: 실행 시점에 사용자에게 값을 물어봅니다.

이 '이전 응답에서 값 끌어오기'가 실무에서 특히 강력합니다. 인증이 필요한 API를 다룰 때, 로그인 요청의 응답에서 토큰을 추출해 후속 요청 헤더에 자동으로 넣는 흐름을 레시피로 굳혀 둘 수 있습니다. Postman의 '환경 변수 + 테스트 스크립트' 조합으로 하던 일을, Slumber는 선언적 설정으로 표현합니다.

6. Git 친화 - 설정을 코드로 다룬다는 것

Slumber의 철학을 한 단어로 요약하면 "소스 우선(source-first) 설정"입니다. 모든 설정과 데이터가 로컬의 일반 텍스트 YAML로 존재하므로, 자연스럽게 다음 이점이 따라옵니다.

  • 버전 관리: slumber.yml을 Git에 커밋하면 API 요청의 변경 이력이 코드 이력과 함께 남습니다. 누가 언제 엔드포인트를 바꿨는지 git blame으로 추적됩니다.
  • 코드 리뷰: 새 엔드포인트 추가나 요청 변경을 PR에서 diff로 리뷰할 수 있습니다. GUI 클릭으로는 불가능한 일입니다.
  • 공유: 리포지토리를 클론한 동료는 별도 계정·클라우드 동기화 없이 같은 컬렉션을 즉시 사용합니다.
  • 재사용: 프로젝트 간에 레시피를 복사·참조해 표준 요청을 재활용합니다.
API 클라이언트의 설정이 클라우드 계정 뒤가 아니라 리포지토리 안에 있을 때, 그 설정은 비로소 코드베이스의 일부가 된다.

이 지점이 무거운 GUI 도구를 쓰며 느끼던 미묘한 불편 — 설정이 도구 안에 갇혀 팀과 동기화되지 않는 문제 — 를 정면으로 해결합니다.

7. 다른 형식에서 가져오기 - Insomnia, OpenAPI 등

이미 다른 도구로 만든 컬렉션이 있다면 처음부터 다시 짤 필요는 없습니다. 소개에 따르면 Slumber는 여러 외부 형식의 임포트를 지원합니다.

  • Insomnia 컬렉션
  • OpenAPI 명세
  • VSCode .rest 파일
  • JetBrains .http 컬렉션

특히 OpenAPI 임포트는 의미가 큽니다. 잘 정의된 API 명세가 있다면 그것을 출발점 삼아 Slumber 레시피를 생성할 수 있어, 기존 자산을 버리지 않고 새로운 워크플로로 옮겨올 수 있습니다.

8. Postman·Insomnia·curl·HTTPie와 비교

이제 본격적인 비교입니다. Slumber의 자리를 다른 도구들 사이에서 가늠해 보겠습니다.

도구 인터페이스 설정 방식 강점 약점
Slumber TUI + CLI YAML 파일 가벼움, Git 친화, 환경 전환 비교적 새 도구, GUI 협업 없음
Postman GUI 클라우드/계정 풍부한 협업·테스트·모니터링 무거움, 계정 의존, 버전 관리 약함
Insomnia GUI GUI/파일 깔끔한 UI, 플러그인 여전히 GUI 중심
curl CLI 명령 인자 어디에나 있음, 즉석 호출 반복·구조화엔 번거로움
HTTPie CLI 명령 인자 사람이 읽기 좋은 출력 컬렉션·환경 관리는 약함

표를 보면 경쟁이 1:1이 아니라는 점이 드러납니다. Slumber는 curl을 완전히 대체하지 않습니다. 즉석으로 한 번 보내고 끝낼 요청에는 여전히 curl이 빠릅니다. 반대로 Postman의 팀 협업·모니터링·목 서버 같은 플랫폼 기능도 대체하지 않습니다. Slumber가 정확히 노리는 자리는 "여러 엔드포인트를 반복적으로 다루되, GUI 플랫폼의 무게는 지고 싶지 않은" 개발자의 일상 워크플로입니다.

9. curl 명령과 레시피의 관계

흥미로운 점은 Slumber 레시피와 curl 명령이 대립이 아니라 보완 관계라는 것입니다. 같은 요청을 두 방식으로 적어 보면 차이가 분명합니다.

# curl 한 줄 (즉석 호출에 좋음)
curl -X POST https://myfishes.fish/fishes \
  -H "Content-Type: application/json" \
  -d '{"kind":"barracuda","name":"Jimmy"}'

위 curl 명령은 빠르지만, 헤더가 늘고 환경이 여러 개가 되는 순간 손으로 관리하기 번거로워집니다. 같은 요청을 Slumber 레시피로 굳혀 두면 환경 전환과 재실행이 깔끔해집니다. 실제로 우리 사이트의 curl 명령어 빌더 같은 도구로 일회성 요청을 빠르게 조립한 뒤, 반복해서 쓸 요청만 Slumber 컬렉션으로 옮겨 정리하는 방식이 잘 어울립니다. 즉석 조립은 빌더와 curl로, 반복·구조화는 Slumber로 나누는 것입니다.

10. 활용 시나리오 - API 테스트, CI, 문서화

Slumber가 실제로 빛을 발하는 장면들을 정리하겠습니다.

10.1 일상 API 디버깅

개발 중인 API를 손으로 두드려 볼 때, 레시피로 정의된 요청들을 TUI에서 골라 보내고 응답을 JSONPath로 살핍니다. curl보다 친절하고 Postman보다 가볍습니다.

10.2 CI 회귀·스모크 테스트

같은 YAML 컬렉션을 CI에서 CLI로 실행해, 배포 후 핵심 엔드포인트가 살아 있는지 확인하는 스모크 테스트를 돌립니다. 개발 때 쓰던 요청 정의를 그대로 검증에 재사용한다는 점이 큰 이점입니다.

10.3 살아 있는 API 문서

slumber.yml 자체가 '이 API를 어떻게 호출하는가'에 대한 실행 가능한 문서가 됩니다. README의 박제된 curl 예시와 달리, 리포지토리의 레시피는 실제로 실행되므로 낡을 일이 적습니다.

10.4 스크립트 통합

셸 스크립트에서 slumber request를 호출해 요청 결과를 후속 처리에 넘깁니다. 동적 요청 기능과 결합하면 토큰 발급·체이닝 같은 복잡한 흐름도 스크립트로 자동화됩니다.

11. 한계와 주의점

균형을 위해 그늘도 분명히 짚겠습니다. Slumber는 만능이 아닙니다.

  • 성숙도: 공식 안내에 따르면 Slumber는 비교적 새로운 도구로, 기능이 아직 완전히 갖춰진 단계는 아닙니다. 명령·설정의 세부 형태가 버전에 따라 바뀔 수 있으니 공식 문서를 기준으로 삼아야 합니다.
  • GUI 협업 부재: Postman식 팀 워크스페이스, 목 서버, 모니터링, 시각적 테스트 러너는 없습니다. 비개발 직군과 협업하거나 비기술 이해관계자에게 공유해야 한다면 GUI 도구가 더 맞습니다.
  • 학습 곡선: YAML과 터미널에 익숙하지 않다면 초기 진입이 GUI보다 가파를 수 있습니다. 다만 한 번 익히면 반복 작업에서 회수됩니다.
  • 적합한 자리: 즉석 한 줄 호출은 curl/HTTPie가, 거대한 협업 플랫폼은 Postman이 낫습니다. Slumber는 그 사이, '코드처럼 다루는 반복 API 워크플로'에 최적입니다.

12. 결론 + 즉시 적용 가능한 3가지

Slumber를 한 문장으로 요약하면 이렇습니다. "요청을 YAML 레시피로 정의해 Git으로 관리하고, TUI와 CLI로 실행하는, 가볍고 공유 가능한 터미널 HTTP 클라이언트"입니다. 풍부한 GUI 협업이 필요하면 Postman이, 즉석 한 줄이면 curl이 낫지만, 그 둘 사이에서 반복적인 API 워크플로를 코드처럼 다루고 싶다면 Slumber는 매우 합리적인 선택입니다.

당장 시도해 볼 수 있는 세 가지로 마무리합니다.

  1. 자주 쓰는 요청 3개를 레시피로 옮겨라. 매번 손으로 치던 curl 명령 중 반복도가 높은 셋을 골라 slumber.yml에 적어 보세요. 작은 컬렉션 하나가 워크플로의 체감을 바꿉니다.
  2. 환경을 프로파일로 분리하라. 로컬·스테이징·운영 호스트를 프로파일로 나눠 두면, 환경을 헷갈려 엉뚱한 서버에 요청을 날리는 실수를 구조적으로 막을 수 있습니다.
  3. 컬렉션을 리포지토리에 커밋하라. slumber.yml을 코드와 함께 커밋해 두면 API 호출 방식이 곧 살아 있는 문서가 되고, 동료는 클론만으로 같은 요청을 즉시 재현합니다.

마지막으로 강조하고 싶은 메시지는 이것입니다. 좋은 도구는 새로운 기능을 더하기보다, 흩어진 작업을 올바른 자리로 옮겨 줍니다. Slumber는 GUI에 갇혀 있던 API 요청 설정을 리포지토리로, 즉 코드의 자리로 되돌립니다. 터미널을 즐기고 설정을 코드처럼 다루고 싶은 개발자라면, 한 번쯤 진지하게 시험해 볼 가치가 있습니다.
