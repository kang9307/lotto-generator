序論: ターミナルがIDEになろうとする発想

GeekNews(hada.io)でomp(oh-my-pi)を初めて見たとき、抱いた感情は懐疑だった。Claude Code、OpenAI Codex CLI、Aiderがすでに定着したターミナルコーディングエージェント市場に、また一つ加わっただけに見えたからだ。ところが紹介を読むと角度が違った。ompは新しいエージェントをゼロから作ったのではなく、Mario Zechnerが作った極端にミニマルなコーディングエージェントPiをフォークして正反対の方向へ突き進めた。Piがツールを最大限に省いて小さくする実験だったなら、ompはターミナルがIDEのように動くまでツールを足し続ける実験だ。

本稿はompの機能紹介ではなく、その発想そのものを検証する文章だ。ターミナルコーディングエージェントという地形がなぜこれほど混み合ったのか、ompがPiから何を継承し何をひっくり返したのか、LSP・デバッガー・Hashline編集という差別化点が実際にどんな問題を解くのか、そして何より日本の開発者がClaude Code・Codex CLIのようなベンダー製品の代わりにompを実務に入れる理由があるのかを冷静に問う。先日扱ったローカルLLMエージェント開発とツール検索・HITL、AIコーディングセッションの揮発的コンテキストをプロジェクトの記憶に残すも、結局は同じ問いの別の側面だった。ompはその問いに「ターミナル一つで全部やろう」と答える。

1. ompとは - Piから派生したバッテリー同梱のターミナルエージェント

ompはcan1357/oh-my-piリポジトリにMITライセンスで公開されたオープンソースプロジェクトだ。インストールはmacOS・Linuxでcurl -fsSL https://omp.sh/install | shの一行、あるいはBun経由のnpmパッケージ(@oh-my-pi/pi-coding-agent)で終わる。WindowsではWSLなしでネイティブバイナリとして動くと明記されている。実行すると、ターミナルの中でコードベースを読み、編集し、実行し、デバッグするエージェントが立ち上がる。

1.1 コア仕様

ompは重い処理を担うネイティブなRustエンジンの上にTypeScriptの拡張層を載せた構成だ。公開資料によれば32個の内蔵ツール(read/write/edit/bash/eval/lsp/debug/browser/web_search/githubなど)、14個のLSP操作、28個のDAP(デバッガー)操作を備え、40以上のモデルプロバイダーに接続する。さらにサブエージェントのオーケストレーション、プランモード、スラッシュコマンド、拡張(プラグイン)システムまで標準搭載する。一言で言えば「箱を開けたらすでに全部入っている」ことを目指す。

1.2 Piとの関係 - 同じコア、逆の哲学

ompを理解する鍵は源流のPiにある。Piはbadlogic/pi-monoモノレポにあるミニマルなハーネスで、モデルにファイル読み・書き・編集・シェル実行というたった4つのツールと1000トークン未満の短いシステムプロンプトだけを与え、残りはユーザーがTypeScript拡張で自分で付けるよう委ねる。「何を省くかが何を入れるかより重要だ」という哲学だ。ompはまさにその逆で、同じコアから出発しながら、ターミナルがIDEのように感じられるまでツールを足す方を選んだ。二つのプロジェクトは競争というより、一つのミニマルなコアが両極端へ伸びた事例と見るのが正確だ。

1.3 急成長するリポジトリ

ompは公開後の短期間でコミュニティの関心を大きく集めた。2026年7月時点でGitHubスターは約1万9千前後で、フォークや貢献者も活発だ。ただしこの数字は変わり続けるスナップショットである点を踏まえるべきだ。いくつかの紹介記事が時点によって5千、1万7千、1万9千と異なる数値を引用するのもこのためだ。スター数そのものより重要なのは、このプロジェクトが「デモ用プロンプトではなく実用ツール」を掲げ、素早くツールを増やしてきた方向性だ。

2. ターミナルコーディングエージェントの地形 - なぜこれほど混むのか

ompがなぜ出てきたかを理解するには、まずターミナルコーディングエージェントというカテゴリー自体を見る必要がある。2025〜2026年にかけて、この領域は急速に混み合った。

2.1 三つの代表格

代表格をざっくり分けるとこうだ。Claude CodeはAnthropicのベンダー製品で、モデルとエージェントが緊密に結合され、安定性と完成度が高い。OpenAI Codex CLIはOpenAI系モデルをターミナルで扱う公式ツールだ。AiderはPythonベースの歴史あるオープンソースで、gitコミット単位の編集とdiffワークフローに強く、モデル選択が自由だ。ompはこの系譜で「オープンソースの開放性はAider側、完成度志向はベンダー側」という二つの軸の間に食い込む。

2.2 なぜよりによってターミナルなのか

IDEプラグインやWeb UIではなくターミナルを表面に選ぶ理由は明確だ。ターミナルはすでに開発者の作業フローの真ん中にあり、SSH・CI・サーバー環境のどこでも同じように動き、シェル・git・ビルドツールと自然に絡む。問題は、ターミナルが本来コードの意味を理解しない点だ。テキストをやり取りするだけで、シンボルがどこで定義され参照されるのか、実行中の変数の値が何なのかは知らない。ompの核心的な賭けはまさにこの隙間、つまり「ターミナルにIDEの理解力を移植する」ことにある。

3. ompの三つの差別化点

ompが他のターミナルエージェントと分かれる点は三つに整理できる。

3.1 Hashline編集 - ハッシュでアンカリングした編集

ターミナルエージェントの慢性的な弱点は、意外にもファイル編集そのものだ。モデルが生成したdiffや文字列置換は、空白一つ、改行一つずれただけでパッチが丸ごと失敗する。ompのHashlineは編集対象の行を内容ハッシュでアンカリングし、位置を正確に特定する編集フォーマットだ。リポジトリが提示するベンチマークによれば、従来のdiffに比べて編集成功率が大きく上がり、出力トークンも相当減るという(具体的な数値はモデルや条件によって異なって提示される)。ただしこの数値はリポジトリ自身の測定である点を明確にすべきだ。編集の信頼性は実使用での体感が大きい指標なので、自分のコードベースで再検証する方が安全だ。

3.2 LSP・DAP・ブラウザ - ガラス越しにコードを見るのを超えて

ompが「IDE級」を自称する根拠がここにある。LSP(Language Server Protocol)を付けて定義へのジャンプ、参照検索、シンボル単位のリネームといった意味的操作を行う。テキスト置換ではなく、言語サーバーが理解した構造の上でリファクタリングするという意味だ。さらにDAP(Debug Adapter Protocol)を載せてブレークポイントを張り、変数やスタックトレースを実際に覗く実デバッグを支援する。print文をばらまく方式ではない。ブラウザ自動化まで含めて、「コードをガラス越しに眺めていた」テキストエージェントを意味的操作ツールへ引き上げようとする試みだ。

3.3 Hindsightの横断セッション記憶とサブエージェント

セッションが終わるとコンテキストが揮発するのは、すべてのコーディングエージェントに共通する弱点だ。ompのHindsightは実行中に事実を残し(retain)、後で呼び出す(recall)横断セッション記憶システムで、プロジェクト構造への理解が会話の間に保たれるようにする。これはAIコーディングセッションの揮発的コンテキストをプロジェクトの記憶に残すで指摘した問題意識とちょうど重なる。またサブエージェントを並列で立ち上げ、スキーマで検証されたJSON結果を受け取り、ワークスペースを隔離するオーケストレーションも標準で支援する。大きな作業を分割して複数のワーカーに配るパターンだ。

4.1 どこで誰が勝つか

筆者の解釈はこうだ。完成度と公式サポートが最優先ならClaude CodeかCodex CLI、検証済みの安定性とgitワークフローが最優先ならAider、ベンダーロックインを避けつつIDE級のツールを自分で組み立てたい開発者ならompが魅力的な地形だ。三つの系統は代替関係というより、異なる優先順位に応える答えと見る方が正確だ。ompの真の差別化点は「ターミナルで意味的操作と実デバッグを、開放型のモデルルーティングとともに」という組み合わせそのものだ。

5. 実務導入の観点

ここから実務の角度に降りる。日本の開発組織や個人開発者がompを入れるとき、何が有利で何が障壁か。

5.1 導入が容易な点

インストールが単一バイナリなのでランタイム依存の地獄が少なく、WindowsでWSLなしにネイティブで動く点は、混在OS環境(社内Windows + サーバーLinux)で実質的な利点だ。40以上のプロバイダーをルーティングする開放性のおかげで、アクセスしやすいモデルや低価格・オープンウェイトのモデルを状況に合わせて付けたり外したりできる。特定ベンダーの料金体系に縛られないことは、コスト管理の観点でも有効だ。

5.2 チーム標準化の壁

逆に組織導入には摩擦がある。ツールの表面が広いということは、学習コストと設定管理の負担が大きいということでもある。ベンダー製品が提供するSSO、監査ログ、組織ポリシーの強制、公式技術サポートといったガバナンス要素は、まだコミュニティのオープンソースが埋めにくい領域だ。チーム全体が同じワークフローを共有しなければならない状況では、個人の自由度がかえって標準化の障壁になり得る。

5.3 権限とセキュリティの境界

ターミナルエージェントは本質的にシェルコマンド・ファイル書き込み・コード実行の権限を持つ。ompのようにツールが多く自動化が深いほど、レビューすべき権限のポイントも増える。自動承認モードを本番リポジトリや認証情報のある環境で無分別に有効化するのは危険だ。承認ゲート、サンドボックス、隔離されたワークスペースをまず設計し、ブラウザ自動化やgithubツールが届く範囲を明示的に制限すべきだ。

6. 長所・短所・限界

ompの発想は魅力的だが、冷静に見るべき限界も明らかだ。

6.1 成熟度と表面積のトレードオフ

「箱を開けたら全部入っている」ことは強みであり弱みでもある。ツールが32個、プロバイダーが40以上ということは、その分だけ保守・互換性・バグの表面が広いということだ。オープンなイシューが相当数ある点も、急成長するプロジェクトの自然な影だ。一方Piのようなミニマルなハーネスは表面が小さく予測可能だ。何をあらかじめ入れておくかの代償は、結局は複雑さだ。

6.2 ベンチマーク数値の帰属問題

Hashlineの編集成功率・トークン削減のような印象的な数値は、ほとんどがリポジトリ自身の測定だ。独立した第三者ベンチマークが十分に積み上がるまでは、この数字をマーケティングではなく実測として受け止めつつ、自分のワークロードで再現してみる態度が必要だ。特定モデル(例えば高速な小型モデル)の組み合わせで出た数値が、他のモデルでも同じである保証はない。

6.3 ベンダー製品に対するエコシステム・安定性

Claude CodeやCodex CLIはモデルとエージェントを同じチームが一緒に最適化し、公式ドキュメント・サポート・更新サイクルが安定している。ompは開放性と自由度を得る代わりに、この安定性・エコシステムを一部手放す。実験や個人プロジェクトにはその交換が有利だが、規制産業やSLAが絡むワークロードでは慎重であるべきだ。

7. 最近の流れとの接続 - ハーネスが製品になる時代

ompは最近の二つの流れと自然につながる。一つはローカルLLMエージェント開発で指摘した「ツール検索・HITL・権限境界」という実務の骨格だ。ompの広いツール表面とサブエージェントのオーケストレーションは、まさにこの骨格をどう設計するかの問題と重なる。もう一つはAIコーディングセッションのコンテキストをプロジェクトの記憶に残すで扱った揮発性コンテキストの問題であり、ompのHindsightがまさにその対応だ。興味深いのは、ompが「ハーネスそのものを製品として」扱う点だ。モデルが全体的に底上げされる局面で、差別化はモデルではなくモデルを包むツール層から出るという見方であり、これはomp独自の主張ではなく、このカテゴリー全体が向かう方向でもある。

8. 導入前チェックリスト

ompであれ類似のターミナルエージェントであれ、導入前に最低限、以下の四つは確認すべきだ。

  • 権限の境界 - シェル・ファイル書き込み・コード実行の権限がどこまで自動的に許可されるか、自動承認と手動承認の境界をどう引くかをまず決める。本番リポジトリと実験リポジトリを分離せよ。
  • 編集の信頼性 - Hashlineの編集成功率を自分のコードベースで再現してみる。言語・プロジェクト規模によって体感が異なり得る。
  • モデルルーティングとコスト - 40以上のプロバイダーのうち実際に使う組み合わせを決め、プロバイダーごとのデータ処理ポリシーとプロンプトの学習再利用の有無を確認する。
  • ガバナンス - チーム導入なら監査・SSO・ポリシー強制・サポート体制が組織の要求を満たすか、不足分をどう埋めるか計画する。個人ならこの項目は軽くなる。

9. 結論 - 今日適用できる3つ

ompは本物の問題 - ターミナルがコードの意味を理解しないという古い隙間 - を正確に狙った。Piのミニマルなコアの上にLSP・DAP・Hashline・Hindsightを載せてターミナルをIDE級に引き上げるという発想自体は有効で新鮮だ。ただしその代償として、複雑さ、まだ検証中の自己ベンチマーク、ベンダー製品に比べ薄いガバナンスという現実的な限界を伴う。開放性と安定性を分けて見ることが正確なアプローチだ。

9.1 実験・個人プロジェクトにまず付けてみよ

顧客露出のないサイドプロジェクトやリファクタリング・デバッグの多い作業にまず試し、Hashline編集の信頼性とLSP・DAPの実際の利得を自分の基準で測定せよ。

9.2 権限の境界をまず設計せよ

ツールの表面が広い分、自動承認の範囲・サンドボックス・隔離ワークスペースを導入初日に設定せよ。本番リポジトリに自動化を無分別に開放するな。

9.3 ベンダー製品と役割を分けよ

SLA・規制・組織標準化が絡むワークロードはClaude Code・Codex CLIのような検証済みの層に置き、ompは開放型の実験と個人の生産性ツールとして役割を分離せよ。より広い文脈はローカルLLMエージェント開発とAIセッション記憶プロジェクトを参照せよ。
