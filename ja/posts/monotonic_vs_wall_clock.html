経過時間を壁時計で測るとマイナスになる - 単調時計を使うべき場所

二つの時計が答える問いは違う - 「今何時か」と「どれだけ経ったか」

2026-07-30 開発/インフラ

症状: 処理時間のログにマイナスが刻まれていた

ある朝、ダッシュボードにduration_ms: -2760が出ていたとしよう。リクエスト一件がマイナス2.7秒かけて処理されたというログだ。コードを開いても何の問題もなさそうに見える。開始時に時刻を刻み、終了時にもう一度刻み、引く。これより単純な計算はない。

ところがその単純な計算はある仮定に依存している。二度目に読んだ時刻が一度目より必ず大きい、という仮定だ。壁時計はそれを保証しない。その間に誰かが時計を直したかもしれない。

この記事の結論は「単調時計を使いましょう」ではない。そういう助言は規則としてしか残らず、規則は忘れられる。代わりにこう整理する。二つの時計は別々の問いに答えている。

  • 壁時計は「今何時か」に答える。人が読む時刻であり、他のマシンと比較できる時刻であり、カレンダーに書ける時刻だ。その代償として外部から直されうる
  • 単調時計は「どれだけ経ったか」に答える。基準点が任意なので、その値自体には何の意味もない。二回読んで引いた差だけに意味がある。その代償として誰も巻き戻せない
  • つまり壁時計は経過時間の根拠になれない。根拠にした瞬間、「外部から直されうる」という性質がそのまま測定値に漏れ込む
  • 逆に単調時計は人に見せる時刻になれない。ログのタイムスタンプに使えば1970年が刻まれ、別のサーバーのログと突き合わせられない

この区別を体で覚える最短の道はマイナスが出る瞬間を自分の目で見ることだ。だからこの記事は実行から始める。十二の実験をNodeとPythonとシェルで走らせ、以下のすべてのブロックはその出力をそのまま写したものだ。

実行環境。すべての出力はWindows 10 Pro (10.0.19045)で実際に実行した結果だ。ランタイムはNode.js v22.16.0 (win32)とPython 3.13.3、シェルはGNU bash 5.2.37 (MSYS2/MinGW64)である。スクリプトはすべてファイルに保存して実行した。

システム時刻は一度も変更していない。管理者権限が必要で環境を壊す。代わりに時刻のジャンプを注入した。プログラムが壁時計を読む場所にDate.now() + offsetの形の関数を置き、測定の途中でそのoffsetを変えた。時刻同期が時計を階段状に動かすときにプログラムが見るものと形が同じだ。単調時計は手を加えない実際の値をそのまま読んでいる。

この記事が扱わないこと。時計がなぜずれるのか、同期状態をどう診断するのかは扱わない。ここでは「時計は戻りうる」という事実までにとどめ、その先の「経過時間の測定にどの時計を使うか」の一点に集中する。タイムゾーン規則と過去の解釈の問題もこの記事の範囲外だ。

--- P-3. what the numbers mean ---

time.monotonic()の20884.475514をUnix時刻として読むと、やはり1970年が出る。Python公式ドキュメントはこれを明示的に釘付けにしている。「返り値の基準点は未定義であり、二回の呼び出し結果の差だけが有効である」という文だ。つまりこの値を保存すること、送信すること、人に見せることは、いずれも仕様が保証しない使い方である。

2. 「終了 − 開始」がマイナスになる瞬間

ここがこの記事の心臓だ。120ミリ秒の仕事をし、時刻補正を3秒戻す形で注入し、もう一度120ミリ秒の仕事をしたうえで終了時刻から開始時刻を引いた。同じ区間を単調時計でも測った。

--- 2-1. THE BUG: elapsed measured on a wall clock that gets corrected ---
start (wall)   : 1785385665815
end   (wall)   : 1785385663055
elapsed  WALL  : -2760 ms
elapsed  MONO  : 239.265 ms
wall elapsed is negative : true

--- 2-2. the same code, printed the way a service logs it ---
{"msg":"request done","duration_ms":-2760,"clock":"wall"}
{"msg":"request done","duration_ms":239.3,"clock":"monotonic"}

--- 2-3. forward jump: the request looks 10 minutes long ---
elapsed WALL : 600050 ms   (10.00 min)
elapsed MONO : 49.368 ms

elapsed WALL : -2760 ms。実際には240ミリ秒働いたのに、壁時計はマイナス2.76秒だと答えた。同じ区間を単調時計で測れば239.265 msだ。サービスがそのままログを出せばduration_ms:-2760という行が残る。冒頭のあの行である。

  • 終了時刻が開始時刻より小さい。1785385663055が1785385665815より小さい。その間に時計が戻ったからだ
  • コードにバグはない。引き算は正確である。間違っているのは「二度目の値が一度目より大きい」という仮定だ
  • 単調時計は同じ注入に揺らがなかった。注入は壁時計を読む場所にだけ掛け、単調時計は実際の値をそのまま読んでいるからだ。仕様上この時計は調整の対象ではない
  • 逆方向も同じ欠陥である。下の2-3では時計を10分前に進めたところ、50ミリ秒の作業が600050 ms、10分として記録された。マイナスよりこちらが危険だ。マイナスは目につくが10分はもっともらしく見える
--- P-4. THE BUG: elapsed on a wall clock that gets corrected ---
start (wall)  : 1785385835.713235
end   (wall)  : 1785385832.953251
elapsed WALL  : -2759.984 ms
elapsed MONO  : 240.017 ms
wall elapsed is negative : True

what a handler would log:
{"msg": "job finished", "elapsed_ms": -2760.0, "clock": "wall"}
{"msg": "job finished", "elapsed_ms": 240.0, "clock": "monotonic"}

Pythonで同じ実験をすると値までほぼ同じになる。-2759.984 msだ。これは言語の問題ではなく時計の性質の問題だという意味である。Python公式ドキュメントはtime.time()について「二回の呼び出しの間にシステム時計が戻された場合、前回より小さい値を返しうる」と書いている。つまりこの挙動はバグではなく仕様に明記された動作だ。

注入の方式について。システム時刻は変更していない。プログラムが壁時計を読む関数にオフセットを足し、「プログラムが見る壁時計が突然動いた状態」を作った。時刻同期の階段状の補正や、人が時刻を手で直すときにプログラムに見えるものと形が同じである。単調時計側はオフセットなしで実際の値を読んでいるので、二つの列の対比は実際の時計の性質の違いをそのまま示している。

ただし、こうしなくても確認できる。Pythonのtime.get_clock_info()がtimeについてadjustable=True、monotonic=Falseをそのまま報告する。この二つの値がすでに「この時計は動かされうるし、戻りうる」という言明だ。注入実験は、その言明がコードにどんな姿で現れるかを示しているだけである。

2.1 時計が戻る場合たち

「時計が戻る」は珍しい出来事のように聞こえるが、実際にはありふれた運用活動の結果だ。どの場合にどの方向へどれだけ動くのかを整理した。動きの大きさが重要である。ミリ秒単位の補正はログに残らず通り過ぎるが、秒単位の階段状の補正はすぐにマイナスを作る。

契機方向大きさ測定に現れる姿
時刻同期の階段状の補正両方数百ミリ秒 〜 数十秒経過時間がマイナスになるか過大になる。この記事の再現がこれ
時刻同期の漸進的な補正両方周波数を少し調整単調時計も影響を受ける。clock_gettime(2)が「周波数調整の影響は受ける」と書いている。ただし戻ることはない
人が手で直す両方分 〜 時間 〜 日最大のジャンプ。開発機と新しいサーバーでよくある
仮想マシンの一時停止と再開通常は前に停止していた時間だけ再開直後に壁時計が一気に飛ぶ
コンテナや仮想環境の時刻ソースの変更両方環境により異なるホストとゲストが違う値を見ていたのが揃う瞬間
起動直後にハードウェア時計から読む通常は前に秒 〜 時間起動初期に始まった測定が最初の同期時点で壊れる

3. 分解能は別の問題だ - そして通説が間違う

「壁時計は分解能が低いから単調時計を使え」という説明をよく見る。この言い方は半分しか正しくない。実際に測ってみた。連続呼び出しで値が変わらない回数を数える方法で最小目盛りを求めた。

--- 3-1. resolution measured by counting repeats  (node) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
Date.now()           400000   38              14402               1 ms
performance.now()    400000   292699          1                   0.000100 ms
hrtime.bigint()      400000   400000          0                   100 ns

--- P-5. resolution measured by counting repeats  (python) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
time.time()            300000   199586          2                   0.000238 ms
time.monotonic()       300000   300000          0                   0.000100 ms
time.perf_counter()    300000   300000          0                   0.000100 ms
time.monotonic_ns()    300000   300000          0                   100 ns
time.perf_counter_ns() 300000   300000          0                   100 ns
  • NodeのDate.now()は40万回の呼び出しで値が38回しか変わらなかった。同じ値が最大14,402回連続で出て、最小変化幅は1ミリ秒だった。ミリ秒より短いものはこの時計では測れない
  • 同じ環境のPythonのtime.time()は30万回で199,586回変わった。最小変化幅が0.000238ミリ秒、つまり238ナノ秒である。get_clock_info()が示した実装はGetSystemTimePreciseAsFileTime()だった
  • つまり「壁時計は粗い」という通説は言語とプラットフォームによって間違う。同じマシンの同じ瞬間に、一方の壁時計は1ミリ秒、他方の壁時計は238ナノ秒だった
  • ところが分解能が高くても問題はそのままだ。Pythonのtime.time()は分解能が十分なのに2節でマイナスを出した。分解能と調整可能性は独立した性質である
  • 単調時計側は両方の言語とも100ナノ秒で、同じ値が二度出ることが一度もなかった。この環境のPythonはmonotonicとperf_counterの両方がQueryPerformanceCounter()を使うと報告した

整理するとこうだ。分解能が低ければ短い区間が測れない。調整されうるならどの区間も信じられない。前者は不便で後者は欠陥である。だから単調時計を使う第一の理由は分解能ではなくadjustable=Falseだ。分解能はおまけとして付いてくる。

4. 1ミリ秒より短い作業を測ると

分解能が実務でどんな姿になるかは、短い作業を測ればすぐに現れる。0.1ミリ秒ほどかかる計算を八回測り、壁時計と単調時計を並べて出力した。

  2           0        0.1023

  6           0        0.0703
  7           0        0.0704
wall reported 0 ms in 7 of 8 runs; hrtime never did

  0          8.4169           8.4145              8.4111
  1          6.5217           6.5193              6.5173

  • つまりこの時計で測ると、この作業は「0ミリ秒または1ミリ秒」だ。実際には二倍の差がある回もあるのに、その差が全部消えた
  • Python側は0が一つもなかった。同じ計算がPythonでは2〜8ミリ秒かかってミリ秒の目盛りの上に乗り、壁時計の分解能もはるかに高かったからだ。つまりこの症状は言語と作業の大きさによって見えたり見えなかったりする
  • 実務的な含意がひとつある。「うちのコードでは0が出ないから大丈夫」という判断が危険だ。作業が速くなるかランタイムが変わればそこから0が出はじめる。性能改善が測定を壊す形になる

5. 同じ区間を100回測ると分布が崩れる

一回測って終わるコードは稀だ。普通は何度も測って平均とパーセンタイルを出す。同じ作業を100回測り、二つの時計の分布を比較した。

--- 5-1. same interval, 100 samples, two clocks  (node) ---
clock                 mean       min        max        median    distinct values
---------------------------------------------------------------------------------
Date.now()           0.0700     0.0000     1.0000     0.0000    2
performance.now()    0.0738     0.0702     0.1177     0.0703    24
wall samples that came out exactly 0 : 93 / 100

--- P-7. same interval, 100 samples, three clocks  (python) ---
clock                   mean      min       max       median    distinct   zeros
------------------------------------------------------------------------------
time.time()             3.1561    2.1367    9.7034    2.3899    98         0
time.monotonic()        5.3347    2.1219    47.3406   3.3695    100        0
time.perf_counter()     4.1934    2.1830    12.9886   3.2359    100        0
  • Nodeでは平均がほぼ同じだった。壁時計0.0700、高分解能時計0.0738ミリ秒である。だから平均だけ見れば何の問題もなさそうに見える
  • ところが壁時計側は互いに異なる値がちょうど2個しかなかった。0と1だ。100個の標本のうち93個がちょうど0だった。高分解能時計は24個の異なる値を出した
  • 最小と最大が0と1というのは分布がないという意味だ。中央値は0、つまり「この作業は時間がかからない」になる
  • Python側は三つの時計がすべてもっともらしい分布を出した。ただしtime.monotonic()の最大値が47.34ミリ秒に跳ねた。これは時計の欠陥ではなく測定中のスケジューリング遅延が実際にあったという意味である。時計が正直にそれを記録した

6. 短い測定を合算するとき - 予想と違う結果

粗い時計で測った値を足し続ければ誤差が積み上がりそうだ。実際に測ってみた。同じ作業2000回を個別に測定して合算し、パーセンタイルまで一緒に出した。

  • 代わりに崩れたのは分布だ。中央値が0.0000、p95とp99が並んで1.0000である。異なる値が2個しかないのだから、パーセンタイルという概念自体が成立しない
  • 実務ではこちらのほうが痛い。合計と平均はダッシュボードでもっともらしく見えるのに、「p99遅延が1ミリ秒に張り付いている」というグラフは測定の目盛りを見ているのであってサービスを見ているのではない
  • 6-3は予算20ミリ秒を個別測定で削って使う実験だ。壁時計は221回、高分解能時計は238回回った。約7パーセントの差である。合計が合っても個別測定を条件に使った瞬間に結果が分かれる

7. タイムアウトと再試行 - ここで事故が大きくなる

ここまでは数字がおかしくなる話だった。ここから動作がおかしくなるほうへ進む。再試行の予算500ミリ秒を壁時計の絶対時刻で固定し、二回目の試行のあとに時計を1時間前に進める形で注入した。

--- 7-1. a wall-clock deadline expires the instant the clock is corrected ---
budget 500 ms of retries, clock steps +3600 s (1 h forward) after attempt 2
 WALL deadline:
  attempt 1: ok, remaining=500 ms
  attempt 2: ok, remaining=470 ms
  << clock stepped 3600 s >>
  attempt 3: ABORT deadline exceeded, remaining=-3599560 ms
  -> attempts completed: 2 of 6, aborted=true
 MONOTONIC deadline:
  attempt 1: ok, remaining=500.0 ms
  attempt 2: ok, remaining=470.8 ms
  << clock stepped 3600 s >> (monotonic unaffected)
  attempt 3: ok, remaining=440.8 ms
  attempt 4: ok, remaining=410.9 ms
  attempt 5: ok, remaining=380.9 ms
  attempt 6: ok, remaining=350.8 ms
  -> attempts completed: 6 of 6, aborted=false

壁時計のほうは三回目の試行で即座に諦めた。残り予算が-3599560 msと計算されたからだ。実際には60ミリ秒しか使っていないのに、500ミリ秒の予算が尽きたものとして処理された。単調時計のほうは六回すべて回った。逆方向はもっと悪い。

--- 7-2. and a backward step makes the same deadline unreachable ---
deadline was set 200 ms out, then the clock stepped -86400 s
remaining according to the wall clock : 86399880 ms  (24.00 h)
real time actually spent waiting      : 319.6 ms (loop cut off by a guard)
without the guard this loop waits a full day for a 200 ms deadline

--- 7-3. sleep-until-instant vs sleep-for-duration ---
sleep until wall instant 1785385765471 :
  if the clock is stepped +1000 s first -> wakes immediately, 0 ms of real waiting
  if the clock is stepped -1000 s first -> waits ~1001 s of real time
sleep for 1000 ms (setTimeout, libuv timer) :
  setTimeout(1000) fired after 1013.7 ms of monotonic time
  the -50000 ms wall step did not move it
  • 前へジャンプ → 即座に期限切れ。再試行が一度も残らず終わる。障害対応中に時刻を合わせると、その瞬間にすべての再試行ロジックが同時に諦める
  • 後ろへジャンプ → 永遠に終わらない。200ミリ秒後に置いた期限を24時間後に延ばした形になった。壁時計が計算した残り時間は86399880 ms、24時間だ。実験では安全装置で切ったが、なければ一日待つ
  • 「絶対時刻まで寝る」と「これだけ寝る」は別の命令だ。前者は時計の補正に流され、後者は流されない
  • 7-3ではsetTimeout(1000)が壁時計を50秒戻す注入をしても単調時間1013.7ミリ秒後に正確に発火した。ランタイムのタイマーはすでに単調時計の上に乗っているという意味である
  • つまりランタイムが与えるタイマーは安全で、自分で計算した期限が危険だ。「何秒後に」をフレームワークに任せられるなら任せるほうがよい

この節がもっとも危険な理由。前の節たちの症状は数字がおかしくなることで、ログを見れば分かる。この節の症状は動作がおかしくなることで、ログには「タイムアウト」としか残らない。すると調査は自然にネットワークと相手のサーバーへ向かう。原因が自分のコードの時計の選択だというところまで行く道がとても遠い。

8. キャッシュの失効とレート制限 - 同じ欠陥の別の顔

タイムアウトとまったく同じ計算がキャッシュとレート制限にも入っている。「今 + TTL」を保存しておいて、あとで「今」と比べる形だ。TTL60秒の項目5個を入れ、実際の時間はまったく流れていない状態で時計だけを動かした。

--- 8-1. a TTL cache keyed on wall instants ---
5 entries, ttl 60 s, nothing has actually elapsed
  before step   wall-cache live=5   mono-cache live=5
  clock +3600 s wall-cache live=0   mono-cache live=5   get(k0)=(expired)
  -> the whole cache evaporates in one tick. every caller goes to the origin at once
  clock -3600 s wall-cache live=5   mono-cache live=5   get(k0)=v0
  -> entries now outlive their ttl by an hour. stale data served as fresh

時計を1時間前に進めると、生きている項目が5個から0個になった。キャッシュが一ティックで全滅したのである。後ろに動かせば逆に失効すべき項目が生き続ける。レート制限も同じ構造だ。

--- 8-2. a fixed-window rate limiter on the same clock ---
 WALL limiter, 3 req / 1000 ms:
   r1 window_age=0ms count=1 -> ALLOW
   r2 window_age=0ms count=2 -> ALLOW
   r3 window_age=0ms count=3 -> ALLOW
   r4 window_age=0ms count=4 -> REJECT
   << clock stepped +5 s, no real time passed >>
   r5 window_age=0ms count=1 -> ALLOW   <- quota reset for free
   << clock stepped back to where it was >>
   r6 window_age=-5000ms count=2 -> ALLOW   <- window frozen, it will never roll again
 MONOTONIC limiter, same sequence:
   r1 window_age=1ms count=1 -> ALLOW
   r2 window_age=1ms count=2 -> ALLOW
   r3 window_age=1ms count=3 -> ALLOW
   r4 window_age=1ms count=4 -> REJECT
   << clock stepped +5 s >>
   r5 window_age=1ms count=5 -> REJECT   <- still rejected, correctly
  • 前へジャンプ → キャッシュ全滅。問題は「キャッシュが空になった」ではなくすべての呼び出し元が同時にオリジンへ殺到することだ。時刻補正の直後にオリジンの負荷が跳ねる形で現れる
  • 後ろへジャンプ → 失効が先送りされる。get(k0)=v0がそのまま返ってきた。失効すべき値が新鮮なものとして提供される。こちらは何のエラーも出ない。ただ古い値が出ていく
  • レート制限は無料の割当をくれる。時計を5秒前に進めると、拒否されていたリクエストがALLOWに変わった。窓が新しく開いたものとして計算されたからだ
  • 戻すと窓が凍りつく。window_age=-5000msだ。窓の年齢がマイナスなので窓が再び回る条件を永遠に満たせない。それ以降はカウンターが増え続けるだけになる
  • 単調時計に変えたほうは同じ順序で正常に拒否を続けた。時計の注入が判断にまったく届かなかった

9. ログのタイムスタンプは必ず壁時計であるべきだ

ここで方向を裏返す。ここまでは壁時計を使ってはいけない場所だった。単調時計を使ってはいけない場所もある。単調時計の値をそのままタイムスタンプとして刻んでみた。

--- 9-1. the reverse mistake: a monotonic value cannot be a timestamp ---
monotonic reading                  : 20810933.933
formatted as if it were epoch ms   : 1970-01-01T05:46:50.933Z
wall reading                       : 1785385762171
formatted                          : 2026-07-30T04:29:22.171Z
a log line stamped with the monotonic value says 1970 and cannot be compared to any other machine

--- 9-2. the line that carries both ---
{"ts":"2026-07-30T04:29:22.176Z","duration_ms":44.628,"route":"/v1/orders"}
ts is orderable across hosts and readable by a human; duration_ms cannot go negative
  • 単調時計の値をタイムスタンプとして整形すると1970-01-01T05:46:50.933Zが出る。基準点がエポックではないので当然の結果だ
  • 他のマシンのログと突き合わせられない。二つのサーバーの基準点が互いに違うので、二つの数字を比べることには意味がない。分散トレーシングがここで崩れる
  • 人が読めない。「20810933.933に障害が始まった」という言明では何もできない
  • 保管ポリシーも引っかかる。「30日過ぎたログを削除」のような規則は絶対時刻がなければ判断できない

だから正解は「どちらか一つを選ぶこと」ではなく二つをそれぞれの場所で使うことだ。9-2の一行がその形である。tsは壁時計で「いつ」を書き、duration_msは単調時計で「どれだけ」を書く。こうすればタイムスタンプは他のホストと並べられて人が読めるようになり、所要時間は絶対にマイナスにならない。一行に二つの時計が入るのは奇妙なことではなく正常だ。

10. プロセスが再起動すると基準点が変わる

単調時計の基準点が任意であるという事実には、実務的な帰結がもうひとつある。その値を保存してはいけない。同じスクリプトを二つのプロセスで連続して走らせ、値を比較した。

--- 10-1. the monotonic origin is per boot and per process ---
field                   previous process     this process         delta
---------------------------------------------------------------------------------
pid                     14920                17368                -
Date.now()              1785386114435        1785386117740        3305 ms
hrtime.bigint()/1e6     21163198.428         21166503.246         3304.818 ms
performance.now()       1869.676             1882.334             12.658 ms
performance.timeOrigin  1785386112566.207    1785386115858.01     3291.803 ms

--- 10-2. so a persisted monotonic deadline is meaningless after restart ---
saved by the previous process : performance.now() + 30000 = 31869.676
this process reads it back and compares to its own performance.now() = 1885.058
  remaining, as computed      : 29984.557 ms
  real time between the runs   : 3305 ms (from the wall clock)
  the two numbers are unrelated. performance.now() restarts near 0 in every process
  • Date.now()は二つのプロセスの間で3305ミリ秒増えた。実際に流れた時間だ。プロセスが違っても同じ座標系を見ている
  • hrtime.bigint()も3304.818ミリ秒増えた。この時計の基準点はプロセスではなく起動なので、再起動を越えて続く
  • performance.now()は12.658ミリ秒しか増えなかった。3.3秒流れたのに12ミリ秒である。この時計はプロセスごとに0から始まり直すからだ。公式ドキュメントの「0が現在のプロセスの開始を表す」がこの数字で確認される
  • 10-2がその結果だ。前のプロセスが保存した期限を後のプロセスが読んで計算すると残り時間が29984ミリ秒と出た。実際には3.3秒流れたのに「まだ30秒残っている」と答えたのである。二つの数字には何の関係もない
値保存・送信してよいか理由
Date.now() / ISO文字列よいすべてのマシンが同じ意味で読む絶対時刻
performance.now()だめ基準点がこのプロセス。再起動すれば0に戻る
process.hrtime.bigint() / time.monotonic()だめ基準点がこの起動。再起動すれば無意味になる
単調時計で測った区間の長さよい二つの値の差はただのミリ秒の個数だ。基準点がない
performance.timeOriginよいこれ自体が壁時計の値である。オフセットと組み合わせれば絶対時刻を復元できる

11. サスペンド区間は誰が数えるのか

単調時計にも分岐がある。マシンがサスペンドしている間にカウンターが止まるのか回り続けるのかだ。この環境で確認できる範囲だけ測った。単調時計の値と、OSが報告する起動時刻から計算した壁時計の経過を並べて置いた。

--- P-9. does the monotonic clock count time spent suspended? ---
time.monotonic() here            : 20892.159 s  (5.80 h)
implementation                   : QueryPerformanceCounter()
OS-reported last boot time       : 2026-07-30T07:42:31.500000+09:00
wall seconds since that boot     : 20892.807 s  (5.80 h)
difference (wall-since-boot minus monotonic) : 0.648 s

POSIX names for the distinction (not reproducible on this host):
  CLOCK_MONOTONIC  - does not step; on Linux it does NOT include suspend
  CLOCK_BOOTTIME   - same, but DOES include suspend
  CLOCK_REALTIME   - the wall clock, may be stepped
  time.CLOCK_MONOTONIC      available in this build : False
  time.CLOCK_BOOTTIME       available in this build : False
  time.CLOCK_MONOTONIC_RAW  available in this build : False
  time.CLOCK_REALTIME       available in this build : False
  • 二つの値の差は0.648秒だった。単調時計は20892.159秒、起動時刻基準の壁時計の経過は20892.807秒である。5.8時間で0.6秒の差だ
  • このマシンは測定区間にサスペンドに入ったことがない。だからこの方法ではサスペンド区間の扱いを観察できなかった。0.6秒は起動時刻の報告の精度と起動後の時刻補正で説明される範囲である
  • サスペンドと休止の区間をこの環境では直接再現できなかった。だから以下の区別はドキュメントの根拠のみで書く。この記事で直接再現できなかった唯一の項目だ
  • clock_gettime(2)のドキュメントはCLOCK_MONOTONICについて「この時計はシステムがサスペンドしていた時間を数えない」、CLOCK_BOOTTIMEについて「CLOCK_MONOTONICと同一だが、システムがサスペンドしていた時間も含む」と書いている。Pythonのドキュメントもtime.CLOCK_BOOTTIMEを同じ意味で説明している

実務的な判断。サーバープロセスならこの区別はほとんど問題にならない。サスペンドに入らないからだ。問題になるのはノートパソコンと携帯機器で動くコードである。蓋を閉じて開ける間に、CLOCK_MONOTONICベースのタイムアウトはその時間を数えない。「5分後にセッション失効」が一晩越えても失効しない形だ。サスペンドの時間も流れたものとして扱うべき失効ならCLOCK_BOOTTIMEのほうが合っていて、人が認識する絶対時刻基準の失効なら、そもそも壁時計の絶対時刻が正しかった。その場合は14節の表の「失効」の行を見てほしい。

12. シェルには単調時計がない

シェルスクリプトにはこの問題を避ける道具がほとんどない。シェルが読める時計を全部出力してみた。

bash 5.2.37(1)-release / msys

--- S-1. the clocks a shell can read ---
date +%s          : 1785385886
date +%s%N        : 1785385886351968200
EPOCHSECONDS      : 1785385886
EPOCHREALTIME     : 1785385886.364763
SECONDS           : 0
all of these trace the wall clock. bash exposes no monotonic clock.

--- S-3. SECONDS advances with the wall clock, not with work done ---
SECONDS after sleep 2        : 2
date delta                   : 2132 ms

timeout available here : /usr/bin/timeout
Usage: timeout [OPTION] DURATION COMMAND [ARG]...

date、EPOCHSECONDS、EPOCHREALTIME、SECONDSのすべてが壁時計に従う。つまり純粋なシェル構文では単調時計に触れる方法がない。だからシェルでもっともよく見る次のパターンは構造的に危険だ。

# the deadline loop everyone writes - both date calls are on an adjustable clock
end=$(( $(date +%s) + 30 ))
while [ "$(date +%s)" -lt "$end" ]; do
    check_ready && break
    sleep 1
done

# the portable fix: stop computing the deadline yourself
timeout 30 sh -c 'until check_ready; do sleep 1; done'
  • 期限を自分で計算しないのが答えだ。timeoutに「何秒間」を渡せば期限の計算がシェルの外へ出る。この環境にも/usr/bin/timeoutがあった
  • dateの呼び出し自体も高い。S-2では200回の呼び出しの最小変化幅が48ミリ秒だった。時計の分解能ではなくプロセス生成のコストである。ループの中で時刻を読むスクリプトはこのコストを毎回払う
  • 待ちを絶対時刻で表現しない。「何時まで」ではなく「何秒間」と書く
  • 本当に正確な測定が必要ならシェルでやらない。一行でも、単調時計のあるランタイムに任せるほうがよい

13. 既存のコードから誤った時計の使用を見つける手順

ここから診断だ。幸いこの欠陥は検索でほぼ全部見つかる。誤った使用が構文の形として現れるからである。四つのパターンを使う。

# A. elapsed  -  the subtraction of two wall readings
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. deadline / expiry  -  a wall reading with something added to it
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. the reverse mistake  -  a monotonic reading assigned into stored state
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. everything already monotonic, to confirm it is used as a difference
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/

実際に走らせてみた。時計の使用が混ざっている例のファイル二つを作り、上のパターンを掛けた。以下がその出力である。

--- 12-1. pattern A: subtraction of two wall readings (the smoking gun) ---
./src/handler.js:7:  const ms = Date.now() - t0;                   // can go negative
./src/worker.py:10:    elapsed = time.time() - start             # can go negative

--- 12-2. pattern B: a deadline built by adding to a wall reading ---
./src/handler.js:13:  const deadline = Date.now() + budgetMs;       // wall-clock deadline
./src/handler.js:28:  CACHE.set(key, { value, expiresAt: Date.now() + ttlMs });   // wall instant
./src/worker.py:15:    deadline = time.time() + timeout_s        # wall-clock deadline

./src/worker.py:51:    state["saved_at"] = time.monotonic()
--- 12-5. every monotonic reading, to confirm the ones that are fine ---
./src/handler.js:32:  const t0 = process.hrtime.bigint();           // correct: monotonic
./src/handler.js:34:  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
./src/worker.py:33:    start = time.monotonic()                  # correct: monotonic
./src/worker.py:36:    emit_metric("batch_seconds", time.monotonic() - start)

--- 12-6. triage counts ---
files with a wall-clock subtraction   : 2
wall-clock deadline sites             : 3
monotonic readings already present    : 5

パターンAがもっとも強い信号だ。壁時計の値の引き算はほぼ例外なく経過時間の計算であり、ほぼ例外なく誤っている。パターンBは判断が必要だ。期限とTTLは直すべきだが、トークンの失効や予約時刻のように絶対時刻が正しい場合もここに掛かる。だから検索は始まりであり、レビューが必要になる。レビューのときに問う文はこうだ。

  • この値を人が見るのか、それとも二つの値を引くのか。引くなら単調時計だ。この一文でほとんどが分かれる
  • この時刻がプロセスの外へ出るのか。保存されるか送信されるか他のマシンと比較されるなら壁時計でなければならない
  • この期限は「何時まで」なのか「これだけの間」なのか。後者なら単調時計だ。ユーザーが指定した「午後6時まで」なら前者が正しい
  • この値がマイナスになると何が起きるのか。答えが「分からない」か「そんなはずがない」なら、その場所が危険な場所だ
  • この失効はプロセスの再起動を越えて維持されるべきか。そうなら単調時計で作った値を保存してはいけない
// before - the duration can come out negative
const t0 = Date.now();
const out = doWork(req);
log({ ts: new Date().toISOString(), duration_ms: Date.now() - t0 });

// after - wall clock names the instant, monotonic clock measures the span
const t0 = process.hrtime.bigint();
const startedAt = new Date().toISOString();
const out = doWork(req);
log({ ts: startedAt, duration_ms: Number(process.hrtime.bigint() - t0) / 1e6 });
# before
start = time.time()
run_batch(items)
emit_metric("batch_seconds", time.time() - start)

# after
started_at = datetime.datetime.now(datetime.timezone.utc)
start = time.monotonic()
run_batch(items)
emit_metric("batch_seconds", time.monotonic() - start, ts=started_at)

直す形は上の二つの断片のように単純だ。開始時刻を壁時計で一度刻んで「いつ」を残し、区間の測定は単調時計で別にやる。行がひとつ増えるが、その代償としてマイナスが消える。振り返るに値する点がひとつある。12-5で単調時計の使用を全部抜き出したとき、正常な使用四件とともに単調時計の値を保存する一件が一緒に掛かった。「単調時計を使っている」は無事の証拠ではない。どう使うかを見なければならない。

14. 判断表 - 用途別にどの時計か

この記事からひとつだけ持ち帰るならこの表だ。左の列で自分の状況を探し、右へ読んでいけばよい。

用途どの時計なぜ典型的な誤り
経過時間の測定単調二つの値を引く計算だ。戻れないことが必要であるDate.now()の引き算 → マイナス
タイムアウト・再試行予算単調「これだけの間」という持続時間だ絶対時刻の期限 → 即座の失効または無限の待ち
レート制限の窓単調窓の年齢は経過時間である壁時計の窓 → 無料の割当、窓の凍結
キャッシュTTL(プロセス内)単調TTLは持続時間だ壁時計の失効時刻 → キャッシュ全滅または古い値の提供
ログ・監査のタイムスタンプ壁時計人が読み、他のホストと突き合わせる単調の値 → 1970年が刻まれる
スケジュール「毎日09時」壁時計カレンダー上の約束だ単調時計では表現自体ができない
失効(トークン・セッション・証明書)壁時計発行者と検証者が別のマシンだ。再起動を越えなければならない単調の値の保存 → 再起動後に無意味
性能プロファイリング単調・高分解能短い区間の分布を見なければならない粗い壁時計 → パーセンタイルが目盛りに張り付く

15. なぜこの欠陥は遅れて発覚するのか

この欠陥のもっとも悪い性質は技術的なものではない。発見される仕方だ。

  • 普段は正確に合っている。二つの時計が並んで進むからだ。1節の増加幅がそれを示している。だからテストを通り、レビューを通り、何年も生きる
  • 間違う瞬間が短い。時刻の補正は瞬間であり、その瞬間に測定区間が跨っていなければ症状が出ない。確率が低い
  • 再現しない。調査するには時計を動かさなければならないが、それは調査者が意図してやらなければ起きないことだ
  • 症状が原因を指さない。「タイムアウト」「キャッシュミスの急増」「p99の異常」はすべて別の場所を指す症状である。時計を疑うまでに何度も外す
  • だから「時々おかしい」として残る。チケットが閉じて再現不可として整理され、次にまた起きる

この性質のために対応の順序が裏返る。普通は症状が出たら直す。この欠陥は症状を待ってはいけない。症状が出たときに原因へ到達する確率が低いからだ。代わりに13節の検索を一度回して予算の中で片付けるほうがはるかに安い。パターンが単純なので大きなリポジトリでも数分で終わる。

最後に判断基準をもう一度一文で書く。この数字を人に見せるのか、それとも他の数字から引くのか。見せるなら壁時計、引くなら単調時計だ。この問いひとつがこの記事の表の全部を代わりに務める。

16. チェックリスト

以下の項目はすべて上の実行で根拠が出たものだ。順に見ていけばよい。

  • 経過時間を測る場所から壁時計の引き算を全部取り除いた(13節パターンA)
  • タイムアウトと再試行の予算が「これだけの間」で表現されていて、絶対時刻の期限ではない
  • キャッシュのTTLとレート制限の窓が単調時計基準である
  • ログのタイムスタンプは壁時計で、所要時間は単調時計だ。一行に二つが一緒にある
  • 単調時計の値を保存したり送信したりする場所がない(13節パターンD)
  • 所要時間の指標にマイナスへの防御があり、マイナスが入ってきたら隠すのではなく警告を残す
  • 短い区間を測る場所が高分解能の時計を使っている。パーセンタイルが目盛りに張り付いていない
  • ノートパソコンや携帯機器で動く失効ロジックならサスペンド区間をどう数えるかを決めてある(11節)

最後にひとつ。マイナスを見つけたときに絶対値を被せたり0に押さえたりしないこと。それは証拠を消す行為だ。マイナスはこの欠陥が実際に発生したという唯一明確な信号であり、この記事で見たように前へジャンプした場合はそういう信号すら残らない。マイナスが見えているなら、むしろ運がよいほうだ。その場所で時計を替えればよい。

# 壁時計 vs 単調時計 — 用途別の選択表とコード点検パターン

> 出典: braindetox.kr — 経過時間を壁時計で測るとマイナスになる
> 根拠: Windows 10 / Node 22.16.0 / Python 3.13.3 / bash 5.2.37 (MSYS2) で実行検証
> このファイルをそのままAIに貼り付けて「この基準でうちのコードの時計の使い方を点検して」と書けば使えます。

## 0. 大前提 — 二つの時計は別の問いに答える

| | 壁時計 (wall clock) | 単調時計 (monotonic clock) |
|---|---|---|
| 答える問い | **今何時か** | **どれだけ経ったか** |
| 値の意味 | エポック基準の絶対時刻 | 任意の基準点からの距離 |
| 外部からの調整 | **受ける** | 受けない |
| 戻ることがあるか | **ある** | ない |
| 他のマシンとの比較 | 可能 | **不可能** |
| 保存・送信 | 可能 | **不可** (差の値のみ可) |

**この数字を人に見せるのか、それとも他の数字から引くのか。**
見せるなら壁時計、引くなら単調時計だ。この一文が以下の表の全部を代わりに務める。

## 1. 用途別の選択表

| 用途 | 時計 | 典型的な誤りと症状 |
|---|---|---|
| **経過時間の測定** | 単調 | 壁時計の引き算 → **所要時間がマイナス** |
| **タイムアウト・再試行予算** | 単調 | 絶対時刻の期限 → 即座の失効または無限の待ち |
| **レート制限の窓** | 単調 | 壁時計の窓 → 無料の割当、窓の凍結 |
| **キャッシュTTL** (プロセス内) | 単調 | 壁時計の失効時刻 → キャッシュ全滅または古い値の提供 |
| **再試行のバックオフ間隔** | 単調 | 壁時計基準の待機 → 間隔がめちゃくちゃになる |
| **ログ・監査のタイムスタンプ** | 壁時計 | 単調の値 → **1970年が刻まれる** |
| **スケジュール**「毎日09時」 | 壁時計 | 単調時計では表現自体ができない |
| **失効** (トークン・セッション・証明書) | 壁時計 | 単調の値の保存 → 再起動後に無意味 |
| **性能プロファイリング** | 単調・高分解能 | 粗い壁時計 → パーセンタイルが目盛りに張り付く |

## 2. 言語別API対応表

| 用途 | Node.js | Python | POSIX / C | シェル |
|---|---|---|---|---|
| 経過の測定 | `process.hrtime.bigint()` | `time.perf_counter()` | `CLOCK_MONOTONIC` | **なし** |
| 経過の測定 (代替) | `performance.now()` | `time.monotonic()` | `CLOCK_MONOTONIC_RAW` | **なし** |
| 現在時刻 | `Date.now()` | `time.time()` | `CLOCK_REALTIME` | `date`, `EPOCHREALTIME` |
| サスペンドを含む経過 | 標準APIなし | `time.CLOCK_BOOTTIME` | `CLOCK_BOOTTIME` | **なし** |
| プロセスのCPU時間 | `process.cpuUsage()` | `time.process_time()` | `CLOCK_PROCESS_CPUTIME_ID` | `times` |
| 持続時間の待機 | `setTimeout` | `time.sleep()` | `clock_nanosleep` | `sleep`, `timeout` |
| 時計の性質の確認 | ドキュメント確認 | **`time.get_clock_info()`** | `clock_getres` | 該当なし |

- Nodeの `hrtime.bigint()` の基準点は**起動**、`performance.now()` の基準点は**プロセス**だ (実測で確認)
- Pythonは `time.get_clock_info('time')` が `adjustable=True`, `monotonic=False` をそのまま教えてくれる
- 表にない言語なら二つだけ確認する: **基準点は何か / 外部から調整されうるか**

## 3. コード検索パターン

```bash
# A. 経過時間 — 壁時計の値の引き算 (もっとも強い信号、ほぼ全部が誤り)
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. 期限・失効 — 壁時計の値に何かを足す形 (レビューが必要)
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. 逆の誤り — 単調時計の値が保存される構造に代入されている
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. すべての単調時計の使用 — 差としてのみ使われているか確認
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/
```

- **Aはほぼ全部が直す対象だ。** 壁時計の引き算は事実上経過時間の計算である
- **Bは判断が必要だ。** 期限・TTLは直し、トークンの失効・予約時刻はそのままにする
- **Dで掛かったものも安心してはいけない。** 単調時計を使うことと正しく使うことは別だ

## 4. レビュー点検文

- [ ] **この値を人が見るのか、それとも二つの値を引くのか** — 引くなら単調時計
- [ ] **この時刻がプロセスの外へ出るのか** — 保存・送信・他マシンとの比較なら壁時計
- [ ] **この期限は「何時まで」か「これだけの間」か** — 後者なら単調時計
- [ ] **この値がマイナスになると何が起きるのか** — 答えが「そんなはずがない」ならその場所が危険だ
- [ ] **この失効はプロセスの再起動を越えて維持されるべきか** — そうなら単調の値を保存してはいけない
- [ ] **短い区間か** — ミリ秒目盛りの壁時計では0が出る
- [ ] **サスペンドする機器で動くか** — `CLOCK_MONOTONIC` はサスペンド区間を数えない


## 6. 実測の参考値 (Windows 10 / Node 22.16.0 / Python 3.13.3)

| 時計 | 最小目盛り | 備考 |
|---|---|---|
| Node `Date.now()` | **1 ms** | 40万回の呼び出しで値が38回しか変わらず、同じ値が最大14,402回連続 |
| Node `performance.now()` | 0.0001 ms | — |
| Node `hrtime.bigint()` | 100 ns | 40万回の呼び出しすべてが互いに異なる値 |
| Python `time.time()` | **0.000238 ms** | 実装 `GetSystemTimePreciseAsFileTime()` — **壁時計も高分解能でありうる** |
| Python `monotonic` / `perf_counter` | 100 ns | 両方とも `QueryPerformanceCounter()` |
| シェル `date +%s%N` の往復 | 約 48 ms | 時計の分解能ではなく**プロセス生成のコスト** |

**分解能と調整可能性は独立した性質だ。** 分解能が十分なPythonの壁時計も時刻補正には同じようにマイナスを出す。

## 7. やらないこと

- ❌ 所要時間のマイナスを**絶対値や0に押さえること** — 証拠を消す行為だ。前へジャンプした場合はそういう信号すらない
- ❌ 単調時計の値を**ファイル・DB・レスポンス本文に保存すること** — プロセスが変われば無意味になる
- ❌ 「何時まで」で表現した**再試行の期限** — 時刻補正で即座に失効するか永遠に終わらない
- ❌ ログのタイムスタンプに**単調の値** — 1970年が刻まれ他のホストと突き合わせられない
- ❌ **平均だけ見て済ませること** — 粗い時計では合計は合っていてパーセンタイルだけが崩れる
- ❌ シェルのループの中で**期限を自分で計算すること** — 調整されうる時計の上にあり `date` の呼び出しコストも大きい
- ❌ 「うちは時刻を変えない」という前提 — 時刻同期・仮想マシンの再開・手動修正はありふれた運用活動だ
