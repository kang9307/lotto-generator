序論: ファイル名に空白が一つ入っただけで引数が三個から五個になる

何年もきちんと動いていた整理スクリプトが、ある日おかしな動きをする。変わったのはコードではなく入力だ。誰かが annual report.pdf という名前でファイルを置いた。空白一つ。その瞬間からスクリプトが三個だと思っていた対象は五個になり、存在しない annual と report.pdf に対してコマンドが実行される。そのコマンドが rm なら、結果はファイル一覧ではなく事故報告書として残る。

これはバグではなくシェルの設計だ。シェルは変数を展開したあと、その結果をもう一度単語へ刻む。この二番目の動作を単語分割と呼び、クォートはそれを切るスイッチだ。ここまでは広く知られている。実際に人を転ばせるのはその先だ。"$@"と$@が違い、"$*"と"$@"がまた違い、"${arr[@]}"と${arr[@]}が違い、IFSは切るときと貼るときで別の規則を使う。この六つのうち一つでも取り違えれば引数の境界が崩れる。

この記事はその境界を目に見えるようにすることに集中する。すべての例は printf '[%s]\n' で引数を一つずつ角括弧に入れて出力する。何個あるのか、どこで切れたのかがそのまま見える。コマンドと出力は GNU bash, version 5.2.37(1)-release と同じ環境の dash で実際に走らせて得たものだ。

クォートそのものの種類別の遮断範囲はシェルのクォート規則で既に扱ったのでここでは繰り返さない。この記事の主題は引用符ではなく引数の境界だ。プロセス境界で値が消える問題はパイプの中のwhileで変数が消える理由が、スクリプトがどう終わっても後始末を保証する問題はtrapで一時ファイルを確実に消すが扱う。

例より先に読むこと。この記事で扱う失敗はファイルを実際に消す。files="annual report.pdf" の状態で rm $files を実行すると、rm は annual と report.pdf の二つの引数を受け取る。その二つの名前のどちらかでも実在すればそれが消える。展開結果に * が混ざっていれば範囲はさらに広がる。ファイル一覧を扱うコードを直すときは、削除コマンドを echo に替えて一度走らせ、対象一覧を目で確認してから戻す。そして rm や mv には -- 終端子を付け、ファイル一覧は文字列ではなく配列に入れて "${files[@]}" で展開する。改行の入った名前まで面倒を見るなら find -print0 と read -d '' の組み合わせを使う。この三つは後で一つずつ走らせて確認する。

1. 三個渡したのに関数は五個受け取る

引数を三個作り、四つの形で関数へ渡して個数を数える。対象は空白の入ったファイル名二つと普通の名前一つだ。

#!/usr/bin/env bash
show() { printf '  count=%d\n' "$#"; printf '  [%s]\n' "$@"; }

f1() { show "$@"; }
f2() { show $@; }
f3() { show "$*"; }
f4() { show $*; }

set -- "annual report.pdf" "q3 data.csv" plain.txt

echo '--- "$@" ---'; f1 "$@"
echo '--- $@  ---';  f2 "$@"
echo '--- "$*" ---'; f3 "$@"
echo '--- $*  ---';  f4 "$@"
$ bash t1.sh
--- "$@" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- $*  ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]

三個入れたのに出てきた個数は3、5、1、5だ。元の個数を守ったのは最初の一つだけである。残る三つはそれぞれ別のやり方で境界を崩した。

1.1 四つの組み合わせがやることを一つの表に

形結果の単語数単語分割グロブ使う場所
"$@"3(元のまま)起きない起きない引数をそのまま渡すとき。事実上唯一の正解
$@5起きる起きる使う場所がほぼない
"$*"1(一つに結合)起きない起きないログ一行に引数を出すとき
$*5起きる起きる使う場所がほぼない

表で $@ と $* の結果が同じに見えるが、これは偶然ではない。クォートを外した瞬間に両者の違いは消える。クォートのない展開はどのみち全部 IFS で刻み直されるので、「どう結合されたか」が意味を失う。つまり $@ と $* の違いを論じることに意味があるのはクォートを付けたときだけだ。

  • "$@" は引数の個数だけの単語に展開される。引数が0個なら単語も0個だ
  • "$*" は常に正確に一単語だ。引数が0個でも空文字列が一個できる
  • $@ と $* は結果が同じだ。どちらも IFS 分割とグロブを通る
  • 引数を他のコマンドへ渡す場面で "$*" を使うと、引数一個に固まって届く
  • 人が読むログ一行を作る場面なら "$*" のほうがむしろ適切だ。echo "実行: $0 $*" のような用途だ
  • $# は位置パラメータの個数だ。上の実行で関数の中の $# が3、5、1、5と出たのがその値だ

1.2 forでも同じ規則が働く

$ bash t12.sh
--- for ループ ---
for x in "$@"
    [annual report.pdf]
    [q3 data.csv]
for x in $*
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
for x in "$*"
    [annual report.pdf q3 data.csv]
リストを書かない for x は "$@" と同じ
    [annual report.pdf]
    [q3 data.csv]

最後の形は覚えておく価値がある。for x; do ... done のようにリストをそもそも書かないと、シェルが "$@" を使う。クォートを落とす余地そのものがなくなる。

2. シェルが展開のあとに黙ってやる二つのこと

なぜこうなるのかは、シェルがコマンド一行を処理する順序を見れば整理できる。変数を展開するのは途中の段階でしかなく、そのあとに二つの段階がある。

  1. 展開 — $var、${arr[@]}、$(cmd) のようなものが値に変わる
  2. 単語分割 — いま出た値を IFS に入った文字で切って複数の単語にする
  3. パス名展開 — 各単語の中に * ? [ があれば実在のファイル名に変える

ダブルクォートで包むと2番と3番を飛ばす。1番はそのまま起きる。だから "$var" は値を取り出しつつ、その値を一単語のまま保つ。この一文がこの記事全体の要約だ。

重要なのは2番と3番が展開から出てきた値にだけ適用されるという点だ。スクリプトに直接書いたリテラルは対象ではない。

$ bash -c 'show() { echo "count=$#"; }; show annual report.pdf'
count=2                # リテラル二単語。もともと二個だ

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show $x'
count=2                # 変数から出たあとに切られた

$ bash -c 'x="annual report.pdf"; show() { echo "count=$#"; }; show "$x"'
count=1                # クォートが2番を切った
  • 真ん中の行が事故の原型だ。変数の中では一塊だった値が、コマンドに届くときには二個になっている
  • コマンド置換 $(cmd) の結果も同じく2番と3番を通る。だから $(...) もクォートで包むのが基本だ
  • 算術展開 $((...)) の結果は数字なので実務で問題になることは稀だが、規則自体は同じだ
  • 代入文の右辺は例外だ。x=$y はクォートがなくても分割されない。代入はもともと一単語を受ける場所だからだ
  • case の対象語と [[ ]] の中も分割が起きない。一方で古い [ ] の中は起きる。この差のせいで [ $x = y ] は x が空だと構文エラーになる

3. IFSは切る刃であり貼る糊でもある

IFS は二つの仕事をするが規則が互いに違う。この非対称を知らないと IFS を変えたあとの結果を予測できない。

3.1 貼るときは先頭一文字だけを使う

#!/usr/bin/env bash
set -- alpha beta gamma
echo "既定の IFS : [$*]"
IFS=,
echo "IFS=,      : [$*]"
IFS=
echo "IFS 空値   : [$*]"
unset IFS
echo "IFS 解除   : [$*]"
IFS=',;|'
echo "IFS=',;|'  : [$*]"
$ bash t3.sh
既定の IFS : [alpha beta gamma]
IFS=,      : [alpha,beta,gamma]
IFS 空値   : [alphabetagamma]
IFS 解除   : [alpha beta gamma]
IFS=',;|'  : [alpha,beta,gamma]

最後の行が肝だ。IFS に三文字入れたのに間に入ったのは先頭の一文字だけである。そして IFS を空値にすると何も挟まずそのまま繋ぎ、unset すると既定値である空白に戻る。空値と解除はまったく別の状態だ。

同じ実行で "$@" は IFS をコロンに変えても揺らがなかった。

IFS=: にした状態でも "$@" はそのまま:
  [alpha]
  [beta]
  [gamma]

3.2 切るときは入った文字すべてを使う

#!/usr/bin/env bash
line="root:x:0:0:root:/root:/bin/bash"
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- 既定の IFS、クォートなし ---'
show $line
echo '--- IFS=: クォートなし ---'
IFS=:
show $line
echo '--- IFS=: だがクォートあり ---'
show "$line"
$ bash t4.sh
--- 既定の IFS、クォートなし ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]
--- IFS=: クォートなし ---
  count=7
  [root]
  [x]
  [0]
  [0]
  [root]
  [/root]
  [/bin/bash]
--- IFS=: だがクォートあり ---
  count=1
  [root:x:0:0:root:/root:/bin/bash]

ここでの IFS はフィールド区切りの役をきちんと果たす。アカウント情報一行を正確に七つのフィールドへ割った。ところが同じ状態でクォートを付けると何も起きない。IFS はクォートのない展開にだけ働く。

3.3 IFSを変えるときに守ること

IFS をグローバルに変えると、その後のすべての未クォート展開が影響を受ける。一つのコマンドにだけ適用する方法がある。

$ bash t13.sh
--- 保存して戻す方式 ---
old_IFS=$IFS; IFS=,; read -r -a parts <<< "alpha,beta,gamma delta"; IFS=$old_IFS
  3 elements
    [alpha]
    [beta]
    [gamma delta]
--- IFS=, read -a : そのコマンドにだけ適用 ---
  3 elements
    [alpha]
    [beta]
    [gamma delta]
  IFS after: $' \t\n'

二つ目の形がよい。IFS=, read -r -a parts のようにコマンドの前に置いた代入はそのコマンドが走る間だけ有効だ。実行後に IFS を確認すると既定値のままだ。保存して戻す方式は途中で return やエラーで抜けると復元されない。

  • 既定の IFS は空白・タブ・改行の三文字だ。上の出力の $' \t\n' がその値だ
  • この三文字は特別扱いを受ける。連続した空白は一つとして扱われ、前後の空白は捨てられる
  • 空白でない区切り、たとえばコロンは違う。連続したコロンは空のフィールドを作る
  • したがって a::b を IFS=: で切るとフィールドは三つで、真ん中は空文字列だ
  • ファイルを一行ずつ読むときに while IFS= read -r line と IFS を空にする理由がここにある。行の前後の空白が削られるのを防ぐ
  • read -r の -r はバックスラッシュをエスケープとして解釈させない。パスを読むときは事実上必須だ

4. クォートを外すと文字列がファイル名に化ける

単語分割ほど知られていないが、より危ないのがパス名展開だ。ファイル三個のあるディレクトリで確認する。

#!/usr/bin/env bash
# このディレクトリには report.txt, notes.txt, archive.tar がある
pattern='*.txt'
show() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
echo '--- クォートなしの $pattern ---'; show $pattern
echo '--- クォート付きの "$pattern" ---'; show "$pattern"
echo '--- set -f を入れた状態 ---'; set -f; show $pattern; set +f
$ bash t5.sh
files here: archive.tar notes.txt report.txt
--- クォートなしの $pattern ---
  count=2
  [notes.txt]
  [report.txt]
--- クォート付きの "$pattern" ---
  count=1
  [*.txt]
--- set -f を入れた状態 ---
  count=1
  [*.txt]

変数に入っている値は *.txt なのに、コマンドが受け取ったのは実在のファイル二個だ。変数に格納された文字列がコマンドに届く直前に別のものへ化けた。この変換はファイルシステムの現在の状態で決まるので、同じコードが昨日と今日で違う動きをする。

4.1 配列要素にグロブが混ざると被害は二重になる

$ bash t5.sh
--- 要素にグロブの入った配列 ---
arr=('*.txt' 'literal name.txt')
  クォートなしの ${arr[@]}:
  count=4
  [notes.txt]
  [report.txt]
  [literal]
  [name.txt]
  クォート付きの "${arr[@]}":
  count=2
  [*.txt]
  [literal name.txt]

要素二個の配列が四個になった。最初の要素はグロブで二つになり、二番目の要素は単語分割で二つになった。二つの段階が順に適用されるので被害が掛け算になる。

  • グロブがどのファイルとも一致しなければ、bash の既定設定ではパターン文字がそのまま残る。だから問題の発見が遅れる
  • shopt -s nullglob を入れると一致がないとき単語が消える。引数が丸ごとなくなるという別の事故になる
  • shopt -s failglob は一致がなければエラーを出す。対話シェルでは便利だがスクリプトでは想定外の中断を生む
  • set -f はグロブだけを切り、単語分割はそのまま残す。上の実行で [*.txt] が一単語のまま残ったのがその結果だ
  • set -f をスクリプト全体に入れておくと、肝心なところでグロブが効かなくなる。必要な区間だけ入れて set +f で戻す
  • 根本的な解決はクォートだ。set -f は他人のコードを直せないときの応急処置に近い

5. 配列展開四つの形で要素数を数える

位置パラメータで見た四つの組み合わせは配列にもそのままある。表記が変わるだけだ。

#!/usr/bin/env bash
arr=("annual report.pdf" "q3 data.csv" plain.txt)
count() { echo "  count=$#"; printf '  [%s]\n' "$@"; }
count "${arr[@]}"
count ${arr[@]}
count "${arr[*]}"
count ${arr[*]}
echo "要素の個数: ${#arr[@]}"
echo "先頭要素の文字数: ${#arr[0]}"
$ bash t2.sh
--- "${arr[@]}" ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- ${arr[@]}   ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "${arr[*]}" ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]
--- ${arr[*]}   ---
  count=5
--- 要素の個数: 3 ---
--- 先頭要素の文字数: 17 ---

1節の表がそのまま適用される。配列を配列らしく使う方法は "${arr[@]}" 一つだけだ。残る三つの形は配列を配列でないものにする。

最後の二行も押さえておく価値がある。${#arr[@]} は要素の個数3、${#arr[0]} は先頭要素の文字数17だ。角括弧の中に何が入るかで # の意味が変わる。

5.1 配列名だけを書くと先頭要素が出る

$ bash t11.sh
arr=("a:b" "c d" "e")
  $arr        = [a:b]
  ${arr[0]}   = [a:b]
  ${arr[@]:1} = [c d e]

$arr は配列全体ではなく ${arr[0]} だ。エラーを出さないので発見が遅れる。要素が一個だけの配列でテストすると、この失敗は最後まで表に出ない。テストデータに要素を最低二個入れる習慣がこの種のバグを漉し取る。

5.2 IFSは配列の未クォート展開にも働く

$ bash t11.sh
arr=("a:b" "c d" "e")
--- IFS=: にしてクォートなし ---
  count=4
  [a]
  [b]
  [c d]
  [e]
--- 同じ状態でクォートを付けると ---
  count=3
  [a:b]
  [c d]
  [e]
--- "${arr[*]}" は先頭のIFS文字で貼る ---
  count=1
  [a:b:c d:e]

最初の結果が興味深い。IFS がコロンなので a:b は二つに割れたが、c d の空白はもう区切りではなくそのまま残った。IFS を変えると何が切られるかが丸ごと変わる。

5.3 スライスと疎な配列

$ bash t11.sh
--- "${arr[@]:1:2}" ---
  count=2
  [c d]
  [e]
--- 要素を一つ消しても番号は振り直されない ---
s=(zero one two); unset 's[1]'
  count=2  indices=0 2
  [zero]
  [two]
--- declare -p で実際の形を確認 ---
declare -a s=([0]="zero" [2]="two")
declare -a arr=([0]="a:b" [1]="c d" [2]="e")

unset で真ん中を消すと番号は振り直されず穴が残る。${#s[@]} は2なのに有効な最後の添字は2だ。だから for ((i=0; i<${#s[@]}; i++)) のような添字ループはこういう配列で要素を取りこぼす。

  • 配列を回すときは添字ループではなく for x in "${arr[@]}" を使う。穴を勝手に飛ばしてくれる
  • 添字がどうしても要るなら ${!arr[@]} で実在する添字の一覧を受ける。上の出力の indices=0 2 がそれだ
  • declare -p は配列の実際の形を添字まで見せる。配列がおかしいとき最初に出力してみるものだ
  • スライス "${arr[@]:1:2}" にもクォート規則がそのまま適用される。クォートを外せばまた刻まれる
  • arr+=("新しい要素") は後ろに足し、arr=("新しい要素") は丸ごと入れ替える。確認すると前者は2個、後者は1個になった
  • 連想配列は declare -A で先に宣言する必要がある。宣言なしに文字列キーを使うと算術評価を経て添字0に入る

6. 空文字列と改行の入った要素はどこで消えるか

要素三個のうち真ん中が空文字列の配列を作って確認する。

$ bash t7.sh
--- 空文字列の要素が入った配列、${#arr[@]}=3 ---
  count=3
  [first]
  []
  [third]
--- 同じ配列をクォートなしで ---
  count=2
  [first]
  [third]

空の要素が跡形もなく消えた。要素は三つなのにコマンドには二つしか届かない。空になりうる選択項目の設定値を配列に入れてコマンドラインへ渡す構造なら、引数の位置が丸ごとずれて次の引数が見当違いの場所に入る。

$ bash t7.sh
--- 要素に改行が入った場合、${#arr2[@]}=2 ---
  count=2
  [line1
line2]
  [tail]
--- クォートなし: 改行もIFS文字なので切れる ---
  count=3
  [line1]
  [line2]
  [tail]

改行は既定の IFS に含まれる三文字の一つだ。だから改行の入ったファイル名はクォートのない展開で二つのファイル名になる。Linux のファイルシステムでファイル名に改行を入れることは禁じられていない。利用者のアップロードや展開結果を扱うコードなら実際に出会いうる。

6.1 空の配列をset -uの下で展開するとき

$ bash t6.sh
bash 5.2.37(1)-release
--- set -u の状態で "${empty[@]}" ---
  OK, 何もなく展開された: rc=0
--- "${empty[*]}" は違う ---
  count=1              # 空文字列が一個できる
--- "${empty[@]}" をコマンドへ渡すと ---
  count=0              # 引数がまったくない
--- ${empty[@]:-既定値} の定型句 ---
  [<既定値>]

bash 5.2.37 では set -u の下で空の配列を "${empty[@]}" で展開してもエラーにならず引数0個に展開された。この動作は bash 4.4 で変わったもので、それ以前のバージョンでは unbound variable エラーになったとされている。旧バージョンの bash はこの環境になく、確認できなかった。古いディストリビューションを対象にするスクリプトでは "${empty[@]:-}" の形で守る定型句がいまも使われる。

同じ出力で "${empty[*]}" が count=1 を出したことに注目したい。空の配列なのに引数が一つできた。空文字列一個だ。この状態でコマンドへ渡ると「引数がない」ではなく「空の引数がある」になり、コマンドの動きが変わる。

7. コマンド出力を配列へ入れる正しいやり方

ファイル二個の入ったディレクトリで四つの方法を比べる。ファイル一つの名前に空白がある。

$ bash t8.sh
files: annual report.txt|notes.txt|
--- arr=($(ls)) ---
  3 elements
  [annual]
  [report.txt]
  [notes.txt]
--- mapfile -t arr2 < <(ls) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- readarray -t arr3 < <(ls) ---
  2 elements
--- arr4=(*) ---
  2 elements
  [annual report.txt]
  [notes.txt]
--- mapfile -d '' arr5 < <(find . -maxdepth 1 -type f -print0) ---
  2 elements
  [./annual report.txt]
  [./notes.txt]

最初の方法だけが間違っている。arr=($(ls)) はコマンド出力を単語分割とグロブへそのまま通す。配列代入の括弧の中はクォートで包めない場所だ。arr=("$(ls)") と書くと今度は出力全体が要素一個になり、配列の意味がなくなる。

  • mapfile -t は行単位で読み、-t が行末の改行を取り除く。対象が行の一覧ならこれが基本形だ
  • readarray は mapfile の別名だ。同じ組み込みコマンドで、確認した結果も同じだった
  • パイプではなく < <(cmd) を使う理由がある。cmd | mapfile と書くと mapfile がサブシェルで走り、配列が外へ出てこない。サブシェルの記事と同じ根だ
  • 対象がファイル名なら arr=(*) が最も安全だ。シェルが直接一覧を作るので、どんな名前でも要素一個に入る
  • ただし arr=(*) は一致するファイルがないとき * という文字列一個の配列になる。shopt -s nullglob と併用するか [ -e "${arr[0]}" ] で確認する
  • 改行の入った名前まで面倒を見るなら mapfile -d '' と find -print0 の組み合わせを使う。ヌル文字はファイル名に入れられない唯一の文字なので区切りとして安全だ
  • mapfile は bash 4 以降の機能だ。POSIX sh へ戻る必要のあるスクリプトでは使えない

7.1 ファイル一覧を一つずつ回る二つの方法

$ bash t10.sh
--- find -print0 + read -d '' ---
    got [./-rf]
    got [./annual report.pdf]
    got [./keep me.txt]
  total=3
--- for f in $(find . -type f) ---
    got [./-rf]
    got [./annual]
    got [report.pdf]
    got [./keep]
    got [me.txt]
  total=5

三個のファイルが五個に増えた。下の形で rm を回すと存在しない report.pdf と ./keep に対して削除が試みられ、その名前のファイルが実在すれば消える。上の形の実際のコードはこうだ。

while IFS= read -r -d '' f; do
    echo "処理: [$f]"
done < <(find . -maxdepth 1 -type f -print0)

IFS= で空にしたこと、-r でバックスラッシュ解釈を切ったこと、-d '' で区切りをヌル文字に変えたこと、この三つがすべて必要だ。一つでも欠ければ特定の名前で崩れる。

8. 配列は関数へ値として渡らない

配列を関数へ渡そうとすると、届くのは配列ではなく引数が複数個だ。

$ bash t9.sh
--- 配列を値として渡せない。引数へ平らになる ---
arr=("annual report.pdf" "q3 data.csv")
takes "${arr[@]}"
  inside: $1=[annual report.pdf]  $#=2
--- 関数の中で配列へ組み直す ---
h() { local -a mine=("$@"); echo "  mine=${#mine[@]}"; }
  mine=2
--- 名前だけ渡して nameref で受ける (bash 4.3+) ---
byref() { local -n ref=$1; echo "  ${#ref[@]} elements, first=[${ref[0]}]"; }
byref arr
  2 elements, first=[annual report.pdf]
--- local -a はグローバルを汚さない ---
  inner has 2
  inner outside: [<unset>]
--- set -- "${arr[@]}" で位置パラメータへ入れ替え ---
  $#=2
  [annual report.pdf]
  [q3 data.csv]

三つの方法にそれぞれ持ち場がある。

  • 引数として受けて配列を作り直す。local -a mine=("$@") の一行で済む。最も単純で移植性も最良だ
  • 欠点は配列を一つしか渡せないことだ。二つ渡すには区切り役の引数を挟むような迂回が要る
  • 名前だけ渡して nameref で受ける。local -n ref=$1 は元をそのまま指すので、関数の中で書き換えれば外にも反映される
  • nameref は bash 4.3 以降の機能だ。そして仮引数名と渡した配列名が同じだと循環参照エラーになる。ref のようなありふれた名前ではなく接頭辞を付ける慣行がある
  • 位置パラメータへ入れ替える。set -- "${arr[@]}" のあとは "$@" がその配列になる。POSIX sh でも通る唯一の方法だ
  • ただし元々あった位置パラメータを上書きする。あとで要るなら別の配列へ先に取っておく
  • local -a で宣言した配列は関数の外から見えない。上の出力で <unset> が出たのがその確認だ
  • local なしに関数の中で配列を作るとグローバルになる。同じ名前を使う別の関数と静かに衝突する

8.1 引数をそのまま渡すラッパー

$ bash t13.sh
good: wrapper_good() { inner "$@"; }
  inner sees 2 arg(s):
    [annual report.pdf]
    [q3 data.csv]
bad:  wrapper_bad()  { inner $@; }
  inner sees 4 arg(s):
    [annual]
    [report.pdf]
    [q3]
    [data.csv]
--- オプションを前に付けて渡す ---
wrapper_opt() { inner --dry-run "$@"; }
  inner sees 2 arg(s):
    [--dry-run]
    [annual report.pdf]

ラッパースクリプトはこの失敗が最も頻繁に出る場所だ。docker や kubectl の前にオプションを二つ三つ足す薄いラッパーを作るとき、最終行の "$@" でクォートを落とすと空白の入った引数を渡した瞬間に静かに壊れる。普段のテストでは引数に空白がないので表に出ない。

9. オプションが付いたり外れたりするコマンドラインを組む

条件でオプションが変わるコマンドを作るとき、文字列で組み立てれば必ず壊れる。配列はまさにこの問題のためにある。

#!/usr/bin/env bash
opts=()
verbose=1
outfile="my output.log"
[ "$verbose" = 1 ] && opts+=(--verbose)
opts+=(--output "$outfile")
echo "${#opts[@]} args:"; printf '  [%s]\n' "${opts[@]}"
$ bash t12.sh
--- 配列で組み立て ---
  3 args:
    [--verbose]
    [--output]
    [my output.log]
--- 文字列で組み立てると ---
optstr="--verbose --output $outfile"
  コマンドが受け取るもの:
    [--verbose]
    [--output]
    [my]
    [output.log]

文字列側はファイル名が二片になった。コマンドは --output my と読み、output.log を別の位置引数として受け取る。エラーメッセージが出ればまだ幸運で、たいていは my という名前のファイルができる。

9.1 条件付き引数の空文字列の罠

$ bash t12.sh
flag=""
probe "$flag" other           ->  got 2 arg(s)
probe ${flag:+"$flag"} other  ->  got 1 arg(s)

"$flag" は値が空でも空の引数を一つ作る。引数をまったく渡さないようにするには ${flag:+"$flag"} のように値があるときだけ展開される形を使うか、そもそも配列へ条件付きで足すほうが読みやすい。

args=()
[ -n "$flag" ] && args+=("$flag")
cmd "${args[@]}" other

9.2 ハイフンで始まる名前と終端子

$ ls -1
-rf
annual report.pdf
keep me.txt

$ ls -1 -rf          # -rf をオプションとして読む
.
..

$ ls -1 -- -rf       # -- の後ろはすべてファイル名
-rf

名前がハイフンで始まるファイルはコマンドがオプションとして読む。これはクォートでは防げない。クォートは単語が割れるのを止めるだけで、割れていない一単語がオプションのように見えるという事実はそのまま残る。上の実行で ls -1 -rf は -r と -f のオプションとして解釈され、ファイルではなくカレントディレクトリの一覧を出した。

  • 解決は -- 終端子だ。その後ろのすべての引数はオプションでないものとして扱われる
  • rm -- "$file"、mv -- "$src" "$dst" のように取り返しのつかないコマンドには習慣として付ける
  • 別の方法はパスを ./ で始めることだ。./-rf はもうハイフンで始まらない
  • find が出すパスが ./ で始まるのはこの点で都合がよい。7節の出力の [./-rf] がその例だ
  • -- に対応しないコマンドもある。その場合は ./ 方式が唯一の代替だ
  • 利用者の入力をそのままコマンドへ渡す場面なら、終端子は選択ではなく必須と見る

10. 配列のないシェルでも引数は安全に渡せる

シバンが #!/bin/sh のスクリプトが本番環境で dash として実行されることはよくある。開発機で /bin/sh が bash に繋がっているとこの差は見えない。

$ dash -c 'arr=(a b c); echo "$arr"'
dash: 1: Syntax error: "(" unexpected

配列の構文そのものがない。ところが位置パラメータはあり、クォート規則も bash と同じだ。

$ dash tp.sh
--- "$@" in POSIX sh ---
  count=3
  [annual report.pdf]
  [q3 data.csv]
  [plain.txt]
--- $@ in POSIX sh ---
  count=5
  [annual]
  [report.pdf]
  [q3]
  [data.csv]
  [plain.txt]
--- "$*" in POSIX sh ---
  count=1
  [annual report.pdf q3 data.csv plain.txt]

bash とまったく同じ結果だ。したがって配列がなくても一覧を一つは安全に扱える。その一覧を位置パラメータに入れて "$@" で展開すればよい。

set -- "annual report.pdf" "q3 data.csv"
set -- "$@" "新しく追加したファイル.txt"     # 後ろに足す
for f in "$@"; do
    echo "処理: [$f]"
done
  • set -- "$@" "新しい項目" が配列の末尾追加にあたる。要素を一つずつ積み上げられる
  • $# が要素の個数を与える。${#arr[@]} と同じ役割だ
  • shift で前から一つずつ取り出せる。待ち行列のように使うパターンだ
  • 一覧が二つ以上要るならこの方法では限界がある。そこが bash をシバンに明記する時点だ
  • local は POSIX にない拡張だが dash で動くことを確認した。ただし標準ではないのですべての sh で保証されるわけではない
  • mapfile・readarray・local -n・declare -p はすべて bash 拡張だ。移植性が要るならこの四つを使わない
  • シバンを #!/usr/bin/env bash と明記することが、配列を使うスクリプトの最低条件だ。#!/bin/sh のままで配列を使えば、いつか別の機械で構文エラーで死ぬ

11. 覚える定型句は六つで足りる

ここまでに出たものを安全な形と危ない形で対にして整理する。

やりたいこと危ない形安全な形何が変わるか
引数をそのまま渡すcmd $@cmd "$@"空白の入った引数が割れない
配列を展開するcmd ${arr[@]}cmd "${arr[@]}"要素数がそのまま保たれる
コマンド出力を一覧へarr=($(cmd))mapfile -t arr < <(cmd)行単位で切るので空白とグロブを通さない

11.1 チェックリスト

  • 展開には基本的にダブルクォートを付ける。外すほうが例外で、外すときは理由をコメントに残す
  • 一覧は文字列ではなく配列に入れる。文字列に入れた瞬間に境界の情報が消える
  • 配列展開は "${arr[@]}" 一つだけを使う。アスタリスク形はログ出力用にだけ使う
  • コマンド出力を配列にするときは mapfile -t を使う。括弧の中のコマンド置換は使わない
  • ファイル名が対象ならシェルのグロブを直接使う。ls の出力を解析しない
  • 削除・移動・コピーのコマンドには -- 終端子を付ける
  • ロジックを直したら削除行を echo に替えて一度走らせ、対象一覧を目で見る
  • テストデータに空白の入った名前を必ず一つ入れる。この記事のすべての欠陥がその一つで露見した
  • 可能なら要素が最低二個のデータで試す。一個では $arr の失敗が表に出ない
  • IFS を変える必要があれば IFS=, read ... のようにコマンドの前に置いてそのコマンドにだけ適用する
  • ファイルを一行ずつ読むときは while IFS= read -r line の形をそのまま使う
  • 配列を使うスクリプトのシバンは #!/usr/bin/env bash と明記する
  • 配列がおかしければ declare -p で添字まで出力する。推測より速い
  • 静的検査器を入れればこの記事の失敗の大半がコミット前に引っかかる。未クォート展開は代表的な検出項目だ

12. 確認できなかったこと

実行で検証できず文書の根拠だけで書いた項目を一か所にまとめる。

  • bash 4.4 未満の set -u の動作。空の配列を "${arr[@]}" で展開したときエラーになったという記述は変更履歴に基づくもので、この環境に旧バージョンの bash がなく再現できなかった。6.1節の防御定型句を勧める根拠も同じ文書だ
  • zsh と ksh の配列の動作。zsh は未クォート展開で単語分割をしないなど規則そのものが違うが、実行できる環境ではなく確認できなかった。この記事の結論をそのまま zsh に当てはめてはいけない
  • busybox ash。最小コンテナイメージでよくあるシェルだが確認できなかった。10節の POSIX の結論がここでも成り立つかは対象環境で一度走らせるほうが確実だ
  • Linux の glibc 環境。実行環境は x86_64-pc-msys 向けの bash 5.2.37 と同じ環境の dash だ。クォートと分割の規則はファイルシステムと無関係なシェル内部の動作なので差の出る余地は小さいが、ファイル名まわりの例は対象環境で再現してみるほうがよい
  • 非常に長い配列の限界。引数の個数と総長にはカーネル側の上限がある。その境界で "${arr[@]}" がどう失敗するかは測っていない
  • 連想配列の走査順。declare -A で作った配列のキーの順序は定まっていないとされるが、この記事では実行で扱っていない
  • ロケールによるグロブの文字範囲。[a-z] のような範囲パターンがロケールで違う動きをする問題はこの記事の範囲外で、確認していない

FAQ

Q1. すべての展開にクォートを付ければよいのか

ほぼそうだ。実務でクォートを外すべき場面は稀だ。外すべきなのは意図的に一つの文字列を複数の引数へ刻みたいときだが、その状況ならそもそも配列を使うほうがよい。ただし何か所かはクォートがなくても安全だ。代入文の右辺 x=$y、[[ ]] の中、case の対象語がそれだ。この場所は単語分割が起きないようシェルが保証する。それでも一貫して付けるほうを勧める。例外を覚えるコストのほうが、クォート二つを余計に打つコストより大きい。そしてコードレビューで「ここは安全だから大丈夫」を毎回検証するより、「全部付いている」を確認するほうが速い。

Q2. "$*" はいつ使うのか

人が読む文字列を一つ作るときだ。ログに「このコマンドがこういう引数で実行された」を一行で残す場面が代表的だ。実行して確認すると "$*" は常に正確に一単語を作り、要素の間は IFS の先頭一文字で貼られる。逆に引数を他のコマンドへ渡す場面では絶対に使わない。三つの引数を渡したのに受ける側には引数一つとして届く。もう一つ注意点がある。ログ用に使うとしても、元の引数に空白があったかどうかは結合された文字列では区別できない。引数の境界まで正確に残したければ printf '[%s] ' "$@" のように各引数を包んで出力するほうがよい。

Q3. 配列代入にクォートを付けられないとはどういう意味か

arr=($(cmd)) で括弧全体をクォートで包む方法がないという意味だ。arr="($(cmd))" と書けば配列ではなく括弧の入った文字列になり、arr=("$(cmd)") と書けばコマンド出力全体が要素一個になる。配列代入の括弧の中は構造的に単語分割を通る場所だ。だからこの構文自体を使わないことが解決策になる。行の一覧なら mapfile -t、ファイルの一覧なら arr=(*) のようにグロブを直接使う。例外的に安全な場合もある。出力が空白のないトークンだけであることが確実で、グロブ文字の混ざる余地がなければ問題ない。ただしその確信が後で崩れるのが事故の典型だ。

Q4. set -f をスクリプト全体に入れてはいけないのか

グロブだけを切って単語分割は残るので半分の解決だ。空白の入ったファイル名の問題はそのまま残る。しかも肝心なところ、たとえば for f in *.log のような行が動かなくなる。実行して確認した結果 set -f の状態で *.txt はパターン文字のまま一単語で残った。使い道がまったくないわけではない。他人のコードをすぐ直せないがグロブの事故だけは止めたい状況、あるいは利用者の入力を短く扱う区間で set -f を入れて終わったら set +f で戻す形なら使える。根本的な解決はクォートと配列だ。

Q5. ファイル名に改行が入ることが実際にあるのか

ある。Linux のファイル名に入れられない文字はヌル文字とスラッシュの二つだけで、改行は禁止一覧にない。利用者が上げた圧縮ファイルを展開したり、別のシステムから移してきたデータを扱うコードなら実際に出会いうる。確認すると改行の入った要素はクォートのない展開で二つに割れる。改行が既定の IFS に入った三文字の一つだからだ。面倒を見るには区切りをヌル文字に変えるしかない。find -print0 で一覧を作り read -d '' または mapfile -d '' で受ける。ヌル文字がファイル名に入れられない唯一の文字なので、区切りに使える唯一の選択になる。

結論: 今日変える三つのこと

一つ目、一覧を文字列に入れるのをやめる。文字列にファイル名を複数入れた瞬間に境界の情報が消え、その後はシェルが IFS で推測して復元する。推測が外れる瞬間が事故だ。一覧は配列に入れて "${arr[@]}" で展開する。配列のないシェルなら位置パラメータに入れて "$@" で展開する。確認した結果、元の個数を守ったのはこの二つの形だけだった。

二つ目、コマンド出力を配列にするとき括弧の中のコマンド置換を使わない。ファイル二個の入ったディレクトリで arr=($(ls)) は要素三個の配列を作り、mapfile -t は正確に二個を作った。対象がファイル名なら arr=(*) のようにシェルのグロブを直接使うほうがさらによい。解析の段階そのものがなくなるからだ。

三つ目、削除・移動のコマンドに -- を付け、ロジックを直したら echo で一度走らせる。名前がハイフンで始まるファイルはクォートで防げず、実際に ls -1 -rf がファイルではなくオプションとして読むことを確認した。削除は取り返しがつかない。対象一覧を目で確認するのにかかる時間は数秒だ。

最後に一つ。この記事のすべての欠陥はテストデータに空白の入った名前を一つ入れるだけで全部露見した。次にファイル一覧を扱うコードを書いたら、touch "annual report.pdf" の一行をテストに足してみればよい。いまうまく動いているように見えるコードがどこで崩れるか、その場で分かる。
