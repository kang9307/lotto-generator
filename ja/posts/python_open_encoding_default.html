はじめに - encodingを省略したopen()は値をどこから得るのか

韓国語を含むテキストファイルをopen('data.txt').read()で読むコードは、開発者のPCでは問題なく動いていても、別のPCではUnicodeDecodeErrorで止まったり、エラーなしで文字が別のものに変わって返ってきたりする。コードは同じなのに結果が違うので、コードの外にもう一つ入力があることになる。その入力が、encoding引数を省略したときにインタープリターが補う既定値である。既定値がどこから来るのか、どれほど簡単に変わるのか、変わるとどんな出力になるのかは、以下の出力が示す。

エンコーディングの問題を扱う記事はすでに複数あり、軸が異なる。BOMの記事はファイル先頭の3バイトがパーサーを壊す場合を、cp949とUTF-8の文字化けの記事は壊れた形から原因をさかのぼる方法を、PowerShell 5.1のリダイレクトの記事はPowerShellがファイルを書くときに決まるエンコーディングを、zipファイル名の記事はアーカイブ内の名前のバイトを扱う。ここではPythonのopen()がエンコーディングを省略したときに使う値が決まる場所、その値を変えるUTF-8モード、危険な行を見つけるEncodingWarning、3.15で予定されている変更、そしてコードで安全に使うパターンに限定する。cp949の記事の8節には、PYTHONUTF8=1がopen()の既定を変えるという短い実行があり、以下の内容はその上に変数を増やして続けるものである。

扱う問いは次のとおりである。

  • encodingなしのopen()の既定値は何で、どの関数が返す値と同じか。
  • UTF-8で書いた韓国語ファイルを既定値で読むと、どの例外がどこで出るか。
  • 逆に既定値で書いたファイルをUTF-8で読むと何が見えるか。
  • 例外なしに文字が変わる場合と、書き込み段階で例外が出る場合は何か。
  • UTF-8モードは何を変え、何を変えないのか。
  • EncodingWarningはどの行に警告を出し、どの行には出さないのか。
  • PEP 686が定める3.15の変更は何か。

既定値はlocale.getencoding()が返す値である

まず実行環境の値を読む。次のコードは、ロケールのエンコーディングを返す二つの関数、UTF-8モードのフラグ、関連する環境変数二つ、標準出力のエンコーディングを一度に出力する。

import locale, os, sys
                    print('python                ', sys.version.split()[0])
                    print('getpreferredencoding  ', locale.getpreferredencoding(False))
                    print('getencoding           ', locale.getencoding())
                    print('utf8_mode             ', sys.flags.utf8_mode)
                    print('PYTHONUTF8            ', os.environ.get('PYTHONUTF8'))
                    print('PYTHONIOENCODING      ', os.environ.get('PYTHONIOENCODING'))
                    print('stdout.encoding       ', sys.stdout.encoding)
python                 3.13.3
                    getpreferredencoding   cp949
                    getencoding            cp949
                    utf8_mode              0
                    PYTHONUTF8             None
                    PYTHONIOENCODING       None
                    stdout.encoding        cp949

このPCではロケールのエンコーディングがcp949で、UTF-8モードはオフ(utf8_mode 0)であり、PYTHONUTF8とPYTHONIOENCODINGは設定されていない(None)。この状態で、open()が実際に使うエンコーディングを直接読む。

import locale, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    f = open('probe.txt', 'w')
                    print('open(w).encoding  ', f.encoding)
                    f.close()
                    print('open(r).encoding  ', open('probe.txt').encoding)
                    print('explicit utf-8    ', open('probe.txt', encoding='utf-8').encoding)
                    print('== getencoding()  ', open('probe.txt').encoding == locale.getencoding())
open(w).encoding   cp949
                    open(r).encoding   cp949
                    explicit utf-8     utf-8
                    == getencoding()   True

書き込みモードも読み込みモードもcp949が出て、encoding='utf-8'と書くとutf-8が出た。最後の行は、ファイルオブジェクトの既定のエンコーディングとlocale.getencoding()の戻り値を比べてTrueが出たものである。Python公式ドキュメントのopen()の項目は、この関係を次のように記している。"The default encoding is platform dependent (whatever locale.getencoding() returns), but any text encoding supported by Python can be used." 出力とドキュメントの文が一致している。

  • 既定値はPythonが選んだ定数ではなく、実行環境のロケールから読み取られる値である。このPCではcp949である。
  • ロケールが異なるPCで同じコードを実行すると、既定値も変わりうる。ドキュメントが「platform dependent」と記している理由である。
  • ファイルオブジェクトのencoding属性で、実際に適用された値をすぐ読める。エラーの原因を推測する前に最初に見る値である。
  • 出力のstdout.encodingの行は標準出力の属性であり、ファイルを開く既定値とは別の属性である。両方を一緒に動かす設定は6節で扱う。

UTF-8で書いた韓国語を既定値で読むと

最もよくある事故は、UTF-8で保存されたファイルをencodingなしで開くことである。エディター、git、他のOSで作られたファイルは、たいていUTF-8である。次のコードは、韓国語の文をUTF-8で書いてバイトを出力し、そのあとencodingなしで読む。

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_utf8.txt', 'w', encoding='utf-8') as f:
                        f.write('한글 테스트')
                    print(open('ko_utf8.txt', 'rb').read().hex(' '))
                    try:
                        open('ko_utf8.txt').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
ed 95 9c ea b8 80 20 ed 85 8c ec 8a a4 ed 8a b8
                    UnicodeDecodeError 'cp949' codec can't decode byte 0xed in position 0: illegal multibyte sequence

1行目は、ファイルに実際に入った16バイトである。韓国語の1文字が3バイト(ed 95 9cが最初の文字)、空白が1バイト(20)である。読み込みでは、位置0の0xedでcp949コーデックが「illegal multibyte sequence」を出して止まった。理由は出力そのものが示している。書き込み側はencoding='utf-8'を明示し、読み込み側は省略して、前の節で見たcp949が適用された。例外メッセージの中にコーデック名'cp949'が入っているので、メッセージだけで読み込み側にどのエンコーディングが適用されたかが分かる。

  • 例外の型はUnicodeDecodeErrorで、メッセージにはコーデック名、問題のバイト(0xed)、位置(position 0)が含まれる。
  • コーデック名がcp949なら、読み込み側のエンコーディングがcp949だったということなので、最初に疑うのはファイルではなく、読み込むコードのencoding引数である。
  • この例外は環境が同じなら毎回再現する。書き込み側と読み込み側が同じPC、同じ設定だと問題が見えない点は、6節の往復の出力にある。

逆方向 - 既定値で書いたファイルをUTF-8で読むと

encodingなしで書いたファイルを、別の場所でUTF-8として読むと、向きが逆の同じ問題が起きる。次のコードは、既定値で書いた韓国語のバイトを見て、cp949で読んだ結果、UTF-8で読んだ結果、errors='replace'を付けて読んだ結果を順に出力する。韓国語を直接出力するとコンソールのエンコーディングが関わるので、ascii()でコードポイントのエスケープを出力する。

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    with open('ko_default.txt', 'w') as f:
                        f.write('한글 테스트')
                    print(open('ko_default.txt', 'rb').read().hex(' '))
                    print(ascii(open('ko_default.txt', encoding='cp949').read()))
                    try:
                        open('ko_default.txt', encoding='utf-8').read()
                    except UnicodeDecodeError as e:
                        print(type(e).__name__, e)
                    print(ascii(open('ko_default.txt', encoding='utf-8', errors='replace').read()))
c7 d1 b1 db 20 c5 d7 bd ba c6 ae
                    '\ud55c\uae00 \ud14c\uc2a4\ud2b8'
                    UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte
                    '\ufffd\u0471\ufffd \ufffd\u05fd\ufffd\u01ae'

既定値で書いた同じ文が、今度はc7 d1 b1 db …として保存された。1文字が2バイトのcp949のバイトである。cp949で読むと元の韓国語(\ud55c\uae00 …)が復元され、UTF-8で読むと最初のバイト0xc7で「invalid continuation byte」となって止まる。errors='replace'を付けると例外は消えるが、結果の文字列は\ufffd(置換文字)と無関係な文字(\u0471、\u05fd、\u01ae)で埋まり、元の文は文字列に残っていない。

公式ドキュメントのerrorsの項目は、既定の動作を次のように記している。"'strict' to raise a ValueError exception if there is an encoding error. The default value of None has the same effect." つまりerrorsを書かない呼び出しはstrictであり、上の例外はその既定の動作の結果である。

  • cp949で書いた韓国語は1文字2バイト、UTF-8で書いた韓国語は1文字3バイトで出力に現れる(3節と4節のバイト列の比較)。
  • 同じ文でも二つのエンコーディングのバイトは異なるので、一方で書いたファイルを他方で読むことは、どちらの方向でも変換ではなく誤読である。
  • errors='replace'はエラーを隠して情報を消す。この出力では元のバイトc7が\ufffdに変わり、文字列から復元できなかった。
  • 壊れたバイトを残すにはerrors='backslashreplace'があり、9節で出力を比較する。

静かに間違う場合と書き込みで失敗する場合

すべての誤読が例外で終わるわけではない。次のコードは、UTF-8のバイトをcp949として解釈したときに例外が出る文字列と出ない文字列を並べる。最後の部分は、cp949で表現できない文字(U+2728)を既定値で書く場合である。

import os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    print('café'.encode('utf-8').hex(' '))
                    for s in ['한글 테스트', '가나다라마바사', 'abc', 'caf\u00e9', '\u2014 dash']:
                        b = s.encode('utf-8')
                        try:
                            print('silent', ascii(s), '->', ascii(b.decode('cp949')))
                        except UnicodeDecodeError as e:
                            print('error ', ascii(s), '->', e.reason, 'at byte', e.start)
                    try:
                        open('emoji.txt', 'w').write('ok \u2728')
                    except UnicodeEncodeError as e:
                        print(type(e).__name__, e)
                    print(os.path.getsize('emoji.txt'))
63 61 66 c3 a9
                    error  '\ud55c\uae00 \ud14c\uc2a4\ud2b8' -> illegal multibyte sequence at byte 0
                    error  '\uac00\ub098\ub2e4\ub77c\ub9c8\ubc14\uc0ac' -> illegal multibyte sequence at byte 2
                    silent 'abc' -> 'abc'
                    silent 'caf\xe9' -> 'caf\ucc55'
                    error  '\u2014 dash' -> illegal multibyte sequence at byte 0
                    UnicodeEncodeError 'cp949' codec can't encode character '\u2728' in position 3: illegal multibyte sequence
                    0

1行目はcaféのUTF-8のバイト63 61 66 c3 a9である。韓国語の文、ハングル音節が続く文、ダッシュ(U+2014)を含む文字列は例外で終わり、ASCII文字だけのabcは二つのエンコーディングで同じなのでそのまま出た。ところがcaféは、例外なしにcaf\ucc55として読まれた。末尾の2バイトc3 a9が、cp949で有効な2バイトの1文字(U+CC55)として解釈された結果である。例外が出ないので、この誤読は画面やデータを見るまで表に出ない。

書き込みでは逆に例外が出る。open('emoji.txt', 'w').write('ok \u2728')はUnicodeEncodeError: 'cp949' codec can't encode character '\u2728'で終わり、ファイルサイズを読むと0である。ファイルは作られたが、書こうとした内容は1バイトも入らなかった。

UTF-8モード - 変わるものと変わらないもの

公式ドキュメントのUTF-8 Modeの項目は、有効化の方法を次のように記している。UTF-8モードは-X utf8コマンドラインオプションとPYTHONUTF8環境変数で有効・無効にする。有効なときに変わるものとして、ファイルシステムのエンコーディングがUTF-8になり、open()、io.open()、codecs.open()が既定でUTF-8を使うと記している。ただしエラーハンドラーは引き続きstrictなので、バイナリファイルをテキストモードで開いたときは、意味のないデータが出るのではなく例外が出やすいと付け加えている。次のコードは、これらの文に対応する値を一度に出力する。以下の出力は、同じスクリプトにオプションだけ変えて与えた結果である。

import sys, locale, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    open('probe.txt', 'w').close()
                    f = open('probe.txt')
                    print('utf8_mode      ', sys.flags.utf8_mode)
                    print('open() default ', f.encoding)
                    print('stdout         ', sys.stdout.encoding)
                    print('getencoding    ', locale.getencoding())
                    print('preferred      ', locale.getpreferredencoding(False))
                    print('fs encoding    ', sys.getfilesystemencoding())
                    print('locale option  ', open('probe.txt', encoding='locale').encoding)

オプションなしの出力である。

                    getencoding     cp949
                    preferred       cp949
                    fs encoding     utf-8

表は5通りのオプションの出力をそのまま写したものである。ここから読み取れることは次のとおりである。

  • -X utf8とPYTHONUTF8=1は同じ結果になった。どちらもutf8_modeが1になり、open()の既定と標準出力のエンコーディングがutf-8に変わった。
  • -X utf8=0とPYTHONUTF8=0は、オプションなしの場合と同じ結果である。この環境では、UTF-8モードを無効にする値が既定の状態と区別できなかった。
  • locale.getencoding()はどの場合でもcp949である。PEP 686はこの関数を、UTF-8モードを無視してロケールのエンコーディングを返す新しいAPIと説明しており、出力がその説明と一致している。
  • locale.getpreferredencoding(False)はUTF-8モードでutf-8に変わる。同じ「ロケールのエンコーディング」を尋ねる二つの関数の答えが違うので、どちらの関数で値を確認したかによって判断が変わる。
  • encoding='locale'を指定すると、UTF-8モードでもcp949が出た。ロケールのエンコーディングをあえて使う必要があるファイル(たとえばその形式で保存された既存の設定ファイル)には、この値が使われる。
  • ファイルシステムのエンコーディング(fs encoding)は、UTF-8モードかどうかに関係なくutf-8だった。

「自分のPCでは動く」が生まれる過程は、次のコードの出力に表れる。次のコードは、韓国語をencodingなしで書き、バイトを出力し、encodingなしで読み直し、cp949で読む。韓国語が直接見えるように、標準出力はUTF-8に合わせてある。同じコードをオプションなしと-X utf8で実行した。

import sys, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    sys.stdout.reconfigure(encoding='utf-8')
                    with open('m2.txt', 'w') as f:
                        f.write('한글 테스트')
                    print(open('m2.txt', 'rb').read().hex(' '))
                    print(open('m2.txt').read())
                    try:
                        open('m2.txt', encoding='cp949').read()
                    except UnicodeDecodeError as e:
                        print('cp949 read:', type(e).__name__, e)

オプションなしで実行した出力である。

c7 d1 b1 db 20 c5 d7 bd ba c6 ae
                    한글 테스트

-X utf8で実行した出力である。

ed 95 9c ea b8 80 20 ed 85 8c ec 8a a4 ed 8a b8
                    한글 테스트
                    cp949 read: UnicodeDecodeError 'cp949' codec can't decode byte 0xed in position 0: illegal multibyte sequence

オプションなしではc7 d1 …(cp949のバイト)が保存されてそのまま読み戻されるので、エラーはない。同じコードに-X utf8だけを加えると、保存されるバイトがed 95 9c …(UTF-8)に変わり、今度はcp949で読む行でUnicodeDecodeErrorが出る。コードは1文字も変わっていない。変わったのは既定値ひとつだけである。これが、設定の異なるPCの間でファイルをやり取りするときに生じるずれの、最小の再現である。

UTF-8モードは過去のファイルにも影響する。先ほどcp949で保存したファイルを、-X utf8で実行したインタープリターでencodingなしに開くと、次の例外が出た。

UnicodeDecodeError 'utf-8' codec can't decode byte 0xc7 in position 0: invalid continuation byte

UTF-8モードを有効にしても問題がなくなるわけではなく、既定値の向きが変わるだけである。cp949のファイルがある環境では、有効にした瞬間にそのファイルが読めなくなる。

EncodingWarningで書き忘れを見つける

-X warn_default_encodingオプションを有効にすると、encoding引数を省略した呼び出しがEncodingWarningを出す。次のコードは、エンコーディングの使い方7通りを1つのファイルに置いたものである。4行目は省略、5行目はPath.read_text()での省略、9行目はencoding=Noneである。

import pathlib, os, tempfile; os.chdir(tempfile.mkdtemp())
                    with open('a.txt', 'w', encoding='utf-8') as f:
                        f.write('x')
                    open('a.txt').read()
                    pathlib.Path('a.txt').read_text()
                    open('a.txt', encoding='utf-8').read()
                    open('a.txt', 'rb').read()
                    open('a.txt', encoding='locale').read()
                    open('a.txt', encoding=None).read()
C:\demo\warn.py:4: EncodingWarning: 'encoding' argument not specified
                      open('a.txt').read()
                    C:\demo\warn.py:5: EncodingWarning: 'encoding' argument not specified
                      pathlib.Path('a.txt').read_text()
                    C:\demo\warn.py:9: EncodingWarning: 'encoding' argument not specified
                      open('a.txt', encoding=None).read()

警告が出たのは4・5・9行目だけだった。書き込みモードでencoding='utf-8'を書いた2行目、読み込みで書いた6行目、バイナリモード('rb')の7行目、encoding='locale'の8行目には警告がなかった。9行目が示すのは、encoding=Noneが省略と同じ扱いになるという点である。警告を例外に引き上げると、最初の箇所で止まる。

                    EncodingWarning: 'encoding' argument not specified

同じ警告は、環境変数PYTHONWARNDEFAULTENCODING=1でも有効にできた。出力はオプションで有効にした場合と同じだった。環境変数は、コードに手を入れずにテストランナーやCIで有効にするのに役立つ。UTF-8モード(-X utf8)と一緒に有効にしても、警告は同じ3行で出た。

警告はコードが実行された行でしか出ない。一度も実行されない分岐のopen()には警告がない。静的に調べる方法も併せて置く。次は、標準ライブラリのastで、encodingのないテキストモードのopen()とread_text()を探す短い検査器である。

import ast, sys
                    hits = []
                    for path in sys.argv[1:]:
                        tree = ast.parse(open(path, encoding='utf-8').read())
                        for node in ast.walk(tree):
                            if not isinstance(node, ast.Call):
                                continue
                            name = ast.unparse(node.func)
                            has_enc = any(k.arg == 'encoding' for k in node.keywords)
                            if name == 'open':
                                mode = node.args[1].value if len(node.args) > 1 else 'r'
                                if 'b' not in mode and not has_enc and len(node.args) < 4:
                                    hits.append((path, node.lineno, 'open() without encoding'))
                            elif name.endswith('.read_text') and not has_enc and not node.args:
                                hits.append((path, node.lineno, name + '() without encoding'))
                    for path, line, msg in sorted(hits):
                        print(path + ':' + str(line), msg)

対象は、encodingなしで書かれた典型的な形を含む例のファイルである。

import json, pathlib
                    cfg = json.load(open('config.json'))
                    with open('out.txt', 'w') as f:
                        f.write('x')
                    raw = open('in.bin', 'rb').read()
                    ok = open('in.txt', encoding='utf-8').read()
                    note = pathlib.Path('note.txt').read_text()

2つのファイルに対して実行した出力である。

legacy.py:2 open() without encoding
                    legacy.py:3 open() without encoding
                    legacy.py:7 pathlib.Path('note.txt').read_text() without encoding
                    warn.py:4 open() without encoding
                    warn.py:5 pathlib.Path('a.txt').read_text() without encoding

json.load(open('config.json'))のように呼び出しの中に入れ子になったopen()もlegacy.py:2として検出され、バイナリモードの行とencodingを書いた行は検出されなかった。ただしこの検査器は、encoding=Noneがある9行目を見逃す(warn.py:9が一覧にない)。一方EncodingWarningはその行を捕まえた。2つの方法は見逃す場所が違うので、実行される経路は警告で、実行されない分岐は静的検査で、と分けて使う。

  • EncodingWarningは、実際に実行された呼び出しについてのみ出る。
  • encoding=Noneは、省略と同じように警告を出す。
  • UTF-8モードを有効にしても警告は消えなかった。警告の目的は、既定値に頼っている行を明らかにすることである。
  • 静的検査は実行されない分岐まで見るが、変数で渡した引数やencoding=Noneのような場合には別の規則が必要になる。

PEP 686 - 3.15の計画

PEP 686の概要は、次の文で始まる。"This PEP proposes enabling UTF-8 mode by default. With this change, Python consistently uses UTF-8 for default encoding of files, stdio, and pipes." 2026-10-06時点の文書では、上部の状態はFinal、対象バージョンはPython 3.15である。仕様は「Python will enable UTF-8 mode by default from Python 3.15.」と記し、無効にする方法としてPYTHONUTF8=0と-X utf8=0を案内している。UTF-8 Modeのドキュメントにある3.15についての案内は1文である。"Python 3.15 will make Python UTF-8 Mode default."

この計画をこれまでの実行と重ねて読むと、3点が出てくる。

  • 3.13で-X utf8を有効にした実行(6節)は、文書が3.15の既定の状態と定めた動作と同じ形である。3.15では、この動作がオプションなしで既定になる。
  • 3.15以降でも、ロケールのエンコーディングが必要なファイルにはencoding='locale'を使い、この値は6節の実行でUTF-8モードに関係なくcp949を返した。
  • 既定値の向きが変わるので、cp949で保存されていてencodingなしで読む既存のコードは、6節の最後の例外と同じ形で読み込みに失敗する可能性がある。

3.15より前のバージョンでは、既定値に頼るコードは環境ごとに動作が変わる。計画があるという事実は、現在のバージョンのコードを安全にはしない。エンコーディングを明示した呼び出しは、2節と6節の出力のとおり、指定した値をそのまま使う。

安全な読み書きのパターン

これまでの実行から得た規則は1行である。テキストモードの読み込みと書き込みの両方でencodingを書く。6節の往復実行では、UTF-8モードを有効にした状態でも、明示したcp949がそのまま適用された。状況ごとの書き方と、この環境で出た出力を表にまとめた。

状況書き方この環境の出力
通常のテキストファイルopen(path, encoding='utf-8')ファイルオブジェクトのencodingがutf-8(2節)
pathlibwrite_text(s, encoding='utf-8')、read_text(encoding='utf-8')韓国語がed 95 9c ea b8 80で保存
改行をLFに固定open(path, 'w', encoding='utf-8', newline='\n')61 0a 62 0a

表の改行・BOM・JSONの行は、次の実行で出た値である。まず改行である。エンコーディングとは別に、テキストモードは書き込み時に改行も変換する。

import pathlib, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    p = pathlib.Path('p1.txt')
                    p.write_text('한글\n둘째', encoding='utf-8')
                    print(p.read_bytes().hex(' '))
                    with open('nl_default.txt', 'w', encoding='utf-8') as f:
                        f.write('a\nb\n')
                    with open('nl_lf.txt', 'w', encoding='utf-8', newline='\n') as f:
                        f.write('a\nb\n')
                    print(open('nl_default.txt', 'rb').read().hex(' '))
                    print(open('nl_lf.txt', 'rb').read().hex(' '))
ed 95 9c ea b8 80 0d 0a eb 91 98 ec a7 b8
                    61 0d 0a 62 0d 0a
                    61 0a 62 0a

1行目はPath.write_text()で書いた한글\n둘째のバイトで、改行の位置に0d 0a(CRLF)が入った。2行目はopen(..., 'w')の既定の動作で、a\nb\nが61 0d 0a 62 0d 0aになったもの、3行目はnewline='\n'を付けて0aだけが残ったものである。このPCでは改行が自動的に変換される。

import csv, json, os, tempfile
                    os.chdir(tempfile.mkdtemp())
                    open('bom.txt', 'wb').write(b'\xef\xbb\xbf' + '가'.encode('utf-8'))

                    print(open('d.json', 'rb').read().hex(' '))

                        csv.writer(f).writerow(['이름', 'x'])
                    print(open('c.csv', 'rb').read().hex(' '))

                    '\uac00'
                    7b 22 6b 22 3a 20 22 ea b0 92 22 7d
                    ec 9d b4 eb a6 84 2c 78 0d 0a

BOM付きのファイルをutf-8で読むと、最初の文字の前に\ufeffが残り('\ufeff\uac00')、utf-8-sigで読むと消える('\uac00')。BOMの用途と問題はBOMの記事が詳しく扱っている。JSONはensure_ascii=Falseのとき韓国語がUTF-8の3バイトで保存され、CSVは韓国語の名前がUTF-8のバイトで保存された。

最後に、壊れたバイトを扱うerrorsの値の出力を比較する。入力は、cp949で保存された韓国語をUTF-8として誤って読む場合である。

b = '한글'.encode('cp949')
                    print(b.hex(' '))
                    print(ascii(b.decode('utf-8', errors='replace')))
                    print(ascii(b.decode('utf-8', errors='backslashreplace')))
c7 d1 b1 db
                    '\ufffd\u0471\ufffd'
                    '\\xc7\u0471\\xdb'

replaceは元のバイトを消す(\ufffd)が、backslashreplaceは\xc7、\xdbのようにバイトの値を文字列に残す。原因の分析に手がかりが必要なら、後者のほうがよい。どちらも誤読そのものは直せず、正しいエンコーディングを書くことが解決策である。

まとめると、次の項目でコードを点検できる。

  • テキストモードのopen()すべてにencodingがあるか。
  • Path.read_text()とwrite_text()にencodingがあるか。
  • CSVを開く箇所にnewline=''があるか。
  • ロケールのエンコーディングを使う意図があるなら、encoding='locale'として表れているか。
  • テストランナーやCIで、-X warn_default_encodingによる警告が0件であることを確認しているか。
  • ファイルをやり取りする相手のエンコーディングが文書で決まっているか。

確認できなかったこと

  • Python 3.15のインタープリターでの動作。このPCには3.13しかなく、3.15の既定のUTF-8モードと実際の既定値は、PEP 686とUTF-8 Modeのドキュメントの文言からの引用だけである。3.15でcp949のファイルの読み込みが失敗しうるという記述は、3.13のUTF-8モードの出力から推し量ったものである。
  • LinuxやmacOSで同じコードが出す出力。ロケールがUTF-8の環境での既定値は実行していない。
  • 他のロケールのWindows(英語、日本語など)での既定値。このPCは韓国語ロケールひとつである。
  • Windowsのシステムロケールで「UTF-8を使用」のオプションを有効にした場合の既定値。
  • sys.stdoutがパイプやファイルにつながれたときのエンコーディング。6節の標準出力の値は、コンソール環境で得たものである。
  • EncodingWarningが、subprocessやio.TextIOWrapperなどopen()の外の呼び出しで出る範囲。
  • -X utf8=0とPYTHONUTF8=0が、この環境で既定の状態と同じ結果になった理由。cp949ロケールであること以外の設定との相互作用は実行していない。
  • cp949とUTF-8以外のエンコーディング(UTF-16、EUC-KRの変種、拡張完成型の範囲外の文字)での動作。
