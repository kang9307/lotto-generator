代码是开放的，名字不是 - 开源许可证不决定的商标、域名与发布权限

许可证规定的是代码的使用条件。项目属于谁，是在许可证之外决定的

2026-09-12 开发/基础设施

任何一个开源项目，仓库最上面都放着一份许可证文件。读完那一份，就能确定这份代码能不能复制、能不能修改、改完之后能不能再发出去、发出去时要附带什么。可是那一份无论读得多仔细，始终答不出一个问题。这个项目属于谁。

需要分清的只有一件事。许可证是为代码这一著作物规定使用条件的文件，而不是为项目这个组织及其附带资产确定归属的文件。这不是抽象的说法，而是多家基金会早已用一句话写进公开政策的内容。Linux Foundation 的商标使用指南这样写：A copyright license, even an open source copyright license, does not include an implied right or license to use a trademark that may be related to the project developing the licensed software.

所以分叉从一开始就只是一半。代码可以整份带走，名字却带不走。域名带不走，取包的那个地址带不走，把更新推送出去的那条通道也带不走。把许可证读得再准确，也读不出这份清单，因为它根本不是许可证管辖的范围。

下文作为依据的是两份许可证正文、开源定义文件、四份公开商标政策，以及 Python 包索引的名称保留规定。引用只限于这些文件实际写下的范围。用作例子的项目都选自有公开政策文件的一方，不涉及进行中争议的当事方，也不评判其中的是非。裁断某一具体事件不是这里要做的事，文件只引到看清结构所需的程度。

缘起 - 属于谁这个问题从哪里冒出来

触发这篇文章的，是一篇就某个广泛使用的开源项目追问这个项目属于谁的公开文章。把那篇文章列出的条目过一遍，有一点很显眼。代码的所有权从一开始就不是争点。被提出来的争点全在代码之外：商标落在哪个法人名下、官方站点的基础设施由谁运维、扩展功能送到用户手里的那条通道由谁开合、董事会由谁决定。

那件事本身有多项程序仍在进行，也还有尚待判断的部分。代替那些判断作出结论，不是这里要做的事。要带过来的只有一样，问题的形状。

问题的形状是这样的。许可证已经给出了答案：代码人人都可以复制、修改、再分发。可是在给出这个答案之后，大约还有六个格子是空的。这些格子在许可证文件里哪儿都找不到，而且各自绑在不同的法律、不同的合同、不同的账号上。

要紧的是，这个形状并非某一个项目独有。设了基金会的项目、由一家公司写出大部分提交的项目、一个人在周末维护的项目，都有同样的六个格子。不同的只是每个格子里写着谁的名字，以及那个名字有没有出现在公开文件里。

许可证实际决定的东西

许可证做的事又窄又清楚。持有著作权这一排他性权利的一方，声明把其中一部分权利以什么条件许给他人。许可的对象大致落在四个方面。

  • 复制 — 能不能做副本。开源许可证在这里一律回答能。
  • 修改 — 能不能改。改完的东西能不能再发出去。
  • 分发 — 原版也好改版也好，能不能交给别人。交的时候要附带什么。
  • 条件 — 保留标示、随附声明文件、若是 copyleft 则向接收方提供源码、是否附带专利许可。

到此为止就是全部。开源定义的十个条目里，同样没有关于商标、治理或所有主体的条款。那份文件只处理分发与使用的权利。

不过关于名字的一句话挂在开源定义第4项的末尾，方向很值得注意。The license may require derived works to carry a different name or version number from the original software. 这不是把名字交出去的条款，而是允许许可证要求衍生物换一个名字的条款。连开源定义本身都预设了名字是不跟着走的那一部分。

条目许可证决定吗若不决定，在哪里决定
代码能否复制、修改、分发决定—
分发时必须附带的声明决定—
触发提供源码义务的条件决定—
是否附带专利许可决定—
能否使用项目名称与徽标不决定商标法与商标权人公开的商标政策
官方域名与站点由谁运营不决定与注册商的合同以及注册人名义
包注册表里那个名字的位置不决定注册表条款与名称保留、移交政策
合并、发布、签名的权限归谁不决定托管账号的组织设置与项目治理
持有资产的法人与董事会构成不决定章程与董事会规程
论坛、问题、文档站点由谁运营不决定付费并签订合同的一方

许可证正文如何把商标切开

说许可证不处理商标并不准确。有多份许可证明确地把商标切开了。那不是沉默，而是排除。

Apache License 2.0 第6条的标题干脆就是商标。This License does not grant permission to use the trade names, trademarks, service marks, or product names of the Licensor, except as required for reasonable and customary use in describing the origin of the Work and reproducing the content of the NOTICE file. 留下的例外只有两个：说明作品来源时的通常范围，以及原样再现声明文件的内容。

MPL 2.0 第2.3项也点在同一个位置。This License does not grant any rights in the trademarks, service marks, or logos of any Contributor. 这里的例外同样只限于遵守声明要求所必需的范围。

值得留意的是，要求保留声明与允许使用商标不是同一回事。Apache License 2.0 第4条要求再分发时在源码中保留著作权、专利、商标与署名声明，并在存在声明文件时包含其内容。这是保留的义务，不是可以使用的许可。把两句话连起来读，方向会整个反过来。

一些简短的宽松型许可证里，干脆没有商标条款。没有条款并不意味着许可。商标是依据与著作权不同的基础产生的权利，因此著作权许可证的沉默对那项权利没有任何影响。Linux Foundation 的政策文件把同一逻辑再往前推了一段：开源许可证允许对著作物无限制地修改，基金会也无意妨碍这项权利，但使用某个具体商标的权利，并不由该软件是以开源许可证获得这一事实来决定。

文件关于商标写了什么留下的例外
Apache License 2.0 第6条不授予使用许可方商号、商标、服务标记、产品名称的许可说明来源的通常范围、再现声明文件
Apache License 2.0 第4条再分发时在源码中保留商标声明并包含声明文件内容是保留义务，不是使用许可
MPL 2.0 第2.3项不授予对任何贡献者商标、服务标记、徽标的任何权利遵守声明要求所必需的范围
没有商标条款的简短许可证对商标只字未提沉默不是许可，权利的基础本就不同
开源定义 第4项允许要求衍生作品使用不同的名称或版本号名字不跟着走更接近默认状态

许可证不决定的六个格子

把留在许可证之外的格子收拢起来，一共六个。要害在于，把每一个格子按住的依据各不相同。

  • 商标与名称 — 由商标法以及商标权人公开的商标政策决定。这与代码完全是两个法律领域。
  • 域名与官方站点 — 由与注册商的合同以及注册人名义决定。合同结束，位置也随之结束。
  • 包注册表账号与分发通道 — 由该注册表的条款、名称保留与移交政策，以及账号所有者名单决定。
  • 仓库管理权限 — 由托管账号的组织设置决定。合并权限、打标签、发布产物上传、流水线密钥值都挂在这里。
  • 基金会与法人结构 — 由章程与董事会规程决定。哪些资产属于法人、谁来决定董事，就是这个格子的内容。
  • 社区基础设施 — 论坛、问题跟踪器、文档站点、翻译平台、邮件列表。大体上绑在付费的一方身上。

这六个格子有一个共同点。全都绑在某一个账号或某一个法人身上，而且不像代码那样可以复制。仓库几秒钟就能出一份副本，域名却出不了副本。注册表里同一个名字的位置也只有一个。所以这些格子一旦分开，立刻就变成排他性的选择。

商标 - 代码可以分叉，名字带不走

六个格子里最常被误解的就是商标，因为代码自由流动这件事会带出名字也该如此的推测。公开的商标政策写的正好相反。

Apache 软件基金会的商标政策开篇就是。The Apache Software Foundation (ASF) owns all ASF-related trademarks, service marks, and graphic logos on behalf of our project communities, and the names of all ASF projects are trademarks of the ASF. 这是把项目名称本身宣告为基金会商标，而持有的名义是代表社区。

Python 软件基金会写明，它持有作为注册商标的语言名称、徽标以及若干活动名称。随后用一句话收拢。All trademarks, even those that apply to open source software, must be used according to certain legal requirements. 不过政策并不只做禁止：它还举例写明，指向与该语言配合使用或适用于该语言的产品名形式是被允许的。用在公司名称上则另有事先书面许可的要求。

WordPress 基金会的政策写明，名称与徽标的商标由基金会持有并监管，相当于活动名称的另一项商标由基金会的子公司法人持有。希望作商业使用的，则指引联系持有独占商业许可的一方。这种安排展示的是，商标的持有与商业开发的权限可以落在不同主体身上。

Linux Foundation 的政策与前三者不同，它先把原理写出来：著作权许可证即便是开源的，也不包含使用相关商标的默示权利。而且它对注册行为的禁止非常明确——不得试图把基金会的商标注册为商标、商号、域名或经营字号。

公开商标政策关于持有主体写了什么关于域名写了什么
Apache 软件基金会基金会代表社区持有全部商标，项目名称本身就是基金会的商标禁止引起混淆的域名使用，不允许把产品名用作二级域名
Python 软件基金会语言名称是注册商标，徽标与活动名称也由基金会持有用在公司名称上需要事先书面许可
WordPress 基金会名称与徽标的商标由基金会持有并监管，活动商标由子公司法人持有不允许用作域名或顶级域名的一部分
Linux Foundation基金会法人持有商标与徽标，并写明许可证不授予商标权这一原理不得把商标用作域名或其一部分，也不得注册为商标、商号、域名或字号

这四份文件安排各不相同，却填的是同一个格子。而且四份都把域名单独写一段。原因在下一节。

域名 - 握住默认路径的那个位置

域名之所以重要，不是因为搜索排名，而是因为它是默认路径。安装说明的第一行、文档里的链接、更新检查请求指向的地址、信任库指向的位置，全都汇到同一个域名上。当官方站点同时承担下载、文档与扩展目录时，一个域名就同时干了三件事。

域名不是所有权，而是注册。它靠与注册商的合同维持，绑定在注册人名义上，而那个名义装在一个账号里。它不像代码那样可以分开。握住这个座位的一方可以决定哪一份软件从那个地址发出去；而只要已安装的版本还在持续访问那个地址，这种关系就会维持相当长的时间。

商标政策把域名单列出来也正因为此。名字进了域名，就既是名字的使用，又是路径的占用。两件事叠在同一个字符串上，因此政策大体都朝着不让它们叠在一起的方向来定。

包注册表里的名字位置

用户实际拿到软件的路径，往往不是仓库而是注册表。配置文件里写着一行名字，每次构建都会去解析它。所以注册表里那个名字的位置，才是分发路径的实体。

这个位置绑在账号上。一个名字带着一份所有者名单，只有所有者能发布新版本，只有所有者能移交权限。而当名字出现争议时注册表如何处理，写在公开政策文件里。

Python 包索引的名称保留规定就是典型。那份规定首先把活跃项目和被弃置的项目分开。只有在被弃置的情况下，而且要把列出的条件全部满足，名字才会移交。至于活跃项目，它用一句话划了界线。The maintainers of the Package Index are not arbiters in disputes around active projects.

判断路径也是分级的。一级是索引维护者，其次是打包工作组，而该工作组对这份文件所涵盖的争议拥有最终决定权。商标在这里再次出现：同一份文件在知识产权侵权一节处理了超出指名使用或合理使用范围地使用第三方商标的情形，并另设了举报渠道。

由此得出的结论很简单。注册表里的名字不靠技术解决，只靠程序解决。而那道程序的门槛通常很高。用新名字另建一个位置往往比走完程序更快，所以真实的分叉几乎总是换新名字。代价是，所有写着旧名字的配置文件都不知道新位置的存在。被删掉的名字与残留的引用如何错位，在被删除的包名为什么还在持续收到请求里按层次梳理过。

仓库管理权限与发布签名

仓库会被复制。但是围绕仓库的那些权限不会被复制。挂在这里的东西列出来是这样的。

  • 合并权限 — 决定哪些变更进入主干。分叉带得走历史，带不走未来的合并点。
  • 标签与发布 — 打版本号、上传分发物的地方。下游自动化正是来查这个地方。
  • 流水线密钥值 — 注册表发布令牌、签名密钥、分发目标凭据。它们在设置里，不在仓库内容里。
  • 安全举报渠道 — 接收非公开报告的通路，以及能读到它的人的名单。
  • 组织所有者账号 — 能把上面所有一切撤回去的上位座位，通常人数最少。

其中发布签名密钥性质稍有不同。别的座位换个地方就行，签名密钥则是验证方的信任绑在那把密钥上。发行版打包者、内部镜像、锁文件的验证设置都认识它。换新密钥签名，就得在所有这些地方重新种下起点，而那份工作跟复制一份仓库完全不在一个量级上。

托管本身迁移时什么跟得走、什么留下来，在让代码托管保持可迁移里逐项整理过。所有权结构分裂的情形，更接近那份清单以条件而非选择的方式压过来的情况。

基金会这个词指向的三种结构

有基金会这件事本身并不构成答案。把公开文件并排放好，立刻就能看到同一个词指向互不相同的安排。

  • 代表社区持有的形式 — 基金会持有全部商标，但把名义放在项目社区上。Apache 软件基金会的政策文件用的就是这句话。
  • 持有与商业开发分开的形式 — 基金会持有商标，商业使用则经由持有另一份独占许可的一方。部分活动商标还可能由子公司法人另行持有。
  • 为每个项目单设法人格的形式 — 在上层基金会之下，把各个项目作为 LLC 的系列来设置。作为 Terraform 分叉起步的 OpenTofu，按其自身文件所写正是以这种形式运作。

所以在有没有基金会之前该问的是三件事。哪些资产由该法人持有。董事会由谁决定。该法人与主要商业主体之间以什么合同相连。公开政策文件大体只回答第一件。第二和第三件在章程或另外的规程里，而且常常并未公开。

答案没有公开，这件事本身不是缺陷。但是没有判断依据这一事实会原样留下。在决定依赖的场合，这个区别会造成实质差异。

社区基础设施 - 论坛、问题与文档

最后一个格子最不起眼。论坛存档、问题跟踪器里的历史记录、文档站点、翻译平台、邮件列表、聊天空间。这些位置既不是商标也不是合同标的，却是项目的记忆存放之处。

把这些位置按住的，大体上是钱。付托管费用的一方、握有管理员账号的一方，决定记录能存多久、谁能访问。而一旦搬迁，多数链接就断了。断掉的链接会悄无声息地从搜索结果里消失，而解释某个决定为何作出的那段讨论，也随之一起消失。

对实务的影响比看上去大，因为旧的问题编号埋在提交信息和注释里。当编号指向的地方空了，代码里残留的那个引用就失去了意义。

分叉带得走什么，带不走什么

把前面的格子按分叉的视角重新排一遍，边界就清晰了。

分类条目依据
带得走源代码、提交历史、分支与标签的内容许可证允许复制、修改与分发
带得走文档正文、测试、构建配置、示例它们作为著作物就在同一个仓库里
带得走贡献者积累的上下文 — 但只有人跟着走时才成立人不是任何合同的标的
带不走项目名称与徽标商标是另一项权利，许可证并不授予
带不走官方域名，以及指向那个地址的既有安装绑定在注册人名义上
带不走包注册表里那个名字的位置由账号所有权与注册表的名称政策决定
带不走发布签名密钥，以及信任那把密钥的下游设置验证的起点绑在密钥上
带不走论坛、问题、文档的记录及其链接绑定在托管主体身上
带不走用户的习惯 — 安装命令、搜索词、书签哪里都没有记录，却是变得最慢的一项

这张表的下半部分才是分叉的真实成本。复制代码的成本基本上等于零，成本全都发生在下半部分。而且下半部分的条目不会被钱立刻解决，多数需要时间。

分叉要站稳，还得有什么跟上来

分叉在技术上成立，和它在生态里站稳，是两个问题。要站稳，除了代码之外还有几样东西必须跟上来。

  • 带着上下文的维护者 — 不是提交权限，而是知道那段代码为何长成这样的人。这项资产会迁移，但不会复制。
  • 分发路径 — 注册表里的新名字、容器镜像标签、下载地址。要做到用户不动手也能收到，才算数。
  • 下游打包者 — 发行版维护者与内部镜像运维者。只有他们采用新名字，才能自动抵达大多数用户。这是开源里最被低估的一个位置。
  • 兼容路径 — 既有配置文件能否照读、扩展接口是否维持、有没有迁移说明文档。这里摩擦一大，用户就不会动。
  • 承担费用的主体 — 基础设施账单、商标注册、最低限度的法务确认。第一年没有这个，下一个分岔口会重演同样的事。
  • 稳定性的证据 — 按既定周期出的版本与安全修复。建立信任的是记录，不是承诺。

这六项里跟代码有关的几乎一项都没有。分叉的难度不是代码的难度，而是生态的难度。谁来维持这个另外的轴，在谁在维持基础设施里单独处理过。所有与维持互相重叠，却不是同一个问题。

使用方在依赖之前该看的东西

如果说以上是结构，那么缩成实务可用的形式就是下面这张表。这些是看完许可证文件之后要看的东西。

要看什么在哪里能读出什么
商标政策文件项目站点或仓库根目录名称与徽标由谁持有、许可到什么程度。文件本身不存在，这也是一种信息
治理文件仓库根目录或社区文档决定如何作出，以及那套程序本身如何改变
有发布权限的人数维护者名单、注册表上的所有者显示如果只有一人，那一人既是单点故障也是单点决策
持有资产的法人站点页脚标注、商标政策、基金会页面资产在个人名下还是法人名下
贡献条件贡献指南文档贡献者许可协议还是原创声明签署。权利是聚拢还是分散
分发通道的数量安装说明路径只有一条时，那一条被堵住就没有替代
切断依赖时的替代方案哪里都没写，只能自己立有没有可替换的实现，数据能不能取出来

最后一行最常是空的。没有替代方案意味着，从这项依赖断掉的那天起才开始构建选项，而那个时点的工作远比平时昂贵。提前把替代方案写下来的成本，不过是几行字。

打开一个仓库时首先要找的文件名，大体是固定的。

LICENSE            使用条件 — 许可证的领地到此为止
TRADEMARK.md       名称与徽标由谁持有，允许到什么程度
GOVERNANCE.md      决定由谁作出，那套程序如何改变
MAINTAINERS  OWNERS  握有合并与发布权限的人的名单
CONTRIBUTING.md    贡献条件 — 协议签署还是原创声明
SECURITY.md        举报渠道与版本的校验方式

建设方要提前定下的东西

从另一边看，同一份清单就变成了设计项目。而且这些项目拖到后面再定就晚了。需要作出决定的时点通常已经是利益分化之后，那时面对同一句话也谈不成共识。

要定的事选项后面再定为何更难
名称与徽标的持有主体个人名义、公司名义、另设法人名字有了价值之后，转让本身就变成谈判对象
贡献者的约定方式贡献者许可协议、原创声明签署、两者都没有要追溯适用，就需要过往全部贡献者同意
发布权限的分散一个人、少数小组、签名密钥分离保管没有交接而那一个人消失，分发就停了
域名与注册表账号的名义个人账号、共用账号、法人账号个人账号会随着那个人一起失去访问手段
有没有治理文件没有、简单原则、把程序也写明争议发生之后才写的规则，会被读成针对当事人的规则
商业使用的允许范围全面允许、附条件、另设许可已经有人在用之后，再加条件就很难
对分叉的态度沉默、要求改名、允许友好标注不定下来，商标法的一般规则就会代为回答

这张表里最便宜的是第一行和第五行。在选定名字那天顺手定下持有主体，成本基本为零；治理文件在早期也只需一页。没有写下来的共识，人一换就不会留下。

改动许可证本身是另一条轴，而且因为与已经发出去的版本之间存在不对称，需要另作一套计算。那套计算在改许可证到底改变了什么里单独整理过。

另一面 - 集中并不总是坏的安排

资产集中在一处这件事本身，说不上是坏结构。由一个主体持有商标的安排，有公开文件写明的目的。WordPress 基金会的政策文件这样写下其宗旨：在代码与传统知识产权都开放的项目里，大家能够依赖的品质与信任标志，就是商标被允许使用的那个位置。

这个逻辑从用户一侧看是实用的。如果名字能随便往上贴，那个名字就什么都保证不了。有了商标政策，才能把官方分发物和非官方的区分开。

分散也有代价。把发布权限放宽，分发中断的风险会下降，但通往供应链的门会变多。把签名密钥放到多个地方，少一处也能撑住，但管理点会随之增加。把治理程序做细，任意决定会减少，决定的速度也会跟着下来。

所以该问的不是集中还是分散。而是有多少写进了文件，以及修改那份文件的程序是什么。这两样写着，任何安排都可以预测；没写，任何安排都无法预测。

小结 - 五句话

把以上缩成五句话，是这样的。

  • 许可证规定代码的使用，不规定项目的所有。多份许可证正文明确排除了商标，开源定义里也没有所有与治理的条款。
  • 剩下的格子有六个，各自绑在不同的依据上。商标靠商标法，域名靠注册合同，注册表的位置靠该注册表的政策，仓库权限靠账号设置，资产靠法人，社区基础设施靠付费的一方。
  • 分叉带走全部著作物，却一件也带不走绑在账号与注册上的东西。名字、域名、注册表位置、签名密钥、记录的链接、用户的习惯，都是留在原地的一侧。
  • 依赖之前要看的，是许可证之后的五份文件。商标政策、治理文件、有发布权限者的名单、持有资产的法人，以及不得不切断时的替代方案。
  • 对建设方来说最便宜的时刻是选定名字那天。那天没有定下的事，之后的任何一天都不会更便宜。

落到实务上只剩一句话。如果依赖清单里只有许可证这一列，那就少了一列。在它旁边再加一格，记下有没有商标政策与治理文件，是这里提到的所有措施中最便宜的一项。

未能确认的部分

以下条目在本次范围内没能从一手资料得出结论。在依据齐备之前不作断言。

  • 进行中事件的事实与判断 — 触发本文的那篇文章所涉事件，程序仍在进行。各项主张的真伪与责任归属，不是公开政策文件能够判定的种类，也不是这里的对象。正文只从那件事里取走了问题的形状。
  • Terraform 分叉的旧名称 — 有多处提到 OpenTofu 早期曾使用另一个名字后来改掉，但在项目自身的公开文件里没有找到写明这段经过的句子。因此正文只写了现在的名称与运作形式。
  • Linux Foundation 体系各项目的单独商标政策正文 — 项目文件指向一个政策合集的地址，但那份文件本次并未打开。正文里 Linux Foundation 的引用仅限于基金会的商标使用政策这一份。
  • 其他语言生态的名称争议处理程序 — JavaScript、Rust、Java 一侧的注册表如何处理活跃项目的名称争议，本次没有纳入范围。正文中的程序说明只是 Python 包索引一处的规定。
  • 贡献者约定方式与商标归属的关系 — 贡献者许可协议是否存在除著作权之外还处理商标的案例，没有从一手文件确认。正文只把两者当作彼此独立的条目来处理。
  • 在韩国法下的适用 — 开源项目名称在韩国的商标注册状况以及当地的纠纷处理程序，在本次调查范围之外。正文引用的政策文件是各基金会自行制定的使用条件，不是任何特定法域的法律解释。
