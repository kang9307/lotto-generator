This article is based on the sentences written in "Iroh global content discovery", published on the official iroh blog on September 30, 2026 under the byline of Rüdiger Klaehn, in the documentation of the iroh-content-discovery repository that the post points to, and in BitTorrent BEP 5. The repository README describes the status of this implementation as "experimental", and everything below should be read within that qualification.

The Problem the Post Starts From — Content the World Can Find Without Permission

The post opens with what attracted its author to IPFS shortly after it was announced: the ability to publish a personal website, a blog post or a political pamphlet and have it remain available globally for as long as enough people are interested in the content. The author writes that, as governments have become more sophisticated in their firewalling methods, this use case for circumvention tools and for "permissionless global content discovery" is still relevant. The post does not name any particular country or event.

What the author gives as the reason for urgency is a single sentence: "IPFS shipyard is shutting down." That passage carries its own qualification: this "does not mean that IPFS will stop working".

The approach is the same one iroh took when it had to solve hole punching. Back then the team looked at existing systems and chose the best open source system as the starting point for its own implementation, and the post says it does the same for global content discovery. The author notes that a number of projects are trying to solve this problem, and picks BitTorrent as the starting point on the grounds that it has actually worked for over two decades. In the words of the post, one project "stands above all others", and it "just works and has done so for over two decades". The mechanics of how two devices behind NAT reach each other are covered separately in how NAT traversal works.

Separating Finding from Fetching — The Structure Taken from BitTorrent

The first thing the post takes from BitTorrent is its structure. BitTorrent consists of a relatively simple protocol for blob transfer and a DHT called Mainline for global content discovery, and the two are separate systems. The DHT was developed later than the transfer protocol. According to the post, BitTorrent was released in 2001 using centralized trackers for content discovery, and the Mainline DHT was added in 2005.

BEP 5 (DHT Protocol) defines this DHT as a distributed hash table for storing peer contact information for "trackerless" torrents, and states that "in effect, each peer becomes a tracker". The protocol is based on Kademlia and is implemented over UDP. The same document also separates two terms. A "peer" is a client/server listening on a TCP port that implements the BitTorrent protocol, and a "node" is a client/server listening on a UDP port that implements the distributed hash table protocol. The DHT is composed of nodes and stores the location of peers.

The iroh implementation carries this separation between content discovery and data transfer over unchanged. Finding the providers of a piece of content is left to Mainline plus one small auxiliary service, and fetching the data from those providers is left to iroh-blobs. The repository README puts it this way: Mainline is the most successful permissionless content discovery system out there, "so we use it as is". The part that the iroh implementation changes is the transfer, which is the subject of the next section.

Comparing Transfer Protocols — SHA-1 Piece Hashes and BLAKE3 Verified Streaming

BitTorrent works by creating a .torrent file that contains information about the data to be downloaded. The file is encoded using bencode, which the post describes as "conceptually similar to JSON", and the post shows its contents in the following notation.

{
                      "announce": "http://tracker.example.com/announce",
                      "comment": "Ubuntu 24.04 desktop image",
                      "created by": "mktorrent 1.1",
                      "creation date": 1714521600,
                      "info": {
                        "name": "ubuntu-24.04-desktop-amd64.iso",
                        "piece length": 262144,
                        "length": 5820411904,
                        "pieces": 9358b5d71f8007ac926000961ad79d865d9652bc
                                  4cce840457bcfac1dd67d864e9386422eee70904
                                  … many more 20-byte hashes …
                      }
                    }

pieces contains the concatenated SHA-1 hashes of all pieces of size piece length. The transfer protocol downloads blocks of these pieces from different peers. The transfer protocol allows requests for ranges within a piece, but a piece can only be validated after it has been downloaded completely and its SHA-1 hash has been computed. A footnote in the post adds that in endgame mode a client may request the same remaining blocks from multiple peers and use whichever responses arrive first.

The author writes that he "thinks" BLAKE3 verified streaming is a superior replacement for this transfer protocol. iroh-blobs is a protocol that uses BLAKE3 verified streaming for sharing blobs of data over iroh connections. With BLAKE3 only a single root hash is needed, and neither a piece length parameter nor the hashes of the individual pieces. The post explains that this is what allows iroh-blobs to validate any piece of a large blob without needing intermediate hashes.

The official iroh documentation gives the basis for this as follows. BLAKE3 is a tree hashing algorithm that splits its input into uniform chunks and arranges them as the leaves of a binary tree, producing intermediate hashes that accumulate up to a root hash. Iroh uses the 32-byte root hash as an immutable blob identifier. Range requests are handled by streaming only the portions of the tree required to verify the designated subsequence. The chunk size is a tunable constant that defaults to 1KiB, which the documentation says results in a 6% overhead on the size of the input blob. Increasing the chunk size reduces the overhead, at the cost of requiring more data transfer before a verification checkpoint is reached.

The iroh-blobs README introduces the protocol as a simple request-response protocol based on BLAKE3 verified streaming. A request describes data in terms of BLAKE3 hashes and byte ranges. The requester opens a QUIC stream to the provider and sends the request, and the provider answers on the same stream with the requested data encoded as BLAKE3 verified streams. A note at the very top of that README says that this version of iroh-blobs is not yet considered production quality, and that anyone who needs production quality should use iroh-blobs 0.35 for now. The post likewise says there is still some work to do to make multiprovider downloads of single blobs efficient.

The Minimalism of the Mainline DHT — What BEP 5 Specifies

The post calls Mainline "an extremely large and stable public DHT deployment" and attributes how well it works to "extreme minimalism". The reasoning given is that the Mainline protocol takes into account that a DHT operates across an extremely large number of nodes and therefore cannot afford large per-node connection state, so both queries and responses are constrained to fit into single non-fragmented UDP packets. Putting the constraints the post lists next to the behaviour BEP 5 specifies gives the following picture.

  • One response per query. KRPC in BEP 5 is a simple RPC mechanism consisting of bencoded dictionaries sent over UDP. A single query packet is sent out and a single packet is sent in response, and there is no retry.
  • Four queries. They are ping, find_node, get_peers and announce_peer.
  • A 160-bit keyspace. Node IDs are chosen at random from the same 160-bit space as BitTorrent infohashes. The distance between two IDs is computed with XOR, and smaller values are closer.
  • get_peers. Its arguments are the id of the querying node and a 20-byte info_hash. If the queried node has peers for that infohash it returns them under values; if not, it returns under nodes the K nodes in its routing table closest to the infohash. In either case a token is included.
  • announce_peer. It has four arguments: id, info_hash, port and token. The queried node must verify that the token was previously sent to the same IP address, and then stores the IP address of the querying node and the supplied port number under that infohash.
  • Tokens. Data can only be stored after first querying the node and returning the short-lived token from its response. The post explains that this proves that, at publishing time, the publisher can receive packets at its claimed IP address, and that the mechanism is similar to the address validation token in QUIC. BEP 5 notes that the BitTorrent implementation uses the SHA1 hash of the IP address concatenated onto a secret that changes every five minutes, and that tokens up to ten minutes old are accepted.
  • A provider record is only a host:port. According to the post, the data stored for a provider is just the public host:port pair as seen from the DHT node, with no user-defined information. BEP 5 encodes peer contact information as a 6-byte string: a 4-byte IP address followed by a 2-byte port.
  • implied_port. This is an optional argument of announce_peer. If it is present and non-zero, the port argument is ignored and the source port of the UDP packet is used as the port of the peer. BEP 5 describes it as useful for peers behind a NAT that may not know their external port, and the document history records it as added on March 22, 2013.
  • Routing table. The number of nodes a bucket can hold, K, is currently eight. A node that has responded to a query within the last 15 minutes is "good", and after 15 minutes of inactivity a node becomes "questionable".
  • The BEP 44 extension. The post says that even for newer extensions like BEP 44 the data is fully self-contained and verifiable (either a tiny piece of data or a signed record) and is limited to fit into a typical MTU.

The post says the result of this minimalism is that Mainline lookups "typically" complete in less than a second. The evidence it presents is a single run log. It shows a BEP 44 lookup of a pkarr record using the get_mutable example from n0-mainline, in which the first result arrived in 37 milliseconds, and the timestamp printed in the log is September 24, 2026. On that basis the author writes that the Mainline DHT shows that millisecond lookups are possible at a global scale, addressing readers who have experienced DHT lookups "taking forever or timing out" with the remark that "it doesn't have to be this way". The post gives neither a number of repetitions nor a measurement location, so the figure is to be read as one example run and not as a statistic.

The Address Index That Links host:port to an EndpointId (udp-addr-index)

One thing does not line up when Mainline is used to find providers for iroh-blobs. A Mainline provider record is an IPv4 host:port pair, whereas iroh connections are dialed by cryptographic identity, currently the Ed25519 public key known as the EndpointId. So, to use Mainline provider records for endpoint discovery in iroh-blobs, there has to be a way to know which EndpointId is currently listening on that host:port. The post adds that in most cases this host:port will be behind a NAT and therefore not reachable from the outside in the first place. According to a footnote, the port in an announce_peer request can technically be chosen, but that gives only 16 bits, which is not enough to store something like a 32-byte EndpointId.

The author writes that he tried a number of ways to store this mapping with current Mainline mechanisms such as BEP 44, and that at present this is not possible. What was added instead is a tiny extra UDP address index service (udp-addr-index). Its properties, as stated in the post and in the README of that crate, are as follows.

  • What it stores. It stores some tiny arbitrary metadata for each verified UDP host:port pair. Per the post the limit is 1 KiB, and it is a "last writer wins" map from a live host:port pair to a tiny blob.
  • How it is reached. It is reachable exclusively through a simple single-packet UDP protocol. Since Mainline requires UDP and this service is an extension for Mainline, the case where sending UDP packets is not possible is not handled.
  • Verifying writes. According to the README, a publisher first asks for a short-lived token, and the server returns the observed public IPv4 socket of the packet together with a stateless MAC bound to that socket. A put carrying the token must arrive from the same socket; the server then derives the key from the packet source and stores the bytes under its own receipt time and TTL.
  • Reads. Reads are public and need no token. Instead, requests are padded to 1200 bytes and shorter ones are dropped. The README explains that a response can therefore never be larger than the request that caused it, and that every response fits one unfragmented datagram. The post gives the purpose of the padding as preventing amplification.
  • The value is not interpreted. The server neither parses nor validates the value it stores.
  • Expiry and in-memory storage. Mappings expire after some time, so a provider has to update its mapping at regular intervals and also when its public host:port changes. The current implementation keeps the map purely in memory. The author writes that not requiring persistence makes the service simpler and cheaper to operate, and that an address index for millions of iroh endpoints can be run on a single small box with a publicly reachable UDP socket.
  • Sharing a socket. Index traffic shares the UDP socket of a Mainline node. According to the README, index datagrams start with a zero byte, and since a zero byte cannot begin a bencoded KRPC message, both protocols can share one socket. Mainline announcements use implied_port, so the announced peer address and the index key describe the same UDP mapping.
  • Independence from iroh. The service does not depend on iroh in any way. The post describes it as infrastructure that could also be useful for applications other than iroh that use Mainline, and the author writes that in the long term he would love this function to be handled by a BitTorrent Mainline extension, since it is simple, generically useful and not specific to iroh.

What goes into the index is decided on the iroh side. For endpoint discovery, the stored record contains the endpoint ID, the current UDP socket address and a timestamp, and is signed with the private key of the endpoint. Only the owner of the endpoint key can write a valid signed record, so one endpoint cannot impersonate another endpoint by writing a record in its name. The README of iroh-mainline-endpoint-discovery adds one more point. Because reads are public, anyone can copy a record; therefore the record is also signed for the socket the server observed, and a reader discards a record it finds under any other socket. Without that binding, the README explains, someone could store a copied record in their own slot, and every resolver would then return that endpoint as a provider for content it does not serve.

The documentation also states who runs the index servers and how far they are trusted. The post names two mechanisms for finding servers: a rendezvous hash that allows address index services to announce themselves, and a BEP 44 record that is a curated list of good address index services. According to the README, the trusted Pkarr list is tried first, and the rendezvous hash is used only when the list yields nothing. The defaults (n0_defaults()) use the list maintained by n0. Candidates obtained through the rendezvous hash are untrusted and may be unreachable or dishonest, and the records a server returns are validated either way. The README also notes that even an address on the signed list only means that the owner of the list vouches for that server. And in every case the index service checks nothing about the endpoint. What get_peers together with this service yields is, in the words of the post, "just a list of candidate iroh endpoints which might serve the content", and the README repeats the point by telling users to check candidates before trusting them.

The Announce and Discovery Workflow — From the SHA-1 Mapping to a QUIC Connection

Both announce and discovery need a Mainline DHT node. The post says the n0_mainline crate is used for this, just as in the existing iroh-mainline-address-lookup crate.

Announce

  • Associating the socket with the EndpointId. To associate the UDP socket of n0_mainline with its own EndpointId, the provider publishes a signed record containing the EndpointId to the address index server through that same UDP socket. This has to happen at regular intervals, and immediately when the public host:port pair changes.
  • Mapping into the 20-byte keyspace. The Mainline keyspace is 20 bytes and is usually used to announce SHA-1 hashes of the info section of a .torrent file. Because the goal is to announce BLAKE3 hashes, the SHA-1 hash of the BLAKE3 hash is computed first.
  • announce_peer. The provider then calls announce_peer for that hash to announce that it is providing data for it. These announces also need to be repeated at regular intervals.
  • Intervals. Per the README, each infohash is announced every ten minutes, with jitter, and the index record is republished when it is older than thirty minutes. Servers keep a record for an hour. Many infohashes share one record, so announcing them costs a single index publication.

The post anticipates the question of whether SHA-1 is still safe for this purpose, and answers it as follows. The collision resistance of SHA-1 is broken, but there is no known practical preimage attack. More importantly, the DHT is just a best-effort mechanism for finding candidate providers. Downloaded data is verified against the original BLAKE3 hash, so a misleading DHT result can waste time, but it cannot make a client accept the wrong content.

Discovery

  • Obtaining an index server. The client first finds at least one working service that can translate host:port pairs into EndpointIds. The announcing side and the discovering side need to agree on the same rendezvous hash or BEP 44 record name.
  • get_peers. The client computes the SHA-1 hash of the BLAKE3 hash it is looking for and calls get_peers. The output is a list of host:port pairs, which are translated to EndpointIds using the address index.
  • Checking candidates. What exists at this point is a stream of unverified EndpointIds. The current implementation sends a quick BLAKE3 size query for the content being sought, to make sure the other side is live and serves the right content, and then hands the endpoints over to the iroh-blobs downloader.
  • The actual connection. The connection is established with the EndpointId and the built-in address lookup and hole punching of iroh. The QUIC connection does not go via the announced UDP host:port pair. That pair is only a key for the address index.
  • Stream handling. According to the README, the Resolver translates up to 16 peers at a time so that one slow lookup cannot hold up the rest, and a downloader can start on the first provider while discovery continues.

The whole flow can be seen in the blobs example of the repository. It runs both publish and resolve in one process, but discovery nevertheless goes via Mainline and the address index. The output printed in the post is the following.

In this log the blob hash, 64 hexadecimal digits long, and the Mainline infohash, 40 hexadecimal digits long, are different values, and that difference is the SHA-1 mapping described above. What Mainline returned is a single host:port; the address index translated that host:port into an EndpointId, which is the same value the log prints as the provider endpoint, and the iroh-blobs downloader then downloaded and verified 44 bytes from it. The post also prints the log of another example that includes a pkarr name (pkarr-publish-resolve), which reports that 35 bytes were downloaded and BLAKE3-verified in 8.24 seconds. Both logs are records of a single run.

Extending to Web Browsing — blake3.net Links and Pkarr Names

Up to this point the subject is content discovery for blobs. The post says this will be useful for tools like sendme and in general for sending around large amounts of data, and then explains that permissionless publishing of websites such as a blog needs some extra components.

  • Link syntax. Content-addressed links are always BLAKE3, and the domain blake3.net was reserved as a global namespace for them. A link has the form https://<hash>.blake3.net, with the hash encoded using zbase32.
  • Browser extension. The author writes that they do not want to run an actual gateway at blake3.net (the reasons are given only as "various"). Instead, the extension rewrites these links to http://<hash>.blake3.localhost:<port>. The post says that this is all the extension does.
  • Supported browsers. Per the post it currently works for Brave, Chrome and Firefox. For Chrome and Brave it is installed from the Chrome Web Store. The Firefox extension is awaiting review, so an unsigned XPI has to be loaded as a temporary add-on in Firefox 140 or later, and it must be loaded again after Firefox is restarted.
  • Local gateway. It serves content-addressed data on localhost. It interacts with Mainline to find content and orchestrates the blob downloads, supports iroh-blobs collections and shows a directory index for them, and also does file type detection. It is derived from the iroh blobs gateway in iroh-examples.
  • Where verification happens. A service worker could have been built to verify the data inside the browser process, but the data is verified inside the gateway instead. The reasoning the post gives is that either way it is software the user has to trust ("it is software that you have to trust"), and that whether it lives in the browser process or elsewhere does not matter much.
  • Port. The port configured on the gateway and on the extension must match. The default is 45475 (B1A3 in hexadecimal).
  • Names that point to changing content. One could use blake3.net links from an existing website, but that requires a registrar and a hoster, so it is not the permissionless publishing the post is after. This is where pkarr comes in. Pkarr is a standard for publishing a DNS record for a keypair, so that only the owner of the secret key can publish new versions, and the records are published on the Mainline DHT. The post says pkarr has been used for years for endpoint address lookup.
  • Pkarr links. The domain pkarr.net was reserved, and a link has the form <name>.pkarr.net, where name is the zbase32 encoding of an Ed25519 public key. The extension rewrites it to <name>.pkarr.localhost:<port>, and the gateway then resolves the pkarr record and either performs a redirect or, if the record links to hash.blake3.net, serves the content-addressed data directly.
  • Publishing tool. Both content-addressed data and pkarr records need continuous announcements. A tool called iroh-share exists for this, and the post suggests thinking of it as sendme running as a daemon with a separate user interface. As places to run it, the post mentions a small box that is on all the time or a VM in the cloud.

The author writes that this structure is very similar to IPNS in IPFS, and explains the nature of pkarr names through the triangle named after Zooko. Anyone can generate a keypair and publish under its public key without asking a naming authority, so pkarr names are decentralized and cryptographically verifiable, but a 52-character encoded public key is not a memorable name. Combining human-readable naming systems with pkarr is mentioned only at the level of "we have some ideas".

The Limits and Current Status Stated by the Authors

In the recap the author writes that the system still falls well short but is a start, and that while the user interface of sharing content-addressed data is extremely simple (the user states what content is wanted and the gateway gets it), the system behind it has a lot of room for improvement. He calls the present stage the "food and shelter phase" of global content discovery, and adds that the current system is nevertheless "certainly better than nothing". The Status section of the repository README likewise opens by saying that this is experimental and that it works but still has a long way to go. The limits named directly in the post and the README are the following.

Area What the post and the README say Note
Scale Mainline is quite scalable, but it "probably" will not scale for the vision of making all content on the internet content-addressable The qualifier in the post (probably) is kept
Blocking Mainline traffic is unencrypted and therefore easily blocked by middleboxes —
Post-quantum security The existing pkarr naming mechanism uses Ed25519 and is therefore not post-quantum secure —
Privacy Mainline does not provide any privacy. If you share content, anybody can look up your IP address Listed in the post as "perhaps most importantly"

Maturity of the transfer layer The current version of iroh-blobs is not yet considered production quality iroh-blobs README

The privacy item follows directly from the behaviour specified in BEP 5. A node that receives announce_peer stores the IP address and port of the querying node under the infohash, and get_peers returns the stored peer information to a query that asks for that infohash. In other words, anyone who knows the hash of a piece of content can learn the addresses that announced it.

The author does not commit to a single direction for improvement. He says the underlying content discovery system will continue to be improved, and that this may happen by extending Mainline or by writing a DHT of their own that uses iroh connections; the wording in the post is "possibly by extending mainline, possibly by writing our own DHT using iroh connections". The claim of the post is that all these improvements to the underlying system can be made while keeping the user interface stable; in its own words, "we can do all these improvements while keeping the user interface stable". As next steps it names getting the most frequently used iroh protocols, irpc, iroh-gossip and iroh-blobs, to 1.0. It states that the endpoint discovery mechanism is experimental, but that all relevant crates are published on crates.io for people to try. The post does not give version numbers for those crates.

What Could Not Be Verified

  • Measurement conditions for the 37 milliseconds and the 8.24 seconds. Both values are numbers from single run logs printed in the post. The number of repetitions, the measurement location and the network conditions are not given, so no basis was found for treating them as general performance figures.
  • Measurements behind "millions of endpoints on a single small box". This is a statement by the author, and neither the post nor the READMEs contain load measurements that support it.
  • The current size of Mainline. The post only links to an external statistics page and does not state a node count in its text.
  • How the address index servers are actually operated. The documents do not say how many servers are on the list maintained by n0 or where they are run. What the README does state is that a client keeps at most two servers.
  • Whether a Mainline extension has been proposed. The sentence about wanting a Mainline extension to take over the address index function is an expression of hope, and the post does not say whether an actual BEP proposal has been submitted.
  • Crate versions and the outcome of the Firefox review. Beyond what the post said at the time of publication, there is no material on the version numbers of the relevant crates or on whether the Firefox extension passed review.
  • The circumstances around IPFS Shipyard. The post mentions it in a single sentence, and its background and subsequent plans are outside the scope of the post.
