myDoo — Claude Codeをデフォルトとして据えたAIネイティブIDE

ターミナルエージェントとGUI IDEの融合が開発体験をどう変えるか — Cursor・Windsurf・Kiroとの差異とAIネイティブIDE潮流を分析する

2026-06-23 IT・技術

序論：エージェントをエディタの中に引き込む試み

2026年6月現在、AIコーディングツール市場は大きく二つの軸に分かれている。一方はAI補強エディタだ。CursorやWindsurfのようにVS Codeをフォークし、その上に独自AIレイヤーを積み上げる。もう一方はCLIエージェントだ。Claude CodeやOpenCodeのようにターミナルからコードベースを自律的に扱う。どちらも開発体験を変えてきたが、本質的に別々の世界だった。エージェントを使うにはターミナルを開く必要があり、エディタを使うにはエージェントのコンテキストの外に出なければならなかった。

開発者イ・グニョンがGeekNews（hada.io）に公開したmyDooは、この溝を埋めようとする試みだ。「Claude Codeの英知とIDEの使いやすさをVS Codeベースで新しい環境に実現した」という一文がその核心を要約している。Claude Codeを外部のターミナルツールではなく、エディタの一級市民として位置づけるという宣言だ。

本稿はmyDooの単純な紹介ではない。この統合がなぜ意義を持つのか、既存ツールと何が違うのか、そしてこの方向がAIネイティブIDEというより大きな潮流においてどんな位置にあるのかを独自の視点で分析する。公開情報が限られているため、確認された事実と推論は明確に区別する。

1. myDooとは何か — Claude CodeをIDEエンジンとして

myDooはClaude CodeをデフォルトLLMとして統合したVS CodeベースのAIネイティブIDEだ。個人開発者のイ・グニョンが制作し、GeekNewsのShow GNセクションに公開した。2026年6月現在、韓国の開発者コミュニティで注目を集めている。

1.1 核心コンセプト：エンジンとしてのエージェント

このツールの本質は「プラグイン」ではなく「エンジン」という概念にある。既存のClaude Code VS Code拡張はエディタの横にClaude Codeを付加する方式だ。エージェントはターミナルで独立して動作し、エディタはその結果を表示するビューアに近い。myDooが目指すのは、Claude Codeがエディタ自体の認知レイヤーになる構造だ。ファイルを開く、探索する、編集する、実行する、レビューするという操作がすべてエージェントと共有された単一コンテキスト上で行われる。

小さな違いに見えるが、開発のフローにおいては決定的だ。エージェントが「今エディタで開いているファイル」を自動的に知っているなら、開発者は毎回コンテキストをコピーして貼り付ける必要がなくなる。エージェントがdiffを生成したらエディタがそれをすぐインラインで表示し、開発者はコンテキスト切り替えなしにレビューして承認できる。

1.2 LLM選択の意味

myDooがClaude Codeをデフォルトに選んだのは戦略的判断だ。2026年6月現在、Claude Codeは専門開発者調査で主要ツール選択率28%と首位を占める（Cursor 24%）。Anthropicはエージェントループ、MCP（モデルコンテキストプロトコル）統合、ツール使用の信頼性を継続的に改善している。この成熟したエージェントを独自LLM開発なしに活用することは、個人プロジェクトとして合理的な選択だ。AnthropicがClaude Codeを改善するたびにmyDooもその恩恵を自動的に受け取る。

ただしこの選択には依存性がある。Claude APIのコスト構造、Anthropicの方針変更、そしてオフライン環境での制約がそれだ。LLMレイヤーを外部委託することで得る開発速度と、失う自律性のトレードオフを直視する必要がある。

2. ターミナルエージェントとGUI IDEの融合 — 何が変わるのか

この統合が開発体験において具体的に何を変えるのかを整理しよう。

2.1 コンテキスト切り替えコストの排除

現在Claude CodeをVS Codeと一緒に使う最も一般的な方法は分離した二つのウィンドウだ。片方にコード、もう片方にターミナルで動くエージェント。開発者はエージェントにファイルパスを伝えたり、エラーをコピーしたり、diffを確認するために絶えず二つの世界を行き来する。このコンテキスト切り替えコストは単なる不便以上のものだ。フロー状態を断ち切り、エージェントに渡すべきコンテキストを手動で組み立てる認知負荷を生み、エラーの余地を増やす。

エディタと統合されたエージェントは、エディタが見ているものをすでに知っている。開かれたファイル、カーソル位置、最近の変更履歴、診断エラーが自動的にエージェントのコンテキストに入る。開発者はその場で質問を入力すればよい。

2.2 インラインdiffレビューとコーディングフローの統合

エージェントがコードを修正するとき最も重要な瞬間は、開発者がその変更をレビューする瞬間だ。ターミナルベースのエージェントはdiffをテキストで出力するか別のツールに渡す。GUIエディタに統合されたエージェントはインラインdiffをエディタ内に直接表示し、ファイル単位・行単位で承認・拒否・修正するUIを提供できる。これが「エージェントをエディタに統合する」最も具体的な価値だ。コードの所有権がエージェントから開発者に移る瞬間を摩擦なく設計することが、エージェントベースのワークフローを実務に定着させる鍵になる。

2.3 即時フィードバックループ

エージェントは誤りを犯す。特にコンテキストが不十分だったり要求が曖昧だったりするとき。ターミナルベースのエージェントは誤りを犯しても、開発者がエディタに切り替えて確認するまでわからない。エディタ統合エージェントは誤りがエディタの診断レイヤーに即座に反映される。コンパイルエラー、型エラー、リント警告がエージェントの修正直後に表示され、エージェントはそれをコンテキストとして受け取り自己修正を試みることができる。このフィードバックループの短縮がエージェントコーディングの信頼性を高める核心だ。

3. Cursor・Windsurf・Kiroとの差異

myDooのポジショニングを理解するには、競合ツールと正直に比較する必要がある。

3.1 Cursor — VSCodeフォークの最高峰

2026年中盤現在、CursorはAI IDE市場で最も完成度の高い製品だ。タブ予測補完はコード行を超えて次のコードブロック全体を予測する。コンテキスト認識も深く、エディタ統合も洗練されている。Cursorは独自AIレイヤーを構築・保守する。Claudeを使えるがClaude Codeのエージェント構造をそのまま取り込むわけではない。myDooとの違いは「Claude Codeのエージェントループ自体をIDEに統合するかどうか」だ。

3.2 Windsurf — 自律性を強調するCascadeエージェント

WindsurfのCascadeエージェントはマルチファイル自律修正で強みを発揮し、「エージェントに丸ごと委任する」ワークフローを好む開発者に訴求する。2026年にCodiumがWindsurfをDevin Desktopに移行したことはこの自律性方向の延長だ。myDooとの違いはエンジンだ。WindsurfはCascadeを使い、myDooはClaude Codeを使う。どちらが優れているかはワークロードによって異なる。

3.3 Amazon Kiro — スペック駆動開発とクラウド統合

2026年に登場したKiroは最も独自のポジショニングを持つ。VS Codeベース（Code OSS）だがAWSサービスと深く統合し、「スペック駆動開発」を前面に出す。コードを書く前にエージェントが要件文書・アーキテクチャ計画・テストスペックを生成し、この構造化された計画の上で実装が行われる。Claude（Sonnet、Opus、Haiku）を含む複数LLMをサポートするが、AWSエコシステムへの依存が明確だ。myDooがクラウド中立でClaude Codeを使うこととは対照的だ。

3.4 myDooの差別点 — 軽量統合とClaude Codeエコシステムの活用

myDooがCursor・Windsurf・Kiroと異なる最大の点は独自AIレイヤーを開発しないことだ。これは弱点であり同時に強点でもある。弱点はClaude Codeの限界がそのままmyDooの限界になること。強点は逆に、AnthropicがClaude Codeを改善するたびにmyDooも一緒に改善されること。個人開発者がAI IDE競争で大きなチームと戦える方程式がまさにこれだ。Claude Codeエコシステムのすべての改善——新モデルアップグレード、MCP統合の拡張、エージェントループの改良——がmyDooに自動的に流れ込む。

4. AIネイティブIDE潮流 — 2026年の地形図

myDooは孤立したプロジェクトではない。2026年のAIネイティブIDE市場のより大きな流れの中で見るべきだ。

4.1 エージェントがエディタを吸収する方向

2025-2026年のAI開発ツール市場の核心的移動は、「AIをIDEに付加する」から「エージェントを中心に置きIDEがその周囲を構成する」方向への転換だ。Claude Code Desktopはエージェントをスタンドアロンアプリとして包み、Google Antigravityはエージェントオーケストレーターを中心に据え、Kiroはスペックをエージェントの出発点とする。myDooはこの流れで「エージェントをエディタ内に統合する」別の経路を取る。

4.2 ターミナルエージェントのGUI化がもたらすもの

ターミナルベースのエージェントは強力だが参入障壁がある。コマンドラインに不慣れな開発者、特にシニアよりジュニア開発者や非開発職種がAIコーディングエージェントを使いにくい理由の一つがターミナル環境だ。GUI IDEにエージェントを統合するとこの障壁が下がる。エージェントの動作が視覚化され、結果レビューがエディタ内で完結し、エラーメッセージをコピーする必要なくエディタの診断がエージェントに直接伝わる。これはエージェントコーディングの大衆化を意味する。

4.3 個人開発者の役割と市場の断片化

myDooが個人開発者のプロジェクトだという事実は、この市場のもう一つの特徴を示している。Cursorは数億ドルの投資を受けたスタートアップで、KiroはAWSのプロジェクトだ。しかしAIネイティブIDE空間では、個人開発者でも成熟した基盤モデル（Claude Code）とオープンソースエディタフレームワーク（VS Code）を組み合わせて競争力あるツールを素早く作れる。2026年のAI IDE市場は驚くほど断片化している。各ツールが「どの開発者に、どのワークフローで」最も合うかを探し続けている段階だ。

5. 開発体験変化の具体論

抽象的な分析を超えて、具体的に開発フローが何を変えるのかを私自身の視点から整理する。

5.1 質問のコンテキストが自動的に構成される

現在ターミナルClaude Codeで最も頻繁に行う作業の一つが「今見ているファイルのこのエラーを直してほしい」という要求だ。この一行をターミナルに伝えるためにファイルパスをコピーし、エラーメッセージをコピーし、必要な場合は関連ファイルも言及しなければならない。エージェントがエディタと統合されていれば、これらすべてのコンテキストが自動的に構成される。質問の質が高まり、回答の精度も共に上がる。

5.2 レビューフローがコーディングフローから切り離されない

エージェントコーディングで最も危険な瞬間は、開発者がエージェントの出力を十分レビューせずに承認する時だ。ターミナルでエージェントがファイルを修正したら、開発者はエディタに切り替えて変更を確認し、また戻らなければならない。この摩擦のせいで多くの開発者がレビューを手抜きにしたり省略したりする。エディタ内でエージェントのdiffがインラインで見えれば、レビューがコーディングフローの自然な一部になる。「エージェントに責任を委ねる」のではなく「エージェントとともに開発する」パラダイムが具体化される。

5.3 エージェントの誤りが即座に見える

コンテキストが不十分だったり要求が曖昧だったりするとエージェントは誤りを犯す。ターミナルベースエージェントの誤りは開発者がエディタに切り替えて確認するまでわからない。エディタ統合エージェントは誤りがエディタの診断レイヤーに即座に反映される。コンパイルエラー・型エラー・リント警告がエージェントの修正直後に表示され、エージェントはそれをコンテキストとして受け取り自己修正を試みることができる。このフィードバックループの短縮がエージェントコーディングの信頼性を高める核心だ。

6. 注意すべき点と限界

myDooをめぐる現実的な限界も直視しなければならない。

6.1 情報の制限

myDooはGeekNewsに公開された個人プロジェクトで、2026年6月現在、詳細な技術文書や機能一覧が十分に公開されていない。本稿で述べた「統合の方向」と「もたらされる体験変化」は公開されたコンセプトとAI IDE市場の一般的な流れを基にした分析であり、実際の実装詳細は異なる可能性がある。直接使っていないツールについての確定的な判断は慎む必要がある。

6.2 Claude API依存性

Claude Codeをデフォルトエンジンとして使うことはAnthropicのAPIコストと方針をそのまま受け入れるということだ。ローカルLLMを使いたい、またはオフライン環境を要求するチームには制約となる。2026年にClaude Codeをローカルプロキシで代替するソリューションが登場したが、公式サポートではない。

6.3 成熟度とエコシステム

Cursorは数百万ユーザーを持ち、高速リリースサイクルでバグを修正し、広いコミュニティと文書を持つ。myDooはその出発点にある。個人プロジェクトが成熟した製品になるまでの道のりには膨大な継続性が必要だ。現段階ではmyDooを主要開発ツールとして使うより、この方向の可能性を探る参照プロジェクトとして見るのが現実的だ。

7. 結論 — AIネイティブIDEの次の一手

myDooが示す方向は明確だ。ターミナルエージェントとGUI IDEの壁を取り払い、Claude Codeをエディタの一級構成要素として位置づける。これが成功すれば、開発者はコンテキスト切り替えなしにエージェントと協働し、エージェントの出力をエディタフロー内でレビューし、AIとともにコーディングする体験を完結したループとして作れる。

2026年6月現在、AIネイティブIDE市場の勝者はまだ決まっていない。Cursorが現在最も完成度が高いが、Kiro・Windsurf・OpenCode・myDooがそれぞれの角度から勢力図を揺るがしている。myDooは「Claude Codeエコシステムを最大限に活用した軽量統合」という答えを試みる。

ターミナルで生まれたエージェントがエディタの中に入ること。そしてエディタがエージェントを中心に再編されること。この二つの動きが交差する地点にmyDooがある。結果がどうであれ、この実験はAIネイティブIDEが何を意味すべきかをより鮮明にするのに貢献する。
