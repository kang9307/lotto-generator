Find Models That Actually Run on Your PC - From RAM/VRAM Matrix to Quantization

Why Local LLMs Are Back in 2026

As recently as 2024, the consensus was "AI lives in the cloud". ChatGPT, Claude and Gemini felt sufficient, and there seemed little reason to run a heavy model on your own machine. By 2025 the mood had clearly shifted. Anthropic and OpenAI raised API prices twice, while the security and legal cost of throwing personal code and internal documents into external APIs became impossible to ignore. At the same time, open-weight models such as Meta's Llama 3.x, Alibaba's Qwen 2.5 and Microsoft's Phi-3.5 in the 7B-70B parameter range evolved fast enough that decent hardware could finally produce GPT-4-class output at home.

A small CLI tool called whichllm recently lit up GeekNews. It does one simple thing: scan your PC and tell you which open models will run on it. The fact that a tiny utility like that attracts almost a hundred comments tells you everything: "will this model run on my machine?" is a universal question right now. This article is the answer. Rather than reviewing the tool, it lays out my own hardware-to-model matrix, quantization guide and runtime comparison as practical decision criteria for 2026.

1. Four Reasons Local LLMs Are Trending Again

1-1. Cloud LLM Price Hikes

Frontier models like Claude Opus and GPT-5 cost roughly 1.5-2x per input token compared to 2024. For workflows that chew through hundreds of thousands of tokens a day - code review, document generation, translation - monthly bills now hit triple digits in USD. Offloading even half of that to a local 7B-14B model meaningfully changes the cost curve.

1-2. Privacy and Data Leakage Concerns

"Are we allowed to send this code to an external API?" is now a routine question for corporate legal teams. Combined with the EU AI Act and tightening privacy laws across Asia, transmitting customer data or internal source code to an external LLM provider is itself a compliance risk. Local inference reduces that risk to zero.

1-3. Offline and Air-Gapped Environments

For banking, healthcare, defense and OT/factory networks where outbound Internet is blocked, cloud LLMs are simply not an option. Local models are the only choice. Through 2025, many large Korean conglomerates began self-hosting Llama or Qwen on internal GPU servers rather than depending on external APIs.

1-4. The Explosion of 7B-70B Open Models

In early 2024, calling a 7B model a "toy" was a common take. In 2026, Llama 3.2 3B is roughly comparable to GPT-3.5 of two years ago, and Qwen 2.5 14B challenges GPT-4 on several benchmarks. Once you reach the 32B-70B class, the practical gap with cloud frontier models for coding, translation and general chat is small. Hardware is the bottleneck, not the models.

2. Hardware-to-Model Matrix

This section is the heart of the article. It is a general guideline I have personally compiled, and memory figures assume GGUF quantization. If a model does not fit into VRAM, the runtime spills into system RAM and speed drops by roughly 5-10x. So "fits in VRAM" is the practical baseline.

RTX 3060 12GB + 32GB RAM. The used-market price is stable and 12GB VRAM cleanly hosts Qwen 2.5 14B Q4. The RTX 4060 (8GB) sits in the same price band but a smaller VRAM ceiling limits model choice, so for LLM purposes the 3060 12GB is the consensus pick.

3. Runtime Comparison: How to Actually Run It

The same model file behaves very differently depending on which runtime loads it. In 2026 the market is dominated by four real options.

Runtime UI Primary Format Strengths Best Audience
Ollama CLI + REST API GGUF One-line install, curated model registry, Docker-friendly Beginners and mid-level developers, RAG backends
LM Studio GUI GGUF GUI Huggingface search, built-in chat UI Non-developers, fast experimenters
llama.cpp CLI (raw) GGUF Lowest-level build, maximum tuning, Metal/CUDA/ROCm/Vulkan Power users, embedded use, performance enthusiasts
vLLM REST API HF Safetensors Multi-GPU, PagedAttention, high concurrency Production server operators

Practical Decision Criteria

  • Just starting on a personal PC: Ollama or LM Studio. Both deliver a first response within five minutes.
  • Integrating into RAG or an application: Ollama. Its REST API is OpenAI-compatible, so existing client code transfers almost unchanged.
  • Maximum performance on a Mac: llama.cpp (Metal build) or Ollama. Both leverage Metal acceleration.
  • Serving many users at once: vLLM. PagedAttention gives it the best concurrent throughput.

Ollama Five-Minute Start

# 1) Install (Linux/macOS)
curl -fsSL https://ollama.com/install.sh | sh

# 2) Pull and run a model
ollama run qwen2.5:7b

# 3) Call it through the OpenAI-compatible API
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen2.5:7b",
    "messages": [{"role":"user","content":"Hello"}]
  }'

4. Quantization Guide: When to Use Q4, Q5 or Q8

Quantization compresses model weights from 16-bit floats into 4-, 5- or 8-bit integers. You trade a little quality for substantial memory and speed gains. The 2026 standard is GGUF K-quants, and the variants you will see most often are these.

Quantization Memory Savings (vs FP16) Perceived Quality Loss Speed Best For
Q4_K_M ~75% 5-10% Fastest General chat, simple summaries, casual coding
Q5_K_M ~68% 2-5% Fast Translation, code completion, RAG
Q6_K ~62% 1-2% Moderate Long-form code generation, reasoning chains
Q8_0 ~50% Almost none Slower Quality-critical work, benchmarking

Matching Quantization to Task

  • Everyday chat and summarization: Q4_K_M is enough. In a fixed VRAM budget, a larger model at Q4 generally beats a smaller model at Q8.
  • Coding assistant: Q5_K_M or better. Code tokens are unforgiving - a single missing character breaks compilation.
  • Translation: Q5_K_M strikes a balance. Q4 accumulates subtle nuance loss, Q8 is needlessly slow.
  • Legal or medical text: Q6_K or better. Single-word semantics matter; choose quality over speed.
"In the same VRAM, a bigger model with stronger quantization usually wins"

For example, with 12GB of VRAM you could load a 7B Q8 (~7.5GB) or a 14B Q4 (~9GB). In most evaluations the latter wins, because parameter count contributes more to output quality than the quality loss from quantization. So the most rational default for general users is "the largest model that fits in my VRAM, quantized to Q4".

5. The Meaning and Limits of Auto-Recommender Tools

Tools like the recent whichllm have a simple premise: feed in your PC spec and get back a list of models you can run. Read it less as "a serious tool" and more as a signal that the open LLM ecosystem has become complex enough to create real friction. New models drop weekly, every model ships with 8-12 quantization variants, and the same model uses different memory amounts under different runtimes. Plenty of people get lost in that maze.

The limits are also clear. First, real inference speed is not determined by model size and quantization alone; tokenizer efficiency, KV cache size, context length, concurrency and memory bandwidth all matter. Second, quality satisfaction depends on the user's actual task and cannot be automated. Third, non-English performance is independent from English benchmark scores, but most auto-recommenders evaluate only in English. Use them as a first filter, then test two or three candidates yourself. This article's matrix is meant to serve as that first filter.

6. Korean-Specific Considerations (Useful Globally)

6-1. Models with Strong Korean Performance

Not every open LLM handles Korean equally well. Based on my own testing, the general ranking is:

  1. Qwen 2.5 (7B/14B/32B/72B): Among Alibaba's models, Korean corpus coverage is high and responses feel natural, particularly in Hanja-heavy domains like law and academia.
  2. Llama 3.1/3.3 Korean fine-tunes: A search for "Llama-3-Korean" on Huggingface returns many variants that outperform the base model in Korean.
  3. Phi-3.5 mini: Strong in English, acceptable for short Korean responses, shaky for long Korean reasoning.

6-2. Why Apple Silicon Matters for LLMs

M3 and M4 Pro/Max chips use unified memory, which means the entire system RAM functions as GPU memory. A 24GB MacBook can run a 70B Q3 model; a 64GB MacBook can run 70B Q8. A MacBook in the same price range as an RTX 4090 (24GB VRAM) desktop can host a larger model - a paradox that holds globally. The tradeoff is that token generation speed (tok/s) is typically 30-50% slower than an equivalent NVIDIA GPU.

6-3. Huggingface Download Throughput

Huggingface averages 30-80MB/s from Asia, but varies with the time of day and model size (a 70B Q8 weighs 40GB+). Enabling hf_transfer parallelizes downloads and roughly doubles speed. Ollama's own mirror tends to be more consistent.

# Accelerated Huggingface CLI download
pip install hf_transfer
export HF_HUB_ENABLE_HF_TRANSFER=1
huggingface-cli download Qwen/Qwen2.5-14B-Instruct-GGUF qwen2.5-14b-instruct-q4_k_m.gguf

6-4. Electricity Cost of a 24/7 Inference Server

An RTX 4090 averaging 50% load draws roughly 200W. At Korean residential progressive tier 3 (over 450kWh/month) the marginal rate is around KRW 285 per kWh, which works out to about KRW 30,000 (~USD 22) per month in additional electricity. Still cheaper than cloud APIs in almost every scenario, but worth budgeting for - it is not free.

7. Conclusion: Who Should Run What in 2026

User Profile Top Recommendation Why
General user (summarize, translate, chat) Llama 3.2 3B Q4_K_M / Qwen 2.5 7B Q4 Runs on RTX 3060 12GB or M2 8GB. Lowest entry cost.
Developer (coding assistant) Qwen 2.5-Coder 7B Q5 or 14B Q4 Code-specialized training, easy to plug into Continue/Cursor locally.
RAG / internal chatbot operator Llama 3.1 8B Q5_K_M + Ollama OpenAI-compatible API; works out of the box with LangChain and LlamaIndex.
Researcher / experimenter Qwen 2.5 32B Q5 or Llama 3.3 70B Q4 Near-frontier quality on RTX 4090, M4 Max and other 24GB+ setups.
Enterprise service operator vLLM + Llama 3.3 70B FP16 (multi-GPU) Good fit for concurrent requests, logging, auth and quotas.

Local LLMs are no longer just a hobby. As of 2026, the 7B class substitutes for GPT-3.5, the 14B-32B class covers about 80% of GPT-4 use cases, and 70B-plus models meet frontier models on a real subset of work. Hold on to a single rule - "run the largest model that fits in my VRAM at Q4_K_M" - and you skip 90% of the typical trial-and-error.
