서론: 번역은 끝났다는데 어딘가 남아 있다

제품 문서를 다섯 언어로 내보낸다고 하자. 파일은 사천 개이고, 절반은 사람이, 절반은 기계가 번역했다. 검수자는 스무 개쯤 열어 보고 괜찮다고 판단한다. 그리고 두 달 뒤에 영어 페이지 한복판에서 한국어 한 문장이 발견된다. 그때쯤이면 그게 어느 배치에서 들어온 것인지 아무도 모른다.

이 결함이 성가신 이유는 어렵기 때문이 아니다. 기계는 몇 초 만에 잡아내는데, 사람은 절대 못 잡는다는 비대칭 때문이다. 사람은 문서 사천 개를 읽지 않는다. 스무 개를 읽고, 그중 눈에 띈 하나를 고치고, 나머지 삼천구백팔십 개는 그대로 나간다.

그래서 이 일은 검수의 문제가 아니라 검사기의 문제다. 그리고 검사기를 만들 때 진짜 어려운 부분은 혼입을 찾아내는 쪽이 아니다. 찾아낸 것 중에서 남아 있는 게 맞는 것을 골라내는 쪽이다. 제품명은 원어로 두는 게 맞고, 코드 예제 안의 문자열은 번역하면 안 되고, 용어 병기는 일부러 두 언어를 나란히 쓴다. 이걸 못 가리는 검사기는 경고를 수백 개 뱉고, 사람은 사흘 만에 그 경고를 무시하기 시작한다.

결론부터 적는다. 문자 코드로 잡을 수 있는 것은 생각보다 많고, 유니코드 블록 범위를 손으로 적는 흔한 방식은 그중 절반을 놓치면서 동시에 멀쩡한 문장을 잘못 잡는다. 스크립트 속성으로 바꾸면 두 문제가 같이 사라진다. 그다음에 남는 것이 예외 설계이고, 여기서부터는 정답이 아니라 대가를 고르는 문제가 된다.

1. 사람 눈으로는 못 잡는 이유

언어 혼입은 눈에 잘 띄는 자리에 생기지 않는다. 제목이나 첫 문단에 통째로 다른 언어가 있으면 누구든 본다. 문제는 그런 게 아니다.

  • 문단 중간에 한 문장. 앞뒤가 자연스럽게 이어져 있어서 스크롤하면서 읽으면 그냥 넘어간다
  • 표의 세 번째 행. 열 개 행 중 하나만 원문이 남아 있으면 표 전체를 훑는 시선에 걸리지 않는다
  • 화면에 안 보이는 자리. 이미지 대체 텍스트, 폼 입력 안내 문구, 오류 메시지, 접근성 라벨은 정상 흐름에서 아예 렌더링되지 않는다
  • 단어 일부만 바뀐 자리. 용어 사전으로 치환하는 방식의 번역은 단어 안쪽 일부만 바꿔 놓기도 한다. 한 낱말 안에서 문자 체계가 바뀌는 형태라 흘려 읽으면 넘어간다
  • 기호처럼 보이는 문자. 장음 부호나 가운뎃점처럼 다른 언어에서 잘 안 쓰는 문장부호가 남는 경우, 글자가 아니라 서식으로 읽혀서 아무도 의심하지 않는다

여기에 하나 더 있다. 검수자는 자기가 아는 언어만 검수한다. 태국어 페이지에 러시아어가 섞여 들어가면 한국어 검수자도 영어 검수자도 잡지 못한다. 실제로 기계 번역 파이프라인에서 엉뚱한 언어가 튀어나오는 일은 드물지 않고, 그 언어를 읽는 사람이 조직에 없으면 그대로 배포된다. 문자 체계 검사는 이 구간에서 사람보다 압도적으로 낫다. 읽을 줄 몰라도 잡을 수 있기 때문이다.

2. 문자에는 언어가 적혀 있지 않다

먼저 용어를 정리해야 한다. 이 검사에서 다루는 것은 언어가 아니라 문자 체계다. 둘은 다르다. 영어와 프랑스어는 언어가 다르지만 문자 체계는 똑같이 라틴이다. 문자 코드만 봐서는 이 둘을 가를 수 없다.

반대로 한국어·일본어·러시아어처럼 문자 체계가 다른 조합은 코드만 봐도 갈린다. 그래서 이 검사가 실제로 하는 일은 이렇게 좁혀진다. 대상 언어에서 나올 수 없는 문자 체계가 문서에 있는가. 이 좁은 질문에는 기계가 완벽에 가깝게 답한다.

2.1 유니코드가 이미 답을 갖고 있다

모든 코드포인트에는 Script 속성이 붙어 있다. UAX #24가 정의하는 값이고, Hangul·Hiragana·Katakana·Han·Cyrillic·Latin 같은 이름을 갖는다. 자바스크립트 정규식은 이 값을 \p{Script=Hangul} 형태로 직접 쓸 수 있다. MDN 문서가 밝히듯 u 또는 v 플래그가 반드시 필요하고, 플래그가 없으면 \p는 그냥 문자 p로 해석된다. 조용히 실패하므로 주의할 값어치가 있다.

두 개의 특수 값을 알아 둬야 한다. Common은 여러 문자 체계가 공유하는 문자(숫자·문장부호 등)에, Inherited는 앞 문자에서 성질을 물려받는 결합 기호에 붙는다. UAX #24는 Common이나 Inherited가 붙은 문자 다수가 실제로는 모든 문자 체계와 쓰이는 게 아니라 제한된 일부와만 쓰인다고 지적하면서, 그 관계를 따로 적어 둔 Script_Extensions 속성을 정의한다.

여기서 실무적인 판단이 하나 나온다. 혼입 검사에는 Script를 쓰고 Script_Extensions는 쓰지 마라. Script_Extensions는 「이 문자를 이 문자 체계에서 쓸 수도 있다」는 넓은 관계라서, 오염 검사에 쓰면 여러 언어가 공유하는 문장부호까지 전부 걸린다. 아래 3절의 실제 판정표가 이 차이를 그대로 보여 준다.

2.2 한자는 언어를 말해 주지 않는다

이 절이 이 글에서 가장 중요하다. 한자가 있다는 사실은 그 문서가 중국어라는 근거가 되지 못한다.

유니코드는 중국어·일본어·한국어에서 쓰이는 한자를 하나의 통합 집합으로 인코딩했다. 유니코드 표준 18장은 이 통합 집합의 존재를 명시하면서, 표준이 한자의 언어를 인코딩하려 시도하지 않으며 언어 태깅과 단어 인식은 상위 계층 소프트웨어의 몫으로 남긴다고 적고 있다. 즉 코드포인트에는 이 글자가 중국어인지 일본어인지가 들어 있지 않다. 애초에 넣지 않기로 한 것이다.

구체적으로 확인해 보면 이렇다. 일본에서 쓰는 신자체 国과 중국 간체자 国은 같은 코드포인트 U+56FD다. 会 역시 U+4F1A로 양쪽이 같다. 두 언어 문서를 나란히 놓고 한자만 뽑아 코드포인트를 비교하면 구분되는 지점이 없다.

// 신자체와 간체가 같은 코드포인트인지 확인
for (const ch of ['国', '会', '發', '发']) {
  console.log(ch, 'U+' + ch.codePointAt(0).toString(16).toUpperCase(),
              /\p{Script=Han}/u.test(ch));
}
// 国 U+56FD true   ← 일본 신자체 = 중국 간체
// 会 U+4F1A true   ← 양쪽 동일
// 發 U+767C true   ← 번체에만
// 发 U+53D1 true   ← 간체에만

그래서 규칙을 이렇게 나눈다.

  • 영어 문서에 한자 — 혼입으로 봐도 된다. 라틴 문자권 문서에 한자가 나올 이유가 거의 없다
  • 일본어 문서에 한자 — 당연히 정상이다. 규칙 자체를 만들면 안 된다
  • 중국어 문서에 한자 — 정상. 대신 어느 계열의 한자인가를 따로 봐야 한다(6절)
  • 한국어 문서에 한자 — 정상이다. 한국어는 한자를 병기 용도로 쓴다. 여기에 한자 금지 규칙을 걸면 법률·학술 문서에서 오탐이 쏟아진다

같은 이유로 일본어 문서에서 한자만으로 이루어진 구간은 판별 불가 구간이다. 회사 이름이나 제목처럼 가나가 하나도 없는 짧은 문자열은 중국어와 구분할 수단이 없다. 이건 검사기의 결함이 아니라 인코딩 설계의 성질이므로, 규칙으로 해결하려 들지 말고 「이 구간은 검사 대상이 아니다」로 처리하는 편이 맞다.

3. 블록 범위 대 스크립트 속성 - 실제 판정 차이

현장에서 가장 흔히 보이는 코드는 유니코드 블록 범위를 손으로 적는 형태다. 한글은 AC00–D7A3과 1100–11FF, 가나는 3040–30FF, 키릴은 0400–04FF, 한자는 4E00–9FFF. 이 범위들 자체는 맞다. 문제는 이 범위만으로는 부족하고, 동시에 지나치다는 데 있다.

아래는 Node 22에서 두 방식을 같은 문자에 적용한 결과다. 직접 확인하려면 이 코드를 파일로 저장해 실행하면 된다.

const BLOCK  = { hangul: /[가-힣ᄀ-ᇿ]/u, kana: /[぀-ヿ]/u };
const SCRIPT = { hangul: /\p{Script=Hangul}/u,
                 kana:   /[\p{Script=Hiragana}\p{Script=Katakana}]/u };

for (const ch of ['한', 'ㄱ', '㉮', 'ｻ', '・', 'ー', 'の']) {
  console.log(ch,
    'U+' + ch.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'),
    'block:',  BLOCK.hangul.test(ch)  || BLOCK.kana.test(ch),
    'script:', SCRIPT.hangul.test(ch) || SCRIPT.kana.test(ch));
}
문자코드포인트블록 범위 방식스크립트 속성 방식무슨 일이 일어나나
한U+D55C적중적중둘 다 정상
ㄱ (호환 자모)U+3131불발적중호환 자모는 3130–318F에 있어 두 범위 어디에도 없다
㉮ (원 문자)U+326E불발적중괄호·원 문자 형태도 Hangul 스크립트다
한글 NFD 분해형U+1112 U+1161 …조건부적중[가-힣]만 쓰면 불발, 자모 범위를 더해야 잡힌다
ｻ (반각 가나)U+FF7B불발적중반각 가나는 FF65–FF9F에 따로 있다
・ (가운뎃점)U+30FB적중 = 오탐불발가나 블록에 있지만 Script는 Common이다
ー (장음 부호)U+30FC적중 = 오탐 소지불발위와 같다. 여러 문자 체계가 공유한다
〜 (물결표)U+301C불발불발둘 다 통과. 정상 동작
のU+306E적중적중둘 다 정상

표에서 읽어야 할 것은 두 가지다. 블록 범위는 흩어진 문자를 놓친다. 반각 가나가 대표적이다. 자동 변환기를 거친 문서에는 반각 가나가 심심찮게 남는데, 3040–30FF만 보는 검사기는 이걸 통과시킨다. 그리고 블록 범위는 공유 문자를 잘못 잡는다. 가운뎃점 U+30FB는 가나 블록 안에 있지만 한국어·중국어 문서에서도 나열 기호로 쓰인다. 이 한 글자 때문에 한국어 문서 수백 개가 「일본어 혼입」으로 보고되는 상황이 생긴다.

3.1 같은 표본에 두 방식을 돌린 결과

오염 여섯 건과 정상 다섯 건, 도합 열네 개 표본에 두 방식을 적용하면 이렇게 갈린다. 오염 표본에는 정상 문서 뒤에 한글·가나·키릴 잔재를 심었고, 정상 표본에는 가운뎃점·물결표처럼 오탐을 부르는 문자를 넣었다.

방식적중(TP)미탐(FN)오탐(FP)정상 통과(TN)
블록 범위6314
스크립트 속성9005

블록 범위가 놓친 셋은 호환 자모·원 문자·반각 가나였고, 잘못 잡은 하나는 가운뎃점을 쓴 한국어 문장이었다. 열네 개짜리 작은 표본이라 비율 자체에 의미를 두면 안 되지만, 실패 유형은 그대로 읽어도 된다. 블록 범위 방식은 「경계 밖에 흩어진 문자」와 「블록 안의 공유 문자」 양쪽에서 무너진다. 그리고 이건 표본을 늘려도 같은 자리에서 계속 무너진다.

UTS #18도 같은 방향을 가리킨다. 이 문서는 문자 식별에 유니코드 블록을 쓰는 데 매우 중대한 단서가 붙는다고 명시하면서, 블록을 문자 체계 식별의 대체물로 다루지 말 것을 권고한다. 손으로 적은 범위가 굴러가는 코드라 해도, 표준이 별도로 Script 속성을 만들어 둔 데는 이유가 있다.

다만 블록 범위가 필요한 자리도 있다. 정규식 엔진이 스크립트 속성을 지원하지 않는 환경(구형 런타임, 일부 데이터베이스의 정규식, 셸 도구)에서는 선택지가 없다. 그럴 때는 최소한 반각 가나 FF65–FF9F와 한글 호환 자모 3130–318F를 범위에 추가하고, U+30FB와 U+30FC는 명시적으로 제외하라. 이 세 가지만 손봐도 위 표에서 블록 방식이 어긋난 다섯 자리 중 넷이 사라진다. 남는 하나는 원 문자 형태인데, 이건 본문에 나올 일이 드물어 감수할 만하다.

4. 검사기를 죽이는 것은 미탐이 아니라 오탐이다

여기서부터가 진짜 어려운 부분이다. 지금까지의 이야기는 문자 코드만 알면 되는 기계적인 작업이다. 이제부터는 남아 있는 게 맞는 원어를 가려내야 하고, 이건 판단이 들어간다.

원어가 남는 게 정당한 자리는 생각보다 많다.

  • 고유명사와 브랜드. 회사명·제품명·인명·지명은 번역하지 않는 편이 원칙에 맞는 경우가 많다
  • 인용. 원문 문장을 그대로 인용할 때 번역하면 인용이 아니게 된다
  • 코드 예제. 변수명·문자열 리터럴·명령어는 번역 대상이 아니다. 번역하면 코드가 동작하지 않는다
  • 용어 병기. 「가나(かな)」처럼 원어를 괄호로 병기하는 것은 번역 품질이 좋다는 신호이지 결함이 아니다
  • 이 글처럼 문자 자체를 다루는 문서. 예제에 여러 문자 체계가 들어가는 것이 본문의 내용이다
  • UI 문자열의 의도적 원어 유지. 법적 고지나 상표 표기는 원어 유지가 요구되기도 한다

이걸 못 가리면 어떻게 되는지가 핵심이다. 검사기는 경고를 300건 뱉고, 사람이 열어 보면 280건이 브랜드명과 코드 예제다. 사흘째에는 아무도 열어 보지 않는다. 일주일째에는 CI에서 이 검사를 뺀다. 그리고 진짜 오염 20건은 그대로 배포된다.

그래서 이 두 실패의 무게가 같지 않다. 미탐 하나는 문서 한 곳을 망치지만, 오탐 누적은 검사기를 통째로 무력화한다. 검사기를 새로 만들 때는 이 비대칭을 기본값으로 깔고 시작해야 한다. 잡히는 범위를 넓히는 쪽이 아니라, 보고되는 것 하나하나가 진짜이도록 조이는 쪽이다. 놓친 유형은 나중에 규칙을 하나 더 추가하면 되지만, 한번 꺼진 검사기는 다시 켜지지 않는다.

5. 예외를 다루는 네 가지 수단과 각각의 대가

수단은 넷이다. 공짜인 것은 없고, 어느 것을 얼마나 쓸지가 설계다.

수단하는 일대가언제 쓰나
검사 범위 축소 코드 블록·URL·속성값·메타데이터를 검사 전에 제거 제거한 구간이 영구 사각지대가 된다 가장 먼저. 값이 싸고 효과가 크다
허용 목록 특정 문자열을 검사 대상에서 뺀다 사람이 계속 채워야 하고, 길어지면 진짜 오염을 가린다 고유명사·브랜드처럼 목록이 유한할 때
비율 임계값 전체 글자 대비 일정 비율 넘을 때만 보고 긴 문서의 한 문장 누락을 놓친다 기계 번역 배치의 대량 미번역 탐지
문서 단위 예외 파일 하나를 통째로 제외 가장 위험하다. 그 파일은 영영 안 본다 최후 수단. 반드시 만료일과 함께

5.1 검사 범위 축소 - 가장 먼저 할 일

코드 블록과 URL을 제거하는 것만으로 오탐의 상당 부분이 사라진다. 순서가 중요하다. 제거를 먼저 하고 검사를 나중에 해야 한다.

function stripUncheckable(text) {
  return text
    .replace(/```[\s\S]*?```/g, ' ')            // 펜스 코드 블록
    .replace(/`[^`\n]*`/g, ' ')                 // 인라인 코드
    .replace(/<code[\s\S]*?<\/code>/gi, ' ')   // HTML 코드
    .replace(/<pre[\s\S]*?<\/pre>/gi, ' ')
    .replace(/https?:\/\/\S+/g, ' ');           // URL
}

주의할 것이 하나 있다. 제거한 구간은 영원히 안 보게 된다. 코드 블록 안의 주석에 미번역 설명이 남아 있어도 잡히지 않는다. 그래서 제거 대상은 최소로 잡고, 「코드 블록 안 주석은 검사하지 않는다」는 결정을 문서로 남겨 두는 편이 낫다. 나중에 그 구간에서 결함이 나왔을 때 검사기의 버그가 아니라 합의된 범위였음이 확인돼야 한다.

5.2 허용 목록 - 유한할 때만

허용 목록은 정확하지만 사람 손을 계속 먹는다. 두 가지 원칙으로 관리 비용을 줄일 수 있다.

  1. 목록은 전역이 아니라 규칙별로. 「en 문서에서 허용되는 한자」와 「ko 문서에서 허용되는 가나」는 다른 목록이다. 하나로 합치면 en에서 허용한 항목이 zh에서도 통과해 버린다
  2. 항목마다 이유를 적는다. 이유 없는 항목은 6개월 뒤에 지울 수도 남길 수도 없게 되고, 그렇게 목록이 영구히 커진다
const ALLOW = {
  en: [
    { term: '任天堂',  why: 'brand name, kept in original' },
    { term: '한글',    why: 'subject of the article itself' },
  ],
  ko: [
    { term: 'かな',    why: 'term gloss in parentheses' },
  ],
};

실제 판정은 이렇게 갈린다. 브랜드명이 들어간 영어 문장은 허용 목록 없이는 Han 3자로 보고되고, 목록에 넣으면 사라진다. 용어 병기가 들어간 한국어 문장도 마찬가지로 Hiragana 2자에서 0으로 떨어진다. 코드 예제 안의 정규식은 범위 축소만으로 이미 0이 된다.

5.3 비율 임계값 - 절대 개수보다 안정적이다

같은 두 글자가 문서 길이에 따라 전혀 다른 의미를 갖는다. 영어 문서에 한글 두 글자가 남아 있다고 하자.

  • 전체 815자 문서에서 → 0.25퍼센트. 브랜드나 인용일 가능성이 높다
  • 전체 6자 문서에서 → 33.33퍼센트. 번역 자체가 안 된 것이다

그래서 임계값은 개수가 아니라 비율로 잡는다. 다만 비율 하나만으로는 부족하다. 긴 문서에 한 문장만 안 번역된 경우가 비율에 묻힌다. 두 규칙을 함께 걸어 두는 구성이 실무에서 맞다. 비율이 일정 수준을 넘으면 대량 미번역으로 보고 차단하고, 비율이 낮더라도 연속된 오염 구간의 길이가 일정 길이를 넘으면 별도로 보고한다. 문장 하나가 통째로 남으면 연속 길이가 길어지므로 두 번째 규칙에 걸린다.

// 연속 구간으로 보고하면 위치까지 같이 나온다
const doc = 'The runner reads the tree. 접근성 트리를 읽고 반환한다. Then it exits.';
const re = /\p{Script=Hangul}+/gu;
let m;
while ((m = re.exec(doc)) !== null) {
  console.log(`offset ${m.index}: ${JSON.stringify(m[0])}`);
}
// offset 27: "접근성"
// offset 31: "트리를"
// offset 35: "읽고"
// offset 38: "반환한다"

보고 형식에서 한 가지를 덧붙인다. 글자 개수로 보고하지 말고 위치와 원문 조각으로 보고하라. 위 예에서 「한글 12자 발견」은 고칠 수 없는 정보이고, 「offset 27에 접근성」은 바로 고칠 수 있는 정보다. 사람이 열어 보는 비용이 낮을수록 검사기가 오래 산다.

5.4 문서 단위 예외 - 만료일 없이는 쓰지 마라

파일 전체를 검사에서 빼는 것은 마지막 수단이다. 한 번 넣으면 그 파일은 다시 검사되지 않고, 목록에 들어간 이유는 반년이면 잊힌다. 굳이 쓴다면 만료일을 필수 필드로 두고, 만료된 항목이 있으면 검사기가 그 사실 자체를 보고하게 만들어야 한다. 예외 목록을 관리 대상으로 만들어 두지 않으면 예외 목록이 곧 사각지대 목록이 된다.

5.5 낱말 안에서 문자 체계가 바뀌는 경우

따로 다뤄야 하는 유형이 하나 있다. 용어 사전으로 치환하는 번역이 낱말 안쪽 일부만 바꿔 놓는 형태다. 이건 문서 전체를 훑는 규칙으로는 잡히지 않는다. 정상 한국어 문서에도 한자는 나오고, 정상 문서에도 한글은 당연히 나오기 때문이다. 걸리는 지점은 둘이 붙어 있다는 사실이다.

여기서 한 가지 함정이 있다. 낱말 단위로 잘라서 한 낱말 안에 두 문자 체계가 있는지 보는 접근이 자연스러워 보이는데, 실제로는 안 된다. 단어 분리기는 문자 체계가 바뀌는 자리를 단어 경계로 취급하기 때문이다.

const seg = new Intl.Segmenter('ko', { granularity: 'word' });
console.log([...seg.segment('会원 가입')].map(p => p.segment));
// [ '会', '원', ' ', '가입' ]   ← 会 와 원 이 서로 다른 토큰으로 갈린다

그래서 낱말이 아니라 인접을 본다. 한자 바로 뒤에 한글이 오거나 그 반대인 자리를 직접 찾는다.

const adj = /(\p{Script=Han}\p{Script=Hangul}|\p{Script=Hangul}\p{Script=Han})/gu;

[...'会원 가입 절차'.matchAll(adj)];   // [ '会원' ]      ← 잡힌다
[...'新규 등록'.matchAll(adj)];        // [ '新규' ]      ← 잡힌다
[...'민법(民法) 제839조'.matchAll(adj)]; // []            ← 병기는 안 잡힌다
[...'한자 漢字 병기'.matchAll(adj)];    // []            ← 띄어쓰기가 있으면 안 잡힌다

이 규칙이 좋은 이유는 정당한 병기를 자동으로 비켜 간다는 데 있다. 괄호 병기와 띄어쓰기 병기는 둘 다 사이에 다른 문자가 끼므로 인접 조건이 성립하지 않는다. 허용 목록을 하나도 쓰지 않고 오탐이 0이 되는 드문 규칙이라, 만들 값어치가 있다.

5.6 눈으로 구별되지 않는 문자

키릴 문자와 라틴 문자에는 모양이 같은 글자가 여럿 있다. 대문자 А(U+0410, 키릴)와 A(U+0041, 라틴)는 화면에서 구별되지 않는다. 기계 번역 파이프라인이나 복사·붙여넣기 과정에서 이런 문자가 섞여 들어가면 검수자가 아무리 봐도 못 잡는다.

이건 오히려 기계가 쉽게 잡는다. 한국어 문서에 키릴 문자를 금지하는 규칙 하나면 걸린다. 여기에 한 낱말 안에 라틴과 키릴이 함께 있는 경우를 추가하면 정확도가 더 올라간다. 정상적인 문서에서 한 단어가 두 알파벳 체계로 이루어질 이유가 없기 때문이다.

function scriptsOf(token) {
  const s = new Set();
  for (const ch of token) {
    if (/\p{Script=Latin}/u.test(ch))    s.add('Latin');
    if (/\p{Script=Cyrillic}/u.test(ch)) s.add('Cyrillic');
  }
  return [...s];
}
scriptsOf('Аpple');  // [ 'Cyrillic', 'Latin' ]  ← 첫 글자가 U+0410
scriptsOf('Apple');  // [ 'Latin' ]

6. 같은 문자권 안의 오염 - 간체·번체·신자체

지금까지의 규칙은 문자 체계가 다를 때만 작동한다. 그런데 실제 로컬라이제이션에서 자주 나오는 결함은 같은 문자 체계 안에서 생긴다. 간체 문서에 번체가 섞이거나, 중국어 문서에 일본식 한자가 남거나, 번역 메모리가 두 계열을 섞어 내놓는 경우다.

2절에서 본 대로 코드포인트만으로는 계열을 알 수 없다. 그래서 다른 방법을 쓴다. 한쪽 계열에만 존재하는 글자를 표본으로 모아 개수를 센다. 발/發, 국/國, 회/會, 문/門, 시/時처럼 간체와 번체가 다른 글자만 골라 두 집합을 만들고, 문서에서 각각 몇 개 나오는지 센다.

const HANS = new Set([...'这么无发国际会议们个东车马门问题时间实现体系统计龙凤业务产资总']);
const HANT = new Set([...'這麼無發國際會議們個東車馬門問題時間實現體系統計龍鳳業務產資總']);

function variant(t) {
  let s = 0, r = 0;
  for (const c of t) { if (HANS.has(c)) s++; if (HANT.has(c)) r++; }
  return { simplified: s, traditional: r };
}
variant('这是国际会议的问题');  // { simplified: 7, traditional: 0 }
variant('這是國際會議的問題');  // { simplified: 0, traditional: 7 }
variant('这是國際会议的问题');  // { simplified: 5, traditional: 2 }  ← 혼용
variant('中文');                // { simplified: 0, traditional: 0 }  ← 판정 불가

이 방식의 성질을 정확히 알아야 오해가 없다.

  • 혼용은 잘 잡는다. 한쪽만 기대되는 문서에서 반대편 표지가 나오면 그 위치가 곧 결함 위치다
  • 판정 불가 구간이 항상 남는다. 두 계열이 같은 글자만으로 이루어진 짧은 문자열은 어느 쪽인지 알 수 없다. 위 예의 中文이 그렇다
  • 표본 크기가 곧 감도다. 표지 글자를 20자만 쓰면 짧은 문서는 대부분 판정 불가로 떨어진다. 실무에서 쓰려면 수백 자 규모의 표를 만들어 두는 편이 낫다
  • 일본 신자체는 별도 문제다. 신자체 중에는 중국 간체와 같은 글자도 있고 다른 글자도 있다. 중국어 문서에 남은 일본식 한자를 잡으려면 「신자체에만 있고 간체에는 없는 글자」로 세 번째 표본을 따로 만들어야 한다

판단을 하나 적는다. 이 규칙은 경고에 두고 차단에 올리지 마라. 인용문에 원문 계열이 그대로 들어가는 경우, 고유명사가 번체로 굳어진 경우, 표본 글자가 우연히 다른 뜻으로 쓰인 경우가 모두 정당한 예외이기 때문이다. 문자 체계가 다른 혼입과 달리 여기서는 사람의 판정이 필요한 비율이 유의미하게 높다.

7. 깨진 글자와 언어 혼입은 다른 문제다

두 결함이 자주 한 검사기에 뭉뚱그려진다. 나눠야 한다. 원인이 다르고 고치는 방법이 다르기 때문이다.

  • 언어 혼입 — 문자는 완전히 정상이다. 있어야 할 자리가 아닐 뿐이다. 원인은 번역 공정에 있다
  • 깨짐(모지바케) — 문자 자체가 잘못 만들어졌다. 원인은 인코딩 처리에 있다

구별은 어렵지 않다. 깨짐에는 지문이 있다.

// UTF-8 바이트를 서유럽 인코딩으로 읽었을 때
Buffer.from('한글', 'utf8').toString('latin1');
// 'íê¸'  →  U+ED U+95 U+9C U+EA U+B8 U+80
//   Hangul 스크립트 0개, 라틴 확장 영역 문자가 줄지어 나온다

// cp949 바이트를 UTF-8로 읽었을 때
Buffer.from([0xC7, 0xD1, 0xB1, 0xDB]).toString('utf8');
// '�ѱ�'  →  대체 문자 U+FFFD 가 박힌다

U+FFFD 대체 문자자주 나온다없다

사람이 읽을 수 있나아니다읽힌다. 다른 언어일 뿐
스크립트 속성 판정원래 문자 체계가 사라진다정상적인 문자 체계로 잡힌다
고치는 곳파일 읽기·쓰기 지점의 인코딩번역 공정과 원본 파일

U+FFFD에 대해서는 유니코드 표준 5장이 잘못된 바이트열을 만났을 때의 처리 원칙을 정하고 있다. 대체 문자가 문서에 있다는 것은 어딘가에서 디코딩이 실패했다는 확정 신호이므로, 이건 언어 검사와 별개로 항상 차단해도 되는 몇 안 되는 규칙이다.

인코딩 오류가 어느 단계에서 생겼는지 특정하는 방법은 한글이 깨지는 지점을 특정하는 법에서 따로 다뤘다. 이 글에서는 그 결함이 언어 혼입 검사에 섞여 들어오지 않게 규칙과 보고 메시지를 분리하라는 데까지만 말한다. 두 결함이 같은 이름으로 보고되면 고치는 사람이 매번 엉뚱한 곳을 먼저 본다.

8. 정규화를 검사 앞에 둘 것인가 뒤에 둘 것인가

정규화 형태에 따라 같은 검사기가 다른 답을 낸다. 이게 실제로 판정을 뒤집는다.

const doc = 'The word 한글 appears here.'.normalize('NFD');

/[가-힣]/.test(doc);              // false  ← 놓친다
/\p{Script=Hangul}/u.test(doc);   // true   ← 잡는다
/[가-힣]/.test(doc.normalize('NFC'));  // true  ← NFC 로 바꾸면 잡힌다

이유는 단순하다. NFD로 분해된 한글은 완성형 음절이 아니라 자모 낱개의 나열이다. [가-힣]은 완성형 음절 영역만 보므로 하나도 걸리지 않는다. 스크립트 속성은 자모에도 Hangul이 붙어 있으므로 그대로 잡는다. UAX #15가 정의하는 네 가지 정규화 형태 중 어느 것으로 들어오느냐에 따라 결과가 갈리는 셈이다.

호환 정규화 쪽에서는 방향이 반대로 작동한다.

'ko 문서 안의 ｻｰﾊﾞｰ';
/[぀-ヿ]/.test(s);                   // false  ← 반각이라 놓친다
/[぀-ヿ]/.test(s.normalize('NFKC')); // true   ← NFKC 가 전각으로 바꿔 준다

'ｻｰﾊﾞｰ'.normalize('NFKC');  // 'サーバー'
'ＡＢＣ'.normalize('NFKC');   // 'ABC'
'㈱'.normalize('NFKC');      // '(株)'

여기서 실무 규칙이 나온다.

  1. 검사 대상 텍스트는 검사 직전에 NFC로 맞춘다. 자모 분해형으로 들어온 텍스트가 규칙을 통과하는 사고를 막는다
  2. 블록 범위 방식을 어쩔 수 없이 쓴다면 NFKC까지 적용한다. 반각 가나가 전각으로 바뀌어 범위에 들어온다
  3. 스크립트 속성 방식을 쓴다면 NFKC는 필요하지 않다. 반각 가나에도 Katakana 스크립트가 붙어 있어 정규화 없이 잡힌다
  4. 정규화한 텍스트를 그대로 저장하지 마라. 검사용 사본에만 적용한다. NFKC는 정보를 지우는 변환이라 원본에 적용하면 되돌릴 수 없다

마지막 항목은 일반적인 원칙의 특수한 경우다. 값을 바꾸는 시점과 검사하는 시점의 순서가 어긋나면 검사 결과 자체가 무의미해지는데, 이 축은 검증하고 나서 값을 바꾸면 검증이 무효가 된다에서 자세히 다뤘다. 한글이 NFC와 NFD 사이에서 어떻게 달라지는지, 어느 경계에서 형태가 바뀌는지는 한글이 자모로 분리되는 순간 쪽이 상세하다.

9. 검사기를 신뢰하려면 오염을 심어라

검사기가 아무것도 보고하지 않을 때, 그게 깨끗하다는 뜻인지 검사기가 고장 났다는 뜻인지 구별할 방법이 필요하다. 이건 실제로 자주 일어나는 실패다. 정규식에 플래그를 빠뜨리거나, 파일 확장자 필터가 어긋나거나, 범위 축소가 너무 넓어져서 본문 전체가 제거되어도 결과는 똑같이 「이상 없음」이다.

해결은 하나뿐이다. 일부러 오염을 심고 검사기가 잡는지 확인한다. 이건 검사기의 단위 시험이 아니라 감도 시험이다. 심는 표본은 실제로 나올 유형이어야 한다.

  1. 대상 언어와 다른 문자 체계 한 문장 — 가장 흔한 유형
  2. 반각 가나 — 블록 범위 방식이 놓치는 대표 사례
  3. 한글 호환 자모 — 자모 범위만 본 검사기가 놓친다
  4. NFD로 분해된 문자열 — 정규화 순서 결함을 드러낸다
  5. 키릴 한 낱말 — 파이프라인 사고 유형
  6. 한자와 한글이 붙은 낱말 — 인접 규칙이 살아 있는지 확인
  7. 간체·번체 혼용 문장 — 표지 표본이 충분한지 확인

그리고 반대편도 같이 심는다. 정당한 예외를 넣고 조용한지 확인해야 한다. 브랜드명이 들어간 문장, 괄호 병기, 코드 블록 안의 정규식, 가운뎃점을 쓴 나열. 오탐이 하나라도 나오면 그 규칙은 아직 배포할 수 없다.

이 시험은 회귀 시험으로 붙박아 두는 것이 요점이다. 표본 파일을 저장소에 넣고, 검사기가 오염 표본 전부를 잡고 정상 표본 전부를 통과시키는지 매번 확인한다. 규칙을 하나 고칠 때마다 예전에 잡던 것을 놓치게 되는 일이 실제로 생기고, 그건 이 시험 없이는 드러나지 않는다.

표본을 만들 때 한 가지. 오염 표본 파일 자체가 검사 대상 폴더 안에 있으면 검사기가 그 파일을 결함으로 보고한다. 표본은 검사 범위 밖에 두거나, 파일명 규칙으로 명확히 제외하라. 그리고 그 제외 규칙 때문에 진짜 문서가 같이 빠지지 않는지 한 번 더 확인해야 한다.

10. 무엇을 막고 무엇을 경고만 할 것인가

규칙을 전부 같은 무게로 다루면 안 된다. 차단으로 올릴 조건은 셋이고, 셋이 동시에 성립할 때만 올린다.

  1. 오탐이 사실상 0이다. 정상 문서에서 걸리는 경우를 설명할 수 없어야 한다
  2. 판정 근거를 즉시 확인할 수 있다. 위치와 원문 조각이 보고에 들어 있어야 한다
  3. 고치는 방법이 명백하다. 「이 문장을 번역하라」처럼 행동이 하나로 정해져야 한다
규칙판정이유
U+FFFD 대체 문자 존재차단디코딩 실패의 확정 신호. 정당한 경우가 없다
en 문서 안의 한글·가나·키릴차단범위 축소와 허용 목록을 거친 뒤라면 오탐이 거의 없다
zh 문서 안의 가나차단위와 같다
ja 문서 안의 한글차단위와 같다
어느 언어든 예상 밖 키릴차단파이프라인 사고 유형. 정상 문서에 들어올 경로가 없다
한자와 한글이 붙은 낱말차단병기 형태를 구조적으로 비켜 가므로 오탐이 낮다
비율 임계값 초과경고임계값 자체가 판단이다. 문서 종류마다 정당한 편차가 있다
간체·번체 혼용경고인용·고유명사라는 정당한 예외가 실제로 존재한다
ko 문서 안의 한자규칙 없음병기가 정상이다. 규칙을 만들면 오탐만 생긴다
한자만으로 된 짧은 문자열의 언어규칙 없음판별 불가 구간. 검사 대상에서 제외한다

표에서 마지막 두 행이 중요하다. 규칙을 만들지 않는 것도 설계 결정이다. 잡을 수 없는 것을 잡으려 들면 그 규칙은 반드시 오탐으로 되돌아오고, 오탐은 4절에서 본 대로 검사기 전체를 끌어내린다.

경고 등급에도 조건을 하나 붙이는 편이 낫다. 경고 건수가 늘어나는 것 자체를 지표로 본다. 지난주 12건이던 경고가 이번 주 80건이면, 개별 건을 다 열어 보지 않아도 어느 배치에서 뭔가 달라졌다는 것을 안다. 경고를 「나중에 볼 목록」이 아니라 추세를 읽는 계기판으로 쓰면 무시되는 속도가 느려진다.

10.1 도입 순서

한 번에 전부 켜면 첫날에 경고 수백 건이 나오고 그대로 꺼진다. 순서를 나눈다.

  1. 먼저 보고만 한다. 차단 없이 한두 주 돌려서 현재 상태의 실제 규모를 본다
  2. 오탐 유형을 분류한다. 브랜드·코드·병기·기타로 나누고, 기타가 무엇인지 반드시 확인한다
  3. 범위 축소와 허용 목록으로 오탐을 0에 가깝게 만든다. 이 단계가 대부분의 시간을 먹는다
  4. 기존 결함을 한 번에 정리한다. 남겨 두고 차단을 켜면 무관한 변경이 전부 막힌다
  5. 오탐이 0인 규칙만 차단으로 올린다. 나머지는 경고에 둔다
  6. 회귀 표본을 붙인다. 이 시점에 붙여야 이후 규칙 변경에서 감도가 유지된다

4단계를 건너뛰는 경우가 많은데, 이게 도입 실패의 가장 흔한 원인이다. 기존 결함이 남아 있는 상태에서 차단을 켜면 이 결함과 아무 상관 없는 변경이 전부 막힌다. 그러면 사람은 검사기를 고치는 대신 우회 주석을 달기 시작하고, 그 주석이 늘어나는 순간 규칙은 이미 죽은 것이다.

11. 확인하지 못한 것

아래 항목은 근거를 특정하지 못해 본문에서 수치나 단정으로 쓰지 않았다.

  • 다른 런타임에서의 스크립트 속성 동작. 본문의 실행 결과는 Node 22 기준이다. 정규식의 \p{Script=…}는 런타임이 내장한 유니코드 데이터 버전에 따라 결과가 달라질 수 있고, 특히 국제화 데이터를 줄여 빌드한 환경에서 어떻게 되는지는 확인하지 못했다
  • 파이썬·자바·Go 등에서의 동등한 표현. 각 언어의 정규식 엔진이 스크립트 속성을 어떤 문법으로 지원하는지, 지원 범위가 같은지는 대조하지 못했다
  • 통계적 언어 판별 라이브러리와의 비교. n-gram 기반 언어 판별기가 짧은 문자열에서 어느 정도 정확한지, 문자 체계 검사와 조합했을 때 이득이 얼마나 되는지는 측정하지 않았다
  • 간체·번체 표지 글자의 적정 규모. 본문 예제는 20자대 표본이다. 실무에서 몇 자를 넣어야 짧은 문서에서도 판정이 서는지는 문서 성격에 따라 달라지므로 수치를 제시하지 않았다
  • 일본 신자체 전용 글자 집합. 신자체에만 있고 간체에는 없는 글자의 완전한 목록은 확인하지 못했다
  • 동남아시아 문자권과 아랍 문자권의 예외 유형. 태국어·크메르어처럼 띄어쓰기가 없는 문자권, 아랍 문자처럼 양방향 텍스트가 들어가는 경우에 어떤 정당한 예외가 추가로 필요한지는 다루지 못했다
  • 오탐률의 절대 수치. 본문 3.1의 열네 개 표본은 실패 유형을 보이기 위한 것이지 정확도 측정이 아니다. 실제 문서 집합에서의 오탐률은 문서 성격에 크게 좌우된다

결론: 잡히는 범위를 넓히지 말고 보고를 조여라

다국어 문서의 언어 혼입 검사는 두 부분으로 갈린다. 앞부분은 기계적이다. 유니코드가 이미 모든 문자에 문자 체계를 적어 뒀으므로, 스크립트 속성을 읽고 대상 언어에서 나올 수 없는 값을 찾으면 된다. 블록 범위를 손으로 적는 흔한 방식보다 이쪽이 명백히 낫고, 바꾸는 데 드는 비용도 크지 않다.

뒷부분이 설계다. 고유명사와 코드와 병기를 가려내지 못하면 검사기는 오탐 더미가 되고, 오탐 더미가 된 검사기는 꺼진다. 그래서 규칙을 만들 때의 기본 방향은 「더 많이 잡기」가 아니라 「보고되는 것이 전부 진짜이도록 조이기」다. 놓친 유형은 나중에 규칙을 하나 더 붙이면 되지만, 한 번 신뢰를 잃은 검사기는 되살리기 어렵다.

당장 해 볼 만한 것 두 가지만 남긴다. 하나는 지금 쓰는 검사 규칙에 반각 가나와 한글 호환 자모를 넣어 보는 일이다. 잡히는 게 나오면 그동안 그 유형을 통째로 놓치고 있었다는 뜻이다. 다른 하나는 정상 문서 열 개에 검사기를 돌려 보는 일이다. 여기서 나오는 경고가 곧 그 검사기의 수명이고, 하나라도 나오면 규칙을 조일 차례다.

  • 1차. MDN - Intl.Segmenter — grapheme·word·sentence 세 가지 granularity, 분절 결과의 isWordLike 속성, 띄어쓰기가 없는 언어에서 split보다 나은 이유의 출처
