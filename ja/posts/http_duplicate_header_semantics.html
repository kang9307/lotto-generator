同じヘッダーが二度届いたら - 結合してよいものと絶対にだめなもの

フィールドごとに異なる「複数」の意味、そしてランタイムが代わりに決めてしまうもの

2026-08-01 開発・インフラ

症状から: クッキーを二つ返したのに一つしか保存されない

ログイン応答でセッションクッキーとテーマクッキーを一緒に返した。サーバーログには両方とも記録されている。ところがブラウザにはセッションクッキーが一つだけ残っている。コードを開いてもクッキーを作る部分に間違いはない。それで多くの場合、ブラウザの設定やドメインの問題を疑って半日を使うことになる。

この症状のかなりの部分は、もっと手前で決まっている。どこかで二行だったヘッダーが一行に結合されたのだ。そしてその結合はたいてい間違いではない。むしろ大半のフィールドでは結合こそが仕様の定める正しい動作である。問題は、仕様がそう定めていないフィールドにまで同じ処理をしたときに起きる。

だからこの記事の主題は「重複ヘッダーを防ごう」ではない。防げないし防ぐ理由もない。本当の問いはこれだ。

  • 同じ名前が二度来たことが、そのフィールドでは何を意味するのか。リストが増えたのか、値が二つあるのか、あってはならない状態なのか
  • 結合するかどうかを誰が決めるのか。開発者が決めるのではなく、ランタイムが先に決めてしまう場合が多い
  • 自分のコードが見ているのは届いたものか、すでに加工されたものか。文字列一つを受け取った時点で、情報はすでに消えているかもしれない

三つとも実行して答えを出した。同じバイト列を異なるランタイムに流し込み、受け取った側が何を手にするのかを出力した。結果は一文にまとまる。フィールドごとに「複数」の意味が違い、ランタイムごとにその意味の扱いが違う。

実行環境。以下のすべての出力はWindows 10 Pro (10.0.19045)で実際に実行した結果である。ランタイムはNode.js v22.16.0 (win32)とPython 3.13.3 (win32)で、サーバーは各言語の標準HTTPモジュールで直接起動した。リクエストは生ソケットでバイトを直接書き込んだ。クライアントライブラリが送信前にヘッダーを正規化するのを避けるためである。使用したポートは18090から18094で、測定が終わったあとすべて終了させた。

この記事は特定の製品の挙動を断定しない。7節に出てくる中継はこの記事のために自分で書いた二十行ほどの最小実装であり、商用プロキシやロードバランサ、Webサーバー製品の挙動を代表しない。各製品がどう処理するかは皆さんの環境で直接測定する必要がある。この記事が提供するのは結論ではなく、測定の方法と判断の基準である。

この記事が扱わないもの。ヘッダー名の大文字小文字が作る別の罠は名前は区別しないのにコードは区別するで扱った。ここでは名前が完全に同じ場合だけを見る。クッキー属性の意味はSameSite Lax・Strict・Noneにある。3節では属性ではなく行を結合すると値が壊れるという一点だけを見る。

1. 同じ名前を二度送ると何が届くのか

まず最も基本的な再現である。名前が同じヘッダーを二行ずつ入れたリクエストを一つ作り、そのまったく同じバイト列を二つのサーバーにそれぞれ送った。送ったのは次のものだ。

GET /dup HTTP/1.1
Host: shop.example.test
X-Trace-Id: aaa-111
X-Trace-Id: bbb-222
Accept: text/html
Accept: application/json
X-Forwarded-For: 203.0.113.9
X-Forwarded-For: 198.51.100.4
Cookie: sid=A1
Cookie: theme=dark
Connection: close

受け取った側が何を持っているかを三つのAPIでそれぞれ出力した。まずNodeである。

1-A. Node.js v22.16.0 / win32
status : HTTP/1.1 200 OK

  req.headers[x-trace-id      ] = 'aaa-111, bbb-222'
  req.headers[accept          ] = 'text/html, application/json'
  req.headers[x-forwarded-for ] = '203.0.113.9, 198.51.100.4'
  req.headers[cookie          ] = 'sid=A1; theme=dark'

  req.headersDistinct[x-trace-id      ] = ['aaa-111', 'bbb-222']
  req.headersDistinct[accept          ] = ['text/html', 'application/json']
  req.headersDistinct[x-forwarded-for ] = ['203.0.113.9', '198.51.100.4']
  req.headersDistinct[cookie          ] = ['sid=A1', 'theme=dark']

  req.rawHeaders (flat, order kept):
    [0] Host: shop.example.test
    [1] X-Trace-Id: aaa-111
    [2] X-Trace-Id: bbb-222
    [3] Accept: text/html
    [4] Accept: application/json
    [5] X-Forwarded-For: 203.0.113.9
    [6] X-Forwarded-For: 198.51.100.4
    [7] Cookie: sid=A1
    [8] Cookie: theme=dark
    [9] Connection: close

三つのAPIが同じリクエストに対してそれぞれ違う絵を返す。最も広く使われる一つ目は、二行をカンマと空白でつないだ文字列一つを返す。二つ目と三つ目は行をそのまま保存する。そしてCookieだけがカンマではなくセミコロンでつながれている点に注目したい。このフィールドはもともとセミコロン区切りのリストなので、ランタイムがフィールドごとに違う規則を適用したのである。

次に同じバイト列をPythonサーバーに送った。

1-B. Python 3.13.3 / win32
status : HTTP/1.1 200 OK

  headers.get(x-trace-id      )     = 'aaa-111'
  headers.get(accept          )     = 'text/html'
  headers.get(x-forwarded-for )     = '203.0.113.9'
  headers.get(cookie          )     = 'sid=A1'

  headers.get_all(x-trace-id      ) = ['aaa-111', 'bbb-222']
  headers.get_all(accept          ) = ['text/html', 'application/json']
  headers.get_all(x-forwarded-for ) = ['203.0.113.9', '198.51.100.4']
  headers.get_all(cookie          ) = ['sid=A1', 'theme=dark']

  headers.items() (order kept):
    Host: shop.example.test
    X-Trace-Id: aaa-111
    X-Trace-Id: bbb-222
    Accept: text/html
    Accept: application/json
    X-Forwarded-For: 203.0.113.9
    X-Forwarded-For: 198.51.100.4
    Cookie: sid=A1
    Cookie: theme=dark
    Connection: close

ここでこの記事の最初の核心が現れる。同じバイト列なのに、文字列APIが返す答えが二つのランタイムで違う。

  • 一方は二行をつなぐ。情報は残るが境界が消える
  • もう一方は最初の行だけを返す。二行目は黙って捨てられる。例外も警告もない
  • 両方のランタイムともすべての行を配列で返す別のAPIを持っている。名前が違うだけで存在は同じだ
  • どちらもエラーを出さなかった。重複ヘッダーそのものはプロトコル違反ではない
  • だから「重複ヘッダーが来たらどうなるのか」という問いはサーバー一つだけを見て答えられない

実務でこの差が恐ろしく現れる場面がある。あるチームが文字列APIを使う言語で前段を書き、別のチームが別の言語で後段を書いたとしよう。同じリクエストについて、前段は「値が二つつながった文字列」を見て、後段は「最初の値一つ」を見る。どちらも正常な動作であり、どちらもログに何の痕跡も残さない。

2. リスト型フィールドは結合するのが仕様

結合が常に間違いだという印象を与えたくない。むしろ逆である。かなりの数のフィールドは結合すべきだ。RFC 9110の5.2節はこう定義している。

一つのセクション内でフィールド名が繰り返される場合、その結合フィールド値は、そのセクション内の対応するフィールドライン値を順序どおりに連結し、各フィールドライン値をカンマで区切ったリストで構成される。(RFC 9110, 5.2節)

つまり「二行で送る」と「一行にカンマで入れる」はリスト型フィールドでは同じ意味でなければならない。本当にそうなのかを確かめた。同じ三つのフィールドを二通りで送り、結果を比較した。

EXP 2. list-based fields: two lines vs one comma line

 [Node.js v22.16.0]
   accept          via req.headers
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     parsed two lines : ['text/html', 'application/json']
     parsed one line  : ['text/html', 'application/json']
     SAME MEANING     : True
   cache-control   via req.headers
     two lines -> 'no-cache, max-age=0'
     one line  -> 'no-cache, max-age=0'
     parsed two lines : ['no-cache', 'max-age=0']
     parsed one line  : ['no-cache', 'max-age=0']
     SAME MEANING     : True
   accept-encoding via req.headers
     two lines -> 'gzip, br'
     one line  -> 'gzip, br'
     SAME MEANING     : True

 [Python 3.13.3]
   accept          via join(get_all())
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     SAME MEANING     : True
   cache-control   via join(get_all())
     SAME MEANING     : True
   accept-encoding via join(get_all())
     SAME MEANING     : True

両方のランタイムで、三つのフィールドすべてが同じリストに分解された。リスト型フィールドでは、行に分かれて来ようが一行にカンマで来ようが最終的な意味は同じだということだ。だからここでは結合は損失ではない。

ただし前提がある。同じ5.3節がこう明記している。

そのフィールドの定義が複数のフィールドライン値をカンマ区切りのリストとして再結合することを許さない限り、送信者は一つのメッセージ内で同じ名前のフィールドラインを複数生成してはならず、すでに同じ名前のフィールドラインがあるところに追加してもならない。(RFC 9110, 5.3節)

つまり結合してよいのは仕様がリストとして定義したフィールドだけであり、それ以外を名前が同じという理由で結合するのは仕様が禁じた側に近い。順序についても同じ節がはっきり書いている。

したがって、同じ名前のフィールドラインが受信される順序はフィールド値の解釈にとって有意であり、プロキシはメッセージを転送する際にこれらのフィールドライン値の順序を変更してはならない。(RFC 9110, 5.3節)

順序が意味を持つという点は実務でよく無視される。値をソートしたり集合にして重複を除いたりするコードはありふれているが、リスト型フィールドでそれは優先順位の情報を捨てる行為である。

2.1 一行に複数、複数行に複数が混ざるとき

実戦では両方が混ざる。二行で来るのに、そのうち一行にさらにカンマが入っている場合だ。このとき行だけを数えると個数を間違える。

request sent:
  > Accept: text/html
  > Accept: application/json, text/plain

readList(accept) = ["text/html","application/json","text/plain"]
  note: 2 field lines, 3 members.

フィールドラインは二つなのにリストの構成要素は三つである。したがってリスト型フィールドを読む正しい手順は二段階だ。まず配列APIですべての行を受け取り、次に各行をカンマで分けて一つに平坦化する。行だけを数えるコードも、文字列一行だけを分けるコードも、どちらも半分でしかない。

3. Set-Cookieは結合すると値が壊れる

ここからが例外である。そしてこの例外は些細ではない。冒頭の症状がまさにここから出てくる。

クッキー二つを正しくそれぞれ一行ずつ返すとこう届く。

3-A. server sent TWO Set-Cookie lines (correct)
 res.headers["set-cookie"] type : Array
 value:
   [0] sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly
   [1] theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 cookies the client will store : ["sid=A1","theme=dark"]
 count = 2

クッキー二つがそのまま保存される。次にまったく同じ二つのクッキーをカンマと空白でつないで一行にした。リスト型フィールドなら何の問題もなかった処理である。

3-B. the SAME two cookies glued with ", " into one line
 raw value on the wire:
   sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly, theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 now split it back on "," the way a list-based field is split:
   [0] sid=A1; Path=/; Expires=Wed
   [1] 20 Aug 2026 10:00:00 GMT; HttpOnly
   [2] theme=dark; Path=/; Expires=Fri
   [3] 22 Aug 2026 10:00:00 GMT
 pieces = 4   (we started with 2 cookies)
 cookies the client would store : ["sid=A1","20 Aug 2026 10:00:00 GMT","theme=dark","22 Aug 2026 10:00:00 GMT"]

クッキー二つが断片四つに砕けた。原因は明確だ。有効期限の表記が曜日の後にカンマを持っているため、カンマを区切り子とみなした瞬間にクッキー一つがその内部で二つに切られる。そして切られた後半が新しいクッキーのように見える。

RFC 9110はこの状況を予見して5.5節にこう書いた。

HTTP-dateやURI-reference要素のように構成要素の中にカンマを含むことが予想されるフィールドは、そのデータ内のカンマを潜在的なリスト区切り子と区別できるよう、当該要素の周りに区切り記号を置いて定義されるべきである。(RFC 9110, 5.5節)

クッキーのフィールドはそう定義されていない。有効期限のカンマを囲む引用符がない。だからカンマだけを見て、どれが区切り子でどれがデータなのかを判別する方法が原理的に存在しない。同じ文書の5.3節はこのフィールドを名前を挙げて例外として明示している。

実際には、Set-Cookieヘッダーフィールドは応答メッセージで複数のフィールドラインにわたって現れることが多く、リスト構文を使用しないため、同じフィールド名の複数のフィールドラインに関する上記の要求に違反している。(RFC 9110, 5.3節)

3.1 有効期限がなくても安全ではない

「では有効期限属性を使わなければよいのでは」と考えるかもしれない。確かめてみるとそちらのほうが悪い。

3-D. even without Expires, joining loses a cookie boundary
 two lines  -> ["sid=A1; Path=/","theme=dark; Path=/"]
   stored   -> ["sid=A1","theme=dark"]  count=2
 one line   -> "sid=A1; Path=/, theme=dark; Path=/"
   a cookie parser reads ONE cookie from ONE line:
     name/value = sid=A1
     attributes = ["Path=/, theme=dark","Path=/"]
   -> "theme=dark" arrived as an ATTRIBUTE of sid, not as a cookie.
   -> stored cookies = ["sid=A1"]   count=1   (one cookie silently vanished)

ここで冒頭の症状が正確に再現される。クッキーを二つ返したのに一つしか保存されなかった。二つ目のクッキーが消えたのではなく一つ目のクッキーの属性として吸収されたのだ。パーサから見れば一行はクッキー一つであり、セミコロンの後はすべて属性である。認識できない属性は無視されるのでエラーも出ない。

  • サーバーログにはクッキーを二つ作った記録が残る。だからサーバー側をいくら見ても原因が見えない
  • ブラウザの開発者ツールのストレージタブにはクッキーが一つだけ見える。応答ヘッダータブには長い一行が見える
  • 消えるのは常に後ろのクッキーだ。だから「最後に入れたクッキーだけ効かない」という形で報告が来る
  • 有効期限属性があると正体不明のクッキーが生まれることもある。切られた日付の断片がクッキー名のように見えるからだ
  • クッキー属性そのものの意味はこの問題とは別である。そちらはSameSiteの挙動で扱った

3.2 文字列に変換した瞬間に戻ってくる

このフィールドを配列でうまく受け取っておきながら最後で台無しにする経路がある。

3-E. what the array API vs the string API report
 res.headers["set-cookie"]         = Array(2)
 res.headersDistinct["set-cookie"] = Array(2)
 res.rawHeaders set-cookie lines   = 2
 String(res.headers["set-cookie"]) = "sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly,theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT"
   <- the moment you coerce it to a string, the "," is back and the damage is done

配列は文字列に変換された瞬間にカンマでつながった一つの文字列になる。ログに出したり、テンプレート文字列に入れたり、別の応答にそのままコピーするコードがこれに当たる。このフィールドだけは配列のまま最後まで扱わなければならない。

4. Hostが二つのとき - どちらをどの層が信じるか

ここからはリストではないフィールドである。Hostはリクエストがどの対象に向かうのかを決める単一値フィールドだ。二行送るとどうなるかを測定した。

EXP 4-A. two Host lines, different authorities
  > GET /who HTTP/1.1
  > Host: front.example.test
  > Host: back.example.test
  > Connection: close

 Node.js v22.16.0:
  status : HTTP/1.1 200 OK
    req.headers[host]         = 'front.example.test'
    req.headersDistinct[host] = ['front.example.test', 'back.example.test']

 Python 3.13.3:
  status : HTTP/1.1 200 OK
    headers.get(host)     = 'front.example.test'
    headers.get_all(host) = ['front.example.test', 'back.example.test']

測定結果はこうだ。両方のサーバーとも拒否しなかった。どちらも200を返し、文字列APIで問うと最初の値を返す。そしてどちらも配列APIで問うと二つの値がどちらも残っている。

ここで興味深いのはNodeの挙動だ。1節ではX-Trace-Idをカンマでつないだのに、Hostはつながずに最初の値だけを返した。同じランタイムがフィールドによって違う規則を使うということである。どのフィールドがそういう扱いを受けるのかをより広く確認した。

EXP 4-B. single-value fields sent twice
  > Authorization: Bearer FIRST
  > Authorization: Bearer SECOND
  > Content-Type: application/json
  > Content-Type: text/plain
  > User-Agent: agent-one
  > User-Agent: agent-two
  > X-Trace-Id: aaa
  > X-Trace-Id: bbb

 Node.js v22.16.0:
    req.headers[authorization]         = 'Bearer FIRST'
    req.headersDistinct[authorization] = ['Bearer FIRST', 'Bearer SECOND']
    req.headers[content-type]          = 'application/json'
    req.headersDistinct[content-type]  = ['application/json', 'text/plain']
    req.headers[user-agent]            = 'agent-one'
    req.headersDistinct[user-agent]    = ['agent-one', 'agent-two']
    req.headers[x-trace-id]            = 'aaa, bbb'
    req.headersDistinct[x-trace-id]    = ['aaa', 'bbb']

 Python 3.13.3:
    headers.get(authorization)     = 'Bearer FIRST'
    headers.get_all(authorization) = ['Bearer FIRST', 'Bearer SECOND']
    headers.get(x-trace-id)        = 'aaa'
    headers.get_all(x-trace-id)    = ['aaa', 'bbb']

Nodeは単一値として知られるフィールドの一覧を内部に持っており、その一覧にあるフィールドはつながずに最初の値だけを残す。だから認証トークンが二つ来たとき、文字列APIは最初のものだけを見せる。二つ目のトークンはコードが動く前にすでに視界から消えている状態だ。

4.1 なぜ危険なのか - 判定する層が二つ以上あるとき

この状況が危険なのは値がおかしいからではない。構造のためである。リクエスト一つを複数の層が順に判定する構成を考えてみよう。前段が何かを見て決定を下し、後段がまた同じものを見て決定を下す。

  • 同じ名前が二行来たとき、どちらが本物なのかは仕様ではなく実装が決める。上の測定では二つのランタイムがたまたま両方とも最初の値を選んだが、それをすべての実装がそうだという根拠には使えない
  • 前段が最初の値を信じ、後段が最後の値を信じる組み合わせが成立すると、二つの層が互いに違う対象について判定することになる。どちらもエラーを出さない
  • 前段が結合して渡し、後段が結合された文字列全体を一つの値として扱う組み合わせもある。このとき後段が見る値は前段が判定した値と文字列そのものが違う
  • このずれはログで追跡しにくい。各層のログにはその層が選んだ値一つしか出ないからだ。二つのログを並べる前には差が見えない
  • したがって対処は値をうまく選ぶことではなく選ぶ必要が生じないようにすることである。つまり境界で正規化するか拒否する

実務の規則は単純だ。対象を決めるフィールドが二行以上来たなら、そのリクエストはすでに正常ではない。どの値が正しいかを悩むのではなく、最も外側の境界で行数を数えて一つでなければ拒否するか一つに正規化し、その後の層が再び判定しないようにすべきである。後ろで各自に判定させた瞬間、層ごとに違う答えが出る余地が生まれる。

5. Content-Lengthの重複 - ここでは拒否が正解

Content-Lengthは本文がどこで終わるのかを決めるフィールドだ。この値が曖昧になるとメッセージの境界そのものが曖昧になる。値が違うときと同じときを分けて測定した。

EXP 5. duplicate Content-Length, measured

 Node.js v22.16.0 http server
  baseline: one Content-Length             -> HTTP/1.1 200 OK    headers['content-length']='5'  headersDistinct=['5']
  two Content-Length, SAME value           -> HTTP/1.1 400 Bad Request
  two Content-Length, DIFFERENT values     -> HTTP/1.1 400 Bad Request
  one Content-Length holding a comma list  -> HTTP/1.1 400 Bad Request

 Python 3.13.3 http.server

  two Content-Length, SAME value           -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '5']
  two Content-Length, DIFFERENT values     -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '7']

 [clientError] code=HPE_UNEXPECTED_CONTENT_LENGTH msg=Parse Error: Duplicate Content-Length

 [clientError] code=HPE_INVALID_CONTENT_LENGTH   msg=Parse Error: Invalid character in Content-Length

二つのランタイムの態度が正反対だ。まとめるとこうなる。

  • Nodeは値が完全に同じでも拒否する。5と5が来たのに400である。「矛盾がないから通す」ではなく「重複そのものがエラー」という態度だ
  • 拒否はアプリケーションコードに届く前のパーサ段階で起きる。リクエストハンドラはそもそも呼ばれなかった
  • 一行にカンマのリストとして入れた場合は別のエラーコードで拒否された。値にカンマが入ったこと自体を問題としたのである
  • Pythonの標準ライブラリのサーバーは四つのケースすべてを通し、よく使われる取得メソッドは5だけを返した。二つ目の値が7でも5でもコードは違いを見られない
  • つまり同じリクエストが一方のランタイムでは400で、もう一方では200である。このフィールドに関しては「一般的なサーバーの挙動」というものが存在しない

仕様は値にカンマが入ることについて明確だ。

送信者は、カンマを含むフィールド値を持つContent-Lengthヘッダーフィールドを送信してはならない。(RFC 9110, 8.6節)

ここから得られる実務指針は一つだ。本文の境界を決めるフィールドは黙って一つを選んではいけない。値が同じに見えても同様である。値が同じだという確認そのものが配列APIを使ってはじめて可能なことであり、文字列APIだけを使うコードは値が同じか違うかすら分からない。このフィールドに関しては厳格なほうが正しい。

6. ランタイムが渡すデータ構造 - 文字列が届いたときにはもう遅い

ここまでの観察を一つにまとめるとこうなる。結合するかどうかをランタイムが代わりに決めてしまえば、開発者はすでに決まった結果だけを見る。これがなぜ取り返しのつかない決定なのかを証明した。

6-B. the proof: a joined string cannot tell you what arrived
 case A: two lines  -> ["aaa-111","bbb-222"]
 case B: one line   -> ["aaa-111, bbb-222"]
 joined A           = "aaa-111, bbb-222"
 joined B           = "aaa-111, bbb-222"
 joinA === joinB    : true
 -> two different wire shapes collapse to the same string.

行が二つだった場合と、行が一つでその中にカンマがあった場合がまったく同じ文字列になった。この文字列を受け取ったコードには、もとは何行来たのかを知る手段がない。情報が隠されたのではなく消えたのである。あとからどれほど精密に解析しても復元されない。

同じ罠が値そのものにカンマが入っているときに逆方向でも生じる。

6-C. a value that legitimately contains a comma
 one line whose value has a comma : ["Wed, 20 Aug 2026 10:00:00 GMT"]
 joined                           : "Wed, 20 Aug 2026 10:00:00 GMT"
 naive split(",")                 : ["Wed","20 Aug 2026 10:00:00 GMT"]
 pieces = 2  from 1 original line(s)

一行だった値がカンマ分割で二つの断片になった。だからカンマで分けるのは、そのフィールドの文法がリストだと定義しているときにだけ有効である。すべてのヘッダーに一律に適用するユーティリティ関数は、まさにこの地点で静かに間違える。

6.1 ブラウザとサーバーが共有するヘッダーオブジェクト

Web標準のヘッダーオブジェクトはブラウザとサーバーの両方で使われる。このオブジェクトが何を返すのかも確認した。

6-A. WHATWG Headers (the fetch API object)
 h.get("x-trace-id")      = "aaa-111, bbb-222"
   typeof                 = string
 h.get("set-cookie")      = "sid=A1; Path=/, theme=dark; Path=/"
   typeof                 = string
 h.getSetCookie()         = ["sid=A1; Path=/","theme=dark; Path=/"]
   length                 = 2
 [...h.entries()]         = [["set-cookie","sid=A1; Path=/"],["set-cookie","theme=dark; Path=/"],["x-trace-id","aaa-111, bbb-222"]]

重要なのは二行目だ。一般の取得メソッドはクッキーのフィールドについてもつなげた文字列一つを返す。3節で砕けるのを見たまさにその形である。だからこのオブジェクトにはクッキー専用の配列取得メソッドが別に用意されている。そのメソッドを使わなければ3節の破壊がそのまま起きる。

一方、項目の走査はクッキーのフィールドを二つの項目として別々に返した。同じオブジェクトの中でも、どのアクセサを使うかで答えが違うというのが要点である。

ここまで実行で確かめたことをまとめた。この表で「損失」と書かれたAPIで判定を下してはならない。

7. 自作中継を一ホップ - 読むAPIが後段の見るものを決める

前節の「情報が消える」が一つのプロセス内の問題で終わらないことを示すには、ホップをもう一つ置く必要がある。そこで二十行ほどの中継を二本作った。二つの中継はヘッダーを読むAPI一つだけが違い、あとは同一である。

この節の中継はこの記事のために自分で書いた最小実装である。いかなる商用プロキシ、ロードバランサ、APIゲートウェイ、Webサーバーの挙動も代表せず、それらがこう動くという根拠には使えない。ここで示したいのは製品の挙動ではなく「中継がヘッダーをどのAPIで読むかが後段の見るものを決める」という因果構造一つだけである。皆さんが使う製品がどう処理するかはこの記事の方法で直接測定すればよい。

=== EXP 7. one hop through a hand-written relay ===
client sends (same bytes in every case):
  > GET /through HTTP/1.1
  > Host: shop.example.test
  > X-Trace-Id: aaa-111
  > X-Trace-Id: bbb-222
  > Accept: text/html
  > Accept: application/json
  > X-Note: first
  > X-Note: second

7-A. NO relay: straight to the origin
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2
   x-note     lines at origin : 2

7-B. relay reading req.headers (the string API)
   origin saw  x-trace-id: aaa-111, bbb-222
   origin saw  accept: text/html, application/json
   origin saw  x-note: first, second
   x-trace-id lines at origin : 1   value="aaa-111, bbb-222"
   x-note     lines at origin : 1   value="first, second"

7-C. relay reading req.rawHeaders (the array API)
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2   value="aaa-111, bbb-222"
   x-note     lines at origin : 2   value="first, second"

結果をまとめるとこうだ。

  • 中継を通さなければ二行が二行のまま届く。元の状態である
  • 文字列APIで読む中継を通すと二行が一行になって届く。中継が値を変えたのではない。中継は自分が持っていないものを転送できなかっただけである。読んだ時点ですでに文字列一つだった
  • 配列APIで読む中継を通すと行数が最後まで保たれる。同じ中継、API一つの差である
  • 注目すべきは7-Cの最後の二行だ。後段で行は二つなのに文字列APIで問うと依然としてつながった一つである。つまり前段がうまく転送しても後段がどのAPIで読むかによって再び損失が起きる
  • したがって両方の層がともに配列APIを使うときにだけ二つの層が同じものを見る。片方だけ直しても足りない

ここから出る結論がこの記事の核心の一つだ。「うちの前段はヘッダーに触らない」という言い方はたいてい値を修正しないという意味である。ところが値を修正しなくても行の構造は読み方だけで変わる。誰も手を触れていないのに形が変わっているのが、この問題の性質である。

8. 設計規則 - 何を結合し何を分けるか

ここまでの測定を実務の規則に変えた。まずフィールドを三つに分類する。この分類がすべての判断の出発点である。

8.1 安全に読む三つの関数

実際に使った実装は短い。分類ごとに一つずつあれば十分である。

// リスト型: 全行を受け取り、各行をカンマで平坦化する（2段階）
function readList(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  return lines.flatMap(v => v.split(',').map(s => s.trim())).filter(Boolean);
}

// 単一値: 行が一つでなければ値を返さず拒否する
function readSingleton(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  if (lines.length === 0) return { ok: true, value: null };
  if (lines.length > 1)   return { ok: false, reason: 'arrived ' + lines.length + ' times', lines };
  if (lines[0].includes(',')) return { ok: false, reason: 'single line contains a comma', lines };
  return { ok: true, value: lines[0] };
}

// 絶対に結合しない: 配列のまま、文字列にしない
function readCookies(distinct) {
  return (distinct['set-cookie'] || []).slice();
}

Python側も構造は同じだ。取得メソッドを変えるのがすべてである。

# 損失あり: 最初の行だけが来る
value = headers.get('x-trace-id')

# 無損失: すべての行が来る
lines = headers.get_all('x-trace-id') or []

# リスト型は2段階
members = [p.strip() for line in lines for p in line.split(',') if p.strip()]

# 単一値は行数を先に見る
if len(lines) != 1:
    raise ValueError('singleton field arrived %d times' % len(lines))

8.2 前段と後段が同じ値を見るようにする方法

7節で見たとおり片方だけ直しても足りない。順番に書くとこうなる。

  • 最も外側の境界で一度だけ正規化する。単一値フィールドが二行以上ならその場で拒否するか一つに減らす。内側の層はすでに整理されたものを受け取ると仮定できなければならない
  • 内側で再び判定しない。同じフィールドを複数の層がそれぞれ解釈する構成がずれの原因である。判定は一箇所でだけ行う
  • 判定に使う値は必ず配列APIで読む。値を使うためではなく何行来たのかを併せて見るためである。行数が分からなければ正規化も拒否もできない
  • 中継のコードは読んだそのままを転送する。文字列で受けて文字列で渡した瞬間、後段の選択肢が消える
  • 独自ヘッダーは分類を文書に書く。リスト型か単一値かの定義がなければ、層ごとに違う解釈をするのが当然である
  • 行数をログに残す。値だけを出すログは、二行来たという事実そのものを記録できない。名前と行数を一緒に残せば事後追跡が可能になる
  • クッキーのフィールドは配列のまま最後まで運ぶ。応答をコピーしたり組み立て直したりするコードがあれば、その地点を特に確認する

8.3 点検リスト

  • ヘッダーを読むコードをすべて探し、文字列APIを使う箇所と配列APIを使う箇所に分けて書き出した
  • 認証・宛先・本文長のように判定に使うフィールドはすべて配列APIに変えた
  • 単一値フィールドが二行以上来たとき黙って通過しないことをテストで確認した
  • リスト型フィールドを読むとき行の配列とカンマ分割の両方を行った（片方だけだと個数を間違える）
  • クッキーのフィールドを文字列に変換するコードがない。ログ・テンプレート・応答のコピー地点をすべて確認した
  • 中継やコピーのコードがヘッダーを読んだ形のまま渡す
  • 独自ヘッダーの分類が文書に書かれており、前段と後段が同じ文書を見る
  • 重複が検知されたとき名前と行数がログに残る
  • 本番環境で使う各構成要素が重複フィールドをどう処理するかを直接測定して記録した（製品文書や推測ではなく）
  • ヘッダー名の大文字小文字は別の問題なのでそちらの点検も別に行った

# 重複ヘッダーの判断基準 — フィールド類型表と安全な読み取り

> 出典: braindetox.kr — 同じヘッダーが二度届いたら
> 根拠: Windows 10 / Node.js v22.16.0 / Python 3.13.3 での実行検証（生ソケットでバイトを直接送信）
> このファイルをそのままAIに貼り付けて「この基準でうちのヘッダー処理を点検して」と書けば使えます。
> ⚠ 下の「製品ごとの挙動」は必ずご自身の環境で実測してください。推測は禁物です。

## 1. フィールド類型別の判断表

| 類型 | 例 | 複数行の意味 | 読み方 | 結合してよいか |
|---|---|---|---|---|
| リスト型 | Accept, Accept-Encoding, Accept-Language, Cache-Control, Vary, Via, TE, Content-Encoding | リストの構成要素が増えた | 配列で全行を受け取り、各行をカンマで再分割 | よい（仕様どおり） |
| 単一値 | Host, Content-Length, Content-Type, Authorization, Location, Date, ETag, Retry-After | あってはならない状態 | 配列で受け取り行数を数え、1でなければ拒否 | だめ |
| 絶対に結合しない | Set-Cookie | 正常。項目が複数あるだけ | 配列専用のアクセサを使い、配列のまま保つ | 絶対にだめ（破壊される） |
| 独自ヘッダー | 自分で作った X- 系 | 定義した人が決めるべき | 定義を文書化し、両側が同じ定義を参照する | 決めたとおりに |

## 2. ランタイム挙動の対照（実測）

| API | 戻り値 | 重複が来たとき | 判定 |
|---|---|---|---|
| Node req.headers[name] | 文字列 | カンマ+空白で結合 / 単一値フィールドは最初の値のみ | 損失あり |
| Node req.headersDistinct[name] | 配列 | 行ごとに1項目 | 無損失 |
| Node req.rawHeaders | 平坦な配列 | 名前と値の対、順序と表記を保持 | 無損失 |
| Headers.get(name) | 文字列 | カンマ+空白で結合（クッキーも結合される） | 損失あり |
| Headers.getSetCookie() | 配列 | 行ごとに1項目 | 無損失（クッキー専用） |
| Python headers.get(name) | 文字列 | 最初の行のみ、残りは破棄 | 損失あり |
| Python headers.get_all(name) | リスト | 行ごとに1項目 | 無損失 |

## 3. 実測まとめ

- 同一のリクエストバイト、二つのランタイム: 一方は二行を結合し、他方は最初の行だけを返した。どちらもエラーなし
- リスト型3種（Accept / Cache-Control / Accept-Encoding）: 二行 = 一行カンマ。意味が同一であることを確認
- Set-Cookie 2件をカンマ結合して再分割: 断片が4つ（有効期限のカンマがクッキーを真っ二つにする）
- 有効期限属性のない単純なクッキー2件を結合: 保存されたクッキーは1件。二つ目が一つ目の属性として吸収された
- Host 2行: 両ランタイムとも200、文字列APIは最初の値。配列APIには両方が残っている
- Content-Length 2行: 一方のランタイムは値が同じでもパーサ段階で400、他方は4ケースすべて200
- 結合された文字列からは元の行数を復元できない（二行と一行+カンマが同じ文字列になる）
- 自作中継1ホップ: 文字列APIで読むと2行が1行に、配列APIで読むと2行のまま

## 4. 安全な読み取り（JavaScript）

```js
// リスト型: 2段階（行の配列 -> 各行をカンマで分割）
function readList(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  return lines.flatMap(v => v.split(',').map(s => s.trim())).filter(Boolean);
}

// 単一値: 行が一つでなければ拒否する
function readSingleton(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  if (lines.length === 0) return { ok: true, value: null };
  if (lines.length > 1)   return { ok: false, reason: 'arrived ' + lines.length + ' times', lines };
  if (lines[0].includes(',')) return { ok: false, reason: 'comma inside a singleton', lines };
  return { ok: true, value: lines[0] };
}

// 絶対に結合しない: 配列のまま保つ
function readCookies(distinct) {
  return (distinct['set-cookie'] || []).slice();
}
```

- [ ] ヘッダーを読む箇所をすべて洗い出し、**文字列API / 配列API** に分類した
- [ ] 認証・宛先・本文長など **判断に使うフィールド** はすべて配列APIで読む
- [ ] 単一値フィールドが2行以上来たとき **黙って通過しない**（テストで確認済み）
- [ ] リスト型は **行の配列 + カンマ分割の2段階** で読む（片方だけだと件数を誤る）
- [ ] **Set-Cookie を文字列に変換するコードがない**（ログ・テンプレート・応答の複製をすべて確認）
- [ ] 中継や複製のコードがヘッダーを **読んだ形のまま** 渡す
- [ ] 独自ヘッダーの **類型が文書に書かれ**、前段と後段が同じ文書を参照している
- [ ] 重複を検知したとき **フィールド名と行数** がログに残る
- [ ] 正規化は **最も外側の境界で一度だけ**、内側では再判定しない
- [ ] 本番構成要素ごとの重複処理の挙動を **実測して記録** した（文書や推測ではなく）

## 7. やってはいけないこと

- ❌ すべてのヘッダーに一律でカンマ分割をかけるユーティリティ — 値の中のカンマを切ってしまう
- ❌ Set-Cookie を文字列として連結 — クッキーが断片化するか丸ごと消える
- ❌ 単一値フィールドで黙って最初の値を採用 — 層ごとに違う値を見る余地を作る
- ❌ 「うちの前段はヘッダーに触らない」という前提 — 値を変えなくても行構造は変わる
- ❌ リスト型での並べ替えや重複除去 — 到着順序が解釈に意味を持つ
- ❌ 製品文書だけを読んで挙動を断定 — バージョンと設定で変わる。実測せよ
- ❌ 値だけを残すログ — 二行来たという事実そのものが記録されない

コピーしてメモアプリやAIツールにそのまま貼り付けてください。

よくある質問

重複ヘッダーそのものを防げばよいのでは

防げないし防ぐ理由もない。リスト型フィールドでは複数行が正常な表現であり、クッキーのフィールドはむしろ複数行が基本である。全面的な遮断は正常なリクエストを壊す。必要なのは遮断ではなくフィールドごとに違う処理だ。8節の三分類がその出発点になる。

配列APIに変えるとコードが複雑にならないか

すべての箇所を変える必要はない。判定に使うフィールドだけ変えればよい。ログに出したり画面に見せたりする用途なら文字列APIでも十分だ。一方、認証、宛先の決定、本文長、アクセス制御のようにその値で分岐する場所では必ず行数を併せて見なければならない。実務でこうした場所はたいてい数えるほどしかない。

順序をソートしたり重複を除いたりしてよいか

リスト型フィールドではだめだ。RFC 9110の5.3節が、同じ名前のフィールドラインが受信された順序が解釈にとって有意であると明記し、中継者が転送の際その順序を変えてはならないと規定している。選好度や優先順位を担うフィールドでソートは意味を変える行為である。集合にして重複をなくすのも同じ理由で危険だ。

製品文書に書かれた挙動を信じてよいか

出発点としては使えるが結論には使えない。この記事で確かめたものだけを見ても、同じリクエストが一方のランタイムでは400で他方では200だった。バージョンと設定によっても変わる。だから勧めるのは、この記事の方法をそのまま使うことだ。生ソケットでバイトを直接書き込み、受け取った側で配列APIを使って行数を数えてみてほしい。二十行あれば足りる。

この記事の結果を自社のインフラにそのまま適用してよいか

だめだ。この記事の数値は明記した二つのランタイムの特定バージョンで測定したものであり、他の製品や他のバージョンを代表しない。特に7節の中継はこの記事のために自分で書いた二十行の実装なので、いかなる商用製品の挙動とも無関係である。持ち帰るべきは数値ではなく方法と分類だ。皆さんの構成要素について同じ測定を行い、8節の表に皆さんの結果を書き入れればよい。
