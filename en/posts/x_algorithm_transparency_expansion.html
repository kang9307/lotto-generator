Introduction: the distance between published and knowable

Two posts from the same account, written with the same care. One sinks without a sound, the other is still pushing notifications on day three. Ask why and there is no answer. That is why news of a recommendation algorithm repository opening always triggers the same hope. Now we will finally know.

That hope mostly goes unmet. You can read the code end to end and still not learn why your post did not spread. Not because the code is thin, but because the answer to that question was never in the code. Most of it is scattered across the parameters of a trained model, the data that model learned from, the experiment configuration running at that instant, and the state values attached to an account.

In August 2026 the X recommendation algorithm repository went through a substantial expansion. The weight values actually used in ranking arrived, along with the rules that decide whether a post is shown at all. That is meaningfully deeper than earlier disclosures. So how much more is verifiable now, and what remains out of reach? This article draws that line.

What it does not do is worth stating up front. There are no reach-boosting tactics here. The moment behaviour is engineered against a published objective function, that metric stops measuring what it was built to measure, and section 6 explains that structure. There is no political assessment of any company or person either. The subject is the structure of algorithm disclosure as an act, and it splits into the same layers on every platform.

1. What landed in the repository

The publication channel is the xai-org/x-algorithm repository, licensed under the Apache License 2.0. Two lines in the README changelog describe the scope of this expansion exactly.

  • 13 August 2026 — key configuration parameters, filtering systems and the Phoenix model code added
  • 14 August 2026 — an explanation of how the weights work, plus a filter relating to the 2026 Brazil election

The components are split by role, and the names alone sketch the shape of the pipeline.

  • home-mixer/ — builds the feed and scores it. The ranking weights live here
  • thunder/ — in-network posts, meaning candidates from accounts you follow
  • phoenix/ — out-of-network retrieval and ranking model, the path that pulls in material you do not follow
  • simclusters/ — cluster-based candidate discovery
  • visibility-filtering/ — decides whether a post is shown to a viewer

Around those sit the content understanding modules (grox/, media-model-proxy/, clip/, agatha/, user-cred-v2/, adult-content/, pnsfwmedia/ among others) and a separate labelling and enforcement family (scarecrow/, botmaker/, botmaker-rules/, abuse-enforcement-service/, safety-label-user-agg/). That second group matters later.

1.1 This is not the 2023 release

A common reaction is that the X algorithm was already published years ago, but the current repository is a different artefact. The 2023 release, twitter/the-algorithm, carried an AGPL-3.0 licence and contained components including Light Ranker and Heavy Ranker, SimClusters, TwHIN, Real Graph, TweepCred, Navi and Product Mixer.

The change with the most practical bite is the licence. AGPL-3.0 is strong copyleft that extends source disclosure obligations to derivatives served over a network; Apache-2.0 is a permissive licence with a patent grant. If you intend to build anything from this code, that difference changes the outcome immediately. Disclosure scope and licensing are separate axes — a point covered on the model side in Kimi K3 Open Weights - Can You Actually Deploy a 2.8T-Parameter Model 2026, where the judgement structure is identical.

2. Disclosure comes in layers

The single phrase algorithm disclosure bundles together five things of entirely different character. Splitting them is the prerequisite for judging what actually opened.

LayerOpened this timeWhat it tells youWhat stays hidden
Source codeYesPipeline shape, which signals exist, where rules are evaluatedWhether this code matches the deployed build
Ranking weights and settingsYesThe relative weight each action carries in the scoreWhether values are overridden per experiment, and when they change
Trained model parametersNot confirmed—The thing that produces predicted probabilities: half the formula
Training dataNot confirmed—What was learned and which biases came with it
Runtime parametersPartialDefault values and the existence of the parametersLive A/B experiment configuration and feature flag state
Manual intervention recordsPartial onlyThe rule families and the kinds of decision they produceLabels actually applied to a given account or post, and their history

Read the table vertically and the pattern is stark. Everything that opened is structure; everything closed is state. Structure is written in code, state lives in databases and running processes. A code repository is a container for structure, so however diligently it is opened it never crosses into state.

With that distinction in hand, two common misreadings resolve. First, the expectation that open code means reproducible results does not hold, because reproduction needs state. Second, concluding that the release is therefore meaningless is equally wrong. Open structure lets you form precise questions. Not knowing what to ask and knowing exactly where to ask but lacking the data are very different positions.

3. The scoring formula and its weights

This is the most concrete part of the expansion. The final score multiplies a predicted probability for each action by a weight and sums the terms, and the repository points at both halves by file. Weights sit in home-mixer/params/param.rs, the arithmetic in home-mixer/scorers/ranking_scorer.rs.

score = Σ ( weight_i × P(action_i) )

The first thing to read is not any single number but the asymmetry. The heaviest positive signal is 20; one negative signal is -234, more than ten times larger. Set that beside a favourite at 0.5 and the design priority is unambiguous. Far more weight is placed on not showing a post to someone who will dislike it than on making people like it.

The second is the ordering inside the share family. Copy link is 20, direct message share is 5, generic share is 2. The further out the sharing travels, the heavier it counts. An action that costs effort and moves content somewhere else is treated as a stronger statement of preference than a single tap.

The third is the conditional boost on replies. A reply inside a mutual follow relationship carries a 15.0 boost. That puts relationship direction directly into the score, and it pulls some weight back toward the friend graph in a feed that had tilted toward the recommendation graph. How those two graphs diverged in the first place is set out in Anti-Social: Your Feed Is Now Ruled by Trends, Not Friends 2026.

The most common way to misread these numbers. The file comment states that the weights apply to predicted probabilities and are not multiplied directly by raw interaction counts. One report is not minus 234 points. The -234 multiplies the model's estimated probability of being reported. If that probability is 0.001, the actual contribution is -0.234. A weight is the exchange rate that converts a probability into a score, not a penalty table.

4. Why the weights still do not predict the outcome

The formula is public and so are the coefficients. The outcome still does not compute, for six separate reasons.

  • The predicted probability is closed. Weights are one term. The other, P(action), is the output of a trained model, and nothing in the code says what it infers or why. It is an equation with known coefficients and unknown variables
  • Candidate generation runs before ranking. thunder, phoenix and simclusters select candidates first. A post that is not selected never gets scored. Ranking low and never being a candidate are different events, yet from outside both look identical
  • The inputs are live. Engagement velocity right now, the relationship state between author and viewer, recent behaviour history — all of it moves by the minute. The code is fixed while the input flows
  • Experiments run concurrently. At any moment several configurations are being served in parallel. The same person can sit in a different arm today than yesterday, and that assignment is not observable from outside
  • Personalisation splits the result. Feed the same code a different person's history and you get a different order. That is the design goal, not a defect, which is why the singular phrase the algorithm's output does not really denote anything
  • Filtering can override ranking afterwards. A high score can still be withheld by a filter decision. Section 5 takes that up

Stack those six and prediction stops being a matter of degree and becomes a matter of kind. Why recommendation pipelines took this shape, and where generative models made them more opaque still, is written up separately in Putting a Generative Model Into Recommendations - What Changes and What Does Not 2026.

5. Visibility filtering happens on a different layer

As important as the ranking weights in this release is visibility-filtering/. The rules are collected in visibility-filtering/rules/registry.rs, and the decision has three outcomes.

  • ALLOW — show it as normal
  • INTERSTITIAL — show it behind a cover the viewer has to click through
  • DROP — do not show it

Ranking and filtering answer different questions. Ranking decides order; filtering decides existence. Treat them as one lump and diagnosis goes wrong from the first step. Being pushed down the order and being caught by a filter have different causes and different recovery paths, but the symptom visible from outside is the same quiet notification tab.

And what the filter decides on sits one layer further back. Its input is labels. The fact that the repository carries separate directories for producing, aggregating and applying labels means, read the other way, that labels themselves are data rather than code. Read the rule file and you learn which label leads to which handling. You do not learn which labels are on your account right now. Rules are publishable structure; labels are per-account state.

That gap is the one that stings in practice. What a creator with falling reach needs is the label state on their own account, and the direction of disclosure points precisely the other way.

6. Why not open everything: the manipulation trade-off

The repository states plainly that some files are not published. The two examples it gives are the specific LLM prompt files used in Grox and some botmaker rules.

Why those two makes sense once you look at their character. Rules that catch spam and automated accounts are information that becomes a circumvention design the moment it is known. Learn which pattern trips the wire and you route around that pattern. In integrity defence, keeping rules closed is not laziness; it is part of the function.

On the other side stands Goodhart's law. A measure ceases to be a good measure once it becomes a target. Publish the objective function and optimisation aimed at that function follows, pulling the function away from what it was meant to capture — whether people genuinely value what they are shown. That risk attaches to weight disclosure too.

In this case, though, the risk is comparatively small, and the reason is the structure from section 3. Weights are coefficients applied to probabilities, and the model producing those probabilities is closed. Knowing that copy-link sharing is worth 20 does not hand you a method for raising that probability. Imitating a form and shifting a model's prediction are different tasks. On top of that, in a design where negative signals run to -234, pushing in a provocative direction invites a large self-inflicted penalty.

The trade-off that has emerged looks like this.

  • Open the objective function. Stating what the system counts as good is what makes explanatory accountability possible, and the manipulation risk there is cushioned by the closed model
  • Keep the defensive rules shut. Opening them makes evasion cheap, and that cost lands on the users who follow the rules
  • Model and data stay out of scope. There is little incentive to open them and no external infrastructure ready to verify them if opened

This trade-off is not one company's choice but a structure anyone operating a recommender system runs into. Open everything and the integrity systems are neutralised; close everything and verification becomes impossible. So the argument is never whether to disclose but which layer to disclose. The same shape of conflict played out on the model side in The Open-Weight AI Regulation Debate - Open vs Closed, Who Is Protecting What 2026.

7. What regulation asks for, at the level of the text

What the rules demand points in a noticeably different direction from code disclosure. The confirmed scope here is three articles of the EU Digital Services Act, Regulation (EU) 2022/2065.

  • Article 27, recommender system transparency. Online platforms using recommender systems must set out the main parameters in their terms and conditions, in plain and intelligible language. At minimum this covers (a) the criteria most significant in determining what is suggested and (b) the reasons for the relative importance of those parameters. Where several options exist, a functionality letting the recipient select and modify their preference at any time must be directly and easily accessible from the interface section where content is being prioritised
  • Article 38, recommender systems. Very large online platforms and very large online search engines must provide at least one option per recommender system that is not based on profiling, with profiling as defined in Article 4(4) of the GDPR
  • Article 40, data access and scrutiny. Vetted researchers gain data access. The conditions include affiliation to a research organisation, independence from commercial interests, disclosure of funding sources, capacity to meet data security and confidentiality requirements, demonstration that access is necessary and proportionate, and agreement to publish results free of charge. The Digital Services Coordinator grants the status and issues the access requests, and the purpose is limited to detecting, identifying and understanding systemic risks in the Union and assessing the adequacy of risk mitigation measures

Line the three up and the target becomes clear. Nowhere is there a requirement to publish source code. What is required is explanation (27), choice (27 and 38) and supervised data access (40). The regulatory axis runs through an explanation a user can read and data a researcher can check, not through code.

Publishing a repository therefore does not automatically satisfy those duties. Article 27 asks for plain language inside terms and conditions, and a Rust source file is not that format. Conversely, a platform that satisfies Article 27 has not thereby opened any code. The two axes run in parallel without overlapping.

This is not legal advice. The summary above is a reading of the provisions as of August 2026. Which duties apply to a given service, and whether it is designated as a very large platform, are not addressed here. Actual compliance judgement requires review by a qualified professional.

8. Users and creators: what you can and cannot answer

Here is what the published material actually settles, sorted by question.

QuestionAnswerableBasis
Which actions are counted as signalsYesThe parameter list is the list of counted actions
How heavy the negative signals areYesReport at -234, mute at -58.8 and the rest are published
How many ways a visibility decision can goYesALLOW, INTERSTITIAL and DROP
Which routes gather feed candidatesYesIn-network, out-of-network and cluster-based paths are separate directories
Can I reproduce my post's scoreNoThe model producing predicted probabilities is not published
Which labels are on my accountNoLabels are per-account state, not code
Why my reach droppedNoCandidate loss, rank decline and filter decisions are indistinguishable from outside
Which experiment arm I am inNoExperiment assignment is not observable
Whether the published code is what runsNoThere is no means of confirming parity with the deployed build

The line dividing the top of that table from the bottom is exactly the structure and state split from section 2. If the question is about structure there is an answer; if it is about state there is not. No exceptions.

So what a creator gains from this release is less a tactic than a recalibration of expectations. A few points worth naming.

  • The claim that the algorithm dislikes me can neither be verified nor refuted. Candidate generation, ranking, filtering, experiments and personalisation are all tangled in a single outcome, which cannot be attributed to one cause
  • Courting negative signals is arithmetically a losing trade. If a provocative post gains replies while raising mute and report probabilities at the same time, the asymmetry in the weights makes that exchange unfavourable
  • Platform metrics are only valid inside the platform. Search and recommendation have different objective functions, and the illusion created by measuring social performance with search tooling is covered in Social Arrives in Search Console - What Platform Properties Show and What They Never Will 2026
  • Published values are point-in-time values. The repository changed within two days. If a number is going to anchor a judgement, record the date you checked it

9. What external verification would need

What would a researcher need to confirm from outside that a system works as described? The starting move is to give up on reproduction. Reproduction requires code, trained parameters, training data, serving infrastructure and the real-time signals of that moment. Missing any one is fatal, and in practice only the first exists.

Three routes remain.

  • Deployment attestation. A way to confirm externally that the published code matches what is running. Without it every other check rests on an assumption. Almost no platform has answered this, and from where this article sits it is the widest open gap
  • Data access. Outcome-side data such as exposure logs, filter application records and experiment assignment history. The vetted researcher route in Article 40 aims here, though its scope is confined to systemic risk in the Union and cannot carry every research question
  • Outcome-based auditing. Measuring exposure distributions across account groups held under controlled conditions. It reads no code at all, yet it lands closer to conclusions about what users actually experience

The third deserves emphasis. Publishing code does not replace auditing. What it does is make the audit hypotheses precise. Knowing the weight on a negative signal lets you design a measurement aimed at how that signal shows up in real exposure. Open structure gives you not answers but better questions — and that is mostly where the value of this release sits.

10. What I could not confirm

Items with no clear answer, gathered in one place rather than hedged through the body.

  • Whether trained model checkpoints are included. The changelog records that model code including Phoenix was added, but whether trained neural network parameter files ship alongside it is unconfirmed
  • The nature and scale of the training data. No documentation on what the models learned from was confirmed
  • Per-experiment weight overrides. Whether the published values are defaults, currently applied globally, or overridden in experiment arms is unconfirmed
  • The content of the Brazil election filter. It is named in the 14 August changelog entry, but the rule content itself was not confirmed
  • Account label visibility for users. The topic source mentions a pilot letting users see labels applied to their account, but this was not confirmed directly in repository documentation
  • The full list of unpublished files. The statement that some files are withheld and two examples are confirmed, but no complete list is given
  • Equivalent duties outside the EU. Whether other jurisdictions impose an Article 27-style parameter disclosure duty is outside the scope confirmed here

The second-to-last item is structurally interesting. That the list of withheld files is itself withheld follows the same logic as section 6. Stating exactly what you hid is itself information. Call it the recursive limit of transparency; no platform resolves it cleanly.

Conclusion: structure opened, state did not

Three sentences. What opened is the shape of the pipeline, the coefficients of the objective function and the rules of the visibility decision. What stays closed is the model that produces predictions, its training data, the experiment configuration currently running, and the labels attached to individual accounts. The former is written in code and the latter lives in data, so however diligently a repository is opened, it never crosses to the second group.

That does not make the release worthless. Open structure sharpens questions, and sharp questions turn into audit designs. It is the same reason regulation asks for explanation and data access rather than code. Verification happens by measuring outcomes, not by reading source. Publishing code is the map that tells you where to point the measurement; it is not the measurement.

Two things are enough to keep. First, when you hear that an algorithm has been published, ask which of the five layers. Most of the hype and most of the disappointment resolve on that one question. Second, when reach falls, do not look for the answer in the code. The answer is in state, and state is not what gets published. Hold those two and you can size up the next disclosure, on any platform, for yourself.
