はじめに - 一つのフィールドを直しただけで他の値まで消える

プロフィールのbioだけを変えるために{"bio":"new"}をPATCHで送ったのに、レスポンスからnameとnicknameが消えている。サーバーのコードはありふれたbody.get(...)にすぎない。この事故の根はサーバーが「キーがない」と「値がnullである」を同じ状態として読んだ点にある。JSON文書では二つの状態は文字が違う。片方には"x":nullと書かれ、もう片方にはxという名前自体がない。ところが言語の読み取りAPIは、両者に同じ値を返す既定動作を持つことが多い。

用語を先に決める。「null」はJSONリテラルのnullである。「キーなし」はオブジェクトにその名前のメンバーがない状態である。undefinedはJavaScriptの値でありJSONの文法にはない。三つの表現は{"x":null}、{}、そしてJavaScriptで{x: undefined}を直列化した結果である。以下ではこの三つをPython・Node・PowerShellがどう読み書きするかを出力で示し、PATCHでどの状態変化になるかをローカルのサーバーへ実際にリクエストを送って確かめる。

扱う問いは次のとおりである。

  • JSONの文法とRFC 7396はnullとキーなしをそれぞれどう定義しているか。
  • Pythonのdict.get、Nodeのd.x、PowerShellの$o.xは二つの状態を区別するか。
  • 区別できないgetパターンがPATCHで値を消す過程はどう再現されるか。
  • 区別できる安全なパターンは何で、出力はどう変わるか。
  • 直列化の段階でキーが消えるのはどのツールのどの値か。

文書が定めていること - JSON文法・Merge Patch・言語ドキュメント

根拠となる文を先に集める。以下のリストの英文は原文そのままである。

  • RFC 8259 3節: A JSON value MUST be an object, array, number, or string, or one of the following three literal names: false, null, true. 値の一覧にundefinedはない。
  • RFC 8259 4節: The names within an object SHOULD be unique. オブジェクトは名前と値の組であり、名前のないメンバーはオブジェクトの中に存在しない。
  • RFC 7396 概要: Null values in the merge patch are given special meaning to indicate the removal of existing values in the target. パッチ内のnullは値ではなく削除の指示である。
  • RFC 7396 1節: ...do not make use of explicit null values. The merge patch format is not appropriate for all JSON syntaxes. 文書がnullを値として使う場合にはこの形式が合わないと、RFC自身が書いている。
  • Pythonドキュメントのdict.get: If default is not given, it defaults to None, so that this method never raises a KeyError. 戻り値だけでは、キーがない場合と値がNoneのキーを分けられない。
  • MDNのin演算子: A property may be present in an object but have value undefined. Therefore, "x" in obj is not the same as obj.x !== undefined.

RFC 7396の疑似コード（2節）は一行に要約できる。パッチのメンバーの値がnullなら、対象にその名前があるときに削除し、nullでなければ値を再帰的にマージする。パッチに名前がないメンバーは処理の対象にならないので、対象にそのまま残る。「nullは削除、キーなしは変更なし」という区別がこの形式のすべてであり、サーバーが二つの状態を区別できなければ形式そのものが成り立たない。

Python - getの既定値はキーがないときだけ使われる

import json
                    
                    for text in ['{"x": null}', '{}']:
                        d = json.loads(text)
                        print(text.ljust(11), '| repr:', repr(d), '| get("x"):', repr(d.get('x')),
                              '| get("x", 0):', repr(d.get('x', 0)), '| "x" in d:', 'x' in d)
                    
                    # Python has no undefined; None is serialized as null and the key stays
                    print(json.dumps({'x': None}), json.dumps({}))
                    
                    MISSING = object()  # sentinel: a value no JSON document can contain
                    
                    def classify(d, key):
                        v = d.get(key, MISSING)
                        if v is MISSING:
                            return 'missing'
                        return 'null' if v is None else 'value'
                    
                    for text in ['{"x": null}', '{}', '{"x": 0}', '{"x": ""}']:
                        print(text.ljust(11), '->', classify(json.loads(text), 'x'))

{"x": null} | repr: {'x': None} | get("x"): None | get("x", 0): None | "x" in d: True
                    {}          | repr: {} | get("x"): None | get("x", 0): 0 | "x" in d: False

d.get("x")は二つの文書でどちらもNoneである。区別は既定値の引数に現れる。d.get("x", 0)はキーがないときだけ0を返し、値がnullのキーではNoneをそのまま返す。既定値は「キーがないとき」の値であり、「値が空のとき」の値ではない。"x" in dはキーの有無だけに答えるので、二つの文書でTrueとFalseに分かれる。

json.dumps({"x": None})は{"x": null}を作る。Pythonにはundefinedがないので、空を表す表現は常にNoneであり、直列化してもキーはnullとして残る。キーなしを作るには、辞書にそのキーを入れないか削除する必要がある。センチネルMISSING = object()を既定値に使うclassifyは、四つの入力をnull・missing・value・valueに分ける。空文字列と0はnullではなく値である。

JSON.parseが作ったオブジェクトでは、{"x": null}のd.xはnull、{}のd.xはundefinedである。つまりNodeは読み取りの時点で二つの状態を値として区別する。d.x === undefinedがキーなしを、d.x === nullがnullを分ける。inとObject.hasOwnはキー自体の存在に答え、二つの文書でtrueとfalseに分かれる。

区別が消えるのは既定値の構文である。分割代入の既定値{ x = "DEFAULT" }はundefinedのときだけ働くので、{}と{x: undefined}ではDEFAULTを、{x: null}ではnullを返す。逆に??はnullとundefinedの両方を既定値に置き換え、二つの状態を一つにまとめる。同じ「既定値」という名前の構文でも、片方は区別し、片方は合流させる。

PATCHエンドポイント - RFC 7396の意味を実装した127.0.0.1サーバー

一つのサーバーに三つの処理系を置く。/naiveはbody.getがNoneならフィールドを削除し、/skipnullはNoneなら飛ばし、/mergeはRFC 7396の疑似コードをそのまま移したmerge_patchを使う。状態はメモリ上の辞書で、POST /resetで戻す。ファイルはすべて一時フォルダの中だけに作り、ソケットはループバック（127.0.0.1）だけに開き、180秒で自分から終了する安全装置を入れた。

import json, os, sys, threading
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    INITIAL = {'name': 'kim', 'nickname': 'kk', 'bio': 'hello'}
                    FIELDS = ['name', 'nickname', 'bio']
                    STATE = {'naive': dict(INITIAL), 'skipnull': dict(INITIAL), 'merge': dict(INITIAL)}
                    
                    
                    def apply_naive(user, body):
                        # get() returns None for a missing key and for an explicit null alike
                        for k in FIELDS:
                            v = body.get(k)
                            if v is None:
                                user.pop(k, None)
                            else:
                                user[k] = v
                    
                    
                    def apply_skipnull(user, body):
                        for k in FIELDS:
                            v = body.get(k)
                            if v is not None:
                                user[k] = v
                    
                    
                    def merge_patch(target, patch):
                        # the MergePatch pseudo-code of RFC 7396 section 2
                        if isinstance(patch, dict):
                            if not isinstance(target, dict):
                                target = {}
                            for name, value in patch.items():
                                if value is None:
                                    if name in target:
                                        del target[name]
                                else:
                                    target[name] = merge_patch(target.get(name), value)
                            return target
                        return patch
                    
                    
                    class H(BaseHTTPRequestHandler):
                        def log_message(self, *a):
                            pass
                    
                        def _send(self, code, obj):
                            raw = json.dumps(obj, sort_keys=True).encode()
                            self.send_response(code)
                            self.send_header('Content-Type', 'application/json')
                            self.send_header('Content-Length', str(len(raw)))
                            self.end_headers()
                            self.wfile.write(raw)
                    
                        def _which(self):
                            first = self.path.strip('/').split('/')[0]
                            return first if first in STATE else None
                    
                        def do_GET(self):
                            w = self._which()
                            self._send(200, STATE[w]) if w else self._send(404, {'error': 'unknown path'})
                    
                        def do_POST(self):
                            if self.path != '/reset':
                                return self._send(404, {'error': 'unknown path'})
                            for k in STATE:
                                STATE[k] = dict(INITIAL)
                            self._send(200, {'reset': True})
                    
                        def do_PATCH(self):
                            w = self._which()
                            if w is None:
                                return self._send(404, {'error': 'unknown path'})
                            body = json.loads(self.rfile.read(int(self.headers.get('Content-Length', 0))))
                            if w == 'naive':
                                apply_naive(STATE[w], body)
                            elif w == 'skipnull':
                                apply_skipnull(STATE[w], body)
                            else:
                                STATE[w] = merge_patch(STATE[w], body)
                            self._send(200, STATE[w])
                    
                    
                    if __name__ == '__main__':
                        srv = HTTPServer(('127.0.0.1', int(sys.argv[1])), H)  # loopback only
                        print('pid', os.getpid(), 'listening on 127.0.0.1:' + sys.argv[1], flush=True)
                        t = threading.Timer(180, lambda: os._exit(0))  # safety: exit by itself after 180 s
                        t.daemon = True
                        t.start()
                        srv.serve_forever()

クライアントはcurlである。同じ三つのリクエストを三つの処理系へ順に送る。リクエストは、フィールド一つだけを変える{"bio":"new"}、フィールド一つを削除する{"nickname":null}、何も変えない{}である。リクエストごとに状態を初期値（name=kim、nickname=kk、bio=hello）に戻す。

/naiveに{"bio":"new"}を送ると、レスポンスは{"bio": "new"}だけになる。リクエストになかったnameとnicknameが消えた。処理系はフィールド一覧を回してbody.get(k)を読むが、リクエストにない名前はNoneになり、Noneは削除として扱われるからである。この結果は上のコードと出力が直接示している。{}を送ってもレスポンスは{}である。何も変えないリクエストがすべてのフィールドを消す。

/skipnullは逆側の誤りを示す。キーなしには安全だが、{"nickname":null}を送ってもnicknameがkkのまま残る。削除の要求が黙って無視される。三つのリクエストすべてで意図どおりに動くのは/mergeだけである。bioだけが変わり、nicknameだけが消え、{}は何も変えない。入れ子のオブジェクトでも{"extra":{"a":null,"b":2}}はextraの中のaだけを消す。

{"nickname":null}すべてのフィールドが削除nickname維持（無視）nicknameだけ削除
{}すべてのフィールドが削除変更なし変更なし

区別する安全なパターン - センチネル・in・オブジェクトの展開

前節のmerge_patchはname in targetとfor name, value in patch.items()で区別する。パッチオブジェクトを名前ごとに回すとリクエストにあるキーだけを訪れるので、ないキーには触れられない。規則は一つである。キーの存在はin（または反復）で尋ね、値がnullかどうかはその後で尋ねる。存在を値から推定しない。

センチネルは、既定値の位置にJSONが作れない値を置く方式である。Pythonのobject()はどのJSON文書からも出てこないので、d.get(key, MISSING)の戻りがMISSINGならキーなしである。オブジェクトの既定値は展開構文に現れる。以下は既定値オブジェクトの上にリクエスト本文を重ねるコードと出力で、Pythonの{**defaults, **body}も同じ方式である。

const defaults = { name: 'kim', nickname: 'kk' };
                    console.log(JSON.stringify({ ...defaults, ...JSON.parse('{}') }));
                    console.log(JSON.stringify({ ...defaults, ...JSON.parse('{"nickname": null}') }));
                    const undef = { ...defaults, ...{ nickname: undefined } };
                    console.log(undef, 'nickname' in undef, JSON.stringify(undef));
{"name":"kim","nickname":"kk"}
                    {"name":"kim","nickname":null}
                    { name: 'kim', nickname: undefined } true {"name":"kim"}
import json
                    defaults = {'name': 'kim', 'nickname': 'kk'}
                    print({**defaults, **json.loads('{}')})
                    print({**defaults, **json.loads('{"nickname": null}')})
                    print(json.dumps({**defaults, **{'nickname': None}}))
{'name': 'kim', 'nickname': 'kk'}
                    {'name': 'kim', 'nickname': None}
                    {"name": "kim", "nickname": null}

{}を重ねると既定値がそのまま残り、{"nickname": null}を重ねるとnicknameがnullに変わる。区別は保たれる。ところがJavaScriptで{nickname: undefined}を重ねると、既定値のkkがundefinedで上書きされ、直列化するとnickname自体が消えて{"name":"kim"}だけが残る。展開はキーの存在を基準に上書きするからである。この動作はinがtrueを出力した行が示している。

  • センチネル: get(key, MISSING)のように、JSONが作れない値を既定値に置く。
  • in・Object.hasOwn・プロパティ一覧: 値を読む前にキーの存在を先に尋ねる。
  • パッチオブジェクトの反復: リクエストにある名前だけを訪れるので、ない名前は変更の対象にならない。
  • オブジェクトの既定値と展開: キーがなければ既定値が残るが、JavaScriptのundefined値はキーがあるものとして上書きする。

                    { x: undefined } [ 'x' ] {}

MDNのJSON.stringifyのドキュメントはこう書いている。undefined, Function, and Symbol values are not valid JSON values. If any such values are encountered during conversion, they are either omitted (when found in an object) or changed to null (when found in an array). 出力はこれをそのまま示している。オブジェクトのx: undefinedはキーごと消え、配列のundefinedと関数はnullになる。最上位のundefinedはJSONテキストではなく値undefinedを返す。最後の行のObject.assignの結果はキーが残った{ x: undefined }だが、直列化は{}である。

この違いがPATCHでどんな状態変化になるかは、三つのツールが作った本文を同じサーバーの/mergeにそのまま送って確かめる。三つのツールとも「nicknameを空にする」という同じ意図でコードを書いた。

B=http://127.0.0.1:18765
                    send() {
                      printf '%-10s body=%-20s -> ' "$1" "$2"
                      curl -s -X PATCH -H 'Content-Type: application/merge-patch+json' -d "$2" "$B/merge"
                      echo
                    }
                    reset() { curl -s -X POST "$B/reset" > /dev/null; }
                    
                    js=$(node -e "console.log(JSON.stringify({nickname: undefined}))")
                    py=$(python -c "import json; print(json.dumps({'nickname': None}))")
                    ps=$(powershell -NoProfile -Command "[pscustomobject]@{ nickname = \$null } | ConvertTo-Json -Compress")
                    reset; send node "$js"
                    reset; send python "$py"
                    reset; send powershell "$ps"
node       body={}                   -> {"bio": "hello", "name": "kim", "nickname": "kk"}
                    python     body={"nickname": null}   -> {"bio": "hello", "name": "kim"}
                    powershell body={"nickname":null}    -> {"bio": "hello", "name": "kim"}

Nodeの{nickname: undefined}は本文が{}になり、状態はそのままである。削除するはずのリクエストが何もしなかった。Pythonの{"nickname": None}とPowerShellの$nullプロパティは、本文に"nickname":nullが載って削除される。同じ意図のコードがツールによって「消せない」と「消える」に分かれる。

症状から原因へ - 点検の順序と隣接する記事

前の出力から症状と原因の対応が得られる。点検は症状ごとに一段ずつ絞り込む。

  • フィールドを一つ変えただけで他が消える: サーバーの処理系がgetのNoneを削除に使っていないかを見る（/naiveの症状）。
  • 値を空にする要求が無視される: nullが飛ばし扱いになっていないかを見る（/skipnullの症状）。
  • JavaScriptクライアントの削除リクエストがサーバーで何もしない: 本文にundefinedが入っていないか、JSON.stringifyの結果にキーがあるかを見る。
  • nullを値として保存すべきフィールドがある: RFC 7396の疑似コードではnullは常に削除なので、そのフィールドはMerge Patchでは表現できない。別の形式かフィールド単位の明示的な値を使う。
  • 配列の一部だけを変えたい: 疑似コードではオブジェクトでないパッチは対象全体を置き換えるので、配列は丸ごと送る。

周辺の話題は別の記事で扱う。同じ名前が二度出る文書をパーサーごとにどう読むかはJSON重複キーの記事に、大きな整数がJSONを通ると変わる問題はJSON数値精度の記事にある。SQLのNULLが比較をどう変えるかはNOT INとNULLの記事が、JSONB列を部分更新する演算子はPostgreSQL JSONBの記事が扱う。デフォルト引数にNoneを見張り番として置く慣用句はPython可変デフォルト引数の記事につながる。この記事の範囲はJSON文書内のnullとキーなし、そしてPATCHの意味までである。

確認できなかったこと

  • Go・Java・Rustなど他言語のJSONライブラリが二つの状態をどう読むか。このPCで実行したのはPython・Node・PowerShell 5.1だけである。
  • PowerShell 7（pwsh）でConvertFrom-Jsonが二つの状態をどう読むか。このPCにはpwshがない。
  • RFC 6902（JSON Patch）との比較実行。本文で扱ったのはRFC 7396だけである。
  • PATCH本文がオブジェクトでない場合（配列・文字列）のサーバー動作。RFCの疑似コードは対象全体の置換と書くが、このサーバーの該当経路は実行していない。
  • 重複キーを含むPATCH本文、および大きな整数・小数を含む本文の処理。隣接する記事の話題である。
  • 運用中のWebフレームワーク（Django REST framework、Expressなど）がPATCH本文をどう解釈するか。実行したのは自作の小さなサーバーだけである。
  • LinuxやmacOSでの出力。この記事の出力はすべてWindows 10で得たものである。
