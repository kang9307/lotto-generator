서론: 루프는 제대로 돌았고, 답만 틀렸다

로그 파일을 훑어서 조건에 맞는 줄을 세는 스크립트를 짰다고 하자. 루프 안에 echo를 하나 넣어 보면 세 줄이 또박또박 찍힌다. 그런데 루프가 끝나고 합계를 출력하면 0이다.

이 시점에 대부분 루프 본문을 의심한다. 산술 확장이 잘못됐나, read가 빈 줄을 먹었나, 변수 이름에 오타가 났나. 전부 아니다. 루프는 정확하게 돌았고 카운터도 3까지 올라갔다. 다만 그 카운터가 살던 프로세스가 루프와 함께 없어졌을 뿐이다.

이 글은 그 프로세스가 언제 생기고 왜 값을 못 돌려주는지, 그리고 고치는 방법이 왜 루프 본문이 아니라 입력을 넣는 방식에 있는지를 실행 결과로 따라간다. 여기에 실린 명령과 출력은 GNU bash, version 5.2.37(1)-release와 dash에서 그대로 돌려 얻은 것이다. 셸 기본기가 아직이라면 쉘 스크립트 기초와 쉘 스크립트 고급을 먼저 보고 오면 읽기 편하다.

1. 카운터가 0으로 돌아오는 순간, 무슨 일이 있었나

재현부터 한다. 세 줄짜리 파일 하나면 충분하다.

$ printf 'a\nb\nc\n' > /tmp/f.txt

$ n=0
$ cat /tmp/f.txt | while read -r l; do n=$((n+1)); done
$ echo "after pipe: n=$n"
after pipe: n=0

이번엔 입력을 넣는 방식만 바꾼다. 루프 본문은 한 글자도 안 건드린다.

$ n=0
$ while read -r l; do n=$((n+1)); done < /tmp/f.txt
$ echo "after redirect: n=$n"
after redirect: n=3

같은 루프, 같은 파일, 같은 셸이다. 다른 건 |가 있느냐 하나다. 여기서 이미 결론이 나온다. 문제의 원인은 루프에 없다.

1.1 파이프는 데이터만 옮기는 게 아니다

파이프를 「명령 A의 출력을 명령 B의 입력으로 넣는 장치」로만 이해하면 이 현상이 설명되지 않는다. 파이프는 그것과 함께 프로세스를 하나 더 만든다. bash는 파이프라인의 각 구성 요소를 별도의 서브셸에서 실행한다.

서브셸은 부모 셸을 복제해서 만들어진다. 그래서 시작 시점에는 부모의 변수 값을 전부 그대로 가지고 있다. 문제는 그 반대 방향이다.

  • 부모의 값은 자식에게 복사된다. 그래서 루프 안에서 $n을 읽으면 0이 잘 보인다
  • 자식이 바꾼 값은 부모에게 돌아가지 않는다. 프로세스 사이에는 그런 통로가 없다
  • 파이프라인이 끝나면 자식 프로세스는 종료된다. 그 안에서 3까지 올라갔던 n은 그 순간 사라진다
  • 부모 셸에는 처음에 만든 n=0이 손대지 않은 채 남아 있다. 그래서 0이 출력된다
  • 즉 「값이 안 올라간」 게 아니라 「올라간 값을 볼 수 없는 자리에서 보고 있는」 것이다

이 현상을 검색할 때 쓸 말. 이건 변수 스코프 문제가 아니라 프로세스 경계 문제다. local이나 export로 해결하려는 시도가 전부 실패하는 이유가 여기 있다. export는 부모에서 자식으로 값을 내려보내는 장치지 자식에서 부모로 올려보내는 장치가 아니다.

2. 프로세스가 몇 개 생겼는지 눈으로 세는 법

추측 대신 세어 보면 된다. bash에는 딱 이 용도로 쓰는 변수가 두 개 있다.

  • $$ — 원래 셸의 PID다. 서브셸 안에서도 바뀌지 않는다. 그래서 서브셸 판별에는 못 쓴다
  • $BASHPID — 지금 이 코드를 실행 중인 프로세스의 실제 PID다. 서브셸에 들어가면 값이 달라진다

둘을 나란히 찍으면 서브셸이 어디서 생겼는지가 그대로 보인다.

$ echo "parent: \$\$=$$ BASHPID=$BASHPID"
parent: $$=1344 BASHPID=1344

$ ( echo "subshell( ): \$\$=$$ BASHPID=$BASHPID" )
subshell( ): $$=1344 BASHPID=1348

$ echo "cmdsub: $(echo "\$\$=$$ BASHPID=$BASHPID")"
cmdsub: $$=1344 BASHPID=1349

$$는 세 번 다 1344로 고정이고 BASHPID만 1344, 1348, 1349로 갈린다. 괄호와 명령 치환이 각각 새 프로세스를 만들었다는 증거다. 스크립트를 디버깅할 때 「여기가 서브셸인가?」가 궁금하면 echo $BASHPID 한 줄이면 끝난다.

PID 값 자체는 실행할 때마다 달라진다. 봐야 할 것은 숫자가 아니라 세 값이 서로 다른가다.

3. 리다이렉션 - 가장 싸고 가장 이식성 좋은 해결

입력이 실제 파일이면 답은 하나다. 파이프를 없애고 done 뒤에 리다이렉션을 붙인다.

# 값이 사라지는 쪽
cat /tmp/f.txt | while read -r l; do n=$((n+1)); done

# 값이 남는 쪽
while read -r l; do n=$((n+1)); done < /tmp/f.txt

이 형태가 좋은 이유를 정리하면 이렇다.

  • 루프가 현재 셸에서 돈다. 서브셸이 아예 안 만들어지므로 변수가 그대로 남는다
  • 프로세스를 하나 덜 만든다. cat 프로세스도 사라진다
  • bash 확장이 아니라 POSIX 문법이다. dash에서도 똑같이 3이 나온다
  • cat 파일 | 형태 자체가 대부분의 경우 불필요한 프로세스다. 이 패턴을 줄이는 습관은 서브셸 문제와 별개로도 이득이다
  • 리다이렉션 위치가 done 뒤라는 점이 처음엔 어색한데, 루프 전체가 하나의 복합 명령이고 그 복합 명령의 표준 입력을 바꾸는 것이라 생각하면 자연스럽다

파일이 여러 개라 cat a b c |를 쓰고 싶어지면, 그때는 리다이렉션 대신 다음 절의 프로세스 치환이 맞다.

4. 프로세스 치환 - 입력이 파일이 아닐 때

현실의 스크립트는 입력이 파일이 아닌 경우가 더 많다. find 결과, grep 결과, API 응답을 jq로 거른 것 같은 것들이다. 이때 쓰는 것이 프로세스 치환이다.

$ n=0
$ while read -r l; do n=$((n+1)); done < <(cat /tmp/f.txt)
$ echo "after procsub: n=$n"
after procsub: n=3

< <(...)는 오타처럼 보이지만 두 개의 다른 문법이 붙어 있는 것이다. <(cmd)가 명령의 출력을 파일처럼 보이게 만들고, 그 앞의 <가 그 가짜 파일을 표준 입력으로 연결한다. 사이에 공백이 반드시 있어야 한다.

4.1 왜 이건 되고 파이프는 안 되나

프로세스 치환에서도 cmd는 별도 프로세스에서 돈다. 차이는 루프가 어느 쪽에 있느냐다.

  • 파이프에서는 루프가 파이프라인의 구성 요소라서 서브셸로 밀려난다
  • 프로세스 치환에서는 루프가 현재 셸에 남고, 서브셸로 밀려나는 것은 데이터를 만드는 쪽이다
  • 데이터를 만드는 쪽은 변수를 안 바꾸므로 서브셸이어도 상관없다

4.2 파일명을 다룰 때 같이 붙는 문제

find 결과를 도는 루프에서 실제로 확인한 결과다. 빈 로그 파일 하나와 내용 있는 파일 하나를 두고 빈 파일 수를 셌다.

$ find logs -name '*.log' | while read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done
$ echo "find | while  -> empty=$empty"
find | while  -> empty=0

$ while IFS= read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done < <(find logs -name '*.log')
$ echo "procsub       -> empty=$empty"
procsub       -> empty=1

여기서 IFS=와 -r이 같이 붙은 이유를 짚어 둔다. 서브셸 문제와는 별개지만 같은 줄에서 터지는 결함이다.

  • IFS=를 안 주면 앞뒤 공백이 잘린다. 공백으로 시작하는 파일명이 조용히 달라진다
  • -r을 안 주면 역슬래시가 이스케이프로 해석된다. 윈도우에서 온 경로 문자열이 특히 위험하다
  • 파일명에 개행이 들어갈 수 있는 환경이라면 find ... -print0과 read -r -d ''를 짝으로 쓴다
  • 이 조합도 프로세스 치환 안에서 그대로 동작한다. 위 실행에서 -print0 버전도 같은 결과를 냈다

5. lastpipe가 먹는 조건과 안 먹는 조건

bash에는 파이프라인의 마지막 구성 요소를 현재 셸에서 실행하게 하는 옵션이 있다.

$ shopt lastpipe
lastpipe        off
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=0

$ shopt -s lastpipe
$ shopt lastpipe
lastpipe        on
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=3

여기까지만 보면 가장 간단한 해결처럼 보인다. 그런데 터미널에 그대로 쳐 보면 아무 일도 안 일어난다. 이유는 job control이다.

5.1 job control이 켜져 있으면 무시된다

스크립트 안에서 set -m으로 job control을 켜고 끄면서 같은 코드를 돌리면 이렇게 갈린다.

$ set -m          # job control ON (대화형 셸의 기본 상태)
$ shopt -s lastpipe
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control ON  -> n=$n"
job control ON  -> n=0

$ set +m          # job control OFF
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control OFF -> n=$n"
job control OFF -> n=3

대화형 셸은 job control을 기본으로 켜 둔다. 그래서 터미널에서 shopt -s lastpipe를 아무리 켜도 결과가 안 바뀐다. 옵션은 확실히 켜졌는데 동작만 안 하는, 디버깅하기 고약한 상태다.

5.2 그래서 lastpipe를 어디에 쓸 것인가

  • 배포하는 스크립트의 기본 해법으로는 권하지 않는다. 읽는 사람이 파일 맨 위의 shopt 한 줄과 백 줄 아래 루프를 연결해서 이해해야 한다
  • bash 전용이다. dash에는 이 옵션 자체가 없다
  • 기존 스크립트를 최소 수정으로 살려야 할 때는 유용하다. 파이프 구조를 그대로 두고 한 줄만 추가하면 된다
  • 「지금 이게 서브셸 때문인가」를 1분 안에 판정하는 용도로 좋다. 이 한 줄로 결과가 바뀌면 원인이 확정된다
  • 켤 때는 반드시 스크립트 안에서 켜고, 그 스크립트가 bash로 실행되는지 확인한다

6. 서브셸이 생기는 나머지 자리들

파이프만 조심하면 되는 게 아니다. 아래는 각각 직접 돌려 확인한 결과다.

구문서브셸변수 변경이 밖에 남나확인한 결과
cmd | while ...생긴다남지 않는다n=0
( k=2 )생긴다남지 않는다k=0
{ k=1; }생기지 않는다남는다k=1
$( ... )생긴다남지 않는다BASHPID가 달라짐
{ m=99; } &생긴다남지 않는다wait 후에도 m=0
while ... done < 파일생기지 않는다남는다n=3
while ... done < <(cmd)루프는 안 생긴다남는다n=3
for v in ...; do생기지 않는다남는다n=6

표에서 가장 헷갈리는 두 줄이 ( )와 { }다. 생김새가 비슷한데 성격이 정반대다.

6.1 괄호는 격리, 중괄호는 묶음

$ k=0; { k=1; };  echo "brace group: k=$k"
brace group: k=1
$ k=0; ( k=2 );   echo "paren subshell: k=$k"
paren subshell: k=0

이 차이가 오히려 도움이 되는 자리도 있다. 서브셸은 격리 장치이기도 하기 때문이다.

$ cd /tmp
$ echo "before: $PWD"
before: /tmp
$ ( cd / ; echo "inside: $PWD" )
inside: /
$ echo "after : $PWD"
after : /tmp

디렉터리를 잠깐 옮겨서 뭘 하고 원래 자리로 돌아와야 할 때, cd 후에 cd -로 되돌리는 대신 괄호로 감싸면 된다. 중간에 실패해서 빠져나가도 부모의 작업 디렉터리는 안 움직인다.

6.2 exit도 괄호 안에 갇힌다

$ ( exit 42 )
$ echo "parent still alive, subshell exit=$?"
parent still alive, subshell exit=42

이건 양쪽으로 다 물릴 수 있다. 정리 코드를 서브셸에 넣어 두면 그 안의 exit가 전체 스크립트를 죽이지 않아 안전하다. 반대로 「오류면 스크립트를 끝내라」는 의도로 넣은 exit 1이 괄호 안에 있으면 스크립트는 멀쩡히 계속 돈다. 후자가 훨씬 자주 사고를 낸다.

7. 값을 건져 오는 여섯 가지 방법과 각각의 대가

세 줄짜리 데이터로 여섯 방법을 전부 돌려 봤다. 데이터는 alpha 10, beta 20, gamma 30이고 목표는 합계 60이다.

방법문법결과대가 · 제약
리다이렉션done < 파일60입력이 실제 파일일 때만. POSIX sh 가능
프로세스 치환done < <(cmd)60bash 확장. POSIX sh에서 문법 오류
히어 스트링done <<< "$(cmd)"60출력 전체를 메모리에 올림. bash 확장
배열로 먼저 읽기mapfile -t a < 파일60bash 4 이상. 대용량이면 메모리 부담
출력을 캡처t=$(cmd | { ...; echo "$t"; })60값 하나만 나올 때 편함. 여러 값이면 파싱 필요
임시 파일 경유... > "$tmp" 후 읽기60가장 이식성 좋음. 정리 책임이 생김

7.1 실행 결과

$ total=0
$ while read -r name v; do total=$((total+v)); done <<< "$(cat /tmp/data.txt)"
$ echo "here-string total=$total"
here-string total=60

$ mapfile -t lines < /tmp/data.txt
$ echo "mapfile count=${#lines[@]} first=${lines[0]}"
mapfile count=3 first=alpha 10

$ total=$(cat /tmp/data.txt | { t=0; while read -r n v; do t=$((t+v)); done; echo "$t"; })
$ echo "captured total=$total"
captured total=60

마지막 방식이 흥미롭다. 서브셸을 없애는 대신 서브셸이 값을 밖으로 내보내는 유일한 통로인 표준 출력을 쓴다. 서브셸에서 변수는 못 나오지만 출력은 나온다.

7.2 고르는 기준

  • 입력이 파일이다 → 리다이렉션. 고민할 것 없다
  • 입력이 명령의 출력이고 bash를 쓴다 → 프로세스 치환
  • #!/bin/sh로 배포해야 한다 → 임시 파일이나 출력 캡처. 프로세스 치환은 못 쓴다
  • 줄 수가 수만 줄 이상이다 → 히어 스트링과 mapfile은 피한다. 전체를 메모리에 올린다
  • 루프에서 나와야 하는 값이 하나뿐이다 → 출력 캡처가 가장 짧다
  • 기존 스크립트를 최소로 고쳐야 한다 → lastpipe. 단 5절의 제약을 주석으로 남긴다

한 줄 요약. 서브셸에서 변수는 못 나오지만 표준 출력과 파일과 종료 상태는 나온다. 값을 건지는 모든 방법은 결국 이 셋 중 하나를 쓰거나, 아니면 서브셸을 애초에 안 만드는 쪽이다.

8. set -e가 파이프와 서브셸에서 어긋나는 지점

서브셸을 이해했으면 set -e가 왜 자주 배신하는지도 같이 풀린다. 실행 결과부터 본다.

$ set -e
$ printf 'a\nb\n' | grep -q zzz | cat
$ echo "survived"
survived

grep이 실패했는데 스크립트가 멈추지 않았다. 파이프라인의 종료 상태는 기본적으로 마지막 명령의 상태이기 때문이다. 마지막 cat이 성공했으니 파이프라인 전체가 성공으로 집계됐다.

8.1 PIPESTATUS로 어느 자리가 죽었는지 본다

$ false | true | false
$ echo "\$?=$? PIPESTATUS=(${PIPESTATUS[@]})"
$?=1 PIPESTATUS=(1 0 1)

배열의 순서가 파이프라인의 순서다. 세 자리 중 첫째와 셋째가 실패했다는 게 그대로 읽힌다. 주의할 점은 이 배열이 바로 다음 명령 하나만 지나도 덮어써진다는 것이다. 쓸 거면 즉시 다른 배열로 복사한다.

8.2 pipefail을 켜면 달라지는 것

$ ( set -e -o pipefail; printf 'a\n' | grep -q zzz | cat; echo "NOT REACHED" )
$ echo "with pipefail exit=$?"
with pipefail exit=1

$ ( set -e; printf 'a\n' | grep -q zzz | cat; echo "reached" )
reached
$ echo "without pipefail exit=$?"
without pipefail exit=0

pipefail이 켜지면 파이프 안 어느 자리든 0이 아닌 상태가 나올 때 파이프라인이 실패로 잡히고, 그제서야 set -e가 동작한다.

8.3 가장 조용한 함정

이건 따로 떼어 쓸 만하다. 서브셸이 ||의 왼쪽에 놓이면 그 안의 set -e가 통째로 무력화된다.

$ ( set -e; false; echo "NOT REACHED" ) || echo "caught"
NOT REACHED

NOT REACHED가 찍혔다. 「실패하면 잡으려고」 붙인 || 때문에 서브셸 전체가 조건 판정 문맥에 들어갔고, 그 안에서는 set -e가 꺼진다. 함수도 마찬가지다.

$ f() { set -e; false; echo "reached anyway"; }
$ f || true
reached anyway

「오류 검사를 붙였는데 오히려 오류 검사가 꺼졌다」는 상황이라 눈으로 찾기 어렵다. 정리하면 실무에서 쓸 규칙은 이렇다.

  • set -euo pipefail을 스크립트 맨 위에 두되 그것만 믿지 않는다
  • 중요한 파이프라인은 PIPESTATUS를 명시적으로 확인한다
  • || 무언가를 붙이는 순간 그 왼쪽의 set -e는 없는 것으로 본다
  • 서브셸의 성패를 확인하려면 ||로 잡지 말고, 실행한 뒤 $?를 별도 줄에서 검사한다
  • ( exit 7 )이 $?=7을 그대로 넘겨주는 것은 확인했다. 종료 상태 자체는 정상적으로 전파된다

9. 셸마다 갈리는 부분

같은 코드를 dash로 돌린 결과다.

$ dash t.sh
dash pipe: n=0
dash redirect: n=3

$ dash -c 'while read -r l; do echo "$l"; done < <(printf "x\ny\n")'
dash: 1: Syntax error: redirection unexpected
항목bash 5.2.37dashzsh · ksh
파이프 안 while의 카운터0 (확인함)0 (확인함)확인하지 못함
리다이렉션으로 해결3 (확인함)3 (확인함)확인하지 못함
프로세스 치환 <(...)동작문법 오류확인하지 못함
shopt -s lastpipe있음 (job control 조건부)없음확인하지 못함
PIPESTATUS있음없음확인하지 못함
mapfile있음없음확인하지 못함

여기서 나오는 실무 규칙은 단순하다.

  • 셔뱅이 #!/bin/sh인데 프로세스 치환을 썼다면 그 스크립트는 배포 환경에서 문법 오류로 죽는다. 개발 장비에서 /bin/sh가 bash로 심볼릭 링크된 경우 이게 안 보인다
  • bash 기능을 쓸 거면 셔뱅을 #!/usr/bin/env bash로 정확히 적는다
  • 이식성이 필요한 스크립트는 배포 대상 셸로 한 번은 실제로 돌려 본다. 이 글의 표를 만드는 데 든 시간은 몇 분이다
  • 컨테이너 이미지에 bash가 없는 경우가 흔하다. 최소 이미지의 기본 셸이 무엇인지 먼저 확인한다

10. 이런 걸 검증하는 스크립트를 쓸 때의 함정

위 결과들은 전부 파일로 저장해서 돌린 것이다. 한 줄짜리 검증이라도 -c 뒤에 코드를 통째로 밀어 넣는 방식은 피하는 편이 낫고, 이유가 두 가지다.

10.1 인용부호가 두 번 벗겨진다

인라인 방식은 문자열이 바깥 셸을 한 번, 안쪽 인터프리터를 한 번 통과한다. 그래서 $, 역슬래시, 따옴표가 어느 단계에서 소비되는지 매번 다르게 계산해야 한다. 위 예제들에서 \$\$처럼 이스케이프가 붙은 자리가 그 흔적이다. 파일로 저장하면 이 단계가 하나 사라진다.

10.2 비ASCII 문자가 조용히 깨진다

더 고약한 쪽이다. 명령줄로 전달되는 문자열은 셸과 터미널과 인터프리터의 인코딩 설정을 차례로 지난다. 이 사슬 중 하나라도 로캘이 다르면 한글·일본어·중국어 같은 비ASCII 문자가 오류 없이 다른 바이트로 바뀐다.

  • 오류가 안 나므로 검사기가 통과했다고 보고한다. 실제로는 검사 대상 문자열이 이미 다른 값이다
  • 이 상태에서 「검출 0건」이 나오면 그걸 무결하다는 뜻으로 읽게 된다. 가장 나쁜 실패다
  • 파일에 저장하면 UTF-8 바이트가 그대로 인터프리터에 전달된다. 인코딩 지점이 하나로 줄어든다
  • 검사기를 새로 만들면 일부러 결함을 심어 놓고 잡히는지부터 확인한다. 안 잡히면 대상이 깨끗한 게 아니라 검사기가 깨진 것이다
  • 한글은 음절 단위로 조합돼 있어서 어간만 쓴 정규식이 활용형을 통째로 놓친다. 문자 클래스로 열어 두는 편이 안전하다

로그를 정규식으로 훑는 작업 전반은 grep과 AWK 가이드와 로그 분석 명령어 가이드에 따로 정리돼 있다.

11. 확인하지 못한 것

이 글에서 실행으로 검증하지 못한 항목을 한자리에 모은다.

  • zsh와 ksh. 두 셸을 실행할 수 있는 환경이 아니어서 확인하지 못했다. ksh 계열이 파이프라인의 마지막 명령을 현재 셸에서 실행한다는 이야기는 널리 알려져 있지만 이 글에서 재현하지 않았다. 해당 셸을 쓴다면 세 줄짜리 스크립트로 직접 재현해 보는 편이 확실하다
  • 진짜 터미널이 붙은 대화형 세션. 5절의 결론은 set -m으로 job control을 켜고 끄면서 얻었다. 제어 터미널이 붙은 실제 로그인 셸에서 같은 실험을 하지는 못했다. 다만 job control 상태에 따라 결과가 갈린다는 것 자체는 확인했다
  • POSIX 표준 원문. 파이프라인 각 요소를 서브셸에서 실행할지를 표준이 구현에 열어 두었다는 점이 셸마다 동작이 갈리는 이유로 자주 언급되지만, 표준 원문 조항을 대조하지는 않았다
  • busybox ash와 최소 컨테이너 이미지. 실무에서 가장 자주 문제가 되는 조합인데 이 글에서는 확인하지 못했다
  • 대용량 입력에서의 메모리 실측. 7절에서 히어 스트링과 mapfile이 전체를 메모리에 올린다고 적었지만, 줄 수에 따른 실제 사용량을 재지는 않았다
  • 구버전 bash. lastpipe와 mapfile이 도입된 정확한 버전 경계는 확인하지 않았다. 매우 오래된 시스템을 대상으로 한다면 그 장비에서 직접 확인해야 한다

FAQ

Q1. 루프 안에서 export n을 하면 되지 않나?

안 된다. export는 부모에서 자식으로 환경을 물려주는 장치다. 방향이 반대다. 서브셸에서 export를 해 봐야 그 서브셸이 다시 만드는 손자 프로세스에만 전달되고, 부모에게는 아무 영향이 없다. 같은 이유로 declare -g도 도움이 안 된다. 전역 범위는 그 프로세스 안에서의 전역이지 프로세스를 넘지 않는다.

Q2. 루프 안에서는 값이 맞는데 왜 밖에서만 틀린가?

정확히 그게 이 현상의 지문이다. 루프 안의 echo는 서브셸 안에서 실행되니까 그 프로세스의 최신 값을 본다. 루프 밖의 echo는 부모 셸에서 실행되니까 건드려진 적 없는 원래 값을 본다. 같은 변수 이름이지만 서로 다른 프로세스의 메모리를 보고 있다. 이 증상이 보이면 파이프부터 찾으면 된다.

Q3. while 말고 for를 쓰면 해결되나?

파이프를 안 쓰게 되니 그런 셈이지만 대가가 있다. for v in $(cmd) 형태는 현재 셸에서 돌아 변수가 남는다. 다만 출력 전체를 메모리에 올리고, 단어 분리와 글로빙이 적용되어 공백이 든 파일명이 쪼개진다. for line in $(cat 파일)은 줄 단위 처리가 아니라 단어 단위 처리다. 줄을 다뤄야 하면 while read에 리다이렉션이 맞다.

Q4. 파이프라인의 각 단계는 순차 실행인가?

아니다. 파이프라인의 구성 요소들은 동시에 시작하고 파이프 버퍼를 통해 서로 흐름을 조절한다. 그래서 앞 명령이 다 끝나기를 기다렸다가 뒤가 시작하는 게 아니다. 이것도 서브셸이 필요한 이유 중 하나다. 별도 프로세스여야 병렬로 돌 수 있다.

Q5. 백그라운드로 돌린 블록의 변수는 wait 뒤에 읽으면 되지 않나?

안 된다. 실행해서 확인한 결과 { m=99; } & 뒤에 wait를 걸어도 m은 0이었다. wait는 자식이 끝나기를 기다릴 뿐 값을 가져오지 않는다. 백그라운드 작업의 결과를 받아야 하면 표준 출력을 파일이나 이름 있는 파이프로 받아 wait 뒤에 읽는다.

결론: 오늘 바꿀 세 가지

첫째, 루프 본문을 고치려 들기 전에 |부터 찾는다. 루프 안에서는 맞고 밖에서만 틀린 값은 거의 항상 파이프 때문이다. cat 파일 | while을 while ... done < 파일로 바꾸는 데 3초가 걸리고, 이걸 모르면 산술 확장을 30분 들여다본다.

둘째, 서브셸을 「변수가 사라지는 곳」이 아니라 「경계」로 읽는다. cd도, set도, trap도, exit도 그 안에 갇힌다. 갇히는 게 문제인 상황과 갇혀서 다행인 상황이 둘 다 있고, ( )는 후자를 위한 도구이기도 하다. 임시로 디렉터리를 옮겨야 할 때 괄호로 감싸는 습관이 그 예다.

셋째, set -e를 안전장치로 신뢰하지 않는다. 파이프 중간의 실패는 기본적으로 안 잡히고, ||를 붙이는 순간 왼쪽의 set -e는 꺼진다. pipefail을 같이 켜고, 중요한 자리는 PIPESTATUS로 명시적으로 확인한다.

마지막으로 하나. 이 글의 표와 출력은 전부 두 줄에서 열 줄 사이의 스크립트로 얻은 것이다. 셸 동작이 의심스러우면 논쟁하지 말고 세 줄을 돌려 보는 게 항상 빠르다. printf 'a\nb\nc\n'와 카운터 하나면 대부분의 질문이 30초 안에 끝난다.
