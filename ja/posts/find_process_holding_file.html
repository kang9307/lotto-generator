ファイルを掴んでいるプロセスを見つける - 消したのに容量が戻らないとき

rm が消すのは名前だけ。まだ掴んでいる側を Linux と Windows の両方で突き止める順序

2026-09-02 開発・インフラ

一番よくある流れはこうだ。ディスクが埋まったという警報が来る。大きなログを一つ見つけて rm で消す。ls にはもう見えない。ところが df は一桁も減っていない。数分待っても同じである。そこで消すものをさらに探しに行く。

この時点で方向がすでにずれている。問題は消すものが足りないことではなく、すでに消したものがまだ生きていることだ。この記事が扱うのは一つだけ、誰が掴んでいるかを特定する手順である。なぜこの症状が起きるのかという四つの原因分類は ディスクは空いているのに No space left on device の側にあり、この記事はそのうちの一つを引き継ぐ。

この記事に出てくる命令のうち プロセスの終了とファイル記述子の切り詰めは取り消せない。該当する節に危険の表示を別に付けてあるので、本番機ではその段落を先に読んでから手を付けるほうがよい。確認するだけの命令と状態を変える命令を混ぜないこと、それがこの作業のほとんどすべてである。

カウンタは二つある - 名前の数と参照の数

この現象の全体が一つの文から出てくる。rm はデータを消す命令ではない。 rm が呼ぶシステムコールは unlink であり、これはディレクトリに書かれた名前を一つ外す操作である。データがあるのは名前ではなく inode で、inode は名前が消えたからといって一緒に消えたりしない。

POSIX 規格はこの動作を誤読の余地なく釘付けにしている。リンクは unlink が返る前に取り除かれるが、ファイル内容の削除はそのファイルへのすべての参照が閉じられるまで先送りされるというものだ。つまり一つのファイルには性格の異なるカウンタが二つ付いていて、両方が 0 になって初めてブロックが戻る。

カウンタ数えるもの0 にするものここで見える
リンク数この inode を指すディレクトリ項目の数rm · unlink · mv による上書きstat -c %h · ls -l の 2 番目の列
開いた参照この inode を開いている記述子とマッピングの数プロセス終了 · close() · ログ再開シグナルlsof · fuser · /proc/<pid>/fd
ブロック返却の条件両方が 0 になる時点最後の参照が閉じた瞬間、カーネルが一度にdf の空きが階段状に跳ねる
観測道具の視野du は名前を歩き df はブロックを数える名前がなければ du には見えない二つの開きが握られた容量

この動作は欠陥ではなく安全装置である。あるプロセスが読んでいる最中に別のプロセスがそのファイルを消したからといって、読んでいる側が壊れては困る。問題はこの安全装置が運用中に静かに発動するところにある。エラーも出ず、ログも残らず、ただ容量が戻らないだけだ。

主題は Linux サーバなのに、以下の出力を作った環境は Windows 10 上の Git Bash である。これを先に明かすのは、どの出力が実際に出たもので、どの命令が出力なしで書かれているかを読者が区別できなければならないからだ。

coreutils は Linux と同じ GNU 8.32 なので stat·df·du·truncate のオプション動作は同一である。MSYS は /proc を独自に真似て提供しており、これが Linux カーネルの procfs ではないという点が後で一度だけ効いてくる。以下がこの記事で実際に走らせたものと走らせられなかったものの一覧である。

  • 走らせたもの (Linux 側) — 削除後も開いたままのファイルの再現、stat -c による inode とリンク数の追跡、stat -f による空きブロック計測、/proc/<pid>/fd の参照と全走査、掴んでいる側が二つのときの挙動、ファイル記述子の切り詰めの試行、開いた直後に unlink する慣用句
  • 走らせたもの (Windows 側) — 共有モードを変えたファイルロックの再現、ロックされたファイルへの Remove-Item·Rename-Item·Get-Content、Git Bash からの rm·cat、Restart Manager API による占有プロセスの特定、openfiles、Get-Process のモジュール一覧検索
  • 走らせられなかったもの — lsof·fuser（この環境に入っていない）、コンテナとネームスペース関連のすべて、NFS マウント
  • 作り話をしていないもの — 走らせられなかった命令の出力はこの記事に一行もない。命令の形と読み方だけを書き、その根拠は各道具のマニュアルである
  • 手を入れたもの — 経路を /tmp/demo に縮めて書いた。数値は一つも変えていない。この機械は他の作業も同時に動く個人用 PC なので空きブロックの値に数百ブロック単位の雑音が混ざっており、その雑音もそのまま残した
  • ブロックサイズは 4,096 バイトと報告される。以下の空きブロック数に 4,096 を掛ければバイトになる

症状 - df と du が食い違う

診断の出発点は二つの道具が違う答えを返すことである。du はディレクトリを歩いて名前の付いたファイルを数える。名前が消えたファイルは du の視野の外だ。df はファイルシステムのブロック会計を読むので、握られた容量を使用中と見る。だから二つが開き、開いた幅がそのまま握られた容量になる。

200MiB のファイルを作り、tail -f で掴んだまま消してから df -h をそのまま出力した。

--- rm の前 ---
du -sh . = 200M
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- rm の後 ---
du -sh . = 0
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- 掴んでいたプロセスを終了した後 ---
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  600G  332G  65% /tmp

三つのブロックを並べて読めば順序がはっきりする。rm は du だけを 200M から 0 に変え、df は一桁も動かなかった。df が 601G/331G から 600G/332G に変わったのは rm ではなくプロセスを終了した後である。容量を返したのは rm ではなく kill だ。

  • 現場ではこの症状はたいていグラフで先に見える。整理作業を回したのにディスク使用量のグラフが階段状に落ちず平らなら、この原因の可能性が高い
  • du -sh / の合計と df の Used を比べるのが最も安い一次判別である。大きな差が出れば名前のないファイルがあるということだ
  • ただし二つの値はもともと完全には一致しない。予約ブロック、ジャーナル、マウントに隠されたディレクトリのせいで数パーセントの差は正常だ。数十 GiB 単位で開くときが信号である
  • 注意すべき落とし穴が一つある。du を root 以外の権限で回すと読めないディレクトリが静かに抜ける。そのとき生じた差はこの現象とは無関係だ

名前は消え inode は残る

前節が症状なら、この節は原理を目で確かめる場所である。512MiB のファイルを作り、tail -f で掴み、消したあとに同じ inode をファイル記述子越しにもう一度覗いた。

[1] 作成直後
    name=app.log inode=4503599629412470 links=1 size=536870912 blocks=524288
    free=86810586   du -sh . = 512M

[2] tail -f (pid=1442) が開いたまま

[3] rm の直後 - 名前は消えた
    ls -A: []
    du -sh . = 0    free=86811452

[4] ところが fd 越しには inode が生きている
    /proc/1442/fd/3  inode=4503599629412470 links=0 size=536870912 blocks=524288
    readlink        /tmp/demo/app.log (deleted)

[5] 掴んだ fd では今も読める
    $ head -c 16 /proc/1442/fd/3 | od -An -tx1
      00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

[6] kill の後 free=86939254

読む順序はこうだ。inode 番号が [1] と [4] で同じである。消したあとも同じ客体だ。変わったのは links 一つだけで、1 から 0 になった。一方 size と blocks は 536870912 と 524288 のままである。名前は消えたがデータは一バイトも返されていないということだ。

空きブロックも同じことを言っている。rm の前後で 86810586 から 86811452 へ、866 ブロックしか動いていない。4,096 を掛ければ 3.4MiB 程度で、これは同じ機械で動く他の作業の雑音である。512MiB は 131,072 ブロックなのに、そのうち何も戻ってこなかった。そして kill のあと 86811452 から 86939254 へ、127,802 ブロックが一度に戻ってきた。

  • links=0 なのに size が大きい。これがこの状況の指紋である。他のどんな状態でもこの組み合わせは出ない
  • カーネルが付ける (deleted) の札は経路文字列の一部ではなく表示である。その文字列をそのまま cat に渡せば、ないファイルだと言われる
  • [5] が示すとおり掴んでいる側は何の支障もなく読み書きを続ける。だからアプリケーションはこの状況をエラーとして報告しない
  • 回復が一度に起きる点も覚えておく価値がある。少しずつ戻って止まるのではなく、最後の参照が閉じるその瞬間に全量である

探し方 ① /proc を直接走査する

本番機に lsof がない場合は思ったより多い。最小構成のイメージ、コンテナの中、閉域網のサーバでは、道具を新たに入れること自体が手続きを要求する。ところがカーネルがすでに答えを露出しているので道具なしでもいける。各プロセスの /proc/<pid>/fd はそのプロセスが開いているファイルを指すシンボリックリンクの束であり、対象が消えている場合は宛先の末尾に (deleted) が付く。

# 特定のプロセス一つだけを見るとき
$ ls -l /proc/1442/fd | grep -i deleted
lrwx------ 3 -> /tmp/demo/app.log (deleted)

# 全走査 - シェルだけで
$ for p in /proc/[0-9]*; do
    pid=${p##*/}
    for fd in "$p"/fd/*; do
      tgt=$(readlink "$fd" 2>/dev/null) || continue
      case "$tgt" in *"(deleted)") echo "pid=$pid fd=${fd##*/} -> $tgt";; esac
    done
  done

pid=318  fd=3  -> /tmp/demo/app.log (deleted)
pid=319  fd=3  -> /tmp/demo/app.log (deleted)

# 握られた大きさまで一緒に見たいなら
$ stat -L -c '%i %h %s %n' /proc/318/fd/3
16607023627971255 0 268435456 /proc/318/fd/3

この方式の値打ちは追加の導入が要らないことだけではない。stat -L を付ければ握られた容量までその場で出るので、候補が複数出たときどれから処理すれば容量が実際に戻るかを大きさ順に決められる。逆に限界も明らかだ。

  • 他のユーザのプロセスは権限がなければ見えない。上の巡回は静かにその行を飛ばすので、結果が空でも存在しないとは限らない。できるだけ sudo で回す
  • fd だけを見るとメモリマッピングを取りこぼす。ファイルを mmap したあと記述子を閉じてもマッピングは参照として残る。そちらは /proc/<pid>/maps にある
  • 巡回の途中でプロセスが消えると readlink が失敗する。上の慣用句が失敗を読み飛ばすのはそのためで、これゆえに同じ命令を二度回すと結果が違うことがある
  • プロセス数が数千なら、この巡回にも時間がかかる。急ぐならまず候補を絞る。ログを書くアプリケーションとそのログを読んで転送する収集器の両方が同じファイルを掴んでいる場合が最も多い

探し方 ② lsof - 命令と読み方

標準の道具は lsof である。この環境には入っていないので走らせられなかった。だから以下に出力例はない。代わりにマニュアルが定める動作と、出力のどの列を見るべきかを書く。

# 消えたのに開いているファイルだけ - この状況の正確な問い
$ sudo lsof +L1

# マウントで絞る（全体走査は遅い）
$ sudo lsof -nP +L1 /var

# 特定の経路を誰が開いているか
$ sudo lsof /var/log/app.log

# 特定のプロセスが何を開いているか
$ sudo lsof -p 1234

# ディレクトリ木の全体（再帰 - 非常に遅くなりうる）
$ sudo lsof +D /var/log

核となるオプションは +L1 である。マニュアルは +L のあとに数値を与えるとリンク数がその値より小さいファイルだけを列挙すると記す。したがって +L1 はリンク数が 0 のファイル、すなわち名前がすべて消えたのにまだ開いているファイルを正確に選ぶ。そして +L を与えると出力に NLINK 列が追加される。

  • 既定の列構成は COMMAND · PID · USER · FD · TYPE · DEVICE · SIZE/OFF · NODE · NAME である。ここで PID と SIZE/OFF と NAME の三つを見ればたいてい終わる
  • +L を与えると NLINK 列が割り込んで列の位置がずれる。 awk '{print $2}' のような位置基準の処理はオプションを変えた瞬間に壊れる。自動化するならオプションごとに列位置を確認し直す
  • FD 列には数値のほかに cwd·txt·mem といった値も来る。mem はメモリマッピングなので /proc/<pid>/fd の巡回では拾えなかった参照だ。lsof が fd 走査より優れる点がここである
  • 数値のあとに付く r·w·u は読み・書き・双方向を意味する。ログファイルを書きで開いている側がたいてい処理対象になる
  • -n と -P は名前とポートの変換を切るオプションである。マニュアルも速度改善を理由に挙げる。ディスクが埋まった急場では習慣的に付けるほうがよい
  • +D はディレクトリ木を再帰で走査する。楽だが対象が大きいと長くかかる。マウント単位で絞るほうを先に試す

探し方 ③ fuser - 経路からプロセスへ

fuser もこの環境にないので走らせられなかった。性格が lsof とは異なる。lsof が一覧を吐く道具なら、fuser は経路を一つ問うてそれを使うプロセスを答える道具である。すでにファイルが特定できているときはこちらが速い。

# このファイルを誰が使っているか（ps 形式で）
$ sudo fuser -v /var/log/app.log

# このファイルシステム全体を誰が使っているか - アンマウントできないとき
$ sudo fuser -vm /var

# 以下の二行はプロセスを殺す。確認せずに打たないこと
$ sudo fuser -k  /var/log/app.log     # 即座に終了
$ sudo fuser -ki /var/log/app.log     # 一つずつ確認しながら終了

-v を与えるとマニュアルの表現どおり ps に似た形で PID·USER·COMMAND が出て、その間に ACCESS 列が付く。この列が fuser を読む要領のすべてだ。マニュアルが定義する文字は次のとおりである。

文字マニュアルの定義この状況での意味
f開いたファイル（既定表示では省略される）読みで開いている。収集器や監視が多い
F書き込みで開いたファイル（既定表示では省略される）最有力の対象。今もこのファイルに書いている
mmmap されたファイルまたは共有ライブラリマッピングで掴んでいる。fd 走査では拾えない側
cカレントディレクトリそこで動いているだけ。アンマウントだけを阻む
e実行中の実行ファイルバイナリ自体がそのファイルシステムにある
rルートディレクトリchroot されたプロセスで見える
危険 — fuser -k はマニュアルどおりファイルにアクセス中のプロセスを殺す。経路を広く与えればその下に書くプロセスがすべて対象になる。-m と -k を併せて与えれば、そのファイルシステムを使うすべてのプロセスが終了する。まず -v で一覧を見て、殺す対象がその一覧と正確に同じかを確かめてからのみ -k を付ける。確認したければ -i も与えるが、マニュアルは -k なしで -i だけを与えると静かに無視されると記している。

掴んでいる側が一つではないとき

実務で無駄骨が最も多く出る場所である。一つ見つけて再起動したのに容量がそのままなら、たいていは道具が間違ったのではなく参照が一つではなかったのだ。256MiB のファイルを二つのプロセスに掴ませ、片方ずつ終了させてみた。

[1] 256MiB 作成            free=86679271
[2] rm 完了                free=86680587   ls -A=[]
[3] 残った参照を全走査
    pid=318  fd=3  -> /tmp/demo/app.log (deleted)
    pid=319  fd=3  -> /tmp/demo/app.log (deleted)
[4] 片方だけ終了 (pid 318)  free=86682346   <-- まだだ
[5] 残りも終了 (pid 319)    free=86748978   <-- ここで戻る

[4] で動いたのは 1,759 ブロック、7MiB 程度の雑音である。256MiB は 65,536 ブロックなのに片方を殺しても何も戻らなかった。[5] で初めて 66,632 ブロックが一度に戻る。カーネルは参照を数えるのであってプロセスを数えるのではない。

  • だから処理の順序は一覧を先に完成させてから手を付けることである。一つ見つけて殺してまた見る方式は、そのたびに一覧が変わって判断が揺れる
  • 同じプロセスが同じファイルを複数の記述子で開いている場合もある。このときはプロセス一つを処理すれば済むが、fd 切り詰めで対応するなら番号をすべて切らなければならない
  • 典型的な多重参照の組み合わせは決まっている。ログを書くアプリケーション、それを読む収集器、そして人が数日前に立てて忘れた tail -f のセッションだ
  • 親が開いたファイルを子が継承している場合も多い。親だけ再起動しても子がそのまま掴んでいる

Windows - 誰がロックしたかを突き止める

Windows では症状そのものが違って現れる。消したファイルが容量を握るのではなく、そもそも消えない。使用中だというメッセージが出るのに、肝心のどのプログラムかは教えてくれないのが普通である。

ここで実際に使えるのは Restart Manager API だ。マイクロソフトの文書はこの API の目的を、インストールや更新の途中でファイルを使っているアプリケーションを終了して再起動し再起動回数を減らすことだと説明する。その過程に必要なのが、まさに我々の欲しい情報、すなわちこのファイルを今誰が握っているかである。管理者権限なしで動き、別途の導入も要らない。

Add-Type -Namespace Rm -Name Api -MemberDefinition @'
[StructLayout(LayoutKind.Sequential)]
public struct RM_UNIQUE_PROCESS { public int dwProcessId;
  public System.Runtime.InteropServices.ComTypes.FILETIME ProcessStartTime; }
[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]
public struct RM_PROCESS_INFO {
  public RM_UNIQUE_PROCESS Process;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 256)] public string strAppName;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 64)]  public string strServiceShortName;
  public int ApplicationStatus; public uint TSSessionId;
  [MarshalAs(UnmanagedType.Bool)] public bool bRestartable; }

Windows - うまくいかない方法たち

検索するとよく出てくるが実際にはうまくいかない方法が二つある。どちらも走らせてみたが、なぜ駄目なのかのほうがむしろ役に立つ。

Get-Process の Modules は筋が違う。まったく駄目なのではなく対象が違う。この一覧に入るのはプロセスに読み込まれた実行イメージ、すなわち EXE と DLL である。上の出力で kernel32.dll はきちんと見つけている。しかしログファイルやデータファイルはモジュールではないので永遠に 0 件だ。

  • Sysinternals の handle 系の道具が広く使われているが、この環境には入っていないので走らせられなかった。だからこの記事にはその出力がない
  • 実際の場面でロックの犯人がアンチウイルス・バックアップ・インデックスサービスであることはかなり多い。これらはファイルを短く開いて閉じるので、同じ照会を数秒間隔で二度やってみれば性格が分かれる

再起動が答えだが再起動できないとき

掴んでいる側が見つかれば処置は単純である。再起動が最も確実だ。ログファイルなら再起動の代わりにログ再開シグナルで足りる場合も多い。ところが稼働中のサービスでどちらも今はできないなら、広く知られた迂回が一つある。開いたファイル記述子を直接切り取ることだ。

危険 — 以下の方法は取り消せず確認の手順もない。ファイル記述子の番号を一つ間違えると、そのプロセスが開いている別のファイルが丸ごと空になる。実行の前に readlink /proc/<pid>/fd/<n> で宛先を目で確かめ、それが (deleted) の表示が付いたログファイルで間違いないと見てからのみ手を付ける。再起動できるなら再起動が常に安全な側である。 
# 1) 必ず先に - 何を切ろうとしているかを目で確認
$ readlink /proc/957/fd/3
/tmp/demo/big.log (deleted)

# 2) そのあとにだけ - 記述子の切り詰め（取り消せない）
$ : > /proc/957/fd/3

# この環境で出た結果
[A] rm の後             free=86771292
    fd: inode=16607023627971255 links=0 size=268435456 blocks=262144
[B] : > /proc/957/fd/3
    tail: big.log: file truncated
    切り詰めの後: size=0  blocks=262144
    free=86770524                     <-- 戻らなかった
[C] truncate -s 0 /proc/957/fd/3
    size=0  blocks=262144
    free=86769107                     <-- 依然として
[D] kill の後           free=86833972

結果は正直に読まねばならない。切り詰め自体は通った。 size が 268435456 から 0 になり、掴んでいた tail が file truncated と反応したのがその証拠である。ところが空きブロックは戻らず blocks も 262144 のままだった。実際の返却は kill のあとの [D] で起きている。

ここで結論を急いではいけない。この環境の /proc は Linux カーネルの procfs ではなく MSYS が真似たもので、その下は NTFS である。Linux で同じ結果になる根拠にはならない。ただしこの失敗から持ち帰る教訓は環境と無関係に有効だ。切り詰めが通ったかどうかは size ではなく df で確認しなければならない。大きさの表示が 0 になったことと容量が戻ったことは別の事実である。

そしてこの方法には対象の制限がある。ログには通じ、データファイルには通じない。理由はファイルの扱い方が違うからだ。

  • ログファイル — たいてい追記モードで開かれ末尾にだけ足す。前の部分が消えても次の書き込みは新しい末尾から続く。切ってもアプリケーションの世界観が壊れない
  • データファイル・DB ファイル — オフセットを計算して特定の位置を読み書きする。切った瞬間にプロセスが覚えている構造とファイルの実体がずれる。次の読み取りが 0 で埋まった領域を正常なデータと解釈すれば、損傷は静かに広がる
  • 追記モードでないログ — オフセットを保ったまま書く実装なら、切ってもファイルの大きさが元のオフセットまで再び伸びる。前の部分が 0 で埋まったスパースファイルになり、見かけの大きさだけ大きく実使用量は小さい状態になる
  • 複数の記述子で開かれたファイル — 一つだけ切っても他の記述子がそのまま掴んでいる。前節で見たとおりだ

ロックは別の話である

ここまでが消えたのに開いているファイルの話だった。ファイルロックは名前が似ていて症状も重なって見えるが別の機序である。そしてこの地点で Linux と Windows が正確に分かれる。

Unix の flock は勧告的だ。マニュアルはこう記す。適切な権限があれば、プロセスは他のプロセスの flock の使用を無視して入出力を行う自由があると。つまりロックは参加すると決めたプログラム同士の約束であって、カーネルが強制する壁ではない。だから Linux では他方がロックしたという理由で rm が失敗することはない。

Windows は違う。ただしよくある誤解とも違う。Windows が無条件に阻むのではなく、ファイルを開く側が開く時点で共有モードを決め、カーネルがそれを強制する。 CreateFile の文書は共有モードが 0 ならそのファイルは共有できずハンドルが閉じられるまで再び開けないと記し、衝突する要求は ERROR_SHARING_VIOLATION で失敗すると記す。実際に確かめると同じファイルが共有モードによって正反対に分かれる。

=== 共有モード None で開いたファイル ===
PS> Remove-Item $target
ERR: IOException
MSG: The process cannot access the file ... because it is being used by another process.
PS> Rename-Item $target renamed.txt      -> 同じエラー
PS> Get-Content $target                  -> 同じエラー

$ stat -c 'inode=%i links=%h size=%s' locked.txt
inode=6192449489676514 links=1 size=19       # メタデータは読める
$ cat locked.txt
cat: locked.txt: Device or resource busy
$ rm locked.txt
rm: cannot remove 'locked.txt': Device or resource busy
$ ls -l
-rw-r--r-- 1 ... 19 Sep  2 09:12 locked.txt  # そのまま残っている

=== 同じファイルを共有モード ReadWrite, Delete で開いた場合 ===
$ cat shared.txt
share-delete payload
$ rm -v shared.txt
removed 'shared.txt'                          # 成功。プロセスはまだ生きている
$ ls -A
(空)

二つのブロックの違いはファイルでも消す命令でもない。開く側が何を許したかの一つだけである。共有なしで開いたファイルは削除も名前変更も読み取りもすべて塞がれ、共有一覧に削除を含めて開いたファイルは掴んでいるプロセスが生きているのに名前が即座に消えた。後者は Unix と事実上同じ形である。

区分Linux / UnixWindows
ロックの性格勧告的。参加するプログラム同士の約束開く時点で決めた共有モードをカーネルが強制
使用中のファイルの削除常に成功。名前だけが消える開く側が削除を許したときだけ成功
失敗したときに見えるもの失敗しない使用中というメッセージ · Device or resource busy
それで生じる問題容量が静かに戻らない配備や更新が騒がしく止まる
探す道具lsof · fuser · /procRestart Manager · リソースモニター
よくある誤解rm がデータを消すWindows は使用中なら絶対に消せない

実務的に残るのはこれだ。Windows で配備がファイルロックで止まるなら、直す場所は消す側ではなく開く側である。ログを開くコードが削除の共有を許せばローテーションは詰まらない。

コンテナ - pid は視点によって違う

コンテナでこの作業が難しくなる理由は道具がないからではなく、pid と経路が視点ごとに違うからである。ホストで lsof を回して得た pid をコンテナの中で kill に渡せば見当違いのプロセスを殺す。逆も同じだ。

コンテナ自体はこの環境で走らせられなかった。ただし同じ性質のずれはここでもそのまま出る。MSYS は自分だけの pid を使い、Windows カーネルは別の pid を使う。

$ tail -f hold.log > /dev/null &
$ echo $!
1410

$ ls -l /proc/1410/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/hold.log (deleted)

$ ps -W | head -1
      PID    PPID    PGID     WINPID  TTY   UID    STIME COMMAND
$ ps -W | grep 1410
     1410    1405    1403        580  ?  197609 09:18:32 /usr/bin/tail

シェルが知る pid は 1410 なのにカーネルが知る pid は 580 である。同じプロセスで、どちらも間違っていない。翻訳表なしに片方の数値をもう片方へ渡してはいけないというのが要点であり、コンテナの pid ネームスペースで起きることも性質は同じだ。以下はその状況で確認すべき場所である。

  • ホストで見た pid をコンテナ内の pid へ移すには翻訳が要る。Linux では /proc/<host-pid>/status の NSpid 行に二つの値が並んで書かれる
  • 経路もずれる。コンテナ内の /var/log/app.log はホストから見ればオーバーレイ上位層のどこかの長い経路である。ホストで取った lsof の結果の経路をコンテナの経路と取り違えないこと
  • コンテナ内に lsof も /proc へのアクセス権もない場合が多い。そのときはホストから見るほうが速い。ホストの /proc/<pid>/root/ の下にそのコンテナのファイルシステムがそのまま見える
  • 最もよくある誤りはコンテナを再起動すれば解決すると見てログのボリュームはそのまま置くことである。掴んでいるプロセスがコンテナの外のログ収集器なら、コンテナを何度再起動しても容量は戻らない
  • オーケストレータが付いていれば人が殺したプロセスを再び立ち上げる。新しく立ったプロセスが同じファイルをまた掴むかまで確認して初めて処置が終わる

ネットワークファイルシステムの .nfs ファイル

NFS では同じ状況が目に見える形で現れる。消したファイルが消えずに .nfs で始まる名前で残っているのを見たことがあるはずだ。これは故障ではなくNFS クライアントが POSIX の動作を真似ようとしてやっていることで、普通は sillyrename と呼ぶ。

事情はこうだ。ローカルのファイルシステムでは名前が消えても開いた参照があれば読み続けられる。NFS プロトコルはこれを直接支えない。そこでクライアントのカーネルが消す代わりに .nfsXXXX という形の名前へ移しておく。 Linux NFS wiki の説明のとおり、クライアントは該当の vnode が非活性になったときにその新しい名前を消す。NFS マウントはこの環境にないので直接は再現できなかった。

  • したがって .nfs ファイルは消すべきごみではなく標識である。まだ誰かが開いているという意味なので、掴んでいるプロセスを見つけて片づければ名前は自然に消える
  • 消そうとしてもうまくいかない。参照が生きている間はクライアントがその名前を守る
  • 同じ wiki が記す例外がある。rename と remove の間にクライアントが落ちるとサーバにごみファイルが残る。この場合にだけ本当に消すべき対象になり、判断の基準はクライアントを再起動しても残っているかどうかだ
  • この真似はクライアントが一つのときだけ成り立つ。他のクライアントがそのファイルを開いているかを知る術がないので、複数のクライアントが同じファイルを共有する配置では開いているファイルが消される状況もありうる
  • rmdir が空に見えるディレクトリで失敗するのも同じ理由である。ls -a で見れば .nfs ファイルが中にある

そもそも起こさないようにする

この状況を作る原因は事実上一つに収束する。ログローテーションの設定が静かにずれていることだ。ファイルを移すか消したあとプロセスに開き直せという合図を送らなければ、プロセスは名前のない古いファイルに書き続ける。ローテーションがどうやってこの状況を作るのかは ログローテーションが静かに失敗する場所 の側で別に扱う。

設計の側でできることもある。一時ファイルが必要なときは開いた直後に名前を消す慣用句がある。名前がないので他のプロセスが触れられず、プロセスがどんな形で終わってもカーネルが勝手に容量を返す。後片づけのコードを書く必要がなくなる。

# 開いた直後に unlink - 無名の一時ファイル
$ exec 9> tmpdata
$ rm tmpdata                      # 名前はここで消える
$ echo "hello anonymous" >&9      # それでも書き込みは続く
$ ls -A
(空)
$ stat -L -c 'inode=%i links=%h size=%s' /proc/self/fd/9
inode=16325548651260599 links=0 size=16
$ exec 9>&-                       # 閉じた瞬間に容量返却。後片づけ不要

# 監視に入れる値 - df と du の差
$ used_df=$(df -k --output=used /var | tail -1)
$ used_du=$(du -sk /var 2>/dev/null | cut -f1)
$ echo "gap_kb=$(( used_df - used_du ))"
  • 監視に df と du の差を指標として入れておけば、この状況が事故になる前に見える。絶対値ではなく推移を見る。普段の幅から外れて開き続けるなら握られたファイルが溜まっている最中だ
  • du は大きなファイルシステムで負担が重いので周期を長く取る。CephFS のように全走査が高くつくファイルシステムではこの方式自体を避け、ファイルシステムが提供する再帰統計を使う
  • ログを書く側と読む側の両方に再開シグナルが届くか確認する。アプリケーションだけがシグナルを受け取り収集器が受け取れなければ半分しか手を放さない
  • ローテーションを名前の変更ではなく中身を空にする方式にすればこの問題は原理的に起きない。代わりにローテーションの瞬間に記録される行が失われうるという代償がある
  • 人が残す tail -f のセッションも原因になる。調査目的で立てたセッションは終わったら閉じるという習慣一つでなくせる類だ

急ぐときの順序

ディスクが埋まった状態では判断する時間がない。だから順序をあらかじめ決めておくほうがよい。以下は確認が安いものから危険なものへの順である。

順序すること見る値ここでしてはいけないこと
1失敗した経路を df に直接与えるその経路は本当にそのファイルシステムかルートの行だけ見て判断すること
2du -sh の合計と df の Used を比較差が数十 GiB か差を即座に原因と断定すること
3lsof +L1 または /proc 走査pid · 握られた大きさ · 経路一覧を最後まで作らずに手を付けること
4同じファイルの参照をすべて集める親·子·収集器·人のセッション一つ殺して数え直すこと
5再起動またはログ再開シグナルdf の空きが階段状に跳ねるかkill -9 を先に使うこと
6それでも駄目なら fd の切り詰めreadlink で対象を確認してからのみデータファイル·DB ファイルに適用
危険 — kill -9（SIGKILL）はプロセスに片づける機会を与えない。バッファに残ったログが消える程度で済むこともあるが、書き込み途中だったファイルが中間状態で残ることもある。まず既定の終了シグナルを送り、数秒待っても生きているときにだけ強制終了を使う。いずれにせよデータベースや状態を持つプロセスには最後の手段である。
  • 3 番で候補が 0 件なら権限をまず疑う。他のユーザのプロセスは静かに抜ける
  • 5 番をやっても df が動かなければ 4 番へ戻る。道具が間違ったのではなく参照が残っているのだ
  • 急場で消すものをさらに探す方向へ行くとたいてい時間を失う。du と df が食い違っているなら消すことでは解決しない
  • 処置が終わったら同じファイルがまた掴まれるかをもう一度見る。ローテーションの設定がそのままなら数日後に同じ場所へ戻ってくる
  • メモリ側が原因のときは症状が似て見えても別の問題だ。その筋は OOM Killer が何を選んだかを読む方法 の側にある

まとめ

rm は名前を消す命令である。データを消すのは最後の参照が閉じる瞬間のカーネルだ。だからこの状況の解決はファイルをまた消すことではなく掴んでいる側に手を放させることであり、そのためにはまず誰が掴んでいるかを特定しなければならない。

特定する道は三つだ。lsof +L1 はリンク数が 0 の開いたファイルだけを正確に選ぶ。fuser -v は経路を一つ問うてプロセスを答え、ACCESS 列が性格を教えてくれる。どちらもなければ /proc/<pid>/fd をシェルで走査すればよく、(deleted) の札が答えの代わりになる。Windows では症状が逆に現れ、Restart Manager がその答えを出す。

そして忘れやすいことが二つある。参照は一つとは限らないということ、そしてファイル記述子の切り詰めはログには通じデータファイルには通じないということだ。この二つを取りこぼすと、処置をしたのに df が動かないか、動いたのに別のものが壊れる。

確認できなかったこと

  • lsof と fuser はこの環境に入っておらず一度も実行できなかった。該当する節の命令と列の説明は各道具のマニュアルに基づくもので、実行出力はこの記事にない。バージョンやディストリビューションによって列構成が変わりうるので、自動化の前に各自の機械で一度確認するほうがよい
  • ファイル記述子の切り詰めはこの環境で size だけが 0 になり空きブロックは戻らなかった。MSYS の /proc が Linux カーネルの procfs ではなくその下が NTFS なので、Linux の ext4·XFS で同じ結果になるかは確認できなかった。この記事はその環境の結果を断定しない
  • コンテナと pid ネームスペースは直接再現できなかった。本文に載せた pid のずれは MSYS と Windows カーネルの間のもので、性質が同じだという類比として書いたのであってコンテナから取った出力ではない。/proc/<pid>/status の NSpid 行もこの環境では確認できなかった
  • NFS マウントがないので .nfsXXXX ファイルを自分で作ってみることはできなかった。該当する節は Linux NFS wiki の説明に基づくものである
  • Sysinternals の handle 系の道具は入っていないので走らせられず、だからこの記事はその道具の出力を引用していない。リソースモニターも GUI なので画面の撮影なしに操作の位置だけを書いた
  • openfiles /Local ON を実際に立ててフラグが有効な状態の動作は確認できなかった。管理者権限と再起動が要るからである。本文の二つのエラーメッセージは下りた状態で出た実際の出力だ
  • 空きブロックの値に混ざった雑音は取り除いていない。この機械で他の作業が同時に動くためで、数百から数千ブロック単位の揺れはそのせいである。再現しても同じ数値にはならない

参考資料

  • unlink - POSIX.1-2017 (The Open Group Base Specifications Issue 7) — リンクは unlink が返る前に取り除かれるが、ファイル内容の削除はすべての参照が閉じられるまで先送りされるという規定
  • lsof(8) マニュアル — +L のあとの数値よりリンク数が小さいファイルだけを列挙するという説明、+L 指定時に NLINK 列が付くという説明、-n·-P·+D·-p の動作
  • fuser(1) - Linux manual page — -v の ps に似た出力、ACCESS 文字 c·e·f·F·r·m の定義、-m·-k·-i の動作
  • flock(2) - Linux manual page — 勧告的ロックであるという規定、プロセスがロックを無視して入出力する自由があるという一文、ロックが開いたファイル記述に結び付くという説明
  • CreateFileW function (fileapi.h) - Win32 apps — dwShareMode が 0 なら共有できずハンドルが閉じられるまで再び開けないという説明、衝突時の ERROR_SHARING_VIOLATION、FILE_SHARE_DELETE の意味
  • About Restart Manager - Win32 apps — 更新対象のファイルを使っているアプリケーションとサービスを終了・再起動して再起動回数を減らすという目的、終了の順序
  • Server-side silly rename - Linux NFS — 開いているファイルを消すとき名前を変えておくクライアントの動作、vnode が非活性になったときに消すという説明、その間にクライアントが落ちるとサーバにごみファイルが残るという言及
  • ディスクは空いているのに No space left on device - inode と開いたままのファイル — この症状の四つの原因分類と診断の順序。この記事はそのうち二番目の原因を引き継ぐ
