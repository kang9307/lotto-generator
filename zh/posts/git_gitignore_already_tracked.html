写进 .gitignore 了却还是一直被提交 - 已经在跟踪中的文件

不是规则写错了，而是顺序错了。取消跟踪的方法，以及取消之后历史里仍然留着的问题

2026年9月1日 开发/基础设施

有一个配置文件，每次提交都要跟着走。把名字写进 .gitignore，改一下文件，敲 git status。还在。怀疑是打错字就再写一遍，加上斜杠又去掉，试着放个星号。还是在。

到这一步，多数人开始搜索模式语法。可是这种症状里的大部分并不是语法问题。不是规则写错了，而是写规则的时机太晚了。这篇文章会在一个临时仓库里把它复现出来，再讲取消跟踪的命令，以及这条命令做不到的事。最后那部分最重要。

运行环境

本文所有输出都取自下面的环境。Git 本身的行为不太受平台影响，但换行处理、路径写法这类地方会随 shell 和操作系统而变，所以先写明。

  • 操作系统 - Windows 10 Pro（版本 10.0.19045）
  • Shell - Git Bash（GNU bash 5.2.37(1)-release, x86_64-pc-msys）
  • Git - git version 2.48.1.windows.1
  • 仓库 - 在临时目录里用 git init -b main 新建的空仓库。没有碰真正的工作仓库

在 Linux 或者 macOS 的 bash、zsh 上，下面的输出基本也能原样重现。可能出现差异的地方有两处。文件名的大小写区分（Windows 和默认设置下的 macOS 不区分，Build/ 和 build/ 可能被当成同一个），以及 core.autocrlf。后者已经固定为 false，免得结果晃动。

复现 - 已经提交过的文件不看规则

与其用话解释，不如跑一遍更快。建一个空仓库，提交一个配置文件，然后才写 .gitignore。这和现实中发生的顺序一模一样。

$ git init -b main demo && cd demo
$ echo 'API_KEY=placeholder' > config.local.json
$ git add -A && git commit -m "initial commit"

# 到这里都没有任何问题。现在来加规则。
$ echo 'config.local.json' > .gitignore
$ git add .gitignore && git commit -m "add gitignore"

# 然后改一下那个文件。
$ printf 'API_KEY=changed-secret\n' > config.local.json
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   config.local.json

no changes added to commit (use "git add" and/or "git commit -a")

规则明明写着，modified: config.local.json 却照样出现。原因往索引里一看就清楚了。

$ git ls-files
.gitignore
README.md
config.local.json
src/app.js

$ git check-ignore -v config.local.json
$ echo $?
1

git ls-files 输出的是索引里登记的路径，也就是当前正在跟踪的文件清单。config.local.json 就大大方方地在里面。而 git check-ignore 一声不吭，只返回退出码 1。不是因为没有规则，而是正在跟踪的路径根本不属于忽略判定的对象，检查被跳过了。这份沉默后面的诊断一节还会再讲。

  • 症状看上去像是「无视规则」，实际却是连规则都不读的状态
  • 模式改了十遍结果还一样，那再折腾语法就是浪费时间。先看索引
  • 判别一行就够了。git ls-files 里有那条路径，原因就定了

为什么这样设计

官方文档把这个行为写在了第一句话里。gitignore 文档的开头就是「指定有意不跟踪的文件。已经被 Git 跟踪的文件不受影响」。这不是什么例外行为，而是明文声明的规格。

为什么这么定，想一想相反的情况就能接受。如果只在 .gitignore 里加一行，已经属于仓库一部分的文件就悄悄脱离，那么一行文本就等于版本管理对象的删除命令。一个 *.conf 这样宽的模式，就可能让几十个被跟踪的文件一次性从历史里脱离。何况这个文件是要提交的，会传播到整个团队。为一个人方便写下的一行，不该在别人的仓库里把文件弄掉。

于是 Git 把两件事分开了。什么东西不再新装进来由配置文件决定，把已经装进来的东西取出来则只能用明确的命令。文档的 NOTES 一节也是这么引导顺序的。要停止跟踪，先用 git rm --cached 从索引里删掉，然后再把名字写进 .gitignore，让它不会再进来。

  • 配置文件是面向未来的规则，不会追溯已经存在的历史
  • 从历史里抽掉东西是难以撤销的动作，所以要求另一条命令
  • 因为这个分离，就算 .gitignore 不小心写得过宽，最坏的结果也只停在「新文件没被拾起」

取消跟踪的方法 - git rm --cached

停止跟踪的命令只有一条，就是 git rm --cached。它只从索引里删掉条目，工作目录里的实际文件一动不动。接着刚才那个仓库执行一下，结果是这样。

$ git rm --cached config.local.json
rm 'config.local.json'

$ ls -1
README.md
config.local.json
src

$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    config.local.json

$ git commit -m "stop tracking config.local.json"
$ printf 'API_KEY=another-change\n' > config.local.json
$ git status --short

$ git check-ignore -v config.local.json
.gitignore:1:config.local.json	config.local.json

按顺序读下来是这样。rm --cached 之后，文件仍然在磁盘上（ls -1 的输出里还有），在索引里则被暂存为删除。提交完之后再改同一个文件，git status --short 什么都不输出。而这时候 check-ignore 才开口，连是哪条规则、第几行抓住了这条路径都告诉你。

注意 - 漏掉 --cached 的 git rm 路径，会把索引和工作目录里的文件一起删掉。如果那是一个装着未提交内容的本地配置文件，就没有办法恢复了。就本文讨论的用途而言，--cached 必须带上。

要整个目录取消跟踪时需要 -r。不加的话 Git 会拒绝。执行之前先用 --dry-run 看一眼目标清单是个好习惯。

$ git rm --cached node_modules
fatal: not removing 'node_modules' recursively without -r

$ git rm -r --cached --dry-run node_modules
rm 'node_modules/pkg/index.js'

$ git rm -r --cached node_modules
  • --cached - 只从索引里移除。工作目录里的文件留着
  • -r - 目标是目录时必须要有。没有就会以 fatal 拒绝
  • --dry-run - 只输出清单，实际什么都不改
  • 移除要提交之后才算定下来。在那之前只是反映在索引里

一次性清理的惯用写法与代价

需要停止跟踪的文件有好几个时，有一种常用做法：把索引整个清空再重新装回去。清空之后用 git add . 重新装，这时会套用当下生效的 .gitignore 规则，被忽略的对象自然就落下了。

$ git rm -r --cached . --dry-run
rm '.gitignore'
rm 'build.log'
rm 'src/app.js'

方便，但附带一个条件。只能在一个未提交的改动都没有的状态下用。清空索引再装回去这个动作，并不是只把忽略规则筛掉，而是把那一刻工作目录里的所有状态原样装进去。下面是在有一处未提交编辑的状态下执行这个惯用写法的结果。

$ echo 'app-edited-but-not-committed' > src/app.js
$ git status --short
 M src/app.js

$ git rm -r --cached .
$ git add .
$ git status --short
D  build.log
M  src/app.js

$ git diff --cached --stat
 build.log  | 1 -
 src/app.js | 2 +-
 2 files changed, 1 insertion(+), 2 deletions(-)

本来只想取消 build.log 的跟踪，结果还没审过的 src/app.js 的编辑混进了同一个提交。如果是几百个文件的仓库，提交信息和实际内容就对不上，之后很难找原因。所以顺序要这样安排。

  • 先确认 git status 是干净的。剩下的改动要么提交，要么另外收好
  • 用 --dry-run 看清单。出来的比预想多，就是规则太宽的信号
  • 目标只有几个的话，不用惯用写法，而是一条一条指定路径。事故范围就被限定在那条路径上
  • 提交前用 git diff --cached --stat 确认装进去的是什么

取消跟踪了，历史里仍然留着

这里是本文最重要的一段。git rm --cached 只从那次提交往后排除文件。过去的提交里，内容一丝不损地留着。把它从索引里消失读成「已经删掉了」，就成了危险的误会。

下面是把装着密码的文件提交两次之后取消跟踪，再确认还能读到什么的结果。值是实验用的占位符。

$ git ls-files
.gitignore
src/app.js

$ git log --oneline -- config/secrets.env
295c575 stop tracking secrets.env
dec8b71 update settings
61f23fd initial commit

$ git show HEAD~2:config/secrets.env
DB_PASSWORD=placeholder-not-a-real-secret

$ git rev-list --objects --all | grep secrets.env
c6dd1f3ef86e381a694fa8c4ad29b2ea0463e33e config/secrets.env
934ceb11a04aff62ef5aaa84c79377a41d57ba15 config/secrets.env

当前的跟踪清单里没有它。可是 git log 会把碰过这个文件的提交全列出来，git show 提交:路径 一行就把当时的内容原样打印出来。最后那条命令更清楚。两个版本的 blob 对象原封不动地留在对象数据库里，克隆仓库的人会把这些一起拿走。

要连过去的提交里也把文件抹掉，就需要重写历史，那是性质完全不同的活儿。所有提交哈希都会变，克隆过仓库的人全都受影响，分支、标签、合并请求之间的一致性也会崩掉。本文只点到这件事需要另外单独做为止，不讲步骤。在大多数情况下，它也不是第一件该做的事。

  • rm --cached 只改未来的提交。过去照旧
  • 删掉分支或者回退提交，对象也不会立刻消失。reflog 还在的期间，它一直读得到
  • 重写历史会改掉所有提交哈希，所以在共享的仓库里，前提是全体协作者都协调好
  • 如果已经推到远端，那么不管本地做什么，对方那份副本都要当成还留着

如果凭据进去了，先换密钥

发现密码或者 API 密钥进了提交，手会反射性地伸向删文件那一边。顺序反了。文件删得再干净，已经被读走的值也回不来。只要推到过远端、有人克隆过，或者备份、镜像、CI 缓存里留着副本，那个值就得当作已经泄露来处理。

所以优先级很明确。把泄露的凭据作废并重新签发，这是第一件事。新值一生效，旧值就没用了，不管它还留不留在历史里，风险都消失了。反过来，要是先从历史下手，那件事进行的整个期间，旧密钥都还活着。

  • 第 1 位 - 把对应的密钥、令牌、密码作废并重新签发。在签发方的控制台上立刻让旧值失效
  • 第 2 位 - 查看那份凭据能访问到的地方的日志，看有没有实际被使用过的痕迹
  • 第 3 位 - 用 git rm --cached 和 .gitignore 挡住同样的事再次发生
  • 第 4 位 - 有必要的话再规划重写历史。等协作者协调完之后再做

补一句，凭据本来就不该以文件的形式放在仓库里。用环境变量或者另外的密钥管理手段，仓库里只放值为空的示例文件。像 config.example.json 这样把名字分开，就成了示例被跟踪、实际文件被规则挡住的结构。

不生效的原因 1 - 路径模式

如果不是索引的问题而规则还是不生效，下一个候选就是模式的写法。容易搞混的地方压缩成两个：前面的斜杠和后面的斜杠。

官方文档的规定是这样。模式的开头或者中间有分隔符，它就是相对于那个 .gitignore 所在目录的路径；没有的话，在它下面任何深度都能匹配。模式末尾有分隔符就只匹配目录，没有则文件和目录都匹配。

# 现在有 build/ 和 src/build/ 两个目录

$ printf '/build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:/build/	build/out.o
# src/build/out.o 不在输出里 = 没有被忽略

$ printf 'build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:build/	build/out.o
.gitignore:1:build/	src/build/out.o

一个前导斜杠，把「只有顶层的 build」和「任何深度的 build」分开了。接下来是后面的斜杠。下面是把 cache 先做成目录、再改成文件，套上同一条规则的结果。

# cache 是目录时
$ printf 'cache\n' > .gitignore
$ git check-ignore -v cache/a.txt
.gitignore:1:cache	cache/a.txt

# cache 是文件时 - 同一条规则照样生效
$ git check-ignore -v cache
.gitignore:1:cache	cache

# 规则末尾加上斜杠，对文件就不生效
$ printf 'cache/\n' > .gitignore
$ git check-ignore -v cache
$ echo $?
1

# 同一条规则对目录生效
$ git check-ignore -v cache/a.txt
.gitignore:1:cache/	cache/a.txt

下面是常用的写法和它们的结果。

写法含义匹配的例子不匹配的例子
build叫 build 的文件和目录，深度不限build, src/build名字不同的
build/只匹配目录，深度不限build/, src/build/叫 build 的文件
/build/只匹配顶层的 build 目录顶层的 build/src/build/
*.loglog 扩展名，深度不限a.log, logs/b.loglog.txt
logs/*.log只在 logs 正下面。中间的斜杠把位置固定住logs/a.loglogs/sub/a.log
logs/**/*.loglogs 下面的所有深度logs/sub/a.loglogs 之外的日志
  • 模式里一个斜杠都没有的话，位置就是自由的。比预想抓得更宽的事故就出在这里
  • 只想针对目录，就在末尾加斜杠。这能挡住把同名文件也一起抓进来
  • 模式是以那个 .gitignore 所在的目录为基准来解释的。放在下级目录里的文件写 /foo，指的不是仓库顶层，而是那个目录下的 foo

不生效的原因 2 - 否定模式复活不了的位置

「这个目录全都忽略，但只想留下这一个文件」是常见的需求。于是把目录整个排除，再给下面那一个文件加上感叹号。可是这个组合不工作。

$ printf 'logs/\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/	logs/error.log
# 写了 ! 结果还是第 1 行赢了

$ printf 'logs/*\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ git check-ignore -v logs/debug.log
.gitignore:1:logs/*	logs/debug.log

差别只在 logs/ 和 logs/* 这一处。前者排除的是目录本身，后者排除的是目录里的条目。官方文档把理由写得很明白：父目录被排除的文件无法再被重新包含，而且出于性能考虑，Git 不会去列举被排除目录的内容，所以针对其中文件的模式无论写在哪里都没有效果。目录整个关上，Git 连里面都不看一眼。

第二个坑是顺序。忽略规则由最后匹配上的模式决定结果。先写例外、后写宽规则，例外就会被盖掉。

$ printf '!logs/error.log\nlogs/*\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:logs/*	logs/error.log

同样的两行，只换了顺序，结果就翻过来了。第 2 行的宽规则盖住了第 1 行的例外。因此 .gitignore 把宽规则放上面、例外放下面的顺序，是事实上的标准。

  • 目录里需要例外时，要写 dir/* 而不是 dir/。差别就在一个字符
  • 嵌套深的话，要一层一层地打开。像 dir/*、!dir/sub/、dir/sub/*、!dir/sub/keep.txt 这样
  • 感叹号那一行，永远排在它想翻过来的那条规则下面

不生效的原因 3 - 哪个文件的规则赢了

能写忽略规则的地方不止一处。仓库的 .gitignore、放在各个下级目录里的 .gitignore、.git/info/exclude，以及用 core.excludesFile 指定的全局文件，全都同时在起作用。

官方文档定的优先级，从高到低是这样。命令行传进去的模式，该路径所在目录及其上级目录的 .gitignore（越靠近下级的文件盖住上级的），info/exclude，最后是全局文件。同一层级之内，最后匹配的赢。把四个层级依次叠上去，就是下面这样。

# 1) 只有全局忽略时 (my_global_ignore 的内容是 *.log)
$ git config core.excludesFile my_global_ignore
$ git check-ignore -v logs/error.log
my_global_ignore:1:*.log	logs/error.log

# 2) .git/info/exclude 赢过全局
$ printf '!logs/error.log\n' > .git/info/exclude
$ git check-ignore -v logs/error.log
.git/info/exclude:1:!logs/error.log	logs/error.log

# 3) 仓库的 .gitignore 赢过 info/exclude
$ printf 'logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/error.log	logs/error.log

# 4) 下级目录的 .gitignore 赢过上级
$ printf '!error.log\n' > logs/.gitignore
$ git check-ignore -v logs/error.log
logs/.gitignore:1:!error.log	logs/error.log

四次执行，每次被指出来的判定者都是不同的文件。如果规则分散写在好几个地方，还在纳闷为什么不生效，那么这份输出本身就是答案。

写在哪里是否共享优先级适合写什么
下级目录的 .gitignore会提交并共享最高只适用于那个目录的规则
顶层的 .gitignore会提交并共享高构建产物、依赖、密钥文件的名字
.git/info/exclude不共享中这个仓库里只有自己用的临时文件
core.excludesFile 全局文件不共享最低编辑器和操作系统产生的副产物
  • 同一条路径上挂着多条规则时，下级目录的文件赢过上级。可以做成上级挡住、下级放开的结构
  • 全局文件最弱。仓库明确写着要忽略的东西，全局设置翻不过来
  • 看不到规则却发现文件被忽略了，就怀疑全局文件和 info/exclude。这两处都在仓库里看不见

诊断 - check-ignore 会指出真凶

前面几节一直在用的 git check-ignore -v 就是标准的诊断工具。传进路径，它会用制表符分隔输出哪个文件第几行的哪条规则做了判定。读的时候有三个特性需要先知道。

# 1) 对正在跟踪的文件一声不吭
$ git check-ignore -v kept.txt
$ echo $?
1

# 2) 加上 --no-index 就能看到规则
$ git check-ignore -v --no-index kept.txt
.gitignore:1:kept.txt	kept.txt

# 3) -v 的退出码不是「被忽略」而是「匹配到规则」
#    规则: logs/* 和 !logs/error.log
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ echo $?
0
$ git check-ignore logs/error.log
$ echo $?
1

第一，对已经在跟踪的文件它保持沉默。就是本文前半段看到的那份沉默。--no-index 的说明把这个用途原样写着：在调试文件为什么因为 git add . 之类的命令进入跟踪状态时使用。输出是空的，加上 --no-index 却出来了，那这个文件就在跟踪中，答案已经有了。

第二，输出的规则如果以感叹号开头，那条路径不会被忽略。文档里 -v 的说明也写着「模式以 ! 开头时是否定模式，匹配上意味着该路径不被排除」。看到有输出就读成「被忽略了」，意思就完全反了。

第三，所以退出码也得小心读。上面的执行里，加 -v 时是 0，去掉时是 1。不是判定翻了，而是 -v 把「匹配到规则」当成功，没有 -v 的形式把「实际被忽略」当成功。在脚本里拿来做判定时，要用没有 -v 的形式。

辅助工具也有两个。git status --ignored 连被忽略的东西也用 !! 标出来给你看，git ls-files -i -c --exclude-standard 则专门挑出匹配到规则却仍在跟踪中的文件。这份清单正好对上本文的主题。

$ git status --short

$ git status --short --ignored
!! logs/
!! scratch.tmp

# 加了 *.log 规则，但 build.log 已经在跟踪中
$ git ls-files -i -c --exclude-standard
build.log
  • git check-ignore -v 路径 - 一行回答哪条规则赢了。第一个该敲的命令
  • 加了 --no-index 才出来，原因就是跟踪状态。转去 git rm --cached
  • git status --ignored - 用眼睛确认到底什么被忽略了
  • git ls-files -i -c --exclude-standard - 把要清理的清单整个抽出来

空目录不会被跟踪

和这个主题连在一起的还有一个问题：只建了目录结构提交上去，别人拿到却没有那个目录。这和忽略规则无关。Git 只记录文件，不会另外保存目录这个概念。只是路径里包含的目录名被顺带重现出来而已。

$ mkdir uploads
$ git add uploads
$ git status --short

$ touch uploads/.gitkeep
$ git add uploads
$ git status --short
A  uploads/.gitkeep

对空目录 git add，既不报错也什么都不发生。往里面放一个文件，才终于被暂存。.gitkeep 的惯例就是从这里来的。它不是 Git 认得的特殊名字，只是为了保住目录而放进去的空文件被叫顺口的一个通称而已。放个 README 结果也一样。

  • 名字是习惯。工具并不特殊对待，团队里定一个用就行
  • 像上传目录那样，里面的内容要忽略但目录要留下的情况最典型
  • 那种情况下规则是 uploads/* 和 !uploads/.gitkeep 两行。因为上一节的理由，写成 uploads/ 例外就复活不了

不要把仓库规则和个人偏好混在一起

.gitignore 是会被提交的文件，所以会原样传给每一个拿到仓库的人。往里面写什么看着像是自己一个人的事，实际上更接近协作约定。写进个人编辑器设置的那一刻，对不用那个编辑器的人来说，也被分发了一行没有意义的东西。

标准很简单。谁拿到都长得一样的东西写进仓库规则，因人而异的东西写进个人设置。构建产物和依赖目录在哪台机器上都是同样的名字，所以归仓库规则是对的。而用哪个编辑器则因人而异。

  • 仓库的 .gitignore - 构建产物、依赖目录、日志、实际密钥文件的名字
  • .git/info/exclude - 只在这个仓库里自己需要的东西。实验用脚本、个人备忘
  • 全局文件（core.excludesFile） - 编辑器设置、操作系统副产物这类在所有仓库里都会重复的东西
  • 三处都遵循上一节的优先级。个人设置最弱，翻不过仓库规则

仓库的 .gitignore 里堆积个人条目，多半是因为不知道还有别的地方可以写。只要告诉一句有 .git/info/exclude 这回事，这个文件就会明显清爽下来。

一开始就该写进去的清单与提交前的习惯

本文的问题全都出在顺序上。是规则比文件到得晚才发生的事。预防也用顺序来做：在仓库的第一次提交里就把 .gitignore 一起放进去。语言和框架不同，清单也不同，但性质分成四类。

性质例子为什么要写漏掉之后
构建产物dist/, build/, target/, *.o随时都能从源码重新生成每次提交都出来巨大的差异，评审很难做
依赖node_modules/, vendor/, .venv/靠锁文件就能重现，没有理由留在历史里仓库体积变成几十倍，克隆变慢
日志和临时文件*.log, *.tmp, .cache/每次运行都不一样的值没有意义的改动一直堆积，把真正的改动盖住
凭据.env, *.pem, *_rsa, secrets.*一旦进去就很难从历史里抽出来除了换密钥没有别的解决办法

最后一行代价最高。前三样就算发现得晚，一次 rm --cached 也就清干净了，凭据却不是这样就完事的。把 .env 这一类在第一次提交之前就放进去，是最划算的做法。

还有一个习惯值得带上。git add . 是省事，可是它会把还没有规则的新文件全都装进去。有规则的话 Git 会挡住，没有的话就悄悄进去了。

$ printf 'TOKEN=placeholder-not-a-real-token\n' > .env.local
$ echo 'note' > memo.txt
$ git add .
$ git status --short
A  .env.local
A  memo.txt
A  uploads/.gitkeep

# 有规则的话会像这样挡住
$ git add logs/error.log
The following paths are ignored by one of your .gitignore files:
logs/error.log
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"

上面那个 git add . 一声警告都没有就把 .env.local 装进去了。下面因为有规则被拒绝了，还提示真要加就用 -f。这个对比就是把规则提前放进去的理由。而且不管哪一边，提交前看一眼 git status 的习惯都是最后一道安全网。读几行花的时间是几秒。

  • 新仓库的第一次提交里就包含 .gitignore。本文的问题大部分都会消失
  • 凭据的模式要在项目还空着的时候放进去。之后再放就晚了
  • git add . 之后用 git status --short 看一眼装进去的是什么
  • 出现拒绝提示时，别反射性地加 -f。挡住可能是有理由的

一页速查

按症状整理该看哪里，就是下面这张表。照顺序从上往下查，大多数在第二行之内就能抓到原因。

症状要确认的命令解决

小结

.gitignore 只忽略未被跟踪的文件。就一句话，本文的大部分内容都是从这里出来的。规则到得晚的文件根本不读规则，所以模式改得再多结果也不变。取消跟踪的命令是 git rm --cached 路径，目录需要 -r，漏掉 --cached 连磁盘上的文件都会消失。

也有模式本身有问题的情况。前导斜杠固定位置，末尾斜杠限定为目录，父目录整个挡住之后里面的例外就复活不了，同一层级里最后匹配的赢。规则还可能散在四个地方。所有这些情况下，git check-ignore -v 一行就能指出真凶。与其靠猜去改模式，不如先敲这条命令。

还有，再说一遍，git rm --cached 只在之后的提交里把文件排除掉。过去的提交里它照旧留着，git show 一行就读得到。要是密码或者密钥进去了，在纠结文件怎么删之前，把那个值作废并重新签发才是第一处置。

未能确认的部分

  • 实验只在 Windows 10 的 Git Bash 和 git 2.48.1.windows.1 上跑过。别的 Git 版本里，输出的措辞可能不同。特别是以 hint: 开头的提示，是随版本变过的部分
  • 区分大小写的文件系统上的行为差异没能直接确认。这是在 Windows 上无法重现的项目
  • 重写历史的工具实际怎么运作、有什么副作用，都排除在范围之外。那是在共享仓库上做的事，验证需要协作环境，恢复也是另一个主题
  • 大型仓库上 git rm -r --cached . 要花多久没有测量。实验仓库的文件数太少，跑不出有意义的数字
