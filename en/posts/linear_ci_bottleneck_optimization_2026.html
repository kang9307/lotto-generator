1. CI Bottlenecks in the Age of AI Coding — Why Tests Multiplied

In contemporary software development organizations, the proliferation of AI coding agents has dramatically accelerated the velocity of writing and shipping code. Generally, tasks that once required extensive manual typing and iterative scaffolding by human engineers are now generated in parallel batches by autonomous coding agents. However, while authoring unit and integration tests has become exponentially faster, the underlying continuous integration (CI) infrastructure responsible for validating those modifications has struggled to expand at the same velocity.

According to an engineering report published by Linear, the creator of the popular project and issue tracking platform, widespread adoption of coding agents beginning in early 2026 triggered an explosive growth in test suite volume. Specifically, Linear reported that its test suites had almost quadrupled since the start of the year, with approximately 2,000 new test cases being added to the repository every single week. Because every pull request (PR) must successfully pass through the CI pipeline before landing in the main branch, this rapid code expansion transformed CI into an acute organizational bottleneck. Developers and agents alike were left waiting for extended intervals to receive feedback on their work.

The original post by Linear engineer Mufeez Amjad recounts how Linear CTO Tuomas assigned him an internal ticket titled "CI costs are high." The assignment was not merely to reduce cloud infrastructure spending, but simultaneously to make CI substantially faster so that engineering momentum would not stall. The operational dilemma confronted by Linear can be categorized into several distinct pressures:

  • An accelerating inflow of automated test code, adding roughly 2,000 tests each week to the existing codebase
  • Escalating cloud runner consumption per pull request, leading to unsustainable operational expenses
  • Prolonged feedback latency that created merge queue gridlock and stalled both human developers and autonomous agents
  • Hardware constraints of default GitHub Actions environments coupled with compounding setup overheads across jobs

In this article's interpretation, attempting to absorb a fourfold increase in automated testing solely by throwing more compute instances at legacy workflows quickly yields diminishing returns. Linear opted instead to examine CI holistically as an interconnected system, systematically re-architecting foundational compute infrastructure, toolchains, critical path dependencies, and test isolation boundaries.

2. Key Performance Metrics and Improvement Summary

When launching the initiative, the Linear team focused on optimizing two primary indicators: the duration of time a pull request waits on CI for completion, and the total runner machine time consumed by each individual test. Achieving meaningful gains across both dimensions while the total volume of tests was nearly quadrupling required structural interventions across every layer of the pipeline.

Empirical metrics shared in the original publication reveal that Linear successfully reduced average pull request wait times from more than 6 minutes down to just over 5 minutes. Simultaneously, the team cut runner machine time per test roughly in half. Had these engineering optimizations not been executed, the team estimated that running the expanded test suite under the original configuration would have required roughly 11 minutes per PR run.

Analyzing these operational results highlights several critical observations regarding pipeline scalability:

  • Total feedback latency decreased even as total test execution load quadrupled, reversing normal pipeline degradation curves.
  • Halving the runner time consumed per individual test prevented cloud infrastructure expenses from ballooning alongside code volume.
  • Unpredictable tail latency and pipeline execution jitter were brought within predictable operational bounds.
  • The performance dividend allowed engineering throughput to remain resilient against further weekly increases in test additions.

To deliver these aggregate outcomes, Linear organized its engineering work into four concrete focus areas: upgrading underlying infrastructure and tooling, optimizing gating jobs that block downstream work, stripping away repeated setup overhead, and maximizing runtime test execution efficiency.

3. Modernizing Infrastructure and Tooling — Third-Party Runners and tsgo

The earliest performance gains realized by Linear required virtually no modifications to the internal logic of their CI workflows. Previously, all CI jobs ran on standard hosted runners provided by GitHub Actions. By migrating their workloads off GitHub Actions to specialized third-party runners equipped with faster modern CPUs, higher-performance storage subsystems, and superior caching infrastructure, Linear provided a significantly more powerful execution environment for identical pipeline jobs.

A like-for-like comparison conducted across the two days on either side of the infrastructure migration revealed that CI jobs ran an average of 34% faster across the board. Workloads characterized by heavy CPU utilization experienced even more dramatic acceleration; notably, TypeScript typechecking jobs (tsc) saw their execution duration drop by 52%. Upgrading raw machine clock speeds and disk I/O throughput provided an immediate baseline lift.

Building upon the infrastructure migration, Linear subsequently addressed the compilation and typechecking layer of its TypeScript codebase. Instead of continuing to rely on the standard Node.js-based tsc compiler for validation, the team adopted tsgo, the native Go-based TypeScript compiler. By replacing the interpreted compiler with a compiled native binary, Linear eliminated significant virtual machine startup latency and garbage collection overhead.

  • Migrated off default GitHub Actions runners to high-speed third-party runners, gaining an immediate 34% average speedup
  • Enhanced hardware specifications reduced pure TypeScript compiler execution time by 52% without pipeline script changes
  • Adopted native Go-based TypeScript compiler tsgo, reducing the weekly median duration of tsc by 73%
  • Successfully removed typechecking as the dominant bottleneck gating total CI completion time

The original post notes that switching to tsgo cut the weekly median duration of the tsc check by 73%. This massive reduction was large enough to shift the primary bottleneck entirely away from typechecking, clearing the way for developers to address other structural inefficiencies in the pipeline.

4. Linting Without the Type Checker — AST Analysis and Oxlint

With typechecking accelerated, code linting quickly emerged as another prominent bottleneck. Linear's codebase relies heavily on TypeScript, and several internal custom lint rules had been written to depend on full TypeScript type information. These rules accessed type metadata either to enforce specific architectural conventions or to apply automated code fixes.

However, requiring type information in even a small handful of lint rules forced ESLint to construct the entire project-wide type graph before any lint evaluation could begin. Consequently, linting became one of the most memory-intensive and slowest jobs in Linear's entire continuous integration matrix, consuming extensive runner time on every push.

To eliminate this overhead, Linear rewrote its custom lint rules using pure static analysis over the abstract syntax tree (AST). Instead of querying the compiler's semantic type system, the rewritten rules identified function-like constructs and guard expressions through structural syntactic inspection. This architectural change allowed ESLint to decouple completely from the TypeScript type checker.

  • Rewrote type-dependent custom ESLint rules to rely solely on AST structural syntax matching
  • Eliminated the mandatory full-project type graph generation phase, dramatically lowering runner memory usage
  • Reduced API package linting time by 68% and full-repository linting time by 55%
  • Created clean syntax-only rules that enabled a frictionless migration to the ultra-fast Rust-based linter Oxlint

According to the original post, removing the type checker dependency reduced API lint time by 68% and trimmed full-repository lint time by 55%, alongside substantial reductions in memory consumption. Furthermore, because the rewritten rules operated purely on syntax, Linear was later able to migrate seamlessly to Oxlint, a high-performance linter built in Rust, reducing runner-minutes dedicated to linting even further.

5. Optimizing Critical Path Gating Jobs — Checkout and Cache Markers

Having accelerated individual compilation and linting tasks, Linear broadened its focus to examine workflow scheduling across the entire CI system. In particular, attention turned to small prerequisite jobs positioned at the very front of the pipeline. In Linear's setup, every workflow begins with change-detection jobs that inspect which files a PR has modified and verify whether identical inputs have already passed testing.

While these gating checks prevent unnecessary downstream jobs from provisioning runners, they sit directly on the critical path. None of the parallel API test shards can begin execution until the change-detection step concludes. Linear discovered that these early jobs were performing full checkouts of the complete working tree despite needing only a tiny fraction of the repository. By capping the git fetch depth, the team reduced the slowest of these gating jobs from 94 seconds down to 20 seconds.

For jobs that never required a working tree at all, checkout was eliminated entirely, dropping execution from 27 seconds to 7 seconds. For commit push and merge-queue events requiring path diffing, implementing a sparse, blobless checkout with limited history saved an additional 11 seconds. In total, the median duration of change-detection jobs fell from 26 to 8 seconds, and p90 duration dropped from 31 to 12 seconds.

Following the third-party runner migration, Linear noticed that standard actions/checkout steps occasionally experienced extended stalls or hangs due to intermittent network link degradation between the runner provider and GitHub. Because early workflows stalled on checkout, entire runs were delayed. To build resilience, Linear replaced actions/checkout with a custom composite action featuring exponential backoff retries, configured GIT_HTTP_LOW_SPEED_LIMIT and GIT_HTTP_LOW_SPEED_TIME to abort hanging connections after roughly 30 seconds, and utilized sticky disk checkout caches keeping persistent git mirrors.

  • Capped git fetch depth on change-detection jobs, slashing critical gate latency from 94 to 20 seconds
  • Eliminated checkout steps entirely from jobs requiring no working tree, reducing runtime from 27 to 7 seconds
  • Engineered a custom checkout action with backoff retries and 30-second low-speed abort limits to counter network stalls
  • Implemented sticky disk git mirror caching to ensure critical path jobs never sit idle waiting on git fetches
  • Moved cache marker writes out of the merge gate into non-blocking parallel jobs, shaving 42 seconds off merge paths

A final critical path optimization targeted the merge queue. Linear had previously written cache markers as part of the final gating check before merging, forcing PRs to linger in the merge queue even after their tests had passed. Moving the cache marker write into an independent non-gating job that executes after test shards finish shaved 42 seconds directly from the merge path for every API pull request.

6. Reducing Repeated Setup — Base Images, pnpm Filtering, and DB Snapshots

In complex CI workflows, jobs that perform only a few seconds of actual computation frequently spend multiple minutes booting runners, configuring runtimes, and downloading dependencies. Linear systematically audited this repeated setup tax across its pipeline to minimize redundant preparation time.

First, each API test shard had been spending 7 to 8 seconds installing the PostgreSQL client via apt on every single run. Linear eliminated this overhead by building a lightweight custom CI base image containing Node.js and the preinstalled Postgres client, allowing shards to start immediately in a ready-to-run environment. Required native build headers were also baked into the image after discoveries showed that downloading them at runtime occasionally stalled.

Second, Linear refined dependency installation within its pnpm monorepo workspace. Previously, API test workflows installed the entire monorepo workspace despite only requiring the API package and its direct dependencies. Restricting the installation scope exclusively to the API package reduced pnpm install duration from 44-73 seconds down to 16-18 seconds, while preventing unnecessary dependency cache uploads.

Third, the team critically evaluated their node_modules caching strategy and determined that rebuilding was faster than restoring caches. Because cache keys depended on a frequently shifting lockfile, even a cache hit required roughly 28 seconds to unpack and restore, compared to only 7.5 seconds for a filtered fresh install. Caching node_modules added upload overhead and duration variance without providing any tangible advantage, leading Linear to abandon it.

  • Created a custom base container image pre-populated with Node.js, Postgres clients, and native build headers
  • Restricted pnpm workspace dependency installation strictly to targeted packages, cutting install time from 44-73s to 16-18s
  • Eliminated node_modules caching after benchmarks proved filtered installs (7.5s) were much faster than cache restores (28s)
  • Replaced full database migration replays with pre-generated schema snapshots, reducing DB boot time from 12s to 1-2s
  • Consolidated 7 short standalone verification jobs into 2 concurrent runner workflows, saving ~87,000 runner-minutes monthly

Fourth, Linear optimized database provisioning by removing redundant migration replays. Previously, API test containers replayed the entire historical database migration sequence on every run even when schema files remained untouched. Switching to pre-generated schema snapshots and bootstrap files reduced database setup from roughly 12 seconds to 1-2 seconds per container. Finally, consolidating 7 independent micro-checks into 2 consolidated jobs running parallel tasks reduced duplicate setup cycles, saving approximately 87,000 runner-minutes per month (11.8% of total CI volume).

7. Efficient Test Execution — 8-Way Sharding and isolate: false

Because the fixed setup overhead per test shard had been compressed from 110-140 seconds down to roughly 40 seconds, Linear could finally afford to parallelize its extensive API test suite across more shards without multiplying setup costs. In earlier configurations, doubling shards would have doubled setup machine time, but lean containers made aggressive sharding economically viable.

Vitest, the test runner utilized by Linear, assigns test execution by file rather than by the duration of individual test functions. Consequently, a small number of oversized test files had previously monopolized individual shards and held up entire test runs while other shards sat idle. Linear resolved this by splitting disproportionately large files into smaller, modular test suites without changing test semantics.

After rebalancing files, Linear expanded its API test matrix from 4 shards to 8 shards. In initial benchmarks, this change made the critical API test job roughly 19% faster while decreasing overall compute cost by 19%. Within one week of deployment, the duration of the slowest shard dropped from 5.25 minutes to 4.33 minutes. Running 8 shards with optimized 40-second setup consumed only 7.5 minutes of total setup time across all workers, whereas 4 shards had previously consumed 8.3 minutes on setup alone.

The single most impactful optimization implemented was the introduction of shared module state. Normally, Vitest strictly isolates each test file, forcing every worker to re-instantiate entity models, GraphQL schemas, and decorator metadata graphs from scratch. Linear introduced an opt-in project configuration leveraging isolate: false, allowing eligible test files to share a cached module registry within each worker process.

To protect against test pollution, eligibility was enforced via explicit opt-in header comments and rigorous teardown routines. Furthermore, because AI agents author the vast majority of Linear's new tests, the team updated their internal agent coding skills so generated tests follow these isolation rules automatically.

8. Optimizing as a System — Compounding Improvements Across Workflows

The primary architectural takeaway from Linear's CI restructuring is that meaningful pipeline acceleration cannot be achieved through isolated, single-parameter tweaks. Infrastructure upgrades established a performant foundation; compiler and linter refactoring removed CPU and memory bottlenecks; and pruning checkout and setup latency made downstream parallelization cost-effective. Each sequential improvement amplified the efficacy of the next.

Had the engineering team attempted to jump directly to 8-way sharding without first reducing the 110-140 second per-shard setup overhead, the pipeline would have squandered 15 to 19 minutes of machine time solely on initialization, exceeding the duration of the tests themselves. Prior setup reductions lowered the marginal cost of concurrency, enabling parallel test execution to deliver genuine compounding dividends.

In modern engineering environments where AI agents continuously generate substantial code volumes, continuous integration serves as the critical constraint on organizational throughput. Linear continues to expand its codebase by approximately 2,000 tests each week, utilizing the holistic profiling methodology established during this initiative to systematically identify and resolve emerging bottlenecks as they arise.

  • Addressed CI holistically across infrastructure, toolchains, gating dependencies, setup, and execution
  • Compressed fixed per-shard setup overhead before expanding sharding to ensure concurrency remained cost-efficient
  • Synchronized AI agent prompting skills with CI architectural constraints to sustain performance at scale
  • Relied on empirical profiling data to target true critical path bottlenecks rather than speculative micro-optimizations

In this article's interpretation, engineering teams seeking to accelerate delivery through AI code generation must invest commensurately in the scalability of their testing and validation pipelines. Linear's experience demonstrates that modern tooling coupled with disciplined systems engineering allows high-velocity engineering teams to maintain short feedback loops and predictable costs, even in the face of exponential test volume growth.
