はじめに: 片付けコードは最終行にあり、スクリプトはそこまで行けなかった

一時ディレクトリを作って中間成果物を積み、使い終わったら最終行で消すスクリプトがあるとする。普段は何の問題もない。問題は普段でないときに起きる。入力ファイルがなくて途中でexit 1で抜けたり、デプロイ中にCIがジョブをキャンセルしたり、誰かがターミナルでCtrl+Cを押したりする。そのたびに片付けコードは実行されない。その行まで到達していないのだから。

こうした残骸は静かに積もる。一つ200MBの作業ディレクトリが一日に数個残れば、数週間後にはディスク警告になって返ってくる。そのとき残ったディレクトリを開いても、いつどの実行から出たものかを知るのは難しい。

trapはこの問題を正面から扱う道具だ。片付けコードを「最後に実行する行」ではなく「シェルが終わるときに必ず実行するコード」として登録する。ただしこの文には例外がいくつも付く。捕まる終わり方と捕まらない終わり方があり、シェルによって結果が分かれ、書き方を誤ると消してはいけないものを消す。

この記事のコマンドと出力はGNU bash, version 5.2.37(1)-releaseとdashでそのまま走らせて得たものだ。消すコマンドはすべて/tmp配下のmktempで作ったパスに対してだけ実行した。シェルの基礎が必要ならシェルスクリプト基礎とシェルスクリプト上級が先だ。

1. どう終わっても消させる一行

基本形は短い。一時ファイルを作り、そのファイルを消すコマンドをEXITに登録する。

#!/usr/bin/env bash
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'rm -f "$tmp"' EXIT

EXITはシグナルではなくシェルが終了する瞬間を指す仮の名前だ。だから正常終了でもexit 1でもset -eに引っかかった失敗でも、すべてこの地点を通る。三つの経路をそれぞれ走らせて確認した結果だ。

$ bash t1.sh ok
created: /tmp/work.Z8kaai
doing work
[trap] cleaning /tmp/work.Z8kaai
exit=0

$ bash t1.sh fail            # スクリプト途中の exit 1
created: /tmp/work.af0aeI
about to exit 1
[trap] cleaning /tmp/work.af0aeI
exit=1

$ bash t1.sh err             # set -e の状態でコマンドが一つ失敗
created: /tmp/work.cLzp5n
about to run a failing command
[trap] cleaning /tmp/work.cLzp5n
exit=1

三つとも ハンドラが動き、終了コードも元の値が保たれた。ここまでがtrapが確実にやってくれることだ。

1.1 シングルクォートとダブルクォートで結果が変わる

トラップの本体は登録するときに一度、発動するときに一度解釈される機会がある。どちらで変数が展開されるかがクォートで分かれる。

$ tmp=/tmp/first
$ trap "echo [double] would remove $tmp" EXIT   # ダブル: 今すぐ展開
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[double] would remove /tmp/first

$ tmp=/tmp/first
$ trap 'echo "[single] would remove $tmp"' EXIT # シングル: 発動時に展開
$ tmp=/tmp/second
$ echo "tmp is now $tmp"
tmp is now /tmp/second
[single] would remove /tmp/second

ダブルクォート側は登録時点の値/tmp/firstを消そうとする。一時パスがあとで決まったりループで変わったりするスクリプトなら、この差がそのまま事故になる。

  • トラップの本体はシングルクォートで囲むのを基本にする
  • 本体が一行を超えたら関数に出してtrap cleanup EXITのように名前だけ登録する。クォートの悩みが消える
  • 関数に出すとtrap -pで確認するときも登録内容が短く、読みやすい
  • デバッグ用に値を固定したいときだけ意図的にダブルクォートを使う

2. Ctrl+Cで切ったのに一時ファイルが残る理由

ここからが実際に分かれる部分だ。EXITだけを掛けたスクリプトをシグナルで殺すとどうなるか。スクリプトが自分自身にシグナルを送るようにして確認した。

$ cat t4.sh
tmp=$(mktemp /tmp/work.XXXXXX)
trap 'echo "[EXIT trap] rm $tmp"; rm -f "$tmp"' EXIT
kill -"$1" $$
sleep 5
echo "SURVIVED the signal"

$ bash t4.sh INT
pid=1349 tmp=/tmp/work.ZaHJMi  sending SIGINT to self
[EXIT trap] rm /tmp/work.ZaHJMi
exit=130 tmpfile=cleaned

$ bash t4.sh TERM
[EXIT trap] rm /tmp/work.By1Y9n
Terminated
exit=143 tmpfile=cleaned

bashではEXITだけでもSIGINT・SIGTERM・SIGHUPでハンドラが動いた。終了コードも130と143で正確だ。128にシグナル番号を足した値である。

2.1 ところがdashでは動かない

同じスクリプトをdashで走らせると結果がひっくり返る。

$ bash /tmp/d2.sh          # EXIT トラップだけ登録、自分に SIGTERM
[EXIT] rm /tmp/work.LJpwWB
Terminated
  rc=143
  cleaned

$ dash /tmp/d2.sh
Terminated
  rc=143
  LEFTOVER /tmp/work.skxk0l

dashはハンドラをまったく実行せずファイルを残した。シバンが#!/bin/shのスクリプトは配布先でdashとして実行されることが珍しくない。開発機で/bin/shがbashにつながっていると、この差は見えない。本番に上げてから残骸が積もり始める。

2.2 シグナルを明示すればdashも片付ける

直す方法はEXITの隣にシグナルを並べることだ。

cleanup() { rm -f "$tmp"; }
trap cleanup EXIT
trap 'cleanup; trap - INT;  kill -INT  $$' INT
trap 'cleanup; trap - TERM; kill -TERM $$' TERM
trap 'cleanup; trap - HUP;  kill -HUP  $$' HUP
$ dash /tmp/d3.sh
[cleanup] rm /tmp/work.Gjy9y6
Terminated
  rc=143
  cleaned

ハンドラがtrap - INTで自分のトラップを解除したあと同じシグナルで自分を撃ち直す部分が重要だ。そのままexit 0で終わらせると、呼び出した側からは成功したように見える。

$ cat /tmp/reraise2.sh
trap 'echo "[INT] cleaning"; exit 0' INT
kill -INT $$

$ bash /tmp/reraise2.sh
[INT] cleaning
rc=0        # 中断されたのに成功として報告される

$ bash /tmp/reraise.sh      # 片付け後に同じシグナルで再発生
pid=587 tmp=/tmp/work.QAJTr9
rc=130      # 128+2、呼び出した側が期待する値

CIランナーや上位スクリプトはこの終了コードで「キャンセル」と「失敗」と「成功」を区別する。片付けをきちんとやっておいて終了コードを壊すと、上位の判断が狂う。

3. シグナルごとに何が動いて何が動かないのか

同じスクリプトを二通りに武装させ、シグナルを一つずつ送って表にまとめた。Aはtrap ... EXITだけ、BはEXITにINT TERM HUP QUITを足したものだ。

シグナル番号A: EXITのみB: EXIT+シグナル終了コード備考
SIGINT2片付く片付く130Ctrl+Cが送るもの
SIGTERM15片付く片付く143killの既定値
SIGHUP1片付く片付く129端末の切断
SIGQUIT3スクリプトが生き残るハンドラは動くが続行0非対話bashは既定で無視
SIGKILL9残骸が残る残骸が残る137捕まえられない

表ではAとBが同じに見えるがこれはbashの話だ。2節で見たようにdashではAが崩れる。移植性を考えるならBが基本形になる。

3.1 SIGQUITは既定で無視される

表の中で一つだけ浮いている行だ。非対話のbashスクリプトはトラップを掛けていないときSIGQUITを無視する。

$ cat /tmp/q2.sh
echo "no trap armed; sending QUIT to self"
kill -QUIT $$
echo "survived"

$ bash /tmp/q2.sh
no trap armed; sending QUIT to self
survived
rc=0

トラップを掛ければハンドラ自体は動く。ただしハンドラがexitをしなければスクリプトはそのまま進む。

$ bash /tmp/q1.sh
armed; sending QUIT to self
[QUIT handler] ran
survived (handler did not abort the script)
rc=0

dashでも同じ結果が出た。実務でSIGQUITを直接扱うことは少ないが、「トラップを掛けたのだからスクリプトは止まるだろう」という前提が外れうる例としては有用だ。ハンドラが動くこととスクリプトが終わることは別だ。

4. kill -9で死ぬと正確に何が残るのか

SIGKILLはプロセスに配送されない。カーネルがプロセスを直接消すのでシェルがコードを実行する機会そのものがない。64KBのファイルを5個作った作業ディレクトリをkill -9で切り、残ったものを数えてみた。

$ bash /tmp/leftover.sh &
$ sleep 1; kill -9 $!
$ du -sh /tmp/work.yURWz1; ls -1 /tmp/work.yURWz1
320K    /tmp/work.yURWz1
    chunk.1
    chunk.2
    chunk.3
    chunk.4
    chunk.5

トラップはEXIT INT TERM HUPにすべて掛かっていたが、何一つ動かなかった。

4.1 bashはKILLにトラップを掛けることを止めない

ここが本当の落とし穴だ。構文エラーで拒否してくれればいいのだが、そうはならない。

$ bash -c 'trap "echo caught" KILL; trap -p'
trap -- 'echo caught' SIGKILL
rc=0

trap -pの一覧にSIGKILLの項目が堂々と表示される。コードレビューでtrap cleanup EXIT INT TERM KILLのような行を見るとKILLまで塞いであるように読めるが、その位置は何もしない。むしろ実体のない安心感を作る。

4.2 だから対策はプロセスの外側に置く

  • 一時パスに固定の接頭辞を付ける。mktemp -d /tmp/myjob.XXXXXXのように作れば、あとで何が残ったかが一目で分かる
  • 別の掃除ジョブがその接頭辞の古いものを定期的に回収するようにする。最終更新時刻で絞れば実行中のものには触らない
  • 本当に大きな成果物なら/tmpではなく容量に余裕のある別ボリュームを使う。残骸が他のサービスを殺さないようにする
  • SIGKILLが来る経路をまず減らす。コンテナのオーケストレータやサービス管理者はたいてい停止猶予時間を超えるとKILLに上がる。片付けがその時間内に終わるようにすればKILLを見ること自体が減る
  • 片付けに数十秒かかる構造なら片付けを減らすほうが正しい。猶予時間を延ばすのはその次だ

5. 片付けを二つ掛けたのに一つしか動かない理由

同じシグナルにトラップを二回掛けると後から掛けたものが前のものを上書きする。積み上がらない。

$ bash -c 'trap "echo first" EXIT; trap "echo second" EXIT; echo body'
body
second

エラーも警告も出ない。関数が二つそれぞれ自分の一時ファイルをEXITに登録しておくと、あとから呼ばれた側だけが生き残り、前の片付けは静かに消える。ライブラリ的なスクリプトをsourceで読み込む構造で特によく起きる。

5.1 片付け項目を積んでおいて一度に実行する

_cleanups=()
add_cleanup() { _cleanups+=("$1"); }
_run_cleanups() {
    for ((i=${#_cleanups[@]}-1; i>=0; i--)); do eval "${_cleanups[i]}"; done
}
trap _run_cleanups EXIT

add_cleanup "echo remove file A"
add_cleanup "echo remove dir B"
add_cleanup "echo release lock C"
$ bash /tmp/stack.sh
body
release lock C
remove dir B
remove file A

登録の逆順で回るのが肝だ。ロックを先に取ってディレクトリをあとで作ったなら、解放はディレクトリから消してロックを最後に外すのが正しい。

5.2 既存のハンドラの後ろにつなげる方法

すでに別の場所でトラップを掛けている状況ならtrap -pで読んでつなげられる。

add_exit() {
    local prev new
    prev=$(trap -p EXIT)
    prev=${prev#trap -- \'}
    prev=${prev%\' EXIT}
    if [ -z "$prev" ]; then new="$1"; else new="$prev; $1"; fi
    trap "$new" EXIT
}
$ bash /tmp/a1.sh
captured: trap -- 'echo first-handler' EXIT
now armed as: trap -- 'echo first-handler; echo second-handler; echo third-handler' EXIT
body
first-handler
second-handler
third-handler

動きはするが二つのことを覚悟する必要がある。第一に、ハンドラ文字列にシングルクォートが入っていると上の文字列切り出しがずれる。第二に、trap -pはbash拡張なのでdashでは使えない。

$ dash -c 'trap "echo x" EXIT; trap -p'
dash: 1: trap: Illegal option -p

dashで引数なしのtrapだけを打てば一覧は出る。ただしそれをパースして戻す方式はクォート処理がさらに厄介だ。移植性が要るなら5.1の配列方式のほうがよい。

$ bash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' SIGINT

$ dash -c 'trap "echo a" EXIT INT; trap'
trap -- 'echo a' EXIT
trap -- 'echo a' INT

bashはSIGINT、dashはINTと書く。出力を機械的に比較する検査器を作るならこの差に引っかかる。

5.3 トラップを消す方法

trap - EXIT       # 既定の動作に戻す
trap '' INT       # 無視させる (解除とは違う)

二つ目の形には副作用がある。無視に設定されたシグナルは子プロセスに継承され、子はそれを戻せない。

$ cat /tmp/ig.sh
trap '' INT
bash -c 'trap "echo child handler" INT; trap -p INT'

$ bash /tmp/ig.sh
trap -- '' SIGINT

子がtrap "echo child handler" INTを実行したのに一覧では空文字列、つまり無視のままだ。親が無視で渡したシグナルを子が捕まえ直すことはできない。スクリプトが別のコマンドを包んで実行するラッパーなら、この継承がそのコマンドのCtrl+C応答を奪う。

6. サブシェル・バックグラウンド・関数でトラップはどこまで追うか

パイプと括弧がプロセスをもう一つ作るという話はパイプの中のwhileで変数が消える理由で扱った。トラップはその境界で変数とはまた違う動きをする。

6.1 サブシェルはトラップを受け継ぐが自分の終了では発動しない

$ cat /tmp/sub_t.sh
trap 'echo "[EXIT] fired in BASHPID=$BASHPID"' EXIT
echo "parent BASHPID=$BASHPID"
( echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t.sh
parent BASHPID=340
  inside subshell BASHPID=341
subshell rc=3
[EXIT] fired in BASHPID=340

サブシェルは別プロセス(341)でexit 3で終わったのに、ハンドラは親(340)で一度だけ動いた。同じ片付けが二回実行されることを心配する必要はない。逆にサブシェルの中だけで使う一時ファイルがあるなら、その中で別に掛ける必要がある。

$ cat /tmp/sub_t2.sh
trap 'echo "[parent EXIT] BASHPID=$BASHPID"' EXIT
( trap 'echo "  [subshell EXIT] BASHPID=$BASHPID"' EXIT
  echo "  inside subshell BASHPID=$BASHPID"; exit 3 )
echo "subshell rc=$?"

$ bash /tmp/sub_t2.sh
  inside subshell BASHPID=344
  [subshell EXIT] BASHPID=344
subshell rc=3
[parent EXIT] BASHPID=343

サブシェルの中で登録したトラップはサブシェルが終わるときにその中で動き、親のトラップは親が終わるときに別に動く。互いに干渉しない。

6.2 バックグラウンドも同様で、パイプラインの内側は外に出ない

$ bash /tmp/sub_t3.sh
parent BASHPID=346
  bg BASHPID=347
parent done
[EXIT] fired in BASHPID=346
$ bash /tmp/a2.sh
echo x | { trap 'echo "[inner EXIT]"' EXIT; cat > /dev/null; }
[inner EXIT]
parent continues
parent trap -p EXIT output:
(nothing between the two lines = the parent has no EXIT trap)

パイプライン構成要素の中で掛けたトラップはその構成要素が終わるときに動き、親には残らない。スクリプト本体でトラップを掛けたのに動かないようなら、その行がパイプの右側や括弧の中にあるかをまず見る。

6.3 関数の中で掛けたトラップは関数を出ても生きている

$ bash -c 'f() { trap "echo [EXIT] set inside f" EXIT; echo "in f"; }; f; echo "after f"'
in f
after f
[EXIT] set inside f

EXITトラップはシェル全体の状態だ。関数ローカルではない。関数が自分の一時ファイルを片付けようとEXITに登録すると、その登録はスクリプトが終わるまで残り、他の関数の登録を上書きする。5節の問題と同じ根だ。

6.4 ERRとRETURNはオプションを入れないと内側まで届かない

ERRトラップはコマンドが失敗したときに動くが、既定の設定では関数・サブシェル・コマンド置換の内側には入らない。

$ bash -c 'set -e; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
rc=1                       # ハンドラが動かなかった

$ bash -c 'set -eE; trap "echo [ERR] caught" ERR; h() { false; }; h; echo "NOT REACHED"'
[ERR] caught
rc=1

set -Eを入れて初めてERRが関数の中まで継承される。RETURNとDEBUGトラップはset -Tが同じ役割をする。

$ bash -c 'trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g

$ bash -c 'set -T; trap "echo [RETURN]" RETURN; g() { echo "in g"; }; g'
in g
[RETURN]

発動の順序も確認しておいた。失敗が起きるとERRが先、EXITがあとだ。

$ bash -c 'trap "echo [ERR]  seen" ERR; trap "echo [EXIT] seen" EXIT; set -e; false'
[ERR]  seen
[EXIT] seen
rc=1

ERRはどこで失敗したかを記録するのに使い、実際の片付けはEXITに置く配置が自然だ。そしてERR・RETURN・DEBUGはすべてbash拡張である。

$ dash -c 'trap "echo err" ERR; false; echo done'
trap: ERR: bad trap
done

$ dash -c 'trap "echo ret" RETURN; f(){ :; }; f'
trap: RETURN: bad trap

7. 消してはいけないものを消させない防御

先に読むこと。この節の内容は後の節の例より先に適用しなければならない。片付けスクリプトは書き方を誤ると消してはいけないものを消す。削除は取り消せず、スクリプトが消したファイルはゴミ箱に行かない。以下の三つの防御を付ける前に、rm -rfの入ったトラップを実データのある機械に上げないほうがよい。

7.1 変数が空ならその場で止める

トラップはスクリプトのどの地点でも発動する。一時パス変数に値が入る前にシグナルが来る場合が実際にある。その状態で削除コマンドがそのまま実行されると、対象が何になるかを予測できない。

cleanup() {
    : "${workdir:?cleanup called with no workdir}"
    ...
}

:は何もしない組み込みコマンドで、${var:?メッセージ}は変数が空ならメッセージを出してその場でシェルを止める展開だ。二つを合わせると値の検査だけをする一行になる。

$ bash -c 'cleanup() { : "${workdir:?cleanup called with no workdir}"; echo "would remove $workdir"; }
trap cleanup EXIT
echo body'
body
environment: line 2: workdir: cleanup called with no workdir

削除の行まで行けずに止まった。この一行がないと何が起きるかは走らせずに説明だけする。rm -rf -- "$workdir"は変数が空なら引数が空文字列になってたいていエラーで終わるが、よく使われる次の形は違う。

  • rm -rf "$workdir"/* — 変数が空だと/*になる。ルート直下のすべてが対象になる
  • rm -rf "$base/$sub" — どちらか一方が空でも残ったスラッシュのせいで意図より一段上が消える
  • cd "$workdir" && rm -rf . — cdが失敗すると現在のディレクトリで実行される。&&があってもcdが成功してパスが見当違いならそのまま進む
  • rm -rf $workdir — クォートがないとパスに空白があるとき複数の引数に割れる。先頭の断片だけが存在するディレクトリならそれが消える

この四つはどれも試しに走らせてみる性質のものではない。防御を先に入れて、そのあとで削除の行を書く。

7.2 パスを固定する

値があるだけでは足りない。値が想定した形かも見る。

cleanup() {
    : "${workdir:?}"
    case "$workdir" in
        /tmp/myjob.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
        *)            echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
    esac
}
$ bash /tmp/guarded.sh
workdir=/tmp/work.nGJBt5
removed /tmp/work.nGJBt5
rc=0

接頭辞が違えば消さずに警告だけ残す。スクリプトを直しているうちにworkdirに別の値が入る失敗をしても、削除は起きずログに痕跡が残る。

7.3 トラップを先に掛けて、そのあとで作る

順序が逆になったコードはよくある。

# 脆い順序: 二行の間で死ぬとファイルが残る
tmp=$(mktemp /tmp/work.XXXXXX)
... 準備作業 40行 ...
trap 'rm -f -- "$tmp"' EXIT

間が短く見えても、その区間でシグナルが来れば残骸がそのまま残る。逆にすればよい。

tmp=
cleanup() { [ -n "$tmp" ] && rm -f -- "$tmp"; echo "[cleanup] handled tmp=[$tmp]"; }
trap cleanup EXIT
tmp=$(mktemp /tmp/work.XXXXXX)
$ bash /tmp/race2.sh
trap armed before anything exists
created /tmp/work.35mmxL
[cleanup] handled tmp=[/tmp/work.35mmxL]

$ bash /tmp/race3.sh        # mktemp の前に終了
[cleanup] handled tmp=[]
rc=1

まだ何も作っていない状態で死んでも、ハンドラが静かに何もせずに終わる。tmp=であらかじめ宣言しておくことがset -uの環境では特に重要だ。

$ bash -c 'set -u; cleanup() { echo "rm -rf -- \"$workdir\""; }; trap cleanup EXIT; echo body'
body
environment: line 3: workdir: unbound variable

7.4 取り消せない地点

  • 削除が始まったあとは中断しても無意味だ。rm -rfが半分ほど進んだ状態でCtrl+Cを押しても、すでに消えたものは戻らない
  • 一時ディレクトリに原本を移しておく設計は危険だ。コピーではなく移動で入れたなら、片付けトラップが原本を消すトラップになる
  • 片付け対象がシンボリックリンクでありうる構造ならリンクを辿るかを確認する。リンク自体を消すつもりが、リンクの指す実データを消すことがある
  • ネットワークファイルシステムや共有ボリュームを一時領域に使うと他のプロセスが同じパスを使っている可能性がある。接頭辞にプロセス識別子を入れて衝突しないようにする
  • 片付けのロジックを変えたら削除の行をechoに変えて一度走らせる。どのパスが対象になるかを目で確認してから実際の削除に戻す
  • 本番機に初めて上げるときはrmではなくmvで隔離ディレクトリに移す方式で数日回す。想定外のパスが引っかかるかがその期間に見える

8. ディレクトリごと使ってディレクトリごと消す

ファイル一つではなく複数を作る作業なら、mktemp -dでディレクトリを一つ取ってその中ですべて処理するほうがよい。片付け対象が一つに減る。

#!/usr/bin/env bash
set -euo pipefail

workdir=
_cleaned=0

cleanup() {
    [ "$_cleaned" -eq 1 ] && return
    _cleaned=1
    trap '' INT TERM HUP
    if [ -n "$workdir" ] && [ -d "$workdir" ]; then
        case "$workdir" in
            /tmp/job.*) rm -rf -- "$workdir" && echo "[cleanup] removed $workdir" ;;
            *)          echo "[cleanup] refusing to remove unexpected path: $workdir" >&2 ;;
        esac
    else
        echo "[cleanup] nothing to remove"
    fi
}

on_signal() {
    local sig=$1
    echo "[signal] SIG$sig received" >&2
    cleanup
    trap - "$sig" EXIT
    kill -"$sig" "$$"
}

trap cleanup EXIT
for s in INT TERM HUP; do trap "on_signal $s" "$s"; done

workdir=$(mktemp -d /tmp/job.XXXXXX)
echo "workdir=$workdir"

printf 'row1\nrow2\nrow3\n' > "$workdir/input.txt"
wc -l < "$workdir/input.txt"

三つの経路すべてを走らせて確認した。

$ bash job.sh ok
workdir=/tmp/job.QoSGZJ
rows: 3
work finished
[cleanup] removed /tmp/job.QoSGZJ
rc=0
verified: /tmp/job.QoSGZJ gone

$ bash job.sh fail
workdir=/tmp/job.aHj3Nw
rows: 3
failing on purpose
[cleanup] removed /tmp/job.aHj3Nw
rc=1
verified: /tmp/job.aHj3Nw gone

$ bash job.sh signal
workdir=/tmp/job.ipwR33
rows: 3
signalling myself
[signal] SIGINT received
[cleanup] removed /tmp/job.ipwR33
rc=130
verified: /tmp/job.ipwR33 gone

このテンプレートに入れた要素を一つずつ挙げるとこうなる。

  • workdir=を先に宣言し、トラップを掛けてからmktemp -dを呼ぶ (7.3)
  • _cleanedフラグで片付けが二度回らないようにする (10節)
  • 片付け開始時にtrap '' INT TERM HUPで追加のシグナルを塞ぐ
  • caseでパスの接頭辞を確認する (7.2)
  • シグナルハンドラは片付け後に同じシグナルで自分を撃ち直し終了コードを保つ (2.2)
  • local sig=$1でハンドラが自分の引数を受け取るようにし、シグナル名ごとに別の関数を書かずに済ませる

8.1 子プロセスも一緒に片付ける

バックグラウンドで上げた作業があるなら、ディレクトリを消すだけでは足りない。消えたパスを使い続けようとする孤児プロセスが残る。

cleanup() {
    echo "[cleanup] killing $(jobs -p | wc -l) background job(s)"
    jobs -p | while read -r p; do kill "$p" 2>/dev/null; done
    : "${workdir:?}"
    rm -rf -- "$workdir"
}
$ bash /tmp/kids.sh
running with 2 children
[cleanup] killing 2 background job(s)
[cleanup] workdir removed
workdir gone: /tmp/work.47Wiqu

順序が重要だ。子を先に殺してディレクトリを消す。逆にすると子が消えたパスに書き込んでエラーログを吐き出す。

9. set -eと一緒に使うときにずれる地点

set -eが入ったスクリプトでトラップハンドラはどうなるか。ハンドラの中で失敗が起きたら残りの片付けはどうなるか。ここから確認した。

$ bash -c 'trap "echo [EXIT] start; false; echo [EXIT] still running; echo [EXIT] done" EXIT; echo body'
body
[EXIT] start
[EXIT] still running
[EXIT] done
outer rc=0

ハンドラ途中の失敗は残りを止めず、終了コードも変わらなかった。ところがハンドラの中でset -eを入れると話が変わる。

$ bash -c 'cleanup() { set -e; echo "[cleanup] step 1"; false; echo "[cleanup] step 2 - NOT REACHED"; }
trap cleanup EXIT
echo body'
body
[cleanup] step 1
outer rc=1

2段目が実行されなかった。片付け関数の中で最初の削除が失敗すると、二つ目の削除とロック解除がまるごと飛ばされる。終了コードも1に変わって元の結果を上書きした。

  • 片付け関数の中ではset -eを入れない。片付けは失敗しても最後まで試すべき性質のコードだ
  • スクリプト冒頭のset -eは関数の中まで有効なので、片付け関数の一行目にset +eを入れるのが安全なこともある
  • 個別コマンドの失敗を吸収するならrm -fのように無くても成功するオプションを使うか|| trueを付ける
  • 失敗は無視しつつ記録は残したいなら|| echo "..." >&2の形で代える

9.1 ハンドラの中のexitが終了コードを上書きする

$ bash -c 'trap "echo [EXIT] handler; exit 99" EXIT; exit 3'
[EXIT] handler
rc=99

$ bash -c 'trap "echo [EXIT] handler" EXIT; exit 3'
[EXIT] handler
rc=3

ハンドラがexitを呼ばなければ元の終了コードがそのまま保たれる。片付けハンドラにexit 0を習慣で付けると、失敗した実行が成功として報告される。自動化パイプラインでこれより悪い欠陥は少ない。

9.2 execはトラップを連れて行かない

$ bash -c 'trap "echo [EXIT] should not print" EXIT; echo before-exec; exec echo after-exec'
before-exec
after-exec

execはシェルのプロセスを別のプログラムで置き換える。置き換わったあとはそのシェルが存在しないのでEXITトラップも消える。コンテナのエントリポイントスクリプトが最後にexecで本体のプログラムを起動する構造なら、その手前で掛けておいた片付けトラップは決して動かない。

10. 片付けの最中にまたCtrl+Cが来たら

片付けに2秒かかる状況で1秒間隔でSIGINTを三回送ってみた。防御のないハンドラだ。

$ bash /tmp/reenter.sh
start (05)
  [cleanup] enter  (06)
  [cleanup] enter  (08)      <-- 前の片付けが終わっていないのにまた入った
  [cleanup] leave  (10)
  [cleanup] leave  (10)
end (16)

enterが二回続けて出た。片付けコードが自分自身の中で入れ子に実行された。この状態で実際に何が起きるか。

  • 同じディレクトリを二回消そうとする。二度目は対象がなくエラーを出す
  • ロック解除が二回回ると、二度目の解除が次の実行がいま取ったロックを外してしまうことがある
  • カウンタを戻したりログを整理したりするコードなら二回適用されて値がずれる
  • 入れ子の内側が先に終わってexitを呼ぶと、外側の片付けが半分だけ実行された状態でプロセスが消える

10.1 フラグとシグナル遮断を一緒に使う

_cleaned=0
cleanup() {
    [ "$_cleaned" -eq 1 ] && { echo "  [cleanup] already done, ignoring"; return; }
    _cleaned=1
    trap '' INT TERM HUP      # 片付けの間はシグナルを無視する
    ...
}
$ bash /tmp/reenter2.sh
start (17)
  [cleanup] enter  (18)
  [cleanup] leave  (20)
end (26)

同じ三回のSIGINTを受けたのに片付けは一度だけ回った。二重に塞いだ理由がある。

  • _cleanedフラグはEXITとシグナルハンドラがどちらも同じ片付け関数を呼ぶ構造で重複を防ぐ
  • trap '' INT TERM HUPは片付けが回っている間に新しいシグナルがハンドラを呼び直すのを防ぐ
  • フラグだけだと二度目の進入がreturnで抜けはするが、その間に一度目の片付けは割り込みを一回受けた状態になる
  • 遮断だけだとEXIT経路から来る重複は防げない。EXITはシグナルではないので遮断の対象にならない

片付けが長いと遮断は危険にもなる。シグナルを無視する区間が長くなると、利用者がCtrl+Cを押しても何の反応もない。結局kill -9につながり、そうなると4節の状況に戻る。片付けは短く保つのが最善の防御だ。

11. ハンドラが遅れて動くように見えるとき

Ctrl+Cを押したのに数秒間なにも起きない経験があるはずだ。シェルはフォアグラウンドの子コマンドを待っている間トラップの実行を先送りする。シグナルの受理は即座だがハンドラはその子が終わってから動く。測ってみるとこうなる。

$ bash /tmp/measure.sh 5        # sleep 5 をフォアグラウンドに置き t+1秒に SIGINT
  signal will arrive at t+1s
  [handler] ran at t+5s
  foreground sleep 5 returned at t+5s

$ bash /tmp/measure2.sh         # sleep 5 & で上げて wait で待つ
  signal will arrive at t+1s
  [handler] ran at t+1s
  wait returned at t+1s

同じ5秒の待ちなのに一方はハンドラが4秒遅れ、一方は即座に動いた。差はwaitがシグナルで中断されるのに対しフォアグラウンドのsleepはそうならない点にある。

11.1 反応を速くする方法

  • 長い待ちはsleep 300 & wait $!の形に変える。シグナルが来ればwaitがすぐ戻る
  • 割れるなら割る。sleep 0.5を何度も回るループで確認したときハンドラはt+1秒に動いた
  • 時間のかかる外部コマンドをバックグラウンドに上げてwaitで待てば同じ効果が出る。ただし終了コードをwait "$job"の戻り値で受け取る必要がある
  • この遅延は片付けができないのではなく遅れてできるだけだ。急いでCtrl+Cを連打すると10節の再入問題に移る
$ bash /tmp/defer5.sh
[04:37] waiting on background sleep 4
  >>> [04:38] TERM handler
rc=143

12. 二重実行を防ぐロックと孤児ロック

片付けトラップのもっともよくある二つ目の用途がロック解除だ。mkdirはすでにあれば失敗し、その検査と生成が一度に起きるのでロックの原始操作として使える。

lockdir=/tmp/myjob.lock
if ! mkdir "$lockdir" 2>/dev/null; then
    echo "another run holds $lockdir - exiting"
    exit 1
fi
trap 'rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
$ bash /tmp/lock.sh &          # 一回目の実行
1854 holds the lock
$ bash /tmp/lock.sh            # すぐ二回目の実行
another run holds /tmp/myjob.lock - exiting
second run rc=1
[cleanup] released /tmp/myjob.lock
lock released

12.1 SIGKILLが残したロックは永遠に残る

4節の結論がここでまた出てくる。kill -9で死ぬとロックディレクトリがそのまま残り、それ以降はどの実行も始められない。ディスクが埋まるよりこちらのほうが急を要する事故だ。ロックの中に所有者情報を残せば次の実行が判定できる。

if mkdir "$lockdir" 2>/dev/null; then
    echo "$$" > "$lockdir/pid"
    trap 'rm -f "$lockdir/pid"; rmdir "$lockdir" 2>/dev/null' EXIT INT TERM HUP
else
    owner=$(cat "$lockdir/pid" 2>/dev/null)
    if [ -n "$owner" ] && kill -0 "$owner" 2>/dev/null; then
        echo "lock held by live pid $owner"
    else
        echo "STALE lock (owner $owner is gone) - safe to break"
    fi
fi
$ bash /tmp/lock2.sh &
acquired by 1862
$ bash /tmp/lock2.sh           # 所有者が生きているとき
lock held by live pid 1862

$ kill -9 1862
$ bash /tmp/lock2.sh           # 所有者が消えたあと
STALE lock (owner 1862 is gone) - safe to break

kill -0はシグナルを送らずそのプロセスが存在するかだけを確認する。ただしこの判定には穴がある。

  • PIDは再利用される。死んだ所有者の番号をまったく別のプロセスが引き継いでいれば生きていると誤読する
  • 複数のサーバが共有ボリュームの同じロックを使うとPID検査は無意味だ。ホスト名も一緒に記録する必要がある
  • 孤児ロックを自動で壊すロジックはそれ自体が競合条件を作る。二つの実行が同時に「古い」と判断しうる
  • 安全な折衷は自動で壊さず警告だけ出して終わることだ。人が確認して消すようにする
  • 所有者情報に開始時刻も一緒に残せば古さの判定がはるかに安全になる

13. 結局どれを使うのか

片付け方式ごとに何を捕まえて何を逃すかを整理するとこうなる。

パターン正常終了exit 1 · エラーINT · TERMKILL移植性
最終行でrm片付く残る残る残るすべてのシェル
trap ... EXIT片付く片付くbashのみ片付く残るdashではシグナルに弱い
trap ... EXIT INT TERM HUP片付く片付く片付く残るbash・dash両方で確認
上記 + 再発生・再入防御片付く片付く片付く・終了コード保持残るbash基準、8節のテンプレート
固定接頭辞 + 外部掃除ジョブ———あとで片付くKILLを覆う唯一の方法

最後の行が重要だ。trapだけではすべての場合を覆えない。三行目までがスクリプトの中でできる最善で、その上はスクリプトの外側の仕掛けが担う。二つを一緒に置くのが実際の答えだ。

13.1 最小チェックリスト

  • 片付けコードは関数に出してtrap cleanup EXITで登録する。クォートの問題が消える
  • EXITの隣にINT TERM HUPを並べる。bashでは要らなく見えてもdashで要る
  • シグナルハンドラは片付け後にtrap - SIGで解除し、同じシグナルで自分を撃ち直す
  • 片付け関数の一行目は: "${var:?}"だ。次がcaseのパス検査になる
  • 変数をあらかじめ空で宣言し、トラップを掛けてからmktempを呼ぶ
  • 再入フラグとtrap '' INT TERM HUPを入れる
  • ハンドラの中でexit 0を呼ばない。元の終了コードを保つ
  • 一時パスに固定の接頭辞を入れ、古い残骸を回収する別ジョブを置く
  • バックグラウンドの子があるならディレクトリを消す前に先に殺す
  • 長い待ちは& waitに変えて反応速度を確保する
  • エントリポイントのスクリプトがexecで終わるなら、その手前のトラップは動かないことを覚えておく
  • 配布先のシェルで一度は実際に走らせる。この記事の表を作るのにかかった時間は数分だ

14. 確認できなかったこと

この記事で実行によって検証できなかった項目を一箇所にまとめる。

  • 実際の端末で押したCtrl+C。検証はすべて非対話のスクリプトが自分自身や子にシグナルを送る方式で行った。端末がプロセスグループ全体にSIGINTを撒く状況、つまりシェルと子が同時にシグナルを受ける場合は再現していない。その条件下ではハンドラの実行順序が変わる余地がある
  • Linux glibcの環境。この記事の実行環境はx86_64-pc-msys向けのbash 5.2.37と同じ環境のdashだ。シグナル配送の層がLinuxと完全に同じとは限らない。特に3節のSIGQUIT無視の挙動と終了コードは、配布先で一度再現してみるほうが確実だ
  • zshとkshとbusybox ash。実行できる環境ではなかったので確認できなかった。最小のコンテナイメージでよくある組み合わせなので、実務では重要な空白だ
  • flockベースのロック。この環境にflockが入っていないため12節はmkdir方式でのみ確認した。ファイルディスクリプタが閉じるときにロックが自動で外れる性質は検証できていない
  • サービス管理者とコンテナオーケストレータの停止手順。停止猶予時間が過ぎるとSIGKILLに上がる動作は4節で対策の根拠として触れたが、実際のサービス定義を作って再現してはいない
  • ネットワークファイルシステムでの削除遅延。7.4で共有ボリュームを一時領域に使う危険に触れたが、実際の遅延や部分削除を測ってはいない
  • 大容量削除の所要時間。10節で片付けを短く保てと書いたが、ファイル数に応じたrm -rfの所要時間は測っていない
  • 旧バージョンのbash。trap -pとset -Eの動作が古いバージョンでも同じかは確認していない

FAQ

Q1. trap cleanup EXITの一行で十分ではないのか

bashだけで回すならおおむね十分だ。実行して確認した結果、bash 5.2.37はEXITだけでもSIGINT・SIGTERM・SIGHUPでハンドラを走らせた。問題は同じスクリプトをdashで走らせたときだ。SIGTERMでハンドラが実行されず一時ファイルがそのまま残った。シバンが#!/bin/shなら配布先でdashとして実行されうるし、開発機で/bin/shがbashにつながっていればこの差は見えない。シグナルを明示的に並べる費用は一行なので、素直に並べるほうがよい。

Q2. 片付けハンドラをexit 0で終わらせてはいけないのか

いけない。確認した結果、ハンドラの中のexit 99は元の終了コード3を99で上書きした。ハンドラがexitを呼ばなければ元の値がそのまま保たれる。片付けハンドラにexit 0を付けると失敗した実行も中断された実行もすべて成功として報告される。CIランナーはそのコードで再試行の可否を決め、上位スクリプトはそのコードで次の段階に進むかを決める。片付けをきちんとやって終了コードを壊すと、前の利得がすべて消える。

Q3. トラップハンドラの中でエラーが起きたら残りの片付けはどうなるか

既定の状態では続行する。ハンドラの途中にfalseを入れても後ろの行がすべて実行され、終了コードも変わらなかった。ただし片付け関数の中でset -eを入れると最初の失敗で止まる。実際に確認すると1段目だけが出て2段目は実行されず、終了コードが1に変わる。片付けは失敗しても最後まで試すべきコードなので、その中ではset -eを入れない。削除コマンドには対象がなくても成功するオプションを使い、失敗を吸収すべき場所には|| trueを付ける。

Q4. 関数ごとに自分の片付けをEXITに掛けるとなぜ問題になるのか

同じシグナルに対するトラップは積み上がらず上書きするからだ。関数Aが掛けて関数Bが掛ければBだけが残る。しかもEXITトラップはシェル全体の状態なので関数を出ても残り続ける。関数ローカルではない。回避法は片付け項目を配列に積んでおき、EXITにはその配列を逆順に回る関数だけを掛けることだ。登録の逆順が資源解放の順序としても合う。ロックを先に取ってディレクトリをあとで作ったならディレクトリから消してロックを最後に外す。

Q5. サブシェルの中で作った一時ファイルはどう消すのか

そのサブシェルの中で別にトラップを掛ける必要がある。実行して確認した結果、サブシェルは親のEXITトラップを一覧としては受け継ぐが、自分が終了するときにそれを実行しない。親で一度だけ動く。逆にサブシェルの中で登録したトラップはサブシェルが終わるときにその中で動き、親には残らない。パイプライン構成要素の中で掛けたトラップも同じだ。だからトラップを掛けたのに動かないようなら、その行がパイプの右側や括弧の中にあるかをまず確認すればよい。

結論: 今日変える三つのこと

第一に、片付けコードを最終行からトラップに移す。そしてEXITの隣にINT TERM HUPを並べる。bashでは要らないように見えてもdashで崩れる。シグナルハンドラは片付け後に自分のトラップを解除し、同じシグナルで自分を撃ち直して終了コードを保つ。

第二に、片付け関数の一行目に: "${var:?}"とパス検査を入れる。トラップはスクリプトのどの地点でも発動するので、変数に値が入る前にシグナルが来る場合が実際にある。その状態で削除が実行されると何が消えるか分からず、消えたものは戻らない。だからこの二行は削除の行より先に書く。ロジックを変えたら削除をechoに変えて一度走らせ、対象のパスを目で確認する。

第三に、trapがすべての場合を覆うと信じない。kill -9は捕まらず、実測で320KBの作業ディレクトリがまるごと残った。bashがtrap ... KILLを構文エラーとして拒否せず一覧に表示までしてくれるので、コードだけを読むと塞いであるように見える。一時パスに固定の接頭辞を付けて古い残骸を回収する別ジョブを置くことが、スクリプトの中では決して解決しないこの穴を埋める唯一の方法だ。

最後にひとつ。この記事の表と出力はすべて十行前後のスクリプトで得たものだ。片付けが動くかどうかが気になるなら推測せず、mktempでファイルを一つ作って殺してみればいい。30秒で終わる。
