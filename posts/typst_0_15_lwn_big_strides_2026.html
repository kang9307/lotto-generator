1. LWN이 주목한 Typst 0.15의 위상과 릴리스 배경

리눅스와 오픈소스 기술 전문 매체인 LWN.net은 2026년 9월 9일 Lee Phillips의 기고를 통해 Typst의 기술적 도약을 다룬 분석 기사를 실었다. 원문은 Typst가 PDF, SVG, PNG뿐 아니라 개발이 진행 중인 HTML 형식으로 문서를 조판하는 시스템이며, 기술적 자료를 능숙하게 처리하여 궁극적인 LaTeX 대체재로 자주 거론된다고 적는다. LWN은 약 1년 전 0.13 버전을 검토한 데 이어, 2026년 6월 릴리스된 0.15 버전을 집중적으로 분석했다. 공식 GitHub 릴리스 기록에 따르면 Typst 0.15.0은 2026년 6월 15일에 공개된 판본이다.

이전에 본 블로그에서 다룬 Papermake와 Typst 서버 아키텍처에서는 REST API 기반의 셀프호스팅 PDF 렌더링 서버로서의 활용성을 중점적으로 살펴보았다. 반면 이번 분석에서는 LWN 기사가 분석한 Typst 0.15 릴리스의 5대 언어적·조판적 진전과 학술 조판 현장의 제도적 진입 장벽에 초점을 맞춘다. 서버 관점의 아키텍처 논의와 달리, 이번 판본에서 조판 언어와 컴파일러가 직접 흡수한 기능적 확장은 문서 작성자의 작업 방식을 직접 다룬다.

일반적으로 마크업 기반의 조판 도구는 텍스트 소스를 파싱하여 레이아웃을 계산하고 규격화된 출력 포맷으로 변환하는 절차를 거친다. 원문은 Typst가 Rust 언어로 작성된 자유 소프트웨어이며 Apache-2.0 라이선스를 따른다고 밝힌다. 0.15 판본의 핵심 변경 사항으로는 가변 폰트 지원, HTML 내보내기 시 MathML 변환, 단일 소스 다중 문서 번들 출력, 장별 다중 참고문헌, 복수 PDF 표준 동시 검증 기능이 꼽힌다.

원문은 이들 기능이 복합적으로 추가되면서 시스템의 표현 능력이 대폭 확장되었다고 서술한다. 이 글의 해석으로는, LWN은 Typst 0.15가 다양한 출력 형식과 조판 기능을 추가하며 큰 진전을 이룬 판본이라고 요약한다. 각 기능이 실제로 어떤 방식으로 동작하는지 원문 서술을 바탕으로 살펴본다.

2. 가변 폰트 지원과 조판 엔진의 유연성

가변 폰트는 타이포그래피 분야의 최신 발전 사항으로, 원문은 가변 폰트가 단일 파일 안에 모든 변형을 담을 수 있어 디스크 공간을 절약하고 저자나 디자이너에게 더 큰 유연성을 부여한다고 적는다. 통상적인 디지털 글꼴 체계에서는 보통체, 굵은체, 기울임체, 굵은 기울임체 등 각 굵기와 스타일에 맞춰 별도의 파일이 나뉘어 배포된다. 그러나 가변 폰트는 하나의 글꼴 아웃라인 정의로부터 매개변수 축을 통해 다양한 형태를 파생시킨다.

원문은 글꼴 특성과 변형이 축 값을 설정함으로써 선택되며, 각 축이 렌더링된 글리프의 특정 측면을 변경한다고 설명한다. 축에는 기능을 켜고 끄는 이산적인 값이 지정되거나, 두 한계값 사이의 연속적인 값이 지정될 수 있다. 연속적인 축의 대표적인 활용 사례는 연속선상에서 글꼴의 두께를 자유롭게 선택하는 것이다. Typst는 텍스트 함수의 매개변수를 통해 스타일, 굵기, 장평, 크기를 자동 구성하며 사용자 정의 축 설정도 지원한다.

기사에서 저자는 오픈소스 가변 폰트인 Roboto Flex(13개 축 제공)와 Zycon(17개 장식 그림 및 6개 연속 축 제공)을 활용해 기능을 시험했다. 원문은 Roboto Flex에서 조작한 축의 이름이 디센더 길이를 결정하는 YTDE 축이었으며, 다른 특성을 유지한 채 글자 아래로 뻗는 획의 길이만 조절할 수 있었다고 보고한다. 원문은 이러한 조절이 표를 조판할 때 디센더와 셀 테두리 사이의 충돌을 방지하는 데 유용할 수 있다고 설명한다. 또한 Zycon 글꼴의 축 조작을 통해 달 모양 글리프의 월령 변화를 표현하는 시험 결과도 제시되었다.

이 글의 해석으로는, LWN은 가변 폰트가 단일 파일로 공간을 절약하고 글꼴의 세부 축을 조정할 수 있게 한다고 설명한다. 한편 커뮤니티 토론(Lobsters 댓글)에서는 가변 폰트의 진짜 장점이 파일 통합 자체가 아니라 연속적 보간이며, TeX의 Metafont가 수십 년 전에 이미 제공했던 개념이라는 지적이 나왔다. 원문과 커뮤니티 의견 모두 가변 폰트 도입으로 서체 제어 범위가 넓어졌다는 점을 언급한다.

3. 웹 수식의 직접 렌더링: MathML과 HTML 내보내기

Typst의 HTML 내보내기는 여전히 실험적 기능으로 분류되어 있지만, 0.15 판본에서는 눈에 띄는 진전을 보였다. 원문에 따르면 주된 새 기능은 수식을 MathML로 변환하는 기능이다. 이전 0.13 판본을 다룬 기사에서 선보였던 특정 정적분 수식을 동일하게 HTML로 내보냈을 때, 최신 웹 브라우저들이 해석할 수 있는 긴 MathML 마크업 문자열이 생성되었다.

원문은 브라우저에서 표시된 MathML 렌더링 결과와 이전 기사의 PDF 출력 결과를 비교했을 때 본질적으로 동일(essentially identical)하다고 서술한다. 원문은 MathJax와 같은 별도의 자바스크립트 라이브러리를 요구하지 않고, 수식을 래스터 이미지로 대체할 필요 없이 브라우저에서 TeX 품질의 수학 표현을 생성할 수 있는 능력이 과학적 커뮤니케이션을 위한 커다란 이점이라고 적는다. 수식을 이미지로 처리할 경우 텍스트 선택이 불가능하고 스크린 리더로 읽을 수 없는 문제가 발생한다.

원문은 실험적인 HTML 출력을 활성화하기 위해 컴파일러 명령줄에서 별도의 기능 플래그가 요구된다고 명시한다. 공식 블로그에 따르면 MathML은 수식의 구조와 의미를 인코딩하므로 스크린 리더 음성 출력이 가능하고 브라우저 고해상도 확대를 지원한다. 다만 공식 블로그는 주요 브라우저 간의 렌더링 품질에 일부 차이가 존재할 수 있어 절대적인 시각적 일관성이 중요한 경우에는 SVG 렌더링이 대안이 될 수 있다고 덧붙인다.

이 글의 해석으로는, LWN은 이 기능이 브라우저에서 JavaScript 라이브러리나 이미지 없이 TeX 품질의 수식을 직접 표시하게 한다고 설명한다. 원문은 HTML 내보내기가 여전히 진행 중인 작업(still considered a work in progress)이라고 거듭 밝히고 있다.

4. 단일 소스 다중 문서화: 번들 내보내기 메커니즘

Typst와 같은 소프트웨어의 전형적인 사용 시나리오는 단일 파일, 주로 논문이나 도서 형태의 PDF 문서를 생성하는 것이다. 그러나 Typst 0.15에 도입된 번들 기능은 작성자가 단일 소스 파일 안에서 Typst가 지원하는 임의의 형식으로 구성된 출력 파일 모음을 지정(specify a collection of output files in a single source file)할 수 있게 해 준다. 원문은 이들 파일이 데이터를 공유할 수 있으며 문서 내부 링크뿐만 아니라 문서 간 상호 링크를 포함할 수 있다고 적는다.

원문은 이 기능이 상호 연결된 HTML 파일들의 네트워크로 구성된 웹사이트를 구축하는 데 이상적이라고 평가한다. 아울러 학술 연구자가 하나의 소스 파일에서 콘퍼런스 발표용 슬라이드 자료와 관련 프리프린트 논문을 동시에 생성하고자 할 때도 유용할 것이라고 덧붙인다. 공식 블로그에 따르면 공식 문서 웹사이트 자체를 Typst로 마이그레이션하는 과정에서 다중 HTML 페이지를 내보내기 위해 이 메커니즘이 설계되었다.

원문 저자는 3개의 문서(2개의 HTML 페이지와 1개의 PDF)가 단일 소스 텍스트 조각을 공유하고 상호 하이퍼링크로 연결되는 예시를 작성해 기능을 시험했다. 원문은 번들 기능이 명시된 대로 동작했으나, HTML 출력과 마찬가지로 개발이 진행 중인 기능이므로 컴파일 시 전용 기능 플래그가 요구된다고 밝힌다. 컴파일 결과 생성된 번들 디렉터리 안에는 지정된 파일들이 생성되며 문서 간 링크가 동작했다.

이 글의 해석으로는, LWN은 번들 기능이 단일 소스로부터 웹사이트나 발표 슬라이드와 프리프린트를 함께 관리하는 데 적합하다고 설명한다. 컴파일러 수준에서 다중 포맷 출력을 묶어내는 방식이 제공된다.

5. 학술 도서 조판의 핵심: 장별 다중 참고문헌

Typst 0.15에서는 단일 문서 내에서 다중 참고문헌 섹션을 구성하는 기능이 허용되었다. 원문은 이것이 많은 기대를 모았던 기능이며, 대표적인 적용 사례는 각 장마다 별도의 참고문헌 섹션을 요구하는 단행본 도서(separate reference section for each chapter)라고 적는다. 복수의 저자가 참여하는 편집 저작물이나 논문 모음집에서는 책 전체 끝에 인용을 모으는 대신 장마다 독립된 서지 목록을 두는 형식이 쓰인다.

원문은 장별 참고문헌을 구성할 때 각 서지 섹션이 서로 다른 데이터베이스 또는 데이터베이스 모음을 참조할 수 있다고 설명한다. 또한 인용 번호 부여 방식을 제어하는 그룹(group) 매개변수가 제공되어, 번호 체계를 각 장마다 1번부터 다시 시작하도록 설정(group: none)하거나 전체 저작물에 걸쳐 연속적으로 이어지도록 구성할 수 있다고 적는다. 이와 같은 서지 목록 분할은 과거 외부 패키지에 의존해야 했던 영역이었다.

공식 블로그에 따르면 이전 버전에서는 커뮤니티가 만든 외부 패키지들이 이러한 요구를 메우고 있었으나, 0.15부터 코어 엔진에 네이티브 다중 참고문헌 기능이 통합되었다. 본문에 인용이 등장하면 가장 가까운 위치의 참고문헌 블록이 해당 인용 키를 자동으로 할당받아 처리하는 규칙이 기본 동작으로 적용된다. 사용자가 인용 수집 규칙을 제어하고자 할 경우 셀렉터 표현식을 활용할 수도 있다.

이 글의 해석으로는, LWN은 장별 참고문헌 분리가 각 장마다 별도의 서지 섹션을 필요로 하는 학술 도서의 전형적 요구를 지원한다고 설명한다. 서지 데이터베이스 분할과 번호 매기기 설정이 공식 지원된다.

6. 아카이빙과 접근성: 복수 PDF 표준 동시 검증

독점적 확장 기능의 사용을 피하는 것만으로도 대부분의 PDF 문서는 뷰어 간 호환성을 유지할 수 있다. 그러나 원문은 더 깊은 차원에서 볼 때 단순한 PDF 파일이란 존재하지 않으며, 장기 보존성과 접근성에 관한 수십 가지의 공식 표준 규격이 존재한다고 짚는다. 아카이빙 표준은 문서가 다양한 리더 소프트웨어에서 오랜 세월에 걸쳐 영구적으로 동작하도록 보장하기 위한 것이며, 접근성 표준은 장애인이 문서를 활용할 수 있도록 보장하기 위한 것이다.

Typst는 기존에도 다양한 PDF 버전과 보존성·접근성 표준을 개별 지정하는 기능을 갖추고 있었다. 원문은 0.15 판본의 새로운 특징이 단일 컴파일 과정에서 하나 이상의 표준(more than one)을 동시에 대상으로 지정할 수 있게 된 점이라고 밝힌다. 이는 장기 보존 규격인 PDF/A와 유니버설 접근성 규격인 PDF/UA 속성을 모두 만족하는 문서를 생성하고자 할 때 쓰이는 기능이다.

원문은 컴파일러 구현체가 호환되지 않는 규격 조합을 지정하거나 대상 표준의 모범 사례를 따르지 않았을 때 경고 또는 오류(warnings or errors)를 발생시켜 사용자가 복잡한 PDF 표준을 올바르게 준수하도록 돕는다고 설명한다. 기사에서는 PDF 1.7 버전과 PDF/A-1b 표준을 동시에 요청했을 때 컴파일러가 호환성 오류를 출력하며 PDF 1.4 버전을 요구하는 힌트를 제시한 사례가 소개되었다. 또한 접근성 표준인 PDF/UA-1을 추가 지정했을 때 문서 제목 메타데이터가 누락되었다는 오류를 컴파일러가 잡아내는 사례도 보고되었다.

원문은 장애인을 돕는 것 외에도, 미국을 비롯한 여러 국가에서 주 및 연방 정부에 접근성 있는 PDF 제작이 법적 요구 사항으로 적용되고 있으므로 아카이브 관리자와 출판사에 중요한 기능이라고 적는다. 이 글의 해석으로는, LWN은 복수 PDF 표준 동시 지정이 아카이빙과 접근성 규격을 함께 준수해야 하는 환경에서 유용하다고 설명한다.

아래 표는 Typst 0.15의 5대 핵심 기능과 이에 대한 LWN의 서술 및 공식 지원 상태를 정리한 것이다.

기능 항목 원문(LWN) 핵심 서술 구현 상태 및 특징
가변 폰트 (Variable Fonts) 단일 파일에 모든 서체 변형을 담아 공간을 절약하고 저자·디자이너에게 유연성을 제공함 정식 지원 (매개변수 축 조작 및 자동 구성)
MathML 변환 (MathML) HTML 내보내기 시 수식을 MathML로 변환하며 결과가 PDF 출력과 본질적으로 동일함 실험적 (HTML 내보내기 진행 중, JS 라이브러리 불필요)
번들 내보내기 (Bundle Output) 단일 소스 파일에서 다중 출력 파일 컬렉션을 지정하고 문서 간 상호 링크를 지원함 실험적 (HTML/PDF 동시 생성, 전용 플래그 필요)
다중 참고문헌 (Multiple Bibliographies) 장별 별도 참고문헌 섹션을 지원하며 서지 그룹별 번호 매기기 제어가 가능함 정식 지원 (도서 및 학위논문 조판 핵심 기능)
복수 PDF 표준 동시 검증 둘 이상의 PDF 표준을 동시 지정하며 호환되지 않는 조합에 경고나 오류를 발생시킴 정식 지원 (PDF/A 보존 규격 및 PDF/UA 접근성 규격 동시 충족)

7. 오픈소스 생태계 지표와 프로젝트 거버넌스

Typst 프로젝트는 커뮤니티의 참여 속에서 생태계를 넓혀가고 있다. 원문은 GitHub에서 개발되는 Typst의 기여자 수가 460명에 달하며, 사용자 참여를 통해 패키지 생태계가 1,500개 이상(over 1500 packages)으로 확장되었다고 보고한다. 이는 다양한 조판 매크로와 서식 템플릿이 등록되어 있음을 보여준다.

동시에 원문은 프로젝트의 거버넌스 구조에 관해서도 사실을 전한다. Typst 프로젝트의 기여자 가이드에는 풀 리퀘스트의 요건이 기술되어 있으며, LLM(거대 언어 모델)이 생성한 코드나 설명은 거부된다는 경고가 포함되어 있다. 또한 프로젝트 창립자들은 Typst가 오픈소스 프로젝트인 동시에 영리 기업이라는 점을 밝히고 있으며, 프로젝트의 방향성과 개별 기여의 적합성을 결정할 때 회사의 필요성을 고려할 것임을 밝히고 있다. 원문은 잠재적 기여자와 사용자가 이 요소를 염두에 두어야 한다고 적는다.

원문에서 제시된 생태계 지표와 거버넌스 특징을 요약하면 다음과 같다.

  • 프로젝트 구현 언어 및 라이선스: Rust 언어 기반 개발 및 Apache-2.0 오픈소스 라이선스 채택.
  • 공동체 참여 규모: 공식 GitHub 저장소 기준 460명의 코드 기여자 참여.
  • 패키지 생태계 규모: Typst Universe 저장소 기준 1,500개 이상의 등록 패키지 보유.
  • 기여 정책 및 거버넌스: LLM 생성 기여 거부 방침 명시 및 오픈소스 프로젝트와 영리 기업의 구조 병행.

이 글의 해석으로는, LWN은 Typst가 오픈소스 프로젝트이면서 영리 기업이므로 기여자가 회사의 필요성을 염두에 두어야 한다고 적는다. LWN 기사 댓글에서 독자 mrugiero는 학술 출판 인프라를 기업 주도 소프트웨어에 의존하는 것에 대한 의견을 남겼으며, 이에 대해 전자책 제작 워크플로 등 실질적 필요성을 언급하는 댓글이 이어졌다.

8. 학술 출판의 네트워크 효과와 1.0 이전의 안정성 장벽

시스템 개발의 진전에도 불구하고, LWN 기사는 출판계의 네트워크 효과가 Typst의 잠재력 실현을 가로막고 있다고 지적한다. 사용자들이 여러 저널의 스타일 규격에 맞는 템플릿을 고안해 냈음에도 불구하고, 단순 PDF가 아닌 소스 제출을 요구하는 학술 저널들은 여전히 LaTeX, Word 또는 기타 정형 형식(LaTeX, Word, or some other format)을 요구하고 있다. 원문은 Typst 마크업으로 작성된 원고를 받아주는 저널이 극소수에 불과하다고 적는다.

원문은 Typst가 1.0 이전 상태(pre-1.0 status)에 머물러 있는 한 이러한 상황이 쉽게 바뀌지 않을 것으로 전망한다. 원문은 1.0 릴리스가 아직 요원한 상태에서 문서에 중대하고 잠재적으로 파괴적인 변경을 요구할 위험(danger of requiring significant, possibly breaking changes to documents)이 상존한다고 적는다. 버전 변경에 따른 문서 호환성 문제가 해결되지 않는 점이 저널 출판사의 채택을 주저하게 만드는 요인으로 지적되었다.

LWN 기사 댓글에서는 조판 품질에 관한 지적도 나왔다. 댓글에서 독자 callegar는 Typst가 기울임체와 직립체 문자가 교차할 때 자간 여백을 자동으로 보정하는 이탤릭 보정(italic correction)을 기본 지원하지 않아 특정 글꼴에서 문자 충돌이 발생하는 문제를 거론했다. 수동 보정은 가능하지만 자동 생성 워크플로에서는 수동 조정이 어렵다는 점이 지적되었다. 또 다른 댓글에서는 리눅스 사용자를 위한 편집기로 Typesetter가 추천되었으며, 대학원생이 Typst로 학위논문을 작성했다는 후기도 언급되었다.

원문 기사 및 댓글에서 확인된 주요 논점들은 다음과 같이 정리할 수 있다.

  • 학술 출판 소스 수납 장벽: 대다수 저널이 소스 제출 시 LaTeX 또는 Word 형식을 요구하며 Typst 마크업 수용은 극소수임.
  • 1.0 이전 버전의 호환성: pre-1.0 상태에서 문서에 파괴적 변경을 요구할 수 있는 위험이 남아있음.
  • 조판 세부 품질 이슈: 댓글에서 이탤릭 보정 부재로 인한 글자 충돌 문제가 지적됨.
  • 접근성 및 포맷 변환: PDF 접근성 표준 지원과 더불어 스크린 리더 환경을 위한 HTML 및 MathML 발행 논의가 이뤄짐.

아래 표는 LWN 기사가 짚은 LaTeX 대체 장애물과 이에 대한 원문 서술, 그리고 이 글의 해석을 대조하여 정리한 것이다.

장벽 범주 원문(LWN) 핵심 서술 이 글의 해석
저널 제출 형식의 고착 대다수 저널이 소스 제출 시 LaTeX, Word 등을 요구하며 Typst 마크업을 수용하는 곳은 극소수임 이 글의 해석으로는, LWN은 대다수 저널이 기존 형식을 고수하고 있어 Typst 소스 제출이 아직 널리 허용되지 않는다고 설명한다.
1.0 이전의 버전 안정성 pre-1.0 상태에 머물러 있어 문서에 중대하고 파괴적인 변경을 요구할 위험이 여전히 존재함 이 글의 해석으로는, LWN은 1.0 이전 상태에서 발생할 수 있는 잠재적 파괴적 변경 위험이 공식 채택의 장벽으로 작용한다고 적는다.

원문 저자는 이러한 장벽에도 불구하고 Typst가 현시점에서도 유용한 도구라고 결론짓는다. 예컨대 드로잉 프로그램을 켜지 않고 텍스트 명령만으로 SVG 로고를 작성하는 작업 등에서 유용성을 언급했다. 저자는 Typst가 많은 지지자들의 바람처럼 LaTeX 대체재가 될 수 있을지는 단언할 수 없으나, 현재의 개발 속도가 유지된다면 10년 혹은 20년에 걸쳐 실현 가능한 가능성이라고 평가한다.

9. 확인하지 못한 것

본 분석을 진행하며 1차 출처 자료를 검토하는 과정에서 아래 사항들은 명확한 정량적 수치나 추가 근거를 확인할 수 없어 본 절에 기록으로 남긴다.

  • 원문 기사에는 Typst 0.15의 컴파일 속도나 대규모 논문 렌더링 시 구체적인 초 단위 벤치마크 수치가 기재되어 있지 않아 성능 비교 수치를 기술하지 않았다.
  • 전 세계 주요 학술 저널 중 Typst 원본 파일(.typ)을 공식 투고 규격으로 공식 승인한 저널의 정확한 전수 통계와 목록은 원문에 기재되지 않아 파악하지 못했다.
  • 원문은 번들 내보내기 및 HTML MathML 변환 메커니즘과 관련하여 내부 파서 및 컴파일러 아키텍처의 구체적인 소스코드 수준 알고리즘 변경 내역을 상세히 상술하지 않아 확인하지 못했다.
