タスクごとにハーネスを - Claude Codeの動的ワークフロー徹底分析

A Harness for Every Task - Inside Claude Code's Dynamic Workflows

2026年6月4日 IT・技術

序論：「タスクごとにハーネス」という発想がなぜ重要か

この2年間、AIコーディングツールをめぐる議論の重心は奇妙に移ってきました。最初は「モデルがどれだけ賢いか」、次に「どれだけコンテキストを入れられるか」でした。ところが2026年に入り、実務者の話題は別の場所へ移りました。同じモデルを使っていても、あるツールはきちんと仕事を終え、別のツールは同じタスクで迷走します。違いはモデルではなく、モデルを包んで実際に仕事を成し遂げさせるハーネス（harness）、すなわち実行の骨格にあったのです。

Anthropicが最近公開したClaude Codeの動的ワークフロー（Dynamic Workflows）は、まさにこの点を正面から狙います。核心は一文で要約できます。「すべてのタスクに一つの固定手順を強いるのではなく、タスクごとに合うハーネスをその場で作れ」。本稿では、その発想が何を変えるのか、静的ワークフローの限界をどう乗り越えようとするのか、そして現場でこれをどう受け止めるべきかを私の視点で分析します。結論を先に言えば、動的ワークフローはエージェントの自律性を高めると同時に、信頼性という請求書を新たに発行します。その請求書をどう支払うかが導入の成否を分けます。

1. ハーネスとは何か - モデルと実行骨格の分離

まず議論の土台を固めます。「AIエージェント」と言うと巨大な言語モデル一つを思い浮かべがちですが、実際に仕事を成し遂げるシステムは二層に分かれます。一つはモデル、もう一つはそれを包むハーネスです。

モデルはテキストを入力として受け取りテキストを出力する関数に近い存在です。それ自体ではファイルを読むことも、テストを走らせることも、結果を検証することもできません。それを担うのがハーネスです。ハーネスは次のような問いに答えるコードと手続きの束です。

  • どのツールを与えるか：ファイル読み取り、シェル実行、検索、テストランナーのうち、何をこのタスクに許可するか。
  • 結果をどう検証するか：モデルが出したコードが実際にコンパイルされ、テストを通過するかを誰が、いつ確認するか。
  • 失敗したらどうするか：検証が壊れたとき、再試行するか、別経路を選ぶか、人に渡すか。

この区別が重要なのは、モデルの品質が同じでもハーネスの設計次第で成果物の信頼性が大きく変わるからです。同じエンジンを載せても車体設計が違えば全く別の車になるのと同じです。動的ワークフローは、まさにこの「車体」をタスクごとに作り直すという宣言です。

2. 静的ワークフローの限界 - 分岐地獄と脆さ

動的ワークフローを理解するには、まずそれが何を克服しようとするのかを見る必要があります。その対象が静的ワークフロー（static workflow）です。静的ワークフローは1からN段階まで流れを人があらかじめ固定します。たとえば「コードを生成する → テストを走らせる → 失敗したら一度直す → PRを開く」といった具合です。

この方式は予測可能で安全です。流れが決まっているので何が起きるか分かり、検証も監査も容易です。問題は、現実のタスクがそれほど定型的でないことにあります。あるタスクはテストが全くなく、あるタスクはデータ移行のように一度実行すると戻しにくく、あるタスクは外部API応答によって経路が分かれます。

静的ワークフローの敵は複雑さではない。想定外のタスクが入ってきたときに爆発的に増える分岐と例外処理、そしてそれらの分岐が絡み合って生まれる脆さである。

現場で静的ワークフローを長く運用したチームなら、この「分岐地獄」を知っています。新しいケースが入るたびにif文が一つ増え、ワークフロー定義は数百行に膨らみ、ある瞬間に誰も全体を理解できない状態になります。動的ワークフローは、この累積する複雑さをワークフロー定義ではなくエージェントのその場の判断で吸収しようとする試みです。

3. 動的ワークフローの仕組み - タスクを見てハーネスを組む

では動的ワークフローは具体的にどう動くのでしょうか。核心は「流れをあらかじめ決めず、タスクを見たうえでそれに合う実行骨格を構成する」ことです。単純化すると次の順序で読み解けます。

静的ワークフロー： [固定された1→2→3→4段階]  → すべてのタスクを同じ型に押し込む
   │
   ▼
動的ワークフロー： タスク観察 → 必要なツール選択 → 検証方式の決定
                → 実行 → 検証 → （失敗時）経路の再構成 → 反復

ここでの決定的な違いは、「検証方式の決定」と「経路の再構成」が流れの中に内蔵されている点です。静的ワークフローでは検証方法があらかじめ埋め込まれていますが、動的ワークフローではエージェントがタスクの性質を見て「これはテストで検証」「これは型チェックで検証」「これは人の確認が必要」をその都度決めます。

この構造の利点は明確です。定型化されていない多様なタスクを一つのコードベース内で柔軟に処理できます。しかし同じ理由で欠点も明らかです。毎回経路が変わるため、「このツールがどのタスクで何をしたか」を事後に再現し検証するのが静的ワークフローより難しくなります。柔軟性を得る代わりに再現性を一部差し出す取引です。

4. 自律性と信頼性のバランス - 核心の緊張

動的ワークフローをめぐるすべての議論は結局一つの緊張に収束します。自律性（autonomy）と信頼性（reliability）の相反です。エージェントにより多くの判断を任せるほど多様なタスクを処理しますが、同時に「何をするか予測しにくくなる」という代償が伴います。

この緊張は新しいものではありません。自動化の歴史で繰り返されたテーマです。航空機の自動操縦、自動運転、産業制御もみな同じ問いの前に立ちました。システムをより賢く自ら判断させるか、それとも予測可能なように行動を制約するか。答えは常に「文脈による」でした。リスクの大きい領域ほど自律性を狭め、リスクの小さい領域ほど自律性を広げました。

動的ワークフローも同じ原理に従うべきです。良い動的ワークフローは「すべてをエージェントに任せる」ことではなく、自律性の範囲をタスクのリスク度に合わせて動的に調整することです。テストで即座に検証されるタスクでは広い自律性を、戻しにくいタスクでは狭い自律性と人の承認を置くという具合です。このバランス感覚が欠けた動的ワークフローは、単なる「制御されない自動化」に過ぎません。このテーマはエージェントの自律性と安全の緊張を扱った別稿AIの次はソフトウェアではない - harnessの時代とも深く結びついています。

5. 検証ループ - 動的ワークフローの心臓

動的ワークフローで最も過小評価される要素が検証ループ（verification loop）です。人々は「エージェントが自分でツールを選ぶ」部分に注目しますが、実際に信頼性を作るのはツール選択ではなく、その結果を検証するループです。

検証ループの品質は「検証信号がどれだけ速く正確か」にかかっています。良い検証信号の例を挙げると次の通りです。

検証信号 特性 適したタスク
テスト合否 速く明確な二値信号 ロジック変更、バグ修正
型チェック/コンパイル 構造的エラーを即座に捕捉 リファクタリング、シグネチャ変更
リント/フォーマット スタイル・慣習違反を検知 コード整理、ボイラープレート
人のレビュー 遅いが判断が必要な信号 設計判断、戻しにくい変更

動的ワークフローの威力は、エージェントがタスクの性質に合う検証信号を自ら選ぶときに現れます。単純なバグ修正ならテストだけで十分ですが、データベーススキーマ変更ならテストと人のレビューを併せて置くべきです。検証信号が乏しいタスク、たとえば自動検証がほぼ不可能なUIの微調整では、動的ワークフローの利点が急激に減ります。検証できないタスクは自動化しにくいという古い真実がここでもそのまま働きます。

6. 動的ワークフローが合うタスクと合わないタスク

すべてのタスクに動的ワークフローが正解ではありません。どこに合いどこに合わないかを見分ける目が導入の核心です。

6.1 合うタスク

検証信号が速く明確で、失敗しても戻しやすいタスクが動的ワークフローに合います。テストが整ったコードベースのバグ修正、リントエラーの一括整理、反復的なボイラープレート生成、仕様が明確な単位機能の実装などがここに属します。こうしたタスクではエージェントが多様な経路を試し、検証が即座に誤った試みを弾くため、自律性を広げても安全です。

6.2 合わないタスク

逆に検証が遅いか不可能で、失敗コストが大きいタスクは動的ワークフローのリスクが高まります。本番データベース移行、決済・セキュリティに直結するロジック、明確な正解のないアーキテクチャ判断などがそうです。こうした領域では動的ワークフローを使っても自律性を狭め、人の承認を必須にすべきです。マルチエージェント環境で自律性を広げる際に生じる調整コストは、別稿マルチエージェントのオーケストレーション税でより深く扱いました。

7. Claude Code設定との接続 - 自律性のダイヤル

動的ワークフローは抽象的な概念ではなく、Claude Codeの具体的な設定と噛み合って動きます。権限モード、許可/遮断ツール一覧、自動実行境界といった設定が「自律性のダイヤル」の役割を果たします。動的ワークフローがいくら柔軟でも、エージェントが触れられるツールの境界はこの設定が決めます。

実務で重要なのは、動的ワークフローをオンにしても制御を放棄するわけではないという事実です。むしろ動的ワークフローを安全に使うには、権限境界を普段より明確に設計する必要があります。たとえばファイル書き込みは特定ディレクトリに制限し、シェルコマンドは危険なパターンを遮断し、外部ネットワークアクセスは明示的に許可した場合のみ開く、といった具合です。こうした設定の細部は別稿Claude Codeの隠れ設定 完全整理で具体的に扱ったので、動的ワークフローを本格導入する前に併せて確認することをお勧めします。

核心原則はこうです。自律性を広げる前に境界をまず狭めよ。動的ワークフローはエージェントに「何をするか」の自由を与えますが、「どこまでできるか」の柵は人が設計すべきです。この柵が堅固なほど、安心して自律性を広げられます。

8. 開発者に与える実務的な意味

では、この変化は実際の開発者の日常に何を意味するのでしょうか。私は三つの変化を予想します。

第一に、ワークフローを組む仕事から検証を設計する仕事へ重心が移ります。かつては「AIに指示する手順を精緻に組む」のが核心スキルでした。動的ワークフロー時代には手順はエージェントが組むので、人の役割は「エージェントの結果を何で検証するか」を設計する側へ移ります。良いテスト、明確な型、速いCIがかつてないほど重要な資産になります。

第二に、観測可能性（observability）が生産性の前提条件になります。動的ワークフローは毎回異なる経路で作業するため、「エージェントが何をしたか」を事後に追跡できなければなりません。実行ログ、ツール呼び出し記録、変更履歴が残らなければ、動的ワークフローは制御不能なブラックボックスになります。ログを残すことが信頼のインフラです。

第三に、開発者の判断力がより貴重になります。エージェントが多様なタスクを自律的に処理するほど、「どのタスクを任せどのタスクを自分でやるか」「エージェントの結果のうち何を疑うべきか」を見分ける目が核心能力になります。逆説的に、自動化が増えるほど人の判断は重要でなくなるのではなく、より重要になります。

9. 現場への導入 - 現実的な示唆

この流れを実際の開発現場に当てはめてみます。いくつかの現実的な示唆があります。

  • テスト文化が前提条件：動的ワークフローの効果は検証信号の品質に比例します。テストが乏しいレガシーコードベースでは利点が大きく減ります。逆説的に、AI自動化の効果を見るにはまずテストに投資すべきです。
  • 規制領域は狭い自律性：金融・医療・公共のように変更追跡と監査が厳格な領域では、動的ワークフローを使っても自律性を狭め、すべての行動にログと承認を残すべきです。「何をしたか証明できるか」が参入条件です。
  • 小規模チームの梃子：人手の足りないチームにとって動的ワークフローは反復作業の労苦を減らす梃子になります。ただし第一順位は派手な自動化ではなく、テスト実行やリント修正のようにリスクが低く検証が容易なタスクです。
  • 母語コンテキスト：母語のコメント・課題・ドキュメントが混在するコードベースでエージェントが文脈をうまく扱うかは、依然として検証が必要な領域です。英語中心のベンチマーク性能をそのまま信頼するより、自分のコードベースで小さなタスクからまず検証するほうが安全です。

10. 批判的分析 - 動的ワークフローの影

バランスのため、反対側を明確に指摘します。動的ワークフローにはバラ色だけではありません。

  • 再現性の弱化：毎回経路が変わるため、同じ入力に同じ結果を保証しにくい。デバッグと監査が静的ワークフローより難しくなります。
  • 自信に満ちた誤答：エージェントが誤った経路をもっともらしく辿ることがあります。検証信号が弱いタスクでは、誤った結果が検証を通過してしまう危険があります。
  • 自動化の逆説：エージェントが多くを自ら処理するほど人はシステムから遠ざかり、いざ介入が必要なときに文脈を失います。航空・原発で知られたリスクがコードにも適用されます。
  • コストの不透明性：動的に経路を探索するとトークン消費と実行時間がタスクごとに大きく変わり、予算予測が難しくなります。

これらの影への共通の解は同じです。観測可能性、検証ゲート、権限境界、ロールバック経路を最初から設計に刻み込むことです。動的ワークフローを強く使うほど、この安全層の重要性も併せて高まります。

11. 今後の展望 - ハーネスが差別化の軸になる

大きな絵で見れば、動的ワークフローはAIコーディングツール競争の重心が「モデル」から「ハーネス」へ移っていることを示す信号です。モデル性能が横並びで上がるほど、同じモデルを誰がよりうまく包むか、つまりどのツールを与え、どう検証し、どう失敗を回復するかが差別化の軸になります。

私は今後1〜2年でこの流れが二つの方向に分かれると見ています。一方は自律性をさらに推し進めて「エージェントが自分で全部やる」方向、もう一方は自律性を意図的に制約して「予測可能で検証可能」な方向です。興味深いのは、結局生き残るツールは、両者の間をタスクのリスク度に応じて動的に行き来するツールだろうという点です。すなわち「自律性の量」を固定せずタスクごとに調整する能力そのものが、次の競争の核心になります。動的ワークフローはその能力の初期形態です。

12. 結論 + 今すぐ適用できる3つ

「タスクごとにハーネス」という発想は、AIコーディングの終着点ではなく方向転換です。動的ワークフローは静的ワークフローの分岐地獄をエージェントのその場の判断で吸収し、タスクの性質に合うツールと検証を毎回新たに構成します。しかしそのすべての柔軟性は、検証ループと権限境界という安全層の上で、そして人の監督のもとで動くときに価値を生みます。一言で要約すれば、動的ワークフローは自律性を高めると同時に信頼性という請求書を発行し、その請求書を設計で支払うチームだけが効果を享受します。

今すぐ適用できる三つで締めくくります。

  1. まず検証を整えよ。動的ワークフローをオンにする前に、速く明確な検証信号（テスト、型チェック、CI）をまず整備してください。検証が弱ければ自律性はリスクに変わります。
  2. リスクの低いタスクから任せよ。テストの整ったバグ修正、リント整理のように戻しやすいタスクから始め、信頼が積み上がれば範囲を広げてください。最初から本番変更を任せてはいけません。
  3. 実行ログを残せ。動的ワークフローは毎回経路が異なるため、エージェントが何をしたか追跡できなければなりません。観測可能性は選択ではなく信頼の前提条件です。
