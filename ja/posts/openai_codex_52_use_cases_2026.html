序論：12から52へ、その間に何が起きたのか

OpenAI開発者サイトのCodexユースケースのページは、2026年3月27日のインターネットアーカイブ保存版では12件の事例を掲載し、5月24日の保存版では52件を掲載していました。韓国の開発者コミュニティGeekNewsでも「Codex、活用事例集を大幅拡張」という題で紹介され、本記事はその直後の2026年5月26日に初めて公開されました。

公開当初、本記事は52件を移行・リファクタリング・テスト・ドキュメント化・運用自動化・学習の6つのコーディングカテゴリに分け、新規項目のうち注目の7つとしてRails 5→7移行、i18nの自動追加、GraphQLスキーマの進化などを挙げていました。2026-09-29に保存版のリストを1件ずつ数え直したところ、その7つは公式リストになく、増えた40件のうち17件はコーディングではない業務でした。今回の更新ではその部分を公式リストに基づいて正しました。確認できない一人称の利用経験と効果の数値もすべて削除しました。

そのため結論も変わります。12→52の拡張は「コーディングツールの事例が深まった」というより、「Codexに任せる仕事の範囲が開発の外へ広がった」に近いものです。本記事では、そのリストをどう読み、どこから試し、チームに合うリストへどう移すかを扱います。

1. 12件の頃と52件の時点 - 何が変わったのか

3月の保存版の12件は、ほとんどが開発者がすぐに思い浮かべる作業でした。大規模コードベースの理解(Understand large codebases)、プルリクエストのレビュー(Review pull requests faster)、OpenAI API連携のアップグレード(Upgrade your API integration)、難しい問題の反復解決(Iterate on difficult problems)、Slackからのコーディング作業の開始(Kick off coding tasks from Slack)、レスポンシブなフロントエンドとFigmaデザインの実装、ブラウザゲーム、ChatGPTアプリ、iOS・macOSアプリ、スライド作成、データ分析レポートです。

5月の保存版の52件には、このうち11件がそのまま残り、iOS・macOSアプリは2つの事例に分かれました。新たに加わったものにはコード移行(Run code migrations)、リファクタリング(Refactor your codebase)、ドキュメントの最新化(Keep documentation up-to-date)のような開発作業もありますが、メール整理(Manage your inbox)、会議の準備とフォローアップ、キャッシュフロー予測(Forecast cash flow)、DCF評価モデル(Model a DCF valuation)、予算対実績のレビューのような業務も一緒に入りました。事例をまとめるコレクションは、ゲーム開発・ネイティブ開発・プロダクションシステム・生産性とコラボレーション・Web開発の5つでした。

Goalsとの関係も訂正します。公開当初は「2025年末にOpenAIがCodexをGoals単位のエージェントとして再定義した」と書きましたが、/goalコマンドは2026年4月30日のCodex CLI 0.128.0に実験機能として初めて入り、5月21日の0.133.0でデフォルト有効になりました。52件の時点のリストでは「Follow a goal」が事例の一つとして入っていました。Goalsはリストの上位概念ではなく、リスト内の長い作業を最後までやり切るための方法の一つです。使い方は、同じ日に公式ドキュメントに基づいて更新したOpenAI Codex Goals 実戦活用ガイドにまとめました。

3. 増えた40件のうち注目の7件

以下の説明は各事例カードの公式要約に沿ったもので、難易度と所要時間は2026-09-29時点のカード表記です。公開当初この節にあったRails 5→7移行、マイクロサービスの抽出、セキュリティパッチの自動化、性能劣化の調査、i18nの自動追加、SQLインデックスの推薦、GraphQLスキーマの進化は、52件の時点のリストにも現在のリストにも該当するタイトルが見つからなかったため削除しました。

3-1. コード移行 (Run code migrations)

レガシーシステムを新しいスタックに対応づけ、移行をマイルストーン単位で進め、各切り替えの前に動作が同じかを確かめる事例です。カード表記は上級・1時間です。特定のフレームワークのバージョンを挙げず、「管理されたチェックポイント」を強調している点が要点です。一度に移さず、確認地点を複数置けという意味です。

3-2. リファクタリング (Refactor your codebase)

動作を変えずに不要なコードを消し、大きなファイルをほどき、重複したロジックをまとめ、古いパターンを現代化する事例です。公式要約は、この作業を小さくレビュー可能な単位に分けて進めるよう書いています。カード表記は上級・1時間です。

3-3. 目標を追う (Follow a goal)

複数ターンにわたり、検証できる停止条件に向かって作業を続ける必要があるときに目標を設定しておく事例です。カード表記は上級・長時間です。上の2つのように、終わりをテストで判定できる作業と組み合わせると役に立ちます。

3-4. コンピューター操作によるアプリのQA (QA your app with Computer Use)

実際の製品フローをクリックしながら何が壊れるかを記録し、バグレポートで締めくくる事例です。カード表記は中級・30分です。コードを読む代わりに画面を操作して検査するという点で、12件の頃にはなかったタイプです。

3-5. 依存関係インシデントの点検 (Audit dependency incidents)

公開されたパッケージ・サプライチェーンのセキュリティ勧告を読み取り専用の点検計画に変え、マニフェスト・ロックファイル・CIワークフロー・スクリプトを信頼できないコードを実行せずに調べる事例です。カード表記は上級・1時間です。セキュリティの事例が「自動パッチ」ではなく「読み取り専用の点検」として設計されている点が注目どころです。

3-6. 作業の流れをスキルとして保存 (Save workflows as skills)

うまくいったCodexの会話、レビュールール、テストコマンド、リリースのチェックリスト、デザインの規約、リポジトリ固有のスクリプトを、以後の作業で再利用できるスキルに変える事例です。カード表記は易しい・5分です。似た系統の事例として、どのフォルダーからでもCodexが実行できるCLIを作る「Create a CLI Codex can use」も一緒に加わりました。

3-7. コーディング外の業務 (Manage your inbox・Forecast cash flow)

メール整理の事例は、たまったメールを片づけ、ユーザーの口調で返信の下書きを書き、決めた周期で新着メールを確認します(易しい・10分)。キャッシュフロー予測の事例は、入力値と制約を受け取って編集可能な予測ワークブックを作り、安全残高を下回る時点と資金繰りを圧迫する前提を示します(中級・30分)。2026-09-29時点では両カードの要約が作業の主体をChatGPTと書いており、このリストがコーディングツールの中にとどまらないことを示しています。

4. Codex Use Cases vs Claude Code vs Cursor - 比較するときに見るもの

公開当初、この節は「新機能・アーキテクチャの議論はClaude Code、大規模な一括変換・運用自動化はCodex、日常の修正はCursor」という区分を利用経験として示していました。公式資料や公開された比較測定の裏付けがないため今回の更新で判定を外し、代わりに比較するときに同じ基準で記録すべき3つを残します。

  • 外部連携：52件の多くは、Slack・GitHub・メールのようなツールとの連携を前提にしています(「Kick off coding tasks from Slack」「Review GitHub pull requests」「Manage your inbox」)。別のツールで同じ仕事をするなら、その連携が公式にサポートされているかをまず確認してください。
  • 長い作業の停止条件：Codexは/goalで目標を設定し、成功・一時停止・予算上限・ユーザー入力が必要な行き詰まりなどの条件で止まります。比較するツールが長い作業をどの条件で止め、何を報告するのかを公式ドキュメントで確認し、同じ表に書いてください。
  • 検証方法：公式の事例説明は繰り返し検証を求めています。コード移行では切り替え前の動作の同一性確認、ドキュメント更新では公開前の検証ステップ、運用作業ではログ・成果物の確認です。どのツールを使うにしても、結果をテスト・ログ・チェックリストのどれで確かめたかのほうがツール名より重要です。

同じ作業を3つのツールに任せ、上の3つの欄を埋めたメモがたまれば、チームのツール分担の基準はそのメモから出てきます。ツールを比較するときによくある測定の誤りは、AIコーディングの計測でよくある12の間違いで別に扱いました。

5. 日本のSI環境に当てはめる8つ

以下の8つはOpenAI公式リストの事例ではありません。日本のSI・SM・自社サービス環境でよくある技術的負債を、公式事例のうち最も近いものに対応させたものです。公開当初に付けていた「実際に適用したもの」という説明は確認できないため削除しました。

  1. Spring 3.x → Spring Boot 3.x移行：「Run code migrations」の段階的なチェックポイント方式が合います。日本のSIで最も多く積み上がった負債の一つです。
  2. JSP → ThymeleafまたはReactへの転換：「Run code migrations」と「Build responsive front-end designs」を合わせて見ます。
  3. jQuery → Vanilla JSまたはReactへの転換：「Refactor your codebase」の小さなレビュー単位の原則に従います。
  4. Oracle PL/SQL → PostgreSQL関数への移行：「Run code migrations」に当たります。DB移行では結果の突き合わせクエリを完了条件にしてください。
  5. JUnit 4 → JUnit 5移行とテストの補強：移行は「Run code migrations」で行い、補強したテストはその後のリファクタリングの安全網にします。
  6. ログ形式の標準化と運用手順の自動化：「Run verified operations」のように、承認済みのスクリプトだけを実行し、ログ・成果物で結果を確かめる方式が合います。
  7. レガシーコードベースのオンボーディング文書：「Understand large codebases」が、リクエストの流れの追跡、見慣れないモジュールの地図、次に読むべきファイルの案内を扱います。
  8. ドキュメント・変更履歴の最新化：「Keep documentation up-to-date」が、コードの変更とPRの文脈を比べてドキュメント更新の下書きを作り、公開前の検証ステップを置きます。

公式事例のうち、閉域網環境でそのまま使えると明言したものは見つかりませんでした。外部AIサービスの利用が遮断された公共系SIでは、上の対応表を作業設計用にだけ使うほうが現実的です。

6. 罠：52件をそのまま受け取ってはいけない理由

52という数字は製品紹介でもあります。公開当初に書いた「52件のうち実際の仕事に活用したのは20件未満」という個人的な測定は削除し、代わりにリストそのものから確認できる罠を書きます。

  1. 開発の事例ばかりだと思い込まない：52件のうち19件は業務補助・データ・財務の事例です(12件の頃からあったスライド作成とデータ分析レポートを含む)。開発チームが導入効果を見積もるときに全体の件数をそのまま使うと過大評価になります。
  2. 「できる」と「本番で使える」は違う：公式の事例も、コード移行は段階ごとの動作確認を、リファクタリングは小さなレビュー単位を前提にしています。PoC → 小さな範囲 → 全社展開の順序を守ってください。
  3. 難易度の表記を無視しない：同じリストの中でも、カード表記は易しい・5分から上級・長時間まで幅があります。最初の試行は易しい事例にしてください。
  4. コストを実測する：長い作業は使用量が積み上がります。Goalsの停止条件に予算上限が入っているのもそのためです。作業の前に、今回の作業に使う上限を決めておいてください。
  5. 法的・ライセンスの罠：生成・変換したコードのライセンスと著作権、社内コードや顧客データを外部モデルに送ってよいかを先に確認してください。日本のSI契約では特に注意が必要です。

7. 開発者が作るべき自分専用のUse Case Library

OpenAIのリストをそのまま受け取るより、チームの働き方に合わせたリストを作るほうが役に立ちます。手順は次のとおりです。

  1. 1週間に繰り返した作業を20個書き出す：コード作成、リファクタリング、ドキュメント化、会議の準備、報告書作成まで、すべて書きます。
  2. 各項目に委任可能度を付ける：完全／部分／不可に分けます。基準は「結果を何で検証できるか」です。
  3. 完全委任の項目からプロンプトのテンプレートを作る：入出力の形式と検証手順を書きます。公式リストの「Save workflows as skills」のようにテンプレートをスキルとして保存しておけば、次の作業で再利用できます。
  4. 月に一度振り返る：うまくいったテンプレートは磨き、うまくいかなかったものは直すか削除します。
  5. チームと共有する：安定したリストはチームのWikiに移し、チームの資産にします。

公開当初の「6か月で20〜30件がたまる」という見込みは根拠がないため削除しました。何件たまるかより、各項目に検証方法が書かれているかがリストの質を決めます。

8. 2026年後半のCodex進化予測 (当時の見通し)

以下の3つの段落は2026年5月の公開当時の見通しで、段落ごとに2026-09-29に確認した結果を添えました。

第一に、事例のリストが再び80〜100件に増え、増える分野はドメイン特化の作業になると見ていました。9月29日の確認時点でカードは105件で、コレクションにはビジネス運営・データサイエンス・教育・財務・ライフサイエンス・営業・セキュリティが新たにできていました。方向は当たり、件数は見通しを超えました。

第二に、あるエージェントがコードを書き、別のエージェントがレビューするマルチエージェント協業が公式事例に入ると見ていました。現在のリストで、マルチエージェント協業をタイトルに掲げた事例は見つかりませんでした。「Set up a project teammate」と「Scan multiple repositories」はありますが、エージェント同士の分業を扱うかどうかは今回確認していません。

第三に、非コード領域へ広がると見ていました。この見通しは、実は公開時点ですでに進んでいました。52件の時点で業務補助・データ・財務の事例が19件あり、現在のリストには授業資料の準備(Create a classroom materials pack)、営業アカウントの優先順位付け(Prioritize accounts)、予算・日程の計画(Plan a budget and schedule)のような事例が加わっています。

10. 結論＋今週できる3つのこと

12→52は単なる項目の追加ではありませんでした。ただしその意味は、公開当初に書いた「コーディングアシスタントからエンジニアリング作業のエージェントへ」より広いものでした。増えた40件のうち17件は開発外の業務で、リストはその後105件に増え、ChatGPT側のサイトへ移りました。開発者に必要なのは全体の件数ではなく、自分のチームの仕事に合う数件と、それを検証する方法です。

今日から始められる3つです。

実行1 - 繰り返し作業を20個書き出す：今週中に、1週間に繰り返す作業を20個書き出し、各項目に委任可能度(完全／部分／不可)と検証方法を1行ずつ付けてください。

実行2 - 易しい事例1つから始める：「Understand large codebases」や「Keep documentation up-to-date」のように、カード表記が易しいの事例を実際のリポジトリに適用してみてください。結果を人が確認しやすい仕事から始めるほうが安全です。

実行3 - 3ツールの比較メモ：同じ作業をCodex・Claude Code・Cursorに任せ、4節の3つの欄(外部連携・停止条件・検証方法)を埋めたメモを1週間ためてください。

52件、今は105件という数字はスタートラインです。そのリストをチームのリストへ移す作業のほうが、ツール選びより長く残ります。

## 3. 始める順序の決定表

| 事例(公式タイトル) | カード表記 | いつ試すか |
|---|---|---|
| Understand large codebases | 易しい・5分 | 最初の試行。結果を人がすぐ確認できる |
| Save workflows as skills | 易しい・5分 | うまくいった作業の流れが1つできた後 |
| Keep documentation up-to-date | 易しい・30分 | 公開前の検証ステップを置けるとき |
| QA your app with Computer Use | 中級・30分 | 主要な製品フローの一覧があるとき |
| Run code migrations | 上級・1時間 | 切り替えごとに動作の同一性をテストで確かめられるとき |
| Refactor your codebase | 上級・1時間 | 小さくレビュー可能な単位に分けられるとき |
