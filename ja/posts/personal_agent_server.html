エージェントが常駐するサーバー - 個人が一台を回すときに新しく必要になるもの

ウェブアプリを立てるのと何が違うのか。トリガー・上限・再開・境界・記録が変わる場所

2026年9月1日 開発・インフラ

個人サーバーに何かを載せるのは古い趣味だ。写真置き場、メモ、メディアサーバー、最近はモデルの配信まで。その一覧に最近ひとつ加わったのだが、これは前のものと性質が違う。常駐するエージェントである。画面を開かなくても回り、リクエストがなくても始まり、次に何をするかをコードではなく自分で決める。

この記事はその違いだけを扱う。どのハードウェアを買うか、ポートをどう開けるかはホームサーバーの基礎のほうにある。ここで見るのは一つだけだ。誰も見ていない間も動くプロセスが、サーバーに新しく要求するもの。 リクエスト応答型のサービスを回してきた感覚では半分ほどしか対応できない。残りの半分が夜のあいだに請求書と静かな失敗になって戻ってくる。

この記事は特定の製品の導入・運用案内ではない。きっかけとなったプロジェクトは事例一つとしてのみ引用しており、確認した範囲はリポジトリとその中の文書までである。セキュリティに関する記述はすべて防御の観点であり、回避の手法は扱わない。

きっかけ - エージェントが住む家という設計

2026年8月末、韓国の開発者コミュニティに mu というプロジェクトが紹介された。Go で書かれたバイナリ一つにメール・チャット・ファイル・ノート・予定・連絡先・シェルを入れ、その上にエージェントを載せた個人サーバーである。ライセンスは AGPL-3.0、リポジトリは2025年11月に作られ、確認時点でスター420・フォーク20・タグ30（最新は v1.6.2）、最後のプッシュは前日だった。若く活発だが、検証された代物ではない。この記事が mu を使う仕方もその程度である。事例一つであって推奨構成ではない。

機能一覧より興味深いのは、このプロジェクトが自分を説明するやり方だ。リポジトリの中の文書はシステムを家に喩えながら、その喩えが何を禁じるかから書き始める。無限にスクロールする面は置かない。用事が一つ増えたからといって部屋を九つにはしない。書き手が一人しかいない面は欠陥である。そして、わざわざ家を選んだ理由を明かす。エージェントを住人の位置に置いてはじめて「別の存在がここに住み、自分がいない間に仕事をする」が機能説明ではなく普通の文になる、というのだ。

構造の線も明確だ。サービスは原子であり、互いを呼び出さず、エージェントを呼び出すこともない。この規則は文書ではなくテストで強制されており、文書がそのテスト名をそのまま書き残している。エージェントはコードでもデプロイでもなく、識別子一つにサービスの部分集合とプロンプトを足したものである。料金はエンドポイント単位で付き、上乗せ分まで設定ファイル一つに公開される。

ところが同じ文書が自分の穴を四つ書き残しており、そのうち二つがこの記事の出発点だ。一つは「家のほうから先に話しかけることがない」である。ここで自ら始まる動きはニュース取得と発火されたイベントの二つだけだと書かれている。もう一つは「組み合わせはモデル呼び出しの中でしか起きない」だ。サービスは葉のまま残り、二つのサービスを結べるのはそうすると決めたモデルだけ、という意味である。

この二文は謙遜した自己評価ではなく、正確な問題記述だ。「エージェントが住む」と「エージェントが常駐する」の距離がそこにある。前者は配置の問題、後者は運用の問題である。以下はその距離を実際に埋めるのに必要なものだ。

リクエスト応答型サービスと何が違うのか

ウェブアプリ一台は形が単純だ。リクエストが来て、仕事が起き、応答が出て、プロセスはまた遊ぶ。運用のほとんどがこの形から派生する。失敗は待っている人がいるのですぐ現れる。一回の作業が使う資源はリクエスト一つ分に収まる。同時実行数はトラフィックについていく。だから 5xx 比率と応答遅延と秒間リクエスト数を見ているだけで、たいてい答えが出る。

常駐するエージェントはこの四つをすべて破る。

  • 始まりがリクエストではない。 失敗を待っている人がいない。しかも誰も画面を見ていない時刻が一日の大半だ
  • 一回の起動が何回の呼び出しを生むかを事前に知らない。 道具をいくつ呼ぶかはモデルが決める。費用と所要時間の上限がコードのどこにも書かれていない
  • 終了条件がコードではなく判断にある。 だから無限ループが文法的に正常だ。プロセスは生きており、CPU は忙しく、ログは増え続ける
  • 作業がプロセスより長く生きる。 再起動が「最初から」を意味しなくなる。どこまで進んだかがプロセスの外のどこかに書かれていなければならない

観測する対象も一緒に変わる。ウェブアプリではログ一行と応答一つが同じ出来事だ。エージェントでは肝心の知りたいこと、すなわちなぜこの道具をこの引数で呼んだのかが、どのリクエスト経路にも残らない。残すと決めて残さなければ、単に存在しない。

トリガーが人でないとき

常駐を作るのは結局トリガーだ。トリガーが利用者一つのときは運用が楽である。三つに増えた瞬間、それぞれが別種の事故を持ってくる。

トリガーいつ回るか新しく必要なものないときに起きること
利用者のリクエスト人が待っているタイムアウト画面が止まる。すぐ気づく
時刻（定期実行）決まった時刻重なり防止、時間帯の固定、遅延実行の許容値前の実行が終わらないうちに次が始まる。夏時間の境目で一日に二回回るか一度も回らない
外部イベント（メール到着・ウェブフック・ファイル変更）他人が決める流入の速度制限、重複抑制、差出人の制限一度の急増がそのまま呼び出しの急増になる
自分の判断（前の結果が次の行動を呼ぶ）予測されない段数の上限、費用の上限、停止条件無限ループが正常動作と区別できない

重なり防止は道具がやってくれることもあれば、やってくれないこともある。cron は前の作業がまだ回っていても次をそのまま立ち上げる。systemd タイマーは同じユニットが実行中なら新しく立てず、後ろに回す。どちらを使っているのか、後ろに溜まった実行があとで集中して回るのは許容できる挙動なのかを決めておかないと、普段は静かでやけに遅かった一日に事故が起きる。自分で掛けるファイルロック一つがこの問題の大半を覆う。

  • 定期実行の時刻は UTC で固定し、見せるときだけ地域時間に変える。夏時間のある地域にサーバーがあるか、移動しながら使う機器で回すなら、この規則が値打ちを出す
  • 毎時ちょうどは避ける。ちょうどは世界中の定期作業が集まる時刻であり、外部 API の速度制限もよりによってそのとき掛かる
  • イベントトリガーは誰が引けるのかから書く。受信箱をトリガーにすれば、アドレスを知る全員がそのトリガーの共同所有者だ
  • 判断駆動のトリガーには上限を三つ同時に掛ける。段数、総費用、実時間。一つだけ掛ければ残りの二つから漏れる

誰も見ていない間に

まず費用から。エンドポイントごとに値を付け、その値をファイル一つに公開しておく mu のやり方は良い形だ。ただしその形が答えてくれるのは「この呼び出しはいくらか」までである。運用で痛い問いはもう一方だ。昨夜は何回だったのか。 だから上限は二層に要る。一回の実行が使える最大値（道具の呼び出し回数・トークン・実時間）が一つ、一日や一か月単位の総額がもう一つだ。そして上限に達したときの既定動作が「警告して続行」ではなく「止めて知らせる」でなければならない。誰も見ていない時間帯の警告は、存在しないのと同じである。

静かな失敗は三つの顔で来る。三つとも指標の上では問題なく見えるという共通点がある。

  • 再試行が失敗を吸収する。 三回目で成功すれば成功率は100パーセントと記録される。変わったのは費用と遅延だけで、その二つを見ている人がいない
  • 失敗が成功として記録される。 モデルが「そのファイルは見つかりませんでした」と答えて正常終了する。終了コードは 0 だ。定期作業でいちばん捕まえにくい形である
  • そもそも何も起きない。 タイマーが死んだかユニットが止まっている。失敗通知は失敗したときにしか来ないので、回っていないことと静かなことが区別できない

三つ目が個人サーバーでいちばん多く、いちばん長引く。対処は発想が逆だ。失敗を知らせる代わりに成功を知らせる。 正常に終わるたび外の何かへ信号を送り、その信号が決めた時間内に来なければ向こうからこちらへ連絡が来る。自分のサーバーが自分を監視すれば、電源が落ちたとき監視も一緒に落ちる。他はともかく、この一つだけはサーバーの外に置かなければならない。

死んだときどこからやり直すのか

プロセスは死ぬ。カーネル更新、メモリ不足、停電、手が滑った再起動。リクエスト応答型ではこの問いが易しい。クライアントがもう一度送ればよい。常駐エージェントには、もう一度送るクライアントがいない。

だから作業一つを設計するとき、先に答えるべきものが三つある。

  • この作業がどこまで進んだかがプロセスの外に書かれているか。メモリの中だけなら、再開という概念自体が成り立たない
  • もう一度実行したとき、二度起きると困ることがその中に混ざっているか
  • 半分だけ終わった状態は有効な状態か。そうでないなら、その半分を戻す方法があるか
操作二度やってよいか必要な仕掛け
ファイルを読んで要約するよいない。費用が二倍かかるだけだ
ローカルのノートや DB に結果を書く条件付き同じキーで上書きする。毎回新しい行を足す方式ではいけない
メールやメッセージの送信いけない送る前に「送る」を先に記録し、送ったあと「送った」に変える
外部 API での注文・決済・投稿絶対にいけないリクエスト識別子を呼ぶ側が作って送り、受ける側が重複を拒否する
ファイルの削除・移動いけない即時削除ではなく隔離フォルダへ移し、猶予期間が過ぎてから消す

三行目のやり方がこの表の核心だ。副作用がサーバーの外へ出る前に「出る」を先に書き、書いてから送る。そうすれば再起動後に「書いたが送っていない」と「送った」が区別できる。書いた直後に死ぬ区間は依然として残るが、その長さが作業全体ではなく呼び出し一つ分に縮む。運用から取り出せるのは事故の除去ではなく、曖昧な区間の縮小である。

一度だけを保証できないとき

正確に一度の実行は一般に保証されない。実務で使うのは最低一度実行し、副作用を何度行っても結果が同じになるようにすることだ。ここまではキューを扱ったことのある人には馴染みがある。エージェントでだけ新しく生まれる罠はその先にある。

  • 冪等キーをモデル出力から作ってはいけない。 同じ作業をもう一度させても文は毎回変わる。出力のハッシュをキーにすればキーが毎回新しく出て、冪等性は形だけ残る
  • キーは結果ではなく意図から作る。「9月1日付の日次要約メール」は本文が違っても同じ作業だ。対象期間と作業の種類がキーの材料である
  • 実行時刻をキーに入れない。後ろに回って遅く走った実行と定刻に走った実行が別のキーになれば、その日に二通出る
  • 二度やってよい操作といけない操作を一つの関数に混ぜない。 再試行の単位が関数全体になるので、安全な前半まで一緒に走り直す
  • 人の承認が要る操作は再開の対象ではなく再承認の対象だ。死ぬ前に得た承認を死んだあとにそのまま使えば、それは別の状況に対する承認になる

最後の項目はよく抜ける。承認は「この操作をしてよい」ではなく「この状況でこの操作をしてよい」であり、再起動とは状況が変わった可能性そのものだ。30分前に承認したファイル移動を、その間に別の作業が同じフォルダに触れたあとでそのまま実行すれば、承認はアリバイとしてしか残らない。

境界 - 隔離が塞ぐものと塞げないもの

エージェントにどこまで触らせるのか。この問いはたいてい「コンテナに入れればよいのでは」で終わるが、隔離手段ごとに塞ぐ軸が違う。軸がずれると、入れたという事実だけが残る。

隔離手段塞ぐもの塞げないもの
コンテナホストのファイルシステム接近、パッケージ・依存関係の汚染外向きのネットワーク。中から外を呼ぶのは既定でそのまま通る
専用 OS アカウント他の利用者のホーム・鍵・設定の読み取りそのアカウントが握るトークン全部。アカウントを分けてトークンを一緒に渡せば分けたことにならない
読み取り専用マウント改竄と削除流出。読めるものは外に送れる
外向きの許可リスト任意の宛先への流出許可した宛先の中で起きること。許可した API 一つがそのまま通路になる
別の物理ホスト・VMカーネルを共有して生じる問題保守量。増えた台数がそのまま一人で管理する台数だ

隔離はできることの一覧を減らすのであって、しようとしていることを変えはしない。だから境界は能力単位で引くべきであり、能力の一覧は「いまこの作業に必要なもの」だけで満たすべきだ。「あとで使うかもしれないもの」が一行入った瞬間、一覧は文書になり境界は消える。

道具の一覧で権限を表す方式には固有の罠が一つある。一覧の中の道具一つが残り全部を含みうる。 mu の既定エージェント二つでこの対比がそのまま見える。一つはすべてのサービスに届き、もう一つはシェルとアプリの二つに狭められている。個数だけ見れば後者のほうがずっと狭い。ところがその二つのうち一つがシェルだ。シェルが一覧にあれば、一覧の長さは意味を失う。狭めたかどうかを判断する基準は個数ではなく最も広い項目である。

  • 権限はエージェント単位より実行単位で狭めるほうがよい。同じエージェントでも、外部入力を読む実行と結果を書く実行が同じ権限を持つ理由はない
  • ファイル接近は経路の一覧で決める。ホームディレクトリ全体を開けてプロンプトに「気をつけろ」と書くのは境界ではなく頼みごとだ
  • 外向きの接続は既定拒否から始めて必要なものだけ開ける。逆の順で始めた一覧は決して縮まない
  • 外部の口座は最小権限の別アカウントを新しく作る。使ってきた個人アカウントを再利用すれば、事故の範囲がそのアカウントの人生全体になる

認証情報は別の問題だ

境界の話をするとすぐ「では鍵はどう渡すのか」に移っていくが、それはこの記事の軸ではない。方向だけ書けば一つだ。エージェントに認証情報そのものを渡さず、認証情報が要る操作を代わりに行う狭い通路だけを与える。その通路が何を許し何を拒むかが、そのまま実際の権限である。具体的な分離の手法はエージェントに認証情報を渡さずに仕事をさせる方法に別途まとめてあり、委任の幅をどこまで広げるかはエージェントの自律性レベルのほうにある。

あとから再構成できなければならない

基準は一つに絞るほうが楽だ。三週間後に「あのときなぜこうしたのか」と訊かれて答えられるか。 この基準から逆算すれば、何を残すべきかがおのずと出てくる。

  • 何がこの実行を始めさせたか。 トリガーの種類と、イベントならその原文。時刻だけ書かれた記録は再構成の半分をあらかじめ捨てたものだ
  • どんな入力がモデルに入ったか。 全文を残せなくても、どの文書でどの対話で何バイトだったかは最低限残す
  • どの道具をどの引数で呼び、何が返ってきたか。 事故の原因はほぼ常にこの行にある
  • モデルの識別子と版。 同じプロンプトが翌月には違う動きをする。版がなければ再現は不可能だ
  • この実行がいくら使ったか。 費用はあとから割り付けられない。実行単位で付けておかなければ月末の請求書一枚だけが残る
  • どう終わったか。 完了・上限超過・エラー・強制終了を区別する。この四つが一つの欄に固まっていると、成功率という数字が嘘をつき始める

mu の文書がスレッドを「どの扉から入ったものであれ、起きたすべての因果の記録」と定義したくだりが、この場所を正確に指している。扉が五つ（メール・ウェブ・MCP・SSH・XMPP）ある系で記録が扉ごとに別々に残れば、再構成は最初から不可能だ。記録の単位は扉ではなく出来事でなければならない。

罠も一緒に書いておく。プロンプトと道具の応答を丸ごと残せば、そのログ自体が新しい秘密の置き場になる。何を残すかと一緒に何を残さないかを決めねばならず、保存期間もその場で一緒に決める。個人サーバーではたいていディスクが先に埋まる。

外から来た文が指示になる場所

リクエスト応答型のアプリでは、外部データは保存されるか画面に表示される。エージェントでは外部データがモデルの文脈に入り、文脈の中では指示と資料が同じ形だ。メール本文、開いてみたウェブページ、課題の説明、カレンダー招待の題名、さらにはファイル名までが全部その位置に置かれる。

新しく発見された問題ではなく、一覧の一行目である。OWASP の大規模言語モデルアプリケーション脆弱性一覧で最初の項目がプロンプトインジェクションであり、そのうち間接注入は、モデルが処理する外部の文書やウェブページの中に指示が仕込まれている場合を指す。常駐エージェントはこの条件をすべて備えた形だ。外部入力を自分で取ってきて、道具を握っていて、人が見ていない。

  • 信頼境界をデータではなく能力に引く。 外から来たものを読む実行には副作用のある道具を付けない。読む実行と書く実行を分ければ、仕込まれた指示が届きうる最大値が「読み取り」で括られる
  • 外部の内容は指示ではなく引用として印を付けて入れる。ただしこれだけでは十分でない点を知って使う。最後の防衛線ではなく最初の層だ
  • 取り消せない操作の前には人の承認を置く。承認画面には「何を」ではなく「何を、どこへ」が出なければならない。宛先が見えない承認は承認ではない
  • 外向きの宛先を狭める。 要約の結果を任意のアドレスへ送れるなら、読み取り権限がそのまま流出経路になる
  • 個人サーバー特有の場所が一つある。受信箱をトリガーにした瞬間、アドレスを知る誰もがトリガーを引ける。mu のように SMTP を直接受ける構成ではこの扉が既定で開いているので、差出人の許可リストが最初の設定になる

保守要員が一人という条件

ここまでは規模と無関係な話だ。個人が回すという条件が付くといくつか足される。これらは会社では組織が吸収してくれていたものなので、最初は見えにくい。

  • 呼び出し担当が一人なら、通知は行動できるものだけ来なければならない。 一日に四十件来る通知は0件と正確に同じ情報量だ。通知を一つ足すたび「これを受け取ったらいま何をするのか」に先に答えてみる
  • 自分が作ったものを自分のサーバーが監視すれば、同じ事故が両方を殺す。 生存信号一つだけは外に置く。別の機器の定期作業一つでも足りる
  • 休暇・引っ越し・病欠がそのまま無点検区間だ。 設計が実際に試されるのはその二週間である。上限がその期間も守られるかが事実上すべてだ
  • 戻す計画がなければ更新をしなくなる。 しなければ半年後にもっと怖くなる。スナップショット一つと以前のバイナリ一式を保管する習慣が、最新を保つ前提条件である
  • 文書は半年後の自分のためのものだ。「なぜこうしたのか」がなければ、自分で掛けた制約を自分で外す。実際にいちばんよく外れるのが費用の上限である
  • 止める手順も設計に含める。 何を止めれば何が一緒に止まるかの一覧がなければ、急ぐときに電源を抜く以外の選択肢がない

個人サーバーに置く値打ちのある仕事

全部載せる必要はない。判断は機能ではなく性質で行う。同じ「日次要約」でも、対象が自分のメール箱なら値打ちが大きく、他人が待っている報告書なら初めから居場所ではない。

仕事の性質個人サーバーに置くと判断
データがすでにここにある（個人のメール・ファイル・ノート）外へ出す理由が消える値打ちが最も大きい
結果が誤っても人がすぐ見る（要約・分類・下書き）静かな失敗の代償が小さい適する
頻度が低く予測できる（一日一回）上限の設計が単純になる適する
取り消せない副作用がある（送信・決済・削除）無人実行の代償が大きい承認なしには置かない
他人が待っている（可用性が要る）一人では守れない適さない
新しさが命で外部依存が大きい外部が変われば静かに止まる監視の費用が利得を超えやすい
記録・監査の義務がある追跡を一人で維持することになるおおむね適さない

基準一つに縮めるとこうなる。夜のあいだに静かに失敗したとき、朝に気づけるか。そして気づいたとき戻せるか。 両方「はい」なら個人サーバーに置く価値がある。一つでも「いいえ」なら、その一つを先に作ってから載せる。順序を変えると作る機会が永遠に来ない。

デプロイ自体の損得、つまり何がなくなり何が新しく生まれるかはデプロイ基盤を自分のサーバーに載せるという選択にまとめてあり、作業環境を丸ごと自分の側に置く形はセルフホスティング AI ワークスペースのほうだ。

まとめ

ウェブアプリを載せることとエージェントを常駐させることの距離は、導入の難しさではなくトリガーにある。始める側が人でなくなった瞬間、失敗に気づく人もいなくなり、上限を決める人もいなくなり、どこまで進んだかを覚えているのもプロセス一つだけになる。残りの問題は全部ここから派生する。

だから新しく必要なものは一つも華やかでない。重ならないようにするロック、三重の上限、副作用が出る前に書いておく一行、能力単位で引いた境界、出来事単位の記録、そしてサーバーの外に置いた生存信号。六つだけなのは易しいからではなく、これらがなければ残りが意味を失うからだ。

きっかけとなったプロジェクトの文書が自ら書き残した文をもう一度借りれば、いまのほとんどの個人サーバーは先に話しかけてこない。 話しかけさせることが次の一歩であり、その一歩の大半はモデルの側ではなく運用の側にある。面白くないほうが残った仕事だ。

確認できなかったこと

  • mu を実際に導入して動かしていない。この記事の mu に関する記述はリポジトリのページとその中の文書二編に書かれた内容に限られ、実際の動作を確認したものではない
  • スター420・フォーク20・タグ30（最新 v1.6.2）とリポジトリ作成時点は2026年9月1日確認時点の値だ。変わり続ける数値であり、活発さが安定性を意味するわけでもない
  • mu が予約実行や定期作業をどんな形で支えるのかは文書から確認できなかった。文書が自ら「ここで始まる動きはニュース取得と発火されたイベントの二つだけ」と書き残したくだりまでを根拠とした
  • 常駐エージェントが実際にどんな事故をどれだけ起こすかについての公開統計は確認できなかった。 この記事の失敗類型は定期作業とキュー運用から来たものであり、エージェント固有の事故の頻度を主張していない
  • OWASP の項目は一覧の最初の項目名と間接注入の定義までを引用した。版によって後ろの項目の番号が変わっているので、個別の番号を引くときは版も一緒に確認しなければならない
