Making the Worst Case Constant Is a Different Goal from Making the Average Fast - Static Allocation and Constant Work

How to tell which work has a deadline, what each technique buys and sells, and the metric that actually shows you the result

2026-09-05 Dev & Infra

Saying that performance improved usually means something got faster. But in some places faster is not the goal at all. Taking the same amount of time every single time is the goal. If the average halves and one call in a hundred takes ten times longer, that is not an improvement in those places. It is a regression.

This piece is about how those two goals differ and why they usually cut into each other. It is not a collection of memory allocation tips. It is about what the decision to remove runtime allocation actually buys and what it sells, and about which metric tells you whether the trade went the way you intended.

Everything quoted here comes from a primary source, and section 1 separates what the article that prompted this piece actually says from what it does not. Where a line of argument is not in the original, the text says so at that point rather than letting it blur.

The prompt - what the original says and what it does not

On 2 September 2026 matklad published Static Allocation, Constant Work. It is short, the example code is Zig, and it uses an order matching engine as its illustration. Notably, the author writes that he has only a vague understanding of what an order matching engine is and merely suspects these tricks might help there. So the piece is best read not as a prescription for a particular domain but as a description of two design habits.

The first habit is static allocation. You take everything you will need once, at startup, and never take more. The example reserves it all in one call, with the ceiling supplied on the command line: const orders: []Order = try gpa.alloc(Order, cli_args.orders_max);. And if more than that many requests arrive at runtime, the surplus requests are rejected. The reasoning is blunt. In the article's own words, attempting to allocate just one more order could cause the kernel OOM killer to terminate the entire order matching engine, losing the other million orders, or, worse, to kill the supervisor process so that you cannot even restart.

The second habit is constant work. Rather than tracking the live objects separately through an index list or a bit set, you always iterate a fixed-size array in full. Inactive slots hold a neutral, no-op value. In the article's example an order carries a tag with the values bid, ask, and reserved, and the last of those is the neutral state.

One detail deserves care. What the original says stays flat is P100, not P99. P99 is the maximum after throwing away the slowest one percent; P100 throws nothing away and is the real maximum. That distinction blurs easily as a claim gets summarized and passed along, and as the next section shows, in work with a deadline that discarded one percent is precisely the one percent that matters.

Work with a deadline and work without one

Why constancy becomes a goal only makes sense once you sort work into two kinds. The test is a single question. If the result is not ready by a fixed moment, does the result become worthless? If yes, the work has a deadline. If no, it does not.

The classic examples on the deadline side are the audio callback, the game frame, and the control loop that moves a machine. The audio device asks for the next buffer at a fixed instant, and if the data is not there, silence goes out and the sound breaks. Producing that audio afterwards is useless because the moment has passed. The value of a late result is zero or negative. This axis is not in the original article, which never mentions deadlines, audio, or games.

Operating system documentation, however, has recorded this property for a long time. The Linux manual page for mlockall(2) states that real-time applications require deterministic timing, and, like scheduling, paging is one major cause of unexpected program execution delays. The same page goes further: real-time processes using mlockall() to prevent delays on page faults should reserve enough locked stack pages before entering the time-critical section, so that no page fault can be caused by function calls. Between those two sentences sits the whole reason that grabbing memory up front is a question of predictability rather than of speed.

/* Lock current and future mappings before the real-time section */
mlockall(MCL_CURRENT | MCL_FUTURE);

That last row is where teams talk past each other most often. Given the same idle CPU, a system with a deadline leaves it empty as insurance against the worst case, while a system without one fills it to increase throughput. Two engineers can read the same dashboard and reach opposite conclusions for exactly this reason.

Why the average and the worst case cut into each other

Most techniques that lower an average share one shape. They defer cost and pay it in a lump later. Caching does this. Lazy initialization does this. Growing an array by doubling does this. Generational garbage collection does this. Most calls become very cheap and one call occasionally becomes very expensive. The total falls. The maximum rises.

A dashboard that shows only averages is structurally incapable of showing that trade. The gain lands on the graph and the cost lands off it. This is why style guides for deadline-bound systems tend to nail the point down explicitly. The TigerBeetle style guide says to put a limit on everything because in reality everything has a limit, and it gives as its example that all loops and all queues must have a fixed upper bound to prevent infinite loops or tail latency spikes. Unbounded loops and unbounded queues are placed side by side as causes of tail latency.

The reverse direction holds too. Constant work deliberately makes the average worse. If ten items are live and you walk a hundred slots, ninety of those visits are thrown away. Total work rises and the average rises with it. In exchange, the ten-item case and the hundred-item case become the same case. The original's sentence about P100 is exactly this bargain. It does not lower the worst case; it makes the worst case permanent, and therefore flat.

One thing comes along for free, and the original lists it right alongside the performance argument. Insufficient performance is discovered when you roll the system out, not during a peak-season on-call at three in the morning. Because with no load the system does the same work it would do at full load. In that sense constant work is less a performance technique than an observability technique.

What disappears when runtime allocation goes away

It is worth counting, one by one, what the rule against allocating at runtime actually removes. Only then can you count how many of those items your own system ever had.

  • The variable cost of the allocation call itself — asking for the same number of bytes does not take the same amount of time twice. It is cheap if a free block of the right size is sitting there, more expensive if blocks must be split or coalesced, and far more expensive if fresh memory has to come from the kernel. With no runtime allocation, that entire distribution vanishes
  • Queueing behind the allocator — when several threads hit the same allocator at once, something somewhere has to order them. If nobody calls it, nobody queues for it
  • Page faults — freshly obtained memory involves the kernel the first time it is touched. This is the point behind the mlockall(2) text quoted above, which names paging as a major cause of unexpected delay. Reserving and touching everything at startup moves that cost into the startup window
  • Garbage collector involvement — no allocation means no pressure to trigger collection. On a garbage-collected language the relationship is not that simple, which is why section 10 treats it separately
  • Tail latency from fragmentation — the longer a process runs, the harder it becomes to obtain a large contiguous block. This cost is absent at first and appears days later, so a short test run almost never catches it
  • One family of use-after-free bugs — the TigerBeetle style guide gives use-after-free avoidance, alongside unpredictable performance, as its reason for static allocation. With no free and no reallocation, the very notion of a pointer to freed memory shrinks

And one more thing disappears that is not on the list: the moment of failure. If you reserve the ceiling at startup, then on a machine that does not have it the process dies immediately. Dying right after deployment is almost always better than dying at three in the morning four days later. Half the reason the TigerBeetle style guide states that all memory must be statically allocated at startup and no memory may be dynamically allocated, or freed and reallocated, after initialization lives right here.

What constant work inverts

The ordinary instinct is that doing only the work that needs doing is a virtue. You keep a list of live items and iterate that list. The original inverts the instinct. You walk the whole array and leave a neutral value in the empty slots that does not change the result.

// The form the original argues against - follow the active indices
for (orders_active) |order_index| {
    const order = orders[order_index];
    process(order);
}

// The form the original prefers - walk every slot unconditionally
for (orders) |order| {
    process(order);
}

The original gives two reasons. The first form reads an index and then uses that value to look up the array again, so each item costs two dependent accesses. The second walks memory front to back in order. In the article's phrasing, the second is much easier for the compiler to vectorize, and for the CPU cache to prefetch. And because it does the same work regardless of how many items are live, P100 latency stays flat regardless of the load.

Designing the neutral state is fussier than it looks, and correctness comes before speed here.

  • The neutral value must not change the result. Zero for a sum, one for a product, the largest representable value for a running minimum
  • If a neutral slot leaks into an aggregate, the program does not crash. It quietly produces a wrong number, and that class of bug outlives performance bugs by a wide margin
  • Reusing a slot requires distinguishing generations. That is why the original describes an object pool as a tagged union whose tag is which generation of object currently lives in the slot. Drop the generation and an old reference points at a new object
  • The bargain only works when handling a neutral slot costs roughly what handling a real one costs. If neutral is far cheaper, walking everything is pure waste; if it is more expensive, the idea makes no sense at all
  • If the array does not fit in cache, walking it in full is a net loss. The prefetch benefit appears when the contiguous memory you walk is memory you actually use
  • The original does not discuss branch prediction. Branches do not disappear; the branch that handles the neutral state simply moves inside the loop

The original applies the same reasoning to search loops with an early return. A form like const item = for (items) |item| { if (predicate(item)) break item; } else null; exits as soon as it finds a match, which is good for the average but makes the running time depend on the data. Scanning everything always takes the same time. That too is the average sold to buy constancy.

The phrase static allocation covers several techniques with fairly different characters. Laying out what each one gives, what it takes, and above all what you look at to confirm it is working makes the choice much less muddled. Arenas and ring buffers do not appear in the original; they belong to the same family, so they sit here alongside the rest.

The details on the ring buffer row are written down in the Linux kernel documentation. The head is the point at which the producer inserts items into the buffer and the tail is the point at which the consumer finds the next item. If the buffer is a power-of-two size, then a much quicker bitwise-AND instruction can be used instead of the slower wrap arithmetic. And the buffer is full when the head pointer is one less than the tail pointer, meaning one slot is permanently sacrificed to distinguish full from empty. To use it without locks, there needs to be just one producer and just one consumer, and instead of a single lock governing both ends the producer uses smp_store_release() while the consumer uses smp_load_acquire().

Cost 1 - how do you pick the ceiling

The first cost of static allocation is that you have to know the ceiling in advance. The original pushes this problem outside the code by taking the ceiling as a command-line argument. That is partly the right answer, since the ceiling depends on the deployment environment rather than on the code and should not be a compiled-in constant. But how to derive the value is not in the original.

  • Find the physical ceiling first: the machine's memory, the file descriptor limit, the network queue depth. A business ceiling larger than this means nothing
  • Then find the business ceiling: measured concurrent connections, outstanding orders, open sessions. Look at the observed maximum, not the average
  • If the observation window is short, the maximum is always an underestimate. The window must contain at least one peak season
  • Keep the ceiling in configuration rather than in the source. The same binary should run on a large machine and a small one
  • Export the number of times the ceiling was reached. Without that counter you cannot tell whether the value is a limit or merely a big number
  • Put an alert threshold at some fraction of the ceiling. Learning about it after the fact is learning about it too late
  • Setting the ceiling high is not free either. Holding the maximum permanently means you cannot put anything else on the same machine

If you also lock the memory, one more constraint appears. The mlockall(2) page notes that since Linux 2.6.9 no limits are placed on how much a privileged process may lock, and that the RLIMIT_MEMLOCK soft resource limit instead defines a limit on how much memory an unprivileged process may lock. It also states that if MCL_FUTURE has been specified, a later system call such as mmap, sbrk, or malloc may fail if it would cause the number of locked bytes to exceed the permitted maximum. Ceiling design does not end inside the application; it interlocks with the resource limits of the environment.

Cost 2 - what happens when it overflows

The second cost is heavier. Past the ceiling there is no graceful failure. More precisely: inside the ceiling everything is graceful, and outside it there are exactly five options, none of which is handling everything somehow.

  • Reject immediately — the original's choice. It only means anything if the caller has a retry policy; without one it is simply loss. Rejection does not remove the problem, it hands the problem to the caller
  • Wait — put a queue in front and let callers wait. But that queue needs a bound too. An unbounded waiting queue reinstates exactly the unboundedness you just removed
  • Drop the oldest — the common ring buffer choice. It suits data where only the latest state matters, such as a sensor reading or a screen refresh
  • Drop the newest — suits data where ordering carries meaning. You protect what is already in flight and cut off the tail
  • Degrade — keep accepting at lower precision or with features switched off. This is the most common answer in deadline-bound systems, where an approximate answer on time beats an exact answer late

Dynamic allocation picks none of those five and imitates the somehow instead. At the end of the imitation stands the OOM killer. As the original points out, what you lose at that moment is not the one request that overflowed but everything that was in flight, and in the worst case the restart path along with it. The essence of imposing a ceiling is not eliminating failure but choosing the shape of it.

So the question you actually have to answer is not whether to reject. It is what to discard and when, and writing that answer somewhere visible in the code is one of the real benefits of static allocation. In dynamically allocating code the decision is written nowhere, which is why nobody ever reviews it.

Cost 3 - full work even when there is nothing to do

The third cost is already in the name. Constant work means the system does peak-load work when there is no load. That reads as pure gain only when keeping a deadline on dedicated hardware is the sole objective.

  • Battery-powered devices — idle stops being idle. The same loop runs with the screen off
  • Usage-billed environments — CPU time is money. You pay the peak rate continuously to buy a flat maximum
  • Shared machines — your idle cost becomes the neighbouring process's latency. Without isolation the neighbour pays your bill
  • Thermally constrained devices — sustained peak work invites clock throttling, and then the deadline you were protecting starts wobbling anyway
  • Dedicated hardware where the deadline is everything — here the cost is simply invisible. You had no other plans for that CPU

The original says nothing about power or batteries. The list above is a cost that follows from the structure, and no published measurement of it was confirmed (see section 13). Measuring idle CPU utilisation in your own environment before and after is the reliable route.

There is a softened variant. Instead of the whole array, walk a fixed number of slots per cycle and continue where you left off next cycle. The maximum is still a constant and the idle cost drops. In exchange, the worst-case delay before any one item is processed grows in proportion to the array size. Whether that variant is the answer depends on whether the deadline applies per item or per cycle.

What changes on a garbage-collected runtime

The rule against runtime allocation assumes manual memory management. On a runtime with a garbage collector, reducing allocation does not make the collector go away. The direction still holds, and the official Go GC guide says why: GC CPU costs are largely determined by allocation rate and the cost per byte to scan memory.

The guide's list of latency sources makes the importance of allocation rate concrete. First, brief stop-the-world pauses when the GC transitions between the mark and sweep phases. Second, scheduling delays because the GC takes 25 percent of CPU resources when in the mark phase. Third, user goroutines assisting the GC in response to a high allocation rate. Fourth, pointer writes requiring additional work while the GC is in the mark phase. Fifth, running goroutines being suspended so their roots can be scanned. The third item is the crux: code that allocates heavily manufactures its own latency.

# The cheapest way to see the collector at work
GODEBUG=gctrace=1 ./myserver

The same tension shows up on the ceiling side. The Go memory limit is a soft limit. In the guide's words, the Go runtime makes no guarantees that it will maintain this memory limit under all circumstances; it only promises some reasonable amount of effort. The reason for the looseness is stated outright: this relaxation is critical to avoiding thrashing behaviour, because it gives the GC a way out. The mechanism is a cap on the CPU time the GC may consume, currently around 50 percent over a 2 * GOMAXPROCS CPU-second window.

What happens without that escape hatch is documented in the same place. Turn GOGC off and keep lowering the limit, and the total time the application takes will start to grow in an unbounded manner as the GC is constantly executing to maintain an impossible memory limit. And one summarising sentence lands exactly on the argument of section 8: in many cases, an indefinite stall is worse than an out-of-memory condition, which tends to result in a much faster failure.

Put together: the original keeping its ceiling hard to avoid the OOM killer, and the Go runtime keeping its ceiling soft to avoid an indefinite stall, are two ends of the same problem. Whichever end you pick, you still have to answer what happens when the limit is hit. The knob itself is simple enough — per the guide, doubling GOGC will double heap memory overheads and roughly halve GC CPU cost — so the memory-versus-CPU trade is exposed on a single dial. Actually measuring what your tools occupy and what goes wrong when a connection ceiling is set badly are covered separately.

What survives the move to servers and what does not

These principles grew up where deadlines are tight. Moving to servers and web backends, some of them are already in use under different names and others do not apply at all.

PrincipleWhere deadlines are tightOn servers and web backends
Reserve the maximum at startupNatural, since physical memory is fixedWhere instances scale up and down, one node's maximum is cost. Restated as a cap on concurrent work in flight, it holds fully
Reject surplus requestsThere is no alternativeHolds directly. It is already standard practice under the name load shedding
Iterate everythingThe data structure is small enough for cacheBarely holds. Anything like iterating all users does not fit in cache
Target P100Obvious, because a deadline existsPer-request deadlines are rare, so P99 or P99.9 is usually the operative target
Remove runtime allocationThe language permits itThe runtime does it for you. It arrives as lowering the allocation rate
Put a limit on everythingApplies as writtenApplies as written. Queue depth, connection pools, timeouts, and retry counts are all the same idea
Fill slots with a neutral stateCheap, because the array is smallRarely used. Pre-created connections and worker pools play the equivalent role

The two lines that transfer best are put a limit on everything and reject the surplus. Neither depends on a language, and on the server side both are already in use under other names. Connection pool size, queue depth, timeouts, and concurrency caps are all instances of putting a limit on everything. The TigerBeetle style guide makes the same point when it says that wherever your program interacts with external entities you should not do things directly in reaction to external events but let the program run at its own pace, and it gives as the reason that this makes it easier to maintain bounds on work done per time period.

The line that transfers worst is iterating everything. That benefit appears only when the contiguous memory you walk is memory you actually use, and server data structures generally do not fit in cache. In between sits reserving the maximum at startup: pinning one process's memory can be a loss in an elastic environment, but restated as a cap on the number of items in flight it is a straight gain.

There are also places that adopt the rule explicitly while being neither embedded nor a game. The ggml repository lists no third-party dependencies, zero memory allocations during runtime, and integer quantization support among its design goals. An inference library states zero runtime allocation as a goal not to boast about speed but to get closer to running the same way wherever it is deployed. What the hardware side decides for you before you get a say is covered in the forks in inference hardware, and the problems of squeezing into a very small device in the case of running a model on an eight-dollar microcontroller. The debate over how much memory safety to delegate to the language is laid out in the argument around memory safety absolutism.

What to measure first

That is the judgement framework. The order of actual work is short, and there is something to measure before you touch any code.

Step 1 - decide whether a deadline exists

Write down, in a sentence, where in this system a late result becomes worthless. If the sentence will not write, there is no deadline and most of the techniques here are unnecessary. If there is one, write the instant and the permitted number of overruns as numbers. The phrase it should be fast is not a deadline.

Step 2 - record the maximum

Put the maximum and the overrun count next to the average and the median. On a dashboard without those two columns, the trade described in section 3 is invisible. Record peak values for items in flight, queue depth, and pool occupancy at the same time. Those are precisely the numbers you will use to set the ceiling.

Step 3 - add a ceiling and count the hits

Add a ceiling to exactly one data structure, the largest, and export the number of times it is reached. Converting the code to static allocation comes after that. A hit count of zero means the ceiling is generous; a steadily rising one means the ceiling is tight or the upstream is letting too much through. That single number makes most of the decisions in sections 7 and 8 for you.

What I could not verify

  • I could not confirm a single normative definition separating hard from soft real time in a primary source. The text therefore avoids those terms and sorts work by the functional test of whether a deadline exists
  • I also could not confirm the definition of priority inversion or its mitigations in a primary source, so the term does not appear in the body at all. The effect of locking on deadlines is left outside this article's scope
  • The vectorization and prefetch benefits the original claims come with no measurements attached. The original argues structurally without presenting evidence, so this piece quotes no multipliers either
  • I could not verify concrete deadline figures for audio callbacks or game frames in a primary source, so none are given. Only the existence of the deadline is used
  • For arena allocators I did not open any specific implementation's official documentation. The arena row in the table therefore states only properties that follow from the definition and carries no numbers
  • I found no published measurements of how much latency allocator contention actually causes, or of how much fragmentation grows tail latency over time. The descriptions in the body follow from structure and are not measured results
  • I also found no measurement of the effect of constant work on power consumption. The list in section 9 is a cost that follows from the structure
  • I could not confirm the latency figures TigerBeetle actually achieves with these rules. What is quoted is only the normative text of the style guide
