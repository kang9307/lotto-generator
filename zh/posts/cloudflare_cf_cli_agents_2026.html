cf 是什么，能确认到哪里

cf 是 Cloudflare 以公开测试版发布的命令行工具。README 把它介绍为「为下一代软件开发打造的 CLI」，并列出四个特点：智能体可以通过定制的搜索与引导（search and steering）找到命令，JSON 是默认接口，TypeScript 配置文件 cloudflare.config.ts 提供安全性与准确性，Vite 集成支持本地开发。

本文的主轴不是介绍新工具，而是设计方向。命令行工具长期以来都以人类阅读和输入为前提。cf 展示了把这一前提换成智能体之后会改变什么，体现在命令发现、输出格式、配置格式三处。三处在原文中都有依据，所以逐一顺着对应关系看。

安装命令与 README 中的写法一致，只有下面一行。README 提示现在就全局安装开放测试版，并可在任何地方运行。

npm i -g cf

  • 博客的「数千」与 GeekNews 摘要的「3,000 以上」方向一致，但并非同一句话，所以本文引用该数字时会一并写明出处。

命令直接由 API 模式生成，这一点与覆盖范围的问题相连。手工逐个添加命令的方式，命令数量受制于作者的工作量；而从模式生成的方式，API 增加，命令也随之增加。博客的解释是，Wrangler 停留在约280项操作、而 cf 覆盖数千项操作，差别就来自这种生成方式。不过，生成出来的命令是否像人工打磨的命令那样易读，原文没有涉及。

面向人类的 CLI 在智能体面前错位的地方

说命令行工具是为人类设计的，具体指三个假设。用户大致记得命令名或能在文档里找到，能用眼睛扫读输出并挑出需要的行，配置则是复制示例稍作修改。智能体对这三点都不能原样适用。以下是解说，cf 在哪里弥补这些错位，就是后面各节的内容。

  • 命令发现。人类通过帮助文本和文档搜索找命令。把数千个命令的完整帮助塞进智能体上下文成本很高，所以需要另设一个只挑出所需命令的入口。
  • 输出消费。对人类来说对齐和颜色有帮助，但智能体更需要可解析的结构和较短的长度。同样的信息，表达方式不同，占用的上下文也不同。
  • 配置校验。人类写错配置，会在部署阶段读错误信息再修改。对智能体来说，如果在编辑时就能报错的类型检查，就能减少反复试错。
  • 覆盖范围。没有命令的任务，智能体只能绕行。命令能触及的任务范围，就是智能体仅靠 CLI 能做的事的范围。

这四点与 cf 发布文所标榜的特点重合。重合只说明设计意图方向一致，并不表示在真实智能体工作中测得了效果。发布文和 README 都没有给出效果的测量值。

可搜索的命令 - cf cli search

当数千项操作都变成命令，列表本身就成了探索的障碍。博客用一个搜索命令来解决。原文的句子是：这个命令让智能体可以用自然语言询问需要做什么，一个小型搜索索引会依据 API 描述和参数提供合适命令的列表。

  • 输入是自然语言。不需要知道命令名，只要写出要做的事。这种方式与命令名由 API 模式生成的结构相吻合。
  • 索引的材料是 API 描述和参数。搜索对象不是另写的手工文档，而是 API 模式中已有的描述。命令来自模式，所以搜索对象也来自同一源头。
  • 提示在首次运行帮助时自动进行。原文写道，智能体第一次运行 --help 时会被自动告知这个命令。README 所说的引导（steering）似乎指的就是这个位置。

作为解说，关键在于搜索结果缩小了智能体下一步的候选行动。不是让它读完整个帮助，而是只让与问题匹配的少数命令进入上下文。不过风险依然存在：如果搜索把错误的命令排在前面，智能体可能原样执行。关于这一点的准确率数字或失败案例，原文中没有。

结构化输出 - 为什么默认是 JSON

README 的句子很短。JSON 是默认接口，对人类美化输出，对智能体压缩输出。博客补了一句：压缩的目的是最大限度节省上下文。

  • 同一份数据，两种呈现。数据格式是同一个 JSON，缩进和空白是保留还是删掉，取决于对象。格式只有一种，所以人类和智能体没有各自独立的输出路径。
  • 上下文是预算。智能体读到的所有输出都会消耗上下文窗口。几个空白字符看似微小，但在数百次调用中会累积。原文把这概括为最大限度节省上下文。
  • 可解析性。这是解说。用正则去切分按行排列的文本表格，不如读取 JSON 字段来得不容易读错。字段名是否稳定，原文没有涉及。

本节的局限也很明确。原文没有给出哪个命令输出哪些字段、压缩后的输出比人类版小多少之类的数字。能节省多少上下文，需要在自己的工作里去测量。

节省了多少上下文，可以自己直接测量。把同一个查询命令的压缩输出和美化输出分别存成文件，比较字符数即可。这个比较是只读的，也没有负载。但字符数并不等于令牌数，用所使用模型的令牌计数工具重新数一遍更准确。原文没有给出这样的比较，所以得到的数值只对各自的工作有效。

配置的类型化 - cloudflare.config.ts

cf 的配置不用 TOML，而是写在 TypeScript 文件 cloudflare.config.ts 中。README 说这带来安全性与准确性，博客则说明了类型检查、自动补全以及用代码构建环境的方式。博客的示例从 cf/config 导入 bindings 和 defineConfig，用函数返回 worker 名称和环境值，函数接收 mode 作为参数。

  • 类型检查与自动补全。配置值的名称和形式在编辑时被检查。对人类是自动补全，对智能体则是在部署前指出错误键的反馈（后者为解说）。
  • 用代码构建环境。由函数按 mode 返回配置，而不是静态文件。发布文的逻辑是：环境越多，用一个函数派生，比维护多份复制的文件更有利。
  • 压缩40%的案例。博客写道，Cloudflare 内部一些 Wrangler 配置文件，从每位开发者有许多自定义环境、超过5,000行的规模，被压缩40%，变成为每位开发者构建配置的工厂文件。该案例描述的是部分内部文件。

这个40%并不是可以直接套用到外部项目的数字。40%是以什么为基准，例如行数还是文件大小，仅凭发布文的句子无法确定。配置类型化能把智能体的任务成功率提高多少，原文也没有数字。

与 Wrangler 的关系和 cf migrate

对已有 Workers 项目的一方来说，最关心的是迁移步骤。博客给出的关系有三条。迁移命令是 cf migrate，转换结果取决于项目的构建方式，测试版结束后 Wrangler 在一段时间内仍会得到维护。

项目状态cf 的行为（原文）本文的解说
已经用 Vite 构建的 Worker会被转换为 cloudflare.config.ts转换后配置变为 TypeScript，因此把 diff 作为审查对象
依赖 Wrangler 的 esbuild 的 Workercf 继续把构建委托给 Wrangler这是暂时需要同时保留 Wrangler 的配置
静态站点无需配置文件即可开始，用 cf deploy 部署新建静态项目的入门门槛很低
测试版结束后Wrangler 获得18个月的维护支持18个月是迁移宽限期的上限
  • 迁移从一个命令开始。原文所指引的迁移入口是 cf migrate。转换什么由项目的构建方式决定。
  • Wrangler 不会立刻消失。测试版结束后承诺提供18个月的维护。这句话的用意是留出迁移的时间。
  • 存在并非完全迁移的混合配置。依赖 esbuild 的 Worker 使用 cf，但构建仍留在 Wrangler。迁移之后两个工具并存。

测试版期间的迁移，最好先定好退路。这是解说：把配置文件放在版本控制中，并在单独的分支上审查转换结果，恢复原状就很简单。本文不以删除或部署这类改变状态的命令为例。

18个月这一期限是制定迁移计划的基准线。测试版何时结束尚未确定，所以这18个月的起点也未定。因此能放进日程表的是顺序，而不是日期。先从已经用 Vite 构建的项目开始审查转换结果，依赖 esbuild 的项目保持 Wrangler 并存的配置，等测试版结束的公告发布后，再决定其余项目的迁移时间。

描绘智能体的工作流 - 从查询到审查变更

前面各节是把功能逐个拆开来看。本节把这些功能串成一条工作流。以下是只用原文中出现的功能画出的解说性场景，并不是对真实 cf 行为的演示记录。删除或部署这类会改变状态的步骤，被有意略去。

  1. 第一次运行帮助。智能体第一次运行 cf 的 --help 时，会自动被告知入口 cf cli search。无需人类把命令清单贴进提示词，这是该设计的第一个好处。
  2. 用自然语言询问候选。智能体用一句话问要做的事，就会返回基于 API 描述和参数的候选命令列表。候选可能有多个，这份列表就成为下一步决策的材料。
  3. 只选择查询类命令。按人类事先定好的规则，只允许运行候选中不改变状态的命令。原文没有提到能区分命令是查询还是变更的功能，所以这个区分是使用方的规则。
  4. 读取压缩后的 JSON。运行结果以为智能体压缩的 JSON 返回。人类若想查看同一结果，同一命令会以美化后的形式输出。
  5. 配置变更放在类型检查之后。需要配置的变更在 cloudflare.config.ts 中进行，先解决编辑器类型检查和自动补全给出的错误。最后设一个环节，在应用之前由人类审查变更。

在这条流程里，cf 承担的是命令发现、输出和配置检查，不承担允许什么的判断。判断留在人类制定的规则和审查环节中。发布文没有提到与这一判断层相关的功能。

这样划分流程，也能看出瓶颈出在哪里。在有数千个命令的工具里，瓶颈不在于命令不够，而在于决定在什么条件下允许哪些命令。扩大智能体可用命令的范围，与在该范围内收窄允许清单，需要同时进行。扩大由工具完成，收窄由运维者完成。

采用前要核对的事项与测试版的局限

设计意图听起来合理，与可以放到生产环境，是两回事。cf 在发布时是公开测试版，以下是采用前需要自己回答的核对项。每一项都区分了原文说了什么和没说什么。

  • 确认包名。安装命令是 npm i -g cf。名字只有两个字母，可能与其他包混淆，所以安装前先确认发布 README 的仓库是 cloudflare/cf。
  • 测试版的范围。作为公开测试版，命令和输出格式可能变化。原文没有区分哪些命令处于稳定阶段，所以如果智能体脚本依赖输出字段，请固定版本。
  • 先从只读开始。最先交给智能体的任务，最好是查询这类不改变状态的操作。搜索选出的命令可能是删除或变更命令，所以在执行前要设一个由人确认的环节。
  • 凭据的范围。命令有数千个，也意味着智能体可用的权限范围很宽。令牌要收窄到所需范围。凭据设计在 CLI 认证指南中有讲。
  • 确认 Wrangler 依赖。先看项目是否依赖 esbuild。如果依赖，即使迁移到 cf，Wrangler 仍会保留。

与同一家公司其他发布的关系，已在各自的文章中讲过。智能体运行时方面参见 Cloudflare OS 一文，Vite 团队加入参见 VoidZero 加入一文。不经预览就不执行命令的设计，--dry-run 设计一文已有梳理。

核对项里相当一部分不用运行就能回答。确认包名与仓库、确认项目的构建方式、审视令牌范围，都只靠阅读就能完成。需要运行的只有亲自确认搜索和输出格式，而且一个查询类命令就足够。采用判断所需的信息大多可以通过这种不改变状态的确认得到，这是处理测试版工具时的安全起点。

  • 「3,000 以上」的操作数量。博客原文的句子是「数千」，README 和博客都没有给出确切数字。3,000 这个值只出现在 GeekNews 摘要中。
  • cf cli search 的搜索准确率和实际输出示例。原文只说明了工作方式，没有给出各查询的结果或失败率。
  • JSON 输出的模式和压缩程度。字段构成以及相对人类版的缩减比例，原文中没有。
  • 配置压缩40%的基准。超过5,000行的内部配置相对什么减少了40%，是行数还是大小，仅凭句子无法确定。
  • 公开测试版的结束时间和正式发布日期。只给出了测试版结束后18个月这一期限，没有给出结束日期。
