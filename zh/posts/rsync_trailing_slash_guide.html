引言: 昨天的命令今天给出不同结果时

在 rsync 这边听到这句话，十有八九是一个斜杠。把两行并排放着看。

rsync -a /tmp/src  /tmp/dst/
rsync -a /tmp/src/ /tmp/dst/

区别只有源路径末尾的一个 /。结果这样分岔: 第一行建出 /tmp/dst/src/ 并把内容放进去，第二行把内容直接摊在 /tmp/dst/ 下面。

到这里还只是不方便。真正的问题出在同一行加了 --delete 的时候。那一刻，一个斜杠的差别不再是「多了一层目录」，而是「目标目录里原有的东西全没了」。rsync 没有撤销，被删掉的文件也不经过任何回收站。

本文把这条规则钉死，标出加了 --delete 之后哪里是不可逆点，并留下一套按回车之前只需一秒的确认流程。rsync 选项的全面介绍 — 压缩、SSH 连接、限速、断点续传 — 放在 Linux Rsync 命令完全指南那边。这里只深挖出事故的那一个点。

1. 斜杠改变的不是路径，而是「你在搬什么」

规则本身只有一句。源路径末尾的 / 表示复制这个目录的内容，没有斜杠则表示按名字复制这个目录本身。

手册还把这条规则写成了一个等式。下面两行产生完全一致的结果，连目标目录的属性设置方式都相同。

rsync -av /src/foo  /dest
rsync -av /src/foo/ /dest/foo

这个等式是记住规则的最快途径。去掉斜杠，等于在目标路径上多加一段名字。每当拿不准源路径要不要加斜杠时，想一想目标路径会怎么变长，答案自己就出来了。

补一句: 斜杠的个数无所谓。/tmp/src// 与一个斜杠的行为完全一样。这不是冷知识 — 第 9 节会直接用这个性质来搭脚本的防线。

2. 四种组合的结果放进一张表

先把前提固定住。/tmp/src 里有 a.txt 和 sub/b.txt，/tmp/dst 已经作为目录存在。

命令目标端出现的东西含义
rsync -a /tmp/src /tmp/dst/tmp/dst/src/a.txt
/tmp/dst/src/sub/b.txt		连目录一起
rsync -a /tmp/src /tmp/dst/同上目标端斜杠无影响
rsync -a /tmp/src/ /tmp/dst/tmp/dst/a.txt
/tmp/dst/sub/b.txt		只要内容
rsync -a /tmp/src/ /tmp/dst/同上目标端斜杠无影响

这张表要从两个方向读。竖着看，目标端的斜杠什么都不改；横着看，源端的斜杠改变了一切。这样读过一遍，以后敲命令时眼睛会先落到源路径的末尾。

目标目录还不存在时 rsync 会替你建，但只建一层。如果目标路径的上级整个都不存在，rsync 建不出目录就会停下。需要连中间路径一起创建时，加上 --mkpath。

3. 目标端斜杠唯一起作用的地方

上面那张表里，目标端斜杠什么也没做。只有一个例外: 把单个条目复制成另一个名字的时候。

rsync 要把搬运的条目改名为目标路径的最后一段，下面三个条件必须同时成立。

  • 传输清单只包含单个条目 — 一个文件，或者一个空目录
  • 目标路径的最后一段不能已经作为目录存在
  • 目标路径不能带末尾斜杠

第三条就是本节的要点。实际的分岔是这样的。

rsync -a a.txt /tmp/dst/b.txt
# -> /tmp/dst/b.txt          名字被改掉

rsync -a a.txt /tmp/dst/b.txt/
# -> /tmp/dst/b.txt/a.txt    b.txt 被当成目录

一个斜杠把「以这个名字保存」和「保存到这个目录里面」分开了。如果脚本用变量拼装目标路径，还习惯性地在末尾补一个 /，改名就会悄悄失效，多出一个谁也没料到的目录。而这种失败不会报错。所以它通常要过几天才被发现。

归纳起来，目标端的斜杠规则只有两行。

  • 同步目录时 — 加不加都一样。加上略好一些，能告诉读代码的人目标是个目录
  • 给单个条目改名时 — 不能加

4. -a 实际启用了什么，又没有启用什么

-a 不是一个选项，而是一个组合，准确说等价于 -rlptgoD。知道里面有什么，才看得出漏在哪里。

选项启用的行为没有它会发生什么
-r递归进入子目录目录被整个跳过
-l把符号链接原样复制为链接链接从清单里消失
-p保留权限按目标端 umask 重新决定
-t保留修改时间每次运行都全量重传
-g保留属组变成目标端默认属组
-o保留属主 (仅超级用户有效)归执行账号所有
-D保留设备文件与特殊文件这些条目被丢掉

实际工作中被 -t 这一行咬到的次数最多。rsync 的默认判定是「大小或修改时间不同就传输」。不保留时间，下次运行时所有文件都像是新的，「为什么每晚都全量传输」这个经典抱怨就是从这里来的。

接下来是更重要的一半: 没有包含的东西。

  • -H — 查找并保留硬链接。不会启用
  • -A — ACL。不会启用
  • -X — 扩展属性 (xattr)。不会启用
  • -U 访问时间、-N 创建时间。两者都不会启用
  • --delete — 绝不包含。这里是核心
  • 一条例外 — 同时使用 --files-from 时，-a 里的 -r 不再被隐含

以为 -a 会顺手删除，这个误解会从两个方向制造事故。信它会删，目标端就留着旧文件，一次发布变成两个版本的混合物；明知它不删却习惯性地跟着敲 --delete，迟早删掉不该删的。把 rlptgoD 这七个字母记牢，两种事故同时被堵住。

5. 启用 --delete 之前必须知道的事

--delete 是一个销毁数据的选项。带着它的命令行，不能和别的命令行放在同一个重量级上对待。手册在这一条下面就直说了: 这个选项若使用不当会很危险，先用 --dry-run(-n)试跑一次看看哪些文件将被删除，是非常好的做法。读完本节不要直接动手，先把第 7 节读完。

把这个选项做的事写准确: 删除接收端存在而发送端不存在的文件，范围仅限于正在被同步的那些目录。

值得细读的是「发送端不存在」这个判定标准。rsync 不会去问它为什么不存在。你在源端有意删掉的文件、因为路径打错而看不见的文件、因为挂载掉了而看不见的文件，判定结果一模一样。正是这种不加区分，制造出第 6 节里的全部事故场景。

几个需要记住的条件。

  • 必须有递归(-r)或 -d 生效，删除才会发生。-a 里含有 -r，所以通常已经是开着的
  • 发送端检测到 I/O 错误时，删除会被自动禁用。这确实是一道保险，但「源是空的」并不是 I/O 错误。不要把它当成你的防线
  • 被 --exclude 排除的文件，即使在目标端也不会被删除。要让它们被删，必须另外启用 --delete-excluded
  • 从 rsync 3 起，若不另行指定，默认是一边传输一边逐步删除
选项删除时机与行为什么时候用
--delete默认行为 (当前为传输过程中删除)常规镜像同步
--delete-before传输开始前一次性删除目标端剩余空间紧张时
--delete-during (--del)边传输边逐步删除文件数量极多、想省内存时
--delete-delay传输中计算，结束后删除想缩短不一致状态窗口时
--delete-after传输全部结束之后目标端正在提供服务、文件突然消失会出问题时
--delete-excluded连被排除的条目一起删要让目标与源完全一致时
--max-delete=N超过 N 个就中断所有自动化都该默认系上的安全带
--backup --backup-dir=DIR不删不覆盖，而是移走要留一条退路时

这张表里价值最大的是最后两行。上面六行是看场景的偏好，下面两行是保险。尤其 --backup-dir，它是唯一能让一条 rsync 命令变得可撤销的装置。

6. 一个斜杠导致数据消失的完整路径

本来打算执行的命令是这条。

rsync -a --delete /tmp/src/ /tmp/dst/
# 让 /tmp/dst 与 /tmp/src 的内容保持一致

这里漏掉一个斜杠。

rsync -a --delete /tmp/src /tmp/dst/
#                          ↑ 没有斜杠

按顺序写出会发生什么。

  1. 源被解释成「一个叫 src 的目录」
  2. 发送端的整个清单变成 src/ 及其下面的条目
  3. /tmp/dst 直下原有的每一个条目都成了「发送端不存在的文件」
  4. --delete 把它们全部删掉
  5. 剩下的只有一个 /tmp/dst/src/

目标目录原有的内容全部消失，原地只剩下一份深了一层的副本。这就是 rsync 事故的标准形态。忘记加斜杠本身只是个常见笔误，只有当它遇上 --delete 时才会走到这个结局。

6.1 通向同一结局的另外三条路

源没有挂载的时候。备份源是外接硬盘或网络卷，而挂载掉了，那么挂载点目录仍然存在，只是空的。rsync 读成「发送端一个文件也没有」，于是把目标端全部删掉。和路径打错不同，这种情况连错误都不报，是正常退出。只看退出码来记录成功的自动化，会把一次事故归档成一次成功。

变量为空的时候。下面这一行如果在目标变量为空的状态下运行，目标就变成了 /。

rsync -a --delete "$SRC/" "$DST/"
# DST 为空 -> 目标变成 /

会删掉什么，就不必再解释了。反过来，SRC 为空则源变成 /，把整个根文件系统往目标里推。后者顶多是把磁盘塞满然后停下，前者会让你失去这台机器。如果是 AI 智能体或自动化在拼装 shell 变量来生成命令，风险还要再加一层 — 性质相近的事故在 PowerShell 变量冲突事故里讲过。

后来才加过滤规则的时候。一直跑得好好的镜像任务，有人加了一条 --exclude。几天后又有人发现被排除的文件还留在目标端，于是打开 --delete-excluded 去清理。那一瞬间，此前一直被保护着的文件被一次性删光。只是多了一个选项，删除的范围却在底下变了。

6.2 不可逆点就是回车键

明确写下来: rsync 没有撤销。被 --delete 删掉的文件不经过回收站，目标端是远程时会立刻从那台服务器的文件系统上消失。删掉之后唯一能做的就是从另一份备份里恢复，而如果那份备份就是你刚刚跑的这条 rsync，那就什么都不剩了。

备份要分代保存，原因就在这里。单一的镜像不是备份。源端删掉、目标端跟着删掉的结构，按定义就会把事故原样复制一份。世代与保留周期怎么划分，在 云备份完全指南和 databasement 深度分析里讲过，放在家里的硬件那一侧则在 NAS 家用服务器怎么选里。

7. 删除前一秒钟就能确认的方法

加一个 -n 就够了。流程分三步。

# 1) 确认 - 加 -n，什么都不改地跑一遍
rsync -avn --delete /tmp/src/ /tmp/dst/

# 2) 读输出  (读法见第 8 节)

# 3) 从 shell 历史调出那一行，只删掉 n 这一个字符
rsync -av --delete /tmp/src/ /tmp/dst/

第三步最关键。不要重新输入路径。你验证过的命令和你执行的命令只差一个字符，检查与执行之间就没有让笔误钻进来的缝隙。把命令重打一遍的习惯，会让整套确认流程失去意义。

-n 让 rsync 做一次什么都不改的试运行，输出与真实执行基本相同。这里的「基本」到底覆盖到哪，需要弄准确。

  • 可以信的 — --itemize-changes(-i)的输出被设计成在试跑和随后的真实执行中保持一致。也就是说，用 -ni 看到的条目清单和每个条目的变更原因，就是将要发生的事
  • 不能信的 — 试跑不会真正发送数据。因此「已发送字节」「已接收字节」这类统计都会偏小，--progress 也没有作用。用试跑去估算传输量或耗时，得到的一定是错的数字

一句话概括: 相信它对「会改什么」的回答，不要信它对「要跑多久」的回答。

放进 cron 或 CI 之前再强调一遍。任何进入自动化的 --delete 命令，都必须有人手工用 -n 跑过。没有什么比第一次执行发生在调度器里面的删除命令更危险了。没人盯着，出了问题下个周期还会再跑一次。

8. 怎样读懂 dry run 的输出

只加 -v 的话，出来的是一串文件名，回答不了「这个文件为什么又要传一遍」。加上 -i 就有答案了。

rsync -ain --delete /tmp/src/ /tmp/dst/

-i 会在每个条目前面加一段 11 位的摘要，格式是 YXcstpoguax。每一位的含义是固定的。

位符号含义
1Y更新的类型
2X条目的类型
3c内容 (校验和) 不同
4s大小不同
5t修改时间不同
6p权限不同
7o属主不同
8g属组不同
9u保留位 (访问时间一类)
10aACL 不同
11x扩展属性不同

前两位上会出现的字符值得单独记一下。

位字符含义
第 1 位<正在发往远程主机
第 1 位>正在本机接收
第 1 位c本地创建或变更 (例如创建目录、创建链接)
第 1 位h它是指向另一条目的硬链接
第 1 位.不更新 (属性仍可能被调整)
第 1 位*后面是一条消息 — 删除就出现在这里
第 2 位f文件
第 2 位d目录
第 2 位L符号链接
第 2 位D设备
第 2 位S特殊文件 (套接字、FIFO 等)

属性位怎么填，有三条规则。

  • 新创建的条目，每个字母位都换成 +
  • 完全相同的条目，点会换成空格
  • 无法确定的属性显示为 ?

8.1 读法练习

>f+++++++++   接收一个全新文件
>f..t......   内容相同，只是把修改时间对齐
>f.st......   大小和时间都不同 = 内容变了
.d..t......   目录本身没变，只调整时间
cd+++++++++   新建一个目录
*deleting     删掉它

最后一行最重要。只要出现哪怕一行 *deleting，就该在那里停下来把整份清单读完。如果将被删除的数量与预期对不上，那条命令就是错的。

数一数也是办法。清单往往长到没法用眼睛扫。

rsync -ain --delete /tmp/src/ /tmp/dst/ | grep -c '^\*deleting'

本该输出 0 的任务却打出一个三位数，那就是你刚刚在它造成损失之前抓住了一个笔误。有些团队干脆把这一行接进发布脚本当作起飞前检查，数量超过阈值就让流水线失败。

9. 七个常见错误与各自的防线

  1. 源路径漏掉斜杠 — 结果深了一层，一旦碰上 --delete，目标就被清空。防线: 在脚本里不要把斜杠写进变量，而是在使用处永远写成 "$SRC/"。即便变量值本身已经以斜杠结尾，// 也等同于一个，两种情况都安全
  2. Tab 补全替你加上的斜杠 — 手打和补全给出的是不同的命令。防线: 补全之后用眼睛看一遍源路径的末尾。带 --delete 的行尤其要看
  3. 以为 -a 包含 --delete — 目标端留着旧文件，发布变成混合物。防线: 记住 -a 就是 rlptgoD 这七个字母
  4. 目标变量为空 — 目标变成 /。防线: 在脚本开头放上 set -euo pipefail 和 : "${DST:?}"。只靠 set -u 抓不到「已定义但是空字符串」
  5. 源的挂载掉了 — 目标全灭，而且不报错。防线: 在 rsync 前面立一道 mountpoint -q，并配合 --max-delete
  6. 无法保留时间的文件系统 — exFAT 和部分网络共享的时间精度不同，会导致每次全量重传。防线: 用 --modify-window=1 给出容差。如果连权限都保不住，就从 -a 降到 -rlt，或加上 --no-p --no-g --no-o
  7. 排除规则与删除相冲突 — 被 --exclude 命中的文件，即使在目标端也不会被删。不知道这点会变成「为什么删不掉」，不知情地打开 --delete-excluded 则会变成「为什么被删了」。防线: 先用一句话写清楚你要的是哪一种，再去选选项

远程路径的规则完全一样。user@backup.example.com:/srv/data 和 user@backup.example.com:/srv/data/ 的区别与本地毫无二致，只是多了「冒号后面是路径」这一点。远程不会让规则变宽松，反而会让事故被发现的时间拖得更长。

10. 把不可逆点标出来的脚本骨架

带 --delete 的那一行，值得与其它行区别对待。下面这段可以直接当骨架用。

#!/usr/bin/env bash
set -euo pipefail

# 变量末尾不放斜杠，在使用处才加。
SRC=/srv/app/current
DST=/mnt/backup/app

: "${SRC:?源路径为空}"
: "${DST:?目标路径为空}"

mountpoint -q /mnt/backup || { echo "备份卷未挂载"; exit 1; }

rsync -a --delete \
  --max-delete=100 \
  --backup --backup-dir="/mnt/backup/_trash/$(date +%F)" \
  --log-file=/var/log/app-sync.log \
  "$SRC/" "$DST/"

逐行说明它各自挡住了什么。

  • set -u — 用到未定义的变量就当场退出
  • : "${DST:?}" — 变量是空字符串时同样退出。补上 set -u 留下的那个洞
  • mountpoint -q — 堵住挂载掉了这条最安静的事故路径
  • --max-delete=100 — 打算删得比预期多时，rsync 会自己停下。数字按这个任务平时的删除量来定
  • --backup-dir — 将被删除或覆盖的文件不再消失，而是移进那个目录。这是唯一能留下退路的装置
  • --log-file — 事后能查到究竟删了什么。这是出事之后再也造不出来的材料
  • "$SRC/" — 变量里不带斜杠，在使用处才加。第 9 节第 1 条的防线就落在这里

在此之上，再加两条由人来执行的流程。

  • 新写的每一行 rsync 都要加 -n 跑一次。没有例外
  • 用了 --backup-dir，就同时把清空那个目录的周期也定下来。否则先被填满的会是备份卷

11. 没能亲自执行验证的部分

把本文无法通过执行确认的条目集中在一处。

  • 代码块里的输出。这里给出的输出形态遵循 rsync 文档所规定的格式，并非在撰写本文的环境中运行后截取的结果 — 那个环境里没有安装 rsync
  • 因此，各种选项组合的结果都应当按「在自己的环境里用 -n 确认一次」的前提来读。表中写的是手册规定的行为，具体细节会因发行版、版本、文件系统而不同
  • 版本差异。--mkpath 是相对较晚才加入的选项，而仅凭 -d 也能触发删除是从 rsync 2.6.7 之后开始的。老机器上同样的命令可能表现不同
  • 目标路径不存在时 rsync 会替你建几层，以及那时确切的报错文字，都没能验证。只建一层这一点有文档依据，文字则随版本而异
  • exFAT 与网络共享的时间精度。每次全量重传是广为人知的现象，但具体哪种挂载选项会产生几秒偏差，不在本文核实的范围内
  • --max-delete 触到上限时的退出码。若打算在自动化里拿这个值做分支判断，最好在自己的版本上亲自测一次

常见问题

Q. src 和 src/ 到底差在哪?

源路径末尾的斜杠表示「这个目录的内容」，没有则表示「这个目录本身」。所以 rsync -a /tmp/src /tmp/dst 建出 /tmp/dst/src/，而 rsync -a /tmp/src/ /tmp/dst 直接摊在 /tmp/dst 下面。记成「去掉斜杠等于在目标路径上多加一段名字」就不会混。

Q. 目标路径末尾也要加斜杠吗?

目录对目录同步这种常规场景下结果相同。例外是把单个条目复制成另一个名字的时候。这时需要传输清单只有单个条目、目标路径最后一段不能已作为目录存在、目标路径不带末尾斜杠。三条中缺一条，改名就会悄悄失效。

Q. 用了 -a，目标端独有的旧文件会被删吗?

不会。-a 是 -rlptgoD 这七个字母的组合，其中不含删除。硬链接、ACL、扩展属性、访问时间、创建时间也都不会启用。要让目标与源一致，必须显式启用 --delete，而一旦启用，这条命令的性质就变了。

Q. 怎样安全地试验 --delete?

先加 -n 跑。三步: 执行 rsync -avn --delete 读输出，核对标记为删除的行数和内容是否符合预期，再从 shell 历史调出那一行只删掉 n 一个字符。再配上 --max-delete 设上限、--backup-dir 留退路，防线就有三层。

Q. dry run 的输出和真实执行完全一样吗?

一部分一样。--itemize-changes 的输出在试跑和真实执行中应当相同，所以「会改什么」这个答案可以信。但试跑不会真正发送数据，传输量统计会偏小，--progress 也没有作用。「要跑多久」这个答案不能信。

结论: 从今天起改三件事

第一，先看源路径的末尾。读一条 rsync 命令时，眼睛该落的第一个位置不是选项，而是源路径的最后一个字符。有斜杠是内容，没斜杠是连目录一起。这一眼就能挡住绝大多数事故。

第二，变量里不放斜杠，在使用处才加。写 SRC=/srv/app，用的时候写 "$SRC/"。因为值本身带不带斜杠结果都一样，团队里不管谁怎么赋值，命令的含义都不会晃动。

第三，带 --delete 的行，绝不在没有 -n 的情况下第一次执行。确认、从历史调出、删掉一个字符。再叠上 --max-delete 和 --backup-dir，人出了错工具还能再拦一次。

最后说一句。这篇文章的题目看起来是斜杠，真正的题目却是如何对待那些收不回来的命令。rsync 恰恰把这类命令做成了极短、极好敲的形式。短意味着方便，不意味着安全。越是顺手的工具，越要把防线立在工具之外 — 立在脚本骨架里，立在手指的习惯里。
