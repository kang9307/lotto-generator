One Character Is Not One Column Wide - East Asian Width and Where Terminal Tables Drift

Character count, byte count and display width are three different numbers, and alignment depends on the third

2026-07-31 Dev & Infra

The symptom: the table drifted only on the CJK rows

An inventory table printed by an operations script lined up perfectly on the ASCII rows, but every row containing Korean text was pushed to the right. Nothing in the code looked wrong. Every cell went through the same function with the same target width. And yet on screen the columns did not meet.

There is exactly one cause. The padding function counts a different number than the terminal does. Python ljust and JavaScript padEnd both fill based on how many characters there are. The terminal draws based on how many columns are occupied. Hangul, Han and kana each take two columns per character, so matching the character count guarantees the column count is off.

This is where a fifth number shows up. A single string already carried four: byte count, code unit count, codepoint count, and the grapheme count that a human would call the number of letters. Those four are pulled apart in the piece on why one emoji counts as eleven characters. This article deals only with the fifth number layered on top of them, display width.

  • Display width cannot be derived from any of the other four. As we will see, some three-byte characters have width 1 and others have width 2
  • Display width is not decided by the character alone either. Unicode has a class it explicitly marks as ambiguous, and the environment decides those
  • So the conclusion here is not «count CJK as 2». The practical goal is separating the places that must count width from the places that must count characters, and making output that stays readable even when it drifts

Environment. Every number below was actually executed on Windows 10 Pro (10.0.19045). The tools were the unicodedata module built into Python 3.13.3 (win32), which carries Unicode data 15.1.0, and Node.js v22.16.0 (win32). Standard output was pinned to UTF-8.

Missing libraries are reported as missing. This machine does not have the Python wcwidth package installed, and it does not have the Node string-width package either. Every width value below was therefore computed inside the script. These numbers come straight from Unicode property values, not from any third-party implementation's judgement.

Nothing here relies on rendering. Every claim was decided from codepoints and width property values. «It looks like this in my terminal» was never used as evidence, and every character is written alongside its U+XXXX value. How many columns something is actually painted in is a separate problem owned by the font and the terminal, and that boundary is handled in section 3.

Out of scope. The difference between bytes, code units and graphemes lives in ZWJ sequences and length validation. The mechanics of one letter becoming two different codepoint sequences live in NFC and NFD; here section 4 only looks at what normalization does to width. Text mangled by reading bytes with the wrong encoding belongs to cp949 and UTF-8 and is unrelated.

The first two lines summarise the whole article. kim and 김철수 are both 3 characters. Their byte counts are 3 and 9, their column counts are 3 and 6. ljust(8) inserted exactly 5 spaces on both sides. The function was scrupulously fair and the result is 3 columns off.

  • Same character count, different width. Padding built on a character count is therefore guaranteed to drift
  • Counting bytes fails too. 김철수 is 9 bytes but 6 columns. Three bytes to two columns is not even an integer ratio
  • The size of the drift equals the number of wide characters in that cell. 김철수 has 3 wide characters and the drift is exactly 3 columns
  • An ASCII-only table will never have this problem. Inside the ASCII range all three numbers agree. The trouble starts the moment one wide character enters

The column marked eaw is the subject of this article. It is the East Asian Width property, a value Unicode attaches to every codepoint. The first six characters carry Na and the last three carry W. The next section counts how many such values exist.

2. The six width values - W, F, H, Na, A, N

  • W and F differ by provenance. W is wide to begin with; F was created separately as the fullwidth form corresponding to a narrow character. The outcome is the same two columns
  • H runs the other direction. It is the halfwidth form corresponding to a wide character and takes one column. Halfwidth katakana belongs here
  • The won sign U+20A9 being H stands out. It is a currency symbol yet it is classified halfwidth. Section 4 shows why that matters
  • N does not mean «unknown character», it means «character that was never in a legacy East Asian encoding». Arabic letters and pictographs land here. In practice they are treated as one column
  • A is not one more width, it is the absence of a decision. This class takes up half of this article
  • UAX #11 explicitly says the property is not a rendering metric. In the standard's own terms the actual display width of a glyph is given by the font and may be further adjusted by layout. The property records a convention for fixed-width contexts, not a screen measurement

3. Ambiguous width (A) is the real problem

UAX #11 states that ambiguous characters require additional information not contained in the character code before their width can be resolved. It points to context such as a language tag, script identification, the associated font, the source of the data, or explicit markup, and recommends treating them as narrow by default when no context can be established. In other words this is the one class whose width is not decided by the character alone.

Which characters fall in it is the whole question. I measured 39 characters people use every day.

Ambiguous among the probe: 33 of 39

33 of 39 were ambiguous. Reading the list makes it obvious why this is the real problem.

  • All of Greek and all of Cyrillic are ambiguous. Reports with formulas, statistical output and Russian data all land here
  • Curly quotes and the ellipsis are ambiguous. U+201C, U+201D and U+2026 are inserted automatically by word processors, so they slip into user input unnoticed
  • Box drawing characters are ambiguous as a block. U+2500, U+2502, U+250C. Draw a bordered table and the border, not the content, is what varies by environment
  • Neighbouring characters can carry different values. U+2588 (full block) is A while U+2591 (light shade) is N. Draw a progress bar from both and the rule changes inside a single line
  • Currency symbols split as well. The euro U+20AC is A while the pound U+00A3 is Na. The guess that «all symbols are ambiguous» is wrong

  • 159 in the U+2400 block. The circled numbers of the U+2460 family, common in bullet lists
  • 160 in the U+0300 block. Greek mixed with combining marks. Combining marks get their own section below
  • 53 in the U+2100 block. Unit symbols such as degree Celsius U+2103 and numero U+2116
  • 1,271 in total does not mean «rare characters». These are the ones that fill office documents and reports every day

This gives the second thesis of the article. Width is not decided by the character alone. For those 1,271 characters Unicode declines to answer and delegates to the environment. Identical alignment across every terminal and every font is therefore impossible in principle.

4. Fullwidth and halfwidth - the same A as two codepoints

Now what F and H look like in practice. There are two characters in Unicode that look like the letter A.

--- 4-1. two codepoints that both look like the letter A ---
  U+0041  LATIN CAPITAL LETTER A             eaw=Na  utf8=1B  width=1  [A]
  U+FF21  FULLWIDTH LATIN CAPITAL LETTER A   eaw=F   utf8=3B  width=2  [Ａ]

  are they equal as strings? False
  NFKC of U+FF21 -> U+0041
  NFC  of U+FF21 -> U+FF21  (unchanged)

--- 4-2. a fullwidth-typed ID compared to an ascii one ---
  ascii     [INV-2026]  chars=8  utf8=8B  width=8
            codepoints: U+0049 U+004E U+0056 U+002D U+0032 U+0030 U+0032 U+0036
  fullwidth [ＩＮＶ－２０２６]  chars=8  utf8=24B  width=16
            codepoints: U+FF29 U+FF2E U+FF36 U+FF0D U+FF12 U+FF10 U+FF12 U+FF16
  s_ascii == s_full            : False
  NFKC(s_full) == s_ascii      : True
  width before NFKC: 16   after NFKC: 8

This result produces two distinct incidents in practice.

  • Same character count, double the width. An order number typed in fullwidth is still 8 characters but eats 16 columns. Every character-count validation passes and only the table drifts
  • String comparison fails. INV-2026 and the same value typed fullwidth are not equal. Values arriving from Japanese or Chinese input methods in fullwidth mode simply will not be found
  • NFC does not fix this. Folding fullwidth to ASCII is compatibility normalization (NFKC); the NFC people usually reach for leaves U+FF21 alone. The difference between the two lives in the NFC and NFD article
  • Applying NFKC halves the width from 16 to 8. So the same input has a different width depending on where the normalization boundary sits

Now the other direction: halfwidth katakana and the halfwidth won sign.

Block 4-5 proves the first claim from the introduction. Width cannot be derived from a byte count. Among three-byte UTF-8 characters, U+FF21 has width 2 while U+FF76 and U+20A9 have width 1. Same byte count, different answer.

  • Halfwidth katakana is 4 characters, 12 bytes, 4 columns. It is not ASCII yet its width is 1. The assumption that «non-ASCII means width 2» dies here
  • Applying NFKC doubles the width from 4 to 8. The opposite direction to 4-2. Normalization both shrinks and grows width
  • A voiced halfwidth kana is two codepoints. U+FF8A plus U+FF9E, which NFKC folds into the single U+30D0. Both the character count and the width change at once
  • The won sign U+20A9 having width 1 directly affects money columns. Reserving two columns for it because it is a currency symbol drifts by exactly that much

5. A function that counts by width

Time to fix it. What is needed is a function that computes padding from a width total rather than a character count. With no external package on this machine, it was built from the standard library alone.

# width_util.py   (Python 3.13.3, unicodedata 15.1.0)
import unicodedata

ZERO_CATS = ("Mn", "Me", "Cf")     # combining, enclosing, format

def char_width(ch, ambiguous=1):
    if unicodedata.category(ch) in ZERO_CATS:
        return 0                            # gate 1: advances nothing
    e = unicodedata.east_asian_width(ch)
    if e in ("W", "F"):
        return 2                            # gate 2: always two columns
    if e == "A":
        return ambiguous                    # gate 3: the environment decides
    return 1

def str_width(s, ambiguous=1):
    return sum(char_width(c, ambiguous) for c in s)

def pad(s, n, ambiguous=1, align="l", fill=" "):
    gap = n - str_width(s, ambiguous)
    if gap <= 0:
        return s
    if align == "l":
        return s + fill * gap
    if align == "r":
        return fill * gap + s
    left = gap // 2
    return fill * left + s + fill * (gap - left)

def trunc(s, n, ambiguous=1, ellipsis="..."):
    if str_width(s, ambiguous) <= n:
        return s
    room = n - str_width(ellipsis, ambiguous)
    out, acc = [], 0
    for ch in s:
        cw = char_width(ch, ambiguous)
        if acc + cw > room:
            break
        out.append(ch)
        acc += cw
    return "".join(out) + ellipsis

The point is that ambiguous is exposed as a parameter. The ambiguous convention is not baked into the function; the caller decides it. As section 3 showed, that value belongs to the environment and is not something the function can know. The table from section 1, redrawn with this function.

The last block is the verification. Across the six finished lines the character counts are 31, 31, 25, 22, 31, 25 - all over the place - while the widths are all 31. Uneven character counts are the correct outcome here.

  • Even the number of inserted spaces differs. In 5-2 the same 16-column field received 12, 5, 4 and 3 spaces depending on the cell
  • Truncation must go by width too. long[:10] keeps 10 characters, but their width is 17 columns and they burst the field
  • The width of the ellipsis itself has to be budgeted. The function above subtracts the width of ... first and fills the rest
  • Half a column can be left over at a wide-character boundary. If one column remains and the next character needs two, it cannot go in. This implementation leaves that column as a space
  • Verification is done by the function, not by eye. Feeding the finished lines back into str_width and checking they match is the only trustworthy check

6. Combining marks and zero width - where the simple sum fails again

The function in section 5 had three gates. This section explains why the first gate is necessary. Some characters have a width property that disagrees with the number of columns they actually take.

The last row is decisive. U+302A carries width property W. A function that only sums width properties assigns it 2. But it is a tone mark that stacks on the preceding character, so it occupies zero columns. UAX #11 itself states that for this class the property cannot be related to the advance width of the characters.

Normalization state produces this problem all by itself.

    codepoints: U+00C5 U+006E U+0067 U+0073 U+0074 U+0072 U+00F6 U+006D
  decomposed  : [Ångström]  chars=10 naive=10 zero-aware=8
    codepoints: U+0041 U+030A U+006E U+0067 U+0073 U+0074 U+0072 U+006F U+0308 U+006D
    same text? False   naive width gap: 2
  • The same word decomposed sums two columns wider. The two combining marks in Ångström were each counted as 1
  • A zero-aware function returns 8 and 8. It treated U+030A and U+0308, both category Mn, as zero
  • The difference is invisible. The screen shows the same word and only the table drifts
  • It shows up most often in databases with mixed normalization. If some rows arrive decomposed and others precomposed, width wobbles inside one column

An invisible character inside a CJK cell produces the same outcome.

--- 6-5. so the rule needs two gates, not one ---
  counter-example proving gate 1 must come FIRST:
    U+0301  cat=Mn  eaw=A  -> naive rule says 1, correct answer is 0
    U+302A  cat=Mn  eaw=W  -> naive rule says 2, correct answer is 0
    U+FE0F  cat=Mn  eaw=A  -> naive rule says 1, correct answer is 0

The three rows in 6-3 can only be told apart by their codepoint lists. All three read as the same four-letter word, yet one contains U+200B and another contains U+200D. The naive sum counts those two as 9 columns and therefore under-fills by one column each.

That fixes the order of the gates in the width function.

  • Gate 1: general category Mn, Me or Cf returns 0. Whatever the width property says is ignored
  • Gate 2: width property W or F returns 2. This much is settled
  • Gate 3: width property A returns whatever the caller passed. The function does not decide
  • Everything else returns 1. H, Na and N all land here
  • Gate 1 must come first. If U+302A hits gate 2 first it becomes 2 and overcounts by two columns

7. Where it actually breaks

That is the theory. Here are four places where the drift becomes visible, each one executed.

--- 7-1. fixed-width log lines (level + module + message) ---
  by ljust (character count):
    INFO  auth        login ok
    WARN  결제          카드 승인 지연
    ERROR batch       retry 3/3
    INFO  재고동기화       12건 반영
  by width:
    INFO  auth        login ok
    WARN  결제        카드 승인 지연
    ERROR batch       retry 3/3
    INFO  재고동기화  12건 반영

--- 7-2. a text receipt with a right-aligned amount ---
  by ljust:
    아메리카노 x2                   9,000
    Croissant x1               5,200
    치즈케이크 x1                   7,800
  by width:
    아메리카노 x2                9,000
    Croissant x1                 5,200
    치즈케이크 x1                7,800
    ----------------------------------

In a fixed-width log the message start position shifts only when the module name is CJK. Scanning logs by eye slows down noticeably once the columns stop meeting. A text receipt is worse. The amount is supposed to be flush right, but its starting point moves with the width of the item name, so the digits in the item rows do not line up with the total row.

--- 7-3. box-drawn table: the border characters are Ambiguous ---

  border chars and their EAW value:
    U+250C  [┌]  eaw=A
    U+252C  [┬]  eaw=A
    U+2510  [┐]  eaw=A
    U+2502  [│]  eaw=A
    U+2500  [─]  eaw=A
    U+2514  [└]  eaw=A
    U+2534  [┴]  eaw=A
    U+2518  [┘]  eaw=A
    U+251C  [├]  eaw=A
    U+253C  [┼]  eaw=A
    U+2524  [┤]  eaw=A
  every one of them is A. the frame itself is undecided, not the content.

This is the nastiest case. All eleven border characters are ambiguous. The table above was drawn assuming ambiguous is 1, so in an environment that treats ambiguous as 2 the frame, not the content, doubles and collapses. However precisely the content cells are computed, it is pointless if the frame moves.

  • A table drawn with box characters is not portable. The same output is correct in one environment and twice as wide in another
  • The alternative is an ASCII frame. -, | and + are all Na and never move. It looks cruder but the width is settled
  • Progress bars have the same problem. U+2588 is A and U+2591 is N, so the rule changes within one bar
  • Table libraries need the same check. Without knowing which convention the library uses, the result is unpredictable

Last comes trailing comment alignment in source code.

--- 7-4. aligned trailing comments in source code ---
  by ljust:
    MAX_RETRY = 3             # 재시도 상한
    TIMEOUT_SEC = 30          # connect timeout
    BATCH = 500               # 한 번에 처리할 건수
    DEBUG = False             # verbose logging
  (the CODE is ascii here, so both methods agree)

--- 7-5. now align something AFTER the comment ---
  by ljust:
    MAX_RETRY = 3             # 재시도 상한              |
    TIMEOUT_SEC = 30          # connect timeout     |
    BATCH = 500               # 한 번에 처리할 건수         |

    MAX_RETRY = 3             # 재시도 상한           |
    TIMEOUT_SEC = 30          # connect timeout       |
    BATCH = 500               # 한 번에 처리할 건수   |
    DEBUG = False             # verbose logging       |

In 7-4 both methods produce the same result, because all the code before the comment is ASCII. That is an important observation. Width problems only occur when wide characters sit before an alignment point. Behind it they have no effect at all. So the drift begins the moment you try to align something after the comment, as in 7-5.

    담당        kim
    상태        승인 대기
  delimiter-separated (cannot break):
    주문번호	A-20260731-0012
    담당	kim

  key=value (cannot break):

    담당=kim
    상태=승인 대기

The heart of this check is that in 8-4 the Korean-only cell comes out stable while café comes out unstable. Hangul syllables are all W, so their width is settled; é is A and belongs to the environment. The result is the opposite of the folk belief that CJK is the problem.

  • Only the cells containing ambiguous characters need flagging. This is not an exhaustive audit, just a search for width property A and categories Mn, Me, Cf
  • The corner brackets 「」 are stable. The U+300C family is settled as W, whereas the U+201C family is A
  • The cheapest fix is to abandon space alignment. Separate with a tab or an equals sign and no width computation is needed at all
  • Delimited output is better for machines too. A space-aligned table forces a parser to guess the column boundaries again
  • If you genuinely need a table, drive ambiguous characters out of it. Swap the border for ASCII and circled numbers for parenthesised digits, and the wobble disappears
  • Perfect alignment is not the goal. Readable-when-drifted is the goal. A table off by one column can still be read; a table with scrambled columns cannot

Python ships unicodedata.east_asian_width in the standard library, so the property value can be asked for directly. Node has no such API. Intl.Segmenter exists, but it splits grapheme boundaries and says nothing about width. So a range table has to be carried by hand, and hand-built tables tend to omit the ambiguous class entirely. The one above silently treats U+03B1 and U+2500 as one column.

  • A range table is bound to a Unicode version. The Python here carries Unicode data 15.1.0, while the latest published property file is 17.0.0. Every new character leaves a hand-built table further behind
  • The default for unassigned codepoints matters too. The property file defaults to N but gives W as the default for U+3400..U+4DBF, U+4E00..U+9FFF, U+F900..U+FAFF and the undesignated areas of planes 2 and 3. Skip that rule and future Han characters become one column
  • A pipeline mixing both runtimes is the most dangerous. If Python aligns by width and Node then slices by code units, the result follows neither convention
  • When choosing an implementation, check how it handles ambiguous first. An implementation with no option has already made the decision for you

Checklist. ① Do padding and truncation use a width total rather than a character count? ② Does the width function filter categories Mn, Me, Cf to zero first? ③ Is the ambiguous value exposed to the caller or baked into the function? ④ Is the table border using the U+2500 family? ⑤ Is fullwidth input (U+FF01 to U+FF60) folded with NFKC at the boundary? ⑥ Are finished lines fed back into the width function and checked for equality? ⑦ Is alignment genuinely required here, or could a delimiter do the job?

What was not confirmed by eye. Every judgement here was made from property values and codepoints. How many columns an ambiguous character is actually painted in on a given terminal, how halfwidth katakana looks in a given font, whether an emoji renders two columns wide - none of that was confirmed, and none of it can be, because it varies by environment. That is precisely the conclusion. Rendering is a separate problem, and the best code can do is produce a prediction grounded in property values.

# Display width alignment — copy-ready tables and padding function

> Source: braindetox.kr — One character is not one column wide
> Basis: executed on Windows 10 / Python 3.13.3 (unicodedata 15.1.0) / Node.js v22.16.0
> Computed with the standard library only; wcwidth and string-width were not installed

## 1. The five numbers attached to one string

| Number | What it counts | e.g. 김철수 | e.g. café (U+00E9) |
|---|---|---|---|
| UTF-8 bytes | transfer and storage size | 9 | 5 |
| UTF-16 code units | JS string length | 3 | 4 |
| Codepoints | Unicode character count | 3 | 4 |
| Graphemes | letters as humans count them | 3 | 4 |
| **Display width** | **terminal columns** | **6** | **1 or 2 (environment)** |

## 2. The six East Asian Width values

| Value | Name | Columns | Measured example |
|---|---|---|---|
| `W` | Wide | 2 | U+4E00, U+D55C, U+3042 |
| `F` | Fullwidth | 2 | U+FF21, U+FF10 |
| `H` | Halfwidth | 1 | U+FF76, U+20A9 |
| `Na` | Narrow | 1 | U+0041, U+0024 |
| `A` | Ambiguous | **environment decides** | U+03B1, U+00B1 |
| `N` | Neutral | 1 | U+0627, U+2603 |

- Only `W` and `F` mean two columns
- `A` is not a width but an **undecided state**. UAX #11 recommends narrow when no context exists
- Full codepoint scan: W 182,417 / F 104 / H 123 / Na 111 / A 138,739 / N 790,570
- Of the A values only **1,271** are assigned characters; the rest are private use

## 3. Width-based padding function (Python, no dependencies)

```python
import unicodedata

ZERO_CATS = ("Mn", "Me", "Cf")

def char_width(ch, ambiguous=1):
    if unicodedata.category(ch) in ZERO_CATS:
        return 0                          # gate 1: must come first
    e = unicodedata.east_asian_width(ch)
    if e in ("W", "F"):
        return 2                          # gate 2
    if e == "A":
        return ambiguous                  # gate 3: caller decides
    return 1

def str_width(s, ambiguous=1):
    return sum(char_width(c, ambiguous) for c in s)

def pad(s, n, ambiguous=1, align="l", fill=" "):
    gap = n - str_width(s, ambiguous)
    if gap <= 0:
        return s
    if align == "l":
        return s + fill * gap
    if align == "r":
        return fill * gap + s
    left = gap // 2
    return fill * left + s + fill * (gap - left)

def trunc(s, n, ambiguous=1, ellipsis="..."):
    if str_width(s, ambiguous) <= n:
        return s
    room = n - str_width(ellipsis, ambiguous)
    out, acc = [], 0
    for ch in s:
        cw = char_width(ch, ambiguous)
        if acc + cw > room:
            break
        out.append(ch)
        acc += cw
    return "".join(out) + ellipsis
```

## 5. Characters whose width property disagrees with reality

| Codepoint | Width property | Category | Real columns |
|---|---|---|---|
| U+0301 combining acute | A | Mn | **0** |
| U+302A tone mark | **W** | Mn | **0** |
| U+FE0F variation selector | A | Mn | **0** |
| U+200B zero width space | N | Cf | **0** |
| U+200D zero width joiner | N | Cf | **0** |

- Summing width properties alone gives U+302A a 2 and **overcounts by two columns**
- So the category check (gate 1) must come **before** the width property check
- UAX #11 also states the property cannot be related to the advance width of combining marks

## 6. Fullwidth and halfwidth summary

| Char | Codepoint | Width property | UTF-8 | Columns |
|---|---|---|---|---|
| A | U+0041 | Na | 1 B | 1 |
| Ａ | U+FF21 | F | 3 B | 2 |
| ｶ | U+FF76 | H | 3 B | 1 |
| ₩ | U+20A9 | H | 3 B | 1 |
| 一 | U+4E00 | W | 3 B | 2 |

- Same 3 bytes, widths of 1 and 2 → **width cannot be derived from bytes**
- NFKC folds fullwidth to ASCII and halves width (16→8); it expands halfwidth kana and doubles it (4→8)
- NFC leaves U+FF21 alone. The fullwidth problem is not solved by NFC

## 8. Checklist

- [ ] Padding and truncation use a **width total**, not a character count
- [ ] The width function filters categories `Mn`/`Me`/`Cf` to **zero first**
- [ ] The ambiguous value is **exposed to the caller**, not baked in
- [ ] Table borders use ASCII `-` `|` `+` instead of the U+2500 family
- [ ] Fullwidth input is folded with NFKC at the boundary
- [ ] Finished lines are **fed back into the width function** and checked for equality
- [ ] Alignment is genuinely required here, or a tab or equals delimiter would do
- [ ] A hand-built range table honours the unassigned default (N, except W in the CJK blocks)
- [ ] Python and Node halves of a pipeline agree on the same convention

## 9. Do not

- Derive display width **from a byte count** — three bytes can be width 1 or width 2
- Bake the ambiguous value in **as a constant** — it belongs to the environment
- Try to draw a **portable table with box characters** — all eleven border characters are A
- **Sum width properties without the category check** — U+302A counts as two columns
- Aim at «perfect alignment» — readable-when-drifted is the realistic target
- **Declare it correct because it looks right** — that is only your terminal's ambiguous convention
