並列コーディングエージェントはどこまで得か - Orca が開いた ADE と限界線

ワークツリー分離・衝突費用・レビューのボトルネックで分ける、エージェントを複数回してよい作業と回してはいけない作業

2026-08-09 IT・技術

序論: エージェントを5つ回すという言葉

Orca のリポジトリは自らをこう名乗る。「並列エージェントの群れと働くための ADE」。この一文に前提がすべて入っている。エージェントは一つではなく複数であり、個別ではなく群れとして扱うべきであり、そのためにはエディタとは別種の環境が要るということ。

README の言い方はもっと直接的だ。「一つのプロンプトを5つのエージェントに展開し、それぞれを自分専用の隔離された git ワークツリーに置き、結果を比較して勝者をマージする」。この道具が何をするかはこの一文で終わる。残る問いはその先にある。ではそれはいつ得なのか。

この問いが重要なのは、並列実行が直感を裏切る領域だからだ。ソフトウェアで作業を5つ同時に回すことは5倍速くなることを意味しない。作業同士が独立していなければならず、合わせる費用が分ける利得より小さくなければならず、結果を判定する人か機械がその速度についていけなければならない。この三条件のうち一つ崩れるだけで並列は損に反転する。コーディングエージェントだけが例外である理由はない。

だからこの記事は道具紹介で止まらない。Orca が実際にすることと、同時期に並んで語られた Paseo との違いを整理したうえで、並列化が効く作業と効かない作業を分ける基準、衝突と重複が実際に請求する費用、そしてレビュー負担がどこへ移るのかを詰める。結論を先に言えばこうだ。並列エージェントは倍速装置ではなく分業装置である。分業が成立しない仕事に分業の道具を当てれば、管理費用だけが残る。

1. ADE という言葉が実際に指すもの

1.1 用語の座標

ADE は Agentic Development Environment の略として使われる。InfoWorld はこの分類を「複数のコーディングエージェントが一つのリポジトリの複数ブランチで複数の課題に取り組むときに起きるべきことをすべて調整し管理する」道具と定義している。同じ記事に引かれた GitKraken CEO マット・ジョンストンの一文が対比を最短でまとめている。「IDE は一人がタイピングする時代のために作られた。ADE は人がエージェントの群れを指揮する時代のために作られた。」

1.2 IDE とずれる軸

名前が似ているので IDE の拡張版のように読めるが、設計の中心軸が違う。

  • 画面の主役: IDE はエディタバッファが中心、ADE は実行中のタスク一覧と各タスクの差分が中心
  • 同時性の単位: IDE はファイルとタブを、ADE はブランチと作業ディレクトリを同時に開く
  • 人の役割: IDE で人は作成者、ADE で人は配分者であり判定者
  • 完了の定義: IDE は保存が完了の単位、ADE はレビュー可能な変更の束が完了の単位

1.3 この呼び名を使う側が増えている

ADE が一社のマーケティング用語で終わらないという兆候はリポジトリのメタデータにも出ている。Orca と Paseo の両リポジトリが GitHub トピックに ade を付けており、Orca 側のトピックには parallel-agents・worktrees・agent-ide が並ぶ。分類名が定着しつつあるということだ。ただし分類が生まれたことと、その分類の道具がすべての作業に有益であることはまったく別の命題である。

2. Orca がすること - ワークツリー分離とプロンプトのファンアウト

2.1 分離の単位はコンテナではない

Orca が選んだ分離の単位は git ワークツリーだ。ワークツリーは同じリポジトリの複数ブランチを一つの git データベースから別々のディレクトリにチェックアウトする機能である。リポジトリを N 回複製せずに作業ディレクトリを複数作れるのが要点だ。エージェント5つがそれぞれのディレクトリでファイルを直せば、少なくともファイルツリーの次元では互いを踏まない。

この選択は軽くて速いが、境界がどこまでかは明確にしておく必要がある。ワークツリーはファイルツリーの分離であって、プロセスやシステム資源の分離ではない。コンテナや仮想マシンのようにネットワーク・ポート・プロセス空間を割ってはくれない。この差が実際どこで火を噴くかは後の表で整理する。

2.2 ファンアウトと「勝者のマージ」

Orca が前面に出す使い方は二通りに読める。一つは異なる作業 N 個を N 個のエージェントに分ける分業であり、もう一つは同じ作業一つを N 個のエージェントに同じように投げて結果を比較するファンアウトだ。README が挙げる「一つのプロンプトを5つのエージェントに展開し勝者をマージする」は後者である。

この二つは見た目は同じ並列だが経済学が正反対だ。分業は N 個の成果物をすべて使おうとするもので、ファンアウトはN 個のうち N-1 個を捨てるために回すものである。捨てる側が無駄という意味ではない。正解が一つに決まっておらず、どの手が当たるか事前に分かりにくい問題では、複数の試行を並列で取り出して比べるほうが一つを抱えて直すより良いことがある。ただし費用が N 倍で出ていき判定負担も N 倍になる事実は計算に入れなければならない。

2.3 ドキュメントが挙げる残りの機能

Orca が自ら説明する機能のうち、並列運用と直接絡むものは次のとおりだ。

  • ターミナルの多重分割と永続スクロールバック: 実行中のエージェント複数を一画面で見守らせる部分
  • モバイル同伴アプリ: 席を外した後も進捗を確認し介入する用途(iOS・Android)
  • SSH リモート実行: ワークツリーをローカルではなく遠隔機に置いて回す構成
  • GitHub・Linear 連携: 課題と差分を道具の中でつなぐ
  • 差分への注釈: コミット前に人が diff にコメントを残す検討段階
  • CLI スクリプティング: orca worktree create のようにワークツリー生成をコマンドで自動化

対応エージェントの範囲は広く取られている。タグラインが直接名を挙げるのは Codex・Claude Code・OpenCode・Pi で、リポジトリのトピックには cursor-agent も並ぶ。基準はモデルの種類ではなくターミナルで走る CLI エージェントかどうかだ。そしてサブスクリプションは利用者の持ち分である。Orca は実行環境を提供するだけで、モデルへのアクセスは提供しない。

3. Orca と Paseo - 同じ問題を違う重心で解く

3.1 二つを並べて置くと

同じ時期に並んで語られた Paseo は自らを「Claude Code・Codex・Copilot・OpenCode・Pi エージェントのための一つのインターフェース」と紹介する。狙う問題は Orca と同じだが強調点が違う。

3.2 ライセンスの違いが実際に意味すること

表のうち導入判断に最も大きく関わる欄はライセンスだ。Orca は MIT を明示する。Paseo は README に AGPL-3.0 と書かれているが、GitHub のライセンス自動判別フィールドはこれを特定のライセンスに分類していない。社内導入を検討するなら、この一欄はリポジトリのライセンスファイルを直接開いて確認すべき項目だ。AGPL 系はネットワーク越しにサービスを提供する形まで頒布とみなすため、社内で改造してチームにウェブで開放する使い方なら判断が変わりうる。

3.3 二つが共有する前提

違いより重要なのは、二つが同じ前提の上に立っている点だ。

  • モデルを売らない: どちらもエージェント CLI を代わりに提供しない。利用者が自分のサブスクリプションと資格情報で先に導入しておく必要がある
  • 実行は利用者の機械で: クラウドのサンドボックスではなく自分の開発環境がそのまま舞台になる。だからローカル環境の状態が結果にそのまま反映される
  • 分離は git に頼る: ブランチとワークツリーという既存の仕組みを再利用する。新しい分離技術を作ってはいない
  • 判定は人に残す: どちらも結果を自動採用しない。比較とマージの決定は利用者に戻る

つまりこれらの道具が売るのはモデル性能ではなく実行と調整の層だ。判断に使う物差しもその層に合わせるべきである。「どちらがコードをうまく書くか」は誤った問いだ。コードはどのみち接続したエージェントが書く。

4. git ワークツリーが分けるものと分けないもの

4.1 分けてくれるもの

ワークツリー分離が確実に解決する問題は三つだ。

  • 作業ディレクトリの衝突: エージェント A が編集中のファイルをエージェント B が同時に上書きする事故が消える
  • ブランチ切り替えの競合: 一つのディレクトリでブランチを行き来して起きる stash とチェックアウトの絡まりがなくなる
  • 複製の費用: リポジトリを N 回クローンしないのでディスクと時間が節約される

4.2 分けてくれないもの

問題は開発作業がファイルだけを触るわけではない点にある。エージェントはビルドを回し、テストを立ち上げ、サーバーを実行する。その瞬間ワークツリーの外の共有資源が登場する。

資源ワークツリーで分離されるかぶつかると起きること対処
ソースファイル・ブランチ分離される-既定の動作で十分
開発サーバーのポート分離されない二つ目のエージェントの起動失敗、テストが他人のサーバーを叩くワークツリー別のポートオフセットを環境変数で注入
ローカルデータベース分離されないマイグレーションが互いを上書き、フィクスチャの汚染スキーマや DB 名をブランチ別に分ける
依存ディレクトリ分離はされるが共有されないワークツリーごとに再インストールでディスクと時間の浪費パッケージマネージャの共通キャッシュやストアを活用
ビルドキャッシュツールによるキャッシュキーが重なると誤った成果物を再利用キャッシュディレクトリをワークツリー別に指定
非追跡の設定ファイル分離されるが複写されない新しいワークツリーで環境変数ファイルがなく即失敗生成時にブートストラップスクリプトで配置
外部 API の使用量・料金分離されない同時実行が上限に先に当たる同時実行数の上限を決めておく
人の注意力分離されない結果が積まれる速度が検収速度を追い越す進行中の作業数を制限する

表の下二行が核心だ。上の項目は設定で解けるが使用量の上限と人の注意力は設定では解けない。並列幅の実質的な上限はたいていこの二行で決まる。

5. 並列化が効く作業と効かない作業

5.1 分ける基準は三つ

作業一覧を並べる前に判別基準を立てるほうが再利用に向く。並列適合度は結局三つの問いで分かれる。

  • 境界: この作業が触るファイルとインターフェースを事前に引けるか。引けなければ他の作業と重なる
  • 検証: 結果が正しいか機械が判定してくれるか。人しか判定できないなら並列幅は人数に縛られる
  • 捨てやすさ: 誤った結果を捨てる費用が安いか。捨てにくい作業ほど試行を増やす戦略は損になる

三つとも「はい」なら並列が得で、三つとも「いいえ」なら並列は管理費用だけを残す。たいていの作業はその間のどこかにある。

5.2 作業類型ごとの判定

5.3 表を貫く規則が一つ

上の表をもう一度読むと規則が一つに整理される。並列がうまくいく作業とは「すでに決定が終わった作業」だ。何を作るかが確定していて残りが実行だけのとき、エージェントを増やせば実行が並列で処理される。逆に決定そのものが残っている作業にエージェントを増やせば、互いに違う前提の上に立つ成果物が増えるだけだ。並列化の先行条件は道具ではなく設計がどこまで確定しているかである。

6. 衝突と重複 - 並列が実際に払う費用

6.1 テキストの衝突はむしろ安いほうだ

同じファイルの同じ行を二つのエージェントが直せばマージ衝突が起きる。これは騒がしいが安い。道具が知らせてくれ、位置が特定され、解決すれば終わる。並列エージェントで人がまず心配するのがこの類型だが、実際には最も扱いやすい部類に入る。

6.2 本当の費用は静かな衝突だ

高くつくのはテキストでは衝突しないのに意味では衝突する場合だ。エージェント A がある関数の戻り値の規約を変え、エージェント B がその関数を旧規約どおりに呼ぶコードを新しく書く。二つの変更は別のファイルにあるのでマージは静かに成功する。壊れるのは実行時点である。

この類型が並列エージェントで特によく生じる理由がある。各エージェントは自分のワークツリーの中のコードしか見ない。他のワークツリーで今何が起きているかは互いに知らない。人のチームなら会話で埋まる部分がここでは埋まらない。Orca と Paseo が共通してワークツリー分離を選んだという事実は、裏返せばエージェント間の相互認知は設計上ないという意味でもある。分離は安全装置であると同時に情報の遮断壁だ。

6.3 重複作業が請求する費用

衝突の次に大きい損失は重複だ。同じ問題を二つのエージェントがそれぞれ発見しそれぞれ直す状況は並列実行でよく出る。

  • トークン費用の二重支出: 同じコードを二度読み二度直す分だけ料金が出ていく
  • レビュー費用の二重支出: 人は二つの差分をそれぞれ読んで初めて同じ仕事だと気づく
  • マージ順序への依存: 先に入ったほうを基準に後のものが無効化されるか衝突する
  • 判断の歪み: 二つの結果が微妙に違えば、どちらが正しいか判定する仕事が新たに生まれる

重複を減らす方法は道具ではなく作業分解にある。作業指示に「触ってよい範囲」と「触ってはいけないもの」を明記すると重複は目に見えて減る。並列エージェントでプロンプトの半分が境界の宣言に使われるのは浪費ではなく必須の支出だ。

7. レビュー負担は消えずに場所を移す

7.1 ボトルネックの移動

並列エージェントが確実にやり遂げることは差分を作る速度を上げることだ。ところがソフトウェアの受け渡し過程で作成は複数段階のうちの一つにすぎない。作成が速くなればその後の段階に待ち行列が積まれる。これは新しい現象ではなく、どんな工程でもボトルネックの手前を加速したときに現れる結果だ。変わったのはボトルネックの位置である。キーボードから人の判断へ移った。

7.2 レビューが崩れている兆候

  • 差分を開いて何を確認すべきか思い出すのに時間がかかる
  • テストが通ったという事実だけで承認する回数が増える
  • マージ後に初めて二つの変更が食い違っていたと気づくことが繰り返される
  • ある決定がなぜそうなったのか説明できる人がいなくなる

最後の項目が最も危うい。コードは残るのに決定の根拠が残らない状態は、時間が経ってから請求書が届く。

7.3 道具が狙う地点と残る持ち分

Orca がコミット前の差分注釈機能を入れたのは、この問題を認識しているという合図として読める。結果を自動採用せず人が diff にコメントを残す段階を挟んだという意味だからだ。ただしこの種の機能は検討を楽にするだけで検討量を減らしはしない。五つのワークツリーから出た五組の差分は依然として五組である。

7.4 並列幅を実際に広げるもの

人の判定に依存する分を機械に移さなければ並列幅は増えない。順に置くとこうなる。

  • テスト: エージェントが自ら失敗を見つけて直せるようにする第一防衛線。カバレッジの低いリポジトリで並列エージェントは危険だけを増やす
  • 型・静的解析: 静かな衝突の相当部分をマージ前に捕らえる低費用の装置
  • 契約検査: モジュール境界の規約をコードで固めておけば、エージェントが互いの前提を破ったかを機械が判定する
  • 変更サイズの制限: 一つの作業の差分が人が一度に読める大きさを超えないよう分解する

整理すると並列エージェント道具の導入準備度は検証自動化の水準で測られる。道具を先に入れてテストを後から付ける順序はおおむね逆効果になる。

8. 並列エージェントを回す前に揃えるもの

8.1 リポジトリ側の準備

  • 新しいワークツリーでインストールとビルドがコマンド一行で終わるか
  • 非追跡の設定ファイルが新しいワークツリーに自動で配置されるか
  • ポートやデータベース名が環境変数で外から注入されるか
  • テストがワークツリーに関係なく独立して回るか
  • ビルドキャッシュの経路がワークツリー別に分離されるか

8.2 作業分解側の準備

  • 作業ごとに触るファイル範囲を指示文に書けるか
  • 作業間に順序依存がないことを確認したか
  • 共有インターフェースの変更が要る作業をあらかじめ分離したか
  • 各作業の完了条件が機械で判定できる形か
  • 失敗したとき丸ごと捨ててよい大きさに切ったか

8.3 運用規則側の準備

  • 同時に回すエージェント数の上限を決めたか
  • マージ順序を誰がどの基準で決めるか合意したか
  • 捨てられたワークツリーを片づける手順があるか
  • 費用の上限と使用量の警告を設定したか
  • 一日に検収できる差分の総量を基準に作業数を決めているか

Paseo の CLI はこうした運用をコマンド一行で表す形を見せる。ワークツリー指定が実行オプションの位置に入っている点が、この種の道具の性格を表している。

paseo run --provider <エージェント/モデル> --worktree <作業名> "作業指示"

9. 5倍で回せば5倍払う

9.1 線形に増えるものと増えないもの

並列実行で確実に N 倍に増えるのは費用だ。エージェント5つがそれぞれリポジトリを読みそれぞれ直せば、トークン使用量も五人分になる。一方で確実に N 倍に減るものはない。実行時間は作業間の依存がないときだけ減り、それでもマージと検収の時間は減らない。

ここにもう一枚ある。サブスクリプション型のエージェントにはたいてい使用量の上限がかかっている。5つを同時に回すということは上限に5倍速く到達することを意味する。ファンアウト戦略が魅力的に見えるほど、この計算を先にしなければならない。五組を作って四つ捨てる方式は、正確に五人分の使用量を使う。

9.2 費用を下げる現実的な選択

  • ファンアウトは狭く: 手が分かれる余地の大きい問題にだけ使い、答えの決まった作業には使わない
  • 分業は広く: 異なる作業を分けるほうは成果物をすべて使うので無駄がない
  • 探索と実行を分ける: 何をするか決める段階は単一エージェントで、決まった後の実行だけ並列で回す
  • 同時実行数に上限: 検収できる量を基準に決める。機械の性能ではなく人の基準だ

10. この道具を今導入するか判断する基準

10.1 導入してよい兆候

  • テストカバレッジがすでに使える水準で、機械が一次判定をしてくれる
  • 作業待ち行列に互いに独立した項目が着実に積まれる
  • 新しいワークツリーのブートストラップがコマンド一行で終わる
  • ブランチを行き来して stash を繰り返すことが多い — ワークツリーだけでも得が出る状態だ
  • 差分を読んで判定する人が実際に確保されている

10.2 見送るほうがよい兆候

  • テストが足りず結果の判定を全面的に人がしている
  • いましている仕事の大半が設計判断と原因究明だ
  • ローカル環境の構築が複雑でワークツリーごとに手がかかる
  • エージェント一つを回すときも結果を読み切れていない
  • 使用量の上限にすでに頻繁にぶつかっている

二つの一覧を合わせると判断は単純になる。エージェント一つをまともに使えない状態で5つ回せば、うまくいっていなかったことが5倍うまくいかなくなる。並列はうまく回っている工程を広げる装置であって、回っていない工程を直す装置ではない。

11. 確認できなかったこと

根拠を確保できずこの記事で断定しなかった項目を一か所にまとめる。

  • Orca の衝突処理の挙動: リポジトリのドキュメントは結果を比較して勝者をマージすると説明するだけで、複数のエージェントが同じファイルを触ったとき道具が自動で何をしてくれるか(自動マージ・衝突表示・リベース戦略)は確認できなかった。この記事の衝突の議論は道具の挙動ではなく並列ブランチ運用一般の性質に基づく
  • コンテナ分離の選択肢の有無: ワークツリー以外にコンテナやサンドボックス水準の分離を選べるかは確認できなかった
  • 成熟度の表記: アルファ・ベータ・正式のような明示的な段階表記は見つからなかった。リポジトリ開設が2026年3月で、オープンな issue と PR が3千件台という事実だけを残す
  • Paseo のライセンスの最終確定: README は AGPL-3.0 と明かすが GitHub の自動判別は特定のライセンスに分類していない。どちらが最終かは確認できなかった
  • 並列エージェントの実測効果: エージェント数を増やしたとき完了時間や欠陥率がどう変わるかを示す公開ベンチマークは確認できなかった。この記事の適合・不適合の判定は測定結果ではなく作業の依存構造から引き出した推論である
  • モバイル・リモート実行のセキュリティモデル: モバイルアプリと SSH リモートワークツリーがどんな権限境界を持つかは確認できなかった。リモート実行を組み込むなら別途の検討が要る

よくある質問(FAQ)

Q1. ADE は IDE と何が違うのか

IDE は一人が一つのファイルを編集する状況を中心に設計されており、ADE は複数のエージェントが一つのリポジトリの複数ブランチで同時に作業する状況を調整する。画面の主役がエディタバッファからタスク一覧と差分へ移り、人の役割も作成者から配分者であり判定者へ変わる。

Q2. Orca はエージェントをどう分離しているのか

コンテナではなく git ワークツリーだ。各エージェントが自分のディレクトリで自分のブランチを扱うので、リポジトリを複製せずにファイル衝突を避けられる。ただしこれはファイルツリーの分離にすぎず、ポート・ローカルデータベース・外部 API の使用量といった共有資源は依然として共有される。

Q3. 並列エージェントが実際に得になる作業は

境界が明確で、検証が自動化されていて、失敗を安く捨てられる作業だ。独立モジュールへのテスト追加、重ならない依存関係の更新、多言語ドキュメントの更新などが当たる。逆に設計判断、共有インターフェースを動かすリファクタリング、原因不明のバグ追跡は並列が損になる。

Q4. エージェントを増やすとレビュー負担はどうなるのか

消えずに場所を移す。作成が速くなった分だけ検収の待ち行列が伸び、ボトルネックが人の判断へ移動する。だから並列幅の実質的な上限はモデル性能ではなく一日にきちんと読める差分の量であり、テストと静的解析で機械が先に濾す分を増やすことだけが幅を広げる方法になる。

Q5. Orca と Paseo のどちらを選ぶべきか

どちらもエージェント CLI を代わりに提供せず実行と調整だけを担うので、コード品質では分かれない。ワークツリー並列と結果比較が目的なら Orca が、デーモン中心の自己ホストと複数クライアントからの接続が目的なら Paseo が筋に合う。社内導入ならライセンスをリポジトリで直接確認するほうが安全だ。

結論 - 並列は倍速ではなく分業だ

Orca と Paseo が作ったのは新しいコーディング能力ではなく複数の実行を並べて置き管理する層だ。この層は実行がボトルネックのときだけ得を出す。そして実際の開発でボトルネックが実行である区間は思ったより狭い。決定が終わり残りがタイピングだけの区間、まさにそこである。

今日適用できる順に整理するとこうなる。

  • 第1段階 — 待ち行列を二つの山に分ける。決定が終わった作業と決定が残っている作業。並列は前者にだけ使う
  • 第2段階 — ワークツリーのブートストラップを先に直す。新しいディレクトリでインストール・ビルド・テストがコマンド一行で通らなければ、並列は開始段階で詰まる
  • 第3段階 — 共有資源から外へ出す。ポートとデータベース名を環境変数へ移す作業が道具の導入より先だ
  • 第4段階 — 同時実行数を人の基準で決める。機械が抱えられる数ではなく一日に検収できる差分の数が上限だ
  • 第5段階 — ファンアウトは最後に出す。手が分かれる余地の大きい問題にだけ使い、答えの決まった作業には使わない

最後にこの記事がしなかったことを明確にしておく。ここにはどの道具が優れているという判定はない。並列エージェントの成否は道具の選択よりリポジトリが並列を受け入れる準備ができているかにはるかに大きく左右されるからだ。テストが薄く環境構築が複雑なリポジトリでは、どの ADE を入れても結果は同じである。準備は道具の外にある。
