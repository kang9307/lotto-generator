Introduction - on some days a local time does not name a single instant

A local time is a value such as 2026-03-08 02:30 that carries only a date and a clock reading. To pin it to one instant, a time zone rule is needed, and in a region with daylight saving time that mapping breaks on the change days. On the day the clocks move forward there is an interval the clock skips, so a reading inside it corresponds to no instant. On the day the clocks move back, the same reading passes twice, so one reading corresponds to two instants.

The phenomenon has names. A local time that does not exist is called a gap, nonexistent or invalid time in English-language documentation, and a time that occurs twice is called an overlap, repeated or ambiguous time. Below, the former is called a hole and the latter a repeated time. The result of the execution is that each tool has a different default for these two cases, and the same string becomes a UTC value that differs by an hour depending on the tool.

That time zone rules are data, that an update changes how past times are read, and that 24 hours later differs from the same clock time tomorrow across a change were covered with Python output in Time zones are data, not code. This article goes beyond a single tool and compares how Node.js and PowerShell 5.1 interpret the same input, and which storage rules prevent the differences.

Python zoneinfo - what fold selects

The zoneinfo module of Python 3.9 and later builds a time zone from an IANA name, and the fold attribute of datetime distinguishes the two moments of a repeated interval. The official documentation (datetime module) describes fold as used to disambiguate wall times during a repeated interval, and says the values 0 and 1 represent, respectively, the earlier and later of the two moments with the same wall time representation. The code below feeds fold 0 and 1 to the hole (03-08 02:30) and the repeated time (11-01 01:30), and then classifies minute by minute into normal, hole and repeated. On Windows, zoneinfo needs the tzdata package, and this PC has tzdata 2025.3 installed.

import sys
                    from datetime import datetime, timezone
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    UTC = timezone.utc
                    print("python", sys.version.split()[0])
                    
                    
                    def show(naive, fold):
                        dt = naive.replace(tzinfo=ny, fold=fold)
                        u = dt.astimezone(UTC)
                        back = u.astimezone(ny)
                        print(naive.strftime("%Y-%m-%d %H:%M"), "fold=%d" % fold, "offset", dt.strftime("%z"),
                              "-> UTC", u.strftime("%H:%MZ"), "-> back", back.strftime("%H:%M"), back.tzname())
                    
                    
                    show(datetime(2026, 3, 8, 2, 30), 0)
                    show(datetime(2026, 3, 8, 2, 30), 1)
                    show(datetime(2026, 11, 1, 1, 30), 0)
                    show(datetime(2026, 11, 1, 1, 30), 1)
                    print("default fold:", datetime(2026, 11, 1, 1, 30, tzinfo=ny).fold)
                    
                    
                    def classify(naive, tz):
                        a = naive.replace(tzinfo=tz, fold=0)
                        b = naive.replace(tzinfo=tz, fold=1)
                        back = a.astimezone(UTC).astimezone(tz).replace(tzinfo=None)
                        if back != naive:
                            return "nonexistent"
                        return "ambiguous" if a.utcoffset() != b.utcoffset() else "normal"
                    
                    
                    print()
                    for s in ["2026-03-08 01:59", "2026-03-08 02:00", "2026-03-08 02:59", "2026-03-08 03:00",
                              "2026-11-01 00:59", "2026-11-01 01:00", "2026-11-01 01:59", "2026-11-01 02:00"]:
                        print(s, classify(datetime.strptime(s, "%Y-%m-%d %H:%M"), ny))

The repeated time (11-01 01:30) behaves just as the documentation says. fold=0 gives the earlier moment, EDT (-0400), which is 05:30Z, and fold=1 gives the later moment, EST (-0500), which is 06:30Z; converting either back to local time gives 01:30. For the hole (03-08 02:30) the output shows the following behavior. fold=0 applies the pre-change offset -0500 and gives 07:30Z, and converting that instant back to local time gives 03:30 EDT. fold=1 applies the post-change offset -0400 and gives 06:30Z, which reads back as 01:30 EST. A time inside the hole is converted without any exception, but the value read back differs from the input.

The principle of the classification code is a round trip. If a local time converted to UTC and back differs, it is a hole; if it is the same but the offsets of fold 0 and 1 differ, it is a repeated time. In the output every minute from 02:00 to 02:59 is a hole, every minute from 01:00 to 01:59 is a repeat, and 01:59 and 03:00 are normal. The default fold value is shown as 0 on the line just above the classification list. Code that does not specify fold quietly picks the earlier side for a repeat and the pre-change offset for a hole.

The official documentation has a sentence that when two aware datetimes share the same tzinfo, the tzinfo and fold attributes are ignored and the base datetimes are compared. That is why fold 0 and 1 of the same local time compare equal with ==, and such a comparison cannot reveal the one-hour difference. The earlier article showed this with numbers in its DST boundary section, so here only the approach of converting to UTC before comparing is taken. Comparing fold 0 and 1 of the same local time directly gives the following.

from datetime import datetime
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    a = datetime(2026, 11, 1, 1, 30, tzinfo=ny, fold=0)
                    b = datetime(2026, 11, 1, 1, 30, tzinfo=ny, fold=1)
                    print("a == b:", a == b, "| offsets:", a.strftime("%z"), b.strftime("%z"))
a == b: True | offsets: -0400 -0500

The comparison is True, yet the offsets of the two values are -0400 and -0500, one hour apart.

JavaScript Date - forward across the hole, earlier for the repeat

The Node.js Date interprets local-time fields (year, month, day, hour, minute) with the time zone rules of the current process. The MDN Date documentation says that setting a local time inside an offset transition uses the same behavior as the Temporal disambiguation option compatible: if the local time corresponds to two instants, the earlier one is chosen, and if it does not exist (a gap), the Date goes forward by the gap duration. The time zone was set to America/New_York inside the script through process.env.TZ. The code below prints the input fields together with the fields read back.

process.env.TZ = 'America/New_York';
                    const pad = n => String(n).padStart(2, '0');

                      const x = new Date(y, mo - 1, d, h, mi);
                      const asked = y + '-' + pad(mo) + '-' + pad(d) + ' ' + pad(h) + ':' + pad(mi);
                      const got = x.getFullYear() + '-' + pad(x.getMonth() + 1) + '-' + pad(x.getDate()) + ' ' + pad(x.getHours()) + ':' + pad(x.getMinutes());
                      console.log(asked, '->', x.toISOString(), 'reads back', got, asked === got ? '(same)' : '(CHANGED)');
                    }
                    probe(2026, 3, 8, 1, 59);
                    probe(2026, 3, 8, 2, 0);
                    probe(2026, 3, 8, 2, 30);
                    probe(2026, 3, 8, 3, 0);
                    probe(2026, 11, 1, 0, 59);
                    probe(2026, 11, 1, 1, 30);
                    probe(2026, 11, 1, 2, 0);

The hole inputs 02:00 and 02:30 come back as 03:00 and 03:30. As instants they are 07:00Z and 07:30Z, and 07:30Z is the same as Python with fold=0. An input inside the hole changes into a value one hour later without any exception. The repeated 01:30 is 05:30Z and reads back as 01:30, so nothing changes in the fields. That the earlier side (EDT) was chosen, however, cannot be seen from the fields alone and appears only when the UTC value is printed. As the last two lines show, an ISO string without an offset (for example 2026-03-08T02:30:00) goes through the same local-time interpretation and gives the same instant.

  • A hole can be detected by reading the fields back with the getXxx methods this code used and comparing them with the input. The lines marked CHANGED for 02:00 and 02:30 are that signal.
  • A repeated time reads back to the same value, so this method cannot detect it. The code has to know separately that two UTC values are possible.
  • The risk of the TZ environment variable approach, where the region differs by process, was shown with Node.js output in the environment-variable section of the earlier article.

PowerShell 5.1 - standard time for the repeat, an exception for the hole

PowerShell uses TimeZoneInfo from .NET. The time zone name is a Windows identifier (Eastern Standard Time), not an IANA name, and SupportsDaylightSavingTime reads True on this PC. The API has detection methods. The official documentation defines IsAmbiguousTime as determining whether a particular date and time can be mapped to two or more UTC times, and says of ConvertTimeToUtc that if the time is ambiguous it assumes standard time, and if it is invalid it throws an ArgumentException.

Even inside one class, a hole is accepted by one method and rejected by another.

How many times does the same time occur in a day - zero, one or two

The problem becomes sharp with a job that runs at 02:30 every day or a reminder set for 01:30. Counting how often one local time appears in a day shows that the value on a change day differs from usual. The following code scans the UTC axis in 15-minute steps and collects the instants whose local reading is exactly that value.

from datetime import datetime, timedelta, timezone
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    UTC = timezone.utc
                    
                    
                    def occurrences(y, m, d, hh, mm, tz):
                        # UTC instants whose wall clock in tz reads exactly y-m-d hh:mm (15-minute scan, +-14 h)
                        base = datetime(y, m, d, hh, mm, tzinfo=UTC)
                        hits = []
                        for k in range(-14 * 60, 14 * 60 + 1, 15):
                            u = base + timedelta(minutes=k)
                            w = u.astimezone(tz)
                            if (w.year, w.month, w.day, w.hour, w.minute) == (y, m, d, hh, mm):
                                hits.append(u.strftime("%H:%MZ"))
                        return hits
                    
                    
                    for y, m, d, hh, mm in [(2026, 3, 7, 2, 30), (2026, 3, 8, 2, 30), (2026, 3, 9, 2, 30),
                                            (2026, 10, 31, 1, 30), (2026, 11, 1, 1, 30), (2026, 11, 2, 1, 30)]:
                        h = occurrences(y, m, d, hh, mm, ny)
                        print("%d-%02d-%02d %02d:%02d" % (y, m, d, hh, mm), "->", len(h), "time(s)", h)
2026-03-07 02:30 -> 1 time(s) ['07:30Z']
                    2026-03-08 02:30 -> 0 time(s) []
                    2026-03-09 02:30 -> 1 time(s) ['06:30Z']
                    2026-10-31 01:30 -> 1 time(s) ['05:30Z']
                    2026-11-01 01:30 -> 2 time(s) ['05:30Z', '06:30Z']
                    2026-11-02 01:30 -> 1 time(s) ['06:30Z']

The 02:30 occurs once each on 03-07 and 03-09 but zero times on 03-08. The 01:30 occurs once each on 10-31 and 11-02 and twice on 11-01 (05:30Z and 06:30Z). A rule such as every day at 02:30 has no target instant on the spring change day, and a rule at 01:30 has two target instants on the autumn change day. Another trap in the schedule notation itself is covered in the cron step article. What the output shows is the fact that a local-time rule can match zero, one or two times in a day.

                    2026-03-08T02:30:00-04:00 -> 2026-03-08 06:30Z

The output of the three tools is identical on all four lines. The -04:00 of the repeat is 05:30Z and the -05:00 is 06:30Z, so the two instants are distinguished and the tool-dependent choice disappears. An offset attached to the hole is also interpreted, but its meaning is awkward. The 06:30Z obtained from 03-08 02:30 with -04:00 is, in the first output above, the instant whose local time is 01:30 EST. That string is a value whose local notation and offset do not agree, so whether an offset string received as input is an actually possible combination in the zone has to be checked separately.

Asia/Seoul - the point of comparison and the 1988 record

Korea has no daylight saving time now, so Asia/Seoul in 2026 has neither a hole nor a repeat. For comparison, feeding the same two dates (2026-03-08 02:30 and 2026-11-01 01:30) to Seoul gives normal results for both. The tz data used by Python and Node.js, however, contains the 1988 daylight saving records, so 02:30 in 1988 shows up in different shapes. Rules for safe handling - what to reject and what to choose

Two things came out of the earlier execution. A local time string has no value in a hole and two values in a repeat. And the default choices of the tools differ. So the rule is not to leave it to a default choice but to decide a policy at the input stage. The code below is a Python function that rejects a hole with an exception, rejects a repeat when fold is missing, and converts it when fold is given.

from datetime import datetime, timezone
                    from zoneinfo import ZoneInfo
                    
                    UTC = timezone.utc
                    
                    
                    def to_utc(naive, tz, fold=None):
                        a = naive.replace(tzinfo=tz, fold=0)
                        b = naive.replace(tzinfo=tz, fold=1)
                        if a.astimezone(UTC).astimezone(tz).replace(tzinfo=None) != naive:
                            raise ValueError("nonexistent local time: " + naive.isoformat(" "))
                        if a.utcoffset() != b.utcoffset():
                            if fold is None:
                                raise ValueError("ambiguous local time: " + naive.isoformat(" ") + " (fold=0 or fold=1 required)")
                            return (b if fold else a).astimezone(UTC)
                        return a.astimezone(UTC)
                    
                    
                    ny = ZoneInfo("America/New_York")
                    for n, f in [(datetime(2026, 3, 8, 2, 30), None), (datetime(2026, 3, 8, 3, 30), None),
                                 (datetime(2026, 11, 1, 1, 30), None), (datetime(2026, 11, 1, 1, 30), 0),
                                 (datetime(2026, 11, 1, 1, 30), 1)]:
                        try:
                            print(n.isoformat(" "), "fold=%s" % f, "->", to_utc(n, ny, f).isoformat())
                        except ValueError as e:
                            print(n.isoformat(" "), "fold=%s" % f, "-> ValueError:", e)

  • To store an instant, use a UTC time (or a time with an offset). In the output with an offset attached (the offset section above) the UTC values agreed across all tools, and in the output with only a local time and no offset (the comparison table above) the values diverged by tool.
  • Receive a local time typed by a person together with a time zone name. Without a zone name a hole and a repeat cannot be classified.
  • Return a hole to the user as an input error and have another time chosen. The silent one-hour correction (Node.js) changes the value the user entered.
  • For a repeat, show the two candidates (05:30Z and 06:30Z) and let the user choose, or state the policy (earlier or later side) explicitly in the code. Leaving it to tool defaults makes PowerShell and Python pick different sides.
  • In .NET, do not convert a DateTime that came from UTC to local time back to UTC. Carry the offset along in a DateTimeOffset.
  • An input with an offset is not automatically safe either. In the offset section above, the string with -04:00 attached to the hole (03-08 02:30) was read as 06:30Z, which is the instant 01:30 EST. Check separately whether the received offset is a possible combination for that zone.
  • Put a hole and a repeat such as 2026-03-08 02:30 and 2026-11-01 01:30 into the test data, and review code that uses a local time string as a key.

What Could Not Be Verified

  • The behavior of Node.js, Python and PowerShell on Linux and macOS. All output comes from this Windows PC.
  • How TimeZoneInfo in PowerShell 7 (.NET 8 and later) accepts IANA names and handles holes and repeats. pwsh is not installed on this PC.
  • The corresponding algorithm in the ECMAScript specification text. The section could not be opened on the specification page, so only the MDN explanation is quoted.
  • The documentary basis for fold 0 and 1 selecting the pre- and post-change offsets in a hole in Python. The datetime documentation that was read describes fold only for repeated intervals, and the behavior in a hole was confirmed from output only.
  • Why the Windows time zone data has no 1988 daylight saving time, and the result on other Windows builds. The adjustment rule count of 0 is a value read on this PC.
  • Behavior in zones with a 30-minute change or a change at midnight, and whether schedulers (cron, Task Scheduler) run a job zero or two times on a change day.
  • The disambiguation option of the Temporal API (not defined in this Node.js version) and other libraries such as pytz and dateutil for Python.
