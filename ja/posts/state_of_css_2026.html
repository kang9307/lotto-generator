CSSが消し去った回避策 - プリプロセッサとJSの仕事をブラウザが引き取るとき

機能ごとに何が消え、何がまだ残り、対応状況をどう読むのか

2026年8月16日 開発・インフラ

はじめに: スタイルシートから静かに消えた行

数年寝かせたプロジェクトを開くと、ほぼ必ず三つが一緒に出てくる。ビルドパイプラインに刺さったプリプロセッサ、親要素にクラスを付けたり外したりするJavaScriptの数行、そしてファイルのあちこちに散ったメディアクエリのブレークポイント。別々の道具に見えるが、由来は同じだ。いずれもCSSにできなかったことを埋めるために置かれていた。

その回避策のかなりの部分が、ここ数年でブラウザの中に入った。ネストはパーサが直接処理し、中身を条件にして親を選ぶセレクタができ、ビューポートではなくコンテナの幅を問えるようになり、優先順位の争いには名前の付いた規則が用意された。だから今の有用な問いは「CSSに何が増えたか」ではなく「それが正確に何を不要にしたか」だ。新しい構文は必要になったときに覚えればいいが、消してよいコードは消さない限り永遠に残る。

この記事では五つの機能がそれぞれ取り除いた回避策を確認し、まだ取り除けていない場所に印を付けたうえで、対応状況の読み方と採用判断の基準を整理する。ブラウザ対応に関する記述はすべて2026年8月16日に確認した内容だ。CSSの対応状況はこのブログが扱うどのテーマよりも速く変わるので、半年後に読むなら各機能のMDNページ上部のバッジをもう一度見てほしい。

フロントエンド20年の流れ自体はフロントエンドに何が起きたか - 2008年jQueryから2026年AIコーディングまでで扱い、ブラウザの基本機能を作り直さないという原則は「Don't Roll Your Own」原則 2026にある。ここではCSSの一層だけを見る。

1. プリプロセッサの仕事 - ネストと変数

プリプロセッサをプロジェクトに入れた理由を挙げてもらうと、たいてい三つ出てくる。ネスト、変数、ミックスインだ。このうち前の二つが標準に吸収された。

1.1 ネスト - パーサが直接読む

ネストはブラウザが自分で解析するので、事前のコンパイルが要らない。構文の中心は親を指す&の一文字だ。

/* 以前: プリプロセッサが変換して初めて意味を持った */
.card { .title { font-weight: 700; } }

/* 現在: ブラウザがそのまま読む */
.card {
  padding: 1rem;
  & .title { font-weight: 700; }
  &:hover { border-color: currentColor; }
}
  • 消えたもの - ビルド段階。宣言を一つ直すためにwatchプロセスを立ち上げ、コンパイル成果物をgitignoreに入れ、ソースマップがずれたら元の行番号を手で探す作業がなくなる。
  • 残る理由 - ミックスインとループ。色の段階や余白スケールを繰り返し処理で生成するコード、コンパイル時の色計算、複数ファイルをまとめるインポート整理は依然としてプリプロセッサの仕事だ。
  • 注意 - 詳細度は今も上がる。ネストはセレクタを見えないところで長くする。プリプロセッサ時代の落とし穴は、標準になったからといって消えるわけではない。深さは二〜三段までを上限にするのが安全だ。

1.2 カスタムプロパティ - プリプロセッサ変数とは別物

どちらも「変数」と呼ばれるので同じものとして扱われがちだが、性質が違う。$gapはコンパイルが終われば消え、成果物には計算された値しか残らない。--gapは実行時に生きている。この一点の違いから残りがすべて出てくる。

:root { --gap: 1rem; --brand: #2c6fdb; }
@media (min-width: 48rem) { :root { --gap: 2rem; } }
.grid { gap: var(--gap); }
.btn  { background: var(--brand); }
/* フォールバック値は第二引数に置く */
.card { border-radius: var(--radius, 6px); }
  • 継承され、条件の中で切り替わる。親で値を変えれば配下がすべて追従し、メディアクエリやコンテナクエリの中で値だけを差し替えられる。条件ごとに規則一式を複製する理由がなくなる。
  • 消えたもの - テーマ用ファイルの複製。ダークモード用のCSSをまるごともう一式作るか、.theme-dark配下に全規則を書き直していたやり方が、ルートでの変数再定義数行に縮む。
  • 消えたもの - インラインスタイルの注入。JavaScriptが要素ごとにstyle属性を埋め込む代わりに、element.style.setProperty('--x', v)で値を一つ渡すだけになる。規則はスタイルシートに残る。
  • 境界。値の型を宣言してアニメーション可能にするのは@propertyの領域だが、この記事ではその対応状況を確認していない。

2. :has() - 親を選ぶためにJSを呼んでいた場所

状況はいつも似ている。カードの中にサムネイルがあればレイアウトを二段にしたい。入力欄に値が入ればラベルを上に上げたい。リストが空なら空状態の案内を出したい。セレクタが下方向にしか流れなかった時代の答えは一つだった。レンダリング時に親へクラスを付ける。

そのクラス一つが連れてくるコストは見た目より大きい。内容が変わるたびにクラスを更新するコードが要り、サーバーレンダリングとクライアントレンダリングの両方に同じ判定ロジックを置く必要があり、そこにテストが付き、時間が経つと誰も消せないクラスになる。何がそれを付けたのか追えなくなるからだ。

/* 入力欄に値があればラベルを上げる - JSなしで */
.field:has(input:not(:placeholder-shown)) label {
  transform: translateY(-1.2em);
  font-size: 0.8rem;
}

/* サムネイルのあるカードだけ二段に */
.card:has(> img) { grid-template-columns: 8rem 1fr; }

確認できた対応状況は比較的はっきりしている。MDNは:has()をBaseline「広く利用可能」と表示し、2023年12月からブラウザ全般で使えると記している(2026年8月16日確認)。ただし文書が併記する制約がいくつかあり、そのうち一つは失敗の仕方が荒いので必ず知ったうえで使うべきだ。

  • :has()の中にさらに:has()を入れることはできない。
  • 疑似要素は:has()の引数にできず、:has()のアンカーにもなれない。
  • 非対応ブラウザでは、そのセレクタを含む規則ブロック全体が無効になる。隣に書いた他の宣言も一緒に死ぬということだ。:is()や:where()のような寛容なセレクタリストに入れれば、その部分だけが捨てられて残りは生き残る。
  • 詳細度は引数のうち最も高いものに従う。:is()・:not()と同じ規則だ。
  • 性能に関する指針も文書にある。body・:root・全称セレクタをアンカーにしないこと、子(>)と隣接兄弟(+)の結合子で走査範囲を狭めることだ。

3. コンテナクエリ - ビューポートではなく置かれた枠を問う

メディアクエリの限界は構文ではなく問いの対象にあった。メディアクエリは画面がどれだけ広いかしか知らない。本当に必要なのは「このカードが置かれた枠がどれだけ広いか」なのに、同じカードコンポーネントが狭いサイドバーにも本文の三段グリッドにも入るなら、画面幅は何も教えてくれない。

だからコンポーネントが自分の居場所を知る必要があった。その知識はたいていvariant="compact"のような属性で注入されるか、ResizeObserverが幅を測ってクラスを切り替える形で実装された。どちらもレイアウトの知識をコンポーネントの外に複製する作業だ。

.sidebar, .main-grid > * { container-type: inline-size; }

@container (width > 30rem) {
  .card { display: grid; grid-template-columns: 8rem 1fr; }
}

MDNは@containerをBaseline「広く利用可能」と表示し、2023年2月からと記す。ただし星印が付いている——一部の部分は対応水準が異なる場合があるという表示だ。同じ文書の下にサイズクエリのほかにスタイルクエリ、スクロール状態クエリ、アンカー関連のクエリが並んでいるからで、「コンテナクエリに対応している」の一文でこの四つをまとめてはいけない。

  • コンテナは明示的に宣言する必要がある。container-typeを指定していない要素は照会の対象にならない。値はinline-size(インライン軸のみ)、size(両軸)、normal(既定値、サイズクエリの対象外)だ。
  • 実務のほとんどはinline-sizeだ。sizeは両軸に抑制がかかって内容が高さを作れなくなるため、高さを別途与えないと要素が潰れる。
  • 自分自身を問うことはできない。クエリは祖先のコンテナに対してのみ成立する。だからカードの外にラッパーをもう一つ置く構造がよく出てくる。
  • 消えたもの。ResizeObserverとクラス切り替え、コンポーネントにレイアウト情報を渡すprops、そしてブレークポイント定数をCSSとJSの両方に複製してずれるのを待つ構造。

4. @layer - 優先順位の争いを規則に変える

デザインシステムのボタンを特定のページだけ少し変えたいのに効かない。セレクタを長くする。それでも効かない。!importantを付ける。半年後にそのページを直しに来た人が同じ順序を繰り返す。この階段は、詳細度という暗黙の競争から生まれる。

@layerはその競争を宣言順という明示的な規則に置き換える。MDNはBaseline「広く利用可能」、2022年3月からと表示している。

/* 順序を先頭で一度に宣言する */
@layer reset, vendor, base, components, utilities;

@layer vendor { /* サードパーティCSSはここへ */ }
@layer components { .btn { padding: .5rem 1rem; } }
@layer utilities { .mt-0 { margin-top: 0; } }

覚えるべき規則は三行で、二行目が設計を決める。

  • 先に宣言したレイヤーが弱く、後に宣言したレイヤーが強い。詳細度ではなく順序が勝つ。
  • レイヤーに入っていないスタイルは、どのレイヤーのスタイルよりも強い。サードパーティCSSを低いレイヤーに閉じ込めておけば、自分のスタイルはレイヤーの外に置くだけで勝つ。
  • !importantはこの順序を反転させる。重要宣言どうしでは先に宣言したレイヤーが最も強くなる。リセットのレイヤーで!importantを使うと上のレイヤーを全部押し潰すということだ。
  • 消えたもの。!importantの階段、.app .page .card .btn.btn-primaryのような詳細度インフレ、そして読み込み順を守るためにバンドラ設定をいじる作業。
  • 注意 - 失敗が静かだ。レイヤー宣言を落としたり名前を書き間違えたりすると、その規則は無名レイヤーかレイヤー外に落ち、エラーなしで優先順位だけがひっくり返る。導入直後は目で確認する画面の一覧を作っておくほうがよい。

5.1 まだJSが残る場所

境界線は一行で引ける。CSSはスタイルを適用するが、値を返さない。ある機能がJavaScriptを消せるかを判断するとき、この軸で分けるとだいたい当たる。

  • 計測値を読む仕事。要素が実際に何ピクセルか、テキストが何行に流れたかを数値として知る必要があるロジックはそのままJSだ。コンテナクエリはその幅に合わせてスタイルを変えてくれるが、幅がいくつかは教えてくれない。AとBの幅を比べてCを決める計算もここに属する。
  • DOMの外のデータが条件になる場合。在庫が3個以下なら赤く、のような規則で条件はサーバー応答の側にあり、CSSがそれを見る方法はない。ただしその値をdata-属性やカスタムプロパティで渡した瞬間からはCSSの担当になる。境界は「誰が値を計算するか」にあり、「誰がスタイルを適用するか」にはない。
  • アクセシビリティ状態の更新。aria-expandedのような属性を変えるのはJSだ。CSSはその属性を読んでスタイリングできるだけで、変えられない。フォーカストラップやキーボード移動順の管理も同じだ。
  • 時点に紐づくロジックとリスト操作。アニメーションが終わったあとに走るコード、要素が画面に入ったときの遅延読み込み、そして並べ替え・絞り込み・仮想スクロール。:has()で「子がなければ空状態を見せる」程度はできるが、項目の順序は変えられない。
  • フォーム検証の内容と時点。どのメッセージをいつ見せるかは制約検証APIの領域だ。CSSが引き取ったのは有効・無効状態の表示だけである。

まとめると、CSSが引き取った区間は「条件 → スタイル」だ。「データ → 条件」と「スタイル → 値」はそのまま残っている。フレームワーク側でこの境界をどう扱うかはFoldkit - 正確性を追求する新しいフロントエンドフレームワークで別に扱った。

6. 「対応済み」の層 - ブラウザ対応の読み方

「あの機能、対応してますか」は一つの問いに聞こえるが、少なくとも四つが混ざっている。層を分けないと、要らないところにフォールバックを敷いたり、逆に敷くべき場所で省いたまま延々と保守することになる。

層意味実務判断この記事で確認した例 (2026-08-16)
広く利用可能多くの端末・ブラウザバージョンで安定して定着。MDNがいつからかを併記するフォールバックなしで使ってよい層:has()は2023年12月から / @containerは2023年2月から(星印) / @layerは2022年3月から
最新ブラウザのみ主要エンジンの最新版にはあるが、古い版にはないプログレッシブエンハンスメントのみ。固定された企業ブラウザや旧型モバイルが対象ならフォールバック必須この記事で確認した例なし
一部エンジンのみエンジンによって分かれる中核のレイアウト経路には使わないことアンカーポジショニング - MDNの概要文書にBaselineバッジが表示されない
フラグ・実験段階利用者が設定を有効にしないと動かない本番禁止。デモと学習用この記事で確認した例なし
  • 「対応済み」ではなく「いつから」を見る。日付が古いほど、利用者の端末のブラウザがすでにそのバージョンを通り過ぎている確率が高い。情報の実体は日付の側にある。
  • 星印を見落とさない。@containerのように「一部の部分は対応水準が異なる場合がある」が付いていれば、その名前の下にまとめられた下位機能を一つずつ確認せよという合図だ。
  • モジュール名とプロパティ名を区別する。仕様モジュール一つに複数のプロパティが入っていて、到着時期はそれぞれ違う。確認の単位はモジュールではなく、実際に書くプロパティと値だ。
  • 自分の利用者のバージョン分布と突き合わせる。最新ブラウザにあるという事実と、自分の訪問者がそのバージョンを使っているという事実は別だ。社内ネットワークで旧版が固定されていたり、メッセンジャーのアプリ内ブラウザの比率が高いサービスなら世界平均の統計は根拠として弱く、解析ツールのブラウザバージョン報告が唯一の実測になる。
  • 確認日を文書に書く。チームのWikiに「2026-08-16確認」の一行を残さなければ、半年後に同じ機能群を最初から調べ直すことになる。

6.1 @supports - フォールバックの設計法

@supportsは、ブラウザが特定の宣言やセレクタを理解するかをCSSの中で問う。構文は三通りだ。

/* 基本は外に、拡張は中に */
.card { display: block; }

@supports (container-type: inline-size) {
  .card-wrap { container-type: inline-size; }
  @container (width > 30rem) { .card { display: grid; } }
}

@supports selector(:has(*)) { /* セレクタ対応の有無 */ }
@supports not (anchor-name: --a) { /* 否定条件 */ }
  • 解析を問うのであって、動作を問うのではない。@supportsはブラウザがその宣言を理解するかだけを確認する。理解はするが実装が部分的な場合をふるい落とせないので、通ったからといって画面確認を飛ばしてはいけない。
  • 向きを守る。@supports自体を知らない非常に古いブラウザは、そのブロックをまるごと無視する。だから基本スタイルはブロックの外、拡張はブロックの中だ。notでフォールバックを包むと、そのフォールバックがまるごと消えるブラウザが出てくる。
  • :has()は包む。非対応ブラウザが規則ブロック全体を捨てるので、:where(.card:has(img))のように寛容なリストに入れれば残りの宣言が生き残る。代わりに:where()は詳細度を0にしてしまうので、その分ほかの規則に負けやすくなる。
  • フォールバック戦略は三つのうち一つを選び、期限を併記する。①プログレッシブエンハンスメント——基本状態がすでに使えるなら拡張だけを重ねる。②同等の代替——メディアクエリで近似したうえでコンテナクエリで精密化する。③見送る——中核のレイアウトでフォールバックを二式維持する必要があるなら、その費用が機能の利得を上回ることが多い。どちらにせよフォールバックの横に「どの条件になったら消すか」をコメントで残さないと、そのコードは条件が満たされたあとも何年か生き続ける。

7. 調査数値の読み方 - 回答者は平均的な開発者ではない

毎年出るCSS調査は、何が議論されているかを見るには良い資料だ。ただし数値を書き写すときは標本の性格も一緒に写す必要がある。State of CSS 2026は2026年5月15日から6月29日まで、4,902人が回答した公開ウェブ調査だ。この一行を外すと、残るのは根拠ではなく印象になる。

  • 自発的回答である。無作為抽出の標本ではなく、調査の存在を知り、答える気のある人が集まる。CSS調査に時間を使う人は定義上CSSへの関心が高い側だ。
  • 募集経路が結果を作る。どのチャネルで広まったかによって回答者の構成はまるごと変わる。この記事は公開ページから募集チャネルを確認できなかったので、その場合はその項目が空いているという事実自体を引用に添える必要がある。
  • 全体Nと設問別Nは違う。4,902は全体の回答者数であり、すべての設問がその母数を持つわけではない。自由回答の設問は特に少ない——「好きな新機能」設問の上位項目はアンカーポジショニング168、:has()158、サイズコンテナクエリ126、CSSネスト116で、これは百分率ではなく言及回数であり、母数も4,902ではない。
  • 「利用率」が何を数えたかを確認し、増減に混ざる標本の変化を差し引く。「試した」と「本番で使っている」と「名前は知っている」は別の設問なのに、要約だけを見て写すとこの区別が消える。前年比で上がったという記述にも、機能が実際に広まった分と回答者構成が変わった分が一緒に入っている。

この前提を付けて読むと、2026年版から読み取れる傾向はこうなる。ブラウザ互換性が採用の最大の障壁として挙げられ、アンカーポジショニングが「使いたいが対応のせいで使えない」の代表例として言及された。フレームワークの設問ではTailwindが1位を維持し、「フレームワークを使わない」がBootstrapを抜いて2位になった。CSSコードのAI生成比率は平均28%程度で他の開発領域より低く出ており、最も多く挙がった懸念は認知的過負荷だった。

そして、この数値が支持しない文がある。「もう誰もが:has()を使っている」はこのデータからは成立しない。成立するのはここまでだ——この標本では:has()が最も広く使われていると回答された新機能の一つだった。二つの文の差が些細に見えるなら、前の文を根拠にフォールバックを外したとき何が壊れるかを考えてみればいい。

8. 今採用するものと見送るもの

判断の軸は四つで足りる。非対応のとき何がどう壊れるか、フォールバックを二式維持する費用、確認できた対応日と自分の利用者分布の距離、そして後から戻す費用だ。このうち最初が最も重い。少し見栄えが悪くなる失敗と、レイアウトが崩れる失敗を同じ天秤に載せてはいけない。

機能非対応時の症状フォールバックの難度判断

見送る側にも費用があることは指摘しておく価値がある。フォールバックを二式維持するチームは、時間が経つとフォールバック経路しか見なくなる。拡張経路が実際にレンダリングされているかを確認する手順がなければ、そのコードは死にコードであり、死んだことも知られないまま保守対象の一覧に残る。新しい機能を入れるときは「どのブラウザで拡張経路を確認するか」も一緒に決めておくほうがよい。

9. 確認できなかったこと

この記事の対応状況に関する記述は各機能のMDN文書から出ており、以下はその範囲外なので断定しない。

  • CSSネストのBaseline等級と導入時期 - 概要文書でバッジを確認できなかった。ネスト文書下部のブラウザ互換性表を直接見ること。
  • アンカーポジショニングのエンジン別対応バージョン - 概要文書に互換性表が現れなかった。バッジが表示されないという事実だけを確認した。
  • @property・aspect-ratio・動的ビューポート単位・スクロール連動アニメーション - 本文では概念のみに触れ、対応状況は確認していない。
  • @containerの星印が指す正確な範囲と、Baseline等級の昇格基準 - 前者は文書が「一部の部分は対応水準が異なる場合がある」としか表示しないので、スタイルクエリとスクロール状態クエリはそれぞれの文書で別に見る必要があり、後者は定義文書を確認していない。
  • 調査の募集経路と設問別の回答数 - 公開の要約ページからは確認できなかった。百分率の数値は集計要約を経て得たものなので、元の設問の表現は確認していない。

よくある質問(FAQ)

プリプロセッサはもう外してよいのか?

ネストと変数しか使っていなかったのなら、外す根拠はできている。ミックスイン、繰り返し処理でユーティリティを生成するコード、コンパイル時の色計算、ファイル分割とインポート順の整理は依然としてプリプロセッサの仕事だ。判断は好みではなく一覧で行う——プリプロセッサのファイルから実際に使っている構文を抜き出し、標準で置き換えられるものとそうでないものに分ければ答えはすぐ出る。

:has()を使うと性能は落ちるのか?

セレクタが遅いのではなく、走査させる範囲がコストを生む。MDNの指針は明確だ——body・:root・全称セレクタをアンカーにせず、子と隣接兄弟の結合子で範囲を狭めること。カード一枚の中で子の有無を問う程度なら問題にならない。気になるなら実際のページでスタイル再計算時間を測るほうが推測より早い。

コンテナクエリはメディアクエリを置き換えるのか?

置き換えではなく分業だ。ページ全体の骨格——何カラムに分けるか、サイドバーを畳むか——は今もメディアクエリの側にある。コンテナクエリはその骨格の中に置かれた部品が、自分の枠の幅に合わせるために使う。両方を重ねて使うことになるので、ブレークポイントの値を一か所にまとめる習慣がむしろ重要になる。

@layerを導入すると既存のCSSが壊れないか?

壊れうるし、静かに壊れる。規則を一つ覚えれば大半は予測できる——レイヤーに入っていないスタイルが、どのレイヤーのスタイルよりも強い。だから既存のCSSをまるごとレイヤーに押し込むと、勝っていた規則が急に負け始める。安全な順序は逆だ。リセットやサードパーティのように常に負けてほしいものから低いレイヤーに入れ、自分のスタイルはレイヤーの外に置いたまま観察する。

調査の数値を根拠に技術選定をしてよいのか?

調査が教えるのは採用率ではなく関心の方向だ。公開ウェブ調査は自発的回答なので、回答者はその話題に関心のある側に寄る。だから利用率が高く出たという事実は自分の利用者のブラウザがその機能に対応している根拠にはならない。役に立つのは検討リストを選ぶところまでで、そこから先の判断はブラウザ互換性の文書と自分のサービスのバージョン分布で行う。

結論: 今日判断する三つ

ここ数年のCSSの変化を一文に縮めると「条件を判断する仕事がスクリプトからスタイルシートに降りてきた」になる。親の状態、置かれた枠の幅、規則どうしの序列——この三つは以前すべてCSSの外で計算され、クラスという形で注入されていた。今はその計算がセレクタの中に入る。だから利得は新しい構文にあるのではなく、消してよいコードにある。

  • まず今あるクラス切り替えを数える。親にクラスを付け外しするコード、ResizeObserverで幅を測るコード、テーマ用のクラス一式。この一覧がそのまま回収可能なコードの一覧だ。
  • 機能ではなく失敗の仕方で判断する。非対応のとき少し見栄えが落ちる機能と、規則ブロック全体が死ぬ機能では採用基準が違うべきだ。:has()を寛容なリストで包む習慣はこの判断から出てくる。
  • 確認日を残す。対応状況は半年で変わる。チームの文書に機能別の確認時点を書いておかないと、同じ調査を繰り返すか、古い判断を使い続けることになる。

最後に調査の話を一行。この種の資料は何を検討リストに載せるかを選ぶときに有用で、そこまでだ。採用の可否はブラウザ互換性の文書と自分のサービスのバージョン分布が決める。回答者数と調査時期を外して引用された数値は、その数値が何であれ根拠ではなく雰囲気である。
