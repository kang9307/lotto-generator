오류 코드 체계를 만든다는 것 - 번호냐 문자열이냐, 그리고 누가 늘리나

코드의 값어치는 클라이언트가 그것을 보고 다른 행동을 할 수 있을 때만 생긴다

2026-08-01 개발/인프라

서론: 클라이언트가 오류 메시지 문자열을 비교하고 있었다

결제 화면의 버그 리포트를 따라가다 이런 코드를 만났다.

if (res.body.message.includes('already paid')) {
  goToReceipt();
}

처음 본 반응은 「누가 이걸 짰나」였다. 그런데 서버 응답을 열어 보니 그 개발자를 탓할 수가 없었다. 서버가 내려보내는 것은 상태 코드 400과 사람이 읽는 문장 하나가 전부였다. 그 상태로 「이미 결제된 주문」과 「잔액 부족」을 구별하려면 문장을 비교하는 것 말고 방법이 없다.

즉 이것은 클라이언트의 잘못이 아니라 서버가 계약을 주지 않은 것이다. 그리고 이 계약의 이름이 오류 코드다.

여기서부터 흔한 반응이 두 갈래로 갈린다. 한쪽은 「그럼 오류 코드를 만들자」며 목록을 만들기 시작한다. 다른 쪽은 「코드가 늘어나면 관리가 안 된다」며 미룬다. 둘 다 같은 것을 놓치고 있다. 오류 코드는 문서가 아니라 계약이다. 문서는 틀리면 고치면 되지만, 계약은 한 번 상대에게 건네고 나면 내 마음대로 못 바꾼다.

이 글은 그 계약을 설계하는 이야기다. 코드를 몇 개 만들지가 아니라 무엇을 기준으로 갈라야 하는지, 왜 코드는 못 바꾸는데 메시지는 바꿔도 되는지, 그리고 목록이 방치되지 않게 하려면 무엇을 자동화해야 하는지를 다룬다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 Node.js v22.16.0 (win32)으로 실제 실행한 결과다. 등장하는 API·오류 코드·팀 이름은 전부 가상이며, 주문과 결제라는 흔한 도메인을 빌려 재현한 것이다. 스크립트는 파일로 저장해 실행했다.

이 글이 다루지 않는 것. 입력 검증 오류에서 어느 필드가 잘못됐는지 가리키는 방법은 응답 스키마의 details 안쪽 문제라 따로 다룬다. 목록이 방치됐을 때 누가 아직 그 코드를 받고 있는지 찾는 법도 별도 주제다. 여기서는 코드 자체의 설계와 수명만 본다. 응답의 다른 계약면은 API 문서를 기계가 읽는 계약으로와 오프셋 페이징이 못 하는 것에 있다.

먼저 문제를 정확히 재현했다. 가상의 결제 API를 만들고, 여섯 가지 서로 다른 실패를 일으켰다.

여섯 가지 실패가 상태 코드 하나로 뭉쳤다. 관측된 서로 다른 상태 값은 400 하나뿐이다. 그런데 오른쪽 열을 보면 클라이언트가 해야 할 일은 여섯 가지가 전부 다르다. 상태만 보고 분기하는 함수를 실제로 짜서 돌리니 여섯 건 모두 결정 불가로 떨어졌다.

여기서 오해하기 쉬운 것이 있다. 이것은 상태 코드가 나쁘다는 뜻이 아니다. 상태 코드는 프록시와 캐시와 재시도 계층이 읽는 축이고, 그 목적에는 충분히 잘 맞는다. 문제는 그 축의 해상도로 사용자에게 무엇을 보여줄지를 정하려 한 것이다. 축이 다르다.

문장을 비교하니 세 건은 정확히 갈렸다. 그래서 이 방법이 살아남는다. 처음에는 잘 동작하고, 아무도 문제를 못 느낀다.

그러다 누군가 문구를 다듬는다. 마지막 블록이 그 순간이다. 앞 글자를 대문자로 바꾸고 마침표를 찍고 어순을 손봤을 뿐인데, 같은 실패에 대해 클라이언트의 행동이 달라졌다. 클라이언트를 배포한 사람도 없고 상태 코드를 바꾼 사람도 없다. 문안 수정 하나가 한 것이다.

  • 이 사고는 배포 이력에 남지 않는다. 서버 코드 한 줄, 그것도 문자열 리터럴만 바뀌었기 때문이다
  • 테스트에도 잘 안 걸린다. 서버 테스트는 상태 코드를 보고, 클라이언트 테스트는 자기가 준비한 가짜 응답을 쓴다
  • 번역을 붙이는 순간 한 언어에서만 동작하는 분기가 된다. 영어 문장에 맞춘 비교는 다른 언어에서 전부 실패한다
  • 근본 원인은 서버가 사람용 필드밖에 안 줬다는 것이다. 클라이언트는 있는 것으로 분기할 수밖에 없다

표준도 이 지점을 명시한다. HTTP API의 오류 본문 형식을 규정한 RFC 9457은 소비자가 사람이 읽는 상세 문구를 파싱해서는 안 되며, 그런 용도로는 확장 필드가 적합하다고 적어 두었다. 기계가 읽을 축을 따로 주라는 뜻이다.

검색도 마찬가지다. 로그에서 숫자만 찾으면 지연 시간과 바이트 수에 우연히 같은 숫자가 있어 실제 두 건을 찾는 데 다섯 줄이 걸렸다. 정확히 찾으려면 필드명까지 붙여야 한다. 문자열은 오탐이 0이었다.

3. 도메인이 늘면 이름이 겹친다

문자열로 정했다고 끝이 아니다. 팀이 하나일 때 지은 이름은 팀이 셋이 되는 순간 부딪힌다. 세 팀이 각자 평평한 목록을 만든 상황을 재현했다.

11개 코드가 게이트웨이를 지나며 6개로 줄었다. 다섯 건이 겹쳤고, 겹친 자리에서는 먼저 등록한 쪽이 이기고 나머지는 사라졌다. 사라진 쪽 팀은 이 사실을 모른다. 자기 서비스를 단독으로 테스트하면 잘 동작하기 때문이다.

3-2가 그 결과다. 배송 조회 실패로 NOT_FOUND가 왔는데, 클라이언트의 분기는 주문 팀이 먼저 써 둔 것이다. 분기가 틀린 게 아니라 코드가 애매한 것이다. 「없다」는 말만 있고 「무엇이」가 없다.

접두사를 붙이자 11개가 11개로 살아남았다. 충돌 0. 대가는 코드당 평균 7.4자다.

여기서 자주 나오는 반문이 「어차피 서비스 이름이 URL에 있는데 왜 또 넣나」다. 이유는 코드가 응답 밖에서도 살아간다는 데 있다. 로그 집계, 지표 라벨, 지원팀 티켓, 클라이언트의 열거형 안에서 코드는 URL 없이 홀로 등장한다. 그 자리에서 NOT_FOUND는 아무것도 말해 주지 않는다.

  • 접두사는 한 겹이면 충분하다. 회사·제품·도메인을 다 붙인 42자짜리는 로그 열을 무너뜨리고, 붙인 정보 중 실제로 쓰이는 것은 하나뿐이다
  • ORDER_ORDER_NOT_FOUND 같은 단어 중복은 도메인 이름과 대상 이름이 같을 때 자동으로 생긴다. 검사기로 잡을 수 있다
  • _ERROR, _EXCEPTION, _FAILURE 접미사는 정보량이 0이다. 오류 코드 목록에 있는 모든 것이 오류다
  • 구분자는 로그 파싱만 보면 무엇이든 통과하지만, 코드가 열거형 멤버명이나 지표 라벨이 되는 순간 밑줄만 살아남는다. 점과 하이픈은 생성된 상수 이름으로 쓸 수 없다
  • 길이 상한을 정해 두는 편이 낫다. 32자면 로그 열 정렬과 가독성이 함께 유지된다

the user now lands on a generic error screen instead of the receipt.

대비가 선명하다. 메시지를 세 개 전부 다시 써도 깨진 분기는 0이었다. 문구를 아무리 바꿔도 클라이언트는 코드를 보기 때문이다. 반면 읽기 좋다는 이유로 코드 이름 하나를 바꾸자 그 분기가 즉시 죽었다. 사용자는 영수증 대신 일반 오류 화면을 본다.

이것이 「메시지는 바꿔도 되지만 코드는 못 바꾼다」는 규칙의 근거다. 그리고 이 규칙은 기계가 읽을 식별자를 주었을 때만 성립한다. 코드가 없으면 반대가 된다. 클라이언트가 문장에 의존하게 되므로 메시지 쪽이 얼어붙는다. 대형 API 설계 지침도 같은 순서로 적어 두었다. 기계용 식별자를 함께 준 API는 문구를 바꿀 수 있고, 식별자 없이 시작한 API는 문구를 고정해야 한다는 것이다.

게이트는 단순하다. 이전 버전의 코드 집합과 비교해 사라진 코드가 있으면 빌드를 세운다. 코드 추가는 통과시킨다. 모르는 코드는 클라이언트에서 기본 분기로 떨어질 뿐이라 깨지지 않기 때문이다.

이름을 정말 바꾸고 싶다면 v4처럼 한다. 새 이름을 대체 코드 필드로 알리기만 하고, 전선에 나가는 값은 그대로 둔다. 실제 교체는 옛 코드의 방출 건수가 0이 된 것을 확인한 뒤에만 한다. 그리고 그것은 문서가 아니라 트래픽만이 알려준다.

  • 코드 이름은 값이지 라벨이 아니다. 좋은 이름을 나중에 붙이려는 유혹이 가장 위험하다
  • 같은 이유로 코드의 HTTP 상태도 못 바꾼다. 프록시와 재시도 계층이 그것으로 판단하고 있다
  • 재시도 가능 여부도 코드 단위로 고정이다. 이것이 바뀌면 클라이언트의 자동 재시도 동작이 소리 없이 달라진다
  • 반대로 details에 필드를 추가하는 것은 언제든 가능하다. 가산적 변경이라 옛 클라이언트가 무시하면 그만이다
  • 코드를 지우는 것은 이름을 바꾸는 것과 똑같이 위험하다. 폐기 절차를 따로 둬야 하는 이유다

그래서 답은 둘 중 하나가 아니라 둘 다다. 5-4처럼 클라이언트는 자기 번역이 있으면 그걸 쓰고, 없으면 서버 문장을 그대로 출력한다. 새 코드가 나가도 화면이 비지 않고, 기존 코드는 로케일 서식을 지킨다.

  • 5-5가 하지 말아야 할 것을 보여준다. 코드를 언어별로 만들면 분기가 한 언어에서만 산다. 세 언어 중 한 곳에서만 발화했다
  • 코드는 식별자이지 문장이 아니다. 언어가 없다는 것이 코드의 성질이다
  • 번역 커버리지는 CI에서 표로 뽑을 수 있다. 5-6에서 여섯 칸이 비어 있었다
  • 중요한 것은 번역 구멍과 코드 누락의 무게가 다르다는 점이다. 번역이 없으면 기본 언어로 버티지만, 코드가 없으면 클라이언트가 아무 결정도 못 한다
  • 지원팀 관점도 있다. 사용자가 캡처해 보내는 것은 문장이다. 문장 안에 코드를 함께 노출해 두면 문의 처리 시간이 크게 줄어든다

  • traceId는 코드와 역할이 다르다. 코드는 실패의 종류를, 추적 id는 그 한 건을 가리킨다. 지원팀이 실제로 쓰는 것은 후자다
  • 추적 id가 없으면 코드와 시간대로 훑어야 하고, 그 범위는 수천 건이 된다. 모든 오류 응답에 반드시 넣는다는 규칙이 값싸고 효과가 크다
  • details는 코드로 갈리지 않는 세부를 담는 자리다. 여기에 담을 수 있는 것을 새 코드로 만들지 않는 것이 목록을 작게 유지하는 요령이다

7-5의 첫 줄은 오탐이다. 접두사를 뺀 토큰이 완전히 같지만 두 코드는 다른 도메인의 다른 실패다. 이런 검사기는 후보를 던져 주는 도구이지 판정 도구가 아니다. 반면 ORDER_ALREADY_PAID와 ORDER_ALREADY_SETTLED처럼 7-4에서도 같이 걸린 쌍은 실제로 볼 필요가 있다.

7-6이 폐기의 현실이다. 폐기 표시를 단 코드는 있는데, 그것이 코드를 없애지는 않는다. 30일간 방출 건수가 0이어야 지울 수 있고, 3건이라도 나오면 그 호출자를 먼저 찾아야 한다.

  • 코드 추가 절차의 첫 단계는 「클라이언트가 무엇을 다르게 하는가」를 한 문장으로 쓰는 것이다. 못 쓰면 코드가 필요 없는 것이다
  • 두 번째 단계는 기존 목록에서 같은 행동을 찾는 것이다. 같은 행동 + 같은 상태 + 같은 재시도 여부면 새 코드가 아니라 details다
  • 모든 코드에 소유자를 적어 둔다. 소유자가 없는 코드는 6개월 뒤 아무도 지우지 못한다
  • 마지막 줄이 가장 중요하다. UNKNOWN_ERROR가 30일에 918건이면 그것은 코드가 아니라 분류되지 않은 실패 918건이다. 쪼갤 후보 1순위다
  • 목록이 방치됐다는 신호는 개수가 아니라 포괄 코드의 비중으로 읽는 것이 정확하다

10. 체크리스트와 하지 말 것

마지막으로 지금 있는 API에 바로 대 볼 목록이다.

  • 클라이언트 코드에 메시지 문자열을 비교하는 분기가 0개다
  • 같은 HTTP 상태로 나가는 실패들이 코드로 구분된다
  • 모든 오류 응답에 code와 추적 id가 반드시 들어간다
  • 재시도 필드가 없을 때 재시도 계층이 불가로 읽는다
  • 코드에 재시도 여부가 문자열로 박혀 있지 않다
  • 도메인 접두사가 있고, 접두사 없는 NOT_FOUND 류가 0개다
  • 코드 목록이 파일 하나에 있고, 문서와 클라이언트 상수는 거기서 생성된다
  • 릴리스 게이트가 사라진 코드를 잡는다
  • 폐기 대상 코드의 방출 건수를 계측하고 있다
  • 각 코드에 소유자가 적혀 있다
  • 포괄 코드가 전체 오류의 몇 퍼센트인지 알고 있다

그리고 하지 말 것.

  • ❌ HTTP 상태만으로 분기하기 — 같은 400이 여섯 가지 이유로 나온다
  • ❌ 메시지 문자열 부분 일치로 분기하기 — 문안 수정 한 번에 죽는다
  • ❌ 읽기 좋다는 이유로 공개된 코드 이름 바꾸기 — 배포된 클라이언트는 되돌릴 수 없다
  • ❌ 접두사 없는 NOT_FOUND — 도메인이 늘면 반드시 겹친다
  • ❌ 코드 문자열에 재시도 여부 박기 — 장애 중에 지표가 두 줄로 쪼개진다
  • ❌ _ERROR, _EXCEPTION 접미사 — 정보량 0에 길이만 늘린다
  • ❌ 코드를 언어별로 번역하기 — 코드는 식별자이지 문장이 아니다
  • ❌ 문서와 클라이언트 상수를 손으로 유지하기 — 반드시 어긋난다
  • ❌ 폐기 날짜만 적고 트래픽을 안 보기 — 지웠는데 누군가 여전히 받고 있었다
  • ❌ 「나중에 쓸지도 모르니까」로 코드 만들기 — 미사용 코드는 목록의 신뢰를 갉아먹는다

정리하면 이렇다. 오류 코드는 문서가 아니라 클라이언트와 맺는 계약이다. 계약의 값어치는 상대가 그것을 보고 다른 행동을 할 수 있을 때만 생긴다. 그래서 개수가 아니라 행동으로 갈리는 단위로 나눠야 하고, 한 번 내보낸 코드는 메시지와 달리 못 바꾼다. 이 두 문장이 나머지 규칙을 전부 만든다.

> 출처: braindetox.kr — 오류 코드 체계를 만든다는 것
> 근거: Windows 10 / Node.js v22.16.0 실행 검증 (가상의 주문·결제 API로 재현)
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 오류 응답을 점검해줘」라고 쓰면 됩니다.
> 대전제: 오류 코드는 클라이언트와 맺는 계약이다. 한 번 내보낸 코드는 메시지와 달리 못 바꾼다.

## 0. 판단의 출발점 — 이 코드는 값어치가 있는가

코드를 하나 늘리기 전에 이 질문에 답한다. 셋 다 「아니오」면 그 코드는 만들지 않는다.

| 질문 | 「예」일 때 의미 |
|---|---|
| 클라이언트가 이 코드를 보고 **다른 화면·다른 동작**을 하는가 | 코드로 갈릴 값어치가 있다 |
| 운영자가 이 실패만 **따로 세거나 알림**을 걸어야 하는가 | 지표 축으로 값어치가 있다 |
| 자동 재시도 여부가 **다른가** | 재시도 계약으로 값어치가 있다 |

- 개수가 아니라 **행동으로 갈리는 단위**로 나눈다
- 같은 화면·같은 동작으로 끝나는 두 실패는 코드 하나 + `details` 로 충분하다
- 「나중에 쓸지도 모르니까」는 근거가 아니다. 코드는 늘리기는 쉽고 줄이기는 거의 불가능하다

## 1. 응답 본문 스키마 — 기계용과 사람용을 갈라 놓는다

```json
{
  "error": {
    "code": "PAYMENT_GATEWAY_UNAVAILABLE",
    "message": "결제사가 응답하지 않습니다. 잠시 후 다시 시도해 주세요.",
    "retryable": true,
    "retryAfterMs": 30000,
    "traceId": "01J8ZQ9K3M7T4V2N6P0R5S8W1X",
    "details": [
      { "subcode": "GATEWAY_TIMEOUT", "attempt": 2 }
    ]
  }
}
```

| 필드 | 대상 | 바꿔도 되나 | 규칙 |
|---|---|---|---|
| `code` | 기계 | **절대 안 됨** (공개된 뒤) | 분기가 읽는 유일한 필드 |
| `message` | 사람 | **언제든** | 절대 파싱 대상이 아니다. 언어별로 다름 |
| `retryable` | 기계 | 코드 단위로 고정 | 없으면 `false` 로 읽는다 |
| `retryAfterMs` | 기계 | 값은 매번 다름 | 없으면 호출자가 정함 |
| `traceId` | 양쪽 | 매 호출 다름 | 사람은 문의에 붙이고, 기계는 로그를 잇는다 |
| `details` | 기계 | **필드 추가만** | 기존 필드 제거·의미 변경 금지 |
| HTTP 상태 | 기계 | 코드 단위로 고정 | 프록시·재시도 계층이 이것으로 판단 |

- `retryable` 을 **코드 문자열에 넣지 않는다** (`..._RETRYABLE` / `..._PERMANENT`)
- 이유: 같은 실패가 상황에 따라 재시도 가능/불가로 갈리면 **코드가 흔들려 지표가 두 줄로 쪼개진다**
- 재시도 여부는 **필드**, 실패의 종류는 **코드**. 축이 다르다

## 2. 코드 형태 판단표

| 판단 항목 | 선택지 | 언제 그것 | 대가 |
|---|---|---|---|
| 번호 vs 문자열 | **문자열 권장** | 로그·스택트레이스를 사람이 읽는다 | 응답당 15~20바이트 증가 |
| | 번호 | 대역폭이 극단적으로 비싸다 (임베디드·SMS) | 6개월 뒤 아무도 못 읽는다 |
| 네임스페이스 | **도메인 접두사** | 도메인이 2개 이상 | 코드 길이 +7자 내외 |
| 구분자 | **밑줄** | 코드가 열거형·메트릭 라벨이 된다 | 없음 |
| | 점·하이픈 | 계층을 시각적으로 보이고 싶다 | 열거형 멤버명으로 못 쓴다 |
| 대소문자 | **전부 대문자** | 상수임을 드러낸다 | 없음 |
| 접미사 | **붙이지 않음** | `_ERROR` `_EXCEPTION` 은 정보가 0 | 없음 |
| 길이 | **32자 이하** | 로그 열 정렬·가독성 | 초과 시 축약이 필요 |

### 번호를 고르면 무엇을 잃나 (실행 확인)

- 오타 한 글자가 **다른 유효한 코드**가 된다 → 조용히 잘못된 분기. 문자열은 대개 목록에 없어 기본 분기로 떨어진다
- 로그에서 `1043` 을 찾으면 `latency_ms=1043`, `bytes=1043` 이 같이 걸린다. 필드명까지 붙여야 정확해진다
- 얻는 것: 고정폭 정렬, 대역별 도메인 구분

## 3. 네임스페이스 규칙

```
{도메인}_{대상}_{상태}      예) ORDER_WINDOW_CLOSED
{도메인}_{상태}             예) SHIPPING_NOT_FOUND
```

- 접두사 없는 `NOT_FOUND` `EXPIRED` `INVALID` `RATE_LIMIT` 은 **도메인이 늘면 반드시 겹친다**
- 겹치면 게이트웨이에서 **먼저 등록한 쪽이 이기고 나머지는 사라진다**. 클라이언트는 무엇이 없는지 알 수 없다
- 단어를 반복하지 않는다: `ORDER_ORDER_NOT_FOUND` ✗
- 정보 없는 접미사를 붙이지 않는다: `..._ERROR` `..._EXCEPTION` `..._FAILURE` ✗
- 접두사는 **한 겹**이면 충분하다. `COMMERCE_ORDER_PAYMENT_WINDOW_CLOSED_ERROR` 는 42자로 로그 열을 무너뜨린다

## 4. 안정성 규칙 — 무엇을 바꿀 수 있고 무엇을 못 바꾸나

| 변경 | 허용 | 이유 |
|---|---|---|
| 메시지 문구 전면 수정 | **가능** | 클라이언트가 파싱하지 않기로 계약했으므로 |
| 번역 추가·수정 | **가능** | 코드는 언어가 없다 |
| `details` 에 필드 추가 | **가능** | 가산적 변경 |
| 새 코드 추가 | **가능** (아래 절차) | 모르는 코드는 기본 분기로 떨어진다 |
| 코드 이름 변경 | **불가** | 배포된 클라이언트의 분기가 즉시 죽는다 |
| 코드 삭제 | **불가** (폐기 절차로만) | 위와 같음 |
| 코드의 HTTP 상태 변경 | **불가** | 프록시·재시도 계층이 이것으로 판단 |
| 코드의 `retryable` 변경 | **불가** | 자동 재시도 동작이 바뀐다 |

- **이름을 바꾸고 싶으면**: 새 이름을 `supersededBy` 필드로 **알리기만** 하고, 전선에 나가는 값은 그대로 둔다
- 실제 교체는 옛 코드 트래픽이 **0이 된 것을 확인한 뒤**에만
- 릴리스 게이트: 이전 버전의 코드 집합과 비교해 **사라진 코드가 있으면 빌드 실패**

## 5. 번역과 메시지

- 서버가 `Accept-Language` 로 문장을 고른다. 없는 언어는 **기본 언어로 폴백**, 그것도 없으면 코드 문자열
- 클라이언트가 자체 번역을 쓰면 **자기가 모르는 새 코드에서 화면이 빈다**
- 그래서 둘 다 보낸다: 클라이언트는 자기 번역을 우선 쓰고, 없으면 서버 `message` 를 그대로 출력
- 숫자·금액·날짜는 서버 문장에 박지 말고 `details` 또는 `params` 로 내려 **클라이언트가 로케일 서식으로 조립**
- **코드 자체를 번역하지 않는다.** `ORDER_ALREADY_PAID_KO` 같은 것을 만들면 분기가 한 언어에서만 산다
- CI에 언어 커버리지 리포트를 붙인다. 번역 구멍은 폴백으로 버티지만, **코드 누락은 못 버틴다**

## 6. 코드를 늘리는 절차

1. **행동을 먼저 적는다.** 「클라이언트가 X를 한다」를 한 문장으로. 못 쓰면 코드가 필요 없는 것이다
2. **기존 목록에서 같은 행동을 찾는다.** 같은 행동 + 같은 HTTP 상태 + 같은 재시도 여부면 **새 코드가 아니라 `details` 다**
3. 이름을 짓는다. `{도메인}_{대상}_{상태}`, 대문자, 밑줄, 32자 이하
4. 레지스트리(단일 파일)에 추가: `code` / `http` / `retryable` / `action` / `since` / `owner`
5. 린터를 돌린다 (§8). 오류 0이어야 병합
6. 문서·클라이언트 상수는 **손으로 쓰지 않는다.** 레지스트리에서 생성
7. 소유자를 적는다. 소유자 없는 코드는 6개월 뒤 아무도 못 지운다

## 7. 코드를 폐기하는 절차

1. `deprecated` 날짜와 `supersededBy` 를 레지스트리에 적는다 — **이 시점에 사라지는 것은 없다**
2. 서버는 계속 옛 코드를 내보낸다. 새 코드는 별도로 추가
3. 옛 코드 **방출 건수를 계측**한다
4. 30일 연속 0이면 삭제 후보. 0이 아니면 **호출자를 먼저 찾는다**
5. 삭제는 레지스트리에서만. 클라이언트 상수·문서는 재생성으로 따라온다

- 폐기 날짜가 코드를 없애는 것이 아니다. **트래픽이 없앤다**
- `UNKNOWN_ERROR` 나 `INTERNAL` 의 방출 건수가 크면 그것은 코드가 아니라 **분류되지 않은 실패 더미**다. 쪼갤 후보 1순위

## 8. 자동 검증 — 레지스트리 한 곳, 나머지는 생성·대조

레지스트리 자체 린트 규칙:

- [ ] `duplicate-code` — 같은 이름이 두 번 등록
- [ ] `bad-shape` — `^[A-Z][A-Z0-9]*(_[A-Z0-9]+)*` 위반
- [ ] `too-long` — 32자 초과
- [ ] `repeated-word` — 접두사와 본문이 같은 단어 반복
- [ ] `useless-suffix` — `_ERROR` `_EXCEPTION` `_FAILURE` 로 끝남
- [ ] `vague-name` — `INTERNAL` `UNKNOWN_ERROR` `INVALID` `FAILED` 같은 포괄어
- [ ] `no-namespace` — 밑줄이 없어 도메인 접두사가 없음
- [ ] `unstable-http` — 같은 코드가 두 상태 코드로 등록
- [ ] `retryable-4xx` — 재시도 가능인데 401/408/429가 아닌 4xx
- [ ] `non-retryable-5xx` — 5xx인데 재시도 불가
- [ ] `deprecated-orphan` — 폐기 표시만 있고 대체 코드가 없음

클라이언트 소스 대조:

- [ ] **죽은 분기** — 클라이언트가 분기하는데 레지스트리에 없는 코드 → **빌드 실패**
- [ ] **미처리 코드** — 서버가 낼 수 있는데 클라이언트가 분기하지 않는 코드 → 커버리지 수치로 보고
- [ ] 죽은 분기에는 **가장 가까운 등록 코드를 제안**한다 (토큰 겹침 비율)

생성물:

- [ ] 클라이언트 상수 (동결된 객체·열거형)
- [ ] 문서 표 (코드 / HTTP / 재시도 / 클라이언트가 할 일)
- [ ] 코드 목록 스냅샷 — 릴리스 게이트가 이전 버전과 비교

## 9. 점검 목록

- [ ] 클라이언트 코드에 **메시지 문자열을 비교하는 분기가 0개**다
- [ ] 같은 HTTP 상태로 나가는 실패들이 **코드로 구분**된다
- [ ] 모든 오류 응답에 `code` 와 `traceId` 가 **반드시** 들어간다
- [ ] `retryable` 이 없을 때 재시도 계층이 **`false` 로 읽는다**
- [ ] 코드에 재시도 여부가 **문자열로 박혀 있지 않다**
- [ ] 도메인 접두사가 있고, 접두사 없는 `NOT_FOUND` 류가 **0개**다
- [ ] 코드 목록이 **파일 하나**에 있고, 문서·클라이언트 상수는 거기서 **생성**된다
- [ ] 릴리스 게이트가 **사라진 코드**를 잡는다
- [ ] 폐기 대상 코드의 **방출 건수를 계측**하고 있다
- [ ] 각 코드에 **소유자**가 적혀 있다
- [ ] 같은 행동 + 같은 상태 + 같은 재시도 여부인 코드 묶음을 **정기적으로 검토**한다
- [ ] `UNKNOWN_ERROR` 류의 비중이 전체 오류의 몇 퍼센트인지 **알고 있다**
- [ ] 번역 커버리지 리포트가 CI에 있다

## 10. 하지 말 것

- ❌ HTTP 상태만으로 분기하기 — 같은 400이 여섯 가지 이유로 나온다
- ❌ 메시지 문자열 부분 일치로 분기하기 — 문구 다듬기 한 번에 죽는다
- ❌ 읽기 좋다는 이유로 공개된 코드 이름 바꾸기 — 배포된 클라이언트는 되돌릴 수 없다
- ❌ 접두사 없는 `NOT_FOUND` — 도메인이 늘면 반드시 겹친다
- ❌ 코드 문자열에 재시도 여부 박기 — 지표가 두 줄로 쪼개진다
- ❌ `_ERROR` `_EXCEPTION` 접미사 — 정보가 0인데 길이만 늘린다
- ❌ 코드를 언어별로 번역하기 — 코드는 식별자이지 문장이 아니다
- ❌ 문서와 클라이언트 상수를 손으로 유지하기 — 반드시 어긋난다
- ❌ 폐기 날짜만 적고 트래픽을 안 보기 — 지웠는데 누군가 여전히 받고 있었다
- ❌ 「나중에 쓸지도」로 코드 만들기 — 미사용 코드는 목록의 신뢰를 갉아먹는다
