Three Axes That Determine Image File Size

The size of an image file matters beyond storage space, because it directly affects how quickly a web page appears and how much data is transferred. The web.dev Learn Images course describes images as the biggest assets on the web in both total transfer size and number of requests, and it states that the median web page transferred roughly 2MB as of June 2022, with images accounting for nearly half of that.

The ways to reduce file size fall into three independent levers. The first is reducing resolution, which cuts the number of pixels itself. The second is adjusting the quality value of lossy compression, which reduces the amount of information stored. The third is converting to a file format that uses a different compression method. The three are not mutually exclusive and can be combined. A statement marked as a calculation is plain arithmetic rather than a sentence from an official document, and only statements that name a source, such as web.dev or MDN, report what that document says.

Which lever to use first depends on where the image will end up. web.dev states that the only way to present a fully rendered image to a user more quickly is by reducing its transfer size. Of the three levers, resolution reduction changes the pixel count itself and so sets the starting point for the other two, while quality value and format change how the same pixels are written down.

Resolution Adjustment - Reducing File Size by Reducing Pixels

Resolution is the number of horizontal and vertical pixels that make up an image. web.dev explains a raster image as a set of pixel-by-pixel instructions for rendering a two-dimensional grid, so fewer cells means fewer instructions to describe. A photo that is 4000 pixels wide and 3000 pixels tall has 12 million cells (calculation), and halving both dimensions leaves 3 million, one quarter of the original (calculation). For compressed formats, file size depends on the image content, so the drop in pixel count is not the same as the drop in file size.

  • The Apple support document says that when you change an image size in Preview, you can enter new values for width and height or choose Percent from the pop-up menu. To keep the original proportions, you select the option for scaling proportionally, and changing one of width or height then changes the other to match.
  • The procedure the same document gives for reducing the image file size is to choose Tools and Adjust Size, select the resample option, and enter a smaller value in the resolution field. The new size appears at the bottom of the dialog. Conversely, the document says that turning the resample option off makes the dimensions smaller without losing detail.
  • web.dev explains that a raster image scaled beyond its inherent dimensions appears distorted, blocky, or blurred. Because the large original may be needed later, keeping it separately is the safer practice. The web.dev PNG page likewise describes keeping a canonical version of a source image in a local environment or repository in case it needs to be edited or re-saved in another format.
  • web.dev treats responsive images, which serve an image sized for how it is displayed, as a separate topic of the Learn Images course. Reducing resolution connects to the starting point of responsive images, which is not making users download an image larger than they need.

The Apple support document introduces resizing as a way to reduce the file size to save disk space or to download an image faster. The new size appears at the bottom of the dialog right away, so you can gauge the result while changing the values.

Compression Methods and Quality Values - Lossy vs Lossless

web.dev explains lossless compression as describing the same information with fewer bytes, using a spoken analogy of run-length encoding, such as stating that row one, columns one through three are blue instead of repeating each cell. The visual information is untouched, so fidelity does not change. Lossy compression, in web.dev's words, is an exercise in finding the balance between the level of visual detail we can perceive and the amount of data sent, and that balance is determined by the content of the source image. MDN summarizes the same split: lossy compression discards image data to get much smaller files, while lossless compression reproduces the original exactly.

  • The quality value: web.dev says the technical detail of JPEG is exposed as a single quality setting, an integer from 0 to 100. A value of 0 gives the smallest file and the worst visual quality, and both quality and file size increase as the value rises. The setting is subjective, so not every tool interprets a value of 75 the same way, and perceived quality varies with the content of the image.
  • How JPEG is structured: web.dev says JPEG encodes image data as eight-by-eight blocks of pixels rather than as individual pixels. It uses a discrete cosine transformation to split the image into luminance and chrominance layers, and because our eyes are more sensitive to differences in brightness than in hue, the chroma layers are reduced significantly, including by subsampling, which stores a chroma layer at a lower resolution.
  • When compression is taken too far: web.dev states that compressing too aggressively reduces detail beyond what our psycho-visual systems would naturally ignore, and because JPEG works in blocks, the seams between blocks can start to show. In the Squoosh example on the same page, a quality setting of 60 reduced the file size by 79%. That is the result for that photo and that tool, not a general figure.
  • Progressive JPEG: web.dev explains that progressive JPEG shows a blurry full image first and sharpens it as the transfer continues. Except for the smallest images it is almost always slightly smaller than a baseline JPEG, though decoding is a little more complex on the client.

web.dev also states that differences in quality across most of the quality scale will be imperceptible to the human eye, even when performing a side-by-side comparison. So the quality value is not a number to push as low as possible but a balance point that depends on the image content. Below that point, the block seams and lost detail described above start to show first.

Format Conversion - Characteristics and Selection of JPEG, PNG, and WebP

The MDN image format guide lists the factors for choosing a format as compression, quality, the breadth and depth of browser support, and whether you need features such as transparency or animation. The same document advises preferring lossless encoding for screenshots, diagrams, logos, and line art, because blurring and colored fringes around text and sharp edges are very visible. It adds that photographs and other continuous-tone images can usually tolerate lossy compression because the discarded detail is harder to see.

JPEG - Lossy Compression Suited to Photographs

MDN describes JPEG as currently the most widely used lossy compression format for still images, particularly useful for photographs. Its compression is lossy and based on the discrete cosine transform, and it does not support an alpha channel for transparency. The document warns that applying lossy compression to content requiring sharpness, like diagrams or charts, can produce unsatisfactory results. The maximum dimensions are 65,535 by 65,535 pixels. MDN advises preferring PNG when more precise reproduction is required, or WebP or AVIF when both better reproduction and higher compression are required.

PNG - Lossless Compression for Transparency and Diagrams

MDN says PNG uses lossless compression, supports full alpha transparency, and is preferred over JPEG for more precise reproduction of source images or when transparency is needed. web.dev says PNG never reduces visual quality but almost invariably produces excessively large files compared with more modern encodings, so it is almost never the right choice for photographic content. It can be considered for simple artwork that needs semi-transparency, such as a company logo containing a drop shadow, and should then be compared carefully with WebP, which also supports semi-transparency. The statement that the same photo might be a few hundred kilobytes as a JPEG and several megabytes as a PNG is on the web.dev raster images page. The PNG page also calls PNG a sound choice for keeping a manageable canonical version of a source image.

WebP - A Format Covering Lossy, Lossless, and Transparency

MDN says WebP supports lossy compression based on the VP8 video codec and lossless compression that uses substitutions for repeating data, along with transparency and animation. By the same document, lossy WebP images are on average 25 to 35% smaller than JPEG images of visually similar compression levels, and lossless WebP images are typically 26% smaller than the same images in PNG format. The maximum dimensions are 16,383 by 16,383 pixels. WebP is widely supported in the latest versions of major browsers, and MDN advises providing a JPEG or PNG fallback for older environments. It also notes that on Safari for macOS, support requires both Safari 14 or later and macOS Big Sur (11) or a more recent version.

MDN also covers AVIF. It gives an example in which lossy AVIF images are around 50% smaller than JPEG images, while warning that AVIF does not support progressive rendering, so files must be fully downloaded before they display and the impact grows for larger files. It advises providing fallbacks with the picture element. web.dev says AVIF support arrived in Chrome and Opera in 2020, Firefox in 2021, and Safari in 2022. Taking these documents together, photos are candidates for JPEG or WebP, and diagrams or logos needing semi-transparency are candidates for PNG or WebP, with browser support weighed in each case.

Reducing Size with Built-in Windows Tools - Paint and Photos

The Microsoft Paint help page presents Paint as suited to simple image cropping, resizing, drawing, and adding basic shapes and text. In the English text of that document, resizing is the Resize option on the Home tab, and the new size can be given in pixels or as a percentage of the original size. In the Korean menu this appears as the feature named Resize and Skew. What follows is the range the documents cover for Windows 11.

  • Reducing resolution in Paint: open the image in Paint, choose the resize feature, pick percentage or pixels as the unit, and enter a value. Entering 50 percent, for example, halves width and height and leaves a quarter of the pixels (calculation).
  • The resize options in Paint: the Resize option on the Home tab takes a new size in pixels or as a percentage of the original. Pixels fix the resulting resolution exactly, while a percentage only needs a ratio to the original.
  • The scope of the Photos app: the Microsoft Photos editing document describes features such as crop, flip, rotate, light and color adjustments, and drawing. The editing it covers is about fixing the shape and color of an image.
  • Images in Office documents: the size of a picture inserted into an Office program is handled by that program's own picture compression feature, which acts on a different object than the image-file methods above.

The Windows method the documents give for reducing resolution is the resize feature in Paint. The Photos app centers on editing features such as crop, rotate, and color adjustment.

Reducing Size with Built-in macOS Tools - Preview Adjust Size and Export

The Apple Preview user guide covers both image resizing and file format conversion. The resizing document (prvw2015) describes the following.

  • Changing the size: open the image in Preview and choose Tools and Adjust Size. Enter new values for width and height, or choose a size from the Fit Into pop-up menu. When you pick a size from that menu, the document notes that the image width or height may come out smaller than the chosen size in order to keep the proportions.
  • Reducing the file size: in Tools and Adjust Size, select the resample option and enter a smaller value in the resolution field, and the new size appears at the bottom. The unit can be switched to percent, and proportions are held with the option for scaling proportionally.
  • Keeping detail: to resize to a smaller size without losing detail, the document says to deselect the resample option before changing the width or height.
  • Export and formats: choose File and Export, set the name and location, then pick an image format such as PNG from the Format pop-up menu. The guide's start page lists the formats Preview supports as HEIC, JPEG, JPEG 2000, OpenEXR, PDF, PNG, and TIFF.

To resize several images at once, the Apple document says to show them in the same window, select them in the sidebar, and then choose Tools and Adjust Size. On export, the documented steps end at setting the name and location and choosing a format from the list on the start page.

Criteria by Use Case - Email, Web, Documents, and Submissions

MDN and web.dev give criteria about format and transfer size rather than a pixel count or percentage for each purpose. This section groups those criteria by use. Where a numeric standard is needed, the specification given by the receiving service or the office collecting the file takes priority. For mail, web, documents, and submissions, the thing to weigh first differs: the service limit, the display size, the kind of image, and the intake specification.

  • Email attachments: limits differ by mail service and by the recipient's settings, so the service's guidance is the reference. If the limit is exceeded, use resolution reduction first among the three levers, and adjust the quality value only if the file is still too large.
  • Web publishing: web.dev says images are the biggest assets on the web, so optimizing them may be the single biggest performance optimization. MDN recommends WebP or AVIF for raster images and advises providing a PNG or JPEG fallback with the picture element for browsers that lack support.
  • Document insertion: borrowing MDN's distinction, lossless suits diagrams and screenshots and lossy suits photos. How much the whole document grows after insertion depends on how the program handles pictures.
  • Proof submissions: if the intake system fixes the format and size, that takes priority. Use lossy compression only as far as text and seals stay unsmeared, and if the file is still too large, consider reducing resolution before lowering quality.

Metadata and Location Information - What to Check Before Sharing

Apart from reducing the file size, there is something to look at before sharing. The Apple support document says that if a photo contains GPS information, you can choose Tools and Show Location Info in Preview to see where it was taken on a world map and a street map. It adds that if the menu item is gray, the image contains no location information. That gray menu item is the signal that separates photos with location data from those without.

  • Whether location data exists: according to the Apple document, a photo file can contain GPS information about where it was taken. For a photo going to a public board or a second-hand marketplace, it is safer to check for such information before uploading.
  • How to check: on macOS, you can tell by whether Tools and Show Location Info is active. If the menu item is gray, the image has no location information.
  • How a tool handles files: the Squoosh GitHub README says it does not send images to a server and that all compression happens locally. The same document also states that it collects basic visitor data, the before and after image size values, and PWA installation details through Google Analytics.
  • Metadata after conversion: location information is a value stored inside the photo file, so a file that has been resized or converted can be checked with the same menu item to see whether it remains.

Making the copy for sharing as a separate file and keeping the original, which holds the location data, apart keeps that original from going out.

What Could Not Be Confirmed

  • The menu name and location of image resizing in the Windows 11 Photos app, a quality slider and recommended values there, the exact name of an aspect ratio checkbox in Paint, and the steps for saving as JPEG in Paint. The Microsoft documents do not describe them.
  • The quality slider, alpha checkbox, and estimated file size display on the macOS Preview export screen. The Apple pages have only the list of export formats and the File and Export path.
  • Recommended resolution and quality values for email, web, documents, and proof submissions, and the attachment limits of mail services. No official standard exists, so these must be decided by situation.
  • General figures for how many percent a file shrinks when resolution is halved or the quality value changes. They differ with image content and the documents do not state them.
  • Whether metadata such as location information remains after resizing or conversion, whether messengers and photo apps remove it, and how automatic compression in Office behaves.
