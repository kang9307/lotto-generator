「Don't Roll Your Own」原則 2026 - ブラウザの基本機能を再発明してはいけない7つの理由

なぜ2026年のWeb UIは再びネイティブへ回帰しているのか

2026-05-25 IT・技術

序論:すべてのWebサイトが同じコンポーネントを再実装する奇妙な風景

無作為に100サイトを開いて検証ツールを覗くと、ある事実に気づく。ほぼすべてのサイトが同じコンポーネントを自前で作っている。ドロップダウン、モーダル、アコーディオン、日付ピッカー、ファイルアップローダー、プログレスバー、フォームバリデーション。これらはすべてブラウザが標準で提供しているのに、90%以上のサイトが div と JavaScript でゼロから再実装している。OSが提供するファイルダイアログをすべてのデスクトップアプリが自前で作り直していたら非効率と呼ぶだろう。だがWebでは、それが標準的な慣行になっている。

news.hada.io 2026年5月24日付トピック6番「Don't Roll Your Own」Principle はこの現象に適切な名前を再び与えた。この原則の出発点は1990年代後半の暗号学領域だ。「Don't roll your own crypto」──自前で暗号アルゴリズムを作るな。誤って作れば安全という幻想だけを与え、実際には危険になるという警告だった。その後同じ原則が認証・セッション管理・HTMLパーサー・日付ライブラリへと拡張された。そして2026年、再びWeb UI領域へ戻ってきた。本稿は hada.io の短い議論を単なる翻訳ではなく、筆者の観察と日本・韓国の開発者環境への含意を加えて12章で展開する。

核心質問は3つだ。第一にブラウザネイティブ機能を自前で再実装すべきでない具体的理由は何か。第二に2026年基準で十分に成熟している機能は何か。第三にそれでも自前で作るべき正当な例外は何か。この3問に答えながら、GitHub・Stripe・Linear のような UX 一流企業がネイティブを選ぶ理由、React・Vue 生態系が作り出した誤った慣行、そして日本のデザイナー・PdMと交渉する実務的方法までを扱う。

「Don't Roll Your Own」の短い歴史 - 暗号からUIへ

原則自体の出自を正確に押さえておく。「Don't roll your own crypto」は Bruce Schneier をはじめとするセキュリティ研究者が1990年代後半から繰り返してきた警告だ。自前の暗号アルゴリズムは検証されないまま配布され、ユーザーに誤った安心感を与える。標準ライブラリ(OpenSSL・libsodium など)は数十年・数百人の専門家の検証を経た成果物だ。両者の信頼度差は比較自体が無意味なほど大きい。

第二の拡張は認証とセッション管理だ。PHPで直接セッションを管理していた時代の無数の脆弱性が、OAuth・OpenID Connect・検証済みセッションライブラリへと整理される中で、同じ原則が定着した。CSRF・セッション固定・セッション再生成の微妙なバグは、自前実装で必ず発生する。「認証は自前で作らず検証済みのものを使え」というコンセンサスがバックエンド陣営に定着した。

第三の拡張がまさに2026年のWeb UI領域だ。この領域で「自前で作るな」と言われている対象こそ、ブラウザが既に提供するネイティブHTML要素群──select・dialog・details・各種 input type・progress・video・audio──だ。これらは W3C・WHATWG 標準を基に、すべての主要ブラウザで数十年磨き上げられた成果物だ。それでも開発者は div を敷き JavaScript を載せてゼロから再実装する。hada.io の議論は要するに、暗号と認証を救った同じ原則をWeb UIにも適用すべき時だと言っている。

再発明すべきでないブラウザネイティブ機能10選

筆者が整理した、2026年基準で既に十分成熟しわざわざ自前実装する理由がないネイティブ機能10選だ。各項目について「なぜよく再発明されるのか」と「なぜネイティブが優れているのか」を簡潔に見ていく。

1) <select> ドロップダウン

最もよく再発明される要素だ。デザイナーが「スタイリングが難しい」と言うため div に置き換えられたケースが多い。だが2024年から appearance: base-select 提案がブラウザに入り始め、2026年には Chromium・Firefox で Customizable Select が正式サポート段階に入っている。標準 select 1行でキーボードナビゲーション、モバイルホイールピッカー、検索、アクセシビリティツリー登録までを無料で得られる。

2) <details> / <summary> アコーディオン

アコーディオンとトグルは details/summary 1組でJS 0行で実装できる。open属性のトグル、キーボードEnter/Space動作、ブラウザ内検索への取り込みまで自動だ。Reactコンポーネントで同じ動作を再現するのに平均100~300行のコードがかかる。

3) <dialog> モーダル

2022年に全主要ブラウザで安定化して以降、dialog はモーダルの正解になった。showModal() 呼び出し1回でフォーカストラップ・ESC閉じ・backdrop自動生成・アクセシビリティ処理まで終わる。::backdrop 擬似要素で背景スタイリングも自由だ。自前モーダルでよく抜ける「モーダル内でのTab循環」のような微妙な動作がネイティブでは無料だ。

4) <input type="date | time | datetime-local"> 日時

React生態系では react-datepicker・MUI DatePicker が事実上の標準のように使われるが、モバイルOSのホイールピッカーをネイティブで提供する input type=date の方が使い勝手が良いケースが多い。日本のモバイルユーザーの大半がiOS・Androidの慣れたOSピッカーをより素早く操作できる。CSS で ::-webkit-datetime-edit の細かいスタイリングも可能になった。

5) <input type="file"> ファイルアップロード

ドラッグ&ドロップ領域まで作りたい場合も、ネイティブ input type=file の上に dropzone CSSを重ねるのが正解だ。multiple・accept・capture 属性はモバイルでカメラ・ギャラリーを直接呼び出すための核心であり、自前アップローダーがほぼ必ず取りこぼす部分だ。

6) <progress> / <meter> プログレスバー

div+width アニメーションで作ったプログレスバーはアクセシビリティツリーに登録されない。スクリーンリーダーはただ「リージョン1」と読み上げる。progress 要素は value・max の2属性だけでアクセシビリティツリーに自動登録され、読み上げ時に正確なパーセントが出る。同機能のためARIAを手動で付けるより遥かに安全だ。

7) <video> / <audio> メディア

video.js のようなライブラリは確かに強力だが、単純再生用ならネイティブ video が PIP・字幕・再生速度・音量まで提供する。controls 属性1行で OS別に最適化されたコントロールが現れる。メディアライブラリが本当に必要なのは HLS・DRM・ストリーミングのような特殊領域だ。

8) input type="color | range | search | tel | email | url"

type を正確に指定するだけでモバイルキーボードが自動変換され、バリデーションが無料で動作し、モバイルで音声入力・自動補完・OSパスワードマネージャー連携まで自動で有効化される。placeholder だけ変えて type を text のままにする間違いが日本のサイトでも頻繁に見られる。

9) フォームバリデーション (required・pattern・minlength・maxlength)

HTML5のフォームバリデーションは自前JSバリデーションより速くアクセシビリティも良い。:valid・:invalid CSS 擬似クラスでスタイリングが可能で、novalidate 属性で部分的に無効化もできる。JSバリデーションはネイティブを補完する用途に留めるのが2026のベストプラクティスだ。

10) スクロール動作 (scroll-snap・scroll-behavior・overscroll-behavior)

カルーセルとスライダーを自前で作る代わりにCSS scroll-snapを使えばJS 0行で滑らかなスナップスクロールが動く。smooth scrolling は scroll-behavior 1行で、オーバースクロール処理は overscroll-behavior で終わる。モバイルの慣性スクロールまでネイティブが自動処理するので手間がかからない。

再発明の5つのコスト - コードが増えるだけではない

「なぜネイティブを使わず自前で作るのか」の次の問いは「自前で作ると正確に何を失うのか」だ。筆者が整理した5つのコストは以下の通り。

  • アクセシビリティ(a11y)の喪失:ネイティブ要素はARIA役割・キーボードショートカット・スクリーンリーダー読み上げパターンがすべて無料だ。divで再実装すると平均200~500行のJSと数十時間のa11y QAが追加で必要となり、それでもネイティブに及ばないケースがほとんどだ。
  • キーボードショートカットの欠落:selectに入って最初の文字を押すとその文字で始まるオプションへジャンプする動作、dialogでTabが循環する動作、detailsでEnterで開閉する動作──こうした微妙なキーボードパターンが自前コンポーネントではほぼ100%抜ける。
  • モバイル互換性問題:ネイティブ input type=date は iOS でホイールピッカー、Android でマテリアルカレンダーを自動表示する。自前datepickerは両プラットフォームで違和感がある。同じことが file・color・range でも発生する。
  • バンドルサイズの肥大化:react-select 50KB、react-datepicker 40KB、react-modal 15KB、react-dropzone 30KB。よくあるSPAの1画面に平均150~300KBのコンポーネントライブラリが入っている。ネイティブに置き換えるとその重さが0KBになる。
  • 保守負担:ライブラリはメジャーバージョン更新のたびに壊れる。React 18→19移行で react-select の API が変更され、数千のSaaSが移行コストを支払った。ネイティブは標準が壊れないため永遠に動作する。

この5つのコストを定量化すると、平均的な中堅SaaSで年間200~500人時(person-hour)の追加コストがコンポーネント再発明から発生する。デザインシステムコンサルでよく聞く反応は「それなら正社員1人分の人件費」というものだ。ネイティブ転換はそのコストをほぼ0にする。

では再発明が正当化される時 - 3つの例外シナリオ

本稿の結論が「すべてのコンポーネントをネイティブで使え」なら半分は間違いになる。自前で作るのが正当な3つのシナリオを正確に押さえておく。

  • ネイティブが全く提供しないインタラクション:ドラッグ&ドロップ並び替え、無限スクロール仮想化、マルチカラムグリッド、コードエディタ、Canvasベースのホワイトボード。これらはネイティブが提供しないため、自前作成か検証済みライブラリの採用が正解だ。
  • ブランドアイデンティティが決定的価値である領域:決済ページの核心カード領域、メインヒーロー領域、ランディングページのシグネチャコンポーネント。デザインが即ユーザーの信頼の根拠となる領域では、ネイティブの制約を解いてカスタムに進むのが正当だ。
  • ネイティブの構造が要件と合わない場合:ネストメニュー(メガメニュー)、仮想キーボード、仮想ドロップダウン(数万件のオプション)。selectが1万件を画面に描画するとブラウザがフリーズする。こうしたケースは仮想化が必須なのでカスタムが正解だ。

核心となる意思決定ルールはシンプルだ。「ネイティブが70%でも満たすならネイティブで行け」。残り30%を埋めようと100%カスタムに進むと、結果としてアクセシビリティ・バンドル・保守コストすべてで損する。30%のギャップはCSSや少しのJSで補完するのがほぼ常に安い。

2026年のネイティブ機能進化 - View Transitions・Anchor Positioning・Popover

2026年がネイティブを再び魅力的にした理由の1つは、ブラウザがこれまで決定的に不足していた機能を急速に埋めている点だ。最も影響力があると見る3つの新機能を見る。

View Transitions API

SPAの滑らかな遷移アニメーションのために framer-motion や react-spring を入れていた時代が終わる。View Transitions API は DOM 変更前後を自動キャプチャし、その間を滑らかに補間する。document.startViewTransition() 1行でページ遷移・要素移動・リスト整列アニメーションがすべて動く。Chrome・Safariがサポート、Firefoxも2026年初に正式サポートに入った。

CSS Anchor Positioning

ツールチップ・ドロップダウン・ポップオーバーの位置取りのために Popper.js・floating-ui を使っていた時代も終わる。CSS anchor-name・position-anchor 属性で「この要素の横に自動配置、画面外なら反対側へ反転」という動作がCSSだけで動く。2025年Chrome正式サポート、2026年Firefox・Safariも安定化段階だ。

Popover API

popover 属性と popovertarget でツールチップ・ドロップダウン・メニューをJSなしで作れる。dialogに似ているがモーダルではない非ブロッキング型なのでより軽い。Anchor Positioningと組み合わせればほぼすべての浮遊UIがネイティブで可能になる。

この3つのAPIの登場により、2024年まで「ネイティブでは不可能」とされていた領域の70~80%がネイティブで可能になった。そしてこの流れは加速する可能性が高い。Interopプロジェクト(2022年開始)が4年目に入り、主要4ブラウザが同じ機能を同じスケジュールでリリースする協力モデルが定着しているためだ。

CSS変数と::backdropでスタイリング - ネイティブを保ちつつデザイン

「ネイティブを使うとデザインが醜くなる」という反論は2026年基準ではもはや有効ではない。CSSの進化でネイティブ要素をほぼあらゆる箇所でスタイリングできるようになったからだ。筆者がよく使う3パターンを見る。

まず::backdrop 擬似要素だ。dialogとpopoverの背景を ::backdrop で掴めば backdrop-filter: blur(10px)・background: rgba(0,0,0,0.5) のような効果が自由になる。iOS Safari も2024年からサポートする。

次にCustomizable Select の appearance: base-select だ。Chromium 130+ Firefox 135+ でネイティブ select のオプション領域をほぼ全側面で CSS スタイリングできる。::picker(select)・option::checkmark のような擬似要素でデザインシステムのルック&フィールを完全に再現できる。

最後にcolor-scheme・accent-color だ。accent-color 1行で input type=checkbox・radio・range・progress のブランドカラーがすべて統一される。自前チェックボックスを作る数百行の労力がCSS 1行で終わる。

この3技法だけ知っていればデザインシステムの90%以上の視覚要件をネイティブの上で満たせる。「デザイン vs アクセシビリティ」の二分法が2026年には消失したことが最大の変化だ。

事例分析 - GitHub・Stripe・Linearがネイティブを使う理由

理論は十分だ。実際にUX一流企業がどうネイティブを使っているか見る。

GitHub

GitHubは2020年頃からデザインシステムPrimerを整備しながらネイティブHTMLを第一順位に置く方針を明文化した。details/summaryで作ったサイドバートグル、dialogで作ったPRモーダル、ネイティブselectの上に乗せた検索可能ドロップダウンが代表例だ。結果としてGitHubのページ重量は同規模SaaS平均より30~40%軽く、キーボードショートカットは全ページで自然に動く。

Stripe

Stripe Dashboardはネイティブform validation・input type=number・input type=emailを積極的に使う。決済ページのカード入力領域だけPCI-DSS要件でiframe隔離されており、その他の領域はほぼすべてネイティブだ。結果としてStripe Dashboardはロード速度とアクセシビリティスコア両方でSaaS平均を圧倒する。

Linear

Linear自体はデザインシステムのインスピレーション源となるサイトだが、内部的にはdetails・dialog・nativeフォームを多く使う。キーボードショートカットがどこでも自然に動く理由の1つがネイティブの上に乗った構造だからだ。デザインがかっこいいからネイティブを諦める必要はないという最良の証拠だ。

3社の共通点は「デザイン vs ネイティブ」の二分法を拒否する点だ。ネイティブの上にデザインを乗せる方が、デザインをゼロから作り直すより速く安定するというコンセンサスが社内に定着している。このコンセンサスはシニアエンジニアとシニアデザイナーの信頼関係でのみ可能だ。

React・Vue生態系の誤った慣行 - shadcn・MUIも無条件に信頼するな

React・Vue生態系のコンポーネントライブラリは2種類だ。1つはネイティブの上に乗せる形式(Radix UI・Headless UI 一部、Ariakit)、もう1つはdivでゼロから作った形式(多くのデザインシステム)。使用前にどちら側か必ず確認する必要がある。

shadcn/uiはRadix UIをベースとするため概して良いアクセシビリティ出発点を提供する。だがその中の一部コンポーネント(特にSelect・Dropdown Menu)はdivで再実装されており、ネイティブselectではない。モバイルでOSホイールピッカーが出ず、キーボード動作も若干異なる。使用前にどのコンポーネントがどの要素を基盤としているか確認する習慣が必要だ。

MUIも同様だ。MUIのSelectはdivベースで、モバイルでネイティブと異なる動作をする。MUIのDatePickerは50KB+の追加バンドルだ。単純なケースならネイティブselect・input type=dateを使う方が軽く速い。

筆者がよく使うルールはシンプルだ。「Radix・Ariakit・Headless UI のような unstyled ライブラリが必要な場合のみライブラリ、それ以外はネイティブ」。デザインシステムのコンポーネントライブラリがゼロから div で作られている場合、使用コストはネイティブより常に高い。

開発者が即適用できる5つのチェックリスト

以下5つを次のPRから適用してみよう。1つだけでも即効性がある。

  1. モーダルはdialogに変えろ。react-modalを使っていた箇所をネイティブdialog + showModal()に置き換える。平均15KBバンドル削減+キーボード動作自動化。
  2. アコーディオンはdetails/summaryに変えろ。自前実装のトグルコンポーネントをすべて削除する。平均200~300行JS削除。
  3. 日付入力はinput type=dateに変えろ。モバイルが70%以上ならほぼ常に使い勝手が向上。react-datepicker 40KB削除。
  4. フォームvalidationはネイティブrequired・patternを第一順位に置け。JSバリデーションは補完用に留める。
  5. 新機能PRでdiv+roleより先にネイティブ要素があるか検索する習慣を持て。「dropdown」キーワードでMDNを先に検索する習慣が1年後に大きな差を作る。

この5つはすべてPR単位で即適用可能で、即可視的効果(バンドルサイズ・Lighthouseスコア・アクセシビリティスコア)を出す。デザイナーとの合意が必要な領域ではなく開発者が単独で決定できる領域だ。

日本のデザイナー・PdMとの交渉方法

日本のIT組織で最もよく発生する対立は「デザインシステムが定めたルックをネイティブが追随できない」というデザイナー側の意見だ。この時筆者が実務で使う交渉パターン3つを共有する。

まず「機能別分離交渉」だ。全コンポーネントを一気にネイティブへ転換せず、影響の大きい5つ(モーダル・ドロップダウン・アコーディオン・日付・ファイル)から先にネイティブへ転換し、残りはデザインシステム維持を約束する。段階的交渉は正面衝突より常に速い。

次に「数字で語る」。デザイン変更のコストをKB・ms・アクセシビリティスコアに換算する。「react-datepickerをネイティブinput type=dateに置き換えるとモバイルで700ms速くなりバンドルが40KB減ります」という文はデザイナーが拒否しづらい。「ネイティブの方が良いです」より100倍効果が大きい。

最後に「デザイナーに統制権を渡す」。CSS変数でデザイントークンを公開し、デザイナーが色・間隔・フォントを直接調整できるようにする。デザイナーが結果物を統制できればネイティブへの抵抗感が大きく減る。これが筆者が見た最も効果的な交渉方法だ。

日本のPdMには「ユーザーの70%がモバイルで、そのユーザーはOSピッカーをより上手に使う」というユーザビリティデータを最初に提示する。UXデータがデザイン意思決定に勝るという事実は日本の企画組織でも徐々に明確になっている。

結論と即実行可能な3つ

本文の核心を1文にまとめる。2026年のWeb UIは「自前で作る」時代を終え「ネイティブの上に乗せる」時代へ移動する。ブラウザはこれまで不足していた機能を急速に埋めており、CSSはネイティブをデザインするあらゆる道具を提供する。自前で作るコストは時間・バンドル・アクセシビリティ・保守の4側面すべてで徐々に高くなる。一方ネイティブの標準は壊れず永遠に動作する。

即実行可能な行動3つを整理する。

  1. 次のPRでモーダル1つをdialogに置き換えろ。1時間以内に完了し、即時バンドル15KB削減+アクセシビリティスコア上昇の結果を見る。
  2. 自社SPAのコンポーネントライブラリ使用実績を監査せよ。どのコンポーネントがネイティブで置き換え可能か1週間以内にリストを作る。このリスト自体が今後1年の改善ロードマップになる。
  3. デザインシステム会議で「ネイティブ第一順位」方針を提案せよ。デザイナーに統制権(CSS変数)を渡す条件で交渉すれば通過確率が高い。方針が定着すれば年間200~500人時の削減が自動で発生する。
