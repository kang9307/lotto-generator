时区是数据而非代码 - 更新之后连过去时刻的解释都会改变

为什么存下来的值没变而屏幕上的时刻变了，以及要存什么才能在日后重新算出答案

2026-07-30 开发/基础设施

引言：存下来的值没变，可看到的时刻和昨天不一样

有一类 bug 最难理解。数据库里的值谁都没动过，可屏幕上显示的时刻和昨天不一样。审计日志的时间戳挪了一个小时。几年前那条记录的时刻变了。而上线的只有一次依赖版本升级。

这时候人们首先怀疑的是代码。翻转换函数、核对服务器时间、翻审计记录找是谁改了数据。然后什么也找不到。因为值真的没变。变的不是值，而是读取这个值所用的规则。

这篇文章的心脏是一句话。

时刻是值，时区是规则。规则不是以代码的形式发布的，而是以会被定期修订的数据文件发布。所以一旦更新，同一个值的解释就会改变 — 不只是未来，过去也一样。

听起来很抽象。所以这篇文章一开始不做任何断言。取而代之的是用此刻在这台机器上跑出来的输出来证明这句话。这台机器上恰好有两个各自携带时区数据的运行时，而且两者的数据版本不同。于是把同一个存储值交给它们，在某些过去的时点上会得到彼此不同的答案。我数清了有多少条、落在哪个地区哪些年份。

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际跑出来的。运行时为 Node.js v22.16.0 (win32 x64) 与 Python 3.13.3 (win32 AMD64)。两者的时区数据来源与版本如下。

  • Node.js — 由内置的 ICU 77.1 携带时区数据。process.versions.tz 报告为 2025b
  • Python — zoneinfo.TZPATH 是空元组。也就是说这个平台没有系统时区数据库，数据由 PyPI 上的 tzdata 包提供。该包版本为 2025.3，tzdata.IANA_VERSION 为 2025c
  • 同一天 IANA 发布页公告的最新版本是 2026c（2026-07-08）。两个运行时都不是最新的，彼此也不一致

本文没有更新也没有改动任何系统时区数据。要证明「更新会改变解释」，并不需要真的去更新。在同一台机器上并排跑两个数据版本不同的运行时就够了。所有脚本都写入文件后执行。

本文不涉及的内容。测量经过时间该用哪种时钟是另一个主题，这里不碰。夏令时边界上的两个洞只用一节带过，那本身值得单独成篇。字符在编码边界上损坏的问题请看 cp949 与 UTF-8。

1. 时刻是值，时区是规则

先要把术语切分清楚。这个区分一旦模糊，后面所有的论述都不成立。

  • 瞬间（instant） — 宇宙中只发生过一次的那个点。通常用自基准时点起的秒数，也就是 epoch 值来表示。这是值。任何政府都改不了这个数字
  • 本地时间（local time） — 某个地区的人给这个瞬间起的名字，比如「2026 年 7 月 30 日 13 点」。这是计算结果
  • 偏移量（offset） — 那个瞬间该地区离基准时有多远，写作 +09:00 这样。这也是计算结果
  • 时区（time zone） — 把瞬间换算成本地时间的整套规则历史。Asia/Seoul 这样的地区标识符指向的就是这一束规则。这才是数据

关键在最后一项。Asia/Seoul 的意思不是「加 9 小时」。它的意思是从 1890 年至今这个地区的钟表遵循过哪些规则的整份记录。这份记录存放在 IANA 时区数据库里，一旦政府改动规则、或者过去记录中的错误被发现，就会以新版本发布出来。

IANA 发布页写着，这份数据会「为反映政治机构对时区边界、基准时偏移量和夏令时规则所做的变更而定期更新」。并且最终用户「通常通过软件和操作系统供应商获得这份数据的更新」。这两句话制造了本文的全部问题。规则在外部改变，而我们大体上不知道自己是什么时候收到的。

  • 取值范围也比想象的宽。+14:00 是存在的。也就是说按本地日期算，总有一些瞬间横跨两个日历日

4. 同一台机器，两个数据版本，33 处不一致

表格最后两行在工程上同样会闯祸。

  • 在 1980 年两个运行时是一致的。也就是说这类不一致并不会遍布整个区间。它只在特定地区、特定年份区间冒出来。如果测试只用近期日期，就永远抓不到

由此得出的结论。「存储值没变而屏幕变了」不是异常行为，而是设计如期运转的结果。用地区标识符存下来的值，本身就是一句「请按那时那个地区的规则重新算一遍」的请求；规则被订正，计算结果就跟着被订正。这是特性。问题在于我们不知道订正什么时候会落下来，也收不到任何「已经订正过了」的通知。

5. 只存偏移量会丢掉什么

这里会冒出一个常见的反问：「那把偏移量一起存下来不就行了？」写成 2026-01-15T10:00:00+09:00 看上去毫无歧义。我数了数消失的是什么。

--- B-1. an offset does NOT identify a region ---
  offset +09:00 at that instant :  12 zone ids  e.g. Asia/Chita, Asia/Dili, Asia/Jayapura, Asia/Khandyga
  offset +05:30 at that instant :   3 zone ids  e.g. Asia/Calcutta, Asia/Colombo, Asia/Kolkata
  offset -05:00 at that instant :  47 zone ids  e.g. America/Atikokan, America/Bogota, America/Cancun, America/Cayman
  offset +01:00 at that instant :  53 zone ids  e.g. Africa/Algiers, Africa/Bangui, Africa/Brazzaville, Africa/Casablanca
  total distinct offsets in use at that instant : 38

在某一个瞬间，用 +09:00 的地区有 12 个，用 -05:00 的有 47 个，用 +01:00 的有 53 个。而那一刻全世界在用的不同偏移量只有 38 种。所以偏移量作为指向地区的信息实在太窄了。

但重点不是「有歧义」，而是重新计算变得不可能。偏移量是计算的结果，只存结果就等于把输入扔了。规则变动时，没有材料可以重新算。

  • 存偏移量确实保住了瞬间。还能算出它对应哪个 epoch。只需要这一点的用途，够用
  • 但问到「这个地区半年后的同一时刻是几点」就答不上来。既不知道是哪个地区，也不知道那时它归哪套规则管
  • 没有地区标识符、只有偏移量，就连规则订正的好处也享受不到。更新数据也不会改变这个值的解释。第 4 节看到的那件事，反过来想也可能是坏事
  • 让用户选了「我的地区」之后只把偏移量发给服务端的前端，正是在这一点上把信息扔掉了。必须把地区标识符一并发过去

6. 把同一个约定用三种方式存下来

现在把三种存储方式正面摆在一起。这需要一个规则确实变过的地区。在这个运行时的数据里逐年查 Europe/Istanbul，会发现2015 年与 2017 年之间存在不连续。

--- B-2. a rule change that is IN the data: Europe/Istanbul ---
  2014-01-15 10:00 local -> offset +02:00  abbr EET   dst 0:00:00 -> UTC 08:00Z
  2015-01-15 10:00 local -> offset +02:00  abbr EET   dst 0:00:00 -> UTC 08:00Z
  2015-07-15 10:00 local -> offset +03:00  abbr EEST  dst 1:00:00 -> UTC 07:00Z
  2016-07-15 10:00 local -> offset +03:00  abbr EEST  dst 1:00:00 -> UTC 07:00Z
  2017-01-15 10:00 local -> offset +03:00  abbr +03   dst 0:00:00 -> UTC 07:00Z
  2018-01-15 10:00 local -> offset +03:00  abbr +03   dst 0:00:00 -> UTC 07:00Z
  2026-01-15 10:00 local -> offset +03:00  abbr +03   dst 0:00:00 -> UTC 07:00Z

2015 年 1 月冬季偏移量是 +02:00，夏天升到 +03:00。从 2017 年 1 月起明明是 1 月却也是 +03:00，且 dst 为 0。也就是切换消失、全年固定了。缩写也从 EET 变成了 +03。

现在造出情形。假设 2014 年时约好「2017 年 1 月 15 日当地时间 10 点通话」并存了下来。那个时点已知的规则是冬季 +02:00。用三种方式存，会这样分岔。

这就是「请存成 UTC」这条建议不够用的地方。存 UTC 保住了瞬间，却丢掉了意图。人们约定的不是一个瞬间，而是「那个地区的早上 10 点」。规则一变，为了守住这个意图，瞬间本身就必须跟着变。把瞬间固定下来存，等于把它固定在了意图会被破坏的那一侧。

  • 「已经发生的事件」正好相反。那一刻的瞬间是确定的，所以存瞬间才对
  • 「将要发生的约定」本质是挂钟意图，所以必须存地区标识符和挂钟时间
  • 最稳妥的是表格最后一行。两者都存，一旦出现不一致就告警。这个不一致本身，就是你能得到的唯一一份「规则变了」的通知
  • 把这项检查自动化，就能事后也察觉到 tz 数据更新：每天把存下来的 UTC 和用地区标识符重算出的 UTC 做比对，挑出有差异的行

7. 未来并不确定，过去也不安全

大多数人的直觉是反的：「过去是确定的，只有未来不确定。」只对了一半。两个方向我都查了。

7.1 未来 — 数据不会替你区分确定与推测

先看看这个运行时声称自己对未来「已经知道」些什么。

--- B-4. past is settled, future is projected ---
  America/New_York transitions the data already asserts for 2027-2030:
      2027-03-14 -> -04:00
      2027-11-07 -> -05:00
      2028-03-12 -> -04:00
      2028-11-05 -> -05:00
      2029-03-11 -> -04:00
      2029-11-04 -> -05:00
      2030-03-10 -> -04:00
      2030-11-03 -> -05:00
  ...and for the year 2100:
      2100-03-14 -> -04:00
      2100-11-07 -> -05:00
  Asia/Seoul transitions 2027-2031 : none

连 2100 年的切换日期都给得出来。显然没有任何人决定过那些日期。那是把当前规则无限外推出来的推测。问题在于：输出里没有任何地方标注它是推测。2027 年的答案和 2100 年的答案在形式上完全一样。调用方的代码没有办法把两者区分开。

7.2 未来 — 这台机器的答案早就过期了

还有更具体的东西要查。这台机器的数据是 2025c，而 IANA 最新是 2026c。如果这中间的版本里有未来规则的变更，那这台机器现在应该还在安排一次已经被取消的钟表切换。tz 项目 NEWS 中 2026b、2026c 的条目记载了若干地区停止季节性切换、改为全年固定。我去问了这台机器。

--- F-3. does this runtime still schedule clock changes that were cancelled? ---
  America/Edmonton     2026-2027 : 2026-03-08 -> -06:00, 2026-11-01 -> -07:00, 2027-03-14 -> -06:00, 2027-11-07 -> -07:00
  America/Vancouver    2026-2027 : 2026-03-08 -> -07:00, 2026-11-01 -> -08:00, 2027-03-14 -> -07:00, 2027-11-07 -> -08:00
  Africa/Casablanca    2026-2027 : 2026-02-15 -> +00:00, 2026-03-22 -> +01:00, 2027-02-07 -> +00:00, 2027-03-14 -> +01:00
  Europe/Chisinau      2026-2027 : 2026-03-29 -> +03:00, 2026-10-25 -> +02:00, 2027-03-28 -> +03:00, 2027-10-31 -> +02:00

--- F-2. and the resulting local time this runtime reports ---
  zone                   date (12:00Z) offset     abbr
  --------------------------------------------------------
  Africa/Casablanca      2026-10-15   +01:00     +01
  America/Edmonton       2026-12-15   -07:00     MST
  America/Vancouver      2026-12-15   -08:00     PST

果然如此。这台机器的回答是：2026 年 11 月 1 日要把钟拨回去。可官方发布说明记载着那些地区并不会做这次切换。换句话说，今天在这台机器上算出来的「今年 12 月的当地时刻」已经是错的了。没有异常，没有告警，就是一个差了一小时的值。

  • 这就是把 tz 数据更新放进发布流水线的工程理由。不更新，未来的计算就会在悄无声息中一直算错
  • 陷阱在于出错的时点不是规则变更那天，而是被计算的那个日期。今天一切正常，到了 11 月预约照样挪一小时
  • 所以「现在跑得好好的」这种确认毫无意义。只有用未来日期去测才会暴露

7.3 过去 — 已确定，但可能被订正

过去这一面第 4 节已经证明了。归纳一下：过去的瞬间是确定的；用本地时间称呼这个瞬间的那个名字不是确定的。那个名字是写在数据里的记录，记录可能有错，错误会被订正。

tz 项目的发布说明专门设有 Changes to past timestamps 这一节，这件事本身就说明了问题。我读到的版本里，就有把几十年前的切换时刻订正为 00:00、以及改动某地区在某段时期所遵循规则的条目。

类别值（瞬间）本地时间显示为何会变怎么知道它变了
过去已确定可能改变历史记录被订正无从得知 — 只能去读发布说明
近期未来未确定可能改变规则变更被公布更新数据后重算再比对
远期未来未确定几乎必然改变当前规则的无限外推（推测）数据不会标注这是推测
无切换地区的未来未确定相对稳定固定偏移量可变动的余地小即便如此也有过变更先例

8. 缩写不是标识符

在界面上打出 KST 或 CST 对人是友好的。可一旦存下来或者拿去解析，就是另一回事了。我把某一个瞬间全部地区的缩写收集起来数了数。

--- B-5. abbreviations are not identifiers ---
  KST  :  3 zone ids, offsets ['+09:00']
           Asia/Pyongyang           +09:00
           Asia/Seoul               +09:00
           ROK                      +09:00
  CST  : 44 zone ids, offsets ['+08:00', '-05:00', '-06:00']
           America/Bahia_Banderas   -06:00
           America/Belize           -06:00
           America/Chicago          -06:00
           America/Chihuahua        -06:00
  IST  :  5 zone ids, offsets ['+02:00', '+05:30']
           Asia/Calcutta            +05:30
           Asia/Jerusalem           +02:00
           Asia/Kolkata             +05:30
           Asia/Tel_Aviv            +02:00
  EST  : 35 zone ids, offsets ['-05:00']

CST 有 44 个地区在用，而这些地区的偏移量有 +08:00、-05:00、-06:00 三种。IST 同时意味着 +02:00 和 +05:30。最大误差是 14 小时。那么把这些字符串喂给解析器会怎样？

--- C-1. parsing a string that carries an abbreviation (Python) ---
  2026-01-15 10:00 KST       -> ValueError: time data '2026-01-15 10:00 KST' does not match format '%Y-%m-%d %H:%M %Z'
  2026-01-15 10:00 CST       -> ValueError: time data '2026-01-15 10:00 CST' does not match format '%Y-%m-%d %H:%M %Z'
  2026-01-15 10:00 UTC       -> 2026-01-15T10:00:00        tzinfo=None
  2026-01-15 10:00 GMT       -> 2026-01-15T10:00:00        tzinfo=None
  2026-01-15 10:00 +0900     -> 2026-01-15T10:00:00+09:00  tzinfo=UTC+09:00

三种不同的失败方式出现在同一个屏幕上。

  • KST 和 CST 连解析本身都失败。这个解析器只接受一个非常狭窄的缩写集合。也就是说「把用户发来的字符串原样读回去」的往返根本不成立
  • UTC 和 GMT 能解析，但 tzinfo 是 None。缩写被读了然后扔掉。结果是一个 naive 值，直接拿去用就会被当作进程的本地时间来解释。因为没有异常，这一种最危险
  • 只有数字偏移量活了下来。而按第 5 节所说，活下来的这个并不是地区标识符

换一个运行时，失败的形态又不一样。

--- G-3. what Date parsing does with each written form (Node) ---
  local zone of this process : Asia/Seoul
  "2026-07-30"                     -> 2026-07-30T00:00:00.000Z  epoch 1785369600
  "2026-07-30T00:00:00"            -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026-07-30T00:00:00Z"           -> 2026-07-30T00:00:00.000Z  epoch 1785369600
  "2026-07-30T00:00:00+09:00"      -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026/07/30 00:00:00"            -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "July 30 2026 00:00:00"          -> 2026-07-29T15:00:00.000Z  epoch 1785337200
  "2026-07-30 00:00:00 KST"        -> Invalid Date
  "2026-07-30 00:00:00 CST"        -> 2026-07-30T06:00:00.000Z  epoch 1785391200

最后两行最精彩。KST 变成了 Invalid Date，而 CST 解析成功了。可结果是 06:00Z，也就是说这个解析器把 CST 读成了 -06:00。如果有人发来的是意为 +08:00 的那个 CST，一个差 14 小时的值就会被悄悄存进去。

  • 前两行也是陷阱。2026-07-30 被读成基准时的午夜，而 2026-07-30T00:00:00 被读成本地的午夜。仅仅是加不加时间部分，就差了 9 小时
  • 也就是说「只有日期的字符串」和「明写了午夜的字符串」是不同的瞬间。日期选择控件送出哪种格式，会让统计整体错一天
  • 斜杠格式和英文月份名格式都按本地解析。日志解析代码遇上这些格式，答案会随服务器所在地区而变
  • 结论很简单：机器读的值固定成一种明写偏移量的格式，地区标识符挪到单独的字段去

9. 夏令时边界上的两个洞

这个主题本身值得单独成篇，这里只讲和存储形式直接相关的部分。有切换的地区存在不存在的挂钟时刻和会来两次的挂钟时刻。

--- C-2. the two holes at a DST boundary (America/New_York, 2026) ---
  nonexistent local time 2026-03-08 02:30
    fold=0 -> offset -05:00 abbr EST  -> UTC 07:30Z -> back to zone 2026-03-08 03:30 EDT
    fold=1 -> offset -04:00 abbr EDT  -> UTC 06:30Z -> back to zone 2026-03-08 01:30 EST
    round trip preserved the wall clock : False

  ambiguous local time 2026-11-01 01:30
    fold=0 -> offset -04:00 abbr EDT  -> UTC 05:30Z -> epoch 1793511000
    fold=1 -> offset -05:00 abbr EST  -> UTC 06:30Z -> epoch 1793514600
    the two are equal by ==            : True
    seconds apart in real time         : 3600

两个洞的性质正好相反。

  • 不存在的时刻不会抛异常。它照收不误，往返一圈之后挂钟就变了（False）。放进去 02:30，回来的是 03:30 或者 01:30。也就是存进去再读出来，值本身变了
  • 来两次的时刻更狡猾。两个值用 == 比较是相等的，实际却相隔 3,600 秒。被判定为相同的两个值，是不同的瞬间
  • 要区分只能靠 fold 这类额外的一位。而这一位既进不了 ISO 字符串，也进不了大多数数据库列
  • 所以把有歧义的时刻只按挂钟 + 地区标识符存起来，信息是不够的。落在这个区间的值必须把瞬间（UTC）也一起存

这就是第 6 节表格最后一行（两者都存）之所以必要的第二个理由。未来的约定需要地区标识符，有歧义的边界需要一个确定的瞬间。

10. 24 小时之后和明天的同一时刻不是一回事

我用执行确认了「一天之后」这句话有两种含义。起点取切换前一天的正午。

--- C-3. 24 hours later vs the same clock time tomorrow ---
  start                          : 2026-03-07 12:00 -0500
  start + timedelta(hours=24)    : 2026-03-08 12:00 -0400
    real seconds elapsed         : 82800
  UTC + 24h, then converted back : 2026-03-08 13:00 -0400
    real seconds elapsed         : 86400
  the two answers differ by      : 12:00 vs 13:00

  the same pair over the autumn boundary
  start                          : 2026-10-31 12:00 -0400
  wall +24h                      : 2026-11-01 12:00 -0500  real seconds 90000
  instant +24h                   : 2026-11-01 11:00 -0500  real seconds 86400

  and where a zone with a 30 minute shift lands (Australia/Lord_Howe)
    start        : 2026-10-03 12:00 +1030
    wall +24h    : 2026-10-04 12:00 +1100  real seconds 84600
    instant +24h : 2026-10-04 12:30 +1100  real seconds 86400
计算方式春季边界秋季边界30 分钟切换地区意味着什么
给挂钟加 24 小时82,800 秒90,000 秒84,600 秒「明天同一时刻」 — 实际经过在晃
给瞬间加 24 小时86,400 秒86,400 秒86,400 秒「正好 24 小时后」 — 挂钟在晃
显示时刻的差别12:00 对 13:0012:00 对 11:0012:00 对 12:30用户看得见的误差
哪个才对由需求决定 — 不能由代码决定有时两个都对
  • 「每天上午 9 点提醒」该用挂钟那一侧，代价是接受每天实际经过的时长不一样
  • 「支付后 24 小时内可取消」该用瞬间那一侧。地区规则不该把用户的权利变多或变少
  • 危险在于这个选择往往是隐式做出的。上面输出里挂钟那一路，不过是给一个 aware 值直接加了个 timedelta。没有任何警告
  • 在 30 分钟切换的地区，误差是 30 分钟，会顺利通过只检查「差一小时」的测试
  • 「按工作日算 3 天」这类计算，连日期边界本身都取决于地区，所以必须把地区标识符作为输入接进来

11. 排序和比较只有在 UTC 上才成立

把多个地区的记录汇总到一个页面就会出排序问题。我把按本地时间文本排的顺序和按瞬间排的顺序并排打了出来。

--- C-4. sorting local-time text vs sorting instants ---
  as written
  id        local text            zone                  fold  offset UTC
  order-A   2026-11-01 01:30:00   America/New_York      0     -04:00 2026-11-01 05:30:00Z
  order-B   2026-11-01 01:30:00   America/New_York      1     -05:00 2026-11-01 06:30:00Z
  order-C   2026-11-01 09:00:00   Asia/Seoul            0     +09:00 2026-11-01 00:00:00Z
  order-D   2026-10-31 22:00:00   Europe/London         0     +00:00 2026-10-31 22:00:00Z
  order-E   2026-11-01 14:30:00   Australia/Lord_Howe   0     +11:00 2026-11-01 03:30:00Z

  sorted by the local text  : ['order-D', 'order-A', 'order-B', 'order-C', 'order-E']
  sorted by the real instant: ['order-D', 'order-C', 'order-E', 'order-A', 'order-B']
  the two orders agree      : False

两个顺序完全不同。按本地时间文本排，order-A 排第二；按真实顺序，它是第四。

  • 本地时间字符串不是同一根轴上的值。拿它们比大小，等于拿不同尺子量出来的长度只比数字
  • order-A 和 order-B 的字符串完全一样。只有本地时间文本时，任何排序都决定不了这两者的先后
  • 就算只在同一个地区内，只要跨过切换时刻，文本排序照样崩。「我们只用一个地区」不是安全的辩护
  • 所以排序、比较、范围查询统统要放在瞬间（UTC）列上。本地时间只在往页面上画的时候才算
  • 如果你为了展示把本地时间存成一列还建了索引，那个索引不能用于排序

12. 规则在序列化和数据库边界上蒸发

就算你好好地拿着地区标识符，值一旦离开进程往往就没了。我把往返过程打了出来。

--- F-5. serialization round trips ---
  original object      : datetime.datetime(2027, 6, 15, 14, 30, tzinfo=zoneinfo.ZoneInfo(key='Asia/Seoul'))
  original tzinfo type : ZoneInfo -> Asia/Seoul
  isoformat()          : 2027-06-15T14:30:00+09:00
  fromisoformat()      : datetime.datetime(2027, 6, 15, 14, 30, tzinfo=datetime.timezone(datetime.timedelta(seconds=32400)))
  tzinfo type after    : timezone -> UTC+09:00
  same instant         : True
  region id survived   : False

  the same pair for a zone that does have transitions:
    stored           : 2027-01-15T14:30:00-05:00
    region form + 6 months : 2027-07-15 14:30 -0400
    offset form + 6 months : 2027-07-15 14:30 -0500
    those are different instants, one hour apart

导出成 ISO 字符串再读回来，瞬间保住了（True），地区标识符没了（False）。类型从 ZoneInfo 变成了固定偏移量。表面上是同一个值，所以这个损失看不见。

可是一旦拿这个值去做下一步计算就会暴露。在有切换的地区往后推半年，带地区标识符的那一路给出 -04:00，带偏移量的那一路给出 -05:00，相差一小时的两个瞬间。仅仅是存了再取，规则就被冻住了。

--- G-4. JSON round trip (Node) ---
  JSON.stringify        : {"label":"meeting","when":"2027-06-15T05:30:00.000Z"}
  the zone the user chose is nowhere in that payload
  same instant revived  : true
  toString() (local)    : Tue Jun 15 2027 14:30:00 GMT+0900
  toISOString()         : 2027-06-15T05:30:00.000Z
  in Asia/Seoul         : 2027-06-15, 14:30:00 GMT+09:00
  in America/New_York   : 2027-06-15, 01:30:00 GMT-04:00

--- F-6. an SQL boundary: with and without zone information ---
  meeting  text=2027-06-15T14:30:00+09:00        epoch=1813037400 zone='Asia/Seoul'
           read back -> 2027-06-15T14:30:00+09:00        tzinfo=UTC+09:00
           with the zone column, recomputable -> 2027-06-15 14:30 +0900
  naive    text=2027-06-15T14:30:00              epoch=1813037400 zone=''
           read back -> 2027-06-15T14:30:00              tzinfo=None
           without a zone column, the reader must guess
  • JSON 序列化连偏移量都不留。永远以基准时的形式输出，用户选的地区在整个 payload 里找不到
  • 同一个对象用 toString() 打出来，看到的是进程所在的本地地区。这是日志和 API 响应说着不同时刻的常见原因
  • 在数据库里，分水岭是有没有一个单独的列装地区标识符。能装偏移量的类型也装不下规则，它装的只是结果值
  • 没有地区的 naive 值读回来是 tzinfo=None。它属于哪个地区，只留在表结构之外的约定里 — 也就是哪儿都没有
  • 所以未来约定的表应该同时有瞬间列和地区标识符列。只有一个是不够的

13. 依赖环境变量会悄悄出错

不在代码里写死地区、而是交给进程环境的做法很普遍。我在这个平台上给两个运行时设了 TZ 并看了结果。

--- H-1. TZ env var, seen by Node ---
  America/New_York     -> resolved America/New_York   | new Date(2026,6,30,12,0) = 2026-07-30T16:00:00.000Z
  Asia/Seoul           -> resolved Asia/Seoul         | new Date(2026,6,30,12,0) = 2026-07-30T03:00:00.000Z
  Europe/London        -> resolved Europe/London      | new Date(2026,6,30,12,0) = 2026-07-30T11:00:00.000Z
  UTC                  -> resolved UTC                | new Date(2026,6,30,12,0) = 2026-07-30T12:00:00.000Z
  EST5EDT              -> resolved America/New_York   | new Date(2026,6,30,12,0) = 2026-07-30T16:00:00.000Z

--- H-3. does TZ reach Python zoneinfo on this platform? ---
  TZ=<unset>            local astimezone() -> +0900  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=America/New_York   local astimezone() -> +0100  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=Europe/London      local astimezone() -> +0100  | ZoneInfo('America/New_York') -> -0400  | tzset available: False
  TZ=UTC                local astimezone() -> +0000  | ZoneInfo('America/New_York') -> -0400  | tzset available: False

两个运行时的反应完全不同。

  • 在 Node 里 TZ 正常工作。给它一个地区标识符，同样的挂钟参数就变成了不同的瞬间。EST5EDT 这个旧名被解析成了规范标识符并给出了答案
  • Python 这边不一样。这个平台上没有 time.tzset（False）。可 TZ 又确实影响了本地地区的判定，而且结果是错的。设成 America/New_York 时得到的是 +0100。7 月那个地区是 -0400
  • 更糟的是设成 Europe/London 时也得到一模一样的 +0100。看上去像是碰巧对了，但既然是同一个值，就说明它根本没有被当作地区标识符解析
  • 反过来，ZoneInfo('America/New_York') 在所有情况下都是 -0400。显式指定的地区不受环境摆布

结论只有一条：把地区作为值的一部分明写出来。从进程环境里读的做法，在某些平台上会悄悄给出错误答案。尤其是在容器和本地开发机环境本就应该不同的今天，环境变量并不是一个可复现的输入。

14. 应对流程 — 什么该以什么形式存

把到此为止的执行结果整理成决策规则。出发点不是「请存成 UTC」，而是「这个值的性质是什么」。

14.1 按值的性质决定存储形式的判断表

值的性质本质是什么存储形式规则变动时能否重算
已发生的事件（日志、支付、审计）瞬间一个瞬间（UTC）瞬间不变，显示可能改变显示可重算
未来的约定（会议、预约）挂钟意图挂钟 + 地区标识符，瞬间作缓存瞬间必须变，意图才守得住能 — 每次重新计算
重复日程（每天 09:00）规则 + 挂钟挂钟 + 地区标识符 + 重复规则下一次发生时刻会变能 — 存瞬间则不能
工作日与截止地区的日期边界地区标识符 + 日期（+节假日日历）日期边界可能移动能
生日与纪念日日历上的日期只存日期（无时刻、无地区）不受影响不适用
落在边界上的值（歧义、不存在的时刻）瞬间是两者之一瞬间 + 挂钟 + 地区标识符，三者都要瞬间已确定，安全能

14.2 为什么 tz 数据更新要进发布流水线

7.2 节就是全部理由。不更新，未来的计算就会一直悄悄算错。今天的结果正常，等被计算的那个日期到了照样出错。而且这种错误不抛异常，监控根本看不见。

  • 把 tz 数据当作应用依赖来管理。把哪个运行时从哪里取数据写进文档 — 这台机器上一边是内置 ICU，另一边是软件包
  • 有多个运行时就把版本对齐。如第 4 节所见，版本不同就会悄悄给出不同答案
  • 把版本打进启动日志。出事之后，这是唯一能知道「当时是哪个版本」的办法
  • 把更新排进例行工作，但要把更新本身当成一次发布。它是可能改变历史数据解释的变更
  • 操作系统的软件包更新未必会改动应用实际用的数据。使用内置数据的运行时，更新系统也不会变

14.3 更新后如何做回归确认

更新了就必须数清楚变了什么。第 4 节用的方法本身就是流程。

  • 更新前先拍快照。把服务用到的所有地区标识符 × 关心时段的偏移量存成一张表。上面那个实验用 418 个地区 × 564 个时点造出 23 万行，几秒钟就跑完了
  • 更新后再拍同一张表，只看差异。出现 33 行这样的小数字是正常的。0 行说明更新没生效，那本身也是个信号
  • 把差异和发布说明对上。出现说明里没有的变化，问题就不在数据，而在代码或配置
  • 把存下来的未来约定全量重算再比对。拿存下来的瞬间和用地区标识符重算的瞬间比，挑出有差异的行。如果你用的是第 6 节表格最后一行，这就是你的告警
  • 校验地区标识符的有效性。看看用户数据里的地区字符串在更新后是否仍然全部可解析。第 4 节里两个运行时之间就差了 180 个
  • 把过去和未来的日期都放进测试。只用当前时刻的测试，原理上就抓不到这类回归
  • 用固定值测试切换边界。把不存在的时刻和会来两次的时刻各钉成一个用例

14.4 评审时该问的问题

  • 这个值是已发生的事件，还是往后的约定？ — 答案不同，存储形式就不同
  • 地区标识符存在哪里？ — 「在偏移量里」是错误答案
  • 以后还会不会拿这个值重新计算？ — 会的话，规则引用就必须留着
  • 排序和比较跑在哪一列上？ — 如果是本地时间列，改掉
  • 「一天之后」指的是挂钟还是经过时间？ — 需求文档里写了吗
  • 有多个运行时的话，tz 数据版本一致吗？ — 能从启动日志确认吗
  • 是否把缩写显示给用户又原样收回来？ — 是的话，改掉
  • 这是一个历史记录的显示绝对不能变的页面吗？ — 是的话，把渲染好的字符串也一并留存

一句话。时刻是值，时区是规则。只存值，规则一变就无法重算；只存规则引用，规则一变答案就会变。哪一边正确，取决于这个值是「已经发生的事」还是「说好要做的事」。而一个从来没做过这个判断的系统，总有一天会在升级了某个依赖之后，眼看着旧记录上的时刻变了样。

# 时区是会被修订的数据 — 存储形式判断表与更新后检查清单

> 出处: braindetox.kr — 时区是数据而非代码
> 依据: Windows 10 / Node v22.16.0 (ICU 77.1, tz 2025b) / Python 3.13.3 (tzdata 2025.3 = IANA 2025c) 实际运行验证
> 把这份文件原样贴给 AI，写上「按这套标准检查我们的表结构和发布流水线」即可。
> ⚠ 观测事实: 同一台机器上的两个运行时，在 235,752 对中有 33 对给出了不同的过去偏移量。没有任何一个存储值发生过改变。

## 0. 大前提 — 时刻是值，时区是规则

| 概念 | 是什么 | 谁来改 |
|---|---|---|
| **瞬间（instant）** | epoch 值。宇宙中只发生过一次的点 | **谁都改不了** |
| **本地时间** | 某地区给这个瞬间起的名字 | 计算结果 |
| **偏移量** | 那一刻该地区离基准时的距离 | 计算结果 |
| **时区** | 把瞬间换算成本地时间的**整套规则历史** | 政府改动，IANA 发布 |

**会丢掉规则的存储方式（只存偏移量）无法回答关于未来的问题。**

## 1. 按值的性质决定存储形式的判断表 — 这张表是核心

| 值的性质 | 本质 | 存储形式 | 规则变动时 | 能否重算 |
|---|---|---|---|---|
| **已发生的事件**（日志、支付、审计） | 瞬间 | **一个瞬间（UTC）** | 瞬间不变，显示可能改变 | 显示可重算 |
| **未来的约定**（会议、预约） | 挂钟意图 | **挂钟 + 地区标识符**，瞬间作缓存 | 瞬间必须变，意图才守得住 | **能** |
| **重复日程**（每天 09:00） | 规则 + 挂钟 | **挂钟 + 地区标识符 + 重复规则** | 下一次发生时刻会变 | **能**（存瞬间则不能） |
| **工作日与截止** | 地区的日期边界 | **地区标识符 + 日期**（+节假日日历） | 日期边界可能移动 | 能 |
| **生日与纪念日** | 日历上的日期 | **只存日期**（无时刻、无地区） | 不受影响 | 不适用 |
| **落在边界上的值**（歧义、不存在的时刻） | 瞬间是两者之一 | **瞬间 + 挂钟 + 地区标识符，三者都要** | 瞬间已确定，安全 | 能 |
| 只有偏移量（`+09:00`） | 计算结果 | **避免** — 只作辅助信息 | 什么也不会发生 | **不能** |
| 缩写（`KST`、`CST`） | 给人看的标签 | **不要存** | 不适用 | **不能** |

### 判定规则三行说清

- 是**已经发生**的事吗 → 存瞬间
- 是**说好要做**的事吗 → 存挂钟 + 地区标识符
- 两者都要？ → **两者都存，重算结果对不上就告警**

## 2. 检查 tz 数据版本的命令

```bash
# Node — 由内置 ICU 携带数据
node -p "process.versions.tz + ' / icu ' + process.versions.icu"
# 实测: 2025b / icu 77.1

# Python — 没有系统数据库时，由 PyPI 的 tzdata 包提供
python -c "import tzdata;print(tzdata.IANA_VERSION)"
python -c "import importlib.metadata as m;print(m.version('tzdata'))"
python -c "import zoneinfo;print('TZPATH:', zoneinfo.TZPATH)"
# 实测: 2025c / 2025.3 / TZPATH: ()   （空元组 = 没有系统数据库）

# 各运行时认识多少地区标识符 — 看两者之间的差
node -p "Intl.supportedValuesOf('timeZone').length"
python -c "import zoneinfo;print(len(zoneinfo.available_timezones()))"
# 实测: 418 vs 598  （180 个只有 Python 认识的兼容链接）
```

- **有多个运行时就把版本对齐。** 版本不同就会悄悄给出不同答案
- **把版本打进启动日志。** 出事后这是唯一能知道「当时是哪个版本」的办法
- 操作系统的软件包更新**未必会改动使用内置数据的运行时**

## 3. 更新后的回归检查清单

- [ ] **更新前拍了快照** — 服务用到的全部地区标识符 × 关心时段的偏移量表
- [ ] **更新后再拍同一张表**，**只看差异**（实测: 418 地区 × 564 时点 = 23 万行，几秒钟）
- [ ] 差异**不是 0 行** — 0 行说明更新没生效
- [ ] 把差异**和发布说明对上** — 说明里没有的变化，问题在代码或配置
- [ ] **把存下来的未来约定全量重算**，与存下来的瞬间做比对
- [ ] 确认用户数据里的**地区标识符在更新后仍然全部可解析**
- [ ] 测试里放了**过去日期和未来日期**（只用当前时刻的测试抓不到）
- [ ] **用固定值测试了切换边界** — 不存在的时刻、会来两次的时刻
- [ ] 确认表结构扛得住**带秒的偏移量**（例如 `+08:27:52`）
- [ ] 确认在 **30 分钟和 45 分钟的偏移量**上不会崩（`+05:30`、`+05:45`、`+08:45`、`+10:30`）
- [ ] 定义了 `+14:00` 地区导致**日报表横跨两个日期**时该怎么算
- [ ] 把更新**当作一次发布来对待** — 它可能改变历史数据的解释

## 6. 不要做的事

- ❌ **只存偏移量** — 瞬间还在，但重算的材料没了
- ❌ **把缩写存下来或拿去解析** — 一个 `CST` 就对应三种偏移量
- ❌ **把未来的约定一次性折算成 UTC 存** — 规则一变就被固定在意图被破坏的那一侧
- ❌ **在本地时间列上排序、比较** — 那是拿不同尺子量出来的值只比数字
- ❌ **把地区交给进程环境变量（`TZ`）** — 在某些平台上会悄悄出错（实测：某个运行时上 `America/New_York` 得到的是 `+0100`）
- ❌ **只用当前时刻做测试** — 原理上就抓不到这类回归
- ❌ **发布时跳过 tz 数据更新** — 未来的计算会在悄无声息中一直算错
- ❌ **在表结构里把偏移量当整小时的整数** — 45 分钟和带秒的偏移量是真实存在的
