GitHub 堆叠 PR 公开预览 - 把大改动堆成层来拆分会带来什么变化

堆出层来很容易，底层一变要把上层重新对齐才难

2026-08-01 开发/基础设施

开篇：评审卡在一个 40 个文件的 PR 前面

一个 PR 里塞了 40 个文件。表结构变更、用到这个表结构的查询层、调用这个层的 API 端点，还有顺手整理的配置文件，全都揉成一团。评审者打开又关上了。到第三天还是没有批准。催一下，回一句「明天看」。这期间作者已经开始把下一项工作叠在这个分支上。到这一步，问题不是评审者不够勤勉，而是工作以一种无法评审的形态送到了他面前。

2026 年 7 月 30 日，GitHub 把堆叠 PR 开放为公开预览，用来把大改动堆成层、让每一层单独接受评审。不过这篇文章关心的不是「出了个新功能」。把分支一个接一个串起来本来用本地 git 就能做，下面我会亲手搭一个给你看。被发布的不是概念，而是维持这个概念所需要的那份反复劳动，如今由平台代劳。

所以这篇文章只抛出一个问题。拆分大改动的成本，工具到底能替你省下多少? 堆叠真正的难处不在于造出层来，而在于底层每变一次，就要把上面全部重新对齐。我把这份工作用本地 git 原样跑了一遍，用输出告诉你哪里疼、哪些被自动化了。

运行环境。下面所有 git 输出都是在 Windows 10 Pro (10.0.19045) 上实际执行的结果。git 2.48.1.windows.1，shell 是 GNU bash 5.2.37 (MSYS2/MinGW64)。命令不是通过 heredoc 传的，而是写进文件再执行，示例仓库是在临时目录里新建的。分支名和文件名全部是虚构的示例。

这篇文章不涉及的内容。怎么开 PR、评审的基本功在Pull Request 与代码评审里。「给未合并 PR 的数量设上限能不能缩短等待」这个队列动力学问题，我在PR 上限与队列动力学里用模拟处理过。本文只看怎么拆一件事的体量。分支策略本身在分支策略里。

1. 到底发布了什么 - 只写我核实过的事实

下面只写我直接打开官方更新日志和文档核实到的内容。没有靠摘要文章或社区帖子去断定功能。

  • 发布日期与状态。GitHub 更新日志 2026 年 7 月 30 日的条目宣布了堆叠 PR 的公开预览。文中说面向全部仓库的推出会「用几天时间」进行
  • 定义。更新日志的原话是「把大改动拆成小而可评审的多个 PR」，并说明它是「一个有序序列，其中每个 PR 承担改动的一个聚焦的层」
  • 结构规则。文档写明最底部的 PR 指向默认分支，其上每个 PR 指向紧邻的下一层分支。并提出了这样一条原则：如果一层的代码依赖另一层的代码，被依赖的对象必须在同一分支或更下面的分支里
  • 可操作的地方。github.com、GitHub CLI 和移动端应用。CLI 扩展用 gh extension install github/gh-stack 安装，文档中出现的子命令有 gh stack init、gh stack add、gh stack submit、gh stack rebase、gh stack push
  • 在网页上创建的办法。文档里也写了另一种方式：把每个 PR 的基准分支指定为下一层 PR 的分支，然后选择创建堆叠的选项
  • 约束。所有分支必须在同一个仓库里，跨派生仓库的堆叠不受支持。GitHub Desktop 里不受支持。不支持自动合并。堆叠的各分支之间需要完全线性的历史
  • 合并队列。文档说堆叠完全支持合并队列，并会按正确顺序进入队列；为了让一个堆叠不被拆开，合并组被允许超出所配置最大规模最多 50%。即便这个余量也装不下时，就会拆到连续的多个合并组里。不过更新日志说合并队列支持要「用几周时间」陆续到位，所以这一块各仓库到达的时间可能不同

预览时点的明示。文档里原样写着「本功能处于公开预览，可能会变化」。本文是按 2026 年 8 月 1 日核实的内容。界面构成、子命令名称、约束清单都可能在正式发布前变动，所以在做引入决定之前，务必回去重新核对原文。

没打开的东西。搜索结果里出现的社区讨论帖、路线图议题、gh-stack 仓库页面、快速上手文档、面向组织的推广教程我都没有打开。因此只存在于那些文档里的内容，本文一律没有。下面的「参考资料」只列出我实际打开并读过的五处。

2. 大 PR 为什么会出问题 - 讲结构，不编数字

「大 PR 没人评审」这话到处都听得到，但要用统计去解释理由，多半就变成搬别人的数字。这里我一个数字都不用，只看结构。评审是三件事：读、把上下文记在脑子里、下判断。当 PR 变大时，这三件事并不以同样的速度变大。

  • 要读的量是线性增长的。文件多一倍，读的时间大体也多一倍。到这一步还扛得住
  • 要维持的上下文涨得更快。看第 40 个文件时，评审者得记着前面 39 个改了什么。想确认「这个函数签名是不是真的改了」，就得往上翻回去找，而这种来回次数随文件数增长
  • 判断的单位反而变大了。评审批准只能按 PR 来。40 个里 39 个完美、1 个可疑，全部都要等着。好的部分被坏的部分扣作了人质
  • 一有修改就要全部重看。作者按意见改完推上来，评审者又得去找「哪里变了」。PR 越大，这份重新确认的成本越高，所以第二轮评审总是更松
  • 回滚的单位等于评审的单位。上线后出问题，能回滚的最小单位就是整个 PR。API 端点会跟着表结构变更一起消失
  • CI 是全有或全无的。40 个文件里某一处的 lint 错误就能把整条流水线变红。另外 39 个通过了这件事一点分量都没有

归纳起来，大 PR 的问题是评审的最小单位和改动的最小单位被强行绑成了同一个。堆叠就是想把这两者拆开：改动照旧做大，但评审、批准和回滚都按层来。

有一点要说清楚。拆分并不会提高评审容量。一个团队一周能消化多少改动，是评审者的时间决定的，不是切 PR 的方式决定的。上限规则为什么减不了等待，我在上一篇里当作队列问题处理过，这里守的是同一条线。堆叠改变的不是总量，而是单件时间和部分通过的可能性。

3. 堆叠是什么 - 用本地 git 亲手搭一个

定义只有一句。把分支的基准取成紧邻的下一层分支，而不是主干。这样每个分支的差异视图里就会去掉下面已经做过的部分，只留下这一层新做的东西。不需要任何特殊工具。

$ git switch -c stack/1-db   main          # 第1层: 数据库连接池配置
$ git switch -c stack/2-repo stack/1-db    # 第2层: 查询层 (建在第1层之上)
$ git switch -c stack/3-api  stack/2-repo  # 第3层: API 端点 (建在第2层之上)

把这样搭出来的仓库翻开看，是这个样子。

git version 2.48.1.windows.1 / MINGW64_NT-10.0-19045

=== 1-2. the stack as one line of history ===
* 3f0f26a (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 50bdde2 (stack/2-repo)          feat(repo): order lookup, raise pool size
* cb5f977 (stack/1-db)            feat(db): add connection pool config

=== 1-3. what each branch points at ===
main          78b0629  chore: bootstrap trunk
stack/1-db    cb5f977  feat(db): add connection pool config
stack/2-repo  50bdde2  feat(repo): order lookup, raise pool size
stack/3-api   3f0f26a  feat(api): GET /orders/:id

三个分支指着同一条线上的三个不同位置。这就是堆叠的全部。不是岔开的枝杈，而是一条线上打的刻度。现在看各层的评审单元。

=== 1-4. the REVIEW UNIT of each layer (diff vs the layer below) ===
--- base=main          head=stack/1-db
 db.yml | 3 +++
 1 file changed, 3 insertions(+)
--- base=stack/1-db    head=stack/2-repo
 db.yml  | 2 +-
 repo.py | 2 ++
 2 files changed, 3 insertions(+), 1 deletion(-)
--- base=stack/2-repo  head=stack/3-api
 api.py | 2 ++
 1 file changed, 2 insertions(+)

=== 1-5. what ONE big PR would have looked like (main..top) ===
 api.py  | 2 ++
 db.yml  | 3 +++
 repo.py | 2 ++
 3 files changed, 7 insertions(+)

是同一份工作。合起来看是 3 个文件新增 7 行，按层看则分成1 个、2 个、1 个文件。示例规模小，但比例会照样放大。把 40 个文件的改动分成 12 个、20 个、8 个，三个人就能并行看，而且第 1 层今天就可能被批准。

3.1 该在哪里切层 - 只有这件事工具做不了

把文档里那条依赖原则再读一遍，切的标准就出来了。一层所依赖的对象，必须在同一层或更下面。按这个条件去切，是堆叠里唯一需要创造的部分，没有工具能代劳。

  • 沿技术方向切。仓储层 → 服务层 → 控制器，让调用方向从下往上。上面认识下面，下面不知道上面
  • 把「准备」和「正事」分开。重命名、挪文件、格式整理这类不改变行为的改动抽到最底层。这一层读起来轻松，批得也快
  • 功能开关放在最上面。把打开开关的提交放到最后一层，下面各层就能以无害状态先发布
  • 互相引用的两块不要切开。A 调 B、B 也调 A，就定不出顺序。这种放在同一层
  • 测试挂在它所属的那一层。把测试都堆到最后一层，下面各层的 CI 就失去意义了
  • 层数要少。层越多，底层一晃动要重新对齐的对象就越多。下一节就展示这份成本

4. 底层一变，上层就晃 - 变基、冲突，以及撤销

这里才是堆叠的实际成本。假设评审者在第 1 层留了一条意见：连接池太小。作者就在第 1 层再加一个提交。看看那一刻发生了什么。

=== 2-1. reviewer asks the bottom layer to change: pool size 5 -> 10 ===
stack/1-db moved: cb5f977 -> 63509a2

=== 2-2. the layers above are now stale ===
* 63509a2 (HEAD -> stack/1-db)  fix(db): pool size 5 -> 10 per review
| * 3f0f26a (stack/3-api)        feat(api): GET /orders/:id
| * 50bdde2 (stack/2-repo)       feat(repo): order lookup, raise pool size
|/
* cb5f977                        feat(db): add connection pool config

原本一条线的历史分叉了。第 2 层和第 3 层仍然挂在旧的第 1 层上。就这么放着的话，第 2 层的 PR 视图里不会反映下面刚改的内容，CI 也按过时的基准在跑。上面这些层必须搬到新的第 1 层之上。

4.1 搬紧邻上层时冲突出现的位置

$ git switch stack/2-repo
$ git rebase stack/1-db
Auto-merging db.yml
CONFLICT (content): Merge conflict in db.yml
error: could not apply 50bdde2... feat(repo): order lookup, raise pool size
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
rebase exit code: 1

--- status while stopped ---
UU db.yml
A  repo.py

--- the conflicted file ---
pool:
<<<<<<< HEAD
  size: 10
=======
  size: 20
>>>>>>> 50bdde2 (feat(repo): order lookup, raise pool size)
  timeout: 30

冲突了。关键在于为什么会冲突。第 1 层把那一行从 5 改成了 10，而第 2 层原本就是把同一行从 5 改成 20 的提交。变基要把第 2 层的提交重新应用到新的第 1 层之上，可作为锚点的那一行已经变了，于是无法自动裁定。

  • 冲突只在各层碰到同一文件的同一行时才发生。层按技术方向切得干净，绝大多数变基会安静地跑完
  • 冲突标记里 HEAD 一侧是新基准，也就是下层，另一侧是正在重放的提交，也就是上层。这跟平时合并的上下感觉是反的，所以经常有人搞错
  • 停下期间仓库处于中间状态。可以通过 .git/rebase-merge 目录是否存在来确认
  • 三层的话这件事最多发生两次。层数就是重复次数

4.2 撤销的办法 - 三个逃生口

面对冲突不必慌，因为撤销是被完全保证的。我实际撤了一遍。

=== 2-4. escape hatch: abort puts everything back ===
$ git rebase --abort
after abort, stack/2-repo = 50bdde2
db.yml on stack/2-repo:
pool:
  size: 20
  timeout: 30

=== 2-9. undoing a FINISHED rebase (reflog) ===
a4f0a88 stack/3-api@{0}: rebase (finish): refs/heads/stack/3-api onto 8e137ce
3f0f26a stack/3-api@{1}: commit: feat(api): GET /orders/:id
50bdde2 stack/3-api@{2}: branch: Created from stack/2-repo

$ git reset --hard stack/3-api@{1}    # 精确回到变基之前的状态

把三种情况分清楚就够了。

  • 还在进行中就用 git rebase --abort。分支会精确回到起点。上面的输出里回到了 50bdde2，文件内容也和原来一样
  • 已经跑完了就用 git reflog。变基前的位置留在 @{1} 上，用 git reset --hard 回到那个点
  • ORIG_HEAD 也是同样的用途。它指向变基前的位置，所以 git reset --hard ORIG_HEAD 是更短的写法。但别的命令会覆盖它，所以 reflog 更保险
  • 一个重要前提。这种撤销只在本地是无害的。如果已经强制推送到远端，别人拉走的历史就对不上了。堆叠分支需要一条约定：只由作者本人推送

4.3 再往上那层必须自己指定起点

搬完第 2 层，第 3 层就成了问题。第 3 层指向的是旧的第 2 层，简单变基会把不相干的提交也拖过来。

=== 2-6. layer 3 still points at the OLD layer 2 ===
layer3 does NOT contain the new layer2 -> must rebase too

=== 2-7. rebase layer 3 with --onto (old base -> new base) ===
$ git rebase --onto stack/2-repo 50bdde2 stack/3-api
Successfully rebased and updated refs/heads/stack/3-api.

=== 2-8. the stack is one line again ===
* a4f0a88 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 8e137ce (stack/2-repo)          feat(repo): order lookup, raise pool size
* 63509a2 (stack/1-db)            fix(db): pool size 5 -> 10 per review
* cb5f977                         feat(db): add connection pool config

git rebase --onto 新基准 旧基准 目标 的三个参数分别是搬到哪、从哪开始、搬什么。请注意旧的第 2 层的提交哈希得手工敲进去。五层的话这种手工活要做四次，哈希写错一个，提交就会消失或者重复。这里正是人会出错的地方，也正是工具瞄准的地方。

5. 一条命令搬动整个堆叠 - update-refs

git 自己也有减少这种重复的机制。git rebase -h 把 --update-refs 描述为「更新那些指向正在被变基的提交的分支」。我把有和没有这个选项的同一情形跑了一遍作对比。情形是主干往前走了，也就是别人的 PR 先合进去了这种再常见不过的状况。

=== 3-1. WITHOUT --update-refs ===
before:  main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6d241f4
$ git switch stack/3-api
$ git rebase main
after:   main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6204587

* 6204587 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 483c62e                        feat(repo): order lookup
* b422809                        feat(db): add connection pool config
* 5ea68a0 (main)                 chore: bump trunk
| * a08d522 (stack/2-repo)       feat(repo): order lookup
| * 9b331dc (stack/1-db)         feat(db): add connection pool config
|/
* c2562b8                        chore: bootstrap trunk

这就是堆叠悄悄散架的样子。第 3 层顺利搬到了新主干上，第 1 层和第 2 层的分支却原地留在了旧主干。这种状态下推上去，第 1 层和第 2 层的 PR 评审的是旧代码，而第 3 层 PR 的差异视图里，下面各层已经做过的东西会再次出现。分层的意义就没了。

=== 3-2. WITH --update-refs, same situation ===
before:  main ebfef49   1-db 7862785   2-repo d8b3ddc   3-api 79b45bc
$ git rebase --update-refs main
Rebasing (1/5)(2/5)(3/5)(4/5)(5/5)
Successfully rebased and updated refs/heads/stack/3-api.
Updated the following refs with --update-refs:
    refs/heads/stack/1-db
    refs/heads/stack/2-repo
after:   main ebfef49   1-db 469e32a   2-repo cd35dca   3-api a807932

* a807932 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* cd35dca (stack/2-repo)          feat(repo): order lookup
* 469e32a (stack/1-db)            feat(db): add connection pool config
* ebfef49 (main)                  chore: bump trunk
* 153d615                         chore: bootstrap trunk

=== 3-3. make it the default for this repo ===
$ git config rebase.updateRefs true
plain 'git rebase main' now moves every layer   exit code: 0

一条线保住了，中间层的分支也跟着一起动了。git 会直接告诉你它更新了哪些引用。把 rebase.updateRefs 设为真，普通的 git rebase main 也会有同样的行为。

这一节是全文的核心。堆叠的概念在第 3 节就已经讲完了，三行命令就能搭出来。可是第 4 节里那份手工活 —— 找出旧哈希再喂给 --onto —— 要按层数重复。工具的价值不在于提供概念，而在于消灭这份重复。--update-refs 在本地干这件事，平台功能则在此之上补齐评审界面、审批规则和合并顺序的串联。所以即便有了工具，在哪里切这个判断，依然是人的活。

5.1 按情形对应的更新命令与撤销方式

情形用的命令注意点撤销
只搬紧邻的上一层git rebase 下层碰过同一行就会冲突git rebase --abort

6. 合并顺序 - 为什么必须从底层开始

文档写着「堆叠 PR 从最靠近主干的底部往上合并」，并明示「不能单独合并中间的 PR，因为它下面的那些总会跟着一起合并」。只读规则会以为是政策，可在本地跑一遍就会发现，这是从历史的性质里长出来的物理约束。

=== 4-2. merge the MIDDLE first: what actually lands ===
commits layer2 would bring in:
  fc9279e feat(repo): order lookup
  6c5b822 feat(db): add connection pool config     <-- 第1层的提交跟着来了

$ git switch main
$ git merge --no-ff stack/2-repo

files now on main:
  README.md  app.yml  db.yml  repo.py            <-- db.yml 也一起进来了

what is LEFT in the bottom PR (main..stack/1-db):
  commits: 0
   repo.py | 2 --
  -> the bottom PR is now EMPTY

只挑第 2 层合并，第 1 层的提交也跟着进了主干。这很自然，因为第 2 层的历史里本来就含着第 1 层的提交。结果就是最后那一行。第 1 层 PR 剩下的提交数变成了 0。

  • 第 1 层没有以自己的名义被评审就进了主干。如果按 PR 设了审批规则，这条规则就被悄悄绕过了
  • 第 1 层的 PR 视图现在显示「无改动」。评审者无从知道发生过什么
  • 还要留意差异是负数。主干已经领先于第 1 层，所以以第 1 层为基准去看，repo.py 像是被删掉了
  • 所以平台不让中间层单独合并，是保护而不是限制。它把下面的一起合进去，从根上堵死这种局面

6.1 压缩合并这个陷阱

相当多的团队把压缩合并当作默认，压成一个提交好让主干历史干净。可压缩会造出一个内容相同、哈希不同的新提交。它跟堆叠碰上会怎样，我分两种情况跑了一遍。

=== 4-3. bottom squash-merged, then the stack rebased (没人动过的情况) ===
$ git merge --squash stack/1-db
$ git commit -m "feat(db): add connection pool config (#1)"
same content, different commit id:
  main:db.yml        c7c0b78
  stack/1-db:db.yml  c7c0b78      <-- 内容(blob)完全相同

$ git switch stack/2-repo
$ git rebase main
warning: skipped previously applied commit 8fd3e84
hint: use --reapply-cherry-picks to include skipped commits
Successfully rebased and updated refs/heads/stack/2-repo.
layer 2 review unit:
 repo.py | 2 ++                                   <-- 干净地收拾好了

=== 4-4. same, but the maintainer edited one line while squashing ===
$ git rebase main
Auto-merging db.yml
CONFLICT (add/add): Merge conflict in db.yml
error: could not apply 1cb43a1... feat(db): add connection pool config
  AA db.yml
pool:
<<<<<<< HEAD
  size: 8
=======
  size: 5
>>>>>>> 1cb43a1 (feat(db): add connection pool config)
  timeout: 30
rebase exit code: 1

两个结果分岔了。没人动过就压缩时，git 会提示「跳过已经应用过的提交」并自行收拾，第 2 层的评审单元干干净净只剩一个 repo.py。可维护者在合并时哪怕只改了一行，同一个文件就被当成两边各自新建的，于是出了 add/add 冲突。

  • 「用压缩合并会毁掉堆叠」这话只对一半。内容原封不动的话 git 自己会跳过
  • 真正毁掉它的是合并时内容发生变化。在网页编辑器里顺手改错别字、流水线里挂了自动格式化、把发布说明塞进提交，这些全都属于这一类
  • 文档要求的完全线性历史说的是同一件事。它直接写明，当有改动被推到下层分支、或者主干往前走时，这个条件就会被打破
  • 除了在引入前用团队默认的合并方式把一个堆叠完整跑一遍，没有别的验证办法

7. 三种方式对照 - 大 PR、独立 PR、堆叠 PR

同一份工作可以用三种方式交出去。没有哪一种更优越，区别在于把成本放在哪里。

标准一个大 PR多个独立 PR堆叠 PR
评审单元整体一大块每个 PR 独立每层独立，下层内容被排除
依赖的表达无（一整块，不需要）表达不了。只能在说明栏里写成文字以基准分支的形式刻进历史
重复的改动没有有重叠文件时两边都出现没有。下层的在上层看不见
回滚全有或全无按 PR，但顺序仍要守自上而下按层
部分通过不可能可以只能自下而上
CI 成本一次，失败就全部重跑与 PR 数相同，互不相干与层数相同 + 底层一变上面全部重跑
合并顺序无约束无约束（冲突各自解决）强制自下而上
作者负担低中（手工解冲突）高。底层一变就要变基
评审者负担非常高低，但看不到全貌低 + 有堆叠图可掌握全貌
所需工具无无本地 git 即可，有平台支持更省事

从表里要读出的是堆叠 PR 的成本压在作者身上。评审者轻松多少，作者就要在变基上还回去多少。所以自己写自己评的团队得不到好处，只有评审确实是瓶颈的团队才划算。

8. 落到真实团队里 - 人数、审批规则、发布分支

这里不谈具体某个组织。只看研发组织里常见的三种结构性条件，以及堆叠如何与之咬合。

8.1 评审者很少的时候

  • 堆叠会增加评审的「件数」。三层就来三条通知。只有一个评审者的话，同一个人要打开三次
  • 总时间会不会减少，取决于层切得好不好。切得好，每层都短，加起来就少；切得不好，反复重建三次上下文，反而更多
  • 有一样收益是确定的。可以先把下半截放行。作者能在已批准的下层之上继续往下做，要回滚的风险也变小
  • 反过来，只有一个评审者而他又不在时，整个堆叠会一起停住。底层堵住，上面就合不了，单点故障因此变强

8.2 有审批规则的时候

  • 有必需审批人数或者代码所有者规则时，每一层都要通过这条规则。文档也写明，它下面的所有 PR 都满足要求之后才能合并
  • 也就是说需要与层数相同的审批事件。必需审批两人、层数四层，就会发生八次审批动作
  • 所以审批规则越严的组织，把层数保持在三四层以内越现实
  • 代码所有者按层不同反而是好事。数据库负责人看第 1 层、API 负责人看第 3 层并行进行，总等待时间确实会下降。换成一个大 PR，这两个人得各自把同样的 40 个文件都翻一遍
  • 文档里不支持自动合并这条约束在这里也能体感到。就算审批都齐了，还得有人去按合并键

8.3 与发布分支策略咬合的时候

  • 堆叠的底座指向的不是主干而是发布分支时，那条分支每进一次热修复，整个堆叠就晃一次。第 5 节的 --update-refs 事实上成了必需品
  • 堆叠横跨发布冻结期时，会出现下层属于本次发布、上层属于下次发布的局面。这时要把上层的基准挪到下一个发布分支，而这又是一次变基
  • 如果有用挑拣提交往发布上带的惯例，6.1 节里内容相同哈希不同的问题会原样复现
  • 靠派生仓库接受贡献的仓库根本用不了。文档明示跨派生仓库的堆叠不受支持
  • 实务上唯一的解法是让堆叠的寿命短于发布周期。层一旦开始跨越发布边界，管理成本就急剧上升

9. 引入的判断 - 什么时候值得，什么时候过头

先说结论。堆叠不是用来提高评审容量的工具。一周能处理多少改动，依然由评审者的时间决定。堆叠改变的只有单件的评审时间和先把下半截放行的可能性这两样。所以判断标准也随之变窄。

情形适合堆叠吗理由
改动沿层次方向自然可分适合依赖方向是单向的，能定出顺序
重命名、挪动这类无害的准备工作量大适合抽到最底层就能很快批准
只发布下层也有意义适合部分通过的收益真的能兑现
代码所有者按层不同适合并行评审能减少总等待
两块互相引用不适合定不出顺序，放同一层
层数超过五层不适合更新成本吃掉收益
底层每天都在变不适合会变成每天给上层变基
PR 本来就只有五个文件左右不适合没什么可拆的，只增开销
从派生仓库接受贡献不可用文档明示不支持
压缩合并 + 合并时顺手编辑的习惯先做试验6.1 节的冲突可能复现

9.1 不靠工具、只用本地 git 能做和不能做的事

  • 能做。造出层来。git switch -c 上层 下层 三行就完事
  • 能做。确认各层的评审单元。git diff --stat 下层..上层 出来的就只有这一层新做的东西
  • 能做。底层一变就把上层搬走。--onto 和 --update-refs 干的就是这活
  • 能做。撤销。--abort、reflog、ORIG_HEAD
  • 能做。连开 PR 也能。手工把每个 PR 的基准分支指到下层，评审界面照样只显示那一层
  • 不能做。底层合并之后自动改掉上层 PR 的基准。手工做的话每次都会忘
  • 不能做。给评审者展示这一层在整体中的位置。只能在说明栏里写个清单，而且很快就过时
  • 不能做。强制按自下而上的顺序合并。只能靠自觉，于是第 6 节的事故就会发生
  • 不能做。一次操作合并多个层
  • 换句话说，平台功能填补的正好就是这四处。其余的 git 里早就有了

9.2 引入前的检查清单

  • 现在的 PR 真的大吗？先去量文件数和等待天数。本来就小还引入就是亏
  • 瓶颈是评审，还是发布或 QA？不是评审的话，堆叠什么也修不好
  • 团队的默认合并方式是什么？是压缩合并的话，先做 6.1 节那个试验
  • 有没有堆叠分支只由作者本人推送的约定？强制推送来回飞，历史就会错位
  • git 版本是2.38 以上吗？没有 --update-refs，手工活就会按层数留着
  • 有没有把堆叠保持在三四层以内的规则？
  • 会不会出现发布分支充当堆叠底座的情况？如果会，就把寿命定得短于发布周期
  • 有没有派生仓库来的贡献？如果有，那条路径用不了堆叠
  • CI 成本承担得起吗？底层一变，上面全部重跑
  • 团队知道这是预览吗？界面和命令都可能变

最后再把全文的那条线画一遍。堆叠 PR 是一件降低拆分大改动这份反复劳动成本的工具，仅此而已。在哪里切、什么放在下面、这个改动值不值得拆 —— 这些判断工具不会替你做。而且拆完之后，决定吞吐量的依然是评审容量。多堆几层并不会让评审者的一天变长。

# 堆叠 PR — 复现堆叠的命令与引入检查清单

> 来源: braindetox.kr — GitHub 堆叠 PR 公开预览
> 依据: 在 git 2.48.1.windows.1 / GNU bash 5.2.37 (MSYS2) / Windows 10 Pro 上实测验证
> 时点: 2026-08-01。GitHub 堆叠 PR 处于公开预览，界面与命令都可能变化。
> 把这个文件直接粘给 AI，写上「按这些标准检查我们的仓库」即可使用。

## 1. 搭建堆叠 (只用本地 git)

```
git switch -c stack/1-db   main          # 第 1 层
git switch -c stack/2-repo stack/1-db    # 第 2 层建在第 1 层之上
git switch -c stack/3-api  stack/2-repo  # 第 3 层建在第 2 层之上
```

查看命令:

```
git log --graph --oneline --decorate main..stack/3-api
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads/
git diff --stat stack/1-db..stack/2-repo    # 只看该层的评审单元
git diff --stat main..stack/3-api           # 若是一个大 PR 就是这么多
```

## 2. 底层变动后更新上层

```
# 只更新紧邻的上一层
git switch stack/2-repo
git rebase stack/1-db

# 往上两层以上 (需显式给出旧基准哈希)
git rebase --onto stack/2-repo OLD_HASH stack/3-api

# 一条命令搬动整个堆叠 (git 2.38+)
git switch stack/3-api
git rebase --update-refs main

# 设为默认行为
git config rebase.updateRefs true
```

## 3. 冲突与撤销

```
# 中途放弃
git rebase --abort

# 解决后继续
git add db.yml
git rebase --continue

# 撤销已完成的变基
git reflog stack/3-api
git reset --hard stack/3-api@{1}
git reset --hard ORIG_HEAD          # 简短写法
```

- 冲突标记里 HEAD 一侧是新基准 (下层)，另一侧是正在重放的上层提交
- 存在 `.git/rebase-merge` 说明处于中间状态
- 撤销只在本地无害。强制推送之后，别人已拉取的历史就对不上了

## 4. 合并流程

- 从下往上合并 (平台文档给出的规则)
- 不能单独合并中间的 PR — 下面的总会一起合并
- 强行先合中间层，底层 PR 的剩余提交会变成 0，等于没被评审就进了主干
- 底层合并后，上层会重新以主干为基准
- 不支持自动合并 (以预览时点为准)
- 压缩合并的试验: 内容原样时 git 会跳过；合并时哪怕改一行也会出 add/add 冲突

## 5. 三种方式对比

| 标准 | 一个大 PR | 多个独立 PR | 堆叠 PR |
|---|---|---|---|
| 评审单元 | 整体一块 | 每个 PR 独立 | 每层独立 |
| 依赖表达 | 不需要 | 表达不了 | 刻在基准分支上 |
| 撤销 | 全有或全无 | 按 PR | 自上而下按层 |
| 部分通过 | 不可能 | 可以 | 只能自下而上 |
| CI 成本 | 一次 | 与 PR 数相同 | 与层数相同 + 底层变动时全跑 |
| 合并顺序 | 无约束 | 无约束 | 强制自下而上 |
| 作者负担 | 低 | 中 | 高 (变基) |

## 6. 引入检查清单

- [ ] 现在的 PR 真的大吗 (先量文件数与等待天数)
- [ ] 瓶颈是评审吗 (若是发布或 QA，堆叠无效)
- [ ] 变更是否沿层次方向可分 (互相引用的放同一层)
- [ ] 有没有把层数控制在三四层以内的规则
- [ ] 团队默认合并方式是压缩合并吗 (若是，先做试验)
- [ ] 有没有「堆叠分支只由作者推送」的约定
- [ ] git 是否为 2.38 以上 (可用 --update-refs)
- [ ] 会不会出现发布分支充当堆叠底座的情况
- [ ] 是否走派生仓库贡献路径 (若是则无法使用)
- [ ] 能否承担底层一变、上层 CI 全部重跑的成本

## 7. 不要做的事

- 把互相引用的部分切成不同层 — 定不出顺序
- 把层数增到五层以上 — 更新成本吃掉收益
- 让多人推送堆叠分支 — 与变基相冲突
- 想先合并中间层 — 底层会未经评审被带进去
- 指望堆叠能提高评审容量 — 总量由评审者的时间决定
- 把预览功能的界面与命令当作固定内容写进文档
