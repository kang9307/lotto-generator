이 글의 출력 블록은 함께 놓인 코드의 출력이며 글자 그대로 붙였다. 환경은 Windows 10의 Git Bash에서 실행한 node v22.16.0, Python 3.13.3, curl 8.12.1과 Windows PowerShell 5.1(5.1.19041.6456)이다. PowerShell 7은 이 PC에 없어 쓰지 않았다. 포트는 모두 127.0.0.1의 로컬 임시 서버이고, 사양·공식 문서를 인용한 곳은 문서의 문장임을 밝혀 실행 관찰과 구분한다.

서론 - 문법에 어긋나지 않는데 값이 정해지지 않는 문서

{"a":1,"a":2} 같은 문서는 JSON 문법 위반이 아니다. RFC 8259의 객체 문법은 member를 쉼표로 이어 붙이는 규칙만 적고 이름의 중복을 막는 조건을 두지 않는다. 유일성은 문법이 아니라 「SHOULD be unique」라는 권고 문장으로만 남아 있다. 그래서 같은 바이트열을 받은 두 프로그램이 서로 다른 값을 읽는 일이 가능하다.

이 차이는 파서 하나만 쓰는 프로그램에서는 드러나지 않는다. 한 번 파싱하고 그 결과를 끝까지 쓰면 마지막 값이든 첫 값이든 일관되기 때문이다. 문제는 같은 문서를 두 번 읽는 구조에서 생긴다. 앞단이 요청 본문을 검사하고, 뒤단이 같은 본문을 다시 파싱해 쓰는 경우가 대표적이다. 숫자 정밀도 쪽 문제는 JSON 64비트 ID 정밀도 글의 13절이 중복 키를 한 항목으로 다뤘고, 그 한 항목을 파서별 비교·검출·재현으로 넓힌 것이 아래 내용이다.

다루는 질문은 다음과 같다.

  • 사양 문서는 중복 키에 대해 무엇이라고 적는가.
  • node·Python·PowerShell 5.1은 같은 문서에서 각각 어떤 값을 내는가.
  • 키 순서, 대소문자만 다른 키, 이스케이프로 쓴 키는 중복으로 취급되는가.
  • 서버 쪽 파서도 로컬 호출과 같은 값을 내는가.
  • 중복 키를 검출하는 스크립트는 어떻게 쓰는가.
  • 검증하는 계층과 쓰는 계층이 다른 값을 보면 실제로 무엇이 통과하고 어떻게 막는가.

사양과 공식 문서가 적은 것

RFC 8259 4절, ECMAScript 사양의 JSON.parse, Python json 모듈 문서, Microsoft Learn의 ConvertFrom-Json 문서(5.1)에서 중복 키를 다룬 문장은 다음과 같다. 원문은 영어 그대로 옮긴다.

출처원문뜻
RFC 8259 4The names within an object SHOULD be unique.이름의 유일성은 권고
RFC 8259 4When the names within an object are not unique, the behavior of software that receives such an object is unpredictable. Many implementations report the last name/value pair only. Other implementations report an error or fail to parse the object, and some implementations report all of the name/value pairs, including duplicates.중복 시 동작은 예측 불가. 마지막 쌍만 보고, 오류를 내고, 전부 보고하는 구현이 모두 있다
ECMAScript JSON.parseIn the case where there are duplicate name Strings within an object, lexically preceding values for the same key shall be overwritten.사양이 앞의 값을 덮어쓴다고 규정

Microsoft Learn ConvertFrom-Json (5.1)if the JSON string contains duplicate keys, only the last key is used by this cmdlet중복 키가 있으면 마지막 키만 사용

표에서 정리되는 것은 네 가지다.

  • RFC는 유일성을 권고할 뿐이고, 중복 시 동작을 마지막 값·오류·전부 보고 세 갈래로 나열한 뒤 예측 불가라고 적는다.
  • ECMAScript 사양은 JSON.parse에서 앞의 값이 덮어쓰인다고 직접 규정한다. 자바스크립트 쪽 「마지막 값 승리」는 관행이 아니라 사양 문장이다.
  • Python 문서와 PowerShell 문서도 마지막 값 사용을 적는다. 이쪽은 해당 구현의 문서화된 동작이다.
  • RFC가 열어 둔 「오류」와 「전부 보고」 쪽 동작은 Python의 object_pairs_hook 같은 확장점으로 구현할 수 있다.

  • 같은 이름이 두 번 나오는 문서는 세 런타임 모두 마지막 값 하나만 남겼다. 사양·문서 인용과 같은 방향이다.
  • 값이 객체인 경우도 병합되지 않고 통째로 교체됐다. 첫 객체의 x는 결과에서 사라졌다.
  • 배열 안의 객체는 객체마다 따로 판정됐다. 첫 객체에서만 k가 2가 됐고 둘째 객체의 k는 3으로 남았다.
  • Python의 object_pairs_hook=list는 [('a', 1), ('a', 2)]를 돌려줬다. 파서가 두 쌍을 모두 읽었다는 뜻이고, 하나만 남기는 것은 그 뒤 dict로 만드는 단계의 일이다.

값은 마지막 것, 자리는 처음 것

표의 둘째 줄 {"a":1,"b":2,"a":3}의 결과는 세 런타임 모두 {"a":3,"b":2}였다. a의 값은 마지막 출현(3)에서 왔지만 키의 자리는 b보다 앞, 곧 처음 출현의 자리에 남았다. 키 순서를 읽어 첫 필드를 판단하거나 순서대로 처리하는 코드가 중복 키 문서를 받으면, 값은 뒤쪽 것인데 순서는 앞쪽 것이라는 조합을 만난다.

자바스크립트에서는 reviver 함수로 파싱 과정을 들여다볼 수 있다. 앞의 node 출력 마지막 줄에서 reviver가 받은 호출은 a=2와 루트 객체 두 건뿐이었다. 값 1은 reviver에 전달되지 않았다.

  • JSON.parse의 결과 객체에는 키가 하나뿐이어서(keys=1) 중복이 있었다는 흔적이 없다.
  • reviver도 덮어쓰인 값은 받지 못했다. 이 실행에서 reviver로는 중복 사실을 알 수 없었다.
  • Python은 object_pairs_hook이 있어 파서가 읽은 쌍 목록 자체를 받을 수 있었다. 검출 스크립트는 이 차이 위에 놓인다(7절).

같은 키로 보이지 않는 같은 키

표의 넷째 줄은 a와 A다. node와 Python은 둘을 별개의 키로 보고 키 2개를 남겼다. PowerShell 5.1은 변환 자체가 실패해 InvalidOperationException이 났다. 같은 문서를 어떤 계층은 받아들이고 어떤 계층은 거부한다. 이 PC의 한국어 로캘에서 예외 메시지는 「중복된 키 'a' 및 'A'」라는 구절을 포함했다. 메시지가 중복 키라는 말로 거부 이유를 직접 적은 것이므로, PowerShell 5.1은 대소문자만 다른 키도 중복으로 판정한 것으로 읽힌다(메시지 문구는 로캘마다 다르다).

다섯째 줄은 키를 이스케이프로 쓴 경우다. 문서 안의 "\u0061"는 디코딩하면 a와 같은 이름이다. 세 런타임 모두 이를 중복으로 보고 마지막 값 2만 남겼다. 이 사실이 문자열 검색 방식의 검증에 어떤 의미인지 다음 스크립트가 보인다. 키 role이 한 번만 보이도록 두 번째 키를 이스케이프로 쓴 문서다.

import json
                    text = '{"role":"user","\\u0072ole":"admin"}'

                    print("parsed pairs: " + str(pairs))

  • 문자열 검색이나 정규식으로 키를 세는 검증은 이스케이프로 쓴 중복을 놓친다. 검증은 파서가 디코딩한 뒤의 키를 기준으로 해야 한다.
  • 대소문자만 다른 키는 런타임마다 다르게 처리됐다. 파서를 둘 이상 쓰는 구조에서는 이 차이도 같은 문서가 계층마다 다르게 읽히는 경로가 된다.

서버 쪽 파서도 같은가

같은 본문을 curl로 보낸 로컬 HTTP 서버 둘의 응답이다. 하나는 Python 표준 라이브러리의 http.server와 json.loads, 다른 하나는 node의 http 모듈과 JSON.parse다. 둘 다 파싱한 결과를 직렬화해 응답 본문으로 돌려준다.

import json
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    class H(BaseHTTPRequestHandler):
                        def do_POST(self):
                            body = self.rfile.read(int(self.headers["Content-Length"]))
                            out = json.dumps(json.loads(body), separators=(",", ":")).encode()
                            self.send_response(200)
                            self.send_header("Content-Type", "application/json")
                            self.send_header("Content-Length", str(len(out)))
                            self.end_headers()
                            self.wfile.write(out)
                        def log_message(self, *a):
                            pass
                    
                    HTTPServer(("127.0.0.1", 18081), H).serve_forever()
const http = require('http');
                    http.createServer((req, res) => {
                      const chunks = [];
                      req.on('data', (c) => chunks.push(c));
                      req.on('end', () => {
                        let out;
                        try {
                          const o = JSON.parse(Buffer.concat(chunks).toString('utf8'));
                          out = JSON.stringify(o);
                        } catch (e) {
                          out = JSON.stringify({ error: e.name });

                        res.writeHead(200, { 'Content-Type': 'application/json' });

두 서버와 이후 절의 게이트웨이를 띄우고 curl을 보내는 스크립트 전체가 아래다. 대기 루프는 서버가 뜰 때까지 최대 50회(0.5초 간격) 확인하고 넘으면 오류로 끝내며, post 함수가 본문을 보낸다.

python echo_py.py & P1=$!
                    node echo_node.js & P2=$!
                    python gateway.py raw 18080 & P3=$!
                    python gateway.py reject 18083 & P4=$!
                    python gateway.py canonical 18084 & P5=$!

                    for i in $(seq 50); do

                      sleep 0.5
                    done
                    [ "$ok" = 1 ] || { echo "servers did not start within 25 s" >&2; kill $P1 $P2 $P3 $P4 $P5; exit 1; }

                    post 18081 '{"a":1,"a":2}'

                    {"a":2}
  • Python 서버와 node 서버 모두 {"a":2}를 돌려줬다. 서버 쪽 파서의 결과가 로컬 호출의 결과와 같았다.
  • 같은 언어의 같은 파서이므로, HTTP를 거치면서 본문이 바뀌는 단계는 이 구성에 없었다.
  • 서버 둘의 결과가 같다는 것은 이 두 파서의 결과가 같다는 뜻일 뿐이다. 두 계층이 정책을 달리하면 어떻게 되는지가 8절의 질문이다.

중복 키 검출 스크립트

Python 문서가 object_pairs_hook을 「쌍 목록을 받아 dict 대신 반환값을 쓰는 확장점」으로 적고 있으므로, 쌍을 dict에 넣는 중간에 이미 있는 키인지 검사하면 검출기가 된다. 아래 스크립트는 한 줄에 JSON 문서 하나가 든 파일을 읽어 줄마다 판정한다.

import json, sys
                    
                    def reject_duplicates(pairs):
                        obj = {}
                        for key, value in pairs:
                            if key in obj:
                                raise ValueError("duplicate key " + repr(key) + ": " + repr(obj[key]) + " then " + repr(value))
                            obj[key] = value
                        return obj
                    
                    for lineno, line in enumerate(open(sys.argv[1], encoding="utf-8"), 1):
                        text = line.rstrip("\n")
                        try:
                            json.loads(text, object_pairs_hook=reject_duplicates)
                            print(str(lineno) + ": OK    " + text)
                        except ValueError as err:
                            print(str(lineno) + ": FAIL  " + text)
                            print("    " + str(err))

입력 파일은 일곱 줄이고, 마지막 줄은 일부러 깨뜨린 문서다. 실행 결과다.

1: OK    {"a":1,"b":2}
                    2: FAIL  {"a":1,"a":2}
                        duplicate key 'a': 1 then 2
                    3: OK    {"a":1,"A":2}
                    4: FAIL  {"a":1,"\u0061":2}
                        duplicate key 'a': 1 then 2
                    5: FAIL  {"l":[{"k":1,"k":2},{"k":3}]}
                        duplicate key 'k': 1 then 2
                    6: OK    {"a":1,"b":{"a":2}}
                    7: FAIL  {"a":1,
                        Expecting property name enclosed in double quotes: line 1 column 8 (char 7)
  • 2번 줄(a 두 번)과 5번 줄(배열 안 객체의 k 두 번)이 걸렸다. 중첩된 객체 안의 중복도 hook이 객체마다 호출되므로 잡혔다.
  • 4번 줄의 이스케이프로 쓴 a도 걸렸다. 앞 절의 문자열 검색과 달리 디코딩 후의 키를 보기 때문이다.
  • 3번 줄(a와 A)과 6번 줄(바깥 a와 안쪽 a)은 통과했다. 이 검출기는 같은 객체 안의 정확히 같은 이름만 중복으로 본다.
  • 7번 줄은 중복이 아니라 구문 오류로 걸렸고, 같은 except ValueError 아래에서 메시지만 달랐다. 구문 오류와 중복을 구분하려면 예외 형식을 나눠 받아야 한다.

두 계층이 서로 다른 값을 보는 재현

구성은 둘이다. 앞단 게이트웨이(Python)는 요청 본문을 파싱해 role이 admin이면 403으로 거부하고, 통과시킨 요청의 원본 바이트를 뒷단(node, 앞의 echo 서버)에 그대로 전달한다. 뒷단은 JSON.parse로 읽은 결과를 돌려주므로, 응답이 곧 뒷단이 본 값이다. 게이트웨이의 파서는 object_pairs_hook으로 「이미 있는 키는 덮지 않는」 첫 값 우선 정책을 직접 구현했다. 이 PC의 표준 파서 셋이 모두 마지막 값 우선이어서, 정책이 다른 두 계층은 이렇게 만들어야 했다. 이 정책 차이는 시연용으로 정한 가정이고, 실제 제품 어느 쪽이 첫 값 우선인지를 보인 것이 아니다.

import json, os, sys, urllib.request
                    from http.server import BaseHTTPRequestHandler, HTTPServer
                    
                    MODE = sys.argv[1]
                    PORT = int(sys.argv[2])
                    BACKEND = "http://127.0.0.1:18082/"
                    
                    def first_wins(pairs):
                        obj = {}
                        for key, value in pairs:
                            obj.setdefault(key, value)
                        return obj
                    
                    def reject_duplicates(pairs):
                        obj = {}
                        for key, value in pairs:
                            if key in obj:
                                raise ValueError("duplicate key " + repr(key))
                            obj[key] = value
                        return obj
                    
                    class H(BaseHTTPRequestHandler):
                        def reply(self, code, text):
                            data = text.encode()
                            self.send_response(code)
                            self.send_header("Content-Length", str(len(data)))
                            self.end_headers()
                            self.wfile.write(data)
                    
                        def do_POST(self):
                            body = self.rfile.read(int(self.headers["Content-Length"]))
                            hook = reject_duplicates if MODE == "reject" else first_wins
                            try:
                                doc = json.loads(body, object_pairs_hook=hook)
                            except ValueError as err:
                                return self.reply(400, "gateway: 400 " + str(err))
                            if doc.get("role") == "admin":
                                return self.reply(403, "gateway: 403 role admin is not allowed")
                            forward = json.dumps(doc).encode() if MODE == "canonical" else body
                            req = urllib.request.Request(BACKEND, data=forward, method="POST")
                            with urllib.request.urlopen(req) as r:
                                self.reply(200, "gateway: passed; backend saw " + r.read().decode())
                    
                        def log_message(self, *a):
                            pass
                    
                    HTTPServer(("127.0.0.1", PORT), H).serve_forever()

앞 절의 run.sh를 그대로 실행한 전체 출력이다. 번호는 run.sh의 echo 제목과 같다.

== 1. python server, one document
                    {"a":2}
                    == 2. node server, same document
                    {"a":2}
                    == 3. gateway, normal request
                    gateway: passed; backend saw {"user":"alice","role":"user"}
                    == 4. gateway, role admin
                    gateway: 403 role admin is not allowed
                    == 5. gateway, role twice (user then admin)
                    gateway: passed; backend saw {"user":"alice","role":"admin"}
                    == 6. gateway that rejects duplicates
                    gateway: 400 duplicate key 'role'
                    == 7. gateway that forwards what it parsed
                    gateway: passed; backend saw {"user":"alice","role":"user"}
                    == 8. gateway, role twice (admin then user)
                    gateway: 403 role admin is not allowed
번호요청 본문의 role게이트웨이 판정뒷단이 본 role
3user통과user
4admin403—
5user, admin통과admin
8admin, user403—
  • 요청 5는 role이 user, admin 순으로 두 번 나온 본문이다. 게이트웨이는 첫 값 user를 보고 통과시켰고, 뒷단은 마지막 값 admin을 읽었다. 거부해야 할 값이 검증을 지나 뒷단에 도달했다.
  • 요청 8은 두 값의 순서만 뒤집은 본문이다. 이번에는 게이트웨이가 첫 값 admin을 보고 403으로 거부했다. 변인을 순서 하나로 좁히면, 게이트웨이가 첫 값을 읽는다는 것이 출력으로 분리된다.
  • 요청 3과 4는 대조군이다. 중복 없는 본문에서는 게이트웨이의 판정과 뒷단의 값이 일치했다.
  • 어느 한 파서가 틀린 것이 아니다. RFC가 예측 불가라고 적은 영역에서, 두 계층이 각자 다른 선택을 했을 뿐이다. 문제는 검증한 문서와 사용한 문서가 같은 바이트열이면서도 같은 값이 아니라는 점이다.

막는 방법 둘 - 거부하거나, 검증한 것을 넘기거나

같은 게이트웨이 코드에서 모드만 바꿔 두 방법을 실행했다. reject 모드는 이미 있는 키를 만나면 파싱을 실패시켜 400으로 돌려보낸다. canonical 모드는 게이트웨이가 파싱한 객체를 다시 직렬화해 뒷단에 보낸다. 요청은 앞 절의 요청 5와 같은 본문이고, 결과는 run.sh의 6번과 7번 출력이다.

방법게이트웨이 동작요청 5와 같은 본문의 결과
중복 거부 (reject)중복 키를 만나면 파싱 실패, 뒷단을 호출하지 않음gateway: 400 duplicate key 'role'
검증한 객체를 직렬화해 전달 (canonical)원본 바이트 대신 게이트웨이가 파싱한 객체를 다시 JSON으로 만들어 전달gateway: passed; backend saw {"user":"alice","role":"user"}
수정 없음 (raw)원본 바이트를 그대로 전달gateway: passed; backend saw {"user":"alice","role":"admin"}
  • reject는 요청이 뒷단에 닿기 전에 400으로 멈췄다. 중복 키를 의도적으로 보내는 정당한 클라이언트가 있다면 그 요청도 400을 받는다.
  • canonical은 뒷단이 게이트웨이가 검증한 값 user를 받았다. 이 방식은 게이트웨이가 첫 값을 고른다는 정책을 뒷단에 강제한 결과이므로, 클라이언트가 의도한 값이 마지막 것이었다면 다른 값이 쓰인다.
  • 두 방법의 공통점은 검증한 객체와 사용하는 객체가 같은 값을 갖도록 만든다는 것이다. 한쪽은 문서를 받아들이지 않고, 다른 쪽은 문서를 한 번만 해석해 그 결과를 넘긴다.
  • 앞 절의 예가 보인 것은 검증 계층과 소비 계층이 원본 바이트를 각자 다시 파싱하는 구조다. 신뢰 경계를 건너는 입력을 한 번만 해석하는 구조는 클라이언트 신뢰 경계 글이 다룬 원칙과 이어진다.

실무에서 점검할 항목은 다음과 같다.

  • 같은 요청 본문을 두 번 이상 파싱하는 계층이 있는가. 있다면 파서의 종류와 설정이 같은가.
  • 검증이 파서가 디코딩한 키를 기준으로 하는가, 원문 텍스트 검색을 기준으로 하는가.
  • 중복 키를 받으면 거부할지, 한 정책으로 정규화해 넘길지 정했는가.
  • 검증한 값과 뒷단이 받는 바이트가 같은지 확인하는가. 앞의 출력에서 canonical 모드의 뒷단이 받은 본문은 원본 바이트가 아니라 게이트웨이가 다시 만든 JSON이었다.

확인하지 못한 것

  • node·Python·PowerShell 5.1 이외 런타임(Go·Java·Ruby·PHP·jq 등)의 동작. RFC가 적은 「오류를 내는 구현」과 「전부 보고하는 구현」의 실제 사례는 Python의 object_pairs_hook=list 외에는 실행하지 못했다.
  • PowerShell 7과 .NET의 System.Text.Json. 이 PC에는 pwsh가 없고 5.1에서는 해당 클래스를 쓰지 않았다.
  • PowerShell 5.1에서 대소문자만 다른 키가 오류가 되는 이유. 문서는 중복 키가 PSObject·Hashtable에서 금지된다고 적고, 이 PC의 한국어 로캘 예외 메시지는 「중복된 키 'a' 및 'A'」를 포함해 중복 키 규칙이 원인임을 직접 말한다. 확인하지 못한 것은 영어 등 다른 로캘에서의 메시지 문구와 이 규칙이 적용되는 .NET 내부 경로다.
  • node에서 중복 키를 검출하는 방법. 이 실행에서는 JSON.parse 결과와 reviver로는 중복 사실을 얻지 못했고, 다른 방법은 시험하지 않았다.
  • 게이트웨이의 첫 값 우선 정책은 시연용으로 직접 구현한 것이다. 실제 제품·라이브러리·프록시 중 첫 값을 택하는 것이 있는지는 확인하지 못했다.
  • Python 표준 http.server와 node http 모듈 이외의 웹 프레임워크 본문 파서, Content-Type·문자 인코딩 헤더가 결과에 미치는 영향.
  • PostgreSQL jsonb·MongoDB 등 저장소가 중복 키를 입력 시점에 처리하는 방식. 이 PC에서 실행하지 않았다.
  • 매우 큰 문서·스트리밍 파서에서의 동작과 성능, JSON5 같은 확장 문법에서의 중복 키 처리.
