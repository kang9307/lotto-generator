서론: 터미널이 IDE가 되겠다는 발상

GeekNews(hada.io)에서 omp(oh-my-pi)를 처음 봤을 때 든 생각은 회의였다. Claude Code, OpenAI Codex CLI, Aider가 이미 자리 잡은 터미널 코딩 에이전트 시장에 또 하나가 얹힌 것처럼 보였기 때문이다. 그런데 소개를 읽어 보니 각도가 달랐다. omp는 새 에이전트를 처음부터 만든 것이 아니라, Mario Zechner가 만든 극단적으로 미니멀한 코딩 에이전트 Pi를 포크해 정반대 방향으로 밀어붙였다. Pi가 도구를 최대한 빼서 작게 만드는 실험이었다면, omp는 터미널이 IDE처럼 동작할 때까지 도구를 계속 더한 실험이다.

이 글은 omp의 기능 나열이 아니라, 그 발상 자체를 검증하는 글이다. 터미널 코딩 에이전트라는 지형이 왜 이렇게 붐비게 됐는지, omp가 Pi에서 무엇을 상속하고 무엇을 뒤집었는지, LSP·디버거·Hashline 편집이라는 차별점이 실제로 어떤 문제를 푸는지, 그리고 무엇보다 한국 개발자가 Claude Code·Codex CLI 같은 벤더 제품 대신 omp를 실무에 들일 이유가 있는지를 냉정하게 따진다. 어제 다룬 로컬 LLM 에이전트 개발과 툴 검색·HITL, AI 코딩 세션의 휘발성 맥락을 프로젝트 기억으로 남기기도 결국 같은 질문의 다른 단면이었다. omp는 그 질문에 "터미널 하나로 다 하자"는 답을 던진다.

1. omp란 - Pi에서 갈라져 나온 배터리 포함 터미널 에이전트

omp는 can1357/oh-my-pi 저장소에 MIT 라이선스로 공개된 오픈소스 프로젝트다. 설치는 macOS·Linux에서 curl -fsSL https://omp.sh/install | sh 한 줄, 혹은 Bun을 통한 npm 패키지(@oh-my-pi/pi-coding-agent)로 끝난다. Windows에서는 WSL 없이 네이티브 바이너리로 돌아간다는 점을 명시한다. 실행하면 터미널 안에서 바로 코드베이스를 읽고, 편집하고, 실행하고, 디버깅하는 에이전트가 뜬다.

1.1 핵심 사양

omp는 무거운 작업을 처리하는 네이티브 Rust 엔진 위에 TypeScript 확장 계층을 얹은 구조다. 공개 자료 기준으로 32개의 내장 도구(read/write/edit/bash/eval/lsp/debug/browser/web_search/github 등), 14개의 LSP 연산, 28개의 DAP(디버거) 연산을 갖추고, 40개 이상의 모델 프로바이더에 연결된다. 여기에 서브에이전트 오케스트레이션, 플랜 모드, 슬래시 커맨드, 확장(플러그인) 시스템까지 기본 탑재한다. 한마디로 "박스를 열면 이미 다 들어 있는" 것을 지향한다.

1.2 Pi와의 관계 - 같은 코어, 반대의 철학

omp를 이해하는 열쇠는 원류인 Pi에 있다. Pi는 badlogic/pi-mono 모노레포에 있는 미니멀 하네스로, 모델에게 파일 읽기·쓰기·편집·셸 실행이라는 단 네 개의 도구와 1000토큰 미만의 짧은 시스템 프롬프트만 주고, 나머지는 사용자가 TypeScript 확장으로 직접 붙이도록 남긴다. "무엇을 빼느냐가 무엇을 넣느냐보다 중요하다"는 철학이다. omp는 정확히 그 반대다. 같은 코어에서 출발했지만, 터미널이 IDE처럼 느껴질 때까지 도구를 더하는 쪽을 택했다. 두 프로젝트는 경쟁이라기보다 하나의 미니멀 코어가 양극단으로 뻗은 사례로 보는 것이 정확하다.

1.3 빠르게 자라는 저장소

omp는 공개 이후 짧은 기간에 커뮤니티 관심을 크게 끌었다. 2026년 7월 기준 GitHub 스타는 약 1만9천 개 수준으로, 포크와 기여자도 활발하다. 다만 이 숫자는 계속 바뀌는 스냅샷이라는 점을 감안해야 한다. 여러 소개 글이 시점에 따라 5천, 1만7천, 1만9천 등 서로 다른 수치를 인용하는 것도 이 때문이다. 스타 수 자체보다 중요한 것은, 이 프로젝트가 "데모 프롬프트가 아니라 실사용 도구"를 표방하며 빠르게 도구를 늘려 왔다는 방향성이다.

2. 터미널 코딩 에이전트 지형 - 왜 이렇게 붐비나

omp가 왜 나왔는지 이해하려면, 먼저 터미널 코딩 에이전트라는 카테고리 자체를 봐야 한다. 2025~2026년 사이 이 영역은 급격히 붐볐다.

2.1 세 갈래의 대표 주자

대표 주자를 거칠게 나누면 이렇다. Claude Code는 Anthropic의 벤더 제품으로 모델과 에이전트가 긴밀하게 결합돼 안정성과 완성도가 높다. OpenAI Codex CLI는 OpenAI 계열 모델을 터미널에서 다루는 공식 도구다. Aider는 파이썬 기반의 오래된 오픈소스로, git 커밋 단위 편집과 diff 워크플로에 강하고 모델 선택이 자유롭다. omp는 이 계보에서 "오픈소스 개방성은 Aider 쪽, 완성도 지향은 벤더 쪽"이라는 두 축 사이를 파고든다.

2.2 왜 하필 터미널인가

IDE 플러그인이나 웹 UI가 아니라 터미널을 표면으로 삼는 이유는 분명하다. 터미널은 이미 개발자의 작업 흐름 한복판에 있고, SSH·CI·서버 환경 어디서나 동일하게 동작하며, 셸·git·빌드 도구와 자연스럽게 얽힌다. 문제는 터미널이 본래 코드의 의미를 이해하지 못한다는 점이다. 텍스트를 주고받을 뿐, 심볼이 어디서 정의되고 참조되는지, 실행 중 변수 값이 무엇인지는 모른다. omp의 핵심 베팅은 바로 이 빈틈, 즉 "터미널에 IDE의 이해력을 이식한다"는 데 있다.

3. omp의 세 가지 차별점

omp가 다른 터미널 에이전트와 갈라지는 지점은 세 가지로 정리된다.

3.1 Hashline 편집 - 해시로 앵커링한 편집

터미널 에이전트의 고질적 약점은 의외로 파일 편집 그 자체다. 모델이 생성한 diff나 문자열 치환은 공백 한 칸, 줄바꿈 하나만 어긋나도 패치가 통째로 실패한다. omp의 Hashline은 편집 대상 줄을 내용 해시로 앵커링해 위치를 정확히 특정하는 편집 포맷이다. 저장소가 제시하는 벤치마크에 따르면, 전통적 diff 대비 편집 성공률이 크게 높아지고 출력 토큰도 상당히 줄어든다고 한다(구체 수치는 모델과 조건에 따라 다르게 제시된다). 다만 이 수치는 저장소 자체 측정이라는 점을 분명히 해야 한다. 편집 신뢰성은 실사용에서 체감이 큰 지표이므로, 본인 코드베이스로 직접 재검증하는 편이 안전하다.

3.2 LSP·DAP·브라우저 - 유리 너머로 코드 보기를 넘어서

omp가 "IDE급"을 자처하는 근거가 여기 있다. LSP(Language Server Protocol)를 붙여 정의로 이동, 참조 찾기, 심볼 단위 리네임 같은 시맨틱 조작을 한다. 텍스트 치환이 아니라 언어 서버가 이해한 구조 위에서 리팩터링을 한다는 뜻이다. 여기에 DAP(Debug Adapter Protocol)를 얹어 중단점을 걸고, 변수와 스택 트레이스를 실제로 들여다보는 실디버깅을 지원한다. print 문을 흩뿌리는 방식이 아니다. 브라우저 자동화까지 포함해, "코드를 유리 너머로 바라보던" 텍스트 에이전트를 시맨틱 조작 도구로 끌어올리려는 시도다.

3.3 Hindsight 교차 세션 기억과 서브에이전트

세션이 끝나면 맥락이 휘발되는 것은 모든 코딩 에이전트의 공통 약점이다. omp의 Hindsight는 실행 중에 사실을 남기고(retain) 이후에 불러오는(recall) 교차 세션 기억 시스템으로, 프로젝트 구조에 대한 이해가 대화 사이에 유지되도록 한다. 이는 AI 코딩 세션의 휘발성 맥락을 프로젝트 기억으로 남기기에서 짚은 문제의식과 정확히 맞닿는다. 또한 서브에이전트를 병렬로 띄워 스키마로 검증된 JSON 결과를 받고 작업공간을 격리하는 오케스트레이션도 기본 지원한다. 큰 작업을 쪼개 여러 워커에 분배하는 패턴이다.

4. 유사 계보 - Claude Code·Codex CLI·Aider와 나란히 놓기

omp의 실제 위치는 경쟁 도구와 나란히 놓아야 보인다. 외부 소개 자료를 교차 확인해 방향성 위주로 정리한 표다(2026년 7월 기준, 세부는 시점·출처마다 다를 수 있어 대략치로 읽을 것).

4.1 어디서 누가 이기나

필자의 해석은 이렇다. 완성도와 공식 지원이 최우선이면 Claude Code나 Codex CLI, 검증된 안정성과 git 워크플로가 최우선이면 Aider, 벤더 종속을 피하며 IDE급 도구를 직접 조립하고 싶은 개발자라면 omp가 매력적인 지형이다. 세 갈래는 대체 관계라기보다 서로 다른 우선순위에 응답하는 답으로 보는 편이 정확하다. omp의 진짜 차별점은 "터미널에서 시맨틱 조작과 실디버깅을, 개방형 모델 라우팅과 함께"라는 조합 자체다.

5. 한국 개발자 실무 도입 관점

이제 실무 각도로 내려온다. 한국의 개발 조직이나 개인 개발자가 omp를 들일 때 무엇이 유리하고 무엇이 걸림돌인가.

5.1 도입이 쉬운 지점

설치가 단일 바이너리라 런타임 의존성 지옥이 적고, Windows에서 WSL 없이 네이티브로 돈다는 점은 한국의 혼합 OS 환경(사내 Windows + 서버 Linux)에서 실질적 이점이다. 40개 이상 프로바이더를 라우팅한다는 개방성 덕분에, 국내에서 접근성이 좋은 모델이나 저가·오픈웨이트 모델을 상황에 맞게 붙였다 뗐다 할 수 있다. 특정 벤더 요금제에 묶이지 않는다는 것은 비용 통제 관점에서도 유효하다.

5.2 팀 표준화의 장벽

반대로 조직 도입에는 마찰이 있다. 도구 표면이 넓다는 것은 학습 곡선과 설정 관리 부담이 크다는 뜻이기도 하다. 벤더 제품이 제공하는 SSO, 감사 로그, 조직 정책 강제, 공식 기술 지원 같은 거버넌스 요소는 아직 커뮤니티 오픈소스가 메우기 어려운 영역이다. 팀 전체가 같은 워크플로를 공유해야 하는 상황이라면, 개인의 자유도가 오히려 표준화의 걸림돌이 될 수 있다.

5.3 권한과 보안 경계

터미널 에이전트는 본질적으로 셸 명령·파일 쓰기·코드 실행 권한을 갖는다. omp처럼 도구가 많고 자동화가 깊을수록, 검토해야 할 권한 지점도 늘어난다. 자동 승인 모드를 프로덕션 레포나 자격증명이 있는 환경에서 무분별하게 켜는 것은 위험하다. 승인 게이트, 샌드박스, 격리된 작업공간을 먼저 설계하고, 브라우저 자동화나 github 도구가 닿는 범위를 명시적으로 제한해야 한다.

6. 장단점·한계·비판

omp의 발상은 매력적이지만, 냉정하게 봐야 할 한계도 분명하다.

6.1 성숙도와 표면적의 트레이드오프

"박스를 열면 다 들어 있다"는 것은 강점이자 약점이다. 도구가 32개, 프로바이더가 40개 이상이라는 것은 그만큼 유지보수·호환성·버그 표면이 넓다는 뜻이다. 열려 있는 이슈가 상당수라는 점도 빠르게 성장하는 프로젝트의 자연스러운 그림자다. 반면 Pi 같은 미니멀 하네스는 표면이 작아 예측 가능하다. 무엇을 미리 넣어 두느냐의 대가는 결국 복잡도다.

6.2 벤치마크 수치의 귀속 문제

Hashline의 편집 성공률·토큰 절감 같은 인상적인 수치는 대부분 저장소 자체 측정이다. 독립적인 제3자 벤치마크가 충분히 쌓이기 전까지는, 이 숫자를 마케팅이 아니라 실측으로 받아들이되 본인 워크로드로 재현해 보는 태도가 필요하다. 특정 모델(예: 빠른 소형 모델) 조합에서 나온 수치가 다른 모델에서도 같으리란 보장은 없다.

6.3 벤더 제품 대비 생태계·안정성

Claude Code나 Codex CLI는 모델과 에이전트를 같은 팀이 함께 최적화하고, 공식 문서·지원·업데이트 주기가 안정적이다. omp는 개방성과 자유도를 얻는 대신 이 안정성·생태계를 일부 포기한다. 실험과 개인 프로젝트에는 그 교환이 유리하지만, 규제 산업이나 SLA가 걸린 워크로드에서는 신중해야 한다.

7. 최근 흐름과의 연결 - 하네스가 곧 제품이 되는 시대

omp는 최근 두 흐름과 자연스럽게 이어진다. 하나는 로컬 LLM 에이전트 개발에서 짚은 "툴 검색·HITL·권한 경계"라는 실무 골격이다. omp의 넓은 도구 표면과 서브에이전트 오케스트레이션은 정확히 이 골격을 어떻게 설계하느냐의 문제와 겹친다. 다른 하나는 AI 코딩 세션의 맥락을 프로젝트 기억으로 남기기에서 다룬 휘발성 맥락 문제이고, omp의 Hindsight가 바로 그 대응이다. 흥미로운 지점은 omp가 "하네스 자체를 제품으로" 취급한다는 것이다. 모델이 상향 평준화되는 국면에서 차별화는 모델이 아니라 모델을 감싸는 도구 계층에서 나온다는 관점인데, 이는 omp만의 주장이 아니라 이 카테고리 전체가 향하는 방향이기도 하다.

8. 도입 전 체크리스트

omp든 유사한 터미널 에이전트든, 도입 전 최소한 아래 네 가지는 확인해야 한다.

  • 권한 경계 - 셸·파일 쓰기·코드 실행 권한이 어디까지 자동으로 허용되는지, 자동 승인과 수동 승인의 경계를 어떻게 그을지 먼저 정한다. 프로덕션 레포와 실험 레포를 분리하라.
  • 편집 신뢰성 - Hashline의 편집 성공률을 본인 코드베이스로 재현해 본다. 언어·프로젝트 규모에 따라 체감이 다를 수 있다.
  • 모델 라우팅과 비용 - 40개 이상 프로바이더 중 실제로 쓸 조합을 정하고, 프로바이더별 데이터 처리 정책과 프롬프트 학습 재사용 여부를 확인한다.
  • 거버넌스 - 팀 도입이라면 감사·SSO·정책 강제·지원 체계가 조직 요구를 충족하는지, 부족분을 어떻게 메울지 계획한다. 개인이라면 이 항목은 가벼워진다.

9. 결론 - 오늘 적용 가능한 3가지

omp는 진짜 문제 - 터미널이 코드의 의미를 이해하지 못한다는 오래된 빈틈 - 를 정확히 겨눴다. Pi의 미니멀 코어 위에 LSP·DAP·Hashline·Hindsight를 얹어 터미널을 IDE급으로 끌어올린다는 발상 자체는 유효하고 신선하다. 다만 그 대가로 복잡도, 아직 검증 중인 자체 벤치마크, 벤더 제품 대비 얇은 거버넌스라는 현실적 한계를 동반한다. 개방성과 안정성을 분리해서 보는 것이 정확한 접근이다.

9.1 실험·개인 프로젝트에 먼저 붙여라

고객 노출이 없는 사이드 프로젝트나 리팩터링·디버깅이 잦은 작업에 먼저 시험하고, Hashline 편집 신뢰성과 LSP·DAP의 실제 이득을 본인 기준으로 측정하라.

9.2 권한 경계를 먼저 설계하라

도구 표면이 넓은 만큼, 자동 승인 범위·샌드박스·격리 작업공간을 도입 첫날에 설정하라. 프로덕션 레포에 자동화를 무분별하게 풀지 마라.

9.3 벤더 제품과 역할을 나눠라

SLA·규제·조직 표준화가 걸린 워크로드는 Claude Code·Codex CLI 같은 검증된 계층에 두고, omp는 개방형 실험과 개인 생산성 도구로 역할을 분리하라. 더 넓은 맥락은 로컬 LLM 에이전트 개발과 AI 세션 기억 프로젝트를 참고하라.
