계기 — 에이전트가 수천 개가 되면 저장소의 기반은 무엇인가

2026년 10월 1일 Cloudflare 공식 블로그에 Dina Kozlov, Dillon Mulroy, Zebulon Piasecki 세 사람이 쓴 글이 올라왔다. 내용은 대회 공지다. Cloudflare는 Workers와 Artifacts를 이용해 「다음 Git 플랫폼」을 만들어 보라고 제안했다. GeekNews에는 2026년 10월 4일 등록된 항목으로 소개되었고, 요약은 대회 마감과 상금, 그리고 Artifacts가 오픈 베타라는 점에 집중한다.

공지의 앞부분은 대회 규정보다 전제를 먼저 말한다. 블로그는 GitHub가 사람이 코드를 쓰고, 저장소로 정리하고, 브랜치·커밋·이슈·풀 리퀘스트로 협업하는 세계를 위해 만들어졌다고 적는다. 그리고 다음 세대의 소프트웨어는 다른 종류의 개발자, 곧 에이전트가 만들게 된다고 말한다. 블로그가 에이전트의 일로 나열하는 것은 버그 수정, 기능 개발, 테스트, 코드 리뷰, 의존성 업데이트, 유지 보수 작업이다. 이 전제에서 공지의 핵심 질문이 나온다. 수백 개, 어쩌면 수천 개의 에이전트가 같은 코드베이스에서 동시에 일하는 세계에서 기반은 어떤 모습이어야 하는가.

블로그는 이 질문을 네 갈래의 미해결 문제로 풀어 놓는다. 에이전트가 다른 에이전트의 동시 작업을 알 수 있는가, 서로 충돌하는 변경을 어떻게 다루는가, 에이전트가 낸 결과물을 어떻게 검토하는가, 어떤 이유로 그렇게 고쳤는지를 어떻게 보존하는가. 대회는 이 네 갈래에 대한 구현물을 모으는 장치로 제시된다. 기존 GitHub에 에이전트를 붙이는 수준을 넘어 저장소, 브랜치, 풀 리퀘스트, 워크트리, 코드 리뷰, 병합 충돌 자체를 다시 생각해 보라는 요구다.

여기서 다루는 범위는 공지에 적힌 조건을 표와 목록으로 정리하고, 같은 대상을 두고도 출처에 따라 값이 갈리는 부분을 분리해 두는 것이다. 마감이 가깝고 요금이 곧 시작되는 서비스라서 날짜가 정확해야 쓸모가 있다. 대회의 가치 판단이나 참가 여부의 권유는 다루지 않는다. 같은 주제의 배경은 AI 네이티브 Git 호스팅을 다룬 Cursor의 Git 서비스 Origin 분석과 에이전트 런타임을 다룬 Cloudflare OS 분석에 있다. 아래는 그 글들이 다루지 않은 이번 대회의 조건과 Artifacts 문서의 수치에 한정한다.

대회 조건 한눈에 — 날짜·상금·제출물

아래 표는 블로그 공지에서 확인되는 항목과 확인되지 않는 항목을 한곳에 모은 것이다. 「—」는 공지에 해당 서술이 없다는 뜻이다. 마감 날짜를 적은 곳에는 시각도 시간대도 없다.

발표 시점——

표에서 두드러지는 것은 비어 있는 칸이다. 대회 공지는 보통 심사 기준과 참가 자격을 규정하는 문서와 함께 읽히지만, 이 블로그 글에는 그 서술이 없다. 따라서 이 표의 「—」를 「제한이 없다」로 읽으면 안 된다. 「공지에서 확인되지 않는다」일 뿐이며, 실제 제출 페이지나 약관에 별도 규정이 있을 가능성을 배제할 근거도 없다.

  • 날짜는 마감 하나만 적혀 있다. 시작일, 중간 점검, 결과 발표일은 없다.
  • 상금은 금액이 적힌 것이 1등 크레딧 하나이고, 나머지는 현물 성격의 참석 지원이다.
  • 제출물은 세 가지이며 모두 만든 사람이 준비해야 하는 문서·링크 성격이다.
  • 과제의 최소 요건은 한 문장으로 적혀 있고, 그 밖의 방향은 예시 수준이다.

제출물 세 가지와 라이선스 조건

블로그가 제출물로 요구하는 것은 세 가지다. 첫째는 만든 것을 보여 주는 5~10분 길이의 영상이다. 영상에는 무엇을 만들었는지, 그것으로 에이전트와 개발자가 무엇을 할 수 있게 되는지, 그리고 어떻게 동작하는지의 세 가지가 담겨야 한다. 둘째는 소스 코드 링크이며 허용적 오픈소스 라이선스로 제공되어야 한다. 괄호로 예시한 라이선스는 MIT, Apache, BSD다. 셋째는 프로젝트를 실행하거나 써 볼 수 있는 방법이다.

이 조건에서 라이선스 항목은 실무적으로 가장 먼저 걸리는 부분이다. 공지가 「허용적(permissive)」이라고 한정하면서 예시로 든 세 라이선스는 모두 사용·수정·재배포에 조건이 가벼운 계열이다. 공지는 이 밖의 라이선스가 허용되는지, 예를 들어 상호주의 조건이 강한 라이선스나 소스 공개를 제한하는 라이선스가 어떻게 취급되는지는 적지 않았다. 의존하는 외부 코드가 있다면 그 라이선스와 제출 라이선스가 충돌하지 않는지도 제출 전에 확인할 항목이다. 이 판단은 대회 규정이 아니라 일반적인 오픈소스 이용 관행에 속하며, 공지는 이 부분을 다루지 않는다.

  • 영상 — 5분 이상 10분 이하. 무엇을 만들었는지, 에이전트와 개발자가 무엇을 할 수 있게 되는지, 어떻게 동작하는지를 보여 주는 용도다.
  • 소스 링크 — MIT·Apache·BSD 계열의 허용적 라이선스로 공개된 것.
  • 실행 방법 — 프로젝트를 돌려 보거나 체험하는 방법의 안내.
  • 제출 양식 — 공지에 적혀 있지 않다. 별도 페이지가 있는지는 확인하지 못했다.

상금 구조 — 1등 크레딧과 상위 3팀 여행

상금은 두 층으로 나뉜다. 상위 3개 프로젝트는 팀당 최대 2명이 샌프란시스코에서 열리는 Cloudflare Connect에 참석해 만든 것을 소개한다. 블로그 문구는 「fly up to two members from each team to San Francisco」, 곧 팀당 최대 2명을 항공으로 보낸다는 것이며 숙박은 적지 않았다. 1등은 여기에 더해 25,000달러 상당의 Cloudflare 크레딧과 Connect 월요일 밤 VIP 연사 만찬 초대를 받는다. 블로그 문구는 크레딧과 만찬 초대를 함께 묶어 1등의 몫으로 적었다.

이 구조에서 읽을 수 있는 것과 읽을 수 없는 것을 나누면 다음과 같다. 읽을 수 있는 것은 현금이 아니라 크레딧이라는 점, 크레딧의 단위가 달러라는 점, 항공 지원이 상위 3팀에 걸린다는 점이다. 읽을 수 없는 것은 2등과 3등에 크레딧이 있는지, 크레딧을 쓸 수 있는 Cloudflare 제품의 범위와 기간이 어떻게 되는지, 항공 지원에 상한이 있는지, 숙박 같은 항공 외 경비가 지원되는지, 팀원 2명 한도가 팀 규모 제한을 뜻하는지다. 마지막 항목은 특히 조심해야 한다. 「팀당 최대 2명의 항공」은 지원의 규모를 말할 뿐 팀 인원 제한이라는 근거는 공지에 없다.

상금의 이점이 실제로 얼마인지는 다른 사람의 일이다. 크레딧은 사용처가 Cloudflare 서비스로 한정되는 가치이고, 그 가치는 환산하지 않는다. Artifacts의 요금표는 공개되어 있어 7절에서 요율을 볼 수 있다. 다만 그 요율로 25,000달러 크레딧이 얼마나 오래 가는지는 작업 횟수와 저장량 같은 사용 패턴에 달려 있어 여기서 계산하지 않는다.

  • 상위 3개 프로젝트: 팀당 최대 2명, 샌프란시스코 Cloudflare Connect로 가는 항공(숙박은 원문에 없음).
  • 1등: 25,000달러 상당 Cloudflare 크레딧 + Connect 월요일 밤 VIP 연사 만찬 초대.
  • 공지에 없는 것: 2등·3등의 크레딧, 크레딧의 유효 기간, 항공 지원의 상한과 숙박 지원 여부.

Artifacts는 무엇인가 — 문서가 정의하는 범위

대회의 바탕이 되는 Artifacts를 블로그는 「Git을 말하는 버전 관리형 파일시스템으로서 수백만 개 저장소까지 확장할 수 있는 것」이라고 정의한다. Cloudflare 개발자 문서의 개요는 「Git을 말하는 버전 관리 저장소」라고 쓰고, 원시 blob이 아니라 버전이 붙은 파일 트리를 저장한다고 설명한다. 변경 이력에 따르면 2026년 4월 16일에 비공개 베타로 시작했고, 2026년 10월 1일에 오픈 베타가 되었다. 오픈 베타의 대상은 Workers Paid 요금제 고객이며 Workers Free에서는 쓸 수 없다.

아래 표는 블로그와 개요 문서가 공통으로 언급하는 기능을 정리한 것이다. 각 기능이 내부에서 어떻게 구현되는지는 두 출처 모두 이 수준의 서술이어서 더 쓰지 않는다.

세 번째 열은 공지의 문장이 아니라 읽는 쪽의 해석이다. 블로그는 이 기능들이 대회 과제에 어떻게 쓰여야 하는지 지정하지 않았다. 문서 개요에 있는 「에이전트 세션을 별도 저장소나 브랜치에 기록한다」「fork·비교·병합으로 병렬 탐색을 한다」는 서술이 대회가 던진 질문과 같은 방향이라는 점까지만 확인된다.

  • 정의: 블로그는 「Git을 말하는 버전 관리형 파일시스템, 수백만 개 저장소까지 확장」, 문서는 「Git을 말하는 버전 관리 저장소」.
  • 시기: 2026-04-16 비공개 베타, 2026-05-18 Wrangler 명령, 2026-06-17 대시보드, 2026-10-01 오픈 베타(문서 변경 이력).
  • 대상: Workers Paid 요금제. Workers Free 불가.
  • 규모 서술의 차이: 블로그는 수백만 개, 변경 이력은 수천만 개라고 쓴다. 표현이 다르며 한도 문서의 저장소 수는 무제한이다.

공식 코드 샘플 두 개 읽기 — fork와 push 이벤트

블로그에는 코드 샘플이 둘 있다. 아래는 원문 샘플을 그대로 옮긴 것이다. 템플릿 리터럴의 백틱과 달러 기호는 HTML 문자 참조로 적었을 뿐 코드는 같다. 여기서 실행하지 않았고, 동작은 블로그가 샘플로 제시한 범위까지만 말한다.

using project = await env.ARTIFACTS.get("my-project");
                    const { defaultBranch } = await project.info();
                    const workspace = await project.fork(`task-${crypto.randomUUID()}`);
                    
                    using repo = await env.ARTIFACTS.get(workspace.name);
                    const instructions = await repo.readFile({
                      ref: defaultBranch,
                      path: "AGENTS.md",
                    });
                    
                    const agentTask = {
                      remote: workspace.remote,
                      token: workspace.token,
                      instructions: instructions ? await instructions.text() : null,
                    };

첫 샘플이 보여 주는 흐름은 네 단계다. 이름으로 프로젝트를 가져오고, 기본 브랜치를 조회하고, 작업마다 무작위 이름을 붙여 fork하고, fork된 저장소에서 기본 브랜치의 AGENTS.md를 읽는다. 그리고 에이전트에게 넘길 작업 객체에 원격 주소, 토큰, 지침 텍스트를 담는다. 눈에 띄는 점은 에이전트가 쓸 접근 정보가 fork된 작업 공간 하나에 묶여 나온다는 것이다. 원본 저장소를 직접 열어 주는 것이 아니라 작업별 사본의 원격과 토큰을 주는 모양새다. 이것이 동시에 여러 에이전트가 일하는 상황에서 충돌을 줄이는 설계 방향이라는 설명은 샘플 코드에서 읽히는 해석이며, 블로그가 그렇게 말한 것은 아니다.

export default {
                      async queue(batch, env) {
                        for (const message of batch.messages) {
                          const event = message.body;
                          if (event.type !== "cf.artifacts.repo.pushed") continue;
                    
                          await env.REVIEW_WORKFLOW.create({
                            params: {
                              namespace: event.source.namespace,
                              repo: event.source.repoName,
                              ref: event.payload.ref,
                              commit: event.payload.after,
                            },
                          });
                        }
                      },
                    };

둘째 샘플은 큐 소비자다. 메시지를 순회하면서 이벤트 타입이 push가 아니면 건너뛰고, push이면 네임스페이스·저장소 이름·ref·커밋을 인자로 REVIEW_WORKFLOW라는 바인딩에 워크플로 인스턴스를 만든다. 블로그의 설명대로라면 이 샘플은 push에 반응해 코드 리뷰 흐름을 시작하는 구조다. 이벤트 이름의 형식(cf.artifacts.repo.pushed)과 페이로드의 필드(source.namespace, source.repoName, payload.ref, payload.after)가 샘플에 그대로 드러난다.

  • 두 샘플 모두 Workers 런타임의 바인딩(env.ARTIFACTS, env.REVIEW_WORKFLOW)을 쓴다.
  • 첫 샘플의 using 선언은 자원이 범위를 벗어나면 정리되는 구문으로 쓰였다. 정리가 정확히 무엇을 하는지는 샘플에 설명이 없다.
  • 샘플은 일부분이며, REVIEW_WORKFLOW의 정의와 큐 설정은 포함되지 않았다.
  • 샘플의 지침 파일은 AGENTS.md이며, 에이전트 지침을 저장소 안 파일에서 읽는 관행을 따른 것으로 보인다.

요금과 한도 — 과금 시작일이 둘로 적힌 이유

요금은 두 축이다. 블로그는 저장소 작업 횟수와 저장된 데이터 양에 기반한다고 적는다. 개발자 문서의 요금 페이지는 구체적인 값을 적는다. 작업은 월 처음 10,000건 이후 1,000건당 0.15달러, 저장 용량은 월 처음 1GB 이후 GB-월당 0.50달러다. GB-월은 30일 청구 기간 동안 일별 최대 저장량을 평균한 값이다.

문제는 과금 시작일이다. 블로그는 2026년 10월 15일부터 Artifacts 사용량에 과금한다고 적는다. 개발자 문서의 요금 페이지는 10월 14일부터 작업과 저장에 과금한다고 쓰고, 변경 이력의 10월 1일 항목도 10월 14일이라고 쓴다. 하루 차이는 시간대 해석으로도 생길 수 있는 크기이지만, 두 출처 어느 쪽도 시간대를 적지 않았다. 원인은 여기서 확정할 수 없다. 확실한 것은 둘 다 10월 중순이며, 대회 마감 날짜(10월 14일)와 같은 주에 요금이 시작된다는 점이다. 그래서 대회 작품을 운영하는 쪽은 마감 이후 며칠 안에 요금이 붙기 시작한다고 보고 계산해 두는 것이 안전하다.

항목값출처
작업(operations)월 처음 10,000건 이후 1,000건당 0.15달러개발자 문서 요금 페이지
저장(storage)월 처음 1GB 이후 GB-월당 0.50달러개발자 문서 요금 페이지
과금 시작일2026-10-15대회 블로그
과금 시작일2026-10-14문서 요금 페이지·변경 이력
저장소 하나의 저장 한도1GB플랫폼 한도 문서
파일·blob 하나의 한도32MB플랫폼 한도 문서
계정당 저장 한도1TB(요청 시 상향 가능)플랫폼 한도 문서
요청률제어 평면은 네임스페이스당, Git 요청은 저장소당 10초에 2,000건플랫폼 한도 문서
저장소·네임스페이스 수무제한플랫폼 한도 문서

한도 중 설계에 직접 영향을 주는 것은 저장소당 1GB와 blob당 32MB이다. 에이전트가 작업마다 저장소를 fork하는 구성에서는 저장소 수가 무제한이고 저장은 합산 1TB까지이므로, 저장소 하나의 크기보다 작업 공간을 정리하는 주기가 청구액에 더 직접적으로 영향을 줄 수 있다. 이는 요금표에서 끌어낸 추론이며 실제 청구 방식은 청구서로 확인해야 한다.

  • 요금 문서는 작업(operation)의 예로 create·push·pull·clone 같은 저장소 동작을 든다. 이 예시 밖의 요청이 어떻게 세어지는지는 확인하지 못했다.
  • 네임스페이스 이름은 2~63자이고 영문자 또는 숫자로 시작하며 이후 영문자·숫자·마침표·밑줄·하이픈을 쓸 수 있다.
  • 무료 할당(작업 10,000건, 저장 1GB)은 Workers Paid 계정 안에서의 값이며 Workers Free에는 적용되지 않는다.

대회가 던진 질문을 설계 항목으로 옮기면

블로그의 질문은 구현 항목으로 바꿀 때 구체성이 생긴다. 아래 목록은 블로그가 열거한 질문과 그에 대응해 읽을 수 있는 Artifacts의 도구를 연결한 것이다. 이 대응은 해석이며, 대회가 이 방향을 요구한다는 뜻이 아니다. 블로그가 요구한 최소 요건은 여러 에이전트가 변경을 동시에 처리하는 모습이다.

  • 동시 작업의 인지 — 한 에이전트가 다른 에이전트의 진행 중인 변경을 아는가. 이벤트 구독의 push·fork 이벤트가 재료가 될 수 있다.
  • 충돌하는 변경 — 같은 파일을 다른 방향으로 고친 변경들. 작업별로 fork해 격리한 뒤 병합 시점에 다루는 방식이 샘플 1의 구조에서 읽히는 한 가지 방향이다.
  • 산출물 검토 — 샘플 2의 push 이벤트가 워크플로를 시작하는 구조가 검토 자동화의 한 형태다.
  • 변경 이유의 보존 — 블로그가 「에이전트 컨텍스트를 보존하는 새로운 방법」을 언급한다. 저장 방식은 지정되어 있지 않다.
  • 동시 비교와 선택 — 여러 변경을 동시에 비교하고 무엇을 배포할지 정하는 단계. 블로그가 예로 든 항목이다.

이 목록에서 어느 하나가 필수인지는 공지에 없다. 심사 기준이 적혀 있지 않으므로 어느 쪽을 강조하는 작품이 유리한지는 알 수 없다. 확실히 말할 수 있는 것은 공지가 개별 기능이 아니라 기반(foundation)을 다시 생각하라고 요청했다는 점이다.

조건을 읽고 나서 정해 둘 것

참가를 권하려는 항목이 아니라, 공지의 조건에서 직접 도출되는 준비 사항을 정리한 것이다. 참가할지는 각자의 판단에 속한다.

  • 요금제 — Artifacts가 Workers Paid 전용이므로 사용하려면 해당 요금제 계정이 필요하다. 요금제 가격은 확인 범위 밖이다.
  • 마감 여유 — 마감 시각과 시간대가 적혀 있지 않으므로 마감 날짜 하루 전에 제출을 끝내는 것이 가장 단순한 대비다.
  • 라이선스 정합성 — 소스는 MIT·Apache·BSD 중 하나로 공개해야 한다. 의존 라이브러리의 라이선스와 맞는지 먼저 본다.
  • 영상 길이 — 5~10분 범위 안에 들어가야 한다. 5분 미만이거나 10분을 넘는 경우를 어떻게 취급하는지는 공지에 없다.
  • 재현 가능성 — 실행 방법 안내가 제출물이므로 환경 변수·토큰 같은 비밀 값을 소스에 넣지 않고 설정 안내로 분리한다.
  • 과금 시작 이후의 비용 — 작품을 마감 뒤에도 켜 둘 계획이라면 10월 14일 또는 15일부터 작업·저장 요금이 붙는 계정에서 도는 것으로 계산한다.
  • 데이터 관할 — Artifacts는 데이터 저장·처리 지역을 미국 또는 EU로 고를 수 있다. 시연에 실제 코드를 쓴다면 어느 지역에 두는지 정해 둔다.

확인하지 못한 것

  • 마감 시각과 시간대. 블로그에는 날짜만 있다.
  • 심사 기준, 심사위원, 결과 발표 시점, 참가 자격, 팀 규모 제한. 블로그에 서술이 없다.
  • 제출 경로와 양식. 별도 제출 페이지가 있는지 확인하지 않았다.
  • 2등·3등의 크레딧 여부, 크레딧의 사용 범위와 유효 기간, 항공 지원의 한도와 숙박 지원 여부.
  • 과금 시작일이 블로그(10월 15일)와 문서(10월 14일)에서 다르게 적힌 이유. 어느 쪽이 기준인지는 확인하지 못했다.
  • create·push·pull·clone 이외의 요청이 작업 한 건에 해당하는지. 요금 문서가 든 예시 밖의 범위는 확인하지 못했다.
  • Workers Paid 요금제의 가격과 포함 항목. 확인 범위 밖이다.
  • 샘플 코드의 실행 결과. 코드를 실행하지 않았다. Artifacts API 상세 문서는 열어 보지 않았다.
