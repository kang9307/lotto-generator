Shell Quoting Rules - What Each Quote Actually Blocks

Single quotes, double quotes and ANSI-C quoting, separated by real output

2026-07-29 Dev & Infra

Introduction: two missing quotes emptied a directory

A fresh scratch directory was created with three files in it. Two have ordinary names. The third has a name that is literally a single star. The goal was to delete only that star file, so its name was stored in a variable and handed to rm. Here is what happened.

$ ls -1
*
keep1.txt
keep2.txt

$ f='*'
$ rm $f
$ ls -1
(empty)

One file was supposed to go. The entire directory was emptied instead. Nothing was mistyped. rm did nothing unusual. The shell replaced $f with *, and then expanded that * into a list of filenames a second time. Two quote characters would have prevented all of it.

The usual advice after an incident like this is "quote your variables". True, but it is not a rule. It does not say which quote to use, nor what that quote blocks and what it lets through. So the same person later wraps an awk program in double quotes and watches the dollar signs get eaten. Opposite direction, identical root cause: not knowing which switch each quote flips.

This article does not list definitions. It runs every case and shows what single quotes, double quotes, backslash and ANSI-C quoting actually block. The grammar was checked against the GNU Bash Reference Manual and the POSIX specification; the behaviour was produced by running commands in a scratch directory. Every block of output below is text that actually appeared on screen. At the end there is a single decision table mapping situation to quote to reason.

One boundary up front. Handling filenames with spaces through find and xargs is covered separately in the find and xargs whitespace trap. This article is about the quoting syntax itself. Whether a script is safe to run twice lives in idempotent shell scripts, and whether you can know the result before running lives in how to build a real dry run.

2. The order the shell reads a line in - which stage does a quote switch off

Quoting feels confusing because people think a quote "makes a string". In the shell it does no such thing. A quote is a switch that turns off some of the processing stages that were going to happen anyway. Once you know which switch turns off which stage, everything becomes predictable.

Roughly, this is what bash does to a line before running it.

one input line
  1. brace expansion       a{1,2}   ->  a1 a2
  2. tilde expansion       ~        ->  home directory
  3. parameter expansion, command substitution, arithmetic expansion
                           $var  $(cmd)  `cmd`  $((1+1))
  4. word splitting        cut into fields on IFS      <- whitespace incidents
  5. pathname expansion    *  ?  [...]  ->  filenames  <- star incidents
  6. quote removal         strip the remaining quote characters
  -> execute

The key point is that stages 4 and 5 come after stage 3. What a variable expands to can be split again, and can swell again. That is exactly the incident in the introduction: $f became * at stage 3, and that * became a file list at stage 5.

Quoting turns off parts of this sequence. Which form turns off which part is the whole subject of this article.

Form$ expansionBackquoteBackslash! historyWord splittingGlobbing
unquotedpassespassespassespasseshappenshappens
single '...'blockedblockedblockedblockedblockedblocked
double "..."passespassespartlyinteractive onlyblockedblocked
ANSI-C $'...'blockedblockedinterpretedblockedblockedblocked
backslash \xblockedblockedblockedblockedblockedblocked

The columns worth staring at are the two on the right. Single quotes and double quotes block word splitting and globbing identically. Ninety percent of production incidents live in those two columns. Which means that once you are asking "which quote should I use here", you are already halfway safe. The real problem is the places with no quotes at all.

3. Single quotes - literal with no exceptions

Single quotes have exactly one rule: every character inside is taken literally. There are no exceptions. The Bash Reference Manual puts it this way.

Enclosing characters in single quotes preserves the literal value of each character within the quotes. A single quote may not occur between single quotes, even when preceded by a backslash.

Here is the run. The same strings were wrapped in single quotes and handed to printf.

$ printf '%s\n' '$name'
$name
$ printf '%s\n' '`printf ran`'
`printf ran`
$ printf '%s\n' '\n  \t  \\'
\n  \t  \\
$ printf '%s\n' '!!'
!!
$ printf '%s\n' 'a "b" c'
a "b" c
$ printf '%s\n' '${name}  $(printf ran)  $((1+1))'
${name}  $(printf ran)  $((1+1))

Not one expansion took place. The important detail is that even the backslash is not special: \\ came out as \\. Inside double quotes it would have collapsed to a single \ (see section 4).

That is why single quotes are the tool for protecting another language's syntax from the shell. An awk program, a sed expression, a regular expression, a find pattern, a command string to hand to another shell — all of them belong in single quotes.

The price is real: a single quote cannot appear inside single quotes. Here is why trying to escape it with a backslash fails.

$ printf '%s\n' 'it\'"'"'s'
it\'s

$ bash -c "printf '%s\n' 'it\'s'"
bash: -c: line 1: unexpected EOF while looking for matching `''

The first line looks odd but is simple. The string 'it\' ended at the quote after the backslash, and the backslash survived as a plain character. In the second example the quotes then failed to pair up and parsing died outright. This is the specification working exactly as written: a backslash is not an escape character inside single quotes.

So to get a single quote into single-quoted text you must close, add one character some other way, and reopen. Four spellings exist and all produce the same bytes.

$ printf '%s\n' 'it'"'"'s'      # close, one char in double quotes, reopen
it's
$ printf '%s\n' 'it'\''s'       # close, one char via backslash, reopen
it's
$ printf '%s\n' "it's"          # just use double quotes
it's
$ printf '%s\n' $'it\'s'        # ANSI-C quoting (section 8)
it's

$ printf '%s' 'it'\''s' | od -c
0000000   i   t   '   s
0000004

The od -c line is the proof: the bytes the shell actually delivered are the four characters it's. The famous '\'' idiom is not magic — it is close, one character, reopen glued together.

4. The four things double quotes let through

Double quotes punch exactly four holes in the single-quote behaviour. The Bash Reference Manual states it directly.

Enclosing characters in double quotes preserves the literal value of all characters within the quotes, with the exception of $, `, \, and, when history expansion is enabled, !.

The strings from section 3, rerun with double quotes instead.

$ name=world
$ printf '%s\n' "$name"
world
$ printf '%s\n' "`printf ran`"
ran
$ printf '%s\n' "\n  \t  \\"
\n  \t  \
$ printf '%s\n' "!!"
!!
$ printf '%s\n' "a "b" c"
a b c
$ printf '%s\n' "${name}  $(printf ran)  $((1+1))"
world  ran  2

Line by line.

  • $name became world — parameter expansion passes
  • The backquote ran and produced ran — command substitution passes
  • \\ collapsed to a single \ — backslash partly passes
  • \n and \t stayed as written — a backslash is not special before arbitrary characters
  • "a "b" c" became a b c — the quoting closed in the middle and reopened

The third and fourth items trip up the most people. Inside double quotes a backslash acts as an escape only before a fixed set of five characters. The manual names them.

The backslash retains its special meaning only when followed by one of the following characters: $, `, ", \, or newline. Within double quotes, backslashes that are followed by one of these characters are removed. Backslashes preceding characters without a special meaning are left unmodified.

So "\n" is not a newline — it is the two characters backslash and n. To get a real newline, let a printf format string produce it, or use the ANSI-C quoting from section 8.

The fourth item, the exclamation mark, is conditional. History expansion is on only in interactive shells by default. Scripts are safe, but commands typed at a terminal are still exposed today. Two lines were fed to an interactive bash.

$ echo hello there
hello there
$ echo "wow!!"
wowecho hello there          <- !! inside double quotes became the previous command
$ echo 'wow!!'
wow!!                        <- single quotes block it

Feeding the same two lines to an interactive shell in POSIX mode gives a different answer — precisely the exception the manual documents.

$ bash --norc -i
$ echo "wow!!"
wowecho hello there

$ bash --norc --posix -i
$ echo "wow!!"
wow!!

In short, double quotes are the tool for "I want the value in, but I do not want it split." Use them when a variable or a command substitution has to sit inside; otherwise single quotes are safer.

5. Unquoted expansion - where most incidents actually come from

This is the centre of the article. The previous two sections were about what goes in. This one is about how many pieces come out. Almost all production incidents live here.

The method is simple: a function that prints the number of arguments and their contents, called once with quotes and once without.

count() {
  printf 'argc=%d\n' "$#"
  local i=1
  for a in "$@"; do printf '  [%d] <%s>\n' "$i" "$a"; i=$((i+1)); done
}

The directory holds three files: my report.txt, notes.txt and keep.txt.

$ f='my report.txt'

$ count $f
argc=2
  [1] <my>
  [2] <report.txt>

$ count "$f"
argc=1
  [1] <my report.txt>

$ wc -c $f
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
exit=1

$ wc -c "$f"
0 my report.txt
exit=0

One value split into two arguments, so wc went looking for two files that do not exist, and the exit status was 1. That is the better case, because the error is visible. The dangerous case is the one that succeeds quietly.

$ pat='*.txt'

$ count $pat
argc=3
  [1] <keep.txt>
  [2] <my report.txt>
  [3] <notes.txt>

$ count "$pat"
argc=1
  [1] <*.txt>

$ empty=''
$ count $empty
argc=0
$ count "$empty"
argc=1
  [1] <>

Three things are visible at once.

  • Unquoted $pat swelled into three files. The value was unambiguously one string
  • Interestingly my report.txt did not split and stayed one field. Word splitting happens before globbing, so glob results are not split again
  • An unquoted empty value disappears from the argument list. Quoted, it remains as one empty-string argument

That last item is the classic conditional trap.

$ empty=''
$ if [ -n $empty ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
NON-EMPTY          <- wrong

$ if [ -n "$empty" ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
empty              <- right

$ two='a b'
$ [ -n $two ]
bash: [: a: binary operator expected
exit=2
$ [ -n "$two" ]
exit=0

The first became [ -n ]. A one-argument test is true when that argument is not the empty string, so the string -n itself evaluated as true. The second became [ -n a b ], a syntax error. Depending on the value, the same code gives you a false positive, a syntax error, or the right answer.

And then there is the incident from the introduction. When an unquoted expansion also reaches globbing, the result is not recoverable.

### directory state (the star is the filename itself)
*
keep1.txt
keep2.txt

### A) rm $f    (f='*')
$ rm $f
$ ls -1
    (empty)

### B) rm -- "$f"    same value, quoting is the only difference
$ rm -- "$f"
$ ls -1
    keep1.txt
    keep2.txt

A and B differ by two quote characters and a --. The outcomes are everything deleted and one file deleted. For the record, -- is a separate mechanism from quoting: it marks "operands from here on, not options" and protects filenames that begin with a dash.

Loop variables obey the same rule. Putting a list into one string loses the game before it starts.

$ list='keep1.txt keep2.txt'
$ for f in $list; do printf ' <%s>' "$f"; done
 <keep1.txt> <keep2.txt>

$ arr=('quarterly report.txt' 'keep1.txt')
$ for f in "${arr[@]}"; do printf ' <%s>' "$f"; done
 <quarterly report.txt> <keep1.txt>

A string list has no way to represent a name containing a space. When you need a list, use an array (section 7). If a filename contains a newline, counting by lines collapses entirely; that is outside this article's scope and belongs to the find and xargs whitespace trap. Still, it is worth noting that the number the shell sees and the number of lines ls prints are not the same.

$ ls -1 | cat -A
    *$
    keep1.txt$
    keep2.txt$
    two$
    lines.txt$

$ n=0; for f in *; do n=$((n+1)); done; echo "count=$n"
    count=4

Five lines, four files. The Word Splitting section of the Bash manual limits what gets split like this.

The shell scans the results of parameter expansion, command substitution, and arithmetic expansion that did not occur within double quotes for word splitting. Words that were not expanded are not split.

The whole condition is "that did not occur within double quotes". One pair of double quotes skips stage 4 entirely.

6. The four positional-parameter forms - counting the arguments

Forwarding a script's arguments to another command is a daily task. There are four ways to spell it and all four behave differently. Four arguments were passed to a function that counts with $#. The arguments are 'a b', 'c', '' (empty) and 'd*e'.

$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a> <b> <c> <d*e>
quoted *:  argc=1 | <a b c  d*e>
bare *:    argc=4 | <a> <b> <c> <d*e>

Only quoted "$@" delivered the original four. Unquoted $@ also reports 4, but the contents are wrong: a b split in two and the empty argument vanished, so the count matched by pure coincidence. Coincidences like that hide bugs for a long time.

The same experiment with IFS set to a comma.

$ IFS=,
$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a b> <c> <> <d*e>
quoted *:  argc=1 | <a b,c,,d*e>
bare *:    argc=4 | <a b> <c> <> <d*e>

### with no arguments at all
quoted @:  argc=0 |
bare @:    argc=0 |
quoted *:  argc=1 | <>
bare *:    argc=0 |

Two things surface. First, the character "$*" joins with became the first character of IFS. Second, with no arguments "$@" gives zero arguments while "$*" gives one empty-string argument. That difference quietly changes behaviour under set -u and in argument-count checks.

Against a real command it looks like this.

$ set -- 'my report.txt' 'notes.txt'

$ wc -c "$@"
0 my report.txt
0 notes.txt
0 total

$ wc -c $@
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

$ wc -c "$*"
wc: 'my report.txt notes.txt': No such file or directory

"$@"exactly the argument countpreservedpreservedthe default for forwarding
$@whatever splitting leaveslostsplitalmost never

$*whatever splitting leaveslostsplitalmost never

The rule is short. Use "$@" to forward arguments and "$*" to build one human-readable line. The two unquoted forms have almost no legitimate use in practice.

7. Arrays and quoting - only one form preserves the originals

Arrays follow the same structure: four ways to expand, one that keeps the originals. Verified with a four-element array.

$ arr=('my report.txt' 'notes.txt' '' 'a*b')

"${arr[@]}"      argc=4 | <my report.txt> <notes.txt> <> <a*b>
${arr[@]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>
"${arr[*]}"      argc=1 | <my report.txt notes.txt  a*b>
${arr[*]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>

$ echo "${#arr[@]}"     # number of elements
4
$ echo "${#arr[0]}"     # length of element 0
13

It is worth noting alongside that ${#arr[@]} and ${#arr[0]} return entirely different things. The first is a count, the second a length.

Why an array matters when assembling a command line shows up in this contrast.

$ opts=(-c)
$ files=('my report.txt' 'notes.txt')

$ wc "${opts[@]}" "${files[@]}"
0 my report.txt
0 notes.txt
0 total

$ wc ${opts[*]} ${files[*]}
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

And then there is the common antipattern of storing an entire command line in a string variable. Why it cannot work is the clearest demonstration of what quoting really is.

$ cmdline='wc -c "my report.txt"'
$ $cmdline
wc: '"my': No such file or directory
wc: 'report.txt"': No such file or directory
exit=1

The quotes are right there, so why does it fail? Because quoting does not operate inside variable values. The shell processes quotes while reading source text, and that processing is already over. Quote characters left inside a variable are just characters. That is why wc received arguments with literal quote marks attached.

The sentence to remember
Quotes attach to code, not to values. A quote character sitting inside a variable value means nothing to the shell. If you must build a command line dynamically, use an array rather than a string; and if that is impossible, let the shell add the quoting for you with printf %q (section 12).

For the record, before bash 4.4 expanding an empty array as "${arr[@]}" under set -u raised an error. On the environment used here (5.2.37) it is fine.

$ empty=()
$ set -u
$ show "${empty[@]}"
argc=0 |
survived: exit=0

8. ANSI-C quoting - the one hole in single quotes

Single quotes block everything, as stated. There is one form that escapes that rule: a dollar sign in front, $'...'. The manual calls it "a special kind of single quotes". Variables still do not expand, but backslash escapes are decoded.

$ printf '%s' 'A\tB\nC' | od -c
0000000   A   \   t   B   \   n   C
0000007

$ printf '%s' $'A\tB\nC' | od -c
0000000   A  \t   B  \n   C
0000005

The same text is 7 bytes and 5 bytes. The $'...' version became a real tab and a real newline. The manual lists what is supported: octal \nnn, hex \xHH, Unicode \uHHHH and \UHHHHHHHH, plus \a \b \e \f \n \r \t \v \\ \' \" \?. Several were run to confirm.

$ printf '%s' $'\x41\x42' | od -c
0000000   A   B
$ printf '%s' $'\101\102' | od -c
0000000   A   B
$ printf '%s' $'é' | od -c
0000000 303 251
$ printf '%s' $'\e[0m' | od -c
0000000 033   [   0   m
$ printf '%s' $'\cG' | od -c
0000000  \a

It is essential to remember that variables are still not expanded.

$ name=world
$ printf '%s\n' $'hello $name'
hello $name

The use case is clear: when a delimiter has to be a tab or a newline. Setting IFS, or the delimiter arguments of sort -t, cut -d and join -t. But $'...' is not in the POSIX specification. In dash nothing expands at all.

$ dash -c "printf '%s' \$'A\tB' | od -c"
0000000   $   A   \   t   B
0000005

The dollar sign survived as a character and \t stayed as two characters. When portability matters, build the value with printf and store it in a variable instead. The bytes come out the same.

$ TAB=$(printf '\t')
$ NL=$(printf '\nx'); NL=${NL%x}
$ printf '%s' "A${TAB}B${NL}C" | od -c
0000000   A  \t   B  \n   C
0000005

The reason NL gets an x appended and then stripped is that command substitution removes all trailing newlines (section 9). Without those two steps NL would be the empty string.

9. Command substitution and backquotes - inner quoting is independent

Quoting inside $(...) is entirely separate from the quoting outside it. Even in the middle of double quotes, the inside is a fresh context.

$ printf '%s\n' "outer $(printf '%s' 'inner literal $HOME') outer"
outer inner literal $HOME outer

$ printf '%s\n' "$(printf '[%s]' "$(printf '%s' 'deep')")"
[deep]

The outer context is double-quoted, yet the inner single quotes worked normally and $HOME survived. Three levels of nested double quotes also went through untouched. Not having to count quotes when nesting is the practical advantage of $(...).

Backquotes are different. The same nesting with backquotes fails to parse.

$ bash -c 'printf "%s\n" "`printf "[%s]" "`printf "%s" deep`"`"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
printf %s deep

A backquote uses the same character to open and to close, so nesting boundaries are unknowable. On top of that, a backslash loses one more layer inside backquotes. That difference changes actual values.

$ printf '%s\n' "$(printf '%s' 'a\tb')"
a\tb
$ printf '%s\n' "`printf '%s' 'a\tb'`"
a\tb

$ printf '%s\n' "$(printf 'a\\b')"
a\b
$ printf '%s\n' "`printf 'a\\b'`"
a

The last two diverged: $(...) gave a\b, the backquote gave a. The backquote ate one backslash first, leaving printf 'a\b', which printf then decoded as a backspace. That gives three reasons to avoid backquotes.

  • They cannot nest — the open and close characters are identical, so the boundary is undecidable and parsing fails as shown above
  • They eat one more backslash — identical arguments produced different result strings
  • They are hard to read — a backquote and a single quote are nearly indistinguishable in many fonts

POSIX specifies both forms, and $(...) works fine in dash too. There is no reason to write backquotes in new code.

Command substitution results also split and swell when unquoted, exactly like variables.

$ show $(printf '%s\n' 'my report.txt')
argc=2 | <my> <report.txt>
$ show "$(printf '%s\n' 'my report.txt')"
argc=1 | <my report.txt>

$ show $(printf '%s\n' '*.txt')
argc=1 | <my report.txt>
$ show "$(printf '%s\n' '*.txt')"
argc=1 | <*.txt>

### trailing newlines are stripped either way
$ printf '%s' "$(printf 'x\n\n\n')" | od -c
0000000   x
0000001

The third example is the nasty one. The command printed the literal text *.txt, and dropping the quotes turned it into a filename that happened to be in the directory. The original string appears nowhere on screen.

10. IFS - the variable that decides what counts as a boundary

Word splitting uses IFS. The default is space, tab and newline, and changing it changes splitting completely. Yet a double-quoted value is unaffected no matter what IFS is, because no splitting happens at all.

$ line='root:x:0:0::/root:/bin/bash'

### default IFS
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>

### IFS=:
$ IFS=:
$ show $line
argc=7 | <root> <x> <0> <0> <> </root> </bin/bash>
$ show "$line"
argc=1 | <root:x:0:0::/root:/bin/bash>

The quoted form is always 1, whatever IFS holds. That is why "when in doubt, double quotes" holds up: however the surrounding code has mangled IFS, a quoted expansion does not move.

It is also worth knowing that whitespace IFS and non-whitespace IFS behave differently.

$ gaps='a   b'
$ show $gaps
argc=2 | <a> <b>                     <- runs of whitespace collapse

$ path='/usr/bin:/bin::/usr/local/bin'
$ IFS=:
$ show $path
argc=4 | </usr/bin> </bin> <> </usr/local/bin>   <- the empty field survives

$ IFS=
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>             <- empty IFS means no splitting

Exactly as the manual describes. When IFS is all whitespace, a run of whitespace is one delimiter and null fields arise only from quoting. When IFS contains a non-whitespace character, each such character is a delimiter, so adjacent ones produce a null field.

IFS also decides the character "$*" joins with.

$ set -- one two three
$ IFS=:
$ printf '%s\n' "$*"
one:two:three
$ for a in "$@"; do printf ' <%s>' "$a"; done
 <one> <two> <three>

The correct way to use IFS in practice is to scope it to a single command. Change it globally and every unquoted expansion after that point is affected.

$ printf '%s\n' "$line" | { IFS=: read -r user pw uid gid gecos home shell
    printf 'user=<%s> uid=<%s> home=<%s> shell=<%s>\n' "$user" "$uid" "$home" "$shell"; }
user=<root> uid=<0> home=</root> shell=</bin/bash>

### changed globally and forgotten
$ IFS=,
$ files='a,b'
$ show $files
argc=2 | <a> <b>         <- possibly not where you wanted it
$ show "$files"
argc=1 | <a,b>

An assignment placed in front of a command, as in IFS=: read -r ..., applies to that command only. Adding -r to read is defence of the same kind as quoting: without it, backslashes in the input are treated as escapes and disappear.

11. Where quotes are unnecessary, and where they must come off

"Quote everything" is not a rule either. There are places where quoting makes no difference, and places where quoting changes the meaning. Both were separated by running them.

$ v='my report.txt'
$ star='*.txt'

### A) right-hand side of an assignment: no splitting, no globbing
$ a=$v
$ b=$star
$ printf 'a=<%s>\n' "$a"
a=<my report.txt>
$ printf 'b=<%s>\n' "$b"
b=<*.txt>

The right-hand side of an assignment is safe without quotes. Many people still quote it out of habit, and the reason is not safety but consistency: create one exception and the next reader has to work out where the exception ends.

Conversely, the pattern position in case and [[ ]] changes meaning with quoting.

$ v='my report.txt'
$ p='my*'

$ case "$v" in
    $p)  echo 'pattern unquoted -> treated as a glob, matched' ;;
    *)   echo 'no match' ;;
  esac
pattern unquoted -> treated as a glob, matched

$ case "$v" in
    "$p") echo 'pattern quoted -> literal, matched' ;;
    *)    echo 'no match (the literal text my* is not this name)' ;;
  esac
no match (the literal text my* is not this name)

[[ ]] is the same. The left side is never split so quoting is optional, but the right side is a pattern, so quoting turns it into a literal.

$ [[ $v == 'my report.txt' ]]  && echo 'left side unquoted: fine'
left side unquoted: fine
$ [[ $v == $p ]]   && echo 'right side unquoted: glob match'
right side unquoted: glob match
$ [[ $v == "$p" ]] || echo 'right side quoted: no match (as intended)'
right side quoted: no match (as intended)

### the same comparison with single brackets
$ [ $v == 'my report.txt' ]
bash: [: too many arguments

[[ ]] is shell syntax and does not word-split internally. [ ] is a command and receives arguments. That is why identical code passes on one side and fails with an argument-count error on the other.

This is also the place to record that glob results are not split again.

$ show *.txt
argc=2 | <my report.txt> <notes.txt>
$ show "$star"
argc=1 | <*.txt>
$ show $star
argc=2 | <my report.txt> <notes.txt>

A *.txt written directly in the source is meant to be unquoted; quoting it turns a glob into a literal string. So there are only two legitimate reasons to drop the quotes: deliberate word splitting and deliberate globbing. Everywhere else, quote.

  • A glob pattern written directly in the code: for f in *.log — leave it unquoted
  • A glob pattern held in a variable that you want treated as a glob: the right side of case and [[ ]]
  • Splitting an option string into several arguments — although an array is safer
  • Everything else: use double quotes
If you drop them, leave a line
Add a comment such as # intentional split wherever you deliberately omitted quotes. Without it, the next person either reads it as an oversight and adds quotes (changing behaviour), or reads a genuine omission as intentional and leaves it.

12. eval and two-layer shells - when quoting is stripped once more

Everything so far assumed the shell reads the text once. When the same string is read twice — through eval, a remote shell, a container invocation — one more layer of quoting comes off.

$ greeting=hello
$ v='$greeting'

$ printf 'plain : %s\n' "$v"
plain : $greeting

$ eval "printf 'eval  : %s\n' \"$v\""
eval  : hello

Same variable, but going through eval made the value interpreted one more time. If the value contains a command separator, what follows is predictable.

$ name='keep.txt; echo INJECTED'

$ printf '%s\n' "$name"
keep.txt; echo INJECTED

$ eval "printf '%s\n' $name"
keep.txt
INJECTED

Printed with quotes it is one value; run through eval everything after the semicolon executes as a separate command. That is the reason eval has its reputation. The safe condition is singular: use it only when every part of the string is something you produced yourself.

The same thing happens when handing a command to a second shell. The reproduction below uses bash -c, but remote execution and container execution work identically: the string is parsed again on the far side.

$ target='my report.txt'

$ bash -c "wc -c $target"
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total

$ bash -c "wc -c \"$target\""
0 my report.txt

$ bash -c "wc -c $(printf '%q' "$target")"
0 my report.txt

Running the question of which layer eats the dollar sign removes the confusion for good.

$ name=outer

$ bash -c "printf 'A: %s\n' $name"
A: outer          <- the outer shell expanded it and baked it into the string

$ bash -c 'printf "B: %s\n" $name'
B:                <- the inner shell expanded it, and it has no name variable

$ bash -c 'printf "C: %s\n" "$0"' "$name"
C: outer          <- the value went as an argument, no string assembly at all

C is the right shape. Pass the value as an argument instead of baking it into a string and the quoting problem never arises.

If baking it in is unavoidable, do not stack quotes by hand — make the shell do it. printf %q and, on bash 4.4 or newer, ${var@Q} are the tools.

$ bad='my report.txt'
$ weird=$(printf 'a b\tc*d')

$ printf 'raw : %s\n' "$bad"
raw : my report.txt
$ printf 'q   : %q\n' "$bad"
q   : my\ report.txt
$ printf 'q   : %q\n' "$weird"
q   : $'a b\tc*d'

$ printf 'atQ : %s\n' "${bad@Q}"
atQ : 'my report.txt'
$ printf 'atQ : %s\n' "${weird@Q}"
atQ : $'a b\tc*d'

### round trip: quote it, then parse it back
$ q=$(printf '%q' "$bad")
$ eval "wc -c $q"
0 my report.txt

Notice that for the value containing a tab the shell picked ANSI-C quoting on its own. It is more accurate than a human choosing the quoting form. That said, both %q and ${var@Q} are bash extensions and do not exist in POSIX sh (section 13).

Finally, when you want to see the expansion results with your own eyes, set -x is the fastest route. It shows the arguments the shell actually passed, with quoting added.

$ set -x
$ wc -c $bad
+ wc -c my report.txt
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
$ wc -c "$bad"
+ wc -c 'my report.txt'
0 my report.txt

In a trace line, bash adding quotes around 'my report.txt' means one argument; plain my report.txt means it split in two. Knowing only that one thing cuts debugging time dramatically.

13. Where POSIX sh and bash part ways

If your script starts with #!/bin/sh you cannot use bash extensions. Running the same things side by side in dash shows where the shared ground ends.

### ANSI-C quoting
bash : A	B
sh   : $A\tB

### [[ ]]
bash : ok
sh   : dash: 1: [[: not found

### arrays
bash : x|y z|
sh   : dash: 1: Syntax error: "(" unexpected

### printf %q
bash : a\ b
sh   : dash: 1: printf: %q: invalid directive

There is also a place where bash is the stricter one: a redirection target that splits into two words.

$ v="r 1.txt"; echo hi > $v          # plain bash
bash: $v: ambiguous redirect
exit=1

$ v="r 2.txt"; echo hi > $v          # bash --posix
exit=0

$ v="r 3.txt"; echo hi > $v          # dash
exit=0

### files actually created
$ ls
r 2.txt
r 3.txt

Plain bash refused; bash in POSIX mode and dash accepted it and created the file. Here is what the POSIX specification says about this position.

Pathname expansion shall not be performed on the word by a non-interactive shell; an interactive shell may perform it, but if the expansion would result in more than one word it is unspecified whether the redirection proceeds without pathname expansion being performed or the redirection fails.

In other words this is a region where implementations are allowed to differ. Which leads to one conclusion: quote redirection targets too. Then every shell behaves the same.

Fortunately the core quoting rules are identical everywhere. The same code was run in both shells.

$ v="a b"; set -- $v;   printf 'unquoted=%d ' "$#"
$ set -- "$v"; printf 'quoted=%d\n' "$#"

dash  : unquoted=2 quoted=1

Compressed into one rule: when in doubt, "$var". Then name the exceptions where you take the quotes off.

One script closes the argument. Below is the common shape with every quote omitted. It has no syntax errors at all, so it passes bash -n.

Conclusion: quotes attach to code, not to values

Turned into a rule, quoting is three sentences.

  • Single quotes block everything. Use them to protect another language's syntax from the shell. A single quote cannot go inside; the workaround is close, one character, reopen
  • Double quotes let four things through: the dollar sign, the backquote, the backslash before certain characters, and the exclamation mark in interactive shells. In exchange they block word splitting and globbing exactly as single quotes do
  • The places with no quotes are where incidents happen. One value becomes several, filenames appear out of nowhere, and empty values disappear entirely

Restating what the runs showed: a value with a space split into two arguments. A value with a star swelled into a file list, and one rm line emptied a directory. An empty value dropped out of the argument list and made [ -n ] true. Only "$@" delivered four arguments intact; the other three forms all differed. Changing IFS moved only the unquoted expansions, while the quoted one stayed at one field. Putting a command line into a string turned the quotes into characters that were handed straight to wc.

That last point is the thesis. Quotes attach to code, not to values. The shell processes quoting while reading source text and never looks at quote characters inside values again. So assembling command lines as strings cannot be fixed in principle; passing things with their structure intact, through an array or "$@", is the only real answer.

Pick a default and keep it. When in doubt, "$var". Take the quotes off only where you can state the reason, and leave that reason in a comment. That single rule removes most shell incidents.

# Shell Quoting Rules — a paste-and-use decision checklist

> Source: braindetox.kr — Shell Quoting Rules
> Basis: GNU Bash Reference Manual (Single Quotes / Double Quotes / ANSI-C Quoting / Word Splitting), POSIX Issue 8 (Shell Command Language 2.2.2, 2.2.3, 2.6.5, 2.7)
> Paste this file into an AI tool and say "fix our script against this checklist".

## 0. The default, in one line

**When in doubt, `"$var"`.** Removing the quotes is the exception, and every exception gets a comment explaining why.

## 1. What each quote blocks

| Form | Dollar expansion | Backquote | Backslash | Bang (history) | Word splitting | Globbing |
|---|---|---|---|---|---|---|
| unquoted | passes | passes | passes | passes | **happens** | **happens** |
| `'...'` | blocked | blocked | blocked | blocked | blocked | blocked |
| `"..."` | **passes** | **passes** | **partly** | **interactive only** | blocked | blocked |
| ANSI-C quoting | blocked | blocked | **interpreted** | blocked | blocked | blocked |
| `\x` | blocked | blocked | blocked | blocked | blocked | blocked |

- [ ] I know single and double quotes **block word splitting and globbing identically**
- [ ] I know a backslash inside double quotes is special **only before** the dollar sign, the backquote, the double quote, the backslash and a newline
- [ ] I know `"\n"` is two characters, not a newline

## 2. Situation to quote

| Situation | Form to use | Reason |
|---|---|---|
| variable as a command argument | `"$var"` | blocks both word splitting and globbing |
| forwarding script arguments | `"$@"` | preserves count, empty args and spaces |
| joining args into one log line | `"$*"` | one string joined with the first IFS character |
| handling a list | `"${arr[@]}"` | a string list cannot hold an element with a space |
| redirection target | `> "$var"` | implementations are allowed to differ here |
| tests and comparisons | `[ -n "$var" ]` | stops an empty value vanishing from the arg list |
| awk / sed / regex programs | `'...'` | protects dollar signs from the shell |
| find patterns | `-name '*.log'` | unquoted, the shell consumes it first |
| a tab or newline as a value | `TAB=$(printf '\t')` | backslashes are not decoded inside double quotes |
| glob written in the code | `*.log` (unquoted) | quoting turns a glob into a literal |
| pattern variable in case / `[[ ]]` | `$p` (unquoted) | quoting makes it a literal comparison |
| sending a command to another shell | pass values **as arguments** | avoid string assembly entirely |
| when you must assemble | `printf %q` / `${var@Q}` | let the shell, not a human, add the quotes |

## 3. Patterns that break, and the fix

```bash
# -- 1) a value with a space splits into several arguments
wc -c $f                      # BAD  my report.txt -> 2 arguments
wc -c -- "$f"                 # GOOD 1

# -- 2) a value with a glob character swells into filenames
rm $f                         # BAD  if f='*' the directory is emptied
rm -f -- "$f"                 # GOOD only that one file

# -- 3) an empty value disappears from the argument list
[ -n $DEBUG ]                 # BAD  becomes [ -n ], always true
[ -n "${DEBUG:-}" ]           # GOOD

# -- 4) never put a list in a string
list='a.txt b.txt'; for f in $list      # BAD  cannot express a name with a space
files=('a b.txt' 'c.txt'); for f in "${files[@]}"   # GOOD

# -- 5) never loop over ls
for f in $(ls "$src")         # BAD  splitting and globbing both apply
for f in "$src"/*; do [ -e "$f" ] || continue       # GOOD

# -- 6) never put a command line in a string (quotes become characters)
cmd='wc -c "a b.txt"'; $cmd   # BAD  wc receives literal quote marks
cmd=(wc -c 'a b.txt'); "${cmd[@]}"                  # GOOD

# -- 7) argument forwarding always looks like this
run() { real_cmd "$@"; }      # GOOD  ($@ / "$*" / $* all behave differently)

# -- 8) quote redirection targets too
echo hi > $out                # BAD  bash says ambiguous redirect, sh accepts it
echo hi > "$out"              # GOOD identical in every shell

# -- 9) to a second shell, send values as arguments
ssh host "wc -c $file"        # BAD  reparsed on the far side
ssh host 'wc -c "$0"' "$file" # GOOD no assembly
```

## 4. The only two reasons to drop the quotes

- [ ] **Deliberate word splitting** — splitting an option string (an array is safer)
- [ ] **Deliberate globbing** — the pattern position of `case` and `[[ ]]`, or a glob written in the code
- [ ] If it is neither of the two, **quote it, no exceptions**
- [ ] Every stripped site carries a comment such as `# intentional split`

## 5. Audit commands — they point at the lines to read

```bash
F=script.sh

# unquoted expansions after a command word
grep -nE '(^|[[:space:]|(&;])(cp|mv|rm|wc|cat|cd|mkdir|source)[[:space:]]+[^|;&]*\$[A-Za-z_{]' "$F"

# unquoted expansions inside a bracket test
grep -nE '\[[^]]*\$[A-Za-z_{][^]"]*\]' "$F"

# looping over command output or a variable
grep -nE 'for[[:space:]]+[A-Za-z_]+[[:space:]]+in[[:space:]]+(\$\(|\$[A-Za-z_{])' "$F"

# unquoted redirection targets
grep -nE '(^|[[:space:]])[12]?>>?[[:space:]]*\$[A-Za-z_{]' "$F"

# see the real expansion with your own eyes
bash -n "$F"                       # syntax only (missing quotes are NOT caught)
bash -x "$F" "one argument" out    # judge by the quotes in the trace lines
```

**How to read a trace line**: if bash shows `'my report.txt'` **with quotes, it is one argument**;
if it shows a bare `my report.txt`, **it split in two**.

## 6. Test fixtures for reproduction — empty scratch directory only

```bash
d=$(mktemp -d) && cd "$d" || exit 1
: > 'my report.txt'          # a space
: > 'keep.txt'
printf 'junk\n' > '*'        # the name is a glob character itself
touch -- "-dash.txt"         # starts with a dash
./your_script.sh "$d" out    # if it breaks here, it is a quoting problem
```

WARNING: run the fixtures **only inside a freshly created, empty scratch directory**. Never in your home directory or on a real server path.

## 7. Porting to POSIX sh

| Feature | POSIX sh | bash | Portable alternative |
|---|---|---|---|
| single / double quote rules | same | same | use as is |
| word splitting, globbing, IFS | same | same | use as is |
| `"$@"` / `"$*"` | same | same | use as is |
| ANSI-C quoting | absent | present | `TAB=$(printf '\t')` |
| arrays | absent | present | positional parameters via `set --` |
| `[[ ]]` | absent | present | `[ ]` with rigorous quoting |
| `printf %q` | absent | present | pass values as arguments, avoid assembly |
| two-word redirection target | allowed | refused | always `> "$v"` |

## 8. One closing sentence

**Quotes attach to code, not to values.** A quote character inside a variable value means nothing to the shell.
So assembling command lines as strings cannot be fixed in principle; passing things with their structure intact, through an array or `"$@"`, is the only answer.
