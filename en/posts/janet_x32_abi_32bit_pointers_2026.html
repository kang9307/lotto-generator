The trigger - a compiler flag said to cut RAM, and what the source concludes

On a 64-bit system a pointer is eight bytes. A data structure that holds many pointers uses that much more memory, and fewer of its objects fit in the same cache. LWN describes the cost this way: "the size of addresses (and, thus, pointers) doubled from four to eight bytes. That change inevitably increases the amount of memory used by a program and, importantly, the amount of cache required to hold the pointed-to values." The x32 ABI is a design that tries to take that cost back. In LWN's words, the idea is to provide all of the x86-64 features but to use 32-bit addresses and data types, bringing the memory and cache footprint back down.

The topic came back into discussion because of Alex Alejandre's post Janet on x32: 32-bit Pointers, 64-bit Speed, 25% Less RAM, published on October 6, 2026. GeekNews introduced it on October 7, 2026. The description of the post reduces to a single question: RAM is expensive again, so can existing software run faster with 50% less RAM through an unloved compiler flag? The author built the Janet language implementation for x32 and compared memory and run time against the 64-bit build.

The post opens by quoting a lobste.rs comment, credited to Hailey. The comment reads: "It's possible to save a dramatic amount of memory (close to half for programs with pointer heavy heaps) and also speed up programs by a modest amount (by way of more data fitting in cache) by using 32 bit pointers on 64 bit systems." It goes on to report that deploying Mastodon on x32 "cut the app's memory usage from 650mb to 350mb". That figure is the commenter's own statement, and the reduction works out to about 46% (calculated).

The conclusion of the post body reads as four points.

  • Memory. The author writes: "-mx32 cut RAM use by 21% (8-32%)". That is an average of 21% with a range of 8 to 32% across the items measured.
  • Speed. The same conclusion sentence says "with equal speed (-13% slower to 10% faster)". The speed is called equal, while the range spreads from 13% slower to 10% faster depending on the task. In this comparison, FFI was disabled and janet.h was edited only in the x32 build.
  • -m32. The conclusion sentence continues "while -x32 reduced speed by half". The spelling differs, but it reads as a reference to the -m32 result of the previous section, about 50% slower.
  • Recommendation. The author believes that Linux distros should include -mx32 support and that daemons and utilities should be compiled down for more efficient idling and day to day computing, and closes with "It only costs a flag." This is the author's opinion, and the measurements below are what it rests on.

The 25% in the title, the 50% in the description and the 21% in the conclusion are three different values. What follows takes the measurements printed in the post body and the 21% of the conclusion sentence as its reference.

What x32 defines - 32-bit pointers on a 64-bit instruction set

The x32 ABI project site describes itself as "A 32-bit psABI for x86-64 with 32-bit pointer size." In other words, it is a platform-specific ABI document for x86-64 in which pointers are 32 bits wide. The x86 options section of the GCC manual separates the three options as follows. -m32 sets the int, long and pointer types to 32 bits and generates code that runs in 32-bit mode. -m64 sets int to 32 bits and long and pointer types to 64 bits, and generates code for the x86-64 architecture. -mx32 sets int, long and pointer types to 32 bits, and generates code for the x86-64 architecture.

Argument passing (Merino post)i386: few registers, arguments mostly passed on the stackSame calling conventions as x86-64, a mixture of 32-bit and 64-bit registersArguments passed in registers as much as possibleJulio Merino

Kernel requirement—Does not run on a regular x86-64 kernel, needs a kernel with x32 support—Merino, source post

In short, -mx32 has the same type sizes as -m32 and the same target architecture as -m64. The source author describes -m32 as the old 32-bit x86 mode that uses only 8 registers and -mx32 as the 64-bit instruction set with shrunken 32-bit pointers. Julio Merino's post of October 7, 2024 disassembles an x32 hello-world and writes that the x32 version "uses the same calling conventions as x86-64, but it contains a mixture of 32-bit and 64-bit registers, delivering a more compact binary size".

  • History. According to LWN the Linux kernel has supported x32 since the 3.4 release in 2012. Wikipedia adds that support was added to the GNU C Library in version 2.16.
  • The ceiling paid in exchange. Wikipedia writes that "the x32 ABI limits the program to a virtual address space of 4 GiB", but that it also "decreases the memory footprint of the program by making pointers smaller", which "can allow it to run faster by fitting more code and more data into cache".
  • A speculation about slow adoption. Among several guesses, LWN names the growth of memory use: "Memory use has grown to the point that it is challenging to shoehorn even a basic 'hello world' app into the 2-3GB of virtual address space that 32-bit pointers afford."
  • The kernel interface is involved. Merino writes that x32 is an ABI that touches the kernel interface too, so binaries cannot be executed on a regular x86-64 kernel. The source post explains that the kernel must be built with CONFIG_X86_X32_ABI to provide the system call entry points, and that Windows and macOS have no equivalent.
  • Checking for support, and the build ingredients. On the Ubuntu server of the source post, the output of grep X86_X32 /boot/config-$(uname -r) was CONFIG_X86_X32=y, and the packages build-essential, git, gcc-multilib and libc6-dev-x32 were installed.

The experimental design - what was measured, and under which conditions

The numbers can only be read once the conditions are known. The source built the same Janet source once for 64 bits and once for x32 and compared the two results. The build method is a fake cc script that intercepts the call to gcc. Because Janet libraries such as Spork supply their own build flags, the author writes that they can be hijacked with a fake cc, so a cc wrapper is placed at the front of PATH and starts the real gcc with the necessary flags.

  • Subjects. The Janet source at commit 0e5fdd53 (the same commit for the 64-bit and x32 builds), the library spork, and the packages declarative-dsls and judge.
  • Environment. Ubuntu 20.04 LTS, whose standard support ended on May 31, 2025, gcc 9.4.0, and the kernel setting CONFIG_X86_X32=y. The source calls such machines deprecated servers.
  • Common compile options. Both builds use CFLAGS of -fPIC -O3 -flto -fno-semantic-interposition -march=native. For the x32 build the cc wrapper adds -mx32 and -DJANET_NO_FFI.
  • Source change. The condition in janet.h that detects 64 bits gained !defined(__ILP32__). The source gives the reason as: "lest Janet choose the 64-bit value layout".
  • FFI. The x32 build disables FFI. A comment in the build script says "FFI build test fails on -mx32 build so -DJANET_NO_FFI". The 64-bit build script printed in the post does not have this option.
  • Measurement. Elapsed time in seconds and a memory value in KB were recorded with /usr/bin/time -f '%e s %M KB'. Each of the four benchmarks was repeated four times, and the declarative-dsls test was run once.
  • The four benchmarks. words builds a text, splits it into words, counts them and sorts the result (a vocabulary of 5,000 words and 600,000 words of text). records groups 300,000 structs by department and summarizes them, with extra fields that are never used, as in real code. parse parses 200,000 lines with a PEG and totals them. tree builds and walks binary trees, and the source calls it the pointer-heaviest example.

The code below shows the two changes the source made to the source tree and the build. The first part is the edit to the condition in janet.h, and the second part is the command that creates the cc wrapper for x32. Only lines taken from the author's actual scripts are shown.

#if ((defined(__x86_64__) || defined(_M_X64)) && !defined(__ILP32__) \
                         && (defined(JANET_POSIX) || defined(JANET_WINDOWS))) \
                    
                    printf '#!/bin/sh\nexec gcc -mx32 -DJANET_NO_FFI "$@"\n' > "$TARGET/cc32/cc"

The measurement used the loop below, which is the one printed in the source. It runs the two builds alternately for each benchmark and prints the name, the time and the memory on one line, with the output of the Janet script itself discarded.

for f in words records tree parse; do
                      /usr/bin/time -f "$f 64:  %e s  %M KB" janet64/bin/janet $f.janet > /dev/null
                      /usr/bin/time -f "$f x32: %e s  %M KB" janetx32/bin/janet $f.janet > /dev/null
                    done

The source also states why it wrote separate benchmarks. In its words, declarative-dsls is "a worst case scenario, using typed c arrays for big speed ups, which don't benefit much from this". That is why the author made four minimal benchmarks "to really test the differences".

Where the memory goes away - Janet object headers and pointers

Janet uses nanboxing, which stores a value in 8 bytes. A comment in the Janet source header (janet.h) reads: "Use nanboxed values - uses 8 bytes per value instead of 12 or 16." Because a value is 8 bytes on a 64-bit build as well, the source locates the saving in the headers of the heap objects that values point to and in the pointers inside them. The P.S. of the post lists that structure byte by byte. What follows is the author's understanding, and its items agree with the struct definitions in the source header (commit c495f11, the one the source links). The janet.h at commit 0e5fdd53, which was used for the measurements, has the same content as the one at that commit.

  • nanbox. Source comment: 8 bytes per value, instead of 12 or 16. For this reason the source treats Janet as an example where the gain from smaller pointers is small.
  • GC header. By the author's understanding, Janet heap objects use 16 bytes to help the garbage collector: 4 bytes of flags, 4 bytes of padding and 8 bytes linking to the next object. In the source header it consists of an int32 flags field and a pointer to the next object (or a reference count).
  • string and tuple. A string adds 8 bytes for length and hash. A tuple adds 8 bytes for length and hash and 8 bytes for source line and column information.
  • array. 8 bytes for count and capacity and 8 bytes for a pointer to the data. In the source header the data pointer points to an array of Janet values.
  • struct and table. A struct has 12 bytes for length, hash and capacity, 4 bytes of padding and 8 bytes for its prototype pointer. A table has 12 bytes for count, capacity and the number deleted, 4 bytes of padding, 8 bytes for a data pointer and 8 bytes for its prototype pointer.
  • Fields that change under x32. The next-object pointer, the data pointers of arrays and tables, and the prototype pointers in the structures above are pointer types. Applying the GCC manual definition that pointer types are 32 bits under -mx32, these fields become 4 bytes (inference). The source does not give the byte counts per structure under x32.

The source then asks whether the headers could also be shrunk for 64-bit use. In the author's words, reducing the 16-byte header would require a different garbage collection strategy, for example an allocator of the project's own, which "would hurt a core Janet use case: embedding in other projects". For structs and tables in particular, the author writes that 8 bytes could be regained "through rearranging (not needing the later padding)", and since only tuples parsed from code need the source information, "a flag could save normal tuples 8 bytes". The author adds that glibc malloc adds 8 bytes and rounds up to multiples of 16, so structs would stay the same size while tables and some tuples would shrink more than the figures above indicate.

The value layout also splits by build. The detection block in the source header defines JANET_64 when the 64-bit condition holds and JANET_32 otherwise, and JANET_32 selects the 32-bit nanbox implementation (JANET_NANBOX_32). The !defined(__ILP32__) edit in the source keeps the x32 build from choosing the 64-bit value layout. The source contains no analysis of what this difference in value layout did to speed.

Why speed is not uniform - cache, registers and the shape of the workload

The factors named by the source and the material it cites are two: cache and registers. Results split by item even within the same pair of builds, so what each source says is taken one at a time.

  • Two explanations in the source. The speed gain comes "by way of more data fitting in cache" (the Hailey comment), and the speed loss of -m32 comes, in the author's words, from the fact that "half the registers aren't used" (the author).
  • The design intent in LWN. x32 was meant to provide all of the x86-64 features with 32-bit addresses and data types, bringing the memory and cache footprint back down, and, in LWN's words, "the result was expected to be the fastest x86 ABI available". LWN adds that evidence for the speedup was scarce while kernel support was under development in 2011 but that by 2013 some realistic benchmark results were being posted.
  • The figures on Wikipedia. On the 181.mcf benchmark of SPEC CPU 2000 the x32 version was 40% faster than the x86-64 version, it is 5 to 8% faster on average on the SPEC CPU integer benchmarks, and there is no speed advantage in the floating-point benchmarks. All of these come from tests that Wikipedia cites in footnotes, and their conditions are not the same as in the Janet measurements.
  • Merino's microbenchmark. In a test that uses linked list nodes the 32-bit build was 27% faster, and "the 64-bit build of this microbenchmark incurs almost double the cache misses than the 32-bit build". After jitter was added to the allocations so that nodes were not consecutive in memory, the 64-bit build executed faster, and Merino adds that "tweaking it slightly will make it show very different results". That comparison is i386 against x86-64 and is not an x32 measurement.
  • The Janet measurements. Within the same pair of builds words and tree slowed down while records and parse sped up. They show a case where the width of the pointer alone does not decide speed, and the source does not analyze the cause item by item.
  • A remark from the 2018 debate. LWN reports that Rich Felker "said that GCC performance benefits from an x32 build and that the ABI is useful for catching portability problems", one of the comments that argued for keeping the support at that time.

The tree benchmark is the one the source calls the pointer-heaviest example, yet its memory fell the most (29.6%) while its time grew by 5.0% (calculated). That memory reduction and speed improvement did not move in the same direction is the fact that can be read from these measurements. Where a given workload falls has to be decided by measuring that workload.

Can it be used now - distribution and kernel support, and the removal debate

The support status combines the statements of the source post with the LWN article (June 1, 2026, by Jonathan Corbet). Each status is as of the time the respective source speaks of, and the table records what each source says without adding to it.

SubjectStatus (as stated by the source)Source

The source author favors distributions that include -mx32 support and daemons and utilities compiled for x32. Among kernel developers, a discussion in the opposite direction is open over the same period. Placing the two views side by side gives the following.

  • 2018. Andy Lutomirski proposed removing x32, saying it was largely unused and that the system-call interface it needed added a lot of complexity to the kernel. Linus Torvalds remarked that the main use of x32 was "extreme benchmarking" and said he would not be opposed to removing support if there were no complaints. Complaints followed, and LWN reports that the idea of removal was dropped and that support remains in current kernels.
  • May 23, 2026. Sebastian Andrzej Siewior reopened the discussion, saying there is "practically no real use for x32" and that the performance benefits it offers are not compelling enough to cause users to adopt it. The suggestion is to remove the configuration symbol first and, if enough time passes without complaint, to remove all of the code implementing the support as well.
  • H. Peter Anvin. He did not oppose phasing out the ABI, noting that it "happened too late to actually be able to become useful". He took issue with the suggestion that the x32-specific system call numbers could be reused, and the article adds that this is not a huge concern, since system call numbers are not in short supply.
  • Corbet's summary. The response to the proposal has seemingly been one of "overwhelming indifference", and there has been a distinct lack of developers offering to help maintain the support. Kernel developers are nevertheless generally reluctant to remove support for features that are actively in use, and the article ends: "So, even though almost nobody wants it (and many actively want it gone), x32 support may yet live on in the kernel."

Before carrying the numbers over - the range they cover

The source author invites others to test their software and languages similarly. It helps to separate what the 21% is a value of before doing so, because that keeps the interpretation steady and keeps a result from one program from being read as a property of the ABI itself. The list below sets out the range the numbers cover, taking the conditions of the source as the reference.

  • The metric. The 21% compares memory values (KB) reported by /usr/bin/time for four small Janet scripts. It is not the memory of a whole service or the size of a heap.
  • The sample. The same configuration was measured four times on one machine. A difference that lies inside the spread of the repeated runs (parse) is hard to read as a difference.
  • The ceiling. Under x32 the virtual address space of a process is limited to 4 GiB. A service that uses more than 4 GiB is outside what this approach can serve.
  • The size of the gain. Even in Janet the reduction ranged from 8.3% to 29.6%. tree, which the source calls the pointer-heaviest example, was largest, and records, which handles 300,000 structs that include unused fields, was smallest.
  • Speed. The sign changed, so it has to be measured with your own workload. The source conclusion also only calls the speed equal and does not claim that it becomes faster.
  • Build conditions. The x32 build disabled FFI, edited janet.h and used gcc 9.4.0. The 64-bit build it was compared with has a different FFI setting.
  • Operating conditions. An x32 binary runs only on a kernel that supports x32, and the Hailey comment quoted in the source says there is not much packaging, so nearly everything has to be compiled by hand. Whether support exists can be read from the kernel configuration file alone, for example with grep X86_X32 /boot/config-$(uname -r), the command the source used.
  • Questions the source leaves open. The questions at the end of the source are whether zig cc with the x86_64-linux-muslx32 target can cross-compile for easy distribution, and how much of the gain remains with a faster allocator such as mimalloc. The source has no answer to either.

None of these limits makes the measurements less useful. They only fix what the numbers are values of. Within the range of four small Janet scripts, one Ubuntu 20.04 machine and an x32 build with FFI turned off, memory fell by 8.3 to 29.6%, and that is the fact that can be read from the source.

What could not be confirmed

  • The aggregate that produced the 25% in the title. The conclusion in the body is 21%, and the body does not explain which items and which calculation lead to 25%.
  • The upper limit of 32% in the conclusion. The largest reduction calculated from the table values is 29.6% on average and 29.9% among individual measurement pairs, and no measurement in the tables corresponds to 32%.
  • The specification of the measurement machine. CPU, RAM and kernel version are not stated in the source, and only Ubuntu 20.04 and gcc 9.4.0 are given.
  • The cause of the speed differences by item. An analysis of why words and tree slowed down while records and parse sped up, and of what the 32-bit value layout (JANET_NANBOX_32) did to the result.
  • The effect on the results of the FFI difference (default for the 64-bit build, disabled for the x32 build).
  • The build options and number of repetitions of the 64-bit control in the Arch section. Only single-run values are printed.
  • The measurement conditions behind Mastodon going from 650mb to 350mb. It is a quoted comment, and neither the environment nor the method is given.
  • The register, calling convention and structure alignment rules in the body of the x32 psABI specification. Only the introductory sentence of the project site and the type-size definitions of the GCC manual served as the basis.
  • How the kernel removal debate developed after October 7, 2026. Only what the LWN article (June 1, 2026) contains is reflected.
