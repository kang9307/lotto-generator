JSON에 담은 64비트 ID의 끝자리가 바뀐다 - 숫자 정밀도가 사라지는 지점

에러는 나지 않는다. 끝 두세 자리만 조용히 달라진다

2026-07-30 개발/인프라

서론: 주문 조회가 안 되는데 ID는 분명히 맞았다

고객센터에서 티켓이 올라온다. 주문번호를 넣었는데 조회가 안 된다는 것이다. 담당자가 받아 적은 번호를 확인해 보니 데이터베이스에 그 주문이 분명히 있다. 그런데 관리자 화면에서 같은 번호로 검색하면 결과가 없다. 화면에 찍힌 번호와 DB의 번호를 나란히 놓고 보면 앞의 열여섯 자리는 똑같고 끝 세 자리만 다르다.

이 시점에서 흔히 나오는 추측은 세 가지다. 복사할 때 잘렸거나, 화면이 반올림해서 보여 주거나, 데이터가 두 벌이라는 것이다. 셋 다 아니다. 값이 바뀐 곳은 서버도 DB도 화면도 아니고, 그 사이에 있는 JSON 한 줄이다.

이 글의 요점은 「식별자는 문자열로 보내세요」라는 결론이 아니다. 그 조언은 이미 다 알고 있고, 그것만으로는 이미 도는 시스템에서 아무것도 못 찾는다. 이 글이 다루는 것은 어디서 정밀도가 사라지고, 대신 무엇을 포기해야 하며, 왜 이 사고가 항상 늦게 발견되는가다.

먼저 이 문제의 성격을 한 문장으로 정리한다. 이 문장이 나머지 전부를 설명한다.

JSON 표준은 숫자의 정밀도를 규정하지 않는다. 깨지는 것은 표준이 아니라 파서, 즉 언어의 선택이다. 그래서 보내는 쪽과 받는 쪽의 언어가 다르면 양쪽 다 정상 동작하면서도 값이 어긋난다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과를 그대로 옮긴 것이다. 런타임은 Node.js v22.16.0 (win32), Python 3.13.3 (win32), Perl v5.38.2(JSON::PP 4.16), SQLite 3.49.1이다. 스크립트는 모두 파일로 저장해 실행했고, 예시로 쓴 ID와 금액은 전부 가상의 값이다.

이 글이 다루지 않는 것. 돈 계산 자체의 원칙, 즉 왜 금액에 부동소수를 쓰면 안 되는가는 핀테크 엔지니어링 핸드북에서 이미 다뤘다. 여기서는 JSON 경계에서의 직렬화만 본다. 스키마와 계약 문서를 어떻게 운영하느냐는 API 문서 거버넌스 쪽이다. 같은 「경계에서 조용히 깨진다」는 구조의 다른 사례로는 인코딩이 깨지는 지점이 있다.

먼저 증상만 보고 어디를 의심해야 하는지 정리해 둔다. 이 표의 오른쪽 칸이 이 글의 목차이기도 하다.

1. 재현: 19자리 ID를 JSON에 한 번 태우면

가장 먼저 할 일은 눈으로 보는 것이다. 트위터·스노플레이크 계열 ID가 그렇듯 19자리 정수를 JSON에 담아 왕복시켰다. 원본과 결과를 나란히 찍었다.

node v22.16.0 / win32

--- 1-1. snowflake-style 19-digit id through JSON round trip ---
sent text     : {"order_id":1234567890123456789,"amount":1000}
parsed value  : 1234567890123456800
re-serialized : {"order_id":1234567890123456800,"amount":1000}
original digits : 1234567890123456789
result   digits : 1234567890123456800
same length     : true
first differing position (0-based) : 16
digits kept     : 1234567890123456
lost tail       : 789  ->  800

읽는 법은 이렇다. 보낸 텍스트에는 1234567890123456789가 분명히 들어 있었다. 파싱한 값은 1234567890123456800이다. 길이는 19자리 그대로이고, 앞의 열여섯 자리도 그대로다. 17번째 자리부터 789가 800으로 바뀌었다.

  • 예외가 없다. 파싱도 성공했고 재직렬화도 성공했다. 표준을 어긴 것도 아니다
  • 길이가 같다. 그래서 자릿수 검증이 있는 시스템도 이것을 통과시킨다
  • 앞자리가 같다. 로그를 눈으로 훑을 때 사람도 못 알아본다. 눈은 앞에서부터 읽는다
  • 재직렬화된 JSON이 다시 유효하다. 그래서 다음 시스템으로 그대로 흘러간다. 아무도 못 막는다

한 건이 아니라 여러 형태로 확인했다. 실무에서 마주치는 모양들을 모아 봤다.

--- 1-2. several real-world shaped ids ---
input                   parsed back              equal  delta
---------------------------------------------------------------------
1234567890123456789     1234567890123456800      false  -11
9007199254740993        9007199254740992         false  1
18014398509481985       18014398509481984        false  1
1541815603606036480     1541815603606036500      false  -20
999999999999999999      1000000000000000000      false  -1
12345678901234567890    12345678901234567000     false  890

여기서 짚을 것이 여러 가지다.

  • 999999999999999999은 1000000000000000000이 됐다. 자릿수가 하나 늘었다. 18자리가 19자리가 됐으니 길이 검사도 통과하지 못한다
  • 9007199254740993은 정확히 1만큼 줄었다. 오차가 큰 것이 아니라 딱 1이다. 이것이 가장 위험한 형태다
  • 1541815603606036480처럼 이미 끝이 0인 값은 20만큼 어긋났다. 밀리초 타임스탬프를 왼쪽으로 밀어 만든 ID가 흔히 이 모양이다
  • 20자리 12345678901234567890은 890만큼 어긋났다. 자릿수가 늘수록 손실 폭도 커진다

오차가 1이라는 사실이 왜 특히 위험한가. 그 옆 번호가 실재하는 다른 주문일 수 있기 때문이다. 조회가 실패하면 그나마 눈에 띈다. 그런데 하필 인접 ID가 존재하면 조회는 성공하고 남의 주문이 열린다. 이 경우 시스템은 끝까지 아무 이상도 보고하지 않는다.

다만 이 기억법은 근사치다. 정확한 경계는 9007199254740991, 즉 2의 53승에서 1을 뺀 값이다. 그 근처를 한 칸씩 넘어가며 봤다.

이 표가 이 글에서 가장 중요한 출력 중 하나다. 경계를 넘으면 전부 깨지는 것이 아니라, 짝수만 살아남는다.

  • 9007199254740992는 정확했다. 경계를 넘었는데도 맞았다
  • 9007199254740993은 9007199254740992로 내려갔다
  • 9007199254740994는 다시 정확했다
  • 9007199254740995는 9007199254740996으로 올라갔다. 방향이 일정하지도 않다

여기서 실무적으로 치명적인 함정이 나온다. 「테스트해 봤더니 되던데요」가 성립한다. 짝수 ID를 몇 개 뽑아 확인하면 전부 통과한다. 홀수를 뽑으면 실패한다. 무작위로 몇 건 확인하는 검증 방식은 이 구간에서 확률적으로 통과해 버린다. 그래서 검증은 표본이 아니라 경계값 목록으로 해야 한다.

왜 짝수만 남는가. 배정도 부동소수는 가수 53비트로 유효숫자를 담는다. 2의 53승을 넘으면 표현 가능한 값의 간격이 1에서 2로 벌어진다. 그 위로 올라가면 간격이 4, 8로 계속 두 배씩 벌어진다. 19자리 구간에서 간격이 얼마나 되는지는 1절의 -11, -20, 890이라는 오차가 그대로 보여 준다.

3. 등호로는 안 잡힌다 - 두 ID가 한 값이 된다

이 문제를 검증 코드로 잡으려 할 때 가장 먼저 부딪히는 벽이 이것이다. 비교 자체가 거짓말을 한다.

--- 3-1. two different integers become the same value ---
literal 9007199254740992 : 9007199254740992
literal 9007199254740993 : 9007199254740992
a === b                  : true
Object.is(a, b)          : true
a - b                    : 0

--- 3-2. x === x + 1 becomes true ---
x                  x+1                x === x+1
-----------------------------------------------------
9007199254740990   9007199254740991   false
9007199254740991   9007199254740992   false
9007199254740992   9007199254740992   true
9007199254740992   9007199254740992   true
1234567890123456800 1234567890123456800 true

서로 다른 두 정수 리터럴을 코드에 그대로 써 놓았는데 엄격 동등 비교가 참이다. 차를 구하면 0이다. 값이 같은 것이 아니라 애초에 같은 값으로 읽힌 것이다.

더 직관을 깨는 것이 그 아래다. x와 x + 1이 같아지는 지점이 있다. 9007199254740992에서 1을 더해도 값이 그대로다. 19자리 ID에서는 말할 것도 없다. 정수론적으로는 있을 수 없는 일인데, 여기서 다루는 것은 정수가 아니라 정수의 근사값이기 때문에 성립한다.

이것이 실제 코드에서 어떻게 나타나는지 보자.

--- 3-3. a lookup that silently matches the wrong row ---
key sent by client   : 1234567890123456789
key after JSON.parse : 1234567890123456800
Map lookup result    : undefined
deduplication test   : how many distinct ids survive?
  sent   : 4 distinct id strings
  after  : 1 distinct numbers -> ["1234567890123456800"]
  • 클라이언트가 보낸 키로 조회했는데 결과가 없다. 키가 이미 다른 값이 됐기 때문이다
  • 더 심각한 것은 아래쪽이다. 서로 다른 네 개의 ID를 배열에 담아 보냈더니 파싱 후 하나로 합쳐졌다. 중복 제거 로직이 셋을 삼켰다
  • 이 경우 시스템은 「중복이 있어서 정리했다」고 판단한다. 정상 동작으로 기록된다
  • 일괄 처리에서 이런 일이 나면 나머지 세 건은 처리되지 않은 채 성공으로 집계된다. 사고를 인지하는 것은 고객이 문의할 때다

검증에서 반드시 지킬 것. 왕복 검증을 값 비교로 하면 안 된다. 손실된 값끼리는 서로 같기 때문에 값 비교는 통과한다. 원본 텍스트와 재직렬화된 텍스트를 문자열로 비교해야 손실이 드러난다. 이 한 줄의 차이가 검증이 되느냐 마느냐를 가른다.

펄은 또 다른 지점에서 갈린다. 64비트 정수에 들어가는 값은 보존하고, 그 밖으로 나가면 부동소수로 떨어진다. 18446744073709551615까지는 그대로였고 거기서 1을 더한 값이 1.84467440737096e+19가 됐다. 경계가 언어마다 다르다는 뜻이다. JavaScript는 2의 53승, 펄은 2의 64승 근처, 파이썬은 사실상 없다.

펄에서는 방향이 다른 함정도 하나 나왔다. 이것은 예상하지 못했던 결과다.

decoded as string : {"id":"1234567890123456789"}
after one numeric use of the same variable:
  re-encoded      : {"id":1234567890123456789}

5. 표준은 무엇을 규정하고 무엇을 규정하지 않는가

여기서 규격을 확인하고 넘어가야 한다. 이 문제를 「구현 버그」로 오해하면 대응 방향이 통째로 틀어지기 때문이다.

RFC 8259의 숫자 절은 표기 문법을 정의한 다음, 정밀도에 대해서는 규정이 아니라 권고를 적어 두었다. 열어서 확인한 문구는 이렇다.

「good interoperability can be achieved by implementations that expect no more precision or range than these provide」 — 이 정도 이상의 정밀도나 범위를 기대하지 않는 구현끼리는 좋은 상호운용성을 얻을 수 있다.

「numbers that are integers and are in the range [-(2**53)+1, (2**53)-1] are interoperable in the sense that implementations will agree exactly on their numeric values」 — 정수이면서 이 범위 안에 있는 수는, 구현들이 그 수치에 정확히 동의한다는 의미에서 상호운용 가능하다.

문장을 정확히 읽어야 한다. 「이 범위를 넘으면 안 된다」가 아니다. 넘어도 문법적으로는 완벽히 유효한 JSON이다. 표준이 말하는 것은 그 범위 안에서만 구현들이 같은 값에 동의한다는 보장이 있다는 것이다. 밖에서는 보장이 없을 뿐이고, 보장이 없다는 것은 깨져도 규격 위반이 아니다는 뜻이다.

결론이 여기서 나온다.

  • 이것은 버그 리포트를 낼 대상이 없는 문제다. 파서도 맞고 직렬화기도 맞다
  • 고칠 수 있는 곳은 오직 계약이다. 어떤 값을 어떤 형태로 주고받을지 정하는 지점 하나뿐이다
  • 그래서 이 문제의 해결책은 라이브러리 교체가 아니라 명세에 한 줄 적는 것이다
  • RFC가 2**53을 명시적으로 적어 둔 이유도 여기 있다. 이 숫자는 JavaScript의 사정이 아니라 상호운용의 공통 분모로 문서에 박혀 있다

같은 문서는 Infinity와 NaN에 대해서도 못을 박아 두었다. 「Numeric values that cannot be represented in the grammar below (such as Infinity and NaN) are not permitted.」 이 문장은 10절에서 다시 쓴다.

6. 문자열로 담으면 - 그리고 무엇을 포기하는가

가장 널리 알려진 해법을 실제로 확인한다. 같은 값을 따옴표 안에 넣어 보냈다.

--- 5-1. the id sent as a JSON string instead ---
parsed value : 1234567890123456789
parsed type  : str
exact        : True

--- 5-2. what you give up: string ordering is not numeric ordering ---
as numbers sorted : [9, 10, 99, 100, 999999999999999999, 1000000000000000000]
as strings sorted : ['10', '100', '1000000000000000000', '9', '99', '999999999999999999']
zero padded to 20 : ['00000000000000000009', '00000000000000000010', '00000000000000000099', '00000000000000000100', '00999999999999999999', '01000000000000000000']

--- 5-3. string ids do not survive arithmetic or range filters ---
string + 1 -> TypeError: can only concatenate str (not "int") to str
"9" > "100"  (lexicographic) : True
  9  > 100   (numeric)       : False

보존된다. 당연하다. 문자열은 파서가 숫자로 해석하지 않으므로 손댈 이유가 없다. 그런데 그렇게 간단하면 왜 처음부터 다들 그렇게 하지 않았는가. 두 번째 블록이 답이다.

  • 정렬 순서가 달라진다. 숫자로 정렬하면 9, 10, 99, 100인데 문자열로 정렬하면 10, 100, ...이 앞에 온다. 자릿수가 다른 값이 섞이면 순서가 완전히 어긋난다
  • 비교 연산이 뒤집힌다. 문자열 비교에서는 9가 100보다 크다고 나온다. 사전순이기 때문이다
  • 0으로 채우면 순서는 복원된다. 20자리로 맞추니 정렬 결과가 숫자 순서와 같아졌다. 대신 저장 공간과 색인 크기가 늘고, 나중에 자릿수가 늘면 전체를 다시 손봐야 한다
  • 산술이 막힌다. 문자열에 1을 더하려 하면 타입 오류가 난다. 이것은 단점이 아니라 오히려 안전장치에 가깝다
  • 범위 조회가 어려워진다. 「어제 이후 발급된 ID」 같은 조건을 ID 자체로 걸던 설계는 다시 짜야 한다

그래서 판단 기준은 타입이 아니라 용도다. 그 값으로 산술이나 범위 비교를 하는가. 하지 않는다면 문자열로 잃을 것이 사실상 없다. 한다면 문자열은 답이 아니고, 값의 크기를 계약으로 제한하는 쪽이 맞다.

7. BigInt로 받으면 되는가

JavaScript에는 임의 정밀도 정수 타입이 있다. 그러면 그것으로 받으면 되지 않느냐는 것이 자연스러운 다음 질문이다. 결론부터 말하면 그냥은 안 된다.

--- 6-1. can JSON.parse produce a BigInt by itself ---

JSON.stringify({v:10n}) -> TypeError: Do not know how to serialize a BigInt

--- 6-2. reviver alone is not enough ---
reviver receives an already-damaged number:
  result : 1234567890123456768
  exact  : false

두 가지가 확인된다. 첫째, 표준 파서는 BigInt를 만들어 주지 않는다. 반대 방향으로 BigInt를 직렬화하려 하면 아예 예외가 난다. 둘째, 파싱한 뒤에 변환하는 것은 너무 늦다. 이미 깨진 숫자를 BigInt로 바꾸면 깨진 값이 정확하게 보존될 뿐이다.

두 번째 블록의 리바이버가 그 함정을 그대로 보여 준다. 리바이버는 콜백이므로 개입 지점이 이른 것 같지만, 콜백이 받는 값은 이미 숫자로 변환된 뒤다. 그래서 결과가 여전히 1234567890123456768이다.

그러면 방법이 없는가. 있다. 원본 텍스트에 접근할 수 있어야 한다.

--- 6-3. the source text is required (context.source, ES2025) ---

  result : 1234567890123456789
  type   : bigint
  exact  : true

--- 6-4. the portable workaround: quote the digits before parsing ---
rewritten text : {"order_id":"1234567890123456789"}
  result : 1234567890123456789
  exact  : true
  caution: a text rewrite also hits digits that are inside real strings
  input  : {"memo":"call 01012345678901234567 back","id":1234567890123456789}
  after  : {"memo":"call 01012345678901234567 back","id":"1234567890123456789"}

--- 6-5. writing BigInt back out ---
toJSON via replacer (string form) : {"order_id":"1234567890123456789","amount":1000}
unquoted number form              : {"order_id":1234567890123456789,"amount":1000}
  the second form is valid JSON, and it breaks again at the next JS reader
  • 이 환경의 Node 22에서는 리바이버의 세 번째 인자로 원본 텍스트 조각을 받을 수 있었다. 그것을 쓰면 1234567890123456789가 정확히 복원된다
  • 이 기능을 쓸 수 없는 환경이라면 파싱 전에 텍스트를 고쳐 따옴표를 씌우는 방식이 있다. 널리 쓰이는 우회법이다
  • 다만 그 우회법에는 대가가 있다. 위 출력의 마지막 사례가 그것이다. 문자열 안에 든 긴 숫자는 건드리지 않아야 하는데, 정규식으로 텍스트를 고치면 경계를 잘못 짚을 수 있다
  • 내보내는 쪽도 문제다. BigInt를 문자열로 내보내면 안전하지만, 따옴표를 벗겨 숫자로 내보내면 다음 소비자에게서 다시 깨진다

정리하면 BigInt는 계산을 위한 도구이지 JSON 경계를 지키는 도구가 아니다. 경계를 지키려면 어차피 텍스트 층에서 개입해야 하고, 그럴 바에는 애초에 문자열로 주고받는 편이 단순하다.

8. 부동소수 왕복 - 몇 자리를 써야 보장되나

정수 이야기를 마쳤으니 소수로 간다. 잘 알려진 예부터 확인했다.

0.1 + 0.2가 0.3이 아니라는 것은 유명하다. 여기서 볼 것은 그 다음이다. 그 값을 JSON으로 내보냈다가 다시 읽으면 정확히 같은 값이 돌아온다. 즉 부동소수의 왕복은 안전하다. 정수와 정반대다.

안전한 이유가 두 번째 블록에 있다. 자릿수를 달리해 20만 번씩 왕복시켜 봤다.

  • 15자리로 쓰면 18만 건 넘게 실패했다. 즉 15자리는 왕복을 보장하지 못한다
  • 16자리도 5만 건 넘게 실패했다
  • 17자리에서 실패가 0이 됐다. 20만 건 전부 정확히 돌아왔다

이것이 배정도 실수에서 17자리라는 숫자가 나오는 근거다. 가수 53비트가 표현하는 값들을 십진수로 구분하려면 그만큼이 필요하다. 파이썬이 보고하는 「보장 자릿수」가 15인 것과 혼동하기 쉬운데, 둘은 방향이 다른 값이다. 15는 십진수에서 출발해 왕복할 때의 보장이고, 17은 이진수에서 출발해 왕복할 때 필요한 자릿수다.

9. 금액 - JSON 경계에서의 직렬화

금액에 부동소수를 쓰면 안 된다는 원칙 자체는 핀테크 엔지니어링 핸드북에서 다뤘다. 여기서는 JSON 경계에서만 일어나는 일을 본다.

--- 8-1. money at the JSON boundary (serialization only) ---
float sum of [19.99,19.99,19.99,0.1,0.2] = 60.27
JSON.stringify(sum)                     = 60.27
rounded to 2dp                          = 60.27
integer minor units sum                 = 6027  (60.27)
difference                              = 0 minor units

  the JSON boundary problem is not the arithmetic, it is the text:
    text 0.10      -> number 0.1       -> re-stringified 0.1       text preserved: false
    text 19.99     -> number 19.99     -> re-stringified 19.99     text preserved: true
    text 1234.50   -> number 1234.5    -> re-stringified 1234.5    text preserved: false
    text 100.00    -> number 100       -> re-stringified 100       text preserved: false
  trailing zeros and the scale of the amount are not part of a JSON number

먼저 위쪽부터. 이 표본에서는 실수 합계와 정수 합계의 차이가 0이었다. 반올림 후 결과가 같았다는 뜻이고, 「소수로 더하면 항상 1원이 사라진다」는 통념이 항상 성립하지는 않는다는 것을 보여 준다. 사라지는 경우가 있고 아닌 경우가 있으며, 이 표본은 후자였다. 그래서 더 위험하다. 테스트가 통과해 버린다.

진짜 문제는 아래쪽이다. JSON 경계에서 사라지는 것은 값이 아니라 표기다.

  • 0.10을 보내면 0.1이 되어 돌아온다. 뒤의 0이 사라진다
  • 1234.50은 1234.5가 된다. 금액 표기로서는 어색하고, 문자열 비교나 서명 검증에서는 불일치가 된다
  • 100.00은 100이 된다. 소수점 자체가 사라진다. 통화의 소수 자릿수 정보가 없어진다
  • 19.99만 그대로였다. 우연히 짧은 표기가 원본과 같았을 뿐이다

즉 JSON 숫자에는 정밀도(scale)라는 개념이 없다. 100.00과 100은 같은 수이고, 직렬화기는 짧은 쪽을 고른다. 소수 자릿수가 다른 통화를 함께 다루는 시스템에서 이것이 문제가 된다.

대안은 두 가지뿐이다. 최소단위 정수로 보내고 통화 코드를 같이 담거나, 문자열로 보내 표기를 그대로 보존하거나. 전자가 일반적이고, 후자는 소수 자릿수를 계약으로 고정하기 어려운 경우에 쓴다. 어느 쪽이든 JSON 숫자로 금액을 보내는 선택지만 빠진다.

10. NaN과 무한대 - 표준에 없는 값

5절에서 인용한 RFC 문장 그대로, 이 두 값은 JSON 문법에 존재하지 않는다. 그런데 프로그램에서는 만들어진다. 0으로 나누거나 범위를 넘으면 생긴다. 그러면 직렬화기는 무엇을 하는가.

--- 9-2. NaN and Infinity at the JSON boundary in JS ---
JSON.stringify(NaN)                  : null
JSON.stringify(Infinity)             : null
JSON.stringify(-Infinity)            : null
JSON.stringify({a:NaN,b:Infinity})   : {"a":null,"b":null}
JSON.stringify([NaN, Infinity])      : [null,null]
JSON.stringify(-0)                   : 0
JSON.parse(JSON.stringify(-0))       : 0  Object.is(-0) : false
  JSON.parse("NaN"        ) -> SyntaxError
  JSON.parse("Infinity"   ) -> SyntaxError
  JSON.parse("-Infinity"  ) -> SyntaxError
  JSON.parse("nan"        ) -> SyntaxError
  JSON.parse("1e400"      ) -> Infinity
  JSON.parse("-1e400"     ) -> -Infinity
  JSON.parse("1e-400"     ) -> 0

JavaScript의 선택은 null로 바꾸는 것이다. 예외도 경고도 없다. 이것이 실무에서 무엇을 뜻하는지 보자. 측정에 실패해 NaN이 된 값과, 애초에 측정하지 않아 null인 값이 수신 측에서 완전히 구별 불가능해진다. 「데이터 없음」과 「계산 실패」가 한 값으로 합쳐진다.

추가로 확인된 것들이 있다.

  • 음의 0이 사라진다. -0을 내보내면 0이 되고, 돌아온 값은 더 이상 음의 0이 아니다
  • 범위를 넘는 리터럴은 무한대가 된다. 1e400은 파싱 오류가 아니라 Infinity다. 즉 읽을 때는 조용히 받아들이고 쓸 때는 null로 바꾼다
  • 너무 작은 값은 0이 된다. 1e-400은 0으로 파싱됐다. 0이 아닌 값이 0이 되는 것은 나눗셈이 있는 코드에서 위험하다
  • 반대로 읽는 쪽은 엄격하다. NaN이나 Infinity라는 글자를 넣으면 구문 오류가 난다

다른 언어는 이 지점에서 또 다르게 행동한다.

--- 9-1. NaN and Infinity: python writes them, the standard has them not ---
json.dumps default      : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}
json.loads of that back : {"nan": NaN, "inf": Infinity, "ninf": -Infinity}
json.dumps allow_nan=False -> ValueError: Out of range float values are not JSON compliant: nan
json.loads('NaN')       : nan
json.loads('Infinity')  : inf
with parse_constant     -> ValueError: rejected NaN

--- 11-5. NaN and Infinity in a third parser ---
  decode(NaN) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(Infinity) -> error: malformed JSON string, neither array, object, number, string or atom,
  decode(-Infinity) -> error: malformed number (no digits after initial minus),
  decode(1e400) -> Inf
  encode([inf, nan]) -> [Inf,NaN]

이 출력이 보여 주는 비대칭이 크다.

  • 파이썬은 기본값으로 NaN과 Infinity를 그대로 써 낸다. 이것은 표준 JSON이 아니다. 그리고 자기가 쓴 것을 자기가 다시 읽을 수 있어서, 같은 언어끼리만 테스트하면 절대 드러나지 않는다
  • 파이썬에는 이것을 금지하는 옵션이 있고, 켜면 예외가 난다. 기본값이 관대한 쪽이라는 것이 핵심이다
  • 펄은 읽기를 거부한다. NaN과 Infinity 모두 파싱 오류다
  • 그런데 펄은 쓸 때는 써 낸다. 무한대와 NaN이 든 배열을 인코드하니 [Inf,NaN]이 나왔다. 이 텍스트는 펄 자신도 다시 읽지 못한다

세 언어의 동작을 한 표로 놓으면 이렇다.

11. 큰 수의 지수 표기 - 자릿수 검사를 빠져나간다

정수 방어를 「16자리 이상이면 위험」이라는 규칙으로 짜면 놓치는 구멍이 있다. 어느 크기부터 표기가 바뀌는지 확인했다.

--- 10-2. where JS flips to exponent notation ---
n                        String(n)                          JSON.stringify(n)
----------------------------------------------------------------------------------
10^18                    1000000000000000000                1000000000000000000
10^19                    10000000000000000000               10000000000000000000
10^20                    100000000000000000000              100000000000000000000
10^21                    1e+21                              1e+21
10^22                    1e+22                              1e+22
10^100                   1e+100                             1e+100

  and back again:
    JSON.parse(1e21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1e+21                   ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1E21                    ) -> 1e+21   re-stringified -> 1e+21
    JSON.parse(1000000000000000000000  ) -> 1e+21   re-stringified -> 1e+21
  a naive digit-count guard misses this shape entirely:
    text          : 1e+21
    /^\d{16,}$/   : false   <- the guard does not fire

정확히 10의 21승부터 지수 표기가 된다. 그 아래인 10의 20승까지는 숫자를 그대로 늘어놓는다. 이 경계는 언어 사양이 정한 것이고 임의로 바뀌지 않는다.

실무에서 이것이 왜 문제인가. 마지막 두 줄이 답이다. 16자리 이상을 찾는 정규식이 1e+21에는 반응하지 않는다. 텍스트가 다섯 글자이기 때문이다. 자릿수 검사를 통과하면서 실제로는 자릿수를 21자리나 잃은 값이 그대로 통과한다.

  • 다시 파싱하면 원래 자릿수는 돌아오지 않는다. 1000000000000000000000과 1e21은 같은 값으로 취급된다
  • 대문자 1E21도 같은 값으로 읽힌다. 검사 정규식에서 대소문자를 빠뜨리는 실수가 흔하다
  • 이 구간의 값은 식별자로 쓰이는 일이 드물지만, 누적 합계나 바이트 수에서는 도달한다
  • 그래서 진단 절차에는 지수 표기 탐색이 별도 항목으로 들어가야 한다

12. DB와 CSV를 거칠 때

JSON만의 문제인지 확인하기 위해 저장 계층을 거쳐 봤다. 같은 값을 정수 컬럼, 실수 컬럼, 텍스트 컬럼에 각각 넣었다.

python 3.13.3 / win32   sqlite 3.49.1

1234567890123456789  1234567890123456789 1.2345678901234568e+18 1234567890123456789

결정하는 것은 값이 아니라 컬럼 타입이다. 정수 컬럼에서는 19자리가 그대로 나왔고, 실수 컬럼에서는 같은 값이 1234567890123456768로 바뀌었다. 실수 컬럼에 넣은 순간 JSON에서와 똑같은 손실이 일어난다.

DB의 JSON 함수도 확인했다. 여기서 같은 엔진 안에서도 경로에 따라 결과가 갈린다는 것이 드러난다.

  • JSON 텍스트에서 값을 뽑는 함수는 정수 타입으로 정확히 돌려줬다. 19자리가 보존됐다
  • 같은 값을 실수로 변환해 JSON 객체를 만들면 1.23456789012346e+18이 됐다. 정밀도가 15자리로 줄었다
  • 1e21은 실수 타입으로 인식됐다. 즉 텍스트 표기가 저장 타입을 결정하기도 한다

CSV와 스프레드시트 경로도 봤다. 여기가 특히 중요한 이유는 정산 자료가 엑셀로 오간다는 현실 때문이다.

--- 11-9. CSV round trip, and the spreadsheet layer ---
  csv text written:
    order_id,amount,note
    1234567890123456789,19.99,big id
    9007199254740993,0.10,boundary
    1000000000000000000000,100.00,exponent shape
  csv reader gives strings, so nothing is lost at this layer:
    1234567890123456789      exact: True   type: str
    9007199254740993         exact: True   type: str
    1000000000000000000000   exact: True   type: str
  but the moment a layer converts to a number:
    1234567890123456789      -> float -> 1234567890123456768      exact: False
    9007199254740993         -> float -> 9007199254740992         exact: False
    1000000000000000000000   -> float -> 1000000000000000000000   exact: True

CSV 자체는 안전하다. 파일에는 텍스트가 그대로 들어가고, 읽어도 문자열로 나온다. 이 계층에서는 아무것도 잃지 않았다.

문제는 어떤 계층이 숫자로 바꾸는 순간이다. 아래쪽 블록에서 같은 문자열이 실수를 거치자 정확히 JSON에서와 같은 손실이 났다. 스프레드시트 소프트웨어는 숫자로 보이는 열을 자동으로 숫자로 해석하므로, 사람이 파일을 한 번 열었다 저장하는 것만으로도 이 변환이 일어날 수 있다.

마지막으로 언어를 건너는 실제 교환을 파일로 해 봤다. 이 글의 논지를 가장 직접적으로 증명하는 출력이다.

    {"order_id": 1234567890123456789, "amount_minor": 1999, "ratio": 0.1}
  sha256 of the bytes python wrote : 1eaf7010a66fad8180d5ff17a3e0ce41

--- 11-11. node reads the file python wrote ---
  bytes on disk : {"order_id": 1234567890123456789, "amount_minor": 1999, "ratio": 0.1}

  • 다른 언어가 그 파일을 읽고 아무 오류 없이 파싱했다
  • 다시 쓴 텍스트의 해시가 원본과 다르다. 바이트가 바뀌었다는 뜻이다
  • 이 교환 전 과정에서 예외는 한 번도 발생하지 않았다. 로그에도 남지 않는다

13. 중복 키·키 순서·정규화 해시

숫자만큼 자주 얽히는 주변 문제들을 같은 실행에서 확인했다.

--- 13-1. duplicate keys: last one wins, silently ---
  JSON.parse({"id":1,"id":2,"id":3}) -> {"id":3}
  a signed payload can carry two values for the same field, and two
  parsers can disagree about which one is real

--- 13-2. key order is not preserved the way you think ---
  input  : {"b":1,"2":2,"a":3,"1":4}
  output : {"1":4,"2":2,"b":1,"a":3}
  integer-like keys are reordered ahead of the rest by the object model

--- 13-3. canonicalize before hashing, or the signature breaks ---
  a raw sha256      : 342ae634b438dfbe6c65969e
  b raw sha256      : 760edb200363c660478ae117
  c raw sha256      : 6225dd8ec799896b92e0af16
  a canonical sha256: 85bdc381b4aff3953e97ddeb
  b canonical sha256: 85bdc381b4aff3953e97ddeb
  c canonical sha256: 85bdc381b4aff3953e97ddeb
  canonical form of a : {"amount":19.99,"id":1234567890123456800}
  and here is the catch:
    canonical form still contains 1234567890123456800
    which is NOT the id that was sent. canonicalization does not undo the loss.

세 가지가 나온다.

  • 중복 키는 마지막 값이 이긴다. RFC 8259는 이름이 유일해야 한다고 권고하면서, 유일하지 않을 때의 동작은 예측 불가능하다고 적어 두었다. 실제로 확인한 세 파서 모두 마지막 값을 택했지만, 이것은 보장이 아니라 관행이다
  • 키 순서가 재배치된다. 정수처럼 보이는 키가 앞으로 끌려 나왔다. 순서에 의미를 부여한 설계는 여기서 깨진다
  • 정규화하면 해시가 일치한다. 공백과 키 순서만 다른 세 텍스트가 정규화 후 같은 해시가 됐다

그런데 마지막 블록에 이 절의 요점이 있다. 정규화된 결과 안에 들어 있는 ID는 이미 손상된 값이다. 정규화는 표기 차이를 없애 줄 뿐, 사라진 자릿수를 되돌리지 못한다. 서명이 일치한다고 값이 원본이라는 보장은 없다는 뜻이다. 정규화 해시로 무결성을 확인하는 시스템은 이 점을 별도로 방어해야 한다.

--- 13-4. escapes and lone surrogates in the same payload ---
  JSON.parse of \u escaped digits stays a string:
    value : 1234567890123456789   length : 19
  numbers cannot be escaped that way:
    JSON.parse of an escaped bare digit -> SyntaxError
  JSON.stringify of a lone surrogate : "\ud800"  (well-formed output, ES2019)
    code unit : U+D800
    round trip identical : true
  and a number-shaped string is not a number:
    JSON.parse('"1e21"') typeof : string

--- 11-6. key order and duplicate keys, third parser ---
  decode of three identical keys -> id = 3
  canonical encode of {b,a,c}    -> {"a":2,"b":1,"c":3}
  default encode of the same     -> {"c":3,"b":1,"a":2}
  • 문자열 안의 숫자는 유니코드 이스케이프로 써도 문자열이다. 손상되지 않는다
  • 반대로 숫자 리터럴은 이스케이프할 수 없다. 이스케이프한 순간 구문 오류다
  • 짝 없는 서로게이트는 직렬화 시 이스케이프 형태로 안전하게 출력됐고 왕복도 동일했다
  • 숫자처럼 생긴 문자열은 여전히 문자열이다. 1e21을 따옴표에 넣으면 숫자가 되지 않는다
  • 펄에서도 중복 키는 마지막 값이었고, 키 순서를 고정하는 옵션이 따로 있었다

14. 왜 항상 늦게 발견되는가

이 사고의 가장 고약한 성질은 기술이 아니라 시간에 있다. 발견이 늦는 이유가 구조적이다.

  • 개발 데이터의 ID가 작다. 1, 2, 3으로 개발하면 이 문제는 존재하지 않는다. 2절의 출력대로 16자리까지는 전부 정상이다
  • 스테이징도 대개 작다. 실서비스 데이터를 그대로 쓰지 않는 것이 보통이므로 여기서도 안 걸린다
  • 초기 실서비스에서도 안 걸린다. 순번 방식이면 ID가 16자리에 도달하기까지 오래 걸린다
  • 터지는 시점은 ID 체계를 바꿀 때다. 순번에서 분산 ID로 옮기거나, 타임스탬프 기반 ID를 도입하거나, 다른 시스템의 ID를 받아 오기 시작할 때 갑자기 19자리가 들어온다
  • 그 시점에는 코드가 이미 여러 곳에 있다. 처음 설계할 때는 한 곳만 고치면 됐을 것이 이제 전 구간이다
  • 테스트가 전부 통과한다. 기존 테스트 픽스처의 ID가 작기 때문이다. 새 코드를 짜도 옛 픽스처로 검증하면 여전히 통과한다

대응은 단순하다. 개발 데이터에 19자리 ID를 섞어 두는 것이다. 픽스처 하나만 바꿔도 이 문제는 개발 단계에서 드러난다. 비용이 거의 들지 않는데 효과는 가장 크다.

덧붙여, 이 문제가 이미 일어났는지 확인하는 방법도 있다. 로그나 감사 기록에서 같은 필드의 값이 끝 한두 자리만 다른 쌍을 찾는 것이다. 앞자리가 완전히 같고 뒤만 다른 값이 반복해서 나타난다면, 그것은 우연이 아니라 이미 발생한 사고의 흔적이다.

15. 진단 절차 - 이미 도는 API에서 찾는 법

운영 중인 API를 점검하는 순서를 실행으로 만들었다. 핵심 원칙은 하나다. 파싱된 객체가 아니라 원문 텍스트를 봐야 한다.

--- 12-2. a scanner: find at-risk numbers in a payload without parsing it as numbers ---
  payload under test:
    {"order_id":1234567890123456789,"user":{"id":42,"wallet":9007199254740993},"items":[{"sku":"A-10
    0","qty":2,"price":19.99},{"sku":"B-200","qty":1,"price":1234.50}],"total":1274.48,"trace":"01012345678901234567","big":1e21,"epoch_ns":1753833600123456789}

  --------------------------------------------------------------
  order_id=1234567890123456789 AT RISK  integer past 2**53-1

  qty=2                       safe

  qty=1                       safe

  total=1274.48               safe
  big=1e21                    AT RISK  exponent form, magnitude 1e+21
  epoch_ns=1753833600123456789 AT RISK  integer past 2**53-1

  because by then the original digits are already gone.

이 스캐너는 JSON을 숫자로 파싱하지 않고 텍스트에서 리터럴을 찾는다. 그래야 손상 전의 값을 볼 수 있다. 결과에서 네 가지 유형이 잡혔다.

  • 2의 53승을 넘는 정수 세 건. 주문 ID, 지갑 잔액, 나노초 시각이다
  • 지수 표기 한 건. 앞 절에서 본 그 구멍이다
  • 표기가 바뀌는 소수 한 건. 1234.50이 1234.5가 된다
  • 문자열 안에 든 20자리 숫자는 잡히지 않았다. 이것이 옳은 동작이다. 문자열은 손상되지 않는다

계약 테스트에 넣을 값 목록도 뽑았다. 표본이 아니라 경계값으로 검증해야 한다는 2절의 결론을 실행 가능한 형태로 만든 것이다.

  • -9223372036854775808은 정확하다. 2의 거듭제곱이라 그렇다. 음수 쪽만 확인하면 통과한다

  • 소수는 대부분 통과한다. 정수와 소수의 위험도가 다르다는 것이 이 표의 결론이다

17. 단정하지 않은 것

이 글에서 확인한 범위와 확인하지 못한 범위를 구분해 둔다.

  • 모든 언어를 확인하지 않았다. 확인한 것은 JavaScript, Python, Perl, 그리고 SQLite뿐이다. 다른 언어와 다른 파서 구현은 또 다르게 동작할 수 있다
  • 같은 언어 안에서도 파서가 여럿이다. 여기서 본 것은 각 언어의 기본 구현이고, 대체 파서는 옵션과 동작이 다르다
  • 버전 의존성이 있다. 리바이버에서 원본 텍스트를 받는 기능은 비교적 최근 사양이고, 이전 런타임에는 없다. 「이 환경에서 됐다」가 「어디서나 된다」는 아니다
  • 금액 실험의 결론을 일반화하지 않았다. 이 표본에서는 실수 합계와 정수 합계가 일치했다. 다른 표본에서는 어긋난다. 이 글은 그 차이가 표본에 의존한다는 것만 말한다
  • 스프레드시트 소프트웨어 자체는 실행하지 않았다. CSV 텍스트 계층과 숫자 변환 계층만 확인했다. 특정 제품의 동작은 별도로 확인해야 한다
  • 성능은 재지 않았다. 문자열 식별자가 색인과 조회에 얼마나 부담이 되는지는 데이터 규모에 따라 달라지므로 각자 측정해야 한다

마치며: 표준이 규정하지 않은 자리

이 문제를 한 문장으로 다시 적으면 이렇다. JSON 표준은 숫자의 정밀도를 규정하지 않았고, 그 빈자리를 각 언어가 자기 방식으로 채웠다. 그 선택이 서로 다르기 때문에, 양쪽이 각자 정상 동작하면서도 값이 어긋난다.

그래서 이 문제는 코드에서 고칠 수 없다. 파서를 바꿔도, 라이브러리를 바꿔도, 언어를 바꿔도 다음 소비자가 다른 언어면 다시 일어난다. 고칠 수 있는 곳은 계약 하나뿐이다. 어떤 값을 어떤 형태로 주고받을지 적어 두는 것, 그리고 그것을 경계 테스트로 상주시키는 것.

당장 할 수 있는 가장 값싼 조치를 하나만 고르라면 개발 데이터에 19자리 ID를 하나 섞어 두는 것이다. 픽스처 한 줄이면 된다. 그 한 줄이 없어서 이 사고는 언제나 실서비스에서, ID가 커진 다음에, 고객 문의로 발견된다.

# JSON 숫자 정밀도 — 타입 결정표와 경계 테스트 값

> 출처: braindetox.kr — JSON에 담은 64비트 ID의 끝자리가 바뀐다
> 근거: Windows 10 / Node 22.16.0 / Python 3.13.3 / Perl 5.38.2 (JSON::PP 4.16) / SQLite 3.49.1 실행 검증
> 규격: RFC 8259 Section 6 — 정수 상호운용 구간은 -(2^53)+1 부터 (2^53)-1

## 1. 한 줄 요약

JSON 표준은 숫자의 정밀도를 규정하지 않는다. 깨지는 것은 파서(언어)의 선택이다.
보내는 쪽과 받는 쪽의 언어가 다르면 **예외 없이 조용히** 값이 달라진다.

## 2. 데이터 성격 → 타입 결정표

| 데이터 성격 | 예 | JSON에 담을 형태 | 이유 | 확인 방법 |
|---|---|---|---|---|
| 식별자 (연산 안 함) | 주문번호, 사용자 ID, 스노플레이크 ID | **문자열** | 산술이 필요 없다. 자릿수 보존이 유일한 요구사항 | 왕복 후 문자열 비교가 완전 일치하는지 |
| 시각 (나노초) | epoch_ns, 트레이스 타임스탬프 | **문자열** 또는 밀리초 정수 | 나노초 19자리는 2^53 을 넘는다 | 19자리 샘플을 왕복시켜 뒷자리 확인 |

| 큰 수 지수 표기 전환 | 1e21 부터 | 정수는 전환 없음 | 정수는 전환 없음 | REAL 은 전환 |

## 5. API 계약 점검 문장 (그대로 명세·리뷰에 붙이기)

- 이 필드는 **식별자**이며 산술 대상이 아니다. JSON 문자열로 전송하고, 최대 길이는 20자다.
- 이 필드는 JSON 숫자로 전송하며, 값은 항상 -(2^53)+1 이상 (2^53)-1 이하임을 보증한다.
- 금액 필드는 통화의 **최소단위 정수**로 전송한다. 단위와 통화 코드를 같은 객체에 함께 담는다.
- 응답에 NaN, Infinity, -Infinity 는 나타나지 않는다. 측정 불가는 `null` 로 표기한다.
- 소비자는 숫자 필드를 배정도 실수로 파싱해도 손실이 없음을 가정할 수 있다.
- 스키마에 `type: integer` 와 `format: int64` 를 함께 적되, `format` 은 문서적 표기이며 언어별 파서를 강제하지 않는다는 점을 명시한다.
- 클라이언트가 식별자를 다시 보낼 때 **받은 텍스트를 그대로** 되돌려 보낼 것을 요구한다.

## 6. 진단 절차 (이미 운영 중인 API에서)

1. 응답 **원문 텍스트**를 확보한다. 파싱된 객체를 보면 이미 늦었다.
2. 원문에서 16자리 이상 정수 리터럴을 찾는다. 문자열 안의 숫자는 제외한다.
3. 찾은 리터럴을 `2^53-1` 과 비교한다. 초과하는 것이 하나라도 있으면 위험이 확정된다.
4. 지수 표기(`e`, `E`)가 든 리터럴을 따로 찾는다. 자릿수 검사만으로는 걸리지 않는다.
5. 소수 리터럴은 재직렬화 결과와 **문자열로** 비교한다. 뒤 0 과 자릿수가 사라지는지 본다.
6. 로그와 감사 기록에서 같은 필드의 값이 **끝 1~2자리만** 다른 쌍을 찾는다. 이미 발생한 사고의 흔적이다.
7. 경계 테스트 값(3절)을 계약 테스트에 넣고, 값 비교가 아니라 문자열 비교로 단정한다.

| 지점 | 할 일 | 하지 말 것 |

| 서버 직렬화 | 식별자를 문자열로 내보낸다 | 숫자로 내보내고 클라이언트에 맡기기 |

## 8. 하지 말 것

- 파싱한 뒤에 큰 정수를 문자열이나 큰수 타입으로 바꾸는 것 — 그 시점에 자릿수는 이미 사라졌다
- 자릿수만 세는 검사 — 지수 표기가 그 검사를 빠져나간다
- 값이 같은지(`==`)로 왕복을 검증하는 것 — 손실된 값끼리는 서로 같다
- 낮은 ID로만 개발·테스트하는 것 — 실서비스에서 ID가 커진 뒤에 터진다
- 정규화 후 해시 비교로 무결성을 확인하는 것 — 정규화는 이미 사라진 자릿수를 되돌리지 못한다
- 「문자열로 보내면 끝」이라고 여기는 것 — 정렬·범위 조회·비교 비용을 어디서 감당할지 정해야 한다
