1. Limitations of Single-Device Benchmarks and the Problem Space

In general, classic filesystem performance evaluations have centered on quantifying sequential throughput across a single isolated storage unit.

The original documentation states that traditional filesystem benchmarks run fio on a single block device with default mkfs options. The original text points out that this conventional approach says nothing about what modern copy-on-write filesystems are actually deployed for in production environments. The source documents that Bartosz Fenski (fenio) engineered the modern-fs-benchmark suite to measure the internal machinery of multi-device copy-on-write (CoW) filesystems including btrfs, ZFS, and bcachefs.

The original text notes that the project comprehensively exercises operational boundaries that single-device ext4-style benchmarks never touch. Specifically, the source documents the target evaluation phases as 「redundancy layouts, snapshot aging and scaling, transparent compression, encryption (native vs LUKS), reflinks, fsync tail latency, degraded operation and rebuild, corruption self-healing, and near-full/ENOSPC behavior」. The source indicates that layered stacks featuring ext4 and XFS over md and LVM are included side by side as classic-stack baselines.

In this article's interpretation, the project deliberately shifts attention away from synthetic throughput competitions toward measuring degradation curves and resilience limits under hostile operating conditions. The original documentation explicitly emphasizes that benchmark charts typically invite an unhelpful debate over which filesystem is fastest. The original author asserts that for long-term storage, the proper question is not who wins the podium, but which storage stack tells you the truth about your data. In this article's interpretation, the entire evaluation methodology is tuned to verify software defensive posture rather than raw speed under pristine conditions.

  • Shortcomings of single-device testing: running fio against default mkfs targets ignores complex multi-disk pooling behaviors
  • Core focus of modern-fs-benchmark: quantifying snapshot fragmentation costs, self-healing scrub mechanics, and tail latencies
  • Paradigm shift in benchmarking: abandoning raw peak throughput races to isolate verifiable data integrity guarantees

2. Classification of the 26 Default Matrix Configurations

In general, even within identical filesystem families, pairing block devices through different volume managers or redundancy schemes alters I/O pipelines substantially.

The original source documents that the default evaluation matrix, codified inside .github/workflows/bench.yml, contains exactly 26 distinct storage configurations. The original text lists ext4, XFS, btrfs, bcachefs, and ZFS as the covered filesystem families. The source methodically groups these configurations from single-device baselines up through layered RAID, native CoW pools, specialized encryption wrappers, and hybrid stacks.

The original documentation records that for single-device btrfs, the -m single parameter is explicitly specified to avoid the default DUP metadata allocation that would double metadata write overhead compared to other rows. In testing encryption variants, the original source specifies that ZFS native per-dataset AES-256-GCM (mirror-enc) and bcachefs native whole-filesystem ChaCha20/Poly1305 (replicas2-enc) are evaluated. For btrfs, which lacks native encryption, the source documents the use of raid1-luks where LUKS wraps each physical device individually, while ext4 employs md-raid10-luks where a single LUKS container sits above the md layer.

The original text documents dual-parity (RAID6-class) evaluations comparing ZFS raidz2, btrfs -d raid6 -m raid1c3, ext4 over md raid6, and bcachefs configured with --erasure_code --replicas=3. The source notes that btrfs pairs raid6 data with raid1c3 metadata because parity metadata is actively discouraged due to write-hole vulnerability. The documentation confirms that erasure coding in bcachefs has been marked stable since version 1.37 and is architecturally write-hole-free because writes replicate first before background reconciliation stripes them.

The original author includes practical Franken-stacks such as XFS layered on top of a ZFS zvol, providing standard XFS semantics while inheriting ZFS snapshots, compression, and underlying self-healing. Furthermore, the source documents an XFS configuration on LVM raid10 combined with dm-integrity (--raidintegrity y), providing per-sector checksumming to quantify the exact performance penalty required for a classic stack to match CoW data guarantees. In this article's interpretation, evaluating these hybrid production combinations prevents theoretical bias by directly measuring realistic system administrator workarounds.

The original source documents that ZFS is evaluated both at its default 128KB recordsize and separately at recordsize=8k across striped mirror pairs. The author describes this as a single-variable proof demonstrating how much of ZFS small-random-write overhead stems from default configuration choices rather than intrinsic architectural design. The original documentation states that bcachefs kernel modules are compiled via DKMS from apt.bcachefs.org because bcachefs moved outside the Linux mainline tree in kernel 6.17. In this article's interpretation, isolating specific parameters across uniform storage topologies prevents broad architectural generalizations from obscuring configuration nuances.

  • Baseline isolation: incorporating single-device ext4 and XFS rows enables isolating baseline CoW software costs
  • Encryption topology comparison: evaluates native per-dataset encryption against layered per-device LUKS overheads
  • Parity write-hole isolation: documents architectural approaches to parity metadata integrity across btrfs, ZFS, and bcachefs
  • Single-variable recordsize tuning: compares ZFS 128KB and 8KB blocks to quantify allocation penalties precisely

3. Measurement Metrics and Corruption Verdict Criteria

In general, common storage benchmarks restrict their measurement scopes to buffered sequential read and write operations on pristine volumes.

The original source documents that modern-fs-benchmark executes more than 14 distinct test phases, ranging from initial host calibration to out-of-band corruption recovery. The documentation explains that trivial-op latency testing schedules one 4KB write followed by fsync every 200ms, tracking both p99 and worst-case completion latencies to mimic interactive shell history additions and editor swap writes during heavy 1MB background streaming. In the source-tree operations phase, the benchmark creates a 20,000 small-file directory tree, measures cold recursive copy operations (cp -r), and tests recursive directory removals (rm -rf).

The original text documents that large-directory scalability testing populates 100,000 empty files within a single directory, performs cold name enumeration, executes cold and warm metadata stat checks across every entry, and finally deletes the structure. In the snapshot aging phase, the suite records random-overwrite bandwidth degradation as snapshots accumulate, taking up to 100 snapshots where technology limits permit. The documentation notes that ZFS at default 128KB recordsize is capped at 10 snapshots because it pins nearly the entire file per snapshot, while legacy LVM snapshots are capped at 8 due to copy-on-write amplification, with both caps identified as technological findings rather than benchmark shortcuts.

The original documentation notes that near-full and ENOSPC phases test sustained write throughput at 95% and 99% capacity before filling the filesystem to hard ENOSPC, explicitly verifying whether files can still be deleted and whether deletion restores write capabilities. In operational systems, disk space allocation anomalies and inode exhaustion dynamics exhibit varied behavioral patterns across filesystems, as explored in No space left on device While the Disk Is Not Full - Inodes and Open Files. The source notes that btrfs encounters its 1GB chunk allocation limit before reported df capacity crosses targets on small virtual arrays.

The original text records that during corruption testing, a 2GB raw data range is directly overwritten onto one block device behind the filesystem's back, followed by an immediate scrub. The source specifies three distinct verdict categories when comparing MD5 hashes of tracked test files after the scrub. A SURVIVED verdict indicates that the scrub completed, the tracked test file remained readable, and its MD5 hash matched original data. A FAIL verdict is assigned if files return corrupted content or if read operations fail. An UNPROVEN verdict is assigned when checksum-less stacks produce matching hashes, as survival cannot be proven without active cryptographic checksums.

The source documentation emphasizes that classic md and LVM RAID arrays protect against missing disks but offer no protection against lying hardware, returning corrupted data to user applications with zero reported errors. In this article's interpretation, elevating silent data corruption detection to a primary benchmark outcome reflects real-world disaster scenarios where bad blocks silently propagate into backup snapshots. The systemic hazards of unverified data degradation propagating unnoticed into backup rotations mirror the integrity principles detailed in Backups Are Not Simple Copies - Retention Cycles and Integrity Verification.

4. Shared Virtual Machines on GitHub Actions and Reliability Principles

In general, cloud-based continuous integration environments host multiple tenants competing dynamically for underlying physical hardware.

The original text documents that modern-fs-benchmark runs inside GitHub Actions shared virtual machines where all target block devices are loop files residing on a single virtual disk. Because of this configuration, the author emphasizes that 「all 'devices' live on one virtual disk」 and 「absolute MiB/s is meaningless」. The documentation states that the test suite was purposefully constructed to analyze relative performance shapes and ratios rather than absolute throughput ceilings.

The source documentation establishes clear reliability principles for interpreting results. Comparisons within the same continuous integration job are directly meaningful because all targets share the exact same virtual machine and physical disk at that moment. When comparing across different filesystems, the author instructs readers to treat small differences spanning tens of percent as environmental noise, while large performance gaps exceeding a 2x factor are treated as genuine architectural differences. In this article's interpretation, openly documenting runner constraints establishes realistic confidence intervals and prevents over-interpreting cloud virtualization artifacts.

The original text explains that multi-run trend lines accumulated over continuous automated repetitions are used to validate findings rather than relying on isolated snapshot runs.

  • Virtual machine disk sharing: loopback devices coexisting on one host disk invalidate raw MiB/s metrics
  • Shape-oriented observation: emphasizes comparative degradation curves and scaling ratios within identical runs
  • Statistical noise thresholding: treats differences below 2x as potential noise while tracking 2x+ divergence as real
  • Longitudinal data accumulation: aggregates hundreds of pipeline executions to isolate consistent behavioral trends

5. Version Recording Mechanisms and the Results Dashboard

In general, out-of-tree kernel modules cannot be reliably identified by inspecting the host operating system release string alone.

The original source notes that for out-of-tree filesystems such as ZFS and bcachefs, the Linux kernel version alone fails to specify what code actually executed. The author explicitly specifies that 「Every result records the exact tools and kernel-module versions tested — essential for ZFS and bcachefs, which are out-of-tree, where the kernel version alone doesn't identify what actually ran」. The documentation states that userspace utility commits and kernel module releases are stored in the raw JSON output and presented across dashboard tables.

The original text documents that aggregate benchmark runs are published directly to an interactive public dashboard at https://bartosz.fenski.pl/modern-fs-benchmark/. The dashboard provides per-metric bar charts sorted best-first, snapshot aging degradation curves, and longitudinal trend lines across historical executions, with filtering controls for filesystem families and layout classes. The documentation records that the web interface supports linear and logarithmic scaling modes alongside sortable metric tables, while raw execution history is preserved on the results-data repository branch. In this article's interpretation, publishing verifiable metadata artifacts guarantees that external researchers can validate environmental parameters independently.

  • Out-of-tree version tracking: records exact git revisions and DKMS module versions for ZFS and bcachefs
  • Multi-dimensional filtering: enables isolating specific configurations such as btrfs versus bcachefs across multi-disk setups
  • Persistent raw telemetry: preserves execution datasets on the results-data branch for independent analysis

6. Local Reproduction Environment and Execution Workflow

In general, modern open-source benchmark suites provide standalone initialization scripts to streamline local testing workflows.

The original text states that the suite's source code is licensed under the Apache License 2.0, while accumulated performance datasets are licensed under CC-BY 4.0. The documentation outlines a direct two-step execution workflow for developers reproducing benchmarks in local environments. The exact commands provided by the author are:

sudo scripts/install-deps.sh <fs>
sudo scripts/run-bench.sh <fs> <layout>

The original documentation notes that local test executions utilize sparse loopback files, eliminating the requirement for dedicated physical multi-disk testbeds. The author explains that evaluating configurations on physical bare-metal hardware requires dedicated block devices wired directly to the system. In this article's interpretation, abstracting complex block-layer setups behind clean CLI helper scripts lowers barriers for third-party filesystem testing.

  • Open-source licensing: permissive Apache 2.0 software licensing paired with CC-BY 4.0 dataset distribution
  • Minimalist CLI interface: dependency resolution and test execution orchestrated through two straightforward scripts
  • Loop device abstraction: enables local developers to reproduce multi-device storage topologies without dedicated hardware

7. Author's Defense of Methodology and Community Criticism

In general, releasing experimental storage benchmarks to engineering communities prompts rigorous debate regarding testbed validity and environmental controls.

The original documentation points to a detailed discussion thread on Hacker News (item?id=49768833) examining the testbed's design parameters. Community participant Farmadupe challenged the methodology, arguing that testing on non-baremetal virtualization renders results incomparable and inquiring whether noisy neighbors on shared storage skew measurements. Specifically, Farmadupe stated: 「if you're not using baremetal for such tests, it's likely that the results are simply not comparable at all? What if another tenant is also using the disk?」.

The original author, Bartosz Fenski (fenio), candidly acknowledged that virtualization noise and neighbor interference exist on shared runners. In his reply, fenio admitted: 「Obviously they could and probably were noisy neighbours」, directly validating the community's observation regarding cloud runner variability. However, the author defended the project's statistical validity by highlighting test volume.

In his comment, fenio stated: 「there are 593 runs recorded so average should still be quite meaningful」, asserting that aggregating hundreds of runs dampens stochastic host noise. Furthermore, the author revealed ongoing efforts to deploy tests onto physical bare-metal infrastructure utilizing Hetzner servers equipped with SAS HDDs. Describing physical execution constraints, fenio noted that 「one run on REAL hardware takes much more time than on GH runner so it's slow」, explaining why bare-metal test iterations accumulate gradually.

In this article's interpretation, openly admitting runner limitations while progressively accumulating statistical volume and investing in physical hardware reflects a disciplined, pragmatic engineering approach.

  • Community skepticism: questioning whether virtualized runner disks invalidate cross-filesystem performance comparisons
  • Transparent author admission: directly acknowledging that neighboring virtual machines introduce I/O interference
  • Statistical defense: relying on averages across more than 593 recorded runs to establish meaningful baseline curves
  • Bare-metal physical testing: expanding verification onto Hetzner servers and SAS HDD arrays to cross-check virtual runner data

8. What Could Not Be Verified

During the compilation of this analysis against primary source code and public discussion records, the following items could not be confirmed with definitive figures and are detailed here.

  • Because the dashboard (bartosz.fenski.pl/modern-fs-benchmark/) continuously updates in real time, the exact cumulative execution count and specific metrics beyond the documented snapshot could not be fixed as a single static figure.
  • The comprehensive benchmark figures and final comparative datasets for ongoing bare-metal testing on Hetzner servers and SAS HDDs have not been published in full, preventing exhaustive physical performance comparisons.
  • The exact quantitative I/O interference margins and noisy-neighbor disk contention levels experienced across individual GitHub Actions runners remain private platform metrics and could not be independently audited.
