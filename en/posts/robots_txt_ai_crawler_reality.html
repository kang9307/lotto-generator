Introduction: before you add that one line

Your access log has filled up with automated requests carrying names you have never seen. Thousands a day, sweeping the same listing pages. The thought that follows is almost always the same one. Add a line to robots.txt.

What that line does is the subject of this article. The short answer is that it changes nothing about your server. The only thing it changes is the behaviour of whoever decided to read the file.

There is a reason the question came back around. A record was published of someone opening the robots.txt of fifteen major Korean platforms one by one and cataloguing their AI crawler policies. The method was to fetch and read each site's publicly served robots.txt directly. The first pass was on 27 July 2026 and a re-check at the level of individual bot names followed on 27 August 2026. One site was dropped because a rate limit response prevented the file from being retrieved at all. The results split four ways, from full blocking to no restriction, and somewhere in between sat the cases that treat training collectors and AI search collectors differently.

Which company landed in which column is not covered here. Copying the name tags across turns the subject into who behaved well, and that is not the interesting part. The interesting part is that the same syntax in the same file produces completely different outcomes depending on who is reading. This article looks at that structure. It does not describe how to obtain anything from a place that has been blocked, and it recommends neither collecting nor blocking everything. Both carry a cost, and the point here is to hand you the axes for calculating that cost.

1. What robots.txt actually does - a request, not a block

The Robots Exclusion Protocol began as a convention in 1994 and was only written up as IETF standards track document RFC 9309 in September 2022. It ran on de facto agreement for nearly thirty years before the document caught up, and the phrasing that document opens with is a summary of this whole article. The specification describes rules that crawlers are requested to honor. It does not say must.

1.1 A server refusing versus a file asking

The difference lies in where the request ends. When a server blocks, the request reached its destination and a refusal came back as the response. A status code demanding authentication or denying access goes out, and the body does not. Even if the client decides to ignore the refusal, there is nothing left to receive.

robots.txt works differently. It is an ordinary text file served normally to anyone who asks, and whatever paths you write inside it, the way the server handles those paths does not change in the slightest. A request arrives at a disallowed address and the server delivers the page as usual. The only place the rule executes is inside the crawler's own code, and an outcome exists only when that code fetches the file, interprets it, and voluntarily folds its own behaviour.

The specification does not hide this. Its security considerations section states that the protocol is not a substitute for valid content security measures. If something needs access control, do it at the layer that controls access.

One side effect. Any path written into a disallow rule is thereby published. robots.txt is fetchable by anyone, so writing your admin paths into it draws a map for whoever wants one. Hiding something and reducing crawl load cannot be handled with the same tool.

1.2 What the specification pins down - and what that implies

What RFC 9309 standardised was interpretation, not force. Listed out, the character of it becomes obvious.

  • Parsers must handle at least 500 kibibytes. Anything past that in a larger file may be ignored without violating the specification
  • A fetched file should not be reused beyond twenty-four hours. Do not assume a rule you edited today takes effect immediately
  • When rules overlap, the most specific one wins, and specificity is counted by length
  • If the file returns a not-found response, a crawler may treat everything as allowed
  • If it returns a server error, the crawler must instead assume a complete disallow. A brief hiccup in serving the file can stop indexing wholesale

Read those five again and the common thread appears. Every one of them governs what the reading side ought to do. Nowhere is there a statement about what happens if it does not. If the syntax itself is what you need, that is written up separately in the complete guide to robots.txt syntax and crawl optimisation. This article looks at the premise underneath the syntax.

2. A rule that rests only on a promise

A convention with no enforcement survived thirty years because compliance was profitable. For search operators robots.txt was a convenience rather than a burden. Sites voluntarily marked the places not worth fetching, crawl costs fell, and a reputation for honouring the rules became an asset in the next negotiation.

2.1 Where compliance and non-compliance divide

The structure reduces to one sentence. Only those with reputation to lose comply. Whether the rules are honoured is therefore decided not by technology but by the other party's business model.

  • A crawler selling a service under its own brand loses a great deal by breaking the rules. It lands on block lists and negotiates from a weaker position
  • Operators that also publish their address ranges and a verification procedure are harder to excuse, because non-compliance can be checked after the fact
  • A collector that declares neither name nor affiliation has nothing to lose. The rules impose no cost on it at all
  • The middle ground is the murkiest. Some access paths are classified by their own operators as outside the scope of the rules, on the grounds that a user asked for a specific page rather than a crawler sweeping automatically

Since 2025 there have been several reported cases of infrastructure providers publicly accusing a crawler of collecting around the rules. I am not going to carry individual names across here. What matters is not any one company's conduct but that when it happens, the convention contains no working remedy at all.

2.2 What happens when voluntary compliance is actually measured

A public study published in 2026 measured how far an automated counterpart honours a signal asking it to stand down. Among agents that received an access-deny signal, the rate of actually withdrawing split between cases at 100% and cases landing at 55 to 75%. That measurement, however, targeted SSH, database, and container orchestration protocols, not robots.txt. The figures cannot be carried over literally.

What can be carried over is the character of the finding. The effect of a deny signal is determined by the implementation that receives it, not by the party that sent it. The same signal in the same format produces divergent outcomes. robots.txt is not a wall but a sign, and a sign's force depends on the disposition of whoever reads it.

3. Crawlers split by purpose - blocking one leaves the others

Automated requests used to mean search indexing and essentially nothing else. Now several strands with different purposes arrive under different names. And different names means the rules have to be written per name as well.

There is one public tally that gives a sense of the proportions. Classifying its news-related customer dataset as of July 2025, the content delivery network operator Cloudflare found that within AI crawler traffic, training purposes accounted for 79%, search purposes 17%, and access driven by user actions 3.2%. The sample is a specific industry's customer base, so it cannot be read as a web-wide average. What can be read is that the three strands differ in scale by more than an order of magnitude between the largest and smallest.

Two things to take from the table. First, blocking one leaves the others. A disallow on a single training name leaves the search names walking straight through. Second, list maintenance becomes a chronic debt. Names differ by operator and keep multiplying, and at the moment a new one appears your file is always the old list. 4. The blocker's dilemma - search visibility closes with it

The reason blocking everything does not work is simple. A large share of the people who reach you arrive riding the products of crawling. Search result listings and citation links inside AI answers both exist because collection happened first. A full block is a decision about reuse and simultaneously a decision to sever distribution.

4.1 Why the split is hard to make

  • Naming schemes differ by operator. Some divide into three, some into four. No common rule applies
  • Dual-purpose agents exist. When one name serves both indexing and training, you have no axis to split on
  • The file is per host. Each subdomain needs its own, and the one you forget is the one left open
  • Wildcards are convenient and therefore dangerous. One line against everything closes search indexing along with the rest
  • The other side's policy changes. When names are added or purposes reorganised, your rules go stale that day
  • Reversal is asymmetric. Blocking takes minutes; recovering an index takes far longer

4.2 What it really comes down to is the default

There is a decision that precedes how you write the rules. When an unfamiliar name shows up, is the default allow or deny? Blocking only the names you know springs a leak each time a new one appears, but never costs you a distribution path. Denying everything and opening only what you know is simpler to manage, but closes off a new search channel whose name you do not yet know.

Neither side is right in the abstract. The criterion, though, can be stated. Does your content generate value through search traffic, or do you sell the content itself? If the former, the former approach loses less; if the latter, the latter. Section 8 lays this axis out as a table.

5. The name is self-declared

On the left side of a rule sits a name. The string after User-agent: is a value the client picks and sends on its own. Nothing anywhere in the specification verifies that the value is true.

The consequence is this. The rule you wrote applies only to clients that chose to introduce themselves under that name. Introduce a different one and you are outside the rule, and your server responds as usual without ever noticing the difference. Control built on declared names holds only on the premise of honesty.

Verification is not entirely out of reach. Major operators publish the address ranges their crawlers connect from and document a procedure of chaining a reverse lookup with a forward confirmation to check authenticity. But that is not something robots.txt does. It is separate work you have to implement on the server side, and from there on it is the domain of code rather than of a file. Where judging a counterpart by its self-declared values goes wrong is covered in Is an empty User-Agent a bot - how to combine signals.

6. Which layer has real effect

What is covered here goes as far as which layer carries real effect. How to obtain something from a place that is blocked is outside the scope of this article, and not a single line goes in that direction.

Split into four layers and compared by character, each one's place becomes clear.

LayerWhat it doesCan it be ignoredWhat it costs
robots.txt declarationStates your intent publiclyYes. Simply do not read itAlmost nothing. No false positives either
Application responseDemands authentication or refuses with a status codeNo. There is nothing to receiveFalse positives in the logic, and upkeep
Edge layerLimits rate and connections at the delivery network and firewallHard toReal users cut off, plus operating cost
Terms and legalDisputes after the fact via terms, licences, copyrightTechnically, yesTime and money, weakening once borders are crossed

Read the table as a set of levers and the conclusion converges. Requests are actually stopped only at the layer that produces the response. robots.txt is where you write that decision down so others can see it, not where you enforce it.

That does not make the file useless. The two are a pair, not substitutes. Refuse at the response layer without declaring anything and even a crawler willing to comply gets nothing but errors and no reason. Declare without touching responses and nothing at all happens to the side that never intended to comply.

Do not invert the order. Rules at the edge layer cut people before they cut automation. Those cut off close the tab rather than filing a ticket, so your metrics record the successful blocks and never the people lost. The higher you climb toward the forceful layers, the more the thing to measure first is not accuracy but the cost of being wrong.

One addition. Response codes are themselves a statement of intent. Not right now and never again are expressed by different codes, and a well-built crawler reads that difference and adjusts its retry interval. If volume is the problem, limiting the rate and saying so in the code is cheaper for both sides than a disallow rule.

7. llms.txt and the newer proposals - adoption is everything

The vocabulary of robots.txt is narrow. In practice it can say come in and stay out, and little else. Conditions such as do not train on this but citation is fine, or allowed if attributed, have no syntax to be expressed in. The newer proposals mostly aim at that gap.

7.1 What llms.txt aims at and what it does not

llms.txt is a proposed Markdown file in which a site lays out where its documents worth reading are. It was never a blocking file; it is closer to a signpost. In practice, though, it often gets bundled under the heading of an AI file, and with that comes the expectation that creating it brings collection under control. That expectation does not hold.

The deeper problem is adoption. In its generative AI optimisation guidance updated on 15 June 2026, Google states that you do not need to create new machine readable files, AI text files, markup, or Markdown to appear in Search, because Google Search itself doesn't use them. A file the reading side has decided not to use is just text, however well its syntax was designed.

7.2 Standardisation is proceeding separately

The IETF has convened a working group specifically for AI usage preferences. Two strands are in progress.

  • A draft defining the vocabulary for expressing preferences. It is a working group document proceeding on the standards track
  • A draft defining how to attach that vocabulary to content. It covers attachment via both HTTP response headers and robots.txt, and has been adopted by the working group

Worth noting is that this effort does not discard robots.txt but layers vocabulary on top of it. That is precisely because the existing file is already in place. Both drafts, however, are not yet finished standards, and no deployment signal is in evidence.

The lesson here becomes the test to apply to every new proposal. A file's worth is decided by the number of parties reading it, not by its syntax. robots.txt has force not because its syntax is excellent but because thirty years of readers accumulated behind it. Adding a new file costs little, so by all means try it. Just do not expect it to be a mechanism that controls collection.

8. What a site operator actually has to decide

The reason no do this instruction appears here is that the right answer inverts depending on the nature of the content. What follows instead are the axes.

8.1 Five axes

  • Revenue structure - does search traffic create the value, or does the content itself get sold? This axis decides most of the rest
  • Reuse damage - is there anything genuinely lost when someone copies it wholesale? A company profile page and a paid database answer this in opposite directions
  • Traffic cost - is the pain right now reuse or request volume? If it is volume, this is a capacity problem rather than a copyright one, and the answer lives at a different layer
  • Reversal cost - how long does it take to reopen what you closed? Decisions touching the search index are the most expensive on this axis
  • Operating capacity - is there someone to revisit the name list each quarter? Without one, a meticulous list becomes a wrong list within months
Nature of the contentValue of search trafficDamage when reusedAxis to look at first
Ad-supported informational contentVery high. Traffic is the revenueModerate. Visits to the original fallSplit off training only, without closing distribution
Paid material and databasesLow. A preview is enough exposureLarge. The substance is copied outrightAuthentication at the response layer. The file is for declaring
Company profile and product docsHigh. Being found is the pointAlmost none. Citation is a net gainWeak grounds to block. Manage volume only
Community and user postsHighUser consent and personal data are at stakeTerms and notice come before damage arithmetic
Personal records and portfoliosModerateSmall, but there is an emotional costReversal cost is low, so experimenting is fine

8.2 The order

  1. Open the logs first. Writing rules without knowing what is actually arriving means blocking a problem you do not have
  2. Separate whether the pain is request volume or reuse. These two are solved at different layers
  3. If it is volume, look at rate limiting and caching first. A disallow rule is not a tool for reducing volume
  4. If it is reuse, settle the terms of use as a document, then reflect that in robots.txt where it can be seen
  5. For decisions touching the response layer, stage them in order of increasing reversal cost
  6. Revisit the name list and policy changes each quarter. What is not on a schedule does not get done

If what to look for in the logs is the unclear part, A year of fighting scrapers - how to tell from your logs covers those steps.

9. What crawling built - the cost of a full block

Read this far and automated collection can start to look uniformly bad. Honesty requires writing down the other side too.

  • Search - nearly every path by which a person finds anything on today's web sits on top of collection. Without crawling there is no search
  • Archives - the reason a vanished page still exists somewhere. Used for citation, for research, and sometimes as evidence in a dispute
  • Accessibility - the tools that convert an original into another form, screen reading and translation and summarisation, mostly presuppose automated collection
  • Research - web-scale corpora pushed language research and search quality forward. The tools in use today stand on that

So a full block carries a cost. The channel through which new readers arrive narrows, the ways to find your own writing later thin out, and maintaining the block becomes an operating expense in itself. And here is the part that stings most. Only those honest enough to declare a name get blocked, while those that declare nothing carry on. A block works only against a counterpart that follows rules, so the harder you push, the worse the composition of the traffic that remains can become.

The substance of the problem is less crawling itself than scale that grew without compensation. And that problem is settled in terms of use, contracts, and policy rather than in one line of a text file. robots.txt is where you record your intent while that discussion runs, not where the discussion ends.

10. What I could not verify

  • How many of the fifteen sites landed in each category is not stated in the source record. No counts appear in this article either
  • That survey verified only the contents of publicly served robots.txt files. Actual crawler access logs and whether anything was blocked at the server were not in scope. It is a reading of what the file declares, not a confirmation that anything was blocked
  • One of the targets was dropped because a rate limit response prevented the file from being retrieved. That site's policy is unknown
  • Public tallies measuring robots.txt compliance across a broad sample are scarce, and those that exist differ in sample, period, and judgement method to the point of being mutually incomparable. This article therefore uses no compliance rate figure at all
  • The deny-signal compliance measurement in section 2 targets SSH, databases, and container orchestration. It cannot be converted into a robots.txt compliance rate
  • The purpose breakdown in section 3 is based on one delivery network operator's news-related customer dataset. It is not a web-wide average, and other industries may compose differently
  • The IETF working group's attachment draft is at working group document stage, and no deployment or implementation signal is in evidence
  • Each operator's crawler names and purpose divisions rest on documentation the operators publish themselves. Whether the published description matches actual behaviour is not externally verified

11. Frequently asked questions

If I add a disallow rule to robots.txt, does that stop AI from using my writing?

No. Even with a rule in place, requests to that path are served exactly as before and the response goes out normally. The only thing that changes is the behaviour of a crawler that has code to fetch and interpret the file. RFC 9309 states that crawlers are requested to honour these rules, and no enforcement mechanism for non-compliance exists in the specification.

If there is no enforcement, is robots.txt worth maintaining at all?

It is worth keeping, but the expectation has to move. It is a place to declare, not to enforce. Most crawlers operated under a public brand read it and follow it, so a large share of the automated traffic you actually receive is shaped here, and excluding paths that waste crawl budget helps index quality. Above all, without a declaration even an honest crawler has no way to learn what you want.

I do not want my content used for training but I do want to appear in AI search. Is that possible?

In principle yes. Operators split names by purpose, so rules can be written per name. The hard part is maintenance. Names differ by operator, keep multiplying, and policies change. Writing one convenient disallow against every agent also closes the path into answer surfaces, so it is safer to schedule a quarterly review of the list alongside the rules.

Does creating an llms.txt file give me control over AI collection?

That is not what it is for. It was never a blocking file but a signpost to documents worth reading. And a file's worth is decided by how many parties read it, not by its syntax. In guidance updated in June 2026, Google states that you do not need to create new machine readable files or Markdown to appear in Search, because Search does not use them.

Where do I actually have to work if I want to reduce the requests themselves?

The layer that can refuse a request is the one producing the response: the application answering with status codes, or the delivery network and firewall in front limiting rate and connections. But when a judgement there is wrong, real people are cut off silently and that loss never shows in your metrics. So the order matters, starting with opening the logs to separate volume from reuse.

12. Conclusion

What a record of opening fifteen sites one by one tells you is not a report card for each company. It is that the same syntax written into the same file produces different outcomes depending on who is reading. The file was designed that way from the start, and becoming a standard did not change that property.

So what there is to decide today reduces to three things.

  1. Move the expectation. robots.txt is a declaration, not an enforcement. Do not take comfort from the mere fact of having written it there
  2. Separate where the pain is. Volume means rate limiting; reuse means terms of use. Trying to solve both with one line in a file solves neither
  3. Set the default. Open or closed when an unknown name arrives. That answer comes from whether your content lives on traffic or on the content itself

One more thing. Every time a new file format appears, the claim that this one really blocks appears alongside it. The thing to look at then is not the syntax but how many have decided to read it. If that number is zero, the file is just a file no matter how refined the syntax.
