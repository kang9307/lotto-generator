Ceph 深度解析：RADOS 概念与 CRUSH Rule 完全掌握

2025-06-02 开发/基础设施

Ceph 是一种现代分布式存储系统，凭借卓越的可扩展性与稳定性，受到众多企业与组织的关注。Ceph 的核心是强大的对象存储 RADOS，以及决定数据放置的 CRUSH 算法。本文将深入介绍 Ceph 的"心脏"——RADOS 的概念以及 CRUSH Rule 的细节。

English Summary: This document provides an in-depth analysis of Ceph's core components: RADOS (Reliable Autonomic Distributed Object Store) and the CRUSH (Controlled Replication Under Scalable Hashing) algorithm. It covers their fundamental concepts, key features, and how they work together to deliver a scalable and reliable distributed storage solution.

1. 什么是 RADOS (Reliable Autonomic Distributed Object Store)？

RADOS 是 Ceph 存储集群的基础核心组件。正如其名所示，它是一个可靠（Reliable）、自治（Autonomic）、分布式（Distributed）的对象存储（Object Store）。

主要特性与构成组件：

  • 基于对象的存储：RADOS 以对象（Object）的形式存储所有数据。与文件系统的文件或块设备的块不同，对象是将数据和元数据一同封装的灵活单元。
  • 分布式与可扩展性：数据分散存储在集群内的多个 OSD (Object Storage Daemon) 上。OSD 是管理实际物理存储设备（HDD、SSD 等）的守护进程。增加新的 OSD 时，集群的容量和性能可呈线性扩展。
  • 高可用与数据可靠性：通过复制（Replication）或纠删码（Erasure Coding），数据会冗余存储在多个 OSD 上，从而在发生故障时防止数据丢失并保障服务连续性。
  • 自治化管理：RADOS 会持续监控 OSD 的状态，在发生故障时自动执行数据恢复与再平衡（Rebalancing），从而大幅减轻运维负担。
  • 核心组件：
    • OSD (Object Storage Daemon)：实际存储数据，并执行数据复制、恢复、再平衡等工作。
    • MON (Monitor)：维护集群映射（Cluster Map）的主副本，管理集群整体状态并在 OSD 之间协调一致性。为保证高可用，一般部署 3 个以上的奇数数量。
    • MGR (Manager)：跟踪集群的状态信息（用量、性能、系统负载等），并提供 Ceph Dashboard 等管理接口。
    • MDS (Metadata Server)：使用 CephFS (Ceph File System) 时，负责存储和管理文件系统的元数据。

RADOS 访问接口：

Ceph 在 RADOS 之上提供多种接口，让用户可以通过多种方式访问存储。

  • librados：允许在 C、C++、Java、Python、PHP 等多种编程语言中直接访问 RADOS 集群的库。它是 RBD、RGW、CephFS 的基础。
  • RADOS Gateway (RGW)：提供与 Amazon S3 及 OpenStack Swift 兼容的 RESTful API 的对象存储网关。
  • RBD (RADOS Block Device)：提供快照、精简置备等功能的块存储服务，可用作虚拟机磁盘镜像等。
  • CephFS (Ceph File System)：一个符合 POSIX 标准的分布式文件系统。

2. CRUSH (Controlled Replication Under Scalable Hashing) 算法

CRUSH 是 Ceph 中决定数据位置的核心算法。它不依赖传统的中心化元数据服务器，而是允许客户端直接计算出数据应存储到哪个 OSD。这极大地促进了 Ceph 的可扩展性与性能。

主要概念：

  • CRUSH Map：定义集群物理拓扑（机架、主机、OSD 等）与数据放置策略的映射。CRUSH 算法基于该映射决定数据位置。
  • Bucket：CRUSH Map 中用于对 OSD 进行分组的逻辑单元。可以通过 host、rack、row、datacenter 等多种类型的 bucket，来设置物理故障域（Failure Domain）或性能域（Performance Domain）。
  • CRUSH Rule：定义特定 Pool 中数据如何放置的规则。例如，可以设置"将 3 份数据副本放置在不同机架的 OSD 上"这样的规则。
  • Placement Group (PG)：在 OSD 内对对象进行分组的单元。对象首先被映射到 PG，然后 PG 再根据 CRUSH Rule 映射到 OSD。PG 提升了数据管理的效率，并减少了 OSD 故障时的数据迁移粒度。

CRUSH 算法的工作方式：

  1. 当客户端请求对某对象进行操作时，会基于对象 ID 与 Pool ID 计算出该对象所属的 PG。
  2. 再结合计算出的 PG ID 与 CRUSH Map 中的 CRUSH Rule，确定该 PG 应存放的 OSD 列表。在此过程中，CRUSH 算法会考虑故障域、OSD 权重（容量等）等因素，尽量让数据均匀分布。
  3. 客户端随后直接访问该 OSD 列表中的 Primary OSD，执行数据操作。

CRUSH Rule 的重要性：

CRUSH Rule 会直接影响数据的可靠性、可用性与性能。管理员必须结合集群的物理环境与业务需求，谨慎设计 CRUSH Rule。

  • 故障域 (Failure Domain)：通过 CRUSH Rule 可以强制使数据副本放置在不同的故障域（例如不同服务器、不同机架）。即便某台服务器或整个机架发生故障，也能避免数据丢失并保障业务持续运行。
  • 性能域 (Performance Domain)：当 SSD 和 HDD 混合部署时，可通过 CRUSH Rule 将特定类型的数据（例如对性能要求较高的元数据）仅放置在 SSD OSD 上。
  • 权重 (Weight)：可以根据 OSD 的容量或性能设置权重，从而引导数据实现更均衡的分布。

3. RADOS 与 CRUSH Rule 的关系

RADOS 是以对象形式存储并管理数据的系统，而 CRUSH 是决定这些对象应存放在集群中哪个 OSD 上的算法。

  • 当客户端要存储或读取数据时，CRUSH 算法将决定目标 OSD。
  • RADOS 通过与 CRUSH 决定的 OSD 通信，完成实际的数据 I/O。
  • 当 OSD 发生故障时，MON 会更新集群映射，CRUSH 会计算出新的数据放置方案。
  • RADOS 则依照该方案自动执行数据恢复与再平衡。

通过这种方式，RADOS 与 CRUSH 紧密协同，共同提供 Ceph 存储的核心能力：数据存储、管理、分布与高可用。

结论

Ceph 的 RADOS 与 CRUSH 算法是高效管理分布式存储系统复杂性、提供卓越扩展性与稳定性的核心技术。RADOS 提供了智能的对象存储后端，CRUSH 则对数据放置提供了灵活而强大的控制能力。深入理解这些组件对于高效地设计、构建与运维 Ceph 集群至关重要。
