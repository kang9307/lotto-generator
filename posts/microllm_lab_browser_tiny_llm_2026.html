무엇을 담은 페이지인가 - 설치·계정·API 없는 실험 환경

MicroLLM Lab은 브라우저 탭 하나에서 초소형 언어 모델을 내려받아 실행하고, 같은 문제로 서로 비교하는 실험 페이지다. GitHub README의 첫 문장이 성격을 요약한다. API 키도, 파이썬도, CUDA 설치도 필요 없다는 것이다. 모델 가중치는 브라우저의 IndexedDB에 오리진별로 저장되어 한 번 받으면 다시 내려받지 않고, 프로젝트 페이지는 어떤 입력이나 사용자 데이터도 기기 밖으로 나가지 않는다고 밝힌다.

이 조합이 주목받는 이유는 LLM 실행의 문턱이 「서버 또는 GPU 워크스테이션」에서 「브라우저 탭」으로 내려왔다는 점에 있다. 다만 문턱이 낮아진 만큼 모델도 작아졌다. 여기서 다루는 모델은 파라미터가 1억 남짓, 4비트 양자화 파일이 15~216MB 수준이다. 이 글은 두 가지 질문에 집중한다. 첫째, 브라우저가 LLM 실행 환경이 되려면 어떤 조건이 갖춰져야 하는가. 둘째, 그 환경에서 자료가 밝힌 한계는 무엇인가.

같은 주제 가운데 하드웨어 쪽 끝점은 별도 글에서 다뤘다. 8달러 마이크로컨트롤러에서 소형 모델을 돌리는 시도는 ESP32-S3 온디바이스 LLM 글에 정리되어 있으며, 이 글은 그 축을 반복하지 않고 브라우저라는 실행 계층에만 집중한다.

모델 표 - 크기·파라미터·용도와 자료 간 불일치

모델 목록은 자료마다 개수가 다르다. GeekNews 요약은 7개를 전하고, GitHub README 표에는 SmolLM 135M Instruct가 하나 더 있어 8행이다. 프로젝트 페이지 본문은 모델 카드를 불러오는 구조여서 목록을 직접 나열하지 않는다. 아래 표는 README의 파라미터·크기를 기준으로 하고, GeekNews 요약이 다르게 적은 값은 각주처럼 뒤에 붙였다. 「적합한 용도」 열은 자료가 밝힌 이름과 크기에서 읽을 수 있는 범위만 적은 것이며 성능 평가가 아니다.

표에서 읽히는 구조는 단순하다. 크기 구간이 세 덩어리로 나뉜다. 20~100M대의 MiniMind2 두 개, 1억 2천만~1억 3천만대에서 서로 비교되는 다섯 개, 3억대의 SmolLM2 360M 하나다. 같은 1억 3천만 급 안에서 제작자와 학습 방식이 다른 모델이 여럿 있다는 점이 이 페이지의 실험 가치다. 크기가 거의 같은 모델의 답이 어떻게 다른지를 한 화면에서 볼 수 있다.

README는 제작자도 함께 적는다. PetitGPT는 yangqi0, SmolLM 계열은 Hugging Face Smol Models Research, L20-Edu는 AliceYin, MiniMind2는 jingyaogong, GPT-2는 OpenAI(Radford 외)다. 라이선스는 GPT-2만 MIT이고 나머지는 Apache-2.0이다. 지원 구조는 Llama 계열(GQA·SwiGLU)과 GPT-2·nanoGPT 계열(LayerNorm+GELU) 두 갈래로 적혀 있어, 이 두 아키텍처 계열에 속한 소형 모델이라면 같은 디코더로 얹을 수 있는 설계다.

3단 폴백 - WebGPU에서 WASM, JS로 내려가는 순서

프로젝트 페이지는 실행 경로를 한 줄로 밝힌다. WebGPU를 우선 쓰고, 안 되면 WASM으로, 그것도 안 되면 JS로 내려간다는 것이다. 세 경로는 성격이 다르다.

  • WebGPU. 브라우저가 GPU의 계산 기능을 직접 쓰게 해 주는 API다. 행렬 곱이 대부분인 LLM 추론이 GPU의 병렬 구조와 맞는다. 원문이 제시한 속도 범위가 가장 높은 경로다.
  • WASM(CPU). WebAssembly로 컴파일된 코드를 CPU에서 돌린다. GPU가 없거나 WebGPU를 지원하지 않는 브라우저에서도 동작한다. 원문이 제시한 속도는 WebGPU의 10분의 1 안팎이다.
  • JS 폴백. 위 두 경로가 모두 안 될 때의 마지막 수단이다. 자료에는 이 경로의 속도가 제시되어 있지 않다.

이 순서의 의미는 「돌아가는 기기의 범위」와 「돌아가는 속도」를 맞바꾸는 구조라는 데 있다. 폴백이 있으면 WebGPU가 막힌 환경에서도 일단 실행은 된다. 그러나 속도가 한 자릿수에서 두 자릿수 토큰으로 내려가면 같은 페이지가 다른 도구처럼 느껴질 수 있다. 글을 읽는 속도가 초당 몇 토큰이라는 감각이 필요한 이유가 여기에 있다. 초당 8~20토큰과 100토큰 이상은 응답이 한 줄씩 차오르는 것과 화면이 흘러가는 것만큼 체감이 다르다. 다만 이 체감은 토큰화 방식과 언어에 따라 달라지므로 자료가 밝힌 값이 아니라 감각의 예시일 뿐이다.

README는 이와 별개로 Safari에서 Metal 디코더와 WebGPU 디코더를 함께 지원한다고 적는다. 자료에는 두 디코더를 병기한 이유가 적혀 있지 않다. 여기서는 README가 두 디코더를 병기했다는 사실까지만 전한다.

이 구조를 자기 화면이나 서비스에 응용한다면 폴백 자체보다 「어느 경로로 돌고 있는지를 사용자에게 알릴 것인가」가 먼저 정할 사항이 된다. 경로에 따라 속도가 크게 달라지는 이상, 같은 기능이라도 기대치가 달라야 하기 때문이다. 이 글의 자료는 MicroLLM Lab이 그렇게 하는지 밝히지 않으며, 아래는 3단 구조가 던지는 설계 질문을 정리한 것이다.

  • 경로 표시. 지금 WebGPU, WASM, JS 중 어느 경로로 도는지를 화면에 보여 줄 것인가.
  • 최소 속도 기준. 어느 속도 아래에서는 기능을 끄고 안내문으로 대체할 것인가. 초당 한 자릿수 토큰에서는 대화형 용도가 어렵다.
  • 첫 다운로드. 15~216MB 파일을 받는 동안 무엇을 보여 줄 것인가. IndexedDB에 저장되므로 두 번째 방문부터는 이 비용이 사라진다.
  • 모델 크기 선택. 경로별로 다른 크기의 모델을 배정할 것인가. WASM 경로에서는 작은 모델이 현실적일 수 있다.

브라우저가 실행 환경이 되기 위한 조건

「설치가 필요 없다」는 말이 「아무 조건도 없다」는 뜻은 아니다. 자료에서 읽히는 조건은 다섯 가지다.

  • HTTP 서빙. README는 모듈과 워커가 오리진을 필요로 하므로 로컬 HTTP 서버가 필요하다고 적는다. 파일 탐색기에서 HTML을 더블클릭해 여는 방식(file 주소)으로는 이 조건이 충족되지 않는다. 저장소는 ZIP 배포도 제공하므로, 받은 폴더를 정적 서버로 띄우는 것이 전제다.
  • 브라우저 버전. GeekNews 요약은 Chrome 113 이상, Edge 113 이상, Brave, WebGPU를 켠 Firefox를 전한다. README는 Safari·Chrome·Edge를 든다. 두 자료가 다른 브라우저 목록을 적었으므로 실제 지원 여부는 각자의 환경에서 페이지가 동작하는지로 판단해야 한다.
  • 저장 공간. 모델 파일은 15~216MB이고 IndexedDB에 오리진별로 저장된다. 같은 파일을 다른 오리진에서 열면 다시 내려받는 구조다.
  • 양자화. 모델은 Q4로 배포된다. GeekNews 요약은 16비트 부동소수점 가중치를 4비트로 압축해 메모리 사용량을 75% 줄인다고 전한다. 16비트에서 4비트로 가면 저장 비트가 4분의 1이 되므로 산술상 75% 감소와 맞는다. 다만 이 압축은 품질 손실과 맞바꾼 것이며, 원 모델과 Q4 모델의 정확도 차이는 자료에 없다.
  • 모델 구조 지원. Llama 계열과 GPT-2 계열 두 갈래만 디코더가 있다. 이 밖의 구조를 가진 모델은 그대로 올릴 수 없다.

이 다섯 조건을 정리하면 브라우저는 「설치 없는 환경」이지 「자원이 무한한 환경」이 아니다. 오리진이라는 보안 경계 안에서 워커와 모듈을 쓰고, GPU에는 브라우저가 허락한 API로만 접근한다. 같은 이유로 프로젝트 페이지가 강조하는 프라이버시도 구조적이다. 추론이 사용자 기기의 브라우저 안에서 끝나므로 입력이 서버로 전송될 경로가 없다. 다만 이 페이지가 모델 파일을 어디서 내려받는지, 통계나 인증서 공유 기능이 외부와 통신하는지는 자료에 적혀 있지 않다.

속도 - 원문이 제시한 범위와 측정 조건

속도 수치는 세 출처에 흩어져 있다. 출처와 조건을 분리해 두지 않으면 서로 다른 측정을 한 줄로 오독하기 쉽다. 아래 표는 그 구분이다.

경로 또는 조건원문이 제시한 속도출처와 조건
WebGPU초당 100~300+ 토큰GeekNews 요약. 기기·모델 조건은 요약에 없음
WASM(CPU)초당 8~20 토큰GeekNews 요약. WebGPU와 10~20배 차이로 서술
JS 폴백—수치 제시 없음
PetitGPT research-v187ms, 초당 115 토큰README. Apple M4, Safari, Metal Q4, 그리디 디코딩, 「Say hello」 프롬프트
SmolLM2 135M Instruct227ms, 초당 66 토큰README. 위와 같은 조건
첫 토큰 지연10ms 미만이라는 문구프로젝트 페이지의 자동완성 용도 소개. 조건 미기재

두 가지가 눈에 띈다. 첫째, README의 M4 측정값은 같은 크기 구간의 두 모델에서 초당 115와 66으로 갈린다. 파라미터가 비슷해도 구조와 토큰 임베딩 크기 등에 따라 속도가 다르다는 것이 이 표에서 읽히는 전부다. 둘째, GeekNews 요약이 전하는 「WebGPU 초당 100~300+」는 README의 M4 측정과 모순되지 않는 범위지만, 요약이 어떤 기기·모델에서의 값인지는 밝히지 않는다. 그래서 이 범위를 「원문이 제시한 범위」로 인용하고 자기 환경의 기대치로 옮기지 않는 것이 안전하다.

프로젝트 페이지는 지속 속도를 「256 토큰 연속 생성」에서 잰다고 설명한다. 짧은 응답의 첫 토큰 지연과 긴 생성의 처리량은 다른 값이다. 자동완성처럼 짧은 응답에서는 첫 토큰 지연이, 요약처럼 긴 응답에서는 지속 속도가 체감을 좌우한다. 페이지가 두 지표를 나란히 보여 주는 이유다.

표를 읽을 때 지켜야 할 규칙은 하나다. 같은 행 안의 값만 서로 비교하고, 서로 다른 출처의 값을 이어 붙여 하나의 추세로 읽지 않는다. 기기, 브라우저, 모델, 프롬프트 가운데 하나라도 다르면 다른 측정이기 때문이다. 특히 첫 토큰 지연 값에서 지속 속도를 계산해 내거나 그 반대로 계산하는 것은 자료에 근거가 없다.

벤치마크·인증서·커스텀 JS 평가의 구성

MicroLLM Lab은 실행만 하는 도구가 아니라 측정 도구를 함께 담고 있다. 자료가 밝힌 구성은 다음과 같다.

  • 객관식 벤치마크. 프로젝트 페이지의 Benchmarks 탭은 정규식이나 정확한 토큰 일치로 판정하는 객관 검사를 쓴다. 판정 기준이 기계적이라 같은 입력에 같은 결과가 나오기 쉽다.
  • 테스트 개수. GeekNews 요약은 21개 테스트를 자동 실행한다고 전한다. README는 「원래 테스트」 14개와 「확장 테스트」 20개를 구분하며, SmolLM2 135M Instruct는 확장 20개 중 14개, PetitGPT는 원래 14개 중 10개를 맞혔다고 적는다. 21이라는 값이 README의 어느 수와 대응하는지는 자료만으로 알 수 없다.
  • 스위트 소요 시간. README는 M4 Safari에서 PetitGPT가 약 1.5초, SmolLM2가 약 6초라고 적는다.
  • 256토큰 지속 속도. 프로젝트 페이지는 연속 256토큰 생성으로 지속 속도(Highest Sustained Speed)를 잰다.
  • 성능 인증서. 기기 하드웨어 사양, 최고 속도와 지속 속도가 담긴 인증서를 만들어 내려받거나 X·LinkedIn으로 공유할 수 있다. GeekNews 요약은 PNG로 생성된다고 전한다.
  • 커스텀 JS 벤치마크. 사용자가 자바스크립트로 벤치마크를 써 넣으면, 프로젝트 페이지 설명대로 이 오리진에서 eval()로 실행되어 디코딩된 모델 출력에 대해 검사한다.

디코딩 방식이 그리디 하나뿐이라는 점은 벤치마크 설계와 맞물린다. 그리디는 매 단계에서 확률이 가장 높은 토큰을 고르므로 같은 입력과 같은 모델에서 결과가 재현되기 쉽다. 샘플링을 쓰면 실행마다 결과가 달라져 정답 통과율을 비교하기 어렵다. 이 도구가 비교 실험에 맞춰 설계되었다는 것을 보여 주는 대목이지만, 같은 이유로 창의적 생성이나 다양한 답변 용도에는 맞지 않는다.

커스텀 JS 평가에는 주의할 점이 있다. eval()은 입력 문자열을 코드로 실행하므로 이 도구의 오리진 안에서 사용자가 쓴 코드가 그대로 돈다. 자기 기기에서 자기 코드를 돌리는 한 문제가 없지만, 남이 준 벤치마크 스크립트를 붙여 넣는 사용은 다른 성격이다. 이 글은 자료가 밝힌 동작을 전하는 데 그치며, 페이지가 이 실행을 어떻게 격리하는지는 자료에 없다.

모델(README 표기)평가 조건보고된 정확도보고된 소요
PetitGPT research-v1원래 테스트 14개10/14스위트 약 1.5초
SmolLM2 135M Instruct확장 테스트 20개14/20스위트 약 6초

위 표의 두 행은 같은 조건이 아니라서 우열을 매길 수 없다. 테스트 집합의 크기가 다르고 모델도 다르다. README가 「원래」와 「확장」을 나눠 적었다는 사실 자체가 테스트 집합이 개정되었음을 뜻하며, 이후 값끼리만 비교해야 한다는 점을 보여 준다.

한계 - 컨텍스트, 디코딩, 환각, 그리고 쓸 수 있는 자리

한계는 README가 스스로 적어 두었다. 이 모델들은 환각을 일으키므로 중요한 질문에 쓰면 안 되고, 컨텍스트는 2,048 토큰으로 제한되며, 디코딩은 그리디만 지원한다.

  • 환각. README의 표현은 이 모델들이 환각을 일으킨다는 것이다. GeekNews 요약이 옮긴 Hacker News 반응 가운데 SmolLM2 360M이 인구를 1억 5,300만과 3억 2,500만으로 모순되게 답했다는 사례와 GPT-2 124M이 2+2 질문에 엉뚱한 답을 했다는 사례가 있다. 두 사례는 특정 사용자의 시험 보고이며 일반화된 통계가 아니다.
  • 컨텍스트 2,048 토큰. 긴 문서를 통째로 넣는 작업은 이 도구의 범위 밖이다. 한 번에 다룰 수 있는 입력과 출력의 합이 그 안에 들어야 한다.
  • 그리디 디코딩. 온도나 샘플링 조절이 없어 출력 다양성을 조정할 수 없다. 같은 질문은 같은 답을 낸다.
  • UI 피드백. GeekNews 요약이 옮긴 반응에는 글자 크기와 정보 밀도 같은 화면 개선 요청도 있다.

그렇다면 이런 모델은 어디에 맞을까. 자료가 직접 밝힌 용도는 프로젝트 페이지의 자동완성 같은 즉각적인 짧은 응답 소개가 전부다. 아래는 위 한계에서 논리적으로 따라오는 해석이며, 자료가 권한 용도가 아니다. 정확한 사실을 요구하지 않고, 출력이 짧고, 틀려도 사람이 바로 걸러낼 수 있는 작업이라면 성립한다. 산수와 사실 확인처럼 정답이 하나로 정해지는 작업은 위 사례들이 실패를 보여 준다. 분류나 필터링처럼 좁은 범위의 판단 작업이 후보가 될 수는 있으나, 이 도구의 테스트 결과가 그것을 입증하지는 않는다. 그런 용도에 쓰려면 자기 데이터로 정답 통과율을 직접 재 보아야 한다. 마침 이 페이지의 커스텀 JS 벤치마크가 바로 그 측정을 위한 자리다.

결국 이 페이지가 보여 주는 것은 「소형 모델의 실력」이 아니라 「브라우저가 추론을 실행할 수 있는 조건이 어디까지 갖춰졌는가」다. WebGPU가 있으면 초당 수백 토큰까지, 없으면 한 자릿수에서 두 자릿수 토큰으로 내려가는 계단이 폴백 구조로 열려 있고, 그 위에서 1억 파라미터 안팎의 모델이 설치 없이 돈다. 반면 그 모델이 무엇을 믿고 맡길 만한가는 별개의 문제이며, 자료 스스로도 그렇게 적고 있다. 실행 환경의 성숙과 모델의 신뢰성은 서로 다른 축이다.

확인하지 못한 것

  • 모델 개수와 테스트 개수의 정확한 값. GeekNews 요약(모델 7개·테스트 21개)과 README(표 8행·원래 14개+확장 20개)가 어긋나며, 어느 쪽이 최신 상태인지 자료만으로는 판별할 수 없다.
  • WebGPU 초당 100~300+ 토큰, WASM 초당 8~20 토큰이 어느 기기·모델에서의 값인지. 요약에 조건이 적혀 있지 않다.
  • 구형 GPU에서 속도가 몇 배 느려지는지. 수치가 확인한 자료에 없다.
  • 분류·필터링 같은 엣지 작업에 적합하다는 평가. 자료가 밝힌 것이 아니며 이 글의 해석 범위로만 다루었다.
  • JS 폴백 경로의 실제 속도와 동작 조건. 프로젝트 페이지에 순서만 적혀 있다.
  • Q4 양자화가 원본 모델 대비 정확도를 얼마나 낮추는지, 커스텀 JS 실행의 격리 방식, 인증서 공유 시 외부 통신 여부. 자료에 없다.
  • 프로젝트 페이지 본문의 모델 목록. 페이지가 모델 카드를 불러오는 구조여서 본문 텍스트에 목록이 나타나지 않았다.
  • 이 글은 직접 실행하여 속도를 재현하지 않았다. 모든 수치는 자료가 제시한 값이다.
