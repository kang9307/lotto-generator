Switching Monitor Inputs From the Command Line - DDC/CI and monitor-input-rs Explained

How to move one monitor between multiple PCs without a hardware KVM switch - the mechanics and practical use of DDC/CI

Jul 22, 2026 Dev & Infra

Introduction: Sharing One Monitor Across Multiple PCs Without a KVM

Picture a desk with a work PC and a gaming PC sitting side by side, sharing a single monitor. If you've ever reached over to the monitor's front panel and clicked through an on-screen display menu just to flip from HDMI1 to DisplayPort, you already know the friction this creates. A hardware KVM switch solves it, but adding another device into the video path can introduce its own headaches: resolution or refresh-rate caps, or HDCP handshake issues that weren't there before.

monitor-input-rs, a project surfaced on GeekNews (hada.io), attacks this problem from a completely different angle. Instead of buying another box, it reaches into a control feature that's already sitting inside most modern monitors and drives it straight from the command line. This piece breaks down what the underlying DDC/CI protocol actually does, why this tool was built the way it was, and where its practical limits are. It's grounded in the repository and supporting documentation as checked in July 2026.

1. What DDC/CI Is - A Standard for Controlling Monitors in Software

DDC/CI (Display Data Channel/Command Interface) is a VESA standard that lets a host PC and a monitor exchange data over a side channel riding alongside the video cable. The upshot is simple: settings like brightness, contrast, and input source can be changed by software commands instead of physical buttons.

1.1 A control channel layered on I2C

DDC/CI uses the I2C bus that already runs inside HDMI, DVI, and DisplayPort cables as its physical layer. The computer acts as the master and the monitor as the slave, exchanging short, defined command sequences at a fixed address. This is entirely separate from the pixels being drawn on screen, so sending a DDC/CI command never causes a visible flicker or glitch.

1.2 VCP codes and the MCCS standard

What can actually be requested over that channel is defined by MCCS (Monitor Control Command Set), which assigns a VCP (Virtual Control Panel) feature code to each setting. Brightness is code 0x10; input source selection is code 0x60. When a Linux tool like ddcutil runs something like setvcp 60 0x0f, it's operating directly on this standard. monitor-input-rs is best understood as a wrapper around these low-level codes, exposing human-readable monitor names and input names instead of requiring users to memorize numeric codes.

2. The Actual Problem monitor-input-rs Solves

monitor-input-rs is an open-source project by developer kojiishi with a single purpose: switch a monitor's input source over DDC/CI from the command line. There's no flashy GUI, no tray icon. That minimalism is exactly why it's easy to wire into scripts and hotkeys.

2.1 One command instead of a button hunt

Switching inputs through a monitor's on-screen menu means hunting through button layouts and menu depths that differ from model to model. monitor-input-rs instead offers one consistent syntax: monitor-name=input-value. Bind it to a script or hotkey once, and every future switch is just that keypress. A GeekNews commenter described building a short shell alias like mon to hop between Windows and Mac - exactly the usage pattern this tool is built for.

2.2 Why cross-platform and why Rust

DDC/CI access differs by platform: Windows has its own monitor configuration API, macOS goes through IOKit-family interfaces, and Linux routes through the i2c-dev kernel module. monitor-input-rs absorbs these differences through the ddc-hi crate, so the same CLI syntax behaves identically across all three. Writing it in Rust is a practical choice too - it ships as a single binary with no runtime to install, and startup latency is effectively zero, which matters when it's triggered from a hotkey or automation script. Because it's command-line-first, it drops straight into shell functions, cron jobs, or hotkey managers - a real difference from GUI-only tools that assume a human is clicking through a window.

3. How to Actually Use It - Install and Command Concepts

Based on the official repository, here's the install and usage pattern. Always check the repository docs for the current exact options.

3.1 Installation

With a Rust toolchain already installed, cargo install monitor-input pulls the published crate from crates.io. To build straight from source, use cargo install --git https://github.com/kojiishi/monitor-input-rs. Linux builds require the libudev development package to be present beforehand. On Windows, if you want a background executable that doesn't pop up a console window, adding the -F winapp feature flag installs monitor-inputw.exe, which surfaces errors as Windows notifications instead.

# Install from crates.io
cargo install monitor-input

# Install directly from the repository
cargo install --git https://github.com/kojiishi/monitor-input-rs

# Windows console-less variant
cargo install monitor-input -F winapp

3.2 Basic commands

Usage boils down to three steps: list monitors, filter by name, and specify the input value. Listing multiple values also enables a toggle/cycle behavior on repeated runs.

# List all connected monitors
monitor-input

# Search for monitors whose name contains a string
monitor-input Dell

# Set a specific monitor's input to DisplayPort 1
monitor-input U2723=dp1

# Toggle between hdmi1 and usbc2 on every run
monitor-input P3223=hdmi1,usbc2

# Cycle hdmi1 -> usbc2 -> dp1 in sequence
monitor-input P3223=hdmi1,usbc2,dp1

The key trick is that listing values with commas turns the command into an automatic cycle. Bind monitor-input P3223=hdmi1,usbc2 to a single hotkey and you get a working toggle button between two sources. Not having to look up vendor-specific VCP value tables is the biggest usability gap compared to lower-level tools like ddcutil.

4. Practical Use Cases - Where to Put This to Work

4.1 Work PC and gaming PC

This is the most intuitive use case: a work laptop and a gaming desktop sharing one monitor, switched with a single hotkey. Once the few seconds of physical-button friction disappear, many people notice they actually switch more often - a familiar UX pattern where reduced friction changes behavior itself.

4.2 Homelab and multi-server consoles

It's also useful in homelab setups managing several servers or mini-PCs off one monitor. Instead of a dedicated console KVM, you can wire each machine to a different monitor input and cycle through them with a script, getting similar convenience at a much lower cost. Keyboard and mouse switching still needs a separate solution, which is covered below.

4.3 Meeting rooms and separated dev environments

The same pattern applies to a meeting-room display that needs to switch between a laptop and a presentation PC, or to a setup where a dedicated development machine is kept physically separate from your everyday work machine. Wrapping the switch command into a meeting-start macro is a natural extension.

5. Comparable Tools - Don't Confuse This With "Software KVM"

Searching this space turns up a lot of similarly named tools, so it's worth sorting them out.

5.1 Linux: ddcutil

ddcutil is a far older and more mature DDC/CI tool for Linux. You discover monitors with ddcutil detect and specify VCP codes and hex values directly, e.g. ddcutil setvcp 60 0x0f. It's powerful but low-level, requiring you to look up code tables yourself. monitor-input-rs runs on the same underlying mechanism but layers a name-based, human-friendly syntax on top, and crucially isn't Linux-only - it works identically on all three major platforms.

5.2 Windows: ControlMyMonitor and ddcswitch

On Windows you'll find approaches like wrapping NirSoft's ControlMyMonitor in a batch script, or purpose-built DDC/CI CLIs like ddcswitch. These overlap functionally with monitor-input-rs but are locked to Windows. Anyone splitting time between Mac and Windows ends up needing to learn a different tool per platform.

5.3 macOS: Lunar and auto-trigger companions

On macOS, tools like Lunar provide GUI-based DDC/CI control of brightness and input, and some setups pair it with a companion tool that detects a device connecting and fires the switch command automatically. That combination switches inputs the moment a cable is plugged in, with no hotkey needed - but monitor-input-rs itself has no auto-detection built in; it's a pure command-in, action-out tool. If automatic triggering is what you want, you'll need to wrap it with your own script or hook.

5.4 "Software KVM" solves a genuinely different problem

Tools like Synergy, Input Director, and Barrier show up constantly in the same searches, but they solve a different layer of the problem. They let a mouse cursor move across screen boundaries and hand keyboard/mouse input between multiple computers that each have their own separate monitor. If instead you have a single physical monitor with several PCs' video cables plugged into it, and only one source can be shown at a time, sharing keyboard and mouse changes nothing about what's actually displayed. Changing what's displayed is exactly the job DDC/CI and monitor-input-rs do. The two categories are frequently combined - a software KVM hands off keyboard and mouse, while monitor-input-rs switches the video source at the same moment.

6. Limitations and Things to Watch For

6.1 The monitor has to properly support DDC/CI

DDC/CI is a standard, but implementation quality varies widely by manufacturer and model. Some budget monitors don't support DDC/CI at all, and even those that do sometimes only support it on a specific port. There are documented reports of certain ultrawide or gaming monitors blocking DDC control over DisplayPort while working fine over HDMI. Before adopting this workflow, check which port on your specific monitor actually carries DDC/CI.

6.2 The USB-C dock and MST hub trap

Going through a USB-C dock or an MST (multi-stream transport) hub commonly produces a working video signal while silently dropping the DDC control channel. This usually traces back to a dock's firmware not properly passing DDC through. Connecting the monitor directly to the PC with a cable is the fastest way to isolate the cause. This is a genuinely common failure point for anyone running a laptop through a dock.

6.3 Sleep mode, signal detection, and Linux distro variance

If a PC goes to sleep right after its input is switched away, the monitor can get stuck searching for a signal, lock onto the wrong input, or show a "no signal" screen. Anyone chasing full automation needs to account for sleep-transition timing as well. GeekNews comments also reported a device-recognition issue on Ubuntu 24.04 - depending on distro and kernel version, whether the i2c-dev module is enabled and how permissions are set can mean the tool doesn't work out of the box on the first try.

Conclusion: Who This Is Actually For

monitor-input-rs isn't flashy new technology - it's closer to dusting off DDC/CI, an old standard already dormant inside most monitors, and re-packaging it for command-line-era habits. Its real value is solving this problem with the monitor and cables you already own, no extra hardware purchase required.

It's a great fit for anyone who wants to move one monitor between a work and gaming setup, or between several homelab machines, without touching a physical button, and who already automates their workflow with shell scripts or a hotkey manager. On the other hand, if you're unsure whether your monitor properly supports DDC/CI, or you're running a complicated chain of docks, start by simply running monitor-input with no arguments to check whether your monitor is even detected. If you also want to hand off keyboard and mouse, pairing it with a software KVM tool is the recommended setup.
