The trigger - what the phrase about no longer compiling to Erlang source covers

On 5 October 2026 the official Gleam site published its v1.19.0 announcement under the title Gleam doesn't compile to Erlang source anymore, and GeekNews picked it up on 6 October. The change named in the title fits in one sentence. Gleam used to generate Erlang source code, and it now generates Erlang abstract forms. According to the announcement, Giacomo Cavalieri has entirely rewritten the Erlang code generator over the last few months, and the new generator has a different design and outputs a different format.

Read on its own, the title invites a wider reading than the text supports. What changed is the format produced by the code generator for the Erlang target. Gleam is a language for both the Erlang virtual machine and JavaScript runtimes, and the announcement covers the JavaScript-side changes in separate sections. The Erlang compiler has not been removed from the picture either. The announcement describes the change as a move from compiling to source code that is fed to the Erlang compiler to an intermediate representation that is fed into the Erlang compiler. Producing bytecode remains the job of the Erlang compiler, as it was before.

So the thing to look at is what one compiler hands to another. When the hand-off changes from human-readable text to a tree-shaped intermediate representation, the work left for the receiving side, the reference point for error locations, and the way generated output is handled all change with it. How far Gleam moves the type boundary on top of the BEAM is a separate axis, and it is laid out in Putting Static Types on the BEAM.

What abstract forms are - the definition in the Erlang documentation

The announcement introduces abstract forms as an intermediate representation used by the Erlang compiler. It describes them as a metadata-annotated tree that represents Erlang syntax, normally produced by running the Erlang tokeniser and parser. The Erlang/OTP documentation calls the same thing the abstract format, and the v1.19 changelog also records this change under the name Erlang Abstract Format.

The Erlang documentation page titled The Abstract Format (OTP 29.1.1) states the following.

  • Definition. It is the standard representation of parse trees for Erlang programs as Erlang terms.
  • The shape of a module. A module declaration is a sequence of forms, and each form is either a function declaration or an attribute. The attribute -module(Mod) is represented as {attribute,ANNO,module,Mod}, and a function declaration as {function,ANNO,Name,Arity,[Rep(Fc_1), ...,Rep(Fc_k)]}.
  • ANNO. The ANNO that appears throughout these representations is an annotation, and among other things it denotes the number of the line in the source file where the construction occurred. The details are in the documentation of the erl_anno module.
  • The functions that handle it. compile:forms/1,2 and the functions in the modules epp, erl_eval, erl_lint, erl_parse, erl_pp and io deal with these parse trees. They are also used as the input and output of parse transforms.
  • Relation to debug information. When the compilation option debug_info is given, the abstract code is stored inside the BEAM file for debugging purposes.

The erl_anno documentation lists what an annotation can hold. There is the column where a token begins, the location that combines line and column, the text of the token, and the line that is derived from these. Beyond those there is a filename and a Boolean called generated that marks abstract code as compiler-generated, among others. The documentation states that the Erlang compiler does not emit warnings for code marked as generated. Reading the location metadata in the announcement alongside this ANNO, the change in error locations discussed further down reads as a question of which source file supplies the line that goes into this slot.

The announcement adds one more point. Abstract forms have a binary encoding that uses the Erlang external term format, and with this binary format the generated code can be loaded directly, skipping the front-half of the Erlang compiler. In the Erlang documentation, the external term format is mainly used in the distribution mechanism of Erlang; the built-in function that converts a term into this format is erlang:term_to_binary/1,2, and the one that converts it back is erlang:binary_to_term/1. The documentation states that all Erlang terms have an external representation. Since the abstract format is a parse tree made of Erlang terms, it can be encoded in this format.

The pipeline before and after - who produces what and what is skipped

Laying the before and after side by side, using only what the announcement and the changelog state, gives the table below. The left-hand column is v1.17.0, the baseline of the benchmark. The announcement says that the first stage of the rewrite was already released in v1.18.0, which is why it compares v1.17.0 with v1.19.0.

Stagev1.17.0 (Erlang source output)v1.19.0 (abstract forms output)
What the Gleam compiler producesErlang source codeErlang abstract forms, as a binary encoded in the external term format
Tokenising and parsing on the Erlang sidePerformed, since this is the normal route from source to abstract formsSkipped. The wording in the announcement is front-half of the Erlang compiler
Compilation after abstract formsErlang compilerErlang compiler
BEAM bytecode generationErlang compilerErlang compiler
Reference for runtime location metadataThe generated Erlang source. Line numbers could be inaccurate and only pointed to the nearest functionThe original Gleam source

Three things can be read from the table. First, what was cut is the front part of the Erlang compiler, not the whole of it. The announcement refers to the optimisations implemented in the Erlang compiler over the decades, and that part stays with the Erlang compiler. Second, the skipped stage is the work of turning source text back into a tree. Spelled out, the round trip in which the Gleam compiler wrote the program out as text and the Erlang side read that text again to rebuild a tree is gone. Third, the reference point for location information has moved. The documentation of the Erlang compile module names as the main disadvantage of the Erlang source code route that it is hard or impossible to map each line of Erlang code back to the corresponding line in the original source file.

The announcement names four benefits of the new code generator.

  • The performance of the compiler has improved, significantly reducing build times for Gleam projects running on Erlang.
  • The location metadata available to the runtime is accurate to the original Gleam source, rather than to the Erlang source the compiler used to generate.
  • The code quality of the Gleam compiler has improved. The Erlang code generator was one of the oldest and most stable parts of the codebase, so it was not causing problems, but the explanation given is that it did not conform to the standards and conventions the project has today.
  • There is no longer a need to hear the word transpiler used as a pejorative. This item carries a footnote.

The footnote on the fourth item bears on this topic. The announcement defines a transpiler as a compiler that outputs a human-readable format, such as source code, and writes that there is nothing about compiling to a human-readable format that makes a compiler easier to implement. It continues that if the output is expected to be nicely formatted, this might even be harder than using a binary format.

The four routes the Erlang documentation lists for language implementors

This set of choices is not unique to Gleam. The documentation of the Erlang compile module has a section titled Recommendations for Language Implementors. It starts from the premise that compilers for other languages running on the Erlang runtime system generally produce a file or binary that is fed into the Erlang compiler, and it lists four ways to do that using documented functionality.

Erlang source code (.erl)The most straightforward and portable way. The main disadvantage is that it is hard or impossible to map each line of Erlang code back to the corresponding line in the original source filecompile:file/2 or erlc <FILE>.erl
The abstract formatSupports mapping every Erlang source line back to its corresponding line in the original source filePass the term representation directly to compile:forms/2, or write it to a .abstr file and use compile:file(<File>, [from_abstr]) or erlc <File>.abstr
Core ErlangThere is a specification, but certain details are left to the implementation via the primop expression, and primops can be added, deleted, or changed in any major release without notice. By generating Core Erlang directly it is possible to construct code that the Core-to-BEAM backend has never encountered before, and there are no guarantees that the final BEAM code will be safeThe from_core option. The exact format of the files is not documented and can change between releases
BEAM assembly codeStrongly discouraged. It is very hard to get right and requires continuous maintenance. New instructions are typically introduced in each major release, and sometimes old ones are removed. BEAM code that does not follow the correct conventions can cause the runtime system to crash (segfault)The from_asm option. The format of assembler files is not documented and can change between releases

The section ends with a one-sentence conclusion: the recommendation is to use either the abstract format or Erlang source code. Gleam has in effect moved from one of these two recommended routes to the other. The line-mapping problem that the documentation names as the main disadvantage of the source code route lines up directly with the location metadata that the announcement names as a benefit.

The option descriptions in the same document contain two caveats that an implementor using this route should know. One is the note in the from_abstr entry, which says that the format of such terms can change between releases. The other is the no_lint option. It skips the pass that checks for errors and warnings and is only applicable together with from_abstr; the documentation explains that it is mainly for implementations of other languages on top of Erlang that have already done their own checks to guarantee the correctness of the code. It comes with a warning that when this option is used there are no guarantees that the code output by the compiler is correct and safe to use, and that the responsibility for correctness lies with the code or person generating the abstract format.

Build time - the numbers and the measurement conditions

Before showing any numbers, the announcement attaches a caveat: benchmarks are always contrived and never tell the full story. The measurement uses a benchmark based on the langcompilebench project by José Valim, and the conditions written in the announcement and in the repository README are as follows.

  • The project measured. 100 modules, each containing 100 functions, and each function returns a hello world string.
  • The kind of build. A full build from scratch, without any caching.
  • Aggregation. The README states that the figures are the median of 11 runs.
  • The versions compared. Gleam v1.17.0 and v1.19.0. Because the first stage of the rewrite went into v1.18.0, the comparison skips one version.
  • Tool versions. The version list in the README includes Erlang 29.0.6, Elixir 1.20.4-otp-29 and Rebar 3.27.0, among others.
Entry (as labelled in the README)SecondsNote
Gleam v1.17.0 Erlang0.434The version that output Erlang source
Gleam v1.19.0 Erlang0.342The version that outputs abstract forms
Erlang0.406An Erlang project of the same shape
Elixir0.509An Elixir project of the same shape
Gleam v1.19.0 JavaScript0.188The JavaScript target

The difference between the two Erlang-target values is 0.092 seconds, a reduction of about 21 percent relative to v1.17.0 (calculated). The body of the announcement does not state these numbers in a sentence; it carries them only as a bar chart, and the values in the table come from the README of the benchmark repository that the announcement links to. The README table also has rows for Go, Java, Rust, C#, Elm and TypeScript. The announcement explains that this comparison is meant to help people get a rough feel for how fast Gleam compiles compared with a language they are familiar with, and it repeats that this benchmark alone is insufficient to draw any hard conclusions about these languages.

The numbers should be read together with the limits that follow from the conditions. As the announcement itself notes, this shape of project is easy to replicate across different languages, but only a small subset of the features of each language gets compiled. Code in real projects is far more varied, and different features have different compilation costs in different languages. In addition, compilation in Gleam is incremental, and the announcement says that during typical development it would be much faster because it will not be compiling the entire project. Nothing in these sources supports assuming that the reduction measured on a full build equals the reduction felt in an edit-and-build loop. The changelog gives no number; it only says that when compiling to Erlang, compile times have been reduced for a typical Gleam package.

Error locations - line numbers that point at the original Gleam source

The second benefit is a change that shows up in operation. According to the announcement, the location metadata available to the runtime is now accurate to the original Gleam source. The example it gives is the line numbers in BEAM crash reports and stack traces. Previously they could be inaccurate and only pointed to the nearest function, and now they are accurate (the wording in the announcement is perfectly accurate). The changelog puts the same point this way: the format supports mapping every generated Erlang line back to its corresponding line in the original Gleam source file.

Three items in the Erlang documentation touch on this change.

  • ANNO. It is part of the representation of each construct in the abstract format and holds the line number in the source file.
  • The {source,FileName} option. It overrides the source file name as presented in module_info(compile) and in stack traces.
  • The {error_location,line | column} option. When the value is column, debug information includes column information. According to the documentation the default is column, and the option has been supported since Erlang/OTP 24.0.

As an interpretation: what changes when line numbers go from function-level to line-level accuracy is the first step of incident response. Going straight from a log to the code depends on the premise that the line named by the stack trace is the point of failure. When only the function is right, a person still has to narrow down which expression inside that function failed.

On debuggers the announcement is more reserved. It says this metadata could also enable full support for Gleam in debuggers such as edb, but that the team has not done any work on this itself. The README of the edb repository introduces edb as a step-debugger for Erlang and states that it requires OTP 29 or later. It also says that a project needs three compile options: debug_info, beam_debug_info and beam_debug_stack. The sentence in the announcement is about a possibility; it is not a statement that Gleam code can be debugged with edb as of v1.19.0.

Why BEAM bytecode is not generated directly

Once the target has moved down to an intermediate representation, an obvious follow-up is why not bypass the Erlang compiler altogether and produce BEAM bytecode directly. The announcement raises this question itself. Could a BEAM bytecode generator be made that outperforms the Erlang compiler, and could the type information in Gleam be used to generate more optimised code? The answer given is that while it is possible to achieve these benefits, it is unlikely that the project would be able to. The reasons it lists are these.

  • Bytecode is not fixed. The announcement says that, unlike Erlang source and Erlang abstract forms, BEAM bytecode is not fixed and unchanging. Each new release of the virtual machine can evolve the bytecode, adding new functionality and sometimes removing functionality that has become redundant.
  • The cost of keeping up never ends. The project would have to keep up with that evolution indefinitely, work closely with the Erlang maintainers to be ready for upcoming changes, and have new versions of Gleam ready for new releases of the virtual machine.
  • Existing optimisations would have to be rebuilt. Reproducing all the optimisations implemented in the Erlang compiler over the decades would be a significant effort, even with the help that the more capable static analysis in Gleam might provide.
  • Funding is limited. The announcement states that Gleam is a community project supported by sponsorship, with only a fraction of the finances of languages backed by corporations or academic institutions.

The conclusion of the announcement is that compiling to Erlang abstract forms is the point where cost and benefit meet for Gleam today (the original wording is cost-benefit sweet-spot). It names Elixir as a language that made the same choice: Elixir also compiles to Erlang via abstract forms.

This judgement and the Erlang documentation in the previous section concern different targets, but the reasons they give point in the same direction. What the documentation strongly discourages is the route of handing BEAM assembly code to the Erlang compiler (from_asm), whereas what the announcement considers is bypassing the Erlang compiler altogether and producing bytecode directly. As reasons for discouraging that route, the documentation gives continuous maintenance and the new instructions introduced in each major release. The two documents do differ, however, in how strongly they describe the format as fixed. The announcement places abstract forms on the fixed side together with Erlang source, while the from_abstr entry in the compile documentation says that the format of such terms can change between releases. As an interpretation: a compiler that targets an intermediate representation sits one step closer to the internals of the other compiler than one that targets source text, and to that extent there are more items to follow in the OTP release notes.

What users see and what to check after upgrading

Regrouped from the user side, what changes is build time and error locations, and what does not change is who produces the code that actually runs. BEAM bytecode is produced by the Erlang compiler, as before.

The following are worth checking directly after upgrading. They are check items that follow from what the announcement and the changelog say, and whether each one applies depends on the project.

  • Build time on your own project. The benchmark is a synthetic project of ten thousand hello world functions (100 by 100, calculated). Timing both a full build with the cache cleared and an ordinary incremental build, before and after the upgrade, shows the size of the change on your own code.
  • Lines in stack traces. Produce a crash report from code that is made to fail on purpose, and see whether the line number matches the corresponding line in the Gleam source.
  • Tools that rely on generated output. If any script reads or post-processes generated files in the build directory, see whether the same files still exist in the same shape after the upgrade. This is a release in which the output format of the code generator changed.
  • Mix and rebar3 integration. If something calls compile-package, look at the flag names. According to the changelog, the --src-only flag from rc1 was renamed to --no-dev in rc2.
  • New warnings. The changelog says the compiler now recognises more unreachable clauses where an earlier clause matches an overlapping string, and adds that code that previously compiled cleanly may now emit this warning. A warning was also added for the [..x] pattern that takes a whole list inside a case, and the changelog notes that this syntax may be removed in a future major release.
  • A name clash with OTP 29. When Erlang type definitions are generated, a type called Record is renamed to record_. The changelog says this is to avoid overwriting the built-in Erlang record type introduced in OTP 29.

Other changes in the same release - the JavaScript target still emits source

In the same release in which the Erlang target moved to an intermediate representation, the JavaScript target refined the source code it generates. The example in the announcement shows the difference between the two formats. Flow control in Gleam is done with pattern matching in a case expression, and this is compiled to nested if statements. John Downey improved this process so that it generates flatter code, with nested if statements collapsed into a single condition and fewer intermediate variables. Given the Gleam code below,

pub fn go(x) {
                      case x {
                        Wibble(1, 2) -> 1
                        _ -> 2
                      }
                    }

the following JavaScript used to be generated. A footnote in the announcement says the code has been slightly edited for clarity, but that the parts related to this improvement are unchanged.

export function go(x) {
                      if (isWibble(x)) {
                        let $ = x[0];
                        if ($ === 1) {
                          let $1 = x[1];
                          if ($1 === 2) {
                            return 1;
                          } else {
                            return 2;
                          }
                        } else {
                          return 2;
                        }
                      } else {
                        return 2;
                      }
                    }

v1.19.0 generates this instead.

export function go(x) {
                      if (isWibble(x) && x[0] === 1 && x[1] === 2) {
                        return 1;
                      } else {
                        return 2;
                      }
                    }

The announcement says this makes little to no change to the size of code bundles once they are minified and compressed, but that the resulting code has fewer branches for JavaScript engines to optimise. Because the generated output is text that a person can read, the improvement can be shown this way, as before and after code side by side. The other changes named in the announcement and the changelog are as follows.

  • List literals. On the JavaScript target, a short list literal is no longer built by constructing an array and passing it to a conversion function; it is generated as more direct code that does not convert from an array. No improvement was recorded for longer lists, so the existing approach is kept for those.
  • TypeScript declarations. An overload was added to the function that checks the variant of a custom type, so that the type information previously lost when the type parameter was generalised to unknown is preserved whenever possible.
  • Other build tools. When compiling to BEAM, gleam now generates the .app resource file that the virtual machine requires. export package-information and export package-interface can now print to standard output. The announcement states that the intent is to get Gleam support in Mix for Elixir and rebar3 for Erlang.
  • Language server. Go-to-definition, find-references and renaming are supported for the labels of fields and arguments.
  • Formatting in the browser. A format_source function was added to the WebAssembly build of the compiler.
  • Error messages. Dedicated messages were added for git merge conflict markers, for record update syntax written in the wrong order, for operators that do not exist in Gleam such as +=, and for uses of | in pattern matching, among others.
  • Build cache. According to the changelog, the build tool now stores its build cache in a more compact binary format, making the cache files noticeably smaller.

On Mix support, the wording in the announcement is at the level of hoping to see it soon, and this release does not mean that the support is complete.

What could not be confirmed

  • The machine used for measurement. Neither the announcement nor the README states the hardware or operating system on which the benchmark was run. The figures 0.434 and 0.342 seconds are numbers to read as a relative comparison under the same conditions rather than as values in their own right.
  • The breakdown of the reduction. The sources do not say how much of the 0.092-second reduction comes from skipping tokenising and parsing on the Erlang side and how much from the Gleam code generator itself becoming faster. The changelog for the same release also has an entry reworking the lexer of the Gleam compiler, so there is more than one factor.
  • What went into v1.18.0. The announcement says only that the first stage of the rewrite was released in v1.18.0. It does not say what that stage included.
  • Whether Erlang source output remains anywhere. No statement was found in the announcement or the changelog on whether generated Erlang source is still emitted for inspection, or on how the contents of gleam export erlang-shipment have changed.
  • How the Erlang compiler is invoked. The sources do not say whether Gleam passes abstract forms through compile:forms/2 or through a .abstr file with from_abstr, or whether it uses no_lint. The source code of the Gleam compiler was not among the sources used.
  • The size of the change on real projects. No public measurement was found of how much build time falls on projects outside the synthetic benchmark.
  • Stability of the abstract format between releases. Between fixed and unchanging in the announcement and can change between releases in the Erlang documentation, the two documents alone do not settle which applies to the route Gleam uses.
  • Column information. The announcement does not say whether stack traces match the Gleam source down to the column as well as the line.
