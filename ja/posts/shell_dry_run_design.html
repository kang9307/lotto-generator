まともな --dry-run の作り方 - まねごとではなく検証を

偽の dry-run 五類型を実行出力で再現し、plan のハッシュ三回一致で証明する

2026年7月29日 開発・インフラ

はじめに: dry-run が約束したことを実行はできなかった

整理スクリプトに --dry-run を付けた。走らせると would delete が十二行出て、一覧も想定どおりだった。安心して本番で実行した。ところが途中でエラーになり、消えたファイルと残ったファイルが混在する状態になった。dry-run ははっきり「こうする」と言ったのに、実行はそのとおりにできなかった。

この状況が特に悪いのは、答えが間違っていたこと自体ではない。dry-run を走らせた人がその間に安心してしまったことにある。何も検証していなければ慎重に実行しただろうに、確認したと信じたからそのまま押し切ったのだ。検証していない状態より、誤って検証した状態のほうが危険だ。これが偽の dry-run の本質的な害である。

その下には広く行き渡った誤解がある。「dry-run とは実行するコマンドを出力するだけのもの」という考えだ。違う。出力は成果物にすぎない。dry-run が値打ちを持つには、実際に実行したときと同じ判断経路をたどらなければならない。同じ条件を評価し、同じ検査を通り、同じ順序で対象を選んだうえで、最後の一歩である「書き込み」だけをしない。この最後の一歩をどこに置くかで、dry-run は検証にもまねごとにもなる。

この記事は定義から始めない。偽の dry-run 五類型を一時ディレクトリで実際に再現した出力から始め、それをどう直すかまで進む。順序はこうだ。まず五類型を一つずつ壊し、次に plan と apply を分ける形を作って三回実行のハッシュが一致することを証明する。続いて終了コード規約と CI 配線を整理し、最後に git clean -n や rsync -n といった既存ツールの dry-run をどこまで信用できるか線を引く。

範囲を先に狭めておく。「二度走らせても同じ結果か」はこの記事の主題ではない。そちらは二度走らせても安全なスクリプトで別に扱った。この記事の問いは一つだけだ。「走らせる前に結果を知ることができるか。」二つの性質は互いを助けるが同じものではない。完全に冪等なスクリプトでも、嘘をつく dry-run をいくらでも持てる。

1. 実行環境と検証方法

この記事の主張はすべて実際に走らせた出力である。再現環境は次のとおり。

  • OS: Windows 10 Pro 10.0.19045 上の MSYS2 系 Unix 環境(Git Bash)
  • シェル: GNU bash 5.2.37(1)-release (x86_64-pc-msys)
  • ユーティリティ: GNU coreutils 8.32, GNU tar 1.35, GNU Awk 5.0.0, git 2.48.1
  • 作業場所: 一時ディレクトリ一つ。実験ごとに新しい下位フォルダを作って隔離

Linux ディストリビューションではなく MSYS2 を使ったのは手元にあったからで、ここで見える挙動はほぼシェル文法と POSIX ユーティリティの仕様から来るものなので環境を移しても同じだ。ただし次の二つは環境依存なので扱わなかった。

  • ファイル権限と所有者に起因する失敗 — この環境は POSIX の権限ビットを完全には模倣しないため再現が信頼できない
  • rsync の実際の挙動 — この環境に導入されておらず実行できなかった。11 節では公式文書に書かれた境界だけを引用し、代わりに同じ性質の分岐を git で再現した
⚠ 警告 — この記事の例は一時ディレクトリ専用です。
本文には rm、sed -i、git clean -f のような取り消せないコマンドが出てきます。すべて新しく作った一時ディレクトリの中だけで実行しており、それ以外を対象にするようには書かれていません。ご自身で確かめる際は空の一時ディレクトリを新規に作り、その中だけで走らせてください。実際のサーバー経路やホームディレクトリでは実行しないでください。特に git clean 系は追跡されていないファイルを復元不能な形で削除します。

2. 類型 1 出力するだけで判断しない

もっともよくある形だ。実行地点ごとに if で分け、dry なら文を出し、そうでなければ本当に呼ぶ。

clean() {
  for f in "$@"; do
    if [ -n "${DRY:-}" ]; then
      echo "would delete $f"
    else
      rm "$f"
    fi
  done
}

対象ディレクトリに a.log と c.log は作り、ghost.log はあえて作らないまま三つとも引数に渡した。

### 対象ディレクトリの状態
a.log
c.log

### DRY=1 (偽の dry-run)
would delete a.log
would delete ghost.log
would delete c.log
exit=0

### 実際の実行
rm: cannot remove 'ghost.log': No such file or directory
exit=0

### 実行後に残ったもの
(なし)

dry-run は存在すらしないファイルを消すと言った。理由は単純で、echo 側の経路はファイルがあるかを一度も尋ねないのに対し、rm は対象を実際に参照する。二つの経路が答えている問いがそもそも違う。

  • dry-run が答えた問い: 「ループにどんな引数が入ってきたか」
  • 実行が答えた問い: 「その引数が指す対象は今存在し、削除できるか」

まとめると、この dry-run が見せたのは実行結果の予測ではなく引数一覧の復唱である。一覧が正しいことと実行が成功することはまったく別の命題なのに、出力形式が would ... なので後者として読まれてしまう。

出力にもう一つ隠れている。実際の実行も終了コード 0 を返した。ghost.log でエラーが出たのにである。ループ最後の rm c.log が成功し、関数の終了状態は最後に実行されたコマンドのものだからだ。この問題は 6 節で改めて扱う。

直す方向は「検査を dry 側にも複写する」ことではない。判断を一度だけ計算し、両モードがその結果を共有するようにすることだ。複写すれば条件分岐が二組になり、次の人が片方だけ直す。

3. 類型 2 条件が実行経路にしかない

類型 1 を経験した人はたいてい検査を足す。ところが検査が実行分岐の内側に入ると状況はむしろ悪くなる。dry-run がより本物らしく見えながら、依然として外れるからだ。

for f in src/*.dat; do
  base=${f#src/}
  if [ -n "${DRY:-}" ]; then
    echo "would archive $base"
    continue                 # ← ここで残りの検査を全部飛ばす
  fi
  # ↓ 以下二つの検査は実行経路にしかない
  if ! mkdir "$LOCK" 2>/dev/null; then
    echo "ERROR: another run holds $LOCK" >&2; exit 3
  fi
  size=$(wc -c < "$f")
  if [ $((used + size)) -gt "$QUOTA" ]; then
    echo "ERROR: quota exceeded at $base (used=$used +$size > $QUOTA)" >&2
    rmdir "$LOCK"; exit 4
  fi
  cp "$f" "dst/$base"
  ...
done

200 バイトのファイル五つを、総量上限 500 バイトの対象に入れてみた。

### DRY=1 — 五件すべて可能と報告
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0

### 実際の実行 — 同じ入力、同じ順序
archived f1.dat (used=200)
archived f2.dat (used=400)
ERROR: quota exceeded at f3.dat (used=400 +200 > 500)
exit=4

### dst の実際の結果
dst/f1.dat
dst/f2.dat

dry-run は五件を約束し、実際は二件で止まった。しかも部分適用の状態が残った。ロックも同じだ。別の実行がロックを握っている状態でもう一度走らせた。

### ロックがすでに握られているとき (別の実行中)
-- DRY=1 --
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0
-- 実際 --
ERROR: another run holds .archive.lock
exit=3

dry-run は今このスクリプトがそもそも始められないという事実すら伝えられなかった。ロック検査が実行経路の中にあるからだ。実務でこうした条件は思ったより多い。

  • ディスク空き容量・inode・クォータ — 書き込む直前に確認する作りにしがちだ
  • 同時実行ロック — 「実際に何かするときだけ握ればよい」という判断で実行分岐に入る
  • 対象サービスのヘルスチェック — dry-run にはわざわざ繋がない
  • 認証・トークンの有効性 — dry-run がリモートに接続しなければ期限切れを掴めない
  • 累積状態 — 上の例のように、前の項目を処理して初めて次の項目の判定が定まる場合

教訓は明快だ。実行可能性を左右する検査は、実行分岐ではなくその手前にあるべきだ。ロックとクォータの検査をループの外の事前点検に引き上げれば、両モードが同じ関門を通る。8 節の plan 構造はこれを強制する形である。

4. 類型 3 dry-run が副作用を残す

「何も変えないモード」なのにファイルを作ったり消したりするなら、名前が嘘をついていることになる。ところがこれは不注意ではなくシェルの評価順序から自然に生まれる事故だ。次のスクリプトを dry-run だけで走らせた。

WORK=$(mktemp -d "./tmp.XXXXXX")     # ① モードと無関係に作られる
mkdir -p logs                         # ② 同じ
exec 3>> logs/run.log                 # ③ ファイルがなければここで生まれる
echo "start $$" >&3

collect() {                           # ④ リダイレクトは分岐の外で評価される
  if [ -z "${DRY:-}" ]; then
    printf 'row-%s\n' 1 2 3
  else
    echo "would write 3 rows" >&2
  fi
} > report.csv

collect
### 実行前の状態
./report.csv
./report.sh
--- report.csv の内容 ---
old-report-do-not-lose-me

### DRY=1 だけで実行
would write 3 rows
exit=0

### 実行後の状態 (dry-run だったのに)
./logs
./logs/run.log
./report.csv
./report.sh
./tmp.XlPBYU
--- report.csv の内容 ---
(0 バイト — 内容が消えた)
--- logs/run.log ---
start 1945
done

dry-run 一回で一時ディレクトリができ、ログディレクトリとログファイルができ、何より既存データの入っていた report.csv が 0 バイトになった。④ が要点だ。関数に付いた > report.csv は関数が実行される瞬間にシェルが先に開くものなので、中でどの分岐を通るかに関係なくファイルが切り詰められる。「出すものがなければ触らないだろう」という直感がちょうど外れる地点だ。

同じ罠はラッパー関数でも出る。実行を包む run 関数を作り、呼び出し側にリダイレクトを付けるとこうなる。

run(){ if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }
run printf 'migrated=%s\n' 3 > state.txt
--- 実行前の state.txt ---
migrated=99
--- DRY=1 実行後の state.txt ---
+ would run: printf migrated=%s\n 3

案内文が状態ファイルの中に入った。次の実行がこのファイルを読んだ瞬間に何が起きるかは想像にお任せする。dry-run が残してはならないものを一覧にするとこうなる。

  • 対象ファイルの切り詰め・生成・削除 — リダイレクトの位置を分岐の中へ移す
  • 一時ディレクトリ — 必要なら apply 段階でだけ作り trap で片付ける
  • ログファイル — dry-run の出力は標準出力・標準エラーへ送り、ファイルに書かない
  • ロックファイル — 読み取り専用の計画には不要だ。「ロックを握れるか」は検査するだけにする
  • リモート状態の変更 — トークン更新・セッション生成・キュー消費のように、参照に見えて状態を変える呼び出し
  • キャッシュ・索引 — 次の実行の判断を変えるので副作用である
確かめ方。dry-run の直前と直後に作業ツリーのファイル一覧と各ファイルのサイズ・ハッシュを出して比べるだけでよい。一行でも違えば、その dry-run は名前負けしている。この比較はそのまま CI に入れられる。

5. 類型 4 後段が前段の結果に依存する

前の三類型はコードを直せば消える。今回は違う。段が鎖で繋がっていると、dry-run は原理的に後段を予測できない。三段の移行処理を作ってみた。1 段目は書庫を展開し、2 段目は展開された設定ファイルを置換し、3 段目は 2 段目の件数に応じて状態を記録する。

run() { if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }

echo "[1/3] リリース展開"
run mkdir -p release
run tar -xf release.tar -C release

echo "[2/3] 設定置換"
n=0
for c in release/*.conf; do
  [ -e "$c" ] || continue
  n=$((n+1))
  run sed -i 's/^mode=old$/mode=new/' "$c"
done
echo "    対象 ${n}件"

echo "[3/3] 後処理"
if [ "$n" -gt 0 ]; then ... else echo "    変更対象がないので飛ばす"; fi
### DRY=1 (何をするか尋ねた結果)
[1/3] リリース展開
+ would run: mkdir -p release
+ would run: tar -xf release.tar -C release
[2/3] 設定置換
    対象 0件
[3/3] 後処理
    変更対象がないので飛ばす
exit=0

### 実際の実行
[1/3] リリース展開
[2/3] 設定置換
    対象 3件
[3/3] 後処理
    state 記録
exit=0

### 実際に変わったファイル
release/app.conf:mode=new
release/db.conf:mode=new
release/web.conf:mode=new
--- migrate.state ---
migrated=3

dry-run は「2 段目の対象 0 件、3 段目は飛ばす」と答え、実際の実行は3 件を変更し状態ファイルまで書いた。ラッパー関数は完璧に動いた。問題はラッパーではなく構造だ。1 段目を実行しなかったので 2 段目が見る入力が存在せず、2 段目の結果が 0 だったので 3 段目の分岐が丸ごと反転した。

ここで最も悪いのは沈黙だ。dry-run は「わからない」と言わず、「やることがない」と断言した。利用者が受ける印象は正反対である。この類型を扱う方法は三つしかなく、いずれも代償がある。

方法内容代償
範囲の縮小dry-run が予測する範囲を最初の段までと明示し、それ以降は (予測不可) と表示する情報量は減るが嘘はなくなる
状態のモデル化計画段階で書庫の一覧を先に読み「展開後に存在するファイル」を計算するモデルと実際がずれうるのでモデル自体の検証が要る
隔離実行使い捨ての作業空間で実際に 1 段目を行い、その上で 2・3 段目を計画する最も正確だが費用が大きく副作用の境界を引き直す必要がある

実務では大半が一つ目を選ぶのが正しい。わからないことをわからないと言う dry-run のほうが、知ったかぶりをする dry-run よりはるかに役に立つ。展開の例なら tar -tf で一覧だけ読み、二つ目を安く真似ることもできる。

6. 類型 5 いつも 0 を返す

ここまでの実行すべてで終了コードも一緒に出してきた。改めて見ると妙な点がある。2 節の実際の実行はエラーを出しながら exit=0 であり、dry-run は例外なく全部 exit=0 だった。

dry-run が常に 0 を返すなら、人が目で読んだときだけ情報が伝わる。人が読むことを前提にする道具は自動化に繋げない。CI で「設定のずれがあればビルドを止める」をやるには、ずれの有無が終了コードで出てこなければならない。

ここに間違えやすい点がある。0 と 1 だけを使うと「変更あり」と「計画の失敗」が同じ値になる。この二つは CI で正反対に扱うべき事象だ。前者は人が承認すれば済む話で、後者はパイプラインが壊れている。だから三つの値が要る。具体的な規約と配線は 10 節で扱う。

7. 五類型の一覧 どこを見れば判るか

ここまで再現したものを一つの表に畳んだ。他人のスクリプトを五分で判定するときに使う表である。

類型症状コード上の兆候再現された結果
1. 判断のない出力存在しない対象にも実行すると言う実行地点ごとに if DRY が繰り返されるないファイルに would delete、実行はエラー
2. 実行経路専用の条件ロックや容量の問題を事前に知らせないdry 分岐直後の continue・returndry は 5 件成功と予測、実際は 2 件で exit=4
3. 副作用の残存dry-run なのにファイルが変わる分岐外のリダイレクト、mktemp、exec N>既存ファイルが 0 バイトに切り詰め
4. 連鎖依存後段を 0 件と誤報する前段の成果物を for・find で読み直すdry は 0 件で飛ばし、実際は 3 件変更し状態記録
5. 無意味な終了コードCI で使えない常に exit 0、値の区別がないエラーを出しても exit=0

五類型には共通点が一つある。どれもエラーを出さない。1 から 5 のどこでも、スクリプトが「この dry-run は正確ではありません」と言ってくれることはない。だからコードレビューで捕まらず、事故のあとになって発見される。

8. 正しい形 plan と apply を分ける

五類型を一度に消す構造がある。「何をするか」を先に計算して一覧にし、実行モードはその一覧を消費するだけにすることだ。インフラ系の道具が plan と apply と呼ぶあの構造である。

要点は二行だ。

  • plan は状態を読むだけ。書き込み・生成・削除・ロック取得が一切ない。出力は整列され、時刻や乱数が混ざらない
  • apply は判断しない。計画の行を読んでその動作だけを行う。条件分岐がないので二つのモードが食い違う余地が消える
# ---------- plan: 読むだけ。何も作らない ----------
make_plan() {
  [ -d "$REQ_DIR" ] || printf 'MKDIR\t%s\tarchive ディレクトリなし\n' "$REQ_DIR"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp)  printf 'DELETE\t%s\t一時ファイル\n' "$f" ;;
      *.log)  if [ -s "$f" ]; then printf 'ARCHIVE\t%s\t内容あり\n' "$f"
              else                 printf 'DELETE\t%s\t0バイト\n' "$f"; fi ;;
      *.conf) if grep -qxF 'mode=old' "$f"; then
                printf 'PATCH\t%s\tmode=old\n' "$f"; fi ;;
    esac
  done
}

# ---------- apply: 計画だけを消費する。自ら判断しない ----------
do_apply() {
  local plan="$1" action path reason
  while IFS=$'\t' read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)   mkdir -p -- "$path"  && echo "ok MKDIR   $path" ;;
      DELETE)  rm -f -- "$path"     && echo "ok DELETE  $path" ;;
      ARCHIVE) mkdir -p -- "$REQ_DIR"; mv -- "$path" "$REQ_DIR/" && echo "ok ARCHIVE $path" ;;
      PATCH)   sed -i 's/^mode=old$/mode=new/' -- "$path" && echo "ok PATCH   $path" ;;
      *)       echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)  make_plan | LC_ALL=C sort
         n=$(make_plan | grep -c . || true)
         [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply) do_apply "${2:?計画ファイルが必要です}" ;;
esac

### plan は副作用を残したか
access.log app.conf build.tmp cache.tmp db.conf empty.log

三回とも 072c4bfb98ee... で一致し、実行後のディレクトリにはファイルが一つも増えていない。4 節で見た副作用がここでは構造的に不可能だ。plan に書き込み命令がそもそもないからである。

では計画を消費させてみよう。

### apply — 計画だけを消費
ok ARCHIVE data/access.log
ok DELETE  data/build.tmp
ok DELETE  data/cache.tmp
ok DELETE  data/empty.log
ok MKDIR   data/archive
ok PATCH   data/app.conf
exit=0

### apply 後に再び plan
exit=0 (0=変更なし)
--- data の最終状態 ---
data/app.conf data/archive data/archive/access.log data/db.conf

apply 後にもう一度計画を立てると空の計画と終了コード 0 が出た。これがこの構造の最後の利点だ。「計画が空である」ことそのものが目標状態に到達した証拠になる。別途の検証スクリプトが要らない。

plan を決定的に保つには。出力に date・$RANDOM・プロセス ID・走査順序を入れないでください。for f in dir/* の順序はロケールで変わりうるので LC_ALL=C sort で固定します。理由の列を入れれば人が読めるようになり、ハッシュ比較もそのまま保てます。

9. 計画が古くなったとき ハッシュで施錠する

plan と apply を分けると新しい隙間ができる。計画を立てた時点と適用する時点の間に状態が変わりうる。承認の手順が挟まればこの間隔は数時間になることもある。その間に誰かがファイルを足せば、承認された計画と実際に起きることが食い違う。

手当ては前節ですでに作ってある。計画のハッシュを一緒に保存し、apply が実行直前に現在の状態から計画を再計算してハッシュを照合すればよい。違えば拒む。

apply)
  want=$(sed -n '1p' "$p.sha" 2>/dev/null || echo '')
  have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
  if [ -n "$want" ] && [ "$want" != "$have" ]; then
    echo "ERROR: 計画以降に状態が変わりました (plan=$want / now=$have)" >&2
    exit 1
  fi
  do_apply "$p" ;;
### 1) 計画の作成
plan exit=2
988ca65d91ce2783486a7216bdfb8dca47db67b8e1af3c0a664080c127aeab83
DELETE  data/cache.tmp  一時ファイル
MKDIR   data/archive    archive ディレクトリなし
PATCH   data/app.conf   mode=old

### 2) 計画と実行の間に別の人がファイルを追加
app.conf cache.tmp late.tmp

### 3) 古い計画で apply
ERROR: 計画以降に状態が変わりました (plan=988ca65d... / now=84f56a62...)
exit=1

### 4) 計画を立て直せば通る
plan exit=2
ok DELETE  data/cache.tmp
ok DELETE  data/late.tmp
ok MKDIR   data/archive
ok PATCH   data/app.conf
apply exit=0

3 の段階でapply が実行を拒んだ。承認された計画に late.tmp がなかったからだ。4 で計画を立て直すと late.tmp が含まれて通った。この一枚で得られるものは大きい。

  • 承認の意味が生きる — 人が承認した一覧と実際に実行される一覧が同じであることを機械が保証する
  • 競合を早く掴む — 二つのパイプラインが同時に走れば後のほうが拒まれる
  • 再現可能な事後分析 — 計画ファイルとハッシュが残るので「何をなぜしたか」が記録される

注意点もある。ハッシュ照合は計画をもう一度計算するので対象が大きいと費用がかかる。そして無関係な変化まで拒む。上の例では late.tmp が実際に計画へ影響したが、計画と無関係なファイルが一つ増えても計画の内容が同じならハッシュは同じで通る。ハッシュは計画を施錠するのであってディレクトリを施錠するのではない。この区別がこの方式の実用性を作る。

10. 終了コード規約と CI 配線

6 節で先送りした問題に戻る。広く使われる規約は三つの値だ。

コード意味CI の動作人がすること
0変更なし — 目標状態と一致通過なし
2適用待ちの変更あり失敗扱い、または承認待ち計画を読み承認・修正
1計画を作れなかった(誤り)即失敗 + 通知パイプラインの修理

2 を「変更あり」に割り当てるのは慣例だ。診断系の道具が長らく正常・差分あり・実行失敗を 0・1・2 に分けてきた流れと同じ発想で、ここでは誤りによくある 1 を残すために 2 を使った。何を使うにせよ三つの状態を区別するという点が大事である。

配線で実際に引っかかる三つ

規約を決めてもシェルの配線で崩れる。三つ再現した。

### A) set -e の下でそのまま呼ぶと
exit=2
   (「ここまで来ました」が出力されない — 後続処理が丸ごと実行されない)

### B) if で包むと 2 と 1 を区別できない
変更あり(または誤り)     ← 正常な「変更あり」(2)
変更あり(または誤り)     ← 誤ったサブコマンドで出た誤り(1)
exit=0

### D) パイプに繋ぐと終了コードが tee のものになる
$?=0  PIPESTATUS=2 0

A は最もよく見る事故だ。set -e は 0 でない値をすべて失敗と見るので、「変更あり」を意味する 2 がスクリプトを殺す。B はもっと静かだ。if は 0 かどうかしか見ないので2 と 1 が同じ枝に落ちる。上の出力の二行はそれぞれ正常なずれと本物の誤りなのにメッセージが同じである。D は | tee で計画をファイルにも残すときに引っかかる。パイプラインの終了状態は最後のコマンドのものなので tee の 0 が残る。

三つの罠をすべて避ける形はこうだ。

#!/usr/bin/env bash
set -uo pipefail
rc=0
./tidy.sh plan > plan.txt || rc=$?          # ← 死なせずにコードを受け取る
case "$rc" in
  0) echo "OK: 目標状態と一致 (変更 0 件)"; exit 0 ;;
  2) echo "DRIFT: 適用待ち $(grep -c . plan.txt) 件"; sed 's/^/    /' plan.txt; exit 1 ;;
  *) echo "FAIL: 計画の作成に失敗 (rc=$rc)" >&2; exit 2 ;;
esac
### C) 規約どおり三分岐にすると
DRIFT: 適用待ち 3 件
    DELETE  data/cache.tmp  一時ファイル
    MKDIR   data/archive    archive ディレクトリなし
    PATCH   data/app.conf   mode=old
CI 終了=1

### E) 適用後に同じ CI をもう一度回すと
apply exit=0
OK: 目標状態と一致 (変更 0 件)
CI 終了=0

ずれがあれば計画をログにそのまま展開してビルドを止め、適用後は同じジョブが通った。CI に組み込むとき実務で押さえることを整理する。

  • フラグを変えないこと — 計画を作った命令行と適用する命令行は、対象・絞り込み・除外規則が完全に同じでなければならない
  • 計画を成果物として保存 — ビルド成果物に残せば承認・監査・事後分析がこのファイル一つで済む
  • プルリクエストでは plan だけ、マージ後に apply — 承認段階を終了コード 2 に紐づける
  • 定期実行でずれを監視 — 一日一回 plan だけ回し 2 が出たら通知する。誰も配備していないのに 2 が出るなら手で変えた人がいるということだ
  • 定期ジョブでは 2 を失敗に上げないこと — 通知は送りつつ、常時赤い表示にすると誰も見なくなる
  • pipefail と PIPESTATUS — パイプに繋ぐときどちらのコードを見るか明示的に決める

11. 既存ツールの dry-run はどこまで信用できるか

自作の話をしたので、既にある道具はどうかを見なければならない。結論から言えば広く使われる道具の dry-run はおおむね信頼でき、何より自分で境界を文書に書いている。問題は道具ではなく人が二つの実行の間にフラグを変える瞬間に生じる。

再現 同じ道具、違うフラグ

一時リポジトリを作り、追跡されていないファイルとディレクトリ、無視規則に掛かったディレクトリ、そして入れ子になった別のリポジトリを入れて確認した。

### git clean -n (既定)
Would remove .gitignore

### git clean -nd (ディレクトリを含む)
Would remove .gitignore
Would remove work/

### git clean -ndx (無視ファイルまで)
Would remove .gitignore
Would remove ignored/
Would remove work/

### 実際の実行: git clean -fd
Removing .gitignore
Removing work/

### 残ったもの
./ignored  ./ignored/c.txt  ./nested  ./nested/.git  ./nested/n.txt

三つの dry-run の答えがすべて違う。そしてそれぞれは同じフラグで実行したときの結果と正確に一致する。公式文書がそのまま説明している。-n は「実際には何も削除せず、何が行われるかだけを示す」であり、-d は「通常、削除しすぎるのを避けるため追跡されていないディレクトリへは再帰しない。-d を指定するとそうしたディレクトリにも再帰する」である。

つまり事故はこう起きる。git clean -n で確認して git clean -fd で実行すること。上の出力で -n は .gitignore の一行だけ見せたのに、-fd はファイル二つの入った work/ の木を丸ごと消した。dry-run が嘘をついたのではなく別の問いに答えたのだ。もう一つ、-nd が見せた Would remove work/ は一行である。その中にファイルが何個あるかは教えてくれない。消える個数を知りたいなら dry-run の出力を数えるだけでは足りない。

入れ子のリポジトリも興味深い。-ndx は nested/ を一覧にまったく入れず、-ndxff を与えるとそこで現れた。文書には「Git は .git 下位ディレクトリを持つ追跡されていない入れ子のリポジトリを、二つ目の -f が与えられない限り変更することを拒む」と書かれている。dry-run が実際の挙動をそのまま映していたのであって、抜け落ちではない。

道具が自ら明かした境界

この環境には rsync がなく実行できなかった。代わりに公式文書が引いた境界を引用する。この段落は実行検証ではなく文書の引用であることを明記しておく。

rsync の文書は --dry-run を「実行とおおむね同じ出力」を出す試走だと説明する。そのうえで dry run は実データを送らないので --progress は効かず、bytes sent・bytes received・literal data・matched data の統計は実際より小さく出て、speedup の値は転送が不要だった実行と同じになると述べる。一方で --itemize-changes の出力はdry run と続く実行で厳密に同じであるべきで、そうでなければそれはバグだと明言している。

この記述は、よくできた dry-run がどうあるべきかをそのまま示している。「何を変えるか」は厳密に同じで、「どれだけ時間がかかり何バイト流れるか」は違うと項目ごとに線を引いたのだ。自作するときにも同じ姿勢が要る。予測する軸と予測できない軸をヘルプに書いておくことがそのまま信頼になる。

既存の道具を使うときの実務規則は短い。

  • 同じ命令行を使う — 確認は -n だけを足した形で。実行時に別のフラグを足さない
  • ファイル一覧を成果物として残す — dry-run の出力をファイルに保存し、実行後の結果と突き合わせる
  • 個数ではなく項目を見る — ディレクトリ一行がファイル数百個ということがある
  • 文書の「例外」節を読む — よくできた道具は自分が予測できないことを書いている
  • リモートが絡めばもう一段疑う — 権限・経路・時刻の解釈が両側で違いうる

12. dry-run が最後まで予測できないもの

どれだけうまく設計しても残る領域がある。この一覧をヘルプに書いておくことが「正直な dry-run」の最後の条件だ。

予測できないものなぜ緩和
時間の経過計画時点と適用時点が違う。保存期間・期限・cron の境界がその間に越える判定基準の時刻を計画に埋め込み apply へ渡す
同時変更他のプロセスや人が同じ対象を触る9 節の計画ハッシュ照合と、適用中のロック
資源の枯渇ディスク・inode・メモリは使う瞬間に足りなくなる計画段階で総量を計算し余裕と比べる(概算と明示)
権限と方針実行ユーザー・セキュリティモジュール・マウント設定が書き込み時に介入する代表経路一つに試し書きをするか、予測不可と表示する
リモートの状態API 応答・サーバー側検証・流量制限は呼んでみないと判らない提供されていればサーバーの検証専用モードを使う
連鎖する成果物5 節 — 前段の結果が後段の入力である範囲を最初の段に固定するか、一覧だけ先に読む
部分失敗のあと途中で止まれば計画の残りは別の状態の上で実行される失敗したら即中断し計画を立て直す

表の最後の行が特に大事だ。計画は「計画を立てたその状態」の上でのみ有効である。半分ほど適用して失敗したなら、残り半分をそのまま押し通してはいけない。計画を捨てて立て直すのが正しく、8 節の構造ならそれは命令一つだ。

結論: dry-run はモードではなく関数だ

この記事で再現した五類型には共通点があった。どれも静かに間違える。ないファイルを消すと言い、5 件だと言っておいて 2 件で止まり、何も変えないと言いながら既存ファイルを空にし、やることがないと断言してから 3 件を変え、そのうえで終了コードは常に 0 だ。どれ一つとして「私の予測は不正確です」と言ってはくれない。

だから判定基準は一つに絞られる。「dry-run は実行と同じ判断を経たか。」同じ条件を評価し同じ順序で対象を選んだなら、その出力は予測だ。引数一覧を復唱しただけならまねごとである。そしてこの問いに確実に「はい」と答える方法は、これまでのところ一つしかない。判断を一か所だけに置くこと — つまり plan が一人で判断し apply は消費だけするようにすることだ。

この構造が良い理由は三つ。第一に二つのモードが食い違うコードが存在しない。類型 1・2 は構造的に発生しえない。第二に検証がただで付いてくる。三回実行のハッシュ比較で決定性を、適用後の空の計画で収束を確かめられる。第三に承認と監査がファイル一つで済む。計画ファイルとそのハッシュがそのまま記録だ。

最後に今日できること一つ。手元のスクリプトの dry-run を空の一時ディレクトリで走らせ、実行前後のファイル一覧とハッシュを比べること。一行でも違えば、その dry-run はすでに何かを変えている。そして終了コードを出してみてほしい。常に 0 なら、その dry-run は人が画面を読んでくれるときだけ働く装置だ。読まれない安全装置は安全装置ではない。

# dry-run 設計指針 — 作る前に目を通す一覧

> 出典: braindetox.kr — まともな --dry-run の作り方
> 根拠: POSIX Issue 8 (Shell Command Language), Bash Reference Manual, git-clean(1), rsync(1)
> このファイルをそのまま AI に貼り「うちのスクリプトをこの基準で直して」と書けば使えます。

## 1. plan / apply 分離の骨格 — そのまま貼る形

```bash
#!/usr/bin/env bash
# usage: tool.sh plan|apply [計画ファイル]
#   終了コード  0=変更なし · 2=変更あり · 1=誤り
set -uo pipefail
TAB=$(printf '\t')          # ANSI-C 引用の代わりに変数で(移植性)

make_plan() {               # ★読むだけ。生成・削除・ロック取得は禁止
  [ -d "$REQ_DIR" ] || printf 'MKDIR%s%s%sなし\n' "$TAB" "$REQ_DIR" "$TAB"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp) printf 'DELETE%s%s%s一時ファイル\n' "$TAB" "$f" "$TAB" ;;
    esac
  done
}

do_apply() {                # ★判断しない。case にない動作は誤り
  local plan="$1" action path reason
  while IFS="$TAB" read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)  mkdir -p -- "$path" ;;
      DELETE) rm -f -- "$path" ;;
      *) echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)
    make_plan | LC_ALL=C sort
    n=$(make_plan | grep -c . || true)
    [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply)
    p="${2:?計画ファイルが必要です}"
    want=$(cat "$p.sha" 2>/dev/null || echo '')
    have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
    [ -z "$want" ] || [ "$want" = "$have" ] || {
      echo "計画が古いです (plan=$want now=$have)" >&2; exit 1; }
    do_apply "$p" ;;
  *) echo "usage: tool.sh plan|apply [planfile]" >&2; exit 1 ;;
esac
```

- [ ] plan の中に書き込み命令が **一行もない**
- [ ] apply の中に状態を見る **条件分岐がない**
- [ ] 計画の各行に **理由の列** がある(人が承認できる必要がある)
- [ ] 出力順を `LC_ALL=C sort` で固定した

## 2. 終了コード規約

| コード | 意味 | CI の動作 |
|---|---|---|
| `0` | 変更なし — 目標状態と一致 | 通過 |
| `2` | 適用待ちの変更あり | 失敗扱い、または承認待ち |
| `1` | 計画を作れなかった | 即失敗 + 通知 |

- [ ] `set -e` の下で `rc=0; cmd || rc=$?` として受け取っているか
- [ ] `if cmd; then` で **2 と 1 を潰して** いないか
- [ ] パイプに繋ぐとき `PIPESTATUS` を見ているか
- [ ] ヘルプにコードの意味を書いたか
- [ ] 定期ジョブでは 2 を失敗に上げず通知だけにしているか

## 3. plan 段階で禁止する副作用

- [ ] 対象ファイルの生成・削除・切り詰め(`>` リダイレクトを含む)
- [ ] `mktemp` · `mkdir -p` による作業ディレクトリ
- [ ] ログファイルを開くこと(`exec 3> ...` は **開いた瞬間** にファイルを作る)
- [ ] ロックファイル・ロックディレクトリの取得(「握れるか」は検査だけ)
- [ ] リモート状態の変更(トークン更新・セッション生成・キュー消費)
- [ ] キャッシュ・索引の更新(次の実行の判断を変えるなら副作用)

★ **リダイレクトは分岐の外で評価される。** `f(){ ...; } > out` は dry でも `out` を切り詰める。
★ ラッパーに `run cmd > state` と書くと案内文が **状態ファイルの中へ** 入る。

## 4. 検証手順 — 三回のハッシュと副作用ゼロ

```bash
snap(){ find "$1" -type f | LC_ALL=C sort | xargs -r sha256sum | sha256sum; }

before=$(snap target)
for i in 1 2 3; do ./tool.sh plan > "p.$i"; echo "run$i $(sha256sum < "p.$i")"; done
cmp -s p.1 p.2 && cmp -s p.2 p.3 && echo DETERMINISTIC || echo "★出力が揺れている"
after=$(snap target)
[ "$before" = "$after" ] && echo "NO SIDE EFFECT" || echo "★plan が状態を変えた"
```

- [ ] 三回のハッシュが一致する
- [ ] before と after のスナップショットが一致する
- [ ] apply 後にもう一度 plan すると **空の計画 + 終了コード 0**
- [ ] 古い計画で apply すると **拒否される**

## 5. dry-run が嘘をつく条件 — 一つでも当たればヘルプに書く

- [ ] 実行分岐の **中にしかない** 検査(ロック・容量・権限・ヘルスチェック)
- [ ] 前段の成果物を後段が読む **連鎖構造**
- [ ] 計画と適用の間に **時間が流れる** 運用(承認・バッチ)
- [ ] リモート API の応答やサーバー側検証で分岐する
- [ ] 実行ユーザー・セキュリティ方針・マウント設定が異なる環境
- [ ] **部分失敗のあとの再開**(残りの計画は別の状態の上で動く)
- [ ] 時刻・乱数・走査順序が結果に混ざる

## 6. 既存ツールを使うとき

- [ ] 確認と実行の命令行が `-n` 一つだけ違うか
- [ ] dry-run の出力を **ファイルに保存** して結果と突き合わせたか
- [ ] ディレクトリ一行をファイル一個と数えていないか(一行が数百個のことがある)
- [ ] 文書の **例外の節** を読んだか(統計や進捗は保証対象外のことがある)
- [ ] リモートが絡むとき権限・経路・時刻の解釈をもう一度疑ったか

## 7. ヘルプに入れる文面のひな型

```
--dry-run   変更を適用せず計画だけを出力します。
            予測できるもの : <ここに書く>
            予測できないもの : <ここに書く>
            終了コード : 0=変更なし / 2=変更あり / 1=誤り
            このモードはいかなるファイルも作らず消しません。
```

★ 破壊的な命令を試すときは **必ず新規に作った空の一時ディレクトリの中だけで** 実行してください。

コピーしてメモアプリやAIツールにそのまま貼り付けてください。
