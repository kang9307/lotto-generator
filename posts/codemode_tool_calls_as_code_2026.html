계기 — 1년 전의 권고와 Pi 1.0의 Codemode

글은 「written on October 06, 2026」으로 표기돼 있고 글쓴이는 Armin Ronacher다. 그는 1년 넘게 전에 쓴 글 몇 편에서 사용자 정의 도구나 MCP 서버를 컨텍스트에 싣지 말고 스크립트를 더 쓰라고 권했다고 되짚는다. 그중 가장 중요한 글이 「Code Is All You Need」이고 「MCP needs code」도 썼다고 적는다. 그런데 Pi 1.0에서 Codemode를 통해 MCP 지원을 넣었다. 글쓴이는 이것이 오래전에 왔어야 할 일이면서도 일부에게는 의외일 수 있다고 쓰고, 그것이 무엇을 뜻하는지 갱신된 생각을 이 글에 적는다고 밝힌다.

  • 글쓴이와 게시일: Armin Ronacher, 2026년 10월 6일.
  • 다루는 도구: Pi. 글쓴이는 Pi 1.0에서 Codemode로 MCP 지원을 추가했다고 쓴다.
  • 이 사이트의 Pi 1.0 글은 1.0의 기능 전반을 다루고, 이 글은 Codemode에 대한 글쓴이의 논지를 따라간다.

도구란 무엇이고 bash가 못 하는 것

글쓴이는 먼저 도구가 무엇인지 짚는다. 하네스가 LLM에게 호출할 도구를 줄 때는 도구 정의를 제공하고, 이 정의는 서버 쪽에서 어떤 토큰 구조로 바뀐다. 모델이 도구를 호출하도록 유도되는지는 강화학습 과정의 결과이며, 글쓴이는 이 주제를 전에 쓴 글에서 다뤘다고 적는다.

글쓴이가 CLI와 bash 쪽으로 강하게 기우는 이유는 두 가지다. 호출을 쉽게 조합할 수 있고, 모델이 학습하면서 파일 시스템이 어떻게 동작하는지도 함께 배우기 때문이다. 모델이 echo foo > /tmp/test.txt 같은 도구 호출을 내면, 그 호출 뒤에 /tmp에 test.txt라는 파일이 생긴다는 것도 함께 학습한다는 설명이다.

그러나 bash에는 근본적인 한계가 하나 있다. 실행되는 프로그램만 조합할 수 있다는 점이다. 글쓴이는 프로그램이 아닌데도 LLM에게는 네이티브 도구인 것이 있고, 그럴 수밖에 없다고 쓴다.

  • read나 view_image: 멀티모달 모델이 이미지를 읽어야 할 때 cat으로는 안 된다. 하네스가 실제 이미지 페이로드를 LLM의 프로토콜에 넣어야 하기 때문이다.
  • 서브 에이전트: 서브 에이전트를 띄우고 조율하려면 하네스가 제공하는 도구를 피하기 어렵다. 이론상 환경 변수와 유닉스 소켓으로 바깥 하네스와 말하는 CLI 도구를 줄 수 있지만 글쓴이는 이를 조잡한 방법이라고 쓴다.
  • 코드가 어디서 실행되는가: 그 방법에는 또 하나의 문제가 있으며 글쓴이는 다음 절에서 이를 풀어 쓴다.

두뇌와 손 — 하네스와 실행 환경

글쓴이는 구성 요소가 각각 어디서 도는지 생각해 보자고 한다. 보통 두 시스템이 있다. 첫째는 두뇌인 하네스로, 한 기계에서 돌고 신뢰된다. 둘째는 손으로, 대개 같은 기계이지만 도구가 실제로 실행되는 곳이다. Pi는 이것을 이제 실행 환경이라 부르며 모든 작업의 대상(target)이라고 이해하면 된다고 한다.

중요한 것은 하네스라는 두뇌와, bash를 돌리고 도구를 실행하는 대상 환경 사이에 경계선이 있다는 점이다. 이를 반으로 나누면 중요한 결과가 따라온다고 글쓴이는 쓴다. 서로 다른 파일 시스템에서 돌고 신뢰 수준도 다르다는 것이다. 예를 들어 Gondolin 같은 샌드박싱을 쓰면 bash 쪽은 잘 샌드박스되지만 하네스 자체는 샌드박스되지 않는다.

구분글쓴이의 설명신뢰·격리
두뇌 (하네스)한 기계에서 실행된다신뢰된다
손 (실행 환경, target)대개 같은 기계이지만 bash와 도구가 실제로 실행되는 곳이다하네스와 파일 시스템이 다르고 신뢰 수준이 다르다
Gondolin 같은 샌드박싱을 쓸 때bash 쪽은 샌드박스된다하네스 자체는 샌드박스되지 않는다

Codemode가 하는 일 — 하네스 쪽 샌드박스

글쓴이는 Codemode가 실제로 하는 일을 이렇게 요약한다. LLM이 복잡한 작업을 표현하고 조율하는 방법인데, 실행 환경 쪽이 아니라 하네스 쪽에서 그렇게 한다. Codemode는 하네스 안의 자체 샌드박스에서 돈다. Pi에서는 WASM 런타임 안의 QuickJS이며 의도적인 제약이 걸려 있다.

  • 네트워크가 없다.
  • 파일 시스템이 없다.
  • 타이머가 없다.
  • RAM이 제한된다.

이 안에서 할 수 있는 일은 더 많은 도구를 호출하는 것뿐이다. 글쓴이는 Scheme 같은 다른 언어를 Codemode에서 돌리는 것도 상상할 수 있다고 덧붙인다. Codemode를 모르는 독자를 위해 글쓴이는 이렇게 정리한다. 어떤 언어 안에서 도구 호출을 내는 방법이고, 여기서는 그 언어가 JavaScript다. 덕분에 그 호출들을 LLM의 컨텍스트를 반드시 거치지 않고 조합할 수 있다. 이름은 Cloudflare가 붙였으며 글쓴이는 이 이름의 공을 Cloudflare 쪽에 돌린다.

컨텍스트에서 달라지는 것

글쓴이는 bash 호출을 예로 든다. 일반 도구 호출로 bash를 내면 Pi는 끝의 2,000줄만 컨텍스트에 넣고, 에이전트가 더 보려면 넘친 부분이 담긴 overflow 파일을 직접 들여다봐야 한다. 같은 호출을 Codemode로 내면 Codemode 쪽이 더 큰 출력을 구조화된 형태로 받는다.

Codemode가 JavaScript이므로 에이전트는 동시 작업과 기본적인 워크플로를 표현할 수 있다. 글쓴이가 요즘 에이전트에서 보는 흔한 사용법은 먼저 어떤 도구 응답에서 5~10개 항목을 살펴 모양을 확인한 다음, 나머지 n개를 처리하는 Codemode 스크립트를 쓰는 것이다.

Codemode는 상태를 트랜스크립트에 넣을 수도 있다. 한 번의 Codemode 호출이 데이터를 따로 보관하면 세션의 다음 호출이 그것을 다시 읽을 수 있다. 글쓴이는 이 저장이 샌드박스가 아니라 하네스 호스트에 있다고 강조한다. Pi에서는 이미지 생성 모델이나 텍스트를 한 번에 분류하는 분류기 모델처럼 Pi의 전통적인 인터페이스에서는 말이 되지 않는 호출도 Codemode로 낼 수 있다. 그런 Pi API는 Codemode로는 노출되지만, 일반 도구로 노출하면 컨텍스트만 낭비하므로 노출하지 않는다.

항목일반 도구 호출Codemode (글쓴이의 설명)
bash의 큰 출력끝의 2,000줄만 컨텍스트에 들어가고 나머지는 overflow 파일로 간다Codemode 쪽이 더 큰 출력을 구조화된 형태로 받는다
동시 작업과 워크플로—JavaScript이므로 동시 작업과 기본 워크플로를 표현할 수 있다
새 응답의 모양 파악—5~10개 항목을 먼저 살펴 본 뒤 나머지를 처리하는 스크립트를 쓴다
상태 보관—트랜스크립트에 데이터를 넣어 두고 다음 호출이 다시 읽는다 (하네스 호스트 쪽)
이미지 생성·분류기 모델 API일반 도구로 노출하면 컨텍스트만 낭비한다Codemode로만 노출한다

실제 세션 세 가지 — 이미지, 이슈 분류, 게임 루프

글쓴이는 자기 최근 Pi 세션에서 가져온 Codemode 호출을 보여 준다. 이 코드는 사람이 쓴 것이 아니라 실제 Pi 세션에서 나온 것이며, 읽기 좋게 들여쓰기만 다시 했다고 밝힌다. 에이전트가 Codemode를 자동으로 쓰기 시작하는 것은 모델이 이미 자연스럽게 그 도구를 고르는 작업이거나 사용자가 요청했기 때문이다. Pi에서 Codemode는 MCP가 켜져 있을 때만 기본으로 켜지고, 설정에서 defaultTools에 "+codemode"를 넣어 켤 수 있다. 글쓴이는 Pi에게 켜 달라고 요청해도 된다고 적는다. 아래 코드는 글의 코드를 공백만 정리한 것이고, 두 번째는 일부를 줄였다.

이미지 생성

이미지 생성은 Pi가 AI SDK 코어에서 지원하는 기능이지만 에이전트가 쓸 수 있는 도구는 아니다. 전에는 이미지 모델을 쓰려면 맞춤 확장을 만들거나 에이전트가 node를 직접 돌려 내부 이미지 API를 쓰게 해야 했다. 내부 모델 API를 상당수 Codemode 안에 노출하므로 이제 에이전트가 쓸 수 있다.

const [painter] = await models.getAvailableOfType("image");
                    const result = await models.generateImages(painter, {
                      input: [{ type: "text", text: "A cute little puppy sitting on a grassy " +
                        "lawn, soft natural light, photorealistic" }],
                    });
                    if (result.stopReason !== "stop") return result.errorMessage;
                    for (const block of result.output) {
                      if (block.type === "image") image(block);
                      else text(block.text);
                    }

image()를 호출하면 이미지가 LLM에게 이미지 콘텐츠로 돌아간다. 하네스 쪽에서는 이를 에이전트에게 바로 넣고, 에이전트가 이미지를 다시 bash에 넘길 수 있도록 디스크에 임시 산출물로도 남긴다.

분류기로 GitHub 이슈 분석

Jev 같은 분류기 모델도 일반 도구로는 에이전트의 워크플로에 잘 맞지 않는다. 맞춤 도구를 만드는 대신 Codemode가 에이전트에게 AI SDK에 직접 손을 뻗어 호출하게 한다. 글쓴이가 보여 주는 코드는 Jev로 GitHub 이슈를 한꺼번에 처리해 빠른 감정 분석을 하는 것이다.

const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
                    const r = await tools.bash({
                      command: "gh issue list --state open --limit 100 " +
                        "--json number,title,body,comments",
                    });
                    const issues = JSON.parse(r.output);
                    const results = await Promise.all(issues.map(async (issue) => {
                      const res = await models.classify(jev, {
                        state: {
                          title: issue.title,
                          body: (issue.body || "").slice(0, 4000),
                          comments: issue.comments.slice(-5).map(c => c.body.slice(0, 800)),
                        },
                        questions: {
                          sentiment: {
                            type: "choice",
                            instructions: "What is the overall sentiment of the author towards pi?",
                            criteria: {
                              positive: "Appreciative, happy, constructive praise",
                              neutral: "Matter-of-fact report or request without emotion",
                              negative: "Frustrated, annoyed, upset, or angry",
                            },
                          },
                          // ... frustration (score), kind (choice)
                        },
                      });
                      // ...
                    }));
                    store("sentiment_results", results);
  • 열린 이슈를 최대 100개 가져온다 (gh issue list에 --limit 100).
  • 이슈마다 본문은 4,000자까지, 댓글은 마지막 5개를 각각 800자까지 잘라 분류기에 보낸다.
  • 질문은 세 가지다. 작성자의 전반적인 감정(positive, neutral, negative 중 선택), 좌절 정도(점수), 이슈 종류(bug, feature, question, other 중 선택).
  • 전체 결과는 store()로 세션 트랜스크립트에 넣고, 좌절 점수가 높은 순으로 12개만 골라 돌려준다. 글쓴이는 나중의 Codemode 호출이 그 결과를 다시 읽을 수 있다고 쓴다.
  • Promise.all이 여기서 괜찮은 이유는 Pi가 동시에 실행하는 도구 수를 4개로 제한하고 나머지는 큐에 두기 때문이다.

게임 디버깅 루프

더 모험적인 예시로 글쓴이는 Jev로 게임 엔진을 구동해 디버깅을 돕는 사례를 든다. 에이전트는 글쓴이의 tankctl 명령을 알고 있었고, 그 주위에 게임 루프를 구동하는 최소한의 하네스를 빠르게 만들었다. 30단계 루프를 돌며 매 단계마다 게임 엔진에서 상태를 텍스트로 덤프하고 Jev에게 다음에 할 일을 판단하게 한다.

예시Codemode로 한 일글쓴이가 짚은 점
이미지 생성models로 이미지 모델을 찾아 생성하고 image()로 결과를 돌려준다Pi가 지원하지만 에이전트용 도구는 아니었다. 내부 모델 API를 Codemode에 노출해 쓸 수 있게 됐다
GitHub 이슈 분류열린 이슈 100개를 Jev로 분류하고 store()로 저장한다분류기는 일반 도구의 워크플로에 맞지 않는다. 맞춤 도구 없이 AI SDK를 직접 호출한다
게임 디버깅 루프30단계 루프에서 엔진의 텍스트 덤프를 Jev에게 보내 다음 행동을 정한다에이전트가 tankctl 주위에 최소한의 하네스를 스스로 만들었다

MCP 서버 호출과 「Codemode 안의 Codemode」

글쓴이는 Codemode가 MCP 서버를 부르는 데 확실히 좋다고 쓴다. Pi는 MCP 도구를 LLM에게 하나도 노출하지 않는다. 대신 에이전트가 Codemode 안에서 제공되는 API로 도구 검색을 먼저 해서 연결된 서버로 무엇을 할 수 있는지 찾는다. 글쓴이는 이런 점진적 발견이 오늘의 많은 사용 사례에서 MCP를 충분히 쓸 만하게 만든다고 본다.

예시에서 에이전트는 도구를 발견하기 전에 곧바로 Sentry MCP에 손을 뻗는다. 글쓴이는 아마 강화학습 과정에서 Sentry MCP가 어떻게 생겼는지 이미 배웠기 때문일 것이라고 추정한다. 다만 시스템 프롬프트에 주입한 정보로 Sentry 서버가 있다는 사실은 안다고 덧붙여, 완전히 짐작만 하는 것은 아니라고 한다.

const orgs = await tools.mcp__sentry__find_organizations({});
                    const { organizations } = orgs.structuredContent;
                    const results = await Promise.allSettled(
                      organizations.map(org => tools.mcp__sentry__find_projects({
                        organizationSlug: org.slug,
                        regionUrl: org.regionUrl,
                      }))
                    );

글쓴이는 MCP를 길게 말하고 싶지 않다고 하면서도, MCP가 Codemode의 혜택을 크게 받는 프로토콜이라고 쓴다. 문제는 MCP가 실제로는 아직 Codemode를 쓰지 않는 하네스를 대상으로 하는 경우가 많다는 점이다. 글쓴이는 흐름이 바뀌고 있다고 본다. 그사이의 임시방편으로 Cloudflare가 했던 것처럼 MCP 서버 안에서 Codemode를 하는 방식이 쓰였다. 그러나 이제는 Codemode 안에 Codemode가 들어가는 꼴이 됐고, 글쓴이는 이것이 꽤 나쁘다고 평가한다.

  • JSON을 이중으로 이스케이프해야 한다.
  • 작은 모델이 쉽게 혼란스러워한다.
  • 안쪽 코드가 바깥 도구를 호출할 수 없다.

그래서 Pi에서 Cloudflare MCP 서버를 쓰면 에이전트가 JavaScript를 쓰고 그것을 또 다른 JavaScript에 흘려 넣어야 한다. 글쓴이는 이것이 최적은 아니지만 왜 이렇게 되는지는 이해할 만하다고 쓴다.

MCP에 바라는 점과 남은 과제

글쓴이는 오늘 Codemode가 MCP와 얼마나 잘 맞느냐는 물음에 아주 잘 맞지는 않는다고 답한다. MCP 서버가 아직 Codemode를 쓰는 하네스를 겨냥하지 않기 때문이다. 지금은 대부분의 하네스가 Codemode를 지원한다고 보지만 서버 쪽이 따라오지 않았다는 취지다. 그래서 잘 맞게 하려면 필요하다고 그가 꼽는 권고가 네 가지다.

항목문제글쓴이의 설명
구조화된 콘텐츠Codemode는 호출이 잘 정리된 JSON을 돌려주길 원하지만 많은 서버가 아직 그러지 않는다MCP의 outputSchema 체계가 이를 위해 좋다
일관된 결과서버가 결과 집합의 항목 수에 따라 토큰을 최적화하면 데이터가 일관되지 않을 수 있다5개 항목으로 한 첫 탐색은 성공하는데, 서버가 최대 배치 크기를 돌려주면 실패하는 경우가 있다
큰 바이너리 데이터MCP가 아직 큰 바이너리 데이터를 지원하지 않아 흥미로운 사용 사례 상당수가 전혀 잘 되지 않는다파일 업로드를 사전 서명 URL로 MCP 밖 채널에서 처리하는 등 갖가지 우회가 생긴다
합성 가능한 도구 검색어떤 도구가 맞는지는 MCP 클라이언트보다 서버가 더 잘 알 수 있다하네스가 여러 MCP 서버에 도구 검색을 퍼뜨릴 좋은 메커니즘이 없어서, 지금은 창발적 행동이고 서버가 여럿이면 확장되지 않는다

글쓴이는 이것이 1년 전의 권고를 뒤집는 것이냐는 물음에 아니라고 답한다. 그가 보기에 MCP 생태계는 1년 전에 지적했던 것, 곧 코드가 통한다는 점을 따라잡았다. Codemode는 MCP를 넘어 하네스 안에서 에이전트에게 더 큰 자유를 표현하는 수단으로도 작동한다. 다만 풀어야 할 것이 남아 있다고 쓴다.

  • 내구성: Codemode에서는 더 까다롭다. 내구성 있는 워크플로 엔진의 아이디어를 가져와 호출을 스냅샷해야 할 수 있다.
  • 합성 언어: 결정적이라는 점에서 Starlark 같은 것이 JavaScript보다 나은 합성 언어일 수 있다.
  • 이미지와 바이너리 데이터가 아직 정리되지 않았다.
  • 작은 모델과는 이 패턴이 통하지 않는다.

글쓴이는 이것이 아직 완벽한 해법은 아니지만 꽤 쓸모 있는 패턴이고 앞으로 더 많이 쓰게 되리라 기대한다고 맺는다.

확인하지 못한 것

  • 샌드박스의 RAM 제한이 얼마인지: 글은 RAM이 제한된다고만 쓰고 수치를 주지 않는다.
  • Codemode를 쓸 때와 쓰지 않을 때의 토큰 수나 시간 차이: 글에는 측정값이 없다.
  • store()로 보관한 데이터가 세션을 다시 시작한 뒤에도 남는지, 어떤 형식으로 저장되는지: 글은 세션 트랜스크립트에 넣는다고만 쓴다.
  • Cloudflare가 먼저 쓴 방식과 Pi의 방식이 세부에서 어떻게 다른지: 두 글을 항목별로 대조하지 않았다.
  • 작은 모델이 Codemode 스크립트를 얼마나 잘 쓰는지: 글은 한계라고만 언급하고 성공률을 주지 않는다.
