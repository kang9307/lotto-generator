1. 極初期プレビュー公開とGEFSの目指す地平

現代のオペレーティングシステムにおいて、ファイルシステムは不揮発性ストレージの物理的制約を覆い隠し、データの永続性と整合性を死守するための基幹インフラである。メモリダンプの構造解析に特化したMemNixFSや、情報理論の限界を突いた思考実験的設計であるπFSといった特殊ファイルシステムとは対照的に、汎用ブロックストレージ向けファイルシステムは、突然の電源断に対する耐性と書き込み増幅の抑制という極めて現実的な課題に立ち向かわねばならない。2026年9月15日、9front（ベル研究所のPlan 9から派生したOS）プロジェクトの関係者であるOri Bernstein氏は、openbsd-techメーリングリストを通じて、新規ファイルシステム「GEFS（Good Enough File-System）」のOpenBSD向け極初期プレビュー（a very early preview）を公開した。先立って開催されたEuroBSDカンファレンスでの発表を受けたこの動きは、ニッチかつ先鋭的なストレージアーキテクチャがOpenBSDカーネルへ移植される端緒を開くものである。

メーリングリスト上で開発者自身が下した現状評価は、極めて率直かつ飾りのないものであった。原文は現在のポートを「粗く、バグが多く、課題だらけのプレビュー（rough, buggy, issue-filled preview）」と明言し、実運用環境（プロダクション）への投入には全く適していないと強く警告している。特にエラーハンドリングの過程でデータの消失（data loss）が起き得ることが開発者によって直接言及されており、現時点でOpenBSD公式ソースツリー（in-tree）へのマージ申請を行う段階にもない。それにもかかわらず、このプレビューが技術的関心を集めている理由は、解決すべき課題の輪郭が明晰に把握されていること、そして何よりカーネル内実装が9,000行未満（under 9,000 lines of code）という極めて簡素なボリュームでありながら、近代的なコピーオンライト（Copy-on-Write, CoW）機能を堅固に実現している点にある。

GEFSという名称は「十分なファイルシステム（Good Enough File-System）」を意味している。あらゆる指標で極限の最適化を競うのではなく、簡潔な構造と明確な優先順位を守り抜くことで、日常的な利用において「これで十分である」と言える信頼性を目指すという実用主義的な意思表明である。本記事では、この名前が掲げた設計優先順位の誓約が実際のコード構造においていかに具現化されているかを検証し、公開された技術的課題の全貌を客観的に記録する。

2. 名前に込められた4大設計優先順位と裏付けのメカニズム

ファイルシステムのエンジニアリングにおいて、相反する要求を同時に満たすことは困難である。書き込み速度を最優先すれば障害時の整合性検証コストが増大し、メタデータの安全性を過度に固めれば直列化のオーバーヘッドが生じる。GEFSの設計文書において、Ori Bernstein氏は設計目標を4つの明確な序列に整理した。その優先順位は、第1にクラッシュ安全性（crash-safe）、第2に破損検知（corruption-detecting）、第3に単純性（simple）、第4に高速スナップショット（fast snapshotting）である。

この優先序列は単なるスローガンではなく、具体的な実装メカニズムと厳格に結びついている。第1のクラッシュ安全性は、全データとメタデータのコピーオンライト配置およびスーパーブロックのアトミックコミットによって達成される。第2の破損検知は、すべてのブロックポインタを物理アドレス・暗号学的ハッシュ・世代番号からなる64ビット3要素タプルとして保持することで実現される。第3の単純性は、階層的なディレクトリツリーや間接ブロックを完全に廃止し、Bε-treeを用いた単一のフラットなキーバリューストアで表現することで、カーネルコードを9,000行未満に収めることによって体現されている。第4の高速スナップショットは、5秒ごとのコミット時にルートブロックの差分のみを複製する仕組みによって最小限のコストで動作する。

設計優先順位（序列） 中核となる技術目標 実装メカニズム アーキテクチャ上の振る舞い
① crash-safe（クラッシュ安全） 突発的な電源断による構造破損の絶対的防止 Copy-on-Write配置とスーパーブロックのアトミック同期、5秒周期スナップショット 再起動時にディスクに同期済みの最新コミットへ復帰。最大5秒のデータ消失はあり得るが構造破損はゼロ
② corruption-detecting（破損検知） 記憶媒体のサイレントディスクトラッシュやビット反転の検知 ブロックポインタを「ブロックアドレス・ブロックハッシュ・生成世代」の3要素タプルで管理 読み取り時にハッシュ照合を実行し破損を検知・報告。将来の自動修復機構の基盤を形成
③ simple（単純性） 複雑な間接層を排除し監査可能なコード量を維持 Bε-tree基盤のフラットなキーバリューストア（間接ブロックや木構造ディレクトリを排除）、9,000行未満のコード 単一構造への複数属性アトミック更新（upsert）、ロックを必要としない安全な読み取り走査
④ fast snapshotting（高速スナップショット） オーバーヘッドのない頻繁なスナップショット生成 一意な整数IDによる不変スナップショット、参照カウント方式による自動回収 ルートバッファの差分書き込みを中心に処理。子孫参照のみとなったスナップショットは自動破棄

この厳格な序列は、トレードオフが生じた際のファイルシステムの挙動を規定している。たとえば、スループットを稼ぐためにハッシュ検査を省略したり、書き込み同期の順序を崩すような最適化は、GEFSの設計思想において断じて許容されない。性能向上は、クラッシュ安全性、破損検知、単純性という上位3つの規範を侵さない範囲内でのみ追求される。

3. Bε-treeアーキテクチャ — 書き込み増幅緩和と読み取り経路のトレードオフ

GEFSの中核をなすデータ構造が「Bε-tree（B-イプシロンツリー）」である。従来のB+treeをコピーオンライトで運用する場合、小さなファイルやメタデータの更新であっても、変更されたリーフノードからルートに至るすべての祖先ノードを新領域に再割り当てして書き込む必要がある。この連鎖的な更新が深刻な「書き込み増幅（write amplification）」を引き起こし、ストレージの寿命と帯域を浪費させる。

Bε-treeは、中間ノードである「ピボットノード（pivot node）」に専用の書き込みバッファ（write buffer）を組み込むことで、この問題を劇的に緩和する。ファイルシステムへの書き込みや属性更新が発生した際、ツリー全体をリーフまで探索するのではなく、ルートノードをコピーしてその書き込みバッファに変形メッセージ（upsert message）を追記する。バッファが満杯になると、保留中のメッセージが最も集中している子ノードを選定し、そこに向けてバッファの内容を一括フラッシュする。このプロセスが下層へと再帰的に伝播し、最終的にリーフノードに到達する仕組みである。

このアーキテクチャの利点は、ディスクへのI/Oをまとまったシーケンシャルな単位に集約できる点にある。さらに、メッセージ自体が変更操作を記述しているため、mtimeの更新やファイルバージョンのインクリメントを行う際に、事前に古いデータをディスクから読み出す必要がない。ルートバッファへの追記だけで完結するため、読み取り・修正・書き込み（read-modify-write）のサイクルを丸ごとスキップできる。ルートノードの容量が許す限り、複数の操作を1つのコミット内で完全にアトミックに適用できる点も大きな強みである。

だが、ソフトウェア工学の不変の原則に従い、この書き込み最適化は読み取り経路（read path）において相応の代償を支払う。特定キーのデータを読み出すためには、ツリーをルートからリーフまで辿る際、その経路上のすべてのピボットノードの書き込みバッファを検査しなければならない。リーフノードの実データに対して、まだ中間バッファに留まっている保留中メッセージを順次適用して初めて最新の整合したデータが得られるからである。原文には定量的レイテンシ測定値は示されていないが、構造的に読み取り処理が多層バッファの照合を伴うという点は、Bε-treeを採用する上で避けられない構造的トレードオフである。

Kdat(qid, offset) → (ptr)
Kent(pqid, name)  → (stat)
Kup(qid)          → Kent(pqid, name)

上の定義が示すように、GEFSはファイルシステムの全構成要素を単一のフラットなキーバリューストアにマッピングする。データブロックポインタはQIDとオフセットを結合したKdatキーで管理され、ディレクトリエントリは親QIDとファイル名を組み合わせたKentキーで保持され、上位ディレクトリへのパスはKupキーで解決される。Bε-treeがキーをソート順で保持するため、ディレクトリ一覧の取得は特定QIDから始まるキーの範囲スキャン（range scan）で高速に行われ、Plan 9の旧来ファイルシステムに見られたO(n)線形走査の遅延を完全に克服している。

4. クラッシュ安全性と3要素タプルによる破損検知構造

ファイルシステムにおけるクラッシュ安全性とは、電源の遮断やOSのパニックが発生した際に、ディスク上の構造が破壊されず正常に復帰できる能力を指す。GEFSはこの安全性を確立するため、厳密なライトオーダリング（書き込み順序制御）を敷いている。変更されたデータやメタデータはすべて未割り当ての空き領域へCoW方式で書き込まれ、それらのブロックが物理メディア上に完全に同期された後にのみ、スーパーブロックのアトミック更新が行われる。

設計文書に明記された具体的な挙動によれば、スーパーブロックが更新される前にシステムがクラッシュした場合、次回のマウント時には直前にディスクへ同期完了していた最後のコミットが読み出される。デフォルトの運用において、最大5秒分の未確定データが消失する可能性はあるが、ファイルシステム内部の構造的破損（corruption）は一切発生しない。すなわち、「データの損失（loss）は生じ得ても、構造の破壊（corruption）は起こさない」という工学的境界線が堅牢に維持される。

さらに、GEFSは記憶媒体の物理的劣化やコントローラの不具合に起因するサイレントデータ破損（silent corruption）を捕捉するため、従来の単純なブロック番号に代えて、以下の64ビット3要素タプルからなるブロックポインタを採用した：

  • ブロックアドレス（block address）：ストレージデバイス上における物理的なブロックオフセット位置を示す。
  • ブロックハッシュ（block hash）：ブロック内の全データから算出された暗号学的ハッシュ値であり、読み出し時の改ざん・破損検知に用いられる。
  • 生成世代（birth generation）：そのブロックがどのスナップショット世代で最初に確保されたかを識別する単調増加カウンタである。

読み出し処理の過程で記憶媒体から破損データが返された場合、GEFSはハッシュ値の不一致により即座に異常を検知し、上位カーネル層にエラーを通知する。破損したデータが正常なふりをしてメモリに展開される事態を阻止できる。現在はI/Oエラーとしての報告にとどまるが、将来的にミラーリングやRAID機能が統合された暁には、このハッシュ検証を起点として自動修復（self-healing）を完結させる設計構想となっている。

5. スナップショットのライフサイクルと空間回収 — ZFS deadlistの採用とbtrfs棄却の理由

純粋なコピーオンライトファイルシステムにおいて、スナップショットの取得自体は極めて軽量である。特定時点におけるツリーのルートポインタを固定して保持するだけで足りるからである。GEFSのスナップショットは一意な整数IDによって管理され、取得された瞬間に完全な不変（immutable）状態となる。人間が識別しやすい文字列ラベルを付与することも可能で、ラベルは更新コミットに合わせて自動追従させることも、特定のスナップショットに固定しておくこともできる。

真の課題はスナップショットの生成ではなく、不要になったスナップショットを破棄した際に、占有されていたブロックをディスクに返却する「空間回収（space reclamation）」の工程で生じる。GEFSは5秒ごとに自動スナップショットを取得する仕様であるため、不要領域を回収できなければストレージは瞬く間に枯渇してしまう。設計段階においてBernstein氏は先行する主要ファイルシステムの空間回収アルゴリズムを精査し、その多くを明確な根拠に基づいて棄却した。

回収方式 ZFS deadlist方式（GEFSが採用） btrfs最適化参照カウント（棄却） HAMMERスタイルガベージコレクション（棄却）
基本構造 スナップショット内で解放されたブロックをdeadlistで追跡し、スナップショット削除時にマージ回収 ツリー内の各ブロックごとに参照カウントを追跡し、共有関係の変動に応じて逐次更新 バックグラウンド処理がディスク全域を定期的に走査（スキャン）して不要ブロックを探索
書き込みI/O特性 世代別のリストへの追記が中心となり、シーケンシャルな書き込み特性を高度に維持 参照カウントの更新に伴い、メタデータ全域に大量の分散した（scattered）ランダム書き込みが発生 走査処理とメタデータ書き込みが帯域を奪い合い、周期的なI/Oレイテンシの悪化を招く
削除処理の効率 削除対象世代のdeadlistに載っているブロックのみをピンポイントで解放するため高速 参照ツリーの書き換えとロック競合により、スナップショット削除時の負荷が大きい テラバイト級の大容量ドライブにおいて全域スキャンの完了に長時間を要する
GEFSの設計判断 採用：ZFSから直接導入し（lifted directly from ZFS）、ランダム書き込みを回避して単純性を確保 棄却：大量の分散書き込みがCoW B-tree本来の性能を著しく損なうと判断 棄却：周期的スループット低下とディスク全域走査のオーバーヘッドが過大と判断

btrfsの方式を棄却した決定的な理由は、「参照カウントを維持するために大量の分散した（scattered）書き込みが発生するため」と明記されている。ブロックごとに参照カウンタを細かく管理すると、スナップショットの分岐や削除のたびにツリーのあちこちへ微細なランダム書き込みが散発し、ストレージ性能を大きく低下させる。また、HAMMERスタイルの全域ガベージコレクションも、書き込み負荷が高まるにつれてメタデータ更新帯域とスキャン帯域が競合し、致命的なレイテンシの悪化を引き起こす。

そこでGEFSは、ZFSで長年実績を重ねてきたdeadlist方式をそのまま採用した。ブロックポインタに刻まれた「生成世代」を活用し、現行スナップショット内で生成され同世代内で破棄されたブロックは即時解放する。過去世代から引き継いだブロックが不要になった場合は、現行スナップショットのdeadlistに登録する。スナップショットが削除されると、そのdeadlistは子孫スナップショットへマージされ、直前の基準世代以降に生成されたブロック群が一括して空き領域へ返却される。deadlistを世代ごとにシャーディングすることで、削除時には対象リストのみを走査すればよく、ディスク全体を総なめにする無駄を徹底的に排除している。

6. OpenBSDポートの現状と原文が明かした12の課題チェックリスト

現在提供されているOpenBSD向けコードは、Plan 9（9front）の実装をカーネルへ持ち込み、初歩的なマウント動作に漕ぎ着けた段階のポートである。Ori Bernstein氏はメーリングリストにおいて、現状のコードに存在する12項目の欠陥や未完成領域を包み隠さず列挙した。このプロジェクトの到達度を正確に見極めるためには、開発者自身の提示したこの技術的チェックリストを精査する必要がある。

  1. スーパーブロック一貫性プロトコルの検証不足（Consistency Protocol）：スーパーブロックの更新は、スナップショットに含まれる全ブロックがディスクへ完全に永続化された後に行われなければならないが、9front側で施された書き込み順序に関する一部の修正がまだOpenBSD側へバックポートされていない。
  2. エラー処理の大半がコメントアウト状態（Commented out error handling）：9front向けに書かれたエラーハンドリング構造がOpenBSDカーネルの設計思想と合致せず、大半の例外処理パスがコメントアウトされたまま残存している。慎重な再実装が必要とされる。
  3. グローバル変数使用による単一マウント制約：カーネルコード内にグローバル変数が残存しているため、現行の実装では同時に1つのGEFSファイルシステムしかマウントできない。
  4. ネイティブなユーザランドツールの欠如（Userspace tools）：OpenBSDネイティブのnewfsやfsckユーティリティが存在しない。ファイルシステムの新規作成や修復を行うには、仮想マシン（VM）上で9frontを起動して作業しなければならない。
  5. スナップショット管理機能の未整備：スナップショットの作成、ラベル操作、削除を行うためのOpenBSD向けコマンドラインツールおよびカーネルioctlインターフェースが未実装である。
  6. POSIX仕様との齟齬の可能性（Posix persnicketies）：非POSIX環境であるPlan 9から移植されたコードであるため、標準的なUNIX/POSIXファイルシステムが要求する厳密な制約条件を満たせていない箇所が多数潜んでいる可能性が高い。
  7. 回帰テストスイートの欠如（Regress）：Plan 9向けには小規模なテストスイートが存在するものの、OpenBSDカーネル向けのregressテスト環境は一切用意されていない。
  8. ハードリンクの未対応（Hardlinks）：アルゴリズム自体の実装は難しくないものの、ファイルごとの参照カウント管理ファイル（refcount file）を扱うロジックがまだ組まれていない。
  9. kqueueイベント通知との未連携：ファイルやディレクトリの変更をカーネルから検知するためのOpenBSD標準イベント機構であるkqueue用vnodeフックが未接続である。
  10. NFSエクスポート機能の欠落：ネットワークファイル共有を行うためのNFSサーバフックおよびvnode変換ロジックが整備されていない。
  11. ブートローダおよびルート運用の未対応：OpenBSDのブートローダからの起動、ルートパーティションとしての利用、ならびにクォータ（quota）機能が実装されていない。
  12. 巨大ファイル削除時の処理遅延：致命的ではないものの、ブロック単位でupsertを繰り返す現在の実装では、大容量ファイルの削除時に処理時間が著しく延びる課題が確認されている。

この12の項目は、本ポートがエンドユーザーの日常運用やサーバ構築の選択肢からは程遠い段階にあることを明白に示している。カーネルコードが9,000行未満とコンパクトであることは解析やハッキングの容易さを意味する反面、堅牢な実用ファイルシステムに必要な付随構造が手付かずのまま残されている証左でもある。

7. ファイルシステムの系譜と移植哲学 — Plan 9環境からBSDへ

GEFSが誕生した背景には、Plan 9および9frontにおける長期にわたるファイルシステムの歴史的蓄積と課題がある。Plan 9には古くから多様なファイルサーバが存在したが、それぞれ固有の弱点を抱えていた。標準であったcwfsは高速で安定していたもののクラッシュ安全性を欠き、ダンプ領域からの回収機構を持たなかった。実験的なhjfsはコードが極めて簡素であったが速度が致命的に遅く、整合性検査機構がなかった。fossilはsoft-updatesによる複雑性のためにデッドロックやクラッシュの報告が絶えず、ventiと組み合わせても空き領域を効率的に再利用できなかった。

GEFSはこれらの欠陥を一掃すべく開発された。そしてこの成果をOpenBSDへ持ち込むにあたり、Bernstein氏は特異なアプローチを選択した。2つのOSの差異を吸収するための無理な抽象化レイヤ（abstraction layer）を挟むことを拒否し、コードを直接複製しながらも、双方の内部データ構造やコアロジックが互いに「韻を踏む（rhyme）」状態を維持するという手法である。

# OpenBSDアップストリームソースの取得
git clone https://github.com/openbsd/src
cd src

# GEFSリモートリポジトリの登録とチェックアウト
git remote add gefs git://shithub.us/ori/openbsd
git fetch gefs
git checkout -b gefs gefs/gefs

上記のコマンドは、開発者が告知の中で示したパッチの適用手順である。OpenBSD特有のコーディング規約であるKNF（Kernel Normal Form）への過度な即時適合も避け、9frontの元コードとの対応関係を見失わないよう配慮されている。Plan 9の9Pディスパッチモデルから受け継いだマルチプロセス構造やエポックベースの領域回収が、OpenBSDカーネルのvnode構造体やロック体系といかに調和していくかが、今後の開発の焦点となる。

8. 価値を発揮する領域と発揮できない領域 — 実験環境と本番の境界

ソフトウェアの工学的価値は、それが投入される環境の文脈によって180度反転する。GEFSの初期プレビューは、極めて高い価値を持つ場所と、断じて立ち入ってはならない場所が明確に二分されている。

本プロジェクトが真価を発揮するのは、ファイルシステムアーキテクチャの研究、カーネルハッキング、そして教育的な実験環境である。OpenZFSやbtrfsのような本格的なプロダクションファイルシステムは数十万行から百万行規模の巨大なコードベースを持ち、単独のエンジニアが全体の動作機序を完全に把握することは極めて難しい。これに対し、GEFSはわずか9,000行足らずのCコードの中に、Bε-tree、Copy-on-Write、アトミック同期、ハッシュ検証、ZFS由来のdeadlistといった現代的ファイルシステムの核心技術を無駄なく凝縮している。ストレージI/Oの最適化理論を実践コードで学びたい開発者にとって、これほど透明性の高い教材は稀である。

反対に、いかなる理由があろうとも投入してはならないのが、実データを扱う本番環境である。開発者自らが「エラー時のデータ消失が予想される」と公言しているファイルシステムに、業務データや個人資産を委ねることは工学的に見て無謀である。また、5秒ごとのコミット仕様は、データベースの先行書き込みログ（WAL）のように即時永続性を求めるワークロードとは本質的に整合しない。現段階のGEFSは、完全に破棄可能な仮想マシンや予備ストレージの上で、アーキテクチャの可能性を探求しバグ出しに貢献するための実験場としてのみ扱われるべきである。
