코드 크기·의존성·변경 이유를 직접 재서 「완성」과 「죽음」을 구분하는 법

서론: 커밋이 3년째 없다는 사실만으로는 아무것도 알 수 없다

의존성 목록에 넣으려는 라이브러리를 열어 본다. 별은 충분히 많고, 문서도 있고, 하는 일도 딱 필요한 만큼이다. 그런데 커밋 그래프가 3년째 평평하다. 이 순간 손이 멈춘다. 관리가 끊긴 코드를 프로덕션에 넣는 것 같아서다.

그래서 대부분은 커밋이 활발한 대안을 찾는다. 그 판단이 항상 틀린 것은 아니지만, 근거는 틀렸다. 커밋 빈도는 소프트웨어의 건강 상태가 아니라 남은 일의 양을 나타내는 지표에 가깝다. 남은 일이 많아서 활발할 수도 있고, 남은 일이 없어서 조용할 수도 있다. 그래프만 봐서는 어느 쪽인지 알 수 없다.

이 글은 그 구분을 측정 가능한 형태로 바꾸려는 시도다. 오래 사는 소프트웨어의 조건을 감상이 아니라 숫자로 다루고, 그 숫자를 재는 스크립트를 직접 돌려 결과를 붙였다. 결론부터 말하면 오래 사는 코드의 조건은 열정도 인기도 아니다. 작고, 의존성이 적고, 범위가 좁고, 문서가 있는 것. 그리고 그 넷은 전부 무언가를 넣지 않기로 한 결정의 결과다. 기술이 아니라 거절의 축적이다.

실행 환경. 아래 측정은 전부 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 셸은 GNU bash 5.2.37 (MSYS2/MinGW64), 도구는 Python 3.13.3, Node.js v22.16.0, npm 11.5.2다. 측정 대상은 그 환경에 설치된 파이썬 3.13 표준 라이브러리와, 공개 레지스트리에서 해결만 한 의존성 트리다. 스크립트는 모두 파일로 저장해 실행했고, 명령을 그대로 옮겨 적었다.

이 글이 다루지 않는 것. 정리 작업의 비용을 언제 회수하는지에 대한 계산은 리팩터링 비용은 언제 회수되나에서 다뤘다. 여기서는 회계가 아니라 판정 기준만 본다. 코드를 애초에 유지보수 가능하게 쓰는 습관은 유지보수 가능한 코드 작성 쪽이다. 이 글은 이미 존재하는 코드를 어떻게 판정하고 처분할 것인가만 다룬다.

1. 「죽었다」와 「완성됐다」는 같은 그래프를 그린다

커밋이 멈춘 상태는 두 가지 서로 다른 사실을 같은 모양으로 보여 준다. 하나는 할 일이 남았는데 아무도 하지 않는 것이고, 다른 하나는 할 일이 실제로 끝난 것이다. 전자는 위험하고 후자는 오히려 안전한데, 저장소 첫 화면에서는 구분되지 않는다.

구분하려면 그래프가 아니라 남아 있는 것들의 성격을 봐야 한다. 아래는 실무에서 실제로 사용할 수 있는 판별 신호다.

관찰 지점방치에 가까운 신호완성에 가까운 신호
열린 이슈의 성격재현 가능한 버그 보고가 무응답으로 쌓임대부분 기능 추가 요청이고, 범위 밖이라며 닫혀 옴

최근 변경 이유변경 자체가 없음, 또는 정체 불명버그 수정과 외부 환경 대응이 대부분

이 표의 핵심은 「변경이 적다」를 문제로 읽지 않는 것이다. 문제는 변경이 적은 게 아니라 있어야 할 변경이 없는 것이다. 그리고 「있어야 할 변경」은 대부분 두 종류다. 안에서 발견된 결함을 고치는 것과, 밖에서 바뀐 세계에 맞추는 것. 이 둘이 나오고 있다면 그 프로젝트는 살아 있다. 기능이 늘지 않는 것은 별개의 사실이며, 때로는 의도된 결과다.

실무적으로 하나만 덧붙이면, 판정을 저장소 하나로 끝내지 말 것이다. 배포판이 그 소프트웨어를 계속 포함하고 있는지, 다른 프로젝트가 여전히 그것을 링크하고 있는지가 훨씬 강한 신호다. 상류가 조용해도 하류가 활발하면 그 코드는 이미 인프라가 된 상태다.

2. 작은 코드베이스가 사는 이유 - 읽을 수 있으면 고칠 수 있다

작은 코드가 오래 사는 이유는 우아해서가 아니라 인수인계 비용이 사람 한 명 안에 들어오기 때문이다. 「이 모듈 이제 네가 맡아」라는 말이 실행 가능한 문장이 되는 크기가 있다. 그 크기를 감으로 말하지 않으려면 재야 한다.

재는 방법은 단순하다. 주석과 빈 줄을 빼고 실제 코드 줄만 세면 된다. 파이썬 표준 라이브러리를 대상으로 돌린 결과다.

여기서 읽어야 할 것은 순위가 아니라 자릿수다. 355줄과 11,165줄은 같은 종류의 물건이 아니다. 앞의 것은 한 사람이 하루 안에 전부 읽고 책임을 넘겨받을 수 있고, 뒤의 것은 그렇지 않다. 유지보수 가능성은 연속적인 척도가 아니라 임계값이 있는 성질에 가깝다.

다만 작다는 것이 곧 좋다는 뜻은 아니다. 작은 모듈은 기능을 덜 담았다는 뜻이고, 부족한 부분은 사용자가 직접 채워야 한다. 크고 기능이 많은 쪽은 그 비용을 자기가 떠안아서 사용자를 편하게 만든 것이다. 어느 쪽이 옳은지는 그 코드가 몇 명에게 얼마나 오래 쓰이는지에 달려 있다. 사용자가 많고 수명이 길수록, 사용자 쪽에 떠넘긴 비용의 합이 커진다.

2.1 크기를 볼 때 같이 봐야 할 것

  • 주석 비율. 위 출력에서 email은 코드 7,764줄에 주석 1,035줄로 13% 수준이었다. 주석이 극단적으로 적은 큰 파일은 읽는 비용이 줄 수 이상이다.
  • 파일 수. 같은 줄 수라도 파일이 33개로 흩어진 것과 1개인 것은 탐색 비용이 다르다.
  • 가장 큰 파일 하나의 크기. 평균이 아니라 최댓값이 병목이다. 한 파일이 3,000줄이면 그 파일이 곧 그 모듈이다.
  • 테스트 코드 제외 여부. 테스트를 포함해 세면 크기가 부풀지만, 인수인계 관점에서는 테스트도 읽어야 할 자산이다. 두 값을 따로 기록하는 편이 낫다.
  • 생성 코드 제외. 파서 생성기 산출물처럼 사람이 읽지 않는 파일은 빼야 한다. 안 빼면 지표가 무의미해진다.

참고로 오래 유지되는 프로젝트 중에는 주석 비율을 아예 공개 지표로 내거는 경우도 있다. SQLite 문서는 자기 소스가 35% 이상이 주석이라고 명시하고, 그것을 장기 지원 근거의 하나로 든다. 주석 비율이 높다고 좋은 코드라는 뜻은 아니지만, 넘겨받을 사람을 상수로 놓고 쓴 코드라는 신호는 된다.

3. 의존성이 수명을 정한다 - 내가 안 건드려도 남이 바꾼다

코드가 깨지는 이유의 상당 부분은 내가 만든 것이 아니다. 내가 아무것도 안 해도 남이 바꾸면 깨진다. 그래서 의존성 수는 기능의 편의성을 재는 숫자가 아니라 외부에 노출된 면적을 재는 숫자다.

문제는 대부분이 이 숫자를 직접 선언한 개수로 센다는 것이다. 실제 면적은 그것보다 훨씬 넓다. 설치하지 않고 트리만 해결해서 재 봤다.

$ cat package.json
{"name":"probe","version":"1.0.0","dependencies":{"express":"4.21.2"}}

$ npm install --package-lock-only --no-audit --no-fund
up to date in 3s

$ node -e "const l=require('./package-lock.json');
           console.log(Object.keys(l.packages).filter(Boolean).length)"

이 표에서 어느 쪽이 낫다는 결론을 내면 안 된다. 트리가 큰 쪽은 그만큼 남이 만든 것을 재사용해 더 빨리 더 많은 일을 한다. 그 속도가 사업적으로 옳은 국면이 분명히 있다. 트리가 1인 쪽은 필요한 것을 직접 구현했다는 뜻이고, 그 구현과 그 버그를 자기가 평생 책임진다는 뜻이다. 둘은 같은 축의 양 끝이 아니라 서로 다른 비용을 선택한 것이다.

다만 수명이라는 축 하나만 놓고 보면 방향은 분명하다. 트리에 들어 있는 항목 하나하나가 각자의 릴리스 주기와 각자의 유지보수자를 가진다. 그중 하나라도 유지가 끊기거나 호환을 깨면 내 코드가 대응해야 한다. 내 코드의 안정성은 내가 통제하지 못하는 항목 수에 반비례한다.

3.1 잠금 파일이 없는 언어에서 재는 법

파이썬처럼 표준 라이브러리 안에서 임포트가 얽히는 경우에는 소스를 구문 분석해 폐포를 구해야 한다. 핵심은 홉 수를 제한하는 것이다.

def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels

이 측정에는 분명한 한계가 있다. 구문 분석은 함수 안이나 예외 처리 블록 안의 지연 임포트까지 전부 세기 때문에 실제 실행 시 필요한 것보다 많이 잡힌다. 그러니 이 값은 상한이다. 그래도 같은 잣대로 비교하는 용도로는 충분하다.

4. 범위를 좁게 잡는 것은 기능을 버리는 것이다

수명이 긴 소프트웨어를 보면 공통적으로 안 하는 일의 목록이 길다. 그런데 이 문장은 자주 오해된다. 「미니멀리즘이 좋다」로 읽히는데, 실제로 벌어지는 일은 기능 요청을 거절하는 노동이다.

구체적인 사례로 OpenBSD의 httpd(8)가 있다. man 페이지는 이것을 FastCGI와 TLS를 지원하는 HTTP 서버라고만 설명한다. 릴리스 노트를 보면 이 서버는 OpenBSD 5.6에서 처음 들어왔고, 같은 릴리스에서 Apache가 기반 시스템에서 제거됐다. 그 릴리스 날짜는 2014년 11월 1일이다.

여기서 한쪽이 우월하다는 결론으로 가면 틀린다. Apache HTTP Server 2.4의 모듈 색인에는 140개 안팎의 모듈이 실려 있다. 인증·권한, 프록시와 로드 밸런싱, 캐싱, 압축, URL 재작성, 로깅, TLS까지 각각 별도 모듈로 제공된다. 이 규모는 방만함이 아니라 설계 목표다. 운영자가 필요한 것만 골라 붙일 수 있고, 그 확장성 덕분에 수많은 환경이 여전히 그것을 쓴다. 좁은 범위로 만든 서버가 애초에 할 수 없는 일들이 그 목록 안에 있다.

그러니 정확한 표현은 이렇다. 범위를 좁히면 수명이 늘고, 대신 적용 범위가 줄어든다. 둘 다 대가다. 판단할 때 물어야 할 것은 「기능이 많은가」가 아니라 「이 기능이 없어서 못 쓰는 사람이 우리 조직에 있는가」다.

  • 기능을 넣지 않기로 하면 그 기능의 버그·문서·테스트·보안 대응이 통째로 사라진다. 절약되는 것은 코드 줄 수가 아니라 영구적인 유지 비용이다.
  • 대신 사용자가 직접 채워야 한다. 그 비용은 사라지지 않고 이동한다.
  • 범위를 문서에 글로 적어 두지 않으면 거절할 근거가 없다. 그래서 좁은 범위는 문서 없이 유지되지 않는다.
  • 확장점을 하나 만들어 두는 것과 기능을 전부 담는 것은 다르다. 경계 하나만 열어 두는 설계가 절충안이다.
  • 거절은 인기를 잃는다. 수명과 채택률은 자주 상충한다는 사실을 인정하고 선택해야 한다.

5. 문서가 코드와 같이 살아야 하는 이유

문서가 없는 코드는 넘겨받을 수 없다. 정확히는 넘겨받을 수는 있는데, 넘겨받은 사람이 원래 의도를 복원하지 못한다. 그래서 문서는 코드의 부속물이 아니라 인수인계 가능성 그 자체다.

이 부분에서 참고할 만한 관행이 있다. OpenBSD의 FAQ는 man 페이지에 대해 OpenBSD 정보의 권위 있는 출처이며 최신성과 정확성을 유지하는 데 상당한 노력을 들인다고 적는다. 더 중요한 문장은 그다음이다. 시스템을 바꾸는 개발자는 코드 변경과 함께 man 페이지도 갱신하도록 기대된다고 명시한다.

이 규칙의 실질은 문서를 잘 쓰자는 권고가 아니다. 문서를 코드 변경의 완료 조건에 넣은 것이다. 이렇게 하면 문서가 코드보다 뒤처지는 일이 구조적으로 줄어든다. 앞의 판별표에서 「문서와 코드가 같은 커밋에서 바뀐다」를 완성의 신호로 넣은 이유가 여기 있다.

5.1 문서를 1급으로 두기 위한 최소 장치

  • 문서를 코드와 같은 저장소에 둔다. 위키로 빼는 순간 갱신 주체가 분리되고, 분리되면 뒤처진다.
  • 공개 인터페이스를 바꾸는 변경은 문서 변경을 동반해야 통과되도록 리뷰 규칙에 넣는다.
  • 문서에 범위 선언을 적는다. 「이것은 하지 않는다」가 적혀 있어야 요청을 닫을 수 있다.
  • 예제는 실행 가능한 형태로 둔다. 실행되지 않는 예제는 시간이 지나면 전부 거짓말이 된다.
  • 버전별로 무엇이 바뀌었는지 사람이 읽을 수 있는 변경 이력을 남긴다. 커밋 로그는 대체재가 아니다.
  • 주석은 왜 이렇게 했는지를 적는다. 무엇을 하는지는 코드가 이미 말한다.

문서 분량이 곧 품질은 아니다. 다만 앞서 본 SQLite처럼 주석 비율을 공개 지표로 관리하거나, man 페이지 갱신을 개발자의 의무로 못 박는 프로젝트들이 공통적으로 오래 간다는 점은 눈여겨볼 만하다. 둘 다 사람이 바뀌는 것을 전제로 만든 장치다.

6. 호환성 약속 - 무엇을 안 바꾸겠다고 정할 것인가

사용자가 떠나는 이유는 기능이 부족해서보다 업그레이드가 아파서인 경우가 많다. 반대로 말하면, 무엇을 안 바꾸겠다고 못 박는 것이 사용자를 남기는 가장 강한 장치다.

이 약속을 극단까지 밀어붙인 사례로 SQLite가 있다. 공식 문서는 개발자들의 의도가 2050년까지 지원하는 것이라고 적고, C 언어 API와 디스크 상의 파일 포맷을 완전한 하위 호환으로 유지하겠다고 약속한다. 오늘 작성한 애플리케이션이 수십 년 뒤에 릴리스될 버전과도 링크되어 동작해야 한다는 문장까지 있다. 같은 문서는 데이터베이스 파일이 32비트와 64비트, 빅엔디언과 리틀엔디언에서 바이트 단위로 동일하다고 명시한다.

이 약속이 만들어 내는 효과는 두 갈래다.

  • 사용자 쪽: 업그레이드가 사건이 아니게 된다. 버전을 올리는 일이 코드 수정을 부르지 않으면 계속 쓰는 것이 기본값이 된다.
  • 개발자 쪽: 설계 자유도가 영구적으로 줄어든다. 한 번 공개한 인터페이스는 실수까지 포함해 안고 가야 한다.

그래서 호환성 약속은 공짜가 아니다. 자주 깨는 쪽에도 이유가 있다. 잘못된 설계를 빨리 버릴 수 있고, 그 덕에 더 나은 형태로 수렴하는 속도가 빠르다. 사용자 층이 얇고 변화가 빠른 영역에서는 그쪽이 합리적일 수 있다. 문제는 약속을 하지 않은 채 자주 깨는 것이다. 그러면 사용자는 매번 놀란다.

실무에서 옮겨 쓸 수 있는 형태로 정리하면 이렇다.

  • 무엇이 공개 인터페이스인지 문서에 적는다. 적히지 않은 것은 바꿔도 된다는 뜻이 된다.
  • 깨는 변경에는 예고 기간과 이행 경로를 함께 낸다. 둘 중 하나만 있으면 사용자는 못 따라온다.
  • 파일 포맷과 저장 스키마는 API보다 훨씬 오래 산다. 여기를 깨면 데이터가 인질이 된다.
  • 기본값 변경은 API 변경과 같은 무게로 다룬다. 시그니처가 그대로여도 동작이 바뀌면 깨진 것이다.
  • 호환을 유지할 수 없다면 이름을 바꾼다. 같은 이름으로 다른 물건을 내는 것이 가장 나쁘다.

7. 인수인계 - 유지보수자가 바뀌어도 이어지는 조건

20년 사는 소프트웨어에서 같은 사람이 20년 붙어 있는 경우는 드물다. 그러니 수명의 실질적인 조건은 열정이 아니라 교체 가능성이다. 흔히 버스 팩터라고 부르는 값을 낮추는 문제다.

재미있는 사례가 앞서 본 두 데몬에 있다. relayd(8)의 man 페이지 HISTORY 절을 보면 이 프로그램은 원래 hoststated라는 이름으로 OpenBSD 4.1에 처음 등장했고, 4.3에서 지금 이름으로 바뀌었다. AUTHORS 절에는 두 사람의 이름이 적혀 있다. 그리고 httpd(8)의 man 페이지는 이 서버가 relayd에서 파생됐다고 밝힌다. 이름이 바뀌고, 사람이 여럿이고, 한 프로그램의 코드가 다른 프로그램으로 갈라져 나간다. 이런 이동이 가능하려면 문서와 경계가 먼저 있어야 한다.

버스 팩터를 낮추는 장치는 추상적인 이야기가 아니라 실제 파일과 규칙이다.

  • 빌드가 한 명령으로 끝나야 한다. 「담당자 노트북에서만 빌드된다」가 가장 흔한 사망 원인이다.
  • 실행 환경을 코드로 적어 둔다. 필요한 런타임 버전과 외부 도구를 문서가 아니라 설정 파일에 박는다.
  • 테스트가 실패를 알려 준다. 인수인계받은 사람이 무언가 고쳤을 때 깨졌는지 스스로 알 방법이 없으면 손을 못 댄다.
  • 배포 절차가 문서에 있다. 코드보다 배포가 더 자주 잊힌다.
  • 결정 기록을 남긴다. 왜 이 구조를 골랐는지가 없으면 후임은 전부 다시 고민하거나, 이유 없이 갈아엎는다.
  • 연락처가 아니라 저장소가 권위를 갖는다. 「그건 누구한테 물어봐」로 유지되는 지식은 그 사람이 나가면 함께 나간다.
  • 이름을 바꿀 수 있어야 한다. 이름·소유자·호스팅이 특정 개인에게 묶여 있으면 이관 자체가 불가능해진다.

여기서 자주 놓치는 항목이 마지막 두 개다. 기술적으로 완벽해도 계정과 권한이 개인에게 묶여 있으면 그 소프트웨어의 수명은 그 계정의 수명과 같아진다. 도메인, 패키지 레지스트리 소유권, 서명 키가 전부 여기 해당한다.

8. 언제 다시 쓰는 게 맞나

지금까지의 이야기가 「오래된 것을 지켜라」로 읽히면 곤란하다. 오래됐다는 사실은 그 자체로 가치도 결함도 아니다. 재작성이 정당해지는 조건은 따로 있다.

앞서 본 사례가 여기서도 유용하다. OpenBSD 5.6은 기존에 있던 서버를 기반 시스템에서 빼고, 새로 만든 서버를 넣었다. 이것은 「오래된 것을 지킨다」의 반대 행동이다. 그러니 이 글의 주장은 보존이 아니라 판정이다.

상황판정근거
요구사항의 전제가 바뀌어 기존 구조로 표현 불가재작성기능 추가가 아니라 뼈대 불일치다
런타임·언어·핵심 라이브러리가 지원 종료재작성 또는 이식코드가 멀쩡해도 돌릴 곳이 없다
읽고 고칠 사람이 없고 문서로도 복원 불가재작성이해 비용이 재작성 비용을 넘었다
보안 결함이 구조에서 반복 발생재작성개별 패치로 수렴하지 않는다
최근 변경이 버그 수정과 외부 대응 위주유지잘 돌고 있다는 신호다
불만이 코드 스타일·기술 유행에 관한 것유지동작하는 것을 취향으로 바꾸는 비용
느리지만 병목이 특정됨부분 교체전면 재작성은 과잉이다

재작성을 결정했다면 하나만 더 지킬 것이 있다. 기존 코드가 왜 그렇게 생겼는지 먼저 복원하는 일이다. 이상하게 보이는 분기 하나가 실제 장애 대응의 흔적인 경우가 많다. 그 이유를 모르고 다시 쓰면 같은 장애를 다시 겪는다.

비용을 언제 회수하는지, 정리 작업을 투자로 어떻게 설명할지에 대한 계산은 이 글의 범위 밖이다. 그 부분은 리팩터링 비용은 언제 회수되나에서 별도로 다뤘다.

9. 사내 코드에 적용하기 - 무엇을 동결할 것인가

여기까지의 조건은 공개 프로젝트만의 이야기가 아니다. 사내 코드에 그대로 적용된다. 오히려 사내 코드가 더 절실하다. 공개 프로젝트는 유지보수자가 떠나면 포크라도 되지만, 사내 모듈은 담당자가 부서를 옮기면 그 자리에서 화석이 된다.

사내에서 실제로 해야 할 일은 「전부 최신으로 유지」가 아니다. 어떤 모듈을 완성으로 선언하고 동결할지 고르는 것이다. 동결은 방치와 다르다. 동결은 유지 비용을 예산에 명시적으로 넣는 결정이다.

점검 항목동결 가능동결 불가
기능 요구최근 4개 분기 신규 요구 없음분기마다 요구가 들어옴
계약 문서입출력 규격이 저장소 안에 있음담당자 머릿속에만 있음
자동 검사실패를 알려 주는 테스트가 돎수동 확인에 의존
외부 의존성해결된 트리가 손에 꼽는 수준트리가 수십 개 이상
크기담당자가 아닌 사람이 하루에 읽을 수준읽는 데만 며칠
장애 이력최근 1년 운영 장애 없음같은 원인이 반복
재검토 시점다음 검토 날짜가 박혀 있음정해진 시점이 없음

가상의 예를 들면 이렇다. 어떤 회사에 사번 형식 검증만 하는 모듈이 있다고 하자. 300줄이고, 외부 의존성이 없고, 규격이 사내 표준 문서로 적혀 있고, 테스트가 있고, 2년 동안 요구가 없었다. 이것은 동결 대상이다. 반대로 정산 배치는 규격이 매 분기 바뀌고 외부 결제사 응답 형식에 물려 있다. 크기가 작아도 동결 불가다. 판단 기준은 크기가 아니라 바깥이 얼마나 자주 움직이는가다.

동결을 선언할 때 같이 적어야 할 것들이 있다.

  • 동결의 의미를 정의한다. 기능 추가는 받지 않되 보안 패치와 런타임 상향은 계속한다는 식으로 범위를 적는다.
  • 재검토 날짜를 박는다. 조건 없는 동결은 방치와 구분되지 않는다.
  • 깨졌을 때 누가 받는지를 적는다. 사람 이름이 아니라 역할로 적어야 인사 이동을 견딘다.
  • 대체 계획의 트리거를 적는다. 「이 조건이 되면 재작성 검토」를 미리 정해 두면 논쟁이 짧아진다.
  • 동결 모듈 목록을 한곳에 모아 공개한다. 목록이 없으면 아무도 그것이 동결됐다는 사실을 모른다.

10. 수명을 재는 지표와 재는 방법

지금까지 나온 조건들을 정기적으로 잴 수 있는 형태로 정리한다. 감사 도구를 새로 사자는 이야기가 아니다. 세 가지 숫자면 대부분의 판단이 선다.

세 번째 지표인 변경 이유의 분포가 가장 중요하고, 동시에 가장 덜 쓰인다. 최근 변경이 기능 추가인지 바깥 대응인지에 따라 그 코드의 상태가 갈리기 때문이다. 실제로 재 봤다. 대상은 이 환경에 설치된 파이썬이 함께 배포하는 변경 이력 파일이다.

$ export PYTHONIOENCODING=utf-8
$ python news_entries.py NEWS.txt "3.13.2 final" | python classify_changes.py

reason     count   share
feature        8    8.8%
defect        58   63.7%
external       6    6.6%
doc            1    1.1%
chore          2    2.2%
other         16   17.6%

total         91

feature share : 8.8%  (n=91)
shape: maintenance only - freeze candidate
note: keyword rules; always eyeball the 'other' bucket before trusting this

같은 도구로 세 구간을 비교하면 지표가 실제로 작동한다는 것이 보인다. 아래는 파이썬 3.13.3과 함께 배포된 변경 이력 파일에서 세 개 구간을 각각 분류한 결과다.

개발 구간에서 27%였던 기능 비중이 유지 구간에서는 9~12%로 떨어진다. 같은 프로젝트, 같은 시기, 같은 사람들인데 변경의 성격이 다르다. 커밋 수만 보면 유지 구간은 「조용해졌다」로 보이지만, 실제로는 성격이 바뀐 것이다. 이것이 앞에서 말한 「죽었다와 완성됐다의 구분」을 숫자로 만든 형태다.

이 측정에는 정직하게 밝혀야 할 한계가 있다.

  • 키워드 분류다. 문장을 이해하는 것이 아니라 단어를 찾는다. 위 출력에서 other가 17.6%였는데, 이 구간은 사람이 직접 읽어야 한다.
  • 결함을 외부 대응보다 먼저 판정하도록 순서를 잡았다. 그래서 「특정 플랫폼에서 나는 버그 수정」이 결함으로 잡힌다. 즉 외부 대응 비율은 하한이다.
  • 변경 이력의 서술 관행에 따라 결과가 달라진다. 커밋 메시지 규칙이 있는 조직이라면 정확도가 훨씬 높아진다.
  • 한 구간만 보면 의미가 없다. 같은 프로젝트의 시간 변화로 봐야 한다.
  • 정규식 규칙은 조직마다 손봐야 한다. 규칙을 고칠 때는 정규식 테스트기로 표본 문장에 먼저 걸어 보는 편이 빠르다.

10.1 세 지표와 임계값

지표재는 방법대략의 해석
코드 크기주석·빈 줄 제외 코드 줄, 파일 수, 최대 파일 크기수백 줄이면 1인 인수인계 가능, 수천 줄이면 팀 단위
의존성 면적잠금 파일 항목 수, 또는 3홉 임포트 폐포전체 폐포는 포화되므로 홉 제한이 필수

주석 비율주석 줄 나누기 코드 줄절대 기준은 없고, 같은 저장소 내 추세로 본다
문서 지연문서 마지막 변경과 코드 마지막 변경의 시차시차가 길수록 인수인계 비용이 커진다
권한 집중도배포·서명·도메인 권한을 가진 사람 수1이면 그 사람이 곧 수명 상한

임계값은 절대적인 것이 아니다. 위에 적은 숫자는 이 글에서 실제로 잰 값들에서 유도한 출발점이며, 조직의 코드 성격에 맞게 옮겨야 한다. 중요한 것은 값 자체가 아니라 같은 잣대로 반복해서 재는 것이다. 한 번 잰 값은 판정에 못 쓰고, 두 번째부터 쓸모가 생긴다.

11. 확인하지 못한 것

이 글에서 확인하지 못했거나 확인할 수 없었던 것을 밝힌다. 나머지 서술과 같은 무게로 읽어 주기 바란다.

  • 출발점이 된 기사 원문을 열지 못했다. 그래서 그 글의 주장이나 표현은 인용하지 않았고, 주제만 가져와 1차 출처로 다시 조사했다.
  • 범위 축소가 명시적 의도였는지는 문서로 확인되지 않는다. 위에서 본 두 데몬의 man 페이지는 무엇을 하는지만 적을 뿐, 무엇을 하지 않는지를 선언하지 않는다. 「좁은 범위」는 문서에 적힌 기능 목록에서 추론한 것이지 프로젝트의 선언이 아니다.
  • OpenBSD의 공식 목표 문서 원문은 확인하지 않았다. FAQ가 별도 페이지로 연결한다는 것만 확인했다.
  • 장수 저장소의 커밋 로그로 변경 이유 분포를 돌리려던 계획은 실패했다. 이 실행 환경에서 저장소 복제가 차단됐다. 그래서 대신 로컬에 설치된 파이썬이 함께 배포하는 변경 이력 파일을 대상으로 삼았다. 커밋 단위가 아니라 릴리스 노트 항목 단위라는 점을 감안해야 한다.
  • 모듈 개수는 개략치다. Apache 2.4 모듈 색인의 정확한 총계는 세지 않았고, 색인 페이지에서 확인한 140개 안팎이라는 규모만 적었다.
  • 분류기의 미분류 구간을 전수 검토하지 않았다. 개발 구간에서 16.1%가 other로 남았다. 표본을 눈으로 훑어 보니 성능 개선과 동작 변경 서술이 많았는데, 전부 읽지는 않았다.
  • 임포트 폐포는 상한이다. 함수 안이나 예외 처리 블록 안의 지연 임포트를 구분하지 않는다. 실제 실행 경로에서 필요한 수는 이보다 적다.
  • 「크기가 작으면 오래 산다」를 통계적으로 검증한 자료는 찾지 못했다. 이 글이 제시하는 것은 인과의 증명이 아니라 지표의 정의와 측정 방법이다. 사례는 사례일 뿐이며, 반례가 있을 수 있다.
  • 측정은 한 시점, 한 환경의 값이다. 다른 버전이나 다른 운영체제에서 같은 스크립트를 돌리면 숫자가 달라질 수 있다.

결론: 오래 사는 것은 거절의 축적이다

처음 장면으로 돌아가자. 커밋이 3년째 없는 라이브러리를 쓸지 말지는, 커밋 그래프로 결정할 수 없다. 대신 세 가지를 재면 된다. 얼마나 큰가, 무엇에 매여 있는가, 마지막 변경들은 왜 일어났는가.

그 셋을 재고 나면 판단이 뒤집히는 경우가 많다. 조용한 저장소가 수백 줄에 의존성 하나, 최근 변경은 전부 런타임 대응이라면 그것은 죽은 것이 아니라 끝난 것이다. 반대로 커밋이 활발한데 트리에 수십 개가 딸려 오고 문서가 코드보다 두 버전 뒤라면, 활발함은 안정성이 아니라 남은 일의 양이다.

그리고 이 조건들은 만들 때부터 정해진다. 작게 유지하려면 기능을 거절해야 하고, 의존성을 줄이려면 편한 라이브러리를 거절해야 하고, 범위를 지키려면 사용자 요청을 거절해야 하고, 문서를 유지하려면 문서 없는 병합을 거절해야 한다. 수명은 무엇을 넣었느냐가 아니라 무엇을 넣지 않았느냐로 결정된다.

같은 원리가 사내 코드에도 그대로 적용된다. 다만 사내에서는 거절할 사람이 명확하지 않아서 조건이 잘 지켜지지 않는다. 그래서 필요한 것이 동결 선언이다. 어떤 모듈에 대해 「여기까지가 이 모듈의 일이고, 그 밖의 요구는 받지 않는다」를 문서로 적는 순간, 그 모듈은 관리 대상에서 빠지는 게 아니라 비로소 관리되기 시작한다. 방치와 동결을 가르는 것은 그 한 문장이다.

```python
import os, sys
SKIP = {".git", "__pycache__", "node_modules", ".venv", "build", "dist"}

def measure(root):
    files = code = blank = comment = size = 0
    targets = [root] if os.path.isfile(root) else []
    if not targets:
        for dirpath, dirnames, filenames in os.walk(root):
            dirnames[:] = [d for d in dirnames if d not in SKIP]
            targets += [os.path.join(dirpath, f) for f in filenames if f.endswith(".py")]
    for path in targets:
        files += 1
        size += os.path.getsize(path)
        for line in open(path, encoding="utf-8", errors="replace"):
            s = line.strip()
            if not s: blank += 1
            elif s.startswith("#"): comment += 1
            else: code += 1
    return files, code, comment, blank, size

for arg in sys.argv[1:]:
    print(os.path.basename(arg.rstrip("/\\")), measure(arg))
```

- [ ] 주석 줄 나누기 코드 줄 = 주석 비율

```python
def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels
```

- **전체 폐포는 쓰지 마라.** 포화돼서 변별력이 없다 (355줄 모듈과 11,165줄 모듈이 124와 180으로 수렴)

- 구문 분석은 함수 안 지연 임포트까지 세므로 이 값은 **상한**이다

`classify_changes.py` 핵심 규칙 (순서 중요)

```python
RULES = [
    ("defect",   r"(fix\w*|bug|crash\w*|leak\w*|regress\w*|cve|vulnerab\w*|"
                 r"overflow|incorrect\w*|correctly|properly|avoid\w*|prevent\w*|"
                 r"no longer|wrong\w*|fail\w*|hang\w*|deadlock)"),
    ("feature",  r"(add\w*|introduc\w*|implement\w*|new |now support\w*|"
                 r"support\w*|allow\w*|expose\w*|optimiz\w*|improv\w*)"),
    ("external", r"(update\w*|upgrade\w*|bump\w*|bundled|vendored|deprecat\w*|"
                 r"compat\w*|toolchain|compiler|installer|platform|portab\w*|"
                 r"windows|macos|android|freebsd|openssl|sqlite|zlib)"),
    ("doc",      r"(document\w*|docs?|docstring|comment\w*|typo|readme|man page)"),
    ("chore",    r"(refactor\w*|clean ?up|style|reformat|renam\w*|test\w*|"
                 r"remov\w*|drop\w*|release|version bump)"),
]
```

**읽는 법**

- `feature` 비중 **25% 이상** → 성장 중, 동결 금지
- `feature` 비중 **10~25%** → 혼합, 6개월 뒤 다시 잰다
- `feature` 비중 **10% 미만** → 유지 전용, **동결 후보**

**반드시 지킬 것**

- [ ] `other` 버킷을 **눈으로 읽었다** (실측에서 최대 17.6%가 여기 남았다)
- [ ] `defect`를 `external`보다 먼저 판정했다 → **외부 대응 비율은 하한**임을 알고 있다
- [ ] 한 구간이 아니라 **같은 프로젝트의 시간 변화**로 비교했다
- [ ] 정규식을 조직의 커밋 메시지 관행에 맞게 고쳤다

| 자동 검사 | 실패를 알려 주는 테스트가 돎 | 수동 확인 | |
| 외부 의존성 | 트리가 한 손에 꼽힘 | 수십 개 이상 | |
| 크기 | 비담당자가 하루에 읽음 | 읽는 데 며칠 | |
| 장애 이력 | 최근 1년 운영 장애 없음 | 같은 원인 반복 | |
| 바깥의 변동 | 외부 규격이 고정 | 외부가 분기마다 바뀜 | |
| 재검토 시점 | 날짜가 박혀 있음 | 정해진 시점 없음 | |

**판정 규칙**

- 8개 중 **7개 이상 「동결 가능」** → 동결 선언
- **4~6개** → 6개월 뒤 재점검, 그동안 문서와 테스트를 보강
- **3개 이하** → 동결 불가. 정상 유지 대상

**주의:** 크기가 작아도 **바깥이 자주 움직이면 동결 불가**다. 판단 기준은 크기가 아니라 외부 변동 빈도다.

## 7. 인수인계 점검 목록

**넘기기 전에 넘기는 쪽이 확인**

- [ ] 빌드가 **한 명령**으로 끝난다 (담당자 노트북 의존 없음)
- [ ] 필요한 런타임 버전·외부 도구가 **설정 파일에 박혀** 있다
- [ ] 테스트가 돌고, **실패했을 때 실패라고 말한다**
- [ ] 배포 절차가 문서에 있고, 문서대로 하면 배포된다
- [ ] 롤백 절차가 문서에 있다
- [ ] 왜 이 구조를 골랐는지 **결정 기록**이 남아 있다
- [ ] 이상하게 보이는 분기마다 **그렇게 된 이유**가 주석이나 이슈로 있다
- [ ] 문서가 코드와 같은 저장소에 있다
- [ ] 예제가 **실행 가능한 형태**다

**권한 — 여기가 가장 자주 빠진다**

- [ ] 저장소 관리 권한 보유자가 **2명 이상**
- [ ] 배포 권한 보유자가 2명 이상
- [ ] 패키지 레지스트리 소유권이 **개인 계정이 아니다**
- [ ] 서명 키의 보관 위치와 접근 방법이 문서에 있다
- [ ] 도메인·인증서 갱신 주체가 **역할로** 지정돼 있다
- [ ] 외부 서비스 계정이 공용 주소로 등록돼 있다

**넘겨받는 쪽이 확인**

- [ ] 문서만 보고 **처음부터 끝까지 한 번 빌드·배포**해 봤다
- [ ] 일부러 하나 깨뜨려 보고 **테스트가 잡는지** 확인했다
- [ ] 가장 큰 파일 하나를 **끝까지 읽었다**
- [ ] 최근 1년 이슈·장애를 훑고 반복 패턴을 찾았다
- [ ] 모르는 것을 **문서에 질문으로 남겼다** (사람에게 묻고 끝내지 않았다)
