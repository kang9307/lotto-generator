Gemini CLI 2026年6月18日停止服务 - Antigravity CLI迁移指南与D-day情景

距D-day约4周 - 从命令到CI/CD切换的一站式实战指南

2026年5月22日 IT/技术

引言: 6月18日 D-day - 谁会受到影响

2026年5月21日，Google通过官方博客宣布Gemini CLI将于2026年6月18日23:59 PT终止服务。换算为中文圈时间是6月19日下午14:59。同一时刻，去年秋季开始非公开测试的Antigravity CLI将转为免费GA，实际上成为Gemini CLI的后继者与替代品。hada.io一篇9分话题刚一上线就堆积了超过70条评论，可见中文圈开发者社区对影响范围也存在不少混乱，这是诚实的现状。本文是本人为自己团队迁移而整理的实战笔记，在可公开的范围内重新撰写。

先把谁会受影响讲清楚。受影响的群体有四类。第一，在本地安装gemini二进制作为日常编程助手的个人开发者。第二，在GitHub Actions或GitLab CI中嵌入gemini的团队。PR自动评审、提交消息生成、变更日志撰写等小型自动化中常见此模式。第三，在VS Code或JetBrains扩展后端调用gemini CLI实现部分自动化工具的副业项目作者。第四，在企业内网中通过CLI而非直接调用Vertex AI的团队。在中国大陆，部分集成商和外企内网环境中此模式意外地常见。

不受影响的群体同样明确。直接通过SDK(Python、Node.js、Go)或REST调用Vertex AI或Google AI Studio的代码原样运行。消失的不是模型本身，只是CLI表面。也就是说本次变化是"调用Gemini模型的方式"在表面上的变化，不是模型EOL。本文8步迁移中有过半基于此前提。核心计算逻辑无需改动，只需整理入口。最后说一下时间压力，撰文时距离D-day约27天。本人团队的计划是这个周末启动金丝雀环境迁移，5月最后一周做CI切换，6月第一周做生产切换，最后一周做监控与回滚预案整理。

Gemini CLI是什么 - 从发布到当下

为补充上下文，简要回顾。Gemini CLI是Google于2024年11月对应Anthropic的Claude Code发布的开源命令行工具。初期版本只是简单的对话补全封装。2025年上半年陆续加入工具调用、文件系统访问、Shell执行、多轮上下文管理。2025年9月v1.0稳定版发布后，它从简单助手晋升为正经的自主编程工具。彼时日活跃用户(DAU)估计约40万。在中文圈，伴随Vertex AI北京/上海可用区与香港/台北的部署而快速扩散，用户规模约为Claude Code的60%，Codex CLI的约1.4倍。

它究竟有何吸引力？本人日常使用约8个月，最强的感受是200万token上下文窗口与低廉价格的结合。能把巨大的Monorepo整体放入上下文进行提问，是与其他CLI工具显著拉开差距的地方。其次Google Workspace集成(把Drive、Docs、Sheets一行命令拉进上下文)，对Workspace为基础协作工具的中文圈初创公司带来了意外的便利。当然也有可批评之处。工具调用准确度比Claude Code 4.7低一档，长时自主任务中丢失自身上下文的频率更高。但仅凭"一次性看遍庞大代码库"这一优势，它就能存活下来。

主要命令体系简洁。gemini chat对话，gemini run "提示词"一次性执行，gemini edit 文件.py修改文件，gemini config管理配置。配置文件集中在~/.config/gemini/config.yaml一处，认证支持gemini auth login的OAuth流程，或直接通过环境变量GEMINI_API_KEY填API密钥这两种模式。这种简洁是巨大优势，但在Antigravity CLI中此模型变得更复杂一档。下一节会诚实地说明这一点。

为何停服 - 本人观点分析

Google官方公告表面上用了"为整合到下一代代理架构"这种常见营销文案。本人看到的真正原因有三。其一，Google CLI策略的整合。从2026年3月Antigravity公开起，事实上就没有同时维持两套CLI的意图。Antigravity以IDE表面(Antigravity Workspace)为先，但共享同一内核的CLI接口从一开始就并存，并在Beta阶段已经在渐进吸收Gemini CLI。这次6/18终止是该吸收的收尾。

其二，向代理工作流优先主义的转变。Gemini CLI的命令体系设计前提是"短发或短对话"范式。多轮虽可，但总让人觉得是"附加功能"。Antigravity CLI从一开始就把"长时间自主任务"作为基本单位来设计，命令、配置、输出格式都向这个方向优化。Anthropic的Claude Code在2025年验证了这一方向后，所有主要实验室都把自家CLI向同方向对齐，这是潮流的一部分。

其三，MCP时代工具表面的再设计。Anthropic在2024年末发起的Model Context Protocol，2026年上半年事实上成为业界标准。Gemini CLI的MCP支持从v0.9起加入，但不是深植内核的后置集成。Antigravity CLI从设计之初就把MCP作为一等公民，外接工具(GitHub、Notion、Linear以及你的企业内部工具)的体验显著更流畅。Google看来没有资源同时维持两者并让两者都很好地发展，所以选择了一边，这是本人的推测。

Antigravity CLI介绍 - 有何不同

Antigravity CLI不是简单改名。本人并行使用约一个月的结果，有意义的差异有五点。其一，命令动词变了。对应gemini chat的命令变为antigravity单独使用(无子命令)。gemini run变为antigravity task，gemini edit仍叫antigravity edit但行为有细微差别，并非同义词。

其二，配置文件位置与结构变了。从原来的~/.config/gemini/config.yaml单文件迁移到~/.config/antigravity/目录下，分为settings.json、profiles/、mcp_servers/三个子结构。乍看复杂，但在多项目环境下按profile分离配置在实务中更整洁。其三，认证模型转向OAuth优先。API密钥环境变量方式仍受支持，但默认流程统一为通过antigravity login命令走浏览器OAuth，令牌存入OS钥匙串(macOS Keychain、Windows Credential Manager、Linux secret-tool)。

其四，输出格式结构化了。Gemini CLI默认输出是纯文本，用--json标志取JSON。Antigravity CLI默认是人类友好的Markdown加旁路JSON元数据，可以用--format plain或--format json明确指定。这一变化是CI环境中需要重做解析器的最大单一原因，文末单独讨论。其五，把MCP服务器当作一等公民。antigravity mcp add <url>一行即可挂接外部工具服务器，挂接的工具在所有对话与任务中自动暴露。Gemini CLI若要用MCP必须创建单独的插件目录并每次显式加载，体验大不相同。

迁移指南 - 分步8步

按本人实际操作顺序展示。每一步末尾附上亲身遇到的陷阱。

步骤1: 备份当前环境

迁移第一条准则是"留好回滚之路"。用cp -r ~/.config/gemini ~/.config/gemini.bak.20260522整体复制配置目录，并通过gemini config show > ~/gemini_config_snapshot.txt留下当前生效配置的纯文本快照。在环境变量与shell rc文件(~/.bashrc、~/.zshrc，fish用户用~/.config/fish/config.fish)中找出所有以GEMINI_开头的变量并移至单独文件。陷阱: 本人首次操作时忽略了direnv按项目设置的.envrc里的GEMINI_API_KEY。请提前跑一遍grep -r GEMINI ~/Projects/。

步骤2: 安装Antigravity CLI

官方支持三种安装路径。macOS用brew install antigravity，Linux用官方安装脚本(curl -fsSL https://antigravity.google.dev/install.sh | sh)，Windows用winget(winget install Google.Antigravity)或直接下载。在中文圈环境下本人推荐的方式是macOS与Linux用Homebrew，Windows用Scoop或winget。若企业内网禁止外部脚本执行，可从GitHub Releases页面直接下载二进制放至/usr/local/bin/。安装完成后用antigravity --version确认GA版本(2026.06.18时为1.0.x系列)。陷阱: 与Gemini CLI可同时安装，这是有意为之的设计，便于在迁移期同时运行两者进行对比。

步骤3: 认证迁移

若选择保留API密钥方式，只需将GEMINI_API_KEY重命名为ANTIGRAVITY_API_KEY即可(同样的值可复用)。推荐切换至OAuth。执行antigravity login命令打开浏览器，用Google账号登录后令牌即保存至OS钥匙串。在CI/CD环境中OAuth不便，仍以API密钥方式为标准答案。陷阱: 企业Workspace账号与个人Gmail同时激活时，首次登录可能选错账号。请用antigravity login --account work显式打标签。

步骤4: 配置转换

好消息是Google提供了官方转换工具。一行antigravity migrate --from gemini就能把~/.config/gemini/config.yaml约80%的内容自动迁移到新结构。未转换的项目会以报告形式输出。按本人经验，转换遗漏主要在(1)自定义别名、(2)外部工具插件定义、(3)Workspace集成OAuth别名这三类。转换后用antigravity config show检查结果，手动补齐遗漏。陷阱: 不要原样保留转换工具生成的新settings.json，先打开并手动把模型默认值(可能保留为gemini-2.5-pro)更新为gemini-3.5-pro。

步骤5: 脚本兼容性验证

找出本地~/bin、~/.local/bin或项目scripts/目录中所有调用gemini命令的脚本。起点是grep -rn "gemini " ~/Projects/ scripts/ ~/bin/。对每个发现的脚本审查三点: (1)命令动词映射，(2)环境变量名称，(3)输出解析后处理。文末的批量转换sed脚本会自动处理80%，但输出解析必须由人复核。陷阱: 在反引号或$()中调用gemini并用jq解析输出的脚本几乎总要改，因为默认输出格式变了。

步骤6: 更新CI/CD流水线

最耗时的一步。无论GitHub Actions、GitLab CI、Jenkins还是CircleCI，都要更新三件事。(a)Docker基础镜像中安装gemini-cli的部分替换为antigravity。(b)Secrets名称映射(GEMINI_API_KEY → ANTIGRAVITY_API_KEY，或把OAuth令牌作为Secret注入)。(c)命令与输出解析逻辑更新。重要建议: 不要把此PR当作普通PR，先在单独分支跑一次金丝雀工作流通过后再合并。CI失败在6/18临近发现会变成恐慌。陷阱: 重新构建Docker镜像后，PR构建和main构建可能各自使用不同缓存镜像。请在缓存键中明确包含antigravity版本。

步骤7: 团队通知

技术迁移结束不等于事情结束。本人团队做了三件事: (a)在Slack或企业微信置顶D-day倒计时和迁移指南链接，(b)在企业wiki撰写一页"在我的环境如何迁移"的指南，(c)每周二开两次30分钟的Office Hours。最后一项效果出人意料地大，比看文档边上有人陪一起做要快5倍。陷阱: 编写指南者只假设自己的环境(macOS + zsh + Homebrew)时，Windows + PowerShell用户会卡住。至少要准备两种OS的截图。

步骤8: 监控(1周观察)

迁移后至少1周并行运行两个环境(或两个命令)对比输出质量。同一PR的自动代码评审在新工具上是否变短，使用token是否突然增加30%，这种变化会在头几天暴露。本人团队在CI中同时运行两个工具，把结果发到单独频道做观察者模式，跑7天后才移除Gemini CLI调用。陷阱: 跳过1周观察期会让你在6/18当天才首次发现问题。届时已无法回退到Gemini。

自动化工具 - 批量转换脚本示例

这是本人使用的sed批量转换脚本。只处理命令动词与环境变量名称，输出格式解析仍需人工复核。

#!/usr/bin/env bash
# migrate_gemini_to_antigravity.sh
# 用法: ./migrate_gemini_to_antigravity.sh <目录>
# 注意: 必须在git已提交状态下运行。

set -euo pipefail

TARGET_DIR="${1:-.}"

# 1. 命令动词映射
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" -o -name "Dockerfile" \) -print0 | \
  xargs -0 sed -i.bak \
    -e 's/\bgemini chat\b/antigravity/g' \
    -e 's/\bgemini run\b/antigravity task/g' \
    -e 's/\bgemini edit\b/antigravity edit/g' \
    -e 's/\bgemini config\b/antigravity config/g' \
    -e 's/\bgemini auth\b/antigravity auth/g'

# 2. 环境变量名称映射
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" -o -name ".env*" -o -name "Dockerfile" \) -print0 | \
  xargs -0 sed -i.bak \
    -e 's/GEMINI_API_KEY/ANTIGRAVITY_API_KEY/g' \
    -e 's/GEMINI_PROJECT_ID/ANTIGRAVITY_PROJECT_ID/g'

# 3. JSON标志映射
find "$TARGET_DIR" -type f \( -name "*.sh" -o -name "*.yml" -o -name "*.yaml" \) -print0 | \
  xargs -0 sed -i.bak -e 's/--json\b/--format json/g'

# 4. 清理备份文件
find "$TARGET_DIR" -name "*.bak" -delete

echo "[OK] 自动转换完成。请用git diff复核结果。"
echo "[注意] 输出解析(jq、awk)部分需手动检查。"

执行前务必确认已git提交状态，执行后必须用git diff复核结果。按本人经验，自动转换处理80%，剩下20%需要人手介入。

迁移时的6大常见陷阱

本人团队与周边团队亲历过的陷阱。

1)漏掉JSON schema微变更而导致解析器破裂。 Antigravity的--format json输出与Gemini CLI的--json输出大框架相同，但response.text变深至output.message.content[0].text，且usage键下的token计数字段名部分变了。jq表达式照搬会得到空值，是一种沉默失败。

2)试图把OAuth令牌原样塞入CI而失败。 Antigravity的OAuth令牌有效期短。CI中正确做法不是OAuth而是把API密钥作为Secret注入。部分团队把本地OAuth令牌原样塞到Secret中，首次过期后突然停摆。

3)中文输入处理的细微差异。 Gemini CLI在中文多字节输入下换行处理偶有别扭，Antigravity改善了这点。但作为结果，部分正则后处理会出现非预期匹配。如有处理简繁混合或全角符号输入的代码请单独检查。

4)模型自动选择与费用暴增。 Antigravity根据任务复杂度自动调用更大模型的选项默认开启。假设以前Gemini CLI显式指定--model gemini-2.5-pro，原样照搬会让相似任务路由到意外的大模型，月度费用可能上升。用antigravity config set routing.auto_upgrade false关闭，或至少打开监控。

5)Windows OS钥匙串警告。 在Windows Credential Manager中保存令牌时，部分公司安全策略会阻拦。此时可回退到API密钥环境变量方式，或与IT部门协商例外。

6)消失的插件。 Gemini CLI的插件系统在Antigravity中被废除，需重新打包为MCP服务器。自研插件的情况下这是最耗时的一块，4周日程中应最先动工。

中文圈开发者环境专属技巧

在中文圈工作时遇到的环境特异点如下。大型外企或国企内网常常拦截外部OAuth回调。若antigravity login挂起，请用antigravity login --device-code启用设备码流程。浏览器无需对外通信，只输入6位代码即可。中文输入方面Antigravity能自动合成拼音/全拼输入，但部分IME(如搜狗输入法、微软拼音)在多字节边界上偶有错位。PowerShell用户用chcp 65001切到UTF-8代码页基本可解决。

使用Vertex AI亚洲可用区的用户还需多确认一点。Antigravity CLI默认可用区是us-central1，必须用antigravity config set vertex.region asia-east1(台北)或asia-northeast3(首尔)等明确指定，否则API调用会路由到美国导致延迟增加。按本人实测，从亚洲到us-central1首token延迟均值约280ms，到asia-east1仅约65ms，相差4倍。因公司安全策略禁止对外LLM调用的环境中，需结合Vertex AI Private Endpoint与Antigravity的endpoint覆盖选项。此配置需与信息安全部协商，本人团队约花了2周完成。

最后是计费与发票。用Google Workspace企业账号支付的Gemini用户，账单会自动迁移到同账号下的Antigravity用量，无需额外注册付款方式。但发票项目名从"Gemini API"变为"Antigravity API"，未在企业财务系统提前登记项目名时，6月发票会被归为未分类导致审批延迟。请提前与财务团队沟通。

D-day之后的情景 - 6月19日早晨会发生什么

假设你已完成迁移，想象一下6月19日的早晨。上午8点，中文圈时间6月19日凌晨已过去几小时，Gemini CLI的API响应已经全部返回401。打开Slack或飞书，可以看到(未迁移的)某些团队的CI失败警报正在刷屏。如果你的团队不在那种状态，此刻最大的风险是未准备好的外部依赖。你的代码调用的某个内部服务若内部仍在用Gemini CLI，那个服务一停，你的代码也会跟着挂。

上午10点，企业ChatOps机器人停止PR自动评审。本人团队已切到Antigravity，但若公司其他团队的机器人仍在调用Gemini，那机器人挂了，本团队PR也会无自动评审等待合并。提前知会其他团队D-day的价值此刻显现。下午2点，Hacker News和hada.io上"Gemini CLI消失的第一天"的回顾文陆续出现。看到本团队稳定运行带来一丝安心。

到6月25日的一周，Antigravity首次token使用量结算，能看到迁移后第一份账单的变化。本人估计同等工作量下通常会有10至20%的费用下降，但若未关闭自动模型升级选项，反而可能上升。基于这一变化在6月底整理最终费用报告并关闭迁移项目。核心是让D-day不真的成为D-day。对准备充分的团队而言，6月19日只是普通的星期四早晨。

结论 + 立即可做的3件事

本次变化的本质不是"一个工具换成了另一个工具"。这是Google CLI策略整合、MCP基础代理范式在所有主要实验室晋升为一等公民的信号。Gemini CLI用户被强制迁移，其他用户最终也会被这个方向拉过去。本人推测OpenAI也很可能在年内把Codex CLI做类似的方向再校准。届时若你的技术栈已经按MCP基础整理好，下一次变化会平滑得多。

距离D-day约4周，本人立即建议你做的三件事如下。第一，本周内在你的笔记本上装好Antigravity CLI并实际用30分钟。手感是后续所有决策的起点。第二，跑一遍grep -rn "gemini" ~/Projects/把你代码的依赖表面绘成一张地图。看不见就搬不走。第三，若有团队，把下周二的30分钟迁移Office Hours加到日历上。无论文档写得多好，旁边有人陪同走一遍快5倍。本周把这三件做完，D-day就只是普通的星期四。
