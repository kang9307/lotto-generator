Code as Agent Harness — 将代码视为AI智能体执行基础的新视角

UIUC、Meta与Stanford 102页综述揭示的范式：代码不是成果物，而是构建智能体推理、行动与验证的Harness执行基础

2026-06-26 开发/基础设施

引言：代码的角色被颠覆了

过去几年，我们谈论AI与代码的方式遵循着固定模式：LLM接收提示，生成代码作为输出。输入提示得到函数，描述错误得到修复补丁。在这个框架里，代码始终是结果产物。

2026年5月，UIUC、Meta和Stanford联合研究团队在arXiv发布的102页综述（arXiv: 2605.18747）正面颠覆了这幅图景。综述提出的核心命题简洁明了：「在新兴智能体系统中，代码不再只是生成目标，而是越来越多地作为智能体推理、行动、环境建模和执行验证的运营基础（operational substrate）。」

本文基于综述内容，以独立视角解析这一转变的含义、重要性及其实践影响。截至2026年6月，这份综述是对智能体AI发展方向最系统的梳理之一。

1. 范式转变：代码是基础，不是输出

实际构建过智能体系统的人，凭直觉就能感受到这一点：LLM的文本输出本身什么都做不了。要在真实环境中执行，必须被包裹在可执行结构中。那个包裹的结构，就是综述所说的Harness（哈内斯）。

综述将代码在智能体系统中扮演的角色归纳为三点：

  • 使推理可执行（Reasoning Executable）：代码将模型内部推理外化为可验证的计算。外部解释器、符号求解器和执行追踪检查并精炼中间步骤。
  • 使行动可编程（Action Programmable）：代码将高层意图转换为具体的可执行操作——工具调用、机器人策略、GUI命令——通过结构化可执行接口使意图落地为行动。
  • 使环境状态可检查（Environment State Inspectable）：代码通过仓库、模拟器、测试和执行日志表示世界状态、转换动态和反馈信号，供智能体执行、编辑和查询。

当这三者咬合运转时，智能体不再只是文本生成器，而是与环境形成闭合循环的系统。代码是那个循环的骨架。

2. Harness解剖：三层结构

综述将智能体Harness分解为三个相互连接的层次。理解这个结构，有助于厘清现代智能体系统为何被设计成现在的形态。

2.1 Harness接口层 — 代码连接智能体与环境的方式

第一层是代码如何在推理、行动和环境建模中充当接口。智能体感知世界并将认知转化为行动的节点在此。核心组件包括：告诉智能体该做什么的指南（如AGENTS.md文件），以及告诉智能体哪里出错的传感器（类型检查器、代码检查工具、测试运行器）。

值得注意的是，Claude Code的CLAUDE.md和OpenAI的AGENTS.md已在生产环境中履行这一指南角色。这些结构化指令文档作为Harness的一部分，在运行时约束和引导智能体行为——它们是行动约束，不是文档说明。

2.2 Harness机制层 — 支撑长期执行的引擎

第二层涵盖使Harness实际运转的机制。综述提出四个要素：

  • 规划（Planning）：通过线性、结构引导、搜索或编排策略分解长期任务。
  • 记忆（Memory）：维护工作状态、语义知识、经验记录和共享交互历史。
  • 工具使用（Tool Use）：将智能体连接到API、验证系统和执行环境。
  • 控制与优化（Control & Optimization）：通过运行时反馈迭代修复和自适应的「计划-执行-验证」循环。

「计划-执行-验证」循环尤为重要。智能体不只是生成输出，而是执行输出、检查结果、决定下一步行动。代码构建了这整个循环。没有代码作为Harness，循环无法闭合。

2.3 Harness扩展层 — 从单智能体到多智能体

第三层解决如何将Harness扩展到多智能体设置。当多个智能体（管理者、编码者、审查者、测试者）分工协作时，共享代码制品成为协调的基础。智能体参照同一仓库、共享同一测试结果、基于相同状态行动。代码成为智能体间的通信媒介和共享真相的单一来源。

3. 优秀Harness的四个属性

综述明确了智能体Harness必须具备的四个属性，可视为Harness设计的需求规范。

属性含义实践示例
可执行性（Executable）意图结果可被形式化验证测试运行器、代码解释器
可检查性（Inspectable）结构化追踪暴露中间计算执行日志、逐步追踪
有状态性（Stateful）持续表示任务进度状态仓库状态、记忆结构
可治理性（Governed）执行权限边界与安全约束工具权限限制、沙箱执行

这四个属性相互依存。没有可执行性，验证无从进行；没有有状态性，长期任务无法持续；没有可治理性，意外行为无法拦截。可信赖的智能体系统需要四者协同运转。

4. Harness工程的崛起：「智能体 = 模型 + Harness」

2026年，Harness工程作为一门学科迅速兴起。公式很简单：智能体 = 模型 + Harness。如果模型是大脑，Harness就是大脑运作的身体和环境。

传统思维是「用更好的模型，得到更好的智能体」。Harness工程对此发起挑战。即使模型权重固定，通过演进Harness——系统提示、工具定义、中间件、验证循环、记忆结构——也能大幅提升智能体性能。

实证支持真实存在。Agentic Harness Engineering（AHE）研究在固定基础模型的情况下，仅通过观察驱动的Harness演进，在Terminal-Bench 2上达到84.7%。将GPT-5.4经过10轮迭代从69.7%提升至77.0%。Harness改进可以替代或补充模型升级。

特别值得关注的是Harness的可移植性：设计良好的Harness在更换底层模型时大多能保持行为一致。这是降低特定模型供应商依赖度的结构性手段——投资Harness，系统逐渐具备模型无关性。

5. 代码的新含义：工具定义、AGENTS.md、执行追踪

从Harness视角看，「代码」的范围远比通常认为的更广。综述将代码定义为「可执行或机器可验证的制品」，包含：

  • 程序、脚本、形式规范
  • 证明脚本、API模式、工具定义
  • 测试、仓库、模拟器、配置文件
  • 执行追踪、日志等代码相邻制品
  • AGENTS.md等指南文档

工具定义出现在列表中。告诉智能体可用工具及使用方式的模式本身，就是Harness的核心组成。综述引用的2025年实证研究揭示了这有多重要：工具数量107个时出现非线性性能断崖，10个工具时成功完成的任务在107个工具环境下实际失败。Harness设计中的工具整理（tool hygiene）是性能的核心变量。

AGENTS.md等指南文档同等重要。它们不是说明文档，而是智能体在运行时读取并据此决定行为方式的可执行约束。这些文件与系统提示一起作为「用户内容」组装传递给智能体——是Harness不可或缺的组成部分。

6. 长期执行与Harness的角色

长期执行（long-horizon execution）仍是智能体AI中最难解决的问题之一。单轮任务表现可以令人印象深刻，但跨越数十步骤进行规划、执行、反思并保持目标的智能体仍然脆弱。

Harness提供了结构性解决方案。记忆结构防止智能体在长任务中迷失方向；规划层将任务分解为可执行单元；验证循环确认中间结果并在必要时修正路径。当这三者以代码形式嵌入Harness时，智能体能够在推进过程中结构性地自我修正。

关键在于验证的位置。验证不是事后由人工检查最终输出的过程，而是内嵌在执行循环中的一道门——测试不通过则停止前进。这就是代码Harness提供自我修正能力的核心所在。

7. 多智能体系统与共享代码基础

超越单智能体，多智能体协作系统对Harness的需求更为迫切。当管理者、编码者、审查者和测试智能体分工协作时，协调它们的不只是自然语言消息，还需要共享仓库状态、公共测试套件和统一工具定义作为结构性协调基础。

这就是综述所说的「共享代码制品」。在多智能体系统中，维持一致状态要求所有智能体基于同一代码基础行动。否则，一个智能体的修改被另一个覆盖，或各自在相互矛盾的假设上行动。代码成为分布式智能体活动中的单一真相来源。

8. 尚待解决的挑战

综述诚实地列出六项开放挑战，指向下一阶段的研究议程：

  1. 超越最终成功的评估：衡量Harness中间步骤可靠性的指标仍然缺乏。
  2. 不完整反馈下的验证：在没有完整预言机的情况下如何评估语义正确性。
  3. 无回归的Harness演进：如何在改进Harness时不降低现有能力。
  4. 多智能体共享状态一致性：如何在多智能体并发修改环境中保证事务语义。
  5. 安全关键任务中的人类监督：如何将责任制编码为可执行的Harness状态。
  6. 多模态扩展：如何将代码Harness接口扩展到视觉、机器人和感知领域。

9. 实践启示

9.1 先设计Harness，再选择模型

构建智能体系统时，最常见的第一个问题是「用哪个模型」。Harness视角要求颠倒这个顺序：先确定智能体能访问哪些工具、有哪些验证循环、采用什么记忆结构，再选择适合该Harness的模型。同一模型在不同Harness中会成为完全不同的智能体。

9.2 将AGENTS.md和工具定义当代码管理

AGENTS.md、系统提示和工具定义不是说明文档，而是决定智能体行为的可执行规范。需要版本控制、测试和评审流程。整个团队必须认识到：Harness代码变更即智能体行为变更，与修改源代码同等重要。

9.3 关注工具质量而非数量

工具数量107个时出现非线性性能下降的实证与直觉相悖。更多工具并不意味着更强的智能体——选项过多反而让智能体迷失。定义清晰的少量工具持续优于模糊的大量工具。工具整理（tool hygiene）是Harness设计中的核心性能变量。

结论：Harness工程师是智能体时代的基础设施设计者

Code as Agent Harness综述描绘的世界，不是代码地位提升的世界，而是代码角色改变的世界。在智能体生成代码的时代，包裹和支撑这些代码生成智能体的结构本身也由代码构成。代码既是产物，又是基础。

Harness工程作为一门规律的兴起，是这一变化落入实践的形态。智能体系统性能不由模型单独决定，包裹模型的Harness——工具定义、指南文档、验证循环、记忆结构、权限边界——共同决定之。设计和演进这个Harness，就是智能体时代的基础设施工程。

截至2026年6月，智能体AI仍在快速演进。但这份综述提供的框架，是读懂这一演进方向的可靠指南针。代码如何编写固然重要，但代码包裹着什么，同样至关重要。
