기본 인자에 빈 리스트를 뒀더니 호출마다 값이 쌓인다 - 파이썬 기본값이 계산되는 시점

「None을 쓰세요」에서 멈추지 않고, 왜 이 설계가 이렇게 되어 있는지까지

2026-07-31 개발/인프라

서론: 두 번째 호출부터 결과에 남의 데이터가 섞여 있었다

주문을 하나씩 받아 목록에 담아 돌려주는 함수가 있었다. 테스트는 통과했고 첫 번째 요청도 정상이었다. 그런데 두 번째 요청의 응답에 첫 번째 요청의 주문 번호가 그대로 남아 있었다. 세 번째 요청에는 앞의 두 개가 다 들어 있었다. 데이터베이스를 뒤져도 이상이 없고, 전역 변수를 찾아도 없고, 캐시 계층은 애초에 붙이지 않았다.

범인은 함수 시그니처 한 줄이었다. 인자에 기본값으로 빈 리스트를 적어 둔 것이다. 이 함정은 널리 알려져 있고, 검색하면 「None을 쓰세요」라는 답이 3초 만에 나온다. 그런데 그 처방만 외우면 같은 원인에서 나오는 나머지 두 가지 증상을 영원히 못 알아본다.

이 글의 축은 처방이 아니라 원인이다. 원인은 딱 한 문장이다.

기본값 표현식은 def 문을 실행할 때 딱 한 번 계산되고, 그 결과 객체가 함수에 붙어 산다.

「호출할 때마다 새로 만들어지겠지」라는 직관이 틀린 것이지, 리스트가 가변이라는 것이 원인은 아니다. 가변성은 그 사실을 눈에 보이게 만드는 조건일 뿐이다. 이 구분이 왜 중요한지는 아래 세 증상을 나란히 놓으면 드러난다.

  • 증상 A. 빈 리스트 기본값에 호출할 때마다 값이 쌓인다 → 원인: 정의 시점 1회 평가
  • 증상 B. 기본값에 넣은 「오늘 날짜」가 며칠이 지나도 그대로다 → 원인: 정의 시점 1회 평가
  • 증상 C. 클래스 본문에 둔 리스트가 모든 인스턴스에서 공유된다 → 원인: 클래스 본문 1회 실행

겉모습이 전혀 다른 세 가지가 사실 같은 얼굴이다. B는 불변 타입에서 일어나므로 「가변이라서」로는 설명이 되지 않는다. 그래서 이 글은 처방 앞에 원인을 먼저 세운다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 돌린 결과다. 인터프리터는 Python 3.13.3 (tags/v3.13.3:6280bb5, 2025-04-08) [MSC v.1943 64 bit (AMD64)], 플랫폼 식별자는 win32다. 모든 스크립트는 파일로 저장해 실행했다. 들여쓰기가 의미를 갖는 언어를 셸 인자나 히어독으로 넘기면 조용히 변형된다.

이 글이 다루지 않는 것. 파이썬 문법 일반과 입문 내용은 파이썬 자동화 입문 연재에 있다. 이 글은 기본 인자의 평가 시점 한 점만 끝까지 파고든다. 실행에 쓴 예제 코드는 전부 가상의 것이다.

1. 재현 - 세 번 호출하면 세 번 다 다르다

가장 짧은 형태로 만들었다. 이름을 받아 바구니에 담고 바구니를 돌려주는 함수다. 바구니를 안 넘기면 빈 바구니로 시작한다 - 라고 읽히지만 그렇지 않다.

python 3.13.3 / win32

--- 1-1. three calls, one function ---
call 1 -> ['apple']
call 2 -> ['apple', 'banana']
call 3 -> ['apple', 'banana', 'cherry']

--- 1-2. two unrelated callers share one list ---
order_a = ['A-1001', 'B-2002']
order_b = ['A-1001', 'B-2002']
order_a is order_b : True

1-1은 교과서적인 재현이다. 세 번의 호출이 각각 다른 결과를 돌려줬고, 뒤로 갈수록 앞의 것이 남아 있다. 함수는 매번 「빈 바구니에 하나 담기」를 한 것처럼 보이지만 실제로는 「같은 바구니에 계속 담기」를 했다.

1-2가 실무에서 실제로 아픈 쪽이다. 서로 아무 관계도 없는 두 호출자가 같은 객체를 받았다. order_a is order_b가 참이라는 것은 둘이 같은 리스트를 가리키는 다른 이름이라는 뜻이다. 웹 요청 두 개가 이런 함수를 지나가면 한 사용자의 데이터가 다른 사용자의 응답에 섞인다. 서론의 증상이 정확히 이것이다.

  • 첫 번째 호출은 항상 정상이다. 그래서 단위 테스트가 함수를 한 번만 부르면 절대 안 걸린다
  • 테스트 순서를 바꾸면 결과가 달라진다. 「우리 테스트는 순서에 의존한다」는 신고의 상당수가 이 형태다
  • 프로세스를 재시작하면 증상이 사라진다. 그래서 「재시작하니 되던데요」로 종결되고 다시 재발한다
  • 예외가 나지 않는다. 로그에 흔적이 없고 오류율 지표도 움직이지 않는다

2. 기본값은 어디에 있나 - 그 객체를 직접 꺼내 본다

추측 대신 물건을 꺼내 보자. 함수 객체에는 기본값을 담아 두는 자리가 있다.

--- 1-3. the default object itself ---
add_item.__defaults__      : (['apple', 'banana', 'cherry'],)
type of default[0]         : list
len of default[0]          : 3

--- 1-4. identity across calls ---
id(default) before call    : 1997832273600
id(returned) call 1        : 1997832273600  same: True
id(returned) call 2        : 1997832273600  same: True
id(default) after 2 calls  : 1997832273600
r1 is r2                   : True

--- 1-5. mutating through the returned reference ---
probe.__defaults__         : (['touched from outside'],)
a caller that never passed anything now sees : ['touched from outside']

1-3이 결정적이다. 세 번의 호출이 끝난 뒤 함수의 기본값을 들여다보니 그 안에 세 개가 들어 있었다. 「빈 리스트」라고 적어 둔 자리에 데이터가 쌓여 있다. 함수는 정말로 자기 기본값을 고치고 있었던 것이다.

1-4는 그 이유를 못 박는다. 호출하기 전 기본값의 주소와, 호출이 돌려준 객체의 주소가 완전히 같다. 두 번째 호출도 마찬가지다. 새로 만드는 것이 아니라 같은 하나를 계속 넘겨준다.

1-5는 이 구조의 가장 불쾌한 면이다. 함수가 돌려준 리스트를 호출자가 바깥에서 고쳤더니 함수의 기본값이 바뀌었다. 그 뒤로 인자를 생략한 모든 호출자가 남이 심어 둔 값을 보게 된다. 함수 안쪽 코드를 아무리 읽어도 이 경로는 보이지 않는다.

진단 요령. 원인 모를 상태 오염을 만났을 때 가장 먼저 할 일은 의심되는 함수의 기본값을 그대로 찍어 보는 것이다. 거기에 비어 있어야 할 자리에 데이터가 있으면 진단이 끝난다. 전역 변수를 뒤지고 캐시를 의심하기 전에 이것부터 본다. 이 확인은 한 줄이면 되고 프로세스를 멈출 필요도 없다.

3. 언제 계산되는가 - def 문이 실행될 때, 딱 한 번

이제 원인을 직접 관측한다. 기본값 자리에 부수 효과가 있는 함수 호출을 넣으면 그것이 몇 번 실행되는지 눈으로 셀 수 있다.

--- 2-1. the default expression runs at def time, not call time ---
about to execute the def statement
    [side effect] make_default() ran
def statement finished
now calling f() three times:
make_default ran exactly once, before any call

순서를 잘 보자. 기본값을 만드는 호출이 def 문 안쪽에서, 함수를 한 번도 부르기 전에 실행됐다. 그 뒤 함수를 세 번 불렀는데 그 호출은 다시 일어나지 않았다.

여기서 흔한 오해 하나가 정리된다. def는 「함수를 선언하는 표시」가 아니라 실행되는 문장이다. 파이썬이 그 줄에 도달하면 기본값 표현식들을 왼쪽부터 계산하고, 그 결과를 담은 함수 객체를 만들어 이름에 묶는다. 기본값 계산은 함수 본문이 아니라 def 문 자체의 일이다.

--- 2-2. defaults are attached to the function object ---
g.__defaults__        : (1, [])
g.__kwdefaults__      : {'d': 2, 'e': {}}
g.__code__.co_varnames: ('a', 'b', 'c', 'd', 'e')

--- 2-3. the default is writable state ---
before : (1, [])
after  : (99, ['patched'])
g('x') : ('x', 99, ['patched'], 2, {})

2-2는 저장 구조를 보여준다. 위치 인자의 기본값과 키워드 전용 인자의 기본값이 서로 다른 자리에 들어간다. 앞의 것은 튜플, 뒤의 것은 딕셔너리다. 점검 스크립트를 직접 짤 때 이 둘을 모두 봐야 누락이 없다.

2-3은 이것이 읽기 전용 메타데이터가 아니라 쓸 수 있는 상태임을 보여준다. 바깥에서 기본값을 통째로 바꿔 넣었더니 이후 호출의 동작이 달라졌다. 함수 객체는 코드와 데이터를 함께 들고 다니는 물건이고, 기본값은 그 데이터 쪽에 속한다.

  • 기본값은 정의하는 쪽의 스코프에서 계산된다. 나중에 그 이름이 가리키는 값을 바꿔도 이미 계산된 기본값은 따라오지 않는다
  • 기본값 표현식은 왼쪽에서 오른쪽으로 계산된다. 앞 인자의 기본값을 뒤 인자의 기본값 표현식에서 참조할 수 없다
  • 데코레이터를 씌워도 이 계산은 이미 끝난 뒤다. 데코레이터는 만들어진 함수 객체를 받는다
  • 모듈을 임포트하는 순간 이 계산이 일어난다. 즉 기본값의 나이는 프로세스의 나이다

4. 시간이 굳는다 - 기본값에 넣은 오늘 날짜

여기서부터가 이 글의 값어치다. 위 원리를 알면 가변 타입과 아무 상관 없는 두 번째 증상이 예측된다. 기본값 자리에 「지금 시각」을 계산하는 호출을 넣어 봤다.

--- 3-1. today captured in a default never moves ---
bad  ('row0', '2026-07-31 05:25:19.168606')
good ('row0', '2026-07-31 05:25:19.569502')
bad  ('row1', '2026-07-31 05:25:19.168606')
good ('row1', '2026-07-31 05:25:19.969964')
bad  ('row2', '2026-07-31 05:25:19.168606')
good ('row2', '2026-07-31 05:25:20.370294')

--- 3-2. the frozen value, straight from __defaults__ ---
stamp_bad.__defaults__ : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
same object 0.5s later : (datetime.datetime(2026, 7, 31, 5, 25, 19, 168606),)
id stays the same      : 2480663196656
datetime.now() right now: 2026-07-31 05:25:20.870691

세 번의 호출 사이에 각각 0.4초씩 쉬었다. 올바른 쪽(good)은 마이크로초까지 매번 달라졌는데, 기본값에 넣은 쪽(bad)은 세 번 모두 완전히 같은 시각이다. 시스템 시각은 건드리지 않았다. 값이 갱신되지 않을 뿐이다.

3-2가 그 이유를 못 박는다. 함수의 기본값을 0.5초 간격으로 두 번 찍었는데 같은 객체가 같은 값으로 그대로 있었다. 그 사이 실제 시각은 계속 흐르고 있었다. 마지막 줄이 그것을 보여준다.

--- 3-3. a date default: the day the module was imported ---
captured end date      : 2026-07-31
report_range.__defaults__: (7, datetime.date(2026, 7, 31))
date.today() now       : 2026-07-31
note: date is IMMUTABLE, yet the value is still stale
      the bug here is not mutation, it is one-time evaluation

--- 3-4. the same shape with a counter ---
{'id': 1, 'payload': 'first'}
{'id': 1, 'payload': 'second'}
{'id': 1, 'payload': 'third'}
_seq module counter    : 1   (next_id ran exactly once)

3-3의 주석이 이 절의 핵심이다. 날짜 객체는 명백히 불변인데도 값이 낡았다. 아무도 그 객체를 고치지 않았다. 그저 임포트하던 순간의 날짜가 그대로 박혀 있을 뿐이다. 「가변이라서 생기는 문제」라는 설명으로는 이 출력을 해석할 수 없다.

이 증상이 실무에서 무서운 이유는 발현까지 시간이 걸린다는 점이다. 배포한 날에는 완벽하게 동작한다. 며칠 뒤 새벽에 「보고서 기간이 이상하다」는 신고가 들어오고, 담당자가 서버를 재시작하면 멀쩡해진다. 그러고는 며칠 뒤 다시 어긋난다. 재시작 주기가 짧은 환경일수록 발견이 늦다.

3-4는 같은 형태를 일련번호로 바꾼 것이다. 세 개의 행을 만들었는데 번호가 전부 1이다. 번호 생성기는 임포트할 때 한 번 돌았고 그 결과가 기본값으로 굳었다. 모듈 카운터가 1에서 멈춰 있는 것이 증거다.

  • 기본값 자리에 괄호가 보이면 일단 의심한다. 호출식은 그 자리에서 한 번 실행되고 결과만 남는다
  • 시각, 난수, 고유 식별자, 설정 파일 읽기, 접속 객체 생성 - 전부 같은 함정에 걸린다
  • 「기본값으로 현재 접속을 쓴다」는 형태는 특히 위험하다. 프로세스가 사는 내내 첫 접속 하나를 재사용하게 된다
  • 증상이 배포 직후가 아니라 한참 뒤에 나타나므로, 원인 지목이 엉뚱한 곳으로 간다

5. 어떤 타입이 위험한가 - 그리고 그 구분의 한계

가운데 열에 규칙성이 있다. 해시가 안 되는 것은 전부 제자리 변경이 되고, 해시가 되는 것은 전부 안 된다. 이것이 우연이 아니라는 근거가 표준 라이브러리 안에 있다. 데이터클래스는 가변 기본값을 금지하는데, 그 판정에 해시 불가능성을 가변성의 근사치로 쓴다고 문서에 적혀 있다. 즉 hash(기본값)이 예외를 내면 그 기본값은 위험하다는 것이 표준 라이브러리와 같은 판정 기준이다.

int, float, str, bytes가능불가없음리터럴이면 안전
tuple, frozenset가능불가원소가 가변이면 샌다내용물을 확인할 것
None가능불가없음권장 기본값
date, datetime, Decimal가능불가값이 굳는다호출식이면 쓰지 말 것

이 표에서 가장 중요한 칸은 「사용자 정의 클래스 인스턴스」 행이다. 해시 판정으로 걸러지지 않는데 위험은 그대로다. 그래서 해시 규칙은 편리한 근사치일 뿐 완전한 판정이 아니다. 다음 출력이 「불변이면 안전하다」는 명제를 정확히 어디까지만 참으로 만드는지 보여준다.

--- 4-2. proof: the immutable default is REBOUND, not changed ---
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump  id-in=140731345413000 id-out=140731345413032  same=False value=1
bump.__defaults__ : (0,)  <- never moved

grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1]
grow  id-in=2415089405120 id-out=2415089405120  same=True  value=[1, 1, 1]
grow.__defaults__ : ([1, 1, 1],)  <- grew every call

두 함수는 소스가 거의 똑같다. 하나는 정수 기본값에 1을 더하고, 하나는 리스트 기본값에 원소 하나를 더한다. 그런데 결과가 정반대다.

  • 정수 쪽: 연산 전후로 주소가 달라졌다. 더하기 결과가 새 객체가 되어 지역 이름에 다시 묶였고, 함수의 기본값은 0 그대로다. 그래서 세 번 호출해도 매번 1이 나온다
  • 리스트 쪽: 연산 전후로 주소가 같다. 원소를 붙이는 연산이 그 객체 자체를 고쳤고, 함수의 기본값이 함께 자랐다
  • 같은 모양의 문법이 타입에 따라 재바인딩이 되기도 하고 제자리 수정이 되기도 한다. 이것이 두 증상을 갈라 놓는 실제 메커니즘이다
  • 정리하면 불변 기본값은 「상태가 새지 않는다」까지만 보장한다. 「값이 최신이다」는 전혀 보장하지 않는다
--- 4-3. tuple default holding a mutable member ---
call 1 -> (['x'], {})
call 2 -> (['x', 'x'], {})
call 3 -> (['x', 'x', 'x'], {})
the tuple itself never changed; its member did

--- 4-4. immutable default, still evaluated once ---
seeded.__defaults__ : (6,)
value is fixed at def time even though int is immutable
so 'immutable = safe' is only half true:
  mutable   -> shared state leaks between calls
  immutable -> value is frozen at import time

4-3이 표의 「원소가 가변이면 샌다」 칸을 증명한다. 튜플을 기본값으로 썼는데도 값이 쌓였다. 튜플 자체는 한 번도 바뀌지 않았다. 그 안에 든 리스트가 자란 것이다. 불변 컨테이너는 자기 자신만 지키지 내용물까지 지키지 않는다.

4-4는 3절과 5절을 잇는다. 정수 기본값을 계산식으로 써 놨더니 그 값은 정의 시점에 확정됐다. 정수는 불변이라 새는 문제는 없지만 「한 번만 계산된다」는 성질은 그대로 적용된다. 위험의 종류가 다를 뿐 원인은 하나다.

6. 올바른 관용구 - None 파수꾼과 그 주변의 함정

처방은 간단하다. 기본값 자리에는 불변의 표식만 두고, 실제 객체는 함수 안에서 만든다. 실행으로 누적이 사라지는 것을 확인했다.

--- 5-1. the None sentinel idiom ---
call 1 -> ['apple']
call 2 -> ['banana']
call 3 -> ['cherry']
add_item.__defaults__ : (None,)

--- 5-2. caller-supplied container still works ---
passed in  -> ['seed', 'apple']
passed in  -> ['seed', 'apple', 'banana']
caller list: ['seed', 'apple', 'banana']  (caller owns it, as intended)

1절의 같은 함수가 이제 세 번 다 하나짜리 리스트를 돌려준다. 함수의 기본값은 None 하나뿐이고, 리스트 생성은 함수 본문 안에서 호출마다 새로 일어난다.

5-2가 중요하다. 이 처방은 호출자가 직접 컨테이너를 넘기는 경우를 망가뜨리지 않는다. 넘겨준 리스트는 그대로 쓰이고 호출자 쪽에서도 결과가 보인다. 이것은 버그가 아니라 호출자가 자기 물건을 넘겼으니 당연한 동작이다.

--- 5-3. why 'or' is not the same as 'is None' ---
arg=[]      or-> ['a', 'DEFAULT']        is-None-> ['a']
arg=['x']   or-> ['a', 'x']              is-None-> ['a', 'x']
arg=None    or-> ['a', 'DEFAULT']        is-None-> ['a', 'DEFAULT']

--- 5-4. when None is a legitimate argument value ---
lookup('a')            : 1
lookup('b')            : None
lookup('z', None)      : None
lookup('z')            : KeyError 'z'

5-3은 흔히 쓰는 축약형이 왜 등가가 아닌지 보여준다. 첫 줄이 갈린다. 호출자가 빈 리스트를 명시적으로 넘겼는데, 한쪽은 그것을 존중했고 다른 쪽은 기본값으로 갈아치웠다. 빈 컨테이너와 0과 빈 문자열이 모두 거짓으로 평가되기 때문이다.

이 어긋남은 예외를 내지 않는다. 「필터를 비워 보냈는데 전체가 나온다」 같은 신고로 며칠 뒤에 돌아온다. 파수꾼 검사에는 반드시 동일성 비교를 쓴다.

5-4는 처방 자체의 한계를 다룬다. None이 정상적인 인자 값일 수 있는 함수라면 그것을 파수꾼으로 쓸 수 없다. 출력에서 「값이 없어 예외」인 경우와 「값으로 None을 받은」 경우가 정확히 갈렸다. 모듈 안에 전용 표식 객체를 하나 만들어 그것과 비교하면 된다.

--- 5-5. copying a caller's list so you do not own their data ---
r1 tags : ['urgent', 'processed']
r2 tags : ['urgent', 'processed']
caller  : ['urgent']  (untouched)

--- 5-6. frozen empty containers as a read-only default ---
render('a')            : a({})
render('b', {'x': 1})  : b({'x': 1})
writing to the default : TypeError 'mappingproxy' object does not support item assignment

5-5는 한 걸음 더 나간 형태다. 호출자가 넘긴 리스트를 함수가 말없이 고치지 않도록 복사해서 쓴다. 출력에서 두 번의 호출이 서로 간섭하지 않았고 호출자의 원본도 그대로다. 「호출자의 물건을 함수가 바꿔도 되는가」는 별개의 설계 결정이고, 대개 답은 「안 된다」이다.

5-6은 「빈 매핑」을 기본값으로 두고 싶을 때의 안전한 형태다. 읽기 전용 뷰를 기본값에 두면 실수로 고치려는 순간 예외가 난다. 고칠 수 없는 것을 공유하는 것은 안전하다. 공유 자체가 문제가 아니라 공유된 것을 고치는 것이 문제였음을 이 출력이 다시 확인해 준다.

7. 같은 원인의 다른 얼굴 - 클래스 본문의 가변 속성

세 번째 증상이다. 서론에서 예고한 대로 같은 원인이 전혀 다른 자리에서 나타난다. 클래스 본문에 리스트를 하나 뒀다.

--- 6-1. a mutable attribute in the class body ---
a.items : ['apple', 'banana']
b.items : ['apple', 'banana']
a.items is b.items      : True
Cart.items              : ['apple', 'banana']
id(Cart.items)          : 1409693232192
id(a.items)             : 1409693232192
'items' in a.__dict__   : False

--- 6-2. the fix: build it in __init__ ---
c.items : ['apple']
d.items : ['banana']
c.items is d.items      : False
'items' in c.__dict__   : True

서로 다른 인스턴스 두 개를 만들어 각각 하나씩 담았는데 둘 다 두 개를 갖고 있다. 마지막 줄이 정체를 드러낸다. 인스턴스에는 그 이름이 아예 없다. 속성을 읽을 때 인스턴스에 없으면 클래스로 올라가 찾기 때문에, 모든 인스턴스가 클래스에 붙은 하나를 보고 있었다.

구조가 기본 인자와 완전히 같다. 클래스 본문도 클래스를 정의할 때 한 번 실행되고, 거기서 만들어진 객체가 클래스에 붙어 산다. 6-2의 처방도 같다. 인스턴스를 만들 때 새로 만들면 각자 자기 것을 갖는다.

--- 6-3. rebinding vs mutating on a class attribute ---
p.hits : 2   q.hits : 1   Counter.hits : 0
p.log  : [1, 2, 1]
q.log  : [1, 2, 1]
the int looks per-instance because += REBINDS onto the instance
the list is shared because append MUTATES the class-level object

--- 6-4. dataclasses refuse the same shape ---
dataclass with list default : ValueError mutable default <class 'list'> for field items is not allowed: use default_factory
Good() g1.items : ['x']
Good() g2.items : []
g1.items is g2.items : False

--- 6-5. plain functions get no such protection ---
plain() -> ['x']
plain() -> ['x', 'x']
no error, no warning: dataclasses check, the interpreter does not

6-3이 이 절에서 가장 헷갈리는 현상을 설명한다. 같은 클래스 안에서 정수 속성은 인스턴스별로 따로 세어지는데 리스트 속성은 공유된다. 코드는 나란히 붙어 있고 문법도 비슷하다.

  • 정수에 대한 더하기 대입은 새 값을 계산해 인스턴스에 다시 묶는다. 그래서 인스턴스마다 자기 값이 생기고 클래스 쪽은 0 그대로다
  • 리스트에 원소를 붙이는 것은 클래스에 붙어 있는 그 객체를 직접 고친다. 새로 묶는 일이 없으므로 모두가 같은 것을 본다
  • 4-2에서 본 재바인딩 대 제자리 수정의 대비가 여기서 그대로 반복된다. 함수와 클래스는 다른 문법이지만 같은 규칙 위에 서 있다
  • 그래서 「클래스 변수는 공유된다」는 설명은 절반만 맞다. 공유되는 것은 객체이고, 재바인딩하면 공유가 끊긴다

6-4에서 표준 라이브러리가 이 문제를 어떻게 다루는지 나온다. 데이터클래스는 가변 기본값을 아예 거부하고 예외를 낸다. 오류 메시지가 대안까지 알려준다. 공장 함수를 지정하면 인스턴스마다 새로 만들어져 두 인스턴스의 리스트가 서로 다른 객체가 됐다.

6-5가 이 글에서 가장 서늘한 부분이다. 일반 함수에는 그런 보호가 전혀 없다. 완전히 같은 형태의 코드가 아무 경고 없이 통과한다. 데이터클래스가 막아 주는 것을 함수는 막아 주지 않는다. 그래서 검출을 스스로 붙여야 한다.

8. 검출 - 인터프리터는 아무 말도 하지 않는다

먼저 인터프리터가 무엇을 해 주는지 확인했다. 답은 「아무것도」다. 그리고 이 환경에는 전용 정적 분석 도구가 하나도 설치돼 있지 않았다. 그래서 표준 라이브러리만으로 스캐너를 직접 만들어 돌렸다.

$ python find_mutable_defaults.py sample_app.py
sample_app.py

  L11   MUTABLE  index(table=...)             dict literal {}
  L16   MUTABLE  dedupe(seen=...)             factory call set()
  L21   MUTABLE  buckets(store=...)           factory call defaultdict()
  L26   CALL     stamp(at=...)                time-like call now() frozen at import
  L30   CALL     window(size=...)             computed expression evaluated once at def time

구문 트리를 훑어 기본값 자리의 노드 종류를 보는 방식이다. 일곱 건이 걸렸고 종료 코드가 1이라 그대로 CI에 붙일 수 있다. 주목할 것은 분류다.

  • MUTABLE - 리스트·딕셔너리·집합 리터럴과 컴프리헨션, 그리고 알려진 공장 호출. 상태가 새는 쪽이다
  • CALL - 기본값 자리의 모든 호출식과 계산식. 값이 굳는 쪽이고, 4절에서 본 대로 불변 타입도 여기 걸린다
  • CLASSATTR - 클래스 본문의 가변 속성. 같은 원인이므로 같은 도구가 잡는다
  • 안전하게 쓴 함수들과 __init__ 안에서 만드는 형태는 한 건도 오탐이 없었다

이미 돌아가는 프로세스를 점검할 때는 다른 방법이 더 확실하다. 함수 객체의 기본값을 실행 중에 직접 훑는 것이다.

--- 7-1. scanning a live module for mutable defaults ---
function               parameter    type       current value

--- 7-2. the same scan AFTER the code has run ---
function               parameter    type       current value
------------------------------------------------------------------------
enqueue                queue        list       ['job-1', 'job-2']
index                  table        dict       {'alpha': 1}
dedupe                 seen         set        {'x'}
buckets                store        defaultdict defaultdict(<class 'list'>, {})
Worker.seen            <class attr> list       []
the defaults now carry leftover data from earlier calls

두 표를 비교하는 것이 요령이다. 임포트 직후에는 전부 비어 있었다. 몇 번 호출한 뒤 같은 스캔을 돌렸더니 기본값 안에 이전 호출이 남긴 데이터가 그대로 앉아 있다. 이것이 상태 누출을 눈으로 확인하는 가장 짧은 방법이다.

운영 중인 서비스에 이 스캔을 붙여 두면 「지금 이 순간 얼마나 새고 있는지」를 잴 수 있다. 정적 분석은 소스가 있어야 하지만 이 방법은 남이 만든 라이브러리에도 그대로 통한다.

--- 7-3. what the interpreter itself will and will not tell you ---

py_compile result                       : OK, no diagnostic

--- 7-4. grep-level heuristic (works anywhere, noisy) ---

  L11   def index(word, table={}):

misses multi-line signatures and factory calls -> use the AST scanner

7-3이 이 절의 결론이다. 문제 있는 함수를 컴파일해도 경고가 0건이고, 바이트코드 컴파일도 아무 진단 없이 통과한다. 언어 차원의 안전망이 없다는 뜻이다. 이 결함이 수십 년째 살아남은 이유가 여기에 있다.

7-4는 도구를 못 쓰는 환경의 최후 수단이다. 정규식으로도 세 건은 잡았다. 다만 공장 호출과 여러 줄로 나뉜 시그니처를 놓쳤다. 급할 때 쓰고, 상시 검사는 구문 트리 쪽으로 옮긴다.

9. 의도적으로 쓰는 경우 - 기본값을 캐시로

이 동작을 알고 이용하는 용법이 있다. 호출 사이에 상태가 남는다는 성질을 그대로 써서 계산 결과를 캐시하는 것이다. 실제로 동작한다.

--- 8-1. the deliberate version: a default used as a cache ---
fib(60)      : 1548008755920
elapsed      : 0.000050 s
cache size   : 61
cache leaks into introspection: fib.__defaults__[0][10] = 55

--- 8-2. a caller can overwrite the cache from outside ---
fib(10) normal            : 55
fib(10, {0: 0, 1: 100})   : 5500
fib(10) again             : 55
the parameter is part of the public signature; nothing hides it

8-1은 이 기법이 실제로 빠르다는 것을 보여준다. 재귀 계산이 사실상 즉시 끝났다. 그러나 캐시가 함수의 기본값 자리에 그대로 노출된다. 마지막 줄에서 내부 캐시의 값을 바깥에서 꺼내 읽었다.

8-2가 이 방식을 권하지 않는 첫 번째 이유다. 캐시가 공개 시그니처의 일부이므로 호출자가 다른 것을 넘길 수 있다. 엉뚱한 초기값을 넘겼더니 결과가 완전히 달라졌다. 숨긴 것이 아니라 그냥 아무도 안 쓸 거라고 가정한 파라미터일 뿐이다.

두 번째 이유는 동시성이다. 여덟 개의 스레드가 같은 기본값 딕셔너리에 읽고-고치고-쓰기를 반복하게 했다. 16만 번을 더했는데 9만 9천여 번만 남았고 6만 번이 사라졌다.

여기서 중요한 관측이 하나 더 있다. 기본 설정 그대로 돌렸을 때는 소실이 0건이었다. 스레드 전환 간격을 기본값에서 훨씬 작게 낮췄더니 그제야 드러났다. 이것이 이 유형의 버그가 무서운 이유다. 테스트 장비에서는 한 번도 재현되지 않다가 부하가 걸린 운영 장비에서 처음 나타난다. 「우리 환경에서는 문제없다」는 결론이 실은 「아직 못 봤다」였던 것이다.

8-4가 대안이다. 표준 라이브러리의 캐시 데코레이터를 쓰면 속도는 사실상 같고 부족했던 것들이 전부 채워진다.

  • 시그니처가 깨끗하다. 감싸인 원본 함수의 기본값이 아예 없다. 캐시가 파라미터로 새 나오지 않는다
  • 상한이 있다. 기본값 캐시는 절대 비워지지 않고 무한히 자라지만 이쪽은 최대 크기를 정한다
  • 관측할 수 있다. 적중과 실패, 현재 크기를 그대로 읽을 수 있다. 캐시 효율을 지표로 낼 수 있다
  • 비울 수 있다. 무효화 수단이 있다. 8-3에서 본 「절대 안 비워짐」이 여기서 해결된다

8-5는 상태를 아예 숨기고 싶을 때의 형태다. 함수를 만들어 주는 함수 안에 상태를 두면 호출자가 손댈 수 없고 인스턴스마다 독립적이다. 두 개를 만들어 각각 세어 보니 서로 간섭하지 않았다. 기본 인자를 캐시로 쓰는 이유가 「상태를 어딘가 두고 싶다」였다면, 그 자리는 시그니처가 아니라 클로저다.

11. 체크리스트

코드 리뷰에서 그대로 쓸 수 있게 정리했다.

  • 시그니처에 =[], ={}, =set()이 하나도 없다
  • =defaultdict(...), =Counter(), =deque() 같은 공장 호출이 없다
  • 기본값 자리에 호출식이 없다 - 시각, 난수, 고유 식별자, 설정 읽기, 접속 생성
  • 기본값 자리에 계산식이 없다 - 임포트 시점에 굳는다
  • 튜플 기본값을 쓴다면 안에 가변 원소가 없는지 확인했다
  • 파수꾼 검사에 or가 아니라 is None을 썼다
  • None이 정상 값일 수 있는 인자에는 전용 표식 객체를 만들어 썼다
  • 호출자가 넘긴 컨테이너를 함수가 말없이 고치지 않는다 (필요하면 복사)
  • 클래스 본문에 리스트·딕셔너리·집합 속성이 없다
  • 데이터클래스 필드는 공장 함수로 지정했다
  • 캐시가 필요하면 기본 인자가 아니라 표준 캐시 데코레이터나 클로저를 쓴다
  • 구문 트리 스캐너를 CI에 붙여 새로 들어오는 것을 막는다
  • 장기 실행 프로세스는 실행 중 기본값 스캔으로 잔여 상태를 점검한다
  • 동시성 관련 검증은 스레드 전환 간격을 낮춘 상태로도 돌려 본다

# 파이썬 기본 인자 — 정의 시점 평가 점검표

> 출처: braindetox.kr — 기본 인자에 빈 리스트를 뒀더니 호출마다 값이 쌓인다
> 근거: Windows 10 Pro (10.0.19045) / Python 3.13.3 (MSC v.1943, 64bit) 실행 검증
> 이 파일을 AI에 그대로 붙여 「이 기준으로 우리 코드베이스를 점검해줘」라고 쓰면 됩니다.

## 0. 대전제 — 한 문장

**기본값 표현식은 def 문을 실행할 때 딱 한 번 계산되고, 그 결과 객체가 함수에 붙어 산다.**

호출할 때마다 다시 계산되지 않는다. 이 한 문장이 아래 세 가지 증상의 공통 원인이다.

| 증상 | 겉보기 원인 | 실제 원인 |
|---|---|---|
| 빈 리스트 기본값에 값이 쌓임 | 「리스트가 가변이라서」 | 정의 시점 1회 평가 |
| 기본값의 오늘 날짜가 안 바뀜 | 「날짜 캐싱 버그」 | 정의 시점 1회 평가 |
| 클래스 속성이 인스턴스 간 공유됨 | 「클래스 변수라서」 | 클래스 본문 1회 실행 |

## 1. 재현 — 3줄로 확인

```python
def add_item(name, basket=[]):
    basket.append(name)
    return basket

print(add_item("apple"))    # ['apple']
print(add_item("banana"))   # ['apple', 'banana']
print(add_item("cherry"))   # ['apple', 'banana', 'cherry']

print(add_item.__defaults__)
# (['apple', 'banana', 'cherry'],)
```

기본값은 `함수.__defaults__` 튜플에 들어 있다. 호출 전후로 `id()` 가 같다.
키워드 전용 인자의 기본값은 `함수.__kwdefaults__` 에 들어 있다.

## 2. 위험 타입 판단표 (실행으로 가른 결과)

| 기본값 타입 | 해시 가능 | 제자리 변경 | 판단 |
|---|---|---|---|
| `list` | 불가 | 가능 | **호출 간 상태 누출** |
| `dict` | 불가 | 가능 | **호출 간 상태 누출** |
| `set` | 불가 | 가능 | **호출 간 상태 누출** |
| `bytearray` | 불가 | 가능 | **호출 간 상태 누출** |
| `defaultdict` · `Counter` · `deque` | 불가 | 가능 | **호출 간 상태 누출** |
| `int` · `float` | 가능 | 불가 | 누출 없음 |
| `str` · `bytes` | 가능 | 불가 | 누출 없음 |
| `tuple` · `frozenset` | 가능 | 불가 | 누출 없음 (원소가 가변이면 예외) |
| `None` | 가능 | 불가 | 누출 없음 — **권장 기본값** |
| `date` · `datetime` · `Decimal` | 가능 | 불가 | 누출은 없으나 **값이 굳는다** |

**판정 규칙**: `hash(기본값)` 이 `TypeError` 를 내면 그 기본값은 위험하다.
표준 라이브러리의 데이터클래스도 같은 방법으로 판정한다 — 해시 불가를 가변의 근사치로 쓴다.

**단, 불변이라고 안전한 것이 아니다.** 불변 기본값은 값이 누출되지 않을 뿐,
**정의 시점에 굳는다.** 아래가 그 형태다.

```python
from datetime import datetime

def stamp(label, when=datetime.now()):   # 나쁨: 임포트 순간이 영원히 박힌다
    return label, when

def stamp(label, when=None):             # 좋음: 호출마다 새로 읽는다
    if when is None:
        when = datetime.now()
    return label, when
```

**호출 표현식이 기본값 자리에 있으면 타입과 무관하게 의심한다.**

```python
# 표준형 — None 파수꾼
def add_item(name, basket=None):
    if basket is None:
        basket = []
    basket.append(name)
    return basket

# 호출자 데이터를 소유하지 않으려면 복사한다
def tag_all(rows, tags=None):
    tags = list(tags) if tags is not None else []
    tags.append("processed")
    return {"rows": rows, "tags": tags}

# None 자체가 정상 인자 값일 때는 전용 파수꾼을 만든다
_MISSING = object()

def lookup(key, fallback=_MISSING):
    table = {"a": 1, "b": None}
    if key in table:
        return table[key]
    if fallback is _MISSING:
        raise KeyError(key)
    return fallback

# 읽기 전용 매핑을 기본값으로 두는 방법
from types import MappingProxyType
_EMPTY = MappingProxyType({})

def render(name, opts=_EMPTY):
    return name, dict(opts)
```

### `or` 를 쓰면 안 되는 이유

```python
extra = extra or ["DEFAULT"]     # 나쁨: 빈 리스트를 기본값으로 갈아치운다
if extra is None:                # 좋음: None 만 걸러낸다
    extra = ["DEFAULT"]
```

빈 리스트·빈 딕셔너리·`0`·빈 문자열은 모두 거짓이다.
호출자가 「비어 있음」을 의도적으로 넘겼는데 기본값으로 되돌아간다.

### 클래스·데이터클래스

```python
class Cart:
    items = []                # 나쁨: 모든 인스턴스가 하나를 공유

class Cart:
    def __init__(self, items=None):
        self.items = [] if items is None else list(items)   # 좋음

from dataclasses import dataclass, field

@dataclass
class Good:
    items: list = field(default_factory=list)   # 좋음
```

데이터클래스는 가변 기본값을 `ValueError` 로 거부한다. **일반 함수는 아무 경고도 하지 않는다.**

## 4. 검출

전용 린터가 설치돼 있지 않은 환경이면 표준 라이브러리 `ast` 로 직접 훑는다.

```python
# find_mutable_defaults.py — 표준 라이브러리만 사용
import ast, os, sys

FACTORIES = {"list", "dict", "set", "bytearray", "defaultdict",
             "OrderedDict", "Counter", "deque"}

def describe(node):
    if isinstance(node, (ast.List, ast.Dict, ast.Set)):
        return "MUTABLE", "가변 리터럴"
    if isinstance(node, (ast.ListComp, ast.DictComp, ast.SetComp)):
        return "MUTABLE", "컴프리헨션"
    if isinstance(node, ast.Call):
        f = node.func
        name = f.id if isinstance(f, ast.Name) else getattr(f, "attr", "")
        if name in FACTORIES:
            return "MUTABLE", "팩토리 호출"
        return "CALL", "정의 시점 1회 평가되는 호출"
    if isinstance(node, ast.BinOp):
        return "CALL", "정의 시점 1회 평가되는 계산식"
    return None, None

def scan(path):
    tree = ast.parse(open(path, encoding="utf-8").read(), filename=path)
    for node in ast.walk(tree):
        if isinstance(node, ast.ClassDef):
            for stmt in node.body:
                value = getattr(stmt, "value", None)
                if value is not None and describe(value)[0] == "MUTABLE":
                    print(path, stmt.lineno, "CLASSATTR", node.name)
        if not isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.Lambda)):
            continue
        a = node.args
        pos = a.posonlyargs + a.args
        pairs = list(zip(pos[len(pos) - len(a.defaults):], a.defaults)) if a.defaults else []
        pairs += [(k, d) for k, d in zip(a.kwonlyargs, a.kw_defaults) if d is not None]
        for arg, default in pairs:
            kind, why = describe(default)
            if kind:
                print(path, default.lineno, kind,
                      getattr(node, "name", "lambda"), arg.arg, why)

for target in sys.argv[1:] or ["."]:
    if os.path.isdir(target):
        for root, _d, files in os.walk(target):
            for f in files:
                if f.endswith(".py"):
                    scan(os.path.join(root, f))
    else:
        scan(target)
```

이미 돌아가는 프로세스를 점검할 때는 런타임 스캔이 더 확실하다.

```python
import inspect

MUTABLE = (list, dict, set, bytearray)

def scan_live(module):
    for name, obj in vars(module).items():
        if not inspect.isfunction(obj):
            continue
        for pname, p in inspect.signature(obj).parameters.items():
            if p.default is not inspect.Parameter.empty and isinstance(p.default, MUTABLE):
                print(name, pname, type(p.default).__name__, repr(p.default)[:40])
```

**운영 중에 이 스캔을 돌리면 기본값 안에 남은 이전 호출의 데이터가 그대로 보인다.**
그것이 곧 상태 누출의 증거다.

### 검출 수단 비교

| 수단 | 다중행 시그니처 | 팩토리 호출 | 클래스 속성 | 서드파티 코드 |
|---|---|---|---|---|
| 정규식 grep | 놓침 | 놓침 | 놓침 | 가능 |
| `ast` 스캐너 | 잡음 | 잡음 | 잡음 | 소스 있으면 가능 |
| 런타임 `__defaults__` 스캔 | 해당 없음 | 잡음 | 잡음 | **가능** |
| 인터프리터 자체 | — | — | — | **아무 경고 없음** |

## 5. 기본값을 캐시로 쓰는 경우 — 권하지 않는 이유

```python
def fib(n, _memo={0: 0, 1: 1}):     # 동작은 한다. 그러나
    if n not in _memo:
        _memo[n] = fib(n - 1, _memo) + fib(n - 2, _memo)
    return _memo[n]
```

- 캐시가 **공개 시그니처에 노출**된다. 호출자가 `fib(10, {0: 0, 1: 100})` 로 오염시킬 수 있다
- **절대 비워지지 않는다.** 상한도 무효화 수단도 없다
- **스레드 안전하지 않다.** 읽고-고치고-쓰는 구간이 갈라지면 갱신이 사라진다
- 문서화 도구와 타입 검사기가 이 인자를 진짜 파라미터로 취급한다

대안:

```python
from functools import lru_cache

@lru_cache(maxsize=128)
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib.cache_info()    # 적중·실패·현재 크기
fib.cache_clear()   # 비우기
```

상태를 숨기고 싶으면 클로저를 쓴다. 호출자가 손댈 수 없고 인스턴스마다 독립이다.

```python
def make_counter():
    tally = {}
    def bump(key):
        tally[key] = tally.get(key, 0) + 1
        return tally[key]
    return bump
```

## 6. 점검 목록

- [ ] 함수 시그니처에 `=[]`, `={}`, `=set()` 이 하나도 없다
- [ ] `=defaultdict(...)`, `=Counter()`, `=deque()` 같은 팩토리 호출이 없다
- [ ] 기본값 자리에 **호출 표현식**이 없다 (`datetime.now()`, `uuid4()`, `time()`)
- [ ] 기본값 자리에 **계산식**이 없다 (임포트 시점에 굳는다)
- [ ] `None` 검사에 `or` 대신 `is None` 을 썼다
- [ ] `None` 이 정상 값일 수 있는 인자는 전용 파수꾼 객체를 쓴다
- [ ] 호출자가 넘긴 컨테이너를 함수가 **말없이 변경하지 않는다** (필요하면 복사)
- [ ] 클래스 본문에 리스트·딕셔너리·집합 속성이 없다
- [ ] 데이터클래스 필드에 `field(default_factory=...)` 를 썼다
- [ ] 캐시가 필요하면 기본 인자가 아니라 `lru_cache` 나 클로저를 쓴다
- [ ] CI에 `ast` 스캐너나 린터를 붙여 새로 들어오는 것을 막는다
- [ ] 장기 실행 프로세스는 런타임 `__defaults__` 스캔으로 잔여 상태를 점검한다

## 7. 하지 말 것

- 「가변 타입만 조심하면 된다」 — 불변 기본값도 **정의 시점에 굳는다**
- 「테스트가 통과했으니 괜찮다」 — 첫 호출은 항상 정상이다. **두 번째부터 드러난다**
- 「스레드 문제는 GIL이 막아준다」 — 전환 간격에 따라 **드러나기도 하고 숨기도 한다**
- 기본값을 `함수.__defaults__` 에 직접 대입해 고치는 것 — 원인이 아니라 증상을 만진다
- 재현되지 않는 상태 오염을 「환경 탓」으로 넘기는 것 — 먼저 `__defaults__` 를 찍어 본다
