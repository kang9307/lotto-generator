はじめに: ダッシュボードに0.82が出た。それでプロダクトは良くなったのか

評価スクリプトを繋ぎ、パイプラインが回り、ダッシュボードに数字が出る。今週0.82、先週0.79。会議で誰かが訊く。この3ポイントは何を意味しますか。

答えに詰まる理由は道具が足りないからではない。順序が逆さまだからだ。スコアとは何が失敗かという文を数字に移したものである。その文がなければ0.82は、どの失敗が何件から何件に減ったという意味ではなく、ただの0.82だ。上がっても何が良くなったのか言えず、下がっても何を直すべきか分からない。

ここで扱うのは、自社プロダクトの自社プロンプトが自社ユーザーの入力でどう間違えるかを測る計器である。リーダーボードのスコアや公開ベンチマークの信頼性は別の問題で、そちらは知識ベンチマークが教えてくれないことと企業が自前のベンチマークを作った事例で扱った。組織がこの仕事を誰に任せ、どんな会議周期で回すかは評価駆動開発の運用の仕方のほうが詳しい。本稿はその間にある技術的な部分、すなわちデータ・採点・検証・ゲートを見る。

1. 何が失敗か - スコアより先にあるべき文

1.1 失敗の定義は想像ではなく観測から出る

評価を設計するとき最も多い初手は、指標の一覧を作ることだ。正確性、関連性、有害性、簡潔性。この一覧はどのプロダクトにも付き、どのプロダクトにも合わない。自社のユーザーが実際にどう損をしているかが抜けているからである。

順序を逆にする。まず出力を読み、そこから指標を取り出す。この作業には質的研究から来た名前が付いている。トレースを読んで気になった点を自由に書き留める段階がオープンコーディング、そのメモを失敗の型にまとめる段階が軸足コーディングだ。カテゴリを先に作ってメモを流し込むのではなく、メモがカテゴリを作る。自動化が手伝えるのは後ろのまとめる仕事であって、前の読む仕事は人がやらなければ情報が入ってこない。

ここでいうトレースとは、一つのユーザー質問に対してシステムがやったこと全部を指す。最終回答だけでなく、実際に組み立てられたプロンプト、ツール呼び出しと戻り値、検索された文書までだ。この区別は後で効いてくる。最終回答しか保存していなければ、なぜ間違えたのかを辿れず、失敗の型がたまに変な答えを出すの一行に潰れる。

止める時点も決めておく。理論的飽和と呼ばれる基準だが、実務で使いやすい形はこうだ。連続二十件を読んで新しい失敗カテゴリが一つも出なければ、その回は終えてよい。着手時の分量は百件程度がよく挙げられる。最初から千件読むという計画はたいてい三百件あたりで止まり、その三百件は整理されないまま残る。

1.2 判定は合格と不合格に落とす

1から5までの尺度は魅力的に見える。情報が多そうだからだ。問題は3と4の差を文で書けるかである。書けなければその尺度はラベラーごとに違う軸になり、平均を取った瞬間に違う軸の平均になる。

ここで一次資料同士が割れる。実務家のFAQは二値判定を勧め、Anthropicの評価作成ドキュメントはリッカート尺度の採点例をそのまま載せている。どちらかが間違っているのではなく前提が違う。等級が必要なほど項目が連続的な性質なら尺度が合い、採点基準を文で書けない項目なら尺度はノイズを作る。

等級が必要なら、尺度を使う代わりに二値項目を複数に割るほうが扱いやすい。合計が等級になり、どこで落ちたかも一緒に出てくる。

{
  "trace_id": "t-10482",
  "checks": {
    "grounded":      0,   // 検索文書にない規約条項に言及した
    "no_jargon":     1,
    "format_valid":  1,
    "answered":      1    // 答えられる質問を拒否しなかった
  },
  "label_source": "human",
  "notes": "返金期限を14日と記述。根拠文書では7日"
}

1.3 良い失敗定義の試し方

失敗の定義が使い物になるかを判定する基準は一つだ。別々の二人が同じ出力を見て同じ結論に至るか。

  • 悪い例 - 回答は十分に役立つか。人によって割れる
  • 悪い例 - 回答は自社のブランドトーンに合っているか。そのトーンがどこにも書かれていない
  • 良い例 - 検索文書にない数値や条項に言及したら失敗
  • 良い例 - ユーザーが訊いた項目のうち一つでも答えなければ失敗
  • 良い例 - 社内システム名をユーザーに露出したら失敗

人が二人で割れている状態でモデル採点者を付ければ、その採点者はどちらかに適当に付いて半分程度の一致度を記録する。そのとき直すべきなのは採点プロンプトではなく定義の文だ。人の不一致を残したまま自動化すれば、自動化されたのは判定ではなく混乱である。

2. 評価データはどこから来るか

2.1 最初の出所は実運用のログだ

評価セットの話で最も省略されるのがこの部分である。指標の名前は会議一回で決まるが、その指標を何に当てて測るかは常にデータの問題だ。そしてログが残っていなければここで即座に詰まる。最低限、以下は残す。

  • ユーザー入力の原文と時刻
  • 実際に組み立てられてモデルに入ったプロンプト全体
  • モデル識別子・バージョン・温度などのサンプリングパラメータ
  • ツール呼び出しの名前・引数・戻り値
  • 検索段階があるなら検索文書の識別子とスコア
  • 最終出力と応答遅延
  • ユーザー行動シグナル - 即座の再質問、会話離脱、コピー、明示的フィードバック

最後の行が後で最も効く。ユーザーが同じ質問をもう一度投げたという事実は、どの自動採点器よりも正確な失敗シグナルだ。

2.2 無作為標本だけでは失敗が捕まらない

失敗率が5パーセントのシステムで無作為に百件取れば失敗は五件である。そのうち特定の型は一件か二件で、一件二件では型とは呼べない。だから標本を混ぜる。

  • 無作為 - 分布を見る基準線。必ず一部はここから出さなければならない
  • 層化 - ユーザー型・要求カテゴリ・入力長・言語ごとに枠を作り、各枠に割り当てる
  • 外れ値 - 応答長の上下位、遅延の上位、ツール呼び出し回数の上位
  • シグナル起点 - 否定的フィードバック、即座の再質問、途中離脱が付いたトレース
  • クラスタ - 入力を埋め込みでまとめ、クラスタごとに取る。同じ質問百件ではなく百通りの質問が得られる
  • 既存の採点器 - すでに回っているルール検査に引っかかった件
標本の出所を必ず記録しておく。 無作為標本は分布を教え、偏った標本は失敗を教える。二つを混ぜて全体の合格率を計算すれば、その数字はどの母集団も代表しない。各件に sample_source のようなフィールドを付けておけば、後から無作為部分だけを取り出して合格率を出せる。

2.3 失敗事例を先に集めるが、それだけを集めはしない

良い出力だけを集めた集合では、無条件に合格を出す採点者でも高い一致率を記録する。性能ではなく錯覚だ。逆に失敗だけを集めれば合格率が意味を失い、採点者の誤検知傾向を測れない。

ここで分けるべきなのは比率ではなく集合そのものである。二つ作って別々に管理する。

  • 較正用集合 - 採点者に識別力があるかを試すのが目的。合格と不合格をおおよそ同じくらい入れ、明白な件より境界事例の価値が大きい
  • 追跡用集合 - 合格率の推移を見るのが目的。実運用の分布をそのまま保つ

一つにまとめると両方できなくなる。較正用に失敗を多く入れたので合格率は実際より低く出て、追跡用の分布を保ったので採点者の試験は偏ったデータで行われる。

2.4 ログを評価セットに移すときの個人情報

ログはユーザーが書いた文章だ。評価セットに編入された瞬間、チームの複数人が読み、外部の採点APIに出ていき、リポジトリにコミットされ、数か月残る。保存方針とは別の統制が要る。

  • マスキングは元のログではなく評価セットの写しに適用する。原本を消すと事故調査ができなくなる
  • マスキングは分布を変える。名前がすべて同じプレースホルダになればモデルの挙動自体が変わる。マスキング後も同じ失敗が再現するか確認してから編入する
  • 評価セットのアクセス権は本番ログのアクセス権と別に持つ
  • 保存期間を決め、期限切れの件は合格率の計算からも外れるよう設計する

3. 合成データ - 働く場所と崩れる場所

3.1 開いたプロンプトで作ると同じものばかり出る

顧客問い合わせを百件作ってくれと指示すれば、表現だけ違う同じ質問が百件出てくる。生成モデルは指示が開いているとき、自分が最もそれらしいと見る方向に寄る。そうして作った評価セットの合格率は、その一種類の質問に対する合格率である。

処方は次元を手で先に決めることだ。ユーザー型、要求カテゴリ、難易度、入力形態といった軸を立てて組み合わせを作り、組み合わせごとに生成させる。組み合わせを全部展開してから成立しないものを除く順序も使える。どちらにせよ核心は同じで、次元設計こそが我々が何をカバーすると主張するかの宣言であり、それがなければカバレッジという言葉も成立しない。

3.2 合成が崩れる四つの条件

  • 複雑な専門領域 - 生成モデルがその領域の実際の質問分布を知らない
  • 低資源言語 - 表現の多様性と誤りの型が実際と違って出る
  • 高リスク用途 - 間違った合成事例一つが誤った基準を固定してしまう
  • 過少代表の集団 - 元のデータで少なかった集団は合成でさらに少なくなる

四条件の構造は同じだ。生成モデルがその分布を知らなければ、合成データはユーザーの分布ではなくモデルが想像した分布になる。ここに同系統のモデルで採点まで行えば、その想像の中だけで採点が行われる。日本語は低資源言語とは言いがたいが、社内用語と敬語の層と機関名の表記が混ざる業務文書では同じ罠がそのまま生じる。

3.3 合成が確実に働く場所

  • ユーザーがまだいない初期プロトタイプ - 合格率を測るのではなく失敗の形を見る段階
  • まれだが必ず処理しなければならない入力 - プロンプト注入の試み、空入力、超長文、言語混在、壊れたエンコーディング
  • 採点者較正用の境界事例 - 明白な合格と明白な不合格はどの採点者でも当てる
  • 回帰用の固定ケース - 実運用データは動き続けるが、回帰テストは止まっていなければならない
合成データで出した合格率をプロダクト品質の指標にしない。 合成ケースは何が壊れるかを教える道具であって、どれだけ良いかを教える道具ではない。この二つを同じダッシュボードに並べれば必ず混ざる。

4. 採点三系統 - コストと信頼条件

採点器はルール・モデル・人の三つしかなく、三つは代替物ではなく性質の違う道具だ。一つだけで済ませるという選択は、たいてい高くつくか不正確かで終わる。

5. どの採点器に送るかは出力の性質が決める

項目ごとの振り分け規則を先に決めておけば議論が消える。

  • 正解が一つに定まるか → ルール。完全一致または数値の許容誤差
  • 構造や形式の要求か → ルール。スキーマ検証とパースで終わる
  • 絶対に出てはいけないものか → ルール優先、モデルは補助。遮断は速く決定的でなければならない
  • 参照文書に対する事実整合か → モデル採点。ただし採点プロンプトに参照文書を一緒に入れる必要がある
  • トーン・完結性・有用性か → モデル採点と人の標本
  • 安全・規制・法的責任か → 人。ここでコストを削ると削った分より大きく払う

ルールで捕まるものをモデルに訊かない。JSONのパース失敗をモデルに訊くのは、金と遅延を買って精度を下げる行為だ。どの項目がルールで判定可能なのかそれ自体が曖昧なら、その境界を引く方法は検証ハーネスが引いた境界線で別途整理した。

順序もコスト設計の一部である。安い層で濾されたものを高い層でもう一度測れば、金を使うだけで情報は増えない。形式が壊れた出力をモデル採点者に送れば、採点者は形式の問題に反応して中身の点数まで低く付ける。

モデル採点者は人の代理人ではなくもう一つのモデルであり、人とは違うものに反応する。以下の三つは論文で測定されているので、設計段階で先に防げる。

三行目が実務で最も無視される。同じモデルで生成し同じモデルで採点すればパイプラインは単純になるが、採点者は自分の文体を報酬しはじめる。Anthropicの評価ドキュメントも、採点には生成と違うモデルを使うことを一般的な推奨として記している。予算の都合で同じモデルを使わざるを得ないなら、せめて人のラベルとの一致度を測り、その差が許容範囲かを確認してから使う。

位置バイアスの条件も注目に値する。品質差が小さいほど大きくなるということは、プロンプトAとAを一行直したA′を比べるときに最も強く出るという意味だ。ところが評価でやろうとしていることは、まさにそれである。

7. 採点者を検証する方法 - 人のラベルとの一致度

7.1 正解率では採点者を測れない

採点者検証で最も多い誤りは正解率を見ることだ。失敗率の低いデータで正解率は、採点者の識別力ではなくデータの偏りを反映する。以下は人がラベルを付けた百件に四つの採点者を走らせた混同行列から計算した値である。

function stats(tp, fn, fp, tn) {          // tp = 人が合格 かつ 採点者も合格
  const n = tp + fn + fp + tn;
  const po = (tp + tn) / n;                // 単純一致率
  const pe = ((tp+fn)/n)*((tp+fp)/n) + ((fp+tn)/n)*((fn+tn)/n);
  return {
    acc:   po,
    kappa: (po - pe) / (1 - pe),           // コーエンのカッパ
    tpr:   tp / (tp + fn),                 // 合格を合格と判定
    tnr:   tn / (tn + fp)                  // 不合格を不合格と判定
  };
}
採点者混同行列 (TP/FN/FP/TN)正解率カッパTPRTNR
A - 無条件に合格90 / 0 / 10 / 00.9000.0001.0000.000
B86 / 4 / 8 / 20.8800.1890.9560.200
C83 / 7 / 5 / 50.8800.3880.9220.500
D - 均衡したデータ44 / 6 / 6 / 440.8800.7600.8800.880

四つのうち三つは正解率が0.880で同じだ。カッパは0.189から0.760まで開く。そして何もしていないAが正解率は最も高く、カッパはちょうどゼロである。正解率だけを見てAをダッシュボードに掛ければ、毎日合格率90パーセントが表示され、その数字はどんなプロンプト修正にも反応しない。

カッパは偶然一致した分を差し引いて残る合意だけを数える。評価者が三人以上、あるいはラベルが順序のある等級ならクリッペンドルフのアルファのほうが扱いやすい。

7.2 真陰性率を別に見る

表のTNR列が核心だ。Bは失敗十件のうち二件しか捕まえない。こういう採点者を付ければ合格率はきれいになり、失敗はそのまま出ていく。逆方向の危険もある。TNRを上げようと採点基準をきつくすれば正常な出力が失敗と判定され、そんな警報が数週間積もればチームはダッシュボードを見なくなる。

  • 失敗を逃してはいけない項目 - TNRを優先し、誤検知は人が濾す
  • 遮断ゲートに使う項目 - TPRを優先。誤検知一つがリリースを止める
  • 両方の要求が同時にあるなら項目を割る。一つの採点者で両方満たそうとする試みはたいてい両方逃す

7.3 採点者もバージョン管理の対象だ

採点基準を直して一致度を上げたなら、その基準はその集合に合わせ込まれている。人のラベル集合を最初から二つに割っておき、基準を整えるときは片方だけを見て、最終の数値は手を付けていないホールドアウトで出す。この手順を飛ばすと、一致度は上がるのに新しいデータでは変わらない状態になる。

  • 採点プロンプト・モデル・温度をバージョンとして記録する。採点者が変われば過去のスコアと比較できない
  • 採点者を替えた日は以前の採点者でももう一度走らせ、二系列を重ねておく
  • 人のラベル集合は失敗の型が変わったときに更新する。暦の周期ではなく事象基準だ

プロンプト自体のバージョン管理とロールバック判断は運用プロンプトの変更・検証・ロールバック設計で別途扱った。採点者はその規律がもう一枚必要な対象である。測る道具が揺れれば、測る対象の変化は見えない。

8. 評価をCIに掛けるとき - 非決定性・しきい値・回帰判定

8.1 一度走らせた結果で判定しない

同じ入力に同じ出力が来ないというのが、この問題の出発点だ。温度をゼロに下げても完全には消えない。バッチ構成、ハードウェア、提供側の更新が残っている。

だから先にやることはしきい値を決めることではなく揺れ幅を測ることである。同じケース集合をコード変更なしで複数回走らせ、回ごとの合格率の分布を見る。その幅を知らなければ、どんな低下も回帰に見えるか、どんな低下もノイズに見える。幅が大きければケースを増やすか、揺れの大きいケースを隔離する。

8.2 しきい値は絶対値ではなく基準線との比較で

合格率0.85のような絶対線は根拠なく決まり、引っかかるたびに人が線を下げる。数か月後にはその線が通過を保証する位置に来ている。

  • 直前のリリースを同じデータで同じ回数だけ走らせる
  • 二つの分布を比べ、低下幅が回ごとの揺れより大きいかを見る
  • 項目別に見る。合計の一行が保たれていても、特定の失敗型だけが二倍になることはよくある
  • 新たに失敗へ変わった個別ケースを一覧で出す。数字よりその一覧のほうが原因を早く教える

8.3 CI用と監視用は別の物だ

軸CIゲート本番監視
データ選別された固定ケース実運用トラフィックの標本
採点ルール中心、決定的モデル採点中心、非同期
時間予算数分制約なし
失敗時マージを遮断通知と標本レビュー
変更周期まれに、意図的に新しい失敗型が出るたび

二つを一つのパイプラインにまとめようとする試みはよく失敗する。CIにモデル採点二百件を入れればパイプラインは遅く高くなり、たまに理由なく赤くなる。数週間後に誰かがその段階を条件付きで飛ばすようにし、そうなるとゲートは消える。実務で回る組み合わせは二層だ。ルールで判定できる項目は一件でも壊れたら遮断し、モデル採点の指標は遮断ではなく警告に留めて人が見る。

9. スコアは上がるのにプロダクトが悪くなるとき

9.1 グッドハートの法則 - 測定が目標になる瞬間

測定が目標になれば、その測定は良い測定であることをやめる。LLM評価でこの法則は特に速く働く。採点者が長い回答を好むと知られればプロンプトは静かに長くなり、スコアは上がり、ユーザーは読まない。先に見た長さバイアスがここでそのままコストになる。

ルールベースの項目も安全ではない。根拠文書の引用を含めば合格という規則を掛ければ、モデルは関係ない文書でも引用する。ルールは形式を見るのであって意図を見ない。

9.2 評価セットの老化 - 通過する方法を覚える

同じ百件を半年見続ければ、チームはその百件を通過する方法を覚える。プロンプトに例外処理が一つずつ付き、その例外は評価セットの特定ケースを狙ったものだ。その時点で評価セットは試験問題ではなく学習データである。公開ベンチマークの汚染と構造が同じで、自前のものなので気づきにくい。

同じ問題の別の顔は、評価形式そのものの寿命だ。作業が長くなり段階が増えれば、単発の出力を採点するやり方は解像度を失う。その転換は長時間作業へ移った評価で別途整理した。

9.3 分布シフト - 測っていた母集団が消える

  • ユーザー層が変わる - 社内試験運用から外部公開に移れば入力の文体から違う
  • 流入経路が変わる - 検索から来たユーザーとアプリから来たユーザーは違うことを訊く
  • 機能が追加される - 評価セットにその機能の入力が一件もない
  • 季節と事象 - 確定申告、新学期、障害告知のような時期には質問分布が丸ごと変わる
  • 上流のシステムが変わる - 検索インデックスを更新すれば同じ質問に違う文書が入る

9.4 防御 - 三つで足りる

  • 回転 - 評価セットの一定割合を毎回新しいログに入れ替える。入れ替え分と固定分のスコアを別々に出す
  • ホールドアウト - チームが見られない集合を残す。そこだけスコアが上がらないなら、最適化が評価セットに向かっていたということだ
  • プロダクト指標の並走 - 再質問率、会話離脱率、有人対応への転送率など評価と独立したシグナルを並べて見る。評価スコアとこれらが逆に動けば評価のほうを疑う

10. 構築段階表 - 何をいつやるか

段階やること成果物次へ進む条件よくある失敗
0. 観測トレース保存を有効にする入力・プロンプト・ツール・出力・ユーザーシグナル過去数日分を辿れる最終回答だけ保存
1. エラー分析標本を読んでメモし、型にまとめる失敗型の一覧と件数連続20件に新しい型が出ない指標の一覧から作る
2. 定義型ごとに判定の文を書く二値項目の一覧二人が同じ結論を出す役に立つかのような文
3. ラベル人がラベルを付ける較正用とホールドアウトの二集合ラベラー間の不一致が解消した良い例だけを集める
4. 自動化項目ごとに採点器を割り当てるルール検査と採点プロンプトルールで済むものがルールにある全部モデルに任せる
5. 検証ホールドアウトで一致度を測るカッパ・TPR・TNRの記録目標一致度に到達した正解率だけ見る
6. ゲートCIと監視を分けて掛ける遮断規則と警告指標揺れ幅を測ってある絶対しきい値を打ち込む
7. 維持回転・ホールドアウト・プロダクト指標回ごとの記録回り続ける一度作って放置

1の段階が全体日程の半分以上を食うという報告があるが、この配分は驚くことではなく正常である。後の段階はすべて1の結果を機械に移す作業なので、1が薄ければ残りは間違ったものを正確に測ることになる。

11. 確認できなかったこと

  • モデル採点者が人と何パーセント一致するかについての一般値はない。 公開されているのは特定の課題・特定の採点基準・特定のデータでの個別事例値だけだ。他組織の一致度の数値を自分たちの目標線に移す根拠は確認できなかった
  • 位置バイアスは二つの公開ベンチマークで測定されたものだ。日本語の業務データや社内領域で同じ大きさで現れるかは確認できなかった
  • 長さ補正の方法は対比較のランキング用に設計されている。単件採点にそのまま移す手順はその論文にない
  • エラー分析に開発時間の60〜80パーセントがかかるという観察、自前のレビュー道具を作ったチームが約十倍速いという観察は実務家の経験報告だ。標本と測定方法が公開された調査は確認できなかった
  • 二値判定とリッカート尺度のどちらが優れているかは結論が出ていない。二つの一次資料が異なる推奨を出しており、条件を分けた比較研究は確認できなかった
  • 評価セットを何パーセントずつ回転させれば老化を防げるかの数値的根拠は確認できなかった。回転が必要だということと、どれだけ必要かは別の問いだ

結論: 評価は道具を選ぶ仕事ではない

評価の導入が失敗する場所はほぼいつも同じだ。道具を先に選び、指標の名前を先に決め、データを後から合わせる。そうすればダッシュボードはできるが、その数字が何の代理なのか誰も言えない。

順序を守れば道具は後の問題になる。出力を読み、失敗を文で書き、その文が二人に同じく読まれるか試し、項目ごとに最も安い採点器を割り当て、採点者を人のラベルで検証し、揺れ幅を測ってからゲートを掛ける。この順序から出てくる0.82はこの失敗型が何件から何件に減ったに翻訳される。

今日始めるなら三つだ。トレース保存を有効にし、標本百件を読み、人のラベル集合を二つに割って片方は手を付けずに残す。残りはこの三つがあって初めて始められるし、この三つさえあれば道具なしでも始められる。
