계기 - 코드가 아닌 설정 파일로 정의하는 에이전트

Docker Agent는 Docker가 공개한 오픈소스 도구로, 에이전트의 모델과 지침, 도구, 함께 일할 동료 에이전트를 YAML 파일에 적어 두고 docker agent 명령으로 실행하는 Docker CLI 플러그인이다. README는 「Build, run, and share AI agents with a declarative YAML config, rich tool ecosystem, and multi-agent orchestration」이라는 한 줄로 소개하고, 본문에서 「no code required」라고 밝힌다.

공식 문서의 첫 문장은 「Docker Agent is to AI agents what docker run is to containers」이다. 문서는 LLM 오케스트레이션 루프, 도구 실행, 멀티 에이전트 위임, 스트리밍 출력을 Docker Agent가 처리하므로 사용자는 연결 방법이 아니라 에이전트가 무엇을 해야 하는지에 집중하면 된다고 설명한다.

GeekNews에는 2026년 10월 8일에 등록됐다. 저장소 메타데이터를 보면 소유자는 docker 조직, 라이선스는 Apache-2.0, 생성일은 2025년 9월 1일이며, 가장 최근 릴리스는 2026년 10월 7일의 v1.149.0이다. 이 값은 GitHub 저장소 정보와 릴리스 페이지의 표기이고, 이후 바뀔 수 있다.

설치는 세 경로로 안내된다. Docker Desktop 4.63 이상에는 플러그인이 미리 들어 있어 docker agent로 바로 실행할 수 있고, Homebrew에서는 brew install docker-agent로 설치한다. GitHub 릴리스의 바이너리를 받아 ~/.docker/cli-plugins에 두면 docker agent로도 쓸 수 있다. 소스 빌드에는 Go 1.27 이상이 필요하다고 설치 문서는 적는다.

Docker Agent의 정체성 - 무엇이고 무엇이 아닌가

공식 문서의 첫 화면에는 도구의 성격을 네 칸으로 요약한 소개 카드가 있다. 아래는 그 문구를 풀어 옮긴 것이다.

  • 무엇인가: YAML 또는 HCL로 선언적으로 정의한 AI 에이전트를 실행하는 CLI이다.
  • 무엇이 아닌가: 코드를 작성하는 프레임워크가 아니고, 호스팅형 SaaS가 아니며, 새로운 모델도 아니다.
  • 누구를 위한 것인가: 접착 코드(glue code) 없이 자신의 작업 흐름에 에이전트를 넣고 싶은 개발자이다.
  • 무엇을 얻는가: TUI, CLI, HTTP API, MCP 서버, A2A, OCI 배포가 제공된다고 문서는 나열한다.
  • 소속: 문서는 Docker Engine, Docker Desktop, Docker Hub, Docker Scout를 만든 Docker의 오픈소스 도구라고 소개한다.

문서는 같은 코딩 어시스턴트를 두 방식으로 비교한다. 코드로 만들면 모델 클라이언트 초기화, 도구 스키마 정의, 디스패치 함수, 메시지 누적 루프를 합쳐 약 30줄의 파이썬 접착 코드가 프로젝트마다 필요하다는 예시를 들고, Docker Agent로는 8줄의 YAML과 docker agent run agent.yaml 한 줄로 끝난다고 대비한다. 줄 수는 문서가 든 예시의 값이다.

단일 에이전트 YAML 구조와 필드

README의 첫 예시는 agents 아래에 root 에이전트 하나를 두고 모델, 설명, 지침, 도구를 적는 형태이다. 실행은 docker agent run agent.yaml이다.

agents:
                      root:
                        model: openai/gpt-5-mini
                        description: A helpful AI assistant
                        instruction: |
                          You are a knowledgeable assistant that helps users with various tasks.
                          Be helpful, accurate, and concise in your responses.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo

공식 문서의 소개 페이지에는 파일 시스템, 셸, think 도구를 가진 코딩 어시스턴트 예시가 실려 있다.

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: A coding assistant
                        instruction: |
                          You are an expert developer. Help users write clean,
                          efficient code. Explain your reasoning step by step.
                        toolsets:
                          - type: filesystem
                          - type: shell
                          - type: think

아래 표는 위 두 예시와 에이전트 설정 문서에 나온 주요 필드를 정리한 것이다. 설정 문서는 「A configuration must define at least one agent under agents」라고 적는다.

필드 형식 문서의 설명 비고
agents 맵 에이전트 이름을 키로 갖는 최상위 항목 최소 한 개의 에이전트를 정의해야 한다
model 문자열 모델 참조. 예시는 공급자/모델 형식 harness를 쓰지 않는 한 필수로 표시된다
description 문자열 이 에이전트가 하는 일 스키마에서 선택 항목
instruction 문자열 또는 목록 시스템 프롬프트 instruction_file과 동시에 쓸 수 없고, 목록은 빈 줄로 이어 붙는다
toolsets 목록 도구 설정 목록 type으로 도구를 고르고 mcp는 ref를 더한다
sub_agents 목록 로컬 또는 외부 서브에이전트 참조 위임 패턴에서 사용한다
handoffs 목록 이 에이전트가 대화를 넘길 수 있는 에이전트 이름 핸드오프 패턴에서 사용한다

모델 공급자에 대해 README는 OpenAI, Anthropic, Gemini, AWS Bedrock, Mistral, xAI, Docker Model Runner 등을 나열하고 「and more」라고 덧붙인다. 소개 문서는 model: 한 줄만 바꾸면 모델을 교체할 수 있다고 설명하며, 로컬 모델은 Docker Model Runner나 Ollama로 쓸 수 있다고 적는다. 모델에 접근하려면 API 키를 환경 변수로 두거나 Docker Model Runner를 써야 한다고 README는 안내한다.

설정 문서의 전체 스키마에는 위 필드 외에도 다음과 같은 항목이 주석과 함께 나열된다.

  • instruction_file: 설정 파일 기준 상대 경로의 파일에서 시스템 프롬프트를 읽는다.
  • fallback: 대체 모델 목록과 재시도 횟수, 대기 시간을 지정한다.
  • max_iterations: 도구 호출 루프의 최대 횟수를 제한한다.
  • harness: 외부 코딩 CLI에 위임하는 설정이며, type 값으로 claude-code, codex, opencode, pi가 적혀 있다.

HCL도 같은 설정 모델의 다른 문법이라고 문서는 밝힌다. .yaml이나 .yml을 받는 곳이면 .hcl도 받으며, HCL을 내부에서 같은 YAML 구조로 바꾼 뒤 동일한 스키마 검증을 거친다.

멀티 에이전트의 두 패턴 - 위임과 핸드오프

멀티 에이전트 문서는 복잡한 작업에서 하나의 에이전트에 모든 것을 맡기는 대신 코디네이터, 개발자, 리뷰어, 리서처처럼 역할이 좁은 에이전트 팀을 만들 수 있다고 설명한다. 각 에이전트는 자신의 모델과 도구, 지침을 따로 가진다. 두 패턴의 비교는 문서의 표를 따른다.

항목 위임 (sub_agents) 핸드오프 (handoffs)
구조 계층형 (부모, 자식, 부모) P2P 그래프 (A, B, C, A)
세션 자식은 하위 세션에서 실행 같은 세션에서 대화 유지
컨텍스트 자식은 정리된 작업 설명을 받음 다음 에이전트가 전체 대화 기록을 봄
제어 흐름 부모는 자식이 끝날 때까지 대기한 뒤 이어서 진행 활성 에이전트가 바뀌고 이전 에이전트는 루프에서 빠짐
도구 transfer_task handoff
적합한 경우 전문가에게 작업 위임 파이프라인 작업 흐름, 대화 라우팅

위임에서는 sub_agents가 있는 에이전트에 transfer_task 도구가 자동으로 제공된다. 도구 문서에 따르면 매개변수는 agent, task, expected_output 세 가지이고 모두 필수이다. 호출은 서브에이전트가 결과를 돌려줄 때까지 막히며, 문서는 한 설정 안에서 sub_agents와 handoffs를 함께 쓸 수도 있다고 적는다.

핸드오프는 대화 전체를 다른 에이전트에게 넘기는 방식이다. 문서의 예시는 코디네이터가 리서처에게, 리서처가 요약 에이전트에게 넘기고, 요약 에이전트가 다시 코디네이터로 돌아오는 구성이다.

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: Coordinator that routes queries
                        instruction: |
                          Route research queries to the researcher.
                        handoffs:
                          - researcher
                    
                      researcher:
                        model: openai/gpt-5
                        description: Web researcher
                        instruction: |
                          Search the web, then hand off to the summarizer.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo
                        handoffs:
                          - summarizer
                    
                      summarizer:
                        model: openai/gpt-5
                        description: Summarizes findings
                        instruction: |
                          Summarize the research results, then hand off
                          back to root.
                        handoffs:
                          - root

핸드오프 문서는 이 도구가 같은 설정 파일에 선언된 로컬 에이전트만 대상으로 하며 네트워크 연결을 열지 않는다고 밝힌다. 원격 에이전트에 위임하려면 A2A 도구셋을 쓰라고 안내한다. 각 에이전트는 자신의 handoffs 배열에 적힌 이름으로만 넘길 수 있다.

문서가 제시하는 선택 기준은 다음과 같다.

  • sub_agents: 코디네이터가 전문가에게 작업을 보내고 결과를 종합해야 할 때 쓴다.
  • handoffs: 에이전트들이 같은 대화를 차례로 처리하는 파이프라인이나 라우팅에 쓴다.
  • background_agents: 서로 독립적인 여러 작업을 동시에 실행할 때 쓴다. 문서는 run_background_agent, list_background_agents, view_background_agent, wait_background_agents, stop_background_agent 도구 이름을 든다.

핸드오프는 모델이 handoff 도구를 부를지 스스로 결정하므로 부르지 않을 수 있다고 문서는 지적한다. 이를 막는 force_handoff는 에이전트가 최종 응답을 낼 때 런타임이 지정한 에이전트로 대화를 넘기며, 설정 로드 시 대상이 설정 안에 정의돼 있어야 하고 자기 자신을 가리킬 수 없으며 순환 체인이 되면 거부된다는 규칙을 적는다.

  • 순환 거부: 위임 체인에 이미 포함된 에이전트를 다시 가리키는 위임(예를 들어 a, b, a)은 오류로 실패한다.
  • 깊이 제한: 중첩 위임은 10단계까지이며, 루트가 첫 서브에이전트에게 위임하면 깊이 1이다.

도구 생태계 - 내장 도구셋과 MCP 서버

도구 문서는 에이전트가 도구 호출을 하면 Docker Agent 런타임이 도구를 실행해 결과를 돌려주고, 에이전트가 그 결과를 이용해 작업을 이어 간다고 설명한다. 내장 도구셋은 toolsets 목록에 type을 적어 켠다.

도구 type 문서가 밝힌 동작 문서가 밝힌 제약
파일 시스템 filesystem read_file, write_file, edit_file, list_directory, search_files_content 등 파일 읽기, 쓰기, 탐색 기본은 제한이 없고 allow_list와 deny_list로 범위를 좁힌다
셸 shell 셸 명령 실행. 호출마다 새로운 격리된 셸 세션 기본 타임아웃 30초, --yolo를 쓰지 않으면 사용자 확인 필요
스크립트 script 미리 정한 셸 명령에 이름과 타입이 있는 매개변수를 붙여 도구로 노출 에이전트가 명령을 직접 쓰는 shell보다 자유도가 낮고 안전하다고 문서는 설명
MCP mcp Model Context Protocol 서버의 도구 연결 Docker MCP, 로컬 stdio, 원격 세 가지 방식
추론과 기억 think, todo, memory README가 내장 think, todo, memory 도구를 나열 —
검색 증강 rag README: BM25, 임베딩, 하이브리드 검색, 리랭킹을 꽂아 쓰는 구조 —

MCP 도구 문서는 연결 방식을 세 가지로 구분한다.

  • Docker MCP(권장): MCP Gateway를 거쳐 Docker 컨테이너로 서버를 실행하며, ref: docker:duckduckgo처럼 Docker MCP 카탈로그의 정의를 참조한다.
  • 로컬 stdio: command와 args로 로컬 프로세스를 띄워 표준 입출력으로 통신한다.
  • 원격: remote.url과 transport_type(streamable 또는 sse)으로 네트워크의 서버에 붙는다. OAuth 흐름은 자동으로 처리된다고 문서는 적는다.
  • 도구 제한과 자동 설치: tools 목록으로 모델에 노출할 도구를 좁힐 수 있고, 로컬 명령이 PATH에 없으면 aqua 레지스트리에서 찾아 설치하며 DOCKER_AGENT_AUTO_INSTALL=false로 끌 수 있다.

OCI 레지스트리로 공유하는 에이전트

배포 문서는 에이전트를 Docker Hub, GitHub Container Registry 같은 OCI 호환 레지스트리에 푸시하고 어디서든 풀해서 실행할 수 있다고 설명한다. 문서의 푸시와 풀 예시는 다음과 같다.

docker agent share push ./agent.yaml docker.io/username/my-agent:latest
                    docker agent share pull docker.io/username/my-agent:latest
  • 실행: README의 빠른 시작은 docker agent run myorg/agent:tag로 레지스트리의 에이전트를 바로 실행하는 형태를 보여 준다.
  • 서명: share push --key로 게시자를 증명하고 변조 여부를 확인할 수 있게 하며, 이때 YAML 자체는 항상 평문으로 푸시되고 증명만 OCI 매니페스트 어노테이션에 담긴다.
  • 암호화: --encrypt를 더하면 YAML 전체의 암호화된 사본도 어노테이션에 기록된다. 암호 키를 지정한 문서의 예시는 ed25519 키와 대칭 비밀값 두 가지이다.
  • 증명 형식: 서명은 in-toto Statement v1을 담은 DSSE 봉투를 덮으며, 문서는 cosign과 in-toto 도구가 쓰는 형식이라 Docker Agent 없이도 읽고 검증할 수 있다고 적는다.
  • 외부 서브에이전트: 서브에이전트를 로컬에 정의하지 않고 OCI 레지스트리의 에이전트를 참조할 수 있다고 멀티 에이전트 문서는 안내한다.

레지스트리나 URL에서 받은 설정은 작성자가 쓴 안전 기본값을 담을 수 있으므로 실행 전에 검토하라고 권한 문서가 경고한다. 서명 검증은 변조 여부를 확인하는 장치이며 설정 내용이 안전하다는 보증은 아니다.

권한과 안전 모드 - 승인 흐름의 구조

도구 문서는 기본 동작을 「셸 명령과 파일 쓰기처럼 부작용이 있는 도구는 실행 전에 사용자 확인을 요청하고, --yolo를 쓰면 모든 도구 호출을 자동 승인한다」고 적는다. 권한 문서는 여기에 더 세분화된 구조를 설명한다.

  • 평가 순서: 권한 규칙은 deny, allow, ask 순서로 평가되며, deny가 우선하고 어느 규칙에도 걸리지 않은 호출은 세션의 안전 모드로 넘어간다.
  • 안전 모드 네 가지: strict는 모든 호출을 묻고, balanced는 안전한 호출만 조용히 실행하고 나머지를 묻는다. restricted는 안전한 호출만 실행하고 나머지를 묻지 않고 거부하며, autonomous는 모두 실행한다.
  • --yolo의 위치: 문서는 autonomous를 옛 --yolo 동작이라고 부르고, --yolo를 옛 표기(legacy spelling)로 남아 있는 별칭으로 취급한다. 모드는 --safety 플래그로 고른다.
  • 명령 분류: 셸 명령은 safe, destructive, unknown으로 분류된다. ls, git status 같은 읽기 명령은 safe이고, rm -rf 같은 명령은 destructive이며, 나머지는 unknown이다.
  • transfer_task와 핸드오프: transfer_task는 항상 자동 승인되며, handoff는 자신의 handoffs 목록에 있는 대상으로만 넘길 수 있다.
  • 경로 제한: filesystem 도구는 allow_list와 deny_list를 지정하지 않으면 제한이 없다. 문서의 예시는 홈 디렉터리 아래의 .ssh와 .aws를 deny_list에 두는 형태이다.
  • 샌드박스 모드: docker agent run --sandbox agent.yaml은 Docker Sandboxes의 VM 안에서 에이전트를 실행한다. restricted 모드를 두고 문서는 「defense in depth, not a security boundary」이며 진짜 격리에는 샌드박스 모드를 쓰라고 적는다.
  • 원격 측정: README는 도구 개선을 위해 익명 사용 데이터를 수집한다고 밝히고 텔레메트리 문서로 안내한다.

「코드 없이」의 범위와 문서가 밝힌 경계

「no code required」는 README의 표현이다. 같은 문서 모음에서 이 말의 범위를 가늠할 수 있는 항목은 다음과 같다.

  • script 도구: 미리 정한 셸 명령을 이름과 타입이 있는 매개변수로 노출한다. 명령 자체는 사용자가 써야 한다.
  • Go SDK 가이드: Docker Agent를 Go 라이브러리로 써서 애플리케이션에 에이전트를 내장하는 방법을 설명하는 별도 가이드가 있다.
  • 셸 도구의 위상: 문서는 셸을 가장 강력한 도구 중 하나라고 부르며, 빌드와 의존성 설치, API 질의, 시스템 상호작용까지 에이전트가 할 수 있다고 설명한다.
  • 구성 요소의 범위: 설정 문서에는 hooks, structured_output, cache, code_mode_tools 같은 항목이 있어 YAML만으로 닿는 기능의 폭을 보여 준다.
  • 실행 환경 의존: 모델 접근에는 공급자 API 키, 계정 로그인, Docker Model Runner, 코딩 하네스 중 하나가 필요하다고 설치 문서가 적는다.

확인하지 못한 것

  • 프로젝트 이름의 변경 이력. 문서의 사용자 설정 경로에 ~/.config/cagent/config.yaml이 남아 있으나 개명 시점과 경위를 적은 문서는 읽은 범위에 없었다.
  • Linux 패키지 관리자(apt, dnf)용 설치 경로. 설치 문서는 Docker Desktop, Homebrew, 바이너리 릴리스, 소스 빌드를 안내한다.
  • Docker Model Runner를 쓸 때의 하드웨어 가속 요구 사항.
  • OCI 아티팩트 레이어 구조와 미디어 타입의 세부 규격.
  • 동시에 여러 에이전트를 실행할 때 CPU와 메모리를 제한하는 설정 필드의 유무. 설정 문서 목록에 budget 항목이 있으나 내용은 읽지 않았다.
  • 성능과 비용에 관한 수치. README와 읽은 문서에는 해당 수치가 없다.
