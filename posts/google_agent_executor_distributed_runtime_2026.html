Agent Executor - Google의 분산 에이전트 런타임 오픈소스 분석 2026

Inside Agent Executor - Google's Open-Source Distributed Agent Runtime

2026-06-05 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 에이전트는 만들기보다 굴리기가 어렵다

지난 2년간 우리는 'AI 에이전트를 어떻게 만드는가'에 대한 글을 수백 편씩 읽었습니다. 프롬프트를 어떻게 짜고, 도구를 어떻게 붙이고, 어떤 프레임워크로 그래프를 그리는지에 관한 이야기였죠. 그런데 막상 에이전트를 프로덕션에 올린 팀이 마주하는 진짜 고통은 다른 곳에 있습니다. 30분짜리 멀티스텝 에이전트가 27분 지점에서 워커 프로세스가 죽으면, 그동안 쓴 LLM 토큰 비용과 외부 API 호출이 통째로 날아갑니다. 무엇이 왜 잘못됐는지 추적할 로그는 흩어져 있고, 똑같은 입력을 넣어도 재현되지 않습니다. 에이전트는 만드는 것보다 안정적으로 굴리는 것이 훨씬 어렵다는 사실을, 운영을 해 본 사람만 압니다.

2026년 6월 초, Google이 이 문제를 정면으로 겨냥한 오픈소스를 공개했습니다. 이름은 Agent Executor, 한 줄로 요약하면 '분산 에이전트 런타임'입니다. 핵심 아이디어는 의외로 고전적입니다. 에이전트 루프의 모든 단계를 이벤트로 로깅하고, 그 이벤트 로그를 실행의 단일 진실 원천으로 삼는 것이죠. 이 글은 hada(GeekNews)에서 화제가 된 이 발표를 출발점으로 삼되, 단순 소개를 넘어 'Agent Executor가 정확히 어떤 문제를 푸는가', '기존 프레임워크와 무엇이 다른가', 그리고 '한국 개발팀이 지금 이걸 도입해야 하는가'를 제 관점에서 분석합니다.

1. Agent Executor가 푸는 진짜 문제

먼저 문제 정의부터 분명히 하겠습니다. AI 에이전트의 본질은 비결정적 루프입니다. 'LLM에게 무엇을 할지 묻고 → 도구를 실행하고 → 결과를 다시 LLM에게 주고 → 끝났는지 판단하는' 사이클을 종료 조건이 만족될 때까지 반복합니다. 이 루프가 단순한 함수 호출과 근본적으로 다른 점은 세 가지입니다.

  • 오래 걸린다: 수십 번의 LLM 호출과 외부 API 대기가 누적되면 한 작업이 수 분에서 수십 분, 길게는 시간 단위로 늘어집니다.
  • 비싸다: 각 단계가 토큰 비용을 쓰고, 외부 API 호출은 부수효과(이메일 발송, 결제, 파일 쓰기)를 남깁니다. 중간에 실패해 처음부터 다시 하면 비용도 부수효과도 중복됩니다.
  • 불투명하다: 어떤 판단으로 어떤 도구를 왜 호출했는지가 LLM 내부에 숨어 있어, 사후 추적과 디버깅이 매우 어렵습니다.

Agent Executor가 내건 네 가지 목표 — 신뢰성(reliability), 안전성(safety), 커스터마이징(customizability), 효율성(efficiency) — 은 정확히 이 세 가지 고통에 대응합니다. 오래 걸리는 루프가 중간에 죽어도 복구되어야 하고(신뢰성), 부수효과가 중복 실행되지 않아야 하며(안전성), 팀마다 다른 도구·정책을 끼울 수 있어야 하고(커스터마이징), 불필요한 재실행 없이 자원을 아껴야 합니다(효율성).

2. 이벤트 소싱 - 에이전트 실행 모델의 핵심

Agent Executor의 설계 철학을 한 단어로 압축하면 이벤트 소싱(Event Sourcing)입니다. 이는 데이터베이스 세계에서 오래 검증된 패턴으로, '현재 상태를 직접 저장하는 대신, 상태를 만들어 낸 모든 이벤트를 추가 전용(append-only) 로그로 기록한다'는 발상입니다.

에이전트 루프에 이를 적용하면 이렇게 됩니다. LLM에게 질의했다 → 이벤트로 기록. 도구 X를 인자 Y로 호출하기로 결정했다 → 이벤트로 기록. 도구가 결과 Z를 반환했다 → 이벤트로 기록. 이 로그를 처음부터 재생(replay)하면, 에이전트의 현재 상태가 정확히 복원됩니다.

[t0] AgentStarted        목표: "이번 주 매출 리포트 작성"
 │
[t1] LLMRequested        프롬프트 + 가용 도구 목록
[t2] ToolCallDecided     query_db(range="this_week")
[t3] ToolCallCompleted   결과: 1,240건 / 매출 8,300만원
 │
[t4] LLMRequested        결과 반영한 다음 판단
[t5] ToolCallDecided     send_email(to=team, body=...)
 ✗   여기서 워커 프로세스 크래시
 │
 ▶   재시작 워커가 로그 재생 → t4까지 복원
     → t5(이메일 발송)는 미완료로 판정 → 안전하게 재개

이 모델의 위력은 크래시 복구만이 아닙니다. 관찰 가능성이 공짜로 따라옵니다. 이벤트 로그 자체가 완벽한 실행 추적(trace)이기 때문에, '왜 이 에이전트가 이 결정을 내렸는가'를 사후에 한 단계씩 그대로 들여다볼 수 있습니다. 비결정적이던 에이전트가, 적어도 '무슨 일이 일어났는가' 측면에서는 결정적으로 검증 가능해지는 것입니다.

3. '분산' 런타임이 의미하는 것

이름에 붙은 분산(distributed)이라는 단어는 단순한 마케팅이 아닙니다. 이벤트 로그가 실행 상태를 프로세스 바깥에 외부화하기 때문에, 에이전트 실행이 더 이상 특정 서버·프로세스에 묶이지 않습니다.

이것이 실무에서 주는 이점은 구체적입니다.

  • 장애 격리: 워커 A가 죽어도 워커 B가 로그를 읽어 이어받습니다. 한 노드의 죽음이 작업의 죽음으로 직결되지 않습니다.
  • 수평 확장: 동시에 1만 개의 에이전트가 돌아가야 한다면, 워커 풀을 늘리기만 하면 됩니다. 상태는 로그에 있으니 워커는 무상태(stateless)에 가깝게 굴릴 수 있습니다.
  • 장시간 실행: 사람의 승인을 며칠 기다리는 에이전트도, 그동안 워커를 점유하지 않고 로그 상태로 '잠들어' 있다가 깨어날 수 있습니다.

여기서 경험 있는 엔지니어라면 데자뷔를 느낄 겁니다. 이것은 Temporal, AWS Step Functions 같은 내구성 워크플로(durable workflow) 엔진이 수년간 풀어 온 문제와 본질적으로 같습니다. 차이는 단 하나, 그 워크플로의 각 스텝이 '사람이 미리 정의한 결정적 단계'가 아니라 'LLM이 런타임에 즉석에서 결정하는 비결정적 단계'라는 점입니다. Agent Executor는 내구성 워크플로의 검증된 사고방식을, 비결정적인 에이전트 시대에 맞게 이식한 시도라고 읽는 것이 정확합니다. 이 흐름은 제가 이전에 다룬 PostgreSQL 기반 내구성 워크플로 글의 문제의식과도 곧장 이어집니다.

4. 기존 에이전트 프레임워크와의 차이

가장 많이 받을 질문은 'LangChain이나 CrewAI랑 뭐가 다르냐'일 겁니다. 핵심은 다루는 계층이 다르다는 점입니다. 비유하자면, 기존 프레임워크가 '요리 레시피'라면 Agent Executor는 '레시피대로 수천 인분을 안 망치고 뽑아내는 주방 운영 시스템'입니다.

구분 조립 프레임워크 (LangChain·CrewAI 등) Agent Executor (런타임)
주 관심사 에이전트를 어떻게 구성·연결하는가 구성된 에이전트를 어떻게 안정적으로 실행하는가
상태 관리 주로 메모리/세션, 직접 영속화 필요 이벤트 로그로 기본 영속화
장애 복구 대체로 사용자 책임 로그 재생으로 내장
관찰 가능성 별도 트레이싱 도구 연동 이벤트 로그가 곧 트레이스

그래서 둘은 경쟁 관계가 아니라 보완 관계일 가능성이 높습니다. LangGraph로 에이전트의 논리 그래프를 그리고, 그 실행을 Agent Executor 같은 런타임 위에 올리는 조합이 자연스럽습니다. 실제로 멀티 에이전트 구성이 복잡해질수록 런타임 계층의 부재가 더 크게 체감되는데, 이 비용 구조는 제가 앞서 분석한 멀티 에이전트의 오케스트레이션 세금과도 맞닿아 있습니다.

5. 신뢰성을 어떻게 보장하는가

에이전트 운영에서 가장 무서운 시나리오는 '부수효과의 중복'입니다. 결제를 호출한 직후 크래시가 나서 재시도했는데, 결제가 두 번 일어나는 식이죠. Agent Executor의 이벤트 모델은 이 문제를 멱등성(idempotency)과 체크포인트로 다룹니다.

각 도구 호출은 '결정(decided)'과 '완료(completed)'라는 두 이벤트로 분리 기록됩니다. 재시작 시 런타임은 로그를 보고 '결정은 됐는데 완료 기록이 없는' 호출을 식별합니다. 이때 무작정 재실행하는 대신, 외부 시스템에 멱등성 키로 결과를 다시 묻거나, 위험한 부수효과는 사람 승인을 거치도록 정책을 끼울 수 있습니다. 이것이 '안전성'이 별도 목표로 명시된 이유입니다. 자동 복구가 오히려 사고를 키우지 않도록, 복구 자체에 안전 장치를 내장한 것이죠.

분산 시스템에서 진짜 어려운 것은 '실패하지 않게 만드는 것'이 아니라 '실패가 일어난 뒤에도 정확히 한 번만 효과가 남도록 만드는 것'이다. 에이전트 런타임도 이 오래된 진실에서 자유롭지 않다.

6. 관찰 가능성과 디버깅의 실무적 가치

현장에서 에이전트를 운영해 본 사람에게 가장 와닿는 가치는 의외로 신뢰성보다 디버깅 가능성일 수 있습니다. 비결정적 에이전트의 버그 리포트는 악몽입니다. '가끔 엉뚱한 답을 한다'는데, 재현이 안 됩니다.

이벤트 로그가 있으면 이야기가 달라집니다. 문제가 된 그 실행의 로그를 그대로 열어, LLM이 어떤 프롬프트를 받았고 어떤 도구를 어떤 인자로 호출했으며 무엇을 반환받았는지를 단계별로 확인할 수 있습니다. 더 나아가 그 로그를 테스트 픽스처로 삼아 회귀 테스트를 만들 수도 있습니다. AI 에이전트 시대의 '재현 불가능한 버그'라는 고질병에 대한, 매우 실용적인 처방입니다.

7. 프로덕션 에이전트 운영의 실무 함의

그렇다면 이 발표가 업계에 던지는 더 큰 메시지는 무엇일까요? 저는 두 가지로 읽습니다.

첫째, 에이전트 논쟁의 무게중심이 '지능'에서 '운영'으로 이동하고 있다는 신호입니다. 2024~2025년이 '얼마나 똑똑한 에이전트를 만드느냐'의 시대였다면, 2026년은 '만든 에이전트를 어떻게 망가지지 않게 굴리느냐'의 시대로 넘어가고 있습니다. 이는 기술이 실험 단계를 지나 프로덕션 단계로 성숙했다는 건강한 신호입니다.

둘째, Google 같은 대형 플레이어가 런타임 계층을 오픈소스로 표준화하려 한다는 점입니다. 모델 경쟁이 어느 정도 평준화된 지금, 차별화의 전장은 '에이전트를 신뢰성 있게 운영하는 인프라'로 옮겨가고 있습니다. 이는 개발자 정체성이 '코드를 짜는 사람'에서 '에이전트라는 harness를 설계·운영하는 사람'으로 이동한다는, 제가 이전 글 Claude Code와 동적 워크플로 harness에서 다룬 흐름과도 정확히 일치합니다.

8. 한국 개발팀 관점의 분석

이제 한국 현실로 내려와 보겠습니다. 글로벌 발표를 그대로 받아들이기 전에, 한국 팀이 따져 봐야 할 지점이 몇 가지 있습니다.

  • 인력 구조: 한국은 전담 ML 인프라 팀을 둔 조직이 많지 않습니다. 이벤트 소싱 기반 런타임은 강력하지만 운영 학습 곡선이 있어, 소규모 팀에는 처음부터 과한 인프라일 수 있습니다.
  • 데이터 주권: 이벤트 로그에는 프롬프트와 도구 입출력이 그대로 남습니다. 금융·통신·공공처럼 규제가 강한 도메인은 이 로그의 저장 위치와 마스킹 정책을 설계 단계에서 못박아야 합니다.
  • 점진적 도입: 전면 교체보다, 가장 길고 비싸고 잘 깨지는 핵심 에이전트 한두 개를 먼저 이 런타임으로 옮겨 효과를 측정하는 파일럿이 현실적입니다.

핵심은 'Google이 냈으니 좋다'가 아니라, '우리 에이전트가 실제로 길고 비싸고 잘 깨지는가'를 먼저 묻는 것입니다. 그렇지 않다면 이 런타임의 이점 대부분은 쓰이지 않는 보험료가 됩니다.

9. 도입 전 점검할 것들

실제 검토에 들어간다면, 신생 오픈소스 특유의 위험을 체크리스트로 챙기길 권합니다.

  1. API 안정성: 초기 버전은 인터페이스가 자주 바뀝니다. 프로덕션 핵심에 깊게 묶기 전에, 추상화 레이어를 두어 교체 비용을 낮추세요.
  2. 저장소 의존성: 이벤트 로그를 어디에 쌓는가(어떤 DB·큐)가 운영 부담의 대부분을 결정합니다. 기존 스택과의 정합성을 먼저 확인하세요.
  3. 비용 모델: 모든 단계를 로깅하면 저장·I/O 비용이 늘어납니다. 로그 보존 기간과 압축·아카이빙 정책을 함께 설계해야 합니다.
  4. 생태계 성숙도: 문서, 예제, 커뮤니티, 기존 프레임워크와의 어댑터가 얼마나 갖춰졌는지가 실제 생산성을 좌우합니다.

10. 한계와 비판적 시선

균형을 위해 반대편도 분명히 짚겠습니다. 이벤트 소싱은 만능이 아닙니다. 첫째, 복잡도 전가 문제가 있습니다. 단순한 에이전트에 이 인프라를 얹으면 얻는 것보다 운영 부담이 더 클 수 있습니다. 둘째, 로그 재생의 함정입니다. 외부 세계는 시간이 지나면 변합니다 — 재생 시점의 API 응답이 원래와 다르면 복원이 어긋날 수 있어, '결정적 재생'은 부수효과의 멱등 처리가 잘 됐을 때만 보장됩니다. 셋째, 벤더·표준 리스크입니다. 지금은 오픈소스지만, 사실상의 표준 자리를 두고 여러 진영이 경쟁할 것이고, 어디에 베팅하느냐가 향후 마이그레이션 비용을 가릅니다.

그럼에도 방향성 자체는 옳다고 봅니다. 에이전트가 장난감을 넘어 비즈니스 크리티컬한 일을 맡는 순간, 신뢰성·복구·관찰 가능성은 선택이 아니라 필수가 됩니다. Agent Executor는 그 필수를 인프라 계층에서 해결하려는, 시의적절한 시도입니다.

결론: 에이전트의 '운영 시대'가 열린다

Agent Executor를 한 문장으로 정리하면, '비결정적 에이전트 루프에 내구성 워크플로의 규율을 입힌 분산 런타임'입니다. 이벤트 소싱이라는 검증된 패턴 위에서 신뢰성·안전성·관찰 가능성을 기본기로 제공하고, 분산 실행으로 확장성과 장애 격리를 더합니다. 화려한 신기능은 아니지만, 에이전트를 실제로 프로덕션에서 굴려 본 사람일수록 그 가치를 알아볼 발표입니다.

마지막으로 실무 권고 세 가지로 마무리합니다. 첫째, 지금 운영 중인 에이전트가 '길고 비싸고 잘 깨지는가'를 먼저 자문하세요 — 그렇다면 런타임 계층 도입의 1순위 후보입니다. 둘째, 전면 교체 대신 핵심 에이전트 하나로 파일럿을 돌려 복구·관찰 가능성의 실제 효과를 측정하세요. 셋째, 이벤트 로그의 저장 위치·보존·마스킹 정책을 설계 단계에서 못박으세요 — 운영 비용과 규제 리스크의 대부분이 거기서 갈립니다. 모델 경쟁의 시대가 저물고, 에이전트 '운영'의 시대가 막 열리고 있습니다.
