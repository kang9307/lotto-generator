きっかけ - 「45分ごと」ではなく「0分と45分に」

GeekNewsで紹介されたcron.withuse.ioの記事は、タイトルがそのまま結論になっている。cronの*/45は45分間隔ではないというのだ。GeekNewsの要約によれば、この式は45分と15分の間隔が交互に現れるように実行され、一定の45分周期にはならない。同じサイトのFAQには、この原理を一文で書いた箇所がある。「stepはスラッシュの前の範囲に適用されるのであって、時計に適用されるのではない」。

この落とし穴が長く生き残るのは、式の見た目が読み手の直感とちょうど逆だからだ。*/5が5分ごと、*/15が15分ごとなら、*/45も45分ごとだろうと推論してしまう。前の二つが合っているのは、5と15がたまたま60を割り切る数だからであって、cronが「N分ごと」を約束しているからではない。この記事はその偶然を取り除いて、規則そのものを書く。規則が分かれば、*/45だけでなく、*/7、0 */5、0 0 */10のように同じ構造の落とし穴を、式を見ただけで拾い出せる。

文法のチュートリアルがこの記事の目的ではない。扱うのは三つである。stepが実際に何をするかの定義、その定義を実行して検算した結果、そして45分間隔が本当に必要なときに使える方法だ。実装ごとに動作が同じかどうかは、最後にドキュメントで確認できた範囲とそうでない範囲に分けて書く。

stepは何をするのか - フィールド内で開始値の倍数を選ぶ

cronieのドキュメント(crontab(5))はstepをこう定義する。範囲の後ろにスラッシュと数を付けると、その範囲をその数だけ飛ばしながら進む。例は時フィールドの0-23/2で、二時間に一回である。そしてすぐ続けて、この記事の主題になる文が来る。stepは、それが適用されたフィールドの中だけで評価される。ドキュメントの例は時フィールドの*/23で、これは暦の一日のうち0時と23時に実行するという意味だ。同じドキュメントは、分フィールドの*/35が35分間隔ではなく、毎時0分と35分に実行される例も挙げている。

この定義をほどくと次のようになる。

  • 範囲が先である。アスタリスクはそのフィールドの全範囲(分は0〜59、時は0〜23)を意味し、stepはその範囲を開始値から飛ばしていく。
  • 計算はフィールドの中で終わる。分フィールドのstepは時の境界を越えて続かない。毎時0分からやり直す。
  • 結果は開始値の倍数である。開始値が0なら、0、N、2N、…のうち範囲に入る値だけが残る。「N分ごと」ではなく「Nの倍数の時刻ごと」である。
  • 残る値は境界で分断される。範囲の長さがNの倍数でなければ、最後の値から次の範囲の開始値までの間隔がNより短くなる。

四つ目の項目が*/45の正体である。分の範囲0〜59を45ずつ飛ばすと0と45が残り、次は90で範囲を外れる。時計が次の時に入って0分が来ると、計算は最初からやり直しになる。だから0分から45分までは45分、45分から次の時の0分までは15分という二つの間隔が交互に現れる。systemd.timeのドキュメントも同じ構造の定義を置いている。値の後ろにスラッシュと繰り返し値を付けると、その値自体と、その値に繰り返し値の倍数を足した値が一致する。範囲に付ければ、開始値から出発して終端値を超えない倍数が一致する。表記は違うが、「範囲内で開始値を基準にした倍数」という定義は同じだ。

実行による検証 - Pythonで範囲を展開した結果

定義が正しいかどうかは手計算でも確かめられるが、式が多くなると間違いが入り込む。次のスクリプトは、crontabに触れずにフィールドの範囲をrangeで展開し、隣り合う実行時刻の間隔を計算する。Python 3.13で実行し、負荷はない。スクリプトは範囲に対する整数の計算だけを行うので、結果は実行する機械に依存しない。最後の二つのブロックは、*/45の一日分と、正確な45分間隔を作る四行の構成(7節)を検算する。

import calendar
                    
                    # 一つのフィールド範囲内でのstep展開 (crontabには触れない)
                    def expand(lo, hi, step):
                        return list(range(lo, hi + 1, step))
                    
                    # 隣り合う実行の間隔。次の周期へ越える区間を含む
                    def gaps(vals, period):
                        g = [b - a for a, b in zip(vals, vals[1:])]
                        g.append(vals[0] + period - vals[-1])
                        return g
                    
                    cases = [("*/15 * * * *", 0, 59, 60, 15), ("*/20 * * * *", 0, 59, 60, 20),
                             ("*/45 * * * *", 0, 59, 60, 45), ("*/40 * * * *", 0, 59, 60, 40),
                             ("*/25 * * * *", 0, 59, 60, 25), ("*/7 * * * *", 0, 59, 60, 7),
                             ("0 */8 * * *", 0, 23, 24, 8), ("0 */5 * * *", 0, 23, 24, 5),
                             ("0 */7 * * *", 0, 23, 24, 7)]
                    for expr, lo, hi, period, step in cases:
                        v = expand(lo, hi, step)
                        print(expr, v, sorted(set(gaps(v, period))))
                    
                    # */45の一日分: 時刻、間隔、一日の実行回数
                    mins = [h * 60 + m for h in range(24) for m in expand(0, 59, 45)]
                    print([f"{t // 60:02d}:{t % 60:02d}" for t in mins[:6]],
                          sorted(set(b - a for a, b in zip(mins, mins[1:]))), len(mins), 1440 // 45)
                    
                    # 日フィールド: 2026年4月・5月・2月の0 0 */10
                    days = expand(1, 31, 10)
                    for m in (4, 5, 2):
                        n = calendar.monthrange(2026, m)[1]
                        d = [x for x in days if x <= n]
                        print(m, d, d[0] + n - d[-1])
                    
                    # 四行で作る正確な45分間隔 (3時間周期、日付をまたぐ区間を含む)
                    lines = [(0, (0, 21, 3)), (45, (0, 21, 3)), (30, (1, 22, 3)), (15, (2, 23, 3))]
                    t = sorted(h * 60 + m for m, (a, b, s) in lines for h in expand(a, b, s))
                    print(sorted(set(y - x for x, y in zip(t, t[1:] + [t[0] + 1440]))), len(t))

結果から読み取れることは次のとおりである。

  • 三行目が*/45である。分の値は0と45だけで、間隔の集合は{15, 45}になる。45分は一種類の間隔ではないという意味だ。
  • 十行目が一日分である。時刻表は00:00、00:45、01:00、01:45と続き、一日の実行回数は48回になる。本当の45分周期なら1,440分を45で割った32回のはずなので、実際には五割多く動く。
  • cronieのドキュメントが挙げた時フィールドの*/23も、同じ関数で展開すると[0, 23]になる。ドキュメントの記述とスクリプトの規則は食い違わない。
  • 最後の行は正確な45分間隔の構成である。間隔の集合は{45}ただ一つで、実行回数は32回になる(7節)。

一般則 - stepが約数のときと、そうでないとき

上の結果を一般化すると、判定式は一つに縮まる。フィールドの値の個数(分は60、時は24)がstepで割り切れれば、境界を越えても間隔が保たれ、割り切れなければ、境界で短い間隔が一度割り込む。表は同じスクリプトの展開結果を式ごとに整理したものだ。間隔が二つ以上の値をとる場合は順に書いた。

式実際の実行時刻間隔落とし穴
*/15 * * * *毎時0・15・30・45分15分で一定—
*/20 * * * *毎時0・20・40分20分で一定—
*/45 * * * *毎時0・45分45分と15分が交互あり
*/40 * * * *毎時0・40分40分と20分が交互あり
*/25 * * * *毎時0・25・50分25分、25分、10分あり
*/7 * * * *毎時0・7・14・…・56分(9回)7分が8回、4分が1回あり
0 */8 * * *0・8・16時8時間で一定—
0 */5 * * *0・5・10・15・20時5時間が4回、4時間が1回あり
0 */7 * * *0・7・14・21時7時間が3回、3時間が1回あり
0 0 */10 * *1・11・21・31日10日間隔、月末でずれるあり

表から目に留まる規則は三つある。

  • 分フィールドで安全なstepは、60の約数である1、2、3、4、5、6、10、12、15、20、30だ。これらの値はどの時刻でも同じ間隔になる。
  • 時フィールドで安全なstepは、24の約数である1、2、3、4、6、8、12だ。5や7は一時間単位のように見えるが、一日の終わりで短い間隔が割り込む。
  • 約数でない値は、「何分ごと」ではなく「一日(または一時間)のうちNの倍数の時刻ごと」と読まなければならない。この読み方を習慣にすれば、式を見ただけで落とし穴に気づける。

stepが範囲の長さに近づくほど、ずれは際立つ。45分は60分に近いので、余りの断片が15分にもなり、結果は「ときどき短い間隔が入る」程度ではなく、実行回数が一日32回から48回へ1.5倍になる。この差は、負荷のある作業、外部APIの呼び出し、課金が発生する作業では、そのままコストと上限に跳ね返る。回数で予算を管理しているチームは、スケジュールよりも先に上限の消費でその差に気づく。

時・日フィールドではずれがより大きく現れる

分フィールドのずれは一時間の中で終わるので目立たない。時フィールドと日フィールドは違う。0 */5 * * *は0、5、10、15、20時に動き、20時の次の実行は翌日の0時なので、最後の間隔だけが4時間になる。「5時間ごとに動く」と信じた運用者は、20時の実行の4時間後である深夜0時に、予期しない実行に出会う。問題が真夜中付近で起きるため、昼間に確認すると見逃す。

日フィールドにはもう一つ特徴がある。日フィールドの範囲1〜31は、月によって実際の長さが違う。0 0 */10 * *は1、11、21、31日を選ぶが、その月に31日がなければ、21日の次の実行は翌月1日になる。上のスクリプトが2026年の三か月で計算した値は次のとおりである。

2026年の月実行される日最後の実行から翌月の最初の実行まで
4月(30日)1・11・21日10日
5月(31日)1・11・21・31日1日
2月(28日)1・11・21日8日

5月には、31日の実行から一日後の6月1日にまた実行される。「十日ごと」を期待した作業が、月末に二日連続で動くことがあるという意味だ。月フィールドの*/5も、範囲1〜12で1月、6月、11月だけが残り、11月の次は翌年の1月なので、二か月の間隔が割り込む。

こうしたずれは「誰のせい」でもなく、stepが時計ではなくフィールドに付くという定義の帰結である。だから代替策も、式をさらに書き直すことにはなく、フィールド内の倍数計算とは別の基準を使うことにある(7節)。

実装ごとに同じか - ドキュメントで確認できた範囲

cronという名前のもとには実装が複数あり、スケジューラが違えば式の意味も違いうる。この記事が公式ドキュメントから直接文を確認した範囲は、下の表のとおりである。確認できなかった実装は「—」のままにし、理由は後の「確認できなかったこと」に書いた。

正確な45分間隔が必要なら

本当の45分周期が必要なときに使える方法を、根拠の種類に応じて三つに分ける。

1. systemd timerの相対タイマー(ドキュメントで確認)。systemd.timerのドキュメントで、OnUnitActiveSec=は、タイマーが起動するユニットが最後に起動された時刻を基準にしたタイマーである。OnUnitActiveSec=45minと書けば、時計の時刻とは無関係に、最後の実行から45分後に次の実行が来る。ドキュメントはOnUnitInactiveSec=も併せて定義していて、こちらは最後に停止された時刻が基準になる。実行にかかった時間が間隔に含まれるかどうかが二つのオプションの違いであり、どちらを使うかは作業の所要時間が変動するかに左右される。最初の実行時点を決める他のオプションとの組み合わせは、この記事では検証していない。

2. cronだけで作る四行(計算で検証)。45分と24時間の最小公倍数は180分、つまり3時間である。3時間周期の中に実行時刻が四つ(0:00、0:45、1:30、2:15)あるので、四行に分けて書けばよい。

  • 0 0-21/3 * * * — 0時、3時、…、21時の0分
  • 45 0-21/3 * * * — 0時、3時、…、21時の45分
  • 30 1-22/3 * * * — 1時、4時、…、22時の30分
  • 15 2-23/3 * * * — 2時、5時、…、23時の15分

上のスクリプトの最後のブロックが、この四行が作る時刻を展開し、日付をまたぐ区間(23:15から00:00)まで含めて隣り合う間隔を計算した。結果は間隔の集合が{45}ただ一つで、一日32回である。この方法は時刻の境界に噛み合う時計基準のスケジュールなので、夏時間のある時間帯や時刻が飛ぶ環境までは検証していない。行が四つに増えるため、管理の負担も増える。

3. 作業の中で時刻を検査する(一般的な設計で、ドキュメントの根拠はない)。短い周期(たとえば毎分)でスクリプトを起こし、スクリプトが最後の成功時刻をファイルに記録しておいて、45分が経っていなければすぐ終了する方式である。この記事が引用したドキュメントには、この方式は書かれていない。特徴は、どのスケジューラでも使えることと、間隔を保証する責任が式からスクリプトに移ることだ。ロックと記録ファイルの更新失敗は、スクリプトが引き受けなければならない。

三つの方法の選び方は単純である。systemd環境なら一つ目が最も直接的だ。式しか使えない環境なら、45分にこだわらず60の約数(30分または60分)に変えるのが最も安全で、45分間隔の意味が本当に必要なら、二つ目か三つ目を使う。

既存のcrontabから落とし穴を探す読み取り専用の点検

すでに運用中のサーバーのcrontabには、同じ落とし穴が残っているかもしれない。以下の点検はすべて読み取り専用で、負荷はない。

  • crontab -lで、現在のユーザーの登録内容を出力するだけにする。編集オプション(-e)は使わない。
  • */Nの形の式を集めて、Nが分フィールドでは60の約数か、時フィールドでは24の約数かを見る。
  • 約数でないものは、上の表の方法で実際の実行時刻を展開し、作業の意図(正確な間隔なのか、単なる頻度なのか)と比べる。
  • 日フィールドや月フィールドの*/Nは、約数かどうかにかかわらず月末・年末で間隔が揺らぐので、別に印を付ける。
  • 展開結果が意図と違うなら、式を直す前に、その作業が正確な間隔を求めるのかをまず決める。求めないなら、60の約数に変えるだけで足りる。

点検の結果は記録に残す。どの式がどんな実際の時刻を作り、なぜそのままにしたのかが残っていれば、次の担当者が同じ論理を最初から繰り返さずに済む。
