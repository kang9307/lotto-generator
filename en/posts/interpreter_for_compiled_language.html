Adding Interactive Execution to a Compiled Language

What changes when the round trip disappears, and where the two executions diverge

Aug 25, 2026 Dev & Infra

Making a File Just to Check One Line

Does this function return the part before the separator or the part after it. What do the field names look like when this struct is marshalled to JSON. The answer takes thirty seconds, but getting to it means creating a scratch directory, writing a main function, running a build, and deleting all of it afterwards. Repeated several times a day, that round trip is less a waste of time than a break in your train of thought.

Which is why attempts keep appearing to bolt interactive execution onto languages that were designed around compilation. The one that resurfaced recently is the Go interpreter gomacro. It offers a REPL and script execution, and on top of that it adds macros, which Go does not have.

This is not a how-to for that tool. There is one question here: when you add interactive execution to a compiled language, what opens up and what gets billed in return? The bill does not arrive as performance; it arrives somewhere else. Putting a different language on the Go runtime was covered in glojure: Clojure Interpreter on Go Runtime — Why It Exists and What It Solves 2026, and how a language's syntax changes verification cost in Language Properties That Lower the Verification Cost of AI-Generated Code - Five Traits Go Has and What They Cost. The condition that differs here is that one language ends up with two ways of executing.

What gomacro Is - The Confirmed Scope as of August 2026

The repository introduces it as an almost complete Go interpreter implemented in pure Go. It supports both an interactive REPL and script execution, and it does not require the Go toolchain at runtime except when importing third-party packages. Go 1.18 or newer is required, and it is distributed under MPL 2.0.

The interesting part is that it adds things standard Go does not have. The repository lists these as extensions.

  • An integrated debugger and configurable special commands
  • Untyped constants can be manipulated directly at the REPL, with implicit conversion to *big.Int, *big.Rat and *big.Float
  • Zero value constructors — writing T() yields the zero value of that type
  • Macros, quoting and quasiquoting — code generation machinery inherited from the Lisp family
  • Unused variables and unused return values never cause errors

Generics are still experimental. Two different implementations ship together: one modelled on C++ templates, the other the CTI approach that treats contracts as interfaces, which is the default. It uses syntax such as Pair#[T,U]. The constraints the repository currently states are these.

  • There is no type inference for generic arguments
  • Generic methods cannot be defined
  • Types are not validated against contracts

The word worth staring at in that description is almost. The rest of this article is effectively about that single word.

What a REPL Actually Changes

It is easy to assume that removing the round trip saves time. What actually changes is the unit of exploration.

When edit, build and run form one expensive lump, people change several assumptions at once. You are only going to run it once anyway, so you fix this and that in the same pass. And then when the result comes back, you do not know which change produced it. When the round trip becomes nearly free, you change one thing at a time instead. Causes get easier to isolate not because the tooling got smarter but because the human behaviour changed.

The second thing that changes is state. Run a file and you start from scratch every time. In an interactive session, the value you built on the previous line is still there and the next line runs on top of it. Anything expensive to construct — a parsed document, an open connection, a large data structure you filled in — can be built once and poked at many times. The bigger the subject, the bigger this difference gets.

  • The unit of exploration shrinks — one assumption verified at a time, so causes are isolated
  • Expensive setup is reused — you touch only the part you care about, repeatedly
  • Wrong attempts cost almost nothing — you can type an expression you are not sure about
AxisEdit-build-run round tripSession that keeps state
Assumptions changed per passSeveral (because the trip is expensive)One (because the trip is cheap)
Setup costPaid again on every runPaid once per session
Price of failureBuild time plus a broken train of thoughtNearly zero
What survivesA file — committable, reviewable, rerunnableScrollback — gone when the session ends
Execution semanticsThe code that will actually shipAn approximation of it

The last two rows of that table are the other half of this article. What you gain is definite, and so is what you give up.

Why Compiled Languages Resist Interactivity

A REPL feels natural in Python or Ruby because those languages were designed to execute one fragment at a time to begin with. Compiled languages stand on the opposite premise: see everything at once, fix it in place, and optimize on top of that certainty. Every obstacle comes out of one of those three.

Static typing - declaration and use come apart in time

A compiler sees the whole package simultaneously. Function a calling b further down the file is not a problem because both are already in front of it. In a REPL, a arrives first and b does not exist yet. So do you reject the definition of a, or accept it and hold it?

Java's JShell faced this head-on and chose accept it but block the call. The official documentation gives support for exploratory programming as the reason it accepts method definitions referencing things not yet defined.

jshell> double volume(double radius) {
   ...>    return 4.0 / 3.0 * PI * cube(radius);
   ...> }
|  created method volume(double), however, it cannot be invoked until variable PI,
   and method cube(double) are declared

The second problem is redefinition. If x was declared an integer and is then redeclared as a string, what happens to the earlier function that used that x? JShell grades this as modified, replaced or overwritten, and warns when an incompatible redefinition breaks a dependent definition. A REPL for a compiled language has to invent rules like these with no help from the language specification. That is already the point where the language and the tool begin to diverge.

Package initialization - there is no moment called start

In Go, package-level variable initialization and init functions run exactly once, in a determined order, when the program starts. The order follows the dependency graph, and code that leans on that order genuinely exists.

An interactive session has no such start. If the user adds one more import twenty minutes in, initialization runs at that moment, which for a program would have finished long before. Code that depends on initialization order, libraries that register global state, imports taken purely for their side effects — all of these acquire room to behave differently here.

Linking - pulling in new code mid-run means breaking the certainty

Go's standard artefact is a single statically linked binary. Which symbol lives where is nailed down at build time. Pulling in a new package while running means pulling that nail out.

The route gomacro takes is this. On Linux, macOS and *BSD it internally compiles and loads a single Go plugin containing the exported declarations of all the packages listed in import ( ... ). Which means the Go toolchain is required at that moment, and the conditions attached to the standard library's plugin package come along with it.

  • Plugins are supported only on Linux, FreeBSD and macOS, which makes them unsuitable for programs meant to be portable
  • The application and its plugins must be built with the exact same toolchain version, build tags and environment variables, and common dependencies must come from identical source
  • A plugin is initialized once when first loaded and cannot be closed or unloaded
  • Race detector support is poor, so even simple races may not be detected automatically

The third item stings the most. Exploring by swapping imports around collides head-on with a mechanism that cannot be unloaded once it is up. The standard documentation itself says that in practice the application and its plugins must all be built together, and suggests interprocess communication such as sockets or RPC as the alternative. This is not laziness in an interpreter implementation; it is a constraint that falls out of where Go sits.

Optimization assumptions - optimization changes what is observable too

A compiler performs inlining, escape analysis and bounds check elimination on the assumption that it knows the whole program. An interpreter cannot establish that assumption and therefore cannot do the same work. So far this is a story about speed, and speed is not what this article is about.

The real issue is that optimization does not only change speed. Whether a value sits on the stack or escapes to the heap changes memory behaviour, and whether a function is inlined changes the shape of a stack trace. Optimization preserves the program's result values but does not preserve what the program observes about itself.

Where Interpreted and Compiled Execution Diverge

Putting the limitations the repository states itself next to compiled Go gives this.

Recursive typesCompleteSome corner cases may not work correctly
gotoBoth directionsCan only jump backward
Unused variables and returnsCompile errorNot an error

Where mostly the same becomes most dangerous

The rows split into two kinds. Most of the upper ones are cases where the interpreter is narrower: something that works in compiled Go does not work here. Differences like that are safe, because trying them fails on the spot.

The dangerous kind is the last row, where the interpreter is wider. Unused variables not being errors is clearly convenient while you are poking around, but inverted it means code that would not compile under standard Go passes here. The inference it worked there so it will work here does not hold. And because differences of this kind do not fail, you cannot notice them at the time.

  • Concurrency — the limitations list says nothing about the scheduling characteristics of goroutines, channels or select. The absence of a mention is not a guarantee of sameness; it means the question was not addressed. Races depend on timing, and a different execution model means different timing. The fact that a race did not show up in the interpreter proves nothing.
  • Reflection — code that inspects type information at runtime is sensitive to who built that information and how. Public documentation offers no guarantee that interpreted types and compiled types look identical to reflection
  • unsafe — pointer conversion is explicitly unsupported. Explicit constraints are the easy kind. What runs quietly differently is always more expensive
  • Build tags — the mechanism that decides which files enter the build. If an interpreter reproduces that decision differently, the same source tree executes different code

So there is only one rule worth fixing. Passing in the interpreter does not substitute for passing a compiled build. The reverse holds as well. Neither execution is a proxy for the other.

When an Interpreter Adds What the Language Lacks

This is the core of the article. In the extension list above, macros and quasiquoting, the custom generic syntax and arbitrary-precision arithmetic on untyped constants are features standard Go does not have. And every one of them is genuinely useful.

Macros especially. Go deliberately left macros out, and because of that absence code generation has been pushed into go:generate and separate programs. Writing a generator, wiring it into the build, committing the output — that entire procedure is the price paid for not having macros in the language. Being able to do it inside the language instead is real power.

But the moment you use that power, that code runs only in that interpreter. go build will not take the source, because the syntax is not Go. And the value of interactive execution lies in the flow where you explore, learn something, and carry it into a program — extensions cut that flow.

  • Stay within the standard Go subset — what you learn transfers directly. In exchange the interpreter never becomes more than a fast-check tool
  • Use the extensions — far more powerful in place. In exchange the code is bound to the tool, and the tool's lifespan becomes the code's lifespan

This is not a defect of one project. It is the price every tool pays for adding, from outside the language, what the language does not have. Macros feel natural in the Lisp family because macros are part of the language and the compiler sees the same thing. Add them from outside and that agreement breaks, leaving source that only one of two implementations will accept.

The same boundary problem appears in the other direction too. The documentation for evcxr, Rust's interactive tool, states that there is currently no way to import macros from external crates. Bringing a language's features fully into a REPL is hard, and getting features the language lacks back out of a REPL is hard.

So the deciding criterion is neither performance nor syntax taste. Is the code you are typing consumed within one session, or saved to a file? If the former, extensions are cheap, use them freely. If the latter, it has just become source for a new language with exactly one implementation, and it gets harder to move with every passing month.

As a Debugger, the Requirements Are Different

gomacro is also used as a source debugger and ships an integrated one. There are three ways in: pressing CTRL+C while interpreted code is running, typing :debug STATEMENT at the prompt, or putting a break string in the code. The debugger accepts step, next, finish, continue, env, inspect, list and print.

The same engine wears two hats, but the two roles want different things and to some degree they obstruct each other.

  • Script execution wants speed and semantic fidelity — run fast, and produce what compilation would have produced
  • Debugging wants suspension and observation — stop anywhere, see every local at that instant, advance one line at a time

The standard answer in compiled languages is a compiled binary carrying debug information with an external debugger attached. Observation is more cumbersome, but the thing under observation is the code that will actually ship. The interpreter debugger's answer is the opposite. An interpreter is already walking node by node, so stopping needs no special machinery and local state is already in hand. In exchange, the thing under observation is not the code that will ship.

Which is why the bugs you catch split. Errors of the I wrote this logic wrong kind are caught perfectly well by an interpreter debugger. Errors that come from execution characteristics — races, scheduling, memory layout, interactions with optimization — are not, because those bugs exist only in the compiled artefact. Not because the tool is weak, but because what it is observing never had the bug to begin with.

Where It Is Worth Using

Starting with the places where the value is unambiguous.

  • Learning — the benefit is largest for someone learning the language. Needing a file and a build to check the return order of one standard library function is a tax on learning. Oracle pinning JShell down in its opening sentence as a tool for learning and prototyping sits in exactly the same place
  • Exploration — getting the feel of an unfamiliar library. There are definitely cases where poking at values beats reading documentation
  • Prototyping — pinning down something whose shape is not settled yet
  • Configuration and automation scripts — using Go syntax without leaving a build artefact behind. This is also the place to be most careful: scripts get saved and rerun, so the semantic gaps from the earlier sections bite harder as time passes
  • Embedding — putting it inside a program to accept user-defined logic. One of the uses the repository lists

Conversely, putting it on a production execution path is not something this article recommends. That is not a judgment on quality. It is that the material needed for the decision — how far concurrency semantics match, how memory behaves under long runs, what policy governs compatibility across versions — is not established by public documentation alone.

Precedents - Where Such Tools Stuck and Where They Did Not

This is not the first attempt to attach interactive tooling to a compiled language. The ones that stuck have something in common.

ToolLanguageWhere it stuckThe line its docs draw
JShellJavaLearning and prototyping, shipped inside the JDKStates itself that it does not replace an IDE
evcxrRustNotebooks and interactive explorationIf the code dies the process restarts and all variables are lost
gomacroGoREPL, scripting, embedding, source debuggingThird-party imports are platform-bound and generics are experimental

The evcxr constraint is especially telling. The documentation says that if code terminates abnormally the process it runs in is restarted and all variables are lost, and it also notes that persistent variables cannot reference other variables. The property listed earlier as a REPL benefit — state survives — turns conditional once it meets how a language handles memory safety and ownership. Interactivity is not a property you can bolt on independently of the language's own properties.

What the tools that stuck have in common converges on one thing.

  • They come from the same place as the language implementation — JShell inside the JDK, Haskell's GHCi inside the compiler distribution. Versions move together, so the room for semantics to diverge shrinks structurally
  • A separate project has no such advantage — when the language changes it must chase, and whatever it fails to catch becomes semantic divergence. Generics entering the language in Go 1.18 while the interpreter's generics remain experimental shows that structure exactly

That said, being a separate project also makes some things possible. Features the language deliberately left out, such as macros, are exactly what an official tool would never add. The portability bill from the previous section is the flip side of that freedom.

The Other Side - When Compiling and Running Is Still Right

There is a reason this round trip is unusually bearable in Go. Builds are fast, a test runner ships as standard, you can select a single test by name, and example functions double as documentation and tests. In other words, the path from a throwaway check to a permanent asset already exists inside the language.

  • When the verification has to survive — a test file remains, a session does not. For the fact that you checked to still be useful to the next person, it has to be a file
  • When the result depends on execution characteristics — concurrency, performance, memory. For the reasons above, an interpreter result is not a proxy
  • When the team has to see it — session logs are not review material
  • When build tags or platform-specific code are involved — if which files actually enter the build is the question, look at a real build

Conversely, the places interactive execution clearly wins are narrow and clear.

  • A check whose answer is used once and thrown away
  • Work that involves poking repeatedly at something expensive to set up
  • Finding out what an unfamiliar API returns and in what order

Summed up, the decision splits on the lifespan of the result. If it will survive, a file; if it will be discarded, a session. And note that a REPL is a convenience rather than a capability — everything you were doing still works without it, which makes it something to weigh against the cost of one more dependency.

What Could Not Be Confirmed

The following did not resolve from public documentation alone, and this article does not fill them in by estimation.

  • How far the semantics match between interpreted and compiled execution. The limitations list is public, but nothing guarantees that list is exhaustive
  • The scheduling characteristics goroutines, channels and select have under the interpreter. The limitations list does not mention them
  • How build tags and conditional compilation are handled
  • Performance. No benchmark was verified for this article, and no multiplier against compiled execution is offered
  • Memory and isolation characteristics when embedded, and behaviour under long-running use
  • The difference in maturity between the two generics implementations and which one survives

There is no substitute for measuring with your own code, and that fact is itself a reason to defer any adoption decision.

Conclusion: Code That Stays or Code That Goes

Adding interactive execution to a compiled language is not bolting on one more convenience. It is making a single source carry two execution semantics. The reason those two are hard to make identical is not that the implementation is unfinished but that compilation, as a stage, does what it does — see everything, fix it, optimize it. However hard an implementation is pushed, the gap remains as long as those three are kept.

Still, the gain is real. And it is not the time saving people usually cite but the shrinking of the unit of exploration. Verify one assumption at a time and causes get isolated.

The bill arrives somewhere equally definite. The moment you use a feature the language lacks, that code cannot leave. Used with that line in view it is a tool; used without it, it becomes an asset you cannot move later. So there is only one thing to settle. Is the code you are typing right now code that stays, or code that goes? Once that is answered, how far to take the tool is answered with it.
