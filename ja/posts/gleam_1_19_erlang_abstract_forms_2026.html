きっかけ — 「Erlangソースにコンパイルしない」が指す範囲

Gleam公式サイトは2026年10月5日、v1.19.0の発表記事を「Gleam doesn't compile to Erlang source anymore」という題で公開し、GeekNewsには10月6日に紹介された。題が述べる変化は一文に収まる。以前のGleamはErlangソースコードを生成しており、現在はErlang abstract formsを生成する。発表記事によれば、Giacomo Cavalieriがここ数か月をかけてErlangコードジェネレータを全面的に書き直し、新しいジェネレータは設計が異なり、出力形式も異なる。

題だけを読むと範囲を広く取りやすい。変わったのは、Erlangターゲットのコードジェネレータが出す形式である。GleamはErlang仮想マシンとJavaScriptランタイムの両方を対象とする言語であり、発表記事はJavaScript側の変更を別の節で扱っている。Erlangコンパイラが外れたわけでもない。発表記事はこの変化を、Erlangコンパイラにソースコードを渡す方式から、Erlangコンパイラに中間表現を渡す方式へ移ったものだと記している。バイトコードを作る仕事はこれまでどおりErlangコンパイラが担う。

したがって見るべきは、あるコンパイラが別のコンパイラに何を渡すのかである。渡すものが人の読むテキストから木構造の中間表現に変わると、受け取る側の仕事、エラー位置の基準、生成物の扱い方がそろって変わる。GleamがBEAMの上で型の境界をどこまで動かしたかは別の軸であり、BEAMの上に静的型を載せるという選択にまとめてある。

abstract formsとは何か — Erlangドキュメントの定義

発表記事はabstract formsを、Erlangコンパイラが使う中間表現として紹介する。Erlangの構文を表すメタデータ付きの木であり、通常はErlangのトークナイザとパーサを実行して作られるという説明である。Erlang/OTPのドキュメントは同じものをabstract formatと呼び、v1.19のchangelogもこの変更をErlang Abstract Formatという名前で記している。

Erlangドキュメントの「The Abstract Format」（OTP 29.1.1）が述べる内容は次のとおりである。

  • 定義。Erlangプログラムの構文木をErlangの項（term）として表す標準表現である。
  • モジュールの形。モジュール宣言はformの並びであり、各formは関数宣言か属性のいずれかである。属性-module(Mod)は{attribute,ANNO,module,Mod}として、関数宣言は{function,ANNO,Name,Arity,[Rep(Fc_1), ...,Rep(Fc_k)]}として表される。
  • ANNO。表現の随所に入るANNOは注釈（annotation）であり、いくつかの情報のうち、その構文が現れたソースファイルの行番号を表す。詳細はerl_annoモジュールのドキュメントにある。
  • 扱う関数。compile:forms/1,2と、epp、erl_eval、erl_lint、erl_parse、erl_pp、ioの各モジュールの関数がこの構文木を扱う。パース変換（parse transform）の入力と出力としても使われる。
  • デバッグ情報との関係。コンパイルオプションdebug_infoを指定すると、abstract codeがデバッグ用途でBEAMファイルの中に保存される。

erl_annoのドキュメントは、注釈に入る項目を列挙している。トークンが始まる列（column）、行と列を合わせた位置（location）、トークンのテキスト（text）、そこから導かれる行（line）があり、そのほかにファイル名（file）や、コンパイラが生成したコードであることを示す真偽値（generated）などがある。ドキュメントは、generatedと印の付いたコードに対してErlangコンパイラは警告を出さないと記している。発表記事の言う位置メタデータとこのANNOを重ねて読むと、後で見るエラー位置の変化は、この欄にどのソースの行を入れるかという問題として読める。

発表記事はもう一点を加えている。abstract formsにはErlangのexternal term formatを使ったバイナリエンコーディングがあり、このバイナリ形式で生成したコードを直接ロードして、Erlangコンパイラの前半を省くというものである。Erlangのドキュメントでは、external term formatは主にErlangの分散機構で使われる形式であり、項をこの形式に変換する組み込み関数がerlang:term_to_binary/1,2、元に戻す関数がerlang:binary_to_term/1である。ドキュメントは、すべてのErlangの項が外部表現を持つと記している。abstract formatはErlangの項でできた構文木であるから、この形式でエンコードできる。

以前と以後のパイプライン — 誰が何を作り、何を省くのか

発表記事とchangelogに書かれた内容で前後を並べると下の表になる。左の列は、ベンチマークの比較基準であるv1.17.0である。発表記事は書き直しの第一段階がすでにv1.18.0でリリースされたと明かしており、そのため前後の比較にv1.17.0とv1.19.0を使っている。

表から読み取れる点は三つある。第一に、減ったのはErlangコンパイラ全体ではなく前の部分である。発表記事はErlangコンパイラに数十年かけて実装された最適化に触れており、その部分はそのままErlangコンパイラが受け持つ。第二に、省かれた段階は、ソーステキストを再び木に戻す仕事である。言い換えると、Gleamコンパイラがプログラムをテキストとして書き出し、Erlang側がそのテキストを読み直して木を作るという往復がなくなった。第三に、位置情報の基準が変わった。Erlangのcompileモジュールのドキュメントは、Erlangソースコードを渡す経路の主な欠点として、Erlangコードの各行を元のソースファイルの対応する行へ対応付けることが難しいか不可能であることを挙げている。

発表記事が新しいコードジェネレータの利点として挙げるのは四つである。

  • コンパイラの性能が向上し、Erlang上で動くGleamプロジェクトのビルド時間が大きく短くなった。
  • ランタイムが利用できる位置メタデータが、コンパイラが生成していたErlangソースではなく、元のGleamソースに合う。
  • Gleamコンパイラのコード品質が向上した。Erlangコードジェネレータはコードベースの中で最も古く安定した部分の一つで、問題を起こしてはいなかったが、現在の基準と慣習には合っていなかったという説明である。
  • 「トランスパイラ」という言葉がさげすむ意味で使われるのを、もう聞かなくて済む。脚注の付いた項目である。

四つ目の項目の脚注はこの主題に関わる。発表記事はトランスパイラを、ソースコードのように人が読める形式を出力するコンパイラと定義し、人が読める形式にコンパイルするからといってコンパイラの実装が易しくなるわけではないと記している。出力をきれいに整形したいのであれば、バイナリ形式を使うよりかえって難しいかもしれないという文が続く。

Erlangドキュメントが他言語の実装者に示す四つの経路

この選択肢はGleamだけのものではない。Erlangのcompileモジュールのドキュメントには「Recommendations for Language Implementors」という節がある。Erlangランタイムシステムの上で動く他の言語のコンパイラは、たいていファイルかバイナリを作ってErlangコンパイラに渡すという前提に立ち、文書化された機能でそれを行う方法を四つ挙げている。

渡すものドキュメントの記述ドキュメントに書かれたコンパイル方法
Erlangソースコード（.erl）最も単純で移植性が高い。主な欠点は、Erlangコードの各行を元のソースファイルの対応する行へ対応付けることが難しいか不可能であることcompile:file/2またはerlc <FILE>.erl
abstract formatすべてのErlangソース行を元のソースファイルの対応する行へ対応付けることをサポートするcompile:forms/2に項の表現を直接渡すか、.abstrファイルに書いてcompile:file(<File>, [from_abstr])またはerlc <File>.abstr
Core Erlang仕様はあるが、一部の詳細はprimop式を通じて実装に委ねられており、primopはどのメジャーリリースでも予告なく追加、削除、変更され得る。直接生成すると、Core-to-BEAMバックエンドが出会ったことのないコードを構成でき、最終的なBEAMコードが安全であるという保証はないfrom_coreオプション。ファイルの正確な形式は文書化されておらず、リリース間で変わり得る
BEAM assembly code強く非推奨。正しく作るのが非常に難しく、継続的な保守が必要である。新しい命令はたいていメジャーリリースごとに導入され、ときには古い命令が削除される。規約に従わないBEAMコードはランタイムシステムをクラッシュ（segfault）させ得るfrom_asmオプション。アセンブラファイルの形式は文書化されておらず、リリース間で変わり得る

節の結論は一文である。推奨はabstract formatかErlangソースコードのどちらかである。Gleamはこの二つの推奨案の一方から他方へ移ったことになる。ドキュメントがソースコード経路の主な欠点として挙げる行の対応付けの問題が、発表記事が利点として挙げる位置メタデータとそのままかみ合う。

同じドキュメントのオプション説明には、この経路を使う実装者が知っておくべき但し書きが二つある。一つはfrom_abstrの項目にある注意書きで、そのような項の形式はリリース間で変わり得ると記している。もう一つはno_lintオプションである。エラーと警告を検査するパスを省くオプションで、from_abstrと併用するときにのみ適用され、ドキュメントはこれを、コードの正しさを保証する独自の検査をすでに済ませた他言語の実装のためのものだと説明している。このオプションを使うと、コンパイラの出力が正しく安全であるという保証はなく、正しさの責任はabstract formatを生成したコードまたは人にあるという警告が付いている。

ビルド時間 — 数値と測定条件

発表記事は数値を示す前に、まず但し書きを置く。ベンチマークは常に人為的であり、全体像を語るものではないというものである。測定に使われたのはJosé Valimのlangcompilebenchを基にしたベンチマークであり、発表記事とリポジトリのREADMEに書かれた条件は次のとおりである。

  • 対象プロジェクト。モジュール100個、各モジュールに関数100個、各関数はhello world文字列を返す。
  • ビルドの種類。キャッシュなしで最初から行うフルビルドである。
  • 集計。READMEには11回実行の中央値と書かれている。
  • 比較するバージョン。Gleam v1.17.0とv1.19.0。書き直しの第一段階がv1.18.0に入ったため、一つ飛ばして比較している。
  • ツールのバージョン。READMEのバージョン一覧には、Erlang 29.0.6、Elixir 1.20.4-otp-29、Rebar 3.27.0などが記されている。

Erlangターゲットの二つの値の差は0.092秒であり、v1.17.0に対して約21%の短縮である（計算）。発表記事の本文にはこの数値は文として現れず、棒グラフとしてのみ載っており、表の値は発表記事がリンクするベンチマークリポジトリのREADMEのものである。READMEの表にはGo、Java、Rust、C#、Elm、TypeScriptの行もある。発表記事は、その比較はGleamのコンパイル速度をなじみのある言語と比べておおよその感覚をつかんでもらうためのものだと説明しつつ、このベンチマーク一つだけではそれらの言語について確かな結論を出すには不十分だと重ねて記している。

数値を読むときは、条件から導かれる限界を併せて見る。発表記事が記すとおり、このプロジェクトの形は複数の言語で同じように再現しやすい代わりに、各言語の機能のごく一部しかコンパイルされない。実際のプロジェクトのコードははるかに多様であり、機能ごとのコンパイルコストは言語によって異なる。またGleamのコンパイルはインクリメンタルであり、発表記事は、通常の開発中はプロジェクト全体をコンパイルしないのでずっと速くなるだろうと記している。フルビルドで測った短縮幅が、編集とビルドを繰り返すときの幅と同じだと見なす根拠は、これらの資料にはない。changelogは数値を挙げず、Erlangへコンパイルする際に典型的なGleamパッケージのコンパイル時間が短くなったとだけ記している。

エラー位置 — 行番号が元のGleamソースを指すということ

二つ目の利点は、運用中に表に出る変化である。発表記事によれば、ランタイムが利用できる位置メタデータが、今は元のGleamソースに合う。例として挙げられているのが、BEAMのクラッシュレポートとスタックトレースの行番号である。以前は不正確なことがあり、最も近い関数しか指さなかったが、今は正確だという（原文の表現はperfectly accurate）。changelogは同じ内容を、この形式は生成されたErlangのすべての行を元のGleamソースファイルの対応する行へ対応付けることをサポートすると記している。

Erlangのドキュメントでこの変化に関わる項目は三つある。

  • ANNO。abstract formatの各構文の表現に入り、ソースファイルの行番号を持つ。
  • {source,FileName}オプション。module_info(compile)とスタックトレースに表示されるソースファイル名を上書きする。
  • {error_location,line | column}オプション。値がcolumnのとき、デバッグ情報に列の情報が含まれる。ドキュメントによれば既定値はcolumnで、Erlang/OTP 24.0からサポートされている。

解釈を添えると、行番号が関数単位から行単位で合うようになると変わるのは、障害対応の最初の一歩である。スタックトレースが指す行が失敗箇所であるという前提が成り立ってはじめて、ログからコードへ直接たどれる。関数だけが合っている状態では、その関数の中のどの式が失敗したのかを、人があらためて絞り込むことになる。

デバッガについて、発表記事は一歩引いた書き方をしている。このメタデータはedbのようなデバッガでGleamを完全にサポートする道を開くかもしれないが、チーム自身はその作業を何もしていないというものである。edbリポジトリのREADMEは、edbをErlang用のステップデバッガと紹介し、OTP 29以降が必要だと記している。プロジェクトにはdebug_info、beam_debug_info、beam_debug_stackの三つのコンパイルオプションが必要だという案内もある。発表記事の文は可能性について述べたものであり、v1.19.0でGleamのコードをedbでデバッグできるという記述ではない。

BEAMバイトコードを直接出力しない理由

中間表現まで下りたのなら、Erlangコンパイラを丸ごと飛ばしてBEAMバイトコードを直接作ればよいのではないか、という問いが続く。発表記事はこの問いを自ら立てている。Erlangコンパイラを上回るバイトコードジェネレータを作れるのではないか、Gleamの型情報を使ってより最適化されたコードを出せるのではないか。答えは、そうした利点を得ることは可能だが、実際にやり遂げられる見込みは低いというものである。挙げられた理由は次のとおりである。

  • バイトコードは固定されていない。発表記事は、Erlangソースやabstract formsと違って、BEAMバイトコードは固定不変ではないと記している。仮想マシンの新しいリリースのたびにバイトコードは進化し得て、新しい機能が加わり、ときには不要になった機能が取り除かれる。
  • 追随のコストに終わりがない。その進化を追い続け、Erlangのメンテナと密に協力して今後の変更に備え、仮想マシンの新しいリリースに合わせてGleamの新しいバージョンを用意しておく必要がある。
  • 既存の最適化を作り直す必要がある。Erlangコンパイラに数十年かけて実装された最適化をすべて再現する作業は、Gleamのより強力な静的解析が助けになるとしても、相当な労力を要する。
  • 財源が限られている。Gleamはスポンサーシップで支えられるコミュニティプロジェクトであり、企業や学術機関が後ろ盾となる言語に比べれば財政はその一部にとどまると発表記事は記している。

発表記事の結論は、Erlang abstract formsへコンパイルすることが、今のGleamにとって費用対効果の釣り合う地点だというものである（原文の表現はcost-benefit sweet-spot）。同じ選択をした言語としてElixirを挙げている。Elixirもabstract formsを経由してErlangへコンパイルするという。

この判断は、前節のErlangドキュメントと対象は異なるが、挙げる理由の向きが同じである。ドキュメントが強く非推奨とするのは、BEAM assembly codeをErlangコンパイラに渡す経路（from_asm）であり、発表記事が仮定したのは、Erlangコンパイラを丸ごと飛ばしてバイトコードを直接作る方式である。ドキュメントは非推奨の理由として、継続的な保守と、メジャーリリースごとに導入される新しい命令を挙げている。ただし、固定という言葉の強さは二つの文書で異なる。発表記事はabstract formsをErlangソースとともに固定された側に置き、compileドキュメントのfrom_abstrの項目は、そのような項の形式がリリース間で変わり得ると記している。解釈を添えると、中間表現を対象にする側は、ソーステキストを対象にするときより相手のコンパイラの内部に一段近づき、その分だけOTPのリリースノートで追うべき項目が増える。

アップグレードの後に自分で見ておく価値があるのは次の点である。発表記事とchangelogの記述から導かれる点検項目であり、該当するかどうかはプロジェクトによって異なる。

  • 自分のプロジェクトのビルド時間。ベンチマークはhello world関数1万個（100×100、計算）の合成プロジェクトである。キャッシュを消したフルビルドと普段のインクリメンタルビルドを、アップグレードの前後でそれぞれ計っておくと、自分のコードでの幅が分かる。
  • スタックトレースの行。わざと失敗させたコードでクラッシュレポートを出し、行番号がGleamソースの該当行と合うかを見る。
  • 生成物に依存するツール。ビルドディレクトリの生成ファイルを読んだり加工したりするスクリプトがあるなら、アップグレード後も同じファイルが同じ形で存在するかを見る。コードジェネレータの出力形式が変わったリリースである。
  • Mixとrebar3の連携。compile-packageを呼び出す側であれば、フラグ名を見る。changelogによれば、rc1の--src-onlyはrc2で--no-devに改名された。
  • 新しく出る警告。changelogは、重なり合う文字列パターンで到達不能な節をより多く認識するようになったと記し、以前は警告なしでコンパイルできたコードが今はこの警告を出すことがあると付け加えている。caseの中でリスト全体を受ける[..x]パターンにも警告が追加され、この構文は将来のメジャーリリースで削除される可能性があると書かれている。
  • OTP 29との名前の衝突。Erlangの型定義を生成するとき、Recordという名前の型はrecord_に改名される。OTP 29で導入されたErlang組み込みのrecord型を上書きしないためだとchangelogは記している。

同じリリースの他の変更 — JavaScriptターゲットは今もソースを出す

Erlangターゲットが中間表現へ移った同じリリースで、JavaScriptターゲットは生成するソースコードそのものを磨いた。発表記事の例が二つの形式の違いを示している。Gleamのフロー制御はcase式のパターンマッチであり、これはネストしたif文にコンパイルされる。John Downeyがこの過程を改良し、ネストしたifを一つの条件にまとめ、中間変数を減らした、より平らなコードを生成するようにした。次のGleamコードがあるとき、

pub fn go(x) {
                      case x {
                        Wibble(1, 2) -> 1
                        _ -> 2
                      }
                    }

以前は次のJavaScriptが生成されていた。発表記事は、コードは読みやすさのために少し手を入れてあるが、この改良に関わる部分はそのままだと脚注に記している。

export function go(x) {
                      if (isWibble(x)) {
                        let $ = x[0];
                        if ($ === 1) {
                          let $1 = x[1];
                          if ($1 === 2) {
                            return 1;
                          } else {
                            return 2;
                          }
                        } else {
                          return 2;
                        }
                      } else {
                        return 2;
                      }
                    }

v1.19.0は次を生成する。

export function go(x) {
                      if (isWibble(x) && x[0] === 1 && x[1] === 2) {
                        return 1;
                      } else {
                        return 2;
                      }
                    }

発表記事は、この変化は最小化と圧縮を経たバンドルのサイズにはほとんど差を生まないが、結果のコードにはJavaScriptエンジンが最適化すべき分岐がより少ないと記している。生成物が人の読むテキストであるから、改良をこのように前後のコードとして並べて示せる。そのほかに発表記事とchangelogが挙げる変更は次のとおりである。

  • リストリテラル。JavaScriptターゲットで、短いリストリテラルは、配列を作って変換関数に渡すのではなく、配列から変換しない、より直接的なコードとして生成される。長いリストでは改善が記録されなかったため、従来の方式が維持される。
  • TypeScriptの宣言。カスタム型のバリアントを判定する関数にオーバーロードが追加され、型パラメータがunknownに一般化されて失われていた情報が、可能な場合には保持される。
  • 他のビルドツール。BEAMへコンパイルするとき、仮想マシンが要求する.appリソースファイルをgleamが生成する。export package-informationとexport package-interfaceは標準出力に書き出せるようになった。ElixirのMixとErlangのrebar3でGleamをサポートさせる意図だと発表記事は述べている。
  • 言語サーバー。フィールドと引数のラベルについて、定義へ移動、参照の検索、名前の変更がサポートされる。
  • ブラウザでの整形。コンパイラのWebAssemblyビルドにformat_source関数が追加された。
  • エラーメッセージ。gitのマージコンフリクトの目印、レコード更新構文の順序の誤り、Gleamに存在しない+=のような演算子、パターンマッチでの|の使用などに専用のメッセージが加わった。
  • ビルドキャッシュ。changelogによれば、ビルドツールがビルドキャッシュをよりコンパクトなバイナリ形式で保存するようになり、キャッシュファイルが目に見えて小さくなった。

Mixのサポートについて発表記事が使った表現は、近いうちに見られることを願うという水準であり、今回のリリースがサポートの完了を意味するわけではない。

確認できなかったこと

  • 測定に使った機器。ベンチマークを実行したハードウェアとオペレーティングシステムは、発表記事にもREADMEにも書かれていない。0.434秒と0.342秒は、値そのものよりも同じ条件での相対比較として読む数値である。
  • 短縮の内訳。短くなった0.092秒のうち、Erlang側のトークン化とパースを省いた分と、Gleamのコードジェネレータ自体が速くなった分がそれぞれどれだけかは、資料にない。changelogには同じリリースでGleamコンパイラのレキサーを改めた項目もあり、要因は一つではない。
  • v1.18.0に入った範囲。発表記事は、書き直しの第一段階がv1.18.0でリリースされたとだけ記している。その段階が何を含んでいたかは書かれていない。
  • Erlangソース出力が残っているかどうか。生成したErlangソースを閲覧用に引き続き出力するのか、gleam export erlang-shipmentの中身がどう変わったのかについて、発表記事とchangelogには記述が見つからなかった。
  • Erlangコンパイラの呼び出し方。Gleamがabstract formsをcompile:forms/2で渡すのか、.abstrファイルとfrom_abstrで渡すのか、no_lintを使うのかは、根拠とした資料にない。Gleamコンパイラのソースコードは根拠とした資料に含めていない。
  • 実際のプロジェクトでの幅。合成ベンチマーク以外のプロジェクトでビルド時間がどれだけ短くなるかについて、公開された測定は見つからなかった。
  • abstract formatのリリース間の安定性。発表記事のfixed and unchangingと、Erlangドキュメントのcan change between releasesのどちらがGleamの使う経路に当てはまるのかは、二つの文書だけでは決まらない。
  • 列の情報。スタックトレースで行に加えて列までGleamソースに合うのかどうかは、発表記事に記述がない。
