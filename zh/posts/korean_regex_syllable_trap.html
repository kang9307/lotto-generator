韩文正则陷阱 - 「아닙니다」里没有「아니」

音节算术、按词尾划分的安全模式、NFC 与 NFD、外壳转义、가-힣 的局限、回归测试，全部附实际运行输出

2026年7月29日 IT/技术

引言：检查器整整两个月都在返回「无问题」

有一个检查器，任务是确认正文里是否包含免责声明。规则很简单：文档中若能找到 /자문이 아니/ 这个模式就算通过，找不到就告警。它每天运行，每天都很安静。既然一次告警都没有出现过，那就说明所有文档都好好地写上了免责声明。

事实恰恰相反。那条规则一次都没有命中过。因为站点正文通篇使用敬语体，也就是「자문이 아닙니다」。规则要找的 아니 并不存在于 아닙니다 之中。检查器忠实地读取每一份文档，忠实地运行规则，忠实地什么也没找到，然后返回「无问题」。

这起事故之所以可怕，是因为结果长着成功而非失败的样子。没有异常，退出码为 0，日志干干净净。没有任何地方会告诉你检查器已经坏了。这种情况称为静默失败。而在处理韩文的代码里，静默失败格外频繁。

根源只有一个：在英文里养成的习惯，到了韩文就彻底塌掉。在英文里搜索 advis，advise、advisor、advisory 会一并命中，因为词尾是往后追加的，词干始终作为子串保留下来。韩文不是这样。词尾附着时前一个字本身就变了。给 아니 加上终结词尾，得到的不是 아니 加上什么，而是 아 + 닙 + 니 + 다。第二个字被换成了另一个完全不同的字。

本文讲的就是这个原理，以及由它派生出的五个陷阱。它有一个特点：每一条论断都附有实际运行过的输出。只读说明容易一带而过，但亲眼看到 -1 这个数字，就很难再忘记。

运行环境。下面所有输出都是在 Windows 10 Pro / Node.js v22.16.0 (win32) 上实际运行的结果，原样照录。所有示例都保存为 .js 文件后执行，原因在第 5 节说明。

本文不涉及的内容。各正则引擎语法不同的问题，也就是方言与可移植性，已在 到处都能跑的正则表达式 中讨论过。本文只挖另一侧，即韩文这套文字体系本身的问题。两篇文章并不重叠。

1. 「아닙니다」里没有「아니」的原因 - 音节是预先合成的单个字

先从事实核验开始。这是输出，不是主张。

node v22.16.0 / win32
--- 1-1. indexOf ---
'아닙니다'.indexOf('아니') = -1
'아닙니다'.includes('아니') = false
'아니다'.indexOf('아니')   = 0
'아니라'.indexOf('아니')   = 0
--- 1-2. 码位 ---
아닙니다 : 아=U+C544 닙=U+B2D9 니=U+B2C8 다=U+B2E4
아니     : 아=U+C544 니=U+B2C8
아니다   : 아=U+C544 니=U+B2C8 다=U+B2E4

在 아니다 与 아니라 中，第 0 位就直接找到了。可是在 아닙니다 中结果是 -1。把码位并排放在一起，原因一目了然。

  • 要找的字符串 아니 = U+C544、U+B2C8
  • 目标字符串 아닙니다 = U+C544、U+B2D9、U+B2C8、U+B2E4
  • 第二个位置是 U+B2D9 而不是 U+B2C8，因此不存在连续的子序列

1.1 加上终声就成了另一个字

第二个位置为什么变了？Unicode 的韩文音节区 (U+AC00~U+D7A3) 是把初声、中声、终声的组合用算术式预先算好并排布而成的。Unicode 标准定义的合成公式如下。

音节码位 = 0xAC00 + (初声索引 * 21 + 中声索引) * 28 + 终声索引

把这个公式反过来分解 니 与 닙，结果是这样。

--- 1-3. 为什么不同 (音节算术) ---
니 U+B2C8 {"初声":2,"中声":20,"终声":0}
닙 U+B2D9 {"初声":2,"中声":20,"终声":17}
加上终声(收音)就会变成完全不同的码位 → '니' ≠ '닙'

初声 (ㄴ) 相同，中声 (ㅣ) 也相同。不同的只有终声，而终声从 0 变成 17 (ㅂ) 的瞬间，码位就整整位移了 17。在字符串匹配器眼里，这两个字就像字母 a 和 r 一样毫不相干。「只是多了一个收音而已」这种人类直觉，在码位序列里没有任何体现。

1.2 与英文有何不同

把差别整理成对照就是下面这样。这组对照是全文的根。

  • 英文 - 屈折以字符追加的方式发生。advise → advisor。前面的 advis 完好保留
  • 韩文 - 屈折以字符替换的方式发生。아니다 → 아닙니다。第二个字本身被换成了另一个字
  • 因此在英文里行得通的前缀匹配策略，在韩文里原理上就不成立
  • 同理，startsWith、LIKE '아니%'、检索索引的前缀匹配也全都踩同一个坑

2. 静默失败 - 只写词干的规则一次也抓不到敬语体

如果说第 1 节是原理，第 2 节就是波及范围。针对五种活用形，把坏规则和好规则并排跑了一遍。

node v22.16.0 / win32
句子                                             仅词干 (BAD)      字符类 (GOOD)     选择分支 (GOOD)
--------------------------------------------------------------------------------------
이 글은 법률 자문이 아닙니다.                        漏检              命中              命中
이 글은 법률 자문이 아니다.                          命中              命中              命中
이 글은 법률 자문이 아니라 정보 제공입니다.             命中              命中              命中
이 글은 법률 자문이 아님을 밝힙니다.                   漏检              命中              命中
이 글은 법률 자문이 아녜요.                          漏检              命中              命中
--------------------------------------------------------------------------------------
仅词干 (BAD)               2/5 检出
字符类 (GOOD)              5/5 检出
选择分支 (GOOD)            5/5 检出

所用的三条规则分别是 /자문이 아니/、/자문이 아[니닙님녜냐]/ 和 /자문이 아(?:니|닙|님|녜|냐)/。

2.1 为什么这是最糟的失败类型

2/5 的检出率不是「性能略有遗憾」这种程度。看一看这条规则在实务中是怎么运作的，性质就完全不同了。

  • 正式文档绝大多数使用敬语体。也就是说实务中最常见的形态，恰恰落在抓不到的那一侧
  • 规则不命中时，检查器报的不是「无违规」，实质上是「未检查」。两者的输出一模一样
  • 检查器在运行这件事本身就制造了虚假的安心。没有它人还会亲自看，有了它反而没人看
  • 更糟的是检出率不是 0% 而是 40%。在陈述体文档上偶尔会命中，于是「规则运转正常」的证据会周期性地被生产出来

2.2 怀疑规则之前先怀疑检查器

由此得出一条实务原则：某条规则长期一条都没抓到，那多半不是说明没有违规，而是说明规则已经死了。对韩文文本尤其如此。构建检查器时把命中次数一并记录下来，再加上对长期为 0 的规则发出告警的机制，就能及早抓到这类事故。第 8 节要讲的回归测试是根本处方，这一条则是便宜的保险。

3. 按词尾划分的安全模式 - 该把什么用字符类打开

那该怎么写？核心是预先把收音附着的位置打开。韩语中发生活用的位置大体是固定的，把那些位置写成字符类就能覆盖大部分情况。

要找的表达常见活用形危险的模式安全的模式
아니다 系列 (不是) 아닙니다 / 아니다 / 아니라 / 아님 / 아녜요 아니 아[니닙님녜냐]
없다 系列 (没有) 없습니다 / 없다 / 없어요 / 없음 / 없이 없다 없[다습어음이는]
하다 系列 (做) 합니다 / 한다 / 해요 / 함 / 하는 하다 (?:합|한|해|함|하)
이다 系列 (系动词) 입니다 / 이다 / 예요 / 임 / 인 이다 (?:입|이|예|임|인)
않다 系列 (否定) 않습니다 / 않다 / 않아요 / 않음 않다 않[다습아음는]
수 있다 / 없다 (能 / 不能) 할 수 있습니다 / 할 수 없다 수 있다 수 (?:있|없)[다습어]

3.1 不要照单全收这张表

上表是起点而非终点。韩语活用形无法靠罗列穷尽。使用这张表时必须一并记住它的局限。

  • 不规则活用无法用字符类覆盖。像 돕다 → 도와、듣다 → 들어，词干本身就变了
  • 分写差异会击穿规则。할 수 있습니다 与 할수 있습니다 是不同的字符串。空格位置必须用 \s* 打开
  • 助词插入同样会击穿。자문이 아닙니다、자문은 아닙니다、자문이 결코 아닙니다 都是有效句子
  • 字符类越放越宽，误报会急剧上升。以 아 开头的无关词开始被命中

3.2 正则撑不住的地方

所以过了某个临界点，不如换掉整个思路。实务中可用的顺序如下。

  1. 第 1 步 - 只找不发生活用的核心名词。자문、면책 这类没有变形的词很适合做锚点
  2. 第 2 步 - 围绕命中的锚点按句切分，在句内判定是否有否定表达。不要试图用一条正则去匹配整句
  3. 第 3 步 - 若还需要更高的准确度，用形态素分析器把词干规范化后再比较。一旦 아닙니다 与 아니다 被规范化成同一词干，问题本身就消失了
  4. 第 4 步 - 剩下的含糊条目输出成清单交给人看。这比自动放行要好

试图用正则覆盖韩语全部活用形的做法，大多以失败告终。规则不断膨胀，某个时刻变成一行没人敢碰的东西。用正则去缩小候选，把判定交给另一层，这样的系统才活得久。

4. NFC 与 NFD - 看上去一样的字并不相等

第二个陷阱更加隐蔽。同样是 한，计算机却可能把它看作两个不同的字符串。这是 Unicode 标准附件 15 所定义的规范化形式问题。

node v22.16.0 / win32
--- 3-1. 长度与码位 ---
'한'.length              = 1 | U+D55C
'한'.normalize('NFD').length = 3 | U+1112 U+1161 U+11AB
屏幕上两者都显示为: 한 / 한

NFC 是组合形，한 就是 U+D55C 这一个字符。NFD 是分解形，会拆成初声 ㅎ (U+1112)、中声 ㅏ (U+1161)、终声 ㄴ (U+11AB) 三个码位。屏幕上两者都显示成一模一样的 한。肉眼绝无可能分辨。

4.1 所有比较全部失败

--- 3-2. 所有比较全部失败 ---
nfc === nfd            : false
'한국'.indexOf(nfd)     : -1
'한국'.normalize('NFD').indexOf('한') : -1
/한/.test(nfd)          : false
/[가-힣]/.test(nfd)      : false
--- 3-3. 规范化即可解决 ---
nfc.normalize('NFC') === nfd.normalize('NFC') : true
'한국'.normalize('NFC').indexOf(nfd.normalize('NFC')) : 0

相等比较、indexOf、正则判定、字符类检查全部失败。而一次规范化就全部解决。问题与处方对应得这么干净的情形，其实并不多见。

4.2 集合与排序也一起崩坏

--- 3-4. 排序与去重也会崩坏 ---
Set([nfc, nfd]).size = 2 ← 同一个字却算成 2 个
规范化之后的 Set.size = 1
--- 3-5. 文件名的情形 ---
两个文件名是否相同 : false
NFC 长度 7 / NFD 长度 10
filter(f => f.startsWith('보고서')) 的结果条数 : 1 ← 本应是 2 条

去重失效，文件名过滤只筛出一半。两个 보고서.txt 里只有一个被筛了出来。去重逻辑一旦静默失败，查明原因可能要花上好几天。因为肉眼看去完全相同的字符串就并排摆在那里，程序却一口咬定它们不同。

4.3 该在哪里做规范化

原则只有一条：在外部字符串进入系统的边界处规范化一次，内部则假定已经规范化。到处都做既浪费性能，又会出现这里做那里不做的窟窿。

位置规范化理由
读取文件系统列表必须随平台与协议不同，可能混入分解形
网络接收 / API 响应解析必须无法控制发送方选择哪种形式
接收表单输入必须输入法与粘贴路径不同，结果可能不同
写入数据库之前推荐在写入时统一可以让查询条件变简单
比较与检索之前次优能跑，但容易出现遗漏规范化的地方
屏幕输出之前无意义比较早已结束，为时已晚

该统一成哪种形式？在 Web 与存储层，NFC 大体上是稳妥的选择。字符串更短，多数系统期待组合形，长度计算也更贴近人的直觉。不过在做首字母检索这类需要按字母处理的功能时，仅在那一段有意使用 NFD 反而更省事。比选择本身更重要的是在一个系统内部统一成一种。

5. 经由外壳，正则会静静地死掉

第三个陷阱不是来自文字体系，而是产生于层与层的边界。但因为结果和前面那些事故一样安静，值得放在一起讨论。

假设你为了去掉空白，用 node -e 跑了一行。命令交给外壳的那一刻，反斜杠被剥掉一层，剩下的字符串又被当作 JavaScript 字符串字面量重新解释。一个反斜杠被消耗了两次。下面是实际运行的结果。

$ node -e "console.log(JSON.stringify('\s'))"
"s"

$ node -e "console.log(String(new RegExp('\s+')))"
/s+/

$ node -e "console.log(JSON.stringify('less  space'.replace(new RegExp('\s+','g'),'')))"
"le  pace"

看第三行。输入是 less space，结果是 le pace。空白原封不动地留着，字母 s 却全部消失了。本该删除空白的代码，做的恰好是相反的事。

同样的命令在 Git Bash 与 Windows PowerShell 5.1 两边都执行过，输出完全一致。这说明它不是某一种外壳的毛病，而是多经过一层就会发生的普遍现象。

5.1 究竟发生了什么

元凶不只是外壳。JavaScript 字符串字面量的规则也是共犯。把同样的代码保存成文件再执行，原因就分离开来了。

node v22.16.0 / win32
--- 4-1. 正则字面量 vs 从字符串构造 ---
字面量 /\s+/            : /\s+/
new RegExp('\s+')      : /s+/
new RegExp('\\s+')     : /\s+/
--- 4-2. 同样的输入，三种结果 ---
原文                     : "less  space"
使用字面量 (正常)         : "lessspace"
new RegExp('\s+') (损坏) : "le  pace"
new RegExp('\\s+') (正常): "lessspace"

整理下来是这样。

  • 在 JavaScript 字符串字面量中 '\s' 是无法识别的转义，反斜杠被丢弃，只剩下普通的 's'
  • 用这个字符串构造正则就得到 /s+/。空白字符类变成了字母 s
  • 正则字面量 /\s+/ 不经过字符串字面量这一步，所以是安全的
  • 若必须从字符串构造，反斜杠要写两遍：'\\s+'
  • 经由外壳可能还要再多一层。每多一层就多一遍

5.2 为什么没人察觉

--- 4-3. 韩文里也会发生同样的事 ---
原文                    : 자문이 아닙니다
new RegExp('\s') 去除    : "자문이 아닙니다"
字面量 /\s/ 去除         : "자문이아닙니다"
--- 4-4. 之所以是静默失败 ---
未抛出任何异常。RegExp 构造成功 : true

在韩文字符串里，本该被删掉的空白原样留了下来。而最后一行正是本节的要害。new RegExp('\s+') 不会抛出异常。一个完全有效的正则对象被创建了出来，只不过它和你想要的正则不是同一个而已。既然没有报错，日志就是干净的，没有测试的话就会一路带到线上。

5.3 实务规则

  • 不要把含正则与韩文的代码作为命令行参数传递。保存成文件再执行
  • 若必须从字符串构造正则，就把结果打印出来用眼睛看一遍。一行 console.log(String(re)) 就够了
  • 如果模式是从配置文件或数据库读取的，就把反斜杠加倍的规则写进文档
  • 把用户输入拼进模式时要转义元字符。不做的话就不只是行为出错，而会演变成性能事故
  • 若内联执行不可避免，就使用单引号包裹的外壳惯例，即便如此也要验证结果

6. [가-힣] 抓不到的东西，以及该用什么替代

检查韩文时几乎条件反射就会用上的 [가-힣]，指向的只有预组合音节区。其余全部漏掉。用九个样本验证过。

类别                  字符      码位                       [가-힣]
------------------------------------------------------------------------
预组合音节            한        U+D55C                     O
辅音单独              ㄱ        U+3131                     X
元音单独              ㅏ        U+314F                     X
组合中的字母          ㄱㅏ       U+3131 U+314F              X
NFD 分解状态          한        U+1112 U+1161 U+11AB       X
古韩文 옛이응         ㆁ        U+3181                     X
古韩文 中声扩展       ힰ        U+D7B0                     X
兼容字母              ㅘ        U+3158                     X
半角韩文              ﾠﾡ        U+FFA0 U+FFA1              X

除去那一个预组合音节，剩下八个样本全部通过。换句话说，用 [가-힣] 来筛掉「非韩文字符」的校验器，会把上面八种全部判定为不是韩文。组合中的输入被拒、分解形文件名被拒这类事故就是从这里来的。

6.1 两种替代方案的比较

--- 5-2. 放宽范围的替代方案 ---
类别                  宽范围       \p{Script=Hangul}
----------------------------------------------------
预组合音节            O            O
辅音单独              O            O
元音单独              O            O
组合中的字母          O            O
NFD 分解状态          O            O
古韩文 옛이응         O            O
古韩文 中声扩展       O            O
兼容字母              O            O
半角韩文              X            O

所比较的两个模式如下。

  • 手工罗列的宽范围 - [ᄀ-ᇿ㄰-㆏ꥠ-꥿가-힣ힰ-퟿]，把字母、兼容字母、扩展区都手动打开了。它抓到了八个样本，却在半角韩文上漏掉了
  • 脚本属性 - /\p{Script=Hangul}/u。九个样本全部抓到。因为它直接查询 Unicode 字符数据库的 Script 属性，无需手工维护区块边界
  • 属性转义必须带 u 标志。少了它不是语法错误，而是按另一种含义解释，于是又一次静默出错

6.2 计数时差距就显出来了

--- 5-3. 韩文字符计数对比 ---
目标字符串的码位数 : 7
match(/[가-힣]/g)            : 2
match(/\p{Script=Hangul}/gu) : 7

同一个字符串给出了 2 与 7。如果你要做「韩文占比多少」这类指标，选哪一个会让答案相差三倍以上。

6.3 放宽并不总是正确答案

不过这里需要拿捏平衡。依目的不同，收窄有时才是对的。

  • 用于检测正文里是否混入了韩文（比如多语言污染检查）时，放宽才对。漏检会让检查器彻底失效
  • 用于校验用户名输入时，收窄可能更好。把组合中的 ㄱㅏ 存成姓名是会出问题的
  • 做检索索引时先规范化，然后再用宽范围。顺序颠倒会让分解形从索引中漏掉
  • 无论哪一种，正确顺序都是先用文字写清楚要放行什么，然后再挑模式。先挑模式，意图就变成事后追认了

7. 长度不止一个 - 正则之外的陷阱

即便不用正则，同一个根源也会带来问题：「字数」这个词有四个答案。

node v22.16.0 / win32
对象           .length   [...s].length   byteLength(utf8)   Intl.Segmenter
------------------------------------------------------------------------
한글             2            2                  6                    2
NFD 한글         6            6                  18                   2
abc              3            3                  3                    3
家庭表情符号      8            5                  18                   1
한글+拉丁字母    5            5                  9                    5

한글 按不同标准计数，结果是 2、2、6、2。若以分解形传入则变成 6、6、18、2。同样是两个字，存储单位的长度却从 2 跳到了 6。

计数方式计数单位适合的用途会出错的场合
s.lengthUTF-16 码元内存估算、索引定位分解形与表情符号上与人的感觉不符
[...s].length码位按字符遍历分解形下仍会膨胀，还会拆开组合表情
Buffer.byteLength字节（依赖编码）存储容量、传输量、列宽不写明编码答案就会变
Intl.Segmenter字素簇用户所见的字数较慢、依赖区域设置、旧环境没有

7.1 存储容量随编码而变

--- 6-2. 各编码的字节数 ---
'한글' utf8 字节  : 6 (每字 3 字节)
'한글' utf16 字节 : 4

在 UTF-8 中一个韩文字符是 3 字节，UTF-16 中是 2 字节。若数据库的列按字节计，就必须连同编码一起算清「最多 10 个字」到底是多少字节。把按字符的长度限制原样搬到按字节的列上，韩文输入就会被截断。

7.2 截断会把字劈成两半

--- 6-3. slice 会把字劈成两半 ---
NFD 字符串 slice(0,2) : "하" ← 只剩初声+中声的残缺字
NFC 字符串 slice(0,1) : "한"

切分解形字符串时终声掉了，한 变成了 하。生成预览文本或截断摘要时就会发生这种事。切之前先规范化这条原则在这里同样成立。要想连表情符号、旗帜、家庭表情都安全处理，就得按字素簇边界来切。

  • 预览与摘要截断 → 先做 NFC 规范化，再按字素簇切
  • 数据库列设计 → 按字节，并写明编码
  • 给用户看的字数限制提示 → 按用户所见的字素簇
  • 哈希与签名的对象 → 以约定固定规范化形式。否则同一个字会算出不同的哈希

8. 回归测试的做法 - 抓住误通过的唯一装置

到目前为止的陷阱全都很安静。没有异常，日志干净。那要靠什么去抓？除了检查检查器本身，别无他法。

关键是把测试项分成两类。

  • MUST_HIT - 在这些句子上规则必须命中。敬语体、陈述体、连接形、名词形各放一条
  • MUST_MISS - 在这些句子上命中就是误报。规则越放越宽时，往往就是在这里崩掉
  • 只有其中一类就只做了一半。只有 MUST_HIT 的话，把规则写成 /./ 也能通过

把两条规则放进同一套测试实际跑了一遍。

[坏规则] /자문이 아니/
  [FAIL] MUST_HIT  敬语体    본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  陈述体    본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  连接形    본 글은 법률 자문이 아니라 일반 정보입니다.
  [FAIL] MUST_HIT  名词形    본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS 无关句    전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS 部分词汇  자문위원회가 심의했습니다.
  => pass 4 / fail 2

[好规则] /자문이 아[니닙님녜냐]/
  [PASS] MUST_HIT  敬语体    본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  陈述体    본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  连接形    본 글은 법률 자문이 아니라 일반 정보입니다.
  [PASS] MUST_HIT  名词形    본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS 无关句    전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS 部分词汇  자문위원회가 심의했습니다.
  => pass 6 / fail 0

=== 汇总 ===
坏规则失败条数 : 2 ← 有回归测试的话第一天就抓到了
好规则失败条数 : 0

六行的测试立刻暴露了两个月里无人知晓的缺陷。引言里那起事故，光靠这一套测试第一天就能挡住。

8.1 测试项里必须放的东西

  1. 敬语体 - 「~습니다 / ~ㅂ니다」。正式文档中最常见，也是最容易漏掉的形态
  2. 陈述体 - 「~다」。词干往往原样保留，所以连坏规则也能通过。只放这一种就毫无意义
  3. 连接形与名词形 - 「~라」「~ㅁ을」。这些正是终声真正发生变化的位置
  4. 口语与缩略形 - 「~예요 / ~네요」。若要处理用户生成内容则是必备
  5. 三种误通过样本 - ①与规则无关的句子 ②核心词被用作另一种含义的句子 ③锚点词是另一个词一部分的句子

8.2 构建检查器时的额外装置

  • 不要用内联执行来跑回归测试。如果第 5 节那种转义事故发生在测试代码里，测试本身就开始说谎。务必保存成文件
  • 故意植入缺陷来确认检出力。把规则弄坏之后测试若不变红，那这套测试什么也没在守护
  • 记录每条规则的命中次数。长期为 0 的规则很可能已经死了
  • 样本句要取自真实正文。凭空编写的句子无法反映实际文体
  • 每次修改规则，都先补测试项。发现的漏检案例本身就是新的测试项

9. 即便照做也仍然防不住的东西

为求平衡，把局限也说清楚。就算把上面的处方全部落实，仍有问题会留下来。

  • 不规则活用 - 词干整个改变的情形无法用字符类覆盖，需要形态素分析器
  • 分写的自由度 - 韩语对分写错误相当宽容，真实文档里混杂着各种写法
  • 语义判定 - 자문이 아닙니다 与 자문이 아니라고 할 수는 없습니다 意思相反，字符串却相似。正则原理上无法区分
  • 形态素分析器的代价 - 准确度会提高，但要付出词典维护、处理速度、发布体积的代价。仅为一个检查器是否值得引入，是另一回事
  • 规范化的副作用 - 虽然少见，但规范化会改变原始字节，因此在需要签名校验或原本保全的地方，必须另行保存规范化之前的原本
  • Script 属性的宽度 - \p{Script=Hangul} 宽是它的优点，但在需要收紧校验的界面上反而过头

所以本文的结论不是「把正则写好一点」，而更接近认清正则能承担的范围，在超出的那一点换用别的工具。

结论：怀疑规则之前先怀疑检查器

本文的起点是一个安静了两个月的检查器。原因既不是正则语法，也不是库的缺陷，更不是编码设置。而是一句话就能讲清的事实：韩文音节是预先合成的单个字符。把在英文里养成的前缀匹配习惯原样搬到韩文上的那一刻，规则就死了，而没有任何东西会告诉你它死了。

重新梳理，一共六条。①韩文在词尾附着时前一个字会变，所以词干匹配不成立。②把收音的位置用字符类打开，同时也要知道罗列无法穷尽。③在外部边界规范化一次，内部假定已规范化。④不要把正则交给外壳，并把构造出的正则打印出来确认。⑤[가-힣] 只覆盖预组合形，按目的考虑 \p{Script=Hangul}。⑥并且把这一切用回归测试固定下来。

六条之中最后一条最重要。前五条是知识，最后一条是让知识被遗忘之后仍然撑得住的结构。人一定会忘。新加入的人本来就不知道。只有测试会留下来。

现在就能做的事有一件：打开检查韩文文本的规则清单，看看有没有最近三个月一条都没命中过的规则。若有，就给那条规则喂一句敬语体的句子跑一遍。安静究竟是因为没有违规，还是因为规则已死，就靠这一行分晓。

# 韩文正则表达式 检查清单

> 来源: braindetox.kr — 韩文正则陷阱，「아닙니다」里没有「아니」
> 标准依据: Unicode UAX #15(规范化)、UAX #29(字素簇)、UAX #44(Script 属性)
> 用法: 在审查任何处理韩文文本的检查器、解析器或搜索代码之前，自上而下扫一遍。
> 也可以把本文件直接贴给 AI，让它按此清单审计你的代码库。

## 0. 三十秒判定 — 命中任意一条就把下面全部看完
- [ ] 用正则或 `indexOf` 检查韩文字符串
- [ ] 韩文来自用户输入、文件名或外部 API
- [ ] 统计「字数」或截断字符串
- [ ] 模式来自配置文件、环境变量或命令行参数

## 1. 编写模式 — 如何为词尾留出位置
- [ ] 是否还有只写词干的模式(`아니`、`없다`、`하다`、`이다`、`않다`)
- [ ] 收音(终声)出现的位置是否用字符类或选择分支打开
- [ ] 是否明确覆盖敬语体(`~ㅂ니다` / `~습니다`)
- [ ] 是否覆盖名词形(`~ㅁ` / `~음`)
- [ ] 是否需要覆盖口语与缩略形(涉及用户生成内容时必需)
- [ ] 空格位置是否用 `\s*` 或 `\s+` 打开(分写习惯不统一)
- [ ] 是否考虑助词变化(`이/은/는/가`)
- [ ] 放宽字符类之后是否重新测量了误报

### 词尾位置速查
| 系列 | 需打开的位置 | 最少候选 |
|---|---|---|
| 아니다(不是) | 第二个字 | 니 닙 님 녜 냐 |
| 없다(没有) | 第二个字 | 다 습 어 음 이 는 |
| 않다(否定) | 第二个字 | 다 습 아 음 는 |
| 하다(做) | 第一个字 | 합 한 해 함 하 |
| 이다(系动词) | 第一个字 | 입 이 예 임 인 |

### 正则撑不住时的转移顺序
1. 改用不发生活用的**核心名词**作为锚点
2. 围绕锚点**按句切分**，在句内做判定
3. 若还需要更高准确度，用**形态素分析器**规范化词干
4. 剩余含糊的条目输出为**人工复核清单**(不要自动放行)

## 2. 规范化 — 在哪个边界做一次
- [ ] 是否确定了唯一的规范化形式(通常为 NFC)
- [ ] 读取文件系统列表之后是否立即规范化
- [ ] 网络接收与 API 响应解析之后是否立即规范化
- [ ] 表单输入接收之后是否立即规范化
- [ ] 写入数据库之前是否统一
- [ ] 比较、排序、去重之前是否保证两边形式一致
- [ ] 截断(`slice`、`substring`)之前是否规范化
- [ ] 若用于哈希或签名，形式是否**以约定固定下来**
- [ ] 需要保留原始字节的地方，是否单独保存了规范化前的值

## 3. 经由外壳与工具 — 反斜杠有几层
- [ ] 是否把正则作为命令行参数传递(`-e`、`--pattern`)
- [ ] 如果传递，是否考虑到每多一层就要多一个反斜杠
- [ ] 从字符串构造正则时反斜杠是否写成两个
- [ ] 是否把构造出的正则**打印出来用眼睛确认过一次**
- [ ] 拼入模式的用户输入是否做了元字符转义
- [ ] 回归测试代码是否保存为**文件**而不是内联执行

### 一行自检
在构造正则对象之后立刻把它的字符串形式写进日志。
只要与预期不符就会当场暴露。这里永远不会抛出异常。

## 4. 字符范围 — 什么算韩文
- [ ] 若使用 `[가-힣]`，是否清楚它只覆盖**预组合音节**
- [ ] 是否用文字写下了以下哪些要放行、哪些要拒绝
  - [ ] 单独的辅音与元音(`ㄱ`、`ㅏ`)
  - [ ] 正在组合中的输入
  - [ ] 分解形(NFD)字符串
  - [ ] 古韩文字母
  - [ ] 兼容字母
  - [ ] 半角韩文
- [ ] 需要放宽时是否考虑过 `\p{Script=Hangul}`
- [ ] 属性转义是否带了 `u` 标志(缺失会悄悄变成另一种含义)
- [ ] 搜索索引是否按**先规范化、再范围检查**的顺序(顺序颠倒会漏掉分解形)

### 按用途推荐
| 用途 | 推荐范围 | 理由 |
|---|---|---|
| 混入与污染检测 | 宽(`\p{Script=Hangul}`) | 漏检会让检查器形同虚设 |
| 输入值校验 | 窄(`[가-힣]` 等) | 阻止保存组合中的字母 |
| 搜索索引 | 规范化后再放宽 | 防备分解形流入 |
| 统计与比例计量 | 宽 | 范围太窄会让数值差出几倍 |

## 5. 长度与截断 — 按什么单位计数
- [ ] 是否定义了「字数」的单位(码元 / 码位 / 字节 / 字素簇)
- [ ] 数据库列若按字节计，是否写明编码并做了换算
- [ ] 展示给用户的字数是否按**字素簇**计
- [ ] 预览截断是否会削掉音节的终声
- [ ] 该字段是否可能混入表情符号与组合字符

## 6. 回归测试 — 检验的是检查器本身
- [ ] 是否有 MUST_HIT 条目(必须命中的句子)
  - [ ] 敬语体
  - [ ] 陈述体
  - [ ] 连接形
  - [ ] 名词形
  - [ ] 口语形(按需)
- [ ] 是否有三种以上 MUST_MISS 条目(命中即误报)
  - [ ] 与规则无关的句子
  - [ ] 核心词被用作另一种含义的句子
  - [ ] 锚点词成为另一个词一部分的句子
- [ ] 样本句是否取自**真实正文**(凭空编写的句子文体不同)
- [ ] 故意破坏规则时测试是否会失败
- [ ] 是否记录每条规则的命中次数
- [ ] 长期零命中的规则是否会触发告警

### 测试骨架
```
MUST_HIT  = [敬语体, 陈述体, 连接形, 名词形, (口语形)]
MUST_MISS = [无关句, 另一含义, 属于另一个词]
结果 = MUST_HIT 全部命中 且 MUST_MISS 全部未命中
```

## 7. 上线前的最后三行
- [ ] 这条规则是否真的能抓到**一个敬语体句子**
- [ ] 这段代码是否真的能处理**一个分解形输入**
- [ ] 你是否**把构造出的正则打印出来看过**
