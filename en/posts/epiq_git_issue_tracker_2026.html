epiq Arrives - A Distributed Issue Tracker That Puts Issues Inside Git to Kill Context Switching

A terminal-native, event-sourced issue tracker reopens an old question - what offline, distributed, portable issue tracking is worth, and where it hits the limits of team collaboration

Jul 6, 2026 Dev & Infra

Intro: Why "Put Issues Inside Git" Is Back on the Table

In July 2026, what put issue trackers back up for debate was not a flashy new product but a very old question: why should issues live somewhere other than the code? epiq, a distributed issue tracker that stores issues entirely inside a Git repository and manages them from the terminal, reopened exactly that question. To developers used to GitHub Issues or Jira, this will sound unfamiliar, but the idea itself is not new. Around 2008, several teams built similar tools out of the same frustration, and most of them quietly disappeared.

This piece does not stop at listing epiq's features. It takes up, from my own vantage point, the question the tool reopens: the friction created when an issue tracker is separated from the code repository, and the trade-offs of moving issues into Git to remove that friction. I use the write-up on hada (GeekNews) as a starting point but do not reproduce it - instead I place epiq alongside prior art like git-appraise, Fossil, and git-issue to see what keeps failing the same way, and what is genuinely different in 2026.

The conclusion up front: the strengths and limits epiq runs into are not very different from what ticgit and Bugs Everywhere ran into more than a decade ago. But one variable has changed. The party reading and writing issues inside the repo is no longer only humans - it now includes AI coding agents working alongside them in the terminal.

1. What Is epiq - A Distributed Issue Tracker Inside the Terminal

epiq is an open-source project published on its GitHub repository, positioned as an issue tracker that runs entirely on a local Git repository with no account and no server.

1.1 Core Design - Event Sourcing and ULIDs

Rather than repeatedly mutating one shared file, epiq records issues as append-only events in per-user files. Each event carries a time-sortable identifier (a ULID) along with a reference to the last known event, so that even after several people work offline and merge later, the order in which events actually happened can be mechanically reconstructed. Handing issue data to Git's ordinary three-way merge invites text conflicts; keeping "who did what, when" as an event log instead is a design choice meant to shrink the conflict surface substantially at merge time.

1.2 A Dual Interface, Synced Through a Git Worktree

On the interaction side, epiq offers both a terminal UI with vim-style keybindings (h/j/k/l movement, a : command line, a ? command palette) and a browser GUI. Issue state lives in a dedicated Git branch and worktree that is managed automatically, keeping issue sync isolated from the ordinary flow of checking out and rebasing your working branch. This is a design meant to sidestep a mistake older issue-tracking tools often made: issue commits bleeding into the real code history and cluttering the log.

1.3 MCP Support - An Issue Tracker Built for AI Agents

epiq ships a separate MCP (Model Context Protocol) server binary so that AI coding agents such as Claude Code can read and write issues directly. I will come back to this, but it is exactly what reframes this tool from a mere "terminal-flavored issue tracker" into an "issue tracker for the agentic-coding era."

2. Context Switching - An Old Piece of Friction

Let's start with the problem epiq confronts head-on: the cost created when the issue tracker and the code repository are separate.

2.1 The Cost of Round-Tripping Through a Browser

Going from the editor to a browser to check one issue, then back to the editor, looks trivial, but it compounds. Some research puts the time needed to regain deep focus after such an interruption at roughly 20 minutes, and industry analyses convert this switching cost into a substantial annual productivity loss per developer. The exact figure matters less than the direction: the act of changing tools just to look at an issue is already a cost.

2.2 Why the Issue Tracker Grew Apart From the Code

So why did issue trackers evolve separately from code repositories in the first place? The reason is simple. A large share of an issue tracker's core users never write code. PMs, QA, designers, support staff, and sometimes customers themselves file issues and track their status. Asking them to access a Git repository and make a commit was never really an option. So the issue tracker naturally settled into a web service anyone could log into and fill out a form, and the trade-off was that developers who touch code ended up having to open one more window, every time. The friction epiq is trying to remove comes directly from this asymmetry.

3. Versioning Issues Alongside Code - The Advantages

The moment an issue becomes a Git object, three concrete gains follow.

3.1 It Never Breaks Offline

When an issue exists as a local Git object, it can be read and written regardless of network connectivity. On a plane, at a site with unreliable connectivity, or inside a closed network that only exposes an internal LAN, you can file and update issues and sync everything with a single push later. Stripping away the always-connected assumption that cloud issue trackers make is not a mere convenience feature - it is a difference in design philosophy.

3.2 It Travels With a Single Repository

One git clone carries the code and the entire issue history along with it. Even without a company SaaS account - even after that SaaS shuts down - the issue data stays intact inside the repository. Forking an open-source project and having its issues fork along with it is effectively impossible on GitHub Issues, but it is the default behavior of a Git-native issue tracker.

3.3 The Causal Link Between Commits and Issues Is Preserved

Which issues were open at a given commit, and what was discussed about them, can be reconstructed from Git history at that point in time alone, with no separate API call. Checking out an old branch and having the issue state of that era come along with it is simply a natural consequence of issues and code sitting on the same physical timeline. epiq's time-travel feature is aimed precisely at this point.

4. The Same Approach's Trade-offs - The Downsides

Listing only the upside would be unfair. The same design has clear costs too.

4.1 Even Event Sourcing Doesn't Fully Eliminate Conflicts

Event sourcing shrinks the conflict surface but does not eliminate it. If two people edit the same issue at the same time while offline, the rule many implementations use is that the event merged later tends to win, and in that case an earlier fix can be silently pushed aside on screen. Having a way to undo (time travel) and having a way to notice a conflict happened in the first place are two different things.

4.2 The Repository Gets Heavier, and Notifications and Search Stay Weak

As issue history accumulates, the repository's own size and clone cost grow with it. Even isolating things into a separate branch and worktree does not fully spare you from fetch/push traffic. More fundamentally, it is hard for a local-first tool to match the management features of a SaaS issue tracker - email notifications, full-text search, automatic assignment, burndown charts - at the same level. No notifications sounds minor, but it means that unless someone actively pulls, nobody finds out an issue was even opened.

4.3 Concerns About the Distribution Method

epiq is distributed two ways: a binary install script and an npm package. At a time when supply-chain trust is a live concern, wariness about piping an install script straight into a shell or using a global npm install is a common reaction, and concerns about the distribution method surfaced in community discussion after launch as well. Separate from the tool's own design, this is a trust barrier any local-first CLI tool has to clear.

5. Coordinates Against Existing Tools - GitHub Issues and Jira

Placing an epiq-style approach next to a SaaS issue tracker makes the trade-off explicit.

The table shows a trade-off, not a hierarchy. GitHub Issues and Jira demand always-on connectivity and account lock-in in exchange for organization-scale visibility and a mature surrounding ecosystem. epiq sits on the opposite side, trading organization-scale visibility for connectivity independence and portability.

6. Prior Art - git-appraise, Fossil, git-issue, and the Experiments of the Late 2000s

Treating epiq as an isolated new product misses a lot. The lineage of tools attempting the same idea is already long.

6.1 git-appraise - Code Review Stored in git-notes

Google's git-appraise targets code review rather than issues, but the philosophy is the same. Review requests, comments, and CI results are recorded in git-notes (refs/notes/devtools/*) with no separate server, so pushing and pulling the repository is enough to propagate the review history along with it. It can be read as an earlier proof, on the code-review side, of the "server-free distributed storage" epiq applies to issues.

6.2 Fossil - All-in-One, but a Narrow Ecosystem

Fossil, the distributed version control system built by SQLite's creator, integrated a ticket system, a wiki, and a forum into a single binary from the start. Even today, it is striking that running one fossil binary with no server setup gets you version control and issue tracking running side by side. But there have been consistent complaints that email notifications are hard to bolt on, and that a GitHub-style pull-request or code-review concept doesn't mesh with the ticket system. The integration is well done, but the prevailing assessment is that it falls short of the surrounding ecosystem (notifications, integrations, search) GitHub Issues provides.

6.3 git-issue - Plain Text Files With Two-Way Sync

dspinellis's git-issue is a middle path: it stores issues as plain text files while allowing two-way import and export with GitHub and GitLab. It keeps the local-first principle - no server needed, no issues lost if a server dies - while also leaving a channel open to sync with a central platform when needed, which is where it differs in character from epiq. That epiq does not yet foreground this level of two-way sync is worth noting.

6.4 ticgit, Bugs Everywhere, Ditz, SD, DisTract - A Landscape Left in Ruins

Around 2008, tools like ticgit (widely called the granddaddy of issues-in-a-branch systems), Bugs Everywhere, Ditz, SD, and DisTract all tried, almost simultaneously, to put issues "inside the version control system." One retrospective looking back on this era compares the ecosystem to a landscape left in ruins after a trench war, noting that most of these projects were later abandoned by their maintainers. The common cause of failure was not technical but social, on two counts: there was no on-ramp for non-developers, and nothing forced an entire team onto the same tool. epiq's event sourcing and worktree isolation meaningfully fix the technical flaws these older tools suffered (conflicts, log pollution), but both social conditions remain exactly as they were.

7. The Limits of Team Collaboration - Non-Developers and Visibility

This is the core warning of this piece. However technically refined an epiq-style tool becomes, two organizational walls stay in place.

7.1 Non-Developers Don't File Issues From a Terminal

The conclusion from the lineage above repeats itself exactly. The moment you ask a stakeholder used to web forms to learn vim keybindings and a command-line mode, that person either stops filing issues or routes around it through another channel - chat, email. epiq tries to lower this barrier by also offering a browser GUI, but that GUI, too, is a window into a local repository rather than an account-based central service, so the underlying premise - that every stakeholder must be able to reach the repository - does not change.

7.2 No Dashboards, Reporting, or Epics

Jira's epics, sprints, and burndown charts, and GitHub Projects' kanban boards and automation, exist to roll many issues up for organization-level reporting. A local-first issue tracker is powerful inside a single repository, but a central roll-up view spanning many repositories and many teams is, by design, a lower priority. Small teams with few issues won't feel this gap, but it shows up quickly as an organization grows.

8. Why It's Getting Attention Again in 2026 - Agentic Coding

Up to this point, epiq reads as just another rerun of old experiments. But there is one place where I read this tool differently.

8.1 The Collaborators Are No Longer Only Human

The core cause of failure a decade ago - lack of non-developer access - remains just as valid today. But in 2026, one new variable has entered the picture. The party working alongside you inside the repository is no longer only human - it now includes AI coding agents such as Claude Code. An agent has no discomfort with vim keybindings and needs no web login. If anything, it can read and write state exposed as local files and Git objects more cheaply and more directly than it can through an API call.

8.2 What MCP Changes About the Calculus

epiq shipping a dedicated MCP server so an agent can handle issues directly is a design aimed precisely at this. The conclusion that a web GUI is still needed for human stakeholders does not go away, but in a workflow where an agent repeatedly creates issues and updates their state, "living in the terminal" stops being a downside and becomes an advantage instead - direct access with no added latency. My read is that the reason for moving the issue tracker back inside the code repository is resurfacing in the agentic-coding era because the human context-switching problem has been rewritten as an agent tool-access problem. This connects to the view, discussed in my Code as Agent Harness analysis, of the codebase itself as the execution substrate for an agent.

9. Conclusion - Where Should You Actually Use This

epiq is a genuine signal, but also a tool that inherits old limitations along with it. As of July 2026, here is my practical read.

9.1 Where It Fits Well

A solo developer or small team, an environment with frequent offline work, and a workflow that wants to delegate part of issue management to an AI coding agent all get an immediate benefit from an epiq-style tool. In particular, if you already use terminal-based agent tooling, keeping issues in the same repository reduces fragmentation.

9.2 Where to Be Cautious

If non-developer stakeholders are actively involved in day-to-day work, or if email notifications, reporting, and compliance tracking are required, it is safer to keep GitHub Issues or Jira as the primary system. A security review of the unverified distribution channel (global npm install and the like) should also happen before adoption.

9.3 A Hybrid Compromise

As with the two-way sync model git-issue demonstrates, a compromise is possible: keep a local issue tracker as the system of record while exporting only select issues to a central platform. The right answer is not one tool, but designing where issues live differently depending on team composition and who you are collaborating with - humans or agents.
