자식 프로세스가 멈추는 진짜 이유 - 파이프 버퍼가 가득 차서 생기는 교착

작은 입력에서는 통과하고 실데이터에서만 멈춘다 - 경계값을 바이트 단위로 측정한 기록

2026-07-30 개발/인프라

서론: 아무 메시지도 없이 멈춰 있었다

야간 배치를 돌려 놓고 아침에 보면 스크립트가 어느 지점에 멈춰 있다. 오류 메시지가 없다. 예외 추적도 없다. 프로세스는 목록에 그대로 있고, CPU 사용률은 0퍼센트다. 로그의 마지막 줄은 몇 시간 전 시각에서 그대로다. 다시 돌리면 같은 자리에서 또 멈춘다. 그런데 어제 짧은 표본으로 돌렸을 때는 5초 만에 끝났다.

이 상황에서 대부분의 시간은 잘못된 곳에서 소모된다. 로직을 다시 읽고, 로그를 더 넣고, 락이나 네트워크를 의심한다. 그러나 코드에는 아무 문제가 없다. 원인은 코드가 아니라 파이프의 버퍼 크기이고, 그것은 소스 어디에도 적혀 있지 않은 숫자다. 그래서 아무리 코드를 읽어도 보이지 않는다.

이 글은 그 숫자를 직접 재고, 그 숫자가 만드는 경계를 바이트 단위로 확인한 기록이다. 결론부터 요약하면 세 문장이다.

  • 파이프는 유한한 버퍼다. 무한한 통로가 아니라 정해진 크기의 상자이고, 이 환경에서는 4096바이트였다
  • 가득 차면 쓰는 쪽이 대기한다. 이것은 버그가 아니라 흐름 제어다. 뒷단이 느려도 파이프라인은 정상 완료한다. 대기 자체는 정상이다
  • 교착은 읽어 줄 사람이 이미 다른 것을 기다릴 때 생긴다. 즉 문제의 형태는 「둘 다 상대를 기다리는 구조」다

그리고 이 구조가 무서운 진짜 이유는 마지막 한 가지다. 출력이 버퍼보다 작으면 아무 일도 일어나지 않는다. 단위 테스트가 쓰는 표본은 거의 항상 버퍼보다 작다. 그래서 이 결함은 모든 테스트를 통과하고, 운영에서 실데이터를 만나는 첫날에만 나타난다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 셸은 GNU bash 5.2.37 (MSYS2 / MINGW64), 런타임은 Python 3.13.3 (win32)과 Node.js v22.16.0 (win32)이다. 스크립트는 모두 파일로 저장해 실행했고, 교착을 재현하는 실험이라 모든 실행에 10초 이내의 타임아웃을 걸었다. 타임아웃에 걸린 것은 「교착 확인」으로 기록했다.

★버퍼 용량은 환경마다 다르다. 아래 숫자는 이 환경의 실측값이고, 다른 운영체제·셸·런타임에서는 다른 값이 나온다. 실제로 같은 기계 안에서도 경로에 따라 세 가지 다른 값이 나왔다. 그래서 이 글은 숫자를 외우라고 하지 않고 재는 방법을 보여준다. 예제 경로는 /tmp/demo 같은 자리표시자로 적었다.

이 글이 다루지 않는 것. 파이프라인의 종료 코드 규약과 PIPESTATUS, 파이프 실패를 알아채는 방법은 종료 코드와 파이프에서 이미 다뤘다. 여기서는 버퍼가 차서 생기는 교착 한 점에만 집중한다. 파일명에 공백이 섞여 파이프라인이 깨지는 문제는 find와 xargs의 공백 함정, 인용 규칙은 셸 인용 규칙에 있다.

1. 파이프는 유한한 버퍼다 - 이 환경에서 4096바이트

먼저 용량을 직접 재야 한다. 파이프를 하나 만들고, 읽는 쪽은 건드리지 않은 채 쓰기만 계속했다. 어느 지점에서 쓰기가 돌아오지 않으면 그것이 용량이다. 무한 대기에 빠지지 않도록 쓰기는 별도 스레드에 두고 5초 후에 상태를 확인했다.

python 3.13.3 / win32
--- 1-1. raw os.pipe() capacity: write until it blocks ---
  writer thread is STILL BLOCKED after 5.0s  <- pipe is full
  bytes accepted before blocking : 4096

--- 1-2. same measurement, 1 byte at a time (exact) ---
  blocked after exactly 4096 bytes

--- 1-3. drain the pipe, does the writer resume? ---
  read 4608 bytes from the read end
  writer counter is now 8704 (was 8704)

--- 1-4. subprocess stdin pipe: child never reads ---
  parent is BLOCKED writing to a child that never reads
  bytes accepted : 4096
  child killed, test over

세 가지를 읽어야 한다. 첫째, 정확히 4096바이트다. 512바이트 단위로 재도 4096, 1바이트 단위로 재도 4096이었다. 어림수가 아니라 딱 떨어지는 값이다. 둘째, 쓰기 스레드는 죽지 않고 대기했다. 오류가 아니라 대기라는 점이 핵심이다. 셋째, 읽는 쪽에서 4608바이트를 빼내자 쓰기가 그대로 이어졌다. 카운터가 8704까지 올라갔다.

이 마지막 관찰이 이 글의 전제를 세운다. 파이프가 가득 차서 쓰는 쪽이 대기하는 것은 고장이 아니다. 자리가 나면 알아서 이어진다. POSIX 규격도 같은 이야기를 한다. 논블록 플래그가 없으면 「쓰기 요청이 스레드를 블록시킬 수 있으나, 정상 완료 시에는 요청한 바이트 수를 반환한다」고 적혀 있다. 즉 설계된 동작이다.

1-4는 방향만 바꾼 같은 실험이다. 자식 프로세스를 띄우고 표준 입력을 파이프로 연 다음, 자식이 아무것도 읽지 않게 했다. 부모가 써 넣을 수 있었던 양도 같은 4096바이트였다. 파이프는 어느 방향으로 쓰든 같은 상자다.

1.1 같은 기계에서 값이 세 개로 갈렸다

그런데 여기서 조심할 것이 있다. 이 4096이라는 값은 이 경로에서만 나온 값이다. 같은 기계에서 다른 경로를 재 보니 전부 달랐다.

계층이 환경 실측재는 방법성격
네이티브 Windows 익명 파이프4096 B읽지 않는 파이프에 1바이트씩 쓰기운영체제 커널 버퍼
MSYS2 셸 파이프65536 B뒷단이 잠든 파이프라인에 쓰기셸 런타임이 만드는 파이프
Node 스트림 수위 표시16384 B스트림 속성 조회사용자 공간 버퍼
Node 미소비 stdout 정지 경계131073 B소비하지 않고 종료 대기, 이분 탐색위 두 층의 합성 결과

표의 마지막 두 줄이 특히 중요하다. Node의 정지 경계 131073바이트는 운영체제 파이프 용량도 아니고 스트림 수위 표시도 아니다. 두 값의 단순한 합도 아니다. 여러 층이 겹쳐 만든 결과값이고, 나는 그 내부 회계를 정확히 확인하지 못했다. 그래서 이 숫자는 측정값으로만 제시하고 공식으로 일반화하지 않는다.

  • 여러분 환경의 값은 여기 적힌 어느 숫자와도 다를 수 있다. 리눅스와 Windows, 셸 종류, 런타임 버전이 모두 변수다
  • 그래서 실무적으로 유용한 것은 숫자가 아니라 재는 절차다. 1-1의 실험은 열 줄이면 재현된다
  • 더 중요한 사실은 개발 환경과 운영 환경의 값이 다를 수 있다는 것이다. 개발에서 통과하고 운영에서만 멈추는 두 번째 이유가 여기 있다
  • 컨테이너 안팎, 로컬과 CI, 셸을 거치는 실행과 직접 실행이 모두 다른 경로다. 하나에서 통과한 것이 다른 하나를 보장하지 않는다

2. 교착 재현 - 4096과 4097 사이

이제 실제 사고 형태를 만든다. 가장 흔한 잘못된 코드는 이 순서다. 자식을 띄우고, 대기를 먼저 하고, 그다음에 출력을 읽는다. 읽기 전에 기다렸다는 점이 함정 전부다.

python 3.13.3 / win32

--- 2-1. parent calls wait() first: small vs large output ---
  child writes     1024 B -> wait(3s) : finished (0.10s)
  child writes     4096 B -> wait(3s) : finished (0.10s)
  child writes     4097 B -> wait(3s) : DEADLOCK (2.01s)
  child writes     8192 B -> wait(3s) : DEADLOCK (2.02s)
  child writes    65536 B -> wait(3s) : DEADLOCK (2.01s)
  child writes  1048576 B -> wait(3s) : DEADLOCK (2.01s)

--- 2-2. bisect the exact boundary ---
  largest output that does NOT deadlock : 4096 bytes
  smallest output that DOES deadlock    : 4097 bytes
  probes                                : 13

이 표가 이 글의 심장이다. 4096바이트는 0.10초에 끝나고, 4097바이트는 영구 대기에 들어간다. 코드는 한 글자도 다르지 않다. 자식이 쓰는 바이트 수가 1바이트 늘어난 것뿐이다.

DEADLOCK 표시는 「타임아웃에 걸렸다」는 뜻이다. 대기 호출에 2초 상한을 두고, 상한을 넘으면 교착으로 판정했다. 상한 없이 돌리면 이 실험 자체가 끝나지 않는다. 교착을 다루는 실험에는 반드시 타임아웃을 걸어야 한다는 것이 첫 실무 교훈이다.

이분 탐색으로 13번 찔러 경계를 확정했다. 통과하는 최대치가 4096, 멈추는 최소치가 4097. 이 값은 1절에서 잰 파이프 용량과 정확히 같다. 우연이 아니고, 그것이 원인이라는 증거다.

2.1 왜 멈추는지 - 두 문장으로

구조는 단순하다. 자식은 파이프에 자리가 나기를 기다린다. 부모는 자식이 끝나기를 기다린다. 자리를 낼 수 있는 사람은 부모뿐인데 부모는 대기 중이다. 자식을 끝낼 수 있는 것은 쓰기 완료뿐인데 그것이 막혀 있다. 서로가 상대의 다음 행동을 기다리는 원이 닫혔다.

  • 출력이 4096바이트 이하면 자식은 전부 써 넣고 그냥 종료한다. 파이프에 데이터가 남아 있어도 자식은 이미 없다. 그래서 대기가 즉시 돌아온다
  • 출력이 4097바이트면 마지막 1바이트를 쓰지 못해 자식이 종료하지 못한다. 대기는 영원히 돌아오지 않는다
  • 이 차이가 어디에도 로그로 남지 않는다. 예외도 없고 오류 코드도 없다. 두 프로세스가 조용히 서로를 기다린다
  • 그래서 증상이 「멈춤」이다. 「실패」가 아니라 아무 일도 일어나지 않음이고, 이것이 진단을 어렵게 만든다

Python 공식 문서는 이 위험을 명시하고 있다. 대기 호출 설명에 「stdout=PIPE 또는 stderr=PIPE를 쓰고 자식이 운영체제 파이프 버퍼가 더 받아 줄 때까지 블록될 만큼 충분한 출력을 만들면 이 호출은 교착에 빠진다」고 적혀 있다. 문서에 적힌 그대로가 실측으로 재현된 것이다.

3. 왜 테스트는 통과하는가

2절의 경계가 이 결함의 성질을 결정한다. 4096바이트는 아무것도 아닌 크기다. 텍스트로는 대략 한글 1,300자, 로그로는 40~50줄이다. 단위 테스트에 넣는 표본이 이보다 큰 경우는 드물다.

상황출력 크기이 환경에서결과
단위 테스트의 짧은 표본수백 B버퍼 안에 다 들어감통과
손으로 확인한 예제 파일1~2 KB버퍼 안에 다 들어감통과
경계 근처4096 B정확히 꽉 찬 상태통과 (0.10초)
경계에서 1바이트 초과4097 B마지막 쓰기가 막힘영구 대기
운영 데이터 한 건수십 KB한참 전에 막힘영구 대기
오류가 많이 난 날수 MB표준 오류에서 막힘영구 대기

표의 마지막 줄이 실무에서 특히 악질적이다. 평소에는 잘 돌던 배치가 하필 오류가 많이 난 날 멈춘다. 경고 로그가 늘어나 표준 오류 출력이 버퍼를 넘긴 것인데, 겉으로는 「장애가 났더니 배치까지 멈췄다」로 보인다. 원인과 결과가 뒤바뀐 채로 조사가 시작된다.

  • 이 결함은 재현이 쉽다. 표본 크기만 키우면 100퍼센트 재현된다. 문제는 아무도 그 시도를 하지 않는다는 것이다
  • 반대로 작은 표본으로는 절대 재현되지 않는다. 그래서 「내 환경에서는 잘 되는데」가 성립한다
  • 따라서 테스트 표본에 버퍼 용량보다 큰 것을 하나 넣는 것이 가장 값싼 방어다. 1절 방법으로 용량을 재고 그보다 큰 표본을 만들면 된다
  • 더 좋은 것은 크기와 무관하게 안전한 구조로 코드를 바꾸는 것이다. 4절부터가 그 이야기다

4. 해결 ① 먼저 읽고, 그다음에 기다린다

가장 단순한 해결은 순서를 뒤집는 것이다. 출력을 다 읽어 파이프를 비운 다음에 대기한다.

--- 2-3. FIX A: read the output first, then wait ---
  read 1048576 bytes, then wait() returned 0 in 0.09s

--- 2-4. FIX A': communicate() does the same thing for you ---
  communicate() -> 1048576 bytes, rc=0, 0.10s

2절에서 영구 대기에 빠뜨렸던 것과 같은 1048576바이트가 0.09초에 끝났다. 바꾼 것은 두 줄의 순서뿐이다. 읽는 동안 파이프가 계속 비워지므로 자식이 막힐 일이 없고, 자식이 끝나면 스트림이 닫혀 읽기도 끝난다.

2-4는 그 일을 해 주는 표준 함수를 쓴 것이다. Python 문서는 「다른 운영체제 파이프 버퍼가 차서 자식이 블록되는 교착을 피하려면 직접 쓰기·읽기 대신 통합 함수를 쓰라」고 권한다. 다만 문서는 대가도 함께 적어 뒀다. 「읽은 데이터는 메모리에 버퍼링되므로 데이터 크기가 크거나 무한하다면 이 메서드를 쓰지 말라」는 것이다. 실제로 확인해 보면 그 대가가 눈에 보인다.

--- 9-4. streaming a huge output line by line: constant memory ---
  streamed 200000 lines in 0.31s, largest object held = 12 chars

--- 9-5. the same data via communicate(): held entirely in memory ---
  communicate() -> one object of 2600000 bytes (2.5 MB) in 0.53s

같은 20만 줄을 두 방식으로 받았다. 한 줄씩 스트리밍하면 어느 순간에도 12자짜리 객체 하나만 들고 있었다. 통합 함수를 쓰면 2.5메가바이트 객체 하나가 메모리에 올라온다. 20만 줄은 작은 편이다. 출력 상한이 없는 자식이라면 이 방식은 언젠가 메모리로 터진다.

  • 출력 상한이 확실하고 작다면 통합 함수가 가장 안전하고 짧다. 상한을 코드 주석에 적어 두면 더 좋다
  • 상한이 없다면 스트리밍이나 파일로 받아야 한다. 통합 함수는 교착은 막지만 메모리 문제를 남긴다
  • 스트리밍은 메모리 상한이 한 줄이라는 점에서 구조적으로 우월하다. 20만 줄이 0.31초에 처리됐다
  • 단, 스트리밍은 자식의 출력 버퍼링에 영향을 받는다. 9절에서 다룬다

5. 가장 잘 걸리는 함정 - 두 파이프, 한 명의 독자

지금까지는 파이프가 하나였다. 실무 코드는 대개 표준 출력과 표준 오류를 둘 다 파이프로 연다. 오류 메시지도 잡아야 하니 당연한 선택이다. 그런데 읽는 코드는 보통 하나뿐이다. 여기서 파이프가 두 개인데 독자가 한 명이 된다.

--- 2-5. the classic trap: stdout AND stderr piped, only stdout read ---
  stdout.read() has NOT returned after 4.0s -> DEADLOCK
  child alive : True   (it is blocked writing stderr)

자식은 표준 오류에 200000바이트를 쓰고, 표준 출력에는 10바이트만 쓴다. 부모는 표준 출력만 읽는다. 표준 출력은 10바이트뿐인데도 읽기가 끝나지 않았다. 4초를 기다려도 돌아오지 않았고 자식은 살아 있었다.

이 경우가 특히 악질적인 이유는 내가 읽는 스트림에는 아무 문제가 없다는 점이다. 표준 출력은 10바이트, 버퍼의 400분의 1이다. 코드를 아무리 봐도 「출력이 커서 막혔다」는 그림이 안 나온다. 막힌 곳은 내가 열어 놓고 쳐다보지 않는 다른 파이프다.

Node에서도 똑같이 재현됐다. 그리고 Node에는 층이 하나 더 있어서 경계값이 훨씬 크다.

node v22.16.0 / win32 / 10.0.19045

주목할 것은 65536바이트가 통과했다는 점이다. Python이라면 한참 전에 막힌 크기다. Node는 운영체제 파이프에서 읽은 데이터를 자기 스트림 버퍼에 쌓아 두기 때문에 더 오래 버틴다. 그래서 Node에서는 이 결함이 더 늦게, 더 큰 데이터에서만 드러난다. 좋은 소식이 아니다. 개발 중에 발견될 확률이 그만큼 낮다는 뜻이다.

Node 공식 문서는 이 상황을 정확히 기술해 놓았다. 「기본적으로 부모 Node 프로세스와 자식 사이에 표준 입력·출력·오류 파이프가 만들어진다. 이 파이프들은 제한된, 그리고 플랫폼에 따라 다른 용량을 가진다. 자식이 출력을 캡처하지 않은 상태로 그 한계를 넘겨 쓰면, 자식은 파이프 버퍼가 더 받아 줄 때까지 기다리며 블록된다」고 적혀 있다. 「플랫폼에 따라 다른 용량」이라는 표현이 1절의 표를 그대로 설명한다.

6. 해결 ② 동시에 읽기, ③ 파일로 받기, ④ 하나로 합치기

두 파이프 문제의 해결은 세 방향이다. 셋 다 실행해서 확인했다.

--- 2-6. FIX B: read stderr concurrently in a thread ---
  stdout 10 B, stderr 200000 B, rc=0, 0.10s -> no deadlock

--- 2-7. FIX B': communicate() reads both streams at once ---
  communicate() -> stdout 10 B, stderr 200000 B, rc=0, 0.20s

--- 2-8. FIX C: give the child a real file instead of a pipe ---
  wait() first with files: rc=0 in 0.10s
  out.tmp 10 B, err.tmp 200000 B

--- 2-9. FIX D: merge stderr into stdout (one pipe, one reader) ---
  merged read 200010 B, rc=0, 0.09s
  first 4 bytes b'EEEE'  last 4 bytes b'OOOO'
  count O=10  E=200000

해결 ② 동시에 읽기. 표준 오류를 읽는 스레드를 따로 띄우고 본 스레드는 표준 출력을 읽었다. 4초를 넘겨도 안 끝나던 것이 0.10초에 끝났다. 비동기 런타임이라면 스레드 대신 동시 대기로 같은 일을 한다. 원칙은 하나다. 파이프를 연 스트림 수만큼 읽는 주체가 있어야 한다.

해결 ③ 파일로 받기. 2-8이 흥미롭다. 출력을 임시 파일로 받으면 대기를 먼저 해도 안전하다. 2절에서 영구 대기를 만들었던 그 순서인데 이번엔 0.10초에 끝났다. 이유는 명확하다. 일반 파일에는 「가득 찼다」는 상태가 없다. 파이프는 고정 크기 상자지만 파일은 디스크가 허용하는 만큼 커진다. 그래서 쓰는 쪽이 대기할 이유가 없고, 교착의 전제 자체가 사라진다.

해결 ④ 하나로 합치기. 표준 오류를 표준 출력으로 합치면 파이프가 하나가 되므로 독자 한 명으로 충분하다. 200010바이트를 0.09초에 다 받았다. 그런데 출력의 앞 4바이트가 EEEE이고 뒤 4바이트가 OOOO다. 자식이 표준 출력을 먼저 썼는데 결과에서는 표준 오류가 앞에 왔다. 순서가 뒤집혔다.

6.1 합치기의 대가 - 순서가 섞인다

이 현상을 짧은 예로 다시 확인했다. 자식이 표준 출력과 표준 오류를 번갈아 세 번씩 쓰게 했다.

--- 2-10. the price of merging: ordering gets scrambled ---
  merged (default buffering):
    ERR-0

    OUT-1
    OUT-2
  merged (PYTHONUNBUFFERED=1):
    OUT-0
    ERR-0
    OUT-1
    ERR-1
    OUT-2

  same bytes? False

자식이 쓴 실제 순서는 OUT-0, ERR-0, OUT-1, ERR-1, OUT-2, ERR-2다. 기본 설정으로 합쳤을 때는 표준 오류 세 줄이 먼저 나오고 표준 출력 세 줄이 나중에 나왔다. 완전히 다른 이야기로 읽힌다.

원인은 파이프가 아니라 프로그램 자신의 출력 버퍼다. 표준 오류는 대개 버퍼링하지 않고 즉시 내보내고, 표준 출력은 파이프에 연결되면 블록 버퍼로 바뀌어 종료 시점에 한꺼번에 나간다. 그래서 시간 순서가 재배열된다. 무버퍼 스위치를 켜면 실제 순서가 그대로 복원됐다.

  • 순서가 중요한 로그를 합치면 안 된다. 진행 로그와 오류를 시간 순으로 읽어야 하는 상황에서 이것은 치명적이다
  • 합치는 것이 편한 경우는 순서를 안 보는 경우다. 실패 시 전체 출력을 덩어리로 저장해 두는 용도라면 문제없다
  • 순서도 지키고 파이프도 하나로 두고 싶으면 자식을 무버퍼로 돌려야 한다. 위 출력의 두 번째 블록이 그것이다
  • 합쳐 놓고 나중에 「표준 오류만 골라내기」는 불가능하다. 합치는 순간 출처 정보가 사라진다

Node 쪽 해결도 대칭적으로 확인했다.

4-4가 재미있다. 데이터를 버리기만 해도 교착이 풀린다. 내용을 쓰지 않을 거라도 스트림을 흐르게 해 주면 자식은 막히지 않는다. 물론 애초에 출력을 볼 생각이 없다면 파이프를 만들지 않는 것이 정답이다. Node 문서도 「출력을 소비하지 않을 것이면 무시 옵션을 쓰라」고 못 박고 있다.

4-7과 4-8은 상한이 있는 방식의 성격을 보여준다. execFile의 기본 상한은 문서상 1메가바이트이고, 넘으면 멈추는 대신 오류를 준다. 자식은 종료되고 출력은 잘린다. 교착보다는 훨씬 낫다. 조용히 멈추는 것보다 시끄럽게 실패하는 것이 언제나 낫다.

7. 셸 파이프라인 - 흐름 제어는 버그가 아니다

같은 원리가 셸에서도 작동하는데, 여기서는 대개 문제가 되지 않는다. 그 이유를 아는 것이 교착과 흐름 제어를 가르는 기준이 된다.

3-1이 1절 표의 두 번째 줄이다. 셸 파이프 용량은 65536바이트로, 같은 기계의 네이티브 파이프보다 16배 크다. 두 가지 다른 측정 단위로 재도 같은 값이었다.

3-3이 이 절의 요점이다. 뒷단이 2초 동안 아무것도 읽지 않게 해 놓았다. 앞단은 65536바이트를 채운 뒤 대기했다. 그런데 파이프라인은 2455밀리초에 종료 코드 0으로 정상 완료했다. 2초를 자고 일어난 뒷단이 읽기 시작하자 앞단이 그대로 이어져 끝까지 갔기 때문이다.

이것이 흐름 제어다. 파이프는 빠른 생산자와 느린 소비자의 속도를 자동으로 맞춘다. 생산자가 대기하는 것은 낭비가 아니라 메모리를 무한히 쓰지 않기 위한 설계다. 이 장치가 없으면 느린 소비자 앞에서 생산자가 메모리를 다 먹는다.

3-4는 반대 방향의 사고다. 읽는 쪽이 먼저 끝나면 쓰는 쪽은 대기하는 대신 종료 신호를 받는다. PIPESTATUS 첫 칸이 141로 나온 것이 그 흔적이다. 이 값의 의미와 파이프라인 종료 코드 규약은 종료 코드와 파이프에서 다뤘으니 여기서는 방향만 짚어 둔다. 교착은 읽는 쪽이 안 읽어서, 이쪽은 읽는 쪽이 먼저 가 버려서 생긴다.

덧붙일 관찰이 하나 있다. 같은 상황에서 네이티브 Windows 프로그램을 앞단에 두면 신호 대신 쓰기 오류가 났다. 종료 코드는 1이었고 오류 메시지는 잘못된 인자를 뜻하는 것이었다. 즉 「읽는 쪽이 사라졌다」는 사실이 전달되는 방식조차 환경에 따라 다르다. 종료 코드로 원인을 특정하려면 자기 환경에서 먼저 확인해야 한다.

8. 버퍼는 한 층이 아니다

지금까지 파이프 버퍼만 이야기했지만, 실제로는 층이 하나 더 있다. 프로그램 자신의 출력 버퍼다. 이 둘은 완전히 별개이고, 섞어 생각하면 진단이 어긋난다.

--- 5-1. what Python says about its own stdout buffering ---

  • 반환값을 무시하면 교착 대신 메모리 고갈이 온다. 증상만 바뀌고 문제는 남는다
  • 반대로 읽기 쪽은 여전히 교착한다. 5절의 131073바이트가 그것이다
  • 즉 런타임이 다르면 같은 원인이 다른 증상으로 나온다. 「우리는 Node니까 괜찮다」는 판단은 절반만 맞다

  • 진행 표시가 안 나오는 원인의 대부분은 프로그램이 느린 것이 아니라 버퍼에 고여 있는 것이다. 5-2와 5-3의 프로그램은 완전히 동일하다
  • 고치는 것은 생산자 쪽이다. 읽는 쪽에서 할 수 있는 일이 없다. 이미 파이프에 안 들어온 데이터는 읽을 방법이 없다
  • 런타임에 맞는 스위치를 써야 한다. 환경 변수와 실행 옵션은 이 환경에서 거의 같은 결과를 냈다 (200밀리초 대 210밀리초)
  • 이 지연은 교착과 무관하다. 두 문제를 혼동하면 엉뚱한 곳을 고친다

10. 둘 다 상대를 기다리는 구조 - 양방향 교착

지금까지는 출력 방향만 봤다. 자식에게 큰 입력도 넣어야 하면 교착이 가장 순수한 형태로 나타난다. 부모가 입력을 전부 쓰고 나서 출력을 읽는 순서다. 그런데 여기서 예상 밖의 결과가 나왔다.

--- 6-1. child A (reads all, then writes) - like sort ---
  payload     4096 B -> ok         (wrote 4096 B, echoed 4096 B, 0.09s)
  payload    65536 B -> ok         (wrote 65536 B, echoed 65536 B, 0.09s)
  payload  1048576 B -> ok         (wrote 1048576 B, echoed 1048576 B, 0.10s)
  payload  4194304 B -> ok         (wrote 4194304 B, echoed 4194304 B, 0.14s)

--- 6-2. child B (streaming filter) - like cat / grep / sed ---
  payload     1024 B -> ok         (wrote 1024 B before stopping, 0.10s)
  payload     4096 B -> ok         (wrote 4096 B before stopping, 0.10s)
  payload     8192 B -> ok         (wrote 8192 B before stopping, 0.09s)
  payload    16384 B -> DEADLOCK   (wrote 10240 B before stopping, 3.01s)
  payload    65536 B -> DEADLOCK   (wrote 10240 B before stopping, 3.01s)
  payload  1048576 B -> DEADLOCK   (wrote 10240 B before stopping, 3.01s)

--- 6-3. verify the bracket, then bisect the streaming case ---
  bracket check: 1 B hangs=False   65536 B hangs=True
  largest payload that survives : 9216 B
  smallest payload that hangs   : 9217 B
  probes : 16

자식이 어떤 종류인지에 따라 결과가 완전히 갈렸다. 이것이 이 실험에서 가장 실용적인 발견이다.

  • 입력을 전부 읽고 나서 출력하는 자식(정렬 도구 같은 부류)은 4메가바이트를 넣어도 교착하지 않았다. 자식이 계속 읽어 주므로 부모의 쓰기가 막히지 않고, 다 쓴 뒤에는 부모가 읽기로 넘어가 있기 때문이다
  • 읽으면서 동시에 쓰는 스트리밍 필터(문자열 검색이나 치환 도구 부류)는 9217바이트부터 교착했다. 자식이 출력 파이프에서 막히면 읽기를 멈추고, 그러면 부모의 쓰기도 막힌다
  • 즉 같은 부모 코드가 상대에 따라 통과하거나 멈춘다. 파이프라인의 중간 도구를 하나 바꿨더니 멈추기 시작하는 사고가 여기서 나온다
  • 부모 코드만 봐서는 판단할 수 없다는 뜻이다. 자식이 스트리밍이냐 아니냐를 알아야 한다

경계값 9216바이트를 분해하면 구조가 눈에 보인다. 4096 + 4096 + 1024 = 9216이다. 자식의 출력 파이프 4096바이트가 차고, 부모의 입력 파이프 4096바이트가 차고, 마지막 1024바이트 덩어리가 전달 중인 상태에서 원이 닫힌다. 두 파이프 용량의 합이 그대로 경계로 나타났다. 이것이 「둘 다 상대를 기다리는 구조」의 산술적 증거다.

--- 6-4. FIX: feed and drain at the same time ---
  communicate() 4 MB in -> 4194304 B out, rc=0, 0.12s

--- 6-5. FIX: writer thread + reader in the main thread ---
  writer thread + main-thread reader -> 4194304 B, rc=0, 0.12s

해결은 하나뿐이다. 넣는 일과 빼는 일을 동시에 한다. 통합 함수에 맡기든 쓰기를 별 스레드로 빼든, 4메가바이트가 0.12초에 끝났다. 순서를 나누는 순간 교착이 되고, 겹치는 순간 풀린다.

11. 멈춘 프로세스 진단 절차

이제 실무 상황이다. 눈앞에 멈춘 프로세스가 있고, 이것이 이 문제인지 판별해야 한다. 특수한 도구 없이 다섯 단계로 가른다. 실제로 교착 상태를 만들어 놓고 절차를 밟았다.

--- 7-1. start a pipeline that is stuck on purpose, then look at it ---
  step 1: are both ends still alive?
          372     369     365      22220  ?         197609 13:40:40 /usr/bin/sleep
          373     370     370       7504  ?         197609 13:40:40 .../python      

  step 2: is the writer making progress? (sample the counter twice)
    bytes written at t=2s : 65536
    bytes written at t=4s : 65536
    -> FROZEN at the same byte count

  step 3: is it burning CPU (a loop) or waiting (blocked)?
    CPU seconds sample 1 : 0.109375
    CPU seconds sample 2 : 0.109375
    -> equal CPU time + alive process = BLOCKED, not looping

  step 4: the decisive test - shrink the payload
     65536 B payload -> writer exit=0  (0 = finished on its own)
    400000 B payload -> writer exit=124  (124 = still blocked when timeout killed it)
    got 65536 B in before blocking
    same code, only the size changed -> the cause is the pipe buffer

네 단계를 순서대로 읽으면 판정이 좁혀진다.

  • 1단계, 생존 확인. 프로세스 목록에 양쪽이 다 보인다. 죽어서 멈춘 것이 아니라 살아서 기다리는 것이다. 이것만으로 「크래시」 가설이 지워진다
  • 2단계, 진척 확인. 쓴 바이트 수가 2초 시점과 4초 시점에 모두 65536이었다. 얼어붙었다. 7절 표에서 흐름 제어와 교착을 가르는 기준이 이것이다
  • 3단계, CPU 확인. 누적 CPU 시간이 0.109375에서 0.109375로 그대로였다. 무한 루프면 이 값이 올라간다. 안 올라갔으므로 계산이 아니라 대기다
  • 4단계, 결정적 시험. 크기만 바꿔 같은 코드를 두 번 돌렸다. 65536바이트는 종료 코드 0으로 정상 종료했고, 400000바이트는 차단 상태로 강제 종료되어 124를 남겼다. 들어간 양은 정확히 65536바이트, 즉 셸 파이프 용량이었다
  • 5단계, 코드 확인. 대기 호출이 읽기보다 앞에 있는지, 파이프로 열어 놓고 소비하지 않는 스트림이 있는지 본다. 앞의 네 단계가 참이면 여기에 반드시 원인이 있다

4단계가 왜 결정적인지 강조할 만하다. 크기 말고 아무것도 바꾸지 않았다. 코드도 환경도 입력 내용도 같다. 그런데 결과가 갈렸다. 이보다 명확한 증거는 없다. 그리고 이 시험은 특별한 도구가 전혀 필요 없다.

관찰판정다음 행동
양쪽 살아 있음 + CPU 시간 정지어딘가에서 블록2·4단계로 파이프인지 확인
살아 있음 + CPU 시간 상승무한 루프파이프 문제 아님. 로직을 본다
진척이 두 표본에서 동일정지교착 유력
진척이 느리지만 움직임흐름 제어정상. 느린 쪽을 개선
크기를 줄이면 통과파이프 버퍼 교착 확정4·6·10절의 해결 적용
크기와 무관하게 항상 멈춤파이프 문제 아님락·네트워크·입력 대기를 본다
자식은 끝났는데 부모가 안 끝남스트림 미소비 또는 미닫힘파이프를 연 스트림 수를 센다

도구에 관해 덧붙인다. 이 환경에서 쓸 수 있었던 것은 프로세스 목록 조회와 CPU 시간 조회뿐이었다. 열린 파일을 보는 도구나 디버거는 없었고, 시스템 호출 추적 도구는 있었지만 이미 돌고 있는 네이티브 프로세스에 붙일 수 없었다. 그래서 위 절차는 의도적으로 어디서나 되는 것만으로 구성했다. 진척 샘플링과 크기 축소 시험은 도구가 아무것도 없는 환경에서도 된다.

12. 타임아웃, 스트리밍, 부모가 죽었을 때

실무에서 함께 걸리는 세 가지를 더 확인했다. 첫째는 타임아웃의 함정이다.

--- 9-1. wait(timeout=) does NOT kill the child; run(timeout=) does ---
  Popen.wait(1.5) raised TimeoutExpired
  child alive right after the exception : True
  after an explicit kill(), alive        : False

--- 9-2. run(timeout=) on a big output: does it survive? ---
  run(capture_output=True, timeout=5) -> rc=0, 2097152 B, 1.23s

--- 9-3. the trap: check_output on a child that also writes stderr ---
  check_output, stderr NOT a pipe (DEVNULL) -> 10 B, 0.38s
  check_output(stderr=PIPE)  -> 10 B, 1.15s

9-1이 중요하다. 대기 호출에 상한을 걸고 예외를 받았는데 자식은 그대로 살아 있었다. 타임아웃은 「내가 기다리기를 그만둔다」는 뜻이고 「상대를 끝낸다」는 뜻이 아니다. 명시적으로 종료시키자 비로소 사라졌다.

  • 타임아웃만 걸고 종료를 안 하면 고아 프로세스가 쌓인다. 배치가 반복 실행되는 환경에서 이것이 조용히 자원을 먹는다
  • 예외를 잡은 자리에서 반드시 종료를 호출해야 한다. 그리고 종료 후 회수까지 해야 한다
  • 9-2와 9-3이 보여주듯 고수준 함수는 이 처리를 해 준다. 2메가바이트 출력이 상한 안에서 정상 종료했고, 표준 오류를 파이프로 열어도 교착하지 않았다
  • 즉 직접 조립할 이유가 없으면 고수준 함수를 쓰는 것이 안전하다. 교착의 대부분은 직접 조립한 코드에서 나온다

둘째는 부모가 먼저 죽었을 때다. 이 경우 자식이 어떻게 되는지 두 종류로 나눠 확인했다.

--- 10-1. orphan that keeps WRITING to the dead parent's pipe ---
  1.5s after the parent exited, still running : False
  -> its next write failed, so it terminated on its own

--- 10-2. orphan that is NOT writing (just sleeping) ---
  1.5s after the parent exited, still running : True
  -> nothing ever tells it the parent is gone; it just keeps sleeping
  had to be killed explicitly

결과가 갈렸다. 계속 쓰는 자식은 저절로 죽었다. 다음 쓰기가 실패했기 때문이다. 반면 쓰지 않고 기다리는 자식은 살아남았다. 부모가 사라졌다는 사실을 알려 줄 계기가 없기 때문이다. 명시적으로 종료시켜야 사라졌다.

  • 「부모가 죽으면 자식도 정리된다」는 기대는 절반만 맞다. 쓰기를 계속하는 자식에게만 맞는다
  • 파이프는 쓸 때만 상대의 부재를 알려 준다. 읽거나 자고 있는 프로세스에게는 아무 신호도 가지 않는다
  • 그래서 자식을 띄우는 코드에는 부모 종료 경로에서 자식을 정리하는 처리가 필요하다. 정상 종료뿐 아니라 예외 경로에도 있어야 한다
  • 이 점은 운영체제와 프로세스 그룹 설정에 따라 다르게 동작할 수 있다. 위 결과는 이 환경의 실측값이다

14. 체크리스트와 하지 말 것

코드 리뷰에서 바로 쓸 수 있는 형태로 정리했다.

  • 파이프로 연 모든 스트림에 소비하는 코드가 있는지 센다. 스트림 수와 독자 수가 같아야 한다
  • 대기 호출이 읽기 뒤에 오는지 본다. 앞에 있으면 그것만으로 결함이다
  • 모든 대기 호출에 타임아웃이 있는지 본다. 없으면 장애 시 조사조차 못 한다
  • 타임아웃 뒤에 자식을 명시적으로 종료하는지 본다. 예외를 받는 것만으로는 자식이 죽지 않는다
  • 출력 상한이 불명확한 자식은 파일이나 스트리밍으로 받는지 본다
  • 테스트 표본 중에 버퍼 용량보다 큰 것이 있는지 본다. 없으면 이 경로는 검증된 적이 없다
  • 큰 입력을 넣는 코드에서 쓰기와 읽기가 동시에 도는지 본다
  • 순서가 중요한 로그를 합쳐 놓지 않았는지 본다. 합치면 시간 순서가 깨진다
  • 진행 표시가 필요한 자식이 무버퍼로 도는지 본다
  • 출력을 쓰지 않는데 파이프를 만들고 있지 않은지 본다
  • 부모 종료 경로에 자식 정리가 있는지 본다. 자고 있는 자식은 저절로 죽지 않는다
  • 운영 환경의 버퍼 용량을 직접 재 봤는지 본다. 개발 환경과 다를 수 있다

반대로 하지 말아야 할 것들이다.

  • ❌ 파이프로 열어 놓고 소비하지 않는 스트림 — 실무에서 압도적으로 흔한 원인이고, 대개 표준 오류다
  • ❌ 대기 먼저, 읽기 나중 — 4096바이트까지만 통과하는 코드다
  • ❌ 대기가 실패했으니 자식도 죽었다고 가정하는 것 — 실측 결과 살아 있었다
  • ❌ 작은 표본만으로 통과 판정 — 경계는 실데이터에서만 넘는다
  • ❌ 버퍼 용량을 다른 환경의 값으로 가정하는 것 — 같은 기계에서 4096, 65536, 131072로 갈렸다
  • ❌ 진행 로그 지연을 프로그램이 느린 것으로 오진하는 것 — 버퍼에 고여 있을 뿐이고 원인이 다르다
  • ❌ 두 스트림을 합쳐 놓고 순서를 신뢰하는 것 — 실측에서 순서가 완전히 뒤집혔다
  • ❌ 타임아웃 없는 대기 — 재현 실험 자체를 불가능하게 만든다. 이 글의 실험도 전부 상한을 걸고 돌렸다
  • ❌ 부모 코드만 보고 안전하다고 판단하는 것 — 10절처럼 자식의 종류가 결과를 바꾼다

# 파이프 버퍼 교착 — 자식 프로세스 실행 점검표

> 출처: braindetox.kr — 자식 프로세스가 멈추는 진짜 이유
> 근거: Windows 10 / bash 5.2.37 (MSYS2) / Python 3.13.3 / Node.js 22.16.0 실행 검증
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 코드를 점검해줘」라고 쓰면 됩니다.
> ⚠ 버퍼 용량은 OS·셸·런타임마다 다릅니다. 아래 숫자는 위 환경의 실측값이며, 여러분 환경에서 다시 재야 합니다.

## 0. 한 줄 원리

파이프는 **유한한 버퍼**다. 가득 차면 쓰는 쪽이 대기한다 — 이것은 버그가 아니라 **흐름 제어**다.
문제는 읽어 줄 사람이 이미 대기 중일 때 생긴다. 그때 **둘 다 상대를 기다리는 교착**이 된다.

## 1. 계층별 실측 용량 (참고값)

| 계층 | 실측 | 의미 |
|---|---|---|
| 네이티브 Windows 익명 파이프 | 4096 B | Python os.pipe / subprocess PIPE |
| MSYS2 셸 파이프 | 65536 B | bash 의 cmd1 파이프 cmd2 |
| Node 스트림 highWaterMark | 16384 B | 파이프 위에 얹힌 사용자 공간 버퍼 |
| Node 미소비 stdout 정지 경계 | 131073 B | 실측 경계, 위 두 값의 단순 합이 아님 |
| Python stdio 버퍼 | 8192 B | io.DEFAULT_BUFFER_SIZE, 파이프와 별개 층 |

## 2. 실측 교착 경계

| 패턴 | 통과 | 교착 | 경계 해석 |
|---|---|---|---|
| Python: wait 먼저, 자식이 stdout 출력 | 4096 B 이하 | 4097 B 이상 | 파이프 용량 그 자체 |
| Node: data 리스너 없이 close 대기 | 131072 B 이하 | 131073 B 이상 | 스트림 버퍼 + libuv 선반영 |
| 부모가 입력 전량 쓰고 나중에 읽기 (스트리밍 필터 자식) | 9216 B 이하 | 9217 B 이상 | 4096 + 4096 + 1024 |
| 부모가 입력 전량 쓰고 나중에 읽기 (전량 슬러프 자식) | 4 MB 도 통과 | — | 자식이 계속 읽으므로 안 막힌다 |

## 3. 실행 방식 선택표

| 상황 | 고를 방식 | 주의점 |
|---|---|---|
| 출력이 작고 상한이 확실 | 고수준 API 한 번 호출 (run / check_output / spawnSync) | 메모리에 전량 적재. 상한을 코드에 문서화 |
| 출력이 크거나 상한이 없음 | 파일 디스크립터로 리다이렉트 | 임시 파일 정리 책임. 디스크 여유 확인 |
| 출력을 실시간으로 처리 | 한 줄씩 스트리밍 소비 | 자식의 stdio 버퍼 때문에 지연됨 → 자식을 무버퍼로 |
| stderr 도 봐야 함 | 두 스트림을 동시에 소비 (스레드·비동기·고수준 API) | 한쪽만 읽으면 반드시 교착 |
| stderr 내용만 필요하고 순서 무관 | stderr 를 stdout 으로 합치기 | 두 스트림의 버퍼링이 달라 순서가 섞인다 |
| 자식에게 큰 입력도 넣어야 함 | 쓰기와 읽기를 동시에 (별 스레드 또는 통합 API) | 전량 쓰고 나중에 읽기는 양방향 교착 |
| 출력을 아예 버림 | 널 디바이스로 지정 | PIPE 로 열고 방치하는 것이 최악 |

## 5. 멈춤 진단 절차 (5단계)

1. **살아 있는지 확인.** 프로세스 목록에서 부모와 자식이 둘 다 보이면 죽은 게 아니라 대기다.
2. **CPU 시간을 두 번 샘플링.** 값이 그대로면 무한 루프가 아니라 **블록**이다. 실측 예: 0.109375 → 0.109375.
3. **진척을 두 번 샘플링.** 쓴 바이트 수, 출력 파일 크기, 마지막 로그 줄이 멈춰 있는지 본다.
4. **결정적 시험 — 입력을 줄인다.** 같은 코드가 특정 크기 밑에서 안 멈추면 원인은 로직이 아니라 **버퍼**다.
   - 실측 예: 65536 B 는 정상 종료(0), 400000 B 는 차단 상태로 강제 종료(124), 들어간 양은 65536 B.
5. **코드에서 순서를 확인.** 대기 호출이 읽기보다 먼저 오는가. 파이프를 열고 소비하지 않는 스트림이 있는가.

| 관찰 | 판정 |
|---|---|
| 프로세스 살아 있고 CPU 시간 정지 | 파이프 블록 (또는 다른 I O 대기) |
| 프로세스 살아 있고 CPU 시간 증가 | 무한 루프. 파이프 문제 아님 |
| 크기를 줄이면 통과 | **파이프 버퍼 교착 확정** |
| 크기와 무관하게 항상 멈춤 | 파이프 문제 아님. 락·네트워크·입력 대기 의심 |
| 자식은 끝났는데 부모가 안 끝남 | 부모가 스트림을 닫지 않았거나 소비하지 않았다 |

## 6. 리뷰 문장 (그대로 붙여 쓰기)

- 이 호출은 자식 출력의 상한이 얼마입니까. 상한이 없다면 파일이나 스트리밍으로 바꿔 주세요.
- stderr 를 파이프로 열었는데 소비하는 코드가 보이지 않습니다. 한쪽만 읽으면 교착입니다.
- 대기 호출이 읽기보다 앞에 있습니다. 순서를 바꾸거나 통합 API 로 교체해 주세요.
- 큰 입력을 전량 쓴 뒤에 출력을 읽고 있습니다. 상대가 스트리밍 필터면 양방향 교착이 됩니다.
- 타임아웃이 없습니다. 대기 호출에는 반드시 상한을 두고, 초과 시 자식을 명시적으로 종료해 주세요.
- 테스트 입력이 작아서 이 경로는 검증된 적이 없습니다. 버퍼 용량보다 큰 표본을 추가해 주세요.
- 진행 로그가 뭉쳐 나옵니다. 파이프에 연결되면 블록 버퍼로 바뀝니다. 생산자를 무버퍼로 돌려 주세요.

## 7. 체크리스트

- [ ] 대기 호출이 **읽기 뒤**에 온다 (또는 통합 API 를 쓴다)
- [ ] 모든 대기 호출에 **타임아웃**이 있다
- [ ] 타임아웃 뒤에 자식을 **명시적으로 종료**한다 (대기 실패가 종료를 뜻하지 않는다)
- [ ] 출력 상한이 불명확한 자식은 **파일이나 스트리밍**으로 받는다
- [ ] 테스트 표본이 **버퍼 용량보다 크다**
- [ ] 큰 입력을 넣을 때 **쓰기와 읽기가 동시에** 돈다
- [ ] 순서가 중요한 로그는 **합치지 않는다** (합치면 섞인다)
- [ ] 진행 표시가 필요한 자식은 **무버퍼**로 돌린다
- [ ] 출력을 안 쓸 거면 **파이프를 만들지 않는다**
- [ ] 부모가 죽을 때 자식을 **정리하는 경로**가 있다
- [ ] 운영 환경의 버퍼 용량을 **직접 재 봤다** (개발 환경과 다를 수 있다)

## 8. 하지 말 것

- ❌ 파이프로 열어 놓고 **소비하지 않는 스트림** — 가장 흔한 원인
- ❌ **대기 먼저, 읽기 나중** — 작은 출력에서만 통과한다
- ❌ 대기 호출이 실패했으니 자식도 죽었다고 **가정하는 것** — 실측 결과 살아 있었다
- ❌ 작은 표본만으로 통과 판정 — 경계는 실데이터에서만 넘는다
- ❌ 버퍼 용량을 **다른 환경 값으로 가정** — 같은 기계에서 4096·65536·131072 로 갈렸다
- ❌ 진행 로그 지연을 **프로그램이 느린 것으로 오진** — 버퍼에 고여 있을 뿐이다
- ❌ 순서가 중요한 두 스트림을 **합쳐 놓고 순서를 신뢰**하는 것
- ❌ 타임아웃 없는 대기 — 재현 실험조차 못 하게 만든다
