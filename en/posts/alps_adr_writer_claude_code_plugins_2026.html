Motivation — Fixing Specifications and Architecture Decisions Before Code Generation

As large language model (LLM) coding agents continue to mature, the velocity with which developers can generate and refactor source code from natural language prompts has accelerated dramatically. However, initiating code generation directly from brief, unstructured prompts exhibits severe vulnerabilities as system complexity grows. Agents naturally fill missing specification gaps through arbitrary inference, routinely adopting naive implementation strategies that overlook long-term architectural trade-offs, state machines, and non-functional system constraints.

Engineering teams frequently experience three structural defects when code is generated without prior specification:

  • Requirement Distortion via Unchecked Inference: Agents fill unspecified edge cases with arbitrary simplifications, distorting domain rules and security boundaries.
  • Omission of Non-Functional Architectural Constraints: Implementations bypass concurrency rules, idempotency boundaries, and fault guarantees to satisfy surface behavior.
  • Downstream Regression Across Sessions: Future agent sessions lack context regarding why previous implementations selected particular schemas, precipitating architectural rot.

This ambiguity causes frequent implementation rollbacks and creates architectural decay over time. As explored in analyses of planning modes versus specification documents (plan_mode_planning_vs_plan_document_2026) and automated code-to-architecture diagramming skills (archify_code_to_system_diagram_agent_skill_2026), software generated by autonomous agents remains sustainable only when explicit architectural contracts govern execution.

Published under the MIT license in October 2026, alps-writer-plugins provides an integrated plugin marketplace suite for Claude Code and OpenAI Codex. The system compels coding agents to articulate product requirements specifications (ALPS PRDs) through structured conversational interviews and record justified architectural choices within Architecture Decision Records (ADRs) before committing code changes.

Core Principle — Preserving Reproducible Conditions Rather Than Recoverable Facts

The foundational rule governing the plugin design is to “preserve reproducible conditions, not recoverable facts.” The most prevalent failure mode in software documentation occurs when engineers duplicate volatile implementation details—such as function signatures, variable names, and file paths—into external documents, causing them to drift into obsolescence the moment code changes.

The repository README establishes an authoritative three-stage gating test to categorize information cleanly:

  • Requirement gate: If a specific fact disappeared, could regenerated code violate a mandatory business value, security permission, state machine transition, ordering invariant, failure guarantee, or boundary condition? If yes, preserve it within the contract layer (PRD or ADR).
  • Code-readthrough test: If the fact is not a fundamental requirement and an agent can recover it unambiguously by reading implementation code, unit tests, or dependency manifests, omit it from documentation and retain it solely in code and tests.
  • ADR admission gate: If code inspection cannot explain why one durable architectural alternative was chosen over competing options, and modifying the fact would alter the system design, preserve the decision, rationale, trade-offs, and underlying assumptions in an ADR.

The matrix below delineates the strict segregation of responsibilities across system layers:

Artifact Layer Persisted Information (Persist) Excluded Information (Do not persist)
ALPS PRD (Product Spec) User problems, observable outcomes, business contracts, success metrics, Out of Scope non-goals, durable constraints Concrete code paths, stack inventories, disposable task plans, copied tickets and debug logs
ADR (Architecture Record) Admitted decisions, exact requirement contracts, rationales, evaluated alternatives, implementation-independent evidence Specific library names, SDK signatures, database field tables, internal execution flowcharts
Code and Unit Tests Implementation layouts, function identifiers, dependencies, tuning parameters, executable verification suites Back-reference comments citing PRD or ADR document paths
Issues, PRs, and Commits Change-specific intent, conversational reviews, and verbatim revision histories Competing secondary sources of architectural truth

Artifact Structure — Division of Responsibilities Across ALPS, Lite ALPS, and ADRs

The plugin manages three distinct artifact formats, each tailored to specific phases of the system lifecycle:

Artifact Format README Description Usage Phase and Entry Command Unverified Boundary
Full ALPS PRD Nine-section unambiguous product specification for agents, treating Out of Scope as a first-class section Comprehensive product planning (/alps-init) Complete exhaustive list of section subheadings
Lite ALPS Four-section working-backwards format for minimum PoCs (problem, C4 Context, experiences, demo scenario) Rapid concept validation and mockups (/lite-alps-init) Support for custom user-defined sections beyond the four core sections
ADR Isolated architectural records capturing decisions, rationale, contracts, and evaluated alternatives Direct authoring (/adr-new) or contract handoff (/feature-to-adr) Interoperability schema for external ADR visualization engines
.mapping.json Internal metadata ledger tracking canonical keys, paths, statuses, and dependency relationships (dependsOn) Automated topological gating during implementation reviews Multi-project partition mechanisms in massive monorepos
glossary.md Appendix file compiling domain terminology and acronym definitions across documents Onboarding non-standard domain terms Bilingual terminology alignment conventions

Functional boundaries across artifact types are governed by exact rules:

  • Full ALPS Rigor: Enforces nine numbered sections and explicit dependency graphs (6.3) to specify vertical-slice features before implementation.
  • Out of Scope as a First-Class Section: Explicitly documents excluded functionality to prevent agent hallucination and scope creep.
  • Lite ALPS PoC Efficiency: Restricts authoring to problem definitions, C4 Context diagrams, and executable demo scenarios to validate prototypes quickly.
  • .mapping.json Topology Engine: Programmatically audits canonical keys, relative paths, status enumerations, and upstream dependsOn requirements.

ALPS (Agentic Lean Product Spec) represents a PRD format purpose-built for agentic software development. Traditional PRDs rely on human readers to interpret missing requirements through intuition. In contrast, ALPS assumes an artificial intelligence agent requires fully unambiguous specifications to generate reliable code. ALPS inverts the authoring cycle: the agent initiates targeted interview questions, the human operator provides clarifications, and no section is persisted to disk without explicit confirmation.

Lite ALPS provides a streamlined four-section working-backwards specification for planners defining a minimum proof-of-concept (PoC). Once the human approves the target problem and desired business impact, the agent drafts the minimum viable solution, a product-level C4 Context diagram, essential user experiences, and a concrete executable demo scenario for sign-off.

ADRs (Architecture Decision Records) follow the established principles documented on adr.github.io, recording justified design choices that address architecturally significant requirements (ASRs). Once an ADR is approved, its canonical key and prerequisites are tracked in .mapping.json.

Plugin Architecture — Unidirectional Coupling from alps-writer to adr-writer

Rather than providing a bloated monolithic system, alps-writer-plugins decouples responsibilities into two independent plugins: alps-writer and adr-writer.

alps-writer (PRD Authoring)
                      │
                      │ /feature-to-adr (Unidirectional Contract Handoff)
                      ▼
                    adr-writer  (ADR Lifecycle Engine, Fully Standalone)
                      ├── /adr-new, /adr-impl, /adr-impl-refactor, /adr-impl-review
                      ├── /adr-sync (Implementation Drift Repair)
                      ├── /adr-rollup (Decision Evolution Consolidation)
                      └── SessionStart Hook (.mapping.json Context Restoration)

The foundational architectural rule governing this split is that adr-writer never references ALPS. It functions as a completely autonomous tool for projects that do not utilize PRDs. The sole integration point is the unidirectional bridge /feature-to-adr located in alps-writer.

  • Complete ADR Autonomy: The adr-writer plugin executes independently in any repository without requiring PRDs or planning files.
  • Unidirectional Contract Handoff (/feature-to-adr): Seamlessly converts Section 7 feature contracts into individual ADRs with full coverage.
  • Legacy Role of PRD Post-Handoff: Following transfer, the PRD serves solely as historical context, while ADRs retain sole implementation authority.

Four Entry Workflows — From Existing Project Discovery to PRD-First Execution

The suite supports four distinct onboarding and development workflows, accessible via /skill-name in Claude Code or $skill-name in Codex:

  • Existing Project Onboarding: Executing /adr-import [scope] directs the agent to analyze existing code, unit tests, and documentation through an EventStorming methodology. The agent reconstructs business events and boundaries into a consolidated intent and conflict report before generating confirmed Proposed ADRs.
  • PoC Authoring: Running /lite-alps-init initiates a focused conversation to draft a four-section proof-of-concept specification and executable demo script.
  • PRD-First Workflow: Teams author a comprehensive nine-section PRD via /alps-init, execute /feature-to-adr to bridge features into ADRs, and proceed to implementation.
  • ADR-Only Workflow: Teams bypass PRD authoring entirely, invoking /adr-new [category] to draft individual architectural decisions directly.

Plugin installation requires no local build steps or npm compilation, leveraging native marketplace mechanisms:

                    /plugin install alps-writer@alps-writer
                    /plugin install adr-writer@alps-writer
                    
                    # Installation via Codex Marketplace

                    codex plugin add alps-writer@alps-writer

Runtime execution requires Node.js version 24 or higher alongside the respective coding agent CLI.

Execution Lifecycle — Topological Dependency Gates and the Refactor-Review Loop

Once an ADR is registered in the Proposed state, advancing from specification to verified code is governed by automated lifecycle gates.

The primary barrier is the Topological Dependency Gate. When an operator triggers /adr-impl [id], the agent inspects the dependsOn array within .mapping.json. If any prerequisite ADR remains in the Proposed state or references an unresolved identifier, the agent halts immediately, requiring prerequisites to be implemented and accepted first in strict topological order.

Once all upstream gates pass, the agent completes the closed implementation loop:

  • Initial Implementation and Testing: The agent implements vertical slices (UI to API to data layer) and runs project test suites. Happy-path coverage alone is rejected; tests must rigorously exercise boundary and failure conditions.
  • Verified Refactoring (/adr-impl-refactor): Upon passing initial tests, the agent reviews execution efficiency, cyclomatic complexity, coupling, and code duplication. Only high-confidence, behavior-preserving local modifications are applied, with before-and-after tests validating correctness.
  • Risk-Based Final Review (/adr-impl-review): A gating audit verifies that implementation code fulfills all contractual conditions declared in the ADR. Only when the review passes is the ADR status transitioned to Accepted.
  • Drift Repair (/adr-sync): When code modifications or refactors introduce divergence between code and ADR contracts, /adr-sync provides targeted alignment.
  • Evolution Consolidation (/adr-rollup): When multiple historical ADRs fragment a single logical decision chain over time, /adr-rollup merges their history into a clean, consolidated record.

Non-Invasive Harness — Standard Markdown Preserved After Plugin Removal

A critical engineering consideration when evaluating AI developer tools is avoiding proprietary vendor lock-in. When tools store configuration in closed binary stores or custom cloud databases, decoupling from the tool becomes costly.

alps-writer-plugins explicitly designs itself as a removable, non-invasive harness. All persistent artifacts managed by the plugins consist solely of standard Markdown files (docs/adr/*.md, docs/adr/glossary.md, docs/adr//decision-log.md), project source code, and a lightweight JSON index (.mapping.json).

The three pillars of sustainability guaranteed by this non-invasive architecture include:

  • Open Standard Formats: Specifications remain regular Markdown files immediately renderable in GitHub web interfaces.
  • Zero Proprietary State: Removing the plugins leaves no dead metadata or corrupted repository configurations behind.
  • Universal Model Interoperability: Future AI coding engines or human developers can read the exact architectural context without tooling translations.
