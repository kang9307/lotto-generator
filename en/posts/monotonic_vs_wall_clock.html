Measuring Elapsed Time on a Wall Clock Gives You Negative Durations - Where the Monotonic Clock Belongs

Two clocks answer two different questions - what time is it now, and how much time has passed

2026-07-30 Development/Infrastructure

The symptom: a duration log with a negative number in it

Picture a dashboard showing duration_ms: -2760 one morning. A single request apparently took minus 2.7 seconds to handle. You open the code and nothing looks wrong. Stamp the time at the start, stamp it again at the end, subtract. There is no simpler calculation than that.

And yet that simple calculation rests on one assumption: that the second reading is necessarily larger than the first. A wall clock does not guarantee that. Somebody may have corrected the clock in between.

The conclusion of this article is not 「use a monotonic clock」. Advice like that survives only as a rule, and rules get forgotten. Here is the framing instead. The two clocks answer two different questions.

  • The wall clock answers 「what time is it now」. It is the time a human reads, the time you can compare against another machine, the time you can put on a calendar. In exchange, it can be corrected from outside
  • The monotonic clock answers 「how much time has passed」. Its origin is arbitrary, so the value itself means nothing at all. Only the difference between two readings means anything. In exchange, nobody can wind it back
  • So a wall clock cannot be evidence of elapsed time. The moment you use it as evidence, the property 「can be corrected from outside」 leaks straight into your measurement
  • Conversely, a monotonic clock cannot be a time you show to a person. Stamp a log line with one and you get 1970, and you cannot line it up against another server

The fastest way to internalise this distinction is to watch the negative number appear. So this article starts with execution. Twelve experiments were run in Node, Python and a shell, and every block below is that output verbatim.

Environment. Every output was produced by actually running the code on Windows 10 Pro (10.0.19045). The runtimes are Node.js v22.16.0 (win32) and Python 3.13.3; the shell is GNU bash 5.2.37 (MSYS2/MinGW64). Every script was saved to a file and executed from there.

The system clock was never changed. That needs administrator rights and it damages the environment. Instead the clock jump was injected: wherever the program reads the wall clock, it calls a function of the form Date.now() + offset, and that offset was changed mid-measurement. That has the same shape as what a program sees when time sync steps the clock. The monotonic clock was read raw, with no offset at all.

What this article does not cover. Why clocks drift, and how to diagnose sync status, are out of scope. Here the story stops at the bare fact that a clock can go backwards, and then focuses on one point: which clock you use to measure elapsed time. Time zone rules and the reinterpretation of past instants are also outside this article.

2. The moment end minus start goes negative

Now the heart of it. The code below does 120 milliseconds of work, injects a 3 second backward correction, does another 120 milliseconds of work, and then subtracts the start instant from the end instant. It measures the same span on a monotonic clock too.

--- 2-1. THE BUG: elapsed measured on a wall clock that gets corrected ---
start (wall)   : 1785385665815
end   (wall)   : 1785385663055
elapsed  WALL  : -2760 ms
elapsed  MONO  : 239.265 ms
wall elapsed is negative : true

--- 2-2. the same code, printed the way a service logs it ---
{"msg":"request done","duration_ms":-2760,"clock":"wall"}
{"msg":"request done","duration_ms":239.3,"clock":"monotonic"}

--- 2-3. forward jump: the request looks 10 minutes long ---
elapsed WALL : 600050 ms   (10.00 min)
elapsed MONO : 49.368 ms

elapsed WALL : -2760 ms. The work really took 240 milliseconds, and the wall clock answered minus 2.76 seconds. The same span on the monotonic clock is 239.265 ms. If a service logs that straight out, the line it leaves behind is duration_ms:-2760. The line from the opening paragraph.

  • The end instant is smaller than the start instant. 1785385663055 is less than 1785385665815, because the clock went backwards in between
  • There is no bug in the code. The subtraction is exact. What is wrong is the assumption that the second value exceeds the first
  • The monotonic clock did not flinch at the same injection, because the injection was applied only where the wall clock is read, and the monotonic clock was read raw. By specification this clock is not a target for adjustment
  • The opposite direction is the same defect. In 2-3 below the clock moves 10 minutes forward and a 50 millisecond job is recorded as 600050 ms, ten minutes. That is more dangerous than a negative number. A negative number gets noticed; ten minutes looks plausible
--- P-4. THE BUG: elapsed on a wall clock that gets corrected ---
start (wall)  : 1785385835.713235
end   (wall)  : 1785385832.953251
elapsed WALL  : -2759.984 ms
elapsed MONO  : 240.017 ms
wall elapsed is negative : True

what a handler would log:
{"msg": "job finished", "elapsed_ms": -2760.0, "clock": "wall"}
{"msg": "job finished", "elapsed_ms": 240.0, "clock": "monotonic"}

Run the same experiment in Python and even the value comes out nearly the same: -2759.984 ms. That tells you this is not a language problem but a property of the clock. The Python documentation states for time.time() that it 「can return a lower value than a previous call if the system clock has been set back between the two calls」. So this behaviour is not a bug; it is specified.

About the injection. The system clock was not changed. An offset was added to the function that reads the wall clock, producing the state of 「the wall clock this program sees has suddenly moved」. That has the same shape as what a program sees when time sync steps the clock or a person edits it by hand. The monotonic side was read with no offset, so the contrast between the two columns reflects the real difference between the clocks.

You can confirm it without any of this, though. Python time.get_clock_info() reports adjustable=True and monotonic=False for time on its own. Those two values are already the statement 「this clock can be moved and it can go backwards」. The injection experiment merely shows what that statement looks like once it reaches your code.

2.1 The ways a clock ends up going backwards

「The clock goes backwards」 sounds exotic, but in practice it is the result of ordinary operational activity. Here is what moves in which direction and by how much. The size of the movement matters. A millisecond-scale correction passes without leaving anything in the logs; a second-scale step correction produces a negative number immediately.

TriggerDirectionMagnitudeHow it shows up in a measurement
Time sync step correctionEitherHundreds of ms to tens of sElapsed time goes negative or gets inflated. This is what this article reproduces
Time sync gradual correctionEitherA slight tweak to the rateThe monotonic clock is affected too. clock_gettime(2) notes that it 「is affected by frequency adjustments」. It still never goes backwards
A person edits it by handEitherMinutes to hours to daysThe largest jump. Common on development machines and freshly built servers
A virtual machine is paused and resumedUsually forwardAs long as the pauseThe wall clock leaps all at once right after resume

3. Resolution is a separate problem - and the folklore is wrong

You often see the explanation 「the wall clock is coarse, so use a monotonic clock」. That is only half true. It was measured. The smallest tick was derived by counting how many consecutive calls return an unchanged value.

--- 3-1. resolution measured by counting repeats  (node) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
Date.now()           400000   38              14402               1 ms
performance.now()    400000   292699          1                   0.000100 ms
hrtime.bigint()      400000   400000          0                   100 ns

--- P-5. resolution measured by counting repeats  (python) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
time.time()            300000   199586          2                   0.000238 ms
time.monotonic()       300000   300000          0                   0.000100 ms
time.perf_counter()    300000   300000          0                   0.000100 ms
time.monotonic_ns()    300000   300000          0                   100 ns
time.perf_counter_ns() 300000   300000          0                   100 ns
  • Node Date.now() changed value only 38 times across 400,000 calls. The same value came back 14,402 times in a row at worst, and the smallest step was 1 millisecond. Anything shorter than a millisecond is unmeasurable with this clock
  • Python time.time() in the same environment changed 199,586 times across 300,000 calls. Its smallest step was 0.000238 milliseconds, that is 238 nanoseconds. get_clock_info() reported the implementation as GetSystemTimePreciseAsFileTime()
  • So the folklore that 「wall clocks are coarse」 is wrong depending on language and platform. On the same machine at the same moment, one wall clock ticked at 1 millisecond and the other at 238 nanoseconds
  • And yet high resolution does not fix anything. That same Python time.time(), with resolution to spare, produced the negative number in section 2. Resolution and adjustability are independent properties
  • On the monotonic side both languages reported 100 nanoseconds, and the same value never came back twice. In this environment Python reported that both monotonic and perf_counter use QueryPerformanceCounter()

To put it plainly: low resolution means you cannot measure short spans; adjustability means you cannot trust any span. The first is an inconvenience, the second is a defect. So the first reason to use a monotonic clock is not resolution but adjustable=False. The resolution comes along as a bonus.

4. Timing a job shorter than a millisecond

What resolution looks like in practice shows up immediately when you time something short. A calculation taking around 0.1 milliseconds was timed eight times, wall clock and monotonic clock side by side.

  • Seven of eight runs in Node reported 0 ms. The remaining one reported 1 ms, the run that happened to cross a millisecond boundary. The real cost was 0.07 to 0.14 milliseconds every time
  • So through this clock the job takes 「0 or 1 milliseconds」. There are runs that genuinely differ by a factor of two, and that entire difference is gone
  • The Python side produced no zeros at all. The same calculation costs 2 to 8 milliseconds in Python, which puts it above the millisecond tick, and its wall clock resolution was far higher anyway. In other words this symptom appears or hides depending on language and workload size
  • There is one practical implication. The judgment 「we never see zeros, so we are fine」 is dangerous. Once the work gets faster or the runtime changes, zeros start appearing. Performance improvements break the measurement

5. Time the same span 100 times and the distribution collapses

Code that measures once and moves on is rare. Usually you measure repeatedly and report a mean and percentiles. The same job was timed 100 times and the distributions from both clocks compared.

It feels as though adding up values from a coarse clock would accumulate error. It was measured. The same job was timed individually 2,000 times, summed, and reported with percentiles.

The rounding error does not lean one way. Summing 1,500 iterations in Python landed inside 0.1 percent as well.

  • 6-3 spends a 20 millisecond budget by decrementing it with individual measurements. The wall clock got 221 iterations, the high resolution clock 238: about a 7 percent difference. The totals may agree, but the moment individual measurements become a condition, the outcome diverges

7. Timeouts and retries - where the damage gets bigger

So far the story has been numbers going wrong. Now it turns to behaviour going wrong. A 500 millisecond retry budget was pinned to an absolute wall clock instant, and the clock was pushed 1 hour forward after the second attempt.

--- 7-1. a wall-clock deadline expires the instant the clock is corrected ---
budget 500 ms of retries, clock steps +3600 s (1 h forward) after attempt 2
 WALL deadline:
  attempt 1: ok, remaining=500 ms
  attempt 2: ok, remaining=470 ms
  << clock stepped 3600 s >>
  attempt 3: ABORT deadline exceeded, remaining=-3599560 ms
  -> attempts completed: 2 of 6, aborted=true
 MONOTONIC deadline:
  attempt 1: ok, remaining=500.0 ms
  attempt 2: ok, remaining=470.8 ms
  << clock stepped 3600 s >> (monotonic unaffected)
  attempt 3: ok, remaining=440.8 ms
  attempt 4: ok, remaining=410.9 ms
  attempt 5: ok, remaining=380.9 ms
  attempt 6: ok, remaining=350.8 ms
  -> attempts completed: 6 of 6, aborted=false

The wall clock version gave up immediately on the third attempt, because the remaining budget computed to -3599560 ms. Only 60 milliseconds had actually been spent, and the 500 millisecond budget was treated as exhausted. The monotonic version ran all six. The opposite direction is worse.

--- 7-2. and a backward step makes the same deadline unreachable ---
deadline was set 200 ms out, then the clock stepped -86400 s
remaining according to the wall clock : 86399880 ms  (24.00 h)
real time actually spent waiting      : 319.6 ms (loop cut off by a guard)
without the guard this loop waits a full day for a 200 ms deadline

--- 7-3. sleep-until-instant vs sleep-for-duration ---
sleep until wall instant 1785385765471 :
  if the clock is stepped +1000 s first -> wakes immediately, 0 ms of real waiting
  if the clock is stepped -1000 s first -> waits ~1001 s of real time
sleep for 1000 ms (setTimeout, libuv timer) :
  setTimeout(1000) fired after 1013.7 ms of monotonic time
  the -50000 ms wall step did not move it
  • Jump forward, expire at once. Not a single retry remains. Correct the clock during an incident and every retry path gives up simultaneously
  • Jump backward, never finish. A deadline set 200 milliseconds out effectively moved 24 hours out. The remaining time the wall clock computed was 86399880 ms, 24 hours. The experiment cut the loop off with a guard; without one it waits a day
  • 「Sleep until an instant」 and 「sleep for a duration」 are different instructions. The first gets swept along by clock corrections; the second does not
  • In 7-3, setTimeout(1000) fired precisely 1013.7 milliseconds of monotonic time later even with a 50 second backward injection on the wall clock. Runtime timers are already sitting on a monotonic clock
  • Which means the timers your runtime hands you are safe, and the deadlines you compute yourself are risky. If you can delegate 「in N seconds」 to the framework, delegate it

Why this section is the most dangerous one. The symptoms in earlier sections are numbers going wrong, and you can see them in a log. The symptom here is behaviour going wrong, and all the log says is 「timeout」. Investigation then naturally turns towards the network and the remote server. It is a very long road from there to the realisation that the cause is a clock choice in your own code.

8. Cache expiry and rate limiting - the same defect wearing another face

Exactly the same calculation as a timeout lives inside caches and rate limiters: store 「now plus TTL」 and later compare it against 「now」. Five entries with a 60 second TTL were inserted, and the clock was moved while no real time passed at all.

--- 8-1. a TTL cache keyed on wall instants ---
5 entries, ttl 60 s, nothing has actually elapsed
  before step   wall-cache live=5   mono-cache live=5
  clock +3600 s wall-cache live=0   mono-cache live=5   get(k0)=(expired)
  -> the whole cache evaporates in one tick. every caller goes to the origin at once
  clock -3600 s wall-cache live=5   mono-cache live=5   get(k0)=v0
  -> entries now outlive their ttl by an hour. stale data served as fresh

Push the clock an hour forward and the live entry count goes from 5 to 0. The cache is wiped out in a single tick. Move it backwards and, conversely, entries that should have expired stay alive. A rate limiter has the same structure.

--- 8-2. a fixed-window rate limiter on the same clock ---
 WALL limiter, 3 req / 1000 ms:
   r1 window_age=0ms count=1 -> ALLOW
   r2 window_age=0ms count=2 -> ALLOW
   r3 window_age=0ms count=3 -> ALLOW
   r4 window_age=0ms count=4 -> REJECT
   << clock stepped +5 s, no real time passed >>
   r5 window_age=0ms count=1 -> ALLOW   <- quota reset for free
   << clock stepped back to where it was >>
   r6 window_age=-5000ms count=2 -> ALLOW   <- window frozen, it will never roll again
 MONOTONIC limiter, same sequence:
   r1 window_age=1ms count=1 -> ALLOW
   r2 window_age=1ms count=2 -> ALLOW
   r3 window_age=1ms count=3 -> ALLOW
   r4 window_age=1ms count=4 -> REJECT
   << clock stepped +5 s >>
   r5 window_age=1ms count=5 -> REJECT   <- still rejected, correctly
  • Jump forward, cache wiped. The problem is not 「the cache is empty」 but that every caller stampedes to the origin at once. It shows up as a spike in origin load right after a clock correction
  • Jump backward, expiry deferred. get(k0)=v0 came straight back. A value that should have expired is served as fresh. Nothing raises an error here. Stale data simply goes out
  • The rate limiter hands out free quota. Move the clock 5 seconds forward and a request that was being rejected turns into ALLOW, because a new window is deemed to have opened
  • Move it back and the window freezes. window_age=-5000ms. With a negative window age, the condition for rolling the window forward can never be satisfied again, and from then on the counter only climbs
  • The monotonic version kept rejecting correctly through the same sequence. The clock injection never reached the decision at all

9. Log timestamps must be wall clock

Now flip the direction. Everything so far has been places where a wall clock does not belong. There are places where a monotonic clock does not belong either. Here a monotonic value is stamped as a timestamp directly.

--- 9-1. the reverse mistake: a monotonic value cannot be a timestamp ---
monotonic reading                  : 20810933.933
formatted as if it were epoch ms   : 1970-01-01T05:46:50.933Z
wall reading                       : 1785385762171
formatted                          : 2026-07-30T04:29:22.171Z
a log line stamped with the monotonic value says 1970 and cannot be compared to any other machine

--- 9-2. the line that carries both ---
{"ts":"2026-07-30T04:29:22.176Z","duration_ms":44.628,"route":"/v1/orders"}
ts is orderable across hosts and readable by a human; duration_ms cannot go negative
  • Format a monotonic value as a timestamp and you get 1970-01-01T05:46:50.933Z, which follows inevitably from the origin not being the epoch
  • You cannot line it up against another machine. Two servers have different origins, so comparing the two numbers is meaningless. Distributed tracing falls apart right here
  • A person cannot read it. The statement 「the incident started at 20810933.933」 supports no action whatsoever
  • Retention policy breaks too. A rule like 「delete logs older than 30 days」 needs an absolute instant to evaluate

So the answer is not 「pick one」 but use both, each in its own place. The single line in 9-2 is that shape. ts records 「when」 from the wall clock, and duration_ms records 「how long」 from the monotonic clock. Now the timestamp sorts against other hosts and reads to a human, while the duration can never go negative. Two clocks in one line is not strange; it is correct.

10. Restart the process and the origin changes

The arbitrariness of the monotonic origin has one more practical consequence: you must not store that value. The same script was run as two consecutive processes and the values compared.

--- 10-1. the monotonic origin is per boot and per process ---
field                   previous process     this process         delta
---------------------------------------------------------------------------------
pid                     14920                17368                -
Date.now()              1785386114435        1785386117740        3305 ms
hrtime.bigint()/1e6     21163198.428         21166503.246         3304.818 ms
performance.now()       1869.676             1882.334             12.658 ms
performance.timeOrigin  1785386112566.207    1785386115858.01     3291.803 ms

--- 10-2. so a persisted monotonic deadline is meaningless after restart ---
saved by the previous process : performance.now() + 30000 = 31869.676
this process reads it back and compares to its own performance.now() = 1885.058
  remaining, as computed      : 29984.557 ms
  real time between the runs   : 3305 ms (from the wall clock)
  the two numbers are unrelated. performance.now() restarts near 0 in every process
  • Date.now() grew by 3,305 milliseconds between the two processes, which is the time that really passed. Different processes look at the same coordinate system
  • hrtime.bigint() grew by 3,304.818 milliseconds too. The origin of this clock is boot, not the process, so it carries across a restart
  • performance.now() grew by only 12.658 milliseconds. 3.3 seconds passed and it moved 12 milliseconds, because this clock restarts from zero in every process. The documentation line about 0 representing the start of the current process is confirmed by this number
  • 10-2 is the consequence. The later process reads back a deadline the earlier one saved and computes 29,984 milliseconds remaining. In reality 3.3 seconds had passed, and it answered 「still 30 seconds to go」. The two numbers are unrelated
ValueSafe to store or transmitWhy
Date.now() / an ISO stringYesAn absolute instant every machine reads the same way
performance.now()NoIts origin is this process. Restart and it returns to zero
process.hrtime.bigint() / time.monotonic()NoIts origin is this boot. Reboot and it becomes meaningless
A span length measured monotonicallyYesA difference of two readings is just a count of milliseconds. It has no origin
performance.timeOriginYesThis is itself a wall clock value. Pair it with an offset and you can reconstruct an absolute instant

11. Who counts the time spent suspended

Monotonic clocks come in variants too: does the counter stop while the machine is suspended, or keep running? It was measured only as far as this environment allows. The monotonic reading is placed next to the wall clock elapsed time computed from the boot instant the operating system reports.

--- P-9. does the monotonic clock count time spent suspended? ---
time.monotonic() here            : 20892.159 s  (5.80 h)
implementation                   : QueryPerformanceCounter()
OS-reported last boot time       : 2026-07-30T07:42:31.500000+09:00
wall seconds since that boot     : 20892.807 s  (5.80 h)
difference (wall-since-boot minus monotonic) : 0.648 s

POSIX names for the distinction (not reproducible on this host):
  CLOCK_MONOTONIC  - does not step; on Linux it does NOT include suspend
  CLOCK_BOOTTIME   - same, but DOES include suspend
  CLOCK_REALTIME   - the wall clock, may be stepped
  time.CLOCK_MONOTONIC      available in this build : False
  time.CLOCK_BOOTTIME       available in this build : False
  time.CLOCK_MONOTONIC_RAW  available in this build : False
  time.CLOCK_REALTIME       available in this build : False
  • The difference between the two was 0.648 seconds. The monotonic clock read 20,892.159 seconds and the wall clock elapsed since boot 20,892.807 seconds: 0.6 seconds apart over 5.8 hours
  • This machine never entered a suspended state during the measurement window, so this method could not observe how suspension is handled. The 0.6 seconds is within what the precision of the reported boot instant and post-boot clock corrections explain
  • Suspend and hibernate could not be reproduced in this environment. So the distinction below is written from documentation only. It is the one item in this article that was not reproduced directly
  • The clock_gettime(2) documentation says of CLOCK_MONOTONIC that 「this clock does not count time that the system is suspended」, and of CLOCK_BOOTTIME that it is 「identical to CLOCK_MONOTONIC, except that it also includes any time that the system is suspended」. The Python documentation describes time.CLOCK_BOOTTIME the same way

The practical judgment. For a server process this distinction almost never matters, because it does not suspend. Where it matters is code running on laptops and handheld devices. Across a lid closing and opening, a CLOCK_MONOTONIC timeout does not count that time. The shape of it is a 「session expires in 5 minutes」 that survives overnight without expiring. If suspended time must be treated as elapsed, CLOCK_BOOTTIME is the right one; and if the expiry is really against an absolute instant a person perceives, a wall clock instant was right all along. For that case see the 「expiry」 row of the table in section 14.

12. A shell has no monotonic clock

Shell scripts have almost no tool for dodging this problem. Every clock a shell can read was printed out.

bash 5.2.37(1)-release / msys

--- S-1. the clocks a shell can read ---
date +%s          : 1785385886
date +%s%N        : 1785385886351968200
EPOCHSECONDS      : 1785385886
EPOCHREALTIME     : 1785385886.364763
SECONDS           : 0
all of these trace the wall clock. bash exposes no monotonic clock.

--- S-3. SECONDS advances with the wall clock, not with work done ---
SECONDS after sleep 2        : 2
date delta                   : 2132 ms

timeout available here : /usr/bin/timeout
Usage: timeout [OPTION] DURATION COMMAND [ARG]...

date, EPOCHSECONDS, EPOCHREALTIME and SECONDS all trace the wall clock. Pure shell syntax offers no route to a monotonic clock. Which makes the single most common pattern below structurally risky.

# the deadline loop everyone writes - both date calls are on an adjustable clock
end=$(( $(date +%s) + 30 ))
while [ "$(date +%s)" -lt "$end" ]; do
    check_ready && break
    sleep 1
done

# the portable fix: stop computing the deadline yourself
timeout 30 sh -c 'until check_ready; do sleep 1; done'
  • The answer is to stop computing the deadline yourself. Hand 「for N seconds」 to timeout and the deadline arithmetic leaves the shell. This environment had /usr/bin/timeout available
  • Calling date is expensive in itself. In S-2 the smallest step across 200 calls was 48 milliseconds. That is not clock resolution, it is process creation cost. A script that reads the time inside a loop pays it every iteration
  • Do not express waiting as an absolute instant. Write 「for N seconds」, not 「until N o’clock」
  • If you truly need accurate measurement, do not do it in a shell. Even for a one-liner, it is better to delegate to a runtime that has a monotonic clock

13. Finding the wrong clock in code you already have

On to diagnosis. Fortunately search finds nearly all of this defect, because the wrong usage reveals itself in the shape of the syntax. Four patterns do the work.

# A. elapsed  -  the subtraction of two wall readings
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. deadline / expiry  -  a wall reading with something added to it
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. the reverse mistake  -  a monotonic reading assigned into stored state
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. everything already monotonic, to confirm it is used as a difference
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/

They were actually run. Two sample files with mixed clock usage were created and the patterns applied. Here is that output.

Pattern A is the strongest signal. Subtracting one wall clock value from another is almost always an elapsed time calculation, and almost always wrong. Pattern B needs judgment. Deadlines and TTLs must be fixed, but cases where an absolute instant is correct, like token expiry or a scheduled instant, land here too. So search is the start and review is required. These are the sentences to ask during review.

  • Will a person look at this value, or will two values be subtracted? If subtracted, monotonic. That single sentence settles most of them
  • Does this instant leave the process? If it is stored, transmitted, or compared with another machine, it has to be wall clock
  • Is this deadline 「until a time」 or 「for a duration」? The latter means monotonic. If a user specified 「by 6 pm」, the former is right
  • What happens if this value goes negative? If the answer is 「no idea」 or 「that cannot happen」, that site is a risky one
  • Must this expiry survive a process restart? If so, a value built from a monotonic clock must not be stored
// before - the duration can come out negative
const t0 = Date.now();
const out = doWork(req);
log({ ts: new Date().toISOString(), duration_ms: Date.now() - t0 });

// after - wall clock names the instant, monotonic clock measures the span
const t0 = process.hrtime.bigint();
const startedAt = new Date().toISOString();
const out = doWork(req);
log({ ts: startedAt, duration_ms: Number(process.hrtime.bigint() - t0) / 1e6 });
# before
start = time.time()
run_batch(items)
emit_metric("batch_seconds", time.time() - start)

# after
started_at = datetime.datetime.now(datetime.timezone.utc)
start = time.monotonic()
run_batch(items)
emit_metric("batch_seconds", time.monotonic() - start, ts=started_at)

The fix looks as simple as the two fragments above. Stamp the start instant once from the wall clock to record 「when」, and measure the span separately with the monotonic clock. One line more, and in exchange the negative numbers disappear. One thing is worth revisiting. When 12-5 pulled out every monotonic usage, four correct uses came back together with one that stores a monotonic value. 「We are using a monotonic clock」 is not evidence of safety. You have to look at how.

15. Why this defect surfaces so late

The worst property of this defect is not technical. It is the way it gets discovered.

  • It is exactly right most of the time, because the two clocks travel together. The increments in section 1 show that. So it passes tests, passes review, and lives for years
  • The moment it is wrong is brief. A clock correction is instantaneous, and a measurement span has to straddle that instant for a symptom to appear. The odds are low
  • It does not reproduce. Investigating means moving the clock, which is something that does not happen unless the investigator does it deliberately
  • The symptom does not point at the cause. 「Timeout」, 「cache miss storm」 and 「p99 anomaly」 all point somewhere else. You miss several times before suspecting a clock
  • So it stays as 「it acts up sometimes」. The ticket closes as not reproducible, and it happens again next time

Because of that, the order of response has to be inverted. Normally you fix things when a symptom appears. With this defect you must not wait for the symptom, because the odds of reaching the cause from the symptom are low. Running the search from section 13 once and cleaning up within budget is far cheaper. The patterns are simple enough to finish in minutes even on a large repository.

To close, the criterion again in one sentence. Will you show this number to a person, or subtract it from another number? Show it, wall clock. Subtract it, monotonic clock. That one question stands in for every table in this article.

16. Checklist

Every item below has its evidence in the runs above. Work down the list.

  • Every wall clock subtraction has been removed from places that measure elapsed time (section 13, pattern A)
  • Timeouts and retry budgets are expressed as 「for this long」, not as an absolute instant deadline
  • Cache TTLs and rate limiter windows are based on a monotonic clock
  • Log timestamps come from the wall clock and durations from the monotonic clock, both on the same line
  • Nowhere stores or transmits a monotonic value (section 13, pattern D)
  • Duration metrics have a guard against negatives, and a negative raises a warning rather than being hidden
  • Places that time short spans use a high resolution clock. Percentiles are not pinned to the tick
  • For expiry logic running on laptops or handheld devices, how suspended time counts has been decided (section 11)

One last thing. When you find a negative, do not wrap it in an absolute value or clamp it to zero. That erases the evidence. A negative is the only unambiguous signal that this defect actually fired, and as this article showed, a forward jump leaves no such signal at all. If you can see a negative, you are on the lucky side. Change the clock at that site.

# Wall Clock vs Monotonic Clock — Selection Table and Code Audit Patterns

> Source: braindetox.kr — Measuring elapsed time on a wall clock gives you negative durations
> Basis: verified by execution on Windows 10 / Node 22.16.0 / Python 3.13.3 / bash 5.2.37 (MSYS2)
> Paste this file straight into an AI tool and say: audit our clock usage against these criteria.

## 0. The premise — two clocks answer different questions

| | Wall clock | Monotonic clock |
|---|---|---|
| Question it answers | **What time is it now** | **How much time has passed** |
| Meaning of the value | An absolute instant against the epoch | A distance from an arbitrary origin |
| Corrected from outside | **Yes** | No |
| Can it go backwards | **Yes** | No |
| Comparable across machines | Yes | **No** |
| Storable / transmittable | Yes | **No** (only differences) |

**Will you show this number to a person, or subtract it from another number?**
Show it, wall clock. Subtract it, monotonic clock. That one sentence stands in for every table below.

## 1. Selection by use case

| Use | Clock | The typical mistake and its symptom |
|---|---|---|
| **Measuring elapsed time** | Monotonic | Wall clock subtraction → **negative duration** |
| **Timeout / retry budget** | Monotonic | Absolute instant deadline → instant expiry or infinite wait |
| **Rate limiter window** | Monotonic | Wall clock window → free quota, frozen window |
| **Cache TTL** (in process) | Monotonic | Wall clock expiry instant → cache wipe or stale values served |
| **Retry backoff interval** | Monotonic | Wall clock based waiting → intervals go haywire |
| **Log / audit timestamps** | Wall clock | Monotonic value → **1970 gets stamped** |
| **Schedule**, daily at 09:00 | Wall clock | A monotonic clock cannot express it at all |
| **Expiry** (token, session, certificate) | Wall clock | Storing a monotonic value → meaningless after restart |
| **Performance profiling** | Monotonic, high resolution | Coarse wall clock → percentiles pin to the tick |

## 2. Per-language API mapping

| Use | Node.js | Python | POSIX / C | Shell |
|---|---|---|---|---|
| Measuring elapsed time | `process.hrtime.bigint()` | `time.perf_counter()` | `CLOCK_MONOTONIC` | **None** |
| Measuring elapsed time (alt) | `performance.now()` | `time.monotonic()` | `CLOCK_MONOTONIC_RAW` | **None** |
| Current instant | `Date.now()` | `time.time()` | `CLOCK_REALTIME` | `date`, `EPOCHREALTIME` |
| Elapsed including suspend | No standard API | `time.CLOCK_BOOTTIME` | `CLOCK_BOOTTIME` | **None** |
| Process CPU time | `process.cpuUsage()` | `time.process_time()` | `CLOCK_PROCESS_CPUTIME_ID` | `times` |
| Waiting for a duration | `setTimeout` | `time.sleep()` | `clock_nanosleep` | `sleep`, `timeout` |
| Inspecting clock properties | Read the docs | **`time.get_clock_info()`** | `clock_getres` | Not applicable |

- In Node, the origin of `hrtime.bigint()` is **boot** and the origin of `performance.now()` is the **process** (measured)
- In Python, `time.get_clock_info('time')` reports `adjustable=True`, `monotonic=False` for you
- For a language not in the table, check only two things: **what is the origin / can it be adjusted**

## 3. Code search patterns

```bash
# A. elapsed time - subtraction of wall clock values (strongest signal, nearly all wrong)
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. deadline / expiry - something added to a wall clock value (needs review)
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. the reverse mistake - a monotonic value assigned into stored state
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. every monotonic usage - confirm each is used only as a difference
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/
```

- **A is almost entirely fix-worthy.** A wall clock subtraction is in practice an elapsed time calculation
- **B needs judgment.** Fix deadlines and TTLs; leave token expiry and scheduled instants alone
- **A hit in D is not reassurance.** Using a monotonic clock and using it correctly are different things

## 4. Review questions

- [ ] **Will a person look at this value, or will two values be subtracted?** Subtracted means monotonic
- [ ] **Does this instant leave the process?** Stored, transmitted or cross-machine means wall clock
- [ ] **Is this deadline until a time, or for a duration?** The latter means monotonic
- [ ] **What happens if this value goes negative?** If the answer is that cannot happen, the site is risky
- [ ] **Must this expiry survive a process restart?** If so, a monotonic value must not be stored
- [ ] **Is the span short?** A millisecond-tick wall clock will report 0
- [ ] **Does this run on a device that suspends?** `CLOCK_MONOTONIC` does not count suspended time

## 5. What the fix looks like

```javascript
// before - the duration can come out negative
const t0 = Date.now();
const out = doWork(req);
log({ ts: new Date().toISOString(), duration_ms: Date.now() - t0 });

// after - the wall clock owns when, the monotonic clock owns how long
const t0 = process.hrtime.bigint();
const startedAt = new Date().toISOString();
const out = doWork(req);
log({ ts: startedAt, duration_ms: Number(process.hrtime.bigint() - t0) / 1e6 });
```

```python
# before
start = time.time()
run_batch(items)
emit_metric("batch_seconds", time.time() - start)

# after
started_at = datetime.datetime.now(datetime.timezone.utc)
start = time.monotonic()
run_batch(items)
emit_metric("batch_seconds", time.monotonic() - start, ts=started_at)
```

```bash
# before - both date calls sit on an adjustable clock
end=$(( $(date +%s) + 30 ))
while [ "$(date +%s)" -lt "$end" ]; do check_ready && break; sleep 1; done

# after - push the deadline arithmetic out of the shell
timeout 30 sh -c 'until check_ready; do sleep 1; done'
```

## 6. Measured reference values (Windows 10 / Node 22.16.0 / Python 3.13.3)

| Clock | Smallest tick | Note |
|---|---|---|
| Node `Date.now()` | **1 ms** | changed 38 times in 400,000 calls; same value up to 14,402 times in a row |
| Node `performance.now()` | 0.0001 ms | — |
| Node `hrtime.bigint()` | 100 ns | all 400,000 calls distinct |
| Python `time.time()` | **0.000238 ms** | implementation `GetSystemTimePreciseAsFileTime()` — **a wall clock can be high resolution** |
| Python `monotonic` / `perf_counter` | 100 ns | both `QueryPerformanceCounter()` |
| Shell `date +%s%N` round trip | about 48 ms | not clock resolution but **process creation cost** |

**Resolution and adjustability are independent properties.** The Python wall clock, with resolution to spare, still went negative under a clock correction.

## 7. Do not

- ❌ **Clamping a negative duration to zero or wrapping it in an absolute value** — that erases the evidence, and a forward jump leaves no such signal at all
- ❌ **Storing a monotonic value in a file, a database or a response body** — it becomes meaningless once the process changes
- ❌ A **retry deadline expressed as until a time** — a clock correction makes it expire at once or never finish
- ❌ A **monotonic value in a log timestamp** — you get 1970 and you cannot line it up against other hosts
- ❌ **Stopping at the mean** — on a coarse clock the total is right and only the percentiles collapse
- ❌ **Computing deadlines inside a shell loop** — it sits on an adjustable clock and `date` calls are expensive
- ❌ The premise that we never change the time — time sync, virtual machine resume and manual edits are ordinary operations
