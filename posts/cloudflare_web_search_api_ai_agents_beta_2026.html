계기 — AI 에이전트에 실시간 웹 검색 맥락을 붙이는 인터페이스

거대언어모델(LLM)을 쓰는 AI 에이전트가 안고 있는 한계는 모델이 특정 시점까지의 데이터로 학습한 뒤 그대로 굳어 있다는 점이다. 그래서 지식 컷오프(knowledge cutoff) 이전에 있던 정보만 알고, 최근 사건이나 바뀌는 API, 빠르게 움직이는 소식은 모델과 함께 다루기 어렵다. About 문서는 검색이 없을 때 실시간 정보가 필요한 에이전트가 보통 페이지의 URL을 추측해 곧바로 가져오려 하고, 추측이 틀리면 요청이 404 Not Found를 돌려받아 에이전트가 다시 시도해야 한다고 설명한다.

2026년 10월 2일 Cloudflare가 변경 기록에 올린 Web Search API는 베타로 제공된다. 변경 기록은 이 API가 AI 에이전트와 애플리케이션이 인터넷을 검색하고, URL을 추측하거나 모델의 학습 컷오프에 기대는 대신 실시간 정보에 근거해 응답하게 해 준다고 소개한다. 사람이 검색엔진에서 출발하듯 에이전트가 질의를 보내면 관련 있는 최신 결과 목록을 받고, 개발자는 그 결과를 모델 컨텍스트에 넣어 응답이 실시간 정보에 근거하도록 만든다.

About 문서가 적은 처리 순서는 네 단계다. 먼저 지정한 AI Gateway를 거쳐 요청을 보낸다. 다음으로 고른 검색 제공사(Ceramic.ai, Exa, Linkup)에 질의를 전달하며, 제공사를 정하지 않으면 Ceramic.ai가 기본이다. 이어서 제공사의 응답을 결과마다 URL과 제목, 그리고 선택적인 설명·이미지·파비콘·최종 수정일을 갖는 일관된 형식으로 정규화한다. 마지막으로 요청을 AI Gateway 로그에 기록하고 계정에 청구한다. 이 흐름에서 눈에 띄는 지점은 문서 기준으로 네 가지다.

  • 첫째, Ceramic.ai·Exa·Linkup이 모두 같은 결과 형식으로 정규화되므로 문서의 표현대로 매개변수 하나만 바꾸면 제공사를 갈아탈 수 있다.
  • 둘째, 모든 요청은 AI 애플리케이션의 제어 평면(control plane)이라고 소개되는 AI Gateway를 거치며, 검색 요청이 모델 추론 요청과 나란히 게이트웨이 로그와 분석에 나타난다.
  • 셋째, 통합 과금(Unified Billing)에 따라 AI Gateway 크레딧 잔액에서 각 제공사의 정가(list API price)대로 추가 할증 없이 차감된다.
  • 넷째, 세 제공사는 Cloudflare의 검증된 봇(Verified Bot) 크롤링 표준을 지키겠다고 약속(committed)했고, About 문서는 모든 검색 결과에 크롤링한 콘텐츠의 위치로 가는 링크가 있어야 한다고 적는다.

핵심 설계 — AI Gateway 단일 창구와 통합 과금 구조

Web Search API는 AI Gateway 위에 만들어졌다. How to use 문서는 어느 백엔드에서나 쓸 수 있는 REST API와 Worker의 AI 바인딩이라는 두 호출 방식이 모두 AI Gateway를 거쳐 요청을 보낸다고 적는다. 모든 계정에는 이름이 default인 게이트웨이가 있고, 필요하면 게이트웨이를 새로 만들 수도 있다. 시작하려면 Cloudflare 계정과 AI Gateway가 있어야 하고, 계정에 충전된 AI Gateway 크레딧이나 게이트웨이에 저장한 제공사 API 키 가운데 하나가 준비되어 있어야 한다.

About 문서는 모든 검색 요청이 게이트웨이를 거치기 때문에 다음 네 가지를 얻는다고 정리한다.

  • 관찰성(Observability): 검색 요청이 모델 추론 요청과 함께 게이트웨이의 로그와 분석에 나타난다.
  • 통합 과금(Unified Billing): 검색은 AI Gateway 크레딧 잔액에서 차감되며, 제공사별 정가를 그대로 내고 추가 할증은 없다. 요율은 Providers 문서에 있다.
  • 자체 키(BYOK): 이미 검색 제공사 계정이 있으면 제공사 API 키를 게이트웨이에 저장할 수 있고, 이때는 제공사가 직접 청구한다.
  • 접근 통제(Access control): 게이트웨이가 쓸 수 있는 제공사와 요청을 보낼 수 있는 주체를 통제한다.

Providers 문서도 같은 내용을 청구 방식으로 풀어 쓴다. AI Gateway 크레딧으로 결제하면 각 검색이 제공사의 정가로 청구되고 추가 할증은 없으며, 자체 키를 가져오면 제공사가 본인과 맺은 계약에 따라 직접 청구한다는 설명이다.

이 구조에서 검색 호출의 기록과 청구가 게이트웨이 한 곳에 모인다는 점이 문서가 말하는 요지다. 다만 접근 통제를 어떤 규칙으로 설정하는지, 게이트웨이 로그에 요청의 어떤 필드가 남는지는 이 문서들에 설명되어 있지 않다. 모델 추론 비용과 검색 비용을 같은 크레딧 잔액에서 본다는 것까지가 문서로 확인되는 범위다.

검색 제공자 3곳의 특성과 Zero Data Retention 표기 비교

베타 출시 시점에 선택 가능한 검색 제공자는 Ceramic.ai, Exa, Linkup 세 곳이다. 호출 시 provider 매개변수에 해당 문자열을 지정하면 즉시 검색 주체가 전환되며, 매개변수를 생략할 경우 기본 제공자인 Ceramic.ai가 선택된다. 세 업체는 인덱스 규모, 검색 알고리즘, 결과물 발췌 방식, 그리고 공식 요금에서 뚜렷한 설계 차이를 보인다.

아래 표는 공식 개발자 문서(Providers)에 기술된 각 제공자의 상세 스펙과 요금을 정리한 것이다.

제공자 식별자 웹 인덱스 및 검색 알고리즘 결과물 발췌 방식 데이터 무보존 (Zero Data Retention) 1,000건당 공식 요금
ceramic (기본값) 400억 개 이상의 독립 웹 페이지 인덱스, 저지연·저비용 설계 최대 8,000자의 상세 본문 설명 Yes (지원) $0.25 (요청당 $0.00025)
exa 키워드와 임베딩 검색을 결합한 auto 검색 타입 질의와 연관성이 가장 높은 페이지 하이라이트(highlights) No (표 기준 미지원 명시) $7.00 (요청당 $0.007)
linkup 신뢰할 수 있는 출처 중심의 fast 검색 심도, 원시 검색 결과 답변 생성 없는 원문 텍스트 스니펫과 링크 Yes (지원) $5.00 (요청당 $0.005)

여기서 공식 문서 사이의 서술이 어긋난다. 2026년 10월 2일 자 변경 기록 본문에는 세 제공사 모두 Cloudflare를 통한 요청에 대해 Zero Data Retention을 지원한다고 적혀 있다. 그러나 같은 날 갱신된 Providers 페이지의 속성 표에서는 Exa의 Zero Data Retention 값이 No로 기재되어 있다. Ceramic.ai와 Linkup은 표에서도 Yes로 일치한다. 어느 쪽이 정확한지 추가 정정은 확인되지 않았으므로, 검색어가 제공사 서버에 남으면 안 되는 환경이라면 세부 표의 값을 기준으로 삼아 provider에 Ceramic.ai나 Linkup을 지정하는 쪽이 문서와 어긋나지 않는다.

Providers 문서는 제공사별 특성을 다음과 같이 소개한다. 어디에 맞는지에 관한 서술은 모두 문서가 각 제공사에 붙인 문구다.

  • Ceramic.ai: 에이전트와 LLM 애플리케이션을 위해 설계한 자체 독립 웹 인덱스(400억 페이지 이상)를 운영하며, 저지연·저비용 검색에 초점을 둔다. 문서는 작업 하나에서 검색을 여러 번 하는 에이전트, 챗봇 답변을 최신 정보에 근거시키는 일, 모델 출력을 실시간 웹 출처와 대조하는 일에 맞는다(a good fit)고 적는다. 결과에는 페이지별로 최대 8,000자의 긴 설명이 담긴다. 가격은 1,000건당 0.25달러다.
  • Exa: AI를 위해 만든 검색엔진으로, 전통적인 키워드 검색과 임베딩 기반 검색을 결합한 자체 인덱스를 쓴다. 요청은 품질과 속도의 균형을 겨냥한 auto 검색 유형을 쓰고, 질의와 가장 관련 있는 텍스트 발췌인 하이라이트가 결과의 설명으로 반환된다. 문서는 간결하고 질의에 맞는 발췌를 모델 컨텍스트에 곧바로 넘기려 할 때 맞는다고 적으며, 가격은 1,000건당 7.00달러다.
  • Linkup: AI 애플리케이션을 위한 웹 검색으로, 웹 전반의 출처가 달린 결과와 텍스트 스니펫을 돌려준다. 요청은 fast 검색 심도와 원시 검색 결과를 쓰므로 답변을 생성하지 않는다. 문서는 신뢰할 만한 출처의 빠르고 인용 가능한 결과가 필요한 에이전트 도구 호출에 맞는다고 적고, 가격은 1,000건당 5.00달러다.
  • 결과 형식: About 문서는 모든 제공사가 같은 결과 형식(URL·제목, 선택적인 설명·이미지·파비콘·최종 수정일)을 돌려주므로 provider 값 하나만 바꿔 제공사를 갈아탈 수 있다고 적는다. 설명은 선택 필드이므로 모든 제공사가 항상 채운다고 가정하지 않는 편이 안전하다.

Providers 문서는 제공사마다 속성 표를 두고 provider 값, Zero Data Retention 여부, 가격과 함께 제공사의 문서 링크와 약관 링크를 싣는다. 약관과 데이터 취급은 제공사가 정하므로, 실제 도입 전에는 각 제공사의 약관 페이지를 따로 열어 보아야 한다는 뜻이다.

호출 인터페이스 — REST API와 Workers AI 바인딩의 규격

Cloudflare는 개발 환경에 따라 두 가지 호출 경로를 제공한다. 외부 서버나 컨테이너 환경에서는 표준 REST API 엔드포인트로 POST 요청을 전송하며, Cloudflare Workers 환경에서는 네이티브 바인딩 메서드인 env.AI.websearch()를 호출한다.

REST API는 POST https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/websearch/ 엔드포인트로 요청을 보낸다. 인증에는 두 가지 권한을 모두 가진 Cloudflare API 토큰을 쓴다. 계정(Account) 수준의 Workers AI > Read와 AI Gateway > Read다.

공식 문서에 명시된 REST API 호출 curl 예시는 아래와 같다.

curl https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/ai/websearch/ \
                      --request POST \
                      --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
                      --header "Content-Type: application/json" \
                      --data '{
                        "query": "What are some fun things to do in Salt Lake City as fall approaches?",
                        "provider": "ceramic",
                        "limit": 5,
                        "options": { "gateway": { "id": "default" } }
                      }'

Workers 환경에서는 Wrangler 구성 파일에 AI 바인딩(ai: { binding: "AI" })을 추가한 뒤 env.AI.websearch()에 게이트웨이 ID와 질의를 넘긴다. 문서의 구성 예시는 compatibility_date를 2026-10-05로 두고, 이 값을 그날의 날짜로 맞추라는 주석을 달아 둔다. websearch()는 표준 Response 객체를 돌려주므로 response.json()으로 결과를 읽는다.

export default {
                    	async fetch(request, env): Promise<Response> {
                    		const response = await env.AI.websearch({
                    			gatewayId: "default",
                    			query: "What are some fun things to do in Salt Lake City as fall approaches?",
                    			provider: "exa",
                    			limit: 5,
                    		});
                    
                    		const results = await response.json();
                    		return Response.json(results);
                    	},
                    } satisfies ExportedHandler<Env>;

문서가 적은 요청 매개변수는 다음과 같다. REST 본문에서는 게이트웨이를 options 객체에, Worker 호출에서는 gatewayId에 넣는다.

  • query (필수, 문자열): 검색어로, minLength가 1이고 maxLength가 1,024다.
  • provider (선택, 문자열): ceramic, exa, linkup 중 하나이며 기본값은 ceramic이다.
  • limit (선택, 정수): 반환할 검색 결과의 최대 개수다. 최솟값 1, 최댓값 10이며 기본값은 10이다. 한 번의 요청이 반환하는 결과는 10건이 한도다.
  • options.gateway.id (REST, 필수) 또는 gatewayId (Worker, 필수): 요청을 라우팅할 AI Gateway의 ID다. 기본 게이트웨이를 쓸 때는 default를 지정한다.
  • byokAlias (선택, 문자열): 게이트웨이에 저장한 제공사 API 키의 별칭으로 패턴은 ^[A-Za-z0-9_-]{1,64}$다. 지정했는데 해당 키가 구성되어 있지 않으면 AI Gateway 크레딧으로 넘어가지 않고 요청이 실패한다.

응답 본문은 모든 제공자가 일관되게 items 배열과 metadata 객체로 구성된 JSON 규격을 따른다.

{
                      "items": [
                        {
                          "url": "https://example.com/salt-lake-city-fall-guide",
                          "title": "Fall in Salt Lake City: A Local's Guide",
                          "description": "From scenic drives up Big Cottonwood Canyon to pumpkin patches..."
                        }
                      ],
                      "metadata": {
                        "query": "What are some fun things to do in Salt Lake City as fall approaches?",
                        "requestId": "<REQUEST_ID>",
                        "latencyMs": 612
                      }
                    }

응답 본문은 모든 제공사에서 items 배열과 metadata 객체(query, requestId, latencyMs)로 구성된다. 결과 아이템에는 url과 title이 기본으로 들어가고, 설명과 이미지·파비콘·최종 수정일은 제공사가 돌려줄 때만 포함된다. 문서의 응답 형식 설명도 선택 필드는 제공사가 반환할 때만 들어간다고 적는다.

How to use 문서는 검색을 모델의 도구로 쓰는 예시도 싣는다. web_search 함수 도구를 모델에 정의해 두고, 모델이 그 도구를 호출하면 websearch()로 검색을 실행한 뒤 결과를 tool 역할 메시지로 모델에 돌려주는 흐름이다. 예시는 Workers AI 모델을 호출하고 검색 결과를 5건으로 제한한다. 문서가 적은 한도는 두 가지뿐이며 검색어 길이 1,024자, 요청당 결과 10건이다.

크롤러 표준과 출처 귀속 — 제공사가 약속한 기준

About 문서의 「Crawler standards」 절은 Cloudflare의 입장에서 시작한다. 크롤러는 정직하고 투명해야 하며 사이트 소유자가 정한 규칙과 선호를 존중해야 하고, 사이트 소유자는 자기 콘텐츠가 어떻게 쓰이는지에 대해 의미 있는 가시성과 통제권을 가져야 한다는 것이다.

이어서 문서는 모든 Web Search API 제공사가 다음 기준을 충족하기로 약속(has committed)했다고 적는다.

  • 검증된 봇 준수(Verified bot compliance): 제공사가 쓰는 크롤러는 Cloudflare가 공개한 검증된 봇 요건을 충족해야 한다. 이 요건에는 크롤러를 식별하는 것과 robots.txt를 존중하는 것이 포함된다.
  • 출처 귀속(Source attribution): 모든 검색 결과는 크롤링한 콘텐츠의 위치로 가는 링크를 포함해야 한다.
  • 문서가 맺음말로 요약하는 목적: 이 API를 쓰면 에이전트는 사이트 소유자에게 콘텐츠가 어떻게 크롤링되는지에 대한 투명성과 통제권, 가시성을 주는 운영자의 검색 결과를 소비하게 된다.

여기까지가 문서가 직접 쓴 내용이다. 약속이 실제로 어떻게 점검되는지, 사이트 운영자가 개별 제공사의 크롤러를 어떻게 식별하고 제어하는지는 이 문서들에 나와 있지 않다. 변경 기록이 말하는 「약속」과 About 문서의 기준 두 가지를 그대로 옮기는 데서 멈추는 것이 이 절의 범위다.

자체 API 키(BYOK) 운영과 비밀값 관리 구조

How to use 문서에 따르면 이미 검색 제공사와 계정이 있는 경우 AI Gateway 크레딧 대신 자신의 API 키를 쓸 수 있고, 이때는 제공사가 직접 청구한다. 절차와 키 선택 규칙은 다음과 같다.

  • 대시보드 등록: Cloudflare 대시보드에서 AI Gateway 페이지로 가서 게이트웨이를 고르고 Provider Keys를 선택한다. Ceramic.ai, Exa, Linkup 중 하나의 API 키를 추가하고 별칭(alias, 예를 들어 default)을 붙인다. 제공사가 목록에 없으면 Configure custom providers를 선택해 추가한다.
  • 키 보관: API 키는 요청에 실려 가지 않는다. AI Gateway가 제공사와 별칭에 해당하는 게이트웨이 저장 키를 꺼내 쓰며, 저장된 키는 Secrets Store로 암호화된다.
  • 별칭을 지정한 경우: byokAlias를 주면 그 별칭의 저장 키를 쓴다. 제공사나 별칭이 게이트웨이에 구성되어 있지 않으면 크레딧으로 넘어가지 않고 400 오류로 실패한다.
  • 별칭을 생략한 경우: 게이트웨이에 해당 제공사의 default 별칭 키가 있으면 그 키를 쓰고, 없으면 검색이 AI Gateway 크레딧으로 청구된다.

문서의 BYOK 예시는 질의 「What is Cloudflare Workers?」에 provider를 exa로, byokAlias를 default로 지정한 요청이다. 호출 형태는 크레딧 방식과 같고 byokAlias 한 줄만 더해진다. 키 보관 방식의 자세한 내용은 AI Gateway의 「Bring your own keys」 문서를 보라고 How to use 문서가 안내한다.

공식 문서 서술과 확인되지 않은 사항의 대조

기술 사양을 검토할 때 가장 중요한 것은 공식 문서에 확인된 내용과 아직 공개되지 않은 한계선을 명확히 분리하는 일이다. 아래 표는 이번 베타 릴리스에서 확인된 사양과 현재 문서상으로 확인할 수 없는 영역을 1:1로 대조한 결과다.

구분 항목 공식 문서가 명시한 사실 검증되지 않았거나 주의할 사항
데이터 보존 정책 Ceramic.ai와 Linkup은 Zero Data Retention 명시 변경 기록에는 3사 모두 지원이라 적혔으나 Exa 표에는 No로 명시되어 불일치 존재
과금 및 정산 구조 제공사 공식 정가 그대로 AI Gateway 크레딧에서 차감, 추가 마진 0 무료 티어 제공 여부 및 계정 등급별 최소 크레딧 충전 단위는 문서에 미기재
호출 매개변수 제약 검색어 최대 1,024자, 결과 최대 10건(기본값 10건)을 한도로 명시 분당/일당 최대 호출 빈도(Rate Limit) 임계치 및 동시 요청 한도는 문서에 미기재
호출 인터페이스 REST API(POST) 및 Worker의 AI 바인딩 지원, 모델 도구 호출 예시 수록 LangChain, LlamaIndex, MCP(Model Context Protocol) 등 외부 프레임워크 전용 어댑터는 이 문서들에서 확인되지 않음

이 대조표에서 확인되듯, 개발팀이 실제 프로덕션 워크로드에 도입하기 전에 점검해야 할 항목들은 다음과 같다.

  • 대규모 배치 검색 시 분당 호출 제한(Rate Limit)에 걸리는지 여부는 사전 부하 테스트를 통해 확인해야 한다.
  • 1회 호출당 최대 10건의 결과만 반환되므로, 수십 개 이상의 웹 문서를 취합해야 하는 광범위한 리서치 에이전트는 검색어 분할 질의 구조를 별도로 구성해야 한다.
  • Exa를 사용할 경우 데이터 무보존이 적용되지 않을 수 있으므로, 내부 규정상 사용자 개인정보나 기업 기밀이 포함된 검색어를 다룰 때는 Ceramic.ai 또는 Linkup을 명시적으로 고정해야 한다.
  • Wrangler 로컬 개발 환경(wrangler dev)에서 AI 바인딩을 통한 websearch() 호출이 로컬 모의(Mock)로 동작하는지 실제 원격 호출로 과금되는지는 문서에 명시되어 있지 않으므로 개발 시 주의가 필요하다.

확인하지 못한 것

  • Exa의 Zero Data Retention 지원 여부에 대한 두 문서 간 상충의 실제 진위. 변경 기록 본문(3사 모두 지원)과 Providers 표(Exa: No)가 상반되나 어느 쪽이 오기인지 추가 정정 공지가 확인되지 않았다.
  • 계정 등급(Free, Workers Paid, Enterprise)에 따른 Web Search API의 분당/일당 호출 쿼터(Rate Limit) 수치. 공식 문서에 매개변수 제한(1,024자, 10건) 외에 전역 호출 한도 임계치가 기재되어 있지 않다.
  • AI Gateway 무료 티어 사용 시 Web Search API 전용 무료 검색 크레딧이나 체험 횟수가 부여되는지 여부.
  • 검색 제공자가 웹을 크롤링할 때 사용하는 고유 User-Agent 명칭과 IP 대역에 관한 상세 공개 문서.
  • Workers 로컬 개발 환경(wrangler dev) 실행 시 env.AI.websearch() 호출의 로컬 시뮬레이션 지원 여부.
