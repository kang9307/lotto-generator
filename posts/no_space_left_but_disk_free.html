2026-09-01 개발/인프라

서비스가 로그를 못 쓴다는 알림을 받고 서버에 들어간다. 습관대로 df -h 를 친다. 여유가 30퍼센트 넘게 남아 있다. 그런데 같은 셸에서 touch 한 번만 해도 No space left on device 가 돌아온다. 이 순간 대부분의 시간이 낭비되는 이유는 하나다. df 가 거짓말을 하고 있다고 생각하기 때문이다.

df 는 거짓말을 하지 않는다. 다만 묻지 않은 것에는 답하지 않는다. 용량을 물으면 용량을 답하고, 루트를 물으면 루트를 답한다. 쓰기가 실패한 진짜 이유가 용량이 아니거나 루트가 아니면 df 의 답은 정확한 채로 쓸모가 없다. 이 글은 그 어긋남이 생기는 네 가지 자리를 갈라 놓고, 어느 순서로 짚어야 가장 빨리 끝나는지를 정리한다.

증상은 하나, 원인은 넷

ENOSPC 는 커널이 응용 프로그램에게 이 쓰기를 받아 줄 수 없다고 말하는 한 가지 신호다. 신호가 하나라고 해서 사정이 하나인 것은 아니다. 사람으로 치면 열이 나는 것과 같아서, 열 자체는 진단이 아니라 진단을 시작하라는 표시다. 그런데 현장에서는 ENOSPC 를 보자마자 곧바로 지울 것 찾기로 넘어가는 일이 잦고, 원인이 용량이 아닐 때 그 작업은 전부 헛수고가 된다.

갈라야 할 자리는 넷이다. 아래 표의 오른쪽 열, 즉 구분되는 신호가 이 글의 실질적인 내용이다. 왼쪽 두 열만 외우면 여전히 순서를 못 잡는다.

원인실제로 찬 것확인 명령구분되는 신호
① inode 고갈파일 개수 한도df -iUse% 는 낮은데 IUse% 만 100%
② 삭제됐지만 열린 파일반환되지 않은 블록lsof +L1 · /proc/<pid>/fddf 는 가득, du 합계는 훨씬 작다
③ 예약 블록root 전용으로 떼어 둔 몫tune2fs -l일반 계정만 실패, root 는 성공
④ 다른 마운트내가 안 본 파일시스템df -h <경로>루트는 여유, 해당 경로만 100%
  • ①과 ④는 확인이 각각 한 줄이다. 그래서 이 둘을 맨 앞에 두는 것이 시간을 가장 많이 아낀다
  • ②는 df 와 du 를 같이 봐야만 드러난다. 하나만 보면 영원히 안 보인다
  • ③은 드물지만 같은 서버에서 사람마다 결과가 다른 기묘한 상황을 만들어 오래 잡아먹는다

이 글의 실행 환경과 검증 범위

이 글의 주제는 리눅스 서버인데, 여기 붙은 출력을 실제로 만들어 낸 환경은 Windows 10 위의 Git Bash 다. 이 사실을 먼저 밝히는 이유는 겸손해 보이기 위해서가 아니라, 어떤 출력은 그대로 믿어도 되고 어떤 출력은 여기 없는지를 독자가 구분할 수 있어야 하기 때문이다.

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -a
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64 2025-01-30 11:14 UTC x86_64 Msys

$ df --version | head -1
df (GNU coreutils) 8.32

coreutils 는 리눅스와 같은 GNU 8.32 이므로 df·du·stat·sort 의 옵션 동작과 계산 방식은 동일하다. 다르게 나오는 것은 그 아래 파일시스템이 NTFS 라는 점뿐이고, 뒤에서 보겠지만 그 차이 자체가 inode 를 이해하는 데 오히려 도움이 된다.

  • 실제로 돌린 것 - df -h, df -i, df --output, stat -f, stat -c, du 각종 조합, find -printf, 그리고 삭제됐지만 열린 파일 재현 전체
  • 돌리지 못한 것 - lsof +L1(이 환경에 lsof 자체가 없다), tune2fs·debugfs·resize2fs(ext4 전용), 컨테이너 오버레이 관련 전부
  • 지어내지 않은 것 - 돌리지 못한 명령의 출력은 이 글에 한 줄도 없다. 명령과 읽는 법만 적었다
  • 손댄 것 - 출력에 나온 사용자 경로만 /tmp/demo 와 <user> 로 줄여 적었다. 숫자는 하나도 고치지 않았다
  • 블록 크기는 이 환경에서 4,096 바이트로 보고된다. 이 글의 블록 계산은 전부 이 값 기준이다
  • 다른 셸(dash·zsh)이나 BSD 계열 df·du 에서는 옵션 이름과 출력 형식이 다르다. 아래 명령들은 GNU coreutils 기준이다

먼저 물을 것 - 정말 그 파일시스템인가

순서상 이것이 첫 번째다. 원인 목록에서는 ④번이지만 확인이 가장 싸기 때문이다. df -h 를 인자 없이 치면 마운트 목록이 나오고, 사람의 눈은 대개 맨 위 루트 줄에서 멈춘다. 정작 실패한 경로가 다른 파일시스템에 붙어 있으면 그 줄은 화면 아래 어딘가에 있다.

고치는 방법은 df 에 경로를 직접 주는 것이다. 이 환경에서도 같은 물리 디스크를 두 개의 다른 마운트로 보고한다.

$ df -h . /
Filesystem                        Size  Used Avail Use% Mounted on
C:/Users/<user>/<temp>  931G  600G  332G  65% /tmp
C:/Program Files/Git                931G  600G  332G  65% /

# 요점 - 현재 디렉터리는 / 가 아니라 /tmp 에 붙어 있다.
# 리눅스에서도 똑같다. 실패한 경로를 df 에 직접 준다.
$ df -h /var/log

리눅스 서버에서 이 함정이 가장 자주 걸리는 자리는 정해져 있다. 아래 목록은 루트에 여유가 있는데도 쓰기가 실패하는 전형적인 배치다.

  • /var 가 별도 파티션인 구성 - 로그와 패키지 캐시가 여기 쌓이므로 루트보다 훨씬 먼저 찬다
  • /boot - 대체로 수백 MB 로 잡혀 있어 커널 패키지 몇 개만 쌓여도 찬다. 증상이 커널 업데이트 실패로 나타나 디스크 문제로 안 보인다
  • /tmp 가 tmpfs 인 구성 - 메모리를 쓰므로 실제 디스크와 무관하게 찬다. 재부팅하면 사라져 원인이 증발한다
  • 컨테이너 안 - 쓰기 가능 레이어와 마운트된 볼륨은 서로 다른 파일시스템이다. 볼륨에 여유가 있어도 레이어가 차면 실패한다
  • 바인드 마운트나 NFS 가 겹친 경로 - 경로 문자열만 보면 같은 트리 같지만 장치가 다르다

원인 ① inode 고갈 - 용량은 남았는데 개수가 찼다

파일시스템은 데이터만 저장하는 것이 아니라 파일 하나하나에 대한 메타데이터 항목도 따로 관리한다. 소유자, 권한, 시각, 그리고 실제 데이터 블록이 어디 있는지를 담은 구조가 inode 다. 파일 이름은 여기 없다. 이름은 디렉터리가 들고 있고, 디렉터리는 이름과 inode 번호를 짝지은 목록이다. 이 구조 때문에 하나의 inode 에 여러 이름이 붙을 수 있고, 그것이 하드링크다.

중요한 것은 이 항목의 개수에 한도가 있을 수 있다는 점이다. 한도가 차면 블록이 아무리 남아 있어도 새 파일을 만들 수 없다. 확인은 df -i 한 줄이다. 그런데 이 환경에서 그 명령은 이렇게 답한다.

$ df -i .
Filesystem                       Inodes IUsed IFree IUse% Mounted on
C:/Users/<user>/<temp>    -     -     -     - /tmp

$ stat -f .
  File: "."
    ID: ea1df1ef00000000 Namelen: 255     Type: UNKNOWN
Block size: 4096       Fundamental block size: 4096
Blocks: Total: 244041727  Free: 86972107   Available: 86972107
Inodes: Total: 18446744073709551615 Free: -1

전부 - 다. 그리고 stat -f 는 그 이유를 보여 준다. inode 총계로 보고된 18,446,744,073,709,551,615 는 부호 없는 64비트 정수의 최댓값, 즉 한도가 없다는 뜻의 표시값이고 Free 는 -1 이다. NTFS 에는 ext4 같은 고정 inode 테이블이 없으므로 보고할 숫자 자체가 없는 것이다.

이 빈칸은 실패가 아니라 가장 중요한 사실을 그대로 보여 주는 화면이다. inode 한도는 파일시스템의 보편적 속성이 아니라 구현마다 다른 설계 선택이다. 그래서 ext4 서버에서 통하는 대응이 XFS 서버에서 그대로 통하지 않는다. 리눅스에서 실제 숫자가 채워진 화면과, 그때 이어서 칠 명령은 이렇다.

# ① 어느 마운트의 inode 가 찼는지
df -i

# ② 그 마운트 안에서 파일이 몰린 디렉터리 (한 번에 크게 보기)
du --inodes -x -d 2 /var 2>/dev/null | sort -n | tail -20

# ③ 디렉터리별 파일 개수를 직접 세기 (du --inodes 가 없는 옛 환경)
find /var -xdev -type f -printf '%h\n' 2>/dev/null \
  | sort | uniq -c | sort -rn | head -20

# 위 세 줄은 이 환경에서 실행하지 못했다.
# NTFS 가 inode 수를 보고하지 않아 ①이 빈칸이기 때문이다.

작은 파일이 수백만 개씩 쌓이는 자리는 대체로 정해져 있다. 아래는 용량 그래프에는 아무 변화도 없는데 inode 만 조용히 차오르는 전형적인 위치다.

  • 세션 파일 - 만료 정리를 걸어 두지 않으면 방문자 수만큼 파일이 쌓이고 각각은 수백 바이트다
  • 메일 큐와 Maildir - 메시지 하나가 파일 하나다. 발송이 막히면 큐가 그대로 개수로 남는다
  • 캐시 조각 - 해시를 디렉터리로 쪼개는 캐시는 디렉터리도 inode 를 쓴다는 점 때문에 두 배로 불어난다
  • 로그 조각 - 회전 주기가 짧고 보관 개수가 크면 압축본이 계속 남는다. 각각은 작지만 개수로 승부가 난다
  • 의존성 디렉터리 - 빌드 환경마다 하나씩 만들어지는 패키지 트리는 파일 수만 수십만 단위로 늘어난다

inode 는 언제 정해지는가 - ext4 · XFS · btrfs

여기서 갈린다. mke2fs 문서는 -i 옵션, 즉 inode 하나당 몇 바이트를 배정할지에 대해 이렇게 못 박는다. 파일시스템이 만들어진 뒤에는 이 비율을 바꿀 수 없으니 값을 신중히 정하라는 것이다. 예약 블록 비율의 기본값이 5퍼센트라는 것도 같은 문서에 있다.

이 한 문장이 실무에서 뜻하는 바는 무겁다. ext4 에서 inode 가 찼다면 늘리는 선택지는 없다. 파일 개수를 줄이거나, 데이터를 옮기고 파일시스템을 다시 만드는 것뿐이다. 장애 한복판에서 알게 되기에는 늦은 사실이라, 스토리지를 설계할 때 미리 정해 두는 편이 낫다.

파일시스템inode 배정 방식나중에 늘릴 수 있는가실무에서 뜻하는 것
ext4mkfs 시점에 개수 고정. -i 비율 또는 -N 개수로 지정불가. 문서가 명시적으로 변경 불가라고 적는다작은 파일이 많을 것을 알면 만들 때 비율을 낮춰 둔다
XFS동적 할당. 상한만 maxpct 로 관리가능. xfs_growfs -m 으로 상한 변경고갈이 나도 상한을 올려 시간을 벌 여지가 있다
btrfs커널 문서 기능 목록에 동적 inode 할당이 올라 있다고정 한도라는 개념 자체가 다르다df -i 의 숫자를 ext4 와 같은 뜻으로 읽으면 안 된다
  • XFS 의 maxpct 기본값은 파일시스템 크기에 따라 다르다. 문서 기준으로 1TB 미만 25퍼센트, 50TB 미만 5퍼센트, 그 이상 1퍼센트 다
  • maxpct 를 0 으로 두면 사실상 파일시스템 전체가 inode 블록이 될 수 있다고 문서는 적는다. 상한을 푸는 것이지 데이터 공간을 지켜 주는 장치가 사라지는 것이기도 하다
  • 그래서 df -i 의 IUse% 는 파일시스템 종류를 알아야 읽을 수 있는 숫자다. 같은 90퍼센트라도 ext4 에서는 경보, XFS 에서는 상한을 올릴지 판단할 재료다

원인 ② 지웠는데 열려 있는 파일

rm 은 데이터를 지우는 명령이 아니다. 디렉터리에서 이름 하나를 떼어 내는 unlink 다. 이름이 전부 사라져 링크 수가 0 이 되어도, 그 파일을 열어 둔 프로세스가 하나라도 남아 있으면 커널은 블록을 반환하지 않는다. 마지막 참조가 닫히는 순간에야 공간이 돌아온다.

이 동작 자체는 결함이 아니라 POSIX 가 정한 안전장치다. 읽는 도중에 파일이 사라져 프로세스가 깨지는 일을 막아 준다. 문제는 이때 관측 도구가 서로 다른 답을 준다는 것이다. df 는 파일시스템의 블록 계정을 읽으므로 붙잡힌 공간을 사용 중으로 본다. du 는 디렉터리를 걸어 다니며 파일을 세므로 이름이 없는 파일은 아예 못 본다. 그래서 둘이 어긋난다.

이 환경에서 그대로 재현됐다. 1GiB 파일을 만들고, tail -f 로 붙잡은 채 지우고, 여유 블록 수를 단계마다 읽었다. 아래는 실제 출력이다.

$ cd /tmp/demo
$ free() { stat -f -c %f .; }          # 여유 블록 수 (1블록 = 4096바이트)

STEP 0  빈 디렉터리          여유 블록: 86970141
$ head -c 1073741824 /dev/zero > big.log
STEP 1  1GiB 생성            여유 블록: 86707994   du -sh: 1.0G
$ ( tail -f big.log > /dev/null & )
STEP 2  tail 이 붙잡음
$ rm big.log
STEP 3  rm 직후              여유 블록: 86708010   du -sh: 1.0K
STEP 3b 2초 뒤               여유 블록: 86708010
$ kill <tail 의 pid>
STEP 4  프로세스 종료 후     여유 블록: 86970153

숫자를 그대로 읽으면 이렇다. 파일을 만들 때 262,147 블록이 줄었다. 4,096 바이트를 곱하면 약 1.0GiB 로, 만든 크기와 맞는다. 그런데 rm 직후 돌아온 것은 16 블록뿐이다. 1GiB 를 지웠는데 64KiB 가 돌아온 것이니 사실상 0 이다. 반면 같은 시점에 du 는 이미 1.0K 를 답한다. df 와 du 가 1GiB 만큼 어긋난 상태가 여기서 만들어진다.

그리고 프로세스를 종료하자 262,143 블록이 한꺼번에 돌아왔다. 지운 것은 rm 이었지만 공간을 반환한 것은 kill 이었다. 해결은 파일을 또 지우는 것이 아니라 붙잡은 쪽을 놓게 만드는 것이라는 말의 근거가 이 두 줄이다.

범인을 찾는 것은 별개의 문제다. 표준 도구는 lsof +L1 인데, 문서는 이 형태가 이름이 지워진 채 열려 있는 파일을 고른다고 설명한다. 다만 이 환경에는 lsof 가 설치돼 있지 않아 돌리지 못했다. 대신 /proc 쪽은 그대로 동작했고, 커널이 붙여 주는 (deleted) 표시가 선명하게 나왔다.

# 이 환경에서 실행한 것 - /proc 으로 확인
$ ls -l /proc/<pid>/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/big.log (deleted)

# 이 환경에서 실행하지 못한 것 - lsof 미설치
$ sudo lsof +L1                  # 링크 수가 1 미만인 열린 파일만
$ sudo lsof -nP +L1 /var         # 특정 마운트로 좁히기
주의 - 프로세스를 재시작할 수 없어 > /proc/<pid>/fd/<n> 로 파일 서술자를 절단하는 방법이 널리 알려져 있다. 공간은 즉시 돌아오지만 번호를 잘못 고르면 그 프로세스가 열어 둔 다른 파일이 통째로 비워진다. 되돌릴 수 없고 확인 절차도 없다. 재시작이 가능하면 재시작이 언제나 안전한 쪽이다.
  • 이 상황을 가장 많이 만드는 것은 로그 회전 설정 실수다. 파일을 옮기거나 지운 뒤 프로세스에게 다시 열라는 신호를 주지 않으면, 프로세스는 이름 없는 옛 파일에 계속 쓴다.로그 회전이 조용히 실패하는 자리가 여기다
  • 붙잡은 프로세스를 특정하는 절차 자체는 이 글의 범위 밖이다. 여기서는 공간이 안 도는 이유까지만 본다
  • 디스크 사용량이 계단처럼 줄지 않는 그래프는 이 원인의 좋은 신호다. 정리 작업을 돌렸는데 그래프가 평평하면 지운 것이 아직 열려 있다
  • 재시작 대상은 대체로 로그를 쓰는 쪽이다. 로그를 파일로 남기는 응용 프로그램, 그리고 그 로그를 읽어 전송하는 수집기 양쪽 모두가 같은 파일을 붙잡고 있을 수 있다

원인 ③ 예약 블록 - root 에게만 보이는 여유

ext 계열은 전체 블록의 일부를 특권 프로세스 전용으로 떼어 둔다. tune2fs 문서는 그 이유를 두 가지로 적는다. 파일시스템 단편화를 피하기 위해서, 그리고 비특권 프로세스가 쓰기를 거부당한 뒤에도 시스템 데몬이 계속 정상 동작할 수 있게 하기 위해서다. 기본값은 5퍼센트다.

그래서 이런 장면이 만들어진다. 애플리케이션 계정으로는 쓰기가 실패하는데, 관리자로 들어가 같은 위치에 파일을 만들면 성공한다. 두 사람이 같은 서버를 보면서 서로 다른 결론을 내는 상황이 여기서 생긴다. df 의 Use% 가 100퍼센트가 아니라 95퍼센트 언저리에서 멈춰 있는데 쓰기가 실패한다면 이 원인을 의심할 만하다.

# 예약 블록 확인 (ext2/3/4) - 이 환경에서는 실행하지 못했다
$ sudo tune2fs -l /dev/sda1 | grep -iE 'block count|reserved'
# Block count:              전체 블록 수
# Reserved block count:     예약된 블록 수
# 두 값의 비율이 곧 예약 비율이다.

# 비율 조정 - 되돌릴 수 있지만 신중히
$ sudo tune2fs -m 1 /dev/sda1    # 5% -> 1%
주의 - tune2fs -m 0 으로 예약을 완전히 없애는 조언이 자주 보이지만, 문서가 밝힌 두 가지 목적이 함께 사라진다. 여유가 0 에 가까워지면 연속된 블록을 찾지 못해 단편화가 급격히 진행되고, 로그를 쓰는 데몬까지 함께 멈춰 장애 원인을 기록할 수단을 잃는다. 마운트된 상태에서 잘못 지정하면 되돌리기 전까지 그대로 적용된다.
  • 예약 비율은 퍼센트다. 그래서 디스크가 커질수록 떼어 내는 절대량이 커진다. 수 TB 볼륨에서 5퍼센트는 상당한 양이 된다
  • 데이터 전용 볼륨, 즉 시스템 데몬이 로그를 쓰지 않는 볼륨에서는 비율을 낮출 근거가 있다. 다만 0 이 아니라 1~2퍼센트 정도로 남긴다
  • 반대로 / 와 /var 에서는 기본값을 그대로 두는 편이 낫다. 여기가 바로 문서가 말한 데몬이 계속 동작해야 하는 자리다
  • XFS 에는 같은 이름의 개념이 없고 다른 방식으로 여유를 관리한다. ext 계열의 습관을 그대로 옮기면 안 된다

작은 파일이 공간을 더 먹는 이유

파일시스템은 바이트 단위로 공간을 주지 않고 블록 단위로 준다. 1 바이트짜리 파일도 블록 하나를 통째로 받는다. 남는 부분은 다른 파일이 쓸 수 없고, 이 낭비를 내부 단편화라고 부른다. 말로만 들으면 사소해 보이지만 개수가 곱해지는 순간 성격이 달라진다.

실제로 재 봤다. du 의 --apparent-size 는 논리적 크기를, 기본 동작은 실제 할당량을 보고한다. 두 값을 나란히 놓으면 차이가 그대로 보인다.

$ du -b --apparent-size one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1        one_byte.txt
100      b100.bin
4096     b4096.bin
4097     b4097.bin
1048576  b1m.bin

$ du --block-size=1 one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1024     one_byte.txt
1024     b100.bin
4096     b4096.bin
8192     b4097.bin
1048576  b1m.bin

가장 눈여겨볼 줄은 b4097.bin 이다. 논리 크기 4,097 바이트에 실제 할당은 8,192 바이트다. 블록 경계를 한 바이트 넘겼다는 이유로 4,096 바이트가 통째로 더 붙었다. 4,096 바이트 파일은 정확히 4,096 을 쓰는데 말이다.

논리 크기실제 할당(측정)낭비배수
1 B1,024 B1,023 B1,024배
100 B1,024 B924 B약 10배
4,096 B4,096 B01배
4,097 B8,192 B4,095 B약 2배
1,048,576 B1,048,576 B01배

여기서 하나 정직하게 짚을 것이 있다. 1 바이트 파일의 할당이 4,096 이 아니라 1,024 로 나온 것은 NTFS 가 아주 작은 파일을 메타데이터 레코드 안에 함께 저장하기 때문이다. ext4 는 이 최적화를 기본으로 쓰지 않으므로 같은 실험에서 4,096 이 나올 것으로 예상되지만, 그 화면은 이 글에 없다. 반면 블록 경계에서 두 배로 뛰는 b4097.bin 의 동작은 블록 단위 할당을 쓰는 파일시스템에 공통이다.

개수를 곱하면 어떻게 되는지도 재 봤다. 1 바이트 파일 2만 개다.

$ time ( for i in $(seq 1 20000); do printf 'x' > "f$i"; done )
real    0m25.766s

$ ls -1 | wc -l
20000

$ du -sb --apparent-size .
20000     .          # 논리 합계 = 20,000 바이트 (약 20KB)

$ du -s --block-size=1 .
24674304  .          # 실제 점유 = 24,674,304 바이트 (약 23.5MiB)

논리 20KB 가 실제로는 23.5MiB 를 차지한다. 약 1,233배다. 이 값에는 파일 자체의 할당분과 2만 개의 이름을 담느라 커진 디렉터리 구조가 함께 들어 있다. 디렉터리도 공간을 쓴다는 사실이 여기서 눈에 보인다.

  • ext4 에서 4KiB 블록으로 같은 일을 하면 산수는 이렇게 된다. 1 바이트 파일 100만 개는 논리 1MB, 실제로는 4,096,000,000 바이트 즉 약 3.8GiB 다. 이 값은 측정이 아니라 블록 크기로 한 계산이며 디렉터리 구조는 뺀 값이다
  • 그래서 파일이 많은 자리에서는 용량과 inode 가 동시에 소진된다. 어느 쪽이 먼저 바닥나는지는 파일 크기 분포에 달렸다
  • 작은 파일을 묶어 하나로 만드는 것이 근본 대응이다. 로그는 회전 후 압축하고, 캐시는 만료를 걸고, 아카이브는 개별 파일이 아니라 묶음으로 보관한다

무엇이 먹었는지 찾기 - du 관용구

마운트를 특정하고 용량 문제가 맞다는 것까지 확인했으면, 그다음은 위에서 아래로 좁혀 내려가는 일이다. 관용구는 하나면 충분하다.

$ du -h -x --max-depth=1 . | sort -h
1.0K    ./deleted_open
1.0K    ./demo2
24M     ./tiny
25M     .

# 큰 것이 아래로 오므로 마지막 줄부터 읽는다.
# 리눅스에서는 보통 이렇게 시작한다.
$ sudo du -h -x --max-depth=1 / | sort -h

세 옵션이 각각 일을 한다. --max-depth=1 은 한 단계만 보여 준다. 깊이를 주지 않으면 수만 줄이 쏟아져 읽을 수 없다. sort -h 는 24M 같은 사람이 읽는 표기를 크기 순으로 정렬한다. 문자열 정렬로는 9K 가 24M 보다 뒤에 온다.

그리고 -x 가 이 관용구의 핵심이다. 다른 파일시스템으로 넘어가지 않게 막는 옵션이다. 이것을 빼고 / 부터 훑으면 마운트된 네트워크 저장소나 컨테이너 레이어까지 따라 들어가서, 시간은 몇 배로 걸리고 지금 찾는 파일시스템과 무관한 숫자가 결과에 섞인다.

다만 여기서도 정직하게 적어 둘 것이 있다. 이 환경에서는 -x 가 실제로 무언가를 막는 장면을 만들지 못했다.

$ stat -c %d / /tmp .
3927831023
3927831023
3927831023
# 셋 다 같은 장치 ID -> -x 가 멈출 경계가 애초에 없다.
# 옵션이 받아들여지고 결과가 같다는 것까지만 확인했다.

# 파일 개수로 좁히는 판 (inode 고갈일 때)
$ find . -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head -5
  20000 ./tiny
      5 .
      1 ./demo2
      1 ./deleted_open
  • sort -h 는 GNU 확장이다. 이 환경의 도움말에 -h, --human-numeric-sort 로 실재함을 확인했지만, BSD 계열이나 최소 컨테이너 이미지에는 없을 수 있다. 그때는 du -k 로 뽑아 sort -n 을 쓴다
  • du --inodes 는 크기가 아니라 항목 개수를 센다. inode 고갈일 때 위 관용구에서 -h 만 빼고 이것으로 바꾸면 그대로 쓸 수 있다
  • find 는 파일을 하나하나 훑으므로 파일이 많은 파일시스템에서 오래 걸린다. 운영 중 서버에서는 부하를 감안해 범위를 좁혀 시작한다
  • 결과가 합계와 맞지 않으면 원인 ②를 의심한다. du 로 아무리 더해도 df 의 사용량에 못 미치면 이름 없는 파일이 어딘가에 열려 있는 것이다

진단 순서 - 네 단계

지금까지의 내용을 실행 순서로 접으면 네 단계다. 각 단계는 다음 단계로 갈지 말지를 결정하기 위해 있다. 순서를 지키는 이유는 앞 단계가 뒤 단계보다 압도적으로 싸기 때문이다.

단계무엇을 묻는가명령이렇게 나오면다음
1어느 마운트인가df -h <실패한 경로>그 줄의 Use% 가 낮다다른 경로를 잘못 보고 있었다. 실패한 경로를 다시 확인
2용량인가 inode 인가df -i <실패한 경로>IUse% 만 100%원인 ①. 파일이 몰린 디렉터리를 찾는다
3du 와 어긋나는가du -sh -x <마운트> 를 df 와 대조du 합계가 훨씬 작다원인 ②. 붙잡은 프로세스를 찾아 재시작
4무엇이 먹었나du -h -x --max-depth=1 | sort -h큰 항목이 특정된다한 단계씩 내려가며 반복
+root 만 되는가일반 계정과 root 로 각각 touchroot 만 성공원인 ③. 예약 블록을 확인
  • 1단계와 2단계는 합쳐서 두 줄이고 부하가 사실상 없다. 그런데 이 둘만으로 끝나는 경우가 실제로 상당수다
  • 3단계를 건너뛰면 4단계에서 시간을 다 쓰고도 아무것도 못 찾는다. du 가 범인을 못 찾는 상황이 존재한다는 것을 아는 것이 이 표의 요점이다

컨테이너와 클라우드에서 달라지는 것

같은 증상이 컨테이너 안에서는 더 헷갈린다. 컨테이너 안의 df 는 그 컨테이너가 보는 마운트를 답하는데, 실제로 찬 것은 호스트 노드의 디스크인 경우가 많다. 반대로 노드는 여유가 넘치는데 컨테이너의 쓰기 가능 레이어에 걸린 한도만 찬 경우도 있다. 어느 쪽에서 df 를 쳤는지를 먼저 정해야 한다.

상황착각하기 쉬운 것실제로 봐야 할 곳
이미지 레이어가 찼다볼륨에 여유가 있으니 괜찮다쓰기 가능 레이어는 볼륨과 다른 파일시스템이다
중지된 컨테이너와 옛 이미지가 쌓였다실행 중인 것만 세면 얼마 안 된다중지된 컨테이너·미사용 이미지·빌드 캐시를 전부 합산
컨테이너 로그가 무한히 자란다애플리케이션이 로그를 안 남긴다런타임이 표준 출력을 파일로 적재한다. 크기 상한 설정 확인
클라우드 디스크를 늘렸는데 그대로다콘솔에서 늘렸으니 끝났다파티션과 파일시스템은 따로 늘려야 한다
노드의 inode 가 찼다용량 그래프가 평평하니 문제없다이미지 레이어는 작은 파일 덩어리다. inode 를 따로 감시

마지막 줄은 특히 자주 걸린다. resize2fs 문서는 이 프로그램은 파티션의 크기를 조작하지 않는다고 명시한다. 즉 블록 장치를 늘렸다면 파티션을 먼저 확장하고, 그다음에 파일시스템을 확장해야 한다. 이 두 단계를 하나로 착각하면 콘솔에서는 용량이 늘었는데 서버 안에서는 그대로인 상태가 된다.

# 클라우드 디스크 확장 후 - 순서가 있다 (이 환경에서 실행하지 못했다)
# ① 커널이 새 크기를 봤는지
lsblk

# ② 파티션 확장 (파티션을 쓰는 구성일 때만)
sudo growpart /dev/sda 1

# ③ 파일시스템 확장
sudo resize2fs /dev/sda1        # ext2/3/4
sudo xfs_growfs /               # XFS 는 마운트 지점을 준다

# 컨테이너 쪽 - 무엇이 자리를 차지하는지 종류별 합계
docker system df
docker system df -v
  • 오버레이 방식은 파일을 수정할 때 원본을 위쪽 레이어로 복사한 뒤 고친다. 큰 파일 한 줄을 고쳐도 그 파일 크기만큼 공간이 더 필요할 수 있다
  • 컨테이너 안에서 지운 파일은 아래 레이어에서 사라지지 않는다. 삭제 표시만 위에 얹히므로 이미지 크기는 줄지 않는다
  • 정리 명령은 편리한 만큼 위험하다. 사용하지 않는 볼륨까지 함께 지우는 옵션이 있고, 그 볼륨에 데이터가 들어 있을 수 있다
  • 노드 전체가 찬 상황에서는 스케줄러가 파드를 다른 노드로 밀어낸다. 증상이 디스크가 아니라 재기동으로 먼저 나타나 원인이 늦게 잡힌다

급할 때 - 지워도 되는 것과 안 되는 것

서비스가 멈춰 있으면 판단할 시간이 없다. 그래서 미리 정해 둔 목록이 필요하다. 다만 첫 수는 지우는 것이 아니다. 붙잡힌 공간이 있는지 먼저 확인하는 것이 첫 수다. 원인 ②라면 무엇을 지워도 회수되지 않으므로, 확인 없이 지우기 시작하면 시간만 잃고 되돌릴 수 없는 삭제만 남는다.

구분대상왜
비교적 안전회전 후 압축된 옛 로그이미 닫힌 파일이다. 보관 기간만 확인하면 된다
비교적 안전패키지 관리자 캐시다시 내려받을 수 있다. 재설치 시간만 든다
비교적 안전빌드 산출물과 임시 디렉터리재생성 가능. 단 진행 중인 빌드가 없는지 확인
주의코어 덤프지워도 되지만 장애 원인 분석 자료다. 먼저 옮긴다
절대 금지지금 열려 있는 로그 본체공간은 안 돌아오고 로그만 잃는다. 원인 ② 를 만든다
절대 금지데이터베이스 파일·잠금 파일·소켓손상이나 기동 불능으로 이어진다
절대 금지내용을 모르는 디렉터리급할수록 확인하지 않고 지운다. 되돌릴 수 없다
주의 - rm -rf 는 확인을 묻지 않고 되돌릴 수 없다. 경로를 변수로 만들어 쓰면 변수가 비었을 때 최상위부터 지우는 사고가 난다. 실행 전에 같은 인자로 ls -d 를 먼저 돌려 대상을 눈으로 확인하는 습관이 값싸다. truncate -s 0 은 파일을 남긴 채 비우므로 열려 있는 로그에 쓸 수 있지만, 내용은 그대로 사라진다. 옮길 값이 있으면 먼저 옮긴다.
  • 공간이 완전히 0 이면 지우는 작업 자체가 실패할 수 있다. 로그를 남기거나 임시 파일을 만드는 도구는 이때 동작하지 않는다
  • 그래서 truncate -s 0 이나 : > 파일 처럼 새 파일을 만들지 않는 비우기가 이 상황에서 유용하다
  • 급한 불을 끈 뒤에는 반드시 원인을 되짚는다. 지워서 해결됐다는 것은 왜 찼는지를 설명하지 않는다. 같은 일이 같은 주기로 돌아온다

애초에 막는 법

이 증상은 감시 항목이 하나 빠져 있어서 생기는 경우가 많다. 용량은 거의 모든 곳에서 보고 있지만 inode 사용률은 기본 대시보드에 없는 일이 흔하다. 그래서 용량 그래프가 평평한 채로 장애가 난다.

임계 초과 마운트만 뽑는 스니펫을 하나 만들어 돌려 봤는데, 여기서 흔한 관용구가 실제로 틀리는 장면이 나왔다. 기록해 둘 만한 실패라 그대로 옮긴다.

# 흔히 쓰는 판 - 이 환경에서 오답을 냈다
$ df -P | awk 'NR>1 && $5+0 >= 80 {print $6, $5}'
65% 347611880          # 값이 뒤집혀 나왔다

# 이유 - 장치 이름에 공백이 있어 필드가 하나 밀렸다
$ df -P | awk 'NR>1 {print "NF=" NF "  $5=[" $5 "]  $6=[" $6 "]"}'
NF=7  $5=[347583704]  $6=[65%]

# 고친 판 - 필드를 세지 말고 지정해서 받는다
$ df --output=pcent,target | awk 'NR>1 && $1+0 >= 60 {print "DISK", $2, $1}'
DISK / 65%

$ df --output=ipcent,target | awk 'NR>1 && $1+0 >= 60 {print "INODE", $2, $1}'
(출력 없음 - 이 파일시스템이 inode 비율을 보고하지 않는다)

df -P 의 출력을 필드 번호로 자르는 방식은 장치 이름이나 마운트 지점에 공백이 없다는 가정 위에 서 있다. 그 가정이 깨지면 조용히 다른 열을 읽고, 조건식은 그대로 참이 되어 틀린 경보가 정상처럼 나간다. df --output= 으로 필요한 열만 받으면 이 가정 자체가 필요 없어진다.

  • inode 사용률을 감시 항목에 추가한다. 용량과 같은 임계로 두면 충분하다. 없는 것보다 낫다는 수준이 아니라, 이 글의 원인 ①은 이것 하나로 전부 예방된다
  • 로그 회전은 보관 개수와 압축 여부를 같이 정한다. 개수만 크게 잡으면 용량은 괜찮은데 inode 가 찬다
  • 임시 파일에는 만료 정리를 건다. 세션과 캐시는 만드는 코드가 지우는 코드까지 갖고 있어야 한다
  • 컨테이너 로그에는 파일 크기 상한과 보관 개수를 명시한다. 기본값이 무제한인 구성이 흔하다
  • 경보는 남은 퍼센트가 아니라 남은 시간으로 보는 편이 낫다. 하루에 몇 GB 씩 늘고 있는지를 알면 언제 찰지를 계산할 수 있다

정리

No space left on device 는 진단이 아니라 진단의 시작이다. 그 뒤에는 최소 네 가지 사정이 있고, 어느 것인지에 따라 해야 할 일이 정반대가 된다. inode 가 찼으면 큰 파일을 찾아도 소용없고, 지워도 열려 있는 파일이 원인이면 더 지우는 것이 해가 된다.

그래서 외울 것은 명령 목록이 아니라 순서다. 실패한 경로를 df 에 직접 주고, df -i 로 용량인지 개수인지 가르고, du 합계를 df 와 맞춰 보고, 그다음에야 무엇이 먹었는지 찾는다. 세 번째 단계가 이 순서의 값어치다. 여기서 어긋남이 보이면 나머지 탐색이 전부 헛수고라는 것을 미리 알 수 있다.

그리고 이 글에서 실제로 재 본 숫자 두 개는 기억해 둘 만하다. 지운 1GiB 가 프로세스를 죽이기 전까지 16 블록만 돌아왔다는 것, 그리고 1 바이트 파일 2만 개가 23.5MiB 를 차지했다는 것이다. 둘 다 df 를 한 번만 보는 습관으로는 절대 보이지 않는 숫자다.

확인하지 못한 것

  • inode 가 실제로 고갈된 화면을 만들지 못했다. 이 환경의 NTFS 는 inode 수를 보고하지 않아 df -i 가 전부 - 로 나온다. IUse% 가 100퍼센트인 출력은 이 글에 없고, 대신 왜 빈칸이 나오는지를 stat -f 로 보였다
  • lsof +L1 을 돌리지 못했다. 이 환경에 lsof 가 설치돼 있지 않다. 옵션의 의미는 문서에서 확인했고, 같은 목적의 /proc/<pid>/fd 쪽은 실제로 돌려 (deleted) 표시까지 확인했다
  • tune2fs·debugfs·resize2fs·xfs_growfs 는 실행하지 못했다. ext4/XFS 전용 도구이고 이 환경에 대상 파일시스템이 없다. 예약 블록 비율 5퍼센트, XFS 의 maxpct 기본값, resize2fs 가 파티션을 건드리지 않는다는 점은 공식 man 문서에서 확인했다
  • ext4 에서 1 바이트 파일의 할당량을 직접 재지 못했다. 이 환경에서는 1,024 바이트로 나왔고 이는 NTFS 의 소형 파일 저장 방식 때문이다. 4KiB 블록 기준 계산값은 본문에 계산이라고 밝혀 적었다
  • du -x 가 파일시스템 경계에서 멈추는 장면을 만들지 못했다. /·/tmp·작업 디렉터리의 장치 ID 가 모두 같아 넘어갈 경계가 없었다. 옵션이 받아들여진다는 것까지만 확인했다
  • btrfs 의 df -i 출력 형태는 확인하지 못했다. 커널 문서 기능 목록에 동적 inode 할당이 올라 있다는 사실만 확인했고, 그 숫자를 어떻게 읽어야 하는지는 이 글에서 다루지 않았다
  • 컨테이너와 클라우드 절은 전부 미실행이다. 오버레이 동작, 정리 명령의 출력, 디스크 확장 절차 중 이 환경에서 돌린 것은 하나도 없다. 명령의 순서와 근거만 적었다

참고 자료

  • mke2fs(8) - man7.org - 예약 블록 기본값이 5퍼센트라는 것, 그리고 -i 의 bytes-per-inode 비율은 파일시스템 생성 후 바꿀 수 없다는 경고
  • tune2fs(8) - man7.org - -m 옵션 설명. 블록을 예약하는 두 가지 이유가 단편화 회피와 비특권 프로세스가 막힌 뒤에도 시스템 데몬이 계속 동작하게 하는 것이라고 적혀 있다
  • mkfs.xfs(8) - man7.org - maxpct 의 뜻과 크기별 기본값(1TB 미만 25%, 50TB 미만 5%, 그 이상 1%), 그리고 이 값을 xfs_growfs 로 바꿀 수 있다는 설명
  • xfs_growfs(8) - man7.org - -m 으로 inode 로 할당 가능한 최대 비율을 새로 지정한다는 옵션 설명
  • lsof(8) - man7.org - +L 뒤에 숫자를 주면 링크 수가 그보다 작은 파일만 나열하며, +L1 형태는 이름이 지워진 채 열려 있는 파일을 고른다는 설명
  • resize2fs(8) - man7.org - 이 프로그램은 파티션의 크기를 조작하지 않는다는 문장. 디스크를 늘린 뒤 파티션과 파일시스템을 따로 확장해야 하는 근거
  • BTRFS - The Linux Kernel documentation - 기능 목록에 동적 inode 할당이 포함돼 있다는 것
