계기 — Git 3.0 계획과 SHA-256 기본 전환을 둘러싼 논쟁

버전 관리 도구의 핵심은 변경 이력의 불변성을 유지하고 필요한 시점의 코드를 정확히 재현하는 데 있다. Git은 2005년 최초 설계 이후 20년 넘게 객체의 고유 식별자로 160비트 암호학적 해시 함수인 SHA-1을 채택해 왔다. 그러나 학계에서 SHA-1의 충돌 취약점 연구가 누적되고 이론적 공격 실증이 이어지면서, Git 프로젝트 내부에서는 차세대 해시 함수로의 전환 작업이 장기간 논의되어 왔다. Git 공식 문서인 BreakingChanges.adoc에 따르면 다가올 메이저 릴리스인 Git 3.0의 주요 파괴적 변경 사항 중 하나로 신규 저장소의 기본 객체 포맷(Object Format)을 기존 SHA-1에서 SHA-256으로 전환하는 계획이 명시되어 있다.

이러한 변화에 대해 개발자 생태계 전반에서는 기대와 우려가 교차하고 있다. 최근 GitHub의 공동 창업자이자 GitButler를 이끌고 있는 Scott Chacon은 기고문을 통해 Git 3.0에서 신규 저장소의 기본값을 SHA-256으로 강제 전환하는 정책이 실질적인 보안 이득에 비해 개발 생태계 전체에 지워지는 비용이 지나치게 크다고 주장하며 논쟁을 촉발했다. 저자의 논점은 단순한 변화 거부가 아니라, 저장소 내부의 객체를 찾는 「내용 주소 지정(Content Addressing)」 해시와 코드 작성자의 출처를 보증하는 「신뢰(Trust)」 메커니즘을 혼동함으로써 불필요한 전이 고통을 자초하고 있다는 지적에 기반한다.

이 글은 Git 3.0 계획에 담긴 해시 전환의 배경을 짚고, 암호학적 관점에서 제기된 공격 벡터의 실효성과 한계를 점검한다. 아울러 기본 포맷 변경 시 발생하는 저장소 간 단절, 서브모듈의 호환성 파손, 40자 16진수 문자열을 가정한 수많은 개발 도구의 오작동 등 현실적인 전이 비용을 목록화한다. 또한 저자가 제안한 커밋 서명 기반 독립 트리 검증 대안의 기술적 구조와 공식 문서상으로 확인 가능한 현황을 객관적으로 비교한다.

Git의 무결성 모델 — 내용 주소 지정(Content Addressable)과 SHA-1의 실제 역할

Git의 내부 동작을 이해하려면 Git이 단순한 파일 추적기가 아니라 「내용 주소 지정 데이터베이스(Content Addressable Key-Value Store)」라는 점을 먼저 살펴야 한다. Git에 저장되는 모든 데이터(파일 내용인 블롭, 디렉터리 구조인 트리, 메타데이터와 히스토리를 잇는 커밋, 태그)는 저장소에 기록될 때 고유한 암호학적 해시 값이 계산되어 해당 객체의 키(Key)로 사용된다. 저장되는 내용 자체가 키를 결정하기 때문에, 완전히 동일한 내용을 갖는 파일은 저장소 내에 중복 저장되지 않고 단 하나의 객체로 참조된다.

이 구조에서 데이터의 무결성은 머클 트리(Merkle Tree) 구조를 통해 보장된다. 커밋 객체는 루트 트리 객체의 해시와 부모 커밋의 해시를 직접 기록한다. 따라서 저장소 과거의 파일 한 글자, 혹은 트리 구조의 작은 변경 하나라도 발생하면 그 객체의 해시가 바뀌고, 연쇄적으로 상위 트리와 이후의 모든 커밋 해시가 완전히 달라진다. 최신 커밋(HEAD)의 해시 하나를 확보하는 것만으로 그 이전까지 누적된 수백만 개의 파일과 커밋 이력 전체의 변경 유무를 수학적으로 확인할 수 있게 된다.

Linus Torvalds가 2005년 Git을 개발할 때 SHA-1을 선택한 주된 이유는 당시 기준에서 충분히 빠르면서도 충돌 가능성이 현실적으로 배제될 수 있었기 때문이다. 이 모델에서 SHA-1 해시가 수행하는 본질적인 역할은 다음과 같다.

  • 객체 식별 및 압축 중복 제거: 저장소 내부 객체를 40자 16진수 키로 빠르게 색인하고 동일 객체의 중복 기록을 방지한다.
  • 우연한 데이터 손상 탐지: 디스크 오류, 메모리 결함, 네트워크 전송 중 발생할 수 있는 비트 반전(Bit Rot)을 완벽하게 검출한다.
  • 히스토리 불변성 사슬 유지: 부모 커밋 해시의 체이닝을 통해 과거 이력이 사후에 임의로 변조되는 것을 구조적으로 방지한다.
  • 로컬 작업 디렉터리의 빠른 상태 비교: 인덱스(Index)에 기록된 해시와 작업 파일의 해시를 비교하여 변경 여부를 고속으로 판단한다.

수학적으로 160비트 출력 공간을 갖는 SHA-1에서 서로 다른 두 파일이 우연히 동일한 해시를 가질 확률은 생일 역설(Birthday Paradox)을 고려하더라도 극도로 희박하다. 단일 프로젝트 내에 약 1.4 × 1024개(1.4 셉틸리온)에 달하는 무작위 파일이 존재해야 비로소 50%의 우연 충돌 확률이 형성된다. 지금까지 전 세계에 생성된 수십억 개의 Git 저장소에서 우연에 의한 자연 충돌 사례는 단 한 건도 보고되지 않았다.

암호학적 파망의 실제 범위 — 충돌 공격(Collision)과 제2역상(Second-Preimage)의 차이

SHA-1이 보안 업계에서 사용 중단 권고를 받게 된 계기는 2017년 CWI 암스테르담과 구글 연구진이 발표한 SHAttered 공격, 그리고 2020년 발표된 SHA-1 is a Shambles 공격 등 의도적 충돌 실증 논문들이다. 암호학에서 해시 함수가 「깨졌다(Broken)」고 표현할 때의 의미는 일상적인 의미의 완전한 무력화와 구별되어야 한다. 여기서 깨졌다는 것은 특정 수학적 취약점을 활용하여 천문학적인 전수 조사를 거치지 않고도, 대규모 GPU 연산 자원과 수만 달러 수준의 비용을 투입해 「의도적으로 같은 해시를 갖는 서로 다른 두 입력값」을 만들어낼 수 있다는 뜻이다.

여기서 핵심적인 기술적 구분이 요구된다. 해시 함수에 대한 공격은 크게 「충돌 공격(Collision Attack)」과 「제2역상 공격(Second-Preimage Attack)」으로 나뉜다.

  • 충돌 공격(Collision Attack): 공격자가 사전에 특수하게 설계된 정상 파일 A와 악성 파일 B를 동시에 계산하여 두 파일이 동일한 해시 값을 갖도록 생성하는 방식이다. 공격자는 자신이 통제하는 두 파일을 모두 알고 있는 상태에서 공격을 개시한다.
  • 제2역상 공격(Second-Preimage Attack): 이미 시스템이나 오픈소스 저장소에 배포되어 널리 쓰이고 있는 기존 파일 X가 주어졌을 때, 공격자가 사후에 X와 정확히 동일한 해시를 갖는 악성 대체 파일 Y를 찾아내는 공격이다.
  • 공격 실현 가능성의 극단적 격차: 충돌 공격은 자유도가 양쪽 파일 모두에 존재하므로 연산 복잡도가 상대적으로 낮아 SHA-1에서 실증되었다. 반면 제2역상 공격은 고정된 출력값을 맞춰야 하므로 복잡도가 상상을 초월한다.
  • 기존 해시 함수의 저항력: 암호학적으로 완전히 파망된 것으로 간주되는 MD5조차 제2역상 공격에 대해서는 실질적으로 면역에 가깝다. 전 세계의 약 30억 개 GPU가 모두 RTX 5090으로 교체되어 초당 2.2 × 1011회의 MD5 연산에만 매달린다고 가정해도 기대 소요 시간은 우주의 나이에 필적하는 약 160억 년에 달한다.

따라서 Git 저장소에 SHA-1을 사용하는 환경에서 공격자가 기존의 리눅스 커널 소스 코드나 특정 라이브러리의 커밋을 있는 그대로 두고 동일한 해시의 악성 코드를 끼워 넣는 제2역상 공격은 불가능하다. 오직 공격자가 초기부터 충돌 쌍을 직접 계산하여 정상 파일인 것처럼 위장해 기여한 뒤, 사후에 악성 파일로 바꿔치기하는 충돌 공격만이 이론적 위협으로 성립한다.

무결성 해시와 출처 신뢰의 분리 — 실제 공급망 공격이 일어나는 경로

Scott Chacon의 기고문에서 가장 강력하게 제기된 통찰은 「내용 무결성(Integrity)」과 「코드의 출처에 대한 신뢰(Trust)」를 분리해서 바라보아야 한다는 점이다. Git 창시자인 Linus Torvalds 역시 2005년 커널 메일링 리스트에서 SHA-1 자체를 보안 메커니즘으로 간주해서는 안 되며, 진정한 보안은 분산 배포와 출처에 있다고 강조한 바 있다. 개발자가 git pull을 수행할 때 신뢰하는 대상은 커밋 객체의 해시 문자열 자체가 아니라, 해당 원격 저장소를 호스팅하는 서버의 인증 체계와 유지보수자의 권한 관리다.

현실 세계의 소프트웨어 공급망 보안 사고를 분석해 보면, 공격자가 수만 달러의 비용과 수백 대의 GPU를 임대하여 SHA-1 충돌 쌍을 계산한 뒤 바이너리 파일 뒤에 널 바이트와 노이즈를 덧붙여 악성 객체를 은밀히 교체하는 시나리오는 극히 드물거나 전무하다. 대신 실제 공급망 침해는 훨씬 간단하고 비용이 들지 않는 사회공학적 기법을 통해 발생한다.

  • 유지보수자 계정 및 토큰 탈취: 오픈소스 패키지 관리소(npm, PyPI 등)나 저장소 관리자의 계정을 탈취하여 악성 코드를 정식 버전으로 배포하는 경로다.
  • 기여권 확보 후 악성 변경 병합: 장기간 활동이 뜸한 프로젝트의 유지보수 권한을 넘겨받거나 협박·매수하여 정상적인 커밋으로 악성 로직을 밀어 넣는 방식이다.
  • 패키지 의존성 설정 조작: package.json이나 의존성 명세에 오타가 포함된 유사 패키지(Typosquatting)를 등록하여 다운로드를 유도하는 경로다.
  • 호스팅 권한 기반 우회: 저장소 쓰기 권한이 공격자에게 넘어간다면, 객체 해시가 SHA-1이든 SHA-256이든 상관없이 메인 브랜치에 악성 코드를 직접 푸시할 수 있다.

신뢰할 수 있는 원격 저장소에서 코드를 가져오는 대다수의 일반 개발 환경에서는 객체 해시의 암호학적 강도가 SHA-1인지 SHA-256인지가 실제 보안 침해 여부를 결정하지 않는다. 저장소 쓰기 권한이 보호되지 않는다면 해시 알고리즘이 아무리 강력해도 공급망 침해를 막을 수 없으며, 반대로 접근 통제와 서명 검증이 확립되어 있다면 SHA-1 해시 충돌 공격 역시 실효성을 갖기 어렵다.

생태계 전이 비용 — 상호 운용 단절과 서브모듈·라이브러리·도구 파손

Git 프로젝트가 Git 3.0에서 기본 객체 형식을 SHA-256으로 변경하려는 취지는 장기적 관점에서 암호학적 건전성을 확보하려는 목적에 있다. 그러나 기본값이 전환되는 순간, 전체 소프트웨어 산업은 막대한 호환성 단절과 전이 비용에 직면하게 된다. 저장소의 해시 함수를 바꾼다는 것은 단순한 설정 플래그 변경이 아니라, Git 내부의 기본 주소 체계 전체를 교체하는 일이기 때문이다.

저자가 지적한 주요 전이 비용과 생태계 파손 요인은 다음과 같다.

  • 저장소 간 상호 운용성 완전 단절: SHA-1 저장소와 SHA-256 저장소는 객체 형식이 달라 직접적인 패치 교환, fetch, push가 불가능하다. 두 저장소는 완전히 분리된 다른 세계로 취급된다.
  • 서브모듈의 이중 관리 부담: 서브모듈을 참조하는 상위 저장소와 하위 라이브러리 저장소의 해시 포맷이 다르면 정상적인 서브모듈 운용이 불가능하다. 오픈소스 라이브러리는 기존 SHA-1 기반 상위 프로젝트와 신규 SHA-256 프로젝트를 동시에 지원하기 위해 두 가지 형태의 저장소를 각각 유지보수해야 할 수 있다.
  • 40자 고정 해시를 전제한 도구 생태계 파손: 지난 20년간 구축된 수많은 CI/CD 파이프라인, 정적 분석 도구, 배포 스크립트, 정규식 파서가 Git 해시를 40자 16진수 문자열로 가정하고 작성되었다. SHA-256의 64자 해시는 이러한 기존 자동화 스크립트 전반에서 파싱 에러를 유발한다.
  • 서드파티 Git 라이브러리의 미흡한 지원: Git 코어 바이너리는 GPL 라이선스로 인해 직접 링크가 불가능하여, 수많은 언어 생태계(libgit2, go-git, git2go, dulwich 등)에서 Git 프로토콜을 자체 재구현해 사용해 왔다. 이들 서드파티 라이브러리의 상당수는 여전히 SHA-256 지원이 불완전하거나 결여되어 있다.
  • 기존 저장소 변환 시 히스토리 단절: 기존 SHA-1 저장소를 SHA-256으로 변환하려면 저장소 내부의 모든 객체를 다시 해싱해야 하므로 모든 커밋 ID가 변경된다. 이 과정에서 기존의 GPG/SSH 커밋 서명이 전부 깨지며, 이슈 트래커, 코드 리뷰 시스템, 문서에 기록된 기존 커밋 링크가 일제히 무효화된다.
  • 호스팅 인프라의 부담과 지연: GitHub, GitLab 등 대규모 코드 호스팅 플랫폼은 저장소 생성 시점부터 해시 포맷을 엄격히 구분해야 하며, 두 포맷 간의 미러링이나 변환 레이어를 제공할 경우 막대한 추가 인프라 부하를 감당해야 한다.

공식 지원 현황과 로컬 환경 점검 — 읽기 전용으로 확인하는 객체 포맷

Git 프로젝트는 이미 버전 2.29 무렵부터 실험적으로 SHA-256 객체 포맷을 지원해 왔다. 현재 설치된 Git 환경에서 사용자가 SHA-256 저장소의 동작을 시험하거나 기존 저장소의 포맷을 확인하는 것은 기존 작업 환경을 파괴하지 않고도 안전하게 수행할 수 있다. 이때 운영 중인 저장소의 히스토리를 변경하거나 원격 저장소로 강제 푸시하는 명령은 절대 사용하지 않아야 하며, 격리된 임시 경로에서 순수한 생성 및 조회 명령만 사용해야 한다.

공식 매뉴얼(git-init, git-rev-parse)에 명시된 비파괴적 명령 체계는 다음과 같다.

# 임시 디렉터리에 SHA-256 형식의 신규 저장소 초기화 (비파괴 시험)
                    git init --object-format=sha256 /tmp/test-sha256-repo
                    
                    # 저장소 내부로 이동 후 현재 객체 포맷 확인 (읽기 전용)
                    cd /tmp/test-sha256-repo
                    git rev-parse --show-object-format
                    
                    # 기존 운영 저장소에서 객체 포맷 조회 (읽기 전용, 기본값은 sha1)
                    git rev-parse --show-object-format

위 명령에서 --show-object-format은 저장소가 초기화될 때 설정된 해시 알고리즘(sha1 또는 sha256)을 단일 문자열로 출력한다. 점검 시 유의할 점은 다음과 같다.

  • 저장소 초기화 후 포맷 불변성: 저장소가 한 번 특정 포맷으로 초기화되면 설정 파일의 옵션을 단순히 수정하는 것으로 포맷을 바꿀 수 없다.
  • 호스팅 원격지 검증: 로컬에서 SHA-256 저장소를 생성하더라도 원격 저장소가 해당 포맷을 지원하지 않으면 푸시 단계에서 거부 에러가 발생한다.
  • 도구 호환성 사전 진단: 사내에서 사용하는 배포 파이프라인이나 스크립트가 있다면, 생성된 임시 저장소에서 커밋을 하나 생성한 뒤 파이프라인의 파서가 64자 해시를 정상 처리하는지 안전하게 모의 시험할 수 있다.
  • 시스템 전역 기본값 점검: 향후 Git 3.0 배포 시 시스템 단위 설정(init.defaultObjectFormat)을 통해 기존 SHA-1 동작을 기본으로 유지하도록 강제할 수 있는지 여부를 정책적으로 검토할 수 있다.

대안으로 제안된 서명 기반 독립 트리 검증 — 원리와 한계

Scott Chacon이 생태계 단절을 피하기 위한 대안으로 제시한 구상은 「커밋 서명 시점에 작업 트리 전체의 체크섬을 독립적으로 계산하여 서명 헤더에 추가하는 방식」이다. 이 접근법은 저장소의 내부 객체 저장 모델은 40자 SHA-1 체계로 그대로 유지함으로써 전 세계의 수많은 개발 도구, 서브모듈, 라이브러리 호환성을 100% 보존한다. 대신 신뢰가 필수적으로 요구되는 릴리스 태그나 중요 커밋에 대해서만 강력한 암호학적 해시(SHA-256, BLAKE3, SHA-512 등)를 병행 적용하는 구조다.

이 아이디어는 완전히 새로운 개념이 아니다. 2015년 Colin Walters가 제안한 git-evtag가 거의 동일한 메커니즘을 사용했다. git-evtag는 커밋, 트리, 모든 블롭을 재귀적으로 순회하여 Git-EVTag-v0-SHA512 체크섬을 생성한 뒤 태그에 포함시켜 서명하는 도구다. Chacon은 이를 확장하여 Rust 기반의 개념 증명 도구(tree-sha256)를 구현하고 극단적인 대규모 저장소에서 체크섬 생성 소요 시간을 실측했다.

# Scott Chacon의 tree-sha256 개념 증명 실측 성능 (M5 Mac 멀티스레드)
                    - Chromium 저장소 (모든 서브모듈 포함 35GB, 210만 파일): 약 5초
                    - Linux 커널 저장소 (전체 트리 1.5GB): 약 257ms (0.257초)
                    - Git 프로젝트 자체 저장소: 약 17ms (0.017초)

이 대안이 갖는 장점과 구조적 한계를 비교 정리하면 다음과 같다.

  • 생태계 연속성 유지: 저장소 포맷 자체는 SHA-1으로 유지되므로 기존 40자 기반 도구, CI 스크립트, 이슈 트래커 링크가 전혀 파손되지 않는다.
  • 해시 민첩성(Crypto Agility) 확보: 훗날 SHA-256이 양자 컴퓨터 등으로 약화되더라도, 저장소 전체를 다시 이전할 필요 없이 서명 헤더에 새 해시(예: BLAKE3, 포스트 퀀텀 서명)를 추가하기만 하면 된다.
  • 이중 무결성 보증: 검증 시점에는 SHA-1과 독립 트리 해시 두 가지가 모두 일치해야 하므로, 단일 알고리즘 전환보다 기술적으로 더 높은 수준의 충돌 저항성을 갖는다.
  • 구조적 한계 — 모든 커밋에 대한 자동 상속 부재: 머클 트리의 상향 전파 특성과 달리, 독립 트리 서명은 명시적으로 서명된 특정 커밋이나 태그에만 유효하며 과거의 모든 중간 커밋까지 자동으로 보호하지는 못한다.

확인하지 못한 것

  • Git 3.0 공식 릴리스의 구체적인 확정 출시 일자. 공식 BreakingChanges 문서에는 계획 사항만 열거되어 있으며 배포 시점은 명시되지 않았다.
  • 주요 클라우드 Git 호스팅 플랫폼(GitHub, GitLab, Bitbucket 등)의 SHA-256 정식 지원(GA) 세부 일정 및 과금 정책 영향.
  • Git 코어 유지보수 팀이 Scott Chacon의 독립 트리 서명 제안을 공식 코어로 채택할 의향이 있는지에 관한 메일링 리스트의 최근 합의 여부.
  • 수천만 개 이상의 객체를 보유한 초대형 모노레포에서 SHA-256 전환 시 발생할 수 있는 메모리 점유율 및 압축 팩파일(packfile) 용량 변화의 실측치.
  • libgit2, go-git 등 주요 오픈소스 재구현 라이브러리들의 버전별 SHA-256 완전 지원 도달 시점.
