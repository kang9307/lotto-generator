Writing Projects Where Meaning Shows - Why Data Modeling Matters More in the AI Era

Code got cheap, but deciding what to build and why is still on us - why domain modeling is becoming the new core skill

Jul 7, 2026 Dev & Infra

Intro: Code Got Cheap - So Why Do So Many Projects Still Go Sideways

As of July 2026, the cost of producing a line of code has fallen by an order of magnitude compared to just a couple of years ago. Agentic coding tools like Claude Code and Codex hold a repository's full context, edit multiple files at once, run tests, and retry on their own when something fails. And yet something odd is happening. Code ships faster, but building genuinely good software has not gotten noticeably easier. If anything, more teams report the experience of trying to bolt on one more feature a few months in, only to watch the whole codebase wobble.

This piece starts from a short essay on hada by the developer behind oborona.zip, "Writing Projects Where Meaning Shows". The author, recounting the experience of extending a repeating-alarm feature in a minimalist to-do app called todox, leaves a brief observation: AI often struggles with the judgment calls involved in building a data model. This piece takes that single observation as a seed and reworks it through my own analytical lens, rather than simply restating the original essay or the hada thread. It asks why domain modeling becomes more valuable, not less, as code generation gets cheaper - and how that value shows up concretely in schemas, types, and naming.

1. What AI Is Good At, What It Isn't - Automating the How, Leaving the What and Why

1.1 Where AI Is Clearly Strong

What coding agents do well today is narrowly specific: generating boilerplate, repeating familiar patterns, standard refactors, drafting test code. These tasks are highly repetitive and low in ambiguity, which lines up precisely with what a language model does best - plausibly stitching together patterns it has seen before.

1.2 Where AI Still Wobbles

Architectural trade-offs are a different matter: whether to prioritize latency or consistency, how to trade velocity against stability. A model can lay out the options, but it cannot make the final call in your organization's specific context and be accountable for it. That decision remains, in the end, a human judgment.

1.3 From Typing Speed to Judgment Speed

Put the two together and the conclusion is singular: AI replaces tasks, not judgment. It has taken over a large share of the how, but what to build and why it should be built that way still belong to people. The trouble is that these two layers rarely stay visibly separated in the code itself. Data modeling is precisely the work of making that separation visible.

2. What the Todox Story Shows - Between 4,000 Lines and 2,000

The app in oborona's essay, todox, is a minimalist to-do app built on D-Bus notifications. It originally expressed recurring schedules with a single boolean, does_repeat. The moment a real request like "repeat this for just two weeks" arrived, that simple boolean immediately showed its limits. Capturing repeat intervals, end conditions, and day-of-week rules meant repeatedly growing the core C struct, and each change rippled up through every layer above it.

Instead of forcing the core to keep growing, the author separated concerns with a standalone Perl GUI wrapper. Vague, abstract user requests ("just two weeks", "every Tuesday") are received and translated by the Perl script into the explicit, individual alarms that todox's C core actually understands. The core only needs to know a simple state; the harder job of interpreting intent is pushed into its own layer.

What stands out is a brief comparison the author leaves behind. Handing the whole thing to an AI copilot and taking a nap could still produce a working app - but the version he modeled by hand himself came out to 1,193 lines of C plus 946 lines of Perl, in place of a roughly 4,000-line Qt app. He sums it up in a short line: "if the purpose is simple, the model should be simple too" (oborona.zip, paraphrased under 30 words). What I take from this is not the line count itself but the placement of the boundary. Once you settle the question of where the core logic ends and intent-interpretation begins, the code explains its own shape. That is what "meaning shows" actually looks like.

3. Why AI Can't Produce a Good Model on Its Own

A large language model works by predicting the most plausible next token. It does not think, and it does not hold the entire system in mind. What it does instead is amplify the quality of the instruction it is given. A vague instruction gets back a structure that looks plausible but is arbitrary. This is exactly the point that 2026's growing body of writing on AI-assisted domain-driven design keeps returning to: the root problem is that nobody designed the system before telling an agent to "just build it."

This lines up precisely with oborona's own observation, paraphrased: AI often struggles with the judgment calls that go into building a data model. My own read on why this is structural, not incidental, is this. Domain modeling is, by definition, a teleological act - drawing a boundary today in anticipation of a requirement that has not yet arrived. Questions like "why should this concept exist as its own thing" or "why should this value be this particular type" are not answered by statistical patterns in past data. They can only be answered by someone who knows the goals and constraints specific to that organization, that product, and those users.

4. What a Project Where Meaning Shows Looks Like - Language, Boundaries, Invariants

Domain-driven design (DDD) offers a vocabulary that has grappled with this problem for a long time. Three concepts matter most here. First, ubiquitous language: the discipline of having business stakeholders and developers use the same word for the same concept. Second, bounded context: explicitly drawing the scope within which a single model is valid. Third, invariant: a rule enforced in code that says "this state must never hold."

Translated into this vocabulary, "meaning shows" means a state where someone - or an AI agent - seeing the code for the first time can infer much of why it is shaped that way just from names, types, and folder structure. The functional-programming principle "make illegal states unrepresentable" pushes this all the way down to the type system. Instead of layering domain rules on top of raw primitives (strings, integers, booleans), you build a dedicated type that simply fails to compile if the rule is violated. The type itself becomes the verifier, and even when documentation goes stale, the code does not lie.

Interestingly, the bounded context finds a new use in the age of AI agents. Constraining each agent to operate within a single bounded context both splits the system into independent units and naturally sizes the work handed to that agent. Drawing the boundary first turns out to be half of good prompt design.

5. A Good Model Is Good Context - Context Engineering and Domain Modeling

Context engineering, much discussed lately, refers to giving an AI the right information in the right format to complete a task. What's interesting is where the research in this space keeps landing: the scaffolding that structures this information is, in the end, a domain model. A representative approach is schema-based representation - expressing the environment as an attributed entity-relation structure. When entities, attributes, and relations are explicitly typed, the instance data an AI references conforms to that same schema.

The practical takeaway I draw from this research is that a schema, type system, or architecture-decision record defined once and well provides far stronger, more durable context than any single improvised prompt sentence. A prompt evaporates once the conversation ends; types and schemas persist in the codebase and enforce the same rules in the next session too. Much of what gets called context engineering is, in practice, another name for domain modeling.

6. The Bill for Fuzzy Design - What Vibe-Coding Technical Debt Actually Looks Like

Skipping the modeling step doesn't just create an abstract worry - it shows up in numbers. Coverage in 2026 reports technical debt rising 30-41% and code duplication rising 48% after teams adopt AI coding tools, while refactoring activity drops 60%. The nature of that debt is the real problem. Code appears to work fine, until the moment someone tries to add a new feature and discovers that three other features were already implicitly depending on this exact behavior. That dependency was never written down anywhere - it only lived in the team's collective memory.

This is often described as code that "works, but nobody knows why." In practice, teams tend to hit a first reckoning around the 90-day mark. Opening a function to fix one small bug reveals it quietly handling four unrelated concerns, with no comments and no commit context left behind. My own reading is that the substance of this debt isn't the volume of code - it's the implicit assumption that was never written down. Had modeling been done, that assumption would have been carved into the code as a type or an invariant. Without it, the assumption survives only in someone's memory, and evaporates the moment that person leaves the team.

7. Practical Application - Schemas, Types, Naming

7.1 Represent the Domain With Types

Guard against primitive obsession - piling domain rules onto raw strings and integers. Instead of "an email string" or "an amount as a non-negative integer," build a dedicated value type that guarantees its own validity. Enforce validation at construction time, and an invalid value can no longer exist anywhere downstream in the code.

7.2 Naming Is Design

Carry the domain's ubiquitous language directly into variable, function, and class names. A vague name gets a vague guess from AI too. Conversely, when a name matches the business term exactly, the name itself becomes context - no separate explanation required.

7.3 Draw the Boundary First

Before handing a large task to an AI agent, split it along bounded-context lines first. A declaration like "this module knows only up to here" doubles as a well-sized unit of work for an agent. Hand over a task with fuzzy boundaries wholesale, and the agent will produce pieces that look plausible individually but don't fit together.

7.4 Spec First, Code Second

Rather than writing code first and documenting it afterward, try a spec-driven flow: document the spec and invariants first, then let AI implement against them. Well-structured artifacts - domain stories, a glossary, state diagrams - are themselves the best prompt you can give an AI.

8. The Obvious Objection - Why Not Just Let AI Do the Modeling Too

Research on AI-assisted domain design reports that candidate bounded contexts can be automatically extracted from existing code, logs, and API call patterns. That's a useful tool, but its limits are clear. What this approach extracts is observed coupling, not a judgment about why a concept should be separated for business reasons. A concept already tangled up in old code just gets that old structure confirmed back to it; it cannot redraw a boundary to fit a requirement that doesn't exist yet. My conclusion: you cannot outsource the judgment, but you can accelerate it. Let AI surface several candidate designs quickly, and let a person pick the one that fits the organization's purpose and own that choice. Reverse that order, and you're back to fuzzy design.

9. Conclusion - Three Things You Can Apply Today

The cost of producing code has genuinely fallen. But the cost of deciding what to build and how to carve it up has, if anything, risen. The more execution AI takes over, the more relative value there is in precisely defining where that execution should be headed. Here are three concrete things worth trying this week.

9.1 Write the Invariant Down Before You Write the Feature

Before touching code, write down in one sentence the rule that must never break - "this value is never negative," "this state can only be followed by that state." That sentence becomes the starting point for both your type design and your tests.

9.2 Promote Your Most-Broken Primitive Into a Type

Pick one spot where bugs keep recurring, and turn the string or number living there into a dedicated value type. It's a small change, but at that one spot, an invalid state simply can no longer be expressed in code.

9.3 Draw the Boundary Before You Delegate

Don't hand a large task to an agent whole - split it along bounded-context lines first, then delegate piece by piece.
