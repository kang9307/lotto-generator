引言: 发布文里最该先读的一句

智能体平台的发布大多长着同一张脸。有一个对话界面，接得上内部数据，能做自动化。这次从外表看也没什么不同。不同的是Cloudflare OS 后面挂了另一句话：服务端代码跑在全局出站网络被关闭的 Dynamic Worker 里。

这一行才是部署决策的起点，而不是产品导览。出站默认关闭既是安全说明，同时也意味着这个平台能接住的活是什么形状，已经被定死了。需要任意外部调用的代码在这里根本跑不起来。而用来补上这个缺口的东西，就叫 Gatekeeper。

Cloudflare 于 2026 年 8 月 5 日在 Agents Week 期间把 Cloudflare OS 开源。它是把公司内部一直在用的工具重做一遍后放出来的，许可证是 Apache-2.0，可以直接部署到自己的 Cloudflare 账户，用自己的 Access 策略和 AI Gateway 配置去跑。

本文不去逐条走功能表，而是落在一个问题上：把我的工作负载放到这里，理由成立吗？打包了什么、执行模型强制了什么、哪些活合适哪些活在结构上就进不来，以及为什么此刻投产还太早。

别和同一家公司方向相反的产品搞混。Cloudflare 也另外做了识别访问站点的 AI 智能体的技术。那一侧写在Precursor 登场 - Cloudflare 为何通过全会话行为识别 AI 智能体里。本文谈的是完全相反的轴，也就是运行智能体的那一侧运行时。同一家公司在同一周把两边都放出来，这件事本身就说明了这个市场眼下的状态。

1. Cloudflare OS 实际打包了哪三块

名字叫 OS 很容易读岔。它既不是新的操作系统，也不是新的基础设施层。把性质摸准，评估方向才不会跑偏。

1.1 是新产品还是重组

两者都不是。它是 Cloudflare 把内部一直在用的应用重做一遍后开源出来的东西。发布文的原话就是「今天我们把 Cloudflare OS 的新版本开源」，而第一版是同年五月向全体员工开放的内部工具。Cloudflare 表示，工程岗之外的人开始用它起草文档、做幻灯片、把重复性工作自动化。

  • 它是一个放进 Cloudflare 账户里的应用，而不是要另外订阅的一朵云
  • 所以开场问题从要不要换供应商，变成要不要把它放进你已经有的账户里
  • 如果已经在用 Workers 和 Access，评估成本明显更低；如果没有，开账户到设计 Access 策略全都是前置工作
  • 有内部落地记录这一点作为证据是有分量的。这是把数千人每天在用的东西重做一遍的产物，不是为发布攒出来的演示

1.2 拆成三块来看

发布把它描述成三个部分的组合。这三块不是各自独立有价值，而是按前一块支撑后一块的顺序堆起来的。

  • 智能体工作空间。预装了公司整理过的上下文与技能，还配了一个可以让智能体写代码并运行的隔离运行时
  • 安全与治理框架。用来安全触达内部数据与服务的那一层。起点是每一个智能体和应用一开始都没有任何访问权
  • 可被个人修改的应用平台。供人构建、共享并持续修改的应用的执行底座
  • 只有第一块，一碰内部数据就危险；只有第二块，无事可做。第三块要有前两块在，才能变成留得下产出的形态
  • 调研和提问不是把整份数据推进模型上下文窗口，而是用代码执行去检索与分析。这是刻意把上下文预算和数据规模解耦的设计
  • 生成出来的文档和表格会保持与原始数据源相连，源数据一变它们跟着更新。需要时也能导出成熟悉的格式

1.3 组件与各自承担的职责

这里只列发布中真正出现过的组件。表里没有的产品，就是这次发布没有提到的。

组件承担的职责这个选择带来的性质
Cloudflare Workers服务端代码运行的运行时底座V8 隔离启动快，但运行时上限原样变成应用上限
Dynamic Workers按需加载各应用的服务端代码每个应用单独的部署流程消失了
Durable Object Facets应用实例与状态的落脚处每个应用有自己的 SQLite，与运行时存储分离
Cloudflare Access进入工作空间时的认证与授权既有的公司身份策略原样沿用
AI Gateway模型路由、成本管控、用量归属所有推理都过同一个点，因此能加预算和限额
Gatekeeper按外部服务划分的权限中介 Worker凭据不会流向智能体
MCP 与 MCP Server Portals接入你已经在跑的 MCP 服务器既有的工具接入资产不必丢弃
Cap'n Web浏览器与服务端之间的 RPC智能体直接调用人做出来的那套接口

这张表要盯的是最后一列。每个组件都不是便利功能，而是各自制造出一条约束。而这些约束加起来，就是这个平台能承载的活的形状。

2. 智能体执行模型 - 一个应用就是一个 Worker

把执行模型压成一句话就是：智能体做出来的应用全都是 Worker。剩下的一切都从这句里长出来。

2.1 客户端代码与服务端代码一起生成

让工作空间做一个应用，智能体会写两部分。在浏览器里渲染界面的客户端代码，以及保存状态、实现行为的服务端代码。服务端这一侧按需作为 Dynamic Worker 加载，并以 Durable Object Facet 实例化。每个应用都有自己的 SQLite 数据库，与管理它的 Cloudflare OS 运行时分离。

浏览器
  └─ 客户端代码 (沙箱框架)
        │  Cap'n Web RPC
        ▼
Dynamic Worker  ← 按需加载
  └─ Durable Object Facet
        └─ 应用专属 SQLite  (与运行时存储分离)

出去的路只有 Gatekeeper 交过来的能力

从客户端调服务端的写法看起来不像远程调用。发布里给出的样子是这样。

const issues = await app.listIssues({
  status: "done",
});
  • 浏览器客户端通过 Cap'n Web 与服务端对话，那是 Cloudflare 开源的对象能力式 RPC
  • 于是人做的接口和智能体调的接口成了同一个东西，不必再单独造一套只给智能体用的 API
  • 数据库按应用分开，某个应用的表结构事故不会蔓延到别的应用
  • 反过来，应用之间要共享数据就必须显式地把那条路修出来。这是拿便利换隔离的设计

2.2 出站默认关闭意味着什么

这是最大程度决定这个平台性格的约束。服务端代码跑在全局出站网络被禁用的 Dynamic Worker 里，客户端代码跑在浏览器的沙箱框架里。两边都只能通过被显式提供的能力去触达外部系统。

  • 智能体生成的代码没法把数据发到任意地址。就算提示注入污染了生成的代码，外泄通道本身就不存在
  • 与此同时，想调什么外部 API 就调什么的代码在这里跑不了。需要的连接都得先做成 Gatekeeper
  • 于是引入成本的真面目露出来了。部署平台是小头，为每个要接的服务写一个 Gatekeeper 才是真正的工作量
  • 公开仓库的说明也写着仍在打磨外部服务配置的工具，并同时指出很多服务商是故意不把这件事做得容易的

2.3 跑代码的运行时到底管到哪

同一周 Cloudflare 还以早期预览的形式放出了 @cloudflare/computer 这个智能体运行时。它是一套按情况在隔离与容器之间挑选的开源运行时，轻量的活跑在 Dynamic Worker 隔离里，需要原生二进制或特定系统工具的活跑在容器里。状态通过一套由 SQLite 支撑的虚拟文件系统在两边同步。Cloudflare 表示目标是让需要容器的活占比低于全部工作的百分之十。

但别把这两个粘在一起读。Cloudflare OS 的发布文和 @cloudflare/computer 的发布文里，都没有说两者是同一个东西，或者其中一个是另一个的组件。这是同一周发出的两份彼此独立的公告。也就是说，不能按「容器反正会自己接上」这个假设去做设计。

3. Gatekeeper - 不交凭据只交权限的办法

既然把出站关上了，总得在某处开一扇门。那扇门叫 Gatekeeper。

3.1 凭据不会到智能体手里

Gatekeeper 是夹在 Cloudflare OS 与外部服务之间、按服务划分的 Worker。它处理 OAuth、保管凭据、执行策略，并记录读过什么。智能体生成的代码拿到的不是凭据，而是带类型的绑定。

const issues = await env.PROJECT.listIssues({
  teamId: "ENG",
  state: "open",
});
  • 发布明确指出把 API 密钥交给人和智能体是危险的。密钥缩不了范围，回收也不留痕迹
  • Gatekeeper 可以只授权到某一个仓库，也可以拆成允许读议题但读不到源码
  • 每一个智能体和应用都从没有任何访问权开始，需要什么资源就当场申请
  • 会在外部产生副作用的动作也全都过这一层。于是「谁做了什么」不是留在应用日志里，而是留在权限层的记录里

3.2 观测记录会限制共享

这里是与传统权限模型分歧最大的地方。Cloudflare OS 记录智能体观测到的每一个资源，而这些观测记录会一直跟着这个智能体和它的产出。当另一个人想打开这个工作空间、与智能体交互或查看它的产出时，Gatekeeper 会核验那个人对被观测资源的访问权。

  • 设计目标是共享一张仪表盘不能变成把里面那张原始表也一并共享出去的绕道
  • 读过敏感数据之后，向某些目标的写入也可能被挡住。读取历史会朝着收窄后续写权限的方向起作用
  • 这个性质与便利性正面冲突。产出共享出去但对方打不开，这是正常行为而不是缺陷，组织得先把这一点想明白
  • 没有数据分级体系的组织，一打开这一层就等于开始建分级体系。这更接近引入的前提而不是副作用

3.3 为什么光有 MCP 还不够

Cloudflare OS 可以通过 MCP Server Portals 接入组织已经在用的 MCP 服务器。但发布把为什么要在不替换 MCP 的前提下再叠一层写得很清楚：光靠 MCP 无法知道智能体观测到了哪些底层资源。

  • MCP 是暴露工具的协议。工具返回了什么、那份数据来自哪个源头，都在协议之外
  • 所以「谁可以看这份产出」这个问题在 MCP 这一层答不出来，观测记录必须另外攒
  • 如果已经在运营好几台 MCP 服务器，不必丢掉这份投入就是一个实实在在拉低引入成本的因素
  • 反之，一台 MCP 服务器都没有的组织，得先为每个要接的系统写好工具定义，才轮到打开这个平台

4. 与传统无服务器分道扬镳的两处

跑在 Workers 上，无服务器的性质原样继承下来。但有两处明显不同。

4.1 部署单元消失了

常规的无服务器要部署函数。改了代码就重跑流水线，产生版本，产生回滚目标。Cloudflare OS 的应用不走这一套，因为它们是在请求时刻作为 Dynamic Worker 加载的。

  • 于是非工程岗的人可以用 AI 直接改自己的应用，而不是提一张需求单。这正是发布着力强调的地方
  • 共享有两种方式。共享应用本身以便实时协作，或者共享蓝图让别人各自生成独立副本
  • 蓝图副本带着原始代码，但状态和所连接的资源是独立的。适合把别人的工具拿过来跑自己的数据
  • 作为交换也失去了东西。没有部署流水线意味着也没有地方挂代码评审和审批闸口。如果公司规章要求部署审批，这条性质就是第一个要谈的

4.2 状态贴在应用身上

一般的函数式无服务器以无状态为前提，把状态推给外部存储。这里反过来。每个应用都挂着 Durable Object Facet 和 SQLite，状态与执行住在同一个地方。

  • 做一个小型内部工具不必另外开数据库，起步成本大幅下降
  • 同时编辑是自然的。多名同事在同一个应用里并行作业，是设计时就假定的形态
  • 但规模一大，性质就翻过来了。状态绑在执行单元上，横向扩展的轴就被钉死在应用这一级
  • 确定性工作流也在同一条轴上。它支持按需触发、按计划执行，或者由外部事件触发

5. 数字上限已经替你定好的事

这是做部署决策时最该先看的地方。Cloudflare OS 的发布文里没有自己的上限数值。但既然应用全都是 Worker，Workers 的平台上限就原样变成应用的上限。

5.1 Workers 平台上限

项目FreePaid这个数值挡掉的东西
每请求 CPU 时间10ms最长 5 分钟 (默认 30 秒)长时间运算一次请求做不完
HTTP 请求墙钟时间客户端保持连接期间不设限瓶颈在 CPU 而不在等待
Cron、告警、队列消费者15 分钟异步批处理的天花板
单个隔离的内存128MBJavaScript 堆与 WebAssembly 分配合计。大体量状态放不进来
并发出站连接每请求 6 条扇出很宽的聚合会被串行化
子请求50/请求10,000 (最多 1000 万)Free 上多系统查询基本不可行
Worker 体积3MB 压缩10MB 压缩 / 64MB 原始沉重的依赖树整块塞不进去
环境变量64 个128 个 (各 5KB)把配置往变量里塞这条路的上限

5.2 这些上限实际砍掉的活

表怎么读很简单。从上往下拿自己的活去比，只要碰到一条，这个活就不该放这儿。

  • 长时间 GPU 训练与自托管大模型服务。计算资源的种类根本就不一样。推理是过 AI Gateway 出到外部模型，不是在这里跑
  • 把数 GB 数据装进内存的分析。128MB 上限正面挡住。要么切成流式，要么一开始就换个地方跑
  • 同时打几十个后端的扇出聚合。并发出站连接每请求 6 条，并行度就断在那条线上
  • 要跑几十分钟的单次批处理。Cron 一族卡在 15 分钟，把作业切开再串起来就成了必须的设计
  • 依赖原生二进制的工具链。在 V8 隔离里跑不了。如果这活需要容器，它就在这个平台的应用模型之外
  • 反过来，几百毫秒内就能收尾的查询与整理类作业能宽宽松松地通过上面每一条。而公司内部业务自动化里，相当大一部分确实就在这一档

6. 数据本地化 - 受监管工作负载的分水岭

既然是处理内部数据的平台，数据落在哪里就决定了能不能引入。应用状态进 Durable Object，而 Durable Object 的位置规则已经有文档。

6.1 管辖区与位置提示是两回事

  • 管辖区(jurisdiction) 是为合规而强制只在特定区域内运行与存储的机制，提供 eu、us、fedramp 三种
  • 位置提示(location hint) 是在不需要管辖强制时用来引导初始落位的值，可选 wnam、enam、sam、weur、eeur、apac、apac-ne、apac-se、oc、afr、me
  • 这两者不能混着用。提示是尽力而为而不是保证，文档明确写着不一定会在被提示的位置上实例化
  • Durable Object 一旦创建就不会迁到别的数据中心。只有第一次 get() 调用参与落位决定
  • 标识符会因为计费和调试的目的被记录到指定管辖区之外。如果在你的设计里标识符本身就是敏感信息，这一点要先审

6.2 有境内存储要求时要核的几件事

提供的管辖区名单里没有多少国家。所以如果背着境内数据必须留在境内的要求，得先把这条轴理清楚。

  • 不在管辖区名单里，和没有本地数据中心，是两回事。但没有作为强制机制提供出来这个事实照旧成立
  • 位置提示 apac-ne 只是往亚洲东北方向引导，不是国家级保证，不能当作合规依据
  • 推理请求会过 AI Gateway 出到外部模型提供方。提供方那一侧的数据处理位置要另立一项来审
  • Gatekeeper 留下的观测记录也是数据。读过什么的清单留了下来，既是审计资产，同时也是需要保留策略的对象

7. 成本究竟从哪里来

先把一件事说清楚：发布里没有 Cloudflare OS 自身的价格体系。它是开源并部署进自己账户的形态，所以成本不是软件使用费，而是那个账户里消耗的资源。

7.1 计费至少分三条轴

  • 计算与状态。Workers 的执行加上 Durable Objects 的存储与请求。应用数一多，Durable Object 数就跟着涨，这条轴也一起涨
  • 模型推理。所有过 AI Gateway 的推理请求。实际账单里通常是这条轴动得最厉害
  • 身份。入口由 Cloudflare Access 管控，所以用户规模决定这条轴
  • 还有一条在账单上看不见的第四轴：写和维护 Gatekeeper 的人力时间。每多接一个对象就多一段代码，而那段代码在权限层，不能随便交给谁去改

7.2 发布真正讲到的成本管控

虽然没有价目表，管控机制说得很清楚。所有推理调用都过 AI Gateway，因此组织可以挑选哪些模型可用，并能按人或按团队追踪支出、设定预算、施加速率限制。每一个请求都归属到发起它的人、团队或工作空间。

  • 归属做到请求粒度，意味着成本可以摊回到部门。在内部推行时，这条性质是政治规格而不是技术规格
  • 模型选择权在组织手上也是同一个逻辑。按作业性质钉好模型，就从结构上避免了昂贵模型贴到琐碎作业上
  • 不过预算超限时怎么办，是拒绝还是降到便宜的模型，发布里没有。这是要自己写进运营策略的项

8. 要不要把工作负载搬上去

这里是本文的终点，用两张表来收。

8.1 按作业性质看适配度

作业性质适配度决定性理由
查几个内部系统再汇总很合适权限能用 Gatekeeper 切开，执行也短
团队级小型内部工具很合适每个应用自带 SQLite，不必另行开通
只在少数节点需要人拍板的重复流程很合适确定性工作流靠计划与事件跑起来
一次性数据整理与报表生成比较合适产出与数据源保持相连并随之更新
数 GB 数据的内存分析不合适直接撞上单隔离 128MB 的上限
长时间 GPU 训练与自托管模型服务不合适计算资源的种类根本不同

规章要求部署审批的系统需要再议应用没有部署单元，审批点无处安放

8.3 把判断压成三个问题

  1. 这个活装得进 128MB 和 5 分钟 CPU 吗。装不进，后面的讨论就没意义
  2. 要接的外部系统有几个，每一个都有人来写 Gatekeeper 吗。这个数字才是真正的引入成本
  3. 产出共享被权限挡住这件事，组织能接受吗。不能接受就得把这个平台的核心机制关掉，关掉之后剩下的也没多少了

9. 为什么现在还不该投产

这是公开仓库的说明自己讲出来的内容。跳过这一段去评估，判断会整个走偏。

  • 说明写着 v2 已经相当能用但仍有不少毛糙之处，并把自己描述为处在密集开发状态。这不是投产就绪的宣告
  • 自托管部署方式标着即将推出。眼下能走的部署路径是用 Cloudflare 账户那条
  • 外部服务接入的配置工具也写着仍在打磨。要接的系统越多，这段未完成区间就越要自己去填
  • 许可证是 Apache-2.0。内部改造与再分发没有障碍，但许可证开放与可以投产是两个问题
  • 所以眼下值得做的收窄成三件：做一次试点部署，看 Access 与 AI Gateway 的配置能不能和公司规章咬合；亲手写一两个 Gatekeeper，摸清权限拆分的粒度；量一量自己真实的作业能不能装进上限里

10. 要引入的话先定下来的事

  • 先把数据分级体系建起来。基于观测记录的共享限制，没有分级就打不开。这是组织共识而不是平台配置
  • 指定 Gatekeeper 的负责人。这是权限层代码，不能谁都来改。它应当是唯一一条不经评审就不会上线的代码路径
  • 把模型白名单和预算超限时的行为写进文档。是拒绝还是降级到便宜模型，发布里没有，得组织自己定
  • 从第一天就设好应用退役策略。每个应用都挂着 Durable Object 和 SQLite，被丢下的应用会原样留成成本和数据
  • 定下观测记录的保留期限。它既是审计资产，本身也是敏感信息。别让一张表同时兼作运营数据和审计留存
  • 把共享蓝图和共享应用分开来培训。前者是状态分离的副本，后者是实时协作。分不清就会把数据搅在一起
  • 先解决与部署审批规章的冲突。没有部署单元这条性质没法留到以后再谈。要么改规章，要么收窄这个平台的适用范围
  • 确认退出通道。得有办法把各应用 SQLite 里攒下的数据导出去。开源这个事实并不自动保证可迁移性

11. 没能确认的部分

把没能拿到依据的项目集中列在一处。

  • Cloudflare OS 自身的价格。发布里没有价格信息，只能确认按账户资源消耗计费这个结构
  • 正式发布阶段的标注。发布说今天即可用，仓库说仍有不少毛糙之处。没能确认 beta 或 GA 这类正式阶段标注
  • Dynamic Workers 与 Durable Object Facets 的单独上限。本文的上限表依据 Workers 平台文档，这两项功能是否另有上限没能确认
  • 并发应用数与每工作空间的上限。发布和仓库说明里都没有数值
  • 内部部署规模的具体数字。只有跨各职能数千人每天在用这个说法，确切人数与应用数量没有公开
  • SLA 与支持体系。开源分发形态下故障响应的责任边界在哪里，没能确认
  • 模型提供方一侧的数据处理位置。过了 AI Gateway 之后在哪里处理，属于各提供方的合约事项，在这次发布范围之外
  • 与 R2、D1、Containers、Workers AI 的关系。这次发布文里这些产品没有作为组件出现，能否联动没能确认

12. 常见问题

Cloudflare OS 是新产品还是既有产品线的重组?

两者都不是。它是 Cloudflare 把内部一直在用的应用重做一遍后开源出来的东西。发布文的原话是「今天我们把 Cloudflare OS 的新版本开源」，而第一版是同年五月向全体员工开放的内部工具。所以并没有多出一层新的基础设施。真正打开的是一个跑在 Workers、Durable Objects、Access、AI Gateway 这些既有组件之上的应用，以及这个应用所需要的权限代持机制，名字叫 Gatekeeper。这也就改变了评估的第一个问题。不是要不要换一朵新的云，而是要不要把这个应用放进你已经有的 Cloudflare 账户里。

智能体做出来的应用怎么运行，状态又存在哪里?

一个应用就是一个 Worker。智能体会同时写两部分代码，一部分在浏览器里渲染界面，另一部分在服务端保存状态并实现行为。服务端按需作为 Dynamic Worker 加载，并以 Durable Object Facet 的形式实例化。每个应用都有自己的 SQLite 数据库，与管理它的 Cloudflare OS 运行时的存储相互分离。浏览器客户端与服务端之间通过 Cap'n Web 这套对象能力式 RPC 通信。这里最关键的性质是没有单独的部署单元。改一个应用不用走部署流程，所以非工程岗位的人不必再提需求单等排期，可以自己直接改自己的应用。

Gatekeeper 和直接发 API 密钥有什么不同?

不同在于凭据根本不会交到智能体手上。Gatekeeper 是夹在 Cloudflare OS 与外部服务之间的、按服务划分的 Worker，它处理 OAuth、保管凭据、执行策略，并记录读过什么。智能体生成的代码拿到的不是密钥，而是带类型的绑定。于是权限可以细到只给某一个仓库，或者只允许读议题而读不到源码。在这之上还叠了一层观测记录。智能体看过的资源会一直跟着这个智能体和它的产出，别人想打开这些产出时，Gatekeeper 会核验那个人对被观测资源的访问权。读过敏感数据之后，向某些目标的写入也可能因此被挡住。

哪些工作负载适合这个平台，哪些不适合?

适合的是短而分散的执行。跑几个内部系统查一遍再整理成结论、只在少数几个节点需要人拍板的重复流程、团队自用的小型内部工具，都在这一类里。不适合的分三种。第一种是长时间 GPU 训练或者自己托管大模型。第二种是大体量状态，因为 Workers 的隔离把 JavaScript 堆和 WebAssembly 分配加在一起限在 128MB，把大数据集整块塞进内存这条路从一开始就不通。第三种是需要任意出站调用的活，因为服务端代码跑在全局出站网络被关闭的 Dynamic Worker 里，要出去就必须把那条路径显式地作为能力交给它。

现在就能在公司里投产吗?

投产还早。公开仓库的说明本身就写着 v2 已经相当能用但仍有不少毛糙之处，并把自己描述为处在密集开发状态。自托管部署的工具也标着即将推出。许可证是 Apache-2.0，内部改造和再分发没有障碍，但许可证开放与可以投产是两回事。眼下值得投入的做法有三个。一，在自己的 Cloudflare 账户里做一次试点部署，看 Access 策略和 AI Gateway 配置能不能和公司规章咬合。二，亲手写一两个 Gatekeeper，摸清权限拆分的粒度。三，量一量自己的实际作业能不能装进 128MB 和 CPU 上限里。

结论: 今天带走的三件事

第一，这个平台的性格由约束定，不由功能表定。出站默认关闭，单隔离 128MB，就这两行，基本就把哪些活进得来、哪些进不来分完了。与其读发布文里花哨的部分，不如先拿这两行去比自己的活，快得多。

第二，引入成本不是部署平台，而是 Gatekeeper 的个数。部署一个账户就够，但每接一个外部系统都得写一个权限中介 Worker 并长期维护。而那段代码在权限层，不能谁都来碰。把要接的对象数一遍，项目的真实体量就出来了。

第三，基于观测记录的共享限制是组织决定而不是技术决定。只有能接受「共享出去对方却打不开是正常行为」，这个平台的核心才转得起来。接受不了就会把那套机制关掉，关掉之后剩下的不过是又多了一个内部聊天机器人。

最后一句。这次发布里能留得久的不是 Cloudflare OS 这个名字，而是这个方向：给智能体的是能力而不是凭据，并把它读过什么当作权限判断的输入。无论最后选哪个平台，做内部智能体设计时都会再次撞上这个方向。跟今天能不能用无关，这条设计原则本身现在就值得读一遍。
