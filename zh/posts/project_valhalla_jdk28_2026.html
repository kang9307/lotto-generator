Project Valhalla — 十年工作如何体现在JDK 28中

值类、堆扁平化和标量化解构Java对象开销 — JEP 401带来了什么，对开发者意味着什么

2026-06-22 开发/基础设施

引言：改变三十年来的根本假设

2026年6月基准，Java历史上持续时间最长的未完成项目终于进入主线。这就是Project Valhalla。2014年Brian Goetz提出的这个项目，历经12年，以JEP 401（Value Classes and Objects）预览形式进入JDK 28。代码约197,000行，设计迭代数十次——为何花了这么长时间，结果是什么，以及对Java开发者实质上带来什么，本文将客观分析。

首先明确文章范围。JDK 28是计划中的版本（基于2026年6月已公开的OpenJDK信息和报道），本文讨论的是预览特性而非确定的生产版本。引用的性能数字来自已报告的基准测试，实际工作负载的结果可能不同。

1. 为何花了十年 — Java的身份危机

Java自1995年诞生以来，建立在一个根本假设上：「所有对象都有身份（identity）」。身份意味着两个对象即使持有相同的值，只要堆地址不同，就是不同的存在。==运算符比较引用地址，synchronized锁定对象实例，System.identityHashCode()具有意义——这些都建立在这一假设之上。

身份带来了代价。每个Java对象都有12-16字节的对象头。持有x、y坐标的Point对象，除字段值8字节外，还需支付16字节的对象头。更严重的是间接引用。ArrayList<Point>不直接存储Point，而是存储指向散落在堆各处的Point对象的指针数组。CPU访问Point的x字段需经过：数组→指针→Point对象→字段，两次内存间接引用。缓存未命中不可避免，在数百万次以上的循环中这一代价不断累积。

Brian Goetz将此问题称为「Java的身份危机」。解决方案清晰：从不需要识别的小型数据类型中去除身份，JVM就能在无需指针的情况下直接放置数据。那为何花了十年？因为整个Java栈——JVM、编译器、语言规范、标准库——都是基于「所有对象有身份」而设计的。在守护数以百万计项目和数十年代码惯性的同时改变根基，不是简单的功能添加，而是范式级别的改造。

2. 值类（value class）是什么

Project Valhalla的口号从一开始就保持一致：「codes like a class, works like an int」——像类一样编写，像int一样运行。JEP 401正是这一目标的具体实现。

2.1 值类的声明

值类通过value关键字声明：

value class Point {
    int x;
    int y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

这个声明意味着两件事。第一，Point实例没有身份。第二，JVM获得权限，可以不用指针而直接内联放置该对象。代码结构与普通类相同，构造器、方法、接口实现均保持不变。但运行时表现从根本上不同。

value record同样受到支持。record本就用于表示不可变数据载体，值记录是概念上最自然的组合。

2.2 无身份带来的约束与优化

值类不允许普通类理所当然的操作：synchronized(point) {}是编译错误；System.identityHashCode(point)失去意义；引用比较==变为内容比较。这些约束同时也是优化的钥匙。没有身份，JVM可以自由复制、重新放置、分解实例而不改变语义。这是堆扁平化和标量化的前提。

3. 堆扁平化与标量化 — 性能从何而来

JEP 401的核心性能技术有两个。它们在不同层次运作，但指向同一方向：消除指针，让数据靠近计算。

3.1 堆扁平化（Heap Flattening）

传统Java中，Color[] colors = new Color[1_000_000]分配的数组持有百万个指针，每个指针指向散落在堆各处的Color对象。访问colors[i].r需要：数组基址→指针→Color对象头→r字段。反复访问时CPU缓存形同虚设。

当Color是值类时，数组不再存储百万指针，而是直接存储r、g、b值填充的连续内存块。colors[i].r通过数组基址的单个偏移即可访问。遍历整个数组变成CPU最喜欢的模式——顺序内存扫描。据报告，在某些场景中这一差异可使内存占用减少40-50%，迭代操作速度提升最多3倍。

3.2 标量化（Scalarization）

标量化是JIT编译器层面的优化。如果方法创建Point p = new Point(3, 4)且只使用p.x和p.y，JIT可以跳过堆分配，直接将x=3, y=4放入CPU寄存器。堆分配本身消失，GC追踪对象也减少。以整数运算的方式处理——这就是「标量」的含义。

有身份的普通对象无法标量化——某处可能持有其堆地址，移动或分解会产生可观察的语义差异。值类无身份，JVM可自由复制、重新放置、分解实例。这是十年设计迭代所解开的核心钥匙。

4. JDK 28实际反映了什么，什么还没有

基于2026年6月的公开OpenJDK信息和报道，明确区分JDK 28预览包含的内容和尚未包含的内容。

4.1 JDK 28预览包含的内容（基于已公布计划）

  • value class和value record声明语法（JEP 401）
  • 针对值类的堆扁平化和标量化JVM优化
  • Integer、Double、Long等现有原始类型包装类迁移为值类（预览范围）
  • 更廉价的装箱（cheaper boxing）——降低包装类装箱开销
  • 通过--enable-preview标志激活

4.2 JDK 28不包含的内容（未来工作）

  • null限制类型（非空引用）：如Point!这样不允许null的类型
  • 特化泛型（JEP 402）：List<int>无需装箱
  • 128位编码支持
  • 完全成熟的JEP 402

特化泛型缺席是最大的遗憾。List<int>目前仍需通过List<Integer>装箱。Brian Goetz说过「去除身份是第一道关卡，打通后特化泛型才成为可能」——这正是JEP 401被称为「第一道关卡」的原因。

5. 包装类迁移的陷阱

Integer成为值类听起来是好消息——Integer[]接近int[]的内存效率，装箱开销大幅降低。但存在重要的副作用。

对Integer实例使用synchronized的代码会抛出运行时异常。值类没有身份，无法作为监视器锁。同样，==比较装箱整数的代码语义也会改变——JDK 5以来Integer.valueOf（-128至127范围）返回缓存实例，==碰巧返回true，但值类迁移后身份同一性的意义消失。

现有代码库中用==比较Integer或将Integer用作锁的模式必须提前检查。2026年6月基准此功能仍处于预览阶段，建议在测试环境中探索而非直接用于生产。

6. 哪些代码获益最大

Valhalla不是对所有Java代码的魔法加速。收益集中在特定模式。

6.1 高收益模式

  • 大规模值对象数组处理：金融数据（交易记录）、坐标处理（游戏/模拟/GIS）、色彩缓冲（图像处理）、传感器数据流
  • 数值密集循环：向量运算、矩阵乘法、统计聚合等CPU缓存利用率关键的代码
  • 小型不可变类型的高频创建和丢弃：Option类型、坐标对、RGB值、金额+货币对等

6.2 收益有限的模式

  • 以锁为核心的共享可变状态：值类无法替代现有synchronized模式
  • 已避免装箱的原始类型代码：如果已在用int[]，额外收益有限
  • I/O和网络密集型代码：瓶颈不在内存布局时，Valhalla优化无关

7. 对Java开发者的意义 — 我的分析

7.1 防御性性能模式变为可选

Java性能调优的长期建议中有：「不要大量创建小对象，优先使用原始类型数组，避免装箱」。这些建议的共同根源是Java对象模型的结构性代价。Valhalla降低了这一代价本身。部分防御性设计原则不再是必须。小型不可变数据类型可以无负担地表达为值类。这是设计自由度的真实提升。

7.2 缩小与C#、Rust、Swift的差距

C#已长期支持struct值类型，Rust默认栈分配，Swift的struct具有值语义。Java在数值密集型工作中相对C、C++、Rust、C#存在明显的内存和性能劣势。Valhalla之后，这一差距大幅缩小。JVM的安全保障（GC、边界检查）仍有代价，但对象数组指针追踪这一结构性弱点得到大幅缓解。

7.3 迁移应循序渐进

Valhalla默认不破坏现有代码。现有class Point {}继续工作。值类的收益需要显式声明value修饰符。风险向量是标准库迁移——当Integer等在正式版本成为值类时，依赖其身份的代码会受影响。实用建议：用--enable-preview探索值类，等待未来LTS正式收录后再战略性应用，同时立即开始审计基于装箱类型synchronized和==比较的模式。

8. 结论 — 十年值得的理由

Project Valhalla花了十二年，不是因为进展缓慢，而是因为问题确实复杂。在不破坏现有代码的前提下改变一门拥有数百万开发者、数十亿行代码的语言的根本假设——这不是常规的工程任务。JEP 401单次提交的197,000行代码，直观呈现了这份重量。

2026年6月基准，JDK 28预览的JEP 401是Valhalla的第一道关卡。值类、堆扁平化、标量化——三者结合，从结构上减少Java在最受影响的工作负载上的内存浪费和缓存未命中问题。特化泛型到来时，将为集合API和泛型代码带来更大的跨越。但现在落地的已足够有意义。「像类一样编写，像int一样运行。」十二年来的承诺，终于可以写成代码了。
