셸 종료 코드와 set -e - 무엇을 잡고 무엇을 놓치는가

errexit·pipefail·nounset의 사각지대를 실행 출력으로 전부 열어 본다

2026-07-29 개발/인프라

서론: CI는 초록불이었고, 배포된 값은 비어 있었다

맨 위에 set -euo pipefail이 붙은 스크립트가 있다. 설정 파일에서 값 두 개를 읽어 정리 명령을 만든다. 설정 파일에 그 키가 없는 상태로 돌려 봤다. 결과는 이렇다.

  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

읽지 못한 값 두 개가 빈 문자열이 되어 그대로 흘렀다. 조립된 명령줄에서는 경로가 /srv/backup/로 끝나 버렸고 보관 일수는 아예 사라져 -mtime +만 남았다. 그런데 스크립트의 종료 코드는 0이다. CI는 초록불을 켰고, 아무도 이 빌드를 다시 보지 않았다.

이 스크립트에는 set -e도, set -u도, set -o pipefail도 전부 켜져 있었다. 흔히 「셸 스크립트 안전 3종 세트」라고 부르는 그 줄이다. 그 줄은 이 사고를 막지 못한다. 왜 못 막는지, 어디까지만 막는지를 아는 것이 이 글의 목적이다.

조용한 실패가 무서운 이유는 단순하다. 실패가 종료 코드 0으로 보고되면 그것은 실패가 아니라 성공이기 때문이다. 사람이 로그를 안 읽어서 놓치는 게 아니라, 파이프라인이 「통과」라고 판정해서 놓친다. 요란하게 죽는 스크립트는 고치면 되지만, 초록불을 켜고 잘못된 일을 하는 스크립트는 고쳐야 한다는 사실 자체가 발견되지 않는다.

이 글은 set -euo pipefail을 붙이라고 권하지 않는다. 그것이 어디까지만 지켜 주는지를 먼저 보여 주고, 그 다음에 붙이라고 말한다. 규정은 GNU Bash Reference Manual과 POSIX 사양에서 확인했고, 동작은 전부 임시 디렉터리에서 직접 돌렸다. 본문의 모든 출력은 실제로 화면에 나온 것이다. 15절의 사각지대 표가 이 글의 결론이다.

축을 미리 갈라 둔다. 같은 스크립트를 두 번 돌려도 되는지는 두 번 돌려도 안전한 스크립트, 돌리기 전에 결과를 미리 알 수 있는지는 --dry-run을 제대로 만드는 법에 있다. 그 글이 「계획과 적용의 결과를 어떻게 전달하나」를 다룬다면, 이 글은 그 앞 단계인 「실패를 애초에 어떻게 감지하나」를 다룬다. 변수에 따옴표를 붙이는 문법은 셸 인용부호 규칙에 있다.

1. 실행 환경과 이 글의 근거

본문의 모든 출력은 실제로 돌려 본 결과다. 재현 환경은 다음과 같다.

  • OS: Windows 10 Pro 10.0.19045 위의 MSYS2 계열 유닉스 환경
  • bash: GNU bash 5.2.37(1)-release (x86_64-pc-msys)
  • POSIX sh: dash — bash와 갈리는 지점을 확인하기 위한 대조군
  • 유틸리티: GNU coreutils 8.32
  • 작업 위치: 새로 만든 임시 디렉터리. 실험마다 하위 폴더를 새로 만들어 격리

본문에 나오는 경로는 전부 /tmp/demo 같은 자리표시자다. 실제 실행은 격리된 임시 폴더에서 했다. 종료 코드와 set 옵션의 동작은 셸 자체의 규정에서 나오는 것이라 리눅스나 macOS로 옮겨도 같다. 다만 이 환경에서 재현되지 않는 항목이 하나 있어 미리 적어 둔다.

환경에서 갈린 지점 — 실행 권한 비트
POSIX는 「찾았지만 실행할 수 없으면 126」을 규정한다. 리눅스에서는 실행 비트를 뗀 파일을 실행하면 126이 나온다. 그런데 이 환경은 NTFS 위라 chmod 644가 실제로 강제되지 않아, 실행 비트를 떼도 스크립트가 그냥 실행되며 0이 나왔다. 그래서 126은 디렉터리를 실행하려는 경우로 확인했고 이쪽은 정상적으로 126이 나왔다. 본문의 126 예제가 권한이 아니라 디렉터리인 이유다.

규정 확인에는 1차 출처만 썼다. 「보통 이렇다」는 서술은 이 글에 없다.

  • GNU Bash Reference Manual — The Set Builtin(-e·-u·pipefail), The Shopt Builtin(inherit_errexit)
  • The Open Group Base Specifications Issue 8 — Shell Command Language 2.8.2 Exit Status and Errors
  • 실행 중인 bash 자신 — help set으로 이 바이너리의 옵션 설명을 직접 확인

2. 종료 코드 기본기 - 0·1·126·127·128+N

모든 명령은 끝날 때 0에서 255 사이의 정수를 남긴다. 셸은 그것을 $?에 담는다. 규칙은 하나다. 0은 성공, 나머지 전부가 실패다. 「1이 실패」가 아니라 「0이 아니면 실패」라는 점이 중요하다.

$ true;  echo $?
0
$ false; echo $?
1
$ no_such_command_xyz 2>/dev/null; echo $?
127
$ ./sandbox 2>/dev/null; echo $?        # 디렉터리를 실행하려 하면
126
$ bash -c 'exit 3'; echo $?
3

127과 126은 POSIX가 직접 규정한 값이다. 사양의 2.8.2절은 이렇게 적는다.

If the command is not found, the exit status shall be 127. (…) if the command name is found, but it is not an executable utility, the exit status shall be 126.

그래서 127은 거의 언제나 오타이거나 PATH 문제다. 명령이 실패한 게 아니라 명령을 못 찾은 것이다. 이 둘을 구분하면 CI 로그를 읽는 시간이 크게 줄어든다.

시그널로 죽은 경우는 128을 더한 값이 된다. 실제로 만들어 확인했다.

$ sleep 30 & pid=$!; kill -9 "$pid"; wait "$pid" 2>/dev/null; echo $?
137
$ sleep 30 & pid=$!; kill -TERM "$pid"; wait "$pid" 2>/dev/null; echo $?
143

137은 128+9(SIGKILL), 143은 128+15(SIGTERM)다. 컨테이너가 메모리 초과로 죽으면 137이 나오는 것이 이 계산 때문이다. 다만 POSIX의 표현은 조금 느슨하다.

If the command terminated due to the receipt of a signal, the shell shall assign it an exit status greater than 128. The exit status shall identify, in an implementation-defined manner, which signal terminated the command.

즉 「128보다 크다」까지가 규정이고, 정확히 128+N인 것은 구현이 정하는 관례다. 실무의 모든 주류 셸이 128+N을 쓰므로 믿고 써도 되지만, 규정으로 오해하지는 말자.

코드는 8비트로 잘린다. 이것도 실측했다.

$ bash -c 'exit 256'; echo $?
0
$ bash -c 'exit -1' 2>/dev/null; echo $?
255
$ sh -c 'exit 300'; echo $?
44

exit 256이 0이 된다. 실패를 알리려고 큰 숫자를 골랐다가 성공으로 보고되는 사고가 여기서 난다. 오류 개수를 그대로 종료 코드로 쓰는 스크립트가 특히 위험하다. 오류가 정확히 256개면 초록불이다.

마지막으로, 0과 1이 언제나 성공·실패인 것도 아니다. 도구마다 자기 규약이 있다.

$ printf 'alpha\nbeta\n' > /tmp/demo/data.txt
$ grep -q alpha /tmp/demo/data.txt; echo $?
0
$ grep -q zzzzz /tmp/demo/data.txt; echo $?
1
$ grep -q alpha /tmp/demo/nope.txt 2>/dev/null; echo $?
2

grep은 0을 찾음, 1을 못 찾음, 2를 오류로 쓴다. 「못 찾음」은 정상 결과이지 오류가 아니다. 그런데 set -e는 1도 2도 똑같이 실패로 본다. grep을 set -e 아래에서 그냥 부르면 「없다」는 정상 결과가 스크립트를 죽인다. 13절에서 다시 다룬다.

3. set -e 의 규정 - 매뉴얼이 예외를 직접 나열한다

set -e(errexit)의 설명은 help set 한 줄로는 이렇다.

-e Exit immediately if a command exits with a non-zero status.

이 한 줄만 읽으면 「실패하면 무조건 멈춘다」로 이해하게 된다. 그리고 그 이해가 이 글에 나오는 모든 사고의 출발점이다. Bash Reference Manual의 온전한 서술은 훨씬 길고, 예외를 직접 나열한다.

The shell does not exit if the command that fails is part of the command list immediately following a while or until reserved word, part of the test in an if statement, part of any command executed in a && or || list except the command following the final && or ||, any command in a pipeline but the last (subject to the state of the pipefail shell option), or if the command's return status is being inverted with !.

다섯 개다. while·until 뒤의 명령 목록, if의 조건, &&와 || 목록의 마지막이 아닌 명령, 파이프라인의 마지막이 아닌 명령, !로 반전된 명령. 여기까지는 비교적 알려져 있다. 진짜 함정은 그 다음 문단이다.

If a compound command or shell function executes in a context where -e is being ignored, none of the commands executed within the compound command or function body will be affected by the -e setting, even if -e is set and a command returns a failure status.

풀어 쓰면 이렇다. 함수를 if 조건에 넣는 순간, 그 함수 본문 전체가 set -e의 보호 밖으로 나간다. 조건 자리에 있는 것은 함수 호출 한 줄뿐인데, 효력은 함수 안의 모든 줄에 미친다. 다음 절에서 실행으로 보여 준다.

4. set -e 가 잡지 못하는 자리들 - 전부 실행으로

규정만 읽으면 추상적이다. 사각지대를 한 스크립트에 전부 몰아 넣고 맨 위에 set -e를 붙여 돌렸다. 하나라도 걸리면 거기서 죽을 것이다.

먼저 기준선이다. set -e가 제대로 동작하는 경우를 확인해 둔다.

== A. baseline: set -e DOES stop here ==
  inner script died, rc=1  (NOT REACHED never printed)

맨몸의 false는 확실히 잡는다. 이제 사각지대다. 아래는 한 번의 실행에서 연속으로 나온 출력이다.

== B. condition of if ==
  survived: if-condition

== C. while condition ==
  survived: while-condition

== D. left side of && / || ==
  survived: false &&
  ran RHS of ||
  survived: false ||

== E. negated with ! ==
  survived: ! true

== F. non-final command of a pipeline ==
  survived: false | cat   rc=0

== G. function failing inside a condition ==
  ...function continued past its own false
  survived: function under if

== H. local x=$(failing) hides the status ==
  local v=$(false) -> rc=0  (local's own status wins)
  split declaration caught it -> rc=1

== J. arithmetic that evaluates to zero ==
  (( c++ )) returned nonzero because the OLD value was 0; c is now 1

== ALL BLIND SPOTS PASSED THROUGH; script still alive ==

하나도 걸리지 않았다. 맨 아래 줄까지 도달했다는 것은 set -e가 켜진 채로 이 모든 실패를 통과시켰다는 뜻이다. 항목별로 짚는다.

  • B·C — if false; then …; fi와 while false; do …; done. 조건은 실패해도 되는 자리다. 당연하다. 실패가 곧 「거짓」이라는 의미이기 때문이다
  • D — false && echo x도, false || echo …도 살아남았다. || true를 붙이는 관용구가 여기서 나온다. 편리하지만 대가가 크다. 13절에서 다시 본다
  • E — ! true는 최종 결과가 실패(1)인데도 통과한다. 반전된 명령은 예외 목록에 명시돼 있다
  • F — false | cat의 종료 코드가 0이다. 파이프라인의 코드는 맨 끝 것이고, cat은 성공했다. 7절의 주제다
  • G — 가장 위험하다. 함수 안의 false 다음 줄이 그대로 실행됐다. 3절 매뉴얼 마지막 문단 그대로다. 함수를 if에 넣는 순간 본문 전체가 무방비가 된다
  • H — local이 종료 코드를 삼켰다. 5절에서 따로 다룬다
  • J — (( c++ ))는 연산 결과가 0이면 종료 코드 1이다. 카운터가 0에서 시작하면 첫 증가에서 스크립트가 죽는다. (( ++c ))나 c=$((c+1))을 쓰면 피할 수 있다
⚠ G가 실무에서 나타나는 형태
「함수로 감싸서 if로 검사한다」는 아주 자연스러운 구조다. if deploy_app; then … 한 줄을 쓰는 순간, deploy_app 안의 모든 실패가 무시된다. 중간 단계가 전부 실패해도 마지막 줄이 성공하면 함수는 0을 돌려주고, if는 참으로 판정한다. 함수 안에서 set -e를 믿고 있었다면 그 믿음이 호출 형태 하나로 사라진다.

5. local 이 종료 코드를 삼킨다

4절의 H가 set -e 함정 중 가장 자주 실무를 무너뜨린다. 원리는 간단하다. local은 대입 문법이 아니라 빌트인 명령이고, 명령의 종료 코드는 local 자신의 것이다. 안쪽 명령 치환이 무엇으로 끝났든 local은 「변수를 잘 만들었다」는 뜻으로 0을 돌려준다.

먼저 그냥 대입이 어떻게 동작하는지 보자. 이쪽은 정상이다.

== plain assignment: status comes FROM the substitution ==
  v=$(false)      -> rc=1
  v=$(exit 7)     -> rc=7
  v="pre-$(exit 7)-post" -> rc=7  v=[pre--post]

대입식의 종료 코드는 명령 치환의 코드가 그대로 올라온다. 문자열 중간에 끼워 넣어도 7이 살아남는다. 그래서 set -e는 이 형태를 정상적으로 잡는다. 이제 앞에 선언 키워드를 하나 붙여 보자.

== declaration builtins SWALLOW it ==
  local    v=$(exit 7) -> rc=0
  declare  v=$(exit 7) -> rc=0
  typeset  v=$(exit 7) -> rc=0
  export   v=$(exit 7) -> rc=0
  readonly r=$(exit 7) -> rc=0

다섯 개 전부 0이다. local만의 문제가 아니라 선언 빌트인 전체의 성질이다. export PATH_X=$(some_command)도 똑같이 실패를 삼킨다.

set -e와 함께 어느 형태가 실제로 스크립트를 죽이는지 확인했다.

== under set -e: which one actually kills the script? ==
  rc=7   out=[]
     form: v=$(exit 7); echo ALIVE
  rc=0   out=[ALIVE-in-func
ALIVE]
     form: f(){ local v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE
  rc=7   out=[]
     form: f(){ local v; v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE

가운데 형태만 살아남아 ALIVE를 두 번 찍었다. 첫째와 셋째는 코드 7로 정상적으로 죽었다. 차이는 오직 선언과 대입을 한 줄에 썼는지 두 줄로 나눴는지뿐이다.

여러 개를 한 줄에 선언하면 더 조용해진다.

== the multi-declaration variant is worse ==
  three locals, rc=0  b=[]

가운데 것만 실패했는데 어느 것이 실패했는지 알 방법이 전혀 없다. 종료 코드는 0이고 실패한 변수만 조용히 빈 값이다.

규칙 하나만 외운다면
local x=$(cmd)는 언제나 두 줄로 쪼갠다. local x로 이름만 만들고, 다음 줄에서 x=$(cmd)로 대입한다. declare·export·readonly도 같다. 이 규칙 하나가 set -e 사고의 상당수를 없앤다.

6. 명령 치환은 errexit 를 물려받지 않는다

또 하나의 사각지대가 있다. $( ) 안쪽은 기본적으로 set -e가 꺼진 별개의 세계다. 실행으로 확인했다.

$ shopt inherit_errexit
inherit_errexit	off

== A. WITHOUT inherit_errexit ==
  out=[LEAKED]  rc=0
  script continued
  rc=0

set -e가 켜진 스크립트에서 out=$( false; echo "LEAKED" )를 실행했다. 안쪽의 false가 서브셸을 멈추지 못했고, 뒤의 echo가 실행되어 LEAKED가 변수에 담겼다. 여러 명령을 $( ) 안에 이어 쓰는 습관이 있다면 앞쪽이 전부 실패해도 마지막 것만 성공하면 값이 만들어진다.

bash 4.4부터 이것을 고치는 옵션이 생겼다. 매뉴얼의 서술은 이렇다.

If set, command substitution inherits the value of the errexit option, instead of unsetting it in the subshell environment. This option is enabled when POSIX mode is enabled.

켜고 같은 코드를 돌리면 결과가 갈린다.

== B. WITH inherit_errexit ==
  rc=1

== C. POSIX mode also turns it on ==
  rc=1

둘 다 안쪽 false에서 죽었다. 매뉴얼대로 --posix로 띄워도 같은 효과가 났다. 그래서 실무 권장은 이렇다.

set -euo pipefail
shopt -s inherit_errexit    # bash 4.4 이상

다만 이것도 만능이 아니다. 12절에서 inherit_errexit를 켜도 통과하는 사례를 보여 준다. local이 먼저 코드를 삼키면 inherit_errexit가 개입할 기회 자체가 없기 때문이다.

7. set -o pipefail - 파이프라인의 상태를 되찾기

파이프라인의 종료 코드는 기본적으로 맨 끝 명령의 것이다. 앞쪽이 무엇으로 죽든 무시된다.

== 1. pipeline status = LAST command, by default ==
  false | true   -> rc=0
  true  | false  -> rc=1
  false | cat    -> rc=0

false | true가 성공이다. 앞이 실패했는데 결과는 0이다. pipefail을 켜면 달라진다.

== 2. same pipelines with pipefail on ==
  false | true   -> rc=1
  true  | false  -> rc=1
  false | cat    -> rc=1

세 경우 모두 실패로 바뀌었다. 실행 중인 bash 자신의 설명은 이렇다.

pipefail — the return value of a pipeline is the status of the last command to exit with a non-zero status, or zero if no command exited with a non-zero status

「0이 아닌 코드 중 가장 오른쪽 것」이라는 뜻이다. 확인했다.

== 3. pipefail returns the RIGHTMOST nonzero ==
  (exit 3)|(exit 4)|true -> rc=4
  (exit 3)|true|true     -> rc=3

실무에서 이것이 가장 크게 걸리는 자리가 tee다. 로그를 남기려고 파이프에 물리는 순간 실패가 사라진다.

== 5. the classic: cmd | tee log ==
  no pipefail: rc=0  PIPESTATUS=(1 0)   <- failure vanished
  pipefail   : rc=1  PIPESTATUS=(1 0)

같은 파이프라인인데 위는 성공, 아래는 실패다. 빌드 명령을 | tee build.log로 감싸는 것은 매우 흔한 패턴이고, pipefail이 없으면 빌드가 깨져도 CI가 통과한다.

그런데 pipefail에는 반대 방향의 대가가 있다. 정상적인 조기 종료를 실패로 만든다.

== 8. pipefail cannot see a head that quits early (SIGPIPE) ==
  yes | head -1 -> rc=141  PIPESTATUS=(141 0)

head -1이 한 줄만 읽고 닫으면 yes가 SIGPIPE로 죽어 141(128+13)이 된다. 아무 문제 없는 정상 동작인데 pipefail이 이것을 실패로 올린다. grep -q나 head로 앞을 끊는 파이프라인을 쓴다면 이 자리는 따로 처리해야 한다.

8. PIPESTATUS - 단계별로 읽고, 즉시 저장하기

pipefail은 하나의 코드로 뭉뚱그린다. 어느 단계가 실패했는지 알려면 bash의 PIPESTATUS 배열을 쓴다.

== 4. PIPESTATUS keeps every stage ==
  rc=0  PIPESTATUS=(3 0 4 0)

네 단계의 코드가 전부 남았다. 종료 코드는 마지막 것을 따라 0인데, 배열을 보면 1번과 3번 단계가 실패했음이 그대로 보인다.

다만 이 배열에는 치명적인 성질이 있다. 다음 명령 하나에 곧바로 덮인다.

== 6. PIPESTATUS is clobbered by the very next command ==
  first read : PIPESTATUS=(3 4)
  second read: PIPESTATUS=(0)   <- the echo above overwrote it

첫 echo가 성공하는 순간 배열이 (0)으로 바뀌었다. 두 번 읽을 수 없다. 그래서 반드시 파이프라인 바로 다음 줄에서 복사해 둔다.

== 7. save it immediately ==
  saved copy : (3 4)  stage0=3 stage1=4

실무 형태는 이렇다. 파이프라인 직후에 배열을 통째로 복사하고, 그 다음부터는 복사본만 본다.

curl -fsS "$url" | gzip -d | psql "$dsn"
st=("${PIPESTATUS[@]}")          # ← 반드시 바로 다음 줄
if [ "${st[0]}" -ne 0 ]; then echo "다운로드 실패 (${st[0]})" >&2; exit 1; fi
if [ "${st[1]}" -ne 0 ]; then echo "압축 해제 실패 (${st[1]})" >&2; exit 1; fi
if [ "${st[2]}" -ne 0 ]; then echo "적재 실패 (${st[2]})"     >&2; exit 1; fi

pipefail만 켜면 「어딘가 실패했다」까지만 알 수 있지만, 이렇게 하면 「다운로드가 실패했다」까지 로그에 남는다. 3단계 이상 파이프라인에서는 이 차이가 크다.

9. set -u - 미정의 변수와 빈 배열

set -u(nounset)는 정의되지 않은 변수를 참조하면 즉시 종료한다. 오타로 만들어진 빈 값이 명령줄로 흘러드는 것을 막는 장치다.

== 1. plain unset reference ==
  echo "[$nope]"     rc=127 bash: line 1: nope: unbound variable
  echo "[${nope}]"   rc=127 bash: line 1: nope: unbound variable

여기서 종료 코드가 흥미롭다. 같은 오류인데 호출 방식에 따라 값이 다르다. 네 조합을 전부 확인했다.

$ bash -u -c 'echo "[$nope]"'   ; echo $?
127
$ bash -u script.sh             ; echo $?
1
$ dash -u -c 'echo "[$nope]"'   ; echo $?
2
$ dash script.sh                ; echo $?
2

bash는 -c로 부르면 127, 스크립트 파일로 부르면 1이다. dash는 둘 다 2이고 메시지도 parameter not set으로 다르다. set -u가 낸 실패를 특정 종료 코드로 구분하려는 시도는 하지 말자. 이식성이 없다.

회피는 기본값 문법으로 한다. 콜론이 있고 없고가 다르다.

== 2. defaults let you opt out ==
  ${nope:-fallback}        rc=0   [fallback]
  ${nope-fallback}         rc=0   [fallback]
  ${nope:?must be set}     rc=127 bash: line 1: nope: must be set

== 3. set vs empty are different ==
  empty="" then ${empty:-d}   rc=0   [d]
  empty="" then ${empty-d}    rc=0   []

콜론이 있으면 「없거나 비었으면」, 없으면 「없으면」이다. 빈 문자열을 유효한 값으로 취급해야 한다면 콜론을 빼야 한다. ${var:?메시지}는 필수 인자를 강제할 때 유용하다. 직접 if를 쓰지 않고 한 줄로 끝난다.

이제 자주 헷갈리는 빈 $@와 빈 배열이다. bash 버전에 따라 갈렸던 부분이라 이 환경의 버전과 함께 적는다. 확인한 버전은 GNU bash 5.2.37이다.

== 4. empty $@ and $1 ==
  no args, "$@"        rc=0   argc=0 / REACHED
  no args, "$1"        rc=127 bash: line 1: $1: unbound variable
  no args, "${1:-def}" rc=0   [def] / REACHED

== 5. empty arrays ==
  declare -a arr=(); "${arr[@]}"   rc=0   n=0 / REACHED
  unset arr; "${arr[@]}"           rc=0   REACHED
  declare -a arr=(); "${arr[0]}"   rc=127 bash: line 1: arr[0]: unbound variable
  empty array + ${arr[@]:-}        rc=0   x=[] / REACHED

정리하면 이렇다. bash 5.2.37에서 인자가 없을 때의 "$@"와 빈 배열의 "${arr[@]}"는 안전하다. 반면 "$1"과 "${arr[0]}"처럼 개별 원소를 집으면 터진다. 구분선은 「전체를 펼치느냐, 특정 원소를 집느냐」다.

옛 bash에 대한 주의
빈 "$@"와 빈 배열이 set -u에서 오류가 되던 시절이 있었다(bash 4.4 이전). 위 결과는 5.2.37에서 직접 확인한 것이고, 이 환경에 옛 bash가 없어 과거 동작은 재현하지 못했다. macOS 기본 bash 3.2처럼 오래된 셸을 대상으로 한다면 "${arr[@]:-}" 형태로 방어하는 편이 안전하다.

마지막으로, set -u는 실패한 명령과 아무 상관이 없다는 점을 확인해 둔다.

== 6. -u alone does not stop a FAILING command ==
  -u only, false   rc=0   REACHED
  -eu, false       rc=1   (no output)

-u만 켜면 false가 스크립트를 죽이지 못한다. 세 옵션은 서로 다른 일을 하며 서로를 대신하지 않는다.

10. trap - ERR 로 찾고 EXIT 로 치운다

trap은 실패 지점을 기록하고 뒷정리를 보장하는 장치다. ERR 트랩부터 보자.

== 1. ERR trap reports line and command ==
  step one
  ERR: line 5 rc=2 cmd=[grep -q nothing /nonexistent/path]
  outer saw rc=2

LINENO·$?·BASH_COMMAND 세 변수로 몇 번째 줄에서 어떤 명령이 무슨 코드로 죽었는지가 한 줄에 남았다. set -x로 전부 찍는 것보다 로그가 훨씬 깨끗하다.

함수 안까지 미치게 하려면 -E(errtrace)가 필요하다.

== 5. functions need -E (errtrace) to inherit the ERR trap ==
  without -E: trap did not fire inside f
  with -E: trap fired inside f

set -e가 아니라 set -eE로 쓰는 이유가 이것이다. -E 없이는 함수·서브셸·명령 치환 안에서 ERR 트랩이 동작하지 않는다.

그런데 결정적인 한계가 있다. ERR 트랩은 set -e와 정확히 같은 사각지대를 갖는다. 4절의 사각지대를 그대로 ERR 트랩 아래에서 돌렸다.

== 4. ERR trap has the SAME blind spots as set -e ==
  reached the end with no ERR trap firing
  outer saw rc=0

if false, false || true, ! true, false | cat, local v=$(exit 7)을 전부 실행했는데 트랩이 한 번도 발화하지 않았다. 「ERR 트랩을 달았으니 실패는 다 잡힌다」는 기대는 성립하지 않는다.

EXIT 트랩은 성격이 다르다. 성공이든 실패든 반드시 실행되므로 임시 파일 정리에 적합하다.

== 2. EXIT trap always runs; use it for cleanup ==
  workdir created: yes
  cleanup: removing workdir
  outer saw rc=5  (EXIT trap did not change it)

코드 5로 죽었는데도 정리가 실행됐고, 종료 코드는 5 그대로 유지됐다. 여기서 흔한 오해를 실측으로 갈랐다.

== 3. an EXIT trap CAN silently rewrite the exit code ==
  cleanup running
  outer saw rc=9
  cleanup running
  outer saw rc=9
  ...now a cleanup with an explicit exit in the trap:
  cleanup running
  outer saw rc=0   <- the real failure was erased

중요한 구분이다. 트랩 안의 마지막 명령이 실패하거나 성공하는 것만으로는 종료 코드가 바뀌지 않는다. 앞의 두 경우는 9가 그대로 유지됐다. 오직 트랩 안에서 exit를 명시적으로 부를 때만 코드가 덮인다. 세 번째에서 진짜 실패 9가 0으로 지워졌다.

⚠ 정리 함수 안에서 exit를 부르지 말 것
trap cleanup EXIT의 cleanup 안에 exit 0이 있으면 모든 실패가 성공으로 보고된다. 실측에서 코드 9로 죽은 스크립트가 0으로 끝났다. 정리 함수는 정리만 하고 조용히 반환해야 한다. 굳이 코드를 다뤄야 한다면 진입 시 rc=$?로 받아 두고 마지막에 exit "$rc"로 되돌려 준다.

11. 서브셸과 함수 경계

set -e가 경계를 넘을 때 어떻게 되는지 정리한다. 매뉴얼은 「셸 환경과 각 서브셸 환경에 따로 적용된다」고 적는다. 실행으로 확인했다.

== 1. set -e is inherited by subshells ==
  rc=1

== 2. ...but not if the subshell sits in a condition ==
  subshell CONTINUED past false
  subshell failure absorbed by ||
  script alive, rc=0

서브셸은 set -e를 물려받지만, 그 서브셸이 조건 자리에 놓이면 안쪽까지 통째로 무방비가 된다. 4절 G와 같은 원리다.

명령 치환은 6절에서 본 대로 기본적으로 물려받지 않는다. inherit_errexit 없이 돌린 결과다.

== 3. command substitution: -e does NOT apply inside by default ==
  out=[SHOULD-NOT-APPEAR]
  rc=0

== 5. the killer: substitution inside a declaration ==
  local out=[SHOULD-NOT-APPEAR] rc=0
  script survived
  rc=0

함수의 반환값은 마지막으로 실행된 명령의 코드다. return을 안 쓰면 이것이 그대로 반환된다.

== 6. a function without an explicit return ==
  f -> 1       # f(){ true; false; }   마지막이 false
  g -> 0       # g(){ false; true; }   마지막이 true
  h -> 0       # h(){ echo "..."; }    echo 가 성공

g가 위험하다. 안에서 실패했지만 마지막 줄이 성공해서 0을 돌려준다. 검증 함수 끝에 echo나 log 한 줄을 습관적으로 붙이면 그 함수는 영원히 성공한다. 이런 함수는 return을 명시해야 한다.

== 7. exit inside a subshell only leaves the subshell ==
  after subshell, rc=4  (parent still running)
  parent rc=0

괄호 안의 exit 4는 서브셸만 끝냈다. 부모는 계속 돌았고 최종 코드는 0이다. 「검증 실패하면 exit」를 서브셸이나 파이프라인 안에 쓰면 스크립트가 안 멈춘다.

파이프라인의 각 단계도 서브셸이라 변수 대입이 사라진다.

== 8. a pipeline runs its stages in subshells ==
  after while-in-pipeline: count=0  (child's copy was discarded)
  with process substitution: count=3

printf … | while read …로 센 값이 0이다. 자식 프로세스의 변수라 부모로 돌아오지 않는다. 프로세스 치환으로 바꾸면 3이 나온다. 오류 개수를 세어 마지막에 판정하는 스크립트가 이 함정에 자주 걸린다. 언제나 「오류 0건」으로 끝난다.

12. set -euo pipefail 을 붙이고도 잘못된 값이 지나간다

서론의 스크립트로 돌아온다. 지금까지의 조각을 합치면 왜 통과했는지 설명할 수 있다. 스크립트는 이랬다.

#!/usr/bin/env bash
set -euo pipefail

read_key() {
  local value=$(grep -m1 "^$1=" "$2" | cut -d= -f2)
  echo "$value"
}

target=$(read_key target /tmp/demo/app.conf)
retain=$(read_key retain_days /tmp/demo/app.conf)

echo "  target      = [$target]"
echo "  retain_days = [$retain]"
echo "  would run: find /srv/backup/$target -mtime +$retain -delete"
echo "  DEPLOY OK"

설정 파일에는 name과 owner만 있고 target·retain_days는 없다. 실행 결과다.

=== run 1: the 'safe' version ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

실패가 세 겹으로 지워졌다. 하나씩 짚으면 이렇다.

  • grep이 키를 못 찾아 1로 끝났지만, | cut이 뒤에 있어 파이프라인 코드는 cut의 0이 된다. pipefail이 켜져 있으니 여기까지는 1로 살아난다
  • 그런데 그 파이프라인이 local value=$(…) 안에 있다. local이 코드를 삼켜 0으로 만든다(5절)
  • 함수는 echo "$value"로 끝난다. echo는 성공하므로 함수의 반환값도 0이다(11절)
  • 결국 target=$(read_key …)는 0을 받는다. set -e가 개입할 이유가 없다. set -u도 소용없다. 변수는 「정의되지 않은」 것이 아니라 「빈 문자열로 정의된」 것이기 때문이다

6절에서 배운 inherit_errexit를 추가하면 어떨까. 같은 스크립트에 shopt -s inherit_errexit 한 줄만 넣고 돌렸다.

=== run 2: same script, inherit_errexit added ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK

결과가 똑같다. inherit_errexit는 명령 치환 안쪽에서 errexit를 살리는 옵션인데, 여기서는 local이 그보다 먼저 코드를 삼키므로 개입할 기회가 없다. 옵션을 더 켜는 방식으로는 이 사고를 막을 수 없다는 뜻이다.

해법은 옵션이 아니라 검증이다. 값을 읽은 뒤 「읽혔는가」와 「비어 있지 않은가」를 직접 확인한다.

read_key() {
  local value
  if ! value=$(grep -m1 "^$1=" "$2"); then
    printf 'config key missing: %s\n' "$1" >&2
    return 3
  fi
  value=${value#*=}
  if [ -z "$value" ]; then
    printf 'config key empty: %s\n' "$1" >&2
    return 3
  fi
  printf '%s\n' "$value"
}
=== run 3: validated version ===
config key missing: target
  run3 rc=3

코드 3으로 정상적으로 실패했고 어느 키가 없는지 메시지에 남았다. 바뀐 것은 네 가지다. local 선언과 대입을 나눴고, grep의 실패를 if !로 직접 받았고, cut 대신 매개변수 확장으로 잘라 파이프라인을 없앴고, 빈 값을 명시적으로 검사했다.

⚠ 이 절의 결론
set -euo pipefail은 「명령이 실패했다」를 잡는 장치다. 「명령은 성공했는데 값이 틀렸다」는 잡지 못한다. 그리고 실무 사고의 상당수가 후자다. 빈 문자열, 예상과 다른 형식, 0건인 목록은 전부 성공한 명령의 정상적인 출력이다. 값의 유효성은 사람이 직접 검사하는 수밖에 없다.

13. 종료 코드 설계 - 호출자에게 무엇을 전달할 것인가

지금까지가 실패를 감지하는 문제였다면, 이제 감지한 것을 전달하는 문제다. 상태가 세 가지 이상이면 0과 1로는 부족하다. 널리 쓰이는 형태는 세 갈래다.

코드뜻호출자가 할 일
0정상 — 문제 없음통과
2차이 있음 — 검사는 성공했고 결과가 다름내용을 보고 판단·승인
1오류 — 검사 자체를 수행하지 못함즉시 실패 + 알림
64 이상사용법 오류 등 세분화된 상태호출 방식을 고침

세 상태를 내는 검사기와, 그것을 받는 쪽을 만들어 돌렸다.

  PASS  : no differences
    -> caller exits 0
  DRIFT : 3 files differ  (gate: fail the build, keep the log)
    -> caller exits 2
  ERROR : checker itself failed
    -> caller exits 1
  USAGE : bad invocation
    -> caller exits 64

받는 쪽의 뼈대는 이렇다. set -e 아래에서 그냥 부르면 0이 아닌 값이 전부 스크립트를 죽이므로, 코드를 변수에 받은 뒤 case로 나눈다.

rc=0
out=$(./check.sh "$1") || rc=$?     # ← 죽지 않고 코드만 받는다
case "$rc" in
  0)  echo "  PASS  : $out" ;;
  2)  echo "  DRIFT : $out" ;;
  1)  echo "  ERROR : checker itself failed" ;;
  64) echo "  USAGE : bad invocation" ;;
  *)  echo "  UNKNOWN rc=$rc" ;;
esac
exit "$rc"

여기서 || rc=$?가 핵심이다. 4절 D에서 본 대로 ||의 왼쪽은 set -e의 사각지대이므로 스크립트가 죽지 않고, 코드는 변수에 그대로 남는다. 사각지대를 문제가 아니라 도구로 쓰는 자리다.

반대로 || true는 같은 자리에서 정보를 파괴한다.

== 3. the anti-pattern: '|| true' erases the state ==
  after || true, rc=0  <- error is gone

== 4. '|| true' vs capturing the code ==
  captured rc=1  <- still known, still recoverable

|| true는 「이 명령은 실패해도 된다」는 뜻으로 붙이지만, 실제로는 「이 명령이 어떻게 끝났는지 영원히 모르겠다」는 선언이다. 실패해도 되는 것과 실패를 알 필요가 없는 것은 다르다. || rc=$?로 받아 두면 둘 다 만족한다.

grep처럼 「없음」이 1인 도구는 이렇게 감싼다.

if grep -q "$pattern" "$file"; then
    echo "찾음"
elif [ $? -eq 1 ]; then
    echo "없음 — 정상"
else
    echo "grep 실행 오류" >&2; exit 1
fi

실패 지점을 빠르게 찾아야 할 때는 set -x가 유용하다. 실행되는 명령을 그대로 찍는다.

== 5. set -x shows the failing command ==
  + grep -q token /nonexistent/file.txt
  grep: /nonexistent/file.txt: No such file or directory

확장이 끝난 최종 형태가 보이는 것이 장점이다. 변수가 비어 있었는지, 경로가 어떻게 조립됐는지가 즉시 드러난다. 다만 출력이 많으므로 문제 구간만 set -x … set +x로 감싸는 편이 낫다.

마지막으로, 받은 코드를 그대로 돌려주는 것을 잊지 말자. 정리 트랩이 있어도 코드는 유지된다.

== 6. exit with the code you were given ==
  propagating rc=2
  cleaning up
  outer sees 2

계획과 적용을 나누는 구조에서 이 규약을 어떻게 배선하는지는 --dry-run을 제대로 만드는 법의 종료 코드 절에서 더 자세히 다뤘다.

14. POSIX sh 와 갈리는 지점

스크립트 첫 줄이 #!/bin/sh라면 지금까지의 절반이 없다. 같은 코드를 bash와 dash에 각각 먹여 대조했다.

  • pipefail이 없다. POSIX sh로 쓰는 스크립트에서 파이프라인 실패를 잡으려면 파이프 자체를 피해야 한다. 임시 파일에 받고 코드를 확인한 뒤 다음 단계로 넘기는 형태가 된다
  • PIPESTATUS도 배열도 없다. 단계별 상태를 볼 방법이 사실상 없다
  • ERR 트랩이 없다. EXIT 트랩은 양쪽 모두 동작하고 종료 코드도 5로 같았다. 정리 로직은 이식 가능하지만 실패 로깅은 아니다
  • local은 dash에도 있다. 그리고 종료 코드를 삼키는 성질까지 똑같다. 5절의 함정은 #!/bin/sh에서도 그대로 성립한다
  • set -e의 사각지대는 동일하다. 함수를 if에 넣으면 양쪽 다 통과했다. 이것은 bash의 특이 동작이 아니라 셸 언어의 규정이다

요약하면 안전장치는 bash 전용이고, 함정은 양쪽 공통이다. 이식성이 필요하면 도구를 잃고 함정만 남는 셈이라, #!/bin/sh를 고를 때는 그만한 이유가 있어야 한다.

16. 템플릿 - 보장하는 것과 보장하지 않는 것

지금까지의 내용을 반영한 시작 틀이다. 이 템플릿이 무엇을 보장하지 않는지를 함께 적는 것이 이 절의 요점이다.

#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true   # bash 4.4+ 에서만

readonly WORKDIR=$(mktemp -d)
cleanup() {
    rm -rf "$WORKDIR"        # exit 를 부르지 않는다 (10절)
}
trap cleanup EXIT
trap 'echo "실패: line $LINENO rc=$? cmd=[$BASH_COMMAND]" >&2' ERR

need() {                     # 필수 값 검증 (12절)
    local name="$1" value="$2"
    if [ -z "$value" ]; then
        echo "필수 값 없음: $name" >&2
        return 3
    fi
}

run_stage() {
    local rc                 # 선언과 대입 분리 (5절)
    local out
    out=$(some_command "$1") || rc=$?
    : "${rc:=0}"
    case "$rc" in
        0) printf '%s\n' "$out" ;;
        *) echo "단계 실패: $1 (rc=$rc)" >&2; return "$rc" ;;
    esac
}

main() {
    local value
    value=$(run_stage fetch)
    need "value" "$value"    # 성공했어도 값을 검증한다
    echo "정상 완료"
}

main "$@"

이 템플릿이 보장하는 것은 다음과 같다.

  • 맨몸으로 실패한 명령에서 즉시 멈춘다(-e)
  • 파이프라인 중간의 실패가 사라지지 않는다(pipefail)
  • 오타로 만들어진 미정의 변수 참조에서 멈춘다(-u)
  • 명령 치환 안쪽의 실패도 잡는다(inherit_errexit)
  • 함수 안에서도 ERR 트랩이 발화해 실패 지점이 로그에 남는다(-E)
  • 어떤 경로로 끝나든 임시 디렉터리가 정리된다(EXIT 트랩)
  • 정리 트랩이 종료 코드를 덮지 않는다(트랩 안에 exit 없음)

보장하지 않는 것이 더 중요하다.

  • 함수를 if나 ||에 넣으면 그 함수 본문 전체가 보호 밖으로 나간다. 템플릿의 run_stage도 예외가 아니다
  • 명령이 성공했는데 값이 틀린 경우는 못 잡는다. 그래서 need를 따로 뒀다. 검증은 사람이 쓰는 것이지 옵션이 해 주지 않는다
  • 0건·빈 목록·예상과 다른 형식은 전부 정상적인 성공이다. 「결과가 있어야 한다」는 조건은 직접 써야 한다
  • pipefail 때문에 head로 앞을 끊는 파이프라인이 141로 실패할 수 있다(7절). 그런 자리는 개별 처리한다
  • set -u는 빈 문자열을 막지 않는다. 정의된 빈 변수는 미정의가 아니다
  • 외부 명령이 실패했는데도 0을 돌려주면 셸은 알 길이 없다. 종료 코드가 부정확한 도구는 출력으로 검증해야 한다

마지막으로 자가 점검용 명령 몇 가지다. 기존 스크립트에서 이 글의 함정을 찾을 때 쓴다.

### 선언과 대입이 붙어 있는 자리
$ grep -rnE '(local|declare|typeset|export|readonly)[[:space:]]+[A-Za-z_]+=\$\(' .

### 파이프에 물려 실패가 사라질 수 있는 자리
$ grep -rn '| *tee' .

### 정리 트랩 안의 exit
$ grep -rnE 'trap .*(exit|EXIT)' .

### 안전 옵션이 아예 없는 스크립트
$ grep -rLE 'set -[a-zA-Z]*e' --include='*.sh' .

결론: 감지되지 않은 실패는 실패가 아니라 거짓 성공이다

규칙으로 압축하면 문장 넷이다.

  • set -e는 「맨몸으로 실패한 명령」만 잡는다. 조건·부정·논리 연산·파이프라인 중간은 전부 예외이고, 이것은 버그가 아니라 매뉴얼이 직접 나열한 규정이다
  • 함수를 조건 자리에 넣으면 본문 전체가 보호를 잃는다. 실측에서 함수 안의 실패한 명령 다음 줄이 그대로 실행됐다. 사각지대 중 가장 넓다
  • local·declare·export는 종료 코드를 삼킨다. 다섯 가지 선언 빌트인 전부 0을 돌려줬다. 선언과 대입을 두 줄로 나누는 것만으로 해결된다
  • 가장 위험한 것은 명령이 성공했는데 값이 틀린 경우다. 어떤 set 옵션으로도 잡을 수 없고, 검증은 손으로 쓰는 수밖에 없다

실행으로 확인한 것을 다시 정리하면 이렇다. 사각지대 아홉 개를 한 스크립트에 몰아 넣고 set -e를 켠 채 돌렸더니 하나도 걸리지 않고 끝까지 도달했다. local을 앞에 붙이자 코드 7이 0이 됐고, 다섯 가지 선언 빌트인 모두 같았다. false | tee는 pipefail 없이 성공으로 보고됐다. PIPESTATUS는 다음 echo 한 번에 지워졌다. 정리 트랩 안의 exit 0이 진짜 실패 9를 0으로 덮었다. 그리고 set -euo pipefail에 inherit_errexit까지 켠 스크립트가 빈 값 두 개를 통과시키고 코드 0으로 끝났다.

마지막 사례가 이 글의 요점이다. 안전 옵션은 「명령이 실패했다」를 잡는 장치이지 「결과가 옳다」를 보증하는 장치가 아니다. 이 둘을 같은 것으로 여기는 순간, 옵션을 켰다는 사실 자체가 검증을 건너뛰는 핑계가 된다. 실제로 서론의 스크립트를 쓴 사람은 set -euo pipefail을 붙였기 때문에 값 검증을 생략했을 가능성이 높다.

그래서 순서를 뒤집자. 먼저 무엇이 잘못될 수 있는지 적고, 그것을 검사하는 코드를 쓰고, 그 다음에 안전 옵션을 붙인다. set -euo pipefail은 바닥이지 천장이 아니다. 15절의 표에서 오른쪽 열이 비어 있지 않은 줄이 하나라도 내 스크립트에 있다면, 그 줄이 다음 사고가 날 자리다.

| 2 | 사용법 오류 또는 「차이 있음」 | 관례 | `grep` 오류 |
| 126 | 찾았지만 실행할 수 없음 | POSIX 2.8.2 | 디렉터리 실행 |
| 127 | 명령을 찾지 못함 | POSIX 2.8.2 | 없는 명령 |
| 137 | 128+9, SIGKILL로 종료 | 구현 관례 | `kill -9` |
| 143 | 128+15, SIGTERM으로 종료 | 구현 관례 | `kill -TERM` |
| 141 | 128+13, SIGPIPE | 구현 관례 | `yes | head -1` |
| 256 이상 | 8비트로 잘림 (256은 0이 된다) | 실측 | `exit 256` |

도구별 관례도 있다. `grep` 은 0=찾음, 1=못 찾음, 2=오류다.
「못 찾음」은 정상 결과인데 `set -e` 는 실패로 본다.

## 2. set -e 사각지대 체크리스트

아래는 전부 `set -e` 가 켜진 상태에서 **통과한다**. 실행으로 확인했다.

- [ ] `if cmd; then` 의 조건 → 통과
- [ ] `while cmd; do` 의 조건 → 통과
- [ ] `cmd && ...` 의 왼쪽 → 통과
- [ ] `cmd || ...` 의 왼쪽 → 통과
- [ ] `! cmd` (부정) → 통과
- [ ] 파이프라인의 마지막이 아닌 명령 → 통과 (`false | cat` 은 rc=0)
- [ ] **함수를 `if` 나 `||` 에 넣으면 함수 본문 전체가 무방비** ← 가장 넓은 사각지대
- [ ] `local x=(명령치환)` → `local` 의 코드가 이겨서 rc=0
- [ ] `declare` / `typeset` / `export` / `readonly` 대입 → 전부 rc=0
- [ ] 명령 치환 `( )` 안쪽 → 기본값에서 errexit 미상속
- [ ] 조건 자리에 놓인 서브셸 → 안쪽까지 무방비
- [ ] 함수의 마지막 줄이 `echo` → 항상 0을 반환
- [ ] 서브셸 안의 `exit` → 서브셸만 끝남
- [ ] 정리 트랩 안의 `exit 0` → 모든 실패를 0으로 덮음
- [ ] **명령은 성공했는데 값이 빈 문자열** ← 어떤 옵션으로도 못 잡음

`(( c++ ))` 는 반대 방향의 함정이다. 연산 결과가 0이면 종료 코드 1이라
카운터가 0에서 시작하면 첫 증가에서 스크립트가 죽는다. `(( ++c ))` 를 쓴다.

## 3. 세 옵션이 각각 하는 일

| 옵션 | 잡는 것 | 못 잡는 것 |
|---|---|---|
| `set -e` | 맨몸으로 실패한 명령 | 위 체크리스트 전부 |
| `set -u` | 미정의 변수 참조 | 빈 문자열, 실패한 명령 |
| `set -o pipefail` | 파이프라인 중간의 실패 | SIGPIPE 조기 종료를 실패로 오인 |
| `shopt -s inherit_errexit` | 명령 치환 안쪽 실패 | `local` 이 먼저 삼키면 무효 |
| `set -E` | 함수 안에서 ERR 트랩 발화 | `set -e` 와 같은 사각지대 |

`set -u` 실측 (bash 5.2.37):
- 인자 없을 때의 `"@"` 전체 전개와 빈 배열 전체 전개는 안전
- `"1"` 이나 `arr[0]` 처럼 개별 원소를 집으면 터짐
- 회피는 `${var:-기본값}`. 콜론이 있으면 「없거나 비었으면」, 없으면 「없으면」
- 종료 코드는 이식성 없음: bash 스크립트 1, bash -c 127, dash 2

## 4. PIPESTATUS 는 즉시 저장한다

파이프라인 직후 한 번밖에 못 읽는다. 다음 명령 하나에 덮인다.

```
curl -fsS "url" | gzip -d | psql "dsn"
st=("${PIPESTATUS[@]}")          # 반드시 바로 다음 줄
[ "${st[0]}" -ne 0 ] && echo "다운로드 실패"
[ "${st[1]}" -ne 0 ] && echo "압축 해제 실패"
[ "${st[2]}" -ne 0 ] && echo "적재 실패"
```

## 5. 안전한 템플릿

```
#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true

readonly WORKDIR=(mktemp 결과를 대입)
cleanup() {
    rm -rf "WORKDIR"         # 여기서 exit 를 부르지 않는다
}
trap cleanup EXIT
trap 'echo "실패: line LINENO cmd=[BASH_COMMAND]" >&2' ERR

need() {                      # 성공했어도 값을 검증한다
    local name="1" value="2"
    if [ -z "value" ]; then
        echo "필수 값 없음: name" >&2
        return 3
    fi
}

run_stage() {
    local rc                  # 선언과 대입을 분리
    local out
    out=(명령 실행 결과 대입) || rc=?
    case "rc" in
        0) printf '%s\n' "out" ;;
        *) echo "단계 실패 (rc)" >&2; return "rc" ;;
    esac
}
```

**보장하는 것**: 맨몸 실패에서 정지, 파이프라인 실패 유지, 미정의 변수 차단,
명령 치환 안쪽 실패 감지, 함수 안 ERR 트랩, 임시 디렉터리 정리, 종료 코드 보존.

**보장하지 않는 것**: 함수를 조건에 넣으면 본문 전체가 보호 밖.
값이 비었거나 형식이 다른 경우는 못 잡는다. 0건 결과는 정상적인 성공이다.
`set -u` 는 빈 문자열을 막지 않는다. 종료 코드가 부정확한 외부 도구는 출력으로 검증해야 한다.

## 6. 종료 코드 설계 규약

| 코드 | 뜻 | 호출자가 할 일 |
|---|---|---|
| 0 | 정상 | 통과 |
| 2 | 차이 있음 (검사는 성공) | 내용 확인 후 판단 |
| 1 | 오류 (검사 자체 실패) | 즉시 실패 + 알림 |
| 64+ | 사용법 오류 등 | 호출 방식 수정 |

받는 쪽은 이렇게 쓴다. `|| rc=?` 로 받으면 `set -e` 가 죽이지 않는다.

```
rc=0
out=(검사 명령 실행) || rc=?
case "rc" in
  0)  echo "PASS" ;;
  2)  echo "DRIFT" ;;
  1)  echo "ERROR" ;;
  *)  echo "UNKNOWN" ;;
esac
exit "rc"
```

`|| true` 는 쓰지 않는다. 「실패해도 된다」가 아니라
「어떻게 끝났는지 영원히 모르겠다」는 선언이 된다.

## 7. POSIX sh 와의 차이

| 기능 | bash 5.2.37 | dash |
|---|---|---|
| `set -o pipefail` | 동작 | **없음** |
| `PIPESTATUS` | 동작 | **없음** |
| 배열 | 동작 | **없음** |
| `trap ... ERR` | 동작 | **없음** |
| `trap ... EXIT` | 동작 | 동작 |
| 프로세스 치환 | 동작 | **없음** |
| `local` | 동작 | 동작 |
| `local` 의 코드 삼킴 | rc=0 | **rc=0 (동일)** |
| `set -e` + 함수 + `if` | 통과 | 통과 (동일) |
