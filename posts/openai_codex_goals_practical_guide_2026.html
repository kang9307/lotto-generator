서론: Codex Goals는 무엇이고 지금 어디까지 왔나

Codex Goals는 Codex에 「끝났을 때 참이어야 할 상태」를 한 번 정해 두면, 그 목표를 스레드에 저장해 두고 여러 턴에 걸쳐 계속 작업하게 하는 기능입니다. 시작은 /goal 명령 하나입니다. 처음 들어온 것은 2026년 4월 30일 공개된 Codex CLI 0.128.0이었고(당시 실험 기능), 2026년 5월 21일 0.133.0에서 기본으로 켜지면서 실험 기능 표시가 빠졌습니다. 이 글이 처음 나간 2026년 5월 20일은 그 사이였습니다. 한국 개발자 커뮤니티 GeekNews(news.hada.io)에서도 빠르게 화제가 됐고, goal-setter 같은 외부 wrapper 도구가 소개되면서 "이거 진짜로 써먹을 만한가"라는 실용적 질문이 나왔습니다.

본 글은 OpenAI 공식 문서를 그대로 옮긴 가이드가 아닙니다. Codex Goals가 어떤 작업에 도움이 되고, 어디서 헛돌기 쉬우며, Claude Code의 작업 방식과 무엇이 다른가를 실무 관점에서 풀어쓴 분석입니다. 2026-09-29 갱신에서는 작동 방식 설명을 OpenAI 공식 문서와 GitHub 릴리스 노트에 맞춰 다시 썼습니다. 결론을 먼저 말하면, 완료 조건을 테스트·측정값으로 판정할 수 있는 마이그레이션·리팩터링에는 잘 맞고, 「무엇이 끝인지」를 말할 수 없는 작업에는 맞지 않습니다.

1. Codex Goals 등장 배경 - 단발성 생성의 한계

2023~2024년 GPT-4 시대의 코딩 어시스턴트는 본질적으로 "함수 한 개씩 짜주는 친구"였습니다. "JWT 디코더 함수 만들어줘"라고 하면 깔끔한 파이썬을 뽑아주지만, 그 함수가 우리 리포의 인증 미들웨어 어디에 들어가야 하고, 기존 세션 처리 코드와 어떻게 충돌하는지는 모릅니다. 결국 사용자가 매번 컨텍스트를 다시 설명해야 했습니다.

2025년 Cursor·Windsurf·Claude Code 같은 도구가 널리 쓰이면서 리포 전체를 컨텍스트로 보는 능력은 크게 향상됐습니다. 그러나 여전히 사용자가 "이걸 해라, 다음은 저걸 해라"라고 단계별로 지시해야 했습니다. 이 단계별 지시 비용이 누적되면 막상 AI를 쓰는 시간이 직접 짜는 시간보다 길어지는 역설이 생깁니다.

Codex Goals는 이 한계를 「목표와 완료 조건을 한 번 정해 두면, 다음 단계는 Codex가 진행 상황을 보며 정한다」는 방식으로 다룹니다. OpenAI 쿡북은 Goals를 결승선은 분명하지만 거기까지 가는 길이 불확실할 때 쓰라고 안내합니다. 프로파일링, 패치, 벤치마크, 불안정한 테스트 재현처럼 다음 단계가 앞 단계에서 알게 된 것에 따라 달라지는 작업이 그 예로 나옵니다.

2. Goals 기능의 작동 방식 (공식 문서 기준)

발행 당시 이 절은 「목표 입력 → 체크리스트 형태의 자동 sub-task 분해(4~10개) → 일정 횟수 실패 시 에스컬레이션하는 검증 루프 → 회고 리포트」의 4단계로 설명했습니다. 2026-09-29에 OpenAI 공식 문서와 대조해 보니 체크리스트식 자동 분해, 실패 횟수 기준 에스컬레이션, 회고 리포트는 공식 문서에서 확인되지 않았습니다. 공식 문서가 설명하는 흐름은 다음과 같습니다.

  1. 목표 설정: /goal <목표>로 목표를 정합니다. 공식 예시는 /goal Finish the migration and keep tests green입니다.
  2. 상태 확인과 조작: /goal만 입력하면 현재 목표를 보여 주고, /goal pause·/goal resume·/goal clear로 일시정지·재개·해제합니다.
  3. 턴을 넘어 계속: 목표는 스레드에 저장되어 여러 턴에 걸쳐 유지됩니다. 다만 다른 턴이 진행 중이거나, 사용자 입력이 대기 중이거나, 스레드의 다른 작업이 남아 있으면 이어서 진행하지 않습니다.
  4. 멈추는 조건: 성공, 일시정지, 해제, 중단, 예산 한도, 사용자 입력이 필요한 막힘 가운데 하나에 이르면 멈춥니다.
  5. 켜기: 0.133.0부터 기본으로 켜져 있습니다. 슬래시 명령 목록에 /goal이 보이지 않으면 config.toml에 features.goals = true를 넣거나 codex features enable goals를 실행하라고 공식 문서가 안내합니다.

핵심은 검증 기준을 누가 정하느냐입니다. 공식 쿡북은 좋은 목표에 들어갈 요소로 여섯 가지를 듭니다. 끝났을 때 참이어야 할 결과(Outcome), 그것을 증명할 테스트·벤치마크·보고서 같은 검증 수단(Verification surface), 작업 중 퇴행하면 안 되는 제약(Constraints), 써도 되는 파일·도구·저장소의 범위(Boundaries), 매 시도 뒤 다음 시도를 정하는 방식(Iteration policy), 더 갈 길이 없을 때 멈추고 보고할 조건(Blocked stop condition)입니다. 즉 검증 루프는 시스템이 알아서 만들어 주는 것이 아니라 사용자가 목표 문장에 적어 넣는 것입니다.

ChatGPT 데스크톱 앱의 슬래시 명령 문서는 /goal을 「지속적인 목표를 정하는 명령」으로 설명하며, /plan으로 먼저 목표를 다듬으라고 안내합니다. 목표가 진행 중이면 입력창 위에 진행 상황과 일시정지·재개·편집·해제 버튼이 표시됩니다. 계획을 먼저 세우는 방식의 장단은 계획 모드는 죽었는가에서 따로 다뤘습니다.

3. 실전 시나리오 3종 (직접 구성한 예시)

아래는 OpenAI 공식 예제가 아니라 한국 SI·스타트업·사이드 프로젝트에서 자주 등장하는 패턴을 가정해 만든 예시입니다. 발행 당시에는 「예상 sub-task 분해」로 소개했지만, Codex가 목표를 이런 목록으로 쪼개 보여 준다는 공식 설명은 없습니다. 아래 목록은 사람이 작업 순서를 미리 그려 본 것이고, 목표 문장에는 완료 조건과 검증 수단을 함께 적었습니다.

시나리오 A. 레거시 REST API v1 → v2 마이그레이션

목표: "v1 REST API를 v2로 이전. 기존 v1 클라이언트는 6개월간 호환 유지. 기존 통합 테스트가 v1·v2 양쪽에서 통과하면 완료."

작업 흐름 예시(가정):

  1. 기존 v1 엔드포인트 전수 스캔 (routes/v1/*.py 등 파일 목록 추출)
  2. v1과 v2의 차이점 매트릭스 생성 (요청·응답 스키마 비교표)
  3. v2 라우터 스캐폴딩 생성 (FastAPI prefix=/v2)
  4. v1→v2 어댑터 레이어 작성 (구 클라이언트가 v1 호출하면 내부적으로 v2 호출)
  5. 호환성 테스트 케이스 추가 (기존 통합 테스트 케이스를 v2 prefix로 복제)
  6. 마이그레이션 가이드 마크다운 문서 작성

주의: 어댑터 레이어에 잘못된 매핑이 들어가면 운영 사고로 직결되므로, 이 부분만은 별도로 사람이 코드 리뷰해야 합니다.

시나리오 B. JWT 인증 → 세션 기반 인증 전환

목표: "사용자 인증을 JWT 토큰 방식에서 세션 쿠키 방식으로 전환. Redis 세션 스토어 사용. 로그인·로그아웃 통합 테스트가 통과하면 완료."

작업 흐름 예시(가정):

  1. 현재 JWT 발급·검증 코드 위치 식별
  2. Redis 클라이언트 모듈 추가 + 연결 설정
  3. 세션 ID 생성·저장·검증 로직 구현
  4. 기존 JWT 검증 미들웨어를 세션 검증 미들웨어로 교체
  5. 로그인·로그아웃 엔드포인트 수정 (토큰 응답 → Set-Cookie)
  6. 프론트엔드 호출부 수정 사항 정리 (Authorization 헤더 제거 + credentials 옵션)
  7. 마이그레이션 전략 문서 (점진 전환·일괄 전환 옵션 비교)

주의: 이 작업은 보안 사고 위험이 크기 때문에 자동 테스트 통과만으로는 불충분합니다. 별도 보안 리뷰가 필요한 영역까지 목표에 넣어 맡기지 마세요.

시나리오 C. 타입 안전성 95% 이상 끌어올리기

목표: "TypeScript 타입 커버리지를 60%에서 95% 이상으로. any 타입 제거 우선. type-coverage 결과 95% 이상이고 기존 테스트가 계속 통과하면 완료."

작업 흐름 예시(가정):

  1. type-coverage 도구 실행 결과 분석 (현재 커버리지 측정)
  2. any 사용 위치 우선순위 매기기 (라이브러리 경계 > 핵심 비즈니스 로직 > 테스트 코드)
  3. 외부 라이브러리 타입 정의 보강 (@types 추가 또는 ambient 선언)
  4. 유틸 함수 시그니처 명시 (제네릭 도입 가능 지점 추출)
  5. strict mode 점진 활성화 (noImplicitAny → strictNullChecks → strict 전체)
  6. 최종 커버리지 측정 + 미해결 any 목록 보고

이 시나리오는 Goals의 설계와 가장 잘 맞는 유형입니다. 완료 조건을 숫자로 적을 수 있어서, 멈출 때와 계속할 때를 판정하기 쉽습니다.

5. 실무 도입 시 주의점

Codex Goals를 처음 쓸 때 흔히 빠지는 함정 4가지입니다.

  • 목표를 너무 넓게 잡는다: "전체 코드베이스를 깨끗하게 만들어라" 같은 목표는 끝을 판정할 방법이 없어 멈출 근거도 없습니다. 공식 문서도 시작 전에 「완료가 무엇인지」를 정하라고 합니다. 한 번의 Goal은 완료를 테스트나 측정값으로 말할 수 있는 단위로 좁히는 것이 안전합니다.
  • 검증 수단 없이 맡긴다: 테스트 없는 리포지토리에서는 목표를 이뤘는지 확인할 방법이 없어 잘못된 방향으로 계속 갈 수 있습니다. 도입 전 최소한의 통합 테스트나 측정 명령이 있어야 합니다.
  • 민감 정보 노출 위험: API 키·DB 비밀번호가 평문으로 코드에 박혀 있는 리포에서는 작업 중 그 값이 외부 모델에 전송될 위험이 있습니다. .gitignore·환경변수 사용을 먼저 점검한 뒤 도입하세요.
  • 롤백 계획 부재: 긴 작업이 끝난 뒤 결과가 마음에 들지 않을 때, 별도 브랜치에서 작업하지 않았다면 되돌리기 어렵습니다. 반드시 새 브랜치를 만들고 시작하고, 건드려도 되는 범위(Boundaries)를 목표 문장에 적어 두세요.
권장 워크플로: 작게 시작 → 결과 검증 → 점진적 확대. 첫 도입은 "테스트 코드 추가"처럼 위험 낮고 완료 조건이 분명한 작업부터 시작하면 학습 곡선이 부드럽습니다.

6. 한국 개발자 실무 시나리오별 적합성

6.1 정부·공공 SI 프로젝트

외부 AI 서비스 사용이 보안 정책상 차단되는 경우가 많습니다. 망분리 환경에서 Codex Goals를 그대로 쓰기는 어렵고, 온프레미스 대안(예: 로컬 LLM 기반 자체 에이전트)을 검토해야 합니다. 다만 RFP 작성·기술 명세 초안 같은 비코드 작업에는 부분적으로 유용할 수 있습니다.

6.2 스타트업·B2B SaaS

효과를 보기 쉬운 영역입니다. 시니어 1명의 시간을 아끼는 가치가 크기 때문입니다. 다만 "개발 속도 자체보다 코드 품질 일관성"이 더 중요한 시점에 도입하는 것이 효과적입니다. MVP 시점에는 과할 수 있고, 기술 부채를 정리하는 시점에 쓸모가 커집니다.

6.3 사이드 프로젝트·1인 개발

가성비는 사용 패턴에 달려 있습니다. Codex는 ChatGPT 요금제에 포함되어 쓰는 방식이 기본이며, 발행 당시 적었던 「Goal 단위 부가 비용」은 공식 문서에서 확인되지 않았습니다. 다만 공식 문서가 멈추는 조건 가운데 하나로 예산 한도를 들고 있으므로, 긴 목표를 걸기 전에 이번 작업에 쓸 예산을 먼저 정해 두는 편이 안전합니다. 이미 쓰는 도구가 있다면 완료 조건이 분명한 큰 작업에서만 Goals를 시험해 보는 방식이 부담이 적습니다.

7. goal-setter 같은 외부 wrapper 도구와 선택지

커뮤니티가 만든 goal-setter 같은 wrapper는 발행 당시 GeekNews에서 소개됐습니다. 이 글은 처음에 그것을 「OpenAI API 직접 호출과 Codex Goals 사이의 추상화 레이어」로 설명했지만, 이번 갱신에서 그 도구의 현재 상태와 기능은 확인하지 못했습니다. 대신 선택지를 공식 문서로 확인되는 사실 기준으로 다시 나눕니다.

목표 기반 작업을 돌리는 방식은 다음 셋으로 나눌 수 있습니다.

  • API 직접 호출: 목표 유지·반복·멈춤 판단 로직을 직접 구현해야 합니다. 도구를 만드는 데 시간이 듭니다.
  • Codex Goals: 목표 저장, 턴을 넘어 이어 가기, 일시정지·재개·해제가 Codex에 들어 있어 바로 시작할 수 있습니다. 검증 기준은 여전히 사용자가 목표 문장에 적어야 합니다.
  • wrapper 도구: 목표 문장 작성이나 비용 추정을 돕는 보조 도구입니다. 쓰기 전에 어떤 권한으로 무엇을 실행하는지 저장소에서 직접 확인하세요.

외부 도구를 Codex에 붙이는 공식 경로는 MCP입니다. Codex는 config.toml의 [mcp_servers.이름] 표와 codex mcp 명령으로 MCP 서버를 연결하도록 문서화되어 있어, Claude Code의 MCP 생태계와 같은 표준 위에서 비교할 수 있습니다.

8. 결론 - 누가 써야 하고 누가 미뤄야 하는가

잘 맞는 대상:

  • 마이그레이션·대규모 리팩토링 빈도가 높은 시니어 개발자
  • 레거시 코드베이스를 모던하게 전환해야 하는 팀 리드
  • 혼자서 여러 리포를 관리하는 1인 인프라 운영자

당장은 미룰 대상:

  • 단발 함수 작성이 주력인 주니어 (과한 도구·학습 기회 감소)
  • 테스트 코드가 거의 없는 리포 (완료를 판정할 수단이 없음)
  • 망분리·보안 규제로 외부 AI 사용이 차단된 환경

당시 전망(2026년 5월): Codex Goals와 Claude Code task의 기능 격차는 점점 줄어들 것이고, 선택의 결정 요인은 "기능"보다 "가격 정책의 안정성"이 될 가능성이 높다고 봤습니다. 2026-09-29 시점에서 보면 Goals는 5월 21일 기본 기능이 됐고, Codex 앱은 ChatGPT 데스크톱 앱으로 합쳐졌습니다. Codex도 ChatGPT 요금제에 포함되어 쓰는 방식이 기본이어서, 당시 적었던 「정액제 대 사용량 기반」이라는 구도는 정확하지 않았습니다.

마지막으로, 어떤 도구를 선택하든 "검증 기준을 직접 설계할 수 있는 역량"이 가장 중요합니다. 공식 문서가 좋은 목표의 요소로 결과·검증 수단·제약·범위를 먼저 드는 것도 같은 이유입니다. 도구가 자율적으로 일할수록 사람의 역할은 "지시"가 아니라 "완료 기준 설계"로 옮겨 갑니다. 모델을 바꿀 때 기존 지시문이 그대로 통하지 않는 문제는 설정을 그대로 옮기면 생기는 일에서 따로 다뤘습니다.

# Codex Goals 점검표 - 목표를 걸기 전에 확인할 것

기준일: 2026-09-29.
아래 값은 OpenAI 공식 문서(Cookbook 「Using Goals in Codex」, 「Follow a goal」, ChatGPT 데스크톱 앱 슬래시 명령 문서, Codex MCP 문서)와 openai/codex GitHub 릴리스 노트·README에서 확인한 것이다. 가격은 적지 않았다.

---

## 1. 명령과 설정

| 하고 싶은 것 | 명령·설정 | 비고 |
|---|---|---|
| 목표 정하기 | `/goal <목표>` | 공식 예시: `/goal Finish the migration and keep tests green` |
| 현재 목표 보기 | `/goal` | |
| 일시정지 / 재개 / 해제 | `/goal pause` / `/goal resume` / `/goal clear` | |
| `/goal`이 목록에 없을 때 | `config.toml`에 `features.goals = true` 또는 `codex features enable goals` | 0.133.0부터 기본으로 켜져 있음 |
| 외부 도구 연결 | `config.toml`의 `[mcp_servers.이름]` 표, `codex mcp` 명령 | MCP |

## 2. 버전과 제공 환경

| 항목 | 확인된 내용 |
|---|---|
| 처음 들어온 버전 | Codex CLI 0.128.0 (2026-04-30, 실험 기능) |
| 기본 활성화 | Codex CLI 0.133.0 (2026-05-21, 실험 기능 표시 해제) |
| 쓸 수 있는 곳 | Codex CLI, ChatGPT 데스크톱 앱의 Codex (`/plan`으로 다듬은 뒤 `/goal` 권장) |
| 확인 못 함 | IDE 확장·Codex 웹(클라우드 작업)에서의 `/goal` 지원 |
| 요금제 | ChatGPT 계정 로그인 후 Plus·Pro·Business·Edu·Enterprise 요금제로 사용. Goal 단위 별도 과금 설명은 공식 문서에서 찾지 못함 |

## 3. 목표 문장 점검표 (공식 권장 6요소)

- [ ] **결과(Outcome)**: 끝났을 때 무엇이 참이어야 하는지 한 문장으로 적었다
- [ ] **검증 수단(Verification surface)**: 그것을 증명할 테스트·벤치마크·명령 출력·보고서를 지정했다
- [ ] **제약(Constraints)**: 작업 중 퇴행하면 안 되는 것(기존 테스트 통과 등)을 적었다
- [ ] **범위(Boundaries)**: 써도 되는 파일·도구·저장소를 적었다
- [ ] **반복 방식(Iteration policy)**: 매 시도 뒤 다음 시도를 어떻게 정할지 적었다
- [ ] **막힘 시 정지 조건(Blocked stop condition)**: 더 갈 길이 없을 때 멈추고 보고하라고 적었다

## 4. 시작 전 점검

- [ ] 리포에 최소한의 통합 테스트나 측정 명령이 있다 (없으면 완료를 판정할 수 없다)
- [ ] 새 브랜치에서 시작한다
- [ ] API 키·DB 비밀번호가 코드에 평문으로 없다 (.gitignore·환경변수 확인)
- [ ] 보안 리뷰가 필요한 부분은 목표에서 뺐다
- [ ] 이번 작업에 쓸 예산을 먼저 정했다 (예산 한도는 공식 문서가 드는 정지 조건 중 하나)

## 5. 멈추는 조건 (공식 문서)

| 조건 | 뜻 |
|---|---|
| 성공 | 목표 달성 |
| 일시정지 / 해제 | 사용자가 `/goal pause` 또는 `/goal clear` |
| 중단 | 실행이 중단됨 |
| 예산 한도 | 정해진 예산에 도달 |
| 막힘 | 사용자 입력이 필요한 상황 |

다른 턴이 진행 중이거나, 사용자 입력이 대기 중이거나, 스레드의 다른 작업이 남아 있으면 이어서 진행하지 않는다.

## 6. 맞는 작업 / 맞지 않는 작업

| 맞는 작업 | 맞지 않는 작업 |
|---|---|
| 결승선은 분명하고 경로는 불확실한 작업 | 「무엇이 끝인지」 말할 수 없는 작업 |
| 레거시 API 마이그레이션, 타입 커버리지 향상 | "전체 코드베이스를 깨끗하게" 같은 넓은 목표 |
| 성능 개선, 불안정한 테스트 재현 | 테스트가 거의 없는 리포 |

복사해서 메모 앱이나 AI 도구에 그대로 붙여 넣으세요.
