계기 — #[derive(...)]가 암묵적으로 붙이는 #[inline]의 발견

Rust 에서 Debug·Display·Clone 같은 핵심 트레이트를 구현하는 가장 흔한 방법은 #[derive(...)] 이다. yossarian 은 2026년 10월 3일자 TIL 에서 Rust 가 현재 이 파생 코드의 일부로 #[inline] 을 함께 내보낸다고 적는다. 그는 이것이 보장된 동작처럼 보이지는 않지만 reference 의 예시가 암시하고 있고, 매크로를 확장해 보면 직접 볼 수 있다고 덧붙인다. 실제로 Rust Reference 의 derive 장에서 #[automatically_derived] 를 설명하는 예시에도 Clone 구현 위에 #[inline] 이 붙어 있다.

원문은 이 동작을 문제 삼는 글이 아니다. 오히려 거의 언제나 원하는 동작이라고 평가한다. #[inline] 은 힌트일 뿐이고, 파생된 Debug·Clone 구현은 대개 내용이 사소해서 인라인의 이득을 본다는 것이다. 다만 항상 그렇지는 않다는 반례로 필드가 많고 여러 층으로 감싸인 오류 계층을 든다. 그런 타입의 Debug 구현이 로깅 호출마다 인라인되면 코드가 늘어난다는 것이 글의 요점이다.

자료는 세 층으로 나뉜다. 원문이 직접 말한 것(확장 결과와 uv 의 약 160KB), PR 페이지에 남은 기록(PR #117727·#118031. 원문에는 이 번호가 나오지 않는다), 현재 rustc 소스에서 직접 읽은 사실이다. 해석은 층이 만나는 곳에서만 붙이고, 누구의 말인지는 문장마다 밝힌다.

매크로 확장으로 확인하는 자동 생성 코드의 실체

확인 방법은 원문이 이미 알려 준다. 매크로를 확장해 보면 된다. 원문은 가장 단순한 구조체에서 시작한다.

#[derive(Debug)]
                    struct Widgets {
                        foo: u32,
                        bar: usize,
                    }

원문은 이것을 Playground 에서 확장하면 다음 구현이 나온다고 보여 준다.

struct Widgets {
                        foo: u32,
                        bar: usize,
                    }
                    #[automatically_derived]
                    impl ::core::fmt::Debug for Widgets {
                        #[inline]
                        fn fmt(&self, f: &mut ::core::fmt::Formatter) -> ::core::fmt::Result {
                            ::core::fmt::Formatter::debug_struct_field2_finish(
                                f,
                                "Widgets",
                                "foo",
                                &self.foo,
                                "bar",
                                &&self.bar,
                            )
                        }
                    }

눈여겨볼 곳은 fmt 바로 위의 #[inline] 이다. 개발자가 쓰지 않았는데도 derive 가 이를 붙였다. 본문 전체는 debug_struct_field2_finish 호출 하나이고, 마지막 필드에만 참조가 한 겹 더 붙는다(&&self.bar). rustc 소스의 주석에 따르면 크기를 모르는(unsized) 타입은 참조를 한 겹 더 요구하는데 그런 타입이 올 수 있는 자리가 마지막 필드뿐이기 때문이다.

#[inline] 이 정확히 무엇을 하는지는 출처마다 말이 조금씩 다르다. 원문은 이것을 그냥 힌트(just a hint)라고 부른다. Lobste.rs 토론에서 tsion 은 힌트만은 아니라고 반박한다. 제네릭 함수는 언제나 크레이트 경계를 넘어 인라인될 수 있지만 제네릭이 아닌 함수는 기본적으로 그럴 수 없는데, #[inline] 이 그것을 가능하게 한다는 것이다. PR #117727 의 댓글에서 saethlin 도 비슷하게 설명한다. 이 속성은 LLVM 에 inlinehint 를 달 뿐이고 실제 인라인은 LLVM 재량이지만, 그와 함께 함수가 MIR 인라이닝의 후보가 되고, 지연되어 lowering 되며, 경우에 따라서는 여러 번 lowering 된다고 한다.

범위도 짚어 둔다. Rust Reference 는 내장 derive 로 Clone·Copy·Debug·Default·Eq·Hash·Ord·PartialEq·PartialOrd 아홉 가지를 꼽고, 이들이 만드는 구현에는 automatically_derived 속성이 붙는다고 적는다. 아주 작은 함수에는 컴파일러가 알아서 #[inline] 을 붙이는지에 대해서는 Lobste.rs 에서 ralfj 가 그렇다고 답한다. 정말 작은 함수에는 자동으로 붙는다는 것이다.

중첩된 오류 타입과 인라인 팽창의 구조

필드가 둘인 구조체의 Debug 는 본문이 호출 하나뿐이라 인라인해도 부담이 없다. 원문은 그런 경우만 있는 것이 아니라며 다음과 같은 오류 계층을 상상해 보라고 한다.

  • ErrorA: String 필드 7개(lots, of, chunky, fields, within, this, type)를 가진 구조체.
  • ErrorB: ErrorA 를 inner 필드로 가진 구조체.
  • ErrorC: ErrorB 를 inner 필드로 가진 구조체.
  • Errors: A(ErrorA), B(ErrorB), C(ErrorC) 세 변형을 가진 열거형.
  • Default: 원문의 확장 결과에는 ErrorA 에 대한 default 구현만 나타나며 여기에도 #[inline] 이 붙어 있다. 입력 코드의 derive 줄에는 Debug 만 적혀 있어 원문 안에서 입력과 출력이 어긋나 있다.

원문이 보여 주는 확장 결과에서 ErrorA 의 fmt 는 필드 이름 슬라이스 배열(names)과 &dyn Debug 값 배열(values)을 만든 뒤 debug_struct_fields_finish 를 호출한다. ErrorB 와 ErrorC 는 debug_struct_field1_finish 한 번이고, Errors 는 match 로 갈라져 변형마다 debug_tuple_field1_finish 를 부른다. 필드 7개짜리만 배열을 쓰는 이유는 rustc 소스에 있다. deriving/debug.rs 의 CUTOFF 상수가 5이고, 필드가 5개 이하이면 배열 없이 필드 수에 맞는 전용 메서드(debug_struct_field2_finish 처럼)를 부르고 5개를 넘으면 배열을 만드는 방식을 쓴다.

원문의 우려는 이 코드가 Errors 의 Debug 가 호출되는 곳마다 인라인될 수 있다는 점이다. 원문은 그런 호출이 예컨대 debug 나 trace 로깅에서 반복해서 일어날 수 있다고 적는다. 각주는 이 계층이 크게 단순화한 것이고 실제 Rust 응용에는 필드가 적지 않은, 깊게 중첩된 오류 열거형이 흔하다고 덧붙인다. 원문이 이 인라인으로 어떤 어셈블리가 몇 줄 늘어나는지는 보여 주지 않는다.

uv 사례에서 나타난 약 160KB 절감과 측정의 전제 조건

원문의 핵심 수치는 한 문장이다. 이 정도 코드면 Rust 바이너리 전체 크기에서 무시할 수 없는 몫이 될 수 있고, uv 에서 rustc 가 특정 Debug 구현을 인라인하지 못하게 막자 바이너리가 약 160KB 줄었다는 것이다. 원문의 표현은 「a given Debug implementation」 이다. 즉 이 160KB 는 Debug 구현 전반이 아니라 지정한 구현에 대한 값이다.

해결 방법은 각주에 있다. 팀은 derive(Debug)와 똑같이 동작하되 #[inline(never)] 를 붙이는 자체 proc-macro 를 추가했다. 160KB 는 분모가 없는 절대값이기도 하다. 원문이 uv 바이너리의 전체 크기를 적지 않았으므로 비율로 환산할 수 없다. 원문이 놀랐다고 적은 지점은 크기 비용이 빠르게 쌓인다는 것과 rustc 가 (겉보기에는) 인라인의 크기·횟수에 한도를 두지 않았다는 것 두 가지이고, 곧바로 이것이 많은 프로그램에서는 옳은 결정일 것이라고 의심한다고 덧붙인다. 컴파일러 기본값을 비판하는 글이 아니라 한 사례의 보고인 셈이다.

컴파일러 관점의 트레이드오프 — 2023년 PR과 벤치마크

derived Debug 에 #[inline] 을 넣은 변경은 rust-lang/rust 의 PR #117727(제목 「Emit #[inline] on derive(Debug)」)이다. 이 PR 은 saethlin 이 2023년 11월 8일에 열었고 이튿날 9일에 머지되었다. 원문은 이 PR 을 언급하지 않으므로 아래는 모두 PR 페이지 기준이다. PR 본문은 짧다. PR #116583 을 작업하다가 cross_crate_inlinable 쿼리가 파생된 Debug impl 을 다수 「호출 하나에 불과한(little more than a call) MIR 본문」으로 식별하는 것을 보았고, 그렇다면 #[inline] 의 좋은 후보일 수 있어 그 변경을 따로 구현했으며, build times 가 눈에 띄게 좋아지는 것으로 보인다고 적는다. 아래의 비교 수치는 rust-timer 봇이 PR 의 try 빌드를 rustc-perf 로 돌려 부모 커밋과 비교한 것이다. 봇은 instruction count 를 전체 판정에 쓴 신뢰도 높은 지표라고 하고, max RSS·cycles·바이너리 크기는 판정에 쓰지 않은 덜 믿을 만한 지표라고 밝힌다.

  • perf 결과: 첫 try 빌드의 instruction count 에서 primary 벤치마크 111건 중 107건이 개선(평균 -2.4%)이고 4건이 회귀(평균 +0.5%)였다. 봇의 총평은 회귀와 개선이 섞였다는 것이다. 바이너리 크기 지표는 primary 에서 개선 113건(평균 -2.7%), 회귀 26건(평균 +0.9%)이다. instruction count 의 secondary 에서는 개선 163건(평균 -3.4%), 회귀 4건(평균 +2.7%)이다. 부트스트랩은 663.159초에서 673.479초로 1.56% 느려졌고 산출물 크기는 308.75MiB 에서 308.99MiB 로 0.08% 커졌다.
  • 리뷰어 nnethercote 의 반응: fmt 에 인라인을 달지 않았던 것은 의도였다(뜨거운 코드가 아니니 인라인되지 않아야 한다는 생각)고 밝힌다. 그러나 perf 결과를 반박할 수 없다며 「faster and smaller binaries」 라고 쓰고, 부트스트랩이 10초 느려지고 컴파일러 산출물이 약간 커진 점은 의아하다고 덧붙인다.
  • 원인 가설: Noratrieb 은 속도 향상의 이유가 단순할 것이라 짐작한다. #[inline] 이 붙은 함수는 다운스트림에서 코드가 생성되고, 죽은 코드라면 아예 생성되지 않는데 Debug impl 은 죽은 코드인 경우가 많다는 것이다. hello world 벤치마크의 링크 시간이 크게 줄어든 것을 근거로 든다. 이것은 PR 본문이 아니라 댓글에 있는 가설이다.
  • 다른 가설: scottmcm 은 debug_tuple_field4_finish 같은 도우미 함수로 옮겨 간 결과라고 본다. 도우미들은 #[inline] 이 아니므로 인라인되는 fmt 는 포인터 투영과 vtable 포인터 복사 후 호출 하나만 하는 얇은 함수라는 가설이다. 그는 코드 생성을 하지 않는 check 빌드가 왜 그렇게 빨라지는지는 의아하다고도 적는다.
  • 머지 후: 머지 뒤의 perf 실행에서도 primary instruction 회귀 5건(평균 3.1%, 최대 13.7%)과 개선 110건(평균 -2.3%)이 섞였다. saethlin 은 큰 회귀가 수집기 지연 때문인 것 같다고 보고 perf-regression-triaged 라벨을 붙였다.

필드 수에 따라 구분하자는 제안은 머지 후 PR #117727 의 댓글에서 나왔다. RalfJung 이 필드 5개 이하의 구조체에만(열거형과 더 큰 구조체는 제외하고) 속성을 붙이면 어떻겠느냐고 물었고, saethlin 이 11월 18일에 PR #118031 로 시험했다. 이 PR 의 실제 제목은 「Try not applying #[inline] to big structs」 이고 상태는 머지되지 않은 채 닫힘이다. 변경은 필드가 5개를 넘는 구조체에서만 #[inline] 을 빼고 열거형은 그대로 두는 것이었다. 결과는 전 항목 회귀였다. instruction count 의 primary 에서 회귀 54건(평균 +1.5%)에 개선은 0건이었고, 같은 실행에서 cycles 는 primary 회귀 33건(평균 +2.3%)에 개선 0건, 바이너리 크기는 primary 회귀 66건(평균 +2.4%)에 개선 4건(-0.2%)이었고 부트스트랩 시간은 거의 같았다(-0.19%). saethlin 은 「huge regression」 이라고 답한 뒤 죽은 코드 효과와 MIR 최적화 효과가 둘 다 중요한 것 같다고 정리했다. 따라서 필드 5개 이하라는 기준은 머지된 정책이 아니라 시도하고 닫은 실험의 임계값이다.

두 PR 을 나란히 놓으면 알 수 있는 것이 있다. 둘 다 같은 벤치마크 모음으로 판정했고 어느 쪽도 uv 같은 모양의 바이너리를 재지는 않았다. PR #117727 의 바이너리 크기 지표도 벤치마크에 따라 개선과 회귀가 섞여 있으므로, 모음 전체의 개선과 특정 프로그램 하나에서의 160KB 절감은 서로 모순되지 않는다.

같은 현상을 두고 Lobste.rs 에서도 가설이 나왔다. ralfj 는 많은 Debug impl 이 한 번도 호출되지 않으며 #[inline] 을 붙이면 아예 코드 생성을 피하게 되는 것이 이유의 일부일 것이라고 추측한다. Noratrieb 의 가설과 같은 방향이다. evmar 는 호출되지 않는 함수라면 최종 바이너리에서 어차피 빠지는 것이 아니냐며, 컴파일 시간에는 영향이 있겠지만 실행 시간과는 어떻게 이어지는지 묻는다. yshui 는 이것이 Rust 의 proc macro 가 실제 타입이 아니라 토큰 위에서 동작하는 데서 오는 한계라고 본다. 타입 정보가 있었다면 중첩된 깊이를 보고 너무 깊을 때 #[inline] 을 붙이지 않을 수 있었을 것이라는 이야기다. 모두 가설이거나 질문이다.

derive별 동작과 바이너리 크기 영향 비교

현재 rustc 소스(compiler/rustc_builtin_macros/src/deriving/)를 보면 각 내장 derive 가 생성하는 메서드에 #[inline] 이 붙는지 알 수 있다. 소스에서 읽히는 것은 속성의 유무이고, 이 인라인이 바이너리 크기에 얼마나 영향을 주었는지는 원문도 PR 도 derive 별로 보여 주지 않는다.

derive#[inline] 이 붙는 생성 메서드확인 근거원문·PR 에서 확인하지 못한 것
Debugfmt원문의 확장 결과, PR #117727, 소스 debug.rs호출 지점 수에 따른 크기 변화(uv 의 160KB 외)

표에서 눈에 띄는 것은 Eq 의 경우다. 소스 주석은 이 메서드가 한 번도 호출되지 않으므로 #[inline] 으로 코드 생성을 피하는 것이 목적이라고 설명하며, 같은 속성이 다른 derive 에서는 성격이 다르다는 점을 보여 준다. 또 Lobste.rs 에서 kornel 은 Ord 와 Eq, 어쩌면 Clone 에 인라인이 붙는 것은 예상하지만 Debug 에 붙는 것은 의외라고 적고, 자신은 fmt 구현에 #[cold] 를 붙인다고 밝혔다. 같은 토론에서 ralfj 는 인라인 기본값 선택이 코드 크기·컴파일 시간·실행 시간 사이의 균형이라 어렵다고 설명한다. 원문 저자도 같은 취지로, 완벽한 기본값이나 휴리스틱은 없다고 본다고 답했다.

원문과 토론이 말하는 대처

원문이 직접 제시한 대처는 하나이고, 나머지는 같은 주제의 토론에서 나온 의견이다. 아래는 모두 누가 말했는지를 붙여 적는다. 일반적인 크기 줄이기 요령은 원문과 PR 어디에도 없었으므로 넣지 않았다.

  • 확장해 보기: 원문이 쓴 방법이다. Playground 나 매크로 확장 도구로 의심되는 타입의 derive 를 펼쳐 #[inline] 이 붙은 본문이 얼마나 긴지 본다. 필드가 6개 이상이면 배열을 만드는 형태가 된다는 점은 위 소스 확인으로 설명된다.
  • 자체 proc-macro: uv 가 한 대처다. derive(Debug)처럼 동작하되 #[inline(never)] 를 붙이는 매크로를 직접 만들어 적용한다. 원문은 매크로의 이름이나 공개 여부를 적지 않았다.
  • #[cold] 사용: Lobste.rs 의 kornel 이 자기 fmt 구현에 붙이고 있다고 쓴 방식이다. derive 가 만든 코드에는 직접 붙일 수 없으므로 수동 구현 쪽에 해당하는 이야기이다.
  • 컴파일러 쪽 보고: Lobste.rs 에서 ralfj 는 이것이 rust-lang/rust 에 올릴 만한 버그 리포트라고 했다. 인라인 기본값은 과거에도 바꾼 적이 있어 다시 바꿀 수 있고, 휴리스틱이 나쁘다는 보고가 여럿 모이면 균형을 조정할 근거가 된다는 취지다. 원문 저자는 이번 주에 올리겠다고 답했다.
  • 크레이트로 분리: Lobste.rs 의 schneems 는 이 선택을 크레이트로 밀어낼 수 있다고 본다. cold 용과 inline 용 Debug 파생을 따로 두거나 컨테이너 속성으로 고르게 하는 구상이다. 아직 구현된 것이 아니라 한 사람의 제안이다.
  • 자기 빌드에서 직접 비교: 160KB 는 uv 의 값이고 원문은 타깃과 설정을 적지 않았다. 같은 효과가 자기 바이너리에도 있는지는 의심되는 타입 하나에 대해 전후 크기를 직접 재어 보는 수밖에 없다.

확인하지 못한 것

  • 160KB 감소를 잰 uv 의 버전·커밋·타깃 트리플·빌드 프로파일(LTO, strip). 원문에 적혀 있지 않다.
  • uv 가 만든 자체 proc-macro 의 이름과 소스, 그리고 어떤 타입들에 적용했는지.
  • LLVM 인라이너가 큰 Debug 구현에 한도를 걸지 않은 이유. 원문도 rustc 가 (seemingly) 한도를 두지 않았다고만 쓴다.
  • PR #118031 의 perf 회귀가 어떤 개별 벤치마크에서 컸는지의 세부(요약 표 외).
  • Debug 외 Default·PartialEq 등의 암묵적 인라인이 실제 대형 프로젝트의 바이너리 크기에 준 영향의 실측.
