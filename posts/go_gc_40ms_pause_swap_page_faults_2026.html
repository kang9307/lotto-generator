문제 제기 — 스왑을 켠 환경에서 관측된 40ms 정지

원문은 저자가 메모리 급증을 흡수하려고 운영 환경에서 스왑을 돌리기로 했다가 이마를 칠 뻔한 경험에서 출발한다. 저자는 자신처럼 이마를 치지 않도록 글을 쓴다고 밝혔다. 실험 구성은 단순하다. cgroup 하나에 프로세스 두 개를 넣었다. 하나는 io.ReadAll로 바이트를 읽은 뒤 proto.Unmarshal로 블롭과 그래프 구조체를 만드는 Go 프로세스이고, 그래프 구조체는 Go 할당기가 scan으로 표시하는 객체다. 다른 하나는 대부분 조용히 있는 HTTP 서버다.

저자의 처음 예상은 이랬다. 컬렉터는 실행될 때마다 scan 스팬을 포인터 하나하나 읽어 가며 처리 방법을 정한다. 메모리 압박이 오면 커널이 페이지를 스왑 장치로 내보내는데, 퇴거는 프로세스가 아니라 cgroup 단위로 일어나므로 두 프로세스의 페이지가 함께 나간다. 그러니 커널과 가비지 컬렉터 사이에서 스왑 인과 스왑 아웃이 슬프게 되풀이될 가능성은 작다고 생각했다. 저자는 이 예상이 틀렸다고 쓴다.

실험 중 발견한 문제는 이렇다. Go의 가비지 컬렉터는 힙 밖에 있고 해제되지 않는 영역의 메타데이터를 세계가 멈춘 구간(stop-the-world)에서 읽는데, 그 메타데이터가 스왑에 있을 수 있다. 저자는 커널 6.8에 MGLRU를 켠 Hetzner 서버에서 모의 실행을 했고, 정지 시간의 중앙값은 약 51µs였으며, 메타데이터가 NVMe에 있을 때 최악의 정지는 40ms였다고 보고한다.

  • 중앙값과 최악값: 중앙값은 약 51µs, 최악은 40ms(상세 측정치 39,902µs)이다. 원문은 40ms가 중앙값의 800배라고 적는다. 39,902를 51로 직접 나누면 약 782배가 나온다(계산).
  • 측정 조건: 최악값은 원문의 표현으로 「메타데이터가 NVMe에 있을 때」의 값이다. 중앙값 51µs를 잰 때 스왑이 사용 중이었는지는 원문에 명시되지 않았다.
  • 전역 정지: 모든 P가 멈추므로, 예를 들어 I/O를 기다리던 고루틴의 I/O가 정지 중에 끝나 돌아와도 그것을 처리할 주체가 없다는 것이 원문의 설명이다.

원문이 강조하는 점은 이 40ms가 어느 한 고루틴이 아니라 세계가 멈춘 구간에서 생긴다는 것이다. 저자는 정지의 길이가 하찮아 보일 수 있다고 인정하면서도, 그것이 STW라는 사실을 짚는다. 같은 급증 구간에서 이런 정지가 두세 번 되풀이되었다는 점도 원문에 있다.

STW 두 지점과 폴트가 난 GC 내부 호출 지점

원문에 따르면 Go GC는 두 지점에서 세계를 멈춘다. 하나는 스윕 종료(sweep termination)를 수행할 때이고 다른 하나는 마킹 종료(mark termination)를 수행할 때다. 저자의 실험에서는 30분 동안 이런 정지가 312번 있었다.

저자는 세계가 멈춘 동안 페이지 폴트를 세는 작은 bpf 스크립트를 썼다. 최악의 사례 한 건의 출력은 다음과 같았다. 정지 39,902µs, 그동안의 폴트 228회, 폴트 안에서 보낸 시간 39,013µs. 저자는 이를 「40ms 중 39ms가 228번의 페이지 폴트에 쓰였다」고 요약한다. 그 폴트들은 GC의 장부 정리(bookkeeping) 안에서 일어났다고 하며, 원문은 addr2line 출력으로 호출 지점을 열 줄 보여 준다.

  • runtime.(*spanSet).reset — internal/runtime/atomic/types.go:194
  • runtime.finishsweep_m — mcentral.go:71, 그리고 다른 스택에서 mgcsweep.go:268
  • runtime.gcStart.func2 — mgc.go:724
  • runtime.systemstack — asm_amd64.s:518
  • runtime.gcStart — mgc.go:722
  • runtime.nextMarkBitArenaEpoch — mheap.go:2481

열 줄은 다섯 프레임씩 두 스택으로 읽힌다. 하나는 spanSet.reset에서 시작하고 다른 하나는 nextMarkBitArenaEpoch에서 시작하며, 둘 다 finishsweep_m, gcStart.func2, systemstack, gcStart로 이어진다. 저장소 스크립트가 ustack(5)로 다섯 프레임을 잡는다는 점과 맞아떨어진다. 원문은 각 함수가 하는 일이나 이 호출 지점들이 어느 STW 지점에 대응하는지는 설명하지 않으므로 여기서도 이름과 위치까지만 적는다.

원문이 설명하는 커널 쪽 경로 — 퇴거에서 메이저 폴트까지

원문이 드는 이유는 이렇다. 런타임은 그 페이지들을 할당한다. 그 페이지들은 해제되지 않고 재사용된다. 그리고 GC 사이클에서 읽힌다. 커널은 나이 순으로 페이지를 퇴거하므로 가장 오래 접근되지 않은 페이지를 스왑으로 보낸다. GC가 세계를 멈추고 그 페이지를 읽으려 하면 이미 스왑에 있으니 메이저 페이지 폴트가 난다.

폴트 한 번의 처리를 저자는 「짧게 줄여서」 이렇게 나열한다. 커널이 PTE를 읽고, do_swap_page를 호출하고, 새 프레임을 찾고, 그것을 cgroup에 부과하고, 페이지를 읽기 위해 bio를 제출하고, 디스크를 기다린 뒤 메모리에 되돌려 놓는다. 원문은 이 단계들 옆에 리눅스 6.8 소스(mm/memory.c, mm/swap_state.c, mm/page_io.c)의 해당 줄로 가는 링크를 단다.

  • 퇴거 기준: 접근 시각이다. 가장 오래 접근되지 않은 페이지가 먼저 스왑으로 간다.
  • 퇴거 단위: 저자의 전제로는 프로세스가 아니라 cgroup이다. 그래서 조용한 HTTP 서버의 페이지도 같은 압박 아래 놓인다.
  • 메타데이터의 접근 패턴: 원문 표현으로 그 페이지들은 GC 사이클에서 읽힌다. 사이클 사이에는 접근되지 않을 수 있다.
  • 폴트 한 번의 비용: 위 나열의 끝에 디스크 대기가 있으므로, 원문의 최악 사례에서는 228번의 폴트가 한 번의 정지 안에서 일어났다.

같은 폴트라도 어디서 나느냐에 따라 파급이 다르다. 저자는 511KiB 메시지를 만드는 고루틴의 지연을 이야기하며, 그 비용은 할당하는 고루틴만 치르므로 메타데이터 정지처럼 전역이 아니라 국소적이라고 쓴다. 반대로 메타데이터 폴트는 세계가 멈춘 안에서 나므로 모든 P가 함께 기다린다.

실험 환경과 bpftrace 스크립트 — stw.bt 전문

원문의 모의 실행은 Hetzner 서버에서 커널 6.8과 MGLRU를 켠 채로 진행되었다. 그래프, 모의 할당기, bpf 스크립트, 파이썬 스크립트 등 실험의 모든 것은 저장소 go-gc-swap-cost에 있다. 관측은 30분이었고 그동안 STW가 312번 있었다. 아래는 그 저장소 bpf/stw.bt의 전문이며, 주석을 포함해 글자 그대로 옮겼다.

// BIN: path of the Go binary as seen by bpftrace, e.g. /proc/<pid>/root/tmp/pagefault
                    // both processes run the same binary, so everything is keyed by pid: a fault counts only
                    // against a pause of its own process
                    uprobe:BIN:runtime.stopTheWorldWithSema /comm == "pagefault"/ {
                      @stw_start[pid] = nsecs; @stw_faults[pid] = 0; @stw_fault_ns[pid] = 0;
                    }
                    uprobe:BIN:runtime.startTheWorldWithSema /@stw_start[pid]/ {
                      $d = (uint64)(nsecs - @stw_start[pid]);
                      @stw_us = hist($d / 1000); @stw_n[pid] = count(); @stw_ns[pid] = sum($d);
                      printf("stw t=%d pid=%d %d us, faults during it %d, %d us in faults\n",
                             elapsed / 1000000, pid, $d / 1000, @stw_faults[pid], @stw_fault_ns[pid] / 1000);
                      delete(@stw_start[pid]);
                    }
                    // swap-in and file-backed faults both: the binary's own code pages can be evicted too
                    kprobe:do_swap_page, kprobe:filemap_fault /comm == "pagefault" && @stw_start[pid]/ {
                      @f_start[tid] = nsecs; @stw_faults[pid]++; @stw_stack[ustack(5)] = count(); // five frames reach gcStart
                    }
                    kretprobe:do_swap_page, kretprobe:filemap_fault /@f_start[tid]/ {
                      @stw_fault_ns[pid] += (uint64)(nsecs - @f_start[tid]); delete(@f_start[tid]);
                    }
                    END { clear(@stw_start); clear(@f_start); clear(@stw_faults); clear(@stw_fault_ns); }

스크립트의 구조는 네 부분이다. 첫째, stopTheWorldWithSema에 건 uprobe는 pid별로 시작 시각을 적고 폴트 횟수와 폴트 시간을 0으로 만든다. 둘째, startTheWorldWithSema에 건 uprobe는 정지 시간 $d를 계산해 마이크로초 히스토그램에 넣고, 정지 시간, 폴트 횟수, 폴트 시간을 한 줄로 출력한 뒤 그 pid의 시작 시각을 지운다. 셋째, kprobe는 do_swap_page와 filemap_fault 진입 때 시각을 적고 폴트 횟수를 올리며 ustack(5)로 호출 스택을 집계한다. 넷째, kretprobe는 같은 두 함수가 끝날 때 소요 시간을 폴트 시간에 더한다.

스크립트의 주석이 알려 주는 것이 두 가지 있다. 두 프로세스가 같은 바이너리를 실행하므로 모든 값을 pid로 구분해 한 폴트가 자기 프로세스의 정지에만 계산되게 했다는 점, 그리고 스왑 인과 파일 기반 폴트를 모두 센다는 점이다. 바이너리 자신의 코드 페이지도 퇴거될 수 있기 때문이다. 이 스크립트를 읽으면 원문이 말하는 228회가 do_swap_page와 filemap_fault 호출을 합친 값이라는 것을 알 수 있다.

  • 관측: 30분 동안 STW 312회.
  • 최악 사례: 정지 39,902µs, 폴트 228회, 폴트 처리 합계 39,013µs.
  • 폴트의 비중: 39,013 ÷ 39,902 ≈ 97.8%이다(계산). 원문의 서술은 「40ms 중 39ms」다.
  • 폴트 밖의 시간: 39,902 − 39,013 = 889µs이다(계산). 이 시간의 내역은 원문에 없다.
  • 반복: 테스트의 메모리 급증 한 번당 이런 정지가 두세 번 나왔다.

메시지 생성 지연 — 할당 고루틴이 혼자 치르는 비용

저자는 또 하나를 알아챘다. 511KiB짜리 메시지를 하나 만드는 데 보통 3~5ms가 걸리는데, 스왑이 NVMe에 있을 때는 105ms로, Hetzner의 네트워크 볼륨에 있을 때는 903ms로 늘었다. 저자는 메시지 하나당 비용이 메타데이터 정지보다 크다고 적는다. 다만 할당하는 고루틴만 그 값을 치르므로 비용이 국소적이고, 메타데이터처럼 전역은 아니라는 점은 다행이라고 덧붙인다.

  • 범위: 지연은 할당을 수행하는 고루틴에 한정된다. 전역 STW와 달리 다른 P를 멈추는 것이 아니다.
  • 매체 차이: 105ms 대비 903ms는 약 8.6배다(903÷105 계산). 같은 작업이 스왑 매체에 따라 이만큼 달라졌다.
  • 시간의 내역: 저자는 이 시간이 어디에 쓰였는지 확인하지 못했다고 직접 밝힌다.

저자가 이 항목을 글에 넣은 이유는 「또 다른 비용을 치러야 할 수 있기 때문」이다. 저자는 이 시간을 메타데이터 폴트와 같은 원인으로 설명하지 않았다. 따라서 메시지 생성 지연을 STW 폴트와 같은 메커니즘의 결과로 읽을 수 없다.

Green Tea GC 재측정과 Go 공식 설명

원문의 9월 14일 업데이트는 짧다. 누군가 Go 1.26의 Green Tea 가비지 컬렉터가 GC가 메타데이터를 읽는 방식을 바꾸었는지 물었고, 저자가 측정해 보니 영향이 무시할 만했다(negligible)는 것이다. 측정 환경과 수치는 공개되지 않았다.

Go 공식 자료는 Green Tea를 이렇게 설명한다. Go 블로그(2025년 10월 29일)에 따르면 핵심 아이디어는 「객체가 아니라 페이지 단위로 작업한다」는 것이다. 객체를 스캔하는 대신 페이지 전체를 스캔하고, 작업 목록도 객체가 아니라 페이지를 추적하며, 마킹된 객체는 힙 전체가 아니라 페이지 안에서 지역적으로 추적한다. 블로그는 이것이 캐시 지역성에 기여한다고 설명한다. Go에서 페이지는 하드웨어 가상 메모리 페이지와 무관하게 8KiB다.

  • Go 1.25: GOEXPERIMENT=greenteagc로 켜는 실험 기능이었다. 블로그는 많은 워크로드에서 GC에 쓰는 시간이 약 10% 줄고 일부는 최대 40% 줄었다고 적는다.
  • Go 1.26: 릴리스 노트에 따르면 실험이었던 Green Tea가 기본값이 되었고, 작은 객체의 마킹과 스캔 성능을 지역성과 CPU 확장성으로 개선한다. GC를 많이 쓰는 실제 프로그램에서 GC 오버헤드가 10~40% 줄 것으로 기대한다(Go 공식 수치).
  • 추가 개선: 새로운 amd64 CPU(Intel Ice Lake, AMD Zen 4 이후)에서는 작은 객체를 스캔할 때 벡터 명령을 써서 GC 오버헤드가 약 10% 더 줄 것으로 기대한다.
  • 끄는 법: 빌드 때 GOEXPERIMENT=nogreenteagc로 끌 수 있으며, 이 설정은 Go 1.27에서 제거될 것으로 예상한다.

공식 수치의 성격을 구분해야 한다. 10~40%는 GC가 쓰는 CPU 오버헤드에 대한 벤치마크 기대치이고, 원문의 문제는 STW 중 메타데이터 읽기에서 난 폴트다. 둘은 측정 대상이 다르므로, 한쪽 수치로 다른 쪽을 추정할 수 없다. 확인되는 것은 저자가 Green Tea에서 메타데이터 읽기의 영향이 무시할 만하다고 측정했다는 문장 하나다.

원문의 결론과 읽을 때의 주의

원문의 결론은 한 문장 반이다. 저자는 Chris Down에 동의해 스왑이 나쁜 것은 아니라고 쓴다. 그러나 스왑은 가비지 컬렉션과는 잘 어울리지 않았고, 자신의 운영 환경은 GC를 많이 돌린다고 덧붙인다. 스왑을 끄라거나 어떤 설정을 바꾸라는 권고는 원문에 없다.

  • 저자가 직접 확인한 것: 세계가 멈춘 구간에서 메타데이터 폴트가 났고, 그 폴트가 정지의 대부분을 차지한 사례가 있었다.
  • 저자가 확인하지 못했다고 쓴 것: 511KiB 메시지 생성 지연의 시간 내역이다.
  • 저자가 짧게만 다룬 것: Green Tea에서의 재측정은 수치 없이 결과만 적었다.
  • 원문에 없는 것: 운영 권고, 설정값, 다른 환경에서의 재현이다.
표 2: 원문이 말한 것과 말하지 않은 것
주제 원문이 말한 것 원문이 말하지 않은 것 글을 읽을 때의 주의
스왑의 평가 Chris Down에 동의, 스왑은 나쁜 것이 아니다 스왑 비활성화나 특정 설정 권고 권고를 원문에 귀속시키지 않는다
GC와의 관계 스왑이 가비지 컬렉션과 잘 어울리지 않았다 일반적 조건에서의 발생 빈도 한 모의 실행의 결과이다
Green Tea 메타데이터 읽기에 대한 영향이 무시할 만하다 측정 수치와 조건 Go 공식의 10~40%는 다른 지표이다
메시지 생성 지연 105ms(NVMe), 903ms(네트워크 볼륨) 시간의 내역 STW 폴트와 같은 원인으로 단정하지 않는다

이 사례에서 얻을 수 있는 일반적 교훈은 조심스럽게만 말할 수 있다. 정지 시간이 짧은 구간에서도 그 구간이 읽는 메모리가 스왑에 있으면 디스크 지연이 정지에 그대로 얹힌다는 것이다. 그것이 어떤 운영 환경에서 얼마나 자주 일어나는지는 원문이 답하지 않는다.

확인하지 못한 것

  • 중앙값 51µs를 잰 조건. 스왑을 사용하던 때의 값인지는 원문에 명시되지 않았다.
  • 511KiB 메시지 생성에 걸린 105ms와 903ms의 시간 내역. 원문 저자도 어디에 쓰였는지 확인하지 못했다고 적었다.
  • 메타데이터가 네트워크 볼륨에 있을 때의 STW 최악값. 원문은 NVMe 경우의 40ms만 적는다.
  • Green Tea GC 재측정의 수치와 실행 조건. 원문은 영향이 무시할 만하다고만 적었다.
  • Hetzner 서버 이외의 환경과 커널 6.8 이외의 커널에서의 재현 결과.
  • 228회 폴트 중 스왑 인(do_swap_page)과 파일 기반 폴트(filemap_fault)의 구성 비율. 스크립트는 둘을 합쳐 센다.
