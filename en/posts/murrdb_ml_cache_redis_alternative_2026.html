murrdb - A Sub-Millisecond Cache for ML/AI Workloads to Replace Redis 2026

A zero-copy cache layered on RocksDB, NVMe, and S3, redesigning the data bottleneck of AI inference

June 15, 2026 Dev/Infra

Intro: The bottleneck in AI inference is data, not the model

No matter how fast your GPU is, if the layer in front of the inference server cannot feed it data in time, that expensive accelerator sits idle. Loading embedding vectors, fetching recommendation features, pulling already computed LLM KV tensors, all of this data movement makes up a large share of inference latency. And the tool we reflexively drop into that slot is usually Redis, because it has been the default cache for over a decade.

In June 2026, a project that lit up GeekNews (news.hada.io), murrdb (project name Murr, repo shuttie/murr), questions exactly that habit. "AI inference data has a different shape than ordinary web cache data, so why use the same tool?" murrdb is a columnar cache that combines a RocksDB-style storage engine with local NVMe and S3, and it pitches a zero-copy protocol that ships tensors whole, with no conversion, plus sub-millisecond latency.

This article dissects murrdb from a developer's point of view. What is different from Redis, what "zero-copy" and "NVMe tiering" actually save, how the burden a cache carries in AI inference came to be, and where to trust it versus where to be careful. We separate claims from the project's own materials from generally established principles.

One-line summary. murrdb is not "Redis is wrong"; it starts from the observation that "AI inference data is not single key-values but batches of large tensors." Columnar batch I/O plus zero-copy plus NVMe/S3 tiering is the core: cut RAM cost while lifting tensor transfer throughput.

1. murrdb at a glance, defined in one sentence

murrdb describes itself as a "columnar in-memory cache for AI inference." By position, it is a caching layer that sits between batch data pipelines and inference applications. In other words, it is the slot that quickly supplies the embeddings, features, and intermediate tensors a model needs at inference time.

The core design decisions come down to three. First, it handles data by column, not by row. ML data is usually "long arrays of same-typed numbers," so columnar layout helps compression, transfer, and computation. Second, tiered storage keeps hot data in memory, cold data on local NVMe, and durable state on S3. Third, a zero-copy wire protocol builds NumPy arrays, Pandas DataFrames, and PyTorch tensors directly from network responses with no conversion.

It is implemented in Rust, open source under Apache 2.0, and the Python client installs with pip install murrdb. Per the introduction, nodes are stateless with state living on S3, so on restart they self-bootstrap from block storage.

2. Why a Redis alternative, the peculiarities of an AI inference cache

Redis is an excellent tool. But its strengths shine where you handle "small values, often, fast." AI inference cache data departs from that assumption on several fronts.

2.1 The data is not small

An LLM KV cache chunk ranges from hundreds of KB to tens of MB. For an 8B-class model, a single 10,000-token request can produce over 1 GB of KV data. Embedding tables and ranking feature matrices are similarly large. Keeping all of that resident in RAM makes memory cost climb steeply.

2.2 It is batch, not single-key

Inference usually reads hundreds to thousands of keys at once (for example, the features of 1,000 documents to rank). In Redis's single-key-centric model, even with pipelining, serialization and deserialization overhead accumulate. murrdb treats columnar batch reads and writes as first-class citizens, to the point that dumping a 1 GB Parquet file through the API is considered a normal scenario.

2.3 In the end it becomes a tensor

Bytes pulled from the cache eventually have to become a NumPy array or tensor. A typical cache hands back serialized bytes, and the application re-parses and copies them into a tensor. That conversion cost is non-trivial for large data. murrdb's zero-copy aims to skip that step.

The core insight is simple. An AI inference cache workload is not "small values times many requests" but "large tensors times batch transfer." When the tool's data model is misaligned with the workload's data shape, structural overhead remains no matter how much you tune.

3. Zero-copy, what gets faster when you remove the copy

"Zero-copy" is a technique that uses bytes received over the network as-is, without an extra memory copy or deserialization. In murrdb's context, it means mapping the received byte buffer directly into the memory of an np.ndarray or pt.Tensor.

Why does this matter? The traditional path usually looks like this: (1) network buffer, (2) deserialize (parse JSON/Protobuf), (3) allocate new object memory, (4) copy values. If the data is tens of MB, that copying and parsing alone burns CPU cycles and time, and in Python it adds GC pressure too. Zero-copy effectively skips (2) through (4), so the effect grows with larger tensors.

For this, murrdb is described as using a columnar memory format (the Apache Arrow family) along with transport paths like Arrow IPC and Arrow Flight (gRPC). Arrow's memory layout is common across languages, so received data can be interpreted as a tensor as-is. That is the foundation that makes "a tensor the moment you receive it" possible.

4. NVMe tiering and S3, how not to burn RAM

The second axis is storage tiering. Instead of putting all data in RAM, murrdb splits it into tiers by access frequency.

  • Hot data: tensors used heavily right now stay in memory, the fastest but most expensive tier.
  • Cold data: data untouched for a while is pushed down to local NVMe SSD, far cheaper than RAM, and modern NVMe offers random reads in the single-digit to tens-of-microseconds range.
  • Durable tier: the real state lives on S3. Using object storage like "a new filesystem," even when a node dies the data remains on S3, and a new node restores itself from there.

The payoff is clear: you can cache far larger datasets for the same budget, and because S3 becomes the single source of truth, the complexity of cross-node replication coordination shrinks. Embedded LSM engines like RocksDB are strong at exactly this kind of disk-based tiering and compression, so it is natural that murrdb runs its cold tier on that family. This also echoes the general principle of separating the cache from the source of truth, a theme covered in why Shopify moved inventory from Redis to MySQL.

5. The role of a cache in AI inference, KV cache, embeddings, features

To understand the slot murrdb targets, you have to see what a cache concretely does in AI inference. There are three big ones.

5.1 KV cache offloading

An LLM computes a key and value tensor for each token it generates. When the same prompt prefix repeats, those KV tensors can be reused to avoid redundant compute, but the catch is that the volume quickly eats into GPU memory. So "KV cache offloading," moving KV outside the GPU (CPU RAM, local disk, remote storage), is an active area. What matters here is tail latency (inference cannot continue until every chunk arrives) and GB/s throughput, which favors a cache strong at large tensor batch transfer.

5.2 Embedding cache

Search, recommendation, and RAG repeatedly use embedding vectors for the same documents, items, and queries. Caching embeddings instead of re-running the encoder every time saves a lot. Embeddings are fixed-dimension float arrays, a good fit for columnar storage.

5.3 Feature cache

Recommendation and ranking models fetch user and item features in bulk at inference time. The traditional feature-store path tends to be slow as serialization and network round-trips pile up. In murrdb's introductory benchmark (a ranking workload of 1,000 documents by 10 float32 columns at the 10M-row scale), Murr shows roughly 104 microseconds latency and claims to be "about 2.5x faster than the best Redis layout and about 36x faster than Feast-style storage," precisely in this feature-serving role.

Read with care. The numbers above come from a specific workload in murrdb's own materials. Benchmarks depend heavily on data shape, hardware, and access pattern, so until you reproduce them on your own workload, treat them as "an upper bound under specific conditions."

7. Use scenarios

So where is it worth trying? Here are concrete scenarios where murrdb's design should shine.

  • Recommendation/search ranking feature serving: paths that read features for hundreds to thousands of items per request and feed them to a model. Batch, columnar, and zero-copy fit exactly.
  • Embedding cache layer: storing repeated embedding vectors in RAG and semantic search at scale on the NVMe tier, without burning all your RAM.
  • LLM KV cache backend: a candidate offloading backend that stores and re-serves KV chunks pushed off the GPU at high throughput.
  • Batch pipeline to online inference bridge: a bridge that loads large Parquet artifacts produced offline as-is and serves them quickly online.

8. Limits and risks, a sober look

Promise aside, when you put new infrastructure on a critical path, you have to count the cost honestly.

8.1 Maturity and ecosystem

Redis has over a decade of operational know-how, clients, managed services, and monitoring tools stacked deep. murrdb's stack is still thin. You have to verify for yourself whether incident response, observability, and HA operating patterns are sufficiently proven.

8.2 The price of generality

Being ML-specialized means general commands, data structures, and transaction semantics may not be as rich as Redis. The urge to do everything in one cache can backfire.

8.3 The operational reality of S3/NVMe dependence

Using S3 as the durable tier means designing cost, latency, and the consistency model around its characteristics. If cold data is called often, NVMe/S3 round-trips can inflate tail latency, so hot/cold boundary tuning and cache hit-rate management drive performance.

8.4 The benchmark trap

As stressed earlier, the impressive multiples are a product of a specific workload. They favor data that "becomes a tensor as-is via zero-copy," like embeddings, but the advantage can shrink for patterns that hammer many small keys at random.

9. Developer view, a pre-adoption checklist

If you actually evaluate it, ask these questions first.

  1. Is my cache data really "large tensor batches"? If it is mostly small key-values, murrdb's advantage is small. This sense of classification also shows up in cases like UUID primary keys and SQLite performance, where "data shape determines performance."
  2. Is the access pattern batch and columnar? Reading many keys bundled per request raises the fit.
  3. Can you use the zero-copy path end to end? The client must consume directly as Arrow/NumPy/tensors. Copy again midway and the advantage evaporates.
  4. Can you operate S3/NVMe? You need monitoring for cost, latency, and hit rate.
  5. Did you isolate and validate before the critical path? Replacing infrastructure that handles durable data is all about validation.

This "caution when swapping a store" applies not only to caches but to workflow durability too. On that note, the discussion in building durable workflows on PostgreSQL is worth reading alongside this.

10. The bigger question murrdb poses

Separate from murrdb's own success or failure, the trend it touches is clear: AI workloads are rewriting infrastructure defaults. Where it was once "cache = Redis," "queue = Redis," "feature store = general DB," now specialized layers tuned to the workload's data shape are appearing everywhere.

This dovetails with broader industry moves at the same time. Dedicated libraries for KV cache offloading, cache data planes aimed at S3 and NFS, and RDMA-based tensor transfer all point at the same question: how do we make AI inference data movement cheap and fast? murrdb is one answer, "columnar plus zero-copy plus tiering," to that question.

11. Conclusion plus three things you can apply now

murrdb is not a project that casts Redis as the "wrong tool." It is a concrete demonstration of what changes when you fit the tool to the data shape (large tensors, batch, columnar) for the specialized workload of an AI inference cache. Promising but new, and its impressive numbers are a product of specific conditions, worth remembering together.

I will close with three things you can apply today.

  1. Re-classify cache data by "shape." Whether it is small key-values or large tensor batches splits the optimal tool. For the latter, a columnar, zero-copy cache is worth evaluating.
  2. Re-examine RAM cost through tiering. Not all cache data needs to be in RAM. A design that pushes cold data to NVMe and durability to S3 builds a bigger cache for the same budget.
  3. Adopt new infrastructure only after isolated validation. Reproduce the benchmark on your own workload, validate with shadow traffic before the critical path, then grow its share.

Next time you slot a cache in front of an inference server, before reflexively typing Redis, ask once: "Is my data small values, or large tensors?" That answer chooses the tool first.

Frequently Asked Questions (FAQ)

Q1. What is murrdb?

A columnar in-memory cache for AI/ML inference. It tiers hot data in memory, cold data on NVMe, and durable state on S3, with a zero-copy protocol that builds tensors directly without conversion. It is written in Rust and open source under Apache 2.0.

Q2. Why does murrdb aim to replace Redis?

Redis keeps all data in RAM, so large embeddings and KV caches get expensive, and its single-key focus adds overhead for tensor batch transfer. murrdb offloads cold data to NVMe/S3 and handles bulk tensors fast via columnar batch zero-copy.

Q3. What do zero-copy and NVMe caching mean?

Zero-copy maps received bytes straight into arrays/tensors with no extra copy or parsing, cutting CPU copies and GC pressure. NVMe caching is tiering that keeps cold data on local SSD instead of expensive RAM, caching more data for the same cost.

Q4. What role does a cache play in AI inference?

LLM KV cache offloading, embedding vector caches, and recommendation/ranking feature caches are the main ones. All exchange large tensors at low tail latency and high throughput, favoring a cache strong at batch, columnar transfer.

Q5. Is murrdb ready for production today?

It is promising in niches (tensor batch serving, feature caching) but new, so compatibility, maturity, and ecosystem may be limited. Reproduce and validate benchmarks on your own workload before adopting it on a critical path.
