Agent Executor - Googleの分散エージェントランタイム解説 2026

Event-Sourced Reliability for the Agentic Loop

2026年6月5日 IT・技術

はじめに:エージェントは作るより動かす方が難しい

この2年間、私たちは「AIエージェントをどう作るか」についての記事を何百本も読んできました。プロンプトをどう書き、ツールをどう繋ぎ、どのフレームワークでグラフを描くか、という話です。ところが実際にエージェントを本番に乗せたチームが直面する本当の苦痛は、別の場所にあります。30分かかるマルチステップのエージェントが27分の地点でワーカープロセスごと落ちると、そこまでに使ったLLMトークンの費用と外部API呼び出しが丸ごと消えます。何がなぜ間違ったのかを追うログは散らばっており、同じ入力を入れても再現しません。エージェントは作ることより安定して動かすことの方がはるかに難しい——この事実は、運用を経験した人だけが知っています。

2026年6月初め、Googleがこの問題に正面から照準を合わせたオープンソースを公開しました。名前はAgent Executor、一言で言えば「分散エージェントランタイム」です。中核となる発想は意外にも古典的です。エージェントループのすべてのステップをイベントとして記録し、そのイベントログを実行の単一の真実の源とするのです。本稿はhada(GeekNews)で話題になったこの発表を出発点としつつ、単なる紹介を超えて「Agent Executorが正確にどんな問題を解くのか」「既存フレームワークと何が違うのか」「開発チームは今これを導入すべきか」を私の視点で分析します。

1. Agent Executorが解く本当の問題

まず問題定義を明確にしましょう。AIエージェントの本質は非決定的なループです。「LLMに何をすべきか尋ね → ツールを実行し → 結果を再びLLMに渡し → 終わったか判断する」というサイクルを、終了条件を満たすまで繰り返します。このループが単純な関数呼び出しと根本的に異なる点は三つあります。

  • 時間がかかる:数十回のLLM呼び出しと外部API待ちが積み重なると、一つの作業が数分から数十分、長ければ時間単位に伸びます。
  • 高くつく:各ステップがトークン費用を使い、外部API呼び出しは副作用(メール送信、決済、ファイル書き込み)を残します。途中で失敗して最初からやり直すと、費用も副作用も重複します。
  • 不透明である:どんな判断でどのツールをなぜ呼んだのかがLLMの内部に隠れており、事後の追跡とデバッグが非常に難しいです。

Agent Executorが掲げる四つの目標——信頼性・安全性・カスタマイズ性・効率性——は、まさにこの三つの苦痛に対応します。長いループが途中で落ちても復旧されねばならず(信頼性)、副作用が重複実行されてはならず(安全性)、チームごとに異なるツールやポリシーを差し込めねばならず(カスタマイズ性)、不要な再実行なく資源を節約せねばなりません(効率性)。

2. イベントソーシング——実行モデルの中核

Agent Executorの設計思想を一語に圧縮すればイベントソーシング(Event Sourcing)です。これはデータベースの世界で長く検証されてきたパターンで、「現在の状態を直接保存する代わりに、状態を生み出したすべてのイベントを追記専用(append-only)ログに記録する」という発想です。

これをエージェントループに適用するとこうなります。LLMに問い合わせた → イベントとして記録。ツールXを引数Yで呼ぶと決めた → イベントとして記録。ツールが結果Zを返した → イベントとして記録。このログを最初から再生(replay)すれば、エージェントの現在状態が正確に復元されます。

[t0] AgentStarted        目標: 「今週の売上レポート作成」
 |
[t1] LLMRequested        プロンプト + 利用可能ツール一覧
[t2] ToolCallDecided     query_db(range="this_week")
[t3] ToolCallCompleted   結果: 1,240件 / 売上 830万円
 |
[t4] LLMRequested        結果を反映した次の判断
[t5] ToolCallDecided     send_email(to=team, body=...)
 X   ここでワーカープロセスがクラッシュ
 |
 >   再起動ワーカーがログを再生 → t4まで復元
     → t5(メール送信)は未完了と判定 → 安全に再開

このモデルの威力はクラッシュ復旧だけではありません。観測性が無料で付いてきます。イベントログそのものが完璧な実行トレースなので、「なぜこのエージェントがこの判断を下したのか」を事後に一段ずつそのまま覗けます。非決定的だったエージェントが、少なくとも「何が起きたか」の面では決定的に検証可能になるのです。

3. 「分散」ランタイムが意味するもの

名前に付いた分散(distributed)という語は単なるマーケティングではありません。イベントログが実行状態をプロセスの外部に出すため、エージェント実行はもはや特定のサーバーやプロセスに縛られません。

これが実務にもたらす利点は具体的です。

  • 障害分離:ワーカーAが落ちてもワーカーBがログを読んで引き継ぎます。一つのノードの死が作業の死に直結しません。
  • 水平スケール:同時に1万個のエージェントを動かすなら、ワーカープールを増やすだけです。状態はログにあるので、ワーカーはほぼ無状態(stateless)で回せます。
  • 長時間実行:人間の承認を数日待つエージェントも、その間ワーカーを占有せずログ状態で「眠って」おき、目覚めることができます。

ここで経験あるエンジニアならデジャヴを感じるでしょう。これはTemporalやAWS Step Functionsのような耐久ワークフロー(durable workflow)エンジンが長年解いてきた問題と本質的に同じです。違いはただ一つ、そのワークフローの各ステップが「人間が事前に定義した決定的なステップ」ではなく「LLMが実行時に即興で決める非決定的なステップ」である点です。Agent Executorは耐久ワークフローの検証された考え方を、非決定的なエージェント時代に合わせて移植した試みだと読むのが正確です。この流れは、以前扱ったPostgreSQLベースの耐久ワークフローの問題意識にも直結します。

4. 既存エージェントフレームワークとの違い

最も多く受ける質問は「LangChainやCrewAIと何が違うのか」でしょう。要点は扱う層が違うということです。たとえれば、既存フレームワークが「料理のレシピ」なら、Agent Executorは「レシピ通りに数千人前を失敗せず作り出す厨房運用システム」です。

区分 組み立てフレームワーク(LangChain・CrewAIなど) Agent Executor(ランタイム)
主な関心 エージェントをどう構成・接続するか 構成されたエージェントをどう安定実行するか
状態管理 主にメモリ/セッション、自前で永続化 イベントログで標準的に永続化
障害復旧 概ね利用者の責任 ログ再生で内蔵
観測性 別途トレーシングツールを連携 イベントログがそのままトレース

したがって両者は競合関係ではなく補完関係である可能性が高いです。LangGraphでエージェントの論理グラフを描き、その実行をAgent Executorのようなランタイム上に乗せる組み合わせが自然です。実際、マルチエージェント構成が複雑になるほどランタイム層の不在がより強く体感されますが、このコスト構造は以前分析したマルチエージェントのオーケストレーション税にも通じます。

5. 信頼性をどう保証するか

エージェント運用で最も恐ろしいシナリオは「副作用の重複」です。決済を呼んだ直後にクラッシュして再試行し、決済が二度起きる、という具合です。Agent Executorのイベントモデルはこの問題を冪等性(idempotency)とチェックポイントで扱います。

各ツール呼び出しは「決定(decided)」と「完了(completed)」という二つのイベントに分けて記録されます。再起動時、ランタイムはログを見て「決定はされたが完了記録のない」呼び出しを識別します。このとき闇雲に再実行する代わりに、外部システムに冪等性キーで結果を再度問うか、危険な副作用は人間の承認を経るようポリシーを差し込めます。これが「安全性」が独立した目標として明記された理由です。自動復旧がかえって事故を拡大しないよう、復旧そのものに安全装置を内蔵したのです。

分散システムで本当に難しいのは「失敗しないようにすること」ではなく「失敗が起きた後でも、効果がちょうど一度だけ残るようにすること」だ。エージェントランタイムもこの古い真実から自由ではない。

6. 観測性とデバッグの実務的価値

現場でエージェントを運用した人にとって最も響く価値は、意外にも信頼性よりデバッグ可能性かもしれません。非決定的なエージェントのバグ報告は悪夢です。「たまにおかしな答えをする」というのに、再現できません。

イベントログがあれば話は変わります。問題となったその実行のログをそのまま開き、LLMがどんなプロンプトを受け、どのツールをどの引数で呼び、何を返されたかを段階ごとに確認できます。さらにそのログをテストフィクスチャとして回帰テストを作ることもできます。AIエージェント時代の「再現不能なバグ」という持病に対する、極めて実用的な処方です。

7. 本番エージェント運用の実務的示唆

では、この発表が業界に投げかけるより大きなメッセージは何でしょうか。私は二つに読みます。

第一に、エージェント論争の重心が「知能」から「運用」へ移動しているという信号です。2024〜2025年が「どれだけ賢いエージェントを作るか」の時代だったなら、2026年は「作ったエージェントをどう壊さず動かすか」の時代へ移りつつあります。これは技術が実験段階を過ぎ本番段階へ成熟したという健全な信号です。

第二に、Googleのような大手プレイヤーがランタイム層をオープンソースで標準化しようとしている点です。モデル競争がある程度平準化した今、差別化の戦場は「エージェントを信頼性高く運用するインフラ」へ移っています。これは開発者のアイデンティティが「コードを書く人」から「エージェントというharnessを設計・運用する人」へ移るという、以前の記事Claude Codeと動的ワークフローharnessで扱った流れとも正確に一致します。

8. 開発チームの現実からの分析

ここで現実に下りてみましょう。グローバルな発表をそのまま受け入れる前に、チームが検討すべき点がいくつかあります。

  • 人員構造:専任のMLインフラチームを持つ組織は多くありません。イベントソーシングベースのランタイムは強力ですが運用の学習コストがあり、小規模チームには最初から過剰なインフラになり得ます。
  • データ主権:イベントログにはプロンプトとツール入出力がそのまま残ります。金融・通信・公共のような規制の強いドメインは、このログの保管場所とマスキングポリシーを設計段階で確定すべきです。
  • 段階的導入:全面置換より、最も長く高く壊れやすい中核エージェントを一つか二つ先にこのランタイムへ移し効果を測るパイロットが現実的です。

要点は「Googleが出したから良い」ではなく、「自社のエージェントが実際に長く高く壊れやすいか」をまず問うことです。そうでなければ、このランタイムの利点の多くは使われない保険料になります。

9. 導入前に確認すべきこと

実際の検討に入るなら、新興オープンソース特有のリスクをチェックリストとして押さえることを勧めます。

  1. API安定性:初期バージョンはインターフェースが頻繁に変わります。本番の中核に深く結びつける前に、抽象化レイヤーを置いて差し替え費用を下げましょう。
  2. ストレージ依存:イベントログをどこに積むか(どのDB・キュー)が運用負担の大半を決めます。既存スタックとの整合性をまず確認しましょう。
  3. コストモデル:全ステップを記録するとストレージ・I/O費用が増えます。ログ保存期間と圧縮・アーカイブのポリシーを併せて設計すべきです。
  4. エコシステムの成熟度:ドキュメント、例、コミュニティ、既存フレームワークとのアダプターがどれだけ揃っているかが実際の生産性を左右します。

10. 限界と批判的視点

バランスのため反対側も明確に指摘します。イベントソーシングは万能ではありません。第一に複雑度の転嫁問題があります。単純なエージェントにこのインフラを乗せると、得るものより運用負担の方が大きくなり得ます。第二にログ再生の罠です。外部世界は時間が経つと変わります——再生時点のAPI応答が元と異なれば復元がずれ得るため、「決定的再生」は副作用の冪等処理がうまくできたときだけ保証されます。第三にベンダー・標準リスクです。今はオープンソースですが、事実上の標準の座を巡って複数の陣営が競い、どこに賭けるかが今後の移行費用を分けます。

それでも方向性自体は正しいと見ます。エージェントがおもちゃを超えてビジネスクリティカルな仕事を担う瞬間、信頼性・復旧・観測性は選択ではなく必須になります。Agent Executorはその必須をインフラ層で解決しようとする、時宜にかなった試みです。

結論:エージェントの「運用時代」が開く

Agent Executorを一文でまとめれば、「非決定的なエージェントループに耐久ワークフローの規律を着せた分散ランタイム」です。イベントソーシングという検証されたパターンの上で信頼性・安全性・観測性を基本機能として提供し、分散実行でスケーラビリティと障害分離を加えます。派手な新機能ではありませんが、エージェントを実際に本番で動かした人ほどその価値を見抜く発表です。

最後に実務的な推奨を三つで締めます。第一に、今運用中のエージェントが「長く高く壊れやすいか」をまず自問しましょう——そうならランタイム層導入の最有力候補です。第二に、全面置換ではなく中核エージェント一つでパイロットを回し、復旧・観測性の実際の効果を測りましょう。第三に、イベントログの保管場所・保存・マスキングポリシーを設計段階で確定しましょう——運用費用と規制リスクの大半はそこで分かれます。モデル競争の時代が暮れ、エージェント「運用」の時代がまさに開こうとしています。
