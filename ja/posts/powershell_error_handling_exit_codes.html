この記事のコードはスクリプトファイルとして保存し、powershell.exe -NoProfile -Fileで実行した。出力はWindows PowerShell 5.1(5.1.19041.6456)で得られたそのままで、パスだけC:\demoにしてある。エラーメッセージは、Windows PowerShellを直接起動したセッションで得た英語の原文である。同じPCでGit Bashからpowershell.exeを起動すると、同じエラーが韓国語のメッセージで表示されるため、メッセージの文言はこの環境のものである。項目ごとに「コード → 実際の出力 → 理由」の順で書く。理由の部分で公式ドキュメントを引用した箇所はドキュメントの文であることを明示し、実行で見たものと区別する。

はじめに - 失敗は3か所で別々に判定される

PowerShellスクリプトが失敗したとき、呼び出し元(タスクスケジューラ、CIランナー、別のスクリプト)が受け取る値はプロセス終了コードひとつだ。ところがその値が決まるまでに、PowerShellの内部には判定の台帳が3つある。1つ目は例外、つまりterminatingエラーとtry/catch。2つ目は直前のコマンドの成否を持つ$?。3つ目は最後に実行したネイティブプログラムの終了コードを持つ$LASTEXITCODEだ。3つの台帳は自動では連動しない。ある台帳に失敗が記録されても、残り2つに記録されるとは限らない。

用語を先に整理する。コマンドレットはGet-Itemのように.NETクラスとして実装されたPowerShellのコマンドで、ネイティブコマンドはcmd.exeやgit.exeのように別プロセスとして実行され整数の終了コードを返す外部実行ファイルだ。ErrorRecordはPowerShellがエラーごとに作るオブジェクトで、例外、エラーカテゴリ、対象オブジェクト、スクリプト上の位置を持つ。失敗が例外として発生したのか、エラーストリームに書かれただけなのかが、この記事で観察するすべての違いを分ける。

bashではset -eと$?だけで大半が説明できる。PowerShellはオブジェクトベースのエラーモデルの上にネイティブプログラムの整数終了コードが別に載っているため、同じ「失敗」が台帳ごとに違って見える。bash側のerrexitとpipefailの死角はシェルの終了コードと set -e - 何を捕まえ何を見逃すかが実行出力で整理しているので、この記事はPowerShellに限定する。

この記事が答える問いは次のとおりだ。

  • try/catchが捕まえるエラーと捕まえないエラーの境目はどこか。
  • $ErrorActionPreferenceはどの範囲まで効き、-ErrorActionとぶつかったときどちらが勝つか。
  • ネイティブコマンドが失敗したとき、$?・$LASTEXITCODE・例外のうち何が変わるか。
  • exitとreturnはプロセス終了コードにどう反映されるか。
  • 同じスクリプトを-Fileと-Commandで呼ぶと終了コードはどう変わるか。
  • Write-Errorとthrow、パイプライン途中のエラー、$Errorコレクションはそれぞれ何を残すか。

terminatingエラーとnon-terminatingエラー - try/catchが見るもの

Microsoft Learnのabout_Try_Catch_Finallyは、try/catchが扱う対象をこう定義している。PowerShellのterminatingエラーには、現在の文を止めるstatement-terminatingエラーと、呼び出しスタック全体を巻き戻すscript-terminatingエラーの2種類があり、どちらもtry/catchで捕まえられる。ここに入らないのがnon-terminatingエラーだ。コマンドレットがエラーストリームにエラーを書き込み、次の項目の処理を続けるケースである。ドキュメントの$ErrorActionPreferenceの項は、この既定の動作をContinue(エラーを表示して実行を続ける)と書いている。

境目を実行で確かめた最初のコードは、存在しないパスにGet-Itemを使うものだ。

try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
Get-Item : Cannot find path 'C:\demo\nope.txt' because it does not exist.
                    At C:\demo\e1.ps1:3 char:7
                    + try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught:  ...
                    +       ~~~~~~~~~~~~~~~~~~~~~~~~~
                        + CategoryInfo          : ObjectNotFound: (C:\demo\nope.txt:String) [Get-Item], ItemNotFoundException
                        + FullyQualifiedErrorId : PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
                    
                    after Get-Item

エラーメッセージは画面に出たがcatchブロックは実行されず、try内の次の文'after Get-Item'がそのまま実行された。理由は先の定義どおりだ。Get-Itemはこのエラーをnon-terminatingとして書いて処理を続けたので、例外が発生していない。同じコードに-ErrorAction Stopを付けると結果が変わる。

try { Get-Item C:\demo\nope.txt -ErrorAction Stop; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().Name }
caught: ItemNotFoundException

今度はcatchが実行され、'after Get-Item'は出力されなかった。ドキュメントは、$ErrorActionPreferenceをStopにするとnon-terminatingエラーがscript-terminatingエラーに格上げされると説明し、-ErrorAction共通パラメーターは1つのコマンドについてその設定を上書きすると書いている。下の表は、同じスクリプトでいろいろな失敗をtry/catchに入れた結果だ。

tryの中のコードcatchの実行catchの$_.Exceptionの型tryの中の次の文
Get-Item C:\demo\nope.txtされない—実行される
Get-Item C:\demo\nope.txt -ErrorAction Stop実行ItemNotFoundException実行されない
$ErrorActionPreference = 'Stop'のあとのGet-Item C:\demo\nope.txt実行ItemNotFoundException実行されない
1/0実行RuntimeException実行されない
NonsenseString(存在しないコマンド)実行CommandNotFoundException実行されない

Write-Error 'from Write-Error'されない—実行される

表から読み取れる規則は次のとおりだ。

  • コマンドレットが自分でエラーストリームに書くエラー(Get-Itemのパスなし、Write-Error)は、既定の設定ではcatchに届かない。
  • 言語が直接起こすエラー(0での除算、型変換の失敗、存在しないコマンド、throw)は例外なので、常にcatchに入る。
  • 同じコマンドレットの同じ失敗が、-ErrorAction Stopひとつでcatchの対象になる。スクリプト全体に適用するなら$ErrorActionPreference = 'Stop'を使う。
  • catch内の$_はErrorRecordで、$_.Exceptionの型でエラーの種類を分けられる。ドキュメントは、PowerShellがすべての例外をRuntimeExceptionで包むと書いている。

$ErrorActionPreferenceの範囲と-ErrorAction

about_Preference_Variablesは、$ErrorActionPreferenceの値としてSilentlyContinue・Stop・Continue(既定)・Inquire・Ignoreを挙げ、設定を変えるとその範囲と子の範囲にだけ適用されると書いている。範囲を実行で確かめたコードだ。

'start: ' + $ErrorActionPreference
                    function Inner { 'inner sees: ' + $ErrorActionPreference }
                    function SetsStop { $ErrorActionPreference = 'Stop'; 'in SetsStop: ' + $ErrorActionPreference; Inner }
                    SetsStop
                    'after SetsStop: ' + $ErrorActionPreference
start: Continue
                    in SetsStop: Stop
                    inner sees: Stop
                    after SetsStop: Continue

関数の中でStopに変えた値は、その関数が呼んだ関数(Inner)には見え、関数が終わって呼び出し元に戻ると元のContinueに戻る。逆方向も同じだ。呼び出し元が$ErrorActionPreference = 'SilentlyContinue'にしてInnerを呼ぶと、inner sees: SilentlyContinueと出力された。つまりこの変数は呼び出しチェーンに沿って下へ継承され、上へは漏れない。

2つの設定がぶつかるときは、コマンド単位の-ErrorActionが勝つ。

$ErrorActionPreference = 'Stop'
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    'survived: ' + $?
survived: False

グローバル設定がStopなのにスクリプトは次の行まで進み、エラーメッセージも出なかった。ただし$?はFalseだ。エラーを隠すことと、失敗がなかったことにすることは別である。

SilentlyContinueとIgnoreはどちらもメッセージを隠すが、$Errorに残すかどうかが違う。ドキュメントはIgnoreが$Errorにエラーを追加しないと書いている。

$Error.Clear()
                    Get-Item C:\demo\a.txt -ErrorAction SilentlyContinue
                    'after SilentlyContinue, $Error.Count = ' + $Error.Count
                    Get-Item C:\demo\b.txt -ErrorAction Ignore
                    'after Ignore, $Error.Count = ' + $Error.Count
after SilentlyContinue, $Error.Count = 1
                    after Ignore, $Error.Count = 1

SilentlyContinueのあとに1件たまり、Ignoreのあとも1件のままだ。Ignoreは記録すら残さないので、あとで$Errorをたどる手がかりが消える。

ドキュメントは$ErrorActionPreferenceの値としてIgnoreも挙げているが、5.1ではIgnoreはcmdletの-ErrorActionパラメーターの値としてしか使えなかった。変数に代入すること自体はエラーなく通り、その状態でエラーが発生した瞬間にNotSupportedExceptionが出た。

$ErrorActionPreference = 'Ignore'
                    'preference set to: ' + $ErrorActionPreference
                    Get-Date | Out-Null
                    'after Get-Date, preference: ' + $ErrorActionPreference
                    try { Get-Item C:\demo\nope.txt; 'after Get-Item' } catch { 'caught: ' + $_.Exception.GetType().FullName; $_.Exception.Message }
                    'preference now: ' + $ErrorActionPreference
preference set to: Ignore
                    after Get-Date, preference: Ignore
                    caught: System.NotSupportedException
                    The value Ignore is not supported for an ActionPreference variable. The provided value should be used only as a value for a preference parameter, and has been replaced by the default value. For more information, see the Help topic, "about_Preference_Variables."
                    preference now: Continue

エラーを出さないGet-Dateは普通に実行され、変数はIgnoreのままだった。ところがGet-Itemがエラーを出すと、NotSupportedExceptionがcatchに入り、本来のItemNotFoundExceptionはcatchに届かなかった。メッセージは、Ignoreは設定変数の値としては使えず、設定パラメーターの値としてだけ使うべきで、与えた値は既定値に置き換えられたと伝えている。実際、最後の行では変数がContinueに戻っていた。まとめると、5.1のIgnoreは-ErrorAction Ignoreのようにパラメーターでしか使えず、変数にIgnoreを置くと、エラーが起きた最初の箇所でこの例外に変わる。この動作は5.1で実行した結果であり、7では実行していない。

この節の結果から導ける使い分けは単純だ。エラーを無視してよい特定の1コマンドには-ErrorAction SilentlyContinueを付け、記録は残す。Ignoreは$Errorに残さないので、あとで原因を調べる必要が出うる処理には使わない。スクリプト全体の既定はStopにして、例外にしたくない箇所だけコマンド単位で上書きする構成が、ここまでの実行結果と矛盾しない。

about_Try_Catch_FinallyのNoteが知らせる動作がもうひとつある。$ErrorActionPreferenceがSilentlyContinueまたはIgnoreのとき、throwさえ伝播せず次の文へ進む。この文はドキュメントのもので、以下の実行はSilentlyContinueだけで行った。Ignoreは上で見たとおり変数に置けないため、確認できなかった。

$ErrorActionPreference = 'SilentlyContinue'
                    throw 'boom'
                    'line after throw ran'
line after throw ran

メッセージboomは出力されず、次の行が実行された。SilentlyContinueについては、ドキュメントの説明と一致する結果だ。この設定をスクリプトの先頭に癖で置くと、throwで作った中断点まで消える。

Stopを使ったあと$Errorに残るものも実行で見た。

$Error.Clear()
                    try { Get-Item C:\demo\nope.txt -ErrorAction Stop } catch { }
                    $Error.Count
                    $Error[0].GetType().FullName
                    $Error[0].Exception.GetType().FullName
1
                    System.Management.Automation.ErrorRecord
                    System.Management.Automation.ItemNotFoundException

公式ドキュメントは、Stopが元のエラーに加えてActionPreferenceStopExceptionオブジェクトをエラーストリームに出すと書いている。この実行の$Errorには1件があり、その例外の型はItemNotFoundExceptionだった。2つの記述の関係は、この実行だけでは解釈しない。

$?と$LASTEXITCODE - ネイティブコマンドの失敗は例外ではない

about_Automatic_Variablesは、$?を直前のコマンドの実行状態(成功ならTrue、失敗ならFalse)、$LASTEXITCODEを最後に実行したネイティブプログラムまたはスクリプトの終了コードと定義している。ネイティブコマンドについては、$LASTEXITCODEが0なら$?はTrue、0以外ならFalseという文が続く。ネイティブコマンドが失敗したときの3つの台帳を実行で見た。

cmd /c exit 3
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = False
                    $LASTEXITCODE = 3

失敗は$?と$LASTEXITCODEに記録された。では例外の台帳はどうか。$ErrorActionPreferenceをStopにして、同じコマンドをtryの中で実行した。

$ErrorActionPreference = 'Stop'
                    try { cmd /c exit 3; 'next line ran' } catch { 'caught' }
next line ran

catchは実行されず、次の文が実行された。ネイティブプログラムの0以外の終了コードはエラーではなく値だ。PowerShellが代わりに止めてはくれないので、Stopを有効にしたスクリプトでもネイティブ呼び出しの失敗は$LASTEXITCODEを自分で読まないと分からない。存在しないプログラム名(nosuchprogram.exe)を実行すると話が違う。このときはPowerShellがコマンドを見つけられなかったので、try内でCommandNotFoundExceptionが捕まった。プログラムが起動したあとの失敗と、起動すらできなかった失敗は台帳が違う。

2つの変数の寿命も違う。次のコードはネイティブ呼び出しのあとにコマンドレットを実行したケースだ。

cmd /c exit 3
                    Get-Date | Out-Null
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
                    Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    '$? = ' + $?
                    '$LASTEXITCODE = ' + $LASTEXITCODE
$? = True
                    $LASTEXITCODE = 3
                    $? = False
                    $LASTEXITCODE = 3

成功したコマンドレットのあとも、失敗したコマンドレットのあとも、$LASTEXITCODEは3のまま残った。この変数はネイティブプログラムやスクリプトを実行したときだけ更新されるので、数行前に残った値を今の呼び出しの結果として読んでしまう間違いが起こりうる。$?は逆に、寿命が1文だ。

Get-Item C:\demo\nope.txt -ErrorAction SilentlyContinue
                    $ok = $?
                    '$? read once = ' + $ok
                    '$? read again (after the assignment) = ' + $?
$? read once = False
                    $? read again (after the assignment) = True

$ok = $?という代入自体が成功したコマンドなので、$?を読み直すとTrueになる。判定が必要なら、失敗したコマンドの直後の文で変数に移しておく。関数の中ではさらに一段ある。ドキュメントは、Write-Errorが実行直後に$?をFalseにするが、その関数を呼んだ側の$?はFalseにしないと書いており、実行も同じだった。

function T { Write-Error 'bad' -ErrorAction SilentlyContinue; 'inside: ' + $? }
                    T
                    'outside: ' + $?
inside: False
                    outside: True

ネイティブのstderrを2>&1でエラーストリームに合流させると、例外の台帳にも影響が及ぶ。同じコマンドがリダイレクトの有無でStopのもとで違う動きをした。下ではcmd /cがstdoutに1行、stderrに1行を書き、終了コード2で終わる。

$ErrorActionPreference = 'Stop'
                    try {
                      $out = cmd /c "echo to-stdout & echo to-stderr 1>&2 & exit 2" 2>&1
                      'no exception; lines captured: ' + @($out).Count
                    } catch {
                      'caught: ' + $_.Exception.GetType().Name + ' / ' + $_.FullyQualifiedErrorId
                    }
caught: RemoteException / NativeCommandError

終了コードが0でもstderrを合流させた2番で例外が出て、終了コードが2でもstderrの行がない3番では出なかった。1番のコマンドから2>&1だけを外した4番は、同じ終了コード2と同じstderrの行を持つのに例外はなかった。先にcmd /c exit 3が終了コードだけでは例外を作らなかったことと合わせると、この4通りで例外の有無は、終了コードではなく、stderrの行が2>&1でエラーストリームのErrorRecordになったかどうかとだけ連動した。この動作は5.1で4通りを実行した結果であり、2>$nullなどほかのリダイレクトは試していない。したがって、ネイティブ呼び出しの失敗検出は、リダイレクトの有無やStopの設定に頼らず、呼び出しの直後に$LASTEXITCODEを検査するコードを明示的に書くのが最も確実だ。

exitとreturn - プロセス終了コードを決めるもの

プロセス終了コードは、起動方法によって別の規則で決まる。about_PowerShell_exeは、-Fileではスクリプトがexitで終わればその数値がプロセス終了コードになり、script-terminatingエラーなら1だと書いている。-Commandでは最後のコマンドの$?がTrueなら0、Falseなら1で、最後のコマンドが0・1以外の終了コードを設定した外部プログラムやスクリプトなら、そのコードは1に変換されると書いている。同じスクリプトを2通りの方法で呼び、親のPowerShellで$LASTEXITCODEを読んだ結果が次の表だ。スクリプトは1行のものである。

スクリプトの内容-Fileの終了コード-Command "& スクリプト"の終了コード出力から読めたこと
'script body ran'00正常完了
'before'; throw 'boom'; 'after'11beforeのあと中断、afterなし
'before'; Write-Error 'bad'; 'after'00afterまで実行、エラーメッセージが出力
'before'; exit 5; 'after'51afterなし
'before'; return 5; 'after'00数値5が出力として出て、afterなし
cmd /c exit 3; 'done'00doneが出力
'first'; cmd /c exit 300最終行が失敗しても0
cmd /c exit 3; if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }; 'done'31doneなし
$ErrorActionPreference='Stop'; cmd /c exit 3; 'done'00Stopなのにdoneが出力
try { 'in try'; exit 4 } finally { 'in finally' }41in finallyが出力された
function F { exit 7 }; 'before'; F; 'after'71関数内のexitが全体を終了、afterなし
function F { return 7 }; 'before'; F; 'after'007が出力として出て、afterも実行
try { throw 'x' } catch { 'handled'; exit 2 }21handledが出力
try { throw 'x' } catch { 'handled' }00捕まえて握りつぶせば成功
'ok'; if ( {(構文エラー)111行目のokも出力されない

表のうち理由がはっきりしている項目を解くと次のようになる。

  • exit 5は-Fileでは5がそのまま出るが、-Command "& スクリプト"では1に変換される。ドキュメントが書く「0・1以外のコードは1に変換」と同じ結果だ。
  • return 5は終了コードではなく出力だ。スクリプトの最上位でreturnはスクリプトを終えるだけで、値は出力ストリームに出るのでプロセス終了コードは0になる。関数内のreturn 7も同じ理由で7が画面に出る。
  • 関数内のexit 7は、関数ではなくプロセス全体を終える。呼び出し元側でafterが出力されなかった。
  • スクリプトの最終行がネイティブ失敗(cmd /c exit 3)でも、-Fileは0を返す。ドキュメントが書く「スクリプトが正常完了すれば0」と同じ結果で、値を渡すにはexit $LASTEXITCODEが必要だ。
  • try { exit 4 } finally { ... }でfinallyが実行された。about_Try_Catch_Finallyがcatch内のexitについて書く文と同じ向きの結果が、try内のexitでも得られた。
  • $ErrorActionPreference = 'Stop'でもネイティブ終了コード3を止められず、doneが出力された。前の節の結果と同じだ。
  • 構文エラーのあるスクリプトは1行目も実行されず、終了コードは1になる。ドキュメントは構文解析エラーが$?に影響しないと書くが、この場合はスクリプト実行前の段階の失敗なので、プロセス終了コードが1になった。

コマンド文字列を直接渡す-Commandでは、判定の基準が最後のコマンドの$?であることがいっそうはっきりする。親のPowerShellからpowershell.exe -NoProfile -Commandに次の文字列を1つずつ渡した結果だ。

-Command文字列終了コード理由
cmd /c exit 31最後のコマンドの$?がFalseで、3は1に変換
cmd /c exit 3; exit $LASTEXITCODE3明示的なexitで値を保存
cmd /c exit 3; 'after'0最後のコマンド(文字列出力)が成功
Get-Item C:\demo\nope.txt1non-terminatingエラーでも最後のコマンドが失敗
Get-Item C:\demo\nope.txt; Get-Date | Out-Null0失敗のあとの成功コマンドが最後
Get-Item C:\demo\nope.txt -ErrorAction Stop1script-terminatingエラー

2つ目の表の結論は1行で言える。-Commandは最後のコマンドの成否だけを見るので、途中の失敗はそのあとの成功コマンド1つで消える。呼び出し元が具体的な終了コードや途中の失敗を知る必要のある自動化には-Fileが安全で、-Commandを使うなら文字列の末尾にexit $LASTEXITCODEを付ける。これはドキュメントが示す方法でもある。

パイプライン途中で起きたエラー

about_Pipelinesは、パイプラインがオブジェクトを1つずつ次のコマンドに送ると説明している。このため、途中の段階のエラーはすでに通過した項目には影響せず、あとの項目が流れ続けるかどうかが論点になる。スクリプトブロックの中で0で割るケースを3通りで実行した。

1,2,0,4 | ForEach-Object { 10 / $_ }
10
                    5
                    Attempted to divide by zero.
                    At C:\demo\e4.ps1:2 char:28
                    + 1,2,0,4 | ForEach-Object { 10 / $_ }
                    +                            ~~~~~~~
                        + CategoryInfo          : NotSpecified: (:) [], RuntimeException
                        + FullyQualifiedErrorId : RuntimeException
                    
                    2.5

0の項目でエラーが起きたが、4の項目は処理されて2.5が出力された。エラーはその項目の文ひとつだけを止め、パイプラインは流れ続けた。同じパイプラインをtry/catchで包むと変わる。

try { 1,2,0,4 | ForEach-Object { 10 / $_ } } catch { 'caught: ' + $_.Exception.Message }
10
                    5
                    caught: Attempted to divide by zero.

2.5は出力されなかった。catchがエラーを受け取った瞬間にパイプライン全体が中断されたのだ。$ErrorActionPreference = 'Stop'のもとでも結果は同じで、スクリプトブロック内のthrow(3の項目で投げる場合)もitem 1、item 2のあとにcaught: threeで終わった。したがって「エラーが出ても残りの項目は処理し、失敗だけ集める」設計では、try/catchをパイプラインの外に置いてはいけない。項目処理ブロックの中で項目ごとに捕まえる必要がある。

ここで見える動作を整理すると、「失敗した項目だけ飛ばして残りを続ける」か「そこで全体を止める」かは、エラーの種類とtry/catchを置いた位置の組み合わせで決まる。ループやForEach-Objectの内側にtry/catchを置けば項目単位の処理になり、外側に置けば最初のエラーで全体が止まる。バッチ処理の設計では、どちらの意味にしたいのかを先に決めてからtry/catchの位置を選ぶことになる。

1つのコマンドレットが複数の入力を受ける場合は、non-terminatingエラーが結果に混ざって出る。4つのパス(2つは存在しないファイル)を一度にGet-Itemへ渡し、2>&1で結果を変数に受けて型を数えた。

$r = Get-Item C:\demo\e1.ps1, C:\demo\nope1.txt, C:\demo\e2.ps1, C:\demo\nope2.txt 2>&1
                    $r | ForEach-Object { $_.GetType().Name }
FileInfo
                    ErrorRecord
                    FileInfo
                    ErrorRecord

成功したオブジェクトとErrorRecordが入力順に混ざって出た。失敗した項目が、あとの項目の処理を妨げなかったということだ。この構造を知らないと、結果の変数にエラーオブジェクトが混じっているのを見て驚くことになる。

パイプラインが終わったあとで$?を読むと、段階ごとの動作が現れる。

Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue | ForEach-Object { 'x' }
                    '$? = ' + $?
                    Get-Date | ForEach-Object { Get-Item C:\demo\nope1.txt -ErrorAction SilentlyContinue }
                    '$? = ' + $?
$? = False
                    $? = True

最初の段階のコマンドレットがエラーを書いたパイプラインは、最後の段階が成功しても$?がFalseだった。逆に、最後の段階のスクリプトブロックの中で起きた失敗は$?に反映されなかった。ドキュメントが$?を「最後のコマンド」の状態と定義している点は2つ目の結果と合うが、1つ目の結果はその定義だけでは説明できない。どちらにせよ、パイプラインのあとの$?は失敗の検出手段として信頼しにくい。段階ごとの失敗は-ErrorVariableか$Errorで集めるほうがよい。

Write-Errorとthrow - 流れを止めるか

2つのコマンドは名前が似ているが、エラーモデルでは反対側に立っている。これまでの実行結果を1つの表にまとめた。

観察項目Write-Errorthrow
エラーの種類non-terminating(エラーストリームに記録)script-terminating
次の文の実行実行される(afterが出力)実行されない
既定設定でのtry/catch捕まらない捕まる
-Fileスクリプトの終了コード01
$ErrorActionPreference = SilentlyContinueのあとメッセージは隠れ、$Errorには記録される伝播せず次の文が実行される
生成される例外の型WriteErrorException文字列のthrowはRuntimeException

同じスクリプトで2つのコマンドを1行ずつ実行した出力が、上の表の根拠だ。

try { Write-Error 'from Write-Error'; 'after Write-Error' } catch { 'caught: ' + $_.Exception.Message }
                    try { throw 'from throw'; 'after throw' } catch { 'caught: ' + $_.Exception.Message }
C:\demo\e1.ps1 : from Write-Error
                        + CategoryInfo          : NotSpecified: (:) [Write-Error], WriteErrorException
                        + FullyQualifiedErrorId : Microsoft.PowerShell.Commands.WriteErrorException,e1.ps1
                    
                    after Write-Error
                    caught: from throw

終了コードまで追うと差はさらに大きくなる。'before'; Write-Error 'bad'; 'after'を-Fileで実行すると、before、エラーメッセージ、afterの順に出て、終了コードは0だ。'before'; throw 'boom'; 'after'はbeforeのあとにエラーが出力され、afterはなく、終了コードは1である。スクリプトが失敗を呼び出し元に知らせなければならないなら、Write-Error1行では足りない。ログにはエラーが出るが、タスクスケジューラは成功と見なす。

Write-Errorのパラメーターでエラーの分類を決められる。次のコードはカテゴリと識別子を指定してから$Error[0]を読んだ結果だ。

Write-Error -Message 'with category' -Category InvalidArgument -ErrorId 'My.Id' -ErrorAction SilentlyContinue
                    $Error[0].CategoryInfo.Category.ToString() + ' / ' + $Error[0].FullyQualifiedErrorId
InvalidArgument / My.Id,e7.ps1

throwは文字列のほかに例外オブジェクトも投げられ、catchは型で振り分けられる。文字列を投げるとRuntimeExceptionに包まれる。

try { throw [System.IO.FileNotFoundException]::new('typed') } catch [System.IO.FileNotFoundException] { 'typed catch: ' + $_.Exception.Message }
                    try { throw 'plain string' } catch { $_.Exception.GetType().FullName + ' / ' + $_.CategoryInfo.Category }
typed catch: typed
                    System.Management.Automation.RuntimeException / OperationStopped

まとめると、Write-Errorは「この項目は失敗したが続けよ」、throwは「ここで止めよ」だ。項目ごとの失敗を報告するライブラリ的な関数は前者を、前提が崩れてこれ以上進めない場合は後者を使う。

$Errorコレクション - 何がたまるか

about_Automatic_Variablesは$Errorを最近のエラーオブジェクトの配列と説明し、最も新しいものが$Error[0]だと書いている。about_Preference_Variablesの既定値の表は$MaximumErrorCountを256としている。2件続けてエラーを起こしたあとで読んだ結果だ。

$Error.Clear()
                    Get-Item C:\demo\first.txt -ErrorAction SilentlyContinue
                    Get-Item C:\demo\second.txt -ErrorAction SilentlyContinue
                    'count: ' + $Error.Count
                    '$Error[0] : ' + $Error[0].Exception.Message
                    '$Error[1] : ' + $Error[1].Exception.Message
count: 2
                    $Error[0] : Cannot find path 'C:\demo\second.txt' because it does not exist.
                    $Error[1] : Cannot find path 'C:\demo\first.txt' because it does not exist.

あとのエラーがインデックス0に来て、前のエラーは後ろへ押される。ErrorRecord1つが持つプロパティも実行で読んだ。前のブロックに続けて同じスクリプトで実行したので、ScriptLineNumberは2つ目のGet-Itemがある3行目である。

$e = $Error[0]
                    $e.GetType().FullName
                    'Exception          : ' + $e.Exception.GetType().FullName
                    'CategoryInfo       : ' + $e.CategoryInfo
                    'FullyQualifiedId   : ' + $e.FullyQualifiedErrorId
                    'TargetObject       : ' + $e.TargetObject
                    'ScriptLineNumber   : ' + $e.InvocationInfo.ScriptLineNumber
System.Management.Automation.ErrorRecord
                    Exception          : System.Management.Automation.ItemNotFoundException
                    CategoryInfo       : ObjectNotFound: (C:\demo\second.txt:String) [Get-Item], ItemNotFoundException
                    FullyQualifiedId   : PathNotFound,Microsoft.PowerShell.Commands.GetItemCommand
                    TargetObject       : C:\demo\second.txt
                    ScriptLineNumber   : 3

これらのプロパティは、$_(catch内)と$Error[0]のどちらからも同じ名前で読める。通知メッセージにFullyQualifiedErrorIdとScriptLineNumberを一緒に入れると、原因の追跡が速くなる。

捕まえたエラーも$Errorに入る。ドキュメントはtryブロックでエラーが起きるとまず$Errorに保存されると書いており、実行でもtry { throw 'caught-me' } catch { ... }のあと$Error.Countは1だった。ただしcatch内の$_と$Error[0]をReferenceEqualsで比べるとFalseが出た。同じエラーを指しているが、同一のオブジェクト参照かどうかは確認できなかった。

$Error.Clear()
                    try { throw 'caught-me' } catch { 'in catch: $_ is $Error[0] -> ' + [object]::ReferenceEquals($_, $Error[0]) }
                    'count: ' + $Error.Count
in catch: $_ is $Error[0] -> False
                    count: 1

-ErrorVariableは指定した変数にエラーを集める共通パラメーターで、この実行では$Errorにも一緒に記録された。

$Error.Clear()
                    Get-Item C:\demo\third.txt -ErrorAction SilentlyContinue -ErrorVariable ev
                    'ev.Count: ' + $ev.Count + ' / $Error.Count: ' + $Error.Count
                    Get-Item C:\demo\fourth.txt -ErrorAction SilentlyContinue -ErrorVariable +ev
                    'ev.Count: ' + $ev.Count
ev.Count: 1 / $Error.Count: 1
                    ev.Count: 2

1行目は-ErrorVariable evで1回失敗したあとの値で、2行目は-ErrorVariable +ev(先頭に+)でもう1回失敗して蓄積したあとの$ev.Countだ。+がないと変数は毎回上書きされる。実務では、スクリプトの先頭で$Error.Clear()を1回呼び、終了直前に$Error.Countと$Error | Select-Object -First 5で握りつぶされたエラーがなかったかを点検する方法が使える。前の節のSilentlyContinueはこの点検にかかり、Ignoreはかからない。

bashとの対応 - set -eに当たるものと当たらないもの

bashに慣れた人がPowerShellスクリプトを書くとき、最初にする質問が「set -eはどこにあるのか」だ。上の実行結果から対応を短くまとめる。コマンド全体の対照は別の記事の役割なので、ここではエラーと終了コードに限る。

bashPowerShell 5.1実行で確認した違い
set -e$ErrorActionPreference = 'Stop'コマンドレットのエラーだけを例外に格上げする。ネイティブ終了コード3はStopのもとでも止められなかった
$?(直前の終了状態の整数)$?(True/False)と$LASTEXITCODE(整数)値が2つに分かれる。$LASTEXITCODEはコマンドレットの実行では更新されない
cmd || exit $?if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }この形で-Fileのとき終了コード3が伝わった
trap ... EXITtry/finallyexitのときもfinallyが実行された(終了コード4)

この表にはpipefailの行がない。パイプラインの段階ごとの状態は、6節で見たように、段階の種類によって$?への反映が違った。bashのset -eの例外規則とpipefailの詳細は、bash側の記事が扱っている。

実践パターン - ネイティブ呼び出しラッパーと終了コードの伝達

上の実行で得た規則を1つのスクリプトにまとめると次のようになる。先頭でStopを有効にしてコマンドレットのエラーを例外にし、ネイティブ呼び出しはラッパーが$LASTEXITCODEを調べてthrowに変え、catchで呼び出し元が読む終了コードをexitで決め、finallyで後始末をする。

$ErrorActionPreference = 'Stop'
                    function Invoke-Native {
                        param([scriptblock]$Command)
                        & $Command
                        if ($LASTEXITCODE -ne 0) { throw ('native command failed with exit code ' + $LASTEXITCODE) }
                    }
                    try {
                        'step 1'
                        Invoke-Native { cmd /c exit 0 }
                        'step 2'
                        Invoke-Native { cmd /c exit 3 }
                        'step 3 (not reached)'
                    }
                    catch {
                        'ERROR: ' + $_.Exception.Message
                        exit 3
                    }
                    finally {
                        'cleanup runs'
                    }

このスクリプトをpowershell.exe -NoProfile -Fileで実行し、親で$LASTEXITCODEを読んだ結果だ。

exit code = 3
                    step 1
                    step 2
                    ERROR: native command failed with exit code 3
                    cleanup runs

3つ目のステップは実行されず、exit 3のあともfinallyの後始末が実行され、プロセス終了コードは3だった。このパターンが依存する事実は、すべて前の節で実行して見たものだ。

  • ネイティブの失敗は例外ではないので、ラッパーでthrowに格上げする(4節)。
  • exitがあってもfinallyは実行される(5節)。
  • -Fileはexitの値をそのまま返す(5節)。

このパターンを使うときの点検項目は次のとおりだ。

  • スクリプト先頭の$ErrorActionPreferenceの値は意図したものか。SilentlyContinueにするとthrowも握りつぶされる。
  • ネイティブ呼び出しの直後に$LASTEXITCODEを読んでいるか。数行あとの値は以前の呼び出しのものかもしれない。
  • 呼び出し元が-Commandで呼ぶ構造なら、文字列の末尾にexit $LASTEXITCODEがあるか。
  • ラッパーを通さず2>&1でstderrを合流させたネイティブ呼び出しが、Stopのもとで例外に変わらないか。
  • 終了直前に$Error.Countを確認し、IgnoreではなくSilentlyContinueで握りつぶされたエラーを点検しているか。

確認できなかったこと

  • $ErrorActionPreferenceがIgnoreのときthrowが伝播しないというドキュメントのNoteのIgnore部分。5.1では変数にIgnoreを置くとエラーが起きる箇所でNotSupportedExceptionに変わり再現できず、確認したのはSilentlyContinueだけである。
  • PowerShell 7(pwsh)の動作。このPCにはpwshがインストールされておらず、5.1との違いを実行で比べられなかった。公式ドキュメントが5.1のページの中で述べているのは、括弧(...)・$(...)・@(...)で包んだ文がPowerShell 7より前は$?を常にTrueに戻していたが7で変わったという点と、-Fileでスイッチパラメーターに明示的なBoolean値を渡せない制限がPowerShell 6(pwsh.exe)で取り除かれたという点だけである。
  • bashのpipefailに当たる5.1の設定。参照した公式ドキュメント5件では見つからなかった。
  • ドキュメントがStopが出すと書くActionPreferenceStopExceptionが、エラーストリームのどこに現れるか。この実行では$Errorに1件しかなかった。
  • cmd.exe・タスクスケジューラ・CIランナーがこの終了コードを受け取る方法。この記事は親のPowerShellで$LASTEXITCODEとしてだけ読んだ。
  • Ctrl+Cで中断したときの終了コード。ドキュメントは-Fileで0、-Commandで1と書くが、対話的な中断は自動実行が難しいので実行しなかった。
  • スクリプトモジュール・バイナリモジュール内のコマンドレットでの$ErrorActionPreferenceの継承、リモート実行(Invoke-Command)やバックグラウンドジョブでのエラー伝播。
  • ネイティブプログラムを一度も実行していないセッションでの$LASTEXITCODEの初期値と、ほかのWindowsビルドでの結果。
  • 同じ5.1でも、ホスト(コンソール・ISE・VS Code統合ターミナル)によってエラーの表示形式が違うかどうか。
