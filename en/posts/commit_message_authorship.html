Commit Messages Are Still Written by Hand

When and by whom commit messages get read, what a diff can never carry, and how far automatic generation can reasonably go

Aug 20, 2026 Dev & Infra

Introduction: The Three Seconds After the Editor Opens

The change is finished. You type git commit, the editor opens, and the cursor blinks on the first line. These days a tool will fill those three seconds for you. It reads the staged change, proposes a line, and the proposal is usually not wrong. The file names are right and the verb is plausible. Yet plenty of developers still delete that suggestion and start over.

It looks like stubbornness, or personal taste. It is neither. A commit message is not a summary of the change; it is the place that holds the information the change does not contain, and those two things are entirely different jobs. Summarizing is something machines do faster and more consistently than people. Information that was never recorded is something no model can produce, because producing it would mean recovering something that does not exist.

This is not an argument against generated commit messages. It is closer to the opposite: an attempt to draw the line between the commits you can hand to a tool and the commits where a person has to intervene. We will look at when messages get read and by whom, what the reader needs at that moment, how far the public conventions actually agree, and where team rules tend to break.

1. What the Original Post Argued - Six Reasons to Write by Hand

The topic came back around because of a personal blog post published on 17 August 2026, titled Why I still hand-write my commit messages. It was picked up on GeekNews and drew a long thread. The author's reasons come to roughly six.

  • To record the why - what changed is already fully visible in the change itself; what matters is the reasoning and the context behind the choice
  • To check yourself - the act of writing the message exposes whether you actually understand the change you just made
  • To keep ownership - even code produced with assistance belongs to the person who commits it, along with the responsibility for it
  • To mark where a tool was used - small, atomic commits make the boundary of tool assistance visible in the history itself
  • To keep a personal voice - the author says plainly that he does not want a tool imitating his writing. His phrasing is I do not actually want an AI to be able to write like I do
  • As an extension of a writing habit - commits are treated as part of the same record-keeping instinct that produces blog posts

The counterarguments in the discussion were just as clear. First, that a model can re-derive the reasoning from the change whenever it is needed, so writing it up front is wasted effort. Second, that mandating this across a whole team is not realistic. Third, that design trade-offs belong in code comments rather than in commits. All three have merit, and each is addressed below.

2. When and by Whom Commit Messages Get Read

The value of a commit message is not decided when it is written. It is decided months later, when someone lands on that line. That someone is usually not the author, and is usually in a hurry. The Linux kernel guide names the situation precisely: the explanation body goes into the permanent changelog, so it has to make sense to a competent reader who has long since forgotten the immediate details. The reader is a future stranger, and that stranger includes you, six months from now.

Concretely, here is where messages get opened.

MomentReaderWhat they wantHow they got there
Code reviewReviewerIntent and scope of the changeCommit list in the PR

Chasing deleted codeBug ownerWhen this handling disappearedgit log -S

The interesting column is not the tooling. It is the point where the tooling stops. Bisect will hand you the exact commit that introduced the problem, and that is the end of its job. If that commit's subject is fix: adjust logic and nothing else, the engineer starts reading code from scratch. If the body records the judgement and the constraints of that day, the round trip disappears. How to drive those history commands is covered separately in our guide to underused Git history commands. The point here is the quality of the destination those commands arrive at.

One more property is easy to overlook. These scenes work anywhere the repository exists. If the issue tracker is down, if the internal wiki was migrated and the links rotted, a laptop with a clone still shows the commit message intact. That is the practical benefit of keeping the context in the same place as the code.

3. What a Diff Tells You and What It Never Will

This is the core of the argument. A diff is a complete and precise record of what changed. When a human restates it in prose, information is usually lost rather than gained: five files were touched, three make it into the body. So restating what changed was never the job of a commit message in the first place.

Readable from the diffOnly ever in the message
Which lines in which files changedWhy this change was made now
Functions and signatures added or removedWhich alternative was tried and dropped
How a dependency version movedWhy it stopped at that version
Whether tests came alongUnder what conditions it reproduced
What a configuration value becameThe measurement behind that value
The final shape of the codeWhich neighbouring code was deliberately left alone

Everything in the right column shares one property: it came from outside the repository. The reproduction steps in an incident report, the usage pattern confirmed by a support ticket, the constraint a vendor replied with, the number a benchmark produced, the priority agreed in a meeting. None of it exists in the code. The commit message is very nearly the only place inside the repository where that outside context can be pinned down.

This is where the third counterargument arrives: surely trade-offs belong in code comments. Half true, and the dividing line is simple. If the constraint is needed every time someone reads that code, it is a comment. Why a constant must hold that exact value, why this ordering must not be swapped, belongs next to the code. If the information is only needed when tracing this change, it is a commit. What you discarded this time and why you narrowed the scope will be deleted along with the code at the next refactor. Commits are not deleted.

4. What You Did Not Do - Unrecorded Decisions Get Retried

There is a second category a diff structurally cannot hold: the work you did not do. Code that does not exist cannot be read by any tool. And in practice, some of the most valuable information lives exactly there.

  • The alternative you rejected - that you tried library A first and why you moved to B
  • The neighbouring code you deliberately left - you wanted to fix it too, but it fell outside this release
  • The fact that this is a stopgap - and what has to be resolved before it can be removed
  • The conditions behind a number - what data size and what hardware produced it
  • Where the external evidence lives - the bug report number, the vendor reply, the section of the specification

What happens when those are missing is entirely predictable. Six months later someone else stands in the same place and tries the same alternative. They hit the same trap and reach the same conclusion. That time is pure waste, and the cause of the waste was two unwritten sentences. A stopgap with no removal condition recorded quietly becomes permanent code. This is also the ceiling of automatic generation. A model summarizes the final state. What you threw away is not in the final state.

5. What Automatic Generation Is Genuinely Good At

None of this means every commit needs a human attached. Open any repository and a large share of the commits have self-evident reasons: typo fixes, formatting runs, routine dependency updates, regenerated code, bulk file moves. Demanding a why on those produces sentences like fix: correct typo - because there was a typo. That is the classic shape of a rule generating noise.

  • Mechanical summarizing - compressing a commit that changed dozens of files the same way into one accurate line
  • Format consistency - matching subject length, mood and prefixes to the team's convention every time
  • Lowering the language barrier - producing readable English subjects for teams that do not work in English natively
  • Catching omissions - not dropping the fifth file that a human would have forgotten to mention
  • Providing a draft - replacing a blank screen with something to correct

That last item is the most useful in practice. People write lazy commit messages not because they are lazy but because a blank editor is intimidating. If a draft summary is already there and the human only adds the reasoning underneath, the hand-written portion shrinks to two or three sentences. So the working rule should not be write everything by hand. It should be a human intervenes on commits whose reason is not self-evident.

6. What Generation Structurally Cannot Fill In

Take the first counterargument head on: a model can re-derive the reason from the change when it is needed. The flaw in that position is that it treats inference and recovery as the same operation. A model looks at the code and produces a plausible reason. That is not the reason that existed on the day. Most of the time the two values are close, which is exactly why the problem stays hidden. The trouble appears in the minority of cases where they diverge.

And that minority is precisely when people go looking for commit messages. Nobody digs through history for a change that the code already explains. Opening blame at 3 a.m. means the code has already failed to explain itself. In that moment a plausible wrong answer is worse than no answer at all, because it pushes the investigation in the wrong direction with confidence attached.

  • Rejected alternatives - no trace in the final code, so there is nothing to infer from
  • External facts - a vendor reply or an incident ticket exists nowhere in the repository
  • Prioritization - why now, and why only this far, is an organizational matter
  • Measurement conditions - the number survives in the code, the environment it was measured in does not
  • Degree of confidence - only the author knows whether this was a certain fix or an educated guess

The last one is worth a great deal in practice. A single sentence saying the root cause was not confirmed and only the symptom was blocked can save the next engineer days of investigation. And a tool cannot produce that sentence, because it has no way of knowing how confident the author was.

There is a side effect too. If you cannot get the message down to one clear sentence, the commit is usually too large or mixing several purposes. The fix is not a longer sentence; it is splitting the commit. The Git book makes the same point when it tells you not to bundle changes for multiple issues into one commit and to stage selectively with git add --patch. Writing the message ends up acting as a gate that inspects the shape of the commit.

7. The Shape of a Good Message - Subject, Body, Trailers, Reverts

On form, the public conventions largely agree already. The specific numbers differ by project, and that difference is more instructive than either number.

ElementConventionSource
Subject lengthA single summary line of 50 characters or lessGit git-commit docs
Subject length (kernel)70 to 75 characters, covering both what and whyLinux kernel submitting-patches
Subject and bodyText up to the first blank line is treated as the titleGit git-commit docs
Body widthWrap at roughly 72 charactersPro Git contributing guidelines
MoodImperative present: Fix bug, not Fixed bugPro Git and kernel docs alike
Bug referencesFixes: plus at least 12 characters of the SHA and the one-line summaryLinux kernel submitting-patches
Sign-off and co-authorsBlank line after the body, then Signed-off-by or Co-authored-byKernel docs and GitHub docs
RevertsAdd the reason yourself after the generated lineGit git-revert docs

There is no need to litigate 50 against 70 to 75. Both documents are asking for the same thing: the line has to deliver its meaning when read alone in a listing. The kernel allows a longer subject for an obvious reason. It requires the summary to carry both what the patch changes and why it changes it.

The imperative mood looks like taste but has a functional basis. The messages Git generates for you, such as merges and reverts, are all imperative, so matching them makes the history read like one document. Pro Git states it flatly: write Fix bug and not Fixed bug.

Revert commits are the easiest place to get sloppy. git revert records which commit was reverted automatically, and when run from a terminal it opens an editor by default. But that generated line only says what. The Git documentation states that explaining why the original commit is being reverted is strongly recommended. The same page even warns that repeatedly reverting reverts produces increasingly unwieldy subject lines such as Reapply "Reapply "..."" . Without one line of reasoning, whoever tries to reintroduce that feature months later has no idea why it left.

A word on conventions as such. Conventional Commits specifies type[scope]: description with breaking changes marked by ! or a dedicated footer, and its stated purpose is generating changelogs and determining semantic version bumps automatically. In other words the cost of the convention is recovered when an automation pipeline actually consumes the commits. That axis is a separate discussion, handled in our critique of Conventional Commits. The one overlap worth stating here: getting the prefix right says nothing whatsoever about whether the body contains a reason.

8. Committing AI-Assisted Code - Marking and Responsibility

This is the part the original author pressed hardest. Code produced with assistance still belongs to the person who commits it, and keeping commits small makes the boundary of that assistance visible in the history itself.

The mechanism already exists: commit message trailers. GitHub's documentation says to leave a blank line after the description and then add one Co-authored-by: name <name@example.com> line per co-author. On the Git side, git commit --trailer attaches the same kind of field. Because the format is fixed, the result can be aggregated mechanically later.

  • Keep commits small - do not mix assisted and hand-written ranges inside one commit
  • Name the tool - months later it is the only clue when a tool-specific pattern needs tracing
  • Record how you verified it - this matters more than the marking itself
  • Do not treat marking as a disclaimer - the trailer does not move review or accountability off the author
  • Agree the format first - if everyone marks differently, nothing can be searched or counted

Two situations make this marking pay for itself. One is quality retrospectives: if the same class of defect keeps appearing in code produced with a particular tool in a particular period, that pattern is only visible if the marking exists. The other is review allocation, since more teams now calibrate review depth to how much of a change was generated. Turning review itself into a procedure is covered in code review is a trained skill.

9. Making It a Team Rule - Hooks, Templates, Review Checks

The second counterargument, that you cannot force this on a team, is broadly right. But teams often fail because they force the wrong thing. If you start with format checks, messages that satisfy the format while saying nothing simply multiply. fix: fix bug passes every linter ever written and carries zero information.

Reverse the order. Make it easy to write first, and let machines block only what they can judge with certainty.

  • Commit template - set commit.template or pass -t to seed the editor. Put questions in it rather than field names, such as why is this needed now and what did you consider and reject
  • Show the diff in the editor - git commit -v appends the change below the message, and passing it twice also shows unstaged work. As the documentation puts it, it reminds you what the commit contains so you can describe it
  • prepare-commit-msg hook - runs right after the default message is prepared and before the editor starts. Its purpose is to edit the message file in place, so it is not suppressed by --no-verify. Good for injecting an issue number from the branch name
  • commit-msg hook - takes the finished message file as its single argument, and can normalize it or refuse the commit. A non-zero exit aborts, and it can be bypassed with --no-verify
  • Review checks - look at content rather than form. Five questions are enough

When a reviewer reads a commit message, these are the questions worth asking.

  • Can you guess what the change is from the subject alone
  • Does the body say why, or does it restate what
  • If an alternative was dropped or scope was left out, is that written down
  • If this is a stopgap, is the removal condition recorded
  • Is there a link to the issue or ticket

Only the last of those is a good candidate for a hook, because a machine can judge it with certainty. Ask a hook to decide whether the body contains a genuine reason and false positives accumulate, and once false positives accumulate the team starts appending --no-verify out of habit. At that moment the hook has effectively ceased to exist.

10. Choosing a Language - English or the Team's Own

Teams outside the English-speaking world hit this question constantly, and Korean teams are a good example. The criterion is not taste but the range of people who will read this repository.

  • Internal only, everyone shares a first language - writing the body in that language carries more information per sentence than a strained translation
  • Any chance of open-sourcing - go English from the start, because retranslating an entire history later is effectively impossible
  • External hires or contractor handover expected - English. The history outlives the people
  • The hybrid - imperative English subject, local-language body. It preserves release-note automation and tool compatibility while keeping explanatory precision
  • Consistency beats either choice - once the two are mixed, git log --grep finds only half of what you want, because it is a string search and you must try both languages

One caution when using the hybrid form. Keywords the issue tracker recognizes, and trailer names, must keep their defined English form regardless of the prose language. Translating Co-authored-by means no tool will recognize it. Write the sentences humans read in whatever language fits, and leave the lines machines read exactly as specified.

It is also worth noting that some teams now commit natural-language specifications into the repository itself. In that setup the role of the commit message grows rather than shrinks, because a place is needed to record why the specification changed. That direction is discussed in committing Korean specifications instead of code.

What Could Not Be Confirmed

  • No public benchmark or academic study comparing the quality of generated commit messages against hand-written ones was located for this piece. The comparison here rests on an information argument instead: what is absent from the final state cannot be recovered from it
  • No statistics were found on which language development organizations in Korea write commit messages in. The language guidance above is a decision framework, not a measurement
  • No data was found measuring the effect of commit body quality on incident recovery time
  • The original author's team size and tooling are not stated in the post

Conclusion: The Message Outlives the Code

Code disappears. The function you wrote today gets renamed in the next refactor and deleted in the redesign after that. The commit that recorded why it was built that way stays. It survives repository migrations, decommissioned wikis and replaced issue trackers. That is why the commit message is the longest-lived document in a project.

So the conclusion is not whether to use generation. It is let the tool draft, and add by hand only what the tool cannot know. In practice that is three habits. First, make the subject readable as a single line in a listing, and feel free to keep the generated summary for it. Second, on any commit whose reason is not self-evident, add two or three sentences of body covering what you rejected and what you left out of scope. Third, on a revert, write why you are reverting. Those three alone change what the next person sees when they open blame at 3 a.m.

The three seconds after the editor opens are really a question you are asking yourself: can I explain this change. If the answer is no, the problem is not the sentence. It is the commit.

Frequently Asked Questions

Q1: Is it fine to let AI generate commit messages?

A: For commits whose reason is self-evident, generation is enough. Dependency bumps, formatting runs and typo fixes fall into that group, because the change itself is the explanation. Commits that discarded an alternative, added a stopgap, or turned on a benchmark number are different. That information is not in the final state of the code, so it cannot be recovered from the change alone.

Q2: How long should a commit subject line be?

A: The Git documentation suggests a summary line of no more than 50 characters, a blank line, then a fuller description. The Linux kernel guide asks for 70 to 75 characters and requires both what and why in that line. The disagreement is the point. There is no absolute number, only the requirement that the line carry its meaning when read alone in a log listing.

Q3: Should design reasoning live in the commit message or a code comment?

A: If the constraint is needed every time someone reads that code, it is a comment. Why a constant must hold a specific value is the classic case. If it is only needed when tracing this change, it is a commit: rejected alternatives, narrowed scope, the removal condition for a stopgap. Comments can vanish in the next refactor; commits do not.

Q4: Should AI-assisted code be marked in the commit?

A: Marking is easy. Leave a blank line after the body and add a Co-authored-by line, or attach it with git commit --trailer. What marking does not do is transfer responsibility. It is a record that lets you trace where a tool was used, while review and accountability stay with the committer. If you mark, keep commits small so the marked range means something.

Q5: How do you introduce commit message rules to a team?

A: Starting with format checks usually fails, because messages that pass the format while saying nothing multiply. Put questions in the commit template and turn on the option that shows the diff in the commit editor. Reserve hooks for what a machine can judge with certainty, such as a missing issue reference, and handle the quality of the body in code review.
