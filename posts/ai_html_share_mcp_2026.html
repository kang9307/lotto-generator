AI가 만든 HTML을 링크 하나로 공유하기 - htmldrop과 MCP가 여는 산출물 공유 방식

마크다운에서 HTML로 옮겨가는 에이전트 산출물, 호스팅형 링크와 MCP 서버가 공유 문제를 어떻게 푸는가

2026-07-11 개발/인프라

서론: 산출물이 링크가 되어야 하는 이유

얼마 전까지 AI 에이전트의 산출물은 대부분 마크다운이었다. 채팅창에 렌더링되는 텍스트, 코드 블록, 표 몇 개면 충분했다. 그런데 요즘 에이전트에게 "보고서를 만들어줘", "대시보드를 짜줘", "이 데이터를 인터랙티브하게 보여줘"라고 시키면 결과물은 점점 HTML로 나온다. CSS로 레이아웃을 잡고, 차트 라이브러리를 붙이고, 클릭하면 값이 바뀌는 요소까지 들어간다. 문제는 그다음이다. 마크다운은 채팅창이 알아서 그려주지만, HTML 파일은 받는 사람이 직접 열어야 하고, 그러려면 파일을 내려받거나 로컬 서버를 띄우거나 어딘가에 업로드해야 한다. 산출물의 형태가 풍부해질수록 공유는 오히려 번거로워지는 역설이 생긴 것이다.

이 글에서 다룰 htmldrop(htmldrop.link)은 이 문제를 정면으로 겨눈 오픈소스 서비스다. GeekNews(hada.io)에 "Show GN: AI가 만든 HTML, 링크 하나로 바로 공유하기 (MCP 지원)"라는 제목으로 올라왔다. 이 글은 그 소개를 그대로 옮기는 대신, htmldrop이 실제로 어떻게 동작하는지를 원문과 저장소 문서로 직접 확인한 뒤, 이것이 가리키는 더 큰 흐름 - 에이전트 산출물의 형태 변화, MCP가 "공유"라는 행위 자체를 도구 호출로 바꾸는 패턴, 그리고 기존 대안들과의 실질적 차이 - 을 짚어 본다.

1. htmldrop이란 무엇인가 - 정확한 동작 방식

htmldrop의 슬로건은 명확하다. "HTML 산출물을 API 한 번으로 공유 가능한 링크로 바꾼다"는 것이다. 과장을 걷어내고 실제로 무엇을 제공하는지 정리하면 다음과 같다.

1.1 세 가지 게시 경로

htmldrop은 HTML을 링크로 바꾸는 경로를 세 가지로 열어 둔다. 첫째는 웹 UI로, 파일을 드래그앤드롭하거나 클립보드에서 붙여넣으면 바로 링크가 나온다. 둘째는 API로, POST /publish(JSON), POST /publish/raw, POST /publish/from-url 세 엔드포인트를 통해 스크립트나 CI 파이프라인에서 자동으로 게시할 수 있다. 셋째는 MCP로, 뒤에서 따로 다룬다. 사람이 쓰든 스크립트가 쓰든 에이전트가 쓰든, 결국 HTML 콘텐츠를 넘기면 렌더링 가능한 URL을 돌려받는 구조는 동일하다.

1.2 무료·용량·공개 범위

회원가입 없이 무료로 쓸 수 있고, 파일 크기는 최대 25MB까지 허용한다. 인라인 CSS·JavaScript는 물론 외부 CDN 리소스를 불러오는 HTML도 그대로 렌더링해 준다. 링크는 기본적으로 비밀번호 없이 누구나 열람 가능한 공개 상태이며, 필요하면 비밀번호를 걸어 접근을 제한할 수 있다. 공개가 기본값이라는 점은 뒤에서 다룰 유의점과 직결된다.

1.3 영속성 설계와 오픈소스

모든 링크에는 TTL(수명)이 있다. 무료 사용자는 7일, 소유자 키를 쓰면 30일까지 유지된다. 이는 버그가 아니라 "공유된 산출물이 영원히 남지 않는다"는 명시적 설계 의도다. 또한 htmldrop은 MIT 라이선스 오픈소스로 GitHub(vin-spiegel/htmldrop)에 공개돼 있어, TypeScript 기반 코드를 내려받아 자체 도메인에 셀프호스팅할 수도 있다. 저장소는 Cloudflare R2 또는 로컬 파일시스템을 선택할 수 있고, 프로덕션 배포에는 와일드카드 DNS가 필요하다고 문서에 명시돼 있다.

2. 왜 지금 이 문제가 불거지는가 - 마크다운에서 HTML로

htmldrop 같은 도구가 등장한 배경을 이해하려면, 에이전트 산출물의 형태가 최근 왜 바뀌고 있는지부터 봐야 한다.

2.1 산출물이 "읽는 것"에서 "보는 것"으로

초기 챗봇형 에이전트의 산출물은 대화의 연장이었다. 질문에 답하는 문단, 설명을 돕는 코드 블록, 정리를 위한 표 - 전부 마크다운으로 충분했다. 그런데 에이전트가 조사·분석·기획까지 대신하기 시작하면서 요구되는 산출물의 형태가 달라졌다. 경쟁사 비교표를 색상으로 강조하고, 매출 추이를 차트로 그리고, 여러 시나리오를 탭으로 나눠 보여주는 식의 리치 리포트가 필요해졌다. 이런 표현은 마크다운의 표현력을 넘어선다. 결국 에이전트가 HTML(과 인라인 CSS·JS)을 직접 산출물로 내놓는 쪽으로 자연스럽게 이동하는 것이다.

2.2 마크다운 공유는 쉬웠지만 HTML은 달랐다

마크다운의 강점은 어디서나 렌더링된다는 점이다. 채팅창이든 깃허브든 노션이든 마크다운을 붙여넣으면 그 자리에서 읽힌다. 반면 HTML은 다르다. 텍스트 그대로 붙여넣으면 태그가 그대로 노출되고, 렌더링되게 하려면 파일로 저장해 브라우저로 열거나, 어딘가에 호스팅해야 한다. 에이전트가 다섯 줄짜리 대시보드 HTML을 만들어 줬다고 해서, 그것을 동료에게 "링크 하나로" 넘길 방법이 마땅치 않았다. 이 격차 - 산출물의 표현력은 높아졌는데 공유의 편의성은 그대로거나 오히려 떨어진 상태 - 가 htmldrop류 도구가 채울 자리를 만든다.

2.3 대시보드·인터랙티브 산출물의 부상

실제로 최근 에이전트 워크플로에서 자주 요청되는 산출물은 정적 텍스트가 아니라 클릭하면 필터링되는 데이터 테이블, 접었다 펼 수 있는 섹션, 간단한 자바스크립트로 동작하는 계산기류 미니 도구다. 이런 산출물은 파일 하나로 완결되는 "단일 HTML 아티팩트" 형태를 띠는 경우가 많다. htmldrop이 굳이 별도 빌드 과정 없이 HTML 하나를 그대로 받아 렌더링하는 데 초점을 맞춘 것은, 정확히 이 단일 파일 산출물 패턴을 겨눈 설계로 보인다.

3. MCP 지원의 의미 - 에이전트가 직접 게시하고 링크를 돌려받는다

htmldrop 소개에서 가장 눈에 띄는 대목은 API 지원이 아니라 MCP(Model Context Protocol) 서버 지원이다. 이것이 왜 API 제공과 별개로 의미 있는지 짚어 본다.

3.1 기존 방식 - 사람이 중간에서 옮긴다

API만 있는 경우를 생각해 보자. 에이전트가 HTML을 만들면, 그것을 API로 게시하기 위해서는 누군가(또는 별도로 짜인 스크립트)가 "이 HTML을 htmldrop API 문서를 보고, 엔드포인트에 맞는 요청을 만들어 보내라"는 절차를 거쳐야 한다. 에이전트 입장에서는 API 문서를 읽고, 인증 방식을 파악하고, 요청 포맷을 맞추는 별도의 학습·구현이 필요하다는 뜻이다.

3.2 MCP 방식 - 도구 호출 한 번

htmldrop은 /mcp 엔드포인트에서 Server-Sent Events 기반 MCP 서버를 띄우고, publish_html이라는 도구를 노출한다. Claude Code라면 claude mcp add --transport sse htmldrop https://htmldrop.link/mcp 한 줄로 이 도구를 등록할 수 있고, 이후 에이전트는 "이 HTML을 게시하고 링크를 줘"라는 의도만 있으면 별도로 API 스펙을 읽지 않고도 publish_html 도구를 호출해 링크를 응답으로 돌려받는다. 저장소 문서는 이 목적을 "에이전트가 API 문서를 읽지 않고도 즉시 게시하게 한다"라고 밝히고 있다.

3.3 왜 이것이 새로운 패턴인가

본인이 보기에 핵심은 "게시"라는 행위 자체가 에이전트 루프 안으로 들어온다는 점이다. 지금까지 에이전트는 콘텐츠를 만드는 역할까지만 맡고, 그것을 사람이 볼 수 있게 배포하는 마지막 단계는 사람이나 별도 파이프라인의 몫이었다. MCP로 노출된 게시 도구는 이 마지막 단계까지 에이전트의 도구 사용 범위 안에 편입시킨다. "보고서를 만들고, 게시하고, 링크를 알려줘"라는 한 문장짜리 지시가 사람의 추가 개입 없이 끝까지 완결될 수 있다는 뜻이다. 이것이 단일 서비스의 편의 기능을 넘어, MCP가 만들어내는 일반적 패턴 - 도구를 호출해 외부 세계에 결과를 남기고, 그 결과의 참조(링크·ID)를 돌려받는다 - 의 한 사례라는 점이 더 흥미롭다.

4. 유사 접근과 비교 - Gist, Pastebin, Vercel, 정적 호스팅, Claude 아티팩트

HTML이든 텍스트든 "만든 것을 링크로 공유하고 싶다"는 니즈 자체는 새롭지 않다. 기존 대안들과 htmldrop이 채우는 자리가 어디인지 비교해 보자.

4.1 GitHub Gist·Pastebin

Gist와 Pastebin은 텍스트·코드 스니펫을 빠르게 공유하는 용도로 오래 쓰여 왔다. 다만 HTML을 그대로 올려도 기본적으로는 소스 코드로 표시될 뿐 렌더링되지 않는다(Gist는 raw 뷰나 GitHub Pages 연결 같은 우회를 거쳐야 렌더링이 가능하고, 이는 API 한 번으로 될 일이 아니다). 즉 텍스트 공유에는 강하지만, "HTML을 웹페이지처럼 바로 보여준다"는 목적에는 원래 설계돼 있지 않다.

4.2 정적 호스팅(Vercel·Netlify·GitHub Pages)

Vercel이나 Netlify는 HTML을 렌더링되는 웹페이지로 완벽하게 배포할 수 있다. 하지만 이들은 원래 지속적으로 운영할 프로젝트를 위한 도구다. 리포지토리 연결, 빌드 설정, 배포 파이프라인이라는 절차가 붙는다. 에이전트가 한 번 쓰고 버릴 리포트 하나를 공유하려고 매번 프로젝트를 만들고 배포하는 것은 지나치게 무겁다. htmldrop은 이 무게를 걷어내고 "파일 하나, 요청 한 번, 링크 하나"로 단순화한 지점에 자리한다.

4.3 Claude 아티팩트 공유

Claude의 퍼블리시 기능은 Claude 안에서 만든 아티팩트를 공개 링크로 바꿔, 로그인 없이 누구나 보고 리믹스(포크)까지 할 수 있게 해 준다. 다만 이는 Claude 생태계 안에서 만들어진 산출물에 한정된 기능이다. 임베드 스니펫도 제공되지만, 공개 시 비밀번호나 만료 없이 전부 공개된다는 제약이 있고(팀·엔터프라이즈 계정은 조직 내부로만 공유 가능), 검색엔진에 노출될 수도 있다고 안내된다. htmldrop은 산출물의 출처를 가리지 않는다는 점, 그리고 TTL로 기본 만료가 걸린다는 점에서 설계 철학이 다르다.

4.4 htmldrop이 채우는 자리

정리하면 htmldrop은 Gist·Pastebin의 가벼움과 정적 호스팅의 실제 렌더링을 결합하되, 프로젝트 설정 없이 API(혹은 MCP 도구 호출) 한 번으로 끝나도록 설계됐다. 그 대가로 장기 보관성은 포기한다. "지속적으로 운영할 사이트"가 아니라 "지금 당장 보여주고 사라져도 되는 산출물"을 겨눈 도구라는 점이 다른 대안들과의 가장 뚜렷한 차이다.

5. 실무 활용 - 보고서·PRD·프로토타입 공유

이런 도구가 실무에서 어디에 끼워 넣을 만한지 시나리오별로 짚어 본다.

5.1 조사·분석 리포트 즉시 공유

에이전트에게 시장 조사나 데이터 분석을 맡기고 그 결과를 표·차트가 섞인 HTML 리포트로 받았다면, 파일을 내려받아 메신저에 첨부하는 대신 링크 하나로 팀에 공유할 수 있다. 받는 사람은 별도 프로그램 없이 브라우저만 열면 된다. 짧은 리뷰 주기의 초안 공유에 적합하다.

5.2 PRD·기획 문서 공유

제품 요구사항 문서(PRD)를 에이전트가 구조화된 HTML(섹션 접기, 우선순위 색상 표시 등)로 만들어 줬다면, 슬랙이나 이메일에 링크만 붙여 넣어 이해관계자가 바로 열람하게 할 수 있다. 다만 PRD에는 민감한 사업 정보가 담기는 경우가 많으므로, 뒤에서 다룰 공개 범위 문제를 함께 고려해야 한다.

5.3 프로토타입·데모 공유

에이전트가 간단한 UI 프로토타입이나 인터랙티브 데모를 HTML/CSS/JS 한 파일로 만들었을 때, 이를 실제로 클릭해 볼 수 있는 형태로 이해관계자에게 넘기려면 렌더링되는 링크가 필요하다. 정식 배포 전 빠른 피드백을 받는 용도로는 정적 호스팅보다 가볍고, 텍스트 공유 도구보다 실제 동작을 보여줄 수 있다는 점에서 적합하다.

6. 유의점 - 민감정보·공개범위·영속성·보안

편리함의 이면을 짚지 않으면 불완전한 분석이다. 실제로 쓰기 전에 확인해야 할 지점들이다.

6.1 민감정보는 애초에 올리지 않는다

htmldrop 링크는 기본적으로 비밀번호 없이 URL만 알면 누구나 열람 가능한 공개 링크다. 고객 데이터, 내부 재무 수치, 개인정보가 포함된 산출물을 이런 서비스에 올리는 것은 권장되지 않는다. 비밀번호 옵션이 있다 해도 사내 SSO나 세밀한 권한 관리 수준의 접근 통제는 아니다.

6.2 공개 범위의 기본값을 확인한다

"공유 링크"라는 말이 주는 인상과 달리, 링크를 아는 모든 사람이 접근할 수 있다는 점을 분명히 인지해야 한다. URL이 예측 불가능한 문자열이라 해도, 링크가 메신저나 이메일을 거쳐 의도치 않게 퍼질 가능성은 항상 있다. Claude 아티팩트의 퍼블리시 기능 역시 같은 구조의 위험을 안고 있고, 검색엔진에 색인될 수 있다는 안내가 별도로 붙어 있다는 점도 같은 맥락이다.

6.3 영속성을 전제로 쓰지 않는다

무료 링크는 7일, 소유자 키를 쓰면 30일 후 만료된다. 이는 장점이기도 하고 제약이기도 하다. 오래 참조해야 하는 문서의 URL로 이 링크를 쓰면 안 된다. 반대로 "지금만 보면 되는" 용도에는 자동 만료가 오히려 정리 부담을 덜어준다.

6.4 보안 - 렌더링되는 HTML이라는 특성

htmldrop은 인라인 JavaScript와 외부 CDN 리소스를 그대로 렌더링한다. 이는 인터랙티브한 산출물을 가능하게 하는 장점이자, 신뢰할 수 없는 출처의 HTML을 열람할 때는 주의가 필요하다는 뜻이기도 하다. 에이전트가 자동 생성한 콘텐츠를 사람이 검수 없이 그대로 게시하고, 그 링크를 다시 다른 사람이 별생각 없이 여는 흐름이 반복되면, 콘텐츠 검증 없이 신뢰가 자동으로 이어지는 사슬이 생길 수 있다. 게시 전 최소한의 사람 검수를 두는 습관은 여전히 유효하다.

7. MCP 생태계 맥락에서 본 htmldrop

htmldrop 하나만 보면 작은 유틸리티지만, 이것이 등장한 배경인 MCP 생태계 전체를 보면 더 큰 흐름이 보인다.

7.1 MCP의 성장과 표준화

MCP는 Anthropic이 2024년 11월 공개한 개방형 프로토콜로, AI 애플리케이션과 외부 데이터·도구를 연결하는 공통 규격을 제공한다. 이후 OpenAI·Google DeepMind·Microsoft 등이 잇따라 지원을 발표했고, 2025년 12월에는 Anthropic이 MCP를 리눅스 재단 산하 Agentic AI Foundation에 이관하며 특정 기업 소유가 아닌 벤더 중립 표준으로 전환됐다. 공개된 활성 MCP 서버가 1만 개를 넘어섰다는 보도도 있다. htmldrop의 MCP 지원은 이 표준화된 생태계 위에 얹힌 수많은 서버 중 하나다.

7.2 "게시형" MCP 서버라는 작은 카테고리

MCP 서버는 크게 데이터를 읽어오는 유형(파일시스템, 데이터베이스, 검색)과 외부 세계에 무언가를 쓰거나 남기는 유형(이슈 생성, 메시지 발송, 배포)으로 나눠 볼 수 있다. htmldrop의 publish_html은 후자에 속하며, 그중에서도 "결과물을 사람이 볼 수 있는 형태로 세상에 내놓는다"는 좁지만 반복적으로 필요한 니즈를 겨눈다. 이런 성격의 도구는 화려하진 않지만, 에이전트가 만든 결과를 실제로 누군가에게 전달하는 마지막 연결 고리라는 점에서 실용적 가치가 있다. 앞으로 유사한 목적(문서 게시, PDF 변환, 짧은 웹사이트 배포)을 가진 MCP 서버가 더 늘어날 가능성이 높다.

7.3 표준 프로토콜이기에 생기는 이식성

MCP가 벤더 중립 표준이라는 점은 htmldrop 같은 서버를 Claude Code뿐 아니라 Cursor, 그리고 MCP를 지원하는 다른 클라이언트에서도 같은 방식으로 쓸 수 있다는 뜻이다. 특정 플랫폼에 종속되지 않고 "게시 도구"를 에이전트 툴체인에 꽂아 넣을 수 있다는 점이, 폐쇄적인 플랫폼별 통합과 구분되는 MCP 생태계의 실질적 이점이다.

결론 - 편리하지만 용도를 가려 써야 하는 도구

htmldrop이 보여주는 것은 거창한 기술 혁신이라기보다, 에이전트 산출물의 형태 변화(마크다운 → HTML)가 만든 실용적 빈틈을 정확히 메운 사례에 가깝다. MCP 지원은 이 빈틈을 메우는 방식을 한 단계 더 밀어붙여, "게시"라는 마지막 단계까지 에이전트의 도구 호출 범위 안으로 끌어들인다. 사람이 파일을 옮기고 업로드하던 자리를, 도구 호출과 링크 반환이 대신하는 흐름이다.

다만 이는 어디까지나 빠르고 가벼운 일회성 공유에 최적화된 도구다. 공개 링크가 기본값이라는 점, TTL이 있어 오래 남지 않는다는 점, 접근 통제가 사내 시스템 수준은 아니라는 점을 감안하면, 민감 정보가 담긴 산출물이나 장기 보관이 필요한 문서에는 맞지 않는다. 반대로 프로토타입 데모, 초안 리포트, 회의 전 빠르게 돌려볼 대시보드처럼 "지금 보여주고 사라져도 되는" 산출물에는 정확히 맞아떨어진다. 도구의 편리함과 그 편리함이 감춘 전제(공개·만료·통제 수준)를 함께 이해하고 쓰는 것이 맞는 사용법이다.
