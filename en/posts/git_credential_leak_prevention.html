The Token Is Sitting in Your Remote URL - Where Git Credentials Leak

Deleting the file does not close this. Six places checked against real output, and the order to follow after an incident

September 1, 2026 Dev & Infra

Talk about credential leaks usually starts with a committed file and ends with a committed file. Someone commits .env by accident, pulls it back out of history, done. But count the paths a token actually takes out of a working environment and the file turns out to be one of six. The other five are never caught by careful file hygiene.

The place it happens most is the remote URL. Clone once in a hurry as https://user:token@host/... and that string settles into the repository config file in plain text, then comes back on screen every time you type git remote -v. It comes back during a screen share. It comes back in a pasted log.

What follows walks through those six places one at a time, with the output from commands that were actually run. The last part is the one that matters most: the order to follow once it has already leaked. Deleting the file is not step one in that order.

Every example here uses values that are obviously fake and a host that cannot exist (.invalid). The runs were isolated in a temporary directory with HOME pointed inside it, and the only edit to the pasted output is shortening the home path to ~. This is about auditing your own setup, not about attacking anything.

The leak points are not only files

A map first. The six places below differ in kind. Some sit inside the repository and some outside it, some you can delete yourself and some live on somebody else's server. The point of this table is that the defense is different for each one.

Leak pointWhere it staysCan you delete it yourselfHow to block it
Committed fileThe commit object, and every clone made of itRewriting never reaches other people's copiesBlock it before the commit. Write the ignore rule first
Token in the remote URL.git/config, and every screen that prints itYes. The value is replaced wholeset-url to a URL with no credentials
.git/configA plain text file in the working directoryYesLeave it to a helper and keep it out of the URL
Shell historyThe history file in your home directoryYes, but easy to forgetKeep secrets off the command line
CI logsThe CI provider's serversDepends on their retention policyDo not turn trace output on
Commit messages and issuesThe commit object, the reflog, the issue serverThe reflog yes. The server is another matterRead it once before you paste

Most of the space here goes to the second and third rows. The first row, the procedure for untracking a file that git is already tracking, was covered separately in the piece on why adding an ignore rule later does not untrack anything. Where that piece ends is where this one starts. Untracking still leaves the file in history, which is why rotating the key comes first.

The environment behind the output

Every output below came from a real run. Not a line of it is invented. Because the token is fake and the host does not exist, anything that needs the network stops at name resolution, which is convenient here: it isolates where a credential is already recorded before any connection happens.

  • git — 2.48.1.windows.1
  • Shell — GNU bash 5.2.37(1)-release, Git Bash
  • Platform — MINGW64_NT-10.0-19045 (an MSYS environment on Windows 10)
  • As of — September 2026
  • Isolation — a fresh repository in a temporary directory with HOME pointed inside it, so the real home configuration and credential files were never touched

Two spots come out differently on Linux or macOS: how file permissions are reported, and the permission check OpenSSH runs on a private key. Both are flagged in their own sections.

git remote -v prints the token as is

The usual beginning looks like this. Interactive authentication is a nuisance, or a script has to connect on its own, so the token goes inside the URL and the clone is made. It works. The question is where that value ends up.

$ git remote add origin "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (fetch)
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (push)

$ cat .git/config
[core]
        repositoryformatversion = 0
        filemode = false
        bare = false
        logallrefupdates = true
[remote "origin"]
        url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

$ git config --get remote.origin.url
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

Three things surface at once. First, remote -v does not mask the token; it appears twice, on the fetch line and on the push line. Second, .git/config is an unencrypted text file and the token sits inside it verbatim. Third, an ordinary lookup such as git config --get prints the same value.

The danger is not the command itself but the situation the command runs in. git remote -v is among the first things anyone types when something breaks, which means it runs at the moment you ask for help, share a screen, or attach a log to an issue. The conditions for a token to travel are in place at exactly that moment.

  • The same value follows into backups and sync folders. Back up the working directory whole and .git/config goes with it
  • With several remotes registered, it survives in the one you forgot. An upstream or a stale backup remote is a common spot
  • The repository information panels in editors and IDEs read and display the same value

How to fix the remote URL

The fix itself is one line: git remote set-url with a URL that carries no credentials. What is worth verifying is whether the old value really disappears, because hand-editing a config file tends to leave the old line sitting there as a comment or copied under another key.

$ git remote set-url origin "https://git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://git.example.invalid/demo/demo.git (fetch)
origin  https://git.example.invalid/demo/demo.git (push)

$ cat .git/config
[remote "origin"]
        url = https://git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

# check whether the old value survives anywhere under .git
# (in a clean repository where only remote add and set-url were run)
$ grep -rl 'ghp_EXAMPLE' .git/
(no output)

The replacement is clean. set-url swaps the whole url value, so no fragment of the old string is left behind, and none of it touches commit objects. Search right after adding the remote and you get one hit, .git/config; search after set-url and you get none.

Do not take comfort from that, though. The repository is clean; the token is not. If you typed that URL on a command line it is in the shell history, and if CI used it, it may be in a log. When you cannot say for certain how far the value travelled, revoking comes before tidying.

  • If there are several remotes, check all of them. git remote -v shows every remote that is registered
  • Submodules keep their own configuration. Look at .gitmodules and at each submodule directory as well
  • Once it is changed, decide how authentication will work. A helper is the default answer, and for automation an SSH key is the better one

What a credential helper leaves, and where

Keep the token out of the URL and git asks a credential helper instead. This is where the choice is made. By the official documentation, git carries two helpers of its own; the rest bridge to secure storage on the operating system side.

HelperWhere it keeps itPersistencePlain textWhere it fits
storeThe .git-credentials file in your homeUntil deletedYesAlmost nowhere worth recommending
cacheMemory, held by a helper processThe timeout you setNever written to diskShared machines, short sessions
OS keychain bridgeThe operating system's secure storeTied to the accountNoThe default on a personal machine
Straight into the URL.git/configUntil deletedYesNowhere. The subject of this article

What store leaves behind is clearest once you put something into it. The helper protocol is a plain exchange of keys and values over standard input, so storing and retrieving can be reproduced exactly without touching the network.

$ git config --global credential.helper store

# store one fake credential through the helper protocol (no network access)
$ printf 'protocol=https\nhost=git.example.invalid\nusername=demo-user\npassword=ghp_EXAMPLE0000000000000000000000000000\n\n' \
    | git credential-store store

$ stat -c '%a %n' ~/.git-credentials
644 ~/.git-credentials

$ cat ~/.git-credentials
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid

# reading it back works just as plainly
$ printf 'protocol=https\nhost=git.example.invalid\n\n' | git credential-store get
username=demo-user
password=ghp_EXAMPLE0000000000000000000000000000

One line of that file is exactly https://user:password@host. The storage format is effectively the same as pinning a token into a remote URL. Only the location differs. The official git documentation says of this helper that it stores passwords unencrypted on disk, protected only by file system permissions, and advises anyone for whom that trade-off is unacceptable to use cache or to find a helper that integrates with the secure storage provided by the operating system.

Treat the permission number with care. The 644 in the output above is what stat reported in this Windows and MSYS environment. The official documentation only says the file's permissions are set so that other users cannot read it, without naming a number, and whether the same value appears on Linux is something I did not check. Either way the conclusion holds. Anything that can read the file can read the token.

  • The primary location is .git-credentials in your home, and failing that, git/credentials under the configuration directory is used too. It is better kept out of backups
  • To remove an entry, pass erase to the helper instead of opening the file by hand, and only that entry goes
  • Git for Windows has manager set in the system configuration by default. The helpers installed alongside it in this environment were cache, store, manager, and one selector
  • Specify several helpers and git asks them in turn until it gets an answer. An old store setting left in place may answer first

What changes on the SSH key side

Connect over SSH and there is no reason to put a token in the URL, so most of what came before disappears. Something else takes its place: the private key file itself. Exactly one thing decides how bad that is, and it is whether the key has a passphrase.

# does it open without a passphrase (-y derives the public key from the private key)
$ ssh-keygen -y -P "" -f ~/.ssh/id_nopass >/dev/null 2>&1 \
    && echo "no passphrase" || echo "passphrase required"
no passphrase

$ ssh-keygen -y -P "" -f ~/.ssh/id_pass >/dev/null 2>&1 \
    && echo "no passphrase" || echo "passphrase required"
passphrase required

# which key this host actually uses (the resolved configuration)
$ ssh -G demo | grep -E '^(hostname|user|identityfile)'
user git
hostname git.example.invalid
identityfile ~/.ssh/id_demo

A key without a passphrase is usable the moment someone holds the file; a key with one has a layer left. That difference only shows up when the file moves in its entirety - a lost laptop, a leaked backup - which is precisely the situation that happens. If typing it every time is a burden, load it into an agent once.

The second command is the more practical of the two. ssh -G shows the resolved result after the configuration files have been read. When you have several keys, do not guess which key goes to which host; this is faster.

One note on permissions. In this environment, setting a private key to 644 and attempting a connection produced no complaint from OpenSSH about permissions at all; it went straight on to failing host name resolution. That looks like MSYS emulating permissions, and the behavior on Linux or macOS is something I did not check. Either way, leaving a private key readable by other users has nothing to recommend it.

CredentialScopeDefault permissionLifetimeWhere it is used
Personal SSH keyEvery repository that user can reachEverything the user hasUntil you delete itA person's working machine
Deploy keyA single repositoryRead-only by default. Write can be grantedUntil you delete itOne server, one repository
Fine-grained tokenOne user or organization, and the repositories you nameGranted per item30 days by default, up to 366 days or noneAutomation, external integrations
Classic tokenEvery repository in the organizations it reachesBroad scope categoriesOptional. Removed automatically after a year unusedSomething to phase out

The table is where the case for deploy keys sits. A personal key opens every repository that person can reach, while a deploy key attaches to one repository and is read-only by default. In the common deployment shape where one server only needs to pull one repository, copying in a personal key and creating a deploy key differ enormously in how much damage an incident does.

Token lifetime and scope

If everything so far was about not leaking, this section is about leaking small. What determines the size of an incident is usually not the leak itself but what that credential could do and how long it stays valid. Both are settled on the screen where the token is created.

As of September 2026, GitHub documentation describes fine-grained personal access tokens as limited to resources owned by a single user or organization, reaching only the repositories you name within that, with permissions granted item by item. Classic tokens, by contrast, work in broad scope categories and open every repository in the organizations that user can reach. The same document strongly recommends setting an expiration, and fine-grained tokens default to 30 days with a maximum of 366 days or no expiration at all. Expiration is optional for classic tokens too, but a token unused for a year is removed automatically.

At the organization level there is another layer. Organization owners can require approval before a fine-grained token touches organization resources, restrict classic token access to the organization, enforce a maximum lifetime policy, and review and revoke the tokens that reach them. Which means a token an individual creates does not stay an individual matter, and from the organization's side this is often the only lever available during an incident.

  • No expiration is not a convenience, it is a debt. It buys comfort now by deferring the revocation date forever
  • Grant only what is needed now. Grant broadly in advance and no occasion to narrow it ever arrives
  • Split tokens by purpose. Use one everywhere and you cannot tell what else stops when you revoke it, so you put the revocation off
  • Name tokens so the purpose is legible. During an incident that changes how quickly you can pick one out of a list
  • Do not mix credentials people use with credentials automation uses. When the person leaves, the automation stops with them

How it leaks in CI

CI is the place where credentials pass through most often and where output is archived automatically. That combination is what makes it dangerous. What you would have to scroll back to see locally is left behind as a link in CI.

The most common accident is turning on tracing to debug something and leaving it on. The shell's set -x prints each command just before it runs, with variables expanded.

$ cat ci_demo.sh
#!/bin/bash
set -x
TOKEN="ghp_EXAMPLE0000000000000000000000000000"
git ls-remote "https://x-access-token:${TOKEN}@git.example.invalid/demo/demo.git"

$ bash ci_demo.sh
+ TOKEN=ghp_EXAMPLE0000000000000000000000000000
+ git ls-remote https://x-access-token:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

Once on the assignment line, once again on the line that uses it. Holding it in a variable does not hide anything, because the entire purpose of set -x is to show the expanded value.

What about git's own output? Here the results diverge. Error messages strip the credential; trace output does not.

# git's own error message strips the credential part
$ git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
fatal: unable to access 'https://git.example.invalid/demo/demo.git/': Could not resolve host: git.example.invalid

# but GIT_TRACE does not strip it
$ GIT_TRACE=1 git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
trace: built-in: git ls-remote https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
trace: run_command: GIT_DIR=.git git remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...
trace: exec: git-remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...

You can see the demo-user:ghp_...@ portion removed wholesale from the error message. Turn tracing on and the same URL appears intact, across several lines. The moment you turn tracing on is usually the moment something will not come unstuck, and the output of that moment goes straight into the CI record.

It is easy to assume the provider's masking covers this, but that feature has edges. GitHub documentation says sensitive values that are not secrets have to be masked deliberately with a separate directive, and in the passage describing the workaround for handling large secrets as files, it states plainly that a secret printed to the log is not masked. It also warns that passing secrets on the command line can expose them in the process list.

  • Masking works on an exact match with the registered string. Slice the value or encode it and the same secret becomes a different string
  • So masking is a safety net, not a design. Not printing it in the first place comes before that
  • Turn tracing on only for the stretch that needs it. Put it at the top of a script and the whole run is in scope
  • Pass credentials through environment variables or standard input rather than command line arguments
  • Logs from failed runs are the more dangerous ones. Nobody opens a successful log, but a failure log gets pasted around
  • By default, secrets are not passed to runs triggered from forks. Configurations that work around that limit are what turn into incidents

Shell history and the process list

Type a command containing a token even once and that line goes into the history file. This place is easy to forget because it is outside the repository. However thoroughly you clean the repository, the history file in your home directory is untouched.

In the Git Bash of this environment, HISTCONTROL was not set. When that variable contains ignorespace, a command beginning with a space stays out of the history, which means it is not behavior to count on as a default. It varies by shell and by distribution, so it is better to check on your own machine.

  • Pass a token through a file or standard input rather than typing it on the command line. That avoids the history and the process list in one move
  • If you already typed it, delete the line from the history. But deleting is the second job; revoking is the first
  • If your remote access tool is configured to write session logs to a file, the same line is there too. Terminal transcripts are a commonly forgotten place

Commit messages - the reflog as a second copy

Sometimes the value is written not into a file but into a commit message, as a note about what was being tested that ends up carrying the value itself. File scanners never see this, because a message is not a file; it is part of the commit object.

And there is one more layer here: the reflog. Git records the history of reference movements separately under .git/logs/, and the first line of each commit message goes into that record. So even if you rewrite or undo the commit, another copy is still around.

$ git commit --allow-empty -m "oops ghp_EXAMPLE0000000000000000000000000000"

$ grep -rl 'ghp_EXAMPLE' .git/
.git/logs/HEAD
.git/logs/refs/heads/main

$ git reflog --format='%gd %gs' | head -2
HEAD@{0} commit: oops ghp_EXAMPLE0000000000000000000000000000
HEAD@{1} commit (initial): init

# after expiring the reflog and running a prune
$ git reflog expire --expire=now --all
$ git gc --prune=now
$ grep -rl 'ghp_EXAMPLE' .git/
(no output)

Two files hold it, and expiry plus pruning clears them. What this experiment teaches is not how to erase the reflog but the opposite: that a repository can keep a copy even after the log has been tidied into looking clean. And this cleanup is only valid inside your own repository. Once it has been pushed, the server and everyone else's copies still have it.

  • For the same reason, the body and comments of an issue or pull request, and a log pasted into chat, are each a separate copy. Many services keep an edit trail even after you edit
  • There is essentially no situation that requires writing the value into a message. Record what you did and not which value you used
  • The cleanup commands cannot be undone. The reflog is also the last resort for recovering from mistakes, so do not expire it casually when nothing is urgent

Catching it before the commit

Everything up to here is a response to something that already happened. The far cheaper side is stopping it before it gets in. Three steps: put the ignore rule in place first, inspect the staged changes with a hook, and hand the rest to automated scanning.

The hook is shorter than you would expect. The one below looks only at added lines in the staged diff and aborts the commit if it finds a URL shaped like it carries a credential or a private key header.

$ cat .git/hooks/pre-commit
#!/bin/sh
if git diff --cached -U0 \
   | grep -nE '^\+.*(://[^/@[:space:]]+:[^/@[:space:]]+@|-----BEGIN [A-Z ]*PRIVATE KEY-----)'; then
  echo "pre-commit: something that looks like a credential is staged. aborting." >&2
  exit 1
fi
exit 0

$ git add deploy.conf && git commit -m "add deploy conf"
7:+url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
pre-commit: something that looks like a credential is staged. aborting.
$ echo $?
1

# the same file with the credential taken out
$ git add deploy.conf && git commit -m "add deploy conf"
committed OK

It shows the offending line with its number and blocks the commit with exit code 1. The same file with the credential removed passes.

The limits are plain, though. A hook lives per repository, so it does not travel with a clone, it can be bypassed, and it misses any shape the pattern does not cover. It is a device for reducing mistakes, not a guarantee. At the organization level, the usual arrangement is server-side push inspection together with a dedicated secret scanner, and those tools know the token formats of each provider, which gives them far more reach than a hand-written pattern.

  • Write the ignore rule before you create the file. Add it afterwards and a file already being tracked will not drop out
  • Commit only example configuration files. Files that will hold real values belong in the ignore list from the start
  • If the hook caught something, do not just fix the file and move on. Look at where that value came from as well
  • The team should know that an option to skip hooks exists. A device that blocks quietly gets bypassed quietly
  • When you hand a repository to an agent or an automation tool, a setup that never gives it the secret at all comes before any hook

The order after a leak

This is the most important section in the article. The first thing people do on discovering a leak is usually delete the file, because that is the visible problem. It is not step one.

GitHub documentation states the same order. If the sensitive data to be removed is a secret such as a password or a token, the first step is to revoke or rotate it, and once revoked it can no longer be used for access, which the document adds may be enough to resolve the problem on its own. The reason is simple: cleaning history can take hours, and the token stays valid for all of them.

OrderWhatWhy hereWhat happens if you defer it
1Revoke the key or token immediately and issue a new oneOnce revoked, that value is no longer a keyIt stays valid for the whole cleanup
2Work out what that credential could reachIt sets the size of the responseYou dig through logs without knowing where to look
3Check access logs and activity recordsWhether it was actually used changes everythingPast the retention window you cannot see it at all
4Check whether the same value sits anywhere elseThe same token in several places is commonYou fix one place and believe you are finished
5Only then clean the historyIt affects every collaboratorRushed, it breaks something else

Step two is easy to skip, and it is the step that sets the size of the response. A leaked read-only deploy key and a leaked token with write access across an organization lead to entirely different work. This is where the advice in the previous section, keep the scope narrow, shows what it was for.

  • Revocation gets deferred out of worry that it will stop a service, and that worry is itself the result of using one token in several places
  • Do not create the new token with the same permissions as the old one. Use the incident as the occasion to narrow the scope
  • Write it down: when, what leaked where, and what you revoked
  • Do not decide alone. Organizational credentials have a defined reporting path, and telling people late is usually worse

Why cleaning history is not enough

Rewriting history gives a definite visible result, and with it the feeling of having solved it. Open the log and the commit is gone. But that commit may already have been copied to several places.

GitHub documentation lists three places where a commit holding sensitive data remains reachable if you only rewrite history and force push: clones and forks of the repository, cached views addressed directly by the SHA-1 hash, and pull requests that reference the commit. It also states that anything left in a fork has to be coordinated with the fork's owner.

The more practical risk is recontamination. The same document puts it this way: a colleague holding a clone from before the rewrite who simply pulls and pushes afterwards brings the sensitive data back. Which means that even after the cleanup is finished, one teammate's reflexive action can return the repository to where it was.

  • On a public repository, crawlers and mirrors add another layer. There is no way to know what took a copy between the moment it went public and the moment you cleaned it
  • Internal repositories keep copies in backup snapshots and search indexes too. Without checking the retention policy you cannot say it has been deleted
  • So cleaning history is hygiene, not recovery. Recovery should already have finished at step one

Why this applies to private repositories too

Asking whether any of this matters for a private repository you work in alone is a fair question, and the size of the risk genuinely is different. The problem is that being private is not a permanent state.

  • Visibility settings change. The moment you open source it or publish it as a portfolio piece, the whole history goes public with it. Few people review every past commit at that point
  • Collaborators get added. The moment you invite one person, that person receives the entire history. There is no way to hand over only the recent commits
  • Backups go elsewhere. Archive the repository whole and upload it to the cloud, or move it to another machine, and .git goes along
  • Accounts can be compromised. Break one account and every private repository it owns opens at once. Private is a state that rests on account security
  • Machines change. When a laptop is replaced or lost, the working directory and the credential files in your home move together
  • Tools read it. Editor extensions, analysis tools and agents read the working directory. What goes where differs from tool to tool

Put together, the safety of a private repository rests on the settings as they are right now, and those settings change several times over a few years. The value written into history, meanwhile, stays exactly where it is. Time takes only one side.

A list of preventive habits

Only the things you can keep without adopting a new tool. Ordered by how much they help.

  • Keep credentials out of remote URLs. Leave authentication to a helper or an SSH key. This one habit closes three of the six places at once
  • Set an expiration on tokens. Simply not choosing no expiration gives an incident a shelf life
  • Grant only the permissions you need now. Widening later is the better direction. Permissions granted broadly never find an occasion to shrink
  • Split credentials by purpose. You will only actually revoke something if you know what stops when you do
  • Use deploy keys on servers. Do not copy in a personal key. If only reading is needed, keep it read-only
  • Put a passphrase on private keys. It is the one layer left when the file moves in its entirety
  • Do not make a plain text helper your default. Choose the one that bridges to the operating system's secure storage
  • Do not leave trace options on permanently. Only for the stretch that needs it, and off when it is done
  • Create the ignore rule before the file. Reverse the order and tracking has already begun
  • Inspect the staged changes with a hook. Even imperfect, it catches the most common mistakes
  • Check the remote URL before sharing a screen. It takes seconds
  • Open your token list regularly. Delete the ones you are not using

Finally, three lines for checking your own setup. Paste them into a repository and run them. They cover three of the places at once.

# ① is a credential pinned in a remote URL
git remote -v | grep -E '://[^/@]+@' && echo "a remote URL carries a credential"

# ② does the same shape appear in the history diffs
git log --all -p | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

# ③ does it appear in commit messages
git log --all --format='%B' | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

② and ③ print counts. A 0 means that shape is absent. This check looks only at URLs with a username and password attached. Keys written out separately inside files, and provider-specific token formats, are beyond it, so leave those to a dedicated scanner. On a large repository, ② takes a while.

Wrapping up

Credentials leak from six places, not from one committed file, and the one that catches people most often is a token pinned into the remote URL. That value sits in .git/config in plain text and reappears on screen every time you type git remote -v. Fixing it is one line of git remote set-url.

The side that makes a leak small is decided on the screen where the token is created. Set an expiration, narrow the scope, split by purpose.

If it has already leaked, the order is everything. Revoke, assess the scope, review the logs, and clean the history after that. Deleting the file is the fourth or the fifth job. However neatly you rewrite history, the copies left in clones, forks and caches are not recalled, and one colleague holding a pre-rewrite clone who pulls and pushes brings it all back. Cleanup is aftercare, not a solution. The solution ends on the first line.

What I Could Not Verify

  • The permission on the .git-credentials file is the 644 that stat reported in this Windows and MSYS environment. The official documentation only says permissions are set so that other users cannot read it, without naming a number, and what the value actually is on Linux is something I did not check
  • When a private key was left at 644 and a connection attempted, OpenSSH in this environment raised no objection to the permissions. That looks like MSYS emulating permissions, but how the same state is handled on Linux or macOS is something I did not check
  • The credential being stripped from the error message is an observation about a message git produced itself at the name resolution failure stage. What an actual server returns in the body of an authentication failure is something I did not check
  • Header masking at the HTTP transport layer within trace output could not be observed, since no real connection was made. The output above is limited to the command execution records of GIT_TRACE
  • The actual detection and false positive rates of secret scanner products were not tested. I noted only that such tools exist and evaluated no particular product
  • Default token expirations and organization policies on hosting services other than GitHub were not checked. The figures above are limited to GitHub documentation as of September 2026
