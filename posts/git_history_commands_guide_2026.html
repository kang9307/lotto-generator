제대로 안 쓰는 Git 히스토리 명령어 - pickaxe·log -L·bisect·reflog 실무 가이드

커밋 하나하나를 파고드는 log -S/-G·log -L·blame --ignore-rev·bisect·reflog, 실무에서 언제 어떻게 쓰는가

2026-07-16 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 우리는 왜 log와 blame만 쓰는가

대부분의 개발자에게 "git 히스토리를 본다"는 것은 git log로 커밋 메시지를 훑거나, git blame으로 이 줄을 누가 썼는지 확인하는 정도에서 끝난다. 그런데 git은 그 두 명령 뒤에 훨씬 정교한 도구 상자를 숨겨 두고 있다. 특정 문자열이 언제 코드베이스에서 사라졌는지 찾는 pickaxe(-S/-G), 특정 함수 하나의 변천사만 뽑아 보는 -L, 버그가 유입된 정확한 커밋을 이진 탐색으로 찾아내는 bisect, 실수로 날린 커밋조차 되살리는 reflog 같은 명령들이다.

이 글은 이런 명령어를 하나씩 나열하는 사전이 아니라, "이럴 때 이 명령을 쓴다"는 실무 시나리오 중심으로 정리한 가이드다. 문법은 공식 문서와 여러 실전 사례를 교차 확인해 정리했고(2026년 7월 기준 최신 git 기준), 각 명령의 한계와 함정도 함께 짚는다.

1. git log 강화 옵션 - 그래프와 필터로 흐름 좁히기

본격적인 도구로 넘어가기 전에, 기본 git log도 옵션을 조합하면 이미 상당히 강력해진다. 여러 브랜치가 얽힌 히스토리를 한눈에 보려면 그래프 옵션이 필수다.

git log --oneline --graph --all --decorate

이 조합은 모든 브랜치(--all)를 그래프(--graph)로, 태그·브랜치 이름까지 표시(--decorate)하며 한 줄씩(--oneline) 보여준다. 여기에 검색 필터를 얹으면 범위를 크게 좁힐 수 있다.

git log --author="Kim" --since="2026-06-01" --until="2026-07-01" --grep="fix"

작성자, 기간, 커밋 메시지 키워드로 동시에 좁히는 이 조합은 "지난달 김 아무개가 고친 버그 수정 커밋"처럼 구체적인 질문에 바로 답한다. 이 정도만 익혀도 로그를 스크롤하며 눈으로 찾는 습관에서 벗어날 수 있다.

2. git log -S / -G (pickaxe) - "이 문자열이 언제 사라졌나"

pickaxe는 커밋 메시지가 아니라 실제 코드 변경 내용(diff)을 검색 대상으로 삼는 옵션이다. "이 API 키 문자열을 누가 언제 지웠지", "이 함수 호출이 언제 추가됐지" 같은 질문에 직접 답한다.

2.1 -S: 등장 횟수의 변화를 추적

-S는 리터럴 문자열을 대상으로, 그 문자열이 diff 안에서 등장한 횟수(추가-삭제)가 변한 커밋만 찾는다. 대소문자를 구분하며 기본은 정규식이 아니다.

git log -S'API_SECRET_KEY' --oneline -- src/

정규식을 쓰고 싶다면 --pickaxe-regex를 추가하고, 매칭된 파일만이 아니라 그 커밋에서 바뀐 모든 파일을 보고 싶다면 --pickaxe-all을 붙인다.

2.2 -G: 정규식으로 "건드려진 줄"을 추적

-G'정규식'은 git 1.7.4부터 있던 옵션으로, 패턴과 일치하는 줄이 diff 어딘가에 나타나기만 하면 잡아낸다. -S와 달리 등장 횟수가 그대로여도, 그 줄이 이동했거나 미세하게 수정됐다면 -G는 감지한다.

git log -G'function\s+parseConfig' --oneline

2.3 실전 차이 - 코드가 이동만 했을 때

예를 들어 어떤 설정 값이 파일 안에서 위치만 옮겨지고 총 등장 횟수는 그대로라면, -S는 이 커밋을 찾아내지 못한다(개수 변화가 없으므로). 반면 -G는 그 줄이 포함된 diff 헝크가 존재하는 한 커밋을 잡아낸다. 정리하면 -S는 "있다/없다"의 변화, -G는 "그 줄에 손을 댄 모든 이력"을 본다. 삭제된 기능의 흔적을 찾을 때는 -S로 시작하고, 그걸로 안 잡히면 -G로 넓혀보는 순서가 합리적이다.

3. git log -L - 특정 함수·라인의 변천사

blame이 "지금 이 줄을 누가 마지막으로 고쳤나"를 보여준다면, -L은 "이 줄(또는 함수)이 시간이 지나며 어떻게 바뀌어 왔나"를 diff 형태로 순서대로 보여준다.

3.1 라인 범위 지정

git log -L 120,150:src/parser.c

파일의 120~150번째 줄이 각 커밋에서 어떻게 바뀌었는지 순차적으로 출력한다. git이 커밋을 거슬러 올라가며 해당 라인 블록을 자동으로 추적해 범위를 조정해준다.

3.2 함수 단위 지정

git log -L :parseConfig:src/parser.c

:함수명:파일 형식은 함수 이름을 정규식처럼 취급해 함수 시작 지점을 찾고, 언어별 userdiff 드라이버(C, Python, Java 등 내장 지원)를 이용해 함수의 끝을 판단한다. git이 함수 경계를 자동으로 못 찾는 경우엔 정규식으로 시작·끝 라인을 직접 지정할 수도 있다.

git log -L '/^int parseConfig/',/^}/:src/parser.c

"이 함수가 왜 지금 이런 모습이 됐나"를 추적할 때 이만큼 직접적인 도구가 없다. 여러 커밋에 걸쳐 조금씩 바뀐 로직을 diff로 순서대로 보면, 코드 리뷰만으로는 안 보이던 설계 의도나 우회 이력이 드러난다.

4. git blame 제대로 쓰기 - 포맷팅 커밋 무시하기

기본 git blame 파일은 강력하지만 큰 함정이 있다. 코드 전체를 재포맷하거나 일괄 치환한 커밋이 히스토리에 껴 있으면, 그 줄의 진짜 작성자 대신 포맷팅 커밋만 계속 가리키게 된다.

4.1 --ignore-rev로 특정 커밋 건너뛰기

git blame --ignore-rev a1b2c3d4 src/app.js

git 2.23부터 지원하는 기능으로, 무시된 커밋이 건드린 줄은 그 이전에 마지막으로 수정한 리비전으로 귀속된다. 여러 개를 무시하려면 옵션을 반복하거나 파일로 관리한다.

4.2 .git-blame-ignore-revs 파일로 관리

# .git-blame-ignore-revs
# 2026-05 전체 포맷팅 (prettier 적용)
a1b2c3d4e5f6...

git blame --ignore-revs-file .git-blame-ignore-revs src/app.js

파일명을 관례대로 .git-blame-ignore-revs로 저장하면 GitHub이 이를 자동으로 인식해 웹 UI의 blame 뷰에도 그대로 반영한다. 매번 옵션을 붙이기 귀찮다면 저장소 설정에 등록해두면 된다.

git config blame.ignoreRevsFile .git-blame-ignore-revs

5. git bisect - 버그 유입 커밋 이진 탐색

"작년까지는 되던 게 지금은 안 된다"는 상황에서 커밋을 하나씩 체크아웃하며 눈으로 확인하는 건 시간 낭비다. bisect는 좋은 커밋과 나쁜 커밋 사이를 이진 탐색으로 좁혀 원인 커밋을 정확히 짚어낸다.

5.1 수동 이진 탐색

git bisect start
git bisect bad                 # 현재(HEAD)는 버그가 있음
git bisect good v1.2.0         # 이 태그 시점에는 정상이었음

이후 git이 중간 지점 커밋을 자동으로 체크아웃한다. 그 상태에서 직접 테스트해보고 결과에 따라 git bisect good 또는 git bisect bad를 반복 입력하면, 로그(N)번의 시도로 범인 커밋을 찾아낸다.

5.2 git bisect run으로 완전 자동화

테스트 과정 자체를 스크립트로 만들 수 있다면 전 과정을 자동화할 수 있다. 스크립트는 종료 코드로 결과를 알려야 한다: 0=정상(good), 1~127 중 하나(단 125 제외)=버그(bad), 125=이 커밋은 테스트 불가(skip)다.

git bisect start HEAD v1.2.0
git bisect run npm test

또는 커스텀 스크립트를 붙일 수도 있다.

#!/bin/bash
# check.sh - 빌드 후 특정 응답을 확인
npm run build || exit 125   # 빌드 자체가 안 되면 skip
curl -sf http://localhost:3000/health | grep -q '"ok":true' && exit 0 || exit 1

git bisect run ./check.sh를 실행하면 git이 알아서 이등분하며 스크립트를 반복 실행해, 사람이 개입하지 않아도 원인 커밋을 찾아낸다. 끝나면 git bisect reset으로 원래 브랜치로 돌아온다.

6. git reflog - 잃어버린 커밋 되찾기

실수로 git reset --hard를 잘못 실행했거나, 리베이스 도중 커밋이 사라진 것처럼 보일 때 reflog가 구원투수다. reflog는 실제 커밋 그래프가 아니라 HEAD와 브랜치가 가리켰던 위치의 이력을 로컬에 기록한다.

git reflog
# 또는
git reflog show HEAD

각 항목은 HEAD@{0}, HEAD@{1} 같은 식으로 번호가 매겨지며, 그 시점에 어떤 동작(commit, checkout, reset, rebase 등)이 있었는지 함께 기록된다. 원하는 지점을 찾으면 먼저 git show <해시>나 git checkout <해시>로 내용을 확인한 뒤, 확신이 서면 되돌린다.

git reset --hard HEAD@{2}

단, reflog는 영원하지 않다. 현재 브랜치에서 여전히 도달 가능한 항목은 기본 90일(gc.reflogExpire), 어디서도 도달 불가능해진 항목은 기본 30일(gc.reflogExpireUnreachable)이 지나면 git gc 실행 시 정리된다. 사고 직후 최대한 빨리 확인하는 습관이 안전하다.

7. git log --follow - 이름 바뀐 파일의 역사 잇기

파일을 이동하거나 이름을 바꾸면 git log 파일경로는 그 이름으로 바뀐 이후 커밋만 보여준다. --follow를 붙이면 이름 변경을 넘어 원래 파일의 히스토리까지 이어서 보여준다(단일 파일에만 적용된다).

git log --follow -p -- src/utils/format.js

여기에 -p를 더하면 각 커밋에서 실제로 무엇이 바뀌었는지 diff까지 함께 확인할 수 있다. 리네임을 감지하는 임계값을 조정하고 싶다면 -M(또는 --find-renames) 옵션을 함께 쓴다.

삭제된 파일이나 코드를 되찾아야 할 때도 비슷한 원리를 쓴다. 먼저 어떤 커밋에서 삭제됐는지 찾고,

git log --diff-filter=D --oneline -- src/legacy/old_parser.js

그 커밋의 부모 리비전에서 파일을 되살린다.

git checkout <삭제된_커밋>^ -- src/legacy/old_parser.js

8. git rev-list / git shortlog - 스크립팅과 통계

rev-list는 사람이 읽는 log와 달리 커밋 해시만 나열하는 저수준(plumbing) 명령이라 스크립트에 넣기 좋다. shortlog는 작성자별로 커밋을 집계해 통계를 뽑는다.

git rev-list --count HEAD                 # 전체 커밋 수
git rev-list --count v1.0.0..v2.0.0        # 두 태그 사이 커밋 수
git rev-list --count --since=yesterday HEAD

git shortlog -sn --no-merges              # 작성자별 커밋 수, 병합 제외
git shortlog -sn --all                    # 전체 브랜치 기준

CI 스크립트에서 "이번 릴리스에 커밋이 몇 개 들어갔나", "이 기간 동안 누가 가장 많이 커밋했나"를 뽑을 때 이 두 명령이 훨씬 가볍고 파싱하기 쉽다.

9. 시나리오별로 무엇을 쓸까

실무에서는 명령어 이름보다 "지금 내가 알고 싶은 게 뭔가"에서 출발하는 편이 빠르다. 아래 표로 정리했다.

궁금한 것쓸 명령어
이 버그가 정확히 언제 들어왔나git bisect (+ run으로 자동화)
이 코드가 왜 지금 이런 모습이 됐나git log -L :함수:파일
이 줄을 마지막으로 고친 사람이 누구인가 (포맷팅 커밋 무시)git blame --ignore-revs-file
삭제된 문자열·설정값이 어디로 갔나git log -S (안 잡히면 -G)
실수로 날린 커밋을 복구하고 싶다git reflog + reset --hard
이름이 바뀐 파일의 과거 이력이 궁금하다git log --follow
릴리스 통계·CI 스크립트에 커밋 수를 넣고 싶다git rev-list --count, git shortlog -sn

10. 참고 - 커밋을 "다시 쓰는" 쪽도 진화하고 있다

이 글은 히스토리를 탐색하는 명령어에 집중했지만, 최근 git 2.54~2.55에는 히스토리를 다시 쓰는 쪽에서도 새로운 실험적 명령이 추가됐다. git history reword, git history split, git history fixup은 과거 커밋의 메시지를 고치거나, 한 커밋을 둘로 쪼개거나, 스테이징된 변경을 옛 커밋에 접어 넣으면서 그 뒤에 이어진 브랜치를 자동으로 리베이스해준다. rebase -i의 대표적인 사용 패턴을 더 안전하게 감싼 것으로, 아직 병합 커밋을 다루지 못하는 등 제약이 있어 실무 도입은 신중히 검토할 단계다. 히스토리를 "읽는" 이 글의 명령어들과 짝을 이루는 흐름으로 기억해두면 좋다.

결론: 도구는 이미 있다, 습관만 남았다

여기 나온 명령어 중 어느 것도 최근에 추가된 게 아니다. -S는 git 초창기부터, --ignore-rev 정도만 비교적 최근(2.23)이고 나머지는 모두 오래전부터 존재했다. 문제는 도구가 없어서가 아니라, log와 blame 바깥으로 나가 볼 습관이 없었다는 데 있다. 다음에 "이 버그가 언제 들어왔지"라는 질문이 떠오르면 커밋을 하나씩 체크아웃하는 대신 bisect를, "이 문자열이 어디로 갔지"가 궁금하면 grep으로 전체 파일을 뒤지는 대신 log -S를 먼저 떠올려보자. 실수로 날린 커밋 앞에서 패닉하기 전에 reflog부터 확인하는 습관 하나만 들여도, 히스토리 탐색에 들이는 시간이 눈에 띄게 줄어든다.
