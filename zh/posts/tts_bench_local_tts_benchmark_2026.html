tts-bench 登场 - 从速度、听感、分数三维度比较 55 款本地 TTS 模型的开源基准

让你在任何硬件上都能选出合适的本地语音合成模型的三个视角，以及其背后的评测方法论

2026-07-11 开发/基础设施

引言: 把 55 种声音放在同一个屏幕上

截至 2026 年 7 月，把文本转为语音的 TTS(Text-to-Speech)技术，已经从「调用云端 API」的阶段，走向个人 GPU 甚至仅靠 CPU 就能生成相当自然声音的本地运行阶段。就在这股潮流中，一个引人注目的开源项目出现了: GitHub 用户 5uck1ess 发布的 tts-bench。这个项目把 55 款可本地运行的 TTS 模型放在 Windows、macOS、Linux 上并排比较，评测维度是速度(Speed)、听感(Listen)、分数(Scores)三个视角。它也被 hada(GeekNews)收录，引起了开发者社区的关注。

本文不止于介绍 tts-bench 是什么。我会从自己的视角，梳理为什么本地 TTS 在此刻受到关注、为什么评测 TTS 模型比想象中更难，以及 tts-bench 用怎样的方式去应对这种难度。本文不会照搬 55 款模型的完整排行榜 — 想看最新排名，去项目官网核实才是准确的做法。相反，本文聚焦于排行榜背后的评测方法论，以及把本地 TTS 引入实际项目时应该依据哪些标准来判断。

1. 为什么是现在的本地 TTS

本地 TTS 重新受到关注，原因可以归纳为四点。

1.1 隐私

把文本发给云端 API，内容就要经过外部服务器。对于处理敏感文本的场景 — 医疗咨询转录、法律文件朗读、私人笔记朗读 — 数据完全不离开设备的本地运行从根本上更安全。提示词在哪里被处理，是独立于音质和价格之外的第一优先级问题。

1.2 成本结构

云端 TTS 通常按字符数或音频时长计费。对于播客自动生成、大批量有声书转换、7x24 小时运行的语音导览这类高用量场景，这种单价会不断累积，成本压力随之增大。本地 TTS 在完成初期硬件投入后不再产生额外使用费，用量越大，越过盈亏平衡点后的单价优势就越明显。

1.3 离线运行

在网络不稳定甚至完全没有网络的环境 — 嵌入式设备、车辆、工厂设备、隔离网络 — 云端 TTS 本身就不是一个选项。本地 TTS 无需联网即可运行，也没有往返网络延迟，响应更快。

1.4 定制自由

直接掌握权重，就能针对特定领域术语调整发音、针对特定声音做微调、按硬件量化 — 这些都是封闭 API 无法提供的调整空间。若使用声音克隆模型，仅凭几秒钟的参考音频复刻特定说话人的声音，也完全在自己的掌控之中。

2. tts-bench 是什么 - 用三个维度看 55 款模型

tts-bench 覆盖的可本地运行 TTS 模型共 55 款，其中 14 款使用预设音色，41 款支持零样本声音克隆。参数规模跨度很大，从数千万级别的超轻量模型到数十亿参数级别的大型模型都有覆盖，发布时间也横跨最近数年。基准测试在三台实测设备上进行 — 一台高性能桌面 GPU、一台 Apple Silicon 设备、另一台桌面 GPU — 分别测量 CPU、CUDA、Apple Silicon 三条执行路径。安装依赖 uv 包管理器与 Python 3.11 以上版本，若下载全部模型，仅各模型的虚拟环境就要占用数十 GB，加上模型权重后总容量会远超 100 GB。基准测试代码本身以 MIT 许可发布，各模型的权重则分别遵循 Apache 2.0、MIT、GPL-3.0、非商用(CC-BY-NC 类)等各自的许可协议。

tts-bench 特别有意思的一点是，它没有把结果压缩成单一分数，而是把速度、听感、分数作为三个独立维度分别呈现，下文会逐一展开。项目还配套运行了一个 Voting Arena(投票竞技场)，通过盲测式 A/B 试听直接收集人类偏好: 在不知道模型名称的情况下，从两段音频中选出更喜欢的一段，结果实时汇入一个持续更新的 Elo 偏好排行榜。这可以理解为一种尝试 — 把自动指标难以完全捕捉的「听着就是舒服」这种感觉，转化为可积累的数据。

3. 为什么评测 TTS 模型很难

3.1 速度、自然度、准确度的三重权衡

很难简单地说某款 TTS 模型「好」，因为「好」这个词里悄悄捆绑了三个相互牵制的维度。第一是速度: 从输入文本到第一段音频出现的延迟，以及生成一秒音频所需的计算时间。第二是自然度: 语调、节奏、气息感等韵律特征与真人声音的接近程度。第三是准确度: 文本中的词是否被完整、正确地转换为语音，而不出现漏读或读错。问题在于，这三个维度大体上是相互权衡的关系。减少计算量以求更快生成，韵律往往会变得单调; 为了追求更高的自然度而使用更深的模型，实时性又会下降。因此不存在单一的「最佳 TTS 模型」，答案会随工作负载的优先级而变化。

3.2 如何把主观的听感质量客观化 - MOS 与 UTMOS

自然度本质上是主观的。衡量它的传统标准是 MOS(Mean Opinion Score，平均意见得分): 多名听众对合成语音的自然度打出 1 分(差)到 5 分(优秀)，再取平均值。问题在于，这种方式每次都要招募听众、组织试听、汇总打分，成本和时间开销都不小。要在一个比较 55 款模型的基准测试中，每次都组织人工评审团，并不现实。

因此逐渐取而代之的，是像 UTMOS 这样基于神经网络的自动 MOS 预测模型。它用真实的人工 MOS 数据训练而成，把语音波形转换为自监督学习(SSL)表征后，再通过多个回归模型的集成，自动估算出与人工评分高度相关的分数。它无法完全取代真人试听，但用同一把尺子快速扫过 55 款模型，已经足够实用。这也是 tts-bench 的 Scores 维度选用 UTMOS 作为自然度指标的原因。

4. 三维度方法论的意义

在 tts-bench 的方法论中，我特别留意的一点是: 它没有把三个维度硬合成一个，而是刻意让它们并列存在。原因在于每个维度回答的问题并不相同。

4.1 Speed - 这款模型在我的硬件上是否可用

Speed 维度分别在 CPU、CUDA、Apple Silicon 三条路径上，报告冷启动/热启动状态下的首个音频响应时间(TTFA)、实时因子(RTF)与内存占用。这是一个与「是否自然」无关的实用问题: 在给定硬件上，这款模型是否真的能跑起来。据项目结果页面显示，一款超轻量 CPU 特化模型在热启动后可实现约 100 毫秒左右的响应，处理倍率可达实时速度的数十倍; 在 GPU 环境下，另一款轻量模型的响应时间据报道更短。不过这些具体数字会随模型版本与运行环境不断变化，想确认最新准确数字，还是去项目官网查看更稳妥。

4.2 Listen - 亲耳听到数字无法捕捉的印象

Listen 维度是一个音频画廊，收录了全部 55 款模型朗读同一批提示语的结果，既可以按提示语浏览(在同一句话上比较多款模型)，也可以按模型浏览(听一款模型在多句话上的表现)，同时支持默认音色与声音克隆两种模式。这一维度保留了无法被数字化的「听起来就是这种感觉」的印象，与后文的分数指标形成互补。项目也正是在这些试听数据的基础上，另外运行了盲测式 A/B 的 Voting Arena，在隐藏模型名称的情况下收集人类的真实偏好，并累积成 Elo 排行榜。

4.3 Scores - 可复现的客观指标

Scores 维度提供三项指标: 代表自然度的 UTMOS、代表发音与文本一致程度的 WER(词错误率)、代表声音克隆准确度的 SIM(说话人相似度)。WER 的计算方式是把合成语音重新送入语音识别(ASR)，将得到的转录文本与原文对比，统计插入、删除、替换三类错误，数值越低说明发音越准确。SIM 则用说话人嵌入模型，以余弦相似度衡量参考音频与合成音频在说话人特征上的接近程度，只对声音克隆模型有意义。这三项指标都能以相同流程自动应用于全部 55 款模型，因此可复现性很高。

把三个维度合在一起看，会得到一个方法论层面的洞察: 速度快的模型不保证听起来自然，分数高的模型也不保证能在你的硬件上实时运行。刻意把三个维度分开呈现，这个设计选择本身就反映出一种判断: 单一的排行榜无法诚实地容纳这三个维度之间的权衡关系。

5. 本地 TTS 生态概览

与其逐一罗列 55 款模型，不如按特性把开发者实际会遇到的本地 TTS 模型大致分成四类。这里的重点不是断言某个具体排名，而是说明每一类各自选择了怎样的权衡。

5.1 超轻量 CPU 特化系

参数量在数千万级别以下，设计目标是即便没有 GPU、仅靠 CPU 也能远快于实时速度运行。轻量到足以在树莓派一类低功耗边缘设备上运行。代价是音色的抑扬顿挫和表现力相对单调，因此特别适合语音播报、通知音效这类简短、格式化的句子。

5.2 均衡通用系

参数量约在一亿左右，比超轻量系更大，但在 CPU 上依然能保持充分的实时处理能力。很多此类模型同时具备多语言支持与宽松许可(对商用限制较少的许可协议)，因此常被希望在速度、自然度与许可灵活性之间取得平衡的服务采用。

5.3 声音克隆特化系

专注于零样本克隆的模型群，仅凭几秒钟的参考音频即可复刻目标说话人的声音特征，部分还支持跨语言的克隆。但这类模型通常更重，需要 GPU 与数 GB 显存，而且或许出于对声音被滥用的担忧，许可协议往往限定为非商用条件。

5.4 大型表现力优先系

参数量达到数十亿级别的大型模型群。它们往往在情感表达与细腻的语调控制上更有优势，但相应地对算力的需求也更大，实时响应能力相对较弱。比起实时对话式服务，这类模型更适合质量优先于速度的内容创作场景。

6. 实际选型时应考虑的因素

如果你正在评估是否引入本地 TTS，建议把以下四点整理成一张表格再做判断。

考虑因素需要确认的问题
硬件是否仅有 CPU，还是可用 GPU 与多少显存
语言支持目标语言(如中文)是否被实际支持且质量已验证
许可协议是否允许商用，是否存在非商用或著佐权限制
实时性是否需要对话式的即时响应，还是可以批量预生成

其中许可协议是最容易被忽略的一项。部分声音克隆类模型性能出色，却使用限制商用分发的许可，原型阶段可能用得顺畅，却在正式上线前突然卡住。硬件需求也是同样的风险: 演示时常用高性能 GPU 跑，而真正的部署目标往往是配置一般的服务器或边缘设备。从一开始就以真实部署硬件为基准筛选候选模型，会更稳妥。

7. 与云端 TTS 相比的优劣

本地 TTS 并非万能。与云端 TTS 放在一起对比，边界会更清晰。

维度本地 TTS云端 TTS
数据隐私不离开设备经由外部服务器
成本结构前期硬件投入，高用量更划算按用量计费，低用量更划算
离线运行可以不可以(需要网络)
初期搭建需要搭建环境、选型模型只需 API Key 即可立即使用
顶级自然度因模型而差异较大整体较稳定地保持高水准
定制能力可自由微调、量化受限于服务商提供的选项

我的看法是: 对于数据绝对不能外流的工作负载、用量大到单价累积成本可观的工作负载、网络不稳定的环境，本地 TTS 明显更有优势。反过来，如果是需要快速验证、又希望立即获得顶级音质的小型项目，先用云端 API 起步，等到用量增长或出现隐私需求时再转向本地，也是一条合理的路径。

8. 结论 - 今天就能落地的三件事

在我看来，tts-bench 的意义与其说在于 55 这个庞大的模型数量，不如说在于它把速度、听感、分数分开呈现的评测方法论。选择 TTS 模型从来不是一张排行榜就能解决的问题，而是需要分别核对自身硬件、语言、许可协议与实时性需求的多维决策。

8.1 在目标硬件上亲自做一次试听测试

基准数字只是参考点。无论是用 tts-bench 的 Listen 画廊，还是自己下载模型，都不要跳过用自己实际会用到的语言和句子亲耳听一遍这一步。

8.2 优先确认许可协议

在从原型迈向正式服务之前，先确认候选模型的许可是否允许商用分发。声音克隆类模型尤其常见非商用限制条款。

8.3 先按工作负载缩小模型系别范围

实时对话式服务可优先考虑超轻量或均衡通用系，内容创作类场景可优先考虑大型表现力系或声音克隆系。在逐一查看全部 55 款模型之前，先按工作负载缩小到合适的系别，效率会更高。
