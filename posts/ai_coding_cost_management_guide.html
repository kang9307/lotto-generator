서론: 개인의 청구서와 조직의 청구서는 다른 문제다

월말에 AI 코딩 도구 청구서가 지난달의 두 배가 되어 있다. 팀은 늘지 않았고, 배포량도 비슷하다. 누가 무엇을 해서 이렇게 됐는지 물으면 아무도 답하지 못한다. 이 상황에서 가장 먼저 나오는 제안은 대체로 하나다. 사람당 한도를 걸자는 것.

그 제안이 왜 잘 안 되는지, 대신 무엇을 하는지가 이 글의 내용이다. 개인이 자기 지출을 로컬에서 뜯어보는 축은 CodeBurn - AI 코딩 도구 지출을 로컬에서 분석하기에서 이미 다뤘다. 도구별 요금제 구조와 어느 항목에서 얼마가 새는지를 개인 관점으로 보고 싶다면 그쪽이 맞다. 여기서는 조직이 정책과 아키텍처로 비용을 통제하는 방법만 본다. 예산과 쿼터, 모델 라우팅, 캐싱, 사용량 가시성, 그리고 그 전부를 집행하는 게이트웨이다.

기준선 하나를 먼저 깔아 두자. Databricks 엔지니어링 블로그가 2026년 8월 7일에 대규모 AI 코딩 비용을 관리하는 방법을 공개했다. 사내에서 실제로 굴리는 구성을 정리한 글이고, 아래에서 몇 가지 수치를 인용한다. 인용한 절감치는 그 회사의 워크로드에서 나온 값이라는 점을 매번 붙여 두겠다. 숫자를 빌리는 것이 아니라 방법을 빌리는 것이 이 글의 목적이다.

1. 비용을 늘리는 것은 사람 수가 아니라 컨텍스트다

좌석 요금제로 쓰던 시절의 직관이 아직 남아 있다. 사람이 늘면 비용이 늘고, 사람이 그대로면 비용도 그대로라는 직관이다. 에이전틱 코딩에서는 그 직관이 깨진다. 같은 인원이 같은 시간 일해도 비용은 배로 뛸 수 있다.

이유는 토큰이 어디서 오는지에 있다. 개발자가 타이핑하는 프롬프트는 전체 입력에서 무시해도 될 만한 비중이다. 나머지는 에이전트가 스스로 끌어모은다. 파일을 읽고, 검색을 돌리고, 테스트를 실행해 출력을 붙이고, 그렇게 부풀린 컨텍스트를 다음 턴에 통째로 다시 보낸다. Databricks도 같은 지점을 짚는다. 실제 비용을 지배하는 것은 컨텍스트 비대이며 사용자 입력은 에이전트가 모은 컨텍스트 안에서 존재감이 없어진다는 것이다.

그래서 조직 비용은 덧셈이 아니라 곱셈으로 자란다.

월 비용 ≈ 활성 사용자 × 사용자당 세션 × 세션당 턴 × 턴당 컨텍스트 토큰 × 토큰 단가

다섯 개 축 중 어디를 건드리느냐에 따라 효과와 부작용이 완전히 다르다. 대부분의 조직이 첫 번째 축만 만지려 하는데, 그건 곱셈에서 가장 효과가 작고 반발이 가장 큰 항이다.

표에서 굵게 표시한 두 축이 이 글의 대부분을 차지한다. 코드 변경이 적고, 사용자 경험을 덜 건드리고, 효과가 즉시 숫자로 보이기 때문이다.

2. 효율 프런티어 - 가장 똑똑한 모델이 아니라 이 일에 충분한 모델

조직의 기본 모델은 대개 한 번 정해지고 오래 간다. 도입 시점에 가장 좋아 보이던 모델이 그대로 굳고, 그 뒤로 나온 저렴한 모델은 아무도 다시 재지 않는다. Databricks가 가장 큰 절감이 나온 곳으로 꼽는 지점이 정확히 여기다. 코딩 지출을 더 효율적인 모델로 옮기는 것.

핵심 개념은 효율 프런티어다. 최대 지능을 좇는 대신, 가격 대비 성능이 가장 좋은 지점을 추적한다는 뜻이다. 실무 작업 대부분은 프런티어급 능력을 필요로 하지 않는다는 관찰이 전제에 깔려 있다.

그 회사가 실제로 내린 판단 두 가지가 글에 나온다. 자체 벤치마크에서 GLM 계열이 가격 대비 성능에서 상당히 경쟁력 있게 나와 사내에 롤아웃했고, 반대로 Opus 4.7은 의미 있는 품질 향상 없이 비용이 되레 올라가는 결과가 나와 도입을 보류했다고 밝혔다.

이 두 판단을 결론으로 가져가지 말 것. 특정 회사의 워크로드, 특정 시점의 모델 묶음, 그 회사의 하네스에서 나온 결과다. 모델은 몇 달 단위로 갱신되고 가격도 따라 움직인다. 옮겨갈 만한 것은 판정 결과가 아니라 절차다. 대표 작업 세트를 고정해 두고, 새 모델이 나올 때마다 같은 세트로 다시 재고, 기본 모델을 바꿀지 결정한다.

프런티어를 재려면 세 가지가 미리 있어야 한다. 이게 없으면 모델 비교는 취향 논쟁으로 끝난다.

  • 대표 작업 세트 - 실제 저장소에서 뽑은 30~50건 정도의 과제. 난이도가 섞여 있어야 한다
  • 작업당 총비용 - 요청당 단가가 아니라 과제 하나를 끝낼 때까지의 누적 비용. 싼 모델이 턴을 두 배로 쓰면 비싼 모델이 더 싸다
  • 성공 판정 - 테스트 통과, 린트 통과, 리뷰어 승인처럼 자동으로 판정되는 기준. 모델의 자기 보고는 쓰지 않는다

세 번째가 가장 자주 빠진다. 성공 판정 없이 비용만 재면 항상 가장 싼 모델이 이긴다. 아무것도 못 끝내는 모델이 토큰을 가장 적게 쓰기 때문이다.

3. 라우팅 ① 요청 단위 - 무엇을 근거로 고르나

기본 모델을 한 단계 내리는 것은 일회성 절감이다. 그다음 단계는 요청마다 다른 모델을 쓰는 것, 즉 라우팅이다.

Databricks는 사내 Smart Router가 평균 작업 비용을 30퍼센트 이상 낮추면서 품질은 해당 모델 묶음에서 가장 비싼 모델과 대체로 맞먹었다고 밝혔다. 라우팅이 매력적인 이유가 이 문장에 다 들어 있다. 사용자에게 보이는 품질을 유지한 채로 단가만 내리는 몇 안 되는 수단이라는 것.

어려운 지점은 하나다. 요청이 도착한 시점에는 그 요청이 어려운지 알 수 없다. 한 줄짜리 질문이 전체 아키텍처 재설계로 번지기도 하고, 장문의 요구사항이 파일 하나만 고치면 끝나기도 한다. 그래서 실무 라우터는 완벽한 난이도 예측을 포기하고, 값싸게 얻을 수 있는 신호부터 소진한다.

  • 입력 규모 - 프롬프트 토큰 수, 첨부 파일 수, 저장소 크기
  • 도구 표면 - 활성화된 도구 개수. 도구가 많을수록 턴 수가 늘어난다
  • 작업 유형 - 자동완성, 인라인 수정, 대화형 질의, 자율 에이전트는 애초에 다른 요금 구간이다
  • 진입점 - IDE 인라인 요청과 CI 파이프라인의 자율 작업은 지연 허용치가 다르다
  • 이력 - 같은 세션에서 이미 실패한 적이 있는가

여기서 자주 걸리는 함정이 있다. 라우터 자체가 비용이다. 난이도 판정에 다시 LLM을 부르면 모든 요청에서 모델을 두 번 호출하는 셈이 된다. 분류용 모델이 아무리 싸도, 절감분의 상당 부분이 거기서 사라진다. 규칙 기반 신호로 갈 수 있는 데까지 가고, 남는 애매한 구간에만 모델 분류를 얹는 순서가 안전하다.

4. 라우팅 ② 작업 단위와 에스컬레이션, 그리고 캐시 함정

요청 단위보다 한 층 위에서 나누는 방법도 있다. 메타 하네스가 작업의 성격을 보고 배분하는 방식이다. 정형화된 단순 작업과 개방형 작업을 다른 모델에 보내고, 개방형 쪽에만 비싼 모델을 붙인다.

여기에 붙는 것이 에스컬레이션이다. 싼 모델이 먼저 시도하고, 실패하면 승격한다. 개념은 단순한데 실무에서 두 가지가 걸린다.

4.1 무엇을 실패로 볼 것인가

승격 판정을 모델의 자기 평가에 맡기면 안 된다. 못 하겠다고 말하지 않는 모델이 더 많다. 판정은 외부 신호로 해야 한다.

  • 테스트 스위트 실패 또는 컴파일 실패
  • 같은 파일에 대한 편집 반복 횟수가 임계 초과
  • 턴 수 또는 누적 토큰이 예산 초과
  • 사용자가 같은 요청을 다시 보냄

4.2 승격은 캐시를 깬다

이게 라우팅 절감을 조용히 갉아먹는 지점이다. 프롬프트 캐시는 모델 단위로 잡힌다. 세션 중간에 모델을 바꾸면 그 세션에 쌓아 둔 캐시는 전부 무효가 되고, 승격된 비싼 모델은 전체 대화를 캐시 미스 상태로 다시 읽는다. 승격 한 번에 그 세션의 캐시 이득이 통째로 날아갈 수 있다.

대응은 두 가지다. 첫째, 승격을 턴 중간이 아니라 세션 또는 작업 경계에서만 허용한다. 둘째, 승격 대상 작업을 서브 에이전트로 분리해 메인 루프의 모델은 고정한 채 하위 작업만 다른 모델에 던진다. 후자는 메인 세션의 캐시 접두부를 보존한다는 점에서 특히 유리하다.

5. 캐싱은 할인이 아니라 아키텍처 결정이다

프롬프트 캐싱을 요금 할인 옵션으로 취급하면 대체로 효과가 없다. 캐시는 접두 일치로 동작하기 때문이다. 렌더링 순서는 도구 정의, 시스템 프롬프트, 메시지 순이고, 앞쪽에서 1바이트가 바뀌면 그 뒤는 전부 무효가 된다. 즉 캐시 히트율은 프롬프트를 조립하는 코드의 구조가 결정한다.

5.1 배수와 손익분기

Anthropic 공식 문서 기준으로 캐시 쓰기는 기본 입력 단가의 1.25배(5분 TTL) 또는 2배(1시간 TTL)이고, 캐시 읽기는 0.1배다. 문서에 실린 Claude Opus 5 예시 단가를 그대로 옮기면 아래와 같다. 모델 단가는 자주 바뀌므로 2026년 8월 10일 확인 기준으로 읽어야 한다.

1시간 TTL은 요청 간격이 벌어지는 버스티한 트래픽에서 항목을 살려 두지만, 쓰기 비용이 두 배이므로 더 많은 읽기가 있어야 본전이 된다. 짧은 간격으로 계속 도는 워크로드라면 기본 5분으로 충분하다.

5.2 조용히 실패하는 최소 길이

같은 문서에 최소 캐시 가능 길이가 명시돼 있다. Claude Opus 5와 Fable 5, Mythos 5는 512토큰, Opus 4.8과 Sonnet 5, Sonnet 4.6, Sonnet 4.5, Opus 4.1, Opus 4는 1,024토큰, Opus 4.7과 Haiku 3.5는 2,048토큰, Opus 4.6과 Opus 4.5, Haiku 4.5는 4,096토큰이다. 이보다 짧은 접두부는 캐시 지시를 붙여도 캐시되지 않으며 오류도 반환하지 않는다. 코드는 정상으로 보이고 청구서만 그대로다.

5.3 조직 규모에서 히트율을 죽이는 것들

개인 도구에서는 눈에 안 띄지만 전사 규모에서는 치명적인 패턴이 몇 가지 있다.

  • 시스템 프롬프트에 현재 시각을 박는 것 - 요청마다 접두부가 달라진다. 전사 히트율이 0에 수렴한다
  • 사용자 ID나 세션 ID를 앞쪽에 끼워 넣는 것 - 사용자별로 캐시가 쪼개져 공유가 사라진다
  • 도구 목록을 사용자별로 조립하는 것 - 도구 정의는 맨 앞에 렌더링된다. 사람마다 다르면 아무도 캐시를 못 쓴다
  • JSON 직렬화 순서를 고정하지 않는 것 - 키 순서가 흔들리면 바이트가 달라진다
  • 조건부 시스템 섹션 - 플래그 조합마다 별개 접두부가 만들어진다

공식 문서가 밝힌 무효화 계층도 함께 봐야 한다. 도구 정의가 바뀌면 도구, 시스템, 메시지 캐시가 전부 무효가 되고, 시스템 프롬프트가 바뀌면 시스템 이하가 무효가 된다. 웹 검색이나 인용 토글, 속도 설정 변경, 노력 수준 변경도 캐시를 건드린다. tool_choice처럼 메시지 블록에만 영향을 주는 항목과 구분해서 다뤄야 한다.

5.4 히트율은 지표로 걸어라

응답의 usage에 세 값이 온다. cache_creation_input_tokens, cache_read_input_tokens, input_tokens이고 셋을 더한 것이 총 입력 토큰이다. 캐시 히트율은 읽기 토큰을 이 총합으로 나눈 값이다. 팀별로 이 비율을 대시보드에 걸어 두면, 누군가 시스템 프롬프트에 타임스탬프를 넣은 날 바로 표가 난다.

6. 토큰이 실제로 새는 자리 - 하네스와 도구 출력

Databricks는 하네스 튜닝과 캐싱 설정 조정으로 생성 토큰 수를 약 50퍼센트 줄이면서 품질을 유지했다고 밝혔다. 이 숫자가 흥미로운 이유는 모델을 바꾸지 않고 나온 값이라는 데 있다. 같은 모델, 같은 작업, 절반의 토큰이다.

어디를 보면 되는지는 대체로 정해져 있다.

  • 도구 출력 전문 삽입 - 테스트 로그 2,000줄, 빌드 출력 전체, 대용량 파일 통째. 상한을 걸고 초과분은 파일로 떨어뜨린 뒤 경로만 넘긴다
  • 같은 파일 반복 읽기 - 에이전트가 이전 턴에 읽은 파일을 다시 읽는다. 세션 내 읽기 캐시 한 겹으로 해결된다
  • 전체 읽기 대신 검색 - 파일을 통째로 읽는 대신 검색으로 필요한 구간만 가져오게 도구 설명을 바꾼다
  • 전체 파일 대신 diff 반환 - 수정 결과를 전문으로 되돌려받지 않는다
  • 실패한 계획의 잔재 - 폐기된 시도가 컨텍스트에 남아 다음 턴마다 다시 청구된다. 오래된 도구 결과를 정리하는 컨텍스트 편집이 여기에 붙는다
  • 장황한 시스템 프롬프트 - 안 쓰는 지침 2,000토큰은 모든 요청에 곱해진다

다만 여기에도 한계선이 있다. 압축이 재작업을 부르면 총비용은 오히려 오른다. 컨텍스트를 잘라 낸 탓에 에이전트가 같은 파일을 다시 찾아 읽으면, 줄인 토큰보다 늘어난 턴이 더 비싸다. 판정은 언제나 요청당 토큰이 아니라 작업당 총비용으로 한다.

7. 예산 ① 하드 캡이 실패하는 이유와 점진적 마찰

사람당 월 한도를 걸고 초과하면 차단하는 방식은 직관적이고 구현도 쉽다. Databricks는 이 방식을 역효과로 본다. 대신 통합된 비용 가시성과 단계적 승인 게이트, 모델 다운그레이드, 그리고 점진적인 마찰을 즉시 차단 대신 놓는다.

왜 역효과인가. 두 가지 때문이다.

첫째, 한도에 걸린 개발자는 일을 멈추지 않는다. 개인 계정으로 넘어가거나, 회사 코드를 개인 채팅창에 붙여 넣거나, 더 싸지만 결과가 나쁜 경로로 우회한다. 조직은 지출을 줄인 것이 아니라 지출의 가시성과 보안 통제를 동시에 잃는다.

둘째, 한도는 정보를 주지 않는다. 월 한도의 80퍼센트를 썼다는 사실은 지금 실행하려는 작업이 얼마짜리인지 알려주지 않는다. 사람은 자기 행동을 조정할 근거를 못 받은 채 갑자기 벽에 부딪힌다.

표 3. 점진적 마찰 - 차단 대신 단계를 둔다
단계작동 방식사용자가 겪는 것목적
1. 가시성거의 실시간 지출 피드백방금 작업이 얼마였는지 즉시 보임행동 조정의 근거 제공
2. 자가 해제 게이트임계 도달 시 경고 표시, 확인하면 계속한 번 멈칫하지만 막히지 않음무의식적 낭비만 걸러냄
3. 다운시프트임계 초과 시 저비용 모델로 자동 전환계속 쓸 수 있으나 결과 품질이 달라짐작업은 살리고 단가만 낮춤
4. 정지최후 수단차단사고 방지

다만 반대편도 사실이다. 조직 단위의 무제한 예산은 사고를 막지 못한다. 잘못 설정된 에이전트 루프 하나가 몇 시간 만에 월 예산을 태우는 일은 실제로 일어난다. 그래서 실무 구성은 두 층으로 갈린다.

  • 사람과 팀에는 점진적 마찰 - 정보를 주고, 대안을 주고, 마지막에만 막는다
  • 개별 세션과 개별 키에는 하드 캡 - 사람이 지켜보지 않는 자동 실행에는 절대 상한이 필요하다

이 구분이 중요하다. 사람에게 거는 한도와 프로세스에 거는 한도는 목적이 다르다. 앞의 것은 행동을 바꾸려는 것이고, 뒤의 것은 폭주를 끊으려는 것이다.

8. 예산 ② 어디에 한도를 거나 - 스코프 설계

예산 정책을 정했으면 어디에 거는지가 남는다. 게이트웨이 계층이 제공하는 스코프를 보면 설계 선택지가 분명해진다. 오픈소스 프록시인 LiteLLM 문서를 예로 들면 스코프가 여러 층으로 나뉜다.

설정 항목 하나가 특히 자주 사고를 낸다. budget_duration은 30s, 30m, 30h, 30d 형식을 받는데, 설정하지 않으면 예산이 리셋되지 않는다. 월 단위로 갱신될 것이라 믿고 비워 두면, 첫 달 예산을 소진한 시점에 팀 전체가 멈춘다.

집행 정확도도 봐야 한다. LiteLLM은 여러 워커에서 빠르고 일관되게 집행하기 위해 Redis 크로스팟 카운터를 쓰고 데이터베이스를 정본으로 두어 백그라운드에서 조정한다. 정확도가 중요한 배포에서는 fail_closed_budget_enforcement를 켜 매 요청마다 데이터베이스와 대조하게 할 수 있다. 즉 예산 집행에는 정확도와 지연의 트레이드오프가 있고, 기본값은 대체로 지연 쪽이다.

8.1 예산보다 속도 제한이 먼저다

예산은 사후 지표다. 이미 쓴 돈을 세는 것이라 폭주를 실시간으로 끊지 못한다. 실시간으로 끊는 것은 속도 제한이다. 분당 토큰과 분당 요청, 동시 요청 수를 먼저 걸어 두면 사고의 최대 크기가 정해진다.

  • 분당 토큰 - 입력만, 출력만, 합계 중 무엇을 셀지 정할 수 있다(token_rate_limit_type)
  • 분당 요청 - 재시도 루프가 폭주할 때 가장 먼저 걸린다
  • 동시 요청 - max_parallel_requests. 병렬 서브 에이전트가 많은 하네스에서 특히 중요하다
  • 모델별 제한 - model_rpm_limit, model_tpm_limit. 비싼 모델만 따로 조인다

순서를 정리하면 이렇다. 속도 제한으로 사고의 상한을 정하고, 세션 캡으로 자동 실행을 끊고, 예산으로 추세를 관리하고, 마찰로 행동을 바꾼다.

9. 사용량 가시성 - 무엇을 재야 통제가 되나

여기가 대부분의 조직이 실제로 막히는 지점이다. 청구서는 있는데 그 안에 사람 이름도, 저장소 이름도, 작업 이름도 없다. 그 상태에서 내릴 수 있는 결정은 총액을 줄이자는 것뿐이다.

9.1 단위를 바꿔야 한다

사람당 월 지출은 통제 가능한 단위가 아니다. 통제 가능한 단위는 작업당 비용이다. 풀 리퀘스트 한 건에 얼마, 버그 수정 한 건에 얼마, 테스트 통과 한 번에 얼마. 이 단위로 환산돼야 모델을 바꿨을 때, 하네스를 고쳤을 때 효과가 숫자로 보인다. 그리고 그 지출이 만들어 낸 산출물과 나란히 놓을 수 있어야 감축과 투자를 구분할 수 있다.

9.2 지표 이름은 표준을 따른다

수집 층에서 지표 이름을 직접 지으면 도구를 바꿀 때마다 대시보드를 다시 만들게 된다. OpenTelemetry의 생성형 AI 시맨틱 컨벤션이 이 부분을 정의해 두었다.

표 5. OpenTelemetry 생성형 AI 지표 (안정성: 개발 단계)

요청 모델과 응답 모델이 별도 속성으로 분리돼 있다는 점이 라우팅을 운영할 때 특히 유용하다. 요청한 모델과 실제로 응답한 모델이 다른 경우, 즉 라우팅이나 폴백이 개입한 경우를 지표에서 바로 구분할 수 있다.

주의할 점 하나. 이 컨벤션은 아직 개발 단계 안정성이다. 지표 이름과 속성이 바뀔 수 있으므로 수집기에 매핑을 한 겹 두고, 대시보드가 원시 이름을 직접 참조하지 않게 하는 편이 낫다.

9.3 AI 지출을 클라우드 지출과 같은 표에 올리려면

AI 지출을 별도 스프레드시트에서 관리하면 결국 아무도 안 본다. FinOps Foundation의 FOCUS는 AI와 클라우드, SaaS, 데이터센터의 청구 데이터를 하나의 스키마로 정규화하는 공개 명세이고 현재 1.4 버전이다. 청구 데이터를 여기에 맞춰 두면 AI 지출을 기존 클라우드 비용 대시보드와 같은 축에서 볼 수 있다.

9.4 지연이 통제력을 결정한다

Databricks가 가시성 항목에서 강조하는 것도 결국 속도다. 거의 즉각적인 지출 피드백을 주는 대시보드. 월말 청구서는 통제 수단이 아니다. 30일 지난 정보로는 아무 행동도 바꿀 수 없다. 하루 단위면 추세를 볼 수 있고, 세션 단위면 사람이 자기 행동을 조정한다.

10. AI 게이트웨이 - 중앙에 한 겹을 두는 값과 대가

앞의 모든 통제 수단에는 공통 전제가 있다. 어딘가 한 곳에서 집행돼야 한다는 것이다. 모델 선택이 팀마다 코드에 박혀 있으면 프런티어가 옮겨가도 따라갈 수 없고, 예산 규칙이 애플리케이션마다 있으면 일관성이 없고, 지표 형식이 제각각이면 작업당 비용을 못 낸다.

Databricks도 중앙 인프라를 둔다. 모델 메뉴 관리, 점진적 마찰 정책을 포함한 예산 추적, 설정 강제, 분석용 세션 로깅을 한 곳에서 담당하는 구성이다. 모델이 바뀌어도 유연성을 유지하기 위한 장치라고 설명한다.

10.1 게이트웨이가 있어야 가능한 것

  • 모델 교체를 설정 변경으로 - 배포 없이 기본 모델을 바꾼다. 이게 프런티어 추적의 전제다
  • 예산과 속도 제한의 단일 집행점 - 우회 경로가 없다
  • 캐시 정책 통일 - 시스템 프롬프트 구조를 표준화해 조직 전체 히트율을 올린다
  • 감사와 데이터 통제 - 어떤 코드가 어느 공급자로 나갔는지 기록이 남는다
  • 공급자 다변화 - 장애나 요율 제한 시 대체 경로

10.2 게이트웨이가 만드는 새 위험

  • 단일 장애점 - 게이트웨이가 죽으면 전사 개발이 멈춘다. 장애 시 통과와 차단 중 어느 쪽이 기본값인지 미리 정해야 한다
  • 지연 한 겹 - 인라인 자동완성처럼 지연에 민감한 경로는 우회로가 필요할 수 있다
  • 캐시 파괴 - 게이트웨이가 프롬프트를 재조립하거나 헤더를 끼워 넣어 접두부를 바꾸면 캐시가 통째로 깨진다. 비용을 줄이려고 넣은 계층이 비용을 올리는 전형적인 경우다
  • 기능 지연 - 공급자의 새 기능이 게이트웨이에 반영될 때까지 못 쓴다

도입한다면 최소한 세 가지는 도입 전에 확인하는 편이 좋다. 캐시 접두부를 바이트 단위로 보존하는가, 예산 집행이 여러 인스턴스에서 일관되게 동작하는가, 장애 시 기본 동작이 무엇인가.

11. 도입 순서 - 무엇부터 손대나

여섯 가지를 한꺼번에 하면 무엇이 효과가 있었는지 알 수 없다. 순서에는 이유가 있다. 앞 단계가 뒤 단계를 측정할 기반을 만든다.

  1. 가시성부터 - 지출을 팀·저장소·작업 단위로 귀속시킨다. 이게 없으면 나머지 전부가 추측이다. 여기서 대개 이미 답이 나온다. 지출의 대부분이 소수의 워크로드에 몰려 있는 경우가 흔하다
  2. 캐시 히트율 회복 - 코드 변경이 가장 적고 효과가 즉시 나타난다. 시스템 프롬프트에서 변동 요소를 빼고, 도구 목록을 결정적으로 만들고, 히트율을 지표로 건다
  3. 하네스 정리 - 도구 출력 상한, 검색 우선, diff 반환, 오래된 도구 결과 정리. 모델을 바꾸지 않고 줄일 수 있는 마지막 구간이다
  4. 기본 모델 재측정 - 대표 작업 세트로 프런티어를 재고 기본값을 옮긴다. 게이트웨이가 있으면 설정 한 줄이다
  5. 라우팅 - 여기서 시작하지 않는 이유는, 앞 단계가 안 돼 있으면 라우팅 효과를 측정할 기준선이 없기 때문이다
  6. 예산 마찰 정책 - 상시 운영. 다만 세션 단위 하드 캡과 속도 제한은 1번과 동시에 걸어 두는 편이 낫다. 사고는 순서를 기다려 주지 않는다

12. 자주 하는 실수

  • 요청당 단가로 모델을 고르는 것 - 싼 모델이 턴을 두 배 쓰면 총비용은 더 비싸다. 판정은 작업당 총비용으로
  • 캐시를 켜 놓고 히트율을 안 보는 것 - 최소 길이 미달과 접두부 변동은 오류 없이 조용히 실패한다
  • 세션 중간에 모델을 바꾸는 것 - 라우팅 절감을 캐시 손실이 상쇄한다
  • 사람에게만 한도를 거는 것 - 자동 실행에 캡이 없으면 사고는 그쪽에서 난다
  • 예산 리셋 주기를 비워 두는 것 - 리셋되지 않는 예산은 소진 시점에 팀을 멈춘다
  • 다른 회사의 절감치를 목표로 삼는 것 - 30퍼센트든 50퍼센트든 그 회사의 워크로드에서 나온 값이다. 옮겨갈 것은 측정 절차다
  • 총사용자 수나 총토큰을 KPI로 두는 것 - 둘 다 줄이는 가장 쉬운 방법은 도구를 안 쓰는 것이다
  • 게이트웨이가 캐시를 깨는 것을 못 보는 것 - 비용 절감용 계층이 비용을 올리는 경우가 실제로 있다
  • 가시성 없이 마찰부터 거는 것 - 정보를 안 주고 막으면 사람은 우회한다

13. 확인하지 못한 것

본문에 쓰지 않은 것들과, 인용했지만 검증 범위가 제한된 것들을 여기 모았다.

  • 인용한 절감치의 측정 조건 - 30퍼센트 이상, 약 50퍼센트라는 수치의 표본 크기, 측정 기간, 워크로드 정의, 품질 판정 기준은 공개돼 있지 않다. 방향성만 참고할 값이다
  • Smart Router의 구현 - 어떤 신호로 라우팅하는지, 어떤 모델 묶음을 대상으로 했는지는 공개 문서에 없다
  • 배치·비동기 처리 할인율 - 지연을 허용하는 대가로 단가를 낮추는 방식은 널리 쓰이지만, 할인 폭은 공급자와 시점에 따라 다르다. 계약서와 현행 요금표에서 직접 확인해야 하는 값이라 여기에 숫자를 적지 않았다
  • 모델별 현행 단가 - 표 2의 단가는 공식 문서에 실린 예시이고 2026년 8월 10일 기준이다. 도입 판단 전에 반드시 다시 확인해야 한다
  • 좌석 요금제와 API 종량제가 섞인 조직의 실효 단가 - 도구마다 구조가 달라 일반화할 근거를 찾지 못했다
  • OpenTelemetry 생성형 AI 지표의 안정화 시점 - 현재 개발 단계이며 GA 일정은 명시돼 있지 않다
  • FOCUS 1.4의 AI 관련 컬럼 세부 - 명세가 AI 청구 데이터를 포함한다는 것까지는 확인했으나, 개별 컬럼 정의는 별도 컬럼 라이브러리 문서를 봐야 한다

결론

정리하면 순서는 이렇다. 먼저 보이게 하고, 그다음 구조를 고치고, 마지막에 한도를 건다. 대부분의 조직이 이 순서를 거꾸로 밟는다. 청구서를 보고 놀라서 한도부터 걸고, 사람들이 우회하고, 가시성은 더 나빠지고, 다음 달 청구서를 보고 또 놀란다.

이 글에서 다룬 여섯 가지 중 코드 변경 대비 효과가 가장 큰 것은 캐싱이다. 시스템 프롬프트에서 변동 요소를 빼고 도구 목록을 고정하는 작업은 하루면 되고, 히트율은 다음 날 지표에 나온다. 가장 오래 걸리지만 반복해서 이득이 나는 것은 모델 프런티어를 주기적으로 재는 절차다. 한 번 만들어 두면 새 모델이 나올 때마다 하루 만에 판단이 나온다.

그리고 한도에 관해서라면, 사람에게 거는 한도와 프로세스에 거는 한도를 절대 섞지 말 것. 사람에게는 정보와 선택지를 주고 마지막에만 막고, 사람이 지켜보지 않는 자동 실행에는 처음부터 단단한 상한을 건다. 이 구분 하나가 정책의 성패를 대부분 가른다.
