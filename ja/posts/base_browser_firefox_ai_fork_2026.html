1. FirefoxのAI統合と「完全削除」への問題意識

現代のウェブブラウザエンジンは、数千万行に及ぶ巨大なコードベースの上で動作しています。一般的にソフトウェアエコシステムが成熟するにつれ、上流ベンダーは収益化モデルや新たな技術トレンドを取り込み、ブラウザ内部に複雑な付加レイヤーを増設していく傾向があります。オープンソースコミュニティにおいて長年、最後の砦とみなされてきたFirefoxも例外ではなく、近年ではデバイス内処理やリモート連携を含む人工知能関連の補助機能がエンジンの深層部に相次いで組み込まれてきました。

こうした状況に対し、セキュリティ研究者であり独立系開発者のSarah Jamie Lewisは、2026年9月19日に公開した論考「Thoughts on the Future of Web Browsers」の中で根源的な危機感を表明しました。原文は7月に著者がMastodonスレッドに投稿した文章を引用し、独立した混じり気のないウェブの未来がわずかでも残されているならば、今こそすべてのFirefoxフォークプロジェクトが結集し、Mozillaから隔離されたハードフォークを維持するために協調すべき時であると指摘しています。原文は、この取り組みが単独の小規模プロジェクトで担うには大きすぎるものの、Mozillaのような組織の指導下に放置するにはあまりにも重要すぎる課題であると位置づけています。

原文において著者は、MozillaおよびFirefoxが過去10年間にわたり自らの進むべき方向性を明確に定め、その方向へ一貫して進み続けてきたと診断しています。原文は次のように記しています。「Mozilla and, by extension, Firefox have laid out the direction they want to go - and have consistently moved in that direction over the last decade. There is no redemption arc there, they are not going to turn the ship around - and every week and month that goes by, Firefox gains more slop and drifts further from the visions that founded it.」すなわち、上流プロジェクトが自発的に舵を切り直す可能性は存在せず、コードベース自体の分離しか残されていないという結論に達したのです。

本稿の解釈では、設定画面のチェックボックスを外すような受動的な抵抗策では、ブラウザコアの再編速度に到底追いつけないという危機感が背景にあるとみられます。上流プロジェクトがブラウザウィンドウ全体をAIエージェントの作業空間として再定義しようとしている局面において、単なるフラグ操作は一時しのぎにすぎません。本稿の推測では、著者が提示した「隔離されたハードフォーク」構想は、こうした機能追加がウェブレンダリングエンジンの信頼性を根本から損ねているという技術的評価から生み出されたものです。

2. Base Browserの正体 — 設定無効化ではなくコードの削ぎ落とし

Mastodonスレッドを発端とした議論は、Codebergプラットフォーム上に開設されたBase Browser Projectとして具現化されました。原文はこのプロジェクトについて、技術的な方向性や設計思想を共有し議論するための場を確保する試みとして立ち上げられたと説明しています。原文に記されたBase Browserの明確な定義は次の通りです。原文は「A set of patches, based around the current Firefox 153 ESR, that strip user hostile features completely out of the code base (as opposed to the common soft-fork approach of disabling these.)」と述べています。

ここにおける決定的な違いは、「設定による無効化（disabling）」と「コードベースからの完全な削ぎ落とし（strip completely out）」の間に存在します。一般的なオープンソースのブラウザ派生プロジェクトでは、設定ファイルやビルドフラグの変更を通じてテレメトリや不要な外部連携機能をオフにするソフトフォーク手法が主流です。しかしBase Browserは単なる機能停止にとどまらず、ユーザーにとって敵対的であるとみなしたモジュールそのものをソースコードから物理的に消去するアプローチを貫いています。

原文の中で著者は、このように機能をコードベースから完全に削除する手法こそが正しいアプローチであると断言しています。著者は原文において「I believe that deleting these features entirely is the correct approach for exactly the reasons that make it a pain - these features are large, and increasingly tightly integrated into the core browser. They also account for an increasingly percentage of the total firefox code base and quite frankly: I do not believe that these features should be anywhere near the core base of a web browser」と力説しています。作業が極めて苦痛であるというまさにその理由ゆえに、完全な削除が不可欠であるという逆説的な論理です。

本稿の解釈では、コードがバイナリ内に残存する限り、意図しないIPC通信経路やライブラリ間の依存関係が潜在的な脆弱性として残り続けるため、削除が選択されたと考えられます。複雑化したブラウザ環境では、無効化フラグが上流のバージョン更新によって突然上書きされたり、予期せず再有効化されたりするリスクを排除できません。本稿の推測では、Base Browser開発チームが削除という維持コストの極めて高い強硬手段を選択したのは、潜在的なコード混入をソースツリー単位で根絶するという強固な設計思想に基づいています。

3. 初期AI除去パッチの規模と圧縮プロセス

Base Browserプロジェクトの最初の具体的な成果物として著者が自ら作成したのは、AI関連の統合モジュールを徹底的に切除する巨大なパッチでした。原文はその規模について「a ridiculous patch impacting 1605 files changed with 852297 deletions, totalling 37 megabytes」と記述しています。単一の機能群を排除するための差分ファイルが37MBに達し、1,605ファイルにわたって85万行以上が削除されるという、前例のない規模のパッチでした。

原文は、この巨大な初期パッチがBase Browserプロジェクトの正式な配布パッチそのものを指しているのではなく、FirefoxからAI連携コードを丸ごと削除しようとした際に直面した初期作業の規模を示すものであると明記しています。ブラウザエンジン全体にAI機能の呼び出しやフック処理がいかに広範囲に侵食していたかを数値で物語る証拠です。その後数週間にわたり、著者と少数のボランティアチームはパッチの改良と追加作業を継続しました。

原文によると、この作業にはcliffmccarthy氏およびgellge氏が具体的に貢献し、パッチのテストや議論に関わった有志が支援を行いました。開発チームは、37MBという巨大なdiffファイルを実用的な1MB未満のサイズへと圧縮するスクリプトを構築しました。原文の説明によれば、Gitに備わっている不可逆削除フラグと独自のPythonスクリプトを組み合わせることで、対象ツリーへの再パッチ適用を可能にしつつ、配布容量を劇的に削減することに成功しました。

本稿の解釈では、37MBから1MB未満への劇的な容量削減は、ファイル全体の削除に伴う冗長な行差分情報をメタデータ形式へと最適化した結果であると推察されます。何百ものソースファイルを丸ごと消去する場合、通常のテキストdiff形式ではファイル内の全行がマイナス符号付きで記録されるため、パッチサイズが肥大化します。本稿の推測では、チームが専用スクリプトを作成せざるを得なかったという事実は、削除対象となったコードの規模がいかに通常のリファクタリングの枠を超えていたかを如実に示しています。

4. 既存フォーク（Tor Browser・Waterfox）の緩和手法との対比

原文において著者は、オープンソースブラウザ界の代表的なプロジェクトであるTor BrowserおよびWaterfoxの現行手法を取り上げ、明確な対比を行っています。原文は「Projects like Tor Browser and Waterfox are painstakingly disabling / patching out the worst - but every release becomes more expensive, and things do slip through.」と述べています。既存の派生ブラウザが採用しているのは、問題のある最悪の機能を丹念に無効化したり、部分的なパッチで抑え込んだりするアプローチです。

しかし、こうした選択的無効化は、上流ブラウザが新バージョンをリリースするたびに膨大な検証コストをもたらします。原文が指摘するように、リリースを重ねるごとにパッチの維持管理コストは高騰し、厳格な監視を敷いていても意図しないコードやテレメトリが網の目をかいくぐって混入する事態が発生します。上流の大規模なコード改修に追随する中で、無効化パッチが不意に破損するリスクは常に付きまといます。

ブラウザのカスタマイズ手法における構造的比較
アプローチ分類 代表的なプロジェクト 実装メカニズム 主なメリット アーキテクチャ上の代償と保守リスク
ソフトフォーク・部分無効化 Tor Browser、Waterfox 設定フラグの停止および問題箇所の局所的パッチ 上流コードとの整合性維持が容易、リベース負担が低い 毎リリースの検証コスト増大、意図せぬコード混入リスク
コードベース完全削除 Base Browser 不要モジュールや関連ファイル全体の物理的除去 コアとの複雑な依存関係を根絶、コードベース軽量化 上流更新時のマージ衝突が極大化、膨大な保守開発力が必要

原文の記述に基づき、これら2つのアプローチが抱える技術的な相違点を整理すると次のようになります。

  • Tor BrowserやWaterfoxは、上流のセキュリティ修正に迅速に追随するため、設定フラグや部分パッチによる無効化を優先してきました。
  • 部分的な無効化パッチは、上流のリリースサイクルが進むにつれて追跡と動作検証にかかる労力が累積していきます。
  • Base Browserは、ブラウザコアと深く癒着する不要機能を根本から排除するため、ソースツリーからの物理的切除を選択しました。
  • 完全削除のアプローチは潜在的な混入リスクをゼロに近づける反面、上流の改修に伴うリベースの難易度を極限まで押し上げます。

本稿の解釈では、既存プロジェクトのメンテナが完全削除の利点を知らなかったわけではなく、毎月更新されるセキュリティパッチを適用し続けるという現実的な制約から、やむを得ず無効化手法を選択してきたと考えられます。コードを大規模に削除した瞬間に、上流ブランチとの共通基盤が崩壊してしまうためです。本稿の推測では、Base Browserの試みは、既存フォークが強いられてきた妥協の限界を打破しようとする挑戦であると同時に、極めて険しい道をあえて突き進む選択といえます。

5. ブラウザの方向性に対する著者の診断 — Smart WindowとAIエージェント

著者がこのような抜本的なコード削除に踏み切った背景には、Firefoxが向かおうとしている将来像に対する深い不信感があります。原文によると、Firefoxは単なる独立したAI機能の追加にとどまらない領域へと歩みを進めています。原文はMastodonリンクを交えつつ、ブラウザ全体のコンテキストが人間のユーザーのためだけでなく、サードパーティのAIエージェントのために構築されたいわゆる「smartwindow」となる未来を描いていると指摘しています。

ブラウザウィンドウが人間の閲覧ツールから、自律型エージェントの作業環境へと変化するとき、ウェブクライアントの基本的な信頼境界は根本から覆ります。以前の論考MistralとMozillaのSmart Window提携が明かしたものと明かさなかったもの — AIブラウジングのプライバシー公約を解剖するで検証した通り、タブ内の閲覧コンテキストをAIモデルに供給する設計は、ブラウザと外部サービスとの間に密接なデータ循環を要求します。その結果、ブラウザエンジン内部には常時動作する状態監視やフック処理が不可欠となります。

原文の中で著者は「I don't want the web to go in that direction and, frankly, I cannot follow.」と表明しています。ウェブがAIエージェント中心のプラットフォームへと変貌していく流れを望んでおらず、率直に言ってそれには追随できないという強い拒絶の意思です。また、著者は自分自身がこのような大規模なプロジェクトを率いるのに適した人間ではないと述べつつも、少なくとも何かが起こるきっかけを作るために行動を起こす必要があったと吐露しています。

本稿の解釈では、ブラウザの主権が人間からエージェントへと奪われつつあるという危機感こそが、コード削除という強硬策を選ばせた最大の原動力であるとみられます。ブラウザシェルがAIの制御盤へと変わる時、旧来のサンドボックスモデルやプライバシー境界は形骸化しかねません。本稿の推測では、著者がBase Browserを通じて守ろうとしたのは単なるフットプリントの節約ではなく、ウェブを人間の能動的なコントロール下に留めておくという主権の防衛です。

6. 消費を超えた創作の道具へ — Amaya、Flock、そして代替プロトコル

原文は単に現状を否定しコードを削除するだけでなく、ウェブブラウザがかつて抱いていた理想的なビジョンへと目を向けています。著者は原文の中で「I often think about the visions put forth by browsers like Amaya and, much later Flock. That a browser should be a tool for creation as much as consumption.」と記しています。ブラウザとは単に完成されたコンテンツを受け取って消費するだけのツールではなく、自ら情報を生み出し共有するための創作の道具であるべきだという思想です。

W3CとINRIAが初期ウェブ標準の実験場として開発したAmayaは、ブラウザであると同時にWYSIWYG型のHTMLエディタでもありました。また2000年代半ばに登場したFlockは、ブログ投稿やソーシャル連携、分散タギングをブラウザ機能として統合し、読み書き可能なウェブの復興を試みました。原文は、2000年代初頭にFirefoxがブラウザルネサンスを引き起こした当時、フィードやブログ連携、自由なコメント投稿など、ブラウザの可能性に対する期待に満ち溢れていた時代を振り返っています。

原文が描き出す過去の理想と現代のウェブ標準との乖離は、以下のような論点として整理されています。

  • Amayaが志向していたような、ウェブ文書の閲覧と執筆が一体となった双方向的な創作ツールとしてのあり方。
  • Flockが示したような、分散型ブログやソーシャル機能と直接結びついたコミュニケーション基盤としてのブラウザ。
  • 商業的利害関係と大企業ベンダーの都合によって規格が極限まで肥大化してしまった現代ウェブ標準の閉塞感。
  • ページを読み込むたびに肌で感じられる、純粋な哲学的理念と期待される投資リターンとの間の構造的摩擦。

原文によれば、著者は創作ツールとしての理想を今なお胸に抱き続けており、近年では大規模言語モデルではなくGeminiプロトコル（geminiprotocol.net、原文で明示的に「LLMではなくプロトコルのGemini」と言及）やRSSをサポートする小型ブラウザを自作する実験を重ねてきました。商業主義に汚染されていない代替技術を通じて、ウェブの新たな可能性を模索しているのです。著者はそれが決定的な未来であるかは確信が持てないとしつつも、一つの未来の形にはなり得ると述べ、「we need new noise（新たな響きが必要だ）」という古いスローガンを引用しています。

7. ウェブ依存度を下げるための3つの暫定的措置

本格的な代替ブラウザ基盤の構築には長い歳月を要します。そのため著者は原文において、Firefoxや巨大ブラウザへの日々の依存度を下げるために自らが実践している3つの具体的な暫定措置を明らかにしています。ブラウザの外側へと作業環境を分散させる実践的な自己防衛策です。

  1. 可能な限りオフラインへ移行する： 原文は、基本的なウェブ閲覧作業を主要ブラウザから切り離す手段として、openzimリーダー（Kiwixなど）を試験的に活用していると述べています。OpenZIM形式はシンプルなブラウザでも処理可能な最小限のHTML/CSS/JSで構成される傾向があり、エンジンを介さずにオフラインでコンテンツを閲覧できます。
  2. 可能な場所ではスタンドアロンアプリへ移行する： デスクトップ環境で多くの時間を過ごす立場として、ブラウザ内で動くウェブアプリよりも独立した専用アプリを好むと記しています。著者はMastodonなど、オフラインリーダーで代替できないオンラインサービスを専用アプリへ移行する実験を行っています。
  3. 可能な場所ではフィードリーダーへ移行する： 独立アプリと同様に、RSSやAtomなどのフィードを活用することで、重厚なブラウザエンジンを起動することなくオンラインの更新情報を受け取り、やり取りを完結させることが可能です。

本稿の解釈では、これらの措置は、現代のウェブが強いる過剰なクライアントサイド演算や追跡環境から物理的に身を守るための実践的防衛ラインと位置づけられます。フル機能のレンダリングエンジンを立ち上げずに静的なフィードや事前に取得したアーカイブを閲覧するスタイルは、ベンダーの方針転換に左右されない堅牢な逃避先となります。本稿の推測では、著者がこうした個人の運用手順を提示したのは、Base Browserのような基盤分離が結実するまでの間、日常の生産性を維持するための現実的な妥協策です。

8. 持続可能性の現実的限界とコミュニティ結集の必要性

原文において最も誠実かつ冷静な点は、この挑戦が直面している冷徹な現実を隠さずに認めていることです。著者は原文において、この戦いに敗れる覚悟ができていると率直に告白しています。原文は「Now, I am well prepared to lose this battle. I do not believe that there is enough funding, or enough developer effort to maintain something like this long term. Unless we all pool our efforts into making a base like this possible.」と明記しています。長期間にわたってこのようなベースを維持するには、資金も開発者のマンパワーも圧倒的に不足しているという現実の吐露です。

ブラウザを開発し、日々の脆弱性を修正し、激変するウェブ標準に追随し続けるには、莫大な資本と専任のエンジニア組織が不可欠です。原文は、過去10年余りでウェブ標準があまりにも商業優先で過飽和になっており、品質保証とセキュリティを備えたブラウザを維持するには潤沢な資金を持つチームを自ら抱えるか、依存関係ツリーの中に組み込むしかないと分析しています。しかし、資金の流入には必ず見返りの制約が伴い、それがブラウザの独立性を損なう要因となります。

原文が示すBase Browserの存続条件と著者の心情は、以下のようにまとめられます。

  • 上流のブラウザが常に構造変化を続けているため、プロジェクトの土台自体が流動的な砂上の楼閣の上に置かれている。
  • 長期的な維持を成し遂げるには、個別に散らばっているフォークプロジェクトやコミュニティが力を結集し、単一のベースを共同保守しなければならない。
  • この取り組みを通じて、わずか数人でもFirefoxをソースコードからビルドする方法を学ぶ人が現れれば、それだけでも十分な勝利とみなす。
  • 既存のどのオープンソースプロジェクトであっても、このパッチセットを公式に採用あるいは活用してくれるならば、これ以上の喜びはない。

本稿の解釈では、Base Browserの真の価値は、単独で完成されたエンドユーザー向け製品を提供することではなく、分断された非Chromiumコミュニティに対して共有可能な「クリーンな共通ベース」という参照点を提示したことにあります。単独では不可能であっても、複数のフォークが単一のベースパッチを共同で保守すれば、上流追随の負担を分散できるためです。本稿の推測では、著者の冷静な敗北宣言は無力感の表れではなく、関係者が厳しい現実を直視し結束することを促すための戦略的メッセージです。
