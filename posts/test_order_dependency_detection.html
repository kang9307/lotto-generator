테스트 순서를 섞으면 드러나는 것 - 숨은 의존을 찾아내는 법

통과는 「맞다」가 아니라 「이 순서에서는 맞다」였다

2026-07-31 개발/인프라

서론: CI에서만 깨지고 내 컴퓨터에선 통과한다

월요일 아침 CI가 빨강이다. 로그를 열어 보니 어제까지 멀쩡하던 테스트 하나가 실패해 있다. 그 테스트를 골라 로컬에서 돌린다. 통과한다. 다시 돌린다. 또 통과한다. 코드를 아무리 들여다봐도 틀린 곳이 없다. 그래서 재실행 버튼을 누른다. 이번에는 초록이 뜬다. 그렇게 넘어간다.

이 상황에서 대부분은 「가끔 깨지는 테스트」라는 이름표를 붙이고 지나간다. 그런데 그 이름표는 원인을 하나도 설명하지 않는다. 이 글은 그중 한 가지 원인만 다룬다. 실행 순서다.

순서 의존은 다른 불안정 요인과 결이 다르다. 시간이나 동시성 때문에 흔들리는 것은 같은 조건에서도 결과가 달라지지만, 순서 의존은 완전히 결정론적이다. 같은 순서로 돌리면 언제나 같은 결과가 나온다. 단지 그 순서가 언제 바뀌는지 아무도 신경 쓰지 않았을 뿐이다.

그래서 이 글의 논지는 「테스트를 격리하세요」가 아니다. 그 말은 결론이지 진단이 아니다. 이 글이 말하려는 것은 이것이다.

테스트 사이에 남는 상태가 있으면 순서가 곧 입력이다. 그러면 통과는 「맞다」가 아니라 「이 순서에서는 맞다」가 된다. 그리고 그 순서는 아무도 검증한 적이 없는 입력이다.

이렇게 보면 순서를 섞는 일이 무엇인지도 달라진다. 그것은 결벽증이나 취향이 아니라 입력 범위를 넓히는 일이다. 하나의 순서만 돌리는 것은 하나의 입력값만 넣어 보고 함수가 옳다고 선언하는 것과 같다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 도구는 Python 3.13.3 (win32, MSC v.1943 64bit)의 표준 라이브러리 unittest와 Node.js v22.16.0 (win32 x64)의 node:test이고, 셸은 GNU bash 5.2.37 (MSYS2)다.

없어서 못 돌린 것. 이 환경에는 pytest가 설치되어 있지 않았다(No module named pytest). Python 3.11에서도 마찬가지였다. nose2도 없었다. 그래서 pytest 계열의 순서 동작과 관련 플러그인은 직접 측정하지 못했다. 이 글에서 pytest를 언급하는 대목은 문서를 근거로 한 것이고, 실측이 아니라고 따로 표시했다.

스크립트는 모두 파일로 저장해 실행했다. 아래 예제와 경로는 전부 /tmp/order-demo 같은 자리표시자로 옮겨 적은 가상 코드다.

1. 문제의 테스트 네 개

실험 대상을 먼저 보자. 아주 흔한 모양이다. 모듈 하나가 전역 딕셔너리를 갖고, 테스트들이 그것을 함께 쓴다.

# /tmp/order-demo/store.py
CONNECTIONS = {}          # 프로세스당 한 번만 임포트되는 모듈 수준 전역

# /tmp/order-demo/tests_shared.py
import unittest
import store

class SessionTests(unittest.TestCase):
    # 일부러 d, b, a, c 순서로 정의했다
    def test_d_close_all(self):
        store.CONNECTIONS.clear()
        self.assertEqual(store.CONNECTIONS, {})

    def test_b_query_uses_connection(self):
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_a_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"
        self.assertEqual(len(store.CONNECTIONS), 1)

    def test_c_registry_has_one_entry(self):
        self.assertEqual(len(store.CONNECTIONS), 1)

네 개 모두 그 자체로는 읽기에 자연스럽다. 연결을 열고, 질의하고, 개수를 세고, 닫는다. 어디에도 「앞 테스트가 연결을 열어 두었을 것」이라고 적혀 있지 않다. 그런데 실제로는 그렇게 되어 있다.

이제 같은 네 개를 두 가지 순서로 돌린다. 코드는 한 글자도 바뀌지 않았다.

2.1 순서가 입력이라면, 입력 공간은 얼마나 되나

두 가지만 보면 「운이 나빴다」로 넘어갈 수 있다. 그래서 24가지 순열을 전부 새 프로세스로 돌려 봤다.

all 24 permutations of 4 tests, each in a fresh process

GREEN (4):
    a b c d
    a c b d
    d a b c
    d a c b

RED   (20):
    a b d c   a c d b   a d b c   a d c b   b a c d   b a d c
    b c a d   b c d a   b d a c   b d c a   c a b d   c a d b
    c b a d   c b d a   c d a b   c d b a   d b a c   d b c a
    d c a b   d c b a

pass rate : 4/24 = 17%

통과율이 17퍼센트다. 그리고 결정적인 사실이 하나 더 있다. 이 도구의 기본 순서인 a b c d가 초록 4개 중 첫 번째다. 개발자는 매일 초록을 보고 있었고, 순서가 조금만 흔들리면 곧바로 빨강이 되는 상태로 몇 달을 지냈을 수 있다.

  • 초록인 네 순열을 보면 공통점이 보인다. a가 b와 c보다 앞에 있고, d는 b·c보다 뒤에 있다
  • 이 제약은 코드 어디에도 적혀 있지 않다. 이름의 알파벳 순서가 우연히 그 제약을 만족시켰을 뿐이다
  • 누군가 test_a_open_connection을 test_setup_connection으로 개명하는 순간 빨강이 된다. 리팩터링이 테스트를 깨뜨리는 것이 아니라 숨어 있던 의존이 드러나는 것이다
  • 테스트를 하나 추가하는 것만으로도 순서가 밀린다. 새 테스트는 아무 잘못이 없는데 다른 테스트가 빨강이 된다

3. 기본 실행 순서는 도구마다 다르다

여기서 가장 흔한 오해를 짚어야 한다. 「테스트는 위에서부터 차례로 돈다」는 생각이다. 그것은 도구에 따라 맞기도 하고 틀리기도 하다. 그래서 일반화하지 말고 쓰는 도구에서 직접 재야 한다. 아래는 이 환경에서 잰 값이다.

3.1 Python 3.13.3의 unittest에서 잰 값

python      : 3.13.3 / win32

    test_d_close_all
    test_b_query_uses_connection

    test_a_open_connection

classes defined in source : ZebraTests -> AlphaTests -> MikeTests

정의 순서가 아니라 이름순이다. 메서드도, 클래스도 마찬가지였다. 문서에도 「테스트 메서드 이름을 문자열의 기본 순서로 정렬해 실행 순서를 정한다」고 적혀 있다.

3.2 Node.js v22.16.0의 node:test에서 잰 값

이제 완전히 같은 논리를 다른 도구로 옮겨 적었다. 공유 상태도, 검사 내용도, 정의 순서도 그대로다.

// /tmp/order-demo/order_probe.test.mjs
import test from 'node:test';
import assert from 'node:assert';

const CONNECTIONS = new Map();

// 역시 d, b, a, c 순서로 정의
test('test_d_close_all',              () => { CONNECTIONS.clear();
                                              assert.strictEqual(CONNECTIONS.size, 0); });
test('test_b_query_uses_connection',  () => { assert.strictEqual(CONNECTIONS.get('main'), 'pg://demo'); });
test('test_a_open_connection',        () => { CONNECTIONS.set('main', 'pg://demo');
                                              assert.strictEqual(CONNECTIONS.size, 1); });
test('test_c_registry_has_one_entry', () => { assert.strictEqual(CONNECTIONS.size, 1); });

$ node --test order_probe.test.mjs

결과를 나란히 놓으면 이렇게 된다.

이 표가 이 글에서 두 번째로 중요한 것이다. 완전히 같은 논리의 테스트가 한쪽 도구에서는 전부 통과하고 다른 쪽에서는 실패했다. 코드는 같고 순서 정책만 달랐다.

일반화하지 말 것. 위 값은 이 도구, 이 버전, 이 환경에서 잰 것이다. 같은 도구라도 버전이 바뀌면 달라질 수 있고, 순서 관련 플러그인을 하나 깔면 그 즉시 달라진다. pytest 행은 설치되어 있지 않아 직접 돌려 보지 못했다. 문서를 근거로 적었을 뿐이니 그대로 믿지 말고 각자 환경에서 재기 바란다. 재는 방법은 간단하다. 정의 순서와 이름 순서가 어긋나게 테스트를 몇 개 만들어 놓고 실제로 어느 쪽으로 도는지 보면 된다.

4. 상태가 남는 다섯 자리

순서가 입력이 되려면 테스트 사이에 무언가가 살아남아야 한다. 그 자리를 다섯 가지로 나눠 각각 실행해 확인했다. 모든 실행은 새 프로세스에서 시작하고, fwd는 이름순, rev는 그 역순이다.

4.1 모듈 수준 전역 변수

case 1  module-level global       order=fwd
  run : a_open_connection -> b_query_uses_connection -> c_close_all
  ==> ALL PASS   (3/3 passed)

case 1  module-level global       order=rev
  run : c_close_all -> b_query_uses_connection -> a_open_connection
  ==> 1 FAILED   (2/3 passed)
      red: b_query_uses_connection
      KeyError: 'main'

가장 흔한 자리다. 모듈은 프로세스당 한 번만 임포트되므로 그 안의 변수는 테스트 전체 수명 동안 살아 있다. 파일을 나눠도 소용없다. 같은 모듈을 임포트하는 순간 같은 객체를 공유한다.

4.2 클래스 속성

class FeatureFlags:
    enabled = set()          # 클래스 속성: 모든 인스턴스가 이 하나를 공유한다

    def on(self, name):
        self.enabled.add(name)     # 인스턴스가 아니라 클래스의 집합을 바꾼다

case 2  class attribute           order=fwd
  run : a_enable_beta -> b_fresh_object_has_no_flags
  ==> 1 FAILED   (1/2 passed)
      red: b_fresh_object_has_no_flags
      AssertionError: Items in the first set but not the second: 'beta'

case 2  class attribute           order=rev
  run : b_fresh_object_has_no_flags -> a_enable_beta
  ==> ALL PASS   (2/2 passed)

여기서는 방향이 반대다. 기본 순서에서 터지고 역순에서 통과한다. self.enabled.add(...)가 인스턴스 속성을 만드는 것처럼 보이지만, 실제로는 클래스에 있는 집합을 찾아가 거기에 넣는다. 그래서 FeatureFlags()로 새로 만든 객체에도 이전 값이 들어 있다.

4.3 캐시와 메모이제이션

USERS = {}

@functools.lru_cache(maxsize=None)
def find_user(uid):
    return USERS.get(uid)

case 3  cache / memoization       order=fwd
  run : a_created_user_is_found -> b_lookup_again -> c_unknown_user_is_none
  ==> ALL PASS   (3/3 passed)

case 3  cache / memoization       order=rev
  run : c_unknown_user_is_none -> b_lookup_again -> a_created_user_is_found
  ==> 2 FAILED   (1/3 passed)
      red: b_lookup_again              AssertionError: None != 'kim'
      red: a_created_user_is_found     AssertionError: None != 'kim'

이 사례가 다섯 중 가장 고약하다. test_a_created_user_is_found의 코드를 다시 보자.

def test_a_created_user_is_found(self):
    USERS[7] = "kim"                          # 데이터를 올바르게 넣고
    self.assertEqual(find_user(7), "kim")     # 올바르게 조회한다  -> 그런데 실패

이 테스트에는 잘못이 하나도 없다. 그런데 역순에서는 빨강이 된다. 앞서 돈 test_b_lookup_again이 아직 데이터가 없을 때 find_user(7)을 호출했고, 그 결과인 None이 캐시에 박혔기 때문이다. 캐시는 「없음」이라는 답도 똑같이 기억한다.

  • 캐시가 붙은 함수는 사실상 전역 변수다. 다만 눈에 보이지 않는 곳에 있다
  • 설정 값을 픽스처에서 되돌려도 캐시를 비우지 않으면 옛 답이 그대로 나온다
  • 부정 결과(찾지 못함, 권한 없음, 비어 있음)의 캐싱이 특히 위험하다. 나중에 상황을 올바르게 만든 테스트가 대신 터진다
  • 애플리케이션 코드의 캐시만이 아니다. 임포트한 라이브러리 내부의 캐시, 컴파일된 정규식 캐시, 커넥션 풀도 같은 자리다

4.4 임시 파일과 디렉터리

case 4  temp file / directory residue  order=fwd
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty
      AssertionError: Lists differ: ['report.csv'] != []

case 4  temp file / directory residue  order=rev
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> ALL PASS   (2/2 passed)

여기까지는 앞의 사례들과 같다. 그런데 이 자리에는 다른 넷에 없는 성질이 하나 있다. 정리를 빼고 두 번 이어 돌려 보면 드러난다.

$ python -c "잔여물 제거"
residue cleared

--- run 1: 정리를 빼고 fwd 순서로 실행 ---
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

--- run 2: 완전히 새 프로세스, rev 순서 (조금 전엔 ALL PASS였다) ---
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

조금 전 ALL PASS였던 역순이 이번엔 빨강이다. 프로세스를 새로 띄웠는데도 그렇다. 파일 시스템에 남은 상태는 프로세스 경계를 넘는다. 즉 이 경우 「앞 테스트」의 자리에 지난번 실행 전체가 들어앉는다.

  • 그래서 이 유형은 「새로 받은 저장소에서는 되는데 내 작업 폴더에선 안 된다」로 나타난다
  • CI가 매번 깨끗한 컨테이너를 쓰면 CI에서만 통과하고 로컬에서 실패하는 반대 모양이 된다
  • 고정 경로를 쓰는 순간 병렬 실행에서도 서로를 밟는다
  • 데이터베이스, 캐시 서버, 메시지 큐도 같은 성질이다. 프로세스를 재시작해도 상태가 남는다

4.5 되돌리지 않은 몽키패치

def test_a_invoice_with_frozen_clock(self):
    clock.now = lambda: 1700000000.0      # 갈아 끼우고 되돌리지 않는다
    ...

case 5  monkeypatch that is never undone  order=fwd
  run : a_invoice_with_frozen_clock -> b_invoice_uses_real_clock
  ==> 1 FAILED   (1/2 passed)
      red: b_invoice_uses_real_clock
      AssertionError: 85445231.48900342 not less than 5.0 : clock is off by 85445231 seconds

case 5  monkeypatch that is never undone  order=rev
  run : b_invoice_uses_real_clock -> a_invoice_with_frozen_clock
  ==> ALL PASS   (2/2 passed)

오차가 8,544만 초, 약 2년 8개월이다. 시각을 고정하는 것 자체는 정당한 기법이다. 문제는 되돌리지 않은 것이다. 시각뿐 아니라 난수 시드, 환경 변수, 네트워크 호출 대체, 로깅 설정이 모두 같은 자리에 있다.

5. 원인 유형별 판별표

위 다섯 가지를 실무에서 바로 쓸 수 있게 정리했다. 이 글에서 하나만 가져간다면 이 표다.

유형어디에 남나전형적 증상확인법되돌리는 법
모듈 수준 전역임포트된 모듈 객체앞이 채운 값을 뒤가 읽어 통과테스트 앞뒤로 모듈 변수를 찍어 비교setUp에서 초기화 + 정리 함수 등록
클래스 속성클래스 객체 자체새로 만든 인스턴스에 이전 값이 있음인스턴스 속성인지 클래스 속성인지 확인가변 기본값을 생성자 안으로
캐시·메모이제이션함수에 붙은 캐시먼저 돈 쪽이 정답을 확정, 나머지가 틀림캐시 적중 통계를 출력setUp에서 캐시 비움
임시 파일·디렉터리파일 시스템새 프로세스에서도 재현됨실행 전후 디렉터리 목록 비교테스트마다 새 임시 디렉터리, 자동 삭제
몽키패치 미복원패치된 모듈 속성시각·난수·네트워크가 엉뚱한 값현재 속성을 원본과 비교패치 전에 복원을 먼저 등록

표를 쓸 때 방향 감각이 도움이 된다. 전역·캐시·몽키패치는 대체로 앞이 뒤를 오염시키고, 클래스 속성은 누적형이라 기본 순서에서 먼저 터지는 경우가 많으며, 임시 파일은 지난 실행이 이번 실행을 오염시킨다.

6. 누가 오염시켰나, 누가 터졌나

진단에서 가장 자주 하는 실수가 빨강이 뜬 테스트를 범인으로 보는 것이다. 눈으로 확인하려고 모든 테스트의 앞뒤에서 공유 상태를 찍었다.

order=fwd
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  b_query_uses_connection    state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  c_registry_has_one_entry   state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  d_close_all                state {'main': 'pg://demo'}  -> {}                     CHANGED
  red tests : (none)

order=rev
  d_close_all                state {}                     -> {}                       --
  c_registry_has_one_entry   state {}                     -> {}                       --
  b_query_uses_connection    state {}                     -> {}                       --
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  red tests : b_query_uses_connection, c_registry_has_one_entry
  who mutated shared state : a_open_connection, d_close_all

마지막 두 줄을 겹쳐 읽어야 한다. 빨강이 된 b와 c는 공유 상태를 한 글자도 바꾸지 않았다(-- 표시). 상태를 바꾼 a와 d는 둘 다 초록이다.

  • 실패 지점과 원인 지점이 완전히 갈린다. 그래서 실패 로그의 스택 트레이스는 범인을 가리키지 않는다
  • 역순에서 진짜 원인은 d_close_all이 맨 앞에서 딕셔너리를 비운 것이다. 그런데 d는 자기 단언을 통과했으므로 아무 신호도 남기지 않았다
  • 이 구조 때문에 피해자에 방어 코드를 넣는 대응이 나온다. 빨강은 사라지지만 오염원은 그대로 남는다
  • 고쳐야 할 곳은 상태를 바꾸고 되돌리지 않은 쪽이다

7. 이분 탐색으로 범인 좁히기

테스트가 네 개면 눈으로 본다. 수백 개면 못 본다. 그래서 절차가 필요하다. 피해자 앞에 두는 테스트 집합을 절반씩 줄이는 것이다.

실험용으로 17개짜리 예제를 만들었다. 대부분은 평범한 계산 검사이고, 그중 하나가 공유 설정을 조용히 바꾼다. 마지막 테스트는 세금을 포함한 합계를 검사한다.

CONFIG = {"tax_rate": 0.10, "currency": "KRW"}

    def test_09_tax_exempt_customer(self):
        # 범인: 면세 검사를 하려고 세율을 바꿔 놓고 되돌리지 않는다
        CONFIG["tax_rate"] = 0.0
        self.assertEqual(CONFIG["tax_rate"], 0.0)

    def test_zz_total_includes_tax(self):
        # 피해자: 혼자 두면 완벽히 옳다
        self.assertAlmostEqual(10000 * (1 + CONFIG["tax_rate"]), 11000.0)

이제 범인을 모른다고 치고 절차대로 좁힌다. 매 시도는 새 프로세스다.

suite size      : 17 tests (16 candidates + 1 victim)
victim          : zz_total_includes_tax

step 0 -- 양 끝을 먼저 고정한다
  trial 1   before=16 [01_amount_is_positive..16_due_date_offset]        -> RED
  trial 2   before=0  [nothing]                                          -> GREEN

step 1 -- 빨강을 유지하는 쪽으로 절반씩 자른다
  trial 3   before=8  [01_amount_is_positive..08_empty_cart_total]       -> GREEN
  trial 4   before=8  [09_tax_exempt_customer..16_due_date_offset]       -> RED
  trial 5   before=4  [09_tax_exempt_customer..12_zero_quantity_skipped] -> RED
  trial 6   before=2  [09_tax_exempt_customer..10_max_line_items]        -> RED
  trial 7   before=1  [09_tax_exempt_customer..09_tax_exempt_customer]   -> RED

minimal reproducing pair : 09_tax_exempt_customer  then  zz_total_includes_tax
subprocess runs used     : 7
brute force would need   : 16 (one run per candidate)

7회 만에 좁혀졌다. 하나씩 넣어 보는 전수 조사라면 16회다. 후보가 늘수록 격차는 벌어진다. 후보 1,000개면 전수 조사는 1,000회지만 이 절차는 스무 번 남짓이다.

  • 0단계를 건너뛰지 말 것. 「전체 앞부분 + 피해자 = 빨강」과 「피해자 혼자 = 초록」이 둘 다 성립해야 순서 의존이다. 피해자가 혼자서도 빨강이면 그냥 깨진 테스트다
  • 매 시도를 새 프로세스로. 같은 프로세스에서 이어 돌리면 시도끼리 오염되어 판정이 뒤집힌다
  • 앞뒤 어느 절반도 빨강이 아니면 범인이 둘 이상이다. 두 테스트가 합쳐져야 조건이 만들어지는 경우다. 이때는 절반씩 빼면서 좁힌다
  • 찾은 최소 재현 쌍은 그대로 회귀 테스트로 남긴다. 이 두 개를 이 순서로 돌리는 전용 테스트를 만들어 두면 같은 사고가 다시 못 들어온다
  • 고치는 곳은 범인 쪽이다. 피해자에 방어 코드를 넣는 것은 응급 처치다

8. 격리 실행이 만드는 착시

「내 컴퓨터에선 되는데」의 구조를 그대로 재현해 보자. 방금 그 17개 예제에서 피해자만 따로 돌린다.

zz_total_includes_tax  단독 실행        GREEN
전체 17개 (이름순)                     RED

이것이 전부다. 개발자가 실패 로그를 보고 그 테스트 이름을 복사해 로컬에서 돌리면 반드시 초록이 뜬다. 그래서 「환경 탓」이라는 결론으로 새고, 재실행 버튼으로 넘어간다.

그런데 앞의 네 개짜리 예제로 같은 걸 해 보면 결과가 다르다.

a_open_connection                PASS
b_query_uses_connection          FAIL
c_registry_has_one_entry         FAIL
d_close_all                      PASS

여기서는 b와 c가 혼자서도 실패했다. 이 차이가 진단에서 아주 중요하다. 순서 의존에는 두 종류가 있다.

구분단독 실행전체 실행성격발견 난이도
선행 의존형실패순서에 따라 통과애초에 자립적인 테스트가 아니다. 앞 테스트를 준비 단계로 쓰고 있다낮음. 단독으로 돌려 보면 바로 드러난다
오염 피해형통과순서에 따라 실패테스트 자체는 옳다. 앞선 테스트가 남긴 상태를 밟았을 뿐이다높음. 「내 컴퓨터에선 된다」가 여기서 나온다

실무에서 시간을 잡아먹는 것은 아래쪽이다. 단독 실행이 통과하는 것은 무사하다는 증거가 아니라 오히려 오염 피해형이라는 증상이다. 그래서 격리 실행은 진단의 시작점일 뿐 결론이 될 수 없다.

9. 무작위 순서와 고정 시드

순서가 입력이라면 답은 분명하다. 입력을 여러 개 넣어 보는 것이다. 다만 무작위를 그냥 켜면 안 된다. 재현할 수 없는 빨강은 진단할 수 없기 때문이다. 시드를 고정하면 무작위와 재현을 동시에 얻는다.

seeds tried : 1..40   (order = random.Random(seed).shuffle)
green seeds : 10  -> [1, 3, 9, 11, 12, 13, 17, 26, 27, 33]
red   seeds : 30  -> [2, 4, 5, 6, 7, 8, 10, 14, 15, 16, 18, 19] ...

40개 시드 중 30개가 빨강이었다. 이제 하나를 골라 고정한다. 이 글에서 쓴 고정 시드는 20260731이다. 같은 시드를 넣으면 누구나 같은 순서를 얻는다.

$ python ci_shuffle.py 20260731
==============================================================
TEST ORDER SEED : 20260731      replay with: ci_shuffle.py 20260731
==============================================================
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

$ python ci_shuffle.py 20260731          # 같은 시드로 다시
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

두 번의 실행이 순서도 결과도 완전히 같다. 이것이 무작위 순서를 실무에 쓸 수 있게 만드는 유일한 조건이다.

  • 실패 로그의 맨 앞에 시드와 재실행 명령을 함께 찍는다. 로그를 받은 사람이 그 줄만 복사해 그대로 재현할 수 있어야 한다
  • 시드는 실행 시각이 아니라 난수로 뽑는다. 시각 기반은 같은 분에 돌린 두 실행이 같은 순서가 되어 탐색 범위를 좁힌다
  • Python 표준 라이브러리만으로 충분하다. 이름 목록을 받아 시드 고정 셔플을 하고 그 순서로 스위트를 조립하면 된다
  • pytest 생태계에는 순서를 섞는 플러그인이 있고, 등록을 끄는 옵션도 함께 제공된다. 다만 이 환경에는 pytest가 없어 직접 확인하지 못했다

10. 되돌리는 규칙 - 픽스처 설계

이제 고치는 쪽이다. 앞의 네 개짜리 테스트를 단언은 그대로 두고 픽스처만 바꿨다.

class SessionTestsFixed(unittest.TestCase):
    def setUp(self):
        # 1. 물려받은 상태를 쓰지 않고, 알고 있는 상태로 도착한다
        store.CONNECTIONS.clear()
        # 2. 되돌리기를 먼저 등록한다. 테스트가 중간에 터져도 실행된다
        self.addCleanup(store.CONNECTIONS.clear)

    def given_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"      # 필요한 전제는 자기가 만든다

    def test_b_query_uses_connection(self):
        self.given_open_connection()
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_c_registry_has_one_entry(self):
        self.given_open_connection()
        self.assertEqual(len(store.CONNECTIONS), 1)

바뀐 것은 두 가지뿐이다. 도착 시점에 상태를 초기화하고, 필요한 전제를 스스로 만든다. 결과를 보자.

fixed suite, all 24 permutations, ALL IN ONE PROCESS
  green : 24
  red   : 0  []
  pass rate : 24/24 = 100%

also run each test alone:
  a                          PASS
  b                          PASS
  c                          PASS
  d                          PASS

4/24에서 24/24가 됐다. 단독 실행도 전부 통과한다. 다섯 가지 원인 유형에도 같은 방식을 적용해 확인했다.

case 1 fixed  global: reset in setUp, undo with addCleanup          order=fwd  ==> ALL PASS
case 1 fixed  global: reset in setUp, undo with addCleanup          order=rev  ==> ALL PASS
case 2 fixed  class attr: move the mutable default into __init__    order=fwd  ==> ALL PASS
case 2 fixed  class attr: move the mutable default into __init__    order=rev  ==> ALL PASS
case 3 fixed  cache: clear it in setUp, same as any other global    order=fwd  ==> ALL PASS
case 3 fixed  cache: clear it in setUp, same as any other global    order=rev  ==> ALL PASS
case 4 fixed  temp files: a per-test directory that cleans itself   order=fwd  ==> ALL PASS
case 4 fixed  temp files: a per-test directory that cleans itself   order=rev  ==> ALL PASS
case 5 fixed  monkeypatch: register the restore before you patch    order=fwd  ==> ALL PASS
case 5 fixed  monkeypatch: register the restore before you patch    order=rev  ==> ALL PASS

10.1 여덟 가지 규칙

  • arrange를 남에게 맡기지 않는다. 필요한 전제는 그 테스트가 직접 만든다. 이것 하나가 순서 의존의 대부분을 없앤다
  • setUp은 「알고 있는 상태로 도착」시키는 것이지 물려받은 상태를 확인하는 곳이 아니다
  • 되돌리기는 패치보다 먼저 등록한다. 테스트 본문이 중간에 예외로 끊겨도 복원이 돌아야 한다
  • 정리 함수는 나중에 등록한 것이 먼저 실행된다. 자원을 얻은 역순으로 반납되므로 의존 관계가 자연스럽게 지켜진다
  • 정리를 테스트 본문 끝에 두지 않는다. 단언이 실패하면 그 줄까지 가지 못한다. 이것이 「하나가 깨지자 열 개가 연달아 깨졌다」의 정체다
  • 캐시도 전역이다. 설정을 되돌렸으면 캐시도 비운다
  • 임시 파일은 테스트마다 새로 만들고 스스로 지워지게 한다. 고정 경로를 공유하지 않는다
  • 클래스 단위 픽스처는 기본값이 아니다. 속도 때문에 어쩔 수 없을 때만, 그리고 읽기 전용으로 쓴다

10.2 공유해도 되는 것과 안 되는 것

공유해도 되는 것공유하면 안 되는 것
불변 상수, 동결된 설정 값딕셔너리·리스트·집합 등 가변 컨테이너
순수 함수캐시가 붙은 함수
읽기 전용 픽스처 데이터쓰기가 일어나는 데이터베이스·파일
테스트마다 새로 만드는 임시 디렉터리고정 경로의 작업 디렉터리
테스트 클래스 안의 헬퍼 메서드클래스 속성으로 둔 가변 기본값
미리 계산해 둔 값의 복사본그 값 자체에 대한 참조

판정 기준은 하나로 줄일 수 있다. 테스트가 그것에 쓰기를 하는가. 쓴다면 공유하지 않는다. 읽기만 한다면 공유해도 되지만, 그 「읽기만」이 정말 읽기만인지는 확인해야 한다. 리스트를 정렬하는 것도, 딕셔너리를 조회하며 기본값을 채워 넣는 것도 쓰기다.

11. CI에 무엇을 붙일까

지금까지의 실행을 파이프라인으로 옮기면 이렇게 된다.

  • 본선은 고정 순서로 둔다. 매 커밋마다 순서가 흔들리면 빨강의 원인이 코드인지 순서인지 구분할 수 없다
  • 무작위 순서는 별도 작업으로 분리하고 시드를 출력한다. 이 작업이 빨강이면 「순서 의존이 있다」는 뜻이고, 본선이 빨강이면 「코드가 틀렸다」는 뜻이다. 신호가 섞이지 않는다
  • 야간 작업에 역순 실행을 한 번 넣는다. 무작위보다 값싸고, 이 글에서 본 것처럼 탐지력이 상당하다. 결정론적이라 재현도 자동이다
  • 새로 찾은 최소 재현 쌍은 전용 테스트로 고정한다. 그 두 개를 그 순서로 돌리는 테스트를 남기면 같은 사고가 다시 들어오지 못한다
  • 실행 후 임시 디렉터리 잔여물을 검사하는 단계를 넣는다. 4.4의 유형은 이것 하나로 대부분 잡힌다
  • 병렬 실행을 켜기 전에 순서 의존부터 없앤다. 병렬은 순서를 더 흔들 뿐 아니라 동시 접근까지 더한다. 순서 문제를 안고 병렬로 가면 원인이 두 겹이 된다

도입 순서 제안. 순서 무작위화를 갑자기 켜면 빨강이 무더기로 쏟아져 팀이 그 작업을 꺼 버리는 결말이 흔하다. 역순 실행 한 번부터 시작하기를 권한다. 결정론적이라 재현이 쉽고, 나온 빨강을 하나씩 최소 재현 쌍으로 좁혀 고치면 된다. 그것이 다 정리된 뒤에 무작위를 켠다.

12. 점검 목록

  • 새로 추가한 테스트를 단독으로 돌려 봤다
  • 순서를 뒤집어 한 번 돌려 봤다
  • 무작위 순서를 시드를 고정해 최소 한 번 돌렸다
  • 실행 후 임시 디렉터리에 남은 파일이 없다
  • 몽키패치마다 복원이 등록되어 있다
  • 캐시를 쓰는 코드의 픽스처에 캐시 비우기가 들어 있다
  • 클래스 속성에 가변 기본값이 없다
  • 테스트가 다른 테스트의 이름이나 순번을 전제하지 않는다
  • 정리 코드가 본문 끝이 아니라 픽스처에 있다
  • CI 로그에 순서 시드가 찍힌다

12.1 하지 말 것

  • 실패한 테스트에 방어 코드부터 넣는 것 - 피해자를 고치고 범인을 놓친다
  • 테스트 이름에 번호를 붙여 순서를 고정하는 것 - 의존을 없애는 게 아니라 숨기는 것이다. 게다가 도구가 이름순으로 돌지 않으면 그마저도 안 통한다
  • 빨강을 재실행으로 넘기는 것 - 순서가 바뀌어 우연히 초록이 된 것뿐이다
  • 무작위 순서를 시드 없이 켜는 것 - 재현이 안 되면 진단도 못 한다
  • 「내 컴퓨터에선 되는데」에서 멈추는 것 - 8절에서 봤듯 단독 통과는 증거가 아니라 증상이다
  • 속도를 이유로 공유 픽스처를 기본으로 삼는 것 - 느린 테스트보다 못 믿을 테스트가 비싸다
  • 순서 의존을 안고 병렬 실행을 켜는 것

13. 정리

이 글에서 실행으로 확인한 것을 다시 모으면 이렇다.

  • 공유 상태를 쓰는 테스트 4개의 24가지 순열 중 초록은 4개였다. 통과율 17퍼센트인데 도구의 기본 순서가 그 4개 중 하나였다
  • 기본 실행 순서는 도구마다 다르다. 측정한 unittest는 이름순, node:test는 정의 순서였다. 같은 논리의 테스트가 한쪽에서 전부 통과하고 다른 쪽에서 실패했다
  • 상태가 남는 자리는 다섯이고, 임시 파일만은 프로세스 경계를 넘는다
  • 빨강이 된 테스트는 공유 상태를 한 글자도 바꾸지 않았다. 범인은 초록이었다
  • 후보 16개에서 7회 만에 최소 재현 쌍으로 좁혀졌다
  • 피해자를 단독으로 돌리면 통과했다. 그것이 「내 컴퓨터에선 되는데」의 정체다
  • 시드 20260731을 고정하니 순서와 실패가 완전히 재현됐다
  • 단언을 그대로 두고 픽스처만 고쳤더니 24/24가 통과했다

결론은 처음에 세운 논지 그대로다. 순서 의존은 「격리를 안 해서」 생기는 도덕적 결함이 아니라, 검증되지 않은 입력이 하나 더 있다는 사실이다. 그 입력의 이름이 순서다.

그래서 마지막 질문이 바뀐다. 「이 테스트가 통과하나」가 아니라 「어떤 순서에서 통과하나」다. 뒤집어 한 번 돌려 보는 데는 몇 초면 충분하고, 그 몇 초가 월요일 아침의 빨강을 지금 여기로 옮겨 온다.

# 테스트 순서 의존 점검표

테스트 사이에 남는 상태가 있으면 **순서가 곧 입력**이다.
그러면 통과는 「맞다」가 아니라 「이 순서에서는 맞다」가 된다.

---

## 0. 30초 판정

| 물음 | 예 | 아니오 |
|---|---|---|
| 그 테스트 하나만 돌리면 통과하나? | **순서 의존 확정** (아래 1절) | 자체 결함 또는 선행 의존 |
| 순서를 뒤집으면 다른 테스트가 터지나? | **순서 의존 확정** | 다른 원인 |
| 실패한 테스트가 공유 상태를 바꾸나? | 그 테스트도 용의자 | **범인은 앞쪽에 있다** |
| 프로세스를 새로 띄워도 재현되나? | 파일·DB 등 **프로세스 밖 상태** | 프로세스 안 메모리 상태 |

핵심: **실패한 테스트는 대개 범인이 아니라 피해자다.**

---

## 1. 원인 유형별 판별표

| 유형 | 어디에 남나 | 전형적 증상 | 확인법 | 되돌리는 법 |
|---|---|---|---|---|
| 모듈 수준 전역 변수 | 임포트된 모듈 객체 | 앞 테스트가 채운 값을 뒤가 읽어 통과 | 테스트 앞뒤로 모듈 변수 찍어 비교 | setUp에서 초기화 + addCleanup으로 복원 |
| 클래스 속성 | 클래스 객체 자체 | 새로 만든 인스턴스에 이전 값이 들어 있음 | 인스턴스 속성인지 클래스 속성인지 확인 | 가변 기본값을 생성자 안으로 옮김 |
| 캐시·메모이제이션 | 함수에 붙은 캐시 | **먼저 돈 테스트가 정답을 확정**, 나머지가 틀림 | 캐시 통계·적중률 출력 | setUp에서 캐시 비움, 캐시도 전역으로 취급 |
| 임시 파일·디렉터리 | 파일 시스템 | **프로세스를 새로 띄워도 재현**됨 | 실행 전후 디렉터리 목록 비교 | 테스트마다 임시 디렉터리 생성, 자동 삭제 |
| 몽키패치 미복원 | 패치된 모듈 속성 | 시각·난수·네트워크가 엉뚱한 값 | 패치 대상 원본과 현재 값 비교 | **패치 전에 복원을 먼저 등록** |

### 유형별 방향 감각

- 전역·캐시·몽키패치: 보통 **앞이 뒤를 오염**시킨다
- 클래스 속성: **기본 순서에서 먼저 터지는** 경우가 많다 (누적형)
- 임시 파일: **지난 실행이 이번 실행을 오염**시킨다 (프로세스 경계를 넘는다)
- 캐시에 **없음(negative)** 결과가 저장되면, 나중에 데이터를 올바로 넣은 테스트가 대신 터진다

---

## 2. 최소 재현 쌍 찾기

목표: 「A 다음에 B면 깨진다」의 A를 찾는다.

### 절차

1. **양 끝을 먼저 고정한다**
   - 전체 앞부분 + 피해자 = 빨강인지 확인
   - 피해자 혼자 = 초록인지 확인
   - 둘 다 성립해야 순서 의존이다
2. **앞부분을 절반으로 자른다**
   - 앞 절반 + 피해자를 돌린다
   - 빨강이면 앞 절반을 채택, 초록이면 뒤 절반을 채택
3. **하나가 남을 때까지 2를 반복한다**
4. 남은 하나가 **범인**, 그 하나와 피해자가 **최소 재현 쌍**이다

### 규칙

- **매 시도를 새 프로세스로** 돌린다. 안 그러면 시도끼리 오염된다
- 앞뒤 어느 절반도 빨강이 아니면 **범인이 둘 이상**이다. 이때는 절반씩 빼면서 좁힌다
- 후보 N개면 대략 **2 곱하기 log2(N) 회** 안에 끝난다. 후보 16개면 7회 안팎, 전수 조사는 16회

### 찾은 뒤

- 최소 재현 쌍을 **그대로 회귀 테스트로 남긴다**
- 범인 쪽을 고친다. 피해자에 방어 코드를 넣는 것은 응급 처치일 뿐이다

---

## 3. 픽스처 규칙

1. **arrange를 남에게 맡기지 않는다.** 필요한 전제는 그 테스트가 직접 만든다
2. **setUp은 「알고 있는 상태로 도착」시킨다.** 물려받은 상태를 그대로 쓰지 않는다
3. **되돌리기는 패치보다 먼저 등록한다.** 테스트가 중간에 터져도 복원이 돌아야 한다
4. **정리 함수는 나중에 등록한 것이 먼저 실행된다.** 자원을 얻은 역순으로 반납된다
5. **클래스 단위 픽스처는 기본값이 아니다.** 느려서 어쩔 수 없을 때만, 읽기 전용으로
6. **캐시도 전역이다.** 설정을 되돌렸으면 캐시도 비운다
7. **임시 파일은 테스트마다 새로, 스스로 지워지게.** 고정된 경로를 공유하지 않는다
8. **정리를 테스트 본문 끝에 두지 않는다.** 실패하면 그 줄까지 못 간다

---

## 4. 공유해도 되는 것 / 안 되는 것

| 공유해도 되는 것 | 공유하면 안 되는 것 |
|---|---|
| 불변 상수, 동결된 설정 값 | 딕셔너리·리스트·집합 등 **가변** 컨테이너 |
| 순수 함수 | 캐시가 붙은 함수 |
| 읽기 전용 픽스처 데이터 | 쓰기가 일어나는 데이터베이스·파일 |
| 테스트마다 새로 만드는 임시 디렉터리 | 고정 경로의 작업 디렉터리 |
| 클래스 안의 헬퍼 메서드 | 클래스 속성으로 둔 가변 기본값 |
| 미리 계산해 둔 값의 **복사본** | 그 값 **자체**에 대한 참조 |

판정 기준 하나: **테스트가 그것에 쓰기를 하는가.** 하면 공유 금지다.

---

## 5. CI 설정

- 순서를 **무작위로 섞되, 시드를 출력**한다. 시드가 없으면 빨강을 재현할 수 없다
- 실패 로그 맨 앞에 **시드와 재실행 명령**을 같이 찍는다
- 야간 작업(nightly)에 **역순 실행**을 한 번 넣는다. 가장 싸고 확실한 탐지법이다
- 기본 파이프라인은 **고정 순서**로 두고, 무작위는 별도 작업으로 분리한다. 그래야 빨강의 원인이 코드인지 순서인지 바로 갈린다
- 새로 발견한 최소 재현 쌍은 **전용 테스트로 고정**한다
- 병렬 실행을 켜기 전에 순서 의존부터 없앤다. 병렬은 순서를 더 흔든다

---

## 6. 점검 목록

- [ ] 새로 추가한 테스트를 **단독으로** 돌려 봤다
- [ ] 순서를 **뒤집어** 한 번 돌려 봤다
- [ ] 무작위 순서를 **시드 고정으로** 최소 한 번 돌렸다
- [ ] 실행 후 임시 디렉터리에 **남은 파일이 없다**
- [ ] 몽키패치마다 **복원이 등록**되어 있다
- [ ] 캐시를 쓰는 코드에 **캐시 비우기**가 픽스처에 들어 있다
- [ ] 클래스 속성에 **가변 기본값**이 없다
- [ ] 테스트가 **다른 테스트의 이름·순번**을 전제하지 않는다
- [ ] 정리 코드가 **본문 끝이 아니라 픽스처**에 있다
- [ ] CI 로그에 **순서 시드**가 찍힌다

---

## 7. 하지 말 것

- 실패한 테스트에 **방어 코드부터 넣는 것** — 피해자를 고치고 범인을 놓친다
- 순서 의존을 **테스트 이름에 번호를 붙여** 고정하는 것 — 의존을 숨길 뿐이다
- 빨강을 **재실행으로 넘기는 것** — 순서가 바뀌어 우연히 초록이 된 것뿐이다
- 무작위 순서를 **시드 없이** 켜는 것 — 재현이 안 되면 진단도 못 한다
- 「내 컴퓨터에선 되는데」에서 **멈추는 것** — 단독 실행이 통과하는 것은 증거가 아니라 증상이다
- 공유 픽스처를 **속도 때문에** 기본으로 삼는 것 — 느린 테스트보다 못 믿을 테스트가 비싸다
- 순서 의존을 고치지 않은 채 **병렬 실행을 켜는 것**
