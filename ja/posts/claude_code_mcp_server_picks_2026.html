何を得て何を差し出すのか - トランスポート・スコープ・権限・信頼・コンテキスト費用で決める選び方

2026-08-06 IT・技術

序論: おすすめリストは半年で腐る

Claude CodeにMCPサーバーを一つ接続するのにかかる時間はコマンド一行だ。難しいのは接続する作業ではなく、選ぶ作業のほうである。

MCPサーバーのおすすめリストはすでに溢れている。用途別のまとめ記事、awesomeリスト、公式ディレクトリまで揃っている。ところがリストには賞味期限がついている。初期のリファレンスサーバーのかなりの部分はすでに別のアーカイブ用リポジトリへ移され、かつて標準的な例のように紹介されていた @modelcontextprotocol/server-github パッケージもその一つだ。半年前のリストをそのままなぞると、保守の止まったコードを自分の開発環境に植えることになる。

リストより長持ちするのは基準だ。そしてMCPで基準がとりわけ重要になる理由がもう一つある。MCPサーバーを接続するとは、便利機能を有効にすることではなくアクセス権限を差し出すことだからだ。ファイルシステムのサーバーはディスクを、データベースのサーバーはデータを、課題管理のサーバーは社内チケットの全文をエージェントの射程内に引き込む。選び方を誤ったサーバーは遅いのではなく危険なのである。

そこでこの記事はリストの代わりに判断軸を6つ立てる。①そもそも接続する理由があるのか、②どのトランスポートで接続するのか、③どのスコープに書くのか、④そのサーバーは何を差し出させるのか、⑤そのサーバーを信じる根拠はあるのか、⑥接続したときコンテキストをどれだけ消費するのか。軸ごとに選択肢が何で、どちらがどんな代償を払うのかを整理する。特定のサーバーに安全の判を押す記事ではなく、読者が自分のサーバーを自分で判定できるようにする記事だ。

1. 接続する理由があるかをまず分ける - コピペ回数という単純な合図

1.1 接続するとき

公式ドキュメントが示す合図は意外なほど素朴だ。ほかのツールの内容をセッションの窓にコピーして貼り付けている自分に気づいたときが接続するときである。課題管理のチケット本文、監視ダッシュボードのスタックトレース、クエリ結果の表——こうしたものを繰り返し運んでいるなら、そのシステムが候補になる。接続すればエージェントは貼り付けを待つ代わりに自分で読んで動く。

1.2 接続すべきでないとき

裏返すと判定はもっと明確になる。コピペしないシステムは接続する理由がない。

  • 月に一、二度しか開かないシステム: 設定・認証・維持の費用が利得を超える
  • すでに使っているCLIで同じことができるシステム: シェルで済む作業をわざわざプロトコルで包む理由は弱い
  • 毎回同じ内容を運んでいる場合: それはサーバーではなくプロジェクト文書に固定すべきものだ
  • 読み取りだけでよいのにサーバーが書き込みツールまで携えてくる場合: 不要な権限が付いてくる
  • 新しい認証情報が必要なのに、その範囲を狭める手段がない場合

1.3 候補をふるいにかける5つの文

  • この2週間でそのシステムからセッションへ移した内容は5回以上あるか
  • 移した内容は毎回違っていたか
  • エージェントはそのシステムへ書き込む必要があるのか、読み取りで足りるのか
  • そのサーバーが要求する認証情報を読み取り専用に狭められるか
  • 接続と切り離しの費用は低いか——低いなら、いったん接続して観察して決めてもよい

2. MCPが実際に標準化したもの - 仕様を知らないと選べない

2.1 プロトコルの座標

MCPはAIアプリケーションを外部システムへつなぐ開放型の標準であり、しばしばAIアプリケーションのためのUSB-Cポートに喩えられる。サーバー側が自分にできることを標準の形で公開すれば、その形を理解するクライアントなら専用の連携コードなしに接続して使える。Claude Codeも、ほかの複数のエディタやエージェントも同じサーバーを共有する。この互換性が以下のすべての選択の前提になる。今日選んだサーバーが特定のツールに縛られないという意味だからだ。

2.2 バージョン表記の読み方

MCPの仕様は YYYY-MM-DD 形式の日付文字列でバージョンを付けるが、この日付には特定の意味がある。最後に後方互換を壊す変更があった日を指すのだ。後方互換が保たれる改善ではバージョンは上がらない。現在の仕様バージョンは 2026-07-28 である。サーバーの文書に書かれた対応バージョンがこれよりずっと古い日付で止まっているなら、それはそのサーバーがそれ以降の互換性破壊に追随していないという合図として読める。

2.3 バージョン交渉が入ってから変わった点

リクエストごとに _meta フィールドの io.modelcontextprotocol/protocolVersion キーで使用バージョンを宣言し、サーバーがリクエスト単位で受理または拒否する。Streamable HTTPでは同じ値が MCP-Protocol-Version ヘッダーにも載る。サーバーが対応していないバージョンなら、対応リストを含むエラーが返るのでクライアントは再試行できる。先に確かめたい場合は server/discover の呼び出し一回で対応バージョン・機能・識別情報をまとめて受け取れる。実務上重要なのは、旧来の初期化ベースの版(2025-11-25 以前)を使うサーバーとの互換経路が仕様に明記されている点だ。古いサーバーがすぐ使えなくなるわけではないが、保守の止まったサーバーほどこの境界で先に問題を出す。

3. 4つのトランスポートのどれで接続するか

3.1 分かれ道は一つしかない

トランスポートの選択は結局、サーバーのコードが自分の機械で動くのか、他人のところで動くのかに行き着く。この違いが信頼モデル全体を書き換える。ローカルのプロセスとして動くサーバーは自分のアカウント権限をそのまま使い、リモートのサーバーは自分の認証情報が他人のインフラを経由する。

トランスポート実行場所認証選ぶ理由注意点
stdio自分の機械のローカルプロセス環境変数・設定ファイルファイル・ローカルツール・自作スクリプト自分のアカウント権限で動く。パッケージの出所が実行権限そのもの
HTTP(streamable-http)リモートのサービスOAuth 2.0 またはヘッダートークンクラウドSaaS連携の既定値。最も広く対応されている設定JSONで type を落とすとstdioと解釈されて失敗する
SSEリモートのサービスOAuth またはヘッダーまだSSEしか公開していないサービスに限る非推奨のトランスポート。HTTPがあるならHTTPで
WebSocketリモートのサービスヘッダーのみサーバーが先にイベントを押し込む構造OAuthが使えず、一覧コマンドにも現れない

3.2 実際の登録コマンド

リモートのHTTPサーバーは名前とアドレスがあればよい。

claude mcp add --transport http <名前> <アドレス>

ローカルのstdioサーバーは -- の後ろに実行コマンドを付ける。この二重ダッシュが重要だ。後続の引数をクライアントが自分のオプションとして解釈せず、サーバーへそのまま渡すための区切り記号である。

claude mcp add --transport stdio <名前> -- npx -y <パッケージ>

登録後の状態確認は claude mcp list、詳細は claude mcp get <名前>、削除は claude mcp remove <名前> だ。セッションの中では /mcp パネルが接続状態・ツール数・認証の要否を一画面で見せる。登録コマンドは認証情報を検証しないため、値が間違っていても登録は成功し、接続の段階で失敗する。登録の成功を接続の成功と取り違えないことが最初の実務的な落とし穴だ。

4. スコープ3つ - どこに書くかが誰がその権限を持つかを決める

4.1 3つのスコープの実際の違い

スコープ開く範囲チーム共有向く用途危険な点
local(既定値)登録したプロジェクトで自分だけされない個人の実験、認証情報を伴うサーバーチームは自分の環境でだけ動く理由が分からない
projectそのプロジェクトの全員バージョン管理で共有チーム共通のツール、再現可能な開発環境自分が与えた権限をチーム全員が持つ
user自分のすべてのプロジェクトされないどこでも使う個人ユーティリティ無関係なプロジェクトでもそのサーバーが常に生きている

4.2 projectスコープが隠している判断

projectスコープはリポジトリ直下の .mcp.json に保存され、リポジトリと一緒に配られる。利点は明らかだ。クローンした人が同じツールを自動的に得る。ところが同じ文を権限の側へ裏返すとこう読める。自分が選んだサーバーがチーム全員の機械で動くことになる。だからプロジェクトスコープのサーバーは初回利用時に承認を通すよう設計されており、承認の選択を戻す専用のコマンドも用意されている。クローンしたリポジトリが自分自身のサーバーを勝手に承認できないよう塞がれているのも同じ理由だ。

4.3 優先順位と、結合されないこと

同じ名前のサーバーが複数の場所に定義されていると、一つだけが生き残る。順序はlocal → project → user → プラグイン提供のサーバー → コネクターだ。見落としやすいのは後半の規則である。フィールドは結合されない。優先順位の高いほうの定義が丸ごと使われる。userスコープにヘッダーを置き、projectスコープでアドレスだけ上書きするという期待は外れる。なお3つのスコープは名前で重複を判定するが、プラグインとコネクターはエンドポイントで判定する。

4.4 認証情報をリポジトリに入れない方法

共有用の .mcp.json には環境変数の展開を使う。${VAR} は変数の値に、${VAR:-既定値} は変数がないとき既定値に展開される。展開が効くのは command、args、env、リモートサーバーの url と headers だ。変数が空で既定値もない場合、設定が丸ごと壊れる代わりに警告とともに原文のまま残る。静かに誤った値で接続する事態を避けるには既定値を明示するほうがよい。

{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": { "Authorization": "Bearer ${API_KEY}" }
    }
  }
}

5.2 ブラウザ系は別の問題だ

ブラウザ制御の行はこの表で最も特異な枡だ。ほかのサーバーは特定のシステム一つを開くが、ブラウザはその中でログイン済みのすべてのサービスを一緒に開く。ブラウザのベンダーが自らMCPサーバーを出しながら、ローカル専用の実行や個人情報アクセスの遮断といった設計を入れ始めたのもこの特殊性ゆえだ。この系統を一つ深く見たい場合は、Safari MCPサーバーの分析記事にベンダーごとの設計差と信頼境界の論点が別途整理されている。

5.3 データベースの枡にある公式の勧告

公式ドキュメントが例の中で正面から勧めている箇所が一つある。データベースのサーバーを接続するとき、接続文字列に読み取り専用アカウントを使えというものだ。理由も明快で、エージェントが実行するクエリがデータを変えられないようにするためである。この一行がこの記事全体の原則を圧縮している。サーバーの選択は信じられるかを問う問題ではなく、信頼が崩れても被害が限定されるようにする問題なのだ。

6. そのサーバーを信じる根拠 - 品質判断の合図8つ

6.1 ディレクトリにあるという事実が意味すること、しないこと

ここは誤解が多いので正確に押さえる必要がある。Anthropicは自社ディレクトリにコネクターを載せる前に掲載基準に沿って審査するが、いかなるMCPサーバーもセキュリティ監査したり管理したりはしないと文書に明記している。つまりディレクトリ掲載は最低限の形式審査を通ったという合図であって、安全認証ではない。公式レジストリもメタデータとインストールコマンドを保管するメタレジストリであり、実際のコードはnpmやPyPIといったパッケージレジストリにそのまま残る。名前空間の所有権は検証するが、アクセス制御や監査証跡といったガバナンスは提供しない。

6.2 実際に見るべき合図

合図確認方法悪い兆候
提供元の一致サービス運営会社が自ら出したサーバーか第三者製の非公式ラッパーなのに公式に見える名付け
保守の活力直近のコミットやリリース、課題への応答数か月の停止、アーカイブ用リポジトリへの移管
仕様への追随対応する仕様バージョンの表記ずっと古い日付で止まっている
権限の明細必要な範囲やトークンの権限を文書化しているか全権限のトークンを要求し理由の説明がない
ツールの表面積ツールの数と破壊的ツールの有無読み取りだけと言いながら削除や送信のツールが付いてくる
ツール説明の品質説明が人が読むための文になっているか説明の中にモデルへ向けた指示文が混じっている

6.3 stdioサーバーにもう一枚見るべきこと

リモートのサーバーは他人のインフラで動くが、stdioのサーバーは自分の機械で自分のアカウント権限で動く。だからstdioサーバーを選ぶときはソフトウェアサプライチェーンの観点がもう一つ加わる。どのパッケージマネージャーで取得するのか、バージョンを固定できるのか、そのパッケージが導入時に何を実行するのかが、すべて判断材料になる。常に最新版を引く実行方式は楽だが、上流が変わった瞬間に自分の機械で動くコードも静かに変わるという意味だ。

7. プロンプトインジェクションとツールポイズニング - この道具に固有の危険

7.1 2つの危険は防御地点が違う

MCPサーバーが抱える危険は二層に分かれる。混ぜて理解すると対応が的を外す。

  • プロンプトインジェクション: サーバーが取得したデータの中に指示文が潜んでいる。外部の人が書いた課題本文、クロールしたページ、利用者が提出したログが通り道になる。防御地点はデータを疑うこと。
  • ツールポイズニング: ツール定義そのものが汚染されている。ツール説明のメタデータに悪意ある指示が入るとモデルはその文を読むが、利用者の画面にはツール名程度しか見えない。防御地点はサーバーを疑うこと。

後者がとりわけ厄介なのは、まさに見えないという点だ。利用者に描画されない文字列がモデルの入力にはそのまま入る。クライアント側の脆弱性分類でこの類型が最も多く影響も大きいと指摘されているのもそのためである。

7.2 クライアントが代わりに防ぐ部分

Claude Code側に掛かっている緩和策は次のとおりだ。これがあるから安心という根拠にはならないが、何がすでに塞がれているかを知っておくと二重投資を避けられる。

  • 既定が読み取り専用の権限で、機微な操作は明示的な承認を通す
  • 新しいMCPサーバーと初めて開くリポジトリは信頼確認の手順を踏む(非対話の -p 実行ではこの確認が働かない)
  • ウェブから内容を取得するシェルコマンドは自動承認の対象ではない
  • ウェブ取得は別のコンテキスト窓を使い、悪意ある指示が本会話へ流れ込むのを減らす
  • 以前に許可したコマンドでも疑わしい形なら再度承認を求め、規則に当たらないコマンドは既定で拒否になる

7.3 それでも残る分

公式ドキュメント自身が、これらの仕掛けは危険を減らすだけで完全な免疫ではないと明言している。そして残る分の大半は人の側だ。外部から来た内容をそのままパイプで流し込まないこと、承認の前に提案されたコマンドを読むこと、外部サービスと接する作業は隔離された環境で回すこと。陳腐に見えるが、この3つが実際に防ぐ事故の比重が最も大きい。

8. 最小権限へ絞る実際の設定

8.1 認証情報の層で絞る

最も外側であり最も効果の大きい層だ。どんなツール規則よりここで絞るほうが確実である。

  • データベースは読み取り専用アカウントで接続文字列を作る
  • コードホスティングのトークンは対象リポジトリだけを含む細粒度トークンで発行する
  • OAuthで接続するサービスは要求範囲を必要な分だけ残す
  • トークンを設定ファイルに直接書く代わりに環境変数の展開で参照する
  • 期限のある認証情報を優先する——忘れて放置しても自ら閉じる

8.2 ツール単位の規則で絞る

MCPのツールは mcp__サーバー名__ツール名 という形の名前を持つ。この名前で許可・確認・拒否の規則を書く。規則の文法には知っておくべき非対称が一つある。

  • 拒否と確認の規則はツール名の位置にグロブを使える。mcp__* はすべてのサーバーのすべてのMCPツールを指す
  • 許可の規則は違う。グロブは mcp__サーバー名__ というリテラルの接頭辞の後ろでのみ許される。サーバーの位置にはグロブを使えない
  • mcp__サーバー名__* はそのサーバーの全ツールを、mcp__サーバー名__get_* は照会系だけを自動承認する
  • 範囲を指定しない許可グロブ(例: 単なるワイルドカード)は警告とともに無視され、何も自動承認しない

実務で効くのは照会系だけを許可し、残りは承認に残す組み合わせだ。接続したからといって全部開けておく必要はない。実際に繰り返される読み取り操作だけを自動化すれば、往復は減り露出は増えない。

8.3 露出範囲の層で絞る

ファイルアクセス系は、クライアントが知らせる作業ルートを尊重するよう作られたサーバーかを確認する価値がある。仕様にはサーバーが自らアクセス範囲を尋ねて制限できるリクエストがあり、Claude Codeはセッションの起動ディレクトリと利用者が追加で許可したディレクトリの一覧で応答する。この一覧が変われば変更通知も送る。この流れを実装したサーバーは利用者が開いた分だけ見る。実装していないサーバーは自分が知る分だけ見る。この違いはサーバーの文書で確認すべき項目だ。

8.4 承認そのものが目的のツール

サーバー制作者側の仕掛けも一つある。ツールのメタデータに利用者の操作が必須という印を付けると、そのツールは自動承認のモードでも毎回承認画面を出し、次回から尋ねないという選択肢も提供しない。許可の規則でも迂回されない。アクセス権限の付与のように、人が同意したことがなければ意味のない操作のために作られた印だ。自分でサーバーを作るなら、破壊的なツールにこの印を付けることが利用者へ渡せる最も正直な安全装置になる。

9. コンテキスト費用と応答の遅延 - 多く接続するほど損をする地点

9.1 ツール定義が占める場所

サーバーを接続すると、そのサーバーのツール定義とサーバー案内文がモデルの入力に場所を取る。サーバーが増えるほど会話に使える空間が減る。Claude Codeはこれを和らげるためツール検索を既定で有効にしている。セッション開始の時点ではツール名とサーバー案内文だけを載せ、実際の定義は必要なときに探して呼び出す。だからサーバーを増やしてもコンテキストへの影響は大きくない。サーバーごとの固定的なツール数の上限はなく、実質的な限界はコンテキストの予算だ。

9.2 調整のつまみ

  • ツール検索の挙動は環境変数で変えられる。先に載せる・全部後回しにする・比率基準で自動判断する、から選ぶ
  • 毎ターン必要な少数のサーバーは常時ロードの選択肢で例外にできる。ただしそのサーバーが接続するまで起動が少し止まる
  • ツール出力が1万トークンを超えると警告が出る。既定の上限は2万5千トークンで、環境変数で上げられる
  • サーバー案内文とツール説明はそれぞれ2KBで切られる。サーバーを作るなら核心を前に置くべきだ
  • ツール呼び出しにはサーバーごとの時間制限と待機の制限が別に掛かる。待機の既定はリモート5分、ローカル30分だ

9.3 定期的に整理すべき本当の理由

トークン費用より実質的な問題は選択の誤りだ。似た名前のツールが複数のサーバーに散らばっていると、モデルが見当違いのほうを選ぶ確率が上がる。3か月前に一度試してそのままのサーバー、実験して途中でやめたサーバー、もう使わないサービスのサーバーを外す作業は、セキュリティ対策であると同時に精度の対策でもある。一覧を開いて直近30日に実際に呼ばれていないサーバーを候補として拾い出す程度の定期点検で十分だ。

10. 接続すべきでないときと代替手段

10.1 MCPが答えでない場合

すべての連携がサーバーである必要はない。次の場合はほかの手段のほうが安い。

  • すでに良いCLIがあるシステム: シェルコマンド一行で済む作業にプロトコル層を重ねると失敗点だけが増える
  • 手順の固まった反復作業: 自然言語で毎回指示する代わりにプロジェクト文書やスクリプトへ固めるほうが再現性が高い
  • 一度きりの照会: 接続して外す費用が照会一回より大きい
  • 認証情報を狭める手段がないシステム: 全権限のトークンしか発行されないなら露出範囲が統制不能だ
  • 出力が過大なソース: 呼び出しのたびに上限にぶつかれば結局は人が切ることになる

10.2 接続する前に試せること

  • まずローカルスコープで接続して2週間使い、実際の呼び出し頻度を見てプロジェクトスコープへの昇格を判断する
  • 読み取りツールだけ自動承認にし、書き込みは承認に残したまま観察する
  • 本番の認証情報ではなくステージングやレプリカの認証情報で先に接続する
  • ツール一覧を一度ざっと見て、破壊的なツールが何かを名前から確認する
  • サーバーが失敗したときどんなメッセージが出るか、わざと一度作ってみる——認証失敗と接続失敗は対応が違う

11. 確認できなかったこと

この記事で根拠を確保できず断定しなかった項目を一か所にまとめる。

  • 個々のサーバーの安全性の判定: この記事はいかなるサードパーティのサーバーも安全とは断定しない。公開された独立のセキュリティ監査結果は確認できなかった
  • ツール検索の実際の削減幅: 既定で有効という挙動は文書で確認したが、サーバー数に対するトークン削減量を示す公開ベンチマークの数値は確認できなかった
  • ツールポイズニングの実際の被害規模: 危険の類型とその優勢さを指摘する研究はあるが、実際の事故件数や被害規模を集計した信頼できる公開統計は確認できなかった
  • サーバー別の採用率の順位: ダウンロード数や導入数を基準にした信頼できる最新の順位表は確認できなかった。だからこの記事に人気順位はない
  • 元となったおすすめ記事の個別サーバー一覧: きっかけとなった記事で用途の区分と注意事項は確認したが、用途の下に並ぶ個別サーバーの全一覧までは確認できなかった
  • レジストリ方針の今後の変化: 公式レジストリがガバナンス機能を追加する計画があるかは確認できなかった

よくある質問(FAQ)

Q1. MCPサーバーを接続すべきかどうかはどう判断するのか?

ほかのツールの内容をセッションへ繰り返しコピーして貼り付けているなら、そのシステムが候補だ。逆に月に一、二度見るシステム、すでに使っているCLIで済む作業、毎回同じ内容で文書に固定できる場合は接続しないほうがよい。サーバー一つごとに設定・認証・コンテキスト費用と権限の露出が一緒に来る。

Q2. local・project・user のスコープは何が違うのか?

localは既定値でそのプロジェクトの中で自分だけが使う。projectはリポジトリの設定ファイルでチーム全体が共有し、初回利用時に承認を通す。userは自分のすべてのプロジェクトで開くが自分にしか見えない。同じ名前が重なるとlocal・project・user・プラグイン・コネクターの順で一つだけが残り、フィールドは結合されない。

Q3. プロンプトインジェクションとツールポイズニングは何が違うのか?

インジェクションはサーバーが取得したデータに指示文が潜む場合で、ポイズニングはツール定義そのものが汚染された場合だ。前者はデータを疑えばよく、後者はサーバーを疑う必要がある。ポイズニングがより厄介なのは、利用者の画面に描画されない文字列がモデルの入力にはそのまま入るからだ。

Q4. 権限を最小限に絞る実質的な方法は?

三層で絞る。認証情報は読み取り専用アカウントと細粒度トークンで、ツールはサーバー名とツール名を明示した規則で、露出範囲は作業ディレクトリの制限と環境変数の参照で絞る。3つのうち認証情報の層が最も効果が大きい。

Q5. ディレクトリやレジストリに載っていれば安全なのか?

違う。掲載基準に沿った審査はあるがセキュリティ監査ではないと文書に明記されている。公式レジストリもメタデータを保管するだけで、アクセス制御や監査証跡といったガバナンスは提供しない。掲載は出発点であって結論ではない。

結論 - 今日から適用する5段階

MCPサーバーの選択は良いリストを手に入れる問題ではなく、自分の基準を持つ問題だ。リストは半年で腐るが基準は残る。今日から適用できる順に整理するとこうなる。

  • 1段階——いま接続されているものから数える。一覧を開き、最近実際に使っていないサーバーに印を付ける。整理はセキュリティ対策であり精度の対策でもある
  • 2段階——各サーバーが何を差し出すのかを一行で書く。書けないサーバーは、まだ理解していないサーバーだ
  • 3段階——認証情報から絞る。読み取り専用アカウント、細粒度トークン、狭いOAuth範囲。ここで絞るほうが規則より確実だ
  • 4段階——スコープを選び直す。チーム全体に与える権限か、自分だけの権限か、このプロジェクトでだけ開く権限かを区別して移す
  • 5段階——新しいサーバーはローカルスコープで2週間試す。読み取りだけ自動承認にして呼び出し頻度を見てから昇格の可否を決める

最後にこの記事がしなかったことを明確にしておく。ここにはどのサーバーが安全だという判定はない。判定を代わりにしてくれるリストは存在しないからだ。あるのは判定に使う軸だけで、その軸を自分の環境に当ててみる作業は結局、接続する人の分担である。
