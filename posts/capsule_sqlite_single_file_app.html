개인용 소도구 개발의 고질적 난제, 완성된 뒤의 배포와 저장

개발은 빨라졌으나 배포와 호스팅은 여전히 무겁다

인공지능 코딩 어시스턴트와 대형 언어 모델의 발전으로 소프트웨어 프로토타입을 제작하는 진입 장벽은 그 어느 때보다 낮아졌다. 과거에는 며칠 혹은 몇 주가 걸리던 개인 맞춤형 가계부, 프로젝트 작업 추적기, 북마크 관리자, 전자기기 인벤토리 도구 같은 소규모 애플리케이션을 이제는 자연어 프롬프트 몇 번으로 단 몇십 분 만에 생성할 수 있다. 하지만 코드를 완성한 순간, 실무 개발자와 개인 제작자는 예외 없이 동일한 현실적인 벽에 부딪힌다. 바로 완성된 도구를 실제로 구동하고 데이터를 저장하며 필요한 이들에게 전달하는 배포의 문제다.

전통적인 웹 애플리케이션 방식을 선택하면 유지보수와 운영 부담이 급격히 증가한다. 간단한 개인용 CRUD 도구 하나를 띄우기 위해서도 도메인을 설정하고, 가상 사설 서버(VPS)나 클라우드 컨테이너를 임대하며, 데이터베이스 인스턴스를 관리하고, HTTPS 보안 인증서를 갱신해야 한다. 매달 청구되는 클라우드 호스팅 비용은 물론이고, 데이터베이스 백업과 서버 취약점 패치라는 지속적인 관리 부채가 발생한다. 반면 단일 HTML 파일로 구성된 순수 클라이언트 웹페이지를 제작하면 웹 서버 호스팅 비용은 없앨 수 있지만, 브라우저의 보안 샌드박스 정책으로 인해 로컬 디스크에 구조화된 대용량 데이터를 안전하게 지속 저장하는 데 심각한 제약을 겪게 된다. 사용자가 브라우저 캐시를 지우거나 시크릿 모드를 닫는 순간 축적된 데이터가 증발할 위험이 항상 도사리고 있다.

그렇다고 데스크톱 네이티브 바이너리나 Electron 기반 애플리케이션으로 패키징하는 길을 택하면 배포 복잡도는 더욱 심화된다. 운영체제별로 런타임을 묶어 수백 메가바이트 크기의 설치 패키지를 빌드해야 하고, macOS의 Gatekeeper나 Windows의 SmartScreen 같은 코드 서명 인증서를 구매하고 통과해야 한다. 동료나 지인에게 가볍게 전달하고 싶어도 설치 관리자를 내려받아 시스템 권한을 승인하며 설치해야 하는 마찰 비용이 너무 크다. 소프트웨어 제작은 가벼워졌으나, 배포와 데이터 지속성 확보는 여전히 무겁게 남아 있는 모순적 상황이 지속되어 온 것이다.

문서와 애플리케이션의 경계가 흐려진 배경

컴퓨팅 역사에서 가장 성공적이었던 정보 교환의 단위는 언제나 파일 형태의 문서였다. PDF, Word 문서(.docx), 스프레드시트(.xlsx)는 전 세계 수십억 명의 사용자에게 직관적인 멘탈 모델을 제공한다. 문서는 이메일 첨부 파일로 보내거나 메신저 대화방에 끌어다 놓기만 하면 즉시 상대방에게 전달된다. 수신자는 별도의 계정 가입이나 서버 설정 없이 뷰어로 파일을 열어 내용을 확인하고, 수정하여 다시 다른 사람에게 전송한다. 데이터와 서식이 하나의 독립된 파일 안에 완전히 완결되어 존재하기 때문이다.

반면 현대의 애플리케이션은 문서와 정반대의 경로를 걸어왔다. 인터페이스와 비즈니스 로직은 클라이언트 뷰어에 분산되고, 실제 데이터는 원격 클라우드 데이터베이스 서버에 종속되는 사일로(Silo) 구조가 표준으로 정착했다. 이로 인해 소프트웨어는 고도의 실시간 협업 기능을 얻었지만, 네트워크 연결 없이는 깡통이 되어버리는 취약성과 데이터 주권의 상실이라는 대가를 치렀다. 만약 애플리케이션의 동적 UI와 풍부한 인터랙션, 그리고 그 애플리케이션이 다루는 구조화된 데이터베이스 전체가 과거의 스프레드시트 파일처럼 하나의 파일 안에 묶여 이메일이나 AirDrop으로 전달될 수 있다면 어떨까? Capsule은 바로 이러한 오래된 질문을 최신 데스크톱 환경과 경량 데이터베이스 기술을 통해 다시 구현하겠다고 나선 프로젝트다.

Capsule이 채택한 구조: .capsule 파일 안의 세 가지 핵심 요소

HTML UI와 CSS 프리셋: 브라우저 기술 기반의 화면 렌더링

공식 웹페이지(`withcapsule.app`)에 명시된 Capsule의 대표 슬로건은 「Documents that run like apps」, 즉 앱처럼 실행되는 문서다. Capsule이 제시하는 기술 아키텍처의 첫 번째 축은 사용자 인터페이스를 웹 표준 기술로 렌더링한다는 점이다. `.capsule` 파일 내부에는 완전히 독립적인 단일 파일 형태의 HTML UI 레이아웃과 CSS 스타일셋이 포함된다.

웹 표준 기술을 화면 엔진으로 채택함으로써 개발자와 AI 에이전트는 이미 검증된 웹 에코시스템의 표현력을 그대로 활용할 수 있다. 복잡한 네이티브 GUI 라이브러리를 학습할 필요 없이 표준 시맨틱 태그, 폼 컨트롤, 플렉스박스 및 그리드 레이아웃, 다크 모드 스타일을 즉시 적용할 수 있다. 공식 제품 설명에 따르면 자연어 프롬프트나 모델 컨텍스트 프로토콜(MCP) 기반 코딩 도구를 통해 화면 기능과 디자인 요소를 즉각적으로 수정하고 확장할 수 있도록 설계되어 있다.

로컬 SQLite 데이터베이스와 스키마의 일체화

Capsule 아키텍처의 두 번째이자 가장 결정적인 요소는 로컬 SQLite 데이터베이스와 테이블 스키마의 일체화다. 일반적인 정적 웹페이지나 프로토타입 도구가 임시 상태 저장을 위해 브라우저의 `localStorage`나 인메모리 자바스크립트 객체에 의존하는 것과 달리, Capsule은 관계형 데이터베이스 엔진인 SQLite를 파일 컨테이너 내부에 직접 내장한다.

이 설계 덕분에 애플리케이션이 다루는 모든 데이터는 단순한 비정형 텍스트 덤프가 아니라, 정규화된 테이블 스키마와 인덱스를 갖춘 온전한 SQL 데이터베이스의 통제를 받는다. 사용자가 작업 목록을 추가하거나, 레시피 메모를 편집하거나, 프로젝트 진척도를 수정할 때 발생하는 모든 데이터 변경은 파일 내부의 SQLite 데이터베이스에 즉시 커밋된다. UI와 스키마, 데이터 행(Row)이 동일한 단일 파일 경계 안에서 결합되어 있으므로, 파일을 다른 위치로 이동하거나 다른 사용자에게 전송해도 데이터와 화면 구조의 정합성이 완벽하게 보존된다.

단일 파일 컨테이너와 데스크톱 전용 호스트 플레이어

Capsule의 세 번째 요소는 이 모든 것을 하나의 물리적 파일로 묶어내는 `.capsule` 컨테이너와 이를 구동하는 데스크톱 전용 무료 호스트 플레이어(Host Player)다. 사용자는 각 운영체제에 맞는 플레이어 애플리케이션을 한 번 설치해 두면, 시스템 내의 모든 `.capsule` 파일을 더블 클릭하여 즉시 독립된 창에서 앱으로 실행할 수 있다.

공유 방식 또한 전통적인 문서 교환 메커니즘을 그대로 따른다. 사용자는 메신저(WhatsApp 등), AirDrop, 이메일 첨부 파일을 통해 상대방에게 `.capsule` 파일을 보낼 수 있다. 수신자가 해당 파일을 열면 이전 사용자가 작성해 둔 데이터가 미리 채워진 상태로 애플리케이션이 즉시 작동한다. 중앙 서버나 원격 데이터베이스 연결이 전혀 개입하지 않으므로 전송 도중 네트워크 패킷이 탈취되더라도 서버 측 유출 사고가 발생할 수 없으며, 제3자의 인프라 가동 여부에 구애받지 않는다.

애플리케이션 파일 포맷으로서의 SQLite, 왜 자연스러운 선택인가

단일 파일 RDBMS가 제공하는 트랜잭션과 무결성

소프트웨어가 로컬 디스크에 상태를 저장할 때 선택할 수 있는 방식은 다양하다. 일반 텍스트 파일, 직렬화된 JSON, 독자적인 바이너리 스트림, 혹은 임베디드 키-값 저장소 등이 대표적이다. 그럼에도 불구하고 Capsule이 저장 계층으로 SQLite를 채택한 것은 컴퓨터 공학적으로 매우 탄탄한 근거를 가진다. SQLite 공식 개발팀은 오래전부터 웹페이지 문서(SQLite As An Application File Format)를 통해 SQLite를 일반 데스크톱 프로그램의 표준 파일 포맷으로 사용할 것을 공식 권장해 왔다.

SQLite가 애플리케이션 파일 포맷으로 발휘하는 최대 강점은 ACID(원자성·일관성·격리성·지속성)를 완벽히 보장하는 트랜잭션 시스템이다. 많은 데스크톱 도구가 독자 파일 포맷을 다룰 때 겪는 치명적인 문제는 애플리케이션 비정상 종료나 운영체제 전원 차단 시 파일 전체가 깨지는 현상이다. 메모리에 전체 데이터를 올려두고 디스크에 덮어쓰는 과정에서 전원이 끊기면 파일의 끝부분이 잘려 복구 불가능한 상태가 된다. 반면 SQLite는 Write-Ahead Logging(WAL)과 롤백 저널 메커니즘을 통해 쓰기 작업 도중 전원이 차단되더라도 재부팅 시 손상 없이 이전 커밋 상태로 자동 롤백되거나 복구된다. 소규모 개인 앱이라 할지라도 데이터 유실 위험을 원천적으로 차단할 수 있는 이유가 여기에 있다.

JSON·XML 직렬화 파일 대비 대용량 및 검색 효율성

JSON이나 XML 기반의 단일 파일 저장 구조와 비교할 때 SQLite의 성능적 우위는 더욱 두드러진다. JSON 형식은 파일 내의 단 한 줄, 단 하나의 필드 값을 수정하려 해도 전체 텍스트를 디스크에서 읽어 파싱 트리를 구성해야 하고, 저장을 마친 뒤에는 전체 텍스트를 다시 직렬화하여 디스크에 써야 한다. 데이터 크기가 수백 킬로바이트 수준일 때는 체감되지 않지만, 기록이 쌓여 수십 메가바이트로 늘어나면 파일 로딩 지연과 메모리 소모가 기하급수적으로 폭증한다.

반면 SQLite는 디스크 공간을 고정 크기의 B-트리 페이지 단위로 관리한다. 따라서 데이터베이스 크기가 수 메가바이트를 넘어가더라도 사용자가 조회하거나 수정한 특정 레코드의 페이지만 디스크에서 부분적으로 읽고 쓸 수 있다. 공식 웹페이지에 나타난 예시 파일 표기인 `Portfolio.capsule 3.2 MB · 24 Projects`나 `Life.capsule 1.2 MB`와 같은 실제 사용 사례에서도, 수 메가바이트 수준의 멀티미디어 자산과 텍스트 데이터가 결합된 환경에서 버벅임 없이 밀리초 단위로 데이터가 갱신될 수 있는 배경에는 SQLite의 페이지 단위 입출력 아키텍처가 존재한다. 본 저장소의 이전 글인 SQLite Editions 제안 2026에서 다루었듯, 20년이 넘는 세월 동안 하위 호환성과 파일 포맷 무결성을 검증받아 온 SQLite의 특성은 장기 보존용 단일 파일 앱의 기반으로 가장 신뢰할 수 있는 토대를 제공한다.

오프라인 동작과 클라우드 배제가 가져오는 명암

서버 침해 없는 프라이버시와 무비용 독립 실행

Capsule의 설계 철학은 클라우드 중앙 서버를 완전히 배제하는 데서 출발한다. 공식 제품 페이지는 「100% Private by Design」이라는 문구를 통해 개인 데이터가 외부 서버로 절대 유출되지 않는다는 점을 핵심 가치로 내세우고 있다. 현대 SaaS 애플리케이션을 사용할 때 사용자는 자신의 사적인 할 일 목록, 가족 레시피, 미공개 포트폴리오, 아이디어 메모를 제3자 기업의 클라우드 서버에 전적으로 위탁해야 한다. 이는 서비스 제공자의 데이터베이스 침해 사고나 계정 해킹, 혹은 기업의 일방적인 서비스 종료나 구독료 인상 위험에 사용자를 무방비로 노출시킨다.

Capsule은 계정 등록 절차가 없고, 원격 API 서버나 클라우드 저장소와 통신하지 않는다. 따라서 인터넷이 연결되지 않는 비행기 기내나 지하철, 혹은 철저한 보안이 요구되는 망분리 사내 업무 환경에서도 100% 독립적으로 작동한다. 사용자는 자신의 하드디스크에 저장된 `.capsule` 파일 하나만 관리하면 되며, 구독 해지로 인해 자신의 데이터에 접근하지 못하게 되는 종속 현상에서 완전히 자유롭다.

다중 기기 실시간 동기화 부재라는 명확한 한계

그러나 클라우드를 완전히 배제한 단일 파일 구조는 치명적인 반대급부를 수반한다. 바로 현대 사용자들이 너무나 당연하게 누리고 있는 다중 기기 간 실시간 자동 동기화의 부재다. 공식 제품 페이지에는 파일 동기화 기능에 대한 서술이 전혀 존재하지 않으며, 오프라인 로컬 저장만을 명시하고 있다.

본 저장소의 분석 글인 오프라인 우선 데이터베이스 동기화에서 상세히 짚었듯, 진정한 의미의 로컬 퍼스트(Local-First) 소프트웨어가 완성되려면 로컬 디바이스의 즉각적인 응답 속도와 함께 네트워크 연결 시 충돌 없이 데이터를 병합해 주는 분산 동기화(CRDT 등) 엔진이 필수적이다. 또한 Linear의 로컬 퍼스트 아키텍처가 입증했듯, 현대 실무 생산성 도구의 경쟁력은 로컬 인메모리 처리의 쾌적함과 백그라운드 중앙 서버 동기화가 조화를 이룰 때 극대화된다.

Capsule의 단일 파일 격리 모델에서는 이러한 매끄러운 동기화가 불가능하다. 사무실 PC에서 할 일 목록을 정리한 뒤 스마트폰이나 자택 노트북에서 동일한 앱을 이어서 사용하려면, 사용자가 매번 수정된 `.capsule` 파일을 AirDrop이나 이메일로 자기 자신에게 전송하여 파일을 덮어써야 한다. 만약 두 기기에서 각각 독립적으로 데이터를 수정한 뒤 같은 클라우드 드라이브에 저장할 경우, 파일 덮어쓰기로 인한 데이터 손실이나 충돌 복사본(Conflicted Copy)이 발생할 수밖에 없다. SQLite 파일 자체는 네트워크 파일 공유 드라이브(SMB, Dropbox, OneDrive 등)에서 동시 쓰기 시 잠금 충돌과 파일 손상에 취약하다는 점 또한 실무 커뮤니티에서 꾸준히 지적되는 기술적 제약이다.

  • 외부 원격 서버에 데이터를 일절 전송하지 않으므로 데이터 프라이버시 침해 및 서버 유출 위험이 원천 차단됨.
  • 네트워크 연결이 차단된 오프라인 환경이나 보안 망분리 구역에서도 완벽하게 모든 기능을 수행함.
  • 공식 명세상 다중 기기 간 자동 백그라운드 동기화 기능이 없어 기기 간 이동 시 수동 파일 전달이 요구됨.
  • 여러 사용자가 동시에 데이터를 갱신하거나 협업할 경우 데이터베이스 충돌 병합 메커니즘이 부재함.

닫힌 포맷의 리스크: 명세 미공개와 데이터 종속의 위험

호스트 플레이어가 사라졌을 때 남겨질 데이터의 운명

Capsule이 GeekNews와 Hacker News 등 기술 커뮤니티에 공개되었을 때 개발자들 사이에서 가장 날카로운 질문이 쏟아진 지점은 바로 파일 포맷의 개방성과 소유권 문제였다. 로컬 퍼스트 소프트웨어가 사용자에게 주는 가장 큰 약속은 영구적인 데이터 주권이다. 클라우드 서비스가 문을 닫더라도 내 하드디스크에 남은 파일은 영원히 내 것이어야 한다는 철학이다.

그러나 공식 제품 페이지에는 Capsule 호스트 플레이어의 소스 코드 라이선스나 `.capsule` 컨테이너의 내부 직렬화 규격에 대한 명세서가 공개되어 있지 않다. 완전히 무료로 제공된다는 점은 밝히고 있으나, 이것이 오픈소스인지 독점적 무료 배포판(Freeware)인지는 명시되지 않았다. 만약 독점적인 비공개 바이너리 컨테이너 규격으로 묶여 있다면, 5년이나 10년 뒤 Capsule 개발팀이 유지보수를 중단하거나 운영체제 업데이트로 호스트 플레이어가 실행되지 않게 되었을 때 사용자는 파일 내부의 SQLite 데이터와 HTML 화면을 온전히 꺼낼 수 없게 된다. 이는 클라우드 SaaS의 벤더 종속(Lock-in)을 피하려다 또 다른 단일 벤더의 전용 뷰어에 종속되는 모순을 낳을 수 있다.

오픈소스화 여부와 명세 공개에 대한 커뮤니티의 우려

실제로 Hacker News 토론에서 한 참여자는 "개인적으로 .capsule이라는 자체 확장자를 보았을 때 관심이 식었다. 직접 만든 형식인 것 같은데 개발자가 더 이상 없거나 연락이 닿지 않으면 내 데이터는 어떻게 되는가"라는 현실적인 의문을 제기했다. 이에 대해 또 다른 커뮤니티 개발자는 앱 전체를 오픈소스로 공개할 계획이 있는지, 혹은 규격 안정화 이후 파일 포맷 명세만이라도 공개할 계획이 있는지를 논의했다.

개발자 커뮤니티의 공통된 의견은, 진정으로 신뢰할 수 있는 단일 파일 앱 생태계가 형성되려면 적어도 표준 zip이나 tar 아카이브 기반의 컨테이너 구조 명세가 공개되어야 한다는 점이다. 전용 플레이어가 없더라도 운영체제 기본 아카이브 도구나 터미널의 `sqlite3` CLI 명령어를 통해 내부의 데이터베이스 파일과 에셋을 즉시 추출할 수 있는 투명성이 담보되지 않는다면, 업무상 중요한 장기 데이터를 보관하기에는 위험 부담이 남을 수밖에 없다.

  • 호스트 플레이어의 소스 코드 라이선스와 오픈소스 공개 로드맵이 공식 페이지에 명시되어 있지 않음.
  • .capsule 컨테이너의 내부 패키징 명세가 비공개 상태일 경우 장기적인 데이터 보존성 확보에 제약이 따름.
  • 독자 포맷에 갇히지 않으려면 표준 아카이브 호환성이나 외부 추출 도구의 공식 제공이 필수적이라는 지적이 제기됨.

단일 파일 앱과 로컬 소프트웨어의 계보 비교

단일 HTML, sqlar, PWA, Electron과의 비교 분석

소프트웨어 인터페이스와 데이터를 하나의 단위로 묶어 로컬에서 실행하려는 시도는 Capsule이 처음이 아니다. 개인용 컴퓨팅이 시작된 이래 개발자들은 다양한 아키텍처를 통해 이 문제를 해결하고자 했다. 대표적으로 2004년에 등장한 TiddlyWiki는 단일 HTML 파일 안에 자바스크립트 엔진과 위키 텍스트 데이터를 모두 포함하여, 브라우저로 파일을 열고 편집한 뒤 브라우저를 통해 자기 자신을 다시 덮어쓰는 독창적인 단일 파일 위키 모델을 개척했다.

한편 SQLite 생태계 내부에서는 공식 아카이브 포맷인 `sqlar`(SQLite Archive)를 활용한 시도가 꾸준히 이어져 왔다. 일반적인 zip 압축 파일 대신 SQLite 테이블 안에 파일 이름, 권한, 압축 데이터를 저장하는 방식으로, sqlar 규격 위에 HTML 정적 자산을 얹어 브라우저나 데스크톱에서 독립 실행되는 앱을 만들려는 시도가 커뮤니티에서 이어져 왔다. 또한 최신 웹 표준 진영에서는 Chromium 기반 브라우저의 File System Access API와 프로그레시브 웹 앱(PWA) 매니페스트를 결합하여, 별도의 데스크톱 뷰어 설치 없이도 브라우저가 직접 로컬 SQLite나 텍스트 파일을 안전하게 읽고 쓸 수 있는 환경(예: 웹 기반 텍스트 에디터나 vscode.dev)을 완성해 가고 있다. 아래 표는 이들 계보와 Capsule의 기술적 특징을 비교한 것이다.

로컬 실행 및 단일 파일 소프트웨어 계보 비교
기술 분류 배포 단위 데이터 저장 방식 오프라인 실행 데이터 이식성 및 개방성
단일 HTML 파일 (TiddlyWiki 계열) 독립 .html 파일 1개 HTML 내부 텍스트 직렬화 및 브라우저 자체 다운로드 덮어쓰기 가능 (표준 웹 브라우저만으로 구동) 매우 높음 (일반 텍스트 에디터로 언제든 열람 가능)
SQLite Archive 기반 앱 (sqlar) 단일 .sqlar 또는 .db 파일 표준 SQLite 관계형 테이블 및 BLOB 스토리지 가능 (전용 런타임 또는 브라우저 wasm) 매우 높음 (표준 sqlite3 명령어로 즉시 추출 가능)
PWA + File System Access API 웹 URL 설치 및 로컬 작업 파일 브라우저 권한을 통한 로컬 파일 직접 입출력 가능 (Service Worker 캐싱 지원 시) 높음 (사용자가 지정한 로컬 파일 포맷에 종속)
Electron / 네이티브 패키징 앱 OS별 실행 바이너리 및 설치 패키지 로컬 앱 데이터 폴더 또는 외부 DB 파일 가능 (완전한 네이티브 권한 보유) 다양함 (앱 개발사의 자체 구현 방식에 따름)
Capsule 단일 .capsule 파일 + 전용 호스트 플레이어 컨테이너 내장 로컬 SQLite 데이터베이스 가능 (100% 로컬 오프라인 실행) 제한적 (공식 명세 미공개, 전용 플레이어 의존)
  • 단일 HTML 방식은 배포가 극도로 간편하지만 대용량 구조화 데이터 쿼리와 영구 저장의 한계를 지님.
  • sqlar 기반 방식은 완전한 표준 데이터 개방성을 제공하나 일반 비개발자 대상의 직관적 실행 환경이 부족함.
  • PWA와 File System Access API는 표준 브라우저 역량을 극대화하나 플랫폼별(크롬 외 브라우저) 지원 편차가 존재함.
  • Capsule은 비개발자 친화적인 문서 교환 경험과 데스크톱 성능을 융합했으나 포맷의 투명성 확보가 숙제로 남음.

어디에 도입할 만하고, 어디에는 피해야 하는가

적합한 워크로드: 개인용 추적기·사내 보안 소도구·단독 포트폴리오

Capsule의 독특한 아키텍처는 명확한 장단점을 지니고 있으므로, 엔지니어링 팀이나 실무자는 워크로드의 특성에 따라 신중하게 도입 여부를 판단해야 한다. 가장 적합한 영역은 타인과의 실시간 동시 협업이 필요 없는 독립적인 1인용 소도구다. 개인의 일일 업무 저널, 개인 자산 기록, 독서 노트, 취미 데이터베이스처럼 데이터의 생성과 소비가 단일 사용자 안에서 완결되는 작업에는 최적의 편의성을 제공한다.

또한 국내 기업이나 공공기관 중 사내 보안 규정상 외부 클라우드 SaaS 접속이나 원격 데이터베이스 연결이 엄격하게 금지된 폐쇄망 환경에서 내부 업무용 소도구를 배포할 때 유용하다. 보안 검토가 까다로운 클라우드 인프라를 신청하거나 무거운 컨테이너를 올릴 필요 없이, 검증된 플레이어 환경 위에서 `.capsule` 파일 하나로 직원들에게 업무 보조 도구를 안전하게 배포할 수 있기 때문이다. 인터랙티브 컴포넌트와 프로젝트 결과물이 데이터와 함께 묶여 전달되는 디자이너나 프리랜서의 단독 포트폴리오 전달용으로도 높은 완성도를 기대할 수 있다.

부적합한 워크로드: 실시간 다중 협업·클라우드 중앙 집중 데이터

반대로 여러 팀원이 동시에 상태를 변경하고 최신 데이터를 실시간으로 동기화해야 하는 엔터프라이즈 협업 워크로드에는 Capsule을 도입해서는 안 된다. 공유 폴더에 파일을 두고 여러 사람이 함께 열어 작업할 경우 SQLite의 파일 잠금 충돌과 데이터 덮어쓰기 사고가 발생할 위험이 크며, 충돌 해결 기능이 없기 때문이다.

아울러 수년 이상 장기 보관해야 하는 기업의 핵심 회계 원장이나 감사 기록, 규제 대응 문서에는 비공개 포맷 기반의 도구를 적용하는 것이 부적절하다. 규정 준수와 영구 아카이빙이 요구되는 데이터는 언제나 표준 SQL 덤프나 오픈소스 포맷으로 언제든 재현 및 추출이 가능한 시스템에 안착되어야 한다.

  • 적합: 클라우드 종속 없이 온전히 개인 기기에서만 다루어지는 개인 일상 및 업무 트래커.
  • 적합: 사내 보안 정책상 외부 클라우드 사용이 제한된 환경에서의 단독 실행형 사내 소도구 배포.
  • 적합: 데이터와 화면이 결합된 상태로 클라이언트에게 온전히 전달되어야 하는 인터랙티브 포트폴리오.
  • 부적합: 다수의 작업자가 동시에 레코드를 읽고 쓰는 실시간 팀 프로젝트 및 고객 지원 티켓 관리.
  • 부적합: 10년 이상의 장기 보존과 표준 형식 열람이 법적으로 강제되는 엔터프라이즈 감사 로그 및 회계 원장.
  • 부적합: 기기 간 실시간 자동 동기화와 모바일-데스크톱의 빈번한 교차 작업이 필수적인 워크플로.

확인하지 못한 것

  • .capsule 컨테이너 내부의 구체적인 패키징 바이너리 구조 및 자체 압축·암호화 적용 여부 (공식 기술 명세 문서가 웹에 공개되어 있지 않음).
  • 데스크톱 호스트 플레이어의 오픈소스화 계획 및 구체적인 소프트웨어 라이선스 정책 (제품 페이지에 완전 무료 표기 외 라이선스 규정 부재).
  • .capsule 파일 1개당 권장되는 최대 SQLite 데이터 용량 한계와 수십만 행 이상의 데이터 적재 시 메모리 점유율.
  • 출시 예정으로 안내된 모바일(iOS 16+, Android 9+) 호스트 플레이어의 구체적인 배포 시점 및 샌드박스 파일 접근 방식.
  • 데스크톱 호스트 플레이어 내부에서 사용된 웹 렌더링 엔진(WebKit, Chromium, Tauri 등)의 구체적인 네이티브 래퍼 스택.
  • 향후 P2P 또는 선택적 클라우드 동기화 모듈이 추가될 계획이 있는지 여부 (현재 공식 설명은 100% 오프라인 동작에만 한정됨).
