The Model Only Emits Text - Everything Else Is Decided by the Harness

Calling the tool, deciding when to stop, choosing whether to retry a failure: none of these are the model's decision

2026-09-05 Dev & Infra

When an agent deletes a file, the model did not delete it. What the model did was generate one block of structured text saying, in effect, that calling the delete tool with these arguments would be appropriate. The program that read that text and made the actual system call sits outside the model entirely.

The distinction sounds pedantic until you have run agents in production, at which point it turns out to account for most of the problems. The same model behaves impeccably against one set of tools and repeats the same query ten times against another. In one environment it retries a failed tool once; in another it gives up immediately. A large share of the reports that begin with the words we swapped the model and the behaviour changed are actually reports that the contract of the layer wrapping the model changed.

The name that layer has acquired is the harness. What follows works through what the harness actually decides, checking each decision against the field names printed in vendor documentation, and then sets out the symptom that appears when each of those decisions is simply left undefined. This is not a framework tour or a feature comparison. The separate question of what shape an agent should take in your codebase was covered in what classes, graphs and config files each hide.

Every field name and default value below is quoted as it appears in the Claude API documentation, the OpenAI function calling guide, the Gemini API type reference, the MCP specification and its JSON schema. Tool calling contracts differ between vendors and get revised within a single vendor, which makes copying field names out of somebody else's write-up the single most common source of error on this topic.

The trigger: a repository that led with the word harness

In early September 2026 a repository called TrueForge was posted to a Korean developer community. The tagline read an open source harness that runs an LLM as a real agent. Not a framework, not a library. Leading with the word harness is the part worth noticing.

The repository's public numbers, as of 04:22 UTC on 5 September 2026, are as follows. 5,221 stars, 374 forks, 91 open issues, roughly 515 commits, roughly 31 contributors, TypeScript, MIT licence, created on 23 July 2026 and last pushed on 4 September, one day earlier. The most recent tagged releases are the @truefoundry/trueforge@0.2.0-rc.0 family from 27 August, and all four npm packages sit at pre-1.0 release candidates. The README requires Node 22.14 or newer.

Star count is not a maturity signal. Five thousand stars in six weeks measures attention, not stability, and the 0.2.0-rc version string and the 91 open issues are facts from the same instant. Leaving the interpretation of those numbers to the reader, what is worth taking from the repository here is the scope it assigns to the word harness. Its documentation defines a harness as the runtime layer around an LLM that turns it into a reliable, long-running agent, and lists its responsibilities as planning, tool routing and execution, context management for long tasks, security boundaries such as sandboxing and human-in-the-loop approvals, and session state that survives reconnects and restarts.

What makes that list interesting is that nothing on it is done by the model. Planning is managed by the harness, and so is tool routing, context, approval and state. Which leaves the question of what the model does.

What the model actually returns: text and a reason for stopping

Call a model API once and two things come back. An array of content blocks and the reason generation stopped. That is the whole of it. Streaming does not change it, and neither does attaching tools.

Attach tools and the array may contain tool_use blocks alongside the text blocks. The Claude API documentation states that such a block carries three fields: id, name and input. Respectively, a unique identifier used to match the call up with its result later, the name of the tool being used, and an object of arguments conforming to the tool's input_schema. Nowhere in there is there an execution. At the instant the block arrives, the file is still on disk.

The stop_reason that carries the reason for stopping is the only signal the harness has for deciding what to do next. Each value demands different handling, and several of them are easy to leave out.

stop_reasonWhat the documentation says it meansWhat the harness has to do
end_turnThe response finished naturallyEnd the loop and use the result as it stands
tool_useA tool is being called and an execution result is expectedRun the tool, return the result, call again
max_tokensGeneration hit the limit set in the requestRaise the limit or continue the response. If a tool_use block was cut off mid-way, discard that turn
stop_sequenceOne of the custom stop strings appearedRead the stop_sequence field to see which one fired
pause_turnThe server-side tool loop reached its iteration limit. The default is 10 per requestSend the assistant content back as it is to continue. This differs from returning tool results
refusalThe model declined. This arrives as a normal 200 response, not an errorRead the policy category from stop_details and route to a fallback path
model_context_window_exceededGeneration hit the model's context window limitTreat the response as truncated. This is a different situation from max_tokens

The two most commonly missing branches in practice are pause_turn and model_context_window_exceeded. The first looks like tool_use but is handled in the opposite way, and mistaking the second for max_tokens leads to repeatedly raising a limit that was never the constraint. A harness with a missing branch simply appears to hang under that condition.

The boundary of responsibility: who decides what

It is worth laying this out in one place. The left column below lists the decisions that somebody has to make in order to run an agent at all, the middle column says where each decision is actually taken, and the right column gives the symptom that appears when nobody takes it.

Read the right column top to bottom and it becomes a familiar incident list. And none of those items is fixed by swapping in a better model. The last row is the sharpest case. The Claude API documentation notes that tool results frequently carry content from sources outside your control, such as web pages, inbound email, user uploads and third-party APIs, and instructs you to treat that content as untrusted and keep it inside tool_result blocks rather than system prompts or plain user text blocks. That is a question of placement, not of model capability.

A tool call is a request, not an execution

Saying that the model calls a tool creates the misunderstanding. What actually happens is closer to filling in a requisition form. The model generates a structure containing a tool name and arguments, and ends its turn there. Everything after that belongs to the outside.

Processing that requisition involves at least six decisions the harness has to make.

  • Name resolution - which real function corresponds to the name the model wrote. If the same name exists on several MCP servers, which one wins
  • Argument validation - does it match the schema. If not, execute anyway or bounce it back
  • Permission check - is this session allowed to call this tool. Is it in a tier that requires approval
  • Execution environment - does it run inside the harness process or in an isolated sandbox
  • Timeout - how long to wait. The MCP specification tells clients to implement timeouts for tool calls
  • Result shaping - if the return value is large, does it go in whole, or does it get summarised or written to a file with only a preview inlined

The last item has a direct effect on outcomes. Drop a 300KB log straight into the context and every subsequent turn is crushed under it. Insert only a preview and the line that mattered may have been cut away. Whichever branch is taken, the world the model sees is an edit produced by the harness. The point at which tool selection itself starts to break down as the catalogue grows, and the ways to narrow it, were covered in how many tools can you attach.

Same concept, different fields: the vendor contracts

Tool calling is a shared concept but the contracts differ by vendor. Those differences become branches in the harness code, and they are where porting goes wrong.

The row that catches the eye first is the shape of the arguments. OpenAI's arguments is a JSON-encoded string while the others are objects. That single line adds one more failure path to the harness. When the model emits syntactically broken JSON, that is not a tool failure but an argument decoding failure, and routing both down the same channel tangles the retry policy.

Where the result goes also splits. The Claude API has no separate tool role and instead puts a tool_result block inside a user message, a difference from other APIs that the documentation calls out explicitly. Attached to it are rules that produce a 400 when broken. Tool result blocks must immediately follow their corresponding tool use message, and within the user message carrying results, the result blocks must come first in the content array. Put text ahead of them and the request is rejected.

That tool definitions are not free is also part of the contract. The Claude API documentation states that attaching tools automatically inserts a system prompt that enables tool use, and that its token count varies by model and by the tool_choice setting, and it publishes a table. For Claude Opus 5 the figure is 286 tokens under auto or none, and 406 tokens under any or a named tool. The tokens for the tool names, descriptions and schemas are added on top of that.

How failure gets handed back to the model

Tools fail. The question is what shape that failure takes when the model sees it, and that is decided entirely by the harness. The portion fixed by the vendor contract is narrower than people expect.

SurfaceWhat the contract fixesWhat the harness must decide
Claude APIis_error: true on the tool_result. The documentation advises writing what went wrong and what to try nextThe wording. Whether to say only that it failed, or to include retry viability and a wait time
OpenAINo dedicated error field. The format of output is left to the caller, whether JSON, error codes or plain textThe entire error convention. The cue that lets the model tell success from failure has to be invented
GeminiThe response object of a functionResponseWhich key inside that object carries the error
MCPProtocol errors and tool execution errors are separated. Unknown tools and invalid arguments become JSON-RPC errors, failures during execution become isError: true in the resultThe criteria deciding which failure goes down which path

The reason MCP split the two carries straight over into harness design. A failure the model needs to see and a failure the model has no business seeing are different things. Calling a tool that does not exist is a protocol violation and a client concern. An API returning 429 is something the model should know about, because it is raw material for deciding to use a different tool or to try again shortly.

One common mistake here. Pasting the error string in verbatim. Pouring a full stack trace into content eats the context, and internal paths or fragments of credentials can ride along inside it. The principle of passing a reference instead of a value was covered separately in getting work done without handing the agent your credentials. Errors are another place the same principle applies.

Parallel calls: what one parameter divides

May the model call several tools in one turn? Vendors generally allow it and provide a way to switch it off. The Claude API caps a turn at a single tool call when disable_parallel_tool_use inside tool_choice is set to true. OpenAI ensures exactly zero or one tool is called when parallel_tool_calls is false. Gemini documents native support for both parallel calling and compositional calling chained across turns.

That one switch changes the shape of the harness considerably.

  • Switched on, latency drops and round trips fall. In exchange the harness has to gather all the results before returning, and has to define what happens when only one of them failed
  • Left on with side-effecting tools exposed, ordering guarantees disappear. When a reader and a writer go out in the same turn, which finishes first is decided by the harness execution strategy
  • Switched off, tracing gets easier and approval flows get simpler. In exchange the same task needs more model calls, which costs money and time
  • The Claude API documentation covers the case where a server tool and a client tool land in the same parallel group. The user message must then contain only result blocks; appending text ends the turn early and produces a 400

The point is not that one setting beats the other. It is that a harness that never made this choice is running on the vendor default, and the defaults are not the same across vendors.

What is really behind we swapped the model

Back to the opening observation. When an agent behaves differently after a model swap, how much of that is the model and where does the harness begin?

Model capability clearly matters. The documentation states that when a required parameter is missing, Claude Opus is much more likely to recognise this and ask for it, whereas Claude Sonnet might ask but might also infer a plausible value. Differences like that are real. What sits on top of them, however, is a difference in contract, and the latter frequently dominates.

  • Tool schema expression - one different line of description changes how often a tool gets selected. If a per-vendor adapter truncates descriptions or flattens schemas, what the model sees changes
  • Forcing level - whether it sits at auto or required is a harness setting, not a model setting. If the adapter maps it differently, the same prompt behaves differently
  • Parallel permission - exactly as in the previous section. Moving between two vendors with different defaults changes the calling pattern itself
  • Error expression - recovery behaviour differs between a harness that signals failure through is_error and one that inlines a bare string
  • Context trimming - if the moment and content of summarisation differ, the whole back half of the run behaves differently
  • System prompt injection - simply attaching tools causes the vendor to insert a system prompt, whose content and size vary by vendor and by setting

In practice this means one thing. Comparing models requires pinning the harness. Numbers taken from two environments with different harnesses and labelled a model comparison leave behind a conclusion that will not reproduce. Where the boundary of machine-checkable verification lies was set out in the line a verification harness draws.

Stop conditions: when nobody decides when to stop

From here on come the items the harness must decide. Leaving them undefined does not mean falling back to a default; it means no limit becomes the implicit default.

The model has no notion of a budget. Each turn, if calling one more tool looks like the plausible move, it does that. That judgement does not take remaining cost or elapsed time as inputs. The only place those get measured is outside.

CeilingWhat it measuresSymptom without itWhat to do when it trips
Maximum stepsModel call round tripsVariations of the same query repeat. The result still looks correctStop, summarise progress so far and hand it to the user
Cost ceilingCumulative input and output tokens, converted to moneyThe invoice is the first notificationStop, or step down to a cheaper model
Wall-clock ceilingReal elapsed time since the session startedThe user is left waiting for a responseEmit partial results and ask whether to continue
Per-tool call countHow many times one tool has been calledThe loop spins inside a single tool while the overall step budget still has roomLock that tool for the session and tell the model
No-progress detectionHow many consecutive calls carried identical argumentsStep counts rise while state stays putReport the repetition in the result so a different path gets tried

The more common problem in practice is not an infinite loop but quiet waste. An agent taking eighty steps over a twenty-step task raises no alarm because the final answer is right. That gap does not surface until a run record is attached. An extreme case of an autonomous agent burning budget is set out in the agent that ran up the bill.

Classifying failure: what to call again and what not to

When a tool fails, the harness has two questions to answer. Call it again? and tell the model? They are independent.

  • Transient failure - network timeout, 502, 429. The harness should retry quietly, with backoff and a retry ceiling, and only tell the model once those are exhausted. Reporting every attempt just burns context
  • Permanent failure - 404, auth rejection, a resource that does not exist. Retrying produces the same answer. Tell the model at once so it can find another path
  • Argument error - schema violation, missing required value, JSON parse failure. The only class the model can actually fix. Return what was missing. The Claude API documentation notes that in this case the model retries with corrections two or three times before apologising to the user
  • Policy denial - approval refused, insufficient permission. Not a retry candidate, and the model should be told. Whether the reason is passed through verbatim is a separate judgement
  • Partial success - three of ten items failed. The hardest to handle. Whether to treat the whole thing as failed, or to commit the successes and report only the failures, varies tool by tool

Skip this classification and it breaks in two directions. Retry everything and an auth failure repeats twenty times; hand everything to the model and one transient 502 sends the whole task off course. Neither is caused by the model being bad.

Idempotency: is this a tool you may call twice

Introducing retries brings a new question. May that tool be called twice? Payments, emails, ticket creation and deployments happen twice when called twice. A first call that ended in a timeout does not mean it did not run. Not receiving a response and not having executed are different things.

MCP provides a place for a tool to declare its own nature: the four fields of ToolAnnotations. The schema's own description, however, is blunt about their standing.

  • readOnlyHint - if true, the tool does not modify its environment. Default false
  • destructiveHint - if true, the tool may perform destructive updates; if false, only additive ones. Meaningful only when readOnlyHint is false. Default true
  • idempotentHint - if true, calling repeatedly with the same arguments has no additional effect. Also meaningful only when readOnlyHint is false. Default false
  • openWorldHint - if true, the tool may interact with an open world of external entities. The schema's own example contrasts a web search tool, whose world is open, with a memory tool, whose world is not. Default true
  • And the decisive sentence: all properties in ToolAnnotations are hints and are not guaranteed to provide a faithful description of tool behaviour. The schema states that clients should never make tool use decisions based on annotations received from untrusted servers

Notice that every default points in the conservative direction. An unannotated tool is to be treated as destructive, non-idempotent and interacting with an open world. And since hints are only hints, retry safety ends up being something the harness has to guarantee on its own side. There are three ways to do it: generate an idempotency key per call and pass it to the tool, check state with a read before retrying, or exclude side-effecting tools from retry altogether. The last is the right answer more often than not.

Approval points: where a person steps in

The MCP specification states, for trust and safety reasons, that there should always be a human in the loop with the ability to deny tool invocations, and asks applications for three things: UI that makes clear which tools are exposed to the model, clear visual indicators when tools are invoked, and confirmation prompts. A separate clause asks that tool inputs be shown to the user before the server is called, to avoid malicious or accidental data exfiltration.

Where to put the approval is a harness policy question. The position is usually one of four.

  • Per tool - certain tools always require approval. Simplest to implement and the most predictable
  • Per argument - the same tool splits on its arguments. Deleting inside a temp directory is automatic, any other path needs approval
  • Cumulative - after N approvals in this session, the rest go through automatically. Reduces approval fatigue at the cost of a blurred boundary
  • Per result - execute, but pause before committing. Only viable for tools that support a dry run

With no approval point at all, irreversible operations execute with no notice. Put one on everything and people start clicking through without reading. The way to grade this on two axes was set out in permission design and where to draw the line, so it is not repeated here. What is worth adding from the harness angle is one thing: where does the state of a session awaiting approval live? Keep it in memory only and a single deployment wipes out everything that was waiting.

Observability: which tool with which arguments

After an incident the questions are fixed. Which tool, with which arguments, at what time, on whose request, and with what result. Only the harness can produce a record that answers them. The model does not remember what it called. It only re-reads what remains in the conversation history.

The MCP specification asks clients to log tool usage for audit purposes and to validate tool results before passing them to the LLM. The minimum set worth keeping looks like this.

  • The call identifier and its matching result - reconstruction after the fact depends on the pairing being intact
  • Tool name and full arguments - keeping only a summary makes the record useless for an investigation. Since arguments can carry sensitive values, a masking rule has to come with it
  • Execution timestamp and duration - without these there is no way to know which tool caused the latency
  • Failure class and retry count - the classification from the previous section has to be recorded for anyone to judge whether the policy was right
  • Token usage and cumulative cost - recorded per step, otherwise there is no telling which stretch was expensive
  • Context edit history - without a record of what was cut away, there is no reconstructing why the model made the judgement it made

The last item is the one most often missing. Summarising and trimming are things the harness does quietly, so they frequently go unlogged, and the result is a system where the same input no longer produces the same run. Dissecting a session in terms of token waste was covered in the agent blackbox analysis, and the production setup for tracking mistakes in the LLM observability field guide.

State and context: what disappears when you trim

Long tasks exceed the context window. What the harness does at that point is trimming. The TrueForge documentation enables this by default and sets the trigger at 80 percent of the model's context length, with a fallback of 50,000 input tokens where that is unknown. The sentence written alongside it matters more: compaction is lossy in the working context, while the full session history remains queryable via the API.

Those two sentences contain the core of state design. What the model sees and what the system stores are different objects. The former is an edit rebuilt on every call; the latter is an append-only record. A harness that treats them as the same thing breaks in one of two directions. With only the edit, nothing can be reconstructed afterwards; with only the record, the window is exceeded and requests fail.

Each trimming strategy loses something different.

  • Drop oldest first - the easiest to implement. What is lost is the early instructions and constraints. The classic symptom of violating the original requirement late in a long task comes from here
  • Replace with a summary - volume drops, but what the summary keeps is decided by yet another model call. Information lost at the summarisation step does not come back
  • Offload large results - write the tool return value to a file and inline only a preview. Loss is small because the model can read it again, but each re-read adds a step
  • Load tool schemas late - give names and descriptions first and fetch schemas on demand. The TrueForge documentation states that this defaults to not preloading
  • Isolate into subagents - run detail work in a separate context and lift only the final result. Handoff loss and coordination cost appear in exchange, and that boundary was covered in the limits of role-split simulation

Whichever route is taken, the model does not know what it has forgotten. Nothing is left to mark the gap. Which is why the trimming policy has to be an observability item.

The loop seen as code

Placing the preceding items on a single flow gives this shape. What follows is not any particular SDK's API but a skeleton written to expose the decision points. Actual field names follow the vendor contracts in the table above.

// Skeleton of a harness loop - the decision points are annotated
async function runAgent(task, tools, limits) {
  const messages = [{ role: 'user', content: task }];
  let steps = 0, spent = 0;
  const startedAt = Date.now();

  while (true) {
    // Decision 1: stop conditions. The model does not measure these
    if (steps >= limits.maxSteps) return stop('MAX_STEPS', messages);
    if (spent >= limits.maxCost) return stop('BUDGET', messages);
    if (Date.now() - startedAt >= limits.maxWallClockMs) return stop('TIMEOUT', messages);

    const res = await model.call({ messages, tools, toolChoice: limits.toolChoice });
    steps += 1;
    spent += estimateCost(res.usage);
    record({ steps, usage: res.usage, stopReason: res.stopReason });  // Decision 6: observability

    // Decision 2: stop_reason branching. One missing branch looks like a hang
    if (res.stopReason === 'end_turn') return finish(res);
    if (res.stopReason === 'refusal') return handleRefusal(res);
    if (res.stopReason === 'max_tokens') return handleTruncated(res);
    if (res.stopReason === 'pause_turn') { messages.push(asAssistant(res)); continue; }

    const calls = res.content.filter((b) => b.type === 'tool_use');
    if (!calls.length) return finish(res);

    // Decision 3: run them in parallel or in sequence
    const results = limits.parallel
      ? await Promise.all(calls.map(execute))
      : await runSequentially(calls, execute);

    messages.push(asAssistant(res));
    messages.push(asToolResults(results));   // result blocks must come first in the array

    // Decision 4: when context hits the threshold, what gets dropped
    if (estimateTokens(messages) >= limits.compactAt) await compact(messages);
  }
}

The part that executes a single tool is where approval and failure classification live. Below, the value returned by classify decides whether to retry, and the idempotency key is what prevents duplicated side effects.

// Tool execution - approval, idempotency and failure classification all meet here
async function execute(call) {
  // Decision 5: the approval point. Show the arguments, then ask
  if (needsApproval(call)) {
    const verdict = await askUser(call.name, call.input);   // pending state goes to durable storage
    if (verdict !== 'allow') return toolError(call.id, 'POLICY_DENIED: refused by the user');
  }

  // Side-effecting tools get a key that is stable across attempts.
  // An unannotated tool is treated as destructive and non-idempotent
  const key = isSideEffecting(call) ? idempotencyKey(call) : null;

  let attempt = 0;
  while (true) {
    try {
      const out = await invoke(call.name, call.input, { key, timeoutMs: TOOL_TIMEOUT_MS });
      return toolResult(call.id, truncateOrOffload(out));   // large results go outside
    } catch (err) {
      const kind = classify(err);   // TRANSIENT / PERMANENT / BAD_ARGS / DENIED
      // Only transient failures are retried quietly. The rest go to the model to judge
      if (kind === 'TRANSIENT' && key && attempt < MAX_RETRY) {
        await backoff(attempt++);
        continue;
      }
      return toolError(call.id, redact(summarize(err, kind)));   // a masked summary, not the raw text
    }
  }
}

Build it or adopt one

A harness looks thin. It looks like one loop and a handful of branches, and the first version really does come together in half a day. The problem is that the items listed above are the harness. Once stop conditions, failure classification, idempotency, approval, observability, context editing and session persistence are all in, it is no longer thin.

AxisConditions favouring building itConditions favouring adopting one
Number of toolsThree or four, fixed, with no plans to growMCP servers will keep being attached
Side effectsEverything is read-onlyWrites, payments and dispatches are mixed in
Run durationIt finishes inside one requestIt has to survive reconnects and restarts
UsersOnly the person who built itSeveral people use it and who did what has to be recorded
VendorsPinned to oneSeveral are in play. An adapter layer is needed regardless
Approval flowNot needed, or everything is automaticPeople intervene mid-run and that state has to survive
Observability demandsStandard output is enoughAudit records and cost breakdowns are required
Operational capacityOne process will doThere is room to run replicas and a database

Two or more matches in the right column and building it costs more than it looks. Conversely, a clean sweep of the left column makes importing someone else's abstraction the losing trade. The isolation problems that appear when several agents are turned loose on one repository sit on a different axis from harness choice, and were covered in collisions and isolation among parallel coding agents.

Returning to the repository that triggered this, the feature list its documentation advertises overlaps almost exactly with the right column above. Sandbox as a tool, subagents, deferred loading of tool schemas, large result offloading, compaction, tool approval, asking clarifying questions, generative UI, plus SQLite in local mode and Postgres with Redis in hosted mode. The README states outright that local mode is for your machine only, has no login by default, and is not a production or internet-facing setup. Whether a sentence like that exists in the documentation is itself material for an adoption decision.

The repository also publishes its own benchmark. Fourteen tasks drawn from DevRev's Enterprise-Bench, run three times per configuration on the same model, the same three MCP servers and the same system prompt, scored by a separate LLM judge, against one closed system and one open source one. That measurement was, however, carried out by the project itself, and no third-party reproduction is presented alongside it. A self-run benchmark is meaningful for publishing its setup, but it is a different object from independent verification.

What could not be established

  • The Gemini function calling documentation presents two different notations. The type reference describes functionCall and functionResponse parts carrying args and response objects, while the guide page reads as function_call and function_result with a call_id. Which is canonical for which SDK version is not resolvable from the documentation alone, so the table above carries the type reference notation
  • Whether Gemini's functionResponse has a dedicated error field was not found in the type reference. The text above says only that the error goes inside the response object
  • The OpenAI documentation has no dedicated field for a tool execution error and states only that the output format is at the caller's discretion. What shape the model was trained to recognise a failure in is not in the documentation, so the effect of any error convention remains something to measure locally
  • Whether the Claude API's default pause_turn limit of 10 can be adjusted per request was not stated in that documentation
  • TrueForge's retry policy, default maximum step count and cost ceiling configuration could not be pinned down from the section titles of the public documentation. What is quoted above is limited to the items where the documentation prints a figure, such as the compaction threshold and the deferred loading default
  • The repository figures are values as of 04:22 UTC on 5 September 2026. What 5,221 stars, roughly 515 commits and roughly 31 contributors imply about operational stability cannot be said from those numbers alone
  • The MCP specification tells clients to implement timeouts for tool calls but offers no recommended value
  • The Claude API table of tool use system prompt token counts varies by model, and what accounts for the differences is not explained in the documentation
