Kubernetes Gateway API로의 전환 - NGINX Ingress Controller 폐기 이후 2026

애너테이션의 시대를 끝내고, 표준 리소스로 트래픽을 다스리다

2026-06-09 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 절반의 클러스터가 흔들리는 사건

2025년 11월, Kubernetes 프로젝트는 한 가지 무거운 발표를 내놓았습니다. 클라우드 네이티브 환경의 약 절반이 의존하던 핵심 인프라, ingress-nginx(NGINX Ingress Controller)가 2026년 3월에 은퇴(retirement)한다는 것입니다. SIG Network와 보안 대응 위원회는 이 프로젝트를 지속 가능하게 만들 추가 인력과 지원을 찾으려 노력했지만 끝내 실패했고, 사용자 안전을 위해 프로젝트를 닫기로 결정했습니다. 공식 발표에 따르면 2026년 3월 이후로는 신규 릴리스도, 버그픽스도, 보안 취약점 패치도 없습니다.

이것은 단순한 라이브러리 하나의 EOL(End-of-Life)이 아닙니다. ingress-nginx는 너무나 많은 곳에서 인터넷과 클러스터 내부를 잇는 관문 역할을 해 왔기 때문에, 그 폐기는 수많은 운영팀에게 '무엇으로 갈아탈 것인가'라는 질문을 동시에 던집니다. 그리고 Kubernetes 프로젝트가 제시한 권장 경로의 중심에는 Gateway API가 있습니다. 이 글은 ingress-nginx 폐기라는 사건을 출발점으로, Ingress가 왜 한계에 부딪혔는지, Gateway API가 그것을 어떻게 표준으로 해결하는지, 그리고 실무에서 어떻게 전환할지를 차분히 정리합니다.

참고: 폐기되는 것은 오픈소스 커뮤니티 프로젝트인 kubernetes/ingress-nginx입니다. F5(구 NGINX Inc.)의 상용 NGINX Ingress Controller는 완전히 별개의 코드베이스로, 자체 수명주기를 따라 계속 유지됩니다. 둘을 혼동하면 잘못된 의사결정을 하기 쉽습니다.

1. Ingress란 무엇이었나 - 그리고 왜 한계에 부딪혔나

먼저 토대를 다지겠습니다. Ingress는 Kubernetes에서 클러스터 외부의 HTTP/HTTPS 트래픽을 내부 서비스로 라우팅하기 위한 표준 리소스였습니다. 호스트 이름과 경로(path)를 기준으로 어떤 서비스로 보낼지를 정의하는, 일종의 L7 라우팅 규칙입니다. 개념 자체는 단순합니다.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ingress
spec:
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80

문제는 이 단순한 스펙이 현실의 요구를 따라가지 못했다는 점입니다. 실무에서는 타임아웃, 리라이트(rewrite), 헤더 조작, 카나리 분배, mTLS, 속도 제한 같은 기능이 필요한데, Ingress 표준 스펙에는 이런 것을 표현할 자리가 없었습니다. 그 결과 각 컨트롤러는 부족한 표현력을 애너테이션(annotation)으로 메웠습니다.

metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$1
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20"

여기서 Ingress의 세 가지 고질병이 드러납니다.

  • 애너테이션 난립: 핵심 라우팅 동작이 표준 스펙이 아니라 컨트롤러별 애너테이션 문자열에 숨습니다. 검증이 어렵고, 오타 하나가 조용히 동작을 망칩니다.
  • 벤더 종속(lock-in): nginx.ingress.kubernetes.io/... 애너테이션은 ingress-nginx 전용입니다. Traefik이나 HAProxy로 바꾸려면 모든 애너테이션을 다시 써야 합니다. '표준'이라는 이름이 무색해집니다.
  • 역할 구분 부재: 호스트·경로·TLS·리라이트가 한 리소스에 뭉쳐 있어, 플랫폼팀과 앱 개발팀이 같은 객체를 건드려야 합니다. 멀티테넌트 환경에서 권한 경계를 긋기 어렵습니다.

ingress-nginx의 보안 부담이 커진 배경에도 이 구조가 있습니다. 애너테이션으로 받은 설정 문자열을 내부적으로 NGINX 설정으로 변환하는 과정은 본질적으로 공격 표면이 넓고, 유지보수 난도도 높습니다. 표준이 표현하지 못하는 것을 우회로 메우다 보니 복잡성이 누적된 셈입니다.

2. Gateway API란 - 표준으로 다시 설계된 트래픽 관문

이 한계를 정면으로 풀기 위해 SIG Network가 설계한 것이 Gateway API입니다. Gateway API는 Ingress의 후속이지만, 단순한 버전 업이 아니라 트래픽 라우팅을 처음부터 다시 모델링한 표준입니다. 핵심 아이디어는 두 가지입니다. 첫째, 실무에서 필요한 기능(헤더·리라이트·트래픽 분배·교차 네임스페이스 라우팅 등)을 애너테이션이 아니라 표준 필드로 표현한다. 둘째, 하나의 거대한 리소스를 역할에 따라 여러 리소스로 분리한다.

가장 중요한 사실은, Gateway API의 핵심 리소스가 이미 v1.0에서 GA(정식, Generally Available)에 도달했다는 점입니다. 공식 문서에 따르면 GatewayClass·Gateway·HTTPRoute는 v1로 graduate 했고, 하위 호환성을 보장하는 안정 API입니다. 즉, 실험 기능이 아니라 프로덕션에 쓸 수 있는 표준입니다.

2.1 세 가지 핵심 리소스

리소스 무엇을 정의하나 비유
GatewayClass 어떤 컨트롤러(구현체)가 트래픽을 처리할지. 클러스터 범위 템플릿. StorageClass와 같은 위치
Gateway 실제 트래픽 진입점 인스턴스. 리스너·포트·프로토콜·TLS를 정의. 로드밸런서 그 자체
HTTPRoute Gateway 리스너에서 백엔드로 가는 HTTP 라우팅 규칙. 경로·헤더 기반 라우팅표

관계는 직관적입니다. 각 Gateway는 하나의 GatewayClass에 연결되어 '누가 이 트래픽을 처리하는가'를 정하고, HTTPRoute 같은 라우팅 리소스가 Gateway에 붙어 '어떻게 라우팅할 것인가'를 정합니다. HTTP뿐 아니라 TCPRoute·TLSRoute·GRPCRoute 같은 형제 리소스도 있어, 프로토콜별로 표준 라우팅을 표현할 수 있습니다.

2.2 같은 일을 Gateway API로 표현하면

# 1) 클러스터 운영자: 트래픽 진입점 정의
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
spec:
  gatewayClassName: envoy        # 어떤 구현이 처리할지
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls:
      mode: Terminate
      certificateRefs:
      - name: shop-tls
---
# 2) 앱 개발자: 라우팅 규칙 정의 (애너테이션 없이 표준 필드로)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-route
spec:
  parentRefs:
  - name: shop-gateway
  hostnames:
  - "shop.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    filters:
    - type: URLRewrite        # 표준 필터: 애너테이션 불필요
      urlRewrite:
        path:
          type: ReplacePrefixMatch
          replacePrefixMatch: /
    backendRefs:
    - name: api-svc
      port: 80

차이가 보입니까? 리라이트가 nginx.ingress.kubernetes.io/rewrite-target이라는 벤더 전용 문자열이 아니라, filters 안의 표준 URLRewrite 필터로 표현됩니다. 이 매니페스트는 Envoy Gateway에서도, Istio에서도, NGINX Gateway Fabric에서도 동일하게 동작합니다. 구현을 바꿔도 라우팅 정의는 그대로입니다.

3. 역할 분리(Role-Oriented) - Gateway API의 진짜 혁신

Gateway API의 가장 깊은 변화는 기능 추가가 아니라 역할 분리입니다. 공식 설계 문서는 Kubernetes 네트워킹에 관여하는 조직의 실제 역할에 맞춰 리소스를 나눕니다.

  • 인프라 프로바이더(Infrastructure Provider): 클라우드 사업자나 플랫폼 제공자가 GatewayClass를 배포합니다. 클러스터 범위 리소스로, 거기서 파생되는 Gateway의 동작을 정의하는 템플릿입니다.
  • 클러스터 운영자(Cluster Operator): GatewayClass를 이용해 Gateway를 띄우고, '트래픽이 어디로 어떻게 들어오는가'를 정의합니다. 포트·TLS·리스너가 이들의 책임입니다.
  • 애플리케이션 개발자(Application Developer): HTTPRoute로 '내 서비스로 트래픽을 어떻게 라우팅할지'만 정의합니다. 인프라 세부 사항은 몰라도 됩니다.

이 분리가 왜 중요할까요? Ingress에서는 TLS 인증서 설정과 앱 라우팅 규칙이 한 객체에 섞여 있어, 앱 개발자가 인프라를 건드리거나 반대로 플랫폼팀이 모든 라우팅을 떠안아야 했습니다. Gateway API에서는 플랫폼팀이 Gateway(진입점·TLS)를 관리하고, 각 팀이 자기 HTTPRoute만 관리합니다. 멀티테넌트 환경에서 안전한 권한 경계가 리소스 모델 자체에 새겨진 것입니다. 이 구조는 플랫폼 엔지니어링의 '셀프서비스, 안전한 가드레일' 철학과 정확히 맞물립니다. 더 넓은 맥락은 플랫폼 엔지니어링 완전 가이드 2026에서 다룹니다.

4. 왜 '표준화'가 중요한가

Gateway API의 가치를 한 단어로 누르면 이식성(portability)입니다. 표준이 표현력을 갖추면, 라우팅 의도가 특정 벤더의 애너테이션 사전에 종속되지 않습니다. 이는 세 가지 실질적 이득으로 이어집니다.

  1. 벤더 교체 비용 급감: GatewayClass의 controllerName만 바꾸면 같은 HTTPRoute로 다른 구현 위에서 동작합니다. 이번 ingress-nginx 폐기 같은 사건이 다시 와도, 표준 위에 있으면 충격이 작습니다.
  2. 검증 가능성: 라우팅이 강타입(typed) 필드로 표현되므로, kubectl·CI에서 스키마 검증이 가능합니다. 애너테이션 오타로 인한 조용한 장애가 줄어듭니다.
  3. 생태계 집중: 모든 구현이 같은 표준을 향해 적합성(conformance) 테스트를 통과하려 경쟁하므로, 기능 혁신이 분산되지 않고 표준 위에 쌓입니다.

요컨대 표준화는 '하나의 구현을 강요'하는 것이 아니라, 여러 구현이 호환되는 공통 언어를 만드는 것입니다. 이것이 Ingress의 애너테이션 바벨탑과 근본적으로 다른 지점입니다.

5. 주요 Gateway API 구현 - 무엇을 선택할까

표준이 하나여도 구현은 여럿입니다. 2026년 기준 주요 구현과 성격을 정리합니다. 중요한 전제는, 어떤 것을 골라도 매니페스트(HTTPRoute 등)는 대부분 재사용된다는 점입니다.

구현 데이터플레인 강점 적합한 경우
Envoy Gateway Envoy 높은 적합성·빠른 기능 속도, Envoy 네이티브 L7 기능을 폭넓게 쓰는 일반적 선택
Istio Envoy(Ambient) 서비스 메시 통합, ms 단위 설정 전파 이미 메시를 쓰거나 mTLS·트래픽 정책이 핵심
Cilium eBPF L4 처리량 최강, 커널 오버헤드 회피 CNI로 Cilium을 쓰고 L4 성능이 중요
NGINX Gateway Fabric NGINX ingress-nginx 사용자에게 친숙, Go 컨트롤 플레인 NGINX 기반에서 가장 가까운 이전 경로
Kong Kong/NGINX API 게이트웨이 기능, 빠른 설정 전파 API 관리·플러그인 생태계가 필요

최근 업계 분석에서는 'Envoy 네이티브' 생태계(Envoy Gateway·Istio Ambient)가 가장 높은 적합성과 기능 속도를 보이며 사실상 지배적 패턴으로 자리 잡고 있다고 평가합니다. L4 처리량이 절대적으로 중요하다면 eBPF 데이터플레인을 가진 Cilium이 두드러집니다. 한편 ingress-nginx에서 출발하는 팀에게는, NGINX 컨트롤 플레인을 Go로 새로 작성해 Gateway API를 네이티브로 말하도록 만든 NGINX Gateway Fabric이 심리적·기술적 거리가 가장 가깝습니다.

6. 마이그레이션 - ingress2gateway와 단계적 전환

가장 현실적인 질문으로 들어갑니다. '이미 수십 개의 Ingress가 도는데 어떻게 옮기나?' 다행히 SIG가 공식 변환 도구를 제공합니다.

6.1 ingress2gateway

ingress2gateway는 기존 Ingress 리소스를 읽어 Gateway·HTTPRoute로 자동 변환하는 Kubernetes SIG 프로젝트입니다. NGINX·Istio·Kong·Apisix·GCE 등 여러 프로바이더의 프로바이더별 애너테이션 처리를 지원합니다. 복잡한 Ingress 규칙과 애너테이션을 손으로 번역하는 것은 오류가 잦은 작업인데, 이 도구가 그 과정을 자동화합니다.

# 클러스터의 모든 Ingress를 읽어 Gateway API 리소스로 출력
ingress2gateway print --input-file=ingress.yaml --providers=ingress-nginx

# 결과(개념적): Gateway + HTTPRoute YAML이 생성됨
# → 그대로 적용하지 말고 반드시 검토할 것 (자동 변환은 '초안')

핵심 주의: 자동 변환 결과는 초안입니다. 표준 필드로 깔끔히 매핑되는 규칙도 있지만, 벤더 전용 애너테이션 중에는 표준에 1:1 대응이 없는 것도 있습니다. 변환 후 차이를 검토하고, 필요하면 구현체별 확장(예: Envoy Gateway의 정책 리소스)으로 보완해야 합니다.

6.2 단계적 전환 로드맵

  1. 인벤토리 파악: 클러스터의 모든 Ingress와, 거기 붙은 애너테이션을 목록화합니다. 어떤 애너테이션이 표준으로 매핑되는지부터 확인합니다.
  2. 구현 선택·설치: 위 비교를 토대로 Gateway API 구현을 고르고, 기존 ingress-nginx와 병행 설치합니다. 한 번에 갈아엎지 않습니다.
  3. 변환 초안 생성: ingress2gateway로 Gateway·HTTPRoute 초안을 만들고 검토·보정합니다.
  4. 비핵심부터 이전: 트래픽이 적거나 위험이 낮은 서비스를 먼저 새 Gateway로 옮겨 동작을 검증합니다.
  5. 트래픽 점진 이전: DNS 가중치·카나리·블루그린으로 트래픽을 단계적으로 새 경로로 옮깁니다. 문제가 생기면 즉시 되돌립니다.
  6. ingress-nginx 제거: 모든 라우팅이 검증되면 구 컨트롤러를 내립니다.

이 점진적 태도는 신뢰성 운영의 기본 원칙과 같습니다. '한 번에 전면 전환'은 가장 빠른 경로처럼 보이지만 가장 위험합니다. 자동화·전환에 항상 롤백 경로를 두는 사고방식은 SRE에서의 AI - 신뢰성 있는 운영의 미래에서 다룬 원칙과 정확히 맞닿아 있습니다.

7. 마이그레이션 시 고려사항 - 함정 점검

전환을 매끄럽게 하려면 몇 가지 함정을 미리 알아야 합니다.

  • 표준에 1:1 대응 없는 애너테이션: 세밀한 NGINX 튜닝(특수 타임아웃, 커스텀 설정 스니펫)은 표준 필드로 다 표현되지 않을 수 있습니다. 구현체별 확장 정책으로 메우되, 그 부분은 다시 벤더 종속이 생긴다는 점을 인지하세요.
  • TLS·인증서 관리 모델 변화: Ingress의 TLS 블록이 Gateway의 리스너 단위 certificateRefs로 이동합니다. cert-manager 연동 방식도 점검해야 합니다.
  • 교차 네임스페이스 라우팅: Gateway API는 ReferenceGrant로 네임스페이스 간 참조를 명시적으로 허용합니다. 보안상 강력하지만, 처음엔 '왜 연결이 안 되지?'의 원인이 되곤 합니다.
  • 구현별 적합성 차이: 모든 구현이 표준의 모든 기능을 100% 지원하지는 않습니다. 쓰려는 기능이 선택한 구현의 적합성(conformance) 범위 안인지 확인하세요. Gateway API v1.5 리뷰 과정에서는 갱신이 멈춘 구현은 목록에서 제외될 예정입니다.
  • 관측성·메트릭 재구성: ingress-nginx 메트릭에 맞춰진 대시보드·알림은 새 데이터플레인(Envoy 등)에 맞춰 다시 짜야 합니다.

8. 한국 인프라 환경에서의 시사점

이 흐름을 국내 운영 현실에 대입하면 몇 가지 실질적 포인트가 보입니다.

  • 관리형 쿠버네티스 사용자: 국내 클라우드(NHN·NAVER·KT 등)와 글로벌 관리형 K8s를 쓰는 팀이라면, 해당 플랫폼이 어떤 GatewayClass를 기본 제공하는지부터 확인하는 것이 출발점입니다. 인프라 프로바이더가 GatewayClass를 깔아 주면 운영팀의 부담이 줄어듭니다.
  • 금융·통신의 보안 요건: 인터넷 노출 클러스터에서 2026년 3월 이후 보안 패치가 끊긴 컨트롤러를 유지하는 것은 규제·감사 관점에서 리스크입니다. 마이그레이션 우선순위를 높여야 합니다.
  • 소규모 운영 인력: 인프라 엔지니어가 여러 역할을 겸하는 국내 다수 조직에서는, 역할 분리가 곧 '운영 부담의 위임'으로 이어집니다. 앱팀이 HTTPRoute를 셀프서비스로 관리하면 플랫폼팀의 병목이 줄어듭니다.
  • 점진 전환 문화: 무중단이 생명인 국내 대형 서비스 특성상, 카나리·병행 운영을 전제로 한 단계적 전환이 사실상 유일한 안전한 길입니다.

9. 자주 하는 오해 바로잡기

9.1 "Ingress가 당장 죽는다"

아닙니다. 죽는 것은 오픈소스 ingress-nginx 컨트롤러입니다. Ingress 리소스(networking.k8s.io/v1) 자체는 Kubernetes에 남아 있고, 다른 Ingress 컨트롤러도 존재합니다. 다만 미래는 Gateway API로 향합니다.

9.2 "Gateway API는 아직 실험 단계다"

아닙니다. 핵심 리소스(GatewayClass·Gateway·HTTPRoute)는 v1.0에서 GA에 도달한 안정 API입니다. 프로덕션에 쓸 수 있습니다.

9.3 "F5 NGINX 상용 제품도 끝난다"

아닙니다. 폐기되는 건 커뮤니티 프로젝트뿐입니다. F5의 상용 NGINX Ingress Controller는 별개로 유지됩니다.

9.4 "구현을 잘못 고르면 처음부터 다시"

대체로 아닙니다. 표준 리소스를 쓰는 한 HTTPRoute 등 라우팅 정의는 대부분 재사용됩니다. 구현 교체 비용은 Ingress 시절보다 훨씬 작습니다.

10. 결론 + 즉시 적용 가능한 3가지

ingress-nginx의 폐기는 위기처럼 보이지만, 더 정확히는 미뤄 온 표준화를 강제하는 전환점입니다. Ingress는 애너테이션이라는 우회로로 10년을 버텼고, 그 우회로가 벤더 종속·검증 불가·보안 부담으로 한계에 다다랐습니다. Gateway API는 같은 문제를 애너테이션이 아니라 표준 필드와 역할 분리로 푸는, 처음부터 다시 설계된 답입니다. 핵심 리소스는 이미 GA이고, 구현은 여럿이며, 어떤 것을 골라도 표준 위에서는 매니페스트가 재사용됩니다.

당장 적용할 수 있는 세 가지로 마무리합니다.

  1. 먼저 인벤토리를 떠라. 클러스터의 모든 Ingress와 애너테이션을 목록화하고, 인터넷에 노출된 것부터 우선순위를 매기세요. 무엇을 옮겨야 하는지 모르면 전환 계획도 세울 수 없습니다.
  2. ingress2gateway로 초안을 만들어라. 손으로 번역하지 말고 SIG 공식 도구로 변환 초안을 뽑은 뒤 검토하세요. 표준에 매핑되지 않는 애너테이션이 어디인지 보이면 절반은 끝난 것입니다.
  3. 병행 운영으로 점진 전환하라. 새 구현을 ingress-nginx와 나란히 띄우고, 비핵심 서비스부터 카나리로 옮겨 검증하세요. 롤백 경로를 항상 열어 두는 것이 무중단 전환의 핵심입니다.

마지막 한 줄로 요약하면 이렇습니다. "폐기된 것은 하나의 컨트롤러일 뿐, 옮겨야 할 곳은 특정 벤더가 아니라 표준이다." ingress-nginx 다음을 고민하는 모든 팀에게, Gateway API는 단순한 대체재가 아니라 '다음에 또 올 폐기'에 흔들리지 않는 토대입니다.
