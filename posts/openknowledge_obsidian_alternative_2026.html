OpenKnowledge — Obsidian·Notion의 오픈소스 AI 우선 대안

AI 에이전트와 함께 지식 베이스를 공동 작성하는 새로운 PKM 패러다임 — 로컬·오픈소스·데이터 소유권의 가치를 분석한다

2026-06-28 IT/기술

서론: PKM 시장에 새 각도가 등장했다

개인 지식 관리(PKM, Personal Knowledge Management) 도구 시장은 오랫동안 두 극단으로 나뉘어 있었다. 한쪽에는 Obsidian — 로컬 마크다운 파일 기반의 강력한 플러그인 생태계를 자랑하는 로컬 퍼스트 도구. 다른 쪽에는 Notion — 팀 협업과 데이터베이스 기능이 탁월하지만 데이터는 전적으로 클라우드에 머무는 SaaS. 2026년 6월, 이 구도에 새로운 선택지가 나타났다. OpenKnowledge다.

OpenKnowledge는 Inkeep이 공개한 오픈소스 AI 우선(AI-first) 지식 관리 IDE로, Hacker News의 Show HN 코너에 등장해 38포인트를 받으며 주목받았다. 한국어 기술 커뮤니티 GeekNews에도 같은 날 소개됐다. 핵심 주장은 단순하지만 야심차다. "마크다운 파일을 기반으로, AI 에이전트와 함께 지식 베이스를 공동 작성한다." 이 글은 공개 발표 자료와 공식 문서, 커뮤니티 반응을 교차 검증해 OpenKnowledge가 실제로 무엇이며, 기존 도구 대비 어디서 진짜 차별점을 갖는지, 그리고 누구에게 맞는지 정직하게 분석한다.

미리 단서를 분명히 한다. 이 글을 쓰는 2026년 6월 기준으로 OpenKnowledge는 초기 공개 단계다. 공식 문서와 Show HN 댓글, 그리고 설치 가능한 CLI·macOS 앱을 통해 확인한 기능 범위 내에서만 판단한다. 아직 검증되지 않은 로드맵 주장은 "예정" 또는 "계획"으로 명확히 구분한다.

1. OpenKnowledge란 무엇인가 — 3계층 구조

공식 문서는 OpenKnowledge를 "에이전트와 협력해 마크다운 기반 지식 베이스와 문서를 공동 작성하는 IDE"로 정의한다. 핵심은 3계층 구조다.

1.1 1계층: WYSIWYG 마크다운 편집기

편집기는 "Google Docs처럼" 마크다운을 편집하면서 결과를 즉시 볼 수 있는 WYSIWYG 방식이다. 소스 모드와 시각적 모드 전환을 지원한다. 단순 텍스트 외에 인터랙티브 HTML, Mermaid 다이어그램, LaTeX 수식, 비디오, PDF 임베드를 지원한다. 우측 패널에서는 문서 구조 개요, 링크 관계 그래프, 편집 타임라인을 확인할 수 있다. 위키 링크와 그래프 시각화도 내장한다.

여기서 Obsidian과 비교하면 흥미롭다. Obsidian의 WYSIWYG 기능은 Live Preview 플러그인으로 충분히 구현됐지만, 기본적으로 "편집기 위에 Obsidian을 얹는" 구조다. OpenKnowledge는 처음부터 WYSIWYG를 기본값으로 설계했다. 차이는 미묘하지만, 진입 장벽에서 체감된다.

1.2 2계층: AI 에이전트 도구 레이어

이것이 OpenKnowledge의 핵심 차별점이다. MCP(Model Context Protocol)와 스킬 레이어를 내장해 Claude Code, Cursor, Codex, OpenCode 등의 AI 에이전트가 지식 베이스를 직접 읽고, 검색하고, 수정할 수 있다. 편집기 내 Composer에서 "Large Language Model에 대한 지식 베이스를 만들어줘"라고 입력하면 선택한 에이전트가 마크다운 파일을 자동 생성·편집한다. 에이전트의 모든 도구 호출을 사전 승인하는 자동 승인 모드도 제공한다.

이는 플러그인으로 AI를 얹는 Obsidian의 Smart Connections, Claudian, Cortex 같은 접근 방식과 본질적으로 다르다. OpenKnowledge에서는 AI 협업이 플러그인이 아니라 기본 작업 흐름이다. MCP는 표준 프로토콜이어서 지원 에이전트가 늘어날수록 자동으로 호환 범위가 넓어지는 구조다.

1.3 3계층: 마크다운 + Git

모든 콘텐츠의 실체는 평문 마크다운(.md) 또는 MDX 파일이다. 이 파일들은 Git으로 버전 관리된다. GitHub 자동 동기화로 팀 공유와 백업이 가능하다. 이 구조의 의미는 크다. OpenKnowledge가 사라지더라도 파일은 남는다. 어느 텍스트 편집기에서도 열리고, 어느 버전 관리 시스템에서도 관리된다. 벤더 종속이 없다.

2. 기존 PKM 도구의 한계 — 왜 새로운 접근이 필요했나

OpenKnowledge가 나온 맥락을 이해하려면 기존 도구들이 2026년 시점에서 어디서 벽에 부딪히는지 봐야 한다.

2.1 Obsidian의 딜레마

Obsidian은 2026년 기준 4,350개 이상의 커뮤니티 플러그인을 보유하며, 로컬 퍼스트·데이터 소유권·마크다운 표준이라는 세 가지 가치에서 탁월하다. 2026년 Bases 기능이 추가되며 Notion 스타일의 데이터베이스 뷰도 오프라인에서 사용할 수 있게 됐다. Ollama를 통한 로컬 LLM 통합도 가능하다.

그러나 한계도 명확하다. AI 통합의 파편화가 가장 큰 문제다. AI 기능을 쓰려면 플러그인을 골라 설치하고, 각각의 API 키를 설정하고, 기능이 충돌하지 않도록 관리해야 한다. 하나의 일관된 AI 협업 경험이 없다. 또한 실시간 팀 협업이 기본적으로 지원되지 않으며, 지식 관리에 일관성 있는 구조를 유지하려면 상당한 "의사결정 피로(decision fatigue)"가 쌓인다.

2.2 Notion의 데이터 통제 문제

Notion은 팀 협업과 비기술 사용자 진입성에서 Obsidian을 앞선다. 그러나 모든 데이터가 Notion 서버에 저장된다는 사실은, 특히 기술 문서나 내부 지식 베이스를 다루는 팀에게 중요한 제약이다. Notion AI($10/월 애드온)는 편리하지만 데이터가 외부 AI 처리 서버를 거친다. 자체 호스팅 경로가 없으며, 보안 요건이 강한 환경에서는 구조적으로 막힌다. 오픈소스 Notion 대안(AppFlowy, AFFiNE, Anytype 등)이 주목받는 것도 이 맥락이다.

2.3 AI 우선 시대의 요구

2026년의 지식 작업은 사람이 혼자 정보를 정리하고 연결하는 것만을 의미하지 않는다. Claude Code나 Cursor 같은 AI 에이전트가 코드와 문서를 함께 다루고, 그 결과물이 팀의 지식 베이스에 자동으로 반영되는 흐름이 현실화되고 있다. 기존 도구들은 이 흐름에 뒤늦게 AI를 얹고 있지만, 처음부터 이 흐름을 전제로 설계된 도구는 없었다. OpenKnowledge는 그 빈자리를 노린다.

3. OpenKnowledge의 실제 강점

확인된 자료 기준으로 OpenKnowledge가 실제로 강한 부분은 세 가지다.

3.1 AI 에이전트 협업의 기본 내장

Claude Code, Cursor, Codex, OpenCode를 별도 설정 없이 지식 베이스 작업 파트너로 끌어들일 수 있다는 것은, AI 에이전트를 이미 쓰는 사람에게 즉각적인 가치다. 기술 문서를 작성하면서 에이전트가 관련 섹션을 자동으로 생성하거나, LLM 위키를 에이전트가 유지하게 하는 것이 기본 사용 시나리오다. Hacker News 댓글에서도 이 부분이 가장 관심을 끌었다.

3.2 데이터 소유권과 벤더 독립성

파일이 로컬 마크다운이고, Git으로 버전이 관리되고, 라이선스가 GPL v3인 조합은 강력한 데이터 주권을 보장한다. Notion처럼 SaaS가 사라지면 데이터 접근이 어려워지는 상황이 구조적으로 발생하지 않는다. 마크다운이라면 어느 에디터에서든 열리고, Git 히스토리는 사라지지 않는다. 오픈소스이므로 원한다면 직접 호스팅하거나 포크할 수 있다.

3.3 풍부한 콘텐츠 표현

단순 텍스트를 넘어 Mermaid 다이어그램, LaTeX, 인터랙티브 HTML, PDF, 비디오를 하나의 문서에 담을 수 있다. 엔지니어링 스펙, 연구 노트, 기술 가이드처럼 다양한 미디어가 섞이는 문서에 특히 유용하다. 기술 팀의 내부 위키나 설계 문서용으로 적합한 표현력이다.

4. 한계와 솔직한 단점

초기 단계 도구를 과장 없이 평가하려면 한계를 명확히 짚어야 한다.

4.1 생태계 성숙도

Obsidian의 4,350개 플러그인, Notion의 수천 개 통합과 비교하면 OpenKnowledge는 아직 맨 처음이다. 특수한 필요(예: 특정 API 연동, Excalidraw, 고급 태깅 시스템)는 OpenKnowledge에서 아직 지원하지 않을 가능성이 높다. Hacker News 댓글에서도 TypeScript 플러그인 지원, Excalidraw·Mermaid 통합, 안드로이드 앱 요청이 이어졌다. 개발팀이 로컬 모델 지원, 댓글 기능, 더 깊은 AI 통합을 로드맵에 올렸지만, 2026년 6월 기준 아직 구현 전이다.

4.2 실시간 팀 협업의 부재

GitHub 자동 동기화를 통해 팀 공유가 가능하지만, Notion 또는 Google Docs처럼 여러 명이 동시에 같은 문서를 편집하는 실시간 협업은 현재 지원하지 않는다. 개발 팀의 기술 위키 용도로는 충분하지만, 마케팅이나 기획처럼 실시간 공동 작성이 필수인 팀에게는 아직 제한적이다.

4.3 비기술 사용자 진입 장벽

설치 방법부터 npm install -g @inkeep/open-knowledge로 시작하는 CLI 기반이다. Node.js 24 이상 또는 macOS M1 이상이 요구된다. 마크다운, Git, AI 에이전트에 익숙하지 않은 사용자에게는 초기 세팅이 상당한 장벽이다. Obsidian이 비기술 사용자에게도 설치 후 바로 시작할 수 있는 것과 대비된다.

4.4 로컬 모델 미지원(현재)

현재 Claude Code, Cursor, Codex 같은 클라우드 기반 AI 에이전트와 연동하는 구조다. 완전 오프라인·에어갭 환경에서 로컬 LLM을 쓰고 싶은 사용자에게는 아직 답이 없다. 개발팀이 로컬 모델 지원을 예정했지만, 구현 시점은 미확인이다.

5. 경쟁 구도 — PKM 도구 시장에서의 위치

OpenKnowledge가 들어선 시장은 이미 선택지가 많다. 좌표를 정리하면 다음과 같다.

OpenKnowledge의 위치는 명확하다. Obsidian처럼 로컬 퍼스트지만, AI 에이전트 통합이 플러그인이 아닌 기본 설계다. Notion처럼 AI 통합을 내장했지만, 클라우드가 아닌 로컬 마크다운 파일이 실체다. 이 교차점이 OpenKnowledge가 만든 새 공간이다.

6. 데이터 소유권과 오픈소스의 실질적 가치

OpenKnowledge를 둘러싼 논의에서 가장 중요한 가치는 데이터 소유권과 오픈소스의 결합이다. 이 둘이 단순히 마케팅 문구가 아닌 이유를 짚어보자.

6.1 데이터는 어디에 있는가

Notion을 쓴다는 것은 회사의 모든 지식 — 회의록, 설계 문서, 고객 정보 — 이 Notion 서버에 있다는 뜻이다. Notion이 조항을 변경하거나 서비스를 종료하거나 침해 사고가 발생했을 때, 선택지가 제한된다. OpenKnowledge는 파일이 본인 기기의 디렉토리에 마크다운으로 존재한다. 데이터에 대한 통제권이 구조적으로 사용자 손에 있다.

6.2 GPL v3의 의미

라이선스가 GPL v3이라는 것은 소스 코드를 볼 수 있고, 수정할 수 있고, 자신의 환경에 맞게 포크할 수 있다는 뜻이다. 단, GPL의 copyleft 특성상 수정 배포 시 동일 라이선스 적용 의무가 있다. 상업적 사용이나 내부 커스터마이즈 용도라면 라이선스 조건을 사전 확인해야 한다. MIT보다 강한 copyleft는 기업 환경에서 주의가 필요한 지점이다.

6.3 AI 시대의 데이터 소유권

AI 에이전트가 지식 베이스를 읽고 생성하는 세계에서, 그 지식 베이스가 어디에 있는지는 더 큰 의미를 갖는다. Notion AI는 Notion의 데이터 파이프라인을 거쳐 AI 처리가 이뤄진다. OpenKnowledge는 Claude Code 같은 에이전트가 로컬 파일을 직접 읽는다. 데이터가 어느 서버로도 나가지 않고 AI 협업이 가능하다는 것은, 특히 민감한 내부 지식을 다루는 팀에게 구조적 차이다.

7. AI가 PKM을 바꾸는 방식 — OpenKnowledge의 시사점

OpenKnowledge의 등장은 단순히 새 도구 하나의 출시가 아니라, PKM이 어떻게 변하고 있는지를 보여주는 신호다.

7.1 지식 관리의 단위가 바뀐다

전통적 PKM은 사람이 정보를 포착하고, 분류하고, 연결하는 작업이었다. OpenKnowledge가 제안하는 모델은 다르다. AI 에이전트가 지식 베이스를 유지·업데이트하고, 사람은 방향을 잡고 검증하는 역할을 한다. "LLM 위키를 에이전트가 관리하게 하라"는 공식 퀵스타트의 예시는 이 전환을 직접적으로 표현한다.

7.2 에이전트와 지식의 결합

MCP를 통해 AI 에이전트가 지식 베이스를 검색·발견하는 기능(agentic search)은 단순히 AI가 노트를 요약하는 것과 다르다. 에이전트가 지식 베이스를 능동적으로 탐색해 관련 정보를 연결하고, 빈 곳을 채우고, 일관성을 유지하는 것을 목표로 한다. 이는 지식 그래프와 RAG(검색 증강 생성)을 사람의 작업 흐름에 통합하는 방향이다.

7.3 코딩과 지식 관리의 경계 소멸

OpenKnowledge가 Claude Code, Cursor, Codex 같은 코딩 에이전트와 연동하는 것은 우연이 아니다. 코드 작업과 지식 작업이 분리되어 있지 않다는 인식이 있다. 코드를 짜면서 설계 문서가 자동으로 생성되고, 에이전트가 작성한 코드와 그 맥락이 함께 지식 베이스에 기록되는 흐름은 개발팀의 실제 필요에 맞닿아 있다.

8. 누구에게 맞는가 — 도구 선택 가이드

모든 도구가 모든 사람에게 맞지 않는다. OpenKnowledge의 현재 상태 기준으로 솔직한 선택 가이드를 제시한다.

8.1 OpenKnowledge가 잘 맞는 대상

  • Claude Code, Cursor, Codex 등의 AI 에이전트를 이미 일상 도구로 쓰는 개발자
  • 팀 내부 기술 위키·엔지니어링 스펙을 Git으로 관리하고 싶은 기술 팀
  • 데이터가 외부 서버에 나가는 것에 민감한 보안·규제 환경 사용자
  • 마크다운·Git에 익숙하며 AI와 함께 지식 베이스를 자동화하고 싶은 사람
  • 오픈소스 코드를 직접 확인하거나 수정할 의향이 있는 사용자

8.2 아직 Obsidian 또는 Notion이 더 나은 대상

  • 방대한 플러그인 생태계와 커뮤니티가 필요한 Obsidian 파워유저
  • 비기술 팀원이 섞인 환경에서 진입 장벽 없는 실시간 협업이 필요한 팀
  • 데이터베이스 뷰, 칸반, 캘린더 같은 Notion의 구조화된 기능이 핵심인 사용자
  • 로컬 LLM을 에어갭 환경에서 쓰고 싶은 사용자(로컬 모델 지원 전까지)

9. 결론 — 아직 초기지만 방향이 옳다

OpenKnowledge는 2026년 6월 기준 초기 공개 단계의 도구다. 생태계 성숙도, 실시간 협업, 로컬 모델 미지원 같은 한계는 지금 당장 한계다. 이것을 부정하면 정직하지 않다.

그러나 방향은 정확하다. AI 에이전트 통합을 플러그인이 아닌 설계 중심으로 내장하고, 데이터를 로컬 마크다운 + Git에 두어 벤더 종속을 없애고, MCP를 통해 표준적으로 에이전트와 연결한다. 이 세 가지 선택은 "AI 에이전트와 함께 일하는 2026년"의 지식 관리가 어디로 가야 하는지를 잘 포착한다.

본인의 판단을 정리하면 이렇다. Obsidian과 Notion은 여전히 각자의 영역에서 성숙한 도구이며, 지금 당장 갈아타야 할 이유는 없다. 그러나 AI 에이전트를 이미 코딩·문서 작업의 파트너로 쓰고 있고, 그 작업의 결과물을 오픈소스·로컬 기반 지식 베이스로 쌓고 싶다면, OpenKnowledge는 지금 가장 직접적인 선택지다. 빠른 성장 속도와 MCP 표준 기반 확장성을 보면, 6개월~1년 후의 완성도는 지금과 꽤 다를 수 있다.

도구를 선택하기 전에 실제로 설치하고 써보라. CLI 한 줄(npm install -g @inkeep/open-knowledge)이면 시작할 수 있다. 본인 프로젝트의 기술 위키 하나를 AI 에이전트와 함께 만들어보면, 이 도구가 본인의 작업 흐름에 맞는지 스스로 판단할 수 있다.
