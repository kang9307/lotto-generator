OpenAI Codex Record & Replay — 관찰한 작업을 재사용 스킬로 바꾸다

매번 같은 프롬프트를 반복하는 비효율을 줄이고 에이전트를 학습시키는 새로운 패러다임, 그 실체와 한계를 분석한다

2026-06-24 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: "설명보다 보여주는 게 빠른" 자동화의 새 접근

2026년 6월 18일, OpenAI는 Codex 앱에 Record & Replay 기능을 추가했다. 핵심 아이디어는 단순하다. 사용자가 Mac에서 반복하는 작업을 한 번 "보여주면" Codex가 그 흐름을 관찰해 재사용 가능한 스킬(Skill)로 만든다. 이후부터는 같은 일을 하고 싶을 때 자연어 한 줄로 에이전트를 호출하면 된다.

이 글은 보도자료를 옮기지 않는다. Record & Replay가 구체적으로 무엇을 하는지, 왜 지금 나왔는지, 그리고 가장 중요하게는 어디가 한계인지를 2026년 6월 기준 확인된 정보 범위 안에서 분석한다. "에이전트가 사용자의 워크플로를 학습한다"는 말이 근사하게 들리지만, 실체는 그보다 구체적이고 또 그보다 제한적이다.

먼저 단서를 박는다. 이 기능은 macOS 전용이고 Computer Use를 활성화해야 쓸 수 있다. EU·영국·스위스에서는 출시 시점에 제공되지 않았다. 이 맥락을 이해하면 기능의 성격이 훨씬 명확해진다.

1. Record & Replay의 실체 — 3단계 흐름

공식 문서와 출시 보도를 교차 검증한 작동 방식은 세 단계다.

1.1 녹화(Record) 단계

Codex 앱의 Plugins 메뉴에서 +를 누르고 Record a skill을 선택한다. 이때 macOS 접근성 권한과 화면 녹화 권한을 요청한다. 초기 사용자들이 "화면 인식만이 아니라 접근성 요소 권한까지 달라고 한다"고 지적했는데, 이는 Codex가 단순 픽셀 캡처가 아니라 UI 요소 트리까지 읽기 때문이다. 화면 좌표보다 버튼 ID나 DOM 요소를 파악하면 레이아웃 변경에 더 강하게 대응할 수 있다.

권한 승인 후 사용자는 실제 작업을 수행한다. 경비 청구서를 제출하거나, 특정 형식의 GitHub 이슈를 만들거나, 매주 받아야 하는 보고서를 다운로드하는 식이다. 완료되면 녹화를 중지한다.

1.2 스킬 생성(Capture & Draft) 단계

Codex는 녹화된 동작을 분석해 SKILL.md 파일을 자동 생성한다. 이 파일은 마크다운 형식으로 작성된 지침이며, 다음 항목을 포함한다.

  • 이 스킬을 언제 써야 하는지(트리거 설명)
  • 필요한 입력 변수(날짜, 파일명, 금액 등)
  • 수행해야 할 단계별 절차
  • 완료 여부를 확인하는 검증 방법

중요한 점은 이 파일이 편집 가능하다는 것이다. 자동 생성된 스킬이 마음에 들지 않으면 텍스트 편집기로 직접 수정할 수 있다. 이것이 단순한 화면 녹화 매크로와 근본적으로 다른 지점이다. 스킬은 "이런 상황에서 이렇게 행동하라"는 의도 기반 지침이지, "이 좌표를 클릭하라"는 좌표 기반 스크립트가 아니다.

1.3 재생(Replay) 단계

스킬이 저장되면 이후부터는 자연어로 호출한다. Codex는 두 가지 방식으로 스킬을 활성화한다. 명시적 호출은 $스킬명 또는 /skills로 직접 지정하는 방식이고, 암묵적 호출은 자연어 설명을 보고 Codex가 알맞은 스킬을 자동 선택하는 방식이다. 예를 들어 "이번 주 출장 경비 정산해줘"라고 입력하면 경비 청구 스킬이 자동으로 선택돼 실행된다.

스킬 디렉토리는 우선순위 순으로 .agents/skills(리포지토리 수준), $HOME/.agents/skills(사용자 수준), /etc/codex/skills(시스템 수준) 세 곳에 저장된다. 리포지토리 안에 두면 팀이 공유할 수 있고, 홈 디렉토리에 두면 개인 전용이 된다.

2. SKILL.md와 에이전트 스킬 아키텍처

Record & Replay를 이해하려면 Codex의 Agent Skills 아키텍처를 먼저 봐야 한다. Record & Replay는 이 아키텍처 위에 "설명 대신 시연으로 스킬을 만드는" 레이어를 얹은 것이다.

2.1 스킬 디렉토리 구조

skill-name/
├── SKILL.md          # 필수: 지침 + 메타데이터
├── scripts/          # 선택: 실행 스크립트
├── references/       # 선택: 참고 문서
├── assets/           # 선택: 템플릿·리소스
└── agents/
    └── openai.yaml   # 선택: UI 설정

SKILL.md의 최소 구조는 다음과 같다.

---
name: expense-report
description: 경비 청구서를 사내 시스템에 제출할 때 사용한다
---

1. 사내 포털 expense.company.com에 접속한다
2. 제출 대상 기간과 금액을 입력한다
3. 영수증 파일을 첨부한다
4. 제출 완료 확인 메시지를 확인한다

Record & Replay는 위 SKILL.md를 사람이 직접 쓰는 대신 Codex가 관찰한 내용을 바탕으로 자동 생성한다. 여기서 핵심 통찰이 있다. 생성된 스킬의 품질은 녹화의 명확성에 비례한다. 군더더기 없이 목적에 맞는 동작만 한 번 깔끔하게 수행해야 좋은 스킬이 나온다.

2.2 컨텍스트 관리 — 토큰 효율

스킬이 많아지면 컨텍스트가 비대해질 수 있다. Codex는 이를 점진적 공개(progressive disclosure)로 해결한다. 스킬 목록을 처음 로드할 때는 모델 컨텍스트 윈도의 최대 2% 또는 8,000자까지만 사용한다. 특정 스킬이 선택된 뒤에야 해당 SKILL.md 전문이 컨텍스트에 들어온다. 스킬 수가 매우 많아지면 description이 단계적으로 축약되거나 일부 스킬이 생략될 수 있다는 경고도 포함된다. 이 설계는 스킬 라이브러리가 커질수록 description을 간결하고 변별력 있게 유지해야 한다는 실무 함의를 갖는다.

3. 왜 지금 이 기능인가 — AI 에이전트 자동화의 방향

Record & Replay는 독립된 기능이 아니라 AI 코딩 에이전트가 나아가는 방향의 한 단면이다.

3.1 "설명 피로"를 줄이는 접근

에이전트 기반 자동화의 가장 큰 마찰은 역설적으로 프롬프트 작성이다. 반복 작업을 에이전트에게 맡기려면 처음에 그 절차를 정확히 설명해야 한다. 그런데 내가 매주 하는 일을 글로 설명하는 것이 그냥 직접 하는 것보다 더 오래 걸리는 경우가 적지 않다. "경비 청구서를 제출해줘"라고 하고 싶은데, 그 절차를 프롬프트로 옮기려면 10단계짜리 지침을 써야 한다.

Record & Replay는 이 마찰을 우회한다. "설명하는 대신 보여줘라." 시연이 프롬프트가 된다. 이 발상은 새롭지 않다. 매크로 녹화기, RPG 도구, Selenium IDE 같은 것들이 오래전부터 비슷한 아이디어를 다뤄왔다. 그러나 AI 에이전트 위에서 구현하면 결정론적 좌표 클릭이 아닌 의도 기반 추론으로 전환된다. 버튼 위치가 바뀌어도 "제출 버튼을 찾아 누른다"는 의도가 남아있으면 스킬이 살아남을 수 있다.

3.2 개인 워크플로에서 팀 자동화로 — 플러그인 확장

스킬을 리포지토리 수준 .agents/skills에 두면 팀이 공유한다. 더 나아가 플러그인 체계로 묶으면 MCP 서버 설정과 앱 매핑까지 함께 패키징된다. 이는 "내가 녹화한 워크플로가 팀 전체의 자산이 된다"는 가능성을 연다. 다만 현 단계에서 팀 배포는 개인 스킬 공유보다 거버넌스 부담이 크다는 점을 뒤에서 짚는다.

3.3 Computer Use라는 전제

Record & Replay가 Computer Use를 필요로 한다는 사실은 기능의 성격을 규정한다. Computer Use는 AI가 실제 화면을 보고 마우스·키보드를 직접 조작하는 능력이다. API가 없는 웹 UI, 사내 레거시 시스템, GUI 전용 도구를 다루기 위한 최후 수단이다. 이 전제 위에서만 "시연을 보고 스킬을 만든다"는 일이 가능하다. 뒤집어 말하면, API로 깔끔하게 자동화할 수 있는 작업에 Record & Replay를 쓰는 것은 과한 선택이다.

4. 결정성 문제 — 가장 솔직하게 봐야 할 지점

에이전트 자동화에서 가장 자주 간과되는 문제가 결정성(determinism)이다. 같은 스킬을 실행해도 매번 결과가 동일하게 나오는가. Record & Replay의 맥락에서 이 문제는 세 층위로 나뉜다.

4.1 UI 레이아웃 변화

스킬을 만든 시점과 실행하는 시점 사이에 웹사이트나 앱 UI가 바뀌면 스킬이 오작동한다. Codex가 접근성 트리를 읽어 좌표 의존성을 줄이지만, 페이지 구조 자체가 크게 바뀌면 재녹화가 필요하다. 사내 시스템처럼 변경 빈도가 낮은 대상에서는 이 문제가 덜하지만, 외부 서비스를 다루는 스킬은 유지보수 부담을 각오해야 한다.

4.2 입력 변수의 범위

스킬은 날짜, 파일명, 금액 같은 변수를 받아 실행할 때 적용한다. 그러나 변수 형식이나 범위가 예상과 다르면 에이전트가 엉뚱한 동작을 할 수 있다. 예를 들어 경비 청구서 스킬에 "이번 달 전체"라는 모호한 날짜 범위를 넣으면 에이전트가 임의로 해석한다. 명확한 입력 스펙을 SKILL.md에 명시하는 것이 이 문제를 줄이는 핵심이다.

4.3 검증 부재의 위험

자동 생성된 스킬은 Codex가 관찰을 바탕으로 "이런 의도일 것이다"라고 추론한 결과다. 추론이 틀릴 수 있다. 중요한 것은 스킬이 편집 가능하다는 점이다. 생성 후 반드시 SKILL.md를 검토해 올바른 의도가 담겼는지 확인해야 한다. 이 검토를 건너뛰고 스킬을 팀에 배포하면 잘못된 자동화가 조용히 퍼진다. 스킬 공유 전 인간 검토는 선택이 아니라 필수다.

5. 보안과 거버넌스 — 조직이 주의해야 할 것

Record & Replay가 개인 사용이 아닌 팀·조직 수준에서 도입될 때 거버넌스 고려가 더해진다.

5.1 녹화 중 민감 데이터 노출

녹화 중에는 창 전체 내용이 캡처된다. 패스워드 필드, 개인정보, API 키가 화면에 표시된 채 녹화되면 SKILL.md에 그 흔적이 남을 수 있다. OpenAI 문서는 이를 보안 위험으로 명시한다. 실무에서는 녹화 전 민감 정보 화면을 닫거나 가리고, 생성된 SKILL.md를 반드시 검토해 자격증명이 포함되지 않았는지 확인해야 한다.

5.2 스킬 버전 관리

SKILL.md는 파일이므로 Git으로 버전 관리할 수 있다. 팀 공유 스킬은 변경 이력을 추적하고, 불량 업데이트를 롤백할 수 있는 체계를 갖추는 것이 합리적이다. 특히 고위험 워크플로(결제, 외부 발행 등)를 다루는 스킬은 변경 시 리뷰 프로세스를 거치는 것이 좋다.

5.3 비용 모델의 이중성

스킬 생성 단계(녹화·분석)와 스킬 실행 단계는 비용 구조가 다르다. 실행 시 Computer Use, 브라우저 동작, 모델 호출이 복합적으로 사용된다. 스킬이 자주 실행되는 팀 환경에서는 사용량 모니터링과 예산 설정이 필요하다.

6. 실무 활용 — 어디에 써야 하고 어디엔 쓰지 말아야 하나

Record & Replay가 빛나는 곳과 그렇지 않은 곳을 명확히 나눠보자.

6.1 잘 맞는 작업

공식 문서와 교차 검증한 적합 작업 유형은 다음과 같다.

  • 반복 빈도 높은 관리 업무: 경비 청구, 시간외 신청, 주간 보고서 다운로드
  • 특정 형식이 있는 작업: 정해진 템플릿의 이슈 생성, 회의록 특정 시스템 입력
  • API가 없는 내부 UI: 레거시 사내 포털, ERP 클릭 작업
  • 개인 선호가 강한 작업: 설명보다 시연이 빠른 다단계 UI 흐름

6.2 맞지 않는 작업

  • 결과가 매번 크게 달라지는 작업: 판단과 창의가 필요한 문서 작성
  • 보안 자격증명이 개입되는 흐름: 로그인 패스워드 입력 시퀀스 전체 녹화
  • API로 깔끔하게 처리 가능한 작업: 굳이 Computer Use를 쓸 이유가 없음
  • 변경 빈도 높은 외부 서비스 UI: 유지보수 비용이 자동화 이득을 초과할 수 있음
  • Windows/Linux 환경: 현재 macOS 전용이므로 크로스플랫폼 팀에서는 적용 범위가 제한됨

7. "학습하는 에이전트"라는 프레임의 정직한 재독

Record & Replay를 둘러싼 표현 중 가장 신중하게 읽어야 할 것이 "에이전트가 사용자의 워크플로를 학습한다"는 프레임이다.

정확히는 이렇다. Codex는 시연을 관찰해 SKILL.md라는 지침 파일을 만든다. 이 파일은 에이전트에게 "이런 상황에서 이렇게 해라"라고 말한다. 에이전트가 지능적으로 패턴을 학습해 모델 가중치를 업데이트하는 것이 아니다. 파인튜닝도, 강화학습도 아니다. 지침 생성의 자동화다.

이 구분이 왜 중요한가. "학습"이라는 단어는 "이번에 배운 것을 다음에도 쓴다"는 기대를 낳는다. 그러나 SKILL.md는 파일이다. 저장하지 않으면 사라지고, 명시적으로 호출하지 않으면 사용되지 않는다. 에이전트는 스킬 파일이 있는 맥락에서만 그 행동을 재현한다. 이 차이를 인식하면 기능을 더 현실적으로 설계할 수 있다.

그럼에도 불구하고 이 접근은 의미 있다. 지침을 수동으로 작성하는 대신 시연으로 생성한다는 것은 에이전트 자동화의 진입 장벽을 낮추는 실질적 진전이다. 모든 사용자가 SKILL.md를 잘 쓸 수 있는 것이 아니라면, 시연 기반 생성은 그 장벽을 허문다. 중장기적으로 이런 도구가 보편화하면 "에이전트에게 일을 가르치는" 방식이 프롬프트 엔지니어링에서 시연과 편집으로 이동할 수 있다.

8. 경쟁 맥락 — 에이전트 자동화의 다른 접근들

Record & Replay는 비슷한 문제를 다루는 여러 접근 중 하나다.

전통적 매크로 도구(AutoHotkey, Selenium IDE)는 좌표·DOM 기반 재현이고, 결정론적이지만 UI 변경에 취약하다. RPA 도구(UiPath, Automation Anywhere)는 비슷한 녹화·재생 패러다임을 엔터프라이즈 수준에서 구현하지만, 설정 비용과 유지보수가 무겁다. 브라우저 AI 에이전트(Operator, Browser Use 등)는 자연어 지시로 UI를 조작하지만 스킬 저장·재사용 체계는 제각각이다.

Record & Replay가 차별화하는 것은 Codex 생태계 내 네이티브 통합이다. 코딩 에이전트가 코드 작업과 UI 자동화를 같은 컨텍스트 안에서 다룰 수 있다. "이 데이터를 분석한 뒤 결과를 사내 포털에 올려줘"라는 복합 작업이 하나의 에이전트 루프 안에서 가능해진다. 이 통합 가치는 특히 개발 작업과 관리 반복 업무가 함께 있는 팀에서 두드러진다.

9. 결론 — 오늘 할 수 있는 것과 현실적인 기대

Record & Replay는 과장된 기대와 지나친 비관 사이 어딘가에 있다. 2026년 6월 기준 확인할 수 있는 것은 이렇다.

할 수 있는 것: macOS에서 Computer Use로 반복 UI 작업을 시연 한 번으로 SKILL.md로 만들고, 이후 자연어로 재호출한다. 스킬은 편집 가능하고 팀 공유도 된다. 수동 프롬프트 작성보다 진입 장벽이 낮다.

현실적 한계: macOS 전용, Computer Use 필수, EU 제외. 스킬 결정성은 UI 변경과 입력 변수 범위에 달렸다. 자동 생성 스킬은 검토 없이 배포하면 위험하다. 민감 데이터가 녹화될 수 있다.

오늘 적용 가능한 행동 세 가지. 첫째, 본인 업무 목록에서 "매번 같은 순서로 반복하는 UI 클릭 작업"을 추려라. 둘째, 그 중 보안 민감 정보가 개입되지 않는 것 하나를 골라 Record & Replay로 스킬을 만들고, 생성된 SKILL.md를 직접 읽어 의도가 정확한지 검토하라. 셋째, 스킬을 리포지토리 수준에 저장하고 팀과 공유하기 전 한 주간 개인 환경에서 검증하라. 이 세 단계면 기능을 안전하게 실험할 수 있다.

에이전트가 사용자의 워크플로를 스킬로 만드는 아이디어는 AI 코딩 도구의 다음 단계를 가리킨다. "코드를 대신 쓰는 에이전트"에서 "반복 작업 전체를 대신 수행하는 에이전트"로. Record & Replay는 그 방향의 초기 구현이며, 지금 당장 완성된 것은 아니지만 방향은 맞다.
