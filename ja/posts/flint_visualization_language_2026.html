LLMにグラフを描かせると何が壊れるのか - 意味ベース仕様の価値と代償

軸の型の誤判定、整数の日付、配色の乱用、そして「ここだけ」が効かない仕様

2026年8月3日 IT・技術

はじめに: 「棒の色だけ変えて」がグラフ全体を塗り替える

モデルに一行だけ投げる。「棒の色だけ青系にして」。返ってきたグラフは色が変わっている。ところが昨日手で合わせたキャンバス幅が元に戻っており、軸の目盛間隔が変わってラベルがいくつか重なっている。直った一つと引き換えに、気づかない回帰を三つ受け取ったことになる。

これが運の悪さで起きた話ではない、というのがこの記事の出発点だ。壊れる場所は驚くほど決まっている。軸を連続型と見るか範疇型と見るかで一度、日付のように見える整数をどう読むかで一度、色を何色まで使うかで一度、そして「ここだけ」という指示が仕様のどの行に当たるかでもう一度。

この四つはモデルの知能が足りないから起きるのではない。モデルが埋めるべき枠が多すぎ、その枠同士が絡み合っているから起きる。Vega-Liteでよく作られたグラフ一つには、スケールの定義域、時間単位、マークの幅、キャンバス幅、ラベルの角度、配色、凡例の位置がすべて手で決められて入っている。そのうち一つを変えれば残りの六つがずれる。人が作ってもずれるのだから、毎回最初から書き直すモデルではもっとひどくずれる。

2026年7月、マイクロソフトリサーチがFlintを公開した。フィールドが何を意味するかだけ宣言すれば、解析・軸・書式・配色・レイアウトをコンパイラが導出する中間言語だ。この記事の目的はFlintの紹介ではなく、Flintが解こうとしている問題が実際に何であり、その方式が何を手放すのかを見ることにある。道具は変わってもこの問題は残る。

結論から書く。意味ベースの仕様が確実に与えるのは「きれいなグラフ」ではなく「短くて直せるチャート定義」だ。品質改善は測定されているが幅は小さく、興味深いことにモデルが強くなるほどその利得は減る。一方で仕様が短くなる効果はモデルと無関係に残る。導入判断はここで分かれる。

1. 壊れる場所は決まっている - 五つの故障

LLMにグラフを任せたことがある人なら、以下の一覧は見慣れているはずだ。この五つは文法がVega-LiteであれEChartsであれMatplotlibであれ、ほぼ同じ形で繰り返される。

故障仕様のどこで生じるか画面にどう現れるか人は気づくか
軸の型の誤判定量的・順序・名義のうち誤ったスケールを選ぶ連続量が棒二十本に散らばる、範疇が線で結ばれるたいてい気づく
時間解析の失敗整数や文字列の日付をそのまま時間軸へ載せる1970年代のどこかへ飛ぶ、順序が入れ替わる気づきにくい
非加算値の積み上げ比率・平均・順位を積み上げ棒にする合計が百パーセントを超える、意味のない高さが生じるほぼ気づかない
配色の誤用と乱用発散型フィールドに逐次型配色、二十範疇に虹色ゼロが中間でない色に落ちる、凡例が画面を食う乱用は見えるが誤用は見えない
修正指示の誤着弾一つの要求が複数の属性へ散っている直してほしかったもの以外が変わるすぐ見えるが原因は見えない

ここで三番目と四番目が特に悪い。成果物がまともに見えるからだ。軸が壊れたグラフは描き直せばよいが、比率を積み上げた棒はそのまま会議資料に出ていく。可視化の価値は美しさではなく異常に気づくまでの時間から出るのに、この二つの故障はその時間を無限大にする。何を見れば異常が見えるのかという問いそのものは、データベース観測ツールを題材に別途扱ったことがある。

五番目は性格が違う。前の四つが一度作るときの問題なら、これは直すときの問題だ。そしてLLMワークフローではグラフを一度で完成させることはまずない。会話はいつも「いいけどここだけ」へ続く。

2. 202001という列一つが生む三つの分岐

抽象的に言っても掴めないので、具体的な場面を一つ取ろう。Flintの論文が例に使ったのと同じ状況で、企業のデータウェアハウスではほぼ毎日出会う形だ。月次指標テーブルの期間列が202001、202002のように六桁の整数で入っている。

人はこれを見た瞬間に2020年1月と読む。モデルもそう読む。問題はモデルが読んだものを仕様へ移す瞬間に三つへ分かれることだ。

モデルの選択仕様に書かれるもの結果なぜそうなるか
そのまま時間軸へフィールド型を時間型に指定年が崩壊する、軸が絡まる202001をUNIX秒や年の値として解釈
範疇型へ回避フィールド型を名義型に指定七十二の枠が生じてラベルが重なる六年分は七十二か月、各月が独立した範疇になる
手で解析変換式、時間単位、マーク幅、キャンバス幅、ラベル角度正しく出る五つの値が互いに合っていないと成立しない

三番目が正解なのだが、正解の形が問題だ。Vega-Liteでこれをきちんと書くとおおよそこうなる。

{
  "transform": [
    { "calculate": "datetime(floor(datum.Period/100), datum.Period%100-1)",
      "as": "PeriodDate" }
  ],
  "mark": { "type": "bar", "width": { "band": 0.9 } },
  "encoding": {
    "x": {
      "field": "PeriodDate", "type": "temporal", "timeUnit": "yearmonth",
      "axis": { "format": "%Y-%m", "labelAngle": -45, "labelOverlap": "greedy" }
    },
    "y": { "field": "Users", "type": "quantitative", "aggregate": "sum",
           "scale": { "zero": true } }
  },
  "width": 504
}

この断片でモデルが間違えうる箇所を数えてみよう。除算と剰余の組み合わせ、月のインデックスが0始まりか1始まりか、時間単位の文字列、書式の文字列、ラベルの角度、重なり回避の戦略、帯幅の比率、キャンバス幅。八つだ。しかもこのうち相当数が互いに依存する。キャンバス幅を720へ広げればラベル角度を0へ戻してもよく、帯幅も見直すことになる。

ここで核心はこれだ。モデルは「2020年1月である」ことをすでに知っている。知っていることを低水準のパラメータ八つへ翻訳する過程でずれる。ならば翻訳をさせずに知っていることをそのまま書かせればよい。これが意味ベース仕様の発想である。

3. 短く書けば見栄えが悪く、長く書けば壊れる

可視化文法には古いジレンマが一つある。Flintの論文と公式ブログが問題提起の出発点にしたのも、まさにこの地点だ。

  • 短い仕様はシステムの既定値に頼る。三行でグラフは出るが、軸の書式は素っ気なく、ラベルは重なり、色はライブラリの既定パレットのままだ。
  • 長い仕様は望む結果をくれる。その代わり冗長で、壊れやすく、人が開いて何をなぜそうしたのか読み取りにくい。
  • 人はこの二つの間を反復修正で行き来する。描いてみて、合わなければ一行直し、また見る。
  • モデルはその反復が苦手だ。毎回全体を作り直すので収束せず振動する。

ここにもう一つ乗る。長い仕様はトークンを食う。グラフ一つに六十行のJSONを毎回まるごと書き直すパイプラインは、会話が長くなるほど費用が線形に増える。そして書き直した六十行のうち、実際に変わるのは一行だ。

構造を圧縮してモデルへ渡すと何が変わるかは、コード側で先に検証された論点である。コードベースを問い合わせ可能なグラフへ変える取り組みが狙ったものも結局は同じだ。モデルにすべてを投げず、モデルが判断すべきものだけを残した表現を渡すこと。

4. 意味型が代わりに決めるもの - 三段階の階層

Flintの仕様は二つの塊に分かれる。フィールドが何であるかを宣言する部分と、どのグラフをどのチャネルに描くかを宣言する部分だ。リポジトリが示す最小の形はこうなっている。

import { assembleVegaLite } from 'flint-chart';

const spec = assembleVegaLite({
  data: { values: myData },
  semantic_types: { weight: 'Quantity', mpg: 'Quantity', origin: 'Country' },
  chart_spec: {
    chartType: 'Scatter Plot',
    encodings: { x: { field: 'weight' }, y: { field: 'mpg' },
                 color: { field: 'origin' } },
    baseSize: { width: 400, height: 300 },
  },
});

originがCountryという一語で複数の決定が付いてくる。範疇型であり、順序がなく、個数が限られ、色で区別するのが自然で、凡例には名前をそのまま書くべきで、逐次型の色ランプを使ってはいけない。低水準の設定六つを代替する単語一つだ。

この型体系は平坦ではなく三段階の階層である。論文が示す構造は次のとおりだ。

段階何を決めるか個数例
第一段階・領域解析戦略。値をそもそも何として読むか6時間型、範疇型、測定値、離散値、識別子、地理
第二段階・系列集計可能性、ゼロの意味、定義域の構造15日時、期間、実体、区間、総量、比率、評点、順位、座標
第三段階・型表現。書式、整列、既定の配色系統44年月、月、百分率、売上、利益、緯度、状態、方向

階層が重要なのは継承のためだ。新しい型を一つ足すとき、解析と集計の規則を最初から定義せず、親の振る舞いを受け継いだうえで表現だけを絞ればよい。社内の指標辞書がある組織なら、この構造は写しやすいという意味でもある。

数字が二つある理由。リポジトリの文書は意味型が七十種類以上と記し、論文は第三段階の四十四種類と記す。数える層が違う。系列と別名まで合わせれば前者の数になり、末端の型だけ数えれば後者になる。引用するときどちらの基準か添えないと、互いに食い違って見える。

第二段階が実務で最も値の張る層だ。総量と比率を区別するということは、積み上げ棒を許すか否かが型の段階で決まるという意味である。先ほど「ほぼ気づかない」と記した非加算値の積み上げ故障が、ここで構造的に塞がれる。人のレビューが捕まえるべきだったものを型が捕まえるのだ。

5. コンパイラがやること - 三つの段階

宣言から実際のチャート仕様までは三段階を経る。この構造を知っておくと、結果が気に入らないときどの段階を疑うかが決まる。

  1. 意味の解決。意味型と元データを併せて見てフィールドの性質を確定する。解析方式、スケールの種類、書式、集計関数がここから出る。
  2. 最適化。制約ベースでレイアウトを解く。軸の長さ、項目間隔、余白、ファセット配置が、データの濃度とキャンバスの限界を併せて見て決まる。
  3. コード生成。ライブラリに依存しない属性集合をバックエンド別のテンプレートで打ち出す。Vega-Lite、ECharts、Chart.js、Plotly、そしてOffice.jsを通じたExcelのネイティブチャート。

第二段階がこの設計で最も知られていない部分だ。論文は各軸とグループとファセットのパネルを「圧縮可能な容器」と置き、好ましい大きさと最小可読の大きさを設けたうえで、離散軸は項目を伸縮させて制約を満たし、連続軸はキャンバスを伸ばして重なりを減らす、と記す。全体段階では縦横比を傾き四十五度の基準で合わせ、ファセットの折り返しの均衡を調整する。

ここが重要だ。七十二か月分の軸が重ならないのは、モデルがキャンバス幅504ピクセルをうまく選んだからではなく、最適化器が最小可読幅から逆算したからである。モデルはその数字を知らなくてよい。逆に言えばその数字をこちらで決めたいときどう介入するかが次節の主題になる。

バックエンドが複数という点も実務では思ったより大きい。同じ仕様がウェブではEChartsとして、報告書の納品ではExcelのネイティブチャートとして出るということは、「画面写真をお送りしましょうか、元ファイルでお渡ししましょうか」という毎回のやり取りが消えるという意味だ。Excel側は画像ではなく編集可能なネイティブチャートとして作られる。

6. 部分修正ができる仕様 - ここが本当の分かれ道

この記事の中心的な主張だ。LLMワークフローにおいて仕様設計の価値は「初回生成の品質」ではなく「二番目の指示がどこに落ちるか」から出る。

理由は単純だ。グラフを一度で完成させる会話はない。実際の会話はこう流れる。

  • 「これ月別にして」 - 時間単位の変更
  • 「y軸を0から始めて」 - スケールの基準値
  • 「凡例を下へ」 - 配置
  • 「この地域だけ強調」 - 色チャネルの条件
  • 「横に寝かせて」 - チャネルの交換

低水準の文法ではこの五つがそれぞれ仕様の異なる二、三か所を同時に触る。「y軸を0から」一つでも、スケールの定義域と軸の目盛設定、場合によってはキャンバスの高さが一緒に動く。モデルはこれを部分編集として処理できず全体を書き直す。書き直せばそれまでの四回の修正が確率的に失われる。

区分利用者・モデルが直接書くものコンパイラが決めるもの
フィールド意味型、固定の値域、基準値解析規則、スケールの種類、書式、整列
チャートチャート種別、チャネル割り当て、集計関数マークの属性、軸の目盛、凡例の構成
レイアウト基準サイズ軸の長さ、間隔、余白、ファセット配置、縦横比
配色(意味型を通じて間接的に)配色系統、定義域の対応、中立値の位置

左の列がすなわち修正の表面積だ。表面積が小さければ「これだけ変えて」が一行に落ち、残りはそのまま残る。論文が示した仕様の長さがバックエンドのネイティブコードに比べ平均で八十五パーセント短いという結果は、単なる節約の話ではなくこの表面積の大きさを測る数字である。

ただし削った分だけ失うものも、まさにその場所で生じる。右の列は私たちが触れない列でもあるという意味だ。

7. 制御権を渡した代償

自動決定はただではない。実務でぶつかる代償は三つの形で来る。

7.1 既定値が意図と違うとき

コンパイラが「このフィールドは比率だから0から100まで」と判断したのに、実際には92から98の間の微細な差を見せなければならない状況がある。こうした要求は間違っているのではなく文脈から出てくる。仕様のスキーマにはエンコーディング水準の再定義項目があり、値域や基準値を直接指定する任意項目もあるが、再定義がどこまで開かれているかは文書が薄い。ここで詰まればコンパイル結果を取り出して手で直す方へ落ちるしかなく、その瞬間に部分修正の利点は消える。

7.2 表現がそのまま要件であるとき

デザインシステムが色コードとフォント寸法とグリッド間隔を仕様として定めた組織では、自動決定そのものが違反だ。「見栄えよく適当に」が価値ではなく費用になる場所である。こうしたチームは低水準の文法を使い続けるのが正しい。フォントの軸をデータへ直接結びつけるバリアブルフォントによる可視化の実験のように、表現そのものが主題である仕事も同じ側だ。

7.3 型の推論が外れるとき

この設計全体が「フィールドに正しい意味型が付く」という前提の上に立っている。ところがその型を付けるのも結局はモデルだ。scoreという列が評点なのか計測値なのか順位なのかは、列名だけでは分かれない。誤って付けば故障は消えるのではなく一段上へ移動するだけである。

ただし移動自体に価値がある。低水準のパラメータ八つがずれた状態は原因を突き止めにくいが、「この列の型が違う」は一行で特定され一行で直る。失敗の数を減らすのではなく、失敗を診断可能な形へ集めること。これが中間言語の設計が実際に売っている商品だ。

論文自身も、一つのフィールドが一つの意味型に対応すると仮定しており、曖昧なフィールドにはこの仮定が不十分だと記している。

8. 数字をどう読むか - 勝率41から45パーセントの意味

評価結果が公開されている。そのまま写すとこうだ。TidyTuesday 2025のデータセット六十三の表(行数の中央値952、列8)から、問い合わせ生成エージェントが三百十五の問いを作り、Flint経路とバックエンド直接生成の経路がそれぞれグラフを作ったうえで、視覚言語モデルが描画結果を採点した。採点項目は関連性・チャートの誤り・明瞭さ・デザイン品質の四つで各5点、合計20点である。

この表をどう読むかが導入判断を分ける。三点を挙げる。

  • 差はあるが小さい。平均点の差は20点満点で0.36から0.57点、百分率では二から四パーセント台だ。「チャート品質が飛躍する」という表現をこの数字は支えない。
  • 強いモデルほど差が縮む。GPT-5.1で有意確率が0.05と最も弱く、勝敗差も129対118で最も狭い。一方GPT-5-miniとGPT-4.1では0.001と0.004で明確だ。モデルが良くなるほど中間言語の品質利得は減ると読むのが自然である。
  • 最も堅牢な数字は品質ではなく長さだ。八十五パーセント短いという結果はモデル性能と無関係に成立し、トークン費用と部分修正の可能性へ直結する。

だからこの道具を「もっときれいなグラフを得る方法」として導入すると期待が外れる。「同じ品質を五分の一の長さの定義で保ち、その定義を人が開いて直せるようにする方法」として導入すれば、数字と期待が合う。

測定方式にも限界がある。採点者が視覚言語モデルなので、モデルが好むグラフと人が有用と感じるグラフが分かれる地点はこの点数では捉えられない。「見える」と「分かる」が別の問題だというのは、観測ツール全般で繰り返される構図でもある。

9. 確認できなかったこと

公開資料では答えが出なかった項目だ。導入を検討するならこの一覧がそのまま事前検証項目になる。

  • 日本語・韓国語・中国語ラベルの幅の計算。レイアウト最適化は最小可読幅を前提とするが、これらの文字の実際の幅をどう取るかは確認できなかった。同じ文字数でもラテン文字より広い。
  • 地域固有の数値書式。万や億といった単位の略記や通貨記号を標準の意味型が覆うのか、再定義で入れる必要があるのか。
  • 再定義の許容範囲。エンコーディング水準の再定義項目がスキーマに存在することまでは確認できるが、どの属性が開かれどの属性が閉じているかの一覧は確認できなかった。
  • 意味型の推論精度。最終的なチャート品質は評価されているが、型の推論段階そのものの精度を別に測った数値は確認できなかった。
  • アクセシビリティの既定値。自動選択される配色が色覚特性に配慮した対比基準を満たすのか、どの基準を使うのか。
  • コンパイルの費用。制約最適化が大きな濃度でどれだけかかるのか、サーバ描画のパイプラインに入れられる遅延なのか。
  • 人による評価。自動採点の結果は公開されているが、人の評価者を使った別途の結果は確認できなかった。
  • 本番導入事例。初公開が2026年7月なので、運用環境への適用事例はまだ公開されていない。

10. 導入判断 - いつ使い、いつ既存の文法に残るか

バージョンが0.4.0で最初のリリースが2026年7月だ。1.0以前であることを判断の前提に置く必要がある。APIは変わりうるし、変われば仕様を書き直すことになる。ライセンスはMITなので、その部分の制約はない。

状況判断理由
エージェントやチャットボットがグラフを作り人が後ろで直す使う部分修正の表面積が小さいことがそのまま価値になる
同じ指標をウェブとExcelの両方へ出す必要がある使う単一の仕様からバックエンド別のネイティブ出力
チャート定義をコードレビューに載せたい使う60行のJSONはレビューできず、10行ならできる
社内の指標辞書があり、フィールドの意味が安定している使う意味型の対応付けが一度で終わる
ブラッシング・ズーム・クロスフィルタが要件使わない相互作用は現時点で一級の対象でないと論文が明示
多層チャートや注釈が中心使わない同じ理由で範囲外
デザインシステムのピクセル規格が契約事項使わない自動決定が価値ではなく費用になる
Python中心のデータパイプライン保留Pythonパッケージがまだソースプレビュー段階
グラフ一、二枚の単発作業使わない依存追加の費用が利得より大きい

試すつもりなら、順序はこう組むのがよい。

  1. 実際に使っている表を一つ選ぶ。日付のような整数キーがある表が差を最も大きく現す。
  2. 今使っている文法で作った仕様と並べ、行数とトークン数を数える。
  3. 「これだけ変えて」を五回連続で投げ、何回目で先の修正が失われるかを見る。これが実際の判断根拠になる。
  4. 社内でよく使う書式が標準の意味型にあるか、再定義で済むかを確認する。
  5. パッケージはnpm install flint-chartで入り、エージェント環境ではnpx -y flint-chart-mcpでMCPサーバを繋ぐ。

結論: 仕様設計がモデル性能を代替する区間

まとめるとこうなる。LLMにグラフを任せるとき壊れる場所は決まっており、その壊れの相当部分はモデルがすでに知っていることを低水準のパラメータへ翻訳する過程で発生する。意味ベースの仕様はその翻訳をコンパイラへ移す。得るのは短い定義と部分修正が可能な表面積であり、失うのは自動で決まった値への直接の制御権だ。

数字が語ることも明確である。品質改善は実在するが大きくなく、モデルが強くなるほど減る。一方で仕様が五分の一になる効果はモデルと無関係に残る。したがってこの手法の寿命は「モデルが良くなれば不要になるもの」と「モデルが良くなっても残るもの」に分かれる。前者が品質補正であり、後者が編集可能な表現だ。

今日すぐ適用できることを三つ挙げて閉じる。

  • 今使っているプロンプトにフィールドの意味から書け。道具を変えなくてよい。「PeriodはYYYYMMの整数、Usersは加算可能な件数、Ratioは比率なので積み上げ禁止」という一行が、軸の型の誤判定と非加算の積み上げを相当程度防ぐ。
  • グラフの修正指示を五回連続で投げてみよ。今のパイプラインが何回目で先の修正を失うかが、そのまま改善余地の大きさだ。
  • 「見栄えよく」を要件から分離せよ。自動決定を使える場所かどうかがここで分かれる。表現が契約なら自動化は費用だ。
