Malloy 是什么 - 解决 SQL 重复连接与逻辑冗余的数据建模语言

Looker 创始人 Lloyd Tabb 打造的关系声明式语言，编译为 SQL 运行在现有引擎之上 - 对比 dbt、LookML、Cube，并分析 AI 时代语义模型的价值

2026-07-23 开发/基础设施

引言: SQL 依旧令人头痛 - 为什么又要一门数据建模语言

凡是处理过数据的开发者，大概都遇到过这样的场景: 每个仪表盘上「营收」数字微妙地对不上，某个连接写错让某项汇总凭空翻倍，还有那两百行的 CTE 叠层，滚动翻看半天才想起这条查询到底想求什么。SQL 至今仍是数据世界的通用语言，但在把「关系」与「含义」声明一次并到处复用这件事上，它始终笨拙。

最近在 hada.io(GeekNews)上流传的 Malloy，是一款自称要解决这个老问题的开源语言。本文没有照搬新闻通稿，而是直接查阅官方文档与代码仓库核实语法，把 Malloy 放进「语义层」这一更大的潮流里定位，并从我自己的角度分析: 在 AI 智能体也开始直接触碰数据的当下，为什么这类语言会重新被关注。

1. Malloy 是什么 - Looker 创始人的第二门语言

1.1 从 LookML 到 Malloy 的 Lloyd Tabb

要理解 Malloy，得先看它出自谁手。Lloyd Tabb 于 2012 年与 Ben Porterfield 共同创立 Looker，并设计了 Looker 的数据建模语言 LookML。LookML 是最早把「指标定义纳入版本控制」这一理念商业化的语言，此后成为整个语义层讨论的原型。2019 年 Looker 被谷歌收购后，Tabb 与谷歌团队开始试验一门新语言，这便是 2022 年发布的 Malloy。换句话说，Malloy 不是业余的side project，而是一位已经把语义建模语言推向商用规模的人，基于那段经验重新设计的第二次尝试。

1.2 核心理念一句话概括

官方对 Malloy 的定义是「用于描述数据关系与转换的开源语言」，兼具语义建模语言与查询语言。关键区别在于，它不是一个新的数据库或执行引擎。用 Malloy 编写的模型与查询会被编译，并直接运行在 BigQuery、Snowflake、PostgreSQL、MySQL、Trino、Presto、Databricks、DuckDB、MotherDuck 等你已经在用的 SQL 引擎之上。目前它在 malloydata 旗下以 MIT 许可开源开发，在 GitHub 上已获得超过 2500 颗星。

2. SQL 的老毛病 - 问题到底出在哪

2.1 反复出现的连接与冗余逻辑

与其说 SQL 是一门表达关系的语言，不如说它是一门要求你每次查询都重新描述关系的语言。同样连接三张表的查询，这周写一遍，下周再写一遍，换个同事又要重写一遍。SQL 本身没有办法把连接条件定义一次、放在一个地方持续复用。结果就是连接逻辑被复制粘贴进几十个查询文件里，一旦表结构变了，就得逐一找出这些副本手动修改。

2.2 语义的缺失 - 同名指标，不同数字

更根本的问题是，SQL 没有地方安放「含义」。像「活跃用户」「准点率」这类需要全组织达成共识的指标，在 SQL 里每次都得在 SELECT 子句里重新展开写一遍。如果分析师 A 把取消订单排除在外计算，分析师 B 把它算进去，同名指标就会在不同仪表盘上给出不同的数字。这不是失误，而是 SQL 从一开始就没有「指标定义」这个概念所导致的结构性问题。

2.3 冗长难读的查询，以及扇出陷阱

连接层层叠加时，汇总结果会悄悄膨胀 - 「扇出(fan-out)」与「断层(chasm)」陷阱也是 SQL 的老毛病。比如把订单表与配送事件表连接后再做 SUM，如果一笔订单挂着多条配送事件，营收就会被重复累加。SQL 本身不会对此发出任何警告。得出的数字看起来完全合理，这正是它要过很久才会被发现出错的原因。

3. Malloy 的思路 - 把关系声明为模型，反复复用

3.1 source 与 extend - 定义一次，一直使用

Malloy 的起点是 source。先定义一个指向某张表的 source，再在 extend 代码块里把属于这张表的度量(measure)、维度(dimension)、连接(join)一并绑定进去。官方文档给出的示例如下。

source: airports is duckdb.table('airports.parquet') extend {
  measure:
    airport_count is count()
    avg_elevation is elevation.avg()
}

这样定义出来的 source，成为活在单个文件里、可反复复用的模型。之后任何人用它写查询，都不必再重新琢磨 airport_count 到底数的是什么。

3.2 measure - 把指标封印在名字背后

「准点率」这类在 SQL 里每次都要重复写 CASE WHEN 与过滤条件的指标，在 Malloy 里只需定义一次，之后按名字调用即可。官方仓库给出的示例正好说明了这一点。

measure: on_time_rate is
  count() { where: cancelled = 'N' and diverted = 'N' and arr_delay < 15 }
  /
  count() { where: cancelled = 'N' and diverted = 'N' }

取消、备降的判定标准与延误的界定，这些业务逻辑被固定在唯一一处。此后谁都只需调用 on_time_rate，如果要改定义，只改这一处，就会作用到所有用到这个指标的查询上。

3.3 join_one · join_many - 把连接刻进模型，从语言层面挡住扇出

join_one: carriers with carrier
join_many: flights2 on code = flights2.origin

在 source 定义里声明一次连接，之后的查询就不必重写连接键，只需按名字引用通过关系连过去的字段即可。更重要的是聚合方式。Malloy 采用「对称聚合(symmetric aggregate)」方式计算，确保即便在多表连接的状态下聚合也不会被重复计算。也就是说，无论连接叠加多少层，因扇出导致数字虚高的事故都会在语言层面被挡住 - 这是在 SQL 里必须靠开发者自己用 DISTINCT 或子查询手动防范的问题。

3.4 run 与 nest - 查询里嵌查询，一个结果里装多个分组

run: airports -> {
  group_by: state
  aggregate: airport_count
  nest: by_facility_type is {
    group_by: fac_type
    aggregate: airport_count
  }
}

run: 后面跟着的 -> 管道，把数据从 source 流向查询的结构直接搬进了代码形态。nest 用一个代码块，表达了 SQL 里原本要跑好几遍独立查询、或者写复杂的 GROUP BY ROLLUP 才能做到的「在一个结果里同时装下子分组明细」。执行结果也不再是一张扁平表，而是以嵌套结构返回，上层分组与下层分组的关系直接保留在结果本身里。已经写好的查询还可以存成 view，用 + { } 接续着继续打磨。这些短小的语法片段本身并非什么炫技的新技术，只是把 SQL 原本要求你每次从头重写的东西，挪到了「定义一次、按名复用」的方向上。这个「只是」积累起来，就能让几十个查询文件收敛成一个模型加几行简短调用。

4. 编译为 SQL 意味着什么 - 不是新引擎，而是一层

Malloy 团队将这门语言定位为架在 SQL 之上的一层，而非替代品，并把这种关系比作 JavaScript 与 TypeScript。正如 TypeScript 最终编译为 JavaScript 在浏览器里运行，Malloy 最终也会编译为面向各个数据库的 SQL 执行。这个设计的关键价值在于引入成本: 不需要新的数据库或新的执行集群，只需在已经在用的 BigQuery、Snowflake、Postgres、MySQL 之上叠加 Malloy 的模型文件即可；在本地，甚至不需要任何服务器，直接用 DuckDB 查询 Parquet、CSV 文件。装上 VS Code 扩展后，模式浏览器、可视化查询构建器、结果预览都能直接在编辑器里使用。

5. 「语义层」潮流中的 Malloy - 对比 dbt、LookML、Cube

5.1 谱系 - Looker 遗产分出的三条路

「指标只定义一次、到处复用」这个想法本身并不新。LookML 是这一理念商业化的原型，此后语义层这股潮流分出了几条路。dbt 在自己的转换流水线之上叠加 Semantic Layer，用 YAML 定义指标，通过 dbt Cloud API 提供服务。Cube 是集定义与服务于一体的无头语义层，主打 API、嵌入式分析与 AI 智能体集成。Malloy 与这条谱系同源，却走了一条不同的路: 它是一门不依附于任何特定 BI 产品或转换框架的独立开源语言。

5.2 具体差异何在

工具形态依赖关系执行方式
LookML专有语言仅限 Looker(BI)在 Looker 内部生成 SQL
dbt Semantic LayerYAML 指标定义依附于 dbt 项目通过 dbt Cloud API 提供服务
Cube无头语义层需另建服务基础设施YAML/JS 定义 + API 服务
Malloy独立开源语言无(MIT)编译为 SQL，运行在现有引擎上

5.3 需要冷静看待之处

正如 hada 讨论中有人指出的，C# LINQ 这类既有语言本就能提供类似的声明式查询体验，且支持的数据库更广，这一反驳有其道理。Malloy 的差异化之处，与其说是「发明了全新的东西」，不如说是「把语义建模与查询整合进一门精简的语言，再把结果直接架在既有的 SQL 生态之上」这种整合能力。每个具体拼块都不算陌生，不同的是拼装方式。

6. 实际会变好的地方

可复用: 在一个 source 里定义好度量、维度、连接后，之后所有查询都直接继承这份定义，写新查询的人不必每次重新发明连接条件与过滤逻辑。指标一致: 像 on_time_rate 这样的指标只在一处定义，仪表盘之间数字对不上的结构性原因大幅减少；改一次定义，就会作用到用到它的所有查询。嵌套结果: 用 nest 可以把子分组明细直接装进一个查询结果里，减少了 SQL 里那种要多跑几次查询、再在应用层重新拼合的工作量。可读性: 得益于对称聚合，即便在多层连接之上也无需手动防御 SUM、COUNT，查询本身就直白地表达出「在求什么」。审阅者不必解读一堆子查询，直接就能读懂查询意图。

7. 局限与引入门槛

生态: SQL 拥有几十年积累的工具、教程与人才储备。Malloy 是 2022 年才出现的语言，主要工具只有 VS Code 扩展与 malloy-composer 一类，第三方 BI 集成与社区规模目前还无法与 SQL、dbt 生态相提并论。学习曲线: source/extend、measure/dimension、join_one/join_many、run/nest 这些新概念与关键字，需要整个团队重新学习。团队越是精通 SQL，越容易产生「为什么要学一门新语言」的抵触情绪。缺乏团队标准: 语义模型需要有人拥有并持续维护。如果没有专人或流程去建立并守住这份标准，模型文件本身就有沦为新一堆意大利面代码的风险。既有 SQL 资产: 如果一个组织已经用 SQL 搭建了成百上千的视图、存储过程、BI 仪表盘，把它们迁移到 Malloy 模型本身就是一笔成本。得益于 Malloy 架在 SQL 之上而非取代它的设计，渐进式引入是可行的，但全面迁移仍是另一个项目级别的决定。

8. AI 时代，语义模型为何重新变得重要

正如本站近期在 Wes McKinney 访谈分析 与 「数据是唯一的护城河」分析 中共同指出的，AI 让写代码这件事越便宜，判断「该做什么、什么才是正确定义」这一层就越重要。语义模型正是把这种判断固化成代码的那一层。

如果让 LLM 直接面对原始数据库结构，它每次都要重新推断 SQL、重新组织连接、重新定义指标。在这个过程中，引用不存在的列、连接接错导致扇出使数字虚高、指标定义每次都有细微出入，这类错误会反复出现。而生成的 SQL 在语法上往往看起来毫无问题，这让人更难察觉它其实算错了。

Malloy 阵营里的 malloyyo 一类项目，正是对这个问题的直接回应。它把已经用 Malloy 定义好的语义模型，通过 MCP(Model Context Protocol)直接提供给 AI 智能体，让智能体按名字请求已验证过的度量、维度、连接，而不是从零开始写 SQL。AI 能触及的范围本身被限定在模型之内，计算逻辑也是复用已验证过一次的结果，因此得到的答案更接近「结构上正确」，而非「碰巧算对」。

我自己的解读是: 模型与代码生成越便宜，竞争力就越会转移到架在其上的定义与判断 - 这个论点在数据领域体现得尤其明显。Malloy 这类语义建模语言之所以在 AI 时代重新被关注，不是因为功能变多了，而是因为它是一种打造「已经被公认正确的定义」供 AI 参照的工具。

9. 什么团队适合，如何开始

9.1 什么团队适合

多名分析师反复用不同方式计算同一指标、或不同仪表盘数字略有出入的组织；在多层连接的表结构上频繁踩到扇出问题的团队；既想把数据访问开放给 AI 智能体、又想把控结果准确性的团队，都尤为适用。反之，如果查询多是一次性的、团队也没有余力做标准化，眼下的收益可能不大。

9.2 如何开始 - 用 DuckDB 在本地试

入门门槛很低。在 VS Code 里装上 Malloy 扩展，在一个 .malloy 文件里用 duckdb.table() 定义一个指向本地 Parquet 或 CSV 文件的 source 就够了。不需要另外的服务器、集群或账号，在笔记本电脑上就能立即定义模型、运行 run: 查询看到结果。等找到感觉后，再把同一份模型定义原样迁到 BigQuery、Postgres 这类实际生产引擎上扩展即可。

结论

Malloy 不是一门想把 SQL 挤走的语言，而是想用精简的语法，补上 SQL 从一开始就不擅长的东西 - 关系的复用、指标的一致性、安全的聚合。把它的历史(由已把语义建模语言推向商用规模的人重新设计而成)、它架在 SQL 之上而非取代 SQL 的设计，以及它能为 AI 智能体提供可信定义这一时代性价值叠加起来看，Malloy 更像是一场潮流中的一个节点，而非一次性的实验。不过，生态与团队标准化这两道引入门槛是真实存在的，与其全面铺开，不如先从反复遭遇扇出与指标不一致问题的团队入手，在本地用 DuckDB 轻量试一试更为合理。截至 2026 年 7 月，这门语言能否在语义层之争中胜出还为时尚早，但它精准地指出了 SQL 的老毛病，这一点是确定的。
