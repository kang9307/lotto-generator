把行尾对齐意味着什么 - 两端对齐真正索取的代价

多出来的空间总得有个去处 - 词间、字间、连字符，以及句子本身

2026年8月31日 潮流/文化

引言：右端齐得像用尺子量过的文字

给正文加上两端对齐，通常会出现两种情况之一。栏够宽时看着还算齐整；栏一窄，就有几行明显变得疏松，段落中间留下一道白痕。右端被对齐所付出的代价去了哪里，眼睛比意识更早发现。把对齐改回左端，那道白痕会消失，可这回右侧边缘变成了锯齿状。

最近又被重新翻出来读的一篇文章，正面碰了这个问题。讲的是1990年代后期一位署名rs1n的作者所写的《超级银河战士》攻略。那是一份超过1万7千词的纯文本文档，而每一行的右端都精确对齐。他并没有跑什么排版工具，而是靠挑选词语把句子重写了一遍。用作者自己的话说，他只是仔细挑选了词，好让右边能对上。

先把话说清楚。这是一个人的手艺式尝试，既不是可以推荐给团队的方法，也不是换个工具就能解决的事。这份记录之所以值得读，理由在别处：当排版引擎悄悄完成的工作被人用手接过来做时，那份工作到底在消耗什么，就暴露出来了。

这篇文章不打算裁定两端对齐是好是坏。答案会随语言、媒介和栏宽而变，本来就不会倒向某一边。它要追的是多出来的空间去了哪里：词间、字间、连字符，以及句子本身。这四者之中，总有一个要付账。

1. 行尾参差不齐为什么是默认状态

行长不齐，背后叠着两个原因。

第一个是每个字形的宽度不同。在拉丁文字里，小写的 i 和大写的 W 占据的位置能差上三四倍。同样是八个字母的单词，由哪些字母构成，实际宽度就会不一样。所以数字符数量并不能把行长对齐。

第二个更要紧：换行的位置不是排版者定的，而是单词定的。引擎把单词一个一个放进一行，直到下一个放不下就在那里断开。此时剩下的零头，取决于下一个单词原本有多长。若接连都是短词，零头就小；若后面等着一个长词，零头就大。哪些词接在哪些词后面，是写作的人决定的，不是引擎决定的，因此这段零头是排版阶段无法控制的量。

这里有一种情况值得停下来看。改用等宽字体，第一个原因就消失了：所有字形宽度相同，字符数就是行宽。可是行尾照样参差不齐，因为第二个原因原封未动。等宽的处境甚至更糟：字宽是定死的，把一个空格撑开0.3个字宽这种微调根本不成立。一行要么正好是N个字符，要么就不是。前面那份攻略之所以除了重写句子别无选择，原因就在这里。

于是只对齐左端成了默认做法。左对齐把零头原样留在右侧作空白，换来的是词间空格在整份文档里被固定成同一个值。眼睛只需要记住一种节奏，也不会在哪里是词边界上犹豫。锯齿状的右边缘是观感上的损失，但它同时也给每一行一个可辨认的轮廓，读者回头找下一行时能借它定位。

2. 多出来的空间去了哪里

一旦决定两端都对齐，零头就消不掉，只能分配出去。去处大致有三个，另外还有一个放弃排版、改用文字来解的第四种。

放到哪里什么被撑开适合的条件付出的代价CSS 线索
词间每个空格的宽度用空格分词的语言、较宽的栏每行空格宽度不同；窄栏里白色痕迹会连成竖线text-justify: inter-word
字间字与字之间的间距按字符换行的语言在拉丁文字里，单词不再被看成一个整块text-justify: inter-character（旧值 distribute）
连字符不撑开，而是让这一行能装下更多该语言有词典且 lang 准确时单词被切断；复制、检索、朗读都会留下痕迹hyphens: auto
句子本身什么都不撑开栏宽与字体固定、且文字今后不再改动由人重写句子；栏宽一变，全部作废（不是 CSS 该做的事）

表里的第一行就是网页的默认行为。text-justify 名义上可以指定方式，取值为 auto、none、inter-word、inter-character、distribute。不过 MDN 把它标注为并非 Baseline，也就是说在一些使用最广泛的浏览器里并不生效，因此不能把结果押在这个属性上。真正可靠的是 text-align: justify，以及单独控制末行对齐方式的 text-align-last，后者自2022年9月起已进入 Baseline 广泛可用。

词间方案为什么最扎眼，一行算术就能说清。假设某一行剩下40像素。这一行如果有二十个词间空格，每个只增加2像素，基本看不出来；同样的40像素若由五个空格分摊，每个就是8像素。考虑到一个正常词间空格大约只有四五像素，这几乎等于把空格撑到三倍。要分配的总量一样，分它的人数不一样而已。

  • 一行里空格数量越少，每个要承担的份额就越大；空格数量与栏宽成正比，所以栏越窄，落差越大
  • 长词密集的段落，在同样栏宽下空格更少，因而处境更不利
  • 段落的最后一行通常不参与对齐，若连它也撑开，几个词就会被摊在整行里
  • 字间方案把同样的余量切得细碎得多，但在拉丁文字里会模糊词形，而读者辨认单词靠的恰恰就是词形

3. 当空白在竖向连起来

只有一行变疏，那不过是一行疏行。麻烦出在连续几行里被撑宽的空格恰好横向位置接近的时候。白痕接上，读起来就像一道贯穿段落的河道。英文排版界把它叫作 river。

这个现象并没有被当成纯粹的美观问题。W3C 的 WCAG 理解文档在禁止两端对齐时直接援引了它。

The uneven spacing between words in fully justified text can cause 'rivers of white' space to run down the page making reading difficult and in some cases impossible.
（完全两端对齐时词间距不均，会让白色空白汇成河流沿页面流下，使阅读变得困难，某些情况下甚至不可能。）

为什么窄栏更严重，上一节的算术就是答案。单个空格张得越开越显眼，而显眼的东西在竖向上只要连着出现两三行，人就会把它读成一条线。宽栏里每个空格只增加一点点，谁也不够突出到能连起来。

行距也掺在里面。行与行挨得近，相邻行的空格在物理上更靠拢，更容易被看成连续的形状。所以既然决定用两端对齐，行距就别省。但要认清这是削弱竖向白痕的手段，不是消除它的手段。只要多出来的总量没变，它就还在页面上的某个地方。

4. 是逐行决定，还是通盘看整段

同一段文字、同样的栏宽、同样的字体，排出来的结果也可能明显不同。分水岭在于决定断行时到底看了多大范围。

最简单的方式是逐行填满：能塞多少塞多少，断开，进入下一行，不再回头。快，但弱点是结构性的。前面做出的选择即使毁掉后面的行，也没有修正的机会。如果一个长词被整体挤到第三行，第二行就空了；而假如第二行少收一个词，三行本可以都过得去。要做这个判断得往后看，而这种方式不看。

另一种方式把整段当成一个问题来求解。高德纳与迈克尔·普拉斯1981年发表在Software: Practice and Experience上的方法就是如此。它用盒子（box）、胶水（glue）、罚分（penalty）三种基本元素为段落建模，再用动态规划找出使整段糟糕程度（badness）总和最小的断行组合。这套方法的要点在于：某一行最终的样子，可能受到后面句子的影响。TeX 正是建立在它之上的。

浏览器长期站在速度那一侧，因为每次有人拖动窗口边缘就重新优化整段实在太贵。CSS 的 text-wrap 属性正在填补其中一部分，而它的两个取值性质并不相同。

  • balance — 让各行的字符数量趋于均匀。MDN 指出由于计算开销大，它只在行数有限的文本块中受支持，并举出 Chromium 系为六行以内、Firefox 为十行以内。它是给标题、图注、引文用的
  • pretty — 行为与 wrap 相同，但用户代理会采用一种更慢、以更好的版面而非速度为先的算法。文档把它定位为正文用，并举出把孤行（orphan）降到最少的场景
  • stable — 行为与 wrap 相同，但用户编辑内容时，被编辑行之前的各行保持不动，而不是整块重新回流

说白了，印刷强在不是眼光，而是时间与范围。它有余裕通盘看整段，结果不满意时人可以改一个词再重排，而最重要的是最终栏宽只有一个确定值。在网页上，这三件事一件都不成立。

5. 韩文、日文、中文的情况并不一样

上面所有的讨论，前提都是用空格分词的语言。前提一破，问题的形状就整个变了。

W3C 的国际化资料这样描述日文与中文的换行：不考虑单词或音节边界，直接把单个字符移到下一行。于是行末剩下的零头最多不超过一个字符宽度，需要撑开的量从一开始就很小。日文和中文书籍的正文两端天然齐整，不是因为排版更精细，而是因为本来就没有多少缝隙可开。

韩文处在两者之间。同一份资料指出，现代韩文文本中的词通常用空格分隔，但按音节断行同样常见，在两端对齐的文本里尤其如此。换句话说，韩文可以按英文那一套来排，也可以按中日那一套来排，而选定其一，就等于同时选定了它的代价。

语言默认换行单位剩下的零头随之出现的问题相关 CSS
英文等拉丁文字空格（词）大到相当于下一个词的长度词间被撑开；连字符几乎成为必需hyphens、text-justify: inter-word
日文、中文字符最多一个字符宽禁则处理；并不能随处断开line-break、hanging-punctuation
韩文空格与音节皆可取决于选了哪一种必须先决定是切开词还是撑开空格word-break: normal 与 keep-all

落到 CSS 上，这个选择就写在 word-break 一行里。normal 使用默认的断行规则，而 keep-all 用 MDN 的原话说，就是不对中文、日文、韩文文本使用词内断行。韩文网页里常见 keep-all，原因正在于此：防止一个双音节词被拆到两行。代价也不难料到——把词整个保住，就等于把英文的问题请了回来：零头变大，一开两端对齐词间就撑开，遇上长词或网址还多出溢出的风险。

按字符断行也不是白得的便宜。这里附带着另一套规则，即禁则处理。W3C 的日文排版需求文档把不能出现在行首的字符与不能出现在行尾的字符分开作了规定。

  • 不能置于行首 — 右括号类、句号类、逗号类、间隔号类。不应该出现以句号开头的行
  • 不能置于行尾 — 左括号类，以及问号、叹号这类分隔符号
  • 要遵守规则，就把字符推到下一行，或者从下一行拉上来
  • 这一推一拉靠加大或压缩字间距来吸收。日文排版原则上是字间不留空的密排，因此这项调整本身就是行调整处理
  • 在 CSS 里用 line-break 的 loose、normal、strict 选择规则的宽严。anywhere 会忽略断行禁则，并且在该取值下不应用连字符

印刷排版里另一个用了很久的手法，是让标点悬挂到版心之外。CSS 提供了 hanging-punctuation，其 allow-end 取值允许句号或逗号在对齐处理之前放不进本行时悬挂在行尾。不过 MDN 同样把这个属性标为并非 Baseline，所以只能当成锦上添花的装置，缺了也不该塌。

最后，真实文档往往是混排的。中文段落里嵌着英文产品名和网址，就意味着两套体系在同一段里同时运转。汉字部分切得很细，而拉丁字母的那一串却是整块移动，于是只有落到那一串的行才会把词间猛地撑开。这篇文章要以四种语言发出去，等于把同一段排版四次；若假定同一份样式表在四种语言里给出同样的结果，恰恰会在这个地方错位。

6. 连字符真正在做的事

让英文的两端对齐勉强能用的，其实是连字符断词。能在词中间切开，就意味着零头很少会整整占掉一个词的长度，词间被撑开的理由也就相应减少。所以不带连字符的两端对齐，通常是最糟的组合。

网页上开启它的属性是 hyphens，取值有三个。

  • manual — 默认值。只有当文本中存在提示断行机会的字符时才断词。什么都不做，就处在这个状态
  • none — 词内不断开，即便标了断点也忽略
  • auto — 浏览器在合适的位置断词，依据文档的 lang 属性进行，并且只有在所声明语言存在相应的断词词典时才生效

最后一条是实务中最常绊住人的地方。设了 hyphens: auto 却什么都没发生，先怀疑 lang 缺失或写错。把语言声明错了更糟：引擎会按另一种语言的词典规则去切，断在莫名其妙的位置上。

手工标记断点的字符也有两个。用 &shy; 写入的 U+00AD 软连字符是不可见的，只有当浏览器确实要在那里断开时才显示出连字符；U+2010 硬连字符则即使该处并不断行，连字符也照样绘制出来。两者混用会让文档里既有看不见的标记又有看得见的字符，所以最好定下只用其中一种。

连字符要付的账，并不都在版面上。

  • 意思会被搅浑。并非哪里都能断，断点得顺着词素边界走，这正是必须有词典的原因
  • 复制与检索会对不上。连字符只是屏幕上生成的，还是作为字符实际存在，结果会不同；若是实打实的字符，用原词去搜就搜不到
  • 可能影响朗读。屏幕上渲染出来的连字符无妨，但嵌进文本里的会改变朗读的单位
  • 韩文、日文、中文没有对应物。这些语言不用连字符切词，那个位置由按字符断行与禁则处理来顶替

前面那位攻略作者避开连字符的理由，就在这份清单里：碍眼，而且妨碍复制粘贴。在纯文本文档中，连字符不是渲染效果，而是实际写进文件的字符，因此这个判断在那里分量格外重。

7. 改写句子来迁就版面这个思路

说到这里，那份攻略究竟做了什么就清楚了。他并没有放弃排版，而是把排版的负担挪到了写作这一侧。与其请引擎去分配多出来的空间，不如挑选那些宽度加起来正好等于目标值的词。

得到的东西很明确。

  • 没有一个空格被撑开，所以竖向白痕根本无从产生
  • 没有连字符，词是完整的，复制出来也原样不变
  • 各行密度一致，整段的灰度均匀
  • 约束会把文字逼得更短更准，拖沓的表达因为塞不进尺寸而自动脱落

失去的东西同样明确。

  • 只在一个宽度上成立。窗口一窄或者字号一大，前提整个塌掉。必须配上等宽字体加固定列数才算稳
  • 有些句子改不动。引文、专有名词、代码、数字、法律条文，没法靠换词来调节长度
  • 维护成本会累积。前面改一个字，后面所有行都要重新断，于是改一个错别字变成重写一整段
  • 经不起翻译。换到另一种语言，这个性质不会保留，每种语言都得从头再做一遍
  • 读者一改设置就失去意义。放大字号阅读的人、用语音收听的人，本来就收不到对齐这件事，留给他们的只是为了迁就尺寸而压缩过的句子

有意思的是，这个思路在小尺度上早已是日常：为了把按钮文案塞进方框而换个说法，为了让表头留在一行而删掉两个字，把菜单项的长度修得彼此接近。全是同一个动作。差别只在于对象是一行还是整篇文档，而正是这个差别把能用的和不能用的分开了。一行可以改写，一万七千个词不行。

8. 无障碍 - 只谈已确认的部分

有一条标准条款直接处理两端对齐：WCAG 2.2 成功准则 1.4.8 视觉呈现。引用时常被漏掉的两个前提先摆在这里。

  • 等级是 AAA。以 AA 为目标的多数站点并不受这条准则约束
  • 这条准则把五项要求捆成一束，只改对齐并不算满足

这五项是：前景色与背景色可由用户选择；宽度不超过80个字符或字形（中日韩为40个）；文本不做两端对齐；段落内行距至少为一倍半，段间距至少为行距的1.5倍；不借助辅助技术放大到200%时，仍能在不横向滚动的情况下读完一行。对齐那一项的原文是：

Text is not justified (aligned to both the left and the right margins).
（文本不做两端对齐——不同时贴齐左右两侧页边。）

理解文档给出的理由有两条。其一，部分认知障碍人士阅读同时贴齐左右两端的文本存在困难，随后接的就是上一节引用的竖向白痕解释。其二，方向相反：两端对齐也可能把单词挤得过近，使人难以定位词的边界。该准则的受益一节说明，这一项帮助有认知、语言与学习障碍的人感知文本，并在成块的文字中不丢失自己的位置。

重要的是到此为止，不要再往前迈。标准提供的是要求及其理由，而不是效应量。文档里并没有「对齐会让阅读速度下降百分之几」这类数字。而从宽度那一项把中日韩单独列为40个字符可以看出，这条准则本身就预设了条件会随书写系统而变。

落到实务上是这样：读者可以改变字号的正文，不宜强制两端对齐。若还是要用，那么开启断词、加宽栏、放大行距这三件事确实能缩小行与行之间的落差，但不能消除它。

9. 实务中该定下什么

「请用两端对齐」和「不要用两端对齐」都没什么用。换成按顺序问四个问题，答案大体就自己出来了。

要问的撑得住两端对齐的一侧撑不住的一侧
最终栏宽是否固定印刷品、PDF、宽度固定的卡片与标签响应式网页、由读者缩放的屏幕
一行能容下多少个词一行能装下不少词的栏宽窄栏、移动端单栏、侧边栏
该语言的断行单位是什么日文、中文；韩文允许按音节断时英文而无法开启连字符时；韩文使用 keep-all 时
文字今后还会不会改印一次就完事的文档频繁修改的文档、会产生译本的文档

顺序是有理由的。栏宽不定，再怎么调也控制不了读者看到的结果；栏宽定了，下一个才是一行分摊零头的余力，有这份余力，针对语言的处置才谈得上有意义。最后一问根本不属于排版，而属于运营：手工调过的断行只在文字不动的期间有效。

真正要动手的地方，其实就那么几处。

  • 把 lang 声明准确。断词、断行规则、字体回退都在这里分叉
  • 英文正文要用两端对齐，就同时开 hyphens: auto。只开一样通常是净亏
  • 韩文里要先于对齐把 word-break 定下来。真正决定右端形状的是它，不是 text-align
  • 标题、图注这类短块用 text-wrap: balance，但要把行数限制当作前提；正文可以考虑 text-wrap: pretty，只是后者管的是版面质量而非对齐方式
  • 不要把结果押在非 Baseline 的属性上（text-justify、hanging-punctuation），只当作有则更好的装置
  • 留一条媒体查询，在窄宽度下关掉两端对齐。桌面端看着没问题的段落在手机上塌掉，是最常见的失败路径
  • 定下来之后，用手上最不利的段落去验：长词和网址混在一起的那一段

结语：把行尾对齐意味着什么

对齐右端表面上是观感问题，到了执行阶段却变成一个分配问题：多出来的空间要摊给谁。摊给词间，就长出竖向白痕；摊给字间，词形就变模糊；摊给连字符，词被切开还得配一部词典。此外还有最后一个选项——由人把句子重写一遍。

那份攻略展示的，正是把最后这个选项推到底会发生什么。成品是美的，条件是苛刻的：一个宽度、一种字体、不做修改。这三条在实务中几乎不会同时成立，所以它更该被当作一份记录而不是一套技法来读。

而这份记录留下的实用结论，朴素得出人意料。两端对齐不是一个决定，而是一个有条件的选择。栏宽固定、一行有余力分摊零头、语言能切得细、文字今后不会再动，那它值得用；四条里缺了任何一条，左对齐都是更安静的答案。锯齿状的右边缘不是排版的失败，而是决定守住词间宽度所留下的痕迹。

未能确认的部分

  • 那份攻略所用的确切列宽（每行字符数）以及写作时使用的编辑器 — 未能从原文中确定
  • 两端对齐对阅读速度或理解度影响的量化数值 — WCAG 只以叙述方式给出理由，未包含效应量，也未能找到单独的对照研究
  • text-wrap: pretty 在各浏览器中实际采用何种算法 — MDN 只说到「更慢的算法」与「把孤行降到最少」为止
  • 整理韩文排版需求的标准文档中禁则规定的细节 — 本文关于禁则的叙述以日文排版需求（JLREQ）为依据，不能保证可以直接对应到韩文
  • hanging-punctuation 与 text-justify 在各浏览器中的最新支持范围 — MDN 只标注它们并非 Baseline。文中的像素数值也是为便于说明而设的假定值，并非实测
