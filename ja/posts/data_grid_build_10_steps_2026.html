データグリッドを自作すると、なぜ崩れるのか

要件3つまでは足し算、4つ目からは掛け算 - 表UIが見た目より難しい本当の理由

2026-07-29 IT・技術

はじめに: 「表を一つ描くだけ」が3週間の叙事詩になる地点

データグリッドを段階的に作ってみる実装記は、開発者コミュニティで周期的に回ってくる。面白いジャンルだ。最初の段階はいつも30分で終わり、最後の段階あたりで筆者はたいてい「だから皆ライブラリを使うのか」という一文にたどり着く。この記事はそうした記事の特定の一本を要約するものではない。出発点となった記事を特定できなかったため、他人の目次を写す代わりに「データグリッドを自前で実装する」という問題そのものを扱う。

そしてこの記事はチュートリアルではない。「こう作りましょう」とは言わない。答えようとする問いは二つだ。「自作するか否かをどう判断するか」、そして「作るとしたら正確にどこで崩れるか」。コードは概念を示す最小限しか出てこない。

原則を先に打ち込んでおく。この記事の技術的記述はMDN、W3CのWAI-ARIA実装ガイド(APG)、各プロジェクトの公式文書で2026年7月29日に直接確認したものであり、確認できなかった主張は外した。特定のライブラリを推奨したり順位づけしたりはせず、ライブラリに関する記述は公式文書に書かれた設計・ライセンスの事実に限る。

1. 足し算から掛け算へ - 要件3つと4つの間

表UIが難しいという言葉はよく聞くが、なぜ難しいのかはあまり説明されない。核心は機能の数ではなく、機能どうしの相互作用の数だ。

ソート、フィルタ、ページネーション。ここまではほとんど互いに干渉しない。三つとも「データ配列を受け取って別の配列を返す関数」に整理でき、レンダリングはその結果をただ描く。順序を決めてパイプラインに挟めば終わりだ。だから最初の三日間は楽しい。

四つ目から性質が変わる。仮想スクロール、列固定、列幅変更、セル編集、キーボードアクセシビリティはデータではなくレンダリングと操作の状態に触れる。そしてこの状態は共有資源だ。スクロール位置、DOMに実際に存在する行の集合、フォーカスの所在、レイアウトを誰が計算するか。五つの機能がこの四つの資源を同時につかむ。

機能の組み合わせ性質ぶつかる資源体感の難度
ソートデータ変換なし半日
ソート + フィルタデータ変換適用順序ぐらい一日
ソート + フィルタ + ページネーションデータ変換フィルタ後の総件数の再計算二日
+ 仮想スクロールレンダリング状態DOM行の集合、スクロール位置週単位に入る
+ 列固定レイアウト重ね合わせコンテキスト、横スクロールさらに数日、ブラウザ差あり
+ 列幅変更レイアウトレイアウトアルゴリズム、再計算の頻度仮想スクロールと再衝突
+ セル編集フォーカス・入力フォーカスの所在、変換中の状態IMEを含めると急増
+ キーボードアクセシビリティ構造の決定タブ順、フォーカスの所有権後付けなら書き直し

表の右端の列が言っていることは単純だ。日程を出すとき機能の数を数えると間違える。機能の対の数を数えたほうが実態に近い。五つの機能なら対は十個で、その十個それぞれが「この二つが同時に有効なとき何が起きるか」という独立した問いだ。

以下の各節はその問いを一つずつ開いていく。

2. 仮想スクロールが静かに持ち去るもの

仮想スクロールの原理は一文だ。見えている範囲の行だけDOMに作り、残りは作らない。十万行を描かずに三十行だけ描くから速い。ここまでは誰でも作れる。

問題はその後だ。ブラウザの多くの標準機能が「文書に存在する」という前提の上で動くのに、仮想スクロールはまさにその前提を壊す。

  • ページ内検索 — ブラウザの検索は文書にあるものしか探さない。消した行は検索対象ではない。利用者は表の値を見つけられないのではなく、存在しないと結論づける。
  • テキスト選択とコピー — ドラッグで数画面をまたいで選択する操作が成立しない。スクロール中に後ろの行が消えるからだ。
  • アクセシビリティツリー — スクリーンリーダーにとっても存在しない行だ。ここでARIAによる補正が必要になる。
  • 表のセマンティクス — 仮想化のためによく使われるのが表要素のdisplayを変える方法だが、MDNはこの点を明示的に警告している。
  • ブラウザ既定のアンカリング — スクロール途中で上側の内容の大きさが変わると位置が飛ぶ。5節で別に扱う。

四つ目は引用に値する。MDNのdisplay文書はアクセシビリティの項で、一部のブラウザでは表要素のdisplay値をblock・grid・flexに変えるとアクセシビリティツリー上の表現が変わり、表が適切に読み上げられなくなると記す。同じ文書はdisplay: noneが要素をアクセシビリティツリーから取り除くこと、そしてdisplay: contentsが一部のブラウザで要素自身をツリーから取り除くが、それは仕様に照らして誤った挙動であることも併記している。つまり「見た目だけ変えた」つもりの一行が意味構造に触れている。

ARIA側の補正は決まっている。MDNのaria-rowcount文書は、この属性が表・グリッド・ツリーグリッドの全体の行数を定義し、値が-1なら大きさが不明という意味で、ブラウザに総行数を数えないよう伝えるものだと説明する。そしてすべての行が常にDOMにあるわけではないときにこの属性を入れるよう明記する。全行が読み込まれてDOMにあるならブラウザが自動的に数えるので不要だ。W3CのAPGグリッドパターンも同じ趣旨を記す。行や列が隠れていたりDOMになかったりするとき、たとえばスクロール時にデータが動的に読み込まれるとき、aria-rowcount・aria-colcountをaria-rowindex・aria-colindexと併せて使い、全体の大きさと現在見えている項目を区別して伝える。

概念だけ見ればこういう形になる。実際のマークアップははるかに長いが、要点は「見えているのは30行だが全体は12万行」という事実をコード自身に語らせることだ。

<!-- 全12万行のうち、4万12番目からだけがDOMにある -->
<div role="grid" aria-rowcount="120000" aria-colcount="6">
  <div role="rowgroup">
    <div role="row" aria-rowindex="1">
      <span role="columnheader" aria-colindex="1">注文番号</span>
      <span role="columnheader" aria-colindex="2">顧客</span>
    </div>
  </div>
  <div role="rowgroup">
    <!-- 手前の4万行余りはDOMにない。だからindexを直接伝える -->
    <div role="row" aria-rowindex="40012">
      <span role="gridcell" aria-colindex="1">A-40012</span>
      <span role="gridcell" aria-colindex="2">山田</span>
    </div>
  </div>
</div>

ここで分かれ道が一つできる。行を本当に消すのか、それとも残したままレンダリングだけ省くのか。MDNのcontent-visibility文書は後者のための値を説明する。autoはレイアウト・スタイル・ペイントの封じ込めを有効にし、要素が利用者にとって関連しなければ内容をスキップするが、スキップされた内容はページ内検索やタブ順の移動といったユーザーエージェント機能に通常どおり提供され続け、フォーカスも選択も通常どおり可能だ。一方hiddenはスキップされた内容がそうした機能からアクセス可能であってはならず、選択もフォーカスもできない。同じ文書はcontain-intrinsic-sizeで大きさの見積もりを与えてレイアウトのずれを減らす例を挙げている。

似た発想はHTML側にもある。MDNのhidden属性の文書はuntil-found状態が要素を隠しつつ、その内容をブラウザのページ内検索やフラグメントナビゲーションからアクセス可能にすると記し、それらの機能が当該要素へのスクロールを引き起こすとブラウザがbeforematchイベントを発火させ、hidden属性を取り除いてからスクロールすると説明する。ブラウザは通常content-visibility: hiddenで実装すること、そして要素のdisplayがnone・contents・inlineだとこの方法では現れないという条件も併記されている。

結論は二者択一ではなく規模の問題だ。数千行ならDOMに残してレンダリングだけ削る方式がブラウザの標準機能を保ちながら十分速い。数十万行ならノード数そのものが負担になるので消さざるを得ず、その瞬間から検索・選択・アクセシビリティを自前で作り直すコストが見積もりに入る。この判断を先にせず「とりあえず仮想化」で始めると、後から戻す代償が大きい。

3. 列固定 - stickyの一行で終わらない理由

「最初の列を固定してください」は会議で3秒で終わる要求だ。実装が3秒で終わらない理由は、position: stickyが孤立した属性ではなく周囲の構造に依存する属性だからだ。

MDNのposition文書が記すstickyの定義をほどくと、条件が三重になっている。第一に、要素は文書の通常フローに従って配置された後、最も近いスクロール祖先と包含ブロックを基準にtop・right・bottom・leftの値に応じてオフセットされる。定義には表関連の要素を含むと明記されている。第二に、固定したい軸でインセットプロパティのうち少なくとも一つがauto以外の値でなければならず、その軸の両インセットがautoならrelativeのように振る舞う。第三に、sticky要素はoverflowがhidden・scroll・auto・overlayに設定されてスクロール機構が生じた最も近い祖先に貼り付き、その祖先が実際にスクロールする祖先でなくてもそうなる。そしてこの値は常に新しい重ね合わせコンテキストを作る。

三つの条件が実務でどう事故に変わるか見てみよう。

  • 途中のラッパー一つ — デザイン上の理由でoverflow: hiddenを与えたラッパーが表とスクロールコンテナの間に挟まると、固定列はそのラッパーに貼り付く。そのラッパーはスクロールしないので、固定が何もしていないように見える。エラーも警告も出ない。
  • インセットの抜け — 縦のヘッダー固定にはtopを与えたのに、横の列固定でleftを落とすと、その軸だけ静かにrelativeになる。ヘッダーは効くのに列は効かない状態のよくある原因だ。
  • 重ね合わせコンテキスト — stickyが新しい重ね合わせコンテキストを作るため、固定列の上に浮くべきドロップダウンやツールチップやリサイズハンドルの階層が意図とずれる。z-indexを上げても効かない場合がここから来る。
  • 角のセル — ヘッダー行と最初の列が交わるセルは両方の軸で固定でなければならず、両方向で他のセルより上になければならない。この一マスのための規則が別途必要になる。
  • 境界線の所有権 — MDNのborder-collapse文書はcollapseで隣接セルが境界線を共有し、separateではそれぞれが自分の境界線を持つと定義する。共有された境界線を固定セルとスクロールするセルのどちらが描くのかが曖昧になるため、実務では結合モードを避けて影や内側の影で境界を表現する選択をすることになる。
  • 影 — 固定列がスクロール中のときだけ影を見せたいなら「いま横にスクロールされているか」を知る必要があるが、この状態はCSSだけでは分からず、スクロールイベントが再登場する。

概念レベルの最小例はこの程度だ。実際のコードでは各固定列のleft値が先行する列の実幅の合計でなければならないので、列幅変更が有効になった瞬間、これらの値が動的に計算される必要がある。次節の主題がまさにそれだ。

/* スクロールコンテナ: stickyが貼り付く対象を明確にする */
.grid-scroll { overflow: auto; max-block-size: 70vh; }

/* ヘッダー行: 縦軸のインセット(top)が必ず要る */
.grid-scroll thead th { position: sticky; top: 0; z-index: 2; }

/* 固定列: 横軸のインセット(left)が必須。値は先行列の幅の累計 */
.grid-scroll .col-fixed-1 { position: sticky; left: 0;     z-index: 1; }
.grid-scroll .col-fixed-2 { position: sticky; left: 120px; z-index: 1; }

/* 角のセル: 両軸で固定 + 両隣より上 */
.grid-scroll thead .col-fixed-1 { z-index: 3; }

/* 共有境界線の所有権問題を避け、境界は影で表現する */
.grid-scroll table { border-collapse: separate; border-spacing: 0; }
.grid-scroll .col-fixed-2 { box-shadow: 1px 0 0 0 #e0e0e0; }

4. 列幅変更 - レイアウトアルゴリズムを先に選ぶ問題

列の境界をドラッグして幅を変える機能は、マウスイベント三つで済みそうに見える。実際には表のレイアウトアルゴリズムを何にするかを先に決める問題だ。

MDNのtable-layout文書は二つのアルゴリズムを区別する。既定のautoは表とセルの幅を内容に合わせて調整する。fixedは表の幅を明示的に指定する必要があり、指定しないかautoならブラウザは自動アルゴリズムに戻る。固定アルゴリズムでの各列の幅は、明示的な幅を持つ列要素があればその値、なければ最初の行のセルに指定された明示的な幅、それもなければ残りの横方向スペースを分け合った値で決まる。性能についての記述も明確だ。固定アルゴリズムは横方向のレイアウトが表の幅と列幅、境界線やセル間隔にのみ依存し、セルの内容には依存しないため自動アルゴリズムより速く、最初の行を受け取って解析した時点で表全体をレンダリングできる。

この一文が幅変更機能の設計を事実上決めてしまう。自動アルゴリズムでは一つの列の幅を変えるとブラウザが他の列も再計算するので、利用者がA列を広げたのにC列が縮む現象が起きる。ドラッグ中はこの再計算がフレームごとに走る。固定アルゴリズムを使えばこの問題は消えるが、代わりにすべての列の幅をアプリが自分で所有しなければならない。つまり機能一つが状態を一つ新たに生み出す。

この状態ができると、他の要求が芋づる式に続く。

  • 固定列のオフセット — 3節で見たleft値がもはや定数ではない。列一つの幅が変われば、その後ろの固定列のオフセットを全部計算し直す必要がある。
  • 仮想スクロールとの関係 — 横方向まで仮想化したなら、画面にない列の幅も分からないとスクロール領域の総幅を出せない。
  • 内容のはみ出し処理 — MDNは固定アルゴリズムで後続のセルの内容が与えられた幅に収まらないことがあり、セルははみ出た内容を切るかどうかを決めるためにoverflowプロパティを使うと記す。省略記号とツールチップが必要になる地点だ。
  • 内容に合わせるダブルクリック — 境界をダブルクリックして内容に合わせる慣習的な操作は、固定アルゴリズムでは内容の幅をアプリが自分で測る必要がある。仮想スクロールを有効にしていれば、画面外の行は測定対象ですらないという問題まで付く。
  • ドラッグ中の性能 — 毎フレーム状態を更新すると、見えているすべてのセルが再描画される。CSS変数で幅を渡して再レンダリングを起こさない、といった迂回が必要になる。
  • 永続化 — 利用者が調整した幅は保存されて初めて意味を持ち、列構成が変わったときの以前の設定の扱い方という規則がさらに要る。

この一覧が1節で言った掛け算の具体的な姿だ。「列幅変更」という一行の要求が、実際には六つの決定を連れてくる。

5. 可変の行高 - スクロールバーが嘘をつき始める

すべての行の高さが同じなら、仮想スクロールの計算は算数だ。全体の高さは行数 × 行高であり、スクロール位置を行高で割れば最初に見える行の番号が出る。スクロールバーの長さと位置も正確だ。

行高が内容によって変わった瞬間、この算数が崩れる。描く前には高さが分からず、高さを知るには描くしかないからだ。実務で使う方法は見積もり値を置いて実際に描いた行の高さで更新することだが、ここで特有の症状が出る。

  • スクロールバーが伸び縮みする — 下に行くほど実測値が見積もりを置き換えるので全体の高さが変わる。つまみがスクロール中に大きさを変える。
  • 上に戻すと位置が飛ぶ — 上側の行の高さが更新されると下の内容の位置がずれ、利用者が見ていた行が画面外に出る。
  • 最後まで到達できない — 見積もりの合計が実際より大きいと、最後の行に届いてもスクロールが残っているように見える。
  • 「N番目へ移動」が不正確 — 特定の行へ飛ぶにはその手前の行の高さの合計が要るが、その合計が見積もり値なら目的地に正確に立てない。
  • ウィンドウのサイズ変更で全部無効化 — 折り返しが変われば、すでに測った高さがすべて古い値になる。

ブラウザにもこの系統の問題を扱う仕組みがある。MDNのoverflow-anchor文書はスクロールアンカリングを、内容の移動を最小化するようスクロール位置を調整するブラウザの挙動と説明する。ビューポートより上の内容の大きさが変わったり新たに読み込まれたりしたとき、見ていた地点をつかんでおく機能だ。autoはその要素をアンカー候補にし、noneは除外する。ただし同じ文書はこの機能が広く使われている一部のブラウザで動作しないためBaselineではないという限定的な利用可能性を併記している。つまり補助手段としては有用だが、これに寄りかかって設計はできない。

だから実際の選択肢は三つに絞られる。行高を固定して内容を切るか、高さの階級を数種類に制限するか、完全な可変を許して上の症状をそれぞれ処理するか。三つ目を選んだときにかかるコストをあらかじめ知っておくことが、この節の目的だ。

6. セル編集 - フォーカス管理とIMEという二つの壁

表の中で値を直す機能は、データグリッドを表示装置から入力装置へ変える。そして入力装置には表示装置になかった要求が付く。

一つ目の壁はフォーカスだ。W3CのAPGグリッドパターンは編集のあるグリッドのキー動作を規定する。Enterはグリッド移動を無効にして編集モードに入るか最初のウィジェットにフォーカスを与える。F2は編集モードやウィジェットフォーカスを切り替える。英数字キーは編集モードに入る。Escapeはグリッド移動を復元する。セルの中にウィジェットが複数あればTabとShift+Tabがウィジェット間を行き来する。

この規定自体は明確だ。問題はこれが仮想スクロールと出会う地点だ。編集中のセルがスクロールで画面を外れると、その行はDOMから消え、フォーカスを持つ要素がなくなる。ブラウザはフォーカスを文書本体に戻し、利用者はさっきまでいた場所を失う。戻ってきたときに同じセルへフォーカスを復元するには、「どの行のどの列が活性か」をDOMではなくアプリの状態として持っておく必要がある。この要求は7節で見る構造の決定とまったく同じ要求だ。

二つ目の壁はIMEで、日本語・韓国語・中国語の環境では特に大きい。MDNはcompositionstartイベントが入力メソッドエディタ(IME)のようなテキスト変換システムが新しい変換セッションを開始したときに発生すると定義し、ピンイン入力メソッドで漢字を入力し始める場面を例に挙げる。そしてKeyboardEvent.isComposingの文書は、この読み取り専用プロパティがイベントが変換セッションの中で、すなわちcompositionstartの後compositionendの前に発生したかを示す真偽値だと記す。

二つの事実を先ほどのキー規定に重ねると、衝突が見えてくる。

  • Enterの二重の意味 — 変換中のEnterは候補の確定だ。グリッドがEnterを「保存して下のセルへ」と処理すると、利用者は一度押しただけなのに確定と移動が同時に起きる。ラテン文字の環境ではこのバグは再現しない。
  • Escapeの二重の意味 — 変換中のEscapeは変換の取り消しだ。APGはEscapeをグリッド移動の復元と規定するので、変換を取り消そうとした利用者が編集そのものを失う。
  • 英数字キーで編集開始 — この慣習はキー入力がそのまま文字になるという前提に立っている。入力メソッドが有効なら、その入力は変換セッションに属するので、最初の一文字が消えたり編集器が開かなかったりする。
  • 矢印キー — 変換中の方向キーは候補リストの移動だ。グリッドがこれをセル移動として奪うと候補を選べない。
  • 入力値の検証タイミング — 変換途中の文字列は完成していない状態だ。入力のたびに検証すると、正常な入力の最中にずっとエラーが出る。

解の方向は一つだ。変換セッション中はグリッドがキーを奪わない。概念コードに移すとこの程度になる。

// セル編集器のキー処理 - 変換セッション中はグリッドが介入しない
input.addEventListener('keydown', (e) => {
  // MDN: isComposing は compositionstart の後 compositionend の前なら true
  if (e.isComposing) return;   // 候補の確定・取消・移動は入力メソッドの領分

  if (e.key === 'Enter')  { commitAndMoveDown(); }
  if (e.key === 'Escape') { cancelAndRestoreGridNavigation(); }
});

// 変換が終わってから検証する - 途中の文字列は完成形ではない
input.addEventListener('compositionend', () => validate(input.value));

この八行がないと、英語圏のテストはすべて通り、日本語や韓国語の利用者だけがバグに遭う。ライブラリを評価するとき、この項目が実際に処理されているかを確認するほうが、機能一覧の長さを比べるよりはるかに有用だ。

7. アクセシビリティが最後に付かない理由

アクセシビリティの作業には二種類ある。後から付くものと付かないものだ。ラベル、コントラスト、キャプションは前者だ。MDNのtable文書は、表の目的を明確かつ簡潔に説明するcaptionが、残りの内容を確認するか読み飛ばすかの判断を助けると記し、thのscope属性は単純な文脈では推測されるので冗長だが、一部の支援技術は正しい推測に失敗しうるので明示すれば体験が改善されることがあると書く。複雑な表ではidとheadersの組み合わせで各セルを関連するヘッダーとプログラム的に結びつけるよう案内している。こうしたものはいつ入れても入る。

付かないほうがキーボードによるグリッド移動だ。理由は、これがマークアップの追加ではなくフォーカスの所有権に関する構造の決定だからだ。

W3C APGのキーボードインターフェース開発の案内は原則を短く記す。タブ順には複合UIコンポーネントの焦点を当てられる要素を一つだけ含めるべきであり、複合ウィジェットが焦点を得た後はTabとShift+Tab以外のキーで内部要素の間を移動する。セルが一万個ある表でTabを一万回押さないと抜け出せない状況を防ぐ規則だ。実装方法としては二つが示される。ローミングtabindexは現在フォーカスされる対象にtabindex="0"、それ以外にtabindex="-1"を置き、移動時に二つの値を入れ替えてからfocus()を呼ぶ方式で、ブラウザが新たにフォーカスされた要素を画面内へスクロールしてくれる利点がある。aria-activedescendantはコンテナだけをタブ順に残し、活性な子のidを指す方式で、支援技術はDOMフォーカスがコンテナにあっても参照された要素をフォーカスされた要素とみなす。

二つの方式の共通点が核心だ。セルは自分のフォーカスを自分で決めない。活性な座標を知っている主体は上位のコンテナだ。したがって、すでに各セルが独立にフォーカスを管理する作りにしてからこの原則を導入しようとすると、セルコンポーネントのインターフェースと状態の所有構造を一緒に変えなければならない。追加ではなく書き直しだ。

APGグリッドパターンが規定するキーの一覧も、先に知って始めたほうがよい。方向キーは一マスずつ横・縦の移動、Page Up/Page Downは複数行の移動、HomeとEndは現在の行の先頭と末尾、Ctrl+HomeとCtrl+Endは最初の行の最初のセルと最後の行の最後のセルだ。選択に対応するならCtrl+Spaceが列の選択、Shift+Spaceが行の選択、Ctrl+Aが全選択、Shift+方向キーが選択の拡張になる。ロールの側はコンテナにgrid、行にrow、セルにcolumnheader・rowheader・gridcellが来て、ソートされたヘッダーにはaria-sort、選択された要素にはaria-selected、編集できないならaria-readonlyが付く。

// ローミングtabindexの骨格 - 活性座標はセルではなくコンテナが所有する
let active = { row: 0, col: 0 };   // アプリの状態。DOM ではない

function moveTo(row, col) {
  active = clampToBounds(row, col);
  // 仮想スクロールなら目標の行が DOM にないことがある - まず描画させる
  ensureRowRendered(active.row);
  const cell = findCell(active.row, active.col);
  setRovingTabindex(cell);   // 直前のセルは -1、新しいセルは 0
  cell.focus();              // ブラウザが画面内へスクロールしてくれる
}

grid.addEventListener('keydown', (e) => {
  if (e.key === 'ArrowDown')  moveTo(active.row + 1, active.col);
  if (e.key === 'ArrowRight') moveTo(active.row, active.col + 1);
  if (e.key === 'Home')       moveTo(active.row, 0);
  if (e.ctrlKey && e.key === 'Home') moveTo(0, 0);
});

ここでensureRowRenderedの一行が2節と7節をつないでいる。アクセシビリティの要求が仮想スクロール実装の内部を呼び出す。二つの機能を別々に作れないという意味であり、これが「後から付ける」が失敗する理由だ。

9. 自作する条件とライブラリを使う条件

「自作するな」という助言は半分しか正しくない。自作したほうがよい場合は確かにある。判断基準をチーム規模・要件の数・寿命の三軸で整理するとこうなる。

10. ライブラリの設計の違い - 事実だけ

ライブラリ選びの話に移るが、順位はつけない。代わりに公式文書に書かれた設計上の分岐だけを押さえる。この分岐を知っていると比較表の読み方が変わる。

一つ目の分岐はレンダリングを含むかだ。TanStack Tableの公式文書は自らをTS/JS・React・Vue・Solid・Qwik・SvelteのためのヘッドレスUIライブラリと紹介し、ヘッドレスUIがマークアップもスタイルも作り置きの実装も提供しないと明記する。代わりに提供するのは関数と状態とユーティリティとイベントリスナーであり、データ処理と状態管理とビジネスロジックを担い、マークアップとスタイルの完全な制御を開発者に残すと記す。同じ文書はより軽い表やデザインの完全な制御が欲しければヘッドレスを、デザインとバンドルサイズが厳しい制約ではなくすぐ使える実装が欲しければコンポーネント方式を検討せよ、と線を引いている。

ここで誤解がよく生じる。ヘッドレスを選んだからといって、この記事の2節から7節が消えるわけではない。データのパイプラインと状態はライブラリが担うが、マークアップ・ARIAロール・フォーカス管理・IMEの処理は依然として自分で書く仕事だ。つまりヘッドレスは1節の「前の三つ」を肩代わりし、「後の五つ」はそのまま残す。

二つ目の分岐はライセンス区分だ。AG Gridの公式ライセンス・価格ページはコミュニティ版がMITライセンスであることを明かし、エンタープライズ版は別の使用許諾契約と1年分の更新を含むと記す。機能の区分もページに表として提示されている。基本的な列操作・テキスト/数値/日付フィルタ・行選択・基本のセル編集器・CSV出力がコミュニティ側で、集合フィルタと高度なフィルタ、セル範囲選択とフィルハンドル、一括編集と取り消し、Excel出力、クリップボード連携、行グループ化とピボット、ツリーデータ、マスター詳細、サーバーサイド処理、統合チャートなどがエンタープライズ側だ。サポート窓口もコミュニティはGitHub、エンタープライズは別の窓口と区分される。

この事実が実務で持つ意味は一つだ。機能一覧を先に確定してからライセンス区分を確認する。順序が逆だと、無料区分で始めて半年後に要件一つのために急いで購入判断を下すことになる。

11. 作ると決めたなら - 崩れない順序

自作する方向に決めたなら、順序が結果を大きく変える。前の各節の衝突は多くが「後から入れるつもりだったもの」が構造を要求するときに爆発するからだ。だから構造を要求するものから入れる。

  • まず要件一覧を閉じる — 「後から追加されるかもしれない」項目まで書く。1節の表でどの行まで下るのかを確認するのがこの段階の目的だ。
  • 活性座標をアプリの状態にする — どの行のどの列が活性かをDOMではなく状態として所有する。アクセシビリティ・編集・仮想スクロールの三つがすべてこの値を要求する。
  • 単一タブストップを最初から適用する — セルごとにフォーカスを与える構造で始めると戻しにくい。
  • レイアウトアルゴリズムを初期に確定する — 列幅変更がロードマップにあるなら、固定アルゴリズムと幅の状態を最初から置く。
  • 仮想化の要否をデータ規模で決める — 要らなければ入れない。仮想化はブラウザの標準機能を返してもらうコストを連れてくる。
  • ARIAロールとインデックス属性をレンダラーに付けておく — 後から走査して入れる方式は仮想化と併用するとずれる。
  • 編集器は変換セッションを尊重するように作る — 6節の八行を最初から入れる。後から入れると再現しづらいバグ報告として返ってくる。
  • スクロールコンテナを一つに確定する — 途中のラッパーにoverflowを与えないという規則をチーム内で文書化する。
  • キーボードだけで全機能を試す手順を作る — マウスだけで検収すると7節の欠陥がリリースまで生き残る。
  • 日中韓の入力で編集を手で試す — 変換セッションを自動テストで再現するのは難しい。
  • 性能目標を行数ではなく操作で立てる — 「10万行のレンダリング」ではなく「ドラッグ中のフレーム維持」が実際の体感だ。
  • 撤退計画を書いておく — どの要件が追加されたらライブラリへ移るかを事前に決めておけば、その瞬間の判断が感情論にならない。

この一覧の前の四つが構造で、残りが手順だ。構造を後回しにすると手順では取り返せない。

結論: 難しいのは表ではなく組み合わせだ

データグリッドが難しいという言葉は正確ではない。表を描くことは易しい。難しいのは八つの機能が同じ画面でスクロール位置・DOM行の集合・フォーカス・レイアウトという四つの資源を同時につかむときに生じる組み合わせだ。だからこの問題のコストは機能一覧の長さではなく、機能の対の数に比例する。

そしてこの記事が繰り返し示した一つのパターンがある。後から付けられるものと付けられないものがはっきり分かれる。ラベルとキャプションは付く。フォーカスの所有権、活性座標を持つ主体、レイアウトアルゴリズムの選択は付かない。この三つは初日の決定であり、先送りすれば後から書き直しとして返ってくる。

だから実用的な結論は「作るな」でも「作れ」でもない。要件一覧を先に閉じ、1節の表で自分がどの行まで下るのかを確認することだ。三行目で止まるなら自作のほうが軽くて正確だ。五行目より下へ行くなら、残る問いは「どう作るか」ではなく「この複雑さを何年間、我々が所有するのか」だ。

最後にこの記事の態度をもう一度書いておく。ここに書かれた制約は誰かの実力の問題ではなく、ウェブプラットフォームの文書化された挙動だ。だから先に読んでおけば、3週間の叙事詩を三日の決定に縮められる。
