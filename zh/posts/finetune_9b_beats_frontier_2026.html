500美元微调超越前沿模型这件事

小模型在窄任务上取胜的条件，以及训练费之外的总成本

2026-07-30 IT/技术

引言: 这篇文章核实了什么，又没能核实什么

「用500美元微调的9B开源模型超越了前沿模型」这句话正在流传。这类句子总会被朝两个方向读错。一边读成「那我们也自建模型吧」，另一边读成「多半是挑好看的数据说事」。两种读法都产生不了可执行的判断。

这篇文章只回答一个问题。在窄任务上微调小模型，什么时候才真的能赢过前沿API。并且要把这个「赢」拆成在指标上赢与在总成本上赢。这两者经常给出相反的答案。

先把本文证据的状态说清楚。引发讨论的原文发表在fermisense.com上，地址已经确认。但是在笔者这边，那个页面两次都返回HTTP 403而打不开。因此原文并未被直接读到。本文引用数字时所依据的，只有实际打开并确认过的两处：一家技术新闻站点对该文的摘要，以及关于它的Hacker News讨论帖。

所以先明确列出因为无法核实而没有写进本文的内容：基座模型的确切身份(只有9B这个规模得到印证)、被比较的前沿模型名称与配置、训练所用GPU的型号与时长、训练数据来源数据集，以及权重、代码、数据是否公开。这些条目在二手检索结果中确实出现过，但没有对着原文核实，所以本文不把它们当作事实使用。与其填上不存在的数字，不如把空栏留成空栏。

有意思的是，这个处境本身就是本文的主题。一个说某样东西「超越」了另一样的主张，其价值完全取决于条件栏里写了什么。条件无法核实时，那个主张只能当方向用，不能当依据用。本文所有成本数字都是虚构的示例，并在出现的地方逐一标明。

1. 把「超越」这一个词拆开

公开摘要与讨论能够支撑的范围是这样。任务是电商目录审核：查看商品的登记信息，使用分类体系与品牌相关工具抽取属性，然后判定是通过还是上报。训练采用强化学习一类的方法，摘要写到使用了177,767条审核回合。结果是训练过的9B模型拿到可达成分数的87.3个百分点，最好的前沿配置为76.9个百分点。比较是在相同工具、相同评分器、相同回合预算下进行的。

这里必须先把「超越」的准确含义定下来。这句话不是说通用能力更强。它说的是在一套评分细则上分数更高，而那套细则是这家公司为自己的工作流制定的。

最扎心的一点 - 评分器同时就是训练信号

公开讨论里最锋利的一点是这个。如果用于训练的评分函数与用于评估的评分函数相同，那么这个分数可能是模型把评分器的缺陷也一起忠实学会的结果。讨论中有人直接问，既然没有说明训练集、验证集与留出集如何分离，读者怎么知道这不只是过拟合的结果。

这不是找茬，而是用强化学习去学窄任务时的结构性风险。模型会把我们衡量的东西抬上去。如果评分器只看五个属性字段是否被填满，模型就会学到把五个字段填得像样的办法。内容对不对评分器没有问过，因此也就没有被学到。

200个回合能不能支撑10个百分点的差距

讨论中提到评估规模为200个回合。这里有一件可以自己算一算的事。下面计算里的标准差是笔者设定的假设，不是作者公布的数值。

  • 把单个回合的分数视为0到1之间的值并假设标准差为0.3，那么200样本均值的标准误就是0.3除以200的平方根，约0.021，也就是约2.1个百分点。
  • 两种配置之差的标准误大致是它的根号2倍，即约3.0个百分点。
  • 87.3与76.9之间的10.4个百分点差距超过它的3倍。因此方向本身很难用噪声来解释。
  • 反过来，如果像摘要所示各个前沿配置彼此聚集在小数第一位之内，那个排名就完全落在噪声之内。「哪个前沿模型排第几」是没有内容可读的数字。
  • 实务结论 - 读这类报告时只把大差距当方向接受，小数位一律丢掉。并且不要把没有区间估计的排行榜当排行榜用。

还有一点。讨论中也指出前沿一侧的基线到底投入了多少提示词打磨并未公开。把基线公平地调好比跑一次训练便宜，而且通常应该排在更前面。

2. 窄到底意味着什么 - 要多窄才成立

接下来讲原理。前沿模型的强项是通用性。它能不做准备就接住没见过的请求、含糊的指示和层层缠绕的推理。这种能力不是免费来的。代价以词元单价与延迟的形式计入账单。

于是问题变成：我们的任务在用这份通用性吗。如果同一个判定一天要重复数万次，输出是固定模式，判断标准写在内部文档里，那就说明我们在为用不到的通用性按次付费。

不过「窄」这个词太松了。必须拆成六个维度才能用于判断。

窄的维度成立的一侧不成立的一侧核实办法
输出空间封闭标签集合或固定模式自由撰写，每次长度都不同的文档能否把输出写成模式文件
可评分性用规则、模式或查询可自动评分正确与否需要人来解释能否把评分器写成代码
定义的稳定性标签体系一年以上没变过定义每个季度都在动过去四个季度标签体系改过几次
重复量每月数十万条以上每月几千条，峰值很尖能否估算服务GPU的利用率
规则的体量与隐性程度几百页规程加上没写进文档的惯例能压缩成两三页的规则规则能否全部塞进提示词
单条上下文短 - 一个商品，一份文档长 - 需要综合几百页能否放进小模型的有效上下文

第五个维度才是决定性的

规则的体量与隐性程度是六个维度里最常被误读的一个。人们把微调的依据落在「小模型便宜」上，但真正让前沿模型赢不了的是价格之外的知识缺失。

准确地说是这样。前沿模型不知道你们公司的分类体系。它没有理由出现在预训练语料里。它也不知道你们团队三年里积累的「这种情况要退回」的判例。把那份知识送进模型的通道只有三条。

  • 写进提示词 - 如果规则只有两三页，这就是答案。便宜、可以立刻回退，而且对审计更友好。
  • 用检索按需送进去 - 如果规则有几十页并且已经以可查询的形式文档化，这就是答案。规则变了改文档就行，不需要重训。
  • 训练进权重里 - 只有当规则达到几百页的量，或者本来就不是文档而是判例时，才剩下这条通道。人也是靠干几个月而不是靠读规程才学会的那类判断，就属于这里。

只有第三条通道能为微调提供正当理由。而实务中常见的错误是在第一条通道就够用的任务上去挖第三条。跑训练之前必须先问：我们想灌进去的知识能写成文档吗。如果能写，写下来送进去几乎总是更好的选择。

如果需要微调本身的步骤或基础概念，那部分在机器学习自学路线图里另行讲过。本文只看排在它之前的那个判断。

3. 总成本不是训练费

这一节是本文最贴近实务的部分。500美元是一次训练。而且是成功的那一次。真实项目里，训练不会一次就过。

一旦开始清算总成本，表格的形状就变了。下面整理的是哪些项目会被计到哪一侧。

成本项目自建微调前沿API为什么容易从算式里漏掉
任务定义与标签体系文档化需要需要被当成本来就要干的活，从不计入成本
人工标注的评测集必备必备最常被漏掉。没有它连优劣都判不了
训练数据获取需要 - 通常最贵不需要用自动生成压低后，成本转移到评分器的可靠性上
训练执行的GPU时长需要不需要「500美元」所指的唯一一栏
失败的训练尝试需要不需要只有成功那一次被报道，于是从读者的算式里消失
常驻的服务GPU需要不需要第二常被漏掉。不调用费用也在流走
推理单价GPU时长除以吞吐按词元计价单位不同无法并排，必须换算成单条成本
重训周期需要厂商承担标签体系每变一次就重新计费
漂移监控必备建议没察觉的话质量会安静地下滑
值班与容量管理需要厂商约定模型服务器进入自己的故障处置范围
模型代际更替自己做厂商做半年后出了更好的开源模型就要从头再来
审计与可复现占优 - 权重可以固定不利 - 版本会动自建明确占优的唯一一栏
数据外流没有需要合同与评审本是与微调无关的另一个问题，却常被混在一起

把表格竖着读，会剩下一句话。自建微调是把成本从厂商那里搬进自己的组织。它不是消失了，而是从词元账单变成了工资与GPU租金。而工资不会出现在用量看板上。所以自建模型看起来比实际更便宜。

用虚构数字并排看一看

  • 工作量 - 单条输入1,500个词元，输出200个词元。
  • 虚构API单价 - 每百万输入词元3美元，每百万输出词元15美元。因此单条0.75美分。
  • 虚构自建服务 - GPU每小时2美元，全天常驻则每月730小时。做冗余用两张卡就是每月2,920美元。
  • 虚构训练费 - 每次500美元，每季度重训一次 → 每月167美元。
  • 虚构评测集更新 - 每季度人工标注200条，每条2美元 → 每月133美元。
  • 虚构运维人力 - 0.2个全职当量，按月薪8,000美元计 → 每月1,600美元。
  • 自建固定成本合计 - 每月4,820美元。其中GPU占2,920，人力占1,600。

这张表里倍数不是重点。该看的是两列的形状。API列是直线，自建列是阶梯。所以规模越大自建越占优在结构上是成立的。问题在于阶梯第一级有多高。

而最能撬动那第一级的并不是GPU。在上面的示例里，把1,600美元的人力成本写成零，盈亏平衡点就从约64万条降到约43万条。放弃冗余把GPU减到一张，则落在约45万条。也就是说，一栏人力成本比一整张GPU更能移动盈亏平衡点。而在实务方案里，最常被写成零的那一栏正是人力成本。

4. 把盈亏平衡点写成结构式 - 让变量露出来

固定的盈亏平衡数字并不存在。存在的只有结构式，读者要把自己的数字代进去。

每月API成本   = N x (T_in x p_in + T_out x p_out)

每月自建成本  = G x H x p_gpu        常驻服务GPU
              + C_train / M          训练费按重训周期摊分
              + L                    运维监控人力
              + E / M_e              评测集更新

  N        每月处理条数
  T_in     单条输入词元       T_out  单条输出词元
  p_in     输入词元单价       p_out  输出词元单价
  G        常驻GPU数量 (含冗余与灰度余量)
  H        每月运行小时数 (全天常驻则为730)
  p_gpu    GPU每小时费率
  C_train  一次训练的费用     M      重训周期 (月)
  L        每月运维人力成本   E      评测集更新成本

盈亏平衡条数:

  N* = (G x H x p_gpu + C_train/M + L + E/M_e)
       / (T_in x p_in + T_out x p_out)

  N < N*    前沿API 更便宜
  N > N*    自建模型 更便宜

  注: 自建成本是几乎与 N 无关的阶梯函数。
    G 只在吞吐超过一张GPU的极限时才加 1。
    API成本是与 N 正比的直线。
    所以 N* 必然存在，但决定它位置的
    往往不是 p_gpu 而是 L。

写出这个式子不是为了给出答案。而是为了让哪一栏正在被操纵变得可见。下表汇总了实务中各个变量如何被写得有利。

变量含义实务中被操纵的方式
N每月处理条数写成均值而不是峰值，从而低估所需GPU数量
T_in, T_out单条词元数用短示例而不是生产提示词去量，结果只有一半
p_in, p_out词元单价剔除缓存与批量折扣按标价写，把API一侧抬高
G常驻GPU数量抽掉冗余与灰度余量，写成一半
H每月运行小时数假设夜间停机，实际却从不去做停机自动化
p_gpuGPU每小时费率按可中断价格写，却不为中断时的应对计成本
C_train, M训练费与重训周期只算一次并把重训当成不存在，失败尝试也不算
L每月运维人力成本最常被写成零。这一栏在很大程度上决定平衡点位置
E, M_e评测集更新误以为一开始做一次就够了

没有填上最后三行的成本清单不算成本清单。把重训、人力、评测集都置零，自建模型永远都赢。那份算式赢的原因不是模型好，而是栏位空着。

5. 利用率决定盈亏平衡点 - 而适配器会改变它

API与自建服务最大的差别不是单价。是利用率。API的利用率永远是1。不调用就一分不花。而自建模型的GPU即使没有请求，费用也在流走。

有效单条成本(自建) = (G x H x p_gpu + 其他固定成本) / N

利用率 u = N x (单条GPU秒数) / (G x H x 3600)

  u = 0.05    你为空着的95%的GPU小时付钱
  u = 0.30    仍然是API容易更便宜的区间
  u = 0.60    有余量而浪费少。以这里为目标
  u > 0.85    峰值时排队堆积。需要把 G 加一

  注: API 的利用率实际上永远是 1。
    自建模型的利用率是要由我们管理的变量。
    如果一个任务填不满一张GPU，
    那个项目的盈亏平衡点永远不会到来。

这里出现了实务上最有价值的转换。按任务为单位算利用率，几乎总是很糟。单个窄任务很少能填满一张GPU。但如果窄任务有五个，情况就不同了。

把适配器叠起来，就能分摊阶梯的第一级

只列官方文档可以确认的事实。首先是适配器训练。PEFT官方文档把LoRA描述为用两个较小的矩阵通过低秩分解来表示权重更新。并写明原始权重矩阵保持冻结、不再接受任何调整，最终结果由原始权重与适配后的权重合并得出。

  • 文档写到LoRA通过大幅减少可训练参数的数量使微调更高效，而这个数量主要由秩r和原始权重矩阵的形状决定。
  • 由于预训练权重保持冻结，文档明确指出可以在同一个基座之上拥有多个轻量且可移植的LoRA模型，服务于各种下游任务。这一句是本节的核心依据。
  • 文档写到由于适配器权重可以与基座模型合并，LoRA不会增加任何推理延迟。
  • 文档写到在Transformer中LoRA通常只应用于注意力模块，并表述用LoRA微调的模型性能与全量微调相当。

接下来是部署。vLLM官方文档说明它支持在单个基座模型之上同时提供多个LoRA适配器。文档写到请求会依据服务端全局的LoRA配置来处理，在max_loras设得足够大时可以与基座模型请求并行，也可能与其他适配器请求并行。

  • 相关配置项文档列出了--enable-lora、--lora-modules、--max-loras、--max-lora-rank与--max-cpu-loras。
  • 除了在服务启动时加载之外，文档写到还可以在运行中通过专用API端点动态配置适配器，这需要VLLM_ALLOW_RUNTIME_LORA_UPDATING环境变量。
  • 不过文档同时给出安全警告：如果不是完全可信的环境，不要在生产中使用这项运行时更新功能。功能存在与可以打开是两个不同的判断。

把这两个事实合起来，盈亏平衡计算的单位就变了。想用一个任务为一张GPU找正当理由，通常会失败。但如果在同一个基座模型之上，把审核、分类、抽取、归一化、去重判定这样的五个窄任务做成适配器叠上去，固定成本就由五个任务分摊。

因此实务指引可以这样归纳。微调的盈亏平衡点要按平台为单位算，而不是按项目为单位算。并且即使第一个任务过不了平衡点，只要第二个和第三个任务确定会来，判断就可能不同。只是这时必须区分「看起来会来」和「已经定了会来」。用还没到来的任务论证下来的GPU，就是一张空转的GPU。

另外要提醒一点。引发讨论的那个案例据称使用了强化学习一类的方法，那和适配器训练不是一回事。上面关于LoRA的事实是用来解释「为什么近年训练费降到了这个程度」和「为什么可以叠多个适配器」的背景，并不是对那个项目训练方式的描述。把这条界线抹掉，就会把别人的成本结构误当成自己的。

6. 真正的交付物不是模型而是评测集

这一节是本文最希望被长久记住的部分。一个微调项目的交付物有三样。

  1. 训练出来的权重 - 半年就旧了。更好的开源模型出现，标签体系变化，商品品类增加。
  2. 任务定义、输出模式与评分细则 - 不会变旧。反而越用越精确。
  3. 人工标注的评测集与切片定义 - 同样不会变旧。而且正是它给出更换模型的自由。

有了第2样和第3样，第1样就成了消耗品。新的开源模型出来就跑同一套评测集，更好就换。前沿API降价了就用同一套评测集重新量，再换回来。评测集是唯一能降低迁移成本的资产。反过来没有评测集就会被现在用的东西锁住，因为无从判断好坏。

这套锁定结构本身，已经在AI厂商锁定的六个层次与退出策略里逐层拆解过，那里把微调当作最强的锁定层来处理。本文只看用什么来抵消这种锁定。答案是评测集。

eval/
  task.md         任务定义。什么算通过，什么算上报
  schema.json     输出模式。字段名、类型、允许值
  rubric.md       评分规则。部分分怎么给
  cases.jsonl     人工标注的判定样例。故意放入边界样例
  slices.yaml     切片定义。新品类、无图、多语言等
  scorer.py       自动评分器。必须是确定性的
  human/          与自动评分器分离的人工复核层

每次更换模型都跑同一套东西

在自动评分器之上再加一层人工

第1节里最扎心的那点在这里回来了。如果只用当初作为训练信号的那个自动评分器来评估，就无法发现模型学到了评分器的缺陷。指标会一直往上走，而真实质量可能原地不动甚至下滑。

  • 只把数据分开还不够 - 留出集回合怎么分都行，但只要评分器相同，评分器的盲区就原封不动地留着。
  • 哪怕薄也要留一层人工 - 从自动评分器给了满分的判定里抽样，让人再看一遍。这样就能得出「评分器判通过但人看是错的」的比例。这才是真正需要盯的那个数字。
  • 按切片分开看 - 整体均值会吞掉那些很少出错但一出就很严重的切片。新品类、没有图片的登记信息、多种语言混在一起的条目这类薄但会出事故的切片要单独量。
  • 故意植入边界样例 - 只收集容易样例的评测集放进任何模型都会得满分。那样一来这套评测集就帮不了任何决定。
  • 先把检查体系弄坏试试 - 故意把几条标签改错放进去，确认分数是否真的下降。如果不降，那之前所有的绿灯都没有任何意义。

7. 在微调之前先试的事

顺序是从便宜且容易回退的开始。下面六步里，大多数团队在第三步就越过了目标。

  1. 把任务拆开 - 一个提示词里混着五个判断时，连哪个判断错了都不知道。拆开之后准确率会提高，而且能按拆分单位看出究竟只有哪一块难。需要训练的通常只是其中一个。
  2. 做出评测集 - 从200到500条的规模开始。边界样例必须混进去。跳过这一步再往下走，之后所有判断都只是印象。
  3. 用模式强制输出并打磨提示词 - 把自由文本改成固定模式，仅此一项就能大幅减少后处理错误。而且把基线公平地调好比跑训练更便宜。
  4. 用检索送入规则 - 如果规则塞不进提示词，先看检索而不是训练。规则变化时只改文档就行的结构能活得久得多。
  5. 加上路由与缓存 - 容易的条目交给规则或小模型处理，只把含糊的上交前沿。重复请求做缓存。实务里相当一部分成本削减来自这里，而且一次训练都不用跑。
  6. 然后再微调 - 上面都做完指标仍然不够，任务定义已经冻结，评测集与自动评分器齐备，重复量足以填满利用率。只有这四个条件同时成立时。

模型代际每半年换一轮的节奏在模型发布对比里另行整理过。在代际更替很快的窗口里，做到第5步然后等待本身也是一种决定。问「往更底层搬有没有价值」的思考框架，与把Python迁移到Rust这个决定是同一套。

8. 不该做的信号

这一边比正面信号更清楚。下面任何一条中了，答案就是现在不做。

  • 任务定义还在变 - 训练是把当下的标签体系钉进权重里。下个季度多一个品类就要从头再来，而在那期间业务一侧只能等模型。
  • 没有人负责标签质量 - 标签一晃动，模型就精确地学会那份晃动。而那种错误不会出现在用同一批标签算出的指标上。
  • 没有评测集 - 这不是信号而是前提条件未达成。判不出有没有变好，就会得到不知道何时算完成的项目。
  • 每月调用量偏低或峰值很尖 - 空着的GPU小时也要自己付钱。这时自建模型输在利用率而不是单价上。
  • 监管要求解释判定依据 - 训练出来的权重无法还原成规则。在审计里回答说模型是学出来的并不管用，而且每次重训都要重新接受审计。这种情况下把规则引擎放在前面、让模型做辅助更合适。
  • 输出是自由撰写的文本 - 正确与否需要人来解释，就造不出训练信号，自动评分也不成立。
  • 说不出数字形式的成功标准 - 「更准一点就好」不是标准。必须先写下哪个指标在哪个切片上要达到多少。
  • 只有一个人维护 - 训练流水线、评分器与部署栈是三种不同的技术。那个人一走，剩下的就是没人能修的便宜模型。

最后压缩成可用的形态。右边一列比中间一列更重要，因为在多数情形下结论之前还有要先核实的东西。

情形结论先核实什么
内部规则几百页，标签体系已固定两年，每月数百万条做微调评分器能否写成代码。人工复核层能否撤掉

结论: 微调不是换模型，而是把任务定下来

先从这个案例真正展示了什么说起。在足够窄的任务上，小的开源模型可以在特定评分细则上拿到比前沿配置更高的分数，而做到这件事的训练成本已经降到数百美元的量级。前半句不新鲜。新的是后半句。

没有展示的部分也要说清楚。总成本并没有写在那500美元旁边。可复现性未能核实。而「超越」的统计稳健性要知道评估规模与评分器如何分离才能判定，而这靠一份公开摘要判不出来。此外笔者没能打开原文页面。所以基座模型的身份、被比较的模型、训练硬件在本文里都留成了空栏。

实务者要带走的有三点。

  1. 看到「取胜」这类主张时，去对照任务的窄度条件。输出空间、可评分性、定义的稳定性、重复量、规则的体量与隐性程度、单条上下文。六项里只要有一项与自己的情形不同，那个结果就不属于我们。
  2. 把500美元旁边的空栏填上。标注、评测集、常驻服务GPU、重训、漂移监控、人力。决定盈亏平衡点位置的不是GPU费率，而是人力成本与利用率。并且盈亏平衡点要按平台为单位算，不是按项目为单位算。
  3. 先把评测集做出来。无论最后做不做微调，半年后剩下的就是它。权重会旧，任务定义、评分细则和标注过的判定样例不会旧。有了这些，模型是可以换的。

最后一句。微调难的地方不是训练。难的地方是把「什么算正确」写成机器能评分的形式。这件事做完，训练就成了几百美元的最后一步；这件事做不完，无论花多少钱都不知道到底哪里变好了。所以这个决定真正的问题不是要用哪个模型，而是我们是否准备好把这个任务定下来。
