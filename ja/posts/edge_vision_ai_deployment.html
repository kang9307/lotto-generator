映像AIを現場機器に置くと決めたら - その決定があらかじめ決めてしまうもの

回線・遅延・規制のどれが理由かで設計が分かれる。そして精度よりランタイムが先に決まる

2026-09-01 IT・技術

映像認識のプロジェクトが揺らぐ場所は、たいていモデルではない。精度はオフィスですでに出ていたし、デモも回った。問題はその後に来る。カメラが12台から60台に増え、設置場所が会議室から工場の通路や屋外ゲートに変わり、回線がオフィスのギガ級から現場のアップリンクに変わる瞬間だ。ここで開き直る問いは「モデルをどう小さくするか」ではなく「この作業を現場に置くのか」である。

そしてその決定は、一度下されるとその後の選択肢の大半をあらかじめ決めてしまう。どのアクセラレータを使えるか、どのモデル系列を候補に入れられるか、何をサーバーへ上げられるか、配備後の更新をどうするか。すべてがここで分かれる。この記事はその決定をどう下すか、そしてその決定が実際に何を決めてしまうのかを順に押さえていく。

本稿は映像認識システムの配置構造についての一般的な整理であり、特定の製品・企業に対する評価や推奨ではない。引用したライセンス・文書の内容は2026年9月初め時点の公開資料に基づくもので、条件は後に変わりうるため実際の導入前に原文の確認が必要だ。法令部分は条文そのものの紹介であり、個別の事案に対する法律助言ではない。

映像は全部上げて処理するという前提が壊れる地点

ほとんどのデータは出来事があったときに生まれる。注文が入れば注文が一件でき、ログインすればログが一行できる。映像は違う。何も起きていない間も同じ速度で生まれ続ける。これが映像認識の配置決定を別種の問題にする第一の理由だ。

数字に置くと感覚がつかめる。1080p の映像一台を 4Mbps で24時間流すと、一日でおよそ 43GB になる。カメラ30台なら一日 1.3TB、一か月で 40TB 近くだ。ここで重要なのは、この値が平均ではなく下限だという点である。場面が複雑だったり夜間ノイズが乗ったりすれば可変ビットレートは上へ張り付く。静かな明け方だからといって半分に減りもしない。

ここにアップリンクの非対称が重なる。現場に入る回線はたいてい下りが広く上りが狭い。オフィスでうまく回っていた構成が現場で崩れる理由は、モデルが重くなったからではなく送り出す通路が狭くなったからである場合のほうがはるかに多い。保管も同じ方向へ増える。保存期間を数日延ばすことと、カメラを数台増やすことが同じコスト軸に並ぶ。

上げられない三つの理由は別々の設計を要求する

「クラウドへ全部は送れない」という一文の中には、異なる三つが混ざっている。回線と保管にかかる金、フレームから動作までの時間、そして映像がその場を離れてはいけないという規制や契約だ。この三つは結論が同じに見えても要求する設計がまるで違う。だからプロジェクトの初期に必ず一つへ絞る必要がある。

三つを一緒くたにすると、よくこういう結果になる。実際の理由はコストなのに遅延を減らすと言って高価なアクセラレータを買い、回線費はそのまま残る。あるいはデータが出てはいけない状況で推論だけを現場に置き、デバッグ用のサムネイルとクラッシュレポートは外へ出続ける。境界は推論にだけ引くものではない。

上げられない理由実際に要求することこれを読み違えると
回線・保管コストアップリンクへ出るバイトを減らすこと。判定は数秒遅れても差し支えない場合が多い遅延を減らそうと高性能アクセラレータを買う。肝心の毎月出ていく費用はそのままだ
応答遅延フレーム到着から動作出力までの時間の上限。平均ではなく最悪値を押さえる必要がある平均遅延だけ測って通す。人が問題と感じるのはたまに跳ねる区間だ
データが出てはいけない境界を物理的に引くこと。推論だけでなくログ・サムネイル・クラッシュダンプ・モデル更新経路まで含まれる推論だけ現場に置き、付随的な経路から映像が漏れ続ける
  • コストが理由なら最適化の対象はモデルではなくアップリンクのバイトだ。モデルを半分にしても原本を上げ続けるなら何も変わらない
  • 遅延が理由なら合格基準をパーセンタイルで書く。平均40ミリ秒は合意文にならない
  • 規制が理由なら最初に描くのはアーキテクチャではなくデータが通るすべての線だ。遠隔支援セッションとログ収集器が最もよく抜ける
  • 三つのうち二つ以上が本当に重なる場合もある。そのときも優先順位は一つでなければ折衷案は出ない

原本ではなくイベントを上げる

配置決定を実際に実行可能にするのは、発想の転換ひとつだ。現場に置くのはモデルではなく映像をイベントに変える変換である。カメラが作り出すのは果てしないピクセルの流れだが、システムが必要とするのはたいてい数個の文だ。「3番ゲートで14時22分07秒にフォークリフトが停止線を越えた」といった類の。

先の数字で計算し直すと差が見える。時刻・分類・座標・信頼度に小さなサムネイルを一枚添えたイベントが 20KB で、カメラ一台が一日200件を作るとしよう。30台全体が一日に作るデータはおよそ 120MB だ。原本を上げるときの 1.3TB と比べれば四桁の差である。これらの値は仮定から出た算数であって測定値ではないが、仮定を二、三倍動かしても桁はひっくり返らない。

  • イベントに変えた瞬間、後段のシステムはありふれたデータパイプラインになる。映像専用のインフラが要らなくなる
  • 代わりに失うものが生まれる。イベントとして捕まらなかった場面は、存在しなかったことになる。後から見返せない
  • だから初期の数か月は意図的に多めに残し、判定基準が安定してから絞る順序が安全だ
  • 保管ポリシーは技術の決定ではなく運用・法務と一緒に決める決定である。後から付けると、すでに溜まったデータが問題になる

境界をどこに引くか

原本かイベントかは二択ではなく連続した目盛りだ。どこに目盛りを置くかが、回線コスト・再学習の可能性・個人情報の露出範囲を一度に決める。この一行が事実上のシステム設計書である。

実務でよく使われる境界はおよそ五か所だ。上へ行くほど情報が多く残り、コストとリスクも一緒に上がる。

境界の位置サーバーへ上がるもの取り戻せなくなるもの合う状況
原本を全量すべてのフレームなしカメラが少数で回線に余裕があり、再学習データが切実な初期段階
イベント前後のクリップ判定の瞬間を含む短い映像判定されなかった区間の場面人が最終確認をしなければならない判定
イベント + サムネイルメタデータと低解像度の画像一枚原本の画質でしか見えない根拠産業検査・計数のように判定が明確な作業
イベントのメタデータのみ時刻・分類・座標・信頼度場面そのもの。誤判定を目で確認できない映像自体を残してはいけない区間
集計値のみ時間あたり件数のような統計個別事案の追跡可能性回線が極端に細い遠隔地
  • 境界はカメラごとに違ってよい。実際出入口区域と生産ラインに同じポリシーを使うほうがおかしい
  • 境界を下げるのは簡単だが上げるのは難しい。すでに捨てたフレームは戻らない
  • だから境界の決定には戻す費用も併記しておく。保管費よりもう一度集める費用のほうがたいてい大きい

現場機器が強いてくる制約

現場に置くと決めたなら、その機器はデータセンターのサーバーとは別物だ。ファンを入れられない密閉ケースに入り、電源は既存の配電盤から引き、夏には周囲温度が上がる。発熱の限界は性能の限界より先に来る。ベンチマークで出た処理量は短い区間の値であり、実運用は数か月を連続で回っている状態だ。

メモリも性格が違う。サーバーでは足りなければ増やせばよいが、現場機器のメモリはたいてい固定で拡張スロットがない。モデル一つではなくデコーダ・前処理バッファ・追跡状態・OS が同じメモリを分け合っている。カメラ台数を増やすと、まずここで引っかかる。

  • 持続処理量と瞬間処理量は違う。温度が上がるとクロックが下がる構造では、30分後の値が本当の値だ
  • 電力予算はケースではなく現場が決める。既存の配電容量に収まらなければ電気工事がプロジェクトに付いてくる
  • 物理的なアクセスが高い。再起動一回に人が移動しなければならないなら、安定性は快適さではなく費用項目だ
  • 供給期間が重要になる。開発ボードは手に入りやすくても、3年後に同じモデルを買えるかは別の問題だ
  • 起動後の自動復旧が基本要件だ。停電は予定どおりには来ないし、現場はたいてい無人である

ランタイムが精度より先に決まる場所

ここがこの話題で最もよく順序の逆転する場所だ。ふつうは精度の表を見てモデルを選び、そのあとハードウェアを付ける。現場配備では逆である。アクセラレータはモデルを実行しない。演算子を実行する。そのアクセラレータのランタイムがサポートしない演算がモデルの中にあれば、その部分は別のところで回るしかない。

ONNX Runtime の文書はこの構造を明示的に説明している。実行プロバイダは GetCapability() インターフェースで自分が引き受けられるノードとサブグラフを申告し、ランタイムはそれに従ってグラフを分割する。そしてプロバイダ一覧は優先順位順だ。['CUDAExecutionProvider', 'CPUExecutionProvider'] と指定すれば、可能なノードは CUDA が引き受け、残りは CPU が引き受ける。

この設計のおかげで変換が丸ごと失敗することは稀だ。問題は失敗しないという点そのものにある。モデルはちゃんと動き結果も合っているのに、グラフの途中の数ノードが CPU へ落ち、その継ぎ目ごとにメモリを往復している。期待した処理量が出ない理由は、どこにもエラーとして残らない。

  • モデル候補を絞るとき、精度の隣の欄に「対象ランタイムで丸ごとオフロードされるか」を一緒に書く
  • 確認方法は文書ではなく実行だ。対象機器で一度変換してみることのほうが表を読むより速い
  • 後処理に特異な演算が入っているなら、その部分だけモデルの外へ出すほうがよい場合が多い
  • そもそも NMS なしで終わるよう設計された系列もある。Ultralytics は2026年1月に公開した YOLO26 が既定のヘッドを一対一構造にして、NMS なしで端から端までの予測を出すと文書に記している

変換の段階で静かに変わるもの

変換は形式だけを変える作業ではない。精度を落とした瞬間、結果も一緒に動く。ONNX Runtime の文書はこれを遠回しにせず書いている。量子化は損失のない変換ではなく、モデルの精度に否定的な影響を与えうる、と。だから同じ文書が、元のグラフと量子化されたグラフの重み・活性値テンソルを比較するデバッグ用ツールを併せて案内している。

選択の基準も文書に出ている。再帰型ニューラルネットワークとトランスフォーマ系には動的量子化を、畳み込みニューラルネットワークには静的量子化を勧める。静的方式は較正用の入力を先に流して量子化パラメータを求め、定数として埋め込むため、較正データが実際の現場の場面と違えば、その差がそのまま精度に乗る。事後量子化で目標に届かなければ量子化認識学習で学習し直せ、というのが文書の次の勧めだ。

小さくする技法そのものの原理と、それが何を先に失うかはこの記事の主題ではない。平均精度が保たれるのに稀な事例から先に崩れる構造は蒸留・量子化で小さくしたモデルが失うもので別に扱った。ここで覚えておくことは一つだ。変換の前後を同じデータで比べなければ、精度が変わった事実そのものを知らないまま配備することになる。

  • 合格基準は変換前のモデルではなく対象機器で実行される変換後のモデルで取る
  • 較正データは学習データではなく設置される現場から抜いたフレームでなければ意味がない
  • 夜間・逆光・粉塵のように条件の悪い区間を評価集合に必ず入れる。平均値はこの区間を隠す
  • 変換パイプラインは手作業でなくスクリプトで固定する。再現できない変換は後から原因を探れない

ライセンスは配備前に読む

この項目が遅れて見つかる理由は単純だ。学習と評価の段階では何の問題も起こさないからである。問題はそのモデルが販売される装置に入る瞬間に生じる。そしてそのときにはすでにパイプライン全体がそのモデルに合わせられている。候補を絞る段階で、精度と同じ欄に置いて読むべき項目だ。

以下は2026年9月初めの時点で各リポジトリ・文書が公開していた条件である。条件は変わるので、導入の時点で原文を読み直す必要がある。

  • モデル系列を替える費用は、後処理と評価コードまで含めて計算して初めて実際の値になる

ボトルネックはたいてい推論ではない

推論時間を数ミリ秒縮める仕事は目に見えやすく、成果としても語りやすい。ところがカメラ入力からイベントまでの経路全体で見ると、その数ミリ秒が全体の小さな一片である場合が多い。圧縮されたストリームを解く仕事、ピクセルをモデルが受け取るサイズと形式に変える仕事、出てきた枠を整理してフレーム間で同じ物体を繋ぐ仕事が、いずれも時間を使う。

カメラ入力 → デコード → 前処理 → モデル推論 → 後処理 → 追跡・判定 → イベント

[アクセラレータが担う区間]  モデル推論
[CPU が抱え込む区間]        前処理 · 後処理 · 追跡 · イベント送出
[ハードウェアデコーダ]      デコード (あれば CPU から外れ、なければ CPU へ来る)

ここでよく起きるのはこうだ。アクセラレータの使用率は低いのに処理量が出ない。原因はたいていデコードとメモリコピーである。ハードウェアデコーダがないか、パイプラインがそれを通らなければ、その負担が丸ごと CPU へ来る。カメラを増やすときに先に飽和するのも、アクセラレータではなくこの区間だ。

  • モデルを替える前に段階ごとの時間を先に分けて測ることが順序だ。測らずに最適化すると、たいてい空いた場所を掘る
  • ハードウェアデコーダがあるかと、選んだパイプラインが実際にそれを使うかは別の問いである
  • アクセラレータと CPU の間のコピーを減らすほうが、モデルを小さくするより効く場合が多い
  • 後処理はカメラ台数に比例して増えるのに加速されない場合が多い。ここが拡張の実際の上限になりがちだ
  • ボトルネックでない場所を速くしても全体は変わらない。どの軸で実際に分かれるかは推論ハードウェア選定で実際に分かれるもので帯域幅・レイテンシ・エコシステムとして整理した

毎秒何フレームではなく毎秒何イベントか

前節の構造がそのまま測定の方法へ繋がる。モデル単体の処理量はパイプラインの一段階の値だ。システムが担えるカメラ台数を決めるのはカメラ入力からイベント発行までの端から端までの処理量である。二つの値は同じ機器でも大きく開く。

測定条件を書かない処理量の値が役に立たない理由もここにある。入力解像度、バッチサイズ、精度、同時ストリーム数、後処理を含むかどうか、そして何分目に測った値かが、すべて結果を変える。同じ機器で同じモデルから出した値でも、条件が違えば比較できない。だからベンダー資料の数値は導入判断の根拠ではなく、候補選別のヒントとしてだけ使うほうがよい。

実務で使える形は一文にまとまる。この機器はこの解像度でこのモデルを使い、これだけのカメラを毎秒何フレームずつ処理しながら、周囲温度何度で何時間を連続で耐える。この一文を埋められないなら、まだ測ったことにはならない。

  • 合格基準には必ず同時ストリーム数が入る。一台で測った値は十台で十分の一に割れてはくれない
  • 測定は冷却が安定してから行う。開始直後の数分の値は実運用の値ではない
  • フレームを捨てるポリシーをあらかじめ決めておく。詰まったとき何を捨てるかが決まっていないと、遅延が積み上がり続ける
  • イベントが集中する瞬間を別に測る。平常時ではなく事案が重なる区間でシステムは崩れる

現場でモデルを更新するということ

サーバーでは配備は戻しやすい作業だ。現場機器ではそうではない。更新をしくじれば、その機器は人が行かないと生き返らない。だから配置の決定を下す瞬間に更新の方式も一緒に決まる。後から付けるものではなく、最初からの要件である。

ここで更新されるのはモデルファイル一つではない。モデル、変換された実行形式、前処理と後処理のパラメータ、判定しきい値、そしてそれらの組み合わせが一緒に動く。この組み合わせがバージョンとして束ねられていなければ、現場ごとに違う状態になる。問題が起きたときどの組み合わせで起きたのか分からない状態が、運用では最も高くつく。

  • 更新に失敗したとき前のバージョンへ自動で戻る経路が要る。人が行かないと復旧しない構造は、そのまま費用だ
  • 全量配備ではなく数台を先に上げる順序を既定にする。現場の条件はサイトごとに違う
  • モデルとしきい値は一つのバージョンに束ねて配る。しきい値だけ別に触る慣習が、再現不能な状態を作る
  • 機器が今どのバージョンを回しているかを遠隔で確認できないなら、そのシステムは更新可能な状態にない

誤った判定を回収する経路

配備されたモデルは必ず間違える。重要なのは間違えた回数ではなく間違えたものが戻ってくる経路があるかだ。この経路がなければシステムは配備時点の性能に固定され、現場の条件が変わるたびに静かに悪くなる。

ところがこの経路は、先の境界の決定と正面から衝突する。再学習に使う資料を残すには場面を保存しなければならず、場面を保存しないと決めたのがまさにその境界の決定だった。両方を満たす答えはなく、どこまで残すかについての合意があるだけだ。この合意を技術チームだけで下すと、後でひっくり返る。

  • 現場の担当者が一度の操作で誤判定を印できる必要がある。別の手続きが要るなら誰もやらない
  • 集めるべきは誤った事例だけではない。当たったが際どかった事例が次の失敗を予告する
  • 収集の対象と保管期間は最初から明示する。後から決めると、すでに溜まったデータが問題になる
  • モデルを替える前に、前のバージョンがどの事例で間違えたかを一覧に残す。これが次の評価集合になる

映像は個人情報と隣り合っている

映像認識システムは人が写る場所に置かれることが多い。韓国の個人情報保護法はこの領域を固定型と移動型に分けて規定している。第25条は固定型映像情報処理機器の設置・運営の制限を定め、第4項で設置目的および場所、撮影範囲および時間、管理責任者の連絡先などを含む案内板を、情報主体が容易に認識できるように設置させる。同条第5項は設置目的と異なる目的で機器を任意に操作したり他の場所を映したりすることを禁じ、録音機能は使用できないと定める。

第25条の2は移動型映像情報処理機器の運営制限を別に置く。業務を目的に運営する場合は原則として撮影が制限され、許される場合に撮影するときも光・音・案内板などによって撮影の事実を表示して知らせなければならない。両条文は2023年3月14日に改正された法律第19234号により2023年9月15日から施行された。実際の適用範囲は設置場所と目的によって変わるため、個別の事案は確認が必要だ。

  • 設計の観点で重要なのは条文そのものより、それが境界の決定と同じ方向を指しているという点だ。残していないものは管理する必要もない
  • 映像をイベントに変える構造は、副次的に露出範囲を狭める。これが現場処理の実質的な利点の一つである
  • デバッグ用に保存する画像が最もよく抜ける。一時という名の付いた保管場所が何年も残っている場合はよくある
  • 映像が本物かと場面が本物かは別の問題だ。この区別はカメラ署名が保証しないもので別に扱った

最も賢いモデルが答えではない理由

ここまでの項目を並べると共通点が見える。回線、発熱、ランタイムのサポート、変換誤差、ライセンス、更新経路、個人情報の範囲。このどれ一つとして精度の表には出てこない。ところが配備されたシステムが止まったり差し戻されたりする理由は、大半がこの一覧から出る。

産業の現場で勝つ構成はたいてい華やかでない。決められた電力と決められたケースの中で、決められた費用で、夏も冬も同じ速度で回ること。そしてそれが百か所の設置場所で同じやり方で繰り返せるものであることだ。一台で最も良い結果を出す構成と、百台で同じ結果を出す構成は同じではない。

モデルのサイズを選ぶ問題そのものは別の問いであり、それは性能ではなく作業をどう定義したかに掛かっている。その話は小さなモデルで十分かで扱った。この記事の軸はその手前だ。この作業を現場に置くのか、そして何を根拠にそう決めるのか。理由を一つに絞り、境界を一行で引き、その境界が要求するランタイム・ライセンス・更新経路を一緒に確定すれば、残りはたいてい付いてくる。順序を変えると、精度は良いのに設置できないシステムができあがる。

確認できなかったこと

  • 特定のアクセラレータモジュールの実測処理量は書かなかった。公開されている数値が解像度・バッチサイズ・精度・同時ストリーム数・測定時間をそれぞれ違えているため、比較可能な形では確認できなかった
  • 産業用機器の供給保証期間と製品寿命ポリシーは製品ごとの契約条件に掛かっており、公開文書では確認できなかった。本文ではそれが検討項目だという点までにとどめた
  • ONNX Runtime 以外のランタイムの演算子サポート一覧は個別に確認できなかった。部分オフロードの構造自体は ONNX Runtime の文書で確認した範囲だ
  • 本文の回線・保管の計算は仮定したビットレートとイベントサイズから出た算数であり測定値ではない。実際の料金単価と現場のアップリンク帯域は確認していない
  • 韓国の産業現場における映像AIの導入率や失敗率についての統計資料は確認できなかったため書かなかった
  • 法令部分は条文内容の紹介であり、特定の設置状況にどう適用されるかの解釈は確認できなかった。個別の事案は別途の検討が必要だ
