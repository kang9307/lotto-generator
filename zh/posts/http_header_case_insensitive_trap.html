头部明明发出去了服务器却看不见 - 名称不区分大小写而代码区分

名称不区分大小写，数据结构区分 - 用实际运行抓出藏在这道错位里的缺陷

2026-07-31 开发/基础设施

引言：确实发出去了，接收方却没有

正在对接的团队来消息说：每个请求我们都加了 X-Request-Id，在浏览器开发者工具里也确认过了。可是我们的服务器日志里没有这个值。打开代码，读取头部的那一行明明就在。也不抛异常。状态码还是200。只是值没有而已。

这种情形之所以特别难缠，是因为什么都没有失败。写错字会报错，网络断了会超时。可是读取对象里不存在的键并不是错误。空值悄悄返回，这个空值流进日志，而日志里一行都不会出现。几天之后同样的问题又冒出来：追踪标识为什么一直没记录。

原因是规范与代码之间的一道错位。这一段话就是本文的全部。

  • HTTP头部的名称不区分大小写。 X-Request-Id、x-request-id 和 X-REQUEST-ID 是同一个头部。规范就是这么定的
  • 可是代码用来装它的数据结构区分大小写。对象的键、字典的键、集合的元素、字符串比较运算符 — 全都把 X 和 x 当成不同的东西
  • 于是本该相同的两个名称在代码里变成了不同的东西。这道错开的缝就是缺陷藏身的地方

常见的药方是「都写成小写吧」。这话不算错，但它是只在自己写的代码里成立的规则。对方用什么拼法发送不是自己能决定的，而且按规范对方用任何拼法都不算错。所以本文不会停在「写成小写吧」。它会用实际运行一步步指出名称在哪个环节被谁改写，并把值(value)为什么必须另作处理也分清楚。

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际运行的结果。运行时是 Node.js v22.16.0 (win32) 和 Python 3.13.3 (win32)，两边都只用标准库。没有安装任何外部包。服务器全部监听在 127.0.0.1 的高号端口（从 18080 开始），运行结束即关闭。脚本不通过命令行参数或内联文档传递，而是全部写成文件后执行。

没能测到的部分。这台机器上没有安装商用反向代理或网关产品，所以第6节的中转是自己写的最小代理，不能推广为某个具体产品的行为。另外关于HTTP/2名称规则的规范原文没能打开，因此第5节只依据实测结果叙述，不引用条文。HTTP/3在这台机器上没有实现，完全没有测到。

本文不涉及的内容。该开哪些安全头部、用什么值，在Web安全基础里讲过。反向代理本身的配置在反向代理配置里。这里只看头部名称这个字符串跨层时是怎么变形的。

1. 复现 - 发出的名称和保存的键不一样

先把问题看清楚。为了精确控制字节，客户端完全不用库，直接往套接字里写请求行。服务器是标准库的默认HTTP服务器。

node v22.16.0 / win32
server listening on 127.0.0.1:18080

--- 1-0. exact bytes the client sent ---
"GET /order HTTP/1.1\r\nHost: 127.0.0.1:18080\r\nX-Request-Id: req-4821\r\nContent-Type: application/json\r\nACCEPT: */*\r\nConnection: close\r\n\r\n"

--- 1-1. what the server code tried ---
req.headers['X-Request-Id'] : undefined
req.headers['x-request-id'] : req-4821
req.headers['X-REQUEST-ID'] : undefined

--- 1-2. the keys actually stored in req.headers ---
  key=[host]  value=[127.0.0.1:18080]
  key=[x-request-id]  value=[req-4821]
  key=[content-type]  value=[application/json]
  key=[accept]  value=[*/*]
  key=[connection]  value=[close]

三行就说明了全部。客户端写的是 X-Request-Id，值也完好地到达了服务器。可是用 X-Request-Id 去找显示没有，用 x-request-id 才找得到。看保存的键列表原因就很清楚了：所有名称都被改写成了小写。

第三行也值得一看。全大写去找同样没有。也就是说这不是「大小写随便对上就行」，而是「必须精确地是小写」。在这个字典里有效的拼法只有一种。

客户端发的 ACCEPT 同样变成了 accept。这个规范化不是只对特定头部生效，而是对全部生效。

2. 运行时改写名称 - 原始拼法去哪了

那么原始拼法是彻底消失了吗？在同一个请求里再往下挖，会挖出有意思的东西。

--- 1-3. req.rawHeaders keeps the bytes as they arrived ---
  raw[0]=[Host]  raw[1]=[127.0.0.1:18080]
  raw[2]=[X-Request-Id]  raw[3]=[req-4821]
  raw[4]=[Content-Type]  raw[5]=[application/json]
  raw[6]=[ACCEPT]  raw[7]=[*/*]
  raw[8]=[Connection]  raw[9]=[close]

--- 1-4. lookup by property vs by normalized key ---
  direct  req.headers[X-Request-Id]            : undefined
  normalized req.headers[x-request-id] : req-4821
  Object.hasOwn(req.headers, X-Request-Id)  : false
  Object.hasOwn(req.headers, x-request-id)  : true

在规范化字典旁边，另有一个按到达顺序排列名称和值的数组。这里 X-Request-Id 和 ACCEPT 都保持着发送时的拼法。偶数位是名称，奇数位是值。

这个事实说明两点。第一，运行时不是丢掉了信息，而是只规范化了一侧。它为了方便造了一个小写字典，同时也留下了原本。第二，因此是可以调查「对方到底用了什么拼法」的。排查对接问题时，直接把这个数组打出来是最快的确认方法。

不过这里有个很大的前提。这个原本数组只有在直连时才可信。正如第6节所见，只要中间多一级中转，这个数组的内容就会整个变掉。

2.1 判断值是否存在的方法也一起错了

  • 存在性检查掉进同一个陷阱。用 X-Request-Id 做自有属性检查是假，用 x-request-id 是真
  • 于是「有头部走A，没有走B」这种分支永远只走B。值明明来了却判定为没来
  • 如果这个分支挂在认证或权限上，功能会整个失效。反过来如果是「没有就放行」的形式，检查就被整个架空了
  • 如果测试代码用了同样的拼法，测试也跟着一起错。这就是测试能过、只在真实环境失败的典型形态
  • 最糟的组合是测试客户端发小写而真实客户端发大写。这时方向是反的，推断原因要花更长时间

3. 发送方会保留 - 线路上的名称

接收方会规范化，那发送方呢？故意把响应头部大小写混着设置，再把实际到达客户端套接字的字节原样打出来。

--- 1-5. res.getHeader is case-insensitive (Node normalizes the lookup) ---
  res.getHeader('X-Trace-Id')  : trace-9f2c
  res.getHeader('x-trace-id')  : trace-9f2c
  res.getHeader('X-TRACE-ID')  : trace-9f2c
  res.getHeaderNames()         : ["x-trace-id","x-lower-name","content-type"]

--- 1-6. exact bytes that came back (wire) ---
  |HTTP/1.1 200 OK
  |X-Trace-Id: trace-9f2c
  |x-lower-name: set-in-lowercase
  |Content-Type: text/plain
  |Date: Thu, 30 Jul 2026 20:22:49 GMT
  |Connection: close
  |Content-Length: 3

这里显露出同一个运行时用了两套不同的策略。

  • 响应头部的读取不区分大小写。三种拼法都返回了同一个值。请求头部不是这样，而响应头部是
  • 名称列表返回的是小写。说明内部存储用的是小写键
  • 可是实际发出去的字节保留了我写的拼法。X-Trace-Id 是大写出去的，x-lower-name 是小写出去的
  • 归纳起来就是内部索引是小写，输出表示是原本。两层各自管理

同一套代码里一个读取区分大小写、另一个不区分，这个事实说明了这个问题为什么靠记忆解决不了。规则因API而异。

3.1 三种客户端写到线路上的名称

再往发送方深挖。起一个什么都不解析、只记录字节的TCP接收端，用三种客户端发送同样的三个头部。

node v22.16.0 / win32
raw TCP sink on 127.0.0.1:18087 (records bytes, never parses them)

--- 7-1. A. node http.request ---
  request line   : GET /a HTTP/1.1
  names on wire  : ["X-Request-Id","X-API-Key","Accept-Language","Host","Connection"]

--- 7-2. B. global fetch (undici) ---
  request line   : GET /b HTTP/1.1
  names on wire  : ["host","connection","X-Request-Id","X-API-Key","Accept-Language","accept","sec-fetch-mode","user-agent","accept-encoding"]

--- 7-3. C. hand-written bytes ---
  request line   : GET /c HTTP/1.1
  names on wire  : ["Host","X-Request-Id","X-API-Key","Accept-Language","Connection"]

--- 7-4. the same three names, side by side ---
  client                    x-request-id      x-api-key         accept-language
  A. node http.request      X-Request-Id      X-API-Key         Accept-Language
  B. global fetch (undici)  X-Request-Id      X-API-Key         Accept-Language
  C. hand-written bytes     X-Request-Id      X-API-Key         Accept-Language

结果跟预想略有出入。三种客户端都把我写的拼法原样放上了线路。连使用符合标准规范的头部对象的第二种客户端，也没有动用户指定的头部拼法。

反倒是第二种客户端的列表里能看到别的东西。库自己加上的头部全是小写。用户给的保持原本，自己造的用小写。所以一条消息里会混着两种写法一起发出去。

  • 这种混杂在规范上完全没问题，因为接收方本就该以不区分大小写的方式处理名称
  • 但是「我们的客户端发小写所以服务器只看小写就行」这个假设在这里就破了。用户指定的头部并不是小写
  • 也就是说不能拿线路上的拼法作为任何判断的依据。那是巧合，不是契约
  • 对HTTP/1.1只需记住发送方的拼法会原样流过去。麻烦出在下一层

4. 每个框架的数据结构都不一样

这里换个语言。用Python标准库的HTTP服务器接收同样的请求，结果完全不同。

python 3.13.3 / win32 / Windows 10
--- 2-1. self.headers type ---
  type      : http.client.HTTPMessage

--- 2-2. case-insensitive lookup on the SAME object ---
  headers[X-Request-Id]   -> 'req-4821'
  headers[x-request-id]   -> 'req-4821'
  headers[X-REQUEST-ID]   -> 'req-4821'
  headers[x-ReQuEsT-iD]   -> 'req-4821'

--- 2-3. but the stored names keep the original bytes ---
  key=[Host]  value=[127.0.0.1:18081]
  key=[X-Request-Id]  value=[req-4821]
  key=[ACCEPT]  value=[*/*]
  key=[X-Tag]  value=[alpha]
  key=[x-tag]  value=[beta]
  key=[Connection]  value=[close]

--- 2-4. keys() is NOT normalized, so naive set logic still misses ---
  list(headers.keys())        : ['Host', 'X-Request-Id', 'ACCEPT', 'X-Tag', 'x-tag', 'Connection']
  'x-request-id' in keys      : False
  'X-Request-Id' in keys      : True
  headers.get(x-request-id)   : 'req-4821'
  '__contains__' on the object: True True

--- 2-5. duplicate names collapse differently ---
  get_all(X-Tag)              : ['alpha', 'beta']
  get(X-Tag)   [first only]   : 'alpha'

这是完全相反的设计。Python这边把头部装进的不是普通字典，而是一个邮件消息对象，而那个对象在读取时以不区分大小写的方式比较名称。四种拼法都返回了值。连 x-ReQuEsT-iD 这样混着写也行。

同时保存的名称保持原本。Node是把小写字典和原本数组分开放，Python则是合并进一个对象来解决。这个设计看上去更安全，这一点是事实。

4.1 可是这里也有同样的陷阱

安全只限于通过那个对象去读取的时候。一旦把名称列表取出来，它又变回普通的字符串列表。

  • 取出名称列表，看 x-request-id 在不在里面，结果是假，因为列表元素是原本的拼法
  • 拿同一个名称直接问对象则是真。也就是说同一份数据给出两个答案
  • 所以「遍历列表逐个筛选」这种代码在Python里同样会打偏。换语言解决不了这个问题
  • 重复名称的处理也不同。分别发送 X-Tag 和 x-tag，两者都作为独立条目保留，而取全部的调用则不区分大小写，把两个值都返回了
  • 相反，只取一个的调用只返回先到的那一个。后面的值悄悄消失

Node在同样的情况下反应不同。正如第7节所见，它把两个值做成一个用逗号连起来的字符串。规范允许把同名的多行用逗号合并，这个运行时选择了这条路。也就是说同样的输入会有三种结果。

层名称存储方式读取时的大小写原本拼法重复名称
Node 请求头部字典全部规范化为小写区分（对象键）另存于单独数组用逗号合并
Node 原本名称数组按到达顺序原样不适用（数组）原样各自保留
Node 响应头部小写索引不区分输出时用原本表示覆盖
标准规范头部对象小写索引不区分列表是小写用逗号合并
Python 头部对象保持原本拼法不区分原样各自保留
Python 名称列表原本拼法的字符串区分（字符串比较）原样各自列出
HTTP/2 传输只允许小写不适用不存在依传输规则

把表格归纳成一句话就是：提供「读取」的一方大体安全，暴露「列表」的一方大体危险。而且无论哪一边，把一种语言的规则搬到另一种语言上都会出错。

5. 在HTTP/2里大写就是协议错误

到此为止都是HTTP/1.1。换了传输方式故事就变了。先用普通的客户端库发送大写名称。

node v22.16.0 / win32  (http2 module, cleartext h2c)

--- 3-1. client sends the name written as X-Request-Id ---
  request({X-Request-Id}) : accepted by the API (no throw)

--- 3-2. what the HTTP/2 server received ---
  key=[:path]  value=[/order]
  key=[:method]  value=[GET]
  key=[:authority]  value=[127.0.0.1:18082]
  key=[:scheme]  value=[http]
  key=[x-request-id]  value=[req-4821]
  stream.session.alpnProtocol : h2c

--- 3-4. response header names the HTTP/2 client sees ---
  key=[:status]  value=[200]
  key=[x-trace-id]  value=[trace-h2]
  key=[content-type]  value=[text/plain]

有三点值得注意。第一，接口接受了大写名称，没有抛异常。第二，可是到达服务器的名称是小写。第三，服务器用大写设置的响应头部到客户端也变成了小写。

也就是说是库悄悄改成小写的。这里不会出任何事故。问题在于这份宽容把真正的规则挡住了。

5.1 手工往压缩层里写大写会怎样

把库拿掉来验证。HTTP/2不是原样发送头部，而是装进专用的压缩格式发送。直接构造那些字节，让名称里带着大写字母发送。为了对照，同一个请求也用小写发了一遍。

node v22.16.0 / win32  (raw HPACK over cleartext h2c)

--- 8-1. field name written as x-request-id (lowercase) ---
  server stream event  : names = [":method",":scheme",":path",":authority","x-request-id"]
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","HEADERS stream=1","DATA stream=1"]
  server saw a stream  : true

--- 8-2. same request, field name written as X-Request-Id ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

--- 8-3. and as ACCEPT ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

结果毫不含糊。小写名称被正常处理，响应也回来了。同一个请求只改名称的拼法，服务器就立刻中断该流并返回错误码1。第二个例子把名称改成 ACCEPT，结果一样。

最重要的是最后一行。服务器的请求处理函数一次都没有被调用。应用代码连这个请求来过都不知道。

  • 也就是说在HTTP/2里大写名称不是「值看不见」的问题，而是「请求不成立」的问题
  • 症状表现为连接被切断，而不是少了一个头部。所以推断原因的方向完全不同
  • 用正常的库很难碰到这种情况，因为库会先把名称改成小写
  • 反过来，直接构造字节，或者在什么地方拼接名称字符串的代码就会撞上这里
  • 「HTTP/1.1下好好的对接，换成HTTP/2之后才坏掉」这类报告里有一支就是这个

把测量范围说清楚。上面的结果是针对这台机器上的一个HTTP/2实现测出来的。由于没能打开规范原文，本文不写「规范如此规定」。确认的事实止于：这个实现收到带大写字母的名称时，会把流当作协议错误切断。HTTP/3在这台机器上没有实现，完全没有测到。不过无论如何，实务上的指引是一样的：把名称固定为小写，在三种传输方式下都安全。

6. 只要过一次代理名称就整个变了

第2节看到原本拼法留在数组里。现在该验证它能不能信了。写了一个最小的中转服务器，用的是最常见的做法：把收到的头部字典原样交给下一跳。

node v22.16.0 / win32
origin on 127.0.0.1:18083   proxy on 127.0.0.1:18084

--- 4-0. field names the client put on the wire ---
  X-Request-Id / X-API-Key / ACCEPT

--- 4-1. DIRECT to origin: names as received ---
  ["Host","X-Request-Id","X-API-Key","ACCEPT","Connection"]

--- 4-2. THROUGH one proxy hop: names as received by the SAME origin ---
  ["host","x-request-id","x-api-key","accept","connection"]

--- 4-3. diff ---
  identical name lists : false

--- 4-4. response names the client sees ---
  direct        : |X-Origin-Marker: origin-1
  through proxy : |x-origin-marker: origin-1

同一个客户端、同样的字节、同一个最终服务器。只插了一级中转，到达的名称就全变成小写了。连那个据说保留着原本拼法的数组，内容也跟着变了。

原因很简单。中转代码传过去的是已经规范化为小写的字典，往下一跳发送时那个字典的键就直接写上了线路。中转不是转发字节，而是把解析结果重新组装了一遍。

响应方向也一样。最终服务器加的 X-Origin-Marker 到客户端变成了 x-origin-marker。

  • 这不是缺陷，而是中转的正常行为。名称不区分大小写，用什么拼法重写都不违反规范
  • 所以依赖原本拼法的逻辑只会在生产环境坏掉。开发环境是不经代理直连的
  • 负载均衡器、内容分发网络、服务网格这类中间层全都站在这个位置上。其中任何一个改了表示都不奇怪
  • 更进一步，如果中间层用HTTP/2接收再用HTTP/1.1转发，原本拼法从一开始就不存在，正如第5节所见
  • 结论只有一个。名称的拼法不是契约。区分大小写来处理头部名称的代码，早晚一定会出错

7. 悄悄打偏的比较代码

接下来看真实代码是怎么打偏的。在一个请求里同时测量了三种常见形态。

--- 5-1. equality and membership on the NAME ---
  keys                        : ["host","x-request-id","authorization","cookie","x-api-key","content-type","x-tag","connection"]
  seen.includes('X-Request-Id'): false
  seen.includes('x-request-id'): true
  Set built from a written spec: ["X-Request-Id","X-API-Key","Authorization"]
  matched by that Set          : []
  matched after normalizing    : ["x-request-id","authorization","x-api-key"]

--- 5-2. the strip list that does not strip ---
  after delete ['Authorization'] : authorization still present = true
  value that would be forwarded  : Bearer sK9xQz
  cookie still present           : true
  normalized filter -> keys      : ["host","x-request-id","content-type","x-tag","connection"]

第一段是最常见的形态。照着对接文档里写的拼法做出名称列表放进集合，再从到达的头部里只挑出在这个集合里的。结果是一个空数组。三个其实都到了，却一个都没挑出来。

第二段更危险。这是往外部转发之前删除敏感头部的代码。按文档写的删除 Authorization 和 Cookie。可是实际的键是小写的，所以删除什么也没做，凭据原样留了下来。

这类事故的性质。删除失败了功能照样正常。请求转发得好好的，响应也好好地回来。一个可见的症状都没有。所以这种失败靠监控抓不到。它不出现在任何指标和日志里，不真正打开外部调用的请求内容就无从知晓。维护删除列表的代码，最好同时带上「删完之后确认确实不在了」的断言。

7.1 日志什么都不留下的形态

--- 5-3. the log line that logs nothing ---
  log ctx rid = {}
  log ctx rid = {"rid":"Req-4821"}
  fallback chain               : Req-4821
  fallback with ?? (nullish)   : MISSING

--- 5-4. WHATWG Headers vs a plain object, same data ---
  Headers.get('X-Request-Id')  : Req-4821
  Headers.get('x-request-id')  : Req-4821
  Headers.has('X-API-KEY')     : true
  [...Headers.keys()]          : ["authorization","content-type","cookie","host","x-api-key","x-request-id","x-tag"]
  plain object same lookups    : undefined / Req-4821

--- 5-6. duplicate names arriving with different casing ---
  x-tag                        : [alpha, beta]

第一行正好解释了本文的引言。往日志上下文对象里放值，结果是一个空对象。值为空的属性在序列化过程中连键一起整个消失。

所以屏幕上出现的不是「值不对」，而是「那一项根本就没有」。翻日志的人找不到那一行，自然就得出「大概是头部没来吧」的结论。调查从这里开始朝着跟原因完全相反的方向走。

  • 常见的替代方案把几种拼法并列确实能找到值。只是拼法写几个都写不全，是应急手段
  • 用只填补空值的运算符反而更糟。前面的读取确实是空的，于是直接落到备用值上，实测中那个位置打印出了占位字符串
  • 用标准规范的头部对象读取是安全的。用任何拼法去问都能拿到值，存在性检查也正常
  • 但那个对象给出的名称列表也是规范化成小写的。拿列表去跟原本拼法比对的代码在这里同样打偏
  • 重复名称被不区分大小写地合并成了一个。分别用 X-Tag 和 x-tag 发的两个值变成了一个逗号连接的字符串。跟第4节Python的结果不同

8. 名称不区分大小写，值不是

这里是实务中最容易混淆的地方：把「HTTP头部不区分大小写」这句话连值也一起套用了。实测下来完全不是这么回事。

--- 5-5. the NAME is case-insensitive, the VALUE is not ---
  value as received            : [Req-4821]
  rid === 'REQ-4821'           : false
  rid === 'req-4821'           : false
  authorization as received    : [Bearer sK9xQz]
  startsWith('Bearer ')        : true
  startsWith('bearer ')        : false
  token                        : [sK9xQz]
  token.toLowerCase() === token: false   <- lowercasing a value destroys it
  content-type                 : [application/json; charset=UTF-8]
  ct === 'application/json'    : false
  ct.split(;)[0].trim().toLowerCase() : [application/json]

三个例子各给出不同的教训。

  • 标识符的值。到达的值是 Req-4821。用上下哪种拼法比较都是假。值写成什么就是什么，规范化之后就成了另一个值
  • 认证头部。前面的方式名称部分可以不区分大小写，但后面的凭据是一个字符都不能变的。实测中转成小写的凭据跟原本不同。对整个值做小写转换会把认证整个搞坏
  • 媒体类型。连值后面的附加项一起整个比较是假。实际需要的是只切出前半部分、去掉左右空白之后再比较
  • 归纳起来就是规范化对名称无条件地做，对值只在确认过该头部的定义之后才做
  • 把处理值的函数和处理名称的函数干脆分开能减少失误。在同一个函数里两边都碰，早晚会混
对象大小写实测结果规范化备注
头部名称不区分四种拼法都是同一个值始终转小写只会来阿斯克码，简单转换就够
追踪标识的值区分上下拼法比较都为假绝对禁止改了就成另一个值
认证方式名称可以不区分只有大写前缀为真仅在比较时要与后面的凭据分开处理
凭据本体区分转小写后值就变了绝对禁止一碰认证就失败
媒体类型前半可以不区分含附加项的比较为假只取前半要先摘掉附加项
附加项的值因项而异本例中以大写到达确认定义之后禁止统一转换
路径与查询字符串区分在测量范围之外禁止不是头部，是请求目标

9. 安全读取的方法 - 规范化之后再取

纠正很简单。在读取的一侧始终把名称规范化即可。不过要连带处理两件事，才算是真正安全。

--- 6-1. one getter, every spelling ---
  getHeader(X-Request-Id)    -> "req-4821"
  getHeader(x-request-id)    -> "req-4821"
  getHeader(X-REQUEST-ID)    -> "req-4821"
  getHeader(x-ReQuEsT-iD)    -> "req-4821"
  getHeader(X_Request_Id)    -> undefined

--- 6-2. the prototype trap of a plain-object lookup ---
  Object.getPrototypeOf(h) === null  : false
  naive h['constructor']             : function Object() { [nat
  naive h['toString']                : function
  getHeader(h,'constructor')         : undefined
  getHeader(h,'toString')            : undefined

第一段跟预期一致。一个函数让四种拼法都返回了同一个值。最后一行是正常的。用下划线写的名称确实是另一个头部，没有值才对。

第二段是不太为人所知的陷阱。头部字典是普通对象，与上级原型相连。所以不做规范化直接读名称，会从一个根本没到达的名称上冒出一个函数。只看真假的检查会因此通过。

  • 也就是说用外部传入的字符串去读头部的代码，其存在性检查会给出意外的结果
  • 安全的读取函数先确认是不是自有属性来堵住这条路。实测中两个名称都返回了空值
  • 读取对象也可能是标准规范的头部对象，所以加一个有专用读取方法就优先用它的分支，一个函数就能覆盖两种情况
  • 名称规范化用简单的小写转换就够了，因为头部名称能用的字符限定在阿斯克码范围内

9.1 发送方混着用拼法会怎样

--- 6-3. send side: two spellings of one name ---
  after setHeader('X-Tag','first')   : getHeaderNames = ["x-tag"]
  after setHeader('x-tag','second')  : getHeaderNames = ["x-tag"]
  res.getHeader('X-TAG')             : second

--- 6-4. names the runtime refuses outright ---
  setHeader("X Request Id") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id:") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id\n") : ERR_INVALID_HTTP_TOKEN
  setHeader("") : ERR_INVALID_HTTP_TOKEN

--- 6-5. what actually went out on the wire ---
  |HTTP/1.1 200 OK
  |x-tag: second
  |X-Trace-Id: trace-9f2c
  |Content-Type: text/plain

在发送方用两种拼法设置同一个名称。结果不是产生两个头部，而是覆盖。名称列表里只有一个条目，值是后写的那个。

而且发到线路上的表示是最后写的那个拼法。最初写成大写，后面再用小写写一遍，出去的就是小写。也就是说输出的表示由最后一次写入决定。

  • 在多个模块各用各的拼法设置同一个头部的代码库里，无法预测会以哪种表示发出去
  • 值是覆盖这一点同样重要。两个模块在互相抹掉对方的值，却没有人知道
  • 带空格、冒号或换行的名称会被运行时拒绝。把用户输入直接放进名称位置的代码会在这里抛异常而死
  • 空字符串也会被拒绝。拼接生成名称的代码需要检查拼接结果可能为空字符串的路径
  • 拒绝表现为异常算是幸运的一边。跟本文里其他事故不同，它至少看得见

9.2 可以直接拿走的读取函数

// 头部名称不区分大小写。在读取的一侧做规范化。
// 用一个函数覆盖普通对象和标准规范头部对象。
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}

// 剔除列表也要一起规范化。只改读取等于只改了一半。
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
# Python。标准头部对象的读取已经是不区分大小写的。
# 危险的是把名称列表取出来用字符串比较的代码。

DROP = {"authorization", "cookie", "x-api-key"}

def get_header(headers, name):
    return headers.get(name)          # 不区分大小写地帮你找

def forwardable(headers):
    # keys() 是原本的拼法，必须规范化之后再比较
    return {k: v for k, v in headers.items() if k.lower() not in DROP}

# 同一个名称可能来了多次。只取一个，其余就消失了
tags = headers.get_all("X-Tag") or []

10. 团队约定与检查清单

只改代码防不住复发。因为这个问题会在人照着文档抄写拼法的那个环节一次次重新诞生。下面整理要用约定钉死的事项。

  • 名称永远写成小写。对接文档、代码常量、测试、日志键全都如此。不要为了好看混进大写
  • 不要把名称字符串散落在代码各处。集中到一处常量里，拼法就没有分岔的余地
  • 把读取头部的通道收成一条。只允许用读取函数，直接下标访问字典的代码在评审中挡掉
  • 剔除列表和读取要一起改。只改读取，会留下敏感头部原样流出去的那一侧
  • 不要对值做规范化。如果确实需要，就只针对那一个头部、确认定义之后再做
  • 让测试客户端故意混着拼法发送。只发小写的测试永远抓不到这个缺陷
  • 至少在带中间层的形态下试一次。只用直连测试就看不到第6节的变形
  • 不要依赖原本拼法。原本数组是给排查用的，不是逻辑的输入

10.1 检查清单

  • 读取头部的每一处是否都用规范化之后再读取
  • 有没有地方还在用带大写的字符串直接下标访问字典
  • 用等值运算符比较名称或把名称放进集合的代码是否经过规范化
  • 敏感头部的删除列表是否用的是规范化后的名称
  • 删除之后是否有确认确实不在了的断言
  • 是否知道放进日志上下文的值为空时连键一起整个消失
  • 存在性分支因继承属性而错误地为真的路径是否堵住了
  • 有没有地方对值做统一的小写转换
  • 带凭据的值是否在比较前没有被改动
  • 媒体类型的比较是否先摘掉附加项
  • 是否处理了同一个头部可能来多次的情况
  • 有没有用户输入原样进入头部名称位置的路径
  • 测试是否也用大写拼法发送请求
  • HTTP/2路径上有没有手工拼接名称的代码

10.2 不要做的事

  • 把文档里的拼法原样抄成代码的键 — 本文所有事故都从这里开始
  • 靠并列好几种拼法来堵 — 写不全，是应急手段
  • 把原本拼法当作逻辑的依据 — 过一次中转就消失
  • 对值做统一规范化 — 凭据和标识符会被破坏
  • 测试只跑小写 — 只会在真实环境坏掉
  • 只放删除列表而不确认结果 — 失败了也没有症状
  • 依赖「我们都是发小写的」这个假设 — 对方没有这个义务

  • RFC 9110 HTTP Semantics, Section 5.5 Field Values（值遵循各字段的定义，没有像名称那样的统一规则）：rfc-editor.org

# HTTP头部名称的大小写 — 安全读取与检查清单

> 来源: braindetox.kr — 头部明明发出去了服务器却看不见
> 依据: Windows 10 / Node.js v22.16.0 / Python 3.13.3 标准库运行验证 (HTTP/1.1 + h2c)

## 0. 大前提 — 错位在哪里

| 层 | 大小写 | 依据 |
|---|---|---|
| **头部名称** | **不区分** | RFC 9110 5.1 |
| **头部值** | **区分**（按字段定义） | RFC 9110 5.5 |
| 代码里的对象键 · 集合 · 字符串比较 | **区分** | 语言规则 |

**缺陷就在把「不区分大小写的名称」装进「区分大小写的数据结构」的那一刻产生。**

## 1. 30秒诊断 — 显示没有值的时候

1. 把实际保存的键整个打出来（不要猜）
2. 用小写名称再读一次
3. 有原本名称数组的话一起打出来（只在直连时可信）
4. 确认有没有中间层 — 有的话原本拼法已经没了
5. 走HTTP/2的路径，名称必定是小写

## 2. 安全读取 (JavaScript)

```js
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}
```

- `hasOwnProperty` 的确认是**必须的**。头部字典与上级原型相连，不做规范化直接读会**从没到达的名称上冒出函数**
- 只看真假的检查会让那个函数**通过**

```js
// 剔除列表也要规范化。只改读取等于只改了一半。
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
```

## 3. 安全读取 (Python)

```python
DROP = {"authorization", "cookie", "x-api-key"}

def get_header(headers, name):
    return headers.get(name)          # 标准头部对象已经不区分大小写

def forwardable(headers):
    # keys() 是原本的拼法，必须规范化之后再比较
    return {k: v for k, v in headers.items() if k.lower() not in DROP}

tags = headers.get_all("X-Tag") or []   # 只取一个，其余就消失了
```

## 4. 各层行为对照表（实测）

| 层 | 名称存储 | 读取的大小写 | 原本拼法 | 重复名称 |
|---|---|---|---|---|
| Node 请求头部字典 | **规范化为小写** | **区分** | 另存于单独数组 | 用逗号合并 |
| Node 原本名称数组 | 按到达顺序原样 | — | **原样** | 各自保留 |
| Node 响应头部 | 小写索引 | **不区分** | 输出用原本表示 | 覆盖 |
| 标准规范头部对象 | 小写索引 | **不区分** | 列表是小写 | 用逗号合并 |
| Python 头部对象 | 保持原本拼法 | **不区分** | **原样** | 各自保留 |
| Python 名称列表 | 原本拼法的字符串 | **区分** | 原样 | 各自列出 |
| HTTP/2 传输 | **只有小写** | — | **没有** | 依传输规则 |

→ **提供「读取」的一方大体安全，提供「列表」的一方大体危险。**

## 5. 名称与值 — 可以规范化的和不可以的

| 对象 | 规范化 | 理由 |
|---|---|---|
| 头部名称 | **始终小写** | 不区分大小写是规范 |
| 追踪标识的值 | **禁止** | 改了就成另一个值 |
| 认证方式名称 | 仅在比较时 | 与后面的凭据分开 |
| 凭据本体 | **禁止** | 一碰认证就失败 |
| 媒体类型前半 | 只取前半 | 先分离附加项 |
| 路径 · 查询字符串 | **禁止** | 不是头部 |

## 6. 实测确认过的事故形态

- 用照文档拼法做的集合去筛，**一个都没挑出来**（其实全都到了）
- 用大写拼法写的删除列表**什么都没删掉** → **凭据被原样转发**
- 往日志上下文放空值，**键也整个消失**，打印出空对象
- 只经过**一级中转**，请求和响应两边的名称就全变成小写
- 在HTTP/2上放大写名称，**流被当作协议错误切断**（应用代码连请求都没看到）
- 用两种拼法设置同一个名称，得到的不是两个头部而是**覆盖**

## 7. 检查清单

- [ ] 读取头部的**每一处**都用规范化之后再读取
- [ ] 没有地方**用带大写的字符串直接下标访问字典**
- [ ] 比较名称或把名称放进集合的代码**经过规范化**
- [ ] 敏感头部的**删除列表用的是规范化后的名称**
- [ ] 删除之后有**确认确实不在了的断言**
- [ ] 存在性判断不会**因继承属性而错误地为真**
- [ ] 没有地方对值做**统一的小写转换**
- [ ] 凭据的值**在比较前没有被改动**
- [ ] 媒体类型的比较**先摘掉附加项**
- [ ] 处理了**同一个头部可能来多次**的情况
- [ ] **用户输入不会原样**进入头部名称位置
- [ ] 测试**也用大写拼法**发送请求
- [ ] 至少在**带中间层的形态**下试过一次
- [ ] HTTP/2路径上没有**手工拼接名称**

## 8. 不要做的事

- ❌ 把文档拼法**原样抄成代码的键** — 所有事故的起点
- ❌ 靠**并列好几种拼法来堵** — 写不全
- ❌ **把原本拼法当作逻辑依据** — 过一次中转就消失
- ❌ 对值做**统一规范化** — 凭据和标识符会被破坏
- ❌ 测试**只跑小写** — 只会在真实环境坏掉
- ❌ 只放删除列表而**不确认结果** — 失败了也没有症状
- ❌ 依赖**「我们都是发小写的」这个假设** — 对方没有这个义务
