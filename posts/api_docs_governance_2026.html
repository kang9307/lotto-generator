서론: 문서가 틀린 게 아니라, 틀릴 수 있게 만들어 둔 것이다

연동 담당자에게 메일이 온다. 첨부는 API명세서_v3_최종_최종2_수정본.xlsx. 시트는 열두 개, 그중 살아 있는 것은 넷이고 나머지는 지운 셈 치기로 한 것들이다. 파트너사는 이 파일을 보고 코드를 짠다. 그런데 서버는 두 달 전 배포에서 응답 필드 하나의 이름을 바꿨고, 그 사실은 엑셀 어디에도 반영되지 않았다. 파트너사 연동은 통합 시험 마지막 날 깨진다. 그리고 회의에서 이런 말이 나온다. 「문서 관리를 좀 더 잘합시다.」

이 결론이 잘못됐다는 것이 이 글의 출발점이다. 담당자가 게을러서 생긴 사고가 아니다. 문서와 코드가 어긋날 수 있는 구조를 그대로 두고, 어긋나지 않기를 사람의 성실성에 기대한 것이 사고의 원인이다. 성실성은 확장되지 않는다. 엔드포인트가 30개일 때 통하던 방식은 300개가 되면 반드시 무너진다.

API 문서가 다른 사내 문서와 다른 점이 하나 있다. 독자가 사람만이 아니라는 것이다. API 명세는 두 프로그램 사이의 약속이고, 약속은 기계가 대조할 수 있어야 강제된다. 엑셀과 PDF의 진짜 문제는 촌스러움이 아니라 대조 불가능성이다. 스프레드시트에 적힌 orderStatus: string은 서버가 실제로 무엇을 내보내는지와 한 번도 비교되지 않는다. 비교할 수 없으니 어긋나도 아무도 모르고, 아무도 모르니 어긋난 채로 몇 달을 간다.

그래서 이 글은 「문서를 잘 쓰는 법」을 다루지 않는다. 어긋나면 즉시 드러나도록 만드는 설계를 다룬다. 논지는 세 줄이다.

  • 문서가 코드와 어긋나는 것은 사람의 태만이 아니라 갱신 트리거가 분리된 구조의 필연적 결과다.
  • 해결의 첫 단추는 도구 도입이 아니라 단일 진실원을 어디에 둘지 정하고, 나머지를 전부 파생물로 강등하는 것이다.
  • 자동화가 잡을 수 있는 것과 없는 것의 경계는 생각보다 뚜렷하다. 경계를 모르면 도구를 사 놓고도 같은 사고가 난다.

이 글이 다루지 않는 것. RAG 색인 대상이 되는 사내 문서 일반의 노후화·거버넌스는 사내 지식베이스는 조용히 썩는다에서 다뤘다. 이 글은 그중 기계가 읽는 API 계약이라는 좁은 축만 파고든다. 두 글의 공통 결론인 소유자·유효기간·폐기 절차는 여기서 반복하지 않는다. 도구 사이의 통신 규약 자체는 MCP 완벽 가이드와 MCP는 끝났는가가, 증권사 공개 API 사례는 토스증권 OpenAPI가 맡는다.

1. 엑셀·PDF 명세가 실제로 잃는 것 - 매체가 아니라 검증 가능성

먼저 오해를 걷어내자. 엑셀로 API를 정리하는 조직이 미개해서 그런 것이 아니다. 엑셀은 진입 장벽이 0에 가깝고, 표 편집이 자유롭고, 누구나 열 수 있는 훌륭한 도구다. 초기 팀이 엑셀로 시작하는 것은 합리적 선택이다. 문제는 그 선택을 되돌리지 않은 채 규모가 커질 때 생긴다.

1.1 기계 판독이 안 되면 검증도 안 된다

OpenAPI 명세는 스스로를 이렇게 정의한다. HTTP API를 위한, 프로그래밍 언어에 종속되지 않는 표준 인터페이스 서술. 핵심은 표준과 기계 판독이다. 형식이 표준이면 그 형식을 읽는 도구가 존재하고, 도구가 존재하면 다음 세 가지를 파이프라인에 넣을 수 있다.

  • 문법·규약 검사 - 이 서술 자체가 유효한가, 사내 명명 규칙을 지켰는가
  • 버전 간 차이 비교 - 지난 배포 대비 무엇이 바뀌었고 그중 무엇이 소비자를 깨뜨리는가
  • 구현과의 대조 - 서술한 대로 서버가 실제로 응답하는가

엑셀과 PDF는 이 셋 중 어느 것도 제공하지 못한다. 정확히 말하면 못 하는 것이 아니라 아무도 만들지 않는다. 셀 병합과 자유 서식이 섞인 표에서 필드 정의를 안정적으로 추출하는 파서를 유지보수하느니, 표준 형식으로 옮기는 편이 싸기 때문이다.

1.2 첨부파일은 배포가 아니라 복제다

두 번째 손실은 더 조용하다. 명세를 메일에 첨부하는 순간 정본은 사라지고 사본만 남는다. 파트너 A는 3월에 받은 파일을, 파트너 B는 5월에 받은 파일을 본다. 둘 다 자기가 최신을 본다고 믿는다. 어느 쪽이 최신인지 확인할 방법이 파일 이름밖에 없고, 파일 이름은 최종이라는 단어를 몇 번 반복했는가로 결정된다.

URL로 배포하면 이 문제의 절반이 사라진다. 하나의 주소가 언제나 현행을 가리키고, 버전 태그가 붙은 주소가 과거를 보존한다. 나머지 절반, 즉 「그 URL의 내용이 실제 서버와 같은가」는 다음 절부터 다룬다.

2. 문서가 코드와 어긋나는 다섯 가지 경로

불일치는 한 가지 원인으로 생기지 않는다. 실무에서 반복해 관찰되는 경로는 다섯 개이고, 각 경로마다 막는 방법이 다르다. 원인을 구분하지 않고 도구부터 도입하면 엉뚱한 경로를 막게 된다.

2.1 경로 ① 갱신 트리거의 분리

가장 흔하고 가장 치명적이다. 코드 변경은 병합이라는 강제 이벤트를 통과하지만, 문서 갱신은 그 이벤트에 걸려 있지 않다. 다른 저장소, 다른 담당자, 다른 일정이면 지연은 확률이 아니라 시간문제다. 처방은 하나뿐이다. 스펙 파일을 코드와 같은 저장소, 같은 변경 요청 안에 두는 것. OpenAPI Initiative의 학습 문서도 스펙 문서를 운영 코드와 나란히 버전 관리해야 할 일급 원본 파일로 취급하라고 적는다.

2.2 경로 ② 사본 확산

앞 절에서 다룬 문제다. 정본 식별자가 없으면 어긋남을 발견해도 어느 사본을 고쳐야 하는지를 모른다. 고쳐도 다른 사본은 그대로 남는다.

2.3 경로 ③ 형식이 담지 못하는 규약

이 경로는 표준 형식으로 옮겨도 남는다. 명세 형식이 표현하지 못하는 약속은 언제나 있다. 예를 들면 이런 것들이다.

  • 금액 필드가 원 단위인가 전 단위인가, 소수점은 몇 자리까지 유효한가
  • 시각 문자열의 표준 시간대가 UTC인가 KST인가, 오프셋 표기가 필수인가
  • 재시도 시 멱등성 키를 어떻게 만들고 얼마나 보존하는가
  • 목록 조회의 페이징 규약이 오프셋인가 커서인가, 커서는 언제 만료되는가
  • 부분 실패 시 어느 것이 성공했는지를 응답 어디에서 읽는가

이 항목들은 스키마에 타입으로 적히지 않는다. 설명문에 자연어로 적히거나, 적히지 않고 구두 합의로 남는다. 그래서 스펙을 도입한 조직도 이 층에서는 여전히 사고를 낸다. 대책은 두 가지다. 설명 필드를 비워 두지 못하게 린터로 강제하는 것, 그리고 이 규약들을 전사 공통 규칙 문서 한 장으로 못 박고 개별 API가 그것을 참조하게 하는 것이다.

2.4 경로 ④ 자동 생성이 만드는 착시

코드 애노테이션에서 문서를 생성하면 어긋남이 사라진다고 흔히 기대한다. 절반만 맞다. 생성기가 읽는 것은 코드가 아니라 애노테이션이고, 애노테이션은 사람이 손으로 유지한다. 응답 객체에 필드를 추가하면서 애노테이션 갱신을 잊으면, 문서는 자동 생성물이라는 이유로 더 강한 신뢰를 얻으면서 틀린 채로 배포된다. 수작업 문서보다 위험할 수 있는 이유가 여기 있다.

OpenAPI Initiative가 설계 우선을 권하는 이유도 이 결과 쪽에 있다. 코드로 만들 수 있는 API의 범위가 OpenAPI로 서술할 수 있는 범위보다 넓기 때문에, 먼저 구현하고 나중에 맞추면 직관적이지 않고 불완전한 서술이 남기 쉽다는 것이다.

2.5 경로 ⑤ 지울 수 없어서 부풀어 오르는 문서

마지막 경로는 시간이 만든다. 옛 엔드포인트와 옛 필드를 지우지 못한 채 새것이 계속 쌓인다. 지우지 못하는 이유는 누가 쓰는지 모르기 때문이다. 사용량을 계측하지 않았으니 지웠을 때 무엇이 깨지는지 알 수 없고, 알 수 없으니 그대로 둔다. 결과적으로 명세는 현행과 과거의 혼합체가 되고, 읽는 사람은 무엇이 살아 있는지 판별하지 못한다. 이 경로는 문서 도구로 못 막는다. 폐기 정책과 사용량 계측이 있어야 한다. 8절과 9절에서 다룬다.

3. 기계가 읽는 계약이란 무엇인가 - OpenAPI가 표준화하는 것과 하지 않는 것

OpenAPI 명세는 HTTP API의 인터페이스를 언어 중립적으로 서술하는 표준이다. 경로와 메서드, 요청 파라미터, 요청·응답 본문의 스키마, 인증 방식, 오류 응답 형태를 정형 구조로 담는다. 여기서 중요한 것은 담기지 않는 것이다. 비즈니스 규칙의 의미, 호출 순서, 성능 특성, 요금 정책은 서술 대상이 아니다. 스펙은 모양의 계약이지 의미의 계약이 아니다.

3.1 3.0과 3.1의 실질적 차이

버전 선택에서 실무적으로 갈리는 지점은 스키마 언어다. 3.0은 JSON Schema의 변형된 부분집합을 썼고, 그 때문에 nullable 같은 자체 키워드가 생겨 도구 호환에 혼선을 낳았다. 2021년 2월 공개된 3.1은 JSON Schema 2020-12와 완전히 정렬되어, 유효한 JSON Schema 2020-12 문서는 그대로 3.1의 스키마로 쓸 수 있다. 웹훅 서술도 3.1에서 정식으로 들어왔다.

명세 자체의 버전 체계는 major.minor.patch이며, major.minor가 기능 집합을 정하고 patch는 오류 수정과 설명 명확화만 담당한다. 즉 3.1.0과 3.1.1은 같은 기능 집합이다. 사내 도구 체인이 3.1을 온전히 지원하는지 확인하지 않은 채 올리면, 도구 쪽이 먼저 깨진다. 2026년 7월 기준으로도 3.1 지원 정도는 도구마다 편차가 있으므로 도입 전 실제 사용하는 생성기·문서화기·모의 서버로 시험하는 편이 안전하다.

3.2 폐기 표시는 스키마 층에도 있다

OpenAPI는 오퍼레이션 객체에 불리언 deprecated 필드를 두어 해당 오퍼레이션이 폐기됐음을 선언하고, 소비자는 사용을 삼가야 한다고 규정한다. 3.1에서는 스키마가 JSON Schema 2020-12를 따르므로 필드 단위 폐기도 표현할 수 있다. JSON Schema의 deprecated는 검증에 영향을 주지 않는 주석 키워드여서, 값이 여전히 통과한다는 점은 알아 둘 필요가 있다. 표시는 신호일 뿐 강제가 아니다.

4. 단일 진실원을 어디에 둘 것인가 - 판단표

도구를 고르기 전에 정해야 하는 것은 정본의 위치다. OpenAPI Initiative의 지침은 단순하다. 정보는 한 곳에만 존재해야 하고, 중복되면 반드시 어느 한쪽이 갈라진다. 불가피하게 두 곳에 두어야 한다면 지속적 통합 시험으로 일치를 강제하라고 덧붙인다.

후보는 다섯 개다. 조직 상황에 따라 정답이 다르므로 표로 정리한다.

엑셀·PDF
(현행 유지)		 엔드포인트 수십 개 이하, 소비자가 사실상 사내 한 팀, 변경이 분기 단위 검증·차이 비교·대조 전부 포기 연동 담당자가 코드를 읽어서 명세를 확인하기 시작함

표를 쓰는 방법은 간단하다. 지금 조직에서 관찰되는 실패 신호를 먼저 찾고, 그 행의 정본이 현재 위치와 다르면 이전을 검토한다. 신호가 없다면 굳이 옮기지 않아도 된다. 마지막 행이 그래서 남아 있다.

가장 흔한 오답. 정본을 두 곳에 두는 것이다. 스펙 파일도 관리하고 애노테이션도 유지하면 둘 다 정본이 아니게 된다. 둘을 함께 두려면 어느 쪽이 파생물인지 명시하고, 파생 방향을 자동화해야 한다. 사람이 양쪽을 손으로 맞추는 구조는 예외 없이 갈라진다.

5. 변경 유형별 파급 분류 - 무엇이 소비자를 깨뜨리는가

「이 변경은 괜찮은가」라는 질문을 매번 감으로 답하면 판정이 사람마다 달라진다. 공개된 지침을 기준으로 삼는 편이 낫다. 여기서는 구글의 API 설계 지침 AIP-180과 스트라이프의 공개 정책을 근거로 정리한다.

변경분류근거·조건
응답에 새 속성 추가대체로 호환스트라이프가 호환 변경으로 공지. 단 미지 필드에서 오류를 내는 엄격 검증 클라이언트는 깨진다

5.1 표에서 읽어야 할 것

이 표의 쓸모는 항목 암기가 아니라 두 가지 원리에 있다.

  • 추가는 대체로 안전하고 제거·변경은 대체로 위험하다. 그래서 성숙한 API는 필드를 지우는 대신 계속 늘리고, 대신 폐기 절차로 정리한다.
  • 안전 여부는 서버가 아니라 소비자의 관용도에 달려 있다. 미지 필드를 무시하고 미지 열거값을 견디는 클라이언트를 전제로 해야 「추가는 안전」이 성립한다. 그래서 이 관용 규칙을 소비자 쪽 문서에도 명시해야 한다.

5.2 스트라이프식 날짜 버전이 주는 교훈

스트라이프는 메이저 릴리스에만 비호환 변경을 담고, 월간 릴리스는 호환 변경만 포함한다고 공지한다. 회사 블로그에는 새 응답을 옛 형식으로 되돌리는 작고 독립된 변환 모듈을 쌓아 과거 버전을 유지한다는 설명이 있다. 이 방식의 비용은 명확하다. 변환 계층이 영원히 쌓인다. 대부분의 조직에는 과한 선택이지만, 여기서 가져올 원칙은 하나다. 비호환 변경을 아무 때나 흘려보내지 않고 한 지점에 모으는 것.

6. 계약 시험은 무엇을 보장하고 무엇을 보장하지 않는가

스펙이 있어도 서버가 스펙대로 응답하는가는 별개 문제다. 이 간극을 메우는 대표적 접근이 소비자 주도 계약 시험이다.

6.1 정의부터 정확히

Pact 공식 문서는 계약 시험을 통합 지점을 각 애플리케이션 단독으로 검사해, 주고받는 메시지가 계약에 문서화된 공통 이해에 부합하는지 확인하는 기법으로 정의한다. 소비자 시험을 실행하는 동안 시험 대역과 주고받은 상호작용이 기록되어 계약이 만들어지고, 제공자 쪽은 그 계약을 재생해 검증한다. 두 서비스를 동시에 띄우지 않고도 통합을 검사할 수 있다는 점이 핵심 이점이다.

6.2 경계를 분명히

같은 문서는 한계도 분명히 적는다. 이 부분이 실무에서 가장 자주 오해된다.

  • 계약은 가능한 모든 상태를 서술하는 스키마와 다르다. 구체적인 요청·응답 쌍 여러 건으로 강제된다.
  • 따라서 소비자가 실제로 쓰는 부분만 검사된다. 아무도 호출하지 않는 필드는 계약에 없고, 없으면 보호되지 않는다.
  • 제공자 쪽 계약 시험만으로는 소비자가 올바른 방식으로 호출하고 있다는 보장을 얻지 못한다.
  • 소비자가 참여해야 성립한다. 누가 쓰는지 모르는 공개 API에는 그대로 적용하기 어렵다.

정리하면 계약 시험은 스펙 린팅이나 파괴적 변경 탐지를 대체하지 않는다. 층이 다르다. 스펙은 넓고 얕게, 계약은 좁고 깊게 덮는다. 둘 다 없으면 아무것도 덮이지 않고, 하나만 있으면 그쪽만 덮인다.

7. CI에서 자동 검증할 수 있는 것과 없는 것

이 절이 이 글의 실질적 핵심이다. 경계를 모르면 도구를 도입하고도 같은 사고가 난다. 항목별로 자동화 가능성을 나눈다.

검증 항목자동화도구 유형남는 위험
스펙 문서의 문법 유효성완전 가능스펙 검증기없음. 통과 못 하면 병합을 막으면 된다
사내 스타일 규약 준수완전 가능린터(Spectral 등)규칙에 없는 관행은 검사되지 않음
설명·예시 누락가능린터 규칙채워졌는지만 알 뿐 내용이 맞는지는 모름
이전 버전 대비 파괴적 변경대체로 가능스펙 차이 비교(oasdiff 등)모양이 같고 의미만 바뀐 변경은 못 잡음
구현이 스펙대로 응답하는가부분 가능속성 기반 시험(Schemathesis 등)생성하기 어려운 상태·부작용이 필요한 경로는 미검사

설명 문장이 사실인가불가능사람 검토가장 비싸고 가장 자주 생략됨
업무 규칙·호출 순서의 정합성불가능설계 검토스펙은 모양만 담는다
폐기 공지가 실제 소비자에게 닿았는가불가능운영 절차·사용량 계측계측이 없으면 확인 자체가 불가

7.1 린터가 잡는 것과 못 잡는 것

Spectral은 스스로를 API 스타일 가이드 강제기이자 유연한 JSON·YAML 린터로 소개한다. OpenAPI 2.0·3.0·3.1, AsyncAPI 2.x, Arazzo 1.0을 기본 지원하고, 규칙 묶음을 정의해 사내 규약을 강제한다. 내장 함수로 패턴 검사, 매개변수 검사, 알파벳 순서, 글자 수, 특정 키의 존재 여부를 확인할 수 있고, 필요하면 함수를 직접 만들 수 있다.

여기서 결정적인 한계 하나. 린터는 스펙 문서만 본다. 서버가 무엇을 응답하는지는 알지 못한다. 린트를 100점 받아도 그 스펙이 현실과 다를 수 있다. 이 점을 팀에 명확히 공유하지 않으면, 린트 통과가 정확성 보증처럼 소비되는 착시가 생긴다.

7.2 차이 비교와 구현 대조

oasdiff는 두 스펙 사이의 차이를 기계 판독 형태로 내고, 소비자를 깨뜨릴 가능성이 있는 변경을 규칙으로 표시한다. 프로젝트는 파괴적·비파괴적 변경 506종을 식별한다고 밝히며, 파괴적 변경이 있으면 종료 코드 1을 반환해 CI 단계를 실패시킬 수 있다. 깃허브 액션은 변경 요청 시점에 기준 브랜치와 비교해 인라인 주석을 남긴다.

Schemathesis는 방향이 다르다. OpenAPI·GraphQL 스키마에서 시험 사례를 자동 생성해 실제로 호출하고, 응답이 스키마에 부합하는지 검사한다. 스키마가 문서화하지 않은 필드를 코드가 반환하거나, 문자열을 약속한 자리에 널이 오는 느린 표류를 잡아낸다는 점이 이 접근의 요지다.

# 예시 파이프라인 - 명령 형태는 도구 버전에 따라 다르므로 공식 문서 확인 필요

# 1) 스펙 문법·사내 스타일 검사
spectral lint openapi.yaml --ruleset .spectral.yaml

# 2) 기준 브랜치 대비 파괴적 변경 탐지 (발견 시 종료 코드 1)
oasdiff breaking base/openapi.yaml head/openapi.yaml

# 3) 스테이징 서버가 스펙대로 응답하는지 대조
schemathesis run openapi.yaml --url https://staging.example.com

7.3 도입 순서를 틀리면 반발만 산다

세 단계를 한꺼번에 차단 조건으로 켜면 기존 스펙에서 수백 건이 쏟아지고, 팀은 규칙을 끄는 방향으로 대응한다. 실전에서 통하는 순서는 이렇다.

  • 1주차: 문법 검증만 차단 조건으로. 나머지는 경고로만 출력
  • 2~4주차: 린터 규칙을 신규 변경분에만 적용. 기존 위반은 목록으로 고정해 두고 점진 상환
  • 5주차 이후: 파괴적 변경 탐지를 차단 조건으로. 단 승인 절차를 함께 만들어 의도된 비호환 변경은 통과시킬 것
  • 구현 대조와 계약 시험은 가장 중요한 엔드포인트 몇 개로 시작

8. 폐기 정책에 반드시 넣을 항목

문서가 부풀어 오르는 것을 막는 유일한 장치가 폐기 절차다. 정책 문서에 들어가야 할 항목을 공개 사례와 표준 문서 기준으로 정리한다.

  • 선언 위치 - 폐기는 스펙 안에 표시한다. Zalando의 공개 지침은 엔드포인트·입력 인자·객체·속성을 폐기할 때 deprecated: true를 설정하고 설명 항목에 사유를 적도록 요구한다.
  • 최소 공지 기간 - 산업 표준 숫자는 없다. 구글 클라우드 이용약관은 서비스 중단이나 고객 대상 API의 하위 호환되지 않는 중대한 변경 전 최소 12개월 통지를 적고, 마이크로소프트 그래프 문서는 정식 출시 API 제거 최소 24개월 전 폐기 선언을 명시한다. 자체 기준은 소비자 성격에 맞춰 정하면 된다.
  • 응답 헤더 신호 - RFC 9745가 정의한 Deprecation 헤더와 RFC 8594가 정의한 Sunset 헤더를 함께 쓴다. Sunset 시각은 Deprecation 시각보다 앞설 수 없다.
  • 안내 링크 - 두 RFC 모두 링크 관계 유형을 정의한다. 정책·이전 안내 문서를 rel 값으로 연결한다.
  • 대체재 명시 - 무엇으로 옮겨야 하는지, 필드 대응이 어떻게 되는지를 적는다. Zalando 지침도 대체 수단과 이전 방법을 상세히 문서화하도록 요구한다.
  • 사용량 계측 - 같은 지침은 API 소유자가 이전 진행 상황을 관측해 통제 불능의 파급을 막도록 요구한다. 소비자별 잔존 호출량이 보이지 않으면 종료 시점을 정할 수 없다.
  • 외부 소비자 합의 - 외부 파트너가 있으면 폐기 후 유지 기간을 정하고 당사자 동의를 받아 둔다.
  • 종료 방식 - 어느 날 갑자기 끊을지, 짧은 시간 동안만 차단해 잔존 소비자에게 신호를 줄지, 오류율을 단계적으로 올릴지 미리 정한다.
  • 예외 조항 - 보안 취약점이나 법 준수 사유가 있으면 기간이 단축될 수 있음을 명시한다. 구글 클라우드 약관도 같은 예외를 둔다.

8.1 스펙과 헤더에 어떻게 적히는가

Sunset: Tue, 01 Sep 2026 00:00:00 GMT
Link: <https://api.example.com/docs/migrate/orders-v2>; rel="deprecation"

Deprecation 헤더 값은 구조화 필드 형식의 날짜여서 @ 뒤에 초 단위 정수가 온다. Sunset 헤더 값은 HTTP 날짜 형식이다. RFC 8594는 Sunset 시각을 힌트로 취급해야 하며 그때까지 가용성이 보장되는 것은 아니라고 명시한다. 즉 헤더는 약속이 아니라 신호다. 약속은 정책 문서와 합의가 만든다.

9. 문서 신선도 지표 - 무엇을 계측하면 어긋남이 보이는가

불일치는 장애를 일으키지 않는다. 알람도 울리지 않는다. 그래서 계측하지 않으면 영원히 보이지 않는다. 아래 지표는 대부분 기존 저장소와 접근 로그만으로 계산할 수 있다.

지표계산읽는 법
스펙 지연핸들러 코드 최종 변경일 − 해당 경로 스펙 최종 변경일양수 구간이 길수록 표류. 경로별 최댓값을 주간으로 본다

폐기 경과일선언일로부터 경과한 일수와 잔존 호출의 교차기간만 채우고 종료하면 사고가 난다

전부 볼 필요는 없다. 시작은 두 개면 충분하다. 유령 경로 수와 미문서화 경로 수다. 이 둘은 라우팅 테이블 덤프와 스펙 파일만 있으면 계산되고, 값이 0이 아닌 순간 지금 이 문서가 틀렸다는 사실을 이견 없이 보여 준다. 회의에서 우선순위를 얻는 데 가장 효과적인 숫자이기도 하다.

10. 엑셀·PDF로 관리 중인 조직의 이행 순서

가장 흔한 실패는 전수 이행이다. 200개 엔드포인트를 한꺼번에 옮기려다 3개월 뒤 중단하고 엑셀로 돌아간다. 순서를 바꾸면 다르다.

10.1 0단계 - 정본 하나 정하기 (며칠)

  • 떠돌아다니는 사본을 모아 현행 정본 하나를 지정하고, 나머지에 폐기 표시를 남긴다. 삭제는 나중에 한다.
  • 접근 로그로 실제 호출량 상위 20개 경로를 뽑는다. 이행 대상은 이 20개다.
  • 소비자 목록을 만든다. 사내 팀, 외부 파트너, 정체불명 호출 세 갈래로 나눈다.

10.2 1단계 - 상위 20개만 스펙으로 (2~3주)

  • 기존 문서와 실제 트래픽을 대조해 실제 동작을 기준으로 적는다. 엑셀에 적힌 것과 다르면 실제가 정답이다.
  • 스펙 파일을 서버 코드와 같은 저장소에 둔다. 이 한 가지가 경로 ①을 막는다.
  • 3.0으로 시작할지 3.1로 갈지는 쓰는 도구가 지원하는 범위로 정한다. 최신이 항상 정답은 아니다.

10.3 2단계 - 파이프라인에 얹기 (2주)

  • 문법 검증을 병합 차단 조건으로 건다.
  • 린터는 경고 단계로만 켠다. 이 시점에 차단하면 반발이 온다.
  • 스펙에서 문서 페이지를 생성해 URL로 배포한다. 이때부터 엑셀 첨부를 중단한다.

10.4 3단계 - 변경 통제 (3~4주)

  • 변경 요청에서 기준 브랜치 대비 차이 비교를 돌려 파괴적 변경을 표시한다.
  • 비호환 변경 승인 절차를 만든다. 승인 없이 통과하지 못하게 하되, 승인 경로는 짧게 유지한다.
  • 5절의 분류표를 팀 위키에 붙이고 판정 기준을 공유한다.

10.5 4단계 - 구현 대조와 계약 (4주 이상)

  • 스테이징 환경에 스키마 적합성 검사를 붙여 실제 응답과 스펙을 대조한다.
  • 가장 협조적인 소비자 한 팀과 계약 시험을 시범 적용한다. 전면 도입은 그다음이다.
  • 폐기 정책을 문서화하고 헤더 신호를 붙인다. 동시에 잔존 호출 계측을 시작한다.

10.6 하지 말아야 할 것

  • 도구부터 고르는 것. 정본 위치가 정해지지 않으면 어떤 도구도 자리를 못 잡는다.
  • 전 경로 동시 이행. 호출량 상위 20%가 대개 대부분의 사고를 만든다.
  • 첫 주부터 전면 차단. 규칙을 끄는 문화가 생기면 되돌리기 어렵다.
  • 엑셀을 병행 유지하는 것. 두 정본은 반드시 갈라진다. 옮겼으면 옛 파일은 읽기 전용으로 잠근다.

11. 이 체계가 막지 못하는 것

과장하지 않고 정리한다. 여기 적은 것을 다 해도 불일치가 사라지지는 않는다. 달라지는 것은 불일치가 드러나는 속도와 비용이다. 남는 구멍은 이렇다.

  • 의미는 여전히 사람이 지킨다. 스펙은 모양의 계약이다. 금액 단위, 시간대, 멱등성 규약처럼 설명문에 자연어로 적히는 약속은 어떤 검사기도 검증하지 못한다.
  • 설계 우선이 언제나 옳지는 않다. OpenAPI Initiative도 코드 우선이 시작하기 쉽다는 점은 인정한다. 요구가 흔들리는 초기 단계에 스펙부터 확정하면 스펙을 고치는 데 시간을 다 쓴다.
  • 자동 생성은 부정확한 구현을 그대로 문서화한다. 생성됐다는 사실이 정확성을 뜻하지 않는다.
  • 계약 시험은 참여자가 있어야 성립한다. 소비자가 누구인지 모르는 공개 API에는 다른 접근이 필요하다.
  • 린터 통과는 정확성 보증이 아니다. 스타일만 본다.
  • 소유자가 없으면 도구는 무력하다. 경보가 울려도 받을 사람이 없으면 경보는 소음이 된다.

그래서 목표를 불일치 0으로 잡으면 실패한다. 현실적인 목표는 이렇다. 어긋남이 배포 시점에 드러나고, 드러난 뒤 고치는 비용이 통합 시험 마지막 날에 발견하는 비용보다 훨씬 싸도록 만드는 것.

결론: 성실성 대신 구조에 맡겨라

엑셀 명세를 쓰는 조직에 필요한 것은 훈계가 아니다. 담당자는 이미 충분히 성실하다. 문제는 성실성이 유일한 방어선이라는 데 있다. 방어선이 하나면 그 하나가 쉬는 날 뚫린다.

바꿔야 할 것은 세 가지뿐이다. 첫째, 정본을 한 곳으로 못 박고 나머지를 파생물로 강등한다. 둘째, 정본을 코드와 같은 변경 요청 안에 넣어 갱신 트리거를 합친다. 셋째, 기계가 대조할 수 있는 형식으로 바꿔 어긋남이 자동으로 드러나게 한다. 이 셋을 하고 나면 린터도 차이 비교도 계약 시험도 그 위에 얹으면 되는 것들이다. 순서를 뒤집어 도구부터 사면 같은 사고가 더 비싼 형태로 재발한다.

마지막으로 이 글에서 가장 오래 남기고 싶은 문장 하나. 문서가 틀리는 것은 사고가 아니라 설계의 결과다. 틀릴 수 있는 구조를 그대로 두면 언젠가 반드시 틀린다. 반대로 틀리면 즉시 드러나는 구조를 만들어 두면, 사람이 게을러도 시스템이 버틴다. 문서 관리는 성실성의 문제가 아니라 구조의 문제다.

다음 주 월요일에 할 일은 하나다. 라우팅 테이블을 덤프해서 현재 명세와 대조하고, 양쪽에 없는 경로 수를 세어 보는 것. 그 숫자가 0이 아니라면 이미 답은 나와 있다.

# API 폐기(Deprecation) 정책 체크리스트

> 출처: braindetox.kr — API 문서는 왜 항상 코드보다 늦는가
> 표준 근거: RFC 8594(Sunset 헤더), RFC 9745(Deprecation 헤더)
> 이 파일을 그대로 AI에 붙여 「우리 서비스 기준으로 채워줘」라고 쓰면 됩니다.

## 1. 정책 문서에 반드시 박아둘 것
- [ ] 폐기 예고 기간 (예: GA 최소 __개월 / 프리뷰 최소 __주)
- [ ] 예고 시작 시점의 정의 (공지일 기준인가, 문서 반영일 기준인가)
- [ ] 호환 변경과 비호환 변경의 경계 (아래 2번 표로 합의)
- [ ] 예외 조항 — 보안 취약점은 예고 기간을 단축할 수 있는가
- [ ] 폐기 후 응답 (410 Gone인가, 계속 200인가)
- [ ] 통보 수단 (헤더 / 변경 로그 / 이메일 / 대시보드 중 무엇이 공식인가)

## 2. 변경 유형 분류 — 합의해 두지 않으면 매번 싸운다
| 변경 | 분류 | 폐기 절차 필요 |
|---|---|---|
| 필드 추가 (옵셔널) | 호환 | 불필요 |
| 필드 삭제 | 비호환 | 필요 |
| 필드 타입 변경 | 비호환 | 필요 |
| enum 값 추가 | **논쟁 지점** | 소비자가 엄격 파싱이면 비호환 |
| 필수 파라미터 추가 | 비호환 | 필요 |
| 에러 코드 추가 | **논쟁 지점** | 분기 처리하는 소비자가 있으면 비호환 |
| 정렬 순서 변경 | **논쟁 지점** | 문서에 보장이 없었다면 호환 |

## 3. 기계가 읽는 신호 (사람 공지만으로는 안 된다)
- [ ] `Deprecation` 응답 헤더 — RFC 9745
- [ ] `Sunset` 응답 헤더 — RFC 8594, 실제 종료 시각
- [ ] `Link` 헤더에 `rel="deprecation"`으로 안내 문서 연결
- [ ] OpenAPI 스펙에 `deprecated: true`
- [ ] 위 셋이 **서로 다른 날짜를 가리키지 않는지** CI에서 검사

## 4. 끄기 전에 확인할 것
- [ ] 최근 30일 호출 로그에서 잔존 호출 수 (0이 아니면 끄지 않는다)
- [ ] 잔존 호출자를 식별할 수 있는가 (API 키 / User-Agent / 계약 단위)
- [ ] 내부 시스템 중 이 엔드포인트를 쓰는 곳 (보통 여기서 사고가 난다)
- [ ] 대체 경로가 **동등한 기능**을 제공하는가 (부분 대체면 폐기 불가)
- [ ] 롤백 방법 — 껐다가 되살릴 수 있는가

## 5. 흔한 실패
- 문서에만 「지원 예정 없음」이라 적고 헤더는 안 보냄 → 아무도 모른다
- 예고는 했으나 **잔존 호출을 세지 않고** 껐다
- 대체 API를 만들었지만 **마이그레이션 가이드가 없다**
- 폐기일을 여러 문서에 적었는데 날짜가 서로 다르다
