Deciding to Serve LLMs Yourself - A Checklist Before You Build the Platform

Engine choice, GPU sizing, batching design and ML platform integration, read through the in-house serving setup Netflix made public

Jul 28, 2026 Dev & Infra
Scope of this article — This is general information assembled from public technical documentation and papers. It does not recommend adopting any particular vendor or open-source project. Serving performance varies widely with model, hardware and request distribution, so none of the configurations described here guarantees any particular result. Base your own decision on measurements taken with your own workload.

Introduction: the moment someone says we should just run it ourselves

Teams that started on hosted APIs usually arrive at the self-hosting question through one of three doors. A data boundary turns out to be stricter than anyone assumed. A fine-tuned model has to reach production and the hosted path does not give the shape you need. Or the monthly invoice crosses a line and finance starts asking questions. Whichever door it is, the sentence in the room sounds the same. Open-weight models have gotten good, so why not run one ourselves?

The question is healthy. What follows it usually is not. The discussion drifts into comparing GPU quotes and benchmark scores, while the items that actually consume time in production never make the evaluation sheet at all. Things like which engine and server versions are safe together, how model artifacts get onto a node, what happens to consumer code when a model is replaced, and whether existing dashboards still work when metrics arrive from two separate places.

On 17 July 2026 the Netflix technology blog published a description of its in-house LLM serving platform, written jointly by the Model Runtime and Inference teams within the AI Platform organisation. What makes it worth reading is not the architecture diagram but the list of things that went wrong. It records which parameter was silently dropped, which version pairing prevented a backend from loading at all, and where latency ended up bound to the CPU.

This article is not a summary of that post. Most of the problems Netflix hit are structural, which means a far smaller team attempting the same thing will meet them too. So the goal here is to convert that list into a decision checklist for anyone evaluating in-house LLM serving. How to control spend is covered separately in governing token cost at the org level, and how to move between vendors in vendor lock-in and exit strategy. What follows deals only with the infrastructure problems on the side where you run the model yourself.

1. What Netflix actually built, and what the structure tells you

The published architecture has three layers. At the front sits a JVM-based serving layer that handles routing, feature retrieval, candidate generation, post-processing and logging. Behind it is a shared inference backend called the Model Scoring Service (MSS), and underneath that the NVIDIA Triton Inference Server takes care of model loading, batching and GPU scheduling. Small CPU models run in-process inside the serving layer; larger models are delegated to MSS over a remote call.

The most consequential decision here is not a technology pick but a placement. Netflix did not stand up a separate LLM stack. In the words of the original post, they run the full stack themselves inside their existing production environment rather than in a separate ML silo. MSS supports XGBoost, TensorFlow, PyTorch and LLMs behind one interface, and every model is scored through the same gRPC call. The Java control plane that already handled deployment, versioning, health checking, autoscaling and multi-region rollout was reused as-is.

  • The goal was not to build an LLM platform. The goal was to add LLMs as one more model type inside an existing model serving system.
  • There are two frontends. gRPC for the existing serving layer and an OpenAI-compatible HTTP surface for newer applications, both exposed from the same instance.
  • OpenAI compatibility exists for the migration path, not for convenience. It minimises code changes when a team graduates from a hosted model to a fine-tuned self-hosted one.
  • Artifact storage was designed separately. Instead of pulling large weights from object storage each time, models are materialised onto a high-performance file system at announcement time.
  • Metrics are merged before they leave the box. A dedicated proxy combines what the inference engine and the model server each publish into a single endpoint.

Invert those five lines and you have the first five entries on any self-hosting evaluation sheet. Where does it attach, what API surface do you expose, how do teams migrate onto it, how do weights reach the node, and where do metrics get merged.

2. Where LLM serving diverges from traditional ML serving

Teams that already operate an ML platform are the most likely to underestimate this part, because it looks like adding one more model. The divergence runs deeper than it appears, and nearly all of it follows from a single property: you do not know the output length when the request arrives.

AxisTraditional ML (trees, small networks)LLM
Output lengthFixed by the schemaVariable, known only once generation ends
Compute per requestOne forward passOne forward pass per output token
Memory profileMostly weights, near constant per requestWeights plus a KV cache that accumulates per request
BatchingGroup requests and run them togetherContinuous batching that admits and retires each step
Main bottleneckGenerally computePrefill is compute-bound, decode is memory-bandwidth-bound
Latency definitionA single response timeSplit into first token and inter-token interval
Capacity limitRequests per secondConcurrent sequences multiplied by context length
Saturation symptomQueueing and timeoutsIn-flight requests rolled back when KV cache runs short

2.1 Prefill and decode are two different jobs

Each request runs in two phases. Prefill reads the whole input at once and builds internal state; decode emits tokens one at a time. Prefill parallelises across input tokens, so the compute units stay busy. Decode has to re-read the model weights to produce a single token, so it is bound by memory bandwidth. The fact that the two phases bottleneck on different resources shapes the entire batching design.

2.2 KV cache is the centre of capacity planning

The KV cache stores keys and values from earlier tokens so decode does not recompute them. It grows per request and linearly with token count, a property traditional ML simply does not have. Memory is decided by the total number of live tokens rather than the number of requests, so the familiar requests-per-second capacity metric does not translate directly.

PagedAttention proposed treating this the way an operating system treats virtual memory: split the cache into blocks, place them in non-contiguous physical space to reduce fragmentation, and allow sharing within and across requests. The original paper set out near-zero waste in KV cache memory as the target and reported throughput improvements of two to four times over the state-of-the-art systems of the time at comparable latency, with larger gains for longer sequences, larger models and more complex decoding.

2.3 Continuous batching changes what batch size means

Static batching groups several requests, runs them together, and leaves the remaining slots idle until the slowest one finishes. With wildly varying output lengths that waste is large. Continuous batching moves the scheduling unit down from the batch to the decoding step, retiring finished requests immediately and admitting waiting ones into the freed slots. As a result a fixed value such as batch size 32 loses its meaning, and two different knobs appear instead: the token budget per step and the ceiling on concurrent sequences.

3. Engine choice is settled by operational fit, not by a benchmark table

Netflix started on a compilation-based engine, then re-benchmarked in the summer of 2025 after the workload mix broadened and settled on vLLM as the paved-path engine. The post lists four reasons for that choice, and the notable thing is that none of them is a performance claim.

  1. Custom architectures load without a multi-step compilation pipeline, which speeds up iteration on non-standard models.
  2. There are extensibility hooks for custom decoding logic, which the constrained-decoding work described later required.
  3. Failures and intermediate state are easier to inspect than with the compiled engine of that period.
  4. Research teams were already using it, which cut the cost of handing work from research into production.

The post judged that the raw performance gap had already narrowed by 2025. In other words the decision was made on which engine fits the way this organisation works, rather than which engine is faster. The point is not to recommend a particular tool, but to note where the deciding axis actually sat.

ApproachCharacterWhere it shinesWhat it costs
Compilation-basedModel is built ahead of time into a hardware-specific engineModel and hardware are fixed and stay that way for a long timeA build step enters the release path and internal state is harder to observe
Runtime-basedWeights are loaded as they are and scheduled at runtimeModels change often and decoding needs customisationA scripting layer stays on the hot path and can become a bottleneck
Model serverHosts multiple backends and manages loading, versioning and batchingSeveral model types have to live in one serverVersion coupling appears between the server and its backends

Using this table in practice is simple. Answer the four questions below and pick whichever side the answers cluster on.

  • How often does the model change? If it is once a quarter, a build step is affordable.
  • Do you need to intervene in decoding? Enforcing an output format requires an extension point.
  • Who gets paged at three in the morning? That person has to be able to open the stack up.
  • What are the research and analytics teams already using? Handover cost is larger than it looks.

4. Conditions that favour in-house serving, and conditions that rule it out

The common mistake is to start from cost. Cost is the last condition. If the ones before it do not hold, no amount of modelling makes that number real. The preconditions behind the Netflix case are visible in the post itself: a shared inference backend and a Java control plane already existed, and there were engineers able to reimplement a constrained-decoding hot path in C++.

AxisTilts toward in-house servingTilts toward a hosted API
Data boundaryRegulation or contract forbids outbound transferNo transfer restriction, or one solvable by contract
ModelYou operate fine-tuned or domain-adapted modelsYou need the newest frontier model quality
Traffic shapeSteady and predictable, with flow even overnightSpiky, with a large peak-to-average ratio
Output controlYou must intervene inside the decode loopPrompting and post-processing are sufficient
OrganisationGPU operations and MLOps staff already existNo dedicated staff, or the role is a side duty
Change cadenceYou keep one model pinned for a long timeYou switch as soon as something better ships
Latency requirementYou need to control the latency floor yourselfA vendor SLA is good enough
ScaleLarge enough to keep one instance consistently busyNot even one instance would be filled

Read the table and one thing becomes clear: a single strong hit in the right-hand column weakens the case for in-house serving sharply. Traffic shape in particular inverts the whole cost calculation. GPUs bill whether or not they are busy, so instances provisioned to survive the peak sit idle the rest of the time and drive up cost per token by exactly that margin. That item returns in the break-even section below.

5. GPU sizing: count weights and KV cache separately

Answering how many gigabytes a model needs with the parameter count alone is only half right. The requirement splits into three parts.

  • Weights — parameter count multiplied by bytes per element; two bytes per parameter for 16-bit floats. Tensor parallelism divides this across cards.
  • KV cache — proportional to the number of live tokens. In practice this is what determines concurrency.
  • Activations and framework overhead — intermediate tensors, communication buffers and whatever the runtime holds. Hard to predict precisely, so leave it as headroom.

5.1 Start from bytes of KV cache per token

The formula is plain arithmetic. Two sets of vectors, keys and values, stored for every layer, for every KV head, at the head dimension.

KV bytes per token
  = 2 (key and value)
  x layers (num_hidden_layers)
  x KV heads (num_key_value_heads)
  x head dimension (head_dim)
  x bytes per element (bf16 = 2)

Example) 32 layers, 8 KV heads, head dim 128, bf16
  = 2 x 32 x 8 x 128 x 2
  = 131,072 bytes = 128 KiB per token

One sequence x 8,000 tokens  ->  about 1.0 GiB
20 concurrent sequences      ->  about 20 GiB

One mistake shows up here again and again. The head count must be the KV head count, not the attention head count. Most recent models use grouped-query attention, so the KV head count is far smaller than the attention head count. Substituting 32 attention heads in the example above would overestimate the requirement fourfold. Read the values from the model configuration file rather than assuming them.

5.2 The sizing sequence

  1. Subtract the weights from total card memory.
  2. Decide how much the runtime pre-allocates. vLLM reserves GPU cache according to gpu_memory_utilization, and raising it enlarges KV space and reduces preemption.
  3. Divide whatever is left for KV by bytes per token multiplied by target context length. That is your concurrency ceiling.
  4. Derive a rough throughput ceiling from concurrency and average handling time. This figure is an estimate and must be replaced by measurement.
  5. Divide peak traffic by that ceiling to get instance count, then add redundancy and the deployment overlap share.
  • Doubling the context ceiling doubles KV per sequence and roughly halves concurrency on the same card. Context is not free.
  • A well-matched prefix cache reduces actual usage below the calculation, but planning to the worst case is safer.
  • Quantisation shrinks weights; it does not automatically shrink the KV cache. KV quantisation is a separate setting whose quality impact must be measured on its own.
  • Development and staging GPUs are frequently omitted. Counting production only leaves the model out of step with the real invoice.

6. What you actually have to decide in batching and queueing

Continuous batching reduces tuning to a handful of knobs. The catch is that those knobs pull against each other. So the exercise is not finding an optimum but deciding in advance which metric you are willing to sacrifice.

DecisionWhat it governsRaising itLowering it
Token budget per stepTotal prefill and decode tokens processed in one stepImproves time to first tokenStabilises the interval between tokens
Concurrent sequence ceilingHow many ways the KV pool is dividedRaises throughput and rollback risk togetherReduces rollback, may leave the GPU idle
Maximum context lengthThe ceiling one sequence may occupyAccommodates long inputsPreserves concurrency
Memory pre-allocation ratioOverall KV pool sizeReduces rollbackLeaves more headroom against out-of-memory
Rollback behaviourWhether to recompute or swapEnvironment dependent; recent implementations default to recompute
Queue wait ceilingWhen to reject a requestFewer rejections, longer tail latencyShorter tail latency, more rejections
Priority separationHow interactive and batch work are splitMixing them in one pool lets batch work push interactive latency up

6.1 Why chunked prefill became the default

When one long prompt arrives, its prefill can occupy an entire step, and requests already streaming answers stall for that duration. To a user it looks like text appearing and then abruptly stopping. Chunked prefill splits a long prefill across multiple steps to soften that. The vLLM documentation states that it improves inter-token latency and decode, and that it also raises GPU utilisation by placing compute-bound prefill and memory-bound decode in the same batch. In the newer architecture it is enabled by default wherever possible.

The tuning direction is documented too. A smaller token budget per step, such as 2048, gives better inter-token latency, while a larger one gives better time to first token. For maximum throughput the guidance is to go above 8192, especially for smaller models on large GPUs. No single value satisfies all three goals, so deciding whether the service is interactive or batch comes first.

6.2 When rollback warnings start appearing

When memory runs short the engine reclaims the KV cache of an in-flight request and reschedules it later. Frequent rollback means the same tokens get computed twice, degrading both throughput and tail latency. The order of response suggested by the vLLM documentation is as follows.

  1. Raise the memory pre-allocation ratio to widen KV space.
  2. Lower the concurrent sequence ceiling so fewer requests are live at once.
  3. Increase the tensor parallel size.
  4. Increase the pipeline parallel size.

6.3 What queueing designs usually forget

  • Without admission control there is no bound on tail latency. An unbounded queue delivers an answer eventually, long after the user has left. Rejecting past a wait threshold is the better outcome.
  • Rejection is a design choice, not a failure. Decide what a client does on a 429 as well: fall back to another model, return a shortened answer, or retry later.
  • Define the SLO in terms of first token and inter-token interval. A single end-to-end target gives you no basis for choosing which way to turn a parameter.
  • Retry policy amplifies load. Automatic retries stacking up during saturation make the queue longer. Pair backoff with a retry budget.
  • The server must notice when a streaming client goes away. Emitting tokens after the user closed the window is pure waste.

7. Packaging and deployment: what breaks when the interface changes

This is the section practitioners will get the most from. There are two ways to package the same model, and the difference between them is coupling rather than performance.

  • Scripted backend — input and output tensor specifications are declared at packaging time and frozen into the artifact. When a frontend upgrade touches those specifications, the packaging code has to change with it, and requests fail at runtime if it does not.
  • Engine backend — the artifact is a configuration file pointing at weights and tokeniser, and the specification is generated dynamically at deployment. Models and frontend can evolve independently, which is why it became the recommended default.

The second approach carries its own price: version coupling between server and engine. The post gives a concrete example in which a particular server release tried to import a module the engine had already removed, and the backend failed to come up at all. Netflix therefore pins jointly validated combinations together. Models needing custom pre-processing, post-processing, ensemble pipelines or non-standard tokenisation still fall back to the scripted backend, and the post says that escape hatch will likely remain necessary for a subset of models.

7.1 Two deployment strategies and their GPU cost

StrategyBehaviourSuitsWeakness
Red-blackNew version comes up alongside, traffic shifts in phases after health checks pass, rollback is atomicStable model interfacesA schema change causes mismatches mid-migration
VersionedIndependent deployment per model and version pair, several versions serve at onceUnavoidable breaking interface changesGPU cost rises temporarily during the overlap

The recommendation in the post is explicit: embed variable configuration such as tensor shapes into the model so the interface becomes version-agnostic, and use the cheaper red-black path. Reserve versioned deployment for the rare unavoidable breaking change. Translated into operational language, that means the following.

  • Deploying an LLM is not swapping a container image. Plan capacity around the fact that GPUs are needed at roughly double for the length of the transition.
  • Without version negotiation in the model interface, replacing a model becomes coupled to deploying consumer code. Breaking that coupling is the purpose of a deployment strategy.
  • Build the rollback path first. You will need the way back more often than the way forward.
  • Keep a list of validated engine and server combinations. Without it every upgrade is a gamble.

8. Six friction points when layering onto an existing ML platform

These are the collisions that teams with an existing serving stack actually run into. Netflix documented how it handled each, which makes them easy to compare against.

  1. Interface contract — existing platforms assume tensors in, tensors out. LLMs need streaming, variable length and mid-flight cancellation. Rather than unifying them, Netflix ran two frontends on the same instance, gRPC and OpenAI-compatible HTTP, so existing consumers stayed put while new ones used the new surface.
  2. Artifact distribution — existing models load in seconds; LLM weights run to tens of gigabytes. The post notes that downloading directly from object storage or a model hub at startup inflates cold start past what schedulers tolerate, and describes materialising models onto a high-performance file system at announcement time instead.
  3. Autoscaling signals — rules built on requests per second and CPU utilisation react too late for LLMs, because a single request stays alive for a long time. Queue depth, KV cache utilisation and waiting time are the signals that work.
  4. Observability — the inference engine and the model server are unaware of each other. According to the post the server bridge surfaced only 9 of more than 40 engine metrics, leaving out exactly the ones that matter, such as token throughput, KV cache utilisation and prefix cache hit rate. Netflix built a lightweight proxy that reads both sources and merges them into one metrics endpoint, so existing dashboards and alerts kept working unmodified.
  5. Silent gaps in the API contract — the most practically useful warning in the whole post. The OpenAI-compatible frontend silently dropped the structured-output field before it reached the engine. Nothing errored, which is why it took a while to notice. Netflix pulled that frontend in and patched it to translate the field into the engine guided-decoding parameters. The lesson is blunt: OpenAI-compatible is not a guarantee of specification compliance. Every field you rely on needs a contract test.
  6. Deployment pipeline and node pools — GPU node pool separation, image size, driver versions and warm-up on node restart all violate assumptions baked into an existing CI/CD setup. Large images in particular lengthen deployments, which feeds back into the strategy choice above.

9. What happens when you enforce structured output

Many services cannot use raw LLM output and need a fixed format. The common approach is to validate after generation and retry on mismatch, which means paying for the invalid generation first and repairing afterwards. Netflix pushed the constraint inside the decode loop instead. Because different requests carry different rules, each request gets its own configured processor.

9.1 Why latency ended up bound to the CPU rather than the GPU

The early implementation exposed a problem: the logits processor ran per request. The GPU produced logits for the whole batch, the CPU copied them over, and constraint logic then ran sequentially for each request. Python global interpreter lock semantics prevented that work from parallelising, so CPU time grew linearly with batch size. The post describes the situation precisely: the forward pass batches efficiently on the GPU while end-to-end latency becomes CPU-bound and tail latencies spike.

The structural fix arrived with the newer engine generation, which moved logits processing to batch level. Netflix rewrote the processor around batch-level data structures and reimplemented the hot path in C++ with multi-threading to step around the lock, after which logits processing time stayed flat as batch size grew. The price is API complexity: batch membership changes have to be tracked explicitly, which is harder to work with than the earlier per-request interface.

9.2 Two problems that only appeared in production

Two issues invisible in benchmarks surfaced under real concurrency. Both are cases of a state machine having its assumptions broken.

[Problem 1] Partial prefill
  With chunked prefill, one request may be prefilled across several steps.
  The batch update information alone cannot distinguish a full prefill
  from a partial one.
  -> Add internal tracking of progress state

[Problem 2] State reset caused by rollback
  Under memory pressure the engine evicts the KV cache of an in-flight
  request and reschedules it later with a different prompt and output
  token list. The state machine had assumed the output token list only
  ever grows.
  -> Detect the token history shrinking between steps, reset the state
     machine and reinitialise from the new prompt

9.3 Most organisations do not need to go this far

Copying this section wholesale would be a poor decision. Work that reaches down to kernel level is justified only when the cost of an invalid generation exceeds the cost of a retry. Three criteria settle it.

  • Current valid output rate — what percentage passes with prompting and a schema declaration alone. A high number leaves little room to improve.
  • Cost of a retry — the money and latency of running one failed case again. Short outputs make retries cheap.
  • Latency budget — whether a retry still fits inside the SLO. For interactive traffic one retry can consume the whole budget.

Only when all three land on the unfavourable side does decode-time intervention pay. Otherwise the ordinary combination of prompt design, schema declaration and retry-on-failure is easier to maintain. Whichever path you take, though, a test verifying that structured-output parameters actually reach the engine is mandatory. The silent-drop case described earlier occurred at exactly that seam.

12. How to compute your own break-even

Numbers along the lines of self-hosting wins above a certain monthly spend, or a certain daily token count being the crossover, circulate widely. The trouble is that those figures are usually presented without their assumptions. If you cannot see which GPU under which contract, what utilisation was assumed, or whether staffing was included, the number does not transfer to another organisation. So this article cites no break-even figure and gives only the framework.

[Hosted API side]
  Monthly = (input tokens x input rate + output tokens x output rate)
            x monthly requests
            - prompt cache savings - batch discount

[Self-hosted side]
  Monthly = GPU hourly rate x instances x 730 hours
            + storage + network + load balancer
            + operations staffing (FTE equivalent)
            + development and staging GPUs
            + extra capacity during deployment overlap

[Basis for comparison]
  Cost per token = monthly cost / tokens actually served that month
  Note: the denominator is the whole game. Half the utilisation
        means double the cost per token.

Work through it in this order.

  1. Plot traffic by hour of day first. The peak-to-average ratio dominates this calculation.
  2. Measure goodput per instance at your target SLO. Estimating instead of benchmarking makes everything downstream unstable.
  3. Derive the instance count needed to survive the peak, then add the redundancy share.
  4. Calculate how idle those instances are during average hours to get effective utilisation.
  5. Divide total cost by monthly tokens served to get cost per token.
  6. Add the human cost. Managing version pairings, tracking engine issues and merging metrics are standing work, not one-off tasks.

The items most often left out of the calculation are worth listing separately.

  • GPUs for development and staging environments. Counting production only leaves you out of step with the invoice.
  • The overlapping instances that run during a deployment transition.
  • Model artifact storage and the high-performance file system holding it.
  • Regional redundancy or standby capacity for failure handling.
  • GPU hours consumed by benchmarking itself. Tuning is never done once.
  • Overnight and weekend coverage. In-house serving produces failures you cannot hand to a vendor.

Three misconceptions are worth naming as well.

  • Open weights so it is free — the weights are free, the serving is not. Most of the cost is GPU hours and people hours.
  • Buy one GPU and you are done — without redundancy that is a single point of failure. A one-card minimum only holds for experiments.
  • Half the price of the API — look for the utilisation assumption behind any such claim. A calculation premised on full utilisation does not survive a real traffic distribution.

How to manage the unit price of tokens and attribute spend to teams is beyond this article; that is covered in token cost governance, while splitting traffic across several models by situation is covered in model routing.

13. Conclusion: write the decision list before you build the platform

What to take from the Netflix case is not the architecture diagram. That architecture was built on the premise of an existing shared inference backend and a JVM serving layer, and an organisation without those premises copying the picture would be worse off. What transfers is the list of decisions they actually had to make.

  1. Does the LLM get its own stack, or join the existing model serving system as one more model type?
  2. What API surface do you expose, and do you run the existing interface and a standard-compatible one side by side?
  3. Do you pick the engine on performance, or on iteration speed and debuggability?
  4. Which packaging approach do you take, and will you accept version pinning in exchange for lower coupling?
  5. Red-black or versioned deployment, and where does the GPU cost for it sit in the budget?
  6. How do you divide the KV cache budget, and which do you give up, context ceiling or concurrency?
  7. How do you split the SLO between first token and inter-token interval, and what are the wait ceiling and rejection policy?
  8. Do you enforce structured output inside decode, or absorb it with post-processing and retries?
  9. Where do metrics get merged, and will existing dashboards keep working unchanged?
  10. By what path do weights reach a node, and what is the cold start budget?

A suggested starting order. Run a real benchmark against your own request distribution to obtain goodput per instance. Define the SLO from that number. Then pilot with one model and one workload, but build metric merging and the deployment strategy during the pilot. Deferring those two means coming back to them at scale-out time.

One closing note. None of the configurations described here guarantees any particular performance. Engine version, model architecture, request length distribution and card generation each move the numbers. A published case tells you what has to be decided; it does not tell you the answer. The answer only comes from measuring against your own traffic, and putting that measurement system in place is the real first step of serving models yourself.
