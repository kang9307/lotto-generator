공개된 것과 글쓴이의 경고 — 아직 일반 사용 단계가 아니다

2026년 10월 5일, Remo Senekowitsch는 자신의 블로그에 「Flirt is now Open-Source」라는 짧은 글을 올려 코드 리뷰 도구 Flirt의 소스 코드를 Codeberg의 flirt/flirt 저장소에 공개했다고 알렸다. GeekNews에는 2026년 10월 6일에 소개됐다. Flirt라는 이름은 2025년 11월의 첫 소개 글에서 「Fabulous, Legendary, Incremental Review Tool」의 약자라고 설명됐고, 저장소 설명란에는 「The Fabulous Legendary Incremental Review Tool」이라고 적혀 있다.

공지는 처음 읽는 사람을 위해 덧붙인 문단에서 Flirt를 세 문장으로 소개한다. 작성자가 변경을 계속 amend·rebase·force-push하는 「패치 시리즈」 워크플로에 맞춘 리뷰 도구이고, 리뷰어가 이전에 리뷰한 것을 기억해 현재 상태와의 차이를 보여 주며, 로컬 우선 도구로서 GitHub와 메일링 리스트 같은 여러 백엔드와 호환된다는 것이다. 그 바로 다음 문단이 경고다.

Warning: I don't yet consider it ready for general use.
                    There are still plenty of bugs and missing features.
                    If you're not considering to become a contributor, I recommend being a little more patient.
                    I'll probably write another blog post when Flirt is ready for you.

옮기면 「아직 일반 사용에 준비됐다고 보지 않는다. 버그와 빠진 기능이 여전히 많다. 기여자가 될 생각이 아니라면 조금 더 참고 기다리기를 권한다. Flirt가 준비되면 아마 글을 하나 더 쓸 것이다」이다. 마지막 문장의 「아마(probably)」는 원문의 단서다. 저장소 README의 경고는 문구가 다르지만 수위는 같다. README는 Flirt가 매우 이른 개발 단계이고 일반 사용에 준비되지 않았으며, 기여할 의도가 있을 때만 시험해 보라고 적는다. 그렇지 않으면 사용 경험에 실망하게 된다는 문장이 이어진다.

공지의 나머지는 두 가지다. 하나는 기여할 생각이 있든 없든 Zulip 토론에 참여해 달라는 것이고, 그곳에서 LLM으로 메시지를 쓰는 것은 허용되지 않는다는 단서가 붙는다. 다른 하나는 Forgejo 백엔드다. Flirt가 Codeberg에 있으니 Forgejo 백엔드가 있으면 Flirt 개발에 Flirt를 쓸 수 있겠지만, 글쓴이는 이것을 「가정적인(hypothetical)」 백엔드라고 부르고 아직 존재하지 않는다고 적는다. 만드는 일이 할 일 목록의 다음 차례라는 문장으로 공지가 끝난다.

공개까지의 경위는 같은 블로그의 글 네 편에 날짜순으로 남아 있다.

  • 2025년 11월 5일 — 개발 착수 알림. Flirt는 글쓴이의 석사 논문 과제이고, 논문을 낼 때까지는 혼자 비공개로 작업하며, 오픈소스 공개는 2026년 8월쯤이 될 것 같다고 적었다. 라이선스는 정하지 못했다고 했다.
  • 2026년 2월 7일 — Native Git 백엔드 경과. 기능 명세와 저장 방식을 설명했고, 이 백엔드가 아직 기능을 다 갖추지 못했다고 적었다.
  • 2026년 8월 15일 — GitHub·메일링 리스트 백엔드 경과. 논문을 8월 1일에 제출했고, 정리한 뒤 1~2개월 안에 공개하는 것을 목표로 한다고 적었다. 이때 이미 공개본이 사용자를 위한 준비는 되지 않을 것이며, 코드 리뷰에 대한 생각에 공감해 초기부터 개발 방향에 참여하려는 사람을 위한 것이라고 밝혔다.
  • 2026년 10월 5일 — 공개 공지. 저장소 주소와 위의 경고, Zulip 안내, Forgejo 백엔드 계획을 담았다.

풀려는 문제 — 강제 푸시 뒤에 같은 코드를 다시 읽는다

README는 두 워크플로를 각주에서 구분한다. 패치 시리즈 워크플로에서는 리뷰 주기를 거치며 커밋이 다시 쓰이고(amend, rebase, force-push 등), 풀 리퀘스트 워크플로에서는 기존 커밋을 건드리지 않고 브랜치 끝에 새 커밋을 더한다. 2025년 11월 글은 이 구분을 더 길게 설명한다.

글쓴이가 「PR 워크플로」라 부르는 쪽은 GitHub의 풀 리퀘스트 기능으로 널리 퍼진 방식이다. 이미 리뷰된 커밋은 건드리지 않고 브랜치 끝에 새 커밋만 더하도록 권하므로, 리뷰어는 마지막으로 리뷰한 커밋과 최신 커밋 사이의 diff만 보면 된다. 글쓴이는 이 방식이 이미 「점진적」이며, 여기에 만족하는 사람은 Flirt에서 얻을 것이 그만큼 많지 않다고 적는다.

「패치 시리즈 워크플로」는 메일링 리스트에서 하는 방식에서 이름을 땄지만 GitHub에서도 쓰이고, 글쓴이는 Jujutsu 프로젝트를 예로 든다. 작성자는 리뷰 주기마다 커밋을 amend, squash, fixup, rebase하며 커밋 이력의 품질을 높여 간다. 글쓴이가 드는 이점은 버그의 출처를 찾을 때 정돈된 이력이 그 버그를 들여온 커밋을 찾아 되돌리기 쉽게 해 준다는 것이다.

대가는 리뷰 쪽에서 치른다. 기존 커밋을 고치는 연산은 커밋 해시를 바꾸고, 그 뒤에는 커밋이 어떻게 달라졌는지 알아내기가 쉽지 않다. 글쓴이의 예는 이렇다. 패치 시리즈의 한 커밋이 100줄을 바꾸는데 99줄은 문제가 없고, 첫 리뷰에서 한 줄에 빠진 세미콜론을 넣으라는 지적이 나온다. 작성자는 「세미콜론 추가」 커밋이 이력에 남지 않도록 기존 커밋을 amend한다. 강제 푸시(또는 새 패치 시리즈 제출) 뒤 리뷰어 앞에는 대체로 100줄짜리 diff 전체가 다시 놓인다. 도구가 지난 리뷰 이후 한 줄만 바뀌었다는 것을 알지 못하기 때문이다. 글쓴이는 이런 도구를 「비점진적」 리뷰 도구라고 부른다.

기존 도구의 보완책에 대한 글쓴이의 평가도 같은 글에 있다. GitHub 풀 리퀘스트 화면의 「changes since last review」 버튼과 파일별 「viewed」 체크박스는 도움이 되지만 평범한 상황 여럿에서 통하지 않는다는 것이 글쓴이의 서술이고, 메일링 리스트 쪽에는 휴리스틱으로 패치 시리즈의 두 판을 비교하는 git range-diff가 있다고 적는다. 글쓴이가 짚은 문제와 Flirt 쪽 대응을 모으면 다음과 같다. 「구상」과 「계획」으로 적은 칸은 해당 글 시점의 서술이다.

대상 독자도 한정돼 있다. 글쓴이는 패치 시리즈 워크플로를 쓰는 사람, 또는 그 문제가 풀리면 옮겨 가려는 사람이 Flirt의 대상이라고 적는다.

change-id로 커밋을 짝짓는다 — interdiff와 git range-diff

해법의 바탕은 change-id다. 2025년 11월 글의 정의로는 커밋 해시와 달리 커밋이 amend되거나 rebase돼도 그대로 유지되는 또 하나의 커밋 식별자다. 리뷰 도구가 이미 리뷰한 커밋을 change-id와 함께 기억해 두면, 새 커밋이 올라왔을 때 같은 change-id를 가진 이전 커밋과 짝지을 수 있다. 두 커밋 사이의 interdiff를 계산하면 리뷰어가 아직 보지 못한 변경만 남는다. 글쓴이는 이것이 Flirt의 중심 기능이라고 적는다. 리뷰한 것을 기억하고, 기본으로는 그것과 비교해 달라진 것만 보여 준다.

용어는 Austin Seipp의 글 「Why some of us like "interdiff" code review」에서 왔고, README도 워크플로 설명의 참고로 이 글을 건다. 글쓴이는 interdiff라는 말이 구현 방식을 가리켜 다소 기술적이라며, 실용적 이점을 드러내는 「점진적 코드 리뷰(incremental code review)」라는 이름을 택했다고 적는다. 가리키는 것은 같다.

change-id가 어디서 오는지에는 조건이 붙는다.

  • Jujutsu는 Git과 호환되는 버전 관리 도구로, change-id를 사용자 정의 커밋 헤더에 기록한다. Flirt가 이 방식을 쓸 수 있는 것은 커밋 작성자가 Jujutsu를 쓸 때다.
  • README는 이 기능이 커밋에 담긴 여러 종류의 메타데이터에 의존하며, 작성자가 Jujutsu를 쓸 때 신뢰도가 가장 높다고 적는다.
  • change-id 헤더가 없으면 대체 휴리스틱이 쓰인다. 2025년 11월 글은 이 대체 수단이 개념상 git range-diff와 같은 일을 하되 처음에는 훨씬 단순한 휴리스틱일 것이라고 적었다.
  • 2026년 8월 글은 제목 줄과 작성자를 맞춰 보는 식의 휴리스틱을 예로 들고, 지금의 제약에서는 무엇을 택하든 휴리스틱일 수밖에 없다고 적었다.
  • Gerrit에도 같은 기능이 있다고 README는 적는다. 글쓴이는 Gerrit의 리뷰 화면이 change-id로 이미 점진적 리뷰를 해낸다고 쓰면서, 자신은 Gerrit을 본격적으로 써 본 적이 없다고 밝힌다.

Gerrit이 있는데 새 도구를 만드는 이유로 글쓴이가 드는 것은 플랫폼 문제다. 자신이 일하는 프로젝트들의 코드 공유 플랫폼을 자신이 정하지 못하고, 직장과 즐겨 기여하는 오픈소스 프로젝트 다수가 GitHub를 쓴다는 것이다. 리뷰 도구가 코드 공유 플랫폼에 묶여 있다는 점을 푸는 것이 Flirt의 두 번째 동기라고 글쓴이는 적는다.

대체 수단의 기준점인 git range-diff는 Git 공식 문서에 이렇게 정의돼 있다. 패치 시리즈의 두 판, 더 일반적으로는 두 커밋 범위 사이의 차이를 보여 주는 명령이고 머지 커밋은 무시한다. 짝을 찾는 근거는 식별자가 아니라 유사도다.

  • 두 커밋의 패치(작성자 정보, 커밋 메시지, 커밋 diff)를 서로 diff한 결과가 패치 크기에 비해 충분히 작으면 두 커밋이 대응한다고 본다.
  • 두 범위의 커밋 쌍마다 「diff의 diff」를 문맥 3줄로 만들어 그 줄 수를 비용으로 삼고, 최소 비용 할당 문제를 푼다.
  • 큰 변경을 통째 재작성(한 커밋의 삭제와 다른 커밋의 추가)으로 잘못 볼 때 조정하는 옵션이 --creation-factor이고 기본값은 60이다.
  • 출력은 사람이 읽기 위한 것이다. 문서는 출력이 바뀔 수 있으며 기계가 읽도록 의도된 것이 아니라고 적는다.

정리하면 range-diff는 패치 내용의 유사도로 짝을 추정하고, change-id 방식은 커밋에 기록된 식별자가 같은지로 짝을 정한다. Flirt의 README가 작성자의 Jujutsu 사용 여부에 따라 신뢰도가 달라진다고 밝히는 이유가 여기에 있다.

백엔드 넷의 상태 — Forgejo는 아직 없다

README는 사용자가 프로젝트의 호스팅 위치를 신경 쓰지 않아도 되는 것을 이상으로 내세운다. Forgejo든 GitHub든 메일링 리스트든 매끄러운 경험을 주는 것이 목표라는 것이다. 이어서 백엔드 넷과 각각의 한계를 적는데, 완성도는 고르지 않다.

백엔드 README가 적은 상태 동작과 제약 덧붙은 서술
Forgejo 아직 존재하지 않는다. 「곧 생길 것」 Flirt가 Codeberg에 있어, 생기면 기여자가 이 백엔드를 Flirt 개발에 직접 써 볼 수 있다 공지: 만드는 일이 할 일 목록의 다음 차례
Native Git 자체(불안정) 형식 리뷰 정보를 Git 객체 저장소에 두고 사용자 정의 ref로 원격에 push·fetch한다. 주 용도는 외부 서비스 없이 하는 시험 모두가 push 권한을 가진 팀에서 쓸 수는 있으나, 형식 불안정과 보관 문제 때문에 지금은 나쁜 생각이라고 README가 적는다
GitHub 아마 가장 많이 쓰일 백엔드 독점 소프트웨어이므로 기여가 GitHub 지원 여부에 막혀서는 안 된다 2026-08 글: 구현했으나 제한적이고 여러 면에서 버그가 있다
메일링 리스트 지금은 개념 증명 메일을 보내지 않고, 시험용 로컬 public-inbox 서버로 가져오기만 한다 git send-email이 Jujutsu의 change-id 커밋 헤더를 보존하지 않아 주 기능의 신뢰도가 낮다

2026년 8월 글에 따르면 Native Git 백엔드에 쓰던 사용자 정의 ref 방식을 다른 백엔드에도 그대로 쓴다. 무언가 할 때마다 GitHub API를 부르거나 메일 스레드를 내려받는 것을 피하려는 것이고, 이 ref들은 로컬에만 머물다가 사용자가 백엔드와 동기화를 요청할 때 API 호출이나 메일로 바뀐다. GitHub 백엔드에 대해 같은 글이 적은 제약은 다음과 같다.

  • 글쓴이가 꼽는 가장 큰 문제는 PR에 대한 과거 강제 푸시 정보를 GitHub에서 얻지 못한다는 것이다. 그래서 모든 제출본 사이의 interdiff를 보여 줄 수는 없다.
  • 표준 용례인 「마지막으로 리뷰한 제출본과 현재 제출본의 interdiff」는 대체로 동작한다. 마지막으로 리뷰한 제출본을 로컬에 기억해 둘 수 있기 때문이다.
  • 작업 기기를 바꾸면 이것이 깨질 수 있다. 그 기기가 마지막으로 리뷰한 제출본을 본 적이 없으면 GitHub API에서 쉽게 가져오지 못한다.
  • API는 리뷰 댓글이 달린 커밋 해시를 알려 주므로 과거 제출본을 재구성하는 데 쓸 수 있다. 다만 중간 커밋에만 댓글이 있고 끝 커밋에는 없으면 제출본이 부분적으로만 재구성되는 경우가 생긴다.
  • GitHub 리뷰 화면은 diff 위에 댓글을 달게 하지만 Flirt는 코드베이스의 특정 상태에 댓글을 단다. 그래서 diff 왼쪽(삭제된 줄)에 달린 댓글을 둘 자리가 문제로 남아 있고, 글쓴이는 구현에 시간이 걸릴 것 같다고 적는다.

메일링 리스트 백엔드는 더 이른 단계다. 같은 글이 적은 내용은 다음과 같다.

  • 지원 범위는 public-inbox를 쓰는 프로젝트로 한정했다. 글쓴이는 리눅스 커널과 Git이 메일링 리스트 보관소로 public-inbox를 쓴다고 적는다.
  • git format-patch는 base 커밋 정보를 기본으로는 넣지 않고 --base 플래그를 줘야 넣는다. 이 정보가 없으면 패치를 어디에 적용할지 정할 수 없다는 것이 글쓴이의 지적이다.
  • git format-patch는 Jujutsu의 change-id 헤더를 보존하지 않는다. README 각주는 이를 고치려는 패치 시리즈가 Git 메일링 리스트에 올라와 비교적 긍정적으로 받아들여졌으나 다른 접근이 요청됐고, 글쓴이가 아는 한 아직 반영된 것은 없다고 적는다.
  • 같은 패치 시리즈의 여러 판을 묶는 근거로는 [PATCH v2 0/N] 같은 제목 줄의 버전 표기가 있지만, 표기가 빠지거나 문구가 바뀔 수 있다.
  • Flirt가 지금 지원하는 형식은 하나다. 새 판의 첫 메일을 이전 판 첫 메일의 답장으로 보내 모든 판이 하나의 스레드가 되게 하는 방식으로, 글쓴이는 Git 프로젝트가 이를 권한다고 적는다. 글쓴이가 인용한 리눅스 커널 문서는 여러 패치로 된 시리즈에서 In-Reply-To로 이전 판에 잇는 것을 피하는 편이 대체로 가장 낫다고 적는다.
  • 댓글을 읽는 쪽은 인용 기호가 겹친 평문을 구조로 풀어야 해서 예외가 많고, 글쓴이는 아주 단순한 경우에만 동작한다고 적는다.
  • 댓글을 보내는 쪽도 실제 메일은 보내지 않는다. 메일을 구성해 public-inbox-mda에 넘겨 로컬 시험용 public-inbox 인스턴스에 넣는다.

Flirt가 지원하는 스레드 구조를 글쓴이는 다음과 같이 그렸다.

[PATCH v1 0/3] add feature
                    ├── [PATCH v1 1/3] implement feature
                    ├── [PATCH v1 2/3] test feature
                    ├── [PATCH v1 3/3] document feature
                    │
                    └── [PATCH v2 0/3] add feature
                        ├── [PATCH v2 1/3] implement feature
                        ├── [PATCH v2 2/3] test feature
                        ├── [PATCH v2 3/3] document feature
                        │
                        └── [PATCH v3 0/3] add feature
                            ├── [PATCH v3 1/3] implement feature
                            ├── [PATCH v3 2/3] test feature
                            └── [PATCH v3 3/3] document feature

리뷰 정보를 Git 저장소에 두는 방식 — git-notes 대신 사용자 정의 ref

README는 Native Git 백엔드의 저장 형식을 「자체(불안정) 형식」이라고만 적는다. 그 내부는 2026년 2월 글에 설명돼 있고, 아래는 그 시점의 서술이다.

글쓴이는 같은 발상의 선행 프로젝트로 git-appraise를 살폈다. 리뷰 정보를 Git 저장소 안에 직접 저장하고, 여러 도구가 서로 호환되도록 표준을 정하는 데 주안점을 둔 프로젝트라고 글쓴이는 소개한다. 그 저장 형식을 Flirt에 쓸 수 있는지 따져 본 결론은 「아니다」였고, 이유는 git-appraise가 정보를 git-notes에 둔다는 데 있었다.

  • 커밋이 git-rebase 등으로 다시 쓰이면 해시가 바뀐다. 이전 해시에 붙어 있던 노트가 새 커밋으로 옮겨 가야 하지만 Git은 기본으로는 그렇게 하지 않는다. 설정으로 켤 수 있으나 선택 사항이다.
  • Jujutsu에서는 커밋을 고칠 때 git-notes를 옮기는 기능이 지원되지 않는다고 글쓴이는 적는다.
  • git-appraise에는 이를 처리하는 문서화되지 않은 rebase 명령이 있지만, 사용자가 모든 커밋 재작성에 그 명령을 쓴다고 기대할 수 없다는 것이 글쓴이의 판단이다.
  • 글쓴이는 리뷰 요청을 만든 뒤 커밋을 amend하고 reflog 만료와 가비지 컬렉션을 곧바로 일으키면 요청이 사라지는 짧은 스크립트를 제시한다. 평소와 다른 점은 가비지 컬렉션을 즉시 일으킨 것뿐이라고 덧붙인다.
  • 조회도 불편하다고 적는다. 커밋·change-id·브랜치에서 리뷰 정보의 위치를 바로 알 수 없어, 노트 목록을 훑으며 JSON을 파싱해야 한다는 것이다.

대안은 사용자 정의 ref다. ref는 객체를 가리키는 포인터이고, 브랜치는 .git/refs/heads/, 태그는 .git/refs/tags/, 노트는 .git/refs/notes/ 아래에 있다. 글쓴이는 다른 디렉터리, 예컨대 .git/refs/flirt/ 아래에 새 ref를 만들 수 있다고 설명한다. 이런 ref는 Git에 특별한 의미가 없지만 똑같이 동작한다. 가리키는 객체가 가비지 컬렉션으로 지워지지 않게 하고, 브랜치처럼 push·fetch할 수 있다.

처음에는 데이터 구조를 JSON으로 직렬화해 blob으로 저장하고 ref가 그 blob을 가리키게 했다. 문제는 중간 제출본이었다. Flirt는 풀 리퀘스트나 패치 시리즈에 해당하는 리뷰 단위를 Spirit(「Set of Patches Intended for Review and Intense Testing」)이라 부르고, 작성자가 올리는 각 판을 제출본(submission)이라 부른다. 리뷰어가 ref를 받아 오면 리뷰 정보는 내려오지만, 브랜치를 받아 와도 최신 제출본의 커밋만 내려오고 그 사이 제출본의 커밋은 내려오지 않는다. Spirit에 해시는 적혀 있어도 커밋이 로컬에 없으니 볼 수 없다.

글쓴이가 택한 방법은 Git의 기존 동작에 기대는 것이다. 커밋을 받아 오면 아직 없는 조상 커밋도 함께 내려온다. 그래서 사용자 정의 ref가 blob이 아니라 커밋을 가리키게 하고, 그 커밋에 각 제출본의 head 커밋을 부모로 넣었다. 커밋의 트리에는 spirit.json이라는 blob 하나가 있고 실제 리뷰 정보는 여기에 담긴다. 리뷰어가 Spirit을 fetch하면 이전 제출본의 커밋이 함께 내려와, Spirit이 어떻게 달라져 왔는지와 과거 댓글이 달린 시점의 코드 상태를 볼 수 있다.

에디터에서 하는 리뷰 — HEAD와 작업 트리, 댓글 스레드 구상

README가 꼽는 둘째 특징은 로컬 우선이다. 네트워크는 리뷰할 것을 내려받고 리뷰를 올릴 때만 필요하고, 리뷰 과정 자체는 오프라인에서 이뤄지며 기존 도구, 그중에서도 텍스트 에디터와 맞물린다고 적는다. 2025년 11월 글은 에디터가 이미 리뷰에 쓸 기능을 갖고 있다는 데서 출발한다. Git HEAD와 작업 트리의 diff 보기, LSP나 언어 플러그인으로 하는 코드 탐색, 언어의 주석 문법으로 메모 달기, 코드와 테스트 실행이다. 그런데 댓글을 남기려면 에디터를 떠나 브라우저를 열고 같은 위치를 다시 찾아 텍스트 상자를 열어야 한다는 것이 글쓴이가 짚는 틈이다.

Flirt의 방식은 interdiff를 로컬 저장소에 「물질화(materialize)」하는 것이다. Git HEAD가 리뷰어가 이전에 리뷰한 Spirit 상태를 가리키게 하고 작업 트리에는 현재 상태를 써 넣는다. Git 연동이 있는 에디터라면 무엇이 새로 바뀌었는지를 그대로 보여 준다. 2025년 11월 글은 이렇게 하면 에디터가 jj interdiff와 같은 것을 보여 준다고 적는다. 댓글은 언어의 주석 문법으로 쓰고, Flirt가 그것을 모아 공백과 주석 표시를 떼어 낸 뒤 백엔드로 보내는 구상이다.

이 방식에서 풀리지 않았던 것이 댓글 스레드다. 에디터에서 인라인으로 댓글을 읽고 쓸 때, 새 댓글이 새 스레드인지 기존 스레드의 답글인지를 Flirt가 알 방법이 필요하다. 2026년 2월 글에서 글쓴이는 기존 스레드를 표식으로 감싸고 답글 자리를 따로 두는 안을 「현재 계획」으로 제시했다. 예시에서 스레드는 // +<3+<3+<3+<3+<3+<3+<3+<3 Flirt thread-ID: ABCXYZ 줄로 시작해 작성자와 시각이 붙은 댓글들, 답글을 적는 자리, 「모두에게 해결로 표시」와 「자신에게만 해결로 표시」 체크 칸을 거쳐 thread-end 줄로 끝난다. 글쓴이는 이 표기가 다소 장황하고 읽기 어렵다고 스스로 적는다. 2026년 8월 글은 댓글 스레드가 「기본적으로 동작하게」 됐다고 적는다.

같은 글들에 적힌 설계 결정과 구상은 다음과 같다. 모두 해당 글 시점의 계획이다.

  • 스레드 재배치. GitHub는 강제 푸시로 스레드가 시작된 커밋이 바뀌면 스레드를 outdated로 표시한다. 스레드가 저장소에 물질화돼 있으면 작성자가 함수를 옮기면서 스레드도 함께 옮길 수 있고, Flirt가 ID로 새 위치를 읽어 Spirit에 기록한다는 구상이다. 글쓴이는 이것을 Native Git 백엔드만 지원할 수 있다고 적는다.
  • 해결 표시 둘. GitHub에서는 스레드 해결 상태가 모두에게 공유된다. 글쓴이는 공유용과 로컬용 토글을 따로 두려 하고, 해결 표시가 없는 메일링 리스트에서는 로컬 토글만 남는다고 적는다.
  • 커밋 단위 리뷰. 여러 패치로 된 Spirit의 합쳐진 diff에 댓글을 다는 것은 지원하지 않을 계획이다. 줄 범위 댓글은 지원하고, Gerrit에 있는 줄 안의 문자 범위 댓글은 지원하지 않을 계획이다.
  • 커밋 메시지 댓글. 지원하려 하며, 이를 지원하지 않는 GitHub로 보낼 때는 커밋 메시지를 인용한 독립 댓글로 표현해야 할 것 같다고 적는다.
  • 판정. 백엔드마다 다르다. GitHub는 Comment·Approve·Request changes, Gerrit은 Code-review 라벨의 -2에서 +2까지의 점수, 메일링 리스트는 Reviewed-by·Tested-by·Acked-by 같은 관례다. 그래서 백엔드별 사용자 정의 판정이 필요하다고 적는다.
  • 화면. 2025년 11월 시점의 Flirt는 기본 기능을 보이기 위한 CLI였다. 글쓴이는 주 화면이 아마 TUI가 되고 중심 로직은 라이브러리로 노출될 것이라고 적었다.

저장소와 커뮤니티 규칙 — Rust, AGPL-3.0-or-later, LLM 정책

저장소의 Cargo.toml에는 패키지 이름 flirt, 버전 0.1.0, edition 2024, 라이선스 AGPL-3.0-or-later가 적혀 있다. 2025년 11월에 글쓴이는 라이선스를 정하지 못했고 GPL과 Unlicense 양쪽에 각각 끌린다고 적었는데, LICENSE 파일은 2026년 9월 30일 커밋으로 추가됐다. 조회 시점의 저장소 화면은 커밋 111개, 브랜치 2개, 태그 0개이고 언어 비율은 Rust 96.9%, Shell 3.1%다. 의존성 목록에는 clap, clap_complete, inquire, jiff, mail-parser, unidiff, serde, serde_json, anyhow, cmd_lib, rand, which가 있다.

README에는 설치·빌드 절이 없다. 「Contributing & Development」 절은 문서가 아직 많지 않다고 적고, Zulip에 들러 관심사를 이야기하며 시작하기를 권한다. 흔한 개발 작업은 tasks/ 디렉터리의 스크립트로 정의돼 있고, 직접 실행하거나 simply-run 또는 mise로 실행할 수 있다고 적는다. README가 내세우는 지침 원칙은 셋이다.

  • 산출물보다 커뮤니티. 좋은 코드 리뷰 도구를 만드는 일은 그것이 무엇인지에 대한 공통 이해를 사람들이 쌓아 가는 과정의 부산물이라고 적는다.
  • 파워 유저 우선. 접근성에 맞춘 리뷰 도구는 많고 Flirt는 그중 하나가 아니라고 적는다. 접근성 개선은 파워 유저를 희생하지 않는 한에서 좋다는 입장이다.
  • 자유·오픈소스 소프트웨어. 기여와 커뮤니티 참여에 독점 소프트웨어가 필요해서는 안 된다. 각주는 그 귀결로 Discord가 공식 소통 수단이 될 수 없고, 독점 백엔드(GitHub)나 운영체제(Windows, Mac) 지원에 기여가 막힐 수 없다고 적는다. 다른 기여자가 최선 노력 수준으로 지원할 수는 있다.

LLM 정책은 README가 스스로 「꽤 엄격한(fairly strict)」이라고 부른다.

  • Flirt 커뮤니티 공간에 LLM이 생성한 텍스트를 올리는 것은 손봤든 아니든 금지된다. 코드, 커밋 메시지, 이슈, PR 설명, 이슈·PR의 댓글, Zulip 메시지가 모두 LLM 없이 쓰여야 한다.
  • 개인적 맥락의 사용은 정책 범위 밖이다. 코드베이스 탐색, 조사, 디버깅, 아이디어 검토가 예로 적혀 있고, 각주는 정책이 개인적 사용을 용인하지도 비난하지도 않는다고 적는다.
  • 좁은 예외가 있다. 생성을 의도하지 않았고(사고였고), 그 텍스트가 특정 개선을 하는 가장 좋거나 유일한 방법이며, 가능한 한 자기 머리로 재현해 「정화(sanitize)」했을 때다.
  • 정화의 예로 README는 모르는 라이브러리 함수를 LLM이 내놓은 경우를 든다. 그 라이브러리를 쓰겠다는 생각에 어떻게 이르렀을지 따져 보고, 함수 이름을 모르는 것처럼 문서에서 기능을 찾고, 문서를 읽어 스스로 결론에 이르는 과정을 밟으라는 것이다.
  • 집행은 선의를 전제한다. 위반이 의심되면 실수로 보고 정책을 상기시키는 데 그치고, 고의 위반에 대해서는 원칙적으로 영구 차단이 합당한 귀결이라고 적는다.

지금의 성숙도 — 문서로 확인되는 것과 아직 없는 것

공지와 README, 개발 기록을 합쳐 현재 상태를 나누면 다음과 같다.

항목 문서로 확인되는 것 아직 없거나 제약인 것
공개 2026-10-05, Codeberg flirt/flirt, AGPL-3.0-or-later 태그 0개, Cargo.toml의 버전 표기는 0.1.0
주 기능 이전에 리뷰한 커밋과 그 현재 판의 interdiff를 찾아 표시 신뢰도가 커밋 메타데이터에 의존하고, 작성자가 Jujutsu를 쓸 때 가장 높다
백엔드 Native Git, GitHub, 메일링 리스트 Forgejo는 없다. 메일링 리스트는 개념 증명이고 Native Git은 형식이 불안정하다
문서 README(소개, 원칙, LLM 정책, 백엔드 지원) 설치·사용 안내가 없고, 문서가 아직 많지 않다고 README가 적는다
사용 단계 기여할 의도가 있는 사람의 시험 일반 사용에 준비되지 않았고, 준비 시점은 제시되지 않았다
소통 Zulip LLM으로 쓴 메시지는 허용되지 않는다

종합하면 Flirt는 「강제 푸시된 변경을 다시 리뷰할 때 무엇을 보여 줄 것인가」라는 물음에 change-id와 로컬 저장으로 답하려는 도구이고, 그 답이 닿는 범위는 지금으로서는 조건부다. 작성자가 Jujutsu를 쓰는지, 백엔드가 무엇인지, 리뷰어가 이전 제출본을 같은 기기에서 봤는지에 따라 결과가 달라진다고 문서가 스스로 적는다.

판단 기준은 글쓴이의 문장 그대로다. 아직 일반 사용에 준비되지 않았고, 버그와 빠진 기능이 많으며, 기여자가 될 생각이 아니라면 조금 더 기다리라는 것이다. README도 기여할 의도가 있을 때만 시험하라고 적는다. 준비가 되면 글쓴이가 아마 다른 글로 알릴 것이라고 했으므로, 업무 흐름에 넣을지의 판단은 그 글 이후로 미루는 것이 글쓴이의 권고에 맞다. 지금의 공개가 겨냥하는 독자는 패치 시리즈 워크플로의 리뷰 문제에 공감해 설계 논의나 백엔드 구현에 참여하려는 사람이고, README는 관심 있는 새 백엔드의 지원을 더하는 일이 기여를 시작하기에 좋은 방법이라고 적는다.

인접한 주제는 다른 글에 있다. 큰 변경을 여러 층의 PR로 나누는 GitHub의 스택 PR은 GitHub 스택 PR 공개 프리뷰에서, 터미널에서 diff를 검토하는 도구 Hunk는 AI 에이전트 코드 리뷰 도구 Hunk에서 다뤘다. 스택 PR은 변경을 나누는 방식이고, Flirt는 다시 쓰인 커밋을 리뷰어가 이전에 본 상태와 비교하는 방식이다.

확인하지 못한 것

  • 공개된 코드의 구현 범위. 스레드 재배치, 두 개의 해결 토글, 백엔드별 판정, 주석 스레드 표기는 이전 글의 계획과 구상이다. 공개된 소스가 이를 어디까지 담고 있는지는 README에 적혀 있지 않고, 소스 코드는 근거 자료에 포함하지 않았다.
  • 설치·빌드·명령줄 사용법. README에 해당 절이 없다. GeekNews가 옮긴 Lobste.rs 토론 요약에는 글쓴이가 설치 안내를 일부러 뺐다고 답했다는 대목이 있으나, 원 댓글은 확인하지 못했다.
  • 일반 사용 준비 시점. 공지는 준비되면 「아마」 글을 쓰겠다고만 적고 일정은 제시하지 않는다.
  • Forgejo 백엔드의 착수 여부와 일정. 「할 일 목록의 다음 차례」「곧 생길 것」이라는 표현 외의 근거는 없다.
  • 대체 휴리스틱의 실제 내용. README는 change-id 헤더가 없으면 대체 휴리스틱이 쓰인다고만 적는다. 무엇을 기준으로 짝짓는지, 짝이 어긋났을 때 화면에 어떻게 드러나는지는 문서에 없다.
  • Git 쪽 변경의 현재 상태. change-id 헤더 보존을 다루는 패치 시리즈의 경과는 README 각주의 서술에 의존했고, 해당 메일링 리스트 스레드는 근거 자료에 포함하지 않았다.
  • 제3자의 사용 사례와 검증. 글쓴이 외의 사용 보고나 다른 리뷰 도구와의 비교 측정은 찾지 못했다.
  • 석사 논문. 논문 본문의 공개 여부와 위치는 블로그와 README에 적혀 있지 않다.
  • 저장소 수치의 시점. 커밋·브랜치·태그 수와 언어 비율은 2026년 10월 7일 조회 시점의 화면 값이며 이후 달라질 수 있다.
