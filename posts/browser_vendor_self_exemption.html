브라우저 설정에 「사이트가 저장한 데이터를 삭제」라는 항목이 있다. 이용자가 그 항목을 켤 때 머릿속에 그리는 그림과, 그 항목을 구현한 코드가 실제로 훑는 범위는 같지 않다. 둘 사이의 간격은 대체로 한 낱말에서 벌어진다. 사이트다.

어디까지가 사이트이고 어디부터가 브라우저 기능인가. 이 선이 어디에 그어져 있느냐에 따라 같은 조작이 지우는 것이 달라진다. 그리고 그 선을 긋는 쪽과, 그 선의 위치로 이득을 보는 쪽이 같은 조직일 수 있다는 것이 이 주제의 구조적인 부분이다.

계기 - 무엇에 대한 예외라는 말인가

2026년 9월 초에 옮겨진 글은 개인 블로그 글이다. 맥용 소프트웨어를 만드는 제프 존슨이 자기 사이트에 적었고, 제목은 크롬이 이용자의 사이트 데이터 설정에서 구글을 다시 예외로 둔다는 취지다. 특정 벤더를 겨냥한 논조의 글이며, 그 점을 먼저 적어 두는 편이 이후 서술을 읽기에 낫다.

기사와 요약을 거치며 가장 자주 빠지는 정보는 무엇에 대한 예외인가다. 여기서 문제 삼는 설정은 하나로 특정된다. chrome://settings/content/siteData 의 세 선택지 가운데 두 번째, 창을 모두 닫으면 사이트가 기기에 저장한 데이터를 삭제하는 항목이다. 쿠키 차단 일반도 아니고 광고 추적 일반도 아니다.

글쓴이가 적은 절차는 이렇다. 그 설정을 켜고, 크롬에 로그인하지 않은 상태에서 구글 검색을 한 번 하고, 창을 전부 닫는다. 그 뒤 기기 내 사이트 데이터 목록을 보면 www.google.com 항목이 약 1,216 KB 남아 있었다고 적는다. 브라우저를 다시 시작해도 남았고, 남은 종류는 쿠키와 로컬 스토리지와 세션 스토리지라고 적었다. 판본은 152.0.7977.83 이다. 그는 자기 화면 캡처가 증명이 아니라 설명을 위한 것이라고 덧붙였고, 의도를 단정하지 않는다는 뜻도 함께 적었다.

같은 글쓴이는 2020년에도 비슷한 취지의 글을 적었고, 그때 지적한 건은 이후 고쳐졌다고 이번 글에 서술한다. 제목의 「다시」는 그 이력을 가리키는 말이다. 여기까지가 관찰이다. 관찰과 규칙은 무게가 다르므로, 표로 갈라 놓고 시작한다.

설정이 약속하는 문장부터 고정한다

크롬에서 이 설정의 이름은 「기기 내 사이트 데이터」이고, 경로는 설정 → 개인 정보 보호 및 보안 → 사이트 설정 → 추가 콘텐츠 설정 → 기기 내 사이트 데이터다. 화면 상단의 설명 문장은 방문한 사이트가 예상대로 동작하도록 정보를 저장할 수 있다고 적으면서, 로그인 유지와 장바구니를 예로 든다. 그 아래 기본 동작 세 가지가 라디오 버튼으로 놓인다.

여기서 간격이 시작된다. 고객센터 문서는 세 선택지의 이름과 대략의 효과까지 적는다. 그러나 맞춤 설정 목록이 기본값과 충돌할 때 어느 쪽이 이기는지, 그 목록에 무엇이 어떤 경로로 올라갈 수 있는지는 그 문서에 없다. 이용자가 화면에서 보는 것은 「기본 동작」이라는 낱말이지만, 실제 판정은 기본값 하나로 끝나지 않는다.

사이트 데이터는 한 덩어리가 아니다

「사이트 데이터」라는 낱말 하나 아래에 성격이 다른 저장소가 여러 개 있다. 브라우저가 창을 닫을 때 도는 루틴도 이 구분을 그대로 따라간다.

  • 쿠키 — 서버가 헤더로 심고 요청마다 다시 실려 가는 값. 오리진이 아니라 도메인 단위로 범위가 잡힌다
  • 로컬 스토리지·세션 스토리지 — 스크립트가 쓰는 키·값 저장소. 세션 스토리지는 탭 수명에 묶인다
  • IndexedDB — 구조화된 데이터베이스. 용량이 크고 오프라인 앱이 주로 쓴다
  • 캐시 스토리지와 서비스 워커 — 오프라인 응답을 담아 두는 저장소와 그것을 다루는 등록 정보
  • Origin Private File System·스토리지 버킷 — 오리진 전용 파일 계층과 저장 단위를 나누는 최신 API
  • 브라우저 캐시 — 사이트가 제어하는 저장소가 아니라 브라우저가 성능을 위해 두는 사본. 별도 항목이다

크로미엄이 창을 모두 닫을 때 실행하는 코드는 두 갈래로 나뉜다. 쿠키가 아닌 저장소는 저장 영역 단위로 한 번에 지우고, 쿠키는 따로 처리한다. 소스의 주석은 그 이유를 쿠키가 오리진 단위가 아니기 때문이라고 적어 두었다. 그리고 「이 오리진이 세션 한정인가」를 판정하는 함수는 쿠키 콘텐츠 설정을 그대로 읽는다.

// chrome/browser/sessions/session_data_deleter.cc
bool OriginMatcher(const blink::StorageKey& storage_key,
                   storage::SpecialStoragePolicy* policy) {
  return policy->IsStorageSessionOnly(storage_key.origin().GetURL()) &&
         !policy->IsStorageProtected(storage_key.origin().GetURL());
}

// chrome/browser/extensions/extension_special_storage_policy.cc
bool ExtensionSpecialStoragePolicy::IsStorageSessionOnly(const GURL& origin) {
  return cookie_settings_->IsCookieSessionOnly(origin);
}

화면에서 고른 「기기 내 사이트 데이터」 상태는 내부적으로 쿠키 콘텐츠 설정으로 저장되고, 그 값 하나가 쿠키가 아닌 저장소의 운명까지 정한다. 이용자에게 두 개로 보이는 개념이 코드에서는 한 개다. 이 사실 하나만 알아도, 쿠키 예외가 로컬 스토리지 잔존으로 이어지는 상황이 이상한 일이 아니게 된다.

어디까지가 사이트이고 어디부터가 브라우저 기능인가

이 설정이 다루는 대상은 「사이트가 저장한 것」이다. 브라우저 자신이 저장하는 것은 다른 칸에 있고, 그 칸은 이 설정의 사정거리 바깥이다. 프로필 디렉터리는 두 종류를 한 폴더에 담는다. chrome://version 의 Profile Path 가 그 위치이며, 사이트 저장소도 여기 있지만 방문 기록·북마크·설정·확장 프로그램 데이터도 같은 곳에 있다.

브라우저 기능이 쓰는 저장소는 웹 페이지의 저장소 API 를 거치지 않는다. 그래서 사이트 데이터 삭제 루틴은 그것을 보지 않는다. 예를 들어 동기화 상태, 안전 브라우징이 내려받아 두는 목록, 주소창 제안이 참고하는 기록, 번역 기능의 설정은 사이트가 만든 저장소가 아니다. 삭제 화면의 다른 항목이나 계정 쪽 설정이 그것을 담당한다.

경계는 한 번이 아니라 두 번 그어진다. 첫째, 데이터가 사이트 저장소에 있는가 브라우저 내부 저장소에 있는가. 둘째, 삭제 루틴이 어디까지 훑도록 짜여 있는가. 두 번째 선에도 명시적인 예외가 있다. 크로미엄 소스는 확장 프로그램 스킴의 오리진과, 이용자가 설치한 호스티드 앱을 「보호된 저장소」로 분류해 종료 시 삭제 대상에서 뺀다. 기본 설치된 앱은 이 보호를 받지 않는다고 같은 함수가 못 박고 있다.

이 예외는 특정 회사와 무관한 브라우저 차원의 설계다. 확장 프로그램이 창을 닫을 때마다 설정을 잃으면 쓸 수 없기 때문이다. 예외의 존재 자체가 이상한 것이 아니라, 어떤 예외가 어디에 적혀 있는가가 판단 대상이라는 뜻이다.

문서에 적혀 있는 예외 - 계정과 활동 기록

크롬의 인터넷 사용 기록 삭제 문서에는 이용자가 자주 놓치는 문장이 세 개 있다. 세 문장 모두 「지웠다」의 범위를 좁히는 문장이며, 숨겨져 있지 않고 문서에 적혀 있다.

  • 크롬에 로그인한 상태에서 쿠키를 삭제해도 구글 계정에서 로그아웃되지 않는다
  • 구글 계정에 저장된 카드와 주소는 이 조작으로 삭제되지 않는다
  • 구글 서비스에서의 검색과 활동은 계정 쪽에 저장되며, 계정 화면에서 따로 지운다

기업용 관리자 정책 쪽에도 같은 취지의 문장이 있다. 창을 모두 닫을 때 지울 항목을 관리자가 지정하는 정책의 설명에, 쿠키를 지우더라도 이용자는 구글 계정에 로그인된 상태로 남는다는 서술이 들어 있다. 같은 설명에 또 하나의 조건이 붙어 있다. 브라우저나 운영체제가 비정상 종료하면 그 회차의 삭제는 일어나지 않는다는 것이다. 창을 닫아서 끝난 것이 아니기 때문이라는 이유까지 적혀 있다.

여기가 이 글의 심장이다. 「사이트 데이터를 지운다」는 조작은 계정 상태를 건드리지 않도록 설계되어 있고, 그 설계가 문서에 있다. 이용자가 기대하는 삭제의 범위와 문서가 규정하는 삭제의 범위가 갈라지는 지점이 바로 이 선이다. 그리고 이 선을 어디에 두느냐는 기술적 판단인 동시에 사업적 판단이다. 로그인이 유지되는 편이 이용자에게 편하고, 동시에 그 계정을 운영하는 쪽에도 유리하다.

코드가 정한 우선순위 - 허용 한 줄이 삭제보다 세다

쿠키 쪽 판정은 크로미엄에 함수 하나로 들어 있고, 순서가 명확하다. 이 순서가 「예외가 들어설 자리」의 정확한 위치다.

  1. 해당 오리진의 쿠키 설정이 허용이면 그 자리에서 삭제 대상이 아니다
  2. 그다음 예외 목록을 훑어, 도메인이 일치하는 항목 가운데 하나라도 허용이면 삭제 대상이 아니다. 세션 한정 항목은 표시만 해 둔다
  3. 마지막으로 기본값이 세션 한정이거나 세션 한정 규칙에 걸렸으면 삭제한다
// components/content_settings/core/common/cookie_settings_base.cc
ContentSetting setting = GetContentSetting(
    origin, GURL(), ContentSettingsType::COOKIES, &setting_info);
if (setting == CONTENT_SETTING_ALLOW) {
  return false;              // 삭제하지 않는다
}
for (const auto& entry : cookie_settings) {
  if (net::cookie_util::IsDomainMatch(domain, host)) {
    if (entry.GetContentSetting() == CONTENT_SETTING_ALLOW) {
      return false;          // 허용 항목 한 줄이 이긴다
    } else if (entry.GetContentSetting() == CONTENT_SETTING_SESSION_ONLY) {
      matches_session_only_rule = true;
    }
  }
}
return setting == CONTENT_SETTING_SESSION_ONLY || matches_session_only_rule;

기본값을 「창을 닫으면 삭제」로 두어도, 도메인이 겹치는 허용 항목이 한 줄 있으면 그 줄이 이긴다. 도메인 일치는 상위 도메인 규칙이 하위까지 덮는 방식이라, 어떤 등록 도메인에 걸린 한 줄은 그 도메인과 하위 도메인의 쿠키 전체에 닿는다. 그리고 앞 절에서 본 대로, 같은 설정 값이 쿠키가 아닌 저장소의 삭제 여부도 결정한다.

같은 취지의 주의가 관리자 정책 문서에도 있다. 허용·차단·세션 한정 세 정책 사이에 겹치는 URL 패턴이 있으면 어느 쪽이 우선하는지 규정하지 않는다고 적혀 있다. 규정되지 않은 우선순위는 판본에 따라 달라질 수 있는 영역이다.

그러니 「예외가 있다」는 관찰만으로는 원인을 특정하지 못한다. 예외가 들어설 자리는 설계에 이미 있고, 화면에도 「맞춤 설정」이라는 이름으로 드러나 있다. 남는 질문은 그 자리에 무엇이 어떤 경로로 들어갔는가이며, 이것은 문서가 아니라 실행 중인 프로필을 보아야 갈리는 문제다.

창을 모두 닫는다는 조건에 붙어 있는 단서들

조건절도 그대로 읽을 필요가 있다. 이 설정의 발동 조건은 「창을 모두 닫는다」이지 「브라우저를 종료한다」가 아니다.

창이 하나라도 남아 있으면 루틴 자체가 돌지 않는다. 백그라운드 앱이나 트레이 상주 설정으로 프로세스가 살아 있는 경우도 이용자 눈에는 다 닫힌 것처럼 보인다. 비정상 종료도 마찬가지다. 정책 문서는 이때 그 회차의 삭제가 건너뛰어진다고 명시한다.

시작 시 이전 세션을 복원하도록 설정한 경우에는 갈래가 하나 더 생긴다. 종료 루틴은 만료 시각이 없는 세션 쿠키의 일괄 삭제 단계를 이때 건너뛴다. 세션 한정 규칙에 걸린 것은 그대로 지운다. 두 삭제는 서로 다른 갈래이고, 이 구분은 설정 화면 어디에도 표시되지 않는다. 같은 루틴에서 세션 한정 오리진의 미디어 장치 식별용 값과 트러스트 토큰의 세션 한정 데이터도 함께 정리된다.

정리하면, 삭제가 일어나지 않는 상태는 이상 동작이 아니라 조건 불성립인 경우가 많다. 잔존을 관찰했을 때 첫 번째로 갈라야 할 것이 이 조건이다.

저장소가 나뉜 뒤의 사이트 - 파티셔닝

「사이트」라는 낱말은 최근 몇 년 사이에 한 번 더 쪼개졌다. 크롬은 115 판본부터 저장소 파티셔닝을 전체 이용자에게 적용한다. 저장소의 키가 오리진 하나가 아니라 오리진과 최상위 사이트의 조합이 되고, 중간에 교차 사이트 프레임이 끼어 있었는지를 나타내는 비트가 하나 더 붙는다.

  • 저장소 API — 쿼터, 로컬·세션 스토리지, IndexedDB, 캐시 스토리지, Origin Private File System, 스토리지 버킷, Clear-Site-Data 헤더의 사정거리, Blob URL 저장소(137 판본부터)
  • 통신 API — BroadcastChannel, SharedWorker, Web Locks
  • 서비스 워커 — 서드파티 문맥에서 등록된 것은 분리된다

그래서 어떤 도메인의 로컬 스토리지는 하나가 아니다. 어느 최상위 사이트 아래에서 만들어졌느냐에 따라 여러 칸으로 나뉜다. 목록 화면에서 도메인 하나로 접혀 보이는 항목이 실제로는 여러 칸의 합일 수 있다는 뜻이다. 잔존 용량 하나만 보고 「어느 사이트가 남겼는가」를 단정하기 어려운 이유가 여기에 있다.

쿠키 쪽 범위 규칙은 이것과 다른 축이다. 어떤 요청에서 쿠키가 실리고 실리지 않는지는 SameSite 값이 요청 유형별로 만드는 판정표가 결정한다. 저장 없이 장치를 알아보는 계열의 신호는 또 다른 축이며, 지울 것이 없는 추적에서 다룬 대로 삭제 설정이 닿지 않는 영역이다.

다른 브라우저에도 같은 자리가 있다

종료 시 삭제를 제공하는 브라우저는 예외 장치를 함께 제공한다. 예외 장치가 없으면 로그인 유지 같은 기능이 성립하지 않기 때문이다. 벤더별로 이름과 문서화 수준이 다를 뿐 자리는 같다.

엣지 쪽 항목은 성격을 특히 구분해 둘 필요가 있다. 마이크로소프트 지원 담당자가 공개 질의응답에서, 자사 도메인의 기본 쿠키가 지워지지 않는 것은 의도된 동작이라고 답한 기록이 있다. 이것은 제품 문서에 실린 규정이 아니라 지원 채널의 답변이며, 두 가지는 인용할 때 무게가 다르다. 다만 같은 구조가 다른 벤더에도 있다는 사실을 보여 주기에는 충분한 자료다.

파이어폭스 쪽 예외는 최근에 명문화된 축에 든다. 종료 시 정리 정책에 예외 오리진 목록이 붙은 것은 154 판본부터이며, 그 전까지는 항목 단위의 켜고 끄기만 있었다. 예외가 필요하다는 인식은 늦게 오더라도 결국 온다.

선을 긋는 쪽과 그 선의 수혜자가 겹칠 때

브라우저를 만드는 조직이 그 브라우저 위에서 검색·광고·계정 사업을 함께 할 때, 「사이트」와 「브라우저 기능」의 경계선을 정하는 쪽과 그 선의 위치로 이득을 보는 쪽이 겹친다. 이것은 어느 회사의 성품에 관한 이야기가 아니라 배치에 관한 이야기다. 같은 배치는 여러 곳에 있다. 운영체제 벤더가 기본 브라우저를 만들 때, 검색 사업자가 브라우저를 만들 때, 콘텐츠 사업자가 그 유통 경로까지 운영할 때 같은 겹침이 생긴다.

배치가 만들어 내는 것은 결론이 아니라 입증 책임의 방향이다. 경계가 자사 서비스에 유리한 쪽으로 놓였을 때, 그것이 기능상 필요 때문인지 사업상 편의 때문인지는 바깥에서 구분하기 어렵다. 로그인을 유지해 주는 예외는 이용자 편의이기도 하고 계정 사업의 자산이기도 하다. 두 설명이 같은 동작을 똑같이 잘 설명한다.

그래서 이런 배치에서는 문서화가 신뢰의 대체물이 된다. 예외가 있다면 그 예외를 적어 두는 것, 목록을 이용자가 볼 수 있는 화면에 두는 것, 우선순위가 정해져 있다면 그 순서를 적어 두는 것이다. 같은 제품 안에서도 이 밀도는 고르지 않다. 계정 로그인 유지 예외는 고객센터와 정책 문서 두 곳에 적혀 있다. 반면 기기 내 사이트 데이터 문서에는 허용 목록이 기본값을 이긴다는 사실이 없다. 그 규칙은 소스와 정책 정의에서만 읽힌다.

이 차이는 실무에 그대로 옮겨 붙는다. 설정 하나가 여러 저장소를 동시에 지배하고, 예외 목록이 기본값을 이기고, 우선순위가 규정되지 않은 구간이 있다면, 그것은 문서에 적혀야 하는 사항이다. 광고 차단과 확장 API 를 둘러싼 힘의 배분도 같은 구조의 다른 얼굴이다.

이용자가 스스로 보는 절차

설정 화면은 상태를 보여 주고, 저장소 화면은 결과를 보여 준다. 두 화면이 어긋날 때 답은 언제나 뒤쪽에 있다.

chrome://settings/content/siteData      기본 동작 3택 + 맞춤 설정 목록
chrome://settings/content/all           기기 내 사이트 데이터 목록(사이트별 용량)
chrome://settings/clearBrowserData      인터넷 사용 기록 삭제(항목별)
chrome://version                        Profile Path — 이 프로필의 저장 위치
chrome://extensions                     설치된 확장 프로그램 목록
  1. 설정 화면에서 기본 동작이 세 선택지 가운데 무엇으로 놓여 있는지 본다
  2. 같은 화면 아래 맞춤 설정 목록 두 개를 본다. 여기 올라온 사이트는 기본값을 따르지 않는다
  3. 기기 내 사이트 데이터 목록에서 남아 있는 사이트와 용량을 본다. 도메인 하나가 여러 파티션의 합일 수 있다
  4. 창을 전부 닫고 다시 연 뒤 같은 목록을 본다. 창이 하나라도 살아 있었다면 조건이 성립하지 않은 것이다
  5. 개발자 도구의 Application 패널에서 유형별로 본다. Cookies·Local storage·Session storage·IndexedDB·Cache storage 가 각각 다른 항목이고, 저장소 개요에 사용량 분포가 함께 나온다

프로필과 게스트 창은 범위를 나누는 다른 방법이다. 프로필은 사용자 데이터 디렉터리 아래의 하위 디렉터리이고, 프로필을 나누면 저장소도 갈린다. 게스트 창은 크롬 고객센터가 적은 대로 방문 기록·쿠키·사이트 데이터를 종료 시 기기에서 지운다. 다만 같은 문서가 한계도 함께 적는다. 방문한 사이트, 로그인한 사이트, 네트워크를 운영하는 조직, 통신 사업자, 검색 엔진 쪽에서는 활동이 그대로 보인다. 기기에 남기지 않는 것과 관측되지 않는 것은 다른 말이다.

이런 보도를 다음부터 읽는 법

브라우저 동작에 관한 관찰 보도는 앞으로도 계속 나온다. 여섯 가지만 갈라 두면 대부분 제자리를 찾는다.

  • 어느 설정에 대한 예외인가 — 설정 이름과 화면 경로까지 특정되어 있는가. 쿠키 차단 일반과 종료 시 삭제는 다른 기능이다
  • 관찰인가 규칙인가 — 한 사람의 재현은 관찰이고, 공식 문서와 소스는 규칙이다. 관찰은 규칙을 뒤집지 못하고, 규칙은 관찰을 설명해야 한다
  • 대조군이 있는가 — 다른 사이트에서 같은 절차를 밟은 결과가 함께 제시되어 있는가
  • 예외가 들어설 자리가 원래 있는가 — 있다면 예외를 목격했다는 사실만으로는 원인이 특정되지 않는다
  • 판본이 적혀 있는가 — 브라우저 동작은 판본마다 바뀌고, 규정되지 않은 우선순위 구간은 특히 그렇다
  • 의도에 관한 문장인가 동작에 관한 문장인가 — 의도는 문서로 판별되지 않는다. 동작만 남기고 읽으면 남는 것이 훨씬 단단하다

이 목록은 브라우저에만 쓰이지 않는다. 클라이언트에서 본 것으로 서버 쪽 규칙을 추론하는 상황은 어디에나 있고, 그 추론이 어디서 끊기는지는 신뢰 경계를 다룬 글에서 다룬 것과 같은 문제다.

확인하지 못한 것

아래 항목은 1차 자료에서 문면을 확인하지 못해 본문에 사실로 넣지 않았다. 사유를 함께 적는다.

  • 보고된 동작 자체 — 특정 도메인의 데이터가 종료 뒤에도 남는다는 관찰은 재현 결과이며, 공식 문서에서 대조되지 않는다. 그래서 본문에서는 관찰로만 귀속했다. 글에 적힌 152.0.7977.83 은 실제로 배포된 안정판 빌드 번호이고, 이 글을 쓰는 시점의 안정판은 153.0.8010.27 이다. 판본이 다르면 결과도 달라질 수 있다
  • 크롬이 특정 도메인에 대한 허용 항목을 기본으로 싣는지 — 설정 문자열 리소스에도 고객센터 문서에도 그런 규정이 없다. 실행 중인 프로필의 예외 목록을 보지 않고는 갈리지 않는 항목이다
  • 관찰된 잔존의 원인 — 허용 항목, 확장 프로그램, 세션 복원 설정, 비정상 종료, 백그라운드 프로세스가 모두 같은 증상을 낸다. 원문은 이 가운데 몇 가지를 배제했다고 적지만, 남은 경로 전부가 배제됐다는 서술은 없다
  • 2020년 건이 언제 어떤 변경으로 고쳐졌는지 — 이번 글은 고쳐졌다고 적으나 해당 변경의 식별자나 판본이 없다. 크로미엄 이슈 번호도 제시되어 있지 않다
  • 대조군의 범위 — 원문은 문제의 도메인이 유일하다고 적으면서, 자기 화면 캡처가 증명이 아니라 설명이라고 덧붙인다. 몇 개의 사이트를 어떤 조건으로 비교했는지는 글에 없다
  • 엣지의 동작을 규정한 제품 문서 — 자사 도메인 쿠키가 남는 것이 의도된 동작이라는 서술은 지원 채널의 답변에서만 확인된다. 같은 취지의 제품 문서를 찾지 못했다
  • 크롬 개인정보 백서의 기능별 저장 위치 서술 — 해당 문서는 스크립트로 본문을 그리는 구조라 정적 요청으로는 본문이 오지 않는다. 그래서 브라우저 내부 기능의 저장 위치는 고객센터와 소스에서 확인되는 범위로만 적었다
