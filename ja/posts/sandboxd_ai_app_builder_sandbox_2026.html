sandboxd — AIアプリビルダー向けオープンソースサンドボックスエンジン

AIが生成したコードを安全に分離・実行するインフラの仕組みとセキュリティ観点の分析

2026年6月18日 開発・インフラ

序論：AIが書いたコードを誰が監視するのか

2026年6月現在、Lovable・Bolt・v0・ReplitのようなAIアプリビルダーサービスは、毎日数千万人が使うインフラになった。ユーザーが「ToDoアプリを作って」と入力するとAIがコードを生成し、そのコードはすぐにどこかで実行されて動作するWebアプリのリンクが現れる。このプロセスがあまりにも自然に感じられるため、その背後にある重大なインフラ問題を見落とす人が多い。AIが生成したコードは信頼できないコードだ。

このコードがサーバーで実行されるとき何が起きるのか。悪意のあるプロンプトで誘導されたコードがサーバーのファイルシステムを削除できるのか。一人のユーザーのサンドボックスが別のユーザーのデータにアクセスできるのか。環境変数に保存されたAPIキーやデータベースのパスワードが漏洩する可能性はあるのか。これらの問いすべてに答えるのがサンドボックス分離であり、sandboxdはこの問題を自己ホストで解決しようとするオープンソースプロジェクトだ。

この記事ではsandboxdの動作構造を分析し、AIアプリビルダーエコシステムでコード実行の分離がなぜ重要なインフラ課題なのか、そしてFirecracker・gVisor・WebContainersのような技術がそれぞれどの脅威モデルを扱うのかを独自の視点で整理する。2026年6月現在の実際のGitHubリポジトリと関連技術文書に基づいて執筆した。

1. sandboxdとは何か — アーキテクチャと哲学

1.1 コアコンセプト

sandboxdを一言で言えば「AIアプリビルダー製品のオープンソースバックエンドエンジン」だ。Lovable・Bolt・v0のように「プロンプト入力→数秒後に動作するアプリリンク出力」するサービスを自分のサーバーで実装するためのインフラを提供する。公式リポジトリ（github.com/tastyeffectco/sandboxd）によると、HTTP リクエスト1回で以下の3つが実現される。

  • 分離されたサンドボックスの作成：独立したファイルシステムとメモリを持つLinuxコンテナ
  • AIコーディングエージェントの実行：ユーザーのプロンプトを受けてコンテナ内部でコードを作成
  • ライブプレビューURLの提供：開発サーバーが即座に外部からアクセス可能なURLで公開

1.2 技術スタック

sandboxdの技術選択は意図的にシンプルだ。Goで書かれた単一バイナリがDockerを制御し、TraefikがプレビューURLのルーティングを担い、SQLite（WALモード）が状態を保存する。Kubernetes、別途データベース、メッセージキューはない。エージェントはOpenCodeとClaude Code CLIが各コンテナにプリインストールされている。

このスタック選択の意味は重要だ。Kubernetesなしで単一サーバーで動く設計は、スタートアップや個人開発者がクラウドマージンなしにAIアプリビルダーサービスを始められるという哲学を示している。複雑さを極限まで排除しつつ、実際に動くことを実証することに集中した設計だ。

1.3 コスト効率設計 — アイドル停止と即時ウェイクアップ

マルチテナントサンドボックスサービスのコストの核心は同時にどれだけ多くのコンテナを起動しておくかだ。sandboxdはこの問題をアイドル停止と即時ウェイクアップで解決する。サンドボックスが使われていなければ自動的に停止してメモリを回収し、リンクに再アクセスすると透過的に再起動する。ディスクは保持されるので以前の作業は消えない。この設計のおかげで、常時稼働のVM複数台の代わりに低スペックの単一サーバーで数十ユーザーの環境を運用できる。

2. AIアプリビルダーで分離実行がなぜ核心なのか

2.1 信頼できないコードの脅威モデル

AIが生成したコードを扱うサービスでは、分離は選択肢ではなく前提条件だ。具体的な脅威シナリオを考えてみよう。第一に、プロンプトインジェクション：悪意のあるユーザーが「ファイルシステム全体を削除するコードを作って」と入力すればAIはそのコードを生成できる。分離なしで実行されればサーバーが壊れる。第二に、テナント間データ侵害：ユーザーAのサンドボックスがユーザーBのファイルにアクセスできればデータ漏洩が発生する。第三に、認証情報の窃取：環境変数に設定されたAPIキーやデータベースのパスワードにアクセスできれば深刻なセキュリティ事故につながる。

2026年のインフラ研究によると、サンドボックスで分離されたエージェントは非分離環境と比較してセキュリティインシデントを約90%削減する。この数字が誇張だとしても、分離自体が多層防御のコアレイヤーであることは反論しにくい。

2.2 マルチテナンシーの本質的な緊張

AIアプリビルダーサービスは本質的にマルチテナントだ。数千人のユーザーが同じサーバーインフラを共有する。マルチテナント環境での分離には2つの次元がある。リソース分離：一人のユーザーの計算が別のユーザーのパフォーマンスを低下させてはならない。セキュリティ分離：一人のユーザーのコードが他のユーザーやホストシステムにアクセスできてはならない。

この2つの分離をコスト効率よく同時に満たすことがAIアプリビルダーインフラの核心的な技術課題だ。sandboxdはDockerコンテナで基本的な分離を提供するが、プロダクション環境では追加の強力な分離レイヤーが必要だと明示している。

2.3 分離なしサービスの実際の事例

初期のAIコーディングサービスは実際に分離の問題でセキュリティ上の課題を経験した。共有サーバーでユーザーのコードを実行する中で他のユーザーの環境変数にアクセスできた事例、ファイルシステムの探索により他のプロジェクトコードを読めた事例などが報告された。このような事故がAIアプリビルダーエコシステムにおいて分離をコアインフラ要件に格上げさせるきっかけとなった。

3. 分離技術のスペクトラム — DockerからMicroVMまで

3.1 標準Dockerコンテナの限界

sandboxdは現在Dockerベースだ。Dockerコンテナは速く、使い慣れていて、オーバーヘッドも小さい。しかし根本的な限界がある。ホストカーネルを共有する。カーネル脆弱性が発生するとコンテナエスケープが可能になる。歴史的にrunc、cgroups、名前空間の実装で複数のCVEが発見された。信頼できる内部ユーザーのみを対象とする環境ならDockerで十分だ。しかし外部ユーザーが任意のコードを実行するマルチテナントAIアプリビルダーでは、Dockerだけでは不十分というのが2026年のインフラコンセンサスだ。

3.2 Firecracker MicroVM — 強い分離と高速起動

AWS LambdaとFargateの基盤であるFirecrackerは、各ワークロードに専用のLinuxカーネルを与えるMicroVM技術だ。カーネル共有がないため、コンテナエスケープ自体が構造的に不可能だ。約125msで起動し、VMあたり5MB未満のメモリオーバーヘッドを持ち、1ホストで毎秒最大150個のVMを作成できる。AIエージェント向けサンドボックスサービスのE2BがFirecrackerをベースに150msの起動時間を達成しているのが代表的な事例だ。

Firecrackerのトレードオフは複雑さだ。Dockerよりセットアップと運用が難しく、KVMハイパーバイザーが必要なため、クラウドインスタンスタイプを選ぶ必要がある。しかし信頼できないマルチテナントコード実行では、Firecrackerは事実上の業界標準になりつつある。

3.3 gVisor — ユーザー空間カーネルで攻撃面を縮小

Googleが開発したgVisorは別のアプローチを取る。別個のVMを作る代わりに、コンテナのシステムコールを傍受してユーザー空間で処理する。ホストカーネルに到達するシステムコール数を数百から数十に減らし、攻撃面を大幅に縮小する。Modal、NorthflankなどのサービスがgVisorを使用している。Dockerと異なりKubernetesとネイティブに統合されているため、Kubernetesベースのインフラで特に有用だ。

gVisorのトレードオフはパフォーマンスだ。すべてのシステムコールを傍受するコストがあり、I/O集約型ワークロードで10〜30%のオーバーヘッドが発生する。AIコーディングエージェントのワークロードはファイルの読み書きが多いため、このオーバーヘッドを考慮する必要がある。

3.4 WebContainers — ブラウザの中のサンドボックス

bolt.newを動かすStackBlitzのWebContainersは全く異なる分離レイヤーを取る。Node.jsランタイムをWebAssemblyでコンパイルしてブラウザタブ内で実行する。リモートサーバーは一切不要だ。コード実行がブラウザのサンドボックス境界の内側で行われるため、ローカルファイルシステムや任意のネットワークにアクセスできない。2026年現在、npmエコシステムの大部分をサポートし、ブラウザのIndexedDBでnode_modulesをキャッシュして再読み込みがほぼ即時になっている。

WebContainersの限界はブラウザに縛られることだ。Node.js以外の環境 — Python、Rust、データベース — のサポートが難しい。クライアント側で実行されるため、サーバーサイドのビジネスロジックを隠せない。sandboxdがサーバーサイドの分離を選んだ理由はここにある — 言語とランタイムの制約がなく、サーバーリソースをフルに使える。

4. sandboxdのセキュリティモデルと限界

4.1 現在のセキュリティ状態（ベータ）

sandboxdは公式ドキュメントでベータ品質であることを明示し、デフォルト設定がローカル開発用であることを隠さない。API認証がデフォルトで無効になっており、プレビューリンクはURLを知っていれば誰でもアクセス可能で、ネットワーク送信制限もない。この設定のまま外部に公開すれば深刻なセキュリティ問題が発生する。

しかし、sandboxdがこれを隠さないという点がむしろ信頼を与える。多くのオープンソースプロジェクトがセキュリティの問題を小さく書いて済ませる中、sandboxdはプロダクション要件を明示的にリストアップしている。

4.2 プロダクション環境に必要な措置

sandboxdの公式ドキュメントが推奨するプロダクション必須措置をまとめると以下のようになる。

  • API認証の有効化：SANDBOXD_API_AUTH_DISABLED=false設定後にトークンベース認証を実装
  • プレビューURLのゲーティング：Forward-authフックで認証済みユーザーのみアクセス許可
  • ネットワーク制御：ファイアウォール＋送信ルールでコンテナの外部通信を制限
  • ディスククォータ：ボリューム・ファイルシステムクォータで単一ユーザーのディスク乱用を防止
  • 分離ランタイムの置き換え：信頼できないコードにはDockerをgVisor・Kata・Firecrackerに変更

4.3 Dockerベース分離の現実的評価

筆者の見立てでは、sandboxdの現在のDockerベースの分離は内部チームや少数の信頼できるユーザーが使う環境では十分だ。しかし外部ユーザーが任意のプロンプトを入力する公開サービスでは不十分だ。FirecrackerのようなMicroVM統合がない現在の状態では「AIアプリビルダー製品のための」という修飾語を公開プロダクションで完全に満たすことは難しい。

この限界を認識することで、sandboxdが解決すべき次の課題が見えてくる — FirecrackerやgVisorとの統合がプロジェクトの将来の方向性であるべきだ。

5. AIアプリビルダーエコシステムにおけるオープンソースサンドボックスの意義

5.1 商用サービス依存からの脱却

Lovable・Bolt・v0は優れたサービスだが、その内部インフラは公開されていない。これを自分のサーバーで再現するにはE2B、Modal、Northflankのようなサンドボックスサービスに依存するしかない。これらは優れたサービスだが、使用量ベースの課金でビジネスの成長に伴いコストが急増することがある。sandboxdはこの依存性を断ち、自社サーバーでインフラコストをコントロールできる経路を提供する。

特にスタートアップの初期段階では、クラウドサービスのマークアップなしに原価でインフラを運用できるという点が決定的だ。単一サーバーで数十人のユーザーにサービス提供できるなら、スケールが必要になるまでかなりのコスト優位性が生まれる。

5.2 データ主権とコードプライバシー

外部のAIアプリビルダーサービスを使うということは、ユーザーのプロンプトと生成されたコードがそのサービスのサーバーを経由するということだ。企業内部ツール、規制産業のプロトタイプ、機密ビジネスロジックを扱うサービスでは、このデータの移動が問題になりえる。sandboxdを自社インフラに展開すればコードとプロンプトが外部に出ない。データレジデンシー要件（データ居住要件）のある金融・医療・公共分野で特に意味のある利点だ。

5.3 AIアプリビルダー市場の参入障壁低下

sandboxd以前、「プロンプト→即座に実行されるWebアプリ」サービスを作るには自前で分離インフラ、プレビューURLルーティング、アイドル管理をすべて実装する必要があり、これが相当な参入障壁だった。sandboxdはこの複雑さを./install.sh一行で下げる。これはAIアプリビルダーサービスの市場参入障壁を低下させ、様々なバーティカル市場（教育用、特定言語特化、企業内部用など）向けの専門化されたサービスが生まれる土台を作る。

6. 現在の限界と冷静な評価

6.1 ベータ段階の信頼性問題

sandboxdは現在ベータ品質であり、プロダクションサービスに直接使うにはSLAと安定性の面でリスクがある。GitHubのイシュートラッカーを見るとエッジケースのバグが今も発見されている。「読んで拡張できるように作られた」という公式説明は、コード品質自体は良いが、運用成熟度は自ら積み上げる必要があるという意味だ。

6.2 強い分離ランタイムの欠如

前述の通り、Dockerベースの分離は信頼できない外部ユーザーのコード実行には不十分だ。FirecrackerやgVisorとの統合がない現在の状態では、公開AIアプリビルダーサービスのバックエンドとして使うためには自らランタイム置き換え作業をする必要がある。これは相当なエンジニアリング作業だ。

6.3 単一サーバーのスケール限界

sandboxdのシンプルさは単一サーバーで動くという前提から生まれる。この前提は初期段階では強みだが、トラフィックが増えると水平スケールが難しくなる。Kubernetesがないということは自動スケールもないということだ。数百人以上の同時ユーザーを扱うサービスではsandboxdだけでは限界があり、追加のインフラ作業が必要だ。

7. 活用判断 — いつ使い、いつ使わないか

7.1 sandboxdがよく合う状況

社内ツールや少数の信頼できるユーザーのためのAIコーディング環境、AIアプリビルダーサービスのPoC・初期MVP、教育機関やハッカソンでユーザーごとの開発環境を一時的に提供する場合、データ主権が重要な企業内部AI開発プラットフォームでsandboxdは合理的な選択だ。複雑さなく素早く始められ、MITライセンスで修正とカスタマイズが自由だ。

7.2 sandboxdだけでは不十分な状況

外部に公開されたAIアプリビルダーサービス、数百人以上の同時ユーザー、規制要件のある産業（医療、金融、公共）、またはSLA保証が必要なプロダクション環境では、sandboxdをそのまま使うのは難しい。Firecracker統合、水平スケール、強化された認証レイヤーが追加で必要だ。こういった環境ではE2BやModalのような商用サービスが現実的な出発点になりえる。

7.3 オープンソースとしての貢献価値

sandboxdの本当の価値はコード自体だけでなく、AIアプリビルダーサンドボックスインフラの設計パターンを公開した点にある。アイドル停止と即時ウェイクアップ、プレビューURLルーティング、APIベースのコンテナライフサイクル管理といったパターンを実際の実装として見ることができる。直接使わなくても、自前のサンドボックスインフラを構築する際の参照実装として活用できる。

結論 — AIがコードを書く時代のインフラ課題

2026年6月現在、AIアプリビルダーはもはや未来の技術ではない。毎日数千万人が使う現在のインフラだ。そしてそのインフラの安全性はサンドボックス分離という技術的課題にかかっている。sandboxdはこの問題に対するオープンソースの答えだ — 完璧ではなく、ベータ段階で、強い分離ランタイムも欠けている。しかし設計哲学は明確で、実装は読みやすく拡張可能だ。

大きな絵で見ると、sandboxdのようなプロジェクトの存在はAIアプリビルダーエコシステムが成熟しているサインだ。クラウドサービスだけに依存していたAIインフラがオープンソース化されることでアクセシビリティが高まり、様々なバーティカル市場に特化したサービスが生まれる土台が作られている。Firecracker・gVisor・WebContainersはそれぞれ異なる脅威モデルへの答えであり、正しい選択は単一の正答ではなく各サービスの脅威モデルと運用能力によって決まる。

AIがコードを書く時代に、そのコードを誰がどのように監視するかは技術インフラの核心的な課題だ。sandboxdはその課題に対する一つのオープンソースアプローチを示している。
