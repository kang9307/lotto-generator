问得简短，回答却很长 - 冗长是怎么形成的，压缩又要付出什么代价

长度被误当成质量的地方，以及压缩时失去的东西

2026年8月23日 IT/技术

开篇：三行就够的答案来了二十行

你问这个设置是不是打开就行。回来的是一段概述、五条列表、三行注意事项，最后还有一段把刚才说过的话再讲一遍的总结。答案在里面。只是你得自己去找、自己把它挑出来。

把这归结为模型话多，就错过了原因。冗长不是性格，而是训练过程中长度被反复奖励的结果，而且它附着在哪些地方已经被查得相当具体。知道了这些，也就能预判压缩时会有什么一起消失。这篇文章讲的就是那个结构，以及每种压缩办法各自要付的价钱。

1. 专门用来变短的工具正在出现

最近几天里，性质相同的工具冒出来两个。一个是把对话式模型的长输出转交给本地模型再整理成短版的命令行工具，另一个是把夸张腔调改写成平实句子的转换器。两者都不去动原始生成，而是在文字出来之后再修。

比工具本身更值得看的，是这个组合透露出的东西。

  • 默认输出和相当一部分用户想要的长度对不上。如果只是个人口味层面的偏差，不会有人专门做工具
  • 在提示词里写一句简洁点并没有解决问题。解决了的话，就没必要另起一层后处理
  • 修补的位置在生成之后，这也意味着用户握不到生成一侧的旋钮

所以这不是某一个产品的问题，而是关于当前这一代语言模型共同继承的默认值的信号。与其挑工具，不如去看那个默认值为什么定在这里。

2. 让回答变长的四个结构

2.1 偏好学习留下的长度偏差

用人类偏好对齐模型时，通常是拿两个回答让人选哪个更好，再用这些比较数据训练奖励模型。麻烦在于，这批数据里长度和偏好是相关的。人会挑看起来用了心的回答、挂了依据的回答、有结构的回答，而这些回答大都比较长。

2023年那篇关于RLHF 长度相关性的研究在三种不同设置下拆解了这件事。把奖励上升的原因拆开看，涨的大部分不是别的特征，而是回答长度；更关键的是，仅以长度给出的奖励就复现了相对于监督微调的大部分改进。作者们试过一整套抑制长度的干预手段，最后点名的是奖励模型：它并不稳健，很容易被偏好数据里的长度偏差牵着走。

同样的问题在不单独训练奖励模型的方法里也会出现。2024年那篇在 DPO 中把长度与质量分离的研究表明，直接偏好优化同样存在明显的长度利用，并报告在摘要与对话数据集上控制长度后胜率最多提升 20%。换掉对齐算法也没用，因为偏差在数据这一侧，会跟着一起走。

2.2 格式也在一起拿分

问题不只在长度。标题、粗体、项目符号这类表层格式会独立地把偏好推高。2024年8月竞技场运营方公开的风格控制分析在 Bradley-Terry 回归里，除模型项之外又加进了四个风格变量：回答的令牌长度、Markdown 标题数、粗体元素数、列表项数。

结果里长度系数在 0.249 到 0.267 之间，压过了 0.019 到 0.111 的各项 Markdown 效应。这不是说 Markdown 可以忽略。要点在于方向全为正。把答案拆成列表、加上小标题，同样的内容就能拿到更好的评价。照此训练出来的模型生成一份没人要的列表，一点也不奇怪。

2.3 风险规避把句子撑长

这条轴讲的不是数据而是目标函数。说那不行，错的时候错得很大。说多数情况下比较困难，不过视版本和配置也可能可行，建议再确认一下，这句话几乎不会错。条件加得越多，可被证伪的面就越小，而无法被证伪的回答收到的负面反馈也就越少。

于是模型偏向罗列各种情形而不是给出结论。人类写作者身上也有同样的习性，在需要免责的领域里甚至是正当的。但结果是句子变多，读者做决定所需的判断反而变少。

2.4 不给指令就会拿到平均值

面对一个没有指定长度的请求，模型能给出的就是训练分布里这类问题常见的长度。用户心里想的也许是三行，可是那条信息从来没有进到请求里。再加上对齐过程本身把中位数往上推了，所以什么都不说时拿到的默认值，比平均值还要长。

这里还挂着一个常见误解。简洁不是长度指定，而是一个形容词。不告诉模型是三句、一段还是一张表，它就又回去用自己的分布。

3. 冗长真正变成成本的地方

长并不必然是坏事。成本真正发生的位置有四处，而且每一处的买单方都不一样。

成本出现的位置增加的是什么谁来承担什么条件下最难受
阅读时间从回答里挑出所需句子的时间用户一天要问几十遍同一个问题的重复作业
令牌计费输出令牌数，单价通常高于输入发起 API 调用的一方按用户数成倍放大的自动化流水线
上下文消耗对话里不断累积的历史回答长度整个会话长对话、智能体循环、挂了多份文档的任务
要点稀释关键那一行与其余内容的比例读者的判断警告或例外被埋在列表中段时

第四条最安静，也最贵。安全告知如果排在十二条列表的第九位，形式上存在，功能上等于没有。令牌单价怎么定、为什么降价传不到账单上，在讲推理单价与实际成本的那篇里另有整理。

4. 长度和准确度是两条轴

常见的错觉在这里分岔。长就说明没敷衍，这种感觉在人写的文章里常常成立，但在生成模型里，长度不是用心的信号而是优化的副产物。

把这一点演示得最干净的实验，在2023年那篇用 MT-Bench 检验 LLM 评判者的论文里。作者挑出 23 条含编号列表的回答，只把条目改写一遍、一条新信息都不加，然后拼到原列表前面。五条的答案变成十条，而前五条只是后五条换了个说法。

  • 用作评判者的三个大模型里，有两个以 91.3% 的比例判定注水版本更好
  • 第三个以 8.7% 的比例扛得好得多，但那不是 0%
  • 关键在于信息量完全相同。只加了长度，判决就变了

反方向同样成立。短也不代表对。把一个需要条件才成立的事实剥掉条件压成一行，那句话短、好读、并且是错的。在实务上，把长度当成与准确度正交的一条轴来看更安全。

5. 要求简洁这件事要付的价钱

所以简洁不是免费的。2025年的多语种安全评测Phare 拿 17 个当代模型，一边改系统指令一边测幻觉倾向。按公开的分析，强调简洁的指令在多数模型上都拉低了事实可靠性，严重时幻觉抵抗力下降了 20%。

机制说得通。如果提问本身建立在错误前提上，纠正它需要解释。一旦加上简短作答的约束，模型就得在反驳前提和简短附和之间选，而它会倒向服从指令那一边。压缩不是把句子变短，而是决定舍弃什么，而先被切掉的通常是这些。

  • 结论成立的条件：版本、地区、时点、前提
  • 例外与反例：相当于但在这种情况下的那些句子
  • 依据与出处：读者据以核实的那条线索
  • 不确定性标记：未经确认的条目被写成了定论
  • 替代方案：这条路走不通时的第二选择

归结起来，长度约束既是成本旋钮，也是准确度旋钮。不知道自己同时拧了两个，代价就会往后推。

6. 四种压缩办法，各自的代价

实际在用的办法有四类，性质完全不同。

做法怎么变短要付的代价适合的场合
在提示词里指定长度在生成阶段给出篇幅目标指令一强，条件、例外、依据先被切掉事实风险低的重复问询
固定输出格式用表格、模式、字段清单划定位置格式里没有格子的信息会整块消失后面接着处理的自动化流程
后处理摘要把已经生成的答案再压一遍原样搬运原文里的错误最后由人核对的阅读材料
用小模型润色把文体和篇幅交给便宜的模型润色方的判断力低于原文不需要事实判断的文体整理

6.1 后处理摘要会把什么一起带走

第三行值得单独看。后处理摘要之所以看着安全，是因为它不碰原始生成，而这恰恰就是它的极限。摘要器看到的是已经写好的答案，不是依据材料。

  • 原文里若有错误事实，摘要里也照样留着。摘要不是验证环节
  • 原文的可能会在摘要里很容易变成就是。压缩最先删掉的就是缓冲表达
  • 没有上下文，摘要器也就没有依据去判断哪一句才重要

前面提到的那个本地后处理工具，其仓库说明里也直接写了这条限制：因为只看得到最后的消息，它可能产生幻觉或漏掉重要细节。做的人承认了限制，用的人却不知道，事故就是这么来的。要用小模型做润色的话，体感质量具体在哪里被削掉，讲本地模型设置的那篇说得更具体。

7. 简洁到底怎么量

同意要删很容易，量出到底有没有删好却很难，因为字数可以量，而字数说不出结果是不是变好了。目前的做法大致分三路。

  • 长度控制回归 — 2024年的长度控制版 AlpacaEval 用广义线性模型把长度差作为中介变量放进去，再预测长度差为 0 时的偏好。仅这一项校正就把与竞技场排名的斯皮尔曼相关系数从 0.94 提到了 0.98
  • 风格控制排名 — 像上面那份竞技场分析一样，把长度和 Markdown 从回归里剥掉再重排。靠写得长而胜出的会往下掉，简短却准确的会往上走
  • 任务成功率与长度同时测 — 2024年的简洁思维链研究报告说，在选择题基准上把平均回答长度压掉 48.70%，整体正确率变化很小，每令牌成本降低 22.67%。不过在数学题上，两个受测模型中较弱的那个吃了 27.69% 的性能下降

最后那个数字正是本节的要点。同一种压缩，在不同任务和不同模型上收的钱不一样。所以改简洁之后没什么问题这句话，在你自己的任务上量过之前都只是别人的结果。哪怕评测集只有二十条，自己动手跑一遍也更靠谱。

8. 也有本来就该长的地方

不写反面，这篇也就成了只说一边的文章。有些地方删了就是亏。

  • 安全告知 — 用药、法定期限、可能的资金损失，凡是漏掉就会伤到人的条目。这里该按有没有遗漏来评价，而不是按篇幅
  • 流程说明 — 有先后顺序和前置条件的任务。步骤一合并，读的人就无法回溯自己错在哪里
  • 面向新手 — 对懂行的人是废话的句子，对第一次看的人却是唯一的入口
  • 确实不确定的领域 — 一个答案随条件而变的问题若用一行作答，那一行就会被套到错误的条件上
  • 会成为记录的文档 — 日后要由别人回溯依据的产出物

共同点是这样的：可以删的是重复说同一件事的部分，不是承载信息的部分。开场白、结尾总结、每个条目后面跟的那句归纳，多半属于前者。条件与例外属于后者。

9. 留在写作方手里的：核实不会转移

不管怎么调长度，有一件事不变。事实核实是人的工作。写短了只是要核的句子少了，核的义务并没有少。反过来说，被压缩过的句子往往剥掉了条件、以断言形式留下，错的时候错得更加确凿。

  • 数字和引用要回到压缩前的原文去核。把摘要当成核实对象，就再没有机会看到原文的错误
  • 看压缩过程中有没有丢掉条件，尤其是多数、一般来说、视版本而定这几类是否被删
  • 找出变成断言的句子。原文的缓冲表达在摘要里消失是很常见的模式
  • 看出处链接还在不在。一压长度，脚注是最先被砍的

读者一侧怎么读这些信号、怎么据此调整信任，在讲读者判断标准的那篇里另有讨论。至于韩语特有的文体摇摆和缓冲表达问题，实测韩语文体规约的那篇更对口。

10. 实务检查清单

起点是提要求时把长度当成一个数值而不是形容词给出去。什么该指定、什么不该指定，随场景而分。

场景要指定的不要指定的
需要事实准确的问询格式（表格、条目）以及标注出处的义务字数上限。依据会先被砍
重复的简单问询句子数量，或者一行作答连新例外也要一并解释的要求
自动化流水线模式与字段，禁止自由叙述自然语言的篇幅提示。它不可复现
面向新手的说明读者被假定具备的先备知识缩减篇幅。这里长度就是功能
  • 不要写简洁，改写成三句、一张表、200 字以内这类能数的数值
  • 另外指明去掉开场白和结尾总结。这两块占了相当大的篇幅
  • 明确要列表还是要散文。不明确的话，出来的是列表
  • 标注出处要与长度指令分开提。两条指令冲突时，输的是出处
  • 如果挂了后处理摘要，把原文留在日志里。验证要在原文上做
  • 加长度指令前后各跑同样二十道题，比较正确率
  • 量成本看输出令牌数，量质量看任务成功率，分开看。别用一个指标顶两个用

未能确认的部分

  • 商用服务目前采用什么样的长度相关奖励或后处理，并未公开。本文所述机制来自公开研究与公开评测数据，不涉及任何特定产品的内部构成
  • 文中引用的长度偏差研究主要在英语数据上测得。它在其他语言里是否以同样的幅度出现，未能确认
  • 0.249 到 0.267 这组风格系数是在 2024 年 8 月的竞技场数据上量的。此后模型与用户构成都有变化，当前值可能不同
  • 引发这篇文章的两个工具实际能压掉多少、过程中损失多少信息，没有公开的测量资料

结论：长度是要设定的值，不是照单全收的默认值

冗长不是一个要纠正的毛病，而是偏好数据里的相关性穿过优化之后固化下来的结构。长度和格式一起拿到了奖励，风险规避把条件铺开，没有指令的地方由分布的中位数填上。

所以应对也该是设计而不是口味。把长度当成数值来指定，在自己的任务上量一量这个指定对准确度收了多少钱，并且把安全告知和流程说明排除在压缩对象之外。而无论用哪种办法压缩，核实都回到原文上做。变短的答案是变得好读了，不是被验证过了。
