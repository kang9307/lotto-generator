cf とは何か、どこまで確認できるか

cf は Cloudflare が公開ベータとして出したコマンドラインツールだ。README はこれを「次世代のソフトウェア開発のために作られた CLI」と紹介し、四つの特徴を挙げる。エージェントが独自の検索と誘導（search and steering）でコマンドを見つけられること、JSON が既定のインターフェースであること、TypeScript の設定ファイル cloudflare.config.ts が安全性と正確さを与えること、Vite 統合でローカル開発を支えることだ。

この記事の軸は新ツールの紹介ではなく設計の方向にある。コマンドラインツールは長く、人間が読んで打つことを前提に作られてきた。cf は、その前提をエージェントに移したときに何が変わるかを、コマンド発見・出力形式・設定形式の三か所で示す。三か所とも原文に根拠があるので、対応関係を一つずつたどる。

インストールコマンドは README にあるとおり次の一行だ。README は、オープンベータを今すぐグローバルにインストールしてどこからでも実行するよう案内している。

npm i -g cf

コマンドが API スキーマから直接生成されるという点は、範囲の問題につながる。手でコマンドを一つずつ追加する方式ではコマンドの数が作り手の作業量に縛られるが、スキーマから作り出す方式では API が増えればコマンドも増える。Wrangler が約280の作業にとどまったことと、数千の作業を扱う cf との違いは、この生成方式から来るというのがブログの説明だ。ただし、生成されたコマンドが人の手で磨かれたコマンドほど読みやすいかは、原文が扱っていない。

人間向けCLIがエージェントの前でずれる箇所

コマンドラインツールが人間向けに設計されているとは、具体的に三つの前提を指す。利用者はコマンド名をおおよそ覚えているかドキュメントで探せること、出力を目で流し読みして必要な行を選べること、設定は例をコピーして少し直して使うこと、の三つだ。エージェントはそのどれにもそのままでは合わない。以下は解説であり、cf がそのずれをどこで埋めるかが次の節以降の内容になる。

  • コマンド発見。 人間はヘルプとドキュメント検索でコマンドを探す。数千のコマンドのヘルプ全文をエージェントのコンテキストに載せる方式は費用が大きいので、必要なコマンドだけを選ぶ入口が別に要る。
  • 出力の消費。 人間には整列や色が助けになるが、エージェントには解析できる構造と短さが大切だ。同じ情報でも表現によってコンテキストの使用量が変わる。
  • 設定の検証。 人間は設定を誤るとデプロイ段階のエラーメッセージを読んで直す。エージェントには、編集時点で誤りを知らせる型検査があると試行錯誤が減る。
  • 範囲。 コマンドのない作業は、エージェントが別の経路で迂回しなければならない。コマンドが届く作業の範囲が、そのまま CLI だけでエージェントにできることの範囲になる。

この四つは cf の発表文が特徴として掲げたものと重なる。ただ、重なるのは設計意図の方向が同じということであって、実際のエージェント作業での効果が測定されたという意味ではない。発表文と README は効果の測定値を示していない。

この表は三通りに読める。根拠が原文のマスはそのまま引用してよい事実であり、原文と解説が併記されたマスは前半だけが事実で、解説の後半は自分の環境で検証すべき仮説だ。たとえば、型エラーが試行錯誤を減らすという記述はもっともらしい推論だが、測定された結果ではない。導入を判断する場面でこの区別を保てば、発表文の意図と実際の効果が混ざらない。

検索できるコマンド - cf cli search

数千の作業がコマンドになると、一覧そのものが探索の障害になる。ブログはこれを検索コマンドで解く。原文の文は次のとおりだ。「このコマンドはエージェントが必要な作業を自然言語で尋ねることを可能にし、小さな検索インデックスが API の説明とパラメータを基に適切なコマンドの一覧を提供する。」

  • 入力は自然言語だ。 コマンド名を知っている必要はなく、したいことを書けばよい。この方式は、コマンド名が API スキーマから生成される構造と噛み合う。
  • インデックスの材料は API の説明とパラメータだ。 手で書いた別のドキュメントではなく、API スキーマにすでにある説明が検索対象という意味だ。コマンドがスキーマから出るので、検索対象も同じ源から出る。
  • 案内は最初のヘルプ実行時に自動だ。 原文は、エージェントが --help を初めて実行したときにこのコマンドを自動で知らせると書く。README が言う誘導（steering）はこの地点を指すと読める。

解説を足すと、要点は、検索結果がエージェントの次の行動候補を絞ることだ。ヘルプ全体を読ませる代わりに、質問に該当する少数のコマンドだけがコンテキストに入る。ただし、検索が誤ったコマンドを上位に出した場合、エージェントがそのコマンドをそのまま実行する危険は残る。この点の精度の数値や失敗事例は原文にない。

構造化出力 - JSON が既定である理由

README の文は短い。JSON が既定のインターフェースで、人間向けには見やすく出力し、エージェント向けには圧縮して出力する。ブログはここに一言足した。圧縮の目的は、コンテキストを最大限節約することだ。

  • 同じデータ、二つの表現。 データ形式は一つの JSON で、インデントと空白を残すか削るかが対象によって分かれる。形式が一つなので、人間とエージェントが別々の出力経路を持たない。
  • コンテキストは予算だ。 エージェントが読む出力はすべてコンテキストウィンドウを消費する。空白の数文字は小さく見えても、数百回の呼び出しでは積み重なる。原文はこれを「コンテキストの最大限の節約」という表現でまとめている。
  • 解析しやすさ。 解説である。行単位のテキスト表を正規表現で切って読むより、JSON のフィールドを読むほうが読み違いが少ない。フィールド名が安定しているかは原文が扱っていない。

この節の限界も明らかだ。原文は、どのコマンドがどのフィールドを出すか、圧縮された出力が人間向けよりどれだけ小さいかという数値を示していない。コンテキストがどれだけ節約できるかは、自分の作業で測る値である。

コンテキストの節約が実際にどれだけかは、自分で測れる。同じ参照コマンドの圧縮出力と見やすく整形された出力をそれぞれファイルに保存し、文字数を比べればよい。この比較は読み取り専用で、負荷もかからない。ただ、文字数とトークン数は同じではないので、使っているモデルのトークン計算ツールで数え直すほうが正確だ。原文はこの比較を示していないので、ここで得られる値はそれぞれの作業でのみ有効である。

設定の型付け - cloudflare.config.ts

cf は設定を TOML ではなく TypeScript のファイル cloudflare.config.ts で書く。README はこれが安全性と正確さを与えると言い、ブログは型検査と自動補完、そしてコードで環境を作る方式を説明する。ブログの例は、cf/config から bindings と defineConfig を読み込み、worker 名と環境の値を関数で返す形で、関数は引数として mode を受け取る。

  • 型検査と自動補完。 設定値の名前と形式が編集時点で検査される。人間には自動補完になり、エージェントには誤ったキーをデプロイ前に知らせるフィードバックになる（後者は解説）。
  • コードで作る環境。 静的なファイルの代わりに、関数が mode に応じて設定を返す。環境が増えるほど、コピーしたファイルを複数維持するより関数一つから派生させるほうが有利だというのが発表文の論理だ。
  • 40%圧縮の事例。 ブログは、Cloudflare 内部の一部の Wrangler 設定ファイルが、開発者ごとのカスタム環境が多い5,000行超の規模から、各開発者の設定を作り出すファクトリーファイルへと40%圧縮されたと書く。事例は内部ファイルの一部についての記述だ。

この40%は、外部のプロジェクトにそのまま当てはまる数値ではない。何を基準にした40%か、たとえば行数かファイルサイズかは、発表文の文だけでは確定しない。設定の型付けがエージェントの作業成功率をどれだけ上げるかも、原文に数値がない。

Wrangler との関係と cf migrate

既存の Workers プロジェクトを持つ側にとって最も気になるのは移行手順だ。ブログが示す関係は三つある。移行コマンドは cf migrate で、変換の結果はプロジェクトのビルド方式によって分かれ、ベータが終わった後も Wrangler は一定期間メンテナンスされる。

プロジェクトの状態cf の動作（原文）この記事の解説
すでに Vite でビルドしている Workercloudflare.config.ts に変換される変換後の設定が TypeScript になるので、差分をレビュー対象にする
Wrangler の esbuild に依存する Workercf がビルドを引き続き Wrangler に委ねる当面は Wrangler も並行して残す必要がある構成だ
静的サイト設定ファイルなしで始め、cf deploy でデプロイする新規の静的プロジェクトは入口の障壁が低い
ベータ終了後Wrangler を18か月間メンテナンスする18か月が移行猶予期間の上限だ
  • 移行は一つのコマンドで始まる。 原文が案内する移行の入口は cf migrate だ。何が変換されるかはプロジェクトのビルド方式が決める。
  • Wrangler はすぐには消えない。 ベータ終了後に18か月のメンテナンスが約束されている。この文は、移行する時間を与える趣旨で書かれている。
  • 完全移行ではない混在構成がある。 esbuild に依存する Worker は cf を使いながらビルドは Wrangler に残る。移行後も二つのツールが共存する。

ベータ期間の移行は、戻す方法を先に決めておくほうが安全だ。解説だが、設定ファイルをバージョン管理に置き、変換結果を別ブランチでレビューすれば、元に戻すのは簡単になる。この記事は、削除やデプロイのような状態を変えるコマンドを例に挙げない。

18か月という期間は、移行計画を立てる基準線になる。ベータが終わる時点が決まっていないので、18か月の起点も未定だ。そのため、予定表に入れられるのは日付ではなく順序になる。まず Vite でビルドしているプロジェクトから変換結果をレビューし、esbuild に依存するプロジェクトは Wrangler を併置する構成のまま残し、ベータ終了の告知が出た時点で残りのプロジェクトの移行時期を決める。

エージェントの作業フローを描く - 参照から変更のレビューまで

前の節では機能を一つずつ見てきた。この節では、それらの機能を一つの作業フローにつなげてみる。以下は原文にある機能だけで描いた解説用のシナリオであり、実際の cf の動作を実演した記録ではない。削除やデプロイのように状態を変える段階は、あえて外した。

  1. 最初のヘルプ実行。 エージェントが cf の --help を初めて実行すると、cf cli search という入口が自動で案内される。人間がプロンプトにコマンド一覧を貼り付ける必要がないことが、この設計の最初の利点だ。
  2. 自然言語で候補を尋ねる。 エージェントがしたいことを文で尋ねると、API の説明とパラメータに基づくコマンド候補の一覧が返る。候補は複数あることもあり、この一覧が次の判断の材料になる。
  3. 参照系のコマンドだけを選ぶ。 人間が決めておいたルールで、候補のうち状態を変えないコマンドだけを実行させる。原文には、コマンドが参照か変更かを区別してくれる機能への言及がないので、この区別は使う側のルールだ。
  4. 圧縮された JSON を読む。 実行結果はエージェント向けに圧縮された JSON で返る。同じ結果を人間が見たいときは、同じコマンドが見やすく整形された形で出力する。
  5. 設定の変更は型検査のあとに。 設定が必要な変更は cloudflare.config.ts で行い、エディターの型検査と自動補完が示すエラーを先に解消する。最後に、適用する前に人間が変更点をレビューする段階を置く。

このフローで cf が担うのはコマンドの発見と出力、設定の検査であり、何を許可するかの判断は担わない。判断は、人間が決めたルールとレビューの段階に残る。発表文は、その判断の層に関する機能には触れていない。

フローをこのように分けると、ボトルネックがどこにできるかも見える。コマンドが数千あるツールでのボトルネックは、コマンドの不足ではなく、どのコマンドをどの条件で許可するかを決めることにある。エージェントが使えるコマンドの範囲を広げることと、その範囲の中で許可リストを絞ることは、一緒に進める必要がある。広げるのはツールが行い、絞るのは運用者が行う。

導入前に点検すること、ベータの限界

設計意図がもっともらしいことと、本番に載せてよいことは別の問題だ。cf は発表時点で公開ベータであり、以下は導入前に自分で答えてみる点検項目だ。項目ごとに、原文が言うことと言わないことを分けた。

  • パッケージ名の確認。 インストールコマンドは npm i -g cf だ。名前が二文字なので他のパッケージと取り違える恐れがあり、README を出したリポジトリが cloudflare/cf か確認してからインストールする。
  • ベータの範囲。 公開ベータなので、コマンドや出力形式が変わりうる。どのコマンドが安定段階かの区別は原文にないため、エージェントのスクリプトが出力フィールドに依存するならバージョンを固定する。
  • まず読み取り専用から。 エージェントに最初に任せる作業は、参照のように状態を変えないものがよい。検索で選ばれたコマンドが削除や変更のコマンドである可能性があるので、実行前に人間が確認する段階を置く。
  • 認証情報の範囲。 コマンドが数千あるということは、エージェントが使える権限の幅が広いということでもある。トークンは必要な範囲に絞る。認証情報の設計は CLI 認証ガイドで扱った。
  • Wrangler 依存の確認。 プロジェクトが esbuild に依存するかを先に見る。そうなら cf に移行しても Wrangler が残る。

同じ会社の他の発表との関係は、それぞれの記事で扱った。エージェントのランタイム側は Cloudflare OS の記事、Vite チームの合流は VoidZero 合流の記事を参照する。コマンドをプレビューなしで実行しない設計は --dry-run 設計の記事がまとめている。

点検項目のかなりの部分は、実行しなくても答えられる。パッケージ名とリポジトリの確認、プロジェクトのビルド方式の確認、トークンの範囲の検討は、すべて読むだけで済む。実行が必要なのは、検索と出力形式を直接確かめることだけで、それも参照系のコマンド一つで足りる。導入判断に要る情報の大半が、このように状態を変えない確認で得られることが、ベータのツールを扱うときの安全な出発点だ。

確認できなかったこと

  • 「3,000以上」という作業数。ブログ原文の文は「数千」で、正確な数は README にもブログにもない。3,000という値は GeekNews の要約にだけある。
  • cf cli search の検索精度と実際の出力例。原文は動作の仕組みを説明するだけで、質問ごとの結果や失敗率を示していない。
  • JSON 出力のスキーマと圧縮の水準。フィールド構成や人間向けに対する削減率は原文にない。
  • 設定40%圧縮の基準。5,000行を超えていた内部設定が何に対して40%減ったのか、行数かサイズかは文だけでは確定しない。
  • 公開ベータの終了時期と正式リリース日。ベータ終了後18か月という期間だけがあり、終了日は示されていない。
