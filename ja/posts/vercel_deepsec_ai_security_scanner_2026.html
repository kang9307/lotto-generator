1. パターン検索とAIエージェントの融合 — 2段階パイプラインの概要

一般的に、ソフトウェアの脆弱性を検出する静的解析ツール（SAST）は、定義済みのルールや正規表現を用いてソースコードを高速に検索します。文字列結合による生のSQLクエリや、認証ミドルウェアが欠落したルートハンドラーを抽出する処理において、こうしたパターンマッチングは優れた速度と再現性を示します。しかし、パターン検出だけでは、流入する入力データが上位レイヤーで既に無害化されているか、あるいは外部ネットワークから隔離された内部専用モジュールであるかといった文脈を十分に判断できません。

一方で、大規模言語モデル（LLM）をベースとするコーディングエージェントは、複数ファイルにまたがるデータの流れを追跡し、既存の防御ロジックを検証することに長けています。しかし、リポジトリ内の全ソースコードを無差別にモデルのコンテキストに投入する手法は、膨大なトークン費用と著しいレイテンシを引き起こします。Flavio Copes氏のレビューによると、VercelのオープンソースセキュリティスキャナーDeepSecは、この2つのアプローチを統合した2段階パイプラインを採用しています。

原典の説明では、高速なパターン検出器がまず詳細なレビューに値するコードを選定し、続く段階でコーディングエージェントがそのコードを読み込み、ファイル間を横断してデータの流れを追い、既存の防御策を精査したうえで所見を作成します。この仕組みにより、計算負荷の低いローカルパターン走査が探索範囲を大幅に絞り込み、推論コストの高い深層調査を厳選された候補ファイルのみに集中させる分業が成立します。

この記述に対する当記事の解釈としては、単一のプロンプトでリポジトリ全体の診断を丸投げする従来型の手法とは異なり、専用ディレクトリで候補群と状態を保持するハーネス構造を備えている点がDeepSecの設計上の強みです。ファイル単位の調査履歴が保持されるため、規模の大きなコードベースであっても反復可能で中断再開が容易な監査が実現します。

2. DeepSec全体ワークフローの6段階とアーキテクチャ

Flavio Copes氏の技術レビューで解説されているDeepSecの実行パイプラインは、単一のコマンドで終わるブラックボックスではなく、段階的に状態を蓄積していく6つのステップで構成されています。リポジトリ認識から最終レポート出力に至るフローは以下の通りです。

表 1: DeepSecセキュリティ監査パイプラインの6段階構造（Flavio Copes氏のレビューに基づく整理）
段階番号 パイプライン段階 主なシステム処理とアーキテクチャ上の責務 コストおよび実行特性
第1段階 リポジトリ (Repository) プロジェクトのワークスペース検出、言語ランタイムおよび技術構成の把握 ローカルファイル読み取り（API費用ゼロ）
第2段階 インベントリ (Inventory) HTTPルート、RPCハンドラー、キュー処理、Webhookなどの外部入力接点を一覧化 攻撃対象領域の可視化とマッチングルール適合性検証
第3段階 パターン走査 (Pattern scan) 宣言的なファイルパスと正規表現マッチャーを適用し、調査対象候補コードを選定 高速なローカル決定論的検査（外部通信なし）
第4段階 AI調査 (AI investigation) コーディングエージェントが候補ファイルを読み込み、呼び出し経路や防御を追跡 モデルトークン消費（主要な費用発生箇所）
第5段階 再検証 (Revalidation) 2回目のエージェント検証を行い、誤検知の排除と深刻度レーティングの再調整を実施 確度の高い候補所見に対する選択的推論
第6段階 レポート (Report) 確定したセキュリティ所見を構造化されたMarkdownや集計データとして出力 ローカル成果物の出力と集約記録

原典によると、DeepSecはこれらすべての処理状態をリポジトリルートに生成される専用ディレクトリ配下に隔離して保管します。ここには設定ファイルとともに、自動生成された脅威モデル、検出されたエントリポイント一覧、中間調査ログが体系的に記録されます。そのため、長時間を要する全体スキャンが途中で停止した場合でも、最初からやり直すことなく完了済みファイルをスキップして再開できます。

この段階的パイプラインがもたらすエンジニアリング上の利点は次の通りです:

  • 静的パターン検査がローカルで無料実行されるため、無関係なファイルに対する無駄なAIトークン出費を事前に抑止できます。
  • 公開エントリポイントの一覧を先行作成することで、静的ルールが重要な攻撃面を見落とす死角を防ぎます。
  • 調査段階におけるモデルの判断根拠とコード追跡履歴が追記専用で記録され、事後レビューが容易になります。
  • 独立した再検証プロセスを挟むことで、単一パスのエージェント推論で生じがちな幻覚や過度な警報を抑制します。
  • すべての設定と成果物が隔離された作業領域に収められ、アプリケーション本体のビルドを汚染しません。

3. 初期セットアップとスキャフォールディング、コスト制御オプション

Flavio Copes氏は、DeepSecを既存のコードベースに導入する際、いきなり全体調査を開始するのではなく、まず環境の骨格だけを安全に生成するアプローチを推奨しています。特に有償の外部モデル呼び出しを行う前に、設定内容を目視確認できるよう専用フラグが用意されています。

作業領域のディレクトリと基本設定の雛形のみを生成し、実際のAI処理を開始しないスキャフォールディングコマンドは以下の通りです:

# パッケージ導入やモデル呼び出しを行わず作業領域の雛形のみを生成して終了
npx deepsec init --scaffold-only

このコマンドを実行すると、隔離された作業ディレクトリが生成され、プロジェクトの概要を記述したファイルや自動検出されたマッチャールールが配置されます。エンジニアは本番スキャンを開始する前にこれらの記述を開き、外部入力の経路が正しく定義されているか、テストコードなどの安全な例外ファイルが除外されているかを事前に確認できます。

また、大規模なリポジトリで初回スキャンを実施する際、予期せぬトークン請求を防ぐための厳格な上限設定フラグも提供されています。レビュー記事で引用されている設定コマンドは次の通りです:

# 最大費用25米ドル、最大実行時間30分に処理を厳格制限
npx deepsec init --max-cost-usd 25 --max-duration 30m

原典によると、このコマンドは設定された金額上限または時間制限のいずれかに達した時点で、安全なチェックポイントで自動的に処理を保留します。停止後に同じコマンドを再実行すると、調査済みのファイルは自動的にスキップされ、未処理の候補ファイルのみを継続して解析するため、予算を厳密に管理しながら段階的に監査を進められます。

初期設定フェーズで遵守すべき実務上の要点は以下の通りです:

  • スキャフォールディング専用コマンドを用い、課金発生前に自動生成された脅威モデルの妥当性を照合します。
  • 費用上限オプションを明示的に指定し、許容可能な予算枠の範囲内で段階的な検証サイクルを維持します。
  • 時間制限フラグを併用することで、特定の極端に複雑なファイルで処理が無限に遅延するリスクを回避します。
  • 環境変数に設定したAPI認証情報が誤ってGitリポジトリにコミットされないよう除外定義を確認します。
  • 自動生成されたマッチャールールが過度に広いファイル群を巻き込んでいないか正規表現を精査します。

4. 日常的な監査ワークフローを担う4つの基本コマンド

初期構成が整った後、日常の開発業務において反復利用されるワークフローは、パッケージマネージャーを介した4つの基本コマンドに整理されています。Flavio Copes氏のレビューで示された主要コマンドは以下の通りです:

# 1. ローカルマッチャーに基づく高速パターン走査（候補ファイルの抽出）
pnpm deepsec scan

# 2. 抽出された候補ファイルを対象にコーディングエージェントによる深層調査を実施
pnpm deepsec process

# 3. 検出された潜在所見に対して二次エージェントによる再検証を実行
pnpm deepsec revalidate

# 4. 検証結果のサマリー集計と最終セキュリティレポートの生成
pnpm deepsec report

各コマンドは2段階パイプラインの独立した責務を担います。第1の走査コマンドはローカルCPUリソースのみを消費して動作するため、極めて高速であり外部API費用も発生しません。この処理で潜在的なリスクパターンを含む候補ファイル一覧が作成されます。

第2の処理コマンドは、保留中の候補ファイルをバッチ単位でまとめ、プロジェクトの文脈情報とともに指定されたコーディングエージェントに渡します。エージェントは関数の呼び出し元、認証層、入力検証ロジックを読み解き、具体的なリスクの根拠を記録します。

第3の再検証コマンドは、1次処理で作成された所見を別のエージェントパスで再評価します。モデルの誤判断や幻覚をふるい落とし、確定した結果を真陽性、偽陽性、修正済み、不確実などのステータスに再分類します。第4のレポートコマンドは、蓄積されたデータをもとに統計をまとめ、Markdown形式の課題文書を出力します。

日常ワークフローの運用において留意すべき指針は以下の通りです:

  • 走査コマンドは無償で実行できるため、コミット前やプルリクエスト作成前に頻繁に実行して候補を更新します。
  • 処理コマンドはAPIトークンを消費するため、必要に応じてファイル数制限オプションを併用して段階的に実行します。
  • 再検証プロセスは、高深刻度と判定された重要所見から優先的に適用することで検証コストを最適化します。
  • 出力されたセキュリティレポートには詳細な脆弱性情報が含まれるため、外部公開リポジトリでの不用意な共有を避けます。

5. Flavio Copes個人プロジェクト走査事例 — 729ファイルと504件の所見

Flavio Copes氏は、自身が保守運用しているWebサイト「flaviocopes.com」のリポジトリに対してDeepSecを実行した実証結果を公開しました。同氏の説明によると、サイト全体はAstroによる静的生成が中心であるものの、Cloudflare Pages Functionsによるニュースレター配信、決済Webhook処理、講座受講認証、各種ブラウザツール、運用スクリプトなど、多岐にわたるサーバーサイドロジックを併せ持っていました。

この実走査で記録された具体的な数値と統計は以下の表の通りです。重ねて留意すべき点として、この結果は特定の開発者が自己のWebサイトを走査した単一の試行結果であり、DeepSec自体の公式な性能ベンチマークではありません。

実行画面に504件という大きな数値が表示された当初、著者は強い警戒感を抱いたと記しています。しかし、ツールはこれらを「潜在的な所見（potential findings）」と明記していました。また、この試行ではローカルに設定されたCodexセッションを通じてChatGPTの既存サブスクリプション枠内で実行されたため、別途のAPI請求は発生しなかったと同氏は述べています。

この実例から得られる要点は次の通りです:

  • 静的サイト基盤であっても、729ファイル規模のリポジトリでは数百件規模の潜在パターンが抽出され得ます。
  • 報告された504件のうち過半数を占める378件は、セキュリティ侵害ではなく通常のソフトウェアバグでした。
  • 全体の精査過程で約1,440万の入力トークンと170万の出力トークンという大規模な計算資源が消費されました。
  • 初回の走査結果に記載された潜在所見という表現は、事後トリアージが前提であることを明確に示しています。
  • ローカルセッションを活用した無償試行であっても、モデル提供元の利用枠上限を消費する点には留意が必要です。

6. 504件の検出が504箇所の修正を意味しない理由 — 深刻度分類とトリアージ

Flavio Copes氏の知見の中で最も実践的な示唆は、「504件の発見が504個の修正作業を意味するわけではありません」という洞察に集約されています。数値の大きさに動揺して直ちに504件のチケットを作成して修正に奔走するのは、本質を見誤った対応です。

著者の分析によれば、504件のうち462件は、サイト上で提供されている小型のブラウザユーティリティ群（src/tools および src/pages/tools）に集中していました。これらのツールはサーバーと切り離されたクライアント環境で完結して動作するものであり、報告内容の多く（378件）は計算処理の境界値ミスやUIのレンダリング崩れといった一般的な製品バグでした。品質向上として直す価値はあるものの、緊急のセキュリティ対応ではありません。

また、ツールのコンポーネント実装とそれを呼び出すAstroラッパーページの両方で、同一原因のアラートが重複して計上されている事例も確認されました。当記事の解釈としては、共通の入力検証関数を1箇所改修するだけで、数十件の警告が一挙に解消される構造が存在していたと考えられます。

著者はエージェントを活用し、ネットワーク到達性と根本原因に基づいて所見を再分類しました。その結果、504件の膨大なリストは以下の少数の重要領域に整理されました:

  • 決済Webhook、受講権限復旧、公開フォーム送信を処理するサーバー側の機密エンドポイント
  • 生のユーザー入力から動的に実行可能スクリプトやコマンドを生成・描画するブラウザツール層
  • 信頼できない外部データがシェルコマンド実行やファイル操作に達する懸念のあるローカル運用スクリプト
  • 緊急対応ではなく通常の製品改善バックログへ移管すべき一般的なソフトウェア品質欠陥
  • セキュリティ講義用にあえて脆弱なコード例を掲載している学習教材などの無害な記述

最終的に、実際にコードの防壁を補強すべき対象は数百箇所ではなく、数えるほどの重要箇所へと収束しました。原典が強調するように、セキュリティ対応の優先順位はツールの深刻度ラベルだけでなく、外部の攻撃者が実際にその処理に到達できるかどうかに基づいて判断されるべきです。

7. 実務導入における適合性と境界条件

DeepSecは、パターン走査の即時性とAIエージェントの深い文脈理解を兼ね備えた強力なツールですが、あらゆるソフトウェアプロジェクトに無条件で適しているわけではありません。Flavio Copes氏のレビューは、このツールが真価を発揮する領域と、逆に導入の適合性が低い境界条件を明確に示しています。

原典によると、DeepSecが最も高い費用対効果を発揮するのは、認証機構、データベースアクセス、外部決済、認可ロジックが複雑に絡み合う多層Webアプリケーションやバックエンドサービスです。一方で、サーバーサイドロジックを持たない純粋な静的サイトや、外部入力を受け付けない単一の小規模スクリプトに適用した場合、設定の手間とトークン費用ばかりが膨らむ結果になりかねません。

実務環境における導入判断の指針は以下の通りです:

  • 認証情報、金融決済、個人データ、アクセス制御を管理するサービスリポジトリを最優先対象とします。
  • 明確な公開エンドポイントを持たない単体ライブラリを監査する場合は、プロジェクト固有の脅威モデル定義を先行させます。
  • 1行の軽微な修正ごとに毎回AIスキャンを実行するのは非効率であるため、通常のリンターと単体テストを第1防衛線とします。
  • 信頼できない第三者コントリビューターのPRをローカル環境で直接スキャンする際は、スクリプト実行リスクに警戒します。
  • モデルが提案する修正案を盲目的にマージせず、人間のエンジニアが防御経路を直接検証したうえで適用します。
  • CI環境に統合する場合は、リポジトリへの読み取り専用権限設定とセキュリティレポートの非公開化を徹底します。
