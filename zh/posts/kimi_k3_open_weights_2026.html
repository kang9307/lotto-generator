Kimi K3 权重公开 - 2.8万亿参数开放权重模型能否落地

许可证条件、显存计算与总成本 - 选型决策真正需要的，不是发布稿里的东西

2026年7月28日 IT/技术

引言：从「已公开」到「能用上」的距离

2026年7月底，Moonshot AI 把 Kimi K3 的权重开放下载。标题数字是 2.8万亿参数。作为人人可获取的权重，这个规模并不常见，于是报道的标题几乎都被这个数字占满。

然而站在选型的角度看，参数量几乎是页面上最不重要的信息。实务人员真正要回答的问题有四个。第一，许可证是否允许我们公司使用。第二，我们能拿到的设备跑得动吗。第三，用在哪些任务上划算，哪些任务上反而吃亏。第四，是否真的比商用 API 便宜。这四问没有答案，是2.8万亿还是28万亿都推进不下去。

本文只讨论这四个问题。与其罗列发布事实，不如核对模型卡和许可证原文里写了什么，并把没能确认的部分明确标注为未确认。特别是每引用一个数字，都会同时标明 由谁测量。厂商自测值与第三方评测机构的测量值，分量并不相同。

另外，上一代的介绍已在 Kimi K2.7-Code 分析 中写过，这里不再重复。围绕开放权重模型的监管与生态讨论，放在 开放权重 AI 的监管议题 和 开放权重的容器编排时刻 里另行整理。本文集中于 一个组织决定是否采用这款模型所需的信息。若想了解各代模型的坐标，可以配合 AI 模型对比中心 一起看。

1. K3 的真实规格 - 公开了什么

以下数值全部来自 Hugging Face 上的 Moonshot AI 官方模型卡，依据的是发布页面原文，而非报道或二次摘要。

1.1 模型结构

K3 采用 混合专家（MoE） 结构。总参数为2.8万亿，但处理单个 token 时真正参与计算的只有 1,040亿（104B）。专家总数为 896个，每个 token 选中 16个，此外还有2个始终启用的共享专家。

  • 总参数：2.8万亿（2.8T）
  • 每 token 激活参数：1,040亿（104B）
  • 专家配置：896个中每 token 选16个，另加2个共享专家
  • 层数：共93层（Kimi Delta Attention 69层 + Gated MLA 24层）
  • 上下文：1,048,576 个 token（百万级）
  • 视觉编码器：MoonViT-V2，约4.01亿参数
  • 词表规模：16万
  • 激活函数：SiTU-GLU

这里真正有实务意义的数字不是2.8万亿，而是 104B，因为决定算力开销和响应速度的是激活参数。反过来，决定内存需求的是总参数。也就是说 K3 是一款 按2.8万亿的量级吃内存、按1,040亿的量级做计算 的模型。这种不对称支配了后面全部的硬件讨论。

1.2 注意力机制 - KDA 与 Gated MLA

模型卡把注意力描述为 Kimi Delta Attention（KDA） 与 Gated MLA 的混合。93层中69层为 KDA，24层为 Gated MLA。大量铺设线性注意力、只掺入少量全局注意力的混合构型，读起来像是为了缓解百万 token 上下文下 KV 缓存膨胀的问题。

不过这种构型的实际效果有多大，没有找到独立验证结果。架构名称与层数分配是模型卡上写明的事实，但它对长文本处理质量贡献多少则是另一回事。如果确实打算用长上下文，用自有数据测一测召回率会更稳妥。

1.3 MXFP4 原生这一选择

这是实务上最关键的一项。K3 以 MXFP4 权重 / MXFP8 激活值 的形式发布，模型卡把它归因于 量化感知训练（quantization-aware training）。

这个差别值得说清楚。通常开放权重模型以 BF16 之类的高精度格式发布，用户事后再压到4比特运行。这种事后量化大多伴随质量损失。而 K3 是 从一开始就按4比特训练好再发布。用户无需另做量化步骤，事后压缩常见的劣化风险也相应下降。

附带效果是体积。每参数4比特即每参数0.5字节，因此2.8万亿参数的权重体积约为 1.4TB。同一模型若按 FP16 发布则为5.6TB。（这两个数值是笔者用参数量乘以位宽算出来的，并非模型卡上写明的数字。）降到四分之一固然可喜，但正如下一节所示，1.4TB 也绝不是小数目。

1.4 相比 K2 世代有何变化

Moonshot 表示，新的架构组件带来了 相对 K2 整体扩展效率2.5倍的提升。这属于 厂商自述，并无第三方复现。用户更容易感知的变化其实在下面。

项目Kimi K2.7-Code（上一代系列）Kimi K3

上下文256K token1,048,576 token

实务上最大的变化是 激活参数从320亿增至1,040亿，涨了三倍以上。质量上去了，但每 token 的算力开销也随之上升。也就是说 K3 并不比上一代 更轻。原先为了省钱用 K2 系列跑编码智能体的团队，若直接换成 K3，成本反而可能上涨。世代更新并不自动等于向上兼容。

还有一点：K3 无法关闭思考模式。模型卡明确写明 K3 始终进行推理并返回 reasoning_content，强度可在 low / high / max 之间调节。把它接到短小简单的分类或抽取任务上，就会持续产生用不上的思考 token，因此在任务编排时必须纳入考虑。

2. 细读许可证 - 开放权重不等于开源

这是全文最重要的一节。企业内部的选型评审真正卡住的地方往往不是性能，而是许可证。

2.1 Kimi K3 许可证的条件

K3 的代码与权重以名为 「Kimi K3 许可证」 的自有许可证发布。它不是 MIT 那样的标准许可证，而是在宽松授权文本上追加了若干条件。以下内容核对自许可证原文。

  • 基本授权：允许使用、复制、修改、合并、发表、分发、再授权与销售。运行、部署、微调 以及创建衍生作品均获明确许可。
  • 保留版权声明：版权声明必须包含在软件的所有副本或实质性部分中。这是基础义务。
  • 大规模服务需另行签约：若以模型即服务的形式提供，且 任意连续12个月合计收入超过2,000万美元，须在该商业使用之前与 Moonshot AI 另行签订协议。
  • 界面标注义务：包括衍生作品在内，用于 月活跃用户超过1亿 或 月收入超过2,000万美元 的商业产品或服务时，必须在用户界面显著位置标出 Kimi K3。
  • 例外：内部使用，以及通过 Moonshot AI 官方产品或认证合作伙伴的访问，不适用上述两项条件。

归纳起来是这样：对绝大多数组织而言，这些条件实际上无害。月收入2,000万美元或月活1亿是多数企业不会触及的水平，而纯内部使用本就被排除在外。但「没有条件」与「有条件但对我们不生效」，在法务评审里是完全不同的两件事。后者需要留下书面记录。

2.2 企业引入前要确认的四件事

若真要推进评审，以下几项值得落到文档里。

  1. 我们的使用形态属于「内部使用」还是「对外服务」。只供员工使用的工具很可能落入例外条款。而一旦嵌入面向客户的产品，就必须持续跟踪收入与月活这两条线。
  2. 路线图上会不会越线。眼下不触及，不代表三年后的增长计划不会越过。在产品设计阶段就知道要加界面标注或另行签约，远好过事后才发现。
  3. 微调产物如何处置。许可证允许创建衍生作品，但评审应以「同样的条件会随衍生作品一起延续」为前提。若打算把用内部数据调过的模型对外销售，尤其如此。
  4. 数据走哪条路径。这属于安全评审而非许可证问题。拿到权重在自有基础设施上运行，提示词不会外流；反之为图方便调用 Moonshot 的托管 API，数据就会出去。使用开放权重模型这一事实本身并不保证数据主权，真正提供保证的是自建部署这一落地方式。

再补充一条实务建议：以上归纳终究是 笔者阅读许可证原文后的整理。合同判断应以原文而非摘要为准，若组织有可能触及金额门槛，走一遍法务评审才是稳妥做法。许可条款可能修订，请以评审当时的原文为准。本文数值为 2026年7月时点。

2.3 为什么不该称它为「开源」

媒体与社区里这两个词常混着用，但选型评审需要区分开。

  • 开源 通常遵循 OSI 定义，其核心是 不得因使用领域、使用者或规模而区别对待。
  • 开放权重 只指「已训练参数可供下载」这一发布方式，条件因许可证而异。
  • K3 许可证会随收入与月活规模改变义务，在这一点上就与 OSI 意义上的开源定义分道扬镳。
  • 此外，训练数据与训练代码不在公开范围内，以复现或偏差审计为目的的透明度并未获得。

这种区分并非咬文嚼字。在公共机构或金融行业的采购文件里写上 开源 提交，事后才被发现附带许可条件，是会带来麻烦的。文件里写成 开放权重模型、自有许可证 更为准确和安全。

独立评测机构 Artificial Analysis 的测量结果如下。这一侧是由非厂商的外部机构在同一条件下跑多个模型得出的，性质不同。

但有一点需要留意：这类指数 每次版本更新、有新模型加入时排名都会变动。事实上在其后的统计中，也能看到分数与名次标注不同的资料。因此与其把 第三 当成固定事实引用，不如理解为 公开权重模型中最接近前沿的一档，这样的说法生命力更长。

3.3 不要只看漂亮的数字 - 幻觉率的倒退

同一机构指出了一项负面结果，而对选型判断来说，它反而更重要：幻觉率从上一代的39%上升到了51%。准确性指标在改善，幻觉指标却在倒退。

这种组合在实务中会造出一种特定的失败模式：更能解决难题，同时更不擅长承认自己不知道。写代码或跑检索智能体时，把结果执行一遍就能暴露错误，风险因而被吸收；而在事实摘要、资料调研、客户应答这类 输出会被人直接采信 的场景里，风险则完全暴露。这正是后文适用与不适用判断的核心依据。

补充一句，基准测试上的领先并 不能保证 它在你自己业务上的质量。无论哪款模型，在用自有数据建的小型评测集跑过之前，都缺乏可靠依据。

4. 真要跑起来 - 先从显存计算说起

很多评审就止步于此。模型卡 没有写明最低硬件要求。所以下面给出笔者自行计算的数值并附上推导过程，这是算术而非引用，读者可以自己验算。

4.1 权重体积的计算

计算很简单：把每个参数占用的字节数乘以参数个数即可。

  • 按 MXFP4（4比特）：2.8万亿 × 0.5字节 = 约1.4TB
  • 作为参照，若为 FP8 则是 2.8万亿 × 1字节 = 2.8TB
  • 作为参照，若为 FP16 则是 2.8万亿 × 2字节 = 5.6TB
  • 也就是说，MXFP4 原生发布把内存需求压到了高精度发布的 四分之一

接下来要把这1.4TB 分摊到加速卡上。以80GB 级加速卡为基准，1.4TB ÷ 80GB ≈ 18张。仅仅装下权重就是18张，之后还要叠加 KV 缓存、激活值与框架开销。换算成八卡一节点，至少三个节点起步。

要注意这个计算是 理论下限。真实部署中，张量并行的通信缓冲、CUDA 上下文、调度器内存与碎片化，会让每张卡上有若干 GB 与参数毫无关系地消失。按刚好够用来设计，往往连启动都启动不了。

顺带一提，网上有不少文章称 单台服务器或五六张 GPU 就能跑，这与上面的算术对不上。2.8万亿参数即使按4比特存放也是1.4TB，物理上装不进六张80GB 卡（480GB）。不建议拿这类资料去编预算。

4.2 KV 缓存与上下文 - 百万 token 的代价

装好权重并不算完，还剩 KV 缓存。它随并发会话数与每个会话的上下文长度成比例增长。

  • 百万 token 上下文的意思是「可以用」，不是「免费」。
  • 只要同时开几个长上下文会话，KV 缓存就可能膨胀到数百 GB 量级。
  • 因此实际容量规划应按 权重 +（并发会话数 × 每会话上下文长度） 来算。
  • 确认推理框架是否提供把 KV 缓存压到 FP8 之类的选项，能腾出不少余量。
  • K3 以 KDA 为主的混合构型正是为减轻这一负担而设计，但 具体的削减比例未能确认。

实务上更好的做法是：不要按最大上下文设计，而应测量实际请求长度的分布，按95分位来设计。若百万 token 的请求只占总量的1%，为这1% 把整个集群放大并不合理，把这类请求单独排一条队列反而更省。

4.3 推理框架

模型卡列出的推理引擎为 vLLM、SGLang 和 TokenSpeed，并写明提供 OpenAI/Anthropic 兼容 API 格式。

  • 必须支持 MoE 路由。要处理896个专家，引擎需具备专家并行能力。
  • 需按引擎版本核实 MXFP4 格式的支持情况。新格式一般只在特定版本以上可用。
  • 提供兼容 API 格式是实打实的优点：既有的 OpenAI SDK 代码往往 只需替换端点 就能接上试跑。
  • 由于是多节点构型，节点间互联带宽 直接决定性能。用普通以太网串起来，token 生成速度可能大幅下滑。
  • 思考模式始终开启，响应中会带 reasoning_content。既有解析器若处理不了，集成阶段就要额外花工夫。

归纳起来，自建 K3 不是「下载一个模型」这件事，而是「运维一个小型 GPU 集群」这件事。这句话就是选型评审中现实的分水岭。

5. 总成本判断 - 自建部署对比商用 API

权重公开这一事实，并不直接等同于 便宜。本节来立判断标准。

5.1 API 的价格坐标

Artificial Analysis 整理的 Kimi API 价格如下。（为2026年7月时点，价格随供应商与时间而变。）

  • 输入：每百万 token 3美元
  • 输出：每百万 token 15美元
  • 缓存命中输入：每百万 token 0.30美元（较标准输入价低90%）
  • 混合单价：每百万 token 2.31美元（按缓存、输入、输出7:2:1的比例假设）

这里有一点值得注意。同一机构评价称，K3 与其他开放权重模型相比属于偏贵的一档。也就是说 开放权重等于低价 这一通念，并不能原样套到 K3 上。激活参数达到1,040亿，服务成本本身就高，这是自然的结果。若追求低单价，激活参数比 K3 更小的开放权重模型可能是更合适的选择。

速度特征同样有记录。同一机构测得输出速度为 每秒33.3个 token，首个 token 的延迟约为 148秒。后一个数字看着吓人，但更自然的解读是：思考模式始终开启，模型在回应前先做推理。其实务含义是，这样的延迟直接接到对话式界面后面会相当吃力。

5.2 盈亏平衡的思考方式

自建与 API 谁更便宜，由 利用率 决定。框架如下。

  • 自建的成本是 固定成本。哪怕一个请求都没有，GPU 租金、电力与机位费用照付。
  • API 的成本是 可变成本。不用就是零。
  • 因此盈亏平衡点取决于 能把集群填满而不空转的月度 token 量。
  • 流量白天集中、夜间空闲的对话式服务利用率低，对自建不利。
  • 反过来，能用夜间批处理把队列填满的大批量文档处理可把利用率维持在接近100%，因而占优。

运维人力没有 GPU 集群运维人员具备推理基础设施运维经验
模型版本策略希望持续切换到最新模型需要长期锁定某一版本
前期投入无法先行投入能够拿到多节点资源
延迟要求需要即时响应可接受批处理或异步

5.3 容易漏算的成本

自建的报价之所以常常算得偏低，多半是因为漏了以下几项。

  • 人力成本：多节点推理集群需要专人负责，这份薪资有时会超过 GPU 租金。
  • 故障处理：少一个节点，整个模型就下线。要做冗余就得准备两套集群。
  • 升级成本：半年后出了更好的模型，集群设计就得重做；用 API 只需改一个字符串。
  • 启用初期的低效：在调好服务参数之前，吞吐达不到预期一半是常有的事。
  • 电力与散热：若为本地机房，机位与电费是另算的成本。

现实的折中方案是 混合部署：只把涉及敏感数据的负载放在自建环境，其余交给 API。由于 K3 提供 OpenAI 兼容格式，用同一套代码处理两条路径相对容易。先用 大模型 API 价格计算器 按用量算一遍 API 成本，有助于建立对盈亏平衡点的直觉。

6. 哪些任务适合，哪些不适合

把前面的依据综合起来，就能得出编排判断。依据有三条：思考模式无法关闭、第三方指出幻觉率倒退、激活参数偏大导致单价不低。

6.1 适合的任务

  • 多步骤智能体任务：在工具调用与网页检索类基准上被报告为强项，也与推理始终在线的设计相契合。
  • 长周期编码课题：在多个文件之间往返地规划、修改与验证。因为结果可执行验证，幻觉风险被吸收。
  • 大体量文档与代码库分析：这是少数真正用得上百万 token 上下文的场景。
  • 文档图像处理：具备原生视觉，且在文档视觉基准上被报告为领先。
  • 禁止外传的数据处理：在没有替代方案的情况下，能拿到权重在内部运行本身就是决定性的。
  • 夜间批处理流水线：延迟不成问题，利用率也填得满。

6.2 不适合或需谨慎的任务

  • 简单分类、抽取与打标：思考模式关不掉，会持续产生用不上的推理 token，小模型便宜得多。
  • 需要即时响应的对话式界面：首 token 延迟测得偏长，在用户等待的画面上会成为负担。
  • 未经核验就直接呈现的事实陈述：既然存在幻觉率倒退的指摘，就必须一并设计出处标注与核验流程。
  • 以成本最小化为首要目标的大批量简单作业：在开放权重阵营里，它的单价也不算低。
  • 小团队的首次自建尝试：多节点 MoE 推理难度不低，先用更小的模型积累运维经验为宜。
  • 需要在合规文件中写作开源的采购：因为前述许可条件，措辞必须准确。

7. 选型决策清单

若要真正推进评审，建议按下面的顺序来，从上往下走，卡在哪一条就停在哪一条。

  1. 用途上 API 够不够用，先问这个。够用就没有下载权重的理由。自建是手段而非目的。
  2. 是否存在禁止外传的数据。有，则自建的评审站得住脚；没有，就单纯按成本判断。
  3. 是否触及许可证的门槛。把「属于内部使用还是对外服务」「路线图会否越过收入与月活线」写进文档。
  4. 能否拿到装得下1.4TB 的硬件。不能，评审到此为止，把候选换成更小的开放权重模型。
  5. 推理框架是否支持 MXFP4 与 MoE 路由。核实到引擎版本。
  6. 是否用自有评测集测过质量。自家业务数据30到100条就能看出方向，不要拿基准排名代替。
  7. 是否有足够用量填满利用率。没有的话 API 更便宜。
  8. 运维与故障处理的责任人是否明确。没有负责人就开起来的集群，最后都会被搁置。

没过这八关就从 「听说2.8万亿参数公开了，我们也下一个试试」 起步的话，多半会在硬件报价环节掉头回来。

8. 局限与未决问题

这里写明撰稿过程中 未能确认的事项。与其用推测去填，不如空着。

  • 官方最低硬件要求：模型卡未作说明。本文的1.4TB 是笔者用参数量与位宽算出的数值。
  • 实测吞吐：关于特定硬件配置下的每秒 token 数或并发会话数，没有找到可靠的一手资料。
  • KDA 构型带来的 KV 节省量化值：架构构成已公开，但节省幅度无法用数字确认。
  • 微调的实务难度：许可创建衍生作品，与实际调得动这个规模，是两回事。未能找到关于所需资源的官方说明。
  • 中文表现：公开的基准大多为英语圈评测，中文业务上的质量需要自行验证。
  • 指数排名的当前值：评测指数会随版本更新而变动名次，本文数值以发布时点为准。

还有一点值得一提：在规模竞赛持续的同时，公开权重的实际可及性反而在下降，这是个悖论。数百亿参数模型陆续开放的时期，配置好的个人工作站也能跑起来；2.8万亿参数则不同。人人都能 下载，但能 运行 的主体收窄到了能运维多节点集群的组织。这一趋势如何改变开放性的含义，在 开放权重的监管议题 与 开放权重生态分析 中有更详细的讨论。

结论 - 压缩成三句话

第一，Kimi K3 是开放权重而非开源。其自有许可证附带了以收入与用户规模为基准的条件。对多数组织无害，但在采购文件与法务评审中，应准确写成 开放权重模型、自有许可证。

第二，公开与跑得动是两回事。即便 MXFP4 原生发布已把体积压到四分之一，单是权重仍约1.4TB，相当于十八张80GB 级加速卡，且以多节点集群运维为前提。卡在这一步，后面的讨论就没有意义。

第三，世代更新并不自动等于向上兼容。激活参数涨了三倍以上，思考模式关不掉，第三方测量中幻觉率反而上升。它是多步骤智能体、长周期编码与大体量文档分析的有力候选，但对简单分类或需要即时响应的对话式服务而言过重且偏慢。这是按负载去编排，而不是去挑一款模型 的原则，这次同样适用。

最后说一条方法论。无论哪款模型，选型结论都应来自 用自己业务数据搭的小型评测集，而不是基准排名。30到100条就足以看出方向。发布材料上的数字只用来缩小候选范围，最终决定交给自己测出来的数值，这样更稳妥。
