1. Background of Why while (true); Was Undefined Behavior

Generally, iterative control statements in programming languages provide the fundamental mechanism for sustaining control flow until specific exit conditions are met or for intentionally keeping an execution context waiting. Across software engineering and low-level development, many programmers write an empty while (true); statement with the explicit expectation that execution will reach this point and stop permanently. However, the source states that prior to C++26, a while (true); loop with no side effects was classified under the language specification as undefined behavior. While many developers naturally assume that such a program is completely well-defined, according to the source, that assumption was formally incorrect before C++26.

The source explains that compilers were granted the liberty to assume that any loop lacking observable side effects will eventually terminate. Taking advantage of this specification leeway, certain optimizing compilers—Clang in particular—would optimize the loop away entirely. The source points out that this aggressive removal led to what it describes as spectacular consequences, producing runtime execution behaviors that completely defied the programmer's plain reading of the source text.

In this article's interpretation, the change resolves a conflict between compiler optimization assumptions and the developer's intuitive expectation of control flow by establishing a clear grammatical exception.

The source emphasizes that the resolution introduced in C++26 does not declare all infinite loops universally safe. Rather than granting blanket immunity to all looping constructs, the modification is strictly and narrowly scoped to specific syntactic patterns. The source writes that loops must satisfy the precise definition of a trivial infinite loop before they are exempted from compiler elimination.

2. Forward Progress Assumptions and Compiler Loop Optimizations

The source identifies the formal foundation enabling compilers to eliminate infinite loops as the forward progress guarantees codified in the C++11 standard under [intro.progress]. Under these provisions, the implementation is explicitly permitted to operate under the assumption that every execution thread will eventually perform at least one observable action. The source quotes the normative C++11 standard wording as follows: 「the implementation may assume any thread will eventually do one of the following: terminate, call a library I/O function, access a volatile glvalue, or perform a synchronization or atomic operation」. Compilers are thus legally entitled by the specification to assume that every thread will reach one of four designated milestones:

  • Terminating execution normally (terminate).
  • Invoking a standard library input/output function (call a library I/O function).
  • Accessing a glvalue qualified with the volatile specifier (access a volatile glvalue).
  • Executing a synchronization operation or an atomic operation (perform a synchronization or atomic operation).

The source notes that a loop whose body consists solely of a single semicolon, such as while (true);, performs none of these four enumerated operations. It conducts no I/O, touches no volatile memory, executes no atomic operations, and contains no code path leading to normal termination. According to the source's explanation, the compiler applies the forward progress rule, assumes that the thread cannot run forever without progress, and deduces that the loop must eventually complete. Because the loop performs no observable side effects during its execution, the compiler concludes that executing the loop is entirely redundant and deletes the loop check and backward branch entirely from the compiled binary.

In this article's interpretation, when a loop performs none of the four observable operations enumerated by the forward progress rule, compilers treated it as terminable and eliminated it.

3. Clang Loop Elimination and Unreachable Code Execution

To demonstrate the real-world ramifications of this optimization, the source presents a concrete, reproducible code sample compiled under the Clang compiler. The source provides the following implementation snippet:

// https://godbolt.org/z/WYMxxeW1T
#include <iostream>

int main() {
    while (true)
        ;
}

void unreachable() {
    std::cout << "Hello world!" << std::endl;
}

The source documents that compiling and executing this program under Clang results in the console printing the string 「Hello world!」. Nowhere in the source code is the function unreachable() ever called, and the body of the main() function contains nothing other than the single while (true); statement. Despite this apparent textual barrier, program execution enters a completely uninvoked function, emits output, and terminates.

The source explains the underlying mechanics: the compiler optimizes away the while (true); loop because it exhibits no side effects, leaving the main function completely empty. Consequently, execution falls straight through the end of main, and the program enters the body of unreachable(), which the linker happened to position immediately adjacent in linear memory. The source describes the execution of this supposed unreachable function as a direct consequence of compiler loop removal.

In this article's interpretation, because the loop was eliminated, the control flow boundary of the function vanished, allowing execution to fall straight through into the adjacent function placed next in memory.

4. Requirements for Trivial Infinite Loops in C++26 P2809R3

The source states that the formal proposal adopted into the C++ standard to rectify this undefined behavior anomaly is proposal P2809R3. The source explains that with the acceptance of this proposal into C++26, trivial infinite loops are no longer categorized as undefined behavior. Crucially, the source stresses that the scope of this protection is defined with extraordinary precision and narrowness.

The source cites the exact definition formulated in the proposal as follows: 「The loop must be a trivially empty iteration statement — meaning its body is literally empty (`;` or `{}`). Any non-empty statement in the body, even a meaningless expression statement such as `"a string";`, disqualifies it. The controlling expression must be a constant expression that evaluates to `true`.」 Breaking down this definition yields four strict technical prerequisites:

  • The loop must qualify as a trivially empty iteration statement whose body is literally void of content.
  • The only allowable syntactic forms for the body are a solitary semicolon (;) or an empty compound block ({}).
  • The presence of any non-empty statement within the body—even a statement like "a string";—immediately disqualifies the loop.
  • The controlling expression governing the iteration must be a compile-time constant expression evaluating strictly to true.

The source clarifies that the requirement for an empty body admits no semantic leniency. Even if an expression statement performs no memory writes, modifies no CPU registers, and carries zero computational side effects at runtime, its mere syntactic existence invalidates the trivial infinite loop status under P2809R3. Consequently, loops containing such expressions remain classified as undefined behavior in C++26, just as they were in prior standards.

In this article's interpretation, the core of the rule is that protection is strictly confined to syntactically empty body structures that can be determined directly from grammar.

5. Comparison of Loop Syntax and Protection Status

To provide clear guidance for practical software development, the source contrasts various syntactical forms of infinite loops, explicitly classifying which variations are protected under C++26 and which remain classified as undefined behavior. The comparative classifications presented in the source are summarized in the following table:

Loop Syntax Form C++26 Protection Status Reason and Criteria from Source
while (true); Protected Controlling expression is constant true and the body is an empty semicolon
for (;;); Protected Omitted controlling expression evaluates to true and the body is completely empty
do {} while (true); Protected Loop body block is empty braces and controlling expression is constant true
constexpr bool go = true; while (go); Protected constexpr condition evaluates to constant true at compile time with an empty body
while (true) { "a string"; } Not Protected Disqualified because the body contains a non-empty expression statement
while (true) if (done) break; Not Protected Body is non-empty due to the inclusion of a conditional branch statement
while (true) if constexpr (false) break; Not Protected Fails empty body requirement because the if constexpr statement is syntactically present
bool done = false; while (!done); Not Protected Controlling expression relies on a non-constexpr variable and is not a constant true

As demonstrated in the comparison table, the syntactic footprint protected by C++26 is remarkably concise. Key observations and caveats emphasized by the source include:

  • The three canonical empty loop notations—while (true);, for (;;);, and do {} while (true);—are all fully protected.
  • Using an externally defined boolean variable is valid only if designated with constexpr to ensure compile-time evaluation.
  • Injecting any statement into the body, including string literals like "a string";, revokes protection and triggers undefined behavior.
  • Loops governed by runtime variables, such as while (!done);, receive no protection under the trivial infinite loop rules.

In this article's interpretation, as shown by the classification of while (!done); as not protected, a loop whose condition relies on ordinary variables without volatile glvalue access, atomic operations, or synchronization as specified in [intro.progress] receives no protection from compiler optimization.

6. Defect Report Adoption and Retroactive Application to Earlier C++

The source highlights a vital practical dimension regarding the scope and timeline of P2809R3. Specifically, the source states that the proposal was officially accepted by the standards committee as a defect report: 「The mentioned proposal was also accepted as a defect report, so implementations may apply the fix to earlier C++ modes as well.」

According to the source, because the change is categorized as a defect report, compiler implementations are permitted to apply the fix retroactively to earlier C++ modes. Consequently, developers working with modern toolchains may find that trivial infinite loops are no longer eliminated by the compiler, even when compiling codebases configured with earlier standard switches. The historical evolution and defect report status across standards are outlined below:

Standard Edition Forward Progress Rule Status Treatment of Trivial Infinite Loops
C++11 onward (since forward progress introduction) Subject to [intro.progress] assumptions Loops with no side effects treated as undefined behavior, permitting removal
C11 (ISO C) Constant controlling expressions exempt Source notes 「C got this right」: constant loops explicitly protected
C++26 (P2809R3) Explicit exemption for trivial loops UB removed for empty bodies with constant true; yield semantics applied
Earlier C++ modes (Retroactive) Subject to Defect Report (DR) adoption Implementations may disable loop elimination in earlier C++ modes

The practical implications of the defect report classification for the broader ecosystem include:

  • When targeting earlier C++ modes, trivial infinite loops may be preserved if the compiler implementation adopts the fix.
  • As the source indicates, implementations possess the discretion to apply this fix to earlier modes, making actual behavior dependent on toolchain vendors.
  • Existing codebases utilizing while (true); can benefit from the change even while remaining on earlier language modes.
  • In this article's interpretation, the defect report adoption provides the formal basis for implementations to preserve trivial loops in earlier C++ modes.

The source indicates that because implementations may apply the fix to earlier modes, developers should verify the specific behavior of their chosen compiler toolchains.

7. Embedded Halt-on-Error Patterns and Freestanding Yield Concerns

The source explains that trivial infinite loops are commonly used in embedded systems and kernel development through the halt-on-error pattern. According to the source, when there is no operating system to exit to, the program simply stops (source: 「there's no operating system to exit to, you simply stop」). The source cites hardware initialization failure (such as a hardware_init_failed() situation) as an example where developers place an empty infinite loop to halt execution permanently after a fatal error.

The source explains that if the compiler eliminates this loop, execution fails to remain halted as intended and falls through beyond the loop. The source notes that P2809R3 accommodates these system programming needs by ensuring that empty loops are retained.

However, the source articulates concern regarding how the standard specifies the replacement mechanics in freestanding environments. Under P2809R3, trivial infinite loops satisfy forward progress requirements by semantically substituting the loop with a call to std::this_thread::yield(). The source points out a critical qualification: 「it is implementation-defined whether the replacement with `std::this_thread::yield()` occurs at all」 in freestanding implementations.

The source voices concern regarding this substitution: 「turning a deliberate halt loop into a cooperative yield could introduce behaviour the programmer never intended」. Key points noted by the source regarding freestanding targets include:

  • In freestanding implementations, whether replacement with std::this_thread::yield() occurs is implementation-defined.
  • Turning a deliberate halt loop into a cooperative yield could introduce behavior the programmer never intended.
  • The source does not enumerate specific malfunction scenarios that cooperative yielding might trigger.
  • In this article's interpretation, verifying implementation-defined yield replacement behavior across specific freestanding targets is practically necessary.

The source notes that based on these concerns, engineers must pay close attention to compiler implementation choices when handling trivial loops in freestanding environments.

8. Comparison with C11 and the C++ Committee Decision

The source contrasts the evolution of C++ with the historical path taken by the C language, remarking that 「C got this right」. When the ISO C committee established forward progress rules in C11, it explicitly exempted loops with constant controlling expressions from termination assumptions, ensuring that infinite loops in C remained protected from compiler deletion.

The source reveals that during deliberations within the C++ standards committee, adopting C11's broader rule directly into C++ was evaluated but ultimately rejected: 「considered and rejected」. Under the C11 model, any loop with a constant condition is protected, regardless of whether statements reside in its body. According to the source, this broader exemption was rejected because it would have imposed excessive constraints on C++ optimizing compilers (optimizer constraints).

Consequently, the C++ committee chose a far narrower, more rigorous compromise than C11. Not only must the loop condition be a constant expression evaluating to true, but the loop body must also be literally empty. The comparative design choices between the two language standards are summarized below:

  • C11 protected all infinite loops governed by constant controlling expressions, providing a broad exemption from forward progress requirements.
  • The C++ committee evaluated adopting the C11 approach directly but rejected it due to optimizer constraints.
  • C++26 adopted a highly restrictive rule requiring both a constant true condition and an entirely empty loop body.
  • In this article's interpretation, C++ chose a much narrower empty-body rule than C11 in order to preserve optimizer performance.

The source emphasizes that C and C++ define infinite loops under distinct rules, and that the C++26 revision remains a distinct compromise rather than a full adoption of C11.
