Why the Same Local LLM Feels Dumber Than It Is - The Settings That Quietly Cut Quality

Where the benchmark holds but the conversation gets worse

Aug 23, 2026 IT/Tech

Introduction: the benchmark held, the conversation did not

The model card shows good numbers. The write-ups you read were positive. Then you run it on your own machine and it half-ignores instructions, breaks the output format, and drops a brace in the middle of a tool call. At that point most people land on the same conclusion: local models just are not there yet.

That conclusion is premature, because with identical weights there are at least five layers outside the weights where the result can diverge. None of them raise an error. They quietly produce a different answer. Nothing lands in the log, so the only impression that survives is that the model is dumb.

This article opens those five layers one at a time. Installation and runtime setup live in the local LLM running guide, and machine selection lives in the hardware selection guide, so neither is repeated here. What follows is about a setup that already runs, and where its perceived quality gets cut.

1. The experiment behind this - same weights, diverging output

The topic resurfaced because of a test log posted on the Level1Techs forum. The author took one set of model weights and varied only the execution environment to see how far the output drifted. Using Qwen3.6-27B at BF16 as the baseline, they combined attention backends (FlashAttention2, Flash Inference, Triton), KV cache precision (BF16, INT8, INT4) and weight quantization formats (FP8, INT8 W8A16, NVFP4, AWQ W4A16), then measured how often the top token differed from the baseline along with distance between probability distributions.

The reported direction comes down to three points. One, divergence grows with context length: early tokens agree almost perfectly and the gap widens further in. Two, squeezing the KV cache to four bits breaks tool calls. Three, some four-bit weight formats flipped close to half of the top tokens at long context. The failures the author showed were things like a router command turning into a different command, or the port number 5432 getting mangled into something like 543ql.

What is worth taking from this is not a specific number but the structure. Weights fix a probability distribution; choosing the actual token happens outside them. A small wobble in the distribution changes nothing at most forks, but where first and second place are nearly tied, the order flips. And those forks tend to be exactly the places where an error is immediately visible: identifiers, numbers and closing brackets.

One common misreading of distribution-distance figures. A metric such as KL divergence tells you how far you moved from a baseline, not that a lower value is better, because there is no guarantee the baseline itself is optimal for your task. When a model card advertises low KL divergence, it only means something once you also know what the baseline was, on which data, and at what context length.

3. Chat template mismatch - the failure that stays quiet

Chat models are not a species that understands dialogue. As the Hugging Face documentation puts it, all causal language models simply continue a sequence of tokens, and a conversation is converted into one such sequence with control tokens marking the roles. Which tokens get used differs per model, and the documentation is explicit that models fine-tuned from the same base may use different formats.

So when the format is wrong, this is what happens.

  • Instructions stop reading as instructions. Paste a directive in front without a system role token and, from the model's point of view, it is just background the user typed
  • The model continues instead of answering. The documentation notes that without the generation prompt that opens the assistant turn, the model may continue the user message rather than reply to it
  • Special tokens go out of sync. The documentation warns directly that adding a beginning-of-sequence token again during a later tokenization step, when the template already includes it, hurts performance. In the other direction, an end token that differs from training leaves the model unsure where to stop
  • Tool call formatting collapses. Tool calls are usually expressed through a dedicated role and dedicated tokens, so they break first when the template is off

The key point is that this failure raises no error. Even with a wrong format the token sequence is valid, and the model dutifully continues it. The result is the state everyone recognizes: it runs, but something is off.

3.1 Why benchmarks miss this

Standard benchmarks are mostly one self-contained question answered once, scored on an expected string or on option probabilities. Under those conditions a slightly wrong template barely dents the score, because all that matters is that the correct token still ranks first.

Real conversations are the opposite: multiple turns, alternating roles, and references back to earlier answers. Template errors accumulate in that structure. That is how you end up with an unchanged score and a worse experience. A large share of the complaint that benchmarks look fine but usage does not belongs here.

3.2 There is only one way to check

Do not guess. Look at the final input string. Pulling it out as text before tokenization is the fastest route.

from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("your_model_repo_name")
messages = [
    {"role": "system", "content": "You answer concisely."},
    {"role": "user", "content": "Hello"},
]

# tokenize=False shows the exact string that will reach the model
print(tok.apply_chat_template(messages, tokenize=False, add_generation_prompt=True))

Compare that output character by character against the format on the model card. Three checks are enough: role tokens present, a token opening the assistant turn at the end, and no duplicated beginning-of-sequence token. The llama.cpp server selects a template from model metadata and lets you override it, so on a server setup the order is to confirm from the startup log which template was chosen.

4. Sampling parameters - defaults differ per runtime

This is the most underrated layer. People compare models when what they actually changed was the runtime. Simply putting the documented defaults side by side makes the point.

The last three rows hurt most in practice.

  • A repetition penalty cuts both ways. With it on, looping text gets rarer, but tokens that legitimately need to repeat get suppressed too. Table syntax, indentation, recurring key names and code that reuses the same identifier are the usual victims
  • The penalty window differs as well. A setting that looks at only the last few dozen tokens will not catch paragraph-level repetition, while applying it across the whole sequence distorts phrasing in long documents
  • Default context length differs. One side uses whatever the model declares, the other documents 2048. If you pasted a long document and felt the model could not remember the beginning, look at that number before you blame the model

One more thing. The Transformers family follows the generation config file shipped with the model. If the model author set recommended sampling values, those apply. Runtimes that do not read that file apply their own defaults instead. That is often why the same weights feel like a different personality under two tools.

One practical rule. Whatever you are comparing, set sampling explicitly. Leave it to defaults and your comparison becomes void the moment you switch tools. For accuracy-sensitive work such as code, structured output and tool calls, start from low randomness with the repetition penalty off, and raise variety only for the tasks that need it, such as writing.

5. The empty slot where a system prompt should be

The default state of a local setup is an empty system prompt. Yet the commercial chat service people compare against always answers with a long, carefully engineered system prompt attached. The gap that opens here is not model capability. It is the presence or absence of instructions.

A system prompt does three concrete things.

  • It pins the format. Length, tone, whether to use lists or tables, whether code blocks carry a language tag - all decided here
  • It supplies a rule for the unknown. Whether the single line telling the model to say so when it is not sure exists or not changes how much hallucination you perceive
  • It anchors task context at the front. The system message stays at the head of the sequence as the conversation grows, so it outlasts instructions that fade in the middle

That said, models handle the system role differently. Some were trained with it as a separate role; others use a template that folds it into the first user message. So the procedure from the previous section applies here too - confirm what form it took in the final string.

6. Quantization - the damage lands at close calls, not on averages

Which quantization to pick is covered in the running guide, so here only the part that connects to perceived quality. The point is that quantization does not shave ability evenly. The same structure appears as in what a model loses when it gets smaller: averages hold while the tail is cut first.

Also, weight quantization and KV cache quantization behave differently. Blur the two together and your diagnosis goes wrong.

  • Weight quantization is static. The error spreads evenly across the model and stays constant regardless of context length, which is why short queries rarely expose it
  • KV cache quantization accumulates. Previously computed keys and values are stored at low precision and referenced continuously, so error piles up as context grows. It is the prime suspect for the pattern where early turns are fine and later ones degrade
  • Sensitivity varies by layer. The vLLM documentation notes that some attention layers, such as sliding-window ones, are more sensitive to cache quantization, and provides an option to keep specific layers at the original data type. Squeezing everything is not the only choice
  • Implementations widen the blast radius. The same documentation states that with a particular attention backend, an 8-bit cache also causes queries to be processed at low precision, and it recommends dataset-based calibration over the default of setting all scales to 1.0. The effect can reach further than the option name suggests

So the order is this. If memory is tight, cut context length first, then weight quantization, and touch the KV cache last. Squeezing the cache threatens long context and tool calls at once, and those two are exactly what a local agent needs most.

7. The context length trap - longer is not better

Maxing out the context window costs nothing is a common misconception. In reality three costs rise at once.

  • Memory. The KV cache scales with context length. Quadruple the window and you quadruple the cache. On a machine where the model barely fit, that alone starts swapping
  • Speed. A longer prompt raises time to first token and slows the decoding that follows. In interactive use you feel it as latency first
  • Accuracy. Length alone guarantees nothing. Lost in the Middle, published by Liu and colleagues in TACL 2023, reports that performance is highest when the relevant information sits at the beginning or the end of the input and degrades significantly when it sits in the middle of a long context. The paper notes the same tendency in models built specifically for long contexts

The trap runs the other way too. A window smaller than the actual input silently truncates the front. No error appears, and the model answers from what remains. To the user it looks like a dumb model that cannot read long documents.

So the practical rule is this. Set the window a little above your real maximum input, but within what the machine can carry. And before widening it, look first at reducing what you put in. Put critical instructions at the very front or the very end, and include only reference material that is actually relevant.

8. The comparison is unfair - model against product, not model against model

If a commercial service still looks better after you align every setting, the last thing to examine is what you are comparing against. A chat service in a browser is not a model. It is a product wrapped around a model.

ComponentCommercial chat serviceDefault local setup
Model selectionRoutes to different models or reasoning budgets by query typeOne set of weights handles everything
ToolsSearch, code execution and file reading wired in by defaultYou have to attach them yourself
System promptA long, engineered one always appliedUsually empty
Post-processingFormat repair, safety filters, retries on failureNone
Context managementSummarization and selection manage the windowOverflow gets truncated
SamplingTuned per taskRuntime defaults

Read that table and it becomes clear what the I put the same question into both experiment was really measuring. Most of it is a pipeline difference, not a model difference. If the gap widens sharply on questions that need fact checking, the other side is probably using search.

To make it fair there are two directions: give both sides the same things, or take the same things away from both. Whatever difference survives that is the real model difference.

9. How to evaluate properly - a small evaluation set of your own

What the original author stressed was methodology as well. Do not judge from three prompts at temperature zero, and do not trust published metrics without their conditions. The alternative is not elaborate.

9.1 Four things to hold fixed

  • The same prompt. Read it from a file instead of retyping. A single space changes the token sequence
  • The same chat template. Save the final string and compare it on every run
  • The same sampling. Set it explicitly. If you use randomness, fix the seed or run several times and look at the spread
  • The same context length. Different window sizes change whether truncation happens, which invalidates the comparison outright

9.2 What belongs in the set

Twenty to fifty items is enough. What matters is not the count but whether they came from work you actually do. The goal is to catch what standard benchmarks miss, so build it around the failure types above.

  • Requests that need tool calls. They fail on the smallest format deviation, so template and cache precision problems surface first here
  • Requests that read long input. Deliberately place the answer in the middle of a document to test context handling
  • Multi-turn requests with a strict format. Force answers into a fixed structure to expose repetition penalty and sampling effects. Single-turn questions alone will miss template problems
  • Requests the model should decline. See whether it says it does not know, or invents an answer with no basis

Keep scoring light. Making roughly half the items machine checkable, such as expected-string presence or format validity, makes repeated runs easy, and marking the rest as pass or fail by hand is enough. Running under identical conditions every time matters far more than a precise score.

10. Where local still wins

Read this far and local looks like the high-effort option. It is. But there are places where what you get for that effort is unambiguous.

  • Data does not leave. For material that contracts forbid exporting, logs containing personal data, or unreleased code, transmission itself is disqualifying, and local is the only option regardless of quality gaps
  • Cost does not scale with usage. In automation that repeats the same task thousands of times a day, per-call billing accumulates fast. Converting that into electricity and depreciation is more predictable
  • It works offline with stable latency. It keeps running on air-gapped networks and through third-party outages, and without network round trips or queues the variance in response time is small
  • The version is pinned. Downloaded weights are the same today as yesterday. For work that must be reproducible, that alone is a feature

The other side deserves a note too. Hardest-tier reasoning, queries needing current information, and heavy multimodal work remain easier on commercial services. Much of that, though, is a tools and pipeline difference that narrows once you attach the same tools locally. The realistic setup is not either-or but division of labor by task.

11. What could not be verified

Collected here are the items this article could not support with a source.

  • The specific figures from the originating experiment, and any ranking among quantization formats. It is a forum post by a single experimenter with no peer review. The values came out of one particular hardware, driver and software combination and do not transfer, so only direction and structure were carried over. No cross-verified material was found that would let anyone declare one format better than another
  • How current the runtime defaults are. The table reproduces what each project documents as of August 2026. These values change across releases, so verify them on the version you actually have installed before relying on them
  • The internals of commercial services. The real structure of routing and post-processing is not published. The table describes only what a user can observe from the outside

12. Conclusion - a checklist in order

When the model feels dumb, work through this order before swapping models. Most cases end near the top, because the higher an item sits, the cheaper it is and the likelier it is the cause.

  1. Print the final input string. Role tokens present, generation prompt attached, no duplicated beginning-of-sequence token
  2. Check the context length setting. Whether a default smaller than your real input is truncating the front
  3. Set sampling explicitly. In particular whether a repetition penalty is on, and whether variety settings are applied to accuracy-critical tasks
  4. Add a system prompt. Three lines on format, length and handling the unknown already shift the experience
  5. Roll back precision settings. If quality degrades from the later turns on, the KV cache is the prime suspect. Check the weight quantization tag on your file as well
  6. Only then change models. A comparison is meaningful only after every step above

To summarize: weights fix nothing beyond a probability distribution. How that distribution is fed a sentence and turned into tokens is decided by the template, the sampling, the precision and the context. Which means the phrase the same model guarantees far less than it sounds like it does.

If you pick only one thing to do today, make it the first item. Print the final string that reaches the model in your current setup. It ends there more often than you would expect.
