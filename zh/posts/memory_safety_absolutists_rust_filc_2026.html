内存安全绝对主义者 - Rust 与 Fil-C 之争

全面重写还是渐进加固，如何按威胁模型与代码寿命作判断

2026年7月27日 开发/基础设施

引言：围绕安全的纯洁性竞赛

内存安全的讨论正朝着奇怪的方向漂移。它的起点是一个极其务实的问题：为什么用 C 和 C++ 写的代码三十年来一直重复同一类漏洞？而社区当下的争论性质不同。有人主张，Rust 既然带着 unsafe 这个逃生口，就不是真正的安全语言，因此只有像 Fil-C 这样在运行时抓住每一次违规的实现才算正统。最近引发讨论的《内存安全绝对主义者》一文正是直指这种姿态。其要点很简单：如果你猛烈抨击 Rust 的逃生口，却对完全不做检查就能编译的普通 C 与 C++ 不施加同等标准，那么你的尺度关心的不是安全，而是阵营。

本文会同时审视这一批评成立与不成立的部分，但从数字而非感想出发。内存安全漏洞的实际占比是多少？Fil-C 以什么为代价换取安全？Rust 的 unsafe 在真实生态中用得有多广？C++ 阵营给出的安全配置方案走到了哪一步？在用公开资料核实这些之后，再以遗留 C 层格外厚重的韩国嵌入式、通信与金融核心系统为具体案例，考察现场究竟什么可行。先给结论：答案不是某个语言的名字，而是这段代码接收什么输入，以及它还要再活多少年。

1. 先看数字再谈立场 - 内存安全问题究竟有多大

这场争论中被引用最多的数字是百分之七十。它不是感觉，而是来自两家公司各自的统计，并且彼此独立地得到了相近的数值，这正是它可信的原因。

1.1 公开的主要统计

  • 微软：其分配 CVE 并修复的安全漏洞中约百分之七十属于内存安全问题，这是对十余年安全更新的汇总。
  • 谷歌 Chromium：对 2015 年以来在稳定版中修复的912 个高危与严重级别缺陷的分析显示，约百分之七十是内存管理与安全类缺陷，其中约一半为释放后使用(use-after-free)。
  • 安卓：内存安全漏洞占比从2019 年的百分之七十六降到 2024 年的约百分之二十四，此后据报已跌破百分之二十。
  • 安卓的 Rust 代码：在约五百万行的规模上，漏洞密度估计为每百万行 0.2 个。与同一组织 C 和 C++ 的历史密度每百万行约 1,000 个相比，差距在一千倍以上。
  • 附带效果：同一份报告提到，Rust 相关变更的回滚率低四倍，代码评审耗时少百分之二十五，与安全会拖慢开发速度的常识判断恰好相反。

1.2 这些数字说了什么，又没说什么

这里需要一点谨慎。安卓 0.2 对 1,000 的比较并非同条件实验。用 Rust 新写的代码多为新功能，而 C 与 C++ 那一侧是数十年来被攻击者集中照射的旧代码。新代码相对被挖掘不足的可能性、模块风险等级的差异、研究投入的偏斜，都混在其中。即便如此，三个数量级的倍率也很难仅用测量偏差解释。而安卓从百分之七十六降到百分之二十以下的走势线揭示了一个事实：占比的骤降并不需要把既有代码全部重写。这一点正是后文实务策略的核心依据。

2. Fil-C 是什么 - 不离开 C 也让 C 变安全

2.1 工作原理：InvisiCaps 与并发 GC

Fil-C 自称是一个「近乎狂热地保持兼容的内存安全 C 与 C++ 实现」。其核心是名为 InvisiCaps 的指针模型：把指针拆成程序可见的地址值与不可见的能力，将边界与生命周期信息保存在独立的元数据中。程序照样可以像操作整数那样摆弄指针，但在真正解引用时会与隐藏的能力比对，一旦越界就以 panic 立即中止。生命周期由并发、并行的垃圾回收器管理，只有在指向某对象的所有指针都消失后才回收内存，因此释放后使用在原理上无法成立。线程只在诸如回边这样的安全点停下，信号处理函数也在安全点执行，从而不会与回收发生冲突。

就成熟度而言它并非玩具。官方站点列出的移植包括 CPython、OpenSSH、GNU Emacs 和 Wayland，还有以 Pizlix 为名、用 Fil-C 构建的整套 Linux 用户空间。截至 2026 年 7 月初已发布 0.681 版本，开发相当活跃。当然，版本号仍以 0 开头这一点也应一并读入。

2.2 代价是什么

安全并不免费。Fil-C 付出的代价很明确，而这些代价直接决定了它的适用范围。

  • 执行速度：指针追逐较多的代码大致减速一到六倍，最差情况在四倍上下。反过来，像 shell(Bash 5.2.32)这类指针密度低的程序，实测几乎感觉不到差别。也就是说不同负载之间的波动极大。
  • 内存占用：含指针的结构体会带上能力元数据，实际占用两倍空间。在内存紧张的嵌入式场景，仅此一项就足以出局。
  • ABI 不兼容：产物无法与普通编译器生成的目标文件链接，意味着整棵依赖树都要重新构建。只要中间夹着一个只提供二进制的商业库，路就在那里断了。
  • 跨语言链接：目前不支持与 Rust 链接，混合技术栈下的边界设计会变得棘手。
  • GC 本身：对硬实时、内核与驱动、有抖动预算的信号路径而言，垃圾回收器的存在本身就是排除理由。

简而言之，Fil-C 的设计是保住既有代码，改为支付运行时资源。这笔交换成立的领域确实存在，不成立的领域同样确实存在。

3. Rust 的安全模型与 unsafe 的现实

3.1 所有权与借用检查器

Rust 从相反方向切入。每个值只有一个所有者，引用要么是一个可变引用，要么是多个只读引用，二者不可同时存在，这一规则在编译期被强制。凭借这些规则，释放后使用、双重释放和数据竞争在程序运行之前就被筛掉。不需要运行时检查和 GC，性能特性因此接近 C。代价则改由人来支付。既有 C 代码那种随性的别名用法无法原样迁移，实际操作中往往要从数据结构设计重来。

3.2 同一个缺陷，三种结局

拿一处释放后使用来看三种路线如何分野，性质差异便一目了然。

/* 标准 C：能编译，通常也能跑，但成了攻击面 */
char *buf = malloc(16);
free(buf);
strcpy(buf, "hi");   /* 向已释放内存写入 - 可能演变为任意代码执行 */
/* Fil-C：源码原样不动。运行中以 panic 立即中止 */
/* 编译器核对指针的能力并拦截无效访问 */
// Rust：根本无法通过编译
let buf = vec![0u8; 16];
drop(buf);
// buf[0] = 1;  // error[E0382]: borrow of moved value: `buf`

三种结局的差别在于何时付费。C 一直拖着不付，等事故发生时一次付清全款。Fil-C 每次执行都付一点。Rust 在开发期一次性付清。哪种方式更划算，取决于这套软件的执行频率、性能余量和剩余寿命。这正是它属于情境判断而非语言优劣排序的原因。

3.3 unsafe 是漏洞还是审计面

绝对主义者的主攻点是 unsafe，而这一批评并非全然无据。确有研究表明，unsafe 内部写错的代码可能制造出在安全代码中显现的缺陷，也有调查梳理了知名 crate 中的大量安全公告与 CVE。但需要有规模感。据 Rust 基金会的报告，crates.io 上使用 unsafe 关键字的 crate 约占百分之二十，其中相当部分用于与 C 互操作，按代码量计则估计在百分之一上下。

这里获得的实质收益不是安全的有无，而是审计面的大小。在 C 代码库中，每一行都可能是 unsafe。在 Rust 中，需要审视的位置在语法上被标注出来并被收窄。在一百万行中集中审查一万行，与审查全部一百万行，从组织角度看是完全不同的任务。「既然有逃生口就毫无意义」这一论断，恰恰因为抹掉了这个差别而在逻辑上站不住。

4. 「绝对主义」批评的要旨 - 全面重写的要求现实吗

原文作者的批评可以读出两条线。第一条是双重标准：把 Rust 的 unsafe 当作致命缺陷，却对完全不做检查就能编译的普通 C 与 C++ 不施以同等力度的指责，那这套标准关乎归属而非安全。第二条是替代方案的不对称：若要把 Fil-C 立为唯一正解，就必须回答 Fil-C 无法覆盖的领域——不能放 GC、不能改 ABI、无法吸收四倍减速的那些地方——由什么来填。眼下填在那个位置上的恰恰是 Rust。

我大体认同这一批评，但要补一句。绝对主义并非只存在于反 Rust 一侧。把所有 C 都用 Rust 重写的要求，同样是一种绝对主义。重写数百万行经过验证的代码，不只是学习新语言的成本问题，更是把数十年在现场磨出来的异常处理与隐性需求整块丢掉的问题。重写过程中很可能出现内存缺陷消失、逻辑缺陷新增的置换。值得注意的是，安卓真正取得的成果来自新代码一律用安全语言的原则，而非重写运动。从百分之七十六降到百分之二十以下的这条曲线，是掐断新增漏洞来源画出来的，不是靠抹掉旧代码。

5. Rust 重写 vs Fil-C 渐进加固 - 成本与风险

把两条路径放在同一组坐标上比较，选择标准会清晰得多。以下按组织实际要支付的科目整理。

项目Rust 重写Fil-C 重新编译保留 C ＋ 加固
前期投入非常高(设计、人力、周期)低(基本是构建流水线更换)最低
运行时开销基本没有一到六倍，最差约四倍没有(加固选项下为个位数百分比)
内存占用与 C 相当含指针结构体最多两倍与 C 相当
空间安全(边界)有保证有保证(运行时 panic)部分
时间安全(生命周期)有保证有保证(GC)无保证
既有资产复用低(实质是新写)高(多数无需改动即可编译)最高
二进制库兼容可通过 FFI不可(必须整体重建)可以
硬实时与内核适配适合不适合(GC)适合

人才获取难度高低(沿用现有 C 人员)低

表格显示，两个选项解决的是不重叠的问题。Fil-C 最大的长处不是性能，而是人员与资产的连续性：既有的 C 开发者留下来，代码也留下来，唯独风险等级下降。反过来，Rust 最大的长处是安全性在运行时几乎免费——付一次之后，此后每次执行都不再叠加成本。因此，越是要长期存活、执行频次又高的核心组件，Rust 一侧的算术越有利；越是剩余寿命不长或性能余量充足的代码，Fil-C 一侧的算术越有利。

6. C/C++ 阵营的回应 - 安全配置与 C++26

C++ 标准化阵营没有选择放弃语言，而是走上安全配置(profiles)这条路。主张另造一套安全方言的「Safe C++」提案，与可对既有代码渐进施加的「配置」提案彼此竞争，表决结果为配置赞成 19 票、Safe C++ 赞成 9 票、两者皆可 11 票、中立 6 票，配置一方胜出并成为方向。2026 年 3 月伦敦克罗伊登会议上 C++26 的技术工作宣告完成，与反射、契约一同纳入了无需重写即可施加的安全加固。继续削减未定义行为的工作和更多配置提案的讨论正瞄准 C++29。苹果用配置式的「超集之子集」方法加固了 WebKit 四百万行以上代码并取得成效，也被作为例证提出。

不过这条路的局限也应当坦率面对。配置主要在空间安全即边界检查上发力，而以释放后使用为代表的时间安全依然是难得多的问题。谷歌在公开表态中明确指出，它没有看到 C++ 演化为包含时间安全在内的严格内存安全语言的现实路径。把这一点与前面 Chromium 统计中内存缺陷有一半是释放后使用叠加起来看，配置无法覆盖的领域恰恰可能是更疼的那一半。即便如此，配置仍有一项决定性优势：今天就能施加于已有代码。现在就打开一项挡住一半问题的措施，通常好过五年后才启动一个挡住全部问题的计划。

7. 监管这个变量 - 建议正在变成采购条款

这场争论已不只是口味问题。美国白宫国家网络总监办公室(ONCD)在 2024 年 2 月的报告《Back to the Building Blocks》中，把编程语言本身点名为安全的基础构件；网络安全和基础设施安全局(CISA)继 2023 年联合指南《内存安全路线图的必要性》之后，又在产品安全相关文件中要求软件制造商：

  • 在 2026 年 1 月 1 日前公布内存安全路线图。该时点已过，如今进入的是核验履行情况的阶段。
  • 路线图应优先处理网络接触面代码与密码运算等高优先级组件。
  • 不能停留在声明，而要证明它带来实质性的、按优先级推进的漏洞削减。
  • 已公布在 2030 年 1 月 1 日之前停止支持的产品不在适用范围内。
  • CISA 自己也承认迁移需要投入相当的时间与资源，并建议短期缓解与长期消除并行。

值得注意的是最后两条。连监管机构都没有要求全面重写，它要求的只是优先级和期限。相比这场绝对主义论战的两个极端，监管文本反而更务实。对出口型企业而言这也并不遥远：向美国公共部门与关键基础设施供货的通信设备、安全设备、汽车零部件和工业控制软件，很快会在采购审查中被问及是否存在这样一份路线图。对于已经在按 MISRA C、ISO 26262、IEC 62443 等既有安全与信息安全规范作业的组织来说，把内存安全路线图叠加到现有文档体系之上并不困难。

8. 遗留厚重的现场实务 - 以韩国为例

8.1 三个截然不同的战场

在韩国产业结构中，C 与 C++ 代码堆积得最厚的大致有三处。它们的约束条件完全不同，套用同一张药方必然失败。

  • 嵌入式与汽车：内存从数百 KB 到数 MB，硬实时约束，功能安全认证负担。一旦挂上 GC，认证论证就会动摇，因此 Fil-C 实际被排除。现实路径是强化 MISRA 系规则、扩大静态分析，以及仅限新模块引入 Rust。
  • 通信设备与网络软件：报文解析器和协议状态机直接接收完全不可信的输入，是三者中威胁暴露最高的位置。但性能要求因子域而异：控制面完全值得用安全语言重写，数据面热路径依然棘手。
  • 金融核心与对账处理：报文解析与批处理居多，因账本一致性而极度回避重写风险。然而夜间批处理的性能余量相对宽裕。这既是 Fil-C 式方案在原理上最契合的位置，也是最容易因商业二进制依赖而卡在 ABI 上的位置。

8.2 人力供给才是真正的瓶颈

真正让组织停摆的是人，而不是技术可行性。国内系统编程人才本就稀薄，能在生产级水平驾驭 Rust 的更少。在系统集成与受托开发占比很高的结构里，还有一堵现实的墙：重写期间的功能冻结发包方难以接受。从这个角度看，Fil-C 这类方案的吸引力不在性能，而在不必换人。反之，若决定引入 Rust，失败率最低的形态不是全面切换，而是选定一个新模块，让两三名工程师用六个月同时完成学习与交付。还要一并记住，前面引用的回滚率低四倍、评审时间少百分之二十五，都是越过学习曲线之后才会出现的指标。

9. 性能开销究竟能承受到哪一步

「慢四倍」这句话本身构不成判断依据，因为四倍致命的场景与四倍毫无影响的场景在同一个组织内并存。按领域拆分可承受的幅度，选择自然就收窄了。

领域可承受的开销决定性约束现实的首选
车载 ECU、PLC 等硬实时实际为百分之零抖动、认证、内存上限静态分析＋新模块用 Rust
内核与设备驱动个位数百分比不允许 GCRust(或保留 C 并加固)
浏览器与渲染引擎百分之十左右用户可感知性能Rust＋沙箱＋安全配置
网络数据面热路径百分之十到二十吞吐与延迟Rust 重写或隔离
控制面与管理守护进程可到两倍运行稳定性Rust 或 Fil-C
文件解析器、编解码器、转换器可到二至四倍暴露于不可信输入Fil-C 的即时候选
夜间批处理与内部工具四倍以上亦可批处理时间窗Fil-C
构建工具与命令行工具多数情况感知不到几乎没有Fil-C

这张表里值得留意的是：威胁暴露高的位置与性能余量大的位置有相当大的重叠。文件解析器、图像与文档转换器、日志处理器这类直接啃外部数据的代码，通常并不在热路径上。这块交集正是 Fil-C 式方案的最佳切入点。与其争论要不要全面采用，不如先把这块交集重新编译一遍，那是生产力高得多的第一步。

10. 代替结论的判断框架 - 不看阵营，看威胁模型与代码寿命

把上面的内容压缩成一次实务决策，问题只剩四个。语言的名字排在这四个之后。

  1. 这段代码是否直接接收不可信输入？若是，它就是第一优先级。按网络边界、文件解析器、密码运算、用户上传处理的顺序列出清单。
  2. 这段代码还要再活多少年？若三年内计划下线，重写投资永远收不回来，用加固选项与隔离撑住更为合理；若还要活十年以上，重写的算术才开始成立。
  3. 性能与内存还有多少余量？若余量在两倍以上且所有依赖都能拿到源码，Fil-C 式方案就是最便宜的安全；若毫无余量，把这个选项从清单上划掉。
  4. 能不能换人？若团队既没有学习 Rust 的余力，也没有招聘的空间，那么全面转向 Rust 的计划只会停留在文档里。这种情况下，收窄到单个新模块的试点是唯一能运转的形态。

答完这四问，多数组织的结论会收敛成相似的形状：新写的代码用安全语言，暴露在威胁下的旧代码靠重新编译或隔离，其余的原样保留并加以监控。安卓从百分之七十六走到百分之二十以下的路径，正是这个形状。

结论：纯洁性不是指标

《内存安全绝对主义者》指出的双重标准是成立的。以 unsafe 为由判 Rust 出局，却默许毫无检查地运行的 C 与 C++，那这套标准衡量的是归属而非安全。与此同时，反方向的绝对主义——要求把所有 C 立刻用 Rust 重写——在现场同样无法运转。两个阵营共享同一个错误：用二分法处理安全，而不看这段代码所处的条件。

对实务者更有用的态度要干燥得多。Fil-C 是在保留既有资产与人员的前提下，付出运行时资源以同时换取时间与空间安全的工具，在能承担 ABI 重建与 GC 的位置上非常有力。Rust 是把成本集中在开发期、让运行时保持空闲的工具，在代码寿命长、执行频繁、性能没有余量的位置上占优。C++ 安全配置是今天就能打开的半套防御，而这半套远胜于零。三者与其说是竞争关系，不如说是为不同约束组合准备的装备。截至 2026 年 7 月，连监管机构谈的也只是优先级与期限，而不是全面重写。与其把时间花在挑选阵营旗帜上，不如用来列一张清单：自己的哪些组件接收不可信输入，各自还剩多少年寿命——那张清单能减少的漏洞，比参与任何一场论战都多。
