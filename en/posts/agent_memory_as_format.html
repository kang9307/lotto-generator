Memory Built as a Pipeline Stays Locked In - What the Proposal to Make Agent Memory a File Format Actually Touches

Memory tied to one pipeline does not follow you when you switch tools. What a format changes, and what stays exactly as hard as before

Sep 3, 2026 Dev & Infra

When people discuss how to give an agent memory, the discussion almost always drifts towards process. What to extract from the conversation, how to summarise it, where to embed it, in what order to search and bring it back. That list is all verbs. And there is one thing the list never asks head-on. What shape does the resulting memory actually have? Is it a file, a row in a database, or the internal state of somebody's service?

This piece does not compare tools. It does not argue about why memory is needed either. There is one axis. Should memory be represented as a process, or as a stored format? The only question here is what that choice decides, and what it leaves undecided.

This piece rests on specification documents and official documentation available as of September 2026. The format proposal discussed here describes itself as a draft, and nothing below is an endorsement or a criticism of any particular product or company.

The trigger - a file format, not a pipeline

In early September 2026 an English-language post circulated through a Korean developer community and put this discussion in exactly the right place. It is titled Agent memory as a file format, and one of its section headings is even blunter: memory should be a data format, not a multi-stage pipeline.

The piece opens with an old line from Frederick Brooks. Show me your flowcharts and conceal your tables and I shall continue to be mystified; show me your tables and I will not usually need your flowcharts, because they will be obvious. That epigraph is the whole argument in miniature. Settle the data structure and the procedure follows from it.

One thing is worth stating immediately. This proposal is not a settled standard. The specification document says of itself that it is draft 0.1, dated August 2026. So this piece should be read not as an account of what has been decided but as an account of what this direction touches.

What the original piece actually argues

The author divides existing memory systems into three kinds and criticises each. The first are the ones that deliberately tie you into a specific harness. The second, in his own words, are ludicrously complicated: he cites a configuration that needs a vector extension, a graph database and an LLM of its own just to decide what is worth remembering. The third is what he calls the High Modernist variety, which imagines an idealised, rationalist form of memory made of graphs and logical propositions. His objection there is that slicing facts out this way strips them of context and leaves them isolated.

What the three have in common reduces to one sentence. They treat memory as a process. His alternative is the opposite side of that: memory, especially to a model, is much better represented as data.

The reasoning is clear enough. Retrieval pipelines are complicated because they are trying to make legacy human-authored documents readable to an agent, and agent memory was never that kind of artefact. At the moment a memory is formed, it is being written directly by an agent that can write prose. So no chunking, no enrichment, no double summarisation. The format that follows has only three pieces.

  • Markdown pages — one memory is one file
  • Optional YAML frontmatter — title, uuid, creation and update times, a summary
  • An optional SQLite vector index — a single file sitting alongside for semantic search

The canonical preservation form for the bundle is a zip. That is a choice made to keep exchange easy, and the specification is deliberately open about where the thing is served from: a local file, object storage or HTTP all qualify. Opened up, a bundle looks like this.

my-memories.memoryfield.zip
├── carbon-fibre-woks.md
├── finnish-bureaucracy-tips.md
├── wec-2026-season-notes.md
└── nomic-embed-text-v1.5.sqlite3

It is better not to attach claims the original does not make. The author does not say this solves the memory problem. As we will see, he leaves several items explicitly unresolved himself.

Build it as a process and the memory is trapped inside one implementation

The real problem with pipeline-built memory is not performance. It is ownership. The moment the summarisation rules live inside one vendor's prompt, the embeddings are computed with a model that vendor picked, and retrieval only runs over that vendor's index, the memory has become the internal state of that implementation. It looks like your memory, but the only portable artefact is the raw conversation log, and turning that log back into the same memory means running the same pipeline again.

This kind of lock-in is quiet. Nothing hurts until you try to switch. It surfaces on the day you switch, which happens to be the moment when months of material have piled up and moving costs the most. That is why the problem is always discovered late.

The other angle the original raises is practical. In a system with a lot of machinery, an agent has to navigate an interface maze to reach its goal. If the interface is large you are loading schema definitions into the context just to use it; if it is small there is not much you can do. Even when the balance is right, it is still somebody else's API, written without foreseeing your needs. This is where the author states his principle: more model, less mechanism.

AspectKept as a processKept as a format
What the memory really isInternal state of a service indexFiles in a directory
Switching toolsRe-run the raw logs to regenerateAnother tool opens the same files
Change historyOnly as much as the service exposesVersion control handles it as-is
AuditNeeds a separate way to query what was storedOpen it and read
DeletionA delete request and an actual delete are different eventsDelete the file
Fault tracingWork out which pipeline stage did itNarrows to a single file

What changes when it is a format

The biggest change is that other tools read the same files. Once a format is written down, implementations that read it appear without the original author writing them. That is not optimism, it is observation: every file format that lasted ended up that way.

After that come the human benefits. Text files diff. If it diffs, it can be reviewed; if it can be reviewed, a record survives of what went in, when, and why. When a bad memory gets written, tracing which session put it there turns from filing a support ticket into reading one line of a log.

  • You can read it — checking what was stored needs no separate query tool
  • You can compare it — what grew and what shrank between two points in time falls out directly
  • You can move it — compress and send. The only thing needing recomputation is the index, and the index can be rebuilt from the originals
  • You can delete a part of it — deleting per file is deleting per memory
  • Other tools can join in — a spell checker, a secret scanner, anything that attaches to text files

Worth noting: every item in that list follows from representing the thing as a file, not from this particular proposal. The same benefits fall out of any design that keeps memory in text files. Which is why the next section matters.

Conventions that already have this shape

The interesting part is that the field had already settled into this shape before anyone proposed it. Two examples stand out.

AGENTS.md describes itself as a simple, open format for guiding coding agents. The more precise framing is the sentence that follows: a README for agents, a dedicated and predictable place to put context and instructions. There are no required fields; it is just Markdown. As of September 2026 the site states that over 60,000 open-source projects use it, and that it is stewarded by the Agentic AI Foundation under the Linux Foundation.

CLAUDE.md has tighter rules. According to the official documentation, the file is looked up in the working directory and every directory above it, and the discovered files are concatenated rather than overriding one another. The order runs from the filesystem root down towards the working directory. Files in subdirectories are loaded on demand, when files in those directories are actually read. There is an import syntax, @path, that pulls in other files, to a maximum depth of four hops.

The same documentation confirms something else. The memory the tool accumulates on its own is also files. Inside a per-project directory sit one index called MEMORY.md and a set of topic Markdown files, and each file's frontmatter carries a type field naming its kind. The documentation is unambiguous about what those are: plain markdown you can edit or delete at any time.

So the proposal to keep memory as a file format is not a proposal to invent something new. It is closer to writing down as a format what is already being done. How tools handle session memory in practice is covered separately in CTX Explained - A Persistent Memory Tool for Claude Code Sessions and in Turning AI Coding Sessions' Ephemeral Context Into Project Memory.

A format is not free

Saying it is better as a format is easy. Looking at what actually has to be pinned down before something is a format makes it less light. The draft spec is a good exhibit. The head of a single page looks like this.

---
title: Carbon Fibre Woks
created: '2026-03-01T09:00:00Z'
updated: '2026-08-22T14:30:00Z'
uuid: 6aa615f0-486f-48a7-a210-ba4f5ff18c8b
summary: Thermal properties of carbon fibre cookware
---

Those quotes around the timestamps are not a stylistic preference. The specification writes down the reason: datetime fields must be quoted strings, because otherwise YAML 1.1 parsers coerce them into datetime objects. Defining a format means nailing down one thing like that after another.

What must be decidedWhat the draft decidedWhat is left over
Schematitle, uuid, created and updated are recommended; summary is optional. Effectively nothing is requiredLoose enough to be compatible, loose enough that two readers expect different things
VersionThe document declares itself draft 0.1, August 2026How a 0.2 reader should treat 0.1 files is not yet addressed
MergingLast-write-wins per page. Conditional writes may be supported by a server but must not be requiredIt can surface a conflict but will not resolve one
Size limitA page should not exceed 8,192 bytes, and an implementation need only handle the first 8,192 bytesHow to split anything longer is left to the writer
IdentityIf the stored and incoming uuid differ, a server should reject with 409The same fact written into two files is not caught

The right-hand column is the point of this section. Defining a format moves problems rather than removing them. What differs is that the place they move to is written down, and therefore arguable.

When two writers edit at once - merge rules are the real test

This is the question most often skipped in format discussions. What happens when two sessions edit the memory at the same time?

The draft's answer is honestly simple. Last-write-wins, per page. Surfacing conflicts through conditional writes, such as an If-Match on an ETag, is something a server may support but must not require. So the format provides a place to surface a conflict while declining to resolve one.

That is a choice, not a defect. But you have to know what the choice costs. For documents people write, last-write-wins is usually absorbed by two editors noticing each other. Where several agents run at once, nobody is there to notice. What one side just wrote disappears quietly.

  • Split the files finely and conflicts drop. In exchange one fact ends up scattered across several files
  • Keep files large and the facts stay together. In exchange the odds of two writers touching the same file rise
  • The 8,192-byte limit has already picked a side on that scale. It picks fine-grained splitting
  • Put it under version control and conflicts become visible. In exchange you acquire a new question: who resolves the merge
  • Pin page identity with a uuid and renaming a file still counts as the same memory. In exchange, files that carry no uuid break that guarantee

A format does not solve what is worth writing down

One thing needs to be stated plainly. Settling the representation leaves what is worth remembering exactly where it was. The format is the container; this is a question about the contents.

The author was asked this and answered as follows: irrelevant material is never surfaced by the semantic search anyway, so it does not apply; irrelevant memories take up space but do not hamper an agent; therefore insert liberally. The tip he attaches is practical — memories work best when they include citations, ideally as URLs, because that helps later passes strengthen them and helps an agent fact-check material that has gone stale or looks suspect.

The objections raised in the discussion ran the other way. People described turning memory features off entirely and keeping documents in a scratch folder that they continually tidy and delete, described a single wrong line contaminating everything downstream, and described memory becoming useless at scale as information goes stale and gets applied in the wrong context. The gap between merely takes up space and contaminates is not something a format settles.

Why choosing what to store is so hard is covered separately in Why Building Memory Turns Into a Program Analysis Engine, so it is not repeated here. The short version: to choose what to store you have to know what it means, and knowing what it means eventually requires analysis.

The reader's cost - selection becomes a process again

Here is the most honest part of the story. Once the files grow, you cannot put all of them into every call. So a stage that picks what to include becomes necessary, and that stage is selection, and selection is a process. An argument that started out reducing process ends up calling process back.

The loop is not wordplay; it shows up as numbers. Placing the published limits side by side gives this.

SubjectThe limit in forcePast it
A memory page in the draft specShould not exceed 8,192 bytesAn implementation need only handle the first 8,192 bytes
The instruction file CLAUDE.mdTarget under 200 lines per fileA file over 4 MiB is skipped
The auto memory index MEMORY.mdFirst 200 lines or 25KB, whichever comes firstContent beyond that is not loaded at session start
Topic memory filesNot loaded at startupRead with file tools when needed

That last row is the answer to this section. You do not load everything. The index is always loaded and the body is read when needed. And keeping that index short is itself summarisation and selection. The draft spec's goal of finishing retrieval in two tool calls — one search, one parallel read — is an answer to the same pressure. Walking links instead means N+1 calls for information N hops deep, with a few seconds attached to each call.

So the accurate sentence is not that pipelines are unnecessary. It is this. The pipeline remains, but its output lands outside the pipeline. Process does not vanish; the result of the process lands in an open format. Blur that distinction and the proposal becomes an overclaim. Where to put the semantic search is a decision of the same kind, and the draft picking a single SQLite file is a choice made to keep the index rebuildable from the originals. The options in general are laid out in What Should Vector Search Run On.

What the long-lived formats have in common

The useful reference points when proposing a new format are the configuration files that survived. Put four side by side and the commonalities are sharp.

FormatWhere it livesWhen layers overlap
.gitignoreThe same directory as the path, and every parent directoryPatterns in higher-level files are overridden by lower-level ones. Within one level the last matching pattern decides
.editorconfigThe directory of the opened file and every parent directoryFiles are read top to bottom and the most recently found rules take precedence. The search stops at root = true
package.jsonThe package rootname and version are required only if you publish. If you do not publish, both are optional
CLAUDE.mdThe working directory and every directory above itConcatenated rather than overriding, ordered from the root down towards the working directory
  • The location is fixed by convention. Nobody has to ask where to look
  • The layer-merging rule is written down. If who wins on overlap is vague, the format behaves differently in every tool
  • Required fields are kept to a minimum. Even package.json has none for a project that does not publish
  • There is an escape hatch. The root = true of .editorconfig is a switch that cuts off the upward search

That last item transfers directly to a memory format. Every format that adopted layered merging has a place that says stop looking upward from here. A memory format will need one too — when a work repository's memory and a personal memory overlap in the same tree — and the draft does not yet appear to contain its equivalent.

Using Markdown as the container

The reasons for putting memory in Markdown are clear. Models handle it well, people can read it, and the tooling is already everywhere. In the author's phrasing, models are accidentally very good at bash, at Markdown and at SQLite. That is a rare kind of advantage in format design: there is no new syntax to learn.

The downside is known too. Markdown has no single settled grammar. The CommonMark project summarises the situation: the canonical description of Markdown's syntax does not specify the syntax unambiguously, and because there was no unambiguous spec, implementations diverged considerably. So the same document renders differently on different systems.

Where that actually bites in a memory file is narrower than it sounds. Slight differences in emphasis or table rendering do not matter. What matters is the part a machine reads, such as the frontmatter. That is precisely where the draft nails down the quoting of dates. The part people read can be permissive; the part machines read cannot.

  • Keep the body as prose. Force structure onto it and the agent loses content while satisfying the shape
  • Define the machine-read fields narrowly and explicitly. A difference between parsers must not change a value
  • Give files meaningful names. Some things get filtered out from the listing alone, before any search runs

Can you delete something remembered wrongly?

This is where format versus process produces the largest difference in outcome. Memory will be wrong eventually. Sometimes because nobody said the fact had changed, sometimes because it was written down wrong to begin with. And then there is one question to ask. Can you find it and delete it?

With files the answer is short. Open it, read it, delete it. That is exactly how the official documentation describes auto memory — plain markdown you can edit or delete at any time, with a single command that opens the list. Auditing, correcting and deleting become the same action.

Inside a process those three split apart. There is one way to see what was stored, there may or may not be a way to correct it, and there is no means of confirming that a deletion response and an actual deletion are the same event. A system where wrong memories cannot be deleted gets worse over time. That is arithmetic rather than prediction: wrong entries accumulate, and if they cannot be removed they do not decrease.

As an aside, the separate question of whether a model produced an answer or regurgitated something it read is a different topic, handled in Telling Reasoning Apart From Recall.

When the memory files enter the repository

One reason files are good was that they go into version control. This section is the other side of that sentence. What is inside leaves with the commit.

What ends up in memory files? The names of the systems being worked on, internal hosts, what lives at which path, how deployment is done, and values pasted in by accident. A document a person writes gets at least a glance before committing. A memory written by an agent has no assigned reviewer.

The original author flags this direction too, and in strong terms — you must not share your context window with parties you do not trust, and that includes sharing it through memories. He writes that one reason the specification includes a static zip form is to let you manually review and pin, by hash, memoryfields you receive from others. And he concedes what remains: there is still no way for an agent to distinguish a good prompt from an evil one. The risk runs both ways. Outbound, your material leaks; inbound, sentences somebody else planted arrive.

  • Excluding the memory directory from version control by default and adding only what you mean to share is the safer posture
  • Per the official documentation, auto memory is machine-local and is not shared across machines. Sharing it means a person deliberately moving it
  • A memory bundle received from someone else is not trusted until it has been opened and read. Hash pinning guarantees you got the same thing, not that the thing is safe
  • Checking for credentials before committing takes a separate habit. The places they leak most often are collected in The Token Is Sitting in Your Remote URL

A convention is not a standard

Finally, the words need using accurately. Nothing covered in this piece can be called a standard.

  • The draft specification labels itself draft 0.1. Carrying a version number and being a standard are different things
  • AGENTS.md calls itself an open format, not a standard. A foundation stewarding it means governance now exists, not that standardisation is finished
  • CLAUDE.md is one tool's convention. As its documentation states explicitly, that tool reads CLAUDE.md and not AGENTS.md, and it directs you to bridge the two with an import or a symlink

That last item shows exactly where things stand. Two conventions with the same purpose do not read each other's files and expect a person to wire them together. A file convention published by one company becomes a de facto convention once widely used, but that state is different from several implementations having agreed to interoperate. Deciding on a file and building a consensus are separate jobs, and the hard one is always the second. The idea of writing an agent's behaviour down as a specification hits the same kind of wall, covered in How Do You Grade a Long-Running Agent.

Summary

Represent memory as a process and whoever owns the process owns the memory. Represent it as a format and whoever holds the files holds the memory. That is the skeleton of the discussion; everything else is the price attached to that decision.

What the format side buys is clear. It can be read, compared, moved and deleted. What it costs is equally clear. A schema has to be decided, a version managed, merge rules chosen, limits imposed. The draft's answers mostly lean towards defining the minimum and leaving the rest open, which is a choice that makes adoption easy and interoperability hard. There is no basis for calling that choice wrong. But you should know the price before picking it.

And two things remain that a format does not solve: what to write down, and what to include in each call. The second is selection, and selection is process again. So the accurate size of this proposal is this. Not removing the process, but leaving the process's output outside the process. That is a large enough difference on its own. Read as more than that, it will disappoint.

What I could not verify

  • The original discussion thread could not be opened directly. The server returned a too-many-requests response, so the discussion was only checked within the range reproduced on the Korean community page. Individual remarks could not be collated against their original wording, which is why no phrasing here is attributed to a named person
  • The actual adoption of this format — how many implementations read and write it — could not be established from any source I found. The specification document itself says it is draft 0.1
  • No comparative measurement showing that the format approach produces better outcomes than the process approach was found. The original does not present one either. What this piece assembles is a list of benefits and costs, not evidence of superiority
  • The project count for AGENTS.md is a figure the site states about itself, and no independently verified tally was found
  • How often different tools actually read and write the same memory files could not be established. That the documentation describes bridging the two conventions with an import or symlink is confirmed; how much that bridge is used is a separate question
