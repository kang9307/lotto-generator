inshellisense - Microsoft's Open-Source Bid to Bring IDE-Style Autocomplete to the Terminal

600+ CLI specs, 8 shells, one engine - how it differs from bash-completion and fzf

Jul 5, 2026 Dev & Infra

Introduction: Why the Terminal Lagged a Generation Behind the IDE

Everyone has hit that moment at a shell prompt: you can't remember what comes after a dash, or how many arguments a subcommand takes, so you fall back to --help for the tenth time that day. Editors solved this problem a long time ago - type a few letters of a function name and IntelliSense-style completion shows you its signature and description on the spot. The terminal shell you open several times a day, though, has been stuck a generation behind that experience.

inshellisense, an open-source Microsoft project still committing actively as of July 2026, is an attempt to close that gap - the name is a literal mashup of "shell" and "IntelliSense." It picked up 11 points on GeekNews, which is modest by buzz standards, but it's worth taking apart precisely because of how it approaches the old problem of terminal completion. Rather than paraphrase a press release, this post works from the actual GitHub repository, figures I verified directly through the GitHub API, and public technical material to lay out, from my own vantage point, what inshellisense does, how it works, and how it differs from established tools like bash-completion and fzf.

1. What Is inshellisense? Microsoft's Take on IDE-Style Completion

1.1 What the Tool Actually Does

inshellisense is an open-source project Microsoft published on GitHub in October 2023 that adds IDE-style autocomplete to terminal shells. It's written in TypeScript (over 87% of the codebase) and distributed under the MIT license. When I checked the GitHub API myself, the repository stood at 10,073 stars and 224 forks as of July 2026, and its most recent commit landed just days before I wrote this - it is still being actively maintained. Installation is a single line, npm install -g @microsoft/inshellisense, or via Homebrew (brew tap microsoft/inshellisense && brew install inshellisense), and running is starts a shell session with autocomplete switched on.

1.2 Eight Supported Shells, Fully Cross-Platform

Breadth of support is this project's most practical strength. Beyond Unix-family shells like bash, zsh, and fish, it covers PowerShell Core (pwsh), Windows PowerShell, an experimental cmd, and the less mainstream xonsh and nushell - eight shells in total. That means genuine cross-platform coverage spanning Windows, Linux, and macOS. The PowerShell and cmd support in particular turns out to be an important clue to this project's lineage, which I get into later.

1.3 Configuration and Customization

Configuration lives in a single file: .inshellisenserc in the home directory, or the XDG-compliant ~/.config/inshellisense/rc.toml. You can rebind the accept key (Tab by default), next/previous navigation (arrow keys), and dismiss (Escape); turn on useAliases to recognize bash/zsh aliases; enable useNerdFont for Nerd Font icons; and cap the candidate count with maxSuggestions. A published JSON schema even lets your editor autocomplete the config file itself - a nice touch of attention to detail.

2. How It Works - a PTY Wrapper and a Custom OSC Protocol

2.1 Wrapping the Shell Instead of Patching It

What's genuinely interesting about inshellisense is less what it shows you and more how it produces it. The tool doesn't patch or fork bash, zsh, or any other shell. Instead it uses the node-pty library to spawn the user's actual shell process inside a pseudo-terminal (PTY) and sits on top of it as a thin wrapper. To the user it looks exactly like the shell they always use; underneath, inshellisense is relaying input and output and layering an autocomplete UI on top at the right moment.

2.2 Tracking Prompt State With a Custom OSC Protocol

The hard part is that the wrapper needs to know whether a prompt has just started, whether a command was just submitted, and what the current working directory is - without parsing each shell's own, differing syntax. inshellisense solves this with shell-integration scripts, shipped per shell, that emit custom OSC (Operating System Command) escape sequences: prompt start (OSC 6973;PS), command submitted (OSC 6973;PE), and current directory (OSC 6973;CWD). Supporting eight very different shells from a single codebase is possible precisely because it leans on this thin, shared signaling convention instead of parsing each shell's native grammar.

2.3 A Spec-Driven Suggestion Engine - 600+ CLIs via withfig/autocomplete

The actual completion candidates come from an internal SuggestionManager that queries a spec-driven runtime as the user types. That runtime is built on @withfig/autocomplete, the open-source spec library originally created by Fig. inshellisense's package.json explicitly pins this dependency at version 2.675.0 - a version number that, on its own, hints at how densely this spec library has been updated over time. The 600-plus CLI specs it contains let inshellisense render subcommands, options, and argument types for tools like git, npm, docker, and kubectl - descriptions included - as an inline overlay just below the command line, using ANSI escape codes.

3. How Is This Different From Native Shell Completion? Comparing bash-completion and zsh

bash-completion, zsh's compinit/compdef, and fish's built-in completions directory have been around for a long time. But they fundamentally require completion scripts to be written and shipped separately per shell and per tool. It's common for a tool to have a solid bash completion script while its zsh or fish equivalent is thin or missing entirely - and even where a script exists, the result is usually a flat list of option names with nothing else.

inshellisense routes around that fragmentation differently. Rather than writing a separate completion script per shell, a single shared spec (in the withfig format) for, say, git or docker produces identical completions across all eight supported shells. Specs also carry type information - is this argument a file path, a branch name? - alongside a short description, which is what makes the IDE-style inline display possible in the first place.

4. How Does It Differ From fzf? A Complement, Not a Competitor

fzf keeps coming up in this conversation, but it genuinely operates at a different layer. fzf itself is a general-purpose fuzzy finder, and plugins that graft it onto shell completion, like fzf-tab, don't generate their own candidates. They take the candidate list the shell's existing completion system already produced and help you narrow it down quickly by fuzzy-matching.

inshellisense, by contrast, is itself a completion engine. It decides what to show as a candidate in the first place by consulting withfig specs, and it surfaces those inline as you type, with no trigger key required. fzf is a search layer that helps you find faster among candidates that already exist; inshellisense is a generation layer that defines, more richly, what candidates exist - and with what description - to begin with. That makes them complementary tools solving different problems rather than substitutes for one another.

5. Productivity and the Learning Curve - What Actually Gets Better

The practical payoff of this design is clear. git alone has dozens of subcommands and options, and heavily used CLIs like docker, kubectl, and gh aren't much different. Instead of digging through --help or a man page every time, having option names and a short description appear the instant you start typing measurably reduces cognitive load. That helps experienced users too, but it does the most for someone who is just starting to learn a given CLI tool - it flattens the learning curve. The interaction itself - Tab to accept, arrows to cycle - isn't far from what native shell completion already trained you to do, so there's no muscle memory to unlearn.

It's worth being equally clear that this benefit is bounded by spec coverage. For an internal, company-only CLI, or a brand-new tool that doesn't have a withfig spec yet, inshellisense has nothing extra to offer and simply falls back to whatever native completion the shell already provides.

6. Tracing the Roots - Fig's Sunset and the Spec Library's Second Life

6.1 What Fig Was

The @withfig/autocomplete spec format inshellisense depends on wasn't originally built by Microsoft. It traces back to Fig, a native macOS (later Linux-beta) terminal autocomplete app that emerged around 2020. Fig open-sourced its own spec format and 600-plus CLI specs (withfig/autocomplete, MIT license) so the community could contribute, and when I checked the API myself, that repository still holds 25,190 stars and 5,455 forks today.

6.2 The Amazon Acquisition, the Sunset, and the Windows-Shaped Gap

The Fig team joined Amazon in August 2023 and, by that November, had already ported its capabilities into Amazon CodeWhisperer (now Amazon Q Developer) for the command line. On September 1, 2024, the Fig app itself was fully sunset, with users directed to migrate to Amazon Q Developer. The interesting wrinkle is that Microsoft's inshellisense had already published its repository in October 2023 - before that sunset was even announced. In other words, inshellisense isn't a hastily assembled replacement born from Fig's demise; it's closer to a case where Fig's spec library, being independently open source, was available to be repurposed as a separate engine from the very start. And there's one clear gap Microsoft drove straight into: Fig never supported Windows at all. inshellisense reaching for pwsh, PowerShell, and cmd reads precisely as filling the space Fig's ecosystem never touched.

6.3 How Fresh Is the Spec Library, Really?

One caution is in order here. When I checked the GitHub API directly, the withfig/autocomplete repository - the source of the specs - last committed in May 2025, more than a year older than inshellisense's own most recent commit (June 2026). That's a reasonable signal that community contributions to the spec repository visibly slowed after the Fig app was sunset. inshellisense keeps consuming those specs as they're updated, but it also means completion quality for a genuinely new CLI tool ultimately hinges on how quickly that upstream repository absorbs a new spec for it.

7. Limits and Caveats

Listing only the upside would be dishonest. First, oversized CLIs like az, gcloud, and aws aren't officially supported because their specs would simply be too large - a real gap if your daily work is cloud infrastructure. Second, even the latest stable release from March 2026 is still versioned 0.0.1. Despite nearly three years of development since October 2023 and over ten thousand stars, the project itself still frames this as a pre-1.0, experimental stage. Third, as covered above, the pace of updates to the underlying spec repository has slowed. Fourth, because the whole design wraps the shell in a PTY, it's theoretically possible - though I haven't personally reproduced this - that unusual rendering issues could surface over an extremely slow network, a remote session, or certain terminal-multiplexer combinations; treat this as an architecturally plausible risk rather than a confirmed bug.

Conclusion: Is It Worth Trying Today?

inshellisense isn't so much a flashy new invention as it is Microsoft reassembling an already-proven idea - Fig's spec-driven autocomplete - into a cross-platform, open-source form. That reassembly matters for two reasons: it brings the same engine to Windows shells that Fig's ecosystem never reached, and it unifies an autocomplete experience that used to be scattered per shell into a single spec and a single engine.

As of July 2026, here are three criteria I'd use to decide whether it's worth trying today. First, if you regularly use option-heavy CLIs like git, docker, kubectl, or npm and find yourself reaching for --help often, a single npm install -g @microsoft/inshellisense should pay off immediately. Second, if your daily driver is a cloud CLI like az, gcloud, or aws, check the spec-support gap first before committing. Third, given the 0.0.1 version number and the pace of upstream spec updates, I'd lean toward testing it lightly in a local dev environment rather than leaning on it hard in a production workflow just yet. This case - an open-source spec asset outliving an acquisition and a product sunset to get a second life in another vendor's hands - looks like a pattern worth expecting to recur in the developer-tooling ecosystem.
