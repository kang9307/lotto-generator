What Was Released and the Author's Warning — Not Yet Ready for General Use

On October 5, 2026, Remo Senekowitsch published a short post on his blog titled "Flirt is now Open-Source", announcing that the source code of the code review tool Flirt is now available in the flirt/flirt repository on Codeberg. It was featured on GeekNews on October 6, 2026. The name Flirt was explained in the first introductory post from November 2025 as standing for "Fabulous, Legendary, Incremental Review Tool", and the description field of the repository reads "The Fabulous Legendary Incremental Review Tool".

In a paragraph added for people reading about it for the first time, the announcement introduces Flirt in three sentences. It is a review tool that optimizes for the "patch series" workflow, where the author continuously amends, rebases and force-pushes their changes; it remembers what the reviewer previously reviewed and shows the difference to the current state; and it is a local-first tool that is compatible with multiple backends such as GitHub and mailing lists. The very next paragraph is the warning.

Warning: I don't yet consider it ready for general use.
                    There are still plenty of bugs and missing features.
                    If you're not considering to become a contributor, I recommend being a little more patient.
                    I'll probably write another blog post when Flirt is ready for you.

The four sentences say that the tool is not yet considered ready for general use, that there are still plenty of bugs and missing features, that anyone not considering becoming a contributor is advised to be a little more patient, and that another blog post will probably follow when Flirt is ready. The word "probably" in the last sentence is the author's own qualifier. The warning in the repository README is worded differently but carries the same weight. The README says that Flirt is in very early development, that it is not ready for general use, and that people should only test it if they intend to contribute to it. It then adds that otherwise they will be disappointed by the user experience.

The rest of the announcement covers two things. One is an invitation to join the discussion on Zulip whether or not you are a potential contributor, with the note that using LLMs to write messages there is not allowed. The other is the Forgejo backend. Since Flirt is hosted on Codeberg, a Forgejo backend would let Flirt be used in the development of Flirt itself, but the author calls it a "hypothetical" backend and states that it does not exist yet. The announcement ends with the sentence that creating it is next up on his todo list.

The path to the release is recorded in date order in four posts on the same blog.

  • November 5, 2025 — development announced. The author wrote that Flirt is his master's thesis, that he would work on it alone and closed-source until the thesis was handed in, and that it would likely become open-source in August 2026. He said he had not decided on the license yet.
  • February 7, 2026 — progress on the Native Git backend. The post explained the planned feature set and the storage approach, and stated that this backend was not yet feature-complete.
  • August 15, 2026 — progress on the GitHub and mailing list backends. The author wrote that he had handed in the thesis on August 1 and was aiming to clean things up and open-source Flirt within one to two months. He already said then that the release would not be ready for users, but for people who can relate to his ideas for code review and want to shape the development of Flirt from early on.
  • October 5, 2026 — the release announcement. It contains the repository address, the warning quoted above, the Zulip invitation and the plan for a Forgejo backend.

The Problem — Reading the Same Code Again After a Force-Push

The README distinguishes the two workflows in a footnote. In the patch series workflow, commits are rewritten (git amend, rebase, force-push and so on) across review cycles; in the pull request workflow, new commits are added at the tip of a branch without touching existing ones. The November 2025 post explains this distinction at greater length.

What the author calls the "PR-workflow" is the approach popularized by GitHub with its pull request feature. It encourages code authors not to touch commits that were already reviewed and to only add new ones at the tip of their branch, so in any review cycle a reviewer only has to look at the diff between their last-reviewed commit and the most recent one. The author writes that this workflow is already "incremental", and that people who use it and are happy with it will not benefit as much from using Flirt.

The "patch-series-workflow" takes its name from the way it is practiced on mailing lists, but it is also practiced on GitHub, and the author gives the Jujutsu project as an example. Code authors amend, squash, fixup and rebase their commits continuously over each review cycle, working towards a high-quality commit history. The benefit the author cites is that, while searching for the source of a bug, a clean history makes it easier to identify and revert the commit which introduced it.

The cost is paid on the review side. Operations that modify existing commits change the hash of a commit, and afterwards it is not easy to determine how the commit was modified. The author's example runs as follows. A commit in a patch series changes 100 lines; 99 of them are good, but the first round of review suggests adding a missing semicolon on one line. The author of the change amends the existing commit so that an "add missing semicolon" commit does not end up in the project history. After a force-push (or a new patch series submission), reviewers are generally presented with the full 100-line diff again, because the tools do not understand that only one line changed since the last review. The author calls such tools "non-incremental" review tools.

The same post also gives the author's assessment of existing mitigations. In his account, the "changes since last review" button and the per-file "viewed" checkboxes in GitHub's pull request UI help but fail in many normal situations, and on the mailing list side there is git range-diff, which uses heuristics to compare two versions of a patch series. The problems the author points out and the corresponding responses on the Flirt side are collected below. Cells marked "idea" or "plan" reflect what the respective post said at the time it was written.

The target audience is limited as well. The author writes that people who use the patch-series-workflow, or who want to switch to it once its problems are solved, are the target audience of Flirt.

Pairing Commits by change-id — Interdiff and git range-diff

The solution rests on the change-id. As the November 2025 post defines it, the change-id is an alternative commit identifier that, in contrast to the commit hash, stays the same when a commit is amended or rebased. If a review tool remembers the commits that have already been reviewed together with their change-id, then once a new commit is proposed for review, the tool can pair it up with the previously reviewed commit that has the same change-id. Calculating the interdiff between these two commits leaves exactly those changes which the reviewer has not yet seen. The author describes this as the core feature of Flirt: it remembers what you reviewed and, by default, only shows you what changed in comparison to that.

The term comes from Austin Seipp's write-up "Why some of us like "interdiff" code review", which the README also links as further reading on the workflow. The author finds the word interdiff a little technical because it refers to how the idea is implemented, and writes that he chose the name "incremental code review" instead because it emphasises the practical benefit. Both names refer to the same thing.

Where the change-id comes from is subject to conditions.

  • Jujutsu is a Git-compatible version control system that sets the change-id in a custom commit header. Flirt can take advantage of this mechanism only if the commit author uses Jujutsu.
  • The README states that this feature relies on various kinds of metadata in commits, and that the best reliability is achieved if the commit author uses Jujutsu.
  • Fallback heuristics are used if there is no change-id header. The November 2025 post said that this fallback would conceptually be doing the same thing as git range-diff, although the heuristics would be much simpler at first.
  • The August 2026 post gives matching the subject line and the author as examples of such heuristics, and says that whatever Flirt ends up doing, it will have to be a heuristic given the current constraints.
  • The README notes that Gerrit also has this feature. The author writes that the review UI built into Gerrit already accomplishes incremental review using a change-id, while stating that he has never seriously used Gerrit himself.

The reason the author gives for building a new tool even though Gerrit exists is a platform problem. He does not control the code sharing platform of all the projects he works on, and his workplace and many of his favorite open-source projects use GitHub. The author writes that solving the fact that review tools are tied together with code sharing platforms is the second motivation for making Flirt.

The reference point for the fallback, git range-diff, is defined in the official Git documentation as follows. It is a command that shows the differences between two versions of a patch series, or more generally two commit ranges, ignoring merge commits. Its basis for finding pairs is similarity rather than an identifier.

  • Two commits are said to correspond when the diff between their patches (the author information, the commit message and the commit diff) is reasonably small compared to the size of the patches.
  • For each pair of commits across the two ranges, a "diff of diffs" is generated with three context lines, the number of lines in that diff is used as the cost, and the least-cost assignment is solved.
  • The option for adjusting cases where a large change is erroneously considered a total rewrite (the deletion of one commit and the addition of another) is --creation-factor, and its default is 60.
  • The output is meant for human readers. The documentation states that the output is subject to change and is not intended to be machine-readable.

In short, range-diff estimates pairs from how similar the patch contents are, whereas the change-id approach decides pairs by whether the identifier recorded in the commits is the same. This is why the Flirt README says that reliability varies depending on whether the commit author uses Jujutsu.

The State of the Four Backends — Forgejo Does Not Exist Yet

The README presents as its ideal that users of Flirt do not have to worry about where a particular project is hosted. Whether it is Forgejo, GitHub or a mailing list, the stated aim is to provide a seamless experience. It then lists four backends and the limitations each of them has, and their maturity is uneven.

Backend Status as stated in the README Behavior and constraints Additional statements
Forgejo Does not exist yet; "it will soon enough" Since Flirt is hosted on Codeberg, contributors will be able to dog-food this backend once it exists Announcement: creating it is next up on the todo list
Native Git A custom (unstable) format Review information lives in Git's object storage and can be pushed to and fetched from a remote using custom refs. Primarily useful for testing without talking to an external service It could be used in teams where everyone has push access, but the README says the unstable storage format and open questions about archival make this a bad idea for now
GitHub Probably the most used backend Because it is proprietary, contributions are not allowed to be blocked on GitHub support August 2026 post: implemented, but limited and buggy in several ways
Mailing list Only a proof-of-concept for now It does not send any emails; it only imports them into a local public-inbox server for testing Because git send-email does not preserve Jujutsu's change-id commit header, the primary feature is less reliable

According to the August 2026 post, the custom ref mechanism used for the Native Git backend is used for the other backends as well. The aim is to avoid hitting the GitHub API or downloading an email thread every time the user wants to do something; these refs stay local and are converted to API calls or emails when the user requests to sync with the backend. The constraints the same post describes for the GitHub backend are as follows.

  • The biggest issue the author names is that GitHub does not provide information about past force-pushes to a PR. As a result, Flirt cannot show the interdiff between all PR submissions.
  • The standard use case, the interdiff between the last-reviewed submission and the current one, works mostly fine, because the last-reviewed submission can be remembered locally.
  • Switching between workstations can break this. If a workstation has never observed the last-reviewed submission, it cannot easily get it from the GitHub API.
  • The API reports which exact commit hash any review comment was made on, which could be used to reconstruct past submissions. However, if there is a comment on a middle commit but none on the commit at the tip, the submission would only be partially reconstructed.
  • GitHub's review UI lets people comment on a diff, whereas Flirt adds comments on a specific state of the code base. Where to put comments made on the left side of the diff (the deleted lines) therefore remains an open problem, and the author writes that it will probably take some time to implement.

The mailing list backend is at an even earlier stage. The same post records the following.

  • Support is limited to projects that use public-inbox. The author writes that the Linux kernel and Git use public-inbox to host their mailing list archives.
  • git format-patch does not add the base commit information by default; users have to request it with the --base flag. The author points out that without this information there is no right answer to where the patches should be applied.
  • git format-patch does not preserve Jujutsu's change-id header. A README footnote says that a patch series to improve this was posted on the Git mailing list and was received relatively positively, with a different approach being requested, and that to the author's knowledge nothing has landed yet.
  • One basis for linking several versions of the same patch series is the version tag in the subject line, such as [PATCH v2 0/N], but the tag can be forgotten and the wording can change.
  • Flirt currently supports one format: the first email of each new version is sent as a reply to the first email of the previous version, so that all versions form one thread. The author writes that the Git project recommends this practice. The Linux kernel documentation he quotes says that, for a multi-patch series, it is generally best to avoid using In-Reply-To to link to older versions of the series.
  • Reading comments requires parsing plain text with nested quote markers into a structure, which has many edge cases, and the author writes that it works for very simple cases only.
  • Sending comments does not involve real emails either. Flirt constructs them and pipes them into public-inbox-mda in order to import them into a local testing instance of public-inbox.

The author drew the thread structure that Flirt supports as follows.

[PATCH v1 0/3] add feature
                    ├── [PATCH v1 1/3] implement feature
                    ├── [PATCH v1 2/3] test feature
                    ├── [PATCH v1 3/3] document feature
                    │
                    └── [PATCH v2 0/3] add feature
                        ├── [PATCH v2 1/3] implement feature
                        ├── [PATCH v2 2/3] test feature
                        ├── [PATCH v2 3/3] document feature
                        │
                        └── [PATCH v3 0/3] add feature
                            ├── [PATCH v3 1/3] implement feature
                            ├── [PATCH v3 2/3] test feature
                            └── [PATCH v3 3/3] document feature

Keeping Review Information in the Git Repository — A Custom Ref Instead of git-notes

The README describes the storage format of the Native Git backend only as "a custom (unstable) format". Its internals are explained in the February 2026 post, and what follows reflects that post at the time it was written.

The author looked at git-appraise as an earlier project built on the same idea. He introduces it as a project that stores code review information directly in the Git repository and whose main aim seems to be to define a standard so that different tools would be compatible with each other. When he examined whether its storage format would work for Flirt, the answer was no, and the reason was that git-appraise stores its information using git-notes.

  • When a commit is rewritten, for example using git-rebase, its hash changes. A note associated with the previous hash should then be associated with the new commit, but Git does not do this by default. It can be configured to, but that is opt-in.
  • The author writes that with Jujutsu, transferring git-notes when editing commits is not supported at all.
  • git-appraise has an undocumented rebase command that takes care of this, but in the author's judgment you cannot rely on users always using it for every commit-rewriting operation.
  • The author presents a short script in which a review request is created, the commit is amended, and reflog expiry and garbage collection are triggered right away, after which the request is gone. He adds that the only unusual thing in it is triggering garbage collection immediately.
  • He also describes lookup as inconvenient. Because a commit, a change-id or a branch does not tell you where its review information is stored, you would have to traverse the list of notes and parse the JSON objects.

The alternative is a custom ref. A ref is a pointer to an object; branches are stored in .git/refs/heads/, tags in .git/refs/tags/ and notes in .git/refs/notes/. The author explains that new refs can be created in other directories, .git/refs/flirt/ for example. Such refs have no special meaning to Git but work the same way. They prevent the objects they point to from being garbage-collected, and they can be pushed and fetched like branches.

The first attempt serialized the data structure to JSON, stored it as a blob and created a ref pointing at that blob. The problem was the intermediate submissions. Flirt calls the unit of review that corresponds to a pull request or a patch series a Spirit ("Set of Patches Intended for Review and Intense Testing"), and calls each version the author puts up a submission. When a reviewer pulls the ref, the review information is downloaded, but pulling the branch only downloads the commits of the latest submission and not those of the submissions in between. The hashes are stored in the Spirit, but since the commits are not available locally, they cannot be viewed.

The approach the author chose leans on existing Git behavior. When a commit is pulled, all of its ancestors that are not yet present are downloaded as well. So the custom ref was made to point to a commit instead of a blob, and that commit has the head commit of each submission as a parent. The commit's tree stores a single blob called spirit.json, which contains the actual review information. When a reviewer fetches a Spirit, the commits of previous submissions are downloaded with it, so the reviewer can examine how the Spirit evolved over time and view the state of the codebase a previous comment was made on.

Reviewing in the Editor — HEAD, the Worktree, and the Comment Thread Idea

The second distinguishing feature the README names is being local-first. It says that the network is required only to download things to review and to upload the review, and that the process of review itself happens offline and integrates with existing tools, most notably the text editor. The November 2025 post starts from the observation that an editor already has the features needed for review: viewing the diff of the Git HEAD and the worktree, navigating code with LSP integration or language plugins, writing notes in language-specific comment syntax, and running the code and its tests. The gap the author points to is that, in order to leave a comment, the reviewer has to leave the editor, open a browser, navigate to the same place again and open a text box.

Flirt's approach is to "materialize" the interdiff in the local repository. The Git HEAD is made to point at the state of the Spirit the reviewer previously reviewed, and the current state is written to the worktree. An editor with some amount of Git integration will then show what is new. The November 2025 post says that this way the editor shows the same thing as jj interdiff. Comments are written in the normal comment syntax of the language, and the idea is that Flirt collects them, strips whitespace and comment markers, and sends them to the backend.

What this approach had not solved was comment threads. When comments are read and written inline in the editor, Flirt needs a way to know whether a new comment is meant to start a new thread or to reply to an existing one. In the February 2026 post the author presented, as his "current plan", the idea of adding a marker around an existing thread with a dedicated space for replies. In the example, a thread begins with the line // +<3+<3+<3+<3+<3+<3+<3+<3 Flirt thread-ID: ABCXYZ, continues with comments that carry an author and a timestamp, a place to write a reply, and checkboxes for "mark as resolved for everyone" and "mark as resolved for yourself", and ends with a thread-end line. The author himself writes that this notation is a little verbose and hard to read. The August 2026 post says that comment threads are "basically working".

The design decisions and ideas recorded in the same posts are listed below. All of them are plans as of the respective post.

  • Thread relocation. GitHub marks a thread as outdated when a force-push changes the commit the thread was started on. If threads are materialized in the repository, the code author can move a thread along with the function it refers to, and the idea is that Flirt reads the new location by the thread ID and stores it in the Spirit. The author writes that only the Native Git backend would support this.
  • Two resolved toggles. On GitHub the thread resolution state is shared for everyone. The author intends to implement separate shared and local toggles, and writes that with a backend that has no thread resolution, such as the mailing list, the user is left with the local toggle.
  • Per-commit review. The plan is not to support commenting on the combined diff of a multi-patch Spirit. Commenting on ranges of lines will be supported, while commenting on a range of characters within a line, a feature Gerrit has, is not planned.
  • Comments on commit messages. The author wants to support them, and writes that when sending them to GitHub, which does not support this, he will probably have to represent them as a free-standing comment that includes the quoted commit message.
  • Verdicts. These differ by backend. GitHub has Comment, Approve and Request changes; Gerrit has a score on the Code-review label ranging from -2 to +2; the mailing list has conventions such as Reviewed-by, Tested-by and Acked-by. The author therefore writes that custom verdicts will be needed at least for each backend.
  • User interface. As of November 2025, Flirt was a CLI meant to show the basic function. The author wrote that the main UI will probably end up being a TUI, with the core application logic exposed as a library.

The Repository and Community Rules — Rust, AGPL-3.0-or-later, the LLM Policy

The Cargo.toml in the repository lists the package name flirt, version 0.1.0, edition 2024 and the license AGPL-3.0-or-later. In November 2025 the author wrote that he had not decided on the license and that both GPL and Unlicense appealed to him, each in their own way; the LICENSE file was added in a commit dated September 30, 2026. At the time the repository page was retrieved it showed 111 commits, 2 branches and 0 tags, with a language breakdown of 96.9% Rust and 3.1% Shell. The dependency list includes clap, clap_complete, inquire, jiff, mail-parser, unidiff, serde, serde_json, anyhow, cmd_lib, rand and which.

The README has no installation or build section. Its "Contributing & Development" section says that there is not much in terms of documentation yet and recommends dropping by on Zulip and talking about what you are interested in to get started. Common development tasks are defined as scripts in the tasks/ directory, and the README says they can be executed directly or with simply-run or mise. The README sets out three guiding principles.

  • Community above output. It says that creating the best code review tool is only a by-product of people building a shared understanding of what that even is.
  • Power users come first. It says that there are a lot of review tools optimizing for accessibility and that Flirt is not one of them. Its position is that improving accessibility is great as long as it does not come at the expense of power users.
  • Free and open-source software. Contributing to Flirt and participating in its community should not require the use of proprietary software. A footnote lists the consequences: Discord cannot be an official communication platform, and contributions cannot be blocked on support for proprietary backends (GitHub) or operating systems (Windows, Mac). These may still be supported by other contributors on a best-effort basis.

The README itself calls its LLM policy "fairly strict".

  • Publishing LLM-generated text in Flirt community spaces is forbidden, edited or not. Code, commit messages, issues, PR descriptions, comments on issues and PRs, and messages on Zulip must all be written without the use of LLMs.
  • Use in a personal context is outside the scope of the policy. Exploring the codebase, research, debugging and bouncing ideas around are given as examples, and a footnote says that the policy does not condone or condemn any form of personal LLM use.
  • There is a narrow exception. It applies when the contributor did not intend to generate the contribution (it was an accident), when the LLM-generated text is the best or only way to make a specific improvement, and when the contributor "sanitized" it by reproducing it, as far as possible, with their own mind.
  • As an example of sanitizing, the README takes the case where an LLM produces a call to a library function the contributor does not yet know. The contributor is to think about how they would have come up with the idea of using that library, search the documentation for the functionality as if they did not know the function name, and read the documentation to reach their own conclusion.
  • Enforcement assumes good intentions. If a violation is suspected, it is assumed to be an honest mistake and the person is only reminded of the policy; for an intentional violation, the README says that the only reasonable consequence, in principle, is a permanent ban.

Maturity Today — What the Documents Confirm and What Is Still Missing

Putting the announcement, the README and the development posts together, the current state divides as follows.

Item What the documents confirm What is missing or constrained
Release 2026-10-05, flirt/flirt on Codeberg, AGPL-3.0-or-later 0 tags; the version field in Cargo.toml is 0.1.0
Primary feature Detects and shows the interdiff of a previously reviewed commit and its current version Reliability depends on commit metadata and is best when the commit author uses Jujutsu
Backends Native Git, GitHub, mailing list Forgejo does not exist. The mailing list backend is a proof-of-concept and the Native Git format is unstable

Taken together, Flirt is a tool that tries to answer the question of what to show when re-reviewing force-pushed changes by means of the change-id and local storage, and for now the reach of that answer is conditional. The documents themselves state that the result depends on whether the commit author uses Jujutsu, on which backend is in use, and on whether the reviewer observed the previous submission on the same workstation.

The yardstick is the author's own wording. Flirt is not yet ready for general use, there are still plenty of bugs and missing features, and anyone not considering becoming a contributor is advised to be a little more patient. The README likewise says to test it only if you intend to contribute. Because the author said he will probably announce readiness in another post, deferring the decision on whether to put Flirt into a working process until after that post is consistent with his recommendation. The readers this release is aimed at today are people who relate to the review problems of the patch series workflow and want to take part in design discussions or backend implementation, and the README says that adding support for a new backend you care about is a great way to get started contributing.

Adjacent topics are covered in other articles. GitHub's stacked pull requests, which split a large change into several layered PRs, are covered in GitHub Stacked Pull Requests in Public Preview, and Hunk, a tool for reviewing diffs in the terminal, is covered in AI Agent Code Review with Hunk. Stacked PRs are a way of splitting a change, whereas Flirt is a way of comparing rewritten commits against the state the reviewer previously saw.

What Could Not Be Confirmed

  • How much of the plans the released code implements. Thread relocation, the two resolved toggles, per-backend verdicts and the comment thread notation are plans and ideas from earlier posts. The README does not say how far the released source implements them, and the source code was not part of the material this article is based on.
  • Installation, build and command-line usage. The README has no such section. The summary of the Lobste.rs discussion carried by GeekNews includes a passage in which the author is said to have replied that the installation instructions were left out on purpose, but the original comment could not be confirmed.
  • When it will be ready for general use. The announcement only says that a post will "probably" follow when it is ready and gives no schedule.
  • Whether and when work on the Forgejo backend has started. There is no basis beyond the phrases "next-up on my todo list" and "it will soon enough".
  • What the fallback heuristics actually do. The README only says that fallback heuristics are used if there is no change-id header. What they match on, and how a wrong pairing shows up for the reviewer, is not documented.
  • The current state of the change on the Git side. The account of the patch series about preserving the change-id header relies on the README footnote, and the mailing list thread itself was not part of the material this article is based on.
  • Third-party usage and validation. No usage reports from anyone other than the author and no comparative measurements against other review tools were found.
  • The master's thesis. Whether and where the text of the thesis is published is not stated on the blog or in the README.
  • The timing of the repository figures. The numbers of commits, branches and tags and the language breakdown are the values shown on the page when it was retrieved on October 7, 2026, and they may change afterwards.
