Toward Not Handing Over the Key at All

Pass a reference, not a value - where to put the boundary, and what remains anyway

Aug 28, 2026 Dev & Infra

Introduction: the question that returns with every new tool

Every time you attach one more tool to an agent, your hand stops in the same place. Where does this key go? Writing it into a config file is convenient, but that file is readable by the agent. Loading it into the environment is convenient too, except the environment follows child processes around. Typing it by hand each time defeats the point of automation. None of the three feels right, and most people pick the first one anyway.

Two recently published tools poked at different faces of that same question. One is an integration layer that gathers external service connections and execution permissions into a single tier and exposes only methods and results to the agent (Corsair). The other is a local utility that keeps secrets in encrypted storage, injects them into a child process only at the moment a command runs, and strips them back out of the returning output (key-amnesia). One works on a remote boundary, the other on a local one. The premise underneath is identical: the agent never sees the value.

What follows is not about what to allow, but about how to avoid handing over credentials in the first place. The framework for grading permissions and measuring blast radius lives in What Should an AI Agent Be Allowed to Do - Permission Design and Failure Barriers, and the conditions under which an approval button is actually a defense are in When Does an Approval Prompt Actually Defend You. This piece assumes both and looks only at the layer beneath them: the value itself.

This is a general design discussion and does not certify the safety of any particular product or configuration. Tool names appear only as the occasion for the discussion, and no judgment about which one is safer is offered here.

1. What the problem really is - a string in context is never recalled

An agent is, in the end, a system that manipulates text. However many tools you attach and however tightly you sandbox it, what the model sees is one blob of characters. Put a credential into that blob once and, from then on, the string travels along paths nobody explicitly chose.

Where it goes is mostly predictable. It stays in the conversation record, rides out again with every request, gets copied into a summary when the context grows long, prints into the traces and logs you turned on for observability, lands in a cache, and comes back as raw material for the next session. The awkward part is that each of these paths was built by a different team for a different reason. Closing one leaves the rest fully alive.

That is why the common answer, just be careful with it, does not hold. Three things stack up.

  • People do not decide when the value moves. Summarization, retries, tool calls, and error reports happen automatically. The party being careful and the party moving the value are not the same party.
  • There is more than one path. Turning off logging does not turn off summarization, and blocking summarization does not stop traces. A partial measure is always partial.
  • The cost is asymmetric. Handle it well 999 times and one slip starts a rotation, with the period in between usually unaccounted for.
  • Deletion barely exists here. A file can be deleted. Context that has already flowed is less a thing to delete and more a thing already copied.

Stated plainly, this is a placement problem rather than an attention problem. If the value never enters that blob, there is nothing to be careful about. Everything after this is one long answer to how that sentence gets implemented.

2. Passing a reference instead of a value - splitting context from execution

The idea is simple. What the model receives is a label saying that some credential belongs in this slot, and the actual value is attached only at the boundary immediately before execution. The model plans and composes the request, but the final piece that completes it is filled in somewhere the model cannot see.

Doing this places three things in three different homes. Intent belongs to the model, the reference belongs to the plan, and the value belongs to the executor. However often the first two are copied and summarized, the value does not follow. The arrangement is not new either. Masked variables in a build pipeline, or a server that makes the call so the browser never receives the key, have the same shape. What changed is only that the untrusted execution party is no longer someone else's browser but a model we attached ourselves.

For the split to actually hold, though, conditions come attached. Miss one and only the shape survives.

  • The substitution point must sit outside the model context. If the model composes a request and then fills in the value itself, the label is decoration.
  • Returning output has to cross the same boundary. Wrapping the request while letting the response through untouched is half a design, and responses that echo values back are more common than people expect.
  • The label itself must not leak information. Reference names usually stay in plain text. Write the target and the purpose into the name and the structure is readable without the value.

3. Where to put the boundary - three positions and their prices

The principle of substituting right before execution stays constant, but the character of the design changes completely depending on where that right before actually is. Three positions show up in practice, and they are not mutually exclusive. Layering them is the norm.

Boundary positionWhere the value livesWhat must holdWhat it costs
Process environment injection Only in the environment of the child process being run, only for that moment The agent must not be able to read that process environment or memory, and output has to be handled separately It is the same machine, so isolation strength is capped at the operating system level. Screen and clipboard remain open
A separate executor A dedicated process kept apart from the agent Requests go in but the executor's internal state must not come back. If a human confirmation is involved, that surface must be outside the agent's reach too The executor becomes a new point of trust. Compromise there opens everything below it at once
Remote proxy or integration layer Our infrastructure, or the external service side Permissions must be narrowable per call, and requesters must be distinguishable in the record Availability and latency enter the picture. And the call permission is delegated as-is

The criterion for choosing is not taste but what you are trying to protect. If the goal is keeping the value from spreading, the first two are often enough. If instead you will have to answer later who did what, the third becomes necessary. Records do not appear because a value was hidden; they appear because calls pass through a single point.

  • For solo local work with only a handful of targets, the first two give the better return on effort.
  • When several people call the same service and the results mix, attribution does not hold without the third.
  • Whichever you pick, the path of the returning output remains as shared ground. Leave that empty and much of the preceding design stops meaning anything.

4. What a proxy actually moves - not the credential, the call permission

This is the step people skip most often. Hiding a value and preventing the action are two different statements.

Put the key behind a proxy and the agent never sees the string. But everything that key could do is still one request away. What was delegated is not the credential, it is the call permission. If mail went out while no key was ever exposed, the mail went out. From the recipient's side, how carefully we stored the value carries no meaning at all.

That does not mean nothing was gained. It means the gains have to be counted precisely before the next decision can be made.

  • The spread of the value shrinks. A leak has one place to revoke, and the failure mode where the same value gets reused across unrelated systems disappears.
  • A place to narrow permissions appears. A raw key can only be handed over whole, but a layer that makes the call on your behalf can slice it down to individual operations.
  • Records gather at one point. The raw material for the questions you will have to answer later is manufactured right there.
  • Revocation finishes in one move. No hunting through scattered copies of the value.

The trouble is how common it is to take only the first and skip the other three. What remains then is the single fact that no key was shared, while the actual risk has merely relocated. The work due on the day a proxy goes in is not celebration but deciding what that layer will narrow.

5. Lifetime and scope - why one permanent key is the worst case

The question after hiding the value is what that value can do, and for how long. Three axes can be reduced, and the three cost very different amounts.

AxisWhat it reducesWhat you gainWhat you pay
Target Which resources can be reached The area an incident can spread across is fixed. Usually one configuration change and done Low. Roughly the effort of maintaining a target list
Scope What can be done The same value can do less, so the consequence of a misfire gets lighter Medium. Miss a needed operation and things fail quietly
Lifetime How long it stays valid The exposure window after a leak is cut by the clock High. The issuing path becomes a new dependency, and the issuer becomes a new top-level secret

Read the table backwards and you can see why a single permanent key is the worst case. Not because all three axes are maxed out, but because that state entrenches itself.

  • Revocation means a full stop. When many places share one value, rotating it halts everything, so it never gets rotated even when suspicion arises.
  • Nobody can tell who used it when. Records exist, but they all show the same actor and answer nothing.
  • The moment of leakage is unknowable. Without expiry there is no baseline for judging since when it was in someone else's hands.
  • Permissions only accumulate. Each new feature adds a line and nobody removes any. A year later, no one knows what that key can do.

If an order is wanted, it is constrain targets, then narrow scope, then shorten lifetime. The first two usually finish in one sitting and add no recurring cost. Shortening lifetimes has the largest effect but creates a permanent issuing burden. It is the same shape as adding a vault and inheriting a vault-key problem, so skipping the first two and starting with lifetimes generally buys less than the added complexity costs.

6. Audit and attribution - does the record say who asked for the call

After an incident, the question you actually have to answer is not whether the key leaked. It is what ran, who asked for it, and whether it can be undone. Nobody is satisfied by an answer that the value stayed secret.

The minimum set to record is therefore fairly fixed: the time, which reference was used, against which target, performing which operation, from which session and task, and whether a human confirmation happened. With those six most questions can be answered, and missing even one turns answers into estimates.

The catch is that this is only easy while there is a single agent. The moment there are several, the basis for attribution quietly collapses.

  • A shared reference erases the caller. The records exist, but they all look like the same actor.
  • A sub-task calling with the parent credential folds the lineage into one line. The side that decided and the side that appears in the record stop matching.
  • Retries and parallel runs break ordering as causation. The line written first is not guaranteed to be the decision made first.
  • Once a summary passes, the reasoning is gone. What happened is in the log, but why it was judged that way vanishes with compaction.

The conclusion here is practically useful. Attribution is not obtained by polishing a log format. Split references per agent and per task and the records separate by themselves. Conversely, in a structure where one reference serves many, no amount of log craftsmanship produces anything but more identical lines. That is why the first step in audit design is credential partitioning rather than logging.

7. What still remains

Doing all of the above does not make risk disappear. It is more honest to separate what shrinks from what merely relocates. Collected in one place, the remainder looks like this.

  • Misuse of the delegated permission. The extension of the previous section. If the side composing requests is manipulated, a formally normal call goes out. The fact that no value leaked blocks none of that path.
  • Data that rides back in the response. When a call result contains another person's information or the contents of another repository, none of it is a secret, so it is not filtered and enters the context intact. Blocking secrets while admitting data is a common configuration.
  • The limits of output filtering. Redaction by direct comparison only works while the string keeps its original form. A different representation of the same value reads as a different string. A filter is the last net, not the last line of defense.
  • Names and metadata. Reference names, target lists, and failure messages usually stay in plain text. The structure is readable without any value.
  • The next link in the chain. Our boundary can be solid while the next tool receiving the result keeps no such discipline, and it goes out there. Boundary strength is set at the weakest link.
  • The human path. Screens, captures, pasting, shared transcripts. It stays open regardless of any technical split, and it is in fact the door that opens most often.

Which is why no configuration ever earns the sentence use only this and you are safe. The goal is not total prevention but a state where an incident can be answered for and undone.

8. Working alone versus working on a team

The same principle produces different worries for one person and for a group. Put an organizational setup on personal work and it gets heavy enough to be abandoned. Put a personal setup into an organization and nobody can be held responsible.

Working alone, the real problem is not the permission model but the fact that everything hangs off a single account. Personal accounts tend to be broad and undivided. A practical order looks like this. Constrain the targets first. Then split the everyday account from the automation account. Finally, verify the revocation path. The measure is whether this value can be made useless within minutes, starting now.

On a team, the problem is not the number of secrets but the number of delegates. From the moment executing parties outnumber people, the managed inventory starts diverging from the roster. The order here is different.

  • Attach an owner. Put one human name on every reference. Ownerless values live the longest and get revoked the latest.
  • Make issuing and revoking easy. Make only the request process heavy and side paths appear. That is how values end up in personal notes.
  • Set an end date. People leave and projects close, but values stay. Attaching a cleanup date in advance is cheaper than auditing after the fact.
  • Reduce shared accounts. Most of the attribution problem from section 6 starts here. A record that cannot be separated is not a record.

One failure shows up on both sides. Nobody knows who created this value, when, or why. Once that is true, it can be neither revoked nor narrowed. Leaving one line behind at the moment a value is born beats any audit tool applied later.

9. Misconceptions that keep coming up

The recurring misreadings in this area mostly come from the assumption that solving storage solves the problem. Storage is the front half. The back half sits after the value comes out.

Common claimWhat is actually trueSo look at
Environment variables are safe An environment variable is a storage location, not a boundary. It is inherited by child processes and can ride along in diagnostic output How far the value travels across processes
A vault settles it A vault solves storage. The paths after retrieval are untouched Whether the retrieval point is inside or outside the model context
Read-only access is fine Reading is leaking too, and what was read becomes material for the next call Where the read content accumulates
It only runs locally, so it is safe Local is a location, not isolation. If it is readable within the same machine, it is no different from remote Whether the same user privileges can reach it
Output is filtered, so nothing escapes A filter stops the shapes it knows. A different representation passes Whether the filter is being used as the last line of defense
An approval prompt was added, so it is handled Approval asks about an action. If the value is already in context, it flowed regardless of the answer Whether the value entered before the approval
It is open source, so it is vetted Being public is auditability, not an audit. Someone has to have read it What you need to look at yourself in your own setup

The last column of that table is the practical checklist here. Sketching where the value travels in your own configuration always comes before the question of which tool to adopt.

10. What could not be confirmed

  • The internal behavior of the two tools was only reviewed as far as their repositories describe publicly. Specific cryptographic parameter settings and how far the output cleanup rules extend could not be confirmed.
  • Latency and stability figures in real production environments are not included, since no published measurements were found.
  • Token lifetime and scope options differ substantially by provider. With no basis for generalizing, only the axis names are given here and concrete values are left out.
  • Which control items of any specific security certification the record fields here correspond to could not be confirmed. Compliance mapping needs separate verification.

Conclusion: there is only one thing to ask

A design that keeps values out of context is a clear gain. The spread of a leak shrinks, revocation finishes in one move, and a place appears both for narrowing permissions and for collecting records. Except the gain does not arrive automatically. Standing up a proxy is half of it. Actually narrowing targets and scope at that layer, and distinguishing requesters in the record, is the other half. Do only the first half and one sentence is all that remains: no key was shared.

And even after all of it, something is left over. The call permission stays delegated, data riding back in responses passes because it is not a secret, and the next link in the chain sits outside our discipline. Those three cannot be designed away; they are things to manage operationally.

So the question to ask before choosing a tool narrows to one. If this value is leaking right now, how many minutes until we can make it useless? A team that answers in minutes is generally fine whatever tooling it uses, and a team that cannot answer is merely trusting whatever tooling it has.
