降低 AI 生成代码验证成本的语言特性

让 Go 在当下占优的五个特性，以及它们各自收取的代价

2026年8月16日 开发/基础设施

引言：评审队列真正堵住的地方

给代理丢一张工单，开完会回来，八百行的改动已经在等你。构建是绿的，测试也过了。可是在按下合并之前还有事要做，而这件事花的时间和去年一模一样。团队真正卡住的位置就在这里。

写的成本和确认的成本没有以同样的速度下降，仅这一处不对称，就是当下语言之争的全部背景。2026 年 8 月 11 日，Go 团队的 Cameron Balahan 与 Google Cloud 的 Richard Seroter 在 Google 开发者博客发文，主张 Go 是适合 AI 辅助软件工程的理想语言，一天之内就在各地社区传开，又转成了那场熟悉的语言高下之争。

但那篇文章真正有价值的不是结论，而是底下那个问题：语言的哪些特性会降低验证成本。这个问题跟 Go 没有绑定，不写 Go 的团队今天也能拿来当判断标准。本文把这类特性收敛成五条，说明 Go 是怎么拿到它们的、作为账单又交出了什么，以及采取相反策略的语言如何回答同一个问题。

先把话说死：本文不主张哪种语言更好。每一条特性都带着对价，哪种对价扛得住，由付账的那支团队的约束条件决定。

1. 验证成本由什么构成

面对八百行的评审者做的不是一件事，而是五件。

  • 看清形状 — 眼睛适应缩进、换行、括号摆法所花的时间
  • 对照惯用法 — 同一件事有多种写法时，确认这里用的方式是否与本代码库一致
  • 确认 API 存在 — 被调用的函数和包是否真的存在、签名是否吻合、在那个版本里有没有
  • 验证语义 — 是否符合需求，边界条件有没有漏掉
  • 追踪副作用 — 这次改动会在别的路径上留下什么

分界就在这里。前三件可以交给语言和工具，后两件无论用什么语言都留给人。所以语言特性能够介入的位置恰好是前三件，从那里挤出去多少，注意力就在后两件上多留多少。目的不是把评审时间缩短，而是让省下来的注意力落到哪里去。

Google 那篇文章里值得引的也正是这一段。它提到反复让模型修改时，第一遍可能有 95% 正确，但一轮轮下来错误率会累积。换句话说，结果由一圈能转多快、筛子能筛多准决定。转速和筛子的性能，就是在这里变成语言问题的。

2. 降低验证成本的五个特性

语言削减上述前三项的方式可以归成五条。这里的写法是把 Go 抽掉也依然成立的。

特性削减的验证项怎么用机器确认代价
语法表面积小看清形状评审者必须记住的语法规则数量表达力受限 — 无法用语法收窄领域
惯用法收敛为一对照惯用法文档里每件事是否只有一个标准解聪明的写法也被拒绝 — 正文变长
强制格式化看清形状diff 里只改了排版的行是否为 0无法体现团队偏好
标准库够宽确认 API 存在新增依赖的条数标准一旦老化，整门语言跟着老化
编译够快前三项的整体转速从改动到第一条报错的时间放弃一部分优化与检查强度

五条里前三条是减少要读的东西，后两条是提高机器替你读的速度。性质不同，所以一门语言不必五条全占。

其中最被低估的是第三条。强制格式化容易被当成审美问题，可产出量上来之后它的性质变了。模型每次都会把同一段代码写成不同的排版。在排版自由的语言里，这份差异会原样留在 diff 中，语义根本没变的行也要过一遍评审者的眼睛。排版被强制之后，那些行压根不会出现。这和静态类型为何自 2010 年代中期重新受宠属于同一类问题，来龙去脉放在静态类型的崛起那边。

3. Go 是怎么拿到这些特性的

Go 拿到这五条，与其说靠语言设计，不如说靠随语言一起分发的那套工具。这是它与多数替代品分道扬镳的地方。

  • gofmt — 排版本身就在语言发行版里。风格争论不会在每个组织重演一遍，纯排版的行也活不到 diff 里。
  • go vet — 能编译但可疑的写法由标准工具抓出来，比如格式化字符串不匹配、锁被复制之类。
  • govulncheck — 用标准工具检查依赖的已知漏洞。产出量越大，这项检查越值钱。
  • go fix 与现代化工具 — 由机器把陈旧惯用法迁到现行写法。模型学到旧代码而输出旧写法时，至少还有一条回来的路。
  • 内置模糊测试 — 从 Go 1.18 起并入 go test。不装任何东西就有随机输入测试。
  • pprof、执行追踪、PGO — 性能回退靠剖析文件抓，而不是靠感觉。

合起来看，下面这条流水线只靠标准发行版就能跑通。

# 把排版差异从 diff 里抹掉
gofmt -l ./...

# 抓能编译但可疑的写法
go vet ./...

# 查依赖的已知漏洞
govulncheck ./...

# 测试与竞态检测一起跑
go test -race ./...

关键在于这四行全都不需要额外安装。少了挑工具、对版本、就配置文件达成一致这些环节，一个全新的仓库从第一天起就挂着同一张筛子。而当代理自己改自己迭代时，这张筛子不需要人在场也照样工作。

标准库的宽度与供应链

Google 文章里最快落到实务上的就是这一条。模型输出的包名停留在训练时点，因此会信心十足地调用早已无人维护、甚至根本不存在的包。标准库够宽，这类调用一开始就少。HTTP 服务、JSON、加密、模板都在标准库里，模型往外找的理由就少，新进来的依赖条数少了，要审计的面也跟着小。

Go 1 兼容承诺实际覆盖到哪里

这是在长寿代码上兑现价值的特性。Go 的兼容性文档写的是按 Go 1 规范编写的程序，意图在该规范的存续期内无需修改即可继续编译并正确运行。但范围要看准。

  • 保证的只是源码层面。已编译包的二进制兼容在版本之间并不保证。
  • 安全问题、依赖规范未定义行为的代码、规范自身错误的修正、缺陷修复，全都被明确列为例外。
  • 省略字段名的结构体字面量、给内嵌类型新增方法、点号导入、使用 unsafe，同样在例外清单上。

也就是说，它的形态不是绝对不会破，而是把可能破的情形事先写进文档，在这些情形之外守住承诺。在生成代码不断堆积的场景里，这个区别很大。不去踩例外清单，本身就成了编码规范的一条。

编译速度的说法有多少是事实

Google 文章说 Go 的编译比 Java、C#、Rust 等生产级编译型语言快上数量级。方向本身与用过 Go 的人的体感并无出入，但文中没有交代硬件、代码规模和工具链版本。没有条件的比较不能当排行榜用。这类数字除了在自己的仓库里实测别无替代，而且实测值会随缓存状态和模块数量剧烈波动。

4. 代价 — 语法省下的，账单以正文长度寄回

特性是有标价的。Go 交出去的主要有四样。

错误处理的啰嗦

Go 处理错误的方式收敛成了一种，于是每次调用都跟着同样的形状。

f, err := os.Open(path)
if err != nil {
    return nil, fmt.Errorf("open %s: %w", path, err)
}
defer f.Close()

data, err := io.ReadAll(f)
if err != nil {
    return nil, fmt.Errorf("read %s: %w", path, err)
}

在生成这一侧，这不构成负担。重复块正是模型输出最稳定的形状，敲键盘的成本也不由人来付。负担出现在阅读那一侧。当 diff 里很大一部分长得一模一样，其中唯一一处把错误默默吞掉的代码就很不显眼。重复变成噪声，真正的信号就埋在噪声里。

这份代价短期内不会消失。2019 年的 try 提案被否决之后又出过几轮方案，2025 年 6 月 Go 团队表示暂不再推进错误处理的语法层变更，并把以该语法为主题的提案一并关闭。同一篇文章里也承认，调查中错误处理被列为使用 Go 时最具体的最大难点。这是明知代价而选择维持的设计。

表达力受限

Go 没有和类型，也没有穷尽式模式匹配。结果就是编译器无法拒绝一个漏了分支的状态机。状态往往写成字符串或整型常量，switch 上挂一个 default，新增状态照样编译通过。这份检查于是落到测试和人身上。

泛型之前留下的痕迹

类型参数是在 Go 1.18 进来的。在那之前，容器类工具要么按类型复制一份，要么用 interface{} 接住再断言，那个年代的代码大量留在公开仓库里。模型有时输出旧惯用法，原因就在这里。不过这种情况的频率有多高，没有任何公开测量可以支撑。正确的应对不是去估一个频率，而是把现代化工具和静态分析挂进持续集成。

并发 — 语法容易并不等于安全

这是最需要留神的一处。一个 go 就能起协程、通道语法又简洁，同时也意味着生成器会毫不犹豫地到处撒并发代码。可数据竞争编译器不管。-race 能抓，但只有那条路径真的执行到才抓得住。围绕这篇文章的社区讨论里，正好有人担心 AI 生成的 Go 代码存在并发缺陷，这一点之所以重要，是因为它落在上面五条特性覆盖不到的区域。排版统一、惯用法唯一，竞争也不会显现在代码的形状上。

5. 另一种答案 — 把验证塞进类型系统

有些语言从相反方向回答同一个瓶颈。如果说 Go 是减少要读的量，那么这一侧是让编译器直接拒绝，从而不必去读。谈不上谁更高明，只是账单的收款对象不同。

  • Rust — 所有权与借用检查在编译期就拒绝一大类内存错误和数据竞争。有和类型，加上 match 的穷尽性检查，新增一个状态时所有没处理的位置都会变成编译错误。在越来越多代码没人读的局面下，这份性质就是直接的价值。代价是构建时间、学习曲线，以及 unsafe 边界的管理。两者之间的迁移判断轴放在Go 迁移到 Rust 完全指南里。
  • TypeScript — 可辨识联合能把状态封死，strict、noUncheckedIndexedAccess 之类的开关可以调节检查强度。代价有两处：类型定义质量随包而异，以及 any 这个出口永远开着，生成物可能悄无声息地绕过检查。
  • Python — 类型提示不影响运行。因此若不把独立的类型检查器挂进持续集成，验证就整体落到测试和运行时。作为交换，数据与机器学习生态的宽度压倒性地强，那是其他特性补不上的位置。

按缺陷类型排一排谁来抓，选择的性质就清楚了。

缺陷类型GoRustTypeScriptPython
API 不存在或签名不符编译器编译器类型检查器运行时或独立检查器
访问缺失值运行时（nil 崩溃）编译器（Option）开启配置后由类型检查器运行时
状态分支遗漏测试与人编译器（match 穷尽性）用可辨识联合时由类型检查器测试与人
数据竞争运行时靠 -race编译器较少涉及（默认单线程）运行时
排版差异造成的 diff 噪声由 gofmt 消除rustfmt（惯例）另行引入格式化工具另行引入格式化工具
供应链暴露面由标准库收窄依赖偏多依赖非常多依赖偏多

竖着读这张表，形状就出来了：Go 在排版和供应链上强，在靠类型抓住的缺陷范围上窄。Rust 正好相反。先看自己团队的事故历史集中在哪一行，判断会快很多。挑一条自己从来不出事的行上表现好的语言，等于什么都没买到。

6. AI 写得好的语言和人读得快的语言是同一个吗

大体重合，但不是全部重合。而判断出错的地方，恰好就在分岔的区间。

  • 重合的一侧 — 惯用法收敛与强制排版对两边都有利。模型只要复现学过的那一种模式，人也只有一个基准要对照。
  • 分岔之一 — 重复。人把重复读成噪声，生成器却不为重复付费。所以同一段代码可能从生成角度看是好的，从评审角度看是坏的。
  • 分岔之二 — 压缩的表达。一行函数式管道对熟手是高密度信息，可一旦错就是整段错，局部验证使不上力。
  • 分岔之三 — 文档惯例。人在注释稀少时用上下文补齐，工具则会把签名和类型里没有的信息编出来。

所以对 AI 友好这个说法把两个不同的主张捆成了一个。一个是模型在这门语言上生成得准不准，另一个是人能不能快速验证结果。前者取决于训练数据分布与模型特性，从外部基本无从确认；后者可以通过工具与语言设计核实。只把能核实的那一半当依据用，才稳妥。至于从头为代理设计一门语言的尝试及其局限，放在代理专用编程语言那边单独讲。

7. 哪些主张有依据，哪些还没有

这个话题容易读错，是因为性质不同的主张常常挤在同一段里。把层次分开，能用的和该搁置的就分清了。

主张性质依据状态实务上
瓶颈从编写转向验证算术产出量涨了，人的一天没涨可以直接当前提
强制格式化消除排版 diff工具事实在自己仓库里当场可验今天就打开
标准发行版自带验证工具工具事实官方文档可确认提升为阻断性检查
Go 1 代码能在最新工具链上构建成文政策仅限源码层，且有例外清单把例外清单翻译成编码规范
Go 编译比别的语言快得多比较性主张条件（硬件、规模、版本）未交代在自己仓库里实测
代理写 Go 写得更好社区说法未确认公开测量与评分标准不作为判断依据
各语言生成准确率有差异定量主张未确认公开数字当作不存在处理

引用基准测试的规则也由此而来。不附模型版本、硬件、任务种类和评分标准的数字，不是排行榜。编程任务的分数尤其会随任务构成而调换次序，缺了条件的引用连方向都保证不了。

8. 真正决定语言选型的是什么

现场决定语言的力量在验证成本的上游。把顺序颠倒过来，就会出现选了个特性优秀的语言、然后自己动手补写不存在的库的局面。

  • 生态 — 这个领域有没有成熟的库。支付对接、文档解析、机器学习流水线常常仅凭这一条就定了候选。
  • 招聘与交接 — 能不能持续找到维护它的人。找不到，验证成本只是换个位置变成交接成本。
  • 运行时要求 — 能容忍多长的 GC 停顿，有没有内存上限，冷启动是否进入服务指标。
  • 交付形态 — 是否一个静态二进制就结束，要不要随包附带运行时，镜像体积与启动时间是否计入成本。
  • 监管与采购 — 在公共部门和金融领域，允许使用的语言和工具有时写在合同里。特性之争还没开始，选项就已经被收窄。
  • 既有资产 — 内部公共库、认证模块、日志规范落在哪门语言上。

实务上更稳的顺序是：上述约束把候选压到两三个，验证成本特性在剩下的里面排序。特性不负责产生候选，只负责区分幸存者。为什么在 AI 时代那句先选成熟技术的老建议反而更硬，写在重新审视选择无聊的技术里。

9. 这个判断在什么条件下能被复制

与其给结论，不如分清同一个结论在哪里成立、在哪里不成立。

  • 容易复制的一侧 — 内部平台 API、网关、批处理流水线、运维 CLI 工具。对领域库依赖低，交付到一个二进制为止，评审者又分散在多个团队，排版与惯用法统一的收益最大。
  • 不易复制的一侧 — 数据与机器学习流水线由生态说了算；前端那把椅子早已被类型检查器坐着；受监管的存量系统首先被人力池和采购规范卡住。
  • 招聘现实 — 各语言有生产经验的工程师储备按地区和行业差别很大。特性再好，没人维护就会变成负债。
  • 组织结构 — 评审者越集中在一两个人身上，排版与惯用法统一的收益越大；反过来，如果评审早已自动化，这份收益已经收走了。

真要动，与其整体切换，不如从评审队列最长的那一条路径开始。失败时回滚范围限于一个服务，而那条路径上评审时间到底有没有真的下降，就是下一次决策的依据。与把代码写成有人会来维护的样子相关的讨论，可以一并参考写代码要像人类将来会维护它一样。

10. 没能确认的部分

把当前填不上的空缺集中放在一处。以下项目在正文中都没有被当作依据使用。

  • 各语言 AI 生成准确率的公开数字 — 没有确认到交代了模型、任务集合与评分标准的比较资料。
  • 训练数据的语言分布 — 主要模型均未公开。某语言因数据多而占优的解释无法验证。
  • 代理写 Go 更好的内部观察说法 — 仅以社区讨论中被引用的形式确认。未确认到交代测量方法与样本的一手资料。
  • 英文原始讨论串 — 访问被反复拦截，未能打开原文。正文中的反方意见仅反映社区整理中已确认的范围。
  • 编译速度比较的条件 — 原文未写明硬件、代码规模与工具链版本。
  • 生成的 Go 代码中并发缺陷的频率 — 担忧的提出可以确认，测量频率的资料未确认到。

结论：选的不是语言，是验证预算的摆放位置

生成速度上去之后涨价的是确认所花的时间。语言是决定这段时间向谁收费的装置。可以把排版和惯用法交给工具，可以把一类缺陷交给类型检查器，也可以原样留给人。三种都是答案，只是对价不同。

明天就能落地的有三件。

  1. 把评审时间拆成五项来量。如果漏在看清形状、对照惯用法、确认 API 存在，那通常是工具没开的信号，而不是语言选错的信号。
  2. 把现有语言里能打开的特性全部打开。在持续集成里强制格式化，把静态分析和漏洞扫描提升为阻断性检查，类型检查的严格设置从新代码开始适用。换语言排在这之后。
  3. 不把没有条件的比较当依据。缺了版本、硬件、任务和评分标准的数字，连方向都保证不了。

压成一句话：Go 占优不是因为它正确，而是因为在验证成本成为瓶颈的条件下，它的那些特性能兑现价值。换到不满足这个条件的团队，同样的特性只会留下表达力的损失和更长的正文。选语言这件事，过去是、以后仍然是先把约束条件写下来的那件事。
