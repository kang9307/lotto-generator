はじめに - ローカル時刻が1つの瞬間を指さない日がある

ローカル時刻は「2026-03-08 02:30」のように日付と時計の表記だけを持つ値である。これを1つの瞬間に定めるにはタイムゾーンの規則が必要で、夏時間のある地域では切り替え日にその対応が崩れる。時計を進める日には時計が飛ばす区間があり、その中の表記はどの瞬間にも対応しない。時計を戻す日には同じ表記が二度通過するので、1つの表記が2つの瞬間に対応する。

この現象には名前がある。存在しないローカル時刻は英語のドキュメントでgap、nonexistent、invalid timeと呼ばれ、二度来る時刻はoverlap、repeated、ambiguous timeと呼ばれる。以下では前者を「穴」、後者を「重複時刻」と書く。この2つの場合の既定動作がツールごとに異なることが実行結果であり、同じ文字列がツールによって1時間ずれたUTCに変わる。

タイムゾーン規則がデータであり、更新されると過去の時刻の解釈も変わること、切り替え区間では24時間後と明日の同じ時刻が異なることは、タイムゾーンはコードではなくデータだがPythonの出力で扱った。ここではPython1つの説明を超え、同じ入力をNode.jsとPowerShell 5.1がどう解釈するか、その差を防ぐ保存規則を比べる。

扱う問いは次のとおりである。

  • UTCの瞬間をローカル時刻に直して並べると、穴と重複はどう見えるか。
  • Python zoneinfoのfoldは穴と重複でそれぞれ何を選ぶか。
  • Node.jsのDateコンストラクタは穴と重複をどう解決し、読み戻すと値が変わるか。
  • PowerShell 5.1のTimeZoneInfoは2つの場合をどう判別し、変換するか。
  • オフセット付きの文字列とUTC保存は、どこまで曖昧さを消すか。
  • 夏時間のないAsia/Seoulは、比較の基準としてどう見えるか。

UTCから見ると穴と重複が見える

ローカル時刻を入力として受け取る側からは、穴は見えない。逆にUTCの瞬間を30分間隔で並べ、各瞬間をAmerica/New_Yorkのローカル時刻で表示すると、どこに穴があり、どこが重なるかが一目でわかる。Intl.DateTimeFormatのformatToPartsで年・月・日・時・分と略称を読むコードである。

                      hour: '2-digit', minute: '2-digit', hourCycle: 'h23', timeZoneName: 'short'

春の区間では06:30Zが01:30 ESTで、次のサンプルである07:00Zがすぐ03:00 EDTになる。表示されたローカル時刻に02時台はない。秋の区間では05:00Zと05:30Zが01:00・01:30 EDT、06:00Zと06:30Zが再び01:00・01:30 ESTである。ローカル時刻の01時台が1時間離れた2つの瞬間に1回ずつ現れ、両者を区別するのは略称(EDT・EST)だけである。略称を識別子にできない理由は、前の記事の略称の節が別に扱っている。

  • サンプル間隔が30分なので、02:00から02:59の間はこの出力だけでは空に見えるにとどまり、区間全体が空であることは次の節の分単位の判別出力が示す。
  • UTC軸では切り替えは連続している。06:30Zの次が07:00Zで、その間の瞬間はすべて存在する。途切れるのはローカル時刻という表記の側である。
  • 秋の重複は、ローカル時刻の文字列が同じでUTCが異なる2つの瞬間である。文字列をキーにすると、異なる2つの瞬間が1つのキーに合わさる。

Python zoneinfo - foldが選ぶもの

Python 3.9以降のzoneinfoはIANA名でタイムゾーンを作り、datetimeのfold属性で繰り返し区間の2つの瞬間を区別する。公式ドキュメント(datetimeモジュール)はfoldを、繰り返し区間で壁時計の時刻を区別するための値と説明し、0と1は同じ壁時計表記を持つ2つの瞬間のうち、それぞれ早い方と遅い方だと記す。下のコードは穴(03-08 02:30)と重複(11-01 01:30)にfold 0と1を入れ、続けて分単位で正常・穴・重複を判別する。Windowsではzoneinfoにtzdataパッケージが必要で、このPCにはtzdata 2025.3がインストールされている。

import sys
                    from datetime import datetime, timezone
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    UTC = timezone.utc
                    print("python", sys.version.split()[0])
                    
                    
                    def show(naive, fold):
                        dt = naive.replace(tzinfo=ny, fold=fold)
                        u = dt.astimezone(UTC)
                        back = u.astimezone(ny)
                        print(naive.strftime("%Y-%m-%d %H:%M"), "fold=%d" % fold, "offset", dt.strftime("%z"),
                              "-> UTC", u.strftime("%H:%MZ"), "-> back", back.strftime("%H:%M"), back.tzname())
                    
                    
                    show(datetime(2026, 3, 8, 2, 30), 0)
                    show(datetime(2026, 3, 8, 2, 30), 1)
                    show(datetime(2026, 11, 1, 1, 30), 0)
                    show(datetime(2026, 11, 1, 1, 30), 1)
                    print("default fold:", datetime(2026, 11, 1, 1, 30, tzinfo=ny).fold)
                    
                    
                    def classify(naive, tz):
                        a = naive.replace(tzinfo=tz, fold=0)
                        b = naive.replace(tzinfo=tz, fold=1)
                        back = a.astimezone(UTC).astimezone(tz).replace(tzinfo=None)
                        if back != naive:
                            return "nonexistent"
                        return "ambiguous" if a.utcoffset() != b.utcoffset() else "normal"
                    
                    
                    print()
                    for s in ["2026-03-08 01:59", "2026-03-08 02:00", "2026-03-08 02:59", "2026-03-08 03:00",
                              "2026-11-01 00:59", "2026-11-01 01:00", "2026-11-01 01:59", "2026-11-01 02:00"]:
                        print(s, classify(datetime.strptime(s, "%Y-%m-%d %H:%M"), ny))

重複(11-01 01:30)ではドキュメントの記述どおりである。fold=0は早い瞬間のEDT(-0400)で05:30Z、fold=1は遅い瞬間のEST(-0500)で06:30Zとなり、どちらもローカル時刻に戻すと01:30である。穴(03-08 02:30)では、出力が示す動作は次のとおりである。fold=0は切り替え前のオフセット-0500を適用して07:30Zとなり、この瞬間をローカル時刻に戻すと03:30 EDTである。fold=1は切り替え後のオフセット-0400を適用して06:30Zとなり、戻すと01:30 ESTである。穴の中の時刻は例外なく変換されるが、戻した値は入力と異なる。

判別コードの原理は往復変換である。ローカル時刻をUTCに変えて戻した値が異なれば穴であり、同じでもfold 0と1のオフセットが異なれば重複である。出力では02:00から02:59までがすべて穴、01:00から01:59までがすべて重複で、01:59と03:00は正常である。既定のfold値が0であることは、判別リストの直前の行に出ている。foldを指定しないコードは、重複では早い方を、穴では切り替え前のオフセットを黙って選ぶ。

同じtzinfoを持つ2つのaware datetimeを比較したり引いたりすると、tzinfoとfoldが無視されるという公式ドキュメントの文がある(the tzinfo and fold attributes are ignored and the base datetimes are compared)。同じローカル時刻のfold 0と1が==で等しいと出る理由であり、この比較では1時間の差がわからない。この問題は前の記事のDST境界の節が数値で示しているため、ここでは比較の代わりにUTCへ変換してから比べる方法だけを取る。同じローカル時刻のfold 0と1を直接比べると次のようになる。

from datetime import datetime
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    a = datetime(2026, 11, 1, 1, 30, tzinfo=ny, fold=0)
                    b = datetime(2026, 11, 1, 1, 30, tzinfo=ny, fold=1)
                    print("a == b:", a == b, "| offsets:", a.strftime("%z"), b.strftime("%z"))
a == b: True | offsets: -0400 -0500

比較はTrueだが、2つの値のオフセットは-0400と-0500で1時間違う。

JavaScript Date - 穴は先へ、重複は早い方

Node.jsのDateは、ローカル時刻をフィールド(年・月・日・時・分)で受け取ると、現在のプロセスのタイムゾーン規則で解釈する。MDNのDateのドキュメントは、オフセット切り替え区間のローカル時刻を設定するとき、Temporalのdisambiguationの「compatible」と同じ動作を使うと記し、ローカル時刻が2つの瞬間に対応すれば早い方を選び、存在しない場合(穴)は穴の長さだけ先へ進むと説明する(原文: the earlier one is chosen; ... we go forward by the gap duration)。タイムゾーンはスクリプト内でprocess.env.TZによりAmerica/New_Yorkに指定した。下のコードは入力フィールドと、読み戻したフィールドを一緒に出力する。

process.env.TZ = 'America/New_York';
                    const pad = n => String(n).padStart(2, '0');
                    function probe(y, mo, d, h, mi) {
                      const x = new Date(y, mo - 1, d, h, mi);
                      const asked = y + '-' + pad(mo) + '-' + pad(d) + ' ' + pad(h) + ':' + pad(mi);
                      const got = x.getFullYear() + '-' + pad(x.getMonth() + 1) + '-' + pad(x.getDate()) + ' ' + pad(x.getHours()) + ':' + pad(x.getMinutes());
                      console.log(asked, '->', x.toISOString(), 'reads back', got, asked === got ? '(same)' : '(CHANGED)');
                    }
                    probe(2026, 3, 8, 1, 59);
                    probe(2026, 3, 8, 2, 0);
                    probe(2026, 3, 8, 2, 30);
                    probe(2026, 3, 8, 3, 0);
                    probe(2026, 11, 1, 0, 59);
                    probe(2026, 11, 1, 1, 30);
                    probe(2026, 11, 1, 2, 0);
                    console.log(new Date('2026-03-08T02:30:00').toISOString());
                    console.log(new Date('2026-11-01T01:30:00').toISOString());

穴の02:00と02:30は、それぞれ03:00と03:30として読み戻される。瞬間では07:00Zと07:30Zで、Pythonのfold=0の07:30Zと同じである。穴の中の入力は、例外なく1時間後の値に変わる。重複の01:30は05:30Zで、読み戻した値も01:30なので変化はない。ただし早い方(EDT)が選ばれたことはフィールドだけではわからず、UTCを出力して初めて見える。最後の2行が示すように、オフセットのないISO文字列(例: 2026-03-08T02:30:00)も同じ規則でローカル時刻として解釈され、同じ瞬間になる。

  • Dateでは、このコードが使ったgetXxxでフィールドを読み、入力と比較する方法で穴を見つけられる。02:00と02:30にCHANGEDと出た行がその合図である。
  • 重複は読み戻しても値が同じなので、この方法ではわからない。UTCの値が2つありうることを、コードが別に知っている必要がある。
  • TZ環境変数方式の危険(プロセスごとに地域が変わること)は、前の記事の環境変数の節がNode.jsの出力で示した。

PowerShell 5.1 - 重複は標準時、穴は例外

  • 重複では分かれる。Python(fold=0)・Node.jsは早い方、PowerShellは標準時(遅い方)なので、同じ文字列で1時間の差が出る。
  • 3つのツールとも、呼び出し側が何も指定しなければ警告なしに値を返す経路がある。例外を出すのはPowerShellの穴だけである。

同じ時刻は1日に何回来るか - 0回、1回、2回

毎日02:30に動くジョブや01:30に設定した通知を考えると、問題がはっきりする。1つのローカル時刻が1日に現れる回数を数えると、切り替え日の値は普段と異なる。次のコードはUTC軸を15分単位で走査し、ローカル時刻がちょうどその値になる瞬間を集める。

from datetime import datetime, timedelta, timezone
                    from zoneinfo import ZoneInfo
                    
                    ny = ZoneInfo("America/New_York")
                    UTC = timezone.utc
                    
                    
                    def occurrences(y, m, d, hh, mm, tz):
                        # UTC instants whose wall clock in tz reads exactly y-m-d hh:mm (15-minute scan, +-14 h)
                        base = datetime(y, m, d, hh, mm, tzinfo=UTC)
                        hits = []
                        for k in range(-14 * 60, 14 * 60 + 1, 15):
                            u = base + timedelta(minutes=k)
                            w = u.astimezone(tz)
                            if (w.year, w.month, w.day, w.hour, w.minute) == (y, m, d, hh, mm):
                                hits.append(u.strftime("%H:%MZ"))
                        return hits
                    
                    
                    for y, m, d, hh, mm in [(2026, 3, 7, 2, 30), (2026, 3, 8, 2, 30), (2026, 3, 9, 2, 30),
                                            (2026, 10, 31, 1, 30), (2026, 11, 1, 1, 30), (2026, 11, 2, 1, 30)]:
                        h = occurrences(y, m, d, hh, mm, ny)
                        print("%d-%02d-%02d %02d:%02d" % (y, m, d, hh, mm), "->", len(h), "time(s)", h)

                    2026-03-08 02:30 -> 0 time(s) []
                    2026-03-09 02:30 -> 1 time(s) ['06:30Z']

                    2026-11-02 01:30 -> 1 time(s) ['06:30Z']

02:30は03-07と03-09に1回ずつ来るが、03-08には0回である。01:30は10-31と11-02に1回ずつで、11-01には2回(05:30Zと06:30Z)である。「毎日02:30」という規則は、春の切り替え日には対象の瞬間がなく、秋の切り替え日(01:30基準)には対象の瞬間が2つある。スケジュール表記自体の別の落とし穴は、cronのstepの記事が別に扱っている。この出力が示すのは、ローカル時刻の規則が1日に0回・1回・2回該当しうるという事実である。

安全に扱う規則 - 拒否するものと選ぶもの

先の実行で2つのことが明らかになった。ローカル時刻の文字列は、穴では値がなく、重複では値が2つある。そしてツールの既定の選択は互いに異なる。したがって規則は、既定の選択に任せず入力の段階で方針を決めることである。下のコードは、Pythonで穴は例外として拒否し、重複はfoldがなければ拒否し、foldがあれば変換する関数である。

from datetime import datetime, timezone
                    from zoneinfo import ZoneInfo
                    
                    UTC = timezone.utc
                    
                    
                    def to_utc(naive, tz, fold=None):
                        a = naive.replace(tzinfo=tz, fold=0)
                        b = naive.replace(tzinfo=tz, fold=1)
                        if a.astimezone(UTC).astimezone(tz).replace(tzinfo=None) != naive:
                            raise ValueError("nonexistent local time: " + naive.isoformat(" "))
                        if a.utcoffset() != b.utcoffset():
                            if fold is None:
                                raise ValueError("ambiguous local time: " + naive.isoformat(" ") + " (fold=0 or fold=1 required)")
                            return (b if fold else a).astimezone(UTC)
                        return a.astimezone(UTC)
                    
                    
                    ny = ZoneInfo("America/New_York")
                    for n, f in [(datetime(2026, 3, 8, 2, 30), None), (datetime(2026, 3, 8, 3, 30), None),
                                 (datetime(2026, 11, 1, 1, 30), None), (datetime(2026, 11, 1, 1, 30), 0),
                                 (datetime(2026, 11, 1, 1, 30), 1)]:
                        try:
                            print(n.isoformat(" "), "fold=%s" % f, "->", to_utc(n, ny, f).isoformat())
                        except ValueError as e:
                            print(n.isoformat(" "), "fold=%s" % f, "-> ValueError:", e)

  • 瞬間を保存するときは、UTC時刻(またはオフセット付きの時刻)を使う。オフセットを付けて渡した出力(前のオフセットの節)ではUTCの値がどのツールでも同じで、オフセットなしでローカル時刻だけを渡した出力(前の比較表)ではツールごとに分かれた。
  • 人が入力したローカル時刻は、タイムゾーン名と一緒に受け取る。タイムゾーン名がなければ、穴と重複は判定できない。
  • 穴は入力エラーとして返し、別の時刻を選んでもらう。黙って1時間後へ補正する動作(Node.js)は、ユーザーが入力した値を変えてしまう。
  • 重複は2つの候補(05:30Zと06:30Z)を見せて選ばせるか、方針(早い方か遅い方か)をコードに明示する。ツールの既定に任せると、PowerShellとPythonが異なる側を選ぶ。
  • .NETでは、UTCからローカル時刻に変えたDateTimeを再びUTCに戻さない。DateTimeOffsetでオフセットを一緒に持ち運ぶ。
  • オフセット付きの入力でも安心はできない。前のオフセットの節で、穴(03-08 02:30)に-04:00を付けた文字列は06:30Zと解釈され、これはローカル時刻01:30 ESTの瞬間である。受け取ったオフセットがそのタイムゾーンで可能な組み合わせかどうかは別に検査する。
  • テストデータに2026-03-08 02:30と2026-11-01 01:30のような穴と重複を入れ、ローカル時刻の文字列をキーに使うコードを点検する。

DB側の同じ問題、つまりセッションのタイムゾーンがAT TIME ZONE演算の結果型に入り込む問題は、PostgreSQL AT TIME ZONEの記事が別に扱っている。時刻と整数の間の変換で単位が分かれる問題は、タイムスタンプ変換の記事が扱っている。

確認できなかったこと

  • Linux・macOSでのNode.js・Python・PowerShellの動作。出力はすべてこのWindows PCで得た値である。
  • PowerShell 7(.NET 8以降)のTimeZoneInfoがIANA名を受け付ける方法と、穴・重複の扱い。このPCにはpwshがインストールされていない。
  • ECMAScript仕様本文の該当アルゴリズム。仕様ページで該当の節を開けなかったため、MDNの説明のみを引用した。
  • Pythonで穴のfold 0・1が切り替え前・後のオフセットを選ぶ動作のドキュメント上の根拠。確認したdatetimeのドキュメントはfoldを繰り返し区間の用途としてのみ説明しており、穴での動作は出力でのみ確認した。
  • Windowsのタイムゾーンデータに1988年の夏時間がない理由と、別のWindowsビルドでの結果。調整規則数0はこのPCで読んだ値である。
  • 30分単位の切り替えや、深夜0時に切り替えが起きるタイムゾーンでの動作、そしてスケジューラ(cron・タスクスケジューラ)が切り替え日にジョブを0回・2回実行するかどうか。
  • Temporal API(このNode.jsのバージョンでは未定義)のdisambiguationオプションの動作と、Pythonのpytz・dateutilのような他のライブラリ。
