LLMのボトルネックは演算ではなくデータ移動である - Apple Neural Engineの逆アセンブルが示した真実

M5におけるANE統合の背景から2,048本MACレーン、カーネル・タイルDMAの直列化遅延まで徹底解析

2026-09-13 開発・インフラ

AIアクセラレーターの性能指標を論じる際、半導体ベンダーが最も強調するのは演算処理能力、すなわち秒あたりテラ演算数（TOPS, Tera Operations Per Second）です。スマートフォンからノートPC、プロ向けワークステーションに至るまで、新世代プロセッサが登場するたびに専用ニューラル処理ユニット（NPU）のTOPS数値が何倍に達したかが大々的に喧伝されます。ダイ上に高密度な積和演算（MAC）アレイが並ぶほど、大規模モデルの推論スループットも直線的に向上するはずだという期待を抱きがちです。

しかし、近年の大規模言語モデル（LLM）を実機上で実行した瞬間、その期待は容易に裏切られます。数十TOPSを誇る最新NPUを搭載したチップセットであっても、数十億パラメータ規模のTransformerモデルを動かすと、秒あたりのトークン生成速度は期待を大きく下回る一桁台や辛うじての二桁台に留まる事態が頻発します。演算ユニットの使用率は半分にも満たず、ハードウェアは常に何かを待機し続けています。この乖離の真相を理解するには、演算ブロックの公称ピーク値ではなく、データがチップ内外を行き交う物理的なデータ移動経路を解剖しなければなりません。

システムソフトウェアエンジニアのEileen Yoon氏が公開したApple Neural Engine (ANE) の深層リバースエンジニアリング分析は、まさにこの疑問に対してシリコン回路と実測データに基づく明確な答えを提示しています。16個の演算コアと合計2,048本の並列積和演算（MAC）レーンを備えたApple Silicon専用NPUが、なぜ最新のLLM推論において演算能力ではなくデータ移動の足枷に縛られてしまうのか、そしてAppleが最新のM5チップにおいてANEコアをGPU内部へと統合した決定的な背景が克明に描かれています。

本稿は2026年8月10日にEileen Yoon氏が公開したANEリバースエンジニアリング技術報告に基づいています。特定のハードウェア設計を批判する意図ではなく、2017年の畳み込みニューラルネットワーク（CNN）時代に最適化されたシリコンの前提条件が、2026年のTransformerワークロードと衝突した際に生じる構造的摩擦を、計測データに基づいて客観的に解説します。

M5がANEをGPU内部へ統合した理由 - スタンドアロンNPU時代の転換点

Apple SiliconにおけるLinuxサポートを切り拓いてきたEileen Yoon氏は、3年前にANE向けLinuxドライバーの開発を中断した経緯の回顧から筆を起こしています。当時同氏が至った所感は、「このブロックは実質的にそれほど有用ではない」という結論でした。ANEのアーキテクチャは極めて特定の処理様式に強く依存しており、汎用的なアクセラレータープラットフォームを構築するには閉鎖的すぎました。ドライバーを通じてハードウェアAPIを開放したとしても、実行可能なワークロードの種類を広げることは叶いませんでした。実際、Apple自身のデスクトップOSであるmacOSでさえ、Finder上で高解像度プレビュー画像をアップサンプリング生成するような限定的バックグラウンド処理を除けば、ANEを定常的に活用していませんでした。

しかし、2025年に登場したM5チップの設計変更は、このアクセラレーターブロックに決定的な終止符を打ちました。AppleはM5の最大の目玉機能として「LLM性能」を大々的に掲げると同時に、独立していたANEコアを物理的に「GPUコアの内部へと折り畳んで統合（conveniently folded inside the GPU cores）」したのです。著者はこの劇的な転換を目の当たりにし、これを「スタンドアロン型NPUの終わりの始まり」と表現しました。

専用シリコン面積を占有していた固定機能アクセラレーターが廃止され、汎用並列プロセッサであるGPUの内部演算ユニットとして吸収された事実は、極めて重大な意味を持ちます。それは積和演算ユニット自体の価値が失われたからではなく、スタンドアロン型NPUが固執してきた固定データフローと専用スケジューラが、Transformer中心のLLMワークロードの要求と根本的に両立できなくなったことを示しています。著者が3年ぶりにM1のANEを徹底的に解剖し、演算、データパス、スケジューラ、メモリ、実行モデルの全貌を逆アセンブルした動機はここにありました。

  • 独立型NPUの限界: 柔軟なメモリ再利用が不可能な固定データフロー構造により、ドライバー層を開放しても対応ワークロードが拡張できませんでした。
  • M5におけるアーキテクチャ統合: M5世代においてAppleはLLMスループットを中核機能と位置付け、独立したANEブロックをGPUシェーダー内へと吸収統合しました。
  • シリコン設計思想の転換: 固定機能パイプラインから脱却し、GPUの柔軟なユニファイドメモリアーキテクチャと結合する方向へオンデバイスAI基盤の主軸が移行しました。

A11 Bionicから始まったシリコンの遺産 - 2017年のCNN最適化設計

ハードウェアアーキテクチャの妥当性を評価するためには、その設計が最初に物理的シリコンとして刻まれた歴史的文脈を振り返る必要があります。現在のApple Silicon Mシリーズに搭載されているANEの骨格は、デスクトップ向けに白紙から設計されたものではありません。その起源は2017年のiPhone Xに搭載されたA11 Bionicチップにまで遡ります。

2017年当時、モバイル機器におけるAIワークロードの主流は、密な画像処理を担う畳み込みニューラルネットワーク（CNN）でした。Face IDにおける顔認証、カメラセンサー入力のリアルタイムノイズリダクション、被写体と背景を分離するセマンティックセグメンテーションなどがチップ設計者に課された最重要課題でした。これらのCNN演算には極めて特徴的な規則性があります。重みフィルターテンサーが一度ロードされると、数百万画素に及ぶ二次元空間上の入力スライディングウィンドウ全体にわたって何度も繰り返し再利用されるという点です。

したがって2017年のシリコン設計者たちは、外部DRAMから重みをチップ内へ転送する際に一定のレイテンシを要したとしても、コア内部のローカルメモリに一旦蓄積してしまえば、圧倒的な空間的・時間的データ再利用（Predictable Reuse）によって外部バス帯域幅の負荷を相殺できると確信していました。モバイル機器特有の厳格な消費電力と熱設計枠（TDP）の中でバッテリーを温存しつつ高TOPSを達成するための、当時の最適解だったのです。ANEのすべてのデータパスとキャッシュ階層は、この2017年の前提を忠実に満たすよう設計されました。

  • 設計原型の成立: 2017年のA11 Bionicで初実装されたデュアルコアNPU構造が拡張され、M1の16コア構成へと受け継がれました。
  • CNN最適化の前提: 密なテンソル縮約演算と、入力平面全体に及ぶ高い重み再利用性を前提としたビジョンモデルに特化して構築されました。
  • モバイルの物理的制約: 限られたバッテリー容量とファンレス放熱環境において、メモリアクセス回数を最小化するための専用ローカルバッファ設計が採用されました。

16個の演算コアと2,048本の並列MACレーンの内部構造

ANE内部の演算クラスターの規模を確認すると、M1 ANEには16個の並列演算コアが整然と配置されています。そして各演算コアの内部には、128本のFP16並列積和演算（MAC）レーンが統合されています。8ビット整数（INT8）で動作させる場合にはレーン幅が実質的に倍増し、256本のINT8レーンとして機能します。チップ全体としての空間並列規模は以下の通りです。

16コア × 128レーン/コア = 合計 2,048本の並列MACレーン

この2,048本のレーンは、単一クロックサイクルごとに2,048回のスカラー積和演算を同時に空間実行します。著者が指摘するように、個々のMACレーンは自身が計算している数値が行列のどの次元なのか、テンソルのどの軸に沿って縮約されているのかを一切認識していません。オペランドaとbが供給されると、16ビット乗算器を経て32ビット加算器へと渡され、ループの間は32ビットアキュムレータレジスタに結果を加算し続けます。

│ ┌───────── 256× MACs ─────────┐  ┌────────────┐ │
│ │ MAD ─► add ─► accumulator   │─►│ activation │ │
│ │        ▲          │         │  └────────────┘ │
│ │        └──────────┘         │                 │
│ └─────────────────────────────┘                 │
└─────────────────────────────────────────────────┘

このデータパスの最大の省電力特徴は、積和演算の中間和（Partial Sum）を保持するフィードバックループが、MACレーン内部のローカルレジスタ内で完結している点です。演算周期の合間に外部メモリへ中間結果を読み書きするトラフィックが発生しないため、純粋な演算集約型タスクにおいては極めて高いエネルギー効率を誇ります。

operand a ──┐   ┌────────────┐   p[31:0]   ┌──────────────┐   s_next[31:0]  ┌─────────────┐
            ├──►│ MULTIPLIER │────────────►│ 32-BIT ADDER │────────────────►│ ACCUMULATOR │
operand b ──┘   └────────────┘             └──────▲───────┘                 └──────┬──────┘
                                                  │                                │ s[31:0]
                                                  └────────────────────────────────┘

演算精度に関して、ANEは固定小数点演算で中間加算を保持し、最終出力時にFP16へと変換して読み出す構成をとっています。乗算器は16ビットで動作し、32ビットレジスタ内では符号付きQ16.16固定小数点形式として累積されます。著者がCoreMLを用いたテストでアキュムレータの飽和特性を計測したところ、2の15乗（32,768）でクランプ（Clamp）が発生し、符号付き32ビット固定小数点レジスタの仕様と完全に一致することが実証されました。

ワークロードの不整合 - 畳み込み再利用パターンとTransformerデコードの衝突

しかし、この強大な2,048本のMACレーンがTransformerベースの大規模言語モデルと対峙した瞬間、その設計思想は決定的な破綻を迎えます。CNNの畳み込み層で内積（Dot Product）を計算する演算子も、TransformerのAttention機構でQueryとKeyの内積を計算する演算子も、本質的な数学処理としては同一のMAC処理です。演算器そのものはモデルの種類を選びません。

しかし、オペランドがいつ、どこから流入し、どこに滞留し、どう排出されるかを司るデータフロー（Dataflow）に目を向けたとき、両者の振る舞いは真逆に乖離します。LLMの推論は、プロンプトを一括処理するPrefill段階と、1トークンずつ連鎖的に出力する自己回帰デコード（Autoregressive Decode）段階に大別されます。実際のチャット応答やコード生成において体感速度を決定付けるのは、この自己回帰デコード処理です。

自己回帰デコードでは、1ステップごとにたった1つのトークンベクトルのみが入力されます。数十億パラメータに及ぶモデル全体の巨大な重み行列は、この1つのトークンベクトルと行列-ベクトル積（GEMV）を実行するためだけに、外部メインDRAMからチップ内へ丸ごとストリーミングされなければなりません。そして次のトークンを生成するためには、モデル全体の重み行列を外部メモリから再び最初から最後まで読み直す必要があります。すなわち、2017年のCNNアーキテクチャが絶対視していた「パラメータの空間的・時間的再利用」という大前提が、LLMのデコードでは完全に消失するのです。

  • 重み再利用の崩壊: CNNでは1つの重みが数万回再利用されたのに対し、LLMデコードにおけるトークンあたりの重み再利用回数は実質1回に収束します。
  • 演算強度の急落: メモリから1バイト取得する間に実行できる演算回数が極端に低下し、システムは完全にメモリ帯域幅バウンドの領域へと転落します。
  • アーキテクチャの空転: 演算コアは重みデータの到着を待つだけで大半のサイクルを遊休させ、メモリバスだけが過負荷に喘ぐ事態に陥ります。

実測DMA帯域幅 - KernelとTile、そしてGPU読み取り性能の格差

この不整合は単なる理論的仮説ではありません。Eileen Yoon氏はANE内部のダイレクトメモリアクセス（DMA）エンジンとGPUのメモリ読み込み速度を実機上で厳密に計測し、具体的な数値として白日の下に晒しました。測定手法として、CoreML環境においてカーネルおよびタイルのサイズを実行時間で除算してANEの転送帯域を算出し、GPUについてはMetalバッファ読み込みシェーダーを用いてユニファイドメモリアクセス帯域を測定しました。

その実測値は、衝撃的なハードウェア格差を示しています。ANE内部で重みを転送するKernel DMAの帯域幅はわずか37.99 GB/sでした。また、入力活性化テンサーをDRAMからL2キャッシュへ転送するTile DMAの帯域幅は59.08 GB/sと計測されました。これに対し、同一ダイ上に存在するGPUのメモリ読み取り帯域幅は77.70 GB/sに達していました。

単一経路の数値だけを比較しても、ANEの重み転送パイプラインはGPUの半分程度の帯域幅しか備えていません。2,048本のMACレーンがどれほど強大であっても、重みをDRAMから汲み上げる導管そのものがGPUに比べて著しく細く作られていたのです。

  • 重み搬送経路の狭隘さ: Kernel DMAの37.99 GB/sという値は、毎ステップ巨大なパラメータを読み出すLLMデコードにとって構造的に不足しています。
  • タイル転送の頭打ち: Tile DMAの59.08 GB/sも、チップ全体のメモリコントローラーの最大潜在能力を十分に引き出せていません。
  • GPUメモリの優位性: 専用設計を謳うNPUでありながら、単純なメモリデータ読み出しスループットにおいて汎用GPUパイプラインの後塵を拝する結果となりました。

ボトルネックの正体 - 合計帯域幅ではなく2つのDMA経路の直列化(Serialization)

しかし、真に致命的なボトルネックは、単一経路の帯域幅の低さだけではありませんでした。Kernel DMA（37.99 GB/s）とTile DMA（59.08 GB/s）の数値を単純合算すると、理論上の合計転送要求は約97.07 GB/s（約98 GB/s）となります。これはテスト環境となったM3プロセッサのシステムDRAM帯域幅上限である100 GB/sに極めて近いものの、超過はしていません。

仮にANEのメモリサブシステムが、重み転送と入力転送の2つのDMAリクエストをコントローラーに対して非同期かつ同時に並行発行できるよう設計されていれば、理論上は98 GB/s付近で処理のオーバーラップが起きていたはずです。しかし、両方の転送を同時に必要とするワークロードを実行した際の実測データは、「全体の実行時間が2つの経路の個別実行時間の単純な物理的合算と完全に一致した」ことを示しました。

この計測結果が示す技術的真実は明快です。「ANE内部の2つのDMA経路は並行動作できず、直列（serially）に順次要求を処理している」ということです。重みの転送が完了するまで入力タイルの転送は待機させられ、タイルの転送が終わって初めて次のステップに進みます。著者はこの実態を指して、ANEのDRAMスループットは「二重の不利益（doubly penalized）」を被っていると結論づけました。個々の経路の速度がGPUより遅いだけでなく、その遅い2つの経路のレイテンシが並行処理されずに直列加算されてしまうためです。

  • リクエストの完全直列化: 独立しているはずの2つのDMAチャネルが相互排他的に順次実行され、待機レイテンシをそのまま積み上げてしまいます。
  • 二重のペナルティ: 物理帯域幅の低さと直列化による待機時間の累積が重なり、実効DRAM利用効率を著しく押し下げます。
  • バス帯域の遊休: システム側は100 GB/sを受け入れ可能であるにもかかわらず、ANE自体の直列化制約によってメモリバスの能力を半分しか消費できません。

ルーフライン限界とオンデバイスLLM推論設計における実践的示唆

プロセッサアーキテクチャの性能限界を視覚化・診断する代表的フレームワークにルーフラインモデル（Roofline Model）があります。システムの理論ピーク演算性能とメモリ帯域幅の傾きが交差するグラフ上で、実行アルゴリズムの演算強度（転送バイトあたりの演算数）がどこに位置するかによって、律速要因が演算かメモリ帯域かを判別します。

M1 ANEは公称仕様として、68 GB/sのシステムDRAM帯域幅環境下で11 TOPSのピーク演算能力を発揮するよう規定されています。データの再利用性がほとんど存在しないLLMの自己回帰デコードをこの上で走らせると、動作点はルーフライン右上の平坦な天井（Compute-bound）ではなく、左下の急峻な傾斜領域（Memory bandwidth-bound）の最下部に完全に拘束されます。

著者が算出したモデル計算によれば、自己回帰デコードがメモリ帯域のルーフライン限界に張り付いている状態において、トークン生成速度を秒間10トークンから25トークンへと2.5倍に引き上げたい場合、ANEの演算コアを増やすことやMACレーンを拡張することは一切効果を持ちません。デコード速度を2.5倍にするための唯一の条件は、「メモリストリーミング帯域幅を正確に約2.5倍に拡張すること」だけです。

この分析がオンデバイスAIアプリケーションを開発・配備するエンジニアに投げかける示唆は明白です。ハードウェア仕様書に記載された「NPU TOPS」の数値は、LLM推論においてはスループットの保証になり得ません。モデルパラメータがどのようなバスを経由して転送されるのか、DMAアクセスが並行化されているのか、そしてユニファイドメモリの実効読み出し帯域幅がどれほど確保されているかを確認しないままNPU専用ランタイムに依存することは、演算器が飢餓状態に陥るハードウェアに空虚な期待を寄せることと同義です。

  • TOPS値の錯覚: 11 TOPSという巨額の演算力は、毎秒全パラメータを外部DRAMから読み出すLLMデコードにおいてはほとんど眠ったままになります。
  • 帯域幅との線形比例: デコード処理速度を2倍にしたければ、コア数やクロックではなく、メモリパイプラインの物理帯域幅を2倍にする必要があります。
  • ランタイム選定の実務: オンデバイス推論においては、固定的なNPUよりも、広大なユニファイドメモリ帯域をフル活用できるGPUバックエンド（Metal等）の方が結果として圧倒的なトークン生成速度を叩き出す論拠がここにあります。

制御パイプラインとデータパス - ControlDMAから融合活性化関数まで

ANEの全体像を精密に把握するには、タスク記述子（Task Descriptor）の受領から演算末端の活性化関数ブロックに至る全データパスを辿る必要があります。ANEにおける処理実行は、厳格に独立した3段階のDMAパイプラインによって開始されます。

まずControlDMAが起動し、ホストソフトウェアから渡されたタスク記述子（TD）をANE内部のハードウェア構成レジスタファイルへとコピーします。続いてKernelDMAが稼働し、DRAM上の重みテンサーWを各演算コアに直結されたローカルカーネルメモリ（KMem）へとロードします。最後にTileDMAが実行され、入力活性化テンサーXをDRAMから共有L2キャッシュへとストリーミングします。16個のコアはこれらのデータを基に行単位の積和縮約を実行し、出力行列Yの1行を生成します。

ここで見落としてはならない極めて決定的なアーキテクチャ上の制約は、共有L2キャッシュとコア専用KMemの間にはハードウェア的な直接接続経路が一切存在しないという点です。KMemはKernelDMAからしか書き込めず、L2キャッシュはTileDMAからしか書き込めません。重みデータと入力データがチップ内部で柔軟にバッファを融通し合うようなメモリ再構成は物理的に遮断されています。

一方、積和演算完了後の活性化関数処理（Activation）には、非常にユニークなハードウェア最適化が施されています。縮約演算が完了した直後、結果をメモリへ書き戻すことなくMACレーン末端の活性化ブロックへ直接パイプラインされます。Eileen Yoon氏がCoreMLコンパイラが生成したハードウェアレジスタファイル（hwx）を解析したところ、オフセット0x4288から始まる連続した33個のFP16定数が発見されました。

この33個の定数は、tanh関数を32区間に均等分割して量子化したサンプルテーブルでした。ANEは複雑な超越関数回路をコアごとに持たせる代わりに、33エントリーの区分線形補間ルックアップテーブル（Piecewise-linear LUT）ハードウェアによって非線形活性化を単一サイクルに近い速度で算出する仕組みを備えていたのです。CNN処理において極めて高い効率を誇ったこうした職人芸的最適化も、前段のDMA直列化というメモリの壁の前では性能を引き出す決定打にはなり得ませんでした。

  • 隔離された3段階DMA: ControlDMA、KernelDMA、TileDMAがそれぞれ独立したレジスタとローカルメモリを満たします。
  • キャッシュ間直接パスの欠如: L2キャッシュとKMemの間に相互転送経路がなく、柔軟なオンチップメモリの再配分が不可能です。
  • 33エントリー区分線形LUT: 複雑な非線形関数を33個のFP16定数による線形補間で高速処理する極端な固定パイプラインを実装しています。

確認できなかったこと

Eileen Yoon氏による一次リバースエンジニアリング技術報告の記載範囲および解析環境の物理的制約に基づき、以下の項目については本稿において確認できていません。

  • M5チップにおけるANE-GPU統合の精密なマイクロアーキテクチャ詳細: 原文はM5がANEコアをGPU内部へと吸収統合したという発表事実と構造的意義に言及しているものの、統合後のレジスタマップ、共有キャッシュ構成、ディスパッチスケジューラの結合仕様などの詳細データは含まれていません。
  • M3およびM4等の後続世代ANEにおけるDMA直列化の存続可否: 本文の詳細なレジスタ解析およびハードウェア追跡はM1プロセッサのANEブロックを対象に実施されたものであり、M3やM4の独立型ANEにおいて2つのDMA経路の並行実行が可能になっていたかどうかは原文で確定されていません。
  • INT4以下の極端な低ビット量子化適用時における実効帯域幅の挙動: ベンチマークが主にFP16およびINT8演算レーンを中心に行われたため、4ビット以下の重み量子化（AWQ、GPTQ等）を適用した際のKernel DMA転送速度とレイテンシの定量的変化は実測されていません。
  • CoreML以外の独自フレームワーク駆動時におけるドライバー層のキューイングオーバーヘッド: 実測に使用されたツールがApple公式のCoreMLランタイムおよびhwxレジスタコンパイラであったため、macOSのドライバー層自体が内包するソフトウェアキューイング遅延がDMA計測値に及ぼした影響の純粋な切り分けは行われていません。
