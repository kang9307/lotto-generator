Why Local LLMs Are Slow on a Mac - How to Check the GPU Is Actually Being Used

The device being detected and the device actually running are two different things

Aug 04, 2026 IT/Tech

Introduction: The Mac Is Not Slow, the GPU Is Idle

You are running a local LLM on a MacBook. The fans are up, the battery is melting, and tokens are arriving one character at a time. What happens next is usually predictable. You drop to a smaller model, crank the quantization harder, and when that does not help you conclude that Macs are just not built for this.

Open Activity Monitor at that moment and bring up the GPU History window, though, and you will often find GPU utilization sitting near the floor. The Apple silicon GPU is doing nothing while every CPU core is pinned. The model is not too big. The computation is running on the wrong device.

This happens especially often when you assembled the pipeline yourself. The model loading code came from somewhere else, and that code was written to use the GPU when CUDA is present and fall back to the CPU when it is not. A Mac has no CUDA, so the branch quietly takes the CPU path with no error at all. It is not a failure, it is a silent fallback, and nothing shows up in the logs.

This article covers exactly that. How to verify whether you are using the GPU right now, which switches actually exist in each framework, and five cases where turning it on changes nothing. Choosing new hardware is covered in the local LLM hardware selection guide, and how far to push quantization formats is covered in the local LLM running guide on hardware requirements and GGUF quantization trade-offs, so neither is repeated here. What this article deals with is making the Mac you already own use its GPU.

For context, what put this topic back in circulation was an optimization write-up from someone's personal pipeline. A one-line change cut total runtime roughly in half. Copying that multiplier over to your setup is meaningless, and the reason is laid out further down.

1. Unified Memory - Why Moving to the GPU Means Something Else on a Mac

Get the structure right first and everything after it follows. On a PC with an NVIDIA card, using the GPU means copying data into VRAM. System memory and VRAM are physically different chips, and the transfer between them is a cost. That is why CUDA code is perpetually concerned with where each thing lives.

Apple silicon differs here. As the MLX documentation puts it, the CPU and GPU have direct access to the same memory pool. Arrays live in unified memory without you specifying a location, and instead the operation chooses which device executes it. Three practical consequences follow.

  • There is no copy cost. Mixing CPU preprocessing with GPU inference does not trigger a transfer at the boundary
  • The model size ceiling is set by total machine memory, not VRAM. A model that will not fit on a single 16GB card fits on a machine with 64GB of unified memory
  • But contention appears. Whatever the browser and IDE consume is memory the model cannot have. That problem does not exist when VRAM is separate

In PyTorch terminology this device is called MPS. The official description is that it introduces a new device that maps machine learning computational graphs and primitives onto the Metal Performance Shaders Graph framework and the tuned kernels provided by the Metal Performance Shaders framework, respectively. In short, it is the backend that connects PyTorch to Apple's GPU compute stack.

One expectation that regularly goes wrong here. Unified memory means you can allocate generously. It does not mean memory bandwidth is generous. LLM decoding sweeps the weights on every token, which makes it memory bandwidth bound, so tokens per second vary widely across chip tiers even at the same memory capacity. Capacity decides whether it loads. Bandwidth decides how fast it runs. Do not conflate the two axes.

Only switches that actually exist are listed here. What matters is that the defaults differ by framework. Some need turning on, some are already on.

2.1 PyTorch - There Are Two Things to Move

PyTorch defaults to the CPU unless you say otherwise, so you have to specify the device in code.

import torch

print(torch.backends.mps.is_available())  # usable on this machine right now?
print(torch.backends.mps.is_built())      # does the installed build contain MPS?

device = "mps" if torch.backends.mps.is_available() else "cpu"
model = model.to(device)
inputs = inputs.to(device)   # ← this is the line people forget

That last line is the most common mistake. Move the model but leave the input tensors on the CPU and you either get a device mismatch error or, if a library quietly reconciles it for you, a transfer sneaks into every step. There is also a clear reason to call both check functions. If is_available() is false, the problem is the machine or the macOS version. If is_built() is false, the PyTorch build you installed has no MPS. The latter is fixed by reinstalling. The former never is.

The messages PyTorch prints when it fails already draw that same distinction. One reads 「MPS not available because the current PyTorch install was not built with MPS enabled.」 The other reads 「MPS not available because the current macOS version is not 14.0+ and/or you do not have an MPS-enabled device on this machine.」 Read the message to the end and it has already told you which one you have.

2.2 llama.cpp - It Is Already On, So Learn to Turn It Off

If you run GGUF models through llama.cpp, there is no switch to hunt for. The official build documentation states plainly that Metal is enabled by default on macOS. What you need to learn here is the opposite direction: how to turn it off so you have a baseline.

# Zero GPU layers: GPU inference is off, but some ops may still touch the GPU
llama-cli -m model.gguf -ngl 0 -p "Hello"

# Fully off: disables GPU acceleration entirely
llama-cli -m model.gguf --device none -p "Hello"

The difference between the two options matters. The documentation notes that even with -ngl 0, the GPU may still be used to accelerate some parts of the computation. So if you want an honest answer to how long this takes without a GPU, you need --device none. Comparing against -ngl 0 without knowing this means your baseline already had GPU help, and the multiplier comes out smaller than it really is.

You can also strip it at build time. Passing -DGGML_METAL=OFF to CMake builds without Metal. If a binary you compiled yourself feels slow, checking whether that flag crept into the build is the first thing to do.

2.3 MLX - Specify the Device on the Operation, Not the Array

MLX, released by Apple, is designed around unified memory, so the mental model is different. There is no API for moving an array. Instead you specify the execution device on the operation through the stream argument.

import mlx.core as mx

a = mx.random.normal((4096, 512))
b = mx.random.uniform(shape=(512,))

c = mx.add(a, b, stream=mx.gpu)   # on the GPU
d = mx.add(a, b, stream=mx.cpu)   # same arrays, on the CPU

The point is that the same arrays a and b are used on both sides without a copy. When there is a dependency, the MLX scheduler inserts a dependency between the streams automatically so ordering is preserved. The documentation shows an example that reaches roughly 2x by splitting heavy work onto the GPU and light work onto the CPU and running them in parallel. That figure comes from the documentation's example workload, though, not from LLM inference.

3. Three Procedures for Checking Whether the GPU Is In Use

This is the core of the article. Three layers have to be checked separately. Looking at only one of them will always lead you to a wrong conclusion.

3.1 First - Is the Device Detected

This is the code-level check. Print both is_available() and is_built() as shown above. Most setups pass this step. And passing it does not mean you are using the GPU. A device existing and your code using it are separate facts.

3.2 Second - Is It Actually Running

This is the system-level check. With inference in flight, use one of the following.

  • Open Activity Monitor and bring up the GPU History window from the Window menu. The graph should rise when inference starts
  • In a terminal, run sudo powermetrics --samplers gpu_power -i 1000 -n 5 and read the GPU figures. It requires administrator privileges

The reading rule is simple. If inference is running but the GPU graph is flat while every CPU core is saturated, the computation is on the CPU no matter what the device check said. If the GPU graph does rise but utilization oscillates low, it is time to suspect the CPU fallback described in the next section.

3.3 Third - Is It Holding Memory

PyTorch exposes functions that show this directly. Print all three together and the state becomes obvious.

import torch

# GPU memory currently occupied by tensors, in bytes
print(torch.mps.current_allocated_memory())

# Total GPU memory the Metal driver allocated for this process, in bytes
print(torch.mps.driver_allocated_memory())

# Recommended max working set size, in bytes
print(torch.mps.recommended_max_memory())
  • current_allocated_memory() is near zero → the model never landed on the GPU. Re-check your device assignment
  • driver_allocated_memory() is close to recommended_max_memory() → you are in the memory pressure zone described in the next section
  • Both look normal and it is still slow → this is not a device problem. Look at your measurement method or the shape of the workload

Passing these three layers in order is the whole of the diagnosis. More than half of all I turned the GPU on and nothing happened reports actually stop at step 3.2.

4. Measuring Properly - What You Need Before Quoting a Multiplier

Once the switch is on, you need to measure how much faster it got. And getting this wrong is as common as failing to flip the switch in the first place. MPS in particular is asynchronous, so putting the clock in the wrong place produces numbers far better than reality.

4.1 Without Synchronization the Clock Stops Before the Kernels Do

The documented behavior of torch.mps.synchronize() is that it waits for all kernels in all streams on an MPS device to complete. Without it, Python moves to the next line the moment the kernel is queued, and your clock ends up measuring submission time.

import torch, time

def timed(fn, warmup=1, runs=3):
    for _ in range(warmup):          # throw away the first-run cost
        fn()
    torch.mps.synchronize()

    times = []
    for _ in range(runs):
        torch.mps.synchronize()
        t0 = time.perf_counter()
        fn()
        torch.mps.synchronize()      # wait for completion before stopping
        times.append(time.perf_counter() - t0)

    times.sort()
    return times[len(times) // 2]    # median

4.2 What Has to Be Held Constant

To state a multiplier you must hold everything below fixed and change only the device. If one of them drifts, the number proves nothing.

  • Same prompt, same max generated tokens. Different output lengths obviously take different amounts of time
  • Same seed. In PyTorch, pin it with torch.mps.manual_seed()
  • Discard at least one warmup run, then take the median of three or more. Use the median rather than the mean because a single background task can wreck an average
  • Fix the power state. Keep adapter connection and low power mode identical across both measurements
  • Clear background processes. If a corporate security agent or a backup daemon fired mid-run, throw that run away
  • Separate prefill from decode. Time to first token and subsequent tokens per second have different bottlenecks. Merging them into one number tells you nothing about what improved

4.3 What to State Alongside a Number

For the same reason, a multiplier you read somewhere is not usable unless the following is stated with it. The same applies when you share your own results.

  • Chip tier, GPU core count, unified memory capacity
  • Model name and parameter scale, quantization type
  • Context length, tokens actually generated, batch size
  • What the comparison was against (CPU execution, -ngl 0, or --device none)
  • If quoting whole-pipeline time, what percentage of it the GPU-eligible section originally occupied

That last item decides everything. In an eight-minute pipeline where six minutes could move to the GPU, halving it is achievable. Where only two minutes could move, no amount of tuning gets you below two. The multiplier is produced by the shape of that pipeline, not by the switch.

5. Five Reasons It Stays Slow After You Turn It On

There is a remaining case where the switch is correctly on, the GPU graph rises, and nothing feels different. The cause is usually one of these five.

CauseSymptomHow to confirmWhat to do
CPU fallback for unsupported opsGPU utilization rises and falls low while the CPU also spikesRun with the fallback variable off and see which operator raises NotImplementedErrorReplace that op with a supported form, or update the upstream library
First-run costOnly the first call is unusually slow, then it is normalMeasure again after a warmupDiscard the first run when measuring. In a service, do one dummy inference at startup

5.1 CPU Fallback - Convenient, Not Free

When MPS meets an operator it has not implemented yet, PyTorch raises an error. That is what PYTORCH_ENABLE_MPS_FALLBACK is for. The documented behavior is that if set to 1, the variable falls back operations to CPU when MPS does not support them.

export PYTORCH_ENABLE_MPS_FALLBACK=1
python app.py

Turn it on and things run. But running and being fast are different outcomes. Every fallen-back operator creates a round trip between CPU and GPU, and if that operator sits inside a loop, the entire speedup disappears. So the right order is this. First run with the fallback off and capture the name of the offending operator, then see whether you can route around it, and only when you cannot should you run with the fallback on. Turning it on from the start means you will never learn what is holding you back.

This variable is read from the process environment. If you set it in Python with os.environ, it has to come before import torch, and the safer route is an export in the shell. The PyTorch issue tracker and forums carry repeated reports of the variable having no effect when set after the import.

5.2 Batch Size 1 Is a Structural Limit

A GPU pulls decisively ahead of a CPU when the same operation runs across a large amount of data in parallel. Interactive local LLM use is exactly the opposite: batch of one, short prompt, one token at a time. The decode phase is bound less by arithmetic than by how fast weights can be read out of memory.

That produces an asymmetry on the same machine: prefill speeds up a lot, decode speeds up less. Workloads that feed a long document and answer briefly feel a big difference. Workloads that ask briefly and generate at length feel a small one. This is a property of the task, not something a setting can flip. Approaches that attack decode speed structurally are covered on the speculative decoding side.

6. Unified Memory Capacity and Model Size - Filter With Arithmetic First

The question of what runs on a 16GB MacBook has an arithmetic answer. Weight footprint is parameter count times bytes per parameter. Sixteen bits is 2 bytes per parameter, eight bits is 1 byte, four bits is 0.5 bytes.

Model scale16-bit8-bit4-bitComfortable on
3B~6GB~3GB~1.5GB8GB and up
7-8B~16GB~8GB~4GB16GB
13-14B~28GB~14GB~7GB16GB is tight, 24GB recommended
30-32B~64GB~32GB~16GB32GB is tight, 48GB recommended
70B~140GB~70GB~35GB64GB and up

Those figures are arithmetic for weights only. Three more things stack on top in practice.

  • The OS and always-on apps. macOS itself, a browser and an editor hold several gigabytes at all times
  • The KV cache. It grows roughly in proportion to context length. Feed a long document and this is what breaks first
  • Quantization overhead. Even four-bit-class GGUF files keep some tensors at higher precision, so real file sizes exceed the arithmetic. Budget from actual file size, not from the formula

So the reasoning that 32GB minus a 16GB 32B model leaves half free does not hold. Load it that way and you will barely be able to do anything else on that Mac. Read the last column as the line at which you can still work, not as the maximum that will load. How far to accept quality loss from each quantization step is covered in the GGUF quantization trade-off breakdown.

Unified memory cannot be upgraded later. Apple silicon memory ships on the SoC package, so there is no post-purchase expansion. When choosing a machine, including used ones, this is the one irreversible decision. Pick the minimum option because 8B is enough today, and there is no path to running a 30B a year from now.

7. How This Differs From CUDA

Bring your PC instincts over unchanged and some of them misfire. Axis by axis, it looks like this.

AxisMac (Metal / MPS)NVIDIA (CUDA)
Memory structureUnified memory. CPU and GPU access the same pool directlySeparate VRAM. Host-to-device copies required
How you scale upOne machine with more memoryMore cards
Operator coverageGaps remain, so a dedicated CPU fallback switch existsBroad enough that no fallback switch is needed
Status toolingActivity Monitor GPU History, powermetricsnvidia-smi
Tuning knobsMostly engine options (-ngl, --device)Open down to kernel and compiler level
Used market responseNo memory upgrade. Replacing the machine is the only pathSwap or add cards

One practical conclusion falls out of this. Macs are strong at getting a large model loaded at all, and weak at squeezing maximum speed out of a loaded model. Putting a 70B-class model on a 64GB unified memory machine is something a single card cannot imitate, but the room to raise tokens per second at the kernel level afterward is far wider on the CUDA side. Knowing this asymmetry settles what to do on a Mac and what not to.

8. When to Give Up on Local and Move to an API

Sometimes every switch is on, the measurement is sound, and you still miss your latency target. At that point there is rarely much left to extract from the same machine. Three options remain, each with a clear price.

  • Shrink the model → you pay in quality
  • Change the machine → you pay in money, and since unified memory cannot be expanded, it is a full replacement
  • Move to an API → data leaves your environment and per-call costs appear

Which is right depends on conditions. Stay local under these.

  • Data must not leave the organization. Under this condition speed is not negotiable
  • High call volume with short prompts on repetitive work: classification, tagging, extraction
  • It has to run offline or on an unreliable network
  • Latency may be slow but must be predictable. Variance from an external API at peak hours is the bigger problem

Conversely, move to an API under these.

  • Model quality directly determines the value of the output: final copy, customer-facing text
  • The scale you need exceeds machine memory, such as needing a 70B on a 32GB machine
  • Context is long. The KV cache eats unified memory, so this is the axis that collapses first locally
  • Several people use it concurrently. A single Mac handles concurrent requests poorly

The realistic answer is usually a mix of both. Run preprocessing, classification and first-pass summarization locally and send only the final generation outward, and you cut call volume while spending money only where quality matters. How to swap and route models in that configuration is covered in handling many models through a single API with an LLM router, and the separate constraints of driving local models as agents are laid out in why local LLM agent development needs tool search and HITL.

9. Context for Running Local LLMs on a Mac in Korea

9.1 The Same Tokens Per Second Does Not Feel the Same

Speed is almost always reported in tokens per second, but how many tokens a given sentence splits into varies by language and tokenizer. Carrying an English-derived tokens-per-second figure straight over to Korean work therefore misleads. It is faster to count how many tokens the Korean text you actually feed becomes under your own model's tokenizer. The token counter in the tool list below will get you a rough figure.

9.2 In an Air-Gapped Network This Is Not a Performance Question

In finance and public sector environments where outbound API calls are blocked, local is not an option but a premise. In that setting, whether the GPU is used is not a question of going faster but of being viable at all. Evaluate a candidate while it runs on the CPU and you will conclude that performance misses requirements, and that conclusion may have come from configuration rather than from the model. Pass the three layers in section 3 before making an adoption decision. Reverse the order and you eliminate perfectly good candidates.

9.3 Corporate Machines Add Variables

Company-issued Macs frequently run resident security agents and asset management tools. When those periodically take CPU, your measurements wobble from run to run. That is another reason section 4 recommends the median over the mean. If an unexpected spike lands mid-measurement, discard that run and measure again.

9.4 What to Check When Buying a Used Mac

If local LLM work is the purpose, the order of inspection in the used market is fixed.

  • Unified memory capacity comes first. It cannot be expanded, which makes it the only irreversible item
  • Chip tier comes second. At equal capacity, memory bandwidth differs, and decode speed is tied to it
  • Storage comes third. Model files are large but external drives cover that
  • Generation is what you look at after settling the three above. An older generation with more memory beats a newer one with less in terms of what will load at all

10. What Could Not Be Verified

The following were not used as figures or methods in the body because no primary source could be secured.

  • The multiplier from the optimization write-up that prompted this article. It is a personal pipeline record shared in the community, reporting that a one-line change cut runtime roughly in half. The chip, unified memory, model, quantization and context length behind it could not be identified, so the number was not carried into the body. The original is linked in the references
  • Apple's own definition of recommended working set size. The Metal-side definition behind what torch.mps.recommended_max_memory() returns could not be opened in Apple's official documentation. So no concrete figure for what percentage of total memory the GPU may use appears here. Printing the value on your own machine is the certain route
  • Raising the GPU memory ceiling via sysctl. Widely circulated in the community, but no Apple primary document could be identified. It changes a system-wide setting, so it is not recommended without a source
  • The roughly 2x in the MLX docs. It comes from the documentation's example workload and is not a measurement of LLM inference. It is cited here only within that scope
  • Internal switches in launchers like Ollama and LM Studio. How far they expose the underlying engine's Metal settings varies by version, so consult each distribution's documentation. Only the three stacks confirmed in official documentation appear in the table
  • Tokens per second by chip tier. It changes with every combination of machine, model, quantization and context, and no public measurement with stated conditions could be secured, so none is included. Measuring on your own machine with the procedure in section 4 is more accurate

11. Conclusion: It Is Not One Switch, It Is an Order

When a local LLM is slow on a Mac, the first suspect is not model size but where the computation is running. And that is not something to guess at. It takes three minutes to confirm.

The order looks like this.

  1. Confirm the device is detected. In PyTorch, print both is_available() and is_built(). The two failure messages mean completely different things
  2. Watch whether it actually runs. Does the Activity Monitor GPU History rise during inference? This is where most setups fail
  3. Check whether it holds memory. If driver_allocated_memory() is near zero, the model is not on the GPU
  4. Measure properly. Wrap in torch.mps.synchronize(), discard warmups, take the median. Skip this and every judgment afterward is unstable
  5. If it is still slow, eliminate the five causes in order. CPU fallback, first-run cost, batch size, memory pressure, measurement error

One last word on multipliers. Numbers shaped as one line for N times faster should be taken for direction and stripped of magnitude. The conclusion that a pipeline which was not using the GPU gets much faster once it does follows from the structure, so it holds. But the multiplier was produced by that person's chip, that person's model, and the share of that person's pipeline the GPU section occupied.

There is one thing to do right now. Put the Activity Monitor GPU History window next to your running inference. If the graph is flat, the model is not what you need to change.
