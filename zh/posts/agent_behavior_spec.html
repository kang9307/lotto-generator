长时间运行的智能体该拿什么来打分 - 把行为写成规格这个想法的实质

结果评估崩掉的位置、可观测叙述的条件，以及评分者该由谁来当

2026年9月1日 开发/基础设施

假设智能体调用了二十次工具，最后给出答案，而这个答案是对的。这件事说明的东西比看上去少得多。二十次里哪一次核对了依据、哪一次没核对就过去了、错了一次之后又做了什么，这些都不会留在最后那句话里。下一次运行还会得到同样答案，这个保证也不从那里来。对的结果和可信的过程是两样东西，而结果评分对后者几乎完全沉默。

所以把评估的重心从结果往过程挪的尝试一直在出现。2026年夏天公开的 Agent Behavior 是其中做法比较直白的一个。把智能体在整个任务里应当反复表现出来的行为写进一个 Markdown 文件，再拿这个文件当评分基准。它不是提示词而是评估基准，这一点就是这个格式的全部，也是本文要看的地方。

本文是针对一个公开格式及其规范文档的技术性检视，不是对任何产品、服务或企业的评价。所引数字为2026年9月1日的仓库公开元数据。该格式处于早期阶段，细节此后可能变动。

缘起 - 一个叫行为规格的格式

Braintrust Data 公开的 braintrustdata/agentbehavior 仓库把自己描述为「定义和评估智能体行为的标准」。许可证是 Apache-2.0，规范文档使用 MUST、SHOULD、MAY 这类 RFC 2119 措辞。它另有一个文档站点，仓库里还带着一份撰写规格用的技能文档和三个可运行的示例项目。

规模最好说准。仓库创建于2026年6月8日，提交15次，最后一次推送在7月29日。星标322、复刻9，没有开放的议题。随附的示例行为规格是四份。也就是说这是公开三个月的早期项目，这也是本文后面要单独处理「标准」这个词的原因。

格式本身很小。一个 Markdown 文件加两行 YAML 前置元数据，就是全部要求。而这个小恰恰是这场尝试唯一的胜算。过程评估的引入成本会直接换算成人的时间，所以文件格式一重，事情还没开始就死了。

只看结果的评估会在哪里崩掉

对最终产物打分，要四个条件同时成立才好用：正确答案只有一个、运行很短、错了能撤回、产物能反映过程。而智能体真正被投进去的地方，通常这四个里已经坏了两个以上。

坏掉的条件最终产物藏起来的东西实务中的表现
正确答案不止一个哪个答案被接受，取决于谁在打分同一条轨迹换个审阅者就在通过与不通过之间来回
中途做了撤不回的事撞运气撞对的运行和守流程的运行拿一样的分出了事故才知道那条路径本来就危险
运行很长几百个决策被折成一个分数出现回归也指不出是哪一步出的
失败很罕见那条路径根本进不了评估集的样本通过率很好看，只在生产环境炸

这时候常见的反应是去改提示词。可是改完提示词，确认改动到底修好了什么的那个装置依旧不存在。结果分数本来就不携带那种信息，而一行提示词和分数波动之间的因果，样本越小越是错觉。要授权到什么程度是另一条轴，放在智能体自主性等级那边讲了，这里只看授权范围定下来之后的判定问题。

  • 结果评分天生是事后判定。在有不可撤回副作用的任务上，判定出来时已经晚了
  • 在长运行里，一个分数的压缩率太高。从压缩过的值里复原不出原因
  • 正确答案不止一个的任务，评分标准本身会停留在默会知识里。换个人，标准也就换了
  • 所以往过程评估挪的动机不是品味问题，而是来自结果评分在物理上答不了的那些问题

这个文件到底长什么样

布局很朴素。在仓库根目录的 .agents/behaviors/ 下面按行为名建一个文件夹，里面放 BEHAVIOR.md。要放背景材料就搁在同一个文件夹的 references/ 里。

.agents/
└── behaviors/
    └── primary-source-tax-research/
        ├── BEHAVIOR.md      # 必需。文件名必须是这个拼写
        └── references/      # 可选。依据、示例、背景文档

规范真正强制的是前置元数据里的两个字段。name 最长64字符，只能用小写字母、数字和连字符，不能以连字符开头或结尾，而且必须与上级文件夹名一致。description 最长1024字符，不能为空。license 和 metadata 是可选的，客户端必须忽略自己不认识的字段。工具应当扫描 .agents/behaviors/，并且必须去找这个确切的文件名，不过也可以接受大小写变体。

---
name: primary-source-tax-research   # 小写、数字、连字符；不超过64字符；与目录同名
description: ...                    # 不超过1024字符；不能为空
---

# 这份规格管的是什么

## 一条行为，一句话说清

触发发生时，什么必须是可观测的。
什么明确不算满足这条行为。

每一次 ___ 算一次发生。

**为什么:** 要求这条行为的理由。

正文是自由格式。这里要点出二次摘要经常漏掉的一处。被引用得最多的六个标签，也就是意图、要核对的证据、判断、执行、恢复、失败模式，并不是规范要求的结构。仓库自己就写明这六个是可选的、用普通 Markdown 也行，而随附的四份示例形态确实不一致。金融工作核验那份用了这六个标签，税务调研那份没用。

反倒是没用的那份更值得学。税务调研那份把一条行为立成标题，在同一段里写清什么不算满足这条行为，用「每一次税务调研过程算一次发生」把计数单位钉死，最后再补一行说明为什么需要这条行为。这四块拼在一起，才是让评分成为可能的最小构成。标签是之后的事。写给工具读而不是写给人读的文档会有什么不同，在面向智能体的文档那边已经谈过。

要成为和提示词不同的文档，需要什么

每出一种新文档格式，第一个问题都一样：这东西塞进提示词不行吗。这个格式自己准备了答案，而那个答案就是它的核心。

文档做的事读者变更时机
行为规格定义什么算好的行为审阅者、评估作者、检查轨迹的智能体行为标准变化时
系统提示词 · AGENTS.md告诉智能体该怎么行动运行时的智能体实现变化时
评估集检查那条行为是否真的发生了评估的设计者测量对象变化时

表格最后一列才是真正的分界线。提示词跟着实现频繁变动，行为标准变得慢得多。把两份文档合在一起，就等于每动一次实现，判定标准也跟着挪。昨天不通过的轨迹今天通过了，而智能体一点没变，就是这么来的。

更糟的是规格变成提示词的副本。那样评分就成了用提示词去确认提示词有没有照做的循环，通过率上去了，什么也没验证。靠不断堆规则来管住智能体为什么会撞墙，整理在长篇政策文档的限度里。行为规格如果能越过那道墙，靠的不是句子更多，而是判定要求句子之外的证据。

  • 同样的内容写进两份文档就会漂移。提示词和规格最好放成引用关系而不是重复关系
  • 规格里一旦写上工具名和函数签名，它当场就变成提示词了，因为实现一变它就得跟着变
  • 反过来太抽象就无法判定。这两堵墙之间的通道很窄，而这个窄度才是这个格式真正的难点
  • 一条实务判据 — 某句话变更的理由如果是代码改动，它属于提示词；如果是方针改动，它属于规格

叙述必须可观测这个条件

谨慎判断、必要时核实、妥当应对。这类句子写在给人看的指引里没问题，当评分基准则一行都用不了。问题不在于它含糊，而在于它从没说自己什么时候适用。没有适用时点就数不出发生次数，数不出来就没有通过率。

这个格式的文档把这一点退回成计量问题。文档里写着：如果轨迹无法暴露某个重要行为，就去提升这条行为的可观测性，或者改进轨迹的埋点。换句话说，规格要能成立，日志得先成立。把这个顺序颠倒过来、先写规格的团队，失败得最多。

写一句话时要过的检查，三条就够。

  • 能不能用一行说清它什么时候适用。「回答税务问题时」可以，「在重要场合下」不行
  • 轨迹里有没有能把满足和不满足分开的事件。必须是留下记录的东西，比如工具调用、文件打开、输出顺序
  • 两个人看同一条轨迹会不会给出同样的判定。如果分歧，是句子错了，不是人错了
  • 在这上面再加一个习惯会更好：把不满足的条件也一起写出来。示例之所以明写「在第一次检索之后才去读不算满足这条行为」，就是这个道理
  • 但别只剩下否定句。只写了不许做什么的规格，会把一件事都没做的轨迹放过去

触发与发生 - 评分单位怎么数

评分分成两步。先看这条行为的触发在轨迹里是否真的发生。没发生，这条轨迹就在这份规格的范围之外，不算失败。发生了，才去看要求的行为能不能被观测到：能看到是阳性，没有或者相反就是阴性。

触发在一次运行里发生多次时，每一次都是独立的判定单位。逐次判定之后再折叠，而折叠规则通常是只要有一次失败，整节就算失败。这是为了不让前面五次的成功盖住最后一次的失败。示例之所以要用「每一次税务调研过程算一次发生」把计数单位钉死，原因就在这里。

这里还挂着一句容易被忽略的但书。没有证据并不自动等于范围之外。触发发生了，而在一条本该完整记录的通道里看不到证据，那通常判为阴性。这句话之所以重要，是因为它意味着埋点质量会直接变成评分结果。只留了部分日志的团队，同一份规格会跑出不同的分。

  • 一句话可评分的四个条件 — 触发不含糊、要求的行为在轨迹里看得见、证据边界清楚、判定不依赖数据标注
  • 最后一条最微妙。看着答案标注去判定，那是披着过程评估外衣的结果评估，这也是这件事最常出错的地方
  • 运营时要看的指标不止通过率一个，还得同时看范围外的比例。触发一次都没发生的话，通过率会显得完美无缺
  • 范围外一直居高不下，只有两种可能：规格和真实工作脱节了，或者评估集根本没造出那个情境

评分者该由谁来当

规格写得再好，如果没定下由谁来做判定，这份文档就只是贴在墙上的标语。选项只有三个，各自的成本和误判方向都不一样。

由人来看

一条轨迹要花几分钟到几十分钟。准确度只在开头高。过了二十来条，标准就松了，而最初几条里定型的那点感觉会统治剩下的全部。所以人不该用在全量评分上，而该用在最初校准标准和裁决判定分歧的时候。

由模型来看

唯一撑得住全量评分的选项。代价是误判往一个方向偏。叙述一含糊它就变宽容，还会把智能体照搬规格原话的轨迹误当成行为。要把「我已核对一次文献」和真的打开过区分开来，规格就必须指向事件而不是指向措辞。

由日志规则来看

最便宜也最不晃。调用顺序、某个工具有没有被调用、某个字段在不在，这类能从文本上确定的项目，用确定性检查了结更划算。局限也一样清楚。它分不清调用过和真的用了调用结果。面对只对形不对实的规避行为，它最脆弱。

评分者成本误判偏向合适的位置
人每条几分钟到几十分钟，无法扩展越往后越松，最初的样本会固定住标准校准规格、裁决分歧、抽样审计
模型按调用计费，随轨迹长度上升偏宽容，把声明当成行为认下每次运行的全量评分、回归监控
日志规则埋点的前期成本，之后接近于零偏严格，会误杀形态不同的正当路径顺序、调用有无这类能从文本确定的项目

实务里的答案不是三选一，而是编排。能从文本确定的压到日志规则里，需要判断的交给模型，只把模型判定分歧或者结果后来被推翻的那些件送到人手上。而且把评分者交给模型的那一刻，这个评分器本身就成了要验证的对象。仓库示例给评判器代码配了测试文件，正是承认了这一点的设计。评分器出错却不会响警报这个问题，放在如何验证验证工具里单独谈过。

规格变旧的速度

行为规格被设计成比提示词变得慢。可是变得慢不等于长久有效。有些位置句子一字未动而含义已经变了，而这些位置多半是随着换模型一起来的。

  • 「先」这个字变得判不了。并行发出工具调用的模型，不会在轨迹里留下线性的先后顺序。同一份规格会突然把失败率抬上去
  • 本来观测得到的东西消失了。中间推理被摘要或者被隐藏之后，只在那里面才看得见的判断依据就从轨迹里没了。行为没变，却因为没证据被判成阴性
  • 明示变得不必要。新模型自己就做了的行为，有时不会以独立事件的形式留在轨迹里。做得更好了，分数反而掉下来
  • 工具改名后日志规则会静悄悄地放行。确定性检查有时分不清条件被满足了和检查对象已经不存在了
  • 轨迹格式本身变了。换掉可观测性栈，规格一个字没动，全部判定却都要重新校准

应对办法不是把模型名字钉进规格里。那么做规格就变成提示词，表格最后一列也就塌了。该做的是给每份规格挂上通过率的走势，一旦没改智能体而数值突变，就把它当警报看。接下来的活是分清突变来自行为变化还是观测变化，分不清这个，规格半年内就会变成没人相信的文档。

和已有的那些东西抢位置

这个格式到底替代了什么，最好说清楚。它几乎什么都没替代。多了一份文档，多了一份评分成本。挪过来的，是那些既有装置本来就答不好的问题。

既有装置它本来回答的问题挪到这里的挪不过来的
单元与集成测试这段代码对这个输入是否返回这个值没有全部。包着智能体的那些代码照样需要测试
评估集这个输入下最终答案对不对用最终答案分不开的那些项答案明确的项目的评分，那边依然更便宜
运行手册人在这种情况下该做什么反复出现的条件与行为配对一次性流程、工具用法、接入信息
评审清单这个改动能不能发出去因审阅者而异的默会标准以改动为单位的放行判定
系统提示词要让智能体做什么没有运行时指令照旧留在提示词里

表格里最诚实的两格，是第一行和最后一行的「没有」。这个格式不会替你减少测试，也不会替你减少提示词。智能体在测试栈里担任什么角色是另一个主题，放在Agentic 测试那边，而两边的方向正好相反。那边智能体是做检查的一方，这里智能体是被检查的一方。

工具检查什么，不检查什么

仓库里带了一个 CLI 包，命令有三个：做结构校验的 validate、列出已发现规格的 list、把其中一份摊开来看的 explain。检查范围在文档里写得很清楚：文件发现、YAML 前置元数据解析、name 与 description 的约束，以及 metadata 的形态。正文按自由格式对待，不做校验。

这份诚实是个可信的信号。要是它宣称能静态检查 Markdown 散文是否可评分，那才更可疑。不过这也是引入方最容易误解的地方。校验通过只意味着文件能被解析，至于能不能拿这份规格去评一条轨迹，它一个字也没说。质量判断被明确留给了人或模型。

  • 亮绿灯的规格和可评分的规格是两个只会偶然重叠的集合。别拿校验当质量闸门
  • 真正的闸门只有一个：两个人对同一条轨迹会不会给出同样的判定。这件事没法自动化
  • 所以引入初期的成本大头不是装工具，而是人读样本轨迹花掉的时间

标准这个词现在指的是什么

介绍这个格式的文章基本都会用上「标准」这个词。不如按句子把这个词眼下究竟指向什么拆开来看。

  • 已确定的事实 — 仓库和文档站点自称标准。规范文档使用 MUST、SHOULD、MAY 的措辞。许可证是 Apache-2.0。客户端应当遵守的发现规则与字段约束都成文了
  • 已确定的事实 — 它没有经过任何标准化组织。仓库创建于2026年6月8日，提交15次，最后一次推送在7月29日，星标322、复刻9。随附的示例行为规格是四份
  • 属于提案的部分 — 六标签的构成、把判定分成阳性、阴性、范围外的惯例，以及逐次判定再折叠的做法。这些规范并不强制，只是指引文档推荐的形态
  • 目前还没有依据的 — 采用了这个格式的外部组织。星标和复刻是关注度指标，不是使用量指标

所以眼下叫它最准确的名字是一家公司公开的早期提案格式。这不是缺点而是位置。有用的想法多半就是从这个状态起步的，而且文件格式是 Markdown，也不会被绑死在某个技术栈上。只是在公司内部讨论引入时，想拿「我们遵循标准」这句话去拍板，这句话目前撑不起分量。撑得起的那句是「我们用二十条轨迹核过，我们的运行在这个格式下评得动」。

要不要上 - 值得的团队和过头的团队

过程评估不是白来的。要留轨迹、要写规格、要接评分器，还要管着规格慢慢变旧。能把这份成本赚回来的条件，其实偏窄。

  • 存在不可撤回的副作用。支付、部署、工单关闭、对外发送这类事后判定来得太晚的工作
  • 正确答案不止一个。调研、分类、排优先级这类多个输出都站得住的工作
  • 运行很长。一次跑几十个工具调用，最终产物根本显示不出原因的工作
  • 已经在留轨迹了。没有这个，规格的价值恰好是零，因为没有可评的对象
  • 审阅者不止一个。标准因人而异、同一条轨迹判定会变的状态
  • 有合规或审计要求。需要回溯地展示的不只是答案，还有依据从哪里来的领域

反过来，过头的情形也很清楚。

  • 智能体一两步就结束、产物一眼能看完的话，结果评分依然更便宜也更准
  • 没有轨迹埋点的话，顺序就搞反了。先留日志，规格排在后面
  • 还在每周重写提示词的探索阶段，行为标准根本还不存在。把不存在的东西钉成文档，只会拖慢探索
  • 一个人写、一个人看的规模下，规格的主要效用也就是判定一致，压根不会发生
  • 写了十份规格却不接评分器，剩下的就是十份没人读的文档

真要开始，最小构成是这样：一份规格、二十条轨迹、人工评分。出现不一致时，先改规格的措辞，再考虑动智能体。这个顺序一旦颠倒，规格的缺陷就会被记成智能体的缺陷，而这种记录事后很难翻回来。

小结

结果评分只在正确答案唯一、运行短、错了能撤回的时候才好用。智能体真正被投进去的地方大多在这些条件之外，判定的重心也就因此往过程挪。行为规格就是把这次挪动落成了一个文件。提示词说的是该做什么，规格说的是什么必须可被观测。

格式本身小而诚实。必填字段只有两个，工具也自己言明只检查结构。难的部分全在格式之外：把句子写得可观测、定下发生的计数单位、编排评分者并且回头验证这个评分者，以及在换模型时抓出同一句话变了意思的那些位置。这四件事，格式一件都不替你解决。

所以眼下对这个格式能说的准确的话就这么多。不是出现了一个新标准，而是很多团队各自临时在做的事情有了一个文件名。这个名字有没有用，二十条轨迹就能知道；在有人读完那二十条之前，谁也不知道。

未能确认的部分

  • 没能确认公开方之外的组织采用案例。星标322和复刻9是关注度指标，不是实际使用的指标。没有找到把这个格式接进真实流水线的团队的公开记录
  • CLI 包是否发布到注册表、安装规模多大，没有核查。包名和命令在仓库文档里有，但分发统计在本文的核实范围之外
  • 没有运行随附的评估代码。关于触发、发生、判定的说明，是按仓库规范文档与指引文档写下的内容为准
  • 其他智能体运行时是否真的会读取这个格式，没能确认。仓库里有面向客户端实现者的指引文档，但没有确认到实现了它的外部工具
  • 关于用了六标签的规格是否比自由格式评分结果更一致，没有比较资料。这也是本文没有推荐这套标签的原因
  • 本文对各类评分者的成本与误判方向的叙述，是基于一般评估运营经验的归纳，不是针对这个格式测出来的数值
