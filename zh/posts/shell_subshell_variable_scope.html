引言：循环跑对了，只有答案是错的

假设写了一个脚本，扫过日志文件统计符合条件的行数。在循环里塞一个 echo，三行清清楚楚地打出来。可循环结束后输出合计，结果是零。

这时候多数人会去怀疑循环体。是算术展开写错了，还是 read 吃掉了空行，或者变量名打错了。都不是。循环跑得完全正确，计数器也确实到了三。只是承载这个计数器的进程随循环一起消失了。

本文用实际执行结果依次追踪：那个进程何时产生、为什么无法把值交还，以及修复为什么不在循环体而在喂入输入的方式上。下面列出的命令和输出，都是在 GNU bash, version 5.2.37(1)-release 和 dash 上直接跑出来的。shell 基本功还不扎实的话，先看Shell脚本基础和Shell脚本高级会更好读。

1. 计数器变回零的那一刻发生了什么

先复现。一个三行文件就够了。

$ printf 'a\nb\nc\n' > /tmp/f.txt

$ n=0
$ cat /tmp/f.txt | while read -r l; do n=$((n+1)); done
$ echo "after pipe: n=$n"
after pipe: n=0

接下来只改喂入输入的方式，循环体一个字符都不动。

$ n=0
$ while read -r l; do n=$((n+1)); done < /tmp/f.txt
$ echo "after redirect: n=$n"
after redirect: n=3

同一个循环、同一个文件、同一个shell。差别只有有没有 |。结论到这里就已经出来了：问题不在循环里。

1.1 管道搬运的不只是数据

如果只把管道理解成「把命令A的输出送进命令B的输入」的装置，这个现象就没法解释。管道在做这件事的同时还多创建了一个进程。bash 会把管道的每个组成部分放进各自的子shell 里执行。

子shell 是复制父shell 而来的，所以启动那一刻它持有父shell 的全部变量值。问题出在反方向。

  • 父进程的值会复制给子进程，所以循环里读 $n 能正确看到零
  • 子进程改动的值回不到父进程，进程之间没有这样的通道
  • 管道结束时子进程退出，那个已经涨到三的 n 随之消失
  • 父shell 里还留着最初创建的 n=0，没有被任何东西碰过，所以输出零
  • 换句话说，不是「值没加上去」，而是「站在看不见增量的位置上看」

检索时该用的词。这不是变量作用域问题，而是进程边界问题。所有想用 local 或 export 解决的尝试都失败，原因就在这里。export 是把值从父进程往子进程送的机制，不存在从子进程往父进程送的机制。

2. 用眼睛数清生成了几个进程

与其猜，不如数。bash 正好有两个为此准备的变量。

  • $$ 是原始shell 的 PID，在子shell 里也不会变，所以判断子shell 时用不上
  • $BASHPID 是当前正在执行这段代码的进程的真实 PID，进入子shell 后值会变

把两者并排打印出来，子shell 在哪里产生就一目了然。

$ echo "parent: \$\$=$$ BASHPID=$BASHPID"
parent: $$=1344 BASHPID=1344

$ ( echo "subshell( ): \$\$=$$ BASHPID=$BASHPID" )
subshell( ): $$=1344 BASHPID=1348

$ echo "cmdsub: $(echo "\$\$=$$ BASHPID=$BASHPID")"
cmdsub: $$=1344 BASHPID=1349

$$ 三次都固定在 1344，只有 BASHPID 分成了 1344、1348、1349。这就是圆括号和命令替换各自创建了新进程的直接证据。调试脚本时想知道「这里是不是子shell」，一行 echo $BASHPID 就够了。

PID 的具体数值每次执行都不同。要看的不是数字，而是三个值彼此是否不同。

3. 重定向 - 最省事也最可移植的解法

输入是真实文件时答案只有一个：去掉管道，在 done 后面加重定向。

# 值会消失的写法
cat /tmp/f.txt | while read -r l; do n=$((n+1)); done

# 值会保留的写法
while read -r l; do n=$((n+1)); done < /tmp/f.txt

这种形式好在哪里，整理如下。

  • 循环在当前shell 里运行。根本不产生子shell，变量原样保留
  • 少创建一个进程，cat 进程也一并消失
  • 这不是 bash 扩展而是 POSIX 语法，dash 下同样输出三
  • cat 文件 | 这个形状本身多数情况下就是多余进程，改掉这个习惯与子shell 问题无关也有收益
  • 重定向放在 done 之后一开始会觉得别扭，但把整个循环看作一条复合命令、在替换它的标准输入，就自然了

文件有多个、想写成 cat a b c | 的时候，该用的不是重定向而是下一节的进程替换。

4. 进程替换 - 输入不是文件的时候

现实中的脚本，输入不是文件的情况更多：find 的结果、grep 的结果、用 jq 过滤过的 API 响应。这时用的就是进程替换。

$ n=0
$ while read -r l; do n=$((n+1)); done < <(cat /tmp/f.txt)
$ echo "after procsub: n=$n"
after procsub: n=3

< <(...) 看着像打错了，其实是两种不同语法挨在一起。<(cmd) 让命令的输出看起来像文件，前面的 < 把这个伪文件接到标准输入上。中间必须有空格。

4.1 为什么这个可以而管道不行

进程替换里 cmd 同样在独立进程中运行。差别在于循环落在哪一边。

  • 管道里循环是管道的组成部分，所以被推进子shell
  • 进程替换里循环留在当前shell，被推进子shell 的是产生数据的那一侧
  • 产生数据的一侧不改变量，所以是子shell 也无所谓

4.2 处理文件名时一并出现的问题

这是在遍历 find 结果的循环里实际验证的结果。放一个空日志文件和一个有内容的文件，统计空文件的个数。

$ find logs -name '*.log' | while read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done
$ echo "find | while  -> empty=$empty"
find | while  -> empty=0

$ while IFS= read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done < <(find logs -name '*.log')
$ echo "procsub       -> empty=$empty"
procsub       -> empty=1

这里要说明 IFS= 和 -r 为什么一起出现。它和子shell 问题是两码事，但会在同一行上炸掉。

  • 不给 IFS= 就会削掉首尾空白，以空格开头的文件名被悄悄改掉
  • 不给 -r 就会把反斜杠当转义解释，来自 Windows 的路径字符串尤其危险
  • 文件名可能含换行的环境里，把 find ... -print0 和 read -r -d '' 配成一对
  • 这个组合在进程替换里照样能用，上面那次执行中 -print0 版本给出了相同结果

5. lastpipe 生效与被忽略的条件

bash 有一个选项，能让管道的最后一个组成部分在当前shell 里执行。

$ shopt lastpipe
lastpipe        off
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=0

$ shopt -s lastpipe
$ shopt lastpipe
lastpipe        on
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=3

看到这里像是最简单的解法。可在终端里照着敲，什么也不会发生。原因是 job control。

5.1 job control 开着就会被忽略

在脚本里用 set -m 开关 job control 再跑同一份代码，结果泾渭分明。

$ set -m          # job control ON（交互式shell 的默认状态）
$ shopt -s lastpipe
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control ON  -> n=$n"
job control ON  -> n=0

$ set +m          # job control OFF
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control OFF -> n=$n"
job control OFF -> n=3

交互式shell 默认打开 job control。所以在终端里怎么开 shopt -s lastpipe 结果都不变。选项确实已启用却偏偏不起作用，这是很难调的一种状态。

5.2 那 lastpipe 该用在哪

  • 不建议作为对外发布脚本的默认解法。读者得把文件开头那行 shopt 和一百行之下的循环联系起来才能理解
  • 它是 bash 专有的，dash 里根本没有这个选项
  • 需要以最小改动救活既有脚本时很有用，管道结构原样保留，只加一行
  • 用来在一分钟内判定「这次是不是子shell 造成的」很合适。加这一行结果就变，原因即可确认
  • 启用时务必写在脚本内部，并确认该脚本确实由 bash 执行

6. 子shell 出现的其余位置

需要留意的不只是管道。下面每一行都是直接跑过验证的结果。

语法子shell变量改动在外部是否保留实测结果
cmd | while ...产生不保留n=0
( k=2 )产生不保留k=0
{ k=1; }不产生保留k=1
$( ... )产生不保留BASHPID 改变
{ m=99; } &产生不保留wait 后仍是 m=0
while ... done < 文件不产生保留n=3
while ... done < <(cmd)循环不产生保留n=3
for v in ...; do不产生保留n=6

表里最容易混的两行是 ( ) 和 { }。外形相似，性格却相反。

6.1 圆括号是隔离，花括号只是分组

$ k=0; { k=1; };  echo "brace group: k=$k"
brace group: k=1
$ k=0; ( k=2 );   echo "paren subshell: k=$k"
paren subshell: k=0

这个差别在有些场合反而是帮助，因为子shell 同时也是隔离装置。

$ cd /tmp
$ echo "before: $PWD"
before: /tmp
$ ( cd / ; echo "inside: $PWD" )
inside: /
$ echo "after : $PWD"
after : /tmp

需要临时切到别的目录做点事再回来时，与其 cd 之后用 cd - 退回，不如用圆括号包起来。中途失败退出，父进程的工作目录也不会动。

6.2 exit 同样被关在括号里

$ ( exit 42 )
$ echo "parent still alive, subshell exit=$?"
parent still alive, subshell exit=42

这一点两头都能咬。把收尾代码放进子shell 是安全的，里面的 exit 不会杀掉整个脚本。反过来，本意是「出错就结束脚本」而写的 exit 1，一旦落在圆括号里，脚本会毫发无损地继续跑。后一种情况闯的祸远多于前者。

7. 把值取出来的六种办法和各自的代价

用三行数据把六种办法全跑了一遍。数据是 alpha 10、beta 20、gamma 30，目标合计是 60。

办法语法结果代价与约束
重定向done < 文件60仅限输入是真实文件。POSIX sh 可用
进程替换done < <(cmd)60bash 扩展，POSIX sh 下语法错误
here stringdone <<< "$(cmd)"60整份输出进内存。bash 扩展
先读进数组mapfile -t a < 文件60需 bash 4 以上，大数据量有内存压力
捕获输出t=$(cmd | { ...; echo "$t"; })60只出一个值时很省事，多值需解析
经由临时文件写入 "$tmp" 后再读60可移植性最好，多出清理责任

7.1 实际执行结果

$ total=0
$ while read -r name v; do total=$((total+v)); done <<< "$(cat /tmp/data.txt)"
$ echo "here-string total=$total"
here-string total=60

$ mapfile -t lines < /tmp/data.txt
$ echo "mapfile count=${#lines[@]} first=${lines[0]}"
mapfile count=3 first=alpha 10

$ total=$(cat /tmp/data.txt | { t=0; while read -r n v; do t=$((t+v)); done; echo "$t"; })
$ echo "captured total=$total"
captured total=60

最后一种很有意思。它不去消灭子shell，而是用子shell 唯一能向外送值的通道，也就是标准输出。变量出不来，输出出得来。

7.2 怎么挑

  • 输入是文件，就用重定向，没什么可犹豫的
  • 输入是命令输出且用 bash，就用进程替换
  • 必须以 #!/bin/sh 发布，就用临时文件或捕获输出，进程替换用不了
  • 行数上万，就避开 here string 和 mapfile，它们把整份内容装进内存
  • 循环里只有一个值要带出来，捕获输出最短
  • 既有脚本要以最小改动修好，就用 lastpipe，但把第5节的约束写进注释

一句话总结。变量出不了子shell，但标准输出、文件和退出状态出得来。所有取值的办法归根结底都是用这三者之一，或者干脆一开始就不制造子shell。

8. set -e 在管道和子shell 里偏离预期的地方

理解了子shell，set -e 为什么频频背叛人也就一并解开了。先看执行结果。

$ set -e
$ printf 'a\nb\n' | grep -q zzz | cat
$ echo "survived"
survived

grep 失败了，脚本却没停。因为管道的退出状态默认取最后一条命令的状态。最后的 cat 成功了，整条管道就被算作成功。

8.1 用 PIPESTATUS 看是哪个位置死了

$ false | true | false
$ echo "\$?=$? PIPESTATUS=(${PIPESTATUS[@]})"
$?=1 PIPESTATUS=(1 0 1)

数组的顺序就是管道的顺序，三个位置里第一个和第三个失败，一眼就读得出来。要注意的是这个数组只要再经过一条命令就会被覆盖。要用就立刻复制到另一个数组里。

8.2 打开 pipefail 之后的变化

$ ( set -e -o pipefail; printf 'a\n' | grep -q zzz | cat; echo "NOT REACHED" )
$ echo "with pipefail exit=$?"
with pipefail exit=1

$ ( set -e; printf 'a\n' | grep -q zzz | cat; echo "reached" )
reached
$ echo "without pipefail exit=$?"
without pipefail exit=0

pipefail 打开后，管道里任何位置出现非零状态，整条管道都会被判为失败，这时 set -e 才动作。

8.3 最安静的那个陷阱

这一条值得单独拎出来。子shell 一旦放在 || 的左边，它内部的 set -e 就被整个废掉。

$ ( set -e; false; echo "NOT REACHED" ) || echo "caught"
NOT REACHED

NOT REACHED 打出来了。为了「失败时接住」而加的 ||，把整个子shell 送进了条件判定语境，而在这种语境里 set -e 是关闭的。函数也一样。

$ f() { set -e; false; echo "reached anyway"; }
$ f || true
reached anyway

这是「加了错误检查反而把错误检查关掉了」的局面，用眼睛很难找出来。整理成实务规则如下。

  • 把 set -euo pipefail 放在脚本开头，但不要只信它
  • 重要的管道要显式检查 PIPESTATUS
  • 一旦加上 || 什么，就当它左边的 set -e 不存在
  • 要确认子shell 成败，不要用 || 去接，而是执行之后在另一行检查 $?
  • 已确认 ( exit 7 ) 会原样交回 $?=7，退出状态本身是正常传播的

9. 各个shell 之间的差异

同一份代码在 dash 下跑出来是这样。

$ dash t.sh
dash pipe: n=0
dash redirect: n=3

$ dash -c 'while read -r l; do echo "$l"; done < <(printf "x\ny\n")'
dash: 1: Syntax error: redirection unexpected
项目bash 5.2.37dashzsh 与 ksh
管道内 while 的计数器0（已验证）0（已验证）未能确认
用重定向解决3（已验证）3（已验证）未能确认
进程替换 <(...)可用语法错误未能确认
shopt -s lastpipe有，受 job control 制约无未能确认
PIPESTATUS有无未能确认
mapfile有无未能确认

由此得出的实务规则很简单。

  • shebang 写着 #!/bin/sh 却用了进程替换的脚本，会在部署环境里因语法错误而死。开发机上 /bin/sh 软链到 bash 时看不出来
  • 要用 bash 特性就把 shebang 准确写成 #!/usr/bin/env bash
  • 需要可移植的脚本，务必在目标shell 上真跑一次。做出上面那张表只花了几分钟
  • 容器镜像里没有 bash 是常事，先确认最小镜像的默认shell 到底是什么

10. 写这类验证脚本时的陷阱

上面的结果全部是存成文件之后执行的。哪怕只有一行的验证，把代码整段塞在 -c 后面的做法也最好避免，理由有两个。

10.1 引号被剥掉两次

内联方式让字符串先过一遍外层shell，再过一遍内层解释器。于是每次都得重新盘算 $、反斜杠和引号在哪一层被消耗。上面例子里 \$\$ 那种带转义的地方就是痕迹。存成文件就少掉一层。

10.2 非 ASCII 字符会悄悄损坏

这是更麻烦的一面。命令行传递的字符串要依次经过shell、终端、解释器的编码设置。这条链上只要有一环 locale 不同，中文、韩文、日文这类非 ASCII 字符就会在不报错的情况下变成别的字节。

  • 因为不报错，检查器会报告通过。而实际上被检查的字符串已经是另一个值
  • 在这种状态下看到「检出 0 条」，就会把它读成完好无损。这是最坏的失败方式
  • 存成文件的话 UTF-8 字节会原样交给解释器，编码交接点减少到一处
  • 新写检查器时，要先故意埋一个缺陷确认能被抓到。抓不到不是对象干净，而是检查器坏了
  • 韩文按音节组合，只写词干的正则会整片漏掉变形形式，用字符类留出余地更稳妥

用正则扫日志这类工作整体上另有整理，见grep 与 AWK 指南和日志分析命令指南。

11. 没能确认的部分

本文未能通过执行验证的项目集中列在这里。

  • zsh 和 ksh。没有能运行这两个shell 的环境，所以未能确认。ksh 系会把管道的最后一条命令放在当前shell 里执行这个说法流传很广，但本文没有复现。在用这些shell 的话，用三行脚本自己复现一次更稳妥
  • 带真实终端的交互式会话。第5节的结论来自用 set -m 开关 job control。没有在挂着控制终端的真实登录shell 上做同样的实验，但结果随 job control 状态而分化这一点本身是确认过的
  • POSIX 标准原文。标准把管道各元素是否在子shell 中执行留给实现，这一点常被当作各shell 行为分化的原因引用，但标准条文本身没有去核对
  • busybox ash 与最小容器镜像。这是实务中最常出问题的组合，本文未能确认
  • 大数据量下的内存实测。第7节写了 here string 和 mapfile 会把整份内容装进内存，但没有按行数测量实际用量
  • 旧版 bash。没有确认 lastpipe 和 mapfile 被引入的准确版本边界。若面向很旧的系统，需要在那台机器上直接确认

FAQ

Q1. 在循环里 export n 不就行了吗

不行。export 是父进程把环境传给子进程的机制，方向正好相反。在子shell 里 export，只会传给这个子shell 之后再创建的孙进程，对父进程毫无影响。同理 declare -g 也帮不上忙。全局作用域指的是那个进程内部的全局，不跨越进程。

Q2. 循环里值是对的，为什么只有循环外是错的

这恰恰是这个现象的指纹。循环内的 echo 在子shell 里执行，看到的是那个进程的最新值。循环外的 echo 在父shell 里执行，看到的是从未被碰过的原值。变量名相同，看的却是两个进程的内存。出现这个症状，先去找管道就对了。

Q3. 把 while 换成 for 能解决吗

因为不再用管道，可以说算解决，但有代价。for v in $(cmd) 在当前shell 里运行，变量能保留。可它把整份输出装进内存，还会应用单词切分和通配符展开，带空格的文件名会被拆开。for line in $(cat 文件) 不是按行处理，而是按单词处理。要按行处理，while read 配重定向才对。

Q4. 管道的各个阶段是顺序执行吗

不是。管道的各组成部分是同时启动的，通过管道缓冲区互相调节流量，并非等前一条命令跑完后一条才开始。这也是需要子shell 的理由之一：只有是独立进程才能并行运行。

Q5. 后台运行的块，其变量在 wait 之后读不就行了吗

不行。实际跑过确认，{ m=99; } & 之后加 wait，m 依然是 0。wait 只是等子进程结束，并不取回值。需要拿到后台任务的结果时，把标准输出接到文件或命名管道，再在 wait 之后读。

结论：今天就能改的三件事

第一，在动手改循环体之前先找 |。循环里对、循环外错的值几乎总是管道造成的。把 cat 文件 | while 改成 while ... done < 文件 只要三秒，不知道这一点就会盯着算术展开看三十分钟。

第二，把子shell 读作「边界」而不是「变量消失的地方」。cd、set、trap、exit 都被关在里面。被关住是麻烦的场合和被关住反而庆幸的场合都存在，( ) 也是为后者准备的工具。临时切目录时用圆括号包起来就是例子。

第三，不要把 set -e 当安全网。管道中间的失败默认抓不到，加上 || 的瞬间左边的 set -e 就关了。把 pipefail 一起打开，重要的地方用 PIPESTATUS 显式确认。

最后一点。本文的表格和输出全部来自二到十行之间的脚本。对shell 行为存疑时，不要争论，跑三行永远更快。一个 printf 'a\nb\nc\n' 加一个计数器，多数疑问三十秒内就能了结。
