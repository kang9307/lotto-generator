AWS 检查项全部通过，路径却还在 - 把资源之间的关系放进检查清单

角色传递、信任策略、资源策略、服务代为调用各自接起了什么，又要看什么才能让接缝显形

2026-09-05 开发/基础设施

云安全检查结果满屏绿色，心里却还是不踏实，这样的时刻是有的。项目全部通过。存储桶不是公开的，静态加密开着，安全组里也没有不该开的端口。可这些加起来，仍然接不出这个账户是安全的这句话。这种不适感不是情绪，而是从结构里来的。

因为检查项所看的单位，和风险所产生的单位并不相同。检查项看的是一个资源。风险是在一个资源和另一个资源之间被制造出来的。只要这两个单位错开，项目再怎么增加，缝隙里长出来的那条路径都不会进入清单。

下面要谈的正是这种错位的结构。权限能够流动的通道有若干固定的类型，每一种类型都必须换一个位置去看才会显形。以下把这些通道分成四类，并为每一类配上一对问题：是什么制造了风险，以及看什么才能让它显形。这里讨论的是可见性，不是攻击步骤。

下文出现的 IAM 概念定义与建议语句，都取自 AWS 官方用户指南的原文。云权限模型的文档修订频繁，条件键和策略类型也在不断增加。所引用的表述以 2026 年 9 月初的文档为准。

缘起 - 通过和安全不再是同一句话的地方

2026 年 9 月初，一个开源仓库以寻找藏在 AWS 配置之间的攻击路径的安全验证工具为题被介绍到开发者社区。标题里最扎眼的词是之间。它说的不是配置之内，而是一项配置和另一项配置之间。

这个说法准确得不该被当成宣传语放过，因为云配置检查所遭遇的结构性限制正好就在那个位置。检查项给每个资源标上真或假。可权限并不被关在资源里，它朝着连上的地方流。流动是图的性质，不是条目的性质。

工具本身放到后半段，只核对事实。前半段要谈的是一个没有工具也成立的问题：在自己的账户里该把什么放进检查清单，那个之间才看得见；以及这份清单为什么无法只靠一堆单独的项目凑齐。

安全为什么是结构问题而不是知识问题，在信息安全为什么格外难学里谈过；不把凭据交到别人手上也能把活干完的做法，在不把凭据交给智能体也能让它干活里。这里刻意避开那两条轴，只看权限在资源之间移动的结构。

检查项看的单位是一个资源

随便想一条云配置检查规则，形状立刻就出来了。规则几乎总是这个资源的这个属性是不是这个值这样的问题。存储桶的公共访问阻止是否开启。数据库快照有没有被标为公开。日志组有没有设置保留期。答案是真或假，而做出判定所需的一切都装在那一个资源的属性里。

这种形状有很实在的好处。判定是确定性的，规则彼此独立，新增一条规则不会动摇已有的规则。写一条规则的人不需要知道别的规则。目录能长到几千条而不塌，原因就在这里。

同一种形状也有一道明确的天花板：判定所需的信息必须装得进单个资源。如果某个事实只有同时看两个资源的属性才成立，那这个事实就无法写成这种形状的规则。而写不出来的东西既不会通过也不会失败，它压根不是观察对象。

常见的误读就从这里生根。项目没有失败，于是被读成这一块是安全的。实际上没有失败和没有看过会以同一种绿色出现在同一块屏幕上。仪表盘并不把这两种状态分开呈现。

风险产生的单位 - 关系

权限不是资源的属性，而是主体与资源之间的关系。AWS 文档自身的组织方式就体现了这一点。基于身份的策略挂在主体一侧，基于资源的策略挂在资源一侧。角色的信任策略规定谁能成为这个角色。这三样单看任何一边都得不出结论。

AWS 用户指南把角色定义为可以在账户中创建的、具有特定权限的 IAM 身份，并立刻与用户区分开：角色不是与某一个人唯一绑定，而是被设计成任何有需要的人都能担任。角色没有密码或访问密钥这类标准的长期凭据，担任角色时会获得角色会话用的临时安全凭据。换句话说，角色本身就是一束会移动的权限。

同一页把委派定义为为了允许访问自己所控制的资源而向某人授予权限，并说明委派要在两个账户之间建立信任。一个是拥有资源的受信任方账户，另一个是拥有需要访问的用户的被信任方账户。在受信任方账户里创建的角色上会挂两份策略：规定能做什么的权限策略，以及规定谁可以担任的信任策略。

再加上角色链，关系就变成了一条链。文档的定义很简短：用一个角色去担任第二个角色。如果某个角色有权担任另一个角色，就能用第一个角色的短期凭据去担任第二个。文档补充了一条值得记住的运维细节：使用角色链时，控制台、命令行和 API 的角色会话被限制为最长一小时，而且这与各个角色上单独配置的最大会话时长无关。

这条链上的每一节，单独看都可能完全正常。角色 A 可以担任角色 B，本身并不是缺陷。真正要紧的是链的起点和终点。如果起点开得比预期宽，终点握着比预期强的权限，那么中间每一节都正常，结果仍会偏离本意。

通道之一 - 把角色交给服务的动作

第一条通道是把角色交给服务的动作。AWS 文档的说明这样开始：要配置许多 AWS 服务，必须把一个 IAM 角色传给该服务。这样服务之后就能担任该角色，代表你执行操作。大多数服务只需在设置时传一次，不必每次服务担任角色时都传。

传递需要权限。同一页写道，要把角色及其权限传给某个 AWS 服务，用户必须拥有把该角色传给服务的权限，并说明其用意是帮助管理员确保只有获批的用户才能用一个授予权限的角色去配置服务。

能显出这条通道性质的警告句就写在文档里：设置 PassRole 权限时，应确保用户不会传递一个权限超出你想赋予该用户范围的角色。文档给的例子很清楚：某个用户也许根本不被允许执行任何存储操作，但只要他能把一个允许存储操作的角色传给服务，那个服务就会在执行作业时代表他执行存储操作。

关系的性质到这里就清楚了。只看用户的权限策略得不出这个事实，只看角色的权限策略同样得不出。它只有把两者接起来才会出现，因为用户的有效权限不是由他自己的策略决定，而是连同他能传递的每一个角色的策略一起决定的。

收窄传递范围的手段，文档也一并给出。一是用策略语句的资源元素过滤可传递的角色，二是条件元素。其中 iam:PassedToService 条件键用来指定角色可以被传给哪个服务主体。文档还明确警告了另一个陷阱：不要试图通过给角色打标签、再在含 iam:PassRole 操作的策略中使用 ResourceTag 条件键来控制谁能传递角色。这种做法不会产生可靠的结果。

从可见性的角度看，最要紧的事实在日志一侧。文档的原话是：PassRole 不是 API 调用。PassRole 是一项权限，因此不会为 IAM PassRole 生成 CloudTrail 日志。要查看哪些角色被传给了哪些服务，必须查看创建或修改了那个接收角色的 AWS 资源的一方所留下的 CloudTrail 日志。按文档的例子，函数在创建时被传入角色，所以创建动作的日志里会留下被传角色的记录。

这一句为什么重要？因为如果审计管线是围绕 IAM 事件搭起来的，这条通道在结构上就不会落进日志。该看的地方不是 IAM，而是接收了角色的那个服务。

通道之二 - 信任策略接受的主体

第二条通道是角色的入口。AWS 文档把信任策略定义为用来定义你信任其担任该角色的主体的 JSON 策略文档，并写明角色信任策略是附加到 IAM 中角色上的必需的基于资源的策略。可以在信任策略中指定的主体包括用户、角色、账户和服务。

同一页也列出了可以担任角色的主体：同一账户或另一账户中的 IAM 用户、同一账户中的 IAM 角色、用于 AWS 服务和功能的服务主体，以及由与 SAML 2.0 或 OpenID Connect 兼容的外部身份提供商所认证的外部用户。最后这一项，把信任策略变成了跨越账户边界的文档。

文档明确写下了一条语法层面的约束：创建信任策略时，不能在主体元素的 ARN 中使用通配符作为其一部分。但这条约束并不会自动收窄信任范围。以账户为单位的主体，或者不带条件的联合身份主体，在语法上完全有效，此时信任的实际范围由条件元素而不是策略语法来决定。

所以在信任策略里该看的不是主体元素本身，而是主体与条件这一对。当主体指向某个账户或某个外部提供商时，它旁边有没有收窄范围的条件，才决定了信任的真实边界。条件为空的信任策略能同时通过语法校验和逐项检查，同时留下一个比任何人本意都要宽的入口。

通道之三 - 资源策略指向账户之外的时候

第三条通道是挂在资源一侧的策略。AWS 文档的定义很直白：基于资源的策略控制指定的主体如何访问该策略所附加的资源。文档还说明，有些服务允许不经角色代理，而是直接给资源附加策略，从而把访问权授予另一个账户中的主体。

这条通道之所以经常从逐项检查里溜走，是因为制造风险的不是策略的存在，而是策略指向的方向。策略存在这件事本身既不真也不假。要下判定，就得判断其中的主体落在信任区之内还是之外，而这个判断需要资源之外的信息：你的账户和组织的边界。

AWS 把这个判断做成了服务，就是 IAM Access Analyzer。文档说它帮助识别你的组织和账户中与外部实体共享的资源，并把方法描述为用基于逻辑的推理分析 AWS 环境中基于资源的策略，从而识别与外部主体共享的资源。创建分析器时选定的组织或账户就是它的信任区，信任区内主体的访问被视为可信。

运维上的注意事项也写在同一份文档里。新增或修改策略后大约 30 分钟内会被分析；在少数收不到变更通知的情况下，会在下一次约 24 小时内的定期扫描时分析。还有一条限制被加粗写出：就外部访问而言，IAM Access Analyzer 只分析应用在与其启用区域相同的区域内的资源上的策略。要覆盖所有区域，必须在每个使用受支持资源的区域各创建一个外部访问分析器。文档同时给出对照：未使用访问的结果不随区域变化，无需按区域逐一创建。

也就是说，这条通道的可见性不是开启就算完成。哪些区域有分析器，就是哪些区域看得见。

通道之四 - 服务代替用户去调用的时候

第四条通道是主体不再是人而是服务的位置。AWS 文档把这里的失效模式称为混淆代理人，定义为一个没有权限执行某项操作的实体，能够胁迫一个权限更高的实体去执行该操作的安全问题。

跨服务情形的说明尤其精确。文档写道，当调用方服务的 AWS 服务主体访问被调用方服务的资源时，被调用方服务的资源策略只授权那个 AWS 服务主体，而不授权配置了调用方服务的行为者。在文档给出的例子里，一个不带任何条件就信任某个服务主体的存储桶，既会收到受信任管理员所配置的日志，也可能收到另一个账户中未获授权者的日志，只要对方知道存储桶的名字。

在跨账户的情形里，外部 ID 是那件装置。文档把它介绍为可以在 IAM 角色信任策略中用来指定谁能担任该角色的可选标识符，并写明外部 ID 的首要作用就是应对并防止混淆代理人问题。取值的掌控方也说得很清楚：外部 ID 的值必须在服务提供方的众多客户之间保持唯一，并且由提供方而不是客户来掌控。所以这个值是从提供方那里拿到的，不是自己想出来的。

{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "Principal": { "AWS": "EXAMPLE-PROVIDER-ACCOUNT-ID" },
    "Action": "sts:AssumeRole",
    "Condition": {
      "StringEquals": { "sts:ExternalId": "EXAMPLE-EXTERNAL-ID" }
    }
  }
}

上面的形状就是文档给出的跨账户信任策略骨架，账户标识符和外部 ID 的位置只放了占位符。这里要看的不是取值，而是条件元素在不在。

跨服务情形的装置在条件键这一侧。文档写道，建议在任何向 AWS 服务主体授予访问你资源的权限的位置，都在资源策略中使用 aws:SourceArn、aws:SourceAccount、aws:SourceOrgID 或 aws:SourceOrgPaths。各自的用途也分得很清楚：代表某个具体资源时用 SourceArn，代表某个具体账户时用 SourceAccount，代表特定组织时用 SourceOrgID，按组织路径时用 SourceOrgPaths。

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "Service": "EXAMPLE-SERVICE.amazonaws.com" },
      "Action": "EXAMPLE-SERVICE:ExampleAction",
      "Resource": "EXAMPLE-RESOURCE-ARN",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "EXAMPLE-ACCOUNT-ID" }
      }
    }
  ]
}

想把同一套控制在组织范围内一次性加上，文档给出的手段是资源控制策略：它让你不必在具体的基于资源的策略里逐条添加语句，就能从中心把跨服务的混淆代理人控制施加到组织、组织单元和账户上。不过文档对服务控制策略和资源控制策略钉下一句：仅靠这些策略不足以向组织中的主体和资源授予权限。服务控制策略和资源控制策略不授予任何权限。它们是上限，不是授予。

把四条通道并进一张表，就能一眼看出每种类型都得换个位置去看才显形。右边一列是本文的核心：制造风险的东西和让它显形的东西并不在同一个资源里。

表的左边两列在设计时就定下了，右边一列则要在运维时另行取得。这两列所处的时点不同，正是这个问题难办的实际原因。设计时形成的关系会一直留着，而能看见它的装置要在之后单独打开。

有效权限是交集 - 策略类型重叠的地方

要沿着关系往下走，先得知道真正通得过的权限是怎么定的。AWS 文档把有效权限定义为影响该用户或角色的所有策略所授予的权限，并列出账户内可能影响实体权限的东西：基于身份的策略、基于资源的策略、权限边界、组织的服务控制策略和会话策略。

规则的骨架是两句话。第一，只要这些策略类型中任何一种对某项操作显式拒绝访问，该请求就被拒绝。第二，允许一侧要看类型的组合。就基于身份的策略与权限边界而言，有效权限是两种策略类型的交集；再加上组织的服务控制策略，则只有三种策略类型全部允许时请求才被允许，有效权限是三者的交集。有会话策略时同样是三者的交集。

权限边界的定义如前所引：它是使用托管策略来设定基于身份的策略可以授予 IAM 实体的最大权限的高级功能，而且实体的权限边界使它只能执行其基于身份的策略和权限边界二者都允许的操作。最关键的一点是，它只限制权限，本身并不提供权限。

到这里可以用交集一个词概括。可紧接着文档就列出了打破这个概括的例外。让关系分析真正变难的，正是这些例外。

  • 在同一账户内，向 IAM 用户 ARN 授予权限的基于资源的策略，不受基于身份的策略或权限边界中的隐式拒绝限制
  • 向 IAM 角色 ARN 授予权限的基于资源的策略，会受到权限边界或会话策略中的隐式拒绝限制
  • 向角色会话 ARN 直接授予权限的基于资源的策略，是把权限直接给了该会话，不受基于身份的策略、权限边界或会话策略中的隐式拒绝限制。担任角色并发出请求时，发出请求的主体是角色会话的 ARN，而不是角色本身的 ARN
  • 联合身份用户会话具有同样的性质；不过如果资源策略把权限授予了发起联合的那个 IAM 用户的 ARN，则该会话期间的请求会受到权限边界或会话策略中隐式拒绝的限制
  • 在文档给出的例子里，被权限边界显式拒绝的对象，即使资源策略允许也访问不了；而边界没有显式拒绝的服务，仅凭资源策略的允许就能访问成立，因为权限边界中的隐式拒绝不限制基于资源的策略

读完这份清单就明白，为什么有效权限很难靠人眼去加总。同样一条允许语句，主体是用户 ARN、角色 ARN 还是会话 ARN，结果就不一样。同时也明白了，逐项检查并不会替你做这道计算。

当作图来看 - 追问可达性

既然关系是风险的单位，下一步自然就是把关系搬进节点和边。把主体、角色、资源放成节点，把担任、传递、授予访问放成有向边。于是问题的形状变了：不再是这项配置对不对，而是从这里能不能走到那里。

这一转换的好处很具体。第一，可以脱离单项是否通过来追问路径的存在。第二，路径存在这件事与路径上哪一节有缺陷无关，因此可以表达没有任何缺陷、路径却存在的状态。第三，处置的优先级性质变了：切断一条路径所需的最小改动落在哪里，成了图上可以计算的问题。

引出本文的那个仓库，其设计文档也走这个方向。文档这样区分单项配置失误与复合风险：单项配置失误只是制造了被攻陷的条件，它们本身并不是攻陷。并把控制与链的差别定义为：控制是关于单个资产属性的谓词，链是多个控制之间的关系。控制回答的是这一件事是否配置正确，链回答的是这些失败合在一起是否造成了大于各部分之和的风险。

同一份文档里还有一个在实务上很有意思的设计选择。链带有升级阈值：一条含三个成员控制、阈值为二的链，在三者中任意两个同时失败时激活。文档给了两个理由：真实的攻击路径通常需要大部分条件而未必是全部；以及阈值能防止某一个控制的瞬时失败直接跳成一条严重的复合结论。

边是怎么形成的，文档也写了。每条链带上从一个封闭能力词表中选出的前置条件与后置条件，若某条链的后置条件与另一条链的前置条件相符，两条链之间就有了一条有向边。文档谨慎地说明这是什么：这不是图算法，而是对活跃链做双重循环取集合交集，并且图结构是数据，不是计算。路径查找、中心性分析和可视化交给外部工具。

静态分析解决不了的事

图的方法有明确的边界，而这些边界大多来自策略文档里没有写的东西。AWS 自己的文档在好几处显出了这条界线。

第一是条件键。AWS 建议可以指定策略语句生效的条件，这样就能只在访问请求满足特定条件时才授予对操作和资源的访问。文档举的例子是要求所有请求都通过 TLS 发送的条件，以及只在通过特定服务使用时才允许的条件。难点在于条件的真假由请求发出那一刻的上下文决定。只摆着策略文档，判定不出那个条件实际什么时候为真。

第二是时间。有些数值在文档里钉死了，比如角色链会话的一小时上限；但会话的实际寿命、凭据此刻是否真的被谁持有，都不会落进配置快照。一条路径在结构上可能，与它此刻通得过，是两个不同的陈述。

第三是账户之外的状态。接受联合身份主体的信任策略，其实际边界取决于外部身份提供商一侧的配置。快照里没有那个提供商的状态。

第四是分析工具自身的观测范围。如前所引，外部访问分析只看应用在与其启用区域相同的区域内的资源上的策略。文档还指出，在某些条件下策略变更的通知可能漏掉而导致结论生成延迟，涉及多区域接入点的变更最长可能需要六小时。基于快照的分析还要再加一条：快照拍下之后发生的变更，不在这份快照里。

第五是日志上的窟窿。PassRole 不留 CloudTrail 记录，这是事后追溯的限制而非静态分析的限制，但两种限制交叠的地方问题会变大。静态分析也许能告诉你路径存在，而仅凭 IAM 日志，没有办法确认这条路径究竟有没有被用过。

引出本文的仓库实际标榜的是什么

这里有必要把社区标题和仓库的自我表述并排放一下。社区上的标题是寻找藏在 AWS 配置之间的攻击路径的安全验证工具。仓库 README 开头一段说的却不同：开源的云配置验证器。它不是去找哪里错了，而是证明你的 AWS 配置是正确的。无需任何凭据，可离线运行。仓库的描述字段另写着找出单资源扫描器会漏掉的复合攻击路径。

两句话的重心落点不同。标题落在寻找，README 落在证明。README 甚至专门强调了这个区分：用词是验证器，不是扫描器；是证明，不是启发式。复合路径的发现是搭在那之上的一条支线，并不是这个项目自我表述的全部。

还有一处与标题对不上。标题特指 AWS，但仓库中生成的控制参考文档在按服务列出的表里，除 AWS 之外还一并列有 Azure 141 项、Cloudflare 29 项、Cisco 30 项这样的条目。AWS 显然是重心，但目录并非只覆盖 AWS。

运行模型上也有一点需要纠正。无需凭据这句话对应的是评估阶段。README 说明评估从不调用 AWS API，只看本地的 JSON 快照；而对拍摄快照的采集阶段，它写明会执行只读的 AWS 命令行调用，并需要 SecurityAudit 凭据。不需要凭据的是评估，采集要花一份只读凭据。

采集方式分成三条路，README 里也用表整理了。面向受监管环境的一条使用随附的采集器或预先写好的过滤器，全程不涉及大语言模型；务实的一条让本地模型把原始 JSON 映射成契约格式，之后再做确定性评估；贡献者的一条让模型写过滤器、由团队审阅后随仓库发布。文档主张，契约与评估在任何一条路上都是确定性的。

官方文档定下的四条最小原则

无论用不用工具，把关系放进清单的底子，是 AWS 文档早已写明的那些原则。下面把四条以接近原文的表述搬过来。

第一，最小权限。原文是用 IAM 策略设置权限时，只授予执行任务所需的权限，做法是定义在特定条件下对特定资源可以采取的操作。还附了一条现实的说明：在摸索工作负载或用例所需权限的阶段，可以先从较宽的权限起步；随着用例成熟，可以逐步收减所授予的权限，向最小权限靠拢。关于托管策略，文档也写明由于面向所有 AWS 客户提供，它们对你的具体用例未必是最小权限。

第二，权限边界。文档建议，在账户内委派权限管理时，用权限边界来设定所委派的最大权限。它举的场景是允许开发者为自己的工作负载创建和管理角色。如前所述，边界是上限，本身不授予任何权限。

第三，条件键。文档专门列了一项：在 IAM 策略中使用条件来进一步限制访问。条件在关系分析里格外重要，因为正如前面那张表所示，好几条通道上分开风险与安全的不是语句在不在，而是条件在不在。

第四，访问分析。文档建议三条路：在授予公共或跨账户访问之前先确认这种访问是否必要并检视结论；根据 CloudTrail 中记录的访问活动生成最小权限策略；以及通过策略校验确认语法与最佳实践。就校验而言，文档写明提供超过 100 项策略检查和可执行的建议。关于未使用的访问，另有一项：定期检视并移除不再需要的用户、角色、权限、策略和凭据。

把这四条改写成关系的语言，就成了检查清单。可传递角色的范围有没有宽过传递方主体的权限。委派有没有加上上限。每一条接受宽泛主体的语句上有没有条件。指向账户之外的策略是否在每个区域都被观测到。这四个问题都有同一个性质：只有同时看两个以上的对象才有答案。
