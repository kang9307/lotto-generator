问名字这件事交给了谁 - 加密 DNS 遮住的范围与它之外

一家公共解析器关门之际，重新画出加密覆盖的区段，以及设置究竟落在哪一层

2026-09-06 IT/技术

在浏览器地址栏敲下一个域名，页面变化之前会先有一次安静的问答。它问这个名字对应哪个地址，然后收到一个数字作为答复。这次问答不会显示在屏幕上，耗时通常只有几十毫秒，所以没人会察觉。可是，最准确掌握一天里访问过哪些站点的，并不是那些站点本身，而是接下了这个问题的那一方。

因此这次问答托付给了谁，分量远不止一个设置项。可这个设置项通常是定一次就被遗忘的。几年前读到某篇文章，往路由器里填了四个数字，此后再没打开过那个页面。这一次，一家免费的公共加密 DNS 公布了关闭时间表，那些被填进去的位置于是一并浮出水面。

这则关闭公告本身是件小事。真正值得借它重画一遍的，是另一幅图。把 DNS 加密之后，究竟什么被遮住，什么原样留着；以及这个设置如今散落在几个层级上，彼此冲突时哪一边胜出。下面没有任何替代服务的推荐，只有选择之前该读什么。

以下关于规范的叙述，都限定在相应 RFC 与各厂商公开文档所写的范围之内。不推荐任何特定服务，也不涉及以绕开封锁为目的的配置。在文档中找不到依据的条目不用推测填补，而是集中放在后面的一节里。

起因 - 一家公共解析器关门

2026 年 9 月 3 日，Mullvad 公告称将关闭其公共加密 DNS 服务器，把资源转为对 Quad9 的资金支持。这项服务自 2022 年起运行，形式是任何人只要在设置里填上地址就能使用。公告写明的期限是2026 年 11 月 2 日，此后手工指定的配置将收不到答复。

标题一般会被转述成加密 DNS 关闭。但把关闭的对象范围划准，要有用得多。把公告和帮助文档并排放着看，界线是这样分的。

  • 关闭的部分 — 只要知道地址谁都能用的公共解析器。按帮助文档的说明，它以 DoH 与 DoT 两种方式提供，并按广告拦截、家庭过滤等分成六个主机名。文档上挂出的提示是「公共加密 DNS 服务将于 2026 年 11 月 2 日停止」
  • 不关闭的部分 — 在使用该厂商 VPN 期间处理查询的内部 DNS。公告写道，使用 VPN 时流量本已加密，内部 DNS 会处理全部查询，因此公共服务器并非必需
  • 会被自动迁移的部分 — 在同一家公司的浏览器里保持默认 DoH 设置或随附广告拦截设置的用户，会被自动迁移到 Quad9。反过来，手工改动过的配置不会被触碰。也就是说，动过手的人反而要自己搬

理由公告里也写了。以隐私为中心运营公共 DNS 是一项高度专业化的工作，与其重复已经在做这件事的组织的努力却只做到其中一部分，不如把资源投向对那一方的资金支持。这里值得带走的不是某家公司的决定，而是公共解析器的运营是一笔持续成本这一事实。用起来免费，不等于运营起来免费。

问名字的流程 - 一次连接里查询经过的位置

把一次连接里什么经过了哪里按顺序摆开，后面所有的讨论都会落在这幅图上。

首先，终端内的存根解析器向递归解析器问一个名字。递归解析器若已有答案就直接从缓存返回，若没有则从根开始，经顶级域一路下到权威服务器，边走边把答案凑齐。这个往下走的过程本身属于委托的问题，每一层各自把什么交给了谁，已经整理在更换域名服务器到底交出了什么里。拿到的答案放在哪里、放多久，则是DNS 缓存告诉我们的事的主题。本文看的是它们之前的那一段，终端与递归解析器之间的单跳。

拿到答案后，终端会向那个 IP 建立 TCP 连接并开始 TLS 握手。从这里起就不再是 DNS 的地盘了。可是从隐私的角度看，这两个阶段是连在一起的，因为紧接着就会向那个名字的地址开出一条连接。

所以把观察者拆成三个位置更准确。这三者看到的东西各不相同，而加密处理的只是其中之一。

  • 链路上的观察者 — 处在同一无线区段的设备、中间网络，以及提供接入的运营方。它看到的是终端与解析器之间往来的数据包
  • 解析器运营方 — 接下查询并作答的一方。处理请求本身就意味着同时处理问了什么与谁在问
  • 看到后续连接的一方 — 处在能看见流向目的地 IP 的流量的位置。它看到的是地址而不是名字，视情况还能看到握手里带的服务器名

规范定下的东西 - DoH 与 DoT 与 DoQ

被笼统称作加密 DNS 的，实际上是三份彼此独立的规范。三者针对的都是终端与递归解析器之间的那一段，区别只在于架在哪种传输之上。

最后一栏里反复出现的表述就是本文的核心。三份规范消除的都是网络之中的观察。它们没有承诺更多。规范文本自己就把范围划得这么窄。

在实务中三者拉开差距的地方不是安全等级，而是可区分性。走专用端口的方式，网络设备容易把它和其他流量分开；走网页端口的则不然。这一性质在管理者立场和使用者立场上各自既是优点也是缺点，哪一种更优的结论并不会从规范文本里长出来。

什么被遮住，什么没有

把被遮住的范围按观察者逐一画出来是值得的，因为之后所有的选择都从这张表派生。左列是观察者，中间两列是该观察者看到的内容，右列是依据。

观察者明文 DNS 时看得到的加密 DNS 时看得到的依据
同一无线区段的设备、中间网络 问过的全部域名、时刻与重复模式 与解析器通信过这件事。名字看不到。不过规范留了一句，对消息时序与大小的分析仍可能透出某些细节 RFC 7858
提供接入的运营方 全部域名，以及后续连接的目的地 IP 名字被遮住了。但后续连接的目的地 IP 原样留着；握手里的服务器名称指示若是明文，那个名字同样可见 RFC 8744
解析器运营方 全部查询，以及发出查询的地址 没有变化。规范文本写道，递归解析器前面通常没有缓存，因此它看得到全部流量，并补上一句，概括起来递归解析器对你了解得相当多 RFC 9076
被访问的目的地服务器 连接这件事本身及其 IP 没有变化。DNS 加密根本不触及这个位置 范围之外
在终端上运行的软件 自己查过什么 没有变化。应用若自带解析器，就会与操作系统的设置无关地走自己的路径出去 范围之外

第三行是这个话题里最常被读反的地方。开启加密 DNS 并不等于谁都看不到。看得见的名单上少了一类，取而代之的是你新选中的那一家留在了那个位置。RFC 9076 还补了一句：全球 DNS 解析流量中由少数几个主体处理的比例越高，用户的隐私就越发取决于那些主体的政策与做法。

解析器之后剩下的 - SNI 与 ECH

拿到名字之后建立的 TLS 连接里带着服务器名称指示。当多个站点共用一个 IP 时，服务器需要知道请求是发给哪一个的，于是客户端会把要连接的名字写进第一条消息。问题在于，这第一条消息此时还没有被加密。梳理 SNI 加密问题与需求的 RFC 8744，起点正是这一点：该扩展以明文放在客户端问候里。

所以在只加密了 DNS 的状态下，路径是这样的：问名字的那次问答被遮住了，紧接着建立的连接的第一条消息又把那个名字用明文写了出去。等于把刚遮住的东西在几毫秒后重新亮了一遍。

针对这个位置的规范是RFC 9849 TLS Encrypted Client Hello。它于 2026 年 3 月作为标准轨道文档发布，定义了用服务器公钥加密客户端问候本身的机制。等它站稳，目的地的名字就会从第一条消息里消失。

不过这里有一处结构值得回头看。RFC 9849 只定义配置的格式，把 DNS 上的发布细节交给了别的文档。配置如何在 SVCB 与 HTTPS 记录中通告由 RFC 9848 处理，记录格式本身则由 RFC 9460 定义。换句话说，用来藏起名字的那把钥匙是通过 DNS 取回来的。规范也写明其他分发方式同样可行，并以客户端预置配置为例。即便如此，在常规路径上，问名字这道工序仍排在藏名字之前。

结果是，向谁问名字这个问题并不会随着时间收窄，反而牵扯得更多。一条查询路径同时挂在缓存、委托、证书签发与握手加密上。

信任不会消失，只会转移

走到这里，结论就变简单了。开启加密 DNS 是一次改变信任对象的操作，而不是消除风险的操作。从前是提供接入的运营方给出默认解析器，由它看着查询；现在是自己挑的解析器运营方在看。名单上的名字换了，名单并没有空。

同样的结构在别的工具上一再重复。开一条隧道，接入运营方的位置就由隧道运营方接手。什么会转移、什么原样不动，已经在VPN 到底保护什么、不保护什么里按区段拆开过。DNS 遵循的正是同一套语法。

所以问题的形式必须换。不是安不安全，而是我新决定去信任谁，以及这个决定日后能不能撤回。后一个问题，才是这次关闭公告真正摆上台面的课题。

这张表里刻意缺了一行：哪一家更好。文档能判断的，到承诺的范围以及为守住承诺所需的组织条件为止；再往后，回答的不是文本，而是审计与时间。

免费公共服务关门时最先坏掉的

关闭公告里人们看的是日期。可真正带来麻烦的不是日期，而是想不起那个地址到底被填进了哪些地方。如果这些年里路由器上填过、笔记本的设置里填过、浏览器的设置里填过、服务器的配置文件里也填过，那么这四处会在四个不同的时点坏掉。

第三行是这张表里最糟的一格，因为那是失败看不见的配置。名称解析断了会马上去修；悄悄退回明文，则会让人过了几个月还相信它开着。所以选择失败模式，其实就是在选择自己什么时候会知道。

第五行也值得翻过来看。保持默认没动的人什么都不会遇到，把设置调得很细的人反而要自己搬。多拿一分控制权就多担一分维护责任，这种常见的交换在这里同样成立。

设置在哪里 - 层级与优先顺序

这个话题里真正的混乱，多半来自设置不止一处这一事实。路由器上能设一次，操作系统里能设一次，浏览器里还能设一次，三者可以指向不同的地方。而当三者冲突时，结果会与用户的预期不一致。下表整理了每一层覆盖什么、与别的层冲突时会怎样，以及用什么去看当前状态。

设置所在位置适用范围与其他设置冲突时如何核对
路由器的 DHCP 下发 连在该网络上的所有终端的默认值。只有终端自己没决定时才会生效 最弱。只要终端或浏览器里钉了值，查询就按钉住的值出去 路由器管理页面的 DHCP 项，以及终端实际拿到的地址
操作系统的 DNS 服务器指定 该终端上所有使用系统解析器的程序 覆盖路由器的值，但覆盖不了自带解析器的应用 Windows 用 PowerShell 查询，Linux 与 macOS 查系统解析器状态
操作系统的加密选项 在同一范围之上再叠一层是否允许退回明文。Windows 给出仅加密、加密优先、仅明文三个值 属于同一层内的下级设置。它在地址定下之后，决定怎么走向那个地址 网络适配器上的 DNS 加密项
移动系统的私人 DNS 整台设备。Android 的说明写道，默认情况下设备会在所有能使用该功能的网络上启用它，并给出关闭、自动、指定主机名三个值 优先于网络下发的值。同一份说明明确写道，该功能只保护 DNS 的问与答，别的一概保护不了 设置的网络项里的私人 DNS
浏览器的安全 DNS 仅限该浏览器的查询。同一台设备上的其他应用不受影响 在该浏览器内部覆盖系统的值，但有若干会让它主动退让的条件 浏览器的安全设置页面
组织的管理策略 受管设备与浏览器。Windows 的组策略给出允许、禁止、必须三个值 优先于用户设置。谷歌的说明写道，设备受管或家长控制开启时，安全 DNS 功能根本无法使用 策略应用结果查询，浏览器的受管状态标识
应用自身的设置 仅限该应用。内置了自有解析器的程序属于这一类 最窄也最强。该应用的查询最终按该应用的设置走 应用的网络设置界面或配置文件

贯穿这张表的规则可以压成一句话。范围越窄的层越强。网络下发的值最弱，应用在自己内部定下的值最强。例外是组织的管理策略，它范围很广，却被设计成能覆盖用户设置。

所以「我已经开了」这句话本身并不构成信息，得把层级补上才有范围。若是在浏览器里开的，同一台笔记本上的通信软件和更新程序依旧走着另一条路径出去。

某一层主动退让的条件

层级表还得再补一格，图才算合上，那就是开着却没有生效的情形。浏览器和操作系统都有关于这一点的文档。

Firefox 的开发文档把跳过可信递归解析器路径、退回原生解析器的原因列成了清单。下面是实际上常碰到的几项。

  • 用户已把相关的设置项明确关掉
  • 系统级家长控制处于开启状态
  • 强制门户检测与连通性检查这类被标记为不走该路径的请求
  • 出现在排除域名列表中的名称
  • 没有网络连接，或系统处于睡眠状态
  • 检测到 VPN、代理，或者无效的 TLS 配置
  • 检测到企业策略，或证书根被修改过

谷歌关于 Chrome 的说明更短。自动模式下若出现问题，浏览器可能退回未加密的方式；指定了自定义提供方时则不会退回。并且明确写道，设备受管或家长控制开启时，这项功能根本无法使用。

操作系统这边最有实务价值的一句在微软文档里。加密优先的设置兼容性最好，但查询从加密切到明文时不会给出通知。同一份文档还警告不要在已加入域的机器上启用必须选项，因为目录服务高度依赖 DNS，而对应的服务器服务并不支持那种方式的查询。企业环境里调紧这项设置结果把登录搞坏的事故，就是从这里来的。

所以需要一套看清当前走哪条路径的流程。Windows 可以分别查询各网卡的服务器地址与已知的加密服务器清单。

# 网卡上配置的 DNS 服务器地址
Get-DnsClientServerAddress -AddressFamily IPv4

# 本系统已知的加密 DNS 服务器清单
Get-DnsClientDohServerAddress

Linux 与 macOS 可以直接查看系统解析器的状态，而某次查询实际由哪台服务器作答，会显示在查询结果的服务器一行上。

# systemd-resolved: 各接口的 DNS 服务器与加密状态
resolvectl status

# macOS: 系统识别到的解析器清单
scutil --dns

# 实际作答的服务器地址
dig example.com | grep SERVER

如果这些值与预期不符，就从层级表里比自己更强的那些层自上而下过一遍，原因就会浮出来。在浏览器里开了，而系统查询指向另一台服务器，这是正常的，因为两层做的本来就是不同的查询。

网络指定解析器的新方式 - DDR 与 DNR

手工填地址这套做法带着一个老问题：要用加密解析器，光有 IP 地址是不够的。还得知道主机名、端口、方式，有时甚至要知道 URI 模板。可传统的下发手段只发 IP 地址。

填补这道缝隙的两份规范于 2023 年 11 月发布。RFC 9462 指定解析器的发现定义了客户端借助 DNS 记录获知解析器加密配置的机制，分两条路：只知道 IP 地址时向一个特殊用途域名发起查询，已经知道名称时则查询 SVCB 记录。RFC 9463 网络指定解析器的发现则定义了通过 DHCP 与路由器通告下发同样信息的选项。DHCPv6 选项 144、DHCPv4 选项 162、IPv6 路由器通告选项 144 负责携带认证域名、地址与服务参数。

这两份规范的现实含义很直白。今后由网络自动指定加密解析器的情形会越来越多。这意味着不用手工填也可能把加密开起来，同时也意味着是谁定的会变得更不可见。正因如此，层级表往后只会更被需要。值得回答的问题从「有没有开」，变成了是哪一层定下了这个值。

RFC 8484 写下客户端不得仅因某地址是在自身配置之外被发现就去使用它，放在这个语境里读来也是同一个意思：发现是便利，信任则是另一个决定。

让自己始终处在能迁移的状态

这件事真正留下的心得，不是挑替代者的窍门，而是让自己下一次也搬得动的做法。服务还会再关，政策还会再改。趁现在把那时要付的代价压低，是更划算的做法。

  • 把填过地址的位置列成清单。路由器、每台设备的操作系统、每个浏览器、服务器配置文件、容器镜像。没有这份清单，关闭公告来了也不知道该去改哪里
  • 把要改的地方收拢到一处。按层级表的规则窄的层胜出，所以把值散在多个层上，改了其中一处结果也不会变。只在网络这一层设定、其余保持默认的构型，维护成本最低
  • 刻意选定失败模式。是让它立刻失败，还是让它悄悄退回明文。Windows 的那两个设置正是这组选项。若目的是隐私，安静的退让会把目的整个架空
  • 看关闭公告时，除日期外还要看三件事。什么会被自动迁移、动过的配置会怎样、对象是公共服务还是连附属功能一起。这次公告里这三个答案各不相同
  • 先确认内部的名称解析。存在内部域名的环境里，强制加密会把内部查询切断。微软文档针对已加入域的机器发出警告，原因正在于此
  • 准备一套区分名字解析不了与连不上的流程。上一节那几行查询命令就足以分开。少了这层区分，解析器关闭会被误诊成线路故障

这份清单里最值钱的是第一条，其余各条都要等清单存在之后才执行得起来。

常见问题

开启加密 DNS 之后，访问记录就不会留下了吗?

只是记录的位置换了地方。RFC 7858 写道，TLS 消除的是网络之中的窃听与在途篡改的机会。被遮住的是终端到解析器之间的那一段。解析器运营方照样看得到查询，RFC 9076 也写明递归解析器前面通常没有缓存，因此它看得到全部流量。拿到名字之后建立的连接仍带着目的地 IP，服务器名称指示则如 RFC 8744 所述以明文传送。

这次关闭对使用该 VPN 的人有影响吗?

公告针对的是只要填上地址谁都能用的公共解析器。该运营方在同一份公告里写道，使用自家 VPN 期间内部 DNS 会处理全部查询，因此公共解析器并非必需。受影响的是那些把地址手动填进设备、浏览器或路由器的配置。只看标题就理解成整个服务消失，会把范围判断错。

DoH 与 DoT 哪一个更安全?

两份规范保护的对象是同一个。DoT 在专用端口 853 上使用 TLS，DoH 则把每一对查询与响应映射成一次 HTTP 交换承载在 HTTPS 之上。DoQ 在规范里自述具有与 DoT 相似的隐私性质。差别不是安全等级，而是显眼程度与管理方式。专用端口在网络上容易区分，混进网页流量的那一种则不然。

浏览器里明明开了，为什么有些查询还是走明文?

因为浏览器主动退让的条件是有文档记录的。家长控制、强制门户与连通性检查、排除域名、检测到 VPN 或代理、企业策略与被修改的证书根，都在那份原因清单里。操作系统这边也一样，Windows 的加密优先设置在退回明文时不会给出通知。

不保留日志这种说法要靠什么来判断?

只能把文档能担保的和担保不了的分开来读。Mozilla 的解析器政策要求 24 小时的保留上限、禁止向第三方出售与转移、禁止与其他数据结合以识别个人，并要求发布解析器专用的隐私声明与至少每年一次的透明度报告。这些条目划定的是承诺的范围，并不能证明承诺被履行，所以管辖地与资金结构也要一并读。

未能确认的部分

以下条目因为在一手文档中找不到依据而从正文中拿掉了，没有用推测去填补。

  • 关闭对象是否明确包含 DoT — 公告正文把公共加密 DNS 服务器称作 DoH，而帮助文档上的提示写的是「公共加密 DNS 服务」整体停止。既然那份文档把 DoH 与 DoT 一并介绍，读作两者都包含是自然的，但方式不同日期是否有别，文档里没有单独的表述
  • Firefox 三档保护级别的名称与定义 — 相应的支持文档页面两次尝试都未能渲染，因此改以公开的开发文档中的绕过原因清单为依据。默认、增强、最高这几档的准确定义没有写进正文
  • Chrome 管理策略的取值定义 — 未能在策略清单页面打开对应条目，因此只引用了面向普通用户的支持文档所写的范围。管理员策略取值的准确名称与行为从正文中拿掉了
  • Android 私人 DNS 使用的协议标注 — 支持文档只说明了功能范围与三个取值，并未写明采用哪一份规范，因此正文中也没有指定方式
  • 苹果系统的加密 DNS 配置文档 — 目标文档地址没有响应，因此没有在层级表中为其建行
  • Windows 客户端版与服务器版的差异 — 引用的文档面向服务器版。客户端版的界面构成与默认值是否相同，没有另找文档做过比对
  • Quad9 资金结构的细节 — 隐私政策文档里只有责任主体与创始组织的标注，并未叙述资金结构。表中只处理了该条目的存在，取值留空
