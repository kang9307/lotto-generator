把部署平台放到自己服务器上这个选择

消失的成本与新产生的成本不是同一种货币 - 以及部署工具自身的复原路径

2026-07-30 开发/基础设施

引言：决定「连部署都在自己服务器上」，究竟买下了什么

第一次看到自托管部署平台，大多会有同一个反应：「有了这个，就不必用托管服务了吧。」屏幕上有一条流程，接上仓库就自动判断技术栈、构建镜像，连域名和证书都替你挂好。听说这条流程可以跑在自己的服务器里，觉得有吸引力是自然的。

但这个决定的真实内容不是消除成本，而是改变成本的种类。消失的一侧是与用量挂钩的重复支出，以及对某一家服务商约定的依赖。新出现的一侧是运维责任：操作系统补丁、备份以及恢复演练、证书续期、构建缓存吃掉的磁盘、入侵响应，还有一项几乎没人提起的——部署系统本身宕机时，你用什么来部署。

本文不是工具介绍。不排名，也不写价格。价格变动频繁，过了核对的那天就会立刻变成错误信息。本文写的是「我们自己托管」这句话所附带的条件，逐项列出。出发点是最近公开的一个开源项目。所有事实都在2026年7月30日直接核对了官方仓库与各组件的官方文档，无法核实的数字一律不写。示例域名统一为example.com，示例地址为192.0.2.1。

顺带说明，选择哪种托管形态不在本文范围内。静态、共享、VPS、PaaS之间的决策树已经在选择网站托管的判断标准里讲过。本文接在那个决定已经落在「我们要用服务器」之后，讨论是否要把部署自动化也放上去。

1. 出发点 - 只写官方仓库确认过的内容

对象是Openship。官方仓库是github.com/oblien/openship，它把自己介绍为内置CI/CD的开源可自托管部署平台。许可证是Apache License 2.0。这里的关键是这个项目并不打算只替代PaaS或者CI，而是同时替代两者。代码进来变成镜像，以容器运行，对外暴露的路由和证书也都在同一个系统里处理。

仓库描述的行为分五个阶段：检测 → 构建 → 运行 → 路由与安全 → 推送即部署。检测阶段会读取package.json、框架配置、锁文件，以及可选的docker-compose.yml或openship.json，来判断技术栈和构建命令。构建阶段产出Docker镜像，或者在目标服务器上产出仓库所称的裸发布；运行阶段以容器或受监管的主机进程运行。路由阶段由OpenResty边缘创建反向代理虚拟主机并签发Let's Encrypt证书。最后一个阶段是GitHub Webhook，被跟踪的分支收到推送时重新触发流水线。

项目官方仓库写明的内容在本文中成为问题的地方
性质内置CI/CD的开源可自托管部署平台同时替代PaaS与CI，故障时的影响面也随之扩大
许可证Apache License 2.0允许商用与闭源使用，许可证不是约束因素
自托管栈PostgreSQL、Redis、API、控制台，以及承担80和443端口的OpenResty边缘五个组件就意味着要按五条支线考虑复原
Compose模式在装有Docker的Linux上以容器方式运行整栈Docker守护进程与磁盘成为共同的故障点
裸模式在macOS、Windows或没有Docker的Linux上以带内嵌数据库的单进程运行单进程更简单，代价是那个进程就是全部
提供形态桌面应用（控制平面在本地）、自托管服务器、Openship Cloud（托管）桌面应用被写为没有公网暴露，风险性质因此不同
备份计划执行，覆盖数据库与卷，一键恢复，随时导出功能存在与演练过恢复是两件不同的事实
成熟度核心可用于生产，正在积极开发需要与多节点集群仍在路线图上这一点一起读

没能核实的内容也明确写出来。官方仓库文档没有写明最低内存、CPU或磁盘等硬件要求。也没有找到最新发布版本的标注。因此本文不写规格数字。如果要评估引入，那个数值是应当用自己的负载直接测量的项目，而不是估算。构建尤其是瞬时内存使用会跳高的作业，与线上服务放在同一台服务器上运行时，最先出问题的资源就是内存和磁盘。

还有一点。仓库在路线图里把多节点集群、负载均衡界面、私有网络、高级监控、可视化CI/CD流水线列为即将到来的功能。路线图上的项目意味着现在还没有。如果你打算围绕跨多节点的部署和精细监控来做设计，就得把这些前提目前还在工具之外这一事实算进去。

2. 消失的成本与新产生的成本不是同一种货币

自托管的争论常常打转，主要是因为把两种成本放在同一个单位里比较。一种是每月以数字送来的账单，另一种是人的时间和事故风险。后者在平常日子里看起来是零，出事那天一次性结算。

维度会减少或消失的新出现的这一项显形的时刻
支出形态与用量挂钩的重复计费人的时间与待命负担平常看不见，事故当天才显形
绑定对平台专有约定的依赖对自己配置的依赖，即自造的绑定负责人更换或文档缺失时
上限构建次数、带宽这类计量上限物理资源上限：磁盘、内存、IOPS在构建集中的那个时点突然出现
安全部分公网暴露，例如管理控制台新的面：Webhook接收与构建执行出现公开仓库或外部贡献时
可用性被服务商故障牵连的风险自己这套栈的单点故障急需部署而部署系统正好宕机时
数据对外部存放位置的不确定性备份、恢复、保留策略的全部第一次尝试恢复的那一刻

这张表右侧那一列才是本文真正的主题。而右侧一列里有很多项目并不随规模而缩放。无论跑一个服务还是十个，操作系统补丁按同样的周期回来，证书续期也按同样的周期回来。所以在小规模下自托管很容易变成单位运维成本最差的形态。这个结构不是否定自托管的理由，而是必须计算从哪个规模开始才划得来的理由。

3. 新产生的运维项目 - 不会寄来账单的那一侧

下面是把部署平台放到自己服务器上之后，从那天起成为你的工作的清单。每一项都要同时定下「谁来做」和「怎么知道它失败了」才算完成。两者缺一，这一项就还不存在。

  • 操作系统与运行时补丁 — 容器运行时、数据库、边缘代理各有自己的安全更新节奏。开启自动更新就要接受无预告的重启，关掉就要接受积压的补丁。无论哪一种，定期查看这件事都留了下来。
  • 磁盘余量 — 部署系统会同时堆积镜像、构建缓存、日志和数据库。磁盘写满的那一刻，失败的不只是构建，数据库写入也会被堵住。下面会单独讲。
  • 备份与恢复演练 — 有备份功能和恢复真的能成功，是两件不同的事实。一次都没有还原过的备份，是你会在事故当天第一次执行的未验证流程。
  • 密钥管理 — 环境变量和部署密钥只放在平台里面，平台宕机时部署所需的值也一起被锁在里面。它们需要第二个存放处。
  • 证书续期与失败检测 — 配好自动续期，和知道续期失败了，是两件分开的工作。两者都有，这套机制才算完成。
  • 保护Webhook接收点 — 由外部请求触发构建，意味着那条路径就是执行开关。
  • 构建执行隔离 — 构建会执行仓库里的代码和依赖安装脚本。它以什么权限、在哪里运行，直接就是风险的大小。
  • 监控与夜间告警 — 进程死了却没人知道，是最常见的长期故障形态。需要一个从外部发起连接的检查。
  • 日志保留与轮转 — 没有日志就找不到原因，放任日志就会写满磁盘。保留期和轮转周期必须是数字，而不是打算。
  • 入侵响应流程 — 如果没有事先决定构建服务器被当成别人的工具时先切断什么，那一夜做出的判断通常是最糟的那个。
  • 变更历史 — 平台设置和服务定义记录在哪里。只在界面里改过的配置，在需要重建时等于不存在。
  • 引导恢复流程 — 这份清单上最常被遗漏的一项，也是下一节的主题。

如果你读完这份清单的反应是「大部分自动化就好了吧」，那只对了一半。自动化是可行的，但没有告诉你自动化失败了的机制，自动化只会放大风险，而不是降低它。这与静默失败的备份比完全没有备份更糟糕，是同一个道理。

4. 最常被遗漏的一项 - 部署工具自身的复原路径

这里是本文的核心。用托管平台时你根本不必想象部署系统宕机的场面。宕了，服务商去修。搬到自托管的那一刻，这个场面就变成真实存在的情景，而它与业务急需修复的时刻重合的概率并不低。磁盘写满导致构建失败，因此回滚和部署都做不了，就是最典型的形状。

按组件把「它停了会停掉什么」和「用什么把它救回来」预先拆开，这个情景的危险就小得多。以Openship仓库写明的自托管栈组件为基准整理，是这样的。

组件它停了会停掉什么复原手段要事先准备的东西
边缘代理（80和443）外部到达服务的全部路径自己起一个最小反向代理绕过去虚拟主机配置与证书文件副本的存放位置
平台API与控制台新部署与回滚的操作用运行时命令直接跑容器当前正在运行的镜像标签清单
元数据数据库服务定义、历史、配置的查阅从备份还原，或从代码重新生成定义把服务定义也留在仓库里
缓存层依赖队列或会话的流水线行为重启后重试，必要时清空缓存确认缓存丢失不等于数据丢失
容器运行时所有容器，也就是平台与业务同时恢复运行时后按重启策略自动起来为每个组件写明重启策略
主机磁盘构建、日志与数据库写入全都停清理后重启，或迁到另一台主机可用空间阈值告警与清理命令清单

最后一列才是真正需要准备的东西。而这些准备物大多只有放在平台之外才有意义。部署系统宕机时需要的信息只存在部署系统里面，那份信息等于没有。

重启策略尤其是细节决定结果。Docker官方文档定义了四种重启策略。no是不自动重启的默认值；on-failure在以非零退出码结束时重启，但文档写明它在守护进程重启时不会重启容器。always只要容器停止就总是重启，但被人手动停止的容器，只有在Docker守护进程重启时或被人手动再启动时才复活。unless-stopped与always类似，只是已停止的容器即使Docker守护进程重启也不会被重启。同一页建议使用重启策略，并避免用进程管理器去启动容器，还警告两者混用会产生冲突。它也说明重启策略只有在容器成功启动并保持运行至少十秒之后才生效。

这个差别为什么重要？因为正确答案取决于你期待为维护而特意停掉的容器在服务器重启后自动复活，还是期待它不要复活。部署平台的数据库和边缘属于重启后必须起来的一侧，为实验而留着的容器则不是。这个区分没有写成策略，一次重启就直接变成故障。

# 引导恢复手册里要写下的内容 - 所有值都是示例
# 1) 要救回的对象与最少信息
EDGE_HOST=192.0.2.1
APP_DOMAIN=example.com
CURRENT_IMAGE=<当前生产镜像标签>

# 2) 不依赖平台、只把服务直接起来的最小路径
docker run -d --restart unless-stopped \
  --name fallback-app -p 8080:8080 \
  --env-file /root-of-secrets/<服务名>.env \
  "$CURRENT_IMAGE"

# 3) 顶替边缘的最小代理规则（尖括号换成实际值）
#    https://<服务域名>/  =>  http://<内网地址>:8080
#
# 4) 把实际执行过这份流程的日期写在这里。
#    如果这里是空的，那它是愿望而不是计划。

引导恢复流程里最常见的遗漏是密钥。上面示例中--env-file指向的值如果只存在平台数据库里，你就无法生成那个文件，流程会停在第一行。所以密钥必须在部署平台之外再存一份。这不是便利性问题，而是引导恢复的前提条件。

5. 为每个组件写明重启策略

把上一节的原则落到配置上，最后归结为一个问题：策略有没有写在声明式文件里。在界面上点一次的设置在重建时会消失，写在文件里的策略会留下来。如果用Compose形态把栈起来，下面差不多就是最低线。Compose本身的用法在Docker Compose那一篇里单独讲过。

# 为部署平台的每个组件写明重启策略 - 值均为示例
services:
  api:
    image: <平台API镜像>
    restart: unless-stopped
  db:
    image: postgres:<版本>
    restart: unless-stopped
    volumes:
      - <数据卷>:/var/lib/postgresql/data
  cache:
    image: redis:<版本>
    restart: unless-stopped
  edge:
    image: <边缘镜像>
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - <证书卷>:/etc/letsencrypt

# 核对事项
# - 证书卷是否包含在主机备份范围内
# - db卷是否在备份范围内，还原是否演练过
# - 是否已决定被人手动停掉的容器该不该在重启后复活

还有一点。证书卷经常从备份清单里漏掉。数据库谁都会想到要备份，但证书和边缘配置很容易被一句「反正重新签发就好」带过去。可是在事故当天从头走一遍签发流程，是延长恢复时间最确定的办法。签发流程本身在免费SSL证书的签发与应用里按步骤讲过。

6. 构建缓存与磁盘 - 悄悄长大的故障原因

自托管部署系统上最常见的第一次事故不是入侵，而是磁盘。原因很简单。构建会留下缓存，而缓存的存在就是为了更快，所以它默认被设计成不会被删掉的方向。而如果同一台主机上还有数据库，磁盘写满的那一刻就不止于构建失败，还会扩散成写入失败。

Docker官方文档对构建缓存的清理写得很具体。除了BuildKit守护进程会在缓存体积过大或缓存寿命到期时清理构建缓存这一句，它还说明默认策略是按顺序评估的。策略有四条：容易重新生成的缓存若超过48小时未被使用则移除；超过60天未被用于构建的缓存移除；未被共享的缓存超出体积上限则移除；最后移除任何超出体积上限的构建缓存。对于Docker驱动，文档写明defaultKeepStorage默认为20GB。

BuildKit配置一侧的默认值也在同一页。reservedSpace为总磁盘的10%或10GB中的较小者；maxUsedSpace为总磁盘的60%或100GB中的较小者；minFreeSpace为20GB。文档还说明两个值同时设置时，一次垃圾回收之后缓存体积会落在这两个阈值之间。

这里在实务上要读出来的不是数字本身，而是基于比例的默认值在小磁盘上会怎样运作。允许缓存长到总磁盘60%的规则，在容量充裕时是合理的，但在业务与数据库共用一个卷的小服务器上，它同时意味着没有为其他进程要用的空间做预留。所以把部署平台放在与业务同一块磁盘上时，两件事里必须有一件：显式压低缓存上限，或者为构建单独分一个卷。

  • 先定下可用空间阈值 — 用多少GB而不是多少百分比来定更安全。百分比会随着磁盘变大而失去意义。
  • 把告警接到人身上 — 越过阈值这件事只显示在控制台上，那么在控制台打不开的场面里它毫无用处。
  • 事先定好清理命令 — 想在事故当天判断哪些可以删，最后一定会删掉不该删的那个。
  • 分离构建用的卷 — 让数据库与构建缓存不共用一个卷，是最可靠的防御。
  • 日志会造成同样的问题 — 不给容器日志和构建日志设保留期，有时日志会比缓存更早写满磁盘。
  • 镜像标签会堆积 — 每次部署都生成新标签，镜像占用就会线性增长。要定下保留多少代。
# 先看现在是什么在吃磁盘
docker system df -v | head -n 20

# 只看构建缓存，先清掉超过48小时未使用的部分
docker buildx du
docker builder prune --filter until=48h

# 在主机一侧从上层路径开始缩小范围
df -h /
du -xh --max-depth=1 /var/lib/docker 2>/dev/null | sort -h | tail -n 10

7. Webhook与构建执行造就的新攻击面

推送就自动部署的流程很方便，但再看一遍结构，它是由外部信号导致代码在你的服务器上执行的一条路径。把这句话照字面读一遍，为什么要谨慎就一目了然。

这个风险并非自托管部署平台独有，而是所有在自己基础设施上跑构建的配置共有的问题。GitHub官方文档对自托管运行器写下了明确的警告：我们建议只在私有仓库上使用自托管运行器，理由是你公开仓库的复刻可以通过创建一个在工作流中执行代码的拉取请求，在你的自托管运行器机器上运行危险代码。同样的逻辑适用于自建的构建系统。只要构建会执行仓库里的脚本，能把代码放进那个仓库的人，就是能在你服务器上执行命令的人。

  • 不要把公开仓库与自建构建混在一起 — 在自己服务器上跑一个接受外部贡献的仓库的构建，没有专门的隔离设计就是危险的。
  • 给每次构建一个干净的环境 — 上一次构建留下的文件影响下一次时，一次污染会一直传下去。
  • 把构建权限压到最小 — 构建以能看到整台主机的权限运行时，一个构建脚本就等同于主机权限。
  • 对Webhook要求签名校验 — 接收点开在公网上时，没有确认发送方是否为真的步骤，就不该触发流水线。
  • 把控制平面从公网暴露里拿出来 — 正如Openship仓库把桌面应用模式描述为控制平面在本地且没有公网暴露，在可行的情况下把管理界面放在公网之外，攻击面更小。
  • 核对漏洞上报通道 — 同一个仓库要求以非公开方式披露漏洞，而不是发在公开的issue或拉取请求里，并把安全公告指为首选通道。引入工具时这类流程是否齐备，值得当成成熟度信号来读。
  • 不要让密钥留在构建日志里 — 实时日志功能很方便，但能看到那些日志的人的范围，就成了密钥的暴露范围。
# 先数一下有什么对外开着
ss -ltnp | grep -E ':(80|443)\b'

# 确认构建以哪个用户权限运行
id
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}'

# 自己从公网地址敲一下管理界面看它是否响应
curl -sS -o /dev/null -w '%{http_code}\n' https://example.com/<管理路径>/

8. 证书与边缘 - 检测自动化失败的那一层

部署平台替你签发证书是很大的便利。不过那份便利是关于签发的，而在运维上出问题的是续期。Let's Encrypt官方FAQ写明默认证书有效期为90天，订阅者可以选择有效期六天的短期证书。续期建议是90天证书每60天续一次，六天证书每三天续一次。并且它明确断言没有办法调整这些有效期，也没有例外。同一份文档说明ACME客户端在随机时刻而不是固定时刻执行例行续期。

把这些事实搬进自托管的语境，结论只有一个：续期必须是自动的，而自动续期的失败必须触达到人。在托管平台上后半句归服务商，现在归你。而续期失败是静默发生的。失败那天什么都不会发生，几天后到期那天才以全面故障的形式浮现。

失败类型表面看到的症状为什么常被漏掉检测方法
续期任务根本没有跑直到到期日都没有任何症状只看成功日志，不核对它的缺席最近一次续期时间早于基准就当作失败
校验失败了只有日志里有错误，服务看起来正常告警只留在控制台里面把续期任务的退出码转发到外部告警
新证书没有被加载文件已更新但响应仍是旧证书边缘重载这一步没有单独核对从外部核对实际提供的证书到期日
证书卷不在备份里恢复之后偏偏只有证书不见了只把数据库当成备份对象把证书核对列入恢复演练项目
与域名变更错开了只有部分主机出现证书错误虚拟主机清单与证书清单分开管理以服务域名清单为基准做一次全量核查
 
# 从外部核对实际正在提供的证书
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates

# 顺便看边缘是否活着、附上了哪些响应头
curl -sI https://example.com/ | head -n 12

# 一次扫过多个域名 - 清单从服务定义里取

#

9. 可以做的条件，与该停手的信号

「这是个好工具吗」是很难回答的问题，「我们现在担得起吗」是可以回答的问题。下面的条件不是关于工具的质量，而是关于组织的准备程度。

  • 可接受的中断时间已经定下来 — 应当能用分钟回答。没有这个数字，恢复设计也没有基准。
  • 有夜间与周末的响应通道 — 告警打到谁的手机上，那个人连不上时下一个是谁，必须已经定下来。
  • 至少有两个人能操作 — 只有一个人时，那个人的休假与离职就直接成为可用性风险。
  • 确实从备份里恢复过一次 — 应当能指出一个日期。「功能是有的」不是答案。
  • 引导恢复流程执行过 — 不依赖平台把服务起来的路径至少走过一次。
  • 构建不会与业务抢资源 — 是否放在同一台主机、卷是否分开，必须在设计阶段就定下来。
  • 配置以文件形式存在 — 只靠界面点击维持的配置，是无法重建的配置。

反过来，如果出现下面这些信号，答案是现在不行。它们不靠换工具来解决，而要靠改变准备程度来解决。

  • 运维人员只有一个 — 部署系统宕机那天这个人联系不上，就没有替代方案。
  • 备份恢复一次都没有演练过 — 在这种状态下自托管，实质上等同于没有备份。
  • 没有让夜间故障被察觉的通道 — 早上才知道的故障，就是整夜持续着的故障。
  • 没有人盯着磁盘余量 — 如前所述，第一次事故大多从这里来。
  • 打算在自己服务器上跑公开仓库的构建 — 没有隔离设计就应当避开这个组合。
  • 密钥只存在平台里面 — 引导恢复在结构上就是不可能的。
  • 引入的理由只有降本一条 — 省下的金额小于运维时间的价值，这笔账本来就已经算不平。

这里有一个误解需要澄清。本文并不是说自托管很贵，而是说划得来的那个点取决于规模与准备程度。在另一类负载上推算自托管成本结构的案例在自托管AI工作区那一篇里讲过，那里结论的形状也是一样的：真实成本来自资源与人的时间，而不是来自价目表。

10. 迁移成本 - 离开时有什么被绑住了

评估引入时几乎没人计算的一项是离开的成本。而这份成本不会仅因为它是开源就变成零。许可证宽松与迁移容易，是两件不同的事。

被绑住的地方为什么会难以搬走如何提前减少
构建配置平台自动检测出的规则变成没有文档的规格把构建命令与产物定义写在仓库内的文件里
密钥值只在平台存储里，连清单都无法复现把键名清单与值的存放位置在平台之外做双份
域名与证书签发与续期的自动化被绑在边缘上签发保持标准ACME，切换前把缓存时间降下来
数据导出格式与重新装载的时间就是停机时间把标准格式导出与还原演练做成周期性工作
服务定义只在控制台里创建的配置在代码中并不存在用声明式文件管理服务、端口、卷与环境
镜像存放位置镜像只存在平台内部的存储里同时推送到一个标准镜像仓库

从这张表能看出一条规则：绑定来自设计，而不是来自合同。便利功能用得越多，那些便利替你做掉的决定就越多地从文档里消失，而离开时这些决定要由人重新做一遍。所以自动检测这类功能，可以用，但要把结果钉进文件里更安全。产物是标准容器镜像确实是有利条件，但如果只有镜像而没有它当初是怎么被运行起来的记录，迁移仍然会变成重写。

也有把数据库备份与恢复作为单独主题的文章。在自托管环境下如何设计备份对象、周期和还原演练，可以对照自托管数据库备份一起读。

11. 判断表 - 从情况到选择

把上面所有内容压缩成一张表。在左边找到最接近自己情况的那一行，连右边的先核对什么一起读，这才是这张表的用法。这里没有哪一边更优的判定。

情况可以倾向的方向先核对什么
文档、博客这类没有服务端逻辑的站点静态托管是否真的没有必须在服务器上运行的代码
一个人做的副业项目，没有夜间值守托管型能否用数字说出可接受的中断时间
运维1人，没有备份恢复经验托管型先演练一次恢复，然后重新判断
服务数量增加、部署频率变高托管型或自托管构建是否能不侵占业务资源
数据所在位置必须在自己掌控之下自托管备份位置、保留期限与恢复时间目标
已经在运维服务器并有值班轮换自托管引导恢复流程是否真的执行过
在公开仓库上接受外部贡献托管型，或隔离的构建复刻的代码是否会在你的主机上执行
服务等级高，停机就是直接损失自托管须以冗余为前提单节点配置是否是可接受的风险
只想要部署自动化，不想做服务器运维托管CI加托管运行环境两个系统之间传递密钥的路径
部署只在内网使用的工具自托管控制平面能否从公网暴露里拿出来
引入的唯一理由是降本暂缓决定把省下的金额与运维时间的价值写在同一张表上比较

再看一遍表里建议「自托管」的那些行，会发现共同点：要么是本来就在运维服务器的组织，要么是有用钱买不到的要求，比如数据所在位置。而建议「托管型」的那些行共同点是另一个：人的时间与响应体系不足。决定结论的是这个条件，而不是工具的质量。

结论：自托管不是节省，而是交换

把部署平台放到自己服务器上并不是坏决定。只是这个决定应当在清楚用什么换了什么的前提下做出。

  • 消失的是使用费与厂商绑定 — 围着计量上限做设计的必要性减少了，产物若是标准容器，可移动性也还留着。
  • 新出现的是运维责任 — 补丁、磁盘、备份与恢复演练、证书续期失败的检测、Webhook与构建执行的隔离、入侵响应，作为一整束一起到来。
  • 最常被遗漏的一项是引导恢复 — 对部署系统宕机时用什么把它救回来没有答案，为便利而引入的工具就会变成单点故障。
  • 判断标准是准备程度，而不是工具 — 可接受的中断时间、值班体系、恢复演练的经验，这三样决定答案。

最后再写一遍态度。无条件推荐自托管的文章，和一味说它危险来吓人的文章，都帮不上忙。需要的是把每个选择附带的项目一个不漏地数出来。所以本文不写金额，像硬件要求这样在官方文档里无法核实的数字一概不用，而写了数字的地方都留下了依据文档。那些文档会变。决定引入的那一天，除了自己重新打开它们，没有更安全的办法。
