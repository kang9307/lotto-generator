공백만 바뀐 diff를 걸러내는 법 - 진짜 변경이 묻히지 않게

-w 와 -b 는 무엇이 다른가, 그리고 포맷팅 커밋을 blame 에서 통째로 빼는 방법

2026-09-01 개발/인프라

리뷰 요청이 하나 올라온다. 변경 파일 세 개, 51줄 추가에 51줄 삭제. 열어 보면 들여쓰기가 탭에서 스페이스로 바뀌어 있고, 줄 끝 공백이 정리돼 있고, 그 사이 어딘가에 옵션 하나가 추가돼 있다. 리뷰어가 해야 할 일은 그 한 곳을 찾는 것인데, 화면에는 나머지 100줄이 똑같은 초록색과 빨간색으로 같이 올라와 있다.

이 상황에서 사람이 하는 일은 대개 둘 중 하나다. 스크롤을 내리면서 눈으로 훑다가 놓치거나, 아예 승인 버튼을 그냥 누르거나. 둘 다 리뷰가 아니다. 그리고 이건 리뷰어의 성실함 문제가 아니라 입력 신호 대 잡음비가 1 대 50 인 화면을 사람에게 준 쪽의 문제다.

다행히 이 문제는 도구로 거의 끝까지 해결된다. git 은 공백 차이를 무시하고 diff 를 다시 계산할 수 있고, 포맷팅 커밋 하나를 이력 추적에서 통째로 빼는 기능도 갖고 있다. 이 글은 그 기능들을 임시 저장소를 만들어 실제로 돌린 출력으로 정리한 것이다.

이 글의 모든 명령과 출력은 아래 §2 에 적은 환경에서 임시 저장소를 새로 만들어 직접 실행한 결과다. 붙인 출력은 실제로 나온 것이고, 실행하지 못한 항목은 §20 에 따로 모았다. 예제 경로는 전부 임의의 이름이다.

한 줄이 100줄에 묻히는 구조

공백 잡음은 대개 사람이 일부러 만들지 않는다. 저장할 때마다 자동으로 도는 포맷터, 팀원마다 다른 편집기 탭 폭 설정, 저장 시 줄 끝 공백을 떼는 옵션을 켠 사람과 켜지 않은 사람. 이 셋만 있으면 파일을 열었다 닫기만 해도 전체가 변경 대상이 된다.

문제는 그 다음이다. diff 는 줄 단위로 비교하므로, 줄에서 눈에 보이지 않는 바이트 하나가 바뀌어도 그 줄은 삭제와 추가 한 쌍으로 표시된다. 40줄짜리 함수의 들여쓰기를 바꾸면 삭제 40줄에 추가 40줄, 즉 80줄이 화면을 채운다. 그 안에 진짜 수정이 한 줄 들어 있어도 시각적으로 다른 79줄과 구별되지 않는다.

여기서 자주 나오는 대응이 두 가지 있는데 둘 다 부분적으로만 맞다. 첫째는 포맷터를 쓰지 말자는 것이다. 이건 포맷터가 없애 주는 다른 종류의 리뷰 낭비를 되살린다. 둘째는 리뷰어가 더 꼼꼼히 보자는 것이다. 이건 도구로 해결되는 문제를 사람의 집중력으로 갚으라는 요구라 오래 가지 않는다. 실제로 쓸 만한 답은 셋째다. 화면에 올릴 때 공백 차이를 계산에서 빼는 것.

실행 환경과 실험 방법

아래 출력은 전부 다음 환경에서 나온 것이다. 옵션 동작은 git 버전에 따라 세부가 달라질 수 있으므로 버전을 같이 적어 둔다.

$ git --version
git version 2.48.1.windows.1

$ diff --version | head -1
diff (GNU diffutils) 3.10

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -s -r -o
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64 Msys

# 실험은 전부 빈 임시 저장소에서 한다
$ mkdir /tmp/demo && cd /tmp/demo
$ git init -q .
$ git config user.name  Demo
$ git config user.email demo@example.com
$ git config core.autocrlf false   # 줄바꿈 변환이 실험을 오염시키지 않게

마지막 줄이 중요하다. Windows 에서 core.autocrlf 가 켜져 있으면 git 이 저장소에 넣고 꺼낼 때 줄바꿈을 바꾸므로, 줄바꿈 관련 실험 결과가 설정에 따라 달라진다. 실험 저장소에서는 이 값을 꺼 두고 시작한다.

공백 변경에는 다섯 종류가 있다

공백 변경을 하나로 묶어서 다루면 옵션 선택을 못 한다. git 의 무시 옵션들이 서로 다른 것을 무시하기 때문이다. 실무에서 마주치는 종류는 다섯 가지고, 각각 만들어지는 경로도 다르다.

종류어떻게 생기나눈에 보이나diff 에 미치는 영향
줄 끝 공백편집 중 남은 스페이스·탭. 저장 시 정리 옵션을 켠 사람이 파일을 열면 한꺼번에 사라진다보이지 않음해당 줄 전부가 변경으로 표시된다
들여쓰기 변환탭 ↔ 스페이스. 포맷터나 편집기 설정 차이거의 보이지 않음들여쓴 줄 전부가 변경으로 표시된다
줄 안쪽 공백 양정렬을 맞추려고 등호 주변 등에 공백을 늘리거나 줄임보임해당 줄이 변경으로 표시된다
빈 줄 증감포맷터의 빈 줄 개수 규칙. 사람이 문단을 나누는 습관보임추가·삭제 줄이 생기고 hunk 범위가 넓어진다
파일 끝 개행마지막 줄을 개행 없이 저장하는 도구보이지 않음마지막 줄이 삭제 후 추가로 표시된다

여섯 번째로 줄바꿈 문자 자체가 있다. CRLF 와 LF 는 성격이 조금 달라서 §13 에서 따로 본다. 눈에 보이지 않는 바이트가 파일을 오염시키는 또 다른 사례로는 파일 앞에 붙는 BOM 3바이트가 있는데, 이쪽은 diff 보다 실행 자체를 깨뜨린다.

한 파일에 다섯 종류를 다 넣어 본다

옵션을 설명하기 전에 비교 대상을 하나 만든다. 여섯 줄짜리 설정 파일에 위의 다섯 종류를 전부 넣고, 그 안에 진짜 변경 하나를 섞어 둔다. 진짜 변경은 timeout 값이 30 에서 60 으로 바뀐 것 하나뿐이다. 나머지는 전부 공백이다.

$ cat -A app.conf          # 커밋해 둔 원본. ^I 가 탭, $ 가 줄 끝
server {$
^Ilisten 8080;$
^Iretries = 3;$
^Itimeout = 30;$
log_level = info;$
}$

$ cat -A app.conf          # 편집한 뒤
server {   $               <- 줄 끝 공백 3칸
    listen 8080;$          <- 탭이 스페이스 4칸으로
^Iretries  =  3;$          <- 줄 안쪽 공백 양 변경
^Itimeout = 60;$           <- 진짜 변경 (30 -> 60)
$                          <- 빈 줄 추가
    log_level = info;$     <- 없던 들여쓰기가 생김
}                          <- 파일 끝 개행 제거 ($ 가 없다)

이 상태에서 아무 옵션 없이 git diff 를 돌리면 이렇게 나온다. 여섯 줄짜리 파일이 여섯 줄 삭제, 일곱 줄 추가가 된다. 바뀐 것은 사실상 숫자 하나인데 파일 전체가 갈린다.

$ git diff
diff --git a/app.conf b/app.conf
index bd81bfd..d0ea0b8 100644
--- a/app.conf
+++ b/app.conf
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
-}
+server {
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
+}
\ No newline at end of file

여기서 리뷰어가 timeout 줄을 찾아내려면 열두 줄을 눈으로 대조해야 한다. 여섯 줄짜리 파일이라 가능한 일이고, 400줄짜리 파일이면 불가능하다.

무시 옵션을 하나씩 걸어 본다

이제 같은 파일에 옵션을 하나씩 건다. 세 개를 차례로 보면 각 옵션이 정확히 무엇까지 삼키는지가 드러난다.

$ git diff --ignore-space-at-eol      # 줄 끝 공백만 무시
@@ -1,6 +1,7 @@
 server {                             <- 문맥 줄로 내려갔다
-	listen 8080;
-	retries = 3;
-	timeout = 30;
-log_level = info;
+    listen 8080;
+	retries  =  3;
+	timeout = 60;
+
+    log_level = info;
 }
\ No newline at end of file

$ git diff -b                         # --ignore-space-change
@@ -1,6 +1,7 @@
 server {
     listen 8080;                     <- 탭 -> 스페이스도 삼켰다
 	retries  =  3;                   <- 줄 안쪽 공백 양도 삼켰다
-	timeout = 30;
-log_level = info;
+	timeout = 60;
+
+    log_level = info;                <- 없던 들여쓰기는 남는다
 }
\ No newline at end of file

$ git diff -w                         # --ignore-all-space
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;                    <- 남은 것은 진짜 변경과
+
     log_level = info;                <- 추가된 빈 줄뿐
 }
\ No newline at end of file

세 출력을 나란히 놓으면 -b 와 -w 의 차이가 딱 한 줄에서 갈리는 것이 보인다. log_level = info; 는 원래 들여쓰기가 없던 줄인데 스페이스 네 칸이 생겼다. -b 는 공백이 하나 이상 있는 구간끼리를 같다고 보므로 0 개와 4 개는 같지 않다. -w 는 공백을 아예 없는 셈 치므로 이것도 삼킨다.

  • --ignore-space-at-eol 은 줄 끝만 본다. 들여쓰기 변환은 그대로 남으므로 포맷터 잡음에는 힘이 약하다
  • -b 는 줄 끝 공백까지 포함해서 무시한다. 즉 --ignore-space-at-eol 의 상위 집합이다
  • -w 는 -b 의 상위 집합이다. 셋은 포함 관계로 정리된다
  • 어느 옵션도 빈 줄 추가는 지우지 못한다. 빈 줄은 별도 옵션 담당이고, 그것도 조건이 붙는다
  • 주목할 점 하나 더. --ignore-space-at-eol 을 걸자 마지막 } 줄이 문맥 줄로 내려갔다. 파일 끝 개행 유무도 줄 끝 공백으로 취급된다는 뜻이다

네 옵션의 차이를 표로

위 실행 결과를 그대로 표로 옮기면 이렇게 된다. 세로축은 §3 의 다섯 종류이고, 표시는 그 옵션이 그 변경을 diff 에서 지워 주는가이다.

변경 종류옵션 없음--ignore-space-at-eol-b
(--ignore-space-change)		-w
(--ignore-all-space)		--ignore-blank-lines
줄 끝 공백보임지움지움지움보임
탭 ↔ 스페이스 들여쓰기보임보임지움지움보임
줄 안쪽 공백 양보임보임지움지움보임
없던 들여쓰기가 생김보임보임보임지움보임
파일 끝 개행 제거보임지움지움지움보임
빈 줄 증감 (단독 hunk)보임보임보임보임지움
빈 줄 증감 (다른 변경과 같은 hunk)보임보임보임보임보임

표에서 굵게 둔 두 칸이 실무에서 사람을 헷갈리게 하는 자리다. 하나는 -b 가 새로 생긴 들여쓰기를 못 지운다는 것이고, 다른 하나는 --ignore-blank-lines 가 조건부로만 동작한다는 것이다. 두 번째를 따로 본다.

--ignore-blank-lines 는 hunk 단위로 판단한다

§5 의 마지막 출력에서 -w 를 걸었는데도 추가된 빈 줄이 남아 있었다. 그러면 --ignore-blank-lines 를 같이 걸면 되겠다고 생각하기 쉬운데, 실제로 걸어 보면 그렇지 않다.

$ git diff --ignore-blank-lines       # §4 의 그 파일에 단독으로
@@ -1,6 +1,7 @@
-server {
-	listen 8080;
...                                   # 아무것도 줄어들지 않았다

$ git diff -w --ignore-blank-lines    # -w 와 같이 걸어도
@@ -1,6 +1,7 @@
 server {
     listen 8080;
 	retries  =  3;
-	timeout = 30;
+	timeout = 60;
+                                     <- 빈 줄이 그대로 남아 있다
     log_level = info;
 }

# 그런데 빈 줄만 바뀐 파일에서는 완전히 동작한다
$ git diff blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta

$ git diff --ignore-blank-lines blanks.txt
                                      # 출력 없음. 전부 억제됐다

$ git diff -w blanks.txt
@@ -1,4 +1,7 @@
 alpha
+
 beta
+
+
 gamma
 delta                                # -w 는 빈 줄을 지우지 못한다

동작 규칙은 이렇다. --ignore-blank-lines 은 줄 단위가 아니라 hunk 단위로 판단한다. 어떤 hunk 의 변경이 전부 빈 줄이면 그 hunk 를 통째로 버리고, 하나라도 내용 있는 변경이 섞여 있으면 hunk 전체를 그대로 낸다. 그래서 빈 줄 정리만 한 커밋에서는 완벽하게 동작하고, 빈 줄과 로직이 같은 자리에서 바뀐 커밋에서는 아무 효과가 없다.

  • 포맷터가 빈 줄 규칙만 손댄 커밋을 리뷰할 때 --ignore-blank-lines 는 가장 강력하다. 그 외에는 기대치를 낮춰야 한다
  • -w 와 --ignore-blank-lines 는 담당 영역이 겹치지 않으므로 둘을 같이 거는 것이 기본이라고 봐도 된다
  • 이 hunk 단위 규칙은 GNU diff 의 -B 도 동일하다. §16 에서 같은 현상을 확인한다

이 변경이 대부분 포맷팅인지 숫자로 판정하기

리뷰를 시작하기 전에 알고 싶은 것은 대개 하나다. 이 변경 안에 진짜 변경이 몇 줄이나 있는가. 이건 눈으로 셀 필요 없이 두 줄로 나온다. 통계 옵션들이 -w 를 그대로 존중하기 때문이다.

# 파일 3개: a.js 는 순수 재포맷, b.js 는 재포맷 + 진짜 변경 1줄, c.js 는 진짜 변경만
$ git diff --shortstat
 3 files changed, 51 insertions(+), 51 deletions(-)

$ git diff -w --shortstat
 2 files changed, 2 insertions(+), 2 deletions(-)

# 파일별로 보고 싶으면
$ git diff --numstat
30	30	a.js
20	20	b.js
1	1	c.js

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # a.js 가 목록에서 사라졌다

$ git diff -w --stat
 b.js | 2 +-
 c.js | 2 +-
 2 files changed, 2 insertions(+), 2 deletions(-)

51줄 대 2줄. 이 비율 하나만 봐도 그 변경을 어떻게 대해야 하는지가 정해진다. 그런데 여기서 한 가지 함정이 있다. --name-only 는 -w 를 무시한다. 파일 목록만 뽑아 자동화에 쓰려던 사람이 걸리는 자리다.

$ git diff -w --name-only
a.js
b.js
c.js                                  # a.js 는 공백만 바뀌었는데도 나온다

$ git diff -w --numstat
1	1	b.js
1	1	c.js                          # 이쪽은 정확하다

# 파일별로 확실히 분류하려면 종료 코드를 쓴다
$ git diff --quiet -w -- a.js; echo $?
0                                     # 0 = 공백 말고는 바뀐 것이 없다
$ git diff --quiet    -- a.js; echo $?
1                                     # 1 = 바이트는 바뀌었다
$ git diff --quiet -w -- c.js; echo $?
1                                     # 진짜 변경이 있다

$ for f in $(git diff --name-only); do
>   if git diff --quiet -w -- "$f"; then echo "  공백만 : $f"; else echo "  진짜   : $f"; fi
> done
  공백만 : a.js
  진짜   : b.js
  진짜   : c.js

--quiet 와 -w 를 조합한 마지막 형태가 실무에서 가장 쓸모 있다. 종료 코드로 답이 나오므로 훅이나 CI 안에서 공백만 바뀐 파일을 자동으로 걸러낼 수 있다. 파일 목록이 필요하면 git diff -w --numstat 의 세 번째 칸을 쓰면 된다.

git blame -w - 포맷터가 이력을 삼킬 때

공백 변경이 남기는 두 번째 피해는 diff 가 아니라 blame 이다. 어떤 줄이 왜 이렇게 됐는지 추적하려고 blame 을 돌렸는데 모든 줄이 반년 전 포맷터 커밋을 가리키면 그 이력은 사실상 지워진 것과 같다.

확인하기 위해 커밋 세 개짜리 저장소를 만든다. Alice 가 로직을 쓰고, Bob 이 포맷터를 돌리고, Carol 이 진짜 버그를 고친다. Bob 의 커밋은 탭을 스페이스 넷으로 바꾸고 작은따옴표를 큰따옴표로 바꾼 것뿐이다. 동작은 하나도 바뀌지 않았다.

$ git log --oneline
db3b770 fix: include zero total          <- Carol
007e2a5 style: run formatter over the repo   <- Bob
5c720df feat: aggregate rows             <- Alice

$ git blame --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
007e2a59 (Bob   2026-02-02 2)     total = 0
007e2a59 (Bob   2026-02-02 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# 일곱 줄 중 다섯 줄이 Bob 것이 됐다. Bob 은 로직을 한 글자도 안 건드렸다.

$ git blame -w --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
007e2a59 (Bob   2026-02-02 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
007e2a59 (Bob   2026-02-02 6)         return {"total": total}
007e2a59 (Bob   2026-02-02 7)     return {"total": 0}

# 세 줄은 Alice 에게 돌아왔지만, 따옴표가 바뀐 세 줄은 여전히 Bob 이다.

-w 의 한계가 여기서 정확히 드러난다. -w 는 공백만 무시한다. 들여쓰기만 바뀐 줄은 되살렸지만, 같은 커밋 안에서 따옴표 문자가 바뀐 줄은 공백 변경이 아니므로 그대로 Bob 에게 남는다. 그런데 현실의 포맷터는 거의 항상 공백과 공백 아닌 것을 같이 바꾼다. 따옴표 스타일, 줄 나누기 위치, 후행 쉼표, 괄호 정렬이 다 그렇다.

즉 -w 로는 포맷터 커밋을 못 지운다. 절반만 지워진 blame 은 어떤 면에서 더 나쁘다. 일부 줄이 되살아났으니 다 됐다고 착각하게 만들기 때문이다. 제대로 된 답은 다른 데 있다.

.git-blame-ignore-revs - 커밋을 blame 에서 빼기

git 은 특정 커밋을 blame 계산에서 통째로 건너뛰는 기능을 갖고 있다. 건너뛴 커밋이 만든 줄은 그 이전 커밋 쪽으로 책임이 넘어간다. 관례상 저장소 루트에 .git-blame-ignore-revs 라는 파일을 두고 거기에 건너뛸 커밋의 SHA 를 적는다.

$ cat .git-blame-ignore-revs
# 2026-02-02 저장소 전체 포맷터 실행 (탭 -> 스페이스 4칸, 따옴표 스타일)
# 동작 변경 없음. blame 에서는 건너뛴다
007e2a5974bd7a4c76aba4ee206b690c1410c23d

# 방법 1. 한 번만 쓰기 - 파일 경로를 직접 준다
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df (Alice 2026-01-10 1) def load(rows):
^5c720df (Alice 2026-01-10 2)     total = 0
^5c720df (Alice 2026-01-10 3)     for r in rows:
^5c720df (Alice 2026-01-10 4)         total += r["amount"]
db3b770e (Carol 2026-03-05 5)     if total >= 0:
^5c720df (Alice 2026-01-10 6)         return {"total": total}
^5c720df (Alice 2026-01-10 7)     return {"total": 0}

# 방법 2. 계속 쓰기 - 설정에 박아 둔다
$ git config blame.ignoreRevsFile .git-blame-ignore-revs
$ git blame --date=short report.py
                                      # 위와 완전히 같은 출력

# 방법 3. 파일 없이 커밋 하나만
$ git blame --ignore-rev 007e2a5974bd7a4c76aba4ee206b690c1410c23d --date=short report.py
                                      # 역시 같은 출력

-w 로는 세 줄이 Bob 에게 남았는데, 이번에는 일곱 줄 전부가 제자리를 찾았다. Alice 가 여섯 줄, Carol 이 실제로 고친 한 줄. 이것이 이 파일의 진짜 이력이다.

비교 항목git blame -w.git-blame-ignore-revs
무시하는 대상공백 차이지정한 커밋 전체
따옴표·줄바꿈 위치 변경못 지운다지운다
설정 없이 즉시 사용가능--ignore-rev 로 가능
팀 전체에 공유각자 옵션을 붙여야 한다파일이 저장소에 같이 커밋된다
대상 커밋을 사람이 골라야 하나아니오예. SHA 를 직접 적는다
실수했을 때영향 없음진짜 변경이 든 커밋을 넣으면 이력이 왜곡된다

파일이 저장소에 같이 커밋된다는 점이 실무에서 가장 크다. 한 사람이 SHA 를 추가하면 팀 전체의 blame 이 같이 고쳐진다. GitHub 은 2022년 3월 24일 변경 로그에서 저장소 루트의 .git-blame-ignore-revs 를 blame 화면에서 인식한다고 밝혔다. 즉 이 파일 하나로 로컬 CLI 와 웹 화면이 같이 정리된다.

ignore-revs 를 쓸 때 걸리는 것들

기능 자체는 단순한데 처음 쓸 때 걸리는 지점이 몇 개 있다. 전부 실제로 재현해서 확인한 것이다.

# 1. SHA 는 반드시 40자 전체여야 한다
$ git rev-parse --short HEAD~1
007e2a5
$ echo 007e2a5 > short-revs
$ git blame --ignore-revs-file=short-revs report.py
fatal: invalid object name: 007e2a5
                                      # 짧은 해시는 blame 자체를 실패시킨다

# 2. 건너뛴 줄에 표시를 남길 수 있다
$ git config blame.markIgnoredLines   true
$ git config blame.markUnblamableLines true
$ git blame --ignore-revs-file=.git-blame-ignore-revs --date=short report.py
^5c720df  (Alice 2026-01-10 1) def load(rows):
^?5c720d  (Alice 2026-01-10 2)     total = 0
^?5c720d  (Alice 2026-01-10 3)     for r in rows:
^?5c720d  (Alice 2026-01-10 4)         total += r["amount"]
db3b770e  (Carol 2026-03-05 5)     if total >= 0:
^?5c720d  (Alice 2026-01-10 6)         return {"total": total}
^?5c720d  (Alice 2026-01-10 7)     return {"total": 0}
                                      # 물음표가 붙은 줄 = 무시된 커밋을 거쳐 추정된 줄

# 3. 어떤 커밋을 넣을지 판단하는 법
$ git show --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 12 ++++++------
 1 file changed, 6 insertions(+), 6 deletions(-)

$ git show -w --stat --oneline 007e2a5
007e2a5 style: run formatter over the repo
 report.py | 6 +++---
 1 file changed, 3 insertions(+), 3 deletions(-)
                                      # -w 로 절반이 사라지면 공백 비중이 큰 커밋이다

첫 번째가 가장 자주 걸린다. 커밋 SHA 를 붙여넣을 때 습관적으로 짧은 해시를 쓰면 blame 이 아예 안 돈다. git rev-parse HEAD 로 전체 SHA 를 뽑아 넣는 것이 안전하다.

  • 주석은 # 으로 시작하는 줄에 쓴다. 그 커밋이 왜 목록에 있는지 적어 두지 않으면 몇 달 뒤 아무도 손대지 못한다
  • 넣기 전에 그 커밋이 정말 포맷팅뿐인지 확인한다. 위 3번의 git show -w --stat 이 그 판정에 쓰인다. -w 를 걸었는데도 줄 수가 그대로면 그 커밋에는 진짜 변경이 들어 있다
  • 진짜 변경이 섞인 커밋을 목록에 넣으면 그 변경의 책임자가 영영 감춰진다. 이건 blame 오염보다 나쁘다
  • blame.markIgnoredLines 를 켜 두면 어느 줄이 추정값인지 눈에 보인다. 팀에 이 파일을 처음 도입할 때 켜 두면 설명이 쉬워진다
  • 이 파일은 blame 만 바꾼다. git log 나 git diff 는 영향을 받지 않으므로 이력이 사라지는 것이 아니다

파일 끝 개행과 No newline at end of file

§4 의 출력 마지막 줄에 \ No newline at end of file 이 있었다. 이 표시는 파일의 마지막 바이트가 개행이 아니라는 뜻이다. 오류가 아니라 사실 서술이다.

이 표시가 존재하는 이유는 텍스트 파일의 정의에 있다. POSIX 는 줄을 개행 문자로 끝나는 0개 이상의 문자열로 정의하고, 텍스트 파일을 그런 줄들의 나열로 정의한다. 이 정의를 따르면 개행 없이 끝난 마지막 조각은 엄밀히 말해 줄이 아니다. 그래서 wc -l 이 한 줄 적게 세거나, 파일 두 개를 이어 붙였을 때 마지막 줄과 첫 줄이 한 줄로 붙어 버리는 일이 생긴다.

$ git show HEAD:eof.txt | tail -c 12 | xxd
00000000: 650a 7477 6f0a 7468 7265 650a            e.two.three.
$ tail -c 12 eof.txt | xxd
00000000: 6e65 0a74 776f 0a74 6872 6565            ne.two.three
                                      # 끝의 0a 하나가 사라졌다. 그것뿐이다

$ git diff
@@ -1,3 +1,3 @@
 one
 two
-three
+three
\ No newline at end of file
                                      # 같아 보이는 줄이 삭제 후 추가로 표시된다

$ git diff --ignore-space-at-eol; echo "종료 코드 $?"
종료 코드 0                            # 완전히 감춰진다
$ git diff -w
                                      # -w 도 마찬가지로 출력 없음
$ git diff --check; echo "종료 코드 $?"
종료 코드 0                            # --check 는 이것을 오류로 보지 않는다

마지막 두 줄이 중요하다. git diff --check 는 줄 끝 공백은 잡지만 파일 끝 개행 누락은 잡지 않는다. 그래서 커밋 훅에 --check 만 걸어 두고 이것까지 막힌다고 생각하면 안 된다. 이쪽은 편집기 설정으로 막는 것이 맞다.

줄바꿈 문자가 diff 전체를 뒤집는다

줄바꿈 문자가 CRLF 와 LF 사이에서 바뀌면 파일의 모든 줄이 변경된다. 눈에 보이지 않는 바이트가 줄마다 하나씩 붙거나 빠지기 때문이다. CRLF 와 LF 자체가 왜 갈라졌고 .gitattributes 로 어떻게 고정하는지는 줄바꿈 문자를 다룬 글에서 따로 정리했다. 여기서는 그것이 diff 를 어떻게 오염시키는지만 본다.

$ cat -A notes.txt                    # 파일 전체를 CRLF 로 바꾸고 한 단어만 수정
line one^M$
line two^M$
line THREE^M$                         <- 진짜 변경은 여기 하나
line four^M$

$ git diff --stat
 notes.txt | 8 ++++----
 1 file changed, 4 insertions(+), 4 deletions(-)
                                      # 네 줄짜리 파일이 통째로 바뀐 것으로 잡힌다

$ git diff
@@ -1,4 +1,4 @@
-line one
-line two
-line three
-line four
+line one
+line two
+line THREE
+line four
                                      # 어느 줄이 진짜인지 화면상 구별되지 않는다

$ git diff --ignore-cr-at-eol
@@ -1,4 +1,4 @@
 line one
 line two
-line three
+line THREE
 line four                            # 한 줄로 줄어든다

$ git diff -w
                                      # -w 도 같은 결과. CR 도 공백 문자라서다
  • git 에는 이 경우만 위한 --ignore-cr-at-eol 이 따로 있다. -w 보다 범위가 좁아 안전하다
  • GNU diff 쪽에는 같은 목적의 --strip-trailing-cr 이 있다. §16 에서 확인한다
  • 근본 대책은 .gitattributes 로 저장소의 줄바꿈을 못박는 것이다. 옵션은 증상 완화지 해결이 아니다

애초에 생기지 않게 막기

여기까지는 이미 생긴 잡음을 화면에서 지우는 방법이었다. 더 나은 쪽은 잡음이 커밋에 들어가지 않게 하는 것이다. 층이 셋 있고, 각각 막는 지점이 다르다.

첫 번째 층은 편집기다. 저장소 루트에 .editorconfig 를 두면 지원하는 편집기들이 저장 시점에 정리해 준다. 편집기마다 지원 범위가 다르므로 이건 규약이지 강제가 아니다.

$ cat .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
indent_style = space
indent_size = 4
trim_trailing_whitespace = true       # 줄 끝 공백 제거
insert_final_newline = true           # 파일 끝 개행 보장

[Makefile]
indent_style = tab                    # 여기는 탭이 문법이다

[*.md]
trim_trailing_whitespace = false      # 줄 끝 두 칸이 줄바꿈을 뜻한다

두 번째 층은 커밋 직전 검사다. git diff --check 는 별도 설정 없이 동작하고, 문제를 찾으면 종료 코드 2 로 끝나므로 훅이나 CI 에 그대로 넣을 수 있다.

$ cat -A ws.txt
ok line$
trailing spaces here   $
trailing tab here^I$
 ^Ispace before tab$
$
$

$ git diff --check
ws.txt:2: trailing whitespace.
+trailing spaces here
ws.txt:3: trailing whitespace.
+trailing tab here
ws.txt:4: space before tab in indent.
+ 	space before tab
ws.txt:5: new blank line at EOF.
$ echo $?
2                                     # 훅에서 그대로 쓸 수 있는 종료 코드

$ git config --get core.whitespace
                                      # 비어 있음 = 내장 기본값이 적용된다
                                      # blank-at-eol, space-before-tab, blank-at-eof

세 번째 층은 적용 시점 교정이다. 남이 보낸 패치에 줄 끝 공백이 들어 있을 때 git apply --whitespace=fix 는 적용하면서 그것을 떼어 낸다.

$ tail -3 patch.diff | cat -A
 ok line$
 clean tail$
+new line with trailing ws   $        <- 패치에 줄 끝 공백이 들어 있다

$ git apply --whitespace=fix patch.diff
patch.diff:8: trailing whitespace.
new line with trailing ws
warning: 1 line applied after fixing whitespace errors.

$ cat -A ws.txt
ok line$
clean tail$
new line with trailing ws$            <- 공백이 제거된 채로 적용됐다
수단막는 시점줄 끝 공백파일 끝 개행스페이스 뒤 탭강제력
.editorconfig저장할 때제거보장간접적편집기가 지원해야 한다
git diff --check커밋 전검출검출 못 함검출종료 코드 2 로 훅에서 차단
git apply --whitespace=fix패치 적용 시제거다루지 않음교정적용하는 쪽이 선택

포맷팅 커밋을 따로 떼는 습관

여기까지의 옵션을 다 안다고 해도, 가장 효과가 큰 것은 도구가 아니라 커밋을 나누는 습관이다. 이유는 단순하다. 옵션은 리뷰어가 매번 기억해서 붙여야 하지만, 나눠 놓은 커밋은 아무것도 기억하지 않아도 된다.

규칙은 한 문장이다. 포맷터를 돌린 결과는 그것만 담은 커밋으로 만든다. 로직 수정과 같은 커밋에 넣지 않는다. 이렇게 하면 세 가지가 동시에 해결된다. 리뷰어는 포맷팅 커밋을 열지 않고 넘길 수 있고, blame 은 그 SHA 하나만 .git-blame-ignore-revs 에 넣으면 되고, 문제가 생겼을 때 되돌릴 범위가 명확해진다.

# 포맷터를 이미 돌려서 로직 수정과 섞여 버렸을 때 되살리는 순서
$ git stash                           # 지금 작업을 잠시 치운다
$ prettier --write .                  # 포맷터를 저장소 전체에 실행
$ git commit -am "style: run formatter (no behaviour change)"
$ git rev-parse HEAD >> .git-blame-ignore-revs
$ git stash pop                       # 로직 수정을 다시 꺼낸다
$ git commit -am "fix: 실제 수정 내용"

# 커밋하기 전에 이 커밋이 정말 포맷팅뿐인지 확인하는 한 줄
$ git diff --cached --quiet -w && echo "공백만 바뀜" || echo "진짜 변경이 있음"
  • 포맷터 도입은 한 번에 저장소 전체를 돌리는 편이 낫다. 파일마다 조금씩 도는 방식은 포맷팅 커밋이 수십 개로 늘어나 ignore 목록 관리가 불가능해진다
  • 포맷팅 커밋의 메시지에는 동작 변경이 없다는 사실을 명시한다. 몇 달 뒤 그 커밋을 판단하는 사람에게 그 한 문장이 전부다
  • 커밋을 나누는 것은 리뷰어를 위한 배려가 아니라 이력을 읽을 수 있게 남기는 일이다. 리뷰는 며칠이면 끝나고 이력은 몇 년을 간다

git 이 없는 자리 - GNU diff

배포 서버에서 설정 파일 두 벌을 비교하는 상황처럼 git 저장소가 아닌 자리도 많다. GNU diff 에도 같은 옵션들이 있고 이름도 거의 같다. 다만 -B 의 hunk 단위 동작까지 git 과 똑같으므로 그 점도 확인해 둔다.

$ diff -u old.txt new.txt              # 옵션 없음
@@ -1,6 +1,7 @@
-alpha
-	beta = 1
-epsilon
+alpha
+    beta  =  1
+    epsilon
+

 gamma
-delta
+delta!

$ diff -u -b old.txt new.txt           # 공백의 양 변화만 무시
@@ -1,6 +1,7 @@
 alpha
 	beta = 1
-epsilon
+    epsilon                           <- 없던 들여쓰기는 남는다
+

 gamma
-delta
+delta!

$ diff -u -w old.txt new.txt           # 공백을 전부 무시
@@ -2,5 +2,6 @@
 	beta = 1
 epsilon                               <- 이번엔 사라졌다

+
 gamma
-delta
+delta!

$ diff -u -B old.txt new.txt           # 빈 줄만 무시
@@ -1,6 +1,7 @@
-alpha
-	beta = 1
...                                   # 아무 효과 없음. git 과 같은 hunk 단위 규칙

$ diff -q -w -B old.txt new.txt; echo $?
Files old.txt and new.txt differ
1                                     # 0 = 같음, 1 = 다름, 2 = 오류
  • -u 는 통합 형식 출력이다. 문맥 세 줄이 같이 나오므로 사람이 읽기 좋고, patch 로 적용할 수도 있다
  • -b 와 -w 의 차이는 git 과 정확히 같다. 없던 들여쓰기가 생긴 epsilon 줄에서 갈린다
  • -B 도 git 의 --ignore-blank-lines 처럼 hunk 단위라 다른 변경과 섞이면 효과가 없다
  • CRLF 가 섞였으면 --strip-trailing-cr 을 같이 준다. 이것 없이는 모든 줄이 다르게 나온다
  • 종료 코드로 판정할 때는 -q 를 쓴다. 출력이 한 줄로 줄어 스크립트에서 다루기 쉽다

공백이 의미를 갖는 자리

이 글의 내용을 다 적용한 뒤 마지막으로 남는 위험이 하나 있다. -w 를 습관으로 만들면 공백이 문법인 파일에서 진짜 변경을 놓친다. 이건 가정이 아니라 재현되는 사실이다.

$ git diff                            # 파이썬 파일에서 한 줄을 반복문 밖으로 뺐다
@@ -2,7 +2,7 @@ def total(rows):
     s = 0
     for r in rows:
         s += r
-        print(s)
+    print(s)
     return s

$ git diff -w
                                      # 출력 없음. -w 는 아무 변경도 없다고 말한다

$ git diff -w --stat
                                      # 여기도 비어 있다

# 그런데 실제 동작은 이렇게 달라진다
$ python total.py                     # 수정 전
1
3
6
$ python total.py                     # 수정 후
6

출력이 세 줄에서 한 줄로 바뀌었다. 프로그램의 동작이 명백히 달라졌는데 git diff -w 는 바뀐 것이 없다고 보고한다. 파이썬에서 들여쓰기는 서식이 아니라 블록 구조 그 자체이기 때문이다.

대상공백이 갖는 의미-w 를 걸면권장
Python들여쓰기 깊이가 블록 구조블록 이동을 통째로 감춘다-w 금지. 필요하면 --ignore-space-at-eol
Makefile레시피 줄 앞은 반드시 탭탭이 스페이스로 바뀐 것을 감춘다-w 금지
YAML들여쓰기가 중첩 구조키가 다른 부모로 옮겨진 것을 감춘다-w 금지
Markdown줄 끝 스페이스 2칸 = 줄바꿈줄바꿈 소실을 감춘다--ignore-space-at-eol 도 위험
Go·Java·C 계열공백은 구분자일 뿐안전-w 를 기본으로 써도 된다
문자열 리터럴·테스트 픽스처공백이 데이터의 일부기댓값 변경을 감춘다파일 단위로 예외 처리

실무 기준은 이렇게 잡으면 무난하다. -w 는 리뷰를 시작할 때 잡음을 걷어내는 용도로만 쓰고, 승인 직전에는 옵션 없이 한 번 더 본다. 첫 번째는 어디를 봐야 할지 정하는 단계고, 두 번째는 놓친 것이 없는지 확인하는 단계다. 두 단계를 하나로 합치려는 순간 위 표의 위험이 살아난다.

리뷰에서 대량 포맷팅을 다루는 법

대부분의 리뷰 도구는 공백 무시 보기를 갖고 있다. 그것을 켜는 것으로 화면은 정리되지만, 그것만으로는 남는 문제가 있다. 리뷰 의견을 특정 줄에 다는 기능은 대개 원래 줄 번호를 기준으로 하므로, 포맷팅으로 줄이 밀리면 예전 의견의 위치가 어긋난다. 그리고 §9 에서 본 대로 blame 오염은 리뷰 화면 옵션으로 해결되지 않는다.

그래서 대량 포맷팅이 로직 수정과 한 덩어리로 올라왔을 때는 분리를 요청하는 편이 낫다. 요청할 때 감정이나 취향이 아니라 숫자를 근거로 쓰면 대화가 짧아진다. §8 의 명령이 그 숫자를 만들어 준다.

  • git diff --shortstat 과 git diff -w --shortstat 두 줄을 그대로 붙인다. 51줄 대 2줄 같은 대비는 설명이 필요 없다
  • 공백만 바뀐 파일 목록을 git diff -w --numstat 으로 뽑아 함께 낸다. 그 파일들은 리뷰할 것이 없다는 뜻이다
  • 요청의 형태는 커밋 분리지 되돌리기가 아니다. 포맷터를 쓰지 말자는 말로 읽히면 논점이 옮겨간다
  • 분리된 포맷팅 커밋의 SHA 를 .git-blame-ignore-revs 에 넣는 것까지를 같은 요청에 포함한다. 그래야 blame 문제가 남지 않는다
  • 반대로 포맷팅만 든 순수 커밋은 빠르게 승인한다. 분리를 요청해 놓고 그 커밋을 오래 붙잡으면 다음부터 아무도 나누지 않는다
  • 저장소에 포맷터 설정이 커밋돼 있고 CI 가 그것을 검사한다면, 포맷팅 커밋의 내용 자체는 사람이 검토할 것이 아니다. 검토할 것은 설정 파일이 바뀌었는지뿐이다

정리

공백 잡음 문제는 두 층으로 나뉜다. 이미 생긴 것을 화면에서 지우는 일과, 애초에 생기지 않게 하는 일이다. 앞쪽은 옵션 네 개로 거의 끝난다. 줄 끝만 지우려면 --ignore-space-at-eol, 들여쓰기 변환까지 지우려면 -b, 없던 들여쓰기까지 지우려면 -w, 빈 줄 정리 커밋에는 --ignore-blank-lines. 셋은 포함 관계이고 마지막 하나만 성격이 다르다.

blame 은 별개 문제다. -w 로는 포맷터 커밋을 지울 수 없다는 것을 §9 에서 확인했다. 실제 답은 .git-blame-ignore-revs 에 그 커밋의 40자 SHA 를 적고 blame.ignoreRevsFile 을 설정하는 것이다. 파일이 저장소에 같이 커밋되므로 한 번 넣으면 팀 전체가 같이 고쳐진다.

그리고 뒤쪽 층, 즉 애초에 막는 일이 결국 더 크다. .editorconfig 로 저장 시점에 정리하고, git diff --check 를 커밋 훅에 걸고, 포맷터 결과는 그것만 담은 커밋으로 낸다. 이 셋이 되면 앞의 옵션들을 외울 일이 별로 없어진다. 다만 마지막으로 하나는 남는다. 파이썬과 YAML 과 Makefile 앞에서는 -w 를 손에서 놓아야 한다. 그 자리에서는 공백이 서식이 아니라 코드다.

확인하지 못한 것

  • --ignore-rev 와 --ignore-revs-file 이 git 몇 버전부터 들어왔는지는 1차 자료로 확인하지 못했다. 여러 곳에서 2.23 이라고 적고 있으나 릴리스 노트를 직접 열어 대조하지 않았으므로 버전 번호는 본문에 쓰지 않았다. 위 출력은 전부 2.48.1 에서 나온 것이다
  • Makefile 의 레시피 줄이 탭이 아닐 때 나는 오류는 직접 재현하지 못했다. 실험에 쓴 Git Bash 에 make 가 없었다. 그래서 §17 의 Makefile 행은 규칙만 적고 실행 출력은 붙이지 않았다
  • .editorconfig 의 각 키가 편집기별로 실제로 어디까지 적용되는지는 확인하지 않았다. 이 파일은 git 이 해석하는 것이 아니라 편집기와 플러그인이 해석하는 것이라, 지원 범위가 도구마다 다르다
  • GitHub 외의 리뷰 도구들이 .git-blame-ignore-revs 를 어디까지 인식하는지는 확인하지 않았다. §18 은 그래서 특정 도구 이름 없이 일반적인 대응만 적었다
  • 모든 출력은 Windows 의 Git Bash 한 곳에서만 얻은 것이다. 리눅스나 macOS 의 다른 git 빌드, 특히 BSD 계열 diff 에서는 옵션 이름과 출력이 다를 수 있다
