はじめに: 22分間に起きたこと - npmエコシステムの時限爆弾

2026年5月19日(UTC未明)、npmでメンテナのアカウント1つが乗っ取られ、そのアカウントが管理していた約300のパッケージに637の悪意あるバージョンが約22分のうちに自動で公開された事件が報告されました。パッケージ数は報道によって314(The Register)または317(SafeDepの分析)とわずかに異なります。1分あたり約29バージョンが公開された計算で、人間の手作業では出せない速度のため、自動化スクリプトで一括公開したものと見られます。22分という短い時間と、1つのアカウントが数百のパッケージを左右するという事実こそが今回の核心であり、JavaScriptエコシステムがメンテナ認証情報という単一障害点にどれほど晒されているかを示しています。

今回の事件は単発の問題ではありません。本記事で整理するように、npmは2018年のevent-stream、2021年のua-parser-js、2022年のcolors/faker、2024年のlottiefiles、2025年9月のShai-Huludワームまで、ほぼ毎年大規模なサプライチェーン事故を経験してきました。SafeDepの分析によれば、今回の悪意あるコードは約3週間前にSAP関連のnpmパッケージ侵害で使われたMini Shai-Huludツールと同系統です。影響を受けたパッケージにはsize-sensor(月間約420万ダウンロード)、echarts-for-react(約380万)、@antv/scale(約220万)、timeago.js(約115万)のように他ライブラリの依存関係に深く組み込まれたものが多く、名前を聞いたことがなくても影響を受け得ます。

本記事は、事件の事実関係を発見・分析報告とGitHub・npmの公式告知で確認したうえで、日本の開発者・チームが今日中に実行すべき緊急対応4つと長期防御戦略7つを整理します。事件自体の技術的な細部よりも、すぐに適用できる行動に焦点を当てます。2026-09-29に一次情報と改めて照合し、事実関係を修正してその後の経過を追記しました。

事件の概要 - 何が、いつ、どのように起きたか

公開された分析と報道で確認できる事件の輪郭は次の通りです。セキュリティアドバイザリを直訳せず、本記事が確認した事実のみを整理し直しました。

  • 時期: 2026年5月19日UTC 01時39分頃に開始。SafeDepは01:39〜01:56と02:05〜02:06の2つの波に分けて記録しており、報道は約22分の一括公開と要約しています。
  • 規模: 悪意あるバージョン637件。パッケージ数は314(The Register)〜317(SafeDep)。@antvスコープのパッケージ多数とsize-sensor、echarts-for-react、timeago.jsなどが含まれます。
  • 侵害経路: 複数メンテナのトークンではなく、AntV関連パッケージ500以上(SafeDep集計で547)を管理していたメンテナアカウント1つ。そのアカウントがどのように乗っ取られたかは公開分析で明らかにされていません。
  • 悪意あるコードの性質: postinstallではなくpreinstallフックで約498KBの難読化されたBunスクリプトを実行。クラウド(AWS・GCP・Azure)の認証情報、GitHub・npmトークン、SSH鍵、Kubernetes・Vaultトークン、DB接続文字列などを収集し、攻撃者が作成したGitHub公開リポジトリと外部サーバーへ送り出します。
  • 検知・報告: あるセキュリティ研究者がGitHubで最初に報告し、SafeDepが詳細な分析を公開しました(The Register報道)。
  • 対応: 一部のバージョンは「誤って公開された」というメッセージとともにdeprecateされ、一部は削除されました。GitHubは状況を監視し、利用規約に従って悪意あるnpmパッケージを無効化していると述べました。

注目すべきは「22分」という短い時間枠です。この時間が意図的に設計されたものかは確認されていません。ただ、短時間でもセマンティックバージョン範囲(^、~)で依存関係を受け取るCIパイプラインは、その間に新しいバージョンをそのまま取り込めたという点で、検知の速さよりもインストール時点のゲートが重要であることを示しています。

攻撃メカニズムの分析 - 認証情報侵害 + 自動化バッチ配信

今回の事件の技術的な核心は、派手なゼロデイではなく「盗んだ認証情報 + 自動化」というありふれた組み合わせです。ありふれていることこそが核心です。派手な脆弱性が不要なほど、1つのアカウントが数百のパッケージの公開権限を握るnpmの認証・公開モデルが単一障害点になるということだからです。

1) アカウント乗っ取りフェーズ

公開分析は、アカウントがどの経路で乗っ取られたかを明らかにしていません。一般にnpmアカウントの乗っ取り経路としては、フィッシング、メンテナPCのマルウェア、過去に流出したトークンの再利用、.npmrcファイルの漏洩などが挙げられます。今回の悪意あるコード自体がnpmトークンとGitHubトークンを収集する以上、1回の感染で流出したトークンが次の侵害の鍵になり得ることは明らかです。また2FAを有効にしていても、2FA回避用トークンが漏れると攻撃者がアカウントを掌握できた点は、GitHub自身が告知で認めた問題です(その後の経過を参照)。

2) バッチ配信フェーズ(22分の時間枠)

公開権限を持つアカウントを1つ手に入れれば、事前に用意した悪意ある変種をそのアカウントのパッケージへ次々とpublishするのは難しくありません。npm publishを自動化で呼び出せば毎分数十件の公開も可能で、約22分で637バージョンが公開された点はこれと整合します。

3) ペイロード実行フェーズ(被害者側)

悪意あるバージョンはpreinstallフックからBunランタイムでスクリプトを実行します。SafeDepは、インストールフックを止めてもgithub:形式の任意依存関係でGitHubのコミットを取り込む2つ目の経路があったと分析しています。さらに感染したPCでは、AIコーディングツールやエディタの設定ファイル(.claude/settings.json、.vscode/tasks.json)に自動実行項目を仕込み、常駐サービスを登録して、1回のインストールが同じPCの他のワークスペースにまで広がるようにしていました。日本企業環境において、このフェーズの脅威は2つに分かれます。(a) ローカル開発PCの侵害: 開発者が無自覚にnpm installを実行した後のトークン・鍵の流出と常駐バックドア。(b) CI/CD侵害: GitHub Actionsや社内Jenkinsでビルド時のシークレットが外部流出。CIトークンは権限範囲が広いケースが多く、本記事は後者をより危険と見ます。

類似事件の歴史 - 同じ構造が繰り返される

npmのサプライチェーン攻撃は初めてではありません。代表的な事件を整理すると次の通りです。

  • 2018 event-stream: メンテナ交代直後に新メンテナが悪意あるペイロードを仕込み、ビットコインウォレット関連プロジェクトを狙った事件。「信頼の譲渡」が単一障害点であることを初めて広く示しました。
  • 2021 ua-parser-js: メンテナアカウント侵害後に悪意あるバージョンを配信。ダウンロード数が非常に多いパッケージで、影響範囲が広範でした。
  • 2022 colors/faker: メンテナ本人が意図的にコードを壊した事件。「信頼は自発的な協力」であることを改めて想起させました。
  • 2023 typosquatting多数: 人気パッケージ名と綴りが似た悪意あるパッケージが大量登録されました。
  • 2024 lottiefilesなど: SDKパッケージの侵害を通じて利用者のウォレット情報を狙った事件。
  • 2025年9月 Shai-Hulud: 乗っ取ったメンテナアカウントでインストールスクリプトを仕込み、自己増殖するワーム。GitHubの発表では500以上のパッケージが侵害され、これを機にGitHubはnpmの認証・トークン強化計画を打ち出しました。
  • 2026年5月 今回の事件: 規模は2025年のShai-Huludより小さいものの、同系統のツール(Mini Shai-Hulud)が数週間おきに再利用されている点が新しい。

このリストのパターンは明確です。毎回「メンテナの認証情報」が破られ、毎回同じ方法でレジストリが公開を許してしまうのです。事件ごとに暫定対応はあっても、構造的な解決策の導入は遅れます。provenance・sigstore・trusted publishingのような長期的な解決策が登場しましたが、すべてのパッケージに広がるには時間がかかります。

なぜnpmは繰り返し攻撃されるのか - 構造的脆弱性5つ

1) 単一メンテナモデル

npmパッケージの多くは1〜2人のメンテナで運営されています。その1人の認証情報が破られると、数百万ダウンロードのパッケージがそのまま露出します。今回のように1つのアカウントが数百のパッケージの権限を持つ場合、被害は一斉に広がります。PyPI、crates.ioなど他のレジストリも似た構造ですが、小さなパッケージを細かく組み合わせるnpmの文化は影響を増幅しやすいと言えます。

2) 深い依存関係ツリー

プロジェクトが直接依存するパッケージが10個でも、間接依存まで展開すると実際にインストールされるパッケージははるかに多くなります。npm ls --allで実際に数えてみると差がわかります。聞いたこともないパッケージがビルド環境で任意のコードを実行できるということです。

3) インストールスクリプトの任意コード実行

npmはインストール時にpreinstall・install・postinstallスクリプトを実行できます。正当な用途(ネイティブビルドなど)もありますが、攻撃者にとってはペイロード自動実行の通り道になります。他のパッケージマネージャの一部はこれをデフォルトで無効にしています。公開当時npmはデフォルトで実行していましたが、2026年7月のnpm v12から依存関係のインストールスクリプトはデフォルトでブロックされるようになりました(その後の経過を参照)。

4) メンテナ信頼譲渡の無防備さ

メンテナが他人にパッケージを譲る手続きは軽いものです。新メンテナの身元・経歴・悪意の有無の検証が弱く、利用者が自動で知る方法もありません。

5) provenance採用の遅い速度

npm provenanceは2023年に導入されましたが、すべてのパッケージが使っているわけではありません。provenanceはパッケージがどのCIワークフローでビルドされたかを証明するだけで、コードが安全である保証ではなく、CIワークフロー自体が侵害されれば悪意あるビルドにもprovenanceが付き得ます。それでも、盗んだトークンで個人PCから公開したバージョンと正規CIから公開したバージョンを見分ける手がかりになるため、採用が広がるほど今回のような事件の攻撃面は小さくなります。

今日中に実行すべき緊急対応4つ

本セクションは本記事で最も実務に近い部分です。日本のJavaScript開発チームが今日(遅くとも今週)中に処理すべき4つの作業です。

1) 疑わしいパッケージの即時確認 - npm audit

まず、すべての稼働中プロジェクトで次を実行します。

npm audit --audit-level=high
npm audit signatures   # レジストリ署名・provenanceの検証
npm outdated

npm audit signaturesは意外と知られていないコマンドで、ダウンロードしたパッケージのレジストリ署名とprovenance証明を検証します。事件時点(5月19日)前後に取得したパッケージがあれば、このコマンドでもう一度確認します。

2) lockファイル変更履歴の検証

package-lock.jsonまたはyarn.lockの最近の変更と、影響パッケージが含まれているかを確認します。

git log --since="2026-05-18" -- package-lock.json
grep -nE "size-sensor|echarts-for-react|timeago\.js|@antv/" package-lock.json

疑わしい時点にlockファイルが変更されていたり影響パッケージがツリーにあったりすれば、そのバージョンが正常かをGitHub Security Advisoriesや発見企業の影響リストと照合します。開発者が無自覚にnpm installした後、lockファイルを一緒にコミットするケースがあるため、PR単位での点検が必要です。

3) ビルドキャッシュの即時無効化

ローカル・CI・社内npmミラーにキャッシュされた悪意あるバージョンを除去します。

npm cache clean --force
rm -rf node_modules
npm ci   # lockファイル基準のクリーン再インストール

GitHub Actionsのactions/cache、GitLab CI cache、社内Nexus/Verdaccioミラーも併せて無効化します。キャッシュに悪意あるバージョンが残っていれば緊急対応の意味がなくなります。

4) 露出可能性のあるトークン・シークレットの即時ローテーション

今回のペイロードの主な標的は、環境変数や設定ファイル内のトークンと鍵です。以下の項目を、5月19日以降に影響バージョンがインストールされた環境に一度でも置いていたならローテーションします。

  • npm publishトークン(CIで使用中なら最優先)
  • GitHub PAT・Actionsトークン
  • AWS・GCP・Azureアクセスキー
  • SSH鍵・Slackトークン・Webhook URL
  • DB接続文字列・内部APIシークレット

トークン交換と併せて、SafeDepが推奨した痕跡も確認します。自分のGitHubアカウントに見知らぬ公開リポジトリができていないか、.claude/settings.json・.vscode/tasks.jsonに見慣れない自動実行項目がないか、知らない常駐サービスが登録されていないかを見ます。トークンだけ替えて常駐プログラムを残せば、新しいトークンもまた漏れます。

長期防御戦略7つ - 次の事件を防ぐシステム

1) trusted publishingとnpm provenanceの利用

npmにパッケージを公開しているなら、長期トークンの代わりにtrusted publishing(OIDC)へ移行します。npmドキュメントによればnpm CLI 11.5.1以上、Node 22.14.0以上が必要で、GitHub Actionsではpermissions: id-token: writeを付与します。GitHub Actions・GitLab CI/CDからtrusted publishingで公開すると、provenanceがデフォルトで自動生成されます。設定後はパッケージ設定で「Require two-factor authentication and disallow tokens」を選び、トークンによる公開を止めることをnpmが強く推奨しています。利用者側ではnpm audit signaturesで署名とprovenanceを検証できます。

2) Frozen lockfileの強制(--frozen-lockfile / npm ci)

ローカルでnpm installを使っていても、CIでは必ずnpm ciまたはyarn install --frozen-lockfileを強制します。lockファイルと一致しなければビルドが失敗するゲートを置くことが核心です。これ一つで「夜間に誰かが新バージョンをpublishし、ビルドがそれを取り込む」経路がほぼ遮断されます。

3) SBOMの生成・管理

ビルドごとにSBOM(Software Bill of Materials)を自動生成して保存します。形式はCycloneDXまたはSPDX。@cyclonedx/cyclonedx-npmのようなツールで簡単に導入できます。SBOMがあれば、次の事件が起きたときに「自分たちはそのパッケージを使っているか」にすぐ答えられます。

4) Dependabot / Renovateの導入

依存関係の更新を人の意志ではなく自動PRにします。ただし自動マージは有効にしません。PRが作られれば人がレビューする手順が強制されます。レビュー時にはnpm viewで最新バージョンのメンテナ・publish時刻・ダウンロード推移を一度確認します。

5) 定期的な依存関係監査サイクル

四半期に一度、依存関係監査ミーティングを設けます。議題は3つです。(a) 使っていないパッケージの削除、(b) deprecatedパッケージの置き換え、(c) メンテナの活動が止まったパッケージのfork・置き換え検討。この1時間が、事故が起きたときに影響範囲を洗い出す時間を大きく縮めます。

6) ミニマル依存関係ポリシー

「この機能のために100行のパッケージを追加する価値があるか」をPRレビューの必須質問にします。座標計算・文字列ユーティリティ・日付フォーマットのような小さな機能は、自前のコード10〜30行で足りることが多いものです。依存関係が少ないほど攻撃面は小さくなります。

7) 行為ベーススキャナ(Socket.devなど)の導入

従来のnpm auditは既知のアドバイザリと照合しますが、Socket.devのようなツールはパッケージコードの疑わしい挙動(ネットワーク呼び出し、eval、インストールスクリプトのパターンなど)を行動ベースで検知します。未知の新規侵害を捕捉する可能性が高まります。公開当時に併記したPhylumは、2025年1月にVeracodeが技術を買収し、Veracodeの製品群に組み込まれました。CIにPRコメント形式で統合するのが日本のチーム基準で最も滑らかな導入方法です。

CI/CDパイプライン強化 - GitHub Actionsの例

上記7つの戦略を実際のGitHub Actionsワークフローにまとめると次のような形になります。核心となるゲートだけを抜粋した例です。Node 20は2026年4月にサポートが終了したため、LTSの24に変更しました。id-token: writeは公開(publish)ジョブにだけ与え、通常のビルドからは外すほうが安全です。

name: secure-build
on: [push, pull_request]
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: 'npm'

      # 1) frozen lockfile - lockと不一致なら即失敗
      - run: npm ci

      # 2) auditゲート
      - run: npm audit --audit-level=high
      - run: npm audit signatures

      # 3) SBOM生成
      - run: npx @cyclonedx/cyclonedx-npm --output-file sbom.json
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

      # 4) 行為ベーススキャン(Socket.devの例)
      # - uses: socket-security/socket-cli-action@v1

      - run: npm test
      - run: npm run build

このワークフローの核心は「1ステップでも失敗すればビルド自体が止まる」という点です。緊急対応を人の意志に任せず、CIゲートとしてシステム化することが本記事の最後の核心メッセージです。

監視ツール比較 - Snyk、Socket.dev、Phylum、npm audit

実務でよく比較されるツールを整理します。

ツール検知方式強み弱み
npm audit既知アドバイザリとの照合無料・標準搭載ゼロデイ・行為ベース検知に弱い
Snykアドバイザリ + ライセンス + 一部行為UI・レポートが優秀、企業向け機能が豊富本格機能は有料プラン
Socket.dev行為ベース(eval/インストールスクリプト/ネットワーク)未知の侵害検知、PRコメントのUX良好偽陽性が一部、日本での導入事例は少ない
Phylum(現Veracode)行為ベース + 悪意あるパッケージのデータベース悪意あるパッケージの分析・遮断2025年1月にVeracodeが技術を買収、単独製品ではなくVeracode製品群として確認が必要
GitHub Dependabotアドバイザリ + 自動PRGitHub統合・無料検知より更新に近い

日本のチームへの推奨構成は次の通りです。(1) ベースはnpm audit + Dependabot(無料、即時導入)。(2) その上にSocket.devまたはSnykのいずれかをPRレビュー段階の補助ゲートとして。(3) 余裕があればVeracode(旧Phylumの技術)のような悪意あるパッケージ遮断層まで加える3段構成を推奨します。

日本企業・スタートアップ環境での適用

上記戦略を日本の環境に移す際によく挙げられる摩擦ポイントを整理します。

  • スタートアップ: セキュリティ人員がいない場合が多い。無料ツール(npm audit、Dependabot、Socket.devの無料枠)だけでもかなりの部分を防げるので、まずは導入から。完璧を追わず「やっていなかったことをやる」を目標に。
  • 中堅・大企業: 社内npmミラー(Nexus、Verdaccio)があれば、ミラー自体にallowlist・blocklistを適用。緊急事件時にミラーで遮断すれば全開発者に同時に効きます。
  • 金融・公共: ネットワーク分離環境でもnpmミラー経由で外部パッケージを取り込む経路は同じ。SBOM・署名検証を社内標準にするのが効果的。
  • フリーランス・1人開発: 自分のPCがそのままインフラ。トークンを平文で.envに置く習慣を即座にやめ、1Password CLI・dopplerのようなシークレットマネージャを導入。

開発者個人の責任の限界と、エコシステムの責任

本記事で整理した11項目(緊急4 + 長期7)をすべて実行しても、サプライチェーン攻撃を100%防ぐことはできません。それが現実です。個人・チーム単位の努力には明確な限界があり、その限界を超えるのはエコシステムレベルの変化です。

公開当時に本記事が挙げたエコシステムの責任は3つでした。(1) npm(GitHub)のメンテナ認証強化 - WebAuthn・ハードウェアキーの義務化。(2) provenance採用率を引き上げるための人気パッケージ向けインセンティブ。(3) インストールスクリプトのデフォルト無効化。このうち3つ目は2026年7月のnpm v12でデフォルトになり、1つ目の方向(2FA回避トークンの制限、trusted publishingへの移行)も段階的に進んでいます。詳しい日付はその後の経過の節にまとめました。

2026年下半期サプライチェーンセキュリティのトレンド - 公開当時の見通し

以下は公開当時(2026-05-22)の見通しです。その後実際に確認された変化は、その後の経過の節に別途記載しました。

  • provenance採用の加速: 人気パッケージのメンテナによる自発的な導入が事件直後に増える可能性。
  • 行為ベーススキャナの標準化: 行為ベーススキャナの導入が無料枠を中心に拡散。
  • SBOM義務化の流れ: 米国EO 14028の流れの影響で、日本の公共・金融入札でSBOM要求が増える可能性。
  • AIベースのコードレビュー + 依存関係分析の結合: PRレビュー時にAIが新しい依存関係のリスクを自然言語でコメントする流れ。
  • npm以外のレジストリ選択肢の検討増加: deno、jsr、bunの独自レジストリへの関心の高まり。ただし短期間でのnpm代替は難しい。

結論 + チェックリスト15項目

本記事の核心を一行でまとめるとこうなります。サプライチェーンセキュリティはツールではなくシステムであり、システムは今日から始められる小さなゲートの積み重ねです。次の事件の時間枠はさらに短いかもしれません。その次の22分を防ぐのは、各チームの緊急4つと長期7つのシステム化です。

最後に、本記事で整理した15項目のチェックリストです。印刷して机の横に貼り、一行ずつ処理してください。

  1. すべての稼働中プロジェクトでnpm audit --audit-level=highを実行
  2. npm audit signaturesで署名・provenanceを点検
  3. 5月19日前後のlockファイル変更履歴と影響パッケージの有無を確認
  4. npmキャッシュ・CIキャッシュ・社内ミラーキャッシュをすべて無効化
  5. 5月19日以降に影響バージョンがインストールされた環境のトークン・シークレットをローテーションし、常駐の痕跡を点検
  6. 公開の自動化をtrusted publishingへ移し、長期publishトークンを削除
  7. CIでnpm ci / --frozen-lockfileを強制
  8. CIでnpm auditをゲート化(高リスク検出時は失敗)
  9. SBOM生成ワークフローを導入(CycloneDX推奨)
  10. DependabotまたはRenovateを有効化(自動マージなし)
  11. 四半期に1回の依存関係監査ミーティングをカレンダーに登録
  12. 公開するパッケージにnpm provenanceを適用(trusted publishingなら自動)
  13. Socket.devまたはSnykのいずれかの無料枠を導入
  14. インストールスクリプトの許可リストを見直す(npm v12のallowScripts)
  15. 社内npmミラー運用時はallowlist/blocklistポリシーを策定

その後の経過(2026-09-29確認)

公開後にGitHub・npmの公式告知で確認できたものだけを日付順に記載します。本文の前半は公開当時(2026-05-22)の解説で、事実関係が一次情報と異なっていた部分だけを修正しました。以下の告知はいずれも今回の事件に直接言及していないため、事件が原因で変わったと断定することはできません。
