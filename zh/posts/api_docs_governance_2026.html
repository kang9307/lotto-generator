API 文档为什么总是落后于代码 - 把 Excel 与 PDF 规格换成机器可读的契约

单一事实来源的落点、破坏性变更分类、CI 检查的边界、废弃策略与新鲜度指标

2026年7月28日 开发/基础设施

引言: 不是文档写错了，而是它被做成了可以出错的样子

对接负责人发来一封邮件，附件叫 API规格书_v3_最终_最终2_修订版.xlsx。里面十二个工作表，还活着的只有四个，其余是大家默认当作已删除的。合作方照着这个文件写代码。可服务器在两个月前的发布里改掉了一个响应字段的名字，而这件事在表格里没有留下任何痕迹。联调最后一天，对接崩了。然后会上有人说：「文档管理还是得再规范一点。」

本文正是从这个结论错在哪里开始。事故不是因为谁偷懒。真正的原因是把文档与代码可以发生偏离的结构原封不动地留着，再把不偏离这件事托付给个人的认真。认真无法扩展。三十个端点时行得通的做法，到三百个时必定崩塌。

API 文档和其他内部文档有一处根本不同：读者不只是人。API 规格是两个程序之间的约定，而约定只有在机器能核对时才具备强制力。Excel 和 PDF 真正的问题不是老派，而是无法核对。表格里写下的 orderStatus: string，从未与服务器实际输出的内容比对过一次。无法比对，偏离了也没人知道；没人知道，就会带着偏离过好几个月。

所以本文不谈「怎么把文档写好」，而谈如何设计出一偏离就立刻暴露的结构。论点只有三行。

  • 文档落后于代码不是人的懈怠，而是更新触发点被分离的必然结果。
  • 第一步不是引入工具，而是决定单一事实来源放在哪里，并把其余全部降级为派生产物。
  • 自动化能抓与不能抓的边界比想象中清晰。不了解边界，买了工具照样会出同样的事故。

本文不涉及的内容。 作为 RAG 索引对象的内部文档整体老化与治理，已在企业知识库在悄悄腐坏中讨论。本文只深挖其中机器可读的 API 契约这一条窄轴，两篇共通的责任人、有效期与废弃流程不再重复。工具之间的通信协议本身由 MCP 完全指南与 MCP 是否已经终结承担，券商公开 API 案例见Toss 证券 OpenAPI。

1. Excel 与 PDF 规格真正失去的东西 - 不是载体，是可验证性

先把成见放下。用 Excel 整理 API 的团队并不落后。Excel 门槛几乎为零、表格编辑自由、人人都能打开，是相当好的工具。初创团队从 Excel 起步是理性选择。问题出在规模变大后仍不回头审视这个选择。

1.1 不能被机器读取，就无法被验证

OpenAPI 规格这样定义自身：面向 HTTP API 的、与编程语言无关的标准接口描述。要点在标准与机器可读。格式是标准的，就会有读这个格式的工具；有工具，下面三件事就能放进流水线。

  • 语法与规约检查 - 这份描述本身是否有效，是否遵守内部命名规则
  • 版本间差异比对 - 相比上次发布改了什么，其中哪些会打断消费方
  • 与实现的核对 - 服务器是否真按描述的那样响应

Excel 与 PDF 三者都做不到。更准确地说，不是做不到，而是没人去做。维护一个能从合并单元格与自由排版中稳定抽取字段定义的解析器，成本高于直接迁移到标准格式。

1.2 附件不是分发，是复制

第二种损失更安静。规格被当作邮件附件发出的那一刻，正本消失，只剩下副本。合作方 A 看的是三月拿到的文件，合作方 B 看的是五月的，双方都相信自己手里是最新版。判断谁更新的唯一线索是文件名，而文件名取决于 最终 这个词被重复了几次。

改用 URL 分发能消掉一半问题：一个地址永远指向当前版本，带版本标签的地址保留历史。剩下的另一半，也就是「那个 URL 的内容是否与真实服务器一致」，从下一节开始处理。

2. 文档偏离代码的五条路径

偏离不是单一原因造成的。实务中反复出现的路径有五条，而且每条路径的堵法都不一样。不区分原因先上工具，堵住的往往是错的那条。

2.1 路径一：更新触发点分离

最常见也最致命。代码变更必须通过合并这一强制事件，而文档更新并不挂在那个事件上。不同仓库、不同负责人、不同排期，滞后就不是概率而是时间问题。药方只有一个：把规格文件放进与代码相同的仓库、相同的变更请求里。OpenAPI Initiative 的学习文档也写道，规格文档应当被当作与生产代码并列做版本管理的一等源文件。

2.2 路径二：副本扩散

上一节已经谈过。没有正本标识，即使发现偏离也不知道该改哪一份副本，改完其他副本依旧原样留着。

2.3 路径三：格式装不下的约定

这条路径即使迁到标准格式也依然存在。任何描述格式都有表达不了的约定，例如下面这些。

  • 金额字段用的是主单位还是最小单位，小数点保留到第几位有效
  • 时间字符串的时区是 UTC 还是本地时间，偏移量标注是否必填
  • 重试时幂等键如何构造、保留多久
  • 列表查询的分页约定是偏移还是游标，游标何时失效
  • 部分失败时，哪些成功了要从响应的哪个位置读取

这些条目不会以类型的形式写进模式，只会以自然语言写在说明字段里，或者干脆不写，留作口头约定。所以已经引入规格的团队，在这一层照样出事。对策有两个：用检查器强制说明字段不得为空；把这些约定钉死在一份全公司通用的规则页上，让各个 API 去引用它。

2.4 路径四：自动生成制造的错觉

人们常期待从代码注解生成文档就能消除偏离，这只对了一半。生成器读的不是代码而是注解，而注解由人手工维护。给响应对象加了字段却忘记更新注解，文档就会因为「是自动生成的」而获得更高信任，同时保持错误地发布出去。这就是它可能比手写文档更危险的原因。

OpenAPI Initiative 推荐设计优先，理由也在这个结果一侧：用代码能构建的 API 范围比 OpenAPI 能描述的范围更广，因此先实现再回头拼凑，容易留下不直观且不完整的描述。

2.5 路径五：删不掉，于是不断膨胀

最后一条路径由时间造成。旧端点与旧字段删不掉，新的却不断堆上来。删不掉的原因是不知道谁在用。没有度量使用量，就不知道删了会打断什么；不知道，就只好留着。结果规格变成现行与历史的混合体，读的人分不清哪些还活着。这条路径靠文档工具堵不住，需要废弃策略与使用量度量，见第 8 节与第 9 节。

3. 机器可读的契约是什么 - OpenAPI 标准化什么、不标准化什么

OpenAPI 规格以语言中立的方式描述 HTTP API 的接口：路径与方法、请求参数、请求与响应体的模式、认证方式、错误响应形态，都收进结构化定义。同样重要的是装不进去的东西：业务规则的含义、调用顺序、性能特征、计费策略都不在描述范围内。规格是关于形状的契约，不是关于含义的契约。

3.1 3.0 与 3.1 的实质差别

版本选择上真正分岔的点是模式语言。3.0 使用的是 JSON Schema 的一个变形子集，因而产生了 nullable 这类自定义关键字，给工具兼容带来混乱。2021 年 2 月发布的 3.1 与 JSON Schema 2020-12 完全对齐，任何有效的 JSON Schema 2020-12 文档都可以直接作为 3.1 的模式使用；Webhook 描述也在 3.1 中正式加入。

规格自身的版本体系是 major.minor.patch，其中major.minor 决定功能集合，patch 只负责修正错误与澄清表述。也就是说 3.1.0 与 3.1.1 是同一套功能集合。没确认内部工具链对 3.1 的支持程度就贸然升级，先坏掉的往往是工具。截至 2026 年 7 月，各工具对 3.1 的支持程度仍有差异，在采用前用你实际使用的生成器、文档渲染器与模拟服务器实测更稳妥。

3.2 废弃标记在模式层也有

OpenAPI 在操作对象上放了布尔字段 deprecated，用来声明该操作已废弃，消费方应当避免使用。在 3.1 中，由于模式遵循 JSON Schema 2020-12，字段级的废弃同样可以表达。需要知道的是，JSON Schema 的 deprecated 是不影响校验的注解关键字，被标记的值依然会通过。标记只是信号，不是强制。

4. 单一事实来源该放在哪里 - 判断表

选工具之前要先定的是正本的位置。OpenAPI Initiative 的指引很直接：信息应当只存在于一处，重复必然导致其中一份分叉。如果不得不放在两处，就用持续集成测试来强制两者一致。

每次都靠直觉回答「这个变更没问题吧」，判定会因人而异。以公开指引为基准更可靠。下面依据谷歌的 API 设计指南 AIP-180 与 Stripe 的公开策略整理。

5.1 从表里真正该读出的东西

这张表的价值不在背条目，而在两条原理。

  • 新增大体安全，删除与修改大体危险。所以成熟的 API 宁可不断堆字段也不删，转而用废弃流程来清理。
  • 是否安全取决于消费方的容忍度，而不是服务端。只有以「忽略未知字段、容忍未知枚举值」的客户端为前提，「新增是安全的」才成立。因此这条容忍规则也必须写进面向消费方的文档。

5.2 Stripe 式日期版本给出的启示

Stripe 公开说明，只有大版本发布才包含不兼容变更，月度发布只含兼容变更。其工程博客提到，它通过堆叠把新响应降级回旧格式的小而独立的转换模块来维持历史版本。这种做法的代价很清楚：转换层会永远堆积。对多数组织而言过于奢侈，但可以带走的原则只有一条：不要让不兼容变更随时流出去，把它们汇聚到一个节点上。

6. 契约测试保障什么、不保障什么

即使有了规格，服务器是否按规格响应仍是另一个问题。填补这道缝隙的代表性做法，就是消费方驱动的契约测试。

6.1 先把定义弄准

Pact 官方文档把契约测试定义为通过单独检查每个应用来测试集成点，确认它发送或接收的消息符合契约中记录的共同理解的技术。消费方测试执行期间与测试替身之间的交互会被记录成契约，提供方一侧再回放该契约进行验证。核心好处在于不必把两个服务同时拉起，就能检查集成。

6.2 把边界划清楚

同一份文档也把限制写得很明白，而这部分在实务中最常被误读。

  • 契约不同于描述所有可能状态的模式，它是通过执行一组具体的请求与响应配对来强制的。
  • 因此只有消费方实际使用的部分会被检查。没人调用的字段不在任何契约里，不在契约里就得不到保护。
  • 仅有提供方一侧的契约测试，无法保证消费方以正确的方式发起调用。
  • 它需要消费方参与，对消费方未知的公开 API 很难直接套用。

归结起来，契约测试不能替代规格检查或破坏性变更检测，它们处在不同层次：规格覆盖得广而浅，契约覆盖得窄而深。两者都没有就什么都没覆盖，只有其一就只覆盖那一侧。

7. CI 能自动验证什么、不能验证什么

这一节是本文的实务核心。不了解边界，引入工具后照样会出同样的事故。按项目逐条区分自动化的可行性。

验证项目自动化工具类型残留风险
规格文档的语法有效性完全可行规格校验器没有。不通过就拦住合并即可
内部风格规约的遵守完全可行检查器(如 Spectral)规则里没有的惯例不会被检查
说明与示例缺失可行检查器规则只知道是否填了，不知道内容是否正确
相对上一版本的破坏性变更大体可行规格差异比对(如 oasdiff)形状相同而只有含义变了的变更抓不到
实现是否按规格响应部分可行属性测试(如 Schemathesis)难以构造的状态与带副作用的路径未被检查
消费方使用的部分是否被遵守可行(有条件)契约测试(如 Pact)没有消费方参与就无法成立
说明文字是否属实不可行人工评审成本最高，也最常被省略
业务规则与调用顺序的一致性不可行设计评审规格只承载形状
废弃通知是否真的到达消费方不可行运营流程与使用量度量没有度量就连确认都做不到

7.1 检查器抓得住什么、抓不住什么

Spectral 自我介绍为API 风格指南的强制器，以及灵活的 JSON 与 YAML 检查器。它内置支持 OpenAPI 2.0、3.0 与 3.1，AsyncAPI 2.x 以及 Arazzo 1.0，通过定义规则集来强制内部规约。内置函数可以做模式匹配检查、参数检查、字母序、字符数以及指定键是否存在的校验，需要时还能自行编写函数。

这里有一个决定性的限制：检查器只看规格文档，它不知道服务器会响应什么。检查拿满分，规格照样可能与现实不符。若不把这一点向团队讲清楚，通过检查会被当成正确性的保证来消费，这是危险的错觉。

7.2 差异比对与实现核对

oasdiff 以机器可读的形式输出两份规格之间的差异，并用规则标出可能打断消费方的变更。该项目称其可识别破坏性与非破坏性变更共 506 种，发现破坏性变更时返回退出码 1，从而让 CI 步骤自动失败。它的 GitHub Action 会在变更请求时与基准分支比对并留下行内标注。

Schemathesis 的方向相反。它从 OpenAPI 或 GraphQL 模式自动生成测试用例并真实发起调用，检查响应是否符合模式。它擅长抓住的正是那种缓慢漂移：代码返回了模式从未记录的字段，或者在模式承诺是字符串的位置返回了空值。

# 示例流水线 - 命令形态随工具版本而异，请以官方文档为准

# 1) 规格语法与内部风格检查
spectral lint openapi.yaml --ruleset .spectral.yaml

# 2) 相对基准分支检测破坏性变更 (发现时退出码为 1)
oasdiff breaking base/openapi.yaml head/openapi.yaml

# 3) 核对预发布服务器是否按规格响应
schemathesis run openapi.yaml --url https://staging.example.com

7.3 落地顺序搞错，只会招来反弹

三个阶段一次性全部设为拦截条件，既有规格会涌出成百上千条问题，团队的应对方式往往是把规则关掉。实战中行得通的顺序是这样的。

  • 第 1 周：只把语法校验设为拦截条件，其余仅输出警告
  • 第 2 到 4 周：检查器规则只作用于新变更部分，既有违规固定成清单逐步偿还
  • 第 5 周起：把破坏性变更检测设为拦截条件，但同时建立审批流程，让有意为之的不兼容变更能够通过
  • 实现核对与契约测试从最重要的几个端点开始

8. 废弃策略必须包含的条目

阻止文档膨胀的唯一装置就是废弃流程。下面依据公开案例与标准文档，整理策略文档应当包含的条目。

  • 声明的位置 - 废弃要标注在规格里。Zalando 的公开指引要求，在废弃端点、输入参数、对象或属性时设置 deprecated: true，并在说明项中写明理由。
  • 最短通知期 - 没有行业统一数字。谷歌云服务条款写明，在停止服务或对面向客户的 API 做不向后兼容的重大修改前至少提前 12 个月通知；微软 Graph 文档写明，正式发布的 API 在移除前至少提前 24 个月宣布废弃。自家标准按消费方性质来定即可。
  • 响应头信号 - 同时使用 RFC 9745 定义的 Deprecation 响应头与 RFC 8594 定义的 Sunset 响应头。Sunset 时间不得早于 Deprecation 时间。
  • 指引链接 - 两份 RFC 都定义了链接关系类型，用 rel 值把策略与迁移指引文档挂上去。
  • 明确替代方案 - 写清楚该迁到哪里、字段如何对应。Zalando 指引同样要求详细记录消费方应改用什么以及如何迁移。
  • 使用量度量 - 同一份指引要求 API 所有者观测迁移进度，以免对现有消费方造成失控的破坏。看不到按消费方拆分的残余调用量，就定不出下线时间。
  • 与外部消费方达成一致 - 存在外部合作方时，要定下废弃后的维护期并取得对方同意。
  • 下线方式 - 事先决定是某天直接切断，还是短时间阻断以向残留消费方发出信号，抑或分阶段抬高错误率。
  • 例外条款 - 写明遇到安全漏洞或合规要求时期限可能缩短。谷歌云条款也设有同样的例外。

8.1 在规格与响应头里长什么样

# openapi.yaml - 操作级别的废弃标记
paths:
  /v1/orders/{orderId}:
    get:
      operationId: getOrderV1
      deprecated: true
      summary: 查询订单详情 (计划下线)
      description: |
        计划于 2026-09-01 下线，替代路径为 GET /v2/orders/{orderId}。
        marketing_agree 字段已迁移到 consents[].marketing。
        迁移指引: https://api.example.com/docs/migrate/orders-v2
      responses:
        '200':
          description: 订单详情
HTTP/1.1 200 OK
Content-Type: application/json
Deprecation: @1785196800
Sunset: Tue, 01 Sep 2026 00:00:00 GMT
Link: <https://api.example.com/docs/migrate/orders-v2>; rel="deprecation"

Deprecation 响应头的值是结构化字段形式的日期，因此 @ 后面跟的是以秒为单位的整数；Sunset 响应头的值使用 HTTP 日期格式。RFC 8594 明确写道，Sunset 时间应当被当作提示，并不保证在此之前一直可用。也就是说响应头是信号而不是承诺，承诺由策略文档与协商达成。

9. 文档新鲜度指标 - 度量什么才能看见偏离

偏离不会引发故障，也不会触发告警。所以不度量就永远看不见。下面这些指标大多只用现有仓库与访问日志就能算出来。

指标计算方式怎么读
规格滞后处理器代码最后变更日 − 该路径规格最后变更日正值区间越长漂移越重，按周观察各路径的最大值
幽灵路径数规格中有但路由表中没有的路径数只要不为 0，就意味着照文档写代码的消费方会被打断
未记录路径数路由中有但规格里没有的路径数同时会暴露内部临时路径被对外开放的风险
说明缺失率说明为空的操作与字段 ÷ 总数用检查器每天算一次，只看趋势也足够
示例覆盖率带有请求与响应示例的操作占比与合作方接入期的咨询量高度相关
契约测试覆盖率存在消费方契约的路径 ÷ 对外开放路径覆盖之外的区域正是真正出事的地方
废弃残余调用标记为 deprecated 的路径按消费方拆分的日调用量不收敛到 0 就该把下线时间往后推
废弃后经过天数自声明起经过的天数与残余调用量的交叉只满足期限就下线会出事故
差异比对告警数每个变更请求中检出的破坏性变更条数突然增多是设计共识正在瓦解的信号

不必全部盯着。起步两个就够：幽灵路径数与未记录路径数。这两个指标只要有路由表导出与规格文件就能算出来，而数值不为 0 的瞬间，就毫无争议地证明此刻这份文档是错的。它们也是在会议上争取优先级最有效的数字。

10. 仍在用 Excel 与 PDF 的组织该按什么顺序迁移

最常见的失败是全量迁移：想一口气搬完 200 个端点，三个月后中断，退回表格。换个顺序，结果就不一样。

10.1 第 0 步 - 先定下唯一正本 (几天)

  • 把在外流转的副本收拢，指定一份现行正本，其余标记为已废弃，删除留到以后再做。
  • 用访问日志取出实际调用量排名前 20 的路径，迁移范围就是这 20 个。
  • 整理消费方清单，分成内部团队、外部合作方与来源不明的调用三类。

10.2 第 1 步 - 只把这 20 个写成规格 (2 到 3 周)

  • 把既有文档与真实流量对照，以实际行为为准来写。表格里的记载与现实不符时，现实是对的。
  • 把规格文件放进与服务端代码相同的仓库，仅这一条就堵住了路径一。
  • 从 3.0 起步还是直接上 3.1，按所用工具支持的范围来决定，最新的未必总是对的。

10.3 第 2 步 - 接进流水线 (2 周)

  • 把语法校验设为合并的拦截条件。
  • 检查器只开警告级别，此时设为拦截会招来反弹。
  • 从规格生成文档页面并以 URL 分发，从这一刻起停止发送表格附件。

10.4 第 3 步 - 变更管控 (3 到 4 周)

  • 在变更请求中运行与基准分支的差异比对，标出破坏性变更。
  • 为不兼容变更建立审批流程，未审批不得通过，但审批路径要保持简短。
  • 把第 5 节的分类表贴到团队知识库，共享判定标准。

10.5 第 4 步 - 实现核对与契约 (4 周以上)

  • 在预发布环境加上模式符合性检查，把真实响应与规格对照。
  • 与最配合的一个消费方团队试点契约测试，全面推广排在之后。
  • 把废弃策略写成文档并加上响应头信号，同时开始度量残余调用量。

10.6 不该做的事

  • 先挑工具。正本位置没定下来，任何工具都找不到自己的位置。
  • 所有路径同时迁移。调用量前 20% 通常制造了绝大部分事故。
  • 第一周就全面拦截。一旦形成关规则的文化，就很难扭转。
  • 让表格继续并存。两个正本必然分叉，迁完就把旧文件锁成只读。

11. 这套体系防不住什么

不夸大地讲：把上面写的全做到，偏离也不会消失，改变的是偏离暴露的速度与代价。留下的窟窿有这些。

  • 含义仍然靠人守。规格是关于形状的契约，像金额单位、时区、幂等约定这类写在说明里的自然语言承诺，任何检查器都验证不了。
  • 设计优先并非永远正确。OpenAPI Initiative 自己也承认代码优先更容易上手。需求摇摆的早期阶段先把规格定死，时间会全花在改规格上。
  • 自动生成会原样记录不准确的实现。「是生成的」并不等于「是正确的」。
  • 契约测试需要参与者。消费方未知的公开 API 需要另一套办法。
  • 通过检查不是正确性的保证。它只看风格。
  • 没有责任人，工具就是摆设。告警响了却没人接，告警就变成噪音。

所以把目标定成零偏离必定失败。现实的目标是：让偏离在发布时点就暴露出来，并让暴露之后的修复成本，远低于在联调最后一天才发现的成本。

结论: 把这件事交给结构，而不是交给认真

用表格管规格的组织需要的不是训话，负责人已经够认真了。问题在于认真是唯一的防线。防线只有一条时，它休息的那天就会被突破。

要改的只有三件事。第一，把正本钉死在一个地方，其余全部降级为派生产物。第二，把正本放进与代码相同的变更请求里，让更新触发点合而为一。第三，换成机器能核对的格式，让偏离自动暴露。做完这三件，检查器、差异比对与契约测试都只是叠加在上面的东西。把顺序颠倒过来先买工具，同样的事故只会以更贵的形式重演。

最后是本文最希望留下的一句话：文档出错不是事故，而是设计的结果。留着可以出错的结构，总有一天会出错；反过来，建好一偏离就立刻暴露的结构，人偷懒时系统也扛得住。文档管理不是认真与否的问题，而是结构的问题。

下周一要做的只有一件事：把路由表导出来与当前规格对照，数一数两边各自缺失的路径有多少。如果这个数字不是 0，答案已经摆在眼前了。

# API 弃用（Deprecation）政策检查清单

> 来源：braindetox.kr — API 文档为何总是落后于代码
> 规范依据：RFC 8594（Sunset 头）、RFC 9745（Deprecation 头）
> 可将本文件直接粘贴给 AI，让它按你所在服务的标准填写。

## 1. 政策文档中必须写明的内容
- [ ] 弃用预告期（例：GA 至少 __ 个月 / 预览版至少 __ 周）
- [ ] 预告起算时点的定义（以公告日为准，还是以文档更新日为准）
- [ ] 兼容变更与不兼容变更的边界（用下面表 2 达成一致）
- [ ] 例外条款 — 安全漏洞是否可以缩短预告期
- [ ] 弃用后的响应（返回 410 Gone，还是继续返回 200）
- [ ] 通知渠道（响应头 / 变更日志 / 邮件 / 控制台，哪一个为正式渠道）

## 2. 变更类型分类 — 不事先约定就会每次争论
| 变更 | 分类 | 是否需要弃用流程 |
|---|---|---|
| 新增可选字段 | 兼容 | 不需要 |
| 删除字段 | 不兼容 | 需要 |
| 修改字段类型 | 不兼容 | 需要 |
| 新增枚举值 | **争议点** | 若调用方严格解析则不兼容 |
| 新增必填参数 | 不兼容 | 需要 |
| 新增错误码 | **争议点** | 若调用方按错误码分支则不兼容 |
| 改变排序 | **争议点** | 若从未承诺过顺序则视为兼容 |

## 3. 机器可读的信号（仅有面向人的公告不够）
- [ ] `Deprecation` 响应头 — RFC 9745
- [ ] `Sunset` 响应头 — RFC 8594，实际停止时间
- [ ] `Link` 头中以 `rel="deprecation"` 指向说明文档
- [ ] OpenAPI 文档中标注 `deprecated: true`
- [ ] 在 CI 中检查上述三者 **是否指向了不同的日期**

## 4. 关停之前必须确认
- [ ] 最近 30 天的残余调用量（不为零就不要关停）
- [ ] 能否识别出残余调用方（API Key / User-Agent / 合同单位）
- [ ] 仍在调用该接口的内部系统 — 事故通常出在这里
- [ ] 替代方案是否提供 **等价能力**（仅部分覆盖则不能弃用）
- [ ] 回滚方式 — 关停后能否恢复

## 5. 常见失败
- 只在文档里写"不再支持"，却不发送响应头 → 没有人会知道
- 已发出预告，但 **没有统计残余调用量** 就关停了
- 做了替代 API，却 **没有迁移指南**
- 弃用日期写在多个文档中，彼此不一致
