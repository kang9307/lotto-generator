契机 — 涵盖模型服务至自主智能体的AI安全自检

随着生成式人工智能从单轮对话系统演进为涵盖底层推理服务器、模型上下文协议(MCP)连接器、自主智能体技能(Agent Skills)及多智能体协作工作流的复杂架构，系统暴露的安全攻击面呈现出多层级交织的态势。传统基于Web特征的安全检测工具，难以直接针对AI推理协议、智能体工具滥用(tool misuse)或对抗性越狱(jailbreak)提供全面诊断。

2026年秋季，腾讯安全平台部旗下的腾讯朱雀实验室正式开源了AI红队安全检测平台AI-Infra-Guard(A.I.G)。该项目基于Apache-2.0许可协议发布，定位于帮助企业和技术团队在内部对AI全技术栈开展安全风险自查。

GeekNews等技术社区对其支持146款AI组件、2000余条CVE规则以及多智能体评估能力给予了广泛关注。但对于安全运维与架构设计人员而言，相较于简单的规则统计数量，更应理性剖析其五个检测层级的具体判定机制、检测盲区以及安全部署该工具的前提条件。

AI-Infra-Guard五层检测体系与诊断覆盖面

AI-Infra-Guard的技术架构将AI系统剖析为五个相互独立的检测层级，分别为每个层级配置了专用的检测引擎与输入规范。官方文档定义的核心能力涵盖：基础设施脆弱性扫描、MCP服务器代码审计、智能体技能安全检测、智能体运行时失控评估，以及大模型越狱与API黑盒审计。

下表依据项目官方文档，整理了五个检测层级对应的检测机制、验证内容及固有技术边界：

检测层级官方文档功能说明实际核验内容无法核验内容 (局限性)
1. AI基础设施扫描基于活跃服务地址扫描已知CVE漏洞指纹识别并匹配2000+条已知CVE规则未收录的零日漏洞及业务级非标配置失误
2. MCP服务器审计针对GitHub地址或源码包执行静态检测工具投毒特征、硬编码凭据、命令注入隐患运行期由动态外部输入触发的隐蔽越权
3. 智能体技能审计基于SkillTrustBench T01-T09进行代码审计字节码伪装规避、本地权限提升特征代码复杂长文本交互场景下的深层逻辑漏洞
4. 智能体运行时审计评估Dify、Coze等工作流下的多智能体执行智能体控制权丧失、工具滥用、数据外发针对全部不可信提示词组合的绝对安全保证
5. 越狱与API审计对抗性越狱测试与API黑盒多探针审计基准测试越狱防御率、模型中继串换痕迹评估数据集未覆盖的全新变种对抗策略

如表格所示，各层级均有特定的检测切入点，某单一层级的合规无法推导得出全系统的绝对安全。底层模型服务器无CVE漏洞并不代表上层MCP工具具备安全性，而模型本体具备较高的越狱防御能力也无法杜绝智能体在复杂流程中产生工具滥用风险。

第一层: 运行中AI服务指纹识别与已知CVE比对

第一层AI Infra Scan聚焦于局域网内处于监听状态的推理引擎与编排平台。运维人员输入目标服务的IP地址与端口(如Ollama的11434、vLLM的8000、ComfyUI的8188等)，扫描引擎通过抓取HTTP响应头、特征端点状态以及协议交互特征，识别目标组件的具体类型与软件版本。

  • 支持组件范围。 截至v4.6.0版本，已支持包括vLLM、Ollama、ComfyUI、n8n、LangFlow、llama-cpp、MLflow在内的146款主流AI基础设施组件。
  • 漏洞指纹比对。 将识别出的软件版本号与内置的2000多条CVE规则库进行交叉对照，判断当前部署是否存在已公开的安全漏洞。
  • 非侵入式探测。 探测机制属于基于元数据与特征指纹的无害化核对，不向目标发送破坏性攻击载荷。
  • 网络扫描安全提醒。 若采用网段扫描模式，高频的特征探测请求可能引发生产推理节点的性能抖动，实操中应严格限定在测试环境内执行。

该层级的局限性在于其完全依赖已知CVE知识库。由源码自行编译的非标版本、未公开漏洞细节的零日风险或错误的访问控制权限，均无法单纯通过版本号比对加以发现。

第二与三层: MCP服务器与智能体技能源代码静态审计

第二层与第三层检测针对连接模型与外部执行环境的扩展工具代码。由于Model Context Protocol(MCP)服务及Agent Skill通常被赋予执行本地命令、读取敏感文件或访问内部API的特权，其源代码质量直接关系到系统边界的安全。

  • 审计输入形式。 无需连接运行中的网络服务，直接以远程GitHub仓库URL或本地源码压缩包作为静态分析输入源。
  • 特征代码扫描。 深度检查源码中硬编码的API密钥、凭据泄露风险、系统命令注入隐患，以及通过编译后的.pyc字节码规避静态检查的特征行为。
  • SkillTrustBench规范映射。 检测结果全面对齐腾讯朱雀实验室建立的SkillTrustBench规范体系，覆盖从T01到T09的9大类风险(包括工具投毒、权限提升、未经授权的网络数据外传等)。
  • CI/CD自动化集成。 除Web控制台外，项目提供了独立的CLI工具aig-skill-scan(已发布至PyPI)及mcp-scan，支持嵌入到代码提交与持续集成流水线中进行阻断性审计。

静态代码分析同样存在原理上的盲区，对于高动态反射调用、运行期从外部动态下载加载的脚本，以及完全由自然语言提示词诱导产生的间接注入攻击，静态规则无法做到完全穷尽。

第四与五层: 智能体工作流运行期审计与大模型越狱·后门评估

第四层与第五层深入至模型在处理动态用户输入时的运行时交互阶段，评估自主系统的鲁棒性与合规边界。

  • 智能体失控模拟审计(Agent Scan)。 针对Dify、Coze等多智能体平台，评估多智能体任务交接(Handoff)过程中的越权风险。依托RogueHandoff-20与FORGE-Bench(arXiv:2609.11024)学术基准，模拟在特定任务压力下智能体是否会偏离设定约束，调用未授权工具或外泄会话上下文。
  • 对抗性越狱评测(Jailbreak Evaluation)。 接入目标LLM的API端点，利用Many-Shot、PAIR、GOAT、ActorAttack等学术界已公布的对抗测试集执行自动化压力测试，量化安全机制被突破的比例。
  • 模型API黑盒防篡改审计(Model & API Checker)。 针对第三方中继代理，利用多轮特定指纹探测提示词分析模型输出分布，以黑盒方式辨别中继服务是否存在以低价模型冒充高阶模型、或在中间层植入后门应答的异常迹象。

动态评测能够呈现特定基准下的相对防守水准，但高分表现不代表能抵御未来所有新型提示词对抗策略。关于智能体权限边界与漏洞利用能力的通用技术剖析，可参阅Anthropic GLM-5.3漏洞利用能力分析 2026。

系统架构、独立CLI组件及标准化部署流程

AI-Infra-Guard采用了平台化Web控制台与轻量化独立CLI相分离的工程架构，便于技术团队根据自身IT自动化成熟度灵活选型。

下表梳理了各主要模块的部署形态、目标输入与实务运维注意事项：

组件模块部署与运行形式目标输入格式安全运维要点
A.I.G 综合控制台Docker Compose容器化集群Web界面支持IP、URL及文件上传缺乏身份验证，严禁公网暴露
aig-skill-scanpip独立的Python命令行工具本地项目目录及大模型API密钥流水线环境变量中做好API密钥加密

agent-scan容器化多智能体测试工具智能体平台API与编排描述文件必须在隔离沙箱环境中执行模拟测试
api-checkerGo编写的CLI与REST后端目标模型API地址与鉴权Token防止测试探测请求外泄内部敏感信息

平台主体的标准容器化部署遵循官方推荐的Docker Compose流程：

                    cd AI-Infra-Guard

容器完成启动后，本地8088端口将开放Web图形界面及基于Swagger规范的API交互文档(/docs/index.html)。

「缺乏内置鉴权」安全警示与企业内网严格隔离原则

引入该自查平台的安全工程师必须严肃对待官方README在安装文档中特别标注的安全警示：

Note: The AI-Infra-Guard project is positioned as an AI red teaming platform for internal use by enterprises or individuals. It currently lacks an authentication mechanism and should not be deployed on public networks.

官方文档明确指出，该平台目前未集成用户鉴权、会话管理或细粒度访问控制功能。若将该Web服务直接映射到公网IP或开放互联网环境中，将带来严重的安全隐患：

  • 自查工具被反向利用。 未经身份验证的外部黑客可随意访问控制台，利用其扫描功能针对内网其他节点或第三方服务器发起无差别探测。
  • 内部资产拓扑外泄。 平台存储的内网AI服务地址、开放端口清单及详细的CVE脆弱性报告将处于完全裸露状态。
  • 模型凭据被盗用。 管理员在越狱评测与API检测中配置的企业商用LLM API Token，可能在无保护界面中被直接读取外泄。
  • 强制内部网络隔离。 该服务必须严格限制在企业内网专区、私有VPC或仅限管理员登录的Jump Server后运行；如需远程访问，必须在外层前置反向代理，强制要求mTLS双向认证或接入企业统一SSO鉴权体系。

此外，作为安全自查的基本法理底线，任何使用该工具开展的漏洞扫描与越狱评估，必须严格限定在已获得书面授权的自有基础设施与资产范围内。未经授权对第三方网络服务执行扫描探测属于违法违规行为。

蓝队防御视角下的检测效用与技术盲区

从蓝队(防御方)的实际工作出发，此类自动化自查平台最大的价值在于帮助运维团队建立起AI资产的集中可视性，快速消除明显的低级安全疏漏。关于智能体在登录浏览器等高权环境下的防护设计，可参阅Tencent BrowserSkill分析 — 登录状态浏览器移交智能体的架构与权限边界 2026，其核心同样在于严格划定操作特权。

然而，若将企业AI安全的防线单纯寄托于扫描工具的报表，将面临以下技术盲区：

  • 规则库的时效性滞后。 尽管目前覆盖了146款组件和2000条CVE，但开源AI工具迭代频繁，新暴发的依赖风险从被披露到规则入库存在不可避免的时间差。
  • 静态审计的误报与漏报。 纯规则匹配的代码分析无法结合真实业务拓扑，既可能将正常的开发辅助代码误判为风险，也难以捕捉深层混淆后的逻辑旁路。
  • 评测分数的认知误区。 在离线静态数据集上取得的高防护率，不等于系统在面对真实生产环境中千变万化的动态对抗时能够万无一失。
  • 纵深防御的不可替代性。 检测工具仅能提供问题度量，无法代替真正的安全控制；必须同步建设网络微隔离、WAF防护、工具调用的最小权限原则以及模型输出内容过滤机制。
  • 规则资产的持续更新要求。 部署后必须建立定期从上游同步规则目录(data/vuln/、data/mcp/)的维护规程，防止工具因知识库老化而失效。

自动化检测工具应定位为日常安全巡检与基线核查的辅助手段，而真正的系统鲁棒性必须根植于严格的最小权限架构与持续的运行期动态监控。

尚未核实的事项

  • 在线专业版(aigsec.ai)的具体功能差异及邀请码审批标准。官方文档仅注明需邀请码接入，其与开源版在核心检测引擎上的具体差异未予公开。
  • SkillTrustBench基准评测的完整原始评测数据与动态榜单。由于相关子域名数据未在此次核验中直接调取，本文仅采信了文档中收录的T01至T09分类法。
  • 在脱离Docker的非容器化裸机环境(原生Linux或Windows)中编译部署时，Python与Go多语言组件的具体依赖冲突情况。
  • 内置2000余条CVE规则中，属于严重等级(CVSS 9.0以上)的高危漏洞具体占比分布。
  • 针对国外主流公有云托管AI服务(如AWS Bedrock、Google Cloud Vertex AI等)的适配性与远程黑盒检测能力。
