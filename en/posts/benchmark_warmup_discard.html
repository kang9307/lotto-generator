The output is from one run on this PC with Python 3.13.3 (win32) and Node v22.16.0 on Windows 10, and values and verdicts change on the next run. Explanations rest only on runs that change one variable and on the documentation sentences cited below. Neither script writes a file; each only starts itself as a child process, and each takes roughly 10 to 20 seconds.

Introduction - the first number is not the speed of the code

In repeated measurement the first call is often several times to several thousand times slower than the calls after it. Put that value into an average and the result no longer describes the speed of the function; it contains a cost that is paid only once. That cost is not a single thing. Module import, the regular-expression compile cache, lazy initialization in user code and the staged optimization of a JIT compiler differ both in size and in how long they last. How many runs to discard therefore cannot be decided by feel; it has to be read from the per-call times of the same function.

Combining measurements that have already been collected is covered in the percentile aggregation article, and the choice of clock in the monotonic versus wall clock article. The scope here is the step before a measurement exists: from which call onward a timing can be used as a measurement at all.

The questions covered are the following.

  • Can variable-separating runs tell whether a slow first call comes from an import, a regular-expression cache or lazy initialization.
  • What shape do the per-call times take as the same function is called repeatedly.
  • Can code choose the discard count as the point where a moving median becomes stable.
  • How far from the steady-state value are the mean that includes warm-up and the mean taken after discarding.
  • How can a check show whether that judgment can be trusted in an environment where measurements wander.

Timing tools and what the official documents say

The Python timeit documentation states that the default timer is always time.perf_counter(). The same page explains that timeit() temporarily turns off garbage collection during timing, which makes independent timings more comparable, with the drawback that GC may be an important part of the performance being measured. About repeated results it says that calculating and reporting the mean and standard deviation is not very useful, that higher values usually come from other processes interfering with the timing rather than from variability in Python, and that the min() of the result is probably the only number worth looking at.

The clock on the Node side is performance.now() from perf_hooks. MDN describes the method as returning a high-resolution timestamp in milliseconds that represents the time elapsed since timeOrigin. The resolution figures on that page, 5 microseconds in isolated contexts and 100 microseconds otherwise, belong to the browser context of the web document. The Node output below wraps each call in two performance.now() readings.

  • Python: wrap one call in time.perf_counter() and convert to microseconds; use timeit.repeat() for repeated measurement.
  • Node: wrap one call in performance.now() and convert to microseconds; no internal optimizer flags are used.
  • Variable separation: time the first and second call in a fresh process, change exactly one condition, and repeat the same measurement.
  • Judgment: apply a moving median to the per-call times and finish with a stationarity check.

First call in CPython - an experiment that changes one variable at a time

The first part of the code below starts a fresh interpreter process, calls one function twice and prints the first and second call time in microseconds. The parent process runs each of five conditions in seven fresh processes and reports the median. Neighboring conditions differ in exactly one respect.

Three things can be read from the output. First, import_cold and import_warm have the same function body and differ only in whether the module was loaded beforehand. The first call dropped from 13248.8 to 1.8, so on this PC the first-call delay of import_cold was produced by the import inside the function. The Python documentation says that during an import the module name is looked up in sys.modules first and, if present, the stored value satisfies the import and the process completes. The documentation states that the cache exists, and the speed difference is shown by the import_warm and re_precompiled contrast outputs.

Second, re_cold and re_precompiled differ only in whether compilation is inside the timed region. The value fell from 280.7 to 15.7. The re documentation says that compiled versions of the most recent patterns passed to re.compile() and to the module-level matching functions are cached, and that re.purge() clears that cache. Only the first call after the purge paid the compile cost. Third, the 48073.7 of lazy_table is produced by code in the first call that builds a 200,000-entry dictionary, and the second call, which only reuses the table, took 3.6 in the same output.

Some difference remains. The 1.8 against 1.0 of import_warm and the 15.7 against 2.9 of re_precompiled are first-call excesses of a few to a few tens of microseconds. Differences of that size are the subject of the convergence rule in the time-series section below.

A time series in one process - a single spike moves the mean

The second part of the code applies judgment functions to a series of 160 calls of the same function in one process. There are three. settle_index returns the first point at which the moving median with window 5 stays within 25 percent of the steady level (the median of the second half) for 10 consecutive positions. stationary compares the medians of the last two quarters. spike_count counts up to the last call among the first 20 that exceeds three times the steady level.

# ---------- detectors ----------
                    def settle_index(t, w=5, tol=0.25, run=10):
                        """First call index from which run consecutive moving medians (window w)
                        stay within +-tol of the steady level (median of the last half)."""
                        ref = statistics.median(t[len(t) // 2:])
                        mm = [statistics.median(t[i:i + w]) for i in range(len(t) - w + 1)]
                        for i in range(len(mm) - run + 1):
                            if all(abs(m - ref) <= tol * ref for m in mm[i:i + run]):
                                return i, ref
                        return None, ref
                    
                    def stationary(t, tol=0.25):
                        q = len(t) // 4
                        a, b = statistics.median(t[2 * q:3 * q]), statistics.median(t[3 * q:])
                        return abs(a - b) <= tol * b, a, b
                    
                    def spike_count(t, k=3.0, head=20):
                        ref = statistics.median(t[len(t) // 2:])
                        bad = [i for i, x in enumerate(t[:head]) if x > k * ref]
                        return bad[-1] + 1 if bad else 0

                    data = [random.random() for _ in range(2000)]
                    def pure():
                        s = 0.0
                        for x in data: s += x * x
                        return s
                    def lazy_series():
                        import sqlite3
                        return sqlite3.sqlite_version

A mean that includes warm-up therefore does not measure the speed of the function.

Noise hides warm-up - the stationarity check and the timeit minimum

In the B output (one run on this PC) the pure series starts with six calls all in the 421 to 431 microsecond range. The steady level is computed as 151.7 and the settle index is 16. Yet stationary is False: the medians of the last two segments are 205.6 against 53.2 microseconds, almost a factor of four apart. The same code moved from 53 to 431 microseconds within a few seconds in a single process. The output alone cannot say why this PC wandered like that. In the three reruns the first six calls ran from 80 to 323 microseconds and stationary came out False, True and False.

In that case a settle index of 16 is not evidence of warm-up. For a series that fails the stationarity check, the discard computation is not used at all and the measurement is repeated. The D output shows the same function run seven times through timeit.repeat, and the time per repeat of 50 calls scattered from 59.5 to 255.7 microseconds in this run; the minimums of the three reruns were 131.7, 76.8 and 99.7.

First call in Node - per-call time and a bar distribution

The Node script calls a function that allocates 20,000 small objects 1000 times, times each call, and prints the median for call ranges together with log-scaled bars. Started with the argument child, the same file runs one process of 500 calls and prints a single line. The code below also reimplements the two judgment functions with the same definitions as in Python.

                    const { spawnSync } = require('node:child_process');

                      let s = 0, o = { a: 1, b: 2 };

                      return s;
                    }
                    function series(n) {
                      const t = [];
                      for (let i = 0; i < n; i++) {
                        const a = performance.now(); work(20000); t.push((performance.now() - a) * 1000);
                      }
                      return t;

                    const med = a => { const b = [...a].sort((x, y) => x - y); const m = b.length >> 1; return b.length % 2 ? b[m] : (b[m - 1] + b[m]) / 2; };
                    const mean = a => a.reduce((x, y) => x + y, 0) / a.length;
                    function settle(t, w = 5, tol = 0.25, run = 10) {
                      const ref = med(t.slice(t.length >> 1));
                      const mm = [];

                      for (let i = 0; i + run <= mm.length; i++) {

                      return { idx: null, ref };

The output shows that the first call is slow, and this experiment cannot separate the cause.

How many runs to discard - the convergence rule

steady level (median of last half): 282 us
                    settle index (w=5, tol=25%, run=10): 15 -> discard first 15 calls
                    stationary check: true (274 vs 295 us)

In this run the steady level (median of the second half) is 282 microseconds, and the moving-median rule says to discard the first 15 calls. The stationarity check is True, with the last two segments at 274 against 295 microseconds, the same level. This series can be used for the judgment. These values come from one run on this PC.

What matters is that this number is not the same from run to run. In the output below, where the same script ran in five fresh processes in one run on this PC, the judged count came out as 1, 94, 25, 18 and 4. What can be stated is the direction, that the verdict differs greatly from process to process; the specific numbers change with every run. A discard count cannot be fixed from one measurement in one process.

  • Window size: a small window is shaken by single noisy calls and a large one blurs a short warm-up. Here 5 is used.
  • Tolerance: 25 percent of the steady level is used. A band narrower than the normal wobble of the environment never yields a verdict.
  • Run length: the window median must stay inside the band for 10 consecutive positions to count as settled.
  • Steady level: the median of the second half of the series. If the second half is still falling, this reference itself is wrong.

A practical procedure - the order for choosing the discard count

The rules obtained from the runs above fall into the following order. Each item rests on the output of an earlier section, except the larger-value rule, which is this article proposal.

  • Record the time of every call in a fresh process, and read the code first to see whether an import, a compile or an initialization sits inside the timed region.
  • Isolate each suspected cost by changing one condition: preloading the module and precompiling the pattern are the examples here.
  • Make the series long enough (160 to 1000 calls here), and cut the repeat count so the total run time stays around 10 seconds.
  • Run the stationarity check first. If it fails, hold the warm-up judgment, quiet the environment and measure again.
  • Obtain the settle point with the moving median, and count single spikes separately with a per-call check.
  • Run several fresh processes and compare their settle points. Using the larger one as the discard count is a rule this article proposes and has no documentation behind it; the evidence goes only as far as the verdicts differing (1 to 94 in one run on this PC).
  • Report the median, the minimum and the spread over the retained part together, never the mean alone.
  • State the environment in the report; every value shown here belongs to Windows 10, Python 3.13.3 and Node v22.16.0 on this PC.

What Could Not Be Verified

  • Causation of the slow first Node call by JIT tier changes. The V8 blog sentence and the output agree in direction, but no control run turned the JIT off.
  • The cause of the pure series moving from 53 to 431 microseconds inside one process. Whether it is CPU clock, OS scheduling or interpreter internals, and why the verdicts differed between reruns, could not be separated by the output.
  • The cause of the first-call excess that remains in import_warm and re_precompiled (1.8 against 1.0, 15.7 against 2.9).
  • The effect of the OS file cache. Emptying it needs administrator rights, so it was not run.
  • Values on Linux or macOS and on other versions of Python and Node. Only Windows 10 on this PC was used.
  • The resolution that performance.now() actually delivers in Node. The MDN resolution sentence concerns the browser context, and the Node documentation was not opened.
  • Whether the judgment parameters window 5, tolerance 25 percent and run length 10 suit other functions.
  • The difference between GC enabled and disabled. The GC suspension described by the timeit documentation did not apply to the perf_counter measurements used here.
