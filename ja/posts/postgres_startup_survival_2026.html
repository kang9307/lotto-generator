スタートアップのPostgres生存ガイド - コネクション枯渇からパーティショニングまで

コネクションプーリング・インデックス・autovacuum・無停止マイグレーション・バックアップリハーサルまで、実務で実際にぶつかる落とし穴と対処法を整理する

2026-07-24 開発・インフラ

序論: Postgresがスタートアップを何度も驚かせる理由

スタートアップのデータベースは通常、一度に壊れることはない。初期にはPostgres一つで数か月、時には1-2年何の問題もなく耐える。トラフィックがある線を超えた瞬間から話が変わる。デプロイ直後にコネクションが急に枯渇したり、昨日まで正常だったクエリが今日突然5秒かかったり、深夜にautovacuumがCPUを全部使い切ったり、カラム一つを変えるマイグレーションがサービスを丸ごと止めてしまったりする。どれも初めて経験するときは原因を推測しにくく、たいてい事後になって「これは事前に知っておくべきだった」と気づくものだ。

本稿はそうした落とし穴を実務の観点から順に整理した生存ガイドだ。ニュースや新製品紹介ではなく、実際にPostgresを運用しながらぶつかる問題 - コネクション枯渇、インデックス、N+1クエリ、autovacuumと肥大化、ロックと無停止マイグレーション、バックアップと復旧、モニタリング、スケールの順序、マネージド対セルフホスティングの判断 - を概念とコマンドのレベルまで具体的に扱う。正確性のため公式ドキュメントと実務レファレンスを相互確認し、2026年7月時点の情報として整理した。

1. コネクション枯渇 - PgBouncerとコネクションプーリング

スタートアップが最初にぶつかる落とし穴はたいていコネクション枯渇だ。Postgresのデフォルトmax_connectionsは100前後で、バックエンドインスタンスが複数台に増えたり、サーバーレス・オートスケーリング環境でインスタンスごとに別々のコネクションプールを維持すると、あっという間に枯渇する。コネクション一つひとつはPostgres側にプロセスを一つ立てるコストなので、数が増えるほどコンテキストスイッチとメモリの負担も一緒に増える。

1.1 アプリケーションプールだけでは足りない理由

ORMやドライバが提供するコネクションプールはインスタンス一つを基準にしか動かない。インスタンスが10台で各プールサイズを20に設定すると、実際のDBには最大200コネクションが集中しうる。ここにバッチジョブ、管理コンソール、モニタリングエージェントまで加われば、max_connectionsを超えるのは時間の問題だ。アプリケーションの再起動やデプロイ時にコネクションが一気に集中する「コネクションストーム」もよくある障害パターンだ。

1.2 PgBouncerで前段でろ過する

最も実証された解決策は、アプリケーションとPostgresの間にPgBouncerのようなコネクションプーラーを置き、アプリケーションから見えるコネクション数と実際のDBコネクション数を切り離すことだ。トランザクションモード(pool_mode = transaction)を使うと、コネクションをトランザクション単位でだけ短く保持して返却するので、はるかに少ないDBコネクションで多くのアプリケーションコネクションをさばける。

[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
listen_port = 6432
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
reserve_pool_size = 5

1.3 トランザクションモードの落とし穴

トランザクションモードはトランザクションが終わるたびにコネクションを別のクライアントに再割り当てするため、セッション状態を前提とするコードと衝突する。トランザクションで囲まれていないSET文、セッション単位のprepared statement、アドバイザリロックのように「このコネクションはずっと自分だけが使う」という前提を置く機能は、トランザクションモードで予期せぬ動作を起こす。こうした機能を使うコードがあるなら、その経路だけセッションモードに分けるか、コードをトランザクションモードに合わせて直す必要がある。プールサイズはむやみに大きくするより、DBサーバーのCPUコア数を基準にし、クライアント待機時間(cl_waiting、平均待機時間)の指標を見ながら調整するのが安全だ。

2. インデックスの不足と過多 - バランスの取り方

インデックスはスタートアップが最もよく両極端にミスする領域だ。まったく作らないか、習慣的に全カラムに作ってしまうかだ。

2.1 インデックスが無いとき起きること

WHERE、JOIN、ORDER BYでよく登場するカラムにインデックスが無いと、オプティマイザはテーブル全体を走査するシーケンシャルスキャン(Seq Scan)を選ぶ。データが少ないうちは体感できないが、テーブルが数十万-数百万行に育つと、同じクエリが突然数秒かかり始める。この変化はトラフィック増加とともに徐々に訪れるため「ある日突然遅くなった」ように感じるが、実際にはテーブルが臨界点を超えただけだ。

2.2 インデックス過多の代償

逆にインデックスを過剰に張ると、INSERT・UPDATE・DELETEのたびに関連インデックスも一緒に更新せねばならず、書き込み遅延が増えストレージも消費する。特に「念のため」作っておいたインデックスが実際には一度も使われないケースがよくある。pg_stat_user_indexesのidx_scanカラムで実際の使用頻度を確認し、使われていないインデックスは整理するとよい。

SELECT relname AS table_name, indexrelname AS index_name, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY relname;

2.3 複合インデックス設計の原則

複数のカラムを併せて条件にするクエリが多いなら、単一カラムインデックスを複数作るより複合(多カラム)インデックス一つのほうが効率的なことが多い。ここではカラムの順序が重要で、等号(=)条件で使われるカラムを前に、範囲(>、BETWEEN)条件やソートに使われるカラムを後ろに置くのが基本原則だ。新規インデックスは稼働中のテーブルなら必ずCREATE INDEX CONCURRENTLYで作成し、テーブルロックを避けるべきだ。

3. N+1と遅いクエリ - EXPLAIN・pg_stat_statementsで捕まえる

コネクションとインデックスをすべて整えても、アプリケーションコードレベルで発生するN+1クエリは別の問題として残る。

3.1 N+1クエリの見分け方

N+1は、一覧を一つ取得した後、項目ごとに関連データを別クエリで一つずつ取得するパターンだ。ORMを使うとき特によく起きる。この問題はログだけでは気づきにくい。個々のクエリ自体は1ミリ秒未満と速いからだ。しかしpg_stat_statementsで見ると、同じパターンのクエリが短時間に数万回呼び出された痕跡がはっきり現れる。「速いクエリなのに呼び出し回数が異常に多い」がN+1のシグナルだ。

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY calls DESC
LIMIT 20;

3.2 EXPLAIN ANALYZEの読み方

遅いクエリの候補を見つけたら、EXPLAIN (ANALYZE, BUFFERS)で実際の実行計画と所要時間を確認する。計画でSeq Scanが大きなテーブルに現れたり、推定行数(estimate)と実際の行数(actual)が大きくずれていたり、Buffers: shared readの値が大きければ(ディスクI/Oが多いという意味)、チューニングの余地があるというシグナルだ。

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at > now() - interval '7 days';

3.3 総実行時間 vs 平均実行時間

チューニングの優先順位は「最も遅いクエリ」ではなく「総実行時間が最も大きいクエリ」から取り組むほうが効率的だ。1秒のクエリが一度回るより、10ミリ秒のクエリが一日100万回回るほうがDB全体の負荷に大きく寄与することが多い。pg_stat_statementsのtotal_exec_time基準の並べ替えがこの優先順位付けに役立つ。

4. autovacuum・テーブル肥大化(bloat)・トランザクションID周回

スタートアップチームが最も遅く気づく落とし穴だが、放置すると最も深刻な結果につながる領域だ。

4.1 MVCCとデッドタプル

PostgresはMVCC(多版同時実行制御)方式のため、UPDATE・DELETEが既存の行を即座に消さず、以前のバージョン(デッドタプル)として残す。autovacuumが周期的に動いてこのデッドタプルを回収してこそ、テーブルとインデックスが肥大化しない。autovacuumが遅れたり設定がワークロードに合わないと、テーブルサイズが実際のデータよりはるかに大きくなる肥大化(bloat)が蓄積し、同じクエリでもより多くのページを読まねばならず遅くなる。

4.2 テーブル単位のチューニングが正攻法

デフォルトのautovacuum_vacuum_scale_factor(デフォルト20%)は大規模・高頻度書き込みテーブルには緩すぎる。行数が数百万のテーブルで20%変わってからvacuumが動くのでは遅すぎる。autovacuumを丸ごと切るのではなく、問題になっているテーブルだけALTER TABLEで個別設定を下げるのが正攻法だ。

ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit = 2000
);

4.3 トランザクションID周回という崖

PostgresのトランザクションID(XID)は32ビットで、約40億で周回(wraparound)する。古い行バージョンはXIDの年齢が一定の閾値を超える前にfreezeされねばならない。XIDの年齢が約16億を超えると警告ログが積み重なり、18億を超えると強制vacuumがかかり、約20億に近づくとPostgresはデータ破損を防ぐため自ら新規書き込みを拒否し始める。この段階まで行くとサービス全体が止まる深刻な障害になる。track_countsが有効になっていてこそautovacuumが正常に動作するため、この設定を勝手に切らないのが基本だ。次のクエリで各テーブルのXID年齢を定期的に確認する習慣をつけるとよい。

SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY xid_age DESC
LIMIT 10;

5. ロックと無停止マイグレーション

スキーマ変更はスタートアップが繰り返しぶつかる落とし穴だ。初期には何の問題もなく通っていたALTER TABLEが、データが蓄積した後にはサービスを止める事故に変わる。

5.1 どのDDLが危険か

テーブル全体を書き直す必要がある作業 - カラム型の変更、CONCURRENTLY無しのCREATE INDEX、古いPostgresバージョンでのNOT NULL追加 - は、処理時間の間ずっと強いロック(ACCESS EXCLUSIVE)を保持する。このロックがかかっている間、他のクエリは待機列に積み重なり、待機クエリが増えるとコネクションまで一緒に枯渇する連鎖障害に広がる。Postgres 11からはデフォルト値を持つカラム追加が即座に処理されるよう改善されたが(値がカタログに保存され読み取り時に適用)、型変更のようにテーブルを実際に書き直す必要がある作業は依然として重い。

5.2 拡張-収縮(expand-contract)パターン

安全な無停止変更の標準パターンは拡張-収縮だ。①新しいカラムをnullableで追加してデプロイする。②アプリケーションが新旧両方のカラムに二重書き込みするようデプロイする。③バックグラウンドバッチで既存データを新カラムに埋める。④検証後、読み取りを新カラムに切り替える。⑤一定期間問題が無ければ古いカラムを削除する。各段階を独立したデプロイに分けると、一段階が失敗してもロールバックが容易だ。

5.3 セッションタイムアウトとツール

マイグレーションのセッションには常にlock_timeoutとstatement_timeoutを短く設定し、ロック待ちが他のクエリを次々に塞ぐ事態を早期に断ち切るべきだ。大規模テーブルのオンライン再構成にはpg_repack(短いロックでテーブルをシャドウコピーしてからスワップ)やpgrollのような拡張-収縮自動化ツールを検討する価値がある。

SET lock_timeout = '2s';
SET statement_timeout = '5s';
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders (customer_id);

6. バックアップ・PITR・復旧リハーサル

バックアップは作っておくことよりも、復旧が実際にできるかを確認することが核心だ。

6.1 PITRの構成要素

時点復旧(PITR、Point-in-Time Recovery)は、pg_basebackupで作った物理ベースバックアップにWAL(Write-Ahead Log)アーカイブを再生し、事故直前の任意の時点にデータベースを戻す方式だ。誤ってテーブルを削除したり、デプロイのバグでデータが誤って更新されたとき、スナップショット復旧だけでは足りず「その事故が起きる数分前」に正確に戻さねばならない状況で必須だ。

6.2 pgBackRestのようなツール

手動でpg_basebackupとWALアーカイブを管理するより、本番環境ではpgBackRestやWAL-Gのような専用ツールを使うのが標準だ。増分・差分バックアップ、バックアップの暗号化、並列処理、保存期間の管理まで自動化してくれる。

pgbackrest --stanza=mydb --type=full backup
pgbackrest --stanza=mydb --type=diff backup

# 特定時点への復旧
pgbackrest --stanza=mydb --type=time \
  --target="2026-07-24 03:00:00" restore

6.3 復旧リハーサルがバックアップより重要な理由

一度も復旧したことのないバックアップは、成功率が分からないバックアップと同じだ。バックアップそのものではなく「復旧」を成果物として扱うべきだ。四半期に一度でも、実際に別環境で特定時点復旧を最後まで実行しデータ整合性を確認するリハーサルを定期スケジュールに組み込む必要がある。RPO(許容できるデータ損失範囲)とRTO(許容できる復旧所要時間)の目標を先に定め、その目標が実際に達成できるかをリハーサルで検証する順序が正しい。

7. モニタリング指標 - キャッシュヒット率・待機・レプリケーション遅延

障害が起きる前に気づくには、どの数字を見るべきかが重要だ。三つが核心となる。

7.1 キャッシュヒット率

バッファキャッシュヒット率は、読み取り要求のうちディスクではなくメモリ(shared_buffers)で処理された割合だ。一般に99%以上が理想的で、80%を下回るとキャッシュが作業セットより小さいか、クエリが不要なディスクI/Oを引き起こしているというシグナルだ。

SELECT
  sum(heap_blks_hit) / nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0) AS cache_hit_ratio
FROM pg_statio_user_tables;

7.2 コネクション飽和とクエリ待機

現在のコネクション数がmax_connectionsにどれだけ近づいているか、そしてロックを待つクエリがどれだけ積み重なっているかを併せて見る必要がある。待機クエリが増えるのは、先に触れたコネクション枯渇や重いDDLロックが実際に起きているという先行シグナルだ。

7.3 レプリケーション遅延

読み取りレプリカを使っているなら、レプリケーション遅延(replication lag)を必ずモニタリングすべきだ。遅延が大きくなるとレプリカから読み取ったデータが古い状態になりうるし、遅延が大きくなったままプライマリに障害が起きると、フェイルオーバー時のデータ損失幅も一緒に大きくなる。Prometheusのpostgres_exporterとGrafanaの組み合わせでこの三つの指標(キャッシュヒット率、待機、レプリケーション遅延)を一つのダッシュボードに置き、閾値アラートを設定しておくのが実務的に十分だ。

8. スケールの順序 - 垂直からシャーディングまで、順序を飛ばさないこと

トラフィックが増えるとすぐシャーディングを思い浮かべるチームがあるが、実務では順序を守るほうが圧倒的に安全で安価だ。

8.1 垂直拡張とコネクション管理が先

最初に試すべきはインスタンス仕様を上げる垂直拡張と、先に触れた設定チューニング、そしてPgBouncerによるコネクション管理だ。ほとんどのスタートアップのトラフィック規模ではこの段階だけでもかなり長く持ちこたえる。

8.2 読み取りレプリカとパーティショニング

読み取り比率が高いならストリーミングレプリケーションで読み取りレプリカを増やし、読み取りトラフィックを分散する。次はパーティショニングだ。大きなテーブル一つを物理的に複数の断片に分け、クエリが必要な断片だけスキャンするようにする。時系列データには日付基準のRANGEパーティショニングが、書き込みを均等に分散したいときはテナントIDやユーザーID基準のHASHパーティショニングが適している。

8.3 シャーディングは本当に最後

シャーディング(複数の独立DBノードへデータを分散)は、アプリケーションがどのシャードにデータがあるかを知る必要がある構造的複雑さを持ち込む最後の手段だ。プライマリノードのCPU・I/Oがチューニング後も70%を超え続ける、最大テーブルが数百GB以上でストレージ増加速度が追いつかない、テナント別のデータ隔離が要件である、バックアップ・復旧の所要時間自体が耐えられない水準である、といったシグナルが出て初めて検討対象になる。これらのシグナルが現れる前からシャーディングを設計するのは、たいてい過剰設計だ。

9. マネージド(RDS・Supabase・Neon) vs セルフホスティングの判断

この判断は技術よりチームの状況に左右される。

9.1 マネージドが有利な場合

DB運用専任の人員がいない初期スタートアップなら、バックアップ、フェイルオーバー、パッチ、モニタリングを代わりに処理してくれるマネージドサービスから始めるほうが失敗コストを減らせる。NeonとSupabaseはサーバーレス課金とブランチ(開発用DBを瞬時に複製)機能で初期開発速度に強みがあり、RDSはAWSエコシステム統合と長く実証された運用ツールが強みだ。

9.2 セルフホスティングが有利な場合

コスト最適化が重要で、チームにPatroniのようなHA構成、pgBackRestバックアップ、自前のモニタリングを直接運用する能力があるなら、セルフホスティングは同スペック比ではるかに安価になりうる。ただしこの節約は運用負担をチームが代わりに背負うことと引き換えであることを明確に認識すべきだ。

9.3 どちらを選んでも守るべき原則

どちらを選ぶにせよ、最初から特定ベンダーの独自拡張や非標準機能に深く依存せず、標準Postgres互換性を維持することが重要だ。そうすれば、トラフィックが大きくなり切り替えが必要になったときも、移行コストが書き直しではなく設定変更程度で済む。

10. 初期にやっておくとよいこと - チェックリスト

ここまで扱った内容を初期セットアップの時点で押さえられるチェックリストとして整理する。

  • PgBouncerを最初からアプリケーションとDBの間に置く。トラフィックが小さいうちから付けておけば、後で急いで導入する必要が無い。
  • pg_stat_statements拡張を最初から有効化する。問題が起きた後で有効にすると、まさに必要な時点のデータが無い。
  • 大規模・高頻度書き込みテーブルの候補(イベントログ、セッションなど)は、あらかじめautovacuumのテーブル単位設定を計画しておく。
  • スキーマ変更は最初から拡張-収縮パターンとCREATE INDEX CONCURRENTLYを基本ワークフローとする。
  • PITRが可能なバックアップ体系(pgBackRestなど)を初期に構築し、復旧リハーサルをカレンダーに定期スケジュールとして入れる。
  • キャッシュヒット率・コネクション飽和・レプリケーション遅延の三指標を一つのダッシュボードに集め、閾値アラートを設定する。
  • RPO・RTOの目標を先に文書で定義し、マネージドかセルフホスティングかをその目標とチームの能力に合わせて決める。
  • 大量の時系列・イベントテーブルは最初からパーティショニング可能なスキーマ(日付カラムなど)で設計し、後で無停止でパーティションを導入しやすくしておく。

結論

Postgresがスタートアップを驚かせるポイントはおおむね似通っている。コネクションが前触れなく尽き、インデックスが無いか過剰なまま放置され、autovacuumが遅れて肥大化が積み重なり、スキーマ変更が予期せぬロックを引き起こし、バックアップはあるのに復旧はしたことが無い。本稿で扱った項目はどれも、事前に知って備えておけばコストは大きくないが、事故が起きた後で学ぶとダウンタイムと信頼の喪失という代償を払うことになる。今チームのPostgresがこのチェックリストのうちいくつをすでに備えているかを点検することが、今日できる最も実用的な次の一歩だ。
