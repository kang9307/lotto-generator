远程 URL 里嵌着令牌 - git 凭据泄漏的地方

不是删掉文件就完事。用实际输出确认六个位置，并定下事故之后的顺序

2026年9月1日 开发/基础设施

讲凭据泄漏的文章，大多从已提交的文件开始，也在已提交的文件那里结束。不小心把 .env 提交进去了，从历史里抠出来，完事。可真要数一数实际工作中令牌往外走的路径，文件只是六条里的一条。剩下五条，文件管得再好也拦不住。

最常出事的地方是远程 URL。哪天赶时间，用 https://用户:令牌@主机/... 的形式克隆了一次，那串字符就以明文赖在仓库的配置文件里，此后每敲一次 git remote -v 就重新出现在屏幕上。屏幕共享的时候会出现，粘贴出去的日志里也会出现。

下面把这六个位置逐个过一遍，每一处都附上实际执行后确认的输出。最后再整理最重要的东西，也就是已经泄漏之后的顺序。在那个顺序里，删文件不是第一步。

本文所有例子只用明显是假的值和不存在的主机(.invalid)。实验是在临时目录里另设 HOME 隔离着跑的，贴出来的输出只把主目录路径缩成了 ~。这里讲的不是攻击手法，而是检查自己环境的方法。

泄漏的地方不只是文件

先画一张地图。下面六处的性质各不相同。有的在仓库里面，有的在仓库外面；有的自己动手就能删掉，有的在别人的服务器上。这张表要说的是，每一处的防法都不一样。

泄漏的地方留在哪里能不能自己删掉怎么防
已提交的文件提交对象，以及克隆出去的每一份副本重写也管不到别人的副本在提交前拦住，忽略规则要先放好
远程 URL 里的令牌.git/config，以及每一次屏幕输出可以，值会被整体替换用 set-url 换成不带凭据的 URL
.git/config工作目录里的明文文件可以交给助手，不要放进 URL
shell 历史主目录下的历史文件可以，但很容易忘不要把机密放在命令行上
CI 日志CI 服务商的服务器取决于他们的保留策略不要打开跟踪输出
提交信息和工单提交对象、reflog、工单服务器reflog 可以，服务器是另一回事粘贴之前先读一遍

本文把最多篇幅放在第二行和第三行。第一行，也就是把已经被跟踪的文件摘出来的步骤，在「后加忽略规则也摘不掉已被跟踪的文件」那篇里单独讲过。那篇的结论正是这里的起点。摘掉之后历史里还在，所以先换密钥。

确认过的环境

下面的输出全都是实际跑出来的，没有一行是编的。只是因为用了假令牌和不存在的主机，需要联网的命令会停在域名解析这一步。这反倒方便，正好能干净地只看到凭据在连接之前就已经被记录到哪里。

  • git — 2.48.1.windows.1
  • shell — GNU bash 5.2.37(1)-release, Git Bash
  • 平台 — MINGW64_NT-10.0-19045 (Windows 10 上的 MSYS 环境)
  • 时点 — 2026年9月
  • 隔离 — 在临时目录里新建仓库，并把 HOME 指到那里面，没有碰真实主目录的配置和凭据文件

如果平台换成 Linux 或 macOS，有两处会不一样：文件权限的显示，以及 OpenSSH 对私钥的权限检查。两处都在各自的小节里点明。

git remote -v 会原样显示令牌

最常见的开头是这样的。交互式认证太麻烦，或者自动化脚本必须自己连上去，于是把令牌塞进 URL 里克隆。是能用。问题在于那个值会留在哪里。

$ git remote add origin "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (fetch)
origin  https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git (push)

$ cat .git/config
[core]
        repositoryformatversion = 0
        filemode = false
        bare = false
        logallrefupdates = true
[remote "origin"]
        url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

$ git config --get remote.origin.url
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

三件事一下子全露出来了。第一，remote -v 不会遮挡令牌，fetch 行和 push 行各出现一次。第二，.git/config 是没有加密的文本文件，令牌就原样躺在里面。第三，git config --get 这种再普通不过的查询命令也会吐出同一个值。

危险不在命令本身，而在这条命令被执行的场合。git remote -v 是出问题时最先敲的命令之一，也就是说，它会在你求助的那一刻、共享屏幕的那一刻、往工单里贴日志的那一刻被执行。令牌往外走所需要的条件，恰好在那时凑齐。

  • 同一个值会跟着备份和同步文件夹走。把工作目录整个备份掉，.git/config 也一起走
  • 登记了多个远程时，它会留在你忘掉的那个上面。upstream 或者老旧的 backup 远程是常见位置
  • 编辑器和 IDE 的仓库信息面板也会读出并显示同一个值

怎么修远程 URL

修的命令本身就一行，用 git remote set-url 换上不带凭据的 URL 即可。值得确认的是旧值是不是真的没了，因为手工改配置文件时，常常会把旧行留成注释，或者复制到别的键上。

$ git remote set-url origin "https://git.example.invalid/demo/demo.git"

$ git remote -v
origin  https://git.example.invalid/demo/demo.git (fetch)
origin  https://git.example.invalid/demo/demo.git (push)

$ cat .git/config
[remote "origin"]
        url = https://git.example.invalid/demo/demo.git
        fetch = +refs/heads/*:refs/remotes/origin/*

# 确认整个 .git 目录里还有没有留着旧值
# (在只做过添加远程和 set-url 的干净仓库里)
$ grep -rl 'ghp_EXAMPLE' .git/
(无输出)

替换得很干净。set-url 会把 url 的值整个换掉，所以旧字符串不会残留，也和提交对象无关。刚添加完远程时搜索会命中 .git/config 一条，set-url 之后一条也搜不到。

不过到这里还不能放心。干净的是仓库里面，那个令牌并没有变干净。如果你在命令行上敲过那个 URL，它就在 shell 历史里；如果 CI 用过，它可能在日志里。要是拿不准这个值走到了哪一步，那就先吊销，再清理。

  • 远程有多个就全部确认。git remote -v 会列出所有已登记的远程
  • 有子模块的话，每个子模块的配置都是独立的。.gitmodules 和各个子模块目录要一起看
  • 改完之后要定好认证方式。交给助手是基本做法，自动化场景用 SSH 密钥更合适

凭据助手把什么留在了哪里

不把令牌放进 URL，git 就会去问凭据助手。选择在这里分岔。按官方文档，git 自己带的助手有两个，其余的都是与操作系统的安全存储对接的。

助手放在哪里持续时间是否明文适合的场合
store主目录下的 .git-credentials 文件直到你删掉是几乎没有值得推荐的场合
cache内存，由辅助进程持有你指定的时长不写入磁盘共用机器、短时间的活
对接系统钥匙串操作系统的安全存储与账户绑定否个人工作机的默认选择
直接写进 URL.git/config直到你删掉是没有，本文讲的就是它

store 到底留下什么，自己放一条进去就清楚了。助手的协议很简单，从标准输入接收键和值，所以不联网也能把保存和读取原样复现出来。

$ git config --global credential.helper store

# 按助手协议放入一条假凭据 (不联网)
$ printf 'protocol=https\nhost=git.example.invalid\nusername=demo-user\npassword=ghp_EXAMPLE0000000000000000000000000000\n\n' \
    | git credential-store store

$ stat -c '%a %n' ~/.git-credentials
644 ~/.git-credentials

$ cat ~/.git-credentials
https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid

# 读回来也是一样的
$ printf 'protocol=https\nhost=git.example.invalid\n\n' | git credential-store get
username=demo-user
password=ghp_EXAMPLE0000000000000000000000000000

文件里的一行，就是 https://用户:密码@主机 的形状。也就是说，它和把令牌嵌进远程 URL 的保存格式实际上是一样的，区别只在位置。git 官方文档对这个助手也写着：密码不加密地存在磁盘上，只靠文件系统权限保护；如果这个取舍不可接受，就用 cache，或者去找一个与操作系统安全存储对接的助手。

权限的数字要留意。上面输出里的 644 是在这套 Windows 和 MSYS 环境下 stat 报出来的值。官方文档只说这个文件的权限会设成别的用户读不到，并没有写出具体数字，而 Linux 上是不是同一个值我没有确认。不管哪一边，结论都不变：只要能读到这个文件，就能看到令牌本身。

  • 保存位置优先是主目录下的 .git-credentials，没有的话也会用配置目录下的 git/credentials。把它排除在备份之外比较好
  • 要删的时候不必手工打开文件，给助手传 erase，只有那一条会被摘掉
  • Git for Windows 的系统配置里默认就是 manager。这套环境里一并装上的助手是 cache、store、manager，还有一个选择器
  • 叠着指定多个助手时，git 会依次询问直到拿到答案。要是旧的 store 配置还留着，可能是它先回答

SSH 密钥这边分岔的东西

用 SSH 连接就没有必要把令牌放进 URL，前面的问题大半都消失了。取而代之的是另一处：私钥文件本身。这里分岔的只有一点，就是有没有口令。

# 没有口令能不能打开 (-y 从私钥推导出公钥)
$ ssh-keygen -y -P "" -f ~/.ssh/id_nopass >/dev/null 2>&1 \
    && echo "没有口令" || echo "需要口令"
没有口令

$ ssh-keygen -y -P "" -f ~/.ssh/id_pass >/dev/null 2>&1 \
    && echo "没有口令" || echo "需要口令"
需要口令

# 这台主机实际用的是哪把密钥 (解析配置之后的结果)
$ ssh -G demo | grep -E '^(hostname|user|identityfile)'
user git
hostname git.example.invalid
identityfile ~/.ssh/id_demo

没有口令的密钥，拿到文件的人立刻就能用；有口令的还隔着一层。这个差别只在文件被整个拿走的场合才显出来，比如笔记本丢失或者备份外泄，而那正是真会发生的场合。要是每次都输嫌麻烦，往代理里加载一次就行。

第二条命令更实用。ssh -G 显示的是解析配置文件之后的最终结果。密钥有好几把时，哪台主机用哪把不要靠猜，这样确认更快。

权限也提一句。在这套环境里把私钥改成 644 再尝试连接，OpenSSH 完全没有拿权限说事，直接走到了主机名解析失败。看起来是MSYS 在模拟权限的缘故，Linux 或 macOS 的行为我没有确认。不管怎样，把私钥放成别的用户能读的状态没有任何好处。

凭据范围默认权限寿命使用场合
个人 SSH 密钥该用户能够到的所有仓库该用户的全部权限直到你自己删掉人的工作机
部署密钥一个仓库默认只读，可另行授予写入直到你自己删掉一台服务器、一个仓库
细粒度令牌一个用户或组织，以及你指定的仓库按项目逐条指定默认30天，最长366天或永不过期自动化、外部集成
经典令牌它能够到的组织里的所有仓库粗放的范畴单位可选，一年未使用会自动移除该逐步收缩的地方

部署密钥有用的理由就在这张表里。个人密钥打开的是那个人能够到的所有仓库，而部署密钥只挂在一个仓库上，默认还是只读。在一台服务器只需要拉取一个仓库这种常见的部署结构里，把个人密钥复制进去和专门做一把部署密钥，出事时的波及范围完全不同。

令牌的寿命与范围

如果说前面讲的是不让它泄漏，这一节讲的就是泄漏了也让它小一点。决定泄漏事故大小的，通常不是泄漏本身，而是那份凭据能做什么、有效到什么时候。这两件事在创建令牌的那个界面上就已经定了。

看 2026年9月 时点的 GitHub 文档，细粒度个人访问令牌被限定在单个用户或组织所拥有的资源之内，在这个范围里也只能够到你指定的仓库，权限还是逐项授予的。相比之下，经典令牌以粗放的范畴单位工作，会打开该用户能够到的组织里的所有仓库。同一篇文档写着强烈建议设置过期时间，细粒度令牌默认是30天，最长可选366天或者永不过期。经典令牌的过期时间也是可选的，但一年内没有被使用的令牌会被自动移除。

放到组织层面看，还多一层。组织所有者可以要求细粒度令牌访问组织资源时先获批准，可以限制经典令牌对组织的访问，可以施加最长寿命的策略，还可以审阅并吊销挂到组织上的令牌。这意味着个人创建的令牌不会只停在个人这一层，而从组织这边看，这往往是事故应对时唯一的杠杆。

  • 永不过期不是方便，是负债。换来眼下的省事，代价是把吊销的时点无限期往后推
  • 权限只给现在需要的。事先给得宽，就不会再有收窄的契机
  • 按用途拆分令牌。一把到处用，吊销时就不知道还有什么会跟着停，于是一拖再拖
  • 给令牌起个能看出用途的名字。出事时从列表里挑出来的速度不一样
  • 不要把人用的凭据和自动化用的凭据混在一起。人一离职，自动化就跟着停

在 CI 里泄漏的方式

CI 是凭据经过最多、而且输出会被自动保存的地方。危险就在这个组合上。本地要往上滚才看得到的东西，在 CI 里变成一个链接留着。

最常见的事故是为了调试把跟踪选项打开就忘了关。shell 的 set -x 会在执行前把命令打印出来，而且是把变量展开之后打印。

$ cat ci_demo.sh
#!/bin/bash
set -x
TOKEN="ghp_EXAMPLE0000000000000000000000000000"
git ls-remote "https://x-access-token:${TOKEN}@git.example.invalid/demo/demo.git"

$ bash ci_demo.sh
+ TOKEN=ghp_EXAMPLE0000000000000000000000000000
+ git ls-remote https://x-access-token:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git

赋值那行打一次，使用那行再打一次。装进变量并不会把它藏起来，因为 set -x 的目的本身就是把展开后的值给你看。

那 git 自己的输出呢。结果在这里分岔：错误信息会把凭据抹掉再显示，跟踪输出不会。

# git 自己的错误信息会抹掉凭据部分
$ git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
fatal: unable to access 'https://git.example.invalid/demo/demo.git/': Could not resolve host: git.example.invalid

# 但 GIT_TRACE 不会抹
$ GIT_TRACE=1 git ls-remote "https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git"
trace: built-in: git ls-remote https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
trace: run_command: GIT_DIR=.git git remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...
trace: exec: git-remote-https https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/...

可以看到错误信息里 demo-user:ghp_...@ 这一段被整段拿掉了。反过来，一打开跟踪，同一个 URL 就完整地出现在好几行里。问题解不开而去打开跟踪的那一刻，通常是很急的一刻，而急的那一刻的输出会原样留进 CI 的记录。

很容易觉得有 CI 服务商的掩码就没事，但那个功能是有边界的。GitHub 文档写着，不是机密的敏感值要用另外的指令自己去遮；在讲把大机密当文件处理的绕行办法那一段里，还明确写着已经打印到日志里的机密不会被遮掉。文档也警告说，用命令行传递机密可能会在进程列表里被看到。

  • 掩码是在与登记的字符串完全一致时才生效。把值截开用或者做了编码，同一个值就变成了另一个字符串
  • 所以掩码是安全网，不是设计。首先是压根别把它打印出来
  • 跟踪选项只在需要的那一段打开。放在脚本最上面，整个运行就都在范围里了
  • 凭据不要走命令行参数，改用环境变量或标准输入传递
  • 失败那次运行的日志更危险。成功的日志没人去翻，失败的日志到处贴出去分享
  • 来自复刻的运行默认拿不到机密。想绕开这个限制的配置，正是酿成事故的东西

shell 历史与进程列表

带令牌的命令只要敲过一次，那一行就进了历史文件。这个位置容易被忘，是因为它在仓库外面。仓库收拾得再干净，主目录下的历史文件还是原样留着。

这套环境的 Git Bash 里 HISTCONTROL 没有设置。这个变量里如果有 ignorespace，以空格开头的命令就不会进历史，但这说明它并不是可以当作默认来指望的行为。各个 shell 和发行版都不一样，在自己环境里确认一下更稳妥。

  • 不要把令牌直接敲在命令行上，改用文件或标准输入传进去。历史和进程列表两边一次都避开了
  • 已经敲过了就把那一行从历史里删掉。不过删是第二件事，吊销才是第一件事
  • 远程连接工具如果设置成把会话日志写进文件，那边也有同样的一行。终端记录是常被忘掉的位置

提交信息 - reflog 这第二份副本

有时候值不是写进文件，而是写进了提交信息。本来只是临时记一下试了什么，结果把值也一起抄了进去。文件检查器看不到这个，因为信息不是文件，而是提交对象的一部分。

这里还多一层，就是 reflog。git 会把引用移动的历史另外记在 .git/logs/ 下面，而提交信息的第一行会一起进到那份记录里。也就是说，即使你重写或者回退了提交，还有一份副本留着。

$ git commit --allow-empty -m "oops ghp_EXAMPLE0000000000000000000000000000"

$ grep -rl 'ghp_EXAMPLE' .git/
.git/logs/HEAD
.git/logs/refs/heads/main

$ git reflog --format='%gd %gs' | head -2
HEAD@{0} commit: oops ghp_EXAMPLE0000000000000000000000000000
HEAD@{1} commit (initial): init

# 让 reflog 过期并跑一次清理之后
$ git reflog expire --expire=now --all
$ git gc --prune=now
$ grep -rl 'ghp_EXAMPLE' .git/
(无输出)

本来留在两个文件里，过期加清理之后就消失了。这个实验要学的不是怎么删掉 reflog，而是反过来：把提交修整得让日志看着干净了，仓库里仍可能留着副本。而且这种清理只在自己的仓库里有效。要是已经推送过，服务器和别人的副本里还原封不动。

  • 同理，工单和拉取请求的正文与评论、贴到聊天里的日志，各自都是独立的副本。很多服务即使编辑过也会留下编辑记录
  • 需要把值写进信息的场合实际上不存在。做了什么可以写，用了哪个值不要写
  • 清理命令没法撤销。reflog 也是事故恢复的最后手段，不急的话别随便让它过期

在提交之前拦下来

到这里为止的所有应对，讲的都是已经发生之后。成本便宜得多的是在进去之前拦住。顺序有三步：先放好忽略规则，用钩子检查暂存区，再把剩下的交给自动扫描。

钩子比想象中短。下面这个只看暂存区里新增的行，发现带凭据的 URL 形状或者私钥头部就中断提交。

$ cat .git/hooks/pre-commit
#!/bin/sh
if git diff --cached -U0 \
   | grep -nE '^\+.*(://[^/@[:space:]]+:[^/@[:space:]]+@|-----BEGIN [A-Z ]*PRIVATE KEY-----)'; then
  echo "pre-commit: 暂存区里有看起来像凭据的字符串，中断。" >&2
  exit 1
fi
exit 0

$ git add deploy.conf && git commit -m "add deploy conf"
7:+url = https://demo-user:ghp_EXAMPLE0000000000000000000000000000@git.example.invalid/demo/demo.git
pre-commit: 暂存区里有看起来像凭据的字符串，中断。
$ echo $?
1

# 同一个文件只把凭据去掉之后
$ git add deploy.conf && git commit -m "add deploy conf"
committed OK

它会把命中的行连行号一起显示出来，并以退出码 1 拦住提交。去掉凭据的同一个文件则能通过。

不过局限也很清楚。钩子是按仓库各自放的，克隆时不会跟着走，可以绕过，模式里没有的形状也抓不到。它是减少失误的装置，不是保证。在组织层面，常见做法是服务器端的推送检查配上专门的密钥扫描器，那类工具认得各家服务商的令牌形状，覆盖面比手写的模式宽得多。

  • 忽略规则要在创建文件之前放好。事后再加，已经被跟踪的文件是摘不掉的
  • 配置文件只提交示例版本。会填入真实值的文件从一开始就列进忽略对象
  • 钩子拦下来了，别只改文件就过去。顺手看看那个值是从哪来的
  • 团队要知道存在强行跳过钩子的选项。偷偷拦住的装置会被偷偷绕过
  • 把仓库交给智能体或自动化工具时，压根不把密钥交出去的配置比钩子更靠前

泄漏之后的顺序

这一节是本文最重要的。发现泄漏的那一刻，人们最先做的通常是删文件，因为那是看得见的问题。可它不是第一步。

GitHub 文档也明确写了同样的顺序：要清除的敏感数据如果是密码或令牌这类机密，第一步就该把它吊销或更换，并补充说吊销之后它就不能再用于访问，仅凭这一步问题可能就解决了。理由很简单，整理历史可能要花上几个小时，而这段时间里那个令牌一直有效。

顺序做什么为什么排在这里往后拖会怎样
1立刻吊销该密钥或令牌并重新签发一旦吊销，那个值就不再是钥匙你整理的整段时间里它都有效
2确认这份凭据能做到什么，也就是范围它决定应对的规模不知道该看哪里就去翻日志
3查访问日志和活动记录是否真被用过，结果完全不同过了保留期限就看不到了
4检查别的地方是否也有同一个值同一个令牌塞在好几处很常见只改了一处就以为完事了
5这之后才轮到整理历史它会影响所有协作者赶着做，会弄坏别的东西

第2步很容易跳过，而它决定了应对的规模。泄漏一把只读的部署密钥，和泄漏一个对整个组织有写权限的令牌，之后要做的事完全不同。上一节说的把范围收窄，用处就在这里显出来。

  • 担心吊销会让服务停掉，于是往后拖，而这份担心本身就是把一个令牌用在多处的结果
  • 新令牌不要按旧令牌的权限来建。就借这次事故把范围收窄
  • 留下记录：什么时候、什么东西泄漏到了哪里、吊销了什么
  • 不要一个人下判断。是组织的凭据就有既定的上报路径，晚说通常更糟

为什么只整理历史不够

重写历史看得见的结果很确切，因而给人一种已经解决了的感觉。翻开日志，那个提交不见了。但那个提交可能早就被复制到了好几个地方。

GitHub 文档列出了只重写历史再强制推送时，含敏感数据的提交仍然可达的三个位置：仓库的克隆与复刻、用 SHA-1 哈希直接访问的缓存视图，以及引用该提交的拉取请求。文档还写着，留在复刻里的部分要和复刻的所有者另行协调。

更现实的危险是再污染。同一篇文档是这么写的：同事手里有重写之前的克隆，重写之后照常 pull 再 push，敏感数据就回来了。意思是即使整理完了，团队里一个人的习惯性动作也可能让它变回原样。

  • 公开仓库还要加上抓取和镜像。从公开的那一刻到整理的那一刻之间，什么东西拿走了副本，没有办法知道
  • 内部仓库也会在备份快照和搜索索引里留下副本。不确认保留策略，就说不上已经删掉了
  • 所以整理历史是卫生工作，不是恢复。恢复应该在第1步就已经做完了

私有仓库也要守的理由

一个人用的私有仓库还有没有必要在意，这个反问很自然，风险的量级确实也不一样。问题在于私有这个状态并不是永久的。

  • 可见性设置会变。转成开源，或者作为作品集公开的那一刻，整个历史也一起公开了。那时候会逐条翻看过去提交的人很少
  • 会加协作者。邀请一个人进来的那一刻，那个人拿到的是完整历史。没有只给最近几个提交的办法
  • 备份会去别的地方。把仓库整个打包传到云上，或者搬到另一台机器，.git 也一起走
  • 账户可能出事。一个账户被攻破，这个账户下所有私有仓库就一次性全开了。私有是搭在账户安全上面的状态
  • 机器会换。笔记本更换或者丢失时，工作目录和主目录下的凭据文件是一起动的
  • 工具会读。编辑器扩展、分析工具、智能体都会读工作目录。什么东西去了哪里，每个工具都不一样

归拢起来，私有仓库的安全依赖的是此时此刻的设置，而这些设置在几年里会变好几次。相比之下，进了历史的值原封不动地留着。时间只站在一边。

预防习惯清单

只收了那些不引入新工具也能守住的。顺序按效果大小排。

  • 不要把凭据放进远程 URL。认证交给助手或 SSH 密钥。仅这一条就同时堵住三处
  • 给令牌设过期时间。只要不选永不过期，事故就有了有效期
  • 权限只给现在需要的量。以后再加更好，给宽了的权限没有收窄的契机
  • 按用途拆分凭据。知道吊销时什么会停，才真的会去吊销
  • 服务器上用部署密钥。不要把个人密钥复制进去。只需要读就设成只读
  • 给私钥加口令。文件被整个拿走时，这是唯一剩下的一层
  • 不要把明文保存的助手当默认。选与操作系统安全存储对接的那种
  • 不要常年开着跟踪选项。只在需要的那一段开，用完就关
  • 忽略规则要先于文件建立。顺序一颠倒，跟踪就已经开始了
  • 用钩子检查暂存区。不完美，但最常见的失误能抓住
  • 共享屏幕之前先确认远程 URL。几秒钟的事
  • 定期打开令牌列表看看。把不用的删掉

最后放三行自检用的命令，在仓库里直接粘贴执行即可，一次看三个位置。

# ① 远程 URL 里是否嵌着凭据
git remote -v | grep -E '://[^/@]+@' && echo "远程 URL 里有凭据"

# ② 历史的改动内容里有没有同样的形状
git log --all -p | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

# ③ 提交信息里有没有
git log --all --format='%B' | grep -cE '://[^/@[:space:]]+:[^/@[:space:]]+@'

②和③数的是条数，0 就表示没有那种形状。这个检查只看带用户名和密码的 URL 形状，文件里另外写着的密钥、各家服务商特有的令牌形状都抓不到，那些交给专门的扫描器更合适。仓库大的话，②会花些时间。

小结

凭据泄漏的地方不是已提交的文件这一处，而是六处，其中最常出事的是嵌在远程 URL 里的令牌。那个值以明文坐在 .git/config 里，每敲一次 git remote -v 就重新出现在屏幕上。修它就是 git remote set-url 一行。

让它泄漏了也小一点，是在创建令牌的界面上定的。设过期时间、收窄范围、按用途拆开。

如果已经泄漏，顺序就是全部。吊销、确认范围、查日志，然后才整理历史。删文件是第四件或第五件事。历史重写得再干净，克隆、复刻和缓存里留下的副本也收不回来；只要有一位同事拿着重写之前的克隆 pull 再 push，它就回来了。整理是善后，不是解决。解决在第一行就结束了。

未能确认的部分

  • .git-credentials 文件的权限，是这套 Windows 和 MSYS 环境下 stat 报出来的 644。官方文档只写了权限会设成别的用户读不到，没有写明数字，Linux 上实际会是什么值我没有确认
  • 把私钥留成 644 再尝试连接时，这套环境的 OpenSSH 没有拿权限说事。看起来是 MSYS 在模拟权限的缘故，但同样的状态在 Linux 和 macOS 上怎么处理，我没有确认
  • 错误信息里凭据被抹掉，是针对域名解析失败阶段由 git 自己发出的信息的观察。真实服务器在认证失败时返回的响应正文里装着什么，我没有确认
  • 跟踪输出里 HTTP 通信层的头部遮挡行为，因为没有真正建立连接而无法观察。上面的输出仅限于 GIT_TRACE 的命令执行记录
  • 各家密钥扫描器产品的实际检出率和误报率没有测试。只写了这类工具存在，没有评价任何特定产品
  • GitHub 之外其他托管服务的令牌过期默认值和组织策略没有确认。上面的数字仅限于2026年9月时点的 GitHub 文档
