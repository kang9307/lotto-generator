ヘッダーは確かに送ったのにサーバーで見えない - 名前は大文字小文字を区別しないのにコードは区別する

名前は大文字小文字を無視、データ構造は区別 - そのズレに棲むバグを実行で捕まえる

2026-07-31 開発/インフラ

はじめに: 送ったのは確かなのに受け取った側に無い

連携中の相手チームから連絡が来る。要求ごとに X-Request-Id を入れて送っています。開発者ツールでも確認しました。ところがこちらのサーバーログにはその値が無い。コードを開くとヘッダーを読む行は確かにある。例外も出ない。ステータスコードも200だ。ただ値が無いだけだ。

この状況が特にたちが悪いのは、何も失敗しないからだ。誤字ならエラーが出たはずだし、ネットワークが切れたならタイムアウトしたはずだ。ところがオブジェクトに無いキーを読むのはエラーではない。空の値が静かに返り、その空の値がログに流れ、ログには一行も残らない。数日後に「トレースIDがなぜ記録されないのですか」という質問がまた上がってくる。

原因は仕様とコードの間にある一つのズレだ。この一文がこの記事のすべてだ。

  • HTTPヘッダーの名前は大文字小文字を区別しない。 X-Request-Id と x-request-id と X-REQUEST-ID は同じヘッダーだ。仕様がそう定めている
  • ところがコードがそれを入れるデータ構造は大文字小文字を区別する。オブジェクトのキー、辞書のキー、集合の要素、文字列比較演算子 — すべてが X と x を別物として扱う
  • だから同じであるべき二つの名前がコードの中で別物になる。このズレた場所がバグの棲み処だ

よく出る処方は「小文字で書きましょう」だ。間違いではないが、これは自分が書くコードの中だけで成り立つ規則だ。相手がどの綴りで送るかは自分では決められないし、仕様上相手はどの綴りを使っても間違いではない。だからこの記事は「小文字で書きましょう」で止まらない。名前がどの地点で誰によって書き換えられるのかを実行で一つずつ押さえ、値(value)をなぜ別に扱うべきかまで切り分ける。

実行環境。以下のすべての出力は Windows 10 Pro (10.0.19045) で実際に実行した結果だ。ランタイムは Node.js v22.16.0 (win32) と Python 3.13.3 (win32) で、どちらも標準ライブラリのみを使った。外部パッケージは入れていない。サーバーはすべて 127.0.0.1 の高番号ポート(18080 から)に立て、実行が終われば閉じた。スクリプトはシェル引数やヒアドキュメントではなくすべてファイルに保存して実行した。

測れなかったもの。この環境には商用のリバースプロキシやゲートウェイ製品が入っていない。だから6節の中継は自作の最小プロキシであり、特定製品の動作を一般化したものではない。またHTTP/2の名前規則についての仕様原文は開けなかった。だから5節は実測結果のみで述べ、条文の引用はしない。HTTP/3はこの環境に実装が無くまったく測れていない。

この記事が扱わないもの。どのセキュリティヘッダーをどの値で有効にするかはWebセキュリティ基礎で扱った。リバースプロキシ自体の設定はリバースプロキシ構成にある。ここではヘッダー名という文字列が層を越えながらどう変形するかだけを見る。

1. 再現 - 送った名前と保存されたキーが違う

まず問題を目で見る。バイトを正確に制御するため、クライアントはライブラリを使わずソケットに直接要求行を書き込んだ。サーバーは標準ライブラリの既定HTTPサーバーだ。

node v22.16.0 / win32
server listening on 127.0.0.1:18080

--- 1-0. exact bytes the client sent ---
"GET /order HTTP/1.1\r\nHost: 127.0.0.1:18080\r\nX-Request-Id: req-4821\r\nContent-Type: application/json\r\nACCEPT: */*\r\nConnection: close\r\n\r\n"

--- 1-1. what the server code tried ---
req.headers['X-Request-Id'] : undefined
req.headers['x-request-id'] : req-4821
req.headers['X-REQUEST-ID'] : undefined

--- 1-2. the keys actually stored in req.headers ---
  key=[host]  value=[127.0.0.1:18080]
  key=[x-request-id]  value=[req-4821]
  key=[content-type]  value=[application/json]
  key=[accept]  value=[*/*]
  key=[connection]  value=[close]

三行がすべてを語る。クライアントは X-Request-Id と書いて送り、値はサーバーに無事到着した。ところが X-Request-Id で探すと無いと出て、x-request-id で探して初めて出る。保存されたキー一覧を見れば理由は明らかだ。すべての名前が小文字に書き換えられている。

三行目も注目に値する。すべて大文字で探しても無い。つまり「大文字小文字をどうにか合わせればよい」ではなく「正確に小文字でなければならない」ということだ。この辞書で有効な綴りはただ一つだ。

クライアントが送った ACCEPT も同じく accept になっている。この正規化は特定のヘッダーだけに適用されるのではなく、すべてにかかる。

2. ランタイムが名前を書き換える - 元の綴りはどこへ行ったか

では元の綴りは完全に消えたのか。同じ要求をもう少し掘ると面白いものが出てくる。

--- 1-3. req.rawHeaders keeps the bytes as they arrived ---
  raw[0]=[Host]  raw[1]=[127.0.0.1:18080]
  raw[2]=[X-Request-Id]  raw[3]=[req-4821]
  raw[4]=[Content-Type]  raw[5]=[application/json]
  raw[6]=[ACCEPT]  raw[7]=[*/*]
  raw[8]=[Connection]  raw[9]=[close]

--- 1-4. lookup by property vs by normalized key ---
  direct  req.headers[X-Request-Id]            : undefined
  normalized req.headers[x-request-id] : req-4821
  Object.hasOwn(req.headers, X-Request-Id)  : false
  Object.hasOwn(req.headers, x-request-id)  : true

正規化された辞書の隣に到着順そのままの名前と値を並べた配列が別にある。ここには X-Request-Id も ACCEPT も送られた綴りのまま残っている。偶数位置が名前、奇数位置が値だ。

この事実は二つを教えてくれる。第一に、ランタイムは情報を捨てたのではなく片側だけを正規化したということだ。利便性のために小文字辞書を作りつつ、原本も残しておいた。第二に、だから「相手がどの綴りで送ったか」を調べることが可能だ。連携の問題をデバッグするときはこの配列をそのまま出力するのが最も速い確認方法だ。

ただしここに大きな但し書きが付く。この原本配列は直結でのみ信頼できる。6節で見るように中継が一つ挟まるだけでこの配列の中身がまるごと変わる。

2.1 値の有無を確かめる方法も同じく外れる

  • 存在確認も同じ罠にはまる。所有属性の検査を X-Request-Id でかけると偽、x-request-id でかけると真だった
  • だから「ヘッダーがあればA、無ければB」式の分岐が常にBにだけ流れる。値が来ているのに来ていないと判断する
  • この分岐が認証や権限に絡んでいると機能がまるごと死ぬ。逆に「無ければ通過」の形なら検査がまるごと無力化される
  • テストコードが同じ綴りを使えばテストも一緒に間違う。テストは通るのに実環境でだけ動かない典型的な形だ
  • 最も悪い組み合わせはテストクライアントが小文字で送り、実際のクライアントが大文字で送る場合だ。このときは方向が逆なので原因の推定にさらに時間がかかる

3. 送る側は保たれる - wire上の名前

受ける側が正規化するなら送る側はどうか。応答ヘッダーをわざと大文字と小文字を混ぜて入れ、クライアントのソケットに実際に届いたバイトをそのまま出力した。

--- 1-5. res.getHeader is case-insensitive (Node normalizes the lookup) ---
  res.getHeader('X-Trace-Id')  : trace-9f2c
  res.getHeader('x-trace-id')  : trace-9f2c
  res.getHeader('X-TRACE-ID')  : trace-9f2c
  res.getHeaderNames()         : ["x-trace-id","x-lower-name","content-type"]

--- 1-6. exact bytes that came back (wire) ---
  |HTTP/1.1 200 OK
  |X-Trace-Id: trace-9f2c
  |x-lower-name: set-in-lowercase
  |Content-Type: text/plain
  |Date: Thu, 30 Jul 2026 20:22:49 GMT
  |Connection: close
  |Content-Length: 3

ここで同じランタイムが二つの異なる方針を使っていることが明らかになる。

  • 応答ヘッダーの取得は大文字小文字を無視する。三種類の綴りすべてが同じ値を返した。要求ヘッダーはそうではなかったのに応答ヘッダーはそうだ
  • 名前一覧は小文字で返る。内部の保存が小文字キーだという意味だ
  • ところが実際に出ていったバイトは自分が書いた綴りのままだ。 X-Trace-Id は大文字で、x-lower-name は小文字で出ていった
  • 整理すると内部の索引は小文字、出力の表記は原本だ。二つの層が別々に管理される

同じコードで取得の一方は大文字小文字を区別し、もう一方は区別しないという事実が、この問題がなぜ記憶では解決しないのかを説明する。規則がAPIごとに違う。

3.1 クライアント三種類がwireに書いた名前

送る側をさらに確かめた。何も解釈せずバイトだけを記録するTCP受信機を立て、三種類のクライアントで同じヘッダー三つを送った。

node v22.16.0 / win32
raw TCP sink on 127.0.0.1:18087 (records bytes, never parses them)

--- 7-1. A. node http.request ---
  request line   : GET /a HTTP/1.1
  names on wire  : ["X-Request-Id","X-API-Key","Accept-Language","Host","Connection"]

--- 7-2. B. global fetch (undici) ---
  request line   : GET /b HTTP/1.1
  names on wire  : ["host","connection","X-Request-Id","X-API-Key","Accept-Language","accept","sec-fetch-mode","user-agent","accept-encoding"]

--- 7-3. C. hand-written bytes ---
  request line   : GET /c HTTP/1.1
  names on wire  : ["Host","X-Request-Id","X-API-Key","Accept-Language","Connection"]

--- 7-4. the same three names, side by side ---
  client                    x-request-id      x-api-key         accept-language
  A. node http.request      X-Request-Id      X-API-Key         Accept-Language
  B. global fetch (undici)  X-Request-Id      X-API-Key         Accept-Language
  C. hand-written bytes     X-Request-Id      X-API-Key         Accept-Language

結果は予想と少し違った。三つのクライアントすべてが自分の書いた綴りをそのままwireに載せた。標準準拠のヘッダーオブジェクトを使う二番目のクライアントさえ、利用者が指定したヘッダーの綴りには手を付けなかった。

代わりに二番目のクライアントの一覧では別のものが見える。ライブラリが自分で付けたヘッダーはすべて小文字だ。利用者が渡したものは原本、自分が作ったものは小文字だ。だから一つのメッセージの中に二つの表記が混ざって出ていく。

  • この混在は仕様上まったく問題がない。受ける側が名前を大文字小文字無視で扱えばよいからだ
  • しかし「うちのクライアントは小文字で送るからサーバーも小文字だけ見ればよい」という仮定はここで崩れる。利用者が指定したヘッダーは小文字ではなかった
  • つまりwireの綴りを根拠にどんな判断もしてはならない。それは契約ではなく偶然だ
  • HTTP/1.1では送る側の綴りがそのまま流れるという点だけ覚えておけばよい。問題は次の層だ

4. フレームワークごとにデータ構造が違う

ここで言語を変えてみる。同じ要求をPython標準ライブラリのHTTPサーバーで受けた。まったく違う結果が出る。

python 3.13.3 / win32 / Windows 10
--- 2-1. self.headers type ---
  type      : http.client.HTTPMessage

--- 2-2. case-insensitive lookup on the SAME object ---
  headers[X-Request-Id]   -> 'req-4821'
  headers[x-request-id]   -> 'req-4821'
  headers[X-REQUEST-ID]   -> 'req-4821'
  headers[x-ReQuEsT-iD]   -> 'req-4821'

--- 2-3. but the stored names keep the original bytes ---
  key=[Host]  value=[127.0.0.1:18081]
  key=[X-Request-Id]  value=[req-4821]
  key=[ACCEPT]  value=[*/*]
  key=[X-Tag]  value=[alpha]
  key=[x-tag]  value=[beta]
  key=[Connection]  value=[close]

--- 2-4. keys() is NOT normalized, so naive set logic still misses ---
  list(headers.keys())        : ['Host', 'X-Request-Id', 'ACCEPT', 'X-Tag', 'x-tag', 'Connection']
  'x-request-id' in keys      : False
  'X-Request-Id' in keys      : True
  headers.get(x-request-id)   : 'req-4821'
  '__contains__' on the object: True True

--- 2-5. duplicate names collapse differently ---
  get_all(X-Tag)              : ['alpha', 'beta']
  get(X-Tag)   [first only]   : 'alpha'

正反対の設計だ。Python側はヘッダーを普通の辞書ではなくメールメッセージオブジェクトに入れる。そしてそのオブジェクトは取得するときに名前を大文字小文字無視で比較する。四種類の綴りがすべて値を返した。x-ReQuEsT-iD のように混ぜて書いても通る。

同時に保存された名前は原本のままだ。Nodeが小文字辞書と原本配列を別々に置いたところを、Pythonはオブジェクト一つに統合して解決した。この設計のほうが安全に見えるのは事実だ。

4.1 ところがここにも同じ罠がある

安全なのはそのオブジェクトを通して取得するときだけだ。名前一覧を取り出した瞬間にまた普通の文字列一覧になる。

  • 名前一覧を取り出して x-request-id が入っているか見ると偽だ。一覧の要素は原本の綴りだからだ
  • 同じ名前をそのままオブジェクトに問い合わせると真だ。つまり同じデータから答えが二つ出る
  • だから「一覧を巡回しながら絞り込む」コードはPythonでも同じように外れる。言語を変えて解決する問題ではない
  • 重複名の処理も違う。X-Tag と x-tag をそれぞれ送ったところどちらも別項目として保管されつつ、全体を取り出す呼び出しは大文字小文字を無視して二つの値を両方返した
  • 一方、一つだけ取り出す呼び出しは先に来たもの一つだけを返す。後の値が静かに消える

Nodeは同じ状況で違う反応をする。7節で見るように二つの値をカンマでつないだ一つの文字列にしてくれる。仕様は同じ名前の複数行をカンマで結合することを許しており、このランタイムはその選択をした。同じ入力に三つの結果が出るということだ。

層名前の保存方式取得時の大文字小文字原本の綴り重複名
Node 要求ヘッダー辞書すべて小文字に正規化区別する(オブジェクトキー)別配列に保存カンマで結合
Node 原本名前配列到着順そのまま該当なし(配列)そのままそれぞれ保存
Node 応答ヘッダー小文字索引無視する出力時は原本表記上書きする
標準仕様ヘッダーオブジェクト小文字索引無視する一覧は小文字カンマで結合
Python ヘッダーオブジェクト原本の綴りを維持無視するそのままそれぞれ保存
Python 名前一覧原本の綴りの文字列区別する(文字列比較)そのままそれぞれ並ぶ
HTTP/2 転送小文字のみ許容該当なし存在しない転送規則に従う

表を一行にまとめるとこうだ。「取得」を提供する側はおおむね安全で、「一覧」を露出する側はおおむね危険だ。そしてどちらにせよある言語の規則を別の言語に移して適用すると間違う。

5. HTTP/2では大文字がプロトコル違反になる

ここまではHTTP/1.1だった。転送方式を変えると話が変わる。まず普通のクライアントライブラリで大文字の名前を送った。

node v22.16.0 / win32  (http2 module, cleartext h2c)

--- 3-1. client sends the name written as X-Request-Id ---
  request({X-Request-Id}) : accepted by the API (no throw)

--- 3-2. what the HTTP/2 server received ---
  key=[:path]  value=[/order]
  key=[:method]  value=[GET]
  key=[:authority]  value=[127.0.0.1:18082]
  key=[:scheme]  value=[http]
  key=[x-request-id]  value=[req-4821]
  stream.session.alpnProtocol : h2c

--- 3-4. response header names the HTTP/2 client sees ---
  key=[:status]  value=[200]
  key=[x-trace-id]  value=[trace-h2]
  key=[content-type]  value=[text/plain]

三つが目につく。第一に、APIは大文字の名前を受け入れ、例外を投げなかった。第二に、ところがサーバーに届いた名前は小文字だった。第三に、サーバーが大文字で入れた応答ヘッダーもクライアントには小文字で届いた。

つまりライブラリが静かに小文字に変えてくれたのだ。ここでは何の事故も起きない。問題はこの寛容さが本当の規則を隠すという点にある。

5.1 圧縮層に手で大文字を書き込むと

ライブラリを取り除いて確かめた。HTTP/2はヘッダーをそのまま送らず専用の圧縮形式に載せて送る。そのバイトを直接作り、名前に大文字が入ったまま送信した。比較のため同じ要求を小文字でも送った。

node v22.16.0 / win32  (raw HPACK over cleartext h2c)

--- 8-1. field name written as x-request-id (lowercase) ---
  server stream event  : names = [":method",":scheme",":path",":authority","x-request-id"]
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","HEADERS stream=1","DATA stream=1"]
  server saw a stream  : true

--- 8-2. same request, field name written as X-Request-Id ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

--- 8-3. and as ACCEPT ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

結果は明確だ。小文字の名前は正常に処理され応答まで返ってきた。同じ要求で名前の綴りだけを変えると、サーバーはストリームを即座に切りエラーコード1番を返してきた。二番目の事例で名前を ACCEPT に変えても同じだった。

最も重要な行は最後だ。サーバーの要求処理関数が一度も呼ばれなかった。応用コードはこの要求が来た事実すら知らない。

  • つまりHTTP/2で大文字の名前は「値が見えない」問題ではなく「要求が成立しない」問題だ
  • 症状がヘッダー一つが欠けるのではなく接続が切れる形で現れる。だから原因推定の方向がまったく変わる
  • 正常なライブラリを使えばこの状況には出会いにくい。ライブラリが先に小文字に変えてくれるからだ
  • 逆にバイトを直接作ったり、名前の文字列をどこかで組み立てたりするコードがあるとここに引っかかる
  • HTTP/1.1では動いていた連携がHTTP/2に変えた後にだけ壊れる事例の一つの系統がこれだ

測定範囲を明確にする。上の結果はこの環境のHTTP/2実装一つを相手に測ったものだ。仕様原文を開けなかったので「仕様がそう定めている」とは書かない。確認された事実は「この実装は大文字が入った名前を受け取るとストリームをプロトコル違反として切る」までだ。HTTP/3はこの環境に実装が無くまったく測れていない。ただし実務上の指針はどちらにせよ同じだ。名前を小文字に固定すれば三つの転送方式すべてで安全だ。

6. プロキシを一度通ると名前がまるごと変わる

2節で原本の綴りが配列に残っているのを見た。それを信じてよいのか確かめる番だ。最小限の中継サーバーを一つ作った。よく使われる方式そのまま、受けたヘッダー辞書をそのまま次の段へ渡す。

node v22.16.0 / win32
origin on 127.0.0.1:18083   proxy on 127.0.0.1:18084

--- 4-0. field names the client put on the wire ---
  X-Request-Id / X-API-Key / ACCEPT

--- 4-1. DIRECT to origin: names as received ---
  ["Host","X-Request-Id","X-API-Key","ACCEPT","Connection"]

--- 4-2. THROUGH one proxy hop: names as received by the SAME origin ---
  ["host","x-request-id","x-api-key","accept","connection"]

--- 4-3. diff ---
  identical name lists : false

--- 4-4. response names the client sees ---
  direct        : |X-Origin-Marker: origin-1
  through proxy : |x-origin-marker: origin-1

同じクライアント、同じバイト、同じ最終サーバーだ。中継を一段入れただけで届いた名前がすべて小文字に変わった。原本の綴りが残っていたはずの配列の中身まで一緒に変わった。

理由は単純だ。中継コードが渡したのはすでに小文字に正規化された辞書で、次の段へ送るときにその辞書のキーがそのままwireに書かれた。中継はバイトを転送したのではなく、解析した結果を組み立て直したのだ。

応答方向も同じだ。最終サーバーが X-Origin-Marker として付けたヘッダーがクライアントには x-origin-marker で届いた。

  • これはバグではなく中継の正常動作だ。名前は大文字小文字無視なので、どの綴りで書き直しても仕様違反ではない
  • だから原本の綴りに依存するロジックは本番でだけ壊れる。開発環境ではプロキシ無しで直結するからだ
  • 負荷分散器やCDN、サービスメッシュのような中間層はすべてこの位置にある。どれか一つが表記を変えてもおかしくない
  • さらに中間層がHTTP/2で受けてHTTP/1.1へ渡すなら、原本の綴りはそもそも存在しない。5節で見たとおりだ
  • 結論は一つだ。名前の綴りは契約ではない。ヘッダー名を大文字小文字を区別して扱うコードはいつか必ず間違う

7. 静かに外れる比較コード

ここからは実際のコードがどう外れるかを見る。よく使われる三つの形を一つの要求で同時に測定した。

--- 5-1. equality and membership on the NAME ---
  keys                        : ["host","x-request-id","authorization","cookie","x-api-key","content-type","x-tag","connection"]
  seen.includes('X-Request-Id'): false
  seen.includes('x-request-id'): true
  Set built from a written spec: ["X-Request-Id","X-API-Key","Authorization"]
  matched by that Set          : []
  matched after normalizing    : ["x-request-id","authorization","x-api-key"]

--- 5-2. the strip list that does not strip ---
  after delete ['Authorization'] : authorization still present = true
  value that would be forwarded  : Bearer sK9xQz
  cookie still present           : true
  normalized filter -> keys      : ["host","x-request-id","content-type","x-tag","connection"]

最初のブロックが最もよくある形だ。連携ドキュメントに書かれた綴りそのままで名前一覧を作って集合に入れ、届いたヘッダーのうちその集合にあるものだけを選び出す。結果は空の配列だった。三つとも実際に届いていたのに一つも選べなかった。

二番目のブロックのほうが危険だ。外部へ渡す前に機微なヘッダーを消すコードだ。ドキュメントどおりに Authorization と Cookie を消した。ところが実際のキーは小文字だったので削除は何もせず、資格情報がそのまま残った。

この事故の性質。消去が失敗しても機能は正常に動く。要求はきちんと転送され応答もきちんと返る。目に見える症状が一つも無い。だからこの失敗は監視では捕まらない。指標にもログにも現れず、外部呼び出しの要求内容を実際に開いて見るまで分からない。削除リストを扱うコードには「消した後に残っていないか」を確認する検査を併せて置くことが安全だ。

7.1 ログが何も残さない形

--- 5-3. the log line that logs nothing ---
  log ctx rid = {}
  log ctx rid = {"rid":"Req-4821"}
  fallback chain               : Req-4821
  fallback with ?? (nullish)   : MISSING

--- 5-4. WHATWG Headers vs a plain object, same data ---
  Headers.get('X-Request-Id')  : Req-4821
  Headers.get('x-request-id')  : Req-4821
  Headers.has('X-API-KEY')     : true
  [...Headers.keys()]          : ["authorization","content-type","cookie","host","x-api-key","x-request-id","x-tag"]
  plain object same lookups    : undefined / Req-4821

--- 5-6. duplicate names arriving with different casing ---
  x-tag                        : [alpha, beta]

最初の行がこの記事のはじめにをそのまま説明する。ログ文脈オブジェクトに値を入れたところ結果が空のオブジェクトだ。値が空の属性は直列化の過程でキーまでまるごと消えるからだ。

だから画面には「値がおかしい」ではなく「その項目がそもそも無い」と出る。ログを漁る人はその行を見つけられず、自然に「ヘッダーが来ていないのだろう」と結論する。原因と正反対の方向へ調査が流れる地点だ。

  • よくある代替の複数の綴りを並べる方式は値を見つけはする。ただし綴りをいくつ書いてもすべては書けない。応急処置だ
  • 空の値だけを埋めてくれる演算子を使うとかえって悪い。手前の取得が本当に空なのでそのまま代替値へ抜ける。実測ではその位置に代替文字列が出力された
  • 標準仕様のヘッダーオブジェクトを使えば取得は安全だ。どの綴りで問い合わせても値が出て、存在確認も正常だった
  • しかしそのオブジェクトも名前一覧は小文字に正規化して渡す。一覧を原本の綴りと突き合わせるコードはここでも外れる
  • 重複名は大文字小文字を無視して一つに結合された。X-Tag と x-tag でそれぞれ送った二つの値がカンマでつながった一つの文字列になった。4節のPythonの結果とは違う

8. 名前は大文字小文字を無視、値は違う

ここが実務で最もよく混同される地点だ。「HTTPヘッダーは大文字小文字を区別しない」という文を値にまで適用してしまうことだ。確かめてみるとまったくそうではない。

--- 5-5. the NAME is case-insensitive, the VALUE is not ---
  value as received            : [Req-4821]
  rid === 'REQ-4821'           : false
  rid === 'req-4821'           : false
  authorization as received    : [Bearer sK9xQz]
  startsWith('Bearer ')        : true
  startsWith('bearer ')        : false
  token                        : [sK9xQz]
  token.toLowerCase() === token: false   <- lowercasing a value destroys it
  content-type                 : [application/json; charset=UTF-8]
  ct === 'application/json'    : false
  ct.split(;)[0].trim().toLowerCase() : [application/json]

三つの事例がそれぞれ違う教訓をくれる。

  • 識別子の値。届いた値は Req-4821 だった。上下どちらの綴りで比較しても偽だ。値は書かれたとおりが意味なので、正規化すると別の値になる
  • 認証ヘッダー。先頭の方式名の部分は大文字小文字を無視してよいが、後ろの資格情報は一文字までそのままだ。実測では小文字に変えた資格情報は原本と違った。値全体に小文字変換をかけると認証がまるごと壊れる
  • メディア型。値に付いた付加項目まで含めてまるごと比較すると偽だ。実際に必要なのは前半だけを切り出し左右の空白を除いてから比較することだ
  • 整理すると正規化は名前にだけ無条件にかけ、値にはそのヘッダーの定義を確認してからかける
  • 値を扱う関数と名前を扱う関数をそもそも分けておくことが失敗を減らす。一つの関数の中で両方を触るといつか混ざる
対象大文字小文字実測結果正規化備考
ヘッダー名無視四種類の綴りがすべて同じ値常に小文字へアスキーのみ来るので単純変換で十分
トレースIDの値区別上下の綴りとも比較は偽絶対禁止変えると別の値になる
認証方式名無視してよい大文字の接頭のみ真比較するときだけ後ろの資格情報と分けて扱うこと
資格情報の本体区別小文字にすると値が変わる絶対禁止触れた瞬間に認証失敗
メディア型の前半無視してよい付加項目を含む比較は偽前半だけ切り出して付加項目を先に外すこと
付加項目の値項目ごとに違うこの事例は大文字表記で到着定義を確認してから一括変換は禁止
パスとクエリ文字列区別測定範囲外禁止ヘッダーではなく要求対象

9. 安全に読む方法 - 正規化してから取得

是正は簡単だ。取得する側で名前を必ず正規化すればよい。ただし二つを併せて処理して初めて実際に安全になる。

--- 6-1. one getter, every spelling ---
  getHeader(X-Request-Id)    -> "req-4821"
  getHeader(x-request-id)    -> "req-4821"
  getHeader(X-REQUEST-ID)    -> "req-4821"
  getHeader(x-ReQuEsT-iD)    -> "req-4821"
  getHeader(X_Request_Id)    -> undefined

--- 6-2. the prototype trap of a plain-object lookup ---
  Object.getPrototypeOf(h) === null  : false
  naive h['constructor']             : function Object() { [nat
  naive h['toString']                : function
  getHeader(h,'constructor')         : undefined
  getHeader(h,'toString')            : undefined

最初のブロックは期待どおりだ。関数一つで四種類の綴りがすべて同じ値を返した。最後の行は正常だ。下線で書いた名前は実際に別のヘッダーなので値が無いのが正しい。

二番目のブロックがあまり知られていない罠だ。ヘッダー辞書は普通のオブジェクトで上位の原型とつながっている。だから正規化せず名前をそのまま読むと実際には来ていない名前から関数が飛び出す。真か偽かだけを見る検査ならこれが通ってしまう。

  • つまりヘッダー名を外部から受け取った文字列で取得するコードは、値の存在検査が思わぬ結果を出す
  • 安全な取得関数は所有属性かをまず確認してこの経路を塞ぐ。実測では二つの名前とも空の値が出た
  • 取得対象が標準仕様のヘッダーオブジェクトの可能性もあるので、専用の取得メソッドがあればそちらを先に使う分岐を入れると二つの場合を一つの関数で覆える
  • 名前の正規化は単純な小文字変換で十分だ。ヘッダー名に使える文字がアスキーに限られているからだ

9.1 送る側で綴りを混ぜて使うと

--- 6-3. send side: two spellings of one name ---
  after setHeader('X-Tag','first')   : getHeaderNames = ["x-tag"]
  after setHeader('x-tag','second')  : getHeaderNames = ["x-tag"]
  res.getHeader('X-TAG')             : second

--- 6-4. names the runtime refuses outright ---
  setHeader("X Request Id") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id:") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id\n") : ERR_INVALID_HTTP_TOKEN
  setHeader("") : ERR_INVALID_HTTP_TOKEN

--- 6-5. what actually went out on the wire ---
  |HTTP/1.1 200 OK
  |x-tag: second
  |X-Trace-Id: trace-9f2c
  |Content-Type: text/plain

送る側で同じ名前を二種類の綴りで設定した。結果はヘッダーが二つできるのではなく上書きだった。名前一覧には項目が一つだけあり、値は後のものだ。

そしてwireに出た表記は最後に書いた綴りだった。最初に大文字で書いても後で小文字で書き直せば小文字で出る。つまり出力の表記は最後の書き込みが決める。

  • 複数のモジュールが同じヘッダーをそれぞれの綴りで設定するコードベースではどの表記で出るか予測できない
  • 値が上書きだという点も重要だ。二つのモジュールが互いの値を消していることを誰も知らない
  • 空白やコロン、改行が入った名前はランタイムが拒否する。名前の位置に利用者入力をそのまま入れるコードはここで例外で死ぬ
  • 空文字列も拒否される。名前を組み立てて作るコードは組み立て結果が空文字列になる経路を確認する必要がある
  • 拒否が例外として現れるのは幸運なほうだ。この記事の他の事故と違い、少なくとも目に見える

9.2 そのまま持っていける取得関数

// ヘッダー名は大文字小文字を無視。取得する側で正規化する。
// 普通のオブジェクトと標準仕様ヘッダーオブジェクトを一つの関数で覆う。
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}

// 除外リストも併せて正規化する。取得だけ直すのは半分だけ直したことだ。
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
# Python。標準ヘッダーオブジェクトは取得がすでに大文字小文字無視だ。
# 危険なのは名前一覧を取り出して文字列で比較するコードだ。

DROP = {"authorization", "cookie", "x-api-key"}

def get_header(headers, name):
    return headers.get(name)          # 大文字小文字を無視して探してくれる

def forwardable(headers):
    # keys() は原本の綴りなので必ず正規化して比較する
    return {k: v for k, v in headers.items() if k.lower() not in DROP}

# 同じ名前が複数回来ている可能性がある。一つだけ取ると残りが消える
tags = headers.get_all("X-Tag") or []

10. チーム規約と点検リスト

コードを直すだけでは再発を防げない。この問題は人がドキュメントを見て綴りを書き写す地点で何度でも生まれ直すからだ。規約で固定すべきものを整理する。

  • 名前はいつも小文字で書く。連携ドキュメント、コード定数、テスト、ログのキーすべて。見栄えのために大文字を混ぜない
  • 名前の文字列をコードに散らさない。定数一つにまとめておけば綴りが分かれる余地が無くなる
  • ヘッダーを読む通路を一つにする。取得関数だけを使わせ、辞書を直接添字で引くコードはレビューで弾く
  • 除外リストと取得は一緒に直す。取得だけ直すと機微なヘッダーがそのまま流れる側が残る
  • 値には正規化をかけない。値の正規化が必要ならそのヘッダー一つについてだけ、定義を確認してかける
  • テストクライアントはわざと綴りを混ぜて送る。すべて小文字でだけ送るテストはこのバグを絶対に捕まえられない
  • 中間層がある形で一度は試す。直結でだけ試すと6節の変形が見えない
  • 原本の綴りに依存しない。原本配列はデバッグ用でありロジックの入力ではない

10.1 点検リスト

  • ヘッダーを読むすべての場所が正規化してから取得を使っているか
  • 辞書を大文字が入った文字列で直接添字引きする場所が残っていないか
  • 名前を比較演算子で突き合わせたり集合に入れたりするコードが正規化を経ているか
  • 機微なヘッダーの削除リストが正規化された名前になっているか
  • 削除後に実際に残っていないかを確認する検査があるか
  • ログ文脈に入れる値が空なら項目までまるごと消えることを知っているか
  • 存在判定が継承属性のせいで誤って真になる経路を塞いだか
  • 値に一括の小文字変換をかける場所が無いか
  • 資格情報の入った値を比較前に変形していないか
  • メディア型の比較が付加項目を先に外しているか
  • 同じヘッダーが複数回来る可能性を処理したか
  • ヘッダー名の位置に利用者入力がそのまま入る経路が無いか
  • テストが大文字の綴りでも要求を送っているか
  • HTTP/2の経路で名前を直接組み立てるコードが無いか

10.2 やってはいけないこと

  • ドキュメントに書かれた綴りをそのままコードのキーへ書き写すこと — この記事のすべての事故がここから始まる
  • 綴りをいくつも並べて塞ぐこと — すべては書けないので応急処置だ
  • 原本の綴りをロジックの根拠にすること — 中継一度で消える
  • 値に一括正規化をかけること — 資格情報と識別子が壊れる
  • テストを小文字だけで回すこと — 実環境でだけ壊れる
  • 削除リストだけ置いて結果を確認しないこと — 失敗しても症状が無い
  • 「うちは全部小文字で送る」という仮定に頼ること — 相手にその義務は無い

  • RFC 9110 HTTP Semantics, Section 5.5 Field Values (値はフィールドごとの定義に従い、名前のような一括規則が無いという点): rfc-editor.org

# HTTPヘッダー名の大文字小文字 — 安全な取得と点検リスト

> 出典: braindetox.kr — ヘッダーは確かに送ったのにサーバーで見えない
> 根拠: Windows 10 / Node.js v22.16.0 / Python 3.13.3 標準ライブラリ実行検証 (HTTP/1.1 + h2c)

## 0. 大前提 — ズレはどこにあるか

| 層 | 大文字小文字 | 根拠 |
|---|---|---|
| **ヘッダー名** | **無視する** | RFC 9110 5.1 |
| **ヘッダー値** | **区別する** (フィールドごとの定義) | RFC 9110 5.5 |
| コードのオブジェクトキー・集合・文字列比較 | **区別する** | 言語の規則 |

**バグは「大文字小文字を無視する名前」を「大文字小文字を区別するデータ構造」に入れた瞬間に生まれる。**

## 1. 30秒診断 — 値が無いと出たとき

1. 実際に保存されたキーをまるごと出力する (推測しないこと)
2. 小文字の名前でもう一度取得してみる
3. 原本の名前配列があれば併せて出力する (直結でのみ信頼)
4. 中間層があるか確認する — あれば原本の綴りはすでに無い
5. HTTP/2の経路なら名前は必ず小文字だ

## 2. 安全な取得 (JavaScript)

```js
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}
```

- `hasOwnProperty` の確認が**必須**だ。ヘッダー辞書は上位の原型とつながっており、正規化せず読むと来ていない名前から**関数が飛び出す**
- 真か偽かだけを見る検査ならその関数が**通ってしまう**

```js
// 除外リストも正規化。取得だけ直すのは半分だけ直したことだ。
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
```

## 3. 安全な取得 (Python)

```python
DROP = {"authorization", "cookie", "x-api-key"}

def get_header(headers, name):
    return headers.get(name)          # 標準ヘッダーオブジェクトはすでに大文字小文字無視

def forwardable(headers):
    # keys() は原本の綴りだ。必ず正規化して比較する
    return {k: v for k, v in headers.items() if k.lower() not in DROP}

tags = headers.get_all("X-Tag") or []   # 一つだけ取ると残りが消える
```

## 4. 層ごとの動作対照表 (実測)

| 層 | 名前の保存 | 取得の大文字小文字 | 原本の綴り | 重複名 |
|---|---|---|---|---|
| Node 要求ヘッダー辞書 | **小文字に正規化** | **区別** | 別配列に保存 | カンマで結合 |
| Node 原本名前配列 | 到着順そのまま | — | **そのまま** | それぞれ保存 |
| Node 応答ヘッダー | 小文字索引 | **無視** | 出力は原本表記 | 上書きする |
| 標準仕様ヘッダーオブジェクト | 小文字索引 | **無視** | 一覧は小文字 | カンマで結合 |
| Python ヘッダーオブジェクト | 原本の綴りを維持 | **無視** | **そのまま** | それぞれ保存 |
| Python 名前一覧 | 原本の綴りの文字列 | **区別** | そのまま | それぞれ並ぶ |
| HTTP/2 転送 | **小文字のみ** | — | **無し** | 転送規則 |

→ **「取得」を与える側はおおむね安全で、「一覧」を与える側はおおむね危険だ。**

## 5. 名前と値 — 正規化してよいものといけないもの

| 対象 | 正規化 | 理由 |
|---|---|---|
| ヘッダー名 | **常に小文字** | 大文字小文字無視が仕様 |
| トレースIDの値 | **禁止** | 変えると別の値 |
| 認証方式名 | 比較するときだけ | 後ろの資格情報と分離 |
| 資格情報の本体 | **禁止** | 触れると認証失敗 |
| メディア型の前半 | 前半だけ | 付加項目を先に分離 |
| パス・クエリ文字列 | **禁止** | ヘッダーではない |

## 6. 実測で確認された事故の形

- ドキュメントの綴りそのままで作った集合で絞ったら**一つも選べなかった** (すべて届いていた)
- 大文字の綴りで書いた削除リストが**何も消せなかった** → **資格情報がそのまま転送された**
- ログ文脈に空の値を入れたら**項目までまるごと消えて**空のオブジェクトが出力された
- 中継**一段**だけで要求・応答の両方の名前がすべて小文字に変わった
- HTTP/2に大文字の名前を載せたら**ストリームがプロトコル違反で切られた** (応用コードは要求を見てもいない)
- 同じ名前を二つの綴りで設定したらヘッダーが二つではなく**上書きされた**

## 7. 点検リスト

- [ ] ヘッダーを読む**すべての場所**が正規化してから取得を使う
- [ ] 大文字が入った文字列で辞書を**直接添字引き**する場所が無い
- [ ] 名前を比較したり集合に入れたりするコードが**正規化を経る**
- [ ] 機微なヘッダーの**削除リストが正規化された名前**だ
- [ ] 削除後に**残っていないかを確認する検査**がある
- [ ] 存在判定が**継承属性で誤って真**にならない
- [ ] **値に一括の小文字変換**をかける場所が無い
- [ ] 資格情報の値を**比較前に変形しない**
- [ ] メディア型の比較が**付加項目を先に外す**
- [ ] 同じヘッダーが**複数回来る**ことを処理した
- [ ] ヘッダー名の位置に**利用者入力がそのまま**入らない
- [ ] テストが**大文字の綴りでも**要求を送る
- [ ] **中間層がある形**で一度は試した
- [ ] HTTP/2の経路で**名前を直接組み立て**ない

## 8. やってはいけないこと

- ❌ ドキュメントの綴りを**そのままコードのキーへ**書き写すこと — すべての事故の出発点
- ❌ 綴りをいくつも**並べて塞ぐこと** — すべては書けない
- ❌ **原本の綴りをロジックの根拠**にすること — 中継一度で消える
- ❌ 値に**一括正規化**をかけること — 資格情報と識別子が壊れる
- ❌ テストを**小文字だけで**回すこと — 実環境でだけ壊れる
- ❌ 削除リストだけ置いて**結果を確認しないこと** — 失敗しても症状が無い
- ❌ 「うちは全部小文字で送る」という**仮定に頼ること** — 相手にその義務は無い

コピーしてメモアプリやAIツールにそのまま貼り付けてください。
