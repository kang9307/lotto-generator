Papermake与Typst - 自托管PDF服务器能否取代LaTeX与无头浏览器方案

写给必须在服务器端把发票、报表、证明文件转成PDF的从业者: 深入剖析基于Typst的开源文档生成服务器Papermake

2026年7月15日 开发/基础设施

引言: 服务器总有需要吐出PDF的那一刻

订单一完成就得出发票，批处理一结束就得堆出报表，申请一获批就得签发证明，出货一结束就得打印面单。每一个这样的瞬间，服务器上某处都在悄悄运行着一条动态生成PDF的流水线。它不起眼，却不可或缺。截至2026年7月，一个用新角度解决这个老问题的尝试引起了我的注意: Papermake，一个通过REST API渲染Typst模板的自托管开源服务器。本文不止于介绍Papermake本身，而是从实务角度分析: 为何服务器端PDF生成至今仍是个痛点，Typst如何缓解这种痛，以及自托管与商用API该如何取舍。

实务中反复出现的4类PDF需求

  • 发票 - 订单或支付完成后须立即生成，往往还要符合各国电子发票的格式要求。
  • 报表 - 定期批处理一次性渲染成百上千份，版式一致性是核心。
  • 证明文件 - 如在职证明、结业证书，频率低但签名、水印等可信度要素很关键。
  • 标签 - 如物流面单，要求超低延迟、高频率，版式小而重复。

1. 既有方案的痛点 - 为何大家都在这件事上受苦

1.1 LaTeX - 质量高，但笨重且慢

数十年来，LaTeX一直是高质量排版的标准。但把它塞进自动化流水线摩擦不小。完整发行版体积达数GB，一旦单体.tex文件里混入图片与复杂图表，编译速度会明显变慢。每一次请求都要重新拉起一个笨重的排版进程，失败时输出的日志对非LaTeX出身的运维人员来说门槛很高。虽然可以搭一套让自动化代码往模板里注入值(比如发票明细行)的架构，但维护这套架构本身的成本并不低。

1.2 HTML转PDF的无头浏览器方案 - 灵活，但吃资源

以Puppeteer、wkhtmltopdf为代表的HTML转PDF方案，魅力在于可以直接沿用Web开发者熟悉的CSS与模板引擎。但代价很明显。无头Chrome仅启动就要占用200-300MB内存，图片、字体多的页面很容易突破500MB。据报告，开启并发渲染会留下未清理的进程，把CPU吃满。反过来，基于老旧WebKit引擎的wkhtmltopdf虽然轻量，却渲染不好现代的CSS Grid、Flexbox。结果是，从业者长期被迫在「轻量」与「正确渲染现代Web标准」之间二选一。

2. Typst是什么 - 排版语言的第三条路

Typst是一款于2023年发布的基于标记语言的排版系统。它用接近Markdown的简洁语法取代了LaTeX那堆反斜杠与花括号，并把计算与排版之间的界限抹平，让变量、循环、条件判断能顺畅地嵌入文档。性能差距尤其显著: 据基准测试，一份LaTeX完整编译要90秒的文档，Typst约15秒即可处理完，微调内容后的增量编译更能在1秒内完成。它还提供编译器级别的清晰报错信息，以及一个汇集化学式、乐谱、电路图等扩展包的生态「Typst Universe」。

2.1 为何对后端PDF引擎有吸引力

由于Typst用Rust实现，它可以作为纯库直接嵌入服务器进程，无需浏览器。也就是说，无需像无头浏览器那样拉起若干笨重的子进程，就能在服务器内部直接渲染文档。这一特性恰好与「服务器端PDF生成」这一场景严丝合缝，也正是Papermake这类项目选择Typst作为渲染引擎的原因。

3. Papermake - 把模板变成API的路径

Papermake是德国开发者Erik Steiger(rkstgr)打造的开源项目，他把它比作「专为文档模板打造的Docker镜像仓库」。它以SHA-256哈希对Typst模板做内容寻址存储，用invoice:latest这样的标签指向具体版本。模板一经发布(publish)即不可变(immutable)，每次渲染请求都会记录输入输出哈希，使整条历史可复现、可审计。

3.1 架构

整体结构由四部分组成。核心papermake是带虚拟文件系统的Typst渲染引擎; papermake-registry把S3兼容存储(存模板)与ClickHouse(存渲染历史)绑在一起; papermake-server是基于Axum的HTTP API层，提供模板发布、渲染、PDF获取等接口; papermake-worker负责基于队列的渲染(尚处早期阶段)。不仅支持PDF 1.7，还支持用于电子发票的PDF/A-2b、PDF/A-3b，这一点读起来像是专门为实务发票自动化而设计的。项目以Apache 2.0许可证开源。

3.2 模板集中管理+REST API带来的价值

这套架构在实务中的意义很清楚。第一，在微服务环境下，订单、结算、客服等多个服务只需一次API调用即可共享同一份发票模板，模板逻辑不会在各服务中重复。第二，多语言、多格式适配变得容易: 按语言或国家给模板版本打标签管理，无需改动应用代码即可发布新版本。第三，不可变版本加上渲染审计日志，能让人事后精确复现「这张发票为何长这样」。在受监管行业或涉及财务审计的文档场景中，这不是可有可无的附加功能，而是核心要求。

4. 自托管 vs 商用PDF API

像Papermake这样的自托管开源方案，与CraftMyPDF、APITemplate.io这类托管型商用API之间，取舍十分鲜明。自托管的优势在于数据不出自有基础设施，且高用量下单位成本可能下降。确实有一家商用厂商公开过对比资料，把基于浏览器的自托管年成本估算在约2.7万美元，同时把自家托管API定价得便宜得多(这是厂商自身的对比，与其照单全收，不如用自己的工作负载直接验证)。反过来，商用API的优势在于零运维负担: 不必操心Docker镜像膨胀、无服务器尺寸限制、浏览器进程崩溃这些问题。结论很清晰: 发送量小、又没有专门运维人员时，托管API是合理选择; 而数据主权重要，或需要大批量处理高频、格式固定的文档(发票、标签)时，Papermake这类自托管方案值得认真掂量。

5. 落地前应考虑的事 - 字体、CJK、性能、安全

5.1 CJK(中日韩)字体支持仍不成熟

这是最需要谨慎的一点。Typst项目本身有公开议题承认CJK排版支持不足: 字体样式(宋体与黑体)切换、CJK与拉丁字符间距调整、竖排文字、注音标注等功能据报告仍不完善。如果打算把以CJK文字为主的文档 - 比如中文发票、证明文件 - 迁移到Papermake/Typst，应先在试点阶段验证实际的中文字体渲染与换行质量。

5.2 性能与安全

性能方面，得益于Rust实现与无需拉起浏览器的结构，预期在高频渲染上有优势，但公开的独立基准测试仍然稀少。安全方面，由于是自托管，模板本身(用户输入流入渲染的注入路径)、S3存储的访问权限、渲染历史数据库的个人信息留存策略，都需要自行设计与审查，这是额外的负担。

结论: 该用在哪里

截至2026年7月，Papermake仍处于早期阶段(版本0.3.0，GitHub star数166)。与其立刻全面上生产，不如先在低风险工作负载上试点 - 例如内部报表、内部证明文件这类即便出错影响也不大的文档。反过来，如果需要大批量打印高频、格式固定的文档(发票、标签)，而LaTeX或无头浏览器的笨重确实成了负担，Typst加Papermake的组合就是一个值得认真评估的选项。不过CJK字体质量与项目成熟度，在引入前必须用自己的数据亲自验证。
