公开了什么与作者的警告 — 尚未达到一般使用阶段

2026年10月5日，Remo Senekowitsch在自己的博客上发表了题为「Flirt is now Open-Source」的短文，宣布代码评审工具Flirt的源代码已在Codeberg的flirt/flirt仓库公开。GeekNews于2026年10月6日作了介绍。Flirt这个名字在2025年11月的第一篇介绍文章中被解释为「Fabulous, Legendary, Incremental Review Tool」的缩写，仓库的描述栏里写的是「The Fabulous Legendary Incremental Review Tool」。

公告在为初次读到的人补写的一段里，用三句话介绍了Flirt。它是针对「补丁系列」工作流优化的评审工具，在这种工作流中作者不断对改动进行amend、rebase和force-push；它记住评审者此前评审过的内容，并显示其与当前状态的差异；它是本地优先的工具，与GitHub、邮件列表等多个后端兼容。紧接着的一段就是警告。

Warning: I don't yet consider it ready for general use.
                    There are still plenty of bugs and missing features.
                    If you're not considering to become a contributor, I recommend being a little more patient.
                    I'll probably write another blog post when Flirt is ready for you.

这四句话的意思是：尚不认为它已可供一般使用；仍有大量缺陷和缺失的功能；如果不考虑成为贡献者，建议再耐心一些；等Flirt准备好了，大概会再写一篇博文。最后一句里的「大概（probably）」是原文自带的限定。仓库README的警告措辞不同，分量相同。README写道，Flirt处于非常早期的开发阶段，尚未准备好供一般使用，请只在打算为它做贡献时才去测试。后面还有一句：否则会对使用体验感到失望。

公告其余部分讲了两件事。一是无论是否打算贡献，都欢迎加入Zulip上的讨论，并附带说明那里不允许用LLM撰写消息。二是Forgejo后端。Flirt托管在Codeberg上，有了Forgejo后端就能在Flirt自身的开发中使用Flirt，但作者称之为「假想的（hypothetical）」后端，并写明它尚不存在。公告以「创建它是待办清单上的下一项」这句话结束。

走到开源这一步的经过，按日期记录在同一博客的四篇文章里。

  • 2026年2月7日 — Native Git后端的进展。文章说明了功能规格和存储方式，并写明该后端尚未功能完备。
  • 2026年8月15日 — GitHub与邮件列表后端的进展。文中写道论文已于8月1日提交，目标是整理之后在一到两个月内开源。当时已经说明，公开的版本不会是为用户准备好的，而是面向那些认同其代码评审理念、想从早期就参与塑造开发方向的人。
  • 2026年10月5日 — 开源公告。内容包括仓库地址、上面的警告、Zulip的邀请以及Forgejo后端的计划。

要解决的问题 — 强制推送后重读同样的代码

README在脚注里区分了两种工作流。在补丁系列工作流中，提交会在各轮评审之间被改写（amend、rebase、force-push等）；在拉取请求工作流中，新提交加在分支末端，不触碰已有提交。2025年11月的文章对这一区分作了更长的说明。

作者所说的「PR工作流」，是随GitHub的拉取请求功能普及开来的做法。它鼓励代码作者不去动已经评审过的提交，只在分支末端追加新提交，因此评审者只需查看上次评审的提交与最新提交之间的diff。作者写道，这种做法本身已经是「增量的」，使用它并且满意的人从Flirt得到的好处不会那么多。

「补丁系列工作流」得名于邮件列表上的做法，但在GitHub上也有人这样做，作者举的例子是Jujutsu项目。代码作者在每一轮评审中不断对提交进行amend、squash、fixup和rebase，以此提高提交历史的质量。作者提到的好处是：查找缺陷来源时，整洁的历史让人更容易找出并回退引入该缺陷的提交。

代价由评审一方承担。修改已有提交的操作会改变提交的哈希，之后很难判断提交究竟是怎么被改的。作者的例子如下：补丁系列中的一个提交改了100行，其中99行没有问题，第一轮评审指出有一行漏了分号。代码作者为了不让「补上分号」这样的提交留在历史里，对原有提交做了amend。强制推送（或重新提交补丁系列）之后，摆在评审者面前的通常又是整个100行的diff，因为工具不知道上次评审之后只变了一行。作者把这类工具称为「非增量的」评审工具。

同一篇文章里还有作者对现有补救手段的评价。按作者的说法，GitHub拉取请求界面上的「changes since last review」按钮和逐文件的「viewed」复选框有帮助，但在许多寻常情况下不起作用；邮件列表一侧则有git range-diff，它用启发式方法比较补丁系列的两个版本。作者指出的问题与Flirt一侧的应对汇总如下。标为「设想」和「计划」的单元格，是相应文章写作时的表述。

用change-id配对提交 — interdiff与git range-diff

解法的基础是change-id。按2025年11月文章的定义，它是另一种提交标识符，与提交哈希不同，提交被amend或rebase后它保持不变。评审工具如果把已评审的提交连同change-id一起记住，那么新提交提出时，就能与change-id相同的旧提交配对。计算这两个提交之间的interdiff，剩下的正是评审者还没看过的改动。作者称这是Flirt的中心功能：记住评审过的内容，默认只显示与之相比发生变化的部分。

这个术语来自Austin Seipp的文章「Why some of us like "interdiff" code review」，README也把它列为了解该工作流的延伸阅读。作者认为interdiff一词指向实现方式，略显技术化，因而选用了强调实际好处的「增量代码评审（incremental code review）」这个名字。两者说的是同一件事。

change-id从何而来，是有条件的。

  • Jujutsu是与Git兼容的版本控制工具，它把change-id写在自定义提交头里。只有提交作者使用Jujutsu时，Flirt才能利用这一机制。
  • README写道，这项功能依赖提交中的多种元数据，提交作者使用Jujutsu时可靠性最高。
  • 没有change-id提交头时使用后备启发式方法。2025年11月的文章说，这种后备手段在概念上与git range-diff做同样的事，只是起初的启发式会简单得多。
  • 2026年8月的文章举了匹配主题行和作者之类的启发式作为例子，并写道在目前的限制下，无论选哪种做法都只能是启发式。
  • README提到Gerrit也有这项功能。作者写道Gerrit内置的评审界面已经用change-id实现了增量评审，同时说明自己从未认真用过Gerrit。

既然有Gerrit还要做新工具，作者给出的理由是平台问题。自己参与的项目用什么代码共享平台并不由自己决定，工作单位和许多喜欢的开源项目都在用GitHub。作者写道，解决评审工具与代码共享平台绑在一起这一点，是做Flirt的第二个动机。

作为后备手段参照物的git range-diff，在Git官方文档中的定义如下：它是显示补丁系列两个版本之间、更一般地说是两个提交范围之间差异的命令，并忽略合并提交。它寻找配对的依据是相似度，而不是标识符。

  • 两个提交的补丁（作者信息、提交信息和提交diff）彼此做diff，结果相对于补丁大小足够小时，就认为这两个提交相互对应。
  • 对两个范围中的每一对提交，以3行上下文生成「diff的diff」，把其行数作为代价，再求解最小代价指派问题。
  • 当大的改动被误判为整体重写（删除一个提交并新增另一个提交）时，用于调整的选项是--creation-factor，默认值为60。
  • 输出是给人读的。文档写明输出可能发生变化，并非为机器读取而设计。

概括起来，range-diff根据补丁内容有多相似来推测配对，change-id的方式则根据提交中记录的标识符是否相同来确定配对。Flirt的README之所以写明可靠性随提交作者是否使用Jujutsu而变化，原因就在这里。

四个后端的现状 — Forgejo尚不存在

README把「用户不必操心项目托管在哪里」作为理想。无论是Forgejo、GitHub还是邮件列表，目标都是提供顺畅一致的体验。随后它列出四个后端及各自的局限，成熟度并不一致。

Native Git 自定义（不稳定）格式 评审信息存放在Git的对象存储中，通过自定义ref向远端push和fetch。主要用途是不依赖外部服务进行测试 在人人都有push权限的团队里可以使用，但README写道，由于格式不稳定和归档方面的未决问题，目前这不是个好主意
GitHub 大概会是使用最多的后端 由于它是专有软件，贡献不得因是否支持GitHub而被阻挡 2026年8月的文章：已实现，但功能有限，并在若干方面存在缺陷

据2026年8月的文章，Native Git后端所用的自定义ref机制也原样用于其他后端。这样做是为了避免每次操作都去调用GitHub API或下载邮件线程；这些ref只留在本地，在用户要求与后端同步时才转换为API调用或邮件。同一篇文章对GitHub后端写下的限制如下。

  • 作者认为最大的问题是，无法从GitHub取得某个PR过去强制推送的信息。因此无法显示所有提交版本之间的interdiff。
  • 标准用法即「上次评审的提交版本与当前提交版本之间的interdiff」基本可用，因为上次评审的提交版本可以记在本地。
  • 更换工作机器可能使之失效。如果那台机器从未见过上次评审的提交版本，就很难从GitHub API取回。
  • API会给出每条评审评论所针对的提交哈希，可用来重建过去的提交版本。不过如果只有中间的提交上有评论、末端提交上没有，提交版本就只能被部分重建。
  • GitHub的评审界面让人在diff上评论，而Flirt是在代码库的某个特定状态上添加评论。因此，打在diff左侧（被删除的行）上的评论放在哪里仍是未解决的问题，作者写道实现它大概需要一些时间。

邮件列表后端处在更早的阶段。同一篇文章记录了以下内容。

  • 支持范围限定为使用public-inbox的项目。作者写道，Linux内核和Git都用public-inbox托管邮件列表归档。
  • git format-patch默认不加入base提交信息，需要用--base参数指定。作者指出，缺少这一信息就无法确定补丁应当应用到哪里。
  • git format-patch不保留Jujutsu的change-id提交头。README的脚注说，有一组改进此事的补丁系列发到了Git邮件列表，反响相对积极，但被要求换一种做法，据作者所知尚无任何内容被合入。
  • 把同一补丁系列的多个版本联系起来的依据之一，是主题行中[PATCH v2 0/N]这样的版本标记，但标记可能被遗漏，措辞也可能改变。
  • Flirt目前支持的格式只有一种：把新版本的第一封邮件作为上一版本第一封邮件的回复发出，使所有版本构成一个线程。作者写道Git项目推荐这种做法。作者引用的Linux内核文档则写道，对于多补丁系列，通常最好避免用In-Reply-To链接到旧版本。
  • 读取评论一侧需要把带有多层引用符号的纯文本解析成结构，特殊情况很多，作者写道目前只在非常简单的情形下可用。
  • 发送评论一侧同样不发真实邮件。Flirt构造出邮件后交给public-inbox-mda，导入本地用于测试的public-inbox实例。

作者把Flirt所支持的线程结构画成了下面这样。

把评审信息放进Git仓库的方式 — 不用git-notes而用自定义ref

README对Native Git后端的存储格式只写了「自定义（不稳定）格式」。其内部做法在2026年2月的文章中有说明，以下是该文写作时的表述。

作者考察了思路相同的先行项目git-appraise。按作者的介绍，这个项目把代码评审信息直接存进Git仓库，主要目标似乎是定义一套标准，使不同工具彼此兼容。作者研究其存储格式能否用于Flirt，结论是不能，原因在于git-appraise把信息存放在git-notes里。

  • 提交被git-rebase等操作改写后哈希会变。挂在旧哈希上的note本应转移到新提交上，但Git默认不这样做。可以通过配置开启，但需要用户主动选择。
  • 作者写道，在Jujutsu中编辑提交时完全不支持转移git-notes。
  • git-appraise有一个未写入文档的rebase命令来处理这件事，但作者判断，不能指望用户在每一次改写提交时都使用它。
  • 作者给出一段简短的脚本：创建评审请求后对提交做amend，并立即触发reflog过期和垃圾回收，请求随之消失。作者补充说，其中唯一不寻常的做法就是立即触发垃圾回收。
  • 作者还写到查找不便。从提交、change-id或分支出发无法直接得知评审信息存在哪里，只能遍历note列表并解析JSON。

替代方案是自定义ref。ref是指向对象的指针，分支在.git/refs/heads/下，标签在.git/refs/tags/下，note在.git/refs/notes/下。作者解释说，可以在别的目录下创建新的ref，例如.git/refs/flirt/。这类ref对Git没有特殊含义，但工作方式相同：它们使所指向的对象不被垃圾回收，并且可以像分支一样push和fetch。

最初的做法是把数据结构序列化为JSON存成blob，再让ref指向这个blob。问题出在中间的提交版本上。Flirt把相当于拉取请求或补丁系列的评审单位称为Spirit（「Set of Patches Intended for Review and Intense Testing」），把作者每次给出的版本称为提交版本（submission）。评审者拉取ref时评审信息会下载下来，但即使拉取分支，也只会下载最新提交版本的提交，中间各提交版本的提交不会下载。Spirit里虽然记着哈希，本地却没有这些提交，也就无法查看。

作者选择的办法是借助Git已有的行为。拉取一个提交时，本地还没有的祖先提交会一并下载。于是让自定义ref指向一个提交而不是blob，并把每个提交版本的head提交设为这个提交的父提交。该提交的树里只有一个名为spirit.json的blob，实际的评审信息就在其中。评审者fetch一个Spirit时，此前各提交版本的提交会一并下载，因此可以查看Spirit是如何演变的，以及过去某条评论发表时代码库的状态。

在编辑器里评审 — HEAD与工作区、评论线程的设想

README列出的第二个特点是本地优先。它写道，只有下载待评审内容和上传评审时才需要网络，评审过程本身离线进行，并与现有工具、尤其是文本编辑器配合。2025年11月的文章从这样一点出发：编辑器已经具备评审所需的功能，包括查看Git HEAD与工作区之间的diff，借助LSP或语言插件浏览代码，用语言自身的注释语法写备注，以及运行代码和测试。可是要留下评论，就得离开编辑器、打开浏览器、重新找到同一位置再打开文本框，这正是作者指出的缺口。

Flirt的做法是把interdiff「物化（materialize）」到本地仓库中：让Git HEAD指向评审者上次评审过的Spirit状态，把当前状态写入工作区。带有Git集成的编辑器便会直接显示新变化的内容。2025年11月的文章写道，这样编辑器显示的内容与jj interdiff相同。评论用语言的注释语法书写，设想是由Flirt把它们收集起来，去掉空白和注释标记后发往后端。

这种做法没有解决的是评论线程。在编辑器里以内联方式读写评论时，Flirt需要有办法知道一条新评论是新线程还是对已有线程的回复。在2026年2月的文章中，作者把「用标记包住已有线程、并留出专门的回复位置」作为「当前的计划」提出。示例中，线程以// +<3+<3+<3+<3+<3+<3+<3+<3 Flirt thread-ID: ABCXYZ这一行开始，接着是带有作者和时间的评论、填写回复的位置、「对所有人标记为已解决」和「仅对自己标记为已解决」两个勾选项，最后以thread-end行结束。作者自己也写道这种写法有些冗长、不易阅读。2026年8月的文章写道评论线程已经「基本可用」。

这些文章中记录的设计决定和设想如下，均为相应文章写作时的计划。

  • 线程重定位。当强制推送改变了线程所在的提交时，GitHub会把线程标为outdated。如果线程物化在仓库里，代码作者移动函数时可以把线程一起移动，设想是由Flirt根据ID读出新位置并记录到Spirit中。作者写道只有Native Git后端能支持这一点。
  • 两个已解决开关。在GitHub上线程的解决状态对所有人共享。作者打算分别设置共享开关和本地开关，并写道在没有解决标记的邮件列表上，用户只剩本地开关可用。
  • 按提交评审。计划不支持对多补丁Spirit的合并diff发表评论。对行范围的评论会支持，而Gerrit具有的行内字符范围评论不在计划之内。
  • 对提交信息的评论。作者打算支持，并写道发往不支持此功能的GitHub时，大概只能表示成一条引用了提交信息的独立评论。
  • 评审结论。各后端做法不同：GitHub是Comment、Approve、Request changes；Gerrit是Code-review标签上从-2到+2的分数；邮件列表则是Reviewed-by、Tested-by、Acked-by之类的惯例。作者因此写道，至少需要按后端支持自定义的评审结论。
  • 界面。2025年11月时的Flirt是一个用于展示基本功能的CLI。作者写道，主界面大概最终会是TUI，中心逻辑则以库的形式提供。

仓库与社区规则 — Rust、AGPL-3.0-or-later、LLM政策

仓库的Cargo.toml中写着包名flirt、版本0.1.0、edition 2024、许可证AGPL-3.0-or-later。2025年11月作者还写道许可证没有定下来，GPL和Unlicense各有吸引之处；LICENSE文件是在2026年9月30日的一次提交中加入的。获取时的仓库页面显示111次提交、2个分支、0个标签，语言比例为Rust 96.9%、Shell 3.1%。依赖列表中有clap、clap_complete、inquire、jiff、mail-parser、unidiff、serde、serde_json、anyhow、cmd_lib、rand和which。

README没有安装或构建一节。「Contributing & Development」一节写道文档还不多，建议先到Zulip上聊聊自己感兴趣的方向再开始。常见的开发任务以脚本形式定义在tasks/目录中，README说可以直接执行，也可以用simply-run或mise执行。README提出的指导原则有三条。

  • 社区高于产出。README写道，做出最好的代码评审工具，只是人们就「那究竟是什么」建立共同理解这一过程的副产品。
  • 高级用户优先。README写道，为易用性优化的评审工具已有很多，Flirt不在其列。它的立场是：改进易用性很好，前提是不以牺牲高级用户为代价。
  • 自由与开源软件。为Flirt做贡献和参与社区不应要求使用专有软件。脚注列出了由此而来的结果：Discord不能成为官方交流平台，贡献不能因是否支持专有后端（GitHub）或操作系统（Windows、Mac）而被阻挡。其他贡献者仍可以尽力而为地提供支持。

README自己把它的LLM政策称为「相当严格（fairly strict）」。

  • 禁止在Flirt社区空间发布LLM生成的文本，无论是否经过编辑。代码、提交信息、议题、PR描述、议题和PR下的评论、Zulip上的消息，都必须在不使用LLM的情况下写成。
  • 个人场景下的使用不在政策范围之内。文中举的例子有浏览代码库、调研、调试和推敲想法，脚注写道该政策对个人使用LLM既不认可也不谴责。
  • 存在一个范围很窄的例外：并非有意生成该贡献（属于意外），该LLM生成的文本是实现某项具体改进的最佳或唯一途径，并且已尽可能用自己的头脑重现从而完成「净化（sanitize）」。
  • 关于净化，README举的例子是LLM给出了贡献者尚不了解的库函数调用。贡献者应当想清楚自己原本会怎样想到使用这个库，像不知道函数名那样在文档里查找所需功能，再通过阅读文档自行得出结论。
  • 执行以善意为前提。怀疑有人违规时，视为无心之失，只是提醒其注意政策；对于故意违规，README写道原则上唯一合理的结果是永久封禁。

综合来看，Flirt是想用change-id和本地存储来回答「重新评审被强制推送的改动时该显示什么」这个问题的工具，而这个回答目前能覆盖的范围是有条件的。文档自己写明，结果取决于提交作者是否使用Jujutsu、用的是哪个后端，以及评审者是否在同一台机器上见过此前的提交版本。

判断的标准就是作者的原话：尚未准备好供一般使用，仍有大量缺陷和缺失的功能，不打算成为贡献者的人请再耐心等一等。README也写着只在打算贡献时才去试用。作者表示准备好之后大概会另写文章告知，因此是否把它纳入工作流程，留到那篇文章之后再判断，才与作者的建议一致。眼下这次公开所面向的读者，是认同补丁系列工作流中的评审问题、愿意参与设计讨论或后端实现的人；README写道，为自己关心的新后端添加支持是开始贡献的好办法。

相邻的话题在其他文章里。把大改动拆成多层PR的GitHub堆叠PR见GitHub 堆叠 PR 公开预览，在终端里评审diff的工具Hunk见AI代理代码评审Hunk。堆叠PR是拆分改动的方式，Flirt则是把被改写的提交与评审者此前看到的状态相比较的方式。
