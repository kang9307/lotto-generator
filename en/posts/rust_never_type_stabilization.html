Why a Type With No Values Matters

Giving a type to expressions that diverge, and the weight of changing an inference default

Aug 28, 2026 Dev & Infra

Introduction: You Were Already Using the Feature That Took So Long

If you have built anything in Rust, you have written a function like this at least once.

fn bail(msg: &str) -> ! {
    eprintln!("{msg}");
    std::process::exit(1)
}

A single exclamation mark where the return type goes. That spelling has simply worked on the stable channel for a long time. And yet in late August 2026 the news went round that the never type had been stabilised after more than a decade. What does it mean to stabilise now something people are already using?

The answer comes in two layers. First, what stable actually allowed until now was only the ! that sits in return position. Putting it in an ordinary type position — let x: !, Result<u32, !>, ! as a generic argument — was nightly-only. Second, and this is the real story, what held everything up was not syntax but a single default: where inference lands when it cannot decide.

This article is about that default. Why a type with no values is useful, and why changing a default in a language already shipped is so expensive. It runs alongside Encapsulating unsafe in Rust through iddqd - borrow-from-value and the trap of self-referential structures, which approaches the same safety model from the unsafe side, and Putting static types on the BEAM - the boundaries Gleam moved and the ones it left, on the cost of adding types to a boundary after the fact.

What Is Being Stabilised and When It Lands — As of August 2026

Pin the timing first. It is not on the stable channel yet.

  • The stabilisation PR rust-lang/rust#155499 (titled, plainly, stabilize never type) was merged on 24 August 2026. The milestone is 1.100.0.
  • Per releases.rs, 1.100.0 branches from master on 25 September 2026 and is due on the stable channel on 12 November 2026.
  • The stable version at the time of writing is 1.98.0, with 1.99.0 scheduled for 1 October 2026.

The headline word stabilised points at the merge. Unless you are on nightly, it reaches your hands in November, and that is also when release notes fix the final scope.

This PR handles four things in one bundle.

  • Stabilise ! as a proper type — usable outside return position
  • Unify the type-inference fallback to ! across every edition
  • Turn std::convert::Infallible into a type alias for !
  • Remove the dependency_on_unit_never_type_fallback lint that had been switched on as advance notice

And the grounds for the phrase more than a decade. The Start Date on RFC 1216 (bang type) is 2015-07-19. Reaching the merge took eleven years and one month. The rounded decade in the headline is a figure of speech, and the interval was not empty either. As we will see, it was stabilised once and then rolled back.

The Idea of a Type With No Values At All

Treat a type as a collection of values and the arithmetic is easy. bool holds two, u8 holds 256, () holds one. So what is a type that holds zero?

With zero values you cannot construct a value of that type. Since you cannot construct one, the code that puts something into a variable of that type is unreachable. Here the meaning flips once — having no values translates into execution never arriving here. A statement about cardinality becomes a statement about control flow. The Rust Reference calls ! a type with no values that represents the result of a computation which never completes.

Why does anyone need this? A type checker keeps going only because every expression has a type. Yet programs are full of expressions that end without handing back a value.

  • panic!("...") — unwinding or aborting, nothing continues after it
  • loop {} — an infinite loop with no break
  • std::process::exit(1) — the process itself disappears
  • return — control leaves the function, so no value is left in this position
  • break and continue — control goes elsewhere
  • The failure path of the ? operator — an early return, so there is no after

Before RFC 1216, Rust attached () to expressions like these. Doing so amounts to claiming there is one value in a spot execution never reaches. From the compiler side that fiction is not free. Dead-code judgements blur, and the type computation where branches merge picks up cruft.

The RFC puts it tersely. ! behaves like an empty enum, except that it can be implicitly converted into any other type. The first half is the fact that it has no values; the second half is the property that makes the type genuinely useful.

It Flows Into Every Type — When One Arm of a Branch Ends

The key property of ! is single. An expression of type ! coerces into every other type. The Reference says exactly that.

Why is that safe? Because the value being converted does not exist in the first place. There is no need even to define a conversion rule. The most naked expression of this logic is Haskell's Data.Void, which carries a function absurd :: Void -> a that the documentation explains as an implementation of the logical principle that from falsehood anything follows. A function that cannot be called cannot lie about what it returns.

In practice the property shows itself most clearly when one arm of a branch simply ends.

let port: u16 = match std::env::var("PORT") {
    Ok(v)  => v.parse().unwrap_or(8080),
    Err(_) => {
        eprintln!("PORT is required");
        std::process::exit(1)   // the type of this arm is !
    }
};

Every arm of a match must have the same type. The upper arm is u16, the lower one is !. Since ! flows toward u16, the two line up. The programmer does not have to invent a meaningless dummy value. In a world without this type you would have to write a 0 or something into the lower arm, and that 0 leaves the reader with a wrong question: could this value ever be used?

Put it in a function signature and the direction of the information shifts again.

fn bail(msg: &str) -> ! { eprintln!("{msg}"); std::process::exit(1) }

let cfg = load_config().unwrap_or_else(|_| bail("config missing"));
//        the type of cfg does not wobble even though the closure yields !

If bail were declared to return () the code above would not compile, because the types do not line up. Declare it as ! and three things hold at once.

  • The call site types line up — it can sit exactly where a return value is required
  • Code after it is judged unreachable — uninitialised-variable diagnostics and dead-code warnings get sharper
  • A change of implementation is blocked at compile time — if someone later returns by accident inside bail, the error appears right there

That last item is where this parts ways with a comment. A line reading // this function does not return does nothing at all when the implementation changes.

Empty Enums and ! — Rolling Your Own Valueless Type

Read this far and one thought arrives on its own. Why not just declare an enum with no variants?

enum Never {}          // no variants, so no value can be constructed

People do exactly that. The standard library's std::convert::Infallible is precisely that object, and its documentation calls it an error type for errors that can never happen, noting that since this enum has no variants a value of this type can never actually exist. RFC 1216 likewise concedes that a user-defined empty type covers every use described above.

So what differs? Three things.

  • Coercion — ! flows into any type on its own. An empty enum does not, so you eliminate it by hand with something like match x {}
  • Expressive power in return position — -> ! says it does not come back. -> Never reads syntactically as it gives you a Never value, and the fact that no such value can exist sits one layer behind
  • Effect on inference — an empty enum is an ordinary user type, so no inference-default argument attaches to it. ! is built into the language, so one does

The third is the whole remainder of this article. And the fate of Infallible was already written in its documentation — the plan is to make Infallible a type alias once ! is stabilised, and eventually to deprecate Infallible. This PR actually performs that alias conversion.

The same document names a pitfall of its own. Code that has attached separate trait implementations to fn() -> ! and fn() -> Infallible will find those implementations overlapping the moment the two become the same type. Which means creating one alias can produce a conflict inside somebody else's code, and having to count things like that is the real bulk of stabilisation work.

Why It Took So Long — When Inference Cannot Decide

Now the heart of it. The syntax that admits ! as a type is not hard. What is hard is the place where type inference ends up deciding nothing at all.

Sometimes a generic type variable is left with no constraint on it whatsoever. The compiler cannot simply give up, so it fills in a default. That is the fallback. Historically Rust fixed that value at ().

The Edition Guide's wording pins the problem down. Historically the fallback type was (). Because of this, ! was coerced into () on its own even in places where, absent fallback, the compiler would not have inferred (). This was confusing and blocked stabilisation of the ! type.

Put another way, treating ! as a real type while laying it down as () wherever inference stalled did not add up. But change that default and code that used to compile stops compiling. Take the example the Edition Guide offers.

fn outer<T>(x: T) -> Result<T, ()> {
    fn f<T: Default>() -> Result<T, ()> { Ok(T::default()) }
    f()?;        // before: T = ()  /  now: T = !
    Ok(x)
}

The success value of f()? is discarded, so nothing constrains T. It used to land on (), and () implements Default, so it passed. Now it lands on !, and ! does not implement Default, so it errors. The only fix is a person nailing down the intent, as in f::<()>()?;.

Annoying as that is, it is safe. A compile error announces itself loudly. The real problem is the side where meaning changes in silence. Here is the example the compiler lint documentation offers.

if true {
    return
} else {
    unsafe { std::mem::zeroed() }   // sound if fallback is (), instant UB if !
};

mem::zeroed has its return type decided at the call site. When the fallback was () it produced a (), which is perfectly sound. Once the fallback becomes !, it has produced a value of a type whose values cannot exist, and that is undefined behaviour on the spot. The code is unchanged; the meaning is not. And it compiles.

How seriously this risk was taken is written into the history. The never type was stabilised once in 1.26 alongside TryFrom, and reverted in April 2018 (PR #50121), because a change in fallback semantics came with it. Afterwards tracking issue #58184 proposed a partial stabilisation along the lines of leaving inference alone and stabilising only the type. In the end inference had to be touched anyway, but in the interval the advance-warning machinery piled up.

The Machinery Needed to Change One Default

Changing a default in a stabilised language means changing the meaning of code already shipped into the world. Rust brought three devices to the job, and all three transfer intact to other languages and other projects.

First, editions. Edition 2024 flipped the fallback to ! ahead of everyone else. Old crates compile under old edition rules and link with new crates without trouble. But an edition is a transition corridor, not a permanent fork. If rules differed per edition forever the language would effectively become several languages, so unification across editions was always the destination, and this PR did that work.

Second, warning stages. Allow, then warn, then deny. Raising the two lints to deny by default in 1.92 was expected to affect around 500 crates, and even so an escape hatch via #[allow] was left open. The release notes framed the move as not a compatibility change, and as something that makes future stabilisation of the never type possible. The habit of naming breakage and advance notice as different things in the documentation lives right here.

Third, crater. An experiment that literally rebuilds the entire public ecosystem. This PR's run reported 3,277 regressions out of 9,024, of which 1,149 were judged unintended noise with a retry recommended. Reading those numbers calls for care.

  • A crater regression count is not the number of broken crates but the length of the list a human has to read
  • One shared cause can be counted hundreds of times, and infrastructure noise is mixed in
  • Conversely, in-house code absent from public repositories is never counted at all — and that matters more
  • So crater should be read as a sample survey, not a safety guarantee

One more thing. The Edition Guide states flatly that there is no automatic fix, but there is automatic detection of code that the edition change will break. The reason cargo fix does not repair it for you is plain. The correct fix is a person deciding which type was intended here, and that is not the sort of decision a tool can make on your behalf.

One general lesson survives. Defaults are API surface. Even when nothing is written in the documentation, even when the user never explicitly chose, people build code on top of them. The same holds for a default in a configuration file or the default behaviour of a library.

How Other Languages Filled the Same Slot

The general name for this concept is bottom type. It has no values and sits beneath every type. Several languages have a counterpart, and the table below is not a ranking. The differences come not from better or worse but from when the feature was introduced and what compatibility burden was carried at the time.

LanguageNameHow it is providedDocumentation checked
Rust!Built-in type plus coercion into every type. The language also decides the inference fallbackReference · RFC 1216
KotlinNothingBuilt in. A subtype of every type. The type of a throw expressionKotlin official documentation
ScalaNothingBuilt in. A subtype of every type. Represents exceptions, termination and infinite loopsScala official tour
TypeScriptneverBuilt in. What remains once a union is exhausted, used for exhaustiveness checkingTypeScript handbook
PythonNever · NoReturnStandard library typing. Notation for static checkersPython typing documentation
HaskellVoidLibrary data type plus the absurd functionData.Void

Read the table across and two dividing axes appear.

  • Library or language core — Haskell's Void and Python's Never sit on the library side. Embedded in the core, a type can affect subtyping relations and inference, at the price of being much harder to change
  • Subtyping or coercion — Kotlin and Scala handle it as a subtype of every type. Rust uses subtyping only for lifetimes, so it obtains the same effect through coercion. The result is similar; the rules live somewhere else
  • Enforced at runtime or not — Python's Never is a statement to a static checker, not something the interpreter enforces. Same name, different party holding it to account

It is worth noting that the Python documentation states Never and NoReturn mean the same thing in the type system and that static checkers treat them as equivalent, and yet keeps both names. NoReturn arrived in 3.6.2, Never in 3.11. Layering a name rather than replacing it is another way of preserving compatibility, and it is the same reason Rust intends to keep Infallible as an alias.

Where You Meet This Type in Practice

The type sounds abstract, but the places it shows its face in real code are fairly concrete.

Saying in the Signature That It Never Fails

The standard library contains an implementation like this.

  • The associated type on impl<T, U: Into<T>> TryFrom<U> for T is type Error = Infallible;
  • It uses the TryFrom interface, where conversion may fail, while stating in the type that in this case no failure variant exists
  • Once ! can be written in ordinary type positions, Result<T, !> becomes directly usable and there is less reason to invent one more dedicated error type
  • On the reading side, whether this API can fail is settled by the signature alone — no trip to the documentation required

Functions That Do Not Return

  • A server main loop, a process-exit wrapper and a fatal-error handler are the typical cases
  • Declare -> ! and the compiler knows everything past the call site is unreachable — uninitialised diagnostics and dead-code warnings get more accurate
  • It appears at FFI boundaries too. The Reference offers the shape unsafe extern "C" { pub safe fn no_return_extern_func() -> !; } as an example. This is where a does-not-return marking on the C side is carried over into a Rust signature
  • The boundary itself is treated separately in Trying to shrink unsafe at the Rust FFI boundary - what the extern fil-c proposal targets and what it charges

Pinning a Generic Parameter to Nothing

  • A state in a state machine that is not yet reachable, or the message type of a channel that sends no events
  • It conveys intent more precisely than keeping a dummy struct around — somebody can later put a value in a dummy, and cannot in a valueless type
  • That said, this design pays off on the library side and easily becomes overkill in application code

Exhaustiveness Checking

  • In TypeScript, never is widely used as the idiom for confirming that a union has been fully handled
  • Rust enforces match exhaustiveness to begin with, so the same idiom is needed less — an example of the same tool carrying different weight in different languages
  • Omitting empty variants in patterns falls outside this stabilisation and remains behind a separate gate

Who Can Ignore This, and When Knowing It Pays

Honestly stated, most code never uses this type directly. You just write panic! and process::exit, and the compiler attaches and detaches ! behind the scenes. Typing ! by hand while writing application code happens once every few months, if that.

If all of the following hold, you may forget what this article says.

  • You have a single-crate application and are not publishing a library
  • You do not design APIs that expose an error type as a generic parameter
  • You have no unsafe blocks
  • You are on the latest edition and keep the toolchain moving
  • You can read the message and fix it whenever a compile error appears — and that really is fine

Conversely, if even one of the following applies, learning it now is the cheaper option.

  • You call a function inside unsafe whose return type is decided at the call site — the mem::zeroed family. Do not paper over the warning here with #[allow]. A compile error can be fixed later, but undefined behaviour has no later. That is exactly why the lint was raised to deny
  • You publish a library and expose an error type as a generic parameter — this is where the Infallible alias conversion can produce implementation conflicts in somebody else's code
  • You maintain a large codebase sitting on an old edition — from 1.100.0 the edition boundary no longer shields you. The warnings appearing now are the workload for that day
  • You use a lot of macros — where the fallback lands inside a macro-generated expression is not visible from the source alone
  • You have been startled by a ! jumping out of an error message — sections 3 and 4 of this article are the answer

When a Type Works as Documentation and When It Does Not

-> ! carves the sentence this function does not return into the code. A sentence written as a type beats a comment for exactly one reason, and that one reason is decisive. The compiler enforces the claim. If the implementation changes and it does return, the build stops right there. A comment simply becomes a lie in silence.

The conditions under which a type genuinely does documentary work are usually these.

  • The compiler enforces it — a mismatch fails the build
  • It changes the shape of the caller's code — Result<T, !> removes error-handling code entirely
  • The notation is short and there is one idiom — when several coexist the reader has to interpret every time

What a type cannot say is equally clear, and knowing this side is more useful.

  • It cannot say why — -> ! states only that control does not come back. What the exit code is, whether anything is logged, whether this unwinds or aborts: silence
  • It cannot distinguish kinds of impossibility — a valueless type does not tell you whether the thing is forever impossible by protocol, merely unimplemented so far, or absent only in this build configuration
  • An unwritten default is not documentation — the fallback was exactly that. Nowhere in the source did it say (), yet the meaning of the code hung on it. This entire article is that case study

So the conclusion is not write everything in types. Types enforce what is impossible; prose records why. That is why a one-line comment next to -> ! is still worth having.

What Could Not Be Confirmed

  • The 1.100.0 release notes are not out yet. Whether the final stabilisation scope matches the merge has to be checked at release
  • Of the 3,277 crater regressions, how many crates actually need fixing — with a noise judgement and a retry recommendation outstanding, there is no settled figure
  • The deprecation date for Infallible — the documentation says only eventually
  • The stabilisation schedule for omitting empty variants in patterns (a separate gate) — under discussion and outside this scope
  • An after-the-fact tally of how the roughly 500 crates predicted in 1.92 actually turned out
  • The scale of impact on in-house and closed code — crater sweeps only public repositories, so this is structurally unknowable

Wrapping Up

Reduced to three sentences: a type with no values is a device for saying, in the type system, that control does not arrive here. It is useful because it flows into any type, so you no longer have to invent a dummy value when one arm of a branch simply ends. And it took more than a decade not because of syntax but because changing the default in the places inference could not decide touches the meaning of code already shipped.

Three things to carry away.

  • Defaults are API. The world's code rests on values nobody explicitly chose. Changing them requires machinery — editions, warning stages, ecosystem experiments — and the time it takes to build that machinery is precisely the reason it took so long
  • A compile error and a change of meaning carry different weight. The first can be fixed later; the second cannot. Rust raising only the lint entangled with unsafe to deny shows that distinction being applied
  • Telling people that most of them can ignore this is information too. Writing this type by hand is rare. But if one of unsafe, a published library or an old edition applies to you, reading the warnings now is cheaper than reading them in November
