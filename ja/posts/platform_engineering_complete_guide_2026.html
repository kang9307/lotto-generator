はじめに - なぜ今また「プラットフォーム」なのか

クラウドネイティブ業界でよく話題にのぼるキーワードの一つがプラットフォームエンジニアリング(Platform Engineering)です。「プラットフォーム」という単語自体は新しくありません。10年前にもPaaSがあり、5年前にも「DevOpsプラットフォーム」という言葉が流行りました。それなのになぜ2024〜2026年に再浮上したのでしょうか。要点は、DevOpsが約束した「you build it, you run it」の範囲が、マイクロサービス時代には一人で抱えきれないほど広がったことです。

一人の開発者がKubernetesマニフェストを書き、Terraformでインフラを作り、Helmでデプロイし、Grafanaのダッシュボードを組み、OpenTelemetryでトレーシングまで面倒を見るとしたら、肝心のビジネスロジックを書く時間はどれだけ残るでしょうか。本記事ではその限界を直視し、プラットフォームエンジニアリングがどのように登場し、どの規模の組織がどう取り入れるとよいかを整理します。

1. プラットフォームエンジニアリングが登場した理由

DevOpsのメッセージは明快でした。開発と運用の壁を壊し、同じチームがビルドから運用まで責任を持つ。2010年代半ばまではこのメッセージが通用しました。モノリスを少しずつ分割し、CI/CDパイプラインを1〜2本作ればよかったからです。

ところがマイクロサービスが爆増して景色が変わります。1社に50〜100個のサービスができ、それぞれが独自のインフラ・可観測性・セキュリティポリシーを抱えます。開発者が「自分のサービスのインフラまで責任」を持とうとすると、知るべきことが爆発的に増えます。これを認知負荷(Cognitive Load)と呼びます。Team Topologiesという本がチーム設計に当てはめて広めた概念で、チームが吸収できる認知負荷には上限があり、超えると生産性が落ちます。

プラットフォームエンジニアリングはその答えとして登場します。中心となる発想は「開発者が直接ぶつかる必要のないインフラの複雑性を抽象化する内部プロダクト(Internal Product)を作る」こと。その成果物がIDP(Internal Developer Platform)であり、Backstage、Humanitec、Port、Kratixなどが代表的なツールです。

一文でまとめると
DevOpsが「壁を壊す」運動だったとすれば、プラットフォームエンジニアリングは「もう一度ちゃんと積み直す」運動です。ただし今回は分離ではなく「セルフサービス」という形で。

2. DevOps vs SRE vs Platform Engineering の比較

この3つの概念は混同されがちです。最もシンプルな比較表は次の通りです。

観点 DevOps SRE Platform Engineering
中心目標 協業・自動化 信頼性・SLO達成 開発者生産性・DevEx
主な利用者 開発+運用統合チーム 運用(SRE)チーム プロダクト開発者
代表的な成果物 CI/CDパイプライン モニタリング・ランブック セルフサービスポータル・IDP
中心指標 デプロイ頻度・リードタイム MTTR・エラーバジェット TTFC・DevExスコア
「開発者に何を与えるか」 パイプライン 安定性の保証 「ワンクリック」

この3つは競合関係ではなく補完関係です。DevOpsは文化、SREは運用方法論、Platform Engineeringは開発者体験を目的とするプロダクト開発パラダイムです。理想的には3つが同じ組織内で動きます。ただし小規模組織は3つ全部を真似ようとして、結局どれも中途半端になる罠に陥ります。

3. IDPの5つのコアコンポーネント

「IDPを導入する」と言っても抽象的です。具体的にどの要素から揃えればよいのか。次の5つは本記事が実務の出発点として選んだものです。参考までに、CNCF Platformsホワイトペーパーはプラットフォームの能力をWebポータル、API、ゴールデンパスのテンプレート・文書、ビルド・テストの自動化、デリバリー・検証の自動化、開発環境、可観測性、インフラ、データ、メッセージング・イベント、ID・シークレット管理、セキュリティ、アーティファクト保管の13領域により広く分けています(2026-09-29確認)。

1) Developer Portal(統合UI)

すべての開発者が触れる単一の入口です。オープンソースの代表的な選択肢はSpotifyで生まれたBackstage(CNCFインキュベーティングプロジェクト)で、商用ではPortやCortexなどがあります。ただし2026年9月現在、Portは公式ドキュメントで自らを「agentic SDLC platform」、Cortexは「Engineering Operations Platform」と紹介しており、ポータルの上にAIエージェントのワークフローを載せる方向へ製品説明が移りつつあります。ポータルの中心となる価値は「発見可能性(Discoverability)」。どんなサービスが存在し、誰が所有し、どう呼び出し、ドキュメントはどこにあるのかが一箇所に集まります。

2) Service Catalog(サービスメタデータの中央管理)

社内のすべてのマイクロサービス、ライブラリ、データセット、APIのメタデータを中央管理します。所有チーム、SLA、依存関係、デプロイ環境などが一箇所に。これがないと、新入社員は初週に「このサービスは誰に聞けばいいんですか?」を一日中聞き続けることになります。

3) Templates / Golden Paths(検証済みの推奨経路)

新規サービスを始めるとき「会社が推奨する技術スタックと構造」をそのまま複製してくれるテンプレートです。cookiecutterのようなツールから始まり、Backstage Software Templatesへ進化します。Golden Pathの本質は「強制」ではなく「強い推奨」。道を外れることもできますが、従えばインフラ・可観測性・セキュリティがすべて自動設定されます。

4) Self-Service Infrastructure(セルフサービスインフラ)

「DBが必要です」とチケットを切る代わりに、ポータルで1クリックしてPostgreSQLインスタンスを受け取ります。バックエンドではCrossplaneやTerraformモジュールが実際のクラウドリソースを作ります。IDPの中でも最も難しく、最も価値のある要素です。

5) Observability Integration(可観測性の統合)

新しいサービスを作ると自動でGrafanaダッシュボードが生まれ、OpenTelemetry SDKが接続され、Loki・Tempoにログとトレースが流れます。開発者が「可観測性を追加する」のではなく「最初から入っている」状態が肝です。

現場のコツ: 5つを一気に揃えようとすると失敗しがちです。Service Catalogを一つきちんと整えるだけでも、目に見える変化が生まれます。

4. 導入段階ガイド(Crawl-Walk-Run)

プラットフォームエンジニアリングはビッグバン導入が最もリスクです。以下の段階と期間は本記事が勧める一例であり、公式の基準ではありません。公式の枠組みが必要なら、CNCFのプラットフォームエンジニアリング成熟度モデルを併せて参照します。このモデルは投資・採用・インターフェース・運用・測定の5つの側面を、Provisional・Operational・Scalable・Optimizingの4段階で捉えます。

段階 期間 主な活動 ツール例
Crawl(這う) 1〜3ヶ月 README標準化、golden pathを1〜2本定義、会社標準サービステンプレート1本 cookiecutter, GitHub Template Repo, 共通Makefile
Walk(歩く) 3〜9ヶ月 Backstageなどのポータル導入、Service Catalog構築、主要サービスの50%登録 Backstage, Port, ArgoCD連携
Run(走る) 9ヶ月〜 セルフサービスインフラ(DB・キャッシュ・キュー)、自動環境プロビジョニング、DevEx測定改善ループ Crossplane, Humanitec, Kratix, DevExサーベイ

ここで最も多い失敗は「Walkを飛ばしていきなりRun」です。ポータルもない会社が突然Crossplaneでセルフサービスインフラを作ろうとすると失敗しがちです。ユーザー(開発者)向けインターフェースが存在しないままバックエンドだけを作っている状態だからです。DORAの2024年レポートも、内部開発者プラットフォームは個人の生産性・チームの成果・組織の成果を高める一方で、変更の安定性とスループットを下げることがあり、導入初期に一時的な成果の落ち込みが起こりうると報告しています。段階を分け、段階ごとに測る理由です。

5. 日本・アジア企業への適用と現実

海外の事例をそのまま持ち込むと、日本やアジアの環境では合わないことが多いです。本記事が見る特徴は次の通り。

本記事の判断基準では、導入効果が最も大きい規模は50〜200名の間です(統計で確認された区間ではなく経験則です)。50名以下だとフルスタック開発者が数人で全部把握しているのでIDPはむしろオーバーヘッドになります。200名を超えるとサイロが既に固まってしまい、変化コストが膨大になります。50〜200名の帯が「構造化が必要だがまだ柔軟に変えられる」ゴールデンゾーンです。

DORAの2025年レポートによると、調査対象組織の90%が内部開発者プラットフォームを使い、76%が専任のプラットフォームチームを置いています。ただし大きな組織の事例をそのまま真似るのは危険です。1,000人規模のプラットフォームと50人規模のプラットフォームは完全に別の生き物です。

では小規模な会社はどう始めればよいのか。本記事が勧める「軽量IDP」の出発点は意外にもシンプルです。

  • 会社標準のMakefile - すべてのサービスがmake build、make test、make deployを同じ形でサポート
  • GitHub Template Repositoryを1〜2本 - 新サービスを1クリックで開始
  • README標準 - 「このサービスは何で、誰のもので、どう動かすか」が全リポジトリの同じ場所にある
  • 中央ダッシュボード1ページ - 全サービス一覧と健全性が一目で見える

この4つだけでも働き方が目に見えて変わります。Backstage・Portはその後で十分です。

6. 導入を台無しにするアンチパターン

導入の過程でよく見られる失敗パターン4つ。

アンチパターン#1 - プラットフォームチームを「運用チーム+1」にする
組織図だけ変えて仕事内容が同じだと、プラットフォームチームが新しいボトルネックになります。開発者が直接インフラを触ってはいけないと考え、すべての要求をプラットフォームチームに集めると、結果的に昔の運用チームと同じになります。プラットフォームチームの目的は「要求を受けること」ではなく「要求が不要になるようにすること」です。DORAの2024年レポートも、支援チームに頼らず自分で作業を終えられる開発者の独立性が、チームと個人の生産性を5%高めたとしています。
アンチパターン#2 - 開発者が望まないものを強制する
IDPは内部プロダクト(Internal Product)です。ユーザー(開発者)が使いたくなって初めて意味があります。「これを使わないとデプロイできない」と強制すると短期的には採用率100%ですが、長期的には回避経路が生まれプラットフォームが急速に陳腐化します。採用は「強制」ではなく「もっと良いから」で起こるべきです。
アンチパターン#3 - ツールだけ作ってドキュメント・教育がない
Backstageを入れて開発者に「使ってください」と言うだけでは誰も使いません。ツール導入には必ずそれに見合うドキュメント・チュートリアル・オンボーディングが必要です。出発点としては「ツール開発時間 : ドキュメント・教育時間 = 1 : 1」を勧めます。
アンチパターン#4 - メトリクスなしで導入
「IDPを入れたから良くなったはず」は最も危険な考えです。DevExスコア、TTFC(Time to First Commit、新入社員が初PRをマージするまでの時間)、デプロイ頻度、平均環境プロビジョニング時間など測定可能な指標を導入前後で比較する必要があります。測定なしでは政治的な成果発表だけが残り、実際の改善は検証されません。

7. 主要ツール5つを一言で

ツール 現在の姿(2026-09-29確認) 合う状況
Backstage Spotifyで生まれたオープンソースの開発者ポータルフレームワーク。2022年3月からCNCFインキュベーティング プラグインを自前で組み込み、カスタマイズできる開発人員がいる組織
Port SaaSの開発者ポータルとして出発、現在の公式ドキュメントは「agentic SDLC platform」と紹介 自前でホスティングせずSaaSでカタログとセルフサービスを始めたい組織
Crossplane Kubernetes CRDでインフラセルフサービスを実装。2025年10月にCNCF卒業(Graduated) すでにK8s中心、GitOpsフレンドリーな組織
Humanitec 商用のPlatform Orchestrator(IDPのバックエンド)。オープンソースのワークロード仕様Score(2024年7月からCNCFサンドボックス)をコードベースのインターフェースとして掲げる 商用のオーケストレーション基盤でデプロイの標準化を広げたい組織
Kratix Syntassoが開発したApache 2.0のオープンソース・プラットフォームオーケストレーションフレームワーク。プラットフォームの能力をPromiseというAPIでモデル化 プラットフォーム自体を製品として設計したい組織

絶対の正解はありません。組み合わせの一例は、50〜100名規模ではSaaSポータルでカタログから始め、規模が大きくなったらBackstageのような自前ポータルとCrossplaneのバックエンドを検討する流れです。ツール名を比べる前に、自前で運用する人員がいるか、SaaSの費用とデータ保管場所の要件が合うかを確認するほうが安全です。

8. 結論 - 2026年に導入すべき企業は?

すべての会社がプラットフォームエンジニアリングを導入すべきわけではありません。本記事で整理した組織規模別の推奨は次の通り。

会社規模 推奨 理由
50名以下 導入非推奨(Makefile + GitHub Templateで十分) オーバーエンジニアリングのリスク。開発者が直接全部把握する方が早い
50〜200名 軽量IDP導入(SaaSポータルまたはBackstageの一部導入) ゴールデンゾーン。構造化の効果が最大
200〜1000名 専任プラットフォームチーム+ポータル+セルフサービスインフラのバックエンド サイロ防止、セルフサービスインフラが必須
1000名以上 プラットフォーム製品部門(PM・デザイナーを含む) 内部プラットフォームを正式な製品として運営することが持続可能性の条件

プラットフォームエンジニアリングの本質はツールではなく「開発者を顧客として扱う思考様式」です。ツールはその思考の結果物にすぎません。BackstageでもPortでもCrossplaneでも、中心となる問いは常に「この変更が本当に我々の開発者の認知負荷を減らすか?」であるべきです。

クラウド移行を終えた組織でも、その上に乗る開発者体験は別途手を入れる必要があるケースが珍しくありません。プラットフォームエンジニアリングはその次の段階へ進む有力な経路であり、ビッグバンではなくCrawl-Walk-Runで漸進的に取り入れれば、50名規模の会社でも意味のある成果が得られます。

## 3. 段階チェック(Crawl-Walk-Run)

| 段階 | 期間の例 | 完了とみなす条件 |
|---|---|---|
| Crawl | 1〜3ヶ月 | README標準、golden path 1〜2本、標準サービステンプレート1本 |
| Walk | 3〜9ヶ月 | ポータル導入、Service Catalog構築、主要サービスの50%登録 |
| Run | 9ヶ月〜 | セルフサービスインフラ(DB・キャッシュ・キュー)、環境プロビジョニング自動化、DevEx測定ループ |

- [ ] Walkを飛ばしてRunへ進もうとしていないか(ポータルなしでバックエンドから作ると失敗しがち)
- [ ] 公式の枠組みと照合したか: CNCF成熟度モデルの5側面(投資・採用・インターフェース・運用・測定)× 4段階(Provisional・Operational・Scalable・Optimizing)

---

## 4. アンチパターンの自己点検

- [ ] プラットフォームチームがすべての依頼を抱え込む新たなボトルネックになっていないか
- [ ] 「これを使わないとデプロイできない」という強制で採用率を作っていないか
- [ ] ツール開発と同じだけの時間をドキュメント・チュートリアル・オンボーディングに使ったか(出発点は1 : 1)
- [ ] 導入前に基準値を測ったか: DevExスコア、TTFC、デプロイ頻度、平均環境プロビジョニング時間
- [ ] 変更の安定性とスループットも測っているか(DORA 2024: プラットフォームは生産性を高めるが、安定性・スループットを下げることがあり、初期に一時的な落ち込みがありうる)
- [ ] 開発者が支援チームなしで作業を終えられるか(DORA 2024: 開発者の独立性でチーム・個人の生産性が5%向上)

## 5. ツールの現状(2026-09-29確認)

| ツール | 現在の状態 | 合う状況 |
|---|---|---|
| Backstage | Spotifyで生まれたオープンソースの開発者ポータルフレームワーク、CNCFインキュベーティング(2022-03-15) | プラグインを自前で組み込み、カスタマイズできる人員がいる組織 |
| Port | SaaS。公式ドキュメントは「agentic SDLC platform」と紹介 | 自前ホスティングなしでSaaSからカタログとセルフサービスを始めたい組織 |
| Crossplane | Kubernetes CRDベースのインフラセルフサービス、CNCF卒業(2025-10-28) | すでにK8s中心、GitOpsフレンドリーな組織 |
| Humanitec | 商用のPlatform Orchestrator(IDPのバックエンド)。Score(CNCFサンドボックス、2024-07-08)をコードベースのインターフェースに採用 | 商用のオーケストレーション基盤でデプロイ標準化を広げたい組織 |
| Kratix | SyntassoのApache 2.0オープンソース・プラットフォームオーケストレーションフレームワーク。能力をPromise(API)でモデル化 | プラットフォーム自体を製品として設計したい組織 |

ツールを選ぶ前に確認すること:

- [ ] 自前ポータルを運用・開発する人員がいるか
- [ ] SaaSの費用とデータ保管場所の要件が合うか
- [ ] この変更が開発者の認知負荷を実際に減らすか
