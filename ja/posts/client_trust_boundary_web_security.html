はじめに: 二つの誤った前提

Web アプリケーションの欠陥リストは長い。ところがそのリストから一歩下がって眺めると、大半が同じ場所から出発している。異なる名前が付き、異なる点検項目に散らばっているだけで、根は二つの文である。

前提 ①「クライアントは変えられない」 — フォームに置いた値、HTML の data- 属性、クッキー、リクエストボディ、リクエストヘッダー。このうち利用者が変えられないものは一つもない。
前提 ②「攻撃者は当てられない」 — リセットトークン、セッション値、内部識別子。予測できる値は秘密ではない。

この二文が重要なのは、欠陥を一つずつ暗記する代わりに コードを読みながら判別できるようになる からだ。ある値がサーバーに届いたとき「この値は自分たちが送ったあの値のはずだ」と前提しているコードが見えたら、それが ① である。ある値を秘密として扱っているのに、その値を作る関数が時刻や連番を材料にしているなら、それが ② である。

この記事は十四の具体的な地点を扱う。クッキーがいつ送出されるのかから、単独では中程度の欠陥が二つ重なると何が可能になるのか、クライアントが計算した金額をサーバーが受け取る設計がなぜ成立しないのか、そして 識別制御が崩れたシステムのログが何を証明でき何を証明できないのか まで。すべての節は脆弱なコードと安全なコードを並べ、節の終わりでその欠陥が ① と ② のどちらの前提から出てきたのかを振り返る。

クッキー送信規則そのものをリクエスト種別ごとに詳しく見たい場合は SameSite Lax・Strict・None - どのリクエストでクッキーが消えるか が別に扱っている。ヘッダーが重複して届いたときの解釈問題は 同じヘッダーが二度届いたら で整理した。

この記事の範囲。 ここでは なぜ危険か と どう防ぐか だけを扱う。動作する攻撃コード、回避手法、自動化ツールの使い方は載せない。最後の節の点検方法も 本人が運営するか明示的な権限があるサイト に限られる。コード例に出てくるパスやファイル名はすべて説明のための架空の値である。

1. ブラウザはいつクッキーを送るのか - SameSite 三つの値の実際の挙動

サーバーコードを読んでいると、暗黙に敷かれている前提が一つある。「セッションクッキーが付いているのだから自分たちの画面から来たリクエストだ」。この前提が成り立つかどうかはサーバーが決めない。ブラウザがいつクッキーを付けるか が決める。その規則を調整するのが SameSite 属性である。

定義は MDN の Set-Cookie ページにある。SameSite=Strict は、クッキーを設定したサイトと同じサイトから始まったリクエストにのみクッキーを送る。 SameSite=Lax は、同一サイトのリクエストに加え、クロスサイトのリクエストのうちトップレベルナビゲーションでありかつ安全なメソッドである場合にのみクッキーを送る。 同じページはトップレベルナビゲーションを「アドレスバーの URL が変わるリクエスト」と定義し、安全なメソッドから除外されるものとして POST・PUT・DELETE を挙げる。SameSite=None はクロスサイトと同一サイトの両方のリクエストにクッキーを送り、この値を使うときは Secure 属性も併せて設定しなければならない。

# 脆弱: 属性が一つもない。スクリプトが読め、平文でも出ていき、
#       クロスサイトのリクエストに付くかどうかがブラウザの既定値に委ねられる。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/

# 脆弱: クロスサイト送信を明示的に開いている。
#       埋め込みのために有効にしてそのまま残った形が多い。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; SameSite=None; Secure

# 安全: セッションクッキーの基本形。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

# 安全: 外部リンクからの流入でログイン状態を保つ必要がある画面があるなら Lax。
#       Strict では外部リンク経由の最初のリクエストがログアウトのように見える。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Lax

1.1 三つの値が実際に何を防ぐのか

表 1. SameSite の値ごとのクッキー送信可否。基準は MDN Set-Cookie ページ（2026-08 確認）の定義であり、「未指定」の行は明示的な値がない場合にブラウザの既定値へ委ねられる状態を指す。
SameSite の値同一サイトのリクエストクロスサイトのトップレベルナビゲーション（GET）クロスサイトの POST・サブリソース推奨される用途
Strict送る送らない送らないセッションクッキーの既定の選択
Lax送る送る送らない外部リンクでログインを保つ必要があるとき
None + Secure送る送る送るクロスサイト埋め込みが 実際に 必要なクッキーのみ
未指定送るブラウザによって異なる挙動を仮定できないなし。値は常に明示する

1.2 既定値に頼ってはいけない理由

MDN の Set-Cookie ページは「一部のブラウザは SameSite が指定されていない場合 Lax を既定値として使う」と記す。文に「一部」が入っている点が要点である。そして既定として適用される Lax は、明示的に指定した Lax と同じではない。同じページの説明はこうだ。既定として適用されるときは より寛容な形式 が使われ、この形式では クッキーが設定されてから 2 分を超えていなければ POST リクエストにもクッキーが含まれる。

クッキー送信条件を明示しなければその判断はブラウザの既定値に委ねられ、既定値はブラウザとバージョンによって変わりうる値である。

  • 既定値はコードレビューで「既定が Lax だから大丈夫だ」という根拠に使いにくい。根拠が自分のコードの外にあるからだ
  • より寛容な既定 Lax の 2 分の窓は、ログイン直後に続く流れと時間帯が重なる
  • None を使いながら Secure を落としたクッキーはブラウザが拒否する。結果は「セキュリティが弱まった状態」ではなく「クッキーがそもそも付かない状態」なので、機能障害として先に表面化しやすい
  • SameSite の判定単位はオリジンではなく登録可能ドメインである。同じドメイン配下の別ホストは同一サイトとして扱われる
  • OWASP Session Management Cheat Sheet は、セッションクッキーが SameSite=Strict を優先として、または Lax を明示的に設定しなければならないと記している

前提の振り返り — ①。「自分たちの画面から送ったリクエストだけが届く」という前提は、リクエストの出所をクライアント側の事情に委ねたものである。

2. CSRF トークンが防ぐものと防げないもの

CSRF とは、OWASP Cross-Site Request Forgery Prevention Cheat Sheet の定義によれば、悪意あるウェブサイト・メール・ブログ・メッセンジャー・プログラムが、認証済み利用者のブラウザを騙して信頼されたサイトで望まない操作を実行させる攻撃である。 同じ文書は成立条件を一文でまとめている。ブラウザのリクエストはセッションクッキーを含むすべてのクッキーを自動的に載せるため、適切な認可が使われない限りこの攻撃は通る。

ここでいう「適切な認可」はログイン状態の確認ではない。ログインはすでに済んでいる。必要なのは このリクエストが自分たちの画面から始まったという証拠 であり、その証拠はブラウザが自動的には付けない値でなければならない。

CSRF トークンの仕事はリクエストの出所を証明することである。だからその値はブラウザが自動的に付けない値でなければならず、自動的に付くクッキーだけではその役割を代わりに果たせない。

2.1 Synchronizer Token - サーバーが覚えている値

OWASP Cross-Site Request Forgery Prevention Cheat Sheet が説明する同期トークンパターンでは、トークンは サーバー側で生成され、セッションごとに一度、またはリクエストごとに生成される。サーバーはリクエストに載って来たトークンが、自分がセッションに保存しておいた値と一致するかを検証する。自動的には付かない値なので、他のサイトで作られたリクエストにはその値が入りようがない。

<!-- 脆弱: 状態を変えるフォームなのに自動的に付く値（クッキー）だけで認証される -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">削除</button>
</form>

<!-- 安全: サーバーがセッションに保存した値をフォームに載せて送る -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="csrf_token" value="PLACEHOLDER_TOKEN_FROM_SESSION">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">削除</button>
</form>
// 脆弱: ログイン状態しか見ない。リクエストがどこから始まったかは見ない。
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();
  deleteItem(req.body.item_id);
  res.status(200).end();
}

// 安全: セッションに保存されたトークンとリクエストのトークンを定数時間比較で照合する。
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();

  const expected = req.session.csrfToken;         // サーバーが覚えている値
  const provided = req.body.csrf_token;           // リクエストが持ってきた値
  if (!expected || !provided || !timingSafeEqual(expected, provided)) {
    return res.status(403).end();                 // 検証失敗は拒否であり通過ではない
  }
  deleteItem(req.body.item_id);
  res.status(200).end();
}

2.2 Double Submit Cookie とその限界

サーバーが状態を保持しにくい構成ではダブルサブミットパターンを使う。同じ値をクッキーとリクエストボディにそれぞれ入れ、サーバーは両者が一致するかだけを見る。問題はサーバーがその値を覚えていない点にある。OWASP Cross-Site Request Forgery Prevention Cheat Sheet は、素朴なダブルサブミットが 対象ドメインにクッキーを書ける攻撃者によって回避可能 だと明記し、その経路として脆弱な兄弟サブドメイン、DNS 乗っ取り、平文 HTTP を通じたクッキー注入を挙げる。同じ文書の推奨は 署名付きダブルサブミット である。サーバー側の秘密鍵でセッションデータにトークンを結びつけて HMAC 処理する。

// 脆弱: 二つの値が一致するかだけを見る。その値がどこから来たかは確認しない。
function verifyCsrf(req) {
  return req.cookies.csrf === req.body.csrf_token;
}

// 安全: セッションに結びついた値をサーバーの秘密鍵で署名する。
//       クッキーが書けるというだけでは有効なトークンを作れない。
function issueCsrf(session) {
  const nonce = randomTokenHex(32);                       // 暗号論的乱数
  const mac   = hmacSha256(SERVER_SECRET, session.id + '.' + nonce);
  return nonce + '.' + mac;
}
function verifyCsrf(req) {
  const [nonce, mac] = String(req.body.csrf_token || '').split('.');
  if (!nonce || !mac) return false;
  const expected = hmacSha256(SERVER_SECRET, req.session.id + '.' + nonce);
  return timingSafeEqual(expected, mac);                  // セッションに紐づくかまで検証
}

トークンが 防げないもの も明確にしておくほうがよい。OWASP Cross-Site Request Forgery Prevention Cheat Sheet は大文字で強調して記している。XSS はすべての CSRF 緩和策を無効化する。 ページ内で攻撃者のコードが実行されていれば、そのコードは DOM からトークンを読み取ってリクエストに付けられる。トークンは「外部サイトが作ったリクエスト」を弾くだけで、「自分たちのページ内で作られたリクエスト」は弾けない。

  • トークン検証に失敗したときの既定動作は 拒否 でなければならない。ログだけ残して通す実装は制御がないのと同じである
  • カスタムヘッダー方式も有効である。同じ OWASP 文書は、すべての最新ブラウザがカスタムヘッダーの付いたリクエストをプリフライト対象に指定するため、サーバーがそのヘッダーの存在を確認すればブラウザ由来のリクエストならプリフライトを経ていると分かると説明している
  • ただしカスタムヘッダー方式は Access-Control-Allow-Origin が緩いと崩れる。ワイルドカードのオリジンはこの防御を無効にする
  • トークンを GET リクエストのクエリ文字列に載せるとログ・リファラー・ブラウザ履歴に残る。状態変更を GET で露出しない
  • セッションごとに一つのトークンと、リクエストごとの新しいトークンはどちらも有効である。リクエストごとに発行する側は、並行タブで先行トークンが無効になる問題も併せて設計する必要がある

前提の振り返り — ①。「このリクエストは自分たちのフォームが作ったものだ」がこの節の前提である。出所を証明する値がなければ、その文は検証されていない推定のまま残る。

3. 二つの欠陥が重なるとき - 単独では中程度、合わさると致命的

点検項目を一つずつ見ると、この二つはそれぞれさほど深刻に見えない。

  • 欠陥 A — 状態変更エンドポイントに CSRF トークン検証がない。 単独では中程度である。ブラウザの既定値がクロスサイトの POST にクッキーを付けない方向へ動いてきており、その既定値が事実上の緩和装置の役割を果たす
  • 欠陥 B — セッションクッキーに SameSite=None; Secure が設定されている。 単独では設定項目として分類される。値そのものは有効で、埋め込みが必要なサービスなら正当な選択でもありうる

ところがこの二つが同じシステムに同居すると性格が変わる。B が ブラウザ側の緩和装置を明示的に切ってしまう。するとクロスサイトのリクエストにもセッションクッキーが載って出ていく。このとき A のせいでサーバーには リクエストの出所を判別する手段が何も残っていない。サーバーが見るのは有効なセッションクッキーの付いた状態変更リクエストが一つだけで、そのリクエストが自分の画面から始まったのか他所から始まったのかを区別する根拠がない。

項目別の点検表は項目に等級を付けるが、実際のリスクは項目ではなく項目どうしの関係から生まれる。項目別の採点表には関係を書く欄がない。

3.1 リスクは足し算ではなく掛け算である

表 2. CSRF トークンの不在（欠陥 A）と SameSite=None の設定（欠陥 B）について、単独の状態と組み合わせの状態を比較したもの。等級の列は項目単位で採点する一般的な点検表で各項目が受ける相対的な扱いを示すものであり、特定の標準の公式等級体系ではない。
状態ブラウザのクッキー送信サーバーの出所検証結果項目単位の点検表での扱い
欠陥 A のみ（CSRF トークンなし）既定値がクロスサイト POST をおおむね遮断なしブラウザの既定値に依存する状態中程度
欠陥 B のみ（SameSite=None）クロスサイトにも送信CSRF トークンで遮断トークンが防いでいる情報または低
欠陥 A + 欠陥 Bクロスサイトにも送信なし外部由来の状態変更リクエストが利用者セッションとして処理されるどの項目にも引っかからない

最後の行の右端のセルがこの節の要点である。項目別の点検表は A に A の等級を、B に B の等級を与える。両項目とも「即時対応」の基準を超えなければ、どちらも待ち行列の下へ降りる。ところが実際のリスクは 経路 にあり、経路は項目どうしの関係から生まれる。

  • 同じ構造が繰り返される組み合わせは他にもある。予測できる識別子 + 所有権検証の欠落、ログイン後も維持されるセッション + セッション値を外部から仕込める経路、緩い Access-Control-Allow-Origin + 資格情報の許可
  • 組み合わせを見るには 項目を数える代わりにリクエスト一つが処理される経路を最後まで追わなければならない。ブラウザが何を付けるのか、サーバーが何を確認するのか、確認しないものは何か
  • 等級を低く付けた項目でも「この項目は今何に依存して緩和されているのか」を併記すると組み合わせが見えてくる。A の緩和根拠がブラウザの既定値だったなら、その既定値を切る設定がどこかにあるかが直ちに確認対象になる
  • 修正の優先順位も変わる。A と B のどちらか一方を無くすだけで経路は切れる。埋め込みが実際に不要なら B を戻すほうがたいてい安い

前提の振り返り — ①。 A と B はどちらも「リクエストがどこから来たのかをクライアント側の事情が教えてくれる」という同じ前提の上に立っている。だから重なったとき互いを打ち消さず増幅する。

4. クッキーに利用者識別子を入れると起きること

実装していると楽なので手が伸びる形がある。ログイン時にクッキーへ利用者番号を入れておき、以後のリクエストでその値を読んで「誰のリクエストか」を判断するものだ。検索を一回減らしてくれる。

# 脆弱: 利用者番号がクッキーにそのまま入っている。
Set-Cookie: uid=1042; Path=/
Set-Cookie: role=member; Path=/

# 脆弱: 人が読める形で身元が入ったセッション値。
Set-Cookie: session=user-1042-member; Path=/; HttpOnly

# 安全: 値そのものには何の意味もなく、身元はサーバーがその値で検索する。
Set-Cookie: session=PLACEHOLDER_OPAQUE_128BIT_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

OWASP Session Management Cheat Sheet の要求は明確である。セッション ID の内容は情報漏えいを防ぐため意味を持たないものでなければならず、セッション ID はクライアント側では単なる識別子であるべきで、その値に機微情報や個人識別情報が含まれてはならない。同じ文書はエントロピーも併せて明記する。総当たり推測を防ぐために最低 64 ビットのエントロピー が必要であり、16 進数エンコードならそのエントロピーを得るために最低 16 文字が必要である。

IDOR とは、OWASP Insecure Direct Object Reference Prevention Cheat Sheet の定義によれば、Web アプリケーションの URL やパラメーターに使われる識別子を操作してオブジェクトにアクセスしたりオブジェクトを変更したりできてしまう脆弱性である。 同じ文書は、この欠陥がオブジェクト、そのオブジェクトを指す参照、そして 欠けているオブジェクトレベルの認可チェック という三要素で成立すると整理している。

// 脆弱: リクエストが伝えてきた利用者番号で検索する。
//       検索対象の所有者とリクエスト送信者が同じか誰も確認しない。

5. 予測できるリセットトークン - 予測できる値は秘密ではない

パスワードリセットのリンクに載るトークンは その間、認証手段の代わりになる値 である。有効なトークンを持つ側がアカウントのパスワードを変える。だからこの値の品質はログインパスワードの品質と同じ階層で扱う必要がある。

CWE はこの欠陥に固有の番号を与えている。CWE-640 は「元のパスワードを知らなくてもパスワードを復旧または変更できる仕組みがあるのに、その仕組みが弱い」状態を Weak Password Recovery Mechanism for Forgotten Password と名づけている。 上位項目は CWE-1390 Weak Authentication と CWE-287 Improper Authentication である。つまり この欠陥は認証の欠陥として分類される。付随機能の問題ではなく、認証経路がもう一つあってそちらが弱い状態である。

5.1 乱数の出所がすべてである

MDN は Math.random() のページ冒頭に警告を置いている。「Math.random() は暗号論的に安全な乱数を提供しない。セキュリティに関わるいかなる用途にも使わないこと。代わりに Web Crypto API を、より正確には Crypto.getRandomValues() メソッドを使うこと。」 同じページは「実装が乱数生成アルゴリズムの初期シードを選択し、利用者がそれを選んだりリセットしたりすることはできない」とも記す。シードを制御できないことは安全という意味ではない。その値が何を材料に作られるかについての保証がないという意味である。

予測できる値は秘密ではない。値を秘密として扱うコードとその値を作るコードが別々の前提の上にあるなら、秘密として扱われているのは値ではなく、その値を作った関数への信頼である。

// 脆弱: 時刻と利用者番号を材料に使う。二つとも外部から絞り込める。
function makeResetToken(userId) {
  return md5(Date.now() + '-' + userId);
}

// 脆弱: 乱数関数は使っているが暗号論的な乱数源ではない。
function makeResetToken() {
  return Math.random().toString(36).slice(2, 12);
}

// 脆弱: 連番。発行された値一つから隣の値の形が見えてしまう。
function makeResetToken(seq) {
  return 'reset' + String(seq).padStart(8, '0');
}

// 安全: 暗号論的な乱数源から十分な長さで取る。
function makeResetToken() {
  const buf = new Uint8Array(32);                 // 256 ビット
  crypto.getRandomValues(buf);
  return [...buf].map(b => b.toString(16).padStart(2, '0')).join('');
}

5.2 トークン一つでは足りない

OWASP Forgot Password Cheat Sheet が求めるのは乱数の品質だけではない。トークンは 暗号論的に安全な乱数生成器で生成 され、総当たりを防ぐのに十分な長さ でなければならず、使用された後は無効化 されなければならない。同じ文書は利用者列挙の防止も併せて求める。存在するアカウントと存在しないアカウントに対して一貫したメッセージを返し、攻撃者がどのアカウントが存在するかを知られないよう応答が一貫した時間内に返る ようにしなければならない。リンクが開くページには リファラー漏えいを避けるため noreferrer の値の Referrer Policy を指定 するよう記され、リセット URL を作るときは Host ヘッダーに依存せずハードコードするか信頼ドメインのリストで検証 するよう明記されている。既存セッションについては 利用者にすべての既存セッションを無効化するか尋ねるか、自動的に無効化 するよう勧めている。

// 脆弱: トークンを平文で保存し、有効期限も一回限りの処理もない。
//       リセット後も以前のログインセッションがそのまま生きている。
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (!user) return { ok: false, message: '登録されていないメールアドレスです' };  // 存在有無が漏れる
  const token = makeResetToken(user.id);
  await db.saveResetToken(user.id, token);
  await sendMail(email, 'https://example.com/reset?token=' + token);
  return { ok: true };
}

// 安全: ハッシュで保存し、有効期限を設定し、一回限りで、応答は常に同一。
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (user) {
    const token = makeResetToken();                       // 暗号論的乱数
    await db.saveResetToken({
      userId:    user.id,
      tokenHash: sha256(token),                           // 原文は保存しない
      expiresAt: Date.now() + RESET_TTL_MS,               // 短い有効期限
      usedAt:    null                                     // 一回限りの印
    });
    await sendMail(email, RESET_BASE_URL + '?token=' + token);  // Host ヘッダーではない
  }
  await constantDelay();                                  // 応答時間を揃える
  return { ok: true, message: 'そのアドレス宛に案内を送りました' };  // 常に同じ文言
}
// 安全: リセットを完了する側の処理。
async function completeReset(token, newPassword) {
  const row = await db.findResetByHash(sha256(token));
  if (!row) return fail();
  if (row.usedAt) return fail();                    // すでに使ったトークン
  if (row.expiresAt < Date.now()) return fail();    // 期限切れのトークン

  await db.markResetUsed(row.id);                   // 先に消費済みにする
  await db.updatePassword(row.userId, hashPassword(newPassword));
  await db.invalidateAllSessions(row.userId);       // 既存セッションをすべて無効化
  await db.invalidateOtherResetTokens(row.userId);  // 残っている他のトークンも整理
  await notifyPasswordChanged(row.userId);          // 本人に事実を通知
  return ok();
}
  • トークンをデータベースに平文で保存すると、その保存領域を読めるようになった側が直ちにアカウント乗っ取りの手段を得る。パスワードと同じ理由でハッシュして保存する
  • トークンを URL のクエリに載せる方式は広く使われるが、その分だけサーバーのアクセスログ・プロキシログ・ブラウザ履歴・リファラーという四つの副次経路を作る
  • リセット要求そのものに速度制限がなければ列挙と大量試行の通路になる。CWE-640 はリセット試行に対する速度制限の欠如を欠陥の形の一つとして挙げる
  • 「登録されていないメールアドレスです」は親切な文言だが、それ自体がアカウントの存在有無を教える応答である。存在有無を教えずに案内を提供する文言が必要になる
  • リセット完了後に既存セッションを残すと、リセットの目的が半分しか達成されない。パスワードを変えた理由が「誰かが入っているようだから」ならなおさらである

前提の振り返り — ②。「攻撃者は当てられない」がこの節の前提である。時刻・連番・一般的な乱数関数はすべてこの前提に頼る材料である。

6. eval() が禁じられる本当の理由 - 数値変換がコード実行になる瞬間

eval() が良くないという話は広く知られているが、その理由が「遅いから」として記憶されている場合が多い。実際の理由は違う。MDN の eval() ページはこの関数をインジェクションシンクとして規定している。渡された引数は動的に解析されて JavaScript として実行され、この種の API はクロスサイトスクリプティング攻撃の媒介になりうる、というものだ。 同じページは「直接 eval() を絶対に使わないこと」という項目で最初の理由をこう記す。「eval() は渡されたコードを呼び出し元の権限で実行する。」

文字列一つを数値に変えようとしたコードが、文字列の中身によって任意コード実行地点になる。そのコードはログイン中の利用者の画面ができることをすべてできる。

// 脆弱: 入力を数値に変えるために eval を使う。
//       入力が数値でなければその中身がコードとして実行される。
const qty = eval(document.getElementById('qty').value);

// 脆弱: サーバーが返した文字列をデータとして信頼しコードとして評価する。
const data = eval('(' + responseText + ')');

// 脆弱: setTimeout に文字列を渡すと内部的に同じ評価が起きる。
setTimeout('refreshPanel(' + panelId + ')', 1000);

// 安全: 数値は数値に変換する。
const raw = document.getElementById('qty').value;
const qty = Number.parseInt(raw, 10);
if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
  return showError('数量が正しくありません');
}

// 安全: JSON は JSON パーサーで読む。
const data = JSON.parse(responseText);

// 安全: コールバックは関数として渡す。
setTimeout(() => refreshPanel(panelId), 1000);

同じ理由で 名前でプロパティにアクセスするために文字列を組み立てて評価するパターン も避ける。MDN の eval() ページが挙げる代替はブラケット記法である。eval('obj.' + name) の代わりに obj[name] を使う。値が利用者から来るなら 許可リストで名前を検証する 段階も併せて置く。

6.1 CSP がこの問題を扱う方法

MDN の Content-Security-Policy ページは unsafe-eval をこう説明する。「既定では、CSP に default-src または script-src ディレクティブがあると、引数を JavaScript として評価する関数が無効になる。これには eval()、setTimeout() の code 引数、Function() コンストラクターが含まれる。」 そして unsafe-eval キーワードがその保護を元に戻すと記し、警告する。「開発者は 'unsafe-eval' を避けるべきである。CSP を置く目的の相当部分を無効にしてしまうからだ。」

  • eval() をコードから消す作業と CSP から unsafe-eval を消す作業には順序がある。コードが残った状態でポリシーだけ締めると機能が壊れる
  • 直接使っていなくても外部ライブラリが内部的に文字列評価を使っている場合がある。ポリシーを締めるとその地点がコンソールエラーとして表面化する
  • MDN の eval() ページは、リスクを下げる手段として文字列の代わりに信頼型オブジェクトを渡し、CSP の require-trusted-types-for ディレクティブでこれを強制する方式を案内している
  • サーバー側にも同じ種類のシンクがある。文字列をコードやクエリとして組み立てて評価する地点は、言語を問わず同じ性質を持つ

前提の振り返り — ①。「この文字列は自分たちが作った数値だ」がこの節の前提である。その文字列が入力欄・URL・レスポンス本文のどこから来たとしても、中身はクライアント側で決まる。

7. 文字列で HTML を組み立てると - コンテキスト別エスケープ

出力エスケープで最もよくある誤解は「特殊文字を置換する関数を一つ作っておいて全部それに通せばよい」というものだ。OWASP Cross Site Scripting Prevention Cheat Sheet の答えは違う。「誤ったエンコード方式を使うと脆弱性が生じたり、アプリケーションの機能が壊れたりしうる。」 値が置かれる場所が変われば必要なエンコードも変わる。

出力エスケープの単位は値ではなく値が置かれる場所である。同じ値でも HTML 本文、属性、JavaScript、URL、CSS でそれぞれ異なるエンコードを要求する。

8. 価格をクライアントに計算させてはいけない理由 - 信頼境界の定義

注文画面を作るとき自然に出てくる構造がある。オプションを選ぶと画面で金額が更新され、決済ボタンを押すと画面に表示された合計額がリクエストに入ってサーバーへ行く。利用者から見える値と処理される値が一致するので直感的である。

// 脆弱: 金額算出の入力がすべて DOM から読んだ値である。
function buildOrder() {
  const unit  = Number(document.querySelector('#unit-price').dataset.price);
  const qty   = Number(document.querySelector('#qty').value);
  const disc  = Number(document.querySelector('#discount').dataset.rate);
  const total = Math.round(unit * qty * (1 - disc));

  return { itemId: currentItemId, qty, unitPrice: unit, discount: disc, total };
}

// サーバー: 受け取った値をそのまま保存する。
function createOrder(req, res) {
  const o = req.body;
  db.insertOrder({ itemId: o.itemId, qty: o.qty, total: o.total });  // 再計算なし
  res.json({ ok: true });
}

この構造でサーバーが保存する金額は サーバーが計算した値ではなくリクエストが伝えてきた値 である。unitPrice、discount、total の三つのフィールドがすべてクライアントから来ており、サーバーにはこれらの値が自分の価格ポリシーと一致するかを確認するコードがない。画面が計算したのだから合っているだろうという前提が唯一の根拠である。

// 安全: クライアントは何を買うかだけを送る。金額はサーバーが作る。
function buildOrder() {
  return {
    itemId:    currentItemId,

  };

// サーバー: 自分の価格表から計算し直す。

  if (!uid) return res.status(401).end();

  const qty = Number.parseInt(req.body.qty, 10);
  if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
    return res.status(400).json({ error: 'INVALID_QTY' });
  }

  const item    = db.findSellableItem(req.body.itemId);          // 販売可能かまで
  if (!item) return res.status(400).json({ error: 'INVALID_ITEM' });

  const options = db.findOptionsOf(item.id, req.body.optionIds); // この商品のオプションか
  if (options.length !== req.body.optionIds.length) {
    return res.status(400).json({ error: 'INVALID_OPTION' });
  }

  const rate  = pricing.discountRateFor(uid, item);              // サーバーが判断
  const total = pricing.total(item, options, qty, rate);         // サーバーが計算

  if (req.body.displayedTotal !== total) {                       // 表示価格と違えば
    return res.status(409).json({ error: 'PRICE_CHANGED', total });  // 再確認を求める
  }

  db.insertOrder({ itemId: item.id, qty, total, userId: uid });
  res.json({ ok: true, total });
}

8.1 信頼境界とは何か

標準的な定義は CWE にある。CWE-501 Trust Boundary Violation の説明によれば、信頼境界とはプログラムを横切って引かれた線であり、線の一方の側でデータは信頼されず、もう一方の側では信頼できるものとみなされる。 同じ文書は検証ロジックの目的を「データが信頼境界を安全に越え、信頼されない状態から信頼される状態へ移動できるようにすること」と規定している。

この記事ではその定義を Web アプリケーションに絞って使う。Web における信頼境界はブラウザとサーバーの間にある。ブラウザ側で作られた値はすべて信頼されない側にあり、その値がネットワークを越えてサーバーに到達する瞬間が境界を越える瞬間であり、境界を越えてきたデータは例外なく検証の対象である。 画面に描かれる値も、スクリプトが計算した結果も、リクエストに入るフィールドもすべて境界の外側にある。

クライアントは意図を送り、サーバーは結果を作る。「この商品のこのオプションをこれだけ」は意図であり、「したがっていくら」は結果であり、結果は境界の内側でしか作れない。

この定義から導かれる実務上の規則は三つである。

  1. クライアントは意図を送り、サーバーは結果を作る。 金額・権限・状態遷移はすべて結果に属する
  2. 画面から消したものは消したことにならない。 ボタンを隠し入力欄を読み取り専用にするのは使いやすさの改善であって制御ではない。制御はリクエストを処理する側になければならない
  3. クライアント検証は案内であり、サーバー検証は制御である。 どちらも必要だが役割が違う。クライアント検証しかないフィールドは検証されていないフィールドである

境界に置かれた値を判別する質問も三つで足りる。

  • この値はサーバーが作り出した値か、リクエストが持ってきた値か
  • リクエストが持ってきた値なら、サーバーはその値の有効範囲を自分のデータで確認しているか
  • 確認しているなら、その確認を すべての入口経路 で行っているか
  • 金額だけの問題ではない。権限等級、販売者識別子、送料、ポイント使用額、クーポン適用可否のように サーバーのポリシーが決めるべき値 がリクエストボディに入っていれば同じ構造である
  • 状態遷移も同様である。「配送完了に変えてほしい」というリクエストで遷移可否を判断するのはサーバーの状態機械であって画面ではない
  • サーバー再計算があっても表示価格との照合がなければ利用者の混乱が生じる。前述の例が 409 で返す理由はセキュリティではなく 表示価格と請求価格が食い違う状況を防ぐため である
  • モバイルアプリや外部連携のように入口経路が複数あるなら、再計算ロジックは 共通レイヤー に置く必要がある。経路ごとに別々に置くと次の節の問題になる

前提の振り返り — ①。 最も純粋な形である。「画面が計算したのだから合っている」という文で計算の主体はクライアントである。

9. 同じコードベース内の非対称 - 一貫しない制御は制御がないのと同じ

実際のコードベースを開くと、制御があるかないかできれいに分かれる場合はまれである。はるかに多いのは あるエンドポイントにはあり別のエンドポイントにはない状態 である。最近作った画面にはトークン検証が入っていて、ずっと前に作った管理画面にはない。一覧取得は所有権を確認するのにダウンロードは確認しない。

// 脆弱: ルートごとに個別に付ける。付け忘れるとそのまま開いてしまう。
app.post('/api/items/create', requireCsrf, requireAuth, createItem);
app.post('/api/items/update', requireCsrf, requireAuth, updateItem);
app.post('/api/items/delete',              requireAuth, deleteItem);  // 抜けている
app.post('/api/admin/purge',                            purgeItems);  // 両方抜けている

// 安全: 既定を遮断にして、例外だけを明示する。
//       新しいルートを追加して何もしなければ保護される側が既定になる。
const CSRF_EXEMPT = new Set([
  'POST /api/webhooks/inbound'   // セッションクッキーを使わない経路のみ。理由をコメントで残す
]);

app.use((req, res, next) => {
  if (SAFE_METHODS.has(req.method)) return next();
  if (CSRF_EXEMPT.has(req.method + ' ' + req.path)) return next();
  return requireCsrf(req, res, next);
});
app.use(requireAuth);   // 認証も同じ方式で既定適用 + 公開経路のみ例外

制御の実効は平均ではなく最小値で決まる。守る側はすべての経路を守らなければならず、通ろうとする側は経路を一つ見つければよいからである。

  • 非対称はたいてい時間から生まれる。制御を導入した時点より前に作られたコードにはその制御がなく、以後のコードにはある。導入時点がコードベースを二つの層に分ける
  • 人からも生まれる。同じ規則を知っていても適用する習慣は人によって違う。規則が文書にしかなくコードで強制されていなければ偏差が残る
  • 「内部用だから大丈夫」という例外が最も長く残る。管理画面、バッチ処理用エンドポイント、一時的に作った点検経路がこれに当たる
  • 解決の方向は オプトインをオプトアウトに反転させること である。制御をルートごとに付ける代わりに全体に掛けて例外を明示する。付け忘れがそのまま保護につながる
  • 例外リストは コードの中にあってこそ レビューの対象になる。設定ファイルや文書にあると変更がレビューを迂回する
  • 同じ原理が出力エスケープにも当てはまる。既定エスケープを有効にして例外だけを明示的に示すテンプレート構成のほうが、場所ごとに関数を呼ぶ構成より偏差が少ない

前提の振り返り — ① と ② の両方。 制御の有無そのものがクライアントがどの経路から入ってくるかに左右されるようになる。その瞬間「どの経路から入ってくるかは自分たちが決める」というもう一つの ① が生まれる。

10. このログは何を証明するのか - 否認防止

ここまでの議論はおおむね「何を防ぐか」だった。この節は少し違う質問を扱う。防げなかったとき、残った記録で何を言えるのか。

否認防止とは、NIST 用語集が SP 800-53 Rev. 5 から引用する定義によれば、特定の行為を行いながらそれを偽って否認する個人に対する保護であり、情報を作成する、メッセージを送る、情報を承認する、メッセージを受信するといった特定の行為をある個人が行ったかどうかを判別できる能力を提供することを指す。 同じ用語集が引用する CNSSI 4009-2015 も同趣旨で記し、NISTIR 4734 はより短く 「特定の行為を行ったことに対する責任を否認できないこと」 と記す。

定義を二つに分けると実務的な意味が見えてくる。前半は「否認に対する保護」であり、後半は 「ある個人がその行為を行ったかどうかを判別できる能力」 である。後半が成立しなければ前半も成立しない。

ログの証明力は識別制御が健全な分だけ成立する。「利用者 X が削除した」という記録は、その X がどこから来た値かによってまったく違う文になる。

10.1 ログの「誰が」はどこから来るのか

ログ一行に利用者識別子が書かれているからといって、その利用者がその行為を行ったという意味にはならない。その識別子が どこから来た値か によって文の意味が変わる。

表 5. ログに記録された行為者識別子の出所別の証明範囲。「前提となる制御」の列の項目は OWASP Session Management Cheat Sheet（セッションのエントロピー・セッション固定の防止）と OWASP Cross-Site Request Forgery Prevention Cheat Sheet（出所検証）から取ったものである。

表の各行は前の節々とそのまま対応する。4 節で見たように 利用者識別子がクライアントの変更できるクッキーにあるかリクエストボディから来るなら、その記録は X を特定できない。 ログが不正確なのではなく、ログが記録した対象が「行為者」ではなく「リクエストが主張した値」なのである。記録そのものは正確だ。記録が指す対象が違うだけである。

三行目でもう一歩踏み込む必要がある理由が セッション固定 である。セッション固定とは、OWASP Session Management Cheat Sheet の定義によれば、攻撃者が被害者のセッション ID を入手する代わりに被害者のブラウザにセッション ID を設定する攻撃である。 同じ文書は対策を必須として記す。「セッション ID は当該利用者セッション内で権限レベルが変更された後に必ず更新または再生成されなければならない」、「セッション ID の再生成はセッション固定攻撃を防ぐために必須である」。権限レベルの変更には、未認証状態から認証状態へ変わるログインの時点が含まれる。

// 脆弱: ログインしてもセッション識別子がそのままである。
//       ログイン前に作られたセッション値がログイン後も有効である。
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();
  req.session.userId = user.id;                // 値を埋めるだけ
  res.json({ ok: true });
}

// 安全: 認証に成功した時点でセッション識別子を作り直す。
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();

  regenerateSessionId(req, () => {             // 以前の識別子は破棄される
    req.session.userId = user.id;
    req.session.authAt = Date.now();
    res.json({ ok: true });
  });
}

四行目がこの節で最も見落とされやすい地点である。CSRF 防御がなければ「X のセッションでリクエストが出た」という事実さえ X の意思を意味しない。 CSRF は定義上 利用者の意図なくリクエストが発生する攻撃 だからである。OWASP Cross-Site Request Forgery Prevention Cheat Sheet の定義がそのままこの結論を含んでいる。認証済み利用者のブラウザが 騙されて 望まない操作を実行すること。セッションは本物であり、リクエストも本当にそのブラウザから出たが、その行為を行うと決めた主体は利用者ではない。

10.2 何を残し何を残さないのか

OWASP Logging Cheat Sheet は残す項目をいつ・どこで・誰が・何をの四つの軸で整理する。誰が に当たる項目は 「送信元アドレス、たとえば利用者のデバイス・マシン識別子、利用者の IP アドレス」 と 「利用者の身元（認証されているか他の方法で分かっている場合）」 である。括弧内の条件節がこの節全体の要約である。分かっている場合にのみ だ。

同じ文書はログと否認防止の関係について慎重な文を残している。ログが 「否認防止の制御を支える（ただし否認防止という性質はログで達成しにくい。ログの信頼性はたいてい記録する側が適切に監査されているという事実にのみ基づくからである）」。ログを証拠として扱うにはログ自体の完全性が先に必要だという意味である。だから同じ文書が 「記録が変更または削除されたかどうかが分かるよう改ざん検知を組み込むこと」 と 「できるだけ早くログデータを読み取り専用の媒体に保存またはコピーすること」 を併せて求めている。

// 脆弱: 行為者をリクエストボディから取る。ログはリクエストの主張をそのまま写す。
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  logger.info('record deleted', {
    actor:    req.body.userId,        // クライアントが決めた値
    recordId: req.body.recordId
  });
  res.status(200).end();
}

// 安全: 行為者はサーバーセッションからのみ取り、判断の根拠も併せて残す。
function deleteRecord(req, res) {
  const actor = req.session.userId;                   // サーバーが知っている値
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);
  if (!rec) return res.status(404).end();             // 所有権の検証

  removeRecord(rec.id);
  logger.info('record deleted', {
    at:          new Date().toISOString(),            // いつ
    service:     SERVICE_ID,                          // どこで
    actor:       actor,                               // 誰が（セッション基準）
    sessionRef:  hash(req.sessionID),                 // セッションの原値は残さない
    sourceIp:    req.ip,
    userAgent:   req.get('user-agent'),
    action:      'record.delete',                     // 何を
    target:      rec.id,
    outcome:     'success',
    csrfChecked: true,                                // どの検証を通ったか
    authMethod:  req.session.authMethod
  });
  res.status(200).end();
}

残してはならないものも明記されている。OWASP Logging Cheat Sheet は 認証パスワード、セッション識別値（ハッシュで代替可能）、アクセストークン、暗号鍵とその他の主要な秘密、口座・決済カード情報、機微な個人データ を記録しないよう記す。上の例がセッション ID の代わりにハッシュを残す理由がこれである。同じセッションで起きたことをまとめて見ることはできる一方、ログを読める側がセッションを再利用することはできなくなる。

10.3 これは誰のための制御か

まとめるとこうなる。否認防止が崩れたシステムのログでは行為者を特定できない。 これは誰の落ち度かを指す文ではなく、その状態で何が可能で何が不可能かについての技術的な記述である。識別手段がクライアントから来るならログの「誰が」は主張であり、出所検証がなければセッション基準の「誰が」も意思を意味せず、セッション再生成がなければセッション自体の帰属が揺らぐ。

  • これは 利用者の保護 である。自分が行っていない行為が自分のアカウントの記録として残る状況で、その記録の限界を技術的に説明できなければならない
  • 同時に 運営者の保護 でもある。責任の所在を正確に切り分けられてこそ運営者も根拠のない紛争に巻き込まれない。ログが何を証明し何を証明しないかを自ら分かっている側が有利である
  • だからこの節の制御は「事故を防ぐ制御」とは性格が違う。事故が起きたとき何を言えるのかをあらかじめ決める制御 である
  • 記録の証明力を高める順序は前の節々と同じである。サーバーセッションに基づく識別 → セッション再生成 → 出所検証 → ログの完全性。後ろから始めると前のものが破られたまま残る
  • 時刻も証明力の一部である。OWASP Logging Cheat Sheet はログの日付と時刻を国際標準の形式で記録するよう記す。サーバー間で時刻がずれると出来事の順序を再構成できない

前提の振り返り — ① と ② の両方。 識別が ① に頼れば「誰が」は主張へ降り、セッション値が ② に頼ればその「誰が」が別人でありうる。

11. CSP と SRI - 最後の防衛線

前の節々が「境界をどこに引くか」だったなら、この節は「境界が破られたとき被害をどこまでに留めるか」である。順序が重要だ。この層は前の制御の代わりにはならない。

CSP とは、MDN の Content-Security-Policy ページの定義によれば、ウェブサイト管理者が特定のページでユーザーエージェントが読み込めるリソースを制御できるようにする HTTP レスポンスヘッダーであり、クロスサイトスクリプティング攻撃の防御に役立つものである。 同じページはインラインスクリプトについて 「既定では、CSP に default-src または script-src ディレクティブがあるとインライン JavaScript の実行は許可されない。これにはインラインの <script> タグ、インラインのイベントハンドラー属性、javascript: URL が含まれる」 と記す。unsafe-inline キーワードがこの保護を元に戻し、同じページは 「開発者は 'unsafe-inline' を避けるべきである。CSP を置く目的の相当部分を無効にしてしまうからだ」 と警告する。

ポリシーが存在するという事実と、そのポリシーが何を防ぐのかは別である。unsafe-inline と unsafe-eval が入ったポリシーは、ヘッダーはあるのに保護は大きく減った状態である。

# 脆弱: ポリシーはあるが二つのキーワードが保護を元に戻す。
Content-Security-Policy: default-src *; script-src * 'unsafe-inline' 'unsafe-eval'

# 安全: リクエストごとに新しい nonce を発行し、その nonce の付いたスクリプトだけを実行する。
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';

# 導入段階: まず違反の報告だけを受けて何が引っかかるかを確認する。
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST';
  report-to csp-endpoint
  • nonce の値は リクエストごとに新しく発行 されなければならない。固定 nonce はポリシーがないのと大きく変わらない
  • MDN の Content-Security-Policy ページは、ディレクティブに nonce やハッシュが入っていると ブラウザが unsafe-inline を無視する と記す。旧ブラウザ互換のために両方を併記できる理由である
  • 同じページによれば、ハッシュソースのアルゴリズム識別子は sha256・sha384・sha512 のいずれかでなければならない
  • strict-dynamic は nonce やハッシュで信頼されたスクリプトが動的に読み込むスクリプトまでその信頼を拡張する。このキーワードがあるとホストリスト・スキーム・'self'・'unsafe-inline' はすべて無視される
  • frame-ancestors はこのページを <iframe> などで埋め込める親を制限する。クリックジャッキング対策の現代的な形である
  • 導入は Content-Security-Policy-Report-Only から始める。同じページは、このヘッダーがコードの実行を止めず違反の報告だけを行うため試験段階で使われると説明している

11.1 SRI が防ぐものと防げないもの

サブリソース完全性とは、MDN の Subresource Integrity ページの定義によれば、ブラウザが取得したリソースが予期せず改変されていないかを検証できるようにするセキュリティ機能であり、取得したリソースが一致しなければならない暗号学的ハッシュを指定する方式で動作する。 同じページはこの機能が防ぐ脅威を サプライチェーン攻撃 として、具体的には攻撃者がサードパーティのホストを掌握してファイルに悪意ある内容を注入したりファイルを丸ごと差し替えたりする場合を挙げる。動作は単純である。ブラウザが受け取った内容のハッシュを計算して指定された値と比較し、一致すれば読み込み、そうでなければ読み込みを拒否してネットワークエラーを返す。

<!-- 脆弱: 外部ホストのスクリプトを検証せず実行する。
     そのファイルが変わると自分たちのページで変わったコードがそのまま動く。 -->
<script src="https://cdn.example.com/widget.js"></script>

<!-- 安全: ハッシュが合うときだけ実行する。
     クロスオリジンのリクエストは CORS モードでなければならないので crossorigin 属性が必須である。 -->
<script src="https://cdn.example.com/widget.js"
        integrity="sha384-PLACEHOLDER_BASE64_HASH_VALUE"
        crossorigin="anonymous"></script>

crossorigin="anonymous" が必要な理由も同じページが説明している。リソースは既定では no-cors モードで読み込まれるが、完全性検証が no-cors で許されると攻撃者がハッシュ値を変えながら試すことでリソース内容についての情報を推測できてしまう。その情報漏えいを防ぐためブラウザは no-cors のリクエストにサブリソース完全性を許可せず、crossorigin のないリクエストは常に失敗する。

  • SRI が検証するのは 内容が指定したハッシュと同じか だけである。元の作者が最初から入れておいたロジックはハッシュが合うのでそのまま通る
  • バージョンが変わるたびにハッシュを更新しなければならない。更新手順が自動化され何の検討もなく新しいハッシュを受け入れるなら、検証の実効は減る
  • 内容が頻繁に変わるスクリプトには適用しにくい。そうしたリソースは自前ホスティングへ移すほうが代替になる
  • CSP は ブラウザの中 でだけ動く。認可チェックの欠落、クライアントが送った金額をそのまま保存する処理、予測できるリセットトークンには何の影響もない
  • どちらの機能も他の防御が破られた後に働く層である。この層があることを理由に前の制御を後回しにすると順序が逆転する

前提の振り返り — この節は前提を直さない。 CSP と SRI は ① と ② がすでに破られたときに被害範囲を狭める層である。

12. 知っていても直らない理由

ここまでの内容に新しいものはあまりない。引用した文書の多くは以前から公開されており広く参照されている。ならば残る問いは一つだ。なぜ知られた欠陥が残り続けるのか。「知らないから」ではなく「知っていても直らない」構造が別にある。

  • 有効にした瞬間に壊れる。 古いコードベースに CSRF 保護を全体適用すると、トークンを入れていない既存のフォームと非同期リクエストがすべて拒否される。利用者に即座に見える障害であり、制御を有効にする作業がそのまま回帰リスクを背負う作業になる
  • 動いているコードに手を入れる負担。 自動テストが薄いほどこの負担は大きくなる。手を入れる範囲を正確に把握できなければ、直すほうが放置するより危険に見える
  • セキュリティ負債は事故の前には費用が見えない。 性能問題や機能欠陥と違い、残っている間は指標に現れない。費用がゼロに見える項目は優先順位の会議で後回しになる
  • 処理の主体がなければ受付は処理につながらない。 通報を受ける窓口があっても、その通報をコード変更へ移す担当が指定されていなければ受付記録だけが積み上がる。これは役割定義の空白から生じる
  • 機能開発との優先順位競争。 同じ人員が二つを担い、片方だけが日程に名前を持つ
  • 範囲が分からない。 一つを直そうと開いてみたら同じパターンがどれだけあるか数えられず、着手そのものが先送りになる。この項目は次の節に直接つながる

この構造が実際に結果に現れることは公開資料で確認できる。Project Zero は 2022 年 6 月 30 日に公開した中間集計でこう記した。「2022 年 6 月 15 日時点で、2022 年に実環境で悪用されたものとして検知・公開された 0-day は 18 件である。」 そして 「そのうち少なくとも 9 件は以前にパッチされた脆弱性の変種である。」 同じ記事の結論の文はこうだ。「2022 年上半期に観測された 0-day の少なくとも半数は、より包括的なパッチと回帰テストによって防げたはずである。」 再悪用までの時間についての記述もある。「2022 年の 0-day のうち 4 件は 2021 年の実環境 0-day の変種である。元の実環境 0-day がパッチされてからわずか 12 か月で、攻撃者は元のバグの変種を持って戻ってきた。」

期限という仕組みがなぜ存在するのかも同じ文脈で読める。Project Zero の Vulnerability Disclosure Policy は ベンダーが通知後 90 日以内にパッチを提供 するよう定め、パッチ提供から 30 日が経過すると詳細を公開 する。90 日以内は難しくても追加の 14 日以内に可能なら猶予を与えることができ、実際の悪用の証拠があれば 90 日ポリシーの代わりに 7 日ポリシーが適用 され、この場合の猶予は 3 日である。

期限を文書で定めているという事実そのものが、期限がなければ修正が遅れるという経験的な判断を含んでいる。

13. 直したはずが変わっていない場合 - 不完全な修正

修正が行われたのに同じ経路が残っている場合がある。修正の範囲を決める方法 から生じる問題であり、類型はおおむね四つである。

  1. 症状だけ直し根本原因はそのまま。 特定の画面で値がそのまま描かれることが確認されるとその画面にだけエスケープを入れる。同じ値を描く別の画面、同じフィールドを返す別のレスポンスには手を付けない
  2. 変種分析の不在。 同じパターンがコードベースにあといくつあるかを数えない。報告された一箇所だけ直せば残りはそのまま残り、その残りが次の報告になる
  3. クライアントだけ直しサーバーはそのまま。 ボタンを隠し、入力欄を読み取り専用に変え、画面側の検証を追加する。リクエストを処理するコードはそのままである
  4. 一つの経路だけ閉じ別の経路は残す。 特定のレスポンスからフィールドを削除したが、同じ情報を運ぶ別のエンドポイント、エラーメッセージ、キャッシュされたレスポンス、ダウンロードファイルが残る

信頼境界の観点からクライアントの修正は防御ではない。画面からボタンを消すのはそのリクエストを送りにくくする作業であって、そのリクエストが到達したときに拒否する作業ではない。

// 修正前: 権限のない利用者にも削除リクエストが処理される。
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  res.status(200).end();
}

// 不完全な修正: 画面でボタンを隠した。
// サーバーコードは上と同一である。境界はそのままだ。
if (!currentUser.isOwner) {
  document.querySelector('#delete-btn').style.display = 'none';
  document.querySelector('#delete-btn').disabled = true;
}

// 完全な修正: リクエストを処理する側で判断する。
function deleteRecord(req, res) {
  const actor = req.session.userId;
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);   // 所有権の検証
  if (!rec) return res.status(404).end();

  removeRecord(rec.id);
  res.status(200).end();
}
// 画面側のボタン非表示はそのまま残してよい。ただしそれは使いやすさであって制御ではない。

二つ目の類型については前の節で引用した数値がそのまま根拠になる。Project Zero が 2022 年上半期の 18 件のうち少なくとも 9 件が以前にパッチされた脆弱性の変種 と記し、少なくとも半数はより包括的なパッチと回帰テストで防げたはずだ と結論づけたことは、この類型が例外的な事例ではなく繰り返されるパターンであることを示している。一つを直すときに 同じパターンをコードベース全体で検索して数える段階 が修正作業の一部であるべき理由である。

13.1 手続きに生じる検証の空白

技術的な類型とは別に、修正の有無を確認する 手続き にも同じ種類の空白が生じる。構造は単純だ。欠陥が受け付けられ、開発主体に伝えられ、開発主体が「修正した」と回答し、その回答で案件が終結する。この流れには 「修正した」という陳述を確認する段階がない。

  • 回答が事実かどうかの問題ではない。回答が 誠実であっても 上の四つの類型のいずれかに該当しうる。直したと判断して回答したのに変種が残っている場合が最も多い
  • 再検証がなければ終結は状態ではなく手続きの終わりである。ところが終結という表示は 「安全になった」という誤認 を生む。リストから消えた項目はもはや誰の待ち行列にもない
  • 再検証にかかる費用はたいてい最初の確認より低い。どこを見ればよいかすでに分かっているからだ。それでも手続きに段階がなければ実行されない
  • 修正の確認は 報告された地点 と 同じパターンの別の地点 の二箇所を見なければならない。前者だけを見ると二つ目の類型をそのまま通してしまう

もう一つ区別しておくべきことがある。謝辞の掲載は修正の証拠ではない。 セキュリティの謝辞ページや貢献者リストに載ることは 受付と認知の証拠 である。その欠陥を知ったという事実を記録したのであって、その欠陥が取り除かれたという事実を記録したのではない。ここに非対称がある。認知にはほとんど費用がかからず、修正には費用がかかる。 だから認知は速やかに表示され、修正はゆっくり進む。二つの指標を同じものとして読むと、実際の状態を実際より良く見積もることになる。

前提の振り返り — ①。 三つ目の類型がまさに ① である。画面を変える修正は「クライアントは変えられない」という前提をそのままにして、その前提の上に一枚重ねたものだ。

14. 自分のサイトを 30 分で点検する方法

この節の内容は本人が運営するか明示的な権限があるサイトに限る。他人のサービスを無断で点検する行為は法的な問題になりうる。 以下の方法はすべてブラウザの開発者ツールで 自分のサイトのレスポンスを読む 水準であり、リクエストを操作したり試行を繰り返したりする内容は含まない。

この 30 分が答える問いは欠陥のリストではなく「自分たちのシステムは今どの前提の上に立っているのか」である。

14.1 5 分 - クッキー属性

開発者ツールの Application（またはストレージ）タブで Cookies を開く。セッションクッキーの一行で見るものは四つある。

  • HttpOnly の列に印があるか。なければスクリプトがその値を読める
  • Secure の列に印があるか
  • SameSite の列の値が何か。空ならブラウザの既定値に委ねられた状態である。None ならそのクッキーがなぜクロスサイトで出ていく必要があるのかを説明できなければならない
  • セッションクッキーの 値 が人の読める形か。利用者番号・メールアドレス・権限名が見えるなら 4 節の状態である

14.2 10 分 - レスポンスヘッダー

Network タブで文書リクエスト（一番上の HTML レスポンス）を選び Response Headers を見る。

  • Content-Security-Policy があるか。なければ 11 節の層がまったくない状態である
  • あるなら 'unsafe-inline' と 'unsafe-eval' が入っているか。入っていれば MDN が警告したその状態である
  • Set-Cookie の行の属性が 14.1 で見たものと一致するか。複数のクッキーが互いに異なる属性で設定される場合が多い
  • ログインの前後でセッションクッキーの値が変わるか。10 節のセッション再生成が行われているかを目で確認できる地点である

14.3 10 分 - 外部スクリプト

ページがどこからコードを取ってきているか数えてみる。以下は 自分のサイト のコンソールで動かす読み取り専用の確認スニペットである。何も変えずリストだけを出力する。

// 読み取り専用: 外部ホストから来るスクリプトのうち integrity のないものを列挙する。
[...document.querySelectorAll('script[src]')]
  .filter(s => new URL(s.src, location.href).origin !== location.origin)
  .map(s => ({
    src:       s.src,
    integrity: s.integrity || '(なし)',
    crossorigin: s.crossOrigin || '(なし)'
  }))
  .forEach(row => console.log(row));

// 読み取り専用: meta タグで設定された CSP があるか確認する。
console.log(
  document.querySelector('meta[http-equiv="Content-Security-Policy"]')?.content
  ?? '(meta の CSP なし - レスポンスヘッダー側を確認すること)'
);
  • 外部ホストのリストが思ったより長ければ、その一つ一つがページ内でコードを実行できる主体である
  • integrity のない項目は、そのファイルが変わればそのまま実行される
  • 内容が頻繁に変わって SRI を掛けられないリソースなら、自前ホスティングへ移せるかを検討対象に上げる

14.4 5 分 - リセットトークンの形

自分のアカウントでパスワードリセットを要求してリンクを受け取る。確認するのはトークンの 形 と 寿命 である。

  • 長さは十分か。文字集合は何か。16 進数の文字列なら 5 節の基準で最低桁数を超えているか
  • 続けて二度要求したとき二つの値の間に目に見える規則性があるか。前半が同じだったり末尾だけ少しずつ変わったりするなら、時刻や連番が材料に使われている可能性がある
  • 一度使ったリンクをもう一度開くとどうなるか。そのままリセット画面が出るなら一回限りの処理がない状態である
  • リセットを終えた後、別のブラウザで開いておいた既存のログインがそのまま維持されるか
  • 存在しないアドレスでリセットを要求したときの応答文言が、存在するアドレスのときと同じか

前提の振り返り — ① と ②。 四項目のうち一つでもクライアント側の事情に頼っていればその地点が ① であり、リセットトークンの形に規則性が見えればその地点が ② である。

確認できなかったこと

本文に書かなかったものをここにまとめておく。根拠を確認できなかった内容は載せていない。

  • リセットトークンの具体的な有効期限。 OWASP Forgot Password Cheat Sheet はトークンを使用後に無効化するよう明記しているが、何分または何時間という 具体的な数値は示していない。本文で「短い有効期限」とだけ書いた理由である
  • 不完全な修正に対する短縮期限。 Project Zero の Vulnerability Disclosure Policy と Vulnerability Disclosure FAQ には 不完全な修正のための別個の短縮期限条項が明記されていない。確認できるのは 90 日の期限、パッチ後 30 日の公開、14 日の猶予、実際の悪用時の 7 日の期限と 3 日の猶予である。不完全な修正に関して引用できるのはポリシーではなく変種の再悪用についての 集計値 である
  • ブラウザ別の SameSite 既定値の現況。 MDN の Set-Cookie ページは「一部のブラウザが Lax を既定値として使う」とだけ記す。どのブラウザがどのバージョンからどう適用するかは各自の対象環境で確認する必要がある
  • 業界全体のパッチ遅延の中央値と未修正率。 公開資料ごとに標本と集計の定義が異なるため一つの数値として引用しなかった。12 節と 13 節が引用した数値は Project Zero が自らの追跡対象について発表した値であり、その範囲の外へ一般化されない
  • SRI が防げないものの公式なリスト。 MDN の Subresource Integrity ページは SRI が防げ ない 項目を明示的に列挙していない。本文の限界の記述は SRI の動作の定義から導かれる範囲までを書いたものである
  • NIST 用語集の信頼境界の見出し語。 NIST 用語集で該当する見出し語を確認できなかった。そのため 8 節の標準的な定義は CWE-501 の説明を引用し、Web に絞った定義はこの記事の作業定義であることを明示している
  • この記事のコード例。 説明のための形であり特定の実行環境で検証したコードではない。関数名やパスはすべて架空の値であり、実際の適用は各自のフレームワークが提供する機能を使うほうがよい

よくある質問

Q1. クッキーにユーザー番号がそのまま見えているが問題になるか

クッキーはサーバーが発行するが、保管するのはクライアントである。開発者ツールで値を書き換えて送り直せるため、その番号でデータを検索するサーバーコードがあると 検索対象の所有者とリクエスト送信者の関係は検証されないまま残る。OWASP Insecure Direct Object Reference Prevention Cheat Sheet は、この欠陥がオブジェクト、そのオブジェクトを指す参照、そして 欠けているオブジェクトレベルの認可チェック という三要素で成立すると整理している。OWASP Session Management Cheat Sheet は、セッション ID の値が情報漏えいを防ぐため 意味を持たないもの でなければならず機微情報や個人識別情報を含んではならないと求め、総当たり推測を防ぐために 最低 64 ビットのエントロピー が必要だと記している。対処は二つある。第一に、クッキーには意味のないセッション識別子だけを置き、利用者の身元はサーバーがその値で検索する。第二に、検索時に所有者の条件をクエリ自体に入れ、自分のものだけを見つけるようにする。識別子を推測しにくい値に変えることは代替にならない。同じ文書が、複雑な識別子を使ってもアクセス制御チェックは必須だと明記している。

Q2. SameSite を Strict にすれば CSRF トークンは不要か

OWASP Cross-Site Request Forgery Prevention Cheat Sheet は、SameSite を単独の防御として頼らず 多層防御の一層 として扱うよう明記している。理由は三つある。第一に、Lax は安全でないメソッドしか遮断しないため、状態を変える操作が GET で露出していればそのまま通る。第二に、SameSite の判定単位はオリジンではなく 登録可能ドメイン であり、同じドメイン配下の別ホストは同一サイトとして扱われる。第三に、ブラウザごとに既定値が異なる。MDN の Set-Cookie ページは、一部のブラウザが SameSite 未指定時に Lax を既定値として使うとだけ記し、既定として適用される Lax はより寛容な形式であり クッキーが設定されてから 2 分を超えていなければ POST リクエストにもクッキーが載る と説明している。Strict はこのうち第一と第三をかなり解消するが、第二は残る。したがってセッションクッキーに Strict を設定しても、状態を変えるリクエストには同期トークンか署名付きダブルサブミットトークンを併用する構成が推奨される。

Q3. HttpOnly を付けたのになぜまだ XSS が問題だと言われるのか

HttpOnly が防ぐのはただ一つ、スクリプトが document.cookie でそのクッキーの値を 読む ことだけである。MDN の Set-Cookie ページは、HttpOnly で作られたクッキーであっても JavaScript が開始したリクエストには依然として送信される と明記している。つまりページ内でコードが動いていれば、クッキーの値を読めなくてもそのクッキーが付くリクエストを作れる。値を盗み出す代わりに値を使う のである。同じ理由で OWASP Cross-Site Request Forgery Prevention Cheat Sheet は、XSS がすべての CSRF 緩和策を無効化すると強調して記している。ページ内で動くコードは正規の画面と同じ権限を持つため、トークンを DOM から読み取ってリクエストに付けられる。まとめると HttpOnly は流出経路を一つ狭める有用な制御であり、XSS そのものの対策は出力エスケープである。OWASP Cross Site Scripting Prevention Cheat Sheet は、innerHTML のような安全でないシンクへの参照を取り除くようコードをリファクタリングし、textContent や value を使うよう勧めている。

Q4. パスワードリセットのリンクが一度使った後も開くが問題ないか

OWASP Forgot Password Cheat Sheet は、リセットトークンを 使用後に無効化 するよう明記している。一度使ったリンクが再び開いてリセット画面が表示されるなら、その要件が実装されていない状態である。問題になる理由はこのトークンの性格にある。リセットトークンは有効な間、認証手段の代わりになる値であり、CWE-640 はこの欠陥を Weak Password Recovery Mechanism for Forgotten Password と名づけ、上位項目を CWE-1390 Weak Authentication と CWE-287 Improper Authentication としている。つまり 認証の欠陥として分類される。リンクはメールボックス、ブラウザ履歴、サーバーのアクセスログ、プロキシログ、リファラーに残りうるため、再利用が可能ならその残留物の一つ一つがアカウント乗っ取りの経路になる。あわせて確認すべきものが三つある。トークンに有効期限があるか、保存先には原文ではなくハッシュが保存されるか、そしてリセット完了後に既存のログインセッションがどうなるかである。同じ文書は、利用者にすべての既存セッションを無効化するか尋ねるか、自動的に無効化するよう勧めている。

Q5. ログにユーザー ID が残っていればその人がやったと言えるか

その ID が どこから来た値か によって変わる。値がリクエストボディやクライアントが変更できるクッキーから来たなら、その記録が意味するのは リクエストが自分をその利用者だと主張した という事実までである。値がサーバーセッションの検索結果から来たなら セッションがその利用者のものだった というところまで届く。ここからさらに二つが必要になる。OWASP Session Management Cheat Sheet は、セッション固定を、攻撃者が被害者のセッション ID を入手する代わりに被害者のブラウザにセッション ID を設定することと定義し、セッション ID の再生成がセッション固定攻撃を防ぐために必須だと記している。これがなければセッション自体の帰属が揺らぐ。そして CSRF 防御がなければ、セッションが本物でもそのリクエストが利用者の意思を意味しない。CSRF は定義上、利用者の意図なくリクエストが発生する攻撃だからである。NIST 用語集が SP 800-53 Rev. 5 から引用する否認防止の定義には ある個人が特定の行為を行ったかどうかを判別できる能力 が含まれる。その能力は識別制御が健全な分だけ成立する。

結論: この記事が主張する四つのこと

要約ではなく命題で閉じる。この記事が主張するのは四つであり、それぞれを支える節を併せて記す。

  1. クライアントから来た値を根拠に使うコードは、その値が何であれ検証されていない状態である。 フォームの値・data- 属性・クッキー・リクエストボディ・リクエストヘッダーがすべてこれに当たる。根拠: 4 節（クッキーの利用者識別子）、8 節（信頼境界の定義とサーバー再計算）、13 節（クライアントだけを直した修正）。
  2. 予測できる値は秘密ではない。秘密として扱う値は、その値を作った乱数源まで確認して初めて成立する。 根拠: 5 節（リセットトークンと CWE-640、Math.random() についての MDN の明示）、10 節（セッション値の帰属）。
  3. 個別の等級が低い欠陥も組み合わされば新しい経路を作り、項目単位の点検表はその経路を捉えられない。 根拠: 3 節（CSRF トークンの不在と SameSite=None の組み合わせ）、9 節（同じコードベース内の非対称）。
  4. 識別制御が崩れたシステムのログでは行為者を特定できない。これは利用者の保護であり運営者の保護でもある。 根拠: 10 節（否認防止の定義、ログ項目の出所別の証明範囲、セッション固定と CSRF がそれぞれ証明力に及ぼす影響）。
