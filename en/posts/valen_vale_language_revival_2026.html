The Golden Spike and the Revival of Vale(n) — Why Connect Directly to the Rust Compiler

A Six-Month Journey and Architectural Trade-Offs of Cross-Language Generics via rustc Patches and Group Borrowing

2026-09-19 Dev & Infra

The standard convention by which systems programming languages consume third-party libraries has remained essentially unchanged for decades. The default operational bridge is the C Application Binary Interface (C ABI). Regardless of how sophisticated a language is, developers carve out wrapper functions adhering to C function signatures, shuttle primitive integers and raw pointers across the boundary, and align CPU registers and stack frames to standard calling conventions. While this paradigm possesses the undeniable advantage of universal operating system and hardware support, it exacts an immense architectural tax: it forcibly reduces the expressive power of modern type systems down to their lowest common denominator.

The intricate challenges surrounding Rust language boundaries were analyzed from a different operational angle in an earlier study (Where Safety Ends at the Rust FFI Boundary - What extern fil-c Is Aiming At). That piece dissected how the compiler's rigorous lifetime and ownership tracking guarantees terminate abruptly at the extern "C" boundary, examining efforts to harden the underlying C runtime to mitigate boundary hazards. However, the architectural exploration examined here proceeds from a fundamentally different premise and pursues a vastly more ambitious objective. Rather than building defensive wrapper abstractions around legacy C code, it involves an entirely new programming language directly patching the internal machinery of the Rust compiler to preserve bidirectional generics and static safety invariants across the language divide.

Language architect Evan Ovadia has published the initial empirical findings from his new systems programming language, Valen, which builds upon the design legacy of his previous project, Vale. Rather than settling for conventional Foreign Function Interface (FFI) bindings, Valen incorporates rustc_driver directly into its compilation process and introduces an approximately 100-line patch to the Rust compiler itself. This enables the Valen compiler (valenc) and rustc to communicate dynamically during generic instantiation. This analysis investigates why the project chose this intrusive, high-risk compiler integration over standard C ABI bridges, the precise engineering mechanics employed, and the inevitable structural maintenance costs this architectural path entails.

1. Introduction: Why Reject the Conventional C ABI Detour

When an emerging programming language attempts to establish a foothold in the software engineering landscape, the most formidable barrier it confronts is rarely syntax aesthetics or compilation velocity; it is the total absence of a mature library ecosystem. Regardless of how elegant a language's static safety proofs might be, reimplementing mission-critical infrastructure from scratch—such as graphics rendering engines, asynchronous networking runtimes, file system drivers, and linear algebra libraries—is practically impossible for a nascent community. Consequently, virtually all new systems languages opt for compatibility with the C language, establishing an FFI layer that wraps established C and C++ libraries.

However, the instant the C ABI is chosen as the connective tissue, the sophisticated abstractions carefully constructed by modern type systems dissolve at the boundary. The C calling convention cannot interpret generic type parameters, nor does it comprehend affine ownership transfer semantics or compile-time lifetime scopes. If an engineer attempts to expose a high-performance graphics engine or parallel computation framework written in Rust through a traditional C ABI, rich structural types are inevitably degraded to opaque void* pointers, specialized monomorphic wrapper functions must be declared manually for every concrete data permutation, and static safety guarantees collapse into fragile developer-maintained discipline.

The traditional C FFI boundary imposes four fundamental structural information losses that severely constrain language ergonomics and safety:

  • Loss of Generic Metadata: Because the C ABI lacks any standardized convention for dynamic or compile-time template parameter evaluation, cross-language generic data structures cannot be instantiated across the interface.
  • Disconnection of Lifetime and Ownership Invariants: Even if both the calling and target languages possess rigorous borrow checkers, passing data through C reduces representations to raw pointers that escape the static analysis scope of both compilers.
  • Incompatibility of Trait and Virtual Dispatch Tables: Rust fat pointers, which bundle data references alongside vtable pointers, do not map cleanly onto single-word C pointer conventions without cumbersome manual glue code.
  • Severance of Coordinated Monomorphization: It is fundamentally impossible for the target language's compiler to generate tailored machine code on demand in response to bespoke types introduced by the caller.

Evan Ovadia concluded that if a new systems language is to genuinely harness the vast infrastructure of the Rust ecosystem—particularly its state-of-the-art graphics programming stack—it cannot rely on the narrow, lossy aperture of the C ABI. Instead, it requires a direct, compiler-to-compiler communication channel. This constituted an extreme engineering choice: penetrating the deepest phases of the compilation pipeline to dissolve the semantic boundary between two independent languages.

2. The Golden Spike Metaphor: Directly Joining Two Disparate Compilers

On May 10, 1869, at Promontory Summit in Utah, a historic ceremony marked the completion of the First Transcontinental Railroad in the United States. Following years of grueling labor through rugged mountain ranges and arid deserts, the rail network extending from the eastern states met the tracks advancing from the Pacific coast. To commemorate the momentous fusion of these two massive infrastructure systems, a 17.6-karat ceremonial golden spike was driven into the final railroad tie.

Evan Ovadia explicitly referenced this historical milestone in his public announcement, noting: 「To me, the phrase 'golden spike' means an incredibly difficult task joining two separate, distant systems」. In the domain of compiler construction, two independent compilers are separated by an architectural chasm far wider than physical geography. Each compiler maintains its own abstract syntax tree (AST), intermediate representation (IR), type inference engine, symbol resolution tables, optimization passes, and code generation backends. Operating systems and toolchains treat these systems as black boxes, making deep internal inspection and cross-compiler synchronization an extraordinary engineering hurdle.

When attempting to fuse two autonomous compilers directly into a single coordinated pipeline, developers confront four formidable architectural rifts:

  • Heterogeneous Type Representations: The internal data structures, type graphs, and memory layouts utilized by the two type checkers share virtually no common conventions.
  • Mismatched Pipeline Phases and Lifecycles: Lexing, parsing, semantic analysis, monomorphization, and code emission proceed at differing rates, with intermediate compiler data structures bound to conflicting lifetimes.
  • Complex Build Orchestration: Executing compilation requires two separate compiler drivers to operate in synchronized lock-step, continuously issuing reciprocal semantic queries across process or memory boundaries.
  • Instability of Non-Public Compiler APIs: In the absence of standardized external interfaces, the host system must bind directly to private, unversioned functions within the target compiler, creating severe ongoing fragility.

The Golden Spike for Valen was never envisioned as a basic static binary linkage. The architectural objective was to allow a Valen program to import Rust structures and traits natively, supply Valen-defined types as generic parameters to Rust libraries, and have both compilers collaboratively generate unified, optimal native machine code in a single seamless compilation pass.

3. From Vale to Valen: Evolution of Memory Safety and Group Borrowing

To fully contextualize Valen's architecture, one must examine Evan Ovadia's prior language endeavor, Vale. Vale was conceived as a high-performance systems programming language that eliminated garbage collection pauses without exposing developers to manual memory hazards such as dangling pointers and use-after-free vulnerabilities. Vale's foundational innovation rested upon pairing generational references with region borrowing.

3.1 Vale's Approach: Generational References and Region Borrowing

Vale's generational reference mechanism allocated memory alongside an integer generation counter, encoding that same generation number directly within the referencing pointer. Upon object deallocation, the generation count at the memory slot was incremented. Any subsequent dereference via an older pointer immediately detected the generation mismatch, aborting execution safely without memory corruption. Although this provided deterministic memory Reclamation without stop-the-world garbage collection pauses, it introduced unavoidable runtime checks on pointer dereferences.

To mitigate this runtime overhead, Vale incorporated region borrowing. When the compiler's static analysis could mathematically prove that an allocation would not be freed within a specific lexical scope or execution phase, it designated that scope a safe region. Within that region, generation counter comparisons were safely omitted, allowing raw pointer execution speeds. Nevertheless, because Vale's memory model relied on a hybrid arrangement of runtime generation tracking and static region verification, its conceptual foundation remained fundamentally distinct from Rust's pure compile-time affine ownership system, inhibiting friction-free interoperation.

3.2 Valen's Transition: Pure Compile-Time Group Borrowing

In designing Valen, Evan Ovadia abandoned generational references and their associated runtime metadata entirely. Instead, the language adopted the group borrowing paradigm formulated by researcher Nick Smith, pivoting entirely toward 100% compile-time static memory safety.

Group borrowing provides an alternative approach to static borrow checking that reduces the syntactic and cognitive overhead commonly associated with explicit lifetime annotations in Rust, while still maintaining provable freedom from data races and memory corruption. Rather than tracking individual references with bespoke lifetime parameters throughout call stacks, objects are categorized into logical borrowing groups. The compiler statically determines the boundaries of exclusive and shared access across these groups during compilation. This completely eliminates runtime generation checks, establishing structural semantic compatibility with Rust's borrow checker.

Safety Verification Timing Hybrid: static compile-time regions plus runtime generation checks 100% pure compile-time static analysis
Dereference Performance Overhead Runtime integer comparison when outside borrowed regions Zero runtime overhead (equivalent to bare native pointers)
Rust Ecosystem Compatibility Constrained to conventional, lossy C ABI wrapper layers Direct compiler coupling enabling native generic interop

The group borrowing model resolves several critical engineering imperatives essential for deep compiler-level interoperability:

  • Deterministic Zero-Overhead Memory Management: Retains raw machine-level execution performance without hidden heap headers, allocation tags, or dereference branching.
  • Semantic Alignment with Rust Types: Provides static invariants that map naturally onto Rust's shared (&) and mutable (&mut) reference rules.
  • Reduced Cognitive Burden: Shields developers from declaring intricate, contagious lifetime annotations across everyday function signatures by utilizing group inference.
  • Uncompromised Cross-Boundary Safety: Guarantees that passing data structures back and forth across the language boundary cannot invalidate the memory invariants of either side.

4. Technical Implementation: Invoking rustc as a Library and Patching the Compiler

Bridging Valen and Rust within an integrated build pipeline required abandoning the standard external process execution model. Standard build orchestrators invoke cargo or rustc as isolated subprocesses, aggregating emitted object files via an external system linker. However, an external child process cannot expose internal compiler symbol tables, macro expansors, or type structures for interactive querying during semantic analysis.

4.1 Embedding rustc via rustc_driver and run_compiler

To establish direct memory-level access, Evan Ovadia linked Rust's primary compiler interface, rustc_driver, directly into the Valen compiler executable (valenc). While the Rust compiler is widely consumed as a command-line binary, its internal architecture is modularized, exposing the rustc_driver::run_compiler entry point to allow embedding within host Rust applications.

When valenc invokes run_compiler, it supplies tailored compiler arguments alongside custom callback handlers implementing the rustc_driver::Callbacks trait. This hook permits the Valen compiler to intercept Rust's internal execution pipeline immediately following parsing, macro expansion, and dependency resolution. Consequently, Valen's type checking engine can directly query Rust crate metadata stored in active memory without resorting to disk serialization or IPC overhead.

4.2 The 100-Line Patch and MIR-Bypassing LLVM Pipeline

While rustc_driver exposes hooks into the compilation lifecycle, its standard public interface lacks the facilities required to instantiate Rust generic functions containing types originating from an alien language. The Rust compiler expects all types participating in monomorphization to exist within its own internal type contexts. Overcoming this fundamental roadblock required applying an approximately 100-line surgical patch directly to the Rust compiler codebase.

This patch introduces custom callback hooks into Rust's monomorphization and LLVM lowering infrastructure. Whenever the Rust compiler encounters a generic function call involving a Valen-defined type argument, the hook yields control back to valenc, allowing the Valen compiler to define the memory layout, field offsets, and calling conventions necessary to lower the specialized implementation into LLVM IR.

Furthermore, the architecture deliberately bypasses Rust's Mid-level Intermediate Representation (MIR). Instead of attempting the brittle task of translating Valen AST structures into valid Rust MIR to satisfy Rust's borrow checker, Valen utilizes its own dedicated LLVM backend. The LLVM module emitted by Rust and the LLVM module generated by Valen's native backend are merged directly at the LLVM IR stage, where whole-program optimizations and inlining take place seamlessly.

This compiler coupling strategy exhibits four key technical characteristics:

  • Monomorphization Phase Callback Hooks: Injects queries at the precise moment generic parameters are bound, allowing coordinated two-way code generation.
  • Isolation from Rust MIR Volatility: Avoids unstable, rapidly changing internal MIR structures by conducting integration at the LLVM IR layer.
  • Unified LLVM Code Generation Context: Enables LLVM optimization passes to inline functions and eliminate cross-language call frame overhead globally.
  • Minimal Surface Area Patch: Confines modifications to roughly 100 lines of rustc code, minimizing intrusive changes to Rust's core codebase.

5. Cross-Language Generics: Gains and Architectural Costs vs C Bindings

Valen's invasive compiler patching strategy was not pursued merely for academic intrigue; it was the essential, non-negotiable prerequisite for achieving true cross-language generics across the language divide.

5.1 Monomorphization and Type Metadata Preservation

In modern systems languages like C++ and Rust, generics rely on static monomorphization. When an application utilizes a generic structure such as Vec<T>, the compiler does not produce a generic runtime object; it generates specialized machine code tailored precisely to whether T is a 32-bit integer, a flat structure, or an allocated handle. This design guarantees contiguous memory allocation and unboxed execution speeds.

If a developer defines a custom structure in Valen—such as PlayerState—and wishes to store it within a Rust Vec<PlayerState>, the Rust compiler must know the exact byte layout, alignment requirements, and destruction semantics of PlayerState to emit valid code. The C ABI cannot facilitate this interactive negotiation. Only by directly coupling the compilers can valenc and rustc interactively exchange symbol metadata, enabling Rust to monomorphize collections around Valen types on the fly.

5.2 The Maintenance Burden of Internal Compiler Dependencies

While this deep integration yields unmatched expressive capabilities, it extracts a heavy ongoing toll in architectural debt. The standard C ABI is a permanent, immutable contract maintained by operating system vendors. In stark contrast, rustc internal interfaces are private implementation details that carry no stability guarantees whatsoever from the Rust Project.

The Rust compiler operates on a rapid six-week release cadence. Across minor version bumps, internal structures such as the type context (TyCtxt), the monomorphization collection algorithms, and internal LLVM lowering paths can be rewritten without warning. Even though Valen's patch is compact—spanning only about 100 lines—any substantive refactoring in upstream Rust middle-end passes risks breaking the integration or introducing subtle, silent compilation failures. The Valen project must commit to continuously tracking upstream Rust commits and maintaining its custom patch set in perpetuity.

This invasive compiler integration path imposes four major structural costs:

  • Upstream Version Pinning Risks: The language risks becoming trapped on specific rustc commit revisions, unable to readily adopt modern Rust compiler improvements.
  • Cumulative Compilation Latency: Hosting two massive compiler engines simultaneously in memory during a single build increases compilation times noticeably.
  • Compounded Debugging Complexity: Isolating internal compilation bugs becomes difficult when diagnosing whether failures stem from Valen, rustc patches, or LLVM lowering.
  • Developer Tooling Isolation: Standard developer utilities such as rust-analyzer and Clippy cannot natively parse the hybrid patched compiler pipeline.

6. First Empirical Validation: Interfacing Rust wgpu with Valen Closures

To demonstrate that deep compiler integration is an achievable engineering reality rather than an abstract theoretical paper, Evan Ovadia selected one of the most demanding real-world test cases imaginable: orchestrating a hardware-accelerated rendering pipeline powered by Rust's modern wgpu graphics library.

Graphics rendering engines represent an extraordinarily brutal validation environment for foreign language interoperation. They demand native OS window handle management, continuous asynchronous event processing, low-latency command queue submissions, and strict pointer alignment. In event-driven graphics architectures, handling user interaction and frame timing fundamentally requires registering callback closures directly within the framework's core event loop.

In this milestone demonstration, a Valen program directly called into a Rust graphics library built atop wgpu. When initializing the rendering window, a Valen closure implementing a Rust trait was passed directly into Rust's event loop as a callback. The Rust runtime received this closure, treated it as a first-class trait object, and invoked it on every frame dispatch. The Valen closure responded by issuing render pass commands directly to the GPU context, successfully outputting visual frames to the display.

Upon seeing the render window appear with the graphics pipeline executing smoothly, the author recorded the achievement in his technical log: 「At last, I got my first render」. This milestone confirmed that two compilers possessing divergent type systems had successfully executed coordinated monomorphization and unified LLVM code generation to produce a fully functional interactive GUI binary.

The successful wgpu demonstration established four critical technical validations:

  • Frictionless Trait-to-Closure Mapping: Valen closures satisfied the calling conventions and vtable layouts required by Rust trait implementations.
  • Stable Lifetime Management within the Event Loop: Memory allocated for Valen callback closures remained intact across ongoing Rust event dispatches without corruption.
  • Correct Hardware Acceleration Control: Low-level GPU pipeline states and command buffers traversed the language boundary without data corruption.
  • Unified Binary Code Emission: LLVM IR generated by both compiler frontends was consolidated into a single native binary without linker symbol collisions.

7. Current Limitations and Practical Perspective: Questions from Half a Year of Exploration

While this accomplishment is an inspiring technical milestone, professional software engineers must evaluate it with objective rigor. As explicitly underscored by Evan Ovadia, the project remains in an extremely early, experimental phase. The progress realized to date represents approximately half a year of intensive conceptualization, prototyping, hacking, refactoring, and redesign—principally concentrated within 2026—and does not signify a production-ready toolchain.

At present, the Valen compiler validates a proof-of-concept centered on the happy path. In production software engineering, a language must deliver comprehensive diagnostic reporting, friendly error messages, resilient IDE integration, robust dependency resolution, and deep multithreaded concurrency verification. Demonstrating that 100 lines of patch code can facilitate a graphics render is a distinct challenge from ensuring seamless operation across thousands of interconnected crates within an industrial enterprise application.

Before Valen can transition toward broader practical adoption, it must confront several daunting engineering hurdles:

  • Limited Diagnostic Capabilities: Mismatched generic constraints or ownership violations occurring at the language boundary often produce inscrutable compiler errors.
  • Unverified Asynchronous Integration: Interoperation with complex asynchronous runtimes, such as Tokio's work-stealing reactors, has yet to be demonstrated.
  • Unlikely Upstream Adoption: The probability of the official Rust Project accepting and maintaining permanent hooks within the core compiler for an external language is exceptionally low.
  • Ecosystem Tooling Fragmentation: Reconciling Cargo's automated build management with Valen's native build infrastructure presents significant packaging complexities.

Consequently, Valen should currently be understood not as an immediate replacement for existing systems tooling, but as a pioneering architectural probe mapping new possibilities for language interoperability.

8. Ecosystem Implications: A New Perspective on Systems Language Interoperability

Valen's audacious undertaking presents profound implications for the broader systems programming ecosystem. For decades, nascent systems languages have been trapped within the gravitational pull of C. Relying on the C ABI meant that any new language remained inherently bounded by the hazardous, antiquated memory models of the 1970s.

Evan Ovadia's work demonstrates that the next generation of systems languages can establish their foundations upon a new structural pillar: the Rust compiler itself. By treating Rust as baseline infrastructure rather than C, an emerging language can explore advanced type theories—such as group borrowing or linear types—without sacrificing access to an established, modern, memory-safe ecosystem.

While invasive compiler patching may not become the universal blueprint for every language designer, the underlying paradigm shift is undeniable. As modern compilers increasingly transition toward library-first architectures, the boundary between languages can migrate upward from raw machine code binaries to AST symbols and synchronized monomorphization passes. The history of software engineering demonstrates that transformative infrastructure often begins when ambitious engineers drive a golden spike across seemingly insurmountable divides.
