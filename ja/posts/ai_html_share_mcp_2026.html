AIが作ったHTMLをリンク一つで共有する - htmldropとMCPが開く成果物共有の形

MarkdownからHTMLへ移るエージェントの成果物、ホスティング型リンクとMCPサーバーが共有問題をどう解くか

2026年7月11日 開発・インフラ

はじめに: 成果物がリンクにならなければならない理由

少し前まで、AIエージェントの成果物の大半はMarkdownだった。チャット画面がそのまま描画してくれるテキスト、コードブロック、表がいくつかあれば十分だった。ところが最近では、エージェントに「レポートを作って」「ダッシュボードを組んで」「このデータをインタラクティブに見せて」と頼むと、結果は次第にHTMLとして返ってくるようになった。CSSでレイアウトを組み、チャートライブラリを組み込み、クリックすると値が変わる要素まで入っている。問題はその先にある。Markdownはチャット画面が勝手に描画してくれるが、HTMLファイルは受け取った側が自分で開かなければならず、そのためにはファイルをダウンロードするか、ローカルサーバーを立てるか、どこかにアップロードする必要がある。成果物の表現力が豊かになるほど、共有はむしろ面倒になるという逆説が生まれているのだ。

本稿で取り上げるhtmldrop(htmldrop.link)は、この問題に正面から取り組むオープンソースサービスだ。GeekNews(hada.io)には「Show GN: AIが作ったHTML、リンク一つですぐ共有(MCP対応)」というタイトルで投稿されていた。本稿はその紹介をそのまま転載するのではなく、htmldropが実際にどう動くのかを公式サイトとリポジトリのドキュメントで直接確認したうえで、これが指し示すより大きな流れ - エージェント成果物の形の変化、MCPが「公開」という行為そのものをツール呼び出しに変えるパターン、そして既存の代替手段との実質的な違い - を整理する。

1. htmldropとは何か - 正確な動作

htmldropのうたい文句は明快だ。「HTML成果物をAPI一回で共有可能なリンクに変える」というものである。誇張を取り除いて、実際に何を提供しているのか整理する。

1.1 三つの公開経路

htmldropは、HTMLをリンクに変える経路を三つ用意している。一つ目はWeb UIで、ファイルをドラッグ&ドロップするか、クリップボードから貼り付けるとすぐにリンクが表示される。二つ目はAPIで、POST /publish(JSON)、POST /publish/raw、POST /publish/from-urlの三つのエンドポイントを通じて、スクリプトやCIパイプラインから自動的に公開できる。三つ目はMCPで、これは後段で別途扱う。人間が使うにせよ、スクリプトが使うにせよ、エージェントが使うにせよ、HTMLコンテンツを渡せばレンダリング可能なURLが返ってくるという構造は共通している。

1.2 無料・容量・公開範囲

会員登録なしで無料で使え、ファイルサイズは最大25MBまで許容される。インラインのCSS・JavaScriptはもちろん、外部CDNリソースを読み込むHTMLもそのままレンダリングされる。リンクは基本的にパスワードなしで誰でも閲覧できる公開状態であり、必要であればパスワードを設定してアクセスを制限することもできる。公開が既定値であるという点は、後述する注意点と直結する。

1.3 有効期限の設計とオープンソース

すべてのリンクにはTTL(有効期限)が設定されている。無料ユーザーは7日間、オーナーキーを使えば30日間まで維持される。これはバグではなく、「共有された成果物が永遠に残り続けない」という明示的な設計意図である。また、htmldropはMITライセンスのオープンソースとしてGitHub(vin-spiegel/htmldrop)に公開されており、TypeScriptベースのコードをダウンロードして自社ドメインにセルフホスティングすることもできる。ストレージにはCloudflare R2かローカルファイルシステムを選択でき、本番デプロイにはワイルドカードDNSが必要だとドキュメントに明記されている。

2. なぜ今この問題が浮上したのか - MarkdownからHTMLへ

htmldropのようなツールが登場した背景を理解するには、エージェント成果物の形が最近なぜ変わってきているのかを見る必要がある。

2.1 成果物が「読むもの」から「見るもの」へ

初期のチャット型エージェントの成果物は、会話の延長にすぎなかった。質問に答える段落、説明を助けるコードブロック、整理のための表 - すべてMarkdownで十分だった。ところがエージェントが調査・分析・企画までを代行するようになると、求められる成果物の形が変わってきた。競合比較表を色分けして強調し、売上推移をチャートで描き、複数のシナリオをタブで分けて見せるといったリッチなレポートが必要になった。こうした表現はMarkdownの表現力を超えている。結果として、エージェントがHTML(とインラインのCSS・JS)を直接成果物として出す方向へ自然に移行しているわけだ。

2.2 Markdownの共有は簡単だったが、HTMLは違った

Markdownの強みは、どこでもレンダリングされるという点にある。チャット画面でもGitHubでもNotionでも、Markdownを貼り付ければその場で読める。一方HTMLは異なる。テキストのまま貼り付けるとタグがそのまま露出し、レンダリングさせるにはファイルとして保存してブラウザで開くか、どこかにホスティングしなければならない。エージェントが5行のダッシュボードHTMLを作ってくれたとしても、それを同僚に「リンク一つで」渡す手段はこれまで乏しかった。この隙間 - 成果物の表現力は上がったのに共有の利便性はそのままか、むしろ下がった状態 - こそが、htmldropのようなツールが埋める場所を作り出している。

2.3 ダッシュボード・インタラクティブ成果物の台頭

実際、最近のエージェントワークフローで頻繁に求められる成果物は、静的なテキストではなく、クリックでフィルタリングできるデータテーブルや、開閉できるセクション、簡単なJavaScriptで動くミニ計算ツールのようなものが多い。こうした成果物は、ファイル一つで完結する「単一HTMLアーティファクト」の形を取ることが多い。htmldropが特にビルド工程なしでHTML一つをそのまま受け取ってレンダリングすることに焦点を当てているのは、まさにこの単一ファイル成果物パターンを狙った設計だと見える。

3. MCP対応の意味 - エージェントが直接公開し、リンクを受け取る

htmldropの紹介で最も目を引くのは、API対応そのものよりもMCP(Model Context Protocol)サーバー対応である。これがAPI提供と別に意味を持つ理由を見ていく。

3.1 従来の方式 - 人間が間に入って運ぶ

APIしかない場合を考えてみよう。エージェントがHTMLを作っても、それをAPIで公開するには、誰か(あるいは別途書かれたスクリプト)が「このHTMLをhtmldropのAPIドキュメントを見て、エンドポイントに合わせたリクエストを作って送る」という手順を踏む必要がある。エージェントの立場からすれば、APIドキュメントを読み、認証方式を把握し、リクエストのフォーマットを合わせるという別途の学習・実装が必要になるということだ。

3.2 MCP方式 - ツール呼び出し一回

htmldropは/mcpエンドポイントでServer-Sent Events方式のMCPサーバーを立て、publish_htmlというツールを公開している。Claude Codeであればclaude mcp add --transport sse htmldrop https://htmldrop.link/mcpという一行でこのツールを登録でき、以降エージェントは「このHTMLを公開してリンクをくれ」という意図さえあれば、別途APIの仕様を読まなくてもpublish_htmlツールを呼び出してリンクを応答として受け取れる。リポジトリのドキュメントはこの目的を「エージェントがAPIドキュメントを読まずに即座に公開できるようにする」と明記している。

3.3 なぜこれが新しいパターンなのか

筆者が見るに、核心は「公開」という行為そのものがエージェントのループの中に入り込むという点にある。これまでエージェントは、コンテンツを作る役割までを担い、それを人間が見られるように配信する最後の段階は人間や別のパイプラインの仕事だった。MCPで公開されたツールは、この最後の段階までエージェントのツール利用範囲の中に組み込む。「レポートを作って、公開して、リンクを教えて」という一文の指示が、人間の追加介入なしに最後まで完結し得るということだ。これが単一サービスの利便機能を超えて、MCPが生み出す一般的パターン - ツールを呼び出して外部世界に結果を残し、その結果の参照(リンクやID)を受け取る - の一事例だという点が、より興味深い。

4. 類似アプローチとの比較 - Gist・Pastebin・Vercel・静的ホスティング・Claudeアーティファクト

HTMLであれテキストであれ、「作ったものをリンクで共有したい」というニーズ自体は新しいものではない。既存の代替手段とhtmldropが埋める場所がどこかを比較してみる。

4.1 GitHub Gist・Pastebin

GistとPastebinは、テキストやコードスニペットを素早く共有する用途で長く使われてきた。ただしHTMLをそのまま貼り付けても、基本的にはレンダリングされずソースコードとして表示されるだけだ(Gistのraw表示やGitHub Pagesとの連携といった迂回策を経てはじめてレンダリング可能になり、これはAPI一回で済む話ではない)。つまりテキスト共有には強いが、「HTMLをウェブページのようにすぐ見せる」という目的には元々設計されていない。

4.2 静的ホスティング(Vercel・Netlify・GitHub Pages)

VercelやNetlifyは、HTMLをレンダリングされるウェブページとして完璧にデプロイできる。しかしこれらは元々、継続的に運用するプロジェクトのためのツールだ。リポジトリ連携、ビルド設定、デプロイパイプラインという手順が付いて回る。エージェントが一度使って捨てるレポート一つを共有するために毎回プロジェクトを作ってデプロイするのは、あまりに重い。htmldropはこの重さを取り除き、「ファイル一つ、リクエスト一回、リンク一つ」に単純化した位置に立つ。

4.3 Claudeアーティファクト共有

Claudeの公開機能は、Claude内で作った成果物を公開リンクに変え、ログインなしで誰でも見て、さらにリミックス(フォーク)までできるようにする。ただしこれはClaudeのエコシステム内で作られた成果物に限定される機能だ。埋め込みスニペットも提供されるが、公開時はパスワードや有効期限なしで全面公開になるという制約があり(チーム・エンタープライズアカウントは組織内でのみ共有可能)、検索エンジンに露出する可能性もあると案内されている。htmldropは成果物の出所を問わない点、そしてTTLで既定の有効期限が設定される点で設計思想が異なる。

4.4 htmldropが埋める位置

整理すると、htmldropはGist・Pastebinの軽さと静的ホスティングの実際のレンダリングを組み合わせつつ、プロジェクト設定なしにAPI(あるいはMCPツール呼び出し)一回で完結するよう設計されている。その代償として長期保存性は放棄する。「継続的に運用するサイト」ではなく「今すぐ見せて、消えてもよい成果物」を狙ったツールであるという点が、他の代替手段との最もはっきりした違いだ。

5. 実務活用 - レポート・PRD・プロトタイプ共有

このようなツールが実務でどこに組み込めそうか、シナリオ別に見ていく。

5.1 調査・分析レポートの即時共有

エージェントに市場調査やデータ分析を任せ、その結果を表やチャートを含むHTMLレポートとして受け取ったなら、ファイルをダウンロードしてメッセージに添付する代わりに、リンク一つでチームに共有できる。受け取る側は特別なプログラムなしでブラウザだけ開けばよい。短いレビューサイクルの草案共有に適している。

5.2 PRD・企画文書の共有

プロダクト要求仕様書(PRD)をエージェントが構造化されたHTML(セクションの折りたたみ、優先度の色分け表示など)として作ってくれたなら、Slackやメールにリンクを貼るだけで関係者がすぐに閲覧できるようにできる。ただしPRDには機密性の高い事業情報が含まれることが多いため、後述する公開範囲の問題を併せて考慮する必要がある。

5.3 プロトタイプ・デモの共有

エージェントが簡単なUIプロトタイプやインタラクティブなデモをHTML/CSS/JS一ファイルで作った際、それを実際にクリックして試せる形で関係者に渡すには、レンダリングされるリンクが必要だ。正式リリース前に素早くフィードバックをもらう用途には、静的ホスティングより軽く、テキスト共有ツールより実際の動作を見せられる点で適している。

6. 注意点 - 機密情報・公開範囲・永続性・セキュリティ

便利さの裏側を確認しなければ不完全な分析になる。実際に使う前に確かめておくべき点を挙げる。

6.1 機密情報はそもそも載せない

htmldropのリンクは基本的にパスワードなしで、URLさえ分かれば誰でも閲覧できる公開リンクである。顧客データ、社内の財務数値、個人情報を含む成果物をこうしたサービスに載せることは推奨されない。パスワードのオプションがあるとはいえ、社内SSOや細かい権限管理のレベルのアクセス制御ではない。

6.2 公開範囲の既定値を確認する

「共有リンク」という言葉が与える印象とは異なり、リンクを知っているすべての人がアクセスできるという点をはっきり認識する必要がある。URLが予測不可能な文字列であっても、リンクがチャットやメールを経由して意図せず広がる可能性は常にある。Claudeアーティファクトの公開機能も同じ構造のリスクを抱えており、検索エンジンに索引付けされる可能性があると別途案内されている点も同じ文脈だ。

6.3 永続性を前提に使わない

無料リンクは7日、オーナーキーを使えば30日で失効する。これは長所でもあり制約でもある。長く参照する必要のある文書のURLにこのリンクを使ってはならない。逆に「今だけ見ればよい」用途には、自動失効がむしろ後片付けの負担を減らしてくれる。

6.4 セキュリティ - レンダリングされるHTMLという特性

htmldropはインラインJavaScriptと外部CDNリソースをそのままレンダリングする。これはインタラクティブな成果物を可能にする長所である一方、信頼できない出所のHTMLを開く際には注意が必要だということでもある。エージェントが自動生成したコンテンツを人間の検証なしにそのまま公開し、そのリンクを別の誰かが深く考えずに開く、という流れが繰り返されると、コンテンツの検証なしに信頼だけが自動的に連鎖する仕組みが生まれかねない。公開前に最低限の人間によるレビューを挟む習慣は依然として有効だ。

7. MCPエコシステムの文脈で見るhtmldrop

htmldrop単体を見れば小さなユーティリティだが、これが生まれた背景であるMCPエコシステム全体を見ると、より大きな流れが見えてくる。

7.1 MCPの成長と標準化

MCPはAnthropicが2024年11月に公開したオープンプロトコルで、AIアプリケーションと外部データ・ツールをつなぐ共通規格を提供する。その後OpenAI・Google DeepMind・Microsoftなどが相次いで対応を発表し、2025年12月にはAnthropicがMCPをLinux Foundation傘下のAgentic AI Foundationに移管し、特定企業所有ではないベンダー中立の標準へと転換した。公開されている稼働中のMCPサーバーが1万件を超えたという報道もある。htmldropのMCP対応は、この標準化されたエコシステムの上に乗る数多くのサーバーの一つだ。

7.2 「公開型」MCPサーバーという小さなカテゴリー

MCPサーバーは大きく、データを読み込むタイプ(ファイルシステム、データベース、検索)と、外部世界に何かを書き込んだり残したりするタイプ(イシュー作成、メッセージ送信、デプロイ)に分けられる。htmldropのpublish_htmlは後者に属し、その中でも「成果物を人間が見られる形で世に出す」という狭いが繰り返し必要とされるニーズを狙っている。こうした性格のツールは華やかではないが、エージェントが作った結果を実際に誰かに届ける最後の連結環という点で実用的な価値がある。今後も同様の目的(文書公開、PDF変換、簡易ウェブサイト配信)を持つMCPサーバーが増えていく可能性は高い。

7.3 標準プロトコルゆえの移植性

MCPがベンダー中立の標準であるという点は、htmldropのようなサーバーをClaude Codeだけでなく、CursorやMCP対応の他のクライアントでも同じ方式で使えるということを意味する。特定のプラットフォームに縛られず「公開ツール」をエージェントのツールチェーンに差し込めるという点が、閉鎖的なプラットフォーム別統合とは区別されるMCPエコシステムの実質的な利点である。

結論 - 便利だが用途を選んで使うべきツール

htmldropが示しているのは、大げさな技術革新というより、エージェント成果物の形の変化(Markdown→HTML)が生んだ実用的な隙間を正確に埋めた事例に近い。MCP対応は、この隙間を埋める方式をもう一段推し進め、「公開」という最後の段階までエージェントのツール呼び出しの範囲に取り込む。人間がファイルを移してアップロードしていた場所を、ツール呼び出しとリンクの返却が代わりに担う流れである。

ただし、これはあくまで速く軽い使い捨ての共有に最適化されたツールだ。公開リンクが既定値であること、TTLがあり長く残らないこと、アクセス制御が社内システムほどではないことを踏まえれば、機密情報を含む成果物や長期保管が必要な文書には向かない。逆に、プロトタイプのデモ、レポートの草案、会議前にさっと見せるダッシュボードのような「今見せて、消えてもよい」成果物には正確に合致する。ツールの便利さと、その便利さが前提とする条件(公開・失効・制御レベル)を併せて理解して使うのが正しい使い方だ。
