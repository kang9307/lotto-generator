1. The settings.json Structure - Core Areas to Know

All roads lead to settings.json. If you want to change how Claude Code behaves, you will eventually be editing this JSON file. The first thing to understand is that settings are layered. In general, a user-global setting (often ~/.claude/settings.json in your home directory), a project setting (.claude/settings.json in the repository), and a personal local setting (.claude/settings.local.json) all work together.

Why does this hierarchy matter? Because the same key behaves very differently depending on which file holds it, in terms of scope and shareability. Global settings affect all of your projects, project settings apply to every teammate who clones that repository, and local settings apply only to you. If you do not grasp this difference, you end up putting personal preferences that should never be forced on others into a shared file, or conversely placing a rule everyone needs into your own local file only.

The core areas you will most often touch in settings.json are roughly these:

  • permissions: defines which commands are auto-allowed or blocked
  • env: environment variables injected into the Claude Code session
  • model: specifies the default model to use
  • hooks: automation that maps shell commands to specific events
  • statusLine: customizes the bottom status line

The safest way to learn the structure is to start from an empty file and add one key at a time, verifying behavior as you go. JSON is strict about syntax, so a single missing comma can cause the whole file to be ignored. It pays to build the habit of making a small change and validating immediately.

There is a subtler reason the layering matters that many people learn the hard way: conflict resolution. When the same key appears in more than one layer, the tool has to decide which one wins, and the resolution is not always the naive last-one-wins you might assume. A permission denied at one layer may intentionally take precedence over an allow at another, because a safety-oriented design tends to let the more restrictive rule win. If you ever find a command being blocked even though you clearly added it to allow, the first thing I check is whether a higher-priority layer is quietly denying it. Understanding this precedence saves hours of confused debugging, and it is exactly the kind of behavior that is easy to misremember across versions, so confirm it against the current docs rather than trusting a blog claim, including this one.

2. Seven Lesser-Known Useful Settings

Now to settings you can actually put your hands on. All seven below are generally public features, yet surprisingly few people use them deeply.

2.1 Cut repetitive prompts with permissions allow

This is the most noticeable setting. Adding obviously safe, read-only commands like git status or ls to the allow list removes the friction of confirming every time. Just never broadly allow dangerous commands such as deletion or external transmission.

2.2 Inject per-project environment variables with env

Defining environment variables that only a given project needs under env spares you from exporting them by hand every session. As a rule, keep sensitive values like tokens in the local file, not the shared one.

2.3 Pin a model to the work with model

Setting a default model per project nature reduces the hassle of switching models constantly. You might configure a repository that needs heavy reasoning differently from one that is mostly light edits.

2.4 Automate formatters with hooks

Hooking a formatter to run automatically after files change keeps code style consistent without human hands. This is the heart of automation, so I cover it separately below.

2.5 Surface context with statusLine

Customizing the status line to always show the current branch, model, and directory is said to reduce context-switching cost.

2.6 Template repetitive prompts as slash commands

Saving frequently used instructions as slash commands means you no longer type long prompts each time. Make them team-shared commands and your workflow becomes standardized.

2.7 Adjust response tone with output styles

Output styles let you tune the format and tone of responses to your taste. Whether you prefer terse answers or richer explanations changes the experience.

3. Using Hooks - The Heart of Automation

Of all Claude Code settings, the one I consider most powerful is hooks. Hooks are understood to automatically run predefined shell commands when a specific event occurs. By attaching scripts to moments such as before and after a tool runs, or at session start, you let the tool handle chores you used to babysit yourself.

Representative use cases include:

  • Auto-formatting: run a formatter when a file changes to keep style consistent
  • Logging and auditing: record when certain commands run for traceability
  • Notifications: fire a desktop alert or message when a long task finishes
  • Guardrails: a safety check that inspects risky patterns in advance

That said, hooks are a double-edged sword precisely because they execute real shell commands. Feeding in unintended commands or untrusted input can be dangerous. So the approach I recommend is to start small. Attach just one safe action like a simple echo or a formatter run at first, confirm it triggers as intended, and expand gradually. The exact event names and input formats can differ by version, so treat the official documentation's hooks section as your reference.

One mental model I find useful is to treat each hook as a tiny piece of production software rather than a throwaway convenience. That means it deserves the same discipline: keep it idempotent so running it twice does no harm, make it fail loudly but safely so a broken formatter does not silently corrupt your flow, and keep it fast because a hook that adds several seconds to every tool call will quietly tax your whole day. I also strongly favor checking the hook's own command into the repository as a script the hook simply invokes, instead of inlining a long, unreadable one-liner in settings.json. A named script is easier to review, easier to test in isolation, and far less likely to hide a dangerous flag that nobody noticed during code review.

Where do hooks pay off the most? In my experience it is the boundary work that humans forget but machines never do: running the formatter on the exact files that changed, regenerating an index or a manifest after edits, or appending an audit line so that a teammate reviewing the session later can reconstruct what happened. None of these are glamorous, but their cumulative effect on consistency is large, and unlike a written team convention, a hook cannot be skipped because someone was in a hurry.

4. MCP Server Settings - Connecting Tools

MCP (Model Context Protocol) serves as the channel through which Claude Code connects to external tools and data sources. Registering an MCP server in your settings is understood to let the model access resources beyond the file system or invoke a particular service's capabilities. Attempts to handle database lookups, issue-tracker integration, or internal document search inside the tool all fall under this.

The point I want to stress in MCP configuration is to scope the connection carefully. MCP servers are powerful, so you must clearly control what they can access. It is safest to register only servers you trust and to restrict access to sensitive resources to the minimum necessary.

In practice I recommend connecting MCP selectively to the projects that need it rather than enabling it globally everywhere. For instance, activate an MCP server that touches internal data only in the relevant work repository, and do not connect it to personal experiment projects. Because the exact registration method and setting keys vary by version and server type, refer to each MCP server's guidance alongside the official documentation.

5. Customizing Slash Commands and Skills

Few things are as inefficient as typing the same long prompt over and over. Slash commands tackle this head-on. Save a frequently used instruction as a file, and a single short command recalls that long prompt.

I find team-shared commands especially valuable. Standardizing repetitive tasks like code-review checklists, commit-message rules, or pre-deploy checks as slash commands gets everyone working the same way. Quality that used to vary from person to person becomes aligned at the tool level.

On top of that, leveraging extension mechanisms like Skills lets you package an entire workflow beyond a simple prompt. You make procedural work, such as report generation or producing documents in a specific format, into a reusable unit. The exact registration locations and formats for commands and Skills can differ by version, so confirm the guidance for your current version when actually applying them.

6. Fine-Grained Permission Control - allow/deny Patterns

Permission settings are where productivity and safety collide head-on. Too many confirmation prompts break your flow; too broad an allowance invites accidents. Striking the balance between the two is the core of permissions.

Permissions are generally controlled through allow and deny lists in the permissions section of settings.json. Patterns in allow run without confirmation; patterns in deny are blocked. The principle I recommend is a conservative start.

  • Safe, read-only first: add only obviously safe commands like git status, git diff, and directory listings to allow.
  • Exclude dangerous actions: it is safest to keep file deletion, force push, and commands that send data outside off the auto-allow list.
  • Keep patterns narrow: overly broad wildcard allowances can trigger unintended execution, so specify as concretely as possible.

By refining the allow list incrementally this way, repetitive prompts shrink while control over dangerous actions stays intact. For the finer rules of pattern syntax and precedence, the official documentation for your version is the accurate source.

A trap I want to flag explicitly is the false economy of allowing too much too early. It is tempting, after the tenth confirmation prompt of the morning, to allow a broad pattern just to make the friction disappear. The problem is that broad patterns age badly: a wildcard that felt safe today can match a genuinely destructive command tomorrow when your tooling or your repository changes. My rule of thumb is that the allow list should grow from observed pain, not from anticipated convenience. Wait until a specific safe command annoys you repeatedly, then allow precisely that command, no wider. This keeps the list both small and meaningful, and it makes the occasional confirmation prompt informative rather than noise, because the prompts you still see are the ones that genuinely deserve a moment of attention.

7. Seven Productivity Tips

Beyond settings themselves, here are usage tips I have actually found effective. These are recommendations based on my experience, not absolute rules.

  1. Allow safe commands first: removing the read-only prompts you hit most often has the biggest felt impact.
  2. Bundle routines into slash commands: turn repeated instructions into commands and reuse them immediately.
  3. Start hooks small: instead of wiring up unverified automation all at once, add and confirm one at a time.
  4. Separate per-project settings: a tailored .claude directory per repository aligns context automatically.
  5. Keep sensitive values local: never put tokens and personal paths into shared files.
  6. Review settings periodically: when the tool updates, re-check your settings for deprecated keys.
  7. Version-control your settings: commit shareable settings to the repository so you can roll back when something breaks.

8. Sharing Team Settings - settings.json vs settings.local.json

If you use the tool alone, it hardly matters whether you have one settings file or two. But the moment you use it as a team, distinguishing the two files becomes a core discipline of collaboration.

The criterion is simple: should it be shared or not?

  • settings.json (shared): common team rules, standard permission policies, shared hooks, shared slash commands. Include it in version control so everyone gets it the moment they clone.
  • settings.local.json (personal): personal API tokens, local paths, experimental settings. Usually gitignored and not committed.

The benefit of this separation is clear. A collaborator gets the team standard automatically the instant they clone the repository, while you prevent personal preferences from clashing or sensitive information from being committed by accident. The most common accident I have seen is putting a personal token into the shared settings.json and committing it as is. Drawing a clear line between the two files' roles from the start structurally blocks this mistake.

9. Applying It in a Korean Dev Environment - Hangul Input, Intranet, Proxy

Using an overseas tool in a Korean environment always brings localization variables. Claude Code is no exception. Here are three things I especially recommend watching.

9.1 Hangul input and encoding

In a repository mixing Korean comments and Korean file names, encoding consistency matters. Standardizing on UTF-8 and aligning the encoding settings of your terminal and editor reduces garbled-Hangul problems.

9.2 Intranet and security policy

On strict intranets such as finance or public sector, external connections are often restricted. Narrow the access scope of MCP servers and external integrations to match internal policy, and configure permissions and connections conservatively so sensitive data does not leave the network.

9.3 Proxy environments

If you must go through a corporate proxy, correctly setting the proxy-related environment variables is the first button to fasten. Standard variables like HTTP_PROXY and HTTPS_PROXY are generally used; since the exact approach varies by tool version and internal network setup, it is safest to confirm with your infrastructure team.

10. A Caution - Version Differences and Checking the Official Docs

If you have read this far, please remember one thing: Claude Code is a fast-evolving tool. Setting key names, hook event names, and permission pattern syntax can be added, changed, or deprecated across versions.

So I urge you to read everything here as general principles of use. Rather than asserting that a specific version behaves in exactly this way, the goal is to give you a sense that these categories of settings exist and can be used in these ways. At the actual application stage, be sure to check:

  • the official documentation for the version you installed
  • the current-version guidance from the in-tool help slash command
  • small-scale behavior verification after changing settings

Blog and community posts are an excellent starting point for ideas, but content that asserts how a specific version behaves should be cross-checked against the official docs. I hope this article serves as one such starting point.

11. Conclusion and Three Things to Apply Right Now

Claude Code's real power comes not from the model alone but from the settings that tame that model to your workflow. The phrase hidden settings does not mean secrets; it is closer to an invitation to make territory that already exists, but that many people pass by, your own. Here are three things you can apply today.

  • Add safe commands to allow: removing the read-only prompts you hit most often cuts friction immediately.
  • Turn repetitive prompts into slash commands: replacing long instructions you typed each time with a one-line command raises both speed and consistency.
  • Separate shared and local settings: dividing the roles of settings.json and settings.local.json from the start structurally prevents collaboration accidents and leaks.

Settings are not a one-and-done artifact but a living asset that grows with the tool. The habit of starting small, verifying, and expanding is the surest path to making Claude Code beyond the docs truly your own.
