LiteLLMを2,900行に削ぎ落としたlitelm - ルーティングだけを残して何を捨てたのか

10万行超の巨大プロキシから呼び出し経路と変換層のみを抽出した軽量設計、19プロバイダーの検証状況とAI開発透明性告知の実務的意味

2026-09-13 開発・インフラ

現代の生成AIアプリケーション開発において、多様な大規模言語モデル（LLM）プロバイダーを統一されたインターフェースで抽象化する作業は、もはや不可欠な基盤設計となっています。OpenAI、Anthropic、Groq、Mistralなど、各ベンダーごとにエンドポイント規格、パラメータ命名規則、ツール呼び出しスキーマ、エラーレスポンス構造が大きく異なるためです。このようなマルチベンダーの分断を解決するために最も広く普及してきたPythonライブラリが、BerriAIが開発したLiteLLMでした。エンジニアはcompletion(model="anthropic/claude-3-5-sonnet", messages=[...])のように、親しみのあるOpenAIフォーマットで様々なモデルを透過的に呼び出すことができました。

しかし、長期にわたる開発と機能追加を経て、LiteLLMは単なるクライアント変換ライブラリの域を大きく超えていきました。エンタープライズの統合要件に応えるため、独立した高機能プロキシサーバーデーモン、RedisやSQLiteを用いた分散キャッシュ層、組織単位の予算管理やトークン費用追跡、独自のガードレール機能、エージェントスケジューラー、マルチモーダル処理パイプラインなどが次々と組み込まれ、コードベースの規模は10万行（100k+ LOC）以上へと膨張しました。数多くの実務システムが真に必要としているのは「モデルルーティングとメッセージフォーマット変換」という中核の呼び出し経路だけであるにもかかわらず、ライブラリを導入するだけで数十個の間接依存関係と重い初期化オーバーヘッドを抱え込むという構造的摩擦が生じていました。

オープンソース開発者のKenneth Wolters氏が公開したlitelm（lが1つ少ない名称）は、まさにこの過剰な肥大化に対する明快なアンサーとして登場したプロジェクトです。元のLiteLLMを敵対的に置き換えるのではなく、その巨大なコードベースの根底にある本質的な呼び出し経路のみを精密に抽出し、わずか約2,900行のPythonコードと、たった2つの依存関係（openai、httpx）で再実装したミニマリストなサブセット（部分集合）です。本稿では、フレームワークの肥大化がもたらす実務上の課題、litelmが意図的に削ぎ落としたものと残したもの、プロバイダー検証の実態、DSPy連携、そしてAI支援開発の透明性告知が提起する新たなエンジニアリング標準を詳細に分析します。

10万行のフレームワークと2,900行のコア — litelmの登場背景

ソフトウェアライブラリがユーザーコミュニティを拡大していく過程で、機能追加（Feature Creep）が累積していく現象は普遍的なものです。LiteLLMも当初は「あらゆるLLMをOpenAI規格で呼び出す」という極めてシンプルな目標から出発しましたが、企業ユーザーの多様な要望を吸収するにつれて構造が巨大化していきました。集中管理型のAIゲートウェイとして機能するためのプロキシサーバーデーモン、ユーザー別APIキー管理、データベース接続、音声認識、OCR、画像生成、ファインチューニングのパイプラインなどが同一リポジトリ内に次々と同居するようになったのです。

しかし、マイクロサービス内部のバックエンド処理や、単一責任の原則に従う自律型コーディングエージェント、軽量なCLIツールを構築する開発者の観点から見ると、このような周辺機能の集約は無視できない技術的負債をもたらします。具体的には、以下の4つの深刻な摩擦が発生します。

  • 依存関係の爆発とサプライチェーンリスク: 多数の外部プロバイダーSDKや補助ユーティリティを直接・間接に参照することで、パッケージ配布サイズが肥大化し、環境内でのライブラリバージョン衝突（Dependency Conflict）を解決するための工数が増加します。
  • セキュリティ監査と脆弱性スキャン負荷: 企業のセキュリティポリシー上、導入されたライブラリの全コード行は静的解析（SAST）や脆弱性（CVE）スキャンの対象となります。10万行におよぶコードベースでは、自社アプリケーションが決して実行しない機能に起因するアラートによってCI/CDパイプラインが停止する事態が頻発します。
  • ランタイムメモリとインポートの遅延: 多数のサブモジュールを走査してインポートする過程でPythonプロセスの初期起動時間（コールドスタート）が著しく悪化し、AWS Lambdaやエッジコンピューティング環境でレイテンシ低下の原因となります。
  • デバッグの不透明性と挙動予測の困難さ: プロバイダーAPI呼び出し時に異常なレスポンスが返ってきた際、内部のプロキシインターセプター、キャッシュ機構、費用追跡フックのどこでリクエストが加工されたかを特定することが極めて難しくなります。

litelmの作者であるKenneth Wolters氏は、まさにこの点に着目しました。大半の開発者がLiteLLMに期待している本質的な価値は、provider/model形式でターゲットを指定し、異なるメッセージ規格を相互変換してくれる呼び出し経路（call path）そのものにあります。litelmはこの中核ロジックのみを約2,900行に濃縮して切り出し、基本依存関係をopenaiとhttpxのわずか2つに限定することで、システムの複雑性を根本から解消しました。

何を残し何を削ぎ落としたのか — 機能比較と設計境界

コード行数を10万行から約2,900行へと30分の1以下に削減したということは、それだけ明確で妥協のない設計境界（Cut-off）を設けたことを意味します。litelmは単にコードを圧縮したのではなく、純粋なクライアントライブラリの責務から逸脱したレイヤーを計画的に削ぎ落としました。公式READMEに明記された両者の機能対比は以下の表の通りです。

メッセージ形式変換（Anthropic, Bedrock, Cloudflare, Mistral） ✓ ✓
ストリーミングおよびstream_chunk_builder対応 ✓ ✓
ツール利用・関数呼び出し（Tool use / Function calling） ✓ ✓

キャッシュ・予算管理・費用追跡（Caching / Budgeting / Cost Tracking） ✓ ✗
トークンカウント機能（Token counting） ✓ ✗
マルチモーダル拡張（画像生成、音声、OCR、ファインチューニング） ✓ ✗

この対比表が示す設計意図は明瞭です。litelmが除外した領域は、決して技術力が足りずに省かれたのではなく、クライアントSDKが持つべき責務の外側にある機能を意図的に切り離した結果です。

  • Routerクラスの除外: プロバイダー間の負荷分散やエラー時の自動迂回処理は、上位のインフラゲートウェイやオーケストレーターが担当すべき領域であり、プロセス内のSDKに抱え込む必要はないという判断です。
  • プロキシサーバー機能の排除: バックエンドサーバーデーモンとしての役割を完全に排除し、呼び出し元のプロセスに直接リンクされるインプロセスライブラリとしての純粋性を維持します。
  • キャッシュと費用追跡の切り離し: データベース接続やキャッシュ有効期限、トークン単価テーブルをSDK内に内包すると、各社の価格改定に伴う追従遅れが発生します。これを潔く排除しました。
  • トークンカウンターの省略: Tiktokenをはじめとするプラットフォーム依存のネイティブバイナリを強制せず、プロバイダーが返却する生のusage情報処理に専念します。
  • マルチモーダルやチューニングの非搭載: テキスト生成、ストリーミング対話、埋め込み生成というテキストLLMの中核ユースケースに集中し、コードの攻撃面を極限まで狭めました。
  • ガードレールやエージェント抽象化の排除: コンテンツフィルタリングやエージェントの状態管理は、アプリケーション側のビジネスロジックに委ねられます。

19プロバイダーのルーティングと検証現況 — 本番適用の境界線

litelmはprovider/model-name構文を通じて、合計19のプロバイダーへのルーティングをサポートしています。また、OpenAI仕様に準拠したあらゆるローカルまたはカスタム推論サーバーは、api_base引数を指定することで制約なく接続可能です。しかし、実務の本番運用を見据えるエンジニアにとって不可欠なのは、構文上の対応（Supported）と動作の実証（Verified）の違いを冷徹に把握することです。

公式READMEでは、対応プロバイダーの一覧とともに、実際に挙動の信頼性が実証されているかどうかが明確に開示されています。以下の表は、litelmが定義する19プロバイダーのハンドラー実装および検証ステータスの一覧です。

この検証マトリクスは、実務導入における極めて明確な境界線を示しています。現在、独自のテストおよびライブ呼出しを通じて安定性が公式に確認されている（Verified: Yes）のは、OpenAI、Anthropic、Groq、Mistral、xAI、OpenRouter、Azureの7社です。これらの主要ベンダーを主力として運用しているシステムであれば、litelmは即座に高い信頼性をもって導入できます。

一方で、AWS Bedrock、Cloudflare、DeepSeek、Together、Fireworksや、ローカル推論環境（Ollama、vLLM、LM Studio）を含む残る12のプロバイダーは未検証（Verified: No）です。これらはルーティング構文やフォーマット変換器のコード自体は存在しているものの、ベンダーの最新APIスキーマやエッジケースに対する十分なライブテスト保証がなされていません。したがって、本番導入に際しては以下の4つのガイドラインを守る必要があります。

  • 検証済み7社を中心とする段階的移行: クラウドLLMトラフィックの大半を占めるOpenAI、Anthropic、Azure、そして超高速推論のGroqを対象に先行して置き換えを進めます。
  • 未検証プロバイダー利用時の単独事前テスト: DeepSeekやBedrockをlitelm経由で呼び出す場合は、自社のステージング環境においてストリーミングや関数呼び出しの整合性を自ら検証する必要があります。
  • ローカル推論サーバーとの整合性確認: api_baseを用いたvLLMやOllamaとの通信では、推論サーバー側が返却するOpenAI互換レスポンスのスキーマ厳密性を事前にテストします。
  • パッケージバージョンの固定（Pinning）: 本プロジェクトは現在Alpha段階にあるため、不意の仕様変更による破損を防ぐため、pyproject.tomlなどでバージョンを厳密に固定して運用します。

コード変更を最小限に抑えるドロップイン互換性 — 基本呼出しから非同期・ストリーミングまで

litelmの最大の強みは、LiteLLMとの完全なドロップイン（Drop-in）互換性にあります。すでにLiteLLMを使用している既存コードベースであれば、アプリケーションのビジネスロジックに手を加えることなく、インポート文においてs/litellm/litelm/の置換を行うだけで即座に切り替えが完了します。関数シグネチャ、引数名、戻り値のオブジェクト形式が完全に一致しているためです。

インストールは必要最小限の依存関係で構成されており、特定のクラウドSDKを必要とする場合のみ追加のオプションを指定します。

pip install litelm                # openai + httpx
pip install litelm[anthropic]     # + anthropic SDK
pip install litelm[bedrock]       # + boto3
pip install litelm[all]           # everything

基本となる呼び出しフローは、単一の補完（Completion）、ストリーミング生成、そして埋め込み（Embeddings）で構成されます。以下はREADME原文に記載されている標準的な使用例です。

import litelm

# 基本補完 (Basic completion)
response = litelm.completion("openai/gpt-4o", messages=[{"role": "user", "content": "Hello!"}])
print(response.choices[0].message.content)

# ストリーミング (Streaming)
for chunk in litelm.completion("groq/llama-3.1-70b-versatile", messages=[{"role": "user", "content": "Hello!"}], stream=True):
    print(chunk.choices[0].delta.content or "", end="")

# 埋め込み (Embeddings)
response = litelm.embedding("openai/text-embedding-3-small", input=["hello world"])

高スループットな非同期サーバーやエージェントループのために、すべての主要関数に対応する非同期版（Async variant）が標準提供されています。READMEに記載されている非同期関数は、acompletion、aembedding、aresponses、atext_completionの4種です。

さらに、プロバイダーごとに異なるエラーレスポンスは、litelm独自の統一された例外階層へとマッピングされます。ベンダー固有の生のエラーペイロードを解析する必要がなく、共通の例外ハンドラーを用いて堅牢なリトライ処理を記述できます。

from litelm import ContextWindowExceededError, RateLimitError, AuthenticationError

try:
    response = litelm.completion("openai/gpt-4o", messages=[{"role": "user", "content": "Hello!"}])
except ContextWindowExceededError:
    # トークン超過時はプロンプトを切り詰めて再試行
    pass
except RateLimitError:
    # レート制限発生時はバックオフを適用
    pass
except AuthenticationError:
    # APIキー無効時のエラー処理
    pass

エージェント実装の中核となるツール呼び出し（Function calling）も、OpenAI標準のスキーマを完全にサポートし、呼び出し先プロバイダーの規格に合わせて自動的に引数をシリアライズします。

tools = [{"type": "function", "function": { "name": "get_weather", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}}, }}]

response = litelm.completion(
    "openai/gpt-4o",
    messages=[{"role": "user", "content": "Weather in Paris?"}],
    tools=tools,
    tool_choice="required",
)

tool_call = response.choices[0].message.tool_calls[0]
print(tool_call.function.name, tool_call.function.arguments)

社内クラスターに配置された自社ホスティングモデルやローカル開発環境への接続は、api_base引数を指定するだけで完了します。

# vLLM環境
litelm.completion("openai/my-model", messages=[{"role": "user", "content": "Hello"}], api_base="http://localhost:8000/v1")

# Ollama環境
litelm.completion("ollama/llama3", messages=[{"role": "user", "content": "Hello"}], api_base="http://localhost:11434/v1")

# LM Studio環境
litelm.completion("openai/local-model", messages=[{"role": "user", "content": "Hello"}], api_base="http://localhost:1234/v1")

DSPy連携とアップストリームコミット監査 — Alpha段階の信頼性検証

新規の軽量ライブラリが登場した際、最も懸念されるのは「複雑なLLMオーケストレーションフレームワークと結合した際に、微小なスキーマ不整合で破綻しないか」という点です。litelmは現在Alphaステータスですが、その互換性を担保するために2つの厳格な工学的検証を実施しています。

第1の検証は、スタンフォード大学の宣言型LLMフレームワークであるDSPyとの完全なドロップイン連携検証です。DSPyはプロンプトをコンパイル可能なプログラムとして扱う性質上、モデル入出力の厳密なプロトコル整合性を要求します。litelmは以下の7つの実行パスすべてを実際のライブ環境でパスしています。

  • Predict: 最も基本的な単一入出力予測モジュール経路
  • CoT（Chain of Thought）: 段階的な推論過程を生成する多段思考経路
  • Typed Signatures: Pydanticによる型制約を課した厳格なシグネチャ経路
  • Streaming: 逐次的なトークン受信を行うストリーミング経路
  • Embeddings: ベクトル検索モジュールに用いられる埋め込み生成経路
  • Tool Use: 外部関数を実行してコンテキストに再反映するツール利用経路
  • Multi-output: 複数の候補や構造化フィールドを同時に出力する生成経路

第2の検証は、本家LiteLLMのコミット履歴に対する徹底したアップストリーム監査（Attestation）です。2026年9月11日付のメンテナー監査報告によると、LiteLLMのルーティングおよびフォーマット変更について、コミット649eb2dから9a715df2までを網羅的に照合しました。この監査では中核経路のコミット360件を精査し、発見された互換性の差異をテスト駆動（Test-first）で修正しました。

現在、litelmのテストスイートはローカルスコープテストで262件合格（262 passed, 55 skipped）を記録し、LiteLLMから移植されたコントラクトテスト75件もすべて合格しています。スキップされた55件はローカル環境で未設定のクラウドAPIキーを要するテストであり、現行の依存関係ロックのもとで契約仕様の整合性が確定的に担保されています。さらに、実際のAPIキーを用いた45件のプロバイダーライブテストと10件のDSPyスモークテストもすべて合格しています。テスト実行コマンドは以下の通りです。

# ローカル非ライブテスト (262件合格)
uv run --extra all pytest tests/ -x --ignore=tests/ported --timeout=10

# アップストリーム高速コントラクトテスト (49件)
bash scripts/ported_contract.sh

# プロバイダーライブテスト (45件)
uv run --extra all pytest tests/test_live.py -m live --timeout=30

# DSPy統合スモークテスト (10件)
uv run pytest tests/test_dspy_smoke.py -m live --timeout=60

AI支援開発と透明性の告知 — ClaudeとGPT-5.5が記述したオープンソースの意味

litelmのドキュメントにおいて、技術的に極めて注目に値するのが開発方式の透明性告知（Development transparency）です。作者はソフトウェアの成立過程を隠蔽せず、客観的事実として次のように明記しています。

"litelm is human-directed, AI-assisted software. Much of the code was written with Claude Code using Claude Opus 4.6/4.7. Code written from 2026-05-14 onward is written through Pi using GPT-5.5. Compatibility claims are based on tests and maintainer review, not AI authorship."

この告知は、AIコーディングツールが日常化した現代の開発文化において、極めて重要な3つの原則を示しています。

  • 人間主導とAI支援の明確な区分: アーキテクチャの設計や不要機能の切り捨てという意思決定は人間の主導（Human-directed）で行われ、コード生成にはClaude CodeとClaude Opus 4.6/4.7が活用されたことが明言されています。
  • 開発ツールの移行履歴の記録: 2026年5月14日以降のコードは、Pi（ツール）とGPT-5.5を用いて執筆されたというツールの変遷が日付とともに正確に記録されています。
  • 品質保証の客観的根拠: 最も本質的な点は「互換性の主張はAIが書いたこと自体に基づくのではなく、網羅的なテスト通過とメンテナーによるレビューに基づいている」と強調している点です。誰が、あるいはどのモデルが書いたかではなく、決定論的なテストの成功こそがソフトウェアの信頼性を担保するという原則です。

AIエージェントによるソフトウェア作成が一般化する中、使用したツールとモデルを透明に開示し、その上でテストによって品質を証明する姿勢は、オープンソース開発における新たな誠実さの基準を示しています。ツールの出自を曖昧にせず、検証の客観性に立脚することこそが、コミュニティからの持続的な信頼を獲得するための決定的な鍵となります。

クライアントSDKの最小化とプロキシ型ルーターの違い — アーキテクチャ選定基準

マルチプロバイダーLLMインフラを構築する際、エンジニアが混同しやすいのが「インプロセスのクライアントSDK」と「独立プロセスのネットワークプロキシ」の役割の違いです。本ブログの先行記事であるすべての呼出しを旗艦モデルに任せない - APIをそのままにモデルを動的切替するLLMルーターとSwitchyardで取り上げたNVIDIA NeMo Switchyardがネットワーク層でリクエストを仲介するプロキシであるのに対し、litelmはアプリケーションプロセス内で直接動作するクライアントライブラリです。

両者は競合するものではなく、アーキテクチャの要件に応じて適切に選択されるべき技術です。選択の基準は以下の4点に整理できます。

  • 単一Pythonプロセスか多言語分散環境か: 純粋なPython環境で低遅延な呼び出しを完結させたい場合、litelmのようなインプロセスSDKがネットワークオーバーヘッドなしで最良の選択肢となります。一方、GoやNode.jsなど多言語環境が混在する組織では、SwitchyardやLiteLLM ProxyのようなHTTPプロキシが不可欠です。
  • 静的ルーティングか動的エスカレーションか: provider/modelによるエンドポイントの切り替えが主目的であればlitelmで十分です。しかし、ツールの実行失敗履歴を解析して上位モデルへと動的に引き上げる（Stage Router）適応型制御が必要な場合は、Switchyardのようなプロキシ層が求められます。
  • 運用オーバーヘッドと攻撃面の最小化: コンテナサイズを抑え、独立したデーモンプロセスなしにサーバーレスで運用したい場合、2,900行のlitelmは保守性の観点から圧倒的に有利です。
  • 全社的な予算管理と共有キャッシュの要否: 組織横断でのトークン消費量上限管理や、Redisによるプロンプトキャッシュ共有を中央で統制したい場合は、フル機能のLiteLLMプロキシサーバーの導入が適しています。

litelmの真の価値は、巨大なフレームワークを盲目的に受け入れるのではなく、システムに真に必要な中核機能のみを選択できるアーキテクチャの自由度を取り戻した点にあります。

  • 高並行非同期環境における詳細な性能・メモリ実測ベンチマーク: 秒間数千リクエスト規模のasyncioイベントループにおいて、litelmと本家LiteLLMのP99レイテンシおよびメモリ消費量の差を直接比較した公式ベンチマークデータは開示されていません。
