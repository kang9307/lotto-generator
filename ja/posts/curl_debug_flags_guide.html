序論: リクエストが遅いときに原因を数値で切り分ける

外部APIやWebサーバーへのHTTPリクエストが著しく遅延した際、エンジニアが最初に直面するのは遅延が発生しているネットワーク層の特定が難しいという問題です。ドメイン名を解決するDNSルックアップで待たされているのか、中間ルーターやファイアウォールを越えたTCP 3ウェイハンドシェイクで引っかかっているのか、TLSの証明書検証や暗号交渉に時間を取られているのか、それともサーバー側アプリケーションの処理遅延により最初の1バイト（TTFB）が遅いのか、感覚的な推測だけでは原因を断定できません。

この疑問を客観的な数値で切り分ける最も身近な道具がターミナルの curl です。しかし、単に curl https://example.com/ を実行したり time コマンドで囲んだりするだけでは、全体の往復所要時間という単一の数字しか得られません。curlが備える強力な診断フラグである -w（--write-out）と -v（--verbose）を適切に組み合わせることで初めて、各段階の遅延をミリ秒単位で分解できます。

本稿は単なるオプションの網羅的な一覧記事ではありません。リクエストが遅延または失敗した際に、どの区間で何ミリ秒を消費したかを数値で正確に切り分ける手順を解説します。特に -w で読み込むフォーマットファイルから改行が消失する意外な仕様、フォーマットファイル9項目のうち累積して増加する6つの時間指標から差分を算出する計算式、Windows Schannel環境下における詳細ログの特性、そして終了コード（exit code）28・6・22の実測検証をまとめます。

関連するネットワークプロトコルの基本原理については、別稿で詳しく解説されています。DNSの階層的キャッシュ構造はDNSキャッシュが教えるもの、TLSハンドシェイクの歴史的変遷はSSLで学んだことが今なぜ誤りなのか、シェルスクリプトでの終了コード判定はシェルの終了コードとset -e、ターミナル完結のHTTPクライアントはSlumberターミナルHTTPクライアントを併せて参照してください。

2. フォーマットファイルの改行の罠 - 物理的な改行を捨てる curl

curlの -w オプションは、通信完了後にカスタム書式に従って詳細な転送統計を標準出力に印字します。計測する変数が増えるとコマンドライン引数が長大になるため、公式ドキュメントで推奨されている @filename 構文を用いて別ファイルから書式を読み込ませる方法が一般的です。

2.1 物理的な改行を入れた際の1行連結現象

最初にフォーマットファイルを作成する際、多くのエンジニアは通常のテキストエディタで行を区切るように各変数の後ろで改行キーを押します。以下は、9行で構成された curl-format.txt を作成して呼び出した実験です。

printf 'namelookup:    %%{time_namelookup}\nconnect:       %%{time_connect}\n…remote_ip:     %%{remote_ip}\n' > curl-format.txt
cat curl-format.txt
curl -s -o /dev/null -w @curl-format.txt https://example.com/

ファイル内には確かに9つの独立した行が存在していたにもかかわらず、curlの画面出力には全く異なる結果が現れました。

namelookup:    %{time_namelookup}
connect:       %{time_connect}
…(ファイルには9行存在)
=== run 1
namelookup:    0.023826connect:       0.150990appconnect:    0.571661pretransfer:   0.571741starttransfer: 0.711580total:         0.734726http_code:     200size_download: 713remote_ip:     172.66.147.243=== run 2

ファイル内に存在していた物理的な改行文字が完全に無視され、すべての出力項目が1つの長い文字列として連結されてしまいました。スクリプトで行ごとに値をパースしようとする処理が破綻する瞬間です。

2.2 文字通りの \n を記述すべきソースコード上の理由

この現象はシェルのクォートによる影響ではなく、curl自体の実装によるものです。curl 8.12.1 の公式ソースコード（src/tool_paramhlp.c）内の file2string() 関数の処理を確認するとその理由が判明します。

同関数はファイルをメモリに読み込む際、memcrlf() を呼び出して改行文字を処理します。ソースコード内のコメントには countcrlf FALSE - return number of bytes from the start that DO NOT include any CR or LF or NULL と明記されています。すなわち、書式ファイルを読み込む際に物理的なCRやLFコードをスキップして連結する仕様になっています。

したがって、出力結果で正常に改行を行うには、物理的な改行キー入力ではなく、バックスラッシュとアルファベットnで構成された文字通りの \n をファイル内に書き込む必要があります。Everything curl ドキュメントの writeout の節でも You can also output a newline by using \n, a carriage return with \r and a tab space with \t と説明されています。

この仕様を反映し、修正版の curl-format2.txt を以下のように用意しました。

namelookup:    %{time_namelookup}\n
connect:       %{time_connect}\n
appconnect:    %{time_appconnect}\n
pretransfer:   %{time_pretransfer}\n
starttransfer: %{time_starttransfer}\n
total:         %{time_total}\n
http_code:     %{http_code}\n
size_download: %{size_download}\n
remote_ip:     %{remote_ip}\n

このファイルは od -c を通じて、各行末にリテラルの \ と n の2文字が物理的に記録されていることを確認しています。

3. -w 時間変数の本質 - 累積された値と差分計算

修正した curl-format2.txt を用いて https://example.com/ へ2回連続でリクエストを実行しました。

for i in 1 2; do echo "=== run $i"; curl -s -o /dev/null -w @curl-format2.txt https://example.com/; done

ターミナルに表示された実測値は次の通りです。

=== run 1
namelookup:    0.016839
connect:       0.148093
appconnect:    0.476784
pretransfer:   0.476995
starttransfer: 0.619743
total:         0.619873
http_code:     200
size_download: 713
remote_ip:     172.66.147.243
=== run 2
namelookup:    0.016120
connect:       0.143699
appconnect:    0.463794
pretransfer:   0.463936
starttransfer: 0.600572
total:         0.603125
http_code:     200
size_download: 713
remote_ip:     172.66.147.243

3.1 6つの時間指標が描くリクエストライフサイクル

出力された数値を上から下へ確認すると、値が一貫して単調増加していることが分かります。run 1 において namelookup は約0.017秒、connect は約0.148秒、appconnect は約0.477秒、total は約0.620秒です。

ここから導き出される重要な結論は、curl の time_* 変数は個々の段階にかかった独立した時間ではなく、リクエスト開始時（0.000秒）からの「累積経過時刻」であるという点です。例えば time_connect の 0.148093秒はTCP接続だけに0.148秒かかったという意味ではなく、直前のDNS名前解決にかかった時間を含んだ通算時刻を表しています。

3.2 段階別の所要時間を求める引き算の計算式

そのため、各段階で消費された純粋な所要時間を知るには、直前の累積時刻を差し引く引き算が必要です。run 1 の実測値を秒からミリ秒（ms）に換算して計算すると以下のようになります。

  • DNS解決所要時間: time_namelookup = 16.8 ms (run 2: 16.1 ms)
  • TCP接続所要時間: time_connect - time_namelookup = 148.1 - 16.8 = 131.3 ms (run 2: 127.6 ms)
  • TLSハンドシェイク所要時間: time_appconnect - time_connect = 476.8 - 148.1 = 328.7 ms (run 2: 320.1 ms)
  • リクエスト準備時間: time_pretransfer - time_appconnect = 477.0 - 476.8 = 0.2 ms (run 2: 0.1 ms)
  • サーバー応答待ち（TTFB）: time_starttransfer - time_pretransfer = 619.7 - 477.0 = 142.7 ms (run 2: 136.6 ms)
  • 本文ダウンロード受信: time_total - time_starttransfer = 619.87 - 619.74 = 0.1 ms (run 2: 2.6 ms)

今回の測定では、全体の約0.62秒のうち半分以上（約328.7 ms）を TLSハンドシェイク が占めていました。最初の実験でも appconnect - connect は約0.30〜0.42秒で、3回とも最大の遅延要因でした。この数値はこの検証環境および特定の通信経路における1回限りの実測値であり、固定値ではない点に留意してください。

4. 段階別区間の分解とボトルネック診断表

累積値の差分を一覧表に整理することで、どの段階が遅延の原因であるかを即座に絞り込むことができます。以下は今回の実測値（run 1）と、各差分が不自然に増大した際に疑うべき一般的なネットワーク背景要因をまとめた決定表です。

肥大化した区間 計算式（累積値の差分） 今回の実測値（run 1・1回測定） 遅延時に疑うべき主な背景要因
DNS解決 namelookup 16.8 ms リゾルバのキャッシュミス、上流DNSサーバーの応答遅延、DNSパケット損失
TCP接続 connect - namelookup 131.3 ms 物理的な距離（RTT）、中間ファイアウォールによる遅延、SYNパケットの破棄

この計算式を用いることで、全体で620msかかった通信を「サーバーが遅い」と大雑把に捉えるのではなく、「DNS 17ms、TCP 131ms、TLS 329ms、サーバー初回バイト待ち 143ms」（この環境での1回測定）と分解してインフラ担当者へ共有できます。

5. -v 詳細出力の読み方と Schannel 環境の制約

5.2 --trace-time タイムスタンプと段階境界の解釈

各行の出力時刻を追跡するため --trace-time を付与したログです。

07:43:32.016000 * Host example.com:443 was resolved.
07:43:32.018000 * IPv6: (none)
07:43:32.018000 * IPv4: 172.66.147.243, 104.20.23.154
07:43:32.018000 *   Trying 172.66.147.243:443...
07:43:32.146000 * schannel: disabled automatic use of client certificate
07:43:32.450000 * Connected to example.com (172.66.147.243) port 443
07:43:32.450000 * using HTTP/1.x
07:43:32.450000 > GET / HTTP/1.1

ここから2つの重要な事実が確認できます。第一に、--trace-time の秒未満の末尾3桁がすべて 000 になっています。この環境のWindowsビルドではミリ秒単位までしか分解能が得られないことを示しています。

第二に、「Connected to」行の出力タイミングです。TCP接続試行（Trying）が .018 に始まり、Schannel初期化ログが .146 に出た後、Connected to はTLSが実質終了した .450 に記録されています。つまり、このSchannelビルドではソケット接続直後ではなくTLSまで終わった時点で接続完了ログを出力していると読み取れます。したがって、ログ行の出力間隔から区間を推測するよりも、前述した -w の time_connect や time_appconnect の値を見る方が正確です。

また、このSchannelビルドの -v では交渉された暗号スイート名や証明書期限などの詳細が出力されず、--trace-config tls,dns を指定しても追加行は出力されませんでした。LinuxやmacOSで使われるOpenSSLビルドの-v出力はこの環境では確認できていないため、ビルドが違えば出力も異なり得る点だけ留意してください。

6. 2種類のタイムアウト(--connect-timeout vs -m)と終了コード

スクリプト処理においてタイムアウトを適切に管理しないと、応答のないサーバーによって処理が長時間停止します。curlには接続段階のみを制限する --connect-timeout と、リクエスト全体を制限する -m（--max-time）が存在します。

6.1 接続段階のみを打ち切る --connect-timeout

応答しないIP 10.255.255.1 に対して --connect-timeout 2 を指定した実行結果です。

time curl -sS --connect-timeout 2 -o /dev/null http://10.255.255.1/; echo "exit=$?"
curl: (28) Connection timed out after 2011 milliseconds
real	0m2.122s
exit=28

約2.011秒後に接続処理が停止し、curlは終了コード28を返しました。manpageの規定通り、このオプションは接続フェーズのみを制限し、一度接続が確立した後のデータ転送には影響しません。

6.2 全体操作を打ち切る -m (--max-time) の優先順位

これに対し -m（--max-time）は、公式ドキュメントに Maximum time in seconds that you allow the whole operation to take とある通り、通信全体の制限時間です。両者を同時に与えた場合を検証しました。

curl -sS --connect-timeout 5 -m 0.2 -o /dev/null https://example.com/; echo "exit=$?"
curl: (28) Connection timed out after 204 milliseconds
exit=28

接続タイムアウトに5秒を指定していたにもかかわらず、全体の制限である -m 0.2 が先に作動し、204ミリ秒で強制終了しました。-m が --connect-timeout より短い場合、接続段階であっても -m が優先されます。

同じ終了コード28であっても、打ち切られた段階によってエラーメッセージが異なります。

  • 接続成立前の打ち切り: curl: (28) Connection timed out after 204 milliseconds
  • 接続後データ待機中の打ち切り（-m 0.5）: curl: (28) Operation timed out after 514 milliseconds with 0 bytes received （このとき http_code は 000）

なお、所要時間内に完了する -m 0.58 を設定した場合は正常に終了コード0とHTTP 200が返されました。

7. スクリプト連携のための -sS、-f、そして JSON 出力

自動化スクリプトで curl を呼び出す際、フラグの指定ミスは深刻な障害検知漏れを引き起こします。

7.1 エラー出力を残す -sS と失敗終了コードを返す -f

存在しないドメイン nonexistent.invalid を問い合わせた際の結果です。

curl -sS -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl -s  -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl: (6) Could not resolve host: nonexistent.invalid
exit=6
=== -s alone hides error
exit=6

進捗表示を消そうとして -s のみを用いると、エラーメッセージまで消去され終了コード6だけが残ります。スクリプトでは必ず進捗は消すがエラーは標準エラー出力に残す -sS（--silent --show-error）を使用します。ドメイン解決不能時の終了コードは仕様通り 6 です。

さらに見落としやすいのが HTTP 404 のようなエラー応答です。

curl -s  -o /dev/null -w '%{http_code}\n' https://example.com/no-such-page; echo "exit(no -f)=$?"
curl -sf -o /dev/null https://example.com/no-such-page; echo "exit(-f)=$?"
404
exit(no -f)=0
exit(-f)=22

今回の実験で curl は 404 を受けても -f なしでは終了コード 0（正常）を返しました。$? だけを見るスクリプトは止まらずに進みます。HTTP 400 以上のエラー時にシェル終了コードを失敗にするには -f（--fail）を付与して終了コード 22 を出させる必要があります。ヘッダー確認には -I（HEADリクエスト）、転送追跡には -L を併用します。

実測検証で確認された終了コードの一覧表です。

検証シナリオ 指定オプション 終了コード 実際に出力されたエラーメッセージ
無応答プライベートIPへの接続試行 --connect-timeout 2 28 Connection timed out after 2011 milliseconds
接続中に全体制限時間到達 -m 0.2 28 Connection timed out after 204 milliseconds
応答待機中に全体制限時間到達 -m 0.5 28 Operation timed out after 514 milliseconds with 0 bytes received
存在しないドメインの解決失敗 -sS（-s のみだと文言なしで 6） 6 Could not resolve host: nonexistent.invalid
HTTP 404 エラー受信 -f 未指定 0 (エラーメッセージなし、正常受信として終了)
HTTP 404 エラー受信 -f 指定 22 —（-s により文言なし）

7.2 curl 8.12 の %{json} および %{header_json} の活用

外部フォーマットファイルを用いずにプログラムから構造化データを取得する場合、curl 8.12.1 で確認した JSON 出力が使えます。

curl -s -o /dev/null -w '%{header_json}' https://example.com/ | head -c 120

# curl 診断フラグと遅延区間分解 - 実務リファレンス表

検証環境: Windows 10 Pro 10.0.19045, curl 8.12.1 (Schannel), Git Bash, Python 3.13.3.
表の値とメッセージはこの環境で実行して確認したものです（時間は1回測定）。4章の3番目のコマンドは例示で、この組み合わせ自体は実行していません。

---

## 1. どこが遅いか — 差分による特定

curl の `time_*` 変数はリクエスト開始からの**累積時刻**です。各段階の所要時間は直前の値との引き算で求めます。

| 肥大化した区間 | 計算式（累積値の差分） | 実測値（1回） | 遅延時に疑うべき要因（一般的背景） |
|---|---|---|---|
| DNS解決 | `time_namelookup` | 16.8 ms | ローカルキャッシュミス、再帰リゾルバの遅延 |
| TCP接続 | `time_connect - time_namelookup` | 131.3 ms | ネットワーク往復時間（RTT）、FWパケット遅延 |
| TLS交渉 | `time_appconnect - time_connect` | 328.7 ms | 証明書チェーン検証、暗号スイート交渉（最大） |
| サーバー応答待ち（TTFB） | `time_starttransfer - time_pretransfer` | 142.7 ms | サーバー処理負荷、DBクエリ遅延、キャッシュミス |
| 本文受信 | `time_total - time_starttransfer` | 0.1 ms (713 B) | レスポンスサイズ、帯域幅の制限 |

## 2. 終了コード一覧表（実測）

| 状況 | 指定オプション | 終了コード | 実際に出力されたエラーメッセージ |
|---|---|---|---|
| 無応答プライベートIPへの接続 | `--connect-timeout 2` | 28 | `Connection timed out after 2011 milliseconds` |
| 接続中に全体制限時間到達 | `-m 0.2` | 28 | `Connection timed out after 204 milliseconds` |
| 応答待ち中に全体制限時間到達 | `-m 0.5` | 28 | `Operation timed out after 514 milliseconds with 0 bytes received` |
| 存在しないドメインの解決 | `-sS` (`-s` のみだと文言なしで 6) | 6 | `Could not resolve host: nonexistent.invalid` |
| HTTP 404 レスポンス受信 | (なし、`-f` 未指定) | 0 | (エラーなし、正常受信として終了) |
| HTTP 404 レスポンス受信 | `-f` (`--fail`) | 22 | — (`-s` により文言なし) |

## 3. 実務チェックリスト

- [ ] **フォーマットファイルの改行の罠**: フォーマットファイル（`@curl-format.txt`）内では物理的な改行ではなく文字通りの `\n` を記述する（物理改行は curl 内部の `file2string()` で削除される）。
- [ ] **スクリプトの基本フラグ**: 自動処理では進捗表示を消し、エラーを標準エラー出力に残す `-sS`（`--silent --show-error`）を使用する。
- [ ] **HTTPエラーの捕捉**: `-f`（`--fail`）を指定しない場合、404でも終了コード0になったため（文書: `-f` は400以上で22）、必ず `-f` を付与するか `%{http_code}` を検証する。
- [ ] **タイムアウトの優先順位**: `--connect-timeout` と `-m` を併用する場合、`-m` の方が短いと、接続中であっても `-m` が先に処理を止めた。
- [ ] **Schannel ビルドの特性**: この環境の Schannel ビルド（curl 8.12.1, x86_64-w64-mingw32）の `-v` では TLS 詳細（バージョン・暗号スイート・証明書）が出力されないため、TLS 測定は `-w` の `time_appconnect` を利用する。
- [ ] **プロトコル対応の確認**: ビルドによって機能が異なるため、診断前に `curl -V` で HTTP2 などの対応状況を確認する。

## 4. 推奨診断テンプレート

### ミリ秒計測用フォーマットファイル (`curl-format.txt`)
```text
namelookup:    %{time_namelookup}\n
connect:       %{time_connect}\n
appconnect:    %{time_appconnect}\n
pretransfer:   %{time_pretransfer}\n
starttransfer: %{time_starttransfer}\n
total:         %{time_total}\n
http_code:     %{http_code}\n
size_download: %{size_download}\n
remote_ip:     %{remote_ip}\n
```

### 実行コマンド例
```bash
# 1. 段階別所要時間の計測
curl -s -o /dev/null -w @curl-format.txt https://example.com/

# 2. JSON形式での統計出力 (curl 8.12.1 で確認)
curl -s -o /dev/null -w '%{json}' https://example.com/

# 3. 安全なスクリプト呼び出しの例 (3・10 は例示の値、この組み合わせ自体は未実行)
curl -sS -f --connect-timeout 3 -m 10 -o output.dat https://example.com/
```
