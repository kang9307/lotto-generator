一个藏了16年的缺陷，在什么条件下才会暴露

以SQLite WAL重置损坏为例看稀有缺陷追踪 - 从检查点原理到向上游报告

2026年8月16日 开发/基础设施

引言：数据悄悄对不上的那类故障

备份任务每晚都以成功结束，磁盘没有报任何错误，应用日志也很干净。可是昨天明明存进去的一行，今天查不到了。走索引的查询和全表扫描给出的答案不一样。

这类故障在实务中属于最难处理的一档，因为它没有崩溃的那一刻。进程不会死，也不会返回500。对不上的数据就这样被装进下一次备份，几周之后账目对不平，或者某个用户来问一个消失的设置，问题才浮出水面。到那时，出问题那个时刻的日志早已被轮转清掉了。

2026年8月13日在GeekNews上被介绍的Tailscale技术报告，讲的正是这种形状的事故。半年内19起数据库损坏，在受控环境里始终无法复现的原因，最后被收敛到SQLite的WAL回绕路径上一个稀有的竞态条件。修复的签入落在2026年3月3日的主干分支上。而WAL进入SQLite是在3.7.0（2010-07-21），两者之间大约隔了16年。

只看数字，很容易读成「被放了16年没人管」。这样读就什么也带不走。本文要谈的是三件事：WAL和检查点实际在做什么；复现条件狭窄的缺陷为什么在统计上看不见，又为什么会在某个时点冒出来；以及遇到这类缺陷时该按什么顺序保全什么。这不是一篇评判某个产品或某个团队对错的文章。

1. WAL模式在做的事 - 为什么快，检查点又是什么

1.1 与回滚日志的区别

SQLite默认的日志方式是回滚日志，它这样工作：改写某一页之前，先把原内容复制到单独的日志文件，然后直接修改主数据库文件。中途进程死掉，就用日志里的原内容回滚。安全，但同一份数据实际上写了两次。

WAL的方向相反。它不动主数据库文件，而是把变更过的页顺序追加到WAL文件末尾。官方文档这样归纳其好处：写事务非常快，是因为内容只写一次（回滚日志要写两次），而且这些写入全部是顺序的。

实务中感受更明显的其实是读取侧。回滚日志下写者直接改主文件，读写会互相阻塞。WAL下主文件原封不动，读者可以继续读自己那个时点的快照，写者同时往WAL末尾追加。读者到哪里去找某一页的最新版本，由wal-index负责告知；它保存在共享内存中，对应名字以 -shm 结尾的文件，文档的说法是让读者以最少的I/O快速定位WAL中的页。

WAL付出的代价是一个数据库变成三个文件：app.db、app.db-wal、app.db-shm。这个事实在后面讲证据保全时还会再起作用。

1.2 检查点 - 把WAL搬回主文件

WAL不能无限增长。把积累的帧搬回主数据库文件的操作就是检查点。照搬文档的表述：把WAL文件中的事务搬回数据库这件事，称为检查点。

默认是自动的：WAL超过一定大小之后，提交结束就会触发检查点。也可以用 PRAGMA wal_checkpoint 自己驱动，共有四种模式。

模式行为选它的理由
PASSIVE不等待读者或写者，能搬多少搬多少默认值，对在线流量影响最小
FULL阻塞到没有写者且所有读者都在最新快照上，再搬运希望WAL被真正清空时
RESTART在FULL基础上，再等到所有读者用完日志文件希望下一次写入从WAL开头开始
TRUNCATE在RESTART基础上，把WAL文件截断为0字节需要立刻回收磁盘占用时
NOOP一帧也不搬，只取回状态值3.51.0（2025-11-04）新增，纯粹用于观测

1.3 回绕 - 不让WAL文件变胖的第二个机制

检查点把内容搬走，并不意味着WAL文件本身会变小。回绕就是在这里登场的。官方文档这样解释：每次发生写入时，写者会检查检查点进行到了哪里；如果整个WAL都已经搬入数据库并完成同步，而且没有读者在使用这个WAL，写者就把WAL回绕到开头，从前面开始堆放新的事务。

这句话值得慢读。做出回绕判断的主体是写者，判断依据是检查点方留下的进度状态。两个不同的主体各自读取、各自更新同一份状态。并发缺陷能住下来的地方，正是这种结构。

这里先埋一句。RESTART和TRUNCATE实际上是在诱发回绕。由应用自己驱动、而且驱动得很频繁的部署，走这条路径的次数远多于交给自动机制的部署。后面「为什么是现在」的答案，一半就在这一行里。

2. 这个缺陷坐在什么位置

修复以签入 7168988acbec2d8d 的形式进入SQLite仓库：2026年3月3日，主干分支，作者是dan。改动的文件是 src/wal.c，同时新增了 test/walrestart.test。签入注释只有一句。

Avoid an obscure race condition between a checkpointer and a writer wrapping around to the start of the wal file.

意思是：避免检查点方与回绕到WAL文件开头的写者之间那个不易显露的竞态条件。上一节看到的结构，被原样写成了一句话。

症状一侧的说明在原报告里。检查点运行过程中，如果写入恰好落在特定时刻，检查点处理会产生混淆，认为WAL中的某些页已经复制进主数据库文件，而实际上并没有。

接下来就通往静默损坏。被标记为已搬运的区间成为可以复用的空间，回绕在它之上堆放新的事务。于是出现了主文件里没有、WAL里也没有的页。行消失了，或者本该指向同一份数据的表和索引持有了不同的内容。

在这种状态下SQLite不会报错，因为它自己相信搬运已经完成。损坏只有跑一次单独的比对才看得见。PRAGMA integrity_check 会检查的项目在文档里有列举。

  • 顺序错乱的表或索引条目
  • 格式损坏的记录
  • 丢失的页
  • 缺失或多余的索引条目
  • UNIQUE、CHECK、NOT NULL 约束的违反
  • 空闲列表的完整性
  • 被重复使用或者完全没有被使用的区段

没有问题时，返回值为 ok 的一行。反过来说，在从不跑这个pragma的系统里，上面这些事故即使发生也不会发出任何信号。

原文披露的范围到此为止。哪一处内部状态以怎样的顺序发生偏差，除签入注释和改动文件清单外没有公开的说明。再往下用似是而非的方式补全，那就不是解释而是猜测。

3. 它藏了16年的原因 - 稀有缺陷的统计结构

3.1 暴露是乘法，不是加法

一个缺陷要出现在某人的报告里，需要三样东西同时不为零。

  • 触发概率 - 走过那条代码路径时真的出错的概率
  • 路径通过次数 - 系统每天要踩到那条路径多少次
  • 观测能力 - 是否存在把错误结果识别为错误的机制

三项相乘而不是相加，只要一项接近零，乘积就趋于零。所以「没有人报告过」和「没有问题」是完全不同的两个命题。

代入这次的情况：触发概率只在检查点、回绕与写入按特定顺序重叠的毫秒级窗口内成立。路径通过次数会因检查点的驱动方式相差几个数量级，而原文说明他们把检查点过程接管为手动控制，并且跑得非常激进。观测能力之所以存在，是因为有一套对备份持续执行完整性检查、并有人盯着结果的机制。

第三项尤其关键。如果没有常态化的完整性检查，那19起就不会是一个事件，而是散落在半年里的19张互不相干的工单。写着「数据偶尔不对」的工单，产生不出能传到上游的信号。

3.2 测试抓得住的缺陷，和抓不住的缺陷

SQLite以测试密度高著称。但覆盖率回答的问题是「这一行有没有被执行」，而不是「这两行有没有按这个顺序交错」。代码行数增加，覆盖率的对象线性增加；两个线程能造出的执行顺序组合却不是这样。

所以成熟软件里活到最后的缺陷，形状往往是固定的。容易的早就被清掉了，剩下的是只在狭窄窗口内成立的顺序问题。这类缺陷不会因为多读代码而减少，它要靠执行量和环境多样性的累积，才会以概率的方式浮现。原文提到，这个缺陷罕见到SQLite开发者不得不在测试环境里加入刻意触发该条件的代码。

16年这个数字，与其说是被忽视的时间，不如说是必要的执行量累积所花的时间。软件活得越久、跑的地方越多样，残留的狭窄条件就会被一个个真正踩到。这是成熟曲线的正常性质，不是某个项目的污点。

3.3 那么该以什么态度开场

在实务上，这个认知改变的是怀疑的顺序。一上来就把老旧而久经验证的组件排除在嫌疑之外，可能会在应用代码里徘徊好几个月；反过来第一天就怀疑库，十次里有九次是错的。

可行的顺序是固定的：自己的代码，然后自己的配置，然后环境（文件系统、内核、硬件），最后才是上游。真正重要的不是顺序本身，而是把每一步排除掉的依据写成文档。没有依据就跳过的那一步，一定会回来找你。排除依据积累起来，才有资格对上游说「这些都不是」。

4. 追踪的步骤 - 按什么顺序保全什么

下表整理了追踪一个无法复现的缺陷时真正能用的顺序。每一步要留下什么才能往下走，以及这一步通常在哪里塌掉，都写在一起。

步骤做什么必须留下的东西容易塌掉的地方
1. 建立计数装置加一个把损坏判定为损坏的自动检查件数、时刻、受影响的实例只当作工单处理，件数从未被汇总
2. 事例标准化所有事例用同一格式记录完整性检查的原文输出写入时就概括掉，之后无法比对
3. 收敛共同条件求版本、配置、硬件、负载模式的交集重叠条件与不重叠条件的清单样本少时把相关当成因果
4. 对齐时刻把应用、数据库、备份、基础设施日志放到一条轴上损坏区间的上下界时刻各主机时钟不同导致顺序颠倒
5. 尝试最小复现在受控环境里收敛条件成功则是步骤，失败则是尝试的边界把复现失败当成没有原因
6. 转向生产观测在可疑层的下一层插入追踪能看出顺序的低层记录只是把应用日志开得更大声
7. 向上游确认附上版本、配置、症状、频率提交报告无需复现也能判断的一整套材料因为没有复现步骤而拖延报告
8. 修复后验证单独统计条件本身是否仍在发生条件计数器与损坏计数器分开把症状消失误认为原因已被清除

第1步和第2步最常被省略，而省略的代价也最大。如果损坏靠人眼判定，事例就不会标准化；没有标准化的事例，第3步做不出交集。追踪就在第3步停住。

把第4步单独拎出来也是同样的道理。把原因和结果连起来的终究是顺序，而不同机器的日志放不到一条轴上，顺序就看不见。测量经过时间的时钟为什么要和标记时刻的时钟分开，在用挂钟测经过时间会得到负数里另有整理。

5. 在生产环境观测无法复现的缺陷

受控环境复现是个好目标，但不是最终目的。目的是定位原因。当复现持续失败时就该换方向：把观测点往下降一层。

5.1 把追踪塞进文件层

SQLite把文件系统访问抽象成一个叫VFS的接口。在那一层夹进一个薄薄的垫片，就能在不改动应用代码的前提下，按顺序看到什么时候往哪个偏移写了什么。这次追踪中SQLite开发者做的就是 tmstmpvfs，一个在文件访问上追加追踪信息的包装层。它留在公开仓库的 ext/misc/tmstmpvfs.c 里。

对于顺序型缺陷，这份顺序记录实际上是唯一的证据。应用日志留下的是「打算做什么」，并不留下这些意图实际以什么顺序抵达磁盘。

5.2 把变更SQL导到外面

第二件工具是把所有变更SQL送到外部的事务日志管道。它一身兼两职：损坏发生时可以在最后一份正常备份之上回放日志来恢复，同时也能构造出「本该是什么状态」，作为与实际状态比对的基准。要确定损坏范围就需要基准，而只有备份的话，基准只能到备份采集的那一刻为止。

5.3 修复之后仍在计数条件的告警

修复发布之后反而更关键。原文提到，他们在修复后保留了一个专门探测写入与检查点相撞情况的告警，并在生产环境确认到：损坏被挡住了，但条件确实还在发生。

为什么需要这个。因为症状消失并不能证明原因已被清除。存在两种可能。

  • 条件仍在发生但不再产生坏结果 → 说明修复真的在起作用
  • 条件本身不再发生 → 也可能只是负载模式或部署形态变了

分不清这两者，几个月后流量上来时就得把整套追踪从头再做一遍。把条件计数器和损坏计数器分开保留，理由就在这里。

5.4 可以一般化的三行

  • 观测点要放在你怀疑的那一层再往下一层。在同一层加日志只会增加数量，看不出顺序
  • 观测从打开的那一刻起就是成本。采样比例和缩小范围的计划，要在打开之前定好
  • 修复之后不要关掉告警。关掉的那一刻，下一次复发就要从一张白纸开始

6. 处理数据损坏时的原则

6.1 保全先于修复

损坏的数据库文件不是一个坏文件，而是证据。可现场最先做的往往是修复：跑VACUUM，做REINDEX，导出后重新导入到新文件。这三件事都会抹掉原因的痕迹。其中导出再导入最要命，它把损坏洗成了正常，之后再也没有办法回溯发生过什么。

复制的范围也要留心。WAL模式下主文件并不是全部。

# 原则：先停，先复制，然后再看
cp app.db      evidence/app.db
cp app.db-wal  evidence/app.db-wal   # 存在就一定要一起复制
cp app.db-shm  evidence/app.db-shm   # 存在也一起复制

# 诊断在再复制一份的副本上做，绝不动证据本身
cp evidence/app.db     work/app.db
cp evidence/app.db-wal work/app.db-wal
sqlite3 work/app.db 'PRAGMA integrity_check;' > evidence/integrity.txt

再复制一份是有理由的。以读写方式打开WAL数据库，可能在连接的瞬间触发恢复或检查点而改写文件。把 sqlite3 直接连到打算留作证据的那份副本上，等于在动证据。原则上应当先停掉进程再复制，但也要知道进程一停 -shm 就没了。无论选哪一边，都要把这个选择本身记录下来。

6.2 把所有时刻放到一条轴上

损坏的时刻不是「发现的时刻」。准确地说，它是最后一次确认正常的时刻与发现时刻之间的那个区间。区间越窄，观测体系越好；而收窄区间的唯一办法，就是更频繁地确认正常。每次备份都跑完整性检查的习惯，正是在这里变成事故应对能力的。

要把多份日志放到一条轴上，还得先处理时钟问题。主机之间的时钟偏差、时区标注混杂的日志、重新同步造成的挂钟跳变，都会把顺序颠倒过来。

6.3 判定要原样保留

  • 不要概括完整性检查的输出。「出了几条」没有意义，哪句话出现了几次才是比对的原料
  • 把版本和配置一起附在事故记录里：sqlite_version()、journal_mode、由谁驱动检查点
  • 在检测到损坏的实例上不要继续接收写入。原文说明，他们对检测到损坏的控制面分片采取立即停机的策略
  • 停机策略是在可用性和一致性之间选择了一致性。数据如果是账本性质，这通常是对的；如果是缓存性质，另一种判断也说得通

7. 修好之后发生的事 - 修复本身也是变更

这个案例里最实用的部分，反而在修复之后。按时间顺序看是这样。

版本或签入日期内容
SQLite 3.7.02010-07-21引入WAL模式
SQLite 3.51.02025-11-04新增 PRAGMA wal_checkpoint=NOOP
签入 7168988acbec2d8d2026-03-03规避检查点方与回绕写者之间的竞态。修改 src/wal.c，新增 test/walrestart.test
SQLite 3.52.02026-03-06发布后撤回，原定功能顺延到3.53.0
SQLite 3.51.32026-03-13只带着WAL重置损坏的修复发布
SQLite 3.53.02026-04-09WAL重置修复，外加表达式索引自愈功能（REINDEX EXPRESSIONS）

3.52.0上线之后不久，备份监控在13个数据库上报告了损坏。原因并不是WAL的修复，而是一项优化微妙地改变了文本转浮点数的舍入行为。

它为什么会变成损坏告警。高精度时间戳以文本形式存储，并在VIRTUAL生成列里被转换成浮点数，而这个列上建了索引。索引里固化的值与新版本计算出的值不再一致，完整性检查就把索引与表的不一致报告成了损坏。这种状态叫作陈旧的表达式索引。存储的数据本身完好无损。

SQLite方面撤回了3.52.0，改为发布只包含WAL修复的3.51.3，并在3.53.0里加入了自动修复陈旧表达式索引的功能。应用一侧则把时间戳精度降到整数秒，直接消除了那个有歧义的转换。

从这里可以带走两点。

  • 表达式索引和生成列存的是函数的结果。函数一变，存下来的结果就会坏掉。哪怕是让精度变得更好的改动，也不例外
  • 完整性告警的第一个问题不是「数据坏了吗」，而是「什么和什么对不上」。这13起是索引与表对不上，不是数据消失。两种情况的处置方式完全不同

这段插曲也给版本锁定之争提供了真实的材料。只锁定，就收不到这次的WAL修复；无条件追最新，生产就会先撞上3.52.0这类改动。两者都不是答案，答案在晋级流程里。向后兼容与安全默认值之间的张力，在SQLite语境下的讨论另见SQLite也需要Rust式的版次。

8. 在自己系统里采取的防御 - 检查表

这不是针对这一个缺陷的对策，而是针对静默数据损坏的一般性防御。可以当作清点自己已经具备几项的工具来用。

项目周期通过标准省掉会发生什么
对备份副本做完整性检查每一代备份除了 ok 一行之外都按失败处理损坏顺着备份代际扩散
还原演练每月至少一次还原件上的抽样查询结果符合预期备份文件在，却救不回来
选对检查用的pragma设计时一次需要比对索引就用 integrity_checkquick_check 不校验索引内容与表内容一致，会漏掉这一类
检测到就停止写入即时、自动停机与告警无需人介入即可动作写入堆在损坏之上，可回退的时间点消失
变更日志存到数据库之外常态最后一份正常备份加回放即可还原只能退回到备份采集的那一刻
版本晋级流程每次发布预发布环境通过备份验证后才晋级随修复一起进来的其他改动由生产先承受
检查点策略成文配置变更时谁在什么时候驱动检查点，写下来不知道自己的系统常走哪条路径
收集版本字符串每次部署记录 sqlite_version() 和构建方式事故之后无法还原当时是哪个构建

可以先从确认现在跑的是什么开始。下面是形态示例，实际使用时要把连接路径和表名换成自己环境的。

-- 先弄清现在用的是什么
SELECT sqlite_version();      -- 是否为3.51.3以上或3.53.0以上
PRAGMA journal_mode;          -- 是否为 wal
PRAGMA wal_autocheckpoint;    -- 自动检查点的阈值

-- 损坏判定。正常时只返回 ok 一行
PRAGMA integrity_check;

备份验证不自动化，最后就一定不会做。按代际运行的最小形态大致是这样。

#!/bin/sh
# 还原过才算备份（形态示例）
set -e
backup="$1"
work=$(mktemp -d)
cp "$backup" "$work/verify.db"

result=$(sqlite3 "$work/verify.db" 'PRAGMA integrity_check;')
if [ "$result" != "ok" ]; then
  echo "INTEGRITY FAIL: $result"
  exit 1
fi

# 通过结构检查，并不代表内容是对的
sqlite3 "$work/verify.db" 'SELECT count(*) FROM users;'
rm -rf "$work"

无论是把备份包进Web界面还是用脚本驱动，只要少了还原验证，塌的地方都一样。工具选型与3-2-1原则的讨论见把散落的数据库备份收进一个Web界面的想法。

9. 向开源上游报告时该准备什么

因为没有复现步骤而拖延报告的情况很常见。但顺序型缺陷本来就是复现步骤最晚才出现的那一类。让上游在没有复现的情况下也能判断的，是条件的密度。

  • 准确的版本 - SELECT sqlite_version() 的结果、构建方式（发行版软件包、内置捆绑、自行编译）以及编译选项
  • 驱动与绑定 - 名称和版本。驱动经常自行管理连接生命周期或检查点
  • 完整的配置 - journal_mode、synchronous、谁在什么时候驱动检查点、并发连接数与进程数、文件系统与挂载选项
  • 症状原文 - 完整性检查的输出照原样贴出。概括之后上游读不出模式
  • 频率与时间跨度 - 多少天里出了多少起。这几乎是上游判断概率的唯一材料
  • 复现尝试的边界 - 在什么条件下试了什么、失败到什么程度。光写一句「无法复现」，信息量为零
  • 已排除的假设及依据 - 硬件、文件系统、应用代码是怎么被排除的
  • 提供观测数据的准备 - 如果上游做出追踪钩子，能不能放进你的生产环境，能放到什么范围

语气同样重要。上游的时间是有限的，通常也不是免费的；原文提到，追踪初期他们与SQLite开发者签订了专业支持合约。开源并不意味着上游的劳动没有成本。

而且报告不会在原因被定位的那一刻结束。这次追踪中做出的VFS追踪垫片留在了SQLite的公开仓库里，这是一个很好的收尾形态，因为下一个遇到类似问题的人，起点就不一样了。比起修好一个缺陷，留下一件追踪工具在生态里活得更久。

10. 没能确认的事项

以下内容在公开资料里无法确定，这也是本文不下断言的理由。

  • 竞态条件的内部动作细节 - 公开的只有签入注释和改动文件清单（src/wal.c、test/walrestart.test）。哪一处内部状态以怎样的顺序偏差，原文和发行说明里都没有
  • 默认配置下的发生率 - 原文说明检查点是手动且激进地驱动的。相对于仅使用自动检查点的标准配置，其相对风险没有公开数值
  • 19起是否同一原因 - 原文如此叙述，但没有公开逐起的对照表
  • 复现步骤 - 原文说明团队在受控环境中未能复现。本文给出的命令示例是诊断与防御用的一般流程，不是复现该缺陷的步骤
  • 3.52.0撤回的官方表述 - 发行说明只写了原定功能顺延到3.53.0。与误报告警之间的因果，来自原文一侧的叙述
  • 其他地方的类似报告 - 没有找到其他运营方公开报告同样症状的记录

结论

从16这个数字里该读出的是结构，不是疏忽。只在狭窄条件下成立的缺陷不会因为代码评审或覆盖率而减少，它要靠执行量与环境多样性的累积，以概率的方式浮现。而浮现还必须有第三个条件：一个把错误结果识别为错误的机制。没有它，事故照样发生，只是永远不会被报告。

这个案例给实务留下的，说到底就是那套机制的清单。每次备份都跑的完整性检查、检测到就自动停机、真的动手还原的演练，以及修复之后仍在计数条件的告警。四样都不显眼，四样在平日里都什么也不做。

今天能做的三件事：

  1. 把现在用的SQLite版本、journal_mode，以及由谁驱动检查点，写在一页纸上
  2. 让每一代备份都跑完整性检查，并把结果留成记录
  3. 本月之内真正还原一份备份，并把抽样查询也确认一遍

三件里最后一件最容易被拖，账单也开得最贵。从没还原过的备份，还算不上备份。
