서론: 재현이 안 되는 실패와, 이름이 같은 두 함수

무작위 입력으로 도는 검사가 어느 날 한 번 걸렸다. 로그에는 「기대값과 다름」이라고만 찍혀 있었다. 다시 돌리니 통과했다. 열 번을 더 돌려도 통과했다. 어떤 입력이 그것을 깨뜨렸는지는 프로세스가 끝나는 순간 함께 사라졌다.

원인을 찾다가 다른 것을 먼저 발견했다. 그 입력을 만드는 코드와, 비밀번호 재설정 링크에 붙는 토큰을 만드는 코드가 거의 같은 이름의 함수를 부르고 있었다. 한쪽은 통계용 생성기였고 다른 한쪽은 보안용이었다. 호출 지점만 봐서는 어느 쪽이 어느 쪽인지 구분되지 않았다.

이 두 가지는 별개의 사고처럼 보이지만 뿌리가 하나다. 난수 API의 어려운 부분은 알고리즘이 아니라 이름과 기본값이다. 어떤 생성기를 쓸지, 시드를 받을지, 범위를 어떻게 자를지는 전부 표면 설계의 문제이고, 그 표면이 애매하면 사용하는 쪽에서 반드시 사고가 난다.

그래서 실제로 돌려 봤다. 아래 숫자는 전부 이 런타임에서 직접 실행해 얻은 것이다. 확인한 것은 네 가지다.

  • 이름이 종류를 감춘다. 통계용과 보안용이 같은 단어를 공유하면 호출 지점에서 구분이 안 된다
  • 시드가 없으면 버그를 두 번 못 본다. 재현성은 편의 기능이 아니라 디버깅의 전제다
  • 범위를 자르는 순간 분포가 기운다. 그리고 그 기울기는 소스 폭에 따라 보이기도, 영원히 안 보이기도 한다
  • 전역 생성기 하나가 재현성을 인질로 잡는다. 시드를 고정해도 소비 순서가 바뀌면 결과가 달라진다

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 Node.js v22.16.0 (win32 x64)으로 실제 실행한 결과다. 통계용 생성기는 32비트 상태를 가진 splitmix32를 직접 구현해 썼고, 보안용은 이 런타임이 제공하는 암호학적 난수 인터페이스를 그대로 썼다. 스크립트는 전부 파일로 저장해 실행했다. 표본 크기는 항목마다 본문에 적었다.

이 글이 다루지 않는 것. 예측 가능성을 어떻게 악용하는지는 다루지 않는다. 「통계용은 예측 가능하다」는 성질만 확인하고, 그 성질을 이용하는 절차는 쓰지 않는다. 서버가 일부러 흐트러진 값을 돌려주는 경우와, 무작위 식별자를 기본 키로 썼을 때의 저장 비용은 각각 별도 글에 있다. 검사가 실행 순서에 의존하는지 가려내는 문제도 여기서는 다루지 않는다. 이 글은 난수 API 자체의 표면만 본다.

1. 이름은 하나인데 종류는 둘이다

먼저 이 런타임이 제공하는 난수 관련 호출을 늘어놓고, 어느 것이 어느 종류인지 표로 찍었다. 그리고 실제 코드 한 줄만 놓고 종류를 알 수 있는지 확인했다.

--- 1-1. every one of these has "random" in the name ---

여섯 개 호출 지점 중 통계용이 셋, 보안용이 셋이다. 그리고 여섯 개 모두 이름에 같은 단어를 담고 있다. 코드 리뷰에서 이 줄들을 스쳐 지나갈 때, 어느 쪽인지 판단하려면 호출자의 이름을 하나하나 기억하고 있어야 한다.

  • 표의 seedable 열이 결정적이다. 시드를 넣을 수 있는 것은 통계용뿐이고, 보안용에는 시드를 넣을 자리 자체가 없다
  • 그런데 이 성질이 이름에 전혀 드러나지 않는다. 문서를 봐야 알 수 있고, 문서를 안 보면 모른다
  • 변수 이름이 token인지 jitter인지가 유일한 힌트인데, 변수 이름은 강제되지 않는다
  • 정적 분석으로 잡으려 해도 「이 값이 밖으로 나가는가」를 추적해야 해서 일반적으로는 어렵다

1.1 왜 두 종류가 필요한가 - 이 런타임에서 잰 처리량

둘로 나뉘어 있는 데는 이유가 있다. 그 이유가 실제로 얼마나 큰지 재 봤다. 그리고 두 계열이 잘못된 인자를 받았을 때 어떻게 반응하는지도 함께 확인했다.

차이가 확실히 있다. 다만 그 차이의 정체가 흥미롭다. 보안용을 한 워드씩 부를 때는 175배 느렸지만, 4,096개씩 묶어 받으면 1.3배 차이로 줄었다. 비용의 대부분이 알고리즘이 아니라 호출당 오버헤드였다는 뜻이다.

  • 「보안용은 느리니까 통계용을 쓴다」는 판단은 대체로 근거가 약하다. 묶어 받으면 대부분의 워크로드에서 차이가 사라진다
  • 보안용 호출에는 한 번에 65,536바이트라는 상한이 있고 넘기면 예외를 던진다. 이 상한 자체가 「묶어 받되 적당히」라는 설계 의도를 드러낸다
  • 보안용은 정수형이 아닌 배열을 주면 거부하고, 최솟값이 최댓값보다 크면 그 자리에서 예외를 던진다
  • 반면 통계용 호출은 인자를 더 줘도 조용히 무시했다. 시드처럼 보이는 문자열을 넘겨도 아무 일이 없다. 이것을 시드로 착각한 코드는 영원히 재현되지 않는다

2. 시드는 편의 기능이 아니라 디버깅의 전제다

서론의 첫 번째 증상으로 돌아간다. 무작위 입력으로 도는 검사가 걸렸는데 어떤 입력이었는지 모르는 상황이다. 시드가 있으면 이 상황 자체가 성립하지 않는다.

구간의 폭이 0이 되면 나눗셈이 무한대를 내는 함수를 하나 두고, 그 함수를 생성한 입력으로 500회 검사했다. 시드를 보고서에 남긴 경우와 그렇지 않은 경우를 나란히 돌렸다.

  • 시드는 실패 보고서의 일부여야 한다. 로그에 남기지 않으면 있어도 없는 것과 같다
  • 마지막 표의 아래 두 줄이 중요하다. 시드가 있든 없든 통계용은 예측 가능하고, 어느 쪽도 비밀 값을 만드는 데 쓸 수 없다
  • 즉 시드의 유무는 재현성 축의 문제이지 안전성 축의 문제가 아니다. 두 축을 섞으면 판단이 흐려진다
  • 실무에서는 시드를 「나중에 필요하면 붙이는 것」으로 미루는 경우가 많은데, 필요해지는 시점은 이미 늦은 시점이다

3. 범위를 만드는 순간 분포가 기운다

난수를 원하는 범위로 옮기는 가장 흔한 방법은 나머지 연산이다. 8비트 값을 100으로 나눈 나머지를 100만 번 뽑아 분포를 봤다. 주사위처럼 작은 범위도 같이 봤다.

--- 3-1. modulo on an 8-bit source, bound = 100 ---
256 = 2 * 100 + 56   -> values 0..55 have 3 preimages, 56..99 have 2
theoretical p(low)  = 1.1719%   p(high) = 0.7813%   ratio = 1.500
measured  mean(0..55) = 11715.7   mean(56..99) = 7816.4   ratio = 1.499
measured  min = 7615  max = 11917  expected if fair = 10000
chi-square (df 99) = 37546   (fair sample lands near 99)
first 8 buckets  : 11623 11596 11859 11710 11869 11676 11634 11520
buckets 56..63   : 7949 7884 7659 7807 7886 7615 7881 7824

--- 3-2. same bug, small bound = 6 (a dice roll) ---
256 = 42 * 6 + 4
face       :         1        2        3        4        5        6
count      :    167301   167670   168621   167747   164466   164195
share      :   16.730%  16.767%  16.862%  16.775%  16.447%  16.419%

이유는 산수 한 줄이다. 256을 100으로 나누면 몫이 2, 나머지가 56이다. 0부터 55까지는 나올 경로가 세 개고 56부터 99까지는 두 개다. 그래서 앞쪽 값이 정확히 1.5배 자주 나온다. 측정값 1.499가 이론값과 맞았다.

주사위 쪽도 같은 구조다. 256을 6으로 나누면 나머지가 4라서 1부터 4까지가 2.38% 더 자주 나온다. 눈으로는 「그럴 수도 있지」 싶은 차이인데, 카이제곱이 104.1로 자유도 5의 기대치를 스무 배 넘게 벗어났다.

3.1 넓은 소스에서는 같은 버그가 영원히 안 보인다

여기가 이 절의 핵심이다. 똑같은 나머지 연산을 32비트 값에 걸고 같은 100만 회를 돌렸다. 그리고 편향을 없애는 방법과 그 비용도 함께 쟀다.

--- 3-3. same "% 6" on a 32-bit source: bias still there, invisible ---
2^32 = 715827882 * 6 + 4
theoretical excess of faces 1..4 = 1.397 parts per billion
count      :    166645   166580   166318   167237   166273   166947
chi-square (df 5) = 4.1   -> indistinguishable from fair
draws needed to see this bias at all: about 512410 x 10^12

--- 3-4. rejection sampling removes the bias at a measurable cost ---
accept only bytes < 200 (= 256 - 256 % 100), then take % 100
measured  min = 9708  max = 10279  expected = 10000
chi-square (df 99) = 104   (fair sample lands near 99)
rejected 280146 of 1280146 bytes = 21.88%  (theory 21.88%)
worst-case rejection rate for an 8-bit source is just under 50% (bound = 129)

32비트 쪽은 카이제곱 4.1로 공정한 표본과 구별되지 않았다. 편향이 사라진 것이 아니라 10억분의 1.4 수준이라 보이지 않을 뿐이다. 이 편향을 통계적으로 잡아내려면 10의 17제곱 회 규모의 표본이 필요하다. 즉 검사로는 절대 걸리지 않는 버그가 된다.

표를 이렇게 읽으면 된다. 왼쪽 세 줄은 금방 들키는 버그이고, 아래 두 줄은 영원히 안 들키는 버그다. 그런데 코드는 양쪽이 똑같이 생겼다. 그래서 「지금까지 문제없었다」는 근거가 되지 못한다.

  • 바이트 단위 소스에 좁은 범위를 거는 조합이 가장 자주 사고를 낸다. 추첨, 주사위, 카드 뽑기가 전부 여기에 해당한다
  • 거절 표집은 범위의 정확한 배수까지만 받아들이고 나머지 꼬리를 버린다. 8비트에 100을 걸면 21.88%를 버리는 대신 편향이 0이 된다
  • 32비트 소스에서 거절 비용은 평균 1.00회, 최악 2.00회다. 실무에서 문제가 되는 수준이 아니다
  • 가장 확실한 해법은 이 함수를 라이브러리가 제공하는 것이다. 호출자가 매번 다시 만들면 절반은 틀린다
// unbiased bounded integers - the code a caller should never have to write again
function intBelow(next, n) {                     // next() returns a uint32
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width (2^32)');
  const limit = 4294967296 - (4294967296 % n);   // largest exact multiple of n
  let v;
  do { v = next(); } while (v >= limit);         // drop the ragged tail
  return v % n;
}

function intBetween(next, lo, hi) {              // closed range, both ends included
  if (!Number.isInteger(lo) || !Number.isInteger(hi)) throw new TypeError('intBetween takes integers');
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}

4. 0 이상 1 미만 실수를 정수로 바꿀 때의 경계

많은 난수 API가 0 이상 1 미만의 실수를 준다. 그것을 정수로 바꾸는 순간 경계값 문제가 생긴다. 1 바로 아래의 최대 실수를 직접 넣어 관용구들이 어떻게 반응하는지 봤다.

먼저 안심할 것이 하나 있다. 내림을 쓰는 한 최댓값이 튀어나오는 일은 없었다. 1 직전의 최대 실수를 곱해도 곱셈 결과가 아래로 반올림되어 n에 닿지 않는다. n이 2의 53제곱 이하인 모든 경우에서 그랬다. 문제는 다른 관용구들이다.

반올림 쪽 분포가 눈에 띈다. 양끝이 5.01%, 가운데가 10.00%다. 정확히 절반이다. 반올림은 0과 n을 폭이 절반인 구간에 대응시키기 때문이다. 추첨이나 등급 배정에 이 관용구를 쓰면 양끝 등급만 조용히 희귀해진다.

  • 0 이상 1 미만은 반열림이다. 500만 회에서 정확히 0도, 정확히 1도 나오지 않았다. 최솟값 관측치는 1.8e-7이었다
  • 비트 연산으로 절단하는 관용구는 2의 31제곱을 넘는 범위에서 음수를 낸다. 폭 50억에서 -544,967,296이 나왔다
  • 실수 한 개가 담는 정보는 최대 53비트다. 그보다 넓은 범위를 요구하면 영영 안 나오는 값이 생긴다
  • 양끝을 포함하고 싶으면 반올림이 아니라 구간 개수를 하나 늘려 내림해야 한다. 표의 두 번째 줄이 그것이다
  • 이 모든 것을 호출자가 매번 판단하지 않게 하려면, API가 열림과 닫힘을 이름으로 밝혀야 한다

세는 것만으로 증명된다. 교환 상대를 배열 전체에서 뽑으면 경로가 n의 n제곱 가지인데, 결과는 n 팩토리얼 가지다. 4원소면 256을 24로 나눠 10.667이 되어 정수가 아니다. 같은 확률의 경로를 정수 개씩 나눠 줄 수 없으니 균등이 불가능하다. 올바른 형태는 교환 상대를 0부터 현재 위치까지에서만 뽑는 것이고, 그러면 경로가 정확히 n 팩토리얼 가지가 된다.

  • 비교자 셔플은 배열 길이가 길수록 더 나빠진다. 길이 16에서 첫 원소가 제자리에 남을 확률이 13.26%로, 공정값 6.25%의 두 배였다
  • 같은 코드가 정렬 알고리즘 구현에 따라 다른 분포를 낸다. 런타임이 바뀌면 결과도 바뀐다는 뜻이다
  • 비교자는 「같은 두 원소를 비교하면 항상 같은 답」이라는 전제 위에서 동작하는데, 무작위 비교자는 그 전제를 깬다
  • 결론은 3절과 같다. 셔플도 라이브러리가 제공해야 한다. 제공하지 않으면 비교자 트릭이 반드시 등장한다

6. 보안용을 써야 하는 자리

이제 두 계열의 차이가 결과에 어떻게 나타나는지 본다. 같은 토큰 생성 함수를 통계용과 보안용 위에 각각 올렸다.

주의할 점을 먼저 밝힌다. 이 절은 「통계용은 예측 가능하다」는 성질만 확인한다. 그 성질을 어떻게 이용하는지, 어떤 절차로 다음 값을 알아내는지는 다루지 않는다.

두 서비스가 같은 시드로 출발하자 24자리 토큰 세 개가 완전히 같았다. 통계용 생성기는 상태가 곧 자기 자신이기 때문이다. 그리고 이 성질은 2절에서 우리가 원했던 바로 그 성질이다. 같은 기능에 정반대 평가가 붙는다. 재현이 필요한 자리에서는 장점이고, 비밀 값을 만드는 자리에서는 결함이다.

이 글에서 하지 않는 것. 예측 가능성을 이용하는 절차는 쓰지 않았다. 필요한 판단에는 성질만으로 충분하기 때문이다. 「이 값은 상태가 정해지면 함께 정해진다」는 사실 하나면 그 값을 비밀로 쓰지 않을 이유가 된다. 반대 방향의 안전 주장, 즉 「알아내기 어렵다」는 주장은 공격 기법이 나아지면 무너지지만, 「구조적으로 정해져 있다」는 사실은 바뀌지 않는다.

  • 그러면 작업들이 병렬로 돌아가도, 순서가 바뀌어도 각 작업의 수열이 그대로 유지된다
  • 전역 생성기를 제공하는 API는 편해 보이지만, 편의 하나 때문에 재현성 전체를 포기하게 만든다
  • 이 문제는 시드를 아무리 잘 관리해도 해결되지 않는다. 구조의 문제이지 값의 문제가 아니다

8. 다시 설계한다면 - 이름, 시드, 범위, 기본값

앞의 일곱 절에서 나온 함정을 전부 막는 표면을 실제로 만들어 돌려 봤다. 규칙은 네 개다. 이름으로 종류가 드러나게, 시드를 명시적으로, 범위 함수를 제공, 기본값을 안전한 쪽으로.

// the family is in the constructor name, and the seed is not optional
function statisticalRng(seed) {
  if (!Number.isInteger(seed)) throw new TypeError('statisticalRng(seed) requires an explicit integer seed');
  const api = core(splitmix32(seed));    // deterministic engine
  api.seed = seed;                       // the value that goes into a failure report
  api.kind = 'statistical';
  return api;                            // an instance, never a module-level singleton
}

const secureRandom = (() => {
  const pool = new Uint32Array(1024);    // batched: per-call overhead was the cost, not the algorithm
  let i = pool.length;
  const u32 = () => { if (i >= pool.length) { crypto.getRandomValues(pool); i = 0; } return pool[i++]; };
  const api = core(u32);
  api.kind = 'security';
  api.token = (chars = 22) => { /* ... */ };     // exists only on this object
  return api;                            // no seed parameter, so none can be passed
})();

// one shared surface, so range and collection helpers read the same on both
function core(u32) {
  return {
    intBelow:     (n) => bounded(u32, n),                      // [0, n)  half-open, the name says below
    intBetween:   (lo, hi) => lo + bounded(u32, hi - lo + 1),  // [lo, hi] closed, the name says between
    unitInterval: () => u32() / 4294967296,                    // [0, 1)  named after its range
    pick:         (arr) => arr[bounded(u32, arr.length)],      // no index arithmetic at the call site
    shuffled:     (arr) => { /* Fisher-Yates on a copy */ },   // past tense: returns a copy
  };
}

핵심은 두 생성자의 모양 자체가 다르다는 것이다. 통계용은 시드 없이 만들 수 없고, 보안용은 시드를 넣을 자리가 없다. 문서를 안 읽어도 표면이 강제한다. 이 표면으로 앞의 세 가지 함정을 다시 통과시켰다.

  • 빠른 경로가 필요하면 제공하되, 이름을 길고 명시적으로 만들어 실수로 고르지 않게 한다

9. 정리 - 어려운 것은 알고리즘이 아니라 이름과 기본값

여기까지의 실행으로 확인한 것을 한 문장으로 줄이면 이렇다. 난수에서 틀리는 지점은 대부분 난수 생성이 아니라 그 값을 다루는 표면이다. 알고리즘은 이미 답이 정해져 있고 라이브러리가 대신 해 준다. 그런데 그 라이브러리가 어떤 이름으로 무엇을 노출하느냐가 사고의 빈도를 결정한다.

특히 두 가지가 결정적이다. 첫째, 통계용과 보안용이 비슷한 이름을 가지면 사고는 반드시 난다. 실측에서 여섯 개 호출이 셋씩 갈렸는데 이름만으로는 구분되지 않았다. 이것은 사용자의 부주의가 아니라 표면의 결함이다.

둘째, 재현성은 있으면 좋은 것이 아니라 디버깅의 전제다. 시드가 없으면 실패를 인용할 수 없고, 인용할 수 없으면 고쳤다는 것을 증명할 수 없다. 시드를 선택 인자로 두면 아무도 넘기지 않는다. 그래서 필수 인자여야 한다.

  • 낯선 사람이 그 값을 알면 뭔가 얻는가. 이 한 줄로 계열을 가른다
  • 나머지 연산으로 범위를 자르지 않는다. 좁은 소스에서는 즉시 드러나고 넓은 소스에서는 영영 안 드러난다
  • 반올림으로 정수 범위를 만들지 않는다. 양끝이 절반 무게가 된다
  • 비교자로 섞지 않는다. 정렬 구현과 배열 길이에 따라 결과가 달라진다
  • 전역 생성기를 공유하지 않는다. 재현성이 호출 순서에 인질로 잡힌다
  • 시드를 나중에 붙이지 않는다. 필요해지는 시점은 이미 늦은 시점이다

# 난수 API 점검표 — 통계용·보안용, 범위, 셔플, 시드

> 근거: Windows 10 / Node.js v22.16.0 (win32 x64) 에서 실행 검증, 2026-08-01

## 1. 한 줄로 가른다

**낯선 사람이 그 값을 알면 뭔가 얻는가?**

- 예 → **보안용**. 토큰, 세션, 비밀번호 재설정 링크, 초대 코드, 임시 파일명, 추첨
- 아니오 → **통계용**. 샘플링, 지터, A/B 배정, 검사용 합성 데이터, 시각 효과

애매하면 보안용을 쓴다. 통계용이 필요한 자리에 보안용을 써서 나는 손해는 속도뿐이고,
반대 방향의 손해는 되돌릴 수 없다.

## 3. 범위 — 편향 없는 정수

`%` 로 자르면 소스 폭이 좁을수록 분포가 기운다. 8비트 소스에 `% 100` 이면
낮은 값 56개가 **50% 더 자주** 나온다 (실측 비율 1.499).

```js
// 편향 없는 [0, n) — 거절 표집
function intBelow(next, n) {
  if (!Number.isInteger(n) || n <= 0) throw new RangeError('bound must be a positive integer');
  if (n > 4294967296) throw new RangeError('bound exceeds source width');
  const limit = 4294967296 - (4294967296 % n);
  let v;
  do { v = next(); } while (v >= limit);   // next() 는 uint32
  return v % n;
}

// 양끝 포함 [lo, hi]
function intBetween(next, lo, hi) {
  if (hi < lo) throw new RangeError('intBetween(lo, hi) needs hi >= lo');
  return lo + intBelow(next, hi - lo + 1);
}
```

- 32비트 소스에서 거절 비용은 평균 **1.00 draw**, 최악 **2.00 draw** (실측)
- 8비트 소스에 `% 100` 은 거절률 21.88%, 그 대가로 편향 0
- 소스 폭이 좁을수록 편향이 커진다: 8비트/`%6` = 2.38%, 32비트/`%6` = 0.00000014%

## 4. 실수 → 정수 경계

| 관용구 | 실제 범위 | 판정 |
|---|---|---|
| `Math.floor(r * n)` | 0..n-1 균등 | **정답** (반열림) |
| `Math.floor(r * (n + 1))` | 0..n 균등 | **정답** (양끝 포함) |
| `Math.round(r * n)` | 0..n, 양끝 절반 | **틀림** — 실측 5.01% vs 10.00% |
| `Math.ceil(r * n)` | 0..n, 0이 거의 안 나옴 | **틀림** |
| `(r * n) \| 0` | 2^31 넘으면 음수 | **틀림** — span 5e9 에서 -544967296 |

`[0, 1)` 는 반열림이다. 실측 500만 회에서 정확히 0도, 정확히 1도 나오지 않았다.
`floor(r * n)` 은 1 직전의 최대 실수를 넣어도 n-1 에서 멈춘다 (n 이 2^53 이하일 때).

## 5. 셔플

```js
// Fisher-Yates — j 는 0..i 에서만 뽑는다
function shuffled(next, arr) {
  const x = arr.slice();
  for (let i = x.length - 1; i > 0; i--) {
    const j = intBelow(next, i + 1);
    const t = x[i]; x[i] = x[j]; x[j] = t;
  }
  return x;
}
```

| Fisher-Yates (j 를 0..i) | 9,782 | 10,197 | 1.04 | **24** |

- 비교자 셔플은 원래 순서를 **11배** 자주 남긴다 (45,021 vs 기대 10,000)
- 잘못된 Fisher-Yates 는 n^n 경로를 n! 결과에 나눈다. n=4 면 256/24 = 10.667, 정수가 아니라 균등이 **불가능**
- 길이가 길수록 비교자 셔플의 치우침이 드러난다: 길이 16 에서 첫 원소가 제자리에 남을 확률 13.26% (공정값 6.25%)

생성기를 나눠 주자 3가지 모두 같아졌다. 작업 단위마다 `시드 + 작업 ID` 로 자식 생성기를 파생하면
병렬로 돌려도 재현성이 유지된다.

## 8. API 설계 점검 목록

- [ ] 함수 **이름에 종류가 드러난다** (statistical / secure)
- [ ] 통계용은 **시드가 필수 인자**다. 인자 없는 형태를 만들지 않는다
- [ ] 보안용에는 **시드 매개변수가 아예 없다**
- [ ] 범위 함수를 라이브러리가 제공한다 (`intBelow`, `intBetween`)
- [ ] 범위 이름이 **열림/닫힘을 말한다** (`below` = 미포함, `between` = 포함)
- [ ] 셔플을 라이브러리가 제공한다. 비교자 트릭이 등장할 자리를 없앤다
- [ ] 생성기는 **인스턴스**다. 전역 싱글턴을 노출하지 않는다
- [ ] 잘못된 인자는 **던진다**. 조용히 이상한 값을 돌려주지 않는다
- [ ] 토큰 생성은 **보안용 객체에만** 존재한다
- [ ] 기본값이 안전한 쪽이다. 빠른 쪽은 명시적으로 골라야 한다
- [ ] 재현성 계약을 문서에 적는다 (버전 올라가도 같은 수열인가)
- [ ] 배열을 **변형하지 않고 복사본을 돌려준다** (`shuffled`, 과거형)

## 9. 하지 말 것

- ❌ 이름만 보고 종류를 짐작하는 것 — 실측에서 6개 호출 중 통계용 3, 보안용 3이 모두 `random` 을 포함했다
- ❌ 토큰을 통계용 생성기로 만드는 것 — 같은 시드면 다른 서버에서도 같은 토큰이 나온다
- ❌ `%` 로 범위 자르기 — 소스 폭이 좁으면 즉시 드러나고, 넓으면 영영 안 드러난다
- ❌ `Math.round` 로 정수 범위 만들기 — 양끝이 절반 무게가 된다
- ❌ `| 0` 으로 절단 — 2^31 넘는 범위에서 음수가 나온다
- ❌ 비교자로 섞기 — 정렬 알고리즘과 배열 길이에 따라 결과가 달라진다
- ❌ 전역 생성기 하나를 여러 곳에서 쓰는 것 — 재현성이 호출 순서에 인질로 잡힌다
- ❌ 시드를 「나중에 붙이면 되는 것」으로 미루는 것 — 재현은 디버깅의 전제다
