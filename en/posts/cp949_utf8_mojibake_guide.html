Locating Where Hangul Breaks - cp949, UTF-8, and the Two Kinds of Encoding Error

Tracing the cause back from the broken shape, and telling recoverable damage from the kind that is gone for good

2026-07-30 Dev & Infra

Introduction: it is broken is not a diagnosis

You open a CSV a partner sent you and every Hangul character shows up as gibberish. Most people respond in one of two ways at this point. They cycle through encoding settings, or they ask the sender to resend. Neither is wrong, but the order is backwards. The first thing you need to know is whether this file is in a fixable state at all.

There are only two kinds of encoding error. You could say this distinction is the whole of this article.

  • (1) The bytes are right, the interpretation was wrong. The original bytes sit intact inside the file and the reading side applied the wrong encoding, so only the display is strange. Fully recoverable.
  • (2) Information disappeared during conversion. Somebody already saved the result of a bad read, or a character missing from the target encoding was swapped for a question mark. The original does not come back.

From the outside both look like the same thing, characters got mangled. But (1) is one command away from done, and for (2) there is nothing to do except get the original again. Skip that determination and you can spend a whole day nursing a file that is already dead.

This article is about making that call. It will not tell you to use UTF-8. That advice does nothing for someone already sitting in front of a broken screen, and it does not change the reality that government offices and banks still send cp949 files. Instead I built a table that traces the cause backwards from the broken shape, and filled every cell of it by execution.

Test environment. Every output below was actually executed on Windows 10 Pro (10.0.19045). The shell is GNU bash 5.2.37 (MSYS2/MinGW64), the tools are Node.js v22.16.0 (win32), Python 3.13.3 and GNU libiconv 1.18. Both the system ANSI and OEM code pages are 949, and in the shell locale LANG is empty with LC_CTYPE=C.UTF-8.

Every script was saved to a file before running. Code mixing Hangul with backslashes gets silently mangled when passed as a shell argument or a heredoc. If the quoting rules themselves are what you are curious about, see Shell Quoting Rules. Example paths were rewritten as placeholders such as /tmp/demo and ~/work.

What this article does not cover. The normalization problem, where the same character becomes two different code point sequences inside Unicode, is covered in NFC and NFD. This article digs only into conversion between Unicode and legacy encodings. The arithmetic of handling Hangul syllables as regex ranges is in The Korean Regex Trap, and the problem of spaces and newlines in filenames breaking pipelines is in The Whitespace Trap in find and xargs. Filenames here are examined only from the encoding angle.

1. Same characters, different bytes - three versus two

The origin of every problem here is simple. The same word 한글 becomes different bytes depending on the encoding. I printed them side by side.

How to read it. UTF-8 writes one Hangul character as three bytes, cp949 as two. ASCII characters are one byte in both, with identical values. That is why a file containing only letters and digits survives the wrong encoding without incident. The accident starts the moment Hangul enters.

--- 1-2. per-syllable breakdown of the word ---
한  U+D55C   utf-8 ED 95 9C (3 B)   cp949 C7 D1 (2 B)
글  U+AE00   utf-8 EA B8 80 (3 B)   cp949 B1 DB (2 B)

--- 1-3. euc-kr vs cp949 coverage ---
char    euc-kr          cp949           note
------------------------------------------------------------
가      B0 A1           B0 A1           in the 2350 basic set
한      C7 D1           C7 D1           in the 2350 basic set
똠      A4 D4 A4 A8 A4 C7 A4 B1  8C 63  outside basic set, cp949 extension only
뷁      A4 D4 A4 B2 A4 CE A4 AA  94 EE  outside basic set, cp949 extension only
펖      A4 D4 A4 BD A4 C3 A4 BD  BC 6A  outside basic set, cp949 extension only

One important fact falls out here. 한 and 가 have exactly the same bytes in euc-kr and cp949. cp949 is an extension of euc-kr, so most of the territory overlaps. That is why mixing the two names usually causes no trouble.

Then 똠 splits them. That syllable sits outside the base 2,350 characters of euc-kr, and cp949 represents it as the two bytes 8C 63. This environment's Python euc_kr codec, by contrast, turned the same character into 8 bytes. It used the old scheme of laying out combining jamo one after another. What kind of accident this difference causes in practice comes back in section 10.

1.1 What cp949 cannot hold at all

--- 1-4. what cp949 cannot hold at all ---
simplified Chinese            U+7B80 U+4F53           UnicodeEncodeError: illegal multibyte sequence
Japanese kana                 U+3042                  AA A2
NFD-decomposed 한 (3 jamo)    U+1112 U+1161 U+11AB    UnicodeEncodeError: illegal multibyte sequence
emoji U+1F600                 U+1F600                 UnicodeEncodeError: illegal multibyte sequence
euro sign U+20AC              U+20AC                  A2 E6
  • Kana fits. cp949 has a Japanese kana area, so U+3042 converted to AA A2. Thinking of cp949 as Hangul only is a mistake
  • The euro sign fits too. It is A2 E6. In other words, conversion failure is not caused by a character not being Korean
  • Simplified Chinese does not fit. The Hanja in cp949 are the traditional set, so 「简体」 was rejected
  • Emoji do not fit. They live outside the Unicode Basic Multilingual Plane, so there is no representation at all
  • Hangul decomposed into jamo does not fit either. Only precomposed syllables are mapped; the combining jamo area has no mapping. Try to export a string in NFD form as cp949 and it blows up right here

2. Breakage has a direction - four faces

Now the core of it. The encoding is wrong is not a single situation. Which bytes were read with which encoding completely changes the kind of character that appears on screen. And that kind tells you the cause.

The two directions look nothing alike. The reason is the three bytes versus two bytes from section 1.

  • Direction A (cp949 read as UTF-8). Most cp949 two byte combinations do not satisfy the UTF-8 rules. In UTF-8 the first byte declares the length and the bytes that follow must fall in a specific range, and cp949 bytes do not obey that. So most of them turn into replacement characters. Six of nine characters were replacement characters
  • Direction B (UTF-8 read as cp949). cp949 consumes two bytes at a time, so it keeps picking up misaligned slices of something written in three byte units. And those combinations often happen to map to valid Hanja or Hangul. That is how you get a result like 「湲덉븸」 that looks like readable characters with no meaning

This asymmetry is decisive for diagnosis. A swarm of replacement characters means direction A; a jumble of Hanja and Hangul means direction B.

2.1 When it is read with a single byte code page

The third and fourth faces are the ones you see overwhelmingly often on the web and in mail. They come from reading with a Western default code page.

One decisively useful rule comes out of this. Letter case.

  • Lowercase accented Latin letters mean the source was UTF-8. In UTF-8 the first byte of Hangul falls between EA and ED, and those values correspond to lowercase accented letters in single byte code pages
  • Uppercase accented Latin letters mean the source was cp949. cp949 first bytes cluster around B0 to C8, and that stretch corresponds to uppercase accented letters and symbols
  • Symbols such as ± and µ mixed into the output are another cp949 signal
  • The important point is that in both of these cases the bytes are intact. As section 4 shows, they recover completely

4. Damage you can undo and damage you cannot

Now I separate (1) and (2) from the introduction by execution. The recoverable side first.

original    : 한글 데이터
cp949 bytes : C7 D1 B1 DB 20 B5 A5 C0 CC C5 CD

--- 3-1. RECOVERABLE: wrong reading, bytes untouched ---
read as latin_1 -> you see : [ÇÑ±Û µ¥ÀÌÅÍ]
re-encode latin_1          : C7 D1 B1 DB 20 B5 A5 C0 CC C5 CD

fully recovered            : True

--- 3-2. NOT RECOVERABLE: replacement char ate the bytes ---
read as utf-8/replace      : [�ѱ� ������]
codepoints                 : U+FFFD U+0471 U+FFFD U+0020 U+FFFD U+FFFD U+FFFD U+FFFD U+FFFD U+FFFD
re-encode utf-8            : EF BF BD D1 B1 EF BF BD 20 EF BF BD EF BF BD EF BF BD EF BF BD EF BF BD EF BF BD
bytes identical to source  : False
source len 11 B  ->  now 27 B
try decode cp949           : [占싼깍옙 占쏙옙占쏙옙占쏙옙]
equals original            : False
every FFFD is 3 bytes EF BF BD, and the byte it replaced is gone

Look carefully at the difference between the two blocks. In 3-1, the re-encoded bytes were identical to the source (True). The bytes were untouched, so reading them again with the correct encoding was enough to bring the original text back.

In 3-2, 11 bytes grew to 27. That is because a single replacement character takes three bytes, EF BF BD, when saved as UTF-8. And decisively, those three bytes hold no information about which byte they stood in for. Every failure gets flattened to the same value. That is why recovery is impossible in principle.

Working rule. Seeing replacement characters is fine. They only appeared on screen for a moment and the file is unharmed. What is dangerous is saving that state. The instant you write the bad read back out, (1) becomes (2), and at that moment the original dies. So for a file whose encoding you doubt, open it read only and do not press save until you are certain. That is the first line of defence.

4.1 When it disappears at encode time

Case (2) has a second route. You lose it not when reading but when writing.

  strict cp949        : UnicodeEncodeError at position 4
  replace -> bytes    : BA B8 B0 ED BC AD 20 3F 3F 20 C3 B7 BA CE
  replace -> decoded  : [보고서 ?? 첨부]
  ignore  -> decoded  : [보고서  첨부]
  xmlcharref -> dec   : [보고서 &#31616;&#20307; 첨부]

  strict cp949        : OK  B0 A1 B0 DD 20 31 30 30 A2 E6 20 C8 AE C1 A4

The third case is instructive. The euro sign exists in cp949, so it survived intact. In other words the rough guess that every non Korean character breaks is wrong. What actually converts and what does not is something you have to check.

  • replace inserts the ASCII question mark 3F. It is indistinguishable from a question mark a person typed, which also makes it hard to find later
  • ignore leaves no trace at all. It is the most dangerous. 「가격 100 확정」 looks grammatically perfect, so nobody suspects a thing
  • xmlcharrefreplace converts to a numeric reference and preserves the information. On a path that flows into HTML, this option prevents the loss
  • Either way, the fact that the target encoding does not know that character does not change. The real fix is not to convert at all

For recovery work, latin-1 is the right choice. It round-trips all 256 byte values. cp1252 has five bytes with no character defined, so when it meets data containing those values the recovery process itself loses information.

The last line proves the impossible to recover cells of the section 3 table again. Once replacement characters are in the string, no encoding you try will produce the original text.

5. What 「占쏙옙」 really is - evidence of double damage

Anyone who has lived through an encoding incident in Korea has seen these characters. I reproduced step by step where they come from.

--- 3-6. where the infamous string comes from ---
step 1. real cp949 text
  한글 -> cp949 C7 D1 B1 DB
step 2. some layer decodes it as UTF-8 with replacement
  -> [�ѱ�]   U+FFFD U+0471 U+FFFD
step 3. that string is saved as UTF-8
  -> EF BF BD D1 B1 EF BF BD
step 4. a later reader opens those bytes as cp949
  -> [占싼깍옙]

the replacement char alone, put through the same two steps:
  U+FFFD as utf-8 : EF BF BD
  x2              : EF BF BD EF BF BD -> [占쏙옙]
  x3              : EF BF BD EF BF BD EF BF BD -> [占쏙옙占�]
  x4              : [占쏙옙占쏙옙]
  odd counts leave a dangling byte: cp949 eats 2 at a time, UTF-8 wrote 3

The structure is clear. Two replacement characters saved as UTF-8 become the six bytes EF BF BD EF BF BD. cp949 reads two bytes at a time, so it cuts them into the three pairs EF BF, BD EF and BF BD. What was written in three byte units was read in two byte units, so three characters come out. The least common multiple of 6 and 3 is 6, which is why the pattern repeats exactly.

The practical conclusion matters. If you have seen this string, stop trying to recover. It is evidence that damage happened twice, and the original bytes were already gone at the first stage. Correct the second misreading and all you get back is replacement characters.

--- 3-7. how to tell single damage from double damage ---
what you see          U+FFFD present  recoverable   meaning
------------------------------------------------------------------------------
ÇÑ±Û                  False           True          misread only, bytes intact
replacement run       True            False         bytes already destroyed
the infamous one      False           False         bytes already destroyed

There is a trap on the third line. A doubly damaged string contains no replacement characters any more. They were mapped to ordinary Hanja and Hangul during the second misreading. So the judgment there are no replacement characters, therefore it is fine is wrong. The absence of replacement characters is not evidence of health. You have to recognize the specific pattern separately.

6.2 The BOM bug that survives correct decoding

Adding a BOM is not the end of it. The problem persists even when you read as UTF-8 correctly.

--- 4-4. the BOM bug that survives correct decoding ---
read with utf-8      header : ['﻿이름', '부서', '금액']
  header[0] codepoints      : U+FEFF U+C774 U+B984
  header[0] == 이름         : False
read with utf-8-sig  header : ['이름', '부서', '금액']
  header[0] == 이름         : True

DictReader with utf-8     keys : ['﻿이름', '부서', '금액']
  d.get(이름)                  : None
DictReader with utf-8-sig keys : ['이름', '부서', '금액']
  d2.get(이름)                 : '김철수'

This is an accident that really does happen a lot in practice. The screen shows 이름, yet the comparison is False and the dictionary lookup returns None. The BOM is sitting in front of the first column name as the invisible character U+FEFF.

  • The symptom appears only in the first column. The second and third columns are normal, which makes the cause hard to find
  • Printing a log does not reveal it. It only shows up when you print code points
  • The fix is to use a codec that strips the BOM. You specify it once, at the point where the file is opened
  • When handling column names, trimming surrounding whitespace will not catch it. U+FEFF is not classified as whitespace

6.4 Validity checks cannot decide it

Plenty of code takes the approach of try UTF-8 and fall back to cp949 on failure. I checked why that is guesswork.

  짙  cp949 C2 A3   -> same bytes as utf-8 give [£] U+00A3
  짚  cp949 C2 A4   -> same bytes as utf-8 give [¤] U+00A4
  짜  cp949 C2 A5   -> same bytes as utf-8 give [¥] U+00A5

  a 4-syllable text built from them : 징짖짙짚
  cp949 bytes                       : C2 A1 C2 A2 C2 A3 C2 A4
  those bytes decoded as utf-8      : [¡¢£¤]

For 345 Hangul syllables the cp949 byte sequence is itself valid UTF-8. So I really could build text that reads without an exception under either encoding. The judgment no exception was raised, therefore it is UTF-8 fails silently in that range.

The conclusion is this. Determining an encoding from bytes alone is impossible in principle. The BOM is the only positive signal, and without it everything else is probability. So the only real fix is for the two sides exchanging files to agree on an encoding and write it down in the spec.

 c3 87 d1 b1 c3 9b 2e 74 78 74 0a eb b3 b4 ea b3
 a0 ec 84 9c 2e 74 78 74 0a

I asked for a file named with the cp949 bytes C7 D1 B1 DB, but the bytes of the name left on disk were C3 87 D1 B1 C3 9B. The bytes I requested were not stored as they were. Taking apart what happened gives this.

  • C7 is a UTF-8 two byte lead byte, but the D1 following it is not a valid continuation byte. So C7 alone was treated as one character
  • The remaining D1 B1 happened to be a valid UTF-8 two byte combination, so it was bundled into one character
  • The final DB was also handled on its own. The result is a three character name, which was then re-encoded as UTF-8 and stored as six bytes
  • In other words, in this environment a cp949 filename cannot exist. Filenames are always re-encoded at the boundary

That is the fundamental difference between a filename and file content. File content is preserved byte for byte, but a filename is converted into the operating system's own form before storage. That is why content round-trips safely even under the wrong encoding while a name does not.

7.2 Why a search catches only half

--- 5-6. can a glob find either one ---
glob 보고* matches : 1
glob *.txt matches : 2
total entries      : 2

--- 5-7. grep for the Korean word: name layer vs content layer ---
grep -l for UTF-8 한글  : ./ÇѱÛ.txt
grep -l for cp949 한글  : ./보고서.txt
one pattern, one encoding, finds only the matching half

These two lines explain the most confusing phenomenon in day to day work. You search for the same word 한글 and get different files depending on the encoding. The UTF-8 pattern caught the file with the broken name, and the cp949 pattern caught the file with the normal name. Search tools compare bytes, so a match happens only when the pattern's encoding matches the target's encoding.

  • A large share of reports saying the word is definitely there but search will not find it are this
  • In a repository with mixed file contents, you have to run the same search twice, once per encoding, to have covered everything
  • The real fix is not a search option but unifying the repository on one encoding
  • Glob patterns follow the same principle. Match on extension alone and both come back; match on a Hangul prefix and only one does

8. Shell, terminal, code page

The same file looks fine in one terminal and broken in another. What decides that is the code page.

OEM / ANSI codepage from the registry side:
    ACP    REG_SZ    949
    OEMCP    REG_SZ    949

--- 6-7. the chcp message is itself a mojibake specimen ---
raw bytes            :  c8 b0 bc ba 20 c4 da b5 e5 20 c6 e4 c0 cc c1 f6 3a 20 39 34 39 0d 0a

the tool announced codepage 949 in codepage 949, and the pipe assumed UTF-8

This output is the whole article in miniature. The tool that reports the code page wrote its own answer out in code page 949, and the pipe that received it assumed UTF-8. That is why 「활성 코드 페이지: 949」 looks broken.

The lesson here is that no encoding information flows through a pipe. A file can carry a BOM and HTTP has headers, but a pipe carries only bytes. Each side uses its own default. In this environment the system code page is 949 while the shell locale is C.UTF-8, so two defaults are in conflict inside one machine.

8.1 What PYTHONIOENCODING changes and what it does not

--- 6-3. PYTHONIOENCODING changes stdout encoding, nothing else ---
[unset]
stdout.encoding = cp949
sys.getdefaultencoding() = utf-8
sys.getfilesystemencoding() = utf-8
[PYTHONIOENCODING=utf-8]
stdout.encoding = utf-8
[PYTHONIOENCODING=cp949]
stdout.encoding = cp949
[PYTHONIOENCODING=ascii]
stdout.encoding = ascii

--- 6-5. what PYTHONIOENCODING does NOT change ---
[unset]
locale.getpreferredencoding(False) = cp949
open() default encoding            = cp949
[PYTHONIOENCODING=cp949]
locale.getpreferredencoding(False) = cp949
open() default encoding            = cp949
[PYTHONUTF8=1]
locale.getpreferredencoding(False) = utf-8
open() default encoding            = utf-8

The distinction has to be precise. PYTHONIOENCODING changes only the encoding of standard output. It does not touch the default encoding used when opening a file. In the environment I checked, that value was cp949.

  • A problem with broken screen output is fixed by PYTHONIOENCODING
  • If the problem is the encoding used to read and write files, this variable has no effect whatsoever. Reaching for it based on the symptom alone wastes your time
  • To align the file side as well in one move you need PYTHONUTF8=1. Running it, the open() default changed to utf-8
  • The most reliable approach is not to depend on environment variables but to state the encoding in the code that opens the file. Environment variables differ from one deployment to the next

--- 6-4. same print, four stdout encodings, bytes captured ---

The key is that the latin-1 line is empty. Specify an encoding that cannot represent Hangul and you do not get mangled characters, the program dies. The exit code was 1.

That distinction is the last row of the section 3 table. If there is no output at all and the exit code is not zero, the data is safe. It stopped before reaching the encoding stage. Conversely, bolt on replace handling and the program survives but only question marks remain. Dying is the safer outcome for the data.

Node is different. In this environment it always wrote UTF-8, unaffected by the code page being 949. In other words Python and Node emit different output bytes on the same machine. Wire the two together with a pipe and that becomes your accident site.

8.3 What LANG and LC_ALL change

--- 6-6. LANG / LC_ALL effect on this toolchain ---
LC_ALL=[]             6  chars   /   sort: A 한글
LC_ALL=[C]            6  chars   /   sort: A 한글
LC_ALL=[ko_KR.UTF-8]  2  chars   /   sort: A 한글
LC_ALL=[ko_KR.eucKR]  3  chars   /   sort:

Asking for the character count of 한글 produced 6, 6, 2 and 3 depending on the locale. The right answer is 2.

  • In the C locale it counts bytes. UTF-8 makes it 6 bytes, so 6 came out
  • Only under ko_KR.UTF-8 did it count by character and give 2
  • ko_KR.eucKR interpreted UTF-8 bytes as two byte characters and produced the nonsense answer 3. And sorting produced no output at all
  • In other words the locale decides how a tool bundles bytes into characters. Character counts, sorting and case conversion all hang off it

9. The HTTP boundary - who reads the charset header

I stood up a server that emits the same bytes under five different Content-Type values and checked how a client interprets them.

node v22.16.0 / win32

--- 7-1. what fetch().text() gives for each declared charset ---
route             Content-Type                    res.text()
----------------------------------------------------------------------------
/utf8-correct     text/plain; charset=utf-8       [한글 금액]
/cp949-declared   text/plain; charset=euc-kr      [�ѱ� �ݾ�]
/cp949-lying      text/plain; charset=utf-8       [�ѱ� �ݾ�]
/cp949-silent     text/plain                      [�ѱ� �ݾ�]

--- 7-3. so did the charset header change anything? ---
charset=euc-kr  -> U+FFFD U+0471 U+FFFD U+0020 U+FFFD U+077E U+FFFD

The result is unambiguous. This client's text() did not look at the declared charset at all. Told exactly euc-kr, it still decoded as UTF-8, and the code points in three of the cases were completely identical.

The line worth staring at is the last one. A UTF-8 body falsely declared as charset=euc-kr was read correctly. Which is to say the charset header plays no role at all on this path. That is why attempts to fix the problem by correcting the header fail.

The prescription is to take the body as bytes rather than text and decode it yourself. Summarizing what was confirmed.

  • The two names euc-kr and windows-949 gave the same result. They wire up to the same decoder, the one that handles extended syllables too
  • Strict mode can be used as a validity check tool. It passed under the correct encoding and threw under the wrong one. All four combinations behaved as expected
  • But as section 6.4 showed, validity alone cannot decide it. Use it to narrow candidates and make the final call from an agreed spec
  • Node has no built-in ability to encode to cp949. Decoding works, encoding does not. If you have a requirement to produce and ship cp949 files, you need a separate approach

I will also note plainly what I could not confirm. What priority a browser gives to the charset header versus meta charset when rendering an HTML document was not verified by execution in this article. The results above concern the path where a script fetches a body, and different rules may apply to the document rendering path.

10. Converting exactly once, at the boundary

There is one realistic way to live with legacy. Convert once at the point where files arrive, and assume everything inside is UTF-8. The problem is that this single conversion can fail silently.

=== 9-1. plain UTF-8 to CP949, one file at a time ===
emoji.txt    FAILED: iconv: emoji.txt:1:7: cannot convert
euro.txt     OK
ext.txt      OK
zh.txt       FAILED: iconv: zh.txt:1:7: cannot convert

=== 9-2. exit codes matter. a silent pipeline loses this ===
exit code             : 1
bytes actually written:  ba b8 b0 ed bc ad 20
what got through     : 보고서
iconv stopped at the offending char and kept the prefix. truncation, not an empty file

This is the most dangerous behaviour there is. The conversion failed, and yet the output file already exists. Inside it is only the part before the failure point. The file exists and its content reads normally, so the only clue that it was truncated is the exit code.

  • If an automated conversion pipeline does not check the exit code, part of the data silently disappears
  • Truncation happens at the end of the file, so an inspection that opens only the beginning will never catch it
  • When commands are chained with pipes, a failure in the middle can be masked. It is exactly the structure covered in Exit Codes and Pipes

10.1 Three ways to push past a failure

=== 9-3. the three escape hatches ===
-c           rc=1  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
//TRANSLIT   rc=0  result=[보고서 :-D]  bytes= ba b8 b0 ed bc ad 20 3a 2d 44 0a
//IGNORE     rc=0  result=[보고서 ]  bytes= ba b8 b0 ed bc ad 20 0a
-c drops it, //TRANSLIT approximates or drops, //IGNORE drops and still reports failure

The //TRANSLIT result is striking. The emoji was approximated as three ASCII characters. A human can read it, but it is not the original.

ApproachBehaviour on failureMeasured exit codeState of the dataWhen it is worth using
No optionStops at the failure point1Everything after it is lostNever. Always check the exit code
-cDrops only the characters it cannot carry1Only those characters are lostWhen you proceed knowing it failed
//IGNOREDrops them0Only those characters are lostNot recommended. It hides the failure
//TRANSLITSubstitutes an approximation0Not the original, but readableLogs meant for humans to read

The most dangerous combination is //IGNORE plus an unchecked exit code. Characters vanished and it reports success. Run it with no option, on the other hand, and it tells you about the failure but leaves an already truncated file behind. Neither is safe, so verification has to be attached separately.

10.2 The same encoding name behaves differently per tool

=== 9-5. EUC-KR vs CP949 for extended syllables ===

This is the trap that holds people up longest in practice. Given the same name 「EUC-KR」, two tools behaved differently.

  • One refused the conversion, on the grounds that the character is not in the base 2,350
  • The other converted it to 8 bytes. That is the old scheme of laying out a fill character plus three combining jamo. Read it back and the original text comes out, so there is no loss
  • The problem is that the byte count is four times larger. Flow that into a place with a column length limit and it gets cut off there
  • So do not relax just because the encoding names line up. You have to push a sample through the tool your pipeline actually uses

10.3 How to verify a conversion

The conclusion is simple. Convert the converted thing back and compare the bytes against the source.

=== 9-6. round trip integrity check you can run in CI ===
original md5      : f765f0504efec35848a3c116a1c98d10
after round trip  : f765f0504efec35848a3c116a1c98d10
VERDICT: lossless

now the same check on a file that cannot survive:
original md5      : 4db91275cca0367a7fe3823751f802e8
after round trip  : 918226859d33c495cb4acde0bafc7e30
VERDICT: LOSSY - do not ship
diff             : 1c1 < 보고서 😀 --- > 보고서

The first file contained a euro sign and the hashes matched exactly. cp949 has the euro sign, so nothing was lost. The second had an emoji, so the hashes differed, and printing the difference showed precisely that one character had disappeared.

This check takes a few lines and its verdict is unambiguous. Attaching it everywhere you automate a conversion is the only way to stop silent data loss.

  1. Look at the first bytes. od -An -tx1 -N 12 f.csv is enough. Most cases are already settled here. Starting with EF BB BF means a BOM; spotting EF BF BD means the file is already damaged

  3. Test UTF-8 validity. Converting to the same encoding as itself works as the test. You only need the exit code of iconv -f UTF-8 -t UTF-8 f.csv
  4. Test cp949 validity. If step 3 fails and step 4 passes, cp949 is likely

12.1 How to live with legacy

The files government offices and banks send will keep being cp949. Here are the principles to hold to in that reality.

  1. Convert once, at the boundary. Convert to UTF-8 and store at the point where the file arrives, then make all code after that unaware of encoding. The moment code starts asking is this part cp949, the design has collapsed
  2. Do not verify after deleting the original. Keep the converted file and the source together, pass the round trip check, and clean up afterwards
  3. Export in the other side's encoding. If they expect cp949, convert again at the outbound boundary. Characters absent from cp949 can slip in here, which makes the round trip check even more important
  4. Never mix internally. Let two encodings coexist inside a repository and search catches only half, as section 7 showed
  5. Be wary of emoji and Simplified Chinese. Mix those into user input and exporting as cp949 is guaranteed to lose data. Screening at the input stage and telling the user beats discovering question marks later
  6. Write the encoding into the spec. As section 6.4 showed, bytes alone cannot decide it. Stating it in the exchange format is the only real fix

13. What this article could not verify

Writing down unverified things as verified would lead the next reader astray. Here are the limits, stated clearly.

  • The actual behaviour of spreadsheet programs. What section 6 calls a legacy reader is a direct reproduction of the decode as cp949 behaviour, not a specific spreadsheet product executed and observed. It may differ by product, version and regional settings
  • Document rendering in browsers. The section 9 results concern the path where a script fetches a body. The priority between meta charset and the HTTP header, and a browser's encoding guessing behaviour, were not verified by execution, so I assert nothing
  • The database boundary. What gets stored when the column character set and the connection character set disagree was not checked. This article's principles, convert once at the boundary and verify the round trip, apply unchanged, but the specific behaviour has to be checked in the product you use
  • Name encoding in archive files. Which encoding zip entry names are stored in is said to differ by tool, but I did not run it in this article
  • Other operating systems. The filename re-encoding result in section 7 may be specific to this environment. On systems that treat filenames as byte sequences the result would likely differ, but I did not check
  • Mail headers and attachment filenames. That area has its own encoding rules and was not covered
  • The accuracy of encoding auto detection libraries. Section 6.4 showed the limit in principle, but how well real tools guess statistically was not measured

The unverified items do share one trait. They are all questions about what the other side does. And the diagnostic method in this article does not depend on knowing the other side's behaviour. Looking directly at the bytes works the same way in any environment. That is why the advice is to look at bytes instead of guessing.

Conclusion: the first question is can this be fixed

Look at a broken screen and you want to start fiddling with encoding settings. But the order is wrong. The first question is whether this file is in a fixable state. The answer completely changes what you should do.

Summarizing what execution confirmed: every misread with intact bytes recovered completely. Even with cp949 bytes read as latin-1, re-encoding, confirming the bytes matched the source, and then reading with the correct encoding brought the original text back exactly. That holds however ugly the screen looks.

By contrast, the moment replacement characters get involved, recovery becomes impossible in principle. 11 bytes grow to 27, and the extra bytes hold no information about the original values. And when that state is misread again you get a specific three character pattern, at which point the only answer is to stop trying to recover and get the source again. Counting EF BF BD in the bytes to make that determination was the fifth step of the diagnosis.

So the conclusion is not convert everything to UTF-8. That does not work. The other side will not change, and validity checks alone cannot even determine the encoding. The realistic conclusion is to pick one conversion point, verify by round trip that the conversion finished without loss, and make everything inside unaware of encoding. And above all, to look at the bytes before you guess.

There is one thing you can do right now. Find the code or script that converts encodings and check whether it inspects the exit code of that conversion. If it does not, that pipeline may have been quietly truncating data all along. And that fact will never surface from an inspection that opens only the front of the file.

> ⚠ Open suspect files **read-only, and do not save until you are sure.** Saving turns a recoverable error into an unrecoverable one.

## 0. The premise — there are exactly two kinds of encoding error

| Kind | What happened | Recoverable |
|---|---|---|
| **1. Misread** | Bytes are intact; the reader applied the wrong encoding | **Fully** |
| **2. Destroyed** | A misread result was saved, or a character absent from the target encoding was substituted | **No** |

**Decide which one first.** Fiddling with encoding settings on a type-2 file is wasted time.

## 1. 30-second triage — look at bytes before opening an editor

```bash
FILE=./suspect.csv

od -An -tx1 -N 16 "$FILE"                                  # first 16 bytes
iconv -f UTF-8 -t UTF-8 "$FILE" >/dev/null 2>&1; echo "utf8  ok=$?"
iconv -f CP949 -t UTF-8 "$FILE" >/dev/null 2>&1; echo "cp949 ok=$?"

# how many replacement characters are baked in (the unrecoverable signal)
od -An -tx1 "$FILE" | tr -d ' \n' | grep -o efbfbd | wc -l
```

- `ok=0` means the file is valid in that encoding
- First three bytes `EF BB BF` means a **UTF-8 BOM** — encoding is settled (the only positive signal)
- If the last line is **greater than zero, the file is already dead.** Request the original again

## 2. What you see on screen -> probable cause

| On screen | Example | Cause | Confirm with | Recoverable |
|---|---|---|---|---|
| Run of diamond-question marks | `�ѱ� ���ڵ�` | cp949 bytes read as UTF-8 | `iconv -f CP949 -t UTF-8` | **Yes**, if only displayed |
| Uppercase accented Latin + symbols | `ÇÑ±Û ÀÎÄÚµù` | cp949 bytes read as latin-1 family | re-encode latin-1, decode cp949 | **Yes** |
| Lowercase accented Latin | `ê¸ˆì•¡` | UTF-8 bytes read as latin-1 family | re-encode latin-1, decode UTF-8 | **Yes** |
| CJK ideographs mixed with Hangul | `湲덉븸 遺꽌` | UTF-8 bytes read as cp949 | re-encode cp949, decode UTF-8 | **Yes** |
| One three-character pattern repeating | `占쏙옙` | **Double damage.** Replacement chars saved, then read as cp949 | count `efbfbd` bytes | **No** |
| Three junk characters before the first cell | `ï»¿이름` | UTF-8 BOM read as latin-1 family | first three bytes | **Yes** (strip BOM) |
| One ideograph before the first cell | `癤우` | UTF-8 BOM read as cp949 | first three bytes | **Yes** |
| Literal ASCII question marks | `보고서 ?? 첨부` | Substituted at **encode** time; target lacks the character | check the byte is `3F` | **No** |
| No output at all | (blank line + exception) | Output encoding cannot represent the character; process crashed | exit code, stderr | Data is **intact** |

**Letter case tells you the direction.** Lowercase accented Latin -> the original was UTF-8. Uppercase accented Latin -> the original was cp949.

## 3. Repair — when it was only a misread

```python
# repair.py — turn a wrongly displayed string back into the original
import sys

seen = sys.argv[1]              # the string as you see it
raw = seen.encode('latin-1')    # resurrect the exact bytes
print(raw.decode('cp949'))      # read them with the right encoding
```

```bash
python repair.py "ÇÑ±Û ÀÎÄÚµù"      # -> 한글 인코딩
```

- **Always use `latin-1`.** It round-trips all 256 byte values
- `cp1252` leaves five bytes undefined (`81 8D 8F 90 9D`), so it **loses data during the repair itself**
- If the mangled bytes were UTF-8, change the last line to `decode('utf-8')`
- For whole files, restore with `iconv -f ISO-8859-1 -t UTF-8` and then re-triage

## 4. Unrecoverable verdict — stop here

```bash
# if replacement characters were saved, the original bytes are gone
od -An -tx1 "$FILE" | tr -d ' \n' | grep -c efbfbd

# trace of double damage (replacement chars re-read as cp949)
grep -c '占쏙옙' "$FILE"
```

If either hits, **do not attempt repair.** Why:

- A replacement character is stored as the three bytes `EF BF BD`, which carry **no record of the original byte**
- Every distinct failure collapses to the same value. An 11-byte sample grew to 27 bytes in testing
- The `占쏙옙` family contains **no replacement characters anymore** — the second misread mapped them onto ordinary glyphs, so **absence of replacement characters is not proof of health**

## 5. Convert once at the boundary — a form that cannot truncate

```bash
# bad: the file gets created even on failure (truncated, holding only the prefix)
iconv -f CP949 -t UTF-8 in.csv > out.csv

# good: leave no artifact when it fails
set -Eeuo pipefail
TMP=$(mktemp)
if iconv -f CP949 -t UTF-8 in.csv > "$TMP"; then
  mv "$TMP" out.csv
else
  rm -f "$TMP"
  echo "conversion failed — inspect the source" >&2
  exit 1
fi
```

**If you do not check the exit code, data disappears silently.** Truncation happens at the end of the file, so eyeballing the first few lines will never catch it.

| Mode | On failure | Measured exit code | Data | Verdict |
|---|---|---|---|---|
| no option | stops at the offending character | 1 | **everything after it is lost** | must check exit code |
| `-c` | drops the character | 1 | only that character lost | when proceeding knowingly |
| `//IGNORE` | drops it | 0 | only that character lost | **not recommended** (hides failure) |
| `//TRANSLIT` | substitutes an approximation | 0 | not the original | human-readable logs only |

## 6. Round-trip verification — attach it wherever you convert

```bash
# prove the conversion was lossless
roundtrip_ok() {
  local src="$1"
  iconv -f UTF-8 -t CP949 "$src" 2>/dev/null | iconv -f CP949 -t UTF-8 | cmp -s - "$src"
}

if roundtrip_ok data.csv; then
  echo "lossless — safe to ship"
else
  echo "lossy — find out which characters vanish" >&2
  iconv -c -f UTF-8 -t CP949 data.csv | iconv -f CP949 -t UTF-8 | diff - data.csv
fi
```

**Always lost** when exporting to cp949: emoji, Simplified Chinese, Hangul decomposed into jamo.
**Survives unexpectedly**: the euro sign (`A2 E6`), Japanese kana. The guess «anything non-Korean breaks» is simply wrong.

## 7. CSV and the BOM

```bash
# add a BOM (tells a spreadsheet the file is UTF-8)
printf '\xEF\xBB\xBF' | cat - body.csv > with_bom.csv

# strip a BOM
sed '1s/^\xEF\xBB\xBF//' with_bom.csv > no_bom.csv

# check the first three bytes
od -An -tx1 -N 3 with_bom.csv
```

```python
# prevent the BOM from sticking to the first column name as U+FEFF
import csv

with open('report.csv', encoding='utf-8-sig', newline='') as f:   # the sig is the point
    for row in csv.DictReader(f):
        print(row['이름'])        # with plain utf-8 this lookup returns None
```

- A BOM is a **UTF-8 marker**. Put it in front of cp949 and the file becomes valid in neither encoding
- Even after a correct UTF-8 decode, the BOM survives as `U+FEFF` **glued to the first column name**
- The symptom appears **only in the first column**. Columns two and three are fine, which hides the cause
- `U+FEFF` is not whitespace, so **trimming will not remove it**

## 8. Validity alone cannot determine the encoding

For **345** Hangul syllables, the cp949 byte sequence is also valid UTF-8. You can build text that decodes without error under either encoding.

```
징 -> cp949 C2 A1   the same bytes read as UTF-8 give U+00A1
징짖짙짚 -> C2 A1 C2 A2 C2 A3 C2 A4   (valid utf-8 · valid cp949 · both)
```

-> «try UTF-8, fall back to cp949» is a **heuristic**, not a decision procedure. Without a BOM the rest is probability. **Writing the encoding into the interchange spec is the only real fix.**

## 9. Who decides the encoding at each boundary

| Boundary | Who decides | Trap |
|---|---|---|
| File write | the writing program | on one machine Python wrote cp949 while Node wrote UTF-8 |
| File name | the operating system | names get **re-encoded** at the boundary; unlike contents, bytes are not preserved |
| Shell output | code page + program | code page and locale can disagree on the same machine |
| **Pipe** | **nobody** | **there is nowhere to declare it.** Both ends must agree in code |
| HTTP header | the server declares | the client **may ignore it**; take the body as bytes and decode yourself |
| CSV prefix | the writer | the BOM is the only signal |
| Conversion tool | the implementation | **the same name behaves differently** (below) |

## 10. Do not trust encoding names

| Name | Python | GNU libiconv | Verdict |
|---|---|---|---|
| `cp949` | extended syllables in 2 bytes | succeeds | **use this for Korean** |
| `euc-kr` | extended syllables in **8 bytes**, composition form | **refuses** | never trust the name alone |
| `johab` | 2 bytes, different scheme | succeeds | rarely used |
| `utf-8` | 3 bytes | succeeds | **make this your internal standard** |

Given the same label «EUC-KR», one tool refused and the other produced 8 bytes. Nothing is lost, but the byte count is **four times larger**, so it truncates wherever a column length limit exists. **Push a sample through the exact tool your pipeline uses.**

## 11. Shell and output encoding

| Setting | Changes | Does not change |
|---|---|---|
| `PYTHONIOENCODING` | standard output encoding only | **the default encoding used when opening files** |
| `PYTHONUTF8=1` | output plus the `open()` default | — |
| `LC_ALL` / `LANG` | how tools group bytes into characters (length, sorting) | file contents |
| `chcp` | the console code page | the meaning of bytes flowing through a pipe |

- If only the display is broken, use `PYTHONIOENCODING`; if file reads and writes are the problem, **this variable does nothing**
- The reliable approach is to stop relying on environment variables and **name the encoding in the code that opens the file**
- Choose an output encoding that cannot represent the text and you do not get mojibake — **the process dies.** A non-zero exit code with empty output means **the data is intact**
- Node has no such switch and always wrote UTF-8 -> piping it into Python is where the accident happens

## 12. Checklist

- [ ] On receiving a broken file, I opened **`od` before an editor**
- [ ] I counted `efbfbd` and **decided recoverability first**
- [ ] I repaired with **`latin-1`**, not `cp1252`
- [ ] I opened the suspect file **read-only** and never saved a misread state
- [ ] My conversion script **checks the exit code**
- [ ] Conversion has a **round-trip check** and leaves no artifact on failure
- [ ] I passed verification before deleting the original
- [ ] CSV reads specify a **BOM-stripping codec**
- [ ] The repository **never mixes two encodings** (search would only find half)
- [ ] User input is screened for **emoji and Simplified Chinese** before a cp949 export
- [ ] The interchange spec **states the encoding**
- [ ] File-name encoding and file-content encoding are treated as **separate problems**

## 13. Do not

- ❌ Reach for encoding settings on sight of mojibake — decide recoverability first
- ❌ Open a suspect file in an editor and **save it** — that converts kind 1 into kind 2
- ❌ Combine `//IGNORE` with **an unchecked exit code** — characters vanish and it reports success
- ❌ Conclude «no exception, therefore UTF-8» — it fails silently across those 345 syllables
- ❌ Match encoding names and **skip verifying tool behaviour**
- ❌ Review **only the head of a file** — truncation happens at the tail
- ❌ Spend time on a file already judged unrecoverable — request the original instead
