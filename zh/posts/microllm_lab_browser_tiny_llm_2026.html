这个页面包含什么 - 无需安装、账号和API的实验环境

MicroLLM Lab 是一个实验页面，在一个浏览器标签页里下载并运行超小型语言模型，并用同样的题目相互比较。GitHub README 的第一句话概括了它的性质：不需要 API 密钥，不需要 Python，也不需要安装 CUDA。模型权重按 origin 保存在浏览器的 IndexedDB 中，下载一次就不必重复下载，项目页面称任何输入和用户数据都不会离开设备。

这种组合受到关注，是因为运行 LLM 的门槛已经从「服务器或 GPU 工作站」降到了「一个浏览器标签页」。不过门槛降低的同时，模型也变小了。这里涉及的模型参数在1亿上下，4位量化后的文件在15~216MB左右。本文集中讨论两个问题。第一，浏览器要成为 LLM 运行环境，需要满足哪些条件。第二，在这个环境里资料自己写明的局限是什么。

同一主题中硬件一端的情况已在另一篇文章中讨论。在8美元的微控制器上运行小型模型的尝试，整理在ESP32-S3 端侧 LLM 文章中，本文不重复那条主线，只聚焦浏览器这一运行层。

项目资料写明的内容
所需条件无需 API 密钥、Python、CUDA 安装（README）
运行位置设备内部。输入和用户数据不会离开设备（项目页面）
权重存储浏览器 IndexedDB，按 origin 保存（README）
支持的浏览器Safari、Chrome、Edge（README）。GeekNews 摘要列出 Chrome 113+、Edge 113+、Brave，以及开启 WebGPU 的 Firefox
代码许可证Apache-2.0。权重保留上游许可证（README）

从表中读出的结构很简单，大小分成三组：20~100M 量级的两个 MiniMind2、在1亿2千万~1亿3千万量级相互比较的五个，以及3亿量级的一个 SmolLM2 360M。在同为1亿3千万级的范围内有多个作者和训练方式不同的模型，这正是该页面的实验价值所在。大小几乎相同的模型回答有何不同，可以在一个画面上看到。

README 还写明了作者。PetitGPT 来自 yangqi0，SmolLM 系列来自 Hugging Face Smol Models Research，L20-Edu 来自 AliceYin，MiniMind2 来自 jingyaogong，GPT-2 来自 OpenAI（Radford 等）。许可证只有 GPT-2 是 MIT，其余为 Apache-2.0。支持的架构写作两个分支：Llama 系（GQA 与 SwiGLU）和 GPT-2、nanoGPT 系（LayerNorm 与 GELU），属于这两个系列的小型模型都可以装到同一套解码器上。

三级回退 - 从 WebGPU 降到 WASM 和 JS 的顺序

项目页面用一句话说明了执行路径：优先使用 WebGPU，不行就回退到 WASM，再不行回退到 JS。三条路径性质各不相同。

  • WebGPU。让浏览器直接使用 GPU 计算能力的 API。以矩阵乘法为主的 LLM 推理与 GPU 的并行结构相匹配。它是资料给出的速度范围最高的路径。
  • WASM（CPU）。把编译成 WebAssembly 的代码放在 CPU 上运行。没有 GPU 或浏览器不支持 WebGPU 时也能工作。资料给出的速度约为 WebGPU 的十分之一。
  • JS 回退。上述两条路径都不可用时的最后手段。资料没有给出这条路径的速度。

这个顺序的含义在于，它是在「能运行的设备范围」与「运行的速度」之间做交换。有了回退，即使在 WebGPU 被封锁的环境里也至少能执行。但速度从个位数降到两位数 token 之后，同一个页面会像换了一个工具。每秒8~20个 token 与100个以上之间的体感差别，就像回答一行一行慢慢涌现与画面整屏滚动的差别。不过这种体感因分词方式和语言而异，只是感觉的举例，并不是资料给出的值。

README 另外写到，在 Safari 上同时支持 Metal 解码器和 WebGPU 解码器。资料没有写明并列两种解码器的原因。这里只转述 README 并列了两者这一事实。

如果把这个结构应用到自己的界面或服务中，要先决定的与其说是回退本身，不如说是是否告知用户当前走的是哪条路径。既然不同路径的速度差别这么大，即使是同一功能，期望值也应当不同。资料没有说明 MicroLLM Lab 是否这样做，下面整理的是三级结构带来的设计问题。

  • 路径显示。是否在画面上显示当前运行的是 WebGPU、WASM、JS 中的哪一个。
  • 最低速度标准。低于什么速度就关闭功能并改为提示文字。每秒个位数 token 时，交互式用途很困难。
  • 首次下载。下载15~216MB文件期间显示什么。由于保存在 IndexedDB 中，从第二次访问起这一开销就消失了。
  • 模型大小选择。是否按路径分配不同大小的模型。在 WASM 路径上，较小的模型可能更现实。

浏览器成为运行环境所需的条件

无需安装并不等于没有任何条件。从资料中可以读出五个条件。

  • HTTP 服务。README 写明模块和 worker 需要 origin，所以需要本地 HTTP 服务器。在文件管理器中双击 HTML 打开（file 地址）无法满足这一条件。仓库也提供 ZIP 下载，前提是把解压后的文件夹用静态服务器运行起来。
  • 浏览器版本。GeekNews 摘要列出 Chrome 113 及以上、Edge 113 及以上、Brave，以及开启 WebGPU 的 Firefox。README 则列出 Safari、Chrome、Edge。两份资料给出的浏览器列表不同，因此实际是否支持，要看页面在自己的环境中能否运行。
  • 存储空间。模型文件为15~216MB，按 origin 保存在 IndexedDB 中。用另一个 origin 打开同一文件，则需要重新下载。
  • 量化。模型以 Q4 形式分发。GeekNews 摘要称，把16位浮点权重压缩为4位，可使内存占用减少75%。从16位到4位，比特数变为四分之一，与减少75%在算术上吻合。但这种压缩是以质量换来的，资料中没有原始模型与 Q4 模型的精度差异。
  • 模型架构支持。只有 Llama 系和 GPT-2 系两个分支有解码器。其他结构的模型不能直接加载。

综合这五个条件，浏览器是「无需安装的环境」，而不是「资源无限的环境」。它在 origin 这一安全边界内使用 worker 和模块，并且只能通过浏览器允许的 API 访问 GPU。出于同样的原因，项目页面强调的隐私也是结构性的：推理在用户设备的浏览器内部完成，因此输入没有被发送到服务器的路径。不过，该页面从哪里下载模型文件，统计和证书分享功能是否与外部通信，资料中没有写明。

速度 - 资料给出的范围与测量条件

速度数值分散在三个出处中。如果不把出处和条件分开，很容易把不同条件下的测量误读成同一条线。下表就是这种区分。

路径或条件资料给出的速度出处与条件
WebGPU每秒100~300+个 tokenGeekNews 摘要。设备和模型条件摘要中没有
WASM（CPU）每秒8~20个 tokenGeekNews 摘要。描述为与 WebGPU 相差10~20倍
JS 回退—未给出数值
PetitGPT research-v187ms，每秒115个 tokenREADME。Apple M4、Safari、Metal Q4、贪心解码、Say hello 提示词
SmolLM2 135M Instruct227ms，每秒66个 tokenREADME。条件同上
首个 token 延迟不到10ms的说法项目页面对自动补全用途的介绍。未写明条件

有两点值得注意。第一，README 的 M4 测量值在同一大小区间的两个模型上分成每秒115和66。从这张表能读出的全部就是：即使参数量相近，速度也会因结构和嵌入大小等细节而不同。第二，GeekNews 摘要所说 WebGPU 每秒100~300+ 与 README 的 M4 测量并不矛盾，但摘要没有说明是在哪台设备和哪个模型上取得的值。所以把这个范围作为「资料给出的范围」引用，而不要当作自己环境的预期，才是稳妥的做法。

项目页面说明，持续速度是用「连续生成256个 token」来测量的。短回答的首个 token 延迟和长生成的吞吐量是不同的值。在自动补全这类短回答中，首个 token 延迟决定体感；在摘要这类长回答中，持续速度决定体感。

阅读这张表只需遵守一条规则：只比较同一行内的数值，不要把不同出处的数值拼接成一条趋势。设备、浏览器、模型、提示词只要有一项不同，就是不同的测量。尤其是从首个 token 延迟推算持续速度，或反过来推算，资料中没有依据。

基准测试、证书与自定义 JS 评测的构成

MicroLLM Lab 不只是运行工具，还附带测量工具。资料给出的构成如下。

  • 客观式基准测试。项目页面的 Benchmarks 标签使用以正则表达式或精确 token 匹配来判定的客观检查。由于判定标准是机械的，相同输入容易得到相同结果。
  • 测试数量。GeekNews 摘要称自动运行21个测试。README 区分了「原有测试」14个和「扩展测试」20个，并写明 SmolLM2 135M Instruct 在扩展的20个中答对14个，PetitGPT 在原有的14个中答对10个。21这个值对应 README 中的哪个数字，仅凭资料无法得知。
  • 测试套件耗时。README 写明在 M4 的 Safari 上，PetitGPT 约1.5秒，SmolLM2 约6秒。
  • 256 token 持续速度。项目页面用连续生成256个 token 来测量持续速度（Highest Sustained Speed）。
  • 性能证书。可以生成包含设备硬件规格以及峰值和持续速度的证书，下载或分享到 X 和 LinkedIn。GeekNews 摘要称它以 PNG 形式生成。
  • 自定义 JS 基准测试。用户用 JavaScript 写入基准测试后，按项目页面的说明，会在该 origin 中通过 eval() 运行，并对解码出的模型输出进行检查。

解码仅为贪心这一点，与基准测试的设计相呼应。贪心在每一步都选择概率最高的 token，所以相同输入和相同模型下结果容易复现。如果使用采样，每次运行结果都会变化，正确率就难以比较。同样的原因也使它不适合创造性生成或需要多样回答的用途。

自定义 JS 评测有一点需要注意。eval() 会把输入字符串当作代码执行，因此用户写的代码会在该工具的 origin 内原样运行。只要是在自己的设备上运行自己的代码就没有问题，但把别人给的基准脚本粘贴进去，性质就不同了。本文只转述资料写明的行为，页面如何隔离这种执行，资料中没有。

模型（README 写法）评测条件报告的正确数报告的耗时
PetitGPT research-v1原有测试14个10/14套件约1.5秒
SmolLM2 135M Instruct扩展测试20个14/20套件约6秒

上表的两行并不在同一条件下，所以不能排出高低。测试集的规模不同，模型也不同。README 把「原有」和「扩展」分开写这件事本身，就意味着测试集经过修订，也说明只应比较后一个集合中的值。

局限 - 上下文、解码、幻觉，以及适用的场合

局限是 README 自己写明的：这些模型会产生幻觉，不能用于重要问题，上下文限制为2,048 token，解码只支持贪心。

  • 幻觉。README 写道这些模型会产生幻觉。GeekNews 摘要转述的 Hacker News 反应中，有 SmolLM2 360M 把人口一会儿答成1亿5,300万、一会儿答成3亿2,500万而自相矛盾的例子，以及 GPT-2 124M 对 2+2 的问题给出答非所问的例子。这两者都是特定用户的测试报告，并非概括性统计。
  • 2,048 token 上下文。把整篇长文档直接放进去的工作超出了该工具的范围。一次处理的输入与输出之和必须在这个范围内。
  • 贪心解码。没有温度或采样调节，无法调整输出的多样性。相同的问题得到相同的答案。
  • 界面反馈。GeekNews 摘要转述的反应中，还有关于字号和信息密度等画面改进的请求。

那么这类模型适合用在哪里？资料直接给出的用途，只有项目页面介绍的自动补全这类即时的短回答。以下是从上述局限中按逻辑推出的解释，并不是资料推荐的用途。对于不要求准确事实、输出很短、出错时人能立刻筛掉的工作，这样的用法是成立的。算术和事实核查这种答案唯一确定的工作，上面的案例已经显示了失败。分类或过滤这类范围狭窄的判断工作可以作为候选，但该工具的测试结果并不能证明这一点。若要这样使用，必须用自己的数据直接测量正确率，而该页面的自定义 JS 基准测试恰好就是做这种测量的地方。

归根结底，这个页面展示的不是「小型模型的实力」，而是「浏览器运行推理的条件已经具备到了什么程度」。有 WebGPU 时可达每秒数百 token，没有时降到个位数到两位数 token 的阶梯，通过回退结构敞开着，在这个阶梯之上，1亿参数上下的模型无需安装即可运行。至于这样的模型值不值得托付任务，则是另一回事，资料自己也是这么写的。

未能确认的内容

  • 模型数量和测试数量的确切值。GeekNews 摘要（7个模型、21个测试）与 README（表格8行、原有14个加扩展20个）不一致，仅凭资料无法判断哪一个更新。
  • WebGPU 每秒100~300+ token、WASM 每秒8~20 token 是在哪台设备和哪个模型上得到的值。摘要没有写明条件。
  • 较旧的 GPU 上速度慢多少倍。所查资料中没有这一数值。
  • 适合分类、过滤这类边缘任务的评价。资料并未给出，本文仅在解释范围内处理。
  • JS 回退路径的实际速度和运行条件。项目页面只写了顺序。
  • Q4 量化相对原始模型会降低多少精度，自定义 JS 执行如何隔离，分享证书时是否有外部通信。资料中没有。
  • 项目页面正文中的模型清单。页面通过加载模型卡片来展示，正文文本中没有出现清单。
  • 本文没有运行该工具来复现速度。所有数值都是资料给出的值。
