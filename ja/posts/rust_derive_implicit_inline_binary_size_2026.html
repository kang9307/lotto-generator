発端 — #[derive(...)]が暗黙に付与する#[inline]の発見

RustでDebugやDisplay、Cloneといった中核的なトレイトを実装する最も一般的な方法は#[derive(...)]である。yossarianは2026年10月3日付のTIL記事で、Rustが現在この派生コードの一部として#[inline]も出力していることを最近まで知らなかったと書いている。保証された動作ではなさそうだが、referenceの例が示唆しており、マクロを展開すれば自分で確認できるという。実際、Rust Referenceのderiveの章で#[automatically_derived]を説明する例にも、Cloneの実装の上に#[inline]が付いている。

用語の確認として、インライン化とは呼び出しを呼び出された関数本体のコピーに置き換えることであり、呼び出しのコストは消えるが、呼び出し箇所の数だけ本体が複製される。元記事はこの動作を問題視する文章ではない。むしろほとんどの場合は望ましい動作だと評価している。#[inline]は単なるヒントにすぎず、派生されたDebugやCloneの実装は中身が自明なことが多いのでインライン化の恩恵を受けるというのである。ただし常にそうとは限らないという反例として、フィールドが多く何層にも包まれたエラー階層を挙げる。そうした型のDebug実装がログ出力の呼び出しごとにインライン展開されるとコードが増える、というのが記事の要点である。

この記事は資料を三つの層に分けて読む。元記事が直接述べたこと（展開結果とuvで約160KBを削減した経験）、PRのページに残る記録（PR #117727と#118031。元記事にはこの番号は出てこない）、現在のrustcソースから直接読み取った事実である。解釈は層が出会うところにだけ付け、誰の発言なのかは文ごとに明記する。

マクロ展開で確認する自動生成コードの実態

確認の方法は元記事がすでに示している。マクロを展開してみることである。元記事はもっとも単純な構造体から始める。

#[derive(Debug)]
                    struct Widgets {
                        foo: u32,
                        bar: usize,
                    }

元記事は、これをPlaygroundで展開すると次の実装が得られると示している。

struct Widgets {
                        foo: u32,
                        bar: usize,
                    }
                    #[automatically_derived]
                    impl ::core::fmt::Debug for Widgets {
                        #[inline]
                        fn fmt(&self, f: &mut ::core::fmt::Formatter) -> ::core::fmt::Result {
                            ::core::fmt::Formatter::debug_struct_field2_finish(
                                f,
                                "Widgets",
                                "foo",
                                &self.foo,
                                "bar",
                                &&self.bar,
                            )
                        }
                    }

注目すべきはfmtの直上にある#[inline]である。開発者が書いていないのにderiveが付けた。本体全体がdebug_struct_field2_finishの呼び出し一つであり、マクロ自身は何も整形しない。型名とフィールド名、フィールド値への参照をFormatterのヘルパーメソッドに渡すだけで、実際の整形はそのヘルパーが行う。参照が一段余分に付くのは最後のフィールドだけである（&&self.bar）。rustcソースのコメントによると、サイズ不定（unsized）の型は参照をもう一段必要とし、そうした型が置けるのは最後のフィールドだけだからである。

#[inline]が正確に何をするのかは、資料によって説明が少しずつ異なる。元記事はこれを単なるヒント（just a hint）と呼ぶ。Lobste.rsの議論でtsionは、ヒントだけではないと反論する。ジェネリック関数は常にクレート境界を越えてインライン化できるが、ジェネリックでない関数は既定ではできず、#[inline]がそれを可能にするというのである。PR #117727のコメントでsaethlinも似た説明をしている。この属性はLLVMにinlinehintを付けるだけで最終的なインライン化はLLVMの裁量だが、それと同時に関数がMIRインライン化の候補になり、遅延してlowering（低レベル表現への変換）され、場合によっては複数回loweringされるという。

範囲についても触れておく。Rust Referenceは組み込みderiveとしてClone・Copy・Debug・Default・Eq・Hash・Ord・PartialEq・PartialOrdの九つを挙げ、それらが生成する実装にはautomatically_derived属性が付くと述べている。ごく小さな関数にコンパイラが自動で#[inline]を付けるのかについては、Lobste.rsでralfjが付くと答えている。本当に小さな関数には自動的に付くという説明である。

深くネストしたエラー型とインライン膨張の構造

フィールドが二つの構造体のDebugは本体が呼び出し一つだけなので、インライン化しても負担はほとんどない。元記事は、そうした場合だけではないとして、次のようなエラー階層を想像してみるよう促す。

  • ErrorA: Stringフィールドを7つ（lots, of, chunky, fields, within, this, type）持つ構造体。
  • ErrorB: ErrorAをinnerフィールドとして持つ構造体。
  • ErrorC: ErrorBをinnerフィールドとして持つ構造体。
  • Errors: A(ErrorA)、B(ErrorB)、C(ErrorC)の三つのバリアントを持つ列挙型。
  • Default: 元記事の展開結果にはErrorAに対するdefaultの実装だけが現れ、これにも#[inline]が付いている。入力コードのderive行にはDebugしか書かれていないため、元記事の中で入力と出力が食い違っている。

元記事が示す展開結果では、ErrorAのfmtはフィールド名の文字列スライスの配列（names）と&dyn Debugの値の配列（values）を作ってからdebug_struct_fields_finishを呼ぶ。ErrorBとErrorCはdebug_struct_field1_finishを一回呼ぶだけで、Errorsはmatchで分岐してバリアントごとにdebug_tuple_field1_finishを呼ぶ。フィールド7個の型だけが配列を使う理由はrustcのソースにある。deriving/debug.rsのCUTOFF定数は5で、フィールドが5個以下なら配列を作らずにフィールド数に応じた専用メソッド（debug_struct_field2_finishなど）を呼び、5個を超えると配列を作る方式になる。つまり5フィールドという境界はderiveの書き方の性質であってオプティマイザの挙動ではなく、インライン化される本体が単一の転送呼び出しなのか、二つの配列を組み立ててから呼び出す本体なのかを分けている。

元記事の懸念は、このコードがErrorsのDebugが呼ばれる箇所ごとにインライン展開されうる点である。元記事は、そうした呼び出しが例えばdebugログやtraceログで繰り返し起こりうると書いている。脚注は、この階層は大幅に単純化したものであり、実際のRustアプリケーションにはフィールド数が少なくない深くネストしたエラー列挙型がよくあると付け加える。元記事はこのインライン化でアセンブリが何行増えるかは示していないので、この記事もその行数を推定しない。

uvの事例に見る約160KB削減と測定の前提条件

元記事の中心となる数値は一文である。これだけのコードはRustバイナリ全体のサイズの中で無視できない割合になりうる。uvではrustcに特定のDebug実装をインライン化させないようにしたところ、バイナリが約160KB縮小したという。原文の表現はa given Debug implementationであり、この160KBはDebug実装全般ではなく指定した実装についての値である。

解決方法は脚注にある。チームはderive(Debug)とまったく同じように動作しつつ#[inline(never)]を付ける独自のproc-macro、つまりアイテムのトークンを受け取って新しいコードを返すコンパイラプラグインを追加した。なお160KBは分母のない絶対値であり、元記事はuvのバイナリ全体の大きさを書いていないので、割合には換算できない。derive自体も同じ仕組みで実装されている。脚注2が対処法を述べている唯一の箇所なので、マクロがどこまで広く適用されたのかは分からない。元記事が驚いたと書いている点は二つで、サイズのコストがすぐに積み上がることと、rustcが（見たところ）インライン化のサイズや回数に上限を設けていなかったことである。筆者は続けて、これは多くのプログラムでは正しい判断だろうと考えていると付け加える。コンパイラの既定値を批判する文章ではなく、一つの事例の報告である。

コンパイラの観点から見たトレードオフ — 2023年のPRとベンチマーク

derived Debugに#[inline]を入れた変更は、rust-lang/rustのPR #117727（タイトルは「Emit #[inline] on derive(Debug)」）である。このPRはsaethlinが2023年11月8日に作成し、翌9日にマージされた。元記事はこのPRに触れていないので、以下はすべてPRのページに基づく。PRの本文は短い。PR #116583の作業中に、cross_crate_inlinableクエリが派生されたDebug実装の多くを「呼び出し一つ程度にすぎない（little more than a call）MIR本体」と識別することに気づき、それなら#[inline]の良い候補になりうると考えてこの変更だけを実装した。build timesが目に見えて改善するように見える、と書かれている。以下の比較数値はrust-timerボットがPRのtryビルドをrustc-perfで走らせ、親コミットと比較したものである。ボットはinstruction countを全体判定に使った信頼性の高い指標とし、max RSS・cycles・バイナリサイズは判定に使っていない信頼性の低い指標だと明記している。

  • perf結果: 最初のtryビルドのinstruction countでは、primaryベンチマーク111件のうち107件が改善（平均-2.4%）、4件が回帰（平均+0.5%）だった。ボットの総評は回帰と改善が混在というものである。バイナリサイズ指標はprimaryで改善113件（平均-2.7%）、回帰26件（平均+0.9%）である。instruction countのsecondaryでは改善163件（平均-3.4%）、回帰4件（平均+2.7%）だった。ブートストラップは663.159秒から673.479秒へと1.56%遅くなり、成果物サイズは308.75MiBから308.99MiBへと0.08%増えた。
  • レビュアーnnethercoteの反応: fmtにinlineを付けていなかったのは意図的で、ホットなコードではないのでインライン化されるべきではないという考えだったと述べる。しかしperf結果には反論できないとして「faster and smaller binaries」と書き、ブートストラップが10秒遅くなりコンパイラの成果物がわずかに大きくなったことは不思議だと付け加えている。
  • 原因の仮説: Noratriebは、高速化の理由は単純だろうと推測する。#[inline]が付いた関数は下流でコードが生成され、デッドコードなら全く生成されず、Debug実装はデッドコードであることが多いというのである。hello worldベンチマークでリンクが大きく速くなったことを根拠に挙げる。これはPR本文ではなくコメントにある仮説である。
  • 別の仮説: scottmcmはdebug_tuple_field4_finishのようなヘルパー関数への移行の幸運な結果だと見る。ヘルパーは#[inline]ではないので、インライン化されるfmtはポインタ投影とvtableポインタのコピーのあと呼び出し一つを行うだけの薄い関数だという仮説である。コード生成をしないcheckビルドがなぜそれほど速くなるのかは不可解だとも書いている。
  • マージ後: マージ後のperf実行でも、primaryのinstruction回帰5件（平均3.1%、最大13.7%）と改善110件（平均-2.3%）が混在していた。saethlinは大きな回帰はコレクターの遅延が原因らしいと見て、perf-regression-triagedラベルを付けた。

フィールド数で区別しようという提案は、マージ後のPR #117727のコメントで出た。RalfJungが、フィールド5個以下の構造体にだけ（列挙型とより大きな構造体は除いて）属性を付けてはどうかと尋ね、saethlinが11月18日にPR #118031として試した。このPRの実際のタイトルは「Try not applying #[inline] to big structs」で、状態はマージされないままクローズである。変更は、フィールドが5個を超える構造体からだけ#[inline]を外し、列挙型はそのままにするものだった。結果は全面的な回帰だった。instruction countのprimaryで回帰54件（平均+1.5%）、改善は0件である。同じ実行でcyclesはprimary回帰33件（平均+2.3%）で改善0件、バイナリサイズはprimary回帰66件（平均+2.4%）に対して改善4件（-0.2%）、ブートストラップ時間はほぼ同じ（-0.19%）だった。saethlinは「huge regression」と答え、デッドコードの効果とMIR最適化の効果の両方が重要らしいとまとめている。したがって5フィールド以下という基準は、マージされた方針ではなく、試してクローズした実験の閾値である。

二つのPRを並べて見ると分かることがある。どちらも同じベンチマーク群で判定され、どちらもuvのような形のバイナリは測っていない。PR #117727のバイナリサイズ指標もベンチマークによって改善と回帰が混ざっているので、ベンチマーク群全体の改善と特定のプログラム一つでの160KB削減は矛盾しない。

同じ現象についてLobste.rsでも仮説が出た。ralfjは、多くのDebug実装が一度も呼ばれず、#[inline]を付けるとそもそもコード生成を避けられることが理由の一部だろうと推測する。Noratriebの仮説と同じ方向である。evmarは、呼ばれない関数はどのみち最終バイナリから外れるのではないか、コンパイル時間には影響しても実行時間にはどうつながるのかと尋ねる。yshuiは、これはRustのproc macroが実際の型ではなくトークンの上で動作することから来る限界だと見る。型情報があれば、ネストの深さを見て深すぎるときは#[inline]を付けないでおけたはずだという話である。いずれも仮説か質問である。

deriveごとの挙動とバイナリサイズへの影響比較

現在のrustcソース（compiler/rustc_builtin_macros/src/deriving/）を直接開き、各組み込みderiveが生成するメソッドに#[inline]が付くかどうかを確認した。確認したのはソース上の属性の有無であり、このインライン化がderiveごとにバイナリサイズへどれだけ影響したかは、元記事にもPRにも示されていない。

表で目を引くのはEqである。ソースのコメントは、このメソッドは一度も呼ばれないので#[inline]の目的はコード生成を避けることだと説明しており、同じ属性でも別のderiveでは性格が違うことが分かる。またLobste.rsでkornelは、OrdやEq、あるいはCloneにインラインが付くのは予想できるがDebugに付くのは意外だと書き、自分はfmt実装に#[cold]を付けていると述べた。同じ議論でralfjは、インラインの既定値の選択はコードサイズ・コンパイル時間・実行時間のバランスなので難しいと説明している。元記事の筆者も同じ趣旨で、Rustが選べる完璧な既定値やヒューリスティクスはないと考えていると答えた。

元記事と議論が示す対処

元記事が直接示した対処は一つで、残りは同じ話題の議論から出た意見である。以下はすべて誰の発言かを付けて記す。一般的なサイズ削減のコツは元記事にもPRにもなかったので入れていない。

  • 展開して見る: 元記事が用いた方法である。Playgroundやマクロ展開ツールで疑わしい型のderiveを展開し、#[inline]が付いた本体がどれほど長いかを見る。フィールドが6個以上だと配列を作る形になることは、上のソース確認で説明できる。
  • 独自のproc-macro: uvが取った対処である。derive(Debug)のように動作しつつ#[inline(never)]を付けるマクロを自作して適用する。元記事はマクロの名前や公開の有無を書いていない。
  • #[cold]の使用: Lobste.rsのkornelが自分のfmt実装に付けていると書いた方法である。deriveが生成するコードには手で付けられないので、手書き実装側の話になる。
  • コンパイラ側への報告: Lobste.rsでralfjは、これはrust-lang/rustに上げる価値のあるバグ報告だと述べた。インラインの既定値は過去にも変えたことがあり再び変えられる、ヒューリスティクスが悪いという報告が複数集まれば均衡を調整する根拠になるという趣旨である。元記事の筆者は今週中に報告すると答えた。
  • クレートへの切り出し: Lobste.rsのschneemsは、この選択をクレートに押し出せると考える。cold用とinline用のDebug deriveを別に用意するか、コンテナ属性で選ばせる構想である。まだ実装されておらず一人の提案である。
  • 自分のビルドで直接比較: 160KBはuvの値であり、元記事はターゲットや設定を書いていない。同じ効果が自分のバイナリにもあるかは、疑わしい型一つについて前後のサイズを自分で測るしかない。

確認できなかったこと

  • 160KBの削減を測った時点のuvのバージョン・コミット・ターゲットトリプル・ビルドプロファイル（LTO、strip）。元記事には書かれていない。
  • uvが作った独自proc-macroの名前とソース、そしてどの型に適用したか。
  • LLVMのインライナが大きなDebug実装に上限をかけなかった理由。元記事もrustcが（見たところ）上限を設けなかったとしか書いていない。
  • PR #118031のperf回帰がどの個別ベンチマークで大きかったかの詳細（要約表以外）。
  • Debug以外のDefaultやPartialEqなどの暗黙のインライン化が、実際の大規模プロジェクトのバイナリサイズに与えた影響の実測。
