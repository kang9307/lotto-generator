我记得在哪儿见过 - 重新找到自己看过的东西为什么不是搜索引擎问题

问题不在排序而在召回。要保存什么才找得到，以及那份保存为什么会造出风险

2026年9月2日 IT/技术

确实读过。几周前，在某篇文章的中间。站名不记得了，标题也没留下，留下的只是那一段大概说了什么。打开浏览器历史，一串地址涌出来，可没有一条是要找的那个。

这次失败不是因为不会搜，而是因为要搜的东西根本没被保存下来。历史里只有标题和地址，留在记忆里的却是正文。这个错位几乎就是个人记录检索这个问题的全部，而它并不是网页搜索的缩小版，是性质不同的问题。

本文不是任何产品的使用说明或安装指引，也不是让谁去用或不要用某个工具的建议。讨论范围只限于本人处理自己的记录，收集他人记录的方法以任何形式都不涉及。文中引用的文档与仓库数据的核对时点为 2026 年 9 月初。

缘起 - 个人搜索引擎这个门类

2026 年 9 月初，韩国的开发者社区上介绍了一个开源项目。要点是把访问过的网页和本地文件的正文全部建成索引，之后可以在里面搜。有意思的不是这个工具做得多完整，而是为什么这个门类偏偏在现在单独出现。浏览器早就有历史记录，操作系统早就有文件检索，笔记应用更是满地都是。可每年还是会在同一个位置冒出新工具。

本文要看的是这个空位的形状。先看这个问题在哪里与网页搜索分岔，把隐私问题放到前面，然后在此之上谈保存、检索与成本。这样排序的理由很简单。先定技术选型再往上贴隐私，多半贴不住。

  • 讨论的 — 为什么这不是排序问题，要保存什么才找得到，那份保存造出的风险是什么性质，用久了会来的东西
  • 不讨论的 — 安装与配置，产品对比与推荐，以及收集他人记录的一切方法
  • 引用原则 — 仓库数据与产品文档都标注时点，未能核实的数字不写

这和公开网页搜索是两个问题

公开网页搜索是从数十亿份文档里挑出前十条。个人记录检索则是在自己看过的几千到几万条里不漏掉那一条。排序的分量在这里被翻了过来。网页搜索中第一名和第四十名的差别是决定性的，可在自己的记录里第四十名也无妨，用眼睛扫一遍就行。但要是压根不在列表上，那就到此为止了。这边重要的不是精确率而是召回率。

查询的性质也不同。网页搜索是我想了解这个，个人检索是我想再看一眼那个。后者有一个特别的性质，使用者已经知道答案是存在的。所以网页搜索失败了，耸耸肩当作没有就完了；个人检索失败了，人就停在明明有却找不到的状态里，被拖住很久。

可用来排序的材料也没有。公开网页靠链接、点击和引用来称文档的分量，自己的记录里没有这些信号。取而代之的是另一类信号。什么时候看的，停留了多久，从哪里跳过来的，有没有再打开过。

项目公开网页搜索检索自己的记录
对象规模数十亿份文档，建索引本身就是基础设施问题几千到几万，一台笔记本装得下
核心指标精确率，前十条就是全部召回率，只要在列表上就能用眼睛找到
查询的含义我想了解这个我想再看那个，而且知道它存在
排序材料链接、点击、引用等外部信号访问时刻、停留、来源路径、回访
失败的样子当作没有，就此打住停在明明有却找不到的状态
数据的性质公开文档，没有泄露这个概念全部关于自己，一个文件就是一份画像
  • 规模小意味着技术上容易，不意味着可以轻看。难点只是从检索算法挪到了数据管理
  • 优先召回，结果就会变得杂乱。把这份杂乱做到可以忍受，才是这个领域真正的界面课题
  • 时间成了很强的一个轴。网页搜索里日期筛选是附加功能，这里常常是第一排序依据
  • 最后一行规定了其余的一切。这份索引不是公开文档的集合，而是关于自己的记录

这个问题的中心是隐私

把访问过的页面连正文一起建索引，不是打开一个功能，而是把原先散落的东西汇到一处。在那之前这些信息是分开的，有的在浏览器里，有的在各站点的服务器上，有的哪儿都没留下。风险有多大，只要设想那一个文件流到外面会漏出什么，立刻就有分寸。

里面有什么，法律已经列成了清单。韩国个人信息保护法第23条与其施行令第18条把思想与信仰，加入或退出工会、政党，政治见解，健康，性生活方面的信息，遗传信息，犯罪经历资料，为识别特定个人而生成的身体、生理、行为特征信息，以及种族与民族信息单列为敏感信息。普通的一个月浏览记录，和这份清单有一半以上是重叠的。

于是设计上的问题分成三条。放在哪里，排除什么，怎么删除。第一条支配其余两条。放在本地，风险的最大尺度被绑在一台设备上，而那条边界是自己知道的边界。一旦出去，那条边界就延伸到服务商的寿命、政策变更、法律管辖和安全事故，而且收不回来。送出去的东西，除了相信对方说已经删了，没有别的办法核实。

这类数据要求什么级别的对待，看大公司解同一个问题时走到了哪一步就知道。微软写在 Recall 文档里的条件就是那条基线。快照只保存在设备上，不会发送给微软；要打开必须用 Windows Hello 确认身份。快照及其附带的向量数据库始终加密，密钥由 TPM 保护。功能本身也是需要用户同意的选择加入，管理员不能替用户打开。要学的不是这个产品，而是要求的水位。

排除规则也在同一份文档里。敏感信息过滤默认开启，受支持浏览器的隐私浏览默认被滤掉，带 DRM 的内容不保存。可同一份文档也写下了限度。即便是被过滤的站点，仍可能以嵌入内容、浏览器历史、非前台的已打开标签页的形式留下一部分。排除规则降低的是概率，造不出保证。

  • 索引文件在哪里，被什么锁着。不需要认证就能打开的索引，实质上就是一个明文文件
  • 默认排除清单里有什么。隐私浏览、金融与医疗域名、公司内部系统是否一开始就在外面，决定了它是什么性质的东西
  • 删除是不是真的全删了。正文删了向量还在，或者索引清空了快照文件还留着，都很常见
  • 往外走的通道是默认还是选择。如果把嵌入发到外部 API 是默认设置，那它就是另一类产品
  • 有没有考虑设备共用的情形。共用的笔记本，或者一个账号多人使用时，隔离是怎么做的

浏览器历史为什么不够用

浏览器留下什么，扩展 API 文档写得很清楚。Chrome 的 history API 里，HistoryItem 是 id、url、title、lastVisitTime、visitCount、typedCount 六个字段。表示单次访问的 VisitItem 有 id、visitId、referringVisitId、visitTime、transition、isLocal。Firefox 那边的定义同样是这六个。

这份清单里没有放正文的位置。没有的东西检索不了。所以浏览器历史只在记得标题时管用，而人实际记住的多半是正文。标题在读的那一瞬间就过去了，正文会留下来。

浏览器历史里留下的东西
  HistoryItem : id · url · title · lastVisitTime · visitCount · typedCount
  VisitItem   : id · visitId · referringVisitId · visitTime · transition · isLocal

记忆抛出的问题，以及它们的下场
  「说加载延迟是缓存造成的那一段」    -> 没有正文字段，检索不了
  「上个月某个晚上读的那份文档」      -> 用 lastVisitTime 能收窄，候选仍有几百条
  「从某篇文章顺着链接过去的页面」    -> 可以用 referringVisitId 追踪
  「标题里带调度器三个字的那篇」      -> 用 title 能检索到

范围上也有限制。Chrome 帮助写明历史只覆盖最近 90 天，内部页面、无痕模式下看过的页面以及用户自己删掉的页面都不保存。可让人想再找一遍的文档，多半比 90 天更早。书签则是另一种不够。书签要的不是容量而是判断，而后来真正会回头去找的页面，恰恰是当时看着不重要的那些。判断的时点和需要的时点错开了，所以书签在结构上就会漏。

  • 浏览器历史是为帮助跳转而设计的数据结构，目的是地址栏补全，不是回想
  • 所以没有正文不是缺陷而是设计。保存正文会让存储变大、风险出现，没有理由默认去付这份代价
  • 书签提前要求判断，历史不要求判断却丢掉正文。两者之间是空的
  • 记忆抓住的线索不只有句子。屏幕上的位置、旁边的插图、那天正在做的事都是线索，只有文本是抓不住这一边的

要保存什么才找得到

保存的项目多了，能回答的问题也就多了。只是每一项回答的问题不同，付出的代价也不同。在得出全都存下来这个结论之前，先把这份对应关系摊开更好。

保存的项目它回答的问题付出的代价
地址与标题那个站叫什么来着几乎没有，浏览器已经在做了
正文文本有那句话的页面是哪一个索引容量，而且敏感的正文会整份进来
访问时刻与顺序上周二晚上在看的那个小，只是作息规律会原样显露
来源路径是从哪篇文章顺着链接过去的小，兴趣的连接关系会变成画像
停留时长与滚动位置只想看读到最后的那些小，阅读习惯会留成记录
屏幕快照当时屏幕上原封不动的样子最大，图像、版式、登录状态都会留下

这张表要看的不是清单而是坡度。越往上越便宜、越无害、越不容易找到；越往下越容易找到、越贵、越危险。找得到和安全，是同一根轴的两端。这不是靠好的实现能消掉的冲突，而是选择站在哪里的问题，而不知道自己站在这根轴的哪一点就开着是最糟的。

  • 快照是性质不同的一项。文本在结果里只露出一个片段，快照则一打开就全都看见了
  • 停留时长与滚动位置几乎不占容量，却能大幅改善排序。性价比最好的项目大多在这里
  • 正文保存效果最大，风险也最大。所以很多设计只为这一项单独设置按域名的排除规则

记得准确的词时，和只记得意思时

保存之后是取出的方式。通常被叫作关键词检索和语义检索的这两条岔路，准确地说，区别在于记忆的形状决定了由哪一边来回答。

全文检索把文档切成词元建倒排索引，对拼写固定的东西很强，比如错误消息、产品名、函数名。表达力也比想象中宽，按 SQLite 的 FTS5 文档来看，短语、前缀、邻近检索加上指定列和布尔组合，全都在查询语法里。

全文检索能表达的形式 (以 SQLite FTS5 语法为准)

  writeback cache               两个词都出现的文档
  「write-back cache」           就是这个顺序的短语
  writeb*                       以此开头的词
  NEAR(cache latency, 10)       两个词在 10 个词元之内同现的地方
  title : scheduler             只在标题列里的
  cache NOT redis               前者有而后者没有的文档

语义检索走另一条路，把文档片段和查询各自变成向量，再挑近的。一个词都不重合，只要意思相近也能命中，所以它回答的是只剩下意思的记忆。不过有两个约束。一是输入长度。广泛使用的小型句子嵌入模型的公开模型卡写明，输出为 384 维，参数为 2,270 万个，而且默认情况下超过 256 个 word piece 的输入会被截断。所以长页面必须切开，而切法直接决定了检索质量。要是记得的那句话偏偏跨在两个片段的交界处，拿它当线索也出不来。

二是失败的样子。语义检索说不出没有，因为它总会返回最接近的那几条。全文检索没有就是 0 条，而 0 条本身就是信息。牛头不对马嘴的五条给不了这样的信号。所以实务上会收敛到两者并用。向量检索该建在什么之上，在向量检索该建在什么之上那边另外谈过。

记忆留下的形状由哪一边回答失败时的样子
准确的词或错误文本全文检索拼写稍有出入就变成 0 条
只剩意思，措辞消失了语义检索出来五条像而不是的
大致的时期时间筛选记错时期就落到范围之外
从哪里过来的来源路径追踪中间的经停点没记录就断了
只剩下画面的印象翻看快照量一多，翻看本身就不可能了
  • 两种一起跑，召回上去了，结果也更杂乱。所以混合结果的规则才决定实际质量
  • 语义检索头几天印象好，后来会让人失望。在明明知道准确的词的情况下拿到牛头不对马嘴的结果，信任崩得很快
  • 只放全文检索能长久稳住，可偏偏对「我记得在哪儿见过」这一类查询会一直失败
  • 只能选一个的话，全文检索优先。它便宜，会给出 0 条这个信号，而且结果解释得清

在本地跑要付的价钱

常驻运行的索引，负担分成存储和计算两头。存储这边有可以拿来估量的公开测量值。SQLite FTS5 文档里有一项对磁盘上 1,636 MiB 邮件集合建索引的试验，仅 FTS 索引在 detail=full 下为 743 MiB，detail=column 下为 340 MiB，detail=none 下为 134 MiB。同一份材料，记录什么会让体积相差五倍以上。丢掉位置信息会变小，但短语检索和邻近检索也一起没了。

在这之上还要加一份原文副本。FTS5 在默认设置下会把原始行的副本一并保存。也有只留索引的方式，但那样就没法在结果里展示正文片段。结果片段几乎是必需的，所以实际上正文和索引两样都会握在手里。

嵌入在存储上的负担反倒不大。一个 384 维的浮点向量按简单计算是 1,536 字节，一万个页面每页切五段，算下来也就几十兆字节。问题在计算。全文索引是把文档过一遍，嵌入却是每个片段跑一次模型，在浏览过程中实时做，风扇转起来是能听出来的。所以实际设计都会往后推。保存立刻做，全文索引很快做，嵌入等接上电源再成批做。副作用是刚看过的页面在语义检索里还没有。

屏幕快照方式的价钱要高一档。微软对 Recall 提出的最低配置显示了这个量级，符合 Secured-core 标准的 Copilot+ PC、40 TOPS 的 NPU、16 GB 内存、8 个逻辑处理器、256 GB 存储。要开启至少需要 50 GB 空闲空间，空闲降到 25 GB 以下保存就会自动停止。配额与设备容量挂钩，256 GB 的设备给 25 GB，512 GB 给 75 GB，1 TB 以上给 150 GB，到上限后从最旧的开始删。

  • 索引的大小，受决定记录什么的影响比受文档数量的影响更大。留不留位置信息就能差出好几倍
  • 嵌入的瓶颈不在存储而在计算。靠电池运行的设备上，这份负担是直接能感觉到的
  • 往后推能减负荷，但会出现最新文档缺席于检索的那段区间。这段区间的长短决定了体感质量
  • 快照是另一个门类，存储容量、运算单元、功耗要求全都上一个台阶

存不了的东西和不该存的东西

不是所有页面都能存，能存的也不是全都该存。这两者重叠的地方，是这个问题里最别扭的部分。

先说存不成立的一边。搜索结果页面、无限滚动的列表、实时仪表盘，地址一样，每次打开内容却不同。对这类页面来说，再找一遍这句话本身就不成立。存下来的不是那个地址，而是当时的那个画面。所以这里既是快照变得必要的地方，也同时是快照最危险的地方。仪表盘上多半还并排显示着不该留下的东西。

再说不该存的一边。邮箱、账户查询、诊疗记录、公司内部系统，通常既是最想再找到的东西，也是最不该保存的东西。这里还多出一层。登录之后的页面里不只有我的信息。收到的邮件里有寄件人写的句子，内部文档里有同事的名字和判断。索引我自己的记录这句话，实际上变成把别人的信息复制到我的设备上，就是在这个地方。

所以排除清单不是附加功能而是前提。只是排除并不完整。同一份 Recall 文档写明，过滤并不能阻止浏览器、网络服务商、网站或组织知道你访问过那个站点。从本地索引里剔除，和不留痕迹，是两回事。

  • 地址相同而内容不同的页面，回想的单位就从地址变成了时刻。时间轴成为第一排序，这里也是一个理由
  • 登录之后的内容，价值和风险朝同一个方向变大。这份重叠靠设置分不开
  • 别人的信息混进来，不是口味问题。在共用设备和工作环境里，它变成划定范围的问题
  • 排除清单按域名来放更有实效。按页面排除管不住，多半只在头一周维持得下去
  • 最实用的判断是这一条。要不要排除犹豫了，就排除。以后再加进来的代价，比以后再挖出去便宜得多

现有工具空出来的位置

这个位置为什么是空的，把现有工具各自做什么、不做什么并排放一下就看得见。

工具是否保存正文覆盖范围空着的地方
浏览器历史不保存访问过的网页，最近 90 天没有正文，用句子找不到
书签只留地址自己当时挑出来的挑的时候不知道什么会变重要
笔记应用只有抄进去的自己动手留下的没抄进去的等于不存在
桌面搜索文件内容会建索引自己设备上的文件在网上看过的不在范围内
网页存档服务保存公开可达的页面那不是自己看过的，是别人存下的

从桌面搜索看，边界很清楚。Windows 搜索在默认的经典模式下为文档、图片、音乐文件夹和桌面建索引，增强模式下为整台电脑建索引。它为包括文件名和完整路径在内的属性建索引，有文本的文件连内容一起建；按文件类型改成只建属性，索引会变小，代价是失去内容检索。上一节那笔存多少与能搜多好的交换，原样就写在操作系统的设置里。

macOS 把排除做成了明确的功能。系统设置的聚焦搜索里有一份搜索隐私清单，把文件夹或磁盘放进去，那个位置就不会被搜到。苹果的文档也把代价一并写下了。排除特定文件和文件夹后可能收不到某些应用的更新通知，若把整块内置磁盘排除，则收不到任何更新通知。要拿掉什么的决定，会在想不到的地方带来代价。

两者都不管在网上看过的东西。浏览器这边知道这个空位。Chrome 有 AI 驱动的历史检索，按帮助文档，开启后你浏览的站点的页面内容会被保存并加密到设备上。只是要自己去开的选择加入，使用时需要人在美国并以英语使用 Chrome，而且即便站点后来变了，结果用的仍是访问当时的内容。不保存正文就谈不上回想，这个结论造浏览器的一方也一样；即便如此，提供的范围还是窄。单独的工具不断冒出来，位置正是这道缝。

笔记应用性质不同。笔记应用握着的只有自己决定抄进去的那些，而决心的时点错开这个问题，和书签一模一样。这种腐坏发生在组织层面会是什么样，写在企业知识库在悄悄腐坏那边。

  • 现有工具各自为别的目的而造，回想不是其中任何一个的目的。空位不是失误而是边界
  • 在操作系统的文件检索与浏览器的访问历史之间，网页正文这一格是空的。这一格就是这个门类存在的理由
  • 浏览器开始填这一格，也可以读作单独工具寿命未必长的一个信号

用得越久越会出现的问题

这类工具真正的考验不是开启后的第一周，而是第二年。第一，会变大。比大小更成问题的是变大的速度。一天 200 个页面，一年就是七万多页，到某个时点重建索引会变成要跑一整夜的活。从那以后改表结构就事实上不可能了，因为要改就得重建，而重建是一天的工作量。

第二，会变旧。保存下来的是访问当时的内容，这期间页面可能被改过，也可能已经消失。这不是缺陷而是性质，原件消失之后，自己的副本反而成了唯一的记录。只是能不能拿那份副本当依据是另一回事，它未经核验，而且只有自己手里有。

第三，会重复。同一份文档会以不同地址、在不同时点，以打印版、移动版和译文页的形式反复进来。前十行成了同一份文档的十个版本，这次检索就是失败的。去重必须先定下什么算是同一个，而这个标准并不是不言自明的。

第四，会不再用。这才是最常见的结局。忘了有这份索引，还是回去重搜一遍网页。个人工具的死法多半不是坏掉而是被遗忘，而这也有理由。只要打开这个工具的摩擦比在搜索框里敲字大哪怕一点，赶时间的时候总会选后者。

  • 表结构必须在重建还便宜的时候定下来。变大之后事实上就冻结了
  • 变旧既是缺陷也是价值。只是拿消失原件的副本当依据时，得把这一点讲明
  • 去重的标准工具替不了你定。不定的话，靠前的结果就会被同一份文档填满
  • 最常见的终局是遗忘。所以这类工具，能挤进既有习惯里的设计常常比性能更要紧

自己做还是用现成的

通常的建议很明确，别自己做，用现成的，因为成本出在维护而不是第一版。可在这个领域这条建议会晃动一格，因为数据越敏感，把它放到别人服务上的代价增长得越不成比例。平常服务关门只是不方便，这里关门的方式却决定了自己全部记录的去向。

话虽如此，自己做也没什么浪漫可言。第一版真的一个周末就能出来，长的是后面。每改一次表结构就要重建一次，浏览器一更新扩展就失效，没做备份地跑着，弄丢一个索引文件就是几年的东西没了。

标准能压成三条。存储位置是否在自己掌控之下。如果有东西要出去，那是默认还是选择。停用时能不能把数据带走。第三条最常被漏掉。只有进路没有出路的设计，几年后会让人成为那份索引的人质。而且开源这件事并不会自动满足第一个条件。可以自托管，和默认设置就是本地，是两句不同的话。许可证也不是保证，许可证决定代码能去哪里，不决定数据去哪里。

  • 自己做的真正成本不在第一次实现，而在表结构变更与重建。先把这两样设计好，其余的会跟上来
  • 用别人的工具就看默认值。不是看文档写了什么做得到，而是看什么都不设置时会发生什么
  • 出路，也就是导出与彻底删除，一开始就要确认。到后来没有余裕去确认
  • 开源是可核验性，不是核验的结果。而许可证对数据的去向什么都没说

引出本文的那个工具现在到哪一步

把引出本文的那个项目的公开数据按 2026 年 9 月初的时点记下来。仓库创建于 2026 年 1 月 4 日，星标 3,526 个，分叉 161 个，开着的 issue 56 个。最新发布是 2026 年 8 月 23 日的 v0.18.0，最后一次代码推送是 9 月 1 日。语言是 Go，许可证是 AGPL-3.0。

这些数字说明两件事。一，活跃。八个月里发布超过十八次，现在也还有提交进来。二，只有八个月，而且还是 0.x。星标数是关注度的指标，不是稳定性的指标。人们喜欢它，和三年后还能读得了自己的索引，是两回事；对承载个人记录的容器来说，这个区别格外重。

功能清单上写的是全文索引、浏览器自动索引、查询能力、可选的语义检索、爬虫与浏览器导入、网页与终端与 MCP 客户端、多用户。

更要紧的是文档自己划出的边界。默认没有遥测也没有云同步，浏览器扩展把索引到的页面内容只发往用户指定的服务器，而开启可选的语义检索后，文档文本会发往用户自己选的嵌入端点。最后这句话，正好落在第 3 节那个岔路口上。本地是默认、往外传输是选择的这种安排并不保证什么，但它至少告诉你该问什么。

  • 看成熟度时，比星标数更有用的是仓库年龄、发布间隔、开着的 issue 是什么性质。前两项在数据里直接看得见
  • 0.x 意味着存储格式还可能变。对要长年累积的数据来说，这一行比任何功能都重
  • 比起功能清单，把默认值和边界讲明的句子能说明更多。完全没有这类句子的工具最难判断

小结

重新找到自己看过的东西，不是网页搜索缩小之后的问题。对象是几万而不是数十亿，所以召回比排序更重要；查询也不是想了解什么，而是想再看一眼什么。浏览器历史干不了这件事，理由同样简单，它有标题和地址而没有正文，人记住的偏偏是正文。

于是就会往保存正文的方向去，而在那一刻问题的性质就变了。散落的东西汇成一个文件，里面装着法律单列为敏感信息的项目中的相当一部分。放在本地的设计和往外送的设计，差别不在便利，而在风险的边界会延伸到哪里。

剩下的是一根轴。所有让它更容易被找到的措施，同时都在放大风险。放进正文，就能用句子去找，敏感的正文也整份进来。放进快照，画面能原样复活，登录状态也一并留下。这根轴没有办法消掉，知道自己站在它上面的哪一点就是能做的全部。

未能确认的部分

  • 引出本文的那个项目内部使用什么索引引擎和存储，未能从公开说明中确认。本文关于索引大小的讨论，依据的是 SQLite FTS5 文档里的公开测量值，而不是那个项目
  • 本地嵌入的实际耗时与耗电，因为没能确认可靠的测量值，所以不带数字地写。说计算是瓶颈，是从方式的差别得出的，不是从测量得出的
  • Chrome 的 AI 历史检索是否自动排除无痕模式或特定站点，以及保存下来的页面内容能否单独删除，未能从该帮助文档中确认
  • 个人把自己的记录保存在自己设备上的行为，适用个人信息保护法的哪一条、如何适用，未能确认。第23条的敏感信息清单只作为衡量风险大小的参考引用，本文不作法律判断
  • 这一门类工具的用户规模或一年后的持续使用率，没有找到公开资料。以遗忘收场这个说法是观察，不是统计
