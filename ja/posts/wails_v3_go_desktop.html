Web技術でデスクトップアプリを作る

システムWebViewとバンドルランタイムが分かれる地点、そしてその選択が請求するもの

2026年8月16日 開発・インフラ

序論: フレームワーク名を並べ始めると答えが出ない

社内ツールをデスクトップに降ろす場面を想定してみる。Web要員はいて、ネイティブ要員はいない。このとき多くのチームは候補フレームワークの名前を表に並べ、星を付け始める。その表は最後まで行っても結論が出ない。軸の取り方が間違っているからだ。

Web技術でデスクトップアプリを作るとき、実際に選んでいるのは四つある。レンダリングエンジンをアプリと一緒に配布するか、バックエンドのロジックをどの言語に置くか、配布物をどの形式で署名し更新するか、OS機能とどこまで深く結ぶか。このうち残り三つの難易度をまとめて決めるのが最初のものだ。エンジンを載せるかどうかが決まれば、アプリ容量の桁が決まり、レンダリングのリグレッションにいつ出会うかが決まり、セキュリティパッチを誰が運ぶかが決まる。

この記事はその最初の軸を縦に立て、残りを配置する。2026年8月にベータへ入ったWails v3を例に使うが、特定のフレームワークを勧める文章ではない。どの道具を使っても残る交換関係を見せることが目的だ。

1. WebView方式が解決するものと、そのまま残るもの

WebView方式が実際に解決するのは人員と資産の問題だ。画面のコードを三通り書かなくてよく、すでに社内に積み上がったコンポーネントとデザインシステムをそのまま持ってこられる。反復サイクルも短い。保存すればすぐ反映される開発体験は、ネイティブのツールキットではありふれたものではない。

残るのはこちらだ。

  • バンドルサイズ — エンジンを同梱すると、アプリひとつがブラウザ一式をまるごと持ち歩く。社内配布では初回ダウンロードより、更新のたびに繰り返される転送量が先に問題になる。
  • メモリ — ブラウザエンジンはマルチプロセス構造だ。レンダラーとGPUのプロセスが別に立ち上がる構造をウィンドウひとつのアプリにそのまま載せると、想定より重い。
  • 起動時間 — エンジンの初期化とフロントエンド資産のパースが順に起きる。Webでは初回描画までの時間が指標だったが、デスクトップアプリではアイコンを押してウィンドウが出るまでの体感がそのまま品質評価になる。
  • ネイティブ統合 — メニューバー、トレイアイコン、ファイル関連付け、システム通知、ウィンドウ外からのドラッグアンドドロップ、アクセシビリティツリーはWeb標準の外にあり、フレームワークがどこまで包んでくれるかが実際の差を作る。ウィンドウ状態の復元やマルチモニターの倍率、ログイン時起動の登録のようにOS別のウィンドウ管理と権限モデルに掛かる項目も、WebViewを使ったからといって消えず、プラットフォームごとに別途付ける。

これらの項目の数字はアプリ構成とビルドオプションで桁が変わる。だからフレームワーク別のMBとミリ秒をひとつに言うことはできない。しかし桁を実際に動かす決定はひとつだ。

2. 分岐点 — ランタイムを同梱するか、システムのものを借りるか

戦略はふたつある。

2.1 ランタイムの同梱

ブラウザエンジンとランタイムをアプリに収めて配布する。Electron系統がこの位置に立つ。得は明確だ。開発者が検証したエンジンのビルドがユーザー端末でそのまま動く。CSS一行がある端末でだけ違って描かれる状況が構造的に起きない。ブラウザのサポート表を見る必要もなくなる。

対価も明確だ。アプリごとにエンジン一式が付く。そしてエンジンのセキュリティパッチを自社リリースで運ぶ責任が開発チームに残る。Chromiumに脆弱性が公開されれば、その修正を含んだアプリのバージョンを出してユーザーに更新させる。この責任をフレームワークが代わりに負ってはくれない。

2.2 システムWebViewの利用

OSがすでに提供しているエンジンを呼ぶ。WailsとTauri系統がこちらだ。Wailsのリポジトリの案内文はこの立場をネイティブなレンダリングエンジンを使い、組み込みブラウザはないという一行で言い切る。配布物からエンジンが外れ、エンジンのパッチはOSやランタイムの更新経路が担う。

対価は多様性だ。ユーザー端末ごとにエンジンのバージョンが違い、サポートされるWeb機能も違う。最新のCSS構文をひとつ使う前にサポート下限を決める必要があるということだ。

2.3 中間地帯がある

この交換がフレームワーク間だけにあるのではない、という点が重要だ。同じプラットフォームの中にもある。WindowsのWebView2は二種類の配布モードを提供していて、自動更新される常時最新モードと、特定バージョンのバイナリをアプリと一緒に載せる固定バージョンモードだ。マイクロソフトの配布ドキュメントは固定バージョンのバイナリが250MBを超え、アプリパッケージがその分だけ大きくなると書く。逆に常時最新モードでは、必要なときに取得するブートストラッパーが約2MBだ。

整理するとこうなる。レンダリングの一貫性と配布容量は同じダイヤルの両端だ。どのフレームワークを選んでもこのダイヤルは残り、どの位置に置くかは製品が決めるしかない。

4. Windows — WebView2と二種類の配布モード

WindowsのシステムWebViewは、Edgeと同じChromium系統のエンジンを使うWebView2だ。実務で知っておくべきことは次のとおり。

  • 常時最新のランタイムはWindows 11のオペレーティングシステムに含まれる。Windows 10は大多数の端末にすでに入っているが全部ではない。だからアプリのインストールや起動の時点で存在を確認する手順が推奨されるが、方法はレジストリからランタイム項目のバージョン値を読むか、利用可能なブラウザのバージョン文字列を返すAPIの結果が空かどうかを見る二通りだ。
  • ない場合は約2MBのブートストラッパーを取得してサイレントインストールするか、オフライン環境なら完全版インストーラーを配布物に同梱する。
  • 端末上のすべての常時最新アプリが一式を共有する。条件が合えばEdgeのバイナリとハードリンクで結ばれ、ディスクとメモリを節約するという説明もドキュメントにある。
  • 運用上の落とし穴がひとつある。ランタイムが更新されても実行中のアプリは以前のバージョンを使い続ける。新しいバージョンへ移るにはアプリを再起動するか、既存の環境オブジェクトの参照を手放す必要がある。長時間起動しっぱなしのアプリが外部コンテンツを描画するなら、これはセキュリティ事案になる。新しいブラウザバージョンの通知イベントを受けて再起動を促す処理が必要なのはこのためだ。
  • 固定バージョンモードには別の制約が付く。ドキュメント上の既知の問題としてネットワークパスから実行できず、Windows 10では特定のランタイムバージョン以降、パッケージ化されていないデスクトップアプリが権限付与のコマンドを追加で実行する必要がある。
  • 本番アプリはEdgeブラウザの安定チャネルをバックエンドのプラットフォームとして使えない。アプリがブラウザのインストール有無に依存しないようにする設計だ。

判断基準はこう置く。社内の全PCに配布し、レンダリングのリグレッションを絶対に受けられない組織、とくにインターネットが遮断された網に配布する場合なら固定バージョンモードが検討対象になる。それ以外は常時最新モードにインストール時点の確認手順を付けるほうが、容量とパッチ負担の両方でまさる。

5. macOSとLinux — 同じシステムWebViewでも性質が違う

macOSは単純なほうだ。システムWebViewがWKWebViewひとつで、OSの更新とともに動く。配布対象のOS下限がそのままエンジンの下限になるので、サポート範囲を決めることがそのままWeb機能のサポート範囲を決めることになる。ビルドにはXcodeのコマンドラインツールが必要だ。

Linuxが本当の変数だ。ディストリビューションごとにgtkの世代とWebKitGTKのバージョンが異なり、同じディストリビューションでもリリースによって開発パッケージ名が変わる。Wails v2のインストールドキュメントはgtk3とWebKit2GTKを要求しつつ、最近のUbuntuのように4.0の開発パッケージがない環境では4.1を入れてビルドタグを付けるよう案内する。この案内がドキュメントに明示的に入っていること自体が状況を物語る。

v3がLinuxのスタックをgtk4とWebKitGTK 6.0へ引き上げたことは方向を示している。以前のgtk3系統は別のビルドタグで残るが、v3.1までと明記されている。そしてv3のサポートプラットフォーム表記がUbuntu 24.04を挙げ、他のLinuxは動くかもしれないと書く書き方が現実をそのまま反映している。

だからLinuxを一級ターゲットにするなら、順番をこう置く。どのディストリビューションのどのバージョンまで責任を持つかを先に固定する。その決定がgtkの世代とビルドタグを決め、それがさらにCIイメージとパッケージ形式を決める。この順番を逆にすると、リリース直前にスタック全体を選び直すことになる。

6. Wailsが取った立場と、v3で変わったこと

Wailsの立場は二文で要約できる。バックエンドはGoに置き、画面はOSのネイティブなレンダリングエンジンに描く。サーバーを立ててブラウザを開く方式を避けながら、GoのプログラムにWebフロントエンドを付けたい人が対象だ。前節の分類ではシステムWebViewの側に立つ。

6.1 バージョンの状態 — 2026年8月16日確認時点

  • リポジトリの案内は二系統を明示する。v2はStable、v3はBetaだ。インストールコマンドもそれぞれwailsとwails3で別にある。
  • リリース一覧ではv2.14.0が2026年8月10日の正式リリースとして上がっている。
  • v3系統の最新はv3.0.0-beta.8で、2026年8月12日のプレリリースだ。最初のベータタグであるv3.0.0-beta.0が8月2日で、その直前まではアルファ系統だった。十日間でベータタグが九回出た計算になる。修正が速いという意味であると同時に、バージョンを固定しなければビルドが揺れるという意味でもある。
  • ベータはベータだ。本番基準の安定チャネルは依然としてv2だ。

6.2 v3で変わったこと

発表された変更と、リポジトリで確認できる痕跡を並べるとこうなる。

  • 明示的なオブジェクトのライフサイクル — 暗黙のコンテキスト中心の構成から、Application・Window・Serviceという明示的なオブジェクト構成に変わった。
  • マルチウィンドウの標準サポート — エディタや検査ツールのようにウィンドウを複数開くアプリで、迂回実装が要らなくなった。
  • Goサービスパターン — 従来のバインディングの位置をサービスが置き換え、バックエンド機能とフロントエンドAPIの境界が明示される。
  • 静的解析ベースの型定義生成 — 引数名とコメントを保った形でフロントエンド用の型定義が出る。
  • ビルド過程の公開 — フレームワークの内部に隠さず、Taskfile形式で表に出す。リポジトリに該当ファイルがあり、インストールドキュメントもパッケージ管理を変えたければプロジェクトのTaskfileを直せと案内する。
  • サーバービルドの選択肢 — デスクトップのUIとバックエンドのロジックを分けて動かせる形がガイドとして入っている。
  • 実験的なモバイル — リポジトリのv3ディレクトリにiOS・Androidのドキュメントファイルがある。実験段階と表記される。
  • ツールチェーン要求の上昇と設定ウィザード — Go 1.24以上を要求する。v2が1.21以上だったのと対照的だ。npmはv3で任意に下がったが、基本テンプレートの多くが必要とする。wails3 setupがプラットフォーム依存関係の点検とプロジェクトの既定値、署名設定を一度に扱うが、ドキュメントに新機能であり主にLinuxで検証されたという注意が付いている。

マイグレーションの観点で重要なのはこのリストの最初の三項目だ。APIの名前が変わった水準ではなく、アプリを構成するモデル自体が変わった。進行中の製品があるなら、正式配布までは新規プロジェクトで試すほうが戻しやすい。

7. 境界をコードで見ると — 概念例

以下は構造を示すための短縮した例であり、実行して確認していない。実際のAPIシグネチャと登録方式は、使うバージョンのドキュメントに従う必要がある。

WebView方式では、バックエンドとフロントエンドの境界が関数シグネチャいくつかに狭まる。Go側にこんな型があるとしよう。

// 概念例 — 動作未確認
type Vault struct {
    root string
}

// フロントエンドに公開されるのはこのメソッドひとつだ。
func (v *Vault) List(prefix string) ([]string, error) {
    // ファイルシステムへのアクセスはGo側にだけ存在する。
    // prefix をそのままパスに繋げず、正規化と検証を通す。
    if strings.ContainsAny(prefix, "/\\.") {
        return nil, errors.New("invalid prefix")
    }
    return filepath.Glob(filepath.Join(v.root, prefix+"*"))
}

フロントエンドは生成された型定義を通して、このメソッドだけを見る。

// 概念例 — 動作未確認
const files = await Vault.List('report-');
render(files);

この図がなぜ重要かは二つある。

  • WebViewの中で動くコードは信頼境界の外だ。レンダラーに読み込まれたスクリプトが何であれ、呼べるのは公開されたメソッドだけであり、その一覧がそのまま攻撃面になる。利便性のためにファイルパスをそのまま受け取る汎用メソッドを開けておけば、その瞬間に任意のパスへのアクセスが可能になる。検証は必ずGo側で行う。
  • 境界を狭めるとドキュメントが付いてくる。静的解析で型定義を生成すれば、フロントエンド側のコードで関数名と引数名、コメントまで見える。手で維持していたインターフェース文書が消えるということだ。

この構造が強制する規律もある。状態の変化はイベントで流し、命令はメソッドで送る形が結局は標準になる。

8. 配布・署名・自動更新 — デスクトップで時間を食う区間

画面を作る仕事が終わると本当の日程が始まる。この区間を浅く見積もるとリリースが遅れる。

8.1 署名と公証

Wails v3の署名ガイドが整理したクロス署名の関係は、実務判断にそのまま使える。

  • Windowsの実行ファイルとインストーラーパッケージは、Windows・macOS・Linuxのどのホストからでも署名できる。
  • LinuxのDEB・RPMパッケージも同様に、PGP鍵でどのホストからでも署名できる。
  • macOSのアプリバンドル署名と公証だけがmacOS上でしかできない。Appleのツール体系のためだ。
  • 署名バックエンドはネイティブなプラットフォームでは各OSの標準ツールを使い、クロスコンパイル時は内蔵実装を使う。v3の設定ウィザードは署名設定をユーザー設定ファイルに書き、パスワードはOSの資格情報ストアに入れる。ビルドスクリプトに平文で残さないという意味だ。

三つ目の項目が予算に直結する。macOSを配布対象に入れた瞬間、CIにMacランナーが必要になる。そして証明書の発行と更新、公証の待ち時間、署名鍵をCIへ安全に注入する作業はコードではなく手続きであり、手続きは日程の中で圧縮できない。

8.2 自動更新

Webはリロードが配布だ。デスクトップは違う。ダウンロードし、検証し、実行中のバイナリを差し替え、再起動を促す必要がある。自作するとき欠けてはならないものは四つだ。

  • 署名の検証 — 取得したものが自分たちが出したものかを公開鍵で確認する。通信区間の暗号化だけでは足りない。
  • 原子的な差し替え — 部分ダウンロードや中断が実行ファイルを壊してはならない。一時領域に取得し、検証してから差し替える順序が基本だ。
  • ロールバック経路 — 新しいバージョンが起動に失敗したとき前のバージョンへ戻る方法がなければ、リモートサポートが電話案内になる。
  • 強制更新ポリシー — セキュリティ修正にはスキップを許さない等級が要る。

Wails v3はこの部分をフレームワーク機能に引き上げた。アップデータがアプリケーションのオブジェクトに付き、配布元のプロバイダを差し込んで使う構造だ。ガイドにはGitHub Releases、商用の配布サービス、Sparkle系統のマニフェスト、公開されたマニフェスト規約、そして自前の実装が列挙されている。取得したファイルは設定した公開鍵で検証し、バイナリを安全に差し替え、状態遷移はフレームワークのイベントバスを流れる。状態は未設定・待機・確認中・最新・更新ありといった値で定義され、既定の更新ウィンドウのUIも提供され、差し替えられる。

ここで4節の落とし穴をもう一度重ねて見る必要がある。システムWebViewを使えば、エンジンのパッチはアプリの更新とは別経路で来る。それは得だ。しかしアプリを何日もつけっぱなしにする使い方なら、そのアプリは古いエンジンを使い続ける。アプリの自動更新とは別に、再起動を促す仕掛けがあってはじめてパッチが実際に効く。

配布チャネルが容量に敏感(低速回線・シンクライアント) システムWebView 配布物からエンジンが外れる 端末ごとのエンジン差の検証負担
ローカルファイルやハードウェアへのアクセスが製品の核心 WebView + ネイティブバックエンド ブラウザのサンドボックス外の作業をバックエンドが担う 公開メソッドがそのまま攻撃面・検証コードが必要
インストール手順そのものをなくしたい PWA・インストール型Webアプリ 署名・公証・更新パイプラインがまるごと外れる OS統合が浅い・ブラウザの方針に従属
OS標準のUIの手触りとアクセシビリティが製品価値 完全ネイティブ ツールキットがアクセシビリティと作法を既定で提供する プラットフォーム別の画面コードを別途維持
既存のWebアプリを包むのが一次目標 PWAを先に、足りない分だけWebView いちばん安い経路から試して実際の不足を確かめる 二度作る区間が生じうる
Linuxのディストリビューション幅が広く下限を狭められない バンドルランタイムのほうが変数が少ない gtkの世代とWebKitGTKのバージョン差を避ける 容量とパッチ責任を引き受ける
バックグラウンド処理が重く画面は単純 システムWebView + コンパイル言語のバックエンド 重い仕事はネイティブコードに、画面は薄く 境界の設計とイベントの流れを自分で組む必要がある

表の使い方は上から下へ読むことではない。自社の製品で譲れない項目ひとつを見つけてその行から固定し、残りの行の対価を引き受けられる範囲に合わせる。譲れない項目が二つ以上あるなら、たいていそのうちひとつは本当の要件ではない。

10. 確認できなかったこと

  • v3発表の原文ページ — 公式サイトのベータ発表記事はアクセスが403で遮られ開けなかった。6節の変更一覧はリポジトリのドキュメント原本とファイル構成、そしてその発表を要約した技術トピックに基づく。
  • フレームワーク別のバンドルサイズ・メモリ・起動時間 — 同一条件で測定した公開の数値を確認できなかった。この記事にフレームワーク別のMBとミリ秒がない理由だ。使った唯一の数値である固定バージョンの250MB超とブートストラッパーの約2MBは、マイクロソフトの配布ドキュメントの値だ。
  • v3.0の正式配布時期 — 公開された日程を確認できなかった。
  • v3のモバイルサポート範囲 — リポジトリにiOS・Androidのドキュメントファイルはあるが実験段階であり、どこまで動作するかは確認できなかった。
  • ElectronとTauriのリリース別の細かい挙動 — この記事の比較はエンジンを同梱するかという構造の差までだ。各フレームワークの最新機能はそれぞれの公式ドキュメントを見る必要がある。
  • 7節のコード — 概念を示すための短縮であり、実行して確認していない。実際のシグネチャと登録方式は、使うバージョンのドキュメントに従う必要がある。

結論: 着手前に決める三つ

フレームワークの比較表を作る前に答えるべき問いは三つだ。

  1. レンダリングの一貫性をどれだけ買うか。代金は配布容量とエンジンのパッチ責任で払う。これが決まれば候補は半分に減る。
  2. サポート下限をどこに引くか。Windows 10をどこまで、macOSを何バージョンまで、Linuxをどのディストリビューションまで。Linuxの答えがいちばん高くつく。
  3. 署名と更新のパイプラインを誰がいつ作るか。macOSが対象ならMacランナーが必要で、自動更新には公開鍵の検証・原子的な差し替え・ロールバック・強制ポリシーが最低限入る。

Wailsはこの構図でシステムWebViewの側に立ち、バックエンドをGoに置く選択肢だ。v3はアプリの構成モデルを組み直した大きな変更であり、2026年8月16日の確認時点でベータだ。安定チャネルはv2だ。試すのは新規プロジェクトで、納品は安定チャネルで、というのが今の時点の安全な配置になる。

最後にひとつ。WebView方式が作る錯覚がある。画面がWebで早く出るので、アプリがほぼ完成したように見える。実際に残っている仕事はインストーラー、署名、公証、更新、クラッシュ収集、ログイン時起動、マルチモニターだ。この一覧を先に日程へ入れて始めれば、後で遅れない。
