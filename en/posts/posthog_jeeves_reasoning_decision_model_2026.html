The account below rests on the figures in the README of PostHog/jeeves on GitHub and in the Hugging Face model card. Every accuracy and latency value is self-reported by the repository side and is not a third-party reproduction. Values that are not in the source are not invented, and anything computed from two values in the source is marked “derived”.

A 9B model that adds reasoning to the Jev family — what the repository claims

The PostHog repository Jeeves on GitHub introduces itself as a “reasoning Jev-style classifier”. It is based on Qwen3.5-9B with LoRA and a pointer head attached so that it outputs a probability for each option, it is trained with SFT followed by reinforcement learning called CISPO, and it ships with a block-4 diffusion drafter that speeds up generation of the reasoning chain. What Jev is appears in the Jev evaluation article, and a way to imitate the same shape with a general-purpose model appears in the Jev-style wrapper article, so those explanations are not repeated here.

The problem statement in the README is one paragraph. Jev-style models give calibrated decision probabilities but at low accuracy, so many pipelines rely on a reasoning model as a fallback. Jeeves trains a Jev-style Qwen3.5-9B with CISPO so that it reasons before it decides. The question this article holds on to is a single one: what does the repository itself say it pays for the accuracy it buys?

  • Composition. Qwen3.5-9B, LoRA (r=16) and a pointer head. The model card says one repository holds the fused weights with the LoRA merged, the head, the fitted temperature and two drafters.
  • Question types. Yes/no (noul), multiple choice (choice) and rating (score) questions can be mixed in one request.
  • Interface. A Jev-compatible API that follows Jev /v1/systemone format. The Python SDK is included as a drop-in replacement for the Jev SDK.
  • Released material. Weights, training code, and train, dev and test data.
  • Headline figures. 0.889 against Jev 0.857 on test data it was not trained on, 0.935 against 0.866 on the JevBench public tiers, and on one H100 with fp8 about 0.3 s per request without thinking and a 3.3 s median with thinking.

In another article of the same theme, the OpenAI Decision API built on Luna is a product whose per-call price and candidate limit have not been disclosed. If that one is a product with almost no public figures, Jeeves is the one whose code and data are also published, so its numbers can be taken apart and read.

Where the figures come from — all self-reported by the repository

The README and the model card are documents from the same repository side. There is no third-party measurement inside either. The model card says a from-scratch reproduction with the released code matched the public checkpoint within noise, but that too is the repository own statement. Before reading the table, the conditions of each source have to be separated.

  • Source of the comparison columns. The README says the Kev-9B and Jev columns are “the numbers Kev publishes”. They are not values the Jeeves side re-measured for Jev in the same environment.
  • Scope of JevBench. According to the README, the JevBench figures are the 231 items of the public easy, standard and hard tiers, and the sealed judge tier is not included. It says the Jev and Kev numbers are restricted to the same public items.
  • Who made JevBench. Who created the benchmark is not stated in the README or the model card. The repository contains an evaluation script (jevbench.py).
  • Comparisons outside JevBench. The limitations list in the README says the Kev and Jev comparisons outside JevBench use different items from the same sources. They are not the same items scored side by side.
  • The asterisk in the table. The JevBench values in the Kev column are Kev-8B (Qwen3), not Kev-9B. The README says no Kev-9B JevBench result is published.
  • Evaluation language. According to the limitations in the model card, the evaluation used English inputs only.

The GeekNews summary reproduces the headline figures of the README almost as they are and writes 93.5% vs 86.6%. That is the README 0.935 and 0.866 converted to percentages. The same summary also carries a criticism that a p90 latency of 17 seconds undermines the speed advantage of Jev. That criticism can be tested against the repository figures.

Reading the table across the rows, a pattern separates. In the repository figures, Jeeves is ahead on the kinds of questions where reasoning is likely to help: PAWS, which asks about the relation between two sentences, the items that read rule structures and policies, and the hard tier. It falls behind on questions that ask for background knowledge, namely MMLU and MMLU-Pro, and QNLI is also slightly lower. One more thing stands out inside the table, in the last row. The rate of answering unknowable questions with high confidence is lower for Jeeves than for Jev, but higher than the 0.000 of Kev-9B. On the quality of “not being confident even when wrong”, the model with reasoning added is not the best of the three.

  • Where it is ahead. Test overall, JevBench overall and hard, PAWS, held-out rule structures, contrastive policies, and Emotion as listed by the repository (0.647 vs 0.588).
  • Where it is level. On TweetEval offensive, Jev and Jeeves are equal at 0.813.
  • Where it falls behind. MMLU, MMLU-Pro, transfer overall and QNLI. The first three are in the same family as the knowledge questions the repository itself lists as a limitation.
  • Calibration metric. The ECE on the JevBench public items is 0.049 for Jev and 0.037 for Jeeves, lower for Jeeves. The Kev column is empty.

Back-calculating the 231 JevBench items — the gap is concentrated in the 111 hard ones

The accuracies in the README are given to three decimal places and the number of items is public, so the number of correct items can be counted backward as integers. Multiplying 0.935 by 231 gives about 216, and multiplying 0.866 by 231 gives about 200. For the hard tier, 0.865 times 111 gives about 96 and 0.730 times 111 gives about 81 (derived). These integers all match the three-digit rounding. The remaining easy and standard tiers are the 120 items left after subtracting 111 from 231, and there Jeeves got about 120 right and Jev about 119.

What this calculation says is the following. The overall gap over the 231 items is about 16 items, and about 15 of them come from the hard tier. The easy and standard tiers are nearly perfect for both, so they show no difference. In other words, what reasoning added is not overall accuracy but the recovery of hard items. It is the same story as the sentence the README stresses in its problem statement, that it beats Jev on JevBench hard, translated into counts of items.

  • Sample size. One item is 0.43 percentage points. The hard tier has 111 items, so one item is 0.9 points. A gap of 15 items looks structurally large, but the README gives no confidence interval or variance across repeated runs.
  • Limit of public items. These figures cover the public tiers only and exclude the sealed judge tier. A score that includes the sealed tier is not in this repository documentation.
  • Ceiling on easy items. If the easy and standard tiers are stuck at the ceiling, those tiers have no power to separate models. If most of the items in your own work are easy, the gain on this benchmark may show up less. This is an interpretation based on the back-calculation.
  • Calibration is a separate metric. The number of correct answers and the quality of the probabilities are different things. ECE of 0.037 vs 0.049 is that separate metric, and the difference is 0.012.

The values for switching reasoning on and off — accuracy and latency table

The price of accuracy is time. The README provides two options that adjust the amount of reasoning (max_think and nothink_threshold) and reports figures per setting on 325 dev questions under the condition of one H100 with fp8. The calculations that can be read from the table are these (derived). On the same 325 dev questions, switching reasoning on raises accuracy from 0.775 to 0.825, by 5.0 percentage points. On the test split it is from 0.804 to 0.840, by 3.6 points. The size of the gain differs by item set even for the same checkpoint, and the two values must not be mixed. The 0.889 at the top of the README is the item-weighted “test overall”, while 0.840 is the value on the test split, and the README does not explain the relation between the two.

The compromise setting keeps 3.1 of the 5.0 points (0.806 − 0.775). In exchange, the median falls from 3.3 s to 2.0 s, the p90 from 17.1 s to 5.6 s, and the mean reasoning tokens from 1,138 to 344, about 30% of the full amount. It is a setting that keeps about 62% of the gain while cutting the tail latency to about one third. At the other end, “no thinking” is about 11 times faster than full thinking on a median basis (3.3 s ÷ 0.3 s).

  • “0.3 s vs 3.3 s” is a comparison between medians. The p90 with full thinking is 17.1 s, and the p90 without thinking is not in the table.
  • The 8.14 s in the example response. It is one example in which three questions reasoned in parallel and used 1,536 tokens. It is not under the same conditions as the 3.3 s median, and is read only as one case showing how much the number of questions and the reasoning length can stretch latency.
  • The numbers in the setting names. The default of max_think is 2,560 and the compromise setting is 768. The reasoning chain is cut at that length and the model answers immediately.

What is lost — knowledge questions, tail latency, reasoning that is hard to read

Combining the limitations in the repository with those in the model card, what is lost comes down to five things. All of them are things the repository itself wrote.

  • Knowledge questions. MMLU 0.793 vs Jev 0.900, MMLU-Pro 0.739 vs 0.840. The README says that even with reasoning added, the 9B model trails Jev on questions that ask for broad knowledge.
  • Tail latency. The p90 with full-length reasoning is 17 s on one H100. The README advises using max_think and nothink_threshold when latency matters.
  • Chains that do not finish. According to the model card, about a third of full-length reasoning chains hit the token cap without closing, and accuracy on those items is lower.
  • Reasoning that is hard to read. According to the README, no language consistency reward was included, so the reasoning chains are not well interpretable. The API has a return_reasoning option that returns the reasoning text, but being able to receive it and being able to read and review it are different things.
  • Input language. The evaluation was limited to English inputs. Accuracy in other languages is not in the documents.

There are also figures for the confidence of the path without thinking. The model card says that with the fitted temperature applied, the no-think path has a top-label calibration error of 0.021 and 1.3% confident errors (wrong at p 0.9 or higher). Read together with the fact that this path finishes in about 0.3 s, it explains why the usage the repository suggests is “fast path by default, reasoning only when unsure”. nothink_threshold is exactly that switch. This is an interpretation that follows from the option description, not a sentence in which the README says it recommends this.

The premise of the Jev evaluation article was that Jev-style models are fast and cheap because of a structure that does not generate text. Adding reasoning means giving up part of that advantage on purpose. How much accuracy is bought in return is what the tables above show, and whether the exchange is a gain is decided by the difficulty distribution of your items and your latency budget.

The structure on one page — a pointer head produces the probabilities and reasoning runs before it

The “How it works” section of the README explains the input format as follows. The state, the questions and the options are put into the Qwen chat template, the model rolls out a reasoning chain, and after the reasoning end token the questions are appended once more and a decide token is placed. The pointer head projects the hidden state at the decide token into a query and the hidden state at each option closing token into a key, and builds the option scores with a scaled dot product. The final probabilities are the softmax of those scores divided by a temperature fitted on the dev data, and the temperature the model card gives is 1.859.

The point to read in this structure is that the probabilities do not come from generated characters but are computed by the head. The reasoning chain may grow long, but the output probabilities stay fixed as a softmax over as many scores as there are options. The README also records the effect of structural choices. Five rarely used special tokens of the Qwen tokenizer serve as delimiters for the state and questions; replacing them with plain text such as “State” made performance worse, and not repeating the questions after the reasoning also lowered performance.

  • SFT. 2 epochs, 596 steps on 8 GPUs. LoRA r=16 and the pointer head were trained on 19,126 questions drawn from 12 public datasets and synthetic policy data. Half of the questions carry a reasoning chain sampled from the base model.
  • CISPO. Stopped at step 402 of a 624-step schedule. 9,992 reinforcement-learning questions, 8 rollouts per question, temperature 1, a reasoning cap of 2,560 tokens. According to the model card, the reward is the probability of the correct option, discounted by up to 10% for long chains.
  • Stopping point. The README says step 402 keeps the best calibration and dev score. Past it, the head over-sharpens on the saturated reinforcement-learning pool.
  • Calibration. A single temperature is fitted on the dev data.
  • Drafter. A diffusion view of the frozen model. For one question, chain generation goes from 109 tokens per second with graphed greedy decoding to 176 tokens with block 4 (1.6 times) and 193 tokens with block 8 (1.76 times). With eight questions batched, block 4 totals about 960 tokens. The default is block 4, which stays cheap when batched.

The README and the model card state that a from-scratch reproduction matches within noise, and the repository has a script that runs the whole training on 8 GPUs. That command is not copied into this spot. If you try to reproduce it in your own environment, follow the relevant section of the repository directly.

What to read before running it — requirements, options, license

The serving conditions the README gives come first. The requirements are Python 3.12 and a CUDA GPU, and inference is also said to run on an Apple Silicon Mac with 48 GB of memory or more.

  • Mac memory. The bf16 weights are 21 GB and the default caches use another 28 GB, so a 48 GB Mac starts to swap. The README gives an example of serving options that shrink the caches. With fp8 the weights fall to 11.5 GB and thinking runs at about 31 tokens per second.
  • Different wording of the FP8 requirement. The README says GPUs with compute capability 8.9 or higher, while the model card says the FP8 kernel needs Hopper. Whether the two sentences mean the same condition cannot be settled from the documents alone, so check the repository issues and code before serving.
  • Compatibility. The README says requests and responses follow the Jev format, and that the options object is optional and ignored by Jev clients that do not send it. Server-wide defaults are set with serving flags.

The commands that start serving are the two lines from the README quickstart. They come after installing the requirements from the repository, and are copied here as they are.

hf download PostHog/jeeves --local-dir jeeves-weights
                    python -m inference.serve --model jeeves-weights --drafter jeeves-weights/drafter_k4.safetensors --port 8009

The items of the options object given with each request are defined in the README as follows.

OptionDefaultEffect
thinktrueWhen set to false, the model answers from the prompt alone (about 0.3 s)
max_think2560Truncates each question reasoning chain at this many tokens and then answers
nothink_thresholdnullAnswers without thinking when the confidence of the no-think path is at least this value

The license is read in separate layers because the wording differs between documents. The README badge says MIT, while the model card says the weights carry the Apache-2.0 license inherited from Qwen3.5-9B and the Jeeves code is MIT. The README states that each public dataset used in training stays under its own license. The GeekNews summary says the weights, training code and datasets are released under MIT, which blurs the distinction. Before distribution or commercial use, look at the three layers of weights, code and data separately.

Before carrying this to your own work — what these numbers do not answer

The repository figures are results of training on twelve public datasets plus synthetic policy data and measuring on test items from the same sources. There is no guarantee inside them that the same gain will appear on your own business documents. The things to reconcile with your own data before carrying it over are as follows.

  • Re-measure with labels from your own domain. On a correct-answer sample built from business documents, score the Jev path, no thinking, the compromise setting and full thinking on the same items. The Jev column in the README is a value Kev published, so it is not used as a baseline as it is.
  • Look at language. The evaluation was limited to English inputs, so inputs in Korean or other languages are outside the repository figures.
  • Measure latency as a distribution. A p90 of 17.1 s bears directly on timeout and retry design. Do not set a budget from the median alone.
  • Draw the max_think curve. What the repository reports is one point, 768. Try several values on your own sample and find where accuracy bends.
  • Separate knowledge-type items from judgment-type items. For items where background knowledge decides the answer, the repository itself says it trails Jev. If your work has many of them, keep the original path.
  • Compare with the fallback structure. The README problem statement assumes that a pipeline uses a Jev-style front stage together with a reasoning-model fallback. Whether Jeeves replaces that whole fallback or takes only part of it at the entrance is decided by the difficulty distribution of your traffic.

If a one-line rule is drawn from these figures, it is this (an interpretation based on the back-calculation). Work with mostly easy items and a tight latency budget fits no thinking or the compromise setting, and work where recovering hard items matters and a few seconds of latency is tolerable fits full thinking. Which one applies is decided by the difficulty of your own item set.

What could not be confirmed

  • Who created JevBench and how its items are composed. The README and the model card say only that there are three public tiers and a sealed judge tier.
  • Independent third-party reproduction or evaluation. Measurements outside the repository are outside the sources of this article. The reproduction statement in the model card is also the repository own.
  • Confidence intervals and variance across repeated runs for the accuracies. They are not in the README, so the statistical weight of the 231-item and 111-item gaps cannot be gauged.
  • Whether the latency table is for a serving setup with the drafter turned on. The table states only the H100 fp8 condition.
  • Performance on inputs other than English. The documents say only that the evaluation was limited to English.
  • A direct measurement of Jev on the same items and the same hardware. The Jev column is the figure Kev publishes, and the original text in the Kev repository was not opened for comparison.
  • Which of the two FP8 requirements (8.9 or higher versus Hopper) is correct. The wording of the two documents differs.
  • The body of the external article the README cites as the Jev design document. Only the link was checked and the body was not opened for comparison.
