databow 与 ADBC 分析 - 用列式零拷贝查询多个数据库的命令行工具

Apache Arrow 打造的 ADBC 标准如何绕开 ODBC、JDBC 的行式瓶颈 - 与 psql、usql、DuckDB CLI 有何不同

2026-07-06 开发/基础设施

引言：为什么现在要关注 databow 与 ADBC

做数据工程或分析的人都熟悉这样的场景：生产库用 PostgreSQL，分析用的数据仓库是 Snowflake 或 BigQuery，本地实验又用 DuckDB 或 SQLite。哪怕只想跑一条查询，也得每次打开不同的客户端、重新记住不同的连接语法，结果格式还各不相同。截至2026年7月，正面瞄准这个问题的工具是 databow。这款在 GeekNews 上被介绍的工具，是 Columnar 公司用 Rust 打造的命令行 SQL 客户端，运行在 Apache Arrow 项目的标准 ADBC(Arrow Database Connectivity) 之上。

比起 databow 本身，本文更看重它背后的 ADBC 这个思路。CLI 工具来来去去，但把每个数据库各自不同的协议统一成列式 Arrow 数据这个想法，在我看来会在未来几年里持续影响整个数据工具生态。作为一个经常在命令行里跨多个数据库工作的人，我想冷静地梳理这款工具与 psql、usql、DuckDB CLI 到底有什么根本区别，以及它现在是否已经能投入实际工作。

1. ADBC 是什么 - Apache Arrow 的数据库连接标准

1.1 为何而生

ADBC 是 Apache Arrow 项目在2023年初发布的 API 标准。目的很简单：在从不同数据库取数据时，不再绕经各个客户端各自不同的协议，而是提供一套直接用 Arrow 列式格式交换数据的统一 API。Arrow 本身是为了跨语言、跨进程边界共享数据而设计的内存列式格式，可以做到无需复制；ADBC 相当于把这套 Arrow 生态延伸到了数据库连接这一层。

1.2 与 ODBC、JDBC 的根本区别

ODBC 和 JDBC 几十年来一直是数据库连接的事实标准，但二者都是按行(row)设计的。JDBC 的 API 本身就假定按行取值，要高效对接 Arrow 这类列式格式在结构上很困难。ODBC 靠块游标支持批量读取，情况略好，但用整数标志位表示 null 这类细节规约，与列式数据并不契合，需要额外的转换开销。ADBC 从一开始就按列式设计，绕开了这个问题。对于分析查询这类需要整批拉取海量行的工作负载，核心收益就是省去了先打包成行、再拆回列的往返开销。不过 ADBC 并不是要完全取代 ODBC、JDBC——正如 Apache Arrow 团队自己所说，ADBC 更像是专为大规模列式读取与写入设计的补充方案，而事务处理这类常规工作负载仍然依赖现有标准。

1.3 与 Flight SQL 的关系

与 ADBC 经常一起被提到的是 Flight SQL。Flight SQL 是面向数据库开发者的客户端-服务器协议，而 ADBC 是包含该协议在内、把多种数据库客户端技术统一封装成一套 API 的应用层标准。也就是说，一个数据库只要实现了 Flight SQL，就能同时支持 ADBC、JDBC、ODBC 客户端。Snowflake 和 DuckDB 在 ADBC 推出后几个月内就采纳了它，部分案例报告称结果读取时间缩短了90%以上（这些数字来自厂商和社区报告，实际效果需要在各自环境中重新验证）。

2. 认识 databow - 构建在 ADBC 之上的 Rust CLI

2.1 这是一款什么样的工具

databow 是 Columnar 开发、以 Apache-2.0 许可发布的命令行工具。它提供支持命令历史与 SQL 语法高亮的交互式 shell、能自动调整列宽的对齐表格输出，以及把结果直接导出为 JSON、CSV、Arrow IPC 文件的功能。交互模式和非交互(单次查询)模式都支持，既方便嵌入脚本，也方便手动探索。

2.2 安装与基本用法

安装方式有两种：uv tool install databow 或 cargo install databow。以 DuckDB 为例，先用 dbc install duckdb 获取对应的 ADBC 驱动，再用 databow --driver duckdb 打开交互式 shell，或直接用 databow --driver duckdb --query 'SELECT 42 AS the_answer' 执行单次查询。用 --file 读取 SQL 文件、用 --output 把结果落到文件，这套流程对用过 psql 或 usql 的人来说并不陌生。唯一的区别在于，底层传递的数据是 Arrow 列式批次，而不是行。

3. 实务价值 - 为何对数据工程师、分析师重要

3.1 日常需要在多个数据库间切换的人

在我看来，databow 这类工具真正的需求来自那些在同一个项目里反复穿梭于不同数据库引擎，做探索、验证、迁移的人。从生产环境的 Postgres 抽样、接到本地 DuckDB 里查看、再和 Snowflake 入库前的格式核对，这类工作很常见。在这种流程里，每次切换客户端都要重新记连接字符串、重新适应输出格式，这笔成本比看上去要大。仅靠一个 CLI、一套 shell 语法就能穿梭于多个引擎之间，本身就能降低上下文切换的成本。

3.2 列式零拷贝带来的实际收益

性能收益不是抽象的说辞，而是取决于具体的工作负载。如果是把成百万行数据抽出来交给 pandas 或 Polars 这类列式分析工具，一开始就以 Arrow 格式接收并直接传递下去，肯定比先按行接收再转换成列要快。反过来，像几行的事务查询或单条更新这类原本就没有列式收益的工作负载，ADBC 的优势根本感受不到。也就是说，databow 的价值在把大量分析数据传递给其他列式工具的流水线中才会被放大。

4. 仍然有限的驱动生态 - 冷静看待

4.1 各驱动成熟度并不均衡

接下来要提醒的一点。翻看 ADBC 驱动文档会发现，各驱动的成熟度差异很大。Snowflake 驱动标注为 Stable，是目前最值得信赖的一个。PostgreSQL 驱动通过 C/C++、C#、Go、R、Ruby、Rust 等多语言绑定已经达到可用水平。相比之下，BigQuery 的 C# 驱动仍处于 Beta、Go 驱动处于 Experimental 阶段，还不稳定；官方文档也明确写明 SQLite 驱动只是开发过程中使用的参考实现，尚未做优化。

4.2 换算成实务风险

也就是说，某个数据库存在 ADBC 驱动，并不代表可以直接上生产环境。像 Snowflake 这样成熟的驱动可以放心使用，但还处于 Beta、Experimental 阶段的驱动，在边缘情况下可能出现预料之外的行为。databow 的官方示例集中在 DuckDB 上，这本身也是当前生态重心所在的一个信号。这是新标准难以避免的阶段性问题，但眼下更该问的不是能不能用，而是这个具体驱动在我的数据库上到底成熟到什么程度，需要逐一确认。

5. 与 psql、usql、DuckDB CLI 的比较

5.1 psql - 经过验证但局限于单一数据库、行式

psql 作为 PostgreSQL 专属客户端，在稳定性和功能完整度上仍是基准。但它从一开始就不是为多数据库设计的，协议也是行式的。如果只用 Postgres，它现在依然接近最佳选择。

5.2 usql - 通用但并非列式

usql 是受 psql 启发做出的通用 CLI，通过 Go 语言的 database/sql 接口覆盖了 PostgreSQL、MySQL、Oracle、SQL Server、SQLite，乃至 ClickHouse、CockroachDB、Presto、Trino、BigQuery。它和 databow 一样，目标是在一个 shell 里穿梭多个数据库，但内部其实是直接封装各数据库自己的标准驱动(通常是行式)。也就是说，在把多个数据库统一到一套体验里这一点上，usql 目前覆盖面更广，但在列式零拷贝传输这个维度上，它和 databow/ADBC 的设计理念本身就不同。

5.3 DuckDB CLI - 拉进自己的引擎计算

DuckDB CLI 可以通过 postgres_scanner、mysql_scanner 这类扩展连接外部数据库，执行跨库查询。但这种方式的本质是把多个数据库的数据拉进 DuckDB 自身的分析引擎里计算。DuckDB 是强大的进程内分析引擎，这让它在本地分析上非常出色，但方向上不同于 ADBC——ADBC 是把该数据库自身原生执行的结果直接以列式接收过来。选择哪种取决于目标是用 DuckDB 计算，还是把各数据库自己的结果原样快速搬出来。

5.4 databow/ADBC - 以零拷贝搬运原生结果

总结来说，databow 与另外三者的不同之处在于，它接收的是每个数据库引擎已经算好的结果，且不打包成行，而是保持 Arrow 列式批次的原样。如果说 usql 的重心在体验统一，DuckDB CLI 的重心在计算引擎的整合，那么 databow/ADBC 的重心就在传输层的效率。与其说这三者是竞争关系，不如说它们各自解决的是不同的问题。

6. 该在什么时候用什么

我自己的实务判断标准是这样的。如果只用一种数据库，该数据库的原生客户端(如 psql)仍是更安全的默认选择。如果要在多个数据库间切换，且优先考虑统一体验和更广的驱动覆盖面，usql 目前更实用。想在本地接入多个数据源快速分析，DuckDB CLI 更合适。而如果核心工作是从多个数据库中取出大量列式数据，并直接流入 pandas、Polars、Arrow 这类流水线，那才是真正值得认真考虑 databow 与 ADBC 的场景——但前提是先确认目标数据库的 ADBC 驱动是否已到 Stable 阶段。

结论

databow 本身还是个小工具。但它背后的 ADBC，是一个方向清晰的标准——把数据库连接从行式重新设计为列式。Snowflake、DuckDB 迅速跟进，很可能正是因为这个方向切中了分析工作负载的真实瓶颈。不过截至2026年7月，各数据库的驱动成熟度差异仍然很大，还处于早期阶段。现在没有理由抛弃 psql、usql 转投 databow，但如果你日常运维的流水线需要频繁搬运大量列式数据，这是一个值得持续关注的方向。
