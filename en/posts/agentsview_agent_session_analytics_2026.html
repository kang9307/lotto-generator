AgentsView Launches - A Local Dashboard That Indexes Claude Code, Cursor, and Codex Sessions for Search and Cost Tracking

In an era of running several AI coding agents in parallel, how a local-first open-source tool tackles session fragmentation and cost opacity

Jul 14, 2026 Dev & Infra

Intro: More Agents, More Scattered Memory

By mid-2026, it is not the exception but the default for a single developer to bounce between several AI coding agents in a single day. One survey reported that 59% of developers run three or more AI coding tools in parallel, and 65% use at least two of them daily. A day where you send a refactor to Claude Code, take an inline suggestion from Cursor, and hand off a separate task to Codex, Gemini CLI, or OpenCode has become ordinary. This is a natural division of labor - each tool is good at one thing - but the cost is that questions like "which agent did I ask to fix yesterday's bug, and how exactly did I phrase it" or "what did I actually spend on AI tools this month" have gotten harder to answer, not easier.

The open-source project stepping into this gap is AgentsView. Introduced on hada.io in July 2026, it gathers the local session logs left behind by multiple AI coding agents - Claude Code, Codex, Cursor, Gemini CLI, OpenCode, and more - into one place, adding conversation search, token and cost statistics, activity analysis, and file-change tracking. This piece works from the public documentation in the GitHub repository (kenn-io/agentsview) to look at what the tool actually does, why a tool like this matters in an era of running multiple agents in parallel, what local collection means for privacy, how it compares to adjacent approaches, and its practical use and limits - all as of July 2026.

1. What Is AgentsView? A Local-First Session Analytics Dashboard

1.1 Forty-Plus Agents Into a Single Index

The list of agents AgentsView recognizes is not short. It covers major tools like Claude Code, Codex, Cursor, GitHub Copilot CLI, Windsurf, and Zed; specialized tools like Devin CLI, OpenCode, Gemini CLI, DeepSeek TUI, and Qwen Code; and lesser-known ones like Aider (opt-in per repository), Forge, gptme, OpenHands, Kiro, and Mistral Vibe - more than 40 in total. Each agent keeps its own session storage path (Claude Code, for instance, uses ~/.claude/projects/), and AgentsView parses each of these paths and merges the results into a single local SQLite database.

1.2 Four Core Features - Search, Cost, Activity, Change

The core functionality boils down to four things. First, unified search: FTS5-based full-text search lets you find conversation content across every agent at once, and optionally wiring up an embeddings endpoint enables semantic search as well. Second, token and cost aggregation: it references LiteLLM's pricing data to compute per-session, per-model token usage and cost, supports an offline fallback, and even accounts for prompt-cache-aware cost calculation - claiming query speeds 100 times faster than re-parsing files each time. Third, activity analysis: sessions are automatically classified into archetypes such as automation, quick, standard, deep, and marathon, and session length, context-window usage, and tool-call distribution are visualized. Fourth, file-change tracking: a feed shows which files an agent recently modified. Results can be exported to HTML or a GitHub Gist.

1.3 Architecture - A Single Go Binary With Optional Team Sharing

The backend is written in Go (roughly 83.8% of the codebase), the frontend in Svelte 5 and TypeScript, and a Tauri-wrapped desktop app is also available. The default store is a writable SQLite database with FTS5 indexing; if you want to share with a team, you can optionally push read-only into PostgreSQL, and for larger-scale analytics, mirror into DuckDB. Installation runs via curl -fsSL https://agentsview.io/install.sh | bash, a Homebrew cask, or a Docker image (ghcr.io/kenn-io/agentsview), and you can run it in the foreground with agentsview serve or as a daemon that auto-syncs every 15 minutes. The web UI opens on 127.0.0.1:8080 by default. It is licensed under MIT.

2. The Root Problem - Three Pains of the Multi-Agent Era

2.1 Session Fragmentation - Memory Split Across Tools

The first pain AgentsView targets is session fragmentation. A 2026 survey found GitHub Copilot still holds the widest reported user base (about 67.9%), with Claude Code close behind (about 62.9%) and OpenAI Codex already at 34.5%. Running multiple tools at once has become the norm rather than the exception. The problem is that each agent keeps its own session files, format, and UI, so confirming "which agent I asked to do this refactor last week, and how" means opening each tool one by one. The more tools you add, the more finely this memory gets shredded.

2.2 Cost Opacity - Spend You Cannot See

The second pain is cost. Multiple reports note that agents burn through tokens far faster than an ordinary chatbot because each planning-execution-verification cycle re-feeds context at every step. One report put the average monthly spend for a developer using an agentic coding tool at $400-$1,500, with extreme cases exceeding $4,000 within days. Another described a 35-engineer startup running Claude Code, Cursor, and a custom bug-triage agent that received an $87,000 monthly bill, and coverage of Microsoft finding per-engineer costs of $500-$2,000 a month and scaling back some Claude Code licenses in response. With each tool's dashboard living separately, this full picture rarely comes into view.

2.3 Hard to Trace What Was Asked, and When

The third pain is retrospective review and audit. Answering "why was this section written this way" in a code review means tracing back exactly what prompt was given to which agent, and when sessions are scattered across tools, that tracing-back becomes work in itself. At the team level, it also means there is no evidence base to explain "how much, and where, did AI actually contribute this sprint." Fragmentation, cost opacity, and the inability to look back all trace to the same root: closed logs per agent, with no view that cuts across them.

3. The Visibility AgentsView Adds - Where the Value Sits

3.1 A Searchable Shared Memory

AgentsView's primary value is simple. Putting every agent's conversation log behind a single search box turns "what did I ask back then" from a job of hopping between apps into typing one query. FTS5 full-text search handles exact phrases, while the optional embedding-based search handles fuzzier, meaning-based queries like "what was that auth refactor again."

3.2 Cost and Tokens on One Screen

The second value is cost visibility. Instead of reconciling bills scattered across tools, you can see tokens and cost by session, model, and period on a single screen, based on LiteLLM's pricing data. That the calculation accounts for prompt caching matters, too - a session with frequent cache hits and one that re-burns the full context every time have genuinely different cost structures, and this approximates that difference more accurately than simple token multiplication.

3.3 Activity Analysis and Change Tracking - Seeing Patterns

The third value is turning activity into types that surface patterns. Classifying sessions as automation, quick, standard, deep, or marathon makes observations possible, like "this project is mostly quick sessions, except this one module keeps racking up marathon sessions." The recently-edited-files feed lets you skim where an agent actually touched code over the past few days without opening a code review. This kind of typing surfaces accumulated usage patterns that are hard to see from any single session log - a different tier of value from a plain log viewer.

4. What Local Collection Means for Privacy

4.1 Localhost by Default, No External Transmission

AgentsView leads with no account required and session data staying on your own machine by default. Its server binds only to 127.0.0.1 by default and does not transmit session content externally. Because this is a tool that handles logs retaining your actual code and prompts, this default is not a minor design choice. Had it been built as a cloud dashboard you upload sessions to, an entire internal codebase transiting a vendor's servers would have become a new problem.

4.2 Minimal Telemetry, With an Off Switch

That said, it is not fully silent. Anonymous information like app version, OS, and CPU is sent to PostHog at startup and every 24 hours. This differs in kind from session content, but it is worth knowing it can be disabled via the AGENTSVIEW_TELEMETRY_ENABLED=0 environment variable - organizations with strict security policies should check this option.

4.3 Team Sharing Still Stays Inside Your Own Infrastructure

Even when you want to share with a team, AgentsView offers PostgreSQL inside your own infrastructure as the option, not a vendor cloud. Because it is structured as a read-only push from SQLite, the answer to "where does the data live" remains your own server even in a team-shared setup. This sits on the same axis as the data-sovereignty logic covered in my analysis of the self-hosted AI agent OpenTag.

5. Comparing Adjacent Approaches - What Overlaps, What Differs

5.1 Built-In Agent Logs - Present, But Locked In

The most basic alternative is the history each agent already provides. Claude Code and Cursor both leave their sessions somewhere and let you browse them through their own UI or CLI. The problem is that this is locked inside one tool. The moment you use two or three tools, the feature of "searching across everything" simply does not exist.

5.2 Similar Session-Management Tools - Overlapping, Differently Focused

AgentsView is not the only attempt here. Mantra gathers Claude Code, Cursor, Gemini CLI, and Codex sessions together too, but its strength is presenting the conversation log as a replayable timeline you scrub through to watch code evolve, plus centralized MCP-server and permission management and automatic secret detection that cleans up API keys in one click. coding_agent_session_search is a local TUI/CLI search tool spanning 11-plus providers, and Agent Sessions similarly focuses on session management for Codex, Claude, OpenCode, Cursor, Copilot, and more. Lined up against these, AgentsView's position becomes clear: next to tools strong on search and replay, it leans more analytics-oriented, pairing cost/token analysis with team-shareable database backends (PostgreSQL, DuckDB).

5.3 LLM Observability Platforms - A Different Product Category

Tools like LangSmith, Helicone, and Langfuse might come to mind, but they solve a fundamentally different problem. These platforms are production observability tools that instrument API traces inside an LLM application you built, via an SDK. LangSmith bills per trace (a free tier of 5,000 traces/month, then paid tiers), and Helicone bills per request while computing cost across 300-plus models at the gateway layer. AgentsView, by contrast, has no target application to instrument at all - it simply reads and indexes, after the fact, the session log files that coding-agent CLIs already write to local disk. Industry consensus roughly holds that Helicone suits under $30K/month in LLM spend, Langfuse the $30K-$200K range, and LangSmith organizations above that with deep LangGraph investment - but that entire spectrum presumes "API traffic from a product I built" to begin with. AgentsView starts from a different premise: "the coding agent I personally use."

5.4 Cost-Focused Tools - Concentrated on Spend Management

Tools like LMSpend, DevOS, and CodeBurn concentrate more heavily on the single axis of cost - team-level spend tracking, budget alerts, finance-ready exports. These tend to be strong on spend management but comparatively shallow on conversation search or session replay. AgentsView sits closer to a generalist across this spectrum, bundling search, cost, activity, and change tracking into one tool.

6. Practical Use - Team Cost Allocation, Prompt Retrospectives, Audit

6.1 Team Cost Allocation

For a team where different members use different agents, syncing SQLite to PostgreSQL read-only gathers session and cost data for the whole team into one store. That lets you present evidence in a finance report or sprint retro for "how much did we actually spend on AI tools this sprint, and where did it concentrate - which project, which model."

6.2 Prompt Retrospectives

There is value at the individual level too. Searching back later to compare a refactor that went well against one that did not lets you trace which prompt patterns produced better results. That means having an immediate answer of "here is exactly what I asked it to do" ready for "why was this written this way" - genuinely useful for both code review and retrospectives.

6.3 The Limits as an Audit Tool - Not a Governance Gate

Using it for audit purposes calls for a clear boundary, though. AgentsView indexes what already happened, after the fact - it is not a gate that blocks a specific action beforehand or enforces a budget in real time. If you need controls like "this request cannot execute without approval" or "this team gets auto-cut-off once it exceeds this month's budget," you need a separate proxy-gateway layer that sits between engineers and model providers, logging, attributing, and controlling every request. It is more accurate to understand AgentsView as the stage before that - a visibility layer that makes what happened visible.

7. Limits and Caveats

7.1 Retrospective Analysis, Not Real-Time Control

As noted above, AgentsView reads logs that have already accumulated. Alerting the moment costs spike, or blocking a request outright, is not this tool's job. If you need real-time budget enforcement, you must design a separate gateway or proxy layer alongside it.

7.2 Pricing Accuracy Depends on an External Source

Because cost calculation depends on LiteLLM's pricing data, in an environment where model prices change often, offline fallback data can drift slightly from an actual bill. Decisions that hinge on an exact figure - budget approval, invoice reconciliation - still need a verification step against the vendor's official billing record.

7.3 Sensitive Data Still Accumulates in the Local Database

Keeping everything local blocks external leakage, but the possibility that session logs themselves mix in API keys, internal URLs, or customer data does not go away. AgentsView appears to ship with no built-in feature equivalent to Mantra's automatic secret detection and cleanup, so it is safer to add a separate sensitive-data check before sharing or backing up the indexed database file with a team.

7.4 Agent Log Format Changes Demand Ongoing Maintenance

Supporting 40-plus agents also means keeping pace with that many log formats. When an agent vendor changes how it stores sessions, the parser has to be updated in turn, and this maintenance burden depends on the vitality of the open-source community around it. Before adopting it, it is worth checking the repository's recent commit frequency and issue-response speed.

8. Conclusion - Three Things You Can Do Today

The direction AgentsView points to is clear: as the number of AI coding agents grows, the visibility layer sitting above individual tool performance matters more, not less. Simply gathering session search, cost aggregation, and activity analysis in one place makes tracing "what did I ask, and when" dramatically easier, and its local-first design means you do not have to hand code over to a vendor's cloud to gain that visibility. Still, be clear that this is a retrospective analysis tool, not a real-time governance tool, and that audit or budget-enforcement purposes call for a separate layer.

8.1 Audit Your Own Agent Usage This Week

Install AgentsView or a similar tool and check first what you actually spent on which agent over the past month. Actual data often diverges from what you assumed.

8.2 If You're a Team, Design Cost Allocation and Audit Separately

Secure cost visibility with a tool like AgentsView, but if you need budget enforcement or request blocking, evaluate a proxy gateway separately. Mistaking the two layers for one leaves you with a dashboard that has no actual controls attached.

8.3 Set Up a Sensitive-Data Check First

Before indexing session logs, check first whether API keys or internal URLs might be mixed into them. It is safer to add one more filtering pass before sharing or backing the data up with a team.
