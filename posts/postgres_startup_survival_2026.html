스타트업의 Postgres 생존 가이드 - 커넥션 고갈부터 파티셔닝까지

커넥션 풀링·인덱스·autovacuum·무중단 마이그레이션·백업 리허설까지, 실무에서 실제로 부딪히는 함정과 대응을 정리한다

2026-07-24 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: Postgres는 왜 스타트업을 몇 번씩 놀라게 하는가

스타트업의 데이터베이스는 보통 한 번에 무너지지 않는다. 초기에는 Postgres 하나로 몇 달, 심하면 1-2년을 아무 문제 없이 버틴다. 트래픽이 어느 선을 넘는 순간부터 이야기가 달라진다. 배포 직후 커넥션이 갑자기 바닥나거나, 어제까지 멀쩡하던 쿼리가 오늘 갑자기 5초씩 걸리거나, 새벽에 autovacuum이 CPU를 다 잡아먹거나, 컬럼 하나 바꾸는 마이그레이션이 서비스를 통째로 멈춰 세우는 식이다. 하나같이 처음 겪을 땐 원인을 짐작하기 어렵고, 대부분 사후에야 "아, 이건 초기에 알았어야 했다"는 걸 깨닫는 것들이다.

이 글은 그런 함정들을 실무 관점에서 순서대로 정리한 생존 가이드다. 뉴스나 신제품 소개가 아니라, 실제로 Postgres를 운영하며 부딪히는 문제들 - 커넥션 고갈, 인덱스, N+1 쿼리, autovacuum과 팽창, 잠금과 무중단 마이그레이션, 백업과 복구, 모니터링, 스케일 순서, 매니지드 대 셀프호스팅 판단 - 을 개념과 명령어 수준까지 구체적으로 다룬다. 정확성을 위해 공식 문서와 실무 레퍼런스를 교차 확인했으며, 2026년 7월 기준 정보로 정리했다.

1. 커넥션 고갈 - PgBouncer와 커넥션 풀링

스타트업이 가장 먼저 만나는 함정은 대개 커넥션 고갈이다. Postgres의 기본 max_connections는 100 수준으로, 백엔드 인스턴스가 여러 대로 늘거나 서버리스·오토스케일링 환경에서 인스턴스마다 커넥션 풀을 따로 유지하면 순식간에 소진된다. 커넥션 하나하나는 Postgres 쪽에 프로세스를 하나씩 띄우는 비용이라, 숫자가 늘수록 컨텍스트 스위칭과 메모리 부담도 함께 커진다.

1.1 애플리케이션 풀만으로는 부족한 이유

ORM이나 드라이버가 제공하는 커넥션 풀은 인스턴스 하나 기준으로만 작동한다. 인스턴스가 10대고 각각 풀 크기를 20으로 잡으면, 실제 DB에는 최대 200개 커넥션이 몰릴 수 있다. 여기에 배치 잡, 어드민 콘솔, 모니터링 에이전트까지 더하면 max_connections를 넘기는 건 시간문제다. 애플리케이션 재시작이나 배포 시 커넥션이 한꺼번에 몰리는 "커넥션 스톰"도 흔한 장애 유형이다.

1.2 PgBouncer로 앞단에서 걸러내기

가장 검증된 해법은 애플리케이션과 Postgres 사이에 PgBouncer 같은 커넥션 풀러를 두어, 애플리케이션이 보는 커넥션 수와 실제 DB 커넥션 수를 분리하는 것이다. 트랜잭션 모드(pool_mode = transaction)를 쓰면 커넥션을 트랜잭션 단위로만 짧게 붙잡았다 반납하므로 훨씬 적은 DB 커넥션으로 많은 애플리케이션 커넥션을 감당할 수 있다.

[databases]
mydb = host=127.0.0.1 port=5432 dbname=mydb

[pgbouncer]
listen_port = 6432
pool_mode = transaction
max_client_conn = 1000
default_pool_size = 20
reserve_pool_size = 5

1.3 트랜잭션 모드의 함정

트랜잭션 모드는 커넥션을 트랜잭션이 끝날 때마다 다른 클라이언트에게 재할당하기 때문에, 세션 상태를 가정하는 코드와 충돌한다. 트랜잭션으로 감싸지 않은 SET 문, 세션 단위 prepared statement, advisory lock처럼 "이 커넥션은 계속 나만 쓴다"는 전제를 깔고 있는 기능은 트랜잭션 모드에서 예상 밖의 동작을 낳는다. 이런 기능을 쓰는 코드가 있다면 해당 경로만 세션 모드로 분리하거나, 코드를 트랜잭션 모드에 맞게 고쳐야 한다. 풀 크기는 무작정 키우기보다 DB 서버의 CPU 코어 수를 기준으로 잡고, 클라이언트 대기 시간(cl_waiting, 평균 대기시간) 지표를 보면서 조정하는 편이 안전하다.

2. 인덱스 부재와 과다 - 균형을 잡는 법

인덱스는 스타트업이 가장 흔히 양극단으로 실수하는 영역이다. 아예 안 만들거나, 습관적으로 모든 컬럼에 다 만든다.

2.1 인덱스가 없을 때 벌어지는 일

WHERE, JOIN, ORDER BY에 자주 등장하는 컬럼에 인덱스가 없으면 옵티마이저는 테이블 전체를 훑는 순차 스캔(Seq Scan)을 택한다. 데이터가 적을 때는 체감이 안 되지만, 테이블이 수십만-수백만 행으로 커지면 같은 쿼리가 갑자기 몇 초씩 걸리기 시작한다. 이런 변화는 트래픽 증가와 함께 서서히 오기 때문에 "어느 날 갑자기 느려진 것"처럼 느껴지지만, 사실은 테이블이 임계점을 넘긴 것뿐이다.

2.2 인덱스 과다의 대가

반대로 인덱스를 지나치게 많이 걸면 매 INSERT·UPDATE·DELETE마다 관련 인덱스를 함께 갱신해야 해서 쓰기 지연이 늘고 저장 공간도 그만큼 늘어난다. 특히 "혹시 몰라서" 만들어 둔 인덱스가 실제로는 한 번도 쓰이지 않는 경우가 흔하다. pg_stat_user_indexes의 idx_scan 컬럼으로 실제 사용 빈도를 확인해 안 쓰는 인덱스는 정리하는 것이 좋다.

SELECT relname AS table_name, indexrelname AS index_name, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY relname;

2.3 복합 인덱스 설계 원칙

여러 컬럼을 함께 조회하는 쿼리가 많다면 단일 컬럼 인덱스를 여러 개 만드는 것보다 복합(다중 컬럼) 인덱스 하나가 더 효율적일 때가 많다. 이때 컬럼 순서가 중요한데, 등호(=) 조건으로 쓰이는 컬럼을 앞에, 범위(>, BETWEEN) 조건이나 정렬에 쓰이는 컬럼을 뒤에 두는 것이 기본 원칙이다. 신규 인덱스는 운영 중인 테이블이라면 반드시 CREATE INDEX CONCURRENTLY로 생성해 테이블 잠금 없이 만들어야 한다.

3. N+1과 느린 쿼리 - EXPLAIN·pg_stat_statements로 잡기

커넥션과 인덱스를 다 챙겨도, 애플리케이션 코드 수준에서 발생하는 N+1 쿼리는 별개의 문제로 남는다.

3.1 N+1 쿼리 알아채는 법

N+1은 목록 하나를 가져온 뒤 항목마다 관련 데이터를 별도 쿼리로 하나씩 조회하는 패턴이다. ORM을 쓸 때 특히 흔하다. 이 문제는 로그만 봐서는 눈에 잘 안 띈다. 각 쿼리 자체는 1ms 미만으로 빠르기 때문이다. 하지만 pg_stat_statements로 보면 같은 패턴의 쿼리가 짧은 시간에 수만 번씩 호출된 흔적이 뚜렷하게 나타난다. "빠른 쿼리인데 호출 횟수가 비정상적으로 많다"는 것이 N+1의 신호다.

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY calls DESC
LIMIT 20;

3.2 EXPLAIN ANALYZE 읽는 법

느린 쿼리 후보를 찾았다면 EXPLAIN (ANALYZE, BUFFERS)로 실제 실행 계획과 소요 시간을 확인한다. 계획에서 Seq Scan이 큰 테이블에 등장하거나, 추정 행 수(estimate)와 실제 행 수(actual)가 크게 어긋나거나, Buffers: shared read 값이 크면(디스크 I/O가 많다는 뜻) 튜닝 여지가 있다는 신호다.

EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.total, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at > now() - interval '7 days';

3.3 총 실행 시간 vs 평균 실행 시간

튜닝 우선순위는 "가장 느린 쿼리"가 아니라 "총 실행 시간이 가장 큰 쿼리"부터 잡는 것이 효율적이다. 1초짜리 쿼리가 한 번 도는 것보다, 10ms짜리 쿼리가 하루 100만 번 도는 쪽이 DB 전체 부하에 더 크게 기여하는 경우가 많다. pg_stat_statements의 total_exec_time 기준 정렬이 이런 우선순위를 잡는 데 유용하다.

4. autovacuum·테이블 팽창(bloat)·트랜잭션 ID 랩어라운드

스타트업 팀이 가장 늦게 깨닫는 함정이지만, 방치하면 가장 심각한 결과로 이어지는 영역이다.

4.1 MVCC와 죽은 튜플

Postgres는 MVCC(다중 버전 동시성 제어) 방식이라 UPDATE·DELETE가 기존 행을 즉시 지우지 않고 이전 버전(죽은 튜플)으로 남긴다. autovacuum이 주기적으로 돌며 이 죽은 튜플을 회수해야 테이블과 인덱스가 부풀지 않는다. autovacuum이 밀리거나 설정이 워크로드에 안 맞으면 테이블 크기가 실제 데이터보다 훨씬 커지는 팽창(bloat)이 쌓이고, 같은 쿼리도 더 많은 페이지를 읽어야 해서 느려진다.

4.2 테이블별 튜닝이 정석

기본 autovacuum_vacuum_scale_factor(기본 20%)는 대형·고빈도 쓰기 테이블에는 너무 느슨하다. 행이 수백만 개인 테이블에서 20%가 바뀌어야 vacuum이 도는 건 너무 늦다. autovacuum을 통째로 끄는 대신, 문제가 되는 테이블만 ALTER TABLE로 개별 설정을 낮추는 것이 정석이다.

ALTER TABLE events SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_cost_limit = 2000
);

4.3 트랜잭션 ID 랩어라운드라는 벼랑

Postgres의 트랜잭션 ID(XID)는 32비트라 약 40억 개에서 순환(wraparound)한다. 오래된 행 버전은 XID 나이가 일정 임계값을 넘기 전에 freeze되어야 한다. XID 나이가 약 16억을 넘으면 경고 로그가 쌓이고, 18억을 넘으면 강제 vacuum이 걸리며, 약 20억에 근접하면 Postgres가 데이터 손상을 막기 위해 스스로 신규 쓰기를 거부하기 시작한다. 이 지점까지 가면 서비스 전체가 멈추는 심각한 장애가 된다. track_counts가 켜져 있어야 autovacuum이 정상 작동하므로, 이 설정을 임의로 끄지 않는 것이 기본이다. 다음 쿼리로 각 테이블의 XID 나이를 주기적으로 확인하는 습관을 들이는 게 좋다.

SELECT relname, age(relfrozenxid) AS xid_age
FROM pg_class
WHERE relkind = 'r'
ORDER BY xid_age DESC
LIMIT 10;

5. 잠금과 무중단 마이그레이션

스키마 변경은 스타트업이 반복적으로 만나는 함정이다. 초기에는 아무 문제 없이 되던 ALTER TABLE이 데이터가 쌓인 뒤에는 서비스를 멈추는 사고로 바뀐다.

5.1 어떤 DDL이 위험한가

테이블 전체를 다시 써야 하는 작업 - 컬럼 타입 변경, 인덱스 없는 CREATE INDEX, 오래된 Postgres 버전에서의 NOT NULL 추가 - 은 처리 시간 내내 강한 잠금(ACCESS EXCLUSIVE)을 잡는다. 이 잠금이 걸린 동안 다른 쿼리는 대기열에 쌓이고, 대기 중인 쿼리가 많아지면 커넥션까지 함께 고갈되는 연쇄 장애로 번진다. Postgres 11부터는 기본값이 있는 컬럼 추가가 즉시 처리되도록 개선됐지만(값이 카탈로그에 저장되고 읽을 때 적용), 타입 변경처럼 테이블을 실제로 재작성해야 하는 작업은 여전히 무겁다.

5.2 확장-수축(expand-contract) 패턴

안전한 무중단 변경의 표준 패턴은 확장-수축이다. ①새 컬럼을 nullable로 추가해 배포한다. ②애플리케이션이 신규·기존 컬럼에 이중 쓰기를 하도록 배포한다. ③백그라운드 배치로 기존 데이터를 신규 컬럼에 채운다. ④검증 후 읽기를 신규 컬럼으로 전환한다. ⑤일정 기간 지나 문제가 없으면 옛 컬럼을 제거한다. 각 단계를 독립 배포로 나누면 한 단계가 실패해도 롤백이 쉽다.

5.3 세션 타임아웃과 도구

마이그레이션 세션에는 항상 lock_timeout과 statement_timeout을 짧게 걸어, 락 대기가 다른 쿼리를 줄줄이 막는 사태를 조기에 끊어야 한다. 대형 테이블의 온라인 재구성에는 pg_repack(짧은 잠금으로 테이블을 그림자 복사 후 스왑)이나 pgroll 같은 확장-수축 자동화 도구를 검토할 만하다.

SET lock_timeout = '2s';
SET statement_timeout = '5s';
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders (customer_id);

6. 백업·PITR·복구 리허설

백업은 만들어 두는 것보다 복구가 실제로 되는지 확인하는 것이 핵심이다.

6.1 PITR의 구성 요소

시점 복구(PITR, Point-in-Time Recovery)는 pg_basebackup으로 만든 물리적 베이스 백업에 WAL(Write-Ahead Log) 아카이브를 재생해, 사고 직전 임의 시점으로 데이터베이스를 되돌리는 방식이다. 실수로 테이블을 지웠거나 배포 버그로 데이터가 잘못 갱신됐을 때, 스냅샷 복구만으로는 안 되고 "그 사고가 나기 몇 분 전"으로 정확히 되돌려야 하는 상황에 필수적이다.

6.2 pgBackRest 같은 도구

수동으로 pg_basebackup과 WAL 아카이빙을 관리하기보다, 프로덕션에서는 pgBackRest나 WAL-G 같은 전용 도구를 쓰는 것이 표준이다. 증분·차등 백업, 백업 암호화, 병렬 처리, 보관 주기 관리까지 자동화해 준다.

pgbackrest --stanza=mydb --type=full backup
pgbackrest --stanza=mydb --type=diff backup

# 특정 시점으로 복구
pgbackrest --stanza=mydb --type=time \
  --target="2026-07-24 03:00:00" restore

6.3 복구 리허설이 백업보다 중요한 이유

한 번도 복구해 본 적 없는 백업은 성공률을 알 수 없는 백업이나 마찬가지다. 백업 자체가 아니라 "복구"를 산출물로 취급해야 한다. 분기에 한 번이라도 실제로 별도 환경에서 특정 시점 복구를 끝까지 실행해 데이터 정합성을 확인하는 리허설을 정기 일정에 넣어야 한다. RPO(허용 가능한 데이터 손실 범위)와 RTO(허용 가능한 복구 소요 시간) 목표를 먼저 정하고, 그 목표를 실제로 달성할 수 있는지 리허설로 검증하는 순서가 맞다.

7. 모니터링 지표 - 캐시 히트율·대기·복제 지연

장애가 나기 전에 알아채려면 어떤 숫자를 봐야 하는지가 중요하다. 세 가지가 핵심이다.

7.1 캐시 히트율

버퍼 캐시 히트율은 읽기 요청 중 디스크가 아니라 메모리(shared_buffers)에서 처리된 비율이다. 일반적으로 99% 이상이 이상적이고, 80% 아래로 떨어지면 캐시가 작업 세트보다 작거나 쿼리가 불필요하게 많은 디스크 I/O를 유발하고 있다는 신호다.

SELECT
  sum(heap_blks_hit) / nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0) AS cache_hit_ratio
FROM pg_statio_user_tables;

7.2 커넥션 포화와 쿼리 대기

현재 커넥션 수가 max_connections에 얼마나 근접했는지, 그리고 잠금을 기다리는 쿼리가 얼마나 쌓였는지를 함께 봐야 한다. 대기 쿼리가 늘어나는 것은 앞서 다룬 커넥션 고갈이나 무거운 DDL 잠금이 실제로 벌어지고 있다는 선행 신호다.

7.3 복제 지연

읽기 복제본을 쓰고 있다면 복제 지연(replication lag)을 반드시 모니터링해야 한다. 지연이 커지면 복제본에서 읽은 데이터가 오래된 상태일 수 있고, 지연이 너무 커진 채로 primary에 장애가 나면 페일오버 시 데이터 손실 폭도 함께 커진다. Prometheus의 postgres_exporter와 Grafana 조합으로 이 세 지표(캐시 히트율, 대기, 복제 지연)를 한 대시보드에 놓고 임계치 알림을 걸어 두는 것이 실무적으로 충분하다.

8. 스케일 순서 - 수직에서 샤딩까지, 순서를 건너뛰지 말 것

트래픽이 늘 때 곧장 샤딩부터 떠올리는 팀이 있는데, 실무에서는 순서를 지키는 편이 압도적으로 안전하고 저렴하다.

8.1 수직 확장과 커넥션 관리가 먼저

가장 먼저 해볼 것은 인스턴스 사양을 올리는 수직 확장과 앞서 다룬 설정 튜닝, 그리고 PgBouncer를 통한 커넥션 관리다. 대부분의 스타트업 트래픽 규모에서는 이 단계만으로도 상당히 오래 버틴다.

8.2 읽기 복제와 파티셔닝

읽기 비중이 높다면 스트리밍 복제로 읽기 복제본을 늘려 읽기 트래픽을 분산한다. 그다음은 파티셔닝이다. 큰 테이블 하나를 물리적으로 여러 조각으로 나눠 쿼리가 필요한 조각만 스캔하게 한다. 시계열 데이터에는 날짜 기준 RANGE 파티셔닝이, 쓰기를 고르게 분산하고 싶을 때는 테넌트 ID나 사용자 ID 기준 HASH 파티셔닝이 적합하다.

8.3 샤딩은 정말 마지막

샤딩(여러 독립 DB 노드로 데이터를 분산)은 애플리케이션이 어느 샤드에 데이터가 있는지 알아야 하는 구조적 복잡성을 끌어들이는 최후의 수단이다. primary 노드의 CPU·I/O가 튜닝 후에도 계속 70%를 넘거나, 최대 테이블이 수백 GB 이상으로 저장 증가 속도가 감당이 안 되거나, 테넌트별 데이터 격리가 요건이거나, 백업·복구 소요 시간 자체가 감당 불가능한 수준일 때만 검토 대상이 된다. 이 신호들이 나타나기 전에 미리 샤딩부터 설계하는 것은 대개 과잉 엔지니어링이다.

9. 매니지드(RDS·Supabase·Neon) vs 셀프호스팅 판단

이 판단은 기술보다 팀 상황에 좌우된다.

9.1 매니지드가 유리한 경우

DB 운영 전담 인력이 없는 초기 스타트업이라면 백업, 페일오버, 패치, 모니터링을 대신 처리해주는 매니지드 서비스로 시작하는 편이 실패 비용을 줄인다. Neon과 Supabase는 서버리스 과금과 브랜치(개발 DB를 순간 복제) 기능으로 초기 개발 속도에 강점이 있고, RDS는 AWS 생태계 통합과 오래 검증된 운영 도구가 강점이다.

9.2 셀프호스팅이 유리한 경우

비용 최적화가 중요하고, 팀에 Patroni 같은 HA 구성, pgBackRest 백업, 자체 모니터링을 직접 운영할 역량이 있다면 셀프호스팅이 동일 스펙 대비 훨씬 저렴할 수 있다. 다만 이 절감은 운영 부담을 팀이 대신 짊어지는 것과 맞바꾸는 것임을 분명히 인지해야 한다.

9.3 어느 쪽이든 지켜야 할 원칙

어느 쪽을 택하든, 처음부터 특정 벤더의 독점 확장이나 비표준 기능에 깊게 의존하지 않고 표준 Postgres 호환성을 유지하는 것이 중요하다. 그래야 트래픽이 커져 전환이 필요해질 때 마이그레이션 비용이 재작성이 아니라 설정 변경 수준으로 끝난다.

10. 초기에 해두면 좋은 것 - 체크리스트

지금까지 다룬 내용을 초기 세팅 시점에 챙길 수 있는 체크리스트로 정리한다.

  • PgBouncer를 처음부터 애플리케이션과 DB 사이에 둔다. 트래픽이 작을 때부터 붙여 두면 나중에 급하게 도입할 필요가 없다.
  • pg_stat_statements 확장을 처음부터 활성화한다. 나중에 문제가 터진 뒤 켜면 정작 필요한 시점의 데이터가 없다.
  • 대형·고빈도 쓰기 테이블 후보(이벤트 로그, 세션 등)는 미리 autovacuum 테이블별 설정을 계획해 둔다.
  • 스키마 변경은 처음부터 확장-수축 패턴과 CREATE INDEX CONCURRENTLY를 기본 워크플로로 삼는다.
  • PITR이 가능한 백업 체계(pgBackRest 등)를 초기에 구축하고, 복구 리허설을 캘린더에 정기 일정으로 넣는다.
  • 캐시 히트율·커넥션 포화·복제 지연 세 지표를 대시보드 하나에 모아두고 임계치 알림을 건다.
  • RPO·RTO 목표를 문서로 먼저 정의하고, 매니지드냐 셀프호스팅이냐를 그 목표와 팀 역량에 맞춰 결정한다.
  • 대량 시계열·이벤트 테이블은 처음부터 파티셔닝 가능한 스키마(날짜 컬럼 등)로 설계해, 나중에 무중단으로 파티션을 도입하기 쉽게 해둔다.

결론

Postgres가 스타트업을 놀라게 하는 지점은 대체로 비슷하다. 커넥션이 예고 없이 바닥나고, 인덱스가 없거나 과한 채로 방치되고, autovacuum이 밀려 팽창이 쌓이고, 스키마 변경이 예상 밖의 잠금을 일으키고, 백업은 있는데 복구는 해본 적이 없다. 이 글에서 다룬 항목들은 하나같이 사전에 알고 대비하면 비용이 크지 않지만, 사고가 난 뒤에 배우면 다운타임과 신뢰 손실로 대가를 치르는 것들이다. 지금 팀의 Postgres가 이 체크리스트 중 몇 개를 이미 갖추고 있는지 점검해 보는 것이, 오늘 할 수 있는 가장 실용적인 다음 걸음이다.
