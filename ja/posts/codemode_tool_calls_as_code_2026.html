きっかけ - 一年前の勧めとPi 1.0のCodemode

記事には「written on October 06, 2026」と記され、筆者はArmin Ronacherである。彼は一年以上前に書いた何本かの記事で、独自ツールやMCPサーバーをコンテキストに載せず、代わりにスクリプトをもっと使うよう勧めたと振り返る。その中で最も重要なのが「Code Is All You Need」で、「MCP needs code」も書いたという。ところがPi 1.0では、CodemodeによってMCPのサポートを加えた。筆者はこれを、ある意味では遅きに失した話でありながら、一部の人には意外かもしれないと書き、その意味について更新した考えをこの記事で共有すると述べる。

  • 筆者と日付: Armin Ronacher、2026年10月6日。
  • 対象のツール: Pi。筆者はPi 1.0でCodemodeによりMCPサポートを加えたと書く。
  • このサイトのPi 1.0の記事は1.0の機能全般を扱い、この記事はCodemodeに関する筆者の論旨を追う。

ツールとは何か、bashにできないこと

筆者はまずツールとは何かを確認する。ハーネスがLLMに呼び出せるツールを与えるときはツール定義を渡し、その定義はサーバー側で何らかのトークン構造に変換される。モデルがツールを呼ぶよう促されるかどうかは強化学習の過程の結果であり、このテーマは以前の記事で書いたと述べている。

筆者がCLIとbashに強く傾く理由は二つある。呼び出しを簡単に組み合わせられること、そしてモデルが学習する際にファイルシステムの動作も一緒に学ぶことだ。モデルがecho foo > /tmp/test.txtのようなツール呼び出しを行えば、その後に/tmpにtest.txtというファイルができることも学ぶ、という説明である。

しかしbashには根本的な限界が一つある。実行できるプログラムしか組み合わせられないことだ。筆者は、プログラムではないのにLLMにとってはネイティブなツールであるものがあり、そうならざるを得ないと書く。

  • readやview_image: マルチモーダルモデルが画像を読む必要があるとき、catでは足りない。ハーネスが実際の画像ペイロードをLLMのプロトコルに注入する必要があるからだ。
  • サブエージェント: 生成して調整するには、ハーネスが提供するツールを避けるのが難しい。理論上は環境変数とUnixソケットで外側のハーネスと話すCLIツールを与えられるが、筆者はそれを粗雑な方法だと書く。
  • コードがどこで動くか: その方法にはもう一つ問題があり、筆者は次の節でそれを解きほぐす。

頭脳と手 - ハーネスと実行環境

筆者は、各要素がそれぞれどこで動くかを考えようと言う。通常は二つのシステムがある。一つ目は頭脳であるハーネスで、一台のマシンで動き、信頼される。二つ目は手で、たいてい同じマシンだが、ツールが実際に実行される場所である。Piはこれを今は実行環境と呼び、あらゆる操作の対象(target)と考えればよいという。

重要なのは、ハーネスという頭脳と、bashを動かしツールを実行する対象環境の間に境界線があることだ。これを二つに分けると重要な結果が生じると筆者は書く。両者は別々のファイルシステムで動き、信頼の水準も異なる。たとえばGondolinのようなサンドボックスを使えば、bash側はきちんとサンドボックス化されるが、ハーネス自体はそうならない。

区分筆者の説明信頼・隔離
頭脳(ハーネス)一台のマシンで動く信頼される
手(実行環境、target)たいてい同じマシンだが、bashとツールが実際に動く場所ハーネスとファイルシステムが異なり、信頼の水準も異なる
Gondolinのようなサンドボックスを使う場合bash側はサンドボックス化されるハーネス自体はサンドボックス化されない

Codemodeがすること - ハーネス側のサンドボックス

筆者はCodemodeが実際にすることをこう要約する。LLMが複雑な操作を表現し調整するための方法であり、それを実行環境側ではなくハーネス側で行う。Codemodeはハーネスの中の専用サンドボックスで動く。PiではWASMランタイム内のQuickJSで、意図的な制約がかかっている。

  • ネットワークがない。
  • ファイルシステムがない。
  • タイマーがない。
  • RAMが制限される。

この中でコードにできるのは、さらにツールを呼ぶことだけだ。筆者は、CodemodeでSchemeなどほかの言語を動かすことも想像できると付け加える。Codemodeになじみのない読者のために、筆者はこう整理する。ある言語の中からツール呼び出しを発行する方法であり、ここではその言語がJavaScriptだ。そのおかげで、呼び出しをLLMのコンテキストを必ずしも通さずに組み合わせられる。名前を付けたのはCloudflareで、筆者はその功績を同社の友人たちに帰している。

コンテキストで変わること

筆者はbash呼び出しを例に挙げる。通常のツール呼び出しとしてbashを発行すると、Piはコンテキストに末尾の2000行だけを入れ、エージェントがもっと見たければオーバーフローファイルを自分で見る必要がある。同じ呼び出しをCodemode経由で発行すれば、Codemode側により大きな出力が構造化された形で届く。

CodemodeはJavaScriptなので、エージェントは並行処理と基本的なワークフローを表現できる。筆者が最近エージェントに見る典型的な使い方は、まずツールの応答から5〜10件を調べて形を確かめ、それから残りのn件を処理するCodemodeスクリプトを書くことだ。

Codemodeは状態をトランスクリプトに入れることもできる。一回のCodemode呼び出しがデータをしまっておけば、セッション内の次の呼び出しがそれを読み直せる。筆者は、これがサンドボックスではなくハーネスのホスト側にあると強調する。Piでは、画像生成モデルや一回でテキストを分類する分類器モデルのように、Piの従来のインターフェースでは意味をなさない呼び出しもCodemodeで発行できる。そうしたPi APIはCodemodeでは公開されるが、通常のツールとして公開してもコンテキストを無駄にするだけなので公開されない。

項目通常のツール呼び出しCodemode(筆者の説明)
bashの大きな出力末尾の2000行だけがコンテキストに入り、残りはオーバーフローファイルへ行くCodemode側がより大きな出力を構造化された形で受け取る
並行処理とワークフロー—JavaScriptなので並行処理と基本的なワークフローを表現できる
応答の形の把握—5〜10件を先に調べ、残りを処理するスクリプトを書く
状態の保持—トランスクリプトにデータを入れ、次の呼び出しが読み直す(ハーネスのホスト側)
画像生成・分類器モデルのAPI通常のツールとして公開するとコンテキストを無駄にするCodemodeでのみ公開する

実際のセッション三例 - 画像、Issue分類、ゲームループ

筆者は自分の最近のPiセッションからCodemodeの呼び出しを示す。このコードは人間が書いたものではなく、実際のPiセッションから出たもので、読みやすいようにインデントを直しただけだと断っている。エージェントがCodemodeを自動で使い始めるのは、モデルがすでに自然にそのツールを選ぶ作業であるか、ユーザーが頼んだからだ。PiではCodemodeはMCPが有効なときだけ既定で有効になり、設定のdefaultToolsに"+codemode"を入れて有効にできる。Piに有効にするよう頼んでもよいと筆者は書く。以下のコードは記事のコードの空白だけを整えたもので、二つ目は一部を省いてある。

画像生成

画像生成はPiがAI SDKコアでサポートする機能だが、エージェントが使えるツールではない。以前は画像モデルを使うには、独自の拡張を書くか、エージェント自身にnodeを動かして内部の画像APIを使わせるしかなかった。内部のモデルAPIをかなりCodemode内に公開しているので、今はエージェントが使える。

const [painter] = await models.getAvailableOfType("image");
                    const result = await models.generateImages(painter, {
                      input: [{ type: "text", text: "A cute little puppy sitting on a grassy " +
                        "lawn, soft natural light, photorealistic" }],
                    });
                    if (result.stopReason !== "stop") return result.errorMessage;
                    for (const block of result.output) {
                      if (block.type === "image") image(block);
                      else text(block.text);
                    }

image()の呼び出しは、画像を画像コンテンツとしてLLMに返す。ハーネス側ではそれをエージェントに直接渡すとともに、エージェントが画像をbashに渡したい場合に備えて、一時的な成果物としてディスクにも書き出す。

分類器でGitHubのIssueを分析する

Jevのような分類器モデルも、通常のツールではエージェントのワークフローにうまく収まらない。独自ツールを用意する代わりに、CodemodeはエージェントがAI SDKに直接手を伸ばして呼び出せるようにする。筆者が示すコードは、Jevを使ってGitHubのIssueを一括処理し、素早く感情分析を行うものである。

const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
                    const r = await tools.bash({
                      command: "gh issue list --state open --limit 100 " +
                        "--json number,title,body,comments",
                    });
                    const issues = JSON.parse(r.output);
                    const results = await Promise.all(issues.map(async (issue) => {
                      const res = await models.classify(jev, {
                        state: {
                          title: issue.title,
                          body: (issue.body || "").slice(0, 4000),
                          comments: issue.comments.slice(-5).map(c => c.body.slice(0, 800)),
                        },
                        questions: {
                          sentiment: {
                            type: "choice",
                            instructions: "What is the overall sentiment of the author towards pi?",
                            criteria: {
                              positive: "Appreciative, happy, constructive praise",
                              neutral: "Matter-of-fact report or request without emotion",
                              negative: "Frustrated, annoyed, upset, or angry",
                            },
                          },
                          // ... frustration (score), kind (choice)
                        },
                      });
                      // ...
                    }));
                    store("sentiment_results", results);
  • 開いているIssueを最大100件取得する(gh issue listに--limit 100)。
  • Issueごとに、本文は4000文字まで、コメントは末尾5件を各800文字までに切って分類器に送る。
  • 質問は三つ。作成者の全体的な感情(positive、neutral、negativeから選択)、苛立ちの度合い(スコア)、Issueの種類(bug、feature、question、otherから選択)。
  • 全結果をstore()でセッションのトランスクリプトに入れ、苛立ちスコアが高い順に12件だけを返す。筆者は、後のCodemode呼び出しがその結果を読み直せると書く。
  • ここでPromise.allが問題ない理由は、Piが同時に実行するツール数を4つに制限し、残りをキューに置くからだと筆者は説明する。

ゲームのデバッグループ

より冒険的な例として、筆者はJevでゲームエンジンを動かしてデバッグを助ける事例を挙げる。エージェントは筆者のtankctlコマンドを知っており、その周りにゲームループを動かす最小限のハーネスをすぐに作った。30ステップのループを回し、各ステップでゲームエンジンから状況のテキストダンプを取り、次に何をするかをJevに判断させる。

例Codemodeでしたこと筆者が指摘する点
画像生成modelsで画像モデルを探して生成し、image()で結果を返すPiはサポートしていたがエージェント用のツールではなかった。内部モデルAPIをCodemodeに公開して使えるようになった
GitHub Issueの分類開いているIssue 100件をJevで分類し、store()で保存する分類器は通常のツールのワークフローに合わない。独自ツールなしでAI SDKを直接呼ぶ
ゲームのデバッグループ30ステップのループでエンジンのテキストダンプをJevに送り、次の行動を決めるエージェントがtankctlの周りに最小限のハーネスを自分で作った

MCPサーバーの呼び出しと「CodemodeのなかのCodemode」

筆者は、CodemodeはMCPサーバーを呼ぶのに明らかに向いていると書く。PiはMCPのツールをLLMにまったく公開しない。代わりにエージェントが、Codemode内で提供されるAPIでまずツール検索を行い、接続されたサーバーで何ができるかを見つける。筆者は、この段階的な発見が、今日の多くのユースケースでMCPを十分に使えるものにしていると見ている。

例では、エージェントはツールを発見する前から、すぐにSentry MCPに手を伸ばす。筆者は、強化学習の過程でSentry MCPがどういうものかすでに学んでいるからだろうと推測する。ただしSentryサーバーが利用できることは、システムプロンプトに注入された情報から分かるので、完全に当て推量しているわけではないと付け加える。

const orgs = await tools.mcp__sentry__find_organizations({});
                    const { organizations } = orgs.structuredContent;
                    const results = await Promise.allSettled(
                      organizations.map(org => tools.mcp__sentry__find_projects({
                        organizationSlug: org.slug,
                        regionUrl: org.regionUrl,
                      }))
                    );

筆者はここでMCPについて多くを語りたくないと言いつつ、MCPはCodemodeから大きな恩恵を受けるプロトコルだと書く。問題の一部は、MCPが実際にはまだCodemodeを使わないハーネスを対象にしていることが多い点にある。筆者は流れが変わりつつあると見ている。その間の一時しのぎとして、Cloudflareが行ったようにMCPサーバーの中でCodemodeを行う方法が使われた。しかし今ではCodemodeのなかにCodemodeが入る形になっており、筆者はこれをかなり悪いと評価する。

  • JSONを二重にエスケープすることになる。
  • 小さなモデルが混乱しやすい。
  • 内側のコードは外側のツールを呼べない。

そのため、PiでCloudflareのMCPサーバーを使うと、エージェントはJavaScriptを書き、それをさらに別のJavaScriptに流し込まなければならない。筆者は、これは本当は最適ではないが、そうなっている理由は理解できると書く。

MCPへの要望と残る課題

今日のCodemodeはMCPとどれだけうまく動くのかと問い、筆者は驚くほどうまくは動かないと答える。MCPサーバーがまだCodemodeを使うハーネスを対象にしていないからだ。今ではほとんどのハーネスが対応していると思うが、という趣旨である。うまく動かすための推奨事項として、筆者は四つを挙げる。

項目問題筆者の説明
構造化されたコンテンツCodemodeは整ったJSONが返ることを望むが、多くのサーバーはまだそうしていないMCPのoutputSchemaの仕組みがそのために優れている
一貫した結果結果の件数に応じてトークンを最適化するサーバーは、一貫しないデータを返すことがある5件での最初の探りは成功するのに、サーバーが最大バッチサイズを返すと失敗する場合がある
大きなバイナリデータMCPはまだ大きなバイナリデータをサポートせず、興味深いユースケースの多くがまったくうまく動かない署名付きURLでファイルのアップロードをMCP以外の経路で行うなど、さまざまな回避策が生まれる
合成できるツール検索どのツールが作業に合うかは、MCPクライアントよりサーバーのほうがよく知っている場合があるハーネスが複数のMCPサーバーにツール検索を振り分ける良い仕組みがなく、現状は創発的な挙動で、有効なサーバーが複数だと拡張できない

これは一年前にCLIを勧めたことの撤回なのか、という問いに、筆者はそうは思わないと答える。彼の見方では、MCPのエコシステムは、一年前に指摘したこと、つまりコードが有効だという点にまさに追いついた。CodemodeはMCPを超えて、ハーネスの中でエージェントにより大きな自由を表現させる有力な手段としても働く。ただし、まだ解決すべきことがあると書く。

  • 耐久性: Codemodeでは難しくなる。耐久性のあるワークフローエンジンの考え方を取り入れ、呼び出しをスナップショットする必要があるかもしれない。
  • 合成言語: 決定的であるという点で、StarlarkのようなものがJavaScriptより良い合成言語かもしれない。
  • 画像とバイナリデータはまだ整理が必要だ。
  • 小さなモデルではこのパターンが通じない。

筆者は、まだ完璧な解決策ではないのは確かだが、かなり有用なパターンで、今後さらに活用すると見込んでいると締めくくる。

確認できなかったこと

  • サンドボックスのRAM制限がどれだけか: 記事はRAMが制限されるとだけ書き、数値を示さない。
  • Codemodeを使う場合と使わない場合のトークン数や時間の差: 記事に測定値はない。
  • store()で保管したデータがセッション再開後も残るか、どの形式で保存されるか: 記事はセッションのトランスクリプトに入れるとだけ書く。
  • Cloudflareが先に書いた方式とPiの方式が細部でどう違うか: 二つの記事を項目ごとには照合していない。
  • 小さなモデルがCodemodeスクリプトをどれだけうまく書けるか: 記事は限界として触れるだけで成功率は示さない。
