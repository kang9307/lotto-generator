校验之后再改值，校验就作废了 - 规范化与校验的顺序

被检查的值与真正使用的值不是同一个字符串时，这次检查等于从未发生

2026-08-01 开发与基础设施

引言: 检查通过了，进来的值却不一样

翻日志时发现了奇怪的值。存下来的名字里夹着换行，或者本不该被打开的那种形状的字符串正坐在文件路径的位置上。打开代码一看，输入检查确实在。正则写得很细，禁止字符的列表也很长，也没有绕过检查的分支。可值还是进来了。

这时大多数人的反应是 把检查规则写得更细。往正则里加字符，把列表拉长，再补上例外分支。可过几天类似的值又进来了。如果规则怎么改都会复发，那问题就不在规则上。

本文只谈一件事: 检查器判定的那个字符串，与程序真正使用的那个字符串，是两个不同的字符串。在这种情形下检查器毫无过错。它对自己收到的值给出了准确的回答，只不过那个回答并不是关于最终值的回答。

所以本文的论点不是「请做校验」。校验早就有了。重要的是 校验了什么。而决定这个「什么」的不是规则，是 顺序。

执行环境。 下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际执行的结果。运行时是 Node.js v22.16.0 (win32)，部分结果用 Python 3.13.3 做了交叉验证。所有脚本都先写入文件再执行。

本文不做的事。 这里 没有攻击步骤，也没有渗透方法。 所有示例只使用无害字符，以及始终留在基准目录内部的路径。要展示的不是「怎么打进去」，而是 「按这个顺序，检查就失去意义」 这一个结构。因此包括路径那一节在内，所有示例都只走到 检查时刻的值与使用时刻的值不同 为止。

本文不涉及的内容。 同一个字符在 Unicode 内部变成多种码点序列的原理，已经在 NFC 与 NFD 里讲过。这里只把规范化当作 放置位置的问题 来看。Web 输入处理的总体背景在 Web 安全基础 里。用允许列表还是禁止列表、校验该放在哪一层，都不是本文的主题。本文只停留在 顺序 这一点上。

1. 同一个检查器，只是换了顺序

先复现最常见的形态。先做禁止字符检查，再把通过的值拿去解码。读这段代码看不出任何问题，检查在前使用在后，顺序似乎是对的。为了看清实际发生了什么，我把 检查时刻的值和使用时刻的值并排 打印出来。

node v22.16.0 / win32
--- 1-1. ORDER A: validate first, decode afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a%3Cb           PASS      a<b             NO
note%3Bnext     note%3Bnext     PASS      note;next       NO
x%26y           x%26y           PASS      x&y             NO
line%0Asecond   line%0Asecond   PASS      line\nsecond    NO
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-2. ORDER B: decode first, validate afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a<b             REJECT    (never used)    -
note%3Bnext     note;next       REJECT    (never used)    -
x%26y           x&y             REJECT    (never used)    -
line%0Asecond   line\nsecond    REJECT    (never used)    -
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-3. the gap, counted ---
order A  passed check but dirty at use : 4 of 6
order B  passed check but dirty at use : 0 of 6
the checker function is identical in both runs. only the order changed.

把第二列和第四列对着看，这是贯穿全文的窍门。在顺序 A 下 a%3Cb 在检查时刻就是 a%3Cb。这个字符串里一个禁止字符都没有，检查器老老实实给了通过。可使用时刻的值是 a<b。检查器从未见过这个字符串。

  • 六个输入里有四个走了这条路。 拿到通过判定之后，禁止字符在最终值里冒了出来
  • 只有最后一行是正常的。 未编码的 plain<bad> 在检查时刻就带着禁止字符，所以被拒绝。也就是说这个检查器只抓 看得见的形态
  • 顺序 B 下通过后被污染的有零件。 检查器函数在两次运行中一个字符都没差
  • 换行那一行尤其重要。line%0Asecond 一旦进到日志或消息头这类 按行确定含义的位置，一个值就变成两行
  • 这个缺陷 靠修检查器是修不掉的。 无论加多少规则，检查器看到的仍然是编码后的字符串

1.1 检查器无从知道自己已经失去意义

这个结构最糟的地方是 没有人会遇到错误。不抛异常，日志里不留警告，检查器还会报告自己准确地完成了工作。跑集成测试也能通过，因为测试塞进去的值多半是已经解码好的普通字符串，两种顺序给出的结果相同。

也就是说这属于 测试不容易抓到、评审也不容易抓到 的那类缺陷。评审者看到的是「有检查」和「有使用」，要想连这两者之间的顺序都起疑，就得先知道 夹在中间的那一行会改变值。

2. Unicode 规范化 - 放在检查之后，判定就会翻转

第二条路径是 Unicode 规范化，它比上一节的解码安静得多。解码至少还留下一个显眼的 %，而规范化是把一个 看上去已经完全正常的字符串 变成另一个字符串。先看一遍它到底做了什么。

node v22.16.0 / win32
--- 2-1. one NFKC pass changes the string itself ---
before      len  after NFKC  len  codepoints after
--------------------------------------------------------------------------
report      6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
ｒｅｐｏｒｔ 6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
a／b        3    a/b         3    U+0061 U+002F U+0062
ﬁle         3    file        4    U+0066 U+0069 U+006C U+0065
①           1    1           1    U+0031
㎡          1    m2          2    U+006D U+0032
ｎｏ＜op    5    no<op       5    U+006E U+006F U+003C U+006F U+0070

值得盯住的是 长度发生变化的行。ﬁle 原本三个字符，规范化后变成四个；㎡ 从一个变成两个。把长度限制放在规范化之前，就会出现 通过了限制的值以超限的状态被存下来。

而最后两行是本节的核心。用全角字符写的值经过规范化，变成了 半角斜杠和半角尖括号。检查时刻并不存在的字符，在使用时刻被造了出来。判定究竟怎样翻转，我用两种方式确认了。

--- 2-2. allowlist verdict before vs after normalization ---
input       allow(before)  allow(after)  flipped?
--------------------------------------------------------
report      true           true          no
ｒｅｐｏｒｔ false          true          YES
a／b        false          false         no
ﬁle         false          true          YES
①           false          true          YES
㎡          false          true          YES
ｎｏ＜op    false          false         no

--- 2-3. denylist verdict before vs after normalization ---
input       deny hit(before)  deny hit(after)  flipped?
------------------------------------------------------------
report      false             false            no
ｒｅｐｏｒｔ false             false            no
a／b        false             true             YES
ﬁle         false             false            no
①           false             false            no
㎡          false             false            no
ｎｏ＜op    false             true             YES

关键在于这两张表 朝相反的方向出错。

  • 允许列表下，正常的值被拒绝。 用全角输入的 ｒｅｐｏｒｔ 规范化之后是完全合法的 report，可要是在规范化之前检查就会被拒。在用户看来这是一个「好好的名字它不收」的缺陷
  • 禁止列表下，本该拦住的值通过了。 规范化之前没有禁止字符，规范化之后才生出来
  • 两种情况下 检查器本身都是准确的。 出错的不是检查器，而是交给检查器的那个值
  • 实务中前一种错误会先被发现，因为用户会抗议。后一种没人抗议，所以留得更久
  • 这两张表是 同一个原因的两副面孔。只修一边，另一边还在

2.1 幂等就可以往前挪

那么规范化该在什么时候做。答案是「最前面」，而且这么说是有依据的: 规范化跑多少次结果都一样。这个性质叫幂等。我连着跑了三次。

--- 2-4. NFKC is idempotent, so doing it FIRST is safe ---
report      n1==n2 true   n2==n3 true
ｒｅｐｏｒｔ n1==n2 true   n2==n3 true
a／b        n1==n2 true   n2==n3 true
ﬁle         n1==n2 true   n2==n3 true
①           n1==n2 true   n2==n3 true
㎡          n1==n2 true   n2==n3 true
ｎｏ＜op    n1==n2 true   n2==n3 true
a normalizer you can run twice with no change can always be moved to the front.

--- 2-5. NFC vs NFKC are not the same job ---
input       NFC         NFKC        NFC==NFKC
--------------------------------------------------
ｒｅｐｏｒｔ ｒｅｐｏｒｔ report      false
ﬁle         ﬁle         file        false
㎡          ㎡          m2          false
á          á           á           true

2-4 的含义很简单: 把规范化挪到前面 不会有任何损失。 就算后面某处又做了一次规范化，值也不会再变，所以安全。这就是「先规范化」这条规则能够毫无风险地成立的理由。

2-5 展示了一个陷阱: NFC 和 NFKC 干的不是同一件事。 最后一行的重音字符两种方式结果相同，可上面三行全都不同。把全角折成半角、把连字拆开，这些只有 NFKC 会做。所以只说「我们做了规范化」，是 说不清做的是哪一种 的。对原理本身感兴趣可以看 NFC 与 NFD。这里需要的结论只有一句: 选定一种形式，写进文档，让所有层都用同一种。

3. 空白与大小写 - 最常见也最看不见的错位

前两节至少还牵涉到特殊字符，比较容易起疑。这一节不一样。trim 和转小写太平常了，没人会把它们当成「改变值的运算」。 以保留名列表检查为例，我按两种顺序各跑了一遍。

node v22.16.0 / win32
--- 3-1. ORDER A: check the raw value, canonicalize when storing ---
requested       value AT CHECK  reserved?  value STORED  stored value reserved?
--------------------------------------------------------------------------------
[alice]         [alice]         false      [alice]       no
[admin]         [admin]         true       [(rejected)]  -
[Admin]         [Admin]         false      [admin]       YES  <- mismatch
[ admin]        [ admin]        false      [admin]       YES  <- mismatch
[ADMIN ]        [ADMIN ]        false      [admin]       YES  <- mismatch
[  support  ]   [  support  ]   false      [support]     YES  <- mismatch
[billing\t]     [billing\t]     false      [billing]     YES  <- mismatch

--- 3-2. ORDER B: canonicalize first, then check ---
requested       value AT CHECK  reserved?  value STORED  stored value reserved?
--------------------------------------------------------------------------------
[alice]         [alice]         false      [alice]       no
[admin]         [admin]         true       [(rejected)]  -
[Admin]         [admin]         true       [(rejected)]  -
[ admin]        [admin]         true       [(rejected)]  -
[ADMIN ]        [admin]         true       [(rejected)]  -
[  support  ]   [support]       true       [(rejected)]  -
[billing\t]     [billing]       true       [(rejected)]  -

顺序 A 下，保留名列表 只对恰好一种拼写有反应。前后加个空白或者混进一个大写，就从列表里溜过去了。可存进去的时候这些值全都被整理成同一个形态，于是 列表里的名字以通过了列表的状态被存了下来。顺序 B 下，同样的列表、同样的输入，全部被拦住。

3.1 唯一性检查与存储键分家的时候

同样的缺陷还有一种安静得多的形态: 重复检查。这里它不像是安全问题，更像是 数据完整性问题。

--- 3-3. uniqueness checked on one value, stored as another ---
order A: unique-check on raw, store canonical
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? false  stored [alice@example.com]
  [ALICE@EXAMPLE.COM]     dup at check? false  stored [alice@example.com]
  distinct values checked : 3
  distinct values stored  : 1   <- three rows collapsed into one key
order B: canonicalize first, then unique-check
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? true   rejected
  [ALICE@EXAMPLE.COM]     dup at check? true   rejected

顺序 A 三次都回答了「不重复」。 检查时刻的这三个字符串确实互不相同，所以这个回答是对的。可换成存储键之后，三个就成了同一个值。于是三个互不相同的请求挤在 同一个键 上。不会抛异常。它日后表现为「同一个地址有两个账号」或者「先建的那个不见了」这类反馈。

3.2 trim 不是一条规则，而是一份名单

实际确认一下 trim 到底删掉什么，会发现和想的不一样。看着像空白的字符并不是都会被删。

--- 3-4. what exactly trim removes, and what it does not ---
input codepoints          trim() result     length change
------------------------------------------------------------
U+0061 U+0020 U+0062      3 -> 3            untouched
U+0020 U+0061             2 -> 1            trimmed
U+0061 U+00A0             2 -> 1            trimmed
U+0061 U+200B             2 -> 2            untouched
U+0061 U+FEFF             2 -> 1            trimmed
U+0061 U+3000             2 -> 1            trimmed
U+00A0 and U+3000 are removed, U+200B and U+FEFF are not.
so trim is not one rule. it is one specific list, and it must run before the check.

--- 3-5. lowercase is locale sensitive ---
input U+0130            : İ
toLowerCase()           : U+0069 U+0307
toLocaleLowerCase(tr)   : U+0069
length after each       : 2 vs 1
two layers using different locales produce two different canonical values.
  • 不换行空格和全角空格会被删。 它们看不见，所以光看存下来的值是看不出来的
  • 零宽空格不会被删。 它看着像空白，但不在这个函数的名单上。带着它的值会被当成另一个值
  • 也就是说 trim 不是「删空白」，而是 「删掉某份特定名单上的字符」。不知道那份名单，就不知道什么会通过
  • 3-5 更微妙: 转小写的结果依赖区域设置。 某个字符在一边变成两个字符，在另一边变成一个
  • 各层用不同的区域设置，就会对同一个输入产生 每层不同的规范形态。这一点第 7 节还会再谈
  • 结论是一样的: 这些转换全都是 改变值的运算，而改变值的运算必须排在检查之前

4. 路径拼接 - 一合起来字符串就被重写了

路径是这个问题最广为人知的领域。所以反过来，先把 不会展示的东西 说清楚。下面的示例全都是留在基准目录内部的正常路径，没有逃逸案例，也没有成功的绕过。这里要展示的只有一件事: 拼接这个动作会重写字符串。

node v22.16.0 / win32
--- 4-1. the string the checker saw vs the string join produced ---
user segment          joined result                   identical tail?
------------------------------------------------------------------------
q1.csv                /srv/data/reports/q1.csv        true
sub//q1.csv           /srv/data/reports/sub/q1.csv    false
./q1.csv              /srv/data/reports/q1.csv        false
sub/./q1.csv          /srv/data/reports/sub/q1.csv    false
sub/inner/../q1.csv   /srv/data/reports/sub/q1.csv    false
sub/                  /srv/data/reports/sub/          true
a/b/../../q1.csv      /srv/data/reports/q1.csv        false
every row above stays inside the base directory. only the SPELLING changed.

--- 4-2. what join collapsed, step by step ---
q1.csv                unchanged
sub//q1.csv           duplicate separator collapsed
./q1.csv              current-dir segment dropped
sub/./q1.csv          current-dir segment dropped
sub/inner/../q1.csv   current-dir segment dropped, parent segment resolved
sub/                  trailing separator dropped
a/b/../../q1.csv      current-dir segment dropped, parent segment resolved

七个输入里有五个给出了 与简单拼串不同的结果。变了什么列在 4-2 里: 重复的分隔符被合并，当前目录标记消失，上级目录标记被解析掉，末尾的分隔符掉了。官方文档也明确写着拼接函数会规范化其结果。

  • 这种整理不是可选项。 只要用拼接函数就一定发生
  • 因此先检查用户输入的片段再拼接，被检查的字符串就不是最终触到磁盘的那个字符串
  • 所有示例都留在基准内部这一点很重要。错位并不是只在危险输入上才出现的
  • 正常输入下值也会变，这说明这种错位 在平时是常态存在的

4.1 分隔符在不同层里含义不同

同一个片段用两种路径风格拼接，结果会分岔。

--- 4-3. same segment on the windows path flavour ---
user segment          posix.join                    win32.join
----------------------------------------------------------------------------
q1.csv                /srv/data/reports/q1.csv      C:\srv\reports\q1.csv
sub/q1.csv            /srv/data/reports/sub/q1.csv  C:\srv\reports\sub\q1.csv
sub\q1.csv            /srv/data/reports/sub\q1.csv  C:\srv\reports\sub\q1.csv
sub//q1.csv           /srv/data/reports/sub/q1.csv  C:\srv\reports\sub\q1.csv
a forward slash is an ordinary character to posix.join but a separator to win32.join.
so one segment has two different meanings depending on which layer joins it.

看第三行。含反斜杠的片段，一边把它留作 普通字符，另一边把它解释成 分隔符。也就是同一个字符串在不同层里被读成了不同的结构。如果开发跑在一种风格上而生产跑在另一种上，就会出现 开发时通过的检查在生产中判定的是另一个值。

4.2 关于拼写的问题和关于文件的问题

核心在这里。我把同一个问题 —— 这条路径在基准内部吗 —— 分别向两个值提了一次。

--- 4-4. the containment test, run on the two different values ---
user segment          test on RAW   test on RESOLVED  same answer?
----------------------------------------------------------------------
q1.csv                true          true              true
sub//q1.csv           true          true              true
./q1.csv              true          true              true
sub/./q1.csv          true          true              true
sub/inner/../q1.csv   false         true              false
sub/                  true          true              true
a/b/../../q1.csv      false         true              false
the RAW column answers a question about spelling.
the RESOLVED column answers a question about the file that will actually be opened.
only the second question is the one the program cares about.

--- 4-5. resolve is idempotent, so it belongs in front of the check ---
q1.csv                r1 == r2 : true
sub//q1.csv           r1 == r2 : true
./q1.csv              r1 == r2 : true
sub/./q1.csv          r1 == r2 : true
sub/inner/../q1.csv   r1 == r2 : true
sub/                  r1 == r2 : true
a/b/../../q1.csv      r1 == r2 : true

两列答案不一致的行有两条，而且 不一致的方向很有意思。看原始拼写的检查把这两条路径拒了，可最终路径老老实实待在基准内部。也就是说在这个例子里，拼写检查 挡住了正常文件被打开。

这是理解顺序问题的一个好角度。检查拼写和检查文件是两个不同的问题，而程序关心的只有第二个。第一个问题的答案会把第二个问题的答案 朝任意方向 带偏。4-5 说明解法很简单: 拼接与整理是幂等的，所以 挪到校验之前不会损失任何东西。

5. 解码不是幂等的

到目前为止出现的规范化步骤全都是幂等的，所以「往前挪就行」这个处方管用。可有一个步骤不一样: 百分号解码。结果会随着跑了几次而不断变化。

node v22.16.0 / win32
--- 5-1. one decode, two decodes, three decodes ---
raw           after 1       after 2       after 3
----------------------------------------------------------------
a%3Cb         a<b           a<b           a<b
a%253Cb       a%3Cb         a<b           a<b
a%25253Cb     a%253Cb       a%3Cb         a<b
100%25        100%          URIError: URI malformed URIError: URI malformed
a%2520b       a%20b         a b           a b
plain         plain         plain         plain

--- 5-2. decoding is NOT idempotent ---
a%3Cb         d1 == d2 : true
a%253Cb       d1 == d2 : false   a second layer changes the value again
a%25253Cb     d1 == d2 : false   a second layer changes the value again
100%25        d1 == d2 : false   a second layer changes the value again
a%2520b       d1 == d2 : false   a second layer changes the value again
plain         d1 == d2 : true
a step you cannot repeat safely cannot be moved around freely.
it must happen exactly once, at a place both sides agree on.

第四行尤其重要。100%25 解码一次变成 100%，再解码一次 就会抛异常，因为以百分号结尾的字符串不是有效的编码。也就是说在解码两次的结构里，甚至会出现 正常的值被错误弄死 的情况。

5.1 每一层都带着自己的解码器

问题在于为什么会发生两次解码。没有人决定要解码两次，只是每一层都在自己的位置上 各做了一次。

--- 5-3. the same string through two different decoders ---
raw           decodeURIComponent    URLSearchParams     same?
----------------------------------------------------------------
a+b           a+b                   a b                 false
a%20b         a b                   a b                 true
a%2Bb         a+b                   a+b                 true
a%3Cb         a<b                   a<b                 true
the plus sign is where the two disagree. one layer sees a space, the other a plus.

--- 5-4. a value that survives a check and then changes at the next layer ---
raw           layer1 out    deny at L1?  layer2 out    deny at L2?
----------------------------------------------------------------------
a%253Cb       a%3Cb         false        a<b           true
a%2526b       a%26b         false        a&b           true
a%3Bb         a;b           true         (rejected)    -
ok-value      ok-value      false        ok-value      false
layer 1 checked the value layer 1 had. layer 2 uses a different string.

--- 5-5. counting decodes across a chain ---
start value : a%25253Cb
gateway     a%25253Cb      -> a%253Cb       (changed)
router      a%253Cb        -> a%3Cb         (changed)
handler     a%3Cb          -> a<b           (changed)
three layers each doing their own decode is three decodes, not one.
nobody wrote that down anywhere. it is the sum of three local decisions.
  • 5-3 说明 同名的操作在不同工具里并不相同。加号一边变成空格，另一边原样保留
  • 所以「我们解码了一次」这句陈述 并不能确定结果字符串是什么
  • 5-4 表明第 1 节的结构在层与层之间同样会复现。第一层检查的值不是第二层使用的值
  • 5-5 里三个层各解码一次，总共解码了三次。没有人做过这个决定，它是三个局部判断相加的结果
  • 标准对这一点也很明确。URL 标准在解析过程中 执行一次百分号解码，并未规定反复解码
  • 因此解码必须 恰好一次，在双方约定好的位置 发生。「保险起见再来一次」在这里不是保险

同一个错误的顺序 按检查器风格朝相反方向出了错。 允许列表下不公正地拒了五个，禁止列表下不公正地放了三个。两种情况下 检查器自身都无从知晓。 它只是对自己收到的字符串给出了准确的回答。

所以规则可以压缩成一句，就是 6-6: 被检查的值和被使用的值必须相同。 只要守住这个等式，其余都会跟着成立。反过来，等式被打破的代码，检查规则再精细，那份精细也不会作用在最终的值上。

7-2 给出了四个答案，而且 全都是对的。 每一层都对自己手里的字符串给出了准确回答。可从整个系统看，「这个请求算通过吗」这个问题没有一个确定的答案。这才是分散规范化的真正代价: 判定成了位置的函数。

7-3 给出了处方。在边界只规范化一次，下面的层不再插手，三个输入在边界以下都只有一个值。7-4 是给这个边界函数本身的警告: 含解码的边界函数 跑两次结果就不同了。 所以「边界一次」不是建议，而是 硬性条件。

7.2 安静的版本 - 缓存分家

当这个缺陷不以安全问题现身时，它就会以性能问题现身。

--- 7-5. cache keys computed at two layers ---
key hashed at layer 1 : dcd41471
key hashed at layer 3 : 845e9183
same request, same user, two cache entries : true
a split cache is the quiet version of this bug. nothing errors, the hit rate just drops.
  • 同一个请求却造出了 每层不同的缓存键。条目变成两个，命中率下降
  • 因为不报错，所以 监控抓不到它。 指标上只表现为「缓存效率比预期低」
  • 同样的原理也适用于 日志聚合。同一个对象按两个名字统计，数据就分家了
  • 限流和去重装置也一样，键一分家就失效
  • 所以缓存键、日志键、存储键全都必须用 边界产出的那个值 来构造

8. 怎样在代码里找出这个顺序

诊断从消费点开始最可靠。先找到打开文件、拼装查询或对外调用的那一行，然后 顺着进入它的变量向上回溯。 遇到校验调用就把两者之间的每一行都读完。只要有一行改变了值，那就是缺陷。

这项工作有相当一部分是机械的。我拿一个样例模块只用文本扫描过了一遍。

this second pattern is the one code review misses. the checked variable is still
untouched, so the diff looks fine. a different variable is what reaches the sink.
  • 第一种形态是 对被校验的变量重新赋值，相对容易被注意到
  • 第二种形态危险得多: 被校验的变量原封不动，另建一个派生变量 拿去使用
  • 第二种形态下差异看着很正常。校验有，被校验的变量也没动过。评审就从这里放行了
  • 检索词按自己的代码库定就行。两份清单足够: 校验函数名清单，以及 会改变值的函数名清单
  • 改变值的清单里要放进解码、规范化、去空白、大小写转换、替换、路径拼接
  • 不需要做到完美。目的是生成一份候选清单交给人去读

8.1 运行时绊线

静态检索拿不准的时候，可以在运行中确认: 记录检查器收到的字符串，到消费点比对是否相同。

9. 检查清单与不要这样做

把上面的内容整理成实务中可以直接用的形态。

检查项确认方法失败迹象
规范化函数统一为一个搜索名字看定义是否唯一每层各有一个相似的函数
规范化函数是幂等的对样本应用两次再比较解码被放进了函数内部
解码只在一处发生全量搜索解码调用网关和处理器两边都有
校验函数收到的是最终值把校验实参与消费点实参对照两个实参是不同的变量
校验与使用之间是空的把中间的每一行都读完哪怕只有一行赋值或加工
路径在整理之后才判定看包含检查是否作用于最终路径正在原始片段里找符号
唯一性与存储键用同一个值比较重复检查实参与存储键只有一边做了规范化
区域设置是固定的搜索大小写转换调用调用时没有给出区域设置
  • ❌ 以「已经加了校验」为终点。 校验了哪个值才是实质
  • ❌ 每层都出于防御再整理一次。 结果是每层一个值，判定成了位置的函数
  • ❌ 在多处进行解码。 没人说得清解码了几次，正常的值有时还会被错误弄死
  • ❌ 用路径字符串的拼写判定包含关系。 正常路径也会被一起拒绝
  • ❌ 以「反正后面会做」为由推迟规范化。 夹在中间的校验会整个作废
  • ❌ 用原文查唯一性、用规范形态做存储。 键会悄悄撞车，而且不报错
  • ❌ 把长度限制放在规范化之前。 规范化会改变长度，限制就没有作用在最终值上
  • ❌ 用「框架会帮我们处理」搪塞过去。 不确认框架在哪里做了什么，它也不过是又一层

结语: 你校验的到底是什么

关于输入校验的建议通常止步于「要校验」。可本文看到的这些失败，全都出自 已经有校验的代码。检查器是准确的，规则是细密的，分支也没有遗漏。可最终的值从来没有通过过那些规则。

所以该问的问题不是「校验了吗」，而是 「校验了什么」。而这个问题的答案由代码的顺序决定。被校验的值与真正使用的值不同时，校验不是可有可无，而是 等于从一开始就不存在。

把执行确认到的东西缩成一句话就是: 先规范化，后校验，中间不插入任何东西。 大多数规范化步骤是幂等的，往前挪不会有任何损失；不幂等的步骤在边界恰好执行一次。这样检查器看到的值就是程序使用的值，此后无论发生什么都无法让校验失效。

# 先规范化，后校验 — 顺序自查速查卡

> 来源: braindetox.kr — 校验之后再改值，校验就作废了
> 依据: 在 Windows 10 / Node.js 22.16.0 / Python 3.13.3 上实际执行验证

## 0. 一句话规则

规范化 → 校验 → 使用。而且 **在校验和使用之间不插入任何东西。**

校验器看到的值必须就是真正被使用的值。这个等式一旦破裂，校验就等于从未存在过。

```
atCheck === atUse
```

## 1. 如何判断顺序被颠倒了

以下任何一条成立，就是顺序缺陷。

- [ ] 检查通过之后，还有一行对该变量重新赋值
- [ ] 检查通过之后，从它派生出 **新变量**，而真正使用的是新变量
- [ ] 传给校验器的实参与传给最终消费点的实参在字符串上不相等
- [ ] 解码、规范化、去空白、转小写、路径拼接中的任何一项发生在检查之后
- [ ] 每一层都按自己的判断修整这个值 (网关、服务、存储)

## 2. 错误的顺序与正确的顺序

### 错误 — 检查之后改动了值

```js
function handle(req) {
  let name = req.query.name;
  if (!isAllowed(name)) return reject();   // 被检查的值: 编码后的原文
  name = decodeURIComponent(name);         // 值在这里改变
  return open(name);                       // 被使用的值: 解码结果
}
```

### 错误 — 检查之后创建派生变量 (评审最容易漏掉的形态)

```js
function handle(req) {
  const label = req.body.label;
  if (!isAllowed(label)) return reject();  // label 本身没被动过
  const key = label.trim().toLowerCase();  // 校验器从未见过这个值
  return store(key);
}
```

### 正确 — 在边界规范化一次，校验该值，使用该值

```js
function normalize(s) {
  let out = String(s == null ? '' : s);
  try { out = decodeURIComponent(out); } catch (e) { /* 保持原样 */ }
  return out.normalize('NFKC').trim().toLowerCase();
}

function handle(req) {
  const name = normalize(req.query.name);  // 规范化
  if (!isAllowed(name)) return reject();   // 校验
  return open(name);                       // 使用 — 同一变量，不再加工
}
```

## 3. 各规范化步骤的性质

| 步骤 | 是否幂等 | 能否在多层执行 | 放置位置 |
| --- | --- | --- | --- |
| trim | 是 | 是 | 边界 |
| toLowerCase | 是 | 是 (需固定区域设置) | 边界 |
| NFKC | 是 | 是 | 边界 |
| 百分号解码 | **否** | **否** | 在边界恰好一次 |
| 路径拼接与整理 | 是 | 是 | 紧接校验之前 |

不幂等的步骤必须 **恰好执行一次**，而且执行位置要写进文档。

## 4. 分层放置原则

- 边界只有一个。只在请求进入的第一个点做规范化
- 边界以下的所有层把这个值 **当作最终形态**，不再触碰
- 逐层规范化会让每层的值都不同，每层的判定结果也不同
- 缓存键、日志键、存储键全部由 **边界产出的那个值** 构造

## 5. 检查清单

- [ ] 存在规范化函数，并且名字统一
- [ ] 规范化函数执行两次结果相同 (解码除外)
- [ ] 解码只在边界发生一次
- [ ] 校验函数接收的实参是规范化之后的值
- [ ] 校验与使用之间没有赋值或加工
- [ ] 被校验的变量与被使用的变量是 **同一个变量**
- [ ] 路径在拼接整理之后才判定包含关系 (不靠拼写判定)
- [ ] 唯一性检查与存储键使用同一个值
- [ ] 依赖区域设置的转换明确写出了区域设置
- [ ] 测试中有「校验器收到的值 == 消费点收到的值」这条断言

## 6. 诊断步骤

1. 先找到消费点 (打开文件、发起查询、外部调用)
2. 沿着进入它的变量向上回溯
3. 看这条路径上是否存在校验调用
4. 如果有，读完 **校验调用到消费点之间的每一行**
5. 其间只要有一行改变了值，那就是缺陷
6. 拿不准就加运行时绊线: 记录校验器收到的字符串，在消费点比对是否相同

## 7. 不要这样做

- ❌ 以「已经加了校验」为终点 — 校验了哪个值才是实质
- ❌ 每层都出于防御再修整一次 — 结果是每层一个值
- ❌ 在多处解码 — 没人说得清到底解码了几次
- ❌ 用路径字符串的拼写判定包含关系 — 正常路径也会被一起拒绝
- ❌ 以「反正后面会做」为由推迟规范化 — 中间那次校验就作废了
- ❌ 用原文查唯一性、用规范化形态做存储 — 键会悄悄撞车
