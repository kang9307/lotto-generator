はじめに: 違反ゼロ件という結果をどこまで信じるか

検査器を回した。結果は違反ゼロ件。この数字に安心する前に、一つ聞くべきことがある。このゼロは対象がきれいだったという意味なのか、それとも検査器が何も見なかったという意味なのか。どちらの場合も出力は同じゼロだ。

他人を検査するコードには奇妙な性質がある。採点器、テスト、リンター、静的解析器、レビュー用スクリプトが全部ここに属する。この種のコードが壊れても、例外を投げたり画面を壊したりはしない。ただ合格が増える。そして合格は誰も開かない。

最近この問題をとてもきれいに示した記録が一つ公開された。注文処理の答案を自動採点するコードを作って使っていた人が、同じ答案二十九件を商用LLMにも採点基準とともに渡し、それぞれ点数を付けさせた。二十七件は二つの判定が同じだった。割れた二件が問題で、開いてみると間違っていたのはモデルではなく自分で書いた採点器だった。

この記事が扱うのはその事例ではなく、その後ろにある問いだ。検査する側が間違ったとき何が起き、それをどう気づき、自動採点の結果をいつ信じてよいのか。テストやリンターやレビュー用スクリプトを信頼の根拠として使う人にも同じ話になる。

1. 失敗は騒がしく、誤通過は静かだ

検査器が出しうる誤りは二方向ある。無い問題を有ると言う誤検知、有る問題を無いと言う見落とし。二つの誤りは対称的に生じるが、発見される確率はまったく対称ではない。

誤検知はただちに人の前に置かれる。ビルドが赤くなり、デプロイが止まり、誰かが該当行を開く。たいていは数分で正体が割れる。一方、見落としは何の痕跡も残さない。ログに一行増えることもなく、ダッシュボードの数字はむしろ良く見えることさえある。見落としを発見する唯一の経路は別のきっかけで問題が起きた後にさかのぼることだが、その頃にはすでにその検査器を根拠にした数か月分の判断が積み上がっている。

この非対称が生む実務的な帰結がいくつかある。

  • 検査器に手を入れるとき誤検知を減らす方向にだけ圧力がかかる。見落としを増やせと要求する人はいないが、うるさいのを静かにしてほしいという要求は毎週来る
  • 条件を一つ足して誤検知を消すと、その条件が切り捨てる本物の違反も一緒に消える。その損失は画面に表示されない
  • 検査器の品質を捕まえた件数で評価すると向きが反転する。何も捕まえない検査器がいちばん静かでいちばん評判が良い
  • 慢性的に誤検知を出すルール一つがリスト全体を無視させ、本物の違反を長く覆い隠す

最後の項目はとくに厄介だ。このサイトのレビュー用ツールでも、あるルールが特定の言語版で常に同じ項目を違反として上げ続け、その警報を習慣的に飛ばすうちに、その下に混じっていた本物の欠陥二件を二か月近く見逃した。検査器は正常に動いていた。人が検査器を信頼しなくなったことが欠陥だった。

2. 他人を検査するコードが間違う四つの形

検査器の欠陥を型に分けておくと、どこから見るかが決まる。実際に出会う形はおおむね四つだ。

型症状なぜ見えないのか捕まえ方
ルールが狭い正解の別の形を違反に数えるか、まったく見ないルールを書いた人が知る形だけが入った性質の違う二番目の判定と突き合わせる
見る範囲が狭い検査対象そのものが抜けてゼロが出る対象数が出力になくゼロ件と区別できない検査した対象数を常に出力する
形だけ見る名前・タグ・拡張子が合えば通る合格は根拠を残さない陽性サンプルを埋め込み検知を確認
基準が間違っている検査器は正確に回るが基準そのものが誤答すべての判定者が同じ基準を共有する人が少量のサンプルを直接ラベリング

四つのうち前の三つは道具で捕まえられる。四つ目だけは道具で捕まえられない。基準が間違っていれば、ルールベースの検査器もモデル判定者も同じ答えを出し、一致率はむしろ美しく出る。

3. ルールが狭いと、あるものを無いと報告する

もっとも多い型だ。ルールを書くとき、人は自分が見た形を書く。問題は有効な形が複数あるのにルールには一つしか入らないことだ。

先に触れた採点記録で割れた二件のうち一つが、まさにこの形だった。答案がある項目を処理しなかったのではなく、サイズを聞き返して確認を求めたケースだったのに、採点コードは確定リストにその項目コードが入っているかだけを機械的に確認した。リストに無いので欠落として数えた。人が読めば明らかに適切な応答であり、文書全体を読んだモデルもそう判定した。

この構造はドメインを問わず繰り返される。

  • 日付形式を一つしか知らないパーサーが、表記が変わった日からデータ無しを報告する
  • 語順を仮定した正規表現が、ある言語では誤検知を撒き、別の言語では丸ごと捕まえられない
  • 否定表現を要求するルールが、否定語なしで同じ意味を伝える文をすべて取り逃がす
  • 合格条件を完全一致で書いたせいで、同義語や省略形が不合格になる

二番目と三番目は、このサイトの多言語レビューで実際に遭遇した型だ。その場で作った正規表現で規模を測ると言語ごとに違う方向へ外れ、その数字を根拠に一括編集を回すと、すでに正常な文書に同じ内容がもう一度入る。

以下は考え方を示すための例だ。動作を検証していない疑似コードであり、実際の採点器にそのまま入れることを前提にしていない。

# 狭いルール - 確定リストにコードがあるかだけを見る
def is_handled_narrow(answer, item_code):
    return item_code in answer.confirmed_codes

# 広げたルール - 聞き返しも有効な処理と認める
def is_handled(answer, item_code):
    if item_code in answer.confirmed_codes:
        return True
    if answer.has_clarification_request(item_code):
        return True          # 確認要求は未処理ではない
    return False

大事なのはコードではなく順序だ。ルールを広げる前に、広げる必要があるという事実を先に知らねばならない。狭いルールは自分から狭いとは言わない。

4. 見る範囲の外は存在しないことになる

ルールが正しくても、ルールを適用する入力が来なければ結果は同じだ。検査器の入力境界がそのまま死角の定義になる。

同じ採点記録の二つ目の不一致がこの型だった。答案の書き手が確認要求を指定された欄ではなく余白に書いており、コード採点器は指定フィールドだけを読むように書かれていたので、そのメモの存在自体を知らなかった。モデルは文書を丸ごと読んだのでそれを見た。ルールの問題ではなく入力範囲の問題だった。

実務でこの型が隠れる場所は決まっている。

  • ファイル一覧を作るパターンが、隠しファイルや特定の拡張子を静かに落とす
  • ログを末尾から一定行だけ読む検査が、その手前で起きた事象を見られない
  • エンコーディングの違うファイルで読み込みが失敗し、例外が飲み込まれて対象ゼロ個につながる
  • フィルター条件が前段ですでに大半を落とし、検査段階には数件しか届かない

対策は単純で、単純なだけによく守られない。検査した対象数を常に出力に刻め。違反ゼロ件と対象ゼロ個はまったく違う事象なのに、出力が同じなら区別する方法がない。対象数が昨日と大きく変わったときの警告まで付ければ、静かな切断はほぼ捕まる。

5. 名前だけ見て通す検査

三つ目の型は形と意味を取り違える検査だ。クラス名があればスタイルが当たっていると見なし、スキーマのキーがあれば値が有効だと見なし、タグがあれば内容が正しいと見なす。存在検査を内容検査と勘違いしている。

このサイトのレビュー用ツールから出た型が二つここに当たる。一つはリンクが存在するかだけを確認する検査だった。リンクはすべて生きていたので結果は長らくきれいだったが、実際の問題は英語の文書が韓国語のページを指していることだった。言語が一致するかを見るルールを別に追加してから、ようやく大量に露見した。

もう一つはマークアップを文字列で探すルールだった。タグに属性が一つ付いた途端にパターンが合わなくなり、検査器はエラーを出す代わりに静かに通した。違反ゼロ件が出力され続けた。あるのに見つけられないルールは、無いルールより悪い。無いルールは少なくとも見ていないと知られているが、見つけられないルールは見たと錯覚させる。

覚えておきたい一文。検査器が合格を出力するとき、それは対象が正しいという意味ではなく、このルールに引っかからなかったという意味だ。二つの文の距離は、ルールが狭いほど遠くなる。

6. 交差検証 - 違う二つが違うことを言うとき

ここまでの型には共通点がある。検査器は単独では自分が間違っているという信号を作れない。だから信号を外から持ち込む必要があり、その方法が交差検証だ。

ただし、どの二つでもよいわけではない。二人の判定者が同じ前提を共有してはいけない。同じパーサーを使う二つの検査器、同じ正規表現を使い回した二つのルールは、交差ではなく重複だ。同じ地点で一緒に間違える。

採点方式強い場所構造的な死角再現性
ルールベース検査形式・数値・存在の有無。速くて安い予期しない有効な形を違反に数える完全再現
参照解答との照合正解が一つに定まる課題正解が複数ある課題では無力完全再現
モデル判定意図・文脈・文書全体。二番目の実装が安い同じ入力に同じ判定が来ないことがある部分再現
人によるラベリング基準そのものの妥当性を唯一検査する規模が出ず、人どうしでも割れる部分再現

表から読むべきなのは各行の長所ではなく、死角どうしが重ならないという事実だ。ルールベースは形に強く意図に弱い。モデル判定は逆だ。この二つを並べると片方の死角区間で判定が割れ、割れた地点がそのまま調査リストになる。

運用ルールは単純だ。一致は情報が少なく、不一致こそが情報だ。二つの判定が同じでも両方正しい保証はないが、二つの判定が違えば少なくとも一方は確実に間違っている。全体を再検討する代わりに割れた数件だけ人が開けばよいという点で、費用も引き受けられる。

7. LLMを二番目の採点者に据えて得られるもの

交差検証は古い発想だ。しかし実際にはほとんど行われなかった。理由は明確で、二番目の実装を作る費用が一番目と同じくらいだったからだ。採点器を二度書こうという提案は、どの会議でも通りにくい。

モデル判定が変えたのは精度ではなくこの費用だ。採点基準を自然言語で整理して渡せば二番目の判定が返る。先の採点記録で実際に起きたのもそれだった。採点器を書き直さずに同じ基準を文にしてモデルへ渡しただけで二つの独立した採点結果が生まれ、その差がバグを指した。

モデル判定がルールベースととくに違う振る舞いをする地点は三つある。

  • 範囲が広い。指定された欄だけを見る代わりに文書全体を読む。余白に書かれたものも入力に入る
  • 形ではなく意図を見る。表現が違っても意味が同じなら同じに判定し、聞き返しのようにルールが知らなかった有効な形を認める
  • 基準を言葉に直させる。モデルへ渡す文を書くうちに、コードへ暗黙に埋まっていた仮定が表に出る

三つ目は副次的効果に見えて価値が大きい。基準を自然言語で完結するように書いてみると、チームが合意したと信じていた項目のうち一度も合意されていなかったものが出てくる。

8. LLM採点者の限界 - 非決定性と共有された誤解

同じ理由で気をつけることも明確だ。モデル判定をルールベース検査と同じ席に置いてはいけない。

第一に、再現しないことがある。同じ答案を同じ基準で二度採点したとき、同じ結果が来る保証はない。関門にそのまま掛けると、コードを一つも直していないのに再実行だけで結果がひっくり返る。関門に使うなら複数回回して多数決を取るか、判定そのものではなく不一致の検出用途に限るほうがよい。

第二に、基準が間違っていれば一緒に間違える。これがより根本的な限界だ。誤った採点基準をそのまま受け取ったモデルは、その基準に忠実に間違った判定を下す。そして同じ基準で書かれたルールベースの検査器と仲良く一致する。一致率が高いという事実は二人の判定者が正しい証拠ではなく、二人が同じ前提を共有している証拠でもありうる。交差検証は実装の誤りを捕まえるが、基準の誤りは捕まえない。

第三に、一致率はサンプル構成に左右される。先の採点記録で書き手本人が挙げた限界でもある。二十九件のうち二十六件が正解だったので、二人の採点者が何もしなくても一致率は高く出る。識別力を測るには間違ったサンプルが十分に入っていなければならない。良い答えばかり集めたサンプルから出た高い一致率は何も証明しない。

第四に、採点者を採点する問題がまた生じる。モデル判定を検証するには別の判定者が必要で、その判定者にも検証が必要だ。この後退は道具では終わらない。どこかで人が少量のサンプルを直接読んでラベルを付ける必要があり、そのラベルが底になる。すべてを見ることはできないので、人が見るサンプルをどう選ぶかが設計上の問題になる。

9. 検査器に回帰テストを付ける

交差検証は予想できなかった型を見つける仕掛けだ。逆にすでに知っている型が捕まり続けるかを守る仕掛けが別に要る。それが検査器に付ける回帰テストだ。

方法は名前のとおりだ。検査器が必ず捕まえるべき欠陥を手で作ってサンプルに埋め込み、検査器を回してそれが全部引っかかることを断言する。同時に絶対に引っかかってはいけない正常サンプルも置き、何も引っかからないことを確認する。通常のコードの単体テストとは向きが逆だ。正常入力に正常出力を期待する代わりに、異常入力に警報が鳴ることを期待する。

埋め込むサンプル期待する判定失敗したときの意味
過去に実際に起きた欠陥必ず検出同じ事故がまた通過する
ルール文面の境界値必ず検出ルールを狭めて検知力が削られた
誤検知を出したことのある正常例検出なし誤検知がよみがえった
表記だけ違い意味は同じ正常例検出なしルールが形に過適合した
対象リストが空の入力対象ゼロ個と報告ゼロ件とゼロ個を区別できない

次は考え方を示すための骨組みだ。実行して検証していない例であり、フレームワークや表記は環境に合わせて変えるべきだ。

# 検査器そのものの回帰テスト (概念例、動作未確認)
POSITIVE = [                      # 必ず引っかかるべきサンプル
    ("case_missing_field", "MISSING"),
    ("case_wrong_order",   "CRITICAL"),
]
NEGATIVE = [                      # 絶対に引っかかってはいけないサンプル
    "case_clarification_request",  # 聞き返しは正常な処理
    "case_note_in_margin",         # 余白のメモも読むべき
]

def test_checker_detects_known_defects():
    for sample, expected in POSITIVE:
        assert run_checker(load(sample)).kind == expected

def test_checker_stays_quiet_on_valid_input():
    for sample in NEGATIVE:
        assert run_checker(load(sample)).violations == []

def test_scope_is_not_silently_empty():
    result = run_checker(load("case_empty_scope"))
    assert result.scanned_count == 0   # ゼロ件ではなくゼロ個だと区別する

運用でこれを生かし続けるルールが一つある。新しい型を見つけるたびに、その型をサンプルへ追加する。増えたサンプルが同じ事故を二度起こさせない。ルールに手を入れるときこのテストを先に回せば、検知力が削られる瞬間が画面に出る。回帰テストなしでルールを狭めるのは、目を閉じて感度を下げることと同じだ。

10. 採点器を直すと古い点数は何になるのか

検査器のバグを直しても、うれしいことばかりではない。対象が一つも変わっていないのにすでに公表した点数が変わる。先の採点記録でも、モデルと答案がそのままなのに採点器を直したという理由だけで公開済みの結果が違ってしまった。

ここから出てくる原則は短い。点数は対象だけの関数ではなく、対象と採点器の版の関数だ。採点器を明かさない点数は単位のない数字と同じだ。とくに複数回を時系列に並べて傾向を読む瞬間、違う物差しで測った値が一つのグラフに乗る。

  • 点数を記録するとき採点器の版とルール内容の指紋を一緒に残す
  • 採点器を直した日には過去の対象を全量再採点して時系列を差し替える
  • 再採点が不可能なら、グラフに採点器の変更時点を縦線で示し、発表文にはどの版で測った値かを一行で明記する
  • 外部の点数を引用するときも同じ問いをする。この値はどの採点器で測ったものか

最後の項目はベンチマークの数字を読むときにそのまま当てはまる。同じ名前の評価でも採点の実装が違えば値は変わる。二つの組織が発表した同名の点数を並べる比較がしばしば成立しない理由がそれだ。

11. 自動採点を信頼する前の点検リスト

ここまでの内容を実行できる形に圧縮するとこうなる。新しく作った検査器でも、引き継いで使っている検査器でも、同じ順で問えばよい。

  • 検査した対象数が出力にあるか。なければゼロ件とゼロ個を区別する方法がない
  • 陽性サンプルが実際に引っかかるか。既知の欠陥を埋め込んで回してみるまで検知力は未知数だ
  • 陰性サンプルが引っかからないか。誤検知が積み上がると人はリスト全体を無視し始める
  • ルールごとに最近何かを捕まえた履歴があるか。何か月もゼロのルールは静かに死んでいる可能性がある。性質の違う二番目の判定と突き合わせたことがなければ、見落とし区間は丸ごと未測定だ
  • 人が少量のサンプルを直接読んでラベルを付けたことがあるか。基準そのものの誤りはここでしか露見しない
  • サンプルに間違った事例が十分入っているか。正解ばかり集めたサンプルから出た高い一致率には情報がない
  • 採点器の版が点数と一緒に記録されるか。そうでなければ回どうしの比較が成立しない
  • 結果が割れたとき人が開く手続きがあるか。不一致を自動で片方へ寄せると信号が消える

順序に意味がある。上の二つは午後半日で付けられ、それだけで最も多い失敗を防ぐ。下へ行くほど費用が増えるので、判定の重さに合わせてどこまで行くか決めればよい。デプロイを止める関門なら最後まで、参考用の警報なら前の四つで足りることが多い。

確認できなかったこと

根拠を示せない項目を一か所にまとめておく。

  • モデル判定の再現性の数値。同じ入力を複数回採点したとき判定がどれだけ揺れるかは、課題と基準とモデルによって変わる。一般化できる値は確認できなかった
  • どのモデルが採点者としてより優れるという比較。製品間の優劣を判断する根拠がない。この記事の論旨は特定のモデルではなく、性質の違う二つの判定を並べる構造にある
  • 交差検証が捕まえる欠陥の割合。先に引用した記録は二十九件中二件だったが、サンプルが小さく正解に偏っているので一般的な割合としては読めない
  • 回帰テストを付けたときの定量的な効果。見落としがどれだけ減るかを測るには見落としの真値を知る必要があるが、その値を知る方法自体が問題の出発点だ
  • 人によるラベリングの適正サンプル数。何件を人が読めば基準の誤りが露見するかは、課題の難度と失敗類型の分布に左右される

結論: ゼロ件は結論ではなく主張だ

検査器が出力する違反ゼロ件は事実の記述のように見えて、実際には主張だ。このルールでこの範囲を見たとき引っかかるものが無かったという主張。根拠は三つに圧縮される。

第一に、何を見たかを明かせ。検査した対象数を出力に刻む一行が、いちばん安上がりな防御だ。静かな切断はこの一行だけでほぼ露見する。

第二に、捕まえられることを示せ。既知の欠陥を埋め込んで検査器がそれを捕まえる回帰テストがあれば、ゼロ件は何も見なかった結果ではないという根拠になる。このテストは、ルールに手を入れるたびに検知力が削られる瞬間を画面に出す。

第三に、別の目と突き合わせろ。性質の違う二番目の判定を並べ、割れた地点だけ人が開く。モデルを二番目の採点者に据える方式がいま価値を持つ理由は、判定がより正確だからではなく二番目の実装を作る費用が下がったからだ。

最後に一つ。この三つの仕掛けをすべて備えても防げないものが残る。採点基準そのものが間違っている場合だ。そのときはルールベースの検査器もモデル判定者も同じ誤答を仲良く出し、一致率はむしろ良くなる。基準の誤りは道具ではなく、人がサンプルを直接読むときにだけ露見する。自動化が代わってくれない席が、まさにそこだ。
