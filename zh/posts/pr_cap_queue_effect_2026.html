「最多开3个PR」并不会缩短评审队列 - 上限规则与队列动力学

把上限3、5、10、20放进900天的队列模型，实测拦截率与等待时间的尾部

2026-07-31 开发与基础设施

引子: 改成「最多3个」了，待办列表却没变

假设某个仓库等待评审的条目超过了200件。会议上得出的结论通常是熟悉的样子：「限制每人同时只能打开3个。」规则上线，一个月过去，待办列表的长度还是老样子。

这时候的反应通常分两种。要么认为规则太松而把上限收得更紧，要么说这种规则本来就没用而悄悄作废。这篇文章讨论第三种可能：加上限的那个点，本来就不是瓶颈。

出发点是2026年7月30日发布在news.hada.io的一则话题，标题说PR数量限制在实际队列中只拦下2到13%。我没有转述那份报告，而是决定自己把同一个问题跑一遍。某个产品内部如何判定、在什么条件下判定，从外面是看不到的，所以本文只建立一个通用的队列模型，并且只在这个模型内部说话。下面所有数字都要带着「在这个模型里」的限定来读。

先说结论。拦截率低并不说明规则松。队列变长是因为处理慢，不是因为到达多，而上限只是推迟到达，并不会让处理变快。所以收紧上限也不会让等待变短。但这不代表上限永远无用，在某些条件下它确实会咬住，这些条件同样可以用数字指明。

本文不再讲怎么开PR、怎么写评审意见。需要那些内容可以看Pull Request与代码审查。这里讲的是队列的动力学。

1. 模型 - 建立了什么

模型刻意做得很小，这样每个数字都能一路追溯到它的来源。

  • 40位作者。各自产生工作项并放进一个共用队列
  • 新工作项每天平均9.6件进来，用泊松分布
  • 工作项归属哪位作者用齐普夫分布(s=1.0)抽取，以便造出少数人打开大部分工作的现实倾斜
  • 评审侧可以同时持有30件，每件平均占用槽位3.0天，用几何分布
  • 因此服务率是每天10.0件(30除以3.0)，利用率是0.96(9.6除以10.0)
  • 上限定义为「一位作者同时可以打开的最大件数」，只在这一点起作用，别处一概不起作用
  • 模拟900天，前300天作为预热丢弃，只统计剩下的600天
// sim.js - node v22.16.0 / win32. fixed seed, so every number below reproduces.
const SEED = 20260731;

function mulberry32(a) {                        // deterministic PRNG
  return function () {
    a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
function poisson(rng, lambda) {                 // Knuth
  const L = Math.exp(-lambda); let k = 0, p = 1;
  do { k++; p *= rng(); } while (p > L);
  return k - 1;
}
function geom(rng, p) {                         // support 1,2,3,... mean 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

// A       how many authors
// lambda  new items per day          R  concurrent review slots
// S       mean days one review occupies a slot   =>  service rate mu = R / S
// cap     how many items one author may have open at the same time
function simulate({ A = 40, s = 1.0, lambda = 9.6, R = 30, S = 3.0,
                    days = 900, warmup = 300, cap = Infinity,
                    retry = false, seed = SEED }) {
  const rng = mulberry32(seed), cum = zipfCum(A, s), p = 1 / S;
  const open = new Int32Array(A);
  let queue = [], active = [], deferred = [];

  for (let d = 0; d < days; d++) {

    // 1. reviews whose duration has elapsed give their slot back
    const still = [];
    for (const it of active) {
      if (it.endsAt <= d) { open[it.author]--; record(it, d); }
      else still.push(it);
    }
    active = still;

    // 2. today's items, plus anything blocked earlier if retry is on.
    //    author and review duration are drawn HERE and never re-drawn, so
    //    changing cap does not shift the random stream.
    const todays = retry ? deferred.splice(0) : [];
    for (let i = 0, n = poisson(rng, lambda); i < n; i++)
      todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

    // 3. the cap is applied here and nowhere else
    for (const ev of todays) {
      if (open[ev.author] >= cap) {             // blocked
        ev.tries++;
        if (retry) deferred.push(ev);           // comes back tomorrow
        continue;                               // otherwise dropped
      }
      open[ev.author]++;
      ev.opened = d;
      queue.push(ev);
    }

    // 4. free review slots pull from the head of the shared FIFO
    while (active.length < R && queue.length) {
      const it = queue.shift();
      it.started = d;
      it.endsAt = d + it.dur;
      active.push(it);
    }
  }
}

[3, 5, 10, 20, Infinity].forEach(cap => report(simulate({ cap })));

设计上有一点格外用心：改变上限值不能让到达序列和评审时长发生偏移。如果在工作项被创建的那一刻就把作者和评审时长一起抽好，那么之后上限是拦下它还是放行它，都不会改变随机数的消耗量。不这样做的话，每个上限值就是在跟不同的世界比较，差异究竟来自上限还是来自运气就无法分辨。我在第一版里正好犯了这个错，是看到每换一次上限总到达数就在5,645到5,793之间晃动才发现的。

          review side holds 30 items at once, each for Geometric(mean 3.0 days)

运行环境。下面所有输出都是在Windows 10 Pro (10.0.19045)上用Node.js v22.16.0 (win32)实际跑出来的。随机数生成器是mulberry32，种子固定为20260731。用同一个种子重跑会得到同样的数字。脚本是保存成文件后执行的，没有通过shell参数或here文档传递。

本文不主张什么。这个模型不是任何产品的实现。某个具体服务在什么条件下拦下什么、上限对谁生效，这里都不涉及。这里涉及的只有「每位作者同时打开数上限」这种形态的规则在一个通用队列里如何表现，仅此而已。

首先新工作项这一列五行都是5,764。前面说的设计在这一列得到了印证：同一条到达序列只换上限，所以下面的所有差异都归于上限。

上限20在5,764件里拦下了8件。有规则和没规则的差别，按完成件数算是3件。上限10也只有2.52%，完成5,584件，是基线的98%。这两个与其说是规则不如说是装饰。

降到上限3就拦下22.62%了。这里必须同时看同一行的完成列。它从5,699件掉到了4,436件。拦下多少就意味着多少没有通过，等待并没有变快。这是因为这张表把被拦下的工作丢弃了，不丢弃而让它重试会怎样，第5节会看到。

下面把种子换成五个再跑的表同样重要。上限3落在20%到23%，上限5落在10%到12%，上限10落在1%到3%，上限20落在0%到0.4%。次序和量级都保持住了。这不是某一条随机序列造成的偶然。

3. 为什么这么低 - 根本没人靠近上限

接下来才是正题。为什么上限10只能拦下2.52%？答案在每位作者同时打开数的分布里。

一个数字几乎解释了全部。57.03%的作者日什么都没打开。算上1件是81.34%，算上2件是89.84%。上限3第一次触及的地方，是剩下的10.16%。

  • 排第1的作者一个人就产生了全部工作的24.4%，平均打开9.60件，峰值到过25件。对这个人来说连上限10都会经常撞上
  • 第2位产生11.7%，平均4.69件，从上限5开始被拦
  • 第9到第40共32人平均只有0.42件。对他们来说上限3是不存在的规则
  • 在测量期内曾经碰到上限3的作者是40人中的13人，上限5是8人，上限10是2人，上限20是1人

这就是低拦截率的真相。不是规则松，而是规则能够触及的对象少。用总量比例报告时这个事实被翻译成「效果甚微」，准确的说法应该是「效果覆盖的人群很窄」。而这个窄小人群同时贡献了相当大一部分吞吐，这一点在后面会成为问题。

4. 把倾斜推到极端会怎样

这里自然会有一个反驳：「我们团队比这个倾斜得多。」我把齐普夫指数从0.4扫到2.4做了确认。

  • 指数0.4时第1位产生6.6%，拦截率是1.08%
  • 基准值1.0时第1位产生24.4%，拦截率是11.57%
  • 指数2.4时第1位产生72.7%，拦截率是57.76%

倾斜加大，拦截率确实会上升。但是要看它是在哪一段上升的。拦截率要超过30%，就得有一个人产出全部工作的40%以上。在40人的组织里一个人产出全部的40%，那已经不是队列设计问题而是别的问题了。在现实的倾斜区间，也就是第1位产出6%到25%的范围内，拦截率停留在1%到12%之间。

而p90那一列反向移动这一点很有意思。倾斜越大，p90反而从3降到1。因为工作越集中到一个人身上，其余大多数就越停在0件。平均意义上的作者离上限更远了，只有一个人每天在撞墙。整体拦截率是对这个人群求平均得到的，于是把「一个人每天撞墙」和「所有人都稍有不便」压成了同一个数字。这正是讨论上限时不能只看整体比例的原因。

同样的陷阱在指标一侧的版本，写在把多台机器的p99平均的错误里。把分布不同的群体折叠成一个数字会丢失信息，结构上是一回事。

5. 拦下和减少不是一回事

到目前为止的表格都把被拦下的工作丢弃了。现实中不会丢。它们会在之后重新打开。于是改成被拦下的工作第二天重新尝试再跑一遍。

需要把三行并排来读。

  • 上限20：有13件至少被拦过一次，完成5,699件，和没有上限时完全一样。队列根本没察觉这条规则存在过
  • 上限10：628件被拦过，完成5,695件，比基线少4件。可是打开到完成的均值从4.05天改善到3.80天。同一次运行的端到端延迟是4.05天变4.06天，实质没动
  • 上限3：完成掉到4,450件，端到端延迟均值变成31.66天

上限10这一行是本节的核心。打开到完成的时间变好了，端到端却纹丝不动。上限做的只是把「工作项被算作打开状态的那段区间」缩短了。它把计时的开始按钮往后按，而不是把终点往前挪。可大多数看板测的正是打开到完成。这条规则什么都没改变，却改善了指标。

这里还有更难受的含义。在这个模型里第1位作者每天产生2.34件，评审平均要3天。上限是3的话，这个人能推过去的最大值是每天1件。当上限低于某人所需的速率时，他的个人积压会永远增长。上限3之下完成掉了22%就是这个原因。这不是「减少」，是「饿着」。

在利用率超过1的状态下，上限不是处方，是把症状挪出画面的装置。

两张表是同一批运行，只有测量的起点不同。上限在第一张表里看起来是改善，在第二张表里看起来是损害。而扩充处理能力在两张表里都朝同一个方向移动。只盯着其中一张，就会相信上限有效，而这个信念会在下个季度变成把上限收得更紧的提案。

均值几乎显示不出这个差别，这一点同样重要。上限3的打开到完成均值是3.02天，基线是4.05天，差一天。可端到端p99是13天对476天。均值把这条规则造成的最坏情形完全藏了起来。

8. 在饱和附近，稍微增加一点就会大幅下降

  • 走到利用率0.900时队列均值是3.9，只不过多加了两个槽位
  • 低于利用率0.800之后改善幅度急剧变小，因为已经几乎没有等待可以消除了

这种非线性有名字。因为等待时间大致与1除以(1减利用率)成正比。利用率0.993时这个系数是143，0.960时是25。能力提高了3%，系数却变成了五分之一。这就是饱和附近小改动带来大效果的原因。反过来，在利用率0.8的地方同样提高3%，几乎什么都不会发生。

最后的等效对比就是本文的摘要。上限3(30个槽位)对无上限(32个槽位)：上限那一侧是打开到完成3.02天、端到端31.66天、完成4,450件。多加两个槽位那一侧是打开到完成3.40天、端到端也是3.40天、完成5,723件。只看打开到完成的话上限略胜，其余每一项指标都输。

由此得出一条规则。上限只有落在每位作者同时打开数的p90之下时才会咬住。基准设置里p90是3，所以上限3拦下22.62%，上限5拦下11.57%，上限10拦下2.52%。6人团队里p90是15，所以连上限5都拦下了34.21%。意思是在定上限值之前应该先测这个分布。

第四行很重要。上限改变人的行为这一效果，本模型无法测量。这个模型里的作者被拦下后不会把工作拆得更小，只是第二天重新尝试同一件。如果在真实组织里上限作为「先完成一件再打开下一件」的纪律起作用，那是这次模拟捕捉不到的真实效果。但如果是冲着这个效果加上限，目的就不该写成缩短队列。

增加规则文档和增加强制点是两回事，这个话题在长篇政策文档管不住智能体里单独讨论过。

10. 该测什么

与其争论上限该定多少，不如去测下面这些，争论本身就会消失。

指标定义本模型中的值为什么要测
服务率单位时间完成的评审件数每天10.0件决定队列长度的是这一侧
到达率单位时间新打开的件数每天9.6件超过服务率队列就会无限增长
利用率到达率除以服务率0.96越过0.9等待会非线性上升
等待尾部打开到完成的p90与p998天与13天均值会掩盖最坏情形
端到端延迟从准备好到完成基线4.05天，上限3时31.66天包含被上限推出去的时间
打开数分布每位作者的p50 / p90 / p990 / 3 / 10告诉你上限能触及的人群有多大
队列长度趋势按周的斜率利用率1.04时上升单个快照看不出发散

转成检查清单就是这样。

  • 在讨论上限之前先测了服务率与利用率
  • 知道每位作者同时打开数的p90，并确认上限落在它之下
  • 把队列长度当作按周的斜率看，不用单个快照下判断
  • 把等待时间当作p90与p99看，而不是均值
  • 分开测量打开到完成与端到端延迟，上限只会让前者变好
  • 有能看见被拦下的工作堆在哪里的界面
  • 利用率越过0.9时优先考虑扩充处理能力
  • 在文档里写清上限的目的是缩短队列还是强制聚焦

11. 这个模型没有复现的部分

不写清模型的边界，上面的数字就会被读得比实际更强。把没有复现的东西如实列出来。

  • 评审人分配与专长领域。这里只有一个共用的先进先出队列。因为某个领域只有一个人能看而产生的瓶颈没有被复现
  • 优先级与加急处理。没有插队。现实中紧急的会往前挪，其余的尾巴会因此更长
  • 评审后的修改与再评审。没有返工循环。有它的话有效服务率会下降，利用率会上升
  • 工作项大小的差异。所有件都从同一个分布抽取时长，大活小活混在一起的效果不存在
  • 上限改变人的行为的效果。这个模型里的作者被拦下后不会把工作拆小。上限最有说服力的优点在这里缺席了
  • 长期打开的工作自身变慢的效果。没有冲突、基线变化、上下文流失。现实中开着越久越难完成
  • 星期周期与休假。到达和处理在每一天都服从同一个分布

其中第三项和第五项可能把结论往反方向推。返工循环会拉低服务率，从而提高上限的必要性；行为改变的效果则会让本文低估上限的收益。所以本文的结论不是「上限不好」，而是「上限不是用来缩短队列长度的工具，为那个目的使用它，只会让指标变好看」。

# 上限规则与队列 — 该测什么，该修什么

> 来源: braindetox.kr — 「最多开3个PR」并不会缩短评审队列
> 验证: node v22.16.0 / win32，固定种子 20260731，900天模拟(前300天丢弃，测量600天)
> 此处所有数字仅在该模型内部成立，并非对任何产品内部行为的断言。

## 1. 模型概要

```
作者40人 · 新工作项 Poisson(9.6件/天) · 作者抽取 Zipf(s=1.0)
评审侧同时持有30件 · 每件 Geometric(平均3.0天)
服务率 mu = 30 / 3.0 = 10.0件/天 · 利用率 rho = 9.6 / 10.0 = 0.96
上限(cap) = 一位作者同时可以打开的最大件数
```

## 2. 复现代码(核心循环)

```js
const SEED = 20260731;

function geom(rng, p) {                  // 支撑集 1,2,3... 均值 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

for (let d = 0; d < days; d++) {
  // 1. 时长已到的评审归还槽位
  const still = [];
  for (const it of active) {
    if (it.endsAt <= d) { open[it.author]--; record(it, d); }
    else still.push(it);
  }
  active = still;

  // 2. 今天的新工作项。作者与评审时长在这里只抽一次，
  //    这样改变 cap 也不会让随机数列错位。
  const todays = retry ? deferred.splice(0) : [];
  for (let i = 0, n = poisson(rng, lambda); i < n; i++)
    todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

  // 3. 上限只在这里起作用
  for (const ev of todays) {
    if (open[ev.author] >= cap) {         // 被拦截
      ev.tries++;
      if (retry) deferred.push(ev);       // 明天再试
      continue;                           // 否则丢弃
    }
    open[ev.author]++;
    ev.opened = d;
    queue.push(ev);
  }

  // 4. 空闲评审槽位从共用FIFO队首取出
  while (active.length < R && queue.length) {
    const it = queue.shift();
    it.started = d; it.endsAt = d + it.dur;
    active.push(it);
  }
}
```

## 7. 与其争论上限值，不如测这些

| 指标 | 定义 | 为什么要测 |
|---|---|---|
| 服务率 mu | 单位时间完成的评审件数 | 决定队列长度的一侧 |
| 到达率 lambda | 单位时间新打开的件数 | 超过 mu 队列会无限增长 |
| 利用率 rho | lambda / mu | 越过0.9等待会非线性上升 |
| 等待时间尾部 | 打开到完成的 p90 / p99 | 均值会掩盖异常 |
| 端到端延迟 | 从准备好到完成 | 包含被上限推迟的时间 |
| 各作者打开数分布 | p50 / p90 / p99 | 告诉你上限能触及多少人 |
| 队列长度趋势 | 按周的斜率 | 上升说明 rho 越过了1 |

## 8. 检查清单

- [ ] 在讨论上限之前先测了**服务率(mu)与利用率(rho)**
- [ ] 知道每位作者同时打开件数的**p90**，并确认上限低于它
- [ ] 把队列长度当作**按周的斜率**看(不用单个快照下判断)
- [ ] 把等待时间当作**p90 / p99**看，而不是均值
- [ ] 分开测量**打开到完成**与**端到端延迟**(上限只会让前者变好看)
- [ ] 能看见被拦截的工作**堆在哪里**
- [ ] 利用率越过0.9时优先考虑**扩充处理能力**
- [ ] 在文档中写清上限的目的是**缩短队列**还是**强制聚焦**

## 9. 不要做的事

- 仅因为队列长就加上限 — 队列长度由处理决定而不是由到达决定
- 因为拦截率低就把上限收得更紧 — 低是因为那个点不是瓶颈
- **只看打开到完成的时间就报告改善** — 可能只是时钟起点被挪动了
- 在利用率超过1时用上限来应对 — 只有看得见的队列缩短，总量不变
- 把上限当作对少数多产作者的惩罚 — 他们贡献了相当大一部分吞吐

## 10. 该模型没有复现的部分

- 评审人分配与专长领域(这里只有一个共用FIFO)
- 优先级、加急通道、插队
- 评审意见后的返工与再评审
- 工作项大小的差异(所有件从同一分布抽取时长)
- 上限改变人的行为的效果(拆得更小、减少上下文切换)
- 长期打开的项目自身变慢的效果(冲突、基线变化)
- 星期周期与休假
