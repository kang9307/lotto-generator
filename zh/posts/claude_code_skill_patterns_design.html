缘起 - 一篇问设计判断而非结构的文章

2026 年 7 月 28 日，stock-engineer.com 发布了一篇题为「Claude Code 技能模式」的文章（9 月 29 日修改），GeekNews 将其作为 2026 年 10 月 4 日登记的条目介绍。原文分为七章。它从同一件工作为何每次都要从头说明出发，确立把技能视为工作判断标准而非命令集合的观点，然后依次讲到从 Anthropic 技能设计中读到的四条原则、按规模划分的构成方式、三个公开合集的设计思路、作者在实务中得到的五条经验，最后是判断是否值得拆成单独技能的六个问题。按作者简介，作者是有嵌入式软件开发经历的工程师，实务经验被描述为来自该开发工作和博客运营。

这一主题的基本结构和写法已在Claude Code Skills A-Z 指南中整理，具体某个技能是如何做出来的见Archify 分析。把规则放在上下文中与改成钩子这两种方式的结构性比较，见把 CLAUDE.md 规则编译成钩子的做法分析。这里只限于那些文章没有直接回答的问题，也就是设计判断：何时拆成技能，description 里写什么才能让调用时机吻合，哪些规则留在技能里，哪些交给钩子。

设计判断是一个证据种类容易混杂的领域。官方文档确定的事实、官方文档建议的做法、某个人说自己在实务中得到的经验，如果混在同一段里，读者就分不清哪里到哪里是规则。所以下面把原文的每条主张与官方文档对照，分成已确认的、只部分确认的、仍只是作者经验的。还要先说明，原文的钩子部分没有解释退出码 2，只有一句说具体设置和退出码陷阱已整理在另一篇受监管行业双重关卡的文章里。PreToolUse 事件和退出码 2 来自官方钩子文档，作为单独条目标出。

原文的主张与官方文档能确认的范围

下表把原文的七条核心主张与官方文档对照。「确认」指官方文档中有同样意思的句子，「部分确认」指只有一部分，「作者经验」指没有可供对照的官方句子。这并不表示作者的经验有误，只是官方文档没有涉及那个领域。

原文的主张与官方文档对照判定与备注

流水线技能串联各阶段，工具技能负责构建、测试、格式化、检查没有使用同样术语的句子。最佳实践说确定性操作要用脚本作者经验。偏好脚本是相邻的建议

  • 仍是作者经验的，恰好是流水线与工具的拆分，以及通用技能的局限。这两点在官方文档的范围之外，所以实务者的判断作用最大。
  • 原文关于钩子的叙述只有一句话的程度，即没有审查文档就拦住 push 命令的钩子，没有写实现方法，只有转到另一篇文章的说明。
  • 在技能成本的叙述中，原文把三者分开计数：技能约 50 个、智能体约 20 个、工具约 60 个。50 就是技能的数量，不是合计数。

description 不是说明文，而是触发语

原文把这一项列为第四条原则。原文说，description 不是写给用户的说明，而是智能体决定是否启用技能的信号，要求同时写明做什么和何时用。例子是：API 变更后需要兼容性测试和迁移验证的工作。官方资料方向一致。最佳实践解释说，description 是技能发现的依据，Claude 在可能多达 100 个以上的技能中选出合适的一个时用的就是这个字段。Claude Code 文档也写道，Claude 用该字段决定何时应用技能，省略时则改用正文的第一行非空内容。

下面的代码是 Claude Code 文档展示的 SKILL.md 头部格式，原样照抄了当前文档中的示例，文档说明该示例设置了四个字段。

---
                    name: my-skill
                    description: What this skill does
                    disable-model-invocation: true
                    allowed-tools: Read Grep
                    ---
                    Your skill instructions here...

这个例子里，与触发有关的字段不止一个。description 是判断调用时机的材料，把 disable-model-invocation 设为 true，则 Claude 不会自动加载该技能。同一文档的表中还有附加在 description 之后的 when_to_use、只让 Claude 调用的 user-invocable，以及用通配符限制启用范围的 paths。这意味着让调用时机吻合，并不只取决于一句话。

  • 做什么与何时一起写 - 最佳实践里的好例子，在提取 PDF 文本和表格、填写表单等功能之后，加上一句：处理 PDF 文件，或用户提到 PDF、表单、文档提取时使用。
  • 含糊的描述会失败 - 最佳实践列为坏例子的是 Helps with documents、Processes data 这样的句子。它们什么都没指明，无法与其他技能区分。
  • 用第三人称 - 最佳实践说，description 会注入系统提示，视角不一致可能导致发现问题，因此建议用第三人称。
  • 上限因文档而异 - 技能编写最佳实践给 description 的上限是 1,024 字符，而 Claude Code 文档说 description 与 when_to_use 合起来的文字在技能列表中于 1,536 字符处被截断。这两个数字出自不同文档的叙述，不能合并成一个。
  • 核心用途放前面 - 因为列表中可能被截断，Claude Code 文档要求把核心使用场景放在前面。
  • 流程放进正文 - 把流程塞进有上限的字段，会把调用时机的信号挤掉。这是由两个上限推出的解读，原文没有这样说。
  • 排除条件 - 关于如何写出「不该用的时候」，在查阅的官方文档范围内没有指引。当技能有重叠时，由设计者决定。

SKILL.md 是目录，细节放到外面

原文的第二和第三条原则指向同一个方向。为了渐进式披露，把 SKILL.md 当目录用，细节放进 references，可执行代码放进 scripts，模板放进 assets。指示只保留必须遵守的顺序、完成条件和禁止事项，背景说明移到单独文档。官方文档中与此对应的是 500 行建议。Claude Code 文档写道，SKILL.md 保持在 500 行以内，详细的参考内容移到单独文件。技能编写最佳实践也为了最佳性能给出同样的标准。

这条原则中需要设计判断的有两处。一是把什么挪出去，二是挪多深。官方最佳实践对后者很具体：参考文件要从 SKILL.md 以一层深度直接链接。当参考文件再指向另一个参考文件时，Claude 可能只预览文件开头就结束，导致信息不完整。超过 100 行的参考文件顶部要放目录，这一建议也出于同样的原因。

  • 500 行是建议 - 两份官方文档都写的是「保持」「为了最佳性能」，没有写超出后会被自动拒绝。
  • 一层深度 - 从 SKILL.md 直接链接到参考文件，避免该参考文件再指向别的文件的结构。
  • 长参考文件放目录 - 超过 100 行就在顶部放目录，让局部阅读时也能看到全部范围。
  • 写明是执行还是阅读 - 在指示中说明脚本是用来读的还是用来运行的。运行时只有脚本的输出占用令牌，内容不进入上下文。
  • 让自由度匹配任务 - 多种做法都有效时给文字指示，有偏好模式时给带参数的脚本，任务脆弱且顺序固定时则像「原样运行这个脚本」那样收窄指示。
  • 一个默认加例外 - 不要罗列许多工具，选定一个默认工具，只补充例外情形。

流水线技能与工具技能的划分标准

原文把这种拆分列为实务经验的第一条。作者描述，流水线技能把从读取工单开始，经分析、编写测试、实现、验证，直到创建 PR 的多个阶段串起来，其中的具体动作，即构建、测试、格式化、检查，由工具技能负责。官方文档里没有这两个术语，因此这种拆分要当作作者的设计经验。不过有相邻的建议可作依据。技能编写最佳实践说，确定性操作要用脚本，理由是比生成的代码更可靠、节省令牌和时间、保证每次使用的一致性。

拆分有意义的条件可以归纳为两个。第一，同一个动作在多个流程中重复出现。像构建和测试这样每条流水线都要经过的动作，单独拆成工具技能，流程变了，动作的定义仍留在一处。第二，流程经常变而动作固定。这两个条件不是原文直接写的，而是从作者叙述中读出的设计解读，原文给出的依据是拆分过这件事本身。

  • 流水线技能 - 持有阶段顺序、阶段之间的完成条件和禁止事项。原文的例子是从读取工单到创建 PR。
  • 工具技能 - 负责构建、测试、格式化、检查这类输入输出相对固定的动作。
  • 连接方式 - 流水线调用工具技能的结构。调用方式的细节原文没有。
  • 适用局限 - 没有依据说这种划分适合所有团队。原文说这来自作者自己的开发流水线和博客运营。

三个公开合集划出的轴

原文把三个公开合集作为不同设计思路的例子。原文作为公开合集列举的是 Superpowers、GSD、caveman 三个，这里也不再增加。在讲规模的部分，原文还举了基于 Karpathy 观察的 CLAUDE.md 项目和 42 个技能的目录，但那些是组成方式的例子。下表第二列是原文的概括，第三列是对它们各自代表技能设计哪一条轴的解读。

合集原文的概括所代表的设计轴（解读）
Superpowers强制开发流程的技能。头脑风暴、计划、RED-GREEN-REFACTOR 实现、规格审查、代码质量审查流程的强制。顺序与审查阶段是技能的核心
GSD从 discuss 到 execute 分割上下文。discuss、plan、execute、verify、ship。拆成小计划，减少主会话上下文的膨胀上下文的分离。把各阶段用到的上下文分开
caveman调节输出密度而非流程。减少冗长说明和惯用语，只输出核心结果输出的调节。改变的是回应方式而不是工作顺序

原文把这三个与按规模划分的构成方式放在一起。单一规则文件安装和维护简单，但难以容纳按任务划分的详细流程。小型技能集容易拆出重复的开发流程，但角色边界可能重叠。大型技能目录能广泛支持多种职务和业务，但检索、权限和版本管理会变复杂。这三者的优缺点是照搬原文的表，官方文档并没有同样的分类。

  • 单一规则文件 - 优点是安装和维护简单，注意点是难以容纳按任务划分的详细流程。
  • 小型技能集 - 优点是容易拆出重复的开发流程，注意点是角色边界重叠。
  • 大型技能目录 - 优点是支持面广，注意点是检索、权限、版本管理的复杂度。

陷阱清单放在哪里

原文的第一条原则是，好的技能不只写正常流程，还要写明常见错误和失败模式。它举的例句是：不要仅凭测试通过就断定需求已满足。这条原则在第二条实务经验里遇到了问题。作者说，陷阱清单增长的速度超过技能正文能承受的速度，采取的办法是把陷阱拆到技能之外的知识文件。技能正文只放流程，知识文件把每个会话得到的教训，按评审、格式、构建、测试、CI、设计之类的前缀分类积累。

官方文档中与此接近的是参考文件的拆分，以及对时效性信息的处理方式。最佳实践说，快要过时的信息不要放在主体里，而是折叠进 old patterns 一节。陷阱的过时速度各不相同，这正是与该建议相接之处。但按前缀分类以及逐会话积累的运作方式，是官方文档里没有的作者做法。

  • 放正文的陷阱 - 跳过步骤就会立刻失败的禁止事项。对应原文第三条原则中的必需顺序、完成条件和禁止事项。
  • 放知识文件的陷阱 - 随会话不断增加的个别案例。按前缀分类，只读需要的类别。
  • 会过时的陷阱 - 绑定特定版本或时间点的陷阱，集中放在 old patterns 之类的区域，与正文分开。
  • 哪些算经验 - 区分正文与知识文件的标准是按上面的方式解读的，原文没有用数字给出标准。

技能下指示，钩子来拦截 - 角色分工

原文的第四条经验就是这种分工。作者说，与其在技能里写一条「先创建审查文档再 push」的指示，不如用一个在缺少审查文档时直接拦住 push 命令的 Claude Code 钩子来强制执行。概括起来，技能说「要做」，钩子让你「做不了」。原文没有解释钩子的事件和退出码，只说具体设置和退出码陷阱已整理在另一篇受监管行业双重关卡的文章里。下面是官方钩子文档所确认的部分。

在官方钩子文档中，退出码 2 是阻断错误。在可以阻断的事件上，无论是否输出了 JSON，退出码 2 都会阻断，JSON 中的 permissionDecision 即使是 allow 也无法覆盖。在 PreToolUse 中，退出码 2 会阻止工具调用。阻断消息在有 JSON 时用其中的理由，否则用标准错误文本。退出码 0 表示成功，其他退出码在大多数事件上本身并不阻断。

{
                      "hookSpecificOutput": {
                        "hookEventName": "PreToolUse",
                        "permissionDecision": "deny",
                        "permissionDecisionReason": "Destructive command blocked by hook"
                      }
                    }

上面的 JSON 是官方文档作为退出码 2 的替代方案展示的 PreToolUse 结构化输出。permissionDecision 可用的值有 allow、deny、ask、defer。钩子在 settings.json 这类 JSON 设置文件或插件中定义，并用 matcher 字段筛选对哪些工具做出反应。官方钩子参考把钩子描述为 shell 命令、HTTP 端点、MCP 工具调用、LLM 提示或子智能体。「确定性（deterministic）」这一表述出自钩子指南，意思是钩子不依赖 LLM 的选择，在固定时点总会执行。这一性质支持原文的分工，也就是不得违反的规则交给钩子的判断。

  • 放进技能的规则（解读） - 需要判断和顺序、违反了也能挽回的内容。是智能体阅读并遵循的流程。
  • 放进钩子的规则 - 不得违反的内容（原文的分工）。在工具调用之前检查条件并拦下。原文的例子是缺少审查文档时拦截 push。
  • 退出码的陷阱 - 要阻断，退出码必须是 2，或结构化输出为 deny。其他非零退出码在大多数事件上本身不阻断，所以不能假定脚本出错退出就等于拦住了。
  • 传达阻断原因 - 阻断消息是智能体会读的信息，具体写出缺了什么才被拦下，对下一步行动更有帮助。这是由文档叙述推出的解读。
  • 技能与钩子的交点 - 官方文档列出的钩子可定义位置中包括技能和子智能体的头部，此时在技能运行期间生效。
  • 更深入的比较 - 把规则注入上下文这种方式的局限，以及改成钩子的做法，见此前的分析文章。

技能越多成本越大

原文的第五条经验是，技能变多后，每个会话的成本也随之增加。作者描述说，技能说明全文，以及约 50 个技能、约 20 个智能体、约 60 个工具的列表进入了上下文，并写到关掉了两个智能体编排插件，回到默认设置。插件名称原文没有写。未使用的技能很多的目录本身就是成本，这是作者的结论。

对照官方文档，成本的本质更精确了。技能编写最佳实践说，启动时只预加载所有技能的名称和描述，SKILL.md 在技能相关时才被读取。Claude Code 文档也写道，描述始终在上下文中，完整技能在被调用时加载，技能正文只在使用时加载，所以在需要之前，长篇参考资料几乎没有成本。也就是说，不用的技能占用的是描述而不是正文。而描述部分在列表中也会在 1,536 字符处被截断。

  • 常驻成本 - 名称和描述（元数据）。随技能数量成比例增加。
  • 调用时成本 - SKILL.md 正文。只在被调用时加载，500 行建议针对的就是这一成本。
  • 如何看作者的数字 - 原文把技能约 50 个、智能体约 20 个、工具约 60 个分开计数。50 就是技能的数量，所以仅技能列表就有约 50 条在每个会话进入上下文。智能体和工具列表、每次使用工具附带的提示文字是另外的成本。
  • 降低的办法 - 把描述写得短且互不重叠，对不需要自动调用的技能，可以选择设置 disable-model-invocation: true。官方技能文档的表把这种情况写为「Description not in context, full skill loads when invoked」，即描述不在上下文中，文档并说明这一设置会把技能从 Claude 的上下文中完全移除（removes the skill from Claude's context entirely）。代价是 Claude 不能自行调用，需要用户手动调用。
