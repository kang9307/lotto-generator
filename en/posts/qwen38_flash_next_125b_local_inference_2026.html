The trigger - the GPU in the headline is not the GPU the source measured

On October 4, 2026, GeekNews listed an item titled, in translation, "Running Qwen 3.8 Flash Next (125B) on consumer hardware (RTX 4090) at 100 tokens per second". The source is the repository documentation of an open-source inference tool called Strata. Read from the title alone, it sounds as if about 100 tok/s was measured on a single RTX 4090, but the benchmark table in the documentation contains two GPUs.

  • NVIDIA: RTX 5070 (12GB), Ryzen 5 7600, 64GB of RAM - the top row is 94 tok/s generation
  • AMD: RX 9070 XT (16GB), Ryzen 9 3900X, 47GB of RAM - the top row is 60 tok/s generation
  • RTX 3090 (24GB): not in the table; there is only an estimate sentence saying it should write about 100 to 140 tokens per second
  • RTX 4090: neither a measured nor an estimated value can be found in the documentation

In this article, therefore, "about 100 tok/s" is used only as a loose pointer to the 94 tok/s reported on a 12GB-class RTX 5070 and the lower end of the RTX 3090 estimate, never as RTX 4090 performance. Where a title and the source disagree, the source is the reference.

The article addresses one question: when a 125B-class MoE model is attached to a single consumer GPU, where is tokens per second decided, and under what conditions should the reported figures be trusted? It is not an installation guide, and it does not evaluate the quality of the model's answers.

What Strata does - splitting 125B across GPU, RAM, CPU and SSD

The documentation introduces Strata as a tool that runs a large, capable model, one that normally needs a server, on an ordinary PC, and names Qwen3.8-Flash-Next as the target model. The model has 125B parameters and a mixture-of-experts (MoE) structure. According to the documentation, it contains 24,576 experts and uses only 10 of them to process one token.

The resource allocation is summarized in the documentation's own sentences.

  • The graphics card keeps the few thousand experts that are used most often
  • RAM holds all of the experts
  • The processor (CPU) works on the rest at the same time
  • The SSD is said to hold a "big lookup table", and the contents of that table are not explained

The documentation states that the implementation uses parts of llama.cpp and ggml. Strata itself is MIT-licensed, while the model follows separate terms from its original developers and the compression contributors (ISTA-DASLab, UkisAI and Unsloth). In other words, the tool's license does not stand in for the usage terms of the model weights.

To run it, one executes START-HERE.bat on Windows or ./setup.sh on Linux; during setup it downloads about 70GB of weights and asks for a context length. Afterwards it is reached through a local browser address (127.0.0.1:8080) or an OpenAI-compatible API (the same address with /v1). In the range confirmed at summary level, compatibility with the Anthropic API and the OpenAI Responses API is also listed among supported interfaces.

Where speed is decided - ten active experts and the memory hierarchy

The documentation describes the model as a team of 24,576 small experts and says "Each word needs only 10 of them". So 10 of 24,576 experts are selected per token. That works out to about 0.041%; counting experts alone, about one in 2,450 moves for each token (24,576 / 10 = 2,457.6, calculated).

10 / 24,576 = 0.000407  (about 0.041%)   [calculated]
                    24,576 / 10 = 2,457.6                    [calculated]

That ratio is not a speed ratio, however, because the cost of reading the same 10 experts depends on which memory they sit in. Following the documented placement, the situations divide as follows.

  • When a selected expert is in GPU memory - the graphics card computes it directly
  • When it is not on the GPU but is in RAM - according to the documentation, the CPU handles that part at the same time
  • The direction that a lower GPU hit rate shifts more work to the CPU and RAM can be read from this arrangement, but no hit-rate figure appears in the documentation

That the documentation puts "the few thousand most frequently used experts" on the GPU reads as a placement meant to narrow this cost gap. Yet how many "a few thousand" is, what percentage of the 24,576 that represents, and whether the selection is static or changes while running are not stated. The sentence "speed is decided by the GPU hit rate" is therefore an inference from the structure, not a fact the documentation shows by measurement.

For the same reason, the fact that it runs on a single 12GB card does not mean GPU performance is everything. The table shows speed rising as the quantization level drops, and the ratio between generation and prompt reading moves differently when the GPU changes. Both observations are checked against numbers in the following sections.

In summary, speed in this structure is set at three layers. The first is the model structure (10 of 24,576 per token), the second is placement (the share handled by GPU-resident experts versus RAM and CPU), and the third is quantization (how many bits each expert is stored in). Only the third layer is shown by measurement in the documentation; the first two are structural explanations. That is why the part of the table where only quantization changes on the same machine is the most reliable comparison in this article.

Three things can be read from the tables.

  • On the NVIDIA machine the generation speed ratio between Q2_0 (94) and IQ3_S (53) is about 1.77x (calculated). Generation is faster in the direction of lower bit counts.
  • For the same Q2_0, generation on the AMD machine is about 0.64x that of NVIDIA (60/94) and prompt reading about 0.44x (1,160/2,650) (calculated). The gap is larger in prompt reading than in generation.
  • The Coder row has generation similar to IQ3_S (55 versus 53) and faster prompt reading (2,180 versus 1,620). The documentation describes Coder as a coding version with half of the experts removed, and the table does not give a quantization name for it.

Converted to feel, and assuming a 4K answer is 4,096 tokens, 94 tok/s is about 44 seconds (4,096/94, calculated). At 53 tok/s for IQ3_S it is about 77 seconds. The documentation does not define exactly how many tokens a "4K answer" is, so this conversion is only a rough sense of scale.

The column-to-column drop can also be read. Going from Q2_0 to IQ3_S, generation falls from 94 to 53, about 44%, and prompt reading falls from 2,650 to 1,620, about 39% (calculated). Because engine version differences are mixed into this range, the difference between the two drops is not interpreted as a meaningful value.

Where comparisons fail - engine versions and machines differ together

The documentation's measurement note is a single line. Q2_0 on NVIDIA used engine 0.1.36, the other rows used 0.1.26, and the conditions were 4K answers and 32K prompts. That one line sharply narrows the range in which the table can be compared.

NVIDIA Q2_0 versus IQ2_XS, IQ3_XXS and IQ3_SQuantization and engine version (0.1.36 versus 0.1.26)Direction only. The share of the gap due to quantization cannot be separated

NVIDIA versus AMDGPU and VRAM (12GB versus 16GB), CPU, RAM (64GB versus 47GB)Cannot be read as a GPU performance difference
RTX 3090 estimate of 100 to 140An estimate, not a measurementNot given the same weight as the table values

The point that needs the most care is the difference between the second and third rows. On the same engine 0.1.26, only NVIDIA's three quantization rows (IQ2_XS 79, IQ3_XXS 62, IQ3_S 53) show the effect of quantization cleanly. In this range the generation speed ratio between IQ2_XS and IQ3_S is about 1.49x (79/53, calculated).

The headline figure of 94 tok/s is a row where two favorable conditions overlap: the newer engine version and the lowest bit count. That this row is the fastest and that the user will obtain that speed at the quality they intend to use are separate matters. The documentation has no statement on how much quality Q2_0 loses, and no quality evaluation table in this range.

The AMD and NVIDIA rows are not a GPU comparison for the same reason. The two machines differ not only in GPU but also in CPU and RAM capacity, and the documentation explains that in this structure the CPU takes part of the expert computation. Whether AMD is slower because of the GPU or because of the CPU and RAM therefore cannot be separated from this table alone.

Speculative decoding at 1.6-1.8x - what can be said

The documentation describes speculative decoding as the speed-up mechanism. A small draft model guesses the next few words, and the large model checks them all at once, so that the answer comes out 1.6 to 1.8 times sooner. The following items are not separated out in the documentation.

  • The baseline for 1.6-1.8x - whether it is the speed with the draft model off or some other setting
  • Which quantization and which machine produced the multiplier
  • The rate at which the draft model guesses correctly (acceptance rate) and how it differs by task type
  • Whether the 94 tok/s and other table values include this effect

Without these four, a back-calculation such as "94 tok/s = a base speed of about 55 to 59 tok/s times 1.6 to 1.8" cannot be made. Computing it, 94 divided by 1.6 to 1.8 is about 52 to 59, but this back-calculation rests on the assumption that the table values were taken with speculative decoding on, and the documentation does not say so. For a reader to find out whether the same effect appears on their own PC, there is no alternative to comparing generation speed with and without the draft model directly.

Speculative decoding is also a device for the generation stage. It does not raise the prompt processing speed at which input is read, so the delay problem in the next section is not solved by it.

Prompt reading and first response - the delay hidden behind generation speed

Besides generation speed, the time spent reading input also has to be counted. The documentation has statements about this delay in three places.

Statement in the documentationValueMeaning converted by calculation
Prompt reading in the benchmark table (NVIDIA Q2_0, 32K input)2,650 tok/sAbout 12 seconds to read 32,000 tokens (calculated)
Long input is read in big piecesUp to 8,192 tokens at a time, over 1,000 tokens per secondEven at the lower bound, one 8,192-token piece takes within about 8 seconds (calculated)
When the first message of a chat is read in fullAbout 1 minute per 30,000 tokensAbout 500 tokens per second (calculated)
Loading at first startupThe PC can be slow or stop responding for 1 to 3 minutes—

The third row and the first row appear to disagree within the same documentation. Reading a 32K input at 2,650 tok/s takes about 12 seconds, yet for reading a first message there is a statement of about 1 minute per 30,000 tokens. The documentation does not explain whether the two share the same conditions. One possible reading is that they refer to different machines, quantizations or cache states, but which of these applies cannot be settled from the documentation alone. For planning, it is safer to use the more conservative of the two (about 1 minute per 30,000 tokens), and even that value must be measured in the real environment.

The documentation says reading the whole first message of a conversation takes about one minute per 30,000 tokens. That this time grows with input length is a calculation from the table's figures, and because prompt reading on the AMD machine (Q2_0, 1,160 tok/s) is less than half of NVIDIA's, the delay for the same input more than doubles (calculated).

Requirements and variants - checking the numbers against each other

The numbers for requirements and variants that the documentation gives are gathered in one table, and whether they fit together is checked.

Two mismatches stand out. First, the default install download is about 70GB while the minimum RAM is 32GB and the recommendation is 64GB. The documentation says RAM holds all of the experts, so for the weights to fit in RAM the variant must be chosen to match RAM capacity. The statement that Coder fits in 32GB of RAM matches that context, but the calculation of how the default variant is placed on a 64GB machine does not close from the documentation alone.

Second, the 94GB download of UD-IQ4_XS exceeds the "about 80GB of free disk" requirement. Using this variant has to be read as changing the disk requirement, and the documentation does not state that value separately.

That UD-Q4_K_XL, the closest in quality, is reported at 7 to 8.5 tok/s compresses the core constraint of this article. The documentation says this variant is slow because "Strata reads most of it from the SSD while it answers". The documentation has no value that gives speed and quality together in one table.

In summary, the requirements are a lower bound, and variant selection is filtered first by RAM and disk capacity. Even with 12GB of VRAM, having less than 32GB of RAM is outside the range the documentation presents, and the documentation does not cover what happens in that case.

A checklist before applying it to your own PC

Getting values for your own environment, instead of expecting the reported figures, takes the following order. Every item is derived from the requirements and limits written in the documentation.

  1. Check that the GPU is on the supported list (NVIDIA RTX 20, 30, 40 and 50, and the Radeon models named in the documentation) and that VRAM is 12GB or more.
  2. Check that RAM is 32GB or more. 64GB is recommended, and the documentation explains that with 32GB only variants that fit that capacity, such as Coder, are candidates.
  3. Check free disk. The default install is about 70GB of downloads, the documented recommended free space is about 80GB, and the 94GB variant needs more than that.
  4. Know that the PC may slow down for 1 to 3 minutes at first startup, and run it for the first time with other work closed.
  5. Because the context length is chosen during setup, decide the input length you will use first. The documentation's delay statement is about 1 minute per 30,000 tokens.
  6. Record generation speed and prompt reading speed separately for each quantization level with the same prompt. If possible, compare with the draft model on and off.
  7. If the use is not code, avoid the Coder variant. The documentation says Coder is weaker outside code, especially in Chinese and other CJK text.
  8. If you plan to use an AMD GPU together with image input, first read the documentation's note that on Linux the processing goes through the CPU and on Windows it does not yet work.

The criterion in this order is to look at speed and input delay separately. 94 tok/s is the documentation's maximum figure, and what a user experiences is decided jointly by the quantization chosen, the input length and the RAM capacity.

What could not be confirmed

  • Measured values on an RTX 4090. They are not in the documentation, and the 4090 in the title does not match the documentation's content.
  • How many experts stay resident on the GPU, how they are chosen (static or dynamic), and the GPU hit rate.
  • The model's active parameter count and file sizes per quantization level. In the range read from the documentation there are only 125B, a download of about 70GB, and about 94GB.
  • The baseline and measurement conditions of the 1.6-1.8x speculative decoding gain, and the identity of the draft model.
  • The quality loss of low-bit quantization such as Q2_0. The 91% SWE-bench Verified for Coder is a figure the documentation states, and no independent verification was opened.
  • Why the 2,650 tok/s for a 32K input and the statement of about 1 minute per 30,000 tokens appear to disagree.
  • Results from running it directly. All figures in this article are values reported in the repository documentation.
  • When the repository was last updated and how engine versions changed afterwards. No date could be read from the documentation.
