값이 하나도 없는 타입은 왜 필요한가

발산하는 표현에 타입을 주는 일, 그리고 추론의 기본값을 바꾸는 일의 무게

2026-08-28 개발/인프라

서론: 오래 걸렸다는 그 기능을 이미 쓰고 있었다

Rust로 뭔가를 만들어 봤다면 이런 함수를 한 번은 썼을 것이다.

fn bail(msg: &str) -> ! {
    eprintln!("{msg}");
    std::process::exit(1)
}

반환 타입 자리에 느낌표 하나. 이 표기는 오래전부터 안정 채널에서 그냥 됐다. 그런데 2026년 8월 말, never 타입이 십수 년 만에 안정화됐다는 소식이 돌았다. 이미 쓰고 있는 걸 이제 와서 안정화한다는 게 무슨 말인가.

답은 두 겹이다. 첫째, 지금까지 안정 채널에서 되던 것은 반환 위치에 붙는 ! 뿐이었다. let x: !, Result<u32, !>, 제네릭 인자로서의 ! 처럼 일반 타입 자리에 놓는 것은 나이틀리 전용이었다. 둘째, 그리고 이쪽이 진짜인데 — 발목을 잡은 것은 문법이 아니라 타입 추론이 끝내 결정하지 못했을 때 어디로 떨어지느냐는 기본값 하나였다.

이 글은 그 기본값에 관한 이야기다. 값이 하나도 없는 타입이 왜 유용한지, 그리고 이미 배포된 언어에서 기본값을 바꾼다는 것이 왜 그렇게 비싼지. Rust의 안전 모델을 unsafe 쪽에서 다룬 iddqd로 보는 Rust의 unsafe 캡슐화 - borrow-from-value와 자기참조 구조의 함정, 타입을 나중에 얹을 때 생기는 경계 비용을 다룬 BEAM 위에 정적 타입을 얹는다는 선택 - Gleam이 옮긴 경계와 남은 경계와 결이 이어진다.

무엇이 안정화되고 언제 들어오나 — 2026년 8월 기준

먼저 시점을 정확히 해 두자. 안정 채널에는 아직 없다.

  • 안정화 PR rust-lang/rust#155499(제목 그대로 stabilize never type)가 2026년 8월 24일에 병합됐다. 마일스톤은 1.100.0이다.
  • releases.rs 기준 1.100.0은 2026년 9월 25일에 master 에서 분기해 2026년 11월 12일에 안정 채널로 나올 예정이다.
  • 이 글을 쓰는 시점의 안정 버전은 1.98.0, 다음 1.99.0의 예정일이 2026년 10월 1일이다.

「안정화됐다」는 헤드라인은 병합 시점을 가리킨 것이다. 나이틀리를 쓰지 않는다면 손에 들어오는 건 11월이고, 릴리스 노트로 최종 범위가 확정되는 것도 그때다.

이 PR이 한 덩어리로 처리하는 일은 넷이다.

  • !를 정식 타입으로 안정화 — 반환 위치 밖에서도 쓸 수 있게 된다
  • 타입 추론 폴백을 모든 에디션에서 ! 로 통일
  • std::convert::Infallible을 !의 타입 별칭으로 전환
  • 예고용으로 켜 두었던 dependency_on_unit_never_type_fallback lint 제거

그리고 「십수 년」이라는 표현의 근거. RFC 1216(bang type)의 Start Date 는 2015-07-19다. 병합일까지 11년 1개월이 걸렸다. 헤드라인의 「10년」은 반올림한 말이고, 그 사이가 비어 있던 것도 아니다. 뒤에서 볼 것처럼 한 번은 안정화됐다가 되돌려졌다.

값이 하나도 없는 타입이라는 발상

타입을 「값의 모임」으로 보면 셈이 쉬워진다. bool은 값이 둘, u8은 256개, ()는 하나. 그러면 0개인 타입은 무엇인가.

값이 0개면 그 타입의 값을 만들 수 없다. 만들 수 없으니 그 타입의 변수에 무언가를 넣는 코드는 도달할 수 없다. 여기서 한 번 뒤집힌다 — 「값이 없다」가 「실행이 이 자리에 오지 않는다」로 번역된다. 값의 개수에 관한 말이 제어 흐름에 관한 말이 되는 것이다. Rust Reference 는 !를 「값이 없는 타입으로, 결코 완료되지 않는 계산의 결과를 나타낸다」고 적는다.

왜 이런 게 필요한가. 타입 검사기는 모든 표현식에 타입이 있어야 계산을 이어 간다. 그런데 프로그램에는 값을 돌려주지 않고 끝나 버리는 표현이 잔뜩 있다.

  • panic!("...") — 되감기든 즉시 중단이든, 뒤로 이어지지 않는다
  • loop {} — break 가 없는 무한 루프
  • std::process::exit(1) — 프로세스 자체가 사라진다
  • return — 함수 밖으로 나가므로 이 자리에는 값이 남지 않는다
  • break · continue — 제어가 다른 데로 간다
  • ? 연산자의 실패 경로 — 조기 반환이므로 뒤가 없다

RFC 1216 이전에 Rust는 이런 표현에 ()를 붙였다. 그러면 실제로는 오지 않는 자리에 「값 하나가 있다」고 말하는 셈이 된다. 컴파일러 입장에서 이 거짓말은 공짜가 아니다. 죽은 코드 판정이 흐려지고, 분기가 합류하는 지점의 타입 계산에 군더더기가 낀다.

RFC의 표현은 간결하다. !는 「빈 열거형처럼 동작하되, 다른 어떤 타입으로도 암묵적으로 변환될 수 있다」. 앞부분은 값이 없다는 사실이고, 뒷부분이 이 타입을 실제로 쓸모 있게 만드는 성질이다.

모든 타입으로 흘러간다 — 분기의 한쪽이 끝나 버릴 때

!의 핵심 성질은 하나다. ! 타입의 표현식은 다른 모든 타입으로 강제 변환된다. Reference 가 그대로 그렇게 적고 있다.

이게 왜 안전한가. 변환할 값이 애초에 존재하지 않기 때문이다. 변환 규칙을 정의할 필요조차 없다. 이 논리를 가장 노골적으로 드러낸 것이 Haskell의 Data.Void인데, 거기에는 absurd :: Void -> a라는 함수가 있고 문서는 이를 「거짓에서는 무엇이든 따라 나온다」는 논리 원칙의 구현이라고 설명한다. 부를 수 없는 함수이므로 무엇을 돌려준다고 약속해도 거짓말이 되지 않는다.

실무에서 이 성질이 눈에 띄는 자리는 분기의 한쪽이 끝나 버릴 때다.

let port: u16 = match std::env::var("PORT") {
    Ok(v)  => v.parse().unwrap_or(8080),
    Err(_) => {
        eprintln!("PORT is required");
        std::process::exit(1)   // 이 팔의 타입은 !
    }
};

match의 모든 팔은 타입이 같아야 한다. 위쪽 팔은 u16이고 아래쪽 팔은 !다. !가 u16 쪽으로 흘러가므로 둘이 맞아떨어진다. 프로그래머가 의미 없는 더미 값을 지어내 넣을 필요가 없다. 이 타입이 없는 세계에서는 아래쪽 팔에 0이라도 적어 넣어야 하고, 그 0은 읽는 사람에게 「이 값이 쓰일 수도 있나」라는 잘못된 질문을 남긴다.

함수 시그니처에 붙으면 정보의 방향이 한 번 더 바뀐다.

fn bail(msg: &str) -> ! { eprintln!("{msg}"); std::process::exit(1) }

let cfg = load_config().unwrap_or_else(|_| bail("config missing"));
//        cfg 의 타입은 클로저가 ! 를 주더라도 흔들리지 않는다

여기서 bail이 ()를 반환한다고 선언돼 있으면 위 코드는 타입이 맞지 않아 컴파일되지 않는다. !로 선언하는 순간 두 가지가 동시에 성립한다.

  • 호출부의 타입이 맞아떨어진다 — 반환값이 필요한 자리에 그대로 놓을 수 있다
  • 뒤 코드가 도달 불가로 판정된다 — 미초기화 변수 진단과 죽은 코드 경고가 정확해진다
  • 구현이 바뀌면 컴파일이 막는다 — 나중에 누가 bail 안에서 실수로 반환하면 그 자리에서 오류가 난다

마지막 항목이 주석과 갈리는 지점이다. // 이 함수는 돌아오지 않음이라는 주석은 구현이 바뀌어도 아무 일도 하지 않는다.

빈 열거형과 ! — 직접 만드는 값 없는 타입

여기까지 읽으면 자연히 드는 생각이 있다. 변종이 없는 열거형을 직접 만들면 되지 않나.

enum Never {}          // 변종이 없으므로 값을 만들 수 없다

실제로 그렇게 쓴다. 표준 라이브러리의 std::convert::Infallible이 바로 그 물건이고, 문서는 「결코 일어날 수 없는 오류를 위한 오류 타입」이자 「이 열거형에는 변종이 없으므로 이 타입의 값은 실제로 존재할 수 없다」고 적는다. RFC 1216도 사용자 정의 빈 타입으로 앞서 말한 용도를 전부 커버할 수 있음을 인정한다.

그러면 무엇이 다른가. 셋이다.

  • 강제 변환 — !는 어떤 타입으로도 저절로 흘러간다. 빈 열거형은 그렇지 않아서 match x {} 같은 형태로 손수 소거해야 한다
  • 반환 위치의 표기력 — -> !는 「돌아오지 않는다」를 말한다. -> Never는 문법상 「Never 값을 준다」로 읽히고, 그 값이 존재할 수 없다는 사실은 한 겹 뒤에 있다
  • 추론에 미치는 영향 — 빈 열거형은 평범한 사용자 타입이라 추론 기본값 논의가 붙지 않는다. !는 언어 내장이라 붙는다

셋째가 이 글의 나머지 전부다. 그리고 Infallible의 운명은 문서에 이미 적혀 있었다 — 「!가 안정화되면 Infallible을 그 타입 별칭으로 만들 계획」이며 「종국에는 Infallible을 폐기한다」. 이번 PR이 그 별칭 전환을 실제로 수행한다.

같은 문서가 스스로 든 함정도 있다. fn() -> !와 fn() -> Infallible에 각각 트레이트 구현을 달아 둔 코드는, 둘이 같은 타입이 되는 순간 구현이 겹친다. 별칭 하나 만드는 일이 남의 코드에서 충돌을 만들 수 있다는 뜻이고, 이런 것까지 세어야 하는 것이 안정화 작업의 실제 부피다.

왜 그렇게 오래 걸렸나 — 추론이 결정하지 못할 때

이제 본론이다. !를 타입으로 인정하는 문법은 어렵지 않다. 어려운 것은 타입 추론이 끝내 아무것도 결정하지 못한 자리다.

제네릭 타입 변수가 아무런 제약도 받지 못한 채 남을 때가 있다. 컴파일러는 그냥 포기할 수 없으므로 기본값을 채워 넣는다. 이것이 폴백(fallback)이다. Rust는 역사적으로 그 값을 ()로 잡아 왔다.

에디션 가이드의 서술이 문제를 정확히 짚는다. 「역사적으로 폴백 타입은 ()였다. 이 때문에 폴백이 없었다면 컴파일러가 ()를 추론하지 않았을 자리에서도 !가 저절로 ()로 강제 변환됐다. 이는 혼란스러웠고 ! 타입의 안정화를 막아 왔다.」

말하자면 !를 진짜 타입으로 대접하겠다면서 정작 결정 못 한 자리에서는 ()로 눕히는 것이 앞뒤가 맞지 않았다. 그런데 이 기본값을 바꾸면 이미 컴파일되던 코드가 컴파일되지 않는다. 에디션 가이드가 드는 예를 보자.

fn outer<T>(x: T) -> Result<T, ()> {
    fn f<T: Default>() -> Result<T, ()> { Ok(T::default()) }
    f()?;        // 예전: T = ()  /  지금: T = !
    Ok(x)
}

f()?의 성공 값은 버려지므로 T에 아무 제약이 없다. 예전에는 ()로 떨어졌고 ()는 Default를 구현하니 통과했다. 이제는 !로 떨어지고 !는 Default를 구현하지 않으니 오류가 난다. 고치는 방법은 f::<()>()?;처럼 사람이 의도를 못 박는 것뿐이다.

이 정도면 성가시긴 해도 안전하다. 컴파일 오류는 시끄럽게 알려 주니까. 진짜 문제는 소리 없이 의미가 바뀌는 쪽이다. 컴파일러 lint 문서가 드는 예가 이것이다.

if true {
    return
} else {
    unsafe { std::mem::zeroed() }   // 폴백이 () 면 건전, ! 면 즉시 UB
};

mem::zeroed는 반환 타입이 호출부에서 정해진다. 폴백이 ()였을 때는 ()를 만들어 냈고 그건 완전히 건전하다. 폴백이 !가 되면 값이 존재할 수 없는 타입의 값을 만들어 낸 것이 되고, 그 자리에서 곧바로 정의되지 않은 동작이다. 코드는 그대로인데 의미가 바뀐다. 컴파일은 통과한다.

이 위험이 실제로 얼마나 진지하게 다뤄졌는지는 이력에 남아 있다. never 타입은 1.26에서 TryFrom과 함께 한 번 안정화됐다가, 2018년 4월에 되돌려졌다(PR #50121). 폴백 의미 변화가 딸려 왔기 때문이다. 이후 트래킹 이슈 #58184는 「추론은 건드리지 말고 타입만 안정화하자」는 부분 안정화를 제안했다. 결국 마지막에는 추론을 손대야 했지만, 그 사이에 예고 장치들이 쌓였다.

기본값 하나를 바꾸는 데 필요한 장치

안정화된 언어에서 기본값을 바꾼다는 건 이미 세상에 배포된 코드의 의미를 바꾼다는 뜻이다. Rust가 이 일에 동원한 장치는 셋이고, 셋 다 다른 언어·다른 프로젝트에서도 그대로 쓸 만한 형태다.

첫째, 에디션. 2024 에디션에서 먼저 폴백을 !로 바꿨다. 옛 크레이트는 옛 에디션 규칙으로 컴파일되고 새 크레이트와 아무 문제 없이 링크된다. 다만 에디션은 영구 분기가 아니라 이행 통로다. 규칙이 에디션마다 영원히 다르면 언어가 사실상 여러 개가 되므로, 마지막에는 전 에디션 통일이 목표였고 이번 PR이 그 일을 했다.

둘째, 경고 단계. 허용 → 경고 → 거부 순으로 올린다. 1.92에서 두 lint 를 기본 거부로 올리면서 약 500개 크레이트가 영향을 받을 것으로 봤고, 그럼에도 #[allow]로 빠져나갈 길은 남겼다. 릴리스 노트는 이 조치를 「호환성 변경이 아니며 장차 never 타입 안정화를 가능하게 하는 것」으로 규정했다. 깨는 것과 예고하는 것을 문서에서 구분해 부르는 태도가 여기 있다.

셋째, 크레이터(crater). 공개 생태계 전체를 실제로 다시 빌드해 보는 실험이다. 이번 PR의 실행 결과는 9,024건 중 3,277건 회귀였고, 그중 1,149건은 의도치 않은 잡음으로 판단돼 재시도가 권고됐다. 숫자를 읽을 때 주의할 게 있다.

  • 크레이터 회귀 수는 「깨진 크레이트 수」가 아니라 「사람이 읽어야 할 목록의 길이」다
  • 같은 원인 하나가 수백 건으로 셈될 수 있고, 인프라 문제로 인한 잡음이 섞인다
  • 반대로 공개 저장소에 없는 사내 코드는 아예 세어지지 않는다 — 이쪽이 더 중요하다
  • 그래서 크레이터는 안전 보증이 아니라 표본 조사로 읽어야 한다

한 가지 더. 에디션 가이드는 「자동 수정은 없지만, 에디션 변경으로 깨질 코드에 대한 자동 감지는 있다」고 못 박는다. cargo fix가 대신 고쳐 주지 않는 이유는 분명하다. 올바른 수정은 「여기서 어떤 타입을 의도했는가」를 사람이 정하는 일이고, 그건 도구가 대신 결정할 수 있는 종류가 아니다.

여기서 남는 일반 교훈 하나. 기본값은 API 표면이다. 문서에 적혀 있지 않아도, 사용자가 명시적으로 선택한 적이 없어도, 사람들은 그 위에 코드를 얹는다. 설정 파일의 기본값이든 라이브러리의 기본 동작이든 마찬가지다.

다른 언어는 같은 자리를 어떻게 채웠나

이 개념의 일반 이름은 바텀 타입(bottom type)이다. 값이 없고, 모든 타입의 아래에 놓인다. 여러 언어에 대응물이 있는데, 아래 표는 순위가 아니다. 차이는 좋고 나쁨이 아니라 언제 도입했는가와 그때 어떤 호환성을 지고 있었는가에서 나온다.

언어이름제공 방식확인한 문서
Rust!언어 내장 타입 + 모든 타입으로의 강제 변환. 추론 폴백도 언어가 정한다Reference · RFC 1216
KotlinNothing언어 내장. 모든 타입의 서브타입. throw 표현식의 타입Kotlin 공식 문서

표를 가로로 읽으면 갈리는 축이 두 개 보인다.

  • 라이브러리인가 언어 코어인가 — Haskell의 Void와 Python의 Never는 라이브러리 쪽에 있다. 코어에 박히면 서브타입 관계나 추론에 영향을 주는 대신, 바꾸기가 어려워진다
  • 서브타이핑인가 강제 변환인가 — Kotlin과 Scala는 「모든 타입의 서브타입」으로 처리한다. Rust는 서브타이핑을 라이프타임에만 쓰므로 같은 효과를 강제 변환으로 얻는다. 결과는 비슷하고 규칙이 사는 곳이 다르다
  • 런타임에 검사되는가 — Python 의 Never는 정적 검사기에 하는 말이지 인터프리터가 강제하지 않는다. 같은 이름이어도 지키는 주체가 다르다

Python 문서가 Never와 NoReturn을 「타입 시스템에서 같은 의미이며 정적 검사기는 둘을 동등하게 취급한다」고 밝히면서도 두 이름을 다 남겨 둔 것은 눈여겨볼 만하다. NoReturn이 3.6.2, Never가 3.11에 들어왔다. 이름을 갈아 치우지 않고 포갠 것 역시 호환성을 지키는 한 가지 방식이고, Rust가 Infallible을 별칭으로 남기려는 이유와 같다.

실무에서 이 타입을 만나는 자리

추상적으로 들리는 타입이지만 실제 코드에서 얼굴을 내미는 자리는 꽤 구체적이다.

절대 실패하지 않는다는 것을 시그니처로 말하기

표준 라이브러리에는 이런 구현이 있다.

  • impl<T, U: Into<T>> TryFrom<U> for T의 연관 타입이 type Error = Infallible;이다
  • 변환이 실패할 수 있는 TryFrom 인터페이스를 쓰면서, 이 경우에는 실패 변종이 존재하지 않는다는 사실을 타입으로 말한다
  • !를 일반 타입 자리에 쓸 수 있게 되면 Result<T, !>를 직접 쓸 수 있고, 전용 오류 타입을 하나 더 만들 이유가 줄어든다
  • 읽는 쪽에서는 「이 API가 실패할 수 있는가」가 시그니처만 보고 결정된다 — 문서를 찾아갈 필요가 없다

돌아오지 않는 함수

  • 서버의 메인 루프, 프로세스 종료 래퍼, 치명 오류 처리기가 전형적이다
  • -> !로 선언하면 호출부 이후가 도달 불가임을 컴파일러가 안다 — 미초기화 진단과 죽은 코드 경고의 정확도가 올라간다
  • FFI 경계에서도 쓰인다. Reference 는 unsafe extern "C" { pub safe fn no_return_extern_func() -> !; } 형태를 예로 든다. C 쪽의 「돌아오지 않음」 표기를 Rust 시그니처로 옮기는 자리다
  • 경계 자체를 다루는 이야기는 Rust FFI의 unsafe를 줄이려는 시도 - extern fil-c 제안이 노리는 자리와 치르는 값에서 따로 다뤘다

제네릭 파라미터를 「없음」으로 못 박기

  • 상태 기계에서 아직 도달할 수 없는 상태, 이벤트를 보내지 않는 채널의 메시지 타입 같은 자리
  • 더미 구조체를 만들어 두는 것보다 의도가 정확히 전달된다 — 더미는 나중에 누군가 값을 넣을 수 있지만 값 없는 타입은 그럴 수 없다
  • 단, 이런 설계는 라이브러리 쪽에서 값이 크고 애플리케이션 코드에서는 과하기 쉽다

완전성 검사

  • TypeScript에서는 유니온을 다 처리했는지 확인하는 관용구로 never가 널리 쓰인다
  • Rust는 match의 완전성을 원래 강제하므로 같은 관용구의 필요가 덜하다 — 같은 도구가 언어마다 다른 무게를 갖는 예다
  • 빈 변종을 패턴에서 생략하는 기능은 이번 안정화 범위 밖이고 별도 게이트 뒤에 남아 있다

몰라도 되는 사람, 알아 두면 이득인 시점

정직하게 쓰자면 대부분의 코드는 이 타입을 직접 쓰지 않는다. panic!과 process::exit는 그냥 쓰면 되고, !는 컴파일러가 뒤에서 붙였다 떼었다 한다. 애플리케이션 코드를 쓰면서 !를 손으로 타이핑할 일은 몇 달에 한 번 올까 말까다.

다음 조건이 전부 맞으면 이 글의 내용을 잊어도 된다.

  • 단일 크레이트 애플리케이션이고 공개 라이브러리를 만들지 않는다
  • 오류 타입을 제네릭으로 노출하는 API 설계를 하지 않는다
  • unsafe 블록이 없다
  • 최신 에디션을 쓰고 있고 툴체인을 꾸준히 올린다
  • 컴파일 오류가 나면 그때 메시지를 읽고 고치면 된다 — 실제로 그래도 된다

반대로 아래 조건 중 하나라도 걸리면 지금 알아 두는 편이 싸게 먹힌다.

  • unsafe 안에서 반환 타입이 호출부에서 정해지는 함수를 부른다 — mem::zeroed 계열. 여기서 나는 경고를 #[allow]로 덮으면 안 된다. 컴파일 오류는 나중에 고쳐도 되지만 정의되지 않은 동작은 나중이 없다. lint 를 거부 등급으로 올린 이유가 정확히 이것이다
  • 라이브러리를 만들고 오류 타입을 제네릭 파라미터로 노출한다 — Infallible의 별칭 전환이 남의 코드에서 구현 충돌을 만들 수 있는 자리다
  • 옛 에디션에 머문 큰 코드베이스를 유지한다 — 1.100.0부터는 에디션 경계가 더 이상 막아 주지 않는다. 지금 나오는 경고가 그때의 작업량이다
  • 매크로를 많이 쓴다 — 매크로가 만들어 낸 표현식에서 폴백이 어디로 떨어지는지는 소스만 봐서 보이지 않는다
  • 오류 메시지에 !가 튀어나와 당황한 적이 있다 — 이 글의 3·4절이 그 답이다

타입이 문서가 되는 조건과 안 되는 조건

-> !는 「이 함수는 돌아오지 않는다」는 문장을 코드에 새기는 일이다. 타입으로 쓴 문장이 주석보다 나은 이유는 하나뿐인데, 그 하나가 결정적이다. 컴파일러가 그 주장을 강제한다. 구현이 바뀌어 실제로 반환하게 되면 그 자리에서 빌드가 멈춘다. 주석은 조용히 거짓말이 된다.

타입이 문서 역할을 제대로 하는 조건은 대개 이렇다.

  • 컴파일러가 강제한다 — 어긋나면 빌드가 실패한다
  • 호출자의 코드 모양을 바꾼다 — Result<T, !>는 오류 처리 코드를 아예 없앤다
  • 표기가 짧고 관용구가 하나다 — 여러 방식이 공존하면 읽는 쪽이 매번 해석해야 한다

반대로 타입이 못 하는 말도 분명하다. 이쪽을 아는 것이 더 실용적이다.

  • 「왜」를 말하지 못한다 — -> !는 안 돌아온다는 사실만 말한다. 종료 코드가 무엇인지, 로그를 남기는지, 되감기인지 즉시 중단인지는 침묵한다
  • 불가능의 종류를 구분하지 못한다 — 값이 없는 타입은 그것이 프로토콜상 영원히 불가능한 것인지, 아직 구현하지 않은 것인지, 이 빌드 구성에서만 없는 것인지 구별해 주지 않는다
  • 적히지 않은 기본값은 문서가 아니다 — 폴백이 정확히 그런 것이었다. 소스 어디에도 ()라고 쓰여 있지 않았지만 코드의 의미는 거기 매달려 있었다. 이 글 전체가 그 사례다

그래서 결론은 「타입으로 다 쓰자」가 아니다. 타입은 무엇이 불가능한지를 강제하고, 산문은 왜 그런지를 남긴다. -> ! 옆에 한 줄 주석이 여전히 필요한 이유다.

확인하지 못한 것

  • 1.100.0 릴리스 노트는 아직 나오지 않았다. 최종 안정화 범위가 병합 시점과 같을지는 릴리스 때 확인해야 한다
  • 크레이터 회귀 3,277건 가운데 실제로 수정이 필요한 크레이트가 몇 개인지 — 잡음 판정과 재시도 권고 상태라 확정 수치가 없다
  • Infallible의 폐기 시점 — 문서는 「종국에는」이라고만 적는다
  • 빈 변종 패턴 생략(별도 게이트)의 안정화 일정 — 논의 중이며 이번 범위 밖이다
  • 1.92에서 예상한 「약 500개 크레이트」가 실제로 어떻게 나타났는지에 대한 사후 집계
  • 사내·비공개 코드에서의 영향 규모 — 크레이터는 공개 저장소만 훑으므로 구조적으로 알 수 없다

정리

세 문장으로 줄이면 이렇다. 값이 하나도 없는 타입은 「이 자리에 도달하지 않는다」를 타입으로 말하는 장치다. 그 장치가 유용한 이유는 어떤 타입으로도 흘러가므로 분기의 한쪽이 끝나 버릴 때 더미 값을 지어낼 필요가 없어지기 때문이다. 그리고 십수 년이 걸린 이유는 문법이 아니라, 추론이 결정하지 못한 자리의 기본값을 바꾸는 일이 이미 배포된 코드의 의미를 건드리기 때문이다.

가져갈 것 셋만 남긴다.

  • 기본값은 API다. 아무도 명시적으로 고르지 않은 값 위에 세상의 코드가 얹힌다. 바꾸려면 에디션·경고 단계·생태계 실험 같은 장치가 필요하고, 그 장치를 만드는 데 걸리는 시간이 곧 「오래 걸린 이유」다
  • 컴파일 오류와 의미 변화는 무게가 다르다. 앞의 것은 나중에 고쳐도 되고 뒤의 것은 안 된다. Rust가 unsafe와 얽히는 lint 만 거부 등급으로 올린 판단이 이 구분을 그대로 보여 준다
  • 몰라도 되는 사람이 대다수라는 사실을 말해 주는 것도 정보다. 이 타입을 직접 쓸 일은 드물다. 다만 unsafe·공개 라이브러리·옛 에디션 셋 중 하나에 걸린다면 지금 경고를 읽어 두는 편이 11월에 읽는 것보다 싸다
