22분 동안 npm에서 일어난 일과, 한국 개발자가 오늘 해야 할 11가지

2026-05-22 IT/기술

서론: 22분간 일어난 일 - npm 생태계의 시한폭탄

2026년 5월 npm 레지스트리에 등록된 314개의 정상 패키지가 단 22분 안에 637개의 악성 버전으로 일제히 갈아치워진 사건이 보고되었습니다. 분 단위로 환산하면 1분에 약 29개의 악성 버전이 푸시된 셈입니다. 사람의 손으로는 절대 불가능한 속도이고, 사전 자동화된 스크립트가 메인테이너 자격증명·토큰 묶음을 활용해 일제히 publish를 실행한 형태로 추정됩니다. 22분이라는 시간 자체가 이번 사건의 핵심이며, 자바스크립트 생태계가 메인테이너 단일 자격증명이라는 단일 실패점에 얼마나 노출되어 있는지를 명확히 보여줍니다.

이번 사건은 단발성 이슈가 아닙니다. 본 글에서 정리하듯 npm은 2018년 event-stream, 2021년 ua-parser-js, 2022년 colors/faker, 2024년 lottiefiles 사건까지 거의 매년 대형 공급망 사고를 겪었고, 매번 같은 구조가 반복되었습니다. 2026년의 차이는 자동화된 일제 배포의 정밀도와 영향 범위입니다. 314개의 패키지 중 다수는 다른 패키지의 의존성으로 깊게 박혀 있어, 본인이 그 이름을 들어본 적이 없어도 영향을 받을 수 있습니다.

본 글은 영감 출처(news.hada.io 5월 21일 5점 글)를 발판으로, 한국 개발자·팀이 오늘 안에 해야 할 응급 조치 4가지와 장기 방어 전략 7가지를 본인 운영 경험을 바탕으로 정리합니다. 사건 자체의 기술적 디테일보다 한국 환경에서 즉시 적용 가능한 행동에 초점을 둡니다.

사건 개요 - 무엇이, 언제, 어떻게 일어났나

현재까지 보고된 사건 윤곽을 시간 순으로 정리하면 다음과 같습니다. 본 글은 보안 advisory를 직번역하지 않고, 공개된 정보를 본인 정리 관점에서 다시 짭니다.

  • 시점: 2026년 5월 중순, 약 22분의 짧은 시간 창.
  • 규모: 314개의 npm 패키지에 걸쳐 총 637개의 악성 버전이 publish.
  • 속도: 평균 분당 약 29개 버전이 푸시되어 사람 작업이 아닌 자동화 스크립트로 확정.
  • 침해 추정 경로: 다수 메인테이너의 npm publish 토큰 또는 자격증명 사전 수집 → 자동화 일괄 배포.
  • 악성 코드 성격: postinstall 스크립트 또는 빌드 시점 환경 변수 유출을 통한 토큰·시크릿 수집 패턴이 다수 보고.
  • 탐지·대응: 보안 커뮤니티와 npm 측 빠른 차단으로 다수 버전이 게시 후 수 시간 내 unpublish.

주목할 점은 "22분"이라는 짧은 윈도입니다. 이 시간은 의도적인 설계입니다. 너무 짧으면 보안 모니터링이 트리거되기 전에 끝나고, 적당히 길면 다수의 CI 파이프라인이 실제 그 시점에 신규 버전을 받아 적용해 피해 표면이 자연 증가합니다. 22분은 그 균형점에 가까운 숫자로 보입니다.

공격 메커니즘 분석 - 자격증명 침해 + 자동화 일괄 배포

이번 사건의 기술적 핵심은 화려한 zero-day가 아니라 "훔친 자격증명 + 자동화"라는 매우 평범한 조합입니다. 평범하다는 것이 핵심입니다. 화려한 취약점이 필요 없을 만큼 npm 생태계의 인증·게시 모델이 단일 실패점을 가지고 있다는 뜻이기 때문입니다.

1) 자격증명 수집 단계 (사전 작업)

공격자는 사건 발생 이전 수개월간 다양한 경로로 npm 토큰·이메일·OTP 회피용 세션 쿠키를 수집한 것으로 보입니다. 수집 경로는 피싱, 메인테이너 PC 멀웨어, 과거 데이터 유출 재활용, npmrc 파일 누출 등 매우 다양합니다. 2FA가 있어도 토큰 자체가 노출되면 우회되는 경우가 있어, 메인테이너 다수가 2FA를 켜두었어도 공격 자체는 성공할 수 있습니다.

2) 일괄 배포 단계 (22분의 윈도)

수집된 자격증명을 가지고 공격자는 사전 준비한 악성 변종을 314개 패키지에 일제히 publish 했습니다. npm publish API를 자동화로 호출하면 분당 수십 개의 publish가 충분히 가능합니다. 22분 안에 637개 버전이 게시된 점은 이 추정과 일치합니다. 일괄 배포 시점을 메인테이너들이 동시에 깨어 있지 않은 시각으로 잡았을 가능성도 높습니다.

3) 페이로드 실행 단계 (피해자 측)

악성 버전은 대부분 postinstall 훅에서 작동하거나 빌드 시점 환경 변수를 수집해 외부 서버로 전송하는 형태로 보고됩니다. 한국 기업 환경에서 이 단계의 위협은 두 가지로 갈립니다. (a) 로컬 개발 PC 침해: 개발자가 무심코 npm install 후 토큰·쿠키 유출. (b) CI/CD 침해: GitHub Actions 또는 사내 Jenkins에서 빌드 시점 시크릿이 외부 유출. CI 토큰은 권한 범위가 넓은 경우가 많아 후자가 본인 관점에서는 더 위험합니다.

유사 사건의 역사 - 같은 구조가 반복된다

npm 공급망 공격은 처음이 아닙니다. 본인 기억에 남는 주요 사건을 정리하면 다음과 같습니다.

  • 2018 event-stream: 메인테이너 교체 직후 새 메인테이너가 악성 페이로드를 끼워 넣어 비트코인 지갑 라이브러리에 영향. "신뢰의 양도"가 단일 실패점이라는 사실을 처음으로 대중에게 보여준 사건.
  • 2021 ua-parser-js: 메인테이너 계정 침해 후 악성 버전 배포. 다운로드 수가 매우 높은 패키지였기 때문에 영향 범위가 광범위.
  • 2022 colors/faker: 메인테이너 본인이 의도적으로 코드를 망가뜨린 사건. "신뢰는 자발적 협력"이라는 사실을 다시 환기.
  • 2023 노드패키지 typosquatting 다수: 인기 패키지 이름과 오타가 비슷한 악성 패키지 다량 등록.
  • 2024 lottiefiles 등: SDK 패키지 침해를 통해 사용자 토큰·지갑 정보 탈취 시도.
  • 2026 5월 314개 패키지 일제 침해: 본 사건. 규모와 속도 모두 신규 단계.

이 목록의 패턴은 명확합니다. 매번 "메인테이너 자격증명"이 깨지고, 매번 같은 방식으로 npm 인프라가 게시를 허용합니다. 사건마다 임시 대응은 있지만 구조적 해결책은 도입이 느립니다. provenance·sigstore 같은 장기적 해법이 등장했지만, 채택률은 여전히 낮습니다.

왜 npm은 반복적으로 공격받는가 - 구조적 취약점 5가지

1) 단일 메인테이너 모델

npm의 대부분 패키지가 1~2명의 메인테이너로 운영됩니다. 이 한 명의 자격증명이 깨지면 수백만 다운로드짜리 패키지가 그대로 노출됩니다. PyPI, crates.io 등 다른 레지스트리도 비슷한 구조지만, npm은 평균 의존성 깊이가 가장 깊어 영향 증폭이 큽니다.

2) 깊은 의존성 트리

본인 프로젝트가 직접 의존하는 패키지가 10개여도, 그 10개의 트리를 펼치면 실제 설치되는 패키지는 보통 1,000개 이상입니다. 본인이 들어본 적도 없는 패키지가 본인 빌드 환경에서 임의 코드를 실행할 수 있다는 뜻입니다.

3) postinstall 훅의 임의 코드 실행

npm은 postinstall 시 임의 스크립트를 실행하도록 허용합니다. 정상 용도(네이티브 빌드 등)도 있지만, 공격자에게는 페이로드 자동 실행 통로가 됩니다. 다른 패키지 매니저 중 일부는 이 훅을 기본 비활성화로 갑니다.

4) 메인테이너 신뢰 양도의 무방비

메인테이너가 다른 사람에게 패키지를 넘기는 절차는 사실상 이메일 한 통입니다. 새 메인테이너의 신원·이력·악의 여부에 대한 검증이 약하고, 사용자가 자동으로 알 수 있는 방법도 없습니다.

5) provenance 채택의 더딘 속도

npm provenance는 2023년 도입되었지만 채택률은 인기 패키지 기준으로도 한 자릿수에서 두 자릿수 초반에 머무는 것으로 알려져 있습니다. 모두가 채택하면 이번 같은 사건의 표면이 크게 줄어들지만, 메인테이너 측 도입 동기 부족이 병목입니다.

오늘 안에 해야 할 4가지 응급 조치

이 섹션은 본 글에서 가장 실무에 가까운 부분입니다. 한국 개발팀이 오늘(혹은 늦어도 이번 주) 안에 처리해야 할 것 4가지입니다.

1) 의심 패키지 즉시 확인 - npm audit

가장 먼저 모든 활성 프로젝트에서 다음을 실행합니다.

npm audit --audit-level=high
npm audit signatures   # provenance/서명 검증
npm outdated

npm audit signatures는 의외로 덜 알려진 명령으로, 패키지의 npm 서명·provenance 유효성을 검증합니다. 사건 발생 시점 전후 24~48시간 내에 받은 패키지가 있다면 이 명령으로 한 번 더 확인합니다.

2) lock 파일 변경 이력 검증

package-lock.json 또는 yarn.lock의 최근 변경을 git 이력으로 확인합니다.

git log --since="2026-05-20" -- package-lock.json
git diff HEAD~5 -- package-lock.json | grep -E "^\+.*\"version\""

의심 시점에 lock 파일이 변경되었다면 그 버전이 실제 정상인지 npm 공식 advisory와 대조합니다. 한 명의 개발자가 무심코 npm install 후 lock 파일을 같이 커밋하는 경우가 있기 때문에 PR 단위 점검이 필요합니다.

3) 빌드 캐시 즉시 무효화

로컬·CI·사내 npm 미러에 캐시된 악성 버전을 제거합니다.

npm cache clean --force
rm -rf node_modules
npm ci   # frozen lockfile 기반 깨끗한 재설치

GitHub Actions의 actions/cache, GitLab CI cache, 사내 Nexus/Verdaccio 미러도 같이 무효화합니다. 캐시에 악성 버전이 남아 있으면 응급 조치 의미가 사라집니다.

4) 노출 가능성 있는 토큰·시크릿 즉시 로테이션

postinstall 페이로드의 주 표적은 환경 변수·토큰·쿠키입니다. 다음 항목을 5월 21일 이후 한 번이라도 빌드에 노출했다면 로테이션합니다.

  • npm publish 토큰 (CI에서 사용 중인 경우 최우선)
  • GitHub PAT·Actions OIDC 토큰
  • AWS·GCP·Azure 액세스 키
  • Slack·Discord 웹훅 URL
  • DB 연결 문자열·내부 API 시크릿

로테이션 작업은 귀찮지만, 토큰 한 개의 비용은 침해 한 건의 비용에 비하면 무시할 만합니다. 본인이 빌드 환경에 한 번이라도 평문으로 둔 시크릿이 있다면 이번 기회에 모두 새로 만드세요.

장기 방어 전략 7가지 - 다음 사건을 막는 시스템

1) npm provenance 사용

본인이 npm에 패키지를 게시한다면 즉시 provenance를 활성화합니다. GitHub Actions 기준 permissions: id-token: write 추가와 npm publish --provenance 한 줄이면 활성화됩니다. 사용자 측에서는 npm audit signatures로 provenance를 강제할 수 있습니다.

2) Frozen lockfile 강제 (--frozen-lockfile / npm ci)

로컬에서 npm install을 쓰더라도, CI에서는 반드시 npm ci 또는 yarn install --frozen-lockfile을 강제합니다. lock 파일과 일치하지 않으면 빌드가 실패하도록 게이트를 두는 것이 핵심입니다. 이 한 가지만으로 "야간에 누군가가 새 버전을 publish해서 빌드가 그것을 가져가는" 경로가 거의 차단됩니다.

3) SBOM 생성·관리

매 빌드마다 SBOM(Software Bill of Materials)을 자동 생성해 저장합니다. 형식은 CycloneDX 또는 SPDX. cyclonedx-bom 또는 @cyclonedx/cyclonedx-npm 같은 도구로 1분 안에 도입 가능합니다. SBOM이 있으면 다음 사건이 터졌을 때 "우리가 그 패키지를 쓰는지"를 5분 안에 답할 수 있습니다.

4) Dependabot / Renovate 도입

의존성 갱신을 사람의 의지가 아니라 자동 PR로 만듭니다. 단, 자동 머지는 절대 켜지 않습니다. PR을 만들면 사람이 검토하는 절차가 강제됩니다. 검토 시 npm view로 최신 버전의 메인테이너·publish 시각·다운로드 추이를 한 번 확인합니다.

5) 정기 의존성 감사 사이클

분기에 한 번 의존성 감사 미팅을 둡니다. 안건은 세 가지입니다. (a) 안 쓰는 패키지 제거, (b) deprecated 패키지 교체, (c) 메인테이너 활동이 멈춘 패키지의 fork·교체 검토. 본인 경험상 이 한 시간이 1년 뒤 사고 대응 시간을 100배 줄여줍니다.

6) 미니멀 의존성 정책

"이 기능을 위해 100줄짜리 패키지를 추가할 가치가 있는가"를 PR 리뷰 단계에서 의무 질문으로 둡니다. 좌표 라이브러리·문자열 유틸·날짜 포맷 같은 작은 기능은 본인 코드 10~30줄로 충분한 경우가 많습니다. 의존성이 적을수록 공격 표면이 작습니다.

7) 행위 기반 스캐너 (Socket.dev, Phylum 등) 도입

전통적 npm audit은 알려진 advisory와 대조하지만, Socket.dev·Phylum 같은 도구는 패키지 코드의 의심 행위(네트워크 호출, eval, postinstall 패턴 등)를 행위 기반으로 탐지합니다. 알려지지 않은 신규 침해를 잡을 가능성이 높아집니다. CI에 PR comment 형태로 통합하는 것이 한국 팀 기준 가장 부드러운 도입 방식입니다.

CI/CD 파이프라인 강화 - GitHub Actions 예시

위 7가지 전략을 실제 GitHub Actions 워크플로로 묶으면 다음과 같은 형태가 됩니다. 핵심 게이트만 발췌한 예시입니다.

name: secure-build
on: [push, pull_request]
permissions:
  contents: read
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      # 1) frozen lockfile - lock과 불일치 시 즉시 실패
      - run: npm ci

      # 2) audit 게이트
      - run: npm audit --audit-level=high
      - run: npm audit signatures

      # 3) SBOM 생성
      - run: npx @cyclonedx/cyclonedx-npm --output-file sbom.json
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

      # 4) 행위 기반 스캔 (Socket.dev 예시)
      # - uses: socket-security/socket-cli-action@v1

      - run: npm test
      - run: npm run build

이 워크플로의 핵심은 "한 단계라도 실패하면 빌드 자체가 중단"이라는 점입니다. 응급 조치를 사람 의지에 맡기지 않고 CI 게이트로 시스템화하는 것이 본 글의 마지막 핵심 메시지입니다.

모니터링 도구 비교 - Snyk, Socket.dev, Phylum, npm audit

실무에서 자주 비교되는 도구를 본인 관점에서 정리합니다.

도구탐지 방식강점약점
npm audit알려진 advisory 대조무료·기본 내장제로데이·행위 기반 탐지 약함
Snykadvisory + 라이선스 + 일부 행위UI·리포팅 우수, 기업용 기능 풍부유료 플랜에서 본격 기능
Socket.dev행위 기반(eval/postinstall/네트워크)알려지지 않은 침해 탐지, PR 코멘트 UX 우수거짓 양성 일부, 한국 사례 사례화 적음
Phylum행위 기반 + 메인테이너 평판메인테이너 신원·이력 분석도입 곡선 약간 가파름
GitHub Dependabotadvisory + 자동 PRGitHub 통합·무료탐지보다 갱신에 가까움

한국 팀의 권장 조합은 다음과 같습니다. (1) 기본은 npm audit + Dependabot(무료, 즉시 도입). (2) 그 위에 Socket.dev 또는 Snyk 중 하나를 PR 리뷰 단계 보조 게이트로. (3) 시간 여유가 있다면 Phylum으로 메인테이너 평판까지 본다는 식의 3단 구성을 권합니다.

한국 기업·스타트업 환경에서의 적용

위 전략을 한국 환경에 옮길 때 본인이 자주 마주치는 마찰 지점을 정리합니다.

  • 스타트업: 보안 인력이 없는 경우가 많습니다. 무료 도구(npm audit, Dependabot, Socket.dev 무료 티어)만으로도 80%를 커버할 수 있으므로 일단 도입부터 합니다. 완벽을 추구하지 말고 "안 하던 것을 한다"를 목표로.
  • 중견·대기업: 사내 npm 미러(Nexus, Verdaccio)가 있다면 미러 자체에 allowlist·블록리스트를 적용합니다. 응급 사건 시 미러에서 차단하는 것이 모든 개발자에게 동시에 효과를 미칩니다.
  • 금융·공공: 망분리 환경이라도 npm 미러를 통해 외부 패키지를 들여오는 경로는 동일합니다. SBOM·서명 검증을 사내 표준으로 만드는 것이 효과적입니다.
  • 프리랜서·1인 개발: 본인 PC가 곧 인프라입니다. 토큰을 평문으로 .env에 두는 습관을 즉시 버리고, 1Password CLI·doppler 같은 시크릿 매니저를 도입합니다.

개발자 개인 책임의 한계와 생태계 책임

본 글에서 정리한 11가지(응급 4 + 장기 7)를 모두 실행해도 공급망 공격은 100% 막지 못합니다. 그것이 현실입니다. 개인·팀 단위 노력의 한계가 분명히 있고, 그 한계를 넘는 것은 생태계 수준의 변화입니다.

본인이 생각하는 생태계 책임은 세 가지입니다. (1) npm Inc.(GitHub)의 메인테이너 보안 인증 강화 - WebAuthn·하드웨어 키 의무화. (2) provenance 채택률을 끌어올리기 위한 인기 패키지 대상 인센티브. (3) postinstall 훅의 기본 비활성화 옵션 제공. 이 세 가지는 개인 노력으로 풀 수 없는 부분이며, npm·GitHub의 정책 변화가 필요합니다.

2026 하반기 공급망 보안 트렌드 - 본인 예측

본인이 예상하는 2026 하반기 공급망 보안 흐름은 다음과 같습니다.

  • provenance 채택 가속: 인기 패키지 메인테이너의 자발적 도입이 사건 직후 늘어날 가능성. 채택률 한 자릿수 → 두 자릿수 중반으로 상승 예상.
  • 행위 기반 스캐너의 표준화: Socket.dev·Phylum의 도입이 무료 티어 중심으로 확산.
  • SBOM 의무화 흐름: 미국 EO 14028 흐름의 영향으로 한국 공공·금융 입찰에서 SBOM 요구가 늘어날 가능성.
  • AI 기반 코드 리뷰 + 의존성 분석 결합: PR 리뷰 시점에 AI가 새 의존성의 위험을 자연어로 코멘트하는 흐름.
  • npm 외 레지스트리 옵션 검토 증가: deno, jsr, bun의 자체 레지스트리에 대한 관심 증가. 단 단기간 npm 대체는 어려움.

결론 + 체크리스트 15개

본 글의 핵심을 한 줄로 요약하면 이렇습니다. 공급망 보안은 도구가 아니라 시스템이며, 시스템은 오늘 안에 시작할 수 있는 작은 게이트의 누적입니다. 22분이 다음에는 더 짧아질 것입니다. 그 다음 22분을 막는 것은 본인 팀의 응급 4가지와 장기 7가지의 시스템화입니다.

마지막으로 본인이 사용하는 15개 항목 체크리스트를 공유합니다. 출력해서 책상 옆에 붙여두고 한 줄씩 처리하세요.

  1. 모든 활성 프로젝트에 npm audit --audit-level=high 실행
  2. npm audit signatures 실행으로 provenance/서명 점검
  3. 5월 20~22일 lock 파일 변경 이력 git으로 확인
  4. npm 캐시·CI 캐시·사내 미러 캐시 전체 무효화
  5. 5월 21일 이후 빌드에 노출된 모든 토큰·시크릿 로테이션
  6. npm publish 토큰 권한 범위 최소화 + 만료 설정
  7. CI에서 npm ci / --frozen-lockfile 강제
  8. CI에서 npm audit 게이트화(고위험 발견 시 실패)
  9. SBOM 생성 워크플로 도입(CycloneDX 권장)
  10. Dependabot 또는 Renovate 활성화 (자동 머지 X)
  11. 분기 1회 의존성 감사 미팅 캘린더 등록
  12. 본인 게시 패키지에 npm provenance 활성화
  13. Socket.dev 또는 Snyk 중 하나 무료 티어 도입
  14. postinstall 훅 사용 패키지 화이트리스트 검토
  15. 사내 npm 미러 운영 시 allowlist/blocklist 정책 수립
