Codex CLI Session Logs Balloon to Hundreds of GB

What a subagent session log disaster teaches about log hygiene in the AI coding CLI era

Jul 21, 2026 Dev & Infra

Introduction: Coding Agents Leave Behind More Than Code

A recent GeekNews topic caught the developer community's attention: someone running subagents through Codex CLI found their session logs had ballooned to hundreds of gigabytes, exhausting local disk space. It sounds implausible at first - surely a log file can't get that large - but the GitHub issue tracker documents a case, with specific numbers, where thousands of child sessions spawned from a single parent session together exceeded 700GB.

By the second half of 2026, running several CLI-based coding agents like Claude Code, Codex, and Cursor at once is nothing unusual for a single developer. The problem is that these tools faithfully record every step of conversation, planning, and tool execution as session files. You review and delete code, but the logs recording how that code got made quietly pile up while nobody's watching. Rather than just retelling the incident, this piece breaks down why this kind of blowup is structurally inevitable, and what to check and change right now.

1. What Was Reported - The Numbers Behind the Blowup

GitHub issue #34061 on the openai/codex repository ("Insane Codex Disk Usage from Subagents") documents the reproduction in detail. A single parent session spawned 2,393 child session files, and those child sessions alone consumed roughly 731.5 GiB. The entire ~/.codex/sessions directory reached about 755 GiB, and the whole ~/.codex directory reached about 760 GiB, nearly filling a 1.8 TiB volume to 99-100% capacity. One single child session file wrote 483.7MB across 353,255 JSONL records in 3 minutes 19 seconds - roughly 1,770 records per second. At the time of reporting this was on Codex CLI 0.144.6 (affected range 0.142.4-0.144.6) on macOS arm64, and the issue remained open with no official maintainer resolution documented as of the check.

A separate issue, #24948, on the same repository points to repeated compaction history and raw tool output accumulating without cleanup, causing session logs to balloon to 700MB-2GB. A thread on the OpenAI developer community also reports disk exhaustion from leaving Codex sessions open for extended periods. Session files are generally reported at paths like ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl, with a separate logging database such as ~/.codex/logs_2.sqlite accumulating alongside. Exact paths and behavior can vary by version, so checking your own installed version's official docs and local directories directly is the safer approach.

2. Why It Can Balloon to Hundreds of GB - Structural Causes

Simply chalking this up to "a lot of logs piled up" doesn't explain the scale. Taken together, the reported cases point to several structural causes stacking on top of each other.

2.1 Subagent Fan-Out

Every time a parent session splits work across multiple subagents, some portion of the parent's state or accumulated context can get written into each child session as well. As the subagent count scales into the hundreds or thousands, the same context effectively gets duplicated that many times, so total size grows not additively but closer to multiplicatively.

2.2 Duplicated Compaction History

Keeping a long conversation going requires compacting older context to save tokens. But if both the compaction process itself and the pre-compaction original record get logged, the structure becomes "original plus summary" accumulating endlessly as the conversation lengthens.

2.3 Context Rematerialization on Resume

Reports point to duplication or re-recording of prior history when reloading and reprocessing an entire past conversation to resume an interrupted session. The more frequently sessions are resumed, the more room this duplication has to accumulate.

2.4 Unbounded Storage of Raw Tool Output

Coding agents need to record file reads, command execution, and test results in full to use them for the next decision. If that output is stored verbatim with no cap or summarization, a single task touching a large log file or a large codebase can balloon a session file almost instantly. The fact that rotation, size caps, and automatic deletion policies aren't a default amplifies every one of these causes.

3. Not Just Codex - Similar Cases Across AI Coding CLIs

This isn't meant as a takedown of one product. That the same class of problem has been reported across other vendors actually illustrates the nature of the issue better. Claude Code's GitHub repository has its own open issue about ~/.claude growing unbounded with no dedicated management mechanism, alongside separate reports of debug logging entering an infinite loop and producing a single file over 20GB, a background task output file reported to reach 324GB in 16 minutes, and a macOS case where ~/.claude/debug and MCP log caches accumulated to roughly 472GB. A feature request for automatic compression of session logs (~/.claude/projects/*.jsonl) is also open in the community, and an open-source TUI tool has appeared specifically to help reclaim disk space from ~/.claude.

In other words, this is best read not as one vendor's isolated bug, but as a signal that several companies, building similar architectures around the same period, are repeating a similar mistake. The more autonomously an agent plans, executes, and retries, the harder it is for a human to anticipate how many events it will generate to record - how many subagents it spawns, how many times tool output gets replayed - and log/cache management policy hasn't caught up with tool maturity yet.

4. The Real Problems - From Full Disks to Contaminated Backups

Session log bloat goes well beyond "it takes up some space" and cascades into several practical problems.

4.1 Disk Full and Interrupted Work

The most direct consequence is running out of disk space. Once a volume fills up, the coding agent itself stalls, and other applications sharing the same disk - in severe cases even OS login or boot - can be affected too.

4.2 Degraded System Performance

Continuously creating and modifying files at the hundreds-of-gigabytes scale can slow down overall system responsiveness through filesystem indexing overhead, backup software's change detection, and disk fragmentation. Some media reports have raised concerns that a particular version's logging approach triggered far more frequent writes than expected, potentially affecting SSD lifespan - though this specific claim hasn't been broadly, independently verified at scale, so it's safer to treat it as a possibility ("write frequency can spike abnormally") rather than a settled fact.

4.3 Backup Contamination and Rising Backup Costs

If you use a personal backup tool or cloud sync service that backs up your whole home directory, a hundreds-of-gigabytes log folder gets swept into the backup set as-is, inflating both backup time and storage cost. It's entirely possible that when you actually need to restore something, useless session logs are taking up most of your backup capacity.

4.4 Expanded Privacy and Security Exposure

Session logs can retain the actual content of files an agent read and wrote, commands it ran, and sometimes even environment variables or API responses verbatim. The larger a log grows and the longer it sits untouched, the more files that could expose sensitive code or credentials accumulate outside anyone's active control. A log size problem is, ultimately, also a data-handling-scope problem.

5. A Defense Playbook - What to Check and Configure Right Now

A complete fix is on vendors, but there's plenty users can do immediately.

5.1 Find Out Where the Logs Actually Live

Start by confirming where your AI coding CLI stores sessions, logs, and caches. Find the storage path in official docs or config files, and periodically check the actual size of that folder with du -sh or the interactive tool ncdu.

5.2 Clean Up Regularly, But Never Touch a Running Session

Start with old sessions you have no plan to resume. Forcibly deleting a file while its writing process is still alive can corrupt it or make it unresumable, so stop the relevant process first, then clean up.

5.3 Set Your Own Rotation and Retention Policy

If the tool doesn't provide one by default, use a general-purpose tool like logrotate to periodically compress and archive old logs, or configure automatic deletion after a set period. Relying on manual deletion means it eventually gets forgotten.

5.4 Minimize Logging via Configuration

If the tool offers an option to lower or disable verbose/trace logging levels, keep it at the minimum by default and only raise it temporarily when you actually need to debug. Exact setting keys and environment variables vary by tool and version, so check your installed version's official documentation first.

5.5 Monitor Disk Usage Continuously

Setting an alert threshold at 80-90% disk usage means that even if a blowup is in progress, you avoid the worst-case scenario of a volume filling up so completely that nothing can run. For teams, adding developer workstation disk metrics to infrastructure monitoring you already run - a Prometheus plus node_exporter setup, for instance - is another option.

5.6 Isolate Onto a Separate Volume With a Symlink

If you expect a session/log folder to keep growing, you can protect your system volume by keeping the actual directory on a separate partition or external volume with ample free space, leaving only a symlink in your home directory.

5.7 Block Accidental Commits With .gitignore

If a tool creates its session/log/cache directory inside or near a project folder, make sure to add that path to .gitignore to prevent accidentally committing a massive log file. Once a large file is committed, removing it from history is far more tedious.

6. Observability Debt and Log Hygiene - A General Lesson for the Agent Era

The bigger lesson here isn't one tool's bug - it's the concept of "observability debt." In traditional software, logs were auxiliary material for humans diagnosing problems, and they accumulated at a relatively predictable rate. An agent that autonomously plans, executes, and retries, by contrast, is much harder for a human to anticipate in terms of how many events it will generate - how many subagents get spawned, how many times tool output gets replayed, depends heavily on the task at hand.

Just as unaddressed technical debt eventually demands a larger payment, neglected log and cache management eventually sends a bill in the form of a full disk. Log hygiene in the AI agent era is no longer just "an occasional habit of deleting a folder" - it needs to be treated as a formal line item in development environment operations. That's the practical conclusion this incident leaves behind.

7. What Vendors Need to Fix

User-side mitigation alone can't fix this at the root. Community issue trackers repeatedly surface the same set of asks: a default retention period and size cap on session/log directories, a warning to the user when thresholds are exceeded, built-in rotation and compression that automatically cleans up compaction history and duplicate events instead of letting it accumulate unbounded, and a diagnostic cleanup command shipped as an official CLI feature. Today, users have to dig through directories themselves to even discover the problem - but as autonomous agents become a standard part of the developer toolchain, these safeguards need to move from optional to default.

8. The Connection to Parallel Agents and Session Visibility Tools

This issue connects to other threads covered recently. As noted in the piece on unleashing multiple AI agents on one repo, scaling up parallel sessions raises throughput, but it raises the rate session logs accumulate by roughly the same factor. Worktrees and containers can stop file conflicts, but log bloat is a separate axis that needs its own management.

Meanwhile, a local dashboard like AgentsView, which indexes Claude Code, Cursor, and Codex sessions in one place for search and cost tracking, solves the visibility problem of seeing all your sessions across tools at a glance - but it doesn't by itself stop disk bloat. If anything, adopting a tool like that is a good occasion to first ask "how much have my session logs actually accumulated to right now." Visibility tooling and cleanup/rotation policy aren't substitutes for each other - they're complements.

Conclusion: Logs Deserve as Much Management as Code

The Codex CLI subagent session log blowup isn't a story that ends with one tool's mistake. Now that autonomously planning and executing AI coding agents are a standard workflow, the pattern of logs and caches recording that process accumulating without control is showing up across multiple vendors. Three practical actions sum up what's worth doing today. First, check exactly where and how much your current AI coding CLI is storing in sessions and logs. Second, set up a rotation/retention policy and disk monitoring right now. Third, periodically check vendor docs and issue trackers for improved defaults in newer releases. Checking what your development environment is leaving behind is becoming as much a basic habit in the AI agent era as reviewing the code itself.
