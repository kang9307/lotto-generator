先写规格能抓到什么 - 模型检查器扫过的范围、状态爆炸这张账单，以及到代码为止还剩的距离

不是测试抓不到，而是测试造出那个顺序的概率很低

2026-09-10 开发/基础设施

有一种比方，把模型检查器摆在证明助手旁边：数学家有用机器检查证明的工具，开发者也有用机器检查设计的工具。这个比方有用，但只对了一半，因为两种工具检查的对象根本不同。

比方贴合的一面是这样。类型检查和单元测试全都通过的程序，一并发跑起来就坏掉，这是常事。两个作业各自在内部保持顺序，但这两串顺序交错的方式有多少种，已经不是人能手工数清的规模。开发者挑出来的那几个场景，在这个数目面前只是样本。如果有一件工具能不去扩大样本而是把全部扫一遍，那它在这个位置上就有价值。

比方走偏的地方有两处。第一，全扫一遍是要付账单的，检查成本随模型规模呈指数增长。所以实务中真正跑起来的永远是极小的模型，而小模型里没有缺陷，并不等于大系统里没有缺陷。第二，模型检查器看到的是设计的模型，不是代码。规格通过了，实现是否遵循这份规格，这个保证得另外造出来。

本文里没有状态数或检查耗时之类的数字。这些值会随模型的变量个数、常量规模和检查器配置整个数量级地变动，脱掉条件的数字每被转述一次就更假一分。这里写的是性质、条件和限度。自己模型的数字，只能从自己的模型里跑出来。

缘起 - 把模型检查器摆在证明检查器旁边

数学那边的工具把命题放成类型，把证明放成该类型的值。语言被设计成这样：说某个值的类型是某个命题，同时也就等于说这个值是那个命题的证明。它的运作方式是检查那个为任意对象生成证据的函数是否被正确构造出来，所以证明可以编译这句话才说得通。

在开发这边占据同一位置的，是形式规格语言和模型检查器。这里的检查对象不是证明，而是状态机。你把系统可能处于的状态写成变量，把从哪个状态可以走到哪个状态写成关系。检查器就从初始状态出发，沿着这个关系把能到达的状态一个个造出来，寻找你写下的条件被打破的位置。

这个对照之所以有用，是因为两边都由机器而不是由人眼来判定。这个对照之所以危险，是因为表面上的相似会让人以为两种工具的保证范围也一样。数学证明的形式化保证什么、不保证什么，在形式化不等于证明里另有整理。本文处理的是另一侧，也就是并发与分布式设计的状态搜索。

各自检查什么 - 跑过的路径与可达的状态

两种方式的差别不在缺陷有多难，而在观察的对象。

  • 单元测试看到的 — 在作者挑选的输入下实际执行过的一条路径。如果涉及多个线程，那天那台机器上碰巧被调度出来的那一个顺序也一并被固定下来。同一个测试跑一千遍，这一千遍可能走的是同一个顺序。
  • 模型检查器看到的 — 把模型允许的每一个后继状态都造出来，扫遍可达状态空间。凡是没有指定哪个动作先发生的地方，两条分支都会走一遍。于是人想不到的交错也被自动试过。
  • 两者共有的限度 — 谁都不检查没被写下来的东西。测试不知道没写过的用例，模型检查器不知道没放进规格里的迁移。后者更危险，后面单开一节谈。

这里有一句常见的滑口话：测试抓不到的缺陷。这不准确。竞态引发的缺陷在时机凑巧时照样会在测试里炸出来，任何测试套件里那些间歇性亮红灯的用例，有相当一部分正是这类缺陷。准确的说法是另一句：测试造出那个顺序的概率很低。概率低和不可能是两个词，这个差别会改变你去拿哪件工具。

概率低会带来两个实务后果。一是难以重现：炸出来之后如果造不回同样的条件，也就无法确认修好了没有。二是间歇性失败会被忽略：重跑一次就过了，结论很容易滑向测试不稳定。模型检查器给的不是把概率提高，而是把概率去掉。只要在模型里这个顺序是可能的，你就一定会碰上它。

把顺序的种数算出来 - 184,756 这个数字在说什么

设有两个作业，各由十个步骤组成。作业内部的顺序是保持的，也就是说 A 的第三步排在 A 的第二步之后。但 A 的步骤和 B 的步骤如何互相交错，并没有被规定。

此时可能的执行顺序有多少种，就变成了二十个位置里把哪十个给 A 的问题。答案是 184,756 种，即二十的阶乘除以十的阶乘的平方。状态本身是有限的，作业也只有两个，光靠顺序就出来这么多。

这个数字里该读的不是它有多大，而是它增长的形状。把作业加到三个，或者把步骤加到二十步，这个值不会慢慢往上爬。而真实系统在此之上还要加进部分失败：每一步都可能成功或失败，失败后面挂着重试，重试又可能制造重复。失败点的种数会乘到顺序的种数上。

人去挑场景，就是伸手到这个乘积里捞五六个出来。眼光好就捞得准，眼光差就捞不准，而真正的问题在于没有办法判定自己捞得准不准。覆盖率数字说的是代码行有没有被执行，它不说顺序有没有被扫过。

所以抓到的缺陷种类不一样

把两种方式各自擅长抓的缺陷分开写，界线就清楚了。值得注意的是下表里哪一侧都没有写不可能，分开的是概率和成本。

缺陷类型 测试能抓到吗 模型检查能抓到吗 为什么
算式错了(边界值、舍入、符号) 抓得很好 基本抓不到 模型通常把计算抽象掉了。它是为了看顺序而不是看数值才造出来的模型。
空引用、类型不匹配 抓得很好 不属于其范围 这是语言层面的问题，规格里没有这种概念。这是类型检查器和测试的地盘。
两个作业争用同一份资源 概率很低 肯定抓得到 只在特定交错下出现。模型检查器把那个交错从偶然变成了规则。
重试造成重复生效 概率很低 肯定抓得到 只从失败与重发的组合里出来。要在真实环境造出这个组合，就得注入故障。
主节点切换过程中的写入丢失 非常低 把迁移放进模型就抓得到 只在切换与写入重叠的那一小段成立。这个迁移不写进规格，检查器同样看不见。

饥饿(某一方一直被往后排) 几乎抓不到 写了公平性就抓得到 这是活性的地盘。不用公平性假设，这个判定根本无法成立。
性能下降、延迟上升 靠测量抓到 不属于其范围 模型里没有时间。有顺序，但没有耗时。

表里最后一行最要紧。两种工具检查的都是人写下来的东西。不同之处在于书写的语言不同，因而书写时人被迫进行的思考种类也不同。规格还在起草，答案就已经浮出来、检查器根本不必跑，这种情况并不少见。

一个例子 - 两个作业分用同一条连接

需要一个具体的形状。设有两个异步作业共用一条连接，每个作业结束时都在收尾里关掉这条连接。用流式库写出来是下面这个样子。

// 有缺陷的摆法 - 收尾挂在各个作业上
merge(
  jobA$.pipe(finalize(() => resource.close())),
  jobB$.pipe(finalize(() => resource.close())),
).subscribe();

// 修正后的摆法 - 让连接的寿命跟着外层订阅
merge(jobA$, jobB$).pipe(
  finalize(() => resource.close()),
).subscribe();

前一种摆法会出什么事，只要指出一个顺序就够了。A 先结束，A 的收尾就跑起来把连接关掉，而还在跑的 B 用上了一条已关闭的连接。反过来 B 先结束也是对称的同一件事。两者几乎同时结束，则什么都不会发生。

这个缺陷在测试里不容易被逮到，原因就在这里。开发环境中两个作业的长度往往相近，或者其中一个短到收尾恰好落在另一个已经结束之后。两个作业时长拉开的条件是在真实流量里才第一次被造出来。而且症状出现的位置不在收尾代码里，而在使用连接的那一侧。

修正后的摆法做的事很简单：把资源的寿命移交给所有者。两个作业谁都不是连接的主人，把它们合并起来的外层订阅才是。把收尾抬到那一层，连接就只在最后一个作业结束之后才关闭。这个修正一边减代码一边消缺陷，属于少见的那一类。

写规格的顺序 - 变量、初始状态、次态关系

把同样的情形搬进模型，书写顺序就固定下来了：选出状态变量，写下初始状态，写下走向下一个状态的关系，写下必须守住的条件。除了这四步之外没有别的地方可写。

---- MODULE SharedConnection ----
VARIABLES connection, aRunning, bRunning
vars == <<connection, aRunning, bRunning>>

Init == /\ connection = "open"
        /\ aRunning   = TRUE
        /\ bRunning   = TRUE

\* A 结束时自己把连接关掉 - 有缺陷的设计
FinishA == /\ aRunning
           /\ aRunning'   = FALSE
           /\ connection' = "closed"
           /\ UNCHANGED bRunning

FinishB == /\ bRunning
           /\ bRunning'   = FALSE
           /\ connection' = "closed"
           /\ UNCHANGED aRunning

Next == FinishA \/ FinishB
Spec == Init /\ [][Next]_vars

\* 不变式 - 只要还有作业在跑，连接就必须是开着的
Safe == (aRunning \/ bRunning) => connection = "open"
====

读法是这样。带撇的名字指的是下一个状态中的取值。aRunning' = FALSE 不是赋值，而是写下下一个状态必须满足的条件。UNCHANGED 表示该变量保持原样，漏掉它，检查器就会把那个变量换成任意取值试一遍。

关键在于 Next 被写成两个动作的选择。哪个先发生没有写，所以检查器两条分支都会踏。换成程序，运行时会替你挑一个；在规格里，没被挑走的那个就原样留下来，成为搜索的一个分支。

要跑起来，只需要一个配置文件，写明检查什么以及用什么条件检查。

SPECIFICATION Spec
INVARIANT Safe
CHECK_DEADLOCK FALSE

在这个模型上，检查器会找到 Safe 被打破的状态：A 已经结束并关掉了连接，而 B 还在跑。并且它会把通往那个状态的路径作为反例吐出来。能给出反例，才是这套方式的实质价值。只被告知条件破了是修不了的，知道是沿哪个顺序走过去破的，才修得了。

不变式与活性 - 始终为真和终将为真

能写的条件有两类。这个区分一旦模糊，你写着规格就会搞不清检查器为什么老是放行。

项目 不变式(安全性) 活性
用话说 坏事不会发生 好事终将发生
判定单位 看一个状态就够 必须看整条状态序列
例句 同时不会有两个主节点 请求最终会收到响应
反例的形状 被打破的状态以及通往它的路径 好事被永远推后的无限循环
在配置文件里的位置 不变式项 性质项
额外需要什么 不需要 公平性假设事实上是必备的
检查成本 相对便宜 贵得多
与缩减手法的配合 可以配合对称性缩减 很难配合对称性缩减

不变式是把一个状态摆出来就能回答真假的句子。前面例子里的 Safe 就是。有没有作业在跑、连接是不是开着，看这两个值判定就结束了。所以检查器每造出一个状态，就当场检查一次。

活性没法这么办。请求最终会收到响应这句话，盯着任何一个时刻的状态都分不出真假，因为那个状态里没有任何东西能区分「这是违反」和「响应稍后就到」。要判定就得把状态序列看到底，而且得处理那些永不结束的序列。

实务中漏掉这个区分会出一件事：只写了不变式，却以为连系统会往前推进也一并检查过了。什么都不做的系统轻松满足大多数不变式，什么都不做，坏事也就不会发生。所以只通过安全性的设计，停在原地也算合格。

不写公平性，活性几乎必然被判违反

规格语言默认假设最坏情况：某个动作现在可行，也可能永远不发生。在这个假设下，凡是「终将如何」的句子几乎全是假的，因为「谁都不做任何事」的执行始终被允许。

所以要检查活性，就得往规格上挂公平性假设。挂法分两步。

\* 挂上公平性的规格 - 能跑的动作终将跑起来
FairSpec == Spec /\ WF_vars(Next)

Done     == /\ ~aRunning
            /\ ~bRunning

\* 活性 - 两个作业都结束后，连接终将被关闭
Liveness == <>(Done /\ connection = "closed")

这里的 WF 是弱公平性：某个动作一直保持在可执行状态，就终将发生一次。强公平性的条件更硬，它认为哪怕不是一直可行，只要无限多次地变得可行，就终将发生。在争抢资源的模型里，这两者的差别会改变结论：有些执行弱公平性允许而强公平性排除，饥饿就住在这条缝里。

公平性假设不是免费的。假设一旦写下去，它是否真的成立，就要由系统那边来承担。调度器不会把某个线程永远往后排、重试不会无限次地失败，这些都是运行环境而不是代码所担保的性质。规格里随手写下的假设若在现场不成立，那么通过的活性只在假设为真的世界里为真。

代价就是状态爆炸

这是这套方式的核心约束。把可达状态一个不漏地扫一遍，意味着要把它们全部造出来并存在某个地方。要避免把已经见过的状态再展开一次，就得记住见过什么，而该记住的东西有多少个，就决定了成本。

而这个数目随模型规模呈指数增长。多一个变量，空间就乘上该变量可取值的个数；多一个参与方，每个参与方的状态就再乘一遍。把节点数从三提到四这样的小改动，就足以让状态数整个数量级地变化。这就是状态爆炸，缓解手法是有的，原理上却消不掉。

缓解手法那一侧有些什么，写出来是这样。

  • 把模型做小 — 用得最多的办法。三个节点、两个取值、消息队列长度为二，缩到缺陷能够出现的最小规模。它依托的经验是：缺陷的结构往往并不依赖参与方的个数。
  • 声明对称性 — 把无需彼此区分的参与方并成一组，让仅仅换了名字的状态被当作同一个。这能大幅削减状态数，但很难与活性检查一起用。
  • 抬高抽象层次 — 只保留值之间是否相异，而不保留值本身。用两个互不相同的元素代替整数，用标签代替负载。只有在待检性质与数值大小无关时才成立。
  • 把范围先切好 — 给重试次数或队列长度加上限，堵住无限扩张。这个上限直接决定了结论的有效范围，必须一并写下来。

这些手法的共同点是：削减成本的办法全都是削减模型。不是把检查器变快，而是把要检查的东西做小。所以省下多少成本，结论的适用范围就跟着缩掉多少。这笔交换就是下一节的内容。

小模型里没有，不等于大系统里没有

检查器一旦找出违反，那个反例是确凿的：在模型允许的顺序当中，确实存在这样一条。反例后面不挂条件。所以这套方式作为找缺陷的工具非常强。

反过来，检查器什么都没找到时，那句话后面要挂三个条件。

  • 在那个规模之内 — 用三个节点跑的，结论就是关于三节点模型的。到四个才第一次出现的缺陷从来不在检查范围里。确实存在必须参与方增多才成立的缺陷，所以这不是一句形式上的免责。
  • 在那些假设之内 — 写了消息不会丢失，那么消息会丢的那个世界就没有被检查。加了公平性，那么只有公平性成立的执行被检查过。假设是把模型做小最有力的手段，因此也最常被忘掉。
  • 在写下的迁移之内 — 这一条最危险。规格里漏掉一个重要迁移，检查器检查的就是一个没有该迁移的系统。通过出来了，而这个通过什么都不代表。可是光看结果画面，它和真正的通过毫无分别。

第三条和「备份成功的日志」与「确实能恢复」是两个命题的结构完全一样，在成功的备份在哪里说谎里谈过的东西与之重叠。绿灯的含义完全取决于那盏绿灯检查了什么。

由此，写规格的人应当养成一个习惯：故意把缺陷放进去，看检查器抓不抓得到。用收尾迁移之前的那个摆法跑，必须出反例；出不来，就说明模型正处于表达不出这个缺陷的状态。只验证过通过的模型，是一台从未被检查过的检查器。

规格通过，也不代表实现正确

这里就是与证明助手的对照分道扬镳的地方。数学那边，被形式化的证明本身就是检查对象，对象和被检物是同一件东西，剩下的落差只有一处：定理的陈述有没有正确地写出它原本想说的命题。

模型检查不是这样。检查对象是人手写出来的设计的模型，而真正在跑的是与之分离的代码。于是落差变成两处。

  • 上面那道落差 — 规格有没有正确刻画真实系统。漏掉的迁移、过强的假设、实际上并不原子却被写成一步的动作，都归在这里。
  • 下面那道落差 — 代码有没有遵循这份规格。规格里没有的捷径、规格中一步而代码中拆成两步的地方、库在背后替你做的事，都归在这里。

触发本文的那篇文章对这一点写得很清楚：检查器的结果只在所配置的有限模型与假设之内有效；漏掉重要迁移的模型即使通过也会漏掉真实缺陷；而且模型的设计有没有被正确实现成实际代码，必须另行查验。它还写到，若需要针对无限范围的一般性证明，就得从模型检查器转向证明工具。

不过原文并没有展开那份「另行查验」由什么构成。把这块整理成要求，就是下一节。

收窄这段落差的三项要求

把规格和代码绑起来的办法有三条。三条都不是完整的保证，叠得越多，落差收得越窄。

第一，写出精化关系

抽象规格和具体规格都写出来，然后检查具体一侧的每一个行为都能映射到抽象一侧的行为。抽象规格里的一步在具体规格里变成好几步也没关系，只要从外面看到的结果相同就成立。这个办法的价值在于可以插入一个中间层：设计与代码相隔太远时，在中间放一份更贴近实现的规格，检查两次。

限度也很清楚。具体规格仍然是规格，不是代码。精化做得再细密，最后那一格 — 也就是具体规格与真实代码之间 — 靠这个办法是合不上的。

第二，给运行加埋点，与模型对照

从跑着的代码里把状态变化留成轨迹，再检查这条轨迹是不是规格允许的执行。方向相反这一点很要紧：前一种办法从规格往下走，这一种从代码往上走。因为只处理实际发生过的事，它扫不到全部可达状态，但换来的是对象是真正的代码。

这里要求的是埋点的质量。对应规格状态变量的那些值必须在同一时刻原子地取到，对照才成立。把不同时刻取到的值捆成一个状态，就会造出一个从未存在过的状态，而那个状态会被报成违反。把日志加多和把埋点做好，是两件不同的事。

第三，从规格里导出测试

把模型检查器产出的反例或探索路径转写成测试场景喂给代码。在代码里强制重现规格找到的那个顺序，正面解决了前面说的概率很低的问题：不是等那个顺序碰巧出现，而是把它造出来。

卡住的地方在重现装置。要在代码里强制某个特定交错，就得能把执行按在选定的点上，而结构分成做得到和做不到两种。有时还得改设计，让线程之间的顺序在测试里可控。也就是说，这个办法会给代码那一侧提出要求。

哪里划得来，哪里划不来

划界的标准不是系统有多难，而是好状态和坏状态能不能用一句话写出来。写得出来就有东西可检查，写不出来，模型做得再漂亮也出不了判定。

对象 不变式能否用话写出 价值 理由
共识与主节点选举 写得出(同时不会有两个主节点) 高 缺陷只在切换那一段出现，而在测试里造出那一段极难。
复制与提交规则 写得出(已提交的条目不会丢失) 高 部分失败与重试的组合很多，而丢失发生得很安静。
租约与独占访问 写得出(只有持有租约的一方才写) 高 问题在过期与续约重叠的那一小段，还牵扯到时钟。
事务与隔离级别 写得出(不会出现不被允许的读结果) 高 允许与否由定义确定，很容易搬进模型。
缓存失效 写得出(写之后的读不会看到旧值) 高 只关乎写入与失效的相对顺序，模型规模很小就够。
重复请求抑制 写得出(同一个请求不会被应用两次) 高 这是重试制造出来的缺陷，在运行测试里很难重现。
取消与完成的竞争 写得出(被取消作业的结果不会生效) 高 两者重叠的瞬间很窄，光读代码看不出它们会重叠。
界面流程与易用性 写不出 低 好状态的定义是人的判断，没有可形式化的对象。
性能与容量 写不出 低 模型里没有时间。有顺序，但没有耗时。
有人介入的运维流程 只能部分写出 低 人的行为可以写成迁移，但「照着做」的保证在模型之外。

表里前七行有个共同性质：缺陷出现的条件很窄，出现时又很安静。大声死掉的缺陷横竖都会被发现，真正长期潜伏的是带着略微不对的值继续跑的那种，而这种缺陷主要来自顺序。多方分用同一份资源而造成停滞的结构，在管道缓冲区装满引发的死锁那边有一个实物。

还有一点要补。有不少地方表面上不像分布式系统，实际上就是。一个设置在多台设备上各自改动、事后再合并，就属于这种。一个开关就是一个分布式系统说的就是这个例子。只要存在被并发写入、事后再合并的值，那个位置就已经带着顺序问题了。

起步的顺序 - 不要给整个系统建模

失败的引入几乎只有一种形状：想把整个系统搬进规格。这种尝试还没撞上状态爆炸，就先耗尽在人的时间里了。触发本文的那篇文章给出的建议方向相同：不要给全局建模，集中在一个具体问题上。它举的例子是共享资源的释放、重复请求的抑制、取消与完成的竞争。

整理成顺序是五步。不是工具用法，而是判断的顺序。

  • 第一，挑出一句话。把这个系统里绝对不能发生的那一件事写成一句话。写不成句子，它就不是模型检查的对象，去找别的办法更快。
  • 第二，只留下这句话牵涉到的变量。句子里没出现的东西不进模型。负载数据、超时数值、日志通常在这一步掉出去。留不留拿不准，就先去掉再跑。
  • 第三，先用有缺陷的设计跑一遍。看着反例出来，再换成修正后的设计。一上来就放修正后的设计，你无从知道那个通过意味着什么。
  • 第四，把规模一档一档往上抬。参与方从二到三、从三到四，看在哪一档检查开始跑不完。那个点就是这个模型所能言说范围的上限。
  • 第五，把结论连同条件一起写下来。在什么规模下、在哪些假设之下、用哪一组迁移检查的，写在与规格同一个位置。少了这三行，下一个人会把那个通过读成无条件的。

第四步在实务中教给人的东西最多。规模往上抬的过程中会显出哪个变量主导了状态数，那个变量能不能被抽象掉就成了下一个判断。检查跑不完并不是失败，而是关于「模型在这个位置要求什么」的信息。

最后整理一下。形式规格给的是确凿的缺陷发现，加上有条件的无缺陷。前者不挂免责，后者挂三条。而无论哪一边，代码是否遵循那份规格仍然是另一个命题。把这三样一起写下来，规格就成了设计文档里少有的、用处能留很久的东西。把行为写成句子这个想法本身能推到多远，在把行为写成规格这个想法的实质里从另一个角度整理过。

没能确认的部分

  • 触发本文那篇文章的检查器运行结果 — 原文载有规格文件、配置文件和运行命令，但没有载检查器吐出的反例输出，也没有探索到的状态数。本文也没有主张超出这个范围的内容。
  • 状态数与检查时间的具体数字 — 各模型规模下的状态数与耗时会随变量构成与运行环境整个数量级地变动，没有依据给出通用值，因此只写到增长的性质为止。
  • 证明工具一侧的实际要求 — 当需要超出有限模型的一般性证明时存在相应的证明系统，原文的叙述到此为止。该工具使用哪些后端证明器、需要多少人工，被放在本文范围之外。
  • 基于符号执行的替代检查器 — 有一类检查器不是逐个展开状态而是把状态当作约束来处理，其在状态爆炸方面的性质据称不同，但没有比对其成立条件，因此没有写进正文。
  • 产业采用案例的单篇文档 — 官方站点有一个汇总产业采用的页面，上面列着处理器缓存一致性协议、云服务、协调服务等条目。但其中多数是会议存档或演讲材料，没有逐条比对其主张，所以正文里没有写出机构名称和成果数字。
  • 轨迹校验工具的成熟度 — 把运行轨迹与规格对照的做法作为要求是清楚的，但哪些语言与运行时已经具备可用的工具，没有做过比对。正文只写到这种做法所要求的条件为止。
  • 模型初稿自动生成的实效 — 原文附带了一个展望，说规格的撰写成本也可能像测试初稿那样降下来。原文里没有支撑这个展望的实测数据，本文也没有把它当作展望来处理。
