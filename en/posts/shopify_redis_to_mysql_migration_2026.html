Why Shopify Migrated Inventory From Redis to MySQL 2026 - An Infrastructure Decision Deep Dive

Redis was faster, so why did Shopify move back to MySQL? The trade-off between speed and accuracy.

May 31, 2026 Tech & IT

Introduction: The Paradox of "Redis Is Faster, So Why MySQL?"

Almost every developer carries one proposition like muscle memory: "Redis is fast, relational databases are slow." As an in-memory key-value store, Redis returns responses dozens of times faster than disk-bound MySQL, so the moment traffic spikes, we reach for Redis almost reflexively. And yet Shopify, which runs one of the largest e-commerce infrastructures on the planet, moved in the opposite direction. It migrated the data for its core inventory system from Redis to MySQL.

When this news first surfaced, many developers asked the same question: "Why go toward the slower option when you have the faster one?" Buried inside that question is an assumption we have absorbed without examining it, the idea that "fast equals good." This article is an attempt to challenge that assumption head-on. The short version: Shopify's choice was not a regression but a redefinition of roles.

Inventory is a peculiar kind of data. A search result appearing 0.1 seconds late and the last unit in someone's cart vanishing at checkout, or being sold to two people at once, are problems of entirely different magnitudes. The former annoys a user and ends there; the latter cascades into refunds, inventory corrections, and a collapse of customer trust. Starting from Shopify's decision, this piece unpacks the essential difference between a cache and a database, and what it all means for the e-commerce world, from a developer's point of view.

The one-line summary. Shopify's decision is not "Redis is bad" but the realization that "inventory must be a source of truth, not a cache." Speed is handled separately by a cache layer, while accuracy is the database's responsibility. That layered separation is the whole point.

1. The Scale of Shopify's Inventory System - Why This Decision Matters

This decision is interesting precisely because Shopify is not a small startup. Millions of stores worldwide run on Shopify, and during peak seasons like Black Friday and Cyber Monday, hundreds of thousands of orders pour in per second. Thousands of shoppers pressing the buy button simultaneously over the last unit of the same hot product is a routine event.

At this scale, even a small design flaw is amplified into enormous cost. If there is 1 unit left but the system tells 2 customers "available," one of them ends up with a cancellation, a refund, and an apology. Multiply that by tens of thousands of incidents a day and the operational cost and reputational damage become astronomical. So at Shopify's scale, changing the data model of the inventory system is not a matter of technical taste; it is re-laying the foundation that supports the reliability of billions of dollars in transactions.

That is exactly why we should pay attention to this case. A company that has lived through massive traffic, while holding the fastest tool available, pulled that tool out of the seat reserved for core data. There is an expensive lesson here about "something more important than speed."

2. Why Redis Was Used for Inventory in the First Place

To be fair, there were good reasons Redis was used for inventory at all. It was by no means the wrong tool.

2.1 Overwhelming Speed

Redis keeps data in memory, so it never touches disk I/O. Both reads and writes respond in microseconds, a territory disk-based databases struggle to reach. For an operation as frequent as decrementing inventory, that speed is genuinely attractive.

2.2 Atomic Operations

Redis ships with atomic counter operations like DECR and INCRBY. Reducing a stock count by one can be handled with a single command, making concurrency control intuitive. Add distributed locks or Lua scripts and you can build even finer control.

2.3 A Simple Data Model

"Product ID to remaining quantity" is essentially a key-value structure, which maps almost perfectly onto Redis. No schema design, joins, or index agonizing; it just works. Early on, that simplicity surely boosted development velocity.

In short, from the view of "inventory equals a number that goes up and down quickly," Redis was nearly an ideal tool. The problem was that inventory is not only that.

3. The Five Limits of Redis (in the Inventory Context)

Leaving Redis's strengths intact, let us examine the limits that emerge in the specific context of inventory. These are not defects in Redis; they are the structural friction of "using a tool designed as a cache as a persistent store."

3.1 The Durability Problem

This is the most fundamental issue. Redis is an in-memory store, and memory is volatile. You can reinforce persistence with RDB snapshots or AOF logs, but both leave a window in which "data written after the last save" can be lost. If a server suddenly dies, the inventory decrements recorded in between can vanish entirely. For a cache, you just refill it; for inventory, that one record is revenue and a promise.

3.2 The Consistency Problem

When you replicate Redis across multiple nodes, replication between master and replica happens asynchronously. The moment a master is replaced due to failure, writes not yet replicated can be lost. For data like inventory, where a single discrepancy translates directly into an oversell, this asynchrony becomes a fatal weakness.

3.3 Memory Cost

Keeping all data in RAM means cost climbs steeply as data grows. Holding every variant and per-warehouse stock for millions of stores resident in memory makes cost efficiency deteriorate rapidly. A disk-based store keeps the same data far more cheaply.

3.4 The Absence of Complex Queries

Inventory is not just a number. You constantly need queries like "products below threshold in a specific warehouse," "stock change history over the past 24 hours," or "aggregated stock per variant." Because Redis is key-value, it does not natively support these joins, aggregations, and range queries well. In the end you patch them awkwardly in application code.

3.5 The Limits of Multi-Step Transactions

A real checkout requires "decrement inventory + create order + record payment" to succeed as one bundle or fail as one bundle. Redis's MULTI/EXEC groups commands, but it does not provide the rollback and isolation levels of a relational database. Cleanly undoing the work when one step fails midway is hard.

4. Why MySQL - The Strengths of a Relational Database

What fits precisely on the opposite side of those five limits is the ACID guarantee of a relational database. What MySQL (especially the InnoDB engine) offers is, ultimately, "the ability to handle data so it is never wrong."

4.1 Durability - If It Commits, It Survives

The D in ACID is the promise that once a transaction commits, it is preserved even if the server dies. InnoDB's redo log is written to disk first, so a committed inventory decrement is safely recovered even after a crash. This is the most fundamental line separating the cache's "data you can afford to lose" from the database's "data you must never lose."

4.2 Consistency - Transaction Isolation That Blocks Overselling

A relational database serializes concurrent decrements with row-level locks and transaction isolation levels. Pessimistic locking such as SELECT ... FOR UPDATE structurally prevents the situation where "two transactions grab the same last unit at once." It guarantees, at the database level, the very oversell that inventory systems fear most.

4.3 Atomicity - All or Nothing

Bundle inventory decrement, order creation, and payment recording into one transaction, and if any single step fails midway, the whole thing rolls back automatically. The ghost state of "stock dropped but no order was created" simply cannot occur by construction.

4.4 Rich Queries and Integrity Constraints

SQL expresses joins, aggregations, and range conditions freely. With foreign keys, CHECK constraints, and unique constraints, the database itself can enforce rules like "stock can never go negative." You no longer have to leave business rules to the application alone.

5. Five Technical Challenges of the Migration

Deciding that moving is correct and actually moving are entirely different problems. Swapping the core store of a giant live system is closer to changing an engine mid-flight.

  • Zero-downtime: An inventory system cannot stop even for a moment. You need a dual-write period running both Redis and MySQL, gradually shifting traffic over.
  • Data consistency: The Redis inventory snapshot at migration time and the MySQL initial values must match exactly. Since live decrements continue during the move, an unbroken sync mechanism to catch up changes is essential.
  • Performance guarantees: Slower responses must not hurt checkout conversion. You must verify in advance that MySQL can withstand peak traffic by combining indexing, connection-pool tuning, read replicas, and a front cache.
  • A rollback safety net: If the new system breaks, you must be able to revert to the old path instantly. For a period, keep both alive, making clear which is the source of truth while keeping the other as fallback.
  • Validation: Run a shadow comparison continuously reconciling inventory values across both systems, tracing the cause whenever a discrepancy appears. Only after passing this validation thoroughly do you close the old path.

6. The Performance Trade-off - Speed vs Accuracy

The crux of this case is, in the end, a trade-off. MySQL is slower than Redis on a single response. That is true. But for inventory, the real question is not "how fast" but "how rarely wrong."

Here we must break a common misconception. Moving to MySQL does not mean every read hits the disk. A realistic architecture is a layered structure where writes (decrements) are the responsibility of MySQL as the source of truth, while frequent reads (showing stock) are served by a Redis cache. In other words, Redis did not disappear; it returned to its own seat, the cache.

In inventory, a response one millisecond faster is a bragging point, but a single oversell is an incident. When accuracy breaks, speed loses its meaning.

So the balance point of the trade-off is "yield a little speed and definitely buy accuracy." And even that yielded speed can largely be reclaimed with a cache layer. It is not a losing trade at all.

8. Other Company Cases - The Cache and Persistent-Store Separation Pattern

Shopify's choice is not a lone outlier. Companies running large systems have generally arrived at a similar conclusion: layered separation patterns like cache-aside or write-through.

The typical setup looks like this. The truth of the data always lives in the relational database, and a Redis/Memcached cache sits in front of it to reduce read load. Writes hit the database first, then invalidate or update the cache. In this pattern, even if the entire cache is wiped out, not a single record is lost. Things just get briefly slower while the cache refills.

The lesson is clear. "A fast store" and "a trustworthy store" are different roles, and mature architectures separate them instead of dumping both onto one tool. Shopify's inventory migration reads as a case of reapplying this universal principle to the most sensitive domain of all: inventory.

9. Five Lessons for Developers

Here are the practical lessons I drew from this case.

  1. "Fast" is not a selection criterion; it is just one property. The nature of the data (can it be volatile, must it be correct) decides the tool first.
  2. The single source of truth must live in a durable store. A cache is a copy, not the original.
  3. Speed can be handled separately as a layer. Putting a cache in front of an accurate database is safer than cramming accuracy into a fast cache.
  4. Early simplicity becomes later debt. Inventory that key-value handled fine at first began demanding transactions and queries as scale grew. Assume the growth curve in advance.
  5. Migration is about validation more than technology. Do not move a core store without dual-write, shadow comparison, and a rollback safety net.

10. Applying This to E-Commerce - Implications for High-Concurrency Markets

This discussion does not stop at a global case. Many e-commerce markets are defined by orders concentrated in narrow time windows, with burst traffic from live commerce, time deals, and flash sales as a daily reality. Tens of thousands of people targeting the last unit of the same hot product at once is something major platforms experience every day.

In such an environment, relying on a cache alone for inventory exposes the oversell risk directly. The implications for e-commerce infrastructure are as follows.

  • Flash sales = extreme concurrency: Writes flood the same row in an instant. A design that serializes with database locking strategies and queuing (order waiting lines) is key.
  • Accurate display is not accurate decrement: Stock shown on screen should be fast via cache; the actual decrement must be accurate via a database transaction. You must recognize these two as separate.
  • Refund and correction costs are expensive: With high expectations for fast support and sensitivity to platform reputation, the intangible cost of a single oversell is large. There is ample justification to invest in accuracy.
  • Tools for small sellers follow the same principle: If you build your own shop, resist the temptation to manage inventory with a Redis counter alone, and make the database the source of truth from the start.

11. The Risk - The Illusion That "Faster Is Always Better"

The bigger risk this case exposes is the psychology of technology choices. We are easily swayed by benchmark numbers, sentences like "X is N times faster than Y." But benchmarks usually do not measure the condition "this data must never be wrong."

Speed-first thinking is dangerous because its bill arrives later, and at the most inconvenient moment. Data loss erupts on the busiest sale day, the instant a node dies in a failure, in the split second replication lags behind. It looks fine most of the time and then collapses exactly when you can least afford it.

Before being seduced by "fast," the question to ask is this: if this data disappears or is wrong, who loses what, and how much?

Mature engineering is not about flaunting fast tools, but about honestly weighing the failure cost of each piece of data and placing tools accordingly. Shopify's choice was the result of exactly that honest calculation.

12. Conclusion + Three Things You Can Apply Today

Shopify's decision to move inventory from Redis to MySQL is not a story of "Redis was wrong." It is a reaffirmation of a fact that perhaps should have been obvious from the start: "inventory is a source of truth, not a cache." Speed was a yielding variable, but accuracy was a non-negotiable constant, and the decision made clear what to protect when the two collide.

Let me close with three things you can apply today.

  1. Classify your data by failure cost. What can be lost goes to the cache (Redis); what must never be wrong goes to the database (MySQL/PostgreSQL). This one line settles most storage decisions.
  2. Make a transactional database the source of truth for inventory, payments, and balances. If you need speed, add a cache in front, but pin the seat of truth to the database.
  3. When moving a store, design dual-write, shadow comparison, and rollback first. Remember that the success of a migration is decided by the validation system, not the new technology.

The next time "Redis is faster, so why?" comes to mind, go one level deeper. The real question is not speed but "what collapses if this data is wrong?"

Frequently Asked Questions (FAQ)

Q1. Why did Shopify move from Redis to MySQL?

Inventory counts must never be wrong, but Redis is an in-memory cache that can lose data and drift out of consistency during failures. Prioritizing durability and accuracy over speed, Shopify moved the source of truth to MySQL, which guarantees ACID and on-disk persistence. Redis was repositioned as a cache, not discarded.

Q2. Is Redis bad for inventory systems?

Redis is not bad; it plays a different role. As a source of truth requiring permanence and zero error it is risky, but for read caches, sessions, and queues where speed is key, it remains excellent.

Q3. When should I use MySQL over Redis?

Use MySQL when data must not be lost, must be correct, and needs multi-step transactions and complex queries. Use Redis when data can be volatile and simple key-value lookups with extreme low latency are the priority.

Q4. Does MySQL handle high traffic like Redis?

With indexing, connection pools, read replicas, and a front Redis cache, it handles it well. The key is a layered design: accuracy-critical writes to MySQL, frequent reads to the cache.

Q5. What is the difference between a cache and a database?

A database is the source of truth, responsible for permanence, consistency, and transactions; a cache is a temporary copy for fast reproduction. An empty cache only slows things down, but a wrong database breaks the business.
