계기 — 엣지 분산 인프라에서 브로커 없는 이벤트 스트리밍의 필요성

전통적인 원격 프로시저 호출(RPC) 기반의 마이크로서비스 아키텍처는 생산자(Producer)와 소비자(Consumer)가 시간과 처리 용량 측면에서 엄격히 결합되어 있다는 구조적 난제를 안고 있다. 생산자가 소비자의 처리 속도를 초과하는 트래픽을 순간적으로 유입시키거나 다운스트림 서비스에 장애가 발생하면 이벤트 유실이 발생할 수밖에 없다. 이러한 결합도를 낮추기 위해 업계에서는 일반적으로 Apache Kafka나 AWS Kinesis와 같은 분산 로그 기반의 메시지 브로커를 도입하여 버퍼링과 비동기 처리를 구현해 왔다.

그러나 전 세계 335개 이상의 도시에서 수많은 엣지 서버를 운영하는 Cloudflare의 인프라 환경에서는 전통적인 Kafka 클러스터를 배포하고 유지하는 방식이 적합하지 않다. 엣지 환경의 머신들은 비교적 작은 연산 슬라이스로 나뉘어 있고 생명주기가 상대적으로 짧으며 노드 간 통신이 공용 인터넷을 경유하는 경우가 빈번하기 때문이다. Cloudflare 내부에서 개발된 스트림 처리 엔진(Arroyo 기반의 Basin Pipelines) 역시 엣지에서 수집되는 대규모 이벤트를 안정적으로 버퍼링할 고내구성 수집 계층이 필요했으나, 기존 분산 시스템을 그대로 엣지에 얹기는 어려웠다.

Cloudflare가 2026년 10월 공개 베타로 발표한 K2는 이러한 제약조건을 극복하기 위해 설계된 완전 서버리스 이벤트 스트리밍 원시(Primitive) 서비스다. 전용 브로커 노드 클러스터를 사이징하거나 파티션을 사전 할당할 필요 없이, 이미 전역에 배포되어 검증된 R2 오브젝트 스토리지를 영속성 계층으로 직접 활용한다. 이를 통해 인프라 운영 복잡성을 제거하면서도 생산자와 소비자를 엣지에서 강력하게 분리하는 구조를 확립했다.

R2 객체 스토리지 위의 순서 로그 — 추가(Append) 없는 스토리지에서 오프셋을 구현한 원리

이벤트 스트리밍 시스템의 본질은 시간에 따라 정렬된 단조 증가 로그(Ordered Log)를 안전하게 기록하고 보존하는 데 있다. Kafka와 같은 전통적 시스템은 파일 시스템 레벨에서 순차 쓰기(Sequential Append)를 활용하여 디스크 성능을 극대화한다. 그러나 K2의 기반 스토리지인 R2를 비롯한 현대적 오브젝트 스토리지는 불변 객체(Immutable Object)를 통째로 쓰고 읽는 인터페이스만 제공할 뿐, 기존 객체의 끝에 데이터를 덧붙이는 append 연산을 지원하지 않는다.

Cloudflare 엔지니어링 팀은 이 근본적인 제약을 해결하기 위해 엣지 런타임의 인메모리 버퍼링과 R2의 원자적 연산을 결합하는 설계를 채택했다. 그 구체적인 메커니즘은 다음과 같다.

  • 인메모리 버퍼 누적: 엣지 노드로 인입되는 개별 이벤트 쓰기를 즉시 스토리지에 쓰지 않고 메모리상에 잠시 모아둔다.
  • 세그먼트(Segment) 일괄 기록: 네트워크 왕복 및 트랜잭션 비용을 정당화할 수 있는 적정 크기의 배치 단위로 이벤트를 묶어 단일 세그먼트 파일로 R2에 쓴다.
  • R2 원자적 연산 기반 오프셋 제어: 별도의 분산 코디네이션 서비스(ZooKeeper나 Raft 합의 엔진 등)를 두지 않고, R2의 강력한 일관성(Strong Consistency)과 원자적 연산(Atomic Operations)을 활용하여 단조 증가 오프셋(Strictly Incrementing Offsets)과 엄격한 순서를 확립한다.
  • 바이트 기반 불가지론적 데이터 모델: K2 내부에서 이벤트는 임의의 바이트 열로 취급되므로 JSON, Protobuf, Avro 등 개발자가 지정한 임의의 직렬화 형식을 자유롭게 사용할 수 있다.

복제와 합의(Consensus)라는 분산 시스템의 가장 까다로운 책임을 11-nines(99.999999999%) 내구성을 보장하는 R2 스토리지 계층으로 위임함으로써, K2 애플리케이션 계층은 브로커 상태 관리의 부담에서 벗어나 연산과 스토리지를 독립적으로 수평 확장할 수 있게 되었다.

지연시간과 배치의 트레이드오프 — p99 1초 지연이 발생하는 이유

오브젝트 스토리지 위에 스트리밍 엔진을 올린 아키텍처는 탁월한 내구성과 저렴한 대규모 보관 비용을 제공하지만, 필연적으로 지연시간(Latency) 측면의 명확한 트레이드오프를 수반한다. 로컬 NVMe SSD에 직접 순차 쓰기를 수행하는 전용 브로커 시스템은 수 밀리초(ms) 단위의 쓰기 응답성을 달성할 수 있다. 반면 K2는 두 단계의 물리적 대기 과정을 거친다.

첫째, 엣지 서비스 메모리에서 세그먼트를 형성하기 위해 짧은 시간 동안 이벤트를 누적해야 하는 배치 대기 시간이 존재한다. 둘째, 누적된 세그먼트를 분산 오브젝트 스토리지로 네트워크를 통해 전송하고 커밋 확인을 수신하는 스토리지 I/O 시간이 소요된다. Cloudflare 공식 블로그에 따르면 초기 릴리스 기준 K2의 생산 지연시간(Produce Latency)은 99번째 백분위수(p99) 기준 약 1초(about 1 second)에 달한다.

이러한 1초의 지연시간 특성은 K2의 실무 적용 범위를 규정짓는 결정적인 잣대가 된다.

  • 적합한 워크로드: 사용자 행동 분석 로그, 대규모 원격 측정(Telemetry) 지표 수집, 과금 트랜잭션의 감사 추적 로그, 배치 ETL 파이프라인 수집 계층 등 초 단위 버퍼링이 허용되는 시스템.
  • 부적합한 워크로드: 금융권 고빈도 매매(HFT), 실시간 게임 세션 동기화, 사용자 대화형 UI에 즉각 응답해야 하는 초저지연 RPC 대체 용도.
  • 처리량과 효율성의 교환: 개별 메시지마다 즉각적인 fsync를 수행하지 않고 배치로 묶음으로써, 엣지 전체에서 유입되는 방대한 대역폭을 저렴한 스토리지 트랜잭션으로 흡수한다.
  • 재시도 모델의 거칠기: 메시지 개별 단위의 세분화된 재시도 대신 배치 단위로 생산 및 소비가 이루어지므로, 에러 핸들링 역시 배치 수준에서 다뤄져야 한다.

소비와 리스 모델 — 5분 리스, ack·nack·extend 및 작업 분할

생산된 이벤트를 읽어가는 소비 계층은 풀(Pull) 기반 아키텍처를 채택하고 있다. 소비자는 HTTP API 또는 향후 지원될 바인딩을 통해 특정 구독(Subscription)에 폴링 요청을 전송하여 메시지 배치를 가져온다. 이때 K2는 메시지 유실을 방지하고 분산 소비자 환경에서 안정적인 병렬 처리를 지원하기 위해 「5분 리스(Lease)」 메커니즘을 적용한다.

클라이언트가 consume 엔드포인트를 호출하여 이벤트 배치를 수신하면, 해당 배치에는 5분간의 독점 처리 권한(Lease)이 부여된다. 소비자는 5분의 리스 기간 내에 비즈니스 로직을 처리한 뒤 다음 세 가지 중 하나의 결정을 내려야 한다.

  • ack (승인): 배치가 성공적으로 처리되었음을 브로커에 통보한다. 해당 배치는 처리 완료로 마킹되며 이후 어떤 소비자에게도 다시 전달되지 않는다.
  • nack (부정 승인): 다운스트림 처리 실패 등으로 인해 배치를 정상 처리하지 못했음을 즉시 알린다. 리스는 즉시 해제되며 해당 배치는 대기열로 복귀하여 재전달 대상이 된다.
  • extend (리스 연장): 대용량 이미지 변환이나 복잡한 AI 추론 등으로 인해 5분 이상의 처리 시간이 소요될 경우, 리스 만료 시점을 연장하여 타 소비자에 의한 중복 처리를 방지한다.
  • 타임아웃 자동 회수: 소비자가 장애로 인해 5분 동안 아무런 신호도 보내지 못하면, 리스는 자동으로 만료되어 타 소비자에게 배치 재전달이 허용된다.
  • 전달 의미론: 최소 한 번(At-least-once) 전달을 보장한다. 처리 도중 장애가 발생하거나 리스가 만료되면 동일 배치가 다시 전달될 수 있으므로 소비자는 멱등성(Idempotency)을 갖추어야 한다.

K2는 이 리스 모델을 기반으로 두 가지 소비 패턴을 제공한다. 첫째는 여러 워커 인스턴스가 단일 구독을 공유하여 작업을 분배받는 「작업 분할(Work Distribution / Read Parallelism)」 방식이며, 둘째는 각 워커 그룹이 독립된 구독을 생성하여 동일한 이벤트 스트림 전체를 복제 수신하는 「팬아웃(Pub/Sub)」 방식이다.

비동기 프리미티브 비교 — K2 Streams·Queues·Basin Pipelines의 경계

Cloudflare 개발자 플랫폼에는 비동기 메시징 및 데이터 처리를 담당하는 여러 프리미티브가 공존한다. 실무 엔지니어링 관점에서는 각 도구의 성격을 명확히 구분하여 적절한 위치에 배치하는 것이 필수적이다. 공식 문서가 명시하는 세 서비스의 기술적 경계는 아래와 같다.

  • Cloudflare Queues: 개별 작업 항목(Individual work item)의 비동기 실행 추적에 특화되어 있다. 특정 작업 단위의 재시도, 지연(Delay), 실패 시 데드레터 큐(DLQ) 격리 등 정교한 작업 제어와 밀리초 단위 저지연 전달을 제공한다.
  • Cloudflare K2 Streams: 대규모 데이터 이동과 장기 보존, 다중 소비자 팬아웃을 목표로 한다. 배치 단위의 효율적 처리를 위해 개별 메시지 단위 재시도 제어를 희생하며 상대적으로 높은 쓰기 지연을 갖는다.
  • Basin Pipelines: R2 또는 Apache Iceberg 기반 데이터 카탈로그로의 정형 데이터 수집 및 변환에 특화된 서버리스 파이프라인이다. 최종 목적지가 스토리지나 분석 테이블인 경우에 권장된다.
  • 선택의 기준: 임의의 목적지로 전송하거나 커스텀 비즈니스 로직(Workers, 외부 API 등)에서 직접 스트림을 소비해야 하는 경우에는 Basin Pipelines 대신 K2 Streams가 사용된다.

베타 한도와 정식 과금 모델 — 10GB·30MB/s의 의미와 비용 구조

K2는 현재 Workers Paid 요금제 구독자를 대상으로 공개 베타(Public Beta)로 제공되고 있다. 베타 기간 중에는 K2 사용에 따른 비용이 청구되지 않으며 무료로 기능을 검증할 수 있다. 다만 안정적인 멀티테넌시 운영을 위해 공식 문서에는 다음과 같은 엄격한 계정별 초기 한도가 명시되어 있다.

  • 스트림당 저장 용량 한도: 스트림당 최대 10GB(Maximum of 10GB storage used).
  • 스트림당 생산 대역폭 한도: 초당 최대 30MB(30 MB/s produce per stream).
  • 기본 보관 수명: 스트림 생성 시 기본 설정되는 보존 기간은 7일(604,800초).
  • 한도 증설 경로: 공식 블로그에 제공된 신청 양식을 통해 엔터프라이즈 또는 고용량 검증을 위한 한도 상향 요청 가능.
  • 과금 개시 시점: 베타 기간 종료 후 정식 상용화 시점부터 사용량 기반 종량제 요금 청구 개시.
과금 항목예상 단가비용 발생 의미공개 베타 기간 정책
Data Produced (생산 데이터)$0.04 / GB생산자가 K2 스트림으로 인입시키는 데이터 용량Workers Paid 가입자 대상 무료
Data Consumed (소비 데이터)$0.04 / GB소비자가 구독을 통해 스트림에서 읽어가는 데이터 용량Workers Paid 가입자 대상 무료
Data Retained (보관 데이터)$0.02 / GB / 월스트림 내에 보존 기간 동안 유지되는 데이터 용량스트림당 10GB 한도 내 무료

생산과 소비에 각각 GB당 0.04달러가 책정되고 저장에 월 GB당 0.02달러가 부과되는 구조는, 별도의 전용 가상 머신이나 브로커 인스턴스 비용 없이 순수 데이터 트래픽에 비례하여 비용을 지불하는 전형적인 서버리스 경제 모델을 보여준다.

향후 로드맵과 실무 검증 절차 — 파티션 키와 Kafka 호환 계획

공개 베타 단계의 K2는 단일 스트림 중심의 엄격한 순서 보장을 제공하지만, 기존 엔터프라이즈 스트리밍 솔루션을 완전히 대체하기에는 아직 기능적 공백이 존재한다. Cloudflare 공식 블로그는 향후 몇 달간에 걸쳐 순차 배포될 K2의 핵심 로드맵 항목들을 다음과 같이 제시했다.

  • 쓰기 병렬성 확대: 초당 수 기가바이트(multi-GB/s) 수준을 처리할 수 있는 고대역폭 스트림 지원.
  • 메시지 키 기반 파티션 순서 보장: 특정 엔터티 키별로 순서를 분할 보장하는 기능 도입.
  • 푸시 기반 Worker 컨슈머: 폴링 방식 외에 이벤트 도착 시 Worker 함수를 즉각 구동하는 푸시 트리거 지원.
  • 저지연 Express 티어: 쓰기 대기 시간을 대폭 단축하여 엔드투엔드 지연을 줄이는 전용 고속 티어 추가.
  • Apache Kafka 클라이언트 드롭인 지원: 기존 Kafka SDK나 생태계 도구가 K2를 네이티브 브로커처럼 호출할 수 있는 프로토콜 호환 계층 제공.

실무 엔지니어링 팀은 현재의 베타 한도(10GB, 30MB/s) 범위 내에서 사내 원격 측정 지표 수집이나 보조 분석 로그 파이프라인에 K2를 시범 연동하여 1초 쓰기 지연의 수용 가능성을 먼저 검증하고, 향후 Kafka 드롭인 호환성 발표 시점에 맞춰 운영 시스템으로의 확대 여부를 결정하는 것이 합리적이다.

확인하지 못한 것

  • Apache Kafka 클라이언트 드롭인 호환성 지원의 구체적인 제공 방식(Kafka 와이어 프로토콜 수준 에뮬레이션인지, 전용 래퍼 라이브러리인지 여부).
  • Express 티어에서 목표로 하는 구체적인 쓰기 지연시간(밀리초 수치) 및 Express 티어 전용 과금 단가.
  • 단일 계정 내에서 생성 가능한 K2 스트림의 최대 개수 상한선.
  • 메시지 키(Message Key) 기반 파티셔닝 도입 시 파티션 리밸런싱이 클라우드플레어 엣지에서 어떻게 분산 처리되는지에 관한 구체적 합의 알고리즘.
  • 공개 베타 종료 및 정식 과금 개시가 이루어지는 구체적인 상용화 일정.
