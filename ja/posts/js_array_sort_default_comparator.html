はじめに - ソートしたのに10が9より前に来る

JavaScriptで数値の配列に比較関数なしでsort()を呼ぶと、数値は数の大きさではなく別の基準で並ぶ。[1, 10, 9, 2]が[1, 10, 2, 9]になるのが最もよく知られた形である。この動作はバグではなく定義であり、定義を知れば、比較関数をどう書くか、どの値がどこへ行くか、誤って書いた比較関数がどんな結果を出すかが一本の線でつながる。

この記事の軸は、sortの既定の比較関数と、比較関数の書き方である。韓国語やロケールがソート順を変える問題は、韓国語のソートが期待と違う理由がツールごとに詳しく扱っており、配列メソッド全般とsortの数値の落とし穴の一行は、JavaScript基本構文にある。ここでは、比較関数が受け取る値、返すべき値、壊す入力を、出力で一つずつ確かめる。

扱う問いは次のとおりである。

  • 既定の比較関数は数値をどんな基準で比べるか。
  • 文字列比較の基準であるUTF-16コードユニット順は、コードポイント順とどう違うか。
  • undefined・空きスロット・null・NaNはどこへ行き、比較関数はそれらを受け取るか。
  • 比較関数は何を返すべきで、ブール値や不整合な比較関数はどんな結果を出すか。
  • 安定ソートは仕様が保証しているか、どの比較関数がそれを壊すか。
  • toSorted・localeCompare・Intl.Collatorは、どの場面でsortと手書きの比較関数の代わりになるか。

既定の比較関数は文字列比較である

MDNのArray.prototype.sortのドキュメントは、既定のソート順を次のように定義する。既定のソート順は昇順で、要素を文字列に変換し、そのUTF-16コードユニット値の並びを比較する方式に基づく。比較関数がなければ、undefinedでないすべての要素が文字列に変換されてコードユニット順で比較されるという文もある。下のコードは、この定義が[1, 10, 9, 2]にどう現れるかを、同じ配列を文字列にしたものや比較関数を与えたものと並べて出力する。

console.log('node ' + process.version);
                    const a = [1, 10, 9, 2];
                    console.log(a.sort());
                    console.log([1, 10, 9, 2].map(String));
                    console.log(['1', '10', '9', '2'].sort());
                    console.log('10' < '9', 10 < 9);
                    console.log([1, 10, 9, 2].sort((x, y) => x - y));
node v22.16.0
                    [ 1, 10, 2, 9 ]
                    [ '1', '10', '9', '2' ]
                    [ '1', '10', '2', '9' ]
                    true false
                    [ 1, 2, 9, 10 ]

最初のソート結果は[1, 10, 2, 9]である。同じ配列を文字列にすると'1', '10', '9', '2'で、文字列配列をソートした結果'1', '10', '2', '9'は、数値配列の結果と同じ順序である。文字列'10'は、先頭の文字'1'(0x31)が'9'(0x39)より小さいので'9'より前に来る。最後から2行目の比較がこれを直接示している。文字列の比較'10' < '9'はtrue、数値の比較10 < 9はfalseである。比較関数(x, y) => x - yを与えると[1, 2, 9, 10]になる。

  • 既定のソートの対象は値ではなく、値の文字列表現である。数値の10と9は比べられず、'10'と'9'が比べられる。
  • 配列が1桁の数だけなら、文字列の順序と数値の順序がたまたま一致してテストを通る。2桁の数が混ざった瞬間にずれる。
  • 比較関数(x, y) => x - yは、値そのものを引き算して符号で順序を知らせる。定義を変えるのではなく、比較の基準を文字列から数値に変えるのである。

文字列比較はUTF-16コードユニット順である

文字列を比べるとは、定義上、コードユニット単位の比較である。ほとんどの文字はコードユニット1つだが、U+FFFFを超える文字(絵文字など)はサロゲートペアでコードユニット2つになる。この違いが、既定のソートとコードポイント順が異なる結果を出す場合を生む。下のコードは、絵文字U+1F600と全角文字U+FF21を通常の文字に混ぜ、既定のソートとコードポイント基準の比較関数の結果を比べる。

const words = ['\u{1F600}', 'Ａ', 'z', 'Z', 'a'];
                    const hex = w => 'U+' + w.codePointAt(0).toString(16).toUpperCase();
                    console.log('default      :', [...words].sort().map(hex).join(' '));
                    console.log('code point   :', [...words].sort((x, y) => x.codePointAt(0) - y.codePointAt(0)).map(hex).join(' '));
                    console.log('first unit of U+1F600 = 0x' + words[0].charCodeAt(0).toString(16).toUpperCase() + ', of U+FF21 = 0x' + words[1].charCodeAt(0).toString(16).toUpperCase());
default      : U+5A U+61 U+7A U+1F600 U+FF21
                    code point   : U+5A U+61 U+7A U+FF21 U+1F600
                    first unit of U+1F600 = 0xD83D, of U+FF21 = 0xFF21

既定のソートはZ, a, z, U+1F600, U+FF21の順で、コードポイント順はZ, a, z, U+FF21, U+1F600である。絵文字の最初のコードユニットは0xD83Dで、全角Aのコードユニットは0xFF21なので、コードユニット順では絵文字が先に来る。コードポイントでは0xFF21が0x1F600より小さいため、逆になる。大文字Z(0x5A)が小文字a(0x61)より前に来るのも、同じ基準から出る。通常の英数字だけを扱う場合、この差は見えないので、絵文字や補助平面の文字が入ったときに、ソート順が直感とずれることが起きる。

undefined・空きスロット・null・NaNはどこへ行くか

MDNは、すべてのundefined要素は配列の末尾にソートされると記し、空きスロットについては、sort()は空きスロットを保持し、元の配列が疎配列なら空きスロットは配列の末尾へ移され、すべてのundefinedより常に後ろに来ると記す。この2つの文が比較関数とどう出会うかは、比較関数が受け取った引数を記録すると見える。

const calls = [];
                    const r = [3, undefined, 1, , 2].sort((x, y) => { calls.push(x + ',' + y); return x - y; });
                    console.log(r, 'length', r.length, '| index 4 in result:', 4 in r);
                    console.log('comparator calls:', calls.join(' | '));
                    console.log('any call saw undefined:', calls.some(c => c.includes('undefined')));
                    console.log([3, undefined, 'a', null, NaN, 1].sort());
                    console.log([3, undefined, 'a', null, NaN, 1].map(String));
                    console.log([3, undefined, 1].sort((x, y) => y - x));
                    console.log(['z', undefined, 'a'].sort(), '| String(undefined) =', String(undefined));
[ 1, 2, 3, undefined, <1 empty item> ] length 5 | index 4 in result: false
                    comparator calls: 1,3 | 2,1 | 2,3 | 2,1
                    any call saw undefined: false
                    [ 1, 3, NaN, 'a', null, undefined ]
                    [ '3', 'undefined', 'a', 'null', 'NaN', '1' ]
                    [ 3, 1, undefined ]
                    [ 'a', 'z', undefined ] | String(undefined) = undefined
  • 1行目は[1, 2, 3, undefined, 空きスロット]である。長さは5のままで、インデックス4は空きスロットとして残った。undefinedが先、空きスロットが最後というMDNの文と同じである。
  • 比較関数が記録した呼び出しは数値のペアだけで、undefinedが引数に入った呼び出しはない。比較関数はundefinedと空きスロットを受け取らない。
  • 降順の比較関数(x, y) => y - xでも、undefinedは末尾に残った。比較関数の符号でundefinedの位置は変えられない。
  • [z, undefined, a]の既定のソートはa, z, undefinedである。String(undefined)は文字列undefinedで、zより小さい文字列なのに末尾に置かれたので、undefinedは文字列として比べられず、別の規則で最後へ行く。
  • nullとNaNはundefinedと違い、文字列nullとNaNに変換され、他の文字列の間で順序が決まる。既定のソート結果では、NaNは3の後でaの前、nullはaの後である。

比較関数は負・0・正を返す関数である

MDNは、比較関数が数値を返すべきだと記す。負はaがbより前、正はaがbより後、0またはNaNは両者が等しいという意味である。より形式的には、比較関数が純粋で、同じペアに同じ結果を返し、反射的(compareFn(a, a) === 0)で、反対称的(compareFn(a, b)とcompareFn(b, a)がともに0か、互いに逆の符号)で、推移的であるべきだと記す。下のコードは、正しい比較関数、ブール値を返す比較関数、定数を返す比較関数を同じ配列に適用し、千個の擬似乱数の配列でソートができたかを数える。

const nums = [10, 9, 1, 100, 2];
                    console.log('a - b       ', nums.slice().sort((x, y) => x - y));
                    console.log('b - a       ', nums.slice().sort((x, y) => y - x));
                    console.log('a > b       ', nums.slice().sort((x, y) => x > y));
                    console.log('a < b       ', nums.slice().sort((x, y) => x < y));
                    console.log('() => 1     ', nums.slice().sort(() => 1));
                    console.log('() => -1    ', nums.slice().sort(() => -1));
                    console.log('() => 0     ', nums.slice().sort(() => 0));
                    console.log('default     ', nums.slice().sort());

                    console.log('1000 numbers, adjacent descents after sort:');
                    console.log('  a - b  ', inversions(big.slice().sort((x, y) => x - y)));
                    console.log('  a > b  ', inversions(big.slice().sort((x, y) => x > y)));

ブール値を返すa > bは、5個の入力では何も変えず、千個の入力では下りが496か所も残った。この環境でNumber(true)は1、Number(false)は0である。ブール値を返す比較関数が返した値は0か1だった。この比較関数は同じペアでa, bに1、b, aに0を返し、MDNの反対称性に違反する。MDNは、実装によって動作が異なりうるため、5つの条件を守って比較関数を整えるよう勧める。このNode.jsでのブール値の結果はこのエンジンの値で、他のエンジンでも同じとは断定しない。

a - bが壊れる入力 - キーの欠落・文字列・BigInt

比較関数a - bは、数値同士でのみ正しい符号を出す。値がなかったり数値でなかったりする場合は引き算がNaNになり、MDNは、比較関数が返したNaNは0と同じく等しいという意味だと書く。MDNはまた、比較関数が一貫した比較結果を返さなければならないと規定する。次のコードは、キーのないオブジェクト、文字列、BigIntでa - bが出す結果を示す。

const rows = [{ p: 4 }, {}, { p: 3 }, { p: 2 }, { p: 1 }];
                    console.log(rows.slice().sort((x, y) => x.p - y.p).map(r => ('p' in r ? r.p : 'none')));
                    console.log(undefined - 1, Number.isNaN(undefined - 1));
                    console.log(['b', 'c', 'a'].sort((x, y) => x - y));
                    console.log(['b', 'c', 'a'].sort((x, y) => (x < y ? -1 : x > y ? 1 : 0)));
                    try {
                      console.log([3n, 1n, 2n].sort((x, y) => x - y));
                    } catch (e) {
                      console.log(e.constructor.name + ': ' + e.message);
                    }
                    console.log([3n, 1n, 2n].sort((x, y) => (x < y ? -1 : x > y ? 1 : 0)));

                    [ 'b', 'c', 'a' ]

                    [ 1n, 2n, 3n ]
  • pキーのないオブジェクトが混ざると、この入力での出力は[4, none, 1, 2, 3]である。上のMDNの文と出力を並べて置いたもので、両者の因果はこの出力では切り分けない。例外も警告もない。
  • undefined - 1はNaNである。2行目のNaN trueがその証拠で、MDNは比較関数の戻り値のNaNを等しいという意味だと書く。
  • 文字列[b, c, a]にa - bを使うと、順序は[b, c, a]のままである。b - cもNaNだからである。文字列にはa < b ? -1 : a > b ? 1 : 0が必要である。
  • BigIntではa - bがBigIntを返し、sortがそれを数値に変換できずTypeError(Cannot convert a BigInt value to a number)になる。このケースだけは黙って間違えず、すぐに表に出る。

安定ソートと同点の扱い

MDNは、バージョン10(ECMAScript 2019)から仕様がArray.prototype.sortを安定ソートと定めていると記す。安定ソートとは、比較関数が等しいと判定した要素が入力順を保つ性質である。下のコードは、キーが0〜4のオブジェクト1000個で、比較関数ごとに、ソートができたか、同点の入力順が保たれたかを調べる。最後の行は、補助キーで先にソートし、主キーで再度ソートする2段階のソートである。

const make = () => Array.from({ length: 1000 }, (_, i) => ({ k: (i * 7919) % 5, i }));
                    const isStable = arr => arr.every((v, j) => j === 0 || arr[j - 1].k !== v.k || arr[j - 1].i < v.i);
                    const sorted = arr => arr.every((v, j) => j === 0 || arr[j - 1].k <= v.k);
                    const good = make().sort((x, y) => x.k - y.k);
                    console.log('k-only comparator : sorted', sorted(good), '| ties keep input order', isStable(good));
                    const tie1 = make().sort((x, y) => (x.k < y.k ? -1 : 1));
                    console.log('tie returns 1     : sorted', sorted(tie1), '| ties keep input order', isStable(tie1));
                    const tie2 = make().sort((x, y) => (x.k > y.k ? 1 : -1));
                    console.log('tie returns -1    : sorted', sorted(tie2), '| ties keep input order', isStable(tie2));
                    const two = make().sort((x, y) => x.i - y.i).sort((x, y) => x.k - y.k);
                    console.log('two passes        : sorted', sorted(two), '| ties keep input order', isStable(two));
k-only comparator : sorted true | ties keep input order true
                    tie returns 1     : sorted true | ties keep input order true
                    tie returns -1    : sorted true | ties keep input order false
                    two passes        : sorted true | ties keep input order true
  • 同点で0を返す正常な比較関数(x.k - y.k)は、ソートができ、同点の入力順も保たれた。1000個の規模の入力で得た結果である。
  • 同点で-1を返す比較関数は、この入力でソートはできたが、同点の入力順は保たれなかった(出力のfalse)。同じペアでどちらの順序でも-1を返すので、MDNが挙げる反対称性の条件を満たさない。結果がその違反によるものかは、この実験では切り分けられない。次の項目の同点で1を返す比較関数も反射性の条件を満たさないが、順序は保たれた。
  • 同点で1を返す比較関数は、このNode.jsでは同点の順序が保たれた。同じ反射性違反なのに結果が異なった。この差がエンジンの引数の渡し方によるものかは、この出力では判別できず、保証としては読まない。
  • 最終行の2回ソートが示すのは、この入力で結果が整列し、同点の順序も保たれた(どちらもtrue)ということだけである。入力がすでにi順なので最初のソートは何も変えず、この行は安定性の証拠には使わない。安定性を確認した実験は、前の1000個の入力の実験である。

sortは元を変更しtoSortedはコピーを返す

MDNは、sort()が配列をその場でソートして同じ配列への参照を返すと記し、元を変更せずにソートするにはtoSorted()を使うよう記す。このNode.jsで2つのメソッドの戻り値の関係を出力で確かめたコードである。

const a = [3, 1, 2];
                    const b = a.sort();
                    console.log('sort():     same array', b === a, a);
                    const c = [3, 1, 2];
                    const d = c.toSorted();
                    console.log('toSorted(): same array', d === c, 'original', c, 'result', d);
                    console.log(typeof Array.prototype.toSorted);
sort():     same array true [ 1, 2, 3 ]
                    toSorted(): same array false original [ 3, 1, 2 ] result [ 1, 2, 3 ]
                    function

sort()の戻り値は元と同じ配列(true)で、元は[1, 2, 3]に変わった。toSorted()の戻り値は元と異なる配列(false)で、元は[3, 1, 2]のまま、結果が[1, 2, 3]である。最後の行は、このNode.jsでArray.prototype.toSortedが関数であることの確認である。ソート結果を共有状態(状態管理ライブラリの不変配列、すでに画面に描画された配列)に書く場面では、コピーを返す方が意図しない変更を防ぐ。比較関数に関する規則は両メソッドで同じである。

数値と文字列が混ざったとき

実際のデータには、数値と数字の形の文字列が混ざって入ってくることがある。既定のソートはすべて文字列として比べ、a - bは数値に変換できない値でNaNになる。型ごとの順位を先に比べる比較関数を立てて、結果を並べた。最後の行は、数字の形の文字列だけの配列にa - bを使った結果である。

const m = [10, '9', 1, 'a', 2, 'B'];
                    console.log('default      ', m.slice().sort());
                    console.log('a - b        ', m.slice().sort((x, y) => x - y));
                    const rank = v => (typeof v === 'number' ? 0 : 1);
                    const mixedCmp = (x, y) => rank(x) !== rank(y) ? rank(x) - rank(y)
                      : (x < y ? -1 : x > y ? 1 : 0);
                    console.log('typed cmp    ', m.slice().sort(mixedCmp));
                    console.log('numeric strs ', ['10', '9', '1'].sort((x, y) => x - y));
default       [ 1, 10, 2, '9', 'B', 'a' ]
                    a - b         [ 1, 2, '9', 10, 'a', 'B' ]
                    typed cmp     [ 1, 2, 10, '9', 'B', 'a' ]
                    numeric strs  [ '1', '9', '10' ]
  • 既定のソートは1, 10, 2, 9, B, aである。数値の10が数値の2より前に来て、数値の1の次に置かれる文字列順が続く。
  • a - bは数値同士はソートするが、文字列'9'が数値の間(2と10の間)に入り、'a'と'B'は入力順のまま末尾に残る。数値に変換できない値が混ざると、結果は部分的にしかソートされない。
  • 型の順位を使う比較関数は1, 2, 10, 9, B, aとなり、数値が先に数値順で、文字列がその後にコードユニット順で並ぶ。混在入力の規則を比較関数に明示した結果である。
  • 数字の形の文字列だけなら、a - bは文字列を数値に変換して引くので、'1', '9', '10'とソートされる。この場合ソートは合っているが、要素は文字列のままである。

韓国語・ロケールのソートは比較関数で解く

文字列のソートでコードユニット順が人の期待する順序と異なるときは、比較関数にlocaleCompareやIntl.Collatorのcompareを使う。同じ文字列のリストを、既定のソート、localeCompare、Intl.Collator、数値オプションの順でソートした。照合規則のツール別の詳しい比較は、韓国語ソートの記事が扱っている。

const names = ['나', '다', '가', 'Z', 'a', 'B', 'ㄱ'];
                    console.log('default       ', [...names].sort().join(' '));
                    console.log('localeCompare ', [...names].sort((x, y) => x.localeCompare(y, 'ko')).join(' '));
                    const col = new Intl.Collator('ko');
                    console.log('Intl.Collator ', [...names].sort(col.compare).join(' '));
                    const files = ['파일10', '파일2', '파일1'];
                    console.log('default       ', [...files].sort().join(' '));
                    console.log('numeric true  ', [...files].sort(new Intl.Collator('ko', { numeric: true }).compare).join(' '));
default        B Z a ㄱ 가 나 다
                    localeCompare  ㄱ 가 나 다 a B Z
                    Intl.Collator  ㄱ 가 나 다 a B Z
                    default        파일1 파일10 파일2
                    numeric true   파일1 파일2 파일10

既定のソートは、大文字のB・Z、小文字のa、ハングル互換字母のㄱ、完成形の音節가・나・다の順で、コードユニット順に従う。localeCompare('ko')とIntl.Collator('ko')は、このNode.jsで同じ結果(ㄱ, 가, 나, 다, a, B, Z)を出した。この順序でハングルがラテン文字より前に来るのは、この環境のICUデータによる値である。2つ目のリストでは、既定のソートは파일1, 파일10, 파일2で、Collatorのnumericオプションをオンにすると파일1, 파일2, 파일10になる。同じCollatorを一度作ってcompareを再利用する点は、上の韓国語ソートの記事が性能測定とともに扱った。

比較関数を書く規則 - 入力の型別の整理

前の出力で実証されたものだけを表にまとめると、次のようになる。各行の根拠となる節は右の列にある。

  • 同点では正確に0を返す。1や-1を返す比較関数は反射性を破る。
  • ブール値を返さない。比較関数の戻り値は数値で、trueとfalseは1と0になり、負の値がない。
  • undefinedと空きスロットは比較関数が受け取らないので、比較関数の中で位置を決められない。末尾に置きたくないなら、ソート前に値を埋めるか代替キーを使う。
  • 元を保つ必要があるなら、toSortedを使うか、コピーを作ってからsortする。
  • 比較関数を変えたら、数値と文字列の混在、キーの欠落、同点の順序を含むテストデータで確認する。5個の入力だけでは、ブール値の比較関数もたまたま通ることがある。

確認できなかったこと

  • ECMAScript仕様本文のArray.prototype.sortとSortCompareのアルゴリズム。仕様のページが目次しか返さなかったため、MDNの記述のみを引用した。
  • Node.js 22以外のエンジン(ブラウザ、Bun、Deno、他のNode.jsバージョン)での、ブール値・不整合な比較関数の結果と、比較関数の呼び出し順。
  • ブール値の比較関数が5個の入力で何も変えなかった内部的な理由。ソートアルゴリズムの内部実装は、このNode.jsでは調べていない。
  • 同点で1を返す比較関数の安定性が、他の入力サイズやエンジンでも保たれるか。
  • 大きな配列(数十万件以上)でのソート時間と比較関数の呼び出し回数。
  • ICUデータのバージョンによる、韓国語とラテン文字の混在ソート順の差と、sensitivity・caseFirstなど他のCollatorオプションの効果。
  • TypedArray.prototype.sortの既定の比較と、Arrayとの違い。
