ヒアドキュメント実践 - 変数展開を切る・入れる、インデントの罠

区切り語にかぶせたクォート一つが本文全体の解釈を変える。全部走らせて出た出力をそのまま貼った

2026-09-01 開発・インフラ

設定ファイル十行をスクリプトで作らなければならないとき、echo を十回書く人とヒアドキュメントを使う人の差は好みではない。十行のうち一行にダブルクォートが入った瞬間、前者は崩れる。ヒアドキュメントはその場所を代わりに引き受けるための構文であり、だから本文をシェルがどこまで触るのかがこの構文のすべてになる。

その境界はたった一か所で決まる。区切り語にクォートが付いているかどうかだ。この一文字が $ とバッククォートとバックスラッシュの運命を同時に変える。残りの罠のほとんどはここから派生するか、終了区切り語が見つからない問題に収束する。

以下の出力はすべて Windows の Git Bash 環境、GNU bash 5.2.37(1)-release (x86_64-pc-msys) で実際に実行して出たものをそのまま写している。比較が要る箇所は同じ箱に入っている dash でも走らせ、結果が分かれる場所はその都度書いた。

シェルの挙動は実装とバージョンによって変わる。この記事の出力は上に書いた一つの組み合わせで出たものであり、とくにヒアドキュメントの内部保存方式と改行の扱いは MSYS 系と glibc Linux で違いうる箇所だ。確認できなかった部分は後ろにまとめてある。

ヒアドキュメントが代わりを務める場所

複数行の文字列を作る方法はいくつもある。echo を繰り返すか、printf に改行を埋め込むか、変数一つに \n を継ぎ足すか。この三つは内容にクォートがない間だけ楽だ。設定ファイルや SQL や JSON のようにクォートが内容の一部であるテキストが入ってくると、外側の引用と内側の引用が重なって読めない行になる。

# 引用符が内容に入ってくる瞬間
echo "{"                     # これは通って
echo "  \"name\": \"$app\","  # ここから目が痛くなる
echo "  \"debug\": false"
echo "}"

# 同じものをヒアドキュメントで
cat <<EOF
{
  "name": "$app",
  "debug": false
}
EOF

ヒアドキュメントが解くのはまさにこの場所だ。本文の中のクォートは何の意味も持たない。シェルがその行を単語に割らないからだ。改行もそのまま生きているし、インデントもそのまま渡る。クォートの一般規則そのものが怪しいなら シェルのクォート規則 のほうが先だ。ここでは区切り語に付くクォートだけを扱う。性格がまったく違う代物である。

  • 本文の中の " と ' はエスケープしない。引用符として扱われない
  • 改行は文字どおり保存される。\n を使う場面がない
  • 本文はコマンドの標準入力に入る。引数ではない。だから引数長の制限とは無関係だ
  • 代わりに標準入力を使うので、すでに標準入力を使っていた場所とぶつかる。第7節で扱う
  • 区切り語には慣例で EOF がよく使われるが、どんな語でもよい。本文に出るはずのない語がよい

区切り語のクォート一文字

この記事から一つだけ持ち帰るならこれだ。<<EOF と <<'EOF' は同じ本文をまるで違うふうに解釈する。八種類の入力を一つのファイルに入れ、二つの形で走らせてみた。

name=world

# A: クォートなしの区切り語
cat <<EOF
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

# B: 本文は一文字も違わず、区切り語だけをクォートで包んだ
cat <<'EOF'
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

出た出力である。

plain: world
cmdsub: hi
backtick: hi
backslash-dollar: $name
backslash-n: \n
backslash-backslash: \
tilde: ~
star: *

=== B: <<'EOF' (quoted) ===
plain: $name
cmdsub: $(echo hi)

\\\\\前者だけバックスラッシュが一枚剥がれる
~~~どちらもそのまま。チルダ展開は起きない
***どちらもそのまま。パス名展開は起きない

切る書き方は三つある

シングルクォートだけが使えるのではない。POSIX 規格は区切り語のどの一部でも引用されていれば本文を展開しないと記している。だから以下の三つはすべて同じ効果だ。三つの形とも bash 5.2.37 と dash の両方で展開が切れることを確認した。

  • <<'EOF' — 最もよくあり、最も目につく。これを使えばよい
  • <<"EOF" — ダブルクォートでも同じように切れる。ダブルだから半分だけ入りそうに見えるが、そうではない
  • <<\EOF — バックスラッシュ一文字でも切れる。短いぶん、かえって見落としやすい

ヒアドキュメントがしない展開

表の最後の二行がよく誤解される。クォートなしのヒアドキュメントでも単語分割とパス名展開とチルダ展開は起きない。本文は最初から単語ではなく、ひと塊のテキストとして扱われるからだ。起きるのはパラメータ展開・コマンド置換・算術展開の三つだけで、バックスラッシュはダブルクォートの中と同じ規則に従う。

  • したがって *.log を本文に書いてもファイル一覧に展開されない。向こう側で展開させたいときはこれが楽だ
  • ~/bin もホームのパスに変わらない。ホームをローカルの値で埋めたいなら $HOME を使う
  • 本文の中の空白はそのままだ。何マスも空けた整列が崩れない
  • 算術展開 $(( )) は入っている。向こうで計算させるなら \$(( )) で止める

半分だけ展開したいとき

実務でいちばんよく出る要求はほとんどはそのままにして、いくつかだけ今の値で埋めることだ。クォートなしのヒアドキュメントを使い、残りを全部 \$ で止めればよい。できるにはできるが、以下を見ればなぜすぐ汚くなるかも一緒に見える。

LOCAL_DIR=/tmp/demo

cat <<EOF
cd $LOCAL_DIR
for f in *.log; do
  echo "\$f"
done
total=\$(( 1 + 2 ))
echo "\$total \$HOME"
EOF
cd /tmp/demo
for f in *.log; do
  echo "$f"
done
total=$(( 1 + 2 ))
echo "$total $HOME"

狙いどおり $LOCAL_DIR 一つだけが値に変わった。問題は比率だ。この例は六行にエスケープが五つある。二十行をこうやって渡すとバックスラッシュが二十個を超えて付き、一つ落としただけで静かに間違った値が埋まる。

  • エスケープの数が三つ四つを超えたら向きを反転する。区切り語をクォートで包み、必要な値は引数で渡す
  • 引数で渡す方法は第9節にある。ローカルで展開される場所を "$1" 一か所に寄せるやり方だ
  • 中間の形として、本文の先頭に VAR=値 の数行だけをクォートなしのヒアドキュメントで先に出し、本文はクォート付きのヒアドキュメントで繋ぐやり方もある
  • どちらにせよ原則は一つ。展開される場所を数えられる個数に保つ

ハイフン付きはタブだけ削る

<<-EOF はインデントを消してくれると知られている。正確には先頭のタブ文字だけを消す。POSIX 規格の文がそう書いてあり、終了区切り語の行にも同じ規則が適用される。スペースは対象ではない。

タブなら通る

# cat -A で見た原本。^I がタブだ
if true; then$
^Icat <<-EOF$
^I^Iline one$
^I^Iline two$
^IEOF$
fi$
echo "after: $?"$

# 実行結果
line one
line two
after: 0

スペースでは通らない

エディタの設定一つがこれを引っくり返す。同じファイルをタブの代わりにスペース四つで保存して走らせた結果だ。

# cat -A で見た原本。タブが一つもない
if true; then$
    cat <<-EOF$
        line one$
        line two$
    EOF$
fi$
echo "after"$

# 実行結果
e2b.sh: line 7: warning: here-document at line 2 delimited by end-of-file (wanted `EOF')
e2b.sh: line 8: syntax error: unexpected end of file
exit=2

ここでは fi があったので構文エラーで落ちた。運がよい場合である。囲むブロックがなければエラーなく静かに通り過ぎる。第5節でそちらを見る。

タブが内容のとき

規格の文は「先頭のタブ文字をすべて取り除く」だ。インデントした分だけではない。だからタブが意味を持つ内容をハイフン付きの形で出すと、そのタブまで消える。Makefile のレシピ行が代表例だ。

# 原本 (^I はタブ)
cat <<-EOF$
^Iall:$
^I^Igcc -o app main.c$
^IEOF$

# 出力 — レシピ行のタブが消えた。この Makefile は動かない
all:$
gcc -o app main.c$

# 同じ内容をハイフンなしで
cat <<EOF$
all:$
^Igcc -o app main.c$
EOF$

# 出力 — タブが残る
all:$
^Igcc -o app main.c$
  • ハイフン付きの形は内容にタブがないときだけ安全だ。あるならインデントを諦めて左端に付ける
  • Makefile、TSV、タブで整列した表を出すときはハイフン付きを使わない
  • エディタの「タブをスペースに」設定と真正面からぶつかる。このファイルだけ例外規則を掛けるか、ハイフン付きを使わないかを選ぶことになる
  • 代案は左端に詰めて書くことだ。見た目は汚くてもエディタの設定に依存しない
  • もう一つの代案は展開可能な形で出したあと sed 's/^ *//' でスペースを消すことだ。内容に先頭空白がないときだけ使う

終了区切り語が見つからないと

終了区切り語の行の条件は三つだ。区切り語と改行だけでなければならず、その間に空白があってはならず、ハイフン付きの形でなければ行頭から始まらなければならない。一つでも外れるとシェルはファイルの末尾までを本文にする。

失敗は静かに来る

囲むブロックがなければ構文エラーすら出ない。以下はスペースでインデントしたハイフン付きの形に、後続のコマンドを付けたものだ。

# 原本
cat <<-EOF$
    body line$
    EOF$
echo "THIS SHOULD PRINT"$
touch /tmp/demo/marker$

# 実行結果
e2c.sh: line 5: warning: here-document at line 1 delimited by end-of-file (wanted `EOF')
    body line
    EOF
echo "THIS SHOULD PRINT"
touch /tmp/demo/marker
exit=0

# marker は作られなかった
ls: cannot access '/tmp/demo/marker': No such file or directory

これがこの構文でいちばん危ない形だ。終了コードは 0 で、警告は標準エラーにしか出ず、後に続いていたコマンドは実行される代わりに文字列として出力される。ログを標準出力だけ集めていたなら成功した実行と区別がつかない。CI ではこのスクリプトに緑のランプが点く。

終了コードが何を取りこぼすかは シェルの終了コードと set -e のほうにある。この事故は標準エラーを捨てないことでしか捕まらない。

外れた条件bash 5.2.37 の反応終了コード捕まるか
区切り語の後に空白一つ警告のあとファイル末尾まで飲み込む0標準エラーを見てこそ
スペースのインデント + ハイフン付き同じ0標準エラーを見てこそ
上と同じだが if ブロックの中警告 + syntax error: unexpected end of file2捕まる
綴りや大小文字の不一致同じ警告。eof は EOF ではない0 または 2上と同じ

同じスペースインデントのファイルを dash で走らせるとメッセージが違う。Syntax error: end of file unexpected (expecting "fi") だけが出て、bash が出してくれる「どの行のヒアドキュメントがどの区切り語を待っていたか」という親切な文はない。診断が要るときは bash 側の警告文のほうがはるかに役に立つ。

  • 区切り語のあとの見えない空白が原因のことが多い。cat -A で EOF$ か EOF $ かを見る
  • 本文に区切り語が出る可能性があるなら EOF の代わりに __CONFIG_END__ のような語を使う
  • 区切り語の照合は大小文字を区別する。本文の中の eof、Eof、MARKERX、インデントされた MARKER はどれも終了として扱われないことを確認した
  • スクリプトを繋ぎ合わせる生成器を使うならここが最初に壊れる。繋いだあと bash -n で構文だけ検査する

リダイレクトとパイプの順序

ヒアドキュメントはリダイレクトの一種だ。だから他のリダイレクトと同じ行に置かれるとき順序が気になる。答えは順序は関係ないである。どちらもコマンドが実行される前に処理され、別々のファイル記述子を触るからだ。

# リダイレクトが先
cat > out1.txt <<'EOF'
one
two
EOF

# リダイレクトが後
cat <<'EOF' > out2.txt
one
two
EOF

# パイプで繋ぐ — 本文はパイプ左側のコマンドの入力だ
cat <<'EOF' | tr 'a-z' 'A-Z'
alpha
beta
EOF
out1.txt:
one
two

out2.txt:
one
two

ALPHA
BETA

三つの形とも狙いどおり動く。ただし読みやすいほうは決まっている。リダイレクトを先に置けばコマンド行だけ読んでもどこへ出るか分かる。後ろに置くとヒアドキュメント本文十行を過ぎてやっと > out.txt が見える。

  • 同じ行にヒアドキュメント二つも置ける。本文は書いた順に次の行から順番に読まれる
  • パイプと混ぜるとき紛らわしい点が一つある。ヒアドキュメントは左側のコマンドの標準入力であって、パイプ全体の入力ではない
  • ファイル名を要求するコマンドには - か /dev/stdin を使うか、プロセス置換 <(...) で包む
  • プロセス置換はサブシェルを作る。その中で変数を変えても外に残らない理由は パイプの中のwhileで変数が消える理由 のほうにある

標準入力を食う

ヒアドキュメントは標準入力を埋める構文だ。だからすでに標準入力を使っていた場所とぶつかるのは予定された話である。いちばん有名な事故がループの中の ssh だ。標準入力を最後まで読むプログラムを代役に置き、三行の一覧で再現してみた。

printf 'host-a\nhost-b\nhost-c\n' > hosts.txt

# ssh のように標準入力をまるごと読む代役
drain() { echo "  [$1] draining stdin..."; cat > /dev/null; }

# 1. そのまま書くと
while read -r h; do
  echo "visiting $h"
  drain "$h"
done < hosts.txt

# 2. 内側コマンドの標準入力を塞ぐ
while read -r h; do
  echo "visiting $h"
  drain "$h" < /dev/null
done < hosts.txt

# 3. 一覧を別のファイル記述子で渡す
while read -r h <&3; do
  echo "visiting $h"
  drain "$h"
done 3< hosts.txt
=== 1. loop body drains stdin (the ssh problem) ===
visiting host-a
  [host-a] draining stdin...

=== 2. same loop, stdin closed for the inner command ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

=== 3. same loop, list fed on fd 3 instead ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

1番は最初の一行だけ処理して終わる。エラーもなく終了コードも正常だ。サーバー三台に配るスクリプトが一台だけ触って成功を報告する形がこれである。実際の ssh は -n オプションで同じことをするし、ffmpeg や一部のパッケージ管理ツールにも同じ癖がある。

面白いのはヒアドキュメントを付けるとこの問題がひとりでに消える点だ。ヒアドキュメントがそのコマンドの標準入力を置き換えてしまうので、内側のコマンドが外の一覧に手を出せない。同じループで drain "$h" <<EOF ... EOF の形に変えると三行すべてが処理されることを確認した。

  • 原因はいつも同じだ。ループの入力とコマンドの入力が同じ記述子である
  • 対処1: 内側コマンドに < /dev/null。いちばん短く、内側が入力を使わないと確かなときに使う
  • 対処2: 一覧を 3< で渡し read -r h <&3 にする。内側コマンドが標準入力を普通に使えるよう残しておく
  • 対処3: 内側コマンドにヒアドキュメントを付ける。どうせ遠くへスクリプトを渡すつもりならこれが自然だ
  • 対処4: そもそも while read ではなく配列を先に埋めて for で回す。一覧が大きくないならこれがいちばん安全だ

ヒアストリングは一行のとき

<<< はヒアドキュメントの一行版の親戚だ。bash 拡張であり POSIX 規格にはない。dash で走らせると Syntax error: redirection unexpected で即死する。移植性が要るスクリプトならここで分かれる。

# ヒアストリングは末尾に改行を付ける
printf 'abc' | wc -c     # => 3
wc -c <<< 'abc'          # => 4

# クォートしなくても単語に割れない
v='a b'
cat <<< $v      # => a b
cat <<< "$v"    # => a b
cat <<< '$v'    # => $v

# read と組めばサブシェルができない
read -r first rest <<< "alpha beta gamma"
echo "first=$first rest=$rest"      # => first=alpha rest=beta gamma

# パイプでやると変数が残らない
echo "alpha beta gamma" | read -r f2 r2
echo "f2=[$f2] r2=[$r2]"            # => f2=[] r2=[]

三つ目のブロックがヒアストリングを使う本当の理由だ。echo ... | read は read がサブシェルで回って変数が消えるが、ヒアストリングはリダイレクトなのでサブシェルを作らない。同じ理由で while ... done <<< "$var" の形も安全だ。

  • 末尾に改行が一つ付く。バイト数を数える場所ではこの一文字が結果を変える
  • 変数が空でも改行一行は入る。wc -l <<< "$empty" は 0 ではなく 1 だ
  • クォートなしで書いても単語分割は起きない。それでも "$v" と書くほうがよい。読む人が迷う
  • 複数行の値を入れてもよい。$'one\ntwo\nthree' を入れると wc -l が 3 を返す
  • 展開を切りたいなら値の側をシングルクォートで包む。区切り語のクォート規則とは別の話だ

遠くへ渡すときどちら側で展開されるか

ssh host bash -s <<EOF の形で事故が起きる理由は一つだ。本文が二度解釈される。一度はローカルのシェルがヒアドキュメントを作るとき、もう一度は向こうのシェルがそのテキストをスクリプトとして読むとき。どちら側で展開するかを決めるのがこの場所のすべてだ。遠隔接続がなくても bash -c を二番目のシェルとして立てれば同じ構造が出る。

export TAG=local-tag

# A: クォートなしの区切り語 — 全部こちら側で展開される
bash -c 'export TAG=remote-tag; exec bash -s' <<EOF
echo "TAG seen = \$TAG"
echo "TAG baked = $TAG"
echo "PID of the second shell = \$\$"
EOF

# B: クォート付きの区切り語 — 全部向こう側で展開される
bash -c 'export TAG=remote-tag; exec bash -s' <<'EOF'
echo "TAG seen = $TAG"
echo "PID of the second shell = $$"
EOF

# C: 必要な値だけを引数で渡す
bash -c 'export TAG=remote-tag; exec bash -s -- "$1"' _ "$TAG" <<'EOF'
echo "argument from the local side = $1"
echo "value from the remote side  = $TAG"
EOF
=== A ===
TAG seen = remote-tag
TAG baked = local-tag
PID of the second shell = 1780

=== B ===
TAG seen = remote-tag
PID of the second shell = 1781

=== C ===
argument from the local side = local-tag
value from the remote side  = remote-tag

(参考: この実験を走らせた外側シェルの PID は 1777 だった)

A の二行がこの節の要約だ。\$TAG は向こうの値 remote-tag を出し、$TAG はローカルの値 local-tag がテキストに埋め込まれて渡った。C はその二つを混ぜないやり方だ。本文はまるごと展開を切り、ローカルの値は引数の枠からだけ入ってくる。展開される場所が目に見える個数まで減る。

sudo は少し肌合いが違う。ここでよくある間違いは sudo cat > /etc/some.conf <<'EOF' だ。リダイレクトは sudo ではなくそれを呼び出したシェルが処理する。権限のない側がファイルを開くのだ。同じ構造を権限の代わりに存在しないディレクトリで確かめてみた。

cat > /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => e12.sh: line 3: /nonexistent_dir/x.conf: No such file or directory

tee /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => tee: /nonexistent_dir/x.conf: No such file or directory

エラーを出す主体が違う。前者はスクリプト名と行番号の付いたシェルのメッセージで、後者は tee 自身のメッセージだ。だから管理者権限でファイルを書くときは sudo tee を使う。ファイルを開く主体が sudo の下に入る。

  • ssh にヒアドキュメントを付けるときはクォート付きの区切り語を既定にする。漏れるほうではなく止めるほうが既定であるべきだ
  • ローカルの値が要るなら bash -s -- "$v1" "$v2" で渡し、向こうで $1、$2 として受ける
  • 向こうで走らせるスクリプトが長くなったら、ヒアドキュメントよりファイルを scp で送って実行するほうがよい。第15節でまた見る
  • 管理者権限の書き込みは sudo tee file > /dev/null か sudo sh -c 'cat > file'。前者のほうが読みやすい
  • どちらにせよ二度解釈されるという事実を忘れない。向こうのログに実際に実行された行を残しておくと診断が速くなる

ファイルを作る三つの慣用句

ヒアドキュメントの半分以上はファイルを作るのに使われる。結果が同じになる三つの形を同じ本文で走らせ、ハッシュを突き合わせてみた。

# 1. いちばんよくある形
cat > a.conf <<'EOF'
key = $VALUE
EOF

# 2. 権限が要るか、画面にも見たいとき
tee b.conf > /dev/null <<'EOF'
key = $VALUE
EOF

# 3. 外部コマンドなしでシェルだけで
while IFS= read -r line; do printf '%s\n' "$line"; done <<'EOF' > c.conf
key = $VALUE
EOF
254b9d772669ad5fc3e7724fe7fe623e *a.conf
254b9d772669ad5fc3e7724fe7fe623e *b.conf
254b9d772669ad5fc3e7724fe7fe623e *c.conf

三つのファイルがバイト単位で同じだ。では何を選ぶか。cat の形が圧倒的に読みやすく、プロセス一つを節約しようと3番を使うのはたいてい損だ。ただし cat も tee も外部コマンドなので、最小環境の初期起動スクリプトのように /bin がまだない場所では3番が唯一の選択になる。

  • 既定は cat > file <<'EOF'。クォートを習慣的に付け、展開が要るときだけ外す
  • 権限が要るなら sudo tee。標準出力が画面に漏れるので > /dev/null を付ける
  • 追記は cat >> file か tee -a。二度回しても安全かは別の問題で、二度実行しても壊れないスクリプト のほうで扱った
  • ファイルを作る前に既存ファイルを退避するならヒアドキュメントの前に条件を付ける。ヒアドキュメントはリダイレクトなので if の中でもそのまま使える
  • 作ったファイルの権限が大事なら install -m 0644 /dev/stdin file <<'EOF' の形も使える。作りながら権限も一緒に決める

変数に入れると末尾が切れる

ヒアドキュメントを変数に入れる慣用句は var=$(cat <<'EOF' ... EOF ) だ。ここには静かな損失がある。コマンド置換が結果末尾の改行を全部消す。19 バイトの本文で四つの方法を測ってみた。

# 原本は 19 バイト: "line one\nline two\n\n"

v=$(cat <<'EOF'
line one
line two

EOF
)

read -r -d '' v2 <<'EOF'
line one
line two

EOF

IFS= read -r -d '' v3 <<'EOF'
line one
line two

EOF

mapfile -t arr <<'EOF'
line one
line two

EOF
=== the source text is 19 bytes ===
19

$(cat <<EOF)        exit=0 bytes=17
read -r -d ''       exit=1 bytes=17
IFS= read -r -d ''  exit=1 bytes=19
mapfile -t          elements=3

四行から読み取ること

一行目は予想どおりだ。改行が二つ消えて 17 バイト。二行目が罠である。read -r -d '' は改行を生かすために使う形なのに、IFS を空にしておかないと結局 17 バイトになる。read が最後のフィールドの前後の IFS 空白を削るからで、既定の IFS には改行が入っている。三行目だけが 19 バイトを守った。

そして二行目も三行目も終了コードが 1 だ。区切り文字をヌル文字にしたのに入力にヌルがないので、read は「区切り文字に出会えず入力が終わった」と報告する。値は正常に入っているのにそうなる。即時終了の設定が入っているとここでスクリプトが死ぬ。

( set -e; read -r -d '' z <<'EOF'
payload
EOF
echo "NEVER REACHED" )
# => subshell exit code = 1   (echo は実行されなかった)

( set -e; read -r -d '' z <<'EOF' || true
payload
EOF
echo "reached, z=[$z]" )
# => reached, z=[payload]
# => subshell exit code = 0
入れる方法末尾の改行終了コードサブシェルいつ使うか
$(cat <<'EOF')切れる (19→17)0できる末尾の改行が関係ないほとんどの場合
read -r -d ''切れる (19→17)1できない使わないほうがよい。中途半端な形だ
IFS= read -r -d ''保存 (19)1できないバイト単位で正確さが要るとき
mapfile -t配列3要素0できない行単位で扱うとき。bash 4 以上
  • read は先頭の空白も削る。read -r a b <<< " x y " は a=[x] b=[y] を返す
  • 同じ入力に IFS= read -r c を使うと c=[ x y ] と空白が生きている。習慣的に IFS= を付ける理由だ
  • -r を外すとバックスラッシュがエスケープとして食われる。ヒアドキュメントで生かしてきたバックスラッシュを read で失うことがある
  • 終了コード 1 は || true で止める。代わりに read ... ; : でもよいが意図が見えにくい
  • mapfile は bash 4 以上で dash にはない。移植性が要るなら候補から外す

関数の中で、一行に二つ

ヒアドキュメント本文が始まる位置は演算子が書かれた行の次の行であって、演算子のすぐ後ろではない。この規則があるから一行にヒアドキュメントを二つ書けるし、ヒアドキュメントの後ろに別のコマンドを繋ぐこともできる。

# 関数の中で — ローカル変数も正常に展開される
emit() {
  local target=$1
  cat <<EOF
[unit]
target=$target
EOF
}
emit alpha

# if の中でも case の中でもそのまま
if [ -n "$HOME" ]; then
  cat <<'EOF'
inside an if
EOF
fi

# 一行に二つ — 本文は書いた順に次の行から読まれる
diff <(cat <<'A'
same
left
A
) <(cat <<'B'
same
right
B
)

# ヒアドキュメントの後ろに別のコマンドを繋ぐ
cat <<'EOF' ; echo "<- this ran after the heredoc"
body of the heredoc
EOF
[unit]
target=alpha
---
inside an if
---
2c2
< left
---
> right
diff exit=1
---
body of the heredoc
<- this ran after the heredoc

最後のブロックが規則をいちばんよく見せている。; echo ... がヒアドキュメント演算子と同じ行にあるのに本文に飲み込まれず、本文が終わったあとに実行された。シェルはその行を最後まで読んでコマンドとして解析し、それから次の行から本文を集める。

  • 関数の中でもインデントの問題は同じだ。終了区切り語を関数本体に合わせて下げるならハイフン付きの形 + タブでなければならない
  • case の中で使うときは ;; が終了区切り語の次の行に来なければならない。同じ行に付けると区切り語でなくなる
  • パイプラインの各段にヒアドキュメントを別々に付けられる。ただしその地点で読む人が道に迷う
  • 本文の中に区切り語と同じ語が行頭以外にあるなら問題ない。xEOF やインデントされた EOF はただの本文だ

本文はパイプか一時ファイルか

ヒアドキュメント本文が実際にどこに入ってコマンドに渡るかは規格が定めていない。実装が勝手にやる。bash 5.2.37 で実行中のコマンドの標準入力を覗くとサイズで分かれるのが見える。

# 小さい本文
ls -l /proc/self/fd/0 <<'EOF'
payload
EOF
# => /proc/self/fd/0 -> pipe:[8589943248]

# 大きい本文 (約 350KB)
# => /proc/self/fd/0 -> /tmp/sh-thd.6MTpiD (deleted)

# 境界を狭めてみた結果
body=65000    pipe:[4294982180]
body=66000    /tmp/sh-thd.ib1lXH (deleted)
body=70000    /tmp/sh-thd.NCKE8B (deleted)

小さい本文はパイプで渡され、パイプ容量を超えると名前を消した一時ファイルに変わる。境界は6万5千バイトと6万6千バイトの間だった。Linux の既定のパイプバッファが 64KiB なので値が合う。古い bash はサイズに関係なく一時ファイルを使っており、パイプを使う挙動は比較的最近入ったものだ。

実務で引っかかる場所は二つだ。標準入力を巻き戻して二度読むプログラムはパイプで失敗する。一時ディレクトリが一杯になったり読み取り専用でも大きなヒアドキュメントが失敗する。

境界の近くで妙なものを一つ見た。本文がちょうど 65,536 バイトと 65,537 バイトのとき、このビルドの bash は永遠に止まる。8秒の制限を掛けて二度再現した。それより大きいと一時ファイルに移って正常に動く。とても狭い区間で MSYS 側のパイプ容量の判定に関係がありそうだが、他の環境で同じかは確認できなかった。
  • 大きなデータを渡すときはヒアドキュメントよりファイルを作ってパスで渡すほうが予測しやすい
  • 標準入力を読み直す必要がある道具なら /dev/stdin ではなく実ファイルを作ってやる
  • 一時ファイル名が (deleted) と見えるのは正常だ。作った直後に消して他のプロセスから見えないようにしている
  • 同じ理由でヒアドキュメント本文は ps やコマンドライン引数に露出しない。秘密の値を渡すとき引数より良い理由だ
  • ただし一時ファイルのパスは一瞬でも存在するので、本当の秘密の値はパイプ区間に収まるサイズに保つほうがよい

厳格モードとぶつかる場所

スクリプトの先頭に set -euo pipefail を掛ける習慣があるなら、ヒアドキュメントと出会う地点を知っておく必要がある。二つある。

# 1. set -u とクォートなしのヒアドキュメント
( set -u; cat <<EOF
value = $DEFINITELY_NOT_SET
EOF
)
# => e12.sh: line 14: DEFINITELY_NOT_SET: unbound variable
# => unquoted exit=1

( set -u; cat <<'EOF'
value = $DEFINITELY_NOT_SET
EOF
)
# => value = $DEFINITELY_NOT_SET
# => quoted exit=0

# 2. 対応の取れないバッククォート
cat <<EOF
a `oops
EOF
# => bash: line 1: bad substitution: no closing "`" in `oops
# => exit=1

cat <<'EOF'
a `oops
EOF
# => a `oops
# => exit=0

一つ目はむしろ歓迎すべき失敗だ。向こうへ渡すつもりだった変数名を打ち間違えたとき、静かに空文字列が埋まる代わりにここで止まる。二つ目は厄介だ。本文にコマンドの例やマークダウンを入れると対応の取れないバッククォート一つでスクリプトが死ぬ。どちらも区切り語にクォートをかぶせれば消える。

  • 本文にコードの例、正規表現、マークダウン、Windows のパスが入るならほぼ常にクォート付きの区切り語が正解だ
  • set -e とぶつかるのは第11節の read -r -d '' だ。|| true を忘れない
  • set -u の下でクォートなしのヒアドキュメントを使うなら ${VAR:-既定値} の形で守る
  • 診断のとき bash -n script.sh で構文だけ検査すると、終了区切り語の問題のかなりが実行前に捕まる
  • bash -x はヒアドキュメント本文をトレースに出さない。本文の確認は cat で一度出してみるほうが速い

ヒアドキュメントを使うべきでないとき

ヒアドキュメントが楽になると全部ヒアドキュメントでやりたくなる。ところが以下の場合は別の道具のほうがよい。基準は単純だ。本文がスクリプトより長生きするか。

  • 本文が30行を超えたら別ファイルに置く。スクリプトを読むとき論理が本文に埋もれる。構文強調も効かず、そのファイルだけ別に検査することもできない
  • 置換する場所が五か所を超えたらテンプレート道具を使う。envsubst は既定の環境にあることが多く、置換対象を明示的に限ることもできる
  • 同じ本文を複数のスクリプトが使うならファイルに抜く。ヒアドキュメントをコピーしておくと二部が少しずつ分かれていく
  • JSON や YAML を作るなら値に特殊文字が入る可能性を先に見る。ユーザー入力が混ざった瞬間、ヒアドキュメントはエスケープの責任を負わない。jq -n か yq が正しい
  • 向こうで走らせるスクリプトが長いならファイルを送って実行する。二度解釈される区間が消え、失敗したとき向こうにファイルが残って再現できる
  • 一行ならヒアドキュメントを使わない。printf '%s\n' '...' かヒアストリングのほうが短い
  • 逆に設定ファイル十行前後、向こうへ渡す短いスクリプト、引用符の多いテキストはヒアドキュメントの正確な居場所だ

確認できなかったこと

  • この記事の出力はすべて MSYS ベースの bash 5.2.37 で出たものだ。glibc Linux の同じバージョンで全部同一かは確認できなかった。とくにパイプと一時ファイルが分かれる境界値、そして 65,536 バイト付近で止まる現象は他の環境で再現されるか分からない
  • CRLF で保存したスクリプトをこのビルドで走らせたとき、ヒアドキュメントは正常に動き出力にキャリッジリターンが残らなかった。MSYS のファイル読み取り方式である可能性が高く、glibc Linux で同じ結果が出るとは見ていない
  • 比較対象としては同じ箱の dash だけを使った。zsh、ksh、BusyBox ash は入っておらず走らせられなかった
  • dash はパッケージ情報を照会できず正確なバージョン番号を書けなかった
  • sudo 関連の記述は権限のないディレクトリではなく存在しないディレクトリで確かめたものだ。リダイレクトを誰が処理するかという構造は同じだが、実際の権限拒否の状況でのメッセージは確認できなかった
  • 遠隔実行は実際の ssh ではなく bash -c で立てた二番目のシェルで再現した。二度解釈されるという構造は同じだが、ssh が引数を合わせて向こうのシェルに渡す方式から来る追加のクォート問題は扱っていない
