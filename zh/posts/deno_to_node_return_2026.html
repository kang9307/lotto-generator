本文以David Bushell于2026年10月3日发表在个人博客上的回顾《Friendship ended with Deno, now Node is my best friend》，以及Node.js v26.10.0文档、pnpm设置文档和fnm的README中写明的语句为依据。原文是一篇带有讽刺意味的个人回顾，这里只取其论点与技术事实，没有照搬它对特定企业的评价。

起因 — 在SvelteKit项目里重新遇到Node

作者David Bushell写道，这个月他在一个基于SvelteKit的客户项目里大量使用了Node。长期以来Deno一直是他的首选运行时，以至于忘了Node该怎么用；回来之后却发现ECMAScript语法已得到支持，从前那些烦人的API要么被替换、要么被现代化了，这就是文章的出发点。他称之为「最重要」的一点，是再也不用看到require()。

回顾由四部分组成：包管理工具的选择、运行TypeScript、把自己的静态站点生成器从Deno迁到Node的经历，以及离开Deno的理由。它是一篇简短的个人记录，并不是为了测量或做对比实验而写的。「一直用Deno是出于习惯和熟悉」这句话也出自作者本人。

下文把作者回到Node时用到的东西逐一取出，放在相应官方文档的定义和限制旁边。选择运行时时一般会在哪些维度上产生分歧，见重写运行时这一决定。

版本管理与包管理 — fnm和pnpm

作者选了Fast Node Manager(fnm)来切换Node版本。他给出的理由是，自己早年使用NVM和npm的体验并不好，又听说fnm在切换版本方面更好。他写道，自己倾向于用最新版本，但有些客户项目要求稳定，因此需要在版本之间来回切换。fnm的README所说明的特性如下。

  • 性质。 README把fnm介绍为用Rust构建的、快速而简单的Node.js版本管理器，并把单文件、易安装、即时启动列为特点。
  • 支持的平台。 macOS、Windows和Linux。
  • 版本文件。 可识别.node-version和.nvmrc文件。
  • 安装途径。 除安装脚本外，README还介绍了Homebrew、Winget、Scoop、Chocolatey、Cargo以及发行版二进制文件。
  • shell配置。 需要在shell中对fnm env的输出求值来设置环境变量，之后才能使用。带--use-on-cd选项的示例按Bash、Zsh、Fish、PowerShell分别给出。

包管理器他选了pnpm。作者给出的理由是避免被攻陷。由于他用的一些脚本把二进制文件名写死了，他说自己加了下面两个别名。

alias npm=pnpm
                    alias npx=pnpx

作者在后来补充的注释中解释说，照抄那些假定已安装npm的安装指南中的命令时，这两个别名很有用。至于设置放在哪里，pnpm文档另有规定：pnpm从命令行、环境变量和pnpm-workspace.yaml中读取配置，从.npmrc中只读取认证和registry相关的设置，其余设置放在pnpm-workspace.yaml或全局的config.yaml中。下文的各项设置之所以都写在pnpm-workspace.yaml里，原因就在这里。

pnpm的安装延迟与信任策略 — minimumReleaseAge和trustPolicy

作者在pnpm-workspace.yaml中加了下面两行。

minimumReleaseAge: 1440
                    trustPolicy: no-downgrade

minimumReleaseAge — 发布后经过的时间

pnpm文档的定义是这样的：minimumReleaseAge规定一个版本发布之后、pnpm安装它之前必须经过的最少分钟数。它不仅适用于直接依赖，也适用于包括传递依赖在内的所有依赖。文档把目的写为「降低安装到被攻陷或有缺陷的包的风险」，并补充说，在大多数情况下，恶意版本会在一小时之内被发现并从registry中移除。

  • 加入的版本与默认值。 在v10.16.0中加入。默认值从v11起为1440，此前为0。
  • 1440的含义。 单位是分钟，所以1440就是一天。文档中的示例也把同一个值解释为「只安装至少一天之前发布的包」。
  • 排除列表。 把包名写进minimumReleaseAgeExclude，这个包就会在发布后立即被安装。模式写法从v10.17.0起可用，指定具体版本从v10.19.0起可用。
  • 没有符合条件的版本时。 由minimumReleaseAgeStrict(v11.0.0)决定。值为false时，pnpm会退回到不满足条件的版本，让安装得以继续；值为true时，依赖解析失败。当minimumReleaseAge被显式配置时，这个值默认为true；而只使用内置默认值1440时，出于向后兼容的考虑，行为是非严格的。
  • 没有发布时间的registry。 minimumReleaseAgeIgnoreMissingTime(v11.0.0，默认true)开启时，元数据中不含time字段的包会跳过这项检查。

作者写道，他起初把这个值设成了「一个月」，结果出现了依赖问题，pnpm难以匹配到合适的版本，于是他降到了「一天」。他写下的1440与文档中v11的默认值是同一个数字。不同之处在于，把这个值显式写进文件之后，上面所说的严格模式会默认开启。设成一个月时遇到的问题可能与这种严格模式有关，这是根据文档措辞得出的解读；原文并没有解释原因。

trustPolicy — 信任级别下降的版本

据pnpm文档，把trustPolicy设为no-downgrade之后，如果一个包的信任级别比此前的版本有所下降，安装就会失败。文档举的例子是：一个包以前由受信任的发布者(trusted publisher)发布，现在却只有来源证明(provenance)，或者完全没有信任凭据。

  • 加入的版本与默认值。 在v10.21.0中加入，默认值为off。可取的值只有no-downgrade和off两个。
  • 比较的依据。 信任检查只以发布日期为依据，而不是semver。只要有任何一个更早发布的版本拥有更强的信任凭据，这个包就无法安装。
  • 预发布版本。 从v10.24.0起，安装正式版本时，预发布版本的信任凭据不计入评估。
  • 排除列表。 写进trustPolicyExclude(v10.22.0)的包或版本不参与检查。
  • 较旧的版本。 trustPolicyIgnoreAfter(v10.27.0)可以让发布时间超过指定分钟数的包不再接受这项检查。

作者写道，迁到自己托管的Forgejo实例之后，他的包失去了「provenance」，他不得不配置pnpm的信任策略来放行自己的包。原文没有说他用的是哪个键。在文档中，与这一用途对应的设置是trustPolicyExclude。

拦截安装脚本 — allowBuilds和strictDepBuilds

作者用一行话写道：「pnpm还会拦截post-install脚本」。在pnpm文档中，决定这一行为的设置如下。

  • 默认行为。 没有写进allowBuilds的包，默认不允许执行脚本，并被当作「未经审查」的包对待。
  • 报错还是警告。 由于strictDepBuilds的默认值是true，默认会输出错误；只要有依赖带有未经审查的构建脚本(文档也称之为postinstall脚本)，安装就会以非零退出码结束。设为false则改为输出警告。
  • 如何放行。 allowBuilds是一张以包匹配器为键的映射表，true表示允许，false表示禁止。安装过程中脚本被忽略的依赖，会连同一个占位值被自动加入pnpm-workspace.yaml；pnpm approve-builds以及pnpm add的--allow-build标志也把条目写到同一处。
  • 旧的设置。 onlyBuiltDependencies、neverBuiltDependencies、ignoredBuiltDependencies等在v11中被移除，由allowBuilds取代。
  • 全部放行。 把dangerouslyAllowAllBuilds(v10.9.0，默认false)设为true之后，依赖的preinstall、install、postinstall脚本无需批准即可执行。文档为此附上了警告：这会让包括传递依赖在内的所有依赖，在现在和将来都可以运行安装脚本。
  • 与ignoreScripts的区别。 ignoreScripts(默认false)是另一项独立的设置，它让项目package.json及其依赖中定义的脚本一律不执行。

关于npm一侧的行为，原文只留下了一句带问号的话。原文点名的供应链事件只有Shai-Hulud一个，其经过见npm供应链攻击分析。

Node的类型剥离 — 文档所定义的范围

作者写道，Node现在可以运行TypeScript了。Node.js v26.10.0文档的「Modules: TypeScript」一章，把在运行时使用TypeScript的途径分成两条：要完整支持TypeScript的全部语法和特性，就使用第三方包(文档以tsx为例)；要轻量的支持，则使用内置的类型剥离(type stripping)。

对内置功能的定义很短。Node.js默认会执行只包含可擦除(erasable)TypeScript语法的TypeScript文件；它把TypeScript语法替换为空白；不做类型检查。要关闭这项功能，可使用--no-strip-types标志。文档中的变更历史如下。

  • v22.6.0。 加入类型剥离。
  • v23.6.0、v22.18.0。 类型剥离默认启用。
  • v24.3.0、v22.18.0。 不再输出实验性功能的警告。
  • v25.2.0、v24.12.0。 类型剥离进入稳定(stable)阶段。
  • v26.0.0。 移除--experimental-transform-types标志。这个标志是在v22.7.0中加入的。
项目 Node.js的行为 文档中的章节
可擦除的TypeScript语法 替换为空白后执行 Type stripping
类型检查 不做 Type stripping
tsconfig.json 不读取。像paths或向旧标准语法的转换这类依赖其设置的特性，是有意不支持的 Type stripping
enum声明 报错 TypeScript features
带运行时代码的namespace 报错(ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX)。不含运行时代码的namespace受支持 TypeScript features
parameter properties、import aliases 报错 TypeScript features
装饰器 不做转换，会导致解析器错误 TypeScript features
不带type关键字的类型import 被当作值import，导致运行时错误 Importing types without type keyword
.tsx文件 不支持 Determining module system
source map 不生成。由于是替换为空白，行号保持不变 Source maps
REPL、--check、inspect 不支持TypeScript语法 Non-file forms of input
node_modules之下的文件 拒绝处理 Type stripping in dependencies

文档说明这一范围是有意为之：刻意不支持那些需要生成JavaScript代码的语法，并把内联类型替换为空白，这样Node.js无需source map就能运行TypeScript代码。关于装饰器，文档写道，它目前是TC39的Stage 3提案，因此不做转换，在JavaScript原生支持之前Node.js不会支持。作为建议，文档给出的是TypeScript 5.8或更高版本，以及下面的tsconfig.json设置。

{
                      "compilerOptions": {
                         "noEmit": true, // Optional - see note below
                         "target": "esnext",
                         "module": "nodenext",
                         "rewriteRelativeImportExtensions": true,
                         "erasableSyntaxOnly": true,
                         "verbatimModuleSyntax": true
                      }
                    }

据文档中的注释，noEmit用于只执行*.ts文件的场合，比如构建脚本；如果打算分发*.js文件，就不需要它。模块系统同样不做转换。.ts文件的模块系统与.js文件以相同的方式确定，.mts始终作为ES模块运行，.cts始终作为CommonJS模块运行。import语句中必须写文件扩展名，因此要写成import './file.ts'。tsconfig的paths不会被转换，因而会报错，文档给出的最接近的功能是必须以#开头的subpath imports。在非文件形式的输入中，--eval和STDIN可以使用类型剥离。

node_modules之下不做类型剥离

作者碰到的正是上表的最后一行。他写道，TypeScript包不能就这样原样发布到npm，并给出了下面这条错误。

error: [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]:
                    Stripping types is currently unsupported for files under node_modules

Node.js的错误文档把ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING解释为「对于node_modules目录之下的文件，不支持类型剥离」，并注明它是在v22.6.0中加入的错误码，与类型剥离功能本身是同一个版本。理由写在TypeScript文档的「Type stripping in dependencies」一节，只有一句话：为了不鼓励包作者发布用TypeScript编写的包，Node.js拒绝处理位于node_modules路径之下的文件夹中的TypeScript文件。

作者把这一限制评价为「与其说是技术上的，不如说是理念上的」。文档给出的理由针对的是发布惯例，而不是实现上的局限，就此而言，这种读法与文档的措辞并不矛盾。他写道，希望ECMAScript能加入轻量的「原生类型」，并提到已有类型注解的提案，同时又说，恐怕等不到它们开花结果，自己就已经退休了。这一限制给作者的工作带来了三个结果。

  • 打包工具。 由于TypeScript包不能原样发布，就需要一个打包工具，作者用的是Tsdown。它多带来了两个配置文件。
  • 配置文件的数量。 他写道，算上删掉的deno.json等文件，正好持平。
  • 来源证明。 迁到自托管的Forgejo之后，包的provenance丢失了，于是需要前一节所说的信任策略例外。

迁移静态站点生成器 — 改了什么，以及15%这个数值

作者拿来当作对Node最后一项测试的，是把自己的静态站点生成器从Deno迁过来。他写道，放在没几个Node版本之前，这还需要一次大规模的重构；而在Node v26.10.0上，要做的事情出乎意料地少。

  • 文件系统。 必须做的第一项改动，是把Deno的文件系统API换成node:fs。他写道，node:fs比他记忆中大约十年前的样子有了很大改进。
  • HTTP服务器。 第二项是把Deno.serve换成Hono的node适配器。作者说这个适配器是对node:http的一层封装。
  • 路径模块。 此后他只多做了一处改动，就是把Deno的@std/path换成node:path，他说这只是改一下import而已。
  • 构建时间。 完成这次最小限度的迁移之后，他写道，构建快了15%。
  • 尚有的余地。 代码库仍然沿用Deno的惯用写法，他猜测，由于没有用上其他内置的Node API，还有一部分性能没有拿到。

15%是出自作者一个人、一个站点生成器的数值。原文中没有构建的绝对时间、站点规模、测量次数，也没有作为对比对象的Deno版本。这个数字记录的是：把同一份代码以最小的改动迁过去之后，在作者的环境里构建没有变慢；它并不是说明两个运行时之间一般性能差异的数值。

作者列出的离开理由与这个案例的范围

作者列出了三件事，作为最终促使他离开Deno的直接原因。

  • 持续了数周的ZSH集成故障
  • JSR的「429 (Too Many Requests)」响应
  • 并发HTTP请求时让Deno卡住的bug

这三项在原文中都只有一行，没有版本、复现条件，也没有issue链接。原文还提到，JSR的支持团队应他的请求很快删除了他的账号，他的包已经不可见，但旧版本仍然可以安装。除此之外，原文中还有作者对Deno背后那家公司发展方向的评价，那属于个人意见，与上面的技术事实是两回事。把作者用到的东西与官方文档放在一起，可以得到下表。

这个案例所能说明的范围很窄。它是一个人把自己的一个静态站点生成器迁移到Node v26.10.0的记录。作者自己也写道，一直用Deno的原因是习惯和熟悉，并补充说，最近他对写服务端JavaScript并没有多大热情。换成另一类工作，或者另一种规模的代码库，是否会得到同样的结果，仅凭原文无从得知。在Node这一侧得到的东西也都带有代价：类型剥离不做类型检查；就作者而言，发布包多出了一个打包步骤，信任策略则需要另行配置来放行自己的包。
