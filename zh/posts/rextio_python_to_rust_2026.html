把Python迁移到Rust这个决定

自动转换工具划下的边界线，以及在实务中重新划这条线的方法

2026年7月29日 IT/技术

引言：「把Python改成Rust」这句话里省略的条件

声称能把Python代码搬到Rust的工具已经出了好几年。2026年7月又公开了一个叫Rextio的项目。每次看到这类消息，反射性冒出来的问题是「那我们的代码能搬吗」，而这个问题几乎总是错的。正确的问题是我的代码里哪一部分具备可被搬运的性质，答案由代码的性质而不是工具的能力决定。

翻开Rextio的仓库文档会发现，这一点反倒是工具方先讲明的。它并不搬运整份代码，只把带类型注解、且落在预设子集内的函数下沉为Rust与PyO3代码，其余原样保留为Python实现。仓库给出的契约只有两句话：没有把握就不猜测而是回退；函数要么以与CPython等价的语义被原生编译，要么带着诊断信息被拒绝并留在Python回退里。

先划一条线。本文不推荐也不评价Rextio这个具体工具。仓库把自己标注为alpha阶段，多项功能挂着实验性标签，确认当时的star数还是个位数。它现在不是能放进生产的东西。本文关心的只有一件事：机器能搬的与不能搬的，这条界线划在哪里，以及这条界线如何改变实务上的判断。

1. Rextio实际在做的事 - 只取官方文档能确认的部分

先把工具的性质说准。Rextio不是那种把代码丢给对话式LLM让它重写成Rust的东西，而是由静态分析器与代码生成器构成的确定性工具。它读取Python AST，只接受落在支持范围内的函数，其余则输出诊断信息并拒绝。产物不是纯Rust程序，而是原生扩展与Python回退共存的混合包。

执行流程也很简单：从源码里找出原生候选，拒掉不合格的，只把接受的生成为Rust与PyO3代码，给其余的生成Python回退包装，最后构建成导入兼容的制品。

python -m pip install rextio

rextio check .                      # 仅诊断哪些会下沉为原生、哪些被拒绝
rextio build . --fallback=cpython   # 构建混合包

REXTIO_NATIVE_MODE=fallback python app.py   # 运行期关掉原生，走纯Python路径

值得注意的是第三行。随时能关掉原生的开关从一开始就写进了设计里。仓库文档把这一点概括为「原生是优化项而不是必要条件」。即使原生模块不存在或加载失败，包也会继续以Python回退运转。后面还会再谈到，这个开关不论用不用工具，自己动手实现时也必须照着做一份。

运行要求是CPython 3.11以上（文档称验证到3.14），Rust最低支持版本1.83以上。许可证为MIT。仓库公开的基准测试如下。下表数值全部照搬仓库文档所载的值，不是笔者复现的结果。

工作负载3次运行的中位倍速怎么读
核心混合57.729倍完全跑在支持子集内的纯计算循环
pandas Series.map66.143倍用户自定义函数调用逐元素重复的区间
NetworkX 迪杰斯特拉3.679倍一旦掺进图库调用，倍数就大幅下滑
NumPy 混合融合2.523倍已经下沉到C的运算，剩余空间很小
PyTorch CPU 深层MLP1.017倍实质等价。文档自己写明这不算有意义的提升

测试环境标注为Apple M4 Pro、CPython 3.11.9，基准日期2026年7月26日。从这张表要带走的教训不是上面那些大数字，而是下面那些接近1倍的数字。仓库文档自己就写着「结果因工作负载而异，接近1倍的值是等价而非有意义的提升」。在重活已经下沉到C或原生库的代码里，Python解释器原本烧掉的时间本身就很少，因而无可回收。这一句也正是全文的主题。

2. 自动转换在原理上做不到的事

看一眼Rextio声明不支持的清单，性质就分得很清楚：类与实例方法、动态属性访问、生成器、async与await、上下文管理器、可变容器的别名式改写、set[float]迭代、星号表达式与star import、动态代码执行，以及没有插件时的绝大多数第三方调用。

这份清单不是偶然。它不是某个工具的未完成项，而是静态转换这一路径本身撞上的墙。把每一项为什么是墙整理出来，就成了下表。

Python侧的性质在Rust中冲突的地方无法机械转换的原因
鸭子类型 · 动态属性访问静态类型 · trait解析到调用时才定下来的东西无法在编译期固定
生成器 · 协程持有所有权的状态机每个暂停点上存活引用的生命周期都得静态证明
可变对象的别名共享借用检查器多个名字同时改同一个对象的代码与所有权模型正面冲突
用异常控制流程Result返回值要全局追踪哪个异常在哪里被捕获，流程才能重建
以GIL为前提的原子性假设显式同步靠GIL侥幸安全的代码，一搬过去就变成竞态
任意精度整数定宽整数同样是int，溢出边界行为却不同
浮点集合中的NaN哈希与相等性规则NaN不等于自身，去重结果因此分叉

表的最后两行尤其实务。同名的类型并不表示同样的语义，这一事实在自动转换里制造的事故最为无声：编译过、测试也过，却只在特定输入上算出不同的值。

由此可以得出一个结论。自动转换器能覆盖的范围，外表是Python、实质上是静态类型语言的那个子集：类型注解完备、只用局部变量、进出的只有标量与简单容器的纯函数。这类代码本来就是容易搬到Rust的代码。反过来，最想搬的那些代码，也就是长年生长起来的业务逻辑，大体上都在这个子集之外。

  • 不要把拒绝读成失败 — 工具拒绝某个函数是正常行为。要是有工具一个不拒全盘接受，那边才更危险。
  • 诊断信息才是真正的产物 — rextio check 这类命令的价值不在转换，而在替你量出自己的代码有多静态。拒绝率到90%，那个代码库就不是这条路径的对象。
  • 为迎合子集去改代码的那一刻，成本就开始了 — 为了通过工具而把类拆成函数、把生成器换成列表，这份代码就已经离Python的惯用写法越来越远。这个代价必须算进账里。
  • 第三方调用实质上就是一堵墙 — 只要调了一行不在支持清单里的库，那个函数就会掉进回退。业务代码里满足这个条件的函数比想象的少。

3. 先把「慢」的原因定下来

在做换语言的决定之前，有一道必须过的关口：现在慢的原因真的是语言吗。实务中以性能问题报上来的案例，相当大一部分与解释器速度无关。按原因分开看，处方完全不同。

症状 · 原因确认方法转Rust的预期效果先该做的事
网络 · 磁盘等待墙钟时间与CPU时间之差几乎没有并发 · 连接池 · 批量化
N+1查询记录每请求的查询次数没有（反而可能更差）join · 预取 · 缓存
序列化 · 反序列化把负载大小与解析时间分开测中等（换个解析器也能收回不少）格式 · 削减列 · 流式处理
算法复杂度把输入规模翻倍观察时间增长率只改善常数倍，阶数不变更换数据结构
GIL争用加线程数吞吐量却不涨大（但先要确定原因）拆进程 · 评估free threading
解释器开销自身时间靠前的函数是纯Python循环大 — 这里是唯一正当的区间定位热点路径后做扩展模块

确认顺序是剖析器优先。要按自身时间而不是累计时间排序，才能看见真正烧CPU的地方。

# 按自身时间排序才能看到真正的燃烧点
python -m cProfile -o prof.out run_workload.py

# 在交互式浏览器中输入 sort tottime 之后再输入 stats 20
python -m pstats prof.out

接下来的一步更重要。量出热点路径在整体中的占比，先把改善的上限算出来。跳过这个计算，就会出现花上几周只换来个位数改善的事。

# 热函数占整体比例p、该部分快了s倍时的整体改善幅度
def upper_bound(p: float, s: float) -> float:
    return 1.0 / ((1.0 - p) + p / s)

print(upper_bound(0.20, 50))   # 1.2437...  -> 整体缩短20%就是上限
print(upper_bound(0.70, 50))   # 3.2051...  -> 从这里起才有投入的价值
print(upper_bound(0.20, 1000)) # 1.2496...  -> 就算快到无穷也过不了1.25倍

第三行就是结论。热点路径占比低的时候，把那部分做到无限快，整体也不会变快。要定一个实务阈值的话是这样：自身时间靠前的那些函数加起来不足整体执行时间的40%，就把换语言从待选项里剔除。超过60%才值得评估，超过80%通常做了更好。

4. 实务正解不是全面移植，而是热点路径扩展模块

走到这里，选项只有两个：把整个应用重写成Rust，或者只把热点路径拆成原生扩展模块、其余留在Python。先说结论，对多数组织而言第二个才是正解，而第一个能被正当化的条件非常窄。

原因在边界成本。Python与原生代码之间，每跨一次就有一笔值转换的开销。这笔开销随每次函数调用发生，搬运的数据越复杂就越大。所以设计糟糕的扩展模块会比纯Python更慢。实际上Rextio也把这个问题显式写进了设计：容器不许跨越原生边界，只允许int、float、bool、str、None这类不可变标量传给回退函数，甚至定了规则——反复来回跨边界的函数干脆降级为回退。

扩展模块设计的原则可以直接从这些约束里推出来。

  • 不要按元素逐个调用 — 一百万个元素调一百万次，边界成本会压过计算成本。把整个数组一次传过去，只调一次。
  • 让跨边界的数据保持简单 — 嵌套字典与自定义对象的转换成本很高。数字数组、字节串、扁平的字符串列表才是理想形态。
  • 不要把回调传过去 — 原生代码反过来调Python函数，就会每个元素往返一次边界。出现这种结构，说明边界划错了地方。
  • 把边界做成纯函数而不是状态 — 在原生一侧留下长期存活的可变状态，所有权问题与线程安全问题会同时找上门。
  • 不要把边界放在接口频繁变动的地方 — 把每周都改签名的函数下沉为原生，就得每周重跑一遍构建矩阵。
  • 不要删掉纯Python实现 — 并行维护两套实现的成本，远小于失去回退能力的风险。

同一个问题在另一种语言组合下的讨论，整理在从Go迁移到Rust那一篇。那边是两种编译语言之间的取舍，判断轴不同，但共存模式与反面信号是完全重合的。

5. PyO3与maturin - 用代码把边界画出来

决定拆出热点路径之后，实际用到的工具是PyO3与maturin。PyO3是连接Rust与Python的绑定，maturin负责把成果构建成Python wheel。下面是PyO3官方仓库最新发布的0.29系列的声明式模块写法。PyO3 0.29支持CPython 3.9以上，Rust最低支持版本为1.83。

# Cargo.toml
[package]
name = "hotpath"
version = "0.1.0"
edition = "2021"

[lib]
name = "hotpath"
crate-type = ["cdylib"]

[dependencies]
pyo3 = "0.29.0"

// src/lib.rs
#[pyo3::pymodule]
mod hotpath {
    use pyo3::prelude::*;

    /// 整个数组一次性接收，一次处理完。
    /// 不按元素逐个调用，这就是这套设计的全部。
    #[pyfunction]
    fn clip_and_scale(values: Vec<f64>, lo: f64, hi: f64, k: f64) -> PyResult<Vec<f64>> {
        Ok(values
            .into_iter()
            .map(|v| v.clamp(lo, hi) * k)
            .collect())
    }
}

maturin new -b pyo3 hotpath   # 生成项目骨架
cd hotpath
maturin develop               # 直接装进当前虚拟环境（供反复开发）
maturin build --release       # 在target/wheels生成发布用wheel

Python一侧要做的是用同一个名字包住原生实现与纯实现，并且保证能退回去。也就是把前面见过的环境变量开关自己做一份。

# myapp/kernel.py
import os

from myapp import kernel_py   # 纯Python原始实现

_impl = kernel_py

if os.environ.get("MYAPP_NATIVE", "1") != "0":
    try:
        import hotpath as _native
        _impl = _native
    except ImportError:
        pass   # 在没有wheel的平台上也照样能跑

clip_and_scale = _impl.clip_and_scale

这里吞掉ImportError是关键。在没有原生扩展的平台上包也要能装上并运行，发布才会简单。备好这个结构，怀疑性能回归时就能靠一个环境变量比较两套实现，出事故时也能不重新发布就退回去。

6. 要把多少东西下沉到原生 - 判断表

「这个函数要不要下沉为原生」不是靠感觉决定的事。按顺序过下面六个条件，并且守住只要有一条为否就不下沉这条规则，在实务中最经得起时间。

确认项目通过阈值为否时的处方
在整体执行时间中的占比按自身时间计20%以上先去看别处
每次调用的工作量单次调用有毫秒级以上的计算按批打包以减少调用次数
跨边界数据的形态标量 · 扁平数组 · 字节串先把接口拍平
接口变更频率每季度1次以下推迟到设计定型为止
能读懂并修改Rust的人数2名以上先备人。只有1名就是组织债务
保留纯Python方案始终保留 + 回退开关退不回去就先别放进去

第五项经常被忽视。扩展模块在做它的人离开的那一刻就变成黑箱。只剩Python开发者的团队里，Rust扩展模块出了bug，选项只有两个：「找一个能修的人」和「退回纯Python」。守住第六项，后者就是30秒的活；不守，就是几周的事故。

反过来，可以考虑全面移植的条件也整理一下，且只有四条全部满足时：产物本身就是发布单元的工具或库核心、外部接口窄而稳定、执行时间的大部分是CPU计算、团队里已经有把Rust当主力语言的人。

7. 用Rust重写的那些工具究竟证明了什么

Python生态里常被当作Rust重写成功案例引用的项目有几个。只照搬各自官方文档实际主张的数值，如下。

项目官方资料所述内容对象领域
ruff仓库明确宣称比既有linter（Flake8）与formatter（Black）快10~100倍。用Rust编写，MIT静态分析工具
uv无缓存时比pip及pip-tools快8~10倍，热缓存下80~115倍。创建虚拟环境比python -m venv约快80倍，比virtualenv快7倍包管理工具
pydantic官方文档写明核心校验逻辑由Rust编写，因而跻身Python中最快的数据校验库之列库核心
CPython本身官方博客公告，Rust for CPython计划以3.16为目标，正在推进用Rust实现一个扩展模块的概念验证并准备PEP解释器内部

这份清单里比倍数更重要的是共同点。四个都不是业务应用，而是开发工具、库的校验核心，或者解释器内部。它们共享三个性质。

  • 接口窄且长期稳定 — linter的输入是源文件，输出是诊断列表。这份契约好几年没变过。
  • 执行时间的大部分是CPU计算 — 解析、规则匹配、依赖求解，全都是解释器原本烧掉的时间。
  • 发布单元本来就是二进制wheel — 用户不需要知道源码是什么语言写的，有各平台的wheel就够了。

反过来说，不满足这三个条件的代码，没有理由期待同样的结果。一个请求要往返数据库三次的Web应用，在三个条件上都站在对面。引用成功案例时，必须连同该案例属于哪个领域一起看。

顺带一提，2026年也出现了不少用AI智能体把大型代码库整体搬到Rust的尝试，什么被证明了、什么没被证明，在用Rust重写Git的尝试里另作讨论。要点是一样的：搬过去了和被验证了是两句不同的话。

8. 另一侧的成本 - 学习曲线 · 构建时间 · 生态空缺

转换的讨论大多只算收益就结束了。因为另一侧的成本不是在引入时，而是从半年后开始结账。按项目分开看。

8.1 构建时间是被测量过的问题

Rust官方博客公开的2025年编译器性能调查收到了3,700份以上的回答，整体满意度报告为满分10分中6分。值得注意的数字如下。

  • 已停止使用Rust的回答者中约45%把编译时间过长列为停用理由之一。
  • 55%回答改完代码后重新构建要等10秒以上。瓶颈被归纳为三类：工作区变更引发的不必要重建、缓慢的链接阶段、单个crate内部的增量编译。
  • 约33%把等待IDE内联注解视为很大的障碍，35%以上把IDE与Cargo互相阻塞视为大问题。
  • 1,495名CI用户中约25%把CI构建性能列为大问题，而其中约36%在CI里完全没有使用缓存。
  • 全体回答者中约42%表示从未尝试过任何一种构建性能改善手段。

最后两项值得反过来读。相当一部分抱怨来自尚未动手的余地。在没做缓存、换链接器、拆分工作区这些基本措施的情况下就断定「Rust很慢」，是错误的结论。不过团队里要是没人能做这些措施，实质成本还是照旧。

8.2 发布多出一个维度

纯Python包一个wheel就完事。原生扩展一挂上去，就需要平台 × 架构 × Python版本相乘那么多次构建。用稳定ABI可以砍掉Python版本这一轴，代价是可用API受限。再加上交叉编译、签名、内部镜像登记。这项工作不是做一次就完，而是每出一个新Python版本就要重来。

8.3 人是最贵的

  • 能读的人和能修的人不是一回事 — 碰上所有权与生命周期错误能自己解决的，才算能修的人。
  • 必须进on-call轮值 — 半夜那个模块炸了，能应对的只有一个人，那个模块就是单点故障。
  • 会出现评审瓶颈 — 能评审Rust代码的只有一个人，那个人的休假就等于发布停摆。
  • 招聘条件会变 — 一个Python岗位变成同时要求Python与Rust的岗位，候选池会变小，周期会变长。

8.4 生态空缺

Python这边已经有的东西，Rust那边可能没有，或者有但成熟度不足：领域专用的数值库、特定厂商的客户端SDK、公司内部标准的日志与追踪层等等。只拆热点路径这条路更有利的理由也在这里。边界划得窄，需要的Rust库就同样少。以内存安全为由推动重写的主张及其反驳，在内存安全绝对主义之争里另作整理。

9. 如何验证生成出来的Rust代码

不管是工具生成的还是人写的，两套实现是否真的给出同样答案必须单独证明。编译成功什么都不保证。整理成可执行的形式，是三个步骤。

9.1 差分测试 - 同一份输入，两套实现

# tests/test_parity.py
import math
from hypothesis import given, settings, strategies as st

from myapp import kernel_py            # 纯Python原版
import hotpath                          # 原生实现

FINITE = st.floats(allow_nan=False, allow_infinity=False, width=64)

@settings(max_examples=1000)
@given(st.lists(FINITE, max_size=4096), FINITE, FINITE, FINITE)
def test_same_output(values, lo, hi, k):
    if lo > hi:
        lo, hi = hi, lo
    expected = kernel_py.clip_and_scale(values, lo, hi, k)
    actual = hotpath.clip_and_scale(values, lo, hi, k)
    assert len(expected) == len(actual)
    for a, b in zip(expected, actual):
        assert math.isclose(a, b, rel_tol=1e-12, abs_tol=0.0)

比较浮点数时一旦引入容差，就必须在文档里写明验证的是「近似」而不是「等价」。像会计或结算这种最后一位有意义的领域，与其设容差，不如把计算搬到整数或十进制类型上。

9.2 边界值不会被随机抽到

属性测试能拓宽覆盖面，但最危险的输入大体上抽不到。要用固定清单另行管理。

EDGE_CASES = [
    [],                       # 空输入
    [0.0], [-0.0],            # 0与负0的位模式不同
    [float("inf"), float("-inf")],
    [float("nan")],           # 不等于自身。排序与去重会分叉
    [1e308, -1e308],          # 溢出前一步
    [1.0] * 1_000_000,        # 能暴露跨边界复制成本的规模
]
  • 整数溢出 — Python整数是任意精度，Rust的i64是定宽。release构建下溢出会回绕，悄悄变成错值。务必确认要搬的函数会不会收到大整数。
  • 取余运算的符号 — Python的%跟随除数符号，Rust的%跟随被除数符号。-7 % 3在Python里是2，在Rust里是-1。要与Python一致就用rem_euclid。
  • 排序稳定性 — 确认两个元素键相同时原顺序是否保持。稳定性不同，结果列表的顺序就会分叉。
  • 字典插入顺序 — Python字典保持插入顺序，Rust的哈希映射不保持。下游有依赖顺序的消费者，就会出事故。
  • Unicode长度 — Python字符串的长度是码点数，Rust的len()是字节数。把切片索引原样搬过去就会崩。
  • 异常的类型与消息 — 调用方若按异常类型分支，连类型都必须一致。也要确认有没有代码依赖消息字符串。

9.3 回退路径要在发布前试一遍

上一节做的环境变量开关，不是做出来就完事了。每次发布都要走纯Python路径把全部测试再跑一遍，那条路径才算被保证还活着。实务中常见的失败是：开关做好后一年没用过，等到真正需要的那一刻，纯实现的接口早就对不上了。

验证项目方法通过标准
结果等价性差分测试 + 属性测试随机1,000件以上，不一致0件
边界值固定清单 + 检查两种语言的规则差异清单全数通过，连异常类型也一致
性能代表性工作负载基准3次取中位达不到目标倍数就重审边界设计
回退路径关掉原生后跑全部测试每次发布都确认通过
wheel发布在全部支持平台上确认可导入不支持的平台上也能安装并运行

10. GIL正在消失这个变量

如果是为了并行性而考虑Rust，那么必须把前提正在改变这件事算进来。CPython从3.13起提供关掉GIL的free threading构建。不过它不是免费的。官方文档写明free threading构建比默认构建有额外开销，按pyperformance基准，平均开销在macOS aarch64上约1%、在x86-64 Linux上约8%这个范围。

另外还有一条做扩展模块的人必须知道的条款。官方文档写着，一部分带扩展模块的第三方包可能尚未为free threading构建做好准备，此时会重新打开GIL。导入一个没有声明支持free threading的C-API扩展模块，GIL就会自动被重新打开并输出警告。

  • 我的扩展模块可能杀掉别人的并行性 — 一个没声明支持的扩展就能让整个进程的GIL复活。要发布扩展模块，这条声明就不是可选项。
  • 目的是并行化的话，值得换个顺序 — 在换语言之前，先量一量现有代码在free threading构建上跑成什么样，成本要低得多。
  • 单线程开销因工作负载而异 — 上面那个区间是基准测试套件的平均值，必须用自己的工作负载亲自测。
  • 解释器自己也在引入Rust — 官方博客称Rust for CPython计划以3.16为目标，正在推进用Rust实现一个扩展模块的概念验证并准备PEP。长期看，两种语言的接触面会变宽。

11. 判断是否引入的流程

最后整理成可以搬走的形式。照这个顺序走下来，多数情况在第3步或第4步就有结论。

  1. 固定一个代表性工作负载 — 必须取自真实生产流量。合成基准会让结论变得乐观。
  2. 把墙钟时间与CPU时间分开测 — 两者差得大，原因就是等待，换语言到此为止。
  3. 按自身时间挑出靠前的函数 — 按累计时间看，只会看见调用栈上层。
  4. 用靠前函数的合计占比算出上限 — 不足40%就在这里中止，该去修别的地方了。
  5. 先看算法与数据结构 — 只要还有能降阶的改动，那件事永远优先。
  6. 确认是不是已经下沉到C的部分 — 时间跑在数值库内部的话，几乎没有可回收的余地。
  7. 把边界候选函数的接口拍平 — 这项工作在没有Rust的纯Python状态下先做完。
  8. 用静态分析工具量一量子集契合度 — 拒绝率高就放弃自动转换，只评估手工移植。
  9. 只搬占比最大的那一个函数并实测 — 就一个。同时搬好几个，就不知道是哪个起了作用。
  10. 备齐差分测试与回退路径之后再发布 — 只在确认回退开关确实可用之后才放出去。
  11. 用运营指标再测一次 — 不看基准，看真实的延迟分布。尾延迟没降下来，就说明还有别的原因。
  12. 没效果就退回去 — 因为舍不得已经做出来的东西而继续留着，是最贵的选择。

结论：工具只能显示边界，不能替你决定边界

Rextio这类工具真正提供的最大价值，很可能不是转换本身而是诊断。光是告诉你代码库有百分之几是能被静态固定的形态、哪些函数为什么被拒绝，就已经是判断材料。反过来，把工具生成的产物原样放进生产这种设想，至少对alpha阶段的工具来说不在考虑范围内。

把本文反复说的话压成一句就是：实务的答案在全部重写与什么都不做之间，而这个答案由边界划在哪里决定。线划得好，搬走5%的代码就解决掉性能问题的大部分，剩下95%照样享受Python的生产力。线划错了，就得到一个只把两种语言的缺点凑在一起的系统：构建慢、能修的人只有一个、还退不回去。

还有，不要把顺序颠倒。先剖析，其次算法，语言放最后。守住这个顺序，多数情况下你会发现根本轮不到语言这一步——而这既是这类评估最常见的结论，也是最便宜的结论。
