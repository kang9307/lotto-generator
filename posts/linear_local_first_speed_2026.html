Linear는 어떻게 밀리초 반응속도를 내는가 - local-first와 인브라우저 DB 2026

왜 어떤 웹앱은 네이티브처럼 즉각적인가 - 동기화 엔진의 비밀

2026-06-09 IT/기술

서론: 클릭과 동시에 끝나는 앱 - 그 비밀은 무엇인가

이슈 트래커 Linear를 처음 써 본 개발자들이 공통적으로 내뱉는 말이 있습니다. "왜 이렇게 빠르지?" 이슈 상태를 바꾸고, 우선순위를 끌어 옮기고, 필터를 거는 모든 동작이 클릭하는 순간 끝납니다. 로딩 스피너도, 잠깐의 멈춤도 없습니다. 마치 웹앱이 아니라 잘 만든 네이티브 데스크톱 프로그램을 다루는 느낌입니다. 보고에 따르면 Linear는 대부분의 상호작용을 수 밀리초 안에 처리하고, 많은 화면이 50ms 이내에 그려집니다.

이 속도는 우연이 아니라 의도된 아키텍처의 결과입니다. 핵심은 local-first(로컬 우선)라는 설계 철학과, 그것을 떠받치는 인브라우저 데이터베이스 그리고 동기화 엔진(sync engine)입니다. 이 글은 'Linear는 어떻게 밀리초 반응속도를 내는가'라는 질문을 출발점으로 삼아, local-first가 무엇인지, 기존의 서버 왕복 방식과 무엇이 다른지, 옵티미스틱 업데이트와 동기화 엔진과 CRDT 충돌 해결이 어떻게 맞물리는지, 그리고 이 접근을 내 프로젝트에 가져올 때의 트레이드오프는 무엇인지까지 차분히 풀어내려 합니다. 결론을 먼저 말하면, Linear의 빠름은 '서버를 더 빠르게 만든 것'이 아니라 '서버를 사용자의 체감 경로에서 빼낸 것'입니다.

1. 기존 웹앱은 왜 느리게 느껴지나 - 서버 왕복의 함정

비밀을 이해하려면 먼저 '느림'의 정체부터 알아야 합니다. 전형적인 웹 애플리케이션은 요청-응답(request-response) 모델 위에서 동작합니다. 사용자가 버튼을 누르면, 브라우저가 서버에 요청을 보내고, 서버가 데이터베이스를 조회·수정한 뒤 응답을 돌려주고, 그제야 화면이 갱신됩니다.

[전통적 요청-응답 흐름]

사용자 클릭
   │  (네트워크 왕복: 수십~수백 ms)
   ▼
서버 처리 → DB 조회/수정
   │  (네트워크 왕복)
   ▼
응답 도착 → 화면 갱신   ← 사용자는 그동안 '기다린다'

문제는 이 모든 과정의 한가운데에 네트워크 지연(latency)이 끼어 있다는 점입니다. 같은 도시의 데이터센터라도 왕복에 수십 밀리초가 들고, 대륙을 넘으면 수백 밀리초로 불어납니다. 거기에 서버 처리 시간과 렌더링까지 더해지면, 단순한 클릭 하나가 체감상 '버벅임'으로 변합니다. CPU나 데이터베이스가 느려서가 아니라, 빛의 속도와 지구의 크기라는 물리적 한계가 사용자 경험을 짓누르는 것입니다.

전통적 최적화는 이 왕복을 '더 빠르게' 만들려 합니다. 캐시를 깔고, CDN을 붙이고, 쿼리를 튜닝합니다. 모두 유효하지만 본질적 한계가 있습니다. 네트워크가 경로에 남아 있는 한, 사용자는 항상 어느 정도는 기다려야 합니다. local-first는 발상을 뒤집습니다. 왕복을 빠르게 만드는 대신, 사용자의 체감 경로에서 왕복 자체를 없애는 것입니다.

2. local-first란 무엇인가 - 데이터를 사용자 곁에 둔다

local-first(로컬 우선)는 2019년 Ink & Switch 연구진이 정리한 소프트웨어 설계 원칙입니다. 한 문장으로 요약하면 "데이터의 1차 사본을 사용자의 기기에 두고, 클라우드는 백업과 동기화의 보조 역할로 둔다"는 것입니다. 기존 클라우드 앱이 '데이터는 서버에 있고 사용자는 그 창을 들여다본다'는 구조라면, local-first는 '데이터는 내 기기에 있고 서버는 그 사본을 거든다'는 구조입니다.

Ink & Switch는 local-first가 추구하는 이상을 일곱 가지로 제시했는데, 본질은 크게 두 축입니다. 첫째는 속도와 가용성입니다. 데이터가 로컬에 있으니 읽기·쓰기가 즉각적이고, 네트워크가 끊겨도 앱이 동작합니다. 둘째는 소유권과 통제입니다. 사용자가 자기 데이터에 대한 1차 권한을 갖고, 서비스가 사라져도 데이터는 남습니다.

local-first의 핵심 전환은 단순하다. "서버에 묻고 기다리는" 앱에서 "이미 가진 데이터로 즉시 답하고 나중에 맞추는" 앱으로 가는 것이다.

Linear는 이 원칙을 협업 도구의 맥락에 맞게 실용적으로 구현한 대표 사례입니다. 순수한 학술적 local-first가 아니라, 빠른 반응성과 멀티 디바이스 동기화를 동시에 잡기 위해 인브라우저 DB와 정교한 동기화 엔진을 결합한 '엔지니어링된 local-first'에 가깝습니다.

3. 인브라우저 데이터베이스 - 브라우저 안의 진짜 DB

local-first가 성립하려면 데이터를 둘 '로컬 저장소'가 필요합니다. Linear를 비롯한 현대 웹앱이 사용하는 것이 바로 브라우저에 내장된 IndexedDB입니다. IndexedDB는 단순 키-값 캐시가 아니라, 인덱스·트랜잭션·대용량 저장을 지원하는 브라우저 내장 데이터베이스입니다.

보고와 리버스 엔지니어링 분석에 따르면 Linear의 데이터 흐름은 대략 다음과 같습니다.

  • 부트스트랩(bootstrap): 사용자가 처음 접속하면 서버의 /sync/bootstrap 엔드포인트가 화면을 그리는 데 필요한 데이터를 한 번에 내려줍니다. 이 데이터는 IndexedDB에 저장됩니다.
  • 메모리 객체 풀(object pool): 이후 앱은 서버가 아니라 IndexedDB에서 데이터를 읽어, 메모리상의 거대한 객체 맵(UUID로 조회하는 객체 풀)에 올립니다. 화면은 이 인메모리 객체를 바라봅니다.
  • 지연 하이드레이션(lazy hydration): 가장 무거운 테이블(이슈·코멘트 등)은 처음부터 전부 로드하지 않고, 실제로 접근할 때 필요한 속성만 채웁니다. 데이터 단위의 코드 스플리팅에 가깝습니다.

핵심은 화면이 '서버'가 아니라 '내 브라우저 안의 메모리 객체'를 바라본다는 점입니다. 데이터가 이미 손안에 있으니, 읽기는 네트워크가 아니라 메모리 접근 속도로 끝납니다. 이것이 50ms 이내 렌더링의 1차 비결입니다.

4. 옵티미스틱 업데이트 - 먼저 보여 주고 나중에 맞춘다

읽기가 빠른 것은 이해됩니다. 그렇다면 '쓰기'는 어떻게 즉각적일까요? 서버에 저장하려면 어차피 네트워크를 타야 하지 않을까요? 여기서 등장하는 것이 옵티미스틱 업데이트(optimistic update)입니다.

옵티미스틱 업데이트의 발상은 이름 그대로 '낙관적'입니다. 사용자가 이슈 상태를 'In Progress'로 바꾸면, 앱은 서버 응답을 기다리지 않고 그 변경을 로컬 객체에 즉시 적용하고 화면을 갱신합니다. 동시에 그 변경을 서버로 보내는 요청을 백그라운드 큐에 넣습니다. 사용자는 이미 결과를 보고 다음 작업으로 넘어갑니다.

[옵티미스틱 업데이트 흐름]

사용자 클릭
   │
   ├─▶ 로컬 객체 즉시 변경 → 화면 갱신 (수 ms, 사용자는 여기서 끝)
   │
   └─▶ 변경을 트랜잭션 큐에 적재 → 백그라운드로 서버 전송
                                      │
                          성공 → 확정(commit)
                          실패 → 롤백 또는 재시도

대부분의 요청은 성공하므로, 이 낙관은 거의 항상 옳습니다. 만에 하나 서버가 거부하면(권한 문제, 충돌 등) 앱은 그 변경을 되돌리거나 재시도합니다. 중요한 설계 포인트는 변경을 IndexedDB의 내구성 있는 트랜잭션 큐에 먼저 적어 둔다는 것입니다. 그래서 전송 도중 브라우저를 닫거나 네트워크가 끊겨도 변경이 사라지지 않고, 연결이 복구되면 큐가 마저 전송됩니다.

5. 동기화 엔진 - 여러 기기를 하나처럼 맞추기

로컬에서 즉시 반영된 변경은, 결국 서버를 거쳐 같은 워크스페이스의 다른 사용자·다른 기기로 퍼져야 합니다. 이 일을 담당하는 것이 동기화 엔진(sync engine)입니다. 동기화 엔진은 local-first 앱에서 가장 어렵고 가장 가치 있는 부품으로 꼽힙니다.

Linear의 동기화 엔진을 분석한 자료들을 종합하면 작동 방식은 다음과 같습니다.

  • 트랜잭션 단위의 변경: 객체의 생성·수정·삭제·보관 같은 모든 변경은 '트랜잭션'으로 캡슐화됩니다. 이 트랜잭션이 서버로 전송되어 실행됩니다.
  • 델타 브로드캐스트: 서버는 실행 결과를 전체 데이터가 아니라 변경분(delta)만 추려, WebSocket을 통해 연결된 다른 클라이언트들에게 실시간으로 내려보냅니다. 네트워크에 흐르는 양이 작아 전파가 빠릅니다.
  • 증분 동기화: 다른 기기는 마지막으로 받은 시점 이후의 델타만 받아 로컬 DB를 갱신합니다. 매번 전체를 다시 받지 않으므로 효율적입니다.

즉, 무거운 데이터는 클라이언트의 IndexedDB에 머물고, 네트워크에는 '무엇이 바뀌었는가'라는 작은 델타만 오갑니다. 서버는 진실의 원천(source of truth)이자 변경의 중계자 역할을 하되, 사용자의 한 동작 한 동작을 가로막는 관문에서는 물러나 있습니다. 이 구조는 우리가 이전에 다룬 UUID 기본키와 분산 환경의 식별자 설계와도 맞닿아 있는데, 클라이언트가 먼저 ID를 만들 수 있어야 옵티미스틱 생성이 매끄럽기 때문입니다.

6. 충돌은 어떻게 해결하나 - CRDT와 병합 전략

여러 사람이 같은 데이터를 동시에 바꾸면 무슨 일이 벌어질까요? A가 오프라인에서 이슈 제목을 고치고, 같은 시간 B가 온라인에서 같은 이슈의 우선순위를 바꿨다면, 두 변경을 어떻게 합칠 것인가 — 이것이 충돌 해결(conflict resolution)의 문제입니다.

가장 강력한 도구가 CRDT(Conflict-free Replicated Data Type, 충돌 없는 복제 데이터 타입)입니다. CRDT는 여러 복제본에서 일어난 동시 변경이 중앙 조정 없이도 자동으로 같은 결과로 병합되도록 수학적으로 설계된 데이터 구조입니다. 각 변경에 고유 식별자와 순서 정보를 부여하기 때문에, 한 사용자가 문서 앞에 글자를 넣고 다른 사용자가 뒤에 글자를 넣어도 두 편집이 충돌 없이 합쳐집니다. Ink & Switch가 만든 Automerge가 대표적인 구현입니다.

다만 모든 충돌에 CRDT가 필요한 것은 아닙니다. 실무에서는 작업 특성에 맞춰 더 단순한 전략을 섞어 씁니다.

전략 방식 적합한 경우
마지막 쓰기 우선(LWW) 타임스탬프가 늦은 변경이 이긴다 상태값·플래그처럼 단일 필드
커스텀 병합 필드별 규칙을 직접 정의 도메인 의미가 명확한 데이터
CRDT 동시 편집을 자동 병합 공동 텍스트·리스트 편집

이슈 트래커 같은 앱은 대부분의 필드가 '상태', '담당자', '우선순위'처럼 단일 값이라, 마지막 쓰기 우선이나 필드별 병합으로 충분한 경우가 많습니다. 텍스트 공동 편집처럼 진짜 동시 편집이 잦은 곳에만 CRDT의 비용을 치르는 것이 현실적인 선택입니다.

7. 왜 '빠르게 느껴지나' - 지각 성능의 심리학

여기서 한 걸음 물러나 중요한 구분을 해야 합니다. 실제 성능(actual performance)과 지각 성능(perceived performance)은 다릅니다. local-first가 진짜로 바꾸는 것은 후자입니다.

인간의 인지는 100ms 안팎을 '즉각적'으로 느낍니다. 이 경계 안에서 화면이 반응하면 사용자는 '내가 시스템을 직접 조작하고 있다'는 직접 조작감(direct manipulation)을 얻습니다. 반대로 0.1초만 넘어가도 미세한 끊김을 인지하기 시작하고, 1초가 넘으면 주의가 끊깁니다. local-first는 옵티미스틱 업데이트로 사용자의 모든 동작을 이 100ms 경계 안쪽으로 끌어넣습니다.

흥미로운 점은, 서버 동기화는 여전히 백그라운드에서 수백 밀리초가 걸린다는 사실입니다. 그러나 사용자는 그 지연을 '체감하지 않습니다'. 왜냐하면 그 시간 동안 이미 다음 작업을 하고 있기 때문입니다. 지연을 없앤 것이 아니라, 지연을 사용자가 보지 않는 시간대로 옮긴 것입니다. 이것이 Linear가 '네트워크보다 빠를 수 없는데도' 네트워크보다 빠르게 느껴지는 역설의 정체입니다.

8. 트레이드오프 - 공짜 점심은 없다

여기까지 들으면 모든 앱을 local-first로 만들어야 할 것 같습니다. 그러나 균형을 위해 비용을 분명히 짚어야 합니다. local-first의 속도는 상당한 복잡도를 대가로 얻은 것입니다.

  • 구현 난도: 클라이언트에 데이터베이스, 동기화 프로토콜, 충돌 해결, 트랜잭션 큐를 직접 만들어야 합니다. Linear조차 동기화 엔진을 자사 역사상 가장 어려운 기술 투자 중 하나로 꼽았습니다.
  • 스키마 변경과 마이그레이션: 데이터가 수많은 클라이언트의 IndexedDB에 흩어져 있으므로, 데이터 모델을 바꿀 때 구버전 클라이언트와의 호환을 신경 써야 합니다.
  • 보안과 권한: 데이터가 클라이언트로 내려오는 만큼, '누가 무엇을 볼 수 있는가'를 부트스트랩·동기화 경로에서 정교하게 통제해야 합니다.
  • 초기 용량과 메모리: 부트스트랩으로 많은 데이터를 내려받고 메모리에 올리므로, 워크스페이스가 커질수록 초기 로딩과 메모리 관리가 과제가 됩니다.

따라서 오프라인 동시 편집이 드물고 화면마다 데이터가 크게 다른 단순 CRUD 앱이라면, local-first의 효용 대비 비용이 클 수 있습니다. 운영 도구나 백오피스처럼 자주 쓰는 핵심 화면이 좁고 반복적인 경우에 투자 대비 효과가 가장 큽니다. 이런 '도구의 빠름'이 생산성에 주는 효과는 터미널 성능과 개발자 생산성에서 다룬 논리와 같은 결을 갖습니다.

9. 같은 흐름의 도구들 - local-first 생태계

Linear가 불씨를 댕긴 이 방향은 2026년 현재 하나의 생태계로 자라고 있습니다. 직접 만들지 않아도 비슷한 경험을 얻도록 돕는 프레임워크와 동기화 엔진이 늘었습니다.

  • 동기화 엔진형 프레임워크: 클라이언트 DB와 서버 동기화를 패키지로 제공해, 옵티미스틱 업데이트·델타 동기화를 직접 구현하지 않아도 되게 합니다.
  • CRDT 라이브러리: Automerge, Yjs 같은 라이브러리로 공동 편집의 자동 병합을 손쉽게 붙일 수 있습니다.
  • 인브라우저 DB 도구: IndexedDB 위에 쿼리·반응형 구독을 얹어 주는 래퍼들이 클라이언트 데이터 계층을 단순화합니다.

공통 메시지는 분명합니다. '서버를 사용자의 체감 경로에서 빼낸다'는 발상이 더는 Linear만의 비기가 아니라, 일반 개발자도 손에 쥘 수 있는 도구로 내려오고 있다는 것입니다. 데이터를 어디에 두고 어떻게 동기화하느냐에 대한 더 넓은 설계 고민은 파일 SDK와 통합 블롭 스토리지의 관점과도 이어집니다.

10. 내 프로젝트에 적용하기 - 점진적 경로

모든 것을 한 번에 local-first로 다시 쓰는 것은 위험합니다. 다음의 점진적 단계를 권합니다.

  1. 병목 식별: 사용자가 가장 자주 하고, 가장 '느리다'고 느끼는 상호작용부터 찾습니다. 모든 화면이 아니라 한두 핵심 동작이 출발점입니다.
  2. 옵티미스틱 업데이트부터: 전면적 local-first 이전에, 자주 쓰는 변경에 옵티미스틱 업데이트와 로컬 캐시만 붙여도 체감이 크게 바뀝니다.
  3. 내구성 있는 큐: 전송 실패와 오프라인을 대비해, 변경을 로컬에 먼저 적어 두고 재시도하는 큐를 둡니다.
  4. 충돌 전략 선택: 대부분 필드는 마지막 쓰기 우선으로 시작하고, 진짜 동시 편집이 필요한 곳에만 CRDT를 도입합니다.
  5. 관측과 폴백: 동기화 실패·롤백 빈도를 측정하고, 낙관이 틀렸을 때 사용자에게 알리는 명확한 폴백 UI를 마련합니다.

핵심 원칙은 'local-first는 전부 아니면 전무가 아니다'입니다. 옵티미스틱 업데이트라는 가장 작은 조각부터 도입해 체감을 확인하고, 필요와 비용을 저울질하며 단계적으로 깊이를 더하는 것이 안전합니다.

11. 결론 + 즉시 적용 가능한 3가지

'Linear는 어떻게 밀리초 반응속도를 내는가'에 대한 답은 명료합니다. 서버를 더 빠르게 만든 것이 아니라, 데이터를 사용자 곁(브라우저)에 두고, 모든 동작을 로컬에서 즉시 처리한 뒤, 서버 동기화를 사용자가 보지 않는 백그라운드로 밀어낸 것입니다. 인브라우저 DB가 데이터를 손안에 두고, 옵티미스틱 업데이트가 쓰기를 즉각적으로 만들며, 동기화 엔진과 충돌 해결이 여러 기기를 조용히 하나로 맞춥니다. 빠름의 정체는 기술의 마법이 아니라 '네트워크를 체감 경로에서 빼낸다'는 설계 결정이었습니다.

당장 적용할 수 있는 세 가지로 마무리합니다.

  1. 지각 성능을 측정하라. 서버 응답 시간이 아니라 '클릭에서 화면 변화까지'의 시간을 측정하세요. 사용자가 느끼는 속도는 그 숫자이지 백엔드 지연이 아닙니다.
  2. 가장 잦은 동작에 옵티미스틱 업데이트를 붙여라. 전면 재설계 없이도, 핵심 상호작용 한두 개를 로컬 즉시 반영으로 바꾸는 것만으로 체감이 달라집니다.
  3. 충돌은 단순하게 시작하라. 처음부터 CRDT를 깔지 말고, 마지막 쓰기 우선으로 출발해 실제 동시 편집이 문제가 되는 지점에만 비용을 투입하세요.
