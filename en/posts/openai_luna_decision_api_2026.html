This article relies on The New Stack report on the OpenAI Decision API by Frederic Lardinois, published on September 29, 2026, cross-checked against The Decoder DevDay coverage of the same day. Values that are not in those reports are not invented, and anything computed from two reported values is marked “derived”. The per-call price, the limit on candidates per request and whether developers can tune the model on their own data have not been disclosed, and this article leaves those cells empty as well.

What was announced — the scope the report covers

On September 29, 2026, at its annual developer event DevDay, OpenAI unveiled an API built on its Luna model. The body of The New Stack report calls it the Decisions API, while the headline and some sentences call it the Decision API. This article uses Decision API throughout. The outline the report gives is short. On top of the small Luna model, it returns a confidence score for each predefined candidate answer; the 150-millisecond response time is OpenAI description; it is in limited preview now; and broad release was announced for a few days later.

The report also explains why so little has been shared. It says the API is likely a reaction to TypeSafe and Jev, that OpenAI probably rushed the announcement ahead of DevDay, and that for now this is all OpenAI is sharing. That is the reporter estimate. The same report quotes an OpenAI spokesperson saying the company plans to share more “at broad rollout”. Most of the items this article lists as “not yet known” are items that may be filled in at that point.

Combining The New Stack and The Decoder, the outline of the announcement comes down to six lines.

  • Event and date. OpenAI DevDay on Tuesday, September 29, 2026. The report was published on the afternoon of the same day.
  • Base. Luna. The report introduces it as the smallest and most affordable model in OpenAI current lineup, and The Decoder describes it as a specialized version of GPT-6 Luna.
  • Input. A question, candidate answers and context. The Decoder says the context can be given as text or images.
  • Output. A confidence score for each candidate answer. It does not return prose.
  • Speed. 150 milliseconds as stated by OpenAI. The report adds that GPT-6 Luna would take 1.6 seconds for the same job.
  • Status. Limited preview. Broad release was announced for “the coming days”.

The naming of the model also needs care. The report names the base model as Luna and the speed baseline as GPT-6 Luna. The report does not explain whether the two names point to the same model, or whether the “specialized version” shares weights with the regular Luna. This article follows the notation of the source and does not assert that the two are the same.

The background of the Luna lineup itself and its price structure are covered in the GPT-6 Sol and Luna release article. This article concentrates only on the new call shape built on Luna.

The “decision model” call shape — how it differs from a chat model

The report describes a decision model as explicitly not a chat model, but one that returns a set of predefined answers with confidence scores. The trigger it cites for the popularity of this type is TypeSafe Jev. What Jev is, how it is called and what an independent measurement found are in the Jev evaluation article, and a way to imitate the same shape with the token probabilities of a general-purpose model is in the Jev-style wrapper article. This article does not repeat those explanations and keeps to the OpenAI call shape.

The report explains the gap this call is meant to fill by comparing it with two existing approaches.

  • A chat model with a carefully worded prompt. You ask it to pick one item from a list and, if you are lucky, read the token probabilities to get something resembling a confidence score. The report says the confidence of a regular LLM is often a rough guess and that it spends quite a few tokens to get there.
  • Training a small classifier. Fast and cheap, but it needs labeled data and a retraining run every time the label set changes.
  • A decision model. In the report wording it sits between the two. It takes new labels in the prompt and still returns a score a developer can work with.

The report also points to the Moderation API. OpenAI Moderation API has long returned per-category scores instead of prose, so the concept is not entirely new. The difference is who sets the categories. In the Moderation API OpenAI presets them, and in the Decision API the developer sets them. That single line summarizes the character of this API most briefly: the cells of the scoring rubric are written by the developer, and the scoring is done by a small model.

In this article reading, because the output is a score over predefined candidates, the parsing step that extracts an answer from free-form text disappears from the call structure. The wrapper article above covered, as background, that attaching a regular expression or a JSON parser to free-form output carries a risk of parse failures. This is, however, an inference from the call shape, and the report does not specify the output format of OpenAI.

150 ms vs 1.6 s — the structure of the claim and the missing conditions

The sentence in the report that carries the speed figure runs like this: OpenAI says its model returns results in 150 milliseconds, compared to GPT-6 Luna, which would take 1.6 seconds. Taking the sentence apart shows that the two figures have different standing. The 150 ms is a value “OpenAI says”. The 1.6 s is phrased in the conditional (“would take”), so the sentence alone does not settle whether it is a measured value or an expected one. The Decoder relays the same claim as “OpenAI says the Decisions API makes decisions ten times faster than GPT-6 Luna does through the regular API”.

“About 10 times” is the division of these two values. Dividing 1.6 by 0.15 gives about 10.7 (derived). The report and The Decoder both state only “ten times” or thereabouts, and since each input may be rounded, there is no reason to read the digits after the decimal point as a separate fact. More important is the condition under which the inputs to that division were obtained. The following conditions are not stated in the report or in The Decoder.

  • The statistic. Whether it is the median, the mean or a tail latency (p95, p99). Even for the same model, the statistic can change the figure several-fold.
  • Input and output size. The context length, the number of candidate answers, and the number of output tokens the 1.6-second call produced.
  • Measurement location. Whether it is processing time inside the server or the round trip a client experiences, and whether the network leg is included.
  • Settings of the 1.6-second call. Which prompt and settings were used to call Luna. Even the same model takes longer if it is made to write a longer output.
  • Who measured and when. Only the fact that it is OpenAI own figure is visible, and third-party measurement is outside the report. The load state during the preview is not known either.

A method for splitting latency into four pieces when choosing a model is covered in the article on where fast models win. If you split the latency of your own calls in that frame in advance, you can compare which segment the 150 ms shortened once public documentation appears. The report does not explain where the factor of ten came from.

It is also wise to be careful about ranking it against the figures in the Jev evaluation article. In the independent measurement reported there, the median response time of Jev was 0.8 to 0.9 seconds and one call took 850 ms. That measurement was taken with 20 calls in flight, whereas the 150 ms is a manufacturer figure whose conditions are not disclosed. The two numbers were not measured with the same ruler, so the sentence “150 ms is faster” cannot be written at present.

That is why the conclusion of this article is not adoption or rejection but a list of cells to reconcile.

Three uses and the conditions attached to each

The report names three uses for this type: classifying content, routing requests, and choosing an agent next action from a limited set of choices. All three share the trait of picking one from predefined candidates. Below are the conditions that can be weighed in advance from public information alone for each use; they are this article organization, not a recommendation from the report.

  • Content classification. The structure favors cases where label definitions are stable. If the label set changes often, the advantage the report describes is that you can respond by editing the prompt instead of retraining a small classifier.
  • Request routing. The number of candidates is the number of routing targets. Until the limit on candidates per request is public, it cannot be known whether one API can replace a router with dozens of targets. The general structure of model-switching routing is in the article on not sending every request to the expensive model.
  • Agent action selection. Because the score directly decides the next action, one wrong pick can skew every later step. Whether a path is needed to hand low-score cases to a person or a larger model becomes a design issue.
  • Image context. If images can be given as context, as The Decoder states, the classification target is not limited to text. The supported formats and sizes have not been disclosed.
  • Several questions in one call. The report says only that the developer provides questions, answers and context. Whether one request can carry several questions is not in the report.

All three uses are jobs that teams have already been doing with a chat model and a prompt. What the new call shape changes is not the kind of work but the way the same work moves from a path that generates sentences and parses them to a path that receives scores.

Reading the confidence score — the conditions behind “more realistic”

The report says a decision model can give more realistic confidence scores than the self-estimates of a general LLM. That sentence is a generalization about the type called decision models. The report does not say that OpenAI presented calibration figures for this model. To use the score in a business decision, four things have to be settled in the documentation.

  • Whether it is calibrated. Whether an answer given a score of 0.9 is actually right nine times out of ten is not the model own claim but a value to be measured on labeled samples. Setting a threshold on an uncalibrated score makes the meaning of the threshold shaky.
  • What the score means. Whether the scores of the candidates form a probability distribution summing to 1 or are independent values changes how a threshold should be applied.
  • Threshold design. The Jev evaluation article covers a design that trusts only the scores at both extremes and hands the middle range to an existing classifier. Whether the same design fits the Decision API score depends on calibration.
  • When candidates increase. In the four-public-dataset measurement reported in that article, Jev scored 76.0% on Banking77 with 77 options, lower than the two small LLMs compared. A similar structure does not mean the same result, and the candidate limit of this API and its accuracy with many candidates have not been disclosed.

The risk differs between inserting this API straight into an automated decision point while the way to read the score is undecided, and running it during the preview as a shadow path reviewed by people, accumulating the scores against actual correct rates. The latter is the order this article proposes.

Measuring with your own traffic — once the preview opens

When access opens, the order for reconciling public figures against your own business data, instead of trusting them as they are, is as follows. It is a design-level proposal that does not depend on any particular tool or command.

  • Build a sample. Draw a few hundred items from real requests and have people attach the correct label. If the job has many candidates, make sure each candidate has a minimum number of items.
  • Measure the baseline first. Run the path you use now, that is, calling Luna with a prompt, on the same sample and record the latency and accuracy in your environment. You need to know what “1.6 seconds” is in your own calls to compare the claim of ten times.
  • Measure latency as a distribution. Record the tail (p95 and p99) together with the median. For a call placed at the front of a router or agent, the tail decides what users feel.
  • Tabulate the correct rate by score band. Splitting the score into bands and writing the actual correct rate for each band reveals calibration and candidate thresholds at once.
  • Measure while increasing the number of candidates. Check whether accuracy holds at the number of candidates of your own business. When the limit is published, include values near the limit.
  • Compute the monthly cost once the price is published. Multiply the per-call price by monthly call volume and place it next to the cost of the existing path. Put the cost of people handling false positives in the same table.
  • Design the failure path. Prepare in advance a path that hands low-score requests to a larger model or a person. With that path in place, the risk of putting a new API at the front is bounded.

After these seven steps, the OpenAI figures of 150 ms and 1.6 s move from “a claim for reference” to “a measurement in your own environment”. If the measured values differ greatly from the claim, the condition that produced the difference is exactly the point to watch when using this API.

Once broad release happens, the details the spokesperson promised to share may come out all at once. At that point, open the table “What is public and what is blank” in this article and fill in the cells marked “undisclosed” first. When a price list appears, continue with the monthly cost calculation above; when a candidate limit appears, with the review of the number of routing targets among the conditions for each use; and when a score definition appears, with the threshold design in the section on the confidence score. If the official documentation reads differently from the report, the documentation is right, because the report conveyed limited information on the first day of the preview.

What could not be confirmed

  • The measurement conditions of 150 ms and 1.6 s. The statistic, input size, measurement location and the settings of the 1.6-second call are not in the report or in The Decoder. The 1.6 s is stated as what it “would take”.
  • The per-call price and the limit on candidate answers per request. These are items the report itself calls unclear.
  • Whether developers can tune the model on their own data. Not disclosed, for the same reason.
  • The definition of the confidence score and calibration figures. “More realistic” is a statement about decision models in general.
  • The body of the official OpenAI DevDay recap page. The attempt to open it was blocked by an access denial, so the official wording could not be checked directly, and the announcement content in this article leans on the accounts of The New Stack and The Decoder.
  • Updates after The New Stack report. The “undisclosed” cells of this article may change once the details promised for broad rollout are published.
  • Independent third-party measurements and a same-condition comparison with Jev. They are not in the report or the related material.
