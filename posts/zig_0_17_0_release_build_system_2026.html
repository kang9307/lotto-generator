계기 — 5개월간 축적된 빌드 시스템과 언어 명세 개편

Zig 핵심 개발팀은 2026년 10월 0.17.0 버전을 공식 발표했다. 공식 릴리스 노트에 따르면 이번 릴리스는 당초 예상보다 긴 5개월 동안 206명의 기여자가 참여하여 925개의 커밋을 반영한 결과물이다. 이 기간 동안 329건의 버그 리포트가 해결되었으며, 언어 안정화를 위한 대대적인 제안 심사가 진행되어 약 25개의 언어 제안이 수용되고 약 125개의 제안이 반려되었다.

0.17.0은 표면적인 버전 번호 증가에 그치지 않고, 프로젝트 전반의 아키텍처에 근본적인 전환을 가져왔다. 특히 빌드 시스템의 내부 구조가 전면 재설계되었으며, 언어의 핵심 내장 함수인 @bitCast의 정의가 변경되었고, 오랫동안 Zig의 C 상호운용성을 대표하던 @cImport 구문이 제거되었다. 대규모 오픈소스 생태계나 실무 프로젝트에서는 버전 업데이트 과정에서 수많은 컴파일 오류와 런타임 이상 동작을 마주할 수밖에 없다. 특히 릴리스 노트를 면밀히 검토하지 않고 기계적으로 코드를 갱신할 경우, 컴파일러 경고 없이 비트 레이아웃 해석이 달라져 잠재적 결함이 심어질 위험이 존재한다.

본 글에서는 0.17.0 릴리스 노트에서 확인된 사실에 입각하여, 빌드 스크립트와 C 연동 코드에서 즉시 파손되는 변경점들을 체계적인 점검표로 정리하고 각 항목의 공식 마이그레이션 절차를 짚어본다. 소프트웨어 업그레이드 결정에 수반되는 위험 평가 관점은 릴리스 노트 트리아지 가이드에서도 다룬 바 있다.

빌드 시스템 프로세스 분리 — configurer와 maker의 독립

0.17.0 빌드 시스템 개편의 핵심 축은 빌드 구성(configuration)과 빌드 그래프 실행(making)의 프로세스 분리다. 종전까지 zig build는 build.zig 파일을 컴파일하고 패키지 관리 및 의존성 그래프 실행까지 하나의 거대한 실행 파일(build runner) 내부에서 함께 처리했다. 이로 인해 build.zig 내용이 조금만 수정되어도 전체 러너를 다시 컴파일해야 했고, 외부 도구가 빌드 그래프 구조를 파악하기 어려웠다.

0.17.0에서는 build.zig를 실행해 그래프를 생성하는 구성 프로세스(configurer)와, 패키지 가져오기 및 실제 아티팩트 빌드 파이프라인을 수행하는 실행 프로세스(maker)가 서로 다른 독립 실행 바이너리로 완전히 분리되었다. 공식 문서가 제시하는 분리의 이점은 다음과 같다.

  • maker 바이너리는 프로젝트의 build.zig 내용과 무관하므로, Zig 툴체인 설치 후 최초 한 번만 빌드되면 이후 스크립트 수정 시 재컴파일되지 않는다.
  • maker 바이너리를 최적화 모드로 빌드할 수 있어, --watch 모드나 --fuzz 실행 시 빌드 그래프 순회 및 의존성 검사 오버헤드가 대폭 감소한다.
  • 사용자가 전달한 명령행 플래그에 따라 build.zig의 구성 로직 실행 자체를 완전히 건너뛰고 캐시된 그래프만 재실행할 수 있다.
  • 기존에 빌드 러너를 포크하여 구조를 가로채던 비표준 방식을 제거하고, 바이너리 직렬화 규격과 Build Server Protocol로 외부 도구 연동 창구를 단일화했다.

생성된 구성 정보는 압축된 바이너리 포맷으로 직렬화되어 디스크에 보관된다. 개발자가 빌드 그래프의 구성 결과를 직접 확인하고자 할 경우, --print-configuration 옵션을 전달하면 표준 출력으로 ZON(Zig Object Notation) 형식의 그래프 표현을 확인할 수 있다.

빌드 스크립트 파괴적 변경 — API 이름 교체와 인자 전달

프로세스 분리와 함께 std.Build 모듈의 광범위한 API가 변경되었다. 기존 0.16.x 프로젝트의 build.zig는 0.17.0에서 빌드 단계부터 컴파일 오류를 발생시킨다. 가장 먼저 드러나는 변화는 프로젝트 루트 디렉터리를 가리키던 b.build_root 필드가 Directory 타입에서 Path 타입인 b.root로 변경된 점이다. 또한 산출물 인자 전달 함수들이 버전 2로 전면 교체되었다.

특히 주의해야 할 변화는 Run 스텝의 전달 인자(passthru arguments) 처리 방식이다. 기존에는 빌드 스크립트 내부에서 if (b.args) |args| 형태로 명령행 인자를 직접 읽어 조건을 분기하거나 다른 스텝에 주입할 수 있었다. 0.17.0에서는 이 능력이 의도적으로 박탈되었다. 스크립트가 실행 인자를 관찰할 수 없게 함으로써, 인자가 달라지더라도 build.zig 자체를 재빌드할 필요가 없도록 만들었다.

// 이전 (0.16.0):
                    if (b.args) |args| {
                        run_cmd.addArgs(args);
                    }
                    
                    // 이후 (0.17.0):
                    run_cmd.addPassthruArgs();

또한 LazyPath.basename 메서드가 제거되었다. 경로의 베이스네임은 실제 maker 실행 단계에서 산출물이 만들어지기 전까지 확정할 수 없다는 설계 원칙에 따른 변경이다. 산출물 추가 함수 역시 addArtifactArg 대신 addArtifactArg2, addOutputFileArg 대신 addOutputFileArg2 계열을 사용하도록 정리되었다.

Build Server Protocol 도입과 ZLS 호환성 현황

0.17.0 이전까지 Zig 생태계의 언어 서버인 ZLS(Zig Language Server)는 Zig 컴파일러가 제공하는 빌드 러너를 자체 러너로 교체(override)하여 프로젝트의 빌드 설정을 추출했다. 그러나 프로세스 분리와 함께 빌드 러너 교체 기능이 완전히 제거되었다. 그 대안으로 도입된 메커니즘이 바로 Build Server Protocol(BSP)이다.

컴파일러에 --listen=- 플래그를 넘겨 실행하면, 빌드 시스템은 표준 입출력을 통해 연결된 클라이언트(IDE나 에디터 플러그인)와 통신하는 서버 모드로 동작한다. 릴리스 노트에 명시된 BSP의 현재 지원 범위는 다음과 같다.

  • 구성 완료 후 정적 빌드 그래프 전체에 접근: 가용한 빌드 단계(step), 설정된 옵션 값, 단계 간 의존성 관계 조회.
  • 빌드 스텝 실행 알림: 각 단계의 시작과 종료 시점, 발생한 오류 메시지, 최종 생성된 파일 경로 통지.
  • 특정 스텝의 선택적 실행 요청 수신 및 제어.

그러나 이 거대한 구조 개편으로 인해 0.17.0 릴리스 시점에 기존 ZLS와의 호환성이 일시적으로 깨지는 상황이 발생했다. 모듈 이름 목록 노출 등 일부 필수 인터페이스가 프로토콜 초기 구현에서 누락되었기 때문이다. 공식 릴리스 노트는 Zig 개발팀과 ZLS 팀이 협력하여 BSP를 확장하고 있으며, 단순한 기능 복구를 넘어 이전 러너 방식보다 훨씬 강력한 분석 기능을 제공할 수 있도록 작업 중이라고 명시하고 있다. 향후 Zig 자체 도구도 BSP 클라이언트로 전환될 예정이다.

캐시 시스템 재작업과 구성 캐시 오염 방지

Zig 0.17.0은 컴파일 및 빌드 캐시 시스템을 전면 재작업했다. 캐시 메타데이터가 기존 텍스트 포맷에서 바이너리 포맷으로 전환되어 캐시 파일 크기가 약 25% 줄어들었으며, 디스크 I/O 부담 완화로 캐시 적중(cache hit) 처리 속도가 5~10% 향상되었다. 캐시 상태를 점검할 수 있는 zig cache-cat 명령도 새로 추가되었다.

더 중요한 개념적 변화는 「구성 캐시 오염(configure cache poisoning)」의 도입이다. build.zig의 로직이 디스크 상의 임의 파일을 읽거나 시스템 명령을 호출하는 등 부수 효과(side effect)를 일으키면, 캐시 시스템이 추적할 수 없는 요소에 의해 빌드 구성이 왜곡될 수 있다. 오염된 구성 정보는 재사용되지 못하고 폐기된다. 개발자는 캐시를 오염시키지 않기 위해 의존성을 명시적으로 선언해야 한다.

  • std.Build.dependOnFileContents: 특정 파일의 내용 변화에 구성이 의존함을 선언.
  • std.Build.dependOnFileMetadata: 파일 크기, inode, 수정 시각(mtime) 변화에 의존함을 선언.
  • std.Build.dependOnDirectoryContents: 디렉터리 항목의 추가, 삭제, 이름 변경에 의존함을 선언.
  • std.Build.dependOnDirectoryMetadata: 디렉터리의 최종 수정 일자에 의존함을 선언.

외부 실행 파일을 찾는 findProgram 역시 즉시 탐색을 수행하여 캐시를 오염시킨다. 따라서 구성 단계가 아닌 실행 단계에서 바이너리를 사용할 목적이라면 새로 도입된 findProgramLazy를 호출해 LazyPath를 반환받아야 한다. 캐시 오염 정책은 --cache-poison=[pure|poisoned|disallowed|ignored] 플래그로 제어할 수 있으며 기본값은 pure다.

언어 수준 파괴적 변경 — @bitCast 논리 비트 재해석과 구문 정리

언어 코어에서도 기존 코드의 유효성을 뒤흔드는 결정적인 변화가 단행되었다. 가장 중대한 항목은 @bitCast 내장 함수의 정의 변경이다. 과거 @bitCast는 대상 머신의 메모리 배치를 재해석하는 방식으로 동작했다. 그러나 0.17.0부터 @bitCast는 값의 논리적 비트 표현(logical bit representation)을 다른 타입으로 재해석하도록 명세가 바뀌었다.

정수와 부동소수점은 최하위 비트(LSB)부터 시작하고, 배열과 벡터는 첫 번째 원소부터 순서대로 각 원소의 논리 비트를 연결한다. 이로 인해 리틀 엔디언 환경에서는 기존 동작과 대체로 일치하지만, 연산이 완전히 엔디언 독립적으로 정의된다. 공식 릴리스 노트는 이 변경이 컴파일 오류를 일으키지 않으면서 기존 코드의 런타임 결과를 조용히 바꿀 수 있다고 강력히 경고하고 있다. 특히 배열이나 벡터가 포함된 @bitCast 호출부는 전수 조사가 필수적이다.

더불어 extern struct와 extern union에 대한 @bitCast 호출이 전면 금지되었다. 메모리상의 물리 배치를 재해석하는 이른바 타입 퍼닝(type punning)이 목적이라면, 이제는 @ptrCast나 extern union을 사용해야 한다.

// 0.16.0 이전 (컴파일 오류 발생):
                    const int: u16 = @bitCast(bytes);
                    
                    // 0.17.0 마이그레이션 (@ptrCast 사용):
                    const int_ptr: *align(1) const u16 = @ptrCast(&bytes);

열거형(enum) 변환에도 파괴적 변화가 적용되었다. 기존 @intFromEnum과 @enumFromInt가 사용 중단 예정으로 지정되고, 새로운 내장 함수 @backingInt와 @fromBackingInt가 도입되었다. @backingInt는 열거형뿐만 아니라 명시적 정수 기반을 갖춘 비트팩, 태그된 유니온의 활성 태그 값을 정수로 추출할 때 사용된다. zig fmt 명령을 실행하면 이 변환을 자동으로 수행해 준다.

// 이전 (0.16.0):
                    return @enumFromInt(graph.generated_files.items.len - 1);
                    const generated_owner_step = graph.generated_files.items[@intFromEnum(gen.index)];
                    
                    // 이후 (0.17.0):
                    return @fromBackingInt(@intCast(graph.generated_files.items.len - 1));
                    const generated_owner_step = graph.generated_files.items[@backingInt(gen.index)];

그 외에도 문법 및 타입 정리가 이루어졌다.

  • 배열 반복 구문 a ** b가 제거되었으며 @splat으로 대체해야 한다.
  • void{} 구문이 제거되었으며 {}로 작성해야 한다.
  • errdefer |err| 형태의 오류 캡처가 문법에서 제거되었다. 오류 정보를 로깅해야 할 경우 함수를 내부 구현과 외부 래퍼로 나누고 바깥의 catch |err| 블록에서 처리해야 한다.
  • 0비트 부호 있는 정수 타입인 i0가 제거되었다. 대체가 필요한 자리는 u0로 전환한다.

C 연동 코드 마이그레이션 — @cImport 제거와 translate-c 패키지

0.17.0 릴리스에서 C 언어 라이브러리와 연동하던 프로젝트에 가장 직접적인 수정 청구서가 전달된 부분은 @cImport의 완전한 삭제다. 0.16.0에서 사용 중단 경고가 붙었던 @cImport 구문은 컴파일러에서 제거되었으며, 빌드 스텝이었던 std.Build.Step.TranslateC 역시 사용 중단 예정으로 처리되었다.

이제 C 헤더를 Zig 모듈로 변환하려면 Zig 소프트웨어 재단(ZSF)이 관리하는 공식 translate-c 외부 패키지를 프로젝트의 명시적 의존성으로 추가해야 한다. 패키지 관리자를 통해 의존성을 등록하고 build.zig에서 모듈을 구성하는 방식이다.

// 0.16.0 이전:
                    const translate_c = b.addTranslateC(.{
                        .root_source_file = b.path("src/c.h"),
                    });
                    
                    // 0.17.0 이후:
                    const translate_c = b.dependency("translate_c", .{});
                    const translator: Translator = .init(translate_c, .{
                        .c_source_file = b.path("src/c.h"),
                        .target = target,
                        .optimize = optimize,
                    });
                    // translator.mod를 타겟 모듈 임포트에 연결

이 분리를 통해 C 헤더 변환기는 메인 툴체인 릴리스 주기와 독립적으로 업데이트되며, 매크로 처리나 타입 변환에 관한 추가 옵션을 유연하게 제공받을 수 있게 되었다. FFI 경계에서의 안전성과 인터페이스 연결 문제는 컴파일러 프론트엔드 분석 및 Rust FFI 가변 인자 규약에서도 살펴볼 수 있다.

표준 라이브러리와 링커 진전 — SafeAllocator와 ELF 증분 빌드

표준 라이브러리에서는 메모리 디버깅의 주축이었던 DebugAllocator가 제거 수순에 들어가고, 새로운 SafeAllocator가 기본 할당자로 도입되었다. SafeAllocator는 스레드 안전성을 내장하고 있으며, 메모리 안전성 탐지를 대폭 강화했다.

  • deinit 호출 시 미해제된 모든 누수를 보고하고 기반 메모리를 정리한다.
  • 할당 크기나 정렬 불일치가 탐지되면 패닉 또는 세그멘테이션 오류를 즉시 유발한다.
  • 이중 해제(double free) 및 크기 조정(resize/remap) 경쟁 상태를 엄격히 감지한다.
  • 할당 뒤쪽에 체크섬으로 보호되는 AllocFooter를 배치하여 스택 추적과 카나리 불일치를 추적한다.

공식 벤치마크 결과에 따르면, -Osafe 컴파일러로 표준 라이브러리 테스트를 수행했을 때 빌드 소요 시간은 29.4초에서 22.1초로 24.7% 단축되었고, 최대 상주 메모리(peak RSS)는 2.24GB에서 1.11GB로 50.3% 감소했다.

한편, 컴파일러 백엔드와 링커에서도 진전이 있었다. 새롭게 작성된 자체 ELF 링커는 x86_64 및 SPARC64를 완전히 지원하고 LoongArch를 부분 지원한다. 정적 및 공유 라이브러리 생성, GOT 생성, DWARF 디버그 정보 처리가 가능해짐에 따라, 대부분의 x86_64-linux 프로젝트에서 zig build -fincremental --watch 플래그를 통한 증분 재빌드가 실용적인 수준으로 동작하게 되었다.

확인하지 못한 것

  • ZLS의 0.17.0 대응 릴리스 일정과 세부 복구 시점은 릴리스 노트 작성 시점 기준으로 확정일이 명시되지 않았다.
  • ARM64(aarch64) 환경에서의 자체 백엔드 기본화 시점 및 x86_64 이외의 환경에서의 증분 컴파일 지원 완성 시점은 로드맵 항목으로만 언급되었고 구체적 날짜는 확인되지 않았다.
  • @bitCast의 논리 비트 변경으로 인해 실제 빅 엔디언 타깃에서 발생한 구체적인 회귀 사례 수치는 릴리스 노트 본문에 제시되지 않았다.
  • LLVM 22.1.8의 루프 벡터화 비활성화 우회책이 실제 사용자 바이너리의 실행 성능에 미친 정량적 저하 폭은 측정값이 없다.
  • 0.17.0에 포함된 329개 버그 수정 목록의 세부 이슈 내역 전체를 직접 검증하지는 못했다.
  • Windows 환경에서 새 COFF 링커의 COMDAT 미지원 유형이 구체적으로 어떤 타사 C 라이브러리 링크 시 문제를 일으키는지는 기재되지 않았다.
