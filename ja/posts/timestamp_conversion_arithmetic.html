「除算を乗算に」はコンパイラがすでにやっている - タイムスタンプ変換で人の手が勝つ三つの場所と、その代償

新しいのは乗算ではなく、定義域・並べ替え・恒等式という三つの情報である

2026-09-09 開発・インフラ

算術の最適化の話には、ほぼ必ず同じ文が出てくる。除算は高いので乗算に置き換える。この文は正しい。ただしこの文だけを持ち出すと、いちばん大事なものが抜け落ちる。除数がコンパイル時に定まる定数であれば、その置き換えはすでに起きている。主要なコンパイラはその場所で除算命令を出さない。

では手書きの最適化が勝てる場所はどこか。こちらのほうがはるかに狭く、はるかに役に立つ問いだ。答えは乗算ではなく情報にある。コンパイラに欠けているのは能力ではない。入力が実際にどこまで来るのかという知識と、式をどんな形に置くかという選択と、その場所でだけ成り立つ代数的な恒等式である。

タイムスタンプを時・分・秒に分けるコードは、この線引きを試すのにほぼ理想的な対象だ。除数が 60 と 3600 という定数であり、入力の定義域が有限であり、正解を作る素朴な実装が三行で済む。つまり何がコンパイラの分で何が人の分か、そしてその分にいくらの担保が入っているかを、すべて数えられる。

ここにサイクル数や遅延の数値はない。それらの値はマイクロアーキテクチャと被演算子の幅とコンパイラのバージョンによって変わり、条件を外した数字は運ばれるたびに偽になる。代わりに性質と条件と検証方法を書く。自分の環境の数字は自分の環境から出る。

きっかけ - 一日の秒を三つに割るコード

扱う問題は狭い。真夜中から流れた秒をひとつ受け取り、時と分と秒の三つの値を出す。日付は扱わない。閏秒を除けば入力は 0 から 86,399 までで、出力は 23:59:59 を超えない。

この問題を解く教科書的なコードは二つの形を持つ。二つは同じ答えを出すが、式のあいだの依存関係が違う。

/* 逐次型 - 各段階が前の段階の結果を待つ */
unsigned hour   = t / 3600;
unsigned rem    = t % 3600;
unsigned minute = rem / 60;
unsigned second = rem % 60;

/* 独立型 - 三つの値を別々に求める。代わりに除算が増える */
unsigned hour   = t / 3600;
unsigned minute = (t / 60) % 60;
unsigned second = t % 60;

逐次型は演算の数が少ないが、鎖がひとつに長くつながる。rem が出るまでは minute を始められず、minute が出るまでは最後の減算ができない。独立型は鎖を切る代わりに同じ除算を何度も行う。演算の数を減らすことと鎖を切ることが互いに逆の方向へ引くという点が、この問題の性格を決める。

ここまでは古い話だ。新しく提起されたのは、鎖を切りながら演算の数も増やさない配置があるという観察と、剰余の演算そのものを別のものに変える二つの手法である。それらの手法がそれぞれどの枠に入るのかが、この記事の本論だ。

整数除算だけが違う理由

加算と乗算と除算は同じ算術演算として括られるが、ハードウェアでの性格が違う。除算が高い理由は、結果を一度に作り出す回路ではなく、桁をひとつずつ確定していく反復構造だからだ。商の各桁を決めるには、その上の桁が決まっている必要がある。

この性質が呼ぶ結果が三つある。

  • 完全なパイプライン化が難しい。加算器や乗算器は前の演算が終わる前に次の演算を流し込める。反復構造を持つ回路はそこまで自由に重ねられず、除算が並ぶと互いを待つことになる。
  • コストが固定値ではない。同じ命令でも、被演算子の幅によって、さらには実際の値の大きさによってかかる時間が変わる実装がある。32ビットの除算と64ビットの除算が同じ値札を持たない。
  • アーキテクチャごとに事情が違う。命令セットによっては整数除算の命令そのものが無い。そこでは除算がライブラリ呼び出しになり、コストは命令ひとつの話ではなくなる。

三つ目が特によく忘れられる。除算が高いという命題は、どのチップでも同じ程度に真な命題ではない。だからこの話題のどんな数値も、条件なしに運ばれてはならない。

最後の行が次の節の前提だ。除算が高いという事実そのものは最適化の根拠にならない。その除算が実際に機械語へ残っているときにだけ根拠になる。

定数の除数はすでにコンパイラが乗算に変えている

ここがこの記事の心臓だ。t / 3600 と書けば機械語に除算命令が入ると信じている人が多いが、おおむね入らない。

原理は単純だ。ある定数 D で割ることは 1/D を掛けることと同じである。整数演算に小数は無いので、1/D を 2 の冪だけ大きくした近似定数を代わりに掛け、掛けた後にその分だけ桁を戻す。これが固定小数点の逆数乗算であり、不変な除数に対するこの変換は1990年代に整理されてコンパイラ最適化の標準項目になった。

定数を作る規則も同じくらい単純だ。幅が b ビットのとき、乗数は 2b を D で割った商に 1 を足した値である。時分秒変換に出てくる定数がまさにその規則から出る。

  • 71582789 — 232 を 60 で割った商に 1 を足した値
  • 1193047 — 232 を 3600 で割った商に 1 を足した値
  • 2443359173 — 243 を 3600 で割った商に 1 を足した値
  • 37283 と 2185 — それぞれ 227 を 3600 で、217 を 60 で割った商に 1 を足した値

重要なのはこれらの定数が手で発明した値ではなく規則の出力であるという点だ。コンパイラも同じ規則で自分の定数を作る。ただしコンパイラは人より不利な条件をひとつ抱えて計算する。型の全範囲で正しくなければならない。入力が32ビットの符号なし整数なら 0 から 4,294,967,295 まですべて合う乗数と桁幅を選ばなければならず、そのため人が選べるものより広い中間幅を使うことになる。

この制約がなぜ解けないのかも明らかだ。コンパイラが見るのはその変数の型であって、その変数に実際に入る値の履歴ではない。関数ひとつだけを見れば引数に何が来るか分からず、呼び出し元をすべて見られる状況であっても、その呼び出し元を呼ぶ側まで辿らなければ範囲は確定しない。だからコンパイラは常に安全な側へ余裕をもって取る。これはコンパイラが怠けているからではなく正しくなければならないからであり、人が勝てる場所が生まれる理由もまさに同じだ。

ところがコンパイラがやることとやらないことの境界は、思ったより尖っている。きっかけとなった記事の著者が観察したところではこうだ。広く使われている二つのコンパイラは t / 60 / 60 を t / 3600 に合わせてくれるが、コードが剰余の演算子ではなく減算と乗算で書かれているときだけそうする。別のひとつのコンパイラは試したすべての場合でその最適化を行わず、ある実行時コンパイラは式を並べ替えた形そのものを見抜けなかった。

同じソースが道具によって別のプログラムになるということだ。著者本人の結論もそれである。この手法はコンパイラが賢いことに寄りかかっており、それが常に成り立つわけではないので、人が素直に並べ替えた形で書いておくほうがよいということ。

著者は理想的にはコンパイラがこのすべてを代わりにやってくれることを望むと書きつつ、有効な入力範囲についてのヒントがあればコンパイラが残りをやれるだろうと付け加える。ところがそのヒントは標準化された契約ではない。GCC の文書は到達不能を示す組み込み関数を制御フローがその地点に至ればプログラムが未定義になるという印としてのみ規定しており、値の範囲を伝える手段だとは書いていない。広く使われている慣用句があることと、文書が保証していることは別だ。

では人が勝てる場所はどこか

前の節をひっくり返すと答えが出る。コンパイラに欠けているのは算術の能力ではなく情報だ。人が売れる情報は三つしかない。

  • 定義域 — 入力が実際にはずっと狭い範囲でしか来ないという事実。一日分の秒は 86,400 通りしかない。コンパイラはこの事実を知る術がないので型の全範囲に合うコードを出す。人は狭い範囲でだけ正しく、その代わり短いコードを書ける。
  • 並べ替え — 三つの結果が互いを待たないように式を置き直すこと。数学的には同値なので危険はないが、どのコンパイラがその同値を見抜くかはまちまちだ。つまりこの場所で人が勝つ理由は数学ではなく道具の偏差である。
  • 恒等式 — その問題でだけ成り立つ代数的な正体。剰余の演算をビットマスクに変える変形がここに属する。コンパイラがこうした正体を知っている理由はないし、知るべき理由もない。

三つの性格が互いに違うという点が重要だ。並べ替えはただである。式が同値なのでどんな入力でも答えが変わらない。一方、定義域と恒等式は担保を取る。これからその関数に入ってくる値が約束を守るという条件のもとでだけ正しい。その約束はコードに書かれておらず、たいてい人の頭の中にある。

だから実務で順序が分かれる。並べ替えは先にやってよく、定義域と恒等式は測る理由ができてからやる。前者が戻せて後者が戻しにくいからではなく、後者が未来の呼び出し側に請求書を送るからだ。

原文の手法をその基準で分類すると

きっかけとなった記事は三つの形を提示する。上の三つの枠にそれぞれを入れてみると、何が新しくて何がすでにあったものかが分かれる。

一つ目 - 純粋な並べ替え

/* 除算二つを互いに独立に置き、残りは乗算と減算で */
unsigned tmin   = t / 60;      /* 真夜中からの総分 */
unsigned hour   = t / 3600;
unsigned second = t - tmin * 60;
unsigned minute = tmin - hour * 60;

定数も魔法もない。除算二つが互いを待たず、その二つが出れば残りの二つの値がそれぞれ乗算ひとつと減算ひとつで終わる。著者はこの形について分がもはや時刻から直接ではなく二つの中間結果から求まるので、すぐには思い浮かばない配置だと書いているが、正確な診断だ。人はたいてい各出力を入力から直接導こうとする。

この形の値打ちは仮定がひとつも無いことだ。どんな入力でも素朴な実装と同じ答えを出す。担保を取らずに得られる唯一の改善である。

二つ目 - 定義域を狭めて得る固定小数点

/* 32ビットの固定小数点。上半分が商、下半分が次の桁までの進行率
     1193047  = (2^32) / 3600 + 1
     71582789 = (2^32) / 60   + 1                                  */
uint64_t hprd = (uint64_t) t * 1193047u;
uint32_t hlow = (uint32_t) hprd;
uint32_t mlow = (uint32_t) ((uint64_t) t * 71582789u);

unsigned hour   = (unsigned) (hprd >> 32);
unsigned minute = (unsigned) (((uint64_t) hlow * 60) >> 32);
unsigned second = (unsigned) (((uint64_t) mlow * 60) >> 32);

発想はこうだ。乗数を掛けた64ビットの結果のうち、上半分は商であり、下半分は次の整数の段階までどれだけ来たかを表す小数部である。その小数部に 60 を掛けて再び上を取れば、残りの分や秒が出る。剰余を別に求めるのではなく、すでに計算された乗算の捨てられていた半分を再利用するわけだ。

代償は定義域である。32ビットの幅でこの計算が成り立つ上限があり、その上では答えが変わる。著者が明かした有効範囲は 0 から 2,255,818 までだ。一日分の秒よりずっと広いので本来の目的には十分だが、その上限はコードのどこにも書かれていない。

三つ目 - 剰余をビットマスクに変える恒等式

/* 恒等式:  x mod D  ==  (x + c*(x/D)) mod (D + c),   ここで c = 4  */
/* 60 に 4 を足すと 64 になるので剰余の演算が & 63 に変わる         */
uint32_t tmin = (uint32_t) (((uint64_t) t * 71582789u) >> 32);
uint32_t hour = (uint32_t) (((uint64_t) t * 1193047u)  >> 32);

unsigned second = (t    + 4 * tmin) & 63;
unsigned minute = (tmin + 4 * hour) & 63;

60 で割った剰余を求めるとき、商を四倍して足した上で 64 で割った剰余を取ると同じ値が出る。64 は 2 の冪なのでその剰余は下位六ビットを残すマスク一回だ。そして x + 4*y の形は主要な二つのアーキテクチャの両方で命令ひとつとして表される。アドレス計算の命令と、桁移動を付けた加算がそれぞれその役を担う。

この恒等式は任意の値で成り立つわけではない。商と剰余が特定の関係を保つ範囲の中でだけ真であり、著者が明かしたその範囲は 0 から 2,257,198 までだ。前の手法と上限が違うという点が後で重要になる。

表を縦に読むと結論が見える。「除算を乗算に」は人が勝つ場所ではない。その席はすでに埋まっている。人が勝つのは下の四行であり、そのうち仮定なしで勝つのは並べ替えの一行だけだ。残りはすべて定義域という担保を取って得ている。

最後の行は別に見る価値がある。ベクトル命令を使う場合、中間結果を64ビットに広げると一つのベクトルに収まる値の個数が減る。だからベクトルの経路ではより正確な定数よりも、より狭い定数が勝つ。狭い乗数を使えば有効範囲は大きく縮むが、代わりにレーンが保たれる。逆にベクトル幅が広いアーキテクチャでは前の形が再び勝つと著者は書いている。同じコードがどのアーキテクチャで最善かは固定された順位ではない。

代償 - 何を担保に入れるのか

最適化の代償を速さの反対語としてだけ考えると半分を取り落とす。ここで支払われるものの大半は未来に請求される項目だ。

代償具体的に何かいつ請求されるかあらかじめ防ぐ方法
定義域の仮定狭い幅の乗数は上限の上で別の値を出すその関数が別の目的で再利用されるとき有効な上限を関数名と注釈に釘打ちし、範囲の表明を付ける
中間値の幅乗数を掛けた値が収まる場所が要る32ビットの対象へ移すとき、ベクトルコードへ移すとき中間の幅を型で明示し、その幅で全数照合する

読む人の検証コストなぜマスクが剰余と同じなのかコードだけでは分かれないそのコードを直すたび恒等式と有効範囲を注釈に残し、試験を一緒に置く
道具への依存同じソースがコンパイラごとに別の機械語になるツールチェーンや最適化水準を変えるとき対象のツールチェーンごとに機械語と測定を見直す

四行目がもっとも過小評価される。読む人が検証できなくなることもコストだ。素朴なコードは間違っていれば目に見える。マスクと乗数でできたコードは間違っていても目に見えず、そのコードを直そうとする人は手を付けないか、手を付けてから分からなくなる。このコストは一度ではなく、そのコードが生きているあいだ繰り返し請求される。

同じ性格の請求書は別の場所にもある。予算を極端に絞った実装でデータ構造を消すと、その構造が静かにやっていた検証まで一緒に消えるのだが、その構造はインタープリターを 1,024 バイトに収めた試みでより鮮明に現れる。消したものはひとつなのに失ったものは二つ、という点が同じだ。

範囲を外れた最初の値で何が起きるか

定義域の仮定の危険は、抽象的な言葉で残すと実感が湧かない。定義域が有限なので、主張された上限のすぐ次の値で何が起きるかをそのまま数えられる。そしてその結果が手法ごとに違う。

手法主張された上限上限の次の値真の値その手法が出す値失敗の性格
狭い幅の固定小数点2,255,8182,255,819626:36:59626:37:59静かだ。三つのフィールドがすべて有効な値なので表明に引っかからない
剰余をビットマスクに2,257,1982,257,199626:59:59627:63:59見える。分の桁が 63 なので範囲の表明ひとつで捕まる
レーン幅維持のための狭い乗数一日分より少し広い程度115,20032:00:00別の値上限がずっと低い。経過時間の用途に回すと早く出会う

二行目と一行目の差が実務で分かれる地点だ。分の桁に 63 が出る失敗はどこかで必ず引っかかる。表示のコードが二桁に揃えようとしておかしくなるか、検証器が弾くか、少なくとも人が画面で気づく。逆に分がひとつずれた時刻はそのままログに残り、そのまま保存され、そのまま集計される。どちらも同じ種類の仮定を破ったのに、発見の時点が数か月違う。

ここから出てくる実務の規則がひとつ。範囲を仮定する関数には、その範囲を表明として書いておく。最適化が成り立つ上限を知っている人がその上限をコードに残さなければ、その知識はその人がチームを去る瞬間に消える。値とその値に付いた条件を一緒に書いておかなければ、後で条件だけが静かに落ちていく。

三行目は再利用の落とし穴を見せる。時刻を割る関数は経過時間を割るのにもそのまま使いたくなる。形がまったく同じだからだ。ところが一日分の秒を前提に選んだ定数は、数日分の経過時間で崩れる。経過時間を扱うとき時計そのものがすでにどんな落とし穴を持っているかは、単調時計と壁時計を分けた記事に別に整理してある。

速くなったという文が成り立つには

速度の主張は条件が付いて初めて命題になる。条件なしに運ばれた倍率は、次の人に届く頃にはたいてい偽だ。少なくとも四つが一緒にある必要がある。

揃えるべきもの無いと起きること具体的な形
正確性の照合速いのに間違ったコードを速いと呼ぶ定義域の全体を素朴な実装と照合する。定義域が有限なので標本ではなく全数で行う
機械語の照合ソースから除算を消しただけなのか、機械語からも消えたのかが分かれないコンパイラエクスプローラや逆アセンブルで除算命令の有無を見る。最適化水準ごとに
環境の明示再現しないコンパイラとバージョン、最適化フラグ、対象アーキテクチャ、オペレーティングシステム
測定軸の区別遅延を測ると言いながら処理量を測ることになる遅延の測定では前の結果を次の計算の入力に戻して並列実行を止める

最後の項目がこの話題でもっともよく崩れる。ループの中で互いに独立な計算を何度も回すと、実行装置がそれらを重ねて処理する。その状態で出た数値は演算ひとつが終わるまでにかかる時間ではなく、単位時間にいくつ処理するかだ。二つの値は逆の方向に動きうる。鎖を切る最適化は遅延で大きく得て、処理量では少ししか得ないか、むしろ失うこともある。

きっかけとなった記事の測定方式はこの区別を明示的に扱う。遅延の測定では前の結果を排他的論理和で次の計算に食わせて並列実行を止め、処理量は別に測る。無作為な値をあらかじめメモリに載せておき、何度か回した上で中央値を使う。ベクトルの経路では自動ベクトル化を試みるのだが、ひとつのコンパイラはベクトルコードを出し、もうひとつは出さなかったと書いている。同じソースについての話だ。

測定の機材は三種類だ。最近のノート用プロセッサ、デスクトップ用の高性能プロセッサ、そして32ビットの小型ボード。最後のものを入れた選択が方法論上の意味が大きい。64ビットの乗算の上半分を安く得られない環境では順位が変わるからだ。三つの軸を置いて測らなければ、自分の環境にだけ合う結論が一般命題として運ばれる。

原文を紹介した掲示板には、別の言語で試したらコンパイラの最適化が差を消したという短い報告が付いている。条件が書かれていないのでその報告そのものを事実として扱うことはできないが、方向は前の節と同じだ。どの道具が何を代わりにやってくれるかが結果をひっくり返す。

定義域が有限であることの意味

この話題には、たいていの最適化に無い性質がひとつある。入力が有限であり、それも数えられるほど小さい。一日分の秒は 86,400 通りだ。前に出てきた拡張範囲も数百万通りの水準である。つまり標本による検証ではなく全数照合ができる。

/* 定義域が有限なので標本ではなく全部を照合できる */
for (uint32_t t = 0; t <= LIMIT; t++) {
    hms fast = fast_hms(t);
    hms ref  = { t / 3600, (t / 60) % 60, t % 60 };   /* 素朴な実装が正解である */

    if (fast.h != ref.h || fast.m != ref.m || fast.s != ref.s) {
        printf("first mismatch at %u\n", t);
        return 1;
    }
}
/* LIMIT を主張範囲より十分大きく取り、境界のすぐ外側が
   どう間違うかまで見る。通る範囲だけを回る試験は、
   その関数を再利用してよいかを教えてくれない。 */

この性質が検証の基準を丸ごと引き上げる。有限な定義域で標本だけ回して正しいと言うのは、根拠を自ら下げることだ。きっかけとなった記事もこの点では明確である。リポジトリの試験が各アルゴリズムの有効範囲全体を素朴な実装と照合すると書かれており、閏秒を扱う変形については数学的な証明は持っておらず、一日の範囲で全数で照合しただけだと著者自ら書いている。

証明が無いという記述を残したことが、この記事でもっとも見習うべき箇所だ。全数照合は証明ではない。有限な定義域ではその二つが実質的に同じになるが、定義域が変わった瞬間に照合は何も保証しない。その境界を自ら印しておいたコードとそうでないコードは、再利用の安全性が違う。

検証の順序にも規則がある。値を変える前に検証し、検証した後に再び変えない。最適化された経路を入れながら同時に入力の正規化に手を付けると、どちらが原因なのか分かれない。この順序がひっくり返ったときに何が無効になるかは、正規化と検証の順序を扱った記事に整理されている。

効く場所と効かない場所

同じ最適化があるコードでは意味があり、別のコードでは無い。分けるのは手法の優秀さではなくそのコードが何回呼ばれるかだ。

効く場所はこうだ。

  • ログの整形 — 行ごとに時刻を打つ。毎秒数万行を書くシステムでは、この変換がログ経路の定数コストになる。
  • 時系列の一括変換 — 数百万行のタイムスタンプを人が読める形に変える一括処理。同じ関数が行の数だけ呼ばれる。
  • 描画と直列化 — 一つの表に数万個の時刻を打つ場合。画面に見えるものよりずっと多く呼ばれることはよくある。

効かない場所はこうだ。

  • 要求ごとに数回呼ぶ経路 — 得られる分が測定誤差より小さい。こうした場所で素朴なコードをマスクと乗数に変えると、コストだけが残る。
  • すでに別のもので詰まっている経路 — ストレージやネットワークを待つコードで算術を減らせば、待つ時間が増えるだけだ。
  • 変換の後の段階がより重い経路 — 時分秒を求めた後には、数字を文字に変えてバッファへ書かなければならない。その段階のほうが大きければ、前を減らしても全体はほとんど動かない。どちらが大きいかは測るまで分かれない。

三つ目の項目がこの話題では特によく引っかかる。時刻を文字列にする関数全体を見れば、除算はその関数の一部にすぎない。部分を最適化して全体が速くなったと言うには、全体を測らなければならない。

そして時刻を扱うコードには算術のコストより先に来る問題がよくある。同じ秒の値がどの時間帯とどの規則で解釈されるかが結果を変え、その規則はコードではなくデータとして更新される。タイムゾーンのデータ更新が過去の時刻の解釈まで変える話がその軸だ。曜日や日付へ移ると計算の性格そのものが変わるのだが、そちらはカレンダーをコードに移す仕事に別にある。

先に測ってから直す

順序を整理すると五段階だ。手法の一覧ではなく判断の順序である。

  • 第一に、その経路が上位にあるかを測る。プロファイルで目立たない関数を直すのは最適化ではなく趣味だ。この段階を飛ばすと残りの四段階がすべて無駄になる。
  • 第二に、機械語に除算が残っているかを見る。残っていなければその場所でやることはすでに終わっている。定数の除数ならたいていここで終わる。
  • 第三に、仮定の無い改善を先に適用する。依存の鎖を切る並べ替えがそれだ。担保を取らないので戻すことになっても失うものが無い。
  • 第四に、それでも足りなければ定義域を掘る。ここから担保が入るので、有効範囲をコードに書き、全数照合をリポジトリに一緒に入れる。試験なしで入った狭い定数は期限の決まった欠陥だ。
  • 第五に、もう一度測る。同じ条件で前後を比べ、遅延と処理量を分けて見る。この段階が無ければ前の四段階は、ただコードを難しくした作業である。

この順序でもっともよく省かれるのは第二だ。除算が高いという知識は広く行き渡っているのに、その除算がすでに消えているかを見る習慣はそこまで行き渡っていない。だからコンパイラがすでにやっておいたことを人がもう一度やり、その代償に定義域の仮定だけを新たに背負う結果になる。

まとめるとこうだ。きっかけとなった記事が実際に見せたのは、乗算が除算より安いという話ではない。人がコンパイラより優れている唯一の地点は、コードに書かれていない情報を持っていることだという話であり、その情報を使った瞬間にそれをコードへ書いておく義務が一緒に生まれるという話である。書いておかなければ、その最適化は次の人にとって時限装置になる。

確認できなかったこと

  • サイクル数・遅延・処理量の数値 — ベンダーの最適化マニュアルを照合していないので、どんな数字も使わなかった。整数除算が加算や乗算より高く、そのコストがアーキテクチャと被演算子の幅によって違うという定性的な記述までを残した。
  • 生成された機械語 — 各形を実際にコンパイルしてどんな命令が出るかは照合できなかった。コンパイラが定数の除数をどう処理するかについての記述は、広く知られた変換規則ときっかけとなった記事の観察に基づく。自分のツールチェーンでの結果は、そこでコンパイルして初めて分かれる。
  • 原文のベンチマークの再現 — リポジトリをビルドして同じ数値が出るかを回してみることはできなかった。本文の測定条件の記述は、原文が明かした方法論を移したものだ。
  • 範囲のヒントを与える標準的な手段 — 値の範囲をコンパイラに伝える方法として広く使われる慣用句があるが、GCC の文書がその組み込み関数を規定する仕方は到達不能の印までである。最近の標準に入った仮定の属性が実際にこの種の最適化を引き出すかは照合できなかった。
  • 閏秒の変形が成り立つ根拠 — きっかけとなった記事の著者本人が、その数式についての形式的な証明は持っておらず一日の範囲で全数照合しただけだと書いている。本文もそれ以上を主張していない。
  • 他の言語・実行環境での再現 — 掲示板に付いた短い報告がひとつあるが、コンパイラのバージョン・フラグ・測定方式が書かれていないので根拠としては使わなかった。
  • 実システムでこの変換が占める割合 — ログの整形や時系列の変換の経路でこの関数が全体の何割かはシステムごとに違い、一般値を示す根拠が無い。だから本文はその割合を測る順序だけを書いた。
