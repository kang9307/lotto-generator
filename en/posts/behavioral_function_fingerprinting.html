Same Output Is Not the Same Function - The False Positives and False Negatives Left When You Judge Functions by Behavior Instead of Bytes

What survives when shape falls apart, and what the decision to compare by running actually charges you

2026-09-10 Dev & Infra

Sitting down in front of an executable whose symbol names have been stripped, the first thing to settle is not what a given function is. It is what will count as grounds for saying two things are the same. Without fixing the grounds there is no fixed answer, and change the grounds and the same file yields a different one.

The grounds have long come in two families. One measures shape: how much the bytes overlap, how closely the control flow graphs resemble each other. The other measures behavior: feed the function values, see what comes out, and watch what it reads and writes along the way. The two families are good at different things, and — more importantly — they are wrong in different shapes.

The axis followed below is the second family. Specifically, the two failures that always come with it: calling two different functions the same, and calling one function two different things. Where each of them is born, and what actually shrinks them.

The trigger - a tool that matches functions by what they do

The trigger was a tool called fnprint. Its README defines itself this way: it matches functions in binaries by what they do, not by what their bytes or control flow graphs look like. Each function is run inside a small emulator on randomized input, the effects that fall out of that run are recorded, and the record is hashed into a fingerprint.

Three uses are named in that document. Putting names on a binary whose symbols have been stripped; pinning down behavioral changes between two builds; and ranking a function of unknown identity against a corpus of known-vulnerable code and a corpus of patched code. Only x86-64 ELF is handled today, with ARM64 and MIPS, plus PE and Mach-O loaders, listed as plans. It is written in Rust and carries the MIT license.

More interesting than the tool itself is the ground of judgment it picked. Deciding to compare by running is not free. What that buys and what it costs is the body of this piece.

Judging by shape - bytes and graphs

Measuring shape is old and still the working default. Broadly it counts three things.

  • Byte sequences — the machine code at the head of the function is matched directly. Positions that hold addresses or relocations take a different value every build, so those positions are marked variable and the rest is checked for overlap.
  • The shape of control flow — a graph is built with basic blocks as vertices and branches as edges, and the two graphs are scored for resemblance. A single changed instruction often leaves the skeleton intact, which is why this survives more than byte matching does.
  • Attached markers — string constants, magic numbers, the names of external symbols the function calls. Optimization rarely touches these, which makes them high-value evidence, but they are useless on a function that carries none.

What these methods are good at is clear enough. They are fast, they never execute anything, and when they hit they are extremely precise. For recognizing the same library built in the same environment, nothing beats them. The problem arrives the moment the build environment changes.

Why shape falls apart - how one source becomes different machine code

Finding the same function is hard not because functions are hard, but because the same source does not always become the same machine code. Compilation is a one-way transform from source to machine code, and that transform is full of decisions the source never wrote down. Optimization level, compiler family and version, target architecture, and choices made at link time all shake the result.

Laid out concretely, here is what breaks the bytes.

TransformWhat happensEffect on byte matchingEffect on graph matching
InliningA small function is spread into the call siteThe separate function is gone; there is nothing left to matchThe caller graph grows and the original shape dissolves into it
Instruction reorderingIndependent instructions swap placesThe same instructions in a different order fail to overlapReordering inside a block leaves the skeleton alone

The right-hand columns are worth staring at, because they diverge. Looking at graphs survives these transforms better than looking at bytes. But survival has limits. Unrolling a loop, or turning a conditional into branchless code, redraws the skeleton itself. Every method that measures shape eventually hits the same wall, because the freedom a compiler has to change shape is wider than the range a human calls the same.

The idea of judging by behavior

That raises a different question. If shape moves, what does not move? Optimization rearranges shape only within the bound of not changing what the program does. So why not measure what it does, directly?

That is the idea behind behavioral judgment. Feed the function values, run it, then record the effects that surface outside it and compress them into a summary. The README for fnprint calls what it records an architecture-neutral stream of effects, and enumerates it: which argument buffers and struct fields the function reads and writes, what class of value it writes — a copy of an input, a small constant, a pointer — what calls it makes, what branches it takes, and what it returns.

That stream of effects is then cut into shingles and turned into a minhash signature. Similarity between two functions is the fraction of signature slots that agree, which estimates how much their behavior overlaps. An LSH band index sits in front so that candidates are not compared everything against everything. Rendered as a picture, the observation of one function comes out roughly like this.

read    arg0[0 .. n)        sequential access
write   arg1[0 .. n)        a copy of the input
call    1                   recorded, not entered
branch  2                   zero-length check / alignment check
return  arg1                the input pointer, unchanged

That summary contains no instruction order, no register names, no absolute addresses. The README says absolute addresses are thrown away and only offsets and shapes are kept. The method has descended to a layer the shape-shaking transforms cannot reach. In exchange, that layer demands a different payment.

Four things the decision to execute charges you

Feeding inputs and comparing outputs means actually running the function. From that moment on, problems appear that static analysis never had. They split four ways.

Side effects - the analysis changes the world

Functions do not merely return values. They delete files, open sockets, mutate globals, terminate processes. Run a function of unknown identity on real hardware and the act of analysis changes things outside the thing being observed. So this approach generally picks simulated execution over real execution: it runs on a layer that imitates instructions, and it closes off the paths that lead out.

Input space - you have to decide what to feed it

The set of values that could arrive as arguments is effectively unbounded. How many of them get chosen sets the quality of the judgment. Feed arbitrary junk and execution usually walks only the front of the function — the one that checks whether the length is zero and returns, the one that filters out a null pointer. Shallow input yields shallow observation. Craft the input more carefully and you need to know what the function expects, which is the very problem you started out trying to solve.

Environment dependence - the same function comes out differently

The result of a run does not belong to the function alone. Read uninitialized memory and whatever happened to be sitting there mixes into the result. A function that reads the clock or draws a random number returns something new every call. Residue from an earlier call left on the stack, alignment, the addresses things got mapped at — all of it leaks into the observation. Leave that wobble in place and you will measure the same function twice and call it two different functions.

Isolation cost - running code you do not know

Executing code whose identity is unknown carries a cost of its own. Touching a bad address must not kill the run; there must be something that cuts an infinite loop short; one function's run must not leave marks on the next one's. Every one of those guards eats speed. Where byte matching sweeps tens of thousands of functions a second, simulated execution has to run each function several times over.

The chargeWhy it arisesCommon responseWhat remains after the response

How the tool behind the trigger handles those charges

How a tool deals with those four charges is the yardstick for the whole approach. Restricting this to what the README for fnprint actually states, here is the list.

  • Unset memory — a read from memory that was never set up returns a deterministic value, and the page gets mapped on the fly. The wobble of uninitialized memory is pinned down by a rule about values.
  • Wild pointers — pointers into nowhere never crash the run, and the same input always gives the same trace. Isolation and reproducibility are bound together in one sentence.
  • Calls to other functions — calls that leave the function get stubbed, which is to say recorded and then skipped. That keeps the run from diving into libc and keeps the observation on this function.
  • Absolute addresses — absolute addresses are thrown away and only offsets and shapes are kept. This is the mechanism that makes the same code produce the same trace when it sits at a different address.

That is what the document contains. What it does not contain matters just as much. There is no statement about what happens when a system call instruction is reached, nor about the level at which isolation is guaranteed. There is no statement about how many inputs go into a single function, nor about the rule by which those values are constructed. The install requirements name a widely used CPU emulation framework and a disassembler; the emulation framework describes itself as a framework that imitates instructions, and its own repository page does not separate out whether it imitates the operating system layer as well.

Absent from the document does not mean unhandled. It means the document alone cannot settle it. When a tool that runs code of unknown identity is brought into production work, this is exactly the column that has to be filled in from somewhere else.

Levels of sameness - overlapping observations versus the same function

Now to the core problem of the approach. Two sentences sit on different levels.

First: the observations overlap on the inputs we chose. That is a claim about measurement. It is a fact about what went in and what came out, and it is true only inside the range of values that went in. Second: these two are the same function. That is a claim about identity. It carries an assertion about behaving alike on every input.

The first does not entail the second. That gap is where false positives are born. Two genuinely different functions producing the same observation on the chosen inputs is not rare. The README names pure computation as a weak spot and puts it plainly: two checksums that both read a buffer and return a number look alike, because from the outside they nearly are.

function A   read buf[0..n)   no writes   returns a 4-byte integer
function B   read buf[0..n)   no writes   returns a 4-byte integer

The summary observed from outside is identical.
What was multiplied and what was added inside leaves no trace outside.

The other direction exists too: the same function looking different because the observation conditions differed. Compare two heavily optimized builds and the behavior that surfaces is itself thin. Once inlining has swallowed the calls and branches have folded into branchless code, there are no effects left to record. And when there is little to record, every function starts to look like every other one.

False positives and false negatives are not symmetric

False positives - calling different things the same

A false positive is quiet. A function with a wrong name attached will not be reopened, precisely because it has a name. Neighboring functions get interpreted on the premise of that name, and further judgments stack on top of those interpretations. One bad match contaminates everything laid over it, and the contaminated output looks finished from the outside. In a situation where thousands of names were attached automatically, that risk grows in proportion to the count.

False negatives - calling the same thing different

A false negative is not loud either, but it lingers. Miss one function while comparing against a corpus of vulnerable code and that function simply stays where it was. Misses do, however, have a property that false positives lack: they usually surface when a human looks again. Attach a step where somebody scans the top few candidates and a large share of the misses come back. The README lands on exactly that point: on one pair the top hit is right 93% of the time while the correct function is in the top five 96.6% of the time, and it adds that a small review budget closes most of that gap.

The conclusion that follows is simple. False positives and false negatives do not weigh the same. In a workflow with human review attached, a miss is a recoverable failure and a false positive is not. Take the human review away and the asymmetry disappears, leaving only the cost of the false positives.

Confidence rests on how many inputs agreed

A single agreement is indistinguishable from coincidence. Compare two functions on one input, get the same result, and that is barely information. Add inputs and the probability of continuing to agree by accident falls, which is what moves agreement closer to evidence of identity. Confidence in a judgment comes from the quantity of observation, not from a property of the function.

And the quantity of observation is not set by the number of inputs alone. What matters more is how much the function has to reveal. A function that takes three arguments, walks a buffer and writes different values depending on a condition leaves many marks. A one-line function that hands a value straight through leaves none. The README calls this property signal, and says functions with low signal are withheld rather than judged.

The measurements published in that same document show the structure directly. They cover 84 functions of zlib 1.3.1, comparing two artifacts built from the same source under different conditions.

What to read out of that table is not the individual numbers but the pattern. Where at least one side is less optimized the figures are high; where both sides are heavily optimized they drop toward half. The README summarizes it the same way: when at least one side has some behavioral richness it lands in the 80 to 98 percent range, and when both sides are heavily optimized the observable behavior gets thin and it drops toward a coin flip. That sentence reads more accurately as an explanation of what the method depends on than as a performance report.

Methods, their strengths, and the shape of their failures

Folded into one sheet, the material so far comes out like this. No method wins on every axis, and the point is that each one fails in a different direction.

The bottom two rows are the ones actually chosen in practice. Allow abstention and the quality of what you commit to rises while the pile of unanswered functions grows. Run both families and the failure shapes differ enough to cover a good deal of ground, but the functions where the two disagree remain as a fresh review queue. Either way the failures do not disappear; they change address.

Different uses make different failures expensive

Even with the same tool, the threshold should sit in a different place depending on what you are trying to do, because which of the two failures costs more differs by task.

UseWhat a false positive costsWhat a miss costsWhich way to tilt
Naming statically linked library functionsA wrong name poisons every later interpretationSome functions stay namelessSuppress false positives — when unsure, attach no name
Diffing before and after a patchUnchanged functions look changed and review inflatesA real change goes unnoticedSuppress misses — keep candidates wide, let humans narrow
Duplicate code detectionUnrelated functions get tangled togetherDuplication goes unfound and cleanup is missedBalanced — hand over a candidate list, let humans judge
Telling a vulnerable build from a patched oneSomething safe is treated as risky and effort is wastedSomething risky stays in placeSuppress misses — skipping is far more expensive

The last row connects back to the asymmetry from the previous section. Whether human review is part of the workflow flips the relative price of the two failures. What has to be settled before the tool's threshold is the shape of the workflow.

Abstention as the third answer

Between same and different sits declining to say. That option does not reduce failure, but it does let you choose which kind of failure you take. The README says the tool abstains on pairs it is not sure about instead of guessing, which is why precision stays high while recall at the same threshold stays low.

Three things are worth separating when abstention is written into a workflow.

  • Not filing abstentions in the same column as misses — a function left unanswered is not a wrong answer, it is a function without an answer yet. Merge the two into one number and it becomes invisible which part of the workflow needs fixing.
  • Deciding in advance where abstentions go — to a human queue, to a judgment from the other family of methods, or nowhere. Without that decision, abstention is just a quiet omission.
  • Separating abstention for lack of signal from abstention for a tie between candidates — the first does not improve when you add inputs, while the second may resolve if you add observation. The responses differ.

The conditions law and contract attach

There is no single answer attached to the act of analyzing a binary. The same work is judged differently depending on where it was done and for what purpose. So this section does not write down that something is permitted or forbidden. It writes down only the points where the judgment hangs.

Law and contract are separate layers. The rules governing use of a program differ in their text between countries, and so does the question of which conditions permit which purposes of analysis. Separately from what the law sets out, the terms of service and license agreed to when the program came into your hands attach their own conditions. The law side can be open while the contract side is closed, and the reverse happens too. The two layers have to be checked independently, and a conclusion from one cannot be carried over to the other.

Technological protection measures are yet another layer. Defeating a measure put in place to control access or copying is treated separately from the legality of analysis as such. Procedures for getting past such a measure are not written here. What is covered above is the character of a method for judging whether this function and that function are the same, applied to code already in hand and already runnable — not a method for opening anything up.

In practice this boundary is usually managed through purpose and records. What the analysis is for, who the output is left with and in what form, and by what route the subject of the analysis was obtained. For anything that needs a decision, the procedure is a legal review that puts jurisdiction and contract on the table together.

Summary - reduced to five sentences

  1. Finding the same function is hard not because functions are hard but because the same source does not always become the same machine code. Inlining, reordering and register allocation break byte signatures.
  2. Where shape wobbles, behavior wobbles less. But measuring behavior means actually executing, and that decision charges four things: side effects, input space, environment dependence, isolation cost.
  3. 「The observations overlap on the inputs we chose」 and 「these are the same function」 are claims on different levels. The first does not entail the second, and that gap is where false positives are born.
  4. Confidence comes from how many inputs agreed and how much the function had to reveal. Thin both out and every method drifts toward a coin flip.
  5. False positives and misses do not weigh the same, and which costs more is set by whether human review is in the workflow. Settling the workflow before the threshold is the right order.

What could not be established

  • Behavior on reaching a system call — the README carries no statement about what happens when simulated execution reaches a system call instruction. It states only that calls leaving the function are recorded and then skipped.
  • Input count per function and the rule for building them — there is a statement about junk going into the argument registers, but not about how many inputs are used or by what rule those values are constructed. That figure directly governs the confidence of a judgment.
  • The guaranteed level of isolation — there is a statement that wild pointers never crash the run, but the document does not spell out how far that isolation extends. For a tool that handles code of unknown identity, this column needs separate evaluation.
  • Performance outside the published measurements — the published figures cover 84 functions of one library. Numbers at other scales, for code written in other languages, or under other optimization pairings are absent from the document.
  • Internal specifications of byte-matching tools — the detailed specification documents for the widely used library-function identification technology were not opened here. The description above is limited to properties that family shares in common, and is not a transcription of any specific implementation.
