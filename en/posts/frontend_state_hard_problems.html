When the Screen and the Server Disagree

State is not one thing - split it by lifetime and owner and you can see where the difficulty lives

Aug 28, 2026 Dev & Infra

Introduction: You hit back and the old title is still there

You edit a title on a detail screen and save. You hit back, the list appears, and the old title is still sitting there. It is the kind of bug that disappears when you reload. Reproduction is flaky, there is no stack trace, and once you fix it the same shape shows up somewhere else a month later. Most of the time frontend engineers lose to a defect, the defect looks like this.

A recent piece by FL on hackers.pub names four things that state management tools still fail to give us: it is hard to change the sharing scope of a piece of state after the fact, hard to express the lifetime of shared state, hard to share derived state as if it were one value, and hard to keep the code of a single feature in one place. The author treats these four as one underlying problem wearing different faces.

Rather than restating that list, this article looks at the same territory from a slightly different angle: not what the tools fail to do for you, but when what the screen shows and what the server holds stop agreeing. Once you can count the places where that drift is born, it becomes much clearer what any given tool actually takes off your hands and what it quietly leaves behind.

One warning up front. There is no and this is how you fix it in here. These are called hard problems precisely because no complete solution exists, and every remedy below takes something in exchange. Naming that price alongside each remedy is the whole point.

1. What the single word state is hiding

When people say state management is hard, the word state is doing a lot of work. It covers values whose properties have almost nothing in common, and lumping them together is where the trouble starts.

Two axes separate them: where the original lives and how long the value should survive. Along those two axes, four families fall out.

  • Data the server owns — order lists, user profiles, stock counts. What the screen holds is a copy, and other people can change the original while you are looking at it
  • Values that live only on this screen — which accordion is open, the text being typed, drag coordinates. It is correct for them to disappear when the screen does
  • Values in the URL — the query, the page number, the selected tab. These are the values you can hand to someone else as a link
  • Values kept in the browser — session tokens, dark mode preference, a dismissed banner. They survive closing the tab

The column worth staring at is who clears it. Only the screen-local value has its lifetime already encoded in the structure of the code. For the other three, a human has to decide when the value gets thrown away. If nobody decides, the value simply stays, and a value that stays long enough eventually becomes a wrong value.

2. Hard problem one: the original lives somewhere else

The order status drawn on your screen is not the order status on the server. It is a copy taken a few seconds ago. In the meantime another admin may have changed it, or a carrier webhook may have fired. A copy starts going stale the moment it is taken. So the question reduces to one thing: when do you ask again?

2.1 Candidate moments to ask again

  • When the screen is first entered — the baseline, but it misses everything that changes while the user sits there
  • After a certain age — and deciding what that age is turns out to be a domain judgement, not a technical one
  • When the tab regains focus — high value for a user who walked away and came back
  • Right after the user changes something — this reflects only your own writes, never anyone else's
  • When the server pushes first — which brings the cost of a live connection and a recovery design for when it drops

2.2 Every direction has a price

Ask often and request volume climbs while the screen shifts under the reader every time a response lands. A list re-sorts, a scroll position jumps. Ask rarely and traffic drops, but the user makes decisions based on a stale value. That is exactly how someone orders the last remaining unit of something that sold out two minutes ago.

So the refresh cadence should not be a matter of taste. The criterion is whether being wrong here can be undone. A profile name that is a few seconds old costs nothing. A balance, a stock count or a permission that is stale leads the user into an action they cannot take back. For values on the second list, do not trust the copy taken at screen entry — let the server re-adjudicate at the moment of execution. The screen is a copy no matter what you do, so the only fully reliable remedy is to stop letting the screen be the one that decides.

3. Hard problem two: what do you show while waiting?

The button is pressed. The response arrives 300 milliseconds later. What should the screen say during those 300 milliseconds? In practice there are three answers.

  • Block and wait — show a spinner and lock the controls. Honest, but short requests make the screen flash and the app feels slower than it is
  • Keep the old value and mark it — hold the list and dim it at the edges. Nothing moves, which is calm, but a user who misses the marker reads the old value as the new one
  • Update optimistically — assume success and change the screen first. The felt delay disappears entirely

3.1 What an optimistic update actually buys

The gain from an optimistic update is not speed but continuity. Tap like and the heart fills immediately, and the user moves to the next item. The round trip takes exactly as long as before, but the experience of waiting is gone. On a screen where people act on item after item in a scroll, that difference is large.

3.2 What a rollback costs

The problem is failure. Rolling back is never just putting the old value back.

  • The user has already done the next thing — new actions are stacked on top of the reverted value, so it is ambiguous which point to revert to
  • Nobody watched the rollback happen — if the element scrolled out of view or the user switched tabs, they leave convinced it worked
  • The server partially succeeded — if the save landed and only the notification failed, reverting the whole screen moves it further from the truth
  • The rollback reorders the list — the item springs back into place and the user taps the wrong row

So optimistic updates are not something to apply uniformly to every action. Keep them for actions with a low failure rate, where the blast radius is that one element, and where the rollback plays out inside the user's field of view. Deletions, payments and anything that changes sort order fail all three tests, and simply making the user wait is the better trade. This is exactly where the argument that every frame must be coherent bites: the fastest screen and the most honest screen are not always the same screen.

4. Hard problem three: the same data on several screens

One order appears in three places — the row in the list, the detail view, and the unhandled-count badge in the header. Change the status in the detail view and the other two need to find out somehow. This is where the bug from the opening paragraph is born.

4.1 Three approaches and what each costs

  • Keep one copy and reference it — the room for divergence shrinks structurally. In exchange, that single copy must satisfy every screen at once, so fixing one screen means touching a shared shape
  • Hold local copies and broadcast changes — screens stay loosely coupled. In exchange, miss one subscription and that one screen goes quietly stale. Users find the missing subscription before you do
  • Keep it in a keyed cache and invalidate after writes — the rule is explicit and traceable. In exchange, invalidate the wrong key and the old value survives with no error anywhere. Key design becomes consistency design

4.2 The normalisation fork

When the same entity keeps arriving inside several different responses, it is natural to want to flatten it out and keep exactly one copy per entity. Do that and a single write updates every screen. In exchange, the shape the server sends, the shape you store and the shape the screen wants all become different shapes. You now have code that flattens responses and code that reassembles them for display, and when those two fall behind a new field, the value goes missing at the reassembly step instead.

Remove the duplication and you trade mismatch for conversion cost. Keep the duplication and you trade conversion for a mismatch you have to police. Neither side is free, and that is the point. If one entity is visible on three or more screens at once and at least one of them can edit it, normalising usually hurts less. If two screens only read it, there is little reason to pay the price.

5. Hard problem four: order is not guaranteed

You type ser into a search box and then serv. The requests went out in order. Nothing guarantees the responses come back in order. If the response for serv lands first and the one for ser arrives late, the screen ends up showing results that do not match the text in the input.

5.1 Accept only the newest

The simplest defence is to tag each request with a number and, when a response returns, check whether that number is still the latest.

latest = 0

on_input(query):
    latest = latest + 1
    my_seq = latest
    result = await fetch(query)
    if my_seq != latest:
        return            # a newer request went out in the meantime
    render(result)

Those few lines stop most of the mismatch between screen and input. The price is discarded responses. If the user deletes a character and retypes it, the earlier response is thrown away even though it answers the same query. And this only protects the screen. The server has already run five searches.

5.2 What cancellation cannot do

Cancelling the previous request when a new one goes out is also common. But cancellation is a statement that you will not read the response, not that the request never happened. If it already reached the server, the processing and its side effects happen anyway. For reads this does not matter. Start treating writes as cancellable and you manufacture a state where the screen believes the action was cancelled while the server has it recorded.

5.3 When writes overlap

Suppose a toggle is tapped twice quickly. An enable and a disable go out, and if the responses come back swapped, the server's final state and the screen's final state part ways. Here the accept-the-newest-response rule actively hurts, because the response that arrives first may be the one that was sent last. For writes you either serialise the requests, collapse them so only the user's final intent is sent, or send a version alongside so the server can adjudicate. Whichever you pick, the screen cannot decide alone; it needs an agreement with the server. The setting that turns itself back on after you toggled it offline has its roots in the same place.

6. Derived state and storing what you could compute

You have cart items and you have a total. The total can be computed from the items — it is derived state. But once several screens need the total, the urge to store it separately shows up. That is the fork.

  • Store it and it drifts — there will be at least one path that changes items and forgets the total. That path is usually in a feature added later
  • Recompute every time and it is expensive — with thousands of items, or a computation that sorts and groups, you redo the same work on every render
  • Memoise it and the key becomes the problem — caching a computed result requires a rule for deciding whether the inputs changed, and if that rule is narrower than the real dependencies, a stale value survives silently

The decision narrows to two questions. Can this value always be derived from the original? And can the user edit it directly? If it can always be derived and the user cannot touch it, the default is not to store it. Conversely, a value the user can override — an automatically computed shipping fee that an operator is allowed to change — is no longer derived at all; it has become an original in its own right and must be stored. Confuse the two and you get the classic incident where a value someone typed in is silently overwritten by a recomputation.

The third item on the list that prompted this article lives right here: it is hard to let several screens share a derived value as if it were one value, and harder still when the computation carries a side effect — when producing the value requires asking the server once. Tools built on the assumption of pure computation do not transfer cleanly. A value that mixes computation with fetching wears the face of derived state but behaves like the server copy from section two, and it inherits every staleness and refetch problem that came with it.

7. Using the URL as state

Put the query, the filters and the page number in the address and several things arrive free. Copy the link to a colleague and they see the same view. Back behaves the way users expect. A reload keeps the screen. Bookmarks and new tabs simply work. Implementing those four by hand takes a serious amount of code, and the address bar has already done it.

The constraints come with it.

  • Strings only — objects and dates have to be serialised, and that format immediately becomes a public contract
  • Other people can see it — it lands in server access logs, referrer headers, and anything visible over a shoulder. Not a place for personal identifiers or tokens
  • Length has a practical ceiling — a design that puts several hundred selected ids in the address gets truncated at some point
  • Changing the schema breaks old links — rename a parameter and every link already shared quietly opens a different view
  • History gets polluted — push an entry per keystroke and the user has to press back twenty times to leave the page

That last one bites most often in practice, and the judgement is simple. Ask whether this is a point the user would want to return to with the back button. If yes, push an entry; if no, replace the current one. Intermediate typing states replace, confirmed filters and page changes push. That usually matches what people expect.

One more thing. In a server-rendered setup, the URL is the only client state the server can know about. If the first paint has to happen on the server, what to paint must be in the address. That fact carries more weight than it first appears when you are deciding which values belong in the URL.

8. What a global store solves and what it defers

By this point the global store suggests itself: gather the values in one place and the drift should shrink. Some things genuinely do get solved.

  • You stop threading values by hand through intermediate components
  • Changes flow through one place, so you can observe what changed and when
  • Events that happen outside any screen — an incoming notification, a token expiry — finally have somewhere to land

What gets deferred is equally clear, and three of the four items from the article that prompted this one sit precisely here.

  • Lifetime — a screen-local value dies with the screen, but a value lifted into a global store has no natural moment of death. On logout, on switching organisation, on leaving a screen, you end up maintaining a hand-written list of what to clear. That list goes stale as fast as features are added
  • Sharing scope — a value used by one screen gets lifted when a second screen needs it, and narrowing it again later means rewriting how it is expressed everywhere. Scope is easy to widen and hard to reverse, which is why it usually stays wide
  • Cohesion — the values, the update logic and the reset for one feature end up in different files. That is how you arrive at a codebase where nobody is confident about what to delete when a feature is removed

Listing tool names does not help here. There is the family that gathers everything into a single store, the family that splits state into small composable units, and the family that pulls the server-data cache out into its own layer. They differ in which of the three problems above they make less painful. None of them removes the drift itself. Whatever you are evaluating, the questions are the same: who clears this value, what has to change if the scope changes, and what is left behind when the feature is deleted. Once those three have answers, picking a tool is the easy part.

9. Common misconceptions

Some sentences come up in every team. They are usually half right, and the wrong half gets expensive later.

The last row repeats most often. A tool migration forces a fresh pass over the code, so things really do look better afterwards. What improved was usually the boundaries you redrew during the migration, not the tool. Drawn with the old tool, the same boundaries would probably have improved things about as much.

10. Where testing gets hard

One reason state defects survive so long is that tests do not stick to them easily. The difficulty comes almost entirely from time and ordering.

  • You need to vary the order responses arrive in, and real networks make that order hard to reproduce on demand
  • Tests that wait on real timers are slow, and slow tests eventually get switched off
  • A cache that survives between tests makes results depend on execution order — the classic passes alone, fails in the suite
  • The intermediate frame of an optimistic update is invisible to a test that only inspects the final state. Verifying the rollback requires deliberately manufacturing failure
  • Values left in browser storage persist into the test environment too, so the old value of a feature you just deleted keeps influencing runs

The remedies carry their own costs. Making time and the network injectable lets you script any ordering, but it adds a layer, and that layer differs subtly from the real thing, which creates a band of behaviour that only tests pass through. Standing up a fake server gets you closer to reality but stays silent when the contract drifts. There is no fully safe combination; you are choosing what to miss.

The priority is nonetheless fairly clear. Test the rollback paths and the invalidation rules first. Both fail without raising an error and leave only a wrong value behind, so without automated checks a user report is your only detection mechanism. Loading indicators and spinner presence, by contrast, are immediately visible to anyone, so they rank lower.

11. What could not be confirmed

  • Generalised performance numbers comparing these approaches — results move with screen size, data volume and update frequency, so benchmarks without stated conditions were not cited here
  • Current default behaviour and APIs of specific libraries — refresh defaults and invalidation mechanics change between releases, so the accurate answer is whatever your own version's documentation says
  • The detail of the solutions proposed by the author of the piece that prompted this — only the framing of the four problems was checked; the subsequent discussion is outside the scope of this article

12. Closing: manage the drift instead of abolishing it

The screen and the server disagree. That is structure, not a bug. As long as the original lives on another computer, other people can change it, and the network between them guarantees neither ordering nor success, a screen holding a copy will always be slightly wrong. State management is less a technique for removing that drift and more a technique for choosing where the drift is allowed to surface.

So the first practical move is not choosing a tool but separating the values. Pick any value in your current code and ask three questions. Where does its original live? When should it disappear? If it is wrong, can the user undo what they did with it? Values that answer all three instantly rarely cause trouble. Any value where one of the three sticks is where your next bug will be born.

That no complete solution exists is not entirely bad news. With no solution, what remains is choices, and choices can be made differently under different conditions. Let the server adjudicate values that cannot be undone. Keep optimistic updates for actions whose rollback is visible. Key invalidation to data rather than to screens. Record in the address only the points people would want to come back to. Those four alone prevent most of the bug from the opening paragraph from ever being born. The rest you handle one at a time. As with UI where requirements multiply rather than add, the hard part here is not any single item but the combination.
