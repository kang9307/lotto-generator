서론: 에이전트는 무엇을 하고 있는가

Claude Code나 OpenCode를 켜고 복잡한 작업을 맡긴 뒤 10분이 지났다. 화면에는 도구 호출 로그가 스크롤되고, API 사용량 계기판의 수치는 빠르게 올라간다. 문제는 왜 그렇게 많이 쓰이는지 알 수 없다는 점이다. 어느 단계에서 불필요한 파일 읽기가 반복됐는지, 서브에이전트가 이미 처리한 정보를 상위 에이전트가 다시 계산하고 있지는 않은지, 세션이 끝난 뒤에는 아무 흔적도 남지 않는다. 에이전트는 여전히 블랙박스다.

Agent-Blackbox는 이 문제를 정면에서 다루는 도구다. 2026년 6월 기준 GeekNews에 38포인트를 받으며 소개된 이 도구는 Claude Code와 OpenCode의 실행 세션을 세션 맵 형태로 시각화하고, 각 단계의 토큰 소비량과 낭비 지점을 분석한다. 단순한 사용량 추적이 아니라 에이전트 실행 관측성(observability)의 개념을 AI 코딩 에이전트 영역에 가져온다는 점이 핵심이다.

이 글은 Agent-Blackbox의 발상에서 출발해, AI 코딩 에이전트에서 토큰 낭비가 어떻게 구조적으로 발생하는지, 세션 맵이 디버깅에 어떤 가치를 주는지, 그리고 에이전트 관측성이라는 개념이 2026년 인프라 실무에서 왜 무시할 수 없는 과제가 됐는지를 본인 관점으로 분석한다. 복제가 아니라 분석이다. 단서를 먼저 밝힌다면, 이 도구는 방향이 옳지만 아직 초기 단계이며, 진짜 가치는 도구 그 자체보다 그것이 제기하는 질문에 있다.

1. 에이전트 블랙박스 문제 — 왜 지금인가

전통적인 소프트웨어 디버깅은 결정론적이다. 같은 입력을 주면 같은 출력이 나오고, 로그를 역추적하면 어디서 잘못됐는지 찾을 수 있다. AI 에이전트는 이 전제를 깬다. 동일한 프롬프트를 줘도 온도(temperature) 0에서조차 비결정론이 남고, 하나의 에이전트 실행이 수십 개의 도구 호출과 서브에이전트 생성으로 이어지며, 각 단계에서 소비된 토큰의 맥락과 이유는 결과 파일 어디에도 기록되지 않는다.

이 문제가 2026년에 더 예리해진 이유가 있다. AI 코딩 에이전트가 개발 워크플로 중심으로 들어오면서, 에이전트 한 세션의 비용이 달러 단위를 넘는 경우가 일상화됐다. Claude Opus 4.x 계열은 같은 에이전트 구성에서 이전 버전 대비 1.5배 가까이 더 많은 토큰을 소비한다는 커뮤니티 보고가 이미 나왔다. 한 회사가 CI 파이프라인에 에이전트를 올렸더니 4시간 세션에서 180개 이상의 도구 호출이 발생하고 수십 달러의 토큰 비용이 나왔다는 사례도 보고된다. 이 비용이 어디서 왔는지 모른다면, 절감할 방법도 없다.

Agent-Blackbox의 문제 정의는 여기서 나온다. "에이전트가 무엇을 했는지 알 수 없다면, 왜 그렇게 많이 썼는지도 알 수 없다." 세션이 끝난 뒤 남는 것은 총 토큰 수와 비용 숫자뿐이다. 어느 도구 호출이 전체 비용의 40%를 차지했는지, 어느 파일 읽기가 불필요하게 반복됐는지, 서브에이전트가 상위 에이전트의 작업과 중복된 부분은 어디인지 — 이것들이 블랙박스 안에 있다.

2. 세션 맵이란 무엇인가 — 에이전트 실행의 해부

Agent-Blackbox가 제시하는 핵심 개념은 세션 맵(session map)이다. 이는 에이전트 실행을 타임라인 또는 트리 구조로 표현한 것이다. 각 노드는 하나의 도구 호출(파일 읽기, Bash 실행, 검색, 서브에이전트 생성 등)을 나타내고, 노드 간 엣지는 호출 순서와 인과 관계를 보여준다. 각 노드에는 소모된 입력 토큰·출력 토큰·캐시 적중 여부·지연 시간이 부착된다.

이런 구조가 있으면 몇 가지 즉각적인 진단이 가능해진다.

  • 반복 읽기 감지: 같은 파일 경로가 세션 맵에 3회 이상 등장한다면 에이전트가 이미 읽은 내용을 컨텍스트에서 잃고 재요청하는 것이다. 컨텍스트 압축 전략이나 캐시 설정이 필요하다는 신호다.
  • 토큰 집중 구간 파악: 전체 토큰의 60%가 단 두 개의 노드에서 나온다면, 그 도구 호출이 과도한 출력을 생성하고 있다는 뜻이다. 파일 읽기 출력 한도(CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS)나 bash 출력 한도(BASH_MAX_OUTPUT_LENGTH) 조정의 근거가 된다.
  • 서브에이전트 중복 탐지: 두 서브에이전트가 비슷한 파일 집합을 각각 읽고 있다면 오케스트레이션 설계에 문제가 있다. 한 에이전트의 결과를 다른 에이전트에 전달하는 컨텍스트 공유 구조로 바꾸면 중복 비용을 제거할 수 있다.
  • 불필요 MCP 호출 식별: MCP 서버에서 등록된 도구 정의만으로 시스템 프롬프트에 수천 토큰이 붙는다. 세션 맵에서 실제로 호출된 MCP 도구와 한 번도 호출되지 않은 도구를 구분하면, 사용하지 않는 MCP를 제거해 고정 비용을 줄이는 데이터를 얻는다.

Claude Code의 경우 PreToolUse와 PostToolUse 훅이 있어 외부 도구가 이 이벤트를 가로채 로그를 쌓을 수 있다. Agent-Blackbox는 이 훅 이벤트 스트림을 읽어 세션 맵을 구성한다고 알려져 있다. OpenCode는 오픈소스 구조라 세션 파일 자체를 직접 파싱하는 방식이 가능하다. 두 에이전트를 통합된 뷰로 비교할 수 있다는 점이 이 도구의 차별점이다.

3. 토큰 낭비의 구조 — 어디서 새는가

세션 맵을 보기 전에, 에이전트 토큰 낭비의 구조적 원인을 이해하는 것이 선행돼야 한다. 2026년 6월 현재 실무에서 관찰되는 낭비 패턴은 크게 네 가지로 분류된다.

3.1 고정 오버헤드: 시스템 프롬프트와 도구 정의

에이전트는 매 턴 시스템 프롬프트와 등록된 도구 정의 전체를 컨텍스트로 포함한다. Claude Code의 빌트인 도구만 20여 개이고, MCP 서버를 10개 연결하면 도구 정의 토큰만 수천이 추가된다. 이 비용은 작업과 무관하게 매 턴 지불된다. 실제로 사용하지 않는 MCP 서버를 연결한 채 에이전트를 돌리면 도구 정의 고정 오버헤드가 전체 비용의 20~30%를 차지하는 경우가 있다.

3.2 대화 히스토리 누적

에이전트는 긴 작업일수록 이전 대화 히스토리를 점점 더 많이 컨텍스트에 물고 다닌다. 파일 읽기 결과·Bash 출력·이전 어시스턴트 응답이 전부 히스토리에 쌓인다. 짧은 에이전트 루프를 100회 돌리면 100번째 턴의 입력 토큰은 1번째보다 기하급수적으로 많아진다. 컨텍스트 압축(context compaction)이 작동하지 않거나 캐시 미적중이 겹치면 비용 폭발이 발생한다. 한 커뮤니티 사례에서는 캐시 저장은 성공했지만 읽기에 실패해 매 대화마다 67,374 토큰을 처음부터 재처리한 케이스가 보고됐다.

3.3 불필요 외부 연결

IDE 자동 연결(autoConnectIde), 웹 검색, 글로벌 문서 자동 로드가 활성화된 상태에서 에이전트를 돌리면, 실제 작업 외 연결 비용이 매 세션 추가된다. OpenCode에서 웹 검색을 비활성화(web_search = disabled)하고 MCP 앱을 끄면(features.apps = false) 단순 코딩 작업에서 세션당 토큰이 눈에 띄게 줄어든다는 실측 결과가 이미 커뮤니티에서 공유됐다.

3.4 서브에이전트 중복 컨텍스트

멀티에이전트 구성에서 오케스트레이터가 동일 파일이나 정보를 여러 서브에이전트에 각각 전달하는 경우, 중복 컨텍스트 비용이 발생한다. 이는 설계 문제이지 에이전트 자체의 문제가 아니지만, 세션 맵 없이는 이 중복이 발생하고 있는지조차 알 수 없다. Agent-Blackbox가 노리는 핵심 가치가 바로 이 지점이다.

4. 에이전트 관측성이란 개념 — 왜 2026년에 본격화하는가

에이전트 관측성(agent observability)은 AI 에이전트의 실행을 구조화된 트레이스로 포착하고, 각 단계를 평가·모니터링·디버깅할 수 있게 만드는 실천이다. 전통 소프트웨어의 APM(Application Performance Monitoring)이 AI 에이전트 영역으로 확장된 개념으로, 2026년 들어 독자 카테고리로 자리 잡기 시작했다.

왜 지금인가. 두 가지 구조적 변화가 맞물렸다. 첫째, 에이전트가 단발 호출이 아니라 수십 스텝의 자율 실행으로 쓰이기 시작했다. 단순 챗봇은 로그 한 줄로 충분하지만, 4시간짜리 에이전트 세션은 180개의 도구 호출이 어떻게 연결됐는지 추적할 수단이 없으면 실패 원인을 찾을 수 없다. 둘째, 비용이 무시하기 어려운 수준이 됐다. 에이전트 코딩이 실제 개발 워크플로에 들어오면서 월 수백 달러의 에이전트 API 비용이 일상화됐고, 이 비용의 어느 부분이 낭비인지 알고 싶다는 수요가 생겼다.

에이전트 관측성의 네 축은 다음과 같다.

  • 실행 트레이스: 도구 호출·서브에이전트 생성·모델 응답을 시간 순서와 인과 관계로 기록
  • 토큰·비용 귀속: 어느 단계에서 얼마를 썼는지 단계별 분해
  • 출력 평가: 각 단계의 결과물이 기대에 맞는지 정량 평가
  • 에이전트 신원 추적: 멀티에이전트 환경에서 어느 에이전트가 어느 작업을 담당했는지 귀속

Agent-Blackbox는 이 중 실행 트레이스와 토큰·비용 귀속에 집중하는 도구다. Claude Code·OpenCode 특화 접근법이 Langfuse나 Arize Phoenix 같은 범용 관측 플랫폼과 다른 점이다. 코딩 에이전트의 세션 파일 포맷과 훅 이벤트를 직접 처리하는 경량 로컬-퍼스트 도구라는 위치가 더 실용적으로 느껴지는 이유가 여기 있다.

5. Claude Code vs OpenCode — 관측성 관점의 비교

Agent-Blackbox가 두 에이전트를 동시에 지원한다는 사실은, 두 에이전트의 관측성 접근법이 구조적으로 다르기 때문에 흥미롭다.

5.1 Claude Code의 관측성 구조

Claude Code는 훅 기반 이벤트 시스템을 내장하고 있다. PreToolUse·PostToolUse·Stop 같은 훅 포인트가 있어, 외부 도구가 Claude Code의 설정(~/.claude/settings.json)에 훅 커맨드를 등록하면 모든 도구 호출 이벤트를 가로채 처리할 수 있다. 이 구조는 관측 도구 입장에서 편리하다. 에이전트 코드를 수정하거나 프록시를 끼울 필요 없이 공식 확장 포인트만 사용하면 된다. 단점은 훅 이벤트가 도구 호출 레벨의 정보를 주지, 내부 추론 과정(extended thinking)의 토큰 사용이나 중간 의사결정 맥락은 노출하지 않는다는 점이다.

5.2 OpenCode의 관측성 구조

OpenCode는 오픈소스이므로 세션 파일 포맷 자체를 파싱해 분석할 수 있다. 소스를 열어보면 에이전트 내부 구조를 더 깊이 이해할 수 있고, 커스텀 계측을 직접 삽입하는 것도 가능하다. 오픈소스 구조가 관측 도구 개발자에게 유리한 환경을 제공한다. 반면 공식 훅 API가 없으므로 OpenCode 버전 업데이트에 따라 파서가 깨질 위험이 있다. 도구가 소스 포맷에 의존한다는 취약성이다.

5.3 두 에이전트의 공통 블랙박스 영역

두 에이전트 모두 내부 추론 토큰(thinking tokens)은 완전히 노출하지 않는다. Claude Code의 extended thinking 모드에서 모델이 내부적으로 얼마나 길게 추론했는지, 그 추론 토큰이 총 비용의 몇 %를 차지했는지는 현재 관측 도구로 접근이 어렵다. 이는 Agent-Blackbox를 포함한 현 세대 관측 도구의 공통 한계다. 에이전트 실행을 블랙박스에서 꺼내는 작업은 아직 절반만 됐다.

6. 실무 적용 — 어떻게 쓸 것인가

2026년 6월 기준, 에이전트 관측성 도구를 실무에 도입할 때 본인이 제안하는 우선순위는 다음과 같다.

6.1 로컬-퍼스트 도구부터 시작하라

세션 로그에는 프롬프트 원문과 코드 내용이 포함된다. 이를 외부 서버로 전송하는 SaaS 관측 플랫폼을 사용하면 데이터 보안 정책과 충돌할 수 있다. Agent-Blackbox·AgentProf·CodeBurn·ccusage 같은 로컬-퍼스트 도구는 분석이 본인 기기에서 이뤄져 이 위험을 줄인다. 도입 첫 단계는 로컬-퍼스트 도구로 세션 데이터를 수집하고, 어느 패턴이 자주 보이는지 먼저 파악하는 것이다.

6.2 고정 오버헤드부터 줄여라

세션 맵 분석 전에도 지금 당장 할 수 있는 최적화가 있다. Claude Code 기준으로는 includeGitInstructions: false(Git 지시문 제거), autoConnectIde: false(IDE 자동 연결 해제), 사용하지 않는 MCP 서버 비활성화만으로도 턴당 고정 오버헤드를 즉시 줄인다. OpenCode에서는 features.apps = false와 웹 검색 비활성화가 같은 효과를 낸다. 이 설정은 세션 맵 분석 없이도 확인된 절감 방법이다.

6.3 세션 맵으로 패턴을 찾아라

Agent-Blackbox 같은 세션 맵 도구는 단발 비용 추적보다 패턴 발견에서 가치가 크다. 비슷한 작업을 10회 돌리고 세션 맵을 나란히 놓으면, 매 세션 반복되는 고비용 패턴이 보인다. "이 에이전트는 항상 X 파일을 3번 읽는다", "Y 도구 호출 직후 동일 검색이 반복된다" 같은 패턴이 발견되면, 그것이 프롬프트 수정이나 도구 설정 조정의 구체적 근거가 된다.

6.4 멀티에이전트 구성에서 더 주의하라

단일 에이전트보다 멀티에이전트 오케스트레이션에서 관측성의 가치가 훨씬 크다. 서브에이전트 두 개가 독립적으로 돌고 있을 때 어느 서브에이전트가 비용의 몇 %를 차지하는지, 두 에이전트 사이에 컨텍스트 중복이 있는지는 세션 맵 없이는 보이지 않는다. Claude Code의 서브에이전트 기능이나 OpenCode의 병렬 에이전트 구성을 쓰고 있다면 세션 맵이 필수에 가깝다.

7. 관측성 도구 생태계 — 2026년 6월 현황

Agent-Blackbox만이 이 공간의 유일한 도구는 아니다. 2026년 6월 기준, 비슷한 목적의 도구들이 동시다발로 등장했다. 이 생태계를 간략히 정리하면 에이전트 관측성의 지형이 보인다.

도구주요 기능접근 방식대상
Agent-Blackbox세션 맵 + 토큰 낭비 분석로컬-퍼스트Claude Code, OpenCode
AgentProf도구별 타이밍·토큰 프로파일링훅 + 웹 대시보드Claude Code, Codex
CodeBurn비용·토큰 TUI 대시보드로컬 세션 파일31개 AI 도구

ccusage일별/월별 토큰 리포트로컬 세션 파일Claude Code, OpenCode 등
AgentsView세션 검색·분석·통계로컬-퍼스트20개 이상 에이전트

이 생태계는 아직 초기다. 각 도구가 각자의 세션 파일 파서와 시각화를 독립적으로 구현하고 있고, 표준화된 에이전트 세션 포맷은 존재하지 않는다. Agent-Blackbox가 다른 도구와 구별되는 지점은 세션 맵 개념, 즉 토큰 양을 집계하는 것을 넘어 왜 그 토큰이 어느 구간에 집중됐는지 인과 흐름으로 보여주는 데 있다.

8. 한계와 냉정한 평가

장점만 나열하는 것은 분석이 아니다. Agent-Blackbox와 현 세대 에이전트 관측성 도구 전반의 한계를 짚어야 한다.

내부 추론 영역의 불투명성: 앞서 언급했지만 Claude Code의 extended thinking 토큰은 훅 이벤트로 포착되지 않는다. 에이전트 비용의 상당 비중을 차지할 수 있는 추론 토큰이 세션 맵에서 빠진다면, 분석의 완결성에 구멍이 있다.

관측 오버헤드: 훅을 추가하거나 이벤트를 로깅하는 것 자체가 미세한 지연을 만든다. 대부분의 경우 무시할 수준이지만, 지연에 민감한 워크플로에서는 관측 도구를 항상 켜두는 것이 부담이 될 수 있다.

로그 보안: 세션 로그를 저장하면 프롬프트 내용과 코드 스니펫이 디스크에 쌓인다. 로컬-퍼스트 도구라도 로그 파일 자체의 접근 제어와 보존 정책을 명시적으로 설정해야 한다.

버전 의존성: 세션 파일 포맷은 에이전트 버전 업데이트마다 바뀔 수 있다. 도구가 특정 포맷에 의존하면 에이전트 업데이트 후 파서가 깨진다. Agent-Blackbox의 장기적 신뢰성은 이 유지보수 문제를 얼마나 잘 처리하느냐에 달렸다.

9. 결론 — 블랙박스에서 꺼낸 질문이 더 중요하다

Agent-Blackbox가 제기하는 질문은 도구 그 자체보다 중요하다. "에이전트가 무엇을 했는지 알고 있는가?" 2026년 6월 기준으로 대부분의 팀이 이 질문에 "잘 모른다"고 답할 것이다. 비용 숫자는 보이지만, 그 숫자가 어디서 왔는지는 보이지 않는다.

에이전트 관측성은 선택 사항이 아니라 에이전트를 프로덕션에서 쓰는 팀이라면 반드시 갖춰야 할 인프라 레이어가 되고 있다. 세션 맵으로 낭비를 찾고, 고정 오버헤드를 줄이고, 멀티에이전트 중복을 제거하는 과정은 결국 에이전트 실행을 더 예측 가능하고, 더 저렴하고, 더 디버깅하기 쉬운 시스템으로 만드는 작업이다.

Agent-Blackbox는 이 방향으로 가는 초기 도구다. 지금 당장 완성된 솔루션은 아니지만, 접근법이 맞다. 에이전트 실행을 블랙박스 상태로 놔두는 비용은, 관측 도구를 도입하는 비용보다 빠르게 커지고 있다.
