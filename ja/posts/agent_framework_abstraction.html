エージェントをコードで何として表現するか - クラス・グラフ・設定ファイルがそれぞれ隠すもの

抽象化を選んだ瞬間、デバッグと再開と移植のコストも一緒に決まる

2026年9月1日 開発・インフラ

エージェントを作るとき最初に選ぶのはモデルでもツールでもない。エージェントをコードで何と呼ぶかである。クラスか、グラフのノードか、設定ファイルの一項目か、プロンプトを書いたテキストファイル一枚か。初日は文法の好みのように見えて、二か月後に請求書として返ってくる。

請求書の項目は決まっている。モデルに実際に何が送られたかを確認する時間、途切れた作業を継ぎ足せるか、ログを読むためにフレームワークの文書も一緒に開く必要があるか、別のものに移すとき何を捨てるか。抽象化はこの四つを静かに前もって決めておく。きっかけになったリポジトリは四つの筋のうち一つを最も鮮明に押し進めた事例なので出発点として都合がよいだけで、そのプロジェクトを紹介することが目的ではない。

この記事は複数のエージェントフレームワークの設計方式を比較するが、どちらが優れているという評価はしない。引用した設計上の事実は各プロジェクトの公式文書とリポジトリで確認した2026年9月初め時点のものであり、この分野はバージョン間の変更が多い。

きっかけ - エージェントがPythonのクラスになるとき

NVIDIA-NeMo 組織の labs-OO-Agents リポジトリは名前のとおりである。フィールドが状態、メソッドが能力、ドックストリングがプロンプト、型注釈が契約だ。本体が ... のメソッドは実行時にモデルが埋め、コードのあるメソッドは決定的な Python のまま残る。

from nooa import Agent

class SupportAgent(Agent):
    """You are a support agent."""
    order_db: OrderDB

    def is_refund_eligible(self, order: Order) -> bool:
        return order.delivered and order.days_since_delivery <= 30

    async def triage(self, message: str, order: Order) -> Ticket:
        """Create a typed support ticket."""
        ...

この十二行のなかに、普通は三か所に分かれているものが集まっている。システムプロンプト、ツールスキーマ、コールバックである。メソッド名と引数とドックストリングがそのままプロンプトなので、ドックストリングを直せば指示が変わる。モデルは self と読み込まれたモジュールにアクセスできる Jupyter 風の REPL で Python を書いて行動する。

  • PyPI パッケージ nooa の公開バージョンは7月30日の 0.0.7 から8月18日の 0.0.9 までである
  • ライセンスは Apache-2.0、LICENSE の著作権表示は NVIDIA CORPORATION & AFFILIATES。個人の実験ではなく社内ラボの成果物である
  • 文書は自らを研究用ソフトウェアと書く。AST 検査とモジュール遮断リストは多層防御の一枚であって隔離の境界ではなく、隔離はコンテナや VM のような OS レベルだと明記する
  • 同名の論文が7月22日に arXiv に上がっている。著者15名、六つの概念として型のある入出力・生きたオブジェクトへの参照渡し・行動としてのコード・ループ設計・明示的なオブジェクト状態・モデルが呼べるハーネス API を挙げる

ここまでがリポジトリと論文の要旨から直接確認できることだ。この記事が関心を持つのはその先である。なぜよりによってクラスなのか、クラスと呼ぶことにすると六か月後に何が決まっているのか。フレームワークを一つ分解する作業はTypeScript サンドボックスのフレームワークを扱った記事でやったので、ここでは表現の仕方そのものを見る。

表現の仕方は四つに集まる

いま使えるものを並べると、表現の仕方はおおむね四つの筋に集まる。それぞれが自然にするコードの形が違い、だからこそぎこちなくするものも違う。

筋エージェントとは何か自然になるコードぎこちなくなること
オブジェクトクラスのインスタンス。フィールドが状態、メソッドが能力継承による共通動作の再利用、型による契約の固定流れを一枚の図で見せること
グラフ・状態機械ノードとエッジ。状態がグラフを流れる分岐・並列・中断点を構造で表現エージェントの同一性がノードに散る
宣言的な設定YAML・JSON の項目。役割・目標・ツールの列挙開発者でない人も直せる、変更履歴が短い条件分岐。結局コードへ逃げる
プロンプトファイルMarkdown 一枚。本文がそのままシステムプロンプトプロンプトをそのまま読み diff で検討型・再利用・組み立て

実際の実装が四つのどれか一つに純粋にとどまることはまれである。ただし主たる筋は文書の最初の画面で見える。最初の例がクラスならオブジェクト寄り、ノードを登録するコードならグラフ寄りだ。

  • Pydantic AI の Agent は依存型と出力型についてジェネリックなクラスである。文書は Agent[Foobar, list[str]] のような表記を例に挙げる
  • OpenAI Agents SDK の Agent は名前・指示文・モデル・ツール・ハンドオフ・出力型をフィールドに持ち、コンテキスト型についてジェネリックだ。指示文の位置に関数を入れることもできる
  • LangGraph は利用者が定義した State でパラメータ化された StateGraph が中心である。ノードは状態を受け取り更新分を返し、エッジは次のノードを決める
  • CrewAI は役割・目標・背景の物語でエージェントを規定する。新しいプロジェクトは agents/<名前>.jsonc を使う設定優先の方式で、以前の config/agents.yaml も引き続き支援される
  • AutoGen のコア文書はエージェントを、メッセージで通信し自分の状態を保ち受け取ったメッセージに反応して行動するソフトウェア実体と定義する。メッセージが唯一の接点である
  • Claude Code のサブエージェントは YAML フロントマターの付いた Markdown ファイルで、本文がそのままシステムプロンプトだ
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

先のクラスの例とこのファイルがスペクトルの両端である。一方は型と継承を最大限に引き寄せ、もう一方はテキストファイル一枚で済ませる。どちらが正しいかではなく、各地点が払う代償が違うということが要点だ。

オブジェクトで包んで得るもの

オブジェクト指向で包む側の利点は優雅さではなく、道具が代わりにやってくれる仕事から来る。

  • エディタが分かる。補完が効き、引数名の打ち間違いが保存時に捕まり、名前変更が呼び出し元まで追う。文字列定数としてしかなければどれも起きない
  • 型が境界を固定する。出力型を宣言しておけばモデルが妙なものを吐いたときその場で止まる。三段上で見当違いに落ちない
  • 共通動作が一か所に集まる。リトライ、予算上限、監査ログを基底クラスに一度書けば下位すべてに効く
  • テストダブルを差し込みやすい。モデル呼び出しのメソッドだけ上書きすれば残りをモデルなしで試せる。CI で回せるかどうかがここで分かれる
  • 決定的なコードとモデルの判断が一つのファイルにある。返金資格の判定は Python で、問い合わせの分類はモデルに任せる形だ。散らばると責任の境界がぼやける

最後の項目が最も大きい。エージェントのコードが長く生き残るかどうかは、規則として書けるものをモデルに任せなかったかにかかっている。配送が三十日以内かの判定をモデルに聞けばたいてい当たるがたまに外し、そのたまにが返金事故になる。本体があれば決定的、... ならモデルの担当という規則は、その境界線を文法に刻んでおく。

オブジェクトで包むと隠れるもの

代償は一か所に集中する。モデルに実際に送られるプロンプトが、ソースのどこにも丸ごと書かれていない状態になることだ。ドックストリングとシグネチャと基底クラスが足した断片と実行時の注入が合わさった結果なので、最終形は計算しないと分からない。

この問題は継承の深さに比例して大きくなる。基底クラスに共通の指示を一行入れるのは再利用だが、三段下のクラスを読む人はその行が付いていること自体を知らない。ツール一覧も同じだ。デコレータで登録されミックスインで合成され実行時に絞られると、ツールが何個付いているかをソースだけ読んで数えることはできない。

Anthropic のエージェント設計に関する記事も同じ場所を指摘する。フレームワークが下にあるプロンプトと応答を覆う層を足してデバッグを難しくすることが多く、下で何が起きているかについての誤った仮定がよくある誤りの原因だという。特定の製品ではなく層を積む行為一般についての指摘である。

  • 隠れが危険になる瞬間は障害の三十分後だ。そのとき要るのはモデルが受け取ったテキストの全文である
  • だから初日に確認すべきは機能一覧ではなく最終ペイロードをファイルに落とす方法だ。一行でできるなら継承が深くても耐えられる
  • 既定でトレースが有効かも選定基準になる。先のリポジトリはすべての呼び出しが既定で追跡されると明記する。有効であることと有効にできることは違う
  • 継承を浅く保つのも手だ。二段までは読まれ、四段からは読まれない
  • 共通のプロンプト断片をクラス内の文字列に埋めるのではなくファイルに出して名前で参照すれば検索できる

グラフが見せるものと散らすもの

グラフ側の強みは流れがデータ構造になる点にある。データ構造なら描けるし、検査できるし、止まる規則を構造で定義できる。命令型の関数のなかに if で散った分岐はこの三つのどれもできない。

LangGraph の文書はこの構造を簡潔にまとめている。ノードが仕事をし、エッジが次を教える。状態スキーマはすべてのノードとエッジの入力スキーマになり、各キーにはリデューサが付く。リデューサを明示しないとそのキーの更新はすべて上書きだ。この既定値が微妙なバグの常連の場所である。積み上がるべき会話履歴を上書きにすると最後のものしか残らず、症状が文脈の喪失として現れてプロンプトの問題と誤認される。

グラフが払う代償は同一性だ。一つのエージェントが何をするかを見るにはノードとエッジをたどらねばならない。流れが複雑なほどグラフが勝ち、エージェント一つ一つが厚いほどオブジェクトが勝つ。いくつに割るかはサブエージェントの個数を扱った記事にある。

  • グラフは流れをコードが握る側に傾く。ノードを事前に登録するので、なかった経路が実行中に生じにくい
  • その性質は再現性に有利で想定外の入力に不利だ。定義されていない状況も定義された経路へ流れてしまう
  • グラフ定義はフレームワーク固有の語彙が多く、移すのが最も難しい資産に属する
  • 逆に中断点を構造で定義できるのはグラフだけの利点だ。人の承認が挟まる流れで大きい
  • リデューサを明示する習慣は安上がりで効果が大きい。上書きが正しいキーにも書いておけば意図か放置かが区別できる

宣言的な設定がぶつかる天井

設定ファイル方式の利点は社会的なところにある。開発者でない人が開いて読み直せて、変更履歴が短く明確なのでレビューで議論しやすい。プロンプトの文言を企画者が直接直す組織なら、この利点が他のすべてを圧倒する。

天井は条件分岐から来る。この場合だけあのツールを使うという要求が入った瞬間、設定言語はプログラミング言語の真似を始める。次の分かれ道は二つだけだ。式の文法を設定に入れるか、コードへ出る抜け道を開けるか。前者はデバッガも型検査器もない小さな言語を新たに作る仕事で、後者は設定とコードの両方を読まないと全体が見えない状態を作る。

  • 設定に残すとよいもの — 人が頻繁に調整し分岐のない値。役割の説明、温度、モデル名、ツールの許可一覧
  • コードへ送るべきもの — 条件、反復、計算、外部状態の照会。設定の中で真似すると必ず読みにくくなる
  • 同じ概念が二か所に分かれた状態が最も悪い。ツール一覧の半分がファイルに半分がデコレータにあると全体を知る人がいなくなる
  • 設定優先の方式がコード側の入口を残しているのは、この天井を知っている設計である

プロンプトファイル - 最も薄い抽象化

Markdown 一枚がそのままエージェントである方式は、先の問題を一つ丸ごと消す。何がモデルに送られたかが問いにならない。ファイルに書かれたものが送られたからだ。フロントマターに名前と説明とツールの許可一覧を書き、その下の本文がシステムプロンプトになる。

Claude Code の文書はこの境界を明示する。サブエージェントはこのシステムプロンプトと作業ディレクトリのような基本的な環境情報だけを受け取り、全体のシステムプロンプトは受け取らないという。何が入らないかまで書かれている点がこの方式の性格を示している。

代償はプログラミングから来る。型がないので出力の形はプロンプトで頼むしかなく、共通部分を抜き出すにはテキスト取り込みの機能が要り、その瞬間また前節の問題に戻る。役割を分ける構成がどこまで成り立つかは役割分担のシミュレーションを扱った記事にある。

  • 合う場所 — 人が頻繁に手を入れ、流れが一本道で、成果物がテキストの作業
  • 合わない場所 — 出力が他のシステムの入力になり、スキーマを破ってはならない作業
  • 隠れた利点はバージョン管理との相性だ。プロンプトの変更が diff で見え、巻き戻しがファイルの巻き戻しである
  • 隠れた欠点は検索だ。同じ指示が十か所に複製され、一つだけ直して直したつもりになる

最大の分かれ道 - 流れを誰が握るか

ここまで見た四つの筋は表現の仕方の違いである。ところがシステムの性質を実際に決めるのはその下の問いだ。次に何をするかをコードが決めるのか、モデルが決めるのか。Anthropic は両者を名前で分けている。ワークフローは LLM とツールがあらかじめ定められたコード経路に沿って調整されるシステムで、エージェントは LLM が自分の過程とツール利用を自ら指揮するシステムだ。

フレームワークごとにこのスイッチをどこに置くかが違い、その位置は表現の仕方より結果に大きく影響する。同じクラス基盤でも流れをコードが全部握ればワークフローに近く、モデルが REPL で次の行動を作れば反対の端に近い。

流れの主合う表現うまくいくこと崩れる場所失敗時の症状
コードが全部握るグラフ・命令型の関数再現性、コスト予測、テスト定義されていない入力静かに誤った経路を完走する
モデルが全部握るプロンプトファイル・単一ループ初めて見る状況、探索ループと重複呼び出し、予算同じツールを八回呼んで止まる
コードが骨格、モデルが区間オブジェクト（決定的＋生成メソッド）実務の大半境界をどこに引くか誤って引かれた区間だけで失敗する
モデルがコードを書いて流れを作るREPL・コード実行環境分岐と反復を一度に隔離がないときサンドボックスの外で事故が起きる

三行目と四行目を一緒に使うのがいま出ている設計の流れだ。表現力は増えるが実行環境がそのまま攻撃面になる。先の文書が AST 検査と遮断リストを隔離の境界ではないとわざわざ念を押す理由である。四行目を選んだ全員が共に負う負担だ。

行動をJSONで書くかコードで書くか

モデルがツールを呼ぶ方法にも二つの筋があり、この選択は前節の分かれ道とくっついている。smolagents は両方を並べて実装している。CodeAgent はツール呼び出しを Python のコード片として作り、ToolCallingAgent は JSON で書く。文書はどちらも使えるとしたうえで、ウェブ閲覧のように毎回の相互作用のあとに待つ必要がある作業には JSON が合うと書く。

  • コード側の利点 — 一度の行動のなかに反復と条件と中間変数が入る。二十件の一覧をなめる仕事が往復一回になる
  • コード側の費用 — 実行環境全体が信頼境界の内側に入る。モジュール、ファイルシステム、ネットワークがすべて考慮対象だ
  • JSON 側の利点 — 引数をスキーマで検証でき、監査ログが均一なので数えたり再生したりしやすい
  • JSON 側の費用 — 往復が増える。トークンと遅延が増え、文脈が切れる確率も増える
  • 表現の仕方との関係 — オブジェクトを REPL に露出する設計はコード側へ、ツールを独立した関数の一覧として置く設計は JSON 側へ傾く

コードで行動する方式が本質的に賢いわけではない。表現の密度が高い代わりに検証点が減る交換である。ツールが純粋な計算に近いほどコード側が勝ち、外の世界を変えるツールほど JSON 側の検証点が値を持つ。

状態と再開 - 直列化が問い返すもの

短い作業ではどんな抽象化でもよく回る。問い返してくるのは長く回る作業だ。三十分の作業が二十五分目で死んだとき何が残っているか。それぞれの筋が違う答えを出す。

グラフ側は正面から扱う。LangGraph はコンパイル時にチェックポインタを指定でき、チェックポイントはスーパーステップの境界で保存されて割り込みや失敗のあとに再開できるようにする。流れがデータ構造だからどこで止まったかを値で表現できる。

オブジェクト側でこの問いはインスタンスをどう直列化するかになる。生きたオブジェクトに参照を渡す設計は表現力を得るが、その参照はプロセスの外へ出られない。開いたソケットやファイル記述子は値ではなくハンドルだからだ。先のパッケージが PyPI の要約で自らをイベントソーシングと直列化された実行を備えたシステムと紹介しているのは、この問題を設計段階で扱っている合図である。

プロンプトファイル側は状態をまったく持たない方向で答える。会話の記録がそのまま状態で、再開は記録をもう一度食わせることだ。単純で丈夫だが、記録が長くなればそのままトークンの費用になる。

  • 状態は値かハンドルか。値なら保存され、ハンドルなら保存されない。再開が要件ならこの区別を初期に引くべきだ
  • 保存地点はどこか。毎回のツール呼び出しの後かノードの境界かで、最悪の損失区間が決まる
  • 再実行は冪等か。チェックポイントから始め直すとき同じ決済 API を二度呼ばないか。フレームワークは保証しない
  • 保存形式はデプロイをまたげるか。読めないなら、デプロイのたびに進行中の作業が消える

確認の方法は一つだ。導入の最初の週に三回目のツール呼び出しのあとでプロセスを強制的に殺してみることである。この実験一回が文書より多くを教えてくれる。

可観測性 - ログがフレームワークの言葉に変わるとき

抽象化の層が増えるとログも層を得る。ノード3でリデューサがどうこうという行は、そのフレームワークの文書を知る人にだけ文であり、知らない人には音だ。深夜に呼び出された人がその文書を初めて開く状況を考えれば、なぜ費用なのかがはっきりする。

必要なログは二種類ある。一つはモデルとやり取りした原本だ。最終プロンプト、応答の全文、ツールへの引数、ツールが返した結果。もう一つはフレームワークの実行記録である。後者しかなければデバッグが推測になる。なぜこの答えが出たのかを聞いたのに、どこを通ったかだけ教えられる格好だ。

  • よい合図 — トレースが既定で有効で、呼び出しが親子の関係を保ったまま残る。先のリポジトリはこの性質を文書に明記し、CLI でビューアを立ち上げる
  • 注意すべき合図 — トレースを見るのに外部サービスへの登録が要る構造。データが出る経路が増え、サービスが落ちればその日の調査が止まる
  • 最低線 — 一回の実行の原本がローカルのファイルに落ちること。ダッシュボードはその次だ
  • 数えること — ログ一行にフレームワークの概念がいくつ要るか。三つを超えるとそのログは知る人しか読めない

エージェントを複数つなげるとこの費用が掛け算になる。調整そのものの費用はオーケストレーション税を扱った記事にまとめた。

ロックインの実際の大きさ

選ぶときいちばん心配されるのがロックインだが、心配の大きさと実際の大きさがよく合わない。移す費用はコードの行数ではなくそれがテキストかフレームワーク固有の形式かから来る。

資産移す難しさ理由
プロンプトのテキスト易しいただのテキストだ。貼り付ければよい
ツール関数の本体易しいたいていは普通の関数。デコレータを差し替えるだけ
出力スキーマ普通標準の型ライブラリに乗っていればそのまま行く。独自型なら書き直す
流れの構造難しいグラフ定義、継承の連鎖、ハンドオフ規則はそのフレームワークの語彙だ
保存済みチェックポイント非常に難しい形式がフレームワークのものだ。進行中の作業は捨てる
トレースと評価の履歴非常に難しいスキーマが違う。回帰を比べる基準線を失う
チームの思考の癖最も難しい人がそのフレームワークの概念で問題を切り分け始める

最後の二行が本当のロックインだ。コードは書き直せばよいが、評価の基準線を失うと新しい構成が以前より良いかを証明する方法がなくなる。半年ほど使うと人が問題をそのフレームワークの概念で切って話すようになるが、これは移行の文書に書かれない費用である。

  • プロンプトをクラス内の文字列ではなくファイルか定数モジュールに出しておく。移行費用のかなりの部分が消える
  • ツールはデコレータの付かない純粋な関数として書き、登録は薄いアダプタで行う。アダプタだけ書き直せばよい
  • 評価データセットと判定基準はフレームワークの外のファイルに置く。最後の二行のうち一つを消してくれる

フレームワークを使わない方が正しい条件

Anthropic の勧めは明確だ。LLM API を直接呼ぶところから始めることを勧め、多くのパターンは数行で実装できると書く。フレームワークが、より単純な構成で足りる場所に複雑さを足したくさせることがあるとも付け加える。

messages = [{"role": "user", "content": task}]
while True:
    reply = client.messages.create(model=MODEL, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": reply.content})
    calls = [b for b in reply.content if b.type == "tool_use"]
    if not calls:
        return reply
    results = [run_tool(c) for c in calls]   # ここから先は全部自分のコードだ
    messages.append({"role": "user", "content": results})

この九行には隠れたものがない。何が出て何が入るかが変数名で見える。代わりにリトライも予算上限も再開も並列も自分で書かねばならない。問題は、この九行が六か月後に九行のままではないことだ。

  • 自前のループで十分な条件その一 — 流れが一本道で分岐を指で数えられる
  • その二 — ツールが十個以内で互いに状態を共有しない
  • その三 — 作業が一リクエスト内で終わり、再開が要件でない
  • その四 — 人が一人か二人で、規約を文書なしで保てる
  • その五 — ログの形式を自分で決めたく、そうする理由がある
  • フレームワークが値を持つ条件その一 — 人が複数いてそれぞれエージェントを追加する。共通規約がコードで強制されねばならない
  • その二 — 再開と人の承認の介入が要件だ。自分で作れば結局フレームワークを一つ作ることになる
  • その三 — 複数の提供者と複数のモデルを差し替える
  • その四 — トレースと評価を最初から均一に積む必要がある。遡るのが最も難しい項目だ

実際によく出る答えは中間である。ループは自分で書きトレースと評価だけライブラリを使うか、フレームワークを使いつつプロンプトとツールを外のファイルに置く形だ。全部使うか全部使わないかの選択に見えること自体が、すでにフレームワークの語彙である。

選ぶ前に答えておく六つ

機能の比較表は役に立たない。どちらでも結局は全部できるからだ。代わりに候補を数日使いながら以下の六つに答えておけば、半年後に何が痛むかが見える。

  • プロンプトの全文をファイルに落とすのに何分かかるか。十分を超えると障害対応の時間がその分伸びる
  • ツール一覧をソースだけ読んで数えられるか。できなければ権限の検討が実行ログの検討になる
  • 三回目のツール呼び出しのあとでプロセスを殺すと何が残るか。何も残らないなら長い作業はこの構成でしない
  • 流れの分岐をコードが握るのかモデルが握るのか、その答えが文書に書かれているか。なければ二つが混ざっており、混ざった場所が事故の地点になる
  • フレームワークを知らない同僚がログだけ読んで何が悪いか言えるか。言えなければ運用が一人に縛られる
  • このフレームワークを外したら何を書き直すことになるか。プロンプトとツール関数だけならロックインは浅く、評価の履歴が混じっていれば深い

抽象化は何を簡単にするかを選ぶ仕事であり、簡単になったものは多く起きる。クラスと呼べば継承で共有し始め、グラフと呼べばノードを割り始め、ファイルと呼べばファイルが増える。選んだ瞬間、チームが半年のあいだ頻繁にする動作が決まる。フレームワークがその答えを代わりに決めてはくれないが、何を簡単にしてあるかは最初の例に全部出ている。文書の最初の画面を設計の宣言として読めば比較表より多くが見える。

確認できなかったこと

  • リポジトリのコミット数は一覧画面で322件と表示されるが、これは既定ブランチ基準で時点によって変わる。ブランチやタグ別の内訳は確認していない
  • 論文の SWE-bench Verified と Terminal-Bench 2.0 の結果は要旨の範囲でのみ確認し、本文の表は開いていない。だから性能の数値は一つも書いていない
  • ここに挙げたフレームワークを同じ条件で比較した資料は確認できなかった。どちらが優れているとは言わない理由である
  • 記した設計上の事実は2026年9月初め時点の各プロジェクト公式文書に基づく。設定ファイルの形式は最近変わった例がある
  • フレームワークを乗り換えたチームの実際の移行費用を定量化した調査は見つからなかった。12節の難易度の区分は測定値ではない
