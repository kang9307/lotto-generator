What a Specification Catches That Tests Do Not - The Sweep, the State Explosion Bill, and the Distance Left to the Code

It is not that tests cannot catch it; it is that tests are unlikely to produce that ordering

2026-09-10 Dev & Infra

There is a comparison that puts a model checker next to a proof assistant. Mathematicians have a tool that checks proofs mechanically, the argument goes, and developers have a tool that checks designs mechanically. The comparison is useful. It is also only half right, because the two tools examine different objects.

Here is where the comparison holds. A program that passes its type checker and its unit tests and then breaks the moment it runs concurrently is an ordinary event. Two jobs may each preserve their own internal order, and the number of ways those two orders can be shuffled together is already beyond anything a person enumerates by hand. The handful of scenarios a developer picks is a sample drawn from that number. If a tool exists that sweeps everything instead of enlarging the sample, it is worth having in that spot.

Here is where the comparison breaks, in two places. First, sweeping everything comes with a bill. The cost of checking grows exponentially with the size of the model. What actually runs in practice is therefore always a very small model, and the absence of a defect in a small model is not the absence of that defect in a large system. Second, what the model checker examined is a model of the design, not the code. Even after the specification passes, that the implementation follows it is a guarantee that has to be manufactured separately.

There are no state counts or checking times in this article. Those values shift by orders of magnitude with the number of variables, the size of the constants and the checker settings, and a number stripped of its conditions becomes false the moment it is quoted elsewhere. What follows are properties, conditions and limits instead. The numbers for your model come out of your model.

The trigger - putting a model checker beside a proof checker

The mathematical tool treats a proposition as a type and a proof as a value of that type. The language is arranged so that saying a value has a certain type is the same as saying that value is a proof of that proposition. It works by checking that a function producing evidence for an arbitrary object is correctly constructed, which is why the phrase the proof compiles makes sense at all.

The tool that occupies the corresponding position on the development side is a formal specification language and a model checker. The object of examination here is not a proof but a state machine. You write down the states the system can hold as variables, and you write down which state may follow which as a relation. The checker then starts from the initial state, generates every state reachable through that relation, and looks for a point where a condition you wrote down is broken.

The comparison is useful because in both cases the verdict comes from a machine rather than from a pair of eyes. The comparison is dangerous because surface similarity suggests the two tools guarantee the same amount. What the formalization of a mathematical proof does and does not guarantee is laid out separately in Formalization Is Not Proof. What this article deals with is the other side: state exploration for concurrent and distributed design.

What each one examines - the path that ran and the states that are reachable

The difference between the two methods is not the difficulty of the defect. It is the object of observation.

  • What a unit test observes — one path that actually executed, under inputs the author chose. If several threads are involved, whatever ordering happened to be scheduled on that machine that day is fixed along with it. Running the same test a thousand times can produce the same ordering a thousand times.
  • What a model checker observes — it generates every next state the model permits and sweeps the reachable state space. Where you did not say which action goes first, both branches are taken. Interleavings that nobody imagined get tried automatically.
  • The limit both share — neither checks what was not written. A test knows nothing of a case that was never authored, and a model checker knows nothing of a transition that was never put in the specification. The second failure mode is the more dangerous one, and it gets its own section below.

There is a phrase that slips here, and it slips often: a defect tests cannot catch. That is not accurate. Race-driven defects do blow up in tests when the timing lands, and a good share of the intermittently red entries in any suite are exactly those defects. The accurate sentence is different: tests are unlikely to produce that ordering. Unlikely and impossible are not the same word, and the difference changes which tool you reach for.

Being unlikely has two practical consequences. One is that reproduction is hard. If you cannot rebuild the same conditions after it blew up, you cannot confirm that the fix fixed anything. The other is that intermittent failures get dismissed. It passes on a rerun, so the conclusion drifts toward the suite being flaky. What a model checker offers is not a higher probability but the removal of probability. If an ordering is possible inside the model, you meet it.

Counting the orderings - what the number 184,756 actually measures

Take two jobs of ten steps each. Order inside a job is preserved, so the third step of A comes after the second step of A. What is not fixed is how the steps of A and the steps of B interleave with one another.

The number of possible execution orders then becomes the question of which ten of the twenty slots belong to A. The answer is 184,756, which is twenty factorial divided by ten factorial squared. The state space itself is finite and there are only two jobs, and ordering alone produces that many runs.

What matters in that number is not its size but the shape of its growth. Raise the jobs to three, or the steps to twenty, and the value does not creep upward. And a real system adds something on top of ordering: partial failure. Each step can succeed or fail, a failure attracts a retry, and a retry can create a duplicate. The count of failure points multiplies into the count of orderings.

For a person to pick scenarios is to reach into the product of that multiplication and take five or six. A good eye picks well and a poor eye picks badly, and the real problem is that there is no way to judge which happened. Coverage numbers report whether lines of code executed; they say nothing about whether orderings were swept.

Which kinds of defect surface, and which do not

Writing down the defects each method catches well draws the line clearly. It is worth noticing that neither column in the table below says impossible. What differs is probability and cost.

Defect type Caught by tests Caught by model checking Why
Wrong arithmetic (boundaries, rounding, sign) Caught well Mostly not caught A model usually abstracts the arithmetic away. It was built to look at ordering, not at values.
Null dereference, type mismatch Caught well Out of scope These live at the language level and the specification has no such notion. That is the territory of type checkers and tests.
Two jobs racing over one shared resource Unlikely Caught reliably It appears only under a specific interleaving. The checker turns that interleaving from an accident into a rule.
A retry causing a duplicate effect Unlikely Caught reliably It emerges only from the combination of failure and resend. Producing that combination live requires injecting faults.
Writes lost during a leader handover Very unlikely Caught if the transition is in the model It holds only in the short window where handover and write overlap. Leave that transition out and the checker cannot see it either.
Cache invalidation reordered, stale value survives Unlikely Caught The issue is the relative order of write and invalidation, so sweeping all orders is the favourable approach.
Deadlock and stalls (nobody can proceed) Caught if reproduced Caught The checker directly looks for a state with no successor. At runtime, stopped and slow are indistinguishable.
Starvation (some party keeps getting deferred) Almost never caught Caught if fairness is written This is liveness territory. Without a fairness assumption the question cannot even be decided.
Performance regression, latency growth Caught by measurement Out of scope There is no time in the model. There is ordering, but no duration.
The requirement itself is wrong Not caught Not caught Both check what was written down. If what was written is wrong, a pass means nothing at all.

The last row is the important one. Both tools check what a person wrote. What differs is the language they are written in, and therefore the kind of thinking a person is forced into while writing. It happens often enough that the answer arrives while the specification is being drafted, and the checker never needs to run.

One example - two jobs sharing a single connection

The argument needs a concrete shape. Consider two asynchronous jobs sharing one connection, where each job closes that connection during its own cleanup. Written with a stream library, it takes this form.

// The defective arrangement - cleanup is attached to each job
merge(
  jobA$.pipe(finalize(() => resource.close())),
  jobB$.pipe(finalize(() => resource.close())),
).subscribe();

// The fixed arrangement - the connection's lifetime follows the outer subscription
merge(jobA$, jobB$).pipe(
  finalize(() => resource.close()),
).subscribe();

One ordering is enough to expose what the first arrangement does. If A finishes first, A's cleanup runs and closes the connection, and B, which is still running, uses a closed connection. If B finishes first the same thing happens by symmetry. If the two finish at almost the same moment, nothing happens at all.

That is precisely why the defect rarely appears in testing. In a development environment the two jobs tend to be of similar length, or one is so short that cleanup lands after the other has already finished. The condition where the two durations diverge gets created for the first time under real traffic. And when it does, the symptom shows up not in the cleanup code but on the side that uses the connection.

What the fixed arrangement does is simple: it moves the resource's lifetime to its owner. Neither job owns the connection; the outer subscription that merges them does. Lift the cleanup to that level and the connection closes only after the last job ends. This correction removes a defect while removing code, which puts it in a rare category.

The order you write a specification in - variables, initial state, next-state relation

Moving the same situation into a model imposes a fixed order of writing. Choose the state variables, write the initial state, write the relation that carries one state to the next, and write the condition that must hold. There is no other slot to write anything in.

---- MODULE SharedConnection ----
VARIABLES connection, aRunning, bRunning
vars == <<connection, aRunning, bRunning>>

Init == /\ connection = "open"
        /\ aRunning   = TRUE
        /\ bRunning   = TRUE

\* A closes the connection on its own way out - the defective design
FinishA == /\ aRunning
           /\ aRunning'   = FALSE
           /\ connection' = "closed"
           /\ UNCHANGED bRunning

FinishB == /\ bRunning
           /\ bRunning'   = FALSE
           /\ connection' = "closed"
           /\ UNCHANGED aRunning

Next == FinishA \/ FinishB
Spec == Init /\ [][Next]_vars

\* Invariant - while a job is still running the connection must be open
Safe == (aRunning \/ bRunning) => connection = "open"
====

Reading it goes like this. A name carrying a prime refers to its value in the next state. The line aRunning' = FALSE is not an assignment; it states a condition the next state has to satisfy. UNCHANGED says a variable stays as it was, and leaving it out lets the checker try arbitrary values for that variable.

The crucial detail is that Next is written as a choice between two actions. Nothing says which comes first, so the checker walks both branches. A program would have had its runtime pick one; in a specification, what you did not pick stays behind as a branch of the search.

Running it needs one configuration file naming what to check and what to check it against.

SPECIFICATION Spec
INVARIANT Safe
CHECK_DEADLOCK FALSE

On this model the checker finds a state where Safe breaks: A has finished and closed the connection while B is still running. And it emits the path that led to that state. The counterexample is the practical value of the method. Being told a condition broke is not enough to fix anything; knowing which ordering broke it is.

Invariants and liveness - always true versus eventually true

There are two kinds of condition you can write. Blur the distinction and you end up unable to explain why the checker keeps passing your specification.

Aspect Invariant (safety) Liveness property
In words Nothing bad ever happens Something good eventually happens
Unit of judgement One state is enough The whole sequence of states is required
Example sentence There are never two leaders at once Every request eventually receives a response
Shape of the counterexample A broken state and the path to it An infinite loop in which the good thing is deferred forever
Slot in the configuration file The invariant keyword The property keyword
Extra requirement None A fairness assumption is effectively mandatory
Cost of checking Comparatively cheap Considerably more expensive
Fit with reduction techniques Symmetry reduction combines well Symmetry reduction is hard to combine

An invariant is a sentence you can answer true or false about a single state. Safe in the example above is one. Two values decide it: whether a job is running and whether the connection is open. The checker therefore evaluates it on the spot, once per generated state.

Liveness does not work that way. Every request eventually receives a response cannot be judged true or false from any one moment, because nothing inside that state distinguishes a violation from a response that arrives a little later. Deciding it means looking at the sequence to its end, including sequences that never end.

Missing the distinction has a specific consequence in practice: writing only invariants and believing that progress has been verified too. A system that does nothing at all satisfies most invariants easily. Do nothing and nothing bad happens. A design that passes safety alone is therefore allowed to be frozen.

Without fairness, liveness properties fail almost every time

The specification language assumes the worst by default. An action that is available right now may never occur. Under that assumption nearly every sentence of the form eventually something becomes false, because a run in which nobody does anything is always permitted.

Checking liveness therefore requires attaching a fairness assumption to the specification. It is attached in two moves.

\* The specification with fairness - an action that can run does run eventually
FairSpec == Spec /\ WF_vars(Next)

Done     == /\ ~aRunning
            /\ ~bRunning

\* Liveness - once both jobs end, the connection eventually closes
Liveness == <>(Done /\ connection = "closed")

Here WF stands for weak fairness: an action that stays continuously enabled will eventually occur. Strong fairness demands more. It says that an action which merely becomes enabled infinitely often will eventually occur. In models where parties contend for a resource, the difference decides the outcome: there are runs that weak fairness permits and strong fairness rules out, and starvation lives in exactly that gap.

Fairness is not free. The moment you write the assumption, something on the system side has to make it true. That a scheduler never defers a thread forever, that retries do not fail indefinitely, are properties guaranteed by the operating environment rather than by code. If an assumption written casually in a specification does not hold in the field, the liveness property that passed is true only in a world where the assumption is true.

The price is state explosion

This is the central constraint of the method. Sweeping every reachable state means generating all of them and keeping them somewhere. Avoiding the re-expansion of a state you have already seen requires remembering what you have seen, and the count of things to remember sets the cost.

That count grows exponentially with the size of the model. Add a variable and the space multiplies by the number of values it can hold; add a participant and the per-participant state multiplies in. A small change such as raising the node count from three to four moves the state count by orders of magnitude. This is state explosion, and while there are mitigations, in principle there is no removing it.

The mitigations that exist look like this.

  • Make the model small — the most common approach by far. Three nodes, two values, a queue of length two: the minimum scale at which the defect can appear. It rests on the experience that the structure of a defect frequently does not depend on the number of participants.
  • Declare symmetry — collapse participants that need no distinguishing into one group, so that states differing only by naming count as the same state. It cuts the state count sharply but is hard to combine with liveness checking.
  • Raise the abstraction — keep only whether values differ rather than the values themselves. Two distinct elements instead of integers, a tag instead of a payload. This holds only when the size of a value plays no part in the property being checked.
  • Bound the ranges — cap the retry count or the queue length so nothing expands without limit. That cap defines the range of validity of the conclusion, and it has to be written down alongside it.

What these techniques share is that every one of them reduces cost by reducing the model. They do not make the checker faster; they make the thing being checked smaller. So the range of the conclusion shrinks by exactly as much as the cost you saved. That trade is the subject of the next section.

Absence in a small model is not absence in a large system

When the checker finds a violation, the counterexample is certain. Among the orderings the model permits, one really is like that. No qualifier attaches to a counterexample. That is what makes this method very strong as a defect finder.

When the checker finds nothing, the resulting sentence carries three qualifiers.

  • Within that size — run with three nodes, the conclusion concerns a three-node model. A defect that first appears at four was never in scope. Defects that require more participants to arise genuinely exist, so this is not a formality.
  • Within those assumptions — if you wrote that messages are never lost, the world where they are lost went unchecked. If you added fairness, only runs where that fairness holds were checked. Assumptions are the most powerful lever for shrinking a model, which is why they are the most frequently forgotten.
  • Within the transitions you wrote — this is the dangerous one. Omit an important transition and the checker has verified a system that does not have it. A pass comes out, and the pass means nothing, and on the results screen it looks exactly like a real pass.

The third item has the same structure as the difference between a log line saying the backup succeeded and the fact that a restore works, covered in where a successful backup lies. The meaning of a green light depends entirely on what that green light examined.

One habit follows for anyone writing specifications: put the defect in deliberately and see whether the checker catches it. Run the arrangement from before the cleanup was moved and a counterexample should appear; if none does, the model is in a state where it cannot express that defect at all. A model whose only observed outcome is a pass is a checker that has never itself been checked.

A passing specification does not certify the implementation

This is where the comparison with proof assistants parts ways. On the mathematical side, the formalized proof is itself the object of checking. The object and the checked artifact are the same thing. The only surviving gap is whether the statement of the theorem faithfully renders the proposition it meant to capture.

Model checking is not like that. The object of checking is a model of the design written out by hand, and what runs is separately the code. The gap therefore doubles.

  • The upper gap — does the specification render the real system correctly? Omitted transitions, assumptions that are too strong, and actions written as one step that are not actually atomic all live here.
  • The lower gap — does the code follow that specification? Shortcuts absent from the specification, places where one specified action becomes two in code, and whatever a library does behind the scenes all live here.

The article that prompted this is clear on the point. It records that results from the checker are valid only within the finite model and assumptions that were configured, that a model missing an important transition can pass and still miss a real defect, and that whether the design of the model was properly implemented in the actual code has to be verified separately. It also notes that a general proof over an unbounded range calls for a proof system rather than a model checker.

What the source does not unfold is what that separate verification consists of. Setting that out as requirements gives the next section.

Three requirements that narrow the gap

There are three ways to tie a specification to code. None of them is a complete guarantee, and the gap narrows as you stack them.

First, write a refinement relation

Write both an abstract specification and a concrete one, then check that every behaviour of the concrete one maps onto a behaviour of the abstract one. One step in the abstract specification may become several steps in the concrete one, and it still holds as long as what is visible from outside is the same. The value of this method is that it lets you insert an intermediate level. When design and code are too far apart, put a specification closer to the implementation in between and check twice.

The limit is plain. The concrete specification is still a specification. It is not code. However fine-grained the refinement, the last gap — between the concrete specification and the actual code — is not closed by this method.

Second, instrument execution and check it against the model

Emit state changes from running code as a trace, and check whether that trace is a run the specification permits. The direction matters: the previous method descends from the specification, and this one ascends from the code. Because it deals only with what actually happened, it does not sweep everything reachable, but in exchange its object is the real program.

What this demands is quality of instrumentation. Values corresponding to the specification's state variables have to be captured atomically at the same instant for the comparison to hold. Bundling values captured at different instants into one state fabricates a state that never existed, and that state comes back as a violation. Adding more logging and building instrumentation are different jobs.

Third, derive tests from the specification

Take the counterexamples or the explored paths the model checker produced and turn them into test scenarios to feed the code. Forcing the code to reproduce an ordering the specification found attacks the earlier problem — the ordering is unlikely — head on. Instead of waiting for the ordering to happen by chance, you build it.

The sticking point is the reproduction machinery. Forcing a particular interleaving requires being able to hold execution at chosen points, and structures divide into those where this is possible and those where it is not. Sometimes the design has to change so that inter-thread ordering becomes controllable from a test. In other words, this method imposes requirements on the code side.

Where it pays off and where it does not

The dividing criterion is not how hard the system is. It is whether the good state and the bad state can be written in a single sentence. If they can, there is something to check. If they cannot, no amount of careful modelling produces a verdict.

Subject Does the invariant fit in words Payoff Why
Consensus and leader election Yes (there are never two leaders at once) High The defect appears only in the handover window, and building that window in a test is extremely hard.
Replication and commit rules Yes (a committed entry is never lost) High Combinations of partial failure and retry are numerous, and loss happens quietly.
Leases and exclusive access Yes (only the lease holder writes) High The problem sits in the short window where expiry and renewal overlap, with clocks tangled in.
Transactions and isolation Yes (no disallowed read result occurs) High What is allowed is fixed by definition, which makes it easy to carry into a model.
Cache invalidation Yes (a read after a write never sees the old value) High Only the relative order of write and invalidation is at issue, so the model stays small.
Duplicate request suppression Yes (the same request is never applied twice) High It is a defect manufactured by retries, which makes it hard to reproduce in a live test.
Cancellation racing completion Yes (the result of a cancelled job is never applied) High The overlapping moment is narrow, and reading the code does not reveal that it overlaps at all.
Screen flow and usability No Low The definition of a good state is human judgement. There is nothing to formalize.
Performance and capacity No Low There is no time in the model. Ordering exists; duration does not.
Operational procedures with a human in them Only partly Low Human actions can be written as transitions, but the guarantee that they are followed sits outside the model.

The first seven rows share a property: the conditions under which the defect appears are narrow, and when it appears it is quiet. Defects that die loudly get found anyway. What persists is the defect that keeps running with a slightly wrong value, and those come mostly from ordering. The structure of a stall that arises when several parties share one resource has a physical example in deadlock from a full pipe buffer.

One more thing belongs here. Plenty of places do not look like distributed systems and are. A single setting changed independently on several devices and merged later is one of them, described in one toggle becoming a distributed system. Wherever a value is written concurrently and merged afterwards, that place already owns an ordering problem.

How to start - do not model the whole system

Failed adoptions look almost identical: an attempt to move the entire system into a specification. That attempt ends in a person's calendar well before it reaches state explosion. The source article recommends the same direction, saying to focus on one specific problem rather than modelling everything, and it names releasing a shared resource, suppressing duplicate requests, and cancellation racing completion as examples.

Laid out as a sequence, it is five steps. Not tool usage, but an order of judgement.

  • First, pick one sentence. Write down, as a sentence, the one thing that must never happen in this system. If it will not fit in a sentence, it is not a subject for model checking, and finding another method is faster.
  • Second, keep only the variables that sentence involves. Anything absent from the sentence stays out of the model. Payloads, timeout values and logging usually drop here. When in doubt, run first with it removed.
  • Third, run the defective design first. Watch the counterexample come out, then move to the corrected design. Start with the corrected design and you have no way to know what the pass means.
  • Fourth, raise the size one notch at a time. Go from two participants to three and three to four, and watch where the check stops terminating. That point is the upper limit of what this model can speak about.
  • Fifth, write the conclusion with its conditions attached. Record at what size, under which assumptions and with which transition set the check ran, in the same place as the specification. Without those three lines the next reader reads the pass as unbounded.

The fourth step teaches the most in practice. Raising the size reveals which variable dominates the state count, and whether that variable can be abstracted becomes the next decision. A check that does not terminate is not a failure; it is information about what the model demands at that point.

To close it out: what formal specification gives you is certain defect discovery and conditional absence of defects. No qualifier attaches to the first; three attach to the second. And either way, that the code follows the specification remains a separate proposition. Write all three down together and the specification becomes one of the rare design documents that stays useful for years. How far the idea of writing behaviour down as a sentence can be pushed is treated from another angle in what it really means to write behavior down as a spec.

What could not be confirmed

  • The checker output from the source article — the source carries the specification file, the configuration file and the run command, but no counterexample output and no count of explored states. Nothing beyond that is claimed here.
  • Concrete numbers for state counts and checking time — state counts and durations per model size vary by orders of magnitude with variable structure and execution environment. There is no basis for offering a general figure, so only the shape of the growth is described.
  • The actual requirements of the proof-system side — that a proof system exists for cases where a general result beyond a finite model is needed is as far as the source goes. Which back-end provers it uses and how much manual work it takes are left outside the scope here.
  • Alternative checkers based on symbolic execution — there is a family of checkers that treats state as constraints rather than enumerating it one by one, with different properties around state explosion, but their conditions of applicability were not compared and so are not asserted here.
  • Individual documents behind the industrial adoption list — the official site keeps a page collecting industrial use, with entries covering processor cache coherence protocols, cloud services and coordination services. Most of them are conference archives or presentations, and their individual claims were not cross-checked, which is why no organization names or outcome figures appear in the body.
  • The maturity of trace-checking tooling — checking execution traces against a specification is clear as a requirement, but which languages and runtimes have usable tooling for it was not surveyed. The body states only the conditions that approach demands.
  • Whether automated draft generation for models works — the source adds a forecast that writing specifications may get cheaper the way drafting tests has. No measurement supporting that forecast appears in the source, and the body does not treat it as one.
