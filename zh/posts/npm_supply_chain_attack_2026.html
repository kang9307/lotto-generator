引言: 22分钟内发生的事 - npm生态系统的定时炸弹

2026年5月19日(UTC凌晨),npm上一个维护者账号被盗,该账号管理的约300个包在约22分钟内被自动发布了637个恶意版本。包的数量因报道而略有不同:The Register报道为314个,SafeDep分析为317个。折算下来每分钟约发布29个恶意版本,这是人工无法达到的速度,因此判断为自动化脚本批量发布。22分钟这一短暂时间,以及一个账号就能左右数百个包的事实,是本次事件的核心,它表明JavaScript生态系统在维护者凭据这一单点故障上暴露得有多严重。

本次事件并非孤立问题。正如本文所整理的,npm从2018年event-stream、2021年ua-parser-js、2022年colors/faker、2024年lottiefiles,到2025年9月的Shai-Hulud蠕虫,几乎每年都经历大型供应链事故。根据SafeDep的分析,本次恶意代码与约3周前入侵SAP相关npm包时使用的Mini Shai-Hulud工具属于同一系列。受影响的包中有不少深嵌在其他库的依赖中,例如size-sensor(每月约420万次下载)、echarts-for-react(约380万)、@antv/scale(约220万)、timeago.js(约115万),即使从未听说过这些名字,也可能受到影响。

本文先用发现与分析报告以及GitHub和npm的官方公告核实事件事实,再为中国开发者和团队整理今日内应执行的4项紧急措施和7项长期防御策略。比起事件本身的技术细节,本文更关注可以立即落地的行动。2026-09-29再次对照一手资料,更正了事实并补充了后续进展。

事件概述 - 发生了什么、何时、如何

根据已公开的分析和报道,可以确认的事件轮廓如下。本文不直译安全advisory,只重新整理本文核实过的事实。

  • 时间: 2026年5月19日UTC 01:39左右开始。SafeDep将其记录为01:39~01:56和02:05~02:06两波,报道则概括为约22分钟的批量发布。
  • 规模: 恶意版本637个。包的数量为314个(The Register)~317个(SafeDep),包括@antv作用域下的大量包以及size-sensor、echarts-for-react、timeago.js等。
  • 入侵路径: 不是多名维护者的令牌,而是管理500多个AntV相关包(SafeDep统计为547个)的一个维护者账号。该账号如何被盗,公开分析中尚未说明。
  • 恶意代码性质: 不是postinstall,而是通过preinstall钩子运行约498KB的混淆Bun脚本。收集云(AWS、GCP、Azure)凭据、GitHub和npm令牌、SSH密钥、Kubernetes和Vault令牌、数据库连接字符串等,并外传到攻击者创建的GitHub公开仓库和外部服务器。
  • 发现与报告: 一名安全研究人员首先在GitHub上报告,SafeDep随后公开了详细分析(The Register报道)。
  • 处置: 部分版本被标记为deprecated并附上"误发布"提示,部分版本被删除。GitHub表示正在监控事态,并依据可接受使用政策停用恶意npm包。

值得注意的是"22分钟"这一短暂窗口。这个时间是否经过刻意设计尚未得到确认。但即使时间很短,按语义化版本范围(^、~)获取依赖的CI流水线也可能在这期间直接装上新版本,这说明比起检测速度,安装时刻的关卡更为重要。

攻击机制分析 - 凭据入侵 + 自动化批量发布

本次事件的技术核心并不是华丽的零日漏洞,而是"被盗凭据 + 自动化"这一平凡组合。平凡恰恰是关键:之所以不需要华丽的漏洞,是因为一个账号掌握数百个包发布权限的npm认证与发布模型本身就成了单点故障。

1) 账号被盗阶段

公开分析没有说明账号是通过什么途径被盗的。一般而言,npm账号被盗的常见途径包括钓鱼、维护者电脑上的恶意软件、重复利用过去泄露的令牌、.npmrc文件泄露等。既然本次恶意代码本身就会收集npm令牌和GitHub令牌,一次感染中泄露的令牌显然可能成为下一次入侵的钥匙。此外,即使开启了2FA,一旦2FA绕过令牌泄露,攻击者仍可接管账号,这一点GitHub也在公告中承认(见后续进展)。

2) 批量发布阶段(22分钟窗口)

只要拿到一个拥有发布权限的账号,把事先准备好的恶意变体依次publish到该账号的包上并不困难。通过自动化调用npm publish,每分钟发布几十个版本完全可行,约22分钟发布637个版本与此相符。

3) 载荷执行阶段(受害方)

恶意版本通过preinstall钩子用Bun运行时执行脚本。SafeDep分析指出,即使阻止了安装钩子,还存在第二条路径:通过github:形式的可选依赖从GitHub拉取提交。此外,它会在受感染电脑的AI编程工具和编辑器配置文件(.claude/settings.json、.vscode/tasks.json)中植入自动运行项并安装常驻服务,使一次安装扩散到同一台电脑上的其他工作区。在中国企业环境中,这一阶段的威胁分两类。(a) 本地开发PC入侵: 开发者不经意运行npm install后,令牌和密钥泄露并留下常驻后门。(b) CI/CD入侵: GitHub Actions或公司Jenkins在构建时密钥外泄。CI令牌通常权限范围较广,本文认为后者更危险。

类似事件的历史 - 同样结构反复出现

npm供应链攻击并非首次。代表性事件整理如下。

  • 2018 event-stream: 维护者交接后,新维护者植入恶意载荷,瞄准比特币钱包相关项目。首次让大众看到"信任的转让"是单点故障。
  • 2021 ua-parser-js: 维护者账号被入侵后发布恶意版本。由于是下载量很大的包,影响范围很广。
  • 2022 colors/faker: 维护者本人故意破坏代码的事件,再次提醒人们"信任是自愿的协作"。
  • 2023 大量typosquatting: 大量与热门包名称拼写相近的恶意包被注册。
  • 2024 lottiefiles等: 通过入侵SDK包来窃取用户钱包信息的事件。
  • 2025年9月 Shai-Hulud: 利用被盗维护者账号植入安装脚本并自我传播的蠕虫。据GitHub公布,超过500个包被入侵,GitHub随后提出了加强npm认证和令牌的计划。
  • 2026年5月 本次事件: 规模小于2025年的Shai-Hulud,但同一系列工具(Mini Shai-Hulud)每隔几周就被重复使用,这一点是新的。

这份列表的模式非常清楚:每次都是"维护者凭据"被攻破,每次注册表都以同样方式允许发布。每次事件都有临时应对,但结构性方案推进缓慢。provenance、sigstore、trusted publishing等长期方案已经出现,但要普及到所有包仍需时间。

为什么npm反复被攻击 - 5个结构性弱点

1) 单一维护者模型

相当多的npm包由1~2名维护者运营。一旦这个人的凭据被攻破,数百万下载量的包就会完全暴露。像本次这样一个账号拥有数百个包权限时,损害会一次性扩散。PyPI、crates.io等其他注册表结构类似,但npm把小包拆得很细的文化更容易放大影响。

2) 深度依赖树

即使项目直接依赖的包只有10个,展开间接依赖后实际安装的包会多得多。用npm ls --all自己数一数就能看出差别。这意味着从未听说过的包可以在构建环境中执行任意代码。

3) 安装脚本的任意代码执行

npm在安装过程中可以执行preinstall、install、postinstall脚本。虽有正当用途(如原生构建),但对攻击者而言却是载荷自动执行的通道。部分其他包管理器默认禁用这类钩子。发布时npm默认执行,但从2026年7月的npm v12起,依赖的安装脚本改为默认阻止(见后续进展)。

4) 维护者信任转让的无防护

维护者把包转交给他人的流程很轻。对新维护者的身份、履历和是否恶意的验证薄弱,用户也没有自动得知的途径。

5) provenance采用速度缓慢

npm provenance于2023年推出,但并非所有包都在使用。provenance只能证明包是在哪个CI工作流中构建的,并不保证代码安全;如果CI工作流本身被入侵,恶意构建也可能带有provenance。尽管如此,它可以帮助区分用被盗令牌从个人电脑发布的版本和从正规CI发布的版本,采用越广,本次这类事件的攻击面就越小。

今日内应执行的4项紧急应急措施

本节是本文最贴近实务的部分。以下是中国开发团队应在今天(最迟本周)内处理的4件事。

1) 立即检查可疑包 - npm audit

首先在所有活跃项目中执行以下命令。

npm audit --audit-level=high
npm audit signatures   # 验证注册表签名与provenance
npm outdated

npm audit signatures是一个意外鲜为人知的命令,它会验证已下载包的注册表签名和provenance证明。如果在事件时间点(5月19日)前后获取过包,请再用这个命令确认一次。

2) lock文件变更历史验证

检查package-lock.json或yarn.lock的近期变更,以及是否包含受影响的包。

git log --since="2026-05-18" -- package-lock.json
grep -nE "size-sensor|echarts-for-react|timeago\.js|@antv/" package-lock.json

如果lock文件在可疑时间点发生变更,或依赖树中存在受影响的包,请把该版本与GitHub Security Advisories及发现方公布的受影响列表进行对照。有时开发者不经意执行npm install后会把lock文件一并提交,因此需要按PR逐一检查。

3) 立即失效构建缓存

清除本地、CI和公司内部npm镜像中缓存的恶意版本。

npm cache clean --force
rm -rf node_modules
npm ci   # 基于lock文件的干净重装

GitHub Actions的actions/cache、GitLab CI cache、公司内部Nexus/Verdaccio镜像也要一并失效。如果缓存中仍残留恶意版本,应急措施就失去了意义。

4) 立即轮换可能泄露的令牌和密钥

本次载荷的主要目标是环境变量和配置文件中的令牌与密钥。如果以下项目曾出现在5月19日之后安装过受影响版本的环境中,请进行轮换。

  • npm publish令牌(若在CI中使用则最优先)
  • GitHub PAT和Actions令牌
  • AWS、GCP、Azure访问密钥
  • SSH密钥、Slack令牌、Webhook URL
  • 数据库连接字符串和内部API密钥

更换令牌的同时,也要检查SafeDep提示的痕迹:自己的GitHub账号下是否出现陌生的公开仓库,.claude/settings.json和.vscode/tasks.json中是否有陌生的自动运行项,是否注册了不认识的常驻服务。只换令牌而留下常驻程序,新令牌也会再次泄露。

7项长期防御策略 - 阻止下一次事件的系统

1) 使用trusted publishing和npm provenance

如果你在npm上发布包,请用trusted publishing(OIDC)取代长期令牌。根据npm文档,需要npm CLI 11.5.1及以上、Node 22.14.0及以上,在GitHub Actions中需授予permissions: id-token: write。通过GitHub Actions或GitLab CI/CD以trusted publishing发布时,provenance会默认自动生成。设置完成后,npm强烈建议在包的发布访问设置中选择"Require two-factor authentication and disallow tokens",以阻止基于令牌的发布。使用方可以用npm audit signatures验证签名和provenance。

2) 强制Frozen lockfile(--frozen-lockfile / npm ci)

即使本地使用npm install,CI中也必须强制使用npm ci或yarn install --frozen-lockfile。关键是设置关卡:与lock文件不一致时构建失败。仅这一项就几乎阻断了"夜里有人publish新版本、构建把它拉进来"的路径。

3) SBOM生成与管理

每次构建都自动生成并保存SBOM(Software Bill of Materials)。格式为CycloneDX或SPDX。借助@cyclonedx/cyclonedx-npm等工具可以轻松引入。有了SBOM,下次事件发生时就能迅速回答"我们是否在用那个包"。

4) 引入Dependabot / Renovate

让依赖更新不再依赖人的意志,而是变成自动PR。但不要开启自动合并。PR一旦创建,就强制进入人工审查流程。审查时用npm view查看最新版本的维护者、publish时间和下载趋势。

5) 定期依赖审计周期

每季度安排一次依赖审计会议。议题有三项:(a) 删除不再使用的包,(b) 替换deprecated包,(c) 评估维护者已停止活动的包的fork或替换。这一小时能大幅缩短事故发生时梳理影响范围所需的时间。

6) 极简依赖策略

在PR审查阶段把"为这个功能添加一个100行的包是否值得"作为必答问题。坐标计算、字符串工具、日期格式化等小功能,往往自己写10~30行代码就足够。依赖越少,攻击面越小。

7) 引入基于行为的扫描器(Socket.dev等)

传统的npm audit是与已知advisory比对,而Socket.dev等工具会基于行为检测包代码中的可疑行为(网络调用、eval、安装脚本模式等),更有可能捕获未知的新型入侵。发布时一并提到的Phylum,其技术已于2025年1月被Veracode收购,并入Veracode的产品线。以PR评论的形式集成到CI,是中国团队最顺畅的引入方式。

CI/CD流水线强化 - GitHub Actions示例

把上述7项策略整合为实际的GitHub Actions工作流,大致如下。这里只摘录了核心关卡。Node 20已于2026年4月结束支持,因此示例改为LTS版本24。id-token: write只授予发布(publish)作业,普通构建中去掉更安全。

name: secure-build
on: [push, pull_request]
permissions:
  contents: read
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '24'
          cache: 'npm'

      # 1) frozen lockfile - 与lock不一致则立即失败
      - run: npm ci

      # 2) audit关卡
      - run: npm audit --audit-level=high
      - run: npm audit signatures

      # 3) 生成SBOM
      - run: npx @cyclonedx/cyclonedx-npm --output-file sbom.json
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

      # 4) 基于行为的扫描(Socket.dev示例)
      # - uses: socket-security/socket-cli-action@v1

      - run: npm test
      - run: npm run build

这个工作流的核心在于"任何一步失败,构建就整体中断"。不把应急措施交给人的意志,而是以CI关卡的形式系统化,这是本文最后的核心信息。

监控工具对比 - Snyk、Socket.dev、Phylum、npm audit

整理实务中经常被比较的工具。

工具检测方式优势劣势
npm audit比对已知advisory免费、内置对零日和行为检测较弱
Snykadvisory + 许可证 + 部分行为UI和报告出色,企业功能丰富完整功能需付费方案
Socket.dev基于行为(eval/安装脚本/网络)可检测未知入侵,PR评论体验好有一定误报,中国落地案例较少
Phylum(现Veracode)基于行为 + 恶意包数据库恶意包分析与拦截2025年1月技术被Veracode收购,需按Veracode产品线而非独立产品确认
GitHub Dependabotadvisory + 自动PRGitHub集成、免费更偏向更新而非检测

对中国团队的推荐组合如下。(1) 基础是npm audit + Dependabot(免费、可立即引入)。(2) 在此之上,选Socket.dev或Snyk之一作为PR审查阶段的辅助关卡。(3) 如有余力,再加上Veracode(原Phylum技术)这类恶意包拦截层,构成三层配置。

中国企业和创业环境的应用

将上述策略迁移到中国环境时常被提到的摩擦点整理如下。

  • 创业公司: 通常没有专职安全人员。仅靠免费工具(npm audit、Dependabot、Socket.dev免费版)就能挡住相当一部分风险,先引入再说。不追求完美,以"开始做以前没做的事"为目标。
  • 中大型企业: 如果有公司内部npm镜像(Nexus、Verdaccio),在镜像层直接配置allowlist/blocklist。紧急事件时在镜像处封禁可同时影响全体开发者。
  • 金融/政务: 即使是网络隔离环境,通过npm镜像引入外部包的路径也相同。将SBOM和签名验证作为公司内部标准更有效。
  • 自由开发者/个人: 你的PC就是基础设施。立即放弃将令牌以明文存放在.env的习惯,引入1Password CLI或doppler等密钥管理工具。

开发者个人责任的边界与生态系统责任

即使执行完本文整理的11项(紧急4项 + 长期7项),也无法100%阻止供应链攻击。这就是现实。个人和团队层面的努力有明确的边界,超越这一边界需要生态系统层面的变化。

发布时本文列出的生态系统责任有三项:(1) npm(GitHub)加强维护者认证——强制WebAuthn和硬件密钥;(2) 针对热门包的激励,以提高provenance采用率;(3) 默认禁用安装脚本。其中第三项已在2026年7月的npm v12中成为默认,第一项的方向(限制2FA绕过令牌、转向trusted publishing)也在分阶段推进。具体日期整理在后续进展一节。

  • provenance采用加速: 事件之后热门包维护者自愿采用的情况可能增加。
  • 基于行为的扫描器标准化: 基于行为的扫描器以免费版为中心扩散。
  • SBOM义务化的趋势: 受美国EO 14028走向影响,中国政务/金融招投标中SBOM要求可能增加。
  • AI代码审查 + 依赖分析结合: 在PR审查时由AI用自然语言点评新依赖风险的趋势。
  • 对npm以外注册表的关注增加: 对deno、jsr、bun自有注册表的兴趣上升,但短期内难以取代npm。

结论 + 15项检查清单

用一句话概括本文的核心:供应链安全不是工具,而是系统,而系统是由今天就能开始的小关卡一点点累积起来的。下一次事件的窗口可能更短。挡住下一个22分钟的,是各团队把4项紧急措施和7项长期策略系统化。

最后是本文整理的15项检查清单。打印出来贴在桌边,一行一行地处理。

  1. 在所有活跃项目中执行npm audit --audit-level=high
  2. 执行npm audit signatures检查签名和provenance
  3. 确认5月19日前后lock文件的变更历史及是否包含受影响的包
  4. 使npm缓存、CI缓存、内部镜像缓存全部失效
  5. 轮换5月19日之后安装过受影响版本的环境中的令牌和密钥,并检查常驻痕迹
  6. 把发布自动化迁移到trusted publishing,删除长期publish令牌
  7. 在CI中强制npm ci / --frozen-lockfile
  8. 在CI中把npm audit设为关卡(发现高风险即失败)
  9. 引入SBOM生成工作流(推荐CycloneDX)
  10. 启用Dependabot或Renovate(不自动合并)
  11. 在日历上登记每季度一次的依赖审计会议
  12. 为发布的包启用npm provenance(使用trusted publishing则自动)
  13. 引入Socket.dev或Snyk其中之一的免费版
  14. 审查安装脚本允许列表(npm v12的allowScripts)
  15. 运营内部npm镜像时制定allowlist/blocklist策略

# 阅读npm供应链入侵新闻时要确认的事项 - 检查清单

基准日: 2026-09-29(以SafeDep分析、The Register报道、GitHub Changelog和npm Docs为准)

仅为一般信息。受影响版本和建议可能随发现方分析及GitHub Security Advisories的更新而变化,采取实际措施前请与最新列表核对。

## 1. 看这类事件时要确认的事项

| 确认事项 | 为什么要看 | 2026年5月事件中确认的例子 |
|---|---|---|
| 是否有准确的日期和时间(UTC) | 只有"5月中旬"无法与lock文件和构建日志对照 | 2026-05-19 UTC 01:39左右开始,两波(01:39~01:56、02:05~02:06) |
| 数字出自哪里 | 各报道数量不同时,要分清哪个是一手分析 | 恶意版本637个,包314个(The Register)~317个(SafeDep) |
| 是一个账号还是多个 | 入侵范围和应对(清理单个账号权限还是整个生态)不同 | 管理500多个包的一个维护者账号 |
| 通过哪个钩子执行 | preinstall、postinstall、github:依赖的阻止方法各不相同 | 通过preinstall钩子运行Bun脚本,还存在github:可选依赖路径 |
| 窃取了什么 | 决定需要轮换的密钥范围 | 云凭据、GitHub和npm令牌、SSH密钥、Kubernetes和Vault令牌、数据库连接字符串 |
| 是否留下常驻痕迹 | 只换令牌可能再次泄露 | `.claude/settings.json`和`.vscode/tasks.json`中的自动运行项、常驻服务 |
| 注册表如何处置 | "删除"和"deprecate"不同 | 部分deprecate,部分删除;GitHub表示正在停用恶意包 |
| 是否有官方说明政策变化源于本事件 | 时间重叠不等于因果 | 之后的GitHub公告没有直接提及本事件 |

## 3. 自己项目的紧急检查清单

- [ ] 执行`npm audit --audit-level=high`
- [ ] 执行`npm audit signatures`(验证注册表签名和provenance)
- [ ] 检查lock文件是否包含`size-sensor`、`echarts-for-react`、`timeago.js`、`@antv/`
- [ ] 确认2026-05-19前后lock文件的变更历史
- [ ] 使本地、CI、内部镜像缓存失效,然后用`npm ci`重新安装
- [ ] 轮换安装过受影响版本的环境中的令牌和密钥
- [ ] 检查GitHub账号下是否出现陌生的公开仓库
- [ ] 检查`.claude/settings.json`和`.vscode/tasks.json`中陌生的自动运行项
- [ ] 检查是否注册了不认识的常驻服务
