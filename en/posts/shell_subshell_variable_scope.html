Introduction: the loop ran correctly and the answer was still wrong

Picture a script that walks a log file and counts the lines matching some condition. Drop an echo inside the loop and three lines print out, one after another, exactly as expected. Then the loop ends, the script prints the total, and the total is zero.

At this point most people start suspecting the loop body. Is the arithmetic expansion wrong? Did read swallow a blank line? Is there a typo in the variable name? None of the above. The loop ran perfectly and the counter really did reach three. The process that held that counter simply ceased to exist along with the loop.

This article follows, through actual execution output, when that process is created, why it cannot hand a value back, and why the fix lives not in the loop body but in the way input is fed to it. Every command and every output printed below was produced by running it under GNU bash, version 5.2.37(1)-release and dash. If shell fundamentals are still shaky, Shell Script Basics and Shell Scripting Advanced make this easier to follow.

1. What happened the moment the counter came back as zero

Start with the reproduction. A three line file is enough.

$ printf 'a\nb\nc\n' > /tmp/f.txt

$ n=0
$ cat /tmp/f.txt | while read -r l; do n=$((n+1)); done
$ echo "after pipe: n=$n"
after pipe: n=0

Now change only how the input is delivered. The loop body is not touched by a single character.

$ n=0
$ while read -r l; do n=$((n+1)); done < /tmp/f.txt
$ echo "after redirect: n=$n"
after redirect: n=3

Same loop, same file, same shell. The only difference is whether a | is present. That alone settles the diagnosis: the cause is not in the loop.

1.1 A pipe moves more than data

If a pipe is understood purely as a device that feeds the output of command A into the input of command B, this behaviour has no explanation. A pipe does that, and along the way it creates an additional process. Bash executes each element of a pipeline in its own subshell.

A subshell is created by duplicating the parent shell, so at the moment it starts it holds every variable value the parent had. The problem is the return trip.

  • Parent values are copied down to the child, which is why reading $n inside the loop correctly shows zero at the start
  • Values the child changes never travel back up. No such channel exists between processes
  • When the pipeline finishes, the child process exits, and the n that had climbed to three evaporates with it
  • The parent shell still holds the n=0 it created, untouched by anything, so it prints zero
  • Put plainly, the value did not fail to increment. It is being read from a place where the increment was never visible

The right words to search for. This is not a variable scope problem, it is a process boundary problem. That is why every attempt to fix it with local or export fails. export is the mechanism for pushing a value from parent down to child; there is no mechanism for pushing one from child back up to parent.

2. Counting the processes with your own eyes

Rather than guessing, count them. Bash provides two variables for exactly this purpose.

  • $$ is the PID of the original shell, and it does not change inside a subshell. That makes it useless for detecting one
  • $BASHPID is the actual PID of the process currently executing this code, and it does change when a subshell is entered

Print them side by side and the subshell boundaries become visible directly.

$ echo "parent: \$\$=$$ BASHPID=$BASHPID"
parent: $$=1344 BASHPID=1344

$ ( echo "subshell( ): \$\$=$$ BASHPID=$BASHPID" )
subshell( ): $$=1344 BASHPID=1348

$ echo "cmdsub: $(echo "\$\$=$$ BASHPID=$BASHPID")"
cmdsub: $$=1344 BASHPID=1349

$$ stays pinned at 1344 all three times while BASHPID splits into 1344, 1348 and 1349. That is direct evidence that the parentheses and the command substitution each spawned a new process. When debugging a script and wondering whether a given line is inside a subshell, a single echo $BASHPID answers it.

The PID values themselves differ on every run. What matters is not the numbers but whether the three values differ from one another.

3. Redirection - the cheapest and most portable fix

When the input is a real file, there is exactly one answer. Remove the pipe and attach a redirection after done.

# the version where the value disappears
cat /tmp/f.txt | while read -r l; do n=$((n+1)); done

# the version where the value survives
while read -r l; do n=$((n+1)); done < /tmp/f.txt

The reasons this form is preferable line up as follows.

  • The loop runs in the current shell. No subshell is created at all, so variables persist
  • It creates one fewer process. The cat process disappears too
  • It is POSIX syntax rather than a bash extension, and dash also returns three for it
  • The cat file | shape is an unnecessary process in most cases anyway, so breaking that habit pays off independently of the subshell issue
  • Placing the redirection after done feels odd at first, but it reads naturally once the whole loop is seen as a single compound command whose standard input is being replaced

When there are several input files and the temptation is to write cat a b c |, that is the moment to reach for process substitution rather than redirection.

4. Process substitution - when the input is not a file

Real scripts more often take input that is not a file at all: the results of find, the results of grep, an API response filtered through jq. Process substitution is the tool for that case.

$ n=0
$ while read -r l; do n=$((n+1)); done < <(cat /tmp/f.txt)
$ echo "after procsub: n=$n"
after procsub: n=3

< <(...) looks like a typo but it is two distinct pieces of syntax adjacent to each other. <(cmd) makes the output of a command look like a file, and the < in front of it wires that pseudo file to standard input. The space between them is mandatory.

4.1 Why this works when a pipe does not

Process substitution also runs cmd in a separate process. The difference is which side the loop ends up on.

  • In a pipeline the loop is an element of the pipeline, so it is pushed into a subshell
  • In process substitution the loop stays in the current shell and the side pushed into a subshell is the one producing the data
  • The data producing side changes no variables, so it does not matter that it is a subshell

4.2 The problem that rides along when handling filenames

Here is what actually came out of a loop over find results, with one empty log file and one non empty file present, counting the empty ones.

$ find logs -name '*.log' | while read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done
$ echo "find | while  -> empty=$empty"
find | while  -> empty=0

$ while IFS= read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done < <(find logs -name '*.log')
$ echo "procsub       -> empty=$empty"
procsub       -> empty=1

Worth noting why IFS= and -r appear together. It is a separate defect from the subshell issue, but it blows up on the same line.

  • Without IFS=, leading and trailing whitespace is stripped, so a filename that begins with a space is silently altered
  • Without -r, backslashes are interpreted as escapes, which is particularly dangerous for path strings that came from Windows
  • In environments where filenames may contain newlines, pair find ... -print0 with read -r -d ''
  • That combination works inside process substitution unchanged; in the run above, the -print0 version produced the same result

5. When lastpipe works and when it is silently ignored

Bash has an option that makes the last element of a pipeline run in the current shell.

$ shopt lastpipe
lastpipe        off
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=0

$ shopt -s lastpipe
$ shopt lastpipe
lastpipe        on
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=3

Read that far and it looks like the simplest fix available. Then you type it at a terminal prompt and absolutely nothing happens. The reason is job control.

5.1 With job control on, the option is ignored

Toggling job control with set -m inside a script while running the identical code splits the result cleanly.

$ set -m          # job control ON (the interactive shell default)
$ shopt -s lastpipe
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control ON  -> n=$n"
job control ON  -> n=0

$ set +m          # job control OFF
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control OFF -> n=$n"
job control OFF -> n=3

Interactive shells turn job control on by default. That is why no amount of shopt -s lastpipe at a terminal changes the outcome. The option is definitively enabled and simply does not act, which is a nasty state to debug.

5.2 So where does lastpipe belong

  • Not recommended as the default fix in scripts you ship. A reader has to connect one shopt line at the top of the file with a loop a hundred lines further down
  • It is bash only. dash does not have the option at all
  • It is useful when an existing script must be rescued with minimal edits, since the pipeline structure stays intact and only one line is added
  • It is excellent for deciding within a minute whether a subshell is the culprit. If that one line changes the result, the cause is confirmed
  • When enabling it, always do so inside the script, and confirm the script is actually being executed by bash

6. Every other place a subshell appears

Pipes are not the only thing to watch. Each row below was verified by running it.

ConstructSubshellChanges visible outsideObserved result

while ... done < <(cmd)not for the loopyesn=3

The two rows that confuse people most are ( ) and { }. They look alike and behave in opposite ways.

6.1 Parentheses isolate, braces merely group

$ k=0; { k=1; };  echo "brace group: k=$k"
brace group: k=1
$ k=0; ( k=2 );   echo "paren subshell: k=$k"
paren subshell: k=0

There are places where this difference is an asset, because a subshell is also an isolation device.

$ cd /tmp
$ echo "before: $PWD"
before: /tmp
$ ( cd / ; echo "inside: $PWD" )
inside: /
$ echo "after : $PWD"
after : /tmp

When you need to step into a directory briefly, do something, and return, wrapping it in parentheses beats following cd with cd -. Even if the block bails out partway through, the parent working directory never moved.

6.2 exit is trapped inside the parentheses too

$ ( exit 42 )
$ echo "parent still alive, subshell exit=$?"
parent still alive, subshell exit=42

This cuts both ways. Putting cleanup code inside a subshell is safe because an exit in there will not kill the whole script. Conversely, an exit 1 written with the intent of ending the script keeps the script running quite happily if it sits inside parentheses. The second case causes far more incidents than the first.

7. Six ways to get the value out, and what each costs

All six approaches were run against the same three line dataset: alpha 10, beta 20, gamma 30, with a target total of 60.

ApproachSyntaxResultCost and constraints
Redirectiondone < file60Only when input is a real file. Works in POSIX sh
Process substitutiondone < <(cmd)60Bash extension. Syntax error in POSIX sh
Here stringdone <<< "$(cmd)"60Loads the entire output into memory. Bash extension
Read into an array firstmapfile -t a < file60Bash 4 or newer. Memory pressure on large inputs
Capture the outputt=$(cmd | { ...; echo "$t"; })60Neat for a single value. Multiple values need parsing
Via a temporary filewrite to "$tmp", then read60Most portable of all. Adds a cleanup obligation

7.1 The runs themselves

$ total=0
$ while read -r name v; do total=$((total+v)); done <<< "$(cat /tmp/data.txt)"
$ echo "here-string total=$total"
here-string total=60

$ mapfile -t lines < /tmp/data.txt
$ echo "mapfile count=${#lines[@]} first=${lines[0]}"
mapfile count=3 first=alpha 10

$ total=$(cat /tmp/data.txt | { t=0; while read -r n v; do t=$((t+v)); done; echo "$t"; })
$ echo "captured total=$total"
captured total=60

The last approach is the interesting one. Instead of eliminating the subshell it uses standard output, the one channel a subshell does have for sending values outward. Variables cannot leave a subshell, but output can.

7.2 How to choose

  • Input is a file, so use redirection. There is nothing to deliberate
  • Input is command output and bash is available, so use process substitution
  • The script ships with #!/bin/sh, so use a temporary file or capture output. Process substitution is off the table
  • The input runs to tens of thousands of lines, so avoid here strings and mapfile, since both pull everything into memory
  • Only one value needs to escape the loop, so capturing output is the shortest route
  • An existing script needs the smallest possible edit, so use lastpipe and leave the caveat from section five in a comment

One line summary. Variables cannot escape a subshell, but standard output, files, and the exit status can. Every technique for retrieving a value ends up using one of those three, or else avoids creating the subshell in the first place.

8. Where set -e drifts from expectation in pipes and subshells

Once subshells make sense, so does the reason set -e betrays people so regularly. Start with the run.

$ set -e
$ printf 'a\nb\n' | grep -q zzz | cat
$ echo "survived"
survived

grep failed and the script did not stop. That is because the exit status of a pipeline is, by default, the status of its last command. The trailing cat succeeded, so the pipeline as a whole was tallied as a success.

8.1 PIPESTATUS shows which position died

$ false | true | false
$ echo "\$?=$? PIPESTATUS=(${PIPESTATUS[@]})"
$?=1 PIPESTATUS=(1 0 1)

The order of the array is the order of the pipeline, so it reads directly that the first and third of three positions failed. The caveat is that this array is overwritten by the very next command. If you intend to use it, copy it into another array immediately.

8.2 What changes once pipefail is on

$ ( set -e -o pipefail; printf 'a\n' | grep -q zzz | cat; echo "NOT REACHED" )
$ echo "with pipefail exit=$?"
with pipefail exit=1

$ ( set -e; printf 'a\n' | grep -q zzz | cat; echo "reached" )
reached
$ echo "without pipefail exit=$?"
without pipefail exit=0

With pipefail enabled, a non zero status anywhere in the pipe marks the pipeline as failed, and only then does set -e act.

8.3 The quietest trap of all

This one is worth extracting on its own. Placing a subshell on the left side of || disables set -e inside it entirely.

$ ( set -e; false; echo "NOT REACHED" ) || echo "caught"
NOT REACHED

NOT REACHED printed. The || that was added in order to catch failures placed the entire subshell into a tested context, and inside such a context set -e is switched off. Functions behave the same way.

$ f() { set -e; false; echo "reached anyway"; }
$ f || true
reached anyway

Since the situation reads as error handling that disabled error handling, it is hard to spot by eye. The practical rules that fall out of it are these.

  • Put set -euo pipefail at the top of the script, but do not treat it as sufficient on its own
  • For pipelines that matter, check PIPESTATUS explicitly
  • The moment || something is appended, treat the set -e on its left as absent
  • To check whether a subshell succeeded, do not catch it with ||; run it and then examine $? on a separate line
  • It was confirmed that ( exit 7 ) hands back $?=7 intact, so exit status itself does propagate normally

10. The trap in writing scripts that verify this sort of thing

Every result above came from a script saved to a file and then executed. Even for a one line check, pushing the whole snippet in after -c is worth avoiding, for two reasons.

10.1 Quoting gets stripped twice

The inline form makes a string pass through the outer shell once and the inner interpreter once. That means recalculating, every single time, which stage consumes each $, backslash and quote mark. The escaped \$\$ sequences in the examples above are traces of exactly that. Saving to a file removes one of those stages.

10.2 Non ASCII characters corrupt silently

This is the worse of the two. A string passed on the command line travels through the encoding settings of the shell, then the terminal, then the interpreter. If any link in that chain has a different locale, non ASCII characters such as Korean, Japanese or Chinese turn into different bytes without raising an error.

  • Because nothing errors, the checker reports a pass. In reality the string being checked is already a different value
  • Reading a result of zero findings in that state means treating it as proof of cleanliness. That is the worst failure mode there is
  • Saving to a file passes the UTF-8 bytes straight to the interpreter, reducing the number of encoding handoffs to one
  • When building a new checker, plant a defect deliberately and confirm it gets caught first. If nothing is caught, the target is not clean; the checker is broken
  • Korean is composed at the syllable level, so a regex written against a bare verb stem misses every inflected form. Opening it up with a character class is safer

Working through logs with regular expressions more broadly is covered in the grep and AWK guide and the log analysis command guide.

11. What was not verified

Everything this article could not confirm by execution is gathered here in one place.

  • Zsh and ksh. Neither shell was available to run, so neither was verified. The claim that ksh family shells execute the last command of a pipeline in the current shell is widely repeated but was not reproduced here. Anyone on those shells should reproduce it with a three line script
  • A genuine interactive session with a controlling terminal. The conclusion in section five came from toggling job control with set -m. The same experiment was not run in a real login shell attached to a terminal, although the fact that the result hinges on job control state was confirmed
  • The POSIX standard text. The point that the standard leaves it to the implementation whether pipeline elements run in subshells is frequently cited as the reason shells diverge, but the standard clauses themselves were not cross checked
  • Busybox ash and minimal container images. That combination causes trouble in production more often than any other, and it was not verified here
  • Memory measurements on large inputs. Section seven states that here strings and mapfile pull everything into memory, but actual usage against line count was not measured
  • Older bash releases. The exact version boundaries at which lastpipe and mapfile were introduced were not checked. Targeting very old systems means confirming it on that machine directly

FAQ

Q1. Would export n inside the loop help?

No. export is the mechanism by which a parent hands its environment down to a child, and the direction here is the opposite. Exporting inside a subshell only affects grandchild processes that subshell goes on to create; it has no effect on the parent. For the same reason declare -g does not help either. Global scope means global within that process and does not cross process boundaries.

Q2. Why is the value right inside the loop but wrong only outside it?

That is precisely the fingerprint of this phenomenon. The echo inside the loop executes within the subshell and therefore sees that process most recent value. The echo after the loop executes in the parent shell and therefore sees an original value nothing ever touched. Same variable name, memory of two different processes. When that symptom appears, go looking for the pipe first.

Q3. Does switching from while to for solve it?

In a sense, since it removes the pipe, but it has costs. A for v in $(cmd) runs in the current shell so variables persist. However it loads the entire output into memory, and word splitting plus globbing apply, so filenames containing spaces get torn apart. for line in $(cat file) is not line oriented processing, it is word oriented processing. When lines are the unit of work, while read with a redirection is the right tool.

Q4. Do the stages of a pipeline run one after another?

No. The elements of a pipeline start simultaneously and regulate each other through the pipe buffer, so the later stage does not wait for the earlier one to finish. That is another reason subshells are necessary in the first place: separate processes are what make concurrent execution possible.

Q5. Can I read the variables from a backgrounded block after wait?

No. Running it confirms that m stays 0 after { m=99; } & followed by wait. wait only blocks until the child finishes; it does not retrieve values. When results from a background job are needed, send them to standard output captured in a file or a named pipe, then read that after wait.

Conclusion: three things to change today

First, look for the | before trying to fix the loop body. A value that is correct inside the loop and wrong outside it is almost always a pipe. Rewriting cat file | while into while ... done < file takes three seconds; not knowing this costs thirty minutes of staring at arithmetic expansion.

Second, read a subshell as a boundary rather than as the place where variables disappear. cd, set, trap and exit are all confined inside it. There are situations where that confinement is the problem and situations where it is a relief, and ( ) is a deliberate tool for the latter. Wrapping a temporary directory change in parentheses is the everyday example.

Third, stop treating set -e as a safety net. A failure in the middle of a pipe is not caught by default, and appending || switches off the set -e on its left. Enable pipefail alongside it and check PIPESTATUS explicitly wherever it matters.

One last note. Every table and every output in this article came from scripts between two and ten lines long. When shell behaviour is in doubt, running three lines always beats arguing about it. A printf 'a\nb\nc\n' and one counter settle most questions in under thirty seconds.
