런타임을 다시 쓴다는 결정 - Bun 1.4 Zig에서 Rust로

이미 쓰는 사람이 있는 소프트웨어를 다시 쓸 때 무엇이 걸리는가, 그리고 호환성이라는 말이 실제로 뜻하는 것

2026-08-21 개발/인프라

서론: 잘 돌아가던 런타임의 구현 언어가 바뀌었다

운영 중인 서비스의 런타임 버전을 올릴 때 우리가 확인하는 것은 대체로 두 가지다. 깨지는 API가 있는가, 그리고 지연 시간이 나빠지지 않는가. 2026년 8월 20일에 공개된 Bun 1.4는 여기에 익숙하지 않은 항목을 하나 더 얹었다. 런타임 자체의 구현 언어가 통째로 바뀌었다는 것이다. 겉으로 보이는 API 표면은 그대로인데, 그 아래가 Zig에서 Rust로 옮겨졌다.

버전 번호만 보면 마이너 업데이트다. 실제 규모는 그렇지 않다. 제작사 공개 글에 따르면 1,448개의 .zig 파일이 Rust로 옮겨졌고, 병합 시점 기준 백만 줄 규모의 변경이 한 번에 들어갔다. 그리고 그 작업은 2026년 5월 3일부터 14일까지 11일 만에 끝났다.

이 글은 릴리스 노트를 옮기는 글이 아니다. 관심은 다른 데 있다. 이미 남이 쓰고 있는 소프트웨어를 다른 언어로 다시 쓴다는 결정은 왜 무거운가. 그리고 그 결정의 성패를 판정하는 유일한 실무 기준인 호환성은 대체 무엇을 뜻하는가. 릴리스 발표에 붙는 배수와 퍼센트를 어떤 조건에서 읽어야 하는지까지 함께 정리한다. 언어를 바꾸는 재작성이라는 주제 자체는 TypeScript 7.0 RC — Go 네이티브 컴파일러, Grit — AI 에이전트로 Git을 Rust로 재작성한 시도에서도 다뤘는데, 그쪽은 도구와 실험이었고 이번은 운영 중인 런타임이라는 점이 다르다.

발표된 것 — 2026년 8월 기준 확인된 범위

먼저 사실 관계를 짧게 정리한다. 아래는 전부 제작사 공식 블로그에 적힌 내용이며, 확인 시점은 2026년 8월이다.

  • 구현 언어 이식 — Bun 1.4가 Rust 포팅본의 첫 정식 릴리스다. 포팅 작업은 2026년 5월 3일 시작해 5월 14일 병합됐다.
  • 재설계가 아님 — 제작사는 목표를 기계적 이식으로 못 박았다. 아키텍처, 자료구조, JavaScriptCore·OpenSSL·SQLite·uWebSockets 같은 C/C++ 라이브러리 연결은 그대로 유지했다.
  • Node.js 테스트 통과 수 — 통과하는 Node 테스트 파일이 v1.2.0의 1,450개에서 v1.4.0에서 3,743개가 됐고, 이번 릴리스에서 1,517건이 새로 통과했다고 밝혔다.
  • 표준 라이브러리 흡수 — 이미지 처리·헤드리스 브라우징·크론·마크다운·XML·아카이브 등 15개 npm 의존성에 해당하는 기능을 내장 API로 옮겼다.
  • 실험 단계 명시 — Bun.serve()의 HTTP/3는 실험 기능이며 제작사 스스로 프로덕션에 켜지 말라고 적었다. fetch()의 HTTP/2·HTTP/3도 기능 플래그 뒤에 있다.

여기까지가 발표문이다. 흥미로운 지점은 그다음이다. 이 정도 규모를 11일에 끝냈다는 서술과, 같은 글에 적힌 19건의 알려진 회귀라는 서술은 같은 사실의 앞뒷면이다. 하나만 읽으면 그림이 반쪽이 된다.

언어를 바꿔 다시 쓴다는 결정의 무게

새 프로젝트를 어떤 언어로 시작할지는 취향과 팀 사정의 문제다. 그러나 이미 프로덕션에서 돌아가는 소프트웨어를 다른 언어로 다시 쓰는 것은 성격이 다르다. 여기서 걸리는 것은 코드가 아니라 축적된 신뢰다.

돌아가는 소프트웨어에는 문서에 없는 자산이 붙어 있다. 몇 년치 버그 리포트를 통과하며 굳어진 엣지 케이스 처리, 사용자가 우회하려고 만든 관행, 명세에 없지만 사실상 계약이 된 동작. 이런 것들은 소스 코드에 명시적으로 적혀 있지 않다. 새 언어로 옮기는 순간, 적혀 있지 않던 것부터 사라진다.

그래서 이런 재작성에는 늘 같은 질문이 따라붙는다. 무엇을 걸고 무엇을 얻는가.

  • 거는 것 1 — 기능 정지: 재작성이 진행되는 동안 새 기능이 멈춘다. 사용자는 그 기간의 정체를 체감하지만, 얻는 것은 나중에야 나타난다.
  • 거는 것 2 — 버그 재유입: 옛 구현이 몇 년에 걸쳐 고친 버그가 새 구현에서 다시 열린다. 이번 사례에서 제작사가 인정한 19건의 회귀가 정확히 이 항목이다.
  • 거는 것 3 — 신뢰의 리셋: 사용자 입장에서는 검증 이력이 초기화된다. 「이 버전은 2년 동안 문제가 없었다」는 말을 다시 처음부터 쌓아야 한다.
  • 얻는 것 — 구조적 해결: 개별 버그를 하나씩 잡는 대신, 그 버그 부류가 애초에 컴파일되지 않는 상태로 만든다. 이게 언어 교체가 주는 유일하고 결정적인 보상이다.

본인의 판단은 이렇다. 재작성이 정당화되는 경우는 「빠르게 하려고」가 아니라 「이 버그 부류를 구조적으로 없애려고」일 때뿐이다. 성능만이 목적이라면 대개 핫패스만 바꾸는 편이 훨씬 싸다. 이 구분은 Go에서 Rust로의 마이그레이션 판단에서 다룬 시그널·안티 시그널과 정확히 같은 축이다.

왜 다시 쓰는가 — 네 가지 동기

실무에서 언어 교체가 검토되는 이유는 대개 넷 중 하나다. 이번 사례가 어디에 해당하는지도 함께 적는다.

  • 메모리 안전성 — 수동 메모리 관리 코드에서 반복되는 use-after-free, double-free, 오류 경로에서의 해제 누락을 컴파일 단계에서 막고 싶을 때. 제작사가 밝힌 이번 이식의 주된 이유가 정확히 이것이다. Zig에는 소멸자가 없어 정리를 호출 지점마다 defer로 적어야 했고, 자체 스마트 포인터를 만들어 봤지만 「Rust보다 나쁜 사용성에 보장은 없는」 결과였다고 적었다. Rust의 Drop이 그 자리를 대신한다.
  • 생태계 — 필요한 라이브러리가 그 언어에 이미 있는가. 암호화·파서·직렬화처럼 직접 만들면 위험한 영역일수록 무게가 커진다.
  • 채용과 인수인계 — 그 언어를 쓸 줄 아는 사람을 구할 수 있는가. 니치 언어일수록 버스 팩터가 작아진다.
  • 도구 — 디버거·프로파일러·정적 분석·의존성 감사가 성숙했는가. 사고가 났을 때 원인을 특정할 수단이 있는지의 문제다.

주의할 것은 이 넷이 서로 다른 무게를 갖는다는 점이다. 메모리 안전성은 재작성으로만 얻을 수 있지만, 생태계·채용·도구는 대개 부분 도입으로도 상당 부분 확보된다. 전면 재작성을 정당화하는 근거로 성립하는 것은 사실상 첫 번째 하나뿐이다.

왜 위험한가 — 재작성이 무너지는 자리

이번 이식이 밟은 절차는 꽤 촘촘하다. 제작사 설명에 따르면 이식 규칙 문서와 수명(lifetime) 대응표를 먼저 만들고, 3개 파일로 시범 운용한 뒤 전체로 확대했다. 구현하는 쪽과 검토하는 쪽의 문맥을 분리해 구현자 하나당 검토자 둘을 붙였고, 언어에 독립적인 테스트 스위트로 검증하면서 테스트를 하나도 건너뛰거나 지우지 않았다고 밝혔다. 병합 후에는 파서 전체를 대상으로 커버리지 기반 퍼징을 상시 돌렸다고 적었다.

그럼에도 이런 작업이 무너지는 자리는 정해져 있다.

  • 테스트가 검사하지 않는 동작 — 이번에 보고된 회귀 예시가 그 성격을 잘 보여준다. UTF-16 문자열을 홀수 바이트 위치에서 자를 때의 결과, 파서의 스택 사용량 변화. 둘 다 API 명세가 아니라 구현 부산물이고, 테스트로 잡기 어렵다.
  • 안전 경계가 남아 있는 구간 — 제작사는 Rust 코드의 약 4%, 대략 13,000개 지점이 unsafe 블록이며 그중 78%는 한 줄짜리 포인터 변환이라고 밝혔다. JavaScriptCore 같은 C/C++ 라이브러리를 계속 쓰는 한 이 구간은 사라지지 않는다.
  • 속도가 만드는 검토 부채 — 짧은 기간에 대량의 코드가 들어가면, 사람이 실제로 읽은 비율은 떨어질 수밖에 없다. 이 지점을 두고 공개적인 반론이 제기됐다. 한 외부 분석 글은 미해결 풀 리퀘스트가 5천 건을 넘었고 안정판 릴리스 간격이 이례적으로 벌어졌다는 점을 들어, 안전성 개선의 실체와 코드 품질을 함께 의심했다.
  • 성과의 귀속 문제 — 다른 외부 분석은 이번 변화가 사용자에게 순이익이라고 평가하면서도, 발표문이 Rust 때문에 얻은 개선과 재작성 없이도 가능했을 엔지니어링을 한데 묶어 과대 서술했다고 지적했다.

이 반론들을 옮기는 이유는 판정을 내리기 위해서가 아니다. 재작성의 성패는 발표 시점에 결정되지 않기 때문이다. 판정에 필요한 것은 배수가 아니라 시간이고, 2026년 8월 현재 그 시간이 아직 지나지 않았다.

「Node.js 호환」이 실제로 뜻하는 것

여기가 이 글에서 가장 실무적인 부분이다. 대안 런타임을 검토할 때 사람들이 가장 먼저 보는 것이 Node.js 호환성인데, 이 단어는 최소 네 개의 서로 다른 층위를 뭉뚱그려 부른다. 어느 층에서 깨지느냐에 따라 대응 비용이 열 배씩 차이 난다.

층위무엇을 뜻하는가깨지는 자리확인 방법
1. API 존재node:fs 같은 모듈과 함수가 있는가구현되지 않은 모듈 호출 시 즉시 예외공식 호환 문서의 모듈별 상태표
2. 동작 일치같은 입력에 같은 출력·같은 오류를 내는가옵션 일부 미지원, 오류 코드·메시지 차이, 인코딩 경계 동작Node 테스트 스위트 통과율, 그리고 내 코드의 테스트
3. 네이티브 애드온C/C++로 빌드된 .node 모듈이 로드되는가N-API 버전 차이, 프리빌드 바이너리 부재, 빌드 툴체인의존성 트리에서 네이티브 패키지를 먼저 골라내 개별 실행
4. 타이밍·비공개 API이벤트 루프 순서, 내부 심볼에 기댄 코드가 도는가APM·계측 라이브러리, 몽키패치, 테스트 러너 훅실제 통합 테스트. 정적 분석으로는 안 잡힌다

1층은 문서로 해결된다. 2층은 테스트 스위트가 상당 부분 잡아 준다. 문제는 3층과 4층이다. 실무에서 마이그레이션이 실패하는 자리는 거의 항상 여기이고, 호환률 숫자는 이 두 층을 거의 반영하지 못한다.

  • 공식 문서 기준으로 node:node-api는 구현돼 있다고 표기되지만, 어느 N-API 버전까지인지와 프리빌드 배포 패키지가 그대로 도는지는 별개의 문제다.
  • node:crypto는 BoringSSL 기반이라 일부 키 타입과 암호 알고리즘이 빠진다고 문서가 명시한다. 인증서·서명 처리를 하는 코드는 여기서 걸린다.
  • node:cluster는 프로세스 간 HTTP 요청 분배가 리눅스에서만 지원된다고 적혀 있다. 개발 머신이 macOS면 로컬에서만 멀쩡할 수 있다.
  • 워커 스레드는 일부 옵션이 무시되고 특정 API가 빠져 있다. 단일 실행 파일 패키징(node:sea)은 미구현으로 표기된다.

호환률 숫자를 읽는 법

발표된 호환률은 대개 Node.js가 배포하는 테스트 스위트의 통과 비율이다. 이 숫자에는 구조적인 한계가 있다.

  • 모수가 내 코드가 아니다. Node 테스트 스위트는 Node 자신을 검증하려고 만든 것이지, 내 의존성 트리를 대표하지 않는다.
  • 파일 단위와 케이스 단위가 섞인다. 「테스트 파일 3,743개 통과」와 「케이스 1,517건 신규 통과」는 서로 다른 세는 단위다. 인용할 때 이 구분을 흘리면 숫자가 과장된다.
  • 모듈별 편차가 총합에 묻힌다. 100%인 모듈과 97%인 모듈이 있을 때, 내 코드가 하필 그 3%를 쓰면 총합은 아무 의미가 없다.
  • 제작사 스스로 100%가 아니라고 적는다. 이번 릴리스 글에도 그 문장이 있다. 발표 주체가 남긴 단서를 인용에서 빼는 것은 정확한 인용이 아니다.

그래서 본인은 호환률을 진입 조건으로만 쓴다. 90%대 중반을 넘겼는지는 「검토를 시작해도 되는가」의 신호일 뿐이고, 도입 결정은 내 저장소에서 install과 테스트가 통과하는지로만 내린다. 이건 어느 런타임을 검토하든 같다.

성능 수치는 발표 주체·조건과 함께 읽는다

런타임 발표에는 늘 배수가 따라붙는다. 배수 자체가 거짓이라는 뜻이 아니라, 배수는 조건과 한 몸이라는 뜻이다. 아래는 이번 릴리스에서 제작사가 공개한 수치와, 그 글에 함께 적힌 조건이다. 전부 제작사가 자체 측정해 발표한 값이며, 제3자 검증치가 아니다.

맨 아래 행이 이 표의 핵심이다. 제작사 스스로 이식 자체의 성능 효과를 2~5%로 적었다. 그 위의 큰 배수들은 이식이 아니라 개별 기능 최적화에서 나온 것이고, 원리적으로는 이식 없이도 가능했던 작업이다. 앞에서 인용한 외부 분석이 「과대 서술」이라고 지적한 지점이 정확히 여기다.

  • 발표 주체를 먼저 확인한다. 자체 측정치인지, 제3자 벤치마크인지, 재현 가능한 스크립트가 공개돼 있는지.
  • 조건이 안 밝혀진 수치는 조건 미기재라고 적는다. 조건 없이 옮긴 배수는 인용이 아니라 유통이다.
  • 비교 대상 버전을 본다. 상대편 런타임의 최신 안정판과 비교했는지, 몇 버전 전과 비교했는지에 따라 그림이 달라진다.

런타임을 고를 때 실제로 갈리는 축

벤치마크는 검토의 시작점일 뿐이다. 실제 도입 여부는 아래 축에서 갈린다. 각 축을 내 프로젝트에서 재는 법까지 함께 적는다.

축무엇이 갈리는가내 프로젝트에서 재는 법함정
시작 시간콜드 스타트가 사용자 지연에 직접 들어가는지실제 진입점을 100회 띄워 중앙값과 p95를 함께 기록빈 스크립트로 재면 의미 없다. 의존성 로딩이 대부분을 차지한다
패키지 설치CI 시간과 락파일 호환성캐시를 비운 상태에서 전체 설치 1회, 캐시 있는 상태 1회락파일 형식이 다르면 팀 전체가 같은 도구로 통일돼야 한다
테스트 러너기존 테스트 자산을 그대로 옮길 수 있는지가장 복잡한 테스트 파일부터 실행. 모킹·스냅샷·타이머 조작을 우선 확인단순 테스트만 통과시키고 넘어가면 이관 막판에 막힌다
번들러 내장 여부빌드 도구 체인 개수와 설정 파일 수현재 빌드 산출물과 바이트 단위로 비교. 소스맵·트리셰이킹 결과 확인내장 번들러가 편한 대신 세밀한 설정이 막힐 수 있다
배포 환경 지원★실무에서 가장 자주 막히는 축사용 중인 PaaS·서버리스·컨테이너 베이스 이미지의 공식 지원 문서를 직접 확인로컬에서 되는 것과 배포 대상이 지원하는 것은 다른 문제다
네이티브 애드온C/C++ 의존 패키지가 로드되는지의존성 트리에서 네이티브 패키지만 추려 개별 실행프리빌드가 없으면 CI에 빌드 툴체인이 통째로 들어온다
장기 지원보안 패치가 몇 년 오는지공식 릴리스 정책 문서에서 지원 종료일을 확인서비스 수명이 지원 기간보다 길면 재이관이 예약된다

이 표에서 하나만 고르라면 배포 환경 지원이다. 나머지 축은 대안이 있지만 이 축은 없다. 배포 대상이 지원하지 않으면 다른 모든 장점이 무의미해진다.

바꾸지 않는 것도 합리적 선택이다

새 런타임 이야기가 나올 때마다 「그래서 언제 옮기나」로 논의가 흐르는데, 본인 판단은 반대쪽에 가깝다. 대부분의 서비스에서 런타임 교체는 우선순위가 낮다. 그 이유를 정직하게 적는다.

  • 성숙도는 시간으로만 산다. 코드 품질과 별개로, 「몇 년 동안 이 조합에서 문제가 없었다」는 이력은 돈으로도 재작성으로도 만들 수 없다. 첫 정식 릴리스는 정의상 이 이력이 없다.
  • 장기 지원 정책이 서비스 수명과 맞아야 한다. 보안 패치가 언제까지 오는지가 명확하지 않으면, 도입 시점에 이미 다음 이관이 예약된 셈이다.
  • 사내 표준에는 이유가 있다. CI 이미지, 보안 스캐너, APM 에이전트, 사고 대응 절차가 전부 특정 런타임을 전제로 짜여 있다. 런타임 하나를 바꾸면 그 뒤에 붙은 것들이 함께 흔들린다.
  • 대개 병목은 런타임이 아니다. 응답 지연의 대부분이 데이터베이스 왕복과 외부 API 대기라면, 시작 시간을 절반으로 줄여도 사용자 체감은 바뀌지 않는다.

그렇다고 새 런타임이 무가치하다는 말은 아니다. 콜드 스타트가 곧 비용인 워크로드, CI 시간이 팀 생산성을 직접 깎는 저장소, 도구 체인을 줄이는 것이 목적인 신규 프로젝트에서는 계산이 완전히 달라진다. 요점은 승패가 아니라 조건이다. 어느 런타임이 이겼는지를 묻는 질문 자체가 대개 잘못 세워진 질문이다.

옮긴다면 — 시험 순서와 되돌릴 지점

검토하기로 했다면 순서가 중요하다. 싸고 빨리 실패하는 것부터 시험하는 것이 원칙이다. 아래 순서는 어느 런타임 이관에도 그대로 적용된다.

  • 1단계 — 의존성 설치만. 프로덕션 코드를 건드리지 않고 새 런타임의 패키지 매니저로 설치만 해 본다. 여기서 막히면 나머지는 볼 필요가 없다. 네이티브 패키지 목록을 이 단계에서 뽑아 둔다.
  • 2단계 — 테스트 러너만 교체. 실행 런타임은 그대로 두고 테스트만 새 러너로 돌린다. 통과율이 아니라 실패한 테스트의 성격을 본다. 모킹·타이머·스냅샷에서 깨지면 4층 문제이므로 비용이 크다.
  • 3단계 — 비핵심 서비스 하나. 트래픽이 있지만 장애 영향이 제한적인 서비스 하나를 골라 실제로 띄운다. 배치 작업이나 내부 도구가 적당하다.
  • 4단계 — 관측 지표 대조. 메모리 상주량, p95·p99 지연, 재시작 빈도, 로그의 예외 종류를 이관 전후로 같은 창에서 비교한다. 평균만 보면 꼬리가 나빠진 것을 놓친다.
  • 되돌릴 지점 1 — 런타임을 코드가 아니라 설정으로 만든다. 컨테이너 이미지 태그나 배포 파이프라인 변수 하나로 옛 런타임에 돌아갈 수 있어야 한다. 소스 코드에 새 런타임 전용 API를 박는 순간 이 지점이 사라진다.
  • 되돌릴 지점 2 — 중단 기준을 미리 적는다. 「p99가 X% 나빠지면 중단」, 「네이티브 의존성 중 하나라도 프리빌드가 없으면 중단」처럼 숫자로 적어 둔다. 이관이 진행될수록 매몰 비용 때문에 기준이 흔들린다.

덧붙이면, 새 런타임의 내장 API(이미지 처리, 크론, 아카이브 같은)를 초기부터 쓰는 것은 권하지 않는다. 편하지만 그만큼 되돌릴 지점을 스스로 지우는 행위다. 이관이 안정된 다음에 하나씩 옮겨도 늦지 않다.

확인하지 못한 것

이 글을 쓰면서 근거를 확보하지 못한 항목을 한자리에 모아 둔다.

  • unsafe 지점 수의 비교 기준선. 약 13,000개라는 값이 같은 규모의 수작업 Rust 프로젝트와 비교해 많은지 적은지를 판단할 공개 기준선을 확인하지 못했다. 비교 없이 많다·적다를 말할 수는 없다.
  • 네이티브 애드온의 실제 통과 범위. 공식 문서는 N-API를 구현 완료로 표기하지만, 지원되는 N-API 버전과 널리 쓰이는 프리빌드 패키지의 실제 동작 여부는 문서에 없다.
  • 항목별 측정 환경의 일관성. 스트림 처리량에는 하드웨어가 명시돼 있지만, HTTP 서버 메모리와 윈도우 시작 시간 등 일부 항목은 하드웨어 기재가 확인되지 않았다.
  • 제3자 재현 결과. 이번 릴리스의 수치를 독립적으로 재현한 벤치마크를 확인하지 못했다. 인용한 외부 글들도 자체 측정이 아니라 발표문 분석이다.
  • 클라우드 벤더별 공식 지원 현황. 주요 서버리스·PaaS가 이 버전을 언제부터 공식 지원하는지는 벤더 문서를 각자 확인해야 한다. 이 글에서는 확인하지 않았다.

결론: 런타임 경쟁이 사용자에게 남기는 것

이번 일에서 남는 것은 어느 런타임이 빠른가가 아니다. 돌아가는 소프트웨어를 다시 쓸 때 무엇을 걸어야 하는지가 공개적으로 기록됐다는 점이다. 11일이라는 기간, 19건의 회귀, 4%의 안전 경계, 2~5%라는 순수 성능 효과, 그리고 그에 대한 공개 반론까지. 이 조합은 앞으로 비슷한 결정을 검토할 팀에게 상당히 구체적인 참조점이 된다.

사용자에게 돌아오는 실익도 분명하다. 런타임이 경쟁하면 시작 시간이 줄고, 도구 체인이 통합되고, 기본값이 개선된다. 이 효과는 옮기지 않는 쪽에도 온다. 경쟁 상대가 생기면 기존 런타임도 같은 축에서 움직이기 때문이다.

정리하면 이렇다. 발표된 배수는 조건과 함께 읽고, 호환률은 진입 조건으로만 쓰고, 도입 결정은 내 저장소에서의 설치와 테스트로 내린다. 그리고 바꾸지 않기로 하는 것 역시 근거 있는 결론이다. 지금 병목이 런타임이 아니라면, 그 판단은 다음 릴리스가 나와도 바뀌지 않는다.
