はじめに: メモリアロケータを気にする理由 - 見えない性能レバー

2026年5月24日、news.hada.io に microsoft/mimalloc の GitHub リポジトリがトピックとして上がりました(当時17点)。2019年に設計が公開されたプロジェクトが再び注目された背景には、アロケータ選択が性能を左右する領域、つまり長期実行サーバ・高同時実行ワークロード・言語ランタイムが広がり続けているという事情があります。2026年9月29日時点で mimalloc は v3.5.3(2026-09-16)を推奨版として公開しており、リポジトリには同日もコミットが反映されるほど保守が活発です。

多くの開発者は malloc・free の背後でどのアルゴリズムが動いているかを意識しません。Rust・Go・Java のようにランタイムが確保を隠す言語ならなおさらです。しかし 長期実行サーバ・高同時実行ワークロード・メモリ断片化に敏感なシステムでは、アロケータ選択が CPU 使用率、RSS(常駐メモリ)、テールレイテンシ、断片化を同時に変える決定になります。ただし効果の大きさはワークロードごとに大きく異なります。mimalloc の README 自体も「汎用アロケータに最適なアルゴリズムはなく、どのアロケータにも苦手なワークロードを作れる」と書いています。本記事が単一の数値より測定手順を重視する理由です。

本記事では (1) mimalloc とは何か、(2) glibc malloc・jemalloc・tcmalloc・mimalloc・rpmalloc の比較マトリクス、(3) 核心設計5つ、(4) 公式ベンチマークの読み方、(5) 置き換える価値がある5つのシナリオ、(6) 言語別の統合法、(7) Rust のグローバルアロケータ置き換えコード、(8) 公開された採用先、(9) リスクと限界、(10) 2026年のアロケータの流れ、(11) 今週できる3つのアクション、そして更新履歴と参考資料を扱います。公式資料(README・技術報告・リリースノート・crates.io)で確認した事実と、本記事の判断の枠組みを分けて記しました。

1. mimalloc とは何か - Microsoft Research 産、MIT ライセンス

mimalloc(「ミー・マロック」)は、Daan Leijen が Koka・Lean 言語のランタイム向けに最初に開発した汎用メモリアロケータです。設計は2019年6月の Microsoft Research 技術報告「Mimalloc: Free List Sharding in Action」(MSR-TR-2019-18、Daan Leijen・Benjamin Zorn・Leonardo de Moura)にまとめられています。公式リポジトリは github.com/microsoft/mimalloc、ライセンスは MIT です。標準の malloc・free・realloc・calloc をそのまま置き換えるよう作られており、README によれば約1万行の小さなコードで Windows・macOS・Linux・WASM・各種 BSD・Haiku・MUSL などに移植されています。共有ライブラリ・静的ライブラリ・単一オブジェクトファイルとしてビルドでき、cmake を使わず src/static.c 1ファイルをプロジェクトに入れてビルドする方法もあります。

他のアロケータと異なる特徴は3つです。第一に drop-in 互換です。Linux・BSD では LD_PRELOAD=/usr/lib/libmimalloc.so myprogram のように再コンパイルなしで差し込め、macOS は DYLD_INSERT_LIBRARIES、Windows は専用のリダイレクト DLL を使います。第二に free list shardingです。サイズクラスごとに大きな free list を1つ持つ代わりに mimalloc ページごとに小さなリストを持ち、さらにページごとに所有スレッドでの解放用と他スレッドからの解放用にリストを分けます。第三に secure モードです。-DMI_SECURE=ON でビルドするとガードページ・ランダム化された確保・free list ポインタのエンコードが加わり、README は性能負荷を開発元のベンチマーク平均で約10%としています。

バージョンは2026年9月29日時点で v3.5.3(2026-09-16)が推奨、v2.5.2(2026-09-12)は「stable, legacy」、v1.15.2(2026-09-12)は legacy です。新しい開発は主に v3 で行われ、v1・v2 はセキュリティ・バグ修正で保守されています。公開当時の本記事は「v2.x が安定版、v3.x が開発ライン」と書きましたが、現在は v3 が推奨版です。README によれば v3 はスレッド間のメモリ共有を改善し、一部の大規模ワークロードでメモリ使用量を大きく減らせる場合があり、どのスレッドからでも確保できる first-class heap をサポートします。GitHub のスター数は13,410(2026-09-29、GitHub API)で、2026年4~8月のリリースノートには LLM による監査で見つかったバグ・セキュリティ修正が複数回記録されています。

2. アロケータ比較マトリクス - glibc / jemalloc / tcmalloc / mimalloc / rpmalloc

主要なアロケータ5つを1つの表にまとめます。開発元・ライセンスは各リポジトリで確認した値で、「特徴」と「向いている環境」の列は本記事の判断です。

アロケータ開発元ライセンス特徴向いている環境(本記事の判断)
glibc malloc(ptmalloc2)GNULGPLLinux の既定・汎用一般的な Linux ワークロード
jemallocJason Evans・Facebook(Meta)BSD 系断片化を抑える設計長期実行 DB・キャッシュ
tcmallocGoogleApache 2.0(google/tcmalloc)スレッドキャッシュ型大規模サーバワークロード
mimallocMicrosoftMITsecure モード・drop-in・小さなコードセキュリティと性能の両立、ランタイム組み込み

本記事の選択基準は単純です。一般的な Linux サービスは glibc から始め、プロファイルでアロケータのコストが見えたときに候補を挙げます。DB・キャッシュのような長期実行プロセスは jemalloc と mimalloc を、スレッド間の確保・解放が多いサーバは tcmalloc と mimalloc を、セキュリティと性能を両立したいなら mimalloc-secure を、ゲームエンジン・リアルタイムシステムは rpmalloc と mimalloc を、同じ負荷で比較します。5つのうちどれも、あらゆるワークロードで最速ではありません。

3. mimalloc の核心設計5つ

README と技術報告に出てくる設計を5つにまとめました。

3-1) Free list sharding(ページごとの free list)

サイズクラスごとに大きな free list を1つ持つ代わりに、「mimalloc ページ」ごとに小さな free list を持ちます。1ページは1つのサイズクラスのブロックだけを収め、64ビット環境では通常 64KiB です。README は、こうすると時間的に近く確保されたオブジェクトがメモリ上でも近くに置かれ、局所性が高まり断片化が減ると説明しています。

3-2) 多重シャーディングと小オブジェクト経路

README が「大きなアイデア」と呼ぶ部分です。ページごとのリストをさらに分け、同じスレッドでの解放用リストと、他スレッドからの並行解放用リストを別々に持ちます。そのため他スレッドからの解放は CAS 1回で済み、リストが数千に分散して競合が1か所に集中しません。小オブジェクト専用の経路もあります。v3 の README は、サイズが MI_SMALL_SIZE_MAX(1KiB)未満と保証できる場合に mi_malloc_small・mi_free_small を使うとより速いと案内しています。

3-3) Secure モード(ヒープ脆弱性の緩和)

-DMI_SECURE=ON でビルドすると次が加わります。(a) 内部ページのメタデータをガードページで囲み、バッファオーバーフローがメタデータに届かないようにします。(b) free list ポインタをページごとの鍵でエンコードし、既知のポインタによる上書きを防ぎ、ヒープ破損を検出します。(c) double free を検出して無視します。(d) free list の初期化順序と確保位置をランダム化します。-DMI_SECURE=FULL は 64KiB ページの末尾ごとにガードページを置きますが、コストが大きく Linux の VMA 上限に達するおそれがあるため、README は一般には推奨していません。性能負荷は README のベンチマーク平均で約10%です。README は、これらは保証ではなく緩和策なので、全体のセキュリティ戦略の中で評価するよう付け加えています。

3-4) 低断片化と eager page purging

ページが空になると(sharding によってその可能性が高まります)、そのメモリを OS に未使用として伝え(reset または decommit)、実メモリの圧迫と断片化を減らします。長期実行プログラムで特に意味があります。README は、メタデータのオーバーヘッドが約0.2%に抑えられ、blowup がなく、最悪確保時間が OS 呼び出しを除けば有界だと説明しています。ただし README 自身が、公開ベンチマークは非常に大規模で長期実行のサーバワークロードを測定していないと明記しているため、長期実行時の断片化は自分で測るべき対象です。

3-5) Drop-in 互換(LD_PRELOAD)

README は動的 override を標準 malloc を置き換える推奨方法として紹介しています。既存バイナリを再コンパイルせず LD_PRELOAD=/usr/lib/libmimalloc.so myserver の1行で適用でき、MIMALLOC_VERBOSE=1 を併せて指定すると実際に mimalloc が使われているか確認できます。元に戻すには環境変数を外すだけです。jemalloc・tcmalloc も同じ方法が使えますが、コードが小さく単一ソースでビルドできる点が mimalloc の導入コストを下げています。

4. ベンチマーク分析 - 公式の表が語ることと語らないこと

この章の数値はすべて mimalloc README の「Performance」節から引いています。公開当時に書いた「glibc 比 1.5~3倍」「32~64スレッドで2倍以上」「jemalloc より10~30%速い」は元の表で見つからなかったため削除しました。

4-1) 測定条件と限界

README の性能節の最終更新は2021-01-30です。16コア AMD 5950x(Ubuntu 20.04、glibc 2.31、GCC 9.3.0)と36コア Intel Xeon(AWS c5.18xlarge)で、mimalloc v1.7.0・v2.0.0(当時ベータ)・secure モードを tcmalloc(gperftools 2.8.1)・jemalloc 5.2.1・tbb・rpmalloc 1.4.1・Hoard・Mesh・glibc と比較しました。2026-09-01 には「古い結果であり、他のアロケータもその後改善されている」という注記が加わっています。ベンチマーク一式は mimalloc-bench として別に公開されています。

4-2) ベンチマーク別の結果の要点

ベンチマーク性格README が記した結果
cfracシングルスレッド、小さく短寿命の確保が多い全アロケータが良好、mimalloc が tcmalloc・jemalloc よりわずかに速い
leanNLean 定理証明器が自身の標準ライブラリを並列コンパイルtcmalloc 比で13%速い
redisシングルスレッドサーバほとんどのアロケータが良好
larsonNスレッド間で確保・解放が行き交うサーバの模擬tcmalloc・jemalloc よりかなり速い
sh6bench確保集約型ベンチマークjemalloc より2.5倍超速い
xmalloc-testN一部のスレッドは確保のみ、一部は解放のみ大差で先行(rpmalloc・tbb・glibc もスケールは良好)

流れをまとめると、シングルスレッド・一般的なパターンでは差が小さく、スレッド間のオブジェクト移動が多いほど mimalloc の優位が大きくなります。ページごとの並行解放リストという設計と整合する結果です。

4-3) 巨大オブジェクト・長期実行ワークロード - 公開表が扱わない領域

README は、このベンチマークが非常に大規模で長期実行のサーバワークロードや確保の最悪レイテンシを測定していないと明記しています。数 MB のバッファ中心のワークロードや、数日生きるオブジェクトが多いワークロードでどのアロケータが優れるかは、公開表からは判断できません。こうしたワークロードは自分の環境で直接測る必要があります。

4-4) jemalloc と比較するとき

公開当時の「長寿命オブジェクトでは jemalloc が優位の可能性」は出典のない傾向の記述だったため、事実としては残していません。確認できるのは、README が jemalloc・tcmalloc を Chrome・FreeBSD のような世界最大級のシステムで使われる産業用アロケータと呼び、ほとんどのアロケータが xmalloc-testN で苦戦すると書いている点です。どちらも実績ある選択肢で、どちらが速いかは対象ワークロードで測る必要があります。

4-5) まとめ

一言でまとめると 「スレッド間の確保・解放が多いほど公開ベンチマーク上の mimalloc の優位は大きく、シングルスレッド・一般的なパターンでは差が小さく、長期実行・巨大オブジェクトは公開資料では判断できない」です。数値は2021年の測定なので、自分のワークロードのトレースで mimalloc-bench や独自ベンチマークを回すことが結論です。

5. mimalloc に切り替える価値がある5つのシナリオ

本記事で整理した「mimalloc への置き換えを試す価値がある5つのシナリオ」です。1つでも当てはまれば staging での負荷テストを行う価値があります。性能保証ではなく、試す対象を選ぶ基準です。

5-1) スレッド間のオブジェクト移動が多いマルチスレッドサーバ

リクエストを受けるスレッドと処理するスレッドが異なり、あるスレッドで確保したメモリを別スレッドで解放するサーバです。README の larsonN・xmalloc-testN が模擬するパターンで、mimalloc の結果が最も際立つ領域です。逆にシングルスレッドサーバは、README の redis の結果のように差が小さいことがあります。CPU プロファイルで malloc・free の競合が見えれば候補です。

5-2) 言語ランタイム・インタプリタ環境

mimalloc は Koka・Lean のランタイム向けに始まり、README はランタイムシステム向けのハートビート・遅延解放のフックを提供すると説明しています。CPython も 3.13 から mimalloc を標準で同梱しています(独自の変更を含む)。短寿命オブジェクトを大量に作るランタイムや組み込みインタプリタで検討する価値があります。

5-3) メモリが徐々に増える長期実行ワークロード

数日~数週間単位で再起動せずに動くサービスで RSS が上がり続けるなら、アロケータの断片化が原因候補です。mimalloc の eager page purging と MIMALLOC_PURGE_DELAY が関連する仕組みで、jemalloc も比較候補です。まず実際のメモリリークでないかを切り分けてください。

5-4) セキュリティが重要なシステム(mimalloc-secure)

ネットワークに公開されるサービスや、信頼できない入力をパースするサービスです。secure ビルドの負荷は README によれば平均約10%で、公開当時に書いた3~5%より大きくなります。性能に余裕のあるサービスから適用するのが安全です。2026年8月のリリース(v3.4.4・v3.5.0)は、secure モードの double free・サイズ検査の強化と double free 検出の高速化を記しています。

5-5) Rust・C++ プロジェクトのグローバルアロケータ置き換え

Rust は #[global_allocator] の1行で mimalloc をグローバルアロケータに指定でき、C++ はリンク段階で置き換えたうえで、README の推奨どおり mimalloc-new-delete.h で new・delete も上書きします。コンパイル時の統合は、デプロイ環境ごとの LD_PRELOAD 設定への依存が小さくなります。

6. 言語別統合方法 - C/C++・Rust・Go・Java

言語別の統合難易度を公式文書に基づいて整理します。

6-1) C/C++ - LD_PRELOAD またはリンク

Linux・BSD は LD_PRELOAD=/usr/lib/libmimalloc.so、macOS は DYLD_INSERT_LIBRARIES=/usr/lib/libmimalloc.dylib(シェルのセキュリティ制限がかかる場合あり)、Windows は mimalloc-redirect.dll を使うリダイレクト方式です。ビルド時の統合は -lmimalloc でリンクするか、cmake で find_package(mimalloc) の後に target_link_libraries(myapp PUBLIC mimalloc) を使います。README が推す使い方として mi_malloc API を直接呼ぶこともできます。C++ では mimalloc-new-delete.h をソースファイル1つだけにインクルードします。

6-2) Rust - GlobalAlloc 置き換え

crates.io の mimalloc クレート(2026年9月29日時点の最新は 0.1.52、2026-05-22 公開)を使います。リポジトリは github.com/purpleprotocol/mimalloc_rust で、microsoft/mimalloc を包むコミュニティ製ラッパーであり、Microsoft が直接配布するクレートではありません。既定で mimalloc v3 を使い、v2 が必要なら features = ["v2"] を指定します。名前の似た mimalloc-rust クレート(lemonhx/mimalloc-rust、0.2.1、最終更新 2023-04-27)は別プロジェクトです。詳しいコードは7章で扱います。

6-3) Go - cgo(限定的)

Go ランタイムのアロケータは、ソースのコメントにあるとおり tcmalloc を出発点としつつ大きく変化しており、差し替えられる構造ではありません。mimalloc が影響するのは cgo で呼ぶ C ライブラリ側の確保だけです。Go のコア領域まで置き換えるにはランタイムを直接パッチする必要があるため推奨しません。

6-4) Java - JNI / 利用困難

JVM は独自の GC ヒープを持ちます。mimalloc が影響し得るのは JVM プロセス内のネイティブ確保(JNI ライブラリなど)だけで、通常の Java オブジェクトには適用されません。Java サービスなら、アロケータの置き換えより先に GC とヒープ設定を見直すのが筋です。

7. 実戦統合例 - Rust でグローバルアロケータ置き換え

最もよく使われる Rust 統合をコードで示します。mimalloc クレート README の使用例と同じ形です。

7-1) Cargo.toml 依存追加

[dependencies]
mimalloc = "0.1"

# オプション: secure モード
# mimalloc = { version = "0.1", features = ["secure"] }
# オプション: mimalloc v2 を使う(既定は v3)
# mimalloc = { version = "0.1", features = ["v2"] }

7-2) main.rs でグローバルアロケータ宣言

use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;

fn main() {
    // この時点から Box, Vec, String などすべての標準確保が mimalloc を通る
    let v: Vec<i32> = (0..1_000_000).collect();
    println!("sum = {}", v.iter().sum::<i32>());
}

7-3) ビルドと確認

cargo build --release

# mimalloc のメッセージ出力で適用を確認
MIMALLOC_VERBOSE=1 ./target/release/myapp

# RSS 確認(Linux)
ps -o pid,rss,command -p $(pgrep myapp)

クレートの README にあるとおりビルドには C コンパイラ(gcc または clang)が必要なので、CI イメージに build-essential または同等のパッケージを事前に入れておく必要があります。ビルド時間と RSS の変化はワークロードによって異なるため、数値を仮定せず直接測ってください。

ヒント - 同じコードで mimalloc と既定のアロケータを比べるには、#[global_allocator] 宣言のあるビルドとないビルドを作り、同じ負荷で測定してください。置き換えも元に戻すのもこれほど簡単だという点が、試してみる最大の理由です。

8. 公開された採用先 - README と公式文書が挙げるもの

公式文書が明記している採用先だけを記します(2026-09-29 確認)。

  • Microsoft のサービス: README の「Usage」節は大規模低レイテンシサービスの例として Bing と Azure を挙げています。README は mimalloc を、数千台のマシンで大規模分散サービスを動かす産業用アロケータと説明しています。
  • ゲーム: 同じ節に、デス・ストランディング PC 版と Unreal Engine(4.25 のリリースノートへのリンク)が採用先として載っています。
  • 言語ランタイム・科学ツール: Koka・Lean のランタイムから始まり、CPython は 3.13 から mimalloc を標準で同梱しています(Python 公式文書「What's New In Python 3.13」)。README の採用先にはゲノムアセンブラ SPAdes もあります。
  • Rust エコシステム: crates.io の mimalloc クレートの累計ダウンロード数は57,647,630回です(2026-09-29、crates.io API)。

公開当時に書いた「2026年は採用曲線がさらに急になる」は当時の見通しでした。今回の確認で言えるのは、v1・v2・v3 の3系統が2026年8~9月にも同時にリリースされるほど保守が活発だという事実までです。

9. リスクと限界 - 正直な点検

mimalloc も完璧ではありません。主なリスクは次のとおりです。

9-1) メモリ使用量(RSS)増加の可能性

スレッドごとのキャッシュと遅延 purge のため、RSS が glibc malloc より高く見えることがあります。README の調整オプションは次のとおりです。MIMALLOC_PURGE_DELAY=N は未使用の OS ページを N ミリ秒後に purge します(v3 の既定は1000、0 なら即時 purge でメモリは減るが性能は落ち、-1 なら purge を無効化)。MIMALLOC_PURGE_DECOMMITS は既定の1で decommit(Linux では MADV_DONTNEED、RSS が即座に減る)を使い、0 なら reset(MADV_FREE)を使います。また v3.5.1 から Linux の既定ビルドが -DMI_ALLOW_THP=FULL となり、透過的巨大ページ(THP)を分割しないため RSS が増えることがあります。実行時は MIMALLOC_ALLOW_THP=0、ビルド時は -DMI_ALLOW_THP=OFF で無効にできます。MIMALLOC_SHOW_STATS=1 はチューニング用ではなく、終了時に統計を表示するオプションです。

9-2) デバッグツールとの相互作用

README は、メモリ追跡ツールと併用する際は基本的に標準アロケータを推奨しています。その代わり mimalloc を Valgrind 対応(-DMI_TRACK_VALGRIND=ON)、AddressSanitizer 対応(-DMI_TRACK_ASAN=ON)、Windows ETW 対応(-DMI_TRACK_ETW=ON)でビルドでき、Valgrind・ASan 対応は初期開発段階だとしています。デバッグビルド(-DCMAKE_BUILD_TYPE=Debug または -DMI_DEBUG=ON)は、サイズ別の統計、ブロック末尾のパディングによるバイト単位のオーバーフロー検出、double free・不正ポインタの解放・free list の破損・一部の use-after-free の検出を提供します。ガードモード(-DMI_GUARDED=ON、デバッグビルドでは既定で ON)は MIMALLOC_GUARDED_SAMPLE_RATE=N で N 回に1回の確保の後ろにガードページを置き、本番でもサンプリング方式でオーバーフローを捕まえられます。

9-3) glibc 特化動作に依存するコード

mallopt のような glibc 専用のチューニングや動作に頼るレガシーコードは、置き換え後に異なる動作をすることがあります。また、プロセス全体を override すると別経路で得たポインタが mi_free に渡る場合があり、README はそのような場合に全ポインタの妥当性を検査する -DMI_FREE_IS_CHECKED=ON(secure モードでは既定で ON)が必要になることがあると書いています。組み込み・ドライバ領域では事前検証が必要です。

9-4) fork() と大きな OS ページ

README は、大きな(2MiB)・巨大な(1GiB)OS ページを使ったまま fork すると、copy-on-write により書き込み時にページ全体がコピーされ、メモリが大きな単位で増えることがあると警告しています。MIMALLOC_ALLOW_LARGE_OS_PAGES や MIMALLOC_RESERVE_HUGE_OS_PAGES を有効にした状態で fork が多いワークロード(prefork サーバなど)は、別途検証が必要です。

9-5) まとめ

リスクはいずれも管理可能な水準ですが、本番適用前に staging で最低1週間の負荷テストを行い、RSS・レイテンシ・p99 を glibc と定量比較する手順は省かないほうがよいでしょう。この期間は本記事の推奨であり、公式基準ではありません。

10. 2026 メモリアロケータトレンド - mimalloc 以外の流れ

公開当時に書いた3つの流れを、2026年9月29日に確認した事実で整理し直します。

10-1) ハードウェアを意識した設定

mimalloc は NUMA ノードを実行時に検出し、MIMALLOC_USE_NUMA_NODES で調整でき、v3 には mi_heap_set_numa_affinity が追加されました。1GiB の巨大ページ予約(MIMALLOC_RESERVE_HUGE_OS_PAGES、特定の NUMA ノードには _AT)、THP の活用(v3.5.1 から Linux で既定)、アーキテクチャ最適化ビルド(-DMI_OPT_ARCH: x64 は haswell・avx2、arm64 は armv8.1、Apple は armv8.3)もあります。README は、NUMA ローカルな確保はベストエフォートで保証ではないとしています。公開当時の HBM・永続メモリに関する見通しは、今回根拠を確認していないため削除しました。

10-2) 別系統のアロケータと派生プロジェクト - まず活動状況を確認

公開当時の本記事は snmalloc を mimalloc の派生・後継作と書きましたが、snmalloc は Microsoft のリポジトリ(microsoft/snmalloc)にある別設計の「メッセージパッシングベースのアロケータ」です。「mi-game」のような派生は確認できなかったため削除しました。派生やフォークを本番で使う前にメンテナの活動状況とパッチ周期を確認するという原則はそのまま有効です。参考までに、GitHub API による最終反映日は mimalloc 2026-09-29、tcmalloc 2026-09-29、jemalloc 2026-09-27、snmalloc 2026-09-23、rpmalloc 2026-07-15 です。

10-3) Rust エコシステムのグローバルアロケータ選択

Rust は #[global_allocator] でプロセス全体のアロケータを1行で置き換えられ、mimalloc クレートの累計ダウンロードは5,700万回を超えました。公開当時の「既定アロケータを置き換えようという議論が周期的に出る」は当時の観察で、今回根拠は確認していません。本記事の推奨は、新規 Rust サービスで mimalloc を候補にしつつ、既定として固める前に自分のワークロードで測定することです。

11. 結論 + 今週できる3つのアクション

mimalloc を一文でまとめるとこうなります。「元に戻しやすい drop-in の malloc 置き換えで、公開ベンチマーク上はスレッド間の確保・解放が多いワークロードで特に強い。ただしその数値は2021年の測定なので、自分のワークロードで測り直す必要がある」。すぐに試せる3つです。

11-1) 即適用1: LD_PRELOAD で30分の PoC

運用中のバイナリに LD_PRELOAD=/usr/lib/libmimalloc.so と MIMALLOC_VERBOSE=1 を付けて適用を確認し、30分の負荷をかけて RSS・CPU・レイテンシを glibc と比較してください。効果が明確なら staging での負荷テストへ、わずかなら環境変数を外して元に戻せば済みます。

11-2) 即適用2: 新規 Rust プロジェクトでは mimalloc を候補に

Rust で新規サービスを作るなら、Cargo.toml に mimalloc = "0.1" を追加して #[global_allocator] を宣言し、既定のアロケータと比べてみてください。5分で済みます。既定は mimalloc v3 で、必要なら v2 feature に切り替えられます。効果の大きさは測定で確かめます。

11-3) 即適用3: セキュリティ重視サービスは mimalloc-secure を検討

ネットワークに公開されるサービスやユーザー入力をパースするサービスは、README によれば平均約10%の負荷でガードページ・free list のエンコード・double free 検出・ランダム化が得られる mimalloc-secure を検討してください。本番でオーバーフローをサンプリングで捕まえることが目的なら、ガードモードと MIMALLOC_GUARDED_SAMPLE_RATE も候補です。

最後に本記事が強調したいメッセージはこれです。メモリアロケータは「見えない性能レバー」です。コード1行、環境変数1行で性能指標を変えられる領域は多くなく、mimalloc はその中でも導入の敷居が低いツールです。ただし効果の大きさはワークロードが決めます。新しいシステムを設計するなら、一度は測ってみる価値のあるコンポーネントです。

## 2. 置き換えを試すかの判断(1つでも当てはまれば staging で試験)

- [ ] あるスレッドで確保し別スレッドで解放することが多い
- [ ] CPU プロファイルに `malloc`・`free` の競合が見える
- [ ] 短寿命オブジェクトを大量に作る言語ランタイム・インタプリタである
- [ ] 再起動なしで数日以上動き RSS が徐々に増える(まずリークでないことを確認)
- [ ] 信頼できない入力をパースし、約10%の性能余裕がある(secure の候補)
- [ ] Rust・C++ プロジェクトでグローバルアロケータを置き換えられる

どれにも当てはまらなければ、既定のアロケータで十分な場合があります。

## 3. 30分 PoC 手順(Linux)

- [ ] 基準: glibc で同じ負荷を30分かけ、RSS・CPU・レイテンシ・p99 を記録
- [ ] `MIMALLOC_VERBOSE=1 LD_PRELOAD=/usr/lib/libmimalloc.so <プログラム>` で適用を確認
- [ ] 同じ負荷を30分かけ、同じ指標を記録
- [ ] 効果が明確なら staging の負荷テスト(本記事の推奨: 最低1週間)へ
- [ ] 効果がわずかなら `LD_PRELOAD` を外して元に戻し、結果を残す

macOS は `DYLD_INSERT_LIBRARIES`、Windows は `mimalloc-redirect.dll` 方式です。

## 4. RSS が高く見えるときの調整表

| オプション | 意味 | 使い方 |
|---|---|---|
| `MIMALLOC_PURGE_DELAY=N` | 未使用の OS ページを N ms 後に purge | 0 = 即時(メモリ減・性能低下)、-1 = purge 無効 |
| `MIMALLOC_PURGE_DECOMMITS` | 1 = decommit(`MADV_DONTNEED`、RSS 即時減少)、0 = reset(`MADV_FREE`) | 既定は1 |
| `MIMALLOC_ALLOW_THP=0` | THP の使用を無効化 | RSS を減らしたいとき |
| `-DMI_ALLOW_THP=OFF` | ビルド時に THP を無効化 | 同じ目的をビルド段階で |
| `MIMALLOC_SHOW_STATS=1` | 終了時に統計を表示 | チューニングではなく観察用 |

## 5. ビルドモード選択表

| 目的 | ビルド | 備考 |
|---|---|---|
| ヒープ攻撃の緩和 | `-DMI_SECURE=ON` | ガードページ・ポインタのエンコード・double free 検出・ランダム化、平均約10% |
| 最大限の緩和 | `-DMI_SECURE=FULL` | ページごとにガードページ、README は一般には非推奨(VMA 上限) |
| 開発中のバグ検出 | `-DCMAKE_BUILD_TYPE=Debug` または `-DMI_DEBUG=ON` | バイト単位のオーバーフロー・double free・一部の use-after-free |
| 本番でのサンプリング検出 | `-DMI_GUARDED=ON` + `MIMALLOC_GUARDED_SAMPLE_RATE=N` | N 回に1回の確保にガードページ |
| Valgrind・ASan の利用 | `-DMI_TRACK_VALGRIND=ON` / `-DMI_TRACK_ASAN=ON` | 初期開発段階、README は通常は標準アロケータを推奨 |
