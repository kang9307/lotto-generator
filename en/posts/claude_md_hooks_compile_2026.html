Compiling CLAUDE.md Rules Into Hooks

Why injecting the whole rule file at session start breaks down, and what turning declarative rules into deterministic gates changes

2026-07-22 Dev & Infra

Introduction: A bigger CLAUDE.md makes rules weaker, not stronger

The standard way to steer an AI coding agent toward a project's conventions is to drop a rule file at the repository root. Claude Code calls it CLAUDE.md; the open standard shared across several agents is AGENTS.md; Cursor has its own rule files. The names differ, but the mechanism is the same - write "in this project, do it this way" in plain language, and the agent reads it in at the start of every session.

The trouble starts once that file grows. Conventions pile up, exception rules accumulate from past mistakes, and as teams grow, the list of "this one must never be violated" items keeps expanding. That looks like the natural direction to take, but the pattern reported repeatedly in the community lately is the opposite: the bigger the rule file gets, the less reliably any single rule is actually followed. This piece looks at why that paradox shows up, and at what an emerging "compile rules into hooks" approach fixes - and doesn't. The starting thread is a Claude Code community plugin covered on GeekNews (see references), but the point here isn't to promote a specific tool - it's the structural problem in context engineering that applies to AI coding agents broadly. Current as of July 2026.

1. How rules get injected into an agent - the system prompt and context files

1.1 Three layers of instruction

An AI coding agent currently learns user intent and team convention through roughly three layers. The first is the vendor's own system prompt, defining default behavior the user can't touch. The second is the project-root context file - CLAUDE.md, AGENTS.md, .cursor/rules/*.mdc, and the like - written by the team and committed to the repo. The third is whatever instruction the user gives in the moment, mid-conversation. This piece is about the second layer: the context file that lives in the repo and gets re-injected every session.

1.2 The default pattern: dump it all in at t=0

The default behavior is simple. At the moment a session starts (t=0), the whole file is read and placed in a system-prompt-equivalent slot. Whether the file holds 100 lines of rules or 1,000, and whether today's task touches one or two of them, the entire thing goes in at once. That's simple to implement and easy for a human to skim - but the problems start right after.

2. The structural limits of this approach

2.1 Wasted tokens and dilution

The context window isn't infinite, and every token inside it is both cost and attention budget. Reading in deployment-script conventions that this session will never touch, or exception rules for a legacy module nobody's using today, means splitting that budget away from the context that actually matters right now - the file currently open, the output of the last command. Unlike a human developer who reads onboarding docs once and looks them up again only when needed, the agent re-reads everything from scratch, every session.

2.2 The longer it gets, the more it's ignored

A more practical problem than token cost is how reliably rules are actually followed. As instructions grow longer, the model's attention isn't spread evenly across every item. And when a long session gets compacted, rules injected at session start are easy to compress or drop entirely during summarization. The thicker the rule book and the longer the session, the lower the odds that any individual rule is actually honored.

2.3 It's probabilistic, so it can't be enforced

The most fundamental limit is separate from all of this. A plain-language instruction is, to a language model, essentially a "suggestion." The model weighs it when predicting its next token, but that prediction is probabilistic. Writing "always run tests before committing" in CLAUDE.md creates no logical link between the model having read that sentence and the model acting on it. Stronger, more repeated phrasing can raise compliance, but it never reaches 100%. Using a probabilistic mechanism for a rule that must never be broken is close to a category error.

2.4 There's no way to verify it happened

Finally, there's no good way to confirm a rule was actually followed. Whether the model read the rule, and whether that rule actually shaped this particular response, is unknowable without a human manually diffing the conversation log. A sentence like "always do it this way" leaves no signal distinguishing compliance from non-compliance.

3. "Compile rules into hooks" - a community plugin case

3.1 What it tries to change

One recent approach to this problem showed up on GeekNews as a community plugin. The idea is straightforward: instead of leaving a CLAUDE.md rule as prose, extract it into a separate file paired with the "action" it actually governs, and inject it only at the moment that action is about to happen. The plugin runs this extraction as a slash command - it reads CLAUDE.md and the documents it references, infers each rule's trigger (which tool call, which command pattern should activate it), and writes the result to a plain-text file a human can review and edit.

3.2 Triggers and three delivery modes

Each compiled rule carries its trigger condition - which tool, which regex the command string must match - as frontmatter. Simplified, it looks something like this:

---
name: pr-template-check
trigger:
  tool: Bash
  pattern: "gh\s+pr\s+create"
strength: require-read
source: docs/pr-rules.md
---
Always use the specified template when opening a PR.

The actual enforcement happens through a hook that intervenes right before a tool call executes. A regex catches a command like gh pr create the moment it's about to run, and the relevant rule is shown to the model before the command executes. Delivery isn't a single mode either - there are three: always block and show the reason, block once per session and allow a retry after showing the rule, or don't block at all and just add context. Enforcement strength can be tuned per rule.

3.3 Surviving compaction

The "rules evaporate on compaction" problem gets a dedicated mechanism. A second hook fires when the session compacts, re-arming rules that were already delivered. A rule isn't a one-shot delivery - the session goes back into a monitored state even after the conversation passes through compaction.

3.4 What the measured numbers say

The numbers this plugin published are interesting in two directions. On the positive side: switching several reference documents from a wholesale session-start read to this delivery model cut session-start tokens by more than 40%, and most rules extracted from several real CLAUDE.md files converted into valid format. On the side worth stating plainly: recall on rule extraction, measured against a self-constructed adversarial gold set, came in below 40%. Translating a natural-language rule into a trigger pattern is, itself, an imperfect step. That number is worth treating as credible evidence rather than a knock against the approach - it shows both what this method can do and where it falls short, in the same breath.

4. From declarative rules to deterministic gates

4.1 Why the compiler analogy actually holds

"Compiling rules into hooks" isn't a loose metaphor - it's a fairly precise description. The source is a declarative rule a human wrote in plain language ("use this template when opening a PR"). The compiled artifact is an executable gate that performs a specific action (block, warn, inject) under a specific condition (the trigger). And that gate runs outside the model, in deterministic code. The way a compiler turns human intent into something a machine can execute, this approach turns a team's intent into something code can execute, rather than something a model probabilistically judges.

4.2 Why the same pattern keeps showing up

This shift isn't unique to one case. Structured outputs that strictly validate a tool call's schema follow the same idea - instead of prompting "please output valid JSON," the schema itself forces the output shape. Allow/deny/ask permission systems in agent harnesses are the same thing applied to tool execution - instead of prompting "this command is dangerous, don't run it," the tool-execution layer blocks it mechanically. Academic work shows a parallel move: research defining agent runtime safety rules through a domain-specific language that specifies triggers, conditions, and enforcement is a formalization of the exact same insight this community plugin applied at practical scale - that a plain-language instruction is not enforcement. Different surfaces arriving at the same conclusion is itself a signal that "declarative instruction to deterministic gate" isn't an isolated idea but a structurally necessary shift.

4.3 Other tools hit the same wall

This problem isn't confined to Claude Code. AGENTS.md, the open standard shared across agents, gets around it in some implementations by hard-capping file size and truncating anything past it. Cursor's rule files use glob patterns in frontmatter so a rule loads only when a matching file extension is opened - the same "load only what's needed" direction, just coarser-grained (file-level rather than tool-call-level) than the hook-based approach. It's more accurate to say the industry is converging on the same conclusion - that always loading the entire rule set doesn't scale - from different angles and at different resolutions.

5. Trade-offs of the hook-based approach

5.1 What you gain: accuracy and enforcement

What a hook-based approach delivers is clear. Because it runs deterministically, it intervenes every time its condition is met. The gap between "usually followed" (probabilistic) and "always followed" (deterministic) is never small in practice. That gap matters most for rules where failure is expensive - security-sensitive actions, irreversible operations like deletions, force pushes, production deploys.

5.2 What it costs: expressiveness and upkeep

The costs are just as real. First, an expressiveness limit. A hook only works on conditions code can mechanically check - a regex match on a command string, a file path pattern, a tool name. A rule that needs judgment, like "does this code match the project's idiomatic style," was never a candidate for compilation in the first place. Rules like that still have to stay in natural language, left to the model's judgment.

Second, the maintenance burden moves toward code rather than disappearing. Translating a natural-language rule into a trigger is itself a separate, error-prone step. As the recall figure above shows, an imperfect mapping between rule and trigger means the hook silently fails to fire in exactly the situations that matter most. And as the trigger list grows, it becomes its own small codebase requiring version control, review, and tests. A plain-text rule file was something any teammate could skim and fix; a rule store built out of hooks and regexes raises that bar.

Third, a false sense of security. Once a rule is "compiled," a team tends to assume it's permanently enforced. But a new command, a new tool, or a trigger invoked in a way nobody anticipated lets the rule get silently bypassed. A hook is only as complete as the trigger conditions a human wrote for it.

6. A general principle for agent instruction design - what goes in context, what goes in a hook

Put together, the practical takeaway isn't "move every rule into a hook" - it's splitting rules into three buckets.

6.1 What needs judgment stays in context - but isn't always loaded

A project's code-style preferences, the reasoning behind an architecture decision, why a specific library was chosen - these need the model's judgment. That guidance still has to stay in natural language, but it doesn't have to be loaded wholesale at session start. Loading it only when the relevant work actually comes up - keeping the name and description always visible, reading the body only when needed - cuts both the token waste and the dilution problem at once.

6.2 What's mechanically verifiable belongs in hooks, lint, or CI

Rules where the condition and the required action are both clearly definable - "never force-push," "run this test whenever this file changes," "PR titles must follow this format" - never needed to be a prompt in the first place. Moving them into a pre-tool-call hook, a commit hook, or a CI gate - a layer that runs deterministically outside the model - is a win on both accuracy and enforcement.

6.3 The third bucket - things not worth enforcing at all

This third category is often overlooked. Low-stakes style preferences and low-priority conventions - things that cost little if violated - don't need context budget or a purpose-built hook to enforce. Given that trying to enforce every single rule was itself part of why the context bloated in the first place, cutting this category out entirely is an optimization in its own right.

7. What to do about it today

If CLAUDE.md or AGENTS.md has already gotten long, it's worth auditing in this order: open the file and, next to each rule, note how often it's actually been violated and how costly a violation would be. Move the high-cost, clearly-defined rules into hooks or CI gates first. Keep judgment-dependent rules in context, but pull them out of the file that's read wholesale at session start into a structure that loads only on demand. Cut whatever's left over that's genuinely low-cost. That ordering itself shows what context engineering actually is - not a technique for writing better prompts, but a design exercise in continually redrawing the line between what gets left to the model's judgment and what gets handed to code.

Conclusion

The paradox that a bigger CLAUDE.md gets less reliably followed is really just the belated surfacing of a fact that was always true - natural-language instructions are probabilistic by nature. Compiling rules into hooks meaningfully reduces part of that problem: wasted tokens, loss to compaction, non-compliance on mechanically checkable rules. But not every rule can move this way, and moving what can doesn't make the maintenance burden vanish. Much like OpenWiki's take on agent-facing documentation or how spec-driven development reopens the question of what counts as the source of truth, this case shows that "what to tell an agent, in what form, and when" is a boundary that AI coding tool design will keep redrawing. Read alongside the observation that understanding is the new bottleneck, deciding where a rule lives and how it's delivered turns out to be, in the end, a question of what a human verifies and what gets delegated to code.
