说是智能体选的，那主语到底是谁 - 用16,893次执行测量三款编码智能体的第三方选择

同一答案的格子占42%、被提及139次却零次入选的名字，以及语言改写胜者的结构

2026-09-06 开发/基础设施

说一句把支付接上，代码就回来了。那段代码里已经接好了某家公司的SDK，环境变量的名字已经定好，计费方案也已经被默认。需求只有支付两个字，产出物里却嵌进了一个供应商。中间究竟决定了什么，通常没有人去看。

2026年9月初公开的一项调查，正是大规模地去看这段中间过程。它让三款编码智能体面对同一类需求反复作答，然后在每个会话里清点哪些名字被当作候选提出，最终又是哪一个进了代码。执行次数是16,893次。标题里常见的1万7千，是这个数字的四舍五入。

这里要谈的不是哪款工具更好。主题是智能体的选择由什么决定，以及当这种决定重复几万次之后市场会如何固化。工具数量增加时选择准确度在哪里崩掉，已经在智能体最多能挂多少工具里写过，所以本文只看实际被选中的分布。

下面的数字全部出自原文。但每个数字的分母都不一样。16,893数的是执行次数，5,292数的是通过有效性判定的会话，42%数的则是汇总网格里的格子。分母一混，同一个数字就成了另一种主张，所以每节都标出分母。

缘起 - 智能体选的这句话里空着的主语

公司群里常出现这样一句话：这个是智能体选的。听上去像在解释什么，其实主语是空的。是哪一款智能体，在哪个仓库之上，依据什么做出的选择，全都没有交代。如果三款都给出同样的答案，主语确实不重要。如果不是，那么主语本身就是答案。

这项调查试图把那个主语填上。它向三款工具反复投放同类需求，把对话与真实的代码变更一起读，把被提出的候选和最终的胜者分开记录。因此得到的结果不是产品排名，而是一份选择分布。

有了分布，问题的形状就变了。不再是该用哪个服务，而是：组织已有既定答案时，智能体给出那个答案的概率有多大。概率低，要动的就不是提示词而是仓库。

测了什么，怎么测 - 分母先于数字

设计并不复杂。用10种语言搭建75个仓库，准备1,163种提示词变体，交给三款编码智能体跑。每次执行都在独立沙箱中进行，沙箱厂商在三家之间轮换。原文写明，沙箱的选择不影响结论这一点是单独验证过的。

用户一方不是真人，而是一个编排器。按原文的表述，这个角色由Gemini 3.7 Flash扮演，它不会一句话交代完，而是跨多轮把对话推进下去。判定同样是自动化的：把对话记录与真实的代码差异一起读，先抽出被提及的候选，再指认最终的胜者。

成为有效会话的条件

判定环节内嵌了有效性检查。原文举出的两个条件是：选择没有被一个已经预先选定供应商的仓库带偏，以及确实有某个方案被选中。只罗列候选就结束的会话没有胜者，因此不进入统计。

通过这道过滤的是5,292个会话，约占16,893次执行的31%。其余11,601次被排除在首轮分析之外，而按何种理由各排除多少，公开文本中没有交代。这个数字之所以重要，是因为后续所有比例的分母都在这里定下。网页检索比例、自研实现比例、提及次数，都要按被过滤后的那一侧来读，而不是完整的16,893。

42% - 三者给出同一答案的格子占比

第一个值得停下来看的数字是它。三款智能体选出同一工具的格子占42%，不到一半。

要精确搬运的词是格子。它不是会话层面的一致率，而是在汇总网格上计数得到的值，而网格的行与列分别是什么，原文从未定义。紧随其后的例子是类目层面的：在语音智能体这一类目里，一款选了Twilio，另一款选了OpenAI Realtime API，第三款选了Vapi。同一个需求，三个答案。

它对实务的含义很直白。说智能体选的，携带的信息量不到一半。如果不同时写明用的是哪一款，这个选择就无法复现。

  • 42%说了什么 — 在超过一半的类目里，换工具就会换结果。定下公司统一的智能体，等于顺带定下了大约一半的供应商名单
  • 42%没有说什么 — 哪一方做出了更好的选择，这个数字里并不包含。一致率是离散度指标，不是质量指标
  • 留下的保留 — 由于格子没有定义，把它当作会话层面的一致率引用就是夸大。类目数越少，按格子计算的比例越容易波动

依据从哪里来 - 网页检索与既有知识的分配

三款工具给出不同答案的原因之一，在于各自从哪里取得依据。调查按工具统计了会话中发生网页检索的比例，跨度相当大。

Codex在94%的会话中使用了网页检索，原文的说法是它几乎总是上网。Cursor在约三分之二的会话中以网页为判断依据。Claude Code主要依赖既有知识，仅在约30%的情况下检索，但一旦检索，它打开的页面数是Codex的三倍。

这三者不是同一把尺子上的三个分数，而是三种失败方式各不相同的设计。网页依赖高，就对当下的文档以及那一页的措辞更敏感；依赖低，训练快照的分布就会原样透进结果里。调查没有裁定哪一种做出了更准确的选择。

领域一旦是新的，行为就会变

这些也不是固定不变的倾向。原文指出，在沙箱这类较新的领域，也就是既有知识较弱的地方，Claude Code的网页检索比例升到约80%。30%是整体均值，会随类目的成熟度大幅移动。

归拢起来，网页检索比例一半由工具决定，一半由领域的年龄决定。在成熟领域，三款工具的答案会向既有知识收敛；在新领域，当天的检索结果就构成了答案。领域越新，同一条提示词再跑一遍得到不同答案的余地就越大。

第四个选项 - 什么都不选，自己动手写

选项从来不是三个，而是四个。除了从候选里挑一个，还可以直接自己实现，一个依赖都不加。调查也统计了这条路径。

Claude Code在19%的会话中不接外部服务而自行实现，Codex与Cursor各自在10%上下。原文把这称作差不多两倍。

这个指标没有既定的好坏方向。不增加依赖是收益，而在本该放入成熟服务的位置上留下手写代码则是负债。在支付或认证这类牵涉合规与安全的地方，后者的分量要重得多。调查没有测量自研代码的质量。因此这19%是行为的记录，而不是对行为的评价。

提及与采用的落差 - 被提及139次却零次入选

这项调查最扎眼的部分既不是一致率也不是检索比例，而是被点名为候选与真正进入代码是两件事这一点，如今以计数的形式留了下来。

PayPal被提及139次，采用0次。原文补充说，这139个会话中有124个被Stripe拿走。也就是说PayPal被提到的场合大多在支付类目，而那个类目的胜者近乎已定。LangChain在194次提及中被采用4次，Netlify在152次中6次，Adyen在175次中3次。Supabase的提及多达242次，而数据库类目的胜者却偏向Neon。

到这里解释要放慢。原文并未查明这个落差的成因。被观察到的是频率差异，而差异背后的机制不在测量范围内。可以摆上台面的解释有几条，其中没有一条是这项调查验证过的。

  • 集成的步数 — 从文档走到能跑的最小示例，各家所需的步数差别很大。智能体必须在一个会话里做出能运行的代码，路径越短越占优

语言改写胜者 - 同样的需求，不同的结论

把同样的需求投进不同语言的仓库，回来的是不同的名字。邮件发送这项功能把这种差异显示得相当干净。

看这张表首先要注意分母各不相同。TypeScript是89次，其余三者各为23到24次。样本量相差近四倍，数值的稳定性自然不同。而且支配的强度也不同：TypeScript的62%描述的是竞争仍在的状态，Java的96%描述的则是结论已定的状态。语言改写胜者这句话没错，但改写的力度因语言而异。

从结构上讲，机制并不难说清。智能体先读仓库，再产出答案。仓库里带着语言、框架、已经存在的库，以及配置文件中的惯例。这些上下文在比较开始前就收窄了候选集合。Java仓库里Azure一系压倒性胜出，很难与企业级Java生态中文档和示例的分布无关。不过这一层因果是从表格形状推出来的，不是调查所证明的。

实务上的后果出现在组织层面。如果一家公司的前端是TypeScript、批处理是Python、网关是Go，那么在各个仓库里把同一需求交给智能体，可能会引入三家不同的供应商。三份合同，三套密钥轮换，故障时三个对接窗口。这并不是智能体做错了，每一次选择都忠实于各自的上下文，也正因如此才推进得格外安静。

集中度因领域而异

并非所有类目都以同样的方式分裂。有的领域答案实际上已经收敛为一个，有的则散成三份。

这张表里藏着一条实务规则：集中度高的领域不必指定，集中度低的领域必须指定。在支付这种十次里有九次都走向同一答案的地方，把供应商写进提示词几乎没有意义。反过来，在语音或邮件这种三分天下的地方，不写下来，每跑一次就会留下不同的结果。

不过Stripe的十次里有九次、Neon的66%、S3的45%，究竟是各自类目内部的比例还是相对全部会话的比例，原文并未写明。按类目内部来读在上下文中更自然，但引用时最好把这个前提一并写出。

文档里的一行字改变结果的地方

整项调查中最具体的因果碎片在这里。原文在解释Mailgun为何反复输给Postmark时指出，那是智能体读到其免费方案页面上1天保留这一表述之后反复出现的结果。

这一观察说的事情很明确：智能体不会试用产品，它只是阅读。它不跑基准测试，也不查故障历史，而是拿那一刻页面上写着的句子来做比较。于是相较产品的真实性质，句子的措辞与摆放位置可能对裁决介入得更深。

卖产品的一方会如何使用这个发现，不是本文关心的事。对引入方来说，剩下两层含义。其一，智能体所依据的那句话可能与我们的实际使用条件无关，免费方案的保留期在付费合同下往往是另一个数字。其二，既然依据是句子，那么要求把依据留下来本身就带来了可核查性。要求写一行为什么选它，人就能判断这一行是否立在错误的前提之上。

这项调查所处的位置 - 谁在测，谁在扮演用户

抛开数字的大小，这项调查并不是中立的观测，而这一点原文自己写明了。

调查方是向开发工具公司出售增长服务的商家，并且自述这项研究是影响编码智能体的选择、让产品被选中这一整体工作的一部分。利益关系不是被藏起来，而是附在正文里。厂商制作的数据并不足以构成丢弃它的理由。如何按顺序衡量调查方的利益立场，已经在如何阅读软件团队的AI使用模式调查里整理过，因此这里只谈仅属于这项调查的设计问题。

模拟用户是另一个大模型

最大的变量是用户角色。对话的另一端不是人，而是运行在Gemini 3.7 Flash上的编排器。真实开发者会提预算，会搬出内部标准，会坚持已经签约的供应商，不满意就回头再问。模拟用户被设计成施加多少这类压力，足以整体挪动胜者的分布。

另外还有一点：用户角色与裁判角色属于同一系列的模型。如果生成对话的一方与指认胜者的一方共享某种倾向，那么这种倾向把结果推向了哪个方向，在这套设计内部很难剥离出来。

  • 四类人设的构成 — 从氛围编码者到大企业工程师的这段光谱是设计者定的。它未必与真实用户构成一致，而按人设拆分的结果也没有公开可供对照
  • 1,163种提示词覆盖的范围 — 需求用什么句子写出来，会改变被纳入考虑的候选集合。这1,163种与真实请求的分布有多接近，原文没有交代
  • 有效性过滤留下的31% — 排除标准表面上合理，但如果某种特定模式恰好集中在被排除的一侧，那就成了选择偏倚。缺少按理由的拆分，就无从检验
  • 格子未被定义 — 由于42%背后的网格从未被描述，同一份底层数据换一个汇总单位就可能得出另一个数字
  • 版本与时点缺失 — 三款智能体的模型与命令行版本、执行的时间窗口都没有写。智能体以周为单位变化，因此这份结果应当被当作某一时点的快照

反过来，这项调查做得好的地方同样清楚。它在正文里披露了利益关系，轮换沙箱厂商并单独检查了执行环境没有制造结果，还公开了执行轨迹，使同样的做法可以被重跑。留出复现空间的厂商数据，比封闭起来的中立数据更好处理。

选择固化市场的路径

把上面的数值捆在一起，会看见一个循环。这个循环本身不是调查所证明的，而是被观察到的数值在结构上所指的方向。

智能体凭既有知识挑选时，训练数据里出现最多的名字获胜。那个选择变成代码，代码堆进公开仓库，又成为下一代的训练数据。靠网页检索挑选时方向也差不多：排在检索前列的，是已经拥有大量文档与示例的一方，而产出这些的能力来自已经达成的规模。

  • 依赖既有知识的路径会把训练时点的市场格局冻结下来。在那之后出现的替代方案，即便名字被提及，也缺少能把会话带到完成的可用示例
  • 依赖网页检索的路径则对文档的写法作出反应。它更新得更快，但优势仍然落在有余力把页面打磨精细的一方
  • 提及与采用的落差表明，这个循环里存在一个被谈论却进不去的位置。被提及139次而零次入选的状态若持续下去，知名度在涨，代码份额却不涨

再叠上按语言的分化，图景更清楚了。生态惯性穿过智能体之后，以更快也更安静的方式被再生产。人来拍板时至少开过一次会；智能体拍板时，会没有了，只剩一份变更差异。

那么应该固定住什么

结论不是换工具。结论是：当组织已经有了答案，除了把那个答案写成文字放在智能体会读到的地方，没有别的办法。只要三款工具在过半类目上分歧，没有指定的位置就会由工具的倾向与仓库的惯性替你填上。

最低限度要写下来的内容

要固定的有四样：已经签约并通过安全评审的许可清单，同一仓库里已经存在的既有技术栈，关于为何这样选的依据要求，以及新依赖出现时的审批路径。前两样收窄答案，后两样在收窄不了的地方为人留出介入点。

# 放进仓库规则文件的最小片段 (AGENTS.md 或 CLAUDE.md 等)

## 外部服务的选择规则

许可清单 - 只从这里选。合同与安全评审都已完成。
  支付      : Stripe
  邮件      : SendGrid
  对象存储  : Amazon S3
  数据库    : 公司内部托管 PostgreSQL

已经存在的东西 - 不要新增，直接用这些。
  lib/mailer  : 已经有 SendGrid 客户端
  lib/storage : 已经有 S3 客户端

如果被要求的领域不在许可清单里 - 不要自行决定，先停下。
  写出 2 到 3 个候选以及各自被淘汰的理由，然后请求审批。

禁止 - 向 package.json 或 go.mod 或 pom.xml 添加新 SDK 的变更，
       未经人工审批不得提交。

如果没有规则文件，或者动不了它，就把同样的内容放进提示词。要点是把选择的指令与留下依据的指令分开。依据留在纸面上之后，上一节看到的问题，也就是拿免费方案的一句话当依据的判断，人就能在上线前把它撤回。

需要外部服务时，按下面的顺序来。

1. 先读仓库。如果已经有做同样事情的客户端，就用它。
2. 如果没有，列出至少 2 个候选，并为每个候选写下
   - 依据是什么 (文档 URL 或仓库内的路径)
   - 假定了哪种计费方案与额度
   - 被淘汰的理由
   各一行。
3. 我们用的未必是免费方案。不要拿免费方案的额度当依据。
4. 最终选择只作为建议提出，依赖的添加在审批之后再提交。
要固定的东西写在哪里为什么需要
许可清单与禁止清单仓库规则文件，按语言分开的每个仓库各写一份防止在集中度低的领域里每跑一次答案就变一次
既有技术栈的位置同一个文件，把路径也写明把仓库上下文收窄候选的力量掉转到自己这一侧
一行依据的要求提示词，或者合并请求模板让人能够撤回那种只靠一句文档撑起来的判断
新增依赖的审批路径合并请求规则，把清单文件的变更转入单独评审防止自研实现与新增SDK悄悄进来
标注用了哪款智能体变更记录与合并请求正文在同一需求会给出不同答案的那一半领域里建立可复现性
  • 如果按语言分了好几个仓库，规则文件也要每个仓库各放一份。正如表里看到的，收窄候选的力量来自仓库上下文，只写在一处就够不着其余的仓库
  • 没必要把集中度高的领域也全写一遍。从真正会分裂的领域写起，投入产出比要高得多
  • 究竟能把多少事情交给智能体，是另一个问题。权限与阻断线的设计整理在该允许AI智能体做什么里
  • 新的SDK进来，合同与条款也会一起进来。引入前该读的条款写在当条款里的一句话足以停掉账号里

未能确认的部分

  • 42%所计数的格子的定义没能确认。网格的行与列究竟是类目，还是类目与语言的组合，原文并未写下。本文没有把这个值改写成会话一致率，原因正在于此
  • 未能通过有效性过滤的11,601次执行按理由的拆分没有公开。由于不知道偏倚排除与未做选择各占多少，也就无法判断被排除那一侧的性质
  • 三款智能体的模型与命令行版本，以及执行发生的时间在原文中缺失。若在另一个时点重跑同样的调查，数值会移动多少，没有可供估算的依据
  • Stripe的十次里有九次、Neon的66%、S3的45%以及邮件的35.6%，究竟是类目内部的比例还是相对全体的比例并未写明。本文按类目内部来读，并把这个前提一并写出
  • 按人设拆分的结果没有公开。氛围编码者与大企业工程师之间胜者分布是否不同，仅凭这项调查无法判断
  • 18个行业的完整清单以及各行业的会话数未能取得。正文中出现的只有支付、数据库、文件存储、邮件、部署与语音等一部分
  • 与Supabase的242次提及相对应的采用数没有给出。只有数据库类目由Neon领跑这一句描述，因此提及与采用表中的那一格留空
