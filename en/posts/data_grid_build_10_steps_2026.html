Why Hand-Rolled Data Grids Collapse at the Fourth Requirement

Three requirements add, the fourth one multiplies - the real reason table UI is harder than it looks

2026-07-29 Tech & IT

Introduction: where a table ticket becomes a three-week epic

Step-by-step accounts of building a data grid come around periodically in developer communities. It is an enjoyable genre. The first step always finishes in thirty minutes, and by the last step the author usually arrives at some version of 「so this is why people use libraries」. This article does not summarize any one of those posts. I was unable to pin down a specific originating article, so rather than copying somebody's outline, this piece takes on the problem itself: implementing a data grid by hand.

It is also not a tutorial. It does not say build it like this. It answers two questions instead. How do you decide whether to build it at all, and if you do build it, exactly where does it fall apart. Code appears only in the minimum needed to show a concept.

One ground rule first. Every technical statement here was verified directly on 29 July 2026 in MDN, the W3C WAI-ARIA Authoring Practices Guide (APG), and official project documentation, and anything I could not verify was left out. No library is recommended or ranked here, and library-related statements are limited to design and licensing facts printed in official documentation.

1. From addition to multiplication - between three requirements and four

Everyone says table UI is hard, but the why is rarely spelled out. The key is not the number of features. It is the number of interactions between features.

Sorting, filtering, pagination. Up to here they barely interfere with each other. All three reduce to 「a function that takes an array of data and returns a different array」, and rendering simply draws the result. Decide an order, drop them into a pipeline, done. That is why the first three days are fun.

From the fourth requirement the character changes. Virtual scrolling, frozen columns, column resizing, cell editing and keyboard accessibility touch rendering and interaction state, not data. And that state is a shared resource. Scroll position, the set of rows that actually exist in the DOM, where focus lives, and who computes layout. Five features grab those four resources at once.

The right-hand column says something simple. Counting features when you estimate gives the wrong number. Count pairs of features and you get closer. Five features make ten pairs, and each of those ten is an independent question: what happens when these two are switched on together.

The sections below open those questions one at a time.

2. What virtual scrolling quietly takes away

The principle of virtual scrolling is one sentence. Create DOM only for the rows in view and do not create the rest. Draw thirty rows instead of a hundred thousand and it is fast. Anyone can get this far.

The trouble comes after. Several browser built-ins operate on the assumption that things exist in the document, and virtual scrolling breaks precisely that assumption.

  • Find in page — the browser only finds what is in the document. A removed row is not a search target. The user does not conclude that the value is unfindable; they conclude it is not there.
  • Text selection and copying — dragging a selection across several screens no longer works, because rows behind you disappear as you scroll.
  • Accessibility tree — those rows do not exist for a screen reader either. This is where ARIA compensation becomes necessary.
  • Table semantics — a common trick for virtualizing is changing the display of table elements, and MDN warns about exactly this point.
  • Browser scroll anchoring — when content above changes size mid-scroll the position jumps. Section 5 covers this separately.

The fourth item deserves quoting. In its accessibility section the MDN display page states that in some browsers, changing the display value of a table element to block, grid or flex will alter its representation in the accessibility tree and the table will no longer be announced properly. The same page notes that display: none removes an element from the accessibility tree, and that display: contents is removed from the accessibility tree in some current implementations, which it describes as incorrect behavior according to the specification. In short, a single line you thought was purely visual touches meaning.

The ARIA compensation is well defined. The MDN aria-rowcount page explains that the attribute defines the total number of rows in a table, grid or treegrid, and that a value of -1 indicates the size is not known and tells the browser not to count the total number of rows. It says explicitly to include the attribute when rows are not all present in the DOM at any time. When every row is loaded and in the DOM you do not need it, because browsers count automatically. The W3C APG grid pattern says the same thing from its side: when rows or columns are hidden or not present in the DOM, for example when data is dynamically loaded while scrolling, use aria-rowcount and aria-colcount together with aria-rowindex and aria-colindex to distinguish total size from the currently visible items.

Conceptually it looks like the following. Real markup is far longer, but the point is to make the code state the fact that 「thirty rows are visible, one hundred twenty thousand exist」.

<!-- Of 120,000 total rows, only those from index 40,012 are in the DOM -->
<div role="grid" aria-rowcount="120000" aria-colcount="6">
  <div role="rowgroup">
    <div role="row" aria-rowindex="1">
      <span role="columnheader" aria-colindex="1">Order ID</span>
      <span role="columnheader" aria-colindex="2">Customer</span>
    </div>
  </div>
  <div role="rowgroup">
    <!-- The 40,000 rows before this are absent, so index must be stated -->
    <div role="row" aria-rowindex="40012">
      <span role="gridcell" aria-colindex="1">A-40012</span>
      <span role="gridcell" aria-colindex="2">J. Park</span>
    </div>
  </div>
</div>

A fork appears here. Do you really delete the rows, or keep them and skip only the rendering. The MDN content-visibility page describes a value for the latter. auto turns on layout, style and paint containment and skips the contents when the element is not relevant to the user, while the skipped contents must still be available as normal to user-agent features such as find-in-page and tab order navigation, and must be focusable and selectable as normal. By contrast hidden means the skipped contents must not be accessible to such features, nor be selectable or focusable. The same page shows contain-intrinsic-size supplying a size estimate to reduce layout shift.

HTML has a related idea. The MDN hidden attribute page says the until-found state indicates the element is hidden but its content will be accessible to the browser find-in-page feature or to fragment navigation, and that when those features cause a scroll to the element the browser fires a beforematch event, removes the hidden attribute, and scrolls to the element. It adds that browsers typically implement this using content-visibility: hidden, and that an element whose display is none, contents or inline will not be revealed this way.

The conclusion is not either-or, but a question of scale. At a few thousand rows, keeping the DOM and cutting only rendering is fast enough while preserving browser built-ins. At hundreds of thousands, node count itself is the cost and deletion is unavoidable, at which point reimplementing find, selection and accessibility yourself enters the estimate. Skip this decision, start with virtualization by default, and reversing it later is expensive.

3. Frozen columns - why one line of sticky is not the end

「Please freeze the first column」 takes three seconds in a meeting. Implementation does not take three seconds because position: sticky is not an isolated property; it depends on the structure around it.

Unpack MDN's definition of sticky on the position page and there are three layers of condition. First, the element is positioned according to normal flow and then offset relative to its nearest scrolling ancestor and containing block, based on the values of top, right, bottom and left; the definition explicitly says this includes table-related elements. Second, at least one inset property must be a non-auto value on the axis you want to make sticky, and if both insets on an axis are auto, sticky behaves like relative on that axis. Third, a sticky element sticks to its nearest ancestor that has a scrolling mechanism, created when overflow is hidden, scroll, auto or overlay, even if that ancestor is not the nearest actually scrolling ancestor. And this value always creates a new stacking context.

Here is how those three become incidents in practice.

  • One wrapper in the middle — a wrapper given overflow: hidden for design reasons, sitting between the table and the scroll container, becomes what the frozen column sticks to. That wrapper does not scroll, so the freeze appears to do nothing. No error, no warning.
  • Missing inset — you gave top for the sticky header but forgot left for the frozen column, so that axis quietly falls back to relative. This is the common cause of the header working while the column does not.
  • Stacking context — because sticky creates a new stacking context, dropdowns, tooltips and resize handles that must float above the frozen column end up layered against your intent. This is where raising z-index stops helping.
  • The corner cell — the cell where the header row meets the first column must be sticky on both axes and must sit above other cells in both directions. That one cell needs its own rule.
  • Border ownership — the MDN border-collapse page defines collapse as adjacent cells having shared borders and separate as adjacent cells having distinct borders. With a shared border it becomes ambiguous whether the frozen cell or the scrolling cell draws it, which is why teams tend to avoid collapsed mode and express the boundary with a shadow instead.
  • Shadows — showing a shadow on the frozen column only while horizontally scrolled requires knowing whether horizontal scrolling has occurred, and that state is not available to CSS alone, so scroll events reappear.

A minimal conceptual example looks like this. In real code the left value of each frozen column must be the sum of the actual widths of the columns before it, so the moment column resizing is switched on, those values must be computed dynamically. That is the subject of the next section.

/* Scroll container: make the sticky attachment target unambiguous */
.grid-scroll { overflow: auto; max-block-size: 70vh; }

/* Header row: the block-axis inset (top) is mandatory */
.grid-scroll thead th { position: sticky; top: 0; z-index: 2; }

/* Frozen columns: inline-axis inset (left) mandatory; value = cumulative width */
.grid-scroll .col-fixed-1 { position: sticky; left: 0;     z-index: 1; }
.grid-scroll .col-fixed-2 { position: sticky; left: 120px; z-index: 1; }

/* Corner cell: sticky on both axes and above both neighbours */
.grid-scroll thead .col-fixed-1 { z-index: 3; }

/* Avoid shared-border ownership; express the edge with a shadow */
.grid-scroll table { border-collapse: separate; border-spacing: 0; }
.grid-scroll .col-fixed-2 { box-shadow: 1px 0 0 0 #e0e0e0; }

4. Column resizing - choosing a layout algorithm first

Dragging a column edge to change its width looks like three mouse events. In reality it is a decision about which layout algorithm the table uses, taken before anything else.

The MDN table-layout page separates two algorithms. The default auto adjusts the widths of the table and its cells to fit the content. fixed requires the table width to be specified explicitly; if it is auto or unspecified the browser falls back to the automatic algorithm. Under the fixed algorithm each column width is determined by an explicit width on a column element if present, otherwise an explicit width on a cell in the first row, otherwise a share of the remaining horizontal space. The performance statement is explicit too: the fixed algorithm is faster because horizontal layout depends only on the table width, column widths and borders or cell spacing, not on the contents of the cells, and the entire table can be rendered once the first row has been downloaded and analyzed.

That sentence effectively decides the design of the resize feature. Under the automatic algorithm, changing one column width makes the browser recompute the others, so the user widens column A and column C shrinks. During a drag this recomputation happens every frame. Switching to the fixed algorithm removes the problem but requires that the app itself owns every column width. In other words one feature manufactures a new piece of state.

Once that state exists, other requirements follow it in a line.

  • Frozen column offsets — the left values from section 3 are no longer constants. Change one column width and every subsequent frozen offset must be recomputed.
  • Relationship with virtual scrolling — if you also virtualize horizontally, you need the widths of off-screen columns to compute total scrollable width.
  • Overflow handling — MDN notes that under the fixed algorithm subsequent cell content may not fit the given widths, and that cells use the overflow property to determine whether to clip. This is where ellipsis and tooltips become necessary.
  • Double-click to fit — the conventional gesture of double-clicking an edge to fit content requires the app to measure content width itself under the fixed algorithm. Add virtual scrolling and off-screen rows are not even measurable.
  • Drag performance — updating state on every frame re-renders every visible cell. Workarounds such as passing widths through CSS custom properties, avoiding re-render entirely, become necessary.
  • Persistence — user-adjusted widths only matter if they are saved, which then needs a rule for what happens to old settings when the column set changes.

This list is the concrete face of the multiplication claimed in section 1. A one-line requirement called column resizing actually brings six decisions with it.

5. Variable row heights - when the scrollbar starts lying

If every row is the same height, virtual scrolling is arithmetic. Total height is row count × row height, and dividing scroll position by row height gives the index of the first visible row. Scrollbar length and position are exact.

The arithmetic collapses the moment height depends on content, because you cannot know the height before drawing, and to know it you must draw. The practical approach is to hold an estimate and replace it with measurements as rows render, which produces a characteristic set of symptoms.

  • The scrollbar grows and shrinks — as you scroll down, measurements replace estimates and total height changes. The thumb resizes mid-scroll.
  • Scrolling upward jumps — when heights of rows above are updated, everything below shifts and the row the user was reading leaves the viewport.
  • You never quite reach the end — if the estimated total exceeds reality, scroll appears to remain even at the last row.
  • Jump to row N is inaccurate — reaching a specific row requires the summed heights of everything before it, and if that sum is an estimate you do not land on target.
  • Window resize invalidates everything — change the wrapping and every height already measured is stale.

Browsers do have a mechanism in this family. The MDN overflow-anchor page describes scroll anchoring as browser behavior that adjusts scroll position to minimize content shifts, holding your reading position when content above the viewport changes size or loads. auto makes an element a potential anchor and none excludes it. The same page, however, carries a limited availability note stating the feature is not Baseline because it does not work in some of the most widely used browsers. So it is useful as a supplement but not something to design around.

Which narrows the real choices to three. Fix row height and clip content, restrict heights to a few size classes, or allow full variability and handle each symptom above. Knowing in advance what the third option costs is the purpose of this section.

6. Cell editing - the two walls of focus management and IME

Editing values inside the table turns a data grid from a display device into an input device. And input devices carry requirements that display devices do not.

The first wall is focus. The W3C APG grid pattern defines the key behavior of editable grids. Enter disables grid navigation and enters edit mode or focuses the first widget. F2 toggles edit mode or widget focus. Alphanumeric keys enter edit mode. Escape restores grid navigation. When a cell holds several widgets, Tab and Shift+Tab move between them.

The specification itself is clear. The problem is where it meets virtual scrolling. If the cell being edited scrolls out of view, its row leaves the DOM and the focused element ceases to exist. The browser returns focus to the document body and the user loses their place. Restoring focus to the same cell on return requires holding 「which row, which column is active」 in application state rather than in the DOM. That is exactly the requirement that section 7 turns into a structural rule.

The second wall is IME, and it is much larger in Korean, Japanese and Chinese environments. MDN defines the compositionstart event as firing when a text composition system such as an input method editor starts a new composition session, and gives the example of a user beginning to enter a Chinese character with a Pinyin input method editor. The KeyboardEvent.isComposing page states that this read-only property returns a boolean indicating whether the event is fired within a composition session, that is after compositionstart and before compositionend.

Lay those two facts over the key specification above and the conflicts surface.

  • Enter has two meanings — during composition Enter confirms a candidate. If the grid treats Enter as save-and-move-down, one keypress performs both confirmation and movement. This bug does not reproduce in a Latin-script environment.
  • Escape has two meanings — during composition Escape cancels the composition. APG assigns Escape to restoring grid navigation, so a user cancelling a candidate loses the whole edit.
  • Alphanumeric to enter edit mode — this convention assumes a keystroke becomes a character directly. With an input method active the keystroke belongs to a composition session, so the first character vanishes or the editor never opens.
  • Arrow keys — during composition arrows move through the candidate list. If the grid intercepts them as cell movement, candidates cannot be chosen.
  • When to validate — an intermediate composition string is unfinished. Validating on every input shows errors continuously during perfectly normal typing.

There is one direction for the fix. While a composition session is active, the grid does not intercept keys. As concept code, roughly this.

// Cell editor key handling - the grid stays out during a composition session
input.addEventListener('keydown', (e) => {
  // MDN: isComposing is true after compositionstart and before compositionend
  if (e.isComposing) return;   // confirm / cancel / navigate belongs to the IME

  if (e.key === 'Enter')  { commitAndMoveDown(); }
  if (e.key === 'Escape') { cancelAndRestoreGridNavigation(); }
});

// Validate after composition ends - intermediate strings are not final
input.addEventListener('compositionend', () => validate(input.value));

Without those eight lines, every English-language test passes and only CJK users hit the bug. When evaluating a library, checking whether this is genuinely handled is far more useful than comparing the length of a feature list.

7. Why accessibility does not bolt on at the end

There are two kinds of accessibility work: the kind that bolts on later and the kind that does not. Labels, contrast and captions belong to the first. The MDN table page says a caption that clearly and concisely describes the table's purpose helps people decide whether to check the rest of the content or skip it, and that the scope attribute on th is redundant in simple contexts because scope is inferred, but that some assistive technologies may fail to draw correct inferences, so specifying it may improve the experience. For complex tables it recommends combining id and headers to programmatically associate each cell with its headers. Those can be added at any time.

What does not bolt on is keyboard grid navigation, because it is not added markup but a structural decision about focus ownership.

The W3C APG guidance on developing a keyboard interface states the principle briefly. The tab sequence should include only one focusable element of a composite UI component, and once a composite contains focus, keys other than Tab and Shift plus Tab enable the user to move focus among its focusable elements. It is the rule that stops a ten-thousand-cell table from requiring ten thousand Tab presses to escape. Two implementations are offered. Roving tabindex puts tabindex="0" on the currently focused element and tabindex="-1" on the others, swaps the two values on navigation and then calls focus(), with the benefit that browsers scroll the newly focused element into view. aria-activedescendant keeps only the container in the tab sequence and points at the id of the active child, and assistive technologies consider the referenced element to be the focused element even though DOM focus sits on the container.

What the two share is the point. A cell does not decide its own focus. The parent container is what knows the active coordinate. So if you have already built cells that manage focus independently and then try to adopt this principle, you must change the cell component interface and the state ownership structure together. That is a rewrite, not an addition.

It also helps to know the APG grid key list before you start. Arrow keys move one cell horizontally or vertically, Page Up and Page Down move multiple rows, Home and End go to the first and last cell in the current row, and Control+Home and Control+End go to the first cell of the first row and the last cell of the last row. Where selection is supported, Control+Space selects a column, Shift+Space selects a row, Control+A selects all cells and Shift plus arrow keys extend selection. On the role side the container takes grid, rows take row, cells take columnheader, rowheader or gridcell, sorted headers take aria-sort, selected elements take aria-selected, and a grid without editing takes aria-readonly.

// Skeleton of roving tabindex - the container owns the active coordinate
let active = { row: 0, col: 0 };   // application state, not the DOM

function moveTo(row, col) {
  active = clampToBounds(row, col);
  // With virtual scrolling the target row may not exist yet - render it first
  ensureRowRendered(active.row);
  const cell = findCell(active.row, active.col);
  setRovingTabindex(cell);   // previous cell to -1, new cell to 0
  cell.focus();              // the browser scrolls it into view
}

grid.addEventListener('keydown', (e) => {
  if (e.key === 'ArrowDown')  moveTo(active.row + 1, active.col);
  if (e.key === 'ArrowRight') moveTo(active.row, active.col + 1);
  if (e.key === 'Home')       moveTo(active.row, 0);
  if (e.ctrlKey && e.key === 'Home') moveTo(0, 0);
});

The single line ensureRowRendered is what ties sections 2 and 7 together. An accessibility requirement calls into the internals of the virtual scrolling implementation. The two features cannot be built separately, and that is why add it later fails.

9. When to build and when to adopt

The advice do not build it yourself is only half right. There are clear cases where building is better. Organized along three axes — team size, requirement count and lifespan — the criteria look like this.

Summarized, the question is not 「is this hard or easy」 but 「are we going to own this complexity indefinitely」. A hand-built grid bills you not on the day it ships but on the day, three years later, when the browser changes.

10. Design differences between libraries - facts only

Moving to library selection, but without ranking anything. Instead here are the design forks printed in official documentation. Knowing the forks changes how you read comparison tables.

The first fork is whether rendering is included. The TanStack Table documentation describes itself as a headless UI library for building tables and datagrids for TS/JS, React, Vue, Solid, Qwik and Svelte and states that headless UI does not provide markup, styles or pre-built implementations. What it provides instead is functions, state, utilities and event listeners, handling data processing, state management and business logic while leaving full control of markup and styles to the developer. The same page draws the line explicitly: consider headless when you want a lighter-weight table or full control over the design, and component-based when design and bundle size are not hard requirements and you want a ready-to-use implementation.

A misunderstanding often follows. Choosing headless does not make sections 2 through 7 of this article go away. The library owns the data pipeline and state, but markup, ARIA roles, focus management and IME handling remain yours to write. Headless removes the first three items from section 1 and leaves the last five untouched.

The second fork is license tier. The AG Grid official license and pricing page states that the Community version is under the MIT license and that Enterprise follows a separate end user license agreement including a year of updates. The feature split is presented on the page as a table. Basic column operations, text, number and date filters, row selection, basic cell editors and CSV export sit on the Community side; set and advanced filters, cell range selection with fill handle, batch editing and undo/redo, Excel export, clipboard integration, row grouping and pivoting, tree data, master detail, server-side operations and integrated charts sit on the Enterprise side. Support channels differ too, with Community support via GitHub and Enterprise support through a separate desk.

The practical meaning is singular. Settle the feature list first, then check the license tier. Reverse the order and you start on the free tier, then find yourself making a rushed purchasing decision six months later because of one requirement.

11. If you decided to build it - an order that does not collapse

If you chose to build, the order changes the outcome substantially. Most of the collisions above detonate when something you meant to add later turns out to demand structure. So put the structural things in first.

  • Close the requirements list first — write down even the items that might be added later. The purpose of this step is to see how far down the table in section 1 you go.
  • Make the active coordinate application state — which row and which column is active lives in state, not the DOM. Accessibility, editing and virtual scrolling all demand this value.
  • Apply the single tab stop from day one — starting with focus on every cell is hard to undo.
  • Fix the layout algorithm early — if column resizing is on the roadmap, adopt the fixed algorithm and width state from the start.
  • Decide virtualization by data scale — if it is not needed, do not add it. Virtualization brings with it the cost of giving browser built-ins back.
  • Attach ARIA roles and index attributes in the renderer — scanning and injecting them later goes out of sync once virtualization is involved.
  • Build the editor to respect composition sessions — include the eight lines from section 6 from the beginning. Retrofitted, they come back as bug reports nobody can reproduce.
  • Fix one scroll container — document the rule that no intermediate wrapper gets an overflow value.
  • Create a keyboard-only test procedure — review with a mouse alone and the defects of section 7 survive to release.
  • Test editing by hand with CJK input — composition sessions are difficult to reproduce in automated tests.
  • Set performance goals by interaction, not row count — 「render 100,000 rows」 is not the felt experience; 「hold frame rate during a drag」 is.
  • Write down an exit plan — deciding in advance which new requirement triggers a move to a library keeps that moment from becoming an argument.

The first four items are structure and the rest are process. Defer the structure and no amount of process makes up for it.

Conclusion: the hard part is not the table, it is the combination

Saying data grids are hard is imprecise. Drawing a table is easy. What is hard is the combination that arises when eight features grab four shared resources — scroll position, the DOM row set, focus and layout — on the same screen at the same time. That is why the cost of this problem scales with the number of feature pairs, not with the length of the feature list.

And one pattern recurred throughout. What can be added later and what cannot are cleanly separated. Labels and captions bolt on. Focus ownership, who owns the active coordinate, and the choice of layout algorithm do not. Those three are day-one decisions, and deferring them returns as a rewrite.

So the practical conclusion is neither do not build it nor build it. It is close the requirements list first, then check how far down the table in section 1 your project goes. Stop at the third row and building is lighter and more precise. Go below the fifth and the remaining question is not how to build it but 「for how many years are we willing to own this complexity」.

One last note on the stance of this article. The constraints described here are not anybody's skill problem; they are documented behavior of the web platform. Read them in advance and a three-week epic shrinks into a three-day decision.
