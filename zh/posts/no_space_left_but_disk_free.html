磁盘没满却报 No space left on device - inode 与仍被打开的文件

症状只有一个，原因却有四个。按顺序把这四个分开的方法

2026年9月1日 开发/基础设施

收到服务写不了日志的告警，登进服务器。照习惯敲下 df -h。空闲还剩三成以上。可是在同一个 shell 里只敲一次 touch，回来的却是 No space left on device。这一刻大部分时间被浪费掉的原因只有一个，就是以为 df 在撒谎。

df 不撒谎。它只是对没问到的事情不作答。你问容量它就答容量，你问根目录它就答根目录。如果写入失败的真正原因不是容量、或者不是根目录，那么 df 的回答仍然准确，却毫无用处。这篇文章把产生这种错位的四个位置分开，并整理出按哪个顺序排查最快收工。

症状只有一个，原因有四个

ENOSPC 是内核对应用程序说 这次写入我接不下 的一个信号。信号只有一个，并不意味着背后的情形也只有一种。用人来打比方就像发烧，发烧本身不是诊断，而是提示该开始诊断了。可是现场常见的做法是一看到 ENOSPC 就直接转入 找东西删，而当原因不是容量时，那些工作全都白费。

要分开的位置有四个。下表最右边一列，也就是 可区分的信号，才是这篇文章的实质内容。只背左边两列，顺序依然排不出来。

原因真正满了的东西确认命令可区分的信号
① inode 耗尽文件数量上限df -iUse% 很低，只有 IUse% 是 100%
② 已删除但仍打开的文件没有归还的块lsof +L1、/proc/<pid>/fddf 显示满了，du 的合计小得多
③ 预留块专留给 root 的那一份tune2fs -l只有普通账号失败，root 会成功
④ 另一个挂载点自己没看的那个文件系统df -h <路径>根目录有余量，只有该路径是 100%
  • ①和④ 各只需一行就能确认。所以把这两个放在最前面最省时间
  • ②必须 把 df 和 du 一起看 才会显形。只看其中一个，永远看不见
  • ③虽然少见，却会制造出 同一台服务器上不同人得到不同结果 的诡异局面，很耗时间

本文的运行环境与验证范围

本文的主题是 Linux 服务器，但真正产出这里这些输出的环境是 Windows 10 上的 Git Bash。先说明这一点不是为了显得谦虚，而是因为读者需要能分清 哪些输出可以照单全信，哪些输出压根不在这里。

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -a
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64 2025-01-30 11:14 UTC x86_64 Msys

$ df --version | head -1
df (GNU coreutils) 8.32

coreutils 与 Linux 一样是 GNU 8.32，因此 df、du、stat、sort 的 选项行为与计算方式完全相同。不同的只是底下的文件系统是 NTFS，而后面会看到，这个差别本身反倒有助于理解 inode。

  • 实际跑过的 - df -h、df -i、df --output、stat -f、stat -c、du 的各种组合、find -printf，以及 已删除但仍打开文件的完整复现
  • 没能跑的 - lsof +L1（这个环境里根本没有 lsof）、tune2fs、debugfs、resize2fs（ext4 专用）、以及容器叠加层相关的全部内容
  • 没有编造的 - 没跑成的命令的输出，本文里一行都没有。只写了命令和 怎么读
  • 动过手的 - 只把输出里的用户路径简写成了 /tmp/demo 和 <user>。数字一个都没改
  • 块大小在这个环境里报告为 4,096 字节。本文所有块计算都以这个值为准
  • 其他 shell（dash、zsh）或 BSD 系的 df、du，选项名与输出格式都不同。下面的命令以 GNU coreutils 为准

先要问的 - 真的是那个文件系统吗

按顺序这是第一件事。在原因清单里它是第④个，但 因为确认起来最便宜。不带参数敲 df -h 会列出挂载清单，而人的眼睛通常停在最上面那行根目录上。真正失败的路径如果挂在别的文件系统上，那一行就在屏幕下面的某处。

纠正的办法是 把路径直接交给 df。就连这个环境也会把同一块物理磁盘报告成两个不同的挂载点。

$ df -h . /
Filesystem                        Size  Used Avail Use% Mounted on
C:/Users/<user>/<temp>  931G  600G  332G  65% /tmp
C:/Program Files/Git                931G  600G  332G  65% /

# 要点 - 当前目录挂的不是 /，而是 /tmp。
# Linux 上也一样。把失败的路径直接交给 df。
$ df -h /var/log

在 Linux 服务器上，最常踩到这个坑的位置是固定的。下面这个清单是 根目录还有余量却写入失败 的典型布局。

  • /var 是独立分区的配置 - 日志和包缓存都堆在这里，所以比根目录早得多就满了
  • /boot - 通常只划几百 MB，堆上几个内核包就满了。症状表现为 内核更新失败，看起来不像磁盘问题
  • /tmp 是 tmpfs 的配置 - 用的是内存，与实际磁盘无关地被填满。重启就消失，原因随之蒸发
  • 容器内部 - 可写层和挂载进来的卷是 彼此不同的文件系统。卷还有余量，可写层满了照样失败
  • 绑定挂载或 NFS 交叠的路径 - 只看路径字符串像是同一棵树，设备却不同

原因 ① inode 耗尽 - 容量还有，数量却满了

文件系统不只保存数据，还会另外管理 针对每一个文件的元数据条目。装着属主、权限、时间以及实际数据块位置的结构就是 inode。文件名不在里面。名字由目录持有，而目录是 把名字和 inode 号配成对的清单。正因为这种结构，一个 inode 可以挂上多个名字，那就是硬链接。

要紧的是 这类条目的数量可能存在上限。上限一满，块再多也创建不了新文件。确认只要 df -i 一行。可是在这个环境里，这条命令是这样回答的。

$ df -i .
Filesystem                       Inodes IUsed IFree IUse% Mounted on
C:/Users/<user>/<temp>    -     -     -     - /tmp

$ stat -f .
  File: "."
    ID: ea1df1ef00000000 Namelen: 255     Type: UNKNOWN
Block size: 4096       Fundamental block size: 4096
Blocks: Total: 244041727  Free: 86972107   Available: 86972107
Inodes: Total: 18446744073709551615 Free: -1

全是 -。而 stat -f 把理由摆了出来。作为 inode 总数报告的 18,446,744,073,709,551,615 是无符号 64 位整数的最大值，也就是 表示没有上限的哨兵值，而 Free 是 -1。NTFS 没有 ext4 那样的固定 inode 表，因此压根就没有可报告的数字。

这些空白不是失败，而是 把最重要的事实原样呈现出来的画面。inode 上限不是文件系统的普遍属性，而是 因实现而异的设计选择。所以在 ext4 服务器上管用的应对，搬到 XFS 服务器上未必管用。在 Linux 上填着真实数字的画面，以及那时接着要敲的命令是这样的。

# ① 哪个挂载点的 inode 满了
df -i

# ② 该挂载点内文件扎堆的目录 (先粗看一遍)
du --inodes -x -d 2 /var 2>/dev/null | sort -n | tail -20

# ③ 直接按目录统计文件数量 (没有 du --inodes 的老环境)
find /var -xdev -type f -printf '%h\n' 2>/dev/null \
  | sort | uniq -c | sort -rn | head -20

# 上面这三行在本环境里没能执行。
# 因为 NTFS 不报告 inode 数量，①是空白。

小文件成百上千万堆起来的地方，大体是固定的。下面是 容量曲线毫无变化而 inode 却在悄悄涨满 的典型位置。

  • 会话文件 - 不设过期清理，就会按访客数量堆文件，每个只有几百字节
  • 邮件队列与 Maildir - 一封消息就是一个文件。投递受阻，队列就原样变成数量留下来
  • 缓存碎片 - 把哈希拆成目录的缓存，会因为 目录也占 inode 而翻倍膨胀
  • 日志碎片 - 轮转周期短、保留份数多，压缩件就会一直留着。每个都小，胜负却由数量决定
  • 依赖目录 - 每个构建环境各生成一份的包目录树，光文件数就能涨到几十万量级

inode 是什么时候定下来的 - ext4、XFS、btrfs

分岔就在这里。mke2fs 文档对 -i 选项，也就是每个 inode 分配多少字节，把话说死了，文件系统创建之后这个比率无法更改，因此要慎重决定取值。预留块比率默认值是 5% 这一点，也写在同一份文档里。

这一句话在实务上分量很重。ext4 上 inode 满了，就没有扩充这个选项。 只能减少文件数量，或者把数据搬走重建文件系统。这是一个在故障当中才知道就太晚的事实，所以最好在设计存储时就预先定好。

文件系统inode 分配方式之后还能增加吗在实务上意味着什么
ext4mkfs 时数量固定。用 -i 比率或 -N 数量指定不行。文档明确写着无法更改若知道小文件会很多，就在 创建时 把比率调低
XFS动态分配。只用 maxpct 管理上限可以。用 xfs_growfs -m 修改上限即使耗尽，也还有抬高上限来争取时间的余地
btrfs内核文档的功能清单里列着 动态 inode 分配固定上限这个概念本身就不一样不能把 df -i 的数字按 ext4 的含义来读
  • XFS 的 maxpct 默认值随文件系统大小而变。按文档是 1TB 以下 25%、50TB 以下 5%、再往上 1%
  • 文档写道，把 maxpct 设为 0，实际上整个文件系统都可能变成 inode 块。这 既是解开上限，也是让守护数据空间的那道机制消失
  • 所以 df -i 的 IUse% 是 不知道文件系统类型就读不懂的数字。同样是 90%，在 ext4 上是警报，在 XFS 上则是判断要不要抬高上限的材料

原因 ② 已删除却仍被打开的文件

rm 不是删除数据的命令，而是 从目录里摘掉一个名字的 unlink。即便名字全没了、链接数变成 0，只要 还有一个进程打开着那个文件，内核就不会归还这些块。要等最后一个引用被关闭的那一刻，空间才回来。

这个行为本身不是缺陷，而是 POSIX 定下的安全装置。它防止文件在读取途中消失而把进程搞崩。问题在于此时 观测工具会给出互相不同的答案。df 读的是文件系统的块账目，所以把被占住的空间算作 已使用。du 是走遍目录去数文件，所以 没有名字的文件它根本看不见。两者于是对不上。

在这个环境里原样复现了。创建 1GiB 文件，用 tail -f 占住后删除，并在每一步读取空闲块数。下面是实际输出。

$ cd /tmp/demo
$ free() { stat -f -c %f .; }          # 空闲块数 (1 块 = 4096 字节)

STEP 0  空目录               空闲块: 86970141
$ head -c 1073741824 /dev/zero > big.log
STEP 1  创建 1GiB            空闲块: 86707994   du -sh: 1.0G
$ ( tail -f big.log > /dev/null & )
STEP 2  tail 占住了它
$ rm big.log
STEP 3  rm 之后立刻          空闲块: 86708010   du -sh: 1.0K
STEP 3b 2 秒后               空闲块: 86708010
$ kill <tail 的 pid>
STEP 4  进程结束之后         空闲块: 86970153

把数字照原样读就是这样。创建文件时少了 262,147 个块。乘以 4,096 字节约为 1.0GiB，与创建的大小对得上。可是 rm 之后立刻回来的只有 16 个块。删了 1GiB 只回来 64KiB，实际上等于零。而同一时刻 du 已经答的是 1.0K。df 与 du 差了整整 1GiB 的状态 就是在这里造出来的。

接着一结束进程，262,143 个块 一次性回来了。删掉文件的是 rm，归还空间的却是 kill。解决办法不是把文件再删一遍，而是让占住它的一方松手，这句话的依据就是这两行。

找出元凶是另一回事。标准工具是 lsof +L1，文档说明这种写法 会挑出名字已被删除却仍打开着的文件。只是这个环境里没有装 lsof，所以没能跑。作为替代，/proc 那一侧照常工作，内核加上的 (deleted) 标记清清楚楚地出来了。

# 在本环境里执行过的 - 用 /proc 确认
$ ls -l /proc/<pid>/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/big.log (deleted)

# 在本环境里没能执行的 - lsof 未安装
$ sudo lsof +L1                  # 只列链接数小于 1 的打开文件
$ sudo lsof -nP +L1 /var         # 收窄到特定挂载点
注意 - 进程无法重启时，用 > /proc/<pid>/fd/<n> 截断文件描述符的做法流传很广。空间会立刻回来，但 号码挑错，那个进程打开着的另一个文件就会被整个清空。 无法撤销，也没有确认环节。只要还能重启，重启永远是更安全的那一边。
  • 制造这种局面最多的是 日志轮转的配置失误。移走或删掉文件之后，没有给进程发出重新打开的信号，进程就会继续往那个没有名字的旧文件里写。日志轮转悄悄失败的地方就在这里
  • 怎么定位占住文件的进程，本身不在本文范围内。本文只看到 空间为什么不回来 为止
  • 磁盘用量不呈阶梯状下降的曲线 是这个原因的好信号。清理跑过了曲线却是平的，说明删掉的东西还开着
  • 重启的对象大多是写日志的那一侧。把日志写成文件的应用，以及读取该日志并转发的采集器，两边都 可能占着同一个文件

原因 ③ 预留块 - 只有 root 看得见的余量

ext 系会把总块数的一部分 专留给特权进程。tune2fs 文档给出了两条理由，为了避免文件系统碎片化，以及 为了让非特权进程被拒绝写入之后系统守护进程仍能继续正常工作。默认值是 5%。

于是就有了这样的场面。用应用账号写入失败，换成管理员登进去在同一个位置建文件却成功。两个人看着同一台服务器却得出彼此不同的结论，就是从这里来的。如果 df 的 Use% 停在 95% 上下而不是 100%，写入却失败，那就值得怀疑这个原因。

# 确认预留块 (ext2/3/4) - 本环境里没能执行
$ sudo tune2fs -l /dev/sda1 | grep -iE 'block count|reserved'
# Block count:              总块数
# Reserved block count:     预留的块数
# 两个值的比例就是预留比率。

# 调整比率 - 可以改回来，但要慎重
$ sudo tune2fs -m 1 /dev/sda1    # 5% -> 1%
注意 - 常能看到用 tune2fs -m 0 把预留完全取消的建议，但文档说明的那两个目的会一并消失。余量接近 0 时 会因为找不到连续的块而让碎片化急剧加剧，写日志的守护进程也跟着停下，于是失去 记录故障原因的手段。在已挂载的状态下指错了值，在改回来之前会一直生效。
  • 预留比率是 百分比。所以磁盘越大，被留出去的绝对量就越大。几 TB 的卷上，5% 就是相当可观的量
  • 在 纯数据卷，也就是系统守护进程不往上写日志的卷上，有理由把比率调低。不过留 1~2% 左右，而不是 0
  • 反过来，/ 和 /var 上还是保持默认值为好。这里正是文档所说 守护进程必须继续工作的地方
  • XFS 没有同名的概念，用别的方式管理余量。不能把 ext 系的习惯照搬过去

小文件更占空间的原因

文件系统不按字节给空间，而是 按块 给。1 字节的文件也会整整领走一个块。剩下的部分别的文件用不了，这种浪费叫内部碎片。光听说法显得无足轻重，可一旦乘上数量，性质就变了。

我实际量了一下。du 的 --apparent-size 报告 逻辑大小，默认行为报告 实际分配量。把两个值并排放着，差别一目了然。

$ du -b --apparent-size one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1        one_byte.txt
100      b100.bin
4096     b4096.bin
4097     b4097.bin
1048576  b1m.bin

$ du --block-size=1 one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1024     one_byte.txt
1024     b100.bin
4096     b4096.bin
8192     b4097.bin
1048576  b1m.bin

最值得看的一行是 b4097.bin。逻辑大小 4,097 字节，实际分配却是 8,192 字节。就因为越过块边界一个字节，整整多贴上 4,096 字节。而 4,096 字节的文件恰好只用 4,096。

逻辑大小实际分配（实测）浪费倍数
1 B1,024 B1,023 B1,024 倍
100 B1,024 B924 B约 10 倍
4,096 B4,096 B01 倍
4,097 B8,192 B4,095 B约 2 倍
1,048,576 B1,048,576 B01 倍

这里有一点要老实说明。1 字节文件的分配量出来是 1,024 而不是 4,096，是因为 NTFS 会把极小的文件一并存进元数据记录里。ext4 默认不用这项优化，所以 同样的实验预计会得出 4,096，但那个画面不在本文里。 相比之下，b4097.bin 在块边界上翻倍的行为，是所有按块分配的文件系统所共有的。

乘上数量会怎样，我也量了。两万个 1 字节文件。

$ time ( for i in $(seq 1 20000); do printf 'x' > "f$i"; done )
real    0m25.766s

$ ls -1 | wc -l
20000

$ du -sb --apparent-size .
20000     .          # 逻辑合计 = 20,000 字节 (约 20KB)

$ du -s --block-size=1 .
24674304  .          # 实际占用 = 24,674,304 字节 (约 23.5MiB)

逻辑上的 20KB 实际占了 23.5MiB。约 1,233 倍。这个值里既有文件本身的分配量，也有为了装下两万个名字而变大的目录结构。目录也占空间 这个事实，在这里看得见了。

  • 在 ext4 上按 4KiB 块做同样的事，算术是这样的。100 万个 1 字节文件逻辑上是 1MB，实际是 4,096,000,000 字节，也就是约 3.8GiB。这个值是 按块大小算出来的，不是实测，而且不含目录结构
  • 所以在文件多的地方，容量和 inode 会同时 消耗。哪一边先见底，取决于文件大小的分布
  • 把小文件打包成一个才是根本对策。日志轮转后压缩，缓存设过期，归档要 按包而不是按单个文件 保存

找出是什么吃掉的 - du 惯用法

确定了挂载点，也确认了确实是容量问题，接下来就是自上而下逐层收窄。惯用法有一条就够。

$ du -h -x --max-depth=1 . | sort -h
1.0K    ./deleted_open
1.0K    ./demo2
24M     ./tiny
25M     .

# 大的排在下面，所以从最后一行往上读。
# 在 Linux 上通常这样开始。
$ sudo du -h -x --max-depth=1 / | sort -h

三个选项各司其职。--max-depth=1 只展示 一层。不给深度就会涌出几万行，根本读不了。sort -h 会把 24M 这类给人看的写法 按大小 排序。按字符串排序的话，9K 会排在 24M 后面。

而 -x 是这条惯用法的核心。它是阻止 越到别的文件系统上去 的选项。去掉它再从 / 开始扫，就会一路跟进挂载的网络存储和容器层，时间要多花好几倍，而且和当前要找的文件系统无关的数字会混进结果里。

不过这里也有要老实写下来的地方。在这个环境里，我没能造出 -x 真正挡住了什么的场面。

$ stat -c %d / /tmp .
3927831023
3927831023
3927831023
# 三个的设备 ID 相同 -> 压根就没有让 -x 停下来的边界。
# 只确认到选项被接受、结果相同为止。

# 按文件数量收窄的版本 (inode 耗尽时)
$ find . -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head -5
  20000 ./tiny
      5 .
      1 ./demo2
      1 ./deleted_open
  • sort -h 是 GNU 扩展。在这个环境的帮助里确认了它以 -h, --human-numeric-sort 的形式实际存在，但 BSD 系或最小容器镜像里可能没有。那时就用 du -k 取出来再用 sort -n
  • du --inodes 数的不是大小而是 条目数量。inode 耗尽时，把上面那条惯用法里的 -h 去掉换成它，就能照样用
  • find 会一个一个地扫文件，所以 在文件多的文件系统上会跑很久。在运行中的服务器上要顾及负载，先把范围收窄再开始
  • 结果 与合计对不上 就要怀疑原因②。用 du 怎么加都够不到 df 的用量，说明某处开着没有名字的文件

诊断顺序 - 四个步骤

把前面的内容折成执行顺序，就是四个步骤。每一步的存在，都是为了 决定要不要进入下一步。之所以要守住顺序，是因为前面的步骤比后面的便宜得多。

步骤问的是什么命令如果是这样下一步
1是哪个挂载点df -h <失败的路径>那一行的 Use% 很低你看错了路径。重新确认失败的路径
2是容量还是 inodedf -i <失败的路径>只有 IUse% 是 100%原因①。去找文件扎堆的目录
3与 du 对不上吗把 du -sh -x <挂载点> 与 df 对照du 的合计小得多原因②。找出占住的进程并重启
4是什么吃掉的du -h -x --max-depth=1 | sort -h能锁定较大的条目一层一层往下重复
+是不是只有 root 能过用普通账号和 root 各 touch 一次只有 root 成功原因③。去确认预留块
  • 第 1 步和第 2 步 加起来两行，几乎没有负载。而只靠这两步就结束的情况实际上相当多
  • 跳过第 3 步，就会在第 4 步把时间耗光却什么也找不到。知道 存在 du 找不出元凶的情形，正是这张表的要点

容器与云上会有哪些不同

同样的症状在容器里更让人犯迷糊。容器里的 df 回答的是 那个容器看得见的挂载，而真正满了的往往是宿主节点的磁盘。反过来也有节点余量充裕，只是容器可写层上的配额满了的情况。得先定下 是在哪一边敲的 df。

情形容易误以为的事实际该看的地方
镜像层满了卷还有余量，所以没事可写层与卷是 不同的文件系统
停止的容器和旧镜像堆积了只数正在运行的，也没多少把停止的容器、未使用的镜像、构建缓存全部合算
容器日志无限增长应用没有留日志是运行时把标准输出写成文件。确认大小上限的设置
云上把磁盘扩容了却没变化在控制台扩了就完事了分区和文件系统 要分别扩
节点的 inode 满了容量曲线是平的，所以没问题镜像层就是一堆小文件。要单独监控 inode

最后一行尤其常中招。resize2fs 文档明确写着 本程序不会操作分区的大小。也就是说，扩了块设备之后要先扩分区，然后再扩文件系统。把这两步当成一步，就会出现控制台上容量涨了、服务器里却没变的状态。

# 云磁盘扩容之后 - 是有顺序的 (本环境里没能执行)
# ① 内核有没有看到新的大小
lsblk

# ② 扩展分区 (只在使用分区的配置里)
sudo growpart /dev/sda 1

# ③ 扩展文件系统
sudo resize2fs /dev/sda1        # ext2/3/4
sudo xfs_growfs /               # XFS 要给挂载点

# 容器这边 - 按类别统计什么占了地方
docker system df
docker system df -v
  • 叠加层方式在修改文件时会 先把原件复制到上层 再改。改大文件里的一行，也可能需要相当于该文件大小的额外空间
  • 在容器里删掉的文件 不会从下层消失。只是在上面盖一个删除标记，所以镜像大小不会变小
  • 清理命令有多方便就有多危险。存在 连未使用的卷也一起删掉的选项，而那些卷里可能装着数据
  • 整个节点满了的时候，调度器会 把 Pod 挤到别的节点上。症状先表现为重启而不是磁盘，原因就被发现得晚

情况紧急时 - 可以删的和不能删的

服务停着的时候没有时间判断。所以需要 事先定好的清单。不过第一步不是删除。先确认有没有被占住的空间 才是第一步。如果是原因②，删什么都收不回来，不确认就开始删，只会白丢时间，留下无法撤销的删除。

分类对象为什么
相对安全轮转后压缩的旧日志已经是关闭的文件。只要确认保留期限即可
相对安全包管理器缓存可以重新下载。只花重装的时间
相对安全构建产物与临时目录可以重新生成。但要确认 没有正在进行的构建
注意核心转储删掉也行，但那是 故障原因分析的材料。先移走
绝对禁止当前正打开的日志本体空间回不来，只丢日志。还会制造出原因②
绝对禁止数据库文件、锁文件、套接字会导致损坏或起不来
绝对禁止内容不明的目录越急越是不看就删。无法撤销
注意 - rm -rf 不会征求确认，也无法撤销。把路径做成变量来用，就会出 变量为空时从最上层开始删的事故。执行前先用同样的参数跑一次 ls -d，用眼睛确认对象，这个习惯很便宜。truncate -s 0 会留下文件把内容清空，所以能用在打开着的日志上，但 内容照样没了。有要留的东西就先移走。
  • 空间彻底为 0 时，删除这个动作本身也可能失败。要留日志或建临时文件的工具，这时是不工作的
  • 所以像 truncate -s 0 或 : > 文件 这样 不创建新文件的清空方式，在这种局面下很有用
  • 把急火压住之后，一定要回头追原因。删掉就解决了，并不能解释它为什么会满。 同样的事会按同样的周期回来

从源头上防住的办法

这个症状很多时候是因为少了一个监控项。容量几乎到处都在看，但 inode 使用率常常不在默认仪表盘上。 于是容量曲线平平的，故障却发生了。

我做了一段只取出超阈值挂载点的脚本跑了跑，结果在这里出现了 常见惯用法真的出错的场面。这是值得记下来的失败，就原样搬过来。

# 常用的版本 - 在本环境里给出了错误答案
$ df -P | awk 'NR>1 && $5+0 >= 80 {print $6, $5}'
65% 347611880          # 值反过来了

# 原因 - 设备名里有空格，字段错开了一位
$ df -P | awk 'NR>1 {print "NF=" NF "  $5=[" $5 "]  $6=[" $6 "]"}'
NF=7  $5=[347583704]  $6=[65%]

# 改好的版本 - 不数字段，而是指定着接收
$ df --output=pcent,target | awk 'NR>1 && $1+0 >= 60 {print "DISK", $2, $1}'
DISK / 65%

$ df --output=ipcent,target | awk 'NR>1 && $1+0 >= 60 {print "INODE", $2, $1}'
(无输出 - 这个文件系统不报告 inode 比率)

按字段号切 df -P 输出的做法，立足于 设备名或挂载点里没有空格这个假设。假设一破，它就悄悄读了别的列，条件式照样为真，于是 错误的告警看起来一切正常地发了出去。 用 df --output= 只接收需要的列，这个假设本身就不需要了。

  • 把 inode 使用率加进监控项。 设成和容量一样的阈值就够了。这不是聊胜于无的程度，本文的原因①靠这一项就能全部预防
  • 日志轮转要把 保留份数和是否压缩 一起定。只把份数调大，容量没事而 inode 会满
  • 给临时文件挂上 过期清理。会话和缓存，写创建代码的人得连删除代码一起写好
  • 容器日志要明确 文件大小上限和保留份数。默认值是无限制的配置很常见
  • 告警按 剩余时间而不是剩余百分比 来看更好。知道一天涨几 GB，就能算出什么时候会满

小结

No space left on device 不是诊断，而是诊断的开始。它背后至少有四种情形，而 该做的事会因为是哪一种而完全相反。inode 满了，找大文件也没用；已删除却仍打开的文件是原因时，删得更多反而有害。

所以要记的不是命令清单而是顺序。把失败的路径直接交给 df，用 df -i 分清是容量还是数量，把 du 的合计与 df 对上，然后才去找是什么吃掉的。第三步就是这个顺序的价值所在。在这里看到对不上，就能提前知道剩下的搜寻全是白费。

还有，本文里实际量出来的两个数字值得记住。删掉的 1GiB 在杀掉进程之前只回来了 16 个块，以及 两万个 1 字节文件占了 23.5MiB。这两个数字，靠只看一次 df 的习惯绝对看不见。

未能确认的部分

  • 没能造出 inode 真的耗尽的画面。这个环境的 NTFS 不报告 inode 数量，所以 df -i 全都出 -。IUse% 为 100% 的输出不在本文里，取而代之的是用 stat -f 展示了 为什么会是空白
  • 没能跑 lsof +L1。 这个环境里没装 lsof。选项的含义在文档里确认过，同样目的的 /proc/<pid>/fd 那一侧则实际跑了，连 (deleted) 标记都确认到了
  • tune2fs、debugfs、resize2fs、xfs_growfs 没能执行。 它们是 ext4/XFS 专用工具，而这个环境里没有对应的文件系统。预留块比率 5%、XFS 的 maxpct 默认值、resize2fs 不碰分区这几点，是 在官方 man 文档里确认的
  • 没能直接测量 ext4 上 1 字节文件的分配量。这个环境里出来的是 1,024 字节，那是 NTFS 存放小文件的方式所致。按 4KiB 块得出的计算值，正文里已 标明是计算
  • 没能造出 du -x 在文件系统边界上停下的场面。/、/tmp 和工作目录的设备 ID 全都相同，没有可越的边界。只确认到选项被接受为止
  • btrfs 的 df -i 输出形式 未能确认。只确认了内核文档的功能清单里列有动态 inode 分配这一事实，那些数字该怎么读，本文没有涉及
  • 容器与云那两节全部未执行。叠加层的行为、清理命令的输出、磁盘扩容的步骤，在这个环境里一个都没跑过。只写了命令的顺序和依据

参考资料

  • mke2fs(8) - man7.org - 预留块默认值是 5% 这一点，以及 -i 的 bytes-per-inode 比率 在文件系统创建之后无法更改 的警告
  • tune2fs(8) - man7.org - -m 选项的说明。里面写着预留块的两个理由是 避免碎片化 和 让系统守护进程在非特权进程被挡住之后仍能继续工作
  • mkfs.xfs(8) - man7.org - maxpct 的含义与按大小的默认值（1TB 以下 25%、50TB 以下 5%、再往上 1%），以及这个值可以用 xfs_growfs 修改的说明
  • xfs_growfs(8) - man7.org - 用 -m 重新指定可分配给 inode 的最大比率的选项说明
  • lsof(8) - man7.org - +L 后面给数字就只列出链接数小于它的文件，而 +L1 这种写法会挑出 名字已被删除却仍打开着的文件 的说明
  • resize2fs(8) - man7.org - 本程序不会操作分区的大小 这一句。它是扩完磁盘之后必须分别扩展分区与文件系统的依据
  • BTRFS - The Linux Kernel documentation - 功能清单里包含 动态 inode 分配 这一点
