관계형 데이터베이스를 운영하는 조직에서 트래픽과 데이터가 불어날 때 가장 먼저 떠올리는 단어는 수평 확장이다. 웹 서버나 애플리케이션 컨테이너를 늘리듯 데이터베이스도 노드를 여러 대로 나누면 쓰기 용량과 저장 공간이 선형으로 늘어날 것이라는 기대를 품는다. 실제로 NoSQL이나 분산 키-값 저장소는 그런 방식으로 확장한다. 그러나 PostgreSQL은 태생이 단일 노드 중심의 강력한 관계형 엔진이다.

단일 인스턴스에서 작동하던 데이터베이스를 여러 대의 물리 머신으로 쪼개는 순간, 우리가 당연하게 누려왔던 수많은 기능이 침묵 속에서 깨지거나 막대한 비용 청구서로 돌아온다. 단일 메모리 공간에서 즉각 검증되던 원자적 트랜잭션은 네트워크 통신을 거치는 분산 합의로 바뀌고, 초고속 해시 조인은 네트워크 대역폭을 잠식하는 데이터 전송 작업이 된다. 테이블 수준에서 유일성을 보장하던 인덱스와 자동 증가 시퀀스는 전역 충돌의 뇌관으로 변한다.

이 글은 특정 분산 도구나 솔루션을 찬양하거나 비하하기 위해 쓰이지 않았다. 단일 머신에서 되던 일들이 네트워크 경계를 넘어서는 순간 구조적으로 무엇이 깨지고, 무엇을 포기해야 하며, 어떤 대체 장치를 마련해야 하는지를 냉정하게 해부한다. 나아가 샤딩이라는 위험하고 되돌리기 어려운 강을 건너기 전에, 단일 인스턴스 안에서 반드시 먼저 쥐어짜 내야 할 최적화 단계들을 짚는다.

이 글에서 다루는 분산 트랜잭션의 한계와 2단계 커밋(2PC), 테이블 파티셔닝 제약은 PostgreSQL 17 공식 문서의 규정을 바탕으로 한다. 계기로 언급하는 Multigres 관련 아키텍처와 한계는 해당 프로젝트의 공식 저장소 README와 기술 문서가 스스로 밝힌 내용에 국한하며, 원문에 없는 성능 벤치마크나 처리량 수치는 일절 적지 않는다.

계기 - Postgres 수평 확장을 표방한 오픈소스의 등장

2026년 9월 초 개발자 커뮤니티에 Multigres라는 프로젝트가 소개되었다. MySQL 생태계에서 수평 확장의 사실상 표준으로 자리 잡았던 Vitess의 아키텍처를 PostgreSQL에 접목하려는 오픈소스 시도다. 이 프로젝트의 핵심은 PostgreSQL의 코드를 수정하여 새로운 호환 데이터베이스를 포크하는 것이 아니라, 순정 PostgreSQL 인스턴스들 앞단에 프록시와 연결 풀러, 오케스트레이터를 계층화하여 수평 확장을 달성하겠다는 점에 있다.

공개 저장소와 공식 문서를 통해 확인할 수 있는 사실은 세 가지로 요약된다.

  • 무엇을 하는 구조인가 — 애플리케이션과 데이터베이스 사이에 다계층 프록시를 둔다. 상위 계층인 Multigateway는 애플리케이션의 PostgreSQL 연결을 받아 적절한 노드로 쿼리를 라우팅하고 분산 조인을 조율하는 일종의 연산 계층이다. 하위 계층인 Multipooler는 각 PostgreSQL 인스턴스마다 1:1로 상주하며 연결 재사용과 트랜잭션 상태를 보존한다. Multiorch는 복제와 자동 장애 전환, 정족수 기반 WAL 동기화를 감시한다.
  • 무엇을 요구하는가 — 연관된 테이블과 행이 동일한 샤드에 물리적으로 위치하도록 설계하는 관계형 샤딩 모델을 채택한다. 그래야만 분산 조인과 분산 트랜잭션을 최소화할 수 있기 때문이다. 샤드 간 트랜잭션이 불가피한 경우 PostgreSQL 자체의 2단계 커밋(2PC) 기능을 활용하도록 설계되어 있다.
  • 문서가 스스로 밝힌 현재의 한계 — 이 프로젝트는 2026년 6월 첫 알파 버전을 공개한 초기 단계다. 현재 공개 릴리스에는 연결 풀링, 자동 장애 전환, 백업과 쿠버네티스 오퍼레이터만 포함되어 있으며, 가장 핵심적인 샤딩 기능은 아직 공식 릴리스에 포함되지 않은 개발 계획 상태다. 또한 풀러 계층을 통과할 때 CREATE DATABASE, 외부 데이터 래퍼(FDW), 일부 동적 SQL이 제한된다고 명시하고 있다.
  • 프로덕션 사용에 대한 원문의 입장 — 프로젝트 공식 문서는 현재 단계를 실험 및 테스트를 위한 알파 상태로 규정하며, 프로덕션 환경에서의 사용을 권장하지 않는다고 분명히 밝히고 있다.

이 발표는 개발자들에게 중요한 질문을 던진다. 기술적으로 거대한 오케스트레이션 계층을 세워서라도 PostgreSQL을 여러 대로 쪼개야 하는 순간은 언제이며, 그 과정에서 시스템이 지불해야 하는 진짜 대가는 무엇인가 하는 점이다.

수직 확장이 먼저 부딪히는 물리적 한계

데이터베이스의 용량이 부족해질 때 가장 자연스럽고 안전한 길은 수직 확장(Scale-up)이다. 더 많은 CPU 코어, 수백 기가바이트의 RAM, 그리고 수만 IOPS를 보장하는 엔터프라이즈 NVMe 스토리지를 단일 머신에 투입하는 방식이다. 수직 확장은 애플리케이션 코드나 SQL을 단 한 줄도 수정할 필요가 없으며, 관계형 데이터베이스가 제공하는 모든 ACID 보장과 인덱스, 제약 조건을 온전히 유지할 수 있다.

실제로 오늘날 대다수의 서비스는 수직 확장만으로도 충분히 운영된다. 현대의 클라우드 인스턴스는 단일 노드에서 수백 개 규모의 vCPU와 테라바이트 단위 메모리를 제공한다. 이 정도 하드웨어에 적절한 인덱싱과 읽기 복제본(Read Replica)을 결합하면 초당 수만 건의 트랜잭션을 너끈히 처리할 수 있다. 그럼에도 불구하고 수직 확장이 물리적으로 완전히 벽에 부딪히는 지점이 존재한다.

  • 단일 마스터의 쓰기 처리량 한계 — 읽기 요청은 복제본을 열 대, 스무 대 늘려 분산할 수 있지만, 데이터 변경(INSERT, UPDATE, DELETE)은 오직 하나의 프라이머리 노드를 통과해야 한다. 쓰기 작업은 WAL(Write-Ahead Logging) 플러시, 공유 버퍼의 더티 페이지 정리, 로우 레벨 잠금 경합을 필연적으로 동반하므로 단일 노드의 스토리지 쓰기 대역폭과 CPU 한계선에 도달하면 더 이상 스케일업이 작동하지 않는다.
  • 유지보수 창과 VACUUM 부담의 폭증 — 데이터가 수십 테라바이트 단위로 누적되면 단일 노드 내부의 유지보수 작업이 재앙으로 변한다. PostgreSQL의 다중 버전 동시성 제어(MVCC)는 죽은 튜플을 청소하기 위해 VACUUM을 필요로 하는데, 테이블 크기가 너무 거대해지면 자동 진공(Autovacuum)이 디스크 I/O를 잠식하여 서비스 응답 속도를 떨어뜨린다. 대용량 B-tree 인덱스를 재구축(REINDEX)하는 작업 역시 수 시간에서 수일이 소요되어 장애 위험을 키운다.
  • 단일 장애점(SPOF)과 복구 시간(RTO) — 단일 노드의 덩치가 커질수록 노드 크래시 발생 시 크래시 복구(Crash Recovery)와 WAL 재생에 소요되는 시간이 기하급수적으로 늘어난다. 페일오버를 수행하더라도 거대한 메모리 버퍼 캐시가 비어 있는 상태(Cold Cache)에서 트래픽을 즉시 감당하지 못하고 연쇄적인 지연을 겪게 된다.
  • 하드웨어 가성비의 급격한 악화 — 상용 서버나 클라우드 인스턴스는 특정 사양을 넘어서는 순간 비용 곡선이 기하급수적으로 가팔라진다. 상위 사양으로 갈수록 비용은 사양에 비례하지 않고 더 가파르게 오른다. 구체적인 배수는 벤더와 시점에 따라 다르므로 실제 견적으로 확인해야 한다.

이처럼 쓰기 한계, 유지보수 불능, 복구 위험이 동시에 임계점에 도달했을 때 비로소 아키텍트는 데이터베이스를 여러 대로 쪼개는 수평 확장을 검토하게 된다.

수직 확장과 수평 확장의 구조적 비교

수직 확장과 수평 확장은 단순히 서버 대수의 차이가 아니다. 시스템의 아키텍처적 패러다임과 제약 조건을 완전히 맞바꾸는 선택이다. 둘 사이의 본질적인 특성을 명확히 비교하면 다음과 같다.

SQL 호환성 100% 완전한 PostgreSQL 기능 지원 조인, 트랜잭션, 제약의 부분적 제한 발생 수평 확장은 애플리케이션 쿼리의 수정을 강제한다.
트랜잭션 보장 단일 엔진의 로컬 ACID (WAL 및 MVCC) 샤드 간 2단계 커밋(2PC) 또는 결과적 일관성 분산 트랜잭션은 대기 시간과 잠금 시간을 폭증시킨다.
운영 복잡도 단일 인스턴스 모니터링 및 단순 백업 프록시, 연결 풀러, 샤드별 오케스트레이션 관리해야 할 프로세스와 장애 지점이 배수로 늘어난다.
쓰기 한계 극복 단일 머신의 하드웨어 천장에 묶임 샤드 키를 기준으로 쓰기 부하를 여러 대로 분산 초고용량 쓰기 트래픽을 감당할 수 있는 유일한 통로다.
데이터 물리 격리 동일 디스크/테이블스페이스에 데이터 응집 샤드 단위로 물리 머신 및 저장소가 분리됨 특정 샤드의 장애가 전체 클러스터 정체로 번지지 않도록 격리해야 한다.

위 표가 보여주듯 수평 확장은 쓰기 처리량과 데이터 용량의 한계를 돌파할 수 있는 강력한 무기지만, 그 대가로 단일 노드가 제공하던 완벽한 관계형 추상화를 파괴한다.

나누는 순간 달라지는 것들 - 한 대에서 되던 것의 파괴

개발자가 PostgreSQL을 사랑하는 이유는 정교하고 강력한 기능들 덕분이다. 외래키를 걸어 데이터의 부모-자식 관계가 어긋나지 않도록 엔진이 감시하고, 복잡한 비즈니스 로직을 단일 트랜잭션 안에 묶어 실패 시 깔끔하게 롤백한다. 여러 테이블을 조인하여 단 한 번의 쿼리로 원하는 보고서 데이터를 뽑아내고, SERIAL 키를 통해 중복 없는 단조 증가 번호를 손쉽게 발급받는다.

그러나 데이터베이스를 여러 대로 쪼개는 순간, 이 모든 편의 기능이 일제히 깨져나간다. 분산 환경에서는 서로 다른 물리 머신에 존재하는 두 테이블 사이의 메모리 포인터를 연결할 수 없으며, 서로 다른 디스크의 WAL을 원자적으로 기록할 수 없다. 즉, 한 대의 컴퓨터 안에서 CPU 메모리 버스를 타고 돌던 통신이 네트워크 케이블과 스위치를 통과하는 TCP 패킷으로 치환되기 때문이다.

단일 인스턴스에서 마이크로초(µs) 단위로 완료되던 잠금 획득과 인덱스 탐색은 네트워크 왕복 시간(RTT)이 개입하면서 밀리초(ms) 단위로 늘어난다. 연산 속도가 천 배 느려지는 환경에서는 단일 노드 방식의 락킹 메커니즘과 일관성 모델을 그대로 유지할 수 없다. 결국 수평 확장이란 공짜 확장이 아니라, 관계형 엔진의 핵심 기능들을 하나씩 포기하거나 분산 시스템용 대용품으로 교체하는 거래다.

트랜잭션 경계 - 샤드를 넘는 2PC와 원자성의 비용

수평 확장 클러스터에서 가장 심각한 타격을 입는 영역은 트랜잭션의 원자성(Atomicity)이다. 하나의 샤드 안에서 완결되는 작업이라면 해당 노드의 로컬 트랜잭션 엔진이 이전과 동일하게 ACID를 보장한다. 문제는 하나의 논리적 작업이 서로 다른 샤드에 위치한 데이터를 동시에 수정해야 할 때 발생한다.

이를 해결하기 위해 데이터베이스 진영이 고안한 고전적 수단이 2단계 커밋(2PC, Two-Phase Commit)이다. 코디네이터 노드가 모든 참여 샤드에 변경 사항을 디스크에 안전하게 기록하고 커밋할 준비가 되었는지 묻는 준비(Prepare) 단계를 거친 뒤, 모든 샤드가 성공 응답을 보냈을 때 비로소 실제 반영(Commit) 명령을 내린다. PostgreSQL은 엔진 수준에서 PREPARE TRANSACTION 및 COMMIT PREPARED 명령을 통해 2PC를 지원한다.

-- 분산 트랜잭션 환경에서 PostgreSQL의 2단계 커밋(2PC) 처리 흐름
-- [1단계: 트랜잭션 시작 및 작업 수행]
BEGIN;
UPDATE user_balance SET balance = balance - 10000 WHERE user_id = 42;

-- [2단계: 커밋 준비 - 현재 세션에서 트랜잭션을 분리해 상태를 디스크에 영속화]
PREPARE TRANSACTION 'tx_shard1_user42_20260912';

-- 코디네이터가 다른 샤드의 준비 상태를 모두 확인한 후 커밋을 지시함
-- [3단계: 최종 전역 커밋 실행]
COMMIT PREPARED 'tx_shard1_user42_20260912';

-- 장애 발생 또는 다른 샤드 실패 시 롤백 수행
-- ROLLBACK PREPARED 'tx_shard1_user42_20260912';

이 2PC 메커니즘은 논리적으로 완벽해 보이지만, 실제 운영 환경에서는 치명적인 성능 저하와 가용성 위험을 유발한다. PostgreSQL 17 공식 문서는 PREPARE TRANSACTION에 대해 다음과 같은 중대한 경고를 남겨두고 있다.

  • max_prepared_transactions 활성화 의무 — 기본 설정값은 0(비활성화)이며, 외부 트랜잭션 관리자를 엄격하게 운영하지 않는 한 0으로 유지할 것을 강력히 권고한다. 실수로 활성화했다가 방치된 트랜잭션이 시스템을 파괴하는 것을 막기 위함이다.
  • 잠금(Lock)의 영구적 유지 — 트랜잭션이 PREPARE 상태에 들어가면 세션이 끊어지더라도 해당 트랜잭션이 잡고 있던 모든 테이블 및 행 잠금이 풀리지 않고 디스크에 유지된다. 네트워크 순단이나 코디네이터 장애로 커밋 명령을 받지 못하면 다른 모든 세션이 해당 데이터에 접근하지 못하고 무한정 블로킹된다.
  • VACUUM 청소의 전면 차단 — 준비된 트랜잭션은 자신이 생성된 시점의 트랜잭션 ID(XID)를 고정시킨다. 따라서 VACUUM 프로세스가 오래된 죽은 튜플을 회수하지 못하게 가로막아 테이블 크기가 비정상적으로 팽창(Bloat)한다.
  • 트랜잭션 ID 래핑(Wraparound)에 따른 셧다운 위험 — 준비된 트랜잭션이 장시간 방치되면 XID 소비가 누적되어 데이터베이스가 데이터 유실을 방지하기 위해 강제로 비상 셧다운되는 최악의 장애로 이어진다.

이러한 물리적 오버헤드 때문에 Multigres 같은 최신 수평 확장 시스템조차 "가능한 한 분산 트랜잭션(2PC)을 피할 수 있도록 샤딩 설계를 최적화해야 한다"고 거듭 강조한다. 결국 여러 샤드에 걸친 ACID 트랜잭션은 성능상 지옥을 의미하며, 실무에서는 사가(Saga) 패턴을 통한 비동기 결과적 일관성을 수용하거나 단일 샤드 내부로 쓰기를 가두는 타협을 해야 한다.

조인 연산 - 데이터 배치와 네트워크 왕복의 병목

단일 PostgreSQL 노드에서 실행되는 조인은 엔진이 최적의 실행 계획(Planner)을 수립하여 중첩 루프(Nested Loop), 해시 조인(Hash Join), 머지 조인(Merge Join) 중 가장 빠른 경로를 선택한다. 모든 테이블 데이터가 동일한 메모리 버퍼와 로컬 디스크에 존재하므로 수십만 건의 조인도 수십 밀리초 안에 끝난다.

하지만 데이터가 열 대의 샤드로 쪼개져 있는 상태에서 orders 테이블과 users 테이블을 조인한다고 가정해 보자. 조인 연산의 실행 양상은 데이터가 어떻게 배치되어 있는가에 따라 극단적으로 갈린다.

  • 콜로케이션 조인 (Collocation Join) — orders와 users가 동일한 샤딩 키(예: user_id)를 기준으로 샤딩되어 있고, 동일한 ID를 가진 행들이 물리적으로 같은 PostgreSQL 노드에 저장되어 있는 경우다. 이 경우 상위 게이트웨이는 조인 쿼리 전체를 각 샤드로 그대로 밀어 넣는다(Pushdown). 각 샤드는 자신의 로컬 데이터만으로 조인을 완결하여 결과를 반환하므로 네트워크 비용이 전혀 들지 않는다.
  • 브로드캐스트 조인 (Broadcast Join) — 코드 테이블이나 카테고리 정보처럼 데이터 크기가 작고 변경이 거의 없는 참조 테이블을 조인할 때 사용된다. 참조 테이블의 전체 복사본을 모든 샤드에 미리 복제해 두고, 로컬 샤드에서 조인을 수행한다. 참조 테이블의 갱신 비용이 매우 커진다는 단점이 있다.
  • 스캐터-개더 조인 (Scatter-Gather Cross-shard Join) — 최악의 시나리오다. 조인 대상 테이블들이 서로 다른 키로 샤딩되어 있거나 연관 관계가 샤드 경계를 넘나드는 경우다. 게이트웨이는 관련된 모든 샤드로 쿼리를 흩뿌려(Scatter) 엄청난 양의 중간 데이터 세트를 네트워크를 통해 수집(Gather)한 뒤, 게이트웨이 자신의 메모리 위에서 직접 해시 테이블을 만들어 조인을 수행해야 한다.

스캐터-개더 조인이 발생하는 순간 네트워크 대역폭은 순식간에 포화 상태에 이르고, 게이트웨이 노드의 메모리가 고갈되어 OOM(Out of Memory) 크래시가 발생할 위험이 커진다. 결국 수평 확장 아키텍처에서는 단일 노드 시절 마음껏 구사하던 다중 조인 쿼리를 봉인해야 하며, 필요한 데이터를 비정규화(Denormalization)하여 중복 저장하거나 애플리케이션 계층에서 여러 번 조회하여 조합하는 고통스러운 작업을 감수해야 한다.

유니크 제약과 시퀀스 - 전역 유일성이 사라지는 자리

단일 인스턴스에서 테이블에 id SERIAL PRIMARY KEY 또는 email VARCHAR(255) UNIQUE를 선언하는 것은 너무나 자연스러운 일상이다. 엔진이 로컬 B-tree 인덱스를 탐색하여 중복된 값이 들어오는 순간 즉각적인 에러를 뿜어내며 무결성을 지켜주기 때문이다.

그러나 노드가 여러 개로 갈라지면 이 전역 유일성(Global Uniqueness)이 완전히 깨진다.

  • 단일 시퀀스의 충돌 — PostgreSQL의 시퀀스는 단일 인스턴스의 메모리 카운터에 기반한다. 샤드 1에서도 1부터 증가하고, 샤드 2에서도 1부터 증가한다면 두 노드에서 생성된 기본 키는 즉시 충돌한다. 분산 환경에서는 자동 증가 시퀀스를 버리고 128비트 UUIDv7(타임스탬프 기반 정렬 지원)을 사용하거나, 트위터가 고안했던 Snowflake 형태(타임스탬프 + 워커 노드 ID + 시퀀스)의 외부 분산 ID 생성기를 구축해야 한다. 이는 저장 공간의 낭비와 인덱스 크기 증가로 이어진다.
  • 샤딩 키 이외 컬럼의 유니크 제약 불가 — 이것은 선언적 파티셔닝과 수평 샤딩 모두에서 동일하게 발생하는 가장 본질적인 제약이다. PostgreSQL 17 공식 문서는 선언적 파티셔닝 테이블에 대해 다음과 같이 명시한다: "유니크 또는 기본 키 제약을 생성하려면 파티션 키가 제약 조건 컬럼에 반드시 포함되어야 한다. 왜냐하면 개별 파티션 인덱스는 오직 자기 파티션 내부의 유일성만 강제할 수 있기 때문이다."
  • 전역 보증을 위한 비용 — 만약 사용자를 user_id로 샤딩한 상태에서 email 컬럼에 유니크 제약을 걸고 싶다면 어떻게 해야 하는가? 엔진 수준에서는 이를 막을 방법이 없다. 샤드 1에 존재하는 이메일이 샤드 2에 다시 INSERT될 때, 샤드 2의 PostgreSQL은 샤드 1의 인덱스를 볼 수 없기 때문이다. 이를 방지하려면 별도의 전역 인덱스 샤드를 두고 이메일 조회를 먼저 수행하게 하거나, 레디스(Redis) 같은 외부 분산 락을 걸어야 한다.
  • 성능 저하의 악순환 — 모든 쓰기 작업마다 유일성을 검증하기 위해 전역 조회를 수행해야 한다면, 수평 확장을 통해 얻으려 했던 쓰기 처리량 증대 효과는 완전히 상쇄되고 만다.

외래키와 분산 집계 - 포기하거나 대체해야 하는 것들

관계형 데이터베이스의 또 다른 기둥인 외래키(Foreign Key)와 집계 연산(Aggregation) 역시 수평 확장의 칼날을 피할 수 없다. 아래 표는 한 대에서 당연하게 동작하던 핵심 기능들이 분산 샤딩 환경에서 어떻게 깨지며, 현업에서 무엇으로 이를 대체하거나 포기하는지를 집대성한 결과다.

관계형 데이터베이스 기능 단일 노드(Single Node) 동작 여러 대로 나눌 때(Sharding) 발생하는 현상 실무적 대체 또는 포기 수단
원자적 트랜잭션 (ACID) 단일 엔진의 로컬 WAL과 MVCC로 즉각적 원자성 보장 여러 샤드에 걸친 갱신 시 2PC 필요, 네트워크 지연 및 락 장기화 동일 샤드 내 트랜잭션으로 한정하거나, 사가(Saga) 패턴 및 결과적 일관성 수용
테이블 간 조인 (JOIN) 로컬 메모리 내 해시/머지 조인으로 수십 ms 내 초고속 처리 샤드 간 대량 데이터 네트워크 전송(Scatter-Gather), 프록시 메모리 폭증 동일 샤딩 키 배치(Collocation) 강제, 데이터 비정규화, 애플리케이션 조합
전역 유니크 제약 (UNIQUE) 로컬 B-tree 인덱스를 통해 중복 삽입 즉시 차단 샤딩 키가 포함되지 않은 컬럼은 타 샤드의 중복을 알 수 없음 샤딩 키를 유니크 키에 합성하거나, 전역 매핑 테이블/외부 분산 락 구축
기본 키 자동 증가 (SERIAL) 단일 시퀀스 카운터로 단조 증가 번호 간편 발급 노드마다 독립된 카운터가 돌아 동일한 번호가 반드시 충돌함 UUIDv7, Snowflake 분산 ID 생성기, 노드별 범위 할당 시퀀스
외래키 제약 (FOREIGN KEY) 부모-자식 참조 무결성 및 CASCADE 삭제를 엔진이 강제 부모 행과 자식 행이 서로 다른 노드에 존재할 경우 참조 검증 불가 엔진 레벨 외래키 전면 제거, 애플리케이션 계층에서 무결성 로직 직접 구현
집계 및 페이징 (GROUP BY / LIMIT OFFSET) 인덱스 역순 스캔 및 인라인 정렬로 즉각 반환 모든 샤드에서 N건씩 긁어모아 프록시에서 재정렬, 심층 오프셋 시 부하 폭발 커서 기반 페이징(Keyset Pagination) 도입, 사전 집계 테이블/OLAP 분리

특히 ORDER BY created_at LIMIT 20 OFFSET 10000 같은 심층 페이징 쿼리는 분산 환경의 대표적인 재앙이다. 게이트웨이는 10개 샤드 전체에 10,020건씩 데이터를 요청하여 총 10만 건 이상의 데이터를 네트워크로 끌어온 뒤 메모리에서 재정렬해야 한다. 관계형 데이터베이스가 주던 편의성은 사라지고, 모든 부담이 애플리케이션 엔지니어의 코드로 전가된다.

샤딩 키는 되돌리기 어렵다 - 핫스팟과 리샤딩의 무게

수평 확장을 결정했다면 가장 먼저 마주하는 숙제가 샤딩 키(Sharding Key, 파티션 키)의 선정이다. 샤딩 키는 어떤 데이터가 몇 번 샤드로 들어갈지를 결정하는 물리적 우편번호다. 샤딩 키를 선정하는 기준과 각각의 위험 요소는 다음과 같다.

샤딩 키 선정 기준 의미와 핵심 고려 사항 권장되는 적합 패턴 부적합한 패턴과 위험성
카디널리티 (값의 다양성) 고유한 값의 가짓수가 충분히 많아야 균등하게 나뉨 수백만 개 이상의 고유 식별자 (user_id, account_id) 상태값(status), 성별, 국가 코드 등 소수의 범주형 값 (극단적 쏠림)
쓰기 트래픽의 균등성 특정 시점에 특정 노드로만 쓰기가 집중되지 않아야 함 해시 기반 샤딩, 무작위성이 보장되는 비즈니스 엔터티 키 타임스탬프, 자동 증가 ID (최신 날짜 샤드 하나만 불타오르는 핫스팟)
접근 패턴의 일치도 대부분의 조회 WHERE 조건에 샤딩 키가 포함되어야 함 핵심 도메인의 진입점 키 (테넌트 ID, 고객 고유 번호) 조회 조건에 거의 쓰이지 않는 내부 UUID (매번 전체 샤드 스캔)
데이터 크기 성장 방향 특정 키에 종속된 데이터 볼륨이 비정상적으로 커지지 않아야 함 개인 사용자 단위, 균등한 규모의 중소형 테넌트 대기업 테넌트가 포함된 B2B 키 (한 테넌트가 샤드 디스크 90% 점유)
키의 불변성 (Immutability) 샤딩 키 값이 수정되면 행을 다른 물리 머신으로 이관해야 함 생성 후 절대로 변경되지 않는 불변의 비즈니스 고유 키 이메일, 부서 코드, 변경 가능한 사용자 설정 닉네임

샤딩 키 선택이 극도로 두려운 이유는 한 번 정하면 되돌리기가 사실상 불가능에 가깝기 때문이다. 만약 날짜별로 샤딩을 했다가 최신 노드에만 쓰기가 몰리는 핫스팟(Hotspot)이 발생하거나, 테넌트 ID로 샤딩했다가 초대형 고객 한 명이 특정 샤드의 디스크를 가득 채우는 불균형이 생기면 어떻게 해야 하는가?

유일한 해결책은 클러스터 전체의 데이터를 완전히 새로운 키나 새로운 규칙으로 다시 분배하는 리샤딩(Resharding)뿐이다. 리샤딩은 단순히 설정을 바꾸는 작업이 아니다. 원본 테이블에서 대상 샤드로 수십 테라바이트의 데이터를 실시간 스트리밍하고, 복제 지연을 따라잡은 뒤 트래픽을 넘기고(Cut-over), 만약의 사태에 대비해 역방향 복제까지 구성해야 하는 초고난도 인프라 수술이다. Multigres 문서조차 리샤딩을 위한 복잡한 워크플로와 장애 롤백 절차를 방대하게 설명하고 있다. 한 번의 잘못된 선택이 수개월간의 개발팀 야근과 장애 위험으로 이어진다.

운영에서 늘어나는 일 - 시점 복원·DDL 전파·관측성

데이터베이스 노드가 하나에서 열 개로 늘어나면 운영 관리 업무는 정확히 열 배가 늘어나는 것이 아니라 복잡도의 제곱에 가깝게 폭증한다. 단일 노드 운영 체계에서는 상상조차 하지 못했던 새로운 관리 항목들이 쏟아져 나온다.

운영 관리 항목 단일 인스턴스 (또는 단일 복제 세트) 분산 샤딩 클러스터 (수평 확장) 복잡도 증가 원인과 운영적 부담
백업 및 시점 복원 (PITR) 단일 WAL 아카이브 스트림 기반으로 특정 시점 복원 완료 각 샤드의 독립된 WAL 타임스탬프 불일치로 글로벌 일관성 보장 난해 모든 샤드의 스냅샷과 WAL을 완벽하게 동기화된 글로벌 타임스탬프로 맞춰야 함
스키마 변경 (DDL 마이그레이션) 단일 트랜잭션 안에서 DDL 실행, 실패 시 완벽한 롤백 수십 대의 샤드에 DDL을 순차 또는 병렬 전파, 버전 불일치 과도기 발생 일부 샤드만 DDL이 적용된 과도기 상태에서 구버전/신버전 호환 코드가 필요함
연결 관리 (Connection Pool) pgBouncer 1~2대로 단일 인스턴스 연결 수 수천 개 방어 게이트웨이 프록시 + 노드별 Multipooler 다계층 연결 풀 운영 연결 풀 계층 자체의 메모리 부하와 라우팅 오버헤드가 급증함
장애 전환과 정족수 합의 Patroni 등을 통한 단일 마스터 리더 선출 및 레플리카 승격 샤드마다 개별 프라이머리-레플리카 존재, 다중 오케스트레이터 감시 네트워크 파티션 발생 시 샤드별 스플릿 브레인(Split-brain) 방지 정족수 관리 필수
관측성 및 슬로우 쿼리 추적 단일 머신의 pg_stat_statements와 리소스 메트릭으로 병목 규명 분산 추적(Distributed Tracing) 및 수십 개 노드의 통합 메트릭 수집 쿼리 지연의 원인이 특정 샤드의 잠금인지, 게이트웨이 병목인지 추적 난이도 폭발

특히 가장 고통스러운 지점은 재해 복구(Disaster Recovery)다. 단일 PostgreSQL에서는 "어제 오후 2시 15분 00초 상태로 복원해 달라"는 요구가 손쉽게 해결된다. 단일 WAL 스트림에 타임스탬프가 순차적으로 기록되어 있기 때문이다. 그러나 열 대의 샤드로 나뉜 상태에서는 샤드 간의 물리적 클록 차이(Clock Skew)와 네트워크 지연 때문에 완벽히 동일한 찰나의 순간으로 클러스터 전체를 되돌리는 일이 극도로 어렵다. 분산 트랜잭션이 진행 중이던 시점으로 복원되면 데이터 불일치가 영구적으로 고착된다.

수평 확장 전에 반드시 거쳐야 할 다섯 단계

수평 확장이 가져오는 이 방대한 복잡도와 위험성을 이해했다면, 현명한 엔지니어링 조직이 취해야 할 태도는 자명하다. "샤딩은 기술적 훈장이 아니라 최후의 보루다." 가능한 한 모든 단일 노드 최적화 기법을 끝까지 밀어붙여 샤딩의 시점을 늦추거나 회피해야 한다.

데이터베이스를 여러 대로 쪼개기 전에 반드시 아래의 5단계를 순서대로 거쳤는지 냉정하게 자문해야 한다.

단계 핵심 점검 및 최적화 작업 기대 효과 건너뛰었을 때 발생하는 위험
1단계: 쿼리 및 인덱스 정비 pg_stat_statements 분석, 누락 인덱스 추가, 불필요 인덱스 삭제, N+1 쿼리 척결 불필요한 디스크 I/O 제거, CPU 사용률 감소 비효율적인 풀 스캔 쿼리를 여러 샤드 클러스터 전체에 뿌리며 증폭시킴
2단계: 읽기 복제본 (Read Replica) 조회용 트래픽, 관리자 대시보드, 배치 집계 쿼리를 읽기 전용 복제본으로 분리 프라이머리 노드의 리소스를 순수 쓰기 작업 전용으로 온전히 확보 단순 조회 부하 때문에 쓰기가 밀리는 착시를 겪으며 섣부른 샤딩을 시도함
3단계: 인스턴스 내 선언적 파티셔닝 PostgreSQL 내장 파티셔닝(Range/List)을 적용하여 대용량 테이블을 물리 파일 분할 파티션 프루닝으로 스캔 범위 축소, VACUUM 부하 격리, 초고속 DROP/DETACH 분산 시스템의 네트워크 복잡도 없이 얻을 수 있는 엔진 내 파티셔닝 이점을 놓침
4단계: 콜드 데이터 아카이빙 1~2년 이상 지난 과거 이력 데이터를 별도 오브젝트 스토리지(S3)나 분석 DB로 분리 활성 워킹 셋(Working Set)을 메모리(RAM) 안에 상주시켜 캐시 적중률 극대화 이미 조회되지도 않는 수년 전 데이터를 안고 샤딩하느라 막대한 인프라 비용 지출
5단계: 하드웨어 수직 증설 (Scale-up) 최신 세대 CPU, 수백 GB~테라바이트급 RAM, 수만 IOPS 고성능 로컬 NVMe 장착 단일 노드의 완벽한 관계형 무결성과 제약을 유지하며 한계 용량을 수배 연장 코드 한 줄 안 바꾸고 돈으로 해결할 수 있는 가장 저렴하고 안전한 기회를 버림

특히 3단계인 PostgreSQL 선언적 파티셔닝(Declarative Partitioning)은 샤딩의 수많은 장점을 네트워크 비용 없이 단일 노드 안에서 제공한다. 아래 예시는 날짜 범위를 기준으로 테이블을 파티셔닝하는 표준적인 DDL이다.

-- 단일 인스턴스 내에서 선언적 파티셔닝(Range Partitioning) 구성 예시
CREATE TABLE measurement (
    city_id         int not null,
    logdate         date not null,
    peaktemp        int,
    unitsales       int
) PARTITION BY RANGE (logdate);

-- 각 월별 파티션 테이블 생성 (물리적으로 분리된 저장 공간을 가짐)
CREATE TABLE measurement_y2026m08 PARTITION OF measurement
    FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE TABLE measurement_y2026m09 PARTITION OF measurement
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

-- 파티션 키를 포함한 인덱스 생성
CREATE INDEX ON measurement (logdate);

-- 쿼리 시 enable_partition_pruning 설정에 의해 필요한 월 파티션만 스캔됨

이 선언적 파티셔닝을 사용하면 수억 건의 데이터가 쌓이더라도 오래된 달의 파티션을 ALTER TABLE measurement DETACH PARTITION ... 명령 하나로 단 1초 만에 분리할 수 있으며, VACUUM도 해당 파티션 단위로만 수행된다. 이 단계를 거치지 않고 샤딩으로 직행하는 것은 계단을 밟지 않고 창밖으로 뛰어내리는 것과 같다.

정리 - 네 문장

이 긴 논의를 현업 엔지니어가 기억해야 할 네 개의 문장으로 요약한다.

  • PostgreSQL을 여러 대로 나눈다는 것은 성능의 마법이 아니라, 관계형 무결성을 네트워크 비용 및 운영 복잡도와 맞바꾸는 값비싼 거래다.
  • 샤드를 넘나드는 순간 ACID 트랜잭션, 크로스 조인, 유니크 제약, 자동 증가 시퀀스는 깨져나가며 그에 따른 정합성 유지 책임은 애플리케이션 코드로 전가된다.
  • 샤딩 키는 데이터의 물리적 위치를 결정하는 되돌리기 어려운 결정이며, 선택을 그르쳤을 때 발생하는 핫스팟과 리샤딩은 시스템 전체를 뒤흔드는 재앙이 된다.
  • 쿼리 튜닝, 읽기 복제본, 단일 노드 선언적 파티셔닝, 데이터 아카이빙, 수직 증설의 끝자락에 도달하기 전에는 결코 데이터베이스 분할을 시작하지 마라.

확인하지 못한 것

이 글을 작성하면서 확인하지 못했거나 문서에 드러나지 않아 결론을 유보한 항목들은 다음과 같다.

  • Multigres의 향후 분산 조인 세부 구현 알고리즘 — 공식 문서는 분산 조인에 대해 샤드별 푸시다운 및 스캐터 조인을 지원할 계획이라고 기술하고 있으나, 대규모 크로스 샤드 조인 발생 시 게이트웨이 노드의 메모리 상한 제어 기법이나 디스크 스필(Disk Spill) 처리 방식에 대한 구체적인 코드는 아직 공개되지 않았다.
  • PostgreSQL 2PC의 구체적 지연 시간 벤치마크 — PostgreSQL 공식 매뉴얼은 PREPARE TRANSACTION과 COMMIT PREPARED의 동작 메커니즘과 VACUUM 방해, XID 래핑 위험을 상세히 경고하지만, 네트워크 지연에 따른 처리량 감소 수치를 정량적으로 제시하지는 않는다. 이는 사용자 환경의 네트워크 인프라와 참여 노드 수에 따라 천차만별이기 때문이다.
  • 알파 버전 이후의 서드파티 확장(Extension) 호환성 — Multigres는 PostgreSQL 순정 테스트 슈트를 통해 높은 호환성을 추구한다고 밝히고 있으나, PostGIS나 pgvector 등 복합 데이터 타입 및 특수 인덱스를 사용하는 대규모 확장이 분산 샤딩 계층 위에서 어떤 제약을 겪는지는 현재 공개 문서만으로 검증할 수 없다.
