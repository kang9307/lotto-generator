AI生成物の検査体制を作る - 文法チェックが見逃すもの

構文・実行時・意味という3層の設計、誤検知の扱い、そして一括置換の落とし穴

2026年7月27日 開発・インフラ

序論: 「チェック合格」は「正常」ではない

AIに文書を書かせ、設定ファイルを作らせ、翻訳を任せるのが日常になった。ここで本当のボトルネックになるのは生成ではなく検査である。1日に1件を手で作っていた頃は全部読んでから出せたが、1日に数十件が押し寄せると全件を目で見るのは物理的に不可能だ。そこで検査ツールを付ける。node --checkが通り、JSONが解析でき、タグの開閉数が合えば緑のランプが点く。

問題は、その緑のランプが点いた生成物が本番で壊れることだ。原因はたいてい検査ツールの不具合ではない。検査ツールがそもそも見ていない領域で欠陥が起きただけである。チェックの合格は「異常がない」という意味ではなく「そのチェックが見ている範囲の中では異常がない」という意味なのに、私たちはこの2つの文をつい同じ意味で読んでしまう。

これは道具の品質の問題ではなく原理的な限界である。ライスの定理は、プログラムの自明でない意味的性質はすべて決定不能だと述べる。「このプログラムはすべての入力で停止するか」という振る舞いについての問いは、「if-else文を含むか」という形についての問いとは根本的に違う。したがってコードだけを見て正しさを一般的に判定する道具は作れない。実務のツールはこの壁を迂回する。健全(sound)な解析器は過大近似して誤検知を受け入れる代わりに見逃しをなくし、完全(complete)な解析器は過小近似して見逃しを受け入れる代わりに誤検知をなくす。ESLintやSonarQubeのようなヒューリスティックな道具はどちらの保証も手放して実用性を取る。つまり私たちが毎日使う検査ツールは、設計上必ず何かを見逃すように作られている。

だとすれば実務者がやるべきことは「完璧な検査ツール探し」ではなく、「何が見えないのかを知り、見えない領域を別の層で覆う工程を組むこと」である。この記事は生成物全般 — 文書・翻訳・設定ファイル・データ — を対象に、その工程をどう設計するかを扱う。モデル性能を評価する問題やコードレビューを自動化する問題とは別の軸だ。ここで扱うのはすでに作られた成果物を出す前にふるいにかける工程である。

1. 検査には層がある - 構文・実行時・意味

検査を一つの塊として見ていると設計ができない。3層に割って初めて、それぞれの層が何を担うのかを言葉にできる。

  • 第1層 構文(syntax) — 問いは「解析できるか」。文字列が規則に合った構造かどうかだけを見る。最も安く、最も速く、最も浅い。
  • 第2層 実行時(runtime) — 問いは「実際に値になり動くか」。解析結果を評価するか実行するか描画して、生きている状態を観察する。
  • 第3層 意味(semantic) — 問いは「内容が正しいか」。値が事実と一致するか、文書として筋が通るか、翻訳が原文と同じことを言っているかを見る。

3層の性質を表にすると次のようになる。

層中心の問い代表的な手段よく捕まえるもの原理的に捕まえられないもの費用
構文解析できるかnode --check、JSONパーサ、XMLスキーマ、リンタ閉じていないタグ、壊れたJSON、綴り違いのキーワード実行してはじめて現れる振る舞い、値の妥当性非常に低い(秒単位)
実行時値になり動くか実際の解析・評価、ヘッドレス描画、単体試験無限再帰、例外、誤った親の下の要素、壊れた参照実行経路に入らない欠陥、事実関係中程度(分単位)
意味内容が正しいか人による確認、出典の突き合わせ、LLM判定、代理指標事実誤り、情報の欠落・追加、不自然な表現、文脈の逸脱抜き取りの外側すべて、判定者のバイアスに弱い高い(人の時間)

ここで最も重要な性質は、3層が並列ではなく直列だという点だ。構文チェックを百個足しても実行時の欠陥は1件も減らない。層が上がるほど費用は上がり自動化率は下がり、下の層は上の層を決して代替しない。検査体制が崩れる典型的な理由は、構文層だけを密に作っておいて「検査があるから大丈夫」と信じることである。

2. 構文層が絶対に捕まえられない4つの事故

抽象的に言っても伝わらないので、実際によく起きる事故の型を4つ見る。4つとも構文チェックを満点で通過する。

2.1 文法は完璧なのに無限再帰で死ぬ場合

次の関数はパーサから見て非の打ちどころがない。括弧も合い、予約語も正しく、セミコロンもある。

function resolveRoot(node) {
  // 意図: 最上位のノードまで遡る
  return resolveRoot(node.parent || node);
}

node.parentがnullになった瞬間、node自身が再び引数として入り、終了条件がないのでスタックが溢れる。構文チェックでは絶対に捕まえられない。実行してはじめて現れる。これが実行時層を必要とする最も単純な理由だ。

2.2 タグの開閉は合っているのに要素が誤った親の下に入った場合

次の断片は開始タグと終了タグが正確に対になっている。タグを数える検査ツールはそのまま通す。

<table>
  <li>1番目の項目</li>
  <li>2番目の項目</li>
</table>

しかしliはulかolの子でなければならない。ブラウザのHTMLパーサは表の中に入ったこれらの要素を表の外へ引きずり出す(foster parenting)。結果は静かに崩れたレイアウトだ。チェックは緑なのに画面は壊れている。開閉の対だけを数える検査と親子関係の規則を知っている検査はまったく別の代物である。

2.3 数値の形式は合っているのに値が事実と違う場合

{"unitPrice": 1200}はJSONスキーマから見れば完璧な整数だ。実際の単価が12,000であっても、通貨が違っても、そもそも存在しない商品でもチェックは通る。形式検証器は値の妥当性について何も語らない。AIが作った設定ファイルで特に危ないのがここだ。構造は学習したパターン通り完璧に出てくるのに、その中の数値には根拠がないことがある。

2.4 翻訳が文法的に完璧なのに原文にない内容が生まれた場合

翻訳品質を測る事実上の標準であるMQM(Multidimensional Quality Metrics)の誤り分類を見ると、正確性(Accuracy)の下にAddition(原文にない内容が訳文に入る)、Omission(原文にある内容が訳文から欠ける)、Mistranslation(誤訳。その下位項目に機械翻訳の幻覚が別立てで入っている)がそれぞれ独立した誤り項目として定義されている。つまり翻訳の失敗の大きな軸は文法ではなく情報量の不一致だ。実際、過剰訳・過少訳を扱った研究は、現行のニューラル翻訳が依然として語を誤って追加・欠落させており、欠落のほうが追加より頻繁に起きると報告している。

この文を文法チェッカに入れても何も問題は出ない。原文と突き合わせて、あるいは原文と訳文の数値集合を比べてはじめて現れる。

事故の型構文層実行時層意味層最も安い検出方法
無限再帰・無限ループ見逃す捕まえる不要タイムアウトを付けた実行
誤った親の下に入った要素見逃す捕まえる不要DOM解析後の親規則チェック
形式は正しく値が違う見逃すほぼ見逃す捕まえる範囲不変条件と出典の突き合わせ
翻訳内容の追加・欠落見逃す見逃す捕まえる数値・URL・固有名詞の集合比較

ある言語版だけ表が丸ごと欠落見逃すほぼ見逃す捕まえる言語間の構造個数の不変条件

3. 実行時層の設計 - 実行してはじめて現れるもの

実行時層は「解析できる」と「値になる」を区別する層だ。実務で効果が大きい手法を5つ挙げる。

  • 再直列化の往復(round-trip) — 解析したあと再び文字列に戻し、元と構造を比べる。パーサが黙って直してくれた部分が差分として現れる。寛容なパーサほどこの手法の価値が大きい。
  • 構造規則のチェック — 親子関係、必須フィールド、相互排他フィールドといった形式ではなく文法を超えた規則を調べる。2.2の事故はここで捕まる。
  • 個数の不変条件(invariant) — 「同じ文書の4言語版はh2の数・表の数・箇条書き項目の数が一致するはず」といった規則。事実確認をしなくても丸ごとの欠落を捕まえてくれる。
  • 隔離実行 — タイムアウトとメモリ上限を付けて実際に動かす。無限再帰はここでしか捕まらない。必ず別プロセスで動かし、本体が巻き添えで死なないようにする。
  • 描画後のチェック — ヘッドレスブラウザで描いたあとDOMを読み直す。ソースでは正しく見えたのに描画結果が違う場合を捕まえる最後の網だ。

3層をそれぞれ1行のコマンドに置き換えると違いがはっきりする。

# 第1層 構文 - 解析できるか
node --check build/report.js

# 第2層 実行時 - 値になるか(タイムアウトを付けて実際に評価する)
timeout 10 node -e "JSON.parse(require('fs').readFileSync('data/config.json','utf8'))"

# 第2層 実行時 - 不変条件も同時に確認する
node -e "const d=require('./data/config.json');
         if (!(d.retries >= 0 && d.retries <= 10)) throw new Error('retriesが範囲外: '+d.retries);
         if (!d.endpoint.startsWith('https://')) throw new Error('endpointが非セキュア: '+d.endpoint);"

2.2の親規則チェックはこう書く。タグを数える代わりにパーサが認めた木を巡回する。

const { JSDOM } = require('jsdom');
const doc = new JSDOM(html).window.document;

// liはulまたはolの直接の子でなければならない
for (const li of doc.querySelectorAll('li')) {
  const parent = li.parentElement.tagName;
  if (parent !== 'UL' && parent !== 'OL') {
    throw new Error(`liが${parent}の中にある: ${li.textContent.slice(0, 30)}`);
  }
}

// 表の各行は列数が揃っていなければならない
for (const table of doc.querySelectorAll('table')) {
  const widths = [...table.querySelectorAll('tr')].map(tr => tr.children.length);
  if (new Set(widths).size > 1) throw new Error('列数の不一致: ' + widths.join(','));
}

重要なのはこれらの検査がすべて機械的判定だという点だ。人の判断が入らないので全件自動化ができ、誤検知もほとんど出ない。検査の予算はこういう項目にまず使うべきである。

4. 意味層 - 人・出典・LLM判定の分業

意味層には判定者が3つあり、3つとも欠点を持つ。どれか1つに寄せれば必ず破られる。

4.1 出典の突き合わせ

同じ事実を独立した2つの出典で確認する方法だ。意味の検査のうち最も自動化に近い。ただし落とし穴が1つある。2つの出典が同じ原典を引いているなら、それは独立ではない。報道記事2本が同じ発表資料を写したものなら、突き合わせではなく同じ情報を2回見ただけである。機関の原文や一次資料まで降りてはじめて本当の突き合わせになる。

4.2 LLM判定(LLM-as-judge)の限界

安くて速いがバイアスがある。「Judging the Judges」という研究は、LLM判定者15種類をMT-BenchとDevBenchという2つのベンチマーク、22の課題、約40の生成モデルにわたって調べ、15万件を超える評価を行った。結論は位置バイアス(position bias)が偶然ではなく体系的であり、判定者と課題によって大きく変わるというものだ。プロンプトの長さの影響は弱かった一方、候補どうしの品質差が大きいほどバイアスが強く出た。別の研究は、モデルが自分の出力を過大評価する自己選好バイアス(self-preference bias)を報告している。このほか長い回答を好む冗長性バイアスも知られている。

だからといって使えない道具ではない。限界を知って設計を変えればよい。

  • 順序を入れ替えて2回尋ねる。2回の答えが一致したものだけを採用する。位置バイアスはこれ1つでかなり除ける。
  • 生成モデルと判定モデルを分ける。自己選好バイアスに対する最も単純な防御だ。
  • 点数ではなくチェックリストを使う。「10点満点で何点」より「原文にない文があるか: はい/いいえ」のほうが再現性がはるかに高い。
  • LLM判定は並べ替え用途に限る。合否を決めるゲートではなく、人が見る順序を決める優先順位付けとして使う。上位20件だけ人が見れば済む状況を作るのが目的だ。
  • 判定結果を抜き取りで再確認する。判定者も検査対象である。判定結果から無作為に抜き取って人が見直し、一致率を記録する。

4.3 人による確認

最も正確だが最も高く、何より抜き取りが小さいと見えない。この限界は勘ではなく計算で言える(第9章)。人の時間は有限な資源なので、どこに使うかを設計することが検査体制の半分を占める。

5. 誤検知が検査ツールを殺す - 警報疲れの構造

静的解析の研究文献は、ツールが不具合として報告した警告のうちおよそ35~91%が実際には対処不要(unactionable)だったと整理している。この幅がこれほど広いこと自体が「ツール・プロジェクト・設定によって千差万別」という意味であり、裏を返せば設定次第で結果が変わるということでもある。

誤検知の本当の費用は確認にかかる時間ではない。警報疲れ(alert fatigue) — 警告が頻繁だと人は鈍感になり、結局は本物の警告まで一緒に無視される。狼を10回叫んだ検査ツールは11回目の本物の狼を止められない。実際、開発者が時間の圧力や警告疲れのために警告を無視・抑制することが複数の研究で観察されてきたし、抑制(suppression)の件数がプロジェクトの寿命とともに増え続ける傾向も観察されている。

実際に経験した事例。多言語サイトの検証ツールが「すべての言語版に特定の共有SDKがなければならない」という規則を掛けていた。ところがそのSDKは、そもそも韓国語ページにだけ入れるのが方針だった。そのため実行のたびに残り3言語で同じ警告が出た。いつも出る警告なので誰も読まず、同じ行に一緒に出ていた本物の誤り(CSSパスの誤り)が2か月埋もれた。規則を「韓国語版にのみ要求」に狭めたところ、その日のうちに本物の誤りが目に入った。検査ツールが常に黄色ランプなら、それは検査ツールではなく背景の雑音である。

ここでチームがよく取る選択を4つ比べると、何が最悪かがはっきりする。

対応短期の効果検出力への影響評価
規則を切る警告が消えるその欠陥の種類を永久に捕まえられない最悪。戻すきっかけがない
閾値を緩める警告が減る境界線上の欠陥が静かに通過悪い。どこまで見逃すのか誰も知らない
警告をそのまま無視するなし警報疲れが深まり本物まで埋もれる悪い。検査ツール自体が無力化
適用範囲を正確に狭めるその条件の警告だけ消える検出力を保ち、信号対雑音比が改善正解。ただし条件の把握に手間がかかる

原則は一文で言える。誤検知の対処法は規則を切ることではなく、規則が真である条件を正確に記述することだ。「A検査が誤検知を出す」という言葉はたいてい「A検査の前提が実際より広く取られている」という意味である。

6. 規則を狭めたら回帰試験を掛けよ

規則を狭めると逆方向の危険が生まれる。狭めすぎて本物まで捕まえられなくなること。検査ツールが静かになった理由が「欠陥がないから」なのか「検査ツールが死んだから」なのかを区別する方法がなければ、狭めることは規則を切ることと実質的に同じになる。

ソフトウェアテストの分野にはすでに答えがある。ミューテーションテスト(mutation testing) — ソースに人工的な欠陥(mutant)を仕込み、テストがそれを捕まえる(kill)かどうかを確認してテスト自体の欠陥検出力を測る手法だ。捕まえた割合がミューテーションスコアであり、この指標はコードカバレッジより実際の欠陥検出力との関係が深いと報告されている。カバレッジは「コードが実行された」としか言わないが、ミューテーションスコアは「壊したときに失敗した」と言えるからだ。

検査パイプラインにもそのまま移せる。名前を付けるなら回帰試験(欠陥の仕込み)である。

#!/usr/bin/env bash
# 検査ツールが生きているか確認する - わざと欠陥を仕込んで捕まるか見る
set -euo pipefail

WORK=$(mktemp -d)                       # 必ず複製で作業する
cp posts/sample.html "$WORK/sample.html"

# 欠陥1: 終了タグを1つ削る
node -e "const fs=require('fs'); const p=process.argv[1];
         fs.writeFileSync(p, fs.readFileSync(p,'utf8').replace('</ul>',''));" "$WORK/sample.html"

if node validate.js "$WORK/sample.html"; then
  echo "FAIL: 検査ツールが仕込んだ欠陥を捕まえられなかった"
  exit 1
else
  echo "OK: 正常に検出"
fi

rm -rf "$WORK"                          # 原本には触れていない

仕込む欠陥の一覧はチームごとに違うが、出発点として使えるものは次のとおりだ。

  • 終了タグを1つ削る — 構文層が捕まえるべき
  • 属性値の閉じ引用符を削る — 構文層
  • JSON配列の最後の要素の後ろにカンマを足す — 構文層
  • 箇条書き項目を表の中へ移す — 実行時層(構造規則)
  • 再帰関数の終了条件を削除する — 実行時層(隔離実行)
  • 必須のmetaタグを削除する — 構文層または規則チェック
  • リンクのドメインに1文字の綴り違いを入れる — 実行時層(HTTP確認)
  • 数値の桁を1つ変える — 意味層(範囲不変条件で一部だけ捕まる)
  • ある言語版から表を1つ丸ごと削除する — 実行時層(個数の不変条件)
  • 訳文に原文にない文を1行足す — 意味層

この一覧を回す時点は2つある。定期(月1回)と規則に手を入れるたびだ。捕まらない項目が出たら、それがそのまま次に破られる穴である。捕まらない項目を見つけることがこの試験の成功だという点をチームで先に合意しておくのがよい。そうしないと誰もこの試験を回したがらない。

安全上の注意。欠陥は必ず複製に仕込む。原本に仕込んで戻す方式は、戻しに失敗した瞬間にそれ自体が事故になる。一時ディレクトリに複製して回し、終わったら丸ごと消すほうが安全だ。バージョン管理下にあるからと油断しないこと — 戻しの失敗とコミットが重なれば欠陥が履歴に残る。

7. ゴールデンファイルとスナップショット - 「変わった」を捕まえる層

ここまでの検査は「規則違反か」を問うてきた。ここにもう1つ足せる。「前と変わったか」である。基準となる生成物を保存しておき、以後の生成物をそれと比べる方法で、呼び名がいくつもある。

  • ゴールデンマスター(golden master) — 音盤のマスタリング由来の言葉。基準となる原本という意味だ。
  • スナップショットテスト(snapshot test) — Jestが広めた名前。初回実行で作られたファイルが承認版になる。
  • 特性化テスト(characterization test) — マイケル・フェザーズが『レガシーコード改善ガイド』で使った言葉。目的は「望ましい振る舞い」ではなく「今の実際の振る舞い」を記録することだと定義されている。
  • 承認テスト(approval test) — リュウェリン・ファルコが提唱した名前。ほぼ同じだが使う前に人が承認する点が違う。

4つの名前が指す手法は実質的に同じで、目標も1つ。システムが違う振る舞いをしたら失敗する試験を持つこと。AI生成物の検査では特に「同じ入力に対して前回と構造が変わった」を捕まえるのに役立つ。

ただしこの手法には広く知られた弱点がある。壊れやすいことだ。意図した変更でも失敗するので基準ファイルを絶えず更新することになり、更新が習慣になると失敗を読まずに更新から入る状態になる。その瞬間この試験は無意味になる。緩和策は次のとおりだ。

  • スナップショットをコードとして扱う。コードレビューの対象に含め、更新コミットをそのまま通さない。文献が最も重要な実践として挙げている点だ。
  • スナップショットの対象を絞る。HTML全体を丸ごと保存すると空白1つで壊れる。代わりに正規化した構造の要約を保存する。
  • 自動更新を既定から外す。承認テストの方式に倣い、更新に明示的な意思表示を要求する。
  • 各スナップショットに説明を付ける。「このファイルは何を保証するのか」を1行書いておけば、壊れたときに更新すべきか直すべきかを判断できる。

構造要約のスナップショットはこういう形になる。文を1つ直したくらいでは壊れないが、表が消えたり節が丸ごと抜けたりすれば必ず壊れる。

// 本文全体ではなく構造だけを取り出して保存する
function structureDigest(doc) {
  return {
    h2: [...doc.querySelectorAll('h2')].map(el => el.textContent.trim()),
    tables: doc.querySelectorAll('table').length,
    listItems: doc.querySelectorAll('li').length,
    codeBlocks: doc.querySelectorAll('pre code').length,
    links: [...doc.querySelectorAll('a[href]')].map(a => a.getAttribute('href')).sort()
  };
}

8. 一括処理の危険 - 範囲指定の置換が生む汚染

検査を自動化すると次の欲が必ず出る。修正も自動化したくなる。ここで最大の事故が起きる。検査ツールは下手に書けば騒がしくなるだけだが、一括修正ツールは下手に書くと数百のファイルを静かに汚染する。

8.1 最もよくある失敗 - 文字オフセットで範囲を取ること

// 悪い例: 先頭2000文字の中だけを置換する
const head = html.slice(0, 2000).replace(/2025/g, '2026');
html = head + html.slice(2000);

2000文字という境界は文書の構造と何の関係もない。あるファイルではその中で本文が始まり、別のファイルでは外部スクリプトのURLが入っており、また別のファイルではヘッドが2000文字を超えて肝心の対象が範囲の外に出る。この方式で数百ファイルを処理すれば必ず例外が生まれ、その例外は静かに誤った値として残る。さらに悪いのは、結果が依然として文法的に完璧だという点だ。構文層も実行時層も通ってしまう。

8.2 2つ目の失敗 - 境界のない正規表現

語を置き換える処理で境界を落とすと別の語の一部に当たる。実際、多言語文書で特定の漢語を平易な語に置き換える辞書置換を回したことがあるが、境界がなかったために無関係な語の内部に当たり、異なる文字体系が1語に融合した文字列が数百件生まれた。HTMLは無傷で、解析もでき、描画もされる。人が読んではじめておかしいと分かる文章だった。以後この型は「1語の中に異なる文字体系が混ざっているか」を見る機械的な代理指標で常時検出するように変えた。意味の検査ができないなら、意味と相関の高い機械的指標を探す — 第10章の原則はここから出ている。

8.3 安全に一括処理する方法

// よい例: 対象をタグ・属性で特定し境界を明示する
html = html.replace(
  /(<meta property="article:published_time" content=")[^"]*(")/,
  '$12026-07-27$2'
);

// 回す前に必ず数える
const hits = [...html.matchAll(/<meta property="article:published_time"[^>]*>/g)];
if (hits.length !== 1) throw new Error(`想定1件、実際${hits.length}件 - 中断`);

一括作業の安全則を表にすると次のようになる。この表はそのままチェックリストとして使える。

安全則具体的な方法防げる事故
対象をノードで特定する文字オフセットではなくタグ・属性・段落を対象に取る境界外の汚染
正規表現に境界を入れる属性値なら引用符境界で、語なら語境界で囲う別の語の内部への的中
先に数える変更予定の件数を出力し、想定と違えば中断する範囲の見誤り
1件を目で見る最初の一致の前後40文字を出して確認してから全体を実行規則そのものの設計ミス
冪等にする2回回して変更0件でなければ規則が誤っている二重適用と累積破損
戻せるようにする作業前にコミットを分けるか複製を残す復旧不能
終わったら3層を回し直す特に意味層の無作為抜き取りをやり直す修正が生んだ新しい欠陥

9. 抜き取り検査の統計的限界 - 20件見て出なければ無いのか

「20件抜き取って問題がなかった」はよく安心の根拠に使われる。計算してみると思ったより弱い根拠だ。

欠陥率がpの母集団から無作為にn件抜き取ったとき、欠陥を1件以上見つける確率は 1 − (1 − p)nである。次の表はこの式をそのまま計算した値だ。

実際の欠陥率抜き取り5件抜き取り20件抜き取り50件抜き取り100件
10%(10件に1件)41.0%87.8%99.5%99.99%
5%(20件に1件)22.6%64.2%92.3%99.4%
1%(100件に1件)4.9%18.2%39.5%63.4%
0.5%(200件に1件)2.5%9.5%22.2%39.4%

表の読み方はこうだ。

  • 欠陥率10%なら20件見るだけで約88%の確率で当たる。頻繁な欠陥は小さな抜き取りで十分捕まる。
  • 欠陥率1%なら20件見ても18%だ。5回に4回はそのまま通る。まれな欠陥は抜き取り検査では事実上捕まらない。
  • 1%の欠陥率を95%の水準で確認するには約300件が必要になる。いわゆる3の法則(必要な件数はおおよそ3÷欠陥率)である。
  • 「先頭から5件だけ見る」という習慣は抜き取りではない。無作為でなければ上の計算は成り立たない。たいてい前のほうの生成物は丁寧に作られているので、結果を楽観側へ歪める。

ここから結論が2つに分かれる。

  • まれだが致命的な項目(公開URL、金額、法的文言、個人情報の露出、古い連絡先)は抜き取りに頼らず全件自動検査を作る。幸いこうした項目は判定基準が機械的なので自動化も比較的やさしい。
  • 頻繁だが致命的でない項目(文体、表現の自然さ、見出しの語感)は無作為抜き取りで十分だ。ここに全件検査を付けても費用ばかりかかって得るものが少ない。

製造業の品質管理はこの均衡をすでに表にしている。ISO 2859-1(米国規格ではANSI/ASQ Z1.4)のAQL表は、ロットの大きさごとに抜き取る件数と合格判定個数を定めている。ソフトウェアの生成物にそのまま使うのは難しいが、「抜き取り件数が決まった瞬間に検出力も決まる」という考え方はそのまま持ってこられる。抜き取り件数を先に決めて検出力を後から問うのは順序が逆だ。

10. 何を自動化し何を目で見るか

自動化の判断は2つの軸で分かれる。判定基準が機械的か、そして繰り返されるかである。

繰り返しが少ない繰り返しが多い
判定基準が機械的使い捨てスクリプトで処理して捨てる最優先の自動化対象。ここから予算を使う
判定基準が主観的人が直接見る。自動化の試み自体が無駄代理指標＋チェックリスト＋無作為抜き取り

費用計算でよく抜け落ちる項目がある。

  • 製作費より維持費のほうが大きい。生成物の形式が変われば規則はすぐ古びる。追いつけなかった規則は誤検知の工場になる。
  • 誤検知1件の費用を掛け算して入れよ。1日30件の誤検知×確認2分＝1日1時間だ。ここに警報疲れで漏れていく本物の欠陥の費用が乗る。
  • 見逃し1件の費用も入れよ。誤った公開URL1つ、間違った金額1つの費用が誤検知100件より大きいことがある。この2つの費用の大小比較が閾値設定の根拠になる。
  • 自動化が難しいなら対象を変えよ。「翻訳が正確か」は自動化しにくいが、「原文と訳文の数値一覧が一致するか」はやさしい。

最後の項目が実務では最も値打ちがある。意味の検査が直接できないなら、意味と相関の高い機械的な代理指標を探す。使える代理指標は次のとおりだ。

  • 数値・URL・固有名詞の集合比較 — 原文と訳文から抽出して集合として比べる。情報の追加・欠落を安く捕まえる。
  • 構造の個数一致 — 言語版ごとの節の数、表の数、箇条書き項目の数が揃っているかを見る。丸ごとの欠落の検出に強い。
  • 分量比の外れ値 — 言語ごとの長さの比が普段の範囲を外れたら印を付ける。言語ごとに密度が違うので絶対的な長さではなく普段の比と比べる必要がある。
  • リンクのステータス全件確認 — リンク切れは判定が完全に機械的なので、自動化の効率が最も高い部類に入る。
  • 文字体系の混入チェック — 1語の中に異なる文字体系が混ざっていないかを見る。置換事故と翻訳事故を同時に捕まえる。
  • 禁止語・廃止値のチェック — 名称が変わった制度、廃止された連絡先のような「かつて正しかった値」を一覧で管理する。事実確認のうち唯一安く自動化できる部分だ。

11. 検査工程を組み立てる順序

最初から3層すべてを作ろうとするとたいてい失敗する。順序がある。

  1. 事故の一覧から作る。直近3か月に実際に出てしまった欠陥を書き出す。検査ツールは想像した欠陥ではなく実際に起きた欠陥から塞ぐべきだ。この一覧がなければ規則の優先順位を決める根拠がない。
  2. 各事故を3層に割り当てる。構文層で捕まるもの、実行時層が要るもの、意味層でしか捕まらないものに分ける。第2章の表をそのまま使えばよい。
  3. 構文層と実行時層から全件自動化する。安くて速く誤検知も少ない。ここで捕まる項目は人の手にそもそも渡らないようにする。
  4. 意味層は代理指標＋無作為抜き取りで組む。致命的な項目だけ全件、残りは抜き取り。抜き取り件数を決めるときは第9章の計算を根拠に使う。
  5. 回帰試験を暦に入れる。月1回、そして規則を修正するたび。この段階が抜けると上の4段階は時間とともに静かに腐る。

運用段階で守る規則もいくつかある。

  • 結果は2値ではなく3値にする。合格 / 不合格 / 要確認。要確認を不合格として扱うと、人は規則を切りたくなる。
  • 新しい規則はまず警告として入れる。誤検知率が十分下がったのを確認してから遮断に昇格させる。最初から遮断で入れると最初の誤検知で規則が消される。
  • 抑制を使うときは理由も残す。理由のない抑制は時間が経つと誰も触れない地雷になる。抑制の件数が増え続けているなら、それ自体が規則に手を入れるべきだという合図だ。
  • どの層まで検査したかを生成物に記録する。事故が起きたとき「検査していなかった」と「検査したのに捕まえられなかった」では対応がまったく違い、後者だけが規則の改善につながる。
  • 検査ツール自体をバージョン管理する。規則がいつどう狭められたかの履歴が残っていてはじめて、後から見つかった見逃しの原因を追える。

結論: 検査ツールは合格印ではなく観測装置である

検査ツールを合格印として使えば必ず負ける。印は「大丈夫だ」と言うが、検査ツールにはそう言う能力がない。検査ツールが言えるのは「私が見ている範囲の中では異常がなかった」だけで、この文は見ている範囲が明示されているときだけ役に立つ。

だから検査ツールは観測装置として扱うべきだ。観測装置の仕様書には測定範囲と誤差が書いてある。私たちの検査体制にも同じものが要る。どの層が何を見るのか、各層が何を見られないのか、その死角を何で覆うのか、そして装置がまだ壊れていないことをどう確認するのか。最後の項目が回帰試験であり、たいていこれが最初に抜け落ちる。

まとめるとこうだ。構文層は安いので全部つける。実行時層は事故の型の相当数をここでしか捕まえられないので必ず作る。意味層は全件をあきらめる代わりに致命的項目の全件＋残りの無作為抜き取り＋機械的な代理指標に割る。誤検知が出たら規則を切らずに条件を狭める。狭めたあとは欠陥を仕込んで検出力が生きているか確認する。一括修正はオフセットではなくノードを対象に、先に数え、冪等に、戻せるようにする。

AIが作る生成物の量は増え続ける。その流れではボトルネックがいつも検査側に生まれ、それを解消しようと検査を浅くすれば緑ランプの信頼度だけが下がる。浅い検査100個より層の分かれた検査10個のほうがよい。2026年7月時点で、うまく回っているチームと事故が続くチームを分けるのは、モデルの選択ではなくこの工程の設計であることが多い。
