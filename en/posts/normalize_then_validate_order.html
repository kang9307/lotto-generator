Change the Value After Validating It and the Validation Is Void - Order of Normalization and Validation

If the checked value and the used value are not the same string, the check may as well never have run

2026-08-01 Dev & Infra

Introduction: the check passed, the value that arrived is different

You are reading logs and you spot something odd. A stored name has a line break inside it, or a string that should never have been openable is sitting in a file path slot. You open the code and the input check is right there. The regex is tight, the forbidden-character list is long, and there is no branch that skips the check. The value got in anyway.

The usual response at this point is to make the rule tighter. Add characters to the pattern, extend the list, bolt on an exception case. Then a few days later a similar value shows up again. If a defect survives every rewrite of the rule, the rule is not the problem.

This article is about exactly one situation: the string the checker judged and the string the program actually used are different strings. In that situation the checker has done nothing wrong. It answered accurately about the value it was handed. Its answer simply was not an answer about the final value.

So the thesis here is not to validate. Validation is already present. What matters is what you validated. And the thing that decides that what is not the rule. It is the order.

Test environment. Every output below was actually executed on Windows 10 Pro (10.0.19045). The runtime is Node.js v22.16.0 (win32) and some results were cross-checked with Python 3.13.3. Every script was saved to a file before running.

What this article does not do. There is no attack procedure and no exploitation walkthrough here. Every sample uses harmless characters and paths that stay inside the base directory. What is being shown is not how to break in but the structure in which a check becomes meaningless. That is why, including the path section, every example goes only as far as demonstrating that the value at check time differs from the value at use time.

What this article does not cover. The mechanics of one character becoming several code point sequences inside Unicode are covered in NFC and NFD. Here normalization is treated purely as a placement problem. General handling of web input is in Web Security Basics. Whether to use an allowlist or a denylist, and which layer validation belongs to, are not the subject here. This article stays on the single point of order.

1. Same checker, only the order changed

Start with the most common shape. The forbidden-character check runs first and the value that passed is decoded afterwards. Read that code and nothing looks wrong: the check is in front, the use is behind, the order seems right. To see what actually happens I printed the value at check time and the value at use time side by side.

node v22.16.0 / win32
--- 1-1. ORDER A: validate first, decode afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a%3Cb           PASS      a<b             NO
note%3Bnext     note%3Bnext     PASS      note;next       NO
x%26y           x%26y           PASS      x&y             NO
line%0Asecond   line%0Asecond   PASS      line\nsecond    NO
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-2. ORDER B: decode first, validate afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a<b             REJECT    (never used)    -
note%3Bnext     note;next       REJECT    (never used)    -
x%26y           x&y             REJECT    (never used)    -
line%0Asecond   line\nsecond    REJECT    (never used)    -
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-3. the gap, counted ---
order A  passed check but dirty at use : 4 of 6
order B  passed check but dirty at use : 0 of 6
the checker function is identical in both runs. only the order changed.

Comparing the second column against the fourth is the trick that runs through this entire article. Under order A, a%3Cb was a%3Cb at check time. That string contains not a single forbidden character. The checker honestly returned a pass. But the value at use time is a<b. The checker has never seen that string.

  • Four of six inputs took that route. They earned a pass and then a forbidden character surfaced in the final value
  • Only the last row behaves. The unencoded plain<bad> already carried a forbidden character at check time, so it was rejected. In other words this checker catches only the visible form
  • Under order B there are zero post-pass contaminations. The checker function does not differ by a single character between the two runs
  • The line-break row matters most. line%0Asecond turns one value into two lines wherever meaning is defined per line, such as a log or a header
  • This defect does not disappear by fixing the checker. However many rules you add, what the checker sees is still the encoded string

1.1 The checker cannot know it has been made meaningless

The ugly part of this structure is that nobody hits an error. No exception is raised, no warning lands in the log, and the checker reports that it did its job correctly. Integration tests pass too, because the values tests feed in are usually plain decoded strings for which both orders give the same result.

So this is the kind of defect that tests rarely catch and review rarely catches. What a reviewer sees is that a check exists and a use exists. To become suspicious of the order between them you first have to know that the line wedged in between changes the value.

2. Unicode normalization - put it after the check and the verdict flips

The second route is Unicode normalization, and it is far quieter than the decoding above. Decoding at least leaves a conspicuous % behind. Normalization takes a string that already looks perfectly normal and turns it into a different string. Here is what one pass does.

node v22.16.0 / win32
--- 2-1. one NFKC pass changes the string itself ---
before      len  after NFKC  len  codepoints after
--------------------------------------------------------------------------
report      6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
ｒｅｐｏｒｔ 6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
a／b        3    a/b         3    U+0061 U+002F U+0062
ﬁle         3    file        4    U+0066 U+0069 U+006C U+0065
①           1    1           1    U+0031
㎡          1    m2          2    U+006D U+0032
ｎｏ＜op    5    no<op       5    U+006E U+006F U+003C U+006F U+0070

The rows worth staring at are the ones where the length changes. ﬁle was three characters and became four; ㎡ went from one to two. Put a length limit ahead of normalization and a value that satisfied the limit gets stored in violation of it.

And the last two rows are the heart of this section. Values written with fullwidth characters came out of normalization as a halfwidth slash and a halfwidth angle bracket. Characters that did not exist at check time were created at use time. I confirmed how the verdict flips under both checker styles.

--- 2-2. allowlist verdict before vs after normalization ---
input       allow(before)  allow(after)  flipped?
--------------------------------------------------------
report      true           true          no
ｒｅｐｏｒｔ false          true          YES
a／b        false          false         no
ﬁle         false          true          YES
①           false          true          YES
㎡          false          true          YES
ｎｏ＜op    false          false         no

--- 2-3. denylist verdict before vs after normalization ---
input       deny hit(before)  deny hit(after)  flipped?
------------------------------------------------------------
report      false             false            no
ｒｅｐｏｒｔ false             false            no
a／b        false             true             YES
ﬁle         false             false            no
①           false             false            no
㎡          false             false            no
ｎｏ＜op    false             true             YES

The important thing is that the two tables fail in opposite directions.

  • With an allowlist, legitimate values get rejected. A fullwidth ｒｅｐｏｒｔ becomes a perfectly valid report after normalization, but checked before normalization it is refused. To the user that is a bug that says a perfectly good name is not accepted
  • With a denylist, values that should be caught pass. The forbidden character is absent before normalization and appears after it
  • In both cases the checker itself is accurate. What is wrong is not the checker but the value handed to it
  • In practice the first failure gets found first, because users complain. Nobody complains about the second one, so it lives longer
  • These two tables are two faces of one cause. Fix only one and the other remains

2.1 Idempotent means you may move it forward

So when should normalization run? At the very front, and there is a concrete reason you are allowed to say that: normalization gives the same result however many times you run it. That property is called idempotence. I ran it three times in a row.

--- 2-4. NFKC is idempotent, so doing it FIRST is safe ---
report      n1==n2 true   n2==n3 true
ｒｅｐｏｒｔ n1==n2 true   n2==n3 true
a／b        n1==n2 true   n2==n3 true
ﬁle         n1==n2 true   n2==n3 true
①           n1==n2 true   n2==n3 true
㎡          n1==n2 true   n2==n3 true
ｎｏ＜op    n1==n2 true   n2==n3 true
a normalizer you can run twice with no change can always be moved to the front.

--- 2-5. NFC vs NFKC are not the same job ---
input       NFC         NFKC        NFC==NFKC
--------------------------------------------------
ｒｅｐｏｒｔ ｒｅｐｏｒｔ report      false
ﬁle         ﬁle         file        false
㎡          ㎡          m2          false
á          á           á           true

The meaning of 2-4 is simple. Moving normalization to the front costs nothing. If normalization happens again somewhere downstream the value no longer changes, so it is safe. That is why the rule normalize first holds without risk.

2-5 shows one trap. NFC and NFKC do different jobs. The accented character in the last row came out the same under both, but all three rows above it differ. Folding fullwidth into halfwidth and expanding ligatures is NFKC work only. So saying we normalize does not tell you which normalization. If the underlying mechanics interest you, see NFC and NFD. The conclusion needed here is one line: pick a form, write it down, and make every layer use the same one.

3. Whitespace and case - the most common and least visible mismatch

The two sections above at least involve unusual characters, so suspicion comes easily. This one is different. trim and lowercasing are so ordinary that nobody registers them as operations that change the value. Taking a reserved-name list as the example, I ran both orders.

--------------------------------------------------------------------------------

[admin]         [admin]         true       [(rejected)]  -

[ADMIN ]        [ADMIN ]        false      [admin]       YES  <- mismatch

[billing\t]     [billing\t]     false      [billing]     YES  <- mismatch

--- 3-2. ORDER B: canonicalize first, then check ---
requested       value AT CHECK  reserved?  value STORED  stored value reserved?
--------------------------------------------------------------------------------
[alice]         [alice]         false      [alice]       no

Under order A the reserved list responded to exactly one spelling. Add surrounding whitespace or a single capital and the value slips past the list. But when it gets stored those values all collapse to the same form, so a name that is on the list ends up stored having passed the list. Under order B the same list and the same inputs caught every one of them.

3.1 When the uniqueness check and the storage key diverge

The same defect has a much quieter shape: duplicate checking. Here it shows up not as a security problem but as a data integrity problem.

--- 3-3. uniqueness checked on one value, stored as another ---
order A: unique-check on raw, store canonical
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? false  stored [alice@example.com]
  [ALICE@EXAMPLE.COM]     dup at check? false  stored [alice@example.com]
  distinct values checked : 3
  distinct values stored  : 1   <- three rows collapsed into one key
order B: canonicalize first, then unique-check
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? true   rejected
  [ALICE@EXAMPLE.COM]     dup at check? true   rejected

Order A answered not a duplicate all three times. The three strings at check time really are different, so that answer is correct. But converted into storage keys, the three become one value. Three separate requests end up contending over a single key. No exception is raised. It surfaces later as a report that two accounts share an address, or that the earlier one vanished.

3.2 Trim is not one rule, it is one list

Check what trim actually removes and it does not match intuition. Not everything that looks like whitespace is removed.

--- 3-4. what exactly trim removes, and what it does not ---
input codepoints          trim() result     length change
------------------------------------------------------------
U+0061 U+0020 U+0062      3 -> 3            untouched
U+0020 U+0061             2 -> 1            trimmed
U+0061 U+00A0             2 -> 1            trimmed
U+0061 U+200B             2 -> 2            untouched
U+0061 U+FEFF             2 -> 1            trimmed
U+0061 U+3000             2 -> 1            trimmed
U+00A0 and U+3000 are removed, U+200B and U+FEFF are not.
so trim is not one rule. it is one specific list, and it must run before the check.

--- 3-5. lowercase is locale sensitive ---
input U+0130            : İ
toLowerCase()           : U+0069 U+0307
toLocaleLowerCase(tr)   : U+0069
length after each       : 2 vs 1
two layers using different locales produce two different canonical values.
  • The non-breaking space and the ideographic space are removed. They are invisible, so you cannot tell by looking at the stored value
  • The zero width space is not removed. It looks like whitespace but is not on this function list. A value carrying it is treated as a different value
  • In other words trim does not mean remove whitespace, it means remove characters on one specific list. Not knowing that list means not knowing what will pass
  • 3-5 is subtler still. The lowercasing result depends on the locale. One character becomes two under one locale and one under another
  • Layers on different locales produce a different canonical form per layer for the same input. Section 7 returns to this
  • The conclusion is the same. These conversions are all operations that change the value, and an operation that changes the value belongs before the check

4. Path joining - the string is rewritten the moment you combine it

Paths are the area where this problem is best known. So let me be explicit about what will not be shown. Every example below is a legitimate path that stays inside the base directory. There is no escape case and no successful bypass. The single thing being demonstrated here is that joining is an operation that rewrites the string.

node v22.16.0 / win32
--- 4-1. the string the checker saw vs the string join produced ---
user segment          joined result                   identical tail?
------------------------------------------------------------------------
q1.csv                /srv/data/reports/q1.csv        true
sub//q1.csv           /srv/data/reports/sub/q1.csv    false
./q1.csv              /srv/data/reports/q1.csv        false
sub/./q1.csv          /srv/data/reports/sub/q1.csv    false
sub/inner/../q1.csv   /srv/data/reports/sub/q1.csv    false
sub/                  /srv/data/reports/sub/          true
a/b/../../q1.csv      /srv/data/reports/q1.csv        false
every row above stays inside the base directory. only the SPELLING changed.

--- 4-2. what join collapsed, step by step ---
q1.csv                unchanged
sub//q1.csv           duplicate separator collapsed
./q1.csv              current-dir segment dropped
sub/./q1.csv          current-dir segment dropped

Five of seven inputs produced a different result from plain concatenation. What changed is listed in 4-2: duplicate separators collapse, current-directory segments disappear, parent segments resolve, trailing separators drop. The official documentation states outright that the join function normalizes its result.

  • That normalization is not optional. It always happens once you use the join function
  • So if you check a user-supplied segment and then join it, the string you checked is not the string that reaches disk
  • It matters that every example stayed inside the base. The mismatch is not something that only appears with dangerous input
  • Since the value differs even for ordinary input, this mismatch is present all the time, in normal operation

4.1 A separator means different things at different layers

Join the same segment under two path flavours and the results diverge.

--- 4-3. same segment on the windows path flavour ---
user segment          posix.join                    win32.join
----------------------------------------------------------------------------
q1.csv                /srv/data/reports/q1.csv      C:\srv\reports\q1.csv
sub/q1.csv            /srv/data/reports/sub/q1.csv  C:\srv\reports\sub\q1.csv

so one segment has two different meanings depending on which layer joins it.

Look at the third row. One side left the backslash in the segment as an ordinary character while the other read it as a separator. The same string is parsed into different structure depending on the layer. If development runs on one flavour and production on another, a check that passed in development judges a different value in production.

4.2 A question about spelling and a question about a file

Now the core. I asked the same question, is this path inside the base, of two different values.

--- 4-4. the containment test, run on the two different values ---
user segment          test on RAW   test on RESOLVED  same answer?
----------------------------------------------------------------------
q1.csv                true          true              true
sub//q1.csv           true          true              true
./q1.csv              true          true              true
sub/./q1.csv          true          true              true
sub/inner/../q1.csv   false         true              false
sub/                  true          true              true
a/b/../../q1.csv      false         true              false
the RAW column answers a question about spelling.
the RESOLVED column answers a question about the file that will actually be opened.
only the second question is the one the program cares about.

--- 4-5. resolve is idempotent, so it belongs in front of the check ---
q1.csv                r1 == r2 : true
sub//q1.csv           r1 == r2 : true
./q1.csv              r1 == r2 : true
sub/./q1.csv          r1 == r2 : true

sub/                  r1 == r2 : true

Two rows disagree between the columns, and the direction of the disagreement is interesting. The check that reads the raw spelling rejected both of those paths, while the final path sat comfortably inside the base. In this example, the spelling check blocked legitimate files from being opened.

That is a useful angle on the ordering problem. Checking a spelling and checking a file are two different questions, and the program cares only about the second. The answer to the first throws off the answer to the second in either direction. 4-5 shows the fix is trivial: joining and normalizing are idempotent, so moving them ahead of validation loses nothing.

5. Decoding is not idempotent

Every normalization step so far has been idempotent, which is why the prescription move it forward worked. One step is different: percent decoding. Its result keeps changing depending on how many times you run it.

node v22.16.0 / win32
--- 5-1. one decode, two decodes, three decodes ---
raw           after 1       after 2       after 3
----------------------------------------------------------------
a%3Cb         a<b           a<b           a<b
a%253Cb       a%3Cb         a<b           a<b
a%25253Cb     a%253Cb       a%3Cb         a<b
100%25        100%          URIError: URI malformed URIError: URI malformed
a%2520b       a%20b         a b           a b
plain         plain         plain         plain

--- 5-2. decoding is NOT idempotent ---
a%3Cb         d1 == d2 : true
a%253Cb       d1 == d2 : false   a second layer changes the value again
a%25253Cb     d1 == d2 : false   a second layer changes the value again
100%25        d1 == d2 : false   a second layer changes the value again
a%2520b       d1 == d2 : false   a second layer changes the value again
plain         d1 == d2 : true
a step you cannot repeat safely cannot be moved around freely.
it must happen exactly once, at a place both sides agree on.

The fourth row is especially important. 100%25 decodes once into 100%, and decoding that again raises an exception, because a string ending in a percent sign is not a valid encoding. So a structure that decodes twice can even kill legitimate values with an error.

5.1 Every layer has its own decoder

The question is why a double decode happens at all. Nobody decides to decode twice. Each layer simply does it once, in its own place.

--- 5-3. the same string through two different decoders ---
raw           decodeURIComponent    URLSearchParams     same?
----------------------------------------------------------------
a+b           a+b                   a b                 false
a%20b         a b                   a b                 true
a%2Bb         a+b                   a+b                 true
a%3Cb         a<b                   a<b                 true
the plus sign is where the two disagree. one layer sees a space, the other a plus.

--- 5-4. a value that survives a check and then changes at the next layer ---
raw           layer1 out    deny at L1?  layer2 out    deny at L2?
----------------------------------------------------------------------
a%253Cb       a%3Cb         false        a<b           true
a%2526b       a%26b         false        a&b           true
a%3Bb         a;b           true         (rejected)    -
ok-value      ok-value      false        ok-value      false
layer 1 checked the value layer 1 had. layer 2 uses a different string.

--- 5-5. counting decodes across a chain ---
start value : a%25253Cb
gateway     a%25253Cb      -> a%253Cb       (changed)
router      a%253Cb        -> a%3Cb         (changed)
handler     a%3Cb          -> a<b           (changed)
three layers each doing their own decode is three decodes, not one.
nobody wrote that down anywhere. it is the sum of three local decisions.
  • 5-3 shows that an operation with the same name differs between tools. One turns the plus sign into a space and the other leaves it alone
  • So the statement we decoded once does not determine what the resulting string is
  • 5-4 shows the structure from section 1 reproducing itself between layers. The value layer 1 checked is not the value layer 2 uses
  • In 5-5 three layers each decoded once and the value was decoded three times overall. Nobody made that decision. It is the sum of three local ones
  • The standard is clear on this point too. The URL Standard performs percent decoding once during parsing and does not prescribe repeated decoding
  • So decoding must happen exactly once, at an agreed place. One more defensive pass is not defence here

So the rule compresses to one line, which is 6-6. The checked value and the used value must be the same. Hold that equality and the rest follows. Break it, and however sophisticated the rules are, that sophistication is not applied to the final value.

7. Normalize once, at the boundary

Fixing the order is not the end. A second rule is needed: there must be exactly one place where normalization happens. Otherwise a different value exists at every layer. I built a chain where four layers each perform one plausible tidy-up and traced the value.

A boundary that includes decoding gives a different result when run twice. That turns normalize once at the boundary from advice into a hard requirement.

7.2 The quiet version - the cache splits

When this defect does not manifest as a security problem, it manifests as a performance one.

--- 7-5. cache keys computed at two layers ---
key hashed at layer 1 : dcd41471
key hashed at layer 3 : 845e9183
same request, same user, two cache entries : true
a split cache is the quiet version of this bug. nothing errors, the hit rate just drops.
  • One request produced a different cache key per layer. Two entries exist and the hit rate falls
  • Nothing errors, so monitoring never flags it. The dashboard only shows that cache efficiency is lower than expected
  • The same principle applies to log aggregation. Count one subject under two names and the statistics split
  • Rate limiters and deduplication guards go inert once their key splits
  • So cache keys, log keys and storage keys must all be built from the value the boundary produced

8. How to find this ordering problem in code

Diagnosis is most reliable when you start at the sink. Find the line that opens a file, builds a query or calls outward, and walk the variable entering it upwards. When you meet a validation call, read every line between the two. If even one of them changes the value, that is the defect.

Much of this work is mechanical. I swept a sample module with nothing but a text scan.

this second pattern is the one code review misses. the checked variable is still
untouched, so the diff looks fine. a different variable is what reaches the sink.
  • The first shape is reassigning the validated variable. It is relatively conspicuous
  • The second shape is far more dangerous: leaving the validated variable alone and building a derived one that gets used instead
  • In the second shape the diff looks fine. Validation is present and the validated variable is untouched. Review waves it through
  • Pick the search terms to fit your codebase. Two lists are enough: validation function names and names of functions that change the value
  • The mutating list should include decoding, normalization, whitespace stripping, case conversion, replacement and path joining
  • It does not need to be exhaustive. The point is to produce a candidate list a human then reads

8.1 A runtime tripwire

When the static scan leaves you unsure, there is a way to check at runtime: record the string the checker received and compare it at the sink.

8.2 Establish the property of each step first

Where a step belongs is decided by whether that step is idempotent. You can determine this directly.

--- 8-4. property check: normalize is a fixed point, decode is not ---

------------------------------------------------------------------------------------
trim                  true                        yes
toLowerCase           true                        yes
NFKC                  true                        yes
decodeURIComponent    false                       NO - must run exactly once

the sample module fails the first three. that is the point of running it on your own code.

The check in 8-4 takes a handful of lines. For a few sample strings, see whether applying the step twice equals applying it once. If it does, the step is harmless at several layers; if not, it must run exactly once.

8-5 turns the checklist into an executable form. The sample module failed three items. The point of this section is to run that list against your own code. A checklist read as documentation is rarely honoured, but a failing check gets fixed.

9. Checklist and what not to do

Here is everything above in a form you can apply directly.

ItemHow to verifyFailure signal
There is one agreed normalization functionsearch the name and see if there is one definitioneach layer has its own lookalike
The normalizer is idempotentapply it twice to samples and comparedecoding sits inside the function
Decoding happens in one place onlysearch every decode callthere is one at the gateway and one at the handler
The validator receives the final valuecompare the validator argument with the sink argumentthe two arguments are different variables
Nothing sits between validation and useread every line in betweenthere is an assignment or a rework
Paths are judged after normalizingsee whether containment tests the final pathit is scanning the raw segment for characters
Uniqueness and the storage key use one valuecompare the duplicate check argument with the keyonly one side is normalized
The locale is pinnedsearch case conversion callsthey are called with no locale given
  • ❌ Treating the job as done once validation is added. Which value you validated is the substance
  • ❌ Defensively tidying the value one more time at each layer. You get one value per layer and the verdict becomes a function of position
  • ❌ Decoding in several places. Nobody can say how many decodes happen, and legitimate values sometimes die with an error
  • ❌ Deciding path containment from the spelling of the string. Legitimate paths get rejected along with everything else
  • ❌ Deferring normalization because it happens later anyway. Every validation wedged in between goes void
  • ❌ Checking uniqueness on the raw value and storing the canonical one. Keys collide silently and no error is raised
  • ❌ Putting the length limit ahead of normalization. Normalization changes length, so the limit is not applied to the final value
  • ❌ Waving it away with the framework handles it. Unless you verify where the framework does what, it is just one more layer

Closing: what did you validate

Advice about input validation usually stops at validate. Yet every failure in this article came out of code that already had validation. The checker was accurate, the rules were tight, no branch was missing. And still the final value had never passed those rules.

So the question to ask is not did you validate but what did you validate. The answer is decided by the order of the code. If the validated value and the used value differ, the validation is not merely weak. It is as if it had never been there.

Reduced to one line, what the runs above establish is this: normalize first, validate second, and put nothing in between. Most normalization steps are idempotent so moving them forward costs nothing, and the steps that are not idempotent run exactly once at the boundary. Then the value the checker saw is the value the program uses, and after that nothing can void the validation.

# Normalize First, Validate Second — A Copy-Paste Order Card

> Source: braindetox.kr — Change the Value After Validating It and the Validation Is Void
> Evidence: verified by execution on Windows 10 / Node.js 22.16.0 / Python 3.13.3

## 0. The rule in one line

Normalize, then validate, then use. And **put nothing between validate and use.**

The value the validator saw must be the value that actually gets used. Once that equality breaks, the validation might as well never have happened.

```
atCheck === atUse
```

## 1. How to tell the order is inverted

If any one of these is true, you have an ordering defect.

- [ ] A line reassigns the variable after it passed the check
- [ ] A **new variable** is derived from it after the check, and that new one is used
- [ ] The argument handed to the validator is not string-equal to the argument handed to the sink
- [ ] Decoding, normalization, trimming, lowercasing, or path joining happens after the check
- [ ] Each layer tidies the value on its own judgement (gateway, service, storage)

## 2. The wrong order and the right order

### Wrong — the value changes after the check

```js
function handle(req) {
  let name = req.query.name;
  if (!isAllowed(name)) return reject();   // checked: the encoded original
  name = decodeURIComponent(name);         // the value changes here
  return open(name);                       // used: the decoded result
}
```

### Wrong — a derived variable after the check (the shape review misses)

```js
function handle(req) {
  const label = req.body.label;
  if (!isAllowed(label)) return reject();  // label itself is untouched
  const key = label.trim().toLowerCase();  // the validator never saw this
  return store(key);
}
```

### Right — normalize once at the boundary, validate that value, use that value

```js
function normalize(s) {
  let out = String(s == null ? '' : s);
  try { out = decodeURIComponent(out); } catch (e) { /* keep as-is */ }
  return out.normalize('NFKC').trim().toLowerCase();
}

function handle(req) {
  const name = normalize(req.query.name);  // normalize
  if (!isAllowed(name)) return reject();   // validate
  return open(name);                       // use - same variable, no rework
}
```

## 3. Properties of each normalization step

| Step | Idempotent | Safe at several layers | Placement |
| --- | --- | --- | --- |
| trim | yes | yes | boundary |
| toLowerCase | yes | yes (pin the locale) | boundary |
| NFKC | yes | yes | boundary |
| percent-decoding | **no** | **no** | exactly once, at the boundary |
| path join and normalize | yes | yes | immediately before validation |

A step that is not idempotent must run **exactly once**, and where it runs has to be written down.

## 4. Layer placement principles

- There is one boundary. Normalize only at the first point the request enters
- Every layer below the boundary treats the value as **final** and does not touch it
- Normalizing per layer produces a different value per layer, and a different verdict per layer
- Cache keys, log keys and storage keys are all built from **the value the boundary produced**

## 5. Checklist

- [ ] A normalization function exists and has one agreed name
- [ ] Running the normalizer twice gives the same result (decoding excepted)
- [ ] Decoding happens once, at the boundary
- [ ] The validator receives the normalized value as its argument
- [ ] Nothing assigns to or reworks the value between validation and use
- [ ] The validated variable and the used variable are the **same variable**
- [ ] Containment for paths is decided after joining and normalizing, not from spelling
- [ ] The uniqueness check and the storage key use the same value
- [ ] Locale-dependent conversions state their locale explicitly
- [ ] A test asserts that the validator argument equals the sink argument

## 6. Diagnostic procedure

1. Find the sink first (opening a file, issuing a query, calling out)
2. Walk the variable that enters it backwards
3. See whether a validation call sits on that path
4. If it does, read **every line between the validation call and the sink**
5. If even one of those lines changes the value, that is the defect
6. When unsure, attach a runtime tripwire: record the string the validator received and compare it at the sink

## 7. Do not

- ❌ Consider the job done once validation is added — which value you validated is the substance
- ❌ Defensively tidy the value one more time at each layer — you get one value per layer
- ❌ Decode in several places — nobody can say how many times it was decoded
- ❌ Decide path containment from the spelling of the string — legitimate paths get rejected too
- ❌ Defer normalization because it happens later anyway — the validation in between goes void
- ❌ Check uniqueness on the raw value and store the normalized one — keys collide silently
