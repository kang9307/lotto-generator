What Happens Inside a GPU When You Launch a CUDA Kernel

From host launch to warp execution, memory hierarchy, and occupancy — a step-by-step deep dive

2026-07-01 Dev & Infra

Introduction: One Line That Triggers a Massive Pipeline

Whether you are training a deep learning model, running a GPU-accelerated simulation, or rendering high-fidelity graphics, you are launching CUDA kernels. From the developer's perspective it is just a single line of code. Behind that line, however, lies a complex sequence of host-driver calls, GPU command queues, thousands of concurrently scheduled threads, and multiple layers of memory hierarchy working in concert.

This post — current as of June 2026 — dissects that pipeline from start to finish. The goal is twofold: to build genuine developer-level intuition for why the GPU behaves the way it does, and to understand why the internals of CUDA are the foundation on which all deep learning and AI inference acceleration is built. Both developers who have just written their first vectorAdd<<<4096, 256>>>(a, b, c, N); and ML engineers tuning training throughput should find concrete mental models here.

One caveat upfront: GPU microarchitecture details vary across generations, and NVIDIA does not disclose everything. The discussion below uses Hopper (H100) and Ada (RTX 40-series) as reference points, based on public documentation and open research. Numbers convey direction, not precise benchmarks.

Stage 1: From Host Code to Kernel Launch

1.1 The nvcc Compilation Pipeline

CUDA code starts as a .cu file and passes through nvcc, which separates host and device code. Device code goes through two compilation stages. First, it is compiled to PTX (Parallel Thread Execution), a virtual ISA that assumes unlimited virtual registers and abstracts away the specific GPU microarchitecture. Then PTX is compiled to SASS (Shader Assembly), the actual machine code for the target GPU (e.g., sm_89 for the RTX 4090). The final binary, called a fatbin, bundles both cubin (machine code) and PTX so that newer GPU generations can JIT-compile from PTX.

1.2 Host Stub and Driver Calls

At runtime, invoking kernelFunc<<>>(args...) executes a host stub generated by nvcc. The stub acts as a key that looks up the kernel in the runtime registration table and marshals arguments into an argument buffer. On the first GPU call, libcuda.so is dynamically loaded and a GPU context is created — a significant one-time cost that is amortized across subsequent launches. A seemingly simple vector addition traced with strace reveals hundreds of ioctl calls, most of which are one-time setup.

1.3 QMD, Pushbuffer, GPFIFO, and Doorbell

The driver constructs a QMD (Queue Meta Data) — the launch descriptor for the compute grid. The QMD encodes grid dimensions, block dimensions, registers per thread, shared memory requirements, the program start address, the constant bank address for kernel arguments, and the completion signal location. The driver writes this QMD into a pushbuffer, a GPFIFO entry points to it, and finally a doorbell MMIO write wakes the GPU. Control now transfers from CPU to GPU.

Stage 2: Grid, Block, and SM — How Work Gets Distributed

2.1 The Three-Level Hierarchy

CUDA's execution hierarchy is grid → block → thread. A grid corresponds to a single kernel launch. Grids and blocks can be 1D, 2D, or 3D, which maps naturally to image processing (2D) or volumetric simulations (3D). Thread IDs in multi-dimensional blocks are linearized in row-major order before being assigned to warps.

2.2 Block-to-SM Assignment

The GPU's physical execution unit is the SM (Streaming Multiprocessor). The H100 has 144 SMs; the RTX 4090 has 128. Blocks from the kernel grid are distributed across available SMs. The critical rule is that all threads in a block must execute on the same SM. This is what enables shared memory and __syncthreads() within a block. Blocks from different grids are independent and cannot be assumed to execute in any particular order. The number of blocks an SM can host concurrently is limited by registers, shared memory, and hardware constraints.

2.3 SM Internal Structure

Inside an SM you find CUDA cores (FP32/INT32 execution units), special function units (SFUs), Tensor Cores (matrix-multiply accelerators), warp schedulers, register files, and the combined L1 cache / shared memory SRAM. An H100 SM contains 128 FP32 cores and 4 warp schedulers, each capable of issuing an instruction from an eligible warp every cycle. Holding many warps in-flight and cycling between them is the GPU's primary latency-hiding strategy.

Stage 3: Warps and SIMT Execution

3.1 What Is a Warp?

A warp is the SM's fundamental scheduling unit: 32 threads that execute the same instruction at the same clock cycle. Threads in a block are grouped into warps in thread-ID order. A 256-thread block becomes 8 warps. This is the SIMT (Single Instruction Multiple Thread) execution model. Each thread has independent registers and a program counter, but under normal execution flow all 32 threads run in lockstep.

3.2 SIMT vs. SIMD

CPU SIMD requires the programmer or compiler to explicitly vectorize data operations. With SIMT, developers write ordinary scalar thread code and the hardware automatically parallelizes 32 threads per warp. The programming model is far simpler. The cost of this simplicity is the assumption that all threads in a warp take the same execution path. When they do not, warp divergence occurs.

3.3 Warp Scheduling and Latency Hiding

An SM holds far more warps in-flight than it can execute simultaneously. When a warp stalls waiting for a global memory access (hundreds of cycles), the scheduler instantly switches to a ready warp with no context-switch overhead. Registers are stored permanently in the SM's register file — nothing needs to be saved or restored. This zero-overhead switching is why GPUs can tolerate very high memory latency by keeping enough warps in-flight to cover it. A warp becomes eligible for scheduling once its scoreboard clears (variable-latency ops) and its stall counter reaches zero (fixed-latency ops).

Stage 4: Warp Divergence — Why Branches Kill Performance

4.1 When Divergence Occurs

Warp divergence happens when threads in the same warp take different paths through an if, for, or switch. Because SIMT requires all 32 threads to execute the same instruction, the hardware serializes the divergent paths: path A executes with path-B threads masked off, then path B executes with path-A threads masked off. Two divergent branches can double the effective instruction count; N branches can multiply it by N.

4.2 Minimizing Divergence

The core principle is to ensure that threads within the same warp take the same code path. The classic anti-pattern is odd/even thread branching, where thread 0, 2, 4... take one path and 1, 3, 5... take another — every thread in every warp diverges. The fix is to partition data so that all 32 threads in a warp are on the same side of every branch. When divergence is unavoidable, pre-sorting or partitioning data by branch condition before the kernel launch often yields large gains. Modern GPUs also implement thread block compaction to reduce some divergence costs at the hardware level.

Stage 5: Memory Hierarchy — From Registers to Global

5.1 Registers — Fastest, Most Constrained

Registers are thread-private, with ~1-cycle access latency. An H100 SM has 65,536 32-bit registers. The compiler maps PTX virtual registers to real registers. As register usage per thread increases, fewer threads (warps) can fit on the SM simultaneously. When register demand exceeds supply, the compiler spills to local memory — which physically resides in global memory — at a steep performance cost.

5.2 Shared Memory — The Block's Collaborative Scratchpad

Shared memory is on-chip SRAM shared among all threads in a block, with ~25-cycle latency — orders of magnitude faster than global memory. On the H100, it shares the same physical SRAM as L1 cache, configurable up to 228 KB per SM. Declared with the __shared__ qualifier. The canonical use case is tiling matrix multiplication: load a tile from global memory into shared memory, compute on it entirely in-chip, then move to the next tile. Beware of bank conflicts: shared memory is divided into 32 banks, and simultaneous accesses to the same bank by threads in the same warp serialize.

5.3 Global Memory — Vast but Slow

Global memory spans the GPU's entire VRAM and is accessible by all threads. The H100's HBM3 delivers ~3 TB/s bandwidth, but latency is ~350 cycles on TLB hit and >1000 cycles on a TLB miss. Hiding this latency requires keeping enough warps in-flight (occupancy). Additionally, coalesced access is critical: when the 32 threads of a warp access consecutive memory addresses, the hardware issues a single wide transaction. Strided or random access patterns fragment into multiple transactions, wasting bandwidth.

Stage 6: Occupancy — How Full Should the SM Be?

6.1 Definition and Limiting Factors

Occupancy is the ratio of resident warps on an SM to the maximum the SM supports. An H100 SM supports up to 64 warps, 2,048 threads, and 32 blocks. Three factors cap occupancy. First, registers: more registers per thread means fewer threads (warps) fit. Second, shared memory: more shared memory per block means fewer blocks (and warps) fit. Third, block size: very small blocks limit the number of warps because the per-block hardware limit kicks in before the per-SM warp limit. For example, a block size of 32 (one warp) allows at most 32 blocks → 32 warps on an H100, giving 50% occupancy.

6.2 More Occupancy Does Not Always Mean More Speed

Beyond roughly 20–40% occupancy, additional warps typically contribute little additional performance. Squeezing out the last bit of occupancy by starving registers causes spills that hurt far more than they help. Investing the shared memory budget in better caching is often more effective than fitting more warps. Use CUDA Occupancy Calculator or Nsight Compute to measure rather than guess.

Stage 7: Kernel Completion and Result Transfer

When all blocks in the grid complete, the GPU posts a completion semaphore. A cudaDeviceSynchronize() or stream event on the CPU side waits for this signal. To retrieve results, cudaMemcpy (device-to-host) moves data from GPU VRAM across the PCIe bus to host memory. In multi-GPU environments with NVLink, GPU-to-GPU transfers bypass the host entirely. Even a simple vector addition traverses this entire pipeline; a 72 MB benchmark measured with Nsight shows ~10–11 µs, ~80% DRAM utilization, and only ~5% warp issue efficiency — a textbook memory-bound kernel.

Stage 8: CUDA Internals as the Foundation of AI Acceleration

8.1 Why GPUs Fit Deep Learning Perfectly

Deep learning training is dominated by matrix multiplications: applying the same operation across millions of weight-activation pairs. This maps exactly onto SIMT — the same instruction across 32 threads, thousands of warps, hundreds of SMs simultaneously. The H100's 144 SM × 128 FP32 cores = 18,432 cores, augmented by Tensor Cores delivering far higher matrix-multiply TFLOPS. The parallelism structure of neural networks and CUDA's SIMT architecture are nearly a perfect match.

8.2 FlashAttention as a Memory-Hierarchy-Aware Kernel

The Attention mechanism in Transformers requires memory accesses that scale as O(n²) in sequence length. A naive implementation repeatedly reads and writes the attention matrix to global memory, making it strongly memory-bound. FlashAttention tiles the computation so that each tile fits in shared memory, computes entirely on-chip, and only writes the final result to global memory. The math is identical; the memory movement is dramatically reduced. This is why FlashAttention delivered training speedups of 2–4x on large language models after 2022 — without changing the algorithm, just the CUDA kernel design. Understanding CUDA internals is a prerequisite for innovations like this.

8.3 When to Write Custom CUDA Kernels

Frameworks like PyTorch and JAX ship highly optimized cuBLAS and cuDNN kernels for standard operations. Custom CUDA kernels become necessary for novel operators, specialized sparsity patterns, or domain-specific kernel fusion. At that point, grid/block sizing, shared memory usage, coalesced access patterns, and divergence minimization all require explicit design choices. Nsight Compute provides per-SM, per-warp granularity to pinpoint exactly where the bottleneck lies.

Practical Takeaways for General Developers

Batch Size and Warp Utilization

In deep learning, very small batch sizes leave SMs only partially occupied, wasting GPU utilization. Setting batch sizes as multiples of 32 ensures complete warps. Values like 512 or 1024 are common starting points. However, excessively large batches can overflow VRAM.

Tensor Dimensions and Memory Alignment

Matrix dimensions that are multiples of 8 or 16 align with Tensor Core requirements and coalesced access patterns. Non-aligned dimensions introduce padding or extra memory transactions that reduce efficiency.

Profile Before Buying Bigger Hardware

Slow code is not always solved by a larger GPU. Profile first with Nsight Compute or PyTorch Profiler to determine whether the kernel is compute-bound or memory-bound. Adding more CUDA cores to a memory-bound kernel does almost nothing. Improving coalesced access or applying kernel fusion to the same GPU can yield several times the speedup.

Conclusion: The Power of Knowing What Lies Beneath the Abstraction

Behind a single kernel<<>>(args) lies an intricate pipeline: compilation, host stub execution, QMD construction, pushbuffer writes, doorbell signaling, SM block assignment, warp scheduling, SIMT execution, memory hierarchy traversal, and completion semaphore signaling. You can run deep learning code without knowing any of this. But diagnosing bottlenecks, designing optimized kernels, and making deliberate choices about memory hierarchy require this structure to be living knowledge.

The throughput and cost of large language model training and inference — in other words, the practical economics of the current AI wave — are determined to a significant degree by how well CUDA kernels exploit GPU memory hierarchy. As of June 2026, understanding these internals is fast becoming essential knowledge for ML engineers and infrastructure developers alike.
