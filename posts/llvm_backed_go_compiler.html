남의 라이브러리를 쓰겠다는 결정이 떠안는 것 - LLVM 기반 Go 컴파일러가 드러낸 경계의 청구서

cgo 가 그냥 함수 호출이 아닌 이유부터, 런타임을 갈아 끼운 뒤 새로 생기는 청구 항목까지

2026-09-07 개발/인프라

Go 로 짠 프로그램에서 NumPy 를 부르고 PyTorch 를 태우고 raylib 로 화면을 그린다는 문장은 매력적으로 들린다. 언어 하나로 쓰던 코드에 남의 생태계가 통째로 딸려 오는 그림이기 때문이다. 그런데 그 문장이 실제로 지시하는 일은 하나다. 서로 다른 실행 모델 두 개를 한 프로세스 안에 겹쳐 놓는 것이다.

겹쳐 놓으면 반드시 경계가 생긴다. 경계에는 값이 붙는다. 메모리를 누가 해제하는지, 수집기가 그 포인터를 보는지, 한쪽의 예외가 다른 쪽의 패닉으로 번역되는지, 스레드 규약이 누구 것인지가 전부 그 경계 위에서 다시 정해져야 한다. 언어 하나만 쓸 때는 컴파일러와 런타임이 대신 지켜 주던 것들이다.

LLVM 을 백엔드로 삼아 Go 를 컴파일하고 C 와 파이썬 라이브러리를 직접 부르게 만든 구현이 정식 판번호를 달고 나왔다. 여기서 볼 것은 그 도구의 사용법이 아니다. 다른 언어의 라이브러리를 쓰겠다는 결정이 무엇을 떠안는가다. 그 구현은 그 청구서를 유난히 또렷하게 보여 주는 표본이다. 문제를 회피하지 않고 정면으로 되받았고, 되받은 대가를 문서로 남겨 두었기 때문이다.

아래에서 표준 Go 의 동작을 서술하는 대목은 전부 공식 문서와 런타임 소스의 설명 주석에 적힌 범위다. 구현 쪽 수치와 선언은 저장소 문서와 공개 API 조회 결과이며, 조회 시각은 2026-09-07 11:56 KST 다. 성능·크기 수치는 그 프로젝트가 스스로 돌린 지속 통합 측정이므로 자체 측정으로 읽어야 한다. 제3자 재현이 아니다.

계기 - 「Go 컴파일러」라는 말이 가리는 것

소개 문구는 대개 짧다. 「LLVM 기반 Go 컴파일러」라고 적혀 있으면 대부분 표준 Go 를 그대로 받아 기계어만 다르게 뽑는 물건으로 읽는다. 그리고 그 읽기는 절반만 맞는다.

저장소가 스스로 적어 둔 범위는 이렇다. Go 1.20 이상 소스와 호환되고 Go 1.27 언어 문법 전체를 지원하며 cgo 도 받는다. 지원 네이티브 플랫폼에서는 표준 라이브러리를 전부 지원한다고 적는다. 여기까지만 보면 부분집합이라는 말은 틀렸다.

그런데 같은 문서가 바로 다음 절에서 다른 이야기를 한다. 런타임이 표준 툴체인과 다르다. 고루틴이 OS 스레드에 1대1로 붙고 스택은 고정 크기 네이티브 스택이며, 기본 수집기는 보수적 방식인 Boehm 계열이다. 베어메탈 대상은 또 다른 보수적 표시·제거 수집기를 쓴다. 문법은 전부 받는데 그 문법이 돌아가는 바닥이 다르다.

그래서 이 물건을 한 줄로 요약할 때 「표준 Go 의 부분집합」은 부정확하고, 「표준 Go 호환」도 부정확하다. 정확한 요약은 문법과 표준 라이브러리는 전부, 런타임 보증은 다름이다. 소개 문구가 지원 플랫폼을 리눅스와 맥으로만 적는 경우도 있는데, 저장소 문서는 윈도우 amd64·arm64 를 MSVC 와 MinGW 두 갈래로 함께 적고 웹어셈블리와 임베디드 보드까지 나열한다. 요약은 늘 늦게 갱신된다.

Go 는 원래 왜 그랬나 - 자체 백엔드를 고른 대가

Go 팀은 프로젝트 초기에 LLVM 을 검토했고 채택하지 않았다. 공식 FAQ 에 그 이유가 한 문장으로 남아 있다. 성능 목표를 맞추기에는 너무 크고 느리다고 판단했다는 것이다. 여기서 말하는 성능은 생성 코드의 실행 속도가 아니라 컴파일러 자신의 속도다. 같은 문서가 다른 자리에서 목표를 명시한다. 큰 실행 파일 하나를 한 대의 컴퓨터에서 몇 초 안에 빌드하는 것이다.

이 선택은 연쇄적으로 언어의 성격을 정했다. 자체 백엔드와 자체 링커를 쓰기 때문에 툴체인이 작고, 정적 링크가 기본이라 배포가 단순하며, 목표 운영체제와 아키텍처를 환경 변수 두 개로 바꿔 크로스 컴파일할 수 있다. 대신 최적화의 깊이는 수십 년 축적된 범용 백엔드에 미치지 못하고, 지원 대상 아키텍처의 폭도 그 백엔드만큼 넓지 않다.

그리고 같은 선택이 cgo 의 성격도 정했다. 자체 호출 규약과 자체 스택 관리, 자체 스케줄러를 쓰는 런타임에서 C 함수를 부른다는 것은 남의 규약으로 잠시 넘어갔다 오는 일이 된다. 넘어가고 돌아오는 절차가 곧 비용이다.

표준 툴체인이 고른 것그 대가로 얻은 것그래서 포기한 것
자체 컴파일러 백엔드큰 실행 파일도 몇 초 수준의 빌드범용 백엔드가 쌓아 온 최적화의 깊이
자체 링커와 정적 링크 기본파일 하나로 끝나는 배포작은 바이너리. 런타임과 타입 정보가 항상 실린다
환경 변수로 지정하는 목표 플랫폼C 도구 없이 되는 크로스 컴파일C 라이브러리를 쓰는 순간 그 단순함이 사라진다
확장 가능한 고루틴 스택수십만 개를 띄워도 견디는 동시성C 코드를 그 스택 위에서 그대로 돌릴 수 없다

표의 마지막 두 줄이 이 글의 나머지 전부를 예고한다. 동시성과 자동 메모리 관리를 값싸게 만든 바로 그 설계가, 경계를 넘는 순간 값을 청구하는 쪽으로 돌아선다.

cgo 는 왜 그냥 함수 호출이 아닌가

Go 런타임 소스의 cgocall 파일 맨 위에는 호출 경로 전체를 설명하는 긴 주석이 붙어 있다. 이 주석이 「비싸다」는 말의 내용물이다.

Go 코드가 C 함수 f 를 부르면, 생성된 코드가 런타임의 cgocall 을 부른다. cgocall 은 먼저 entersyscall 을 부른다. 다른 고루틴과 수집기를 막지 않기 위해서다. 주석은 이 호출의 목적을 명시한다. 외부 코드에 들어가 있는 동안 다른 고루틴을 돌릴 스레드를 하나 더 만들어야 한다는 것을 스케줄러에 알리는 것이다.

그다음 어셈블리 계층의 asmcgocall 이 현재 고루틴 스택을 떠나 g0 스택으로 옮긴다. 주석은 그 이유까지 적어 둔다. g0 스택은 운영체제가 잡아 준 스택이라 C 컴파일러가 만든 코드를 올려도 안전하기 때문이다. 뒤집어 말하면 고루틴 스택 위에서는 C 코드를 그대로 돌릴 수 없다. 필요할 때 늘어나는 스택 위에서 C 함수가 실행되면 안 되기 때문이다.

C 함수가 끝나면 원래 고루틴 스택으로 되돌아오고, cgocall 이 exitsyscall 을 부른다. 주석은 이 함수의 성질을 한 문장으로 적는다. 병렬 실행 한도를 어기지 않고 이 스레드가 Go 코드를 돌릴 수 있을 때까지 막힌다는 것이다. 즉 복귀는 즉시가 아니라 스케줄러의 허락을 기다리는 절차다.

C 쪽에서 Go 함수를 되부르면 이 계단을 거꾸로 한 번 더 내려간다. 어댑터가 C 호출 규약을 Go 호출 규약으로 바꾸고, 다시 g0 스택에서 원래 고루틴 스택으로 옮긴 뒤, 거기서 다시 exitsyscall 로 한도를 기다린다. 콜백 한 번에 왕복 전환이 두 겹으로 쌓인다는 뜻이다.

이 표를 보면 「호출이 비싸다」가 마이크로초 단위의 상수 지연 이야기가 아님이 드러난다. 스케줄러 회계와 스택 소유권이 매 호출마다 오간다. 그래서 큰 계산을 한 번 넘기는 경우에는 거의 문제가 되지 않고, 작은 함수를 촘촘히 부르는 경우에는 구조 자체가 문제가 된다.

포인터 전달 규칙 - 컴파일러가 아니라 규약이 지킨다

비용보다 위험한 것은 규칙이다. cgo 문서는 포인터를 넘길 때의 조건을 못 박아 둔다. Go 포인터를 C 로 넘기려면 그 포인터가 가리키는 메모리가 고정되지 않은 다른 Go 포인터를 담고 있지 않아야 한다. 그리고 C 코드는 호출이 끝난 뒤에 Go 포인터의 사본을 보관할 수 없다. 예외는 고정 장치로 그 메모리를 붙들어 둔 경우뿐이다.

인자로 넘긴 Go 포인터는 호출이 지속되는 동안에만 암묵적으로 고정된다. 호출이 끝나는 순간 그 보증도 끝난다. 문자열은 더 단순하다. C.CString 은 C 힙에 사본을 만들고, 문서는 해제 책임이 호출자에게 있다고 적는다.

// 표준 Go 의 cgo - 경계를 넘는 값은 복사되고, 해제 책임은 호출자에게 남는다
cs := C.CString(s)                  // C 힙에 사본을 만든다
defer C.free(unsafe.Pointer(cs))    // 이 한 줄이 없으면 그대로 샌다
n := C.strlen(cs)                   // 여기서부터는 C 의 메모리다

호출이 끝난 뒤에도 C 가 Go 메모리를 들고 있어야 하는 경우에는 고정 장치를 쓴다. 표준 라이브러리의 Pinner 는 대상을 수집기가 옮기지도 회수하지도 못하게 붙들어 둔다. 고정된 객체가 다시 다른 Go 객체를 가리키고 C 가 그것까지 따라간다면, 그 대상도 따로 고정해야 한다.

// C 가 호출 이후에도 Go 포인터를 들고 있어야 할 때
var pinner runtime.Pinner
pinner.Pin(p)            // 수집기가 옮기지도 회수하지도 못하게 붙든다
defer pinner.Unpin()     // 풀기 전까지만 C 쪽 참조가 유효하다

여기서 눈여겨볼 것은 규칙의 집행 주체다. 이 규칙들은 타입 검사기가 잡아 주지 않는다. 컴파일은 그대로 통과하고, 어겼을 때의 결과는 즉시 나타나지도 않는다. 수집기가 그 메모리를 실제로 옮기거나 회수하는 시점에야 증상이 생긴다. 부하가 높거나 힙이 커진 뒤에 처음 터지는 종류의 결함이다.

  • 넘길 수 있는 것의 조건 — 가리키는 메모리 안에 고정되지 않은 Go 포인터가 없어야 한다. 구조체 안에 슬라이스나 문자열이 들어 있으면 이 조건에 걸린다
  • 보관의 금지 — C 가 호출 이후까지 Go 포인터를 들고 있으려면 고정이 필요하고, 고정을 푸는 순간 그 참조는 근거를 잃는다
  • 해제의 귀속 — C 힙에 만든 것은 C 규약으로 해제한다. Go 의 수집기는 그 메모리를 세지 않으므로 누수는 조용히 쌓인다

같은 문제를 언어 차원에서 어떻게 줄일 수 있는지는 Rust FFI 경계에서 끊기는 안전 보증 에서 다룬 축이다. 그쪽은 경계 자체를 줄이는 접근이고, 여기서 볼 것은 경계를 없애기 위해 바닥을 바꾸는 접근이다.

런타임을 갈아 끼운다는 선택

3절의 계단은 전부 하나의 전제에서 나온다. 고루틴 스택과 스케줄러가 C 의 것이 아니라는 전제다. 그 전제를 지우면 계단도 사라진다. LLVM 기반 구현이 고른 길이 정확히 그것이다.

저장소 문서의 표현은 간결하다. 네이티브 고루틴이 OS 스레드에 1대1로 붙고 스택은 고정 크기 네이티브 스택이므로, C 를 직접 부를 때 Go 에서 C 로의 스택 전환도 스케줄러 전환도 필요 없다는 것이다. 바인딩 방식도 래퍼를 거치지 않는다. Go 선언 하나를 C ABI 심볼에 직접 묶는다.

import _ "unsafe" // go:linkname 지시자를 쓰려면 필요하다

//go:linkname Sqrt C.sqrt
func Sqrt(x float64) float64

이 지시자 자체는 표준 컴파일러에도 있다. 공식 문서는 그 성질을 이렇게 적는다. Go 변수나 함수 선언이 쓸 목적 파일 심볼을 지정해 두 심볼이 같은 것을 가리키게 만들며, unsafe 를 임포트한 파일에서만 활성화된다. 그리고 이 지시자가 비공개 선언의 캡슐화나 심지어 타입 안전성까지 우회할 수 있다고 명시한다. 편리함의 정체가 무엇인지 문서가 직접 말해 두는 셈이다.

바꾼 것은 호출 경로만이 아니다. 기본 수집기가 보수적 방식으로 바뀌었다. 정밀한 포인터 지도 없이 스택과 레지스터를 훑어 포인터처럼 생긴 값을 전부 살아 있는 것으로 취급하는 방식이다. 이 선택 덕분에 C 코드가 만든 메모리와 Go 코드가 만든 메모리를 한 힙에서 다루기가 쉬워진다. 그리고 그 대가가 다음 절의 목록이다.

「전부 지원」과 「호환 목표 밖」 사이

흥미로운 것은 이 프로젝트가 호환성을 문장이 아니라 목록으로 관리한다는 점이다. 표준 배포판의 컴파일러 시험 모음을 그대로 돌리고, 통과하지 못한 항목을 두 개의 파일로 나눠 둔다. 하나는 아직 못 맞춘 것이고, 다른 하나는 애초에 맞출 생각이 없는 것이다.

아직 못 맞춘 쪽은 열한 건이다. 그중 여섯 건은 파서가 내놓는 오류 메시지 문구가 표준과 다르다는 것이다. 잘못된 패키지 선언, 망가진 이름, 바이트 순서 표식 같은 상황에서 진단문이 다르게 나온다. 나머지 다섯 건은 힙 표본 프로파일과 관련된 것이고, 그중 둘에는 미병합 제안 번호가 사유로 적혀 있다.

맞출 생각이 없는 쪽은 백서른여섯 건이다. 이쪽이 진짜 경계선이다. 백열 건은 사유가 같은 문장으로 끝난다. 그 툴체인에 특유한 동작을 지원하는 것은 호환 목표가 아니다라는 것이다. 나머지는 사유가 더 구체적이다. 보수적 수집기를 쓰므로 정확한 생존 판정과 종료자 시점을 맞추지 않는다는 항목이 열여덟 건 남짓이고, 쓰기 장벽을 쓰지 않으므로 그와 관련된 진단을 재현하지 않는다는 항목이 여러 건이며, 고정 크기 네이티브 스택을 쓰므로 늘어나는 스택의 동작을 재현하지 않는다는 항목도 있다.

축선언된 범위실제로 갈리는 지점

  • 문법 호환과 런타임 호환은 다른 축이다. 같은 소스가 컴파일된다는 사실과, 같은 소스가 같은 시점에 같은 관측을 낸다는 사실은 별개다
  • 종료자와 약한 참조에 기대는 코드가 첫 번째 위험군이다. 보수적 수집기에서는 회수 시점이 표준과 어긋날 수 있다
  • 고루틴을 아주 많이 띄우는 설계가 두 번째 위험군이다. 1대1 매핑에서는 그 개수가 곧 스레드 개수다

LLVM 을 쓰면 무엇이 바뀌나

얻는 쪽

범용 백엔드를 쓰면 그 백엔드가 쌓아 온 것이 전부 딸려 온다. 최적화 통과 묶음, 링크 시점 최적화, 아키텍처별 코드 생성기, 그리고 그 위에 붙어 있는 디버거와 분석 도구다. 목표 확대도 같은 방식으로 온다. 이 구현이 웹어셈블리를 여러 갈래로 뽑고 임베디드 보드까지 대상에 넣을 수 있는 것은 그 백엔드가 이미 그 아키텍처들을 알고 있기 때문이다.

C ABI 로 직접 붙는다는 성질도 여기서 나온다. 같은 백엔드가 C 도 컴파일하므로 호출 규약과 타입 표현이 처음부터 같은 언어로 표현된다. 래퍼 계층이 필요 없는 이유가 이것이다.

치르는 쪽

백엔드가 크다는 것은 툴체인이 크다는 뜻이다. LLVM 공식 문서는 소요 디스크를 이렇게 적는다. LLVM 만 빌드하면 1에서 3기가바이트, LLVM 과 Clang 을 함께 빌드하면 15에서 20기가바이트 가량이다. 이 구현은 LLVM 22 계열의 컴파일러·링커·디버거를 전부 선행 조건으로 요구하고, 여기에 보수적 수집기 라이브러리와 외부 함수 인터페이스 라이브러리, 암호 라이브러리와 압축 라이브러리를 더 요구한다.

이 목록이 곧 빌드 재현성의 청구서다. 표준 Go 의 크로스 컴파일이 값싼 이유는 목표 플랫폼용 C 도구가 필요 없기 때문이다. 경계를 여는 순간 그 전제가 무너진다. 개발자 기계와 지속 통합 기계와 배포 대상의 시스템 라이브러리 판번호가 모두 결과에 들어온다.

LLVM 을 백엔드로 갈아 끼우는 시도 자체는 이 프로젝트가 처음이 아니다. Go 공식 FAQ 도 GCC 백엔드를 쓰는 프런트엔드와 같은 프런트엔드를 쓰는 실험적 LLVM 백엔드의 존재를 적고 있다. TypeScript 를 같은 방식으로 내리는 시도는 Perry - TypeScript 를 LLVM 기계어로 직접 컴파일하는 네이티브 컴파일러 에서 다뤘고, 그 글에서 다룬 함정 하나가 여기서도 되풀이된다. 더 좋은 백엔드가 자동으로 더 빠른 결과를 뜻하지는 않는다. 언어의 의미론이 그 백엔드에 잘 내려가느냐가 먼저다.

자체 측정 숫자 하나 - 웹어셈블리 파일 크기

이 프로젝트는 전용 저장소에서 크기 비교를 지속적으로 돌리고 결과를 공개한다. 조건이 함께 적혀 있으므로 인용할 만하다. 다만 측정 주체가 프로젝트 자신이라는 점은 그대로 안고 읽어야 한다.

조건은 이렇다. 실행 번호 403, 생성 시각 2026-09-07 07:11 UTC, 지속 통합 러너는 리눅스 x64 의 우분투 24 이미지, 목표는 웹어셈블리 시스템 인터페이스 대상이다. Go 1.26.2, LLVM 22, TinyGo 0.41.1 을 썼고 표본은 응용 프로그램 열 개, 지표는 산출 파일의 총 바이트 수다. 빌드 옵션도 함께 공개되어 있다. Go 쪽은 경로 제거와 심볼·디버그 정보 제거를 걸었고, TinyGo 쪽은 크기 우선 최적화와 디버그 정보 제거를 걸었으며, 이 구현 쪽은 크기 우선 최적화에 링크 시점 최적화와 전역 죽은 코드 제거를 조합했다.

이 표에서 읽어야 할 것은 배수 자체가 아니라 배수의 방향이 둘 다 있다는 사실이다. 같은 산출물이 한쪽 기준으로는 3분의 1이고 다른 쪽 기준으로는 여섯 배에 가깝다. 개별 사례로 보면 더 분명하다. 표본에 들어 있는 Base64 변환기의 경우 표준 Go 산출물이 약 228만 바이트, 소형 컴파일러 산출물이 약 9만 7천 바이트, 가장 작은 구성의 산출물이 약 60만 바이트다. 어느 쪽과 비교하느냐에 따라 같은 숫자가 승리도 되고 패배도 된다. 배수만 떼어 온 문장이 위험한 이유가 이것이다.

그리고 이 표는 실행 속도가 아니라 파일 크기다. 크기와 속도는 다른 축이고, 크기 우선 최적화를 건 빌드는 속도 축에서 유리하지 않을 수 있다.

경계를 넘을 때 실제로 깨지는 것들

여기가 이 글의 중심이다. 어느 언어에서 어느 언어로 넘어가든, 경계에서 깨지는 것의 목록은 대체로 같다. 중요한 것은 각 항목이 어떤 증상으로 나타나는가다. 증상을 알아야 원인을 그쪽으로 의심할 수 있기 때문이다.

빌드 재현성시스템 라이브러리와 도구 판번호가 결과에 들어온다내 기계에서는 되는데 지속 통합에서 안 된다선행 조건 목록의 판번호 고정 여부

두 번째 줄은 추상적인 경고가 아니다. 이 구현의 문서에 실제 사고 기록으로 남아 있다. 지연 실행 사슬의 머리를 스레드 지역 저장소에만 원시 포인터로 두었더니 보수적 수집기가 그것을 보지 못했다는 것이다. 백만 건의 지연 실행을 거는 부하 시험에서 수집기가 그 노드를 회수했고, 그 결과 지연 실행 안에서 죽었다. 진단은 명료하다. 논리적 손상이 아니라 루트 등록 누락이었다. 고친 방식도 그에 맞춰, 그 상태를 수집기가 아는 뿌리에서 할당하게 바꾼 것이다.

일곱 번째 줄도 구체적인 문서 근거가 있다. 이 구현의 타입 대응표는 C 함수 포인터가 인자로 올 때와 구조체 필드로 올 때를 다르게 처리한다. 인자 자리에서는 Go 함수 타입으로 받지만 구조체 필드에서는 일반 포인터로 받는다. C 의 함수 포인터는 함수 하나의 주소일 뿐이고 Go 의 함수 값은 클로저일 수 있어서다. 배열도 마찬가지로 인자 자리에서는 포인터로 낮아지고 구조체 안에서만 배열로 남는다. 윈도우 콜백에 대해서도 같은 이유로, 상태를 캡처하는 클로저 대신 직접 함수 참조를 넘기고 문맥은 별도 포인터로 전달하라고 문서가 명시한다.

파이썬을 부른다는 것 - 잠금이 딸려 온다

C 라이브러리를 부르는 것과 파이썬 라이브러리를 부르는 것은 난이도가 다르다. 후자는 인터프리터라는 상태 기계 하나를 통째로 프로세스 안에 들여놓는 일이기 때문이다. 그 상태 기계에는 자기 규약이 있다.

파이썬 공식 C API 문서의 문장은 짧고 단정하다. 자유 스레드 빌드가 아닌 한 인터프리터는 일반적으로 스레드 안전하지 않으며, 그래서 전역 인터프리터 잠금이 있고, 그 잠금을 쥔 스레드만이 파이썬 객체를 다루거나 파이썬 C API 를 부를 수 있다. 외부 스레드에서 들어올 때는 상태를 확보하고 해제하는 짝을 맞춰야 하며, 문서는 모든 확보 호출이 같은 스레드에서의 해제 호출과 짝을 이뤄야 한다고 명시한다.

// 파이썬 라이브러리를 Go 코드에서 그대로 부른다
x := math.Sqrt(py.Float(2))       // 파이썬 math.sqrt 에 넘긴다
std.Print(py.Str("sqrt(2) ="), x) // 파이썬 print 로 찍는다

겉보기에는 함수 호출 두 줄이다. 그런데 이 두 줄이 성립하려면 프로세스 안에서 인터프리터가 이미 초기화되어 있어야 하고, 이 코드를 실행하는 스레드가 잠금을 쥐고 있어야 하며, 넘긴 값들이 파이썬 객체로 만들어져 참조 계수 규약을 따라야 한다. 보이지 않는 전제가 세 겹이다.

이 조건이 Go 의 실행 모델과 어떻게 만나는지를 보면 왜 1대1 스레드 매핑이라는 선택이 나왔는지 짐작이 간다. 표준 Go 에서 고루틴은 스레드에 붙박이가 아니다. 스케줄러가 옮긴다. 잠금을 쥔 채 고루틴이 다른 스레드로 옮겨 가면 규약이 깨진다. 고루틴 하나가 스레드 하나에 고정되어 있으면 이 문제는 구조적으로 사라진다.

자유 스레드 빌드도 만능은 아니다. 공식 문서는 그 빌드에서도 스레드 상태를 떼어 놓는 절차는 여전히 필요하다고 적는다. 인터프리터가 일관된 시야를 얻기 위해 주기적으로 모든 스레드를 잠시 멈추기 때문이다. 예로 수집기를 돌리는 동안이 그렇다.

  • 병렬성의 상한이 남의 것으로 정해진다. Go 쪽에서 고루틴을 아무리 늘려도 파이썬 객체를 만지는 구간은 잠금 하나를 두고 줄을 선다
  • 잠금 규약은 컴파일러가 검사하지 않는다. 확보와 해제의 짝이 어긋나도 컴파일은 통과한다
  • 서드파티 라이브러리는 별도 설치다. 배포물 안에 인터프리터와 그 패키지들이 있어야 하고, 그 판번호가 결과에 들어온다

언제 이 선택이 맞나

기존 라이브러리가 사실상 유일한 구현일 때

판단은 대체로 한 질문으로 압축된다. 그 라이브러리를 대체할 순수 구현이 있는가. 없다면 경계 비용은 선택지가 아니라 전제다. 수치 계산의 특정 커널, 오래 다듬어진 코덱, 특정 하드웨어의 공식 드라이버, 규제 대응 때문에 특정 구현을 써야 하는 암호 모듈 같은 것이 여기 해당한다. 이런 경우 논점은 「쓸 것인가」가 아니라 「경계를 몇 군데에 둘 것인가」로 옮겨 간다.

경계를 줄이는 방법은 대체로 같다. 호출 지점을 한곳에 모으고, 그 안에서 굵게 한 번 넘긴다. 작은 함수를 촘촘히 부르는 대신 배치로 넘기는 것이다. 3절에서 본 계단이 매 호출마다 붙는 구조이므로, 호출 횟수를 줄이는 것이 곧 비용을 줄이는 것이다.

순수 구현이 있을 때

순수 구현이 있으면 계산은 달라진다. 비교 대상은 성능이 아니라 운영 총비용이다. 경계를 열면 배포물에 시스템 라이브러리가 따라 들어오고, 크로스 컴파일이 어려워지고, 장애 조사에 두 언어의 지식이 필요해지고, 표준 도구의 프로파일러와 경합 검출기가 반쪽만 보게 된다.

상황경계를 여는 쪽순수 구현 쪽결정을 가르는 것
대체 구현 자체가 없다사실상 유일한 선택해당 없음경계를 몇 군데로 줄일 수 있는지
순수 구현이 있으나 느리다호출당 계산량이 클 때만보통 이쪽한 번에 넘기는 작업량. 작으면 전환 비용이 이득을 먹는다
순수 구현이 기능이 부족하다부족한 기능이 핵심일 때부족한 부분을 안 쓸 수 있다면그 기능이 요구사항의 중심인지 주변인지
배포 대상이 다양하다불리하다유리하다목표 플랫폼마다 C 도구를 갖출 수 있는지
고루틴을 아주 많이 띄운다런타임 교체형은 불리하다유리하다동시성 규모가 스레드 개수로 환산될 때 견디는지
운영 조직이 한 언어만 안다장애 조사 비용이 커진다유리하다새벽에 죽었을 때 원인을 찾을 사람이 있는지

마지막 줄이 실무에서 가장 자주 결정을 뒤집는다. 경계를 연 시스템의 장애는 한쪽 언어의 지식만으로는 끝까지 따라가기 어렵다. Go 와 다른 언어 사이에서 이 판단을 어떻게 세우는지는 Go 에서 Rust 로 마이그레이션 완전 가이드 에서 다른 각도로 다뤘고, 언어 선택 자체를 검증 비용으로 환산하는 축은 AI 생성 코드의 검증 비용을 낮추는 언어 성질 에 있다.

성숙도를 읽는 법 - 별 개수 말고

별 개수가 말해 주지 않는 것

공개 저장소의 별 개수는 관심의 지표이지 신뢰의 지표가 아니다. 이 저장소는 조회 시점 기준 별 749개, 포크 50개, 열린 이슈 151개다. 2023년 12월에 만들어졌고 조회 당일에도 커밋이 들어오고 있다. 이 숫자들만으로는 도입 판단에 필요한 것이 하나도 나오지 않는다.

대신 볼 것은 네 가지다. 릴리스 태그의 궤적, 열린 이슈의 종류, 호환성 선언의 형태, 표준 준수 범위의 자기 기술이다.

실제로 볼 네 가지

릴리스 궤적부터 보면 첫 태그가 2024년 4월, 정식 판번호 1.0.0 이 2026년 8월 24일이다. 사전 배포판 다섯 개를 일주일 남짓에 몰아 낸 뒤 정식 판을 냈고, 그 뒤 8월 29일과 9월 6일에 보수 판이 두 번 나왔다. 총 릴리스는 마흔아홉 개다. 정식 판번호까지 2년 4개월이 걸렸고 그 직후 두 번의 보수가 있었다는 사실이, 별 개수보다 훨씬 많은 것을 말한다.

네 번째 줄이 이 표에서 가장 값어치 있다. 대부분의 프로젝트는 호환성을 산문으로 적는다. 「거의 호환된다」는 문장은 검증할 수 없지만, 사유가 붙은 예외 목록은 읽고 따질 수 있다. 그 목록에 자기 코드가 기대는 동작이 들어 있는지를 직접 대조할 수 있다는 뜻이다. 언어 프로젝트가 열린다는 것이 실제로 무엇을 바꾸고 무엇을 안 바꾸는지는 Mojo 컴파일러 오픈소스 공개 에서 거버넌스 축으로 다뤘다. 여기서 볼 축은 호환성 선언의 검증 가능성이다.

도입 전에 답해야 할 다섯 가지

도구를 고르는 일은 대체로 질문을 고르는 일이다. 아래 다섯 개에 답이 나오면 결정은 따라온다.

  1. 경계를 몇 번 넘는가. 호출 횟수가 적고 한 번에 넘기는 작업량이 크면 표준 cgo 로도 충분하다. 촘촘한 호출이 구조적으로 불가피할 때만 런타임 교체가 논점이 된다
  2. 고루틴을 몇 개 띄우는가. 1대1 매핑에서는 동시성 규모가 곧 스레드 개수다. 수만 개를 전제한 설계라면 이 경로는 맞지 않는다
  3. 종료자와 회수 시점에 기대는 코드가 있는가. 보수적 수집기에서는 그 시점이 표준과 달라진다. 자원 해제를 종료자에 맡긴 코드가 첫 번째 점검 대상이다
  4. 배포 대상이 몇 종인가. 목표 플랫폼마다 LLVM 계열 도구와 시스템 라이브러리를 갖추고 판번호를 고정할 수 있는지가 실제 도입 비용의 대부분이다
  5. 새벽에 죽었을 때 누가 보는가. 경계를 연 시스템의 장애는 두 언어의 지식을 요구한다. 그 사람이 조직에 있는지가 기술 판단보다 먼저다

다섯 질문 모두 성능을 묻지 않는다는 점이 중요하다. 경계를 여는 결정에서 성능은 대개 이미 답이 정해진 축이고, 실제로 프로젝트를 무너뜨리는 것은 나머지 네 개다. 컴파일 언어에 대화형 실행을 붙일 때도 같은 종류의 교환이 나오는데, 그 축은 컴파일 언어에 대화형 실행을 붙인다는 것 에 정리해 두었다.

확인하지 못한 것

  • 속도 비교를 확인하지 못했다. 공개된 지속 통합 측정은 웹어셈블리 산출 파일의 바이트 수이고, 실행 시간 비교는 같은 형식으로 공개된 것을 찾지 못했다. 8절의 배수를 속도로 옮겨 읽으면 안 된다
  • 네이티브 대상의 크기 표는 열지 못했다. 결과 파일이 네이티브 항목을 별도 요약과 표 형식으로 가리키고 있으나 그 내용은 이 글의 근거에 넣지 않았다
  • C 호출 경로의 실제 절감폭을 수치로 확인하지 못했다. 스택·스케줄러 전환이 없다는 것은 설계상의 서술이며, 표준 cgo 대비 호출당 지연을 같은 조건에서 비교한 공개 수치는 확보하지 못했다
  • 제3자 재현을 확인하지 못했다. 8절의 수치는 전부 프로젝트 자신이 돌린 것이고, 독립된 측정 보고를 찾지 못했다
  • 열린 이슈 151건의 구성을 확인하지 못했다. 결함과 기능 요청과 문서 항목의 비율을 가르지 않았으므로, 이 숫자를 품질 지표로 읽어서는 안 된다
  • 기여자 수의 정확한 총계를 확인하지 못했다. 목록 첫 페이지에 19명이 나오지만 전체 페이지를 합산하지 않았다
  • 파이썬 자유 스레드 빌드에서 이 구현이 어떻게 동작하는지 확인하지 못했다. 저장소 문서가 요구하는 것은 3.12 이상이라는 조건뿐이고, 잠금 없는 빌드에 대한 별도 기술은 확인 범위에 없었다
