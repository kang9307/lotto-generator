きっかけ - 「そのまま動く」で始まる文書

2026年9月初め、韓国の開発者コミュニティにこのガイドが紹介され、反応のなかに「複雑に書かないといけないし、単純に書こうとすると高くつく」という趣旨の指摘があった。文書の性格を正確に突いている面がある。あれは機能紹介ではなく症状の索引に近い。冒頭が「ツール呼び出しの間にテキストがほとんど無いならこの節へ」「エージェントループでターンあたりのツール呼び出しが一つだけならこの節へ」という形で並んでいる。

この形式が語っていることがひとつある。ここに書かれた変化はエラーを出さない。エラーを出すなら索引は要らなかった。代わりに画面が静かになる、ターンがひとつ増える、応答が詰まって読みにくくなる、という形で現れる。デプロイの数週間後に「最近ちょっと遅い気がする」として発見される種類だ。

Fable 5 世代そのものの背景はこのサイトに既にある。公開時点の仕様は第5世代モデル公開の解説、どんな作業に向くかは実戦活用事例、料金プランへの組み込みはMax・Team Premium 上限の件、アクセス制御をめぐる経緯は輸出規制による遮断とその解除にある。この記事はその上に載せる移行の角度の一本だ。

2番目の項目には静かに起きるという但し書きが付いており、別途見る価値がある。リクエストが対象モデルの読めないブロックを載せてくると、API はモデルに渡る前にそのブロックを捨てる。捨てられたブロックは input_tokens に計上されず課金もされない。問題は通知だ。thinking-binding-controls-2026-08-01 ベータヘッダを使えばトップレベルの input_transformations 配列にその事実が報告されるが、ヘッダが無ければ破棄は静かに起きる。つまりモデルを差し替えるルーターを置いているなら、推論が毎リクエスト捨てられていても請求書にも応答にも痕跡が出ない。

拒否の扱いは破壊的変更ではなく Fable 5 からそのまま引き継がれるが、移行のチェックリストには並べておくほうがよい。拒否されたリクエストはHTTP 200 で、stop_reason: "refusal" と発動したポリシー領域を示す stop_details を伴って返る。エラーコードではないので例外処理の経路に乗らず、応答本文を読む前に stop_reason を見るコードが必要になる。出力が出る前に届いた拒否は課金されず、Fable 5.1 に許可されたフォールバック先は Claude Opus 4.8 と Claude Opus 5 である。

effort - 移行で最初に触る値

effort は一つの応答にモデルが使うトークン量を調整する値だ。ここでよく誤解が生じるが、この値が調整するのは思考ブロックだけではない。公式ドキュメントは effort が応答のすべてのトークンに影響すると明記している。テキスト応答と説明、ツール呼び出しとその引数、そして思考である。だから思考を使わないリクエストでも effort は働き、低い effort ではツール呼び出し自体が少なく短くなる。

レベルは5つで、文書が付けている説明は次のとおりだ。

レベル文書の説明文書が挙げる用途
maxトークン消費に制約を置かない絶対的な最大能力可能なかぎり深い推論と最も徹底した分析を要する作業
xhigh長期的な作業のための拡張能力30分を超え、トークン予算が数百万単位のエージェント・コーディング作業
high高い能力。パラメータを設定しないのと同等複雑な推論、難しいコーディング問題、エージェント作業
medium適度なトークン節約を伴う均衡点速度・コスト・性能の均衡を要するエージェント作業
low最も効率的。大幅なトークン節約と一部の能力低下最高の速度と最低のコストを要する単純な作業、たとえばサブエージェント

文書が添える但し書きが重要だ。effort は厳密なトークン予算ではなく行動の合図だという点である。低いレベルでも十分に難しい問題ならモデルは依然として思考し、ただ同じ問題を高いレベルで扱うときより少なく思考する。だから low を「思考オフ」と読んではいけない。思考を切るスイッチはこのモデルにそもそも無い。

レベルを上げたとき増えるものと減るものも文書が分けて書いている。高いレベルではツール呼び出しの数が増え、行動の前に計画を説明し、変更の要約が詳しくなり、コードのコメントが増える。低いレベルでは複数の作業がより少ない呼び出しにまとまり、前置き無しに実行し、確認メッセージが短くなる。effort は品質のつまみというより「口数と手数の総量」のつまみに近い。UI がモデルの説明に依存していたなら、effort を下げた瞬間に画面も一緒に空く。

「medium ならより安く同等に」の正確な条件

ここが最も切り取られて引用される箇所だ。原文の構造はこうである。Fable 5.1 の能力向上はすべての effort レベルにわたって現れ、高い設定で最も大きい。そして medium では結果がおおむね Claude Fable 5 と同等になり、コストはより低い。したがって自前の評価が品質の維持を示す領域では medium か low に下げよ。

条件が三重に付いている。

  • 比較対象が旧世代である。medium が並ぶ相手は Fable 5.1 の high ではなくFable 5 だ。「5 の水準を保ってより安く」であって「5.1 をそのまま保ってより安く」ではない
  • 「おおむね」が付いている。同等宣言ではなく近似の表現だ。作業の性質によって分かれうる、と読むほうが安全である
  • 「自前の評価が品質の維持を示す領域では」という但し書きがある。確認の責任を使う側に渡した文だ。評価セット無しに下げるのは、この文が許した範囲ではない

同じ節に low についての文もある。低い effort の Fable 5.1 は作業あたりのコストで Claude Opus・Sonnet 系と張り合えるうえスコアはより高い場合が多いので、より小さいモデルをより高い effort で回す場面なら比較対象に入れてみよ、という趣旨だ。ただしこれはベンダーが自社のモデル群について行う自己評価であり、どのベンチマークをどの条件で測ったのかはこの文書に出てこない。だからこの文は「こういう主張があるので候補に入れてみよ」までしか役に立たず、それ以上は自分のワークロードで測るしかない。

実務的に low を検討するなら、付いてくる副作用をひとつ知っておく必要がある。low では Fable 5.1 は検索・検索拡張ツールを Fable 5 より呼ばず、記憶に頼って答える傾向がある。検索に依存する製品がコストを削ろうと low に下げれば、節約したトークンのぶんだけ鮮度が削れる。文書が示す対応は二つだ。当該のターンだけ effort を上げるか、変化の速い領域の名前は見覚えがあることと現状を知っていることは違うのでユーザーが書いた表記のまま検索せよ、という趣旨の文をシステムプロンプトに入れることである。

なぜスイープを最初からやり直すのか

この移行で最も安く手に入る教訓がここにある。ガイドはこう書く。Claude Fable 5 ですでにスイープを走らせていても再度走らせよ。effort のレベル名はモデルをまたぐと同じ量の思考に対応しない。

この文の意味は単純だが帰結は大きい。medium という名前は絶対的な目盛りではなく、そのモデルの中でのみ意味を持つ相対的な目盛りだということだ。Fable 5 の medium と Fable 5.1 の medium は同じ名前であって同じ量ではない。だから「前回 medium が最適だと結論した」という記録は、モデルが変わった瞬間に根拠としての寿命が尽きる。設定ファイルに残った値が依然として有効に見えるのが罠だ。壊れていないから見直さなくなる。

移行ガイドも同じことを別の角度から繰り返す。high から始めてスイープし、Fable 5 に合わせて調整した設定を引き継がず自前の評価セットで新たに回せ、というものだ。そして 5.1 の向上分が xhigh・max で最も大きい一方、そのレベルは思考時間と初回応答までの時間も一緒に伸ばすという但し書きを添える。得るものと失うものが同じつまみに結ばれているということだ。

Fable 5.1 にはセッションの途中で effort を変える方法もできた。テキストを持たず output_config だけを載せた role: "system" メッセージを差し込むと、次のユーザーターンから新しいレベルが適用され、プロンプトキャッシュが壊れない。ベータヘッダ mid-conversation-output-config-2026-07-01 が必要だ。

{"role": "system", "content": [], "output_config": {"effort": "low"}}

文書は Fable 5.1 でこの形をトップレベル値の変更より優先せよと勧める。理由は二つあり、二つ目が興味深い。トップレベル値を変えるとキャッシュが最初からやり直しになるだけでなく、モデルの誘導が効きにくくなるというのだ。先行する応答が以前のレベルで書かれているため、モデルがそのトーンとの一貫性を保とうとする傾向があるという説明である。会話の中でスタイルは慣性を持つ。

進捗更新が減った - そして取り戻す代償

実務で最初に体感される変化はおそらくこちらだ。Fable 5.1 のデフォルト挙動は、長いツール呼び出しのターンのあいだFable 5 よりユーザー向けテキストを少なく書くことで、この傾向は effort が高いほど、ツールの連鎖が長いほど顕著になる。ユーザーの目には、エージェントが数分ずつ静かになるか、最後のメッセージが作業全体ではなく最後の段階だけを要約しているように見える。

ここで順序を守ることが重要だ。文書が勧める最初の段階はプロンプトを直すことではない。

  1. クライアントが更新を受け取れているかを確認する。モデルがツール呼び出しの合間に書く短いメモ（何を見つけ、次に何をするか）は進捗更新用の thinking ブロックとして返る。ところが thinking.display のデフォルトが omitted なので、そのブロックは空で届く。そもそも要求していなかった可能性がある
  2. 表示設定を入れる。display: "updates"（ベータヘッダ thinking-display-updates-2026-08-18）にすれば、推論は隠したまま進捗更新だけをテキストで受け取れる。このとき中身が空でない thinking ブロックはそのままステータス行として描画すればよい。"summarized" は要約された推論と混ぜて返す
  3. 古い抑制文を探して消す。以前のモデルが作業中の更新を出しすぎていた頃に入れた「すべての発見は最終応答まで保留せよ」の類の文がシステムプロンプトに残っていることが多い。何かを足す前にこれを抜く
  4. それでも足りなければ、そこで初めて要求する。始める前に何をするかを一行、作業中の短い更新、そして最後のメッセージだけを見た読み手にも全体像が分かる自立した締めの要約を、という形でいつ・何を入れるかまで指定する

この順序を守るべき理由はトレードオフが実在するからだ。更新をもっとくれと要求すれば出力トークンが増えてターンが長くなる。表示設定を入れるだけで解決する問題だったなら、あるいは抑制文が残って生じた沈黙だったなら、その費用は払う必要がなかった。順序を飛ばして4番から始めれば、元々あった更新に要求した更新が重なって二度払うことになる。

関連する罠がもうひとつある。製品がツール出力を畳んだり隠したりする UI なら、その事実をモデルに伝える必要がある。そうしないとモデルはユーザーに「見せるために」コマンドを実行するが、その出力は画面に出ない。文書はこの案内をターンスコープのシステムメッセージ（clear_at: "next_user_message"）で伝えることを勧める。

独立したツール呼び出しを一つの応答にまとめる

Fable 5.1 はたいてい並列のツール呼び出しを期待どおりに出す。リクエストが複数の対象を明示的に指名すれば、それらを並列で呼ぶ。問題になる箇所は狭く具体的だ。次に必要な独立した呼び出しが明示的に要求されたのではなく、作業の性質上そこに含意されているとき、つまりカスタムのコーディングエージェントや bash・エディタのハーネス、コンピュータ操作のループでターンあたり一つずつ出ることがある。

文書がはっきりさせている点がある。これは回答の品質を落とさない。増えたターンごとにトークンと往復と実時間がかかる、というのが費用のすべてだ。だからこの項目は品質の後退としては捕まらず、請求書と体感速度にだけ現れる。対応は現在のリクエストの末尾に添える一文である。

{
  "role": "system",
  "clear_at": "next_user_message",
  "content": "First privately list what you need next; then request every item that doesn't depend on another's result in this one response."
}

ここで順序依存が隠れているときが問題になる。この文の防御線は「他の結果に依存しない項目だけ」という条件節ひとつだけで、その判断はモデルが行う。実際には順序があるのにスキーマ上には現れないツール——ロックを取ってから書くツール、先行する呼び出しが作ったファイルを読むツール、状態を変えるツールとその状態を照会するツール——が混じっていると、まとめる指示はその依存を踏み越えうる。防御はプロンプトではなくツール側に置くほうが確実だ。説明に前提条件を書き、順序が違う呼び出しはツールがエラーで返すようにする。

どこに置くかにも規則がある。ツール結果を返すたびに、そのユーザーメッセージの後ろへターンスコープのシステムメッセージとして新しい写しを足し、以前の写しはバイト単位でそのまま置いておく。後にユーザーメッセージができると API が以前の写しを消すのでモデルは最新のものだけを読み、消された写しは入力トークンを使わない。消したり書き換えたりするのは先行ターンを編集する行為であり、それが次節の主題だ。

会話履歴が追記専用になった

移行で実際にコードを直す必要が最も高い項目だ。規則は一行にまとまる。アシスタントのターンを API が返したそのまま、thinking ブロックまで含めて履歴に追記し、リクエストの間に先行ターンを編集しない。

強制の時点が明示されている。2026年8月31日以降に作成されたアカウントでは、Fable 5.1 の thinking ブロックはそれを生み出したまさにその会話でのみ有効だ。プレフィックス（システムプロンプト、ツール一覧、先行メッセージのいずれか）が変わった後に thinking ブロックを再生するリクエストは 400 で拒否され、エラーメッセージは当該ブロックが別の会話に結び付いているという趣旨になる。それ以前に作ったアカウントはまだ強制されないが、文書は今後のモデルが全アカウントにこの検査を強制すると見込まれるとして今からこのパターンを採用せよと書く。つまり今日通ることは明日の根拠にならない。

何が引っかかり何が引っかからないかは文書がリストで分けている。

以降の thinking ブロックを無効化するもの無効化しないもの
先行ターンを編集・並べ替え・削除しつつ後のターンを残す思考ブロックの塊を先頭から連続して取り除く
リクエストごとに先行ターンへリマインダやステータス行を注入し、次のリクエストで抜くサーバ側のコンパクション・コンテキスト編集が履歴を削ること
同じ会話の中でトップレベルの system や tools 配列を作り直すcache_control の印の位置を動かすこと
画像・文書の URL が後のリクエストで別のバイトを返すこと（URL ではなくバイトを見る）リクエストの間に effort を変えること

右列の一行目には条件が付いている。先頭以外の場所から thinking ブロックを抜くと、それ以降のすべての thinking ブロックが無効になる。「古いものから順に」が条件であって「何でも古いもの」ではない。真ん中を切り取る最適化はこのモデルでは成立しない。

自分のハーネスが既に何を編集しているかを突き止める方法も出ている。ベータヘッダ thinking-binding-controls-2026-08-01 とともに次の設定で1セッション回し、応答の input_transformations を記録すれば、何がどんな理由で落ちたかが列挙される。モデルを変えた後に出るモデル結合の不一致項目は正常で、プレフィックス結合の不一致項目が直すべきものだ。

"thinking": {
  "block_binding": { "prefix_mismatch_behavior": "drop_block" }
}

より単純な確認法も併記されている。普通の数ターンのあいだハーネスが実際に送るリクエストをそのまま捕まえて、連続する二つのリクエストが追記したターンを除いてバイト単位で同一かだけを見ればよい。コードを読むより速く、自分でも気づかずにやっていた編集を捕まえる。

長いセッションで何を残し何を捨てるか

履歴を追記専用にすると次の問いが続く。では長くなる会話はどう縮めるのか。文書の第一の答えは縮める仕事をサーバに任せよである。サーバ側のコンパクションとコンテキスト編集は編集に数えられない。検査が送ったとおりの会話を比較するからで、したがってそれらが取り除いたものは後の thinking ブロックを無効化しない。

クライアントでコンパクションを維持するなら、文書が認める形が三つある。

  • 単純コンパクション（推奨）。履歴全体を要約メッセージ一つと新しいユーザーターンでまるごと置き換え、残りは再生しない。thinking ブロックが持ち越されないので失敗するものが無く、モデルは圧縮された会話の上で新たに思考する。文書は Claude モデルがこの方式で長期作業を学習しており、大半のワークロードでより精緻な方式と同程度の性能を出すと書いている
  • 末尾保持コンパクション。要約の後ろに直近のターンを原文のまま残すなら、それらのターンから thinking と redacted_thinking ブロックを取り除かなければならない（テキストとツール呼び出しは残してよい）。その思考は履歴全体を前提に作られたもので、要約の後ろでは成立しないからだ
  • バックグラウンドコンパクション。要約を非同期で作って後から差し込む方式なら、その間にできたすべてのターンは差し替え以前の思考を抱えることになる。差し替え前に作られたブロックを載せたすべてのリクエストに drop_block を送るか、いっそ同期的に圧縮する

三つに共通して禁じられることがひとつある。トランスクリプトの真ん中から個々のターンを切り取らないこと。どのクライアント側の形でもこれは避けられないと文書は言い切る。

費用の判断には反転がひとつ付く。Fable 5.1 はキャッシュ読み取りが基本入力価格の0.025倍に下がったため、文書はコストを節約しようと早く圧縮する慣行がもはや最適でないかもしれないとして、圧縮の時点を遅らせて実験してみよと勧める。移行前に「長いセッションは早く切る」が正解だったなら、その判断の前提自体が変わったことになる。料金プランの上限をどう読み何が実際の費用かはAI 料金プランの利用上限表記を読む方法で別途扱い、エージェントに何を入れるかという設計の問題はコンテキストエンジニアリング実践ルールにある。

要約を自分で作るなら、ガイドがまるごと提供する要約指示がある。六つを必ず保存せよ、というのが趣旨だ。生じた問題とその処理、提起・試行・除外された選択肢とその理由、要請・決定・合意・除外・制約として確立されたものをそのままの表現で、今どこまで来ているかという現状、まだ開いているか約束されていること、そして再構成の難しい具体（名前・数値・日付・正確な文言・リンク）。そこに二つの声へ異なる重みを与えよという指示が付く。ユーザーが言ったことは本人の表現に近い形で守り、モデル自身の説明と推論は結論と成果物の水準までもっと圧縮してよい。

出力形式 - 古い抑制規則が逆に働く

出力形式の変化は方向が反転した点で特異だ。以前のモデルは対話で箇条書きと太字を使いすぎ、それを抑えるために書かれた反形式の規則が多くのプロンプトにそのまま残っている。ところが Fable 5.1 は逆側に傾く。太字を使うことが減り、見出し・リスト・引用符に手を伸ばしにくくなった。その上に古い抑制規則が載れば、内容が必要とする構造まで押さえつけられる。

文書の処方は抑制文を消すか、禁止ではなく条件に書き換えることだ。要請があるとき、または内容が多面的で明瞭さに役立つときはリストを使い、ユーザーが最小限の形式を明示的に求めるならそれに従い、対話的・個人的・感情的なやり取りでは平文を保つ、という形である。「使うな」から「こういうときに使え」へ移すのが要点だ。

散文の密度は別の項目だ。Fable 5.1 の文章は決まり文句が減り説明のない専門用語も減ったが、場合によっては Fable 5 より詰まっている。文が長くなり段落の切れ目が減る。ここに対して文書は興味深い処方を出す。「短く書け」ではなくアンチパターンを定義してやれというのだ。直截さの代わりに比喩と修辞を置く書き方がなぜ問題なのか——読み手をより働かせて書き手を見せびらかし、書き手が選んでいない含意を比喩が引き込む——を説明したうえで「字義どおりの表現があるならそれを使え」で閉じる形である。短い版も効くと添えてある。

要約で原文を引用表示なしに持ってくる傾向も形式の問題として分類されている。Fable 5.1 は文書を要約するとき、原文の一節を引用表示なしに再現する可能性が Fable 5 より高い。処方は規則ではなく完全な例ひとつだ。ユーザーの要請、正しい応答、そしてその応答がなぜ正しいのかを説明する文まで、まるごとシステムプロンプトに入れる。

文書が挙げる残りのデフォルト変化

残りの項目はそれぞれ短いが、どれが自分のワークロードに当たるかは先に眺めておくほうがよい。

  • 仕事が終わる前にターンが閉じる。複雑な非同期の作業でモデルが次にすべきことをやる代わりに述べたり、元の要請に既に含まれる段階について許可を尋ねたりする。文書はシステムプロンプトの二塊を一緒に入れることを勧めつつ、長さを削る必要があれば最初の塊だけでも効果の大半が残ると書く。なかでもユーザーがリアルタイムで見ていないという最初の一文が効果のかなりの部分を担う
  • 要請していない修正とテストが付いてくる。近くのコードを直したり、言及されていない挙動を拡張したり、変更規模に比べて多いテストファイルをコミットしたりしうる。何を外すべきかを明示すると、要請のない追加が大きく減り作業の成功率には測定可能な変化がなかったと文書は書く
  • 小さな変更にファイル全体を書き直す。成果物はたいてい同じだが、出力トークンと時間が余計にかかる。「ファイル編集に使うトークンは他の条件が同じなら最小化するほうがよい」という一文で、小・中規模の変更が Fable 5 の水準に戻る
  • xhigh・max で長い成果物が切れる。一つのリクエストが長い成果物を求めると、思考の中で下書きを書いておいて応答としてもう一度書くことが起きる。待ちが長くなり出力トークンが二倍かかる。第一の処方は推奨の出発点である high でこうしたリクエストを回すことで、あえて上げるなら max_tokens を応答の長さではなく思考と応答を合わせた大きさで取る
  • 安全分類器の誤検知。誤検知が出やすい状況を三つ文書が挙げる。コンパイルの可否を問う言い回し（代わりに「このプログラムにバグはあるか」と問う）、あまり知られていない言語、そしてツール出力に載って入ってくる base64 データだ。ソースコードから脆弱性を見つける作業自体は許可されている

移行手順 - A/B で測るには何を固定するか

ここまでの項目を一度に適用すると、何が何を変えたのか分からなくなる。移行を測定可能にする原則はひとつだ。一度に一つの軸だけ動かす。

段階変えるもの固定するもの測るもの
0何も。現行の Fable 5 で基準線を収集すべて品質スコア、ターン数、入出力トークン、初回応答までの遅延、総所要
1モデル ID だけ claude-fable-5-1 へプロンプト、effort、ツール定義、評価セット0段階と同じ5指標。ここで開く差が「デフォルト挙動の変化」だ
2effort だけを5レベルでスイーププロンプト、ツール定義、評価セットレベル別の品質とコスト・遅延。この表が運用レベルの根拠になる
3プロンプトを項目ごとに一つずつモデル、effort（2段階の結論）、評価セット項目別の効果。古い抑制文の除去が先で、新しい文の追加は後

最もよく破られるのは1段階だ。モデルを変えるついでにプロンプトも触るのが自然に感じられるからである。しかし1段階を純粋に守って初めて、文書が言うデフォルト挙動の変化が自分のワークロードで実際に現れるかが分かる。ある組織では進捗更新の減少は何の問題でもなく、別の組織ではそれが最大の課題になる。

測定指標を品質ひとつにしないことも同じくらい重要だ。文書が指摘する変化の多くは品質に現れないように設計された変化である。ツール呼び出しのまとめは「回答の品質に影響しない」と明記され、ファイル全体の書き直しも「成果物はたいてい同じ」と書かれている。品質スコアだけを見ればどちらも後退なしで通り、コストは静かに上がる。移行ガイドが再評価とあわせてコストと遅延の基準線を自分のワークロードで取り直せと念を押す理由だ。トークン数はおおむね据え置きだがキャッシュ読み取りの単価が変わったので、セッションの長さとキャッシュのヒット率が違うワークロードは同じ方向には動かない。

モデル ID を固定することの意味

再現性を重んじるチームはたいてい「別名ではなく日付付きのバージョン ID を使え」という規則を持っている。別名がある日静かに新しいスナップショットを指せば、昨日通っていた評価が今日壊れるからだ。この世代ではその規則の前提が変わった。

モデル一覧文書の脚注が明示している。すべての Claude モデル ID は固定されたスナップショットであり、4.6 世代から使われる日付の無い ID も同様である。4.6 より前のモデルで別名は日付付き ID へ解決される利便のためのポインタだったが、日付の無い ID はそれ自体が固定スナップショットであり、別名の行は同じ値を繰り返しているにすぎない。

したがって claude-fable-5-1 は「この時点の最新を指す名前」ではなく、それ自体がスナップショットだ。再現性のために日付付きの別 ID を探して使う必要はなく、探しても出てこない。同じ表の他の行には日付付きの形も依然として登場するので（Haiku 4.5 は API ID が日付付きで別名が日付の無い形だ）、ざっと見ると Fable 5.1 にも日付付きがありそうな印象を受けやすい。世代によって規則が違うという点がこの表の罠だ。

代わりに気を配るべきものが別にある。ID が固定でもモデルが永遠ではない。提供終了の約束は Anthropic 運営プラットフォーム基準で2027年9月1日より早くはない、というもので、Amazon Bedrock と Google Cloud は独自の日程を定める。同じ ID でもプラットフォームが違えば寿命が違う。そして再現性は ID だけで決まらない。このモデルは temperature・top_p・top_k にデフォルト以外の値を渡すと 400 なので、調整できるサンプリングのつまみがそもそも無い。実質的なバージョンの軸はeffort・システムプロンプト・ツール一覧・会話履歴の四つで、それらを固定しなければモデル ID を固定した値は大きくない。

まとめ

この移行の性質は一文に要約される。壊れないから危ない。モデル ID を変えればほとんどそのまま動き、だから見直す機会が生じない。そのあいだにプロンプトには存在理由を失った文が残り（古い反形式の規則、「最終応答まで保留せよ」の類の抑制文）、目につかないところでターン数と出力トークンが増える。

手をつける順序は文書が事実上定めている。組織設定（データ保持・サービスティア）が先、次にコードが会話履歴を編集していないかの確認、次に high から始める effort スイープ、そしてプロンプトの文を足すのは最後だ。そしてここに書いた値自体が長くはもたない。料金・ID・デフォルト値は2026年9月4日に確認したものであり、ベータヘッダの付いた機能——ターンスコープのシステムメッセージ、メッセージ単位の effort、進捗更新の表示、思考ブロックの結合制御——は定義上動きうる箇所だ。バージョン番号が小数点ひとつ上がったとき開き直すべきはリリースノートではなく自分のプロンプトである。
