はじめに: 22分間に起きたこと - npmエコシステムの時限爆弾

2026年5月、npmレジストリに登録されていた314の正規パッケージが、わずか22分間に637の悪意あるバージョンへ一斉に書き換えられた事件が報告されました。1分あたりに換算すると約29の悪意あるバージョンがpublishされた計算になります。これは人手では絶対に不可能な速度であり、事前に自動化されたスクリプトがメンテナの認証情報・トークン群を活用して一斉にpublishを実行した形と推定されます。22分という時間そのものが今回の事件の核心であり、JavaScriptエコシステムがメンテナ単一の認証情報という単一障害点にどれほど露出しているかを明確に示しています。

この事件は単発のインシデントではありません。本稿で整理するように、npmは2018年のevent-stream、2021年のua-parser-js、2022年のcolors/faker、2024年のlottiefiles事件まで、ほぼ毎年大規模なサプライチェーン事故を経験しており、毎回ほぼ同じ構造が繰り返されています。2026年の違いは、自動化された一斉配信の精度と影響範囲です。314のうち多くは他パッケージの依存関係に深く組み込まれており、名前を聞いたことがなくても影響を受けうるのが特徴です。

本稿はnews.hada.io 5月21日の5点記事を起点に、JavaScript開発チームが今日中に実行すべき緊急対応4つと長期防御戦略7つを、筆者の運用経験を基に整理します。事件の技術的詳細よりも、現場で今すぐ適用可能な行動に焦点を置きます。

事件の概要 - 何が、いつ、どのように起きたか

現在までに報告されている事件の輪郭を時系列で整理します。本稿はセキュリティアドバイザリを直訳せず、公開情報を筆者の視点で再構成します。

  • 時点: 2026年5月中旬、約22分間の短い時間枠。
  • 規模: 314のnpmパッケージにわたって計637の悪意あるバージョンをpublish。
  • 速度: 平均で1分あたり約29バージョンがpush。人手ではなく自動化スクリプトの仕業と確定。
  • 推定される侵入経路: 複数メンテナのnpm publishトークンまたは認証情報を事前収集 → 自動化バッチ配信。
  • 悪意あるコードの性格: postinstallスクリプトまたはビルド時の環境変数流出によるトークン・シークレット収集パターンが多数報告。
  • 検知・対応: セキュリティコミュニティとnpm側の迅速な遮断により、多くのバージョンが公開後数時間以内にunpublish。

注目すべきは「22分」という短い時間枠です。これは意図的な設計と考えられます。短すぎればセキュリティ監視がトリガされる前に終了し、適度に長ければ世界中の多数のCIパイプラインがその時間帯に新規バージョンを取得して適用するため、被害表面が自然に拡大します。22分はその均衡点に近い数字です。

攻撃メカニズムの分析 - 認証情報侵害 + 自動化バッチ配信

本事件の技術的核心は派手なゼロデイではなく、「盗んだ認証情報 + 自動化」という非常に平凡な組み合わせです。平凡であることこそが核心です。派手な脆弱性が必要ないほど、npmエコシステムの認証・公開モデルが単一障害点を抱えていることを意味するからです。

1) 認証情報収集フェーズ(事前作業)

攻撃者は事件発生以前の数か月間、様々なルートでnpmトークン・メールアドレス・OTP回避用セッションクッキーを収集していたと見られます。収集経路はフィッシング、メンテナPCのマルウェア感染、過去のデータ流出の再利用、.npmrcファイルの誤公開など多岐にわたります。2FAがあってもトークン自体が漏れれば迂回されるケースがあり、メンテナの多くが2FAを有効化していても攻撃自体は成功し得ます。

2) バッチ配信フェーズ(22分の時間枠)

収集した認証情報を使い、攻撃者は事前準備した悪意ある変種を314パッケージに一斉にpublishしました。npm publish APIを自動化で呼び出せば、1分あたり数十のpublishは十分可能です。22分で637バージョンが公開された点はこの推定と一致します。一斉配信の時刻をメンテナが同時に起きていない時間帯に合わせた可能性も高いです。

3) ペイロード実行フェーズ(被害者側)

悪意あるバージョンの多くはpostinstallフックで作動するか、ビルド時の環境変数を収集して外部サーバーに送信する形で報告されています。日本企業環境において、このフェーズの脅威は2つに分かれます。(a) ローカル開発PCの侵害: 開発者が無自覚にnpm installを実行してトークン・クッキーが流出。(b) CI/CD侵害: GitHub Actionsや社内Jenkinsでビルド時のシークレットが外部流出。CIトークンは権限範囲が広いケースが多く、後者の方が筆者の観点ではより危険です。

類似事件の歴史 - 同じ構造が繰り返される

npmのサプライチェーン攻撃は今回が初めてではありません。筆者の記憶に残る主要事件を整理します。

  • 2018 event-stream: メンテナ交代直後に新メンテナが悪意あるペイロードを差し込み、ビットコインウォレットライブラリに影響。「信頼の譲渡」が単一障害点であることを初めて広く知らしめた事件。
  • 2021 ua-parser-js: メンテナアカウント侵害後の悪意あるバージョン配信。ダウンロード数が極めて多いパッケージのため影響範囲が広範囲。
  • 2022 colors/faker: メンテナ本人が意図的にコードを破壊した事件。「信頼は自発的な協力」であることを再確認させた。
  • 2023 typosquattingの多発: 人気パッケージ名と1文字違いの悪意あるパッケージが大量登録。
  • 2024 lottiefilesなど: SDKパッケージの侵害を通じてユーザートークン・ウォレット情報を窃取しようとする試み。
  • 2026年5月 314パッケージ一斉侵害: 本事件。規模と速度ともに新たな段階。

このリストのパターンは明確です。毎回「メンテナの認証情報」が破られ、毎回同じ方法でnpmインフラがpublishを許可します。事件ごとに臨時対応はあるものの、構造的な解決策の導入は遅いままです。provenance・sigstoreのような長期的解決策は登場していますが、採用率は依然として低い水準です。

なぜnpmは繰り返し攻撃されるのか - 構造的脆弱性5つ

1) 単一メンテナモデル

npmの大半のパッケージは1~2人のメンテナで運営されています。この1人の認証情報が破られれば、数百万ダウンロード級のパッケージがそのまま露出します。PyPI、crates.ioなど他のレジストリも似た構造ですが、npmは平均依存深度が最も深いため影響の増幅が大きいです。

2) 深い依存関係ツリー

あなたのプロジェクトが直接依存するパッケージが10個でも、そのツリーを展開すると実際にインストールされるパッケージは通常1,000個以上になります。あなたが名前すら聞いたことのないパッケージが、あなたのビルド環境で任意のコードを実行できるという意味です。

3) postinstallフックの任意コード実行

npmはpostinstall時に任意スクリプトの実行を許可しています。正規用途(ネイティブビルドなど)もありますが、攻撃者にとってはペイロード自動実行の経路になります。他のパッケージマネージャの一部は、このフックをデフォルトで無効化しています。

4) メンテナ信頼譲渡の無防備さ

メンテナが他人にパッケージを引き渡す手順は、事実上メール一通です。新メンテナの身元・経歴・悪意の有無に対する検証が弱く、ユーザーが自動で知る手段もありません。

5) provenance採用の遅い速度

npm provenanceは2023年に導入されましたが、採用率は人気パッケージ基準でも一桁から二桁前半に留まっているとされます。全員が採用すれば今回のような事件の表面は大きく縮みますが、メンテナ側の導入動機不足がボトルネックです。

今日中に実行すべき緊急対応4つ

本セクションは本稿で最も実務に近い部分です。日本のJavaScript開発チームが今日(遅くとも今週)中に処理すべき4つの作業です。

1) 疑わしいパッケージの即時確認 - npm audit

まず全アクティブプロジェクトで以下を実行します。

npm audit --audit-level=high
npm audit signatures   # provenance/署名検証
npm outdated

npm audit signaturesは意外に知られていないコマンドで、パッケージのnpm署名・provenanceの有効性を検証します。事件発生時点前後24~48時間以内に受け取ったパッケージがある場合、このコマンドで再度確認します。

2) lockファイル変更履歴の検証

package-lock.jsonまたはyarn.lockの最近の変更をgit履歴で確認します。

git log --since="2026-05-20" -- package-lock.json
git diff HEAD~5 -- package-lock.json | grep -E "^\+.*\"version\""

疑わしい時点にlockファイルが変更されていれば、そのバージョンが実際に正規かをnpm公式アドバイザリと照合します。開発者が無自覚にnpm install後にlockファイルも一緒にコミットするケースがあるため、PR単位の点検が必要です。

3) ビルドキャッシュの即時無効化

ローカル・CI・社内npmミラーにキャッシュされた悪意あるバージョンを削除します。

npm cache clean --force
rm -rf node_modules
npm ci   # frozen lockfileベースのクリーン再インストール

GitHub Actionsのactions/cache、GitLab CI cache、社内のNexus/Verdaccioミラーも同時に無効化します。キャッシュに悪意あるバージョンが残ったままでは緊急対応の意味がなくなります。

4) 露出可能性のあるトークン・シークレットの即時ローテーション

postinstallペイロードの主標的は環境変数・トークン・クッキーです。以下の項目を5月21日以降に一度でもビルドに露出していれば、ローテーションします。

  • npm publishトークン(CIで使用中の場合は最優先)
  • GitHub PAT・Actions OIDCトークン
  • AWS・GCP・Azureアクセスキー
  • Slack・Discord WebhookのURL
  • DB接続文字列・内部APIシークレット

ローテーション作業は面倒ですが、トークン1個のコストは侵害1件のコストに比べれば無視できる規模です。ビルド環境に一度でも平文で置いたシークレットがあれば、この機会にすべて再発行してください。

長期防御戦略7つ - 次の事件を防ぐシステム

1) npm provenanceの利用

自分でnpmにパッケージを公開している場合は、今すぐprovenanceを有効化します。GitHub Actions基準でpermissions: id-token: write追加とnpm publish --provenanceの1行で有効化されます。利用者側ではnpm audit signaturesでprovenanceを強制できます。

2) Frozen lockfileの強制(--frozen-lockfile / npm ci)

ローカルでnpm installを使っていても、CIでは必ずnpm ciまたはyarn install --frozen-lockfileを強制します。lockファイルと一致しなければビルドが失敗するゲートを設けるのが核心です。これ一つだけで「夜間に誰かが新規バージョンをpublishしてCIがそれを取得する」経路がほぼ遮断されます。

3) SBOMの生成・管理

ビルドごとにSBOM(Software Bill of Materials)を自動生成して保存します。形式はCycloneDXまたはSPDX。cyclonedx-bomまたは@cyclonedx/cyclonedx-npmのようなツールで1分以内に導入可能です。SBOMがあれば、次の事件が起きた時に「私たちはそのパッケージを使っているか」に5分で答えられます。

4) Dependabot / Renovateの導入

依存関係の更新を人の意志ではなく自動PRで行います。ただし自動マージは絶対に有効化しません。PRを作成すれば人がレビューする手続きが強制されます。レビュー時にnpm viewで新バージョンのメンテナ・publish時刻・ダウンロード推移を一度確認します。

5) 定期的な依存関係監査サイクル

四半期に一度、依存関係監査ミーティングを設けます。議題は3つです。(a) 使っていないパッケージの削除、(b) deprecatedパッケージの置換、(c) メンテナ活動が止まったパッケージのfork・置換の検討。筆者の経験上、この1時間が1年後の事故対応時間を100倍短縮します。

6) ミニマル依存関係ポリシー

「この機能のために100行のパッケージを追加する価値があるか」をPRレビュー時の必須質問にします。座標ライブラリ・文字列ユーティリティ・日付フォーマットのような小さな機能は、自前コード10~30行で十分なケースが多いです。依存関係が少ないほど攻撃表面は小さくなります。

7) 行為ベーススキャナ(Socket.dev、Phylumなど)の導入

従来のnpm auditは既知のアドバイザリと照合しますが、Socket.dev・Phylumのようなツールはパッケージコードの疑わしい行為(ネットワーク呼び出し、eval、postinstallパターンなど)を行動ベースで検知します。未知の新規侵害を捕捉する可能性が高まります。CIにPRコメント形式で統合するのが日本のチーム基準で最も滑らかな導入方法です。

CI/CDパイプライン強化 - GitHub Actionsの例

上記7戦略を実際のGitHub Actionsワークフローにまとめると以下のような形になります。核となるゲートのみを抜粋した例です。

name: secure-build
on: [push, pull_request]
permissions:
  contents: read
  id-token: write
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      # 1) frozen lockfile - lockとの不一致で即座に失敗
      - run: npm ci

      # 2) auditゲート
      - run: npm audit --audit-level=high
      - run: npm audit signatures

      # 3) SBOM生成
      - run: npx @cyclonedx/cyclonedx-npm --output-file sbom.json
      - uses: actions/upload-artifact@v4
        with:
          name: sbom
          path: sbom.json

      # 4) 行為ベーススキャン(Socket.devの例)
      # - uses: socket-security/socket-cli-action@v1

      - run: npm test
      - run: npm run build

このワークフローの核心は「1ステップでも失敗するとビルド自体が中断」という点です。緊急対応を人の意志に委ねず、CIゲートとしてシステム化することが本稿の最後のキーメッセージです。

監視ツール比較 - Snyk、Socket.dev、Phylum、npm audit

実務でよく比較されるツールを筆者の視点で整理します。

ツール検知方式強み弱み
npm audit既知アドバイザリ照合無料・標準搭載ゼロデイ・行為ベース検知が弱い
Snykアドバイザリ+ライセンス+一部行為UI・レポート優秀、企業向け機能豊富有料プランで本格機能
Socket.dev行為ベース(eval/postinstall/ネットワーク)未知の侵害検知、PRコメントのUX良好偽陽性が一部、日本事例化は少ない
Phylum行為ベース+メンテナ評判メンテナ身元・履歴分析導入カーブがやや急
GitHub Dependabotアドバイザリ+自動PRGitHub統合・無料検知より更新自動化に近い

日本のチームへの推奨構成は次の通りです。(1) ベースはnpm audit + Dependabot(無料、即時導入)。(2) その上にSocket.devまたはSnykのいずれかをPRレビュー段階の補助ゲートとして。(3) 時間に余裕があればPhylumでメンテナ評判まで見るという3段構成を推奨します。

日本企業・スタートアップ環境での適用

上記戦略を日本の環境に移す際、筆者がよく出会う摩擦ポイントを整理します。

  • スタートアップ: セキュリティ人員がいない場合が多い。無料ツール(npm audit、Dependabot、Socket.devの無料枠)だけでも80%カバーできるので、まずは導入から。完璧を追わず「やっていなかったことをやる」を目標に。
  • 中堅・大企業: 社内npmミラー(Nexus、Verdaccio)があれば、ミラー自体にallowlist・blocklistを適用。緊急事件時にミラーで遮断すれば全開発者に同時に効きます。
  • 金融・公共: ネットワーク分離環境でもnpmミラー経由で外部パッケージを取り込む経路は同じ。SBOM・署名検証を社内標準にするのが効果的。
  • フリーランス・1人開発: 自分のPCがそのままインフラ。トークンを平文で.envに置く習慣を即座にやめ、1Password CLI・dopplerのようなシークレットマネージャを導入。

開発者個人の責任の限界と、エコシステムの責任

本稿で整理した11個(緊急4+長期7)をすべて実行しても、サプライチェーン攻撃を100%は防げません。それが現実です。個人・チーム単位の努力には明確な限界があり、その限界を超えるのはエコシステムレベルの変化です。

筆者が考えるエコシステム責任は3つです。(1) npm Inc.(GitHub)によるメンテナセキュリティ認証の強化 - WebAuthn・ハードウェアキー義務化。(2) 人気パッケージを対象とするprovenance採用率の引き上げのためのインセンティブ。(3) postinstallフックのデフォルト無効化オプション提供。これらは個人の努力では解決できない部分で、npm・GitHubの政策変更が必要です。

2026年下半期サプライチェーンセキュリティのトレンド - 筆者の予測

筆者が予想する2026年下半期のサプライチェーンセキュリティの流れは以下の通りです。

  • provenance採用の加速: 人気パッケージメンテナの自発的導入が事件直後に増える可能性。採用率が一桁から二桁中盤へ上昇する見込み。
  • 行為ベーススキャナの標準化: Socket.dev・Phylumの導入が無料枠を中心に拡大。
  • SBOM義務化の流れ: 米国EO 14028の流れの影響で、日本の公共・金融入札でSBOM要求が増える可能性。
  • AIベースのコードレビュー+依存関係分析の結合: PRレビュー時にAIが新規依存関係のリスクを自然言語でコメントする流れ。
  • npm以外のレジストリ選択肢の検討増加: deno、jsr、bunの独自レジストリへの関心増。ただし短期でnpmを置き換えるのは困難。

結論 + チェックリスト15項目

本稿の核心を一言でまとめるとこうです。サプライチェーンセキュリティはツールではなくシステムであり、システムは今日から始められる小さなゲートの積み重ねです。22分は次回さらに短くなります。次の22分を止めるのは、あなたのチームの緊急4つと長期7つのシステム化です。

最後に筆者が使っている15項目のチェックリストを共有します。印刷して机の横に貼り、1行ずつ処理してください。

  1. 全アクティブプロジェクトでnpm audit --audit-level=highを実行
  2. npm audit signaturesでprovenance/署名を点検
  3. 5月20~22日のlockファイル変更履歴をgitで確認
  4. npmキャッシュ・CIキャッシュ・社内ミラーキャッシュをすべて無効化
  5. 5月21日以降のビルドに露出した全トークン・シークレットをローテーション
  6. npm publishトークンの権限範囲を最小化+有効期限設定
  7. CIでnpm ci / --frozen-lockfileを強制
  8. CIでnpm auditをゲート化(高リスク検出時に失敗)
  9. SBOM生成ワークフローを導入(CycloneDX推奨)
  10. DependabotまたはRenovateを有効化(自動マージは無効)
  11. 四半期に1回の依存関係監査ミーティングをカレンダー登録
  12. 自分が公開しているパッケージにnpm provenanceを有効化
  13. Socket.devまたはSnykのいずれかを無料枠で導入
  14. postinstallフックを使うパッケージのホワイトリスト見直し
  15. 社内npmミラー運用時にallowlist/blocklistポリシーを策定
