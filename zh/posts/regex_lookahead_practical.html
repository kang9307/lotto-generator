前瞻只看位置 - 用零宽度解决的正则表达式问题

正因为不进入匹配结果才做得到的事 - 叠加条件、只保留边界的替换、重叠匹配，以及在韩文里最先崩掉的地方

2026-08-11 开发/基础设施

引言：条件必须加上，却不想让它进入结果

要从日志里只挑出含 ERROR 的行，同时排除含 timeout 的行。于是用管道接上 grep。接下来，只需要那一行里 host= 后面的值。再接一个管道，用 sed 把前面部分切掉。等管道接到四个左右，这条命令再读一遍也看不出它到底在做什么了。

在替换里问题更加露骨。要把 password=hunter2 改成 password=***。如果不把 password= 一起匹配进来，就没有办法单独挑出 hunter2；可一旦匹配进来，替换的时候它也会跟着一起消失。于是只好用捕获组抓住它，再用 $1 贴回去。键只有一个时还能忍，变成三个就开始数编号了。

这两种情形有一个共同点。都存在作为条件需要、作为结果却不需要的部分。环视正是为这个位置而存在的。它检查条件，但不把它包含进匹配结果，也不移动下一次匹配开始的位置。这个性质被称为零宽度（zero-width）。

大多数讲解介绍完四个符号就结束了。可是在实务中真正产生价值的部分不是符号，而是因为宽度为 0 而派生出来的那些结果。条件可以在同一个位置叠加任意多个，可以在不碰边界的情况下只改值，可以数出彼此重叠的匹配。这篇文章把篇幅花在那一侧。

运行环境。下面的输出基于 Windows 10 Pro 上的 Node.js v22.16.0、Python 3.13.3 与 3.11.9、Perl 5.38.2、GNU grep 3.0。含韩文的模式如果作为 shell 参数传入，转义会被剥掉，所以全部保存为脚本文件后再执行。

范围。各引擎语法产生分歧的整体问题，在随处可用的正则表达式里讨论。这里只简短地点一下后顾这一处。韩文正则的陷阱本身以韩文正则陷阱为主场，本文只看环视这个工具在韩语里从哪里开始空转。

1. 零宽度 - 检查了，但不吃掉

用嘴说太抽象，量一量长度就明白了。

A1 match = "foo" | length = 3 | index = 0
A2 lastIndex after exec(g): 3
A3 replace = Xbar
A4 without lookahead = X
A5 consuming = "foobar"

模式是 /foo(?=bar)/，输入是 foobar。明明确实检查过后面是不是跟着 bar，匹配字符串却只有 foo 三个字符。更重要的是 lastIndex。如果消耗掉了应该是 6，实际却是 3。这意味着光标停在 bar 前面，下一次匹配从那里重新开始。

所以替换结果变成了 Xbar（A3）。被当作条件使用的 bar 原样留在了原文里。如果换成消耗型的模式 /foobar/ 做同样的替换，就只剩下 X（A4）。不需要为了把条件里用到的部分在结果中复原而动用捕获组，这就是第一个实用价值。

宽度为 0 这句话是字面意义上的。只由环视构成的模式会匹配到空字符串。

C1 split by zero-width = [ 'one', 'Two', 'Three' ]
C2 empty match array = [ '' ]
C3 empty match str  = ""

'abc'.match(/(?=b)/) 的匹配字符串是长度为 0 的空字符串。只有位置信息，没有内容。'oneTwoThree'.split(/(?=[A-Z])/) 能在一个字符都不丢的情况下切成三段，也是同样的道理。因为不消耗分隔符，所以大写字母原样保留。

2. 四种环视，以及它们所站的位置

符号有四个，轴却只有两条。看哪一侧（前／后）与必须存在还是必须不存在（肯定／否定）的组合。

符号名称观察方向成功条件
(?=...)肯定前瞻当前位置的右侧右侧以 ... 开头
(?!...)否定前瞻当前位置的右侧右侧不以 ... 开头
(?<=...)肯定后顾当前位置的左侧左侧以 ... 结尾
(?<!...)否定后顾当前位置的左侧左侧不以 ... 结尾

把这四个都套到同一个字符串上，各自挑出什么就一目了然了。

입력: price: 100USD, 200EUR, 300USD

B1 /\d+(?=USD)/g       = [ '100', '300' ]
B2 /\d+(?!\d)(?!USD)/g = [ '200' ]
B3 /(?<=price: )\d+/g   = [ '100' ]

입력: a1 b2 c3
B4 /(?<![ab])\d/g      = [ '3' ]

2.1 否定前瞻被回溯攻破的位置

B2 里为什么要多挂一个 (?!\d)，就是这一节的核心。去掉它，只写 /\d+(?!USD)/g 会变成这样。

입력: 100USD 200EUR

K1 /\d+(?!USD)/g       = [ '10', '200' ]
K2 /\d+(?!\d)(?!USD)/g = [ '200' ]
K4 첫 매치 = "10"

本想过滤掉带着 USD 的 100，模式却返回了 10。引擎先用 \d+ 抓住 100，检查 (?!USD) 失败之后并不放弃，而是一边缩短消耗长度，一边寻找绕开条件的办法。缩到 10 时，它右边是 0USD，而这并不以 USD 开头，于是否定条件就通过了。

否定前瞻只是对那个位置本身的判定，并不表示「这一整块数字后面没有 USD」。所以必须用 (?!\d) 把右端钉死，消掉 \d+ 变短的余地。加否定条件时，先确认匹配的边界是否被固定住了。这是环视里最常犯的逻辑错误。

2.2 捕获只在肯定一侧存活

L1 /(?!(\d+))X/ 의 그룹 1 = undefined
L2 /(?=(\d+))\d+/ 의 그룹 1 = 123 | 전체 매치 = 123

否定前瞻内部的分组不会留下值。否定条件要求内部匹配失败才算成功，所以在成功的那一刻，分组里没有可填的东西。反过来，肯定前瞻内部的分组会被正常捕获。第 5 节的重叠匹配就建立在这个性质之上。

3. 「有 A 而没有 B 的行」 - 把条件堆在同一个位置

这就是引言里的日志问题。环视不移动位置，所以接上多少个，就都会在同一个点完成判定。意思是行首可以叠加任意多个条件。

$ grep -P '^(?=.*ERROR)(?!.*timeout)' app.log
2026-08-11 10:00:01 ERROR db connect failed host=db01 retry=1
2026-08-11 10:00:04 ERROR auth rejected user=svc_batch
2026-08-11 10:00:06 ERROR db connect failed host=db02 retry=2

ERROR upstream timeout 那一行栽在第二个条件上，INFO timeout tuning applied 那一行栽在第一个条件上。想再加一个条件，也只要再写一个就行。

D2 /^(?=.*ERROR)(?!.*timeout)(?=.*(db|auth))/ 매치 = 2건
D3 순서를 바꿔도 같은 결과 = true
D4 소비형 /ERROR.*db/ : 'db ERROR' → false, 'ERROR db' → true

D3 是这一节的要点。条件之间没有顺序依赖。前瞻不移动光标，所以检查完第一个之后，光标依然停在行首。因此换个顺序写结果也一样，以后要追加条件时，也不必纠结该插在哪里。

换成消耗型的模式做同样的事，这份自由就消失了（D4）。/ERROR.*db/ 只在文档中 ERROR 出现得比 db 早的时候才命中。一旦日志格式变化、字段顺序颠倒，它就会悄无声息地什么都抓不到。

3.1 过滤与提取一次搞定

把条件组合和 \K 接在一起，四个管道的命令就折叠成一条。

$ grep -oP '^(?=.*ERROR)(?!.*timeout).*?host=\K\S+' app.log
db01
db02

$ grep -oP '(?<=retry=)\d+' app.log
1
2

$ grep -oP '\w+(?==)' app.log | sort -u
host pool retry user

最后那条只抽取等号前面的键名。(?==) 看着陌生，含义却是「后面跟着等号的位置」，而等号本身不被消耗，所以不会出现在输出里。

4. 在替换里只抓边界

这是要改值、却必须留下键的替换。用后顾把左边界「只做检查」，就不需要捕获组了。

입력: user=admin&password=hunter2&host=db01&token=abc123def

E1 /(?<=password=)[^&]+/g  → '***'
   user=admin&password=***&host=db01&token=abc123def
E2 /(password=)[^&]+/g     → '$1***'
   user=admin&password=***&host=db01&token=abc123def
E3 /(?<=(?:password|token)=)[^&]+/g → '***'
   user=admin&password=***&host=db01&token=***

E1 和 E2 结果相同。也就是说捕获组同样能办到，单看这里只是口味问题。差别出现在 E3。哪怕键增加到多个，替换式依然是 *** 这一小块。若用捕获的写法，就得一边数分组编号一边管理 $1，而且以后一旦多插入一个分组，编号就会错位，悄悄地坏掉。

4.1 完全不做消耗的替换

更极端的一侧是匹配字符串为空字符串的替换。什么都不删除，只往位置上插入。

F1 '1234567'      .replace(/\B(?=(\d{3})+(?!\d))/g, ',') = 1,234,567
F2 '999'          .replace(같은 패턴, ',')              = 999
F3 '1000'         .replace(같은 패턴, ',')              = 1,000
F4 '123456789012' .replace(같은 패턴, ',')              = 123,456,789,012

V1 'oneTwoThreeID'  .replace(/(?<=[a-z])(?=[A-Z])/g, '_') = one_two_three_id
V2 'HTTPServerError'.replace(/(?<=[A-Z])(?=[A-Z][a-z])/g, '_') = HTTP_ServerError

把千位分隔符的模式拆开看，条件有三个。不是单词边界（\B，防止开头被加上逗号）、右边接着一组三位数、那一组后面不再有数字。三者都是零宽度，所以匹配字符串是空字符串，替换就成了纯粹的插入。

V2 处理的是缩写。把 HTTPServerError 在每个大写字母处切开，会变成 H_T_T_P_...。把条件收窄成「位于大写字母之后，且大写字母后面跟着小写字母的位置」，缩写那一块就会连在一起，只在单词边界处切开。这种同时看左边和右边的条件，用消耗型模式很难表达。

4.2 跳过已经处理过的地方

입력: see http://a.example and <a href="http://b.example">b</a>
패턴: /(?<!href=")http:\/\/\S+?(?=[\s<])/g → '[LINK]'
결과: see [LINK] and <a href="http://b.example">b</a>

只把裸 URL 变成链接、已经在标签内部的就放着不动，这是很常见的需求。用否定后顾要求它不在 href=" 之后，用前瞻抓住右边界但不消耗那个字符。要是消耗了，结果里的空白或尖括号就会消失。

4.3 掩码

$ echo '카드 4111111111111111 로 결제' | perl -pe 's/\d(?=\d{4})/*/g'
카드 ************1111 로 결제

只把「后面还剩四个以上数字的数字」换成星号。既不数位数，也不计算长度。条件是用位置来表达的，所以卡号长度是十六位还是十四位，同一个模式都照样工作。

5. 重叠匹配 - 正因为零宽度才办得到

正则引擎一旦找到匹配，就把光标移到它的末尾。因此它找不到相互重叠的匹配。

H1 'AAAA'.match(/AA/g)                    = [ 'AA', 'AA' ]
H2 [...'AAAA'.matchAll(/(?=(AA))/g)]      = [ 'AA', 'AA', 'AA' ]
H3 그 위치                                 = [ 0, 1, 2 ]

H4 'ABABABA'.match(/ABA/g)                = [ 'ABA', 'ABA' ]
H5 [...'ABABABA'.matchAll(/(?=(ABA))/g)]  = 위치 [ 0, 2, 4 ]

AAAA 里含有的 AA 在位置 0、1、2 上共三个。可是消耗型模式只数出两个。因为在 0 处找到之后光标跳到 2，把位置 1 跨过去了。

(?=(AA)) 绕开了这个问题。外层匹配是零宽度，光标每次只前进一格，而真正想找的字符串则从前瞻内部的捕获组里取出来。2.2 节看到的「肯定一侧的捕获会存活」，在这里派上了用场。

5.1 零宽度匹配的死循环

这个技法附带着一个陷阱。直接跑 exec 的话，光标不前进，循环不会停止。

const r = /(?=a)/g;
let m;
while ((m = r.exec('aaa')) !== null) {
  // ...
  if (m.index === r.lastIndex) r.lastIndex++;   // 이 줄이 없으면 끝나지 않는다
}
M1 결과 = 3
M2 [...'aaa'.matchAll(/(?=a)/g)].length = 3

匹配长度为 0 时 lastIndex 原地不动，于是永远在同一个位置反复查找。matchAll 和 replace(/.../g) 在内部替你做了这件事，所以是安全的。不要对零宽度模式直接写 exec 循环，用 matchAll。这个陷阱在别的语言里也一样存在，Perl 里同样需要手动推动 pos()。

$ echo 'AAAA' | grep -oP '(?=(AA))'
(출력 없음 - 매치가 빈 문자열이라 -o 가 찍을 것이 없다)

$ echo 'AAAA' | perl -ne 'while (/(?=(AA))/g) { print "$1 at ", pos(), "\n"; pos() = pos() + 1 }'
AA at 0
AA at 1
AA at 2

6. 自己定义单词边界

\b 也是零宽度条件。只不过单词字符的定义是固定的，一旦这个定义和我的数据对不上，就无从下手。环视让你可以自己把那个定义写出来。

模式匹配数抓到的东西
/cat\b/g3cat、cat-x 的前半、concat 的后半
/cat(?!s)/g4上面三个 + catx 的前半
/cat(?![a-z])/g3cat、cat-x、concat
/(?<![a-z])cat(?![a-z])/g2只有 cat、cat-x

输入是 cat cats catx cat-x concat。\b 把连字符视为边界，所以抓住了 cat-x，也抓住了 concat 的尾巴。如果那不是想要的行为，用否定环视把两侧亲手堵住是唯一的办法。

在韩文里，这个差别就不是口味问题，而是决定能不能工作了。

입력: 고양이 고양이들 왕고양이

T6 /\b고양이\b/g                    = null
T7 /(?<![가-힣])고양이(?![가-힣])/g = [ '고양이' ]

\b 一个都抓不到。\b 的单词字符定义是 [A-Za-z0-9_]，韩文压根就不是单词字符，而空白与 고 之间两侧都是非单词字符，边界因此不成立。没有异常也没有警告，直接返回 null。在韩语文本里需要按词检索时，就得抛开 \b，用环视亲手定义边界。

7. 密码规则 - 能做到的和做不到的

这是前瞻被复制粘贴得最广的用途。把「是否混合了多种字符类型」堆成好几个条件。

/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9]).{12,}$/

PASS | Passw0rd!1234
FAIL | passw0rd!1234     (대문자 없음)
FAIL | PASSW0RD!1234     (소문자 없음)
PASS | Password!1234
PASS | Pw0!aaaaaaaaaaaa

它按预期工作了。可是真正用起来时会卡住的限制有三个，而且三个都不是前瞻的错，而是因为想用这个工具去做的事，原本就不是正则的活。

7.1 它无法告诉你是在哪里没通过

结果不是真就是假，只有一个。没有信息可以告诉用户「缺了大写字母和特殊字符，还需要再多四个字符」。把条件拆开，这份信息就出现了。

규칙을 조각으로 나눠 각각 판정:
I7 'passw0rd' 미충족 = 대문자, 특수문자, 12자 이상

把所有条件堆进一条正则，是一种丢弃检查结果的设计。如果只需要判定，比如服务器端的最终确认，那一行更好；如果是要向用户做提示的界面，那拆开更好。若两处都要用，就把一份片段数组当作唯一的事实来源，需要时再拼起来，这样才不会出现偏差。

7.2 数长度的单位和人不一样

J1 'Passw0rdAB😀'  사람이 센 글자 = 11 | .{12,} 가 센 것 = 12 | 통과 = true
J2 'Passw0rdABc!'  사람이 센 글자 = 12 | .{12,} 가 센 것 = 12 | 통과 = true
J3 이모지가 특수문자 조건을 충족시킨다 = true
J5 같은 J1 입력에 u 플래그를 붙이면      = false

问题出在 J1。用户输入了十一个字符，却通过了「十二个字符以上」的规则。因为 JavaScript 的 . 数的是 UTF-16 码元，一个表情符号被算成了两个。附带地，表情符号的一半还落进了 [^A-Za-z0-9]，连特殊字符条件也一并满足了。加上 u 标志就变成按码点计数，一切恢复正常（J5）。

韩文则会因规范化形式而分道扬镳。

K1 '비밀번호입니다'  NFC 길이 = 7 | NFD 길이 = 17
K2 /^.{12,}$/       NFC = false | NFD = true

屏幕上看起来一模一样的字符串，会因为以哪种形式进来，而有时通过同一条规则、有时被拒绝。对策是在输入边界处先跑一遍 normalize('NFC')，这个问题的全貌整理在韩文正则陷阱那一边。

7.3 通过规则并不等于是好密码

I2 통과 = true  | Password1234!
I3 통과 = true  | Qwerty12345!
I4 통과 = false | correct horse battery staple   (28자)

最常见泄露清单上的前排选手通过了，而二十八个字符的句子被拒绝了。字符构成规则不是量熵的工具，而是量形状的工具。用前瞻堆得再精巧，这道鸿沟也不会缩小。把长度下限提高、再接上泄露清单比对，实效要大得多。先决定放行什么形状，这种思路本身，和禁止清单永远慢一步里讨论的允许清单是同一条脉络。

8. 后顾与变长 - 引擎分道扬镳的那一点

前瞻在稍微像样点的回溯引擎里都有。产生分歧的只有一件事：后顾的长度是否必须固定。原因在实现上。向前看时，从当前位置往右读下去就行；而向后看时，必须先知道该从哪里开始读。长度固定的话，往左退相应的距离即可；长度可变的话，就得把要退的距离一个一个试过去。

(?<=ab|abc)\d       → 'xab7 yabc8' 에서 7, 8
(?<=a{1,3})\d       → 'aaa9' 에서 9

线画在了三个不同的地方。Python 连长度不同的交替都拒绝。Perl 和 PCRE 有界就接受，遇到无限量词才停下。JavaScript 全盘接受。若考虑可移植性，后顾只用定长的写法是安全的下限。

8.1 需要变长时的替代方案

  • 使用 \K。PCRE 和 Perl 里有一个「到这里为止从匹配中排除」的标记。password=\K[^&]+ 会先消耗 password=，再把它从结果里丢掉。因为是往前读下去的，所以没有长度限制。
  • 用捕获组还原。这是到哪里都通用的最小公倍数。把 (password=)[^&]+ 替换成 $1***，在 Python、POSIX sed、Go 上都会得到同样的结果。
  • 分成两步。先宽松地匹配下来，再在程序一侧切开。附带的效果是模式变短、更好读。
  • 如果是 Python，第三方 regex 模块支持变长后顾。只是它不属于标准库，依赖会多出一个。
  • 也有干脆不用后顾的设计。如果是日志或配置这类由我自己掌控格式的数据，只要把分隔符做成唯一的就结束了。模式越是变得精巧，那通常是数据含混的信号，而不是需要正则功力的信号。
$ perl -pe 's/password=\K[^&]+/***/'     → user=a&password=***&x=1
$ sed -E 's/(password=)[^ ]+/\1***/'    → user=a&password=***&x=1
  Python: re.sub(r'(password=)[^&]+', r'\1***', s) → user=a&password=***&x=1

8.2 POSIX ERE 不会报错

这是表里最危险的一格。没有环视这件事本身不是问题，问题是它不告诉你没有。

입력 파일: foobar / foobaz
의도: bar 가 뒤따르는 foo 만

$ grep -oE 'foo(?=bar)' input.txt
(출력 없음)
$ echo $?
1
$ grep -oP 'foo(?=bar)' input.txt
foo

# ERE 가 (?=bar) 를 무엇으로 읽었나
입력에 foo?=bar / foo=bar / foobar 를 넣고 같은 ERE 패턴을 돌리면
$ grep -oE 'foo(?=bar)' input2.txt
foo=bar

在 ERE 里，(?=bar) 大致被解释成「一个可能有也可能没有的、以等号开头的 =bar 分组」。于是它命中了 foo=bar 这个完全不同的字符串，反而对本来想要的 foobar 不命中，而退出码就是普通的 1。在脚本里把 grep -E 和 grep -P 混着用，换回来的会是一种看上去像正常结果的沉默，即「没有匹配」。要用环视就明确写上 -P，并确认那个脚本会不会在没有 -P 的构建上运行。

8.3 后顾是从右往左对齐的

R1 /(?<=(\d+))$/.exec('1234')[1]  = "1234"
R3 /(?<=(\d+))/ .exec('1234')[1]  = "1"

同样是后顾，结果却不一样。R3 没有锚点，所以在最靠左的成功位置索引 1 处匹配，从那里往左读只有一个 1。R1 因为有 $，只在末尾成功，从那里贪婪地往左读，把 1234 全部拿走。MDN 在说明同一性质时也举了例子：/(?<=([ab]+)([bc]+))$/ 在 abc 上会捕获到 a 和 bc。意思是靠后的分组先贪婪。在后顾里放两个以上分组时，贪婪的方向看起来会和直觉相反。

9. 想用前瞻排除韩语词尾的时候

想找出「아니」，但要排除「아니요」。自然的尝试是 /아니(?!요)/。

HIT  이것은 사실이 아니다
miss 이것은 사실이 아닙니다      ← 의도하지 않은 누락
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요        ← 의도한 배제
miss 이것은 사실이 아님          ← 의도하지 않은 누락

本想排除的「아니요」确实漂亮地被排除了。可是「아닙니다」和「아님」也一起被漏掉了。在这里动手去修前瞻，那就是在浪费时间。前瞻一点错都没有。前面的 아니 一开始就没有匹配上，否定条件连被检查的机会都没有。

N2 '아닙니다'.indexOf('아니') = -1
N3 '아님'.indexOf('아니')     = -1
N4 니 = U+B2C8  닙 = U+B2D9  님 = U+B2D8

韩文音节是把初声、中声、终声合成出来的一个码点。一旦加上终声，前一个字就被替换成了另一个字。所以词干不会以子串的形式留下来。原理整理在韩文正则陷阱里，这里要看的是这个性质对环视用法造成的影响。

顺序被颠倒了。若是英语，抓住词干、再用前瞻削掉不想要的活用形就行。而在韩语里，必须先把终声那一位打开、让匹配得以成立之后，前瞻才有意义。

/아[니닙님](?!요)/ 로 자리를 연 뒤:
HIT  이것은 사실이 아니다
HIT  이것은 사실이 아닙니다
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요
HIT  이것은 사실이 아님

现在前瞻干起了自己的活。在动手修排除条件之前，先确认包含条件是否曾经命中过哪怕一次。否定前瞻的失败表现为结果变少的样子，而匹配本身为 0 条同样也是没有结果的样子，两者无法区分。

9.1 无法用环视来判定终声

假设想找出附着了冠形词形词尾「ㄹ」的位置。看起来用 [을ㄹ] 打开就行。

miss 할 수 있다
miss 갈 예정이다
HIT  먹을 만하다
miss 하는 중이다

四个里只抓到一个。「먹을」是因为「을」是独立音节才命中的，而「할」和「갈」里的 ㄹ 是坐进音节内部的终声，并不是单独的字符。无论用字符类还是用环视都够不着。终声的判定不是字符比较，而是算术。

종성 인덱스 = (코드포인트 - 0xAC00) % 28

할 = 8 (ㄹ)   하 = 0 (없음)   갈 = 8 (ㄹ)

산술로 판정하면:
HIT  할 수 있다   (종성 = ㄹ)
HIT  갈 예정이다  (종성 = ㄹ)
HIT  먹을 만하다  (종성 = ㄹ)
miss 하는 중이다  (종성 = ㄴ)

这不是正则能做的事。韩语的形态条件不要往环视里塞，把它挪到代码里去。能用环视的位置，仅限于音节整个充当边界的情形。

P1 '재고가 있음, 재고가 없음'.match(/(?<=재고가 )있음/g) = [ '있음' ]
P2 '재고가 있음, 재고가 없음'.match(/(?<!없)음/g)        = [ '음' ]

到这个程度，也就是以音节为单位刚好切齐的条件，环视就很合适。而且因为是定长的，在任何引擎上都能跑，这也是优点。

10. 性能 - 真正危险的是什么

「前瞻很慢」这句话经常在流传，可一测就会发现危险的所在完全在别处。下面是在五十万字符的输入上只增加条件数的结果。

입력 길이 500,004자

조건 1개  : 0.276 ms
조건 2개  : 0.422 ms
조건 4개  : 0.734 ms
한 번 훑기 : 5.291 ms   ← 같은 판정을 손으로 구현
길이 가드 : 0.00004 ms  ← 128자 넘으면 정규식을 돌리지 않음

条件增加到四个，也没有超过一个条件时的三倍。它确实会把输入扫描好几遍，但扫描次数只是与条件数成比例而已。更引人注目的是，把同样的判定用字符循环亲手写出来的那一侧慢了七倍。字符类扫描走的是引擎内部优化过的路径，所以「觉得正则会慢就手写了」反而常常吃亏。

10.1 真正的危险 - 环视里的嵌套量词

패턴: /^(?=(a+)+$)/     입력: 'a' * n + 'b'

n=20    6.6 ms
n=22   27.2 ms
n=24  108.6 ms
n=26  431.4 ms
n=28 1764.6 ms
n=30 7104.6 ms

每多两个字符就是四倍。在 n=30 要花 7 秒的模式，到了 n=40 就不是人能等下去的时间了。这就是 ReDoS 的典型，原因不在前瞻，而在它内部的 (a+)+。给带量词的分组再加一个量词，切分同一个字符串的方法就会呈指数级增长，而在匹配失败时会把这所有情况都试一遍。

前瞻确实有一处会让局面变糟。前瞻很容易造出每次都必须失败的条件。否定前瞻按定义要求内部匹配一路失败到底才算成功，所以在里面放一个会爆炸的模式，最坏路径就总是被执行。相对地，不带嵌套写成的 /^(?=a+$)/，在十万字符的输入上也只有 0.15 毫秒。

10.2 对策

  • 在正则之前先检查长度上限。最便宜也最可靠。就是上表里 0.00004 毫秒的那一行。像密码、账号、文件名这类上限一目了然的输入，光靠这一条基本就结束了。
  • 不制造嵌套量词。把 (a+)+、(a|a)*、(\s*)+ 这些形状列进模式评审的检查项。
  • 如果是让用户输入模式的位置，就不要用回溯引擎。Go 的 regexp 和 Rust 的 regex 保证与输入长度成线性的时间，代价是不提供环视。这个取舍不是偶然，而是同一个设计决定的正反两面。
  • 有超时机制就挂上。像 .NET 那样，有些运行时可以给正则执行加上时间限制。虽不是根本解决，但能把故障变成延迟。
  • 否定前瞻内部要格外保持简单。那里面是即使在正常输入下也每次都要搜索到底的区间。
  • 把模式固定成常量。用字符串拼接来造正则，用户输入就会混进模式本身，偶然造出会爆炸的形状。值应该作为参数传入，而不是作为模式。

11. 没能确认的部分

  • Java java.util.regex 的变长后顾。这个环境里没有 JDK，无法通过运行来确认。这就是第 8 节表格里那一格留空的原因。
  • .NET 的变长后顾。出于同样的原因没能做运行确认。只按文档写到了它支持环视本身为止。
  • Go regexp 的行为。没有 Go 工具链，表格里那一行依据的是 regexp/syntax 文档所列举的零宽度条件清单（^ $ \A \b \B \z）里没有环视这一事实。并不是通过运行确认的。
  • 最新 PCRE2 的变长后顾。表格里的 PCRE 行以链接进 GNU grep 3.0 的构建为准。据说 PCRE2 在之后的版本里放宽了这一限制，但在这个环境里无法确认。不要笼统地说 PCRE，去自己用的构建上直接编译一次试试。
  • ReDoS 数值的可移植性。第 10 节的测量值以 V8 为准。呈指数增长这一性质是回溯引擎共通的，但具体的毫秒数和临界 n 会随引擎和硬件而变。要看的不是绝对值，而是增长率。
  • Unicode 属性转义与环视的组合。第 6 节的韩文边界例子写的是 [가-힣]，而这只覆盖预组合音节。需要涵盖单独字母或分解形式时的行为，本文没有涉及。

12. 实战惯用法汇总

想做的事模式结果
有 A 而没有 B 的行^(?=.*A)(?!.*B)与条件顺序无关，个数不限
留下键，只对值做掩码(?<=key=)[^&]+ → ***key=***
千位分隔符\B(?=(\d{3})+(?!\d)) → ,1,234,567
把 camelCase 变成 snake_case(?<=[a-z])(?=[A-Z]) → _one_two_three_id
保持缩写不拆开地分隔(?<=[A-Z])(?=[A-Z][a-z]) → _HTTP_ServerError
只留后四位做掩码\d(?=\d{4}) → *************1111
数出重叠匹配(?=(AA)) + matchAllAAAA 里 3 条
在大写字母前切开split(/(?=[A-Z])/)['one','Two','Three']
自己定义单词边界(?<![a-z])cat(?![a-z])排除 cats·concat
韩文的词边界(?<![가-힣])말(?![가-힣])\b 在韩文上不管用

需要变长时（PCRE·Perl）prefix\K值没有长度限制

结论：不是抓什么，而是在哪里抓

如果把环视当成「多加一个条件的语法」来学，就会停在复制一行密码校验拿去用的地方。而在那个位置上，其实用捕获组大多也办得到。这个工具真正值钱的地方，是必须把条件和结果分开的位置。

  • 条件里用到的字符必须留在结果中时 — 只抓边界的替换
  • 多个条件必须在同一个点上完成判定时 — 不被顺序绑住的过滤
  • 光标不能前进时 — 重叠匹配
  • 引擎定下的边界定义与我的数据对不上时 — 自己写的 \b
  • 必须同时看左边和右边时 — 像缩写边界那样需要双向条件的位置

把判断标准压成一条就是这样。是否存在不能进入匹配结果的条件。有，那就是环视；没有，那多半用更简单的模式就够了。

还有两件事养成习惯，事故就会减少。第一，后顾只用定长的写法。Python 连长度不同的交替都拒绝，Perl 和 PCRE 在无限量词处停下。真的需要变长时，退到 \K 或捕获组上更容易搬来搬去。第二，加否定条件时，把匹配边界一起固定住。\d+(?!USD) 会返回 10 的那个位置，就是理由。

最后，如果处理的是韩语，顺序必须颠倒过来。在用前瞻削掉活用形之前，先确认包含条件是否曾经匹配过哪怕一次。匹配 0 条和排除得很干净这两种状态，在结果画面上长得一模一样。
