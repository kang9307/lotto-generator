一个看不见的字节在 shebang、变量比较和 git 索引里做了什么，以及恢复的顺序

2026年9月1日 IT/技术

在 Windows 上改好的部署脚本传到服务器，只留下一行 bad interpreter 就死了。打开文件看不出任何问题，第一行明明是 #!/bin/bash，没有拼错，权限也对，可就是跑不起来。这种时候多数人会把脚本从头重打一遍，通常也就好了，而问题出在哪里始终没人知道。

一共有三种 - 直接看字节

换行方式有三种。类 Unix 系统用的 LF 是 0x0A 一个字节，Windows 用的 CRLF 是 0x0D 0x0A 两个字节，经典 Mac OS 用过的单独 CR 是 0x0D 一个字节。第三种如今几乎不会再产生，但接手旧资料时仍会碰到。与其背概念，不如把字节看一遍。

$ printf 'hello\nworld\n'     > lf.txt
$ printf 'hello\r\nworld\r\n' > crlf.txt
$ printf 'hello\rworld\r'     > cr.txt

$ xxd lf.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.
$ xxd crlf.txt
00000000: 6865 6c6c 6f0d 0a77 6f72 6c64 0d0a       hello..world..
$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ file lf.txt crlf.txt cr.txt
lf.txt:   ASCII text
crlf.txt: ASCII text, with CRLF line terminators
cr.txt:   ASCII text, with CR line terminators

xxd 右侧的点是用来代替无法打印的字符的。LF 文件里 hello 后面只有一个点，CRLF 文件里有两个。这个差别就是本文的全部内容。看得见的文本完全一样，只有文件大小按行数增加。三行的文件就是 17 字节和 20 字节的差别。

名称字节转义主要使用场合现在会在哪里遇到
LF0x0A\nLinux、Unix、现代 macOS、Web、多数语言的源码默认值。没有特别理由就用它
CRLF0x0D 0x0A\r\nWindows 记事本和批处理文件、很多网络协议Windows 编辑器常给新文件加上
CR0x0D\r2001 年以前的经典 Mac OS只在接手旧资料时。不会再新产生

当初为什么会分成两种

这两个字符的名字本身就带着来历。CR 是 carriage return，把打印头拉回行首的动作，LF 是 line feed，把纸推进一行的动作。在机械打印设备上这是两个分开的动作。一支脉络把这个习惯原样留在了文件格式里，另一支则认为一行一个字符就够了。

Unix 一侧的选择写进了标准。POSIX 把行定义为「零个或多个非换行字符，加上一个作为终止的换行字符」。这里的换行字符只指 \n，CR 只是包含在数据里的普通字符。所以把 CRLF 文件交给 Unix 工具时，CR 会被当成这一行的最后一个字符。它不是应当被剥掉的控制字符，而是作为值的一部分被带进来。后面出现的所有事故，都是从这一句话派生出来的。

  • 从 Unix 的角度看，CRLF 文件的每一行都是「内容 + CR」。CR 不是分隔符，而是内容的最后一个字
  • 于是你以为读到 "prod" 的变量里，实际装的是 "prod\r"
  • 比较、拼路径、数值转换、算哈希全都对不上，而屏幕上看不出任何异样
  • 反方向，也就是把 LF 文件交给 Windows 工具，宽容得多。如今的 Windows 工具大多能直接读 LF

shell 脚本是怎么死的

先看最有名的症状。把第一行是 #!/bin/bash 的脚本存成 CRLF，这一行的实际字节就变成 #!/bin/bash\r\n。内核解析 shebang 时，解释器路径取到换行之前，于是要启动的程序名不是 /bin/bash，而是/bin/bash 后面多了一个 CR 字符的名字。这样的文件不存在，所以失败。

看字节就没有怀疑的余地了。

$ printf '#!/bin/bash\r\necho "hi"\r\n' > crlf.sh
$ chmod +x crlf.sh
$ head -c 24 crlf.sh | xxd
00000000: 2321 2f62 696e 2f62 6173 680d 0a65 6368  #!/bin/bash..ech
00000010: 6f20 2268 6922 0d0a                      o "hi"..

6173 68 是 ash，紧接着就是 0d 0a。路径字符串 /bin/bash 后面直接跟着 0x0D。这样运行就会报找不到解释器。这个机制不经过 shebang 也能复现，直接调用一个路径末尾带 CR 的可执行文件即可。

$ "/bin/bash$(printf '\r')" -c 'echo hi' 2>err.txt
$ cat -A err.txt
/usr/bin/bash: line 1: /bin/bash^M: No such file or directory$

$ xxd err.txt
00000000: 2f75 7372 2f62 696e 2f62 6173 683a 206c  /usr/bin/bash: l
00000010: 696e 6520 313a 202f 6269 6e2f 6261 7368  ine 1: /bin/bash
00000020: 0d3a 204e 6f20 7375 6368 2066 696c 6520  .: No such file
00000030: 6f72 2064 6972 6563 746f 7279 0a         or directory.

偏移 0x20 处的 0d 是关键。错误信息里面含有一个真实的 CR 字节。cat -A 把它显示为 ^M。常见的 bad interpreter: /bin/bash^M 里的 ^M 正是这个字节，并不是 shell 凭空造出来的字符。

如果 shebang 走的是 env，错误的样子会不太一样。env 会把拿到的参数原样引起来显示，反而更友好。

$ env "bash$(printf '\r')" --version
env: 'bash\r': No such file or directory

这里 \r 干脆被逐字打了出来。用 env 开头写 shebang 的习惯，在排查时反倒占了便宜。

Git Bash 会把这个 bug 藏起来

到这里就能看出这个问题为什么活得那么久。把上面做的 crlf.sh 直接在 Git Bash 里运行，什么事都不会发生，它正常跑完。

$ ./crlf.sh
hi

$ printf '#!/usr/bin/cat\r\nhello\r\n' > catshebang.sh
$ chmod +x catshebang.sh
$ ./catshebang.sh | cat -A
#!/usr/bin/cat^M$
hello^M$

第二个例子就是证据。把 shebang 指向 /usr/bin/cat 后运行，cat 真的被执行并吐出了文件内容。也就是说 MSYS2 的执行层会自动把 shebang 行末的 CR 去掉，再去找解释器。而文件里的 CR 依然原封不动，这一点从同一段输出也能确认，内容行仍然带着 ^M。

结果就是，脚本在开发者的笔记本上跑得很好。提交通过，评审通过，进了部署流水线，然后在 Linux 服务器上第一次死掉。这就是这个 bug 能通过代码评审的原因。顺带一提，据说有些 bash 构建带有让它忽略 CR 的 igncr 选项，但至少本环境的 bash 5.2.37 没有。

$ shopt igncr
/usr/bin/bash: line 1: shopt: igncr: invalid shell option name

所以在这个话题上，「我本地明明是好的」这句话不构成信息。如果本地是 Windows，那本来就该是好的。

真正麻烦的是变量值末尾的 CR

shebang 这种情况好歹死得响亮。真正会拖住人很久的，发生在读配置文件写进变量的时候。脚本本身是 LF，而它读取的 .env 或配置文件是 CRLF，这种组合很常见。这时候程序不会死，只是条件判断给出错误答案。

$ printf 'ENV=prod\r\nPORT=8080\r\n' > app.conf

$ cat readconf.sh
#!/bin/bash
while IFS='=' read -r k v; do
  export "$k=$v"
done < app.conf
echo "ENV=[$ENV]"
if [ "$ENV" = "prod" ]; then echo "MATCH"; else echo "NO MATCH"; fi
echo "length=${#ENV}"

$ bash readconf.sh
ENV=[prod]
NO MATCH
length=5

屏幕上写着 ENV=[prod]，方括号里就是 prod 四个字符。可它说这不等于 prod，还说长度是 5。想靠肉眼把这三行同时讲通，能耗掉好几个小时。用 cat -A 一看就结束了。

$ bash readconf.sh | cat -A
ENV=[prod^M]$
NO MATCH$
length=5$

值不是 prod，而是 prod 后面带一个 CR 的五个字符。这里有一处细微差别需要点明，读取方式不同，CR 有时留下有时消失。

$ printf 'v2.4.1\r\n' > version.txt

$ read -r VER2 < version.txt
$ echo "len2=${#VER2}"
len2=7
$ printf '%s' "$VER2" | xxd
00000000: 7632 2e34 2e31 0d                        v2.4.1.

$ VER=$(cat version.txt)
$ echo "len=${#VER}"
len=6
$ printf '%s' "$VER" | xxd
00000000: 7632 2e34 2e31                           v2.4.1

用 read 读，CR 留下来，是 7 个字符；用命令替换读则是 6 个。本环境的 bash 在命令替换里去掉末尾换行时，把 CR 也一起去掉了。不过这同样属于只在 Windows 上安静的那一类。管道会把 CR 原样送过去。

$ printf 'a\r\nb\r\n' | xxd
00000000: 610d 0a62 0d0a                           a..b..

也就是说，同一个文件，用 while read 循环、用 $(...) 接收、还是用管道传递，CR 残留的位置都不一样。于是就出现了某些行能跑、某些行跑不通的脚本。这种不一致最妨碍追查原因。

错误信息为什么会被截得莫名其妙

CR 一旦混进值里，打印出来的那一刻终端就会有反应，因为 CR 本来就是把光标送回行首的控制字符。消息中间出现 CR，后面的字符就会盖住前面的部分。不是被删掉了，而是被盖住了。

假设你想打印 deploy failed: version v2.4.1 not supported，而版本值末尾带着 CR。终端会画到 v2.4.1，然后把光标送回行首，再把 not supported 盖上去。剩下的是一行前后混在一起的短文本，原句看上去无处可寻。重定向到文件再用 cat -A 打开，完整原文原封不动地在那里。

  • 如果消息看起来像是中间被截断了，先怀疑 CR。多数情况并不是日志代码的 bug
  • 同样的原因会让进度显示变乱、提示符互相重叠，也会让人误以为 grep 的结果变短了
  • 确认时一定要先接到文件里。终端画出来的画面不是原本
  • CI 的日志查看器对 CR 的处理各家不同，同一份日志在本地和网页上可能长得不一样

怎么找 - grep 返回 0 的陷阱

确认用四条命令就够。file 一眼看出，cat -A 按行看，xxd 按字节看，dos2unix -i 按个数看。造一个混合的文件，把四条并排跑一遍。

$ printf 'first\r\nsecond\nthird\r\n' > mixed.txt

$ file mixed.txt
mixed.txt: ASCII text, with CRLF, LF line terminators

$ cat -A mixed.txt
first^M$
second$
third^M$

$ dos2unix -i mixed.txt lf.txt crlf.txt cr.txt
       2       1       0  no_bom    text    mixed.txt
       0       2       0  no_bom    text    lf.txt
       2       0       0  no_bom    text    crlf.txt
       0       0       2  no_bom    text    cr.txt

dos2unix -i 的三个数字，从左到右分别是 CRLF、LF、单独 CR 的个数。mixed.txt 是 2 1 0，和造它的方式一致。第四列是有没有 BOM，第五列是判定为文本还是二进制。要从一堆文件里只挑出含 CRLF 的，用 -ic，它只输出文件名。

可是流传最广的那个办法，在本环境里会给出假阴性。

$ grep -c $'\r' mixed.txt
0

$ grep -Uc $'\r' mixed.txt
2

$ awk '/\r$/{n++} END{print n+0}' mixed.txt
0

$ awk -v BINMODE=3 '/\r$/{n++} END{print n+0}' mixed.txt
2

对一个含两行 CRLF 的文件，grep -c $'\r' 返回 0。本环境的 GNU grep 3.0 以文本模式读文件，会先把行尾的 CR 剥掉。加上 -U 让它按二进制模式读，就能正确得到 2。gawk 也一样，需要 -v BINMODE=3。Linux 上没有这种预处理，不加 -U 也能匹配到，所以「我在 Windows 上确认过」这句话是不可信的。写检查脚本时漏掉这一个字母，检查器就会永远返回通过。

命令能看出什么注意
file 文件用名称告诉你是 CRLF、LF 还是 CR混合时会把两种都列出来
cat -A 文件每行的 ^M 和行尾的 $最直观。制表符显示为 ^I
xxd 文件 | head真实字节，亲眼看到 0d0a文件长就用 head 截一段
dos2unix -i 文件CRLF、LF、CR 的个数和 BOM 状态适合把多个文件放在一张表里看
grep -Uc $'\r' 文件含 CR 的行数不加 -U 在本环境会返回 0
git ls-files --eol仓库索引和工作树的状态看的是仓库，不是单个文件

三种修法，以及各自会毁掉什么

常用的转换方法有三种。对普通的 CRLF 文本文件，三者结果一样。

$ dos2unix -q mixed.txt
$ sed -i 's/\r$//' mixed.txt
$ tr -d '\r' < mixed.txt > out.txt

$ cat -A mixed.txt
first$
second$
third$

分歧出现在不普通的文件上。tr -d '\r' 完全不区分是不是行尾，会把文件里的 0x0D 一个不剩地删掉。以一份用 CR 覆盖打印进度的日志为例，结果是这样。

$ printf 'progress: 10%%\r progress: 100%%\rdone\n' > prog.log
$ xxd prog.log
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

$ tr -d '\r' < prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 2520 7072  progress: 10% pr
00000010: 6f67 7265 7373 3a20 3130 3025 646f 6e65  ogress: 100%done
00000020: 0a                                       .

$ sed 's/\r$//' prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

过了 tr 的那份，三段进度显示接成了一行，原本的意图没了。sed 's/\r$//' 只针对行尾的 CR，所以没有动这个文件。不过 sed 也不是万能的，它对旧 Mac 那种单独 CR 的文件几乎无从下手，因为那种文件在 Unix 工具眼里是一整行。

$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ sed 's/\r$//' cr.txt | xxd
00000000: 6865 6c6c 6f0d 776f 726c 64              hello.world

$ tr -d '\r' < cr.txt | xxd
00000000: 6865 6c6c 6f77 6f72 6c64                 helloworld

$ dos2unix -q -c mac cr.txt
$ xxd cr.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.

sed 只摘掉了最末尾的一个 CR，中间那个留着。tr 把两行并成了 helloworld 一坨。只有 dos2unix -c mac 把 CR 换成 LF 并保住了两行。会不会丢数据，就取决于选了哪条命令。

在二进制文件上差别更极端。dos2unix 默认会跳过二进制。

$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ dos2unix bin.dat
dos2unix: Binary symbol 0x00 found at line 1
dos2unix: Skipping binary file bin.dat
$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ tr -d '\r' < bin.dat | xxd
00000000: 504e 4789 000a 1a0a ffd8                 PNG.......

经过 tr 的文件少了一个字节。不管是图片还是压缩包，到这一步就不能用了，而且没有任何警告。把 find 和 tr 组合起来在整个仓库上跑的脚本，危险就在这里。

工具行尾 CRLF行中间的 CR单独 CR 的文件二进制BOM
dos2unix转换保留用 -c mac 转换默认跳过默认删除
sed -i 's/\r$//'转换保留几乎无从下手可能弄坏不动
tr -d '\r'转换一并删除行被并起来会损坏不动

表格最右一列是个意料之外的副作用，值得单独确认。不给选项的话，dos2unix 会把文件开头的 BOM 一起删掉。

$ printf '\xef\xbb\xbfname,qty\r\nsalt,2\r\n' > bomcrlf.csv
$ xxd bomcrlf.csv
00000000: efbb bf6e 616d 652c 7174 790d 0a73 616c  ...name,qty..sal
00000010: 742c 320d 0a                             t,2..

$ dos2unix -q bomcrlf.csv
$ xxd bomcrlf.csv
00000000: 6e61 6d65 2c71 7479 0a73 616c 742c 320a  name,qty.salt,2.

开头三个字节 efbbbf 不见了。像要交给 Excel 的 CSV 这类需要 BOM 的文件，必须加 -b 保留它。这是想修换行却顺手改了别的东西的典型场面。

git 介入的两个位置 - core.autocrlf

git 可以在两个位置动换行符，提交时(从工作目录到索引)和检出时(从索引到工作目录)。core.autocrlf 的三个值对这两个位置的处理各不相同。造一个用完即弃的仓库验证一遍，就没有可含糊的余地了。

先看检出侧。把一个内容以 LF 提交的仓库，用三种设置各克隆一次。

$ cd /tmp/demo/src
$ git ls-files --eol
i/lf    w/lf    attr/                   src.txt

$ git -c core.autocrlf=true  clone -q /tmp/demo/src /tmp/demo/w-true
$ git -c core.autocrlf=input clone -q /tmp/demo/src /tmp/demo/w-input
$ git -c core.autocrlf=false clone -q /tmp/demo/src /tmp/demo/w-false

$ xxd /tmp/demo/w-true/src.txt
00000000: 6c69 6e65 310d 0a6c 696e 6532 0d0a       line1..line2..
$ xxd /tmp/demo/w-input/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.
$ xxd /tmp/demo/w-false/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.

只有 true 把工作目录里的文件改写成了 CRLF。接下来是提交侧。在三个仓库里各造一个 CRLF 文件提交，然后看索引状态。

$ printf 'new1\r\nnew2\r\n' > added.txt
$ git add added.txt
$ git commit -qm add
$ git ls-files --eol -- added.txt

# core.autocrlf=true
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=input
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=false
i/crlf  w/crlf  attr/                   added.txt

true 和 input 都以 LF 放进索引，false 则原样放进了 CRLF。也就是说，这两个值的差别在检出，不在提交。这张表就是结论。

core.autocrlf提交时 (工作 → 索引)检出时 (索引 → 工作)适合谁
true把 CRLF 转成 LF 存入把 LF 转成 CRLF 交给你只用 Windows 编辑器的人。仓库会保持干净
input把 CRLF 转成 LF 存入不转换，保持 LF在 Windows 上写 Linux 脚本的人
false不转换，写成什么就是什么不转换只用 .gitattributes 管理换行的仓库

此外还有一个 core.eol，取值为 lf、crlf、native，默认是跟随平台惯例的 native。而把 core.safecrlf 设成 true 或 warn，可以在转换不可逆时发出警告或直接拦下。

  • core.autocrlf 是个人配置，每个拿到仓库的人取值都可能不同
  • 所以在团队里公告一个统一值这种做法，在每个新加入的人身上必定会破一次
  • 官方文档把 core.autocrlf=true 解释为「等同于对所有文件设置 text=auto 并把 core.eol 设为 crlf」
  • 这就是说 autocrlf 更像 .gitattributes 的缩写。既然如此，不如直接写本体

.gitattributes 更好的理由

差别只有一点。core.autocrlf 绑在人身上，.gitattributes 绑在仓库上。后者会被提交并随代码一起分发，所以无论协作者怎么配置，同一套规则都会生效。新来的人什么都不设置规则也照样起作用，这才是实质差别。

# .gitattributes
* text=auto

*.sh   text eol=lf
*.py   text eol=lf
*.yml  text eol=lf
*.yaml text eol=lf

*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf

*.png binary
*.jpg binary
*.pdf binary

属性的含义是这样。指定 text 后，每次入库都会把索引里的换行规范化为 LF。text=auto 交给 git 自行判断是文本还是二进制。eol=lf 表示检出时使用与索引相同的换行，eol=crlf 表示把工作目录里的文件改成 CRLF。binary 是 -text -diff 的别名，意思是什么都别转。

这里有个容易漏掉的点。只写 * text=auto 并不能让工作目录变成 LF。文档说明，当 eol 未指定且 core.autocrlf 和 core.eol 都没有设置时，默认是在 Windows 上 eol=crlf，在其他平台上 eol=lf。重新克隆一次，看到的正是这个结果。

$ git clone -q /tmp/demo/repo /tmp/demo/fresh
$ cd /tmp/demo/fresh
$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          .gitattributes
i/-text w/-text attr/text=auto          blob.bin
i/lf    w/lf    attr/text eol=lf        deploy.sh
i/lf    w/crlf  attr/text=auto          notes.md

$ xxd notes.md
00000000: 610d 0a62 0d0a                           a..b..
$ xxd deploy.sh
00000000: 2321 2f62 696e 2f62 6173 680a 6563 686f  #!/bin/bash.echo
00000010: 2068 690a                                 hi.

同一个仓库里，notes.md 是以 CRLF 落地的，deploy.sh 是以 LF 落地的。差别只有 *.sh text eol=lf 这一行。要在 Linux 上执行的文件必须显式写 eol=lf，理由就在这里。只信 text=auto，shell 脚本会在 Windows 的工作树里以 CRLF 复活。

输出格式也值得记一下。git ls-files --eol 会显示三列。

列含义可能的取值
i/索引中所存 blob 的换行lf、crlf、mixed、-text(二进制)
w/当前工作目录中文件的换行取值相同。与 i/ 不一致有时也正常
attr/该路径上正在生效的属性text=auto、text eol=lf、空白等

.gitattributes 不会修正过去

这一节大概会是本文被用得最多的部分。加了 .gitattributes 很容易以为事情就完了，可是在规则加入之前已经提交的 blob 会原样留着。规则只对今后的转换生效。

把一个在 core.autocrlf=false 下提交了 CRLF 文件的仓库加上 .gitattributes，看到的状态是这样。

$ git ls-files --eol
i/crlf  w/crlf  attr/                   deploy.sh
i/lf    w/lf    attr/                   notes.md

$ printf '* text=auto\n*.sh text eol=lf\n*.bat text eol=crlf\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm "add gitattributes"

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text eol=lf        deploy.sh
i/lf    w/lf    attr/text=auto          notes.md

$ git check-attr text eol -- deploy.sh
deploy.sh: text: set
deploy.sh: eol: lf

attr/ 那一列已经正确带上了新规则，check-attr 也回答 eol: lf。可 i/ 那一列还是 crlf。规则生效了，数据还是老样子。把这个仓库部署到 Linux 服务器上，脚本照样会死。

更容易迷惑的是只写了 * text=auto 的情况。文档对这个值的说法是，如果是文本，并且该文件此前没有以 CRLF 进入 Git，才会转换换行。那么把这个文件改一改再提交一次是不是就好了？验证一下，并不是。

$ git ls-files --eol
i/crlf  w/crlf  attr/                   legacy.txt

$ printf '* text=auto\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm attrs

$ printf 'one\r\ntwo\r\nthree\r\n' > legacy.txt
$ git add legacy.txt
$ git commit -qm edit

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650d 0a74 776f 0d0a 7468 7265 650d  one..two..three.
00000010: 0a                                       .

改过又重新提交，索引里的 blob 依然是 CRLF。text=auto 会一直把曾经以 CRLF 进来的文件当成例外。也就是说，规则加进去之后过几个月它也不会自己理顺。

要理顺就需要一次显式的重新规范化，顺序和官方文档给的一样。在工作树干净的状态下执行。

$ git add --renormalize .
$ git status --short
M  legacy.txt
$ git commit -qm "normalize line endings"

$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650a 7477 6f0a 7468 7265 650a       one.two.three.

索引现在是 LF 了。可 w/ 那一列还是 crlf，因为重新规范化只改索引，不动工作目录里的文件。要把工作树也对齐，把该文件删掉再检出一次即可。

$ rm deploy.sh
$ git checkout -- deploy.sh
$ git ls-files --eol
i/lf    w/lf    attr/text eol=lf        deploy.sh
  • 重新规范化的提交内容没变，看上去却几乎每一行都改了。别和别的改动混在一起，单独成一个提交
  • 如果有进行中的分支，合并冲突会很大。先把该合的合掉，再做规范化更稳
  • 如果 git status 里冒出预料之外的文件，先用 -text 把它排除掉再重新跑
  • 规范化之后仍有 i/crlf 残留，说明那条路径没被规则覆盖。用 git check-attr 确认

哪些文件应该是 CRLF

「全都统一成 LF」的建议很常见，「Windows 专用文件也这样会出事」的反对同样常见。我实际测了一下到底会出多大的事。用只含 LF 的批处理文件，放进标签与 goto、for 循环、if else 块、用 call 调子例程，还有最后一行不带换行的情况，然后用 cmd.exe 跑。

C:\> cmd /c lf2.bat
item 1
item 2
item 3
yes
SUB

C:\> powershell -NoProfile -ExecutionPolicy Bypass -File lf.ps1
ps LF ok
block ok

全部正常运行。在 Windows 10 内部版本 19045.6466 的 cmd.exe 和 PowerShell 5.1 上，LF 的批处理文件跑起来了。「必须是 CRLF」这个说法，至少在这个组合里没有复现。

但这不等于建议把批处理文件改成 LF。判断的依据不是跑没跑通，而是风险的不对称。把 Windows 专用文件保持 CRLF，不会损失任何东西，因为它不会在 Linux 上执行。反过来把要在 Linux 上跑的文件写成 CRLF，则必定会坏。于是规则很简单，按它在哪里运行来定。

文件建议理由
.sh、.bash、.py、.pl、.rbLFshebang 会把 CR 并进解释器路径
Makefile、systemd 单元、cron 文件LF值末尾带上 CR，路径和命令就会对不上
.env、.conf、.yml、.jsonLF视解析器而定，值末尾的 CR 会原样进去
SSH 公钥、authorized_keysLF密钥字符串变了，认证会静默失败
.bat、.cmdCRLF本环境里 LF 也能跑，但这是 Windows 专用，用 CRLF 没有损失
.ps1都可以LF 运行正常。这一类反而是 BOM 更常出问题
图片、压缩包、字体禁止转换在 .gitattributes 里标为 binary

在编辑器和 CI 里拦住它

不让它发生比事后修更便宜。一共三层，编辑器拦一次，仓库拦一次，流水线拦一次。编辑器这一层交给 .editorconfig。按规范，end_of_line 接受 lf、cr、crlf，取值不区分大小写。

# .editorconfig
root = true

[*]
end_of_line = lf
insert_final_newline = true
charset = utf-8
trim_trailing_whitespace = true

[*.{bat,cmd}]
end_of_line = crlf

[*.md]
trim_trailing_whitespace = false

这两个文件的职责不重叠。前者在编辑器保存时起作用，后者在git 提交和检出时起作用。两个都放，并且把扩展名清单对齐。一旦对不上，保存时的取值和提交时的取值就不同，每次都会冒出改动。

最后一层是检查。仓库索引里有没有以 CRLF 进去的文本文件，一行就能确认。

$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
$ echo $?
1

# 在被污染的仓库里
$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
i/crlf  w/crlf  attr/                   added.txt
$ echo $?
0

干净时不输出任何东西并返回退出码 1，有问题时列出清单并返回 0。在 CI 步骤里，前面加个 ! 把它反过来，找到就算失败。比起直接扫文件，这个办法有三个好处。二进制会显示为 i/-text 自动被排除，用 .gitattributes 允许 CRLF 的文件规范化之后显示为 i/lf，而最重要的是它绕开了前面看到的 grep 文本模式陷阱。

再补一句，换行一旦混乱，最先崩掉的是代码评审，因为内容相同也会被显示成全部改过。

$ diff a_lf.txt a_crlf.txt
1,3c1,3
< alpha
< beta
< gamma
---
> alpha
> beta
> gamma

$ diff --strip-trailing-cr a_lf.txt a_crlf.txt
$ echo $?
0

看得见的字符完全一样，却说三行都不同。评审者再也找不到真正的改动，这种状态持续几天，整个仓库就混了。--strip-trailing-cr 是着急时的权宜之计，不是解决方案。

最后，也值得知道为什么有些代码毫发无伤。有些语言运行时在读取阶段就已经替你转换好了。

$ python nl.py
default  : 'ENV=prod\n'
newline='': 'ENV=prod\r\n'
binary   : b'ENV=prod\r\n'
split    : ['ENV', 'prod']
split raw: ['ENV', 'prod\r']

以文本模式打开时，Python 默认会把换行统一成一个 \n。所以 Python 代码读 CRLF 文件大多没事。反过来用 newline="" 或二进制模式打开，CR 就会原样进来，再对这个值做 split，得到的是 'prod\r'。这意味着两段代码把同一个文件读成不同结果的情况是真实存在的。

换行和 BOM 是两回事

这两个经常被放在一起讲，但成因、位置和解法都不同。换行在每一行的末尾，BOM 只在文件最开头出现一次。症状看起来相似，只是因为两者共享「看不见的字节混进值里」这个形式，而不是同一个原因。

  • 换行是 0x0D 0x0A，UTF-8 的 BOM 是 0xEF 0xBB 0xBF，没有重叠的字节
  • 修复工具也不同。只是 dos2unix 默认会同时动这两样，前一节已经验证过
  • shebang 被破坏这个症状两者都会造成。第一行前面有 BOM，或者第一行末尾有 CR，都会导致找不到解释器
  • 区分只需要一行 xxd 文件 | head -1。看开头是不是 efbbbf，行尾是不是 0d0a 就够了

BOM 这一侧的细节另外整理在 BOM 制造的 bug - 看不见的三个字节在哪里弄坏 shell、JSON 和 CSV。文字显示成方块或问号则是另一层，那部分在 定位韩文乱码发生的那一点 - cp949 与 UTF-8，两种编码错误。三个问题叠在一起时，按编码 → BOM → 换行的顺序一层层剥掉会更快。

按顺序来 - 简版

如果现在手上就有坏掉的文件，步骤很短。用 file 确认种类，用 dos2unix 转换，再跑一次。到这里五分钟。问题在后面。如果同样的事下周又发生，要修的就不是文件而是流水线了。

  1. 诊断。file 文件 和 xxd 文件 | head -1。分清是行尾的 0d0a 还是开头的 efbbbf
  2. 转换。dos2unix 文件。像 CSV 那样需要 BOM 就加 -b，旧 Mac 文件用 -c mac。不要用 tr -d '\r'
  3. 仓库规则。.gitattributes 里写 * text=auto，并按可执行文件的扩展名写 eol=lf。Windows 专用写 eol=crlf
  4. 清理过去。在干净的工作树上执行 git add --renormalize .，单独提交。不做这一步，规则就只是摆设
  5. 编辑器。.editorconfig 里写 end_of_line = lf，扩展名清单和 .gitattributes 对齐
  6. 检查。在 CI 里加一行 ! git ls-files --eol | grep -E '^i/(crlf|mixed)'

最重要的是第四步。本文所有跑出来验证过的事实里，在实际工作中最常绊住人的，就是加了规则历史依然不动这一条。在 * text=auto 之下修改那个文件并重新提交，索引里仍然是 CRLF。重新规范化不会自己发生。

「我在 Windows 上确认过」不构成依据。光是本文验证到的就有三条。Git Bash 会替你处理 CRLF 的 shebang 并让脚本正常运行，grep -c $'\r' 在 CRLF 文件上返回 0，命令替换会把值末尾的 CR 摘掉。三者都把问题遮了起来。验证要在真正会部署的环境里做，至少也要用 git ls-files --eol 这类不依赖平台的方法。

未能确认的部分

  • 我没能在真实的 Linux 机器上打印出 bad interpreter: /bin/bash^M 这句原文，本机没有安装 Linux 发行版。正文里贴出的是在执行层复现的同一机制，消息的措辞会因 shell 和发行版而不同
  • 同样的原因，我确认了本环境的 bash 在命令替换里会摘掉 CR，但Linux 的 bash 会保留 CR 这个对照没能用执行验证
  • MS-DOS 选择 CRLF、Unix 选择 LF 的历史一手资料没能确认。正文只写到两个控制字符的名字所指的动作，以及 POSIX 对行的定义
  • 关于注册表文件和某些 Windows 工具要求 CRLF 的说法，验证方式不够安全，因此没有测试，正文里也没有写
  • 批处理文件的测试只在这一台 Windows 10 内部版本 19045.6466 上做过。在其他 Windows 版本或其他批处理语法下 LF 会不会出问题，并未排除
  • dos2unix 最新发行版是 7.5.7(2026-08-27)，而本环境的构建是 7.5.2。新版本里改变的行为没能确认
  • git 官方文档中的 git-config 页面在抓取时正文中途被截断，core.autocrlf 条目读不到。因此改用 kernel.org 镜像上的同一份文档确认，参考资料里给出的是实际读到的那一份
