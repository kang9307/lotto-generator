How to Build a Real --dry-run - Verification, Not Imitation

Five fake dry runs reproduced with real output, then proven fixed by three identical plan hashes

Jul 29, 2026 Dev & Infra

Introduction: the dry run promised something the real run could not do

You add --dry-run to a cleanup script. It prints twelve lines of would delete, the list matches your expectations, and you relax. Then you run it for real, it errors out halfway, and you are left staring at a directory where some files are gone and some are not. The dry run clearly said it would do one thing, and the real run could not do it.

What makes this situation genuinely bad is not that the answer was wrong. It is that the person who ran the dry run relaxed in between. With no verification at all they would have proceeded carefully. Because they believed they had checked, they pushed straight through. Believing you verified is more dangerous than not verifying. That is the real harm a fake dry run does.

A widespread misconception sits underneath it: a dry run just means printing the commands instead of running them. It does not. Printing is the artifact, not the substance. For a dry run to be worth anything it must travel the same decision path the real run would travel. It evaluates the same conditions, passes the same checks, selects the same targets in the same order, and only then skips the final step of writing. Where you place that final step decides whether you built verification or an impression of it.

This article does not define terms. It starts with five kinds of fake dry runs reproduced in a scratch directory with the actual output, then shows how to fix them. The order is: break each of the five, then build a plan and apply split and prove determinism by hashing three consecutive runs, then settle the exit code contract and CI wiring, and finally draw a line around how far the dry runs of existing tools like git clean -n and rsync -n can be trusted.

One boundary up front. Whether running twice yields the same result is not this article's subject. That belongs to Idempotent Shell Scripts, which I wrote separately. The question here is a different one: can you know the outcome before you run it? The two properties help each other, but they are not the same thing. A perfectly idempotent script can still ship a dry run that lies.

The article contains irreversible commands such as rm, sed -i and git clean -f. All of them were executed inside freshly created temporary directories, and none of this code is written to be pointed at anything else. If you reproduce it, create an empty temporary directory and stay inside it; do not run these against a real server path or your home directory. In particular, git clean variants delete untracked files with no way to recover them.

2. Type 1 - printing without deciding

The most common shape. At every point of action an if splits: print a sentence in dry mode, call the real thing otherwise.

clean() {
  for f in "$@"; do
    if [ -n "${DRY:-}" ]; then
      echo "would delete $f"
    else
      rm "$f"
    fi
  done
}

I created a.log and c.log in the target directory, deliberately did not create ghost.log, and passed all three as arguments.

### target directory state
a.log
c.log

### DRY=1 (fake dry run)
would delete a.log
would delete ghost.log
would delete c.log
exit=0

### real run
rm: cannot remove 'ghost.log': No such file or directory
exit=0

### what remains
(nothing)

The dry run promised to delete a file that does not exist. The reason is simple: the echo path never asks whether the file is there, while rm genuinely looks it up. The two branches answer different questions to begin with.

  • What the dry run answered: which arguments entered the loop
  • What the real run answered: whether each argument names something that currently exists and can be removed

So this dry run produced a read-back of the argument list, not a prediction of the outcome. That the list is correct and that the run will succeed are entirely different propositions, but the would ... phrasing invites you to read it as the second.

One more thing hides in that output. The real run also returned exit code 0, despite the error on ghost.log. The last command in the loop, rm c.log, succeeded, and a function's exit status is that of the last command executed. Section 6 takes this up on its own.

The fix is not to copy the existence check into the dry branch. It is to compute the decision once and let both modes consume that result. Copy it and you now have two sets of conditionals, and the next person will update only one.

3. Type 2 - conditions that live only on the real path

Having been burned by type 1, most people add checks. But if the check lands inside the execution branch, things get worse rather than better: the dry run looks more credible while remaining just as wrong.

for f in src/*.dat; do
  base=${f#src/}
  if [ -n "${DRY:-}" ]; then
    echo "would archive $base"
    continue                 # ← skips every remaining check
  fi
  # ↓ both checks below exist only on the real path
  if ! mkdir "$LOCK" 2>/dev/null; then
    echo "ERROR: another run holds $LOCK" >&2; exit 3
  fi
  size=$(wc -c < "$f")
  if [ $((used + size)) -gt "$QUOTA" ]; then
    echo "ERROR: quota exceeded at $base (used=$used +$size > $QUOTA)" >&2
    rmdir "$LOCK"; exit 4
  fi
  cp "$f" "dst/$base"
  ...
done

Five files of 200 bytes each, into a destination with a 500 byte total cap.

### DRY=1 — reports all five as feasible
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0

### real run — same input, same order
archived f1.dat (used=200)
archived f2.dat (used=400)
ERROR: quota exceeded at f3.dat (used=400 +200 > 500)
exit=4

### what actually landed in dst
dst/f1.dat
dst/f2.dat

The dry run promised five and reality stopped at two, leaving a partially applied state behind. The lock behaves the same way. Here is the run with another instance already holding the lock:

### with the lock already held (another run in progress)
-- DRY=1 --
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0
-- real --
ERROR: another run holds .archive.lock
exit=3

The dry run could not even tell you that the script cannot start at all right now, because the lock check sits on the execution path. In production such conditions are more common than you would think.

  • Free disk space, inodes and quotas — easy to check only right before writing
  • Concurrency locks — the reasoning that you only need a lock when you actually do something puts it on the execution branch
  • Health checks of the target service — usually not wired into the dry path
  • Credential and token validity — a dry run that never contacts the remote cannot see expiry
  • Accumulated state — as above, where processing earlier items decides the verdict for later ones

The lesson is clean: checks that determine feasibility belong before the execution branch, not inside it. Lift the lock and quota checks into a preflight stage outside the loop and both modes pass the same gates. The plan structure in section 8 enforces exactly this.

4. Type 3 - the dry run leaves side effects

If a mode named change nothing creates and destroys files, the name is a lie. Yet this is rarely carelessness; it falls out naturally from the shell's evaluation order. I ran the script below in dry mode only.

WORK=$(mktemp -d "./tmp.XXXXXX")     # ① created regardless of mode
mkdir -p logs                         # ② likewise
exec 3>> logs/run.log                 # ③ creates the file if absent
echo "start $$" >&3

collect() {                           # ④ the redirection is evaluated outside the branch
  if [ -z "${DRY:-}" ]; then
    printf 'row-%s\n' 1 2 3
  else
    echo "would write 3 rows" >&2
  fi
} > report.csv

collect
### state before
./report.csv
./report.sh
--- report.csv content ---
old-report-do-not-lose-me

### run with DRY=1 only
would write 3 rows
exit=0

### state after (this was a dry run)
./logs
./logs/run.log
./report.csv
./report.sh
./tmp.XlPBYU
--- report.csv content ---
(0 bytes — the content is gone)
--- logs/run.log ---
start 1945
done

A single dry run created a temp directory, created a log directory and a log file, and above all truncated report.csv, which held existing data, to zero bytes. Item ④ is the crux. The > report.csv attached to the function is opened by the shell the moment the function runs, regardless of which branch executes inside. The intuition that nothing gets touched when there is nothing to print is exactly where this breaks.

The same trap appears in wrapper functions. Build a run helper and attach a redirection at the call site:

run(){ if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }
run printf 'migrated=%s\n' 3 > state.txt
--- state.txt before ---
migrated=99
--- state.txt after DRY=1 ---
+ would run: printf migrated=%s\n 3

The advisory message went inside the state file. What happens when the next run parses that file is left to your imagination. Here is the list of what a dry run must never leave behind.

  • Truncation, creation or deletion of target files — move the redirection inside the branch
  • Temporary directories — create them only in the apply stage and clean up with trap
  • Log files — send dry run output to stdout and stderr, not to a file
  • Lock files — a read-only plan needs none; whether a lock could be taken is a check, not an acquisition
  • Remote state changes — token refresh, session creation, queue consumption and other calls that look like reads but mutate
  • Caches and indexes — anything that changes the next run's decision is a side effect
How to check. List the working tree with each file's size and hash immediately before and after a dry run, then compare. If even one line differs, that dry run is not living up to its name. This comparison drops straight into CI.

5. Type 4 - later stages depend on earlier ones

The first three types disappear when you fix the code. This one does not. When stages form a chain, a dry run cannot in principle predict what comes after the first link. I built a three stage migration: stage 1 extracts an archive, stage 2 rewrites the extracted config files, stage 3 records state depending on how many stage 2 touched.

run() { if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }

echo "[1/3] extract release"
run mkdir -p release
run tar -xf release.tar -C release

echo "[2/3] patch configs"
n=0
for c in release/*.conf; do
  [ -e "$c" ] || continue
  n=$((n+1))
  run sed -i 's/^mode=old$/mode=new/' "$c"
done
echo "    targets: ${n}"

echo "[3/3] post-processing"
if [ "$n" -gt 0 ]; then ... else echo "    nothing to change, skipping"; fi
### DRY=1 (asking what it would do)
[1/3] extract release
+ would run: mkdir -p release
+ would run: tar -xf release.tar -C release
[2/3] patch configs
    targets: 0
[3/3] post-processing
    nothing to change, skipping
exit=0

### real run
[1/3] extract release
[2/3] patch configs
    targets: 3
[3/3] post-processing
    state recorded
exit=0

### files actually changed
release/app.conf:mode=new
release/db.conf:mode=new
release/web.conf:mode=new
--- migrate.state ---
migrated=3

The dry run answered zero targets, skipping, and the real run changed three files and wrote a state file. The wrapper worked flawlessly. The problem is not the wrapper, it is the structure: stage 1 never ran, so stage 2 had no input to see, and because stage 2 counted zero, stage 3 flipped entirely.

The worst part is the silence. The dry run did not say I do not know. It asserted there is nothing to do, which reads as the opposite of the truth. There are only three ways to handle this type, and each has a price.

ApproachWhat it doesPrice
Narrow the scopeDeclare that the dry run predicts only through stage 1 and mark everything after as (not predictable)Less information, but the lying stops
Model the stateRead the archive listing during planning and compute which files will exist after extractionThe model can drift from reality, so the model itself needs verifying
Isolated executionActually perform stage 1 in a throwaway workspace and plan stages 2 and 3 on top of itMost accurate but costly, and it redraws the side effect boundary

In practice the first option is usually right. A dry run that says it does not know beats one that pretends to. For the extraction example, tar -tf reads the listing alone and gets you a cheap version of the second option.

6. Type 5 - it always returns zero

Every run above printed its exit code. Look again and something stands out. The real run in section 2 emitted an error and still exited 0, and every single dry run exited 0.

When a dry run always returns zero, information travels only if a human reads the screen. A tool that assumes a human reader cannot be wired into automation. To make CI stop a build when configuration has drifted, the drift has to come out as an exit code.

There is an easy mistake here. If you use only 0 and 1, pending changes and a failed plan collapse into the same value. Those two events must be handled in opposite ways: the first waits for a human approval, the second means the pipeline is broken. Hence three values. The concrete contract and wiring are in section 10.

7. The five types at a glance

Everything reproduced so far, folded into one table. This is what I use to judge someone else's script in five minutes.

2. Real-path-only conditionsCannot warn about locks or capacitycontinue or return right after the dry branchDry predicts 5 successes, real stops at 2 with exit=4

All five share one trait: none of them raises an error. Nowhere does the script announce that its dry run is inaccurate. That is why they survive code review and are discovered only after an incident.

8. The correct shape - separate plan from apply

One structure removes all five at once: compute what you intend to do first, emit it as a list, and let the execution mode do nothing but consume that list. This is what infrastructure tools call plan and apply.

Two rules carry the whole design.

  • Plan only reads state. No writes, no creation, no deletion, no lock acquisition. Its output is sorted and free of timestamps and randomness
  • Apply does not decide. It reads plan lines and performs the named action. With no conditionals, there is nowhere for the two modes to diverge
# ---------- plan: read only. creates nothing ----------
make_plan() {
  [ -d "$REQ_DIR" ] || printf 'MKDIR\t%s\tarchive dir missing\n' "$REQ_DIR"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp)  printf 'DELETE\t%s\ttemp file\n' "$f" ;;
      *.log)  if [ -s "$f" ]; then printf 'ARCHIVE\t%s\thas content\n' "$f"
              else                 printf 'DELETE\t%s\tzero bytes\n' "$f"; fi ;;
      *.conf) if grep -qxF 'mode=old' "$f"; then
                printf 'PATCH\t%s\tmode=old\n' "$f"; fi ;;
    esac
  done
}

# ---------- apply: consumes the plan. never decides ----------
do_apply() {
  local plan="$1" action path reason
  while IFS=$'\t' read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)   mkdir -p -- "$path"  && echo "ok MKDIR   $path" ;;
      DELETE)  rm -f -- "$path"     && echo "ok DELETE  $path" ;;
      ARCHIVE) mkdir -p -- "$REQ_DIR"; mv -- "$path" "$REQ_DIR/" && echo "ok ARCHIVE $path" ;;
      PATCH)   sed -i 's/^mode=old$/mode=new/' -- "$path" && echo "ok PATCH   $path" ;;
      *)       echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)  make_plan | LC_ALL=C sort
         n=$(make_plan | grep -c . || true)
         [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply) do_apply "${2:?a plan file is required}" ;;
esac

Proving it by running plan three times

An assertion is worthless on its own. I built the plan three times against the same state and compared it byte for byte.

run#2 exit=2 sha256=072c4bfb98ee74f7be43c92b2f7824a9c5aa926211cc9df111b84d1645b7cc0f
run#3 exit=2 sha256=072c4bfb98ee74f7be43c92b2f7824a9c5aa926211cc9df111b84d1645b7cc0f

access.log app.conf build.tmp cache.tmp db.conf empty.log

All three produced 072c4bfb98ee..., and the directory gained no files at all. The side effects from section 4 are structurally impossible here, because plan contains no write commands.

Now let the plan be consumed.

### apply — consuming the plan only
ok ARCHIVE data/access.log
ok DELETE  data/build.tmp
ok DELETE  data/cache.tmp
ok DELETE  data/empty.log
ok MKDIR   data/archive
ok PATCH   data/app.conf
exit=0

### plan again after apply
exit=0 (0 = no changes)
--- final state of data ---
data/app.conf data/archive data/archive/access.log data/db.conf

Planning again after apply returned an empty plan and exit code 0. That is the last advantage of the structure: the emptiness of the plan is itself the proof that the target state was reached. No separate verification script is needed.

Keeping plan deterministic. Never put date, $RANDOM, process IDs or traversal order into the output. The order of for f in dir/* can depend on locale, so pin it with LC_ALL=C sort. Adding a reason column keeps the plan human readable without breaking hash comparison.

9. When the plan goes stale - lock it with a hash

Splitting plan from apply opens a new gap: state can change between the moment you plan and the moment you apply. Add an approval step and that interval can stretch to hours. If someone adds a file in between, the approved plan and what actually happens no longer match.

The remedy is already built. Store the plan's hash alongside it, and have apply recompute the plan from current state just before executing and compare. If they differ, refuse.

apply)
  want=$(sed -n '1p' "$p.sha" 2>/dev/null || echo '')
  have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
  if [ -n "$want" ] && [ "$want" != "$have" ]; then
    echo "ERROR: state changed since the plan (plan=$want / now=$have)" >&2
    exit 1
  fi
  do_apply "$p" ;;
### 1) build the plan
plan exit=2
988ca65d91ce2783486a7216bdfb8dca47db67b8e1af3c0a664080c127aeab83
DELETE  data/cache.tmp  temp file
MKDIR   data/archive    archive dir missing
PATCH   data/app.conf   mode=old

### 2) someone adds a file between plan and apply
app.conf cache.tmp late.tmp

### 3) apply with the stale plan
ERROR: state changed since the plan (plan=988ca65d... / now=84f56a62...)
exit=1

### 4) replanning makes it pass
plan exit=2
ok DELETE  data/cache.tmp
ok DELETE  data/late.tmp
ok MKDIR   data/archive
ok PATCH   data/app.conf
apply exit=0

At step 3 apply refused to run, because the approved plan did not contain late.tmp. Replanning at step 4 included it and passed. That one layer buys a lot.

  • Approval regains meaning — a machine guarantees that what a human approved is what will execute
  • Races surface early — if two pipelines run concurrently, the second one is rejected
  • Reproducible postmortems — the plan file and its hash record what was done and why

There are caveats. The comparison computes the plan a second time, which costs real time on large targets. And it rejects some irrelevant changes too. In the example above late.tmp genuinely affected the plan, but a new file that does not change the plan's content leaves the hash unchanged and passes. The hash locks the plan, not the directory. That distinction is what makes the technique practical rather than obstructive.

10. The exit code contract and CI wiring

Back to what section 6 deferred. The widely used contract uses three values.

CodeMeaningCI behaviourHuman action
0No changes — matches the target statePassNone
2Pending changesFail, or wait for approvalRead the plan, approve or amend
1Could not produce a plan (error)Fail immediately and alertRepair the pipeline

Assigning 2 to changes present is a convention. It follows the long tradition of diagnostic tools splitting fine, differences found, and failed to run across 0, 1 and 2; here I reserved the more common 1 for errors and used 2 for drift instead. Whatever numbers you pick, the point is that three states are distinguishable.

Three things that break the wiring in practice

Even with a contract, shell wiring undoes it. I reproduced three failures.

### A) calling it directly under set -e
exit=2
   (the line "we got this far" never printed — everything after was skipped)

### B) wrapping it in if collapses 2 and 1
changes present (or error)     ← a legitimate drift (2)
changes present (or error)     ← an error from a bad subcommand (1)
exit=0

### D) inside a pipe the status belongs to tee
$?=0  PIPESTATUS=2 0

A is the one you meet most often. set -e treats every nonzero value as failure, so a 2 that means changes present kills the script. B is quieter. if only asks whether the status is zero, so 2 and 1 fall into the same branch. In the output above the two lines are a genuine drift and a real error, printing identically. D bites when you pipe the plan through tee to keep a copy; a pipeline's status is that of its last command, so tee's 0 wins.

The shape that dodges all three:

#!/usr/bin/env bash
set -uo pipefail
rc=0
./tidy.sh plan > plan.txt || rc=$?          # ← capture the code without dying
case "$rc" in
  0) echo "OK: matches target state (0 changes)"; exit 0 ;;
  2) echo "DRIFT: $(grep -c . plan.txt) pending"; sed 's/^/    /' plan.txt; exit 1 ;;
  *) echo "FAIL: could not build a plan (rc=$rc)" >&2; exit 2 ;;
esac
### C) split into three arms per the contract
DRIFT: 3 pending
    DELETE  data/cache.tmp  temp file
    MKDIR   data/archive    archive dir missing
    PATCH   data/app.conf   mode=old
CI exit=1

### E) rerunning the same CI job after apply
apply exit=0
OK: matches target state (0 changes)
CI exit=0

On drift it unfolded the plan into the log and failed the build; after applying, the same job passed. Practical points when wiring this into CI:

  • Do not change flags — the command line that produced the plan and the one that applies it must share targets, filters and exclusions exactly
  • Store the plan as an artifact — approval, audit and postmortem all reduce to that one file
  • Plan on the pull request, apply after merge — hang the approval gate on exit code 2
  • Schedule plan-only runs to watch for drift — a daily plan returning 2 when nobody deployed means somebody changed things by hand
  • Do not escalate 2 to a failure in scheduled jobs — alert instead; a permanently red dashboard is a dashboard nobody reads
  • pipefail and PIPESTATUS — decide explicitly which stage's status you care about when piping

11. How far can you trust an existing tool's dry run

Having covered building your own, the obvious next question is what the established tools do. The short answer: the dry runs of widely used tools are broadly trustworthy, and better still, they document their own boundaries. The trouble comes not from the tool but from a human changing flags between the two runs.

Reproduction - same tool, different flags

I created a scratch repository containing untracked files and directories, a directory matched by an ignore rule, and a nested separate repository.

### git clean -n (default)
Would remove .gitignore

### git clean -nd (including directories)
Would remove .gitignore
Would remove work/

### git clean -ndx (including ignored files)
Would remove .gitignore
Would remove ignored/
Would remove work/

### real run: git clean -fd
Removing .gitignore
Removing work/

### what remains
./ignored  ./ignored/c.txt  ./nested  ./nested/.git  ./nested/n.txt

The three dry runs give three different answers, and each one matches exactly what the same flags do for real. The official documentation says so plainly: -n means do not actually remove anything, just show what would be done, and -d means that normally git clean will not recurse into untracked directories to avoid removing too much; specify -d to have it recurse into such directories as well.

So here is how the accident happens: you check with git clean -n and run with git clean -fd. In the output above, -n showed a single line for .gitignore, while -fd wiped out the entire work/ tree containing two files. The dry run did not lie; it answered a different question. And note that the Would remove work/ shown by -nd is one line. It does not tell you how many files sit inside. Counting dry run lines is not a way to count deletions.

The nested repository is interesting too. -ndx omitted nested/ from the listing entirely, and it appeared only once I added -ndxff. The documentation states that git will refuse to modify untracked nested git repositories (directories with a .git subdirectory) unless a second -f is given. The dry run was faithfully mirroring the real behaviour, not omitting something.

A tool that states its own boundary

rsync is not installed in this environment, so I could not run it. Instead I quote the boundary its official documentation draws. This paragraph is documentation, not execution evidence.

The rsync manual describes --dry-run as a trial run that produces mostly the same output as a real run. It then notes that a dry run does not send the actual data, so --progress has no effect, the bytes sent, bytes received, literal data and matched data statistics are too small, and the speedup value equals that of a run where no transfers were needed. Meanwhile it states that --itemize-changes output is supposed to be exactly the same on a dry run and a subsequent real run, and that any difference is a bug.

That passage is a model of what a well built dry run looks like. It draws the line item by item: what will change is identical, how long it takes and how many bytes move is not. The same attitude is what we need when building our own. Writing down which axes you predict and which you cannot, right there in the help text, is trustworthiness.

The practical rules for using existing tools are short.

  • Use the same command line — verify with nothing added but -n, and add no other flags when you execute
  • Keep the listing as an artifact — save the dry run output to a file and diff it against the real result
  • Read the items, not the count — one directory line can be hundreds of files
  • Read the exceptions section — a well built tool documents what it cannot predict
  • Be extra sceptical when a remote is involved — permissions, path handling and timestamp interpretation can differ on each side

12. What a dry run can never predict

Some territory remains no matter how well you design. Writing this list into your help text is the final condition of an honest dry run.

Not predictableWhyMitigation
Elapsed timePlanning and applying happen at different moments; retention windows, expiries and cron boundaries cross in betweenFreeze the reference timestamp into the plan and pass it to apply
Concurrent changesAnother process or person touches the same targetsThe plan hash check from section 9, plus a lock during apply
Resource exhaustionDisk, inodes and memory only run out at the moment of useSum the totals during planning and compare with headroom, flagged as an estimate
Permissions and policyThe executing user, security modules and mount options intervene at write timeTry a probe write on one representative path, or mark it not predictable
Remote stateAPI responses, server side validation and rate limits are only known by callingUse the server's own validation-only mode where one exists
Chained artifactsSection 5 — an earlier stage's output is a later stage's inputPin the scope to the first stage, or read the listing ahead of time
Life after partial failureStopping midway means the rest of the plan would run on a different stateAbort on failure and rebuild the plan

The last row matters most. A plan is valid only on the state it was planned against. If you failed halfway through applying, do not push the remaining half. Discard the plan and build a new one, which in the section 8 structure is a single command.

Conclusion: a dry run is a function, not a mode

The five types reproduced here share one trait: they all fail quietly. One promises to delete a file that does not exist; one announces five and stops at two; one claims to change nothing while emptying an existing file; one asserts there is nothing to do and then changes three files; and through all of it the exit code stays zero. Not one of them says my prediction is unreliable.

So the test collapses to a single question. Did the dry run travel the same decision path as the real run? If it evaluated the same conditions and selected the same targets in the same order, its output is a prediction. If it only read the argument list back, it is an imitation. And so far there has been exactly one way to answer that question with confidence: keep the decision in one place — let plan decide alone and let apply only consume.

Three things make that structure good. First, there is no code where the two modes could diverge, so types 1 and 2 cannot occur. Second, verification comes for free: three hashed runs prove determinism, and an empty plan after apply proves convergence. Third, approval and audit reduce to one file — the plan and its hash are the record.

One thing you can do today. Run your script's dry mode inside an empty scratch directory and compare the file listing and hashes before and after. If a single line differs, that dry run is already changing something. Then print its exit code. If it is always zero, that dry run is a safety device that works only while a human is reading the screen. A safety device nobody reads is not a safety device.

# Dry Run Design Checklist — skim this before you build one

> Source: braindetox.kr — How to Build a Real --dry-run
> Basis: POSIX Issue 8 (Shell Command Language), Bash Reference Manual, git-clean(1), rsync(1)
> Paste this file into an AI assistant and say: rewrite our script against these rules.

## 1. Plan / apply skeleton — copy this shape

```bash
#!/usr/bin/env bash
# usage: tool.sh plan|apply [planfile]
#   exit codes  0=no changes · 2=changes pending · 1=error
set -uo pipefail
TAB=$(printf '\t')          # a variable instead of ANSI-C quoting (portability)

make_plan() {               # ★read only. no create, no delete, no lock
  [ -d "$REQ_DIR" ] || printf 'MKDIR%s%s%smissing\n' "$TAB" "$REQ_DIR" "$TAB"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp) printf 'DELETE%s%s%stemp file\n' "$TAB" "$f" "$TAB" ;;
    esac
  done
}

do_apply() {                # ★never decides. unknown action is an error
  local plan="$1" action path reason
  while IFS="$TAB" read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)  mkdir -p -- "$path" ;;
      DELETE) rm -f -- "$path" ;;
      *) echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)
    make_plan | LC_ALL=C sort
    n=$(make_plan | grep -c . || true)
    [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply)
    p="${2:?a plan file is required}"
    want=$(cat "$p.sha" 2>/dev/null || echo '')
    have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
    [ -z "$want" ] || [ "$want" = "$have" ] || {
      echo "stale plan (plan=$want now=$have)" >&2; exit 1; }
    do_apply "$p" ;;
  *) echo "usage: tool.sh plan|apply [planfile]" >&2; exit 1 ;;
esac
```

- [ ] Plan contains **not a single** write command
- [ ] Apply contains **no conditionals** that inspect state
- [ ] Each plan line carries a **reason column** (a human has to approve it)
- [ ] Output order is pinned with `LC_ALL=C sort`

## 2. Exit code contract

| Code | Meaning | CI behaviour |
|---|---|---|
| `0` | No changes — matches target state | Pass |
| `2` | Changes pending | Fail, or wait for approval |
| `1` | Could not build a plan | Fail immediately and alert |

- [ ] Under `set -e`, capture with `rc=0; cmd || rc=$?`
- [ ] Do not let `if cmd; then` **collapse 2 and 1**
- [ ] Read `PIPESTATUS` when the command is piped
- [ ] Document the code meanings in the help text
- [ ] Scheduled jobs alert on 2 instead of turning red permanently

## 3. Side effects banned from the plan stage

- [ ] Creating, deleting or truncating target files (including a `>` redirection)
- [ ] Work directories from `mktemp` or `mkdir -p`
- [ ] Opening log files (`exec 3> ...` creates the file **at open time**)
- [ ] Acquiring lock files or lock directories (only *check* whether one is free)
- [ ] Remote state changes (token refresh, session creation, queue consumption)
- [ ] Cache and index updates (anything that alters the next run's decision)

★ **Redirections are evaluated outside the branch.** `f(){ ...; } > out` truncates `out` even in dry mode.
★ Writing `run cmd > state` in a wrapper puts the advisory text **inside the state file**.

## 4. Verification procedure — three hashes and zero side effects

```bash
snap(){ find "$1" -type f | LC_ALL=C sort | xargs -r sha256sum | sha256sum; }

before=$(snap target)
for i in 1 2 3; do ./tool.sh plan > "p.$i"; echo "run$i $(sha256sum < "p.$i")"; done
cmp -s p.1 p.2 && cmp -s p.2 p.3 && echo DETERMINISTIC || echo "★output drifts"
after=$(snap target)
[ "$before" = "$after" ] && echo "NO SIDE EFFECT" || echo "★plan mutated state"
```

- [ ] All three hashes match
- [ ] Before and after snapshots match
- [ ] Planning again after apply yields an **empty plan and exit code 0**
- [ ] Applying a stale plan is **refused**

## 5. Conditions under which a dry run lies — document any that apply

- [ ] Checks that exist **only inside** the execution branch (lock, capacity, permission, health)
- [ ] A **chain** where later stages read what earlier stages produced
- [ ] Operations where **time passes** between plan and apply (approval, batching)
- [ ] Branching on remote API responses or server side validation
- [ ] A different executing user, security policy or mount option
- [ ] **Resuming after partial failure** (the remaining plan runs on a different state)
- [ ] Timestamps, randomness or traversal order leaking into the result

## 6. When using an existing tool

- [ ] Does the verification command line differ from the real one by `-n` alone
- [ ] Did you **save the dry run output to a file** and diff it against the result
- [ ] Did you avoid counting one directory line as one file (it can be hundreds)
- [ ] Did you read the **exceptions section** (statistics and progress are often out of scope)
- [ ] With a remote involved, did you re-examine permissions, paths and timestamp handling

## 7. Help text template

```
--dry-run   Print the plan without applying any change.
            Predicted     : <fill in>
            Not predicted : <fill in>
            Exit codes    : 0 = no changes / 2 = changes pending / 1 = error
            This mode creates and deletes nothing.
```

★ When testing destructive commands, run them **only inside a freshly created empty temporary directory.**
