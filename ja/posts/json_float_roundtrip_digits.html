はじめに - 同じ数でなくなる2つの方向

doubleはメモリ上では64ビットだが、ファイル・ログ・JSON・CSVの中では文字である。値を文字として書く瞬間と文字を読み戻す瞬間の間で何桁を使うかが、値の同一性を決める。このときの「往復」には方向が2つあり、保証される桁数が違う。

  • 文字 → double → 文字: 人が書いた十進文字列がそのまま復元されるか。保証される桁数は15である。
  • double → 文字 → double: 計算で得た値が同じビットで復元されるか。必要な桁数は17である。
  • 2つの方向を混ぜて「15桁までは安全」と言うと、計算結果を15桁で保存するコードが静かに値を変える。

扱う問いは次のとおりである。

  • 6・9・15・16・17桁で書いた文字を読み戻すと、何個が別のビットになるか。
  • PythonのreprとJavaScriptのtoStringが選ぶ「最短往復表記」は何を保証するか。
  • 17桁が必要な値はどんな姿か。
  • Python・Node・PowerShell 5.1・awk・SQLiteは、設定なしで何桁を出力するか。
  • ツール間で値が変わる事例は、書く側と読む側のどちらで起きるか。

JSON数値精度の記事の8節は、15・16・17桁の失敗数を20万個の標本で数えている。この記事はその表を繰り返さず、ビットパターン・算術結果・15桁以下の入力という3種類の標本の対比、float32の6・9桁、ツールの既定の出力桁数、ツール間のやり取りでの変数の切り分けを扱う。

ビットで見る0.1と0.1+0.2

Python公式チュートリアルの浮動小数点のページは、IEEE 754 binary64の値が53ビットの精度を持ち、0.1は3602879701896397 / 2 ** 55で近似されると書いている。同じページは、0.1、0.10000000000000001、0.1000000000000000055511151231257827021181583404541015625がすべて同じ近似値を指すので、どれを表示してもeval(repr(x)) == xが保たれると説明している。この説明をビットと16進表記で確かめたコードである。

出力から読み取れることは次のとおりである。

  • 0.1+0.2のビットは3FD3333333333334で、0.3のビットは3FD3333333333333である。最後のビットが1つ違い、2つは別のdoubleである。

  • %.17gで書くと0.30000000000000004になり、読み戻すと元のビット(...334)に戻る。
  • 0.3の周りの隣のdoubleは0.29999999999999993、0.3、0.30000000000000004である。17桁は隣の値と区別するのに必要な桁数である。
  • 0.1を17桁で書くと0.10000000000000001で、reprは0.1である。2つの文字は同じdoubleに戻る。

6・9・15・16・17桁の往復表 - 3種類の標本

次のコードは標本を3種類作り、%.Ngで書いた文字をfloatとして読み戻して64ビットをすべて比べる。Aはランダムな64ビットパターンのうち有限の値(指数の全範囲)、Bは通常の範囲の算術結果(掛け算と割り算)、Cは有効数字1〜15桁で入力した十進文字から作った値である。float32も同じ方法で数える。

import random, struct, math, sys
                    def bits(x): return struct.unpack('<Q', struct.pack('<d', x))[0]
                    def f32(x): return struct.unpack('<f', struct.pack('<f', x))[0]
                    def f32bits(x): return struct.unpack('<I', struct.pack('<f', x))[0]
                    print(sys.version.split()[0], 'float_info.dig =', sys.float_info.dig, ' mant_dig =', sys.float_info.mant_dig)
                    rnd = random.Random(20261006)
                    N = 100000
                    A = []
                    while len(A) < N:
                        x = struct.unpack('<d', struct.pack('<Q', rnd.getrandbits(64)))[0]
                        if math.isfinite(x): A.append(x)
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(N)]
                    C = [float('%.*g' % (rnd.randint(1, 15), rnd.uniform(-1e6, 1e6))) for _ in range(N)]
                    def fails(S, n):
                        return sum(1 for x in S if bits(float('%.*g' % (n, x))) != bits(x))
                    print('double, %d values per set; text = %%.Ng, then float(text), compare all 64 bits' % N)
                    print('%-4s %10s %10s %10s' % ('N', 'A:bitpat', 'B:arith', 'C:<=15dig'))
                    for n in (6, 9, 15, 16, 17):
                        print('%-4d %10d %10d %10d' % (n, fails(A, n), fails(B, n), fails(C, n)))
                    F = [f32(rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000)) for _ in range(N)]
                    def f32fails(n):
                        return sum(1 for x in F if f32bits(f32(float('%.*g' % (n, x)))) != f32bits(x))
                    print('float32, %d values; text = %%.Ng, then back to float32' % N)
                    for n in (6, 7, 8, 9):
                        print('N=%d  failures=%d' % (n, f32fails(n)))

表から読み取れる規則は次のとおりである。

  • AとBでは17桁の失敗が0件である。15桁では約94%、16桁では約42〜45%が別のビットで戻った。doubleを文字として書く側では、15桁は安全線ではない。
  • Cでは15・16・17桁のすべてが0件である。Pythonドキュメントのsys.float_info.digの説明、つまり有効数字15桁以下の十進文字列はfloatに変えて書き戻すと同じ十進値が復元されるという文と一致する。同じページは、16桁の文字列9876543211234567を.16gで書き戻すと9876543211234568に変わる例を挙げている。
  • Cの6桁と9桁の失敗(59411、39308)は、入力の文字が最大15桁だったため、6・9桁に切り詰めた時点で値が変わったものである。書く側の桁数が元の文字より短ければ、どちらの方向でも復元されない。
  • float32は9桁で0件、8桁で1568件が失敗する。Microsoft Learnの標準数値書式の文書はDoubleにG17、SingleにG9を使うよう書いており、この表と一致する。
  • 標本で失敗が0件でも、すべてのdoubleの証明ではない。17桁が必要だという根拠は、この標本とMicrosoft Learnの推奨が同じ方向を指していることである。

最短往復表記 - reprとtoStringがすること

毎回17桁を書くと0.1が0.10000000000000001になり、読みにくい。Pythonドキュメントは3.1からreprが候補のうち最も短い文字列を選ぶと書き、sys.float_repr_styleがshortのときfloat(repr(x)) == xが成り立つと説明している。ECMAScript仕様のNumber::toStringはs・n・kを決めるときkをできるだけ小さくすると定め、MDNはtoStringが隣の値と区別するのに必要な最小の有効桁数を使うと書いている。この「最短」が値ごとに何桁になるかを数えたコードである。

import random, collections
                    rnd = random.Random(20261006)
                    def need(x):
                        for n in range(1, 18):
                            if float('%.*g' % (n, x)) == x: return n
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(100000)]
                    h = collections.Counter(need(x) for x in B)
                    print('smallest N with float(%.Ng) == x, 100000 arithmetic values:')
                    for n in sorted(h): print('  N=%2d  %6d' % (n, h[n]))
                    print('examples (digits needed, repr):')
                    for x in (0.1, 0.1 + 0.2, 0.1 * 3, 1.1 * 1.1, 0.1 + 0.7, 1 / 3, 2 / 3, 100 * 1.1, 1e23, 5e-324):
                        print('  %2d  %s' % (need(x), repr(x)))

  • Microsoft Learnの標準数値書式の文書は、G書式の既定の桁数をDoubleについて「往復可能な最小の桁数(.NET FrameworkではG15が既定)」と書いている。PowerShell 5.1の15桁出力はこの文と同じ値である。このPCの5.1は.NET Framework上で動く。

  • Node toLocaleStringはこのPCのロケールで小数3桁までしか書かなかった。数値の書式関数は値を保つシリアライズの経路ではない。

ツール間のやり取り - 値を決めるのは書く側

ツール間で値が変わる原因が書く側か読む側かは、変数を切り分けて初めて分かる。次の実験では、Pythonが2000個の値のビットパターン(16進)をファイルに書き、書くツール3つが同じ値をそれぞれの方法で8個のテキストファイルに書き、読むツール3つがその8個を全部読んで元のビットと比べる。書き方は8通り、読むツールは3つで、データは同じである。

何をどう書くか - 選択基準

実行で得た結果を、書く目的別に整理すると次のとおりである。

目的書き方この記事で見た根拠
人が読む表示、復元不要%g・G15・toLocaleStringなどの短い書式5節の出力。値の一部を捨てる
復元が必要なdouble(JSON・ログ・CSV)最短往復(repr・JSON.stringify)または有効数字17桁(%.17g・G17)3節の17桁0件、6節の表

ツール間で値が変わったかの確認同じファイルを2つのツールで読みビット(16進)を比べる6節の構成
  • 復元が目的なら、「何桁で書くか」よりも「最短往復か17桁か」を先に確認する。
  • 15桁は文字 → double → 文字の方向の保証なので、人が入力した値の表示には合い、計算結果の保存には合わない。
  • 書くツールの既定の桁数は、ツールと出力経路ごとに違う。同じPowerShell 5.1の中でも、補間とConvertTo-Jsonが違う。
  • 値の比較には文字ではなくビットを使う。Pythonはstruct、NodeはDataView、PowerShellはBitConverterで64ビットを取り出せる。
  • 大きな整数に近い値や64ビットIDの問題は、ここで扱った小数の桁数とは別で、JSON数値精度の記事で扱っている。

確認できなかったこと

  • PowerShell 7と最新の.NET。このPCにpwshはない。Microsoft LearnはDoubleのG書式の既定桁数を「往復可能な最小の桁数」と書き、.NET FrameworkだけをG15と区別しているが、実行で比べられなかった。
  • Java・Go・Rust・Cなど他の言語と、Node以外のJavaScriptエンジンの既定の出力桁数。
  • 17桁がすべてのdoubleで復元されるという全数の証明。標本は3種類で各10万個である。
  • ConvertTo-Jsonがどの値に15桁を、どの値に17桁を使うかの規則。反例1つと2000個の標本の結果だけがある。
  • PowerShell 5.1のDecimalキャストが1ビットずれる原因と、double.Parseが-6667.211341195974を違うように読む原因。
  • 無限大・NaN・負のゼロ・非正規数(subnormal)の往復。標本Aに非正規数が含まれたかは数えていない。
  • ConvertTo-Jsonにオブジェクトや配列を渡したときの桁数。スカラーのdoubleだけを渡した。
  • LinuxとmacOSでの動作と、カンマを小数点に使うロケール。PowerShellのコードはInvariantCultureに固定した。
  • SQLiteのprintfで%.17gが17桁で出なかった現象。実行では0.3と出たが、原因は調べていない。
