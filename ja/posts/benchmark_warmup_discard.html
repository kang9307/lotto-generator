はじめに - 最初の数字はコードの速度ではない

繰り返し測定では、最初の呼び出しが以後の呼び出しより数倍から数千倍遅いことがよくある。この値を平均に入れると、関数の速度ではなく「最初の1回だけ払うコスト」が平均に混ざる。そのコストの正体は1つではない。モジュールのimport、正規表現のコンパイルキャッシュ、ユーザーコードの遅延初期化、JITコンパイラの段階的な最適化は、大きさも続く時間も異なる。したがってウォームアップを何回捨てるかは勘ではなく、同じ関数の回ごとの時間から決める必要がある。

すでに集めた測定値を合算する問題はパーセンタイル集計の誤りの記事が、どの時計で測るべきかは単調時計と壁時計の記事が扱う。ここでは測定値ができる前の段階、つまり何回目の呼び出しから測定値として使えるかに範囲を絞る。

扱う問いは次のとおりである。

  • 初回呼び出しの遅れがimport・正規表現キャッシュ・遅延初期化のどれから来るのかを、変数を分離して切り分けられるか。
  • 同じ関数を繰り返し呼ぶとき、回ごとの時間はどのような形で下がるか。
  • 捨てる回数を、移動中央値が安定する点としてコードで決められるか。
  • ウォームアップを含む平均と、捨てた後の平均は、安定時の値からどれだけ離れるか。
  • 測定が揺れる環境で、その判定を信じてよいかをどう検査するか。

計測ツールと公式文書の記述

Pythonのtimeit文書は、既定のタイマーが常にtime.perf_counter()だと述べる。同じ文書は、timeit()が測定中にガベージコレクションを一時的に止めること、その利点は独立した測定を比較しやすくすることで、欠点はGCが測定対象の性能の重要な一部かもしれないことだと説明する。繰り返し測定の結果については、平均と標準偏差を計算して報告してもあまり有用でなく、高い値は多くの場合Pythonの速度変動ではなく他のプロセスが測定を妨げるために生じるので、min()がおそらく唯一見るべき数だと述べる。

Node側の時計はperf_hooksのperformance.now()である。MDNはこのメソッドを、ミリ秒単位の高解像度タイムスタンプを返し、timeOriginからの経過時間を表すと説明する。そのページの解像度の記述(隔離された文脈で5マイクロ秒、そうでなければ100マイクロ秒)はWeb文書のブラウザ文脈についてのものである。以下のNode出力は、呼び出し1回を2回のperformance.now()で挟んだ値である。

  • Python: 呼び出し1回をtime.perf_counter()で挟みマイクロ秒に換算する。繰り返し測定にはtimeit.repeat()を使う。
  • Node: 呼び出し1回をperformance.now()で挟みマイクロ秒に換算する。内部の最適化オプションは使わない。
  • 変数分離: 新しいプロセスで初回と2回目を測り、条件を1つだけ変えて同じ測定を繰り返す。
  • 判定: 回ごとの時間に移動中央値を適用し、最後に定常性検査をする。

CPythonの初回呼び出し - 変数を1つずつ変えた実験

以下のコードの前半は、新しいインタプリタプロセスを起動して同じ関数を2回呼び、初回と2回目の時間をマイクロ秒で出す。親プロセスは5つの条件をそれぞれ7つの新しいプロセスで実行し、中央値を出す。隣り合う条件は1点だけが異なる。

import sys, time, re, subprocess, statistics, platform, random
                    
                    def us(fn, *a):
                        t = time.perf_counter(); fn(*a); return (time.perf_counter() - t) * 1e6
                    
                    # ---------- child mode: one fresh interpreter, time call 1 and call 2 ----------
                    def child(case):
                        if case == "import_cold":
                            print("sqlite3 already loaded:", "sqlite3" in sys.modules)
                            def f():
                                import sqlite3
                                return sqlite3.sqlite_version
                        elif case == "import_warm":
                            import sqlite3
                            def f():
                                import sqlite3
                                return sqlite3.sqlite_version
                        elif case == "re_cold":
                            re.purge()
                            def f(): return re.search(r"(\d{4})-(\d{2})-(\d{2})", "date: 2026-10-06 end")
                        elif case == "re_precompiled":
                            c = re.compile(r"(\d{4})-(\d{2})-(\d{2})")
                            def f(): return c.search("date: 2026-10-06 end")
                        elif case == "lazy_table":
                            box = {}

                                if "t" not in box:

                        child(sys.argv[1]); sys.exit()

                    print("python", platform.python_version(), sys.platform)
                    print("A. fresh process, call 1 vs call 2 (us), median of 7 processes")
                    print("%-16s %12s %12s %8s" % ("case", "call 1", "call 2", "ratio"))
                    for case in ["import_cold", "import_warm", "re_cold", "re_precompiled", "lazy_table"]:
                        r = []
                        for _ in range(7):
                            o = subprocess.run([sys.executable, __file__, case], capture_output=True, text=True).stdout.split()[-2:]
                            r.append((float(o[0]), float(o[1])))
                        c1 = statistics.median(x[0] for x in r); c2 = statistics.median(x[1] for x in r)
                        print("%-16s %12.1f %12.1f %8.1f" % (case, c1, c2, c1 / c2))
  • import_cold: 関数の中でsqlite3をimportする。プロセス開始時、sqlite3はまだ読み込まれていないモジュールである(出力のloaded行を参照)。
  • import_warm: 同じ関数だが、時間を測る前にsqlite3を先にimportしておく。import_coldとの違いはこの1点だけである。
  • re_cold: re.purge()で正規表現キャッシュを空にしてから、文字列パターンでre.searchを呼ぶ。
  • re_precompiled: パターンを計測前にre.compileで作っておき、searchだけを呼ぶ。re_coldとの違いはコンパイルが計測区間の中にあるかどうかの1点である。
  • lazy_table: 初回に20万項目の辞書を作って保持し、以後は再利用するユーザーコードの遅延初期化である。

出力から読み取れることは3つある。第一に、import_coldとimport_warmは関数本体が同じで、モジュールを先に読み込んだかどうかだけが異なる。初回が13248.8から1.8に下がったので、このPCでimport_coldの初回の遅れは関数内のimportが作ったものである。Pythonの文書は、import時にモジュール名がまずsys.modulesで探され、あればその値がimportを満たして処理が終わると述べる。文書が述べるのはキャッシュの存在であり、速度の差はimport_warmとre_precompiledの対照出力が示す。

第二に、re_coldとre_precompiledはコンパイルが計測区間の中にあるかどうかだけが異なる。280.7が15.7に下がった。reの文書は、re.compile()とモジュールレベルのマッチ関数に渡した最近のパターンのコンパイル結果がキャッシュされ、re.purge()がそのキャッシュを消すと述べる。キャッシュを空にした直後の初回だけがコンパイルコストを払ったことになる。第三に、lazy_tableの48073.7は、初回の中に20万項目の辞書を作るコードがあるために生じた値で、表を再利用するだけの2回目は同じ出力で3.6だった。

残る差もある。import_warmの1.8対1.0と、re_precompiledの15.7対2.9は、数マイクロ秒から十数マイクロ秒規模の初回超過である。この規模の差は、次の時系列の節にある収束判定が扱う対象である。

同一プロセスの時系列 - 1回のスパイクが平均を変える

コードの後半は、1つのプロセスで同じ関数を160回呼んだ時系列に判定関数を適用する。判定関数は3つある。settle_indexは、窓5の移動中央値が安定水準(後ろ半分の中央値)の25パーセント以内に10回連続で留まる最初の点を返す。stationaryは後ろ2つの四分位区間の中央値を比べる。spike_countは最初の20回のうち安定水準の3倍を超える最後の回を数える。

# ---------- detectors ----------
                    def settle_index(t, w=5, tol=0.25, run=10):
                        """First call index from which run consecutive moving medians (window w)
                        stay within +-tol of the steady level (median of the last half)."""
                        ref = statistics.median(t[len(t) // 2:])
                        mm = [statistics.median(t[i:i + w]) for i in range(len(t) - w + 1)]
                        for i in range(len(mm) - run + 1):
                            if all(abs(m - ref) <= tol * ref for m in mm[i:i + run]):
                                return i, ref
                        return None, ref
                    
                    def stationary(t, tol=0.25):
                        q = len(t) // 4
                        a, b = statistics.median(t[2 * q:3 * q]), statistics.median(t[3 * q:])
                        return abs(a - b) <= tol * b, a, b
                    
                    def spike_count(t, k=3.0, head=20):
                        ref = statistics.median(t[len(t) // 2:])
                        bad = [i for i, x in enumerate(t[:head]) if x > k * ref]
                        return bad[-1] + 1 if bad else 0
                    
                    random.seed(42)
                    data = [random.random() for _ in range(2000)]
                    def pure():
                        s = 0.0
                        for x in data: s += x * x
                        return s
                    def lazy_series():
                        import sqlite3
                        return sqlite3.sqlite_version
                    
                    print()
                    print("sqlite3 loaded before series:", "sqlite3" in sys.modules)
                    series = {"pure": [us(pure) for _ in range(160)],
                              "import-in-call": [us(lazy_series) for _ in range(160)]}
                    print("B. 160 calls in one process (us)")

                        ok, qa, qb = stationary(t)
                        print("%-15s first 6: %s" % (name, " ".join("%.1f" % x for x in t[:6])))
                        print("%-15s steady %.1f | settle index %s | spike count %d | stationary %s (%.1f vs %.1f)" % (
                            "", ref, idx, spike_count(t), ok, qa, qb))
                    
                    print()
                    print("C. naive mean of all 160 calls vs mean after discarding spike_count calls (us)")
                    for name, t in series.items():
                        k = spike_count(t)
                        print("%-15s naive %.2f | discard %d -> %.2f | median %.2f" % (name, statistics.mean(t), k, statistics.mean(t[k:]), statistics.median(t)))

                    r = timeit.repeat(pure, number=50, repeat=7)
                    print()
                    print("D. timeit.repeat(pure, number=50, repeat=7), us per call:", " ".join("%.1f" % (x / 50 * 1e6) for x in r))
                    print("   min %.1f | median %.1f" % (min(r) / 50 * 1e6, statistics.median(r) / 50 * 1e6))

  • 窓5・許容25パーセント・連続10回はここで決めた値であり、文書の規定ではない。

ノイズがウォームアップを隠す - 定常性検査とtimeitの最小値

B出力(このPCでの1回の実行)のpure系列は、最初の6回がすべて421〜431マイクロ秒台である。安定水準は151.7と計算され、settle indexは16である。しかしstationaryはFalseで、後ろ2区間の中央値が205.6対53.2マイクロ秒と4倍近く開いた。同じコードが1つのプロセスの中で数秒のうちに53から431マイクロ秒まで動いたのである。このPCでの揺れの原因は出力だけでは切り分けられない。3回の再実行では最初の6回が80〜323マイクロ秒で、stationaryはFalse・True・Falseに分かれた。

この場合、settle index 16はウォームアップの証拠ではない。定常性検査を通らない系列では、捨てる回数の計算そのものを使わず、測定をやり直す。D出力は同じ関数をtimeit.repeatで7回繰り返した値で、1回の繰り返し(50回呼び出し)あたりの時間が59.5から255.7マイクロ秒に散らばった(この1回の実行の値で、3回の再実行の最小値は131.7、76.8、99.7だった)。

Nodeの初回呼び出し - 回ごとの時間と棒分布

Nodeスクリプトは、小さなオブジェクトを2万個作って通り過ぎる関数を1000回呼び、呼び出しごとに時間を測り、回数区間ごとの中央値と対数目盛の棒を出す。同じファイルを引数childで呼ぶと、500回呼んだ1プロセスの結果を1行で出す。以下のコードは判定関数2つをPythonと同じ定義で実装し直している。

const { performance } = require('node:perf_hooks');
                    const { spawnSync } = require('node:child_process');
                    
                    function work(n) {
                      let s = 0, o = { a: 1, b: 2 };
                      for (let i = 0; i < n; i++) { o = { a: o.b + (i % 7), b: o.a ^ i }; s += o.a * 3 + (o.b >> 1); }
                      return s;
                    }
                    function series(n) {
                      const t = [];
                      for (let i = 0; i < n; i++) {
                        const a = performance.now(); work(20000); t.push((performance.now() - a) * 1000);
                      }
                      return t;
                    }
                    const med = a => { const b = [...a].sort((x, y) => x - y); const m = b.length >> 1; return b.length % 2 ? b[m] : (b[m - 1] + b[m]) / 2; };
                    const mean = a => a.reduce((x, y) => x + y, 0) / a.length;
                    function settle(t, w = 5, tol = 0.25, run = 10) {
                      const ref = med(t.slice(t.length >> 1));
                      const mm = [];
                      for (let i = 0; i + w <= t.length; i++) mm.push(med(t.slice(i, i + w)));
                      for (let i = 0; i + run <= mm.length; i++) {
                        if (mm.slice(i, i + run).every(m => Math.abs(m - ref) <= tol * ref)) return { idx: i, ref };
                      }
                      return { idx: null, ref };
                    }
                    function stationary(t, tol = 0.25) {
                      const q = t.length >> 2;
                      const a = med(t.slice(2 * q, 3 * q)), b = med(t.slice(3 * q));
                      return { ok: Math.abs(a - b) <= tol * b, a, b };
                    }
                    
                    if (process.argv[2] === 'child') {

何回捨てるか - 収束判定の規則

steady level (median of last half): 282 us
                    settle index (w=5, tol=25%, run=10): 15 -> discard first 15 calls
                    stationary check: true (274 vs 295 us)

この実行では安定水準(後ろ半分の中央値)は282マイクロ秒で、移動中央値の判定は最初の15回を捨てるよう返す。定常性検査はTrueで、後ろ2区間は274対295マイクロ秒と同じ水準である。この系列は判定に使える。これらの値はこのPCでの1回の実行のものである。

重要なのは、この数字が実行ごとに同じではないことである。同じスクリプトを新しいプロセスで5回走らせた下の出力(このPCでの1回の実行)では、判定回が1、94、25、18、4に分かれた。断定できるのはプロセスごとに判定が大きく分かれるという向きだけで、具体的な数字は実行のたびに変わる。1つのプロセスの1回の測定で捨てる回数を断定することはできない。

  • 窓の大きさ: 小さいと単発のノイズに振られ、大きいと短いウォームアップがぼやける。ここでは5を使った。
  • 許容幅: 安定水準の25パーセントを使った。環境の通常の揺れより狭くすると判定がいつまでも出ない。
  • 連続回数: 窓の中央値が許容幅の中に10回連続で留まったときを安定とみなす。
  • 安定水準: 時系列の後ろ半分の中央値である。後ろ半分がまだ下がっている途中なら、この基準自体が誤る。

実践手順 - 捨てる回数を決める順序

上の実行で得た規則を順序にまとめると次のようになる。各項目は前の節の出力に根拠があるが、大きい方を使う項目だけはこの記事の提案である。

  • 新しいプロセスで呼び出しごとの時間を記録する。計測区間の中にimport・コンパイル・初期化が入っていないか、まずコードを読む。
  • 疑わしいコストは条件を1つだけ変えて分離する。モジュールの先読み込みやパターンの事前コンパイルがその例である。
  • 時系列を十分に長く取る(ここでは160〜1000回)。時間が長いときは繰り返し回数を減らし、総実行時間を10秒前後に収める。
  • 定常性検査を先に行う。落ちたらウォームアップの判定を保留し、環境を整えて測り直す。
  • 移動中央値で判定回を求め、単発のスパイクは回ごとの検査で別に数える。
  • 新しいプロセスを複数走らせ、判定回を比べる。大きい方を捨てる回数にするのはこの記事が提案する規則で、文書の根拠はない。根拠は判定が分かれるところまでである(このPCでの1回の実行で1から94)。
  • 捨てた後の区間で、中央値と最小値と散らばりを一緒に報告する。平均だけを書かない。
  • 報告に環境を書く。ここに載せたすべての値は、このPCのWindows 10・Python 3.13.3・Node v22.16.0での値である。
観察意味対処
初回1回だけ大きく遅い単発のコスト(importや初期化)回ごとの検査で1回捨て、原因の変数を分離する
数十回かけて緩やかに低下段階的な最適化の区間移動中央値の判定回だけ捨てる
定常性検査に落ちる環境が揺れている判定を保留し、測り直し、最小値と分布を一緒に見る
判定回がプロセスごとに大きく違う1回の判定は不安定複数プロセスを走らせて大きい値を使う(この記事の提案)

確認できなかったこと

  • Nodeの初回の遅れがJITの段階切り替えによるという因果。V8ブログの文と出力の向きが合うだけで、JITだけを止めた対照実験はしていない。
  • pure系列が1つのプロセスの中で53から431マイクロ秒まで動いた原因。CPUクロック・OSのスケジューリング・インタプリタ内部のどれか、また再実行のたびに判定が分かれた理由を、出力では切り分けられなかった。
  • import_warmとre_precompiledに残る初回超過(1.8対1.0、15.7対2.9)の原因。
  • OSのファイルキャッシュの影響。消すには管理者権限が必要なので実行していない。
  • LinuxやmacOS、他のバージョンのPythonとNodeでの値。このPCのWindows 10でのみ実行した。
  • Nodeのperformance.now()が実際に出す解像度。MDNの解像度の文はブラウザ文脈のもので、Nodeの文書は開いていない。
  • 窓5・許容25パーセント・連続10回という判定パラメータが他の関数にも合うか。
  • GCを有効にした場合と止めた場合の差。timeit文書が述べるGCの停止は、ここで使ったperf_counterの測定には適用されていない。
