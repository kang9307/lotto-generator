zstd를 Rust로 다시 쓰는 이유, 압축 알고리즘 비교, 그리고 실무 적용 가이드

서론: 압축 라이브러리를 Rust로 다시 쓰는 이유

2026년 6월 news.hada.io 화제 토픽 중 하나는 Rust로 구현한 Zstandard 발표였습니다. 이미 수년째 C로 잘 동작하는 압축 라이브러리를 굳이 Rust로 다시 쓴다는 소식에 "왜?"라는 반응과 "드디어"라는 반응이 동시에 나왔습니다. 본인이 보기에 이 사건은 단순한 언어 취향 논쟁이 아니라, 신뢰할 수 없는 외부 입력을 파싱하는 시스템 소프트웨어가 메모리 안전 언어로 이동하는 큰 흐름의 한 장면입니다.

압축 라이브러리는 우리 눈에 잘 띄지 않지만 거의 모든 시스템의 뒤편에서 동작합니다. 웹 서버가 응답을 압축할 때, 데이터베이스가 디스크에 데이터를 쓸 때, 컨테이너 레지스트리가 이미지를 전송할 때, 백업 도구가 파일을 아카이브할 때 모두 압축 코덱이 호출됩니다. 그리고 이 코덱들은 대부분 네트워크나 파일로 받은, 통제할 수 없는 데이터를 해제합니다. 해제 과정에서 메모리 버그가 하나라도 있으면 공격자는 악의적으로 조작한 압축 파일 하나로 서버를 장악할 수 있습니다.

이 글은 단순한 발표 요약이 아닙니다. 본인이 정리한 12개의 H2를 통해 (1) Rust 재구현의 배경, (2) Zstandard가 무엇인지, (3) 왜 하필 Rust인지, (4) C 압축 라이브러리의 취약점 역사, (5) Rust 재구현의 5가지 이점, (6) gzip·lz4·zstd·brotli 비교 매트릭스, (7) zstd가 인기 있는 이유, (8) Rust 생태계에서의 활용, (9) Rust vs C 성능 트레이드오프, (10) 5가지 실무 시나리오, (11) 한국 개발 환경 적용, (12) 결론과 즉시 적용 3가지까지 솔직하게 다룹니다. 원문을 직역하지 않고 본인이 정리한 매트릭스와 의사 결정 프레임이 본문의 핵심입니다.

1. Zstandard란 - zstd 압축 알고리즘 개요

Zstandard(줄여서 zstd)는 Facebook, 현재의 Meta가 개발해 2016년에 공개한 범용 무손실 압축 알고리즘입니다. 공식 저장소는 github.com/facebook/zstd이고 라이센스는 BSD입니다. 핵심 설계 목표는 명확했습니다. gzip 수준의 압축률을 유지하면서 압축·해제 속도를 대폭 끌어올리는 것입니다.

zstd가 다른 알고리즘과 구별되는 특징은 세 가지입니다. 첫째, 압축 레벨이 1부터 22까지 폭넓게 조정됩니다. 레벨 1은 lz4에 근접한 속도로 가볍게 압축하고, 레벨 19~22는 brotli에 근접한 높은 압축률을 냅니다. 한 알고리즘으로 실시간부터 아카이브까지 커버됩니다. 둘째, 사전(dictionary) 학습 기능입니다. JSON 메시지처럼 구조가 비슷한 작은 데이터를 반복 압축할 때, 미리 학습한 사전을 쓰면 압축률이 극적으로 좋아집니다. 셋째, 스트리밍 API가 깔끔해서 대용량 파일을 메모리에 다 올리지 않고 처리할 수 있습니다.

내부적으로 zstd는 FSE(Finite State Entropy)와 Huffman 코딩을 조합한 엔트로피 인코더 위에 LZ77 계열의 사전 매칭을 얹은 구조입니다. 깊은 이론까지 들어가지 않아도, 본인이 강조하고 싶은 점은 zstd가 2020년대 압축의 사실상 표준이 되었다는 사실입니다. Linux 커널, RocksDB, Parquet, ZFS, btrfs, 그리고 수많은 패키지 매니저가 zstd를 채택했습니다.

2. 왜 Rust로 재구현하나 - 메모리 안전성의 가치

잘 동작하는 C 라이브러리를 굳이 Rust로 다시 쓰는 이유는 단 하나로 압축됩니다. 메모리 안전성입니다. 본인이 이 가치를 강조하는 이유를 풀어 보겠습니다.

C와 C++은 강력하고 빠르지만, 메모리를 수동으로 관리합니다. 포인터 산술, 수동 할당·해제, 경계 검사 부재는 곧 버퍼 오버플로, use-after-free, double free, 정수 오버플로로 이어집니다. 이들은 단순한 버그가 아니라 보안 취약점입니다. 마이크로소프트와 구글이 공개한 통계에 따르면 자사 보안 취약점의 약 70%가 메모리 안전 문제에서 비롯됩니다.

Rust는 소유권(ownership)과 빌림 검사(borrow checker)로 이 문제를 컴파일 시점에 차단합니다. 가비지 컬렉터 없이, 런타임 오버헤드 없이, 메모리 안전을 정적으로 보장합니다. 즉 zstd 같은 압축 코덱을 Rust로 다시 쓰면 "신뢰할 수 없는 입력을 파싱하다 메모리 손상이 일어나는" 부류의 CVE를 구조적으로 제거할 수 있습니다. 본인 시각에서 이것이 Rust 재구현의 본질이고, 약간의 초기 성능 손해를 감수할 만한 충분한 이유입니다.

핵심 - 압축 라이브러리는 거의 항상 "외부에서 받은 통제 불가능한 데이터"를 해제합니다. 이 지점이 바로 메모리 안전 언어가 가장 큰 가치를 발휘하는 영역입니다.

3. C 구현의 위험 - 압축 라이브러리의 보안 취약점 역사

추상적인 위험이 아닙니다. 압축 라이브러리는 실제로 심각한 CVE를 반복해 왔습니다. 본인이 기억하는 대표 사례를 정리합니다.

3-1) zlib와 압축 해제 폭탄

가장 널리 쓰이는 zlib는 수십 년간 다듬어졌지만, 그 위에서 동작하는 수많은 래퍼와 파서에서 압축 해제 관련 취약점이 끊임없이 발견됐습니다. "압축 폭탄(zip bomb)"처럼 작은 압축 파일이 해제 시 거대한 메모리를 차지하게 만드는 공격은 지금도 유효합니다.

3-2) 정수 오버플로와 힙 손상

압축 포맷은 길이·오프셋 필드를 다룹니다. C에서 이 값을 검증 없이 곱하거나 더하면 정수 오버플로가 발생하고, 그 결과로 힙 버퍼가 잘못된 크기로 할당되어 힙 손상으로 이어집니다. 압축 코덱 류에서 반복적으로 보고된 전형적 패턴입니다.

3-3) XZ Utils 백도어 사건(2024)

2024년 발견된 XZ Utils(liblzma) 백도어 사건은 압축 라이브러리가 공급망 공격의 표적이 될 수 있음을 충격적으로 보여줬습니다. 이것은 메모리 안전과 다른 차원의 문제(공급망·신뢰)이지만, 압축 라이브러리가 시스템 깊숙이 박혀 있어 한 번 뚫리면 피해가 광범위하다는 점을 모두에게 각인시켰습니다.

본인이 강조하고 싶은 결론은 이것입니다. 압축 코덱은 "잘 동작하니 건드리지 말자"의 영역이 아니라, 가장 우선적으로 메모리 안전성을 확보해야 하는 보안 핵심 컴포넌트입니다. Rust 재구현은 이 인식의 자연스러운 귀결입니다.

4. Rust 재구현의 5가지 이점

본인이 정리한 Rust로 압축 라이브러리를 재구현했을 때의 다섯 가지 실질적 이점입니다.

4-1) 메모리 안전

가장 큰 이점입니다. 버퍼 오버플로·use-after-free·double free를 컴파일러가 차단합니다. unsafe 블록을 최소화하면, 신뢰할 수 없는 입력을 파싱해도 메모리 손상 부류의 취약점이 원천 봉쇄됩니다.

4-2) 안전한 동시성

Rust의 소유권 모델은 데이터 레이스를 컴파일 시점에 막습니다. 압축은 블록 단위 병렬화가 자연스러운 작업인데, Rust에서는 rayon 같은 라이브러리로 안전하게 멀티 스레드 압축을 구현하기 쉽습니다.

4-3) 통합 용이성

Rust crate는 cargo 한 줄로 의존성을 추가합니다. C 라이브러리 특유의 빌드 시스템 지옥(autotools, CMake, 헤더 경로) 없이, 순수 Rust 구현이면 크로스 컴파일과 WASM 빌드도 매끄럽습니다.

4-4) 유지보수성

Rust의 강한 타입 시스템과 패턴 매칭은 압축 포맷 파서처럼 상태가 복잡한 코드를 더 안전하고 읽기 쉽게 만듭니다. 컴파일러가 잡아주는 영역이 넓어 리팩터링 부담이 줄어듭니다.

4-5) 신뢰

위 네 가지가 합쳐져 결국 신뢰가 됩니다. "이 라이브러리는 악의적 입력을 받아도 메모리 손상이 없다"는 보증은, 보안이 중요한 인프라에서 채택 결정을 크게 앞당깁니다. 본인 시각에서 이 신뢰가 Rust 재구현의 진짜 자산입니다.

5. 압축 알고리즘 비교 - gzip / lz4 / zstd / brotli

본격적으로 zstd를 평가하기 전에 주요 압축 알고리즘 네 가지를 한 표로 정리합니다. 본인이 적용·관찰한 경험과 공개 벤치마크를 종합한 비교 매트릭스입니다.

알고리즘압축률속도적합 용도
gzip보통보통범용, 레거시 호환
lz4낮음매우 빠름실시간 처리
zstd높음빠름균형 (대세)
brotli매우 높음느림웹 정적 자원

본인이 정리한 선택 기준은 단순합니다. 특별한 이유가 없으면 zstd를 기본값으로 두고, 극단적 속도가 필요하면 lz4, 한 번 압축해 여러 번 전송하는 웹 정적 자원은 brotli, 오래된 시스템과의 호환이 필요하면 gzip입니다. 네 알고리즘 중 어느 하나가 모든 상황에서 최고는 아니며, zstd의 강점은 "가장 넓은 영역에서 무난하게 1등"이라는 균형감입니다.

6. Zstandard가 인기 있는 이유 - 속도와 압축률 균형

zstd가 짧은 시간에 사실상 표준이 된 이유를 본인 시각으로 정리합니다.

6-1) 균형감

5장 표에서 보듯 zstd는 압축률은 높음, 속도는 빠름입니다. 대부분의 워크로드는 "압축률도 속도도 적당히 좋아야" 하는데, zstd가 정확히 그 자리를 차지합니다. gzip보다 빠르고 더 잘 압축되며, lz4보다 훨씬 잘 압축됩니다.

6-2) 레벨 튜닝의 자유

압축 레벨 1~22 하나로 실시간(레벨 1~3)부터 아카이브(레벨 19~22)까지 한 도구로 커버됩니다. 운영 중에 레벨만 바꿔 속도·용량 트레이드오프를 조정할 수 있는 유연성은 본인이 본 가장 실용적인 강점입니다.

6-3) 사전 학습

작은 메시지를 대량으로 압축하는 환경(예: 마이크로서비스 간 JSON 메시지, IoT 센서 데이터)에서 사전 학습은 압축률을 2~5배 끌어올립니다. gzip에는 없는 zstd만의 결정적 무기입니다.

6-4) 생태계 채택

Linux 커널(initramfs·모듈 압축), ZFS·btrfs 파일시스템, RocksDB·Parquet, Arch·Fedora 패키지 매니저, 수많은 컨테이너 레지스트리가 zstd를 기본으로 채택했습니다. 채택이 채택을 부르는 선순환이 자리 잡았습니다.

7. Rust 생태계에서의 활용

Rust 진영에서 압축은 이미 잘 통합되어 있습니다. 본인이 쓰는 방식을 기준으로 정리합니다.

7-1) cargo 의존성 추가

기존에 가장 널리 쓰이는 zstd crate는 C 레퍼런스 구현에 대한 바인딩이고, 순수 Rust 구현(ruzstd 등 디코더)도 성장 중입니다. 사용법은 의존성 한 줄로 끝납니다.

[dependencies]
# C 바인딩(가장 성숙한 선택)
zstd = "0.13"

# 또는 순수 Rust 디코더(메모리 안전 우선)
# ruzstd = "0.7"

7-2) 기본 압축·해제 코드

use std::io::Read;

fn main() -> std::io::Result<()> {
    let data = b"Hello, Zstandard in Rust! ".repeat(1000);

    // 압축 (레벨 3 = 균형, 19+ = 아카이브)
    let compressed = zstd::encode_all(&data[..], 3)?;
    println!("원본 {} bytes -> 압축 {} bytes", data.len(), compressed.len());

    // 해제
    let mut decompressed = Vec::new();
    zstd::Decoder::new(&compressed[..])?.read_to_end(&mut decompressed)?;
    assert_eq!(data, decompressed);
    Ok(())
}

7-3) 시스템 프로그래밍에서의 위치

Rust로 작성된 스토리지 엔진, 로그 수집기, 네트워크 프록시는 zstd를 거의 기본 압축으로 채택합니다. 순수 Rust 디코더가 성숙하면, FFI 경계(C 바인딩) 없이 전체 압축 경로를 메모리 안전하게 유지할 수 있다는 점이 본인이 보는 가장 큰 매력입니다.

8. 성능 - Rust vs C 구현 트레이드오프

가장 자주 나오는 질문은 "Rust 재구현이 C보다 느리지 않냐"입니다. 본인이 정리한 솔직한 답은 다음과 같습니다.

8-1) 이론상 천장은 같다

Rust는 LLVM 백엔드로 C/C++과 동급의 네이티브 코드를 생성합니다. 가비지 컬렉터가 없고 런타임 오버헤드가 없으므로 이론적 성능 천장은 C와 동일합니다.

8-2) 초기 격차는 존재한다

현실에서는 C 레퍼런스 구현이 수년간 SIMD 손튜닝과 어셈블리 핫패스로 극한까지 최적화되어 있습니다. 처음부터 작성한 Rust 구현은 특정 벤치마크에서 5~20% 정도 느릴 수 있습니다. 이것은 언어의 한계가 아니라 최적화 투자 시간의 차이입니다.

8-3) 격차는 좁혀진다

Rust에서도 std::simd, core::arch intrinsics로 SIMD를 쓸 수 있고, 안전한 병렬화로 멀티코어 이득을 더 쉽게 얻습니다. 시간이 지날수록 격차는 좁혀지고, 일부 워크로드에서는 동등하거나 앞서는 결과도 나옵니다.

주의 - "5~20% 느림"이라는 수치는 워크로드·레벨·데이터에 따라 크게 달라집니다. 단일 벤치마크 숫자를 절대화하지 말고, 본인 데이터로 직접 측정하는 것이 본인 추천입니다.

본인 시각에서 결론은 명확합니다. 약간의 성능 트레이드오프는 "악의적 입력에도 메모리 손상이 없다"는 보안 가치로 충분히 상쇄됩니다. 특히 보안이 중요한 인프라일수록 이 교환은 합리적입니다.

9. 실무 활용 시나리오 5가지

본인이 정리한 zstd 적용이 정당화되는 다섯 가지 시나리오입니다.

9-1) 로그 수집·저장

로그는 양이 많고 반복 패턴이 강해 압축률이 잘 나옵니다. zstd는 압축률이 좋아 스토리지 비용을 줄이고, 해제가 빨라 로그 검색·분석 시 지연이 작습니다. Elasticsearch·Loki 같은 도구가 zstd를 지원합니다.

9-2) 백업·아카이브

장기 보관 백업은 압축률이 곧 비용입니다. zstd 레벨 19~22를 쓰면 brotli에 근접한 압축률을 얻으면서 해제는 여전히 빠릅니다. 복원 시간이 짧다는 점이 아카이브에서 특히 중요합니다.

9-3) 네트워크 전송

API 응답·메시지 큐·스트리밍에서 낮은 레벨(1~3)의 zstd는 실시간성을 유지하면서 대역폭을 절약합니다. 사전 학습을 결합하면 작은 JSON 메시지의 압축률이 극적으로 좋아집니다.

9-4) 스토리지·데이터베이스

RocksDB, Parquet, ClickHouse, ZFS, btrfs가 zstd를 기본 또는 권장 압축으로 채택합니다. 디스크 I/O가 병목인 환경에서 압축은 사실상 성능 향상 수단입니다 - 읽고 쓸 바이트가 줄기 때문입니다.

9-5) 컨테이너 이미지·패키지

컨테이너 레지스트리와 패키지 매니저(Arch·Fedora 등)는 zstd로 전송 시간과 저장 공간을 동시에 줄입니다. 이미지 풀 속도가 빨라져 배포 파이프라인 전체가 가벼워집니다.

10. 한국 개발 환경 적용

한국 개발자 관점에서 zstd와 Rust 재구현이 갖는 의미를 정리합니다.

10-1) 비용 절감 효과

국내 클라우드(네이버 클라우드, KT 클라우드)와 AWS·GCP 한국 리전 모두 스토리지·전송 비용이 무시할 수 없습니다. 로그·백업·DB 압축을 gzip에서 zstd로 바꾸기만 해도 스토리지 사용량과 전송량이 줄어 직접적인 비용 절감으로 이어집니다.

10-2) 보안 규제 대응

금융·공공 부문은 보안 요구가 강합니다. "신뢰할 수 없는 입력을 파싱해도 메모리 손상이 없다"는 Rust 재구현의 보증은, 보안 심사·취약점 점검 부담이 큰 한국 환경에서 설득력 있는 채택 근거가 됩니다.

10-3) 점진적 도입 전략

본인 추천은 한 번에 전부 바꾸지 말고, 신규 로그 파이프라인이나 신규 백업 작업부터 zstd로 시작하는 점진적 도입입니다. 기존 gzip 자산은 호환성 때문에 유지하되, 새로 만드는 부분에 zstd를 기본값으로 두면 리스크 없이 이득을 누적할 수 있습니다.

11. 결론 + 즉시 적용 가능한 3가지

Rust로 구현한 Zstandard를 한 문장으로 요약하면 이것입니다. "균형감 좋은 표준 압축 zstd에, 메모리 안전이라는 보안 가치를 더한 합리적 진화"입니다. 본인이 즉시 적용하는 세 가지 패턴을 공유합니다.

11-1) 즉시 적용 1: 신규 압축은 zstd를 기본값으로

새로 만드는 로그·백업·전송 경로는 특별한 이유가 없으면 zstd 레벨 3(균형)을 기본값으로 두십시오. gzip 대비 더 빠르고 더 잘 압축됩니다. 5분이면 바꿀 수 있고 손해 볼 일이 거의 없습니다.

11-2) 즉시 적용 2: 데이터별 최적 레벨을 측정으로 결정

실시간 경로는 레벨 1~3, 아카이브는 레벨 19~22로 시작하되, 본인 실제 데이터로 압축률·속도를 측정해 최적점을 잡으십시오. 반복되는 작은 메시지라면 사전 학습을 반드시 시험해 보십시오.

11-3) 즉시 적용 3: Rust 프로젝트는 메모리 안전 디코더를 우선 검토

Rust로 신뢰할 수 없는 입력을 해제한다면, 순수 Rust 디코더(ruzstd 등)를 우선 검토해 FFI 경계를 줄이십시오. 성숙도가 부족하면 C 바인딩(zstd crate)을 쓰되, 향후 순수 Rust로 이전할 수 있게 인터페이스를 추상화해 두는 것이 본인 추천입니다.

마지막으로 본인이 강조하는 메시지는 이것입니다. 압축은 "보이지 않는 비용 절감 지렛대"이자 "보이지 않는 보안 표면"입니다. zstd는 비용 절감 지렛대를 가장 균형 있게 제공하고, Rust 재구현은 그 보안 표면을 구조적으로 닫습니다. 2026년 신규 시스템 설계자라면 이 조합은 한 번쯤 진지하게 평가할 가치가 있습니다.
