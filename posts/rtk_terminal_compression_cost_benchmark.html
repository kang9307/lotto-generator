RTK는 토큰을 아낀다는데, 실제 비용 벤치마크는 다르게 말한다 - Terminal-Bench 2.1 1,740회 비교

Fable −5%와 DeepSeek +5%의 청구액 차이, rtk gain 지표의 69% 왜곡과 프롬프트 캐시·턴 증가가 만든 비용 역전 실증 분석

자율 코딩 에이전트(Autonomous Coding Agent)가 소프트웨어 엔지니어링의 일상적인 실무 도구로 편입되면서, 기술 조직이 직면한 가장 현실적인 장벽은 다름 아닌 기하급수적인 토큰 추론 비용이다. 코드베이스를 정밀하게 탐색하고 셸 터미널에서 컴파일 명령이나 테스트 스위트를 실행하는 과정에서, 에이전트는 수천 줄에 달하는 터미널 표준 출력과 장황한 디버깅 로그를 컨텍스트 윈도우로 쉼 없이 끌어들인다. 이러한 입력 토큰의 폭발적 팽창을 원천적으로 억제하기 위해 개발자 커뮤니티에서 거대한 기대를 모은 도구가 바로 RTK(Rust Token Killer)이다.

RTK는 에이전트가 셸을 통해 실행하는 명령 출력을 중간에서 가로채 압축하고 장식적 메타데이터를 제거함으로써, 토큰 사용량을 드라마틱하게 줄여 준다는 약속을 전면에 내세웠다. 개발자 커뮤니티와 소셜 미디어 플랫폼에서는 RTK를 프로젝트에 붙이기만 하면 에이전트 구동 비용을 60%에서 최대 90%까지 줄일 수 있다는 소식이 폭발적으로 공유되었다. 실제로 GitHub 저장소에서 79k 이상의 스타를 기록할 정도로 RTK는 개발자들에게 AI 코딩 비용을 절감하는 사실상의 필수 유틸리티로 확고히 자리 잡았다.

하지만 AI 에이전트의 세션 수준 비용 인텔리전스를 전문적으로 분석하는 Quesma 블로그가 수일간 1,500달러 이상의 순수 토큰 비용을 직접 투입해 진행한 대규모 실측 벤치마크 결과는 이러한 통념을 정면으로 뒤엎었다. 터미널 상호작용 과제로 구성된 Terminal-Bench 2.1 벤치마크에서 총 1,740회에 걸쳐 대조군 실험을 수행한 결과, 도구가 화면에 출력하는 거대한 자체 토큰 절감 보고와 실제 클라우드 API 청구액 사이에는 믿기 힘들 만큼 큰 괴리가 존재한다는 사실이 밝혀졌다. 본 분석에서는 Quesma 블로그의 정밀 벤치마크 데이터를 바탕으로 「토큰이 줄어들면 비용도 반드시 줄어든다」는 직관적 가정이 왜 현대 에이전트 아키텍처에서 빗나갈 수밖에 없는지, 그 구조적 원인을 면밀히 살펴본다.

터미널 출력 압축 도구 RTK와 '토큰 90% 절감' 주장의 배경

RTK(Rust Token Killer)의 핵심 작동 원리는 단순하고 직관적이다. 코딩 에이전트가 환경과 대화하기 위해 호출하는 셸 도구(Claude Code의 Bash 또는 OpenCode의 bash 도구)의 출력 문자열을 가로채, 동일한 의미를 지니는 더 짧은 텍스트로 재작성(rewrite)하는 프록시 계층으로 동작한다. 예를 들어 Git 이력 조회, 패키지 설치 로그, 디렉터리 목록 조회 등에서 불필요한 공백, 장식 프레임, 권한 소유자 정보, 타임스탬프를 제거하여 모델에게 건네는 방식이다.

원문이 소개한 대표적인 터미널 출력 재작성 사례는 다음과 같다. ls -la 명령을 실행했을 때 출력되는 파일 목록에서 소유자 계정이나 수정 날짜를 걷어내고, 권한 코드(644)와 파일명, 바이트 용량만을 압축하여 반환한다.

$ ls -la /app/warriors
-rw-r--r-- 1 root root  824 Sep 13  2025 g2-clear.red
-rw-r--r-- 1 root root  487 Sep 13  2025 paper.red

$ rtk ls -la warriors/
644  g2-clear.red  824B
644  paper.red  487B

이러한 메커니즘은 터미널 상호작용이 긴 자율 에이전트에서 즉각적인 기대를 모았다. 에이전트의 컨텍스트 윈도우가 가득 차기 전에 텍스트를 줄이면 추론 한도에 걸리지 않고 비용도 극적으로 줄어들 것이라는 가설은 매우 그럴듯하게 들렸다. 소셜 미디어와 기술 매체에서는 다음과 같은 주장들이 광범위하게 확산되었다.

  • 소셜 미디어 확산: X(구 트위터)에서 RTK가 Claude Code의 토큰을 최대 60%까지 줄여 준다는 게시물이 31만 3천 회 이상의 조회수를 기록하며 큰 화제를 모았다.
  • 사례 연구와 영상 콘텐츠: 유튜브 FuturMinds 채널은 RTK가 토큰을 90% 아껴 준다는 영상을 게시했고, Soba Labs는 블로그를 통해 Claude Code의 토큰 소모를 절반으로 줄였다고 보고했다.
  • 비용 최적화 가이드: ComputeLeap을 비롯한 기술 블로그들은 RTK를 사용해 토큰 비용을 60~90% 절감하는 실무 가이드를 발행하며 도입을 권장했다.

하지만 대중적인 찬사와 달리, RTK 공식 GitHub 저장소의 README 문서는 명확한 자체 고지 문구를 남겨 두고 있었다. README 본문은 "RTK cuts up to 90% of the bash output your agent reads. […] it is not the same as cutting your bill by 90%."라고 명시했다. 즉, 에이전트가 읽는 Bash 출력 문자열의 90%를 줄인다는 사실이 실제 청구 금액을 90% 줄여 준다는 뜻은 전혀 아니라는 점을 분명히 밝힌 것이다.

Terminal-Bench 2.1 1,740회 실험 설계와 측정 환경

Quesma 블로그는 이러한 의문을 해소하기 위해 통계적으로 유의미한 대규모 벤치마크 실험을 설계했다. 평가 프레임워크로는 터미널 상호작용 비중이 높은 Terminal-Bench 2.1을 채택했다. 후속 버전인 3.0이나 4.0 대신 2.1을 선택한 이유는 실무적 관점 때문이었다. 최신 버전은 과제 난이도가 너무 높아 에이전트들이 대부분 실패하는 반면, 2.1은 대다수 과제를 해결할 수 있어 「성공한 작업에서 실제로 비용이 얼마나 드는가」를 정확히 측정할 수 있기 때문이다. 실패한 작업에서의 비용 감소는 실제 엔지니어링 생산성에 아무런 의미가 없다.

실험은 모델 라우트, 플랫폼, 과제별 타임아웃을 동일하게 고정한 상태에서 각 과제를 RTK 미적용 5회, RTK 적용 5회씩 총 10회 반복 실행하는 방식으로 진행되었다. 시험에 사용된 정밀한 환경 구성과 버전은 다음과 같다.

  • 프론티어 모델 환경: Claude Code 2.1.220 클라이언트에서 Fable 5.0 모델을 결합하여 최고 성능 환경을 구성했다.
  • 오픈소스 에이전트 환경: OpenCode 1.18.25 플랫폼에서 OpenRouter를 경유하여 DeepSeek V4 Pro 0813 모델을 호출했다.
  • 벤치마크 및 도구 버전: 벤치마크 실행 플랫폼으로 Harbor 0.20을 사용했고, 터미널 압축 유틸리티로는 RTK 0.45.0을 적용했다.
  • 과제 규모와 시도 횟수: 보안 정책 거부(Refusal)가 발생한 4개 Fable 과제를 제외한 85개 Fable 과제와 89개 DeepSeek 과제를 대상으로 하여, 총 1,740회의 시도 데이터를 수집했다.

원문 저자는 며칠에 걸쳐 지속된 이 벤치마크를 수행하면서 1,500달러 이상의 순수 토큰 비용을 지출했다고 밝혔다. 소수의 샘플이나 인위적인 단일 턴 테스트가 아닌, 1,740회에 달하는 다회차 대조군 측정은 도구의 실제 경제성을 판별하는 확고한 통계적 근거를 제공한다.

전체 청구액과 과제별 평균의 괴리 — 집계 −5%와 과제별 +17%의 역설

실험의 첫 번째 단순 합산 결과는 언뜻 기대에 부합하는 것처럼 보였다. 벤치마크 전체에서 발생한 누적 청구 금액을 모두 합산했을 때, RTK를 적용한 Fable 5.0 환경에서는 총비용이 기준선 대비 5% 감소(−5%)했다. 반면 DeepSeek V4 Pro 환경에서는 전체 지출이 5% 증가(+5%)하는 엇갈린 결과를 보였다.

작업 통과율(Pass Rate)에서도 소폭의 변화가 관찰되었다. Fable 5.0 환경의 통과율은 RTK 미적용 시 84%에서 RTK 적용 시 83%로 1%포인트 낮아졌다. DeepSeek V4 Pro 환경에서는 71%에서 69%로 2%포인트 하락했다. 통과율 격차 자체는 1~2%포인트로 작았지만, 실패한 시도까지 포함한 전체 지출을 성공한 과제 수로 나눈 「성공당 실질 비용」을 계산하면 Fable은 3% 저렴해진 반면 DeepSeek은 7% 더 비싸졌다.

그러나 데이터를 각 과제에 동일한 가중치를 부여하는 과제별 평균(Per-task average)으로 재집계하자 전혀 다른 결론이 드러났다. 벤치마크에서는 극도로 비용이 높은 단 하나의 과제가 전체 단순 합산 금액을 크게 왜곡할 수 있기 때문에, 각 과제 단위로 기준선 평균과 RTK 평균의 변화율을 구한 뒤 이를 평균 내는 방식이 표준적인 엔지니어링 분석법이다.

이 과제별 평균 기준에서 Fable 5.0의 비용 변화율은 단순 합산의 −5%가 아니라 1% 증가(+1%, 95% 신뢰구간 −3% ~ +5%)로 나타나 0을 중심으로 통계적 차이가 없었다. DeepSeek V4 Pro의 결과는 더욱 극단적이었다. 단순 합산에서 +5%였던 비용 변화율이 과제별 평균 기준으로는 무려 17% 증가(+17%, 95% 신뢰구간 +8% ~ +28%)로 치솟았다. 10회 시도가 모두 통과한 36개 DeepSeek 과제만을 따로 떼어 확인해도 비용 증가율은 여전히 18%에 달했다.

rtk gain 지표의 치명적 함정 — 바이트 계산과 train-fasttext의 왜곡

실제 청구 비용이 이처럼 증가하거나 제자리에 머물렀음에도, RTK 도구가 실행 로그에 표시하는 자체 절감 지표인 rtk gain은 완전히 엉뚱한 수치를 가리키고 있었다. DeepSeek RTK 시도 445회에서 RTK는 3억 4,920만 토큰(349.2M tokens)을 절약했다고 보고했다. 이는 전체 터미널 출력 토큰의 89%를 깎아냈다는 계산이었다.

보고된 절감량과 실제 청구액이 정반대로 움직인 이유는 rtk gain 지표가 태생적으로 지닌 결함 때문이다. RTK 공식 문서는 rtk gain을 「필터링 전 원본 텍스트의 바이트 수에서 필터링 후 바이트 수를 뺀 뒤 4로 나눈 값」으로 정의한다. 이 수식은 실제 API 제공자가 청구하는 과금 토큰 수와 아무런 관련이 없다. 이 지표가 안고 있는 측정상의 결함은 다음과 같다.

  • 토크나이저와 과금 체계 무시: 바이트를 4로 나눈 단순 나눗셈은 BPE 토크나이저의 서브워드 분할 구조나 클라우드 벤더의 실제 청구 로직을 반영하지 못한다.
  • 후속 행동과 턴 비용의 누락: 텍스트를 압축한 뒤 에이전트가 다음 턴에서 어떤 추가 명령을 실행하는지, 턴이 늘어남에 따라 발생하는 비용을 전혀 포착하지 않는다.
  • 가상의 전체 읽기(Phantom Read)와의 대조: 에이전트가 애초에 파일 전체를 읽을 생각이 없었던 제한된 명령조차 전체 파일을 읽은 것과 대조하여 거대한 절감분으로 왜곡 적립한다.

이러한 측정 방법론의 치명적인 결함을 보여 주는 가장 구체적인 사례가 바로 `train-fasttext` 과제였다. 이 과제에서 모델은 파일의 가장 첫 줄만을 확인하기 위해 head -1 train.txt 명령을 두 차례 호출했다. 정상적인 환경이라면 이 명령은 단 한 줄의 텍스트만을 화면에 출력하므로 수십 바이트의 토큰만을 유발한다.

하지만 RTK는 이 호출을 가로채면서, 모델이 「수백 메가바이트에 이르는 train.txt 파일 전체를 전부 읽었을 경우」와 비교하여 매 호출마다 1억 2,050만 토큰을 절약했다고 카운터에 기록했다. 모델은 애초에 전체 파일을 읽을 명령을 내리지 않았음에도, 두 번의 head -1 호출만으로 2억 4,100만 토큰의 가짜 절감액이 만들어졌다. 이 두 번의 호출이 해당 과제 rtk-gain 절감 카운터의 69%를 차지했다. 실무자가 자체 카운터의 수억 토큰 절감 보고를 보며 비용이 아껴졌다고 착각하는 동안, 실제 시스템은 아무런 절감 효과도 얻지 못하고 있었던 것이다.

토큰이 줄어도 비용이 줄지 않는 세 가지 이유 — 캐시 할인·턴 수 증가·도구 우회

Quesma 블로그의 분석에 따르면, 터미널 출력을 아무리 깎아내더라도 청구 요금이 내려가지 않거나 오히려 늘어나는 현상 이면에는 세 가지 근본적인 아키텍처 요인이 작동하고 있다.

구조적 영향 요인 명목상 직관 및 주장 실제 측정치 및 기술적 기제 최종 비용에 미친 경제적 결과
`rtk gain` 계산 지표 토큰이 89% 절감되었다고 보고 단순 (원본−필터 바이트) ÷ 4 산술값. `head -1`을 전체 파일 읽기와 대조해 허수 계상 보고된 3.49억 토큰 절감에도 불구하고 실제 요금은 전혀 감소하지 않음
프롬프트 캐시 요금 할인 입력 토큰을 줄이면 비례하여 요금 절감 입력의 94%(Fable)~98%(DeepSeek)가 캐시 적중. 캐시 단가는 정상가의 1/10~1/30 터미널 텍스트를 줄여도 아껴지는 금액은 지극히 미미한 수준에 불과
에이전트 턴 수 증가 (Tokenflation) 턴당 출력이 작아지면 총 토큰 감소 턴당 입력은 7% 줄었으나 전체 턴 수가 18% 증가. 누적 히스토리가 매 턴 재전송 늘어난 턴마다 캐시 읽기·추론 비용이 반복 청구되어 절감분을 완전히 상쇄
도구 분리와 RTK 적용 범위 에이전트의 모든 파일 출력을 압축 셸 도구(Bash)만 재작성. 전용 파일 읽기(Read, Grep, Glob) 도구는 완전 우회 실제 터미널 호출의 31%(Claude Code)~51%(OpenCode)만 RTK를 경유

이 세 가지 메커니즘을 상세히 들여다보면 다음과 같은 인프라적 현실이 드러난다.

  1. 프롬프트 캐싱의 압도적인 단가 할인: 현대 코딩 에이전트는 다단계 대화 루프로 실행되며, 이전 턴에서 축적된 컨텍스트는 공급자 인프라의 KV 캐시에 저장된다. 캐시 적중(Cache Read) 토큰의 가격은 정상 입력 단가 대비 Fable은 1/10, DeepSeek은 1/30에 불과하다. 실측 결과 RTK 적용 시 Fable 입력 토큰의 94%가 캐시 적중이었으나 비용 비중은 30%에 그쳤고, DeepSeek은 입력의 98%가 캐시 읽기였지만 요금 비중은 26%였다. 즉, 이미 단가가 1/10에서 1/30 수준으로 할인된 터미널 텍스트를 쥐어짜 보아야 전체 청구서에서 깎여 나가는 실질 금액은 지극히 미미하다.
  2. 턴 수의 팽창과 토큰플레이션(Tokenflation): 텍스트를 압축하면서 필요한 단서까지 삭제되면 에이전트는 상황을 파악하지 못해 방황하게 된다. DeepSeek의 경우 RTK 적용 시 턴당 평균 입력 문자는 7% 감소했지만, 전체 턴 수는 18% 증가했다. 58개 과제에서 턴 수가 늘어났고, 그중 44개 과제에서 비용이 증가했다. 턴 수가 단 한 번만 더 늘어나더라도, 매 턴마다 수만 토큰의 누적 대화 기록이 다시 입력으로 들어가고 모델의 추론 출력이 새롭게 생성된다. DeepSeek에서 모델 출력(추론 토큰 포함)은 요금의 56~57%를 차지했다. 턴 하나가 추가되는 순간 텍스트 압축으로 아낀 푼돈은 눈 깜짝할 사이에 증발한다.
  3. 도구 분리와 낮은 실제 적용률: RTK는 셸 도구(Bash/bash)만을 가로챈다. 하지만 Claude Code나 OpenCode와 같은 최신 에이전트들은 파일 읽기나 검색을 위해 전용 도구(Read, Grep, Glob)를 별도로 제공한다. 이러한 비셸 도구 호출은 RTK를 완전히 우회(bypass)한다. 결과적으로 벤치마크 전체에서 Claude Code 터미널 관련 호출의 31%, OpenCode 호출의 51%만이 RTK를 거쳤다. 더욱이 Claude Code의 Bash 호출 중 약 절반은 이미 모델 스스로 head, tail, wc를 조합해 출력을 제한하고 있었다.

단 하나의 과제가 전체 통계를 지배한 Fable과 339회 루프 사고

그렇다면 전체 단순 합산에서 Fable 5.0의 비용이 5% 줄어든 것으로 나타났던 이유는 무엇일까? 개별 과제 데이터를 추적한 결과, Fable의 절감분 전체는 거의 전부 `winning-avg-corewars` 단 하나의 과제에서 나온 것으로 밝혀졌다.

이 과제에서 Fable은 RTK 적용 시 턴 수가 약 절반으로 줄어들었다. 턴 수가 절반 가까이 줄면서 발생한 막대한 절감분이 85개 과제 전체의 합산 그래프를 왜곡했던 것이다. 실제로 winning-avg-corewars 한 과제를 제외하면, 나머지 84개 과제에서 Fable의 절감률은 1% 미만에 불과했다. 반대로 DeepSeek 환경에서는 동일한 과제에서 RTK 적용 시 턴 수가 늘어나며 비용이 오히려 증가했다.

또한 에이전트 셸 명령을 도구가 임의로 재작성하는 방식은 치명적인 런타임 장애를 초래할 수 있음이 드러났다. DeepSeek 환경의 git-multibranch 과제 시도 중 하나에서 심각한 무한 루프가 발생했다.

에이전트는 find 명령에 특정 플래그를 붙여 실행했다. 그러나 당시 RTK 0.45.0 버전의 rtk find는 해당 플래그를 지원하지 않았다. 플러그인은 명령을 rtk find로 재작성했고, 실행 결과 "Use `find` directly(find 명령을 직접 사용하라)"는 에러가 에이전트에게 반환되었다. 에이전트는 지시에 따라 다음 턴에서 다시 find를 호출했으나, 플러그인은 이를 또다시 rtk find로 재작성하여 동일한 오류를 유발했다.

이 에러 루프는 약 12분 동안 이어지며 339회의 연속 실패를 기록했다. 에이전트는 타임아웃 직전에 간신히 과제를 통과했지만, 정상적으로 통과한 동일 기준선 시도 대비 약 9배에 달하는 비용을 소모했다. 비록 단일 이상치였고 RTK 0.46.0에서 수정되었다 하더라도, 에이전트의 피드백 루프 중간에서 명령어를 강제 변형하는 도구가 시스템의 자율 수정 메커니즘과 충돌할 때 얼마나 위험한 비용 폭탄이 터질 수 있는지를 명확히 보여 준다.

JetBrains SkillsBench 교차 검증과 프론티어 모델의 터미널 효율

Quesma 블로그의 벤치마크 결과는 외부 기관의 독립적인 검증과도 일치한다. 글로벌 개발 도구 기업 JetBrains는 자사의 SkillsBench 평가 프레임워크를 사용해 Claude Code와 RTK의 조합을 시험한 뒤, "절감 효과가 전혀 나타나지 않았다"고 발표했다.

JetBrains 연구진이 확인한 거동 역시 일맥상통했다. 모델의 탐색 노력이 낮은(Low effort) 조건에서는 터미널 출력 압축으로 인해 정보가 결핍되어 불필요한 턴 수만 증가했고, 노력이 높은(High effort) 복잡한 과제 조건에서는 비용이 전혀 줄어들지 않았다.

이러한 현상이 발생하는 기술적 배경은 프론티어 파운데이션 모델의 진화와 직결되어 있다. 과거의 구형 모델들은 터미널에서 전체 디렉터리 목록이나 수천 줄의 로그를 무차별적으로 출력한 뒤 컨텍스트 윈도우를 소진하는 비효율적인 행동을 자주 보였다. 당시에는 외부 도구가 출력을 강제로 잘라 주는 방식이 부분적인 효과를 낼 수 있었다.

그러나 최신 프론티어 모델들은 이미 터미널을 극도로 효율적으로 다룬다. 실제 트랜스크립트를 보면 Fable 5.0의 컨텍스트 중 터미널 출력이 차지하는 비중은 약 7%에 불과했다. 모델 스스로 긴 로그를 확인할 때 head -n이나 tail -n을 명령어 뒤에 붙여 필요한 만큼만 슬라이싱하여 읽는다. 모델 자체가 이미 터미널 출력을 능동적으로 통제하고 있는 환경에서, 외부 도구를 끼워 넣어 텍스트를 한 번 더 깎아내는 것은 일반적인 절감 수단이 될 수 없으며, "틈새 최적화(Niche optimization)"에 불과하다는 것이 저자의 평가다.

LLM 도구 생태계의 교훈 — 자체 보고 지표의 맹점과 에이전트 비용 통제

Quesma 블로그의 최종 결론은 명확하다. 원문 저자는 "RTK does not make AI coding cheaper"(RTK는 AI 코딩을 더 싸게 만들지 않는다)라고 결론짓고, Terminal-Bench 2.1 벤치마크 결과를 근거로 RTK를 일반적인 비용 절감 도구로 추천하지 않는다고 밝혔다.

이 벤치마크는 생성형 AI 도구 생태계를 평가할 때 엔지니어링 실무자가 반드시 유념해야 할 네 가지 핵심 교훈을 제시한다.

  • 자체 보고 지표(Self-Reported Metrics)의 회의적 검증: 도구가 콘솔에 찍어 주는 절감 수치는 실제 비즈니스 비용(클라우드 청구액)과 정반대로 움직일 수 있다. 지표의 산식과 정의를 직접 확인하고 실제 인보이스 데이터와 대조해야 한다.
  • 비용 통제의 본질은 텍스트 길이가 아닌 턴 수 관리: 프롬프트 캐싱이 정착된 환경에서 텍스트 몇 바이트를 줄이는 것은 요금에 거의 영향을 주지 못한다. 부주의한 압축으로 인해 에이전트가 방황하며 턴이 늘어나는 순간 비용은 통제 불능으로 치솟는다.
  • 단일 과제 착시와 통계적 엄밀성: 단순 합산 통계는 단 하나의 대형 과제에 의해 왜곡될 수 있다. 과제별 정규화 평균과 신뢰구간을 교차 검증하지 않는 벤치마크는 잘못된 기술 결정을 유도한다.
  • 구조적 인프라 통제의 필요성: 출력을 인위적으로 깎아내는 미시적 도구보다는, 이전 분석 글 모든 요청을 비싼 모델에 맡기지 않는다 - LLM 라우터와 Switchyard에서 살펴본 것과 같은 동적 모델 라우팅이나 본 블로그의 AI 코딩 비용을 조직 단위로 통제하는 법에서 제시한 체계적인 예산 상한선 및 캐시 최적화 전략이 훨씬 안전하고 검증된 대안이다.

확인하지 못한 것

공개된 벤치마크 보고서 및 기술 자료의 한계로 인해, 본 분석에서 독립적으로 검증하지 못한 사항들은 다음과 같다.

  • Terminal-Bench 3.0 및 4.0 고난도 환경에서의 RTK 거동: 본 실험은 에이전트 통과율이 안정적인 2.1 버전을 기준으로 진행되었으며, 복잡도가 급격히 상승한 3.0과 4.0 벤치마크에서 터미널 출력 압축이 작업 완결률과 비용에 미치는 영향은 확인하지 못했다.
  • RTK 0.46.0 이후 버전에서 명령어 루프 버그 수정 후의 장기 안정성: git-multibranch 과제에서 339회 에러를 낸 rtk find 버그가 0.46.0에서 수정되었다는 사실은 확인했으나, 패치된 버전으로 1,740회 전체 실험을 다시 수행한 통계 데이터는 공개되지 않았다.
  • Fable 및 DeepSeek 이외의 타사 파운데이션 모델군에서의 턴 수 변화: 시험은 Claude Code + Fable 5.0과 OpenCode + DeepSeek V4 Pro 조합만을 대상으로 했으며, GPT-5나 Gemini 3.8 등 다른 모델군에서 터미널 압축 시 턴 수가 증가하는 구체적 비율은 확인하지 못했다.
  • 터미널 조작이 거의 없고 순수 단일 파일 패치만 수행하는 실무 프로젝트에서의 비용 효과: 터미널 벤치마크가 아닌, 개발자가 작성한 명확한 이슈 티켓을 기반으로 단일 파일 단위의 코드 수정만 반복하는 일반 기업 코드베이스에서의 누적 청구액 데이터는 공개되지 않았다.
