정규식이 멈추지 않는다 - 탐욕 매칭과 백트래킹 폭발

한 글자가 늘 때마다 시간이 두 배가 되는 구조를 직접 재고, 네 가지 방법으로 끊는다

2026-09-01 개발/인프라

정규식이 틀린 결과를 내면 금방 안다. 테스트가 빨갛게 뜨고, 로그에 잘못 잘린 값이 남는다. 곤란한 쪽은 정규식이 답을 내지 않는 경우다. 예외도 없고 오류 메시지도 없다. 그냥 그 줄에서 프로세스가 서 있다. CPU 는 한 코어를 100퍼센트로 물고, 스택 추적을 떠 보면 String.prototype.match 어딘가다.

이 상황에서 가장 자주 나오는 오해는 입력이 크다는 것이다. 아래에서 재 볼 예제의 입력은 31 바이트고, 그걸 처리하는 데 7.8 초가 걸렸다. 원인은 데이터의 크기가 아니라 패턴의 모양에 있다. 이 글은 그 모양이 무엇인지, 왜 지수로 커지는지, 어떻게 끊는지를 전부 시간을 재서 확인한다.

이 글에 붙은 숫자는 아래 「측정 환경」에 적은 한 대의 기계에서 실제로 실행해 얻은 값이다. CPU·런타임 버전·다른 프로세스의 부하에 따라 절대값은 얼마든지 달라진다. 봐야 할 것은 밀리초의 자릿수가 아니라 입력이 조금 늘 때 시간이 어떤 비율로 늘어나는가다. 그 비율만은 기계가 달라도 같은 모양으로 나온다.

백트래킹이라는 구조

대부분의 프로그래밍 언어가 쓰는 정규식 엔진은 역추적(backtracking) 방식이다. 동작 방식은 이름 그대로다. 패턴을 왼쪽부터 읽어 가며 문자열에 맞춰 보다가, 어딘가에서 막히면 가장 최근에 선택지가 있었던 지점으로 되돌아가 다른 선택을 해 본다. 미로에서 갈림길마다 표시를 남기고, 막다른 길을 만나면 마지막 표시로 돌아가는 것과 같다.

이 방식이 느릴 수 있는데도 널리 쓰이는 이유가 있다. 되돌아갈 수 있어야만 표현되는 기능들이 있기 때문이다.

  • 역참조 — (\w+)\s+\1 처럼 「앞에서 잡은 것과 같은 것」을 요구하는 문법. 앞의 그룹이 무엇을 잡았는지 기억하고 다시 시도할 수 있어야 성립한다
  • 룩어라운드 — (?=...), (?<=...) 같은 위치 검사. 한 지점에서 다른 패턴을 시험 삼아 맞춰 보고 원래 자리로 돌아와야 한다
  • 탐욕 수량자의 되물림 — .* 가 일단 끝까지 먹고, 뒤가 안 맞으면 한 글자씩 게워 내는 동작 자체가 되돌아가기다
  • 선택지의 우선순위 — (a|ab) 에서 왼쪽을 먼저 시도하고 실패하면 오른쪽으로 간다는 규칙도 되돌아가기 위에 얹혀 있다

이 기능들은 형식 언어 이론에서 말하는 정규 언어의 범위를 넘어선다. 그래서 상태 기계 한 번 훑기로는 처리할 수 없고, 탐색이 필요하다. 탐색에는 최악의 경우가 있다. 그리고 그 최악은 대개 우리가 생각하는 것보다 훨씬 가까이 있다.

재앙을 재현한다 - 한 글자에 두 배

교과서적인 예제는 ^(a+)+$ 다. 여기에 a 를 n 개 이어 붙이고 마지막에 b 를 붙인 문자열을 넣는다. b 는 절대 매칭되지 않으므로 엔진은 가능한 모든 분기를 다 시도한 뒤에야 실패를 선언할 수 있다. 잰 코드는 이렇다.

const CAP_MS = 4000;   // 한 번이 4초를 넘으면 중단

for (let n = 10; n <= 34; n++) {
  const s = 'a'.repeat(n) + 'b';
  const re = new RegExp('^(a+)+$');
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  console.log(n, ms.toFixed(3));
  if (ms > CAP_MS) break;
}

비율 열이 전부 2 근처에 모여 있다. 이것이 지수 증가의 지문이다. 한 글자가 시간을 두 배로 만든다는 뜻이고, 그러면 열 글자가 천 배다. 위 표를 그대로 연장하면 40 자에서 두 시간대, 50 자에서 몇 달 단위가 된다. 그래서 「멈췄다」고 느끼는 것이다. 실제로 멈춘 것이 아니라, 끝나는 시점이 사람의 시간 감각 밖으로 나간 것뿐이다.

눈여겨볼 지점은 구간이 매우 좁다는 것이다. 20 자까지는 6 밀리초여서 어떤 테스트도 통과한다. 25 자에서 0.1 초, 29 자에서 2 초, 31 자에서 7.8 초다. 개발 중에 쓰는 짧은 샘플로는 절대 걸리지 않고, 운영에서 조금 긴 값이 들어오는 순간 한 번에 넘어간다.

왜 폭발하는가 - 나누는 방법의 개수

병의 이름은 모호성이다. (a+)+ 에서 안쪽 a+ 는 a 를 한 개 이상 먹고, 바깥 + 는 그것을 한 번 이상 반복한다. 그러면 aaaa 라는 네 글자를 이 패턴에 맞추는 방법이 하나가 아니다. 4, 3+1, 1+3, 2+2, 2+1+1, 1+2+1, 1+1+2, 1+1+1+1 — 여덟 가지다. 일반적으로 n 글자를 이렇게 쪼개는 방법은 2n-1 가지다.

매칭이 성공하면 엔진은 첫 번째로 찾은 방법에서 멈춘다. 그런데 뒤에 b 가 있어서 $ 가 실패하면, 엔진은 「다른 방법으로 나눴다면 됐을지도 모른다」고 판단하고 전부 시도한다. 나누는 방법이 2n-1 가지니까 시도도 그만큼이다. 같은 문자열을 여러 방식으로 나눌 수 있고, 그 결과가 모두 실패하는 것 — 이 두 조건이 겹치는 자리가 폭발 지점이다.

이 진단이 맞는지 확인하는 방법은 같은 병을 앓는 다른 모양들을 재 보는 것이다. 겉모습은 전혀 다르지만 「나누는 방법이 여럿」이라는 성질은 같다.

패턴n=20n=24n=28n=29
^(a+)+$6.480 ms109.264 ms2233.649 ms3995.791 ms
^(a|a)*$13.354 ms191.011 ms3368.902 ms6640.935 ms
^(a*)*$12.359 ms242.906 ms3675.270 ms7156.893 ms

셋 다 같은 곡선을 그린다. (a|a)* 는 두 분기가 정확히 같은 것을 문다. 어느 쪽을 골라도 결과가 같으니 n 번 반복하면 2n 가지 경로가 생기고, 전부 똑같이 실패한다. (a*)* 는 안쪽이 빈 문자열까지 먹을 수 있어서 분할 가짓수가 더 늘어난다. 문법은 다르지만 병은 하나다.

  • 수량자 안에 수량자가 들어 있고, 안쪽이 가변 길이다 — (a+)+, (\w+\s?)*, ([a-z]*)+
  • 선택 분기들이 같은 글자를 물 수 있다 — (a|a)*, (\d|\w)*, (x|xy)*
  • 반복 안에 빈 문자열을 매칭할 수 있는 요소가 있다 — (a*)*, (\s?)*
  • 세 경우 모두 조건은 하나로 요약된다. 같은 입력을 패턴에 대응시키는 방법이 두 가지 이상이면 실패했을 때 그 전부를 확인한다

실패할 때만 터진다

이 성질은 진단할 때 결정적이다. 같은 패턴, 같은 크기의 입력이라도 매칭이 성공하면 아무 일도 일어나지 않는다. 엔진은 첫 성공에서 즉시 멈추기 때문이다. 같은 n=26 에서 세 경우를 나란히 쟀다.

입력 "a"×26 + "b"   패턴 ^(a+)+$    447.897 ms   (실패)
입력 "a"×26 + "b"   패턴 ^(a+)+     0.0005 ms    (즉시 성공)
입력 "a"×26        패턴 ^(a+)+$    0.0002 ms    (즉시 성공)

세 번째 줄이 특히 중요하다. 패턴은 문제의 그 패턴 그대로인데, b 하나가 없으니 0.0002 밀리초다. 백만 배 넘는 차이가 입력의 마지막 한 글자에서 나온다. 두 번째 줄은 $ 를 뺀 것이다. 끝까지 맞을 필요가 없어지자 앞부분에서 바로 성공하고 끝난다.

여기서 실무적인 결론이 하나 나온다. 유효한 값만 넣어 보는 테스트로는 이 결함을 절대 못 잡는다. 정규식 테스트를 쓸 때 성공 케이스만 채워 넣는 습관이 흔한데, 이 부류의 결함은 정확히 그 사각에 숨는다. 그리고 운영에서 들어오는 값은 대체로 유효하지 않은 쪽이 훨씬 다양하다.

같은 이유로 앵커의 유무도 시간을 바꾼다. 시작 앵커 ^ 가 없으면 엔진은 첫 글자에서 실패한 뒤 두 번째 글자부터 다시, 세 번째 글자부터 다시 시도한다. n=24 에서 ^(a+)+$ 가 116.532 밀리초일 때 (a+)+$ 는 295.768 밀리초로 2.5 배였다. 앵커를 붙이는 것은 지수를 없애 주지는 않지만 앞에 붙는 계수를 지운다.

탐욕과 게으름과 소유

수량자에는 세 가지 성격이 있다. 셋의 차이는 「얼마나 먹는가」가 아니라 「먹은 것을 돌려줄 것인가」다.

목표가 앞에 있을 때 게으름이 900 배 가까이 빠르다. 탐욕은 일단 20 만 자를 끝까지 먹고 거기서부터 되돌아오기 때문이다. 그런데 목표가 뒤에 있으면 세 패턴이 사실상 같다. 게으름이 이번에는 앞에서부터 한 글자씩 늘려 가며 20 만 번 시도하기 때문이다. 게으름은 성능 대책이 아니라 의미의 선택이다. 최단 매칭을 원하면 쓰는 것이고, 속도는 데이터의 생김새를 따라간다.

진짜 대책은 소유 수량자와 원자적 그룹이다. 이 둘은 엔진에게 「여기서 되돌아가는 것을 포기하라」고 명시적으로 지시한다. a++ 는 a 를 최대한 먹고, 뒤가 실패해도 게워 내지 않는다. 게워 낼 선택지가 없으면 분기가 생기지 않고, 분기가 없으면 지수도 없다. Python 3.13.3 과 Perl 5.38.2 에서 확인한 값이다.

Python 3.13.3
  ^(a+)+$    n=26        3323.962 ms
  ^(a++)+$   n=100000    0.0398 ms
  ^(?>a+)+$  n=100000    0.0395 ms

Perl 5.38.2
  ^(a++)+$   n=100000    0.0091 ms
  ^(?>a+)+$  n=100000    0.0091 ms

입력이 3800 배 커졌는데도 시간은 0.04 밀리초다. 다만 주의할 것이 있다. 소유 수량자는 의미를 바꾼다. "[^"]*+" 처럼 되돌아갈 필요가 없는 자리에 쓰면 안전하지만, 뒤에서 되물림이 필요한 패턴에 그냥 붙이면 맞던 것이 안 맞게 된다. 성능 옵션이 아니라 의미 선언으로 다뤄야 한다.

자바스크립트에서 되돌아가기를 끊는 법

자바스크립트에는 이 도구가 없다. Node.js v22.16.0 (V8 12.4.254.21-node.26) 에서 셋 다 컴파일 단계에서 거부된다.

> new RegExp('^(?>a+)+$')
SyntaxError: Invalid regular expression: /^(?>a+)+$/: Invalid group

> new RegExp('^a*+$')
SyntaxError: Invalid regular expression: /^a*+$/: Nothing to repeat

> new RegExp('^a++$')
SyntaxError: Invalid regular expression: /^a++$/: Nothing to repeat

Nothing to repeat 라는 메시지가 상황을 그대로 보여 준다. V8 은 a++ 를 「소유 수량자」로 읽지 않고 「+ 를 + 로 또 반복하라」는 문법 오류로 읽는다. 소유라는 개념 자체가 없는 것이다.

대신 같은 효과를 내는 관용구가 있다. 룩어헤드 안에 그룹을 넣고 그 그룹을 역참조하는 방식이다. (?>X) 를 (?=(X))\1 로 바꾼다. 룩어헤드는 안쪽에서 한 번 확정하고 나면 밖에서 되돌려 주지 않기 때문에, 역참조로 그 결과를 그대로 소비하면 원자적 그룹과 같아진다.

// ^(a+)+$  를 원자화
const naive  = /^(a+)+$/;
const atomic = /^(?=(a+))\1+$/;

// "a"×26 + "b"
naive.test(s)    →  528.117 ms
atomic.test(s)   →  0.0005 ms

// 같은 atomic 패턴을 훨씬 큰 입력에
n=1000     0.0009 ms
n=10000    0.0077 ms
n=100000   0.0771 ms

입력이 100 배씩 커질 때 시간도 대략 10 배씩 커진다. 선형에 가깝다는 뜻이다. 이 관용구는 읽기 어렵다는 단점이 분명하니, 쓸 거면 왜 이렇게 썼는지 주석을 반드시 남긴다. 나중에 누군가 「불필요한 룩어헤드」로 판단해 정리하면 결함이 그대로 돌아온다.

지수가 아니어도 느리다

지수 폭발은 극적이지만 흔하지는 않다. 실무에서 훨씬 자주 만나는 것은 다항 백트래킹이다. .* 를 여러 번 쓰고 그 사이를 구분자로 나누는 패턴이 전형적이다. 로그 파싱과 CSV 처리에서 거의 매번 나온다.

^"(.*)" "(.*)" "(.*)"$ 같은 패턴에 따옴표로 감싼 필드가 여러 개 있는 줄을 넣고, 끝에 한 글자를 더 붙여 매칭이 실패하게 했다. 세 개의 .* 가 구분자 위치를 고르는 조합만큼 일한다.

필드 수줄 길이"(.*)""([^"]*)"
1050 자0.003 ms0.0001 ms
20110 자0.024 ms0.0001 ms
40230 자0.208 ms0.0001 ms
80470 자1.774 ms0.0001 ms

길이가 20 배 늘 때 시간은 5000 배가 됐다. 두 배마다 8 배 안팎이니 대략 세제곱이다. 지수처럼 즉사시키지는 않지만, 로그 한 줄이 길어졌을 때 파서 전체가 느려지는 원인으로는 이쪽이 훨씬 흔하다. 그리고 오른쪽 열을 보면 답이 나와 있다. .* 를 [^"]* 로 바꾸는 것만으로 모든 크기에서 평평해진다.

이유는 단순하다. [^"]* 는 따옴표를 만나면 무조건 멈춘다. 멈추는 자리가 하나로 정해지므로 조합이 생기지 않는다. .* 는 따옴표도 먹을 수 있으니 어디서 멈출지를 엔진이 시도해 봐야 한다. 구분자를 문자클래스에서 빼는 것이 이 부류에서 가장 값싼 수정이다.

실무에서 자주 나오는 모양

위험한 패턴은 보통 「위험해 보이게」 생기지 않았다. (a+)+ 라고 써 놓는 사람은 없고, 실제로 들어 있는 형태는 아래쪽이다.

모양실제로 보이는 형태숨어 있는 것
중첩 수량자^(\w+\s?)*$ — 단어들이 공백으로 이어진 줄인지 검사\s? 가 선택적이라 \w+ 끼리 붙을 수 있고, 그러면 분할이 여러 가지
겹치는 분기(\d|\w)+ — 숫자나 글자의 반복\d 가 \w 에 포함되어 모든 숫자가 두 경로를 만든다
점-별표 연쇄^(.*) (.*) \[(.*)\] "(.*)"$ — 액세스 로그 한 줄구분자 위치 조합. 필드가 길어질수록 다항으로 늘어난다
느슨한 이메일 검증^([\w.-]+)+@([\w-]+\.)+[a-z]{2,}$앞부분이 (X+)+ 와 같은 모양. 도메인 쪽도 반복 안의 반복이다
공백 정리^(\s*)+$ 또는 (\s|\t)*$빈 문자열을 먹을 수 있는 요소의 반복. 탭·공백 혼합에서 갈라진다

첫 줄을 실제로 재 봤다. ^(\w+\s?)*$ 에 글자를 n 개 이어 붙이고 끝에 ! 를 붙였다. 공백 없는 문자열에서도 \s? 가 빈 것을 먹을 수 있어 분할이 갈라진다.

이 패턴은 「사용자 이름이 단어와 공백으로만 이루어졌는지」를 검사하는 입력 검증에 흔히 들어간다. 그리고 그런 검증은 정의상 사용자 입력을 직접 받는 자리에 있다.

ReDoS - 정지성이 가용성 문제가 되는 자리

지금까지 본 것은 성능 이야기였다. 사용자 입력이 이런 패턴에 닿는 순간 성격이 바뀐다. 정규식 서비스 거부(ReDoS) 는 짧은 입력 하나가 처리 스레드를 오래 붙잡아 서비스 전체를 세우는 상황을 가리킨다. 특별한 권한도, 대량의 트래픽도 필요 없다는 점이 이 문제의 성격이다.

단일 스레드 이벤트 루프에서 도는 런타임에서는 파급이 특히 크다. 요청 하나가 매칭에 7 초를 쓰면 그 7 초 동안 같은 프로세스의 다른 모든 요청이 대기한다. 헬스체크가 응답하지 않아 인스턴스가 교체되고, 교체된 쪽에 같은 요청이 들어가면 그대로 반복된다.

이 글은 취약한 입력을 만드는 방법을 다루지 않는다. 필요한 것은 어디에 어떤 모양이 있는지 스스로 찾아 막는 쪽이다.

  • 입력 길이를 먼저 자른다. 정규식에 닿기 전에 if (s.length > 200) return false; 를 두는 것만으로 최악이 상수로 묶인다. 지수 곡선에서는 상한 몇 글자 차이가 크다
  • 패턴에서 모양을 없앤다. 근본 수정이다. 중첩 수량자를 풀고, 분기가 겹치지 않게 하고, 문자클래스에서 구분자를 뺀다
  • 경계에 시간 상한을 둔다. 사용자 입력을 처리하는 매칭을 별도 워커나 시간 제한이 있는 경로로 옮긴다. JS 표준 정규식 자체에는 타임아웃이 없다
  • 패턴을 데이터로 받지 않는다. 사용자가 넣은 문자열로 new RegExp() 를 만드는 자리는 패턴 자체가 통제 밖이 된다. 이 경우 위의 어떤 검토도 소용이 없다
  • 의존성에 들어 있는 패턴도 대상이다. 자기 코드에 없어도 파서·검증 라이브러리 안에 있으면 같은 결과가 난다

첫 번째 항목의 효과를 실제로 쟀다. 같은 취약 패턴에 상한만 다르게 걸었을 때의 최악값이다.

maxLength=16   최악 0.195 ms
maxLength=20   최악 3.131 ms
maxLength=24   최악 51.605 ms
maxLength=28   최악 849.141 ms

상한을 28 에서 16 으로 내리는 것만으로 4000 배가 줄어든다. 다만 이건 완화이지 수정이 아니다. 길이 상한은 나중에 요구사항이 바뀌면 조용히 올라가고, 그때 결함이 되살아난다. 패턴 자체를 고치는 쪽이 항상 우선이다.

엔진마다 다르다

여기서 예상 밖의 결과가 하나 나왔다. 같은 ^(a+)+$ 를 Perl 5.38.2 에서 돌렸더니 폭발하지 않았다. n=20 에서 0.017 밀리초, n=34 에서 0.018 밀리초로 평평했다. ^(a*)*$ 와 ^(\w+\s?)*$ 도 마찬가지였다. Perl 의 엔진이 실패한 (위치, 패턴 지점) 조합을 기억해 같은 일을 다시 하지 않는 최적화를 갖고 있는 것으로 보인다.

그렇다고 Perl 이 안전하다는 뜻은 아니다. 같은 Perl 에서 앞 절의 다항 패턴 ^"(.*)" "(.*)" "(.*)"$ 는 그대로 느려졌다. 필드 10 개에서 0.011 밀리초, 80 개에서 6.199 밀리초, 320 개에서 323.276 밀리초였다. 최적화가 잡아 주는 모양이 있고 그렇지 않은 모양이 있다는 뜻이다.

반대편에는 오토마타 기반 엔진이 있다. 되돌아가는 대신 가능한 상태를 동시에 들고 입력을 한 번만 훑는다. GNU grep 3.0 으로 같은 패턴을 재 봤다.

grep 프로세스 기동만 (1바이트 파일)      0.046 ~ 0.052 s

기동 시간이 0.05 초라서 그 아래는 측정되지 않는다. 의미 있는 값은 마지막 줄이다. 500 만 자를 실제 매칭 작업 약 0.05 초에 끝냈다. Node 가 31 자에 7.8 초를 쓴 그 패턴이다. 곡선 자체가 다르다.

맞바꾸는 것이 있다. Go 의 regexp 패키지 문서는 「이 패키지가 제공하는 구현은 입력 크기에 선형인 시간에 도는 것이 보장된다(대부분의 오픈소스 정규식 구현이 보장하지 않는 성질이다)」고 명시한다. 그 대가로 RE2 문법 문서는 역참조 \1 과 룩어라운드 (?=re)·(?!re)·(?<=re)·(?<!re) 를 전부 지원하지 않음으로 표시한다.

여기에 미묘한 대칭이 있다. 앞 절에서 자바스크립트의 폭발을 막은 관용구 (?=(a+))\1 는 룩어헤드와 역참조를 둘 다 쓴다. 즉 역추적 엔진을 구해 내는 그 도구가, 애초에 폭발이 없는 오토마타 엔진에는 존재할 수 없는 도구다. 선형 시간 보장과 표현력은 같은 축의 양 끝이다.

고치는 법 - 전후를 나란히 재기

고치는 방법은 네 가지고, 위에서 이미 하나씩 나왔다. 여기서는 전후를 같은 표에 놓는다. 순서는 위쪽이 더 근본적이다.

중첩 수량자를 푼다

가장 확실한 수정이다. (\w+\s?)* 처럼 「반복 안에 선택적 요소」가 있으면, 그 선택적 요소를 반복 밖으로 빼서 분할을 하나로 확정한다. ^\w+(\s\w+)*$ 로 바꾸면 공백이 반드시 있어야 다음 반복이 시작되므로 나누는 방법이 하나뿐이다.

문자클래스를 좁힌다

구분자로 쓰는 글자를 클래스에서 뺀다. "(.*)" → "([^"]*)", (.*) → (\S+) . 멈출 자리가 하나로 정해지면 조합이 사라진다. 의미도 대개 더 정확해진다.

되돌아가기를 포기시킨다

Python·Perl·PCRE 계열이면 소유 수량자나 원자적 그룹을 쓴다. 자바스크립트면 룩어헤드 관용구를 쓴다. 이건 모양을 그대로 두고 증상만 막는 쪽이라, 위의 두 방법을 쓸 수 없을 때의 선택지다.

정규식을 쓰지 않는다

구분자로 자르는 일이라면 문자열 함수가 더 빠르고 더 읽기 쉽다. 602 자짜리 세 필드 줄을 20 만 번 분해한 결과다.

자기 패턴을 재는 최소 스크립트

패턴을 눈으로 봐서 판정하는 것은 생각보다 어렵다. 대신 입력 길이를 늘려 가며 시간을 재면 눈으로 판정할 필요가 없어진다. 선형이면 비율이 1 근처에 머물고, 지수면 비율이 계속 2 근처에 있다.

// redos-probe.js
// 사용: node redos-probe.js "<패턴>" [반복단위] [꼬리]
const [, , src, unit = 'a', tail = 'b'] = process.argv;
const BUDGET_MS = 2000;
const re = new RegExp(src);
let prev = 0;

console.log('n\tms\t직전대비');
for (let n = 2; n <= 200000; n = n < 40 ? n + 2 : Math.ceil(n * 1.6)) {
  const s = unit.repeat(n) + tail;
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  const ratio = prev > 0.05 ? (ms / prev).toFixed(2) : '-';
  console.log(n + '\t' + ms.toFixed(3) + '\t' + ratio);
  if (ms > BUDGET_MS) {
    console.log('\n판정: 초선형. n=' + n + ' 에서 ' + ms.toFixed(0) + ' ms');
    process.exit(2);
  }
  prev = ms;
}
console.log('\n판정: n=200000 까지 ' + BUDGET_MS + ' ms 를 넘지 않았다');

핵심은 BUDGET_MS 다. 한 번이 이 값을 넘으면 즉시 중단한다. 지수 곡선에서 다음 단계는 두 배이므로, 상한 없이 돌리면 스스로가 자기 기계를 세우게 된다. tail 값은 매칭을 실패시키는 글자여야 한다. 성공하는 입력으로는 아무것도 드러나지 않는다는 것이 앞에서 본 결과다.

판정: n=200000 까지 2000 ms 를 넘지 않았다

두 출력의 차이가 그대로 진단이다. 위쪽은 n 이 2 씩 늘 때 시간이 4 배가 된다. 아래쪽은 n 이 1.6 배 늘 때 시간이 1.6 배가 된다. 두 번째 열이 아니라 세 번째 열을 본다. 절대 시간은 기계마다 다르지만 비율은 패턴의 성질이다.

정규식을 쓰지 말아야 할 때

여기까지가 고치는 이야기였고, 마지막은 애초에 쓰지 않는 자리다. 정규식이 표현할 수 있는 것은 중첩 깊이가 정해지지 않은 구조를 뺀 나머지다. 이 경계를 넘어가면 패턴이 길어지고, 길어진 패턴에 위에서 본 모양들이 딸려 들어온다.

  • HTML·XML — 태그가 서로 감쌀 수 있어서 깊이에 제한이 없다. 정규식으로 여는 태그와 닫는 태그를 짝지을 수 없다. 파서를 쓴다
  • JSON·YAML — 같은 이유. 객체 안의 객체는 재귀 구조이고, 표준 라이브러리에 파서가 이미 있다
  • 괄호 짝 맞추기 — 정규 언어의 범위 밖이라는 것이 형식적으로 증명돼 있는 대표 사례다. 세면서 훑는 코드가 정답이다
  • 이메일 주소 검증 — 규격을 정확히 따르는 정규식은 길고, 대체로 위험한 모양을 포함한다. 「@ 가 하나 있고 앞뒤가 비어 있지 않은가」 정도로 형식만 보고, 진짜 검증은 확인 메일로 한다
  • URL 파싱 — 각 언어에 URL 클래스나 동등한 것이 있다. 직접 쓴 패턴은 예외 케이스에서 반드시 틀린다
  • 정해진 구분자로 자르기 — split·indexOf 로 되는 일에 정규식을 쓰면 느리고 읽기 어렵다
  • 고정 문자열 찾기 — includes 나 grep -F 를 쓴다. 패턴이 아닌 것을 패턴 엔진에 넣을 이유가 없다

정규식이 맞는 자리는 여전히 넓다. 평평하고, 길이가 제한돼 있고, 구조가 재귀적이지 않은 텍스트에서 정규식만큼 짧게 의도를 적는 도구가 없다. 문제는 그 자리를 벗어난 뒤에도 계속 쓰는 것이다.

같은 정규식이라도 도구마다 문법이 다르다는 문제는 정규식 방언 호환성에서, 룩어헤드의 실전 용법은 룩어헤드 실무 활용에서, 한글을 다룰 때의 음절 함정은 한글 정규식 음절 함정에서 따로 다뤘다. 셸에서 글롭과 정규식을 헷갈리는 문제는 셸 글롭과 정규식의 차이에 있다.

확인하지 못한 것

  • Perl 5.38.2 가 ^(a+)+$ 에서 폭발하지 않은 정확한 기제는 확인하지 못했다. 실패한 조합을 기억하는 최적화로 보이지만, 이 기계의 perldoc 이 동작하지 않아 공식 문서에서 그 이름과 조건을 확인할 수 없었다. 측정값만 그대로 적었다
  • Go 와 RE2 는 이 기계에 설치돼 있지 않아 실행하지 못했다. 표의 해당 행은 실측이 아니라 공식 문서의 서술이다. 선형 시간 보장과 역참조·룩어라운드 미지원은 문서에서 확인했지만, 실제 시간은 재지 않았다
  • GNU grep 3.0 의 내부 구현을 코드로 확인하지는 않았다. 「오토마타 방식」은 널리 알려진 서술이고 측정 결과가 그것과 일치하지만, 이 글이 확인한 것은 폭발이 관측되지 않았다는 사실까지다
  • grep 측정은 프로세스 기동 시간 약 0.05 초에 묻혀서, 그 아래 구간의 실제 매칭 비용은 분해하지 못했다. 500 만 자에서 0.104 초라는 값에서 기동분을 뺀 나머지로 추정했을 뿐이다
  • Python 의 regex 서드파티 모듈과 re2 바인딩은 이 환경에 없어 비교에서 빠졌다. 표준 re 만 쟀다
  • 다른 자바스크립트 엔진(SpiderMonkey·JavaScriptCore)은 재지 않았다. V8 에서 나온 값이 다른 엔진에서 같으리라는 근거는 없다
