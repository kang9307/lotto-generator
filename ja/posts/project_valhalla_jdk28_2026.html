Project Valhalla — 10年の開発がJDK 28にどう反映されたか

値クラス・ヒープフラット化・スカラー化がJavaのオブジェクトオーバーヘッドを解体する — JEP 401が提供するものと開発者への影響

2026-06-22 開発・インフラ

序論：30年来の前提を変える

2026年6月現在、Javaの歴史上最も長い未完のプロジェクトがついにメインラインに入った。Project Valhallaだ。2014年にBrian Goetzが提案したこのプロジェクトは、12年の歳月を経てJDK 28でJEP 401（Value Classes and Objects）としてプレビュー反映された。コード約197,000行、数十回の設計反復——なぜこれほど時間がかかり、何が変わり、Java開発者に何をもたらすのかを正直に分析する。

まずこの記事の範囲を明確にする。JDK 28は計画・プレビュー段階であり（2026年6月時点の公開情報・報道に基づく）、確定したプロダクションリリースではない。パフォーマンス数値は報告されたベンチマークからの引用であり、実際のワークロードでの結果は異なる場合がある。

1. なぜ10年かかったのか — Javaのアイデンティティ危機

Javaは1995年の誕生以来、ひとつの根本的な前提の上に立ってきた。「すべてのオブジェクトはアイデンティティ（identity）を持つ」。アイデンティティとは、2つのオブジェクトが同じ値を持っていても、ヒープアドレスが異なれば別の存在だという意味だ。==演算子が参照を比較し、synchronizedがオブジェクトインスタンスをロックし、System.identityHashCode()が意味を持つのは、すべてこの前提の上にある。

アイデンティティはコストを生む。すべてのJavaオブジェクトは最低12〜16バイトのヘッダを持つ。x・y座標を持つPointオブジェクトはフィールド値8バイトの他にヘッダ16バイトを支払う。さらに深刻なのが間接参照だ。ArrayList<Point>はPointを直接格納しない。Pointオブジェクトを指すポインタの配列を格納する。CPUがPointのxにアクセスするには、配列→ポインタ→Pointオブジェクト→フィールドという2段階のメモリ間接参照が必要だ。キャッシュミスは避けられず、数百万回以上のループでこのコストは積み重なる。

Brian Goetzはこの問題を「Javaのアイデンティティ危機」と呼んだ。解決策は明確だ。識別が不要な小さなデータ型からアイデンティティを取り除けば、JVMはポインタなしにデータを直接配置できる。では、なぜ10年かかったのか。既存のJVM・コンパイラ・言語仕様・標準ライブラリの全レイヤが「すべてのオブジェクトはアイデンティティを持つ」を前提に設計されていたからだ。30年分のコードと生態系を守りながら根幹を変える作業は、単純な機能追加ではなく、パラダイムの手術だった。

2. 値クラス（value class）とは何か

Project Valhallaのスローガンは最初から一貫している。「codes like a class, works like an int」——クラスのように書き、intのように動く。JEP 401はこの目標の具体的な実現だ。

2.1 値クラスの宣言

値クラスはvalueキーワードで宣言する。

value class Point {
    int x;
    int y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

この宣言が意味することは2つだ。まず、Pointインスタンスはアイデンティティを持たない。次に、JVMはこのオブジェクトをポインタなしにインラインで配置してよいという権限を持つ。コード構造は通常のクラスと同じで、コンストラクタ・メソッド・インターフェース実装もそのままだ。ただし、ランタイム上の表現が根本的に変わる。

value recordもサポートされる。recordはすでに不変データキャリアを表現するために使われているため、値レコードは概念的に最も自然な組み合わせだ。

2.2 アイデンティティがないことが可能にする最適化

値クラスでは通常のクラスで当然だったことが許可されない。synchronized(point) {}はコンパイルエラー。System.identityHashCode(point)は意味を失う。参照比較==は内容比較に動作が変わる。これらの制約が同時に最適化の鍵だ。アイデンティティがないため、JVMはインスタンスをコピーや再構成しても意味が保たれる。これがヒープフラット化とスカラー化を可能にする前提だ。

3. ヒープフラット化とスカラー化 — 性能はどこから来るか

JEP 401の核心的な性能技術は2つだ。異なるレベルで動作するが、同じ方向を指している——ポインタを排除し、データを近くに置け。

3.1 ヒープフラット化（Heap Flattening）

従来のJavaでColor[] colors = new Color[1_000_000]を宣言すると、配列は100万個のポインタを持ち、各ポインタはヒープ全体に散在したColorオブジェクトを指す。colors[i].rへのアクセスには、配列ベース→ポインタ→Colorオブジェクトヘッダ→rフィールドという経路が必要だ。繰り返しアクセス時、CPUキャッシュはほぼ無効化される。

ColorがValueクラスなら、配列は100万個のポインタの代わりにr・g・b値が詰め込まれた連続メモリブロックを直接格納する。colors[i].rは配列ベースオフセット1つでアクセスできる。配列全体の反復処理は、CPUが最も好むパターン、すなわち順次メモリスキャンになる。報告されたベンチマークによれば、この差だけで一部のシナリオでメモリフットプリントが40〜50%削減され、反復演算で最大3倍の高速化が報告されている。

3.2 スカラー化（Scalarization）

スカラー化はJITコンパイラレベルの最適化だ。メソッドがPoint p = new Point(3, 4)を生成し、そのx・yフィールドだけを使うなら、JITはPointオブジェクトをヒープに確保する代わりに、x=3, y=4をCPUレジスタに直接置くことができる。ヒープへの確保自体がなくなる。GCの追跡対象も減る。整数を演算するように処理されるという意味で「スカラー」だ。

アイデンティティのある通常のオブジェクトはスカラー化できない。誰かがそのオブジェクトのアドレスを持っている可能性があり、アドレスが変わると観測可能な意味の差が生じる。値クラスはアイデンティティがないため、JVMがコピー・再配置・分解を自由に行える。これが10年の設計反復が解き明かした核心の鍵だ。

4. JDK 28で実際に反映されたものとされていないもの

2026年6月時点の公開OpenJDK情報と報道を基に、JDK 28プレビューに含まれるものと含まれないものを明確に区別する。

4.1 JDK 28プレビューに含まれるもの（公開計画に基づく）

  • value classとvalue recordの宣言構文（JEP 401）
  • 値クラスへのヒープフラット化とスカラー化JVM最適化
  • Integer・Double・Longなどの既存プリミティブラッパークラスの値クラスへの移行（プレビュー範囲）
  • 安価なボクシング（cheaper boxing）——ラッパークラスのボクシングオーバーヘッド削減
  • --enable-previewフラグで有効化

4.2 JDK 28に含まれないもの（今後の課題）

  • null制限型（非ヌラブル参照）：Point!のようにnullを不許可にする型
  • 特殊化ジェネリクス（JEP 402）：List<int>のようにボクシングなしでプリミティブパラメータ化されたジェネリクス
  • 128ビットエンコーディングサポート
  • 完全に成熟したJEP 402

特殊化ジェネリクスが含まれないことが最も惜しい点だ。List<int>は現在もList<Integer>としてボクシングを経る必要がある。Brian Goetzが直接述べたように「アイデンティティ除去が第一の壁であり、それが開けば特殊化ジェネリクスが可能になる」——JEP 401が「第一の関門」である理由だ。

5. ラッパークラス移行の落とし穴

IntegerがValueクラスになることは朗報に聞こえる。Integer[]がint[]に近いメモリ効率を持てば、ジェネリクスコレクションの長年のボクシングコスト問題が大幅に緩和される。しかし、重大な副作用がある。

Integerインスタンスにsynchronizedをかけていたコードは例外が発生する。値クラスはアイデンティティがないためモニター（monitor lock）の対象になれない。また、==比較の意味も変わる。JDK 5以降のInteger.valueOf（-128〜127の範囲）はキャッシュされたインスタンスを返し、==比較が偶然trueになっていた。値クラス移行後、このアイデンティティ同一性の意味が失われる。

既存コードベースで==でIntegerを比較したり、Integerをロックとして使うパターンは必ず事前点検が必要だ。2026年6月現在これはプレビュー段階のため、プロダクション直接適用よりテスト環境での探索が適切だ。

6. どのコードが最も恩恵を受けるか

Valhallaがすべてのコードを魔法のように速くするわけではない。恩恵が大きいパターンとそうでないパターンがある。

6.1 最大恩恵パターン

  • 大規模な値オブジェクト配列処理：金融データ（取引レコード）、座標処理（ゲーム・シミュレーション・GIS）、色バッファ（画像処理）、センサーデータストリーム
  • 数値集約ループ：ベクトル演算、行列積、統計集計など、CPUキャッシュ活用が重要なコード
  • 小さな不変データ型の高頻度生成・破棄：OptionType、座標ペア、RGB値、通貨金額+通貨ペアなど

6.2 恩恵が限定的なパターン

  • ロック・同期化が核心の共有可変状態：値クラスは既存のsynchronizedパターンを代替できない
  • すでにボクシングが少ないプリミティブ型コード：int[]を既によく使っているなら追加の恩恵は少ない
  • I/O・ネットワークバウンドコード：ボトルネックがメモリレイアウトでなければValhallaの最適化は無関係

7. Java開発者への意味 — 私の解釈

7.1 防御的パフォーマンスパターンがオプションになる

Javaパフォーマンスチューニングの長年のアドバイスに「小さなオブジェクトを大量に作るな、オブジェクトリストより配列を使え、ボクシングを避けろ」というものがあった。これらの根本はJavaのオブジェクトモデルが持つ構造的コストだ。Valhallaはそのコスト自体を下げる。防御的な設計原則の一部がもはや必須ではなくなる。小さな不変データ型を値クラスとして臆せず表現できるようになる。

7.2 C#・Rust・Swiftとの距離を縮める

C#はstruct値型を長年サポートし、Rustはスタック配置がデフォルトで、Swiftのstructも値意味論を持つ。Javaはこの分野で遅れており、数値集約作業ではC・C++・Rust・C#に対して明確なメモリ・性能の不利があった。Valhalla以降、この格差が大幅に縮まる。GC・境界チェックなどJVMの安全網はコストを持ち続けるが、オブジェクト配列のポインタ追跡という構造的弱点は大きく緩和される。

7.3 マイグレーションは段階的に

Valhallaは既存コードをデフォルトで壊さない。既存のclass Point {}はそのまま動作する。値クラスの恩恵を受けるには明示的にvalueを宣言する必要がある。ただし標準ライブラリの移行——IntegerなどがValueクラスになる——は受動的に影響を受ける。実用的な推奨事項：プレビュー段階では--enable-previewで探索しつつプロダクション依存を避け、将来のLTSに正式収録された後に戦略的に適用する。その前に既存コードベースでのIntegerロックパターンと==比較をあらかじめ取り除いておくのが先手の準備だ。

8. 結論 — 10年が正当化される理由

Project Valhallaが10年かかったのは遅さではなく、複雑さの誠実な反映だ。30年の言語の根本的な前提を既存の生態系を壊さずに変えることは、単純な機能追加では終わらない。言語・コンパイラ・JVM・標準ライブラリ・生態系の全レイヤが整列しなければならない。JEP 401一つのためのコミット197,000行はその重さを数字で示している。

2026年6月現在、JDK 28プレビューとして反映されたJEP 401はValhallaの第一の関門だ。特殊化ジェネリクスが来ればJavaの表現力と性能の両面でより大きな跳躍が来る。しかし今反映されたものだけでも意義は大きい。値クラス、ヒープフラット化、スカラー化——この3つが組み合わさると、Javaの慢性的なメモリ浪費とキャッシュミス問題を構造的に減らす。「コードはクラスのように、動作はintのように。」12年来の約束がついてコードで書ける現実になった。
