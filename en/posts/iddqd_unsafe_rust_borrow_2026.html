iddqd - The Hardest Kind of Unsafe Rust 2026 - Borrowing Keys From Values

The borrow-from-value pattern, self-referential structs, and in-memory indexing for control planes

Jun 4, 2026 Tech & IT

Introduction: Why a Map That Borrows Keys From Values Is Hard

Anyone who has spent real time with Rust has fought the borrow checker at least once. Most fights resolve with a small refactor. But some problems cannot be expressed in pure safe Rust no matter how you twist the code. A tiny map library called iddqd tackles exactly that class of problem. iddqd solves a seemingly mundane requirement: "index values in memory by borrowing a field inside each value as the key." Yet behind that mundanity sit Rust's thorniest unsafe topics all at once - self-referential structures, moves and dangling pointers, Pin, and safe encapsulation.

This article takes the early-June 2026 news.hada.io topic "iddqd: the hardest kind of unsafe Rust" as a starting point, but instead of translating the source, it dissects the problem from my own perspective. As an aside, the name iddqd appears to be lifted from the classic game DOOM's invincibility cheat code - a wink that says "an index invincible to bugs." We will look at whether it really is invincible, and at what cost that invincibility is bought.

The twelve H2 sections ahead are: (1) defining the borrow-from-value problem, (2) how it differs from a regular HashMap, (3) why self-referential structures are dangerous, (4) the mechanics of move and dangling, (5) the role and limits of Pin, (6) iddqd's design idea, (7) multi-key indexing and control planes, (8) principles of unsafe encapsulation, (9) verification with Miri, fuzzing, and RustSec, (10) traps when rolling your own, (11) implications for engineering teams, and (12) conclusions and takeaways. I include code where it helps, but stay at the level of "why it is hard and how it is handled" rather than diving into compiler internals.

1. Borrow-From-Value - Defining the Problem Precisely

Let us define the problem sharply. Suppose we hold a list of objects in memory and want to look them up fast. The usual tool is a key-value map. But in many real situations the key already lives inside the value. A user struct, for instance, has an id field, and we want to find the user by that id.

struct User {
    id: u64,        // this field is the key
    name: String,
    addr: String,
}

With a plain HashMap<u64, User>, the key id is stored once in the map's key slot and again inside User.id - the same value in two places. That looks trivial but two things grate. First, duplication. Second, and more fundamentally, when key and value are stored separately there is room for them to drift apart. If someone changes the value's id, it no longer matches the map's key.

Borrow-from-value is the idea of eliminating that duplication. Instead of storing a separate copy of the key, borrow the field inside the value directly as the key and build the index from it. Conceptually the map owns the User and simultaneously builds its hash table from references pointing at User.id. That "owning while referencing its own interior" is the seed of the hardest structure to express in Rust.

2. How It Differs From a Regular HashMap

The standard library's HashMap treats keys and values as separate owned data. When you insert a key you usually clone it or move ownership in. That model is simple and safe, but it fits poorly with the "key inside the value" situation above.

AspectRegular HashMapBorrow-from-value map (iddqd style)
Key storageCloned/owned separatelyBorrowed from inside the value
DuplicationDuplicated if key is also in valueNone (single ownership)
ConsistencyKey and value can driftKey is the value, cannot drift
Multi-keySeparate map per indexSeveral key indexes on one value
DifficultySimple in safe RustNeeds internal unsafe

The crucial differences are the last two rows. A borrow-from-value map can attach several key indexes to the same value at once (look up by id or by name), and in exchange it accepts unsafe internally. The value iddqd provides is that it takes responsibility for that unsafe and encapsulates it, so the user never writes any.

3. Why Self-Referential Structures Are Dangerous

Let us go one level deeper into why unsafe is unavoidable. A map that owns a User while building hash buckets from pointers into that User.id means a reference that points at itself appears inside the data structure. That is a self-referential struct.

// Conceptual shape (does not compile as-is)
struct Index {
    storage: Vec<User>,        // owns the values
    by_id: HashMap<&u64, usize>, // borrows the id inside storage
}

This does not compile because the borrow checker has no way to express the lifetime of by_id's references. by_id is valid only while storage lives, but when both sit in the same struct there is no way to write "this reference lives as long as a sibling field." Rust's lifetime notation is designed for references that point at data outside the struct, so a cycle pointing at one's own interior cannot be proved statically.

Safe Rust rejecting self-reference is not a defect but honesty. The compiler is simply saying, "I cannot prove this reference is safe."

So there are two options. Use an index (usize) instead of a reference as the key (safe, but with a layer of indirection), or express the self-reference directly with raw pointers and unsafe while taking personal responsibility for its safety. Libraries like iddqd choose the latter for performance and ergonomics, and cage the danger inside a narrow unsafe core.

4. Move and Dangling - The Most Subtle Trap

The truly frightening part of self-reference is at runtime, not compile time. The key word is move. In Rust values are movable by default, and a move is usually a byte copy in memory. When a value is relocated to a new address, the raw pointer that pointed into it is left aiming at the old address. At that instant the pointer is dangling, and dereferencing it is undefined behavior (UB).

// Why it is dangerous - pseudocode
let mut v = vec![user];          // user lives in heap buffer A
let p: *const u64 = &v[0].id;    // points into A
v.push(other);                   // capacity exceeded -> reallocate to buffer B (move!)
// now v[0] is in B, but p still points at A -> dangling
unsafe { let _ = *p; }           // UB: dereferencing freed memory

As this shows, a single Vec reallocation invalidates every internal pointer at once. This is the most common and hardest-to-catch bug when building self-referential structures. It compiles fine, happens to work on small inputs, and then corrupts memory the moment a reallocation triggers at a particular size.

Caution - these bugs may survive in debug builds and explode in release, or vice versa. "It works on my machine" becomes the most dangerous sentence in this territory.

5. The Role and Limits of Pin

If movement is the problem, one axis of the solution is clear: pin the value so it cannot move. For this the standard library provides the Pin type. Pin<P> promises at the type level that the pointee will no longer be relocated in memory. Once a self-referential structure settles into the right place, Pin keeps that place so the internal pointers stay valid.

What I want to stress, though, is that Pin is not a universal safety device. All Pin guarantees is the constraint that "safe code cannot move the target." The responsibility for setting up and maintaining the self-referential pointers correctly still rests with whoever writes the unsafe. It is a finicky set of rules involving non-Unpin types and using unsafe gates like get_unchecked_mut only under the exact invariants.

use std::pin::Pin;
use std::marker::PhantomPinned;

struct SelfRef {
    data: String,
    // a pointer into data (conceptual)
    slice: *const u8,
    _pin: PhantomPinned, // marker that makes the type non-Unpin, blocking moves
}

Hand-written Pin code is notoriously hard. So many libraries, rather than exposing Pin directly, hide the danger of self-reference inside and show the user only an ordinary map API. iddqd's value lies precisely in this hiding. The user calls only insert and get, while the library shoulders the hell of Pin and raw pointers.

6. iddqd's Design Idea

So how does iddqd solve this? Based on public information and the general principles of borrow-from-value maps, here is the core idea as I understand it. (Implementation details vary by version, so treat this as principle-level.)

6-1) Own each value exactly once

The map stores each value in a single, stable place. Once a value settles, its address must not move, so the storage strategy is designed to keep addresses stable (for example, an allocation scheme that guarantees stable addresses). This address stability is the foundation that keeps self-referential pointers valid.

6-2) Build indexes by borrowing keys from values

The user tells the map, via a trait, how to extract the key from a value. On insertion the map borrows the key by that rule, hashes it, and registers it in the internal index. Because the key is never copied or owned separately, duplication disappears and key and value can never drift apart.

6-3) Cage unsafe in a narrow core

The danger of raw pointers and self-reference lives only in a small core, with a 100% safe public API on top. Not a single unsafe appears in user code.

// Conceptual usage (API varies by version)
let mut map = IdHashMap::new();
map.insert(User { id: 1, name: "kim".into(), addr: "10.0.0.1".into() });
map.insert(User { id: 2, name: "lee".into(), addr: "10.0.0.2".into() });

// Look up by borrowing the id inside the value - an ordinary map to the user
if let Some(u) = map.get(&1) {
    println!("{} @ {}", u.name, u.addr);
}
Key point - the virtue of a good unsafe library is not "removing the danger" but "caging the danger in a narrow spot and guaranteeing safety outside that boundary." That boundary design is exactly what iddqd aims at.

7. Multi-Key Indexing and Control Planes

The real strength of borrow-from-value shows in multi-key indexing. When you want to look up the same value by several keys, you normally maintain a separate map per index by hand. The problem is that every insert, delete, and update must touch all of those maps, and missing one breaks the index.

// Maintaining multiple indexes by hand is sync hell
by_id.insert(u.id, u_ref);
by_name.insert(u.name.clone(), u_ref);
by_addr.insert(u.addr.clone(), u_ref);
// miss one of the three on delete -> ghost entries, leaks, wrong lookups

A borrow-from-value map stores the value once and attaches several key indexes on top, so inserts and deletes propagate consistently to all indexes automatically. The stage where this shines is the control plane. A control plane holds metadata such as cluster nodes, services, and endpoints in memory and must find the same object instantly by ID, by name, and by network address.

  • Service discovery: look up the same object by both service name and instance ID
  • Node registry: use node UUID, hostname, and IP all as keys
  • Scheduler state: cross-reference job ID and assigned node

Such systems query extremely often, and an index mismatch quickly becomes an outage. So the iddqd-style guarantee of "store once, many keys, automatic consistency" is not mere convenience but a safeguard for correctness. 8. Unsafe Encapsulation - Good Unsafe vs Bad Unsafe

There is no need to overreact to the word unsafe. Rust's own standard library carries vast unsafe internally; even Vec and String are safe APIs built on raw pointers. What matters is not the presence of unsafe but the quality of design.

My conditions for "good unsafe" are these:

  • Narrow surface: unsafe blocks isolated in a few core spots
  • Documented invariants: the safety conditions each unsafe relies on are written clearly in comments and docs
  • Safe boundary: the public API must not cause UB on any input (soundness)
  • Verification trail: those invariants have actually been hammered with Miri, fuzzing, and tests

Conversely, "bad unsafe" has a wide surface, invariants that exist only in someone's head, and a public API that leaks into UB under certain usage. When I evaluate a library like iddqd, the first thing I look at is not the feature list but the unsafe surface and the verification trail. 9. Verification Tools - Miri, Fuzzing, RustSec

Because the compiler does not guarantee safety for unsafe code, the author must prove safety with tools - all the more so for a library that handles self-reference and raw pointers. Here are the three tools I lean on as grounds for trust.

9-1) Miri - the undefined-behavior detector

Miri interprets Rust at the MIR level and catches UB such as dangling references, alignment violations, and use-after-free. A single line, cargo +nightly miri test, runs your tests under Miri. Pointer-rule violations in self-referential data are exactly the class Miri catches best.

# Run tests under Miri (nightly required)
rustup +nightly component add miri
cargo +nightly miri test

9-2) Fuzzing and property testing

cargo-fuzz generates large volumes of random input to pound edge cases, while proptest and quickcheck automatically check invariants like "the index stays consistent under any order of inserts and deletes." For self-referential maps you must especially target bulk-insert scenarios that trigger reallocation.

9-3) RustSec and cargo-audit

cargo audit checks dependencies against the RustSec advisory database for known vulnerabilities. When adopting a library that carries unsafe, confirming whether past soundness issues were reported and how they were patched is basic hygiene.

10. Traps When Rolling Your Own

You might be tempted to think, "this seems minor, can I just write it myself?" In my experience the classic traps when implementing a self-referential map yourself are these.

  1. Overlooking Vec reallocation: exactly as in section 4. Push enough elements past capacity and the buffer moves wholesale, invalidating every internal pointer. You need a container with stable addresses, not a Vec.
  2. Wrong drop order: in a self-referential struct, a wrong field-drop order can leave a pointer briefly aiming at already-freed memory. Subtle UB hides in the Drop impl.
  3. Mutable aliasing violations: if a mutable reference coexists with another reference to the same data, you violate Rust's aliasing rules (notably the stacked/tree borrows model), and optimizations can wreck the code.
  4. Forgetting to update indexes on mutation: if a key field changes, the index must update too; if the safe API does not prevent it, it silently breaks. That is why good designs treat key fields as immutable.

This list alone shows that using a vetted library is almost always the sensible choice. My recommendation: consider your own implementation only when it is truly a hot path and measurement confirms the bottleneck - and even then, always attach Miri and fuzzing.

11. Practical Implications for Teams

The topic is niche, but there are a few clear implications for engineering teams.

11-1) Rust infrastructure adoption is rising

More teams are writing network proxies, storage engines, and Kubernetes-adjacent control planes in Rust. The more such systems you have, the more directly the correctness and performance of in-memory indexes translate into stability - and the easier it is to feel the value of a borrow-from-value map.

11-2) The skill of reviewing unsafe becomes an asset

As more teams adopt Rust, the ability to read and evaluate unsafe grows scarce and valuable. A senior who can size up a library's unsafe surface, inspect Miri and fuzzing trails, and reason about soundness boundaries holds a direct weapon in hiring and code review.

11-3) Adoption criteria are verification, not features

My recommendation when choosing a library that carries unsafe is to make verification maturity, not stars or feature tables, the top criterion. If Miri runs in CI, fuzz targets exist, the RustSec history is clean, and every unsafe carries a safety comment, the library is trustworthy. 12. Conclusion + Three Takeaways

iddqd in one sentence: "a small map that borrows keys from values to build an in-memory index, encapsulating head-on the hardest unsafe territory in Rust under a deceptively ordinary surface." It cages the hard problems - self-reference, move, Pin, aliasing - in a narrow core and hands the user a plain map API. I close with three takeaways from this topic.

12-1) Takeaway 1: an "ordinary requirement" can be the doorway to unsafe

"I want to look up by the id inside the value" is an utterly ordinary requirement that, dug deep enough, leads to Rust's hardest self-reference problem. The habit of asking early, "does this end up referencing itself?" prevents large accidents.

12-2) Takeaway 2: unsafe is not removed but caged

A good library does not drive unsafe to zero. It isolates the danger in a narrow core and guarantees safety outside that boundary. As users, what we should look at is not the existence of unsafe but its surface and verification.

12-3) Takeaway 3: if you touch self-reference, Miri is mandatory, not optional

The moment you touch raw pointers and self-reference, ordinary tests can miss dangling and aliasing violations. Do not say "it works" until you have actually pounded the invariants with Miri, fuzzing, and property tests. For me, iddqd's real lesson is not a flashy trick but an attitude: the harder the unsafe, the more humbly it must be verified.
