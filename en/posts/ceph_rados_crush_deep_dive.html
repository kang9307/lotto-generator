Ceph Deep Dive: Mastering RADOS Concepts and CRUSH Rules

2025-06-02 Dev & Infra

Ceph is a modern distributed storage system that has drawn broad attention from enterprises and organizations alike, thanks to its outstanding scalability and reliability. At the heart of Ceph lies RADOS, a powerful object store, and the CRUSH algorithm that determines where data is placed. In this article, we take a close look at RADOS - the core of Ceph - along with CRUSH Rules.

This document provides an in-depth analysis of Ceph's core components: RADOS (Reliable Autonomic Distributed Object Store) and the CRUSH (Controlled Replication Under Scalable Hashing) algorithm. It covers their fundamental concepts, key features, and how they work together to deliver a scalable and reliable distributed storage solution.

1. What Is RADOS (Reliable Autonomic Distributed Object Store)?

RADOS is the foundational component of the Ceph storage cluster. As its name suggests, it is a Reliable, Autonomic, and Distributed Object Store.

Key Features and Components:

  • Object-based storage: RADOS stores all data as objects. Unlike files in a filesystem or blocks on a block device, an object is a flexible unit that bundles data together with its metadata.
  • Distributed and scalable: Data is spread across multiple OSDs (Object Storage Daemons) within the cluster. An OSD is a daemon that manages the actual physical storage devices (HDDs, SSDs, etc.). Adding new OSDs lets capacity and performance scale out nearly linearly.
  • High availability and data durability: Data is stored redundantly across multiple OSDs via replication or erasure coding, preventing data loss and keeping services running even when failures occur.
  • Autonomic management: RADOS continuously monitors OSD status and automatically recovers and rebalances data when something goes wrong, dramatically reducing operational overhead.
  • Core components:
    • OSD (Object Storage Daemon): Stores the actual data and handles replication, recovery, and rebalancing.
    • MON (Monitor): Maintains the master copy of the cluster map, oversees overall cluster state, and brokers consensus among OSDs. For high availability, it is typically deployed in odd numbers of three or more.
    • MGR (Manager): Tracks cluster state information (usage, performance, system load, etc.) and provides management interfaces such as the Ceph Dashboard.
    • MDS (Metadata Server): Stores and manages filesystem metadata when CephFS (Ceph File System) is used.

RADOS Access Interfaces:

Ceph layers a variety of interfaces on top of RADOS, giving you several ways to reach storage.

  • librados: A library that lets programs written in C, C++, Java, Python, PHP, and other languages talk directly to the RADOS cluster. It forms the foundation for RBD, RGW, and CephFS.
  • RADOS Gateway (RGW): An object storage gateway that exposes RESTful APIs compatible with Amazon S3 and OpenStack Swift.
  • RBD (RADOS Block Device): A block storage service offering features such as snapshots and thin provisioning. It is commonly used for virtual machine disk images and similar workloads.
  • CephFS (Ceph File System): A POSIX-compatible distributed file system.

2. The CRUSH (Controlled Replication Under Scalable Hashing) Algorithm

CRUSH is the core algorithm Ceph uses to decide where data lives. Rather than relying on a centralized metadata server, CRUSH lets clients compute on their own which OSDs will store a given piece of data. This design is a major contributor to Ceph's scalability and performance.

Key Concepts:

  • CRUSH Map: A map that defines the cluster's physical topology (racks, hosts, OSDs, etc.) along with data placement policy. The CRUSH algorithm uses this map to decide where objects go.
  • Bucket: A logical unit for grouping OSDs within the CRUSH Map. You can define various bucket types such as host, rack, row, and datacenter to model physical failure domains or performance domains.
  • CRUSH Rule: A rule that defines how data for a given pool will be stored. For example, you might set a rule such as "store 3 replicas of this data on OSDs in different racks."
  • Placement Group (PG): A unit used to group objects within OSDs. Objects are first mapped to PGs, and PGs are then mapped to OSDs according to the CRUSH Rule. PGs improve data management efficiency and reduce the amount of data that must move when an OSD fails.

How the CRUSH Algorithm Works:

  1. When a client requests an operation on a specific object, the PG that the object belongs to is computed from the object ID and the pool ID.
  2. Using the computed PG ID together with the CRUSH Rule from the CRUSH Map, the algorithm determines the list of OSDs that will hold that PG. In this process, CRUSH considers failure domains, OSD weights (capacity, etc.), and more, striving to distribute data evenly.
  3. The client then contacts the Primary OSD in the computed list directly to perform the data operation.

Why CRUSH Rules Matter:

CRUSH Rules directly affect data durability, availability, and performance. Administrators must design CRUSH Rules carefully, matching them to the physical environment and the requirements of the cluster.

  • Failure Domain: With CRUSH Rules, you can force replicas to be stored in different failure domains (for example, different servers or different racks). This keeps services running without data loss even when an entire server or rack fails.
  • Performance Domain: When mixing SSDs and HDDs, you can use CRUSH Rules to ensure that specific types of data (for instance, metadata that demands high performance) are stored only on SSD-backed OSDs.
  • Weight: By assigning weights based on OSD capacity or performance, you can steer data toward a balanced distribution.

3. The Relationship Between RADOS and CRUSH Rules

RADOS is the system that stores and manages data as objects, while CRUSH is the algorithm that decides which OSDs in the cluster will hold those objects.

  • When a client writes or reads data, the CRUSH algorithm runs to determine the target OSDs.
  • RADOS then communicates with the OSDs chosen by CRUSH to carry out the actual I/O.
  • When an OSD fails, the MONs update the cluster map and CRUSH computes a new data placement plan.
  • RADOS automatically recovers and rebalances data according to that new plan.

Through this tight cooperation, RADOS and CRUSH deliver Ceph's core capabilities: data storage, management, distribution, and high availability.

Conclusion

Ceph's RADOS and CRUSH algorithm are essential technologies for effectively managing the complexity of distributed storage while delivering outstanding scalability and reliability. RADOS provides an intelligent object storage backend, and CRUSH offers flexible, powerful control over data placement. A deep understanding of these components is essential for successfully designing, deploying, and operating a Ceph cluster.
