auth.md — AIエージェントがユーザーに代わってサインアップするオープンプロトコル

ドメインルートのMarkdownファイル一つで会員登録・認証を自動化 — セキュリティのジレンマ、同意の空白、エージェントウェブ標準競争を分析する

2026-06-27 IT・技術

序論：サインアップフォームの終焉が始まった

2026年6月時点で、ウェブ最古の慣行の一つが静かに揺らいでいる。会員登録フォームだ。名前、メールアドレス、パスワード、場合によっては住所やカード番号まで直接入力するあの儀式。AIエージェントがユーザーに代わってウェブを操作する時代において、この手続きはボトルネックであり障壁だ。エージェントはフォームをスクロールしたりCAPTCHAを解釈するために最適化されていない。

auth.mdはこの問題を正面から攻略する。WorkOSが2026年5月にMITライセンスで公開したこのオープンプロトコルはシンプルだ。サービスがドメインルート（例：https://yourapp.com/auth.md）にMarkdownファイルを置けば、AIエージェントはそのファイルを読んでユーザーをどの方式で登録するか理解し、認証フローを自律的に実行する。フォームも、ブラウザクリックも、OAuthの同意画面もなしに。

この記事はauth.mdの仕様を単純にまとめることはしない。このプロトコルが何を変えるのか、どこで破綻するのか、そしてエージェントウェブ（agentic web）という大きな標準競争の中でどのような位置を占めるのかを自分なりに分析する。robots.txtがクローラーに、llms.txtが言語モデルに道を示したなら、auth.mdはエージェントに扉の鍵を渡す。

1. auth.mdとは何か — ファイル構造と動作原理

まず確認された事実の範囲のみを扱う。auth.mdの核心はエージェントが読めるサービスメタデータだ。サービスはドメインルートにMarkdown形式のファイルを公開する。このファイルは三つのことを宣言する。

  • このサービスが対応する認証フロー（Agent Verified / User Claimed）
  • エージェントが要求できる権限スコープ
  • エージェントが受け取る認証情報の種類（APIキー、短命トークンなど）

重要なのは、このファイルが人間と言語モデルの両方が読みやすいMarkdownで書かれていることだ。新しいバイナリプロトコルや独自APIを発明しない。既存のOAuth標準の上にエージェント向け発見レイヤーを重ねる構造だ。

1.1 二つの認証フロー

auth.mdは二つのコアフローを定義する。この選択がプロトコルのセキュリティ哲学を決定する。

Agent Verifiedフローは、エージェントのIDプロバイダ（OpenAI・Anthropic・Cursorなど信頼できるプラットフォーム）がユーザーの身元を保証する方式だ。エージェントは署名済みのID-JAG（Identity Attestation for Agents）トークンを取得し、サービスの/agent/authエンドポイントに送信する。サービスはこのトークンの署名を検証し、有効であれば同期的に認証情報を返す。人間の介入は一切ない。速度面では最適だが、IDプロバイダの信頼性に全面的に依存する。

User Claimedフローには人間確認ステップがある。エージェントがワンタイムコードをユーザーに提示し、ユーザーが直接サービスにログインしてそのコードでエージェントのリクエストを承認する。遅いが、人間が明示的に同意したという記録が残る。金融取引・センシティブなデータアクセス・規制産業など責任の所在が重要な領域に適している。

サービスは両フローの片方または両方をサポートできる。どのフローを受け付けるかはサービス運営者が決定する。この設計が合理的な理由は、「エージェント自動化」と「人間の同意」という二つの価値を一つのフレームワーク内で同時に収容しているからだ。

1.2 認証情報の設計

auth.mdが発行する認証情報は短命・取り消し可能・スコープ制限のトークンだ。これは偶然ではない。エージェントが無制限の権限を持つトークンを保有していれば、悪用時の被害は致命的だ。サービス運営者はどのスコープを許可し、どの認証情報を発行するかを完全にコントロールする。プロトコルはこのコントロール権をサービス側に置く。

2. エージェントウェブ標準競争 — robots.txtからauth.mdまで

auth.mdを正しく理解するには、より大きな絵が必要だ。2024〜2026年の間、ウェブはエージェントが読んで行動するウェブとして急速に再編された。この転換の過程で、ファイルベースのプロトコルが競争的に登場した。

プロトコル場所目的主体
robots.txtドメインルートクローラーアクセス制御W3C非公式標準（1994〜）
llms.txtドメインルートAIに読むべきコンテンツを案内Anthropic・コミュニティ主導
AGENTS.mdリポジトリルートコーディングエージェントにリポジトリルールを案内Anthropic主導（オープン）
auth.mdドメインルートエージェントの会員登録・認証を自動化WorkOS主導（MIT）
MCPサーバーサイドエージェントとサービスの構造的相互作用Anthropic主導

このパターンから分かることがある。各プロトコルはエージェント・ウェブ相互作用の異なるレイヤーを扱う。robots.txtは「どこに行ってはいけないか」、llms.txtは「何を読むべきか」、AGENTS.mdは「このリポジトリでどう振る舞うか」、auth.mdは「どのように登録・認証するか」、MCPは「どのようにサービスと相互作用するか」だ。これらは競合ではなく、エージェントウェブの異なるインフラレイヤーを構成する。

2.1 llms.txtとの実質的な違い

llms.txtは言語モデルに「このサイトのどのページが最も有用か」を伝える。発見とルーティングの問題だ。auth.mdはそれよりはるかに重いステップを扱う。エージェントが実際にアカウントを作成し、認証情報を取得し、APIを呼び出すまでの全フローを定義する。読み取り権限（llms.txt）と書き込み・実行権限（auth.md + MCP）の違いと言える。

2.2 MCPとの関係

MCP（Model Context Protocol）はエージェントが外部ツール・データソースと構造的に相互作用するフレームワークだ。より汎用的で機能が豊富だ。auth.mdはMCPよりはるかに狭い問題に集中する。「エージェントがサービスに初めて登録する瞬間」にのみ介入する。この最初の関門を標準化することで、MCPのような上位レイヤーがよりクリーンに動作できる。auth.mdをMCPの前処理ステップとして見るのも妥当な視点だ。

3. 採用状況 — 実際に使われているのか

2026年6月時点で確認されている採用状況だ。WorkOSがプロトコルを公開してから約一ヶ月以内にCloudflare・Firecrawl・Resend・Monday.com・Zuplo・NanoGPT・AgentMailなどが実装を完了した。Ora.aiは「エージェント対応度スコアカード」にauth.mdの準拠確認を項目として追加した。

特にCloudflareの参加が注目される。Cloudflareは単にファイルを置くにとどまらず、Protected Resource Metadata標準と連携する形でauth.mdをインフラレベルでサポートした。これはauth.mdが特定ベンダーのツールにとどまらず、実質的なウェブインフラとして参入する可能性を示す。

しかしこの採用リストを冷静に見ると、大半がインフラ・開発者ツール企業だ。一般消費者サービスや金融・医療などの規制産業の参加は依然として極めて限定的だ。その理由は次節で扱うセキュリティ・同意の問題と直結している。

4. セキュリティのジレンマ — 自動化の祝福と呪い

auth.mdが解決する問題は明確だ。しかしその解決方式が新しい問題を生む。このプロトコルで最も重要な緊張がここにある。

4.1 エージェントが登録できるなら、悪意のあるエージェントも登録できる

auth.mdの設計者たちも認める最も鋭いリスクだ。エージェントが自動的にアカウントを作れるようになると、悪意ある行為者のエージェントは瞬時に何千ものアカウントを作成できる。CAPTCHAやフォームの摩擦がなくなることは、誠実なエージェントと悪意のあるエージェントに等しく適用される。

具体的なリスクは三つだ。第一に、スパムアカウントの大量生成。利用規約の検証、無料プランの濫用、評判操作に使用される可能性がある。第二に、認証情報の収集。特にAgent Verifiedフローで信頼プロバイダが汚染されたりエージェントが乗っ取られると、大規模なアカウントが一度に作成される可能性がある。第三に、予算超過ループ。エージェントがエラー復旧ロジックで繰り返し登録したり、有料サービスで課金を引き起こすループに陥る可能性がある。

4.2 サービスが構築すべき防御線

auth.mdの仕様自体はこの防御をサービス運営者の責任とする。実際の実装では以下が必須だ。レート制限は基本中の基本だ。エージェントIDプロバイダ別・IP別の登録頻度に上限を設けなければならない。信頼プロバイダ許可リストは、Agent VerifiedフローでどのIDプロバイダを信頼するかを明示的に管理する必要がある。最小スコープの原則は、エージェントに必要最小限の権限のみを付与し短命トークンを使用することだ。異常検知は、短時間での大量登録・類似パターンの繰り返し・異常なスコープリクエストをリアルタイムで検出する必要がある。

これらの防御コストはauth.mdのシンプルさと対照的だ。ファイルを一つ置くことは簡単だが、そのファイルが開く扉を安全に管理することははるかに複雑だ。この非対称性が規制産業の参加を躊躇させる核心的な理由だ。

5. 同意の問題 — ユーザーは何に同意しているのか

技術的なセキュリティ問題とは別に、より根本的な問いがある。ユーザーがエージェントに登録権限を委任するとき、ユーザーは正確に何に同意しているのか？

5.1 同意の曖昧さ

ユーザーがAIエージェントに「このサービスに登録して」と言う。エージェントがAgent Verifiedフローでアカウントを作り、メールマーケティング受信・データ処理規約・第三者共有への同意にチェックを入れたなら、ユーザーは実際にその内容を読んで同意したと言えるのか？法的に有効な同意なのか？この問いにはまだどの国も明確に答えていない。

User Claimedフローはこの問題を部分的に緩和する。ユーザーが直接ログインしてエージェントのリクエストを承認するため、最低限の確認ステップがある。しかしAgent Verifiedフローにはこのステップすらない。利用規約が何千ワードであっても、エージェントはそれをユーザーに十分に説明せずにクリックできる。

5.2 GDPRと個人情報保護法の文脈

EU GDPRは個人データ処理への同意が「自由で、具体的で、情報に基づき、明確でなければならない」と要求する。エージェントが代わりに締結した利用規約がこの基準を満たすかは現在法的空白だ。この法的不確実性がauth.mdの拡散速度を実質的に制限する最大の非技術的要因だ。

6. エージェントウェブのより大きな構造 — 何が標準になるか

auth.mdは単独プロジェクトではない。エージェントがウェブの主要な利用者になる世界を前提とした一連のプロトコルの一つだ。この前提が正しければ、エージェントウェブ標準をめぐる競争は単純な技術論争ではなく、未来のインターネットの権力構造を決める争いだ。

6.1 標準提案者の利害関係

現在エージェントウェブ標準を主導する組織はすべて強い利害関係を持っている。AnthropicはMCPとAGENTS.mdを主導し、Claudeエージェントエコシステムを中心に設計する。WorkOSはauth.mdで認証インフラ市場を先取りしようとする。Cloudflareはインフラレベルでエージェントトラフィックを処理しゲートキーパーの位置を強化する。彼らが提案する「オープンプロトコル」が本当にオープンなのか、それとも特定ベンダーのエコシステムをロックインする手段なのかを批判的に見る必要がある。

auth.mdはMITライセンスで公開され、別途レジストリや承認が不要という点で真のオープンプロトコルに近い。しかしID-JAG信頼プロバイダリストを誰が管理するかによって実質的な権力が集中する可能性がある。OpenAIやAnthropicが信頼プロバイダとして承認されなければAgent Verifiedフローが動作しないなら、そのリストを管理する主体がエージェントウェブの門番となる。

6.2 標準になる条件

インターネットの歴史を見ると、最もシンプルでデプロイコストが低いプロトコルが勝つ傾向がある。robots.txtが30年生き残った理由は、ファイル一つ、数行のテキストで十分だったからだ。auth.mdはこの方向性を忠実に踏まえている。しかしセキュリティ防御の構築コストが大きく、法的不確実性が残り、消費者サービスの参加がまだ限定的だ。この三つの摩擦が解消されなければ、真の標準にはなれない。

7. 開発者・サービス運営者のための実践的判断基準

分析を超えて、実際に何をすべきか。直接的な指針を示す。

7.1 今すぐ実装すべきサービス

エージェントトラフィックが既に有意に入ってきている開発者ツール・APIサービス・インフラプラットフォームは今auth.mdを検討する価値がある。Cloudflare・ResendのようなアーリーアダプターがインフラとDev Toolの企業であることは偶然ではない。この領域のユーザー（開発者）はエージェントと共に作業することに既に慣れており、エージェントが新しいAPIキーを生成するユースケースが実際に発生している。

7.2 慎重にすべきサービス

規制産業（金融・医療・教育）、消費者向けサービス、EU市場サービスは法的ガイドラインが明確になるまで待つのが合理的だ。エージェント登録自動化の利便性よりも、同意紛争・アカウント濫用の責任・個人情報処理の法的リスクが大きくなる可能性がある。

7.3 エージェント開発者の立場から

エージェントを構築する開発者なら、auth.mdが開く可能性よりもユーザーへの責任を先に考えるべきだ。エージェントがユーザーに代わってサービスに加入し、権限を取得し、コストを発生させることについて、ユーザーに明確に通知し同意を得るメカニズムがエージェント側にも必要だ。auth.mdがサービス側の扉を開く標準だとすれば、エージェント側の同意管理標準はまだ空白だ。この空白が埋まるまで、エージェント開発者の倫理的な設計選択がユーザー保護の第一の防御線だ。

8. 結論 — シンプルなファイルが開く複雑な世界

auth.mdは技術的にシンプルだ。Markdownファイル一つ、OAuth標準の上の薄いレイヤー。しかしそれが開く可能性とリスクはシンプルではない。

エージェントウェブの方向性は明確だ。人間がすべてのインターフェースを直接操作する時代から、エージェントが人間に代わってサービスと相互作用する時代へ。auth.mdはその転換で「認証」という最も根本的な関門を標準化しようとする試みだ。

2026年6月時点で、このプロトコルは有望だがまだ初期段階だ。インフラ・開発者ツール分野での採用は実質的であり、WorkOSとCloudflareが主導する実装速度は印象的だ。しかしセキュリティ防御構築の実質コスト、法的同意の不確実性、規制産業の不在が真の汎用標準への道を塞いでいる。

最終判断はこうだ。auth.mdはエージェントウェブインフラの実質的な構成要素となるだろう。しかしrobots.txtのようにどこにでも当然存在するレベルになるためには、法的明確性と消費者信頼を構築する時間がさらに必要だ。
