GLM 5.2 公開 - 100万トークンの長文脈と自律エージェントを狙うオープンソースモデル

Zhipu がコーディング・自律エージェントに焦点を置いた 1M 文脈オープンウェイトモデルを公開した - 何が新しく、開発者に何を意味するか

2026-06-15 IT・技術

序論: 100万トークンを携えてきたオープンソースモデル

2026年6月13日、中国の AI 企業 Zhipu(Z.ai)がフラッグシップモデル GLM 5.2 を公開した。見出しは二つだ。一つは 100万(1M)トークンという非常に長い文脈ウィンドウであり、もう一つは複雑な作業を最後まで自律的に処理する エージェントコーディング志向だ。さらに重みを MIT ライセンスで公開する オープンソース(オープンウェイト)モデルである。

この1年、私たちは中国のラボが価格で、次いで開放性で西側フラッグシップを圧迫する流れを見てきた。GLM 5.2 はその上に文脈規模と自律エージェントという軸を重ねる。単に安い・公開されているにとどまらず、リポジトリ全体を一度に見て長い作業を一つの流れで終えられると主張する。本稿はプレスリリースを写すのではなく、実際に何が発表され、それが開発者に何を意味するかを正直に解きほぐす。

まず断りを明確にする。ここに出る仕様と日程は Zhipu の公開発表と公開報道を基準とする。そして最大の注記を先に打っておく。Zhipu は公開時点で 標準ベンチマーク数値を出していない。したがって「強力なコーディング」「強い長期自律」のような表現はまだ検証されていないベンダー主張だ。主張を伝える部分と私の解釈を出す部分を区別する。本稿は MiniMax-M3 価格破壊の分析と Kimi K2.7-Code のトークン効率分析で扱った中国モデルの流れに連なるが、角度が違う。そちらが価格と効率なら、今回は 文脈規模と自律性だ。

1. GLM 5.2 とは - 1M 文脈のコーディング特化オープンウェイトモデル

Zhipu は清華大学系から出発した中国の AI 企業で、GLM 系列モデルと Z.ai ブランドで知られる。GLM 5.2 はその GLM-5 ラインの 2026年6月最新作であり、コーディングと自律エージェント作業に重きを置く。

1.1 主要仕様

公開資料によると GLM 5.2 の仕様は次のとおりだ。文脈ウィンドウは 1,000,000 トークン(モデル ID に [1m] 表記)で、最大出力は 131,072 トークンだ。思考(thinking)努力プリセットは High と Max の二段階で提供され、コーディングには Max が推奨される。1M 入力と13万出力という組み合わせは、リポジトリ規模のエージェントリファクタリングや「まず計画し次に実行する」長いトレースを一つの文脈に収めるのに十分な幅だ。ただし総パラメータ数は公開時点で開示されていない。

1.2 チャットではなく自律作業を狙う

GLM 5.2 のポジショニングは一般会話ではなく コーディングファーストと 自律エージェントだ。つまり一度の問答ではなく、複数のステップにわたって計画を立て、ファイルを編集し、ツールを実行し、結果を見てデバッグするエージェントループを狙う。公開初日から Claude Code、Cline、OpenCode、Roo Code、Goose、Crush、OpenClaw、Kilo Code といった主要エージェントツールとの互換が発表された。これは単発のコードスニペット生成より、自律コーディングエージェントのバックエンドに直接差し込んで使うことを前提とした設計だ。

1.3 提供方式と日程

GLM 5.2 は公開時点で GLM Coding Plan の全等級(Lite/Pro/Max/Team)に追加費用なしで即座に提供された。報じられた等級構造は、Lite が月約 $18 で週約 400 回のプロンプト、Pro が週約 2,000 回、Max が週約 8,000 回、Team が席数ベースの組織課金だ。要は オープンウェイトと独立 API の時点差だ。公開発表によれば独立 API、Z.ai チャットボット、そして MIT ライセンスのオープンウェイトは公開当日ではなく翌週に順次公開予定だった。つまり公開日基準ではコーディングプラン加入者だけが即時利用でき、自前ホスティング用の重みは時差をおいて出る構造だった。

2. 100万トークン文脈の意味 - 長い文書とコードベース

このモデル発表で最も実用的な数値が 1M 文脈だ。なぜこれが単なる数字自慢ではなく本質的な差なのかを押さえよう。

2.1 文脈ウィンドウとは

文脈ウィンドウはモデルが一度の要求で同時に参照できる入力の量だ。トークンは単語より小さい単位で、100万トークンはおおよそ分厚い書籍数冊、あるいは中規模プロジェクトのソースコード全体に相当する量だ。文脈が小さいと長い文書やコードベースを細かく分割して入れねばならず、その過程でモデルが全体像を見られず断片的な答えを出しやすい。

2.2 長い文書とリポジトリを丸ごと

1M 文脈の直接的な効果は二つだ。第一に 長文書処理。数百ページの契約書、膨大なログ、長い議事録を分割せず一度に入れ、全体の文脈の上で要約・検索・分析できる。第二に コードベース全体処理。複数ファイルにまたがる依存関係をモデルが一目で見て、一つのファイルを直すとき他のファイルへの影響を併せて考慮できる。コーディングエージェントにとってこれは決定的だ。リポジトリ規模のリファクタリングが「ファイルを一つずつ見て文脈を失う」作業から「全体を見て一貫して直す」作業へ変わる。

2.3 自律作業で文脈が重要な理由

自律エージェントは一つの作業を複数ステップに分け長く進める。計画を立て、実行し、中間結果を読み直し、次のステップを決める。この長いトレース全体が文脈に積もる。文脈が狭いとエージェントは前に立てた計画やすでに直した内容を忘れ、同じことを繰り返したり矛盾した修正をしたりする。1M 文脈はこの「長期記憶」を広げ、長い自律作業が途中で道を失う危険を減らす。GLM 5.2 が 1M 文脈と自律エージェントを併せて掲げたのは偶然ではない。両者は一対だ。

3. 自律エージェント作業能力 - 何を主張するか

Zhipu が GLM 5.2 で強調したのは複雑な作業の 自律完了だ。正確に何が主張され、どう読むべきかを押さえる。

3.1 長期自律作業とは

ここで自律作業とは、人が各ステップで介入しなくてもモデルが計画→実行→点検→修正を自ら繰り返し目標に到達することを指す。コーディング文脈では「このバグを直せ」のような一行指示で、モデルが関連ファイルを探し、原因を推定し、修正し、テストを走らせて結果を確認する全過程をつなぐことだ。GLM 5.2 の最大出力13万トークンは、プルリクエスト規模の大きな diff と長い計画・実行トレースを一つの応答に収められる幅だ。

3.2 思考努力プリセット

GLM 5.2 は思考努力を High と Max の二段階で提供する。努力を上げるとモデルは答えを出す前により深く推論するが、その分トークンと遅延が増える。コーディングに Max が推奨されることは、複雑な自律コーディング課題ではより深い推論が結果品質に有利だという設計判断と読める。ただしこれは費用・速度とのトレードオフなので、実務では課題の難度に応じてプリセットを使い分ける運用が合理的だ。

3.3 責任を持って読む方法

ここに私の常時の警告がある。「複雑な作業の自律完了」は魅力的だが、Zhipu はそれを裏づける 標準ベンチマーク数値を公開時点で出していない。SWE-bench Verified も LiveCodeBench も HumanEval も無かった。自律性は最も検証が難しい能力だ。デモで一つの作業を見事に終えることと、自分の実際のコードベースの厄介なエッジケースを安定して処理することは全く別の問題だ。ベンダーの自律性主張は方向を示唆するが、自分の課題での信頼性は直接確認せねばならない。

4. 中国オープンウェイト AI の台頭 - DeepSeek・Qwen・Kimi・MiniMax の文脈

GLM 5.2 は孤立した出来事ではない。2025-2026 を規定した中国オープンウェイトの流れの最新の一拍だ。

4.1 流れの系譜

DeepSeek は西側級の品質を価格の一部で合わせられることを実証し、恒久値下げで打ち込んだ。Qwen はオープンウェイトを非常に積極的に推し、「どの API が安いか」を「そもそも API が要るのか」に変えた。Kimi はトークン効率で同じ仕事をより少ない計算で行う軸を加え、MiniMax は価格と性能を同時に主張して一段格上げした。この系譜に GLM 5.2 が加えるのは 文脈規模と自律性だ。報道によれば 2026 年に入り中国のラボはオープンウェイト上位の多くを占め、GLM・Qwen・Kimi・DeepSeek がそれぞれ異なる能力次元で先頭を争う構図になった。

4.2 オープンウェイトが変えた問い

オープンウェイトモデルが増えるにつれ、開発者の問いが変わった。かつては「どの API 提供者が最良か」だったが、今は「このワークロードを外部 API へ送るか、重みを入手して自分で動かすか」が先に来る。コーディングのようにコードベース全体がプロンプトとして出る機微な作業、しかも 1M 文脈で本当に全体を入れる場合は、この問いが特に重い。GLM 5.2 の(翌週公開予定の)MIT オープンウェイトはその選択肢を一層真剣にする。

4.3 西側との距離

報じられた流れによれば、中国最上位のオープンウェイトモデルは OpenAI・Anthropic・Google の最上位クローズドモデルに、なお一桁台後半の点差ほど遅れると評価される。ただしその差は大半の予測より速く縮まった。GLM 5.2 は絶対 1 位を争うより、十分に良い性能を 1M 文脈・自律エージェント・(予定された)オープンウェイトで束ねて側面を突く戦略と読むのが正確だ。

5. 競争構図 - Claude・GPT との対比

GLM 5.2 が入った市場はすでに混み合うコーディング・エージェントモデル市場だ。座標を整理しよう。

5.1 市場の地形

コーディング・エージェントの上段はなおクローズドのフラッグシップが占める。標準のコーディング・エージェントベンチマークの多くで西側最上位モデルが先頭を守る。しかしその優位は次第に縮まり、費用差と開放性の差は次第に開く。GLM 5.2 の戦略は正面勝負ではなく側面迂回だ。絶対 1 位を争うより、十分に良い性能を 長い文脈と公開された重み、エージェントツール互換で束ねて提示する。

公開された主張に基づき私が読んだ地形だ(2026、推定 - 精密値ではなく方向として受け取ってほしい)。GLM 5.2 は公開時点でベンチマークが無く「主張」段階であることを明確にする。

5.3 どこで誰が勝つか

私の解釈はこうだ。最高品質が絶対的に重要な高リスク・顧客露出のコーディング(本番マイグレーション、セキュリティ機微なコード)では、検証済みのクローズドフラッグシップがなお安全な選択だ。一方 長い文書・大規模コードベースを丸ごと扱う作業、そして費用とデータ統制が重要な自律コーディングでは、1M 文脈のオープンウェイトである GLM 5.2 が魅力的だ。正解は単一モデルではなくワークロード別の配置だ。特に文脈が狭く作業を分割せざるを得なかったワークロードなら、1M 文脈が局面を変えうる。

6. オープンソースモデルの長所 - ローカル・費用・カスタマイズ

GLM 5.2 が「オープンウェイト」であることがなぜ単なるライセンスの脚注ではないのかを解こう。三つの実質的な利点がある。

6.1 ローカル実行とプライバシー

重みを保有すればコードとプロンプトが外部 API へ出ない。自前のコードベースを、しかも 1M 文脈で丸ごと入れる作業ではこれが決定的だ。セキュリティ機微な企業、規制産業、あるいは単にコード流出を嫌うチームに、オープンウェイトは外部 API が与えられないデータ統制を与える。プロンプトがどこで処理されるかは、価格・性能とは独立した第一級の問いだ。

6.2 費用構造の転換

ホスティング API はトークン単価で課金される。オープンウェイトを自前運用すると、費用基盤が 保有ハードウェアに変わる。高ボリューム・常時稼働のワークロードなら、GPU を埋める限りトークンあたりの限界費用がホスティング単価を下回りうる。ただしこの転換は無料ではない。GPU 資本・電力・運用人員という固定費を負う。特に 1M 文脈は推論時のメモリ・計算負担が大きいので、長い文脈を実際に埋めて使う運用なら、ハードウェア要求は侮れない。損益分岐はボリュームと文脈使用量に左右される。

6.3 カスタマイズの自由

重みがあればドメインデータでファインチューニングしたり、ハードウェアに合わせて量子化したり、システムプロンプトとデコードパラメータを深く調整できる。クローズド API では不可能か制限された統制だ。特定のコードスタイル・内部ライブラリ・社内慣行にモデルを合わせたいチームに、この自由は大きな価値だ。MIT ライセンスなら商用活用と改変の幅も広い。

7. 開発者の活用 - どこで使うか

運用上重要な問いだ。GLM 5.2 をどこに差し込むか。私の答えはワークロードのトリアージだ。

7.1 よく合う場

長い文脈が本当に必要な作業が第一だ。リポジトリ規模のコード分析・リファクタリング、膨大な文書・ログ分析、複数ファイルにまたがる一貫した修正のような「全体を見るべき」作業で、1M 文脈は即座に意味がある。またデータを外部へ出しにくいセキュリティ機微なコードベースでは、(オープンウェイト公開後の)ローカル実行可能性が決定的だ。すでにコーディングエージェントツールを使っているなら、初日互換リストのツールでバックエンドだけ替えて試せる。

7.2 慎重であるべき場

顧客露出・高リスク・一発の正確性が重要なコーディング(本番ホットフィックス、セキュリティパッチ、マイグレーション)では、検証済みのフラッグシップを主力に保つほうが安全だ。ベンチマークが公開されていない新モデルの信頼性・エッジケース処理は不明だからだ。また 1M 文脈を実際に埋めて使うと費用と遅延が併せて大きくなる点、自前運用を選ぶなら長い文脈のメモリ・計算負担を過小評価してはならない点に留意すべきだ。

7.3 導入手順

勧めるパターンは明確だ。自分の実ワークロードからゴールデンセット(課題 50-200 個)を作り、GLM 5.2 を現行ツールと突き合わせて品質・トークン消費・遅延・費用を測る。特に長い文脈が実際に役立つか - 全体を入れたとき答えが良くなるか - を直接確認する。ベンチマークが無いので自分のデータが唯一の根拠だ。通れば低リスクのワークロードから段階移行し、高リスクはフラッグシップのフォールバックと併せたデュアルスタックにする。オープンウェイトが出たら自前ホスティングの損益分岐を別途計算する。

8. 限界と注意点

長所だけ見せるのは不誠実だ。明示的に押さえるべき限界がある。

8.1 公開時のベンチマーク不在

最大の注記は、Zhipu が公開時点で標準ベンチマークを一切出していない点だ。「強力なコーディング」「長い自律」のような表現は検証されていないベンダー主張だ。Claude Opus 4.8 や GPT-5.5 との直接比較は明示的に「不明」のまま残った。マーケティング文言を意思決定の根拠にせず、自分のゴールデンセットで検証せよ。

8.2 オープンウェイトの時点と運用負担

オープンウェイトが公開当日ではなく翌週公開予定だった点に留意すべきだ。つまり公開直後に自前ホスティングを計画したなら時差を考慮せねばならなかった。また自前運用は GPU 資本、推論最適化、稼働・保守人員を要し、1M 文脈はメモリ・計算面で負担が特に大きい。長い文脈を使わないなら、わざわざ 1M モデルである理由が減る逆説もある。

8.3 成熟度と規制の不明

ベンチマークが無い新モデルは、SLA 成熟度、ツール生態系の互換性、エッジケース安定性で検証が浅い。また中国ラボのモデルをめぐるデータ居住国・輸出規定は速く変わりうるので、ホスティングエンドポイント使用時に規制領域で制約が生じうる。重みを入手して自前インフラで動かせばデータ経由の問題は相当緩和されるが、調達・規定の面は別途点検すべきだ。

9. 結論 - 今日適用できる3つ

GLM 5.2 は本物の信号だが、正直な注記が付く。公開時点でベンチマークが無く、絶対性能の主張はまだ検証されていない。しかしこのモデルが示す方向 - 1M 文脈 + 自律エージェント + (予定された)MIT オープンウェイト - は、2026 年の AI 競争が単価から文脈規模・自律性・開放性へ移っていることを鮮明に示す。

今週、私が打つ具体的な手を三つ。

9.1 長い文脈が自分の作業に役立つか検証せよ

自分の実課題 50-200 個でゴールデンセットを作り、「全体を一度に入れる」場合と「分割して入れる」場合の答えの品質を比べよ。1M 文脈は長い文書・大規模コードベースでのみ本当の効果を出す。効果が確認できるワークロードを先に選り分けよ。

9.2 低リスクのワークロードから移し、フォールバックを置け

リポジトリ分析・リファクタリング・文書要約のように長い文脈の利点が大きく、リスクの低い作業を GLM 5.2 へ送り、高リスク・顧客露出のコードは検証済みのフラッグシップに保て。提供者非依存のゲートウェイで設計すれば、バックエンドの差し替えは書き直しではなく設定変更になる。ベンチマークが出たら比重を再調整せよ。

9.3 オープンウェイト公開を待って損益分岐を計算せよ

コード流出が負担か高ボリュームのワークロードなら、MIT オープンウェイトが出た後に自前ホスティングの損益分岐を計算してみよ。ただし 1M 文脈のメモリ・計算費用を自分のボリュームに当てはめねばならない。より広い文脈は MiniMax-M3 価格破壊の分析、Kimi K2.7-Code のトークン効率分析、DeepSeek V4-Pro 値下げの分析を参照されたい。
