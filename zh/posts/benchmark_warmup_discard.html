引言 - 第一个数字不是代码的速度

在重复测量中，第一次调用经常比之后的调用慢几倍到几千倍。把这个值放进平均值，平均值反映的就不是函数的速度，而是混入了只需支付一次的开销。这种开销不止一种。模块import、正则表达式编译缓存、用户代码的延迟初始化、JIT编译器的分阶段优化，在大小和持续时间上都不相同。因此预热舍弃几次不能凭感觉，要从同一函数逐次的耗时中确定。

已收集好的测量值如何合并，见百分位数聚合误差一文；用哪种时钟来测，见单调时钟与墙上时钟一文。这里只讨论测量值产生之前的一步，即从第几次调用起，耗时才可以当作测量值使用。

讨论的问题如下。

  • 首次调用的延迟来自import、正则缓存还是延迟初始化，能否通过分离变量来区分。
  • 反复调用同一函数时，逐次耗时以什么形状下降。
  • 舍弃次数能否由代码按移动中位数趋于稳定的位置来确定。
  • 包含预热的平均值与舍弃之后的平均值，各自偏离稳定值多少。
  • 在测量会波动的环境里，如何检查这个判定是否可信。

计时工具与官方文档的说法

Python的timeit文档写明，默认计时器始终是time.perf_counter()。同一文档说明，timeit()在计时期间会暂时关闭垃圾回收，好处是让独立的计时更具可比性，缺点是GC可能是被测函数性能的重要组成部分。对于重复测量的结果，文档写道，计算并报告平均值和标准差不太有用，较高的值通常不是Python速度的波动，而是其他进程干扰了计时，所以结果中的min()大概是唯一值得关注的数字。

Node一侧的时钟是perf_hooks中的performance.now()。MDN说明该方法返回以毫秒为单位的高精度时间戳，表示自timeOrigin以来经过的时间。该页面中关于分辨率的数字(隔离上下文为5微秒，其他情况为100微秒)是针对网页文档的浏览器上下文。下面的Node输出，是把一次调用夹在两次performance.now()之间得到的值。

  • Python：用time.perf_counter()夹住一次调用并换算成微秒；重复测量使用timeit.repeat()。
  • Node：用performance.now()夹住一次调用并换算成微秒；不使用内部优化选项。
  • 变量分离：在新进程中测量第一次与第二次调用，只改变一个条件，重复同样的测量。
  • 判定：对逐次耗时应用移动中位数，最后做平稳性检查。

CPython首次调用 - 逐个改变变量的实验

下面代码的前半部分会启动新的解释器进程，把同一个函数调用两次，以微秒输出第一次与第二次的耗时。父进程把五种条件各自在7个新进程中运行并取中位数。相邻的条件只有一处不同。

import sys, time, re, subprocess, statistics, platform, random
                    
                    def us(fn, *a):
                        t = time.perf_counter(); fn(*a); return (time.perf_counter() - t) * 1e6
                    
                    # ---------- child mode: one fresh interpreter, time call 1 and call 2 ----------
                    def child(case):
                        if case == "import_cold":
                            print("sqlite3 already loaded:", "sqlite3" in sys.modules)
                            def f():
                                import sqlite3
                                return sqlite3.sqlite_version
                        elif case == "import_warm":
                            import sqlite3
                            def f():
                                import sqlite3
                                return sqlite3.sqlite_version
                        elif case == "re_cold":
                            re.purge()
                            def f(): return re.search(r"(\d{4})-(\d{2})-(\d{2})", "date: 2026-10-06 end")
                        elif case == "re_precompiled":
                            c = re.compile(r"(\d{4})-(\d{2})-(\d{2})")
                            def f(): return c.search("date: 2026-10-06 end")
                        elif case == "lazy_table":
                            box = {}
                            def f():
                                if "t" not in box:
                                    box["t"] = {i: i * i for i in range(200000)}
                                return box["t"][777]
                        a = us(f); b = us(f)
                        print("%.1f %.1f" % (a, b))
                    
                    if len(sys.argv) > 1:
                        child(sys.argv[1]); sys.exit()
                    
                    # ---------- parent ----------
                    print("python", platform.python_version(), sys.platform)
                    print("A. fresh process, call 1 vs call 2 (us), median of 7 processes")
                    print("%-16s %12s %12s %8s" % ("case", "call 1", "call 2", "ratio"))
                    for case in ["import_cold", "import_warm", "re_cold", "re_precompiled", "lazy_table"]:
                        r = []
                        for _ in range(7):
                            o = subprocess.run([sys.executable, __file__, case], capture_output=True, text=True).stdout.split()[-2:]
                            r.append((float(o[0]), float(o[1])))
                        c1 = statistics.median(x[0] for x in r); c2 = statistics.median(x[1] for x in r)
                        print("%-16s %12.1f %12.1f %8.1f" % (case, c1, c2, c1 / c2))
  • import_cold：函数体内import sqlite3。进程启动时sqlite3是尚未加载的模块(见输出中的loaded行)。
  • import_warm：同一个函数，但在开始计时前先import sqlite3。与import_cold的区别只有这一点。
  • re_cold：用re.purge()清空正则缓存，再以字符串模式调用re.search。
  • re_precompiled：在计时前用re.compile构建模式，只调用search。与re_cold的区别只有编译是否落在计时区间内。
  • lazy_table：用户代码的延迟初始化，首次调用时构建含20万项的字典并保存，之后重复使用。

从输出中能读出三点。第一，import_cold与import_warm的函数体相同，只有是否预先加载模块不同。首次调用从13248.8降到1.8，所以在这台电脑上import_cold首次调用的延迟是函数内的import造成的。Python文档写道，import时先在sys.modules中查找模块名，若存在则该值满足此次import，过程即告完成。文档说明的是缓存的存在，速度差别由import_warm与re_precompiled的对照输出显示。

第二，re_cold与re_precompiled只有编译是否在计时区间内不同。数值从280.7降到15.7。re文档写道，传给re.compile()和模块级匹配函数的最近模式的编译结果会被缓存，re.purge()会清空该缓存。清空缓存后的首次调用独自支付了编译开销。第三，lazy_table的48073.7是首次调用中构建20万项字典的代码造成的，只复用该表的第二次调用在同一输出中为3.6。

仍有残留的差别。import_warm的1.8对1.0，以及re_precompiled的15.7对2.9，是几微秒到十几微秒量级的首次超出。这一量级的差别，正是下一节时间序列中收敛判定处理的对象。

同一进程的时间序列 - 一次尖峰就能改变平均值

代码的后半部分，对同一进程中同一函数调用160次得到的时间序列应用判定函数。判定函数有三个。settle_index返回窗口为5的移动中位数连续10次保持在稳定水平(后半段的中位数)25%以内的第一个位置。stationary比较后两个四分位区间的中位数。spike_count统计前20次中超过稳定水平3倍的最后一次。

# ---------- detectors ----------
                    def settle_index(t, w=5, tol=0.25, run=10):
                        """First call index from which run consecutive moving medians (window w)
                        stay within +-tol of the steady level (median of the last half)."""
                        ref = statistics.median(t[len(t) // 2:])
                        mm = [statistics.median(t[i:i + w]) for i in range(len(t) - w + 1)]
                        for i in range(len(mm) - run + 1):
                            if all(abs(m - ref) <= tol * ref for m in mm[i:i + run]):
                                return i, ref
                        return None, ref
                    
                    def stationary(t, tol=0.25):
                        q = len(t) // 4
                        a, b = statistics.median(t[2 * q:3 * q]), statistics.median(t[3 * q:])
                        return abs(a - b) <= tol * b, a, b
                    
                    def spike_count(t, k=3.0, head=20):
                        ref = statistics.median(t[len(t) // 2:])
                        bad = [i for i, x in enumerate(t[:head]) if x > k * ref]
                        return bad[-1] + 1 if bad else 0
                    
                    random.seed(42)
                    data = [random.random() for _ in range(2000)]
                    def pure():
                        s = 0.0
                        for x in data: s += x * x
                        return s
                    def lazy_series():
                        import sqlite3
                        return sqlite3.sqlite_version
                    
                    print()
                    print("sqlite3 loaded before series:", "sqlite3" in sys.modules)
                    series = {"pure": [us(pure) for _ in range(160)],
                              "import-in-call": [us(lazy_series) for _ in range(160)]}
                    print("B. 160 calls in one process (us)")
                    for name, t in series.items():
                        idx, ref = settle_index(t)
                        ok, qa, qb = stationary(t)
                        print("%-15s first 6: %s" % (name, " ".join("%.1f" % x for x in t[:6])))
                        print("%-15s steady %.1f | settle index %s | spike count %d | stationary %s (%.1f vs %.1f)" % (
                            "", ref, idx, spike_count(t), ok, qa, qb))
                    
                    print()
                    print("C. naive mean of all 160 calls vs mean after discarding spike_count calls (us)")
                    for name, t in series.items():
                        k = spike_count(t)
                        print("%-15s naive %.2f | discard %d -> %.2f | median %.2f" % (name, statistics.mean(t), k, statistics.mean(t[k:]), statistics.median(t)))
                    
                    import timeit
                    r = timeit.repeat(pure, number=50, repeat=7)
                    print()
                    print("D. timeit.repeat(pure, number=50, repeat=7), us per call:", " ".join("%.1f" % (x / 50 * 1e6) for x in r))
                    print("   min %.1f | median %.1f" % (min(r) / 50 * 1e6, statistics.median(r) / 50 * 1e6))

  • import-in-call：函数体内import sqlite3。该序列开始时sqlite3尚未加载(输出中的loaded行)。
  • 窗口5、容差25%、连续10次是这里自行选定的值，并非文档规定。
  • 两个序列在同一进程中先后测量。

噪声掩盖预热 - 平稳性检查与timeit的最小值

B输出(这台电脑的一次运行)中pure序列的前六次都在421到431微秒。稳定水平算得151.7，settle index为16。但stationary为False，后两段的中位数是205.6对53.2微秒，相差近4倍。同一段代码在一个进程里几秒之内就从53微秒变到431微秒。这台电脑为何这样波动，仅凭输出无法区分。重新运行三次时，前六次在80到323微秒之间，stationary依次为False、True、False。

这种情况下，settle index 16不是预热的证据。对未通过平稳性检查的序列，不使用舍弃次数的计算，而是重新测量。D输出是用timeit.repeat把同一函数重复7次的结果，每次重复(调用50次)的耗时散布在59.5到255.7微秒之间(这是这一次运行的值，重新运行三次的最小值为131.7、76.8、99.7)。

Node首次调用 - 逐次耗时与条形分布

Node脚本调用一个创建2万个小对象的函数1000次，逐次计时，输出各调用区间的中位数和对数刻度的条形。以参数child启动同一文件时，会运行一个500次调用的进程并输出一行结果。下面的代码还用与Python相同的定义重新实现了两个判定函数。

const { performance } = require('node:perf_hooks');
                    const { spawnSync } = require('node:child_process');
                    
                    function work(n) {
                      let s = 0, o = { a: 1, b: 2 };
                      for (let i = 0; i < n; i++) { o = { a: o.b + (i % 7), b: o.a ^ i }; s += o.a * 3 + (o.b >> 1); }
                      return s;
                    }
                    function series(n) {
                      const t = [];
                      for (let i = 0; i < n; i++) {
                        const a = performance.now(); work(20000); t.push((performance.now() - a) * 1000);
                      }
                      return t;
                    }
                    const med = a => { const b = [...a].sort((x, y) => x - y); const m = b.length >> 1; return b.length % 2 ? b[m] : (b[m - 1] + b[m]) / 2; };
                    const mean = a => a.reduce((x, y) => x + y, 0) / a.length;
                    function settle(t, w = 5, tol = 0.25, run = 10) {
                      const ref = med(t.slice(t.length >> 1));
                      const mm = [];
                      for (let i = 0; i + w <= t.length; i++) mm.push(med(t.slice(i, i + w)));
                      for (let i = 0; i + run <= mm.length; i++) {
                        if (mm.slice(i, i + run).every(m => Math.abs(m - ref) <= tol * ref)) return { idx: i, ref };
                      }
                      return { idx: null, ref };
                    }
                    function stationary(t, tol = 0.25) {
                      const q = t.length >> 2;
                      const a = med(t.slice(2 * q, 3 * q)), b = med(t.slice(3 * q));
                      return { ok: Math.abs(a - b) <= tol * b, a, b };
                    }
                    
                    if (process.argv[2] === 'child') {

  • 条形按中位数的常用对数比例绘制，因此数字之间的差别远大于条形长度的差别。
  • 在这份输出中，第51到100次的中位数187低于之后的211和279。区间中位数的这种起伏只限于这份输出所显示的范围，其方向并非每次运行都相同。

V8博客在Sparkplug一文中介绍，Sparkplug位于Ignition解释器与TurboFan优化编译器之间，并写道因为稳定的对象形状反馈尚不存在，无法更早开始优化。首次调用需要几千微秒、几十次后降到几百微秒的输出，与这一说明方向一致。输出显示首次调用较慢，原因无法用这个实验区分。

舍弃几次 - 收敛判定规则

steady level (median of last half): 282 us
                    settle index (w=5, tol=25%, run=10): 15 -> discard first 15 calls
                    stationary check: true (274 vs 295 us)

在这次运行中，稳定水平(后半段的中位数)为282微秒，移动中位数规则给出舍弃前15次。平稳性检查为True，后两段为274对295微秒，处于同一水平。这个序列可以用于判定。这些数值是这台电脑一次运行的结果。

关键是这个数字每次运行并不相同。在下面把同一脚本在五个新进程中运行的输出(这台电脑的一次运行)里，判定次数分别是1、94、25、18、4。能够断言的只是方向，即各进程的判定差别很大，具体数字每次运行都不同。仅凭一个进程的一次测量，无法断定舍弃次数。

  • 窗口大小：太小会被单次噪声带偏，太大会模糊较短的预热。这里使用5。
  • 容差：使用稳定水平的25%。比环境的正常波动更窄，判定就永远出不来。
  • 连续次数：窗口中位数连续10次保持在容差内，才视为稳定。
  • 稳定水平：时间序列后半段的中位数。如果后半段仍在下降，这个基准本身就是错的。

实践流程 - 确定舍弃次数的顺序

把上面运行得到的规则整理成顺序，如下。每一项在前面的章节都有输出作为依据，只有取较大值这一项是本文自己的提议。

  • 在新进程中记录每次调用的耗时，并先读代码，看计时区间内是否含有import、编译或初始化。
  • 对可疑的开销，每次只改变一个条件来分离，例如预先加载模块、预先编译模式。
  • 把序列取得足够长(这里是160到1000次)，耗时较长时减少重复次数，使总运行时间保持在10秒左右。
  • 先做平稳性检查。未通过则搁置预热判定，整理环境后重新测量。
  • 用移动中位数求出判定次数，单次尖峰另用逐次检查单独统计。
  • 运行多个新进程，比较各自的判定次数。取较大的作为舍弃次数是本文提出的规则，没有文档依据；依据只到判定会出现分歧为止(这台电脑的一次运行中为1到94)。
  • 对保留的区间，同时报告中位数、最小值和散布，不要只写平均值。
  • 在报告中写明环境；这里所有数值都属于这台电脑的Windows 10、Python 3.13.3和Node v22.16.0。
观察含义处理
只有首次调用特别慢一次性开销(import、初始化)用逐次检查舍弃1次，并分离变量找出原因
几十次内缓慢下降分阶段优化的区间舍弃移动中位数判定的次数
平稳性检查未通过环境在波动搁置判定，重新测量，并结合分布查看最小值
各进程判定次数差别很大单次判定不稳定运行多个进程并取较大的值(本文的提议)

未能确认的内容

  • Node首次调用变慢是由JIT层级切换造成的这一因果。V8博客的文字与输出方向一致，但没有做关闭JIT的对照运行。
  • pure序列在一个进程内从53微秒变到431微秒的原因。是CPU时钟、操作系统调度还是解释器内部，以及各次重新运行的判定为何不同，输出都无法区分。
  • import_warm和re_precompiled中残留的首次超出(1.8对1.0，15.7对2.9)的原因。
  • 操作系统文件缓存的影响。清空缓存需要管理员权限，因此没有运行。
  • Linux或macOS以及其他版本的Python和Node上的数值。只在这台电脑的Windows 10上运行过。
  • Node中performance.now()实际给出的分辨率。MDN的分辨率说明针对浏览器上下文，Node文档没有打开。
  • 窗口5、容差25%、连续10次这组判定参数是否适合其他函数。
  • GC开启与关闭的差别。timeit文档所述的GC暂停，并不适用于这里使用的perf_counter测量。
