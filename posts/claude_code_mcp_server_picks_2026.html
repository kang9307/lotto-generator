Claude Code MCP 서버 고르는 기준 - 목록 말고 판단 축 여섯 개

무엇을 얻고 무엇을 내주는가 - 전송·스코프·권한·신뢰·컨텍스트 비용으로 따지는 선택법

2026-08-06 IT/기술

서론: 추천 목록은 반년이면 상한다

Claude Code에 MCP 서버를 하나 붙이는 데 걸리는 시간은 명령 한 줄이다. 어려운 쪽은 붙이는 일이 아니라 고르는 일이다.

MCP 서버 추천 목록은 이미 넘쳐난다. 범주별 정리 글, 어썸 리스트, 공식 디렉터리까지 다 있다. 그런데 목록에는 유통기한이 붙어 있다. 초기 레퍼런스 서버 상당수는 이미 별도의 아카이브 저장소로 옮겨졌고, 한때 표준 예제처럼 소개되던 @modelcontextprotocol/server-github 패키지도 그중 하나다. 반년 전 목록을 그대로 따라 붙이면 관리가 끊긴 코드를 자기 개발 환경에 심게 된다.

목록보다 오래 가는 것은 기준이다. 그리고 MCP에서 기준이 유난히 중요한 이유가 하나 더 있다. MCP 서버를 붙인다는 것은 편의 기능을 켜는 일이 아니라 접근 권한을 내주는 일이기 때문이다. 파일시스템 서버는 디스크를, 데이터베이스 서버는 데이터를, 이슈 트래커 서버는 사내 티켓 전문을 에이전트의 사정거리 안으로 끌어들인다. 잘못 고른 서버는 느린 게 아니라 위험하다.

그래서 이 글은 목록 대신 판단 축 여섯 개를 세운다. ① 애초에 붙일 이유가 있는가, ② 어떤 전송 방식으로 붙는가, ③ 어느 스코프에 적는가, ④ 그 서버가 무엇을 내주게 만드는가, ⑤ 그 서버를 믿을 근거가 있는가, ⑥ 붙였을 때 컨텍스트를 얼마나 먹는가. 축마다 어떤 선택지가 있고 어느 쪽이 어떤 대가를 치르는지 정리한다. 특정 서버에 안전 도장을 찍어 주는 글이 아니라, 독자가 자기 서버를 스스로 판정할 수 있게 하는 글이다.

1. 붙일 이유가 있는지부터 가른다 - 복붙 횟수라는 단순한 신호

1.1 붙일 때

공식 문서가 제시하는 신호는 의외로 소박하다. 다른 도구의 내용을 세션 창에 복사해 붙여넣는 자신을 발견할 때가 서버를 붙일 때다. 이슈 트래커의 티켓 본문, 모니터링 대시보드의 스택 트레이스, 쿼리 결과 표 — 이런 것을 반복해서 옮기고 있다면 그 시스템이 후보다. 서버를 붙이면 에이전트가 붙여넣기를 기다리는 대신 직접 읽고 움직인다.

1.2 붙이지 말아야 할 때

뒤집으면 판정이 더 명확해진다. 복붙하지 않는 시스템은 붙일 이유가 없다.

  • 한 달에 한두 번 들여다보는 시스템: 설정·인증·유지 비용이 이득을 넘는다
  • 이미 쓰는 CLI로 같은 일이 되는 시스템: 셸에서 되는 것을 굳이 프로토콜로 감쌀 이유는 약하다
  • 매번 같은 내용을 옮기는 경우: 그건 서버가 아니라 프로젝트 문서로 고정할 일이다
  • 읽기만 필요한데 서버가 쓰기 도구까지 함께 들고 오는 경우: 필요 없는 권한이 딸려 온다
  • 자격증명을 새로 발급해야 하는데 그 자격증명의 범위를 좁힐 방법이 없는 경우

1.3 후보를 걸러내는 다섯 문장

  • 지난 2주 동안 그 시스템에서 세션으로 옮긴 내용이 다섯 번 이상인가
  • 옮긴 내용이 매번 달랐는가
  • 에이전트가 그 시스템에 쓰기까지 해야 하는가, 읽기로 충분한가
  • 그 서버가 요구하는 자격증명을 읽기 전용으로 좁힐 수 있는가
  • 붙였다 떼는 데 드는 비용이 낮은가 — 낮다면 일단 붙여 보고 판단해도 된다

2. MCP가 실제로 표준화한 것 - 사양을 알아야 고를 수 있다

2.1 프로토콜의 좌표

MCP는 AI 애플리케이션을 외부 시스템에 연결하는 개방형 표준이다. 흔히 AI 애플리케이션을 위한 USB-C 포트에 비유된다. 서버 쪽이 자신이 할 수 있는 일을 표준 형식으로 노출하면, 그 형식을 이해하는 클라이언트라면 맞춤 연동 코드 없이 붙여 쓸 수 있다. Claude Code도, 다른 여러 편집기와 에이전트도 같은 서버를 공유한다. 이 호환성이 서버 선택의 전제다. 오늘 고른 서버가 특정 도구에만 묶이지 않는다는 뜻이기 때문이다.

2.2 버전 표기를 읽는 법

MCP 사양은 YYYY-MM-DD 형식의 날짜 문자열로 버전을 매기는데, 이 날짜는 마지막으로 하위 호환을 깨는 변경이 있었던 날을 뜻한다. 하위 호환이 유지되는 개선은 버전을 올리지 않는다. 현재 사양 버전은 2026-07-28이다. 서버 문서에 적힌 지원 버전이 이보다 한참 옛날 날짜에 머물러 있다면, 그건 곧 그 서버가 그 이후의 하위 호환 파괴 변경을 따라오지 않았다는 신호로 읽을 수 있다.

2.3 버전 협상이 도입된 뒤 달라진 점

요청마다 _meta 필드의 io.modelcontextprotocol/protocolVersion 키로 사용 버전을 선언하고, 서버가 요청 단위로 수락하거나 거절한다. Streamable HTTP에서는 같은 값이 MCP-Protocol-Version 헤더로도 실린다. 서버가 지원하지 않는 버전이면 지원 목록을 담은 오류를 돌려주므로 클라이언트가 다시 시도할 수 있다. 미리 확인하고 싶으면 server/discover 호출 한 번으로 지원 버전·기능·신원을 한꺼번에 받을 수 있다. 실무적으로 중요한 대목은, 옛 초기화 기반 방식(2025-11-25 이하)을 쓰는 서버와의 호환 경로가 사양에 별도로 명시돼 있다는 점이다. 오래된 서버가 곧바로 못 쓰게 되는 것은 아니지만, 유지보수가 끊긴 서버일수록 이 경계에서 먼저 문제를 낸다.

3. 전송 방식 네 가지 중 무엇으로 붙일까

3.1 판단의 갈림길은 하나다

전송 방식은 결국 서버 코드가 내 기계에서 도는가, 남의 서버에서 도는가로 갈린다. 이 차이가 신뢰 모델 전체를 바꾼다. 로컬 프로세스로 도는 서버는 내 계정 권한을 그대로 쓰고, 원격 서버는 내 자격증명이 남의 인프라를 거친다.

전송실행 위치인증고르는 이유주의점
stdio내 기계의 로컬 프로세스환경 변수·설정 파일파일·로컬 도구·직접 만든 스크립트내 계정 권한으로 실행됨. 패키지 출처가 곧 실행 권한
HTTP(streamable-http)원격 서비스OAuth 2.0 또는 헤더 토큰클라우드 SaaS 연동의 기본값. 가장 널리 지원됨설정 JSON에서 type을 빠뜨리면 stdio로 해석돼 실패
SSE원격 서비스OAuth 또는 헤더아직 SSE 엔드포인트만 여는 서비스에 한정더 이상 권장되지 않는 전송. HTTP가 있으면 HTTP로
WebSocket원격 서비스헤더 전용서버가 먼저 이벤트를 밀어 넣는 구조OAuth를 쓸 수 없고 목록 명령에도 안 잡힘

3.2 실제 등록 명령

원격 HTTP 서버는 이름과 주소만 있으면 된다.

claude mcp add --transport http <이름> <주소>

로컬 stdio 서버는 -- 뒤에 실행 명령을 붙인다. 이 이중 대시가 중요하다. 뒤쪽 인자를 클라이언트가 자기 옵션으로 파싱하지 않고 서버에 그대로 넘기게 하는 구분자다.

claude mcp add --transport stdio <이름> -- npx -y <패키지>

등록 뒤 상태 확인은 claude mcp list, 세부 확인은 claude mcp get <이름>, 제거는 claude mcp remove <이름>다. 세션 안에서는 /mcp 패널이 연결 상태·도구 개수·인증 필요 여부를 한 화면에 보여 준다. 등록 명령은 자격증명을 검증하지 않으므로, 값이 틀려도 등록은 성공하고 연결 단계에서 실패한다. 등록 성공을 연결 성공으로 착각하지 않는 것이 첫 번째 실무 함정이다.

4. 스코프 세 개 - 어디에 적느냐가 곧 누가 그 권한을 갖느냐다

4.1 세 스코프의 실제 차이

스코프열리는 범위팀 공유어울리는 용도위험 지점
local(기본값)등록한 프로젝트에서 나만안 됨개인 실험, 자격증명이 딸린 서버팀원은 왜 내 환경에서만 되는지 모른다
project해당 프로젝트 전원버전 관리로 공유팀 공통 도구, 재현 가능한 개발 환경내가 준 권한을 팀 전원이 갖는다
user내 모든 프로젝트안 됨어디서나 쓰는 개인 유틸리티무관한 프로젝트에서도 그 서버가 늘 살아 있다

4.2 project 스코프가 감추고 있는 결정

project 스코프는 프로젝트 루트의 .mcp.json에 저장돼 저장소에 함께 올라간다. 편의는 분명하다. 저장소를 받은 사람이 같은 도구를 자동으로 얻는다. 그런데 같은 문장을 권한 쪽으로 뒤집으면 이렇게 읽힌다. 내가 고른 서버가 팀 전원의 기계에서 돌게 된다. 그래서 프로젝트 스코프 서버는 처음 쓸 때 승인 절차를 거치도록 설계돼 있고, 승인 선택을 되돌리는 별도 명령도 있다. 저장소를 클론했다고 해서 그 저장소가 스스로 자기 서버를 승인할 수는 없게 막혀 있는 것도 같은 이유다.

4.3 우선순위와 병합되지 않음

같은 이름의 서버가 여러 곳에 정의돼 있으면 우선순위 하나만 살아남는다. 순서는 local → project → user → 플러그인 제공 서버 → 커넥터다. 여기서 놓치기 쉬운 규칙이 있다. 필드가 병합되지 않는다. 우선순위가 높은 쪽의 정의가 통째로 쓰인다. user 스코프에 헤더를 넣어 두고 project 스코프에서 주소만 바꿔 덮어쓰는 식의 기대는 어긋난다. 참고로 세 스코프는 이름으로 중복을 판별하지만, 플러그인과 커넥터는 엔드포인트로 판별한다.

4.4 자격증명을 저장소에 올리지 않는 방법

공유용 .mcp.json에는 환경 변수 확장을 쓴다. ${VAR}는 변수 값으로, ${VAR:-기본값}은 변수가 없을 때 기본값으로 펼쳐진다. 확장이 되는 자리는 command, args, env, 원격 서버의 url과 headers다. 변수가 비어 있고 기본값도 없으면 설정이 통째로 깨지는 대신 경고와 함께 원문 그대로 남는다. 조용히 잘못된 값으로 붙는 상황을 막으려면 기본값을 명시하는 편이 낫다.

{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": { "Authorization": "Bearer ${API_KEY}" }
    }
  }
}

5. 범주별로 무엇을 내주는가 - 권한 관점의 지도

5.1 편의가 아니라 노출로 보는 표

범주별 추천은 대개 무엇이 편해지는지로 쓰인다. 같은 표를 무엇이 노출되는지로 다시 쓰면 선택이 달라진다.

범주얻는 것내주는 것최악의 경우좁히는 수단
파일시스템프로젝트 밖 파일 읽기·쓰기디스크 경로 접근홈 디렉터리의 키·설정 파일 노출허용 디렉터리 목록 제한, 작업 경계 밖 차단
git·코드 호스팅이슈·PR 읽기, 리뷰, 생성저장소 권한을 담은 토큰토큰 범위 안 전 저장소에 커밋·이슈 생성저장소별 세분화 토큰, 읽기 권한 위주
데이터베이스스키마 조회, 즉석 질의연결 문자열과 그 계정의 모든 권한운영 데이터 수정·삭제읽기 전용 계정, 별도 리플리카
이슈 트래커티켓 본문에서 바로 구현사내 티켓 전문과 첨부외부에서 쓴 티켓 본문이 지시문으로 작동프로젝트 단위 권한, 쓰기 도구 분리
모니터링·분석에러 로그·사용 지표 조회운영 로그(개인정보 포함 가능)로그에 섞인 토큰·식별자 유출OAuth 범위 축소, 로그 마스킹 확인
브라우저 제어실제 렌더링 확인·자동화브라우저 세션 조작 권한로그인된 세션으로 임의 조작전용 프로필, 로컬 전용 실행
디자인 도구디자인 시안 기반 구현디자인 파일 전체미공개 제품 화면 유출파일 단위 공유 링크
메신저·메일대화 읽기, 초안 작성대화 이력과 수신함대화 내용에 심긴 지시문 실행읽기 전용 범위, 발송은 승인 필수

5.2 브라우저 계열은 별도의 문제다

브라우저 제어 계열은 이 표에서 가장 특이한 칸이다. 다른 서버는 특정 시스템 하나를 여는데, 브라우저는 그 안에 로그인된 모든 서비스를 함께 연다. 브라우저 벤더가 직접 MCP 서버를 내면서 로컬 전용 실행·개인정보 접근 차단 같은 설계를 넣기 시작한 것도 이 특수성 때문이다. 이 계열 하나를 깊게 보려면 Safari MCP 서버 분석 글에 벤더별 설계 차이와 신뢰 경계 논점이 따로 정리돼 있다.

5.3 데이터베이스 칸에 있는 공식 권고

공식 문서가 예제 안에서 대놓고 권고하는 대목이 한 군데 있다. 데이터베이스 서버를 붙일 때 연결 문자열에 읽기 전용 계정을 쓰라는 것이다. 이유는 명확하다. 에이전트가 실행하는 질의가 데이터를 바꿀 수 없게 만들기 위해서다. 이 한 줄이 이 글 전체의 원칙을 압축한다. 서버 선택은 신뢰 여부를 묻는 문제가 아니라, 신뢰가 무너져도 피해가 제한되게 만드는 문제다.

6. 그 서버를 믿을 근거 - 품질 판단 신호 여덟 가지

6.1 디렉터리에 있다는 사실이 뜻하는 것과 뜻하지 않는 것

이 대목은 오해가 많아 정확히 짚을 필요가 있다. Anthropic은 자사 디렉터리에 커넥터를 올리기 전에 등재 기준에 따라 검토하지만, 어떤 MCP 서버도 보안 감사하거나 관리하지 않는다고 문서에 명시하고 있다. 즉 디렉터리 등재는 최소한의 형식 심사를 통과했다는 신호이지 안전 인증이 아니다. 공식 레지스트리 역시 메타데이터와 설치 명령을 보관하는 메타 레지스트리이고, 실제 코드는 npm·PyPI 같은 패키지 저장소에 그대로 남는다. 네임스페이스 소유권 검증은 하지만 접근 제어나 감사 추적 같은 거버넌스는 제공하지 않는다.

6.2 실제로 볼 신호

공급자 일치서비스 운영사가 직접 낸 서버인가제3자가 만든 비공식 래퍼인데 공식처럼 보이게 이름 지음

6.3 stdio 서버에 한 겹 더 봐야 하는 것

원격 서버는 남의 인프라에서 돌지만 stdio 서버는 내 기계에서 내 계정 권한으로 돈다. 그래서 stdio 서버를 고를 때는 소프트웨어 공급망 관점이 하나 더 붙는다. 어떤 패키지 매니저로 받는지, 버전을 고정할 수 있는지, 그 패키지가 설치 시점에 무엇을 실행하는지가 모두 판단 재료다. 항상 최신 버전을 끌어오는 실행 방식은 편하지만, 업스트림이 바뀌는 순간 내 기계에서 도는 코드도 조용히 바뀐다는 뜻이다.

7. 프롬프트 인젝션과 툴 포이즈닝 - 이 물건의 고유 위험

7.1 두 위험은 방어 지점이 다르다

MCP 서버가 안고 있는 위험은 두 층으로 나뉜다. 섞어서 이해하면 대응이 어긋난다.

  • 프롬프트 인젝션: 서버가 가져온 데이터 안에 지시문이 숨어 있다. 외부인이 쓴 이슈 본문, 크롤링한 웹 페이지, 사용자 제출 로그 같은 것이 통로다. 방어 지점은 데이터를 의심하는 것.
  • 툴 포이즈닝: 도구 정의 자체가 오염돼 있다. 도구 설명 메타데이터에 악성 지시가 들어가면 모델은 그 문장을 읽지만 사용자 화면에는 도구 이름 정도만 보인다. 방어 지점은 서버를 의심하는 것.

둘째 유형이 특히 까다로운 이유는 보이지 않는다는 점이다. 사용자에게 렌더링되지 않는 문자열이 모델의 입력에는 그대로 들어간다. 클라이언트 쪽 취약점 분류에서 이 유형이 가장 흔하고 영향이 크다고 지목되는 것도 그래서다.

7.2 클라이언트가 대신 막아 주는 부분

Claude Code 쪽에 걸려 있는 완화 장치는 다음과 같다. 이것들이 있다고 안심할 근거는 아니지만, 무엇이 이미 막혀 있는지는 알고 있어야 중복 투자를 피한다.

  • 기본이 읽기 전용 권한이고, 민감한 동작은 명시적 승인을 거친다
  • 새 MCP 서버와 처음 여는 저장소는 신뢰 확인 절차를 거친다(비대화형 -p 실행에서는 이 확인이 동작하지 않는다)
  • 웹에서 내용을 가져오는 셸 명령은 자동 승인 대상이 아니다
  • 웹 페치는 별도 컨텍스트 창을 써서 악성 지시가 본 대화로 흘러드는 것을 줄인다
  • 이전에 허용한 명령이라도 의심스러운 형태면 다시 승인을 요구하고, 규칙에 걸리지 않는 명령은 기본이 거부다

7.3 그래도 남는 몫

공식 문서 스스로 이 장치들이 위험을 줄일 뿐 완전 면역은 아니라고 못박는다. 그리고 남는 몫은 대부분 사람 쪽이다. 외부에서 들어온 내용을 그대로 파이프로 밀어 넣지 말 것, 승인 전에 제안된 명령을 읽을 것, 외부 서비스와 붙는 작업은 격리된 환경에서 돌릴 것. 진부해 보이지만 이 셋이 실제로 막아 주는 사고의 비중이 가장 크다.

8. 최소 권한으로 좁히는 실제 설정

8.1 자격증명 층에서 좁히기

가장 바깥이자 가장 효과가 큰 층이다. 어떤 도구 규칙보다도 여기서 좁히는 편이 확실하다.

  • 데이터베이스는 읽기 전용 계정으로 연결 문자열을 만든다
  • 코드 호스팅 토큰은 대상 저장소만 담은 세분화 토큰으로 발급한다
  • OAuth로 붙는 서비스는 요청 범위를 필요한 것만 남긴다
  • 토큰을 설정 파일에 직접 적는 대신 환경 변수 확장으로 참조한다
  • 기간 만료가 있는 자격증명을 우선 쓴다 — 잊고 방치해도 스스로 닫힌다

8.2 도구 단위 규칙으로 좁히기

MCP 도구는 mcp__서버이름__도구이름 형태의 이름을 갖는다. 이 이름으로 허용·질의·거부 규칙을 쓴다. 규칙 문법에는 알아 둘 비대칭이 하나 있다.

  • 거부·질의 규칙은 도구 이름 자리에 글로브를 쓸 수 있다. mcp__*는 모든 서버의 모든 MCP 도구를 뜻한다
  • 허용 규칙은 다르다. 글로브는 mcp__서버이름__이라는 리터럴 접두어 뒤에서만 허용된다. 서버 자리에는 글로브를 쓸 수 없다
  • mcp__서버이름__*는 그 서버의 모든 도구를, mcp__서버이름__get_*는 조회 계열만 자동 승인한다
  • 범위를 지정하지 않은 허용 글로브(예: 전체 와일드카드)는 경고와 함께 무시되고 아무것도 자동 승인하지 않는다

실무적으로 유용한 조합은 조회 계열만 허용하고 나머지는 승인으로 남기는 것이다. 붙였다고 다 열어 두지 않고, 실제로 반복되는 읽기 동작만 자동화하면 왕복은 줄고 노출은 늘지 않는다.

8.3 노출 범위 층에서 좁히기

파일 접근 계열은 클라이언트가 알려 주는 작업 루트를 존중하도록 만들어진 서버인지 확인할 가치가 있다. 사양에는 서버가 스스로 접근 범위를 물어 제한할 수 있는 요청이 있고, Claude Code는 세션의 시작 디렉터리와 사용자가 추가로 허용한 디렉터리 목록으로 응답한다. 이 목록이 바뀌면 변경 알림도 보낸다. 이 흐름을 구현한 서버는 사용자가 연 만큼만 본다. 구현하지 않은 서버는 자기가 아는 만큼 본다. 이 차이는 서버 문서에서 확인해야 하는 항목이다.

8.4 승인 자체가 목적인 도구

서버 제작자 쪽 장치도 하나 있다. 도구 메타데이터에 사용자 상호작용 필수 표시를 달면, 그 도구는 자동 승인 모드에서도 매번 승인 화면을 띄우고 다시 묻지 않기 선택지도 제공하지 않는다. 허용 규칙으로도 우회되지 않는다. 접근 권한 부여 같은, 사람이 동의한 적 없으면 의미가 없는 동작에 쓰라고 만들어진 표시다. 서버를 직접 만든다면 파괴적 도구에 이 표시를 다는 것이 사용자에게 주는 가장 정직한 안전장치다.

9. 컨텍스트 비용과 응답 지연 - 많이 붙일수록 손해 보는 지점

9.1 도구 정의가 먹는 자리

서버를 붙이면 그 서버의 도구 정의와 서버 안내문이 모델의 입력에 자리를 차지한다. 서버가 늘수록 대화에 쓸 공간이 줄어든다. Claude Code는 이를 완화하려고 도구 검색을 기본으로 켜 둔다. 세션 시작 시점에는 도구 이름과 서버 안내문만 싣고, 실제 정의는 필요할 때 찾아 불러온다. 그래서 서버를 더 붙여도 컨텍스트 영향이 크지 않다. 고정된 서버당 도구 개수 상한은 없고, 실질적인 한계는 컨텍스트 예산이다.

9.2 조절 손잡이

  • 도구 검색 동작은 환경 변수로 바꿀 수 있다. 미리 싣기·전부 미루기·비율 기준 자동 판단 중에서 고른다
  • 매 턴 필요한 소수의 서버는 항상 싣기 옵션으로 예외 처리할 수 있다. 다만 그 서버가 연결될 때까지 시작이 잠깐 막힌다
  • 도구 출력이 1만 토큰을 넘으면 경고가 뜬다. 기본 상한은 2만 5천 토큰이고 환경 변수로 올릴 수 있다
  • 서버 안내문과 도구 설명은 각각 2KB에서 잘린다. 서버를 만든다면 핵심을 앞에 둬야 한다
  • 도구 호출에는 서버별 시간 제한과 유휴 제한이 따로 걸린다. 유휴 기본값은 원격 5분, 로컬 30분이다

9.3 정리를 주기적으로 해야 하는 진짜 이유

토큰 비용보다 실질적인 문제는 선택 오류다. 비슷한 이름의 도구가 여러 서버에 흩어져 있으면 모델이 엉뚱한 쪽을 고를 확률이 올라간다. 세 달 전에 한 번 써 보고 그대로 둔 서버, 실험하다 만 서버, 이제 안 쓰는 서비스의 서버를 떼는 일은 보안 조치이기도 하지만 정확도 조치이기도 하다. 목록을 열어 최근 30일 안에 실제로 호출된 적 없는 서버를 후보로 걸러 내는 정도의 주기적 점검이면 충분하다.

10. 붙이지 말아야 할 때와 대체 수단

10.1 MCP가 답이 아닌 경우

모든 연동이 서버여야 하는 것은 아니다. 다음 경우에는 다른 수단이 더 싸다.

  • 이미 좋은 CLI가 있는 시스템: 셸 명령 한 줄이면 되는 일에 프로토콜 계층을 얹으면 실패 지점만 는다
  • 절차가 고정된 반복 작업: 자연어로 매번 지시하는 대신 프로젝트 문서나 스크립트로 굳히는 편이 재현성이 높다
  • 일회성 조회: 붙였다 떼는 비용이 조회 한 번보다 크다
  • 자격증명을 좁힐 방법이 없는 시스템: 전체 권한 토큰만 발급되는 서비스라면 노출 범위가 통제 불가다
  • 출력이 지나치게 큰 소스: 매 호출마다 상한에 부딪히면 결국 사람이 잘라 줘야 한다

10.2 붙이기 전에 해 볼 수 있는 것

  • 일단 로컬 스코프로 붙여 2주 써 보고, 실제 호출 빈도를 보고 프로젝트 스코프 승격을 판단한다
  • 읽기 도구만 자동 승인해 두고 쓰기는 승인으로 남긴 채 관찰한다
  • 운영 자격증명 대신 스테이징·리플리카 자격증명으로 먼저 붙인다
  • 도구 목록을 한 번 훑어 파괴적 도구가 무엇인지 이름부터 확인한다
  • 서버가 실패했을 때 어떤 메시지가 뜨는지 일부러 한 번 만들어 본다 — 인증 실패와 연결 실패는 대응이 다르다

11. 확인하지 못한 것

이 글에서 근거를 확보하지 못해 단정하지 않은 항목을 한자리에 모은다.

  • 개별 서버의 안전성 판정: 이 글은 어떤 서드파티 서버도 안전하다고 단정하지 않는다. 공개된 독립 보안 감사 결과를 확인하지 못했다
  • 도구 검색의 실제 절감 폭: 기본 활성화라는 동작은 문서로 확인했지만, 서버 수 대비 토큰 절감량을 보여 주는 공개 벤치마크 수치는 확인하지 못했다
  • 툴 포이즈닝의 실제 피해 규모: 위험 유형과 그 우세함을 지적하는 연구는 있으나, 실제 사고 건수·피해 규모를 집계한 신뢰할 만한 공개 통계는 확인하지 못했다
  • 서버별 채택률 순위: 다운로드 수나 설치 수 기준의 신뢰할 만한 최신 순위표는 확인하지 못했다. 그래서 이 글에는 인기 순위가 없다
  • 원문 추천 글의 개별 서버 목록: 계기가 된 글에서 범주 구분과 주의사항은 확인했지만, 범주 아래 나열된 개별 서버 전체 목록까지는 확인하지 못했다
  • 레지스트리 정책의 향후 변화: 공식 레지스트리가 거버넌스 기능을 추가할 계획이 있는지는 확인하지 못했다

자주 묻는 질문(FAQ)

Q1. MCP 서버를 붙여야 할지 어떻게 판단하나?

다른 도구의 내용을 세션에 반복해서 복사해 붙여넣고 있다면 그 시스템이 후보다. 반대로 한 달에 한두 번 보는 시스템, 이미 쓰는 CLI로 되는 일, 매번 같은 내용이라 문서로 고정할 수 있는 경우는 붙이지 않는 편이 낫다. 서버 하나마다 설정·인증·컨텍스트 비용과 권한 노출이 함께 온다.

Q2. local·project·user 스코프는 무엇이 다른가?

local은 기본값으로 그 프로젝트에서 나만 쓴다. project는 저장소의 설정 파일로 팀 전체가 공유하며 처음 쓸 때 승인을 거친다. user는 내 모든 프로젝트에서 열리지만 나에게만 보인다. 같은 이름이 겹치면 local·project·user·플러그인·커넥터 순으로 하나만 살아남고 필드는 병합되지 않는다.

Q3. 프롬프트 인젝션과 툴 포이즈닝은 무엇이 다른가?

인젝션은 서버가 가져온 데이터에 지시문이 숨어 있는 경우이고, 포이즈닝은 도구 정의 자체가 오염된 경우다. 앞의 것은 데이터를 의심하면 되고, 뒤의 것은 서버를 의심해야 한다. 포이즈닝이 더 까다로운 이유는 사용자 화면에 렌더링되지 않는 문자열이 모델 입력에는 그대로 들어가기 때문이다.

Q4. 권한을 최소한으로 좁히는 실질적 방법은?

세 겹에서 좁힌다. 자격증명은 읽기 전용 계정과 세분화 토큰으로, 도구는 서버·도구 이름을 명시한 규칙으로, 노출 범위는 작업 디렉터리 제한과 환경 변수 참조로 좁힌다. 셋 중 자격증명 층이 가장 효과가 크다.

Q5. 디렉터리나 레지스트리에 올라와 있으면 안전한가?

아니다. 등재 기준에 따른 검토는 있지만 보안 감사는 아니라고 문서에 명시돼 있다. 공식 레지스트리도 메타데이터를 보관할 뿐 접근 제어나 감사 추적 같은 거버넌스는 제공하지 않는다. 등재는 출발점이지 결론이 아니다.

결론 - 오늘 적용할 다섯 단계

MCP 서버 선택은 좋은 목록을 구하는 문제가 아니라 자기 기준을 갖는 문제다. 목록은 반년이면 상하지만 기준은 남는다. 오늘 적용할 수 있는 순서로 정리하면 이렇다.

  • 1단계 — 지금 붙어 있는 것부터 센다. 목록을 열어 최근 실제로 쓴 적 없는 서버를 표시한다. 정리는 보안 조치이면서 정확도 조치다
  • 2단계 — 각 서버가 무엇을 내주는지 한 줄로 적는다. 적히지 않는 서버는 아직 이해하지 못한 서버다
  • 3단계 — 자격증명부터 좁힌다. 읽기 전용 계정, 세분화 토큰, 좁은 OAuth 범위. 여기서 좁히는 게 규칙보다 확실하다
  • 4단계 — 스코프를 다시 고른다. 팀 전체에 줄 권한인지, 나만 쓸 권한인지, 이 프로젝트에서만 열릴 권한인지를 구분해 옮긴다
  • 5단계 — 새 서버는 로컬 스코프에서 2주 시험한다. 읽기만 자동 승인해 두고 호출 빈도를 본 뒤 승격 여부를 정한다

마지막으로 이 글이 하지 않은 일을 분명히 해 둔다. 여기에는 어떤 서버가 안전하다는 판정이 없다. 판정을 대신해 주는 목록은 존재하지 않기 때문이다. 있는 것은 판정에 쓸 축뿐이고, 그 축을 자기 환경에 대 보는 일은 결국 붙이는 사람의 몫이다.
