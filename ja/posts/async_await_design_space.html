きっかけ - ログ一行が4通りに終わる

原文の出発点はごく小さなプログラムだ。遅いログ書き込みを模したタスクを一つ起こし、そのタスクを待たずに関数が戻る。外側では少し休んでから印をもう一つ出す。その結果として出てくる文字列が、7つのランタイムで4通りに分かれる。

ここで大事なのはどの答えが正しいかではない。このプログラムには競合状態もなく、共有資源もなく、スレッドを複数使ってもいない。それでも答えが分かれるなら、分岐の原因はプログラムではなくその下に敷かれたランタイムが何を既定値と定めているかにある。原文が9本の軸を立てた理由がそれだ。

原文はタスクの一生を三つの区間に切り、軸を配置している。タスクがどう始まるか、どう終わるか、どうキャンセルされるか。そして各軸について性能・メモリ使用量・使い勝手・意味論のあいだのトレードオフがあるだけで、正解も不正解もないと明記する。言語ごとに固有の設計根拠があるということだ。

並行性の欠陥をコードの外側で捕まえる話、つまり順序の場合の数を列挙して到達可能な状態をなめる方法は、仕様を先に書くと何が捕まるのかで別に扱った。以下はその反対側だ。言語が非同期をどんな形で表現するかが主題である。

色のある関数 - 印が呼び出し階層へ広がる仕組み

非同期を初めて触った人が最初にぶつかる壁は、キャンセルでも例外でもない。async 関数を一つ呼ぼうとしたら呼ぶ側も async でなければならず、その上もそうで、結局エントリポイントまで印が上っていく現象だ。俗に色のある関数と呼ばれる。

スタックをどこに置くか

この広がりは文法の好みではなく実装方式が強制する帰結だ。普通の関数呼び出しはローカル変数と戻り先を機械のコールスタックに積む。そのスタックはオペレーティングシステムのスレッドが所有する。だから同期関数が何かを待つとスレッドが丸ごと止まる。スタックがスレッドに縛られている以上、ほかに手はない。

中断可能な関数はこの前提を壊す。途中で止まって呼び出し元に制御を返し、後からその位置で続きを回さなければならない。そのためにはawait をまたいで生き残る状態をスタックの外に保存する必要がある。何が残るべきかは決まっている。

  • await の後でも使われるローカル変数 — スタックフレームが消えた後にも値がなければならない
  • 再開地点 — 本体のどの位置から続きを回すかを指す目印
  • 後始末の対象 — 開いた資源、解放すべきロック、回るべき finally ブロックの位置

コンパイラはこの三つを収めるオブジェクトを作り、関数本体を await 地点ごとに切って再開可能な断片へ再配置する。この変換は関数に印が付いているときにだけ起きる。MDN の await ドキュメントが async 関数の本体は await 地点で分かれると説明しているのが、この地点だ。

だから上へ広がる

印のない普通の関数はその保存領域を持たない。したがって中断可能な関数の結果を使うには二択しかない。スレッドを丸ごと塞いで待つか、自分も同じ変換を受けるかだ。前者を選べば非同期を使う理由が消え、後者を選べば印が一段上がる。呼び出し階層全体へ広がる理由がこれである。

この広がりは印が署名に現れる設計でのみ起きる。後で見る軽量スレッド系はスタックをスレッドから切り離してタスクごとに一つ付ける方を採るので、どんな関数でも中断でき、したがって印が要らない。

広がりは欠陥か情報か

広がりをめぐって判断が分かれる地点がある。一方はこれを伝染と見る。ライブラリが一つ非同期になれば、その上のすべてのコードが直されねばならず、同じ機能の同期版と非同期版が並んで維持される重複が生じる。

もう一方はこれを意図された型情報と見る。印が付いているということは、その呼び出しが中断されうるという事実が署名に書かれているということであり、その事実は実際に役に立つ。

  • 不変条件が観測される地点が分かる — 中断が起きればほかのタスクが割り込んで共有状態を見られる。印はその窓が開く場所を示す
  • ロックを持ったまま中断するコードを目で探せる — ロック区間の中の await は署名ではなく本体にそのまま見える
  • キャンセルが届きうる地点が分かる — 協調型のキャンセルはたいてい中断地点で伝えられる
  • コストの異なる呼び出しを区別してくれる — 即座に戻る呼び出しと待ちを含む呼び出しを署名で分ける

どちらが正しいと言う場ではない。同じ性質が直すコストとして計算されれば欠陥であり、読む情報として計算されれば機能である。コードベースがすでに大きく同期ライブラリに深く絡んでいれば前者のコストが大きく、共有状態を扱うコードが多く割り込み地点を統制しなければならないなら後者の価値が大きい。

開始の2軸 - 即時性と中断保証

即時性はasync 関数を呼んだその瞬間に仕事が始まるかを分ける。遅延側では呼び出しがオブジェクトを一つ作るだけで何も起きない。Python の標準ライブラリドキュメントはコルーチンをただ呼んでも実行がスケジュールされないと明記し、呼び出し結果がコルーチンオブジェクトとして表示される例を併せて載せている。Rust 標準ライブラリの Future ドキュメントはもっと強く書く。フューチャーはそれ自体では不活性であり、下に敷かれた計算が進むには能動的にポーリングされなければならないというのだ。

即時側は逆だ。C# のドキュメントは async メソッドが最初の await で中断されるとき呼び出し元にタスクを返し、そのタスクが進行中の作業を表すと説明する。呼んだ瞬間にはすでに回っているのである。

中断保証の軸はもっと微妙だ。await を書いたのだからここで必ず一度譲ると仮定してよいのかという問題である。MDN は JavaScript について明確に書く。使われたプロミスがすでに履行済みであっても async 関数の実行は次のティックまで止まり、待機対象がプロミスでなくてもすでに予約されたすべてのマイクロタスクが処理されるまで制御が戻らないというのだ。

// await は対象がプロミスでなくても次のティックまで譲る
async function step(name) {
  console.log(name, 'start');
  await console.log(name, 'middle');
  console.log(name, 'end');
}

step('first');
step('second');
// first start / first middle / second start / second middle / first end / second end

C# は同じ場所で違う答えを出す。マイクロソフトのドキュメントは待機対象が await に至る前にすでに完了していれば制御はそのメソッドに留まると書き、中断して戻ってくるコストを払う理由がないという根拠を併記している。同じ await という語が、一方では譲りを保証し、他方では保証しない。

  • 静的な中断は割り込み地点をコードから数えられるようにする。代わりにすでに準備された値にも一ティックを支払う
  • 動的な中断は準備された値で往復コストを節約する。代わりに同じコードが負荷状態によって違う順序で回る
  • 遅延した開始は作っておいて後から回す組み合わせを可能にする。代わりに回すのを忘れると何も起きない

終了の4軸 - 寿命・参照・後始末・例外

寿命範囲は起こしたタスクがいつまで生きていてよいかを定める。無期限側ではタスクが自分を作った関数より長く生きられ、動的側では作ったスコープが終わる前に片付けられる。Swift の並行性提案書は後者の規則を一文で書いている。子タスクを作った関数は戻る前にそのタスクが終わるのを待たなければならないというのだ。Trio のドキュメントも同じ形だ。子を産むブロックはすべてのタスクが終わるまで抜けないと書かれており、責任ある親になる用意がなければ子タスクを始められないという記述が併記されている。

参照の強さは実務でもっとも静かに引っかかる軸だ。Python の asyncio ドキュメントは create_task の項に警告を付けている。イベントループはタスクを弱い参照でしか保持せず、他所から参照されていないタスクは完了前でもいつでも回収されうるというのだ。だからドキュメントは背景タスクを集合にまとめて強い参照を作り、完了コールバックでその参照を外すよう案内している。

import asyncio

background = set()

async def main():
    task = asyncio.create_task(write_log())
    background.add(task)                       # 強い参照を作る
    task.add_done_callback(background.discard) # 終わったら参照を外す
    await asyncio.sleep(1)

後始末の方式は寿命が終わる瞬間の処分だ。残ったタスクを待ってやる側、キャンセルを掛けて片付けさせる側、そのまま断ち切る側に分かれる。ここが後始末のコードが回るか回らないかを決める。C# のドキュメントが記した条件一つがこの軸の性格をよく示す。await での中断はメソッドからの脱出ではないのでその時点で finally ブロックは回らない。再開されないタスクの後始末コードは、だから実行されないまま残る。

例外の伝播は誰も待たなかったタスクが失敗したときを扱う。Python のドキュメントは結果を回収しない方式を使うとタスクが失敗しても例外が回収されず、回収時点で取得されなかったタスク例外というメッセージがログにだけ残ると書く。Trio は反対側だ。処理されなかった例外が親タスクの中で再送出され、例外グループにまとめられる。

  • 無期限の寿命は背景作業を楽にする。代わりに終了時点で何が残っているのか誰も分からない
  • 動的な寿命はスコープを抜ければ残りがないことを保証する。代わりに長く回る作業のためのスコープを手で作らねばならない
  • 弱い参照は参照漏れを防ぐ。代わりに保持していない背景タスクが消えることがある
  • 例外をタスクの中に閉じ込める設計は一つの失敗がほかのタスクを巻き添えにしないようにする。代わりに失敗がログ一行にしか残らない

キャンセルの3軸 - 認識・方向・持続

キャンセルは原文が三本の軸を別々に割り当てた唯一の束だ。それだけ枝分かれが多い。

認識はタスクがキャンセルに反応できるかを問う。反応できる側ではキャンセルが協調型になる。Swift の提案書はキャンセルが全面的に協調的かつ同期的であり、何かがキャンセルの有無を確認しなければ何の効果もないと書く。Python のドキュメントも同じ性格を別の形で述べる。Task.cancel は次のイベントループ周期にキャンセル例外をコルーチンの中へ投げるよう予約するだけであり、コルーチンは後始末の機会を得て例外を飲み込んで要求を拒むこともできる。ドキュメントはその行為を推奨しないと併記している。

方向はキャンセルがグラフをどちら側へ流れるかだ。Swift の提案書は親がエラーで抜けると子タスクが暗黙にキャンセルされると書く。Python の TaskGroup は別の形だ。グループのいずれかのタスクがキャンセル例外以外の例外で最初に失敗するとグループの残りのタスクがキャンセルされ、その時点で本体がまだ生きていればそのブロックを含むタスクまでキャンセルされる。失敗した例外は最後に例外グループへまとめられて送出される。

async def main():
    try:
        async with asyncio.TaskGroup() as tg:   # スコープが子を掴む
            tg.create_task(write_log())
            tg.create_task(fetch_config())      # 一つ失敗すると残りがキャンセルされる
    except* OSError:                            # 残った失敗はグループでまとめて来る
        handle_failure()

async def write_log():
    try:
        await asyncio.sleep(2)
    except asyncio.CancelledError:
        raise                                   # 飲み込まずに再送出する
    finally:
        close_handle()

持続は一度掛かったキャンセルがどれだけ続くかだ。Trio のドキュメントは自分の側の性格をレベルトリガという語で説明する。ブロックがキャンセルされた後は、そのブロックの中のキャンセル可能なすべての演算がキャンセル例外を送出し続けるというのだ。Swift も同じ方向だ。提案書はキャンセルのフラグが一度立つと決して消されないと書く。Python は反対側の余地を残している。キャンセル例外を捕まえて飲み込んだコードは Task.uncancel を呼んでキャンセル状態を取り除かねばならず、取り除けば予約されていたキャンセルが撤回されうる。

  • 持続型のキャンセルは後始末の途中でキャンセルがそっと解けて作業が続くことを防ぐ。代わりに後始末の中で待ちが必要なら保護区間を別に開かねばならない
  • 一時型のキャンセルはキャンセル後も後処理を続ける余地を与える。代わりにキャンセルを飲み込んだコードが残っていると期限が守られない
  • 認識しないキャンセルは対象コードに何も要求しない。代わりに中断された地点で何が半分終わっているかは別に扱わねばならない

例外 — 破壊的失敗が必ず誰かに届く隣のタスクも切られ例外がまとめて来る
キャンセル — 認識する後始末と部分的な巻き戻しをタスク自身が行うすべての待ち地点がキャンセルを通さねばならない
キャンセル — 持続後始末の途中でキャンセルが解けない後始末の中の待ちは保護区間を別に開かねばならない

原文にない軸 - 誰が再開させ、スタックはどこにあるか

原文の9軸はタスクの観測可能な意味論を分ける軸だ。実務で選ぶときにはその下にもう二本の軸が要るのだが、この二つは原文の分類にない。ここでは原文の軸と区別して別に立てる。

一つ目は誰が実行を再開させるかだ。言語が実行器を一緒に提供する設計があり、言語は中断可能な断片だけを定義して実行器はライブラリとして選ばせる設計がある。Rust の Future ドキュメントが後者をそのまま述べている。フューチャーを使うとき普通は poll を自分で呼ばず .await を使い、進行可能になったフューチャーを繰り返しポーリングする責任は実行器にあるというのだ。準備の合図は Waker を通じて戻る。ポーリングが Poll::Pending を返すとき現在のコンテキストの Waker を複製して置き、進行可能になったらそれを起こす仕組みである。

二つ目はスタックをどこに置くかだ。先に見た状態機械への変換が一方で、タスクごとに別のスタックを付ける方がもう一方である。Java の仮想スレッド提案書は後者の実装を明示する。仮想スレッドのスタックはJava のガベージコレクション対象ヒープにスタックチャンクオブジェクトとして保存され、実行に応じて伸び縮みするというのだ。

  • ランタイム内蔵 — 標準が一つなのでライブラリの互換が容易だ。代わりにスケジューリング方針を変える余地が狭い
  • 実行器を選択 — 仕事の性格に合わせて実行器を差し替えられる。代わりに実行器を前提としたライブラリ同士が混ざらない
  • 状態機械への変換 — タスクあたりのメモリが必要な分だけ確保される。代わりにスタックトレースが元の呼び出し階層とずれる
  • 別スタック — 呼び出し階層がそのまま残り追跡とデバッグが続く。代わりにスタック自体を置く場所が要る

色をなくす設計 - 取り戻すものと手放すもの

印を付けずに同じ目標へ至る方法がある。スレッドをオペレーティングシステムのスレッドより安く作り、塞ぐコードをそのまま書きつつ塞がれているあいだは搬送スレッドを解放する方式だ。Java の仮想スレッドがこの設計をもっとも詳しく文書化した事例である。提案書は仮想スレッドを特定のオペレーティングシステムスレッドに縛られない java.lang.Thread のインスタンスと定義し、Java コードを下位のオペレーティングシステムスレッドの上で回すがコードの一生のあいだそのスレッドを占有はしないと述べる。

取り戻すもの

提案書が非同期方式について記した記述が、そのまま取り戻すものの一覧になる。非同期方式は要求処理のロジックを小さな段階へ分割させ、ループや try-catch といった言語の基本的な逐次合成手段を放棄させる。観測の側の記述はさらに直接的だ。スタックトレースには使える文脈がなく、デバッガは要求処理のロジックを段階実行できず、プロファイラはある演算のコストをその呼び出し元に結び付けられないというのである。

// 色のない側: 塞ぐ呼び出しをそのまま使い、スレッドをタスクごとに与える
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var request : requests) {
        executor.submit(() -> {
            var body = httpClient.send(request, ofString()); // 塞いでもよい
            return store.save(body);                         // ループや try がそのまま使える
        });
    }
}

手放すもの

代わりに手放すものがある。まず中断地点の可視性だ。どの呼び出しが止まりうるかが署名に書かれないので、ロックを持ったまま止まるコードや、不変条件が壊れたままほかのスレッドに観測される区間を署名だけでは探せない。次に境界条件だ。提案書は仮想スレッドが搬送スレッドから降りられない二つの場合を明示する。synchronized ブロックまたはメソッドの中で実行するとき、そしてネイティブメソッドや外部関数を実行するときだ。

提案書が自ら引いた線も併せて見るべきだ。仮想スレッドはより速いスレッドではなく、コードをより速く回しはしない。速度ではなく規模のために存在するという文がそれである。適用条件も併記されている。同時タスク数が数千を超え、仕事が計算中心でないときにスループットが上がる。

どちらが優れていると言う場ではない。計算が支配的な仕事ならどちらを選んでも待ちがないので得るものが少なく、既存コードがすでに塞ぐ呼び出しで埋まっていてそのライブラリに非同期版がなければ色のある側へ移すコストが大きい。逆に共有状態を扱うコードが多く割り込み地点を統制しなければならないなら署名に書かれる印が価値を出す。

実務で実際に引っかかる場所

キャンセルが伝わらず残る作業

原因は単純だ。キャンセルが届く経路がその作業まで通じていない。経路は三つの形のどれかだ。引数として流れるキャンセル信号、子を掴んでいるスコープ、そして破棄。何も使わずにタスクだけを起こすと、そのタスクは誰の子でもなくなる。

  • 信号を渡す形 — Go の標準ライブラリドキュメントはコンテキストを構造体に入れず、必要な関数ごとに第一引数で渡すよう規定する。渡さない区間で経路が切れる
  • スコープが掴む形 — Swift の提案書は構造化されていないタスクと分離されたタスクのどちらも親子の完了制約に従わないと書く。スコープの外へ出たタスクはスコープと一緒には終わらない
  • 参照が切れる形 — Python のドキュメントの弱い参照の警告がこの場合だ。保持していない背景タスクは終わる前に消えることがある

例外が消える経路

待機されなかったタスクが失敗すると、その例外を受け取る者がいない。Python のドキュメントはその状態を取得されなかったタスク例外というログメッセージで説明し、そのメッセージが出る時点が回収されるときだと書く。失敗とログのあいだに時間の隔たりがあるということだ。

  • 戻り型が例外を運べない場合 — C# のドキュメントは void を返す async メソッドは待機できず、呼び出し元がそのメソッドの送出する例外を捕まえられないと書く
  • 結果を誰も回収しない場合 — Python のドキュメントはこの経路を避けるなら TaskGroup を使うよう案内する。グループは各タスクに強い参照を保ち、待機し、例外を伝播する
  • 例外をタスクの中に閉じ込める設計 — 原文の例外伝播の軸でなしの側がこの性質だ。反対側では Trio のように親が再送出する

塞ぐ呼び出し一つがランタイムを止める

原因は実行器スレッドが今まさに自分のコードを回しているという事実にある。状態機械方式では再開断片が実行器スレッドの上で回る。その断片の中でオペレーティングシステム水準で塞ぐ呼び出しを行えば、そのスレッドはそのあいだほかのタスクの断片を一つも回せない。実行器が単一スレッドなら、ランタイム全体がそのあいだ止まったのと同じである。

  • 計算が長くかかる区間 — 塞ぐ呼び出しでなくても結果は同じだ。譲り地点がなければそのあいだ何のタスクも進めない
  • 同期ライブラリの呼び出し — ファイル入出力、名前解決、暗号演算のように非同期版がない呼び出しが代表的だ
  • 軽量スレッド側の対応する現象 — Java の提案書の固定条件がこの場所だ。synchronized の中やネイティブ関数の中では搬送スレッドを降ろせない

互いに相手を待って誰も進めない構造そのものは非同期だけの問題ではない。資源を一つ分け合って両方が止まる実例はパイプバッファが満杯になって起きるデッドロックに整理してある。

順序の保証がないのにあると仮定するコード

先の中断保証の軸がそのまま欠陥として現れる場所だ。ここで一度譲るのだからそのあいだに向こうが回るだろうという仮定、あるいはこれは即座に終わるのだから中断されないだろうという仮定がコードに埋め込まれる。二つの仮定は互いに反対なのに、ランタイムがどちらを保証するかはドキュメントを見なければ分からない。

  • 静的な中断を仮定したコードを動的な中断のランタイムへ移すと — 予約しておいた後続作業が予想より遅く回る
  • 動的な中断を仮定したコードを静的な中断のランタイムへ移すと — 即座に終わると思っていた区間に割り込みが生じる
  • 遅延した開始を即時の開始と取り違えると — 作っておいただけで回していないコルーチンが静かに何もしない

キャンセルモデルの比較

キャンセルは三つの形で作られる。下の表はそれぞれが何を保証し何を要求するかを整理したものだ。根拠の列には公式ドキュメントに対応する文がある項目だけを書いた。

期限をどこに掛けるかも併せて決めねばならない。Python のドキュメントの timeout は現在のタスクをキャンセルし、そのキャンセル例外を内部でタイムアウトエラーに変えて返す。反対方向の道具もある。shield は包んだ作業をキャンセルから保護するが、ドキュメントが併記しているとおり呼び出した側は依然としてキャンセルされ、待機式がキャンセル例外を送出する。キャンセルが規模で崩れる別の層の話はセッション取り消しが規模で崩れる地点にある。

順序を前提にしたコードが静かに壊れる場所

非同期コードの欠陥のなかで再現がもっとも難しいのが順序の仮定だ。原因は三つが重なって生じる。

第一に、中断が保証されるかどうかがランタイムごとに違う。JavaScript のように常に譲る側では await の後のコードが必ず次のティックへ押し出される。すでに準備された値であってもそうだ。C# のように準備された値で留まる側では同じコードがその場で続けて回る。同じ構造のコードを二つのランタイムへ移せば順序が変わる。

第二に、タスクが始まる時点が違う。遅延側では作っておくことと回すことが分かれ、即時側では呼んだ瞬間に回り出す。作っただけのコルーチンが後で待機されて初めて始まるなら、そのあいだにあったことを基準に組んだ順序の仮定は崩れる。

第三に、完了の順序と予約の順序が違う。複数を同時に起こせば終わる順序は外部要因が決める。ところがコードはしばしば起こした順に結果が来ると仮定する。

  • 表現へ移せ — 順序が必要ならイベント、キュー、ロックのように順序を明示する手段で書く。待ち地点の副作用に頼らない
  • スコープで束ねよ — 複数を起こして全部終わってから次が回る区間はグループ API で表現する。スコープが終わったという事実自体が保証になる
  • 仮定を試験で固定せよ — 順序の仮定が残らねばならないなら、その仮定を検査する試験を併せて置く。負荷ではなく論理で再現されるようにする

結論 - 選んだのは文法ではなく失敗の仕方だ

同じプログラムが7つのランタイムで4通りに終わるという観察は、非同期が文法の一対ではなく9本以上の独立した決定だという事実を露わにする。その決定はドキュメントのどこかに散らばっており、たいていは事故の後になって読まれる。

  • 印の広がりはスタックをどこに置くかの帰結だ — 文法の好みではない。なくすにはスタックをタスクごとに付ける方へ行かねばならず、そうすると中断地点の可視性を手放すことになる
  • キャンセルは機能ではなく経路だ — 信号、スコープ、破棄のどれで作るかを先に決めてこそ、後から残る作業がなくなる
  • 既定値を読むことが半分だ — 寿命、参照の強さ、例外の伝播は誰も明示しなければランタイムの既定値が使われる

非同期を導入する決定は、だからどの失敗の仕方を引き受けるかの決定である。原文が各軸にトレードオフだけがあり正解も不正解もないと書いた理由も同じだ。

確認できなかったこと

  • 4通りの出力の正確な文字列とランタイムの対応 — 原文は7つのランタイムが4通りの答えを出すと述べ、その対応を図で載せている。図の中の文字列はテキストとして回収されなかったため写していない
  • 原文にぶら下がる論文の本文 — 形式意味論の細部とコア計算体系の定義は論文の側にある。今回の作業では調査範囲を文書型の資料に限ったため開いていない
  • Tokio と Smol の個別の動作 — 二つのランタイムの軸の配置は原文の分類のみを根拠として述べた。各プロジェクトの公式ドキュメントにある対応する文は今回の範囲に入れていない
  • Rust でフューチャーを捨てることがキャンセルになるか — 標準ライブラリの Future ドキュメントには完了前に破棄したときの動作を述べる文がない。原文が Rust をキャンセル認識の軸の認識しない側へ置いた根拠は原文の側にある
  • Swift 公式言語ガイドの該当節 — 記述は Swift Evolution 提案書 SE-0304 の本文を根拠とした。言語ガイド側のページは本文が回収されなかった
  • Kotlin などそのほかのランタイム — 原文の分類にもなく今回公式ドキュメントと突き合わせてもいないので、記述の対象から外した
  • 数値と性能の比較 — どの設計がどれだけ速いかについての値は載せていない。Java の提案書が自ら書いたとおり仮想スレッドは速度ではなく規模のためのものであり、そのほかの比較は条件に大きく左右される
