どこでも動く正規表現 — 言語・ツール間の互換性の落とし穴と解法

JS・Python・Go・PCRE・POSIXで同じパターンがなぜ壊れるのか — 方言差・後読み・Unicode・アンカーの落とし穴と移植可能な正規表現の原則を実用的に分析する

2026-06-30 開発・インフラ

はじめに：正規表現はなぜ「どこでも」動かないのか

正規表現（regex）はソフトウェア開発者が必ず遭遇するツールだ。ログ解析、入力バリデーション、設定ファイルの処理、テキスト検索——どこにでも登場する。ところが、Pythonスクリプトで完璧に動いていたパターンをGoのコードに貼り付けるとコンパイルエラーが出る。grepで正しくマッチするパターンがsedでは全く違う結果を返す。JavaScriptでUnicode文字が正規表現マッチングから消える。このような経験があるなら、原因は一つだ。

正規表現に単一の標準は存在しない。 POSIX BRE/ERE、PCRE、ECMAScript、PythonのreモジュールIW、GoのRE2——これらはすべて似ているように見えるが、文法、サポート機能、エンジン動作が微妙に、あるいは根本的に異なる方言（フレーバー）だ。2026年6月現在、この方言間の互換性問題は解消されていない。むしろGoやRustがRE2系に収束したことで、PCRE系パターンとの断絶がより明確になった。

この記事では各方言の違いを解説し、複数の環境で動作する移植可能な正規表現の原則をまとめ、よくある落とし穴とデバッグ方法を紹介する。最後に「正規表現をいつ使うべきか、いつ避けるべきか」というより根本的な問いに答える。

1. 正規表現方言の地図 — 何がどれだけ違うか

正規表現エンジンは大きく3つの系統に分かれる。POSIX系（BRE/ERE）、PCRE系（Perl、PHP、Python、Java、Ruby、.NET、JavaScript）、RE2系（Go、Rustのregexクレート）だ。これらの違いは文法の好みではなく、エンジン設計哲学の違いから生じている。

1.1 POSIX — 最も古い標準、最も誤解される

POSIXはBRE（Basic Regular Expression）とERE（Extended Regular Expression）の2つを定義する。grepとsedはデフォルトでBREモードを使用する。ここに重大な落とし穴がある：BREでは+, ?, (, ), |, {, }はデフォルトでリテラル文字だ。メタ文字として使うにはバックスラッシュが必要だ。ERE（grep -E、awk）では逆にこれらの文字がバックスラッシュなしでメタ文字となる。

# BRE (grepデフォルト) — バックスラッシュがメタ文字を有効化
grep '\(foo\)\+' file.txt      # 'foo'の1回以上の繰り返し
grep '(foo)+' file.txt         # リテラル文字列'(foo)+'を検索 — 意図と異なる！

# ERE (grep -E) — バックスラッシュなしでメタ文字
grep -E '(foo)+' file.txt      # 'foo'の1回以上の繰り返し（正しい）
grep -E '\(foo\)+' file.txt    # リテラル'\(foo\)+'を検索 — 逆転！

エスケープルールがBREとEREで逆転している。シェルパイプラインのバグの多くがこの混同から生じる。またPOSIXは前読み（lookahead）、後読み（lookbehind）、名前付きグループを一切サポートしない。シンプルだが移植性は最も高い。

1.2 PCRE — 事実上の業界標準、しかし実装ごとに差異

PCRE（Perl Compatible Regular Expressions）はPhilip Hazelが1997年にPerlの正規表現を基に作成したライブラリだ。PHP、Python（reモジュール）、Ruby、Java、.NET、JavaScriptがこの系統に従う。前読み・後読み、名前付きグループ、原子グループ、非欲張り数量子、後方参照などの現代的な正規表現機能はここから来た。

ただし「PCRE系」も均一ではない。2026年6月現在の主な差異を示す。

Pythonの標準reモジュールは原子グループと所有的数量子をサポートしない。必要な場合はサードパーティのregexモジュールを使う。PHPでコンパイルできるパターンがPythonでは修正なしにコンパイルできないことがある。

1.3 RE2 — 線形時間保証のために諦めた機能

GoのregexpパッケージはGoogleが開発したRE2エンジンを使用する。RE2の設計原則は一つだ：O(n)線形時間保証。バックトラッキングの代わりにThompson NFAアルゴリズムを採用し、入力長に関わらず実行時間が線形以下であることを保証する。バックトラッキングなしに実装できない機能はRE2から除外されている。

  • 後読み（lookbehind） — (?<=...)、(?<!...)
  • 前読み（lookahead） — (?=...)、(?!...)
  • 後方参照 — \1、\2
  • 原子グループ、所有的数量子

PythonやJavaScriptで動作していた後読みパターンをGoに貼り付けると、regexp.Compile時点でエラーになる。これはバグではなく意図的な設計だ。2026年6月現在、EPFLの研究チームがRE2に線形時間後読みを追加する研究を発表したが、まだ公式RE2エンジンにマージされていない。GoではしばらくはlookbehindをNG前提で考えるべきだ。

一方で、RE2はReDoS（正規表現によるサービス拒否攻撃）が構造的に不可能だという重要な利点を持つ。

2. よくある落とし穴4つ — 実際に間違えやすい状況

2.1 後読み：PCREからGoへの移植でコンパイルエラー

最もよく見る移植失敗ケースだ。PythonでメールアドレスのドメインをマッチするのにUseを使っていたなら、このパターンはGoでは即コンパイルエラーになる。修正はキャプチャグループで書き直すことだ。

# Python — 後読みを使用
import re
m = re.search(r'(?<=@)[\w.]+', 'user@example.com')
# => 'example.com'

# Go — キャプチャグループで代替
re := regexp.MustCompile(`@([\w.]+)`)
m := re.FindStringSubmatch("user@example.com")
// m[1] => "example.com"

2.2 Unicode：JavaScriptのuフラグ漏れ

JavaScriptでuフラグなしの\wは[a-zA-Z0-9_]と同等だ。ひらがな、カタカナ、漢字、韓国語、アラビア文字などの非ASCII文字は\wにマッチしない。uフラグを付けるとUnicodeコードポイント単位で処理される。

// uフラグなし — 日本語が無視される
/\w+/g.exec('hello世界')  // => ['hello'] のみ

// uフラグあり — Unicodeプロパティエスケープ使用
/\p{L}+/gu.exec('hello世界')  // => ['hello', '世界'] 両方マッチ

// 絵文字のサロゲートペア問題
'😀'.length       // 2 (UTF-16サロゲートペア)
/^.$/.test('😀')  // false (uなし：2文字として扱う)
/^.$/u.test('😀') // true  (uあり：コードポイント単位)

2026年現在、全ての主要ブラウザとNode.jsがuフラグをサポートしている。多言語テキストを扱うすべての正規表現にuフラグを付けることを標準的な実践とすべきだ。

2.3 アンカー：言語によるマルチラインモードの違い

Pythonのre.MULTILINEフラグ、JavaScriptのmフラグを付けると、^は各行の先頭、$は各行の末尾をマッチする。フラグなしではそれぞれ文字列全体の先頭・末尾だ。またPythonでは$が末尾の改行の直前もマッチするのに対し、\Zは厳密に文字列末尾のみをマッチするという細かい違いがある。

# Python アンカーの動作差
text = "line1\nline2\nline3"
re.findall(r'^line\d', text)         # ['line1'] のみ
re.findall(r'^line\d', text, re.M)   # ['line1', 'line2', 'line3']

# 厳密な末尾マッチ
re.match(r'\d+$', '123\n')   # マッチ ($は改行前もOK)
re.match(r'\d+\Z', '123\n')  # マッチしない (\Zは厳密)

2.4 エスケープ：BRE/EREの逆転と言語レベルのダブルエスケープ

BRE/EREのエスケープ逆転はすでに説明した。言語レベルでも文字列リテラルの二重エスケープ問題がある。Pythonのr"..."（rawString）やGoのバッククオート`` `...` ``を使えばこの問題を回避できる。

# Python — rawStringで解決
re.match("\\d+\\.\\d+", "3.14")   # 動作するが読みにくい
re.match(r"\d+\.\d+", "3.14")     # rawStringで清潔に

# JavaScript — 正規表現リテラルが最適
new RegExp("\\d+\\.\\d+")  // 文字列：二重エスケープ必要
/\d+\.\d+/                 // リテラル：一回だけ

3. 移植可能な正規表現のための5つの原則

原則1：共通サブセットのみを使う

前読み・後読み、名前付きグループ、後方参照はPCRE系では動くがRE2とPOSIXでは動かない。移植性が重要なら、これらの機能なしでパターンを再設計する。後読みをキャプチャグループで代替し、コードロジックで後処理する。

原則2：フラグを明示的に指定する

マルチライン・Unicode・大文字小文字無視などを暗黙的なデフォルトに頼らず、常に明示的に指定する。JavaScriptではuフラグ、Pythonでは必要に応じてre.MULTILINEやre.UNICODEを明記する。

原則3：数量子の貪欲性を意識する

.*はデフォルトで貪欲（greedy）だ。HTMLのような区切り文字がある構造では、貪欲な数量子が最後の閉じタグまでマッチしてしまう。.*?（非貪欲）や否定文字クラス[^<]*を使い、意図を正確に表現する。

原則4：パターンをドキュメント化する

正規表現は書いた時は理解できても、半年後には解読困難だ。Pythonのre.VERBOSEやPCREの(?x)でインラインコメントを追加する。または複雑なパターンを小さな部品に分けて変数に格納し、結合する。

# Python verboseモード
date_pattern = re.compile(r"""
    (?P<year>  \d{4})  # 4桁の年
    -
    (?P<month> \d{2})  # 2桁の月
    -
    (?P<day>   \d{2})  # 2桁の日
""", re.VERBOSE)

原則5：対象エンジンで直接テストする

regex101.comではPCRE2、ECMAScript、Python、Go、Javaの方言を選択して結果を確認できる。移植前に必ず対象エンジンモードでテストすること。Regexperはパターンを鉄道ダイアグラムで視覚化し、構造的な問題を直感的に見せてくれる。

4. ReDoS — 正規表現がサーバーを止める仕組み

PCRE系のバックトラッキングエンジンには構造的な弱点がある。ネストした数量子（(b+)+z）や重複する選択肢（(a|ab)+）のパターンに悪意を持って設計された短い入力を与えると、バックトラッキング回数が指数的に爆発してサーバーが停止する。これがReDoS（Regular Expression Denial of Service）だ。

# 脆弱なパターン — 細工された入力でバックトラッキング爆発
/^(b+)+z$/.test('bbbbbbbbbbbbbbbbc')   // 数十秒かかることも
/^(a*)*$/                              // ネストした数量子
/^(a|aa)+$/                            // 重複する選択肢

Cloudflareが2019年にReDoSで全世界のサービス障害を引き起こした事例は有名だ。防止策をまとめると以下の4点だ。

  • ネストした数量子(x+)+と重複する選択肢(a|ab)+を避ける
  • ユーザー入力の長さを正規表現処理前に厳格に制限する
  • GoのようなRE2エンジンを使用する（ReDoSが構造的に不可能）
  • regex101.comのデバッガでバックトラッキング回数を事前確認する

5. 正規表現を使うべき場面と避けるべき場面

5.1 正規表現が適している場面

  • シンプルな書式バリデーション：郵便番号、日付形式（YYYY-MM-DD）、電話番号パターン
  • ログからの固定パターン抽出：IPアドレス、タイムスタンプ、エラーコード
  • テキストエディターでの検索・置換：一括置換
  • レクサーの個別トークンパターン：字句解析の最初のステップ

5.2 正規表現が適していない場面

  • HTML/XMLの解析：HTMLは正規言語ではない。BeautifulSoup、lxml、DOM APIを使う
  • URLの分解：urllib.parseやURL APIが正確で安全
  • メールアドレスの完全検証：RFC 5322の完全実装は正規表現では困難。最小限の形式チェック後、実際の送信で確認するのが現実的
  • JSON/YAMLの解析：json.loads、yaml.safe_loadを使う。2026年にはLLM出力の解析でも正規表現は時代遅れ
  • ソースコードの解析：ASTパーサーを使う。正規表現では文字列リテラルや複数行構文を確実に処理できない
  • 単純な文字列検索：indexOf、containsが正規表現より速くて明確

6. 移植性チェックリスト

2026年6月現在、正規表現を移植する前に確認するリストだ。

  1. 前読み・後読み（(?=)、(?!)、(?<=)、(?<!)）を含むか — Goでは不可。キャプチャグループで書き直す
  2. 後方参照（\1、\2）を含むか — RE2では不可。コードロジックで分離
  3. POSIXモードはBREかEREか — grepとsedのデフォルトはBRE
  4. JavaScriptでuフラグがあるか — 多言語テキストには必須
  5. ネストした数量子・重複する選択肢があるか — ReDoSリスク
  6. ^/$にマルチライン動作が必要か — フラグを明示。Pythonでは厳密な末尾マッチに\Zを使う
  7. regex101.comで対象エンジンモードでテスト後にデプロイ

まとめ — 正規表現は方言であることを前提に使う

正規表現は単一の言語ではない。POSIX BRE、ERE、PCRE、ECMAScript、RE2——それぞれ異なるルールを持つ方言の集合体だ。2026年6月現在、この方言間の分断はむしろ明確になった。GoとRustがRE2系に収束し、ルックアラウンドや後方参照に依存したPCREパターンの直接移植が失敗するケースが増えている。

移植可能な正規表現の核心は、最小公倍数の機能だけを使うことだ。ルックアラウンドや後方参照なしでも、キャプチャグループとコードロジックで大半の作業を処理できる。高度な機能が必要なときは対象エンジンを明確に定め、そのエンジンでのみテストする。そして正規表現がそもそも適切なツールかどうかを先に問うべきだ。HTMLを解析したりURLを分解するのに正規表現を使うなら、それはすでに間違った道に入っている。

正規表現は狭く明確な問題に使うときが最も強い。その範囲を守れば、言語が変わっても落とし穴は少なくなる。
