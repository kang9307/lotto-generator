Here-Documents in Practice - Turning Expansion Off and On, and the Indentation Trap

One pair of quotes on the delimiter changes how the entire body is read. Every output below was actually run

2026-09-01 Dev & Infra

When a script has to write a ten-line config file, the gap between someone who reaches for ten echo calls and someone who reaches for a here-document is not a matter of taste. The moment one of those ten lines contains a double quote, the first approach collapses. Here-documents exist to take over that job, which makes how far the shell reaches into the body the whole of this syntax.

That boundary is set in exactly one place: whether the delimiter carries quotes. That one character decides the fate of $, backticks and backslashes at the same time. Most of the remaining traps either descend from it or collapse into the problem of a terminator that is never found.

Every output below was produced by actually running the code on Git Bash on Windows, GNU bash 5.2.37(1)-release (x86_64-pc-msys), and pasted as it came out. Where a comparison was useful I also ran it under the dash that ships in the same box, and noted the places where the two diverge.

Shell behaviour varies by implementation and version. The output here comes from the one combination named above, and the internal storage of a here-document and the handling of line endings in particular are places where MSYS and glibc Linux may differ. What I could not check is collected near the end.

The job a here-document takes over

There are several ways to build a multi-line string: repeat echo, embed newlines in a printf, or concatenate \n into one variable. All three stay comfortable only while the content has no quotes in it. Bring in a config file, some SQL or JSON, where quotes are part of the content, and the outer and inner quoting overlap into lines nobody can read.

# the moment quotes become part of the content
echo "{"                     # this is fine
echo "  \"name\": \"$app\","  # and it hurts from here on
echo "  \"debug\": false"
echo "}"

# the same thing as a here-document
cat <<EOF
{
  "name": "$app",
  "debug": false
}
EOF

This is exactly the spot a here-document fixes. Quotes inside the body carry no meaning at all, because the shell never splits those lines into words. Newlines survive verbatim and so does indentation. If the general quoting rules themselves are what feels shaky, Shell Quoting Rules comes first. This article deals only with the quotes attached to the delimiter, which is a completely different animal.

  • " and ' inside the body need no escaping. They are not treated as quotes
  • Newlines are preserved literally. There is never a reason to write \n
  • The body arrives as the command's standard input, not as arguments, so argument length limits do not apply
  • In exchange it occupies standard input, which collides with anything already using it. Section 7 covers that
  • EOF is the conventional delimiter but any word works. Pick one that cannot appear in the body

One character of quoting on the delimiter

If you take one thing from this article, take this. <<EOF and <<'EOF' read the same body in completely different ways. I put eight inputs in one file and ran it both ways.

name=world

# A: unquoted delimiter
cat <<EOF
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

# B: not one character of the body differs, only the delimiter is quoted
cat <<'EOF'
plain: $name
cmdsub: $(echo hi)
backtick: `echo hi`
backslash-dollar: \$name
backslash-n: \n
backslash-backslash: \\
tilde: ~
star: *
EOF

Three ways to switch it off

Single quotes are not the only option. The POSIX specification says the body is not expanded if any part of the delimiter word is quoted. So the three below all have the same effect, and I confirmed that all three switch expansion off under both bash 5.2.37 and dash.

  • <<'EOF' — the most common and the most visible. Use this one
  • <<"EOF" — double quotes switch it off just as completely. It looks like it should be half on, and it is not
  • <<\EOF — a single backslash does it too. Being short, it is the easiest to miss on a read

Expansions a here-document never does

The last two rows of the table are the ones people get wrong. Even in an unquoted here-document, word splitting, pathname expansion and tilde expansion do not happen. The body was never a word to begin with; it is treated as one block of text. What does happen is parameter expansion, command substitution and arithmetic expansion, with backslash following the same rules as inside double quotes.

  • So *.log in the body does not expand into a file list. That is convenient when you want the far side to expand it
  • ~/bin does not become a home path either. Use $HOME when you want the local value baked in
  • Spaces in the body survive untouched. Column alignment built from repeated spaces does not fall apart
  • Arithmetic expansion $(( )) is on. Write \$(( )) when the far side should do the arithmetic

When you want only half of it expanded

The request that comes up most often in practice is keep almost all of it literal and bake in a couple of current values. Use an unquoted here-document and block everything else with \$. It works, and the example below also shows why it turns ugly fast.

LOCAL_DIR=/tmp/demo

cat <<EOF
cd $LOCAL_DIR
for f in *.log; do
  echo "\$f"
done
total=\$(( 1 + 2 ))
echo "\$total \$HOME"
EOF
cd /tmp/demo
for f in *.log; do
  echo "$f"
done
total=$(( 1 + 2 ))
echo "$total $HOME"

Exactly one thing, $LOCAL_DIR, became a value. The problem is the ratio: five escapes across six lines. Push twenty lines through this way and you are carrying more than twenty backslashes, and missing a single one silently bakes in the wrong value.

  • Once the escape count passes three or four, flip the approach. Quote the delimiter and pass the values you need as arguments
  • Section 9 shows how to pass them. The idea is to funnel every locally expanded spot into a single "$1"
  • A middle form also exists: emit a few VAR=value lines first from an unquoted here-document, then continue the body from a quoted one
  • Either way the principle is the same. Keep the number of expanding spots small enough to count

The dash form strips tabs only

<<-EOF is known as the one that removes indentation. More precisely it removes leading tab characters only. That is what the POSIX wording says, and the same rule applies to the terminator line. Spaces are not in scope.

Tabs work

# the source as seen through cat -A. ^I is a tab
if true; then$
^Icat <<-EOF$
^I^Iline one$
^I^Iline two$
^IEOF$
fi$
echo "after: $?"$

# what it printed
line one
line two
after: 0

Spaces do not

One editor setting flips this. Here is the same file saved with four spaces instead of tabs.

# the source as seen through cat -A. not one tab in it
if true; then$
    cat <<-EOF$
        line one$
        line two$
    EOF$
fi$
echo "after"$

# what it printed
e2b.sh: line 7: warning: here-document at line 2 delimited by end-of-file (wanted `EOF')
e2b.sh: line 8: syntax error: unexpected end of file
exit=2

This one blew up as a syntax error because there was an fi waiting. That is the lucky case. With no enclosing block it goes by quietly, with no error at all. Section 5 looks at that side.

When the tab is the content

The specification says all leading tab characters are stripped, not just the ones you indented with. So if you emit content where tabs carry meaning through the dash form, those tabs go too. Makefile recipe lines are the classic case.

# the source (^I is a tab)
cat <<-EOF$
^Iall:$
^I^Igcc -o app main.c$
^IEOF$

# output — the recipe line lost its tab. this Makefile does not work
all:$
gcc -o app main.c$

# the same content without the dash
cat <<EOF$
all:$
^Igcc -o app main.c$
EOF$

# output — the tab survives
all:$
^Igcc -o app main.c$
  • The dash form is safe only when the content has no tabs. When it does, give up the indentation and push the body to column zero
  • Do not use the dash form when emitting Makefiles, TSV, or anything aligned with tabs
  • It runs head-on into the editor setting that converts tabs to spaces. Either carve out an exception for that one file or stop using the dash form
  • The alternative is writing the body flush left. It looks untidy but it does not depend on editor settings
  • Another alternative is emitting through an expanding form and stripping spaces with sed 's/^ *//'. Only when the content has no leading whitespace of its own

When the terminator is never found

The terminator line has three conditions: it must contain the delimiter and a newline, there must be no blanks between them, and unless you are using the dash form it must start at column zero. Break any one of them and the shell takes the rest of the file as body.

The failure arrives quietly

With no enclosing block there is not even a syntax error. Below is the space-indented dash form with commands following it.

# the source
cat <<-EOF$
    body line$
    EOF$
echo "THIS SHOULD PRINT"$
touch /tmp/demo/marker$

# what it printed
e2c.sh: line 5: warning: here-document at line 1 delimited by end-of-file (wanted `EOF')
    body line
    EOF
echo "THIS SHOULD PRINT"
touch /tmp/demo/marker
exit=0

# marker was never created
ls: cannot access '/tmp/demo/marker': No such file or directory

This is the most dangerous shape in the whole syntax. The exit status is 0, the warning goes only to standard error, and the commands that followed are printed as text instead of running. If your logging collects standard output alone, this is indistinguishable from a successful run. In CI the script goes green.

What exit statuses miss is covered in Shell Exit Codes and set -e. This particular accident is caught only by not discarding standard error.

Running the same space-indented file under dash produces a different message. You get only Syntax error: end of file unexpected (expecting "fi"), without the helpful bash sentence naming which line's here-document was waiting for which delimiter. When you need to diagnose, the bash warning is far more useful.

  • An invisible blank after the delimiter is a frequent cause. Use cat -A to see whether it is EOF$ or EOF $
  • If the delimiter word could plausibly appear in the body, use something like __CONFIG_END__ instead of EOF
  • Delimiter matching is case sensitive. I confirmed that eof, Eof, MARKERX and an indented MARKER inside the body were all ignored as terminators
  • If you use a generator that concatenates scripts, this breaks first. Run bash -n on the result to check syntax alone

Ordering with redirection and pipes

A here-document is a kind of redirection, so its ordering against other redirections on the same line invites the question. The answer is that the order does not matter. Both are processed before the command runs, and they touch different file descriptors.

# redirection first
cat > out1.txt <<'EOF'
one
two
EOF

# redirection last
cat <<'EOF' > out2.txt
one
two
EOF

# through a pipe — the body is input to the command on the left
cat <<'EOF' | tr 'a-z' 'A-Z'
alpha
beta
EOF
out1.txt:
one
two

out2.txt:
one
two

ALPHA
BETA

All three do what they look like. Which one reads better is not open, though. Put the redirection first and the command line alone tells you where the output goes. Put it last and > out.txt only appears after ten lines of body.

  • Two here-documents on one line also work. The bodies are read in the order written, starting on the next line
  • There is one confusing point when mixing with pipes: the here-document feeds the command on the left, not the pipeline as a whole
  • For commands that demand a filename, use - or /dev/stdin, or wrap it in process substitution <(...)
  • Process substitution creates a subshell. Why variables changed in there do not survive outside is in Why Variables Vanish Inside a Piped while Loop

It eats standard input

A here-document is syntax for filling standard input. Colliding with anything that was already using standard input is therefore scheduled. The most famous accident is ssh inside a loop. I reproduced it with a three-line list and a stand-in that reads standard input to the end.

printf 'host-a\nhost-b\nhost-c\n' > hosts.txt

# a stand-in that drains stdin whole, the way ssh does
drain() { echo "  [$1] draining stdin..."; cat > /dev/null; }

# 1. the naive version
while read -r h; do
  echo "visiting $h"
  drain "$h"
done < hosts.txt

# 2. block stdin for the inner command
while read -r h; do
  echo "visiting $h"
  drain "$h" < /dev/null
done < hosts.txt

# 3. feed the list on a different file descriptor
while read -r h <&3; do
  echo "visiting $h"
  drain "$h"
done 3< hosts.txt
=== 1. loop body drains stdin (the ssh problem) ===
visiting host-a
  [host-a] draining stdin...

=== 2. same loop, stdin closed for the inner command ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

=== 3. same loop, list fed on fd 3 instead ===
visiting host-a
  [host-a] draining stdin...
visiting host-b
  [host-b] draining stdin...
visiting host-c
  [host-c] draining stdin...

Case 1 processes the first line and stops. No error, and a normal exit status. This is the shape of a deploy script that touches one of three servers and reports success. Real ssh offers -n for exactly this, and ffmpeg and some package managers share the habit.

What is interesting is that attaching a here-document makes the problem disappear on its own. The here-document replaces that command's standard input, so the inner command cannot touch the outer list. Changing the same loop to drain "$h" <<EOF ... EOF processed all three lines.

  • The cause is always the same: the loop's input and the command's input are the same descriptor
  • Fix 1: add < /dev/null to the inner command. Shortest, and right when you are sure the inner command wants no input
  • Fix 2: feed the list on 3< and use read -r h <&3. This leaves standard input usable by the inner command
  • Fix 3: attach a here-document to the inner command. Natural when you were going to send it a script anyway
  • Fix 4: skip while read and fill an array first, then loop with for. Safest when the list is not large

Here-strings are for one line

<<< is the one-line relative of the here-document. It is a bash extension and is not in POSIX. Under dash it dies instantly with Syntax error: redirection unexpected. If portability matters, this is where the road forks.

# a here-string appends a newline
printf 'abc' | wc -c     # => 3
wc -c <<< 'abc'          # => 4

# no word splitting even unquoted
v='a b'
cat <<< $v      # => a b
cat <<< "$v"    # => a b
cat <<< '$v'    # => $v

# paired with read, no subshell is created
read -r first rest <<< "alpha beta gamma"
echo "first=$first rest=$rest"      # => first=alpha rest=beta gamma

# the pipe version keeps nothing
echo "alpha beta gamma" | read -r f2 r2
echo "f2=[$f2] r2=[$r2]"            # => f2=[] r2=[]

The third block is the real reason to reach for a here-string. With echo ... | read the read runs in a subshell and the variables evaporate, while a here-string is a redirection, so it creates no subshell. For the same reason while ... done <<< "$var" is safe.

  • One newline is appended at the end. Anywhere you count bytes, that single character changes the answer
  • Even an empty variable still contributes one newline. wc -l <<< "$empty" is 1, not 0
  • Word splitting does not happen even unquoted. Write "$v" anyway; the reader will not be sure otherwise
  • Multi-line values are fine. Feed $'one\ntwo\nthree' and wc -l returns 3
  • To switch off expansion, single-quote the value side. That is a different rule from delimiter quoting

Which side expands when you send it away

The reason ssh host bash -s <<EOF goes wrong is singular: the body is interpreted twice. Once when the local shell builds the here-document, and again when the remote shell reads that text as a script. Deciding which side does the expanding is the whole of this section. You can reproduce the same structure without a remote host by standing up a second shell with bash -c.

export TAG=local-tag

# A: unquoted delimiter — everything expands on this side
bash -c 'export TAG=remote-tag; exec bash -s' <<EOF
echo "TAG seen = \$TAG"
echo "TAG baked = $TAG"
echo "PID of the second shell = \$\$"
EOF

# B: quoted delimiter — everything expands over there
bash -c 'export TAG=remote-tag; exec bash -s' <<'EOF'
echo "TAG seen = $TAG"
echo "PID of the second shell = $$"
EOF

# C: pass only the values you need, as arguments
bash -c 'export TAG=remote-tag; exec bash -s -- "$1"' _ "$TAG" <<'EOF'
echo "argument from the local side = $1"
echo "value from the remote side  = $TAG"
EOF
=== A ===
TAG seen = remote-tag
TAG baked = local-tag
PID of the second shell = 1780

=== B ===
TAG seen = remote-tag
PID of the second shell = 1781

=== C ===
argument from the local side = local-tag
value from the remote side  = remote-tag

(for reference: the outer shell running this experiment had PID 1777)

The two lines in A are the summary of this section. \$TAG yielded the remote value remote-tag, while $TAG travelled across with the local value local-tag baked into the text. C is how you keep the two apart. The body has expansion off entirely, and local values enter only through the argument slots. The number of expanding spots drops to something you can see.

sudo has a slightly different grain. The common mistake there is sudo cat > /etc/some.conf <<'EOF'. The redirection is handled not by sudo but by the shell that invoked it, so the unprivileged side opens the file. I checked the same structure using a missing directory instead of a permission barrier.

cat > /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => e12.sh: line 3: /nonexistent_dir/x.conf: No such file or directory

tee /nonexistent_dir/x.conf <<'EOF'
payload
EOF
# => tee: /nonexistent_dir/x.conf: No such file or directory

Different parties raise the error. The first is the shell's message, carrying a script name and a line number; the second is tee speaking for itself. So when writing a file with elevated privileges, use sudo tee. The party opening the file moves under sudo.

  • When attaching a here-document to ssh, make the quoted delimiter your default. The blocking form should be the default, not the leaking one
  • If you need local values, pass them with bash -s -- "$v1" "$v2" and receive them remotely as $1 and $2
  • Once the remote script grows long, sending a file with scp and running it beats a here-document. Section 15 returns to this
  • For privileged writes, sudo tee file > /dev/null or sudo sh -c 'cat > file'. The first reads better
  • Either way, never forget that it is interpreted twice. Logging the actually-executed lines on the remote side speeds up diagnosis

Three idioms for writing a file

More than half of all here-document usage is writing files. I ran three forms that should produce the same result over the same body and compared hashes.

# 1. the most common form
cat > a.conf <<'EOF'
key = $VALUE
EOF

# 2. when you need privileges, or want it on screen too
tee b.conf > /dev/null <<'EOF'
key = $VALUE
EOF

# 3. with the shell alone, no external command
while IFS= read -r line; do printf '%s\n' "$line"; done <<'EOF' > c.conf
key = $VALUE
EOF
254b9d772669ad5fc3e7724fe7fe623e *a.conf
254b9d772669ad5fc3e7724fe7fe623e *b.conf
254b9d772669ad5fc3e7724fe7fe623e *c.conf

All three files are byte-identical. So what decides? The cat form reads far better, and reaching for form 3 to save one process is usually a loss. That said, both cat and tee are external commands, so in a minimal early-boot script where /bin is not there yet, form 3 becomes the only option.

  • Default to cat > file <<'EOF'. Add the quotes by reflex and remove them only when expansion is wanted
  • For privileges, sudo tee. Standard output leaks to the screen, so append > /dev/null
  • To append, cat >> file or tee -a. Whether that is safe on a second run is a separate question, covered in Idempotent Shell Scripts
  • To back up an existing file first, put a condition in front of the here-document. It is a redirection, so it works inside if unchanged
  • When the resulting file's mode matters, install -m 0644 /dev/stdin file <<'EOF' is worth knowing. It sets permissions as it creates

Capturing it into a variable trims the end

The idiom for capturing a here-document is var=$(cat <<'EOF' ... EOF ). There is a quiet loss in it: command substitution removes every trailing newline from the result. I measured four methods against a 19-byte body.

# the source is 19 bytes: "line one\nline two\n\n"

v=$(cat <<'EOF'
line one
line two

EOF
)

read -r -d '' v2 <<'EOF'
line one
line two

EOF

IFS= read -r -d '' v3 <<'EOF'
line one
line two

EOF

mapfile -t arr <<'EOF'
line one
line two

EOF
=== the source text is 19 bytes ===
19

$(cat <<EOF)        exit=0 bytes=17
read -r -d ''       exit=1 bytes=17
IFS= read -r -d ''  exit=1 bytes=19
mapfile -t          elements=3

What to read in those four lines

The first line is as expected: two newlines gone, 17 bytes. The second line is the trap. read -r -d '' is the form people reach for to keep newlines, yet without emptying IFS it also lands on 17 bytes. read trims IFS whitespace from both ends of the last field, and the default IFS contains a newline. Only the third line held all 19 bytes.

And both the second and the third return exit status 1. The delimiter was set to the null character and the input contains no null, so read reports that input ended before the delimiter arrived. It does that even though the value landed correctly. With errexit on, the script dies right here.

( set -e; read -r -d '' z <<'EOF'
payload
EOF
echo "NEVER REACHED" )
# => subshell exit code = 1   (the echo never ran)

( set -e; read -r -d '' z <<'EOF' || true
payload
EOF
echo "reached, z=[$z]" )
# => reached, z=[payload]
# => subshell exit code = 0

  • read trims leading whitespace too. read -r a b <<< " x y " gives a=[x] b=[y]
  • On the same input, IFS= read -r c yields c=[ x y ] with the spaces intact. That is why IFS= belongs there by habit
  • Drop -r and backslashes get eaten as escapes. You can carry a backslash safely through the here-document and then lose it at read
  • Block the exit status of 1 with || true. read ... ; : works too but shows the intent less clearly
  • mapfile needs bash 4 or later and does not exist in dash. Drop it from the shortlist when portability matters

Inside functions, two on one line

The body of a here-document starts on the line after the one carrying the operator, not immediately after the operator. That rule is what makes two here-documents on one line possible, and what lets another command follow a here-document.

# inside a function — local variables expand normally
emit() {
  local target=$1
  cat <<EOF
[unit]
target=$target
EOF
}
emit alpha

# unchanged inside if, and inside case
if [ -n "$HOME" ]; then
  cat <<'EOF'
inside an if
EOF
fi

# two on one line — bodies are read in the order written, from the next line
diff <(cat <<'A'
same
left
A
) <(cat <<'B'
same
right
B
)

# chaining a command after a here-document
cat <<'EOF' ; echo "<- this ran after the heredoc"
body of the heredoc
EOF
[unit]
target=alpha
---
inside an if
---
2c2
< left
---
> right
diff exit=1
---
body of the heredoc
<- this ran after the heredoc

The last block shows the rule best. ; echo ... sits on the same line as the here-document operator, yet it was not swallowed into the body and it ran after the body ended. The shell reads that line to its end and parses it as a command, then collects the body starting on the next line.

  • The indentation problem is the same inside a function. To indent the terminator with the function body you need the dash form plus tabs
  • Inside case, the ;; must come on the line after the terminator. Put it on the same line and the delimiter stops matching
  • You can attach a separate here-document to each stage of a pipeline. That is also the point where the reader gets lost
  • The delimiter word inside the body is harmless anywhere but column zero. xEOF or an indented EOF is just body text

Pipe or temporary file

Where a here-document body actually lives on its way to the command is not fixed by the specification; the implementation decides. Looking at the standard input of a running command on bash 5.2.37, you can see it split by size.

# a small body
ls -l /proc/self/fd/0 <<'EOF'
payload
EOF
# => /proc/self/fd/0 -> pipe:[8589943248]

# a large body (about 350KB)
# => /proc/self/fd/0 -> /tmp/sh-thd.6MTpiD (deleted)

# narrowing down the boundary
body=65000    pipe:[4294982180]
body=66000    /tmp/sh-thd.ib1lXH (deleted)
body=70000    /tmp/sh-thd.NCKE8B (deleted)

A small body is handed over through a pipe, and once it exceeds the pipe capacity it becomes a temporary file with its name already unlinked. The boundary sat between 65,000 and 66,000 bytes, which matches the 64KiB default pipe buffer on Linux. Older bash used a temporary file regardless of size; the pipe behaviour arrived comparatively recently.

Two things catch you in practice. A program that rewinds and reads standard input twice fails on the pipe. And a full or read-only temporary directory breaks a large here-document.

I saw one odd thing near the boundary. At exactly 65,536 and 65,537 bytes of body, this build of bash hangs forever. I reproduced it twice under an eight-second limit. Anything larger falls through to a temporary file and works. It is a very narrow window and it looks related to how MSYS reports pipe capacity, but whether other environments behave the same I could not check.
  • For large payloads, writing a file and passing the path is more predictable than a here-document
  • For a tool that must re-read standard input, give it a real file instead of /dev/stdin
  • Seeing (deleted) on the temporary file name is normal. It is unlinked immediately so no other process can open it
  • For the same reason a here-document body is not exposed through ps or the command line. That is why it beats arguments for passing secrets
  • Still, the temporary path exists for a moment, so real secrets are better kept small enough to stay in the pipe range

Where it collides with strict mode

If you have the habit of putting set -euo pipefail at the top of a script, there are places where it meets here-documents. Two of them.

# 1. set -u against an unquoted here-document
( set -u; cat <<EOF
value = $DEFINITELY_NOT_SET
EOF
)
# => e12.sh: line 14: DEFINITELY_NOT_SET: unbound variable
# => unquoted exit=1

( set -u; cat <<'EOF'
value = $DEFINITELY_NOT_SET
EOF
)
# => value = $DEFINITELY_NOT_SET
# => quoted exit=0

# 2. an unbalanced backtick
cat <<EOF
a `oops
EOF
# => bash: line 1: bad substitution: no closing "`" in `oops
# => exit=1

cat <<'EOF'
a `oops
EOF
# => a `oops
# => exit=0

The first is a welcome failure, really. When you typo the name of a variable meant for the far side, it stops here instead of silently baking in an empty string. The second is a nuisance. Put a command example or some Markdown in the body and one unbalanced backtick kills the script. Both disappear once the delimiter is quoted.

  • When the body contains code examples, regular expressions, Markdown or Windows paths, a quoted delimiter is almost always right
  • What collides with set -e is the read -r -d '' from section 11. Do not forget the || true
  • If you must use an unquoted here-document under set -u, defend with ${VAR:-default}
  • When diagnosing, bash -n script.sh checks syntax alone and catches a good share of terminator problems before execution
  • bash -x does not print here-document bodies in its trace. Dumping the body once through cat is quicker for checking

When not to use a here-document

Once here-documents feel comfortable, everything starts looking like one. The cases below are better served by something else. The test is simple: does the body outlive the script?

  • Past thirty lines of body, put it in a separate file. The logic gets buried in the body when you read the script, there is no syntax highlighting, and you cannot lint that file on its own
  • Past five substitution points, use a template tool. envsubst is often already present and can restrict which names it substitutes
  • When several scripts share the same body, move it to a file. Copies of a here-document drift apart slowly
  • When generating JSON or YAML, look first at whether values can carry special characters. The moment user input is in the mix, a here-document takes no responsibility for escaping. jq -n or yq is the right tool
  • When the remote script grows long, ship the file and run it. The doubly-interpreted stretch disappears, and on failure the file is still there to reproduce with
  • For a single line, skip the here-document. printf '%s\n' '...' or a here-string is shorter
  • Conversely, a ten-line config file, a short script sent to a remote host, text full of quotes is exactly where a here-document belongs

What I Could Not Verify

  • Every output here came from bash 5.2.37 on MSYS. Whether all of it is identical on the same version under glibc Linux I could not check. The pipe-versus-temporary-file boundary and the hang around 65,536 bytes in particular are things I cannot say reproduce elsewhere
  • Running a CRLF-saved script on this build, the here-documents worked and no carriage returns showed up in the output. That is most likely how MSYS reads files, and I would not expect the same result under glibc Linux
  • The only comparison shell was the dash in the same box. zsh, ksh and BusyBox ash were not installed, so I could not run them
  • Package information for dash was not available, so I could not record its exact version number
  • The sudo discussion was checked with a nonexistent directory rather than an unwritable one. The structure of who handles the redirection is the same, but I did not confirm the message in a real permission-denied case
  • Remote execution was reproduced with a second shell stood up by bash -c, not real ssh. The interpreted twice structure is identical, but the extra quoting problems that come from how ssh joins arguments before handing them to the remote shell are not covered
