GitHub 스택 PR 공개 프리뷰 - 큰 변경을 쌓아서 나누면 무엇이 달라지나

층을 쌓는 것은 쉽다. 아래가 바뀌었을 때 위를 다시 맞추는 것이 어렵다

2026-08-01 개발/인프라

서론: 파일 40개짜리 PR 앞에서 리뷰가 멈춘다

PR 하나에 파일 40개가 들어갔다. 스키마 변경, 그 스키마를 쓰는 조회 계층, 그 계층을 부르는 API 엔드포인트, 그리고 그 김에 정리한 설정 파일까지 한 덩어리다. 리뷰어가 열었다가 닫았다. 사흘째 승인이 없다. 재촉하면 「내일 보겠다」는 답이 온다. 저자는 그동안 다음 작업을 이 브랜치 위에 얹기 시작한다. 이 시점에 문제는 리뷰어의 성실함이 아니라 리뷰가 불가능한 형태로 일이 도착했다는 것이다.

2026년 7월 30일 GitHub이 스택 PR을 공개 프리뷰로 열었다. 큰 변경을 층으로 쌓아 층마다 따로 리뷰받게 하는 기능이다. 그런데 이 글의 관심은 「새 기능이 나왔다」가 아니다. 브랜치를 이어 붙이는 일은 원래 로컬 git으로 되던 것이고, 실제로 아래에서 직접 만들어 보인다. 발표된 것은 개념이 아니라 그 개념을 유지하는 데 드는 반복 작업을 플랫폼이 대신 해 준다는 부분이다.

그래서 이 글이 던지는 질문은 하나다. 큰 변경을 나누는 비용을 도구가 얼마나 줄여 주는가. 쌓기의 진짜 어려움은 층을 만드는 데 있지 않다. 아래가 바뀔 때마다 위를 다시 맞추는 일에 있다. 그 작업을 로컬 git으로 그대로 돌려서, 어디가 아프고 무엇이 자동화되는지 출력으로 보인다.

실행 환경. 아래 git 출력은 전부 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. git 2.48.1.windows.1, 셸은 GNU bash 5.2.37 (MSYS2/MinGW64)다. 명령은 히어독이 아니라 파일로 저장해 실행했고, 예제 저장소는 임시 디렉터리에 새로 만든 것이다. 브랜치 이름과 파일 이름은 전부 가상의 예제다.

이 글이 다루지 않는 것. PR을 여는 법과 리뷰 기본기는 Pull Request와 코드 리뷰에 있다. 「오픈 PR 개수에 상한을 걸면 대기가 줄어드는가」라는 큐 동역학 문제는 PR 상한과 큐의 동역학에서 시뮬레이션으로 다뤘다. 이 글은 한 건의 크기를 나누는 방법만 본다. 브랜치 전략 자체는 브랜치 전략에 있다.

1. 무엇이 발표됐나 - 확인한 범위의 사실만

공식 문서와 체인지로그를 직접 열어 확인한 내용만 적는다. 요약 기사나 커뮤니티 글로 기능을 단정하지 않았다.

  • 발표일과 상태. GitHub 체인지로그 2026년 7월 30일 자 항목이 스택 PR의 공개 프리뷰를 알렸다. 전 저장소 대상 롤아웃이 「며칠에 걸쳐」 진행된다고 적혀 있다
  • 정의. 체인지로그의 문장은 「큰 변경을 작고 리뷰 가능한 PR들로 쪼갠다」이고, 「변경의 초점 잡힌 층들을 각각 담당하는 순서 있는 PR 묶음」이라고 설명한다
  • 구조 규칙. 문서는 맨 아래 PR이 기본 브랜치를 향하고, 그 위 각 PR은 바로 아래 브랜치를 향한다고 적었다. 그리고 「한 층의 코드가 다른 층의 코드에 의존한다면 그 의존 대상은 같은 브랜치이거나 더 아래 브랜치에 있어야 한다」는 원칙을 제시한다
  • 다룰 수 있는 곳. github.com, GitHub CLI, 모바일 앱이다. CLI 확장은 gh extension install github/gh-stack으로 설치하고, 문서에 등장하는 하위 명령은 gh stack init, gh stack add, gh stack submit, gh stack rebase, gh stack push다
  • 웹에서 만드는 법. 각 PR의 기준 브랜치를 바로 아래 PR의 브랜치로 지정한 뒤 스택 생성 항목을 고르는 방식도 문서에 있다
  • 제약. 모든 브랜치가 같은 저장소에 있어야 하고 포크를 가로지르는 스택은 지원하지 않는다. GitHub Desktop에서는 지원되지 않는다. 자동 머지는 지원되지 않는다. 스택 브랜치들 사이에 완전한 선형 이력이 필요하다
  • 머지 큐. 문서는 스택이 머지 큐를 완전히 지원하며 올바른 순서로 큐에 들어간다고 적었고, 스택을 한 덩어리로 유지하려고 머지 그룹이 설정된 최대 크기를 최대 50퍼센트까지 초과하도록 허용한다고 밝혔다. 그 여유로도 부족하면 연속된 머지 그룹으로 쪼개진다. 다만 체인지로그는 머지 큐 지원이 「몇 주에 걸쳐」 순차 적용된다고 했으므로, 이 부분은 저장소마다 도달 시점이 다를 수 있다

프리뷰 시점 명시. 문서에 「이 기능은 공개 프리뷰이며 변경될 수 있다」는 문구가 그대로 적혀 있다. 이 글은 2026년 8월 1일 기준으로 확인한 내용이다. 화면 구성, 하위 명령 이름, 제약 목록은 정식 출시 전에 바뀔 수 있으니 도입 결정 전에 반드시 원문을 다시 확인하라.

열지 못한 것 / 열지 않은 것. 검색 결과에 나온 커뮤니티 토론 글, 로드맵 이슈, gh-stack 저장소 페이지, 빠른 시작 문서, 조직 롤아웃 튜토리얼은 열지 않았다. 그래서 그 문서들에만 있는 내용은 이 글에 없다. 아래 「참고 자료」에는 실제로 열어 읽은 다섯 곳만 적었다.

2. 왜 큰 PR이 문제인가 - 수치가 아니라 구조로

「큰 PR은 리뷰가 안 된다」는 말은 흔하지만, 그 이유를 통계로 설명하려 들면 대체로 남의 숫자를 옮기게 된다. 여기서는 숫자를 쓰지 않고 구조로만 본다. 리뷰는 읽고, 문맥을 머리에 유지하고, 판단하는 세 단계다. PR이 커질 때 이 셋이 같은 속도로 커지지 않는다.

  • 읽을 양은 선형으로 는다. 파일이 두 배면 읽는 시간도 대체로 두 배다. 여기까지는 견딜 만하다
  • 유지해야 할 문맥은 그보다 빨리 는다. 40번째 파일을 볼 때 리뷰어는 앞의 39개가 무엇을 바꿨는지 기억하고 있어야 한다. 「이 함수 시그니처가 바뀐 게 맞나」를 확인하려면 위로 스크롤해서 다시 찾아야 하고, 그 왕복이 파일 수에 따라 늘어난다
  • 판단의 단위는 반대로 커진다. 리뷰 승인은 PR 단위로만 가능하다. 40개 중 39개가 완벽하고 하나가 미심쩍으면 전부가 대기 상태가 된다. 좋은 부분이 나쁜 부분에 인질로 잡힌다
  • 수정이 들어오면 전부 다시 본다. 저자가 지적을 반영해 푸시하면 리뷰어는 「무엇이 바뀌었는지」를 다시 찾아야 한다. PR이 클수록 그 재확인 비용이 크고, 그래서 두 번째 리뷰가 느슨해진다
  • 되돌리기 단위가 리뷰 단위와 같다. 배포 후 문제가 나면 되돌릴 수 있는 최소 단위는 그 PR 전체다. 스키마 변경 때문에 API 엔드포인트까지 함께 사라진다
  • CI가 전부 아니면 전무로 움직인다. 40개 파일 중 한 곳의 린트 오류가 전체 파이프라인을 빨갛게 만든다. 나머지 39개가 통과했다는 사실은 아무 힘이 없다

정리하면 큰 PR의 문제는 리뷰의 최소 단위와 변경의 최소 단위가 강제로 같아진다는 것이다. 쌓기는 이 둘을 떼어놓으려는 시도다. 변경은 크게 하되, 리뷰와 승인과 되돌리기는 층 단위로 한다.

한 가지는 분명히 해 두자. 나누기는 리뷰 용량을 늘리지 않는다. 한 주에 팀이 소화할 수 있는 변경의 총량을 정하는 것은 리뷰어의 시간이지 PR을 자르는 방식이 아니다. 상한 규칙이 대기를 줄이지 못하는 이유를 앞 글에서 큐로 다뤘는데, 여기서도 같은 선이 유지된다. 스택이 바꾸는 것은 총량이 아니라 한 건당 시간과 부분 통과 가능성이다.

3. 쌓기란 무엇인가 - 로컬 git으로 직접 만든다

정의는 한 줄이다. 브랜치의 기준을 트렁크가 아니라 바로 아래 브랜치로 잡는 것. 그러면 각 브랜치의 변경 화면에는 아래에서 이미 한 일이 빠지고 그 층이 새로 한 일만 남는다. 특별한 도구 없이 만들어진다.

$ git switch -c stack/1-db   main          # 1층: DB 연결 풀 설정
$ git switch -c stack/2-repo stack/1-db    # 2층: 조회 계층 (1층 위에)
$ git switch -c stack/3-api  stack/2-repo  # 3층: API 엔드포인트 (2층 위에)

이렇게 만든 저장소를 들여다보면 이렇다.

git version 2.48.1.windows.1 / MINGW64_NT-10.0-19045

=== 1-2. the stack as one line of history ===
* 3f0f26a (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 50bdde2 (stack/2-repo)          feat(repo): order lookup, raise pool size
* cb5f977 (stack/1-db)            feat(db): add connection pool config

=== 1-3. what each branch points at ===
main          78b0629  chore: bootstrap trunk
stack/1-db    cb5f977  feat(db): add connection pool config
stack/2-repo  50bdde2  feat(repo): order lookup, raise pool size
stack/3-api   3f0f26a  feat(api): GET /orders/:id

세 브랜치가 한 줄 위의 서로 다른 지점을 가리키고 있다. 이것이 스택의 전부다. 갈라진 가지가 아니라 한 줄에 찍힌 눈금이다. 이제 각 층의 리뷰 단위를 보자.

=== 1-4. the REVIEW UNIT of each layer (diff vs the layer below) ===
--- base=main          head=stack/1-db
 db.yml | 3 +++
 1 file changed, 3 insertions(+)
--- base=stack/1-db    head=stack/2-repo
 db.yml  | 2 +-
 repo.py | 2 ++
 2 files changed, 3 insertions(+), 1 deletion(-)
--- base=stack/2-repo  head=stack/3-api
 api.py | 2 ++
 1 file changed, 2 insertions(+)

=== 1-5. what ONE big PR would have looked like (main..top) ===
 api.py  | 2 ++
 db.yml  | 3 +++
 repo.py | 2 ++
 3 files changed, 7 insertions(+)

같은 작업이다. 통합해서 보면 파일 3개에 7줄 추가이고, 층으로 보면 파일 1개, 2개, 1개로 갈린다. 예제라 규모가 작지만 비율은 그대로 커진다. 파일 40개짜리가 12개, 20개, 8개로 갈리면 세 사람이 병렬로 볼 수 있고, 1층은 오늘 승인될 수 있다.

3.1 층을 어디서 자르는가 - 이것만은 도구가 못 한다

문서의 의존성 원칙을 다시 읽어 보면 자르는 기준이 나온다. 한 층의 코드가 의존하는 대상은 같은 층이거나 더 아래에 있어야 한다. 이 조건을 만족하도록 자르는 일이 쌓기의 유일한 창작 부분이고, 도구가 대신해 주지 않는다.

  • 기술 방향으로 자른다. 저장소 → 서비스 → 컨트롤러처럼 호출 방향이 아래에서 위로 가게 놓는다. 위가 아래를 부르고 아래는 위를 모른다
  • 「준비」와 「본작업」을 가른다. 이름 바꾸기, 파일 옮기기, 포맷 정리처럼 동작이 안 바뀌는 변경을 맨 아래 층으로 뺀다. 이 층은 읽기가 쉬워서 빨리 승인된다
  • 기능 플래그를 맨 위로. 스위치를 켜는 커밋을 마지막 층에 두면 아래 층들은 무해한 상태로 먼저 배포될 수 있다
  • 서로를 참조하는 두 덩어리는 자르지 않는다. A가 B를 부르고 B도 A를 부르면 순서를 정할 수 없다. 이런 것은 한 층에 둔다
  • 테스트는 그 층에 붙인다. 테스트를 마지막 층에 몰면 아래 층 CI가 의미를 잃는다
  • 층 수는 적게. 층이 늘어날수록 아래가 흔들릴 때 다시 맞출 대상이 늘어난다. 다음 절이 그 비용을 보여 준다

4. 아래가 바뀌면 위가 흔들린다 - 리베이스와 충돌, 그리고 되돌리기

여기가 쌓기의 실제 비용이다. 리뷰어가 1층에 지적을 하나 남겼다고 하자. 연결 풀 크기가 너무 작다는 지적이고, 저자는 1층에 커밋 하나를 더 얹는다. 그 순간 무슨 일이 일어나는지 보자.

=== 2-1. reviewer asks the bottom layer to change: pool size 5 -> 10 ===
stack/1-db moved: cb5f977 -> 63509a2

=== 2-2. the layers above are now stale ===
* 63509a2 (HEAD -> stack/1-db)  fix(db): pool size 5 -> 10 per review
| * 3f0f26a (stack/3-api)        feat(api): GET /orders/:id
| * 50bdde2 (stack/2-repo)       feat(repo): order lookup, raise pool size
|/
* cb5f977                        feat(db): add connection pool config

한 줄이던 이력이 갈라졌다. 2층과 3층은 여전히 옛 1층 위에 매달려 있다. 이 상태로 두면 2층의 PR 화면에는 아래에서 방금 고친 내용이 반영되지 않고, CI도 낡은 기준으로 돈다. 위 층들을 새 1층 위로 옮겨야 한다.

4.1 바로 위 층을 옮기다가 충돌하는 지점

$ git switch stack/2-repo
$ git rebase stack/1-db
Auto-merging db.yml
CONFLICT (content): Merge conflict in db.yml
error: could not apply 50bdde2... feat(repo): order lookup, raise pool size
hint: Resolve all conflicts manually, mark them as resolved with
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
rebase exit code: 1

--- status while stopped ---
UU db.yml
A  repo.py

--- the conflicted file ---
pool:
<<<<<<< HEAD
  size: 10
=======
  size: 20
>>>>>>> 50bdde2 (feat(repo): order lookup, raise pool size)
  timeout: 30

충돌이 났다. 왜 났는지가 중요하다. 1층이 그 줄을 5에서 10으로 고쳤고, 2층도 원래 같은 줄을 5에서 20으로 고치는 커밋이었다. 리베이스는 2층의 커밋을 새 1층 위에 다시 적용하려 하는데, 기준이 되는 줄이 이미 바뀌어 있어 자동으로 결정할 수 없다.

  • 충돌은 층이 같은 파일의 같은 줄을 건드릴 때만 난다. 층을 기술 방향으로 잘 잘랐다면 대부분의 리베이스는 조용히 끝난다
  • 충돌 표시에서 HEAD 쪽이 새 기준(아래 층)이고 아래쪽이 지금 적용 중인 커밋(위 층)이다. 평소의 머지와 위아래가 반대로 느껴지는 지점이라 자주 틀린다
  • 멈춘 동안 저장소는 중간 상태다. .git/rebase-merge 디렉터리가 존재하는지로 확인할 수 있다
  • 층이 세 개면 이 일이 최대 두 번 일어난다. 층 수가 곧 반복 횟수다

4.2 되돌리는 방법 - 세 가지 탈출구

충돌 앞에서 당황할 필요가 없는 이유는 되돌리기가 완전히 보장되기 때문이다. 실제로 되돌려 봤다.

=== 2-4. escape hatch: abort puts everything back ===
$ git rebase --abort
after abort, stack/2-repo = 50bdde2
db.yml on stack/2-repo:
pool:
  size: 20
  timeout: 30

=== 2-9. undoing a FINISHED rebase (reflog) ===
a4f0a88 stack/3-api@{0}: rebase (finish): refs/heads/stack/3-api onto 8e137ce
3f0f26a stack/3-api@{1}: commit: feat(api): GET /orders/:id
50bdde2 stack/3-api@{2}: branch: Created from stack/2-repo

$ git reset --hard stack/3-api@{1}    # 리베이스 직전 상태로 정확히 복귀

세 가지를 구분해 두면 된다.

  • 진행 중이면 git rebase --abort. 브랜치가 시작 지점으로 정확히 돌아간다. 위 출력에서 50bdde2로 복귀했고 파일 내용도 원래대로였다
  • 이미 끝났으면 git reflog. 리베이스 전 위치가 @{1}에 남아 있다. git reset --hard로 그 지점으로 되돌린다
  • ORIG_HEAD도 같은 용도다. 리베이스 직전 위치를 가리키므로 git reset --hard ORIG_HEAD가 짧게 쓰인다. 다만 다른 명령이 덮어쓰므로 리플로그가 더 안전하다
  • 중요한 전제. 이 되돌리기는 로컬에서만 무해하다. 이미 원격에 강제 푸시했다면 다른 사람이 받아 간 이력이 어긋난다. 스택 브랜치는 본인만 푸시한다는 합의가 필요하다

4.3 그 위 층은 시작점을 직접 지정해야 한다

2층을 옮기고 나면 3층이 문제다. 3층은 옛 2층을 가리키고 있어서 단순 리베이스로는 엉뚱한 커밋까지 끌고 온다.

=== 2-6. layer 3 still points at the OLD layer 2 ===
layer3 does NOT contain the new layer2 -> must rebase too

=== 2-7. rebase layer 3 with --onto (old base -> new base) ===
$ git rebase --onto stack/2-repo 50bdde2 stack/3-api
Successfully rebased and updated refs/heads/stack/3-api.

=== 2-8. the stack is one line again ===
* a4f0a88 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 8e137ce (stack/2-repo)          feat(repo): order lookup, raise pool size
* 63509a2 (stack/1-db)            fix(db): pool size 5 -> 10 per review
* cb5f977                         feat(db): add connection pool config

git rebase --onto 새기준 옛기준 대상의 세 인자가 각각 어디로, 어디서부터, 무엇을이다. 옛 2층 커밋 해시를 손으로 적어 넣어야 한다는 점에 주목하라. 층이 다섯이면 이 손작업이 네 번이고, 해시를 하나 잘못 적으면 커밋이 사라지거나 중복된다. 여기가 사람이 실수하는 자리이고, 도구가 노리는 자리다.

5. 스택 전체를 한 번에 옮기기 - update-refs

git 자체에도 이 반복을 줄이는 장치가 있다. git rebase -h가 「리베이스 대상 커밋을 가리키는 브랜치들도 함께 갱신한다」고 설명하는 --update-refs다. 없을 때와 있을 때를 같은 상황에서 돌려 비교했다. 상황은 트렁크가 앞으로 나간 경우, 즉 다른 사람의 PR이 먼저 머지된 흔한 상황이다.

=== 3-1. WITHOUT --update-refs ===
before:  main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6d241f4
$ git switch stack/3-api
$ git rebase main
after:   main 5ea68a0   1-db 9b331dc   2-repo a08d522   3-api 6204587

* 6204587 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* 483c62e                        feat(repo): order lookup
* b422809                        feat(db): add connection pool config
* 5ea68a0 (main)                 chore: bump trunk
| * a08d522 (stack/2-repo)       feat(repo): order lookup
| * 9b331dc (stack/1-db)         feat(db): add connection pool config
|/
* c2562b8                        chore: bootstrap trunk

이것이 스택이 조용히 부서지는 모습이다. 3층은 새 트렁크 위로 잘 옮겨졌는데 1층과 2층 브랜치는 옛 트렁크에 그대로 남았다. 이 상태로 푸시하면 1층 PR과 2층 PR은 옛 코드를 리뷰하게 되고, 3층 PR의 변경 화면에는 아래 층들이 이미 한 일이 다시 등장한다. 층을 나눈 의미가 사라진다.

=== 3-2. WITH --update-refs, same situation ===
before:  main ebfef49   1-db 7862785   2-repo d8b3ddc   3-api 79b45bc
$ git rebase --update-refs main
Rebasing (1/5)(2/5)(3/5)(4/5)(5/5)
Successfully rebased and updated refs/heads/stack/3-api.
Updated the following refs with --update-refs:
    refs/heads/stack/1-db
    refs/heads/stack/2-repo
after:   main ebfef49   1-db 469e32a   2-repo cd35dca   3-api a807932

* a807932 (HEAD -> stack/3-api)  feat(api): GET /orders/:id
* cd35dca (stack/2-repo)          feat(repo): order lookup
* 469e32a (stack/1-db)            feat(db): add connection pool config
* ebfef49 (main)                  chore: bump trunk
* 153d615                         chore: bootstrap trunk

=== 3-3. make it the default for this repo ===
$ git config rebase.updateRefs true
plain 'git rebase main' now moves every layer   exit code: 0

한 줄이 유지됐고 중간 층 브랜치들이 함께 이동했다. git이 「다음 참조들을 갱신했다」고 직접 알려 준다. rebase.updateRefs를 참으로 두면 평범한 git rebase main에도 같은 동작이 적용된다.

이 절이 이 글의 핵심이다. 쌓기의 개념은 3절에서 이미 끝났다. 명령 세 줄이면 만들어진다. 그런데 4절에서 본 손작업 — 옛 해시를 찾아 --onto에 넣는 일 — 이 층 수만큼 반복된다. 도구의 가치는 개념을 제공하는 데 있지 않고 이 반복을 없애는 데 있다. --update-refs가 로컬에서 그 일을 하고, 플랫폼 기능은 여기에 리뷰 화면과 승인 규칙과 머지 순서를 연결하는 것을 더한다. 그래서 도구가 있어도 어디서 자를지 정하는 판단은 여전히 사람 몫이다.

5.1 상황별 갱신 명령과 되돌리기

상황쓰는 명령주의점되돌리기
바로 위 층 하나만 옮김git rebase 아래층같은 줄을 건드렸으면 충돌git rebase --abort
두 칸 이상 위 층을 옮김git rebase --onto 새기준 옛기준 대상옛 기준 해시를 손으로 찾아야 함git reset --hard 대상@{1}
트렁크가 앞으로 나감git rebase --update-refs maingit 2.38 이상 필요리플로그로 각 층 개별 복귀
매번 자동으로git config rebase.updateRefs true저장소 단위 설정설정을 false로
리베이스가 이미 끝남git reflog 브랜치@{1}이 직전 위치git reset --hard
충돌 해결 중 포기git rebase --abort부분 해결도 함께 버려짐해당 없음
이미 원격에 푸시함강제 푸시 필요다른 사람이 받아 갔으면 위험원격 리플로그는 없음

6. 머지 순서 - 아래부터여야 하는 이유

문서는 「스택 PR은 트렁크에 가장 가까운 아래에서 위로 머지된다」고 적었고, 「중간 PR을 단독으로 머지할 수 없으며 그 아래 PR들이 항상 함께 머지된다」고 명시했다. 규칙만 읽으면 정책처럼 보이지만, 로컬로 해 보면 이력의 성질에서 나오는 물리적 제약이라는 것이 드러난다.

=== 4-2. merge the MIDDLE first: what actually lands ===
commits layer2 would bring in:
  fc9279e feat(repo): order lookup
  6c5b822 feat(db): add connection pool config     <-- 1층 커밋이 딸려 있다

$ git switch main
$ git merge --no-ff stack/2-repo

files now on main:
  README.md  app.yml  db.yml  repo.py            <-- db.yml 이 같이 들어왔다

what is LEFT in the bottom PR (main..stack/1-db):
  commits: 0
   repo.py | 2 --
  -> the bottom PR is now EMPTY

2층만 골라 머지했더니 1층의 커밋이 함께 트렁크에 들어갔다. 당연하다. 2층의 이력 안에 1층 커밋이 이미 들어 있기 때문이다. 그 결과가 마지막 줄이다. 1층 PR에 남은 커밋 수가 0이 되었다.

  • 1층은 자기 이름으로 리뷰받지 못한 채 트렁크에 들어갔다. 승인 규칙을 층마다 걸어 두었다면 그 규칙이 조용히 우회된다
  • 1층 PR 화면은 이제 「변경 없음」으로 보인다. 리뷰어는 무슨 일이 있었는지 알 길이 없다
  • 변경 비교가 음수로 나온 것도 눈여겨보라. 트렁크가 1층보다 앞서 있어서, 1층을 기준으로 보면 repo.py가 삭제된 것처럼 보인다
  • 그래서 플랫폼이 중간 단독 머지를 막는 것은 제한이 아니라 보호다. 아래를 함께 머지해서 이 상황을 원천 차단한다

6.1 스쿼시 머지라는 함정

한국 팀 상당수가 스쿼시 머지를 기본으로 쓴다. 커밋 하나로 눌러서 트렁크 이력을 깔끔하게 유지하려는 것이다. 그런데 스쿼시는 내용은 같고 커밋 해시는 다른 새 커밋을 만든다. 스택과 만나면 어떻게 되는지 두 경우로 나눠 돌렸다.

=== 4-3. bottom squash-merged, then the stack rebased (아무도 손대지 않은 경우) ===
$ git merge --squash stack/1-db
$ git commit -m "feat(db): add connection pool config (#1)"
same content, different commit id:
  main:db.yml        c7c0b78
  stack/1-db:db.yml  c7c0b78      <-- 내용(blob)은 동일

$ git switch stack/2-repo
$ git rebase main
warning: skipped previously applied commit 8fd3e84
hint: use --reapply-cherry-picks to include skipped commits
Successfully rebased and updated refs/heads/stack/2-repo.
layer 2 review unit:
 repo.py | 2 ++                                   <-- 깨끗하게 정리됐다

=== 4-4. same, but the maintainer edited one line while squashing ===
$ git rebase main
Auto-merging db.yml
CONFLICT (add/add): Merge conflict in db.yml
error: could not apply 1cb43a1... feat(db): add connection pool config
  AA db.yml
pool:
<<<<<<< HEAD
  size: 8
=======
  size: 5
>>>>>>> 1cb43a1 (feat(db): add connection pool config)
  timeout: 30
rebase exit code: 1

두 결과가 갈렸다. 아무도 손대지 않고 스쿼시했을 때는 git이 「이미 적용된 커밋을 건너뛴다」고 알리며 알아서 정리했고, 2층의 리뷰 단위는 깨끗하게 repo.py 하나가 됐다. 그런데 관리자가 머지하면서 한 줄이라도 고치면 같은 파일이 양쪽에서 새로 생긴 것으로 취급되어 add/add 충돌이 났다.

  • 「스쿼시 머지를 쓰면 스택이 깨진다」는 말은 절반만 맞다. 내용이 그대로면 git이 알아서 건너뛴다
  • 깨지는 것은 머지 시점에 내용이 바뀔 때다. 웹 편집기로 오타를 고치는 습관, 자동 포맷터가 붙는 파이프라인, 릴리스 노트를 커밋에 끼워 넣는 관행이 전부 여기에 해당한다
  • 문서가 요구하는 완전한 선형 이력 조건도 같은 이야기다. 아래 브랜치에 푸시가 들어가거나 트렁크가 앞으로 나가면 그 조건이 흔들린다고 문서가 직접 적었다
  • 도입 전에 팀의 기본 머지 방식으로 스택을 한 번 통과시켜 보는 것 말고 확인할 방법이 없다

7. 세 가지 방식 대조 - 큰 PR, 독립 PR, 쌓은 PR

같은 작업을 세 가지로 낼 수 있다. 어느 것이 우월한 게 아니라 비용을 어디에 두느냐가 다르다.

기준하나의 큰 PR여러 독립 PR쌓은 PR
리뷰 단위전체가 한 덩어리PR마다 독립층마다 독립, 아래 내용은 빠짐
의존성 표현없음(한 덩어리라 불필요)표현 못 함. 설명란에 글로 적을 뿐기준 브랜치로 이력에 새겨짐
중복 변경없음겹치는 파일이 있으면 양쪽에 나타남없음. 아래 것은 위에서 안 보임
되돌리기전부 또는 전무PR 단위, 다만 순서를 지켜야 함위에서부터 층 단위
부분 통과불가가능아래부터만 가능
CI 비용1회분, 실패하면 전체 재실행PR 수만큼, 서로 무관층 수만큼 + 아래가 바뀌면 위 전부 재실행
머지 순서제약 없음제약 없음(충돌은 각자 해결)아래부터 강제
저자 부담낮음중간(충돌 수동 해결)높음. 아래가 바뀔 때마다 리베이스
리뷰어 부담매우 높음낮음, 다만 전체 그림이 안 보임낮음 + 스택 지도로 전체 파악
필요한 도구없음없음로컬 git으로 가능, 플랫폼 지원 시 편함

표에서 읽어야 할 것은 쌓은 PR의 비용이 저자에게 몰린다는 점이다. 리뷰어가 편해지는 만큼 저자가 리베이스를 감당한다. 그래서 혼자 쓰는 팀에서는 이득이 없고, 리뷰가 실제로 병목인 팀에서만 값어치가 생긴다.

8. 한국 팀에서의 현실 - 사람 수, 승인 규칙, 릴리스 브랜치

여기서는 특정 조직 이야기를 하지 않는다. 국내 개발 조직에서 흔히 보이는 구조적 조건 세 가지와 스택이 어떻게 맞물리는지만 본다.

8.1 리뷰어가 적을 때

  • 스택은 리뷰 「건수」를 늘린다. 층이 셋이면 알림이 세 개 온다. 리뷰어가 한 명뿐이면 같은 사람이 세 번 열게 된다
  • 총 시간이 줄어드는지는 층이 잘 잘렸는지에 달렸다. 잘 잘렸으면 각 층이 짧아 합이 줄고, 잘못 잘렸으면 문맥을 세 번 다시 잡느라 오히려 는다
  • 얻는 것은 확실히 하나 있다. 아래 절반을 먼저 통과시킬 수 있다. 저자는 승인된 아래 층 위에서 다음 작업을 이어 갈 수 있고, 되돌릴 위험이 줄어든다
  • 반대로 리뷰어가 한 명이고 그 사람이 자리를 비우면 스택 전체가 통째로 멈춘다. 아래가 막히면 위는 머지될 수 없기 때문에 단일 실패 지점이 강해진다

8.2 승인 규칙이 걸려 있을 때

  • 필수 승인 인원이나 코드 소유자 규칙이 있으면 층마다 그 규칙을 통과해야 한다. 문서도 아래 PR들이 모두 요구 조건을 만족해야 머지된다고 적었다
  • 승인 이벤트가 층 수만큼 필요하다는 뜻이다. 필수 승인이 두 명이고 층이 넷이면 승인 행위가 여덟 번 일어난다
  • 그래서 승인 규칙이 엄격한 조직일수록 층을 서넛 이하로 유지하는 편이 현실적이다
  • 코드 소유자가 층마다 다르면 오히려 유리하다. DB 담당이 1층을, API 담당이 3층을 병렬로 보면 총 대기 시간이 실제로 줄어든다. 큰 PR에서는 두 사람이 같은 40개 파일을 각자 훑어야 했다
  • 자동 머지가 지원되지 않는다는 문서상의 제약도 여기서 체감된다. 승인이 다 모여도 사람이 머지 버튼을 눌러야 한다

8.3 릴리스 브랜치 전략과 맞물릴 때

  • 스택의 밑바닥이 트렁크가 아니라 릴리스 브랜치를 향하면, 그 브랜치에 핫픽스가 들어갈 때마다 스택 전체가 흔들린다. 5절의 --update-refs가 사실상 필수가 된다
  • 릴리스가 잠기는 기간에 스택이 걸쳐 있으면 아래는 이번 릴리스, 위는 다음 릴리스가 되는 상황이 생긴다. 이때 위 층의 기준을 다음 릴리스 브랜치로 옮겨야 하고 그것이 또 리베이스다
  • 체리픽으로 릴리스에 반영하는 관행이 있으면 6.1절의 내용은 같고 해시는 다른 문제가 그대로 재현된다
  • 포크 기반으로 기여받는 저장소라면 애초에 쓸 수 없다. 문서가 포크를 가로지르는 스택은 지원하지 않는다고 명시했다
  • 실무적으로는 스택의 수명을 릴리스 주기보다 짧게 유지하는 것이 유일한 해법이다. 층이 릴리스 경계를 넘기 시작하면 관리 비용이 급격히 오른다

9. 도입 판단 - 언제 값어치가 있고 언제 과한가

결론부터 적으면 이렇다. 스택은 리뷰 용량을 늘리는 도구가 아니다. 한 주에 처리되는 변경의 총량은 여전히 리뷰어의 시간이 정한다. 스택이 바꾸는 것은 한 건당 리뷰 시간과 아래 절반을 먼저 통과시킬 수 있는 가능성, 이 둘뿐이다. 그러므로 판단 기준도 좁아진다.

상황쌓기가 맞나이유
변경이 계층 방향으로 자연히 갈린다맞다의존 방향이 한쪽이라 순서를 정할 수 있다
이름 바꾸기·이동 같은 무해한 준비 작업이 크다맞다맨 아래 층으로 빼면 빨리 승인된다
아래 층만 먼저 배포해도 뜻이 있다맞다부분 통과의 이득이 실제로 발생한다
코드 소유자가 층마다 다르다맞다병렬 리뷰로 총 대기가 준다
두 덩어리가 서로를 참조한다아니다순서를 정할 수 없다. 한 층에 둔다
층이 다섯을 넘는다아니다갱신 비용이 이득을 먹는다
아래 층이 매일 바뀐다아니다위 층을 매일 리베이스하게 된다
PR이 이미 파일 5개 수준이다아니다나눌 것이 없다. 오버헤드만 는다
포크에서 기여받는다불가문서가 지원하지 않는다고 명시
스쿼시 머지 + 머지 시점 편집 관행먼저 시험6.1절의 충돌이 재현될 수 있다

9.1 도구 없이 로컬 git만으로 되는 것과 안 되는 것

  • 된다. 층을 만드는 것. git switch -c 위층 아래층 세 줄이면 끝이다
  • 된다. 각 층의 리뷰 단위를 확인하는 것. git diff --stat 아래층..위층이면 그 층이 새로 한 일만 나온다
  • 된다. 아래가 바뀔 때 위를 옮기는 것. --onto와 --update-refs가 이 일을 한다
  • 된다. 되돌리기. --abort, 리플로그, ORIG_HEAD
  • 된다. PR을 여는 것까지도. 각 PR의 기준 브랜치를 손으로 아래 층으로 지정하면 리뷰 화면은 똑같이 그 층만 보여 준다
  • 안 된다. 아래가 머지됐을 때 위 PR의 기준을 자동으로 바꾸는 것. 손으로 하면 매번 잊는다
  • 안 된다. 리뷰어에게 이 층이 전체 중 어디인지 보여 주는 것. 설명란에 목록을 적어 두는 수밖에 없고 금방 낡는다
  • 안 된다. 아래부터 머지되도록 강제하는 것. 규율에 의존하게 되고 6절의 사고가 난다
  • 안 된다. 여러 층을 한 번의 조작으로 머지하는 것
  • 즉 플랫폼 기능이 채우는 자리는 정확히 이 네 가지다. 나머지는 이미 git에 있다

9.2 도입 전 점검 목록

  • 지금 PR이 실제로 큰가. 파일 수와 리뷰 대기 일수를 먼저 재라. 작은데 도입하면 손해다
  • 병목이 리뷰인가, 아니면 배포나 QA인가. 리뷰가 아니면 스택은 아무것도 고치지 못한다
  • 팀의 기본 머지 방식이 무엇인가. 스쿼시라면 6.1절 시험을 먼저 하라
  • 스택 브랜치를 본인만 푸시한다는 합의가 있는가. 강제 푸시가 오가면 이력이 어긋난다
  • git 버전이 2.38 이상인가. --update-refs가 없으면 손작업이 층 수만큼 남는다
  • 층을 서넛 이하로 유지할 규칙이 있는가
  • 릴리스 브랜치가 스택 밑바닥이 될 일이 있는가. 있다면 수명을 릴리스 주기보다 짧게 잡아라
  • 포크 기반 기여가 있는가. 있다면 그 경로는 스택을 쓸 수 없다
  • CI 비용을 감당할 수 있는가. 아래가 바뀌면 위 전부가 다시 돈다
  • 프리뷰라는 사실을 팀이 알고 있는가. 화면과 명령은 바뀔 수 있다

마지막으로 이 글 전체의 선을 다시 긋는다. 스택 PR은 큰 변경을 나누는 반복 작업의 비용을 낮추는 도구다. 그 이상도 이하도 아니다. 어디서 자를지, 무엇을 아래에 둘지, 이 변경을 나눌 값어치가 있는지 — 이 판단은 도구가 대신해 주지 않는다. 그리고 나눈 뒤에도 처리량을 정하는 것은 여전히 리뷰 용량이다. 층을 늘린다고 리뷰어의 하루가 길어지지는 않는다.

# 스택 PR — 쌓기 재현 명령과 도입 점검 목록

> 출처: braindetox.kr — GitHub 스택 PR 공개 프리뷰
> 근거: git 2.48.1.windows.1 / GNU bash 5.2.37 (MSYS2) / Windows 10 Pro 실행 검증
> 시점: 2026-08-01. GitHub 스택 PR은 공개 프리뷰이며 화면과 명령이 바뀔 수 있습니다.
> 이 파일을 그대로 AI에 붙여 「이 기준으로 우리 저장소를 점검해줘」라고 쓰면 됩니다.

## 1. 스택 만들기 (로컬 git만으로)

```
git switch -c stack/1-db   main          # 1층
git switch -c stack/2-repo stack/1-db    # 2층은 1층 위에
git switch -c stack/3-api  stack/2-repo  # 3층은 2층 위에
```

확인 명령:

```
git log --graph --oneline --decorate main..stack/3-api
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads/
git diff --stat stack/1-db..stack/2-repo    # 그 층의 리뷰 단위만
git diff --stat main..stack/3-api           # 큰 PR 하나였다면 이만큼
```

## 2. 아래가 바뀌었을 때 위 갱신

```
# 바로 위 한 층만
git switch stack/2-repo
git rebase stack/1-db

# 두 칸 이상 위 (옛 기준 해시를 명시)
git rebase --onto stack/2-repo OLD_HASH stack/3-api

# 스택 전체를 한 번에 (git 2.38+)
git switch stack/3-api
git rebase --update-refs main

# 매번 자동으로
git config rebase.updateRefs true
```

## 3. 충돌과 되돌리기

```
# 진행 중 포기
git rebase --abort

# 해결하고 계속
git add db.yml
git rebase --continue

# 이미 끝난 리베이스 되돌리기
git reflog stack/3-api
git reset --hard stack/3-api@{1}
git reset --hard ORIG_HEAD          # 짧은 형태
```

- 충돌 표시의 HEAD 쪽이 새 기준(아래 층), 반대쪽이 지금 적용 중인 위 층 커밋
- `.git/rebase-merge` 가 있으면 중간 상태
- 되돌리기는 로컬에서만 무해. 강제 푸시 후에는 남이 받아 간 이력이 어긋난다

## 4. 머지 절차

- 아래부터 위로 머지한다 (플랫폼 문서의 규칙)
- 중간만 단독 머지 불가 — 아래가 항상 함께 머지된다
- 중간을 억지로 먼저 머지하면 아래 PR의 남은 커밋이 0이 되고, 리뷰 없이 통과한 셈이 된다
- 아래가 머지되면 위는 트렁크를 기준으로 다시 잡힌다
- 자동 머지는 지원되지 않는다 (프리뷰 시점 기준)
- 스쿼시 머지 시험: 내용 그대로면 git이 건너뛴다. 머지 시점에 한 줄이라도 고치면 add/add 충돌

## 5. 세 방식 비교

| 기준 | 큰 PR 하나 | 독립 PR 여럿 | 쌓은 PR |
|---|---|---|---|
| 리뷰 단위 | 전체 한 덩어리 | PR마다 독립 | 층마다 독립 |
| 의존성 표현 | 불필요 | 못 함 | 기준 브랜치로 새겨짐 |
| 되돌리기 | 전부 또는 전무 | PR 단위 | 위에서부터 층 단위 |
| 부분 통과 | 불가 | 가능 | 아래부터만 |
| CI 비용 | 1회분 | PR 수만큼 | 층 수만큼 + 아래 변경 시 전부 |
| 머지 순서 | 제약 없음 | 제약 없음 | 아래부터 강제 |
| 저자 부담 | 낮음 | 중간 | 높음 (리베이스) |

## 6. 도입 점검 목록

- [ ] 지금 PR이 실제로 큰가 (파일 수·대기 일수를 먼저 측정)
- [ ] 병목이 리뷰인가 (배포·QA면 스택은 무효)
- [ ] 변경이 계층 방향으로 갈리는가 (서로 참조하면 한 층에)
- [ ] 층을 서넛 이하로 유지할 규칙이 있는가
- [ ] 팀의 기본 머지 방식이 스쿼시인가 (그렇다면 먼저 시험)
- [ ] 스택 브랜치는 본인만 푸시한다는 합의가 있는가
- [ ] git 2.38 이상인가 (--update-refs 가용)
- [ ] 릴리스 브랜치가 스택 밑바닥이 될 일이 있는가
- [ ] 포크 기반 기여 경로인가 (그렇다면 사용 불가)
- [ ] 아래가 바뀔 때 위 CI가 전부 재실행되는 비용을 감당하는가

## 7. 하지 말 것

- 층이 서로를 참조하게 자르는 것 — 순서를 정할 수 없다
- 층을 다섯 이상으로 늘리는 것 — 갱신 비용이 이득을 먹는다
- 스택 브랜치를 여러 사람이 푸시하는 것 — 리베이스와 충돌한다
- 중간 층을 먼저 머지하려는 것 — 아래가 리뷰 없이 딸려 들어간다
- 스택으로 리뷰 용량이 늘 거라 기대하는 것 — 총량은 리뷰어 시간이 정한다
- 프리뷰 기능의 화면·명령을 고정된 것으로 문서화하는 것
