同一个头部出现两次 - 哪些能合并哪些绝对不能

每个字段对「多个」的含义都不同，而运行时会替你先做决定

2026-08-01 开发/基础设施

从症状说起：下发了两个 Cookie，只存下一个

登录响应里同时下发了会话 Cookie 和主题 Cookie，服务器日志里两条都在。可浏览器里只剩下会话 Cookie 一条。翻开代码，生成 Cookie 的那段没有任何问题。于是多半会去怀疑浏览器设置或域名，然后耗掉半天。

这个症状里有相当一部分，是在更靠前的地方就决定了的。某个环节把本来两行的头部合成了一行。而且这个合并通常并不是错误。恰恰相反，对大多数字段来说合并才是规范规定的正确行为。麻烦出在把同样的处理用到了规范没有这样定义的字段上。

所以本文的主题不是「封堵重复头部」。既封不住，也没有理由去封。真正的问题是这三个。

  • 同一个名字来了两次，对这个字段而言意味着什么。是列表变长了，是有两个值，还是本就不该出现的状态
  • 合不合并由谁来定。很多时候不是开发者定的，是运行时先替你定了
  • 你的代码看到的是到达的东西，还是已经被加工过的东西。拿到一个字符串的那一刻，信息可能已经没了

三个问题都用实际运行给出了答案。把同样的字节推给不同的运行时，再把接收方最终握在手里的东西打印出来。结果可以压缩成一句话：每个字段对「多个」的含义都不同，而每个运行时对这个含义的处理也不同。

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际跑出来的。运行时为 Node.js v22.16.0 (win32) 和 Python 3.13.3 (win32)，服务器直接用各自语言内置的 HTTP 模块启动。请求是用原始套接字逐字节写进去的，为的是避免客户端库在发送前把头部规范化。使用的端口是 18090 到 18094，测量结束后全部关闭。

本文不对任何具体产品的行为下结论。第 7 节里的中继是为本文亲手写的二十来行最小实现，不代表任何商用代理、负载均衡器或 Web 服务器产品的行为。各产品怎么处理，需要在你自己的环境里直接测量。本文给的不是结论，而是测量方法和判断标准。

本文不涉及的内容。头部名称大小写造成的另一个陷阱在名称不区分大小写而代码区分里讲过，这里只看名字完全相同的情况。Cookie 属性的含义在SameSite Lax、Strict、None 里。第 3 节只看一件事：把行合并会把值弄坏。

1. 同一个名字发两次，到达的是什么

先做最基本的复现。造一个请求，把几个名字各写两行，然后把完全相同的这串字节分别发给两个服务器。发出去的是这些。

GET /dup HTTP/1.1
Host: shop.example.test
X-Trace-Id: aaa-111
X-Trace-Id: bbb-222
Accept: text/html
Accept: application/json
X-Forwarded-For: 203.0.113.9
X-Forwarded-For: 198.51.100.4
Cookie: sid=A1
Cookie: theme=dark
Connection: close

用三种 API 分别打印接收方手里的东西。先看 Node。

1-A. Node.js v22.16.0 / win32
status : HTTP/1.1 200 OK

  req.headers[x-trace-id      ] = 'aaa-111, bbb-222'
  req.headers[accept          ] = 'text/html, application/json'
  req.headers[x-forwarded-for ] = '203.0.113.9, 198.51.100.4'
  req.headers[cookie          ] = 'sid=A1; theme=dark'

  req.headersDistinct[x-trace-id      ] = ['aaa-111', 'bbb-222']
  req.headersDistinct[accept          ] = ['text/html', 'application/json']
  req.headersDistinct[x-forwarded-for ] = ['203.0.113.9', '198.51.100.4']
  req.headersDistinct[cookie          ] = ['sid=A1', 'theme=dark']

  req.rawHeaders (flat, order kept):
    [0] Host: shop.example.test
    [1] X-Trace-Id: aaa-111
    [2] X-Trace-Id: bbb-222
    [3] Accept: text/html
    [4] Accept: application/json
    [5] X-Forwarded-For: 203.0.113.9
    [6] X-Forwarded-For: 198.51.100.4
    [7] Cookie: sid=A1
    [8] Cookie: theme=dark
    [9] Connection: close

三种 API 对同一个请求给出了三幅不同的图。用得最多的第一种返回一个把两行用逗号加空格拼起来的字符串，另外两种把行原样保留。还要注意 Cookie 是用分号而不是逗号拼的。这个字段本来就是分号分隔的列表，所以运行时按字段套用了不同的规则。

接着把同样的字节发给 Python 服务器。

1-B. Python 3.13.3 / win32
status : HTTP/1.1 200 OK

  headers.get(x-trace-id      )     = 'aaa-111'
  headers.get(accept          )     = 'text/html'
  headers.get(x-forwarded-for )     = '203.0.113.9'
  headers.get(cookie          )     = 'sid=A1'

  headers.get_all(x-trace-id      ) = ['aaa-111', 'bbb-222']
  headers.get_all(accept          ) = ['text/html', 'application/json']
  headers.get_all(x-forwarded-for ) = ['203.0.113.9', '198.51.100.4']
  headers.get_all(cookie          ) = ['sid=A1', 'theme=dark']

  headers.items() (order kept):
    Host: shop.example.test
    X-Trace-Id: aaa-111
    X-Trace-Id: bbb-222
    Accept: text/html
    Accept: application/json
    X-Forwarded-For: 203.0.113.9
    X-Forwarded-For: 198.51.100.4
    Cookie: sid=A1
    Cookie: theme=dark
    Connection: close

本文的第一个核心结论在这里出现了：字节完全相同，字符串 API 在两个运行时里给出的答案却不一样。

  • 一边把两行拼起来。信息还在，但边界没了
  • 另一边只给第一行。第二行被悄悄丢掉，没有异常也没有警告
  • 两个运行时都带着把所有行以数组返回的另一套 API。只是名字不同，能力是一样的
  • 两边都没有报错。重复头部本身并不是协议违规
  • 所以「来了重复头部会怎样」这个问题不能只看一个服务器就作答

这个差异在生产里有个变得很难缠的场合。假设一个团队用字符串 API 会拼接的语言写前端一层，另一个团队用另一门语言写后端一层。对同一个请求，前面看到的是「两个值拼成的一个字符串」，后面看到的是「第一个值」。两边都是正常行为，两边都不会在日志里留下任何痕迹。

2. 列表型字段本来就该合并

我不想留下「合并总是错的」这种印象，事实恰恰相反。相当多的字段就应该合并。RFC 9110 第 5.2 节是这样定义的。

当一个字段名在某一段落内重复出现时，其合并字段值由该段落内对应的各字段行值按顺序连接、并以逗号分隔各字段行值所构成的列表组成。(RFC 9110, 第 5.2 节)

也就是说「分两行发」和「写成一行逗号分隔」在列表型字段里应当是同一个意思。这一点做了验证：同样三个字段用两种方式各发一遍，再比较结果。

EXP 2. list-based fields: two lines vs one comma line

 [Node.js v22.16.0]
   accept          via req.headers
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     parsed two lines : ['text/html', 'application/json']
     parsed one line  : ['text/html', 'application/json']
     SAME MEANING     : True
   cache-control   via req.headers
     two lines -> 'no-cache, max-age=0'
     one line  -> 'no-cache, max-age=0'
     parsed two lines : ['no-cache', 'max-age=0']
     parsed one line  : ['no-cache', 'max-age=0']
     SAME MEANING     : True
   accept-encoding via req.headers
     two lines -> 'gzip, br'
     one line  -> 'gzip, br'
     SAME MEANING     : True

 [Python 3.13.3]
   accept          via join(get_all())
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     SAME MEANING     : True
   cache-control   via join(get_all())
     SAME MEANING     : True
   accept-encoding via join(get_all())
     SAME MEANING     : True

两个运行时、三个字段全部拆成了同一个列表。对列表型字段来说，成员是分行来的还是一行逗号来的，最终语义完全一致。所以这里的合并不是损失。

不过这里有前提。同一个第 5.3 节说得很死。

除非该字段的定义允许把多个字段行值重新组合成逗号分隔的列表，否则发送方不得在一条消息中生成多个同名的字段行，也不得在已存在同名字段行时再追加一行。(RFC 9110, 第 5.3 节)

换句话说，能合并的只有规范定义为列表的那些字段，把别的字段仅仅因为名字相同就合并，更接近规范禁止的那一侧。关于顺序，同一节也写得很清楚。

因此，同名字段行被接收到的顺序对字段值的解释是有意义的；代理在转发消息时不得改变这些字段行值的顺序。(RFC 9110, 第 5.3 节)

顺序带有语义这一点在实务里经常被忽略。给值排序、或者转成集合去重的代码很常见，而对列表型字段来说那是在丢弃优先级信息。

2.1 一行多个和多行多个混在一起时

实战里两种形态是混着来的：来了两行，而其中一行里还带着逗号。这时候只数行数就会数错个数。

request sent:
  > Accept: text/html
  > Accept: application/json, text/plain

readList(accept) = ["text/html","application/json","text/plain"]
  note: 2 field lines, 3 members.

字段行是两个，列表成员却是三个。所以读列表型字段的正确步骤是两步：先用数组 API 拿到所有行，再把每一行按逗号拆开摊平成一个。只数行的代码和只拆一个字符串的代码，都只做了一半。

3. Set-Cookie 一合并值就坏

下面是例外，而且这个例外并不小。开头的症状正是从这里来的。

两条 Cookie 正常地各占一行下发时，是这样到达的。

3-A. server sent TWO Set-Cookie lines (correct)
 res.headers["set-cookie"] type : Array
 value:
   [0] sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly
   [1] theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 cookies the client will store : ["sid=A1","theme=dark"]
 count = 2

两条 Cookie 原样存下。接着把完全相同的这两条用逗号加空格拼成一行。要是列表型字段，这么做完全没问题。

3-B. the SAME two cookies glued with ", " into one line
 raw value on the wire:
   sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly, theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 now split it back on "," the way a list-based field is split:
   [0] sid=A1; Path=/; Expires=Wed
   [1] 20 Aug 2026 10:00:00 GMT; HttpOnly
   [2] theme=dark; Path=/; Expires=Fri
   [3] 22 Aug 2026 10:00:00 GMT
 pieces = 4   (we started with 2 cookies)
 cookies the client would store : ["sid=A1","20 Aug 2026 10:00:00 GMT","theme=dark","22 Aug 2026 10:00:00 GMT"]

两条 Cookie 碎成了四片。原因很明确：过期时间的写法在星期几后面带一个逗号，所以一旦把逗号当作分隔符，一条 Cookie 就在自己内部被切成两半，而被切下来的后半截看上去像是一条新的 Cookie。

RFC 9110 早就预见到这种情况，写进了第 5.5 节。

预期在成员内部包含逗号的字段，例如 HTTP-date 或 URI-reference 元素，应当在该元素两侧定义分隔符，以便把这些数据内部的逗号与潜在的列表分隔符区分开来。(RFC 9110, 第 5.5 节)

Cookie 这个字段并不是那样定义的，过期时间里的逗号外面没有引号包着。所以仅凭一个逗号，原理上无法判断哪个是分隔符哪个是数据。同一份文档的第 5.3 节点名把这个字段列为例外。

实际上，Set-Cookie 头部字段在响应消息中经常跨多个字段行出现，并且不使用列表语法，因而违反了上述关于同名多字段行的要求。(RFC 9110, 第 5.3 节)

3.1 不用过期属性也并不安全

你可能会想「那不用过期属性不就行了」。实测下来那条路更糟。

3-D. even without Expires, joining loses a cookie boundary
 two lines  -> ["sid=A1; Path=/","theme=dark; Path=/"]
   stored   -> ["sid=A1","theme=dark"]  count=2
 one line   -> "sid=A1; Path=/, theme=dark; Path=/"
   a cookie parser reads ONE cookie from ONE line:
     name/value = sid=A1
     attributes = ["Path=/, theme=dark","Path=/"]
   -> "theme=dark" arrived as an ATTRIBUTE of sid, not as a cookie.
   -> stored cookies = ["sid=A1"]   count=1   (one cookie silently vanished)

开头的症状在这里被精确复现：下发了两条 Cookie，只存下了一条。第二条不是消失了，而是被当作第一条的属性吸收掉了。在解析器看来，一行就是一条 Cookie，分号后面的全是属性；无法识别的属性会被忽略，所以也不会报错。

  • 服务器日志里确实记着创建了两条 Cookie，所以怎么盯服务器那边都看不出原因
  • 浏览器开发者工具的存储面板里只看得到一条 Cookie，响应头面板里则是长长的一行
  • 消失的永远是后面那条，所以报上来的说法往往是「只有最后加的那个 Cookie 不生效」
  • 带过期属性时还可能冒出来历不明的 Cookie，因为被切断的日期片段看着像个 Cookie 名字
  • Cookie 属性本身的含义和这个问题是两回事，那部分在SameSite 行为里讲过

3.2 转成字符串的那一刻它又回来了

有一条路径能在你正确拿到数组之后，在最后一步把它毁掉。

3-E. what the array API vs the string API report
 res.headers["set-cookie"]         = Array(2)
 res.headersDistinct["set-cookie"] = Array(2)
 res.rawHeaders set-cookie lines   = 2
 String(res.headers["set-cookie"]) = "sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly,theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT"
   <- the moment you coerce it to a string, the "," is back and the damage is done

数组一旦被转换，就变成一个用逗号拼起来的字符串。打进日志、塞进模板字符串、或者原样复制到另一个响应里的代码都算在内。唯独这个字段必须以数组的形态一路带到底。

4. Host 有两个时 - 哪一层相信哪一个

下面是非列表的字段。Host 是决定请求指向哪个目标的单值字段。发两行会怎样，做了测量。

EXP 4-A. two Host lines, different authorities
  > GET /who HTTP/1.1
  > Host: front.example.test
  > Host: back.example.test
  > Connection: close

 Node.js v22.16.0:
  status : HTTP/1.1 200 OK
    req.headers[host]         = 'front.example.test'
    req.headersDistinct[host] = ['front.example.test', 'back.example.test']

 Python 3.13.3:
  status : HTTP/1.1 200 OK
    headers.get(host)     = 'front.example.test'
    headers.get_all(host) = ['front.example.test', 'back.example.test']

测量结果是这样的：两个服务器都没有拒绝。都返回了 200，用字符串 API 去问，给的都是第一个值。而且两边用数组 API 去问，两个值都还在。

这里有意思的是 Node 的行为。第 1 节里 X-Trace-Id 是用逗号拼起来的，而 Host 没有拼，只给了第一个值。也就是说同一个运行时对不同字段用了不同规则。到底哪些字段会受这种待遇，做了更大范围的确认。

EXP 4-B. single-value fields sent twice
  > Authorization: Bearer FIRST
  > Authorization: Bearer SECOND
  > Content-Type: application/json
  > Content-Type: text/plain
  > User-Agent: agent-one
  > User-Agent: agent-two
  > X-Trace-Id: aaa
  > X-Trace-Id: bbb

 Node.js v22.16.0:
    req.headers[authorization]         = 'Bearer FIRST'
    req.headersDistinct[authorization] = ['Bearer FIRST', 'Bearer SECOND']
    req.headers[content-type]          = 'application/json'
    req.headersDistinct[content-type]  = ['application/json', 'text/plain']
    req.headers[user-agent]            = 'agent-one'
    req.headersDistinct[user-agent]    = ['agent-one', 'agent-two']
    req.headers[x-trace-id]            = 'aaa, bbb'
    req.headersDistinct[x-trace-id]    = ['aaa', 'bbb']

 Python 3.13.3:
    headers.get(authorization)     = 'Bearer FIRST'
    headers.get_all(authorization) = ['Bearer FIRST', 'Bearer SECOND']
    headers.get(x-trace-id)        = 'aaa'
    headers.get_all(x-trace-id)    = ['aaa', 'bbb']

Node 内部维护着一份已知为单值的字段清单，清单里的字段不拼接，只保留第一个值。所以来了两个认证令牌时，字符串 API 只会给你看第一个。第二个令牌在你的代码运行之前就已经不在视野里了。

4.1 为什么危险 - 当判断的层不止一个

这种局面危险，不是因为值看着奇怪，而是因为结构。设想一个请求被若干层依次判断的形态：前面一层看着某个东西做出决定，后面一层又看着同一个东西再做一次决定。

  • 同一个名字来了两行时，哪一个算数是由实现决定的，不是由规范决定的。上面的测量里两个运行时碰巧都取了第一个，但这不能拿来当作「所有实现都这样」的依据
  • 一旦出现前面信第一个值、后面信最后一个值的组合，两层就是在对不同的目标做判断。两边都不会报错
  • 还有一种组合是前面拼接后转发，后面把拼接后的整个字符串当成一个值。这时候后面看到的值，和前面判断过的值在字符串层面就是不一样的
  • 这种错位很难靠日志追踪，因为每一层的日志里只会写下这一层选中的那一个值。不把两份日志摆在一起，看不出差别
  • 因此对策不是把值挑得更准，而是让「挑」这件事根本不会发生 —— 在边界上规范化或者拒绝

实务规则很简单：如果决定目标的字段来了两行以上，这个请求本身就已经不正常了。不要纠结哪个值才对，应该在最外层边界数清行数，不等于一就拒绝或规范化为一个，并且不让后面的层再判断一次。一旦放任后面各层自行判断，就给不同层得出不同答案留下了空间。

5. Content-Length 重复 - 这里拒绝才是正解

Content-Length 决定正文在哪里结束。这个值一旦含糊，消息的边界本身就含糊了。值不同和值相同两种情况分开测量。

EXP 5. duplicate Content-Length, measured

 Node.js v22.16.0 http server
  baseline: one Content-Length             -> HTTP/1.1 200 OK    headers['content-length']='5'  headersDistinct=['5']
  two Content-Length, SAME value           -> HTTP/1.1 400 Bad Request
  two Content-Length, DIFFERENT values     -> HTTP/1.1 400 Bad Request
  one Content-Length holding a comma list  -> HTTP/1.1 400 Bad Request

 Python 3.13.3 http.server
  baseline: one Content-Length             -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5']
  two Content-Length, SAME value           -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '5']
  two Content-Length, DIFFERENT values     -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '7']
  one Content-Length holding a comma list  -> HTTP/1.1 200 OK    get('content-length')='5, 5'   get_all=['5, 5']

 --- node server error log ---
 [clientError] code=HPE_UNEXPECTED_CONTENT_LENGTH msg=Parse Error: Duplicate Content-Length
 [clientError] code=HPE_UNEXPECTED_CONTENT_LENGTH msg=Parse Error: Duplicate Content-Length
 [clientError] code=HPE_INVALID_CONTENT_LENGTH   msg=Parse Error: Invalid character in Content-Length

两个运行时的态度完全相反。整理如下。

  • Node 即使两个值完全相同也拒绝。5 和 5 来了照样是 400。它的态度不是「没有矛盾就放行」，而是「重复本身就是错误」
  • 拒绝发生在到达应用代码之前的解析阶段，请求处理函数根本没有被调用
  • 写成一行逗号列表的那种情况是用另一个错误码拒绝的，它针对的是值里出现了逗号这件事本身
  • Python 标准库服务器四种情况全部放行，常用的取值方法只返回 5。第二个值是 7 还是 5，代码看不出任何差别
  • 也就是说同一个请求在一个运行时是 400，在另一个是 200。对这个字段而言，根本不存在所谓「一般服务器的行为」

规范对值里带逗号这件事说得很明确。

发送方不得发送字段值中含有逗号的 Content-Length 头部字段。(RFC 9110, 第 8.6 节)

从这里能得到的实务指引只有一条：决定正文边界的字段绝不能悄悄挑一个值。哪怕值看起来一样也是如此，因为「确认值是否一样」这件事本身就得用数组 API 才做得到。只用字符串 API 的代码，连值是相同还是不同都无从判断。就这个字段而言，严格的那一方是对的。

6. 运行时交给你的数据结构 - 字符串到手时已经晚了

把前面的观察串起来就是：如果合不合并由运行时替你决定，开发者看到的就永远只是一个已经做完的决定。为什么这个决定不可逆，做了证明。

6-B. the proof: a joined string cannot tell you what arrived
 case A: two lines  -> ["aaa-111","bbb-222"]
 case B: one line   -> ["aaa-111, bbb-222"]
 joined A           = "aaa-111, bbb-222"
 joined B           = "aaa-111, bbb-222"
 joinA === joinB    : true
 -> two different wire shapes collapse to the same string.

来了两行的情形，和只来一行但里面带逗号的情形，变成了完全相同的字符串。拿着这个字符串的代码没有任何办法知道原本来了几行。信息不是被藏起来了，是没了。之后再怎么精细地解析也复原不出来。

同样的陷阱在值本身带逗号时会朝反方向发作。

6-C. a value that legitimately contains a comma
 one line whose value has a comma : ["Wed, 20 Aug 2026 10:00:00 GMT"]
 joined                           : "Wed, 20 Aug 2026 10:00:00 GMT"
 naive split(",")                 : ["Wed","20 Aug 2026 10:00:00 GMT"]
 pieces = 2  from 1 original line(s)

本来一行的值被逗号拆成了两片。所以按逗号拆分只在该字段的文法把自己定义为列表时才有效。把它一律套到所有头部上的工具函数，正是在这个地方悄悄出错。

6.1 浏览器与服务器共用的头部对象

Web 标准的头部对象在浏览器和服务器两边都在用。它会给出什么，也确认了一下。

6-A. WHATWG Headers (the fetch API object)
 h.get("x-trace-id")      = "aaa-111, bbb-222"
   typeof                 = string
 h.get("set-cookie")      = "sid=A1; Path=/, theme=dark; Path=/"
   typeof                 = string
 h.getSetCookie()         = ["sid=A1; Path=/","theme=dark; Path=/"]
   length                 = 2
 [...h.entries()]         = [["set-cookie","sid=A1; Path=/"],["set-cookie","theme=dark; Path=/"],["x-trace-id","aaa-111, bbb-222"]]

要紧的是第二行：通用的取值方法对 Cookie 字段也返回一个拼好的字符串。正是第 3 节里碎掉的那种形态。所以这个对象另外配了专门返回数组的 Cookie 取值方法。不用那个方法，第 3 节的破坏就会原封不动地发生。

相反，遍历条目时 Cookie 字段是作为两个独立条目出来的。在同一个对象里，用哪个访问器决定了你得到什么答案，这才是重点。

6.2 API 对照表

把到目前为止实际跑出来的结论整理如下。凡是表里标注「有损」的 API，都不要用来做判断。

API返回重复字段会变成什么Cookie 字段判定
Node req.headers[name]字符串用逗号加空格拼接（单值字段只留第一个）数组（例外）有损
Node req.headersDistinct[name]数组每行一项数组无损
Node req.rawHeaders扁平数组名称与值成对，保留顺序成对保留无损 + 顺序 + 原始写法
标准 Headers.get(name)字符串用逗号加空格拼接拼接（破坏）有损
标准 Headers.getSetCookie()数组不适用每行一项无损（仅限 Cookie）
Python headers.get(name)字符串只给第一行，其余丢弃只给第一行有损
Python headers.get_all(name)列表每行一项每行一项无损

这张表该这么读：每个运行时都已经带着无损 API 了。缺的不是功能，是习惯。只不过有损的那个名字更短、在示例里出现得更早，于是就被当成默认值用了。

7. 自制中继走一跳 - 你用什么 API 读，就决定了后端看到什么

要说明上一节的「信息会消失」并不止步于一个进程内部，就得再加一跳。于是写了两个二十来行的中继。这两个中继只有读取头部的 API 不同，其余完全一致。

本节的中继是为这篇文章亲手写的最小实现。它不代表任何商用代理、负载均衡器、API 网关或 Web 服务器的行为，也不能拿来当作它们就是这样工作的依据。这里要展示的不是产品行为，而是一条因果结构：中继用哪种 API 读头部，决定了后端看到什么。你手上的产品是怎么处理的，用本文的方法直接测一下就知道了。

=== EXP 7. one hop through a hand-written relay ===
client sends (same bytes in every case):
  > GET /through HTTP/1.1
  > Host: shop.example.test
  > X-Trace-Id: aaa-111
  > X-Trace-Id: bbb-222
  > Accept: text/html
  > Accept: application/json
  > X-Note: first
  > X-Note: second

7-A. NO relay: straight to the origin
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2
   x-note     lines at origin : 2

7-B. relay reading req.headers (the string API)
   origin saw  x-trace-id: aaa-111, bbb-222
   origin saw  accept: text/html, application/json
   origin saw  x-note: first, second
   x-trace-id lines at origin : 1   value="aaa-111, bbb-222"
   x-note     lines at origin : 1   value="first, second"

7-C. relay reading req.rawHeaders (the array API)
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2   value="aaa-111, bbb-222"
   x-note     lines at origin : 2   value="first, second"

结果整理如下。

  • 不经过中继时两行就是两行地到达，这是原始状态
  • 经过用字符串 API 读的中继，两行变成一行到达。中继并没有改动值，它只是没法转发自己从来没拿到过的东西 —— 读进来的那一刻就已经是一个字符串了
  • 经过用数组 API 读的中继，行数一路保住。同样的中继，差的只是一个 API
  • 值得注意的是 7-C 的最后两行：后端那里行是两个，可用字符串 API 去问依然是拼在一起的一个。也就是说即便前面转发得很老实，后面用哪种 API 读，损失还会再发生一次
  • 因此只有两层都用数组 API 时，两层看到的才是同一个东西。只改一边是不够的

由此得出的结论是本文的核心之一。「我们前面那层不碰头部」这句话，通常指的是不修改值。可就算一个值都不改，行的结构也会仅仅因为读取方式而改变。谁都没动过它，形态却变了 —— 这就是这个问题的性质。

8. 设计规则 - 什么该合并，什么该分开

把前面的测量变成可执行的规则。先把字段分成三类，这个分类是一切判断的起点。

类别例子多行意味着什么怎么读能否分多行发送
列表型Accept, Cache-Control, Accept-Encoding, Vary, Via列表成员变多了用数组接收全部行，再把每行按逗号拆开可以。与写成一行逗号同义
单值型Host, Content-Length, Content-Type, Authorization, Location本不该出现的状态用数组接收并数行数，不等于 1 就拒绝或规范化不可以。合并也不是答案
绝不合并Set-Cookie正常，只是条目有多个用数组专用访问器，全程保持数组可以。多行才是正常形态，合并就会被破坏
自定义头部自己造的 X- 系列定义它的人必须先定好把定义写进文档，两侧代码引用同一份按你定的来。没定过，那本身就是问题

把这个分类写成代码后，拿一个真实请求跑了一遍。下面是对一个混着列表型、单值型、还带自定义头部的请求的结果。

关键在于 readSingleton 没有返回值，而是拒绝了。换成字符串 API，这个位置会悄悄把 Bearer FIRST 递回去。这个拒绝本身就是功能。「哪个才对」不该由代码擅自决定，而应该抛回给调用方。

8.1 安全读取的三个函数

实际用到的实现很短，每类一个就够了。

// 列表型：拿到所有行，再把每行按逗号摊平（两步）
function readList(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  return lines.flatMap(v => v.split(',').map(s => s.trim())).filter(Boolean);
}

// 单值型：行数不为一就不给值，直接拒绝
function readSingleton(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  if (lines.length === 0) return { ok: true, value: null };
  if (lines.length > 1)   return { ok: false, reason: 'arrived ' + lines.length + ' times', lines };
  if (lines[0].includes(',')) return { ok: false, reason: 'single line contains a comma', lines };
  return { ok: true, value: lines[0] };
}

// 绝不合并：保持数组，不要转成字符串
function readCookies(distinct) {
  return (distinct['set-cookie'] || []).slice();
}

Python 那边结构一样，换个取值方法就是全部工作。

# 有损：只会来第一行
value = headers.get('x-trace-id')

# 无损：所有行都会来
lines = headers.get_all('x-trace-id') or []

# 列表型要两步
members = [p.strip() for line in lines for p in line.split(',') if p.strip()]

# 单值型先看行数
if len(lines) != 1:
    raise ValueError('singleton field arrived %d times' % len(lines))

8.2 让前端和后端看到同一个值的做法

正如第 7 节所见，只改一边是不够的。按顺序写下来是这样。

  • 在最外层边界只规范化一次。单值字段来了两行以上就在那里拒绝或收敛成一个。内层必须能够假定自己拿到的已经是整理过的东西
  • 内层不要再判断一次。同一个字段被多层各自解释，正是错位的来源。判断只在一个地方做
  • 用于判断的值一定要用数组 API 读。不是为了拿值，而是为了同时看清来了几行。不知道行数，既没法规范化也没法拒绝
  • 中继代码要按读到的样子原样转发。用字符串接、用字符串传的那一刻，后端就没有选择余地了
  • 自定义头部要把类别写进文档。没有列表型还是单值型的定义，各层解释不一才是必然结果
  • 把行数写进日志。只打值的日志根本记不下「来了两行」这件事。把名字和行数一起记下来，事后才追得动
  • Cookie 字段要以数组形态带到最后。如果有复制或重新组装响应的代码，尤其要检查那个位置

8.3 检查清单

  • 把所有读取头部的代码找出来，按用字符串 API 的地方和用数组 API 的地方分开列了出来
  • 认证、目标、正文长度这类用于判断的字段全部改成了数组 API
  • 用测试确认了单值字段来两行以上时不会静悄悄放行
  • 读列表型字段时行数组和逗号拆分两步都做了（只做一步就会数错）
  • 没有把 Cookie 字段转成字符串的代码，日志、模板、响应复制的位置全部检查过
  • 中继和复制代码按读到的形态原样转发头部
  • 自定义头部的类别写在文档里，前端与后端看的是同一份
  • 检测到重复时名称和行数会写进日志
  • 生产环境里各个组件如何处理重复字段，都已直接测量并记录（不是看产品文档，也不是猜的）
  • 头部名称的大小写是另一个问题，所以那边的检查另外做了一遍

# 重复头部判断标准 — 字段类型表与安全读取

> 来源: braindetox.kr — 同一个头部出现两次时
> 依据: Windows 10 / Node.js v22.16.0 / Python 3.13.3 实际运行验证（用原始套接字直接写入字节）
> 把这个文件原样贴给 AI，写上「按这个标准检查我们的头部处理」即可。
> ⚠ 下面的「各产品行为」务必在你自己的环境里实测。不要靠猜。

## 1. 按字段类型的判断表

| 类型 | 例子 | 多行意味着什么 | 怎么读 | 能否合并 |
|---|---|---|---|---|
| 列表型 | Accept, Accept-Encoding, Accept-Language, Cache-Control, Vary, Via, TE, Content-Encoding | 列表成员变多了 | 用数组接收全部行，再把每行按逗号拆开 | 能（规范如此） |
| 单值型 | Host, Content-Length, Content-Type, Authorization, Location, Date, ETag, Retry-After | 本不该出现的状态 | 用数组接收并数行数，不等于 1 就拒绝 | 不能 |
| 绝不合并 | Set-Cookie | 正常，只是条目有多个 | 用数组专用访问器，全程保持数组 | 绝对不能（会被破坏） |
| 自定义头部 | 自己造的 X- 系列 | 定义它的人必须先定好 | 把定义写进文档，两侧引用同一份 | 按你定的来 |

## 2. 运行时行为对照（实测）

| API | 返回 | 遇到重复时 | 判定 |
|---|---|---|---|
| Node req.headers[name] | 字符串 | 用逗号加空格拼接 / 单值字段只保留第一个值 | 有损 |
| Node req.headersDistinct[name] | 数组 | 每行一项 | 无损 |
| Node req.rawHeaders | 扁平数组 | 名称与值成对，保留顺序和大小写写法 | 无损 |
| Headers.get(name) | 字符串 | 用逗号加空格拼接（Cookie 也被拼接） | 有损 |
| Headers.getSetCookie() | 数组 | 每行一项 | 无损（仅限 Cookie） |
| Python headers.get(name) | 字符串 | 只给第一行，其余丢弃 | 有损 |
| Python headers.get_all(name) | 列表 | 每行一项 | 无损 |

## 3. 实测要点

- 同样的请求字节，两个运行时：一个把两行拼起来，另一个只返回第一行。两边都没有报错
- 三个列表型字段（Accept / Cache-Control / Accept-Encoding）：两行等于一行逗号。确认语义完全一致
- 把两条 Set-Cookie 用逗号拼接再拆开：得到 4 个碎片（过期时间里的逗号把一条 Cookie 拦腰截断）
- 把两条没有过期属性的简单 Cookie 拼接：只存下 1 条。第二条被当成第一条的属性吸收掉了
- 两行 Host：两个运行时都返回 200，字符串 API 给出第一个值。数组 API 里两个值都还在
- 两行 Content-Length：一个运行时即使两值相同也在解析阶段返回 400，另一个四种情况全部返回 200
- 拼接后的字符串无法还原原本的行数（两行与一行加逗号会得到同一个字符串）
- 自制中继一跳：用字符串 API 读取时 2 行变 1 行，用数组 API 读取时仍是 2 行

## 4. 安全读取（JavaScript）

```js
// 列表型：两步（行数组 -> 每行按逗号拆分）
function readList(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  return lines.flatMap(v => v.split(',').map(s => s.trim())).filter(Boolean);
}

// 单值型：行数不为一就拒绝
function readSingleton(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  if (lines.length === 0) return { ok: true, value: null };
  if (lines.length > 1)   return { ok: false, reason: 'arrived ' + lines.length + ' times', lines };
  if (lines[0].includes(',')) return { ok: false, reason: 'comma inside a singleton', lines };
  return { ok: true, value: lines[0] };
}

// 绝不合并：保持数组
function readCookies(distinct) {
  return (distinct['set-cookie'] || []).slice();
}
```


- [ ] 把所有读取头部的位置列出来，按 **字符串 API / 数组 API** 分类

- [ ] 单值字段来了两行以上时 **不会静悄悄放行**（已用测试验证）

## 7. 不要做的事

- ❌ 对所有头部一律做逗号拆分的工具函数 — 会把值里面的逗号也切开
- ❌ 把 Set-Cookie 拼成字符串 — Cookie 会被切碎或整条消失
- ❌ 在单值字段上悄悄取第一个值 — 给不同层看到不同值留下了空间
- ❌ 假定「我们的前端不碰头部」 — 就算不改值，行的结构也会变
- ❌ 对列表型做排序或去重 — 到达顺序对语义是有意义的
- ❌ 只读产品文档就下结论 — 版本和配置不同结果就不同，要实测
- ❌ 只记录值的日志 — 来了两行这件事本身不会被记下来

复制后可直接粘贴到笔记应用或 AI 工具中。

常见问题

直接把重复头部封掉不就行了

封不住，也没有理由封。对列表型字段来说多行是合法的表达方式，而 Cookie 字段多行才是常态。一刀切地拦截会把正常请求搞坏。需要的不是拦截，而是按字段分别处理。第 8 节的三分类就是起点。

改用数组 API 会不会让代码变复杂

不需要处处都改，只改用于判断的字段就够了。只是打日志或显示在界面上的用途，字符串 API 完全够用。但认证、目标决定、正文长度、访问控制这类拿这个值去分支的地方，必须同时看清行数。实务里这样的地方通常一只手数得过来。

可以对值排序或者去重吗

列表型字段不行。RFC 9110 第 5.3 节明确指出同名字段行被接收到的顺序对解释是有意义的，并规定中继在转发时不得改变这个顺序。对承载偏好或优先级的字段来说，排序就是在改变语义。转成集合去重也因为同样的理由而危险。

产品文档里写的行为可以信吗

可以当起点，不能当结论。仅就本文验证过的部分来看，同一个请求在一个运行时是 400，在另一个是 200，而且还会随版本和配置而变。所以我的建议是直接照搬本文的方法：用原始套接字把字节写进去，在接收方用数组 API 数一数行数。二十行代码就够了。

能把本文的结果直接套到我们的基础设施上吗

不能。本文的数字是在写明的那两个运行时的特定版本上测出来的，不代表其他产品或其他版本。特别是第 7 节的中继，是为本文亲手写的二十行实现，与任何商用产品的行为都无关。要带走的是方法和分类，不是数字。对你自己的组件做同样的测量，把你的结果填进第 8 节的表里就行了。
