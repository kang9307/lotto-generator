SameSite Lax, Strict, None - Which Requests Drop Your Cookie

Why you were logged out the moment you came back from checkout, read off a per-request-shape verdict table

2026-07-31 Dev & Infra

The symptom: I came back from checkout and I was logged out

A user hits pay in the cart. The browser moves to an external payment screen, card details go in, the charge is approved. Then it comes back to our site. And the user is logged out. The payment went through fine, yet the order history page is unreachable.

Tickets like this usually get closed by extending session lifetime, by asking the payment provider, or simply as not reproducible. Yet the answer is often already sitting in the server log. The returning request has no session name in its Cookie header at all. Authentication did not fail; the cookie was never sent in the first place.

Deciding whether to send a cookie is not the server side of the conversation. It is the client. The attribute that drives that decision is SameSite, and it has exactly three values. But those three are not a straight line from strong to weak. They split differently for each shape of request.

  • Strict is never attached to a request initiated by another site. Not even when the user clicks the link themselves
  • Lax makes one exception: a move that changes the address bar using a safe method. Those two conditions are the heart of this article
  • None attaches to everything. In exchange, without Secure the cookie is not even stored

This article does not end at 「just switch to None」. That is leaving the door open without looking at the cause. Instead it builds a procedure: write down first which requests this cookie must ride on. Once the list exists, the value picks itself.

Environment. Everything below was actually run on Windows 10 Pro (10.0.19045) with Node.js v22.16.0 (win32). Two local servers were bound to arbitrary high ports (18081, 18082) and both were shut down when the runs finished. The normative basis is RFC 6265bis (draft-ietf-httpbis-rfc6265bis-22, 2025-12-01) plus MDN. Scripts were saved to files and executed, never passed as shell arguments or heredocs.

What this article could NOT verify directly. No browser was launched and no cookie jar was observed. So every 「the cookie rides / does not ride」 verdict is computed by implementing the spec text as code, not measured from a real browser. The table below carries a dedicated column marking which rows rest on the spec and which were measured. Re-check on your target browsers before shipping.

Out of scope. General web security and the full CSRF toolkit live in web security basics and IDS and IPS. This piece drills into one point only: how the SameSite values behave. Every domain, port and cookie name here is fictitious.

1. What the three values actually separate

The spec is terse. RFC 6265bis defines Strict as 「sent only along with same-site requests」, Lax as 「sent with same-site requests, and with cross-site top-level navigations」, and None as 「sent with same-site and cross-site requests」. The trouble is that those three sentences do not tell you which element on your page falls into which bucket. Is an image tag a top-level navigation? A form submission? An iframe?

So the decision rules were transcribed into code and run against every request shape a page can produce.

Read the table down the columns and all you learn is that None is the most permissive. It becomes useful when you read it across. Here are only the places where the values disagree.

--- 3-2. the same table, but only the differences that matter ---
  shapes where Strict and Lax disagree:
    - cross-site link click

  shapes where Lax and None disagree:
    - cross-site image load
    - cross-site script/css load
    - cross-site form POST

    - cross-site iframe load

  • Strict and Lax differ on exactly three rows. Link click, form GET, and returning via 302 to land as GET. All three share one trait: the address bar changes
  • Lax and None differ on everything else. Images, scripts, fetch, iframes and POST
  • In other words Lax reduces to 「never on subresources」. Another site pulling an image off our server does not carry our session. That is also why Lax became the default
  • Within the same site all three behave identically. Which means a test that only clicks around your own site will never surface the difference

2. What you get when you write nothing

The most common failure starts right here. A cookie with no SameSite attribute does not mean 「unrestricted」. RFC 6265bis says that when the attribute is absent or unrecognised, a default enforcement mode equivalent to Lax applies. MDN puts it the same way: 「If no SameSite attribute is set, the cookie is treated as Lax by default.」

That is how a checkout return breaks one day even though nobody touched a line of code. Your server side is unchanged; the default policy on the side that interprets the cookie moved. Writing nothing is not skipping a decision, it is handing the decision to someone else.

The worse case is writing it and having it not register. A parser was built to see what a typo in the value does.

--- 2-3. the silent-typo trap, side by side ---
  SameSite=Strict     -> Strict
  SameSite=strict     -> Strict
  SameSite=Strick     -> Default(Lax)   <- NOT what the author typed
  Samesite=Strict     -> Strict
  SameSite =Strict    -> Strict
  • SameSite=Strick is not an error. The value is unrecognised, so it quietly falls back to the default enforcement mode, which is Lax
  • Meanwhile the case of the attribute name and whitespace around the equals sign are harmless. Samesite and SameSite =Strict both parse correctly
  • So the only dangerous mistake is a typo in the value, and it is the one thing that changes policy without a warning
  • The practical defense is therefore to keep the value string in a constant and check it by eye in review. No syntax checker will catch this one for you

The default carries one more condition. The spec permits an optional compatibility mode called Lax-allowing-unsafe. For cookies that did not explicitly set SameSite, and only while they are very young, it may still attach on a cross-site POST. The spec notes that 「a cookie age of 2 minutes or less」 looks like a reasonable limit.

--- 3-3. the 2-minute window applied to a cross-site POST ---
  cookie age   10s  ->  maybe*   (explicit Lax would be: no)
  cookie age  119s  ->  maybe*   (explicit Lax would be: no)
  cookie age  121s  ->  no   (explicit Lax would be: no)
  cookie age 3600s  ->  no   (explicit Lax would be: no)
  a cookie that works in testing and fails in production may simply be older.

This is very often the real story behind 「it works on my machine」. The developer logs in and immediately clicks pay. The cookie is brand new. The real user logs in and checks out much later. The same code appears to behave differently over time. Since the mode is optional, it is a bonus when it happens and never a basis for design.

3. Use None without Secure and the cookie is thrown away

Switching to SameSite=None on sight of the symptom is a common reflex. There is a trap in it, and the trap raises no error whatsoever. The storage algorithm of RFC 6265bis contains this sentence: if the cookie same-site flag is None, then unless the secure-only flag is true, abort the algorithm and ignore the cookie entirely.

Whether the server really emits that header, and how the response looks when it does, was checked directly.

node v22.16.0 / win32   server 127.0.0.1:18081

--- 7-1. server emits it, the jar decides ---
recipe             HTTP status   what left the server                    jar verdict
-----------------------------------------------------------------------------------------------
None, no Secure    200 OK        sid=abc; SameSite=None                  REJECTED  (None without Secure)
None + Secure      200 OK        sid=abc; SameSite=None; Secure          stored  (None + Secure)
Lax, no Secure     200 OK        sid=abc; SameSite=Lax                   stored  (Lax)
Strict + Secure    200 OK        sid=abc; SameSite=Strict; Secure        stored  (Strict + Secure)
none + secure      200 OK        sid=abc; samesite=none; secure          stored  (None + Secure)
None; Secure=1     200 OK        sid=abc; SameSite=None; Secure=1        stored  (None + Secure)

  every row returned 200. the server never objects.
  row 1 is thrown away before it is ever stored, so no request will carry it.
  row 6 shows Secure is a valueless flag: Secure=1 still reads as present.

All six rows are 200 OK. The server has no objection to this combination. All the server does is put a string into a header; the decision to keep or discard happens on the other side.

--- 7-2. the failure you will actually observe ---
  HTTP/1.1 200 OK
  Set-Cookie: sid=abc; SameSite=None
  Date: Thu, 30 Jul 2026 20:33:11 GMT
  Connection: close
  Content-Length: 3

  response looks perfect. no 4xx, no log line, no exception.
  the symptom surfaces one request later, as a missing session,
  in a completely different part of the code. that is why it costs a day.

--- 7-3. why the rule exists, in one line ---
  SameSite=None means: send me on requests I did not initiate.
  Secure means: only over a protected transport.
  the spec refuses to let a cookie be maximally exposed and unprotected at once.
  • The failure never shows up in the response. Status code 200, nothing in the logs, nothing in exceptions
  • The symptom arrives one request later, in a completely different part of the code, as 「no session」. That is what makes it eat a full day
  • Secure is a valueless flag. As rows five and six show, writing it in lower case or as Secure=1 still reads as present
  • The rule is simple logic. None means 「send me even on requests I did not initiate」 and Secure means 「only over a protected transport」, so the spec refuses to permit a cookie that is maximally exposed and unprotected at once

Sequencing matters in practice. None presupposes https. If an internal tool still serves over plaintext, None is not an option on the menu but a prerequisite to fix first. Adding the __Host- prefix additionally forces Secure, Path=/ and no Domain, which blocks the mistake structurally.

4. How a Set-Cookie string is actually read

Once you know how a single Set-Cookie line is parsed, it becomes clear why the traps above are so quiet. The spec parsing procedure was implemented and fed ten strings.

node v22.16.0 / win32

--- 2-1. parsing ten Set-Cookie strings ---
input                                                              -> SameSite      Secure  note
---------------------------------------------------------------------------------------------------------
[sid=abc123; Path=/; HttpOnly; SameSite=Lax]                       -> Lax           false
[sid=abc123; path=/; httponly; samesite=lAx]                       -> Lax           false
[sid=abc123;SameSite=Strict;Path=/]                                -> Strict        false
[sid=abc123;    SameSite   =   None   ;   Secure  ]                -> None          true
[sid=abc123; SameSite=None]                                        -> None          false   DISCARDED (None without Secure)
[sid=abc123; SameSite=Loose; Path=/]                               -> Default(Lax)  false
[sid=abc123; SameSite; Path=/]                                     -> Default(Lax)  false
[sid=abc123; SameSite=Strict; SameSite=None; Secure]               -> None          true
[sid=abc123; Path=/; Flavour=vanilla; Priority=High; SameSite=Lax] -> Lax           false   ignored attrs: Flavour=vanilla, Priority=High
[sid=; Path=/; Max-Age=0]                                          -> Default(Lax)  false

--- 2-2. what the parser proved ---
  case of attribute name and value is irrelevant : true
  attribute order is irrelevant                  : true
  surrounding whitespace is stripped             : true
  unknown attribute drops the ATTRIBUTE only     : true  (ignored: Flavour=vanilla)
  duplicate attribute: last one wins             : None
  typo in the VALUE is not an error, it degrades : Default(Lax)   <- raw was [Loose]
  • Attribute names are case-insensitive. The spec says so outright: presented in CamelCase, but any case is accepted
  • Order is irrelevant. Writing Secure first or last gives the same result
  • Whitespace is stripped. Removing leading and trailing space from names and values is written into the procedure
  • An unknown attribute drops only that attribute. Something like Flavour=vanilla in the mix leaves the cookie itself alive. That is what lets new attributes be standardised without breaking old clients
  • When the same attribute appears twice, the last one wins. Row eight starts with Strict and ends up as None. This is where two pieces of middleware touching the same cookie go wrong
  • An unrecognised value is not an error, it is a demotion. Rows six and seven show it, and the typo trap of section 2 comes from here

The last row deserves attention too. sid=; Max-Age=0 is the idiomatic way to delete a cookie, and even there SameSite falls back to the default. If the deletion Set-Cookie does not match the original attribute combination, the delete silently fails to take. It is a common root cause behind a logout that does not log anyone out.

5. Domain, Path, and what counts as the same site

Looking only at SameSite gives you half the picture. Whether a cookie rides on a request is decided by passing three filters. The domain must match, the path must match, and only then does the SameSite verdict apply. The first two were checked first.

node v22.16.0 / win32

--- 5-1. host-only cookie vs Domain cookie ---
request host              no Domain attr   Domain=example.com
---------------------------------------------------------------
example.com               true             true
www.example.com           false            true
api.a.example.com         false            true
notexample.com            false            false
example.com.evil.net      false            false
  omitting Domain is the TIGHTER setting. adding it widens the blast radius.

--- 5-2. Path matching ---
Path=/app   request path        match
------------------------------------------
            /app                true
            /app/               true
            /app/orders         true
            /application        false
            /                   false
            /x/app              false
  /application does not match /app. the boundary is a slash, not a prefix.
  • Omitting Domain is the narrower setting. Omit it and the cookie goes only to the host that issued it. That is the exact opposite of the intuition that a default must be loose
  • Writing Domain=example.com sends it to every subdomain. Several levels down, like api.a.example.com, included
  • Similar names do not match. Neither notexample.com nor example.com.evil.net matches, because the suffix comparison requires a dot boundary in front
  • The boundary for Path is a slash. Path=/app does not match /application. That said, as MDN states flatly, Path is not a security measure

And then there is the word 「site」. In everyday speech it means roughly 「our service」, but here it has a precise meaning: scheme plus registrable domain. It is not the same thing as 「origin」, the word people reach for alongside it.

--- 5-4. what "same site" actually compares ---
A                              B                              same site?
---------------------------------------------------------------------------
https://app.example.com/       https://api.example.com/       YES
https://app.example.com/       https://example.com/           YES
https://app.example.com:443/   https://app.example.com:8443/  YES
https://app.example.com/       http://app.example.com/        no
https://app.example.com/       https://app.example.net/       no
https://shop.example.co.kr/    https://pay.example.co.kr/     YES
https://a.github.io/           https://b.github.io/           no
http://localhost:18081/        http://localhost:18082/        YES
http://localhost:18081/        http://127.0.0.1:18082/        no

--- 5-5. site vs origin, side by side ---
  URL    : https://app.example.com:8443/orders?x=1
  origin : https://app.example.com:8443        <- scheme + host + PORT
  site   : https://example.com     <- scheme + registrable domain, no port
  these two words are not interchangeable, and cookies use the second one.
  • A different port is still the same site. Cookies are not origin-scoped. That is why a dev server on 8443 ends up sharing cookies with production
  • A different scheme is a different site. http and https split apart
  • Under a public suffix one more label is consumed. shop.example.co.kr and pay.example.co.kr are the same site, but a.github.io and b.github.io are not. That is why static page hosting cannot read its neighbours cookies
  • localhost and 127.0.0.1 are different sites. Mixing them while faking cross-site locally creates an unintended cross-site condition, while changing only the port fails to reproduce cross-site at all

One design consequence follows. Splitting into subdomains creates no isolation whatsoever from the SameSite point of view. Carving out a separate payment domain still leaves it the same site if it sits under the same registrable domain, and even a Strict cookie rides on moves between them. If you want isolation, look at separating the domain itself or at dropping the Domain attribute.

6. The path by which a login comes undone, step by step

Now back to the opening symptom. In a flow that leaves for an external payment or identity provider and comes back, the question is at precisely which point the cookie disappears. There is exactly one fork: the method you return with.

This part is not a rule but a measurement. Two local servers were started, one redirecting to the other, and the landing method was measured per status code after going out as a POST.

node v22.16.0 / win32
provider 127.0.0.1:18082  ->  app 127.0.0.1:18081/return

--- 4-1. we POST to the provider; it redirects us back. which method lands? ---
redirect status   we sent   we landed with   Lax cookie would ride?
---------------------------------------------------------------------------
301               POST      GET              yes - safe method
302               POST      GET              yes - safe method
303               POST      GET              yes - safe method
307               POST      POST             NO  - unsafe method
308               POST      POST             NO  - unsafe method

  measured with an HTTP client on this machine, not with a browser.
  the method rewrite on 301/302/303 is the whole ballgame:
  307 and 308 preserve POST, and a Lax cookie is withheld on arrival.
  • 301, 302 and 303 rewrite the method to GET on landing. That satisfies both of the Lax conditions, top-level navigation and safe method, so the cookie rides
  • 307 and 308 preserve POST. The landing request becomes a cross-site POST, and under Lax the cookie is withheld
  • This difference is not in our code at all; it is one number on someone else configuration screen. Our side can stay still while the symptom appears and vanishes
  • Under Strict the cookie is withheld regardless of the method. Landing as GET via 302 changes nothing
  • Auto-submitting a form to hand the result back as a POST behaves the same way. It merely does not look like a redirect; it is still a cross-site POST
--- 4-2. the redirect chain, step by step ---
  step 1  POST http://127.0.0.1:18082/go?code=307
          <- 307 Location: http://127.0.0.1:18081/return?via=307
  step 2  the client repeats the request at the new URL
          this second request is cross-site AND it is a POST
          -> Strict: withheld.  Lax: withheld.  None+Secure: sent.

--- 4-3. same chain, but the provider returns us with 303 ---
  landed method : GET   (the body was dropped)
  -> Strict: still withheld (cross-site).  Lax: sent.  None+Secure: sent.
  one number in the provider config moves the session between present and absent.

--- 4-4. and the second hop, once we are back on our own site ---
  same-site GET landed with method GET
  this is why the bug looks intermittent: reload the page after landing
  and the next request IS same-site, so Strict starts working again.

6.1 Broken into six steps

  1. The user hits pay on our site. Up to here everything is same-site and all three values behave normally
  2. The browser moves to the provider domain. Our cookie plays no part in this leg
  3. The provider sends the approval result back to our return URL. This request is cross-site
  4. If the return is a GET, the Lax cookie rides and the login survives
  5. If the return is a POST, the Lax cookie is withheld. The server sees a request from a logged-out user and renders the login screen
  6. The moment the user clicks anything on that screen, it is same-site from there on and the cookie returns. Hence the follow-up report of 「it worked after I refreshed」, and hence the ticket closed as not reproducible

The remedy order falls out of this. Loosening the value to None is the last resort. First consider changing the return hop into a thin endpoint that accepts GET. If you need the result payload, take that payload over a server-to-server notification and send the browser back with GET only. The symptom disappears without widening the cookie policy at all.

7. Size and count: there are two ceilings, not one

There is another route by which a session disappears: the cookie is too large to be stored. The spec is explicit. If the sum of the lengths of the name and the value exceeds 4096 octets, abort the algorithm and ignore the Set-Cookie string entirely.

node v22.16.0 / win32
max HTTP header size this runtime accepts: 16384 bytes

--- 6-1. the 4096-octet line, name + value together ---
name len   value len   sum     jar keeps it?
-----------------------------------------------
3          4093        4096    true
3          4094        4097    false
3          4095        4098    false
500        3596        4096    true
500        3597        4097    false
  the limit counts the NAME too. renaming session_identifier to sid buys you bytes.

--- 6-2. an oversized cookie is dropped whole, not truncated ---
  value length          : 5000
  jar keeps it          : false
  what the app receives : nothing at all
  no error, no warning, no half-value. the next request simply has no session.
  • The name counts toward the length. Shortening session_identifier to sid buys exactly that many bytes for the value
  • It is discarded whole, not truncated. You do not get a prefix; you get nothing
  • So the symptom reads as 「there is no cookie」 rather than 「the value looks wrong」. That is why it takes so long before anyone suspects size
  • Non-ASCII text or emoji change the arithmetic again. The unit is octets, so you must count bytes after encoding, not characters

There is more than one ceiling. Above the cookie jar limit sits a separate limit: HTTP header size. This one was tested against a real server.

--- 6-3. many cookies at once, measured against a real server ---
count   Cookie header bytes   server response
-------------------------------------------------------
10      856                   200 OK  cookies=10 bytes=848
50      4296                  200 OK  cookies=50 bytes=4288
100     8596                  200 OK  cookies=100 bytes=8588
180     15556                 200 OK  cookies=180 bytes=15548
300     25996                 431 Request Header Fields Too Large
  past the runtime header budget the request dies before your code runs.
  the cookie jar has its own per-domain cap on top of this. two ceilings, not one.

--- 6-4. every cookie rides on EVERY matching request ---
  one 1.2 KB cookie             : 1204 bytes per request
  60 requests to render a page  : 72240 bytes uploaded, per page view
  and Domain=example.com sends it to the image host and the API host too.
  this is the real argument for keeping an identifier in the cookie and state on the server.

180 cookies (15,556 bytes) passed and 300 cookies (25,996 bytes) came back 431. The crucial part is that the application code never ran. None of your logs, none of your exception handling, none of your error pages. That is how you get a report saying 「the whole site is broken, but only for this one user」, cured by clearing that user cookies. This is exactly what MDN means by 「cookies are sent with every request, so they can worsen performance」.

8. Why the server cannot know the reason

There is a structural reason why this is hard to diagnose. What the server sends and what it receives are not symmetric.

node v22.16.0 / win32
server A 127.0.0.1:18081   server B 127.0.0.1:18082

--- 1-1. exact Set-Cookie bytes the server puts on the wire ---
recipe            Set-Cookie line as received
---------------------------------------------------------------------------
no-attr          Set-Cookie: sid=abc123; Path=/; HttpOnly
lax-explicit     Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Lax
strict           Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Strict
none-no-secure   Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None
none-secure      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None; Secure
bogus-value      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Loose
weird-case       Set-Cookie: sid=abc123; path=/; httponly; samesite=lAx

--- 1-3. what the server sees when a client sends a Cookie header ---
  with Cookie header : cookie-header-seen: sid=abc123; theme=dark
  without            : cookie-header-seen: (none)
  the server cannot tell WHY a cookie is missing. absent == never-sent == blocked.

--- 1-4. no SameSite attribute survives into the Cookie header ---
  cookie-header-seen: sid=abc123
  Cookie: carries name=value only. no Path, no Domain, no SameSite.
  the server gets no evidence of which policy was applied.
  • Set-Cookie carries every attribute. Path, HttpOnly and SameSite all go out on the wire
  • The returning Cookie header carries only names and values. Not one bit of information about the policy under which it was stored
  • So the server cannot distinguish why a cookie is missing. A logged-out user, a block by SameSite, a storage refusal for exceeding the size limit, or a user who cleared it by hand all look identical
  • You are left inferring from the request side. Check Origin and Referer for where it came from, check the method, and cross-reference that combination against the table in section 1

The practical countermeasure is therefore logging. Record the method, Origin and Referer for any request that arrives without a session, and a single cross-reference against the verdict table narrows the cause dramatically. Without that one log line you burn days on reproduction attempts.

9. What goes where, and how to pick the value

By this point the question has changed. It is not 「which value is best」 but 「what belongs in the cookie」 first.

The principle is two lines. Put only an identifier in the cookie. Keep state on the server. The two ceilings in section 7 are the justification, and following it makes the size problem and the bandwidth problem vanish together. Then write down which requests that identifier must ride on, and the value falls straight out of the list.

Display preferences such as language or themenoLaxSecure, consider local storage
  1. Write down every case where this cookie must ride on a request initiated by another site. If there are none, write that down too
  2. If the list is empty, use Lax. If you are confident it is unnecessary even for top-level navigation, narrow it to Strict
  3. Only when the list is non-empty do you reach for None, and then you write Secure alongside it. And leave that list in a comment or a document. It stops the next person from widening it again for want of a reason

One line to draw clearly at the end. SameSite is a CSRF mitigation, not the whole of CSRF defense. MDN says it 「provides some protection against cross-site request forgery attacks」, not that it solves them. Whatever the value, state-changing requests still need separate token validation. The broader shape of web security is in web security basics, and the detection layer in IDS and IPS.

The signature symptom column is the most useful one in the field. Reading the symptom and tracing back to the value is far faster than deploying one value after another to see what sticks.

10. Checklist

  • The session cookie states its SameSite value explicitly (no leaning on defaults)
  • Every cookie using None also carries Secure
  • The reason for None can be written out as a list of requests
  • The status code and method of the external payment or OAuth return hop were checked
  • If the return hop is a POST, a separate thin GET endpoint exists
  • The Domain attribute is set only where it is genuinely needed (omitting is narrower)
  • The design accounts for subdomains grouping into the same site
  • Local tests do not mix localhost and 127.0.0.1 by accident
  • Each cookie keeps name plus value under 4096 octets
  • Cookie count and total bytes per domain were actually measured
  • There is no typo in the SameSite value string (a typo silently becomes the default)
  • Requests arriving without a session get their method, Origin and Referer logged

11. Misconceptions and things not to do

  • ❌ Switching to None the moment symptoms appear — first list which requests actually need it
  • ❌ Using None and forgetting Secure — the cookie is discarded at storage time
  • ❌ Relying on the default — an unspecified cookie follows whatever the interpreting side decides
  • ❌ Verifying only on localhost — a local setup that only varies the port cannot reproduce cross-site conditions
  • ❌ Believing subdomain separation gives isolation — under the same registrable domain it is the same site
  • ❌ Treating SameSite as the whole of CSRF defense — it is a mitigation, not the defense itself
  • ❌ Stuffing entire session state into the cookie — you pay both the 4096-octet ceiling and per-request bandwidth

One last thing. Do not assert version-specific browser behavior. The scope of the default, whether Lax-allowing-unsafe is adopted, and how partitioned storage is handled can differ between implementations and change over time. The spec settles what is permitted; it does not guarantee that every implementation behaves alike. Building a step that verifies on your target browsers before rollout is the only countermeasure that never ages.

# SameSite Cookies — Value Decision Table and Per-Request-Shape Verdict Table

> Source: braindetox.kr — SameSite Lax, Strict, None: which requests drop your cookie
> Basis: RFC 6265bis (draft-ietf-httpbis-rfc6265bis-22, 2025-12-01) + MDN
> Ran on: Windows 10 Pro 10.0.19045 / Node.js v22.16.0 (win32) / two local servers
> **Stated limit**: real browser cookie-jar behavior was NOT verified here.
> The verdict cells below are **computed by implementing the spec text as code**. Re-check on your target browsers before shipping.

## 1. Verdict table by request shape

Cookie was set by: `https://app.example.com`
Request originated from: `https://portal.other-site.com`

| Request shape | Strict | Lax | None+Secure | no attribute | Basis |
|---|---|---|---|---|---|
| Page-to-page move inside the same site | sent | sent | sent | sent | spec |
| Link click from another site | **withheld** | sent | sent | sent | spec |
| Image loaded by another site | withheld | withheld | sent | withheld | spec |
| Script or CSS loaded by another site | withheld | withheld | sent | withheld | spec |
| form GET from another site | **withheld** | sent | sent | sent | spec |
| form POST from another site | withheld | **withheld** | sent | withheld | spec |
| fetch or XHR from another site | withheld | withheld | sent | withheld | spec |
| Loaded inside an iframe | withheld | withheld | sent | withheld | spec |
| Same-site fetch | sent | sent | sent | sent | spec |
| Returned via 302, landing as GET | **withheld** | sent | sent | sent | spec + landing method measured |
| Returned via 307, landing as POST | withheld | **withheld** | sent | withheld | spec + landing method measured |

Two lines to remember:

- **Strict and Lax differ on exactly three rows: top-level navigation with a safe method.**
- **Lax and None differ on subresources and POST, which is everything else.**

## 2. Value decision table

| What the cookie holds | Needed on cross-site requests? | Recommended value | Set alongside |
|---|---|---|---|
| Login session identifier (ordinary web app) | no | `Lax` | `Secure` `HttpOnly` `Path=/` |
| Login session + external payment or OAuth return | only at the return hop | `Lax` + make the return a **GET** | `Secure` `HttpOnly` |
| Admin console or internal tool | no | `Strict` | `Secure` `HttpOnly` `__Host-` prefix |
| CSRF token (double-submit pattern) | no | `Strict` or `Lax` | `Secure`, no `HttpOnly` |
| Widget or SSO iframe embedded on third-party pages | yes | `None` | **`Secure` required** + consider `Partitioned` |
| Advertising or analytics identifiers | yes | `None` | `Secure`, design for being blocked |
| Display preferences such as language or theme | no | `Lax` | `Secure`, consider local storage instead |

**The selection procedure is three sentences.**

1. Write down the list of **cross-site-initiated requests** this cookie must ride on.
2. If the list is empty, use `Lax`. If it is empty even for top-level navigation, use `Strict`.
3. Only when the list is non-empty do you reach for `None`, and then `Secure` is **mandatory**.

## 3. The three values at a glance

| Value | One-line definition | Signature symptom |
|---|---|---|
| `Strict` | Rides only on same-site requests | First screen after an inbound external link is logged out |
| `Lax` | Same-site plus **top-level navigation with a safe method** | Session vanishes when payment or OAuth returns you by POST |
| `None` | Rides on every request | Drop `Secure` and the cookie is never stored at all |
| (absent) | Treated the same as `Lax` | Nobody touched the code and one day it broke |

## 4. Set-Cookie authoring rules (confirmed with a parser)

- Attribute **names and values are case-insensitive**. `samesite=lax` equals `SameSite=Lax`
- Attribute **order does not matter**. `Secure; SameSite=Lax` equals `SameSite=Lax; Secure`
- **Whitespace around the equals sign is stripped**. `SameSite = None` parses fine
- **An unknown attribute drops only that attribute.** The cookie itself survives
- **If the same attribute appears twice, the last one wins**
- **A typo in the value is not an error.** `SameSite=Strick` silently becomes the default (Lax)
- `Set-Cookie` goes server to client; `Cookie` goes client to server. **The `Cookie` header carries name=value only.** The server has no way to see which policy was applied

## 5. Diagnosis order for a session that keeps dropping

1. Check your server log for whether the failing request **carried the session name in its `Cookie` header**. If not, this is a cookie problem, not an auth problem
2. Check whether that request was **initiated from another site**. If same-site, SameSite is not your culprit
3. Check the request **method**. If it is `POST`, a `Lax` cookie being withheld is correct behavior
4. Check **which status code** the external service sends you back with. 301, 302 and 303 land as GET; **307 and 308 preserve POST**
5. Change the landing hop into a **thin endpoint that accepts GET**. Do this before you loosen the value to `None`
6. If it still fails, make the landing page issue **one more same-site request** and check the session there

## 6. Size and count ceilings (measured)

- The per-cookie limit is **name length + value length no greater than 4096 octets**. The name counts
- Exceeding it does not truncate; the cookie is **discarded whole**. No error, no warning
- The HTTP header budget in the test runtime was **16384 bytes**, and 300 cookies (25996 bytes) produced a **431 response**. Application code never ran
- Cookies ride on **every matching request**. One 1.2 KB cookie across 60 requests per page uploads roughly 72 KB per page view
- Hence the single rule: **identifier in the cookie, state on the server.**

## 7. Checklist

- [ ] The session cookie **states its `SameSite` value explicitly** (no leaning on defaults)
- [ ] Every cookie using `None` **also carries `Secure`**
- [ ] The reason for `None` can be written out **as a list of requests**
- [ ] The **status code and method of the external payment or OAuth return hop** were checked
- [ ] If the return hop is a `POST`, a separate thin **GET endpoint** exists
- [ ] The `Domain` attribute is set **only where actually needed** (omitting it is narrower)
- [ ] The design accounts for **subdomains counting as the same site**
- [ ] Local tests do not **mix `localhost` and `127.0.0.1`** (they are different sites)
- [ ] A different scheme means a different site (http vs https) was verified
- [ ] Each cookie keeps **name plus value under 4096 octets**
- [ ] Cookie **count and total bytes per domain** were measured
- [ ] There is **no typo** in the `SameSite` value string (a typo silently becomes the default)
- [ ] `HttpOnly` is set on session cookies
- [ ] CSRF defense does **not rest on SameSite alone**

## 8. Do not

- ❌ Switch to **`None` the moment symptoms appear** — decide which requests need it first
- ❌ Use `None` and **forget `Secure`** — the cookie is discarded at storage time
- ❌ **Rely on the default** — an unspecified cookie follows whatever the implementation decides
- ❌ **Verify only on `localhost`** — local setups do not reproduce cross-site conditions
- ❌ **Assert version-specific browser behavior** — implementations differ, so check your targets
- ❌ Treat SameSite as **the whole of CSRF defense** — it is a mitigation, not the defense
- ❌ Stuff **entire session state into the cookie** — you pay in both size limit and bandwidth
