如何把AI助手真正用在工作里

不是功能介绍而是边界线 - 用任务类型划分它适合什么、不适合什么

2026-07-29 IT/技术

引言：「AI能不能做这个」是一个没法回答的问题

这个问题没有答案，因为对几乎所有任务，答案都是「它会给出点什么」。真正的问题不是能不能做，而是把它给出的东西变成可用状态需要多少成本。不算这笔账，就会出现越用工具活越多的区间，而且没有任何机制让你察觉。

所以本文不罗列功能。要回答的问题只有一个：「我现在要做的这件事，属于可以交出去的那一类吗。」 要回答它，需要的不是宣传语，而是两样东西。一是这些模型是怎么造出来的，因而会怎样失败；二是我能以多低的成本核验结果。

先把原则钉死。本文写到的产品事实全部于2026年7月29日在官方文档中直接确认，无法确认的数字一律略去。模型阵容、价格、用量上限都是几个月就会变的项目，所以本文在这些位置放的不是数字，而是确认流程。本文也不判定哪家服务更好，排名是别的文章的事，这里讲的是无论用哪个工具都同样适用的边界线。

不夸大也不贬低。「AI全都能干」是错的，「没什么用」也是错的。正确的说法后面永远跟着条件。

1. 边界来自机制 - 为什么有些活擅长有些活不擅长

不必把长处和短处分开记。两者出自同一种性质，理解了这一种性质，两份清单会自己长出来。

核心是这样。这些模型不是由人一行行写下规则的程序。 Anthropic的可解释性研究对此说得很清楚：模型用大量数据训练，自己形成解决问题的策略。这些策略不是人设计的流程，而是装在训练过程中形成的内部计算里。同一项研究还补上一个关键观察：模型讲述的解法与实际发生的计算可能并不一致。

最鲜明的例子是加法。研究人员观察到，模型会并行运行一条估算大致数值的路径和一条确定末位数字的路径。可是当被问到怎么算的，它却描述学校里教的那套带进位的标准算法，给出的说明与真正跑过的过程不同。同一项研究还描述了模型从想要的结论倒推理由的动机性推理，并指出它可能产出听起来合理却并不反映实际计算的步骤。

长处和短处从这同一种性质里一起长出来。列成表是这样：

性质由此产生的长处同一性质带来的短处
策略来自数据而非规则对形式不固定的语言任务很灵活在只有一个正确答案的流程性任务上跑偏
很擅长写出貌似合理的延续起草、摘要、改写都很快不知道的时候也会写出合理的句子
说明与实际过程可能分离会附上人类易读的理由陈述那段理由无法充当验算
学习的时点是固定的沉淀的通识面很宽此后的事实在结构上并不存在
在给定的上下文里作答对贴进去的材料处理精度高没有内部数据就不了解组织的实情

表格右边两列不是两份清单，而是同一个格子的正反两面。所以去找一个「能修好短处的设置」，方向就错了。要修的不是工具，而是任务的分配。

最新信息的问题也可以用同样的方式理解。官方文档会逐个模型标注知识最为充分、最可信的时点。按2026年7月29日的标注：Claude Opus 5是2026年5月，Claude Fable 5与Claude Sonnet 5是2026年1月，Claude Haiku 4.5是2025年2月。该时点之后的事实不在模型里。 接了搜索工具就能去查，没接的时候去问，上一段那种性质意味着它可能不说没有，而是造出来。

2. 适合的六类活 - 共同点是「答案可以有多个，由人来挑」

下面六项看起来各不相同，却有一个共同条件：成果可以有多种，人始终握着最终选择权，出错时立刻能看见。

  • 起草 — 消掉从空白页开始的成本。草稿按定义就是拿来改的，所以里面有错损失也小。这里得到的不是成品，而是可供编辑的对象。
  • 格式转换 — 把散文变成表格、表格变成JSON、日志变成整齐的清单。没有新信息被造出来，只是重新排列，所以把原件放在旁边核验几乎是免费的。
  • 摘要 — 从长材料里抽出发生过什么。因为原文还在，可疑的那一行可以回原文比对。重要的是，一旦丢掉原文只留摘要，这个优势就消失了。
  • 代码审查的第一遍 — 在人看之前先筛掉明显的问题。某条意见对不对，打开代码当场就能判定，这正是核验便宜的含义。
  • 头脑风暴 — 目的是把选项变多，所以错的点子也不算成本。反正由人来挑，差的候选还能帮你划出好候选的边界。
  • 为陌生领域画地图 — 用途是在第一次接触的领域里搞清楚该去搜什么。目标不是拿到答案而是拿到术语和分支，所以后续调研自然会把它纠正过来。

六项浓缩成一句话就是「人仍然是判断主体的任务」。反过来，一旦人把结果原样送进下一道工序，同一件事就滑进下一节的清单。

3. 不适合的五类活 - 共同点是「答案只有一个且代价很大」

下面五项不会因为工具更完善而改变性质，因为它们直接从第1节的性质推出来。

  • 未经核实的事实确认 — 最常见也最昂贵的误用。对模型来说，写出一句貌似合理的话比说不知道更自然。Anthropic官方文档推荐的第一条缓解手段就是明确允许它承认不确定，这件事本身就反证了这种性质：需要专门写下这条许可，说明那并不是默认行为。
  • 最新信息 — 知识时点之后的事实没有。不接搜索工具去问，无法被告知某样东西缺失的风险原样留着。价格、版本、人事、法规修订这类以变动为本质的项目尤其危险。
  • 精确计算 — 第1节的加法例子原样适用。结果有时是对的，但说明与实际过程不同，因此无法用说明来验算。金额、比例、截止日的计算交给计算器或电子表格，模型只负责到把算式列出来为止更安全。
  • 法律医疗税务的最终判断 — 这里答错的代价不对称地大，而正确答案还会随管辖、时点和个案情况变化。用来理解背景，或者整理出该向专业人士提出的问题很有用，但不能让它替代结论。
  • 没有内部数据的决策 — 在不了解本单位真实数字、合同条件、人力状况和内部约束的情况下给出的建议是泛泛之论。泛泛之论在会上很难反驳，因此反而危险。把材料贴进去再问情况就不同，但那时候要先过下一节的输入管理。

五项的共同点是「答案只有一个，错了很难回退」。第2节与第3节的边界线画在任务的结构上，而不是画在工具有多聪明上。

4. 核心标准 - 核验成本超过写作成本就别用

不必每次都背前面两份清单，它们可以压缩成一条标准。

AI产出的东西不是拿来直接用的，而是必须过一遍检查的。 因此真正省下的时间是「写作时间减去核验时间」，不是「写作时间」。这个减法为负的区间确实存在，在那个区间里使用工具会变慢或者变危险。变慢还算好的，更常见的是省掉核验而滑向危险那一侧。

这条标准在官方文档里有依据。那篇讲减少幻觉的文档在结尾明确写道，这些方法并不能完全消除幻觉，尤其在重要判断上必须始终核验信息。也就是说，核验不是可选项而是成本项。既然是成本项，就得算。

任务核验方式核验成本结论
把会议记录整理成决定、负责人、期限与原件并排比对低交出去
把表格转成JSON或CSV核对行数与抽样几行，用解析器跑一遍低交出去
撰写报告初稿反正人会从头改到尾低交出去
代码改动的第一遍审查打开被指出的行，跑测试低交出去
整理陌生领域的术语与分支后续调研会自然纠正低可以交，但不当结论用
内部文档摘要（保留原文）只对可疑句子回原文确认中有条件地交出去
引用没有出处的统计数字必须自己去找一手来源高不交
引用法规、判例或条款必须去查原文条款高不交
金额、税额、剂量的计算最后还是要拿计算器重算高把计算交给别的工具
确认最新价格、版本或规定还得重新打开官方页面高一开始就去官方页面

表中核验成本低的那些行只有一个共同点：核验所需的材料已经在手边。会议记录原件、原始表格、代码、测试都是如此。相反，成本高的那些行都得往外跑一趟才能确认，这段路程正好把省下的时间吃掉。

写成当场可用的形式是这样：

  • 核验材料已经在对话里，就交出去 — 对贴进去的文档做摘要、转换、抽取都属于这一类。
  • 要往外跑才能核验，就一开始往外走 — 反正都要打开官方页面，没理由把顺序颠倒。
  • 想省掉核验的念头本身就是信号 — 想省是因为核验贵，而贵这件事已经把答案说出来了。
  • 先定好错了谁负责 — 如果责任在自己，核验就不是可谈判的，而是成本。

5. 输入管理 - 什么东西不能放进去

只管输出不管输入，后面惹出的麻烦会大过前面省下的时间。要确认的有两层：服务方如何处理数据，以及所在组织的规定，两者不能互相替代。

2026年7月29日在Anthropic官方隐私说明里确认到的内容是这样：在个人版套餐中，只有当用户自己开启了用于改进模型的选项，对话和编程会话才会被用于改进模型，另有被标记为安全审查等其他情形一并说明。文档明确写道，无痕对话即使开启了该设置也不会用于改进Claude。而商用产品与API适用另外的条款，并链接到另一份文件。也就是说，同一家公司的产品，用哪个产品、开哪个设置，处理方式都不一样。这正是不能跳过自己去打开设置页面确认这一步的原因。

而且服务方允许与所在单位允许是两回事。公司设备、公司账号、公司资料另有单位规定，而且往往更严。

输入类型默认判断原因替代做法
密码、API密钥、令牌等凭据绝对不放一旦泄露立即造成损害换成占位符，真值放进密钥管理工具
身份证件号、银行账号、卡号绝对不放受法律保护且是不可替代的标识符只保留格式，去掉数值
客户实名、联系方式、住址不放会引出超目的使用与第三方提供的问题化名为客户A、000-0000-0000
未公开的财务数字、合同条件确认单位规定前不放牵涉商业秘密与信息披露规则把数值换成比例或相对值再提问
公司内部源码取决于规定与产品类型商用产品与个人版套餐条款不同只在获准的工具与账号上，只放必要文件
公开文档、标准、论文可以放本来就是公开材料无限制，但引用要回原文核对
自己写的草稿与笔记基本没问题是自己的作品，没有敏感信息就风险低只需检查是否混入了第三方信息

实务上化名处理能解决大部分问题。把「请分析客户张某三月营收4200万为何环比下滑」换成「客户A三月营收环比下滑18个百分点」，答案质量几乎不变，因为模型需要的是结构而不是身份。觉得去掉姓名和真实数字结果就会变差的直觉，通常没有依据。

6. 实务流程（一） - 会议纪要、文档初稿、格式转换

从这里开始按实际使用的样子写。每个流程都把提示结构和核验方式成对给出。没有核验方式的流程不是流程，是赌博。

写提示时的原则在官方提示指南里有整理。文档建议像对一位缺少你这边背景的聪明新同事解释那样，写得清楚而直接，并给出一条自检：把提示拿给同事看，如果他会困惑，模型也会困惑。文档还写道，把指令的理由和动机一并写上会让结果更好，而用XML标签把指令、背景、输入分区能减少误读。下面的模板就是照这套建议来的。

流程A - 从会议记录里提取决定与待办

<角色>
你是负责整理会议记录的执行人员。
</角色>

<目的>
这份整理稿给没能参会的同事看。
所以决定和负责人比背景说明更重要。
</目的>

<规则>
1. 只用记录里写到的内容，不要靠推测补齐。
2. 负责人或期限没有定下来，就写「待定」。
3. 算不算决定不清楚的发言，另外归入「暂缓事项」。
4. 每一条末尾原样引用一句作为依据的发言。
</规则>

<输出格式>
## 决定事项
- 决定 | 负责人 | 期限 | 依据发言
## 待办事项
- 待办 | 负责人 | 期限 | 依据发言
## 暂缓事项
- 议题 | 原因
</输出格式>

<会议记录>
（贴在这里）
</会议记录>
  • 核验 — 把每条后面的依据发言拿去在记录里做字符串搜索。搜不到，那一条就是编的。
  • 为什么要求引用依据 — 官方文档提到，处理长文档时先让它抽出逐字引用，能把回答绑在真实文本上从而减少幻觉。这里把那个方法当作核验装置来用。
  • 为什么允许「待定」 — 填空的压力就此消失。给它一个说不知道的位置，正是第一条缓解手段。

<素材>

</素材>

  • 核验 — 先看「待确认」清单。如果它是空的而初稿里却有具体数字，那些数字就是造出来的。
  • 为什么约束写得长 — 官方指南建议具体指定想要的输出格式与约束。把字数和段落数钉成数字，比说「简洁一点」有效得多。
  • 待确认清单的作用 — 让模型把空缺报上来而不是自己填。核验点从整篇文档缩小到几行。

7. 实务流程（二） - 代码审查、陌生领域、学习辅助

流程D - 代码审查的第一遍

<角色>
你是在人工审查之前先过一遍这份改动的初审者。
最终判断由人来做。
</角色>

<审查顺序>
1. 这次改动可能弄坏的既有行为
2. 缺少输入校验的地方
3. 没有错误处理的路径
4. 需要测试却没有测试的部分
5. 可读性差的部分（放在最后，简短写）
</审查顺序>

<规则>
- 不要对没打开过的文件做推测。
  代码不在这里，就只写「需确认：文件名」。
- 每条意见都要写出文件与行号。
- 用高、中、低标出把握程度。
- 把握低也不要删掉，全都写出来。筛选是我的活。
</规则>

<改动>
（贴入diff）
</改动>
  • 核验 — 真的去打开被指出的那些行。代码审查里意见的真假当场就有定论，所以它是核验最便宜的任务之一。
  • 禁止推测这一条的依据 — 官方提示指南在讲如何减少编程任务的幻觉时，举的例子正是不要对没打开过的代码做推测，先把文件读了这类指令。上面的规则就是把那个形式搬过来。
  • 为什么要求标把握程度 — 说「只讲重要的」会连真的缺陷一起筛掉。把筛选这一步挪到人这边，回收率更高。

流程E - 为陌生领域画地图

我第一次接触<领域>。我要的不是答案，
而是想知道自己该去调研什么。

请按下面的顺序整理。

1. 理解这个领域所需的核心概念5到8个
   - 每个概念用一行说明
2. 实务中会分岔的主要选项，以及决定这些选择的标准
3. 新手常有的三个错误前提
4. 我应当自己去核对的一手来源属于哪一类
   - 是标准文件、官方手册，还是法规
5. 这个主题里最近很可能已经变过的项目
   - 标出可能落在你知识时点之后的部分

每一项都标出把握程度，
把握低就写低。不知道就写不知道。
  • 核验 — 这个流程是用来拿检索词而不是拿结论的。真正去打开第4项点名的一手来源，错误就在那一刻被纠正。
  • 第5项的意义 — 让它自己标出可能落在知识时点之后的部分。前面说过每个模型标注的知识时点不同，所以这一项就等于「必须到外面确认的清单」。
  • 不当结论用 — 这一步的产出是地图不是目的地。把地图当成目的地，是这个流程唯一的失败方式。

流程F - 学习辅助

下面写的是我对<主题>的理解。
请以对话伙伴而不是阅卷人的身份回应。

<我的理解>
（在这里用自己的话讲一遍）
</我的理解>

顺序：
1. 先指出我的说明里与事实不符的部分，并说明理由。
2. 指出对了但表述不准确的部分。
3. 告诉我漏掉了哪些重要条件或例外。
4. 提三个能检验我是否真的理解的问题。
   - 不要提前给答案。
5. 列出这个主题里我必须回原文确认的项目。

不要给我总结正确答案，而要让我再讲一遍。
  • 核验 — 自己去回答第4项的问题就是核验。答不上来就说明没理解，这个结构会让这件事立刻显形。
  • 为什么禁止总结 — 拿到总结会让人觉得读懂了，但复述的能力并不会长进。把讲述留在人这一侧，就是这个提示的全部用意。
  • 第5项的作用 — 把学习内容里需要回原文确认的项目分离出来，等于把复习范围和核验范围分开。

8. 提示要写成结构，不要写成句子

前面六个模板看着长，原理却只有几条，而这些原理都白纸黑字写在官方指南里。需要记住的是下面六条。

  • 写得清楚而直接 — 文档建议像对一位缺少背景的聪明新同事解释那样写，并给出自检：同事看了那段指令会困惑，模型也会困惑。「你看着办」不是指令。
  • 把理由一并写上 — 同一份文档写道，说明指令背后的动机会让结果更好。「不要用省略号」不如「这段文字会被语音朗读，所以不要用省略号」。
  • 放三到五个示例 — 文档称示例是决定输出格式与语气最可靠的手段，并建议放三到五个既贴近真实场景又彼此差异足够的示例。
  • 用XML标签分区 — 指令、背景、示例、输入混成一团，解读就会飘。文档建议把每一类各自用标签包起来。
  • 长材料放上面，问题放下面 — 文档建议处理超过两万个词元的材料时，把长文档放在提示的上部、问题与指令之上，并提到有测试显示把问题放在末尾能让复杂多文档输入的回答质量最多提升30个百分点。
  • 给它一个说不知道的位置 — 减少幻觉那份文档的第一条就是明确允许它承认不确定。「不确定就写不确定」这一行确实有效。

还要补一条。官方文档明确写道，并非所有问题都该用提示工程来解；例如延迟和成本，有时换一个模型比打磨提示更容易改善。如果提示改了五遍还是同一种失败，那多半不是提示的问题而是任务分配的问题，这是该回到第3节清单的信号。

想更深入看方法本身，另有轴线不同的文章。基础在提示工程基础，思维链与链式调用之类的进阶方法在进阶提示方法里讲。本文不讲方法清单，只讲要不要把这件事交出去的判断。

9. 模型与套餐 - 与其记数字不如有一套确认流程

这一节故意很少出现数字，因为模型阵容与价格是本文里过时最快的部分。取而代之的是每次该去哪里确认什么。

2026年7月29日在官方模型文档里确认到的构成是这样：当前一代的表里列着Claude Fable 5、Claude Opus 5、Claude Sonnet 5、Claude Haiku 4.5，而更早的Claude Opus 4.8、4.7、4.6以及Claude Sonnet 4.6、4.5等放在另一个章节。文档建议拿不准用哪个就从Claude Opus 5开始，需要最高能力的工作则推荐Claude Fable 5。上下文长度标注为：Fable 5、Opus 5、Sonnet 5是100万词元，Haiku 4.5是20万词元。这个构成是会变的。

套餐方面，个人向分为免费、Pro、Max，组织向分为Team、Enterprise。价格与用量上限本文不写，因为变动频繁，而错的数字比没有数字更糟。付钱之前到官方定价页面直接确认，是唯一正确的做法。

选择不是口味问题，三项确认就能定下来。

  • 要处理的材料装得进上下文吗 — 整叠几百页的合同和润色一封邮件，需要的长度完全不同。看文档标注的上下文长度来判断。
  • 需要的信息是否在知识时点之后 — 如果是，要做的不是换模型，而是接入搜索工具或自己把材料贴进去。这是任务设计问题，不是套餐问题。
  • 是否满足所在单位要求的数据处理条件 — 如第5节所见，个人向产品与商用产品适用的条款不同。这一项要放在最前面确认。
  • 如果问题出在速度和成本，就换个模型试试 — 正如官方文档直接提到的，延迟和成本有时靠选模型而不是靠改提示来解决。

如果你关心的正是模型之间的性能比较，那条轴线在AI模型比较总览里另外讲。本文只讲对任何模型都同样适用的边界。

10. 五种常见失败与各自的纠正

失败大多不是工具的错，而是分配的错。下面写出常见的五种及其真实原因。

读着像那么回事，事实却是错的把核验昂贵的任务在不核验的情况下交出去了回到第4节的表重新分配任务

结论：选工具之前先给任务分类

「该不该用AI」是个得不出答案的问题。拆成三个，每次都能得出答案。

  • 这件事的正确答案是一个还是多个 — 多个而且由我来挑，就适合。只有一个而且错了难回退，就不适合。
  • 确认结果需要什么 — 手边现有的材料就够，那就交出去；必须往外找，那就一开始往外走。
  • 错了谁负责 — 如果是自己负责，核验就不是可谈判的，而是成本，要提前算进去。

这个工具很有用。只是它有用的理由，跟广告说的理由不太一样。填满空白页、在格式之间搬运、从长材料里抽出分支、在人看之前先过一遍 — 这些地方很难找到替代品。而在确定事实、精确计算、最新信息和最终判断上，别的工具和别的人会做得准确得多。

最后再写一遍态度。没有理由吓唬人，也没有理由把它吹大。需要的是准确知道这个工具真正擅长的范围，而这个范围来自官方文档和一笔核验成本的账，不是来自宣传语。

# AI助手实务判断卡

要不要把一件事交出去，标准只有一条：**核验成本超过自己动手写的成本，就不要用。**
真正省下的时间是「写作时间减去核验时间」。

---

## 1. 按任务类型的判断表

| 任务 | 交不交 | 原因 | 核验方式 |
|---|---|---|---|
| 从会议记录提取决定与待办 | 交 | 原件就在手边 | 把依据发言拿到原文里做字符串搜索 |
| 表格与日志的格式转换 | 交 | 没有新信息被造出来 | 核对行数 + 过解析器 |
| 通知与报告初稿 | 交 | 反正要从头改到尾 | 检查待确认清单，核对数字出处 |
| 代码改动的第一遍审查 | 交 | 意见真假当场就有定论 | 打开被指出的行 + 跑测试 |
| 把握陌生领域的术语与分支 | 交，但不当结论用 | 这是拿检索词的阶段 | 自己去打开它点名的一手来源 |
| 检查自己的学习成果 | 交 | 被检验的是我自己的讲述 | 自己回答它反问的问题 |
| 头脑风暴 | 交 | 错的候选也不算成本 | 由人做最终挑选 |
| 翻译初稿 | 有条件 | 术语一致性要靠人把关 | 与术语表比对，按段落对照 |
| 内部文档摘要 | 有条件 | 丢掉原文核验就不可能了 | 保留原文，只回溯可疑句子 |
| 引用统计与数字 | 不交 | 一手来源在外面 | 一开始就去原始资料 |
| 解释法规或合同条款 | 不交 | 答案随管辖与时点变化 | 查原文后再找专业人士确认 |
| 金额、税额、剂量的计算 | 不交 | 说明无法充当验算 | 用计算器或电子表格重算 |
| 确认最新价格、版本或规定 | 不交 | 知识时点之后在结构上不存在 | 直接打开官方页面 |
| 医疗或投资决策 | 不交 | 代价不对称地大 | 找有资质的专业人士确认 |

**一句话总结**
- 写「交」的行的共同点：核验所需的材料全在手边。
- 写「不交」的行的共同点：要确认就得往外跑。

## 2. 可直接使用的六个提示模板

### T1. 会议记录整理

```
<角色>
你是负责整理会议记录的执行人员。
</角色>

<目的>
这份整理稿给没能参会的同事看。
所以决定和负责人比背景说明更重要。
</目的>

<规则>
1. 只用记录里写到的内容，不要靠推测补齐。
2. 负责人或期限没有定下来，就写「待定」。
3. 算不算决定不清楚的发言，另外归入「暂缓事项」。
4. 每一条末尾原样引用一句作为依据的发言。
</规则>

<输出格式>
## 决定事项
- 决定 | 负责人 | 期限 | 依据发言
## 待办事项
- 待办 | 负责人 | 期限 | 依据发言
## 暂缓事项
- 议题 | 原因
</输出格式>

<会议记录>
（贴在这里）
</会议记录>
```

**核验**：把依据发言拿到原文里做字符串搜索，搜不到就是编的。

```
</约束>
```

```
<我的理解>
（在这里用自己的话讲一遍）
</我的理解>

顺序：
1. 先指出我的说明里与事实不符的部分，并说明理由。
2. 指出对了但表述不准确的部分。
3. 告诉我漏掉了哪些重要条件或例外。
4. 提三个能检验我是否真的理解的问题。
   - 不要提前给答案。
5. 列出这个主题里我必须回原文确认的项目。

不要给我总结正确答案，而要让我再讲一遍。
```

**核验**：自己去回答第4项的问题。

---

## 3. 核验清单

把活交出去之前：

- [ ] 这件事的正确答案是一个还是多个
- [ ] 核验结果所需的材料现在是否就在手边
- [ ] 如果要往外跑才能确认，一开始就往外走是不是更快
- [ ] 错了是不是由我负责
- [ ] 准备贴进去的材料里有没有混进不该放的东西

拿到结果之后：

- [ ] 有数字的话，我有没有要求出处并打开那份出处
- [ ] 有引用的话，我有没有回原文做字符串搜索确认
- [ ] 有计算的话，我有没有用计算器重算一遍
- [ ] 明明给了说不知道的位置，那一栏为什么是空的
- [ ] 需要最新信息的项目，我有没有到官方页面确认
- [ ] 如果我想省掉核验，这是不是在提示我别把这件事交出去

## 4. 不能放进去的东西

| 输入类型 | 判断 | 替代做法 |
|---|---|---|
| 密码、API密钥、令牌 | 绝对禁止 | 换成占位符，真值放进密钥管理工具 |
| 身份证件号、银行账号、卡号 | 绝对禁止 | 只保留格式，去掉数值 |
| 客户实名、联系方式、住址 | 禁止 | 化名为客户A、000-0000-0000 |
| 未公开的财务数字、合同条件 | 确认规定前禁止 | 换成比例或相对值再提问 |
| 公司内部源码 | 取决于规定与产品 | 只在获准的工具与账号上，只放必要文件 |
| 混有他人个人信息的笔记 | 清理后才可 | 先去掉第三方信息 |
| 公开文档、标准、论文 | 可以 | 引用要回原文核对 |
| 自己写的草稿与笔记 | 基本可以 | 只需检查是否混入第三方信息 |

**输入管理的两层**

1. 服务方如何处理数据 — 个人向产品与商用产品、API适用的条款不同。自己打开设置页面确认。
2. 所在组织的规定 — 服务方允许，单位未必允许，而且通常单位这边更严。

**化名原则**：模型需要的是结构而不是身份。去掉姓名和真实数字，答案质量几乎不变。

---

## 5. 提示的六条原则

1. 像对一位缺少背景的聪明新同事解释那样，写得清楚而直接。
2. 把指令的理由一并写上。
3. 放三到五个示例，既贴近真实场景又彼此差异足够。
4. 用XML标签把指令、背景、示例、输入分区。
5. 长材料放在提示的上部，问题与指令放在下面。
6. 加上「不确定就写不确定」，给它一个说不知道的位置。

如果提示改了五遍还是同一种失败，那不是提示的问题而是任务分配的问题，回到第1张表。

复制后可直接粘贴到笔记应用或 AI 工具中。
