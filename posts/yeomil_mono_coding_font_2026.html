여밀 모노 등장 - Geist Mono와 프리텐다드로 한글 자소분리를 잡은 코딩 폰트

개발자가 매일 응시하는 그 글꼴 이야기 - 하이브리드 결합이 겨냥한 것과 실제로 해결되는 것을 가른다

2026-07-06 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 매일 응시하는 화면 속 그 글꼴

개발자가 하루 중 가장 오래 바라보는 대상은 다름 아닌 코드 에디터의 글자다. 문법 하이라이팅, 자동완성, 코드 리뷰, 커밋 로그까지 모든 상호작용이 결국 한 줄 한 줄의 텍스트로 수렴한다. 그래서 최근 몇 년 사이 JetBrains Mono, Fira Code, 그리고 Vercel의 Geist Mono처럼 합자(ligature)와 가독성을 앞세운 코딩 전용 폰트가 꾸준히 주목받아 왔다. 그런데 이 흐름에서 한국어 개발자는 오랫동안 반쪽짜리 혜택만 누려 왔다. 서구에서 잘 만든 영문 모노스페이스 폰트는 대개 한글 글리프를 아예 포함하지 않거나, 포함하더라도 조형이 영문과 따로 노는 경우가 많았기 때문이다.

2026년 7월 기준, 이 틈을 겨냥한 오픈소스 프로젝트가 하나 등장했다. 개발자 taevel02가 GitHub에 공개한 여밀 모노(Yeomil Mono)다. Vercel의 Geist Mono와 국내 표준급 한글 서체로 자리잡은 프리텐다드(Pretendard)를 하나의 폰트 파일로 엮어, 한글 코딩 환경의 오래된 골칫거리인 자소분리(NFD) 문제와 영한 혼용 시 어긋나는 정렬을 함께 겨냥한다. 이 글은 여밀 모노 자체의 소개를 넘어, 한글 코딩 폰트가 왜 유독 어려운 숙제였는지, 하이브리드 결합이라는 접근이 어떤 의미를 갖는지, 그리고 실제로 무엇이 해결되고 무엇은 여전히 남는지를 직접 분석한다.

1. 여밀 모노란 무엇인가 - Geist Mono와 프리텐다드의 결합

1.1 이름의 유래와 조합 방식

'여밀'이라는 이름은 옷깃 등을 흐트러짐 없이 단정하게 여미다라는 뜻의 순우리말 '여미다'에서 왔다고 프로젝트는 설명한다. 영문과 한글이 한 줄에 섞여도 흐트러지지 않고 단정하게 정돈된다는 의도를 이름에 담은 셈이다. 실제 구성은 영문·기호 영역은 Vercel이 2023년 공개한 모노스페이스 서체 Geist Mono를, 한글(및 CJK) 영역은 2020년 공개돼 국내 웹·앱의 사실상 표준 산세리프로 자리잡은 프리텐다드를 가져와 하나의 글꼴 파일로 병합한 형태다. 즉 완전히 새로 그린 서체가 아니라, 이미 각자의 영역에서 검증된 두 폰트를 정교하게 이어 붙인 결과물이다.

1.2 왜 이 두 폰트를 골랐나

Geist Mono는 Vercel과 Basement Studio가 스위스 타이포그래피 전통을 참고해 만든 모노스페이스 서체로, Inter·Univers·SF Mono 등의 계보를 이었다고 공개돼 있다. 흥미로운 지점은 프리텐다드 역시 로마자 부분이 Inter 구버전을 바탕으로 만들어졌다는 사실이다. 즉 두 폰트는 애초에 남남이 아니라 Inter라는 공통 뿌리를 공유한다. 여밀 모노가 굳이 다른 조합이 아니라 이 둘을 골라 붙였을 때 조형적 이질감이 상대적으로 덜한 이유를, 본인은 이 계보의 우연한 일치에서 찾는다. 한글 쪽 프리텐다드는 본고딕(Source Han Sans) 계열 골격을 애플 시스템 서체 느낌으로 다듬은 서체로, 2021년 전후로 국내 앱·웹에서 이미 폭넓게 검증된 가독성을 갖췄다.

1.3 배포 방식과 라이선스

여밀 모노는 SIL Open Font License 1.1(OFL-1.1)로 배포된다. 이는 원본인 Geist Mono와 프리텐다드가 모두 채택한 라이선스와 같아서, 두 폰트를 병합해 재배포하는 데 법적 정합성이 깔끔하다는 점이 실무적으로 중요하다. 과거 한글·영문 결합 폰트 프로젝트 중에는 서로 다른 라이선스의 서체를 섞어 배포 범위가 애매해지는 사례가 종종 있었던 것과 대비된다. GitHub 저장소(taevel02/yeomil-mono)에서 TTF·OTF를 직접 내려받거나 설치 스크립트로 받을 수 있고, 터미널에서 아이콘을 쓰는 사람들을 위한 Nerd Font 패치 버전도 별도로 제공된다.

2. 한글 코딩 폰트의 고질적 문제 - NFD와 자소분리

2.1 완성형(NFC)과 조합형(NFD), 그리고 왜 갈리는가

한글 한 글자, 예를 들어 '값'은 유니코드 안에서 두 가지 방식으로 표현될 수 있다. 하나는 '값'이라는 완성된 음절 하나를 통째로 한 코드포인트에 담는 NFC(정준 결합) 방식이고, 다른 하나는 이를 초성·중성·종성, 즉 자모 낱자로 쪼개 여러 코드포인트를 이어 붙이는 NFD(정준 분해) 방식이다. 문제는 macOS의 파일시스템이 기본적으로 NFD를 쓰는 반면 Windows·Linux 계열과 대부분의 웹·터미널 환경은 NFC를 전제로 동작한다는 데 있다. 그 결과 macOS에서 만든 한글 파일명이나 텍스트가 다른 환경으로 넘어가면 자모가 낱개로 흩어진 채 해석되는 사고가 발생한다.

2.2 왜 터미널·에디터에서 한글이 깨져 보이는가

이 정규화 방식의 차이는 단순히 파일명 문제로 끝나지 않는다. 조합형(NFD)으로 인코딩된 한글 문자열이 들어오면, 렌더러가 초성·중성·종성 낱자를 다시 하나의 음절 블록으로 조합해 그릴 수 있어야 정상적으로 보인다. 그런데 코딩 폰트는 대개 영문 위주로 설계돼 한글 자모 각각의 결합 글리프까지 세심하게 다듬어 두지 않는 경우가 많다. 이때 터미널이나 에디터에서 자모가 겹쳐 보이거나, 벌어져 보이거나, 일부가 잘려 보이는 현상이 나타난다. 특히 macOS 터미널·git 로그·일부 CLI 도구에서 한글 파일명이나 커밋 메시지가 이상하게 표시되는 경험을 한 개발자가 많은 것도 이 때문이다.

2.3 너비 비율 문제까지 - 오래된 두 번째 숙제

한글 코딩 폰트에는 NFD 말고도 오래된 숙제가 하나 더 있다. 고정폭 폰트에서 한글은 보통 영문·숫자 폭의 2배로 설계돼야 영한 혼용 줄에서도 정렬이 어긋나지 않는다. 그런데 네이버가 2009년 공개한 나눔고딕코딩이나 그 뒤를 이은 D2Coding 같은 검증된 한글 코딩 폰트조차, 특정 포인트 크기에서는 이 2:1 비율이 정확히 지켜지지 않아 표나 주석 정렬이 미묘하게 어긋난다는 사용자 보고가 GitHub 이슈로 여러 건 남아 있다. 렌더링 과정의 반올림(hinting) 오차가 원인으로 지목되는데, 완전히 없애기 어려운 종류의 문제다.

3. 영문·한글 하이브리드 결합이라는 접근의 의미

3.1 기존 방식의 한계 - 폰트 폴백 체인

지금까지 한국 개발자 다수가 써 온 해법은 VSCode 등에서 "editor.fontFamily": "'Geist Mono', 'Pretendard'"처럼 영문 폰트와 한글 폰트를 쉼표로 이어 붙이는 폴백 체인이었다. 영문은 앞 폰트에서, 한글은 뒤 폰트에서 글리프를 가져오는 방식이라 대체로 그럴듯하게 보이긴 한다. 그러나 두 폰트가 원래 따로 설계된 만큼 어센트·디센트·행간 같은 수직 메트릭이 미묘하게 달라, 영한이 섞인 줄에서 기준선이 미세하게 흔들리는 현상이 생기기 쉽다. 게다가 이 설정은 사용자가 에디터마다, 터미널마다 직접 해 줘야 하는 번거로움이 있고, 애초에 폴백은 NFD로 들어온 한글 자모를 다시 조합해 보여주는 문제까지 손대지는 못한다.

3.2 여밀 모노가 실제로 하는 일

여밀 모노의 접근은 이 폴백을 아예 폰트 제작 단계로 끌어올린다. 공개된 설명에 따르면 이 프로젝트는 한글 글리프의 수평 메트릭을 Geist Mono의 격자에 맞춰 재정렬해, 한글이 잘리거나(clipping) 수직으로 어긋나 보이는 현상을 줄이는 데 초점을 맞췄다. 즉 사용자가 폰트 하나만 지정하면, 폴백 체인을 직접 짜고 미세조정하던 수고를 프로젝트가 대신 해결해서 배포한 셈이다. 진입장벽을 낮췄다는 점에서 이는 실질적인 개선이다.

3.3 우연한 계보 - 왜 궁합이 나쁘지 않은가

앞서 짚었듯 Geist Mono와 프리텐다드는 둘 다 Inter 계열의 영향을 받았다는 공통점이 있다. 서로 다른 회사가, 다른 시점에, 다른 목적으로 만든 폰트지만 조형의 뿌리가 겹친다는 점은 병합했을 때 이질감을 줄이는 실질적 이점으로 작용했을 가능성이 크다. 다만 이는 본인의 해석이며, 프로젝트 측이 이 계보를 의도적으로 노렸다고 명시한 자료는 확인되지 않는다.

3.4 정직한 경계 - 폰트가 못 푸는 것

여기서 분명히 해 둘 것이 있다. 여밀 모노가 겨냥하는 것은 한글 글리프가 깨지거나 어긋나 보이는 시각적 증상을 완화하는 일이지, macOS가 파일시스템 차원에서 한글을 NFD로 저장하는 근본 동작 자체를 바꾸는 것은 아니다. 즉 NFD로 인코딩된 문자열이 여전히 들어올 수 있지만, 폰트가 이를 최대한 자연스러운 모양으로 그려 주는 완충 역할을 한다고 보는 편이 정확하다. 정규화 방식 차이를 근본적으로 없애려면 셸·에디터·OS 차원의 유니코드 정규화 처리가 함께 필요하며, 이 부분까지 폰트 하나로 해결됐다고 보기는 어렵다. 공개된 자료만으로는 여밀 모노가 정확히 어떤 OpenType 규칙으로 조합형 자모를 처리하는지 세부까지 확인되지는 않아, 이 점은 사용자가 직접 체감해 볼 부분으로 남는다.

4. 코딩 폰트가 개발 경험에 미치는 영향

코딩 폰트는 단순한 미관의 문제가 아니다. l(소문자 엘)과 1(숫자 일), O(대문자 오)와 0(숫자 영)을 착각해 생기는 오탈자, 장시간 화면을 볼 때 쌓이는 눈의 피로, 주석과 변수명이 매끄럽게 읽히는지에 따른 리뷰 속도까지 실무 생산성에 두루 영향을 준다. 한국 개발 현장에서는 변수명은 영문, 주석과 커밋 메시지는 한글이라는 혼용이 흔한 만큼, 두 문자 체계가 한 줄에서 조형적으로 얼마나 자연스럽게 어울리는지가 다른 나라 개발자보다 체감상 더 크게 다가온다. 이런 맥락에서 여밀 모노처럼 애초에 혼용을 전제로 설계된 폰트가 갖는 값어치는, 겉보기보다 크다는 것이 본인의 판단이다.

5. 실무 적용 - 에디터·터미널 설정

적용은 어렵지 않다. GitHub 릴리스에서 TTF·OTF를 내려받아 시스템에 설치한 뒤, VSCode라면 설정에서 "editor.fontFamily": "Yeomil Mono" 한 줄이면 폴백 체인 없이 끝난다. 터미널에서 파일 트리 아이콘이나 git 상태 표시를 쓰고 싶다면 Nerd Font 패치 버전을 대신 설치하면 된다. 다만 한 가지는 짚어야 한다. 실제로 자소분리 현상이 완전히 사라졌는지는 사용 중인 셸(zsh, bash 등)과 터미널 앱(iTerm2, Windows Terminal 등) 자체의 유니코드 정규화 처리 방식에 따라 체감이 달라질 수 있다. 폰트 교체만으로 100% 해결된다고 단정하기보다, 본인이 자주 겪는 macOS 파일명·git 로그 환경에서 직접 켜 보고 비교하는 것이 안전하다.

6. 한국 개발자에게의 가치와 한계

가치는 명확하다. macOS를 쓰거나, 터미널을 많이 들여다보거나, 영한 혼용 코드·문서를 자주 다루는 개발자라면 폰트를 하나 바꾸는 것만으로 매일 누적되는 미세한 불편이 줄어들 수 있다. 별도 폴백 설정 없이 한 줄 지정으로 끝난다는 점도 실질적인 진입장벽 완화다. 다만 한계도 있다. 우선 이 프로젝트는 사실상 1인 개발자가 주도하는 오픈소스로 보이며, 앞으로 얼마나 꾸준히 유지보수될지는 지켜봐야 한다. 또한 2026년 7월 기준 공개된 지 오래되지 않아 다양한 에디터·터미널·폰트 렌더러 조합에서의 호환성이 폭넓게 검증됐다고 보기는 이르다. 이미 D2Coding이나 나눔고딕코딩 같은 익숙한 한글 코딩 폰트에 만족하고 있는 개발자라면, 체감 이득이 기대보다 크지 않을 수도 있다.

7. 결론 - 오늘 해볼 수 있는 3가지

여밀 모노는 화려한 신기능이 아니라, 오래 방치돼 온 한글 코딩 환경의 기본기를 정면으로 다룬 시도라는 점에서 의미가 있다. 오늘 바로 해 볼 수 있는 세 가지를 제안한다. 첫째, 본인이 쓰는 에디터·터미널에서 지금 자소분리나 정렬 어긋남을 실제로 겪고 있는지부터 확인한다. 둘째, GitHub 릴리스에서 여밀 모노를 내려받아 하루이틀만 로컬에서 써 보며 기존 폴백 조합과 체감 차이를 비교한다. 셋째, 팀 dotfiles나 에디터 설정을 공유하는 입장이라면, 개별 폴백 체인 대신 병합형 폰트를 표준으로 채택하는 방안을 검토해 본다. 국한문 혼용 변환 라이브러리 Gukhanmun 분석에서 다룬 것처럼, 한글 텍스트 처리의 디테일은 사소해 보여도 실제 개발 경험을 좌우하는 경우가 많다.
