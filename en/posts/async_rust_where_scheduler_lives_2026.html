This article rests on sentences written in "Async Rust: Where does the scheduler live?", published in MOND←TECH MAGAZINE on October 3, 2026, and in the Rust standard library documentation, the Async Book, the Tokio 1.53.2 documentation and tutorial, RFC 230, and the Without Boats post "Why async Rust?". The trigger - an essay that starts from twenty-five complaints and then overturns its own

On October 3, 2026, MOND←TECH MAGAZINE published an essay titled "Async Rust: Where does the scheduler live?", and GeekNews picked it up on October 6. The byline reads Mond. The essay opens by collecting the complaints that keep coming back about async Rust into a 5×5 bingo card. Function coloring, async closures, Tokio defaultism, "just use threads", Async Drop, cancellation safety, the proliferation of Send + Sync + 'static bounds, io_uring and Pin are all there, twenty-five squares in total, followed by a cheat sheet that attaches reading material to each square.

Then comes the complaint that belongs to the author. What bothers the author about async Rust is that it requires a runtime. Rust is known for giving memory safety without requiring a runtime such as a garbage collector, the essay says, so going back to a runtime-based model feels like a regression. The instant there is a runtime, functions are no longer run directly but handed to an engine that runs them according to its own rules. Scheduling algorithms are optimization problems that force a choice of one specific point on a tradeoff boundary, and there is no one-size-fits-all solution. The grievance ends with the picture of tweaking the Tokio runtime like the Java garbage collector just to squeeze out a little more performance.

And then the author withdraws that complaint. The sentence in the essay is "In short, that whole gripe was nonsense." The reason given is that the runtime feeling, the tradeoffs of scheduler optimization and the complexity are not problems specific to async Rust but general issues of concurrent code. The rest of the essay unpacks that turn. A scheduler has to exist somewhere, and the question that is left is where.

That place is also what the sections below follow. The kernel, a runtime built into the language, a crate, and the fourth place the author would prefer, a parameter, are taken in order, and for each one the costs and constraints named in the essay are set beside the wording of the official Rust and Tokio documentation. Function coloring, where the marker spreads up the call hierarchy, and the semantics of cancellation form a separate axis, which is laid out in Why the Same Async Code Ends Differently on Each Runtime.

The scheduler does not go away - the five steps of the argument

The starting proposition of the author is short. If code is to run concurrently, a runtime is needed to handle scheduling, and that is practically built into the definition of concurrency. Avoiding async Rust altogether and using threads changes only one thing, namely that the kernel is now the scheduler instead of Tokio. There is still a scheduler, the author writes, with all or at least some of the same problems. The essay then lays out what the problem actually is in five steps.

  1. Concurrency, in some form or another, is necessary.
  2. Concurrency always requires a runtime. The questions then become where the runtime lives and who manages the stack.
  3. For anyone who wants to avoid a runtime, the best available options are two. Writing an event loop by hand means maintaining a runtime of your own, and "just use threads" means using the kernel as a runtime and juggling kernel threads that are far heavier than specialized Tokio tasks. The essay states that difference in weight with deliberate exaggeration.
  4. Doing what Go does and shipping a runtime with the language is not possible without making Rust harder to embed and imposing a cost at the FFI boundary.
  5. With the available options exhausted, what remains is the present state of things. A runtime is a crate. It is pulled in, initialized, perhaps passed around, and used to schedule futures.

The author writes about going over the design decisions one by one with the intention of complaining, only to arrive at the conclusion that each of them was reasonable. The sentence that sums it up is "The scheduler has to live somewhere, and Rust doesn't get to trade performance for convenience." A qualification is attached here as well. The author first admits to not knowing whether some yet-undiscovered abstraction exists that would evaporate half of the problems people have with async Rust, and then says the inclination is to answer no. The ground for that is that many of those problems are general concurrency problems.

One distinction is worth carrying forward from this summary. The author proposes splitting the problems of async Rust into inherent concurrency problems on one side and issues downstream of the decision to have the scheduler live in a crate on the other. Following that split, the first kind can be read as following wherever the scheduler is placed, and the second kind as changing shape when the place changes. Which problems belong to the second kind is taken up further below through the three items the author names directly.

What the standard library defines - Future, poll and Waker, but no scheduler

What the fifth step, "a runtime is a crate", looks like in practice is visible in the standard library documentation. std::future::Future is a trait that has been stable since Rust 1.36.0, and the following is its entire definition.

pub trait Future {
                        type Output;
                    
                        // Required method
                        fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
                    }

The documentation describes a future as a value that might not have finished computing yet. poll is the method that attempts to resolve the future into a final value, and it does not block if the value is not ready. Instead, the current task is scheduled to be woken up when it becomes possible to make further progress by polling again. No type in this documentation decides who calls poll. What the documentation does state is that futures alone are inert and that they have to be actively polled for the underlying computation to make progress. It also notes that code using a future generally does not call poll directly but uses .await on the value.

The side that does the polling is the executor. The Waker documentation defines a Waker as a handle for waking up a task by notifying its executor that it is ready to be run. Its typical life is that it is constructed by an executor, wrapped in a Context, and then passed to Future::poll(). Deciding which task runs next is likewise left to the executor. The same documentation states that yielding to competing tasks is not guaranteed, that it is the choice of the executor which task to run, and that the executor may choose to run the current task again. The standard library fixes the channel through which a task is woken, and leaves open when and on which thread the woken task is run.

The Async Book states the reason for this arrangement directly. Many programming languages provide a runtime, and commonly that runtime does a lot more than manage async tasks: it might manage memory, have a role in exception handling, or even be a full virtual machine. Rust is a low-level language that strives towards minimal runtime overhead, so its async runtime has a much more limited scope than the runtimes of many other languages. And because there are many ways to design and implement an async runtime, Rust lets the programmer choose one depending on requirements rather than providing one. The book puts the price in a single sentence as well: getting started with async programming requires an extra step. On the structure of a runtime it says there are no strong rules, only the terms and the division of responsibilities shown in the table, which are common. As for why spawn is a function of Tokio and not of the standard library, the book explains that tasks are purely a runtime concept.

First place, the kernel - what just-use-threads actually moves

One square on the bingo card reads "just use threads". The cheat sheet summarizes the most common variant of this reasoning as the idea that async only ever becomes necessary when writing a server that has to support 10k+ connections at the same time, and that otherwise a thread pool is enough. The answer of the author is that this choice does not remove the scheduler. With threads, the kernel becomes the scheduler.

The properties of this place are set out in RFC 230, the document written when Rust removed its green threads. The RFC calls the model in which a task always corresponds to an OS-level thread the 1:1 model, and the model in which a userspace scheduler maps tasks onto worker threads the M:N model. In the 1:1 model tasks are threads and therefore have to be equipped with their own stacks, and since each task is an OS thread, a task can block freely without any risk for other tasks. In the M:N model, blocking in the OS sense means blocking the worker thread. The RFC adds that the same applies to long-running loops and to page faults.

The cost the author names for this place is weight. Kernel threads are far heavier than specialized Tokio tasks, the essay says. For the other side of that comparison the Tokio tutorial records one figure. Under the hood, Tokio tasks require only a single allocation and 64 bytes of memory, and applications should feel free to spawn thousands, if not millions, of them. The tutorial calls a Tokio task an asynchronous green thread. A size figure for kernel threads appears neither in the essay nor in the documents above.

The author raises one more thought about this place and labels it a spicy take. Instead of reinventing and litigating new runtimes inside programming languages, could kernel threading and scheduling somehow be fixed, or a new type of kernel thread be introduced, so that "just use threads" becomes efficient? The reasoning is that goroutines are an abstraction running on top of the kernel, and if they can be made cheap and fast, it should be possible for the kernel to support some variant of such threading. Three reservations from the author come attached to this idea.

  • The essay notes that people have tried this a few times, usually under a name like "M:N user-level threading", and states plainly that no research on those attempts was done for the essay.
  • In practice, the author argues, the kernel will not know as much about the code as a language-specific runtime does. That limits its ability to schedule threads and probably means that language-specific runtimes will keep coming out on top unless a way is found to hand the kernel the additional data it needs. The essay puts a question mark after the word "always".
  • Even in the ideal case, the result is a move back to a world in which everyone uses threads for everything, only with higher performance. On whether that is better, the author says the answer is not known and that opinions may vary.

Second place, the language runtime - what Go chose and what Rust removed

The language the essay uses as its example of a built-in runtime is Go. The description by the author runs as follows. No one expects Go to have bare-metal performance, and everyone understands that there is a tradeoff. Some performance is sacrificed in exchange for convenience, and that is why Go has goroutines, that is, green threads. The cheat sheet describes green threading as a model in which the language brings its own runtime. Of Rust the author writes that it cannot choose your scheduler for you, because there is no perfect scheduler and different schedulers have different use cases. The question of what to weigh when moving between Go and Rust is covered in the Go to Rust migration guide.

Rust once stood in this place too. RFC 230, whose start date is recorded as September 16, 2014, is the proposal to remove the runtime system that was part of the standard library at the time. According to the state of affairs the RFC describes, Rust initially supported only the green threading model, and native threading was added later and ultimately became the default. Green threads in Rust were scheduled M:N and equipped with their own stacks, but the segmented stacks used at first were removed in favor of pre-allocated stacks, which, the RFC writes, means that those green threads were not lightweight. The RFC lists five problems.

  • Forced co-evolution. The green and native threading models had to provide the same I/O API at all times, even though there is functionality that is only appropriate or efficient in one of the two.
  • Overhead. Because the mixture of the two models was implemented with trait objects, costs appeared in binary sizes, in task-local storage, and in allocation and dynamic dispatch. On the last of these the RFC adds its own qualification: in most cases the costs are trivial compared with the cost of actually doing the I/O, so they are not strong arguments against the design.
  • Problematic I/O interactions. Native code that calls blocking I/O had the potential to block the worker thread running the green scheduler. The I/O API was unified, yet it was not fully interoperable.
  • Embedding Rust. When calling Rust from C code or embedding it in high-level languages, a fair amount of setup was needed to provide the runtime infrastructure that the standard library relied on.
  • Maintenance burden. Providing such a flexible threading model made the standard library more complex.

The argument about FFI cost is not developed in the essay itself. It is handed over to "Why async Rust?", a post by Without Boats dated October 15, 2023. That post states that switching code from executing on a green thread to running on the OS thread stack can be prohibitively expensive for FFI, and that Go just accepts this FFI cost. It goes on to explain that this was especially problematic for Rust, because Rust is designed to support embedding a Rust library into a binary written in another language, and to run on embedded systems that do not have the clock cycles or memory to operate a virtual threading runtime. The author of the essay grants that the embedded point is valid, and adds the observation that bringing up embedded programming during async Rust discussions has almost become a meme in its own right.

What the author reads out of this history is a design principle. The decision to eschew green threads, in this reading, codified a principle that was still in flux at the time: that Rust would go down the route of being a C++ replacement, usable in embedded no_std environments and equipped with zero-cost abstractions. The verdict of the author is that in hindsight this direction looks like the right call. After granting that nobody knows what the counterfactual world in which Rust doubled down on green threading would look like, the essay adds the guess that it is not a world in which Rust entered the Linux kernel. The essay itself marks this with the verb "assume". How the safety guarantees of Rust stop at the FFI boundary is a separate subject, covered in Where Safety Guarantees End at the Rust FFI Boundary.

Third place, a crate - the scheduler Tokio writes down in its documentation

Once the runtime is a crate, the behaviour of the scheduler is written down not in a language specification but in the documentation of that crate. The Tokio 1.53.2 documentation states that asynchronous applications, unlike other Rust programs, require runtime support, and names three services that are necessary. They are an I/O event loop, called the driver, which drives I/O resources and dispatches I/O events to tasks; a scheduler to execute tasks; and a timer for scheduling work to run after a set period of time. The Runtime type of Tokio bundles all three as a single type.

The documentation says that Tokio provides multiple task scheduling strategies suitable for different applications, and it draws the rule of thumb for choosing among them as a decision tree. If work-stealing or a multi-thread scheduler is wanted, the answer is the Multi-threaded Runtime; if not, and !Send futures are executed, it is the Local Runtime; otherwise it is the Current-thread Runtime. The documentation qualifies the tree as not exhaustive, since other factors may influence the decision. The multi-thread scheduler executes futures on a thread pool using a work-stealing strategy, by default starts a worker thread for each CPU core available on the system, and is selected by default.

The section titled "Detailed runtime behavior" describes the internals with numbers. The subsection headings for both runtimes carry the words "behavior at the time of writing", and the text says that this behavior may change in future versions of Tokio. The values in the table below have to be read under that condition.

The fairness guarantee is conditional as well. If the total number of tasks does not grow without bound, and no task is blocking the thread, then it is guaranteed that tasks are scheduled fairly. Beyond that there is no guarantee about the order in which tasks are scheduled, and no guarantee that the runtime is equally fair to all tasks. The example in the documentation is two tasks A and B that are both ready: the runtime may schedule A five times before it schedules B, and all that is guaranteed is that it will schedule B eventually.

Placing the essay next to this documentation brings out two things. First, what the author calls an optimization problem that requires picking a specific point on a tradeoff boundary shows up in Tokio as values and settings such as 31, 61, 256 and 10ms. Second, those values are the point chosen by one version of one crate. The standard library documentation contains no corresponding values, only the sentence in the Waker documentation that it is the choice of the executor which task to run.

The price of the crate - three things the author names

The author names directly the problems that arise because the scheduler lives in a crate: Tokio defaultism, a lack of runtime agnosticism, and Send + 'static bounds.

  • Tokio defaultism. In the words of the cheat sheet, it is the notion of Tokio as the only runtime that matters. Not realizing that what one is talking about only applies to Tokio, and not to async Rust in general, falls under it. The Async Book introduces Tokio as a general purpose runtime and the most popular runtime in the ecosystem, and notes in the same passage that in some circumstances a different runtime might give better performance or simpler code.
  • Futures are not runtime agnostic. The cheat sheet states that task spawning is dependent on the runtime and has various assumptions baked into it, and that certain matters are baked into traits. This is one of the issues people refer to when they talk about an "ecosystem split"; the other, it adds, is that async splits the entire Rust ecosystem into async and non-async libraries.
  • Spreading Send + 'static bounds. The explanation given by the author is that Send bounds spread through generic code since the language itself cannot know whether a runtime will move tasks between threads.

The third item can be checked against the wording of the Tokio documentation. The signature of tokio::spawn is as follows.

pub fn spawn<F>(future: F) -> JoinHandle<F::Output>
                    where
                        F: Future + Send + 'static,
                        F::Output: Send + 'static,

The Tokio tutorial gives the reason for each bound separately. The 'static bound means that the spawned task cannot contain any references to data owned outside the task. The Send bound allows the Tokio runtime to move tasks between threads while they are suspended at an .await, and tasks are Send when all data that is held across .await calls is Send. The spawn documentation also notes that holding on to a !Send value across calls to .await results in an unfriendly compile error message.

That this bound comes out of the scheduling choice called work-stealing is stated in another square of the cheat sheet. Work-stealing means tasks can be moved from one CPU core to another, ensuring that each thread always has work to do, but requiring all tasks to have Send bounds, whereas this limitation does not apply to thread per core runtimes. This is also where the author locates the difficulty of the idea that the standard library should standardize APIs for spawning tasks: runtimes have different expectations. The separate Local Runtime branch in the Tokio decision tree reflects the same circumstance.

Blocking is another problem whose shape changes in this place. The standard library documentation says that an implementation of poll should strive to return quickly and should not block, and that if a call is known ahead of time to take a while, the work should be offloaded to a thread pool or something similar. The spawn_blocking square of the cheat sheet describes what it looks like when this goes wrong. If a Tokio worker thread is blocked by accident, the remaining work of that thread is stolen by other threads, so the program may keep limping along, but the worker pool is down one full worker thread for as long as the call blocks, and this can be really hard to notice as long as traffic is low. It fits together with the fact that the Tokio fairness guarantee stands on the assumption that no task is blocking the thread.

The same kind of friction is recorded on the I/O interface side. According to the cheat sheet, in io_uring APIs the kernel owns the buffer until the operation finishes, which fights with futures being cancellable by drop, and fixing that in Tokio would require reworking its APIs. How io_uring itself behaves is covered in io_uring SQPOLL and System-Call-Free I/O.

Enumerating the costs and asking for the decision to be reversed are two different things in the essay.

The implicit executor context - one function, a panic depending on the calling thread

The complaint the author raises about Tokio specifically concerns its implicit ambient executor model. The tone is mild: the essay calls it a little frustrating. A spawned Tokio task attaches itself to an executor looming in a thread-local context, and breaks with a runtime panic if such an executor does not exist. The example in the essay is the following.

fn record_metric(_value: u64) {
                        tokio::spawn(async move {
                            // do stuff
                        });
                    }
                    
                    fn checksum(data: &[u8]) -> u64 {
                        let sum = data.iter().map(|&b| b as u64).sum();
                        record_metric(sum);
                        sum
                    }
                    
                    #[tokio::main]
                    async fn main() {
                        let data = vec![1u8; 1024];
                        checksum(&data); // fine
                    
                        let (tx, rx) = tokio::sync::oneshot::channel();
                        rayon::spawn(move || {
                            let _ = tx.send(checksum(&data)); // panics, process abort
                        });
                        println!("{:?}", rx.await);
                    }

Judged by its signature alone, checksum is a synchronous function that takes a byte slice and returns a sum. The fact that record_metric, which it calls, uses tokio::spawn does not appear in the signature. In the essay, the line that calls it directly under #[tokio::main] carries the comment "fine", and the line that calls the same function inside a closure handed to rayon::spawn carries the comment "panics, process abort".

The wording of the Tokio documentation records the same contract. tokio::spawn has to be called from the context of a Tokio runtime, and the Panics section states that it panics if called from outside of the Tokio runtime. The documentation explains alongside this that tasks running on the Tokio runtime are always inside its context, and that the context can also be entered using the Runtime::enter method. The Async Book tells readers at the introductory stage that, for now, the runtime can be imagined like a global variable which is only accessible in async functions.

The author likens this to a "secret argument" that gets passed around by all Tokio functions. Forgetting the incantation, that is, trying to use Tokio outside of the context of a Tokio runtime, produces a runtime error. The properties the author objects to are these.

  • There are side effects.
  • There are hidden global-ish variables.
  • There is hidden dynamic scoping.

Read against the example above, the side effect does not show in the signature of checksum, whether the same function succeeds depends on the context of the thread that called it, and the error arrives at run time and not at compile time.

In a footnote the author concedes that this is asking for too much. Rust does not have an effect system, and it cannot even track whether code is capable of panicking, let alone track side effects. Even so, the author writes, it is unwelcome that this is not tracked at compile time. Another footnote records that Tokio does have Handle::spawn, and names as the problem that the ambient form is the default.

In the ideal world the author sketches, tasks cannot be spawned without passing the executor all the way through the code to the place where the task is spawned. The author says outright that many people would hate that world. The second-best arrangement, for those who really want to reach for the Tokio executor without passing it through, is that it should be sitting in a global variable and be grabbed from there at the call site. The yardstick is whether a search can find it. The author writes that this property should be greppable, not hidden.

The as-good-as-it-gets belief - the future size example

The essay contains one side note on performance. There is a belief that async Rust is "as good as it gets" in some vague way, and the author says this is not really the case. The belief singled out is that Rust futures compile down to an optimally sized state machine that is exactly as large as it has to be to hold all the data. The author writes that this is the idea, but that a variety of long-standing issues exist, and gives the case of arguments being twice as expensive if held across yield points.

async fn test(arg: [u8; 8192]) {
                        wait().await;
                        drop(arg);
                    }
                    
                    async fn wait() {}
                    
                    fn main() {
                        // Expected: 8194 == 2 + 8192
                        // Actual: 16386 == 2 + 2 * 8192
                        println!("{}", std::mem::size_of_val(&test([0; 8192])));
                    }

The values in the comments are all the figures the essay offers. When the size of the future of an async function that takes an 8192-byte array as an argument is printed with std::mem::size_of_val, the expected value is 8194 (2 + 8192) and the actual value is 16386 (2 + 2 × 8192). The essay adds the suggestion to remove the drop(arg); call and see what happens, without recording the result. It also says that the size blowup is exponential when futures are passed as arguments, and points to pull request 135527 in the rust-lang/rust repository as the work under way to resolve the problem.

What deserves attention when reading this example is the kind of number it is. 8194 and 16386 are the byte sizes of a state machine produced by the compiler, not the throughput or latency of any runtime. The essay contains no benchmark that compares runtimes with one another, or threads with async. The cheat sheet has a separate square for the futures of severely nested async functions blowing the stack. The essay treats this belief as a misconception distinct from the idea that a scheduler exists that suits every use. The misconception about schedulers concerns which scheduler is chosen, and the misconception about future size concerns how large the compiler makes a future.

Fourth place, a parameter - the Zig I/O interface and the caveats attached

The example the author gives of what a principled version might look like is Zig. In Zig, an I/O interface is passed around to all functions that need it. Async-ness and I/O then become properties baked into the exact implementation that is being passed around. The example, which the essay credits to a post by Loris Cro, is the following.

const std = @import("std");
                    const Io = std.Io;
                    
                    fn saveData(io: Io, data: []const u8) !void {
                        const file = try Io.Dir.cwd().createFile(io, "save.txt", .{});
                        defer file.close(io);
                    
                        try file.writeAll(io, data);
                    
                        const out: Io.File = .stdout();
                        try out.writeAll(io, "save complete");
                    }

The first parameter of saveData, io: Io, is that interface. io is handed to every call that creates, closes or writes a file. The author writes that the I/O interface defines the contract for the runtime, and summarizes that, in principle and on the assumption that everyone is strict about passing the interface around, three things are gained.

  1. It becomes possible to track exactly where blocking operations may happen.
  2. Function coloring is avoided, because the color becomes a function parameter. A footnote qualifies this: function coloring is encoded as a parameter passed to the function and not as a special language feature, and whether that counts as function coloring is something people will not be able to agree on.
  3. All library code becomes agnostic to the executor or scheduler. A different implementation of the I/O interface can be passed in, so the ecosystem is not split.

This is where the answer of the author to the question in the title appears. Putting the scheduler into a parameter that is passed around feels right, the essay says. It is verbose, but it solves a lot of problems, and by the count of the author it solves something like a third of the bingo card. Not the kernel and not some ambient execution context, but something that can be passed around as a parameter and swapped out as needed: that is where the author would like the scheduler to live.

Caveats follow this answer one after another. In the order of the essay they are as follows.

  • Zig is not stable yet, and async is very difficult to get right. In the words of the author, this approach has not been proven in the wild yet.
  • If the Zig team can make it work, the author is confident that an experiment to evolve Rust in that direction would be worthwhile. The sentence opens with a condition.
  • Going all-in would require a rewrite of Rust standard library APIs such as std::fs, so the author regards it as almost certainly off the table.
  • The crate ecosystem lives under no such constraints, so it might be possible. The wording in the essay is "Maybe it's possible."

The conclusion of the author is not a recommendation that Rust should follow Zig. It keeps the assessment that the present choice of a crate was right for Rust, and goes only as far as two statements: if the Zig team can make it work, an experiment to evolve Rust in that direction would be worthwhile, and in the crate ecosystem it may perhaps be possible.

Putting the four places so far into one table, using only the items the essay and the documentation name, gives the following. The last row is the option the author mentions together with threads in the third step, and items absent from the essay are left as "—".

For code that sits in the third row of the table, the wording of the documents above yields a set of checks straight away. The list below rearranges statements from the essay and from the official documentation into the order in which code is read.

  1. Does the kind of runtime fit the workload? Follow the order of the decision tree in the Tokio documentation. Is work-stealing or a multi-thread scheduler wanted, and if not, are !Send futures executed? The documentation says most applications should use the multi-thread scheduler, with exceptions in some niche use cases such as when running only a single thread is required.
  2. Is there a path that reaches spawn from outside the runtime context? Search for tokio::spawn calls inside synchronous functions and check whether those functions can be called from another thread pool. The panic in the example from the essay occurs on such a path.
  3. Where does the Send bound come in? The tutorial states that whether all data held across .await calls is Send decides whether the task is Send. The spawn documentation includes an example that confines a !Send value to a scope with no .await.
  4. Is there a blocking call inside poll? The advice in the standard library documentation is to offload work that may take a while to a thread pool or something similar. The Tokio fairness guarantee rests on the assumption that no task is blocking.
  5. Has the size of the future been measured? It can be measured with std::mem::size_of_val, as in the example from the essay. An argument that holds a large value across a yield point is the first candidate.
  6. For a library, which runtime does it assume? The cheat sheet states that task spawning is dependent on the runtime. The runtime a library assumes sets the range of places where that library can be used.

For the choice between threads and async, what the essay offers as a criterion is a question and not a number. Whichever is chosen, there is a scheduler. What differs is where that scheduler lives, where its behaviour can be read, and whether it can be swapped out. The behaviour of the Tokio scheduler is written in the crate documentation together with a version, as in the table earlier, and that documentation goes as far as saying that the values may change.

What could not be confirmed

  • The bodies of the posts the essay links to. The Zig post by Loris Cro, the post by Andrew Kelley on Zig async I/O, the Corrode.dev post on async and the discussion in pull request 135527 were not opened. The Zig example and the three benefits are reported only as far as the essay carries them.
  • The real output of the future size example. 8194 and 16386 are the values in the comments of the essay and are not results obtained by running the code on particular compiler versions. The value after removing drop(arg); is not written in the essay either.
  • A real run of the example that spawns outside the runtime. "panics, process abort" is a comment in the essay, and what was compared against the Tokio documentation goes only as far as the Panics section stating that a call from outside the runtime panics.
  • Figures that weigh kernel threads against Tokio tasks under the same conditions. The 64 bytes in the Tokio tutorial is a value for the task side only.
  • Official Go documentation on the behaviour of the Go runtime scheduler and on FFI cost. Statements about Go are limited to sentences in the essay and in the Without Boats post.
  • The content and outcome of attempts at M:N user-level threading at the kernel level. The author of the essay also states that no research was done on them.
  • The level of io_uring support in Tokio. The essay says, with the qualifier "Afaik", that Tokio still does not fully support it, and this was not compared against Tokio documentation.
  • Whether the detailed figures of the Tokio scheduler hold in versions after 1.53.2. The documentation itself states that they may change.
