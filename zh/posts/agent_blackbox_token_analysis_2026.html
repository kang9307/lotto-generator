Agent-Blackbox — 用会话图和令牌浪费分析Claude Code与OpenCode执行过程

打开AI编码智能体的黑盒子 — 可视化会话流程、令牌消耗与浪费点，分析智能体可观测性在2026年为何至关重要

2026-06-23 开发/基础设施

引言：智能体究竟在做什么

将复杂任务交给Claude Code或OpenCode后过了10分钟，屏幕上工具调用日志滚动不停，API使用量仪表盘上的数字迅速攀升。问题在于你完全不知道为什么会消耗那么多。哪个步骤中发生了不必要的文件重复读取？子智能体是否在重新计算上层智能体已经处理过的信息？会话结束后什么痕迹都不留下。智能体依然是黑盒子。

Agent-Blackbox正面解决了这个问题。这款工具于2026年6月在GeekNews上以38分被介绍，它将Claude Code和OpenCode的执行会话可视化为会话图，并分析每个步骤的令牌消耗量和浪费点。其核心不是简单的使用量追踪，而是将智能体可观测性（observability）的概念引入AI编码智能体领域。

本文从Agent-Blackbox的理念出发，从独立视角分析以下问题：AI编码智能体中令牌浪费如何在结构上产生，会话图对调试有何价值，以及智能体可观测性这一概念为何在2026年的基础设施实践中成为不可忽视的课题。以2026年6月为基准，该工具仍处于初期阶段。方向是正确的，但Agent-Blackbox提出的问题比工具本身更为重要。

1. 智能体黑盒问题 — 为何是现在

传统软件调试基于确定性假设：相同输入产生相同输出，通过回溯日志可以找到问题所在。AI智能体打破了这一前提。即使温度为零，非确定性依然存在；单次智能体执行会引发数十个工具调用和子智能体创建；每个步骤消耗的令牌的上下文和原因在任何输出文件中都没有记录。

2026年这一问题变得更加尖锐有其结构性原因：AI编码智能体进入了开发工作流的核心，单次智能体会话的成本突破了美元单位。社区报告显示，Claude Opus 4.x系列在相同智能体配置下消耗的令牌接近前版本的1.5倍。有报告显示，某CI流水线中一个4小时的智能体会话产生了180多次工具调用，产生了数十美元的令牌费用。如果不知道这些成本从何而来，就无法削减它们。

Agent-Blackbox的问题定义源于此：「如果不知道智能体做了什么，就无法知道为什么消耗那么多。」会话结束后留下的只有总令牌数和成本数字。哪个工具调用占了总成本的40%，哪个文件读取被不必要地重复了三次，子智能体之间哪里存在上下文重复——这些都在黑盒子里。

2. 什么是会话图 — 智能体执行的解析

Agent-Blackbox提出的核心概念是会话图（session map）。这是以时间线或树状结构表示智能体执行过程的可视化形式。每个节点代表一次工具调用（文件读取、Bash执行、搜索、子智能体创建等），节点间的边显示调用顺序和因果关系。每个节点附带消耗的输入令牌、输出令牌、缓存命中状态和延迟时间。

有了这种结构，以下几种即时诊断成为可能：

  • 重复读取检测：如果同一文件路径在会话图中出现3次以上，说明智能体在上下文中丢失了已读取的内容并重新请求。这是需要调整上下文压缩策略或缓存设置的信号。
  • 令牌集中区间识别：如果60%的令牌来自两个节点，说明这些工具调用正在生成过多输出。这为设置文件读取输出限制（CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS）或Bash输出限制（BASH_MAX_OUTPUT_LENGTH）提供了具体依据。
  • 子智能体重复检测：如果两个子智能体各自独立读取相似的文件集，说明编排设计存在问题。将一个智能体的结果传递给另一个智能体的上下文共享结构可以消除重复成本。
  • 无用MCP调用识别：注册的MCP服务器工具定义会在每轮系统提示词中占据数千令牌。会话图区分实际被调用的MCP工具和从未被调用的工具，为删除未使用的MCP服务器、降低固定成本提供数据支撑。

对于Claude Code，PreToolUse和PostToolUse钩子允许外部工具拦截这些事件。Agent-Blackbox通过读取这个钩子事件流来构建会话图。OpenCode作为开源项目，可以直接解析会话文件格式进行分析。能够以统一视图比较两个智能体是该工具的差异化优势。

3. 令牌浪费的结构 — 从哪里泄漏

在查看会话图之前，需要先理解AI编码智能体中令牌浪费的结构性原因。以2026年6月为基准，实践中观察到的浪费模式大致分为四类。

3.1 固定开销：系统提示词和工具定义

智能体每轮都将完整的系统提示词和所有注册的工具定义包含在上下文中。Claude Code内置约20个工具，连接10个MCP服务器会额外增加数千令牌的工具定义。无论任务需要什么，这个成本每轮都要支付。据报告，连接未使用的MCP服务器运行智能体时，工具定义的固定开销可能占总成本的20-30%。

3.2 对话历史累积

随着智能体会话延长，过去的工具输出、Bash结果、助手响应全部积累在对话历史中并在每轮上下文中携带。将短智能体循环运行100次后，第100轮的输入令牌会比第1轮指数级增长。当上下文压缩失败或缓存读取失败时，成本会急剧增加。社区有报告记录了这样的案例：缓存写入成功但读取失败，导致每次对话都要从头重新处理67,374个令牌。

3.3 不必要的外部连接

启用IDE自动连接（autoConnectIde）、网络搜索和全局文档自动加载的情况下运行智能体，每次会话都会增加与实际任务无关的连接成本。在OpenCode中禁用网络搜索（web_search = disabled）和MCP应用（features.apps = false），对于简单编码任务，每次会话的令牌数量明显减少，这一实测结果已在社区中共享。

3.4 子智能体重复上下文

在多智能体配置中，当编排器将相同文件或信息分别传递给多个子智能体时，会产生重复上下文成本。这是设计问题，不是智能体本身的问题，但没有会话图就无法知道这种重复是否正在发生。这正是Agent-Blackbox所瞄准的核心价值所在。

4. 智能体可观测性概念 — 为何在2026年全面发展

智能体可观测性（agent observability）是将AI智能体的执行捕获为结构化追踪、对每个步骤进行监控、评估和调试的实践。它是传统软件APM（应用性能监控）向AI智能体领域的延伸，2026年开始形成独立的类别。

两个结构性变化推动了这一趋势。第一，智能体从单次调用实用工具转变为运行数十个步骤的自主执行器，会话持续数分钟到数小时。简单聊天机器人一行日志就够了，但一个包含180次工具调用的4小时智能体会话，如果没有追踪整个执行树的可见性手段，就无法诊断失败原因。第二，成本变得不可忽视。智能体编码进入实际开发工作流，每月数百美元的智能体API成本已成常态，人们迫切想知道这些钱花在哪里了。

智能体可观测性的四个维度如下：

  • 执行追踪：按时间顺序和因果关系记录工具调用、子智能体创建和模型响应
  • 令牌与成本归因：每个步骤消耗了多少的分步明细
  • 输出评估：对每个步骤成果是否符合预期的定量评估
  • 智能体身份追踪：在多智能体环境中归因哪个智能体负责哪个任务

Agent-Blackbox专注于前两个维度：执行追踪和令牌成本归因。这种聚焦范围使其区别于Langfuse或Arize Phoenix等通用可观测性平台。专门处理Claude Code和OpenCode会话文件格式和钩子事件的轻量级本地优先工具定位，使其更具实用性。

5. Claude Code vs OpenCode — 可观测性视角比较

Agent-Blackbox同时支持两个智能体，这很有意思，因为两者呈现出结构上不同的可观测性接口。

5.1 Claude Code的可观测性架构

Claude Code内置了官方钩子系统。外部工具可以在设置文件（~/.claude/settings.json）中注册钩子命令，拦截所有工具调用事件。从可观测性工具的角度来看，这很方便：不需要修改智能体代码或插入代理层，只需使用官方扩展点即可。缺点是钩子事件提供的是工具调用级别的信息，不暴露内部推理过程（extended thinking）的令牌使用量或中间决策上下文。

5.2 OpenCode的可观测性架构

OpenCode是开源的，可以直接解析会话文件格式并插入自定义仪器。但没有稳定的钩子API契约，OpenCode版本更新时解析器可能失效。工具依赖特定格式这一脆弱性需要考虑。

5.3 两个智能体的共同盲点

两个智能体都无法完全暴露内部推理令牌（thinking tokens）。Claude Code的extended thinking模式中模型内部推理的长度，以及推理令牌占总成本的比例，目前的可观测性工具都难以获取。这是包括Agent-Blackbox在内的当代可观测性工具的共同局限。将智能体执行从黑盒中解放出来的工作还只完成了一半。

6. 实践应用 — 2026年的使用优先级

以2026年6月为基准，将智能体可观测性引入实际工作流的优先顺序如下。

6.1 从本地优先工具开始

会话日志包含原始提示词和代码内容。将其发送到外部服务器的SaaS可观测性平台可能与数据安全策略冲突。Agent-Blackbox、AgentProf、CodeBurn、ccusage等本地优先工具在本机完成分析。第一步是使用本地优先工具收集会话数据，首先了解哪些模式频繁出现。

6.2 先减少固定开销

在进行会话图分析之前，有些优化现在就可以做。对于Claude Code：设置includeGitInstructions: false、autoConnectIde: false，以及禁用当前任务不需要的MCP服务器，可以立即减少每轮固定开销。对于OpenCode：设置features.apps = false和禁用网络搜索具有相同效果。这些是无需会话图分析即可实施的已验证优化方法。

6.3 用会话图发现模式

Agent-Blackbox这样的会话图工具，其价值在于模式发现，而非单次成本追踪。对类似任务运行10次并排对比会话图，就能看到每次会话都重复出现的高成本模式。「这个智能体总是读取X文件3次」「Y工具调用后立即出现相同搜索」这类模式一旦发现，就成为修改提示词或调整工具设置的具体依据。

6.4 多智能体配置中更需注意

可观测性的价值在多智能体编排中远大于单一智能体。两个子智能体独立运行时，哪个子智能体占了多少百分比的成本，两个智能体之间是否存在上下文重复，没有会话图都看不见。如果团队正在使用Claude Code子智能体功能或OpenCode并行智能体配置，会话图几乎是必需的。

Agent-Blackbox不是这一领域的唯一工具。2026年6月，具有类似目标的工具同时涌现。梳理这一生态系统可以看清智能体可观测性的格局。

8. 局限性与客观评价

只列举优点不是分析。必须指出Agent-Blackbox和当代智能体可观测性工具的共同局限。

内部推理区域的不透明性：如前所述，Claude Code的extended thinking令牌无法通过钩子事件捕获。如果推理令牌占会话成本的相当大比例，会话图的分析完整性就存在缺口。

观测开销：添加钩子和记录事件本身会引入微小延迟。大多数情况下可以忽略，但对延迟敏感的工作流中，常开可观测性工具可能会造成负担。

日志安全：存储会话日志意味着原始提示词和代码片段会积累在磁盘上。即使是本地优先工具，也需要明确设置日志文件的访问控制和保留策略。

版本依赖性：会话文件格式可能随智能体版本更新而改变。工具依赖特定格式，智能体更新后解析器可能失效。Agent-Blackbox的长期可靠性取决于如何处理这一维护问题。

9. 结论 — 从黑盒中提取的问题更为重要

Agent-Blackbox提出的问题比工具本身更重要：「你知道智能体做了什么吗？」以2026年6月为基准，大多数团队会坦诚地回答：不太清楚。他们看到了成本数字，但看不到这些数字从何而来。

智能体可观测性正在成为基础设施，而非可选功能。对于在生产工作流中运行智能体的团队而言，继续对执行过程视而不见的代价——调试时间、浪费的令牌成本、静默重复的编排低效——正在超过部署可观测性层的代价。会话图、令牌归因和执行追踪是使智能体执行更可预测、更低成本、更易于调试的基本工具。

Agent-Blackbox是朝正确方向迈出的早期工具。它还不是完整的解决方案，但方法是正确的。将智能体执行保持在黑盒状态的成本，正在比引入可观测性工具的成本更快地增长。
