ktx: An Executable Context Layer for Data and Analytics AI Agents

Why AI agents hallucinate on enterprise data — and what an executable semantic context layer does about it

Jun 19, 2026 Dev & Infra

Introduction: The Gap Between AI Agents and Enterprise Data

As of June 2026, AI coding agents like Claude Code and Codex demonstrate impressive results when working with code repositories. But connect the same agent to a corporate data warehouse and ask it to "calculate the average payment cycle for active customers last quarter," and the story changes fast. The agent will generate SQL almost instantly — but whether that SQL aligns with your organization's agreed-upon definition of "active customer" is another matter entirely.

This is not a model intelligence problem. The agent simply does not know the approved metric definitions, table relationship rules, or business glossary terms your company has built up over years. General-purpose LLMs are trained on the public internet, not on your organization's internal data contracts. The layer that bridges this gap is called a "context layer," and ktx is an open-source implementation of that idea.

This post analyzes ktx's architecture, how it works, and why semantic and context layers are becoming essential infrastructure for data analytics agents — not hype, but a prerequisite for agents to be trusted in real decision-making pipelines.

1. The Problem: Why AI Agents Hallucinate on Data

When an AI agent analyzes a codebase, it has an explicit source of truth: the source files themselves. In enterprise data environments, truth is distributed. The word "revenue" might mean something different to the finance team, the sales team, and the marketing team. "Active user" might mean logged in within 30 days, 90 days, or paid in the last quarter. These definitions typically live scattered across Slack threads, Google Docs, dbt code comments, and outdated wikis.

1.1 The Real Limits of Text-to-SQL

Text-to-SQL technology has advanced significantly in converting natural language queries into SQL. But it remains fragile in front of complex enterprise join graphs. Two classic traps appear repeatedly:

  • Fan-traps: In one-to-many relationships, aggregating without knowing join order inflates values incorrectly.
  • Chasm-traps: Two many-to-many relationships sharing a bridge table cause Cartesian product explosions during joins.

For an agent to avoid these independently, table relationship rules must be pre-defined. Having agents reverse-engineer schemas by issuing exploratory queries is expensive, slow, and produces inconsistent SQL for the same problem on different runs. The output becomes unreliable across sessions.

1.2 The Cost of Hallucination at Scale

At the chatbot level, hallucination was an inconvenience. When agents autonomously process data pipelines, dashboards, and executive reports, the cost escalates sharply. A SQL query built on an unapproved metric definition that makes it into a monthly business report — and then into a budget decision — is no longer a technical curiosity. Industry analysis suggests that without proper context grounding, agent accuracy on enterprise data queries hovers around 50%, while organizations that deploy structured context platforms have reported accuracy rates above 90%.

2. ktx's Solution: Executable Context

ktx (GitHub: Kaelio/ktx, Apache 2.0) addresses this problem through structured, agent-consumable context. The core philosophy is simple: Context as Code. Metric definitions live in YAML files rather than Slack messages. Business terminology is git-managed rather than buried in wikis — reviewable, diffable, mergeable.

2.1 Architecture Overview

ktx operates across two connected pipelines:

  • Ingest pipeline: Reads databases, BI tools (Looker, Metabase, etc.), modeling code (dbt, MetricFlow, LookML), documentation (Notion, etc.), and query history to build context. When contradictions are detected across sources, they are flagged for human review. Outputs land in two places: wiki/ Markdown files and semantic-layer/ YAML definitions.
  • Runtime service: When an agent queries ktx through MCP or CLI, ktx runs combined full-text and semantic search over the wiki and semantic layer, then compiles approved metrics into read-only SQL to return to the agent.

One design decision deserves special attention: ktx is read-only by design. Agents can consume context but cannot modify data directly. This is an explicit safety constraint, not an oversight.

2.2 What the Semantic Layer Actually Does

ktx's semantic layer overlaps with tools like dbt but serves a different purpose. Where dbt focuses on versioning transformation logic, ktx produces agent-consumable "approved knowledge." Concretely:

  • It auto-generates join graphs that pre-resolve fan-trap and chasm-trap paths, so agents reference safe join routes instead of improvising.
  • Aggregation methods, filter conditions, and dimensions are declared in YAML — agents reuse approved definitions instead of reinventing SQL from scratch each time.
  • Ingest-time contradiction detection between sources prevents incorrect definitions from propagating silently across the organization.

2.3 Why MCP as the Runtime Interface

ktx's choice of MCP (Model Context Protocol) as the agent interface is strategically sound. MCP is becoming the de facto standard for agent-tool communication, with Anthropic driving adoption and the industry converging on it. Any MCP-compatible agent — including Claude Code — can integrate with ktx without additional API scaffolding. This vendor-neutral integration surface is a defensible design choice at a time when the agent ecosystem is evolving rapidly.

3. Context Layer vs. Semantic Layer: Clarifying the Concepts

The two terms are frequently conflated, but the distinction matters in practice.

ConceptCore RoleKey ContentsRepresentative Tools
Semantic LayerCentralizes metric and dimension definitionsMetric definitions, join rules, aggregation logicdbt Semantic, MetricFlow, LookML
Context LayerProvides executable agent-consumable knowledgeSemantic + business glossary + query history + decision tracesktx, DataHub

A context layer includes the semantic layer but extends it. For agents to be trustworthy not just accurate, they need to explain why a metric is defined this way — a requirement for audit trails in regulated or high-stakes environments. ktx's wiki component handles this: definition provenance and change history are tracked in git.

4. The Enterprise Data AI Perspective

The first question data teams face when deploying AI agents is: "How do we guarantee accuracy?" If an agent autonomously generates dashboards shown to executives, and a number is wrong, who owns that? Until the accountability chain is clear, agents remain supplementary tools no matter how capable the underlying model is.

4.1 Building a Single Source of Approved Truth

A context layer is the infrastructure that creates accountability. When a metric is defined in YAML and version-controlled in git, there is a record of who reviewed and approved it. When an agent generates SQL by referencing that definition, the accountability chain is explicit: "the team approved this metric, and the agent applied it." That shifts the framing from "the agent did something on its own" to "the agent executed against team-approved definitions."

4.2 The Self-Improving Feedback Loop

ktx's self-improvement mechanism re-ingests query history to enrich the context. As teams accumulate repeated SQL patterns, the semantic layer strengthens and agent accuracy on subsequent queries improves. In principle, the context converges toward how the organization actually works over time. In practice, the quality of the query history matters: if incorrect queries accumulate, they can pollute the context. The rigor of the human review layer determines how well this loop works.

4.3 Practical Adoption Considerations

Before adopting ktx, organizations should assess several factors:

  • Initial build cost: Organizations without existing metric documentation, or with definitions scattered across multiple systems, face meaningful upfront structuring work. Automated ingest helps, but the source-reconciliation review step cannot be skipped.
  • Ownership model: When metric definitions change, someone must update the YAML. Who owns this? "Everyone" typically means "no one" in practice.
  • Agent trust boundaries: Even with a context layer in place, running agents in a fully autonomous loop without human review is premature for high-stakes data decisions. Context infrastructure raises accuracy; it does not eliminate the need for oversight.

5. Ecosystem Position and Industry Trends

The enterprise data context layer market is forming quickly as of June 2026. Established data governance platforms like DataHub and Atlan are adding AI agent context layer features. dbt's Semantic Layer is deepening agent integration. Gartner forecasts that by 2027, organizations prioritizing semantics in AI-ready data will improve GenAI accuracy by up to 80% and cut costs by up to 60%.

5.1 The Strategic Case for Open Source

ktx's Apache 2.0 release is more than a license choice. A context layer is where an organization's core business knowledge lives. Organizations that are uncomfortable putting that into a closed vendor's cloud — a legitimate concern around data residency and control — find open-source to be a compelling alternative. The TypeScript and Python codebase is forkable and customizable for internal needs.

5.2 MCP Standardization and the Road Ahead

MCP is consolidating as the dominant agent-tool interface standard. ktx's bet on MCP appears well-calibrated. However, as Gartner notes, MCP alone is insufficient. MCP is the wiring; the context layer is the signal. Without it, agents connected via MCP still generate SQL from scratch every time, with all the consistency problems that implies.

6. Critical View: Unresolved Challenges

ktx addresses the right problem. But several questions remain open.

6.1 Context Freshness

As businesses evolve, metric definitions change. A context layer that lags behind the actual business injects stale "approved truth" into agents — a paradox that could make things worse than no context at all. ktx's self-improvement mechanism partially addresses this, but "when to re-ingest" and "what triggers re-review" are operational policy questions that the tool alone cannot answer.

6.2 Adoption Barrier for Small Teams

ktx's value is most visible in mid-to-large organizations with complex metric governance and cross-team definition conflicts. A five-person startup on a single Snowflake schema running a data agent might find the overhead of maintaining a context layer outweighs the benefit. Calibrating tool fit to organizational scale matters.

6.3 The Fundamental Trust Question

A context layer helps agents produce more accurate SQL. But the accountability question for a fully autonomous loop — where agents generate SQL, execute it, interpret results, and write reports without human review — is a different layer of discussion. Better infrastructure improves agent accuracy; it does not resolve the question of whether fully autonomous data decision-making is appropriate in a given context.

7. Conclusion: Essential Infrastructure for the Data Agent Era

ktx is well-timed. As AI agents expand from code to data, the absence of structured context means agents remain approximation machines at best and misinformation generators at worst. The concept of an "executable context layer" is not marketing language — it is a prerequisite for agents to earn genuine trust in data analysis workflows.

That said, deploying ktx is the beginning, not the end. The real ongoing cost of a context layer is not the initial build but the continuous maintenance and review culture required to keep it accurate. Organizations that define who owns metric definitions, how changes are reviewed, and how often freshness is audited will get the value ktx promises. Those that treat it as a one-time setup will find the context drifting from reality. For data teams ready to invest in that discipline, the time to evaluate this approach is now.
