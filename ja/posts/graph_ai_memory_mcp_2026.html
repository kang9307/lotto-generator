共有可能なグラフベースAI Memory MCP - エージェント永続メモリの新パラダイム

AIエージェントが長期記憶をグラフ構造で保存しMCPで共有する — なぜ今この方式が台頭するのか

2026-06-18 開発・インフラ

はじめに：AIが「覚えられない」ことの本当の意味

AIエージェントを実務に導入して最初にぶつかる壁は、能力の問題ではない。記憶の問題だ。今日説明したプロジェクトのコンテキストを、明日また最初から説明しなければならない。先週確定したアーキテクチャ上の決定を、エージェントは知らない。チームメンバーAがエージェントと合意したコーディング規則を、同じコードベースを扱うメンバーBのエージェントは受け取っていない。これはLLMの構造的な限界だ。ステートレス設計は水平スケーラビリティと再現性のための意図的な選択だが、その代償としてエージェントは毎回新たに生まれ直す。

2026年6月、この問題を正面から解決しようとするオープンソースプロジェクトが注目を集めている。MemoryWeftは、AIの会話と文書をSQLiteまたはPostgreSQLに保存し、MCP（Model Context Protocol）を通じて複数のエージェントがその記憶を共有できるよう設計されたMCPサーバーだ。核心的なアイデアは2つある。第一に、記憶を単純なテキストではなくグラフ構造として保存すること。第二に、そのグラフをMCP公開エンドポイントとして公開し、Claude・Codex・Gemini CLIのような異質なエージェントが同一の知識ベースを読み書きすること。

この記事では、その方向性がなぜ意味を持つのか、どのような限界があるのか、そして2026年のAIメモリインフラ地形においてこのアプローチがどこに位置するのかを分析する。以前に取り上げたSupermemory AIコンテキストエンジンが単一エージェントのコンテキスト管理と高速検索に焦点を当てたものとは異なり、本稿はグラフ構造・MCP標準・マルチエージェント共有という3つの軸を中心に論じる。

1. LLMはなぜ忘れるのか — 構造的原因

永続メモリがなぜ必要かを理解するためには、LLMがなぜ忘れるのかから見ていく必要がある。

1.1 ステートレス設計というトレードオフ

LLMは設計哲学の水準でステートレスだ。各API呼び出しは独立したコンテキストウィンドウを受け取って処理し、呼び出しが終わると中間計算はすべて捨てられる。このステートレス性があるからこそ、同じモデルを何万人もの同時ユーザーが使えるし、同じ入力が同じ出力を生む（再現性）。クラウド規模のAIサービスが可能なのは、このステートレス構造のおかげだ。

しかし代償がある。エージェントがユーザーの好みを学習しても、その学習はコンテキストウィンドウの外に出た瞬間に消える。長期プロジェクトで意思決定を積み重ねても、次のセッションでエージェントはゼロに戻る。チームが複数のエージェントを運用すれば、各エージェントはお互いのコンテキストを知らないまま独立して動く。これがメモリ問題の本質だ。

1.2 長いコンテキストウィンドウという錯覚

100万トークンのコンテキストモデルが登場したことで「長い記憶もコンテキストに全部入れればいい」という期待が生まれた。しかしこのアプローチには3つの問題がある。第一に、毎回の呼び出しに数十万トークンを付加するコストはすぐに実用限界に達する。第二に、重要なものとそうでないものを区別せずに積み上げると検索精度が低下する。第三に、決定的なことに、コンテキストウィンドウはセッションが終わると消える。長いウィンドウは短期記憶の容量を増やしただけで、長期記憶の問題を解決していない。2026年6月時点、AIエージェントメモリ分野の主流の見解はこうだ。永続メモリレイヤーはエージェントインフラの荷重支持要素であって、オプションの最適化ではない。

2. グラフメモリがベクトルより優れている理由

エージェントメモリ保存方式の第一世代はベクトルデータベースだった。会話内容を埋め込みに変換し、類似度ベースで検索する方式だ。有効なケースも多いが、構造的な限界がある。

2.1 ベクトルストアの3つの構造的弱点

第一に時間的無感覚だ。ベクトルデータベースはタイムスタンプを検索重みに反映しない。6ヶ月前の決定と昨日の決定のテキスト類似度が同じなら、同等に返ってくる。エージェントが最新の状態を基に判断すべきとき、古い事実が同じ重みで混じり込む。

第二に関係の走査不可だ。ベクトルストアは類似チャンクのフラットなランキングを返す。「この認証サービスが依存しているモジュールを最後に変更した人は？」のような多段ホップ（multi-hop）クエリはベクトル類似度だけでは表現できない。

第三にコンテキストの断絶だ。個別チャンクはお互いを参照しない。エージェントが「AとBの間に何があったか」を問うとき、ベクトルストアはAに関するチャンクとBに関するチャンクを別々に返すだけで、その関係自体は保存されていない。

2.2 グラフメモリが優れている3つの理由

グラフメモリはエンティティ（ノード）・関係（エッジ）・時間マーカーを一緒に保存する。これが上の3つの弱点を直接補う。

第一に時間推論だ。グラフエッジにvalid_from・valid_until・recorded_atのような時間属性をつけることで、過去の状態と現在の状態を明確に区別してクエリできる。これはベンチマークでも確認されており、ZepのGraphiti（グラフベース）はGPT-4oでLongMemEvalスコア63.8%を記録し、ベクトルベースのMem0（49.0%）を約15ポイント上回っている。

第二に関係の走査だ。グラフでは「Aliceが完了した認証サービス → そのサービスに依存する決済モジュール → 決済モジュール担当のBob」のような多段ホップ経路を自然にクエリできる。エンティティ間の関係が明示的なエッジとして存在するためだ。

第三にスキーマなしの進化だ。MemoryWeftのECKG（Event-Centric Knowledge Graph）アプローチのように、事前に関係タイプを定義しなくてもデータが蓄積されるにつれてグラフが自然に成長する方式が可能だ。硬直したスキーマなしに複雑なドメイン知識を蓄積できる。

2.3 ベクトルが依然として適している場面

グラフが常に優れているわけではない。非構造化した長いテキストの意味的検索、単純な類似度ベースのリコール、低い運用複雑性が重要な場合はベクトルが実用的だ。2026年の本番アーキテクチャの主流はベクトルとグラフのハイブリッドだ。エピソード記憶（特定イベント履歴）にはベクトル、セマンティック記憶（概念・関係）にはグラフ、タスク状態には別途状態ストアを使う3レイヤー構造がコミュニティ標準となっている。

3. MCPでメモリを共有するということの意味

MemoryWeftが単純なメモリ保存ツールと区別される核心は共有だ。MCPを通じてメモリを公開すると何が変わるのか。

3.1 メモリサイロ問題

既存のエージェントメモリ設計の支配的な前提は「メモリは単一のエージェントまたは単一のセッションに帰属した状態」というものだった。Claude Desktopのメモリ、Cursorのメモリ、Gemini CLIのメモリはそれぞれ分離したサイロだ。同じコードベースを扱っていても、昨日Claudeと合意したアーキテクチャ上の決定を今日別ツールで引き出す方法がなかった。複数エージェントを調整するワークフローでは、各エージェントが異なる状態で動けば、衝突・重複・非一貫性は必然的に起きる。

3.2 MCP共有メモリのアーキテクチャ

MCP（Model Context Protocol）はAnthropicが提案した開放型標準で、AIエージェントと外部ツール・データソース間のインタフェースを標準化する。この標準の上にメモリサーバーを実装することで、どのMCP対応エージェントでも同じプロトコルでメモリを読み書きできる。MemoryWeftはこの設計を実際に実装し、Claude・Codex・Gemini CLIという3つの異質なAIプラットフォームが1つのメモリサーバーを共有することをサポートすると発表した。エージェントAが設計上の決定をグラフに書き込めば、エージェントBが同じグラフを読んでその決定を文脈として引き継ぐ。単一の知識基盤の上で複数エージェントが協力する構造だ。

3.3 チームコラボレーションへの拡張

個人ユーザーレベルでも有用だが、MemoryWeftが強調するより大きな価値はチームメンバー間のメモリ共有だ。チームの各メンバーが各自のエージェントを使っていても、共有MCPメモリサーバーを通じてチーム全体の知識グラフを蓄積・クエリできる。Aがインフラの決定を記録すれば、Bはその決定の文脈の上でコードを書き、Cはその履歴を参照してドキュメントを書く。各自のエージェントが別々のツールで動いても、知識は一か所に蓄積される。これはエージェントコラボレーションのパラダイム転換を示唆する。エージェントは個人アシスタントではなく、共有知識基盤の上に立つチームメンバーになる。

4. 2026年のAIメモリエコシステムの地形

MemoryWeftは孤立したプロジェクトではない。2026年にすでに成熟段階に入ったAIエージェントメモリエコシステムの一地点だ。

4.1 エコシステムの現状

2026年6月時点、AIエージェントメモリのインフラは21以上のフレームワーク、20以上のベクトルストア、そしてマネージドクラウド・オープンソース自己ホスティング・ローカルMCPという3つのホスティングモデルに分化している。主要なプレイヤーを整理すると以下の通りだ。

4.2 共通の方向性：標準化と共有

このエコシステムで見えてくる共通の方向性は2つだ。一つは標準プロトコルへの収束だ。MCPが事実上の標準として定着しつつあり、ほとんどのメモリソリューションがMCP互換インタフェースを追加するか、MCPを基本インタフェースとして採用している。もう一つは単一エージェントメモリからマルチエージェント共有メモリへの移行だ。個人カスタマイゼーションからチーム知識共有へ重心が移っている。注目すべき学術的潮流もある。2026年6月に発表された「Memory as a Service（MaaS）」論文は、メモリを単一エージェントに帰属した状態ではなくサービス指向モジュールとして抽象化する方向を提案しており、MemoryWeftの共有メモリ哲学と同じ方向を向いている。

4.3 本番環境での考慮事項

理論的な利点とは別に、実際の導入では3つのことを検討する必要がある。第一に一貫性の保証だ。複数エージェントが同時に同じグラフに書き込む環境での書き込み競合をどう処理するか。MemoryWeftはPostgreSQLバックエンド利用時はデータベーストランザクションに委ねるが、分散環境では追加の考慮が必要だ。第二に精度 vs リコールのトレードオフだ。MemoryWeftは精度より関連性の発見（ヒント提供）を優先すると明示している。このAI補助ツールとしての哲学が自分のワークロードに合っているか検討が必要だ。第三に運用複雑性だ。ローカルSQLiteから始めるとシンプルだが、チームスケールでPostgreSQLサーバーを共有運用すれば別途インフラ管理の負担が伴う。

5. グラフベース共有メモリが開く可能性

5.1 長期ソフトウェアプロジェクトの知識蓄積

6ヶ月のソフトウェアプロジェクトを想像してみよう。チームは数百のアーキテクチャ上の決定を下す。なぜこのライブラリを選んだか、なぜそのパターンをやめたか、どんなトレードオフを受け入れたか。現在この知識はドキュメントに一部記録され、大半は個人の記憶とSlackの履歴に散在する。新メンバーや外部AIエージェントはこの文脈にアクセスできない。グラフベース共有メモリがあれば、これらの決定がグラフのノードとエッジとして蓄積される。「なぜTypeScriptを選んだか」→「どんな代替案を検討したか」→「その決定がその後どんな変更を引き起こしたか」が探索可能な関係網となる。

5.2 マルチエージェントワークフローの調整

コードレビューエージェント・ドキュメント作成エージェント・テスト生成エージェントが分業するワークフローを考えてみよう。各エージェントが独立したメモリを持つなら、コードレビューエージェントが発見した設計上の問題を文書エージェントもテストエージェントも知らない。共有グラフがあれば、コードレビューエージェントが「このモジュールはX理由で脆弱だ」というノードを書いた瞬間に、文書エージェントとテストエージェントがその文脈を引き継ぐ。分業しつつも知識は共有する構造だ。

5.3 プラットフォームに依存しないユーザーコンテキストの移植性

個人ユーザーの観点でも強力なシナリオがある。今日Claude Desktopでエージェントと作業し、明日Cursorに切り替え、明後日Gemini CLIを使っても、共有MCPメモリサーバーに蓄積された自分のコンテキストはどのツールからでもアクセスできる。ツールを変えるたびに最初から説明する繰り返しがなくなる。メモリはツールではなくユーザーに帰属する構造だ。

6. 限界と冷静な視点

6.1 グラフ構成の品質がすべて

グラフメモリの価値はグラフをいかに意味のある形で構成するかに完全にかかっている。どのイベントをノードにし、どの関係をエッジにつなぐかを決めることが核心だ。この抽出がうまくいかなければグラフはノイズの塊になる。ECKGのようにスキーマなしで進化するアプローチは柔軟だが、関係が一貫して表現される保証はない。

6.2 セキュリティとプライバシー

チーム単位で共有メモリを運用するには、誰が何を読み書きできるかについての細かいアクセス制御が不可欠だ。MemoryWeftのような初期段階のオープンソースプロジェクトが詳細な権限管理をどの程度サポートしているかは、実際の展開前に確認が必要だ。共有グラフに機密性の高いビジネス上の決定が蓄積される場合、この問題はさらに重要になる。

6.3 MCPエコシステムの成熟度

MCPは良い標準だが、まだ急速に発展している標準だ。MCP互換性を主張するツール間でも、細かい動作方式に差異がある場合がある。複数のエージェントが実際に単一のMCPメモリサーバーを同時に使用するときの安定性は、実際の負荷環境での検証が必要だ。

7. 結論 — 今週できる3つのアクション

2026年6月時点、AIエージェントメモリの方向性は明確だ。ステートレスLLMの上に永続メモリレイヤーを重ねることは選択ではなく必須となった。その保存構造としてグラフがベクトルの限界を補う核心的な手段として台頭している。そこにMCPを通じた共有が加わることで、エージェントは個人ツールから共有協力者へと飛躍する。

MemoryWeftはこの3つの要素を一度に実装しようとするオープンソースの試みだ。まだ初期段階で、本番規模での検証はさらに必要だ。しかし方向性は正しい。グラフ・MCP・共有という3軸の組み合わせは、2026年のエージェントインフラの核心的な進化ベクトルだ。

今週すぐ適用できる3つのことを挙げるなら。第一に、自分のエージェントワークフローで「なぜ同じ文脈を毎回また説明しているのか」を実際のコスト（時間・損失）として計測せよ。そのコストが大きければ、メモリレイヤーへの投資の根拠になる。第二に、AnthropicのKnowledge Graph Memory MCP公式サーバーをローカルで試してみよ。設定が簡単で、グラフメモリの基本動作を確認するのに最適だ。第三に、チームスケールの共有が必要なら、MemoryWeftかGraphitiをPostgreSQLバックエンドで構成し、実際のコラボレーションシナリオでテストせよ。グラフの品質とアクセス制御を先に確認してから本番に持ち込む順序が安全だ。
