What follows summarizes what the Docker Agent repository README and the docs directory state. Configuration examples and commands are copied from those documents, and comparisons or forecasts that the documents do not contain are left out.

Context - Agents Defined in a Config File Instead of Code

Docker Agent is an open-source tool published by Docker. It is a Docker CLI plugin: the agent's model, instructions, tools and the teammate agents it works with are written in a YAML file and run with the docker agent command. The README introduces it in one line as "Build, run, and share AI agents with a declarative YAML config, rich tool ecosystem, and multi-agent orchestration", and its description section says "no code required".

The first sentence of the official documentation reads "Docker Agent is to AI agents what docker run is to containers". The documentation explains that Docker Agent handles the LLM orchestration loop, tool execution, multi-agent delegation and streaming output, so that the user can focus on what the agent should do rather than on how the pieces are wired together.

The project was registered on GeekNews on 8 October 2026. According to the repository metadata the owner is the docker organization, the license is Apache-2.0, the repository was created on 1 September 2025, and the latest release is v1.149.0, dated 7 October 2026. These values are as shown on the GitHub repository and release pages at the time of writing and may change afterwards.

Installation is described through three routes. Docker Desktop 4.63 or later ships the plugin pre-installed, so docker agent can be run immediately, and Homebrew installs it with brew install docker-agent. A binary downloaded from the GitHub releases can be placed in ~/.docker/cli-plugins so that it also works as docker agent. The installation page states that building from source requires Go 1.27 or higher, and that releases are published for Windows, macOS and Linux.

Identity of Docker Agent - What It Is and What It Is Not

The landing page of the official documentation contains four summary cards that describe the tool. The items below restate those cards.

  • What it is: a CLI that runs AI agents defined declaratively in YAML or HCL.
  • What it is not: not a framework you write code in, not a hosted SaaS, and not a new model.
  • Who it is for: developers who want agents in their workflow without glue code.
  • What you get: the documentation lists a TUI, a CLI, an HTTP API, an MCP server, A2A and OCI distribution.
  • Origin: the documentation presents it as an open-source tool from Docker, the maker of Docker Engine, Docker Desktop, Docker Hub and Docker Scout.

The documentation contrasts two ways of building the same coding assistant. Without Docker Agent its example needs roughly 30 lines of Python glue code in every project, covering client setup, tool schemas, a dispatch function and a message loop. With Docker Agent the same assistant is described in 8 lines of YAML plus the single command docker agent run agent.yaml. The line counts belong to the example given in the documentation itself.

Single-Agent YAML Structure and Fields

The first example in the README places one root agent under agents and sets its model, description, instruction and tools. It is started with docker agent run agent.yaml.

agents:
                      root:
                        model: openai/gpt-5-mini
                        description: A helpful AI assistant
                        instruction: |
                          You are a knowledgeable assistant that helps users with various tasks.
                          Be helpful, accurate, and concise in your responses.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo

The introduction page of the documentation carries a coding assistant that uses the filesystem, shell and think tools.

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: A coding assistant
                        instruction: |
                          You are an expert developer. Help users write clean,
                          efficient code. Explain your reasoning step by step.
                        toolsets:
                          - type: filesystem
                          - type: shell
                          - type: think

The table below summarizes the main fields shown in those two examples and in the agent configuration reference. The reference states "A configuration must define at least one agent under agents".

Field Type What the documentation says Notes
agents Map Top-level entry keyed by agent name At least one agent must be defined
model String Model reference; the examples use a provider/model form Marked required unless a harness is set
description String What this agent does Optional in the schema
instruction String or list The system prompt Mutually exclusive with instruction_file; a list is joined with blank lines
toolsets List Tool configurations type selects the tool; mcp adds a ref
sub_agents List Local or external sub-agent references Used by the delegation pattern
handoffs List Names of agents this agent can hand the conversation to Used by the handoff pattern

On model providers, the README lists OpenAI, Anthropic, Gemini, AWS Bedrock, Mistral, xAI and Docker Model Runner, followed by "and more". The introduction page says a model can be swapped by changing the single model: line and notes that local models can be used through Docker Model Runner or Ollama. The README also instructs readers to set at least one API key, or to use Docker Model Runner for local models.

The full schema in the configuration reference lists further entries with inline comments. Four of them are summarized here.

  • instruction_file: loads the system prompt from one or more files relative to the config.
  • fallback: sets fallback models together with a retry count and a cooldown.
  • max_iterations: caps the number of tool-calling loops.
  • harness: delegates to an external coding CLI; the type values listed are claude-code, codex, opencode and pi.

The documentation also states that HCL is another syntax for the same configuration model. Wherever a .yaml or .yml file is accepted a .hcl file is accepted too, and HCL is converted internally to the equivalent YAML structure before the same schema validation runs.

Two Multi-Agent Patterns - Delegation and Handoffs

The multi-agent page explains that complex tasks benefit from specialization: instead of one monolithic agent, a team can be built from a coordinator, a developer, a reviewer and a researcher, each with its own model, tools and instructions. The comparison of the two patterns follows the table in the documentation.

Item Delegation (sub_agents) Handoffs (handoffs)
Topology Hierarchical (parent, child, parent) Peer-to-peer graph (A, B, C, A)
Session The child runs in a sub-session The conversation stays in the same session
Context The child receives a clean task description The next agent sees the full conversation history
Control flow The parent blocks until the child finishes, then continues The active agent switches and the previous agent leaves the loop
Tool transfer_task handoff
Best for Delegating tasks to specialists Pipeline workflows and conversational routing

In delegation, an agent that has sub_agents automatically receives the transfer_task tool. According to the tool page it takes three parameters, agent, task and expected_output, and all three are required. The call blocks until the sub-agent returns its result, and the documentation adds that sub_agents and handoffs can be combined in a single configuration. The page walks through delegation in five steps: the user sends a message to the root agent; the root agent analyzes the request and decides which sub-agent should handle it; the root agent calls transfer_task with the target agent, a task description and the expected output; the sub-agent processes the task in its own agentic loop using its tools; and the results flow back to the root agent, which responds to the user. Its example call delegates to an agent named developer with the task of creating a REST API endpoint for user authentication and the expected output of working Go code with tests.

A handoff passes the entire conversation to another agent. The documentation lists three situations where this fits: pipeline workflows in which data flows through a chain of specialized agents, conversational routing in which a coordinator sends the user to the right specialist who can route back when done, and graph topologies in which agents form cycles such as A to B to C to A. The flow has five steps. The user messages the starting agent, Agent A processes the message and calls handoff to route to Agent B, Agent B becomes the active agent and sees the full conversation history, it can respond, use its own tools or hand off again, and this continues until an agent responds directly without handing off. The documentation's example has a coordinator that routes to a researcher, who hands off to a summarizer, who returns control to the coordinator.

agents:
                      root:
                        model: anthropic/claude-sonnet-4-5
                        description: Coordinator that routes queries
                        instruction: |
                          Route research queries to the researcher.
                        handoffs:
                          - researcher
                    
                      researcher:
                        model: openai/gpt-5
                        description: Web researcher
                        instruction: |
                          Search the web, then hand off to the summarizer.
                        toolsets:
                          - type: mcp
                            ref: docker:duckduckgo
                        handoffs:
                          - summarizer
                    
                      summarizer:
                        model: openai/gpt-5
                        description: Summarizes findings
                        instruction: |
                          Summarize the research results, then hand off
                          back to root.
                        handoffs:
                          - root

The handoff page states that the tool only targets agents declared in the same config file and opens no network connection. To delegate to a remote agent it points to the A2A toolset. Each agent can hand off only to the names listed in its own handoffs array.

The selection criteria given by the documentation are as follows.

  • sub_agents: use when a coordinator must send tasks to specialists and synthesize their results.
  • handoffs: use when agents take turns processing the same conversation, as in pipelines or routing.
  • background_agents: use when several independent tasks can run at the same time. The documentation names the tools run_background_agent, list_background_agents, view_background_agent, wait_background_agents and stop_background_agent.

The documentation points out that with plain handoffs the model decides whether to call the handoff tool, so it may fail to do so. The force_handoff option closes that gap: when the agent produces its final response, the runtime itself routes the conversation to the named agent. The rules enforced at load time are that the target must be defined in the config, an agent cannot force a handoff to itself, and chains of force_handoff edges must not form a cycle.

  • Cycle rejection: a delegation that targets an agent already in the active delegation chain, for example a to b to a, fails with an error.
  • Depth cap: nested delegations are limited to 10, and the root delegating to its first sub-agent counts as depth 1.

Tool Ecosystem - Built-in Toolsets and MCP Servers

The tools page explains that when an agent makes a tool call, the Docker Agent runtime executes the tool and returns the result, which the agent then uses to continue. A built-in toolset is switched on by adding its type to the toolsets list. The filesystem page adds that edit_file applies a sequence of find-and-replace edits in memory and writes the result once after every edit validates, so a rejected edit, such as one with an empty oldText, leaves the file untouched. The shell page adds that destructive commands are labelled with a blast radius of low, medium or high, which the confirmation dialog of the terminal interface shows as a colored badge.

Tool type Behavior stated in the documentation Constraints stated in the documentation
Filesystem filesystem Reading, writing and searching files through read_file, write_file, edit_file, list_directory, search_files_content and others Unrestricted by default; allow_list and deny_list narrow the reachable directories
Shell shell Runs shell commands; each call uses a fresh, isolated shell session Default timeout of 30 seconds; user confirmation required unless --yolo is used
Script script Exposes predefined shell commands as named tools with typed parameters Described as giving the agent less freedom but more safety than the generic shell tool
MCP mcp Connects tools from Model Context Protocol servers Three flavors: Docker MCP, local stdio and remote
Reasoning and memory think, todo, memory The README lists built-in think, todo and memory tools —
Retrieval rag README: pluggable retrieval with BM25, embeddings, hybrid search and reranking —

The MCP tool page distinguishes three ways of connecting servers.

  • Docker MCP (recommended): servers run as Docker containers through the MCP Gateway, and a reference such as ref: docker:duckduckgo pulls a definition from the Docker MCP Catalog.
  • Local stdio: a local process is started with command and args and communicates over standard input and output.
  • Remote: remote.url and transport_type (streamable or sse) connect to a server on the network. The page states that OAuth flows are handled automatically.
  • Tool filtering and auto-install: a tools list narrows which tools are exposed to the model, and a local command missing from PATH is looked up in the aqua registry and installed, which DOCKER_AGENT_AUTO_INSTALL=false turns off.

Sharing Agents Through OCI Registries

The distribution page says an agent can be pushed to any OCI-compatible registry, such as Docker Hub or GitHub Container Registry, and pulled and run from anywhere. The push and pull examples in the documentation are the following.

docker agent share push ./agent.yaml docker.io/username/my-agent:latest
                    docker agent share pull docker.io/username/my-agent:latest
  • Running: the README quick start shows docker agent run myorg/agent:tag for running an agent straight from a registry.
  • Signing: share push --key lets pullers verify who published the agent and that it was not altered. The YAML itself is always pushed in clear, and only the proof goes into the OCI manifest annotations.
  • Encryption: adding --encrypt also records an authenticated encrypted copy of the whole YAML in the annotations. The documentation's examples use an Ed25519 key and a symmetric secret.
  • Attestation format: the signature covers an in-toto Statement v1 carried in a DSSE envelope, which the documentation says is the format cosign and in-toto tooling use, so it can be read and verified without Docker Agent.
  • External sub-agents: the multi-agent page says sub-agents need not be defined locally and can reference agents from an OCI-compatible registry.

The permissions page warns that a configuration pulled from a URL or an OCI registry carries defaults chosen by its author, and advises reviewing third-party configurations before running them. Signature verification checks integrity and provenance; it is not a statement that the configuration is safe. The distribution page also warns that the key kinds differ: a passphrase-protected key is not supported, and a symmetric secret can be guessed offline against the public YAML, so it recommends random material such as the output of openssl rand -hex 32 rather than a password.

Permissions and Safety Modes - How Approval Works

The tools page states the default behavior as follows: Docker Agent asks for user confirmation before executing tools with side effects such as shell commands and file writes, and --yolo auto-approves all tool calls. The permissions page describes a finer-grained structure. It also states that a session which never chooses a safety mode keeps the historical default, in which read-only tools are approved automatically and everything else asks, and that for a new root session the first source found in a fixed order wins: an explicit --safety flag, then an explicit --yolo flag, then the alias option, then the user settings, then the selected agent's own safety field, then the runtime-wide safety field.

  • Evaluation order: permission rules are evaluated as deny, then allow, then ask. Deny takes priority, and a call matched by no rule falls through to the session's safety mode.
  • Four safety modes: strict asks about every call. Balanced runs safe calls silently and asks about the rest. Restricted runs safe calls and denies everything else without asking, and autonomous runs everything.
  • Place of --yolo: the documentation calls autonomous the legacy --yolo behavior and treats --yolo as a legacy spelling that remains as an alias. A mode is chosen with the --safety flag.
  • Command classification: shell commands are labelled safe, destructive or unknown. Read commands such as ls and git status are safe, commands such as rm -rf are destructive, and everything else is unknown.
  • transfer_task and handoffs: transfer_task is always auto-approved, and handoff can only target names in the agent's own handoffs list.
  • Path restrictions: the filesystem tool is unrestricted unless allow_list or deny_list is set. The documentation's example denies .ssh and .aws under the home directory.
  • Sandbox mode: docker agent run --sandbox agent.yaml runs the agent inside a Docker Sandboxes VM. Of the restricted mode the documentation says it is "defense in depth, not a security boundary" and points to sandbox mode for real isolation. The sandbox page adds that the agent process runs inside the VM, the working directory is mounted read-write, the Docker Agent configuration directory is mounted read-only, and Docker Sandboxes must be installed and configured beforehand.
  • Telemetry: the README states that anonymous usage data is collected to improve the tool and refers to a telemetry page.

The Scope of No Code and the Boundaries the Documentation States

"No code required" is the wording of the README. The same documentation set contains several items that help gauge its scope.

  • The script tool: predefined shell commands are exposed as named tools with typed parameters. The commands themselves still have to be written by the user.
  • The Go SDK guide: a separate guide explains how to use Docker Agent as a Go library to embed agents in applications.
  • Standing of the shell tool: the documentation calls the shell one of the most powerful tools and says it lets agents run builds, install dependencies, query APIs and interact with the system.
  • Breadth of configuration: the configuration reference includes hooks, structured_output, cache and code_mode_tools, which indicates how much can be reached through YAML alone.
  • Environment dependency: the installation page lists a provider API key, an account login, Docker Model Runner or a coding harness as the ways to reach a model.
