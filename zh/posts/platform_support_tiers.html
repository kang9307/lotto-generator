「官方支持平台」实际承诺了什么 - 用分级制度读懂支持的边界

能跑起来，和一旦坏掉就阻止发布，是两种不同的承诺

2026年8月31日 开发/基础设施

引言：「我们支持它」这句话里被压平的东西

假设一台新架构的机器刚到手，或者你正在评估要不要把某个新平台放进公司的标准镜像，又或者你在发布说明里读到了「自此正式支持」这一行。接下来该确认的并不是「能不能跑」，而是坏了之后由谁负责修，以及这次损坏会不会挡住一次发布。

这两个答案，各个项目都写在文档里。问题出在没人翻开文档，只读了「官方支持」这四个字。这个说法实际上被用在至少三种不同的分量上。它可能是强到足以挡住发布的承诺，可能是一天之内修好的中等承诺，也可能只是已经跑着一台 buildbot，坏了至少能看见这样的承诺。第三种同样叫「官方支持」。

本文要谈的就是这种分量差异。既不讨论哪种架构更好，也不评价任何厂商。轴线是支持分级这套制度为何存在、每一档的文本究竟承诺了什么，以及这份承诺在哪里终止。

这次定下来的事 - 已确认的范围

先把这条消息切到它真实的尺寸。CPython 把64位 RISC-V Linux 提升为 Tier 3 支持平台。可以确认的范围到这里为止。

  • 对象 — PEP 11 的 Tier 3 名单中已经列出 riscv64-unknown-linux-gnu(glibc, clang/gcc)
  • 负责人 — 同一份名单把 Stan Ulbrych、Emma Smith 两人登记为联络人
  • 机器 — 据公告所述，RISE Project 为 CPython 提供了多台 RISC-V 机器
  • 公告 — Python Insider，2026年8月24日，由 Stan Ulbrych 撰写。文中注明作者的这项工作得到了 Sovereign Tech Agency 奖助的支持
  • 被列为下一步的事 — 通过 RISE 的 runner 把 RISC-V 直接接入 CPython 的 CI、长期争取升到 Tier 2，以及针对该架构的优化

文档所写的到此为止。公告本身在结尾也收窄了范围：CPython 只是 Python 生态的一部分，软件包、编译器、工具链和基础设施都要一起跟上。这一句话正是本文后半部分的主题。

为什么会有分级这回事

分级制度看上去像官僚流程，实际上是对一道算术题的回答。需要支持的组合是乘出来的：指令集 × libc 实现 × 编译器 × 内核版本 × 构建选项。而能修这些问题的人，连加法都增长得很勉强。

PEP 11 给出的背景也落在同一处。它写道，随着时间推移，CPython 的源码里积累了各种平台专有代码，这些代码在某个时点上曾被认为是在特定平台上使用 CPython 所必需的。麻烦在于随之而来的状态：没有人知道那些代码是否仍然需要、是否仍然可用、是否还有人在看。

不做分级，失败会同时朝两个方向发生。

  • 承诺过头 — 写上「我们全都支持」，那些没人修得动的平台的缺陷报告就会堆积，无人回应的 issue 会反过来侵蚀本来可信的部分
  • 承诺不足 — 什么都不写，那么即便一个平台跑得很好，也没有任何依据去论证可以采用它
  • 无从清理 — 没有判断什么可以丢弃的标准，陈旧的平台代码就会一直留着，抬高每一次重构的成本

于是 PEP 11 把支持拆成若干档，每一档带有不同的要求，并由此产生关于支持的不同承诺。这句话的方向很关键。先有要求，承诺是它的结果。 是拿到了多少机器和多少人力决定了承诺的分量，而不是先许下承诺再去找人。

每一档实际承诺了什么

照文本抄下来是这样。值得盯住的是最后两列，响应时限与是否阻止发布决定了一档的实质。

档位要求的验证机制由谁负责响应时限是否阻止发布
Tier 1 CI。CI 失败会阻止发布 全体核心开发者都有责任让 main、进而让这些平台保持可用 会弄坏 main 的改动根本不允许合入，已经坏掉的要立即修复或回退 阻止
Tier 2 必须有可靠的 buildbot 至少两名核心开发者登记负责该平台 弄坏的改动须在24小时内修复或回退 阻止
Tier 3 必须有可靠的 buildbot 至少一名核心开发者登记负责该平台 对失败没有响应时限 不阻止
不支持 无 核心团队不予支持 不适用 不适用

先纠正一点。分级不是四档。 PEP 11 定义的档位是三个，凡是不在上述三份名单里的平台，一律归为核心团队不予支持。不支持并不等于排斥，面向这类平台的代码在只给核心团队带来最小维护负担，并且让远多于贡献者本人的人受益时仍会被接受。但那是接受条件，不是承诺。

验证机制那一列同样不能一眼带过。Tier 1 写的是 CI，Tier 2 和 Tier 3 写的是 buildbot，而这两者运行的时点不同。Tier 1 之所以能写出「会弄坏 main 的改动不允许合入」，正是因为检查发生在合入之前。而 buildbot 是定期构建已经合入的分支并上报结果的装置。所以同样是「自动检查」，前者是门，后者是警报。这次公告之所以把接入 CI 单列为后续工作，原因就在这里。

把表格竖着读，还能看出各档之间的间距并不均匀。Tier 1 与 Tier 2 共享「阻止发布」，差别只在责任范围与时限。而Tier 2 与 Tier 3 之间，承诺的种类本身变了。时限不是从24小时放宽到48小时，而是消失了；阻止发布不是变弱了，而是没有了。真正的分界线在这里。

Tier 3 并不意味着什么

这是本文的正题。「被列为官方支持平台」这句话，通常会被读成下表左栏。规定所定的是右栏。

「官方支持」给人的印象Tier 3 条款实际定下的
发布前必须在这个平台上通过测试该平台上的失败不会阻止发布
坏了很快就会被修对失败没有响应时限
整个核心团队都盯着这个平台有一名以上登记的负责人即满足要求
合入前会在这个架构上跑检查被要求的是 buildbot，这正是公告把接入 CI 列为后续工作的原因
会一并发布该平台的二进制产物分级文档根本不涉及分发产物

误解的根子在一个词上。「支持」被读成了「保证」。 但 Tier 3 要求的是验证装置和联络人，不是结果。这一档真正带来的改变是下面三条。

  • 回归不会悄悄堆积 — buildbot 跑着，坏掉的时点和对应提交就会留下记录，不至于半年后连「从什么时候开始不行的」都说不上来
  • 有了报告的去处 — 名单上有具名负责人，意味着 issue 不会一直漂在无人认领的区域
  • 平台代码离开待清理清单 — 处于不支持状态时，相关代码随时都是移除候选，进了名单，这个理由就不成立了

所以准确的总结是：Tier 3 承诺的是「坏了会被看见」，而不是「它能跑」。 这不是一个小承诺，但它所处的层面，与生产环境的采用决策并不是同一层。

档位会升，也会降

把分级当成代码的属性，下面这件事就理解不了：源码一行不改，档位也可能下降。 因为要求的是人和机器。

  • 降级条件 — 当前档位的要求在相当长一段时间内不再被满足时，由发布经理或指导委员会判断降到下一档
  • 实际的触发点 — 负责人离开项目、buildbot 的机器停摆、结果长期红着。三者都与代码质量没有直接关系
  • 完全退出分级时 — 规定要求记录系统名称、第一个不再支持它的发布版本号，以及第一个真正移除历史支持代码的发布版本
  • 如何告知用户 — 构建被改为在有人尝试于该平台安装时发出警告，configure 也会就该平台不受支持给出提示

升级也是对称的。要从 Tier 3 升到 Tier 2，登记的核心开发者要从一人变成两人，要附上24小时内修复或回退的承诺，buildbot 还得可靠地维持下去。每一条都要花掉某个人的时间，所以升级与其说是技术成熟度的问题，不如说是能否持续投入人力的问题。

明白了这个结构，读这条消息该用的时态也就定了。不是「这个平台现在稳定了」，而是「此刻有人登记在册，也有机器在跑」。前一句谈的是未来，后一句谈的是现在。分级制度所背书的只有后者。

使用方要确认的事 - 语言能跑不等于生态能跑

这里最容易出现落差。解释器的分级文档只覆盖解释器自身的可移植性。PEP 11 的管辖对象是 CPython 本身，分发包与第三方工具都在它的范围之外。公告特意补上「CPython 只是生态的一部分」，也正是因为这个。

真正卡住的不是语言，而是原生扩展。纯 Python 代码几乎不受架构影响，而用 C、C++、Rust 写的扩展模块，编译和分发这两关都得过。按下面这个顺序排查，比较不容易漏。

  • 把整棵依赖树展开 — 不只是直接依赖，还要包括传递依赖。问题通常藏在往下两层
  • 把原生扩展挑出来 — 分发产物的文件名是纯 Python 还是带平台标记，可以先做一轮粗分
  • 逐个确认有没有该平台的预构建产物 — 没有的话，安装就会退化成从源码构建
  • 确认源码构建是否成立 — 编译器版本、头文件，以及像数值计算库这类需要按架构提供实现的系统依赖
  • 看运行时的代码路径 — 加密、压缩、序列化这类库常常另设按架构优化的路径。没有这条路径时程序照样能跑，但性能特征会变
  • 看能否拿到 CI runner — 拿不到就只能靠模拟运行，构建时间会翻好几倍。这是研发效率成本，所以它是悄悄累积的
  • 看容器基础镜像与运维工具 — 基础镜像、探针、性能剖析工具是否也为该架构发布，看到这一层部署链路才算闭合

归纳起来，判断顺序是这样的：语言的支持分级是必要条件，而不是起点。 它排在前面，只是因为语言跑不起来的话后面都不用看了。反过来并不成立——语言能跑，并不会把下面那四层一起带过来。

预先做好的，和从源码构建的

新架构上最疼的就是这一段。先看规格这边，瓶颈其实已经不如从前。

  • 旧办法的 Linux 分发标签把架构逐一列在文档里。官方规格文档为 manylinux2014 给出的清单是 x86_64、i686、aarch64、armv7l、ppc64、ppc64le、s390x，riscv64 不在其中
  • PEP 600 改掉了这个结构。标签形如 manylinux_${GLIBCMAJOR}_${GLIBCMINOR}_${ARCH}，其中 ${ARCH} 直接采用 Python 自己报告的平台值
  • 结果是为了一个新架构不必再写一份新的 PEP。PEP 600 本身就把这一点写成设计目标：在旧办法下每加一个架构，都要写一份新 PEP、改动 PyPI 与 pip 的代码使其识别新标签，再等待新版 pip 扩散到用户手里，是一套相当繁琐的流程

也就是说，规格这一侧已经打开了。剩下的瓶颈不在文档，而在由谁去构建并上传这些产物。那需要每个包的维护者在自己的 CI 上挂一个该架构的 runner，问题于是又回到机器和人。和分级制度撞上的是同一堵墙。

当没有产物、安装退化为源码构建时，实际会变化的是这些。

  • 安装耗时的量级变了 — 原本以秒计的会变成以分钟甚至小时计。在频繁重建容器的流水线里，这份成本每次都要付
  • 构建工具进入镜像 — 编译器和头文件如果留在最终镜像里，体积和需要持续复查的面会一起变大
  • 失败点变多 — 头文件缺失、编译器版本不匹配、编译过程中内存不足，都是直接取用预构建产物时根本不存在的失败类型
  • 可复现性变弱 — 预构建产物由哈希固定，而源码构建的结果取决于构建环境。同一份锁文件在两台机器上可能产出不同的二进制
  • 内网隔离环境尤其难受 — 内部镜像源里只有源码而没有产物时，连构建依赖也得全部镜像一遍

别的项目切法不一样

面对同一个问题，其他语言项目也设了分级，但它们选的分级轴各不相同。与其看成排名，不如读作各自最常被问到什么的差别，这样更准确。只取公开文档能确认的三个并排放一下。

项目最高档承诺什么中间档最低档分级所依据的轴
CPython CI 失败会阻止发布，全体核心开发者对保持这些平台可用负责 buildbot + 两名负责人 + 24小时内修复。失败会阻止发布 buildbot + 一名负责人。没有时限，也不阻止发布 响应时限与是否阻止发布
Rust 可以视为保证可用的一档。项目为其构建官方二进制版本，并由自动化测试确保每次改动后都能构建并通过测试 保证可构建。发布标准库的官方二进制并跑自动构建，但自动测试并不总是运行，因此并不保证产出可用的构建 代码库里有对它的支持，但项目不会自动构建或测试，所以可能能用也可能不能用。不提供官方构建 自动化做到构建还是做到测试
Go 坏掉的构建会阻止发布。所有贡献者实际上都负有责任(弄坏了就自己修，或者找得到能修的人)，并要求构建机器由 Go 团队自己拥有 其余移植目标上，弄坏它的改动未必会被回退。若某个移植在 1.N 里一直是坏的，核心团队可以选择在 1.N+1 中移除它 是否阻止发布与构建机器的归属

把三份文档叠在一起，措辞虽异，却有三处收敛到同一个地方。

  • 机器是前提。 三者都要求自动验证装置，Go 更是把构建机器的归属直接写进要求里
  • 必须有具名的人。 Go 要求新移植目标须指定并征得两名开发者同意来维护，另加一名维护构建机；CPython 则按档位规定负责的核心开发者人数
  • 最低一档不承诺能用。 只是说法不同，「可能能用也可能不能用」是共同的文本

这条消息该怎么读

夸大和贬低，都是在往远离原文的方向走。先说夸大式误读，就是把它换算成「现在可以上生产了」。Tier 3 的条款里没有这层意思。没有响应时限、不阻止发布，这两句话已经把它的分量说清楚了。

反过来的贬低式误读是「档位这么低，没什么意义」。这同样不对。不在名单上和在名单上之间是有实质差别的，差别就是上面那三条：buildbot、负责人、离开待清理清单。处在不支持状态时，连回归是什么时候出现的都无从判断。

把会变的和不会变的分开列，是这样。

  • 会变的 — 回归被发现的时点提前、issue 有了接收方、平台代码退出移除候选，以及多出一个可供别的项目引用的先例
  • 不会变的 — 发布关卡、响应时限、分发产物的可得性、容器与工具链，还有性能。针对架构的优化，公告自己就把它列为后续工作
  • 时态要守住 — 分级描述的是当前已确保的人力与机器状态，不是对未来的承诺

还有一点。这类消息通常是过程中的一个中间点，而不是一项决定。名字出现在分级名单上，是在有人张罗到机器、接上构建、把失败一个个修掉之后才发生的事，顺序不会反过来。所以把「什么时候能用」换成「现在确保了什么、还剩下什么」，判断会轻松很多。这一次确保下来的是机器、负责人和名单收录，公告自己列出的剩余项则是接入 CI、更高的档位和优化。剩余项被写进文档这件事本身，就是一个值得信任的信号，比一份声称万事俱备的公告要好。

如果只留一条能用于实务的判据，那就是这条。今后再读到「官方支持」这一行，就打开那个项目的分级文档，只找两句话：失败会不会阻止发布，以及有没有响应时限。这份支持的真实分量，多半就全在这两句里，其余的说明都是它们的脚注。

未能确认的部分

没有写进正文的东西集中放在这里。用推测去填空白是最糟的做法。

  • 指导委员会的批准日期与名单更新日期 - 多份摘要里流传着8月20日和22日，但我没能打开一份写有这些日期的一手文档，因此没有写进正文。文中的日期是公告的发布日
  • buildbot 的台数、配置与在线率 - 没有找到可以确定有多少台、以何种配置、运行得如何的资料
  • 该架构的软件包产物实际覆盖率 - 各个包情况不同，也没有找到覆盖整个索引的公开统计，因此没有给出数字
  • 升到 Tier 2 的时间点 - 公告只把它写成目标，并未给出满足要求的计划或时间表
  • 性能 - 本文没有写任何跨架构的比较数字。我未能确认在同等条件下测得的公开数据，而未经确认的性能对比与编造无异

结论：压缩成三句话

第一，分级记录的是人的承诺，不是代码的状态。 既然要求是 buildbot 和具名负责人，那么源码原封不动、人一走，档位照样下降。第二，Tier 3 定下的是「坏了会被看见」，不是「它能跑」。 没有响应时限、不阻止发布这两句文本，把边界画得很准。第三，使用方的判断从依赖开始，而不是从语言开始。 解释器能跑和自己的技术栈能跑是两个问题，而分级文档只管前一个。

如果只做一件事，我建议做这件：打开你现在正在运维的服务的依赖清单，只把带原生扩展的包挑出来数一数。那个数字就是迁到新架构时真正需要逐项核对的条目数，而语言的支持分级，不过是这份清单最上面的一行罢了。
