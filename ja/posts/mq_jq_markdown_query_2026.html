mq - jqスタイルのMarkdownクエリ言語 2026

jqがJSONに行ったことを、今度はMarkdownに

2026-06-10 IT・技術

はじめに：Markdownは溢れているのに、扱う道具は貧弱だ

開発者の一日を思い浮かべると、Markdownはほぼあらゆる場所にあります。README、Wiki、Issue、設計文書、ブログの下書き、そして2026年現在はLLMのプロンプトと応答まで。テキストで書かれた構造化文書の事実上の標準になりました。ところがいざこのMarkdownを「プログラムのように」扱おうとすると、道具が貧弱です。grepで見出しを探そうとするとコードブロック内の#コメントまで引っかかり、sedでリンクを書き換えようとすると表の中のパイプ記号と衝突します。Markdownは人が読みやすい形式ですが、機械が構造的に扱うには意外と厄介です。

この空白をまさに狙ったツールが、GeekNewsでも話題になったmqです。mqは一言でいえば「Markdownのためのjq」です。JSONを扱う標準ツールjqの哲学、つまりドット記法で要素を選び、パイプで変換をつなぎ、フィルタを合成するという考え方を、そのままMarkdownに持ち込みました。本記事ではjqとは何かを軽く復習したうえで、mqがどんな問題を解き、どんな仕組みで動き、実戦でどう使うのか、そしてpandoc・remark・mdqといった近隣のツールと何が違うのかを丁寧に整理します。

1. まずjqの復習 - JSONのためのクエリツール

mqを理解するには、その原型であるjqから押さえる必要があります。jqはコマンドラインでJSONを扱う軽量プロセッサで、よく「JSONのためのsed/awk」あるいは「JSON用のSQL」と呼ばれます。核となる概念はフィルタです。jqプログラムは入力を受け取り出力を出すフィルタであり、最も単純なフィルタ.は入力をそのまま通す恒等演算子です。

jqの強力さは、小さなフィルタをパイプ（|）でつなぐところから生まれます。シェルのパイプと同じく、前のフィルタの出力が次のフィルタの入力になります。

# オブジェクトからnameフィールドだけ抽出
echo '{"name":"Ada","age":36}' | jq '.name'
# => "Ada"

# 配列を走査しageが30超の項目だけ選択
echo '[{"n":"A","age":36},{"n":"B","age":20}]' \
  | jq '.[] | select(.age > 30)'
# => {"n":"A","age":36}

覚えておくべき点は三つです。第一に、ドット記法（.name）で構造を掘り下げる。第二に、パイプで段階をつなぐ。第三に、select()のような関数で絞り込む。他の言語ならループと条件分岐で書くことを、jqではフィルタを糊のようにつないで解決します。まさにこの発想がmqにほぼそのまま移植されています。

2. ところがMarkdownはJSONではない - 問題の本質

jqがこれほど快適な理由は、JSONが最初から機械が解析しやすい構造を持っているからです。キーと値、オブジェクトと配列が明確に入れ子になっており、ドット記法でどこでも正確に指せます。

Markdownは違います。Markdownは人が読み書きしやすいように設計された平文テキストです。見た目は単純ですが、その中には見出し・段落・リスト・引用・表・リンク・コードブロックという暗黙の構造が隠れています。問題は、この構造がテキストの行単位ではうまく現れない点です。

  • grepの限界： grep '^#'で見出しを探すと、コードブロック内のシェルコメント#まで一緒に引っかかります。grepはテキスト行しか見ず、その行がコードブロック内部かどうかを知りません。
  • sedの限界： リンクを一括置換しようとしても、正規表現だけでは入れ子の括弧や表の中のパイプ（|）と衝突しがちです。
  • 構造への無知： 結局grep・sed・awkはMarkdownの構造に対して「目が見えない」のです。彼らにとって文書はただの行の羅列にすぎません。

反対の端にはpandocがあります。pandocは文書をまるごと別フォーマットに変換する強力なツールですが、「この文書からh2見出しだけ、あるいはRustコードブロックだけ取り出して」といった外科的な抽出には大げさすぎます。この「行単位のツール」と「全体変換ツール」の間の空白こそ、mqが狙う場所です。

3. mqとは何か - Markdownのためのjq

公式の紹介によれば、mqはjqに似た構文でMarkdownを処理するコマンドラインツールで、Rustで書かれています。データを切り出し、フィルタし、マップし、変換する作業をMarkdownに対して行います。jqがJSONのオブジェクトや配列を扱ったのに対し、mqは見出し・段落・コードブロックといった文書ノードを扱います。

mqの正体を一文で要約するとこうなります。

grepとsedはMarkdownの構造に目が見えず、pandocは文書をまるごと変換する。mqはその間で、Markdown内の要素を外科的にクエリし変形する。

紹介資料で強調されるmqの主な用途は次のとおりです。

  • LLMワークフロー： LLMのプロンプトと出力に使われるMarkdownを効率的に加工・整理します。2026年に最も注目される用途です。
  • ドキュメント管理： 複数の文書ファイルにまたがってコンテンツを抽出・変換・整理します。
  • コンテンツ分析： 特定のセクションやパターンをMarkdown文書から素早く取り出します。
  • バッチ処理： 複数のMarkdownファイルに一貫した変換を適用します。

ツール支援も豊富に紹介されています。対話的な実験のためのREPL、VSCode拡張とLSP（Language Server Protocol）のサポート、そしてクエリを段階的に覗き込むデバッガまで備えているとされます。~/.local/bin/にmq-で始まる実行ファイルを置けば、カスタムサブコマンドとして拡張することもできます。

4. 動作原理 - MarkdownをASTとして見る

mqがgrepと根本的に異なる点はここにあります。mqはMarkdownを行の羅列ではなく、構造化されたツリー、すなわちAST（Abstract Syntax Tree、抽象構文木）として解析します。

たとえば次のような短いMarkdownがあるとします。

# インストール

次のコマンドでインストールします。

```bash
cargo install mq-run
```

## 使い方

詳細は[ドキュメント](https://mqlang.org/)を参照してください。

人の目にはただのテキストですが、mqはこれを次の構造として理解します。

Document
├─ Heading(level=1)  "インストール"
├─ Paragraph         "次のコマンドでインストールします。"
├─ CodeBlock(lang=bash)  "cargo install mq-run"
├─ Heading(level=2)  "使い方"
└─ Paragraph
   └─ Link(url="https://mqlang.org/")  "ドキュメント"

こうして構造が明示的に現れると、「見出しだけ」「レベル2の見出しだけ」「bashコードブロックだけ」「すべてのリンクだけ」といった選択が正確になります。コードブロック内の#はもう見出しと誤認されません。mqがjqのように動ける秘密は、この「AST上でのクエリ」にあります。jqの入力がJSONツリーだったように、mqの入力はMarkdown ASTというわけです。

5. 基本セレクタ - 見出し、コードブロック、リンク

では実際の構文を見ましょう。mqのセレクタはjqのドット記法に似ていますが、対象はMarkdown要素です。以下の例は公式ドキュメントと紹介資料で示されたパターンを整理したものです。

5.1 見出し抽出（.h）

# すべての見出しを抽出
mq '.h' README.md

# h1見出しだけ
mq '.h(1)' README.md

# h1とh2の見出しだけ
mq '.h(1, 2)' README.md

# レベル1～3の見出し（範囲）
mq '.h(1..3)' README.md

5.2 コードブロック抽出（.code）

# すべてのコードブロック
mq '.code' example.md

# rustコードブロックだけ
mq '.code("rust")' example.md

# javascriptコードブロックだけ
mq '.code("javascript")' example.md

ここにjqで見たselect()とcontains()を組み合わせると、条件フィルタリングになります。

# "install"を含む見出しだけ
mq '.h | select(contains("install"))' README.md

# "name"を含むコードブロックだけ
mq '.code | select(contains("name"))' example.md

ドット記法、パイプ、select。jqを使ったことがある人なら即座に親しみを感じる構造です。他言語のループの代わりにフィルタをつなぐjqの発想がそのまま生きています。

6. 変換と合成 - テキストに展開する

mqは抽出にとどまらず変換も行います。抽出したノードを平文テキストに展開したり、大文字小文字を変えたり、リンクで包んだりします。

# すべての見出しをテキストに変換
mq '.h | to_text()' README.md

# コードブロックをテキストに変換
mq '.code | to_text()' example.md

# パイプラインでツールを連結（抽出後に小文字化）
cat README.md | mq '.h' | mq 'downcase()'

jqと同じく、mqの本当の力は小さな部品をつなぐ合成にあります。シェルのパイプとmq内部のパイプを併用すれば、「見出しだけ抜き出して→小文字に→次のツールへ渡す」といった流れが一行で完成します。

7. 実戦での活用例

では、これで何ができるのでしょうか。抽象的な構文より具体的なシナリオの方が、ツールの価値をよく示します。

7.1 目次（TOC）の自動生成

文書のh1・h2見出しだけを集め、アンカーリンク付きの目次を作れます。公式の紹介でも、見出しを集めてto_link()でリンク化する目次生成の例が示されています。長いREADMEやWiki文書を自動で整える際に便利です。

7.2 READMEからコード例だけ抜き出して検証

mq '.code("bash")'でREADMEのシェル例だけ抽出し、実際に動くかをCIで回せます。文書に書かれたコマンドが現実とずれる「ドキュメントの腐敗（rot）」を防ぐ良い仕掛けです。

7.3 LLMプロンプト・応答の整理

LLMが長く吐き出したMarkdown応答から見出し構造とリンクだけ抜き出して要約コンテキストとして使ったり、不要なコードブロックをフィルタしてトークンを節約したりできます。ヘッダーとリンクを抽出してLLM入力を軽くする活用は、紹介資料でも主要な用途として挙げられています。

7.4 文書の一括変換・検証

数十のMarkdownファイルに同じクエリを適用して、壊れたリンクを見つけたり特定セクションの有無を検査したりするドキュメントリンティングのパイプラインを作れます。grepでは構造が分からず難しかった作業です。

8. CLI使用例を一目で

これまでのパターンを実戦コマンドにまとめてみます。

# インストール（公式案内に基づく）
cargo install mq-run

# 1) 文書のすべてのh2見出しをテキストで
mq '.h(2) | to_text()' docs/guide.md

# 2) pythonコードブロックだけ抽出
mq '.code("python")' docs/guide.md

# 3) "deprecated"を含む段落を探す
mq 'select(contains("deprecated"))' CHANGELOG.md

# 4) パイプライン：見出し抽出 → 小文字化
cat README.md | mq '.h' | mq 'downcase()'

パターンが見えますか。選択 → フィルタ → 変換というjqの3段構造が、Markdownの上でそのまま繰り返されます。一度覚えれば新しいクエリを書くコストが非常に低くなります。圧縮やシステムツールをRustで実装する流れに興味があれば、RustによるZstandardの実装の記事も合わせて参考になります。

9. PythonバインディングとMCP

mqはCLIだけのツールではありません。PyPIにmarkdown-queryというパッケージとしてPythonバインディングが提供されており、Pythonスクリプトの中から同じ構文でMarkdownをクエリできると紹介されています。データパイプラインや文書処理の自動化をPythonで書くチームに便利です。

2026年の文脈で特に興味深いのはMCP（Model Context Protocol）連携です。紹介資料によれば、mqをMCPサーバとして公開し、AIアプリケーションがMarkdownを構造的に加工できるようにつなげられます。LLMが長い文書をまるごと飲み込む代わりに、mqで必要な部分だけ精密に切り出して渡す方式です。AIツールエコシステムのより広い流れは、2026年に開発者が実際に使うツールで整理しています。

10. 類似ツール比較 - mq vs mdq vs pandoc vs remark

Markdownを扱うツールはmqだけではありません。それぞれ狙う場所が違います。紹介・比較資料をもとに整理すると次のとおりです。

ツール 性格 得意なこと 限界/特徴
mq jqスタイルのクエリCLI（Rust） 要素の抽出・変換、REPL・LSP・デバッガ、MCP・Pythonバインディング 機能が豊富な分、覚える表現が多い
mdq jqスタイルのクエリCLI（Rust） 文書から特定要素をシンプルに集中して選択 mqより軽量でシンプルな選択ツールとして紹介
pandoc 汎用ドキュメント変換器 フォーマット間のまるごと変換（MD↔HTML↔PDFなど） 外科的な要素抽出には大げさ
remark JSのMarkdown処理フレームワーク プラグインベースの変換・リンティング、ビルド統合 CLIの一行クエリよりプログラミング志向

要約すると、mqとmdqは同系列のjqスタイルクエリツールです。mqはツール支援（REPL・LSP・デバッガ）と統合（MCP・Python）が豊富な側、mdqはよりシンプルで集中的な選択ツールとして紹介されています。pandocは「変換」、remarkは「JSエコシステムのフレームワーク」という点で趣が異なります。つまりmqを使うかどうかは、「文書を変換するのか、文書の中から選び出すのか」で分かれます。

11. mqを導入する際の検討点

良いツールも文脈に合ってこそ輝きます。mqを導入する前に現実的に考えておくべき点です。

  • 学習コスト： jqの経験があれば入りは速いですが、jq自体に不慣れなら、ドット記法・パイプ・フィルタ合成という発想からまず身につける必要があります。
  • インストール依存： Rustベースなのでcargo installが最も手軽な経路として案内されます。バイナリ配布の有無は使うプラットフォーム次第で確認が必要です。
  • 成熟度： 活発に開発中の比較的新しいツールなので、一部の表現や機能はバージョンによって変わる可能性があります。未確認の挙動は公式ドキュメントで確認するのが安全です。
  • 適した作業： 一度きりの抽出には大げさかもしれません。反復的な文書自動化・検証・LLM前処理のように「同じクエリを何度も」回す場面で価値が大きくなります。

12. 開発者とドキュメント作業者にとっての意味

mqの登場は単なる「便利なCLIが一つ増えた」を超える意味があります。それはMarkdownをデータとして扱う発想の広がりです。これまでMarkdownは「人が読む文書」であって、「機械が問い合わせるデータ」ではありませんでした。jqがJSONを一級のデータにしたように、mqはMarkdownをクエリ可能な構造へと引き上げます。

この変化は二つの層に特に響きます。開発者にとっては文書がコードパイプラインの一部になります。READMEのコード例をテストし、変更ログを検証し、ドキュメントリンティングをCIに入れることが自然になります。ドキュメント作業者にとっては、数十の文書を手で直していた反復労働が一行のクエリに縮みます。

そして2026年の決定的な文脈は、やはりLLMです。AIがMarkdownを大量に生産・消費する時代に、そのMarkdownを精密に切り分けフィルタするツールの需要は大きくならざるをえません。mqがLLMワークフローとMCPを前面に押し出すのは偶然ではありません。MarkdownがAIと人間の共通語になるほど、その共通語を扱う「jqのようなツール」の居場所はより明確になります。

13. 結論 + 今すぐ試せる3つ

mqは「jqのMarkdown版」という一行で十分に要約できますが、その一行が指すものはかなり広いです。grep・sedが構造に目が見えず、pandocが大げさなその空白で、mqはMarkdownをASTとして解析し外科的にクエリ・変換します。jqを使ったことがある人なら、ドット記法・パイプ・フィルタという馴染みの構文ですぐに出発できます。

今すぐ試せる3つで締めくくります。

  1. 一番長いREADMEで見出しから抜いてみよう。 mq '.h' README.mdの一行で文書の骨格が一目で見えます。効果を最も速く体感できる出発点です。
  2. コードブロックを抽出して検証パイプラインに入れよう。 mq '.code("bash")'で文書中のコマンドを抜き出しCIで回せば、文書と現実のずれを自動で捉えます。
  3. LLM前処理に挟んでみよう。 長いMarkdown応答から必要な要素だけmqで切り出して渡せば、トークンを節約しコンテキストを綺麗に保てます。

ツールが常に語る真実は同じです。人が反復していた構造的作業を機械に渡すほど、私たちはより本質的な判断に集中できます。mqはMarkdownという馴染みのテキストを、まさにその対象へと引き上げた、小さくも賢いツールです。
