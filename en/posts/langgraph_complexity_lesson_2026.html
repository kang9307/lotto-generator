Why LangGraph Made Our Code More Complex - Lessons From a Framework Failure

What state graphs promise versus what they actually cost - when to adopt an agent framework, and when to build it yourself

Jul 21, 2026 Dev & Infra

Intro: We Adopted a Framework - So Why Did Things Get More Complicated?

As of 2026, if you say you're building an AI agent, nine times out of ten the first thing evaluated is an orchestration framework like LangGraph, CrewAI, or AutoGen. The expectation that "this time, state management and control flow will finally be clean" sounds reasonable enough - the framework has already built conditional branching, checkpointers, and human-in-the-loop interrupts, so surely you just need to bolt your business logic on top.

But a retrospective recently shared on GeekNews (news.hada.io) tells the opposite story. The author built a workflow engine on a NestJS/TypeScript backend using LangGraph, and recalls ending up with 8,692 lines of code spread across three executor layers - even though the core logic, the actual LLM calls and prompt assembly, came to fewer than 100 lines.

This post uses that retrospective as a starting point, but it isn't a summary of the original. It works through, in my own terms, the gap between what agent frameworks like LangGraph and LangChain promise and what they actually charge, my own analysis of why that gap opens up, and a more general set of principles for deciding when to adopt a framework and when to build it yourself.

1. What Agent Frameworks Promise

1.1 State Graphs and Orchestration

LangGraph's core pitch is straightforward. Represent an agent's flow as a state graph of nodes and edges, and control flow - conditional branching, loops, parallel execution - can be declared as graph structure instead of scattered across code. On top of that, a checkpointer persists session state so a conversation can resume after an interruption, and human-in-the-loop interrupts pause execution at specific points to wait for a person's approval. The promise is that the framework will take responsibility for exactly the parts that are easy to get wrong when hand-rolled.

1.2 Reuse and Ecosystem

On top of that, there's the appeal of a standardized tool-calling convention, a single interface across multiple LLM providers, and access to patterns the community has already battle-tested - RAG pipelines, multi-agent routing, and the like. The promise that you don't have to build everything from scratch is hard to turn down, especially with a small team or a tight deadline.

2. What Actually Happened - 8,692 Lines of Spaghetti

2.1 A Graph That Wasn't Really a Graph

The trouble started after adoption. The author recalls the actual graph had "just one node" - a single edge from current_step to END, with no conditional branches, no forks, no parallel execution. The three things LangGraph was supposed to own - conditional edges, checkpointing, and human-in-the-loop - were all already implemented outside the graph, in the service layer. The router inside the graph, the author notes, was simply repeating a decision the service layer had already made.

2.2 Double Checkpointing, State Scattered Across Five Places

The more serious problem was state management. The same session state was managed separately in both LangGraph's in-memory checkpointer (MemorySaver) and a custom-built PostgreSQL checkpointer service. Add the in-memory caches on top of that, and state was effectively scattered across five places - with no one able to say for certain which one was authoritative, according to the author's account.

2.3 The Same Logic, Reimplemented Three Times Over

Every time a feature was added, three separate executors reimplemented the same logic - prompt assembly, confirmation-menu handling, marker extraction - each in its own slightly different way. The result was 4,094 + 2,602 + 1,595 lines, for a total of 8,692. Core logic sat around 100 lines; boilerplate made up more than 90% of the codebase.

3. The Root Cause - Local Optimizations Piled Up Without Understanding the Framework's Boundaries

3.1 Knowing the API Is Not the Same as Understanding the Design

The root cause the author identifies isn't a single technical mistake. It's the diagnosis that knowing a framework's API and understanding what that framework is designed to be responsible for are two entirely different things. The team was "using" LangGraph, but no one noticed that the service layer had quietly taken over the conditional branching and checkpointing the graph was supposed to own - and features kept piling up on top of that blind spot.

3.2 AI-Assisted Coding and the Trap of Local Optimization

What stands out to me in particular is that the author also frames this as a consequence of AI-assisted ("vibe") coding. AI is strong at local optimization - implementing one feature at a time - but weak at global optimization, i.e., checking whether that feature still respects the overall architecture's boundaries of responsibility. Neither the double checkpointing nor the triple duplication was designed up front; both accumulated from local optimizations made at every feature addition. I'd read this as a warning that applies well beyond LangGraph, to any framework adoption where AI is used to bolt on features quickly.

4. The Framework-vs-Library Debate - LangChain Fatigue and Minimalism

4.1 Why the Fatigue Built Up

This case isn't an isolated failure story. Fatigue with LangChain-family frameworks has been building in the developer community for a few years now. Common complaints include excessive abstraction layers, frequent API churn, control flow hidden behind callback systems and memory wrappers, and wrapper overhead that can add up to a full second or more per request. There's also a fair critique that one of LangChain's original selling points - unifying multiple LLM providers behind a single API - has been substantially diluted now that each provider has standardized its own API.

4.2 The Swing Back Toward Minimalism

One document frequently cited in this context is Anthropic's official guide, "Building Effective Agents." Its core point is that frameworks simplify low-level tasks like calling LLMs, defining and parsing tools, and chaining calls together - but the added abstraction layers can obscure the underlying prompts and responses, making debugging harder. Anthropic's recommendation is to start by using LLM APIs directly, since most patterns can be implemented in just a few lines of code. In the same vein, minimalist libraries like SmolAgents (roughly 1,000 lines) and PocketFlow (roughly 100 lines), or even a basic agent loop that just repeats calling the LLM and executing a tool (about 60 lines of Python), are proving sufficient for a growing number of cases.

5. The Cost of the Wrong Abstraction

5.1 More Expensive Than Duplication

In 2016, software engineer Sandi Metz laid out the principle that "duplication is far cheaper than the wrong abstraction." A wrong abstraction doesn't reveal itself all at once. When a new requirement "almost" fits an existing abstraction, a developer adds a parameter, slips in a conditional, and forces it to fit. Repeat that patching enough times, and the abstraction becomes progressively harder to understand while the cost of eventually undoing it snowballs.

5.2 Mapping It Onto the LangGraph Case

As I read it, the real debt in this case wasn't the fact that "LangGraph was adopted" - it was the layering of a wrong abstraction that formally repeated, inside the graph, a decision the service layer had already made. The graph wasn't functionally doing anything, yet its form - nodes, edges, state schema - still had to be maintained, and the cost of maintaining that form ended up exceeding the cost of the actual logic. It reads as a textbook example of a wrong abstraction quietly accumulating until it arrives as one large bill.

6. When to Use a Framework, and When Not To - General Principles

The most useful question to pull out of this failure story isn't "is LangGraph bad," but "when is the cost of a framework like this actually justified." I'd suggest judging it against four criteria.

CriterionSignal favoring a frameworkSignal favoring rolling your own
Problem scaleConditional branching, loops, parallel execution genuinely existFlow is effectively linear with one node
TeamMultiple people repeatedly implementing the same patternOne or two people covering a narrow scope
LifespanA product to be maintained long-termA one-off script or proof of concept
Complexity vs. costState, interrupts, and persistence are real requirementsRequirements are smaller than the framework's learning curve

6.1 When a Framework Is the Right Call

There are, on the other hand, clear cases where a framework genuinely lightens the load: multi-step agents with real state, flows where conditional branching and loops actually exist, cases where human-in-the-loop interrupts are a real requirement, and sessions that need to persist beyond a process restart. This overlaps closely with the supervision-point design covered two days ago in The Human in the Loop Is Tired, and the multi-agent isolation problem covered yesterday in What Happens When You Unleash Multiple AI Agents on One Repo. If agents genuinely need to exchange state with each other and a human needs to step in at specific points, a framework's checkpointing and interrupt features are considerably safer than rolling your own.

6.2 When a Library or Direct Implementation Is the Right Call

Conversely, if - as in this case - the flow effectively has one node, there's no real branching, and changing a single prompt requires touching type definitions, node signatures, and graph topology all at once, you're solving the framework's problem instead of your own. In that situation, a handful of thin functions that call the LLM API directly are usually enough.

7. Practical Lessons - Start Small, Expand When You Actually Need To

Four practical lessons come out of this failure story.

  • Start small. Validate the requirements with a direct API-call loop first, and watch for the moment when state, branching, or interrupts genuinely become necessary.
  • Adopt when you actually need it. Bring in a framework after conditional branching, loops, or persistent sessions have actually shown up in your code. Adopt first and fill in later, and you risk ending up like this case - a graph that's a shell of form with nothing real inside it.
  • Keep an exit ramp. Design so that core logic - prompt assembly, tool calls, validation - can be tested independently even if you strip the framework layer away.
  • Own the core logic. Understand exactly what the framework does for you - and what it doesn't - and enforce that boundary yourself. Even when AI helps you bolt on features quickly, verifying that boundary is still, in the end, a human's job.

Conclusion: Not the Framework's Fault - a Question of Fit

Summarizing this retrospective as "LangGraph is bad" misses the point. The author, after all, ended up solving the problem on top of LangGraph - by removing an unnecessary router, lightening the state, and splitting a giant node into role-specific ones. The problem was never the framework itself; it was adopting a framework mismatched to the problem's actual scale without checking for fit, and then piling features on top without understanding where its responsibilities were supposed to end. As of July 2026, the agent framework ecosystem is still evolving fast, and tools like LangGraph, CrewAI, and AutoGen genuinely earn their keep on stateful, multi-agent problems. But that value only comes back when they're used to match the actual scale of the problem, and as intended by their design - not simply because they were adopted. That is the most honest lesson this failure story has to offer.
