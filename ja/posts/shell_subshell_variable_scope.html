はじめに: ループは正しく回り、答えだけが違った

ログファイルを走査して条件に合う行を数えるスクリプトを書いたとしよう。ループの中に echo を一つ入れてみると、3行がきちんと出力される。ところがループが終わって合計を出すと0だ。

この時点でたいていはループ本体を疑う。算術展開が間違っているのか、read が空行を食べたのか、変数名にタイプミスがあるのか。どれも違う。ループは正確に回り、カウンタも3まで上がっていた。ただそのカウンタが住んでいたプロセスがループと一緒に消えただけだ。

この記事はそのプロセスがいつ生まれ、なぜ値を返せないのか、そして直し方がループ本体ではなく入力の与え方にある理由を、実行結果でたどる。以下に載せたコマンドと出力は GNU bash, version 5.2.37(1)-release と dash でそのまま走らせて得たものだ。シェルの基礎がまだなら シェルスクリプト基礎とシェルスクリプト上級を先に見ておくと読みやすい。

1. カウンタが0に戻ったその瞬間、何が起きていたのか

まず再現から。3行のファイル一つで足りる。

$ printf 'a\nb\nc\n' > /tmp/f.txt

$ n=0
$ cat /tmp/f.txt | while read -r l; do n=$((n+1)); done
$ echo "after pipe: n=$n"
after pipe: n=0

今度は入力の与え方だけを変える。ループ本体は一文字も触らない。

$ n=0
$ while read -r l; do n=$((n+1)); done < /tmp/f.txt
$ echo "after redirect: n=$n"
after redirect: n=3

同じループ、同じファイル、同じシェルだ。違うのは | があるかどうかだけ。ここですでに結論が出ている。原因はループにない。

1.1 パイプはデータだけを運ぶのではない

パイプを「コマンドAの出力をコマンドBの入力に入れる装置」としてだけ理解していると、この現象は説明できない。パイプはそれと同時にプロセスをもう一つ作る。bash はパイプラインの各構成要素を別々のサブシェルで実行する。

サブシェルは親シェルを複製して作られる。だから開始時点では親の変数値をすべてそのまま持っている。問題はその逆方向だ。

  • 親の値は子にコピーされる。だからループの中で $n を読むと0がちゃんと見える
  • 子が変えた値は親に戻らない。プロセス間にそんな通路はない
  • パイプラインが終わると子プロセスは終了する。その中で3まで上がった n はその瞬間に消える
  • 親シェルには最初に作った n=0 が手つかずのまま残っている。だから0が出力される
  • つまり「値が上がらなかった」のではなく「上がった値が見えない場所から見ている」のだ

この現象を検索するときの言葉。これは変数スコープの問題ではなくプロセス境界の問題だ。local や export で解決しようとする試みがすべて失敗する理由がここにある。export は親から子へ値を下ろす装置であって、子から親へ上げる装置ではない。

2. プロセスがいくつ生まれたかを目で数える方法

推測せずに数えればいい。bash にはまさにこの用途の変数が二つある。

  • $$ — 元のシェルの PID だ。サブシェルの中でも変わらない。だからサブシェル判別には使えない
  • $BASHPID — いまこのコードを実行中のプロセスの実際の PID だ。サブシェルに入ると値が変わる

二つを並べて出力すると、サブシェルがどこで生まれたかがそのまま見える。

$ echo "parent: \$\$=$$ BASHPID=$BASHPID"
parent: $$=1344 BASHPID=1344

$ ( echo "subshell( ): \$\$=$$ BASHPID=$BASHPID" )
subshell( ): $$=1344 BASHPID=1348

$ echo "cmdsub: $(echo "\$\$=$$ BASHPID=$BASHPID")"
cmdsub: $$=1344 BASHPID=1349

$$ は3回とも1344で固定、BASHPID だけが1344、1348、1349に分かれる。括弧とコマンド置換がそれぞれ新しいプロセスを作った証拠だ。スクリプトをデバッグしていて「ここはサブシェルか」が気になったら echo $BASHPID の一行で済む。

PID の値そのものは実行のたびに変わる。見るべきは数字ではなく三つの値が互いに違うかだ。

3. リダイレクト - 最も安く最も移植性の高い解決

入力が実際のファイルなら答えは一つだ。パイプをなくして done の後ろにリダイレクトを付ける。

# 値が消えるほう
cat /tmp/f.txt | while read -r l; do n=$((n+1)); done

# 値が残るほう
while read -r l; do n=$((n+1)); done < /tmp/f.txt

この形が良い理由を整理するとこうなる。

  • ループが現在のシェルで動く。サブシェルがそもそも作られないので変数がそのまま残る
  • プロセスを一つ減らせる。cat プロセスも消える
  • bash 拡張ではなく POSIX 構文だ。dash でも同じく3が出る
  • cat ファイル | という形自体がたいてい不要なプロセスだ。このパターンを減らす習慣はサブシェル問題と別に得がある
  • リダイレクトの位置が done の後ろというのは最初こそ奇妙だが、ループ全体が一つの複合コマンドで、その複合コマンドの標準入力を差し替えているのだと考えれば自然だ

ファイルが複数あって cat a b c | を書きたくなったら、そのときはリダイレクトではなく次節のプロセス置換が正解だ。

4. プロセス置換 - 入力がファイルでないとき

現実のスクリプトは入力がファイルでない場合のほうが多い。find の結果、grep の結果、API レスポンスを jq で絞ったものなどだ。そこで使うのがプロセス置換だ。

$ n=0
$ while read -r l; do n=$((n+1)); done < <(cat /tmp/f.txt)
$ echo "after procsub: n=$n"
after procsub: n=3

< <(...) はタイプミスに見えるが、二つの別の構文が隣り合っているだけだ。<(cmd) がコマンドの出力をファイルのように見せ、その前の < がその偽のファイルを標準入力につなぐ。間に空白が必ず要る。

4.1 なぜこれは効いてパイプは効かないのか

プロセス置換でも cmd は別プロセスで動く。違いはループがどちら側にあるかだ。

  • パイプではループがパイプラインの構成要素なのでサブシェルへ押し出される
  • プロセス置換ではループが現在のシェルに残り、サブシェルへ押し出されるのはデータを作る側だ
  • データを作る側は変数を変えないので、サブシェルでも問題ない

4.2 ファイル名を扱うときに同時に付いてくる問題

find の結果を回すループで実際に確かめた結果だ。空のログファイル一つと内容のあるファイル一つを置いて、空ファイルの数を数えた。

$ find logs -name '*.log' | while read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done
$ echo "find | while  -> empty=$empty"
find | while  -> empty=0

$ while IFS= read -r f; do
    [ -s "$f" ] || empty=$((empty+1)); done < <(find logs -name '*.log')
$ echo "procsub       -> empty=$empty"
procsub       -> empty=1

ここで IFS= と -r が一緒に付いている理由を押さえておく。サブシェル問題とは別だが同じ行で壊れる欠陥だ。

  • IFS= を与えないと前後の空白が削られる。空白で始まるファイル名が静かに変わる
  • -r を与えないとバックスラッシュがエスケープとして解釈される。Windows から来たパス文字列が特に危ない
  • ファイル名に改行が入りうる環境なら find ... -print0 と read -r -d '' を対で使う
  • この組み合わせもプロセス置換の中でそのまま動く。上の実行で -print0 版も同じ結果を返した

5. lastpipeが効く条件と効かない条件

bash にはパイプラインの最後の構成要素を現在のシェルで実行させるオプションがある。

$ shopt lastpipe
lastpipe        off
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=0

$ shopt -s lastpipe
$ shopt lastpipe
lastpipe        on
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done; echo "n=$n"
n=3

ここまで見ると最も簡単な解決に見える。ところがターミナルにそのまま打ってみると何も起きない。理由は job control だ。

5.1 job controlが有効だと無視される

スクリプトの中で set -m により job control を入れたり切ったりしながら同じコードを走らせると、こう分かれる。

$ set -m          # job control ON (対話型シェルの既定状態)
$ shopt -s lastpipe
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control ON  -> n=$n"
job control ON  -> n=0

$ set +m          # job control OFF
$ n=0; printf 'a\nb\nc\n' | while read -r l; do n=$((n+1)); done
$ echo "job control OFF -> n=$n"
job control OFF -> n=3

対話型シェルは job control を既定で有効にしている。だからターミナルで shopt -s lastpipe をいくら有効にしても結果は変わらない。オプションは確かに有効なのに動作だけしない、デバッグの厄介な状態だ。

5.2 ではlastpipeをどこに使うか

  • 配布するスクリプトの既定の解法としては勧めない。読む人がファイル冒頭の shopt 一行と百行下のループを結び付けて理解する必要がある
  • bash 専用だ。dash にはこのオプション自体がない
  • 既存スクリプトを最小の修正で救う必要があるときには有用だ。パイプ構造をそのままにして一行足すだけで済む
  • 「いまこれはサブシェルのせいか」を1分で判定する用途に良い。この一行で結果が変わるなら原因が確定する
  • 有効にするときは必ずスクリプトの中で有効にし、そのスクリプトが bash で実行されるかを確認する

6. サブシェルが生まれる残りの場所

パイプだけ気をつければいいわけではない。以下はそれぞれ直接走らせて確かめた結果だ。

構文サブシェル変数の変更が外に残るか確認した結果
cmd | while ...生まれる残らないn=0
( k=2 )生まれる残らないk=0
{ k=1; }生まれない残るk=1
$( ... )生まれる残らないBASHPID が変わる
{ m=99; } &生まれる残らないwait 後も m=0
while ... done < ファイル生まれない残るn=3
while ... done < <(cmd)ループは生まれない残るn=3
for v in ...; do生まれない残るn=6

表で最も紛らわしい二行が ( ) と { } だ。見た目が似ているのに性格が正反対だ。

6.1 括弧は隔離、波括弧はまとめ

$ k=0; { k=1; };  echo "brace group: k=$k"
brace group: k=1
$ k=0; ( k=2 );   echo "paren subshell: k=$k"
paren subshell: k=0

この違いがむしろ助けになる場面もある。サブシェルは隔離装置でもあるからだ。

$ cd /tmp
$ echo "before: $PWD"
before: /tmp
$ ( cd / ; echo "inside: $PWD" )
inside: /
$ echo "after : $PWD"
after : /tmp

ディレクトリを一時的に移して何かをし、元の場所に戻る必要があるとき、cd の後に cd - で戻す代わりに括弧で包めばいい。途中で失敗して抜けても親の作業ディレクトリは動かない。

6.2 exitも括弧の中に閉じ込められる

$ ( exit 42 )
$ echo "parent still alive, subshell exit=$?"
parent still alive, subshell exit=42

これは両方に働きうる。後始末のコードをサブシェルに入れておけばその中の exit がスクリプト全体を殺さないので安全だ。逆に「エラーならスクリプトを終わらせろ」という意図で入れた exit 1 が括弧の中にあると、スクリプトは平然と回り続ける。後者のほうがはるかに頻繁に事故になる。

7. 値を取り出す六つの方法とそれぞれの代償

3行のデータで六つの方法をすべて走らせた。データは alpha 10、beta 20、gamma 30 で、目標は合計60だ。

方法構文結果代償・制約
リダイレクトdone < ファイル60入力が実ファイルのときのみ。POSIX sh 可
プロセス置換done < <(cmd)60bash 拡張。POSIX sh では構文エラー
ヒアストリングdone <<< "$(cmd)"60出力全体をメモリに載せる。bash 拡張
先に配列へ読むmapfile -t a < ファイル60bash 4 以上。大容量ならメモリ負担
出力をキャプチャt=$(cmd | { ...; echo "$t"; })60値が一つなら楽。複数ならパースが要る
一時ファイル経由... > "$tmp" の後に読む60移植性が最も高い。後始末の責任が生じる

7.1 実行結果

$ total=0
$ while read -r name v; do total=$((total+v)); done <<< "$(cat /tmp/data.txt)"
$ echo "here-string total=$total"
here-string total=60

$ mapfile -t lines < /tmp/data.txt
$ echo "mapfile count=${#lines[@]} first=${lines[0]}"
mapfile count=3 first=alpha 10

$ total=$(cat /tmp/data.txt | { t=0; while read -r n v; do t=$((t+v)); done; echo "$t"; })
$ echo "captured total=$total"
captured total=60

最後の方式が面白い。サブシェルをなくす代わりにサブシェルが値を外に出せる唯一の通路である標準出力を使う。サブシェルから変数は出られないが出力は出られる。

7.2 選ぶ基準

  • 入力がファイルだ → リダイレクト。悩む必要がない
  • 入力がコマンドの出力で bash を使う → プロセス置換
  • #!/bin/sh で配布する必要がある → 一時ファイルか出力キャプチャ。プロセス置換は使えない
  • 行数が数万行以上ある → ヒアストリングと mapfile は避ける。全体をメモリに載せる
  • ループから出す値が一つだけだ → 出力キャプチャが最も短い
  • 既存スクリプトを最小限で直す必要がある → lastpipe。ただし5節の制約をコメントに残す

一行まとめ。サブシェルから変数は出られないが標準出力とファイルと終了ステータスは出られる。値を取り出すあらゆる方法は結局この三つのどれかを使うか、そもそもサブシェルを作らないかのどちらかだ。

8. set -eがパイプとサブシェルでずれる地点

サブシェルを理解すると、set -e がなぜ頻繁に裏切るのかも一緒に解ける。実行結果から見る。

$ set -e
$ printf 'a\nb\n' | grep -q zzz | cat
$ echo "survived"
survived

grep が失敗したのにスクリプトが止まらなかった。パイプラインの終了ステータスは既定で最後のコマンドのステータスだからだ。最後の cat が成功したのでパイプライン全体が成功として集計された。

8.1 PIPESTATUSでどの位置が死んだかを見る

$ false | true | false
$ echo "\$?=$? PIPESTATUS=(${PIPESTATUS[@]})"
$?=1 PIPESTATUS=(1 0 1)

配列の順序がパイプラインの順序だ。三つの位置のうち一つ目と三つ目が失敗したことがそのまま読める。注意すべきは、この配列が次のコマンドを一つ通るだけで上書きされるという点だ。使うなら即座に別の配列へコピーする。

8.2 pipefailを有効にすると変わること

$ ( set -e -o pipefail; printf 'a\n' | grep -q zzz | cat; echo "NOT REACHED" )
$ echo "with pipefail exit=$?"
with pipefail exit=1

$ ( set -e; printf 'a\n' | grep -q zzz | cat; echo "reached" )
reached
$ echo "without pipefail exit=$?"
without pipefail exit=0

pipefail が有効になるとパイプ内のどの位置でも0以外のステータスが出た時点でパイプラインが失敗と判定され、そこで初めて set -e が動作する。

8.3 最も静かな罠

これは別に取り出して書く価値がある。サブシェルが || の左側に置かれると、その中の set -e が丸ごと無効化される。

$ ( set -e; false; echo "NOT REACHED" ) || echo "caught"
NOT REACHED

NOT REACHED が出力された。「失敗したら捕まえよう」と付けた || のせいでサブシェル全体が条件判定の文脈に入り、その中では set -e が切れる。関数でも同じだ。

$ f() { set -e; false; echo "reached anyway"; }
$ f || true
reached anyway

「エラー検査を付けたのにむしろエラー検査が切れた」という状況なので目で見つけにくい。整理すると実務で使う規則はこうなる。

  • set -euo pipefail をスクリプト冒頭に置きつつ、それだけを信じない
  • 重要なパイプラインは PIPESTATUS を明示的に確認する
  • || 何か を付けた瞬間、その左側の set -e はないものとみなす
  • サブシェルの成否を確認したいなら || で捕まえず、実行した後に $? を別の行で検査する
  • ( exit 7 ) が $?=7 をそのまま渡すことは確認した。終了ステータス自体は正常に伝播する

9. シェルごとに分かれる部分

同じコードを dash で走らせた結果だ。

$ dash t.sh
dash pipe: n=0
dash redirect: n=3

$ dash -c 'while read -r l; do echo "$l"; done < <(printf "x\ny\n")'
dash: 1: Syntax error: redirection unexpected
項目bash 5.2.37dashzsh・ksh
パイプ内whileのカウンタ0 (確認済)0 (確認済)確認できず
リダイレクトで解決3 (確認済)3 (確認済)確認できず
プロセス置換 <(...)動作構文エラー確認できず
shopt -s lastpipeあり (job control 条件付き)なし確認できず
PIPESTATUSありなし確認できず
mapfileありなし確認できず

ここから出る実務規則は単純だ。

  • シバンが #!/bin/sh なのにプロセス置換を使ったなら、そのスクリプトは配布環境で構文エラーで死ぬ。開発機で /bin/sh が bash にシンボリックリンクされている場合これが見えない
  • bash 機能を使うならシバンを #!/usr/bin/env bash と正確に書く
  • 移植性が必要なスクリプトは配布対象のシェルで一度は実際に走らせる。この記事の表を作るのにかかった時間は数分だ
  • コンテナイメージに bash がない場合はよくある。最小イメージの既定シェルが何かを先に確認する

10. こうした検証スクリプトを書くときの罠

上の結果はすべてファイルに保存して走らせたものだ。一行の検証でも -c の後ろにコードを丸ごと押し込む方式は避けたほうがよく、理由は二つある。

10.1 引用符が二度剥がれる

インライン方式は文字列が外側のシェルを一度、内側のインタプリタを一度通過する。だから $、バックスラッシュ、引用符がどの段階で消費されるのかを毎回違う形で計算する必要がある。上の例で \$\$ のようにエスケープが付いている箇所がその痕跡だ。ファイルに保存すればこの段階が一つ消える。

10.2 非ASCII文字が静かに壊れる

より厄介なほうだ。コマンドラインで渡される文字列はシェルとターミナルとインタプリタのエンコーディング設定を順に通る。この鎖のどれか一つでもロケールが違うと、日本語・韓国語・中国語のような非ASCII文字がエラーなしに別のバイトへ変わる。

  • エラーが出ないので検査器は通過したと報告する。実際には検査対象の文字列がすでに別の値だ
  • この状態で「検出0件」が出ると、それを無傷という意味で読んでしまう。最悪の失敗だ
  • ファイルに保存すれば UTF-8 のバイトがそのままインタプリタへ渡る。エンコーディングの受け渡し地点が一つに減る
  • 検査器を新しく作るならわざと欠陥を仕込んで捕まるかをまず確認する。捕まらないなら対象がきれいなのではなく検査器が壊れているのだ
  • 韓国語は音節単位で組まれているため語幹だけの正規表現が活用形を丸ごと取り逃す。文字クラスで開いておくほうが安全だ

ログを正規表現で走査する作業全般はgrepとAWKガイドとログ分析コマンドガイドに別途整理してある。

11. 確認できなかったこと

この記事で実行により検証できなかった項目を一箇所にまとめる。

  • zsh と ksh。この二つのシェルを実行できる環境ではなかったため確認できなかった。ksh 系がパイプラインの最後のコマンドを現在のシェルで実行するという話は広く知られているが、この記事では再現していない。当該シェルを使うなら3行のスクリプトで自分で再現しておくのが確実だ
  • 本物の端末が付いた対話型セッション。5節の結論は set -m で job control を入れたり切ったりして得た。制御端末が付いた実際のログインシェルで同じ実験はしていない。ただし job control の状態によって結果が分かれること自体は確認した
  • POSIX 標準の原文。パイプラインの各要素をサブシェルで実行するかを標準が実装に委ねているという点はシェルごとに動作が分かれる理由としてよく言及されるが、標準の条文そのものは照合していない
  • busybox ash と最小コンテナイメージ。実務で最も頻繁に問題になる組み合わせだが、この記事では確認できなかった
  • 大容量入力でのメモリ実測。7節でヒアストリングと mapfile が全体をメモリに載せると書いたが、行数に応じた実際の使用量は測っていない
  • 旧版の bash。lastpipe と mapfile が導入された正確なバージョン境界は確認していない。非常に古いシステムを対象にするならその機材で直接確認する必要がある

FAQ

Q1. ループの中で export n をすればいいのでは

だめだ。export は親から子へ環境を引き継ぐ装置で、方向が逆だ。サブシェルで export をしてもそのサブシェルがさらに作る孫プロセスにしか伝わらず、親には何の影響もない。同じ理由で declare -g も助けにならない。グローバル範囲とはそのプロセスの中でのグローバルであってプロセスを越えない。

Q2. ループの中では値が合っているのに、なぜ外でだけ違うのか

まさにそれがこの現象の指紋だ。ループ内の echo はサブシェルの中で実行されるのでそのプロセスの最新値を見る。ループ外の echo は親シェルで実行されるので触られたことのない元の値を見る。同じ変数名だが互いに別のプロセスのメモリを見ている。この症状が見えたらパイプから探せばいい。

Q3. while ではなく for を使えば解決するか

パイプを使わなくなるのでそうとも言えるが代償がある。for v in $(cmd) の形は現在のシェルで動くので変数が残る。ただし出力全体をメモリに載せ、単語分割とグロブが適用されて空白入りのファイル名が割れる。for line in $(cat ファイル) は行単位の処理ではなく単語単位の処理だ。行を扱うなら while read にリダイレクトが正解だ。

Q4. パイプラインの各段階は順次実行なのか

違う。パイプラインの構成要素は同時に開始し、パイプバッファを通じて互いに流量を調整する。だから前のコマンドが終わるのを待ってから後ろが始まるのではない。これもサブシェルが必要な理由の一つだ。別プロセスであってこそ並行して動ける。

Q5. バックグラウンドで回したブロックの変数は wait の後に読めばいいのでは

だめだ。実行して確かめた結果、{ m=99; } & の後に wait をかけても m は0だった。wait は子が終わるのを待つだけで値を持ってこない。バックグラウンド処理の結果を受け取る必要があるなら、標準出力をファイルや名前付きパイプで受けて wait の後に読む。

結論: 今日変える三つのこと

第一に、ループ本体を直そうとする前に | を探す。ループの中では合っていて外でだけ違う値は、ほぼ常にパイプのせいだ。cat ファイル | while を while ... done < ファイル に変えるのに3秒かかり、これを知らないと算術展開を30分眺めることになる。

第二に、サブシェルを「変数が消える場所」ではなく「境界」として読む。cd も set も trap も exit もその中に閉じ込められる。閉じ込められるのが問題な状況と、閉じ込められて助かる状況の両方があり、( ) は後者のための道具でもある。一時的にディレクトリを移す必要があるとき括弧で包む習慣がその例だ。

第三に、set -e を安全装置として信頼しない。パイプ途中の失敗は既定では捕まらず、|| を付けた瞬間に左側の set -e は切れる。pipefail を一緒に有効にし、重要な箇所は PIPESTATUS で明示的に確認する。

最後に一つ。この記事の表と出力はすべて2行から10行の間のスクリプトで得たものだ。シェルの動作が疑わしいなら議論せず3行走らせるほうが常に速い。printf 'a\nb\nc\n' とカウンタ一つで、たいていの疑問は30秒で終わる。
