引言：两个错误的假设

Web 应用的缺陷清单很长。可是从清单往后退一步看，大多数条目其实出自同一个地方。它们只是名字不同、散落在不同的检查项里，根却是两句话。

假设 ①「客户端改不了」 — 放在表单里的值、HTML 的 data- 属性、Cookie、请求体、请求头。这里面没有一样是用户改不动的。
假设 ②「攻击者猜不到」 — 重置令牌、会话值、内部标识符。可以预测的值不是秘密。

这两句话之所以重要，是因为它们让人可以 边读代码边判断，而不必逐条背诵缺陷目录。看到某段代码在值到达服务端时就默认「这应该就是我们发出去的那个值」，那就是 ①。看到某个值被当作秘密，而生成它的函数却拿时间或序号当原料，那就是 ②。

本文走过十四个具体的位置。从 Cookie 究竟何时被送出，到两个各自只算中危的缺陷叠加后会变成什么，到服务端接收客户端算出的金额这种设计为什么不成立，再到 识别控制垮掉之后系统日志能证明什么、不能证明什么。每一节都把脆弱代码与安全代码并排放，并在节末点明这个缺陷源自 ① 还是 ②。

若想按请求类型更细地了解 Cookie 发送规则，SameSite Lax、Strict、None - 哪些请求会丢掉 Cookie 另有专门讨论。头部重复到达时的解释问题在 同一个头部出现两次 里整理过。

本文的范围。 这里只讲 为什么危险 和 怎么防住，此外一概不涉及。不提供可运行的攻击代码、绕过手法或自动化工具用法。最后一节的检查方法也仅限于 本人运营或已获明确授权的站点。代码示例中的路径与文件名全部是为说明而虚构的值。

1. 浏览器什么时候发送 Cookie - SameSite 三个取值的实际行为

读服务端代码久了会发现底下压着一个没说出口的前提：「会话 Cookie 带着呢，所以这是从我们自己的页面发来的请求。」这个前提成不成立不由服务端决定，而由 浏览器何时附上 Cookie 决定。调节这条规则的就是 SameSite 属性。

定义在 MDN 的 Set-Cookie 页面上。SameSite=Strict 只在请求来自设置该 Cookie 的同一站点时才发送 Cookie。 SameSite=Lax 在同站请求之外，只有当跨站请求既是顶层导航又使用安全方法时才发送 Cookie。 同一页面把顶层导航描述为「会让地址栏 URL 发生变化的请求」，并明确 POST、PUT、DELETE 不属于安全方法。SameSite=None 在跨站和同站请求上都发送 Cookie，使用这个取值时必须同时设置 Secure 属性。

# 脆弱：一个属性都没有。脚本能读，明文也会发出去，
#       跨站请求带不带它则交给浏览器默认值决定。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/

# 脆弱：明确打开了跨站发送。
#       常见的形态是为了嵌入而打开，之后就一直留着。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; SameSite=None; Secure

# 安全：会话 Cookie 的基本形态。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

# 安全：如果有页面需要从外部链接进来时保持登录状态，就用 Lax。
#       用 Strict 时，从外部链接进来的第一个请求在用户看来像是掉线了。
Set-Cookie: session=PLACEHOLDER_SESSION_VALUE; Path=/; HttpOnly; Secure; SameSite=Lax

1.2 为什么不能依赖默认值

MDN 的 Set-Cookie 页面写道「部分浏览器在未指定 SameSite 时把 Lax 当作默认值」。句子里有「部分」两个字，这就是要点。而且作为默认值应用的 Lax 与显式设置的 Lax 并不相同。同一页面的说明是：作为默认值应用时使用的是 更宽松的版本，在这个版本里 只要 Cookie 设置后不超过两分钟，POST 请求也会带上它。

不写明 Cookie 的发送条件，这个判断就交给了浏览器默认值，而默认值是会随浏览器与版本变化的东西。

  • 默认值很难在代码评审里作为「默认就是 Lax，没问题」的依据，因为依据落在自己代码之外
  • 更宽松的默认 Lax 的两分钟窗口，与登录之后紧接着的流程在时间上重合
  • 用了 None 却漏掉 Secure 的 Cookie 会被浏览器拒绝。结果不是「安全性变弱」而是「Cookie 根本带不上」，通常先以功能故障的形式暴露出来
  • SameSite 的判定单位是可注册域名而不是源。同一域名下的其他主机会被当作同站
  • OWASP Session Management Cheat Sheet 写明会话 Cookie 必须显式设置 SameSite=Strict 为优先，或者设置 Lax

回看假设 — ①。「只有从我们自己页面发出的请求会到达」这个前提，把请求来源的判断交给了客户端一侧的情形。

2. CSRF 令牌挡得住什么，挡不住什么

按照 OWASP Cross-Site Request Forgery Prevention Cheat Sheet 的定义，CSRF 是指恶意网站、邮件、博客、即时消息或程序诱使已认证用户的浏览器在受信任站点上执行非本意操作的攻击。 同一份文档用一句话概括了成立条件：浏览器请求会自动带上包括会话 Cookie 在内的所有 Cookie，因此只要没有使用恰当的授权，这种攻击就行得通。

这里说的「恰当的授权」不是检查是否登录。登录早就完成了。需要的是 这个请求确实从我们自己页面发起的证据，而这个证据必须是浏览器不会自动附上的值。

CSRF 令牌的职责是证明请求的来源。所以它必须是浏览器不会自动附上的值，而自动附上的 Cookie 无法代替这个角色。

2.1 Synchronizer Token - 服务端记得住的值

在 OWASP Cross-Site Request Forgery Prevention Cheat Sheet 描述的同步令牌模式里，令牌 在服务端生成，每个会话生成一次或每个请求生成一次。服务端校验请求带来的令牌与自己存在会话里的值是否一致。因为浏览器不会自动附上它，其他站点构造的请求里就不可能有这个值。

<!-- 脆弱：改变状态的表单，却只靠自动附上的值（Cookie）来认证 -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">删除</button>
</form>

<!-- 安全：表单带上服务端存在会话里的值 -->
<form method="POST" action="/api/items/delete">
  <input type="hidden" name="csrf_token" value="PLACEHOLDER_TOKEN_FROM_SESSION">
  <input type="hidden" name="item_id" value="PLACEHOLDER_ID">
  <button type="submit">删除</button>
</form>
// 脆弱：只看是否登录，不看请求从哪里发起。
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();
  deleteItem(req.body.item_id);
  res.status(200).end();
}

// 安全：用常数时间比较把会话里的令牌与请求的令牌做比对。
function handleDelete(req, res) {
  if (!req.session.userId) return res.status(401).end();

  const expected = req.session.csrfToken;         // 服务端记得的值
  const provided = req.body.csrf_token;           // 请求带来的值
  if (!expected || !provided || !timingSafeEqual(expected, provided)) {
    return res.status(403).end();                 // 校验失败是拒绝，不是放行
  }
  deleteItem(req.body.item_id);
  res.status(200).end();
}

2.2 Double Submit Cookie 及其局限

在服务端不便保存状态的结构里会使用双重提交模式：把同一个值分别放进 Cookie 和请求体，服务端只检查两者是否相同。问题在于服务端并不记得这个值。OWASP Cross-Site Request Forgery Prevention Cheat Sheet 明确指出，朴素的双重提交 会被能在目标域上写 Cookie 的攻击者绕过，并列出了具体路径：存在漏洞的兄弟子域、DNS 接管，以及通过明文 HTTP 注入 Cookie。同一份文档的建议是 签名的双重提交，用服务端密钥把令牌与会话数据绑定后做 HMAC 处理。

// 脆弱：只看两个值是否相同，不确认这个值从哪里来。
function verifyCsrf(req) {
  return req.cookies.csrf === req.body.csrf_token;
}

// 安全：用服务端密钥对绑定了会话的值签名。
//       仅仅能写 Cookie 已不足以伪造出有效令牌。
function issueCsrf(session) {
  const nonce = randomTokenHex(32);                       // 密码学随机数
  const mac   = hmacSha256(SERVER_SECRET, session.id + '.' + nonce);
  return nonce + '.' + mac;
}
function verifyCsrf(req) {
  const [nonce, mac] = String(req.body.csrf_token || '').split('.');
  if (!nonce || !mac) return false;
  const expected = hmacSha256(SERVER_SECRET, req.session.id + '.' + nonce);
  return timingSafeEqual(expected, mac);                  // 连是否属于本会话一并校验
}

把令牌 挡不住什么 也说清楚会更好。OWASP Cross-Site Request Forgery Prevention Cheat Sheet 用大写强调写着：XSS 会让所有 CSRF 缓解手段失效。 只要攻击者的代码在页面里执行，它就能从 DOM 里读出令牌并附到请求上。令牌只筛掉「其他站点构造的请求」，筛不掉「在我们自己页面里构造的请求」。

  • 令牌校验失败时的默认行为必须是 拒绝。只记日志然后放行的实现等同于没有控制
  • 自定义头部的方式同样有效。同一份 OWASP 文档说明，所有现代浏览器都会把带自定义头部的请求标记为需要预检，因此服务端确认该头部存在，就知道若请求来自浏览器则必然经过了预检
  • 不过自定义头部的方式在 Access-Control-Allow-Origin 过宽时会失效。通配符源会让这道防御归零
  • 把令牌放在 GET 请求的查询字符串里，它会留在日志、Referrer 和浏览器历史中。不要用 GET 暴露状态变更
  • 每会话一个令牌和每请求一个新令牌都有效。按请求签发的一方还需要一并设计并行标签页中先前令牌失效的问题

回看假设 — ①。「这个请求是我们的表单构造的」是本节的假设。没有证明来源的值，这句话就只是未经验证的推测。

3. 两个缺陷叠加时 - 各自中危，合起来致命

逐条看检查项时，这两件事各自都不算特别严重。

  • 缺陷 A — 改变状态的端点没有 CSRF 令牌校验。 单独看是中危。浏览器默认值一直在朝着不给跨站 POST 附带 Cookie 的方向变化，这个默认值事实上充当了缓解装置
  • 缺陷 B — 会话 Cookie 带着 SameSite=None; Secure。 单独看会被归为配置项。取值本身合法，对需要被嵌入的服务来说也可能是正当选择

可是这两者共处于同一系统时，性质就变了。B 明确关掉了浏览器一侧的缓解装置，于是跨站请求也会带上会话 Cookie。此时因为 A，服务端 一点判断请求来源的手段都不剩。服务端看到的只是一个带着有效会话 Cookie 的状态变更请求，没有依据分辨它是从自己页面发起的还是从别处发起的。

逐项检查表给条目打分，可真正的风险产生于条目之间的关系，而按条目打分的表格里没有写关系的那一栏。

3.1 风险是相乘而不是相加

状态浏览器的 Cookie 发送服务端的来源校验结果按条目检查表中的待遇
仅有缺陷 A（无 CSRF 令牌）默认值大体拦截跨站 POST无依赖浏览器默认值的状态中危

最后一行最右侧的单元格就是本节的要点。按条目的检查表给 A 打 A 的分，给 B 打 B 的分。两项都没越过「立即处置」的线，就一起落到队列下方。可真正的风险在 路径 上，而路径产生于条目之间的关系。

  • 同样结构的组合还有别的：可预测的标识符 + 缺失的所有权校验，登录后仍延续的会话 + 可从外部植入会话值的路径，宽松的 Access-Control-Allow-Origin + 允许携带凭据
  • 要看到组合，就必须 不去数条目，而是把一个请求的处理路径追到底。浏览器附上什么，服务端确认什么，不确认的又是什么
  • 即便是评级较低的条目，一并记下「这一条现在靠什么在被缓解」也能让组合浮现。如果 A 的缓解依据是浏览器默认值，那么某处是否存在关掉该默认值的配置，就立刻成为需要确认的对象
  • 修复的优先次序也会变。只要去掉 A 与 B 中的任意一个，路径就断了。如果嵌入其实并不需要，回退 B 通常更便宜

回看假设 — ①。 A 与 B 都立在同一个假设上：客户端一侧的情形会如实告知请求来自何处。所以它们叠加时不会互相抵消，而是互相放大。

4. 把用户标识符放进 Cookie 会发生什么

写实现时有一种顺手就会用的形态：登录时把用户编号放进 Cookie，之后的请求读这个值来判断「这是谁的请求」。它省下了一次查询。

# 脆弱：用户编号原样放在 Cookie 里。
Set-Cookie: uid=1042; Path=/
Set-Cookie: role=member; Path=/

# 脆弱：以人能读懂的形式承载身份的会话值。
Set-Cookie: session=user-1042-member; Path=/; HttpOnly

# 安全：值本身没有任何含义，身份由服务端凭这个值查出。
Set-Cookie: session=PLACEHOLDER_OPAQUE_128BIT_VALUE; Path=/; HttpOnly; Secure; SameSite=Strict

OWASP Session Management Cheat Sheet 的要求很明确。会话 ID 的内容必须没有含义以防信息泄露攻击，会话 ID 在客户端一侧应当只是一个标识符，其取值绝不能包含敏感信息或个人身份信息。同一份文档也一并写明了熵的要求：为防止暴力猜测，会话标识符必须至少具备 64 位熵，若采用十六进制编码则至少需要 16 个字符。

按照 OWASP Insecure Direct Object Reference Prevention Cheat Sheet 的定义，IDOR 是指攻击者能够通过操纵 Web 应用 URL 或参数中使用的标识符来访问或修改对象的漏洞。 同一份文档把这类缺陷归纳为三个要素：对象、指向该对象的引用，以及 缺失的对象级授权检查。

// 脆弱：用请求告知的用户编号去查询。
//       被查对象的所有者与请求发起者是否一致，没人确认。
function getOrder(req, res) {
  const uid = req.cookies.uid;                    // 客户端决定的值
  const order = db.findOrder(req.params.orderId);
  res.json(order);                                // 没有所有权校验
}

// 安全：身份只从服务端会话取得，并把所有权写进查询条件。
function getOrder(req, res) {
  const uid = req.session.userId;                 // 服务端记得的值
  if (!uid) return res.status(401).end();

  // 不是先找到再比较，而是一开始就只找属于自己的。
  const order = db.findOrderOwnedBy(req.params.orderId, uid);
  if (!order) return res.status(404).end();       // 连是否存在也不泄露
  res.json(order);
}

难猜不等于访问控制。OWASP Insecure Direct Object Reference Prevention Cheat Sheet 写明，即使使用复杂标识符，访问控制检查依然是必需的；即便攻击者拿到了未授权对象的 URL，应用也仍应阻断其访问尝试。

  • Cookie 过期只是客户端一侧的清理。OWASP Session Management Cheat Sheet 写道，会话过期时应用必须 在客户端与服务端两侧都使其失效，从安全角度看后者最为关键且属强制要求
  • 同一份文档明确要求不要把认证令牌、会话 ID、JWT、刷新令牌等凭据存进 localStorage 或 sessionStorage
  • 把权限放进 Cookie 也是同样的问题。客户端持有的 role=member 只是展示用的提示，不能作为授权依据

回看假设 — ①。「Cookie 是我们种下的，所以还是我们写的那个值」是本节的假设。Cookie 由服务端签发，保存它的却是客户端。

5. 可预测的重置令牌 - 可以预测的值不是秘密

密码重置链接里的令牌 在有效期内替代着认证凭据。谁拿到有效令牌，谁就能改掉账号密码。因此这个值的质量必须与登录密码放在同一层面对待。

CWE 给这类缺陷单独编了号。CWE-640 把「产品提供了无需知道原密码即可找回或修改密码的机制，而该机制很弱」的状态命名为 Weak Password Recovery Mechanism for Forgotten Password。 其父项是 CWE-1390 Weak Authentication 与 CWE-287 Improper Authentication。也就是说 这类缺陷被归类为认证缺陷。它不是附属功能的问题，而是多出了一条认证路径，且那一条更弱。

5.1 随机数的来源就是全部

MDN 在 Math.random() 页面顶部挂了一条警告：「Math.random() 不提供密码学安全的随机数。不要将其用于任何与安全相关的用途。请改用 Web Crypto API，更确切地说是 Crypto.getRandomValues() 方法。」 同一页面还写道「实现会选择随机数生成算法的初始种子，用户无法选择或重置它」。无法控制种子并不意味着安全，而意味着对这个值由什么材料生成没有保证。

可以预测的值不是秘密。当把值当作秘密的代码与生成这个值的代码立在不同的前提上时，被当作秘密对待的就不是那个值，而是对生成它的那个函数的信任。

// 脆弱：用时间和用户编号做材料。两种材料都能从外部收窄。
function makeResetToken(userId) {
  return md5(Date.now() + '-' + userId);
}

// 脆弱：虽然用了随机函数，但不是密码学随机源。
function makeResetToken() {
  return Math.random().toString(36).slice(2, 12);
}

// 脆弱：序号。拿到一个签发值就能看出相邻值的形态。
function makeResetToken(seq) {
  return 'reset' + String(seq).padStart(8, '0');
}

// 安全：从密码学随机源取足够的长度。
function makeResetToken() {
  const buf = new Uint8Array(32);                 // 256 位
  crypto.getRandomValues(buf);
  return [...buf].map(b => b.toString(16).padStart(2, '0')).join('');
}

5.2 只有一个好令牌还不够

OWASP Forgot Password Cheat Sheet 要求的不只是随机数质量。令牌必须 使用密码学安全的随机数生成器生成，必须 长到足以抵抗暴力破解，并且 在使用之后失效。同一份文档还要求防止用户枚举：对存在的账号与不存在的账号返回一致的消息，并且 确保响应在一致的时间内返回，以防攻击者枚举出哪些账号存在。对链接打开的页面，指引是 添加取值为 noreferrer 的 Referrer Policy 标签以避免 Referrer 泄露；构造重置 URL 时则明确要求 不要依赖 Host 头，应写死或对照可信域名清单校验。对既有会话，建议 询问用户是否要使其所有既有会话失效，或者自动使其失效。

// 脆弱：令牌以明文保存，既没有有效期也没有一次性处理。
//       重置之后此前的登录会话依然活着。
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (!user) return { ok: false, message: '该邮箱尚未注册' };  // 泄露账号是否存在
  const token = makeResetToken(user.id);
  await db.saveResetToken(user.id, token);
  await sendMail(email, 'https://example.com/reset?token=' + token);
  return { ok: true };
}

// 安全：以哈希保存、设置有效期、一次性，且响应始终相同。
async function requestReset(email) {
  const user = await db.findUserByEmail(email);
  if (user) {
    const token = makeResetToken();                       // 密码学随机数
    await db.saveResetToken({
      userId:    user.id,
      tokenHash: sha256(token),                           // 不保存原文
      expiresAt: Date.now() + RESET_TTL_MS,               // 较短的有效期
      usedAt:    null                                     // 一次性标记
    });
    await sendMail(email, RESET_BASE_URL + '?token=' + token);  // 不取自 Host 头
  }
  await constantDelay();                                  // 对齐响应时间
  return { ok: true, message: '已向该地址发送指引' };        // 始终是同一句话
}
// 安全：完成重置的那一侧的处理。
async function completeReset(token, newPassword) {
  const row = await db.findResetByHash(sha256(token));
  if (!row) return fail();
  if (row.usedAt) return fail();                    // 已经用过的令牌
  if (row.expiresAt < Date.now()) return fail();    // 已过期的令牌

  await db.markResetUsed(row.id);                   // 先标记为已消耗
  await db.updatePassword(row.userId, hashPassword(newPassword));
  await db.invalidateAllSessions(row.userId);       // 使既有会话全部失效
  await db.invalidateOtherResetTokens(row.userId);  // 清理其余仍存活的令牌
  await notifyPasswordChanged(row.userId);          // 向本人通报该事实
  return ok();
}
  • 把令牌以明文存进数据库，等于让能读到该存储的一方立刻获得账号接管的手段。出于与密码相同的理由，应当哈希后保存
  • 把令牌放在 URL 查询里的方式很常见，但它同时制造出四条旁路：服务器访问日志、代理日志、浏览器历史与 Referrer
  • 如果重置请求本身没有速率限制，这个端点就成了枚举与批量尝试的通道。CWE-640 把重置尝试缺乏节流列为该缺陷的形态之一
  • 「该邮箱尚未注册」是句体贴的提示，同时也是关于账号是否存在的直接回答。需要一句既能提供指引又不回答这个问题的措辞
  • 重置完成后仍保留既有会话，重置的目的就只达成了一半。如果改密码的理由是「感觉有人已经进来了」，这一点尤其明显

回看假设 — ②。「攻击者猜不到」是本节的假设。时间、序号和通用随机函数都是依赖这个假设的材料。

6. eval() 被禁用的真正原因 - 数字转换变成代码执行的瞬间

eval() 不好这句话流传很广，可理由常被记成「因为慢」。真实的理由不是这个。MDN 的 eval() 页面把这个函数界定为注入汇点：传给它的参数会被动态解析并作为 JavaScript 执行，这类 API 有可能成为跨站脚本攻击的媒介。 同一页面在「绝不要使用直接 eval()」一节里把第一条理由写成：「eval() 以调用者的权限执行传给它的代码。」

一行本想把字符串转成数字的代码，会因字符串的内容而变成任意代码执行点。那段代码能做登录用户的界面所能做的一切。

// 脆弱：为了把输入转成数字而使用 eval。
//       输入若不是数字，其内容就会作为代码执行。
const qty = eval(document.getElementById('qty').value);

// 脆弱：把服务端返回的字符串当作数据信任并作为代码求值。
const data = eval('(' + responseText + ')');

// 脆弱：给 setTimeout 传字符串会在内部触发同样的求值。
setTimeout('refreshPanel(' + panelId + ')', 1000);

// 安全：数字就用数字的方式转换。
const raw = document.getElementById('qty').value;
const qty = Number.parseInt(raw, 10);
if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
  return showError('数量不正确');
}

// 安全：JSON 用 JSON 解析器读取。
const data = JSON.parse(responseText);

// 安全：回调以函数的形式传入。
setTimeout(() => refreshPanel(panelId), 1000);

出于同样的理由，为了按名称访问属性而拼接字符串再求值的写法 也要避开。MDN 的 eval() 页面给出的替代是方括号记法：用 obj[name] 而不是 eval('obj.' + name)。若名称来自用户，则还要一并加上 用允许清单校验名称 的步骤。

6.1 CSP 处理这个问题的方式

MDN 的 Content-Security-Policy 页面这样说明 unsafe-eval：「默认情况下，若 CSP 中含有 default-src 或 script-src 指令，则把参数作为 JavaScript 求值的函数会被禁用。这包括 eval()、setTimeout() 的 code 参数以及 Function() 构造器。」 随后它指出 unsafe-eval 关键字会撤销这层保护，并警告：「开发者应当避免使用 'unsafe-eval'，因为它抵消了设置 CSP 的大部分意义。」

  • 从代码中清掉 eval() 与从策略中清掉 unsafe-eval 是有先后顺序的。代码还在时只把策略收紧，功能会坏
  • 即使自己从不直接调用，第三方库也可能在内部对字符串求值。收紧策略正是让那些位置以控制台报错的形式浮现出来
  • MDN 的 eval() 页面介绍了降低风险的手段：传入受信类型对象而非字符串，并用 CSP 的 require-trusted-types-for 指令强制执行
  • 服务端也有同类汇点。把字符串拼成代码或查询再求值的位置，不分语言都具有相同的性质

回看假设 — ①。「这个字符串是我们生成的数字」是本节的假设。这个字符串若来自输入框、URL 或响应体中的任何一处，其内容就在客户端一侧被决定。

7. 用字符串拼接 HTML 之后 - 按上下文转义

关于输出转义最常见的误解是「写一个替换特殊字符的函数，把所有值都过一遍就行了」。OWASP Cross Site Scripting Prevention Cheat Sheet 的回答不同：「使用错误的编码方式可能引入弱点，或者破坏应用的功能。」 值落在哪里变了，需要的编码也就变了。

输出转义的单位不是值，而是值所落的位置。同一个值在 HTML 正文、属性、JavaScript、URL 和 CSS 中要求各不相同的编码。

// 脆弱：把用户输入拼成字符串，再让它按 HTML 解析。
el.innerHTML = '<span class="name">' + user.name + '</span>';

// 脆弱：在属性位置不加引号就放入值。

el.innerHTML = '<img src=' + imgPath + ' alt=profile>';

const span = document.createElement('span');

const img = document.createElement('img');

// 脆弱：未经校验就把 URL 放进链接属性。
//       不控制 scheme 时，这个值可能变成点击即执行的形态。
a.href = profile.website;

// 安全：先用 scheme 允许清单过滤。
function safeHttpUrl(raw) {
  let u;
  try { u = new URL(raw, location.origin); } catch { return null; }
  return (u.protocol === 'https:' || u.protocol === 'http:') ? u.href : null;
}
const href = safeHttpUrl(profile.website);
if (href) { a.href = href; } else { a.removeAttribute('href'); }
  • 即便是服务端转义后下发的值，客户端若再用 innerHTML 塞回去，编码也会错位。OWASP Cross Site Scripting Prevention Cheat Sheet 指出服务端编码对基于 DOM 的缺陷不起作用
  • 模板引擎的自动转义大体以 HTML 正文上下文为准。把同一个值放进脚本块内或 href 时需要另行处理
  • 仅仅在属性中用引号括住值，就能减少需要编码的字符集合。同一份文档明确强调了这一点
  • 「这个值出自我们的数据库，所以安全」这种判断不成立。把这个值写进数据库的，通常也是客户端
  • 在保存时转义，等于在不知道展示上下文的情况下编码。转义要 在输出的时点，按那个位置合适的方式 进行

回看假设 — ①。「这个值是我们控制的值」是本节的假设。若值的内容可能在客户端被决定，被控制的就不是值，而是放置这个值的位置。

8. 为什么不能让客户端算价格 - 信任边界的定义

做订单页面时会自然长出一种结构：选好选项后页面上的金额刷新，按下支付时把页面显示的总额放进请求发往服务端。用户看到的值与被处理的值一致，这很直观。

// 脆弱：金额计算的输入全部读自 DOM。
function buildOrder() {
  const unit  = Number(document.querySelector('#unit-price').dataset.price);
  const qty   = Number(document.querySelector('#qty').value);
  const disc  = Number(document.querySelector('#discount').dataset.rate);
  const total = Math.round(unit * qty * (1 - disc));

  return { itemId: currentItemId, qty, unitPrice: unit, discount: disc, total };
}

// 服务端：收到什么就原样保存什么。
function createOrder(req, res) {
  const o = req.body;
  db.insertOrder({ itemId: o.itemId, qty: o.qty, total: o.total });  // 没有重算
  res.json({ ok: true });
}

在这种结构里，服务端保存的金额 不是服务端算出来的值，而是请求告知的值。unitPrice、discount、total 三个字段全部来自客户端，服务端也没有代码去确认这些值是否与自己的定价策略一致。唯一的依据是「页面算过了，所以应该没错」这个前提。

// 安全：客户端只发送买的是什么。金额由服务端生成。
function buildOrder() {
  return {
    itemId:    currentItemId,
    optionIds: selectedOptionIds,        // 所选项的 ID 列表
    qty:       Number(document.querySelector('#qty').value),
    displayedTotal: shownTotal           // 展示价。用于比对，而不是依据
  };
}

// 服务端：从自己的价目表重新计算。
function createOrder(req, res) {
  const uid = req.session.userId;
  if (!uid) return res.status(401).end();

  const qty = Number.parseInt(req.body.qty, 10);
  if (!Number.isInteger(qty) || qty < 1 || qty > MAX_QTY) {
    return res.status(400).json({ error: 'INVALID_QTY' });
  }

  const item    = db.findSellableItem(req.body.itemId);          // 连是否可售也确认
  if (!item) return res.status(400).json({ error: 'INVALID_ITEM' });

  const options = db.findOptionsOf(item.id, req.body.optionIds); // 是否属于该商品
  if (options.length !== req.body.optionIds.length) {
    return res.status(400).json({ error: 'INVALID_OPTION' });
  }

  const rate  = pricing.discountRateFor(uid, item);              // 由服务端判断
  const total = pricing.total(item, options, qty, rate);         // 由服务端计算

  if (req.body.displayedTotal !== total) {                       // 与展示价不同则
    return res.status(409).json({ error: 'PRICE_CHANGED', total });  // 要求再次确认
  }

  db.insertOrder({ itemId: item.id, qty, total, userId: uid });
  res.json({ ok: true, total });
}

8.1 什么是信任边界

标准定义在 CWE 里。据 CWE-501 Trust Boundary Violation 的说明，信任边界可以理解为贯穿程序划出的一条线：线的一侧数据不受信任，另一侧数据被假定为可信。 同一份文档把校验逻辑的目的界定为「让数据安全地跨越信任边界，从不受信任的状态移动到受信任的状态」。

本文把这个定义收窄到 Web 应用来使用。在 Web 上，信任边界位于浏览器与服务端之间。浏览器一侧产生的一切值都在不受信任的那一侧；这些值跨越网络抵达服务端的瞬间就是跨越边界的瞬间；而跨越边界的数据无一例外都是校验的对象。 页面上绘制的值、脚本算出的结果、装进请求的字段，全都在边界之外。

客户端发送意图，服务端生成结果。「这个商品的这些选项要这么多」是意图，「所以是多少钱」是结果，而结果只能在边界的内侧生成。

由这个定义可以推出三条实务规则。

  1. 客户端发送意图，服务端生成结果。 金额、权限、状态迁移全部属于结果
  2. 从页面上抹掉不等于抹掉了。 隐藏按钮、把输入框设为只读，是易用性的改善而不是控制。控制必须落在处理请求的那一侧
  3. 客户端校验是引导，服务端校验才是控制。 两者都需要，但角色不同。只有客户端校验的字段就是未经校验的字段

判别落在边界上的值，三个问题就够了。

  • 这个值是服务端生成的，还是请求带来的
  • 若是请求带来的，服务端有没有用自己的数据确认它的有效范围
  • 若确认了，是否在 所有入口路径 上都做了确认
  • 这不只是金额的问题。权限等级、卖家标识符、运费、积分抵扣额、优惠券是否适用，凡是 应由服务端策略决定的值 出现在请求体里，都是同样的结构
  • 状态迁移同理。「请改成已送达」这个请求能不能迁移，由服务端的状态机判断，而不是页面
  • 即使有服务端重算，缺少与展示价的比对也会造成用户困惑。前面的示例返回 409 不是出于安全，而是 为了防止展示价与实收价不一致
  • 若有移动应用或外部对接等多个入口路径，重算逻辑必须放在 公共层。按路径各放一份，就变成下一节的问题

回看假设 — ①。 这是最纯粹的形态。「页面算过了所以没错」这句话里，做计算的主体是客户端。

9. 同一代码库内部的不对称 - 不一致的控制等于没有控制

打开真实的代码库，很少能干净地分成「有控制」和「没控制」。远为常见的是 某些端点有而另一些端点没有。最近做的页面里有令牌校验，很久以前做的管理页面里没有。列表查询会确认所有权，下载却不确认。

// 脆弱：按路由逐个挂上。忘记挂就直接敞开了。
app.post('/api/items/create', requireCsrf, requireAuth, createItem);
app.post('/api/items/update', requireCsrf, requireAuth, updateItem);
app.post('/api/items/delete',              requireAuth, deleteItem);  // 漏了
app.post('/api/admin/purge',                            purgeItems);  // 两个都漏了

// 安全：默认拦截，只写明例外。
//       新增路由时什么都不做，默认就是被保护的那一侧。
const CSRF_EXEMPT = new Set([
  'POST /api/webhooks/inbound'   // 仅限不使用会话 Cookie 的路径。用注释留下理由
]);

app.use((req, res, next) => {
  if (SAFE_METHODS.has(req.method)) return next();
  if (CSRF_EXEMPT.has(req.method + ' ' + req.path)) return next();
  return requireCsrf(req, res, next);
});
app.use(requireAuth);   // 认证也用同样的方式默认应用，只把公开路径设为例外

控制的实效由最小值而不是平均值决定，因为防守一方必须守住所有路径，而想通过的一方只需找到一条。

  • 不对称大多源自时间。引入控制之前写的代码没有它，之后写的代码有。引入的时点把代码库切成两层
  • 也源自人。知道同一条规则，落实的习惯却因人而异。规则只写在文档里而没有被代码强制时，偏差就会留下
  • 「内部用的，没关系」这条例外留存得最久。管理页面、批处理端点、临时做的排查路径都属于这一类
  • 解决的方向是 把 opt-in 反转为 opt-out。不再按路由挂控制，而是全局挂上并写明例外。漏掉反而意味着受保护
  • 例外清单 必须放在代码里 才会成为评审对象。放在配置文件或文档里，改动就绕过了评审
  • 同样的原理也适用于输出转义。默认开启转义、只显式标出例外的模板结构，比在每个位置调用函数的结构偏差更小

回看假设 — ① 与 ② 兼有。 控制存在与否本身，取决于客户端从哪条路径进来。那一刻又生出一个 ①：「从哪条路径进来由我们决定」。

10. 这条日志证明了什么 - 不可否认性

到此为止的讨论大体是「挡住什么」。这一节讨论的问题略有不同。没挡住的时候，留下的记录能说明什么。

按照 NIST 术语表引自 SP 800-53 Rev. 5 的定义，不可否认性是指针对实施了某一行为却虚假否认的个人的保护，并提供判定某个个人是否实施了诸如创建信息、发送消息、批准信息或接收消息等特定行为的能力。 同一术语表引用的 CNSSI 4009-2015 表述同旨，NISTIR 4734 则更短：「无法否认对实施特定行为所负的责任。」

把定义拆成两半，实务含义就显现出来。前半是「针对否认的保护」，后半是 「判定某个个人是否实施了该行为的能力」。后半不成立，前半也就不成立。

日志的证明力只在识别控制健全的限度内成立。「用户 X 删除了」这条记录，会因这个 X 从哪里来而变成完全不同的句子。

10.1 日志里的「谁」从哪里来

日志一行里写着用户标识符，并不意味着那个用户实施了该行为。这个标识符 从哪里来，句子的含义就随之改变。

表 5. 按行为者标识符的来源划分的日志证明范围。「前提控制」一列的条目出自 OWASP Session Management Cheat Sheet（会话熵、会话固定防护）与 OWASP Cross-Site Request Forgery Prevention Cheat Sheet（来源校验）。
行为者标识符的来源决定该值的主体前提控制缺少该控制时记录的含义范围
请求体中的字段客户端无请求 自称 是 X
客户端可修改的 Cookie客户端无Cookie 上 写着 X
服务端会话查询结果服务端会话 ID 熵、会话固定防护该会话属于 X
服务端会话查询 + CSRF 校验服务端会话 ID 熵、会话固定防护、请求来源校验请求发起自 X 的页面

表中每一行都与前面的各节一一对应。正如第 4 节所示，若用户标识符放在客户端可修改的 Cookie 里，或者来自请求体，那条记录就无法特定出 X。 不是日志不准确，而是日志记下的对象不是「行为者」而是「请求所主张的值」。记录本身是准确的，只是它指向的对象不同。

需要在第三行上再进一步的理由是 会话固定。按照 OWASP Session Management Cheat Sheet 的定义，会话固定是指攻击者不去获取受害者的会话 ID，而是把会话 ID 设置到受害者浏览器上的攻击。 同一份文档把对策写为强制要求：「会话 ID 必须在该用户会话内权限级别发生任何变化之后更新或再生成」，「会话 ID 的再生成是防止会话固定攻击的强制要求」。权限级别的变化包含从未认证状态转为已认证状态的登录时点。

// 脆弱：登录之后会话标识符照旧。
//       登录前生成的会话值在登录后依然有效。
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();
  req.session.userId = user.id;                // 只是填上了值
  res.json({ ok: true });
}

// 安全：在认证成功的时点重新生成会话标识符。
function login(req, res) {
  const user = authenticate(req.body.id, req.body.pw);
  if (!user) return res.status(401).end();

  regenerateSessionId(req, () => {             // 先前的标识符被废弃
    req.session.userId = user.id;
    req.session.authAt = Date.now();
    res.json({ ok: true });
  });
}

第四行是本节最常被忽略的地方。没有 CSRF 防御时，连「请求是以 X 的会话发出的」这一事实也不代表 X 的意愿。 因为 CSRF 按定义就是 在用户没有意图的情况下发生请求的攻击。OWASP Cross-Site Request Forgery Prevention Cheat Sheet 的定义本身就含着这个结论：已认证用户的浏览器被 诱使 执行非本意的操作。会话是真的，请求也确实从那个浏览器发出，但决定实施该行为的主体不是用户。

10.2 留下什么，不留下什么

OWASP Logging Cheat Sheet 把要记录的条目按何时、何处、何人、何事四条轴整理。何人 对应的字段是 「来源地址，例如用户的设备或机器标识符、用户的 IP 地址」 与 「用户身份（在已认证或以其他方式已知的情况下）」。括号里的条件从句就是本节的浓缩：只在已知的情况下。

同一份文档对日志与不可否认性的关系留下了谨慎的表述。日志支撑 「不可否认性控制（注意：不可否认性这一性质对日志而言难以达成，因为日志的可信度往往仅基于记录方被恰当审计这一事实）」。这意味着要把日志当作证据，得先有日志自身的完整性。所以同一份文档一并要求 「内建篡改检测，以便知道某条记录是否被修改或删除」 以及 「尽快把日志数据保存或复制到只读介质上」。

// 脆弱：行为者取自请求体。日志原样照抄了请求的主张。
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  logger.info('record deleted', {
    actor:    req.body.userId,        // 客户端决定的值
    recordId: req.body.recordId
  });
  res.status(200).end();
}

// 安全：行为者只取自服务端会话，并一并留下判断依据。
function deleteRecord(req, res) {
  const actor = req.session.userId;                   // 服务端知道的值
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);
  if (!rec) return res.status(404).end();             // 所有权校验

  removeRecord(rec.id);
  logger.info('record deleted', {
    at:          new Date().toISOString(),            // 何时
    service:     SERVICE_ID,                          // 何处
    actor:       actor,                               // 何人（以会话为准）
    sessionRef:  hash(req.sessionID),                 // 不留会话原值
    sourceIp:    req.ip,
    userAgent:   req.get('user-agent'),
    action:      'record.delete',                     // 何事
    target:      rec.id,
    outcome:     'success',
    csrfChecked: true,                                // 通过了哪些校验
    authMethod:  req.session.authMethod
  });
  res.status(200).end();
}

不该留下的内容也写明了。OWASP Logging Cheat Sheet 列出 认证密码、会话标识值（可用哈希替代）、访问令牌、加密密钥及其他主要秘密、银行账户或支付卡持卡人数据、敏感个人数据，要求不要记录。上面的示例用哈希代替会话 ID，理由正在于此。既能把同一会话内发生的事串起来看，又让能读到日志的一方无法复用该会话。

10.3 这是为谁设的控制

归纳起来是这样：不可否认性垮掉的系统，其日志无法特定出行为者。 这不是指认谁的过错的句子，而是关于在那种状态下什么可能、什么不可能的技术陈述。识别手段来自客户端时，日志里的「谁」是主张；没有来源校验时，以会话为准的「谁」也不代表意愿；没有会话再生成时，会话本身的归属就不稳。

  • 这是 对用户的保护。当自己没做过的行为以自己账号的记录留存下来时，必须能从技术上说明那条记录的局限
  • 同时也是 对运营方的保护。能准确划分责任归属，运营方才不会被卷进没有依据的纠纷。清楚自家日志能证明什么、不能证明什么的一方处境更有利
  • 因此本节的控制与「防止事故的控制」性质不同。它是 事先决定事故发生时能说出什么的控制
  • 提升记录证明力的顺序与前面各节一致：基于服务端会话的识别 → 会话再生成 → 来源校验 → 日志完整性。从后往前做，前面的就一直敞着
  • 时间也是证明力的一部分。OWASP Logging Cheat Sheet 要求以国际标准格式记录日志的日期与时间。服务器之间时钟错位，事件顺序就无法重建

回看假设 — ① 与 ② 兼有。 识别若依赖 ①，「谁」就降格为主张；会话值若依赖 ②，那个「谁」就可能是别人。

11. CSP 与 SRI - 最后一道防线

前面各节讲的是「边界划在哪里」，这一节讲的是「边界被突破后把损害限制到哪里」。顺序很重要：这一层不能替代前面的控制。

按照 MDN Content-Security-Policy 页面的定义，CSP 是一个允许网站管理员控制用户代理在给定页面上可加载哪些资源的 HTTP 响应头，它有助于防御跨站脚本攻击。 同一页面关于内联脚本写道：「默认情况下，若 CSP 中含有 default-src 或 script-src 指令，则不允许内联 JavaScript 执行。这包括内联 <script> 标签、内联事件处理器属性以及 javascript: URL。」 unsafe-inline 关键字会撤销这层保护，同一页面警告：「开发者应当避免使用 'unsafe-inline'，因为它抵消了设置 CSP 的大部分意义。」

策略存在这件事，与该策略挡住了什么，是两回事。含有 unsafe-inline 和 unsafe-eval 的策略，是响应头在而保护已大幅减少的状态。

# 脆弱：策略是有，可两个关键字把保护撤销了。
Content-Security-Policy: default-src *; script-src * 'unsafe-inline' 'unsafe-eval'

# 安全：每个请求签发新的 nonce，只执行带该 nonce 的脚本。
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';

# 落地阶段：先只接收违规报告，看看会拦下什么。
Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self' 'nonce-PLACEHOLDER_RANDOM_PER_REQUEST';
  report-to csp-endpoint
  • nonce 的值必须 每个请求重新签发。固定的 nonce 与没有策略相差无几
  • MDN 的 Content-Security-Policy 页面写明，指令中含有 nonce 或哈希时 浏览器会忽略 unsafe-inline。这就是为了兼容旧浏览器可以两者并列的原因
  • 据同一页面，哈希源的算法标识符必须是 sha256、sha384 或 sha512 之一
  • strict-dynamic 把 nonce 或哈希赋予的信任扩展到受信脚本动态加载的脚本。带上这个关键字后，主机清单、scheme、'self'、'unsafe-inline' 都会被忽略
  • frame-ancestors 限制哪些父级可以用 <iframe> 等嵌入本页面。它是点击劫持防护的现代形态
  • 落地从 Content-Security-Policy-Report-Only 开始。同一页面说明这个响应头不阻止代码执行、只报告违规，因此用于测试阶段

11.1 SRI 挡住什么，挡不住什么

按照 MDN Subresource Integrity 页面的定义，子资源完整性是一项让浏览器能够验证所获取的资源在传递过程中未被意外篡改的安全特性，其工作方式是提供一个所获取资源必须匹配的密码学哈希。 同一页面把该特性防御的威胁界定为 供应链攻击，具体是指攻击者控制了第三方主机，向其文件注入恶意内容或整体替换文件的情形。机制很简单：浏览器计算收到内容的哈希并与指定值比较，匹配则加载该资源，否则拒绝加载并返回网络错误。

<!-- 脆弱：不做校验就执行外部主机的脚本。
     那个文件一变，我们页面里跑的就是变过的代码。 -->
<script src="https://cdn.example.com/widget.js"></script>

<!-- 安全：只在哈希匹配时执行。
     跨源请求必须使用 CORS 模式，因此 crossorigin 属性是必需的。 -->
<script src="https://cdn.example.com/widget.js"
        integrity="sha384-PLACEHOLDER_BASE64_HASH_VALUE"
        crossorigin="anonymous"></script>

crossorigin="anonymous" 为何必需，同一页面也做了说明。资源默认以 no-cors 模式加载，若在 no-cors 下允许完整性校验，攻击者就能通过反复更换哈希值试探，从而推断出子资源内容的信息。为防止这种信息泄露攻击，浏览器不允许 no-cors 请求使用子资源完整性，没有 crossorigin 的请求将始终失败。

  • SRI 校验的只是 内容是否与指定的哈希一致。原作者从一开始就放进去的逻辑因为哈希吻合，会照常通过
  • 每次版本变更都必须更新哈希。若更新流程自动化到不加审阅就接受新哈希，校验的实效就会减弱
  • 对内容频繁变化的脚本难以适用。这类资源改为自托管是可行的替代
  • CSP 只在 浏览器内部 起作用。对缺失的授权检查、把客户端发来的金额原样保存的处理、可预测的重置令牌，它毫无影响
  • 这两项功能都是在其他防御被突破之后才起作用的层。以这一层存在为由推迟前面的控制，顺序就颠倒了

回看假设 — 本节不修正任何假设。 CSP 与 SRI 是在 ① 与 ② 已经被突破之后收窄损害范围的层。

12. 明知却修不掉的原因

以上内容新鲜的地方不多。所引文档大多早已公开且被广泛参考。那么剩下的问题只有一个：为什么已知的缺陷还在持续存在。 不是「不知道」，而是另有一套「知道了也修不掉」的结构。

  • 一打开就坏。 给老代码库全局应用 CSRF 保护，会让所有没加令牌的既有表单和异步请求全部被拒。这是用户立刻能看见的故障，于是开启控制这件事本身就变成了背上回归风险的事
  • 动正在跑的代码的心理负担。 自动化测试越薄，这份负担越重。无法准确圈出改动影响范围时，修反而看起来比放着更危险
  • 安全债在事故之前看不见成本。 与性能问题或功能缺陷不同，它留着的时候不会出现在任何指标上。成本读作零的条目在优先级会议上排不进去
  • 没有承接主体时，受理不会变成处置。 即使有接收通报的窗口，若没有指定把通报转成代码变更的负责人，就只会积下受理记录。这源自角色定义上的空白
  • 与功能开发争优先级。 同一批人做两件事，而只有其中一件在排期上有名字
  • 不知道范围。 为修一处打开代码，发现同样的写法多到数不清，于是连着手本身也被推后。这一条直接连到下一节

这套结构确实反映在结果上，可以用公开资料确认。Project Zero 在 2022 年 6 月 30 日公开的中期统计里写道：「截至 2022 年 6 月 15 日，2022 年被检测并公开为在野利用的 0-day 有 18 起。」 以及 「其中至少 9 起是先前已修补漏洞的变种。」 同一篇文章的结论句是：「2022 年上半年观测到的 0-day 中，至少有一半本可通过更全面的修补与回归测试加以预防。」 关于再次被利用所需的时间也有记述：「2022 年的 0-day 中有 4 起是 2021 年在野 0-day 的变种。距原始在野 0-day 被修补仅仅 12 个月，攻击者就带着原漏洞的变种回来了。」

期限这套机制为何存在，也能在同一脉络下读出来。Project Zero 的 Vulnerability Disclosure Policy 规定 厂商在收到通知后 90 天内向用户提供补丁，并在 补丁提供满 30 天后公开细节。若 90 天内难以完成但在额外 14 天内可以完成，可以给予宽限期；若有实际被利用的证据，则 以 7 天政策取代 90 天政策，此时的宽限期为 3 天。

把期限写进文件这件事本身，就包含着一个经验判断：没有期限，修复就会拖延。

表的最后一列才是实务上有用的部分。从成本低、回归风险低的做起，着手就不会卡住。 加三个 Cookie 属性通常是一处配置改动，回退也容易。反过来把全局 CSRF 放在清单第一项，它等着的时候下面的也一起停住。

回看假设 — 本节的层级不同。 ① 与 ② 是代码的假设，本节讨论的是组织的约束。不过结果是一样的：边界一直没被划出来。

13. 说是修好了却没变 - 不完整的修复

有时修复做了，同样的路径却还在。问题出在 确定修复范围的方式 上，形态大体有四种。

  1. 只治症状，根因照旧。 确认某个页面上的值被原样渲染，就只在那个页面加转义。渲染同一个值的其他页面、返回同一字段的其他响应都没动
  2. 缺少变种分析。 没人去数同样的写法在代码库里还有多少处。只修被报告的那一处，其余照旧留着，而这些其余就成了下一次报告
  3. 只修客户端，服务端照旧。 隐藏按钮、把输入框改成只读、加上页面侧校验。处理请求的代码一动没动
  4. 只关掉一条路径，另一条留着。 从某个响应里删掉了字段，可承载同样信息的其他端点、错误消息、被缓存的响应、下载文件还在

从信任边界的视角看，客户端的修改不是防御。从页面上移除按钮是让这个请求更难发出，而不是在这个请求抵达时拒绝它。

// 修复前：对没有权限的用户，删除请求也会被处理。
function deleteRecord(req, res) {
  removeRecord(req.body.recordId);
  res.status(200).end();
}

// 不完整的修复：在页面上把按钮藏了起来。
// 上面的服务端代码原封不动。边界还在原处。
if (!currentUser.isOwner) {
  document.querySelector('#delete-btn').style.display = 'none';
  document.querySelector('#delete-btn').disabled = true;
}

// 完整的修复：在处理请求的那一侧做判断。
function deleteRecord(req, res) {
  const actor = req.session.userId;
  if (!actor) return res.status(401).end();

  const rec = db.findRecordOwnedBy(req.body.recordId, actor);   // 所有权校验
  if (!rec) return res.status(404).end();

  removeRecord(rec.id);
  res.status(200).end();
}
// 页面侧隐藏按钮可以保留。只是那属于易用性，不是控制。

关于第二种形态，前一节引用的数字本身就是依据。Project Zero 记录 2022 年上半年 18 起中至少 9 起是先前已修补漏洞的变种，并得出 至少一半本可通过更全面的修补与回归测试加以预防 的结论，说明这一形态不是个别案例而是反复出现的模式。这也是为什么修一处时，在整个代码库中检索并清点同样写法的步骤 应当属于修复工作的一部分。

13.1 流程上产生的验证空白

撇开技术形态，确认是否修复的 流程 上也会产生同一种空白。结构很简单：缺陷被受理，转给开发主体，开发主体回复「已修复」，案件据此结案。这条流程里 没有一个环节去核实「已修复」这句陈述。

  • 这不是回复是否属实的问题。回复即便 完全出于诚意，也可能落进上面四种形态之一。判断已经修好而回复、实则变种仍在，是最常见的情形
  • 没有复验，结案就不是一种状态而只是流程的终点。可结案这个标记会造成 「已经安全了」的误认。从清单上消失的条目不再出现在任何人的队列里
  • 复验的成本通常低于首次确认，因为已经知道该看哪里。即便如此，流程里没有这个环节就不会有人去做
  • 修复确认必须看两个地方：被报告的那一处 与 同样写法的其他各处。只看前者，第二种形态就会径直通过

还有一点值得区分。致谢名单不是修复的证据。 被列进安全致谢页面或贡献者名单，是 受理与知悉的证据。它记录的是知道了这个缺陷，而不是这个缺陷已被移除。这里存在一处不对称：知悉几乎不花成本，修复要花成本。 于是知悉被迅速标记出来，而修复缓慢推进。把两个指标当成同一件事来读，就会把实际状态估计得比实情更好。

回看假设 — ①。 第三种形态正是 ①。改动页面的修复把「客户端改不了」这个假设原样留着，又在这个假设之上叠了一层。

14. 30 分钟自查自己站点的方法

本节内容仅限于本人运营或已获明确授权的站点。未经许可检查他人的服务可能引发法律问题。 下面的方法全部停留在用浏览器开发者工具 读取自己站点响应 的层面，不包含操纵请求或反复尝试的内容。

这 30 分钟回答的不是一份缺陷清单，而是「我们的系统现在立在哪个假设上」。

14.1 5 分钟 - Cookie 属性

在开发者工具的 Application（或存储）标签页里打开 Cookies。会话 Cookie 那一行要看四样东西。

  • HttpOnly 这一列有没有标记。没有的话脚本就能读到这个值
  • Secure 这一列有没有标记
  • SameSite 这一列的取值是什么。为空表示交给了浏览器默认值。若是 None，就得能说清这个 Cookie 为什么必须跨站发出
  • 会话 Cookie 的 值 是不是人能读懂的形式。看得到用户编号、邮箱地址或权限名，就是第 4 节描述的状态

14.2 10 分钟 - 响应头

在 Network 标签页选中文档请求（最上面那条 HTML 响应），查看 Response Headers。

  • 有没有 Content-Security-Policy。没有的话，第 11 节那一层就完全不存在
  • 若有，里面是否含 'unsafe-inline' 或 'unsafe-eval'。含有的话就是 MDN 警告的那个状态
  • Set-Cookie 各行的属性与 14.1 里看到的是否一致。多个 Cookie 被设成互不相同的属性是常见情况
  • 登录前后会话 Cookie 的值有没有变。这是能用眼睛确认第 10 节的会话再生成是否在执行的位置

14.3 10 分钟 - 外部脚本

数一数页面从哪里取代码。下面是在 自己站点 的控制台里运行的只读确认代码片段。它不改动任何东西，只打印清单。

// 只读：列出来自外部主机且没有 integrity 的脚本。
[...document.querySelectorAll('script[src]')]
  .filter(s => new URL(s.src, location.href).origin !== location.origin)
  .map(s => ({
    src:       s.src,
    integrity: s.integrity || '(无)',
    crossorigin: s.crossOrigin || '(无)'
  }))
  .forEach(row => console.log(row));

// 只读：确认是否通过 meta 标签设置了 CSP。
console.log(
  document.querySelector('meta[http-equiv="Content-Security-Policy"]')?.content
  ?? '(没有 meta CSP - 请查看响应头一侧)'
);
  • 外部主机清单若比预想的长，那么其中每一个都是能在页面内执行代码的主体
  • 没有 integrity 的条目，那个文件一变就照变后的样子执行
  • 若资源内容变动频繁以致无法挂 SRI，就把能否改为自托管列入评估对象

14.4 5 分钟 - 重置令牌的形态

用自己的账号申请密码重置并拿到链接。要看的是令牌的 形态 与 寿命。

  • 长度是否足够，用的是什么字符集。若是十六进制字符串，是否超过第 5 节标准所要求的最少位数
  • 连续申请两次，两个值之间有没有肉眼可见的规律。前半段相同或只有末尾略有变化，就有可能用了时间或序号作材料
  • 把用过一次的链接再打开会怎样。若直接就出现重置界面，说明没有一次性处理
  • 完成重置之后，在另一个浏览器里开着的既有登录是否照旧保持
  • 用不存在的地址申请重置时的响应措辞，与存在的地址时是否相同

回看假设 — ① 与 ②。 四个条目中只要有一个依赖客户端一侧的情形，那一处就是 ①；重置令牌的形态若能看出规律，那一处就是 ②。

未能确认的内容

  • 重置令牌的具体有效期。 OWASP Forgot Password Cheat Sheet 明确要求令牌在使用后失效，但 没有给出几分钟或几小时这样的具体数值。这就是正文只写「较短的有效期」的理由

  • 各浏览器 SameSite 默认值的现状。 MDN 的 Set-Cookie 页面只写了「部分浏览器把 Lax 当作默认值」。哪款浏览器从哪个版本起如何应用，需要各自在目标环境中确认
  • 全行业补丁延迟的中位数与未修复率。 各公开资料的样本与统计口径不同，因而没有引用为单一数值。第 12 节与第 13 节引用的数字是 Project Zero 就自身追踪对象发布的值，不向该范围之外一般化

  • NIST 术语表中的信任边界词条。 在 NIST 术语表中未能确认到相应词条。因此第 8 节的标准定义引用了 CWE-501 的说明，而收窄到 Web 的定义则注明是本文的工作定义
  • 本文的代码示例。 它们是为说明而写的形态，并未在特定运行环境中验证过。函数名与路径全部是虚构的值，实际落地时使用各自框架提供的功能会更好

常见问题

Q1. Cookie 里直接能看到用户编号，这算问题吗

Cookie 由服务端签发，但保存在客户端。用户可以在开发者工具里改掉这个值再发回来，所以 只要服务端有代码用这个编号去查数据，被查对象的所有者与请求发起者之间的关系就一直没人验证过。OWASP Insecure Direct Object Reference Prevention Cheat Sheet 把这类缺陷归纳为三个要素：对象、指向该对象的引用，以及 缺失的对象级授权检查。OWASP Session Management Cheat Sheet 要求会话 ID 的取值必须 没有含义 以防信息泄露，且绝不能包含敏感信息或个人身份信息，并写明为抵抗暴力猜测 至少需要 64 位熵。相应的处置有两条。第一，Cookie 里只放没有含义的会话标识符，用户身份由服务端凭该值查出。第二，查询时把所有者条件写进查询本身，只找属于当前用户的记录。把标识符换成难猜的值并不是替代方案，同一份文档明确写着即使使用复杂标识符，访问控制检查依然是必需的。

Q2. 把 SameSite 改成 Strict 之后还需要 CSRF 令牌吗

OWASP Cross-Site Request Forgery Prevention Cheat Sheet 明确表示不要把 SameSite 当作单独的防御，而应作为 纵深防御的一层。理由有三个。第一，Lax 只拦截不安全的方法，如果改变状态的操作通过 GET 暴露出来，请求会照常通过。第二，SameSite 的判定单位是 可注册域名 而不是源，同一域名下的其他主机会被当作同站。第三，各浏览器的默认值不同。MDN 的 Set-Cookie 页面只写了部分浏览器在未指定 SameSite 时把 Lax 当作默认值，并说明作为默认值应用的 Lax 是更宽松的版本，只要 Cookie 设置后不超过两分钟，POST 请求也会带上它。Strict 在很大程度上解决了第一点和第三点，但第二点仍然存在。因此即便会话 Cookie 设为 Strict，推荐的配置仍是在改变状态的请求上同时使用同步令牌或签名的双重提交令牌。

Q3. 已经加了 HttpOnly，为什么还说 XSS 是问题

HttpOnly 只挡住一件事：脚本通过 document.cookie 读取 该 Cookie 的值。MDN 的 Set-Cookie 页面写明，即使是用 HttpOnly 创建的 Cookie，在 JavaScript 发起的请求中依然会被送出。也就是说只要页面里有代码在跑，读不到 Cookie 的值也照样能构造带着这个 Cookie 的请求。用这个值取代了偷这个值。 出于同样的原因，OWASP Cross-Site Request Forgery Prevention Cheat Sheet 着重写明 XSS 会让所有 CSRF 缓解手段失效。页面里运行的代码拥有与正常界面相同的权限，因此能从 DOM 里读出令牌并附到请求上。归纳起来，HttpOnly 是收窄一条外泄路径的有用控制，而 XSS 本身的对策是输出转义。OWASP Cross Site Scripting Prevention Cheat Sheet 建议重构代码，移除对 innerHTML 这类不安全汇点的引用，改用 textContent 或 value。

Q4. 密码重置链接用过一次之后还能打开，这样可以吗

OWASP Forgot Password Cheat Sheet 明确要求重置令牌 在使用之后失效。如果用过一次的链接再次打开还能进入重置界面，说明这条要求没有落地。之所以要紧，在于这个令牌的性质。重置令牌在有效期内替代了认证凭据，CWE-640 把这类缺陷命名为 Weak Password Recovery Mechanism for Forgotten Password，其父项是 CWE-1390 Weak Authentication 与 CWE-287 Improper Authentication。也就是说 它被归类为认证缺陷。链接可能留在邮箱、浏览器历史、服务器访问日志、代理日志和 Referrer 中，一旦可以重复使用，这些残留的每一处都会成为账号接管的路径。还有三件事值得一并确认：令牌是否设置了有效期，存储中保存的是哈希还是原文，以及重置完成后既有的登录会话会怎样。同一份文档建议询问用户是否要使所有既有会话失效，或者自动使其失效。

Q5. 日志里留下了用户 ID，能据此认定就是那个人做的吗

取决于这个 ID 从哪里来。如果值来自请求体或客户端可以修改的 Cookie，那条记录的含义只到 请求自称是该用户 为止。如果值来自服务端会话查询，含义可以到 会话属于该用户 为止。从这里还需要两样东西。OWASP Session Management Cheat Sheet 把会话固定定义为攻击者不去获取受害者的会话 ID，而是把会话 ID 设置到受害者浏览器上，并写明会话 ID 的再生成是防止会话固定攻击的强制要求。没有它，会话本身的归属就不稳。再者，如果没有 CSRF 防御，会话是真的也不代表那个请求表达了用户的意愿，因为 CSRF 按定义就是在用户没有意图的情况下发生请求的攻击。NIST 术语表引自 SP 800-53 Rev. 5 的不可否认性定义中，包含 判定某个个人是否实施了特定行为的能力。这个能力只在识别控制健全的限度内成立。

结论：本文主张的四件事

不做总结，以命题收尾。本文主张的有四条，并一并标出支撑各条的章节。

  1. 把客户端来的值当作依据的代码，无论那个值是什么，都处于未经校验的状态。 表单值、data- 属性、Cookie、请求体、请求头全都属于这一类。依据：第 4 节（Cookie 中的用户标识符）、第 8 节（信任边界的定义与服务端重算）、第 13 节（只修了客户端的修复）。
  2. 可以预测的值不是秘密。把某个值当作秘密对待，要确认到生成它的随机源才算成立。 依据：第 5 节（重置令牌与 CWE-640、MDN 关于 Math.random() 的明示）、第 10 节（会话值的归属）。
  3. 单项评级低的缺陷组合起来会造出新的路径，而按条目的检查表捕捉不到这些路径。 依据：第 3 节（CSRF 令牌缺失与 SameSite=None 的组合）、第 9 节（同一代码库内部的不对称）。
  4. 识别控制垮掉的系统，其日志无法特定出行为者。这既是对用户的保护，也是对运营方的保护。 依据：第 10 节（不可否认性的定义、日志条目按来源划分的证明范围，以及会话固定与 CSRF 各自对证明力的影响）。
