AI를 위한 대한민국 대중교통 경로·비용 탐색 MCP 서버 — 에이전트가 길을 찾다

오픈소스 나어려(naeryeo)로 보는 MCP의 실용성 - 지하철·버스 데이터를 에이전트에게 쥐여주면 무엇이 달라지나

2026-07-03 개발/인프라

서론: 우리는 왜 이 작은 프로젝트에 주목해야 하는가

2026년 7월 초, 개발자 GyeongHoKim이 GitHub에 나어려(naeryeo)라는 오픈소스 프로젝트를 공개했다. '우솝, 내려'라는 구어체 표현에서 이름을 따온 이 도구는 대한민국의 지하철·버스 경로와 예상 요금을 검색해 주는 커맨드라인(CLI) 도구이자, 동시에 MCP(Model Context Protocol) 서버다. GeekNews(news.hada.io)의 Show GN 코너에도 소개되며 12점을 받는 등, 규모는 작지만 꾸준한 관심을 받았다.

스타 수나 화제성만 놓고 보면 이 프로젝트는 결코 크지 않다. 그런데도 본인이 이 글에서 다루려는 이유는 따로 있다. naeryeo는 "MCP가 실제로 무엇을 바꾸는가"를 아주 작고 구체적인 단위로 보여주는 사례이기 때문이다. 거대 플랫폼의 공식 MCP 서버가 아니라, 한 개발자가 자신의 불편(청년 주택 신청 시 출퇴근 거리·비용을 손으로 계산해야 했던 경험)에서 출발해 만든 도구가 어떻게 AI 에이전트 생태계의 한 조각으로 편입되는지를 이 사례가 보여준다. 이 글은 naeryeo 소개를 넘어, MCP라는 프로토콜이 왜 지금 이렇게까지 확산되고 있는지, 그리고 한국이라는 특수한 대중교통 데이터 환경에서 이런 도구가 왜 필요한지를 본인 관점에서 분석한다.

1. 나어려(naeryeo)란 무엇인가

1.1 무엇을 하는 도구인가

naeryeo는 "강남역에서 홍대입구역까지 어떻게 가?" 같은 질의에 최적 경로, 환승 정보, 소요 시간, 예상 요금을 알려준다. CLI로 쓰면 naeryeo route --from "강남역" --to "홍대입구역" 한 줄로 끝나고, MCP 서버로 등록하면 Claude Desktop이나 Claude Code 같은 AI 클라이언트에서 자연어로 같은 질문을 던질 수 있다. 핵심 로직은 Go로 작성됐고(전체 코드의 약 3분의 2), 배포 스크립트가 셸로, npm 패키지 래퍼가 자바스크립트로 구성돼 있다. CLI와 MCP 두 모드가 동일한 내부 로직(internal/core)을 공유한다는 점이 이 프로젝트 설계의 핵심이다 - 인터페이스만 다를 뿐 경로 탐색 엔진은 하나다.

1.2 API 조합 - ODsay + 카카오 지오코딩

naeryeo는 직접 대중교통 데이터를 수집하지 않는다. 대신 두 개의 기존 상용 API를 조합한다. 경로 탐색은 대중교통 전문 API인 ODsay가 맡고, "강남역" 같은 역명이 아니라 건물명·주소로 질의할 때의 좌표 변환(지오코딩)은 카카오 로컬 API가 맡는다. 프로젝트 README는 이 조합을 택한 이유로 카카오맵·네이버지도가 제3자 개발자에게 대중교통 경로탐색 API를 공개하지 않는다는 점, 그리고 구글맵은 규제상 국내에서 쓰기 어렵다는 점을 든다. 후자는 한국이 안보를 이유로 정밀 지도 데이터의 국외 반출을 오랫동안 제한해 온 정책과 맞닿아 있으며, 그 결과 구글맵의 국내 대중교통 길찾기 기능이 다른 나라만큼 강력하지 않다는 사실은 이미 여러 해 전부터 널리 알려져 있다. naeryeo는 이런 빈틈을, 공공데이터포털이 제공하는 원시 도착정보 API가 아니라 이미 경로 탐색까지 가공해 주는 ODsay라는 상용 레이어 위에서 메운 셈이다.

1.3 두 가지 통합 방식 - Skills와 MCP

naeryeo는 Anthropic이 최근 정착시킨 Claude Skills(SKILL.md 형식, npx skills add로 설치)와 MCP 서버 두 방식을 모두 지원한다. Skills는 필요할 때만 컨텍스트에 로드돼 토큰을 아끼는 방식이고, MCP는 stdio 기반으로 항상 연결돼 있는 도구 서버다. 설정은 claude_desktop_config.json에 {"mcpServers": {"naeryeo": {"command": "naeryeo", "args": ["mcp"]}}} 몇 줄을 추가하는 것으로 끝난다. API 키는 naeryeo setup 한 번으로 OS 기본 키체인(Keychain·Credential Manager·Secret Service)에 암호화 저장되고, 설정 파일이나 MCP 통신 어디에도 평문으로 노출되지 않는다.

2. MCP가 왜 유용한가 - LLM에 실시간 도구를 연결한다는 것

2.1 MCP 이전의 문제 - M×N 통합

거대언어모델은 태생적으로 학습 시점 이후의 정보나, 애초에 학습 데이터에 없던 사설·실시간 데이터를 모른다. 오늘 강남역에서 홍대입구역까지 지하철이 몇 분 걸리고 요금이 얼마인지는 모델 가중치 안에 들어 있지 않다. 이 문제를 풀려면 모델이 외부 시스템을 "호출"할 수 있어야 하는데, MCP 이전에는 AI 애플리케이션(호스트)마다, 그리고 연동하려는 서비스마다 각각 다른 통합 코드를 새로 짜야 했다. 서비스가 N개, AI 애플리케이션이 M개라면 이론상 M×N개의 커스텀 연동이 필요한 셈이다.

2.2 MCP 이후 - 표준 커넥터

Anthropic이 2024년 11월 공개한 MCP는 이 문제를 M+N으로 줄인다. 서비스 제공자는 자신의 기능을 한 번만 MCP 서버로 감싸면 되고, AI 애플리케이션은 MCP 클라이언트를 한 번만 구현하면 그 서버를 지원하는 모든 서비스와 통신할 수 있다. 흔히 "AI 애플리케이션을 위한 USB-C"에 비유되는데, 적절한 비유다 - 기기마다 다른 충전 단자를 쓰던 시절에서 하나의 규격으로 통일된 것처럼, MCP는 각 서비스가 저마다 다른 플러그인 API를 만들던 관행을 표준 프로토콜(호스트-클라이언트-서버 구조, tools·resources·prompts라는 세 가지 원시 타입)로 정리한다. naeryeo가 딱 이 구조를 그대로 따른다 - "경로 탐색"이라는 하나의 tool을 MCP 서버로 감싸 놓았을 뿐인데, Claude Desktop이든 다른 MCP 호환 클라이언트든 별도 연동 코드 없이 곧바로 쓸 수 있다.

2.3 확산 속도가 말해주는 것

업계 보도를 종합하면 2026년 상반기 기준 MCP는 Anthropic뿐 아니라 OpenAI·Google·Microsoft·AWS 등 주요 AI 벤더 대부분이 지원하는 사실상 표준으로 자리잡았고, GitHub·Slack·Notion·PostgreSQL 같은 주요 서비스도 공식 MCP 서버를 제공한다고 알려져 있다. 다운로드·스타 수 같은 구체적 수치는 집계 시점과 출처에 따라 편차가 있어 단정하기 조심스럽지만, 방향성만은 뚜렷하다 - 한 프로토콜을 여러 벤더가 동시에 채택하는 일은 AI 도구 생태계에서 드문 합의다.

3. 대중교통 데이터를 에이전트가 다루면 가능해지는 것

3.1 여행 계획을 대화로 끝내기

MCP가 없던 시절이라면 "강남역에서 홍대까지 얼마나 걸려?"라는 질문에 챗봇은 일반적인 요약을 하거나, 정확한 실시간 답을 주지 못했을 것이다. naeryeo가 MCP로 연결되면 에이전트는 실제 ODsay 경로 데이터를 호출해 정확한 소요 시간·환승·요금을 답하고, 이어서 "그럼 3곳을 하루에 도는 최단 동선을 짜줘" 같은 다단계 요청도 처리할 수 있다. 각 구간의 경로 도구 호출을 에이전트가 스스로 반복하고 결과를 조합하는 방식이다. 이건 단순 정보 조회가 아니라, 여러 번의 도구 호출을 하나의 대화 흐름 안에서 계획하고 실행하는 에이전트적 행동이다.

3.2 비용 최적화와 실사용 사례

naeryeo가 예로 든 실사용 사례는 인상적이다 - 청년 주택 신청 시 AI로 출퇴근 거리와 비용을 계산하는 용도다. 한국의 여러 청년·신혼부부 주택 지원 사업은 직장까지의 거리나 통근 비용을 심사 요건 혹은 참고 자료로 요구하는 경우가 있는데, 이를 매물 후보마다 손으로 조회하는 대신 에이전트에게 "이 다섯 개 매물 중 회사까지 대중교통비가 가장 적게 드는 곳은?"이라고 물어 한 번에 비교할 수 있다. 이런 시나리오는 여행 계획보다 오히려 더 한국적이고 실용적인 응용이며, "정보 조회"가 아니라 "의사결정 보조"로 MCP 도구가 쓰이는 사례라는 점에서 눈여겨볼 만하다.

3.3 다른 도구와의 조합 가능성

MCP의 진짜 힘은 서버 하나가 아니라 여러 서버를 동시에 연결할 때 나온다. 캘린더 MCP 서버와 naeryeo를 함께 연결하면 "다음 주 화요일 오후 3시 미팅에 늦지 않게 가려면 몇 시에 출발해야 해?"를 한 번에 물을 수 있고, 지도·날씨 서버까지 더하면 우천 시 대체 경로까지 고려한 답을 받을 수 있다. 이는 naeryeo 하나만의 가치가 아니라, MCP 생태계가 커질수록 각 서버가 조합되며 만들어내는 승수 효과다.

4. 로컬·오픈소스 도구의 가치

4.1 이동 데이터는 민감하다

어디서 어디로 이동하는지는 위치 데이터 중에서도 민감한 축에 속한다. naeryeo는 stdio 기반으로 로컬에서 실행되고, API 키는 OS 키체인에만 저장되며 별도의 중개 서버로 전송되지 않는다고 밝히고 있다. 즉 "오늘 회사에서 병원까지 어떻게 가?" 같은 질의가 naeryeo를 만든 개발자의 서버나 제3의 SaaS를 거치지 않고, 사용자의 기기에서 ODsay·카카오 API로 직접 나간다(이 두 API 자체에는 여전히 요청이 가지만, 최소한 중간에 낀 별도의 데이터 수집 계층이 없다는 뜻이다).

4.2 비용과 통제

MIT 라이선스로 공개된 코드는 누구나 감사하고, 필요하면 포크해 자신의 요구에 맞게 고칠 수 있다. 상용 SaaS형 "AI 여행 비서" 서비스를 구독하는 대신, 무료로 발급받는 ODsay API 키 하나로 같은 기능을 로컬에서 무기한 쓸 수 있다는 점도 실질적인 이점이다. 다만 이 자유는 공짜가 아니다 - 바이너리 설치, API 키 발급, 설정 파일 편집까지 개발자 친화적인 절차를 직접 거쳐야 하며, 아직 비개발자가 원클릭으로 쓸 수 있는 수준은 아니다.

5. MCP 생태계 확산이 보여주는 것 - 롱테일의 힘

MCP를 다루는 기사 대부분은 GitHub·Slack·Salesforce 같은 거대 서비스의 공식 서버를 예로 든다. 그런데 본인이 보기에 프로토콜의 진짜 저력은 그런 대형 사례보다, naeryeo처럼 한 개발자가 만든, 특정 국가·특정 데이터에 특화된 좁은 서버가 얼마나 쉽게 생겨나고 배포되는지에서 드러난다. MCP가 없었다면 이런 프로젝트는 "그냥 CLI 도구"로 끝났을 가능성이 크다. 표준 프로토콜 덕분에 이 CLI가 별다른 추가 작업 없이 AI 에이전트의 도구로도 즉시 승격됐다. 이런 롱테일 서버가 지역·언어·산업별로 쌓일수록, MCP 생태계는 소수 빅테크의 공식 통합을 넘어 각 나라·각 도메인의 실제 데이터에 뿌리내리게 된다. 한국 대중교통이라는 좁은 영역에서 이미 이런 일이 일어났다는 사실 자체가, 앞으로 다른 나라·다른 공공 데이터 영역에서도 비슷한 프로젝트가 반복될 것이라는 합리적 근거가 된다.

6. 한계와 주의점

과장하지 않는 게 중요하다. 몇 가지 명확한 한계가 있다. 첫째, naeryeo는 ODsay라는 상용 API에 의존하므로 무료 티어의 호출량 제한이나 요금 정책 변경에 영향을 받을 수 있다. 둘째, 로컬 stdio 기반 MCP 서버는 현재 Claude Desktop·Claude Code 같은 데스크톱 클라이언트에서만 곧바로 동작하고, 모바일 앱이나 웹 챗봇에서 쓰려면 별도의 원격 배포(HTTP 기반 MCP 서버 등)가 필요하다. 셋째, 설치·설정에 API 키 발급과 JSON 설정 파일 편집이 필요해 비개발자 접근성은 아직 낮다. 넷째, 경로·요금 계산의 정확도는 결국 ODsay 원본 데이터의 갱신 주기(월 2회로 알려짐)에 달려 있어, 실시간성이 완벽하지는 않다. 이런 한계는 naeryeo 개인의 문제라기보다 이 시점 MCP 생태계 전반의 성숙도를 보여주는 지표에 가깝다.

결론: 작은 도구가 보여주는 큰 흐름

naeryeo 자체는 스타 수백 개짜리 대형 프로젝트가 아니다. 그러나 이 도구가 보여주는 패턴 - 기존 상용 API를 얇게 감싸 MCP 인터페이스로 재포장하고, 이를 통해 CLI 도구가 AI 에이전트의 도구로 승격되는 흐름 - 은 2026년 하반기 AI 생태계에서 반복될 가능성이 높은 템플릿이다. 개발자에게는 "우리 API에도 MCP 서버 하나 얹으면 새로운 사용자층(AI 에이전트를 쓰는 사람들)에 닿을 수 있다"는 신호이고, 일반 사용자에게는 "이제 대중교통 경로 조회조차 대화 한 줄로 끝날 수 있다"는 변화의 증거다. 본인은 이런 좁고 실용적인 MCP 서버가 앞으로 한국의 다른 공공 데이터 영역(부동산 실거래가, 기상, 행정 정보 등)으로도 확산될 것으로 본다. 2026년 7월 기준으로는 아직 개발자 중심의 실험 단계이지만, 설치 마찰이 줄어들수록 - 예컨대 원클릭 설치 방식이 보편화될수록 - 이런 도구는 일반 사용자에게도 성큼 다가올 것이다.
