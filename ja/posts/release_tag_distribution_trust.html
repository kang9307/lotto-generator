ビルドが申請フォームの前で止まるとき

昨日まで問題なく回っていたパイプラインが、今朝は手ぶらで戻ってくる。スクリプトもリポジトリのアドレスもそのままなのに、git fetch --tags が新しいタグを一つも取ってこない。リモートには前回のリリースまでしかなく、今回のバージョンに当たる名前がない。上流が落ちたわけでも権限が切れたわけでもない。ただその名前がもうそこに現れないだけだ。

代わりに案内が出ている。様式を埋めて申請すると、数日後、ときには数週間後にファイル一つを受け取るリンクが届く。ファイルは完全で、コードもすべて入っている。それでもパイプラインは止まったままだ。

この食い違いが本記事の主題である。配布経路を変える作業は、外から見ればダウンロード方法を一つ取り替えることに見える。実際にはその経路に乗っていたものが一緒に降りてくる。固定された参照、ハッシュで成り立っていた検証、自動化が取りに行っていたアドレス、第三者が同じものを手に入れられるという前提。この四つはタグとリリースアーカイブという形式に既定で付いていたものであって、別に構築したものではない。だから形式が変わると静かに一緒に消える。以下はその一覧だ。

確認された事実

2026年8月8日、GrapheneOSプロジェクトが自前のマストドンアカウントに短い投稿をした。要旨は、グーグルが一部のソースコードについてGitタグを公開する方式を、フォームで申請したうえでドライブから受け取る方式に置き換えたこと、申請処理が次第に遅くなっていること、そして自分たちはこれをGPLv2違反と見ている、というものである。核となる一文は Google replaced pushing Git tags for certain source code with obtaining source code via Google Drive after making a request through Google Forms. だった。

二日後にアンドロイド専門メディアの報道が出た。対象はピクセル端末のカーネルソースと特定され、手続きはグーグルフォームの提出とドライブリンクの受領であり、数時間で済んでいたものが数週間かかるというプロジェクト側の記述と、更新履歴が読みにくい単一ファイルに圧縮されるという指摘が併せて掲載された。当該報道はグーグルに問い合わせたが掲載時点まで回答がなかったと明記している。

ハッカーニュースの議論では技術的な層がもう少し見えた。ピクセルカーネルとユーザースペースドライバのリポジトリが併せて言及され、アンドロイドのビルドシステムがコンポーネントごとのGitリポジトリを前提としてGitコマンドを実行するため、単一のtarball形式ではそのまま噛み合わないという指摘が出た。

タグはURLではなく固定された参照である

Gitタグを「リリースごとに貼るラベル」程度に理解していると、今回の変化の大きさがつかみにくい。タグが実際にしているのは、名前一つで内容全体を一つの値に束ねることだ。

構造をほどいてみよう。タグはコミットを指し、コミットはSHAハッシュで識別され、そのコミットはツリーオブジェクトを、ツリーは下位ツリーとファイルのブロブをまたハッシュで指す。最上段のハッシュ一つが下のすべてを覆うマークル構造だ。だから v1.2.3 という名前を知る二人は、ファイルをやり取りしなくても同じ内容を持っているか確認できる。一バイト違えば値が変わる。ここに注釈付きタグと署名が加わると、「このスナップショットをこの名前で呼ぶと決めた主体は誰か」という層が増える。内容が正しいかと出所が正しいかは別の問いであり、両方が必要だ。

整理すると、公開タグは四つを同時に提供している。

  • 名前と内容の固定 — 同じタグ名はいつ照会しても同じコミットを指すという慣行の上で、あらゆるツールが動いている
  • 内容の自己証明 — ハッシュが内容から計算されるため、別途の一覧がなくても完全性が成り立つ
  • 出所の証明 — 署名付きタグは配布主体を暗号学的に確認できるようにする
  • 対称性 — 誰がいつ要求しても同じアドレスから同じものが得られる。検証を第三者が再現できるという意味だ

リクエスト方式に変わるとファイル自体は残る。残りの三つは既定から任意へ降りる。配布者が公開チェックサムを掲示し、署名を付け、すべての要求者に同一の成果物を保証するならかなり復元されるが、それは追加で設計すべきことであって形式に付いてくることではない。

アーカイブのハッシュが実際に保証するもの

パッケージングをした人にとって、ソースはファイルではなく「アドレス+チェックサム」の対である。形は生態系ごとに違っても構造は同じだ。

  • Arch系の PKGBUILD — source=() と sha256sums=() が並んで宣言される
  • Homebrewのformula — url のすぐ下に sha256 が付く
  • Nix — fetchurl 系が引数としてハッシュを要求し、違えばビルドが始まりすらしない
  • RPM・Debianのパッケージング — Source0 や debian/watch で上流を指定し、ファイルごとのハッシュを記録する
  • 言語生態系 — モジュールプロキシやロックファイルが依存ごとにハッシュを固定する

ここでよく潰れる区別がある。チェックサムは、途中で壊れていないかを見る転送の完全性と、自分が確認して承認したそのバイト列かを見る同一性の合意を同時に担う。前者はリクエスト方式でもそのまま働くが、後者は他者も同じアドレスから同じ値を出せるときにだけ意味を持つ。

二つ目が核心だ。パッケージャがレシピにハッシュを埋め込むのは、自分のダウンロードが壊れていないか確かめるためではなく、世界中のビルドサーバが同じ値を得るか確かめるためである。上流のファイルが静かに差し替わればその瞬間に全部が失敗し、その失敗がそのまま警報になる。

この観点で見ると、自動生成アーカイブがもともと脆かったという事実が浮かぶ。ホスティングサービスがタグからその場で作るtarballは、圧縮の実装や生成ロジックが変われば内容が同じでもバイト列が変わりうる。だから慎重なパッケージャは自動生成物よりアップロード者が作って添付したリリース資産を好んできた。後者は一度固定されるからだ。

リクエスト方式はこの問題をもう一段押し進める。「同じアドレス」という前提がそもそも成り立たない。要求者ごとにリンクが異なり、再申請の時点で別の成果物が来ることもある。するとハッシュは依然として計算されるが、共有可能な基準ではなくなる。ハッシュはファイルではなく合意を検証している。合意すべき対象が公開されていなければ、ハッシュは検証装置ではなく個人的なメモに近づく。

再現可能ビルドで切れる環

再現可能ビルドはロマンチックな目標ではなく鎖である。環が一つでも切れると、結論が「検証した」から「信じることにした」へ変わる。

  1. ソースの固定 — どのバイト列から出発したか
  2. ツールチェーンの固定 — どのコンパイラとライブラリのバージョンで回したか
  3. 環境の固定 — パス・時刻・ロケールなど非決定要素をどう抑えたか
  4. 出力の照合 — 独立した二者が同じ成果物を得るか

現代のサプライチェーン証明ツールはこの鎖の上に乗る。ビルドの出所証明は「この成果物がどのソースからどのビルダで出たか」を署名付き文書として残し、SBOMは部品一覧とともに各部品の元の所在を記録し、署名ツールがその文書に身元を付ける。三層とも一番目の環が公開されているという前提の上に立っている。

SBOMの側が特にはっきりしている。部品項目のダウンロード所在フィールドに申請様式のアドレスを書けば、それは資料のアドレスではなく手続きのアドレスだ。SBOMの存在理由は「この成果物に何が入っていて、それをどこから再度取得できるか」なのに、後半が条件付きになる。形式検証は通るが目的は半分しか達成されない。

出力の照合はもっと直接に塞がる。再現検証の定義自体が独立した第三者が同じ入力から同じ結果を得ることなのに、その第三者が入力を得るのに数週間かかるなら、検証は常時の活動ではなくイベントになる。常時でない検証は退行を捕まえられない。

履歴がそのまま根拠になる場所

スナップショットだけ来るのとコミット履歴が一緒に来るのとの差を「利便性」に分類すると規模を見誤る。履歴は利便ではなく根拠として使われる。実務で実際に消費される場所は五つある。

  • 退行の二分探索 — どのバージョンからではなくどの変更から壊れたかを探す。二つのスナップショットの間が数万行の一塊なら二分探索は成り立たない
  • セキュリティ修正の特定とバックポート — どのコミットがどの脆弱性の修正かを知って初めて旧版へ移せる。スナップショットは「直った」だけを伝え、「どこがなぜ」は伝えない
  • 原因分析 — コミットメッセージと変更範囲が揃って初めて「この行がなぜこうなったか」に答えられる。コードだけ残ると意図が消える
  • 著作者とライセンスの追跡 — どのコードがどこから来て、どんな条件が付くかを確認する作業は、たいてい履歴をさかのぼって行う
  • 上流への再貢献 — ローカルの修正を上流へ戻すには上流の状態と自分の変更を分離する必要がある。ベースが一塊だと分離費用が跳ね上がる

ここでライセンスの文言が自然に登場する。GPLv2の第3条はソースコードをこう定義する。The source code for a work means the preferred form of the work for making modifications to it. 履歴がその「改変を加えるのに好ましい形態」に含まれるのか。今回の論争の技術的な核心はこの一文の上にある。

一方は、上流が内部でコミット単位に開発しその形で改変作業をしているなら、圧縮された単一スナップショットは定義上好ましい形態ではないと見る。他方は、条文はビルドと改変が可能な完全なソースを求めるだけでバージョン管理履歴を明示しておらず、履歴なしでソースのみを配布した前例も長く存在すると見る。どちらが正しいかは条文解釈と管轄の問題であり、本記事は判定しない。ただし技術的に何が消えるかは上の五項目で明確だ。

誰が困るのか - 四つの層、それぞれ別の理由で

「不便になる」でひとまとめにすると対応が出てこない。困り方の性質が層ごとに違い、したがって代替手段も違う。

ディストリのパッケージャ - まず検知が死ぬ

パッケージャが最初に失うのはファイルではなく信号だ。新しいバージョンが出たという事実を、人ではなく道具が気づく構造が広く使われている。上流のリリースページやタグ一覧を定期的に読んで新版を検知し、更新通知や下書きコミットまで作る。公開一覧が消えるとこの層が丸ごと止まり、気づきが遅れればセキュリティ修正がディストリに遅れて届く。

二つ目に失うのはレシピに書く恒久的なアドレスだ。パッケージングレシピは公開されるべきで、その中のソースアドレスは誰でもたどれなければならないが、申請ごとのリンクは書けない。するとディストリはソースを自前のインフラにミラーする必要があり、それは保存費用であり再配布権限の問題になる。ライセンスが再配布を許す部品なら解決するが、そうでない部品が混じればミラー自体が不可能になる。

CIと自動化 - 待ち時間が周期と合わない

パイプラインは人の承認待ちに耐えるようには設計されていない。夜間ビルドが毎日回るのに入力一つの取得が数週間なら、その入力はパイプラインの外へ出るしかない。実務では、人が受け取ったファイルを社内のアーティファクトストアに上げ、パイプラインがそこを見るようにする形へ落ち着く。動きはする。ただしその瞬間にソースの出所が上流ではなく組織内部のキャッシュになる。

監査の観点ではこの一段が重い。「このリリースに入ったソースはどこから来たか」の答えが上流の座標から内部パスに変わり、そのパスから上流までつながる線はファイル一つと担当者の記録だけになる。文書に残しておかなければ、数四半期後に誰も復元できない。

閉域網・エアギャップ - 手続きがスクリプトから人へ降りる

網が分離された環境は、もともと外部の資料を内部へ移す手続きを持っている。重要なのはその手続きが固定できるかだ。タグ基準なら搬入手続きはスクリプトに固まる。決まったアドレスから受け取り、決まったハッシュで検証し、検証ログを搬入審査の記録として残す。審査者が再現できるので承認が速い。

リクエスト方式になると版ごとに人が張り付く。より厄介なのは審査が求める出所の証明だ。公開アドレスと公開ハッシュがあれば証明は自己完結するが、それがなければ受信メールとリンクが証拠になる。セキュリティ要求が強い組織ほど、この形を承認根拠として受け入れにくい。結果として導入が遅れるか、そもそもその部品を使わない方向で決まる。

アーカイブと長期保存 - クロール対象から外れる

ソフトウェアの長期保存は、公開されたリポジトリを機械がなめて写しを取る方式で行われる。アクセスが申請制になればその対象から外れる。すぐには目立たず、問題は数年後に来る。旧版にその欠陥があったかを確かめる脆弱性の遡及分析、特定時点に何が配布されていたかを第三者が確認すべき法的紛争、論文が参照したコードの学術的再現、サポートが終わった端末をコミュニティが引き継ぐ保守。この四つはすべてそのとき誰かが写しを取っていたから可能だったことであり、写せなければ代替手段はない。

反対側 - 配布方式を変える理由は実在する

公開リポジトリを実際に運用したことがある側なら知っている費用がある。どの組織がどんな理由で何を変えたかは発表されなければ分からず、本記事はそれを推測しない。ただし配布方式を変えさせる一般的な圧力が何かは整理できる。

  • 帯域と自動化トラフィック — 公開Gitリポジトリのトラフィックのかなりの部分は人ではなく機械だ。浅いクローンを使わないパイプラインが全履歴を繰り返し取得すると費用が線形に増え、大規模リポジトリほど体感が大きい
  • 履歴公開そのものの精査負担 — コミット単位の履歴には内部パス、未公開のコードネーム、個人が特定される作成者情報、中間段階の実験コードが混じる。公開前の精査は自動化しにくく、間違いの代償が大きい
  • サードパーティのライセンス境界 — ツリーに再配布条件の異なるコードが混じっていれば、公開範囲を部品単位で調整する必要がある。丸ごと公開するより手がかかる
  • 再パッケージと出所の混同 — 公開アーカイブがそのまま再配布され、出所や完全性がぼやける事例は生態系ごとにある。配布地点を絞ることはそれへの対応の一つとして実際に使われる

これらの圧力は実在する。「公開が無条件に正しく申請制が無条件に悪い」という整理は正確ではない。ただし一つだけははっきり言える。費用は消えずに移動する。配布者が負っていた帯域と精査の費用が、下流の待ち時間、ミラー運用、検証の再構築の費用へ移る。総量が減ったかは別の問いであり、その答えはたいてい測られない。移った側の費用は複数の組織に散らばっていて、誰も合計を出さないからだ。

依存する側が今日できること

上流の判断は制御の外だ。制御の内にあるのは「その判断が自分たちのビルドを何日で止めるか」である。順に並べるとこうなる。

  1. 外部依存のアドレス一覧をまず作る — ビルドがネットワークから取ってくるものを一つの表に集める。この表を初めて作ると、たいてい予想の二倍ほど出てくる
  2. ハッシュのない項目にハッシュを付ける — アドレスだけ書かれチェックサムのない行が脆い行だ。最も安い対策でありながら効果がすぐ出る
  3. ソース保管の方針を文書化する — ビルドに実際に使ったアーカイブを保管期間とともに残し、ファイルだけでなく取得日・取得経路・ハッシュ・担当も併記する。後で必要になるのはファイルではなく、そのファイルが何なのかについての記述だ
  4. ミラーはライセンス確認が先 — 再配布が許される部品だけを内部ミラーに置く。「オープンソースだから大丈夫だろう」で流さず、該当条件と組織の法務確認を通す。社内専用キャッシュと外部公開ミラーは要求条件が違う
  5. ベンダリングは部品ごとに判断する — リポジトリにソースを入れると自立性は上がるが、容量と更新の摩擦が増え、セキュリティ修正の追跡責任がこちらへ移る。全部ベンダリングは答えではない。「これがないとリリースできない」に当たる部品から選ぶ
  6. 上流のタグの新しさを監視し、代替不能な部品をリスク台帳に載せる — 配布方式の変更は告知より先に「タグがしばらく上がらない」として現れる。最終タグからの経過日数を指標に置けば数週間早く気づく。そして「この部品が来期に手に入らなければ製品はどうなるか」に答えがなければ、それは技術的負債ではなくサプライチェーンのリスクだ

この一覧にない項目もはっきりさせておこう。配布者が定めた手続きを飛ばす方法はここに含まれない。それは実務対応ではなく別の問題を新たに作る行為であり、組織の規模では特にそうだ。

入手性とライセンスは別の問題である

今回の件が明らかにしたもののうち最も長く残るのは、個別リポジトリの事情ではなくこの区別だ。ライセンスは「受け取った人が何をできるか」を定め、入手性は「そもそも受け取れるか」を定める。二つはよく一塊に扱われるが、実際には別の層である。

GPLv2第3条の構造がその違いを示している。3aはバイナリとともに a medium customarily used for software interchange で完全なソースを同梱する方式であり、3bは3年以上有効な書面の申し出により要求に応じて提供する方式だ。つまり条文自体が要求に応じる形を配布方法の一つとして認めている。「誰にでも常時公開のリポジトリを運用せよ」という要求は条文にない。

だからライセンス義務は満たしつつ実質的な入手性は大きく落ちる状態が原理的に成立する。逆に今回の件でプロジェクト側は、遅延と形態が条文の要求から外れると見ている。どちらの解釈が正しいかは本記事が判定する場ではなく、有権解釈や判断も確認されていない。実務者にとって重要な結論は別のところにある。

  • 「オープンソースだからいつでも手に入る」という前提をライセンスは保証しない。大半のオープンソースライセンスは配布者に常時公開インフラの運用を求めていない
  • その前提の上に建てたパイプラインは、実はライセンスではなく配布者の運用方針に依存していた。運用方針はライセンスよりはるかに頻繁に変わる
  • 生態系がこの隙間を埋めてきた方法は一つだけだ。公開ミラー、アーカイブ、パッケージリポジトリのソースキャッシュ。すべて誰かが写しを取っていたから動いている
  • したがって写せるうちに写しておくことが、唯一拡張可能な防御である。アクセスが閉じた後に作れる写しはない

この区別をチームに定着させる方法は意外に簡単だ。依存関係の検討表で、ライセンスの列の隣に取得経路の列をもう一つ作る。公開リポジトリか、リリース資産か、申請制か、社内ミラーか。この列があれば、次の方針変更のときに影響範囲を一日で出せる。

確認できなかったこと

本記事が根拠にした資料は、公開投稿、報道、公開の議論、ライセンス原文である。それ以外の範囲は次のように開いたままだ。

  • 「一部のソースコード」の正確な範囲 — 報道で特定されたのはピクセルのカーネルで、議論ではユーザースペースドライバのリポジトリも併せて挙がったが、対象リポジトリの一覧を示す公開仕様は見つからなかった。AOSP全般が同じ方式になったと見る根拠はない
  • 変更の施行時点と実際の所要 — 投稿は処理が次第に遅くなったという記述のみで、方針転換の日を明示していない。数週間という数字も特定プロジェクトが述べた経験であり、平均や中央値に当たる公開資料はない
  • 配布主体の公式説明 — 報道は問い合わせへの回答が掲載時点までなかったと記録している。その後に公式説明が出たかは確認できなかった
  • 提供される成果物の正確な形態 — 履歴が単一ファイルに圧縮されるという記述はあるが、どの水準まで圧縮されるかについての一次資料は確認できなかった
  • ライセンスの判断と波及 — GPLv2違反かについての有権解釈や司法判断は存在が確認されず、双方の論拠のみが公開されている。他のベンダに同じ方式が広がるか、今回の変更が戻されるかについても判断の根拠はない

結論 - アドレスではなく約束を固定せよ

タグとリリースアーカイブを長く使ってきた人ほど、それを「ダウンロードリンク」として扱いやすい。実際にはその形式が静かに四つを代わりにやってくれていた。名前と内容を結び、完全性を自己証明させ、出所に署名を付ける場所を作り、第三者が同じものを得られるようにしてくれた。この四つがあったからこそチェックサムが共有可能な基準になり、SBOMに書く座標が生まれ、再現検証が常時の活動になれた。配布経路が変わればその四つが一緒に揺れる。ファイルは依然として届く。揺れるのはそのファイルについて言えることだ。

だから今回の変更を他人のリポジトリの話として流す前に、三つだけチームに問えばよい。第一に、自分たちのビルドが外部から取ってくるアドレスの全一覧を今から三十分で出せるか。第二に、そのうちハッシュが付いていない項目は何個か。第三に、そのアドレスの一つが明日申請制に変わったら、自分たちのリリースは何日後に止まるか。

三つ目に「分からない」が出るなら、今回の件はまだ来ていないだけで他人事ではない。そしてこれらの問いに答えを作る作業は、上流が何をしようと損がない。一覧とハッシュと写しは、配布方針が変わらなくてもそのまま価値がある。まれな種類の投資だ。
