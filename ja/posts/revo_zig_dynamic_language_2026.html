revo - プログラミングの楽しさのためのZig製動的言語 2026

everything is something - Zigで書き直す動的言語の楽しさ

2026年6月13日 IT・技術

はじめに: 「楽しさ」を最優先に掲げた言語の登場

新しいプログラミング言語が世に出るとき、その多くは「より速い」「より安全」「よりスケールする」を掲げます。ところが2026年6月に開発者コミュニティで話題になったrevoは、別の一文を掲げました。「プログラミングの楽しさのための動的言語（a dynamic language for the joy of programming）」。性能指標でもベンチマークでもなく、楽しさを最初の行に置いたのです。しかも興味深いことに、この言語はZigで実装されています。楽しさを追求する動的言語が、よりにもよってメモリを直接扱う低レベルなシステム言語の上に建てられているのです。

本記事では、新興言語revoを、その思想と構文、そして「Zigで動的言語を作る」という選択の意味を軸に分析します。中核概念であるeverything is something（すべては何かである）が何を意味するのか、spawnベースの並行処理モデルがどう動くのか、RubyやLuaといった既存の動的言語とどう違うのか、そしてどんな用途に向き、どんな限界があるのかまでをバランスよく見ていきます。先に断っておくと、revoはまだ0.0.0段階の非常に早いプロジェクトです。したがって一部の構文は公開された紹介資料に基づき、確定していない部分は一般的な言語設計の原理で補って説明します。

1. revoとは何か - 一文での定義

まず土台を固めましょう。revoはZigで書かれた動的型付け言語です。動的型付けとは、変数の型をコンパイル時ではなく実行時に決めるという意味で、Python・Ruby・JavaScript・Luaがすべてこの系統に属します。revoの公式紹介は自らを「表現力があり、動的型付けで、プログラミングの楽しさのための言語」と規定しています。

ここで二つのキーワードが目を引きます。一つは表現力（expressive）、もう一つは楽しさ（joy）です。この二つは実は結びついています。コードを短く自然に流れるように書けるとき、開発者は「楽しい」と感じやすく、revoの構文設計はまさにその流れを生むことに集中しています。パイプ演算子、式中心の構造、簡潔な関数定義は、すべてその方向を指しています。

revoは単なるツリーウォーキング・インタプリタではなく、ソースをバイトコードにコンパイルして実行する構造を備えます。CLIにはスクリプト実行はもちろん、バイトコードコンパイル（-b）、逆アセンブル（--dis）、テスト（--test）、ベンチマーク（--bench）、対話型REPLといったオプションが用意されています。小さな言語にしてはツール構成がかなり本格的です。

2. 中核となる思想 - everything is something

revoを理解する最も重要な鍵がeverything is something、すなわち「すべては何か（値）である」という原則です。これは言語設計でいう式指向（expression-oriented）思想の一つの表れです。噛み砕いて言えば、コードのほぼすべての構造が「文（statement）」ではなく「式（expression）」として働き、結果の値を返すということです。

例えば多くの言語ではifは流れを分ける文にすぎず、値を生みません。しかし式指向言語ではifが値を返すため、その結果をそのまま変数に代入できます。revoの紹介資料にあるブロック式の例は次の通りです。

let x = do
    let y = 5 + 10
    y
end

ここでdo ... endブロック全体が一つの式であり、ブロックの最後の値（y）がそのままブロックの値となってxに入ります。この思想はRubyの「ほぼすべてが式」やRustのブロック式と同じ系統です。効果は明確です。一時変数と別個の代入を減らし、コードを上から下へ自然に流れる一つの流れとして読ませます。

式指向設計の本質は「計算するコード」と「値を生むコード」の区別をなくすことだ。すべてが値を生むなら、コードは命令の羅列ではなく値の流れになる。

3. パイプ演算子 - 値の流れをそのまま書く

everything is somethingの思想が最も視覚的に表れる場所がパイプ演算子（|>）です。Unixシェルのパイプと同じ発想で、前の式の結果を次の関数へ流し込みます。revoの紹介にある例はこうです。

let x = "hello"
  |> _:upper()
  |> _:sub(1, 2)
  |> assert_eq("el")

ここで_は「直前の段階から流れ込んできた値」を指すプレースホルダのように見えます。"hello"が大文字に変わり、その結果の一部を切り出し、最後に期待値と比較する過程が、上から下へ一行ずつ読めます。入れ子の括弧でassert_eq(sub(upper("hello"), 1, 2), "el")のように内から外へ読まねばならないコードを、処理の順に読めるよう展開したのです。Elixir・F#・最近の多くの言語が採用した流れで、データ変換のパイプラインを表現するのに特に向いています。

4. 関数とパターンマッチ - 結果型でエラーを扱う

revoの関数定義は無駄が少ないです。そしてエラー処理では現代言語の流れに沿って結果型（result type）とパターンマッチを使います。例外（exception）を投げる代わりに、成功・失敗を値として返し、その値で分岐する方式です。紹介資料の例を見ましょう。

fn safe_div(a, b)
  if b == 0 (:err, :DivByZero)
  else (:ok, a / b)

match safe_div(10, 2)
  | (:ok, v)  => print(v)
  | (:err, e) => print(e)

ここで:ok、:err、:DivByZeroのようにコロンで始まる値はシンボル（symbol／atom）のように見えます。RubyのシンボルやElixirのアトムと同じ概念で、「それ自体が名前である軽量な定数」です。safe_divは0で割ると(:err, :DivByZero)を、正常なら(:ok, 結果)をタプルで返します。呼び出し側はmatchでそのタプルの形を見て分岐します。

この方式の利点は、エラーが「隠れた例外」ではなく「現れた値」になる点です。関数が失敗しうるという事実が戻り値の形にそのまま刻まれるため、呼び出し側は失敗ケースを取りこぼしにくくなります。RustのResult、Goの多値返し、Elixirの{:ok, ...} / {:error, ...}慣用と同じ系統の設計思想です。

5. 並行処理モデル - spawn一つで非同期を点ける

revoで最も興味深い部分が並行処理（concurrency）モデルです。中核は紹介資料のこの一行に凝縮されています。「ブロッキングなコードをまず書き、その前にspawnを付けて非ブロッキングにする」。つまり並行処理を最初から設計に押し込まず、普通のコードを書いた後、必要な箇所にspawnという一語を足して非同期へ転換する段階的アプローチです。

const h = spawn fn() add(20, 22)
join(h)

spawnは後続の関数呼び出しを別タスクとして起動し、そのタスクを指すハンドル（h）を返します。join(h)はそのタスクの終了を待ってから結果を取り出します。同期コードの形をほぼそのまま保ったまま、呼び出し一行の前にspawnを乗せるだけで並行実行になるわけです。

タスク間の通信はチャネル（channel）で行います。chan()でチャネルを作り、send()で値を送り、recv()で受け取ります。紹介資料のワーカー例は次の通りです。

let ch = chan()
fn worker(n) do
  if n == 6 do
    send(ch, :done)
    return n
  end
  sleep(n * 100)
  send(ch, n * 10)
end

このチャネルベースのメッセージ受け渡しモデルは、Goのゴルーチン・チャネル、Erlang/Elixirのアクターモデルと同じ系譜にあります。共有メモリにロックを掛ける代わりに「値をやり取りして通信する（communicate by sharing）」という思想です。データ競合（data race）を構造的に減らしやすいモデルと評価されています。

6. なぜよりにもよってZigか - 実装言語の意味

ここでもう一段深く入りましょう。revoが「Zigで作られた」という事実は、単なる技術トリビアではなく、言語の性格を決める重要な選択です。動的言語はユーザーが直接機械語をコンパイルせず、あらかじめ作られたインタプリタ／バイトコードVMがコードを実行します。だからそのインタプリタを何で作るかが、言語の性能と移植性を左右します。

Zigは2026年現在、1.0を控えたシステムプログラミング言語で、次の特性を持ちます。

Zigの特性 意味 インタプリタへの利点
ランタイムなし Cのように隠れたランタイム・GCがない 実行環境が軽く予測可能
手動メモリ管理 アロケータを明示的に扱う VMメモリを細かく制御
comptime コンパイル時のコード実行・ジェネリクス 分岐テーブル等の事前生成で高速化
容易なクロスコンパイル 一度のビルドで複数プラットフォーム対象 インタプリタ配布の移植性向上
C相互運用 既存のCコード・ライブラリを直接連携 埋め込み・バインディングが容易

要するに、ZigはCに近い速度を出しながらビルドが単純でクロスコンパイルも容易です。動的言語のインタプリタに必要な「速く、軽く、どこでも動く」条件をよく満たします。実際revoはC埋め込みAPIを提供し、他のプログラムにインタプリタを組み込めますが、これもZigのC親和性が支える部分です。一方、Zigがまだ1.0前で標準ライブラリと非同期モデルが変動中である点は、revoのような初期プロジェクトにとってそのままリスク要因でもあります。

7. 動的言語の設計トレンド - revoはどこに立つか

revoの構文は無から湧いたものではなく、動的言語が数十年かけて磨いてきた良いアイデアを集めた結果に近いです。主要言語と比べると、revoの座標がはっきりします。

  • Ruby: 「ほぼすべてが式」、開発者の幸福を明示的な目標に置く点でrevoに最も似ています。revoの「楽しさ」宣言はRubyの精神を直接受け継ぎます。
  • Lua: 小さく軽く、他のプログラムへ埋め込みやすいインタプリタという点で、revoのC埋め込み志向と通じます。
  • Elixir/Erlang: アトム、パターンマッチ、メッセージ受け渡しの並行処理は、revoのシンボル・match・チャネルに直接対応します。
  • Go: spawn-joinとチャネルは、ゴルーチン・チャネルの発想を動的言語の文脈へ移した形です。
  • Rust: 結果型ベースのエラー処理、ブロック式はRustの影響が読み取れます。

興味深いのはこの組み合わせの方向性です。2010年代後半以降、新興言語は「式指向＋パターンマッチ＋メッセージベースの並行処理」をほぼ標準セットのように採用してきました。revoはこの現代的なセットを、ガベージコレクタを持つ動的言語の快適さの上で、Zigという速い基盤で実装しようとする試みと読めます。コンパイラ実装トレンドというより広い流れはPerry - TypeScriptで作るLLVMコンパイラでも扱いました。

8. どんな問題・用途に向くか

では、revoは実際どこに使うとよいのでしょうか。現在の段階と設計の傾向を総合すると、次の領域が自然です。

  • スクリプティング・自動化: 動的型付けと簡潔な構文は、短いスクリプト、ツール、グルーコードによく合います。
  • 組み込みスクリプトエンジン: C埋め込みAPIと小さなインタプリタは、Luaのように他アプリケーションの拡張言語として組み込むのに向きます。
  • 並行処理の実験: spawn-join・チャネルモデルは、並行処理の概念を軽く学び実験するのに良い遊び場です。
  • 言語設計の学習: Zigで書かれたバイトコードVMの構造そのものが、インタプリタ実装を学びたい人にとって優れた読み物です。

逆に、大規模な本番サービス、豊富なライブラリが必須のデータ分析・Webバックエンド、長期保守が重要なシステムにはまだ早いです。その領域はPython・Ruby・Node.jsのようにエコシステムの厚い言語の役目です。

9. 限界とエコシステム - 冷静に見る

バランスのため、影もはっきり指摘します。revoは魅力的ですが、2026年現在、明白な制約を抱えています。

  • 初期段階（0.0.0）: 構文と標準ライブラリがいつでも変わりえます。今日動くコードが次のバージョンで壊れる可能性があるということです。
  • 小さなエコシステム: パッケージリポジトリ、サードパーティライブラリ、検索して出てくる例や回答がほとんどありません。問題に当たれば自力で解くしかありません。
  • プラットフォーム差: 紹介によれば、一部のプラットフォーム（例: Windows）では非同期バックエンドや完全なラインエディタがまだ整っていません。機能の体感がOSごとに異なりえます。
  • 性能未検証: Zigベースという潜在力とは別に、実ベンチマークで実証された成熟した最適化はまだ早いです。
  • 少ない貢献者: 少人数が率いる初期プロジェクトの性質上、継続性と方向が外部変数に敏感です。

これらの限界は欠陥というより「年齢」の問題です。あらゆる成熟した言語もかつては0.0.0でした。ただ導入を検討する立場では、revoを「明日のメイン言語候補」ではなく「今日の興味深い実験」と見る視線が正確です。

10. 開発者が興味を持つ点

それでもrevoが開発者の好奇心を引くには明確な理由があります。整理すると三つです。

第一に、思想の誠実さです。「楽しさ」をスローガンではなく設計原則として引っ張った痕跡が構文の随所に見えます。パイプ、式ブロック、簡潔な関数は、すべて「コードを書く人の気分」へ向きます。性能競争に疲れた人々にとって、この方向はそれ自体で新鮮です。

第二に、良いアイデアの組み合わせです。Rubyの表現力、Elixirの並行処理、Rustの結果型、Luaの埋め込み性を一つの言語に集めようとする試みは、それ自体が学習価値が大きいです。各アイデアがなぜ良いのか、一箇所に集めたときどう調和するのかを小さなコードで体験できます。

第三に、Zigエコシステムの成長です。revoは「Zigで何が作れるか」の生きた事例です。Zigが1.0へ向かう今、こうした言語実装プロジェクトはZigの可能性を測る良い物差しになります。システム言語で別の言語を作るという点で、Rustでツールを書き直す流れとも通じており、その文脈はGoからRustへ - 移行ガイドとRustで実装したZstandardでより広く扱いました。

11. 自分で触ってみたいなら - 始め方ガイド

revoを軽く触ってみたい開発者のための現実的な経路を整理します。あくまで学習・実験目的であることを前提とします。

  1. まずZigを用意: revoはZigでビルドされるので、最新のZigツールチェーンをまず入れます。zig buildでデバッグビルド、リリースは最適化フラグを与えます。
  2. REPLで感覚をつかむ: 対話型REPLで式ブロックやパイプを直接入力してみます。everything is somethingの感覚は一行実行で最も速く身につきます。
  3. 小さな並行処理の例: spawn-joinとチャネルでワーカーをいくつか起動してみます。「同期コードにspawn一語」の体験が核心です。
  4. テスト内蔵を体験: testブロックをソースに併記して--testで回し、コードと検証が一つのファイルに同居する構造を感じます。
  5. 逆アセンブルを覗く: --disでバイトコードを出力し、動的言語が内部でどうコードを表現するかを観察します。
新興言語に触れる最も健全な態度は「これで何を作ろうか」より「この設計はなぜこうなったのか」を問うことだ。revoは後者の問いに答えの多い言語である。

12. 結論 + すぐに使える3つ

revoを一文でまとめるとこうなります。「Zigという速い基盤の上に、式指向・パターンマッチ・メッセージ並行処理という現代的な動的言語のアイデアを『楽しさ』を基準に編んだ初期の実験」です。まだ本番言語ではありませんが、言語設計の良い流れがどこへ向かうかを、小さく鮮明に見せてくれます。最後に、revoでなくても今日すぐ持ち帰れる三つを残します。

  1. 式指向へ思考を切り替えてみる。 使う言語が何であれ、ifやブロックを「値を生むもの」と見る習慣はコードを短く読みやすくします。一時変数を減らす小さなリファクタリングから始めましょう。
  2. エラーを例外ではなく値として扱ってみる。 成功・失敗を戻り値の形で現せば、失敗処理を取りこぼしにくくなります。Result・タプル返しの慣用を一つの関数にでも適用してみましょう。
  3. 並行処理は「後からspawn」で臨む。 最初から非同期で設計せず、同期コードをまず明確に書いてからボトルネックだけをタスクに分離する順序が、デバッグと理解に有利です。
