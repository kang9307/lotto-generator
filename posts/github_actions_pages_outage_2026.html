서론: 빨간 워크플로보다 무서운 것

대규모 장애가 나면 화면은 대개 빨갛게 물든다. 실패한 작업, 재시도 버튼, 대기열에 박혀 움직이지 않는 잡. 그런데 2026년 8월 6일 GitHub Actions 장애에서 가장 값비싼 손실은 빨간 표시가 아니었다. 아예 목록에 나타나지 않은 실행이었다.

GitHub는 인시던트를 닫으면서 푸시와 풀 리퀘스트를 포함한 일부 워크플로 트리거 이벤트가 처리되지 않았고 자동으로 재생할 수 없다고 공지했다. 실패는 눈에 보이지만 부재는 보이지 않는다. 검사 목록이 비어 있는 커밋은 통과한 커밋과 화면상 구분이 잘 안 된다. 그리고 그런 커밋이 병합되면, 장애는 끝나도 결과는 남는다.

이 글은 장애 보도가 아니다. 사건은 짧게 정리하고, 배포 경로 전체를 한 회사에 걸어 둔다는 결정이 실제로 어떤 비용을 청구하는지로 간다. 무엇이 멈추고 무엇은 계속 도는지, 상태 페이지가 정상인데 내 것만 실패할 때 어떻게 갈라내는지, 그리고 취미 사이트가 멀티 클라우드를 짓는 것이 왜 손해인지까지 다룬다.

이 글은 Actions 사용법 글이 아니다. 워크플로 문법, 트리거 종류, 잡과 스텝 구성 같은 기초는 GitHub Actions와 CI/CD - Git & GitHub 협업 마스터 5편에서 다뤘다. 여기서는 그 워크플로가 도는 판이 멈췄을 때의 판단만 취급한다.

1. 공식 기록으로만 추린 타임라인

사후 기사와 커뮤니티 요약은 시각이 조금씩 엇갈린다. 아래는 GitHub 상태 페이지의 인시던트 갱신에 남은 내용만 추린 것이다. 시각은 전부 UTC이고, 한국 시간은 여기에 9시간을 더하면 된다.

  • 영향 등급: critical. 구성 요소는 Actions와 Pages 두 개로 기록됐다

1.3 회복 곡선이 알려 주는 것

성공률이 30~40퍼센트에서 65퍼센트로, 다시 97퍼센트와 99퍼센트로 올라간 경로는 스위치를 껐다 켜는 복구가 아니었다는 뜻이다. 대기열을 비우면서 조금씩 정상 처리 비율을 끌어올리는 형태였고, 그래서 중간 지점에서 개별 사용자가 체감하는 결과는 복불복이었다.

  • 회복 국면에서 GitHub는 웹훅 처리량을 의도적으로 조였다. 회복을 돕기 위한 조치였고, 한때 처리량이 정상의 15퍼센트 수준이라는 갱신이 있었다
  • 웹훅이 조여 있는 동안에는 푸시나 풀 리퀘스트가 새 워크플로 실행을 만들어 내지 못했다
  • 회복 국면에 언급된 다른 영향 대상으로는 Copilot 코드 리뷰, Copilot 코딩 에이전트, 호스티드 러너, 셀프 호스티드 러너, 웹훅 전달, GitHub Enterprise Importer 마이그레이션이 있었다
  • 셀프 호스티드 러너 쪽은 등록 시 오류나 속도 제한이 날 수 있다는 안내가 따로 나왔다. 러너를 내 쪽에 둔다고 해서 제어 평면 의존이 사라지지 않는다는 사실이 여기서 드러난다

2. Actions와 Pages가 멈추면 실제로 멈추는 것

대비를 설계하려면 먼저 영향 경계를 정확히 그어야 한다. 여기서 흔한 실수가 두 방향으로 난다. 하나는 GitHub가 죽으면 전부 죽는다고 넘겨짚는 것, 다른 하나는 정적 사이트라 아무 상관 없다고 넘겨짚는 것이다. 둘 다 틀리다.

2.1 멈추는 것

  • 새 배포. Pages 배포를 Actions 워크플로로 돌린다면 배포는 곧 CI다. Actions가 멈추면 새 글도 새 버전도 못 올라간다
  • 병합 게이트. 필수 상태 검사를 걸어 둔 저장소는 검사가 안 도는 동안 병합이 막힌다. 이건 오히려 안전 장치가 제대로 동작한 결과다
  • 릴리스 자동화. 태그를 밀면 빌드하고 서명하고 아티팩트를 붙이는 흐름은 통째로 멈춘다
  • 예약 작업. 크론 스케줄로 도는 정리·백업·리포트 워크플로는 그 시간대 실행분이 그냥 사라진다. 대기했다가 나중에 도는 것이 아니다
  • Actions API에 의존하는 감시 도구. 실행 상태를 API로 읽어 대시보드에 그리던 것들이 오류를 받는다
  • 컨테이너 이미지 빌드·푸시 흐름. 레지스트리가 살아 있어도 이미지를 만들어 밀어 넣는 주체가 Actions면 결과는 같다

2.2 안 멈추는 것

  • 이미 배포되어 다른 곳에서 서빙 중인 결과물. 빌드 산출물을 자체 서버나 다른 CDN에 올려 두었다면, 그 서빙 경로는 Actions와 무관하게 계속 돈다
  • 로컬 개발. 클론된 저장소에서 브랜치를 파고 커밋하고 테스트를 돌리는 일은 전부 로컬에서 된다. Git은 원래 분산 버전 관리다
  • 이미 받아 둔 의존성. 락 파일과 캐시가 있으면 외부 레지스트리가 살아 있는 한 빌드 자체는 손에서 재현된다
  • 다른 CI에 걸어 둔 파이프라인. 저장소는 GitHub에 두되 빌드를 다른 러너에서 돌리는 구성이라면, 소스 접근만 되면 계속 간다

2.3 이번에 확실히 안 갈린 경계

가장 궁금한 지점이 정작 공개 기록으로 안 갈린다. Pages가 저하됐다는 표시가 새 배포만 막힌 것인지, 이미 게시된 사이트의 서빙까지 흔들린 것인지가 그것이다. 상태 페이지 문구는 두 상황을 구분해 적지 않았다. 커뮤니티 스레드에 올라온 보고는 배포 실패 쪽이 압도적으로 많았지만, 그것은 사용자 보고의 분포일 뿐 서빙이 무사했다는 증거가 아니다.

실무에서는 이 구분이 대비 설계를 통째로 바꾼다. 아래 표는 두 경우를 나눠 놓은 것이다.

3. 이번 장애의 진짜 청구서 - 사라진 트리거

10시간 넘게 실패한 워크플로는 다시 돌리면 된다. 진짜 비용은 그 다음에 온다.

3.1 웹훅 스로틀이 만든 조용한 실패

워크플로는 저절로 돌지 않는다. 푸시나 풀 리퀘스트 같은 사건이 실행을 만들어 낸다. 회복을 돕기 위해 그 전달 경로가 조여져 있었고, 조여 있는 동안 발생한 사건 상당수는 나중에 배달되는 대기열에 쌓인 것이 아니라 그냥 처리되지 않았다.

그래서 나오는 결과가 이렇다.

  • 커밋은 저장소에 정상적으로 들어가 있다. 코드는 하나도 안 잃었다
  • 그런데 그 커밋에 붙은 검사 목록이 비어 있다. 실패가 아니라 부재다
  • 필수 검사를 안 걸어 둔 저장소라면 그 상태로 병합이 된다. 리뷰어는 빨간 표시가 없으니 문제를 못 느낀다
  • 린트·테스트·보안 스캔이 통째로 건너뛰어진 커밋이 기본 브랜치에 들어간다
  • 며칠 뒤 다른 이유로 CI가 돌 때 그 커밋의 문제가 터지고, 원인은 엉뚱한 최신 변경으로 지목된다

GitHub의 안내는 명확했다. 새 커밋을 푸시하거나, 풀 리퀘스트를 갱신하거나, 가능한 경우 워크플로를 수동으로 다시 실행해서 트리거 행위 자체를 반복하라는 것이다. 자동 재생이 없다는 문장이 여기에 붙는다.

3.2 장애가 끝난 뒤 반드시 훑을 것

인시던트가 닫혔다고 일이 끝난 게 아니다. 아래는 종료 이후에 사람이 확인해야 하는 목록이다.

  • 장애 창 안에 들어온 커밋 목록. 시각을 UTC로 맞춰 놓고 그 구간의 기본 브랜치 커밋을 뽑는다
  • 검사 목록이 빈 커밋. 실패한 것 말고 아무것도 안 붙은 것을 찾는다. 이게 핵심이다
  • 그 구간에 병합된 풀 리퀘스트. 승인은 사람이 했어도 자동 검사는 안 돌았을 수 있다
  • 예약 워크플로의 결번. 매일 도는 백업이나 정리 작업이 하루치 빠졌는지 본다. 이건 실패 알림도 안 온다
  • 배포 상태와 실제 서빙 내용의 일치 여부. 마지막 성공 배포가 정말 최신 소스인지 확인한다
  • 중간에 취소하거나 강제 종료한 잡의 뒷정리. 락 파일, 임시 리소스, 반쯤 올라간 아티팩트가 남아 있을 수 있다

가장 값싼 방법은 장애 구간 직후에 기본 브랜치에 빈 커밋 하나를 밀어 전체 워크플로를 한 번 돌리는 것이다. 이러면 최소한 현재 HEAD가 검사를 통과하는지는 확실해진다. 다만 중간에 끼어 병합된 개별 커밋의 문제는 이 방법으로 안 잡히니, 위 목록을 따로 훑어야 한다.

4. 상태 페이지는 초록인데 내 워크플로만 실패할 때

이번 장애처럼 등급이 critical까지 올라가면 판단이 쉽다. 어려운 쪽은 상태 페이지가 정상인데 내 것만 안 되는 상황이다. 실무에서는 이쪽이 훨씬 자주 온다.

4.1 순서대로 좁히기

  • 1단계. 같은 워크플로를 최근에 성공시킨 실행이 있는지 본다. 없으면 내 변경이 원인일 확률이 크다
  • 2단계. 다른 저장소의 무관한 워크플로를 하나 돌려 본다. 그것도 안 되면 계정·조직 범위의 문제다
  • 3단계. 실패 지점이 잡 시작 전인지 후인지 가른다. 시작 전이면 러너 배정과 대기열, 시작 후면 내 스크립트다
  • 4단계. 같은 명령을 로컬에서 돌린다. 로컬에서 재현되면 인프라 장애가 아니다
  • 5단계. 여기까지 와서 원인이 안 나오면 그때 상태 페이지와 커뮤니티 인시던트 스레드를 본다

순서를 이렇게 두는 이유는 간단하다. 상태 페이지는 항상 늦다. 이번에도 사용자 증상과 최초 조사 공지 사이에 시차가 있었고, 등급이 최종 수준으로 올라가기까지는 한 시간 넘게 걸렸다. 상태 페이지가 초록이라는 사실은 장애가 아니라는 증거가 아니라, 아직 집계되지 않았다는 정보일 뿐이다.

4.2 내 쪽이 원인일 때 나오는 신호

  • 실패가 특정 잡이나 특정 스텝에만 몰린다
  • 에러 메시지가 구체적이다. 모듈을 못 찾는다거나 권한이 없다거나 하는 식이다
  • 같은 커밋을 다시 돌려도 같은 지점에서 같은 메시지로 죽는다
  • 최근에 액션 버전, 러너 이미지, 의존성 락 파일 중 하나를 바꿨다
  • 다른 저장소의 워크플로는 멀쩡히 돈다

4.3 제공자 쪽이 원인일 때 나오는 신호

  • 잡이 실행되지도 못하고 대기열에 오래 머문다
  • 에러가 두루뭉술하다. 러너가 작업을 가져가지 못했다는 식의 문장이 나온다
  • 재실행할 때마다 실패 지점이 달라진다. 결정론적이지 않다는 건 강한 단서다
  • 내 코드와 무관한 워크플로도 같이 실패한다
  • 웹 UI나 API 응답이 평소보다 느리거나 간헐적으로 오류를 낸다

장애 중에 하면 상황을 더 나쁘게 만드는 행동. 실패했다고 반사적으로 전체 재실행을 반복하는 것이다. 회복이 계단식으로 진행되는 국면에서 대량 재시도는 대기열을 다시 부풀려 자신의 회복도 늦춘다. 이번 사례에서도 회복은 대기열을 비워 가며 성공률을 끌어올리는 방식으로 진행됐다. 재시도는 성공률이 눈에 띄게 올라온 뒤에 몰아서 하는 편이 낫다.

5. 내 배포 경로에 단일 지점이 몇 개인가

여기서부터가 이 글의 본론이다. GitHub에 배포를 걸어 둔다는 결정은 나쁜 결정이 아니다. 다만 그 결정이 실제로 몇 개의 칸을 한 회사에 몰아 두는지는 세어 봐야 한다.

5.1 네 칸으로 쪼개기

배포 경로는 대체로 이 네 칸으로 나뉜다.

  • 소스 보관. 코드가 사는 곳. 원격 저장소
  • 트리거. 사건을 실행으로 바꾸는 층. 웹훅과 스케줄러
  • 연산. 실제로 빌드와 테스트를 돌리는 머신. 러너
  • 배급. 만들어진 결과물을 사용자에게 내보내는 곳. 호스팅과 CDN

전형적인 구성에서 이 네 칸이 어떻게 배치되는지 보면, 왜 한 회사의 장애가 배포 전체를 세우는지가 바로 보인다.

  • 소스 보관 = GitHub
  • 트리거 = GitHub 웹훅
  • 연산 = GitHub 호스티드 러너
  • 배급 = GitHub Pages
  • 네 칸 전부 같은 회사. 이 구성에서 단일 지점의 개수는 1이 아니라 4다

5.2 셀프 호스티드 러너가 줄여 주는 칸

러너를 자체 인프라로 옮기면 연산 칸이 빠질 것 같지만, 이번 사례가 그 기대를 정확히 반박한다. 셀프 호스티드 러너 쪽에서도 등록 시 오류나 속도 제한이 보고됐고, 자체 쿠버네티스 클러스터에서 도는 Actions Runner Controller 러너는 유휴 상태로 굳어 사람이 파드를 지우거나 애플리케이션을 재배포해야 했다.

  • 러너가 내 인프라에 있어도 작업을 배정하는 제어 평면은 여전히 GitHub다
  • 그래서 셀프 호스팅은 연산 용량과 환경을 내 것으로 만드는 수단이지, 제어 평면 의존을 끊는 수단이 아니다
  • 오히려 장애 시 복구해야 할 대상이 하나 더 생긴다. 굳은 러너 파드를 정리하는 일은 내 몫이다
  • 셀프 호스팅의 정당한 이유는 보안 경계, 사내망 접근, 특수 하드웨어, 비용이다. 가용성은 그 목록에 없다

6. 대비 수단별 비용과 효과

대비는 전부 하거나 전부 안 하거나가 아니다. 값이 거의 안 드는 것부터 아주 비싼 것까지 층이 있고, 대부분은 아래 세 줄에서 끝난다.

6.1 값싼 것부터

대비 수단드는 비용이번 유형의 장애에서 실제 효과권장 대상
빌드 산출물을 아티팩트로 보관거의 0. 워크플로 몇 줄높음. 다시 빌드하지 않고 손으로 올릴 수 있다전부
로컬에서 같은 명령으로 빌드되는지 유지낮음. 규율의 문제높음. CI 없이도 결과물을 만들 수 있다전부
상태 페이지 알림 구독0중간. 원인 판별 시간을 줄인다전부
필수 상태 검사 강제0. 설정 한 번높음. 검사 부재 커밋의 병합을 막는다전부
장애 후 커밋 훑기 절차 문서화낮음높음. 사라진 트리거를 잡는 유일한 방법팀 이상
배포 스크립트를 CI에서 분리중간. 리팩터링 한 번중간~높음. 사람 손으로 같은 배포를 할 수 있다수익이 걸린 서비스
다른 CI로의 전환 가능한 워크플로 유지중간. 이중 관리중간. 전환에 시간이 걸려 당일 장애에는 늦다팀 이상
배급 경로 이중화(다른 호스팅 상시 대기)높음. DNS·인증서·동기화서빙이 죽는 유형에만 유효가용성이 매출인 곳
저장소 자체의 상시 미러높음. 권한·훅·이슈 동기화낮음~중간. 이번 유형에는 거의 무효규제·계약 요구가 있는 곳

6.2 표에서 읽어야 할 한 줄

표 위쪽 네 줄은 비용이 사실상 0인데 효과가 높다. 아래쪽 두 줄은 비용이 크고 이번 유형에는 효과가 제한적이다. 그런데 장애 직후에 사람들이 논의하기 시작하는 것은 대개 아래쪽 두 줄이다. 순서가 거꾸로다.

  • 아티팩트 보관은 워크플로에 업로드 스텝 하나를 더하는 일이다. 장애 중에도 마지막 성공 빌드의 결과물이 손에 있다
  • 로컬 빌드 재현성은 별도 도구가 아니라 습관이다. CI에서만 도는 마법 같은 절차를 만들지 않으면 저절로 유지된다
  • 필수 상태 검사는 이번 장애의 핵심 손실인 검사 부재 커밋을 구조적으로 차단한다. 검사가 안 돌면 병합이 안 되니 사람이 알아챈다
  • 배포 스크립트를 CI 문법에서 떼어 놓으면, 같은 스크립트를 노트북에서 실행해 급한 배포를 할 수 있다

7. 어디까지가 과잉인가 - 규모별 선 긋기

대형 장애 뒤에는 항상 과잉 대응이 뒤따른다. 멀티 클라우드는 대부분의 경우 손해다. 손해인 이유를 정확히 짚어야 논의가 끝난다.

7.1 취미·개인 사이트

  • 반나절 배포가 밀려도 잃는 것이 없다. 손실 자체가 0에 가까운데 대비에 돈과 시간을 넣으면 순손실이다
  • 이중 호스팅을 상시로 유지하면 구성 자체가 새 고장 원인이 된다. DNS 전환, 인증서 두 벌, 리다이렉트 규칙, 동기화 스크립트가 늘어난다
  • 실제로 대부분의 사고는 장애가 아니라 이 부속들에서 난다. 쓰지 않는 예비 경로는 조용히 썩는다
  • 여기서 합리적인 상한선은 산출물 보관, 로컬 빌드 유지, 상태 알림 구독 세 가지다. 전부 무료이고 전부 오늘 끝난다
  • 굳이 하나 더 한다면, 정적 결과물을 압축해 별도 저장소나 클라우드 스토리지에 주기적으로 떨궈 두는 정도다

7.2 수익이 걸린 소규모 서비스

  • 기준이 바뀐다. 배포가 막히는 것과 서비스가 안 열리는 것을 분리해서 값을 매겨야 한다
  • 배포 지연은 대개 견딜 수 있다. 반나절 늦은 기능 배포로 회사가 흔들리는 경우는 드물다
  • 서빙 중단은 다르다. 여기에는 이중화가 정당해진다. 다만 이 경우 대비 대상은 CI가 아니라 호스팅과 DNS다
  • 즉 이 규모에서도 CI 이중화는 대개 낭비다. 돈은 서빙 경로 쪽에 쓰는 게 맞다
  • 실질적으로 값어치가 큰 건 배포 스크립트를 CI 문법에서 분리해 두는 것이다. 장애 중에도 사람이 같은 절차를 실행할 수 있다

7.3 팀·회사 규모

  • 여기서부터는 손실이 시간당으로 계산된다. 개발자 수 곱하기 시간이 곧 비용이다
  • 그래도 첫 투자는 이중화가 아니라 절차다. 장애 시 누가 판단하고 어떤 순서로 훑는지가 정해져 있으면 손실의 큰 부분이 줄어든다
  • 릴리스 일정에 여유 구간을 넣는 것이 이중화보다 싸고 확실하다
  • CI 이중화를 검토한다면 전체 파이프라인 복제가 아니라 핵심 경로 하나만 다른 러너에서도 돌 수 있게 두는 형태가 현실적이다
  • 이중화한 경로는 정기적으로 실제로 돌려야 한다. 안 도는 예비 경로는 장애 당일에 반드시 실패한다

8. 자체 러너를 두면 해결되는가

앞에서 한 번 짚었지만 이번 사례가 워낙 선명해서 따로 정리한다. 이번 장애에서 셀프 호스티드 러너를 쓰던 쪽은 더 편하지 않았다.

  • 러너 등록 단계에서 오류와 속도 제한이 보고됐다. 러너 프로세스는 내 서버에 있어도 등록은 GitHub와 통신해야 한다
  • 쿠버네티스에서 Actions Runner Controller로 러너를 굴리던 쪽은 파드가 유휴 상태로 굳는 현상을 겪었다
  • GitHub의 안내는 굳은 파드를 kubectl로 지우거나 ARC 애플리케이션을 재배포하라는 것이었다. 그러면 대체 러너가 자동으로 생성된다
  • 즉 회복 작업의 마지막 구간에서 사람 손이 필요한 쪽은 자체 클러스터를 가진 쪽이었다
  • 호스티드 러너만 쓰던 쪽은 대기열이 비워지기를 기다리면 됐다

이 대비는 셀프 호스팅이 나쁘다는 뜻이 아니다. 셀프 호스팅의 이유 목록에서 가용성을 지우라는 뜻이다. 사내망 리소스에 접근해야 한다거나, 특정 GPU가 필요하다거나, 장시간 잡의 비용이 문제라거나, 컴플라이언스상 빌드 환경을 통제해야 한다면 셀프 호스팅은 옳다. 그런데 그 이유로 도입한 뒤에 가용성까지 좋아졌다고 기대하면 어긋난다.

9. 릴리스 일정에 여유를 넣는 실무

가장 값싼 대비는 기술이 아니라 일정이다. 그런데 이건 금요일 배포 금지 같은 이야기와는 다르다.

9.1 재시도 예산이라는 개념

  • 릴리스 계획에 배포가 처음에 실패한다고 가정한 여유 시간을 명시해 둔다. 몇 시간이면 충분하다
  • 여유가 있으면 장애 중에 무리하게 밀어붙이는 결정이 안 나온다. 무리한 결정은 대개 여유가 없어서 나온다
  • 외부 공지가 걸린 릴리스는 배포 완료와 공지 시각을 분리한다. 배포는 미리, 공개 전환은 나중에
  • 정적 사이트라면 결과물을 먼저 만들어 두고 게시만 나중에 하는 형태가 자연스럽다
  • 규모가 큰 릴리스일수록 파이프라인 재시도 횟수가 늘어난다. 여유는 규모에 비례해서 잡는다

9.2 장애 중에 내리면 안 되는 결정

  • 검사를 임시로 끄는 것. 급하다고 필수 상태 검사를 해제하면, 정확히 이번 장애가 만든 손실을 스스로 만든다
  • 파이프라인 대수술. 장애 중에 워크플로를 크게 고치면 나중에 무엇이 원인이었는지 못 가른다
  • 다른 CI로의 즉석 이전. 준비 없이 하는 이전은 그날 안에 안 끝나고, 끝나도 검증이 안 된 파이프라인이 남는다
  • 대량 재실행. 회복 국면에 대기열을 다시 부풀린다
  • 수동 배포의 흔적을 안 남기는 것. 급하게 손으로 올렸다면 무엇을 어떤 커밋에서 올렸는지 반드시 기록한다. 다음 자동 배포가 그걸 덮어쓸 수 있다

10. 확인하지 못한 것

근거가 확보되지 않은 항목을 한자리에 모은다.

  • 근본 원인. GitHub는 15시 45분 UTC 갱신에서 장애를 일으킨 지점을 파악했다고 밝혔지만, 그 지점이 무엇이었는지는 인시던트 종료 시점까지 공개하지 않았다
  • 회복 국면에 언급된 표현의 지위. 유효하지 않은 작업을 배정받는 러너, 유휴 상태로 굳은 ARC 파드는 증상과 완화 대상으로 언급된 것이지 원인의 서술로 확인되지 않았다
  • 이미 게시된 Pages 사이트의 서빙 영향. 배포만 막힌 것인지 서빙까지 흔들린 것인지 공개 문구로 갈리지 않는다
  • 커뮤니티에서 도는 원인 설명. 부하 증가나 인프라 이전을 원인으로 지목하는 이야기가 있으나 출처가 GitHub가 아니다. 이 글에서는 사실로 취급하지 않는다
  • 영향 규모의 절대 수치. 몇 개의 저장소, 몇 건의 실행이 영향을 받았는지에 대한 공개 수치는 확인되지 않았다
  • SLA 보상 여부. 이 인시던트에 대한 크레딧 정책이 어떻게 적용되는지는 공개 기록으로 확인하지 못했다
  • 사후 상세 보고서의 발행 여부와 시점. 이 글을 쓰는 시점에는 나와 있지 않다. 나중에 갱신될 수 있다
  • 웹훅 스로틀 구간의 정확한 시작·종료 시각. 15퍼센트라는 수치는 회복 국면 갱신에 등장하지만, 조이기 시작한 시점과 완전 해제 시점이 분 단위로 명시되지는 않았다

11. 자주 묻는 질문

이번 GitHub 장애는 언제 시작해서 언제 끝났나?

GitHub 상태 페이지 기준으로 인시던트는 2026년 8월 6일 15시 22분 UTC에 열렸고 8월 7일 02시 04분 UTC에 종료 처리됐다. 전체 창은 10시간 42분이다. 다만 이 숫자를 그대로 다운타임으로 읽으면 안 된다. 사이에 완화 처리 시점이 따로 있어서, 시스템 전반의 대기열이 비워지고 완화됐다는 갱신이 8월 7일 00시 05분 UTC에 나왔다. 그 뒤 약 두 시간은 Actions Runner Controller 러너가 늦게 회복되는 꼬리 구간을 정리하는 데 쓰였다. 한국 시간으로 옮기면 8월 7일 새벽 0시 22분에 시작해 같은 날 오전 11시 4분에 닫힌 셈이라, 국내 근무 시간대에는 이미 끝나 있던 장애다.

GitHub는 이 장애의 원인을 공개했나?

공개하지 않았다. 상태 페이지 갱신에는 15시 45분 UTC에 장애의 원인이 되는 지점을 파악했고 완화 작업 중이라는 문장이 있지만, 그 지점이 무엇이었는지는 인시던트가 닫힐 때까지 문장으로 나오지 않았다. 회복 국면에서 언급된 표현들, 이를테면 더 이상 유효하지 않은 작업을 계속 배정받는 러너나 유휴 상태로 멈춘 Actions Runner Controller 파드 같은 것은 증상과 완화 대상이지 근본 원인의 서술이 아니다. 인터넷에 도는 몇 가지 설명은 출처가 GitHub가 아니라 커뮤니티 추정이므로 사실로 옮기지 않는 편이 안전하다.

장애 중에 푸시한 커밋이 CI를 못 돌렸다면 어떻게 되나?

자동으로 되살아나지 않는다. GitHub는 마지막 갱신에서 푸시와 풀 리퀘스트를 포함한 일부 워크플로 트리거 이벤트가 인시던트 중에 처리되지 않았고 자동 재생이 불가능하다고 밝혔다. 이 경우 새 커밋을 푸시하거나 풀 리퀘스트를 갱신하거나 워크플로를 수동으로 다시 실행해서 트리거 행위 자체를 반복해야 한다. 실무에서 위험한 대목은 실패한 워크플로가 아니라 목록에 아예 나타나지 않은 워크플로다. 빨간 표시는 눈에 띄지만, 실행 자체가 없는 커밋은 화면상 아무 흔적이 없어서 검사를 통과한 것처럼 보인다.

이미 배포된 GitHub Pages 사이트는 계속 열렸나?

이 부분은 공개 기록으로 갈리지 않는다. Pages는 인시던트 구성 요소로 올라갔고 성능 저하와 정상 사이를 오갔지만, 공개된 갱신 문구는 새 배포가 막힌 것인지 이미 게시된 사이트의 서빙도 영향을 받은 것인지를 구분해 적지 않았다. 커뮤니티 스레드에 보고된 증상은 배포 실패 쪽이 압도적으로 많았다. 다만 그것은 사용자 보고의 분포일 뿐 서빙이 무사했다는 근거는 아니다. 그래서 이 글은 서빙 무사를 전제로 어떤 판단도 하지 않고, 확인되지 않은 항목으로 따로 분류해 둔다.

개인 블로그도 다른 호스팅을 미리 준비해 둬야 하나?

대체로 아니다. 취미와 개인 사이트에서 이중 호스팅을 상시로 유지하면 그 구성 자체가 새로운 고장 원인이 된다. DNS 전환, 인증서 두 벌, 리다이렉트 규칙, 동기화 스크립트가 늘어나고 대개는 장애가 아니라 이 부속들이 먼저 말썽을 낸다. 반나절 배포가 밀려서 손해가 나지 않는 사이트라면 합리적인 대비는 세 가지로 충분하다. 하나, 빌드 산출물을 아티팩트로 남겨 다시 만들지 않아도 되게 한다. 둘, 로컬에서 같은 명령으로 빌드가 되는지 가끔 확인한다. 셋, 상태 페이지 알림을 구독해 장애인지 내 실수인지 판단하는 시간을 줄인다.

결론: 오늘 가져갈 세 가지

첫째, 이번 장애의 손실은 실패가 아니라 부재였다. 10시간 넘게 빨갛게 물든 워크플로는 다시 돌리면 그만이다. 문제는 트리거 자체가 처리되지 않아 실행 목록에 아무것도 안 남은 커밋이고, 그건 자동으로 되살아나지 않는다. 장애가 끝난 뒤 그 구간의 커밋을 사람이 훑는 절차가 있느냐 없느냐가 실제 손실을 가른다.

둘째, 단일 지점의 개수는 회사 수가 아니라 칸의 수로 센다. 소스·트리거·연산·배급 네 칸이 한 회사에 몰려 있으면 그 회사의 장애는 배포 전체를 세운다. 그리고 러너만 내 인프라로 옮겨도 트리거와 제어 평면은 그대로 남는다. 이번에 자체 클러스터를 가진 쪽이 오히려 손으로 파드를 정리해야 했던 것이 그 증거다.

셋째, 대비의 가성비 순서를 뒤집지 마라. 산출물 보관, 로컬 빌드 재현, 필수 상태 검사, 장애 후 점검 절차. 이 넷은 사실상 공짜인데 이번 유형의 손실을 대부분 막는다. 반면 배급 경로 이중화와 저장소 미러는 비싸고, 이번처럼 배포가 막히는 유형에는 효과가 제한적이다. 그런데 장애 직후 회의에서 먼저 나오는 이야기는 항상 비싼 쪽이다.

마지막으로 하나. 상태 페이지의 초록불은 정상이라는 증거가 아니라 아직 집계되지 않았다는 정보다. 이번에도 사용자 증상과 공지 사이, 공지와 등급 상향 사이에 시차가 있었다. 그래서 판별은 언제나 내 쪽에서 시작해야 한다. 같은 명령을 로컬에서 돌려 보는 데 드는 몇 분이, 남의 상태 페이지를 새로고침하며 보내는 한 시간보다 낫다.
