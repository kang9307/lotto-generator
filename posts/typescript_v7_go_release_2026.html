TypeScript 7 정식 출시 - Go 네이티브 컴파일러가 바꾸는 것과 바꾸지 못하는 것

RC 이후 3주 만의 GA, 마이그레이션·호환성·esbuild와의 관계를 실무 관점에서 따진다

2026-07-09 개발/인프라

서론: 컴파일러 교체가 "정식"이 되는 순간

2026년 7월 8일, Microsoft는 TypeScript 7의 정식 출시(GA)를 발표했다. 지난 6월 18일 RC가 나온 지 약 3주 만이다. 본인은 RC 단계에서 이미 이 재작성의 구조와 기술적 배경을 분석한 적이 있다. 이번 글의 초점은 다르다. RC는 "예고편"이었고, GA는 그 예고가 어디까지 그대로 확정됐는지, 그리고 실제로 프로젝트에 적용할 때 무엇을 신경 써야 하는지를 보여주는 "확정판"이다.

이 글은 2026년 7월 기준 공식 발표와 출시 직후 보도를 근거로, 세 가지 질문에 답한다. 왜 처음부터 컴파일러 전체를 Go로 옮겨야 했는가, 그 결과 개발자가 실제로 얻는 것은 무엇인가, 그리고 무엇보다 지금 당장 옮겨도 되는지다. 마지막 질문이 가장 실무적이면서 가장 자주 생략되는 질문이라고 본다.

1. tsc는 왜 느려질 수밖에 없었나

TypeScript 팀이 굳이 컴파일러 전체를 다른 언어로 옮긴 이유를 "그냥 빠른 언어를 좋아해서"로 읽으면 핵심을 놓친다. 문제는 알고리즘이 아니라 실행 모델이었다.

1.1 두 가지 구조적 벽

기존 tsc는 TypeScript 자신(사실상 JavaScript)으로 짜여 JavaScript 엔진 위에서 돌았다. 이는 두 가지 천장을 만든다. 첫째, 네이티브 코드가 아닌 이상 JIT을 거쳐도 실행 오버헤드를 완전히 없애지 못한다. 둘째, 사실상 단일 스레드 모델이라 멀티코어가 흔해진 지금도 대형 프로젝트의 타입 검사를 병렬로 쪼갤 방법이 마땅치 않았다. 코드베이스가 수십만 줄을 넘어가면 타입 체크가 수십 초씩 걸리고, 에디터의 자동완성·오류 표시가 타이핑을 따라가지 못하는 현상이 바로 이 천장의 증상이었다.

1.2 왜 Rust가 아니라 Go였나

흥미로운 것은 Go를 택한 이유다. 성능만 보면 Rust도 후보였을 것이다. 그러나 공개된 설명에 따르면 기존 컴파일러 코드베이스는 공유 가변 상태와 포인터가 많은 그래프 순회 구조에 크게 의존한다. 이런 구조를 소유권 모델이 엄격한 Rust로 옮기려면 설계를 상당 부분 다시 짜야 하지만, GC 기반인 Go는 기존 로직과 데이터 구조를 거의 그대로 유지한 채 방법론적 포팅(methodical port)이 가능했다. 새로 쓰는 대신 옮기는 쪽을 택한 이유는 명확하다. 수십 년 치 테스트 스위트로 "새 구현이 기존과 같은 답을 내는지"를 검증할 수 있어야, 컴파일러라는 신뢰가 생명인 도구를 안전하게 교체할 수 있기 때문이다.

2. 개발자가 실제로 얻는 것 - 빌드와 에디터

공식 수치로 제시된 사례는 두 가지다. VS Code 코드베이스(약 150만 줄)는 빌드 약 78초에서 약 7.5초로, Sentry는 약 133초에서 약 16초로 줄었다고 보고됐다. 대략 8~10배 구간이다. 이 속도는 두 요인의 합이다. 네이티브 컴파일이 주는 약 3~4배, 그리고 이전엔 불가능했던 병렬 처리가 주는 약 3~4배다. 부수적으로 Go의 인라인 구조체가 JavaScript의 할당 위주 객체보다 메모리를 적게 써, 대형 프로젝트에서 메모리 사용량이 절반 수준으로 줄었다고 알려졌다.

본인이 더 크게 보는 체감 지점은 빌드 시간보다 에디터 반응성이다. 언어 서버가 느리면 "타이핑하는 동안 빨간 줄이 늦게 뜨는" 정도가 아니라, 자동완성 자체가 지연되어 개발자가 도구를 못 믿고 우회하게 만든다. 네이티브 언어 서버가 이 지연을 근본적으로 줄인다면, 체감 생산성은 CI 시간 단축보다 훨씬 즉각적이다. 다만 이 수치들은 벤치마크 프로젝트 기준이며, 본인 코드베이스의 실제 이득은 구성·하드웨어에 따라 달라질 수 있다는 점은 분명히 해 둔다.

3. 마이그레이션의 진짜 함정 - Compiler API 공백

여기가 이번 GA에서 가장 실무적으로 중요한 대목이라고 판단한다. tsc의 타입 검사 결과 자체는 6.0과 최대한 동일하게 유지하는 것이 목표지만, 프로그래매틱 Compiler API는 7.0 네이티브 컴파일러에 아직 없다. 7.1에서야 제공될 예정이라는 점이 GA에서도 재확인됐다.

3.1 무엇이 깨지는가

영향은 "코드를 컴파일하고 타입을 검사하는" 일반적인 용도가 아니라, ts.createProgram이나 ts.transpileModule 같은 API를 직접 호출해 AST를 조작하는 도구에 집중된다고 보고된다. 예컨대 AST 기반 코드 생성·리팩토링 도구, 선언 파일(.d.ts)을 프로그래매틱하게 만드는 번들러 플러그인, tsc를 네이티브 바이너리로 그대로 갈아 끼운 테스트 러너 설정 등이 후보로 거론된다. 반면 에디터 확장이 쓰는 Language Service Plugin API는 7.0에도 그대로 남아 있어, 대다수의 IDE 자동완성·린트 플러그인은 이 공백과 별개로 계속 동작하는 것으로 파악된다.

3.2 안전망 - 구버전 병행

이 공백을 메우기 위해 이전 API를 그대로 노출하는 호환 패키지가 함께 제공된다. 새 tsc는 빠른 네이티브 컴파일러를 가리키고, 별도 실행 파일로 예전 JavaScript 기반 컴파일러와 API를 그대로 쓸 수 있게 하는 방식이다. 즉 빌드·타입 검사는 새 컴파일러로 옮기되, API에 의존하는 도구만 예전 실행 파일에 남겨 두는 이원 운용이 공식적으로 권장되는 과도기 전략이다.

3.3 예고된 브레이킹 체인지

API 공백과 별개로, TypeScript 7은 strict 기본 활성화, target: es5 제거(최소 ES2015), module의 AMD·UMD·SystemJS 형식 제거, moduleResolution: node10 제거 같은 정리를 함께 확정했다. 이들은 RC 단계부터 예고됐고, TypeScript 6.0에서 미리 경고를 띄우도록 설계돼 있어 성실히 6.0으로 먼저 올려 두면 대부분 예측 가능한 종류다.

4. esbuild·swc와의 관계 - 경쟁이 아니라 역할 재조정

자연스럽게 나오는 질문이 있다. "이미 esbuild나 swc로 빌드가 빠른데, TypeScript 7이 왜 필요한가?" 이 질문에는 전제 하나가 숨어 있다. esbuild와 swc는 애초에 타입을 검사하지 않는다. 타입 주석을 제거만 하고 통과시키는 트랜스파일러이기 때문에 빠른 것이다. 그래서 실무에서는 이 둘로 변환은 빠르게 하고, 정작 느린 타입 검사는 별도로(에디터에서, 또는 CI에서만, 때로는 아예 생략) 돌리는 이원화 구조가 널리 퍼졌다.

TypeScript 7은 이 이원화의 필요성 자체를 줄인다. 타입 검사를 담당하는 tsc 본체가 빨라지면, "빌드는 빠르게, 검사는 나중에"라고 쪼갤 이유가 약해진다. 그렇다고 esbuild·swc가 밀려나지는 않는다. 둘은 번들링·미니파이·JSX 변환까지 담당하는데, 이는 tsc가 애초에 해 온 적이 없는 역할이다. 본인의 해석은 이렇다. TypeScript 7은 "타입 검사가 느려서 어쩔 수 없이 우회했던" 워크플로를 재검토하게 만들지만, 번들러로서의 esbuild·swc는 그대로 남는다. 경쟁이라기보다 각자의 영역이 다시 명확해지는 쪽에 가깝다.

5. 실무 도입 시점 판단

결국 가장 중요한 질문으로 돌아온다. 지금 옮겨야 하는가, 기다려야 하는가. 본인은 워크로드 기준으로 나눠 판단하는 것을 권한다.

5.1 지금 옮겨도 되는 경우

tsc와 에디터 위주로만 쓰고, ts-morph류의 AST 조작 도구나 tsup --dts 같은 API 의존 빌드 단계가 없는 팀이라면 지금 전환해도 위험이 낮다고 판단한다. 특히 CI 시간과 대형 모노레포 타입 체크가 병목이었던 팀에게는 체감 효과가 즉시 나타날 가능성이 크다.

5.2 기다려야 하는 경우

내부 코드 생성기, 커스텀 트랜스포머, 스키마·타입 기반 코드 생성 도구를 운영 중이라면 서두르지 않는 편이 안전하다. Compiler API가 7.1에서 어떤 형태로 나올지 확인한 뒤 전환해도 늦지 않는다. 그 사이에는 빌드·타입 검사만 새 컴파일러로 옮기고, API 의존 도구는 병행 제공되는 예전 실행 파일에 남겨 두는 이원 운용이 현실적인 절충안이다.

5.3 공통 체크리스트

어느 쪽이든 첫 단계는 같다. 먼저 TypeScript 6.0으로 올려 사용 중단 경고를 전부 확인하고, 그다음 신구 컴파일러를 CI에서 나란히 돌려 출력 diff가 없는지 검증한 뒤 전환하는 순서다. 벤더가 강조하는 속도 수치보다, 본인 코드베이스의 실제 diff와 도구 체인 호환성 점검이 훨씬 신뢰할 수 있는 근거다.

결론: 네이티브화는 시작이지 완성이 아니다

TypeScript 7의 GA는 "자바스크립트 생태계 도구가 자기 언어를 벗어나 네이티브로 옮겨가는" 더 큰 흐름의 한 장면이다. Vite·esbuild·SWC·Rspack 같은 도구들이 이미 이 흐름 위에 있었고, TypeScript는 그중 가장 오래 버틴 축이 대열에 합류한 사례에 가깝다. 다만 이번 GA가 보여주는 것은 속도만이 아니다. 속도를 얻는 대신 프로그래매틱 API라는 확장성 일부를 임시로 내줬다는 사실도 함께 드러났다. 이 균형을 이해하고 본인 도구 체인을 점검한 뒤 옮기는 팀과, 속도 수치만 보고 무작정 올리는 팀의 결과는 다를 것이다.
