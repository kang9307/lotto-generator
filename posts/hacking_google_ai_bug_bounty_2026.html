AI로 구글 취약점 찾아 7억 원 버그바운티 — AI 보조 보안 연구의 부상

보안 연구자가 AI를 보조 도구로 활용해 구글 API 수천 개를 분석하고 책임공개로 거액을 받은 사례 — 방법론, 생태계 변화, 방어자 관점을 분석한다

2026-06-24 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 7억 원짜리 질문

2026년 6월, 보안 연구자 brutecat이 공개한 블로그 포스트가 보안 커뮤니티에서 큰 주목을 받았다. 원문 제목은 "Hacking Google with AI"다. 핵심은 간단하다. AI(구체적으로는 Claude)를 보조 도구로 삼아 구글의 공개 API 1,500개 이상을 체계적으로 분석한 결과, 단 3개월 만에 약 50만 달러(한화 약 7억 원)의 버그바운티를 획득했다. GeekNews(news.hada.io)에도 29pts를 기록하며 빠르게 퍼졌다.

이 사례를 단순한 "해커의 성공담"으로 읽으면 절반도 이해한 게 아니다. 진짜 주목해야 할 것은 세 가지다. 첫째, AI가 보안 연구 방법론을 어떻게 바꾸고 있는가. 둘째, 버그바운티 생태계가 AI 시대에 어떻게 진화하는가. 셋째, 방어자(개발팀·보안팀) 입장에서 무엇을 달리 해야 하는가. 이 글은 그 세 축을 분석한다. 공격 재현이나 익스플로잇 방법은 다루지 않는다. 교육과 방어 목적이다.

출발점을 분명히 한다. 이 분석에서 언급되는 금액·취약점 유형·방법론은 연구자의 공개 블로그 포스트(brutecat.com)와 다수 보안 미디어 보도(TechRepublic, GBHackers, CyberPress 등)를 교차 검증한 범위 안에서만 서술한다. 확인되지 않은 사항은 명시한다.

1. 사례 개요 — AI로 API 1,500개를 분석하다

연구자는 구글 서비스들이 내부적으로 사용하는 "Discovery Documents"라는 공개 API 명세서(Swagger 문서와 유사한 역할)를 수집하는 것에서 출발했다. 61,200개의 Android APK와 2,800개 이상의 구글 웹 도메인을 분석해 3,600개의 API 키와 1,500개 이상의 API를 발굴했다. 이 규모의 분석을 수작업으로 진행하면 수개월이 필요하다. 연구자는 여기서 AI를 끌어들였다.

1.1 AI 활용 방식 — MCP + Claude

연구자는 Claude를 MCP(Model Context Protocol) 도구와 연결해, 수집한 API 명세서를 AI가 참조할 수 있도록 구성했다. 단순히 "이 API에 취약점이 있나?"라고 묻는 방식이 아니었다. 초기에는 AI가 거짓양성을 많이 내거나 조기에 분석을 포기하는 문제가 있었고, 연구자는 프롬프트를 반복 개선했다. 엔드포인트를 논리적 그룹으로 묶어 넣고, 각 테스트에 재현 가능한 operation ID를 첨부하고, "존재 열거만으로는 취약점으로 보고하지 말 것" 같은 구체적 가이드라인을 제공했다. 결과적으로 AI의 정탐률이 50% 이상으로 올라갔다고 연구자는 밝혔다.

여기서 중요한 점이 있다. AI가 취약점을 "찾아낸" 것이 아니라, 방대한 표면을 빠르게 훑어 인간 연구자가 집중해야 할 후보를 추려줬다는 것이다. 최종 검증, 보고서 작성, 구글과의 커뮤니케이션은 모두 연구자가 직접 수행했다. AI는 피로 없이 반복 검토하는 탐색 파트너였다.

1.2 발견된 취약점의 성격

공개 보고서에 따르면 발견된 취약점들은 정교한 공격 기법이 아니라 반복되는 기본 보안 실수에서 비롯됐다. 대표적 패턴은 세 가지다.

  • 스테이징 환경의 프로덕션 데이터 노출: 테스트용 서버가 실제 프로덕션 데이터를 가리키면서 접근 제어가 없었다.
  • 인증·인가 체크 누락: 내부 전용으로 설계된 API가 외부에서 인증 없이 접근 가능한 상태였다.
  • 마이크로서비스 간 느슨한 경계: 서비스 간 데이터 소유권 검증이 없어, 한 서비스에서 다른 서비스의 민감 데이터를 조회할 수 있었다.

Google Voice 계정 정보 접근(약 2만 달러), YouTube 비공개 영상 ID 유출(약 1.2만 달러), Widevine DRM 키 조회(약 1.6만 달러) 등 다수의 개별 취약점이 이 범주에 속했다. 가장 심각한 취약점은 신고 후 수 시간 내 P0/S0 등급으로 패치됐다고 연구자는 기술했다. 개별 취약점의 상세한 악용 방법은 이 글에서 다루지 않는다.

2. 책임공개와 버그바운티 — 윤리적 기반

이 사례가 단순한 "해킹"과 근본적으로 다른 이유는 책임공개(Responsible Disclosure) 원칙에 있다. 연구자는 발견한 모든 취약점을 구글에 먼저 신고했고, 구글의 VRP(Vulnerability Reward Program) 채널을 통해 처리됐다. 패치가 완료된 후 연구자가 기술 내용을 공개했다.

2.1 책임공개가 중요한 이유

취약점을 발견했다는 사실 자체는 중립적이다. 같은 취약점을 발견하고도 악용하는 행위자, 조용히 묻어두는 행위자, 즉각 공개해 혼란을 만드는 행위자, 그리고 책임공개로 수정을 이끄는 연구자가 있다. 버그바운티 프로그램은 마지막 유형을 경제적으로 유인하는 구조다. 구글은 2025년 한 해만 VRP 보상으로 1,710만 달러를 지급했다. AI 취약점 보상 프로그램도 별도 운영 중이다.

책임공개의 핵심 요건은 두 가지다. 첫째, 업체에 패치 시간을 충분히 줄 것(업계 관행상 90일). 둘째, 공개 범위를 기술 세부 내용 수준으로 제한하고 실제 악용 가능한 도구나 코드는 포함하지 말 것. 이 연구자는 두 요건을 지켰다.

2.2 구글의 반응과 평가

보도된 내용에 따르면 일부 보고서는 "예외적 품질"이라는 평가를 받았고, 이는 추가 보상으로 이어졌다. 구글이 개별 취약점 보고서를 단순히 처리하는 것을 넘어 연구 방법론의 완성도까지 평가한다는 점은 주목할 만하다. 버그바운티 생태계가 성숙할수록 단순 보고 건수보다 연구 깊이와 재현 가능성이 더 중요해지는 방향으로 진화하고 있다.

3. AI가 바꾸는 보안 연구 방법론

이 사례는 AI가 보안 연구에서 어떤 역할을 맡기에 적합한지를 구체적으로 보여준다. 2026년 기준으로 AI 보조 보안 연구의 특성을 정리하면 다음과 같다.

3.1 AI가 잘하는 것

광범위한 표면 커버리지가 AI의 가장 큰 강점이다. 1,500개 API 엔드포인트를 일관된 기준으로 반복 검토하는 작업은 인간에게 극도로 피로한 작업이다. AI는 집중력 저하 없이 동일 기준을 유지한다. 또한 패턴 인식에 강하다. 접근 제어 누락, 인증 부재, 스테이징-프로덕션 혼용 같은 반복적 보안 실수 패턴을 빠르게 플래그할 수 있다. 마지막으로 대규모 코드·문서 독해다. 방대한 API 명세서를 빠르게 소화해 이상한 조합이나 논리적 모순을 찾는 데 유용하다.

3.2 AI가 못하는 것

AI는 맥락 의존적 비즈니스 로직 취약점을 포착하기 어렵다. 기술 명세에는 문제가 없어 보이지만 실제 비즈니스 맥락에서 악용 가능한 취약점은 도메인 지식이 있는 인간 연구자가 더 잘 찾는다. 또한 최종 판단은 항상 인간의 몫이다. AI가 "이 엔드포인트는 취약할 수 있다"고 플래그해도, 실제로 취약한지, 어느 정도 위험한지, 어떻게 보고할지는 연구자가 결정한다. 이 사례에서도 연구자가 AI 정탐률을 50%라고 언급한 것은 절반은 여전히 인간이 걸러야 했다는 의미다.

3.3 프롬프트 엔지니어링이 연구 설계가 되다

흥미로운 관찰은 이 연구에서 프롬프트 설계가 연구 설계의 핵심이었다는 점이다. 어떤 범위를 분석할 것인지, AI에게 어떤 기준을 줄 것인지, 어떤 결과물 형식을 요구할 것인지가 최종 성과에 직접 영향을 미쳤다. 이는 AI 시대의 보안 연구자에게 새로운 역량이 요구된다는 뜻이다. 좋은 해커는 이제 좋은 프롬프트 엔지니어이기도 해야 한다.

4. 버그바운티 생태계의 변화

이 사례는 버그바운티 생태계 전반에 걸쳐 나타나는 변화의 압축판이다. 2026년 6월 현재, 생태계는 세 방향에서 동시에 변하고 있다.

4.1 AI로 인한 연구 속도와 규모의 증가

AI 도구의 보급으로 보안 연구자 한 명이 커버할 수 있는 공격 표면이 크게 넓어졌다. 이는 버그바운티 프로그램 입장에서 양면이다. 좋은 면은 더 많은 취약점이 악용되기 전에 발견된다는 것이다. 도전적인 면은 보고서 품질 편차가 커진다는 것이다. 규모만 늘리고 검증은 느슨한 저품질 보고가 쏟아지면 프로그램 운영팀의 부담이 커진다. 이 때문에 버그바운티 플랫폼들은 재현 가능성·영향도·보고 품질 기준을 강화하는 방향으로 움직이고 있다.

4.2 AI 자체가 취약점 대상이 되다

2026년에는 AI 제품 자체가 버그바운티 대상이 됐다. OpenAI, Anthropic, 구글 모두 AI 전용 VRP를 운영하거나 확대했다. 프롬프트 인젝션, 학습 데이터 추출, 안전 장치 우회 같은 AI 특화 취약점이 새로운 카테고리로 부상했다. HackerOne 통계에 따르면 AI 취약점 유효 보고 건수는 210% 증가했다. 보안 연구의 전선이 서버에서 AI 모델로도 확장되고 있다.

4.3 윤리 논쟁 — 도구는 중립이지만 사용은 중립이 아니다

AI 도구가 보안 연구에 쓰이면 같은 도구가 악의적 탐색에도 쓰일 수 있다는 우려가 있다. 이것은 사실이다. 그러나 현재 가장 활발하게 사용되는 방향은 방어 쪽이다. 이유는 단순하다. 윤리적 연구자는 공개적으로 활동하며 평판을 쌓고, 버그바운티로 경제적 유인을 얻는다. 악의적 행위자는 법적 위험을 감수해야 한다. 버그바운티 생태계가 성숙할수록 이 경제적·법적 비대칭성은 더 강화된다. 이 사례는 그 비대칭성이 작동한 좋은 예다.

5. 방어자 관점 — 이 사례가 알려주는 것

이 분석의 핵심 독자는 실제 서비스를 운영하는 개발자·보안팀이다. 이 사례가 방어 측에 주는 교훈을 구체적으로 정리한다.

5.1 스테이징 환경을 프로덕션처럼 대우하라

이번 사례에서 발견된 취약점 중 상당수는 스테이징 환경이 프로덕션 데이터를 가리키면서 접근 제어가 없었던 구성 오류에서 비롯됐다. "테스트 환경이니까 보안은 나중에"라는 생각은 위험하다. 스테이징에서도 프로덕션 수준의 접근 제어, 인증 요구사항, 네트워크 분리를 적용해야 한다. 특히 마이크로서비스 아키텍처에서는 스테이징 서비스가 프로덕션 데이터 스토어에 연결되는 상황을 체계적으로 차단해야 한다.

5.2 API 노출 면을 정기적으로 감사하라

서비스가 성장하면 API 엔드포인트 수는 자연히 증가하고, 오래된 엔드포인트는 목록에서 누락되기 쉽다. 이 연구자가 발견한 방식 — APK에서 API 키 추출, 도메인에서 엔드포인트 수집 — 은 공격자도 쓸 수 있는 방법이다. 방어자 입장에서는 스스로 이 프로세스를 수행해야 한다. 정기적으로 "우리 서비스 외부에서 접근 가능한 API 전체 목록"을 작성하고, 각각에 인증·인가·레이트리밋이 적절히 적용돼 있는지 검증하는 것이다.

5.3 AI를 방어 도구로도 활용하라

공격자가 AI로 탐색 속도를 높인다면, 방어자도 AI로 감사 속도를 높여야 한다. 코드 리뷰 과정에서 AI를 사용해 접근 제어 누락, 인증 미적용, 민감 데이터 노출 가능성을 1차 필터링하는 것은 충분히 실현 가능하다. 사람이 모든 줄을 꼼꼼히 읽는 것보다, AI로 1차 스크리닝하고 사람이 플래그된 부분에 집중하는 방식이 커버리지와 효율 면에서 낫다.

5.4 버그바운티 프로그램을 운영하거나 활용하라

외부 연구자의 시각은 내부 팀이 놓치기 쉬운 사각지대를 드러낸다. 자체 버그바운티 프로그램을 운영할 규모가 아니라면 Bugcrowd, HackerOne 같은 플랫폼을 통한 관리형 프로그램도 선택지다. 핵심은 외부 연구자가 발견한 취약점을 신속하게 처리하고 책임 있게 보상하는 문화를 갖추는 것이다. 이 신뢰가 더 많은 윤리적 연구자를 유인한다.

6. AI 보조 보안 연구의 한계와 오해

이 사례를 과대 해석하는 방향도 경계해야 한다. 몇 가지 오해를 명시적으로 짚는다.

6.1 "AI가 자동으로 해킹한다"는 오해

이번 사례는 AI가 자율적으로 취약점을 발견해 보고서를 쓴 것이 아니다. 숙련된 보안 연구자가 AI를 도구로 활용한 것이다. API 명세서 수집, 분석 파이프라인 구성, 프롬프트 설계, 결과 검증, 보고서 작성, 구글과의 커뮤니케이션 모두 연구자가 수행했다. AI는 그 과정에서 반복 검토와 패턴 인식을 담당했다. 도메인 전문성이 없는 상태에서 AI만 쥐여줘도 된다는 식의 해석은 사실과 다르다.

6.2 "대형 서비스는 뚫릴 수밖에 없다"는 오해

이 사례가 보여주는 것은 충분히 큰 공격 표면에는 언제나 구멍이 있다는 현실이다. 그것이 구글이 취약하다는 뜻은 아니다. 구글이 무한한 엔지니어링 리소스에도 불구하고 수천 개의 마이크로서비스를 완벽하게 보안 검증하기 어렵다는 현실이다. 중요한 것은 사전 예방과 신속 대응 체계를 갖추는 것이고, 구글은 P0/S0 취약점을 수 시간 내 패치한 사례처럼 대응 체계가 성숙해 있었다.

6.3 방법론 복제의 위험성

이 연구자의 방법론은 합법적 버그바운티 프로그램 범위 안에서 구글의 동의하에 수행된 것이다. 동일한 방법론을 버그바운티 프로그램이 없는 서비스에, 또는 프로그램 범위를 벗어나 적용하면 사이버 범죄가 된다. 국가마다 법이 다르지만, 무단 접근은 민형사상 책임을 수반한다. 보안 연구는 반드시 적법한 범위 안에서, 명확한 허가를 받고 수행해야 한다.

7. 2026년 기준 — AI 보안 연구의 현황과 전망

2026년 6월 기준으로 AI 보조 보안 연구는 주류로 진입했다고 볼 수 있다. 몇 가지 데이터가 이를 뒷받침한다.

구글 VRP는 2025년 한 해 1,710만 달러를 지급했고, AI 관련 취약점 보상 전용 프로그램을 별도 운영하고 있다. OpenAI는 2026년 3월 월 100만 달러 규모의 Safety Bug Bounty Program을 시작했다. Anthropic 역시 2026년 5월 HackerOne 공개 프로그램을 런칭했다. HackerOne에 따르면 유효 AI 취약점 보고는 전년 대비 210% 증가했다.

방향성은 명확하다. AI는 보안 연구의 도구이자 대상이 됐다. 공격 표면이 AI로 확장되면서 보안 연구자의 역량에 AI 활용 능력이 추가됐다. 동시에 AI 시스템 자체의 취약점 — 프롬프트 인젝션, 학습 데이터 노출, 안전 우회 — 이 새로운 연구 영역이 됐다. 버그바운티 생태계는 이 변화를 흡수하며 프로그램 범위를 넓히고 있다.

8. 결론 — 방어와 윤리가 함께 간다

brutecat의 사례는 AI 시대 보안 연구의 전형적인 모범 사례로 기록될 것이다. AI를 활용해 탐색 범위를 확장하고, 책임공개 원칙을 지키고, 합법적 버그바운티로 가치를 인정받았다. 7억 원이라는 금액 못지않게 중요한 것은 그 과정이 윤리적이었다는 점이다.

방어자 관점에서 이 사례의 메시지는 단순하다. AI는 탐색 속도를 높인다. 공격자도 그 속도를 누린다. 방어자가 먼저 그 속도를 활용해 자신의 취약점을 찾아야 한다. 스테이징 환경 보안, API 노출 면 감사, 버그바운티 프로그램 운영 — 이 세 가지는 AI 시대에 더욱 중요해진 방어 기제다.

마지막으로 하나를 강조한다. AI는 보안을 자동화하지 않는다. 보안 전문가의 판단을 보조하고 속도를 높인다. 판단과 책임은 여전히 인간의 몫이다. 이 분리를 유지하는 것이 AI 시대 보안 생태계의 건강함을 지키는 조건이다.
