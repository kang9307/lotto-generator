Baidu Unlimited OCR — One-Shot Long-Document Parsing with Constant KV Cache

How R-SWA breaks the page-by-page limit and what it means for Document AI and RAG pipelines in 2026

2026-06-25 Tech

Introduction: Why OCR Has Always Been Page-by-Page

In June 2026, Baidu released Unlimited OCR. The name sounds like marketing, but the problem it addresses is specific and long-standing: why has OCR always had to slice documents into pages, and what would it take to stop doing that?

Think about how document AI actually works in practice. When you feed a contract, a research paper, or a financial report into an AI system, OCR comes first. And that first step already introduces loss. Existing LLM-based OCR models cut the document into pages, process each separately, then stitch the results together. The stitching step is exactly where errors compound: tables split across page boundaries break, multi-column layouts lose their reading order, and continuous paragraphs get severed. Unlimited OCR eliminates the stitching entirely by processing the whole document in a single pass. As of June 2026, here is an honest analysis of how far that approach actually goes.

1. The Structural Problem: Linear KV Cache Growth

The shift from rule-based OCR to LLM-based end-to-end models has been the dominant trend. Models like DeepSeek OCR represent that wave — feed in an image, get text out, with layout, math, and tables handled together.

But decoder-based LLMs carry a structural cost. Every token generated adds to the KV cache (Key-Value cache), which grows linearly with output length. For short documents this is fine. For a fifty-page report in a single context, memory spikes and generation slows sharply. The paper reports roughly a 35% throughput drop at 6,000-token outputs compared to shorter sequences.

The traditional fix was chunking: split the document by page or by fixed token count, process each chunk, combine results. But combination is precisely where errors live. A table spanning two pages cannot survive the split intact. A footnote referencing earlier text loses its target. Unlimited OCR takes the opposite route — redesign the attention mechanism so the cache stays small regardless of output length.

2. R-SWA: The Core Idea

Reference Sliding Window Attention (R-SWA) is the technical heart of Unlimited OCR. The paper describes it as mimicking how a human transcribes a book: you keep the source text in view at all times, remember the last few words you wrote, and let everything further back fade — because you can always look at the source again.

R-SWA implements this as an attention mechanism. At each generation step, the model attends to two fixed sets: all visual reference tokens (the full encoding of the input image, always accessible) and only the preceding 128 output tokens. The output attention window slides forward; tokens pushed out of it undergo soft forgetting rather than abrupt removal. The visual source stays fully visible throughout. This keeps KV cache at a constant size regardless of how long the output grows.

A key design choice: the paper reports freezing the visual encoder from DeepSeek OCR and replacing only the language decoder's attention layers with R-SWA. This preserves existing strong visual encoding capability while surgically modifying the component responsible for KV cache growth. The paper describes replacing all standard attention with R-SWA as "both effective and lossless."

2.1 Specifications

As of the June 2026 release: 3B total parameters, 500M activated, MoE architecture. Maximum context 32,768 tokens. Two inference modes: gundam (640px, speed-first) and base (1024px, layout fidelity). MIT license — free for commercial use.

2.2 Benchmark Numbers

On OmniDocBench v1.6: 93.92%, reported as a new end-to-end SOTA. Against DeepSeek OCR's 87.01% on v1.5, the gap is over 6 percentage points. Edit distance below 0.11 is maintained on 40+ page documents. Note: the v1.5/v1.6 benchmark versions differ, so direct numerical comparison requires care. Treat the figures as directional indicators, not a clean head-to-head measurement.

3. What Actually Changes — Tables, Layouts, Repetition

The practical question is not the mechanism but the outcome: what does single-pass processing change for real documents?

3.1 Tables

Tables are the classic OCR weak point. When a table spans two pages in a page-by-page system, the two halves come out as separate text blocks that cannot be reassembled into the original structure without additional processing. Unlimited OCR holds the entire document in a single context, so a table that crosses a page boundary is treated as one structure. The paper reports 6%+ improvement in formula and table extraction categories.

3.2 Multi-Column Layouts

Two-column academic papers are notorious for reading-order errors in OCR. A spatially naive system reads left-to-right by position, so the right column's first paragraph gets interleaved with the left column's content. Since Unlimited OCR reads layout visually across the full page context during decoding, this class of ordering errors is reduced. Independent validation on all layout variants is still limited — test your specific document types before committing.

3.3 Repetition Suppression

Long-generation models can loop on repeated elements: headers, footers, table row patterns. Unlimited OCR inherits and extends DeepSeek OCR's ngram-based suppression mechanism, applying the constraint across the full sliding window rather than only local context. The paper notes this becomes especially important for hundred-page documents.

4. Chinese Language Strength — The Baidu Factor

The case for Unlimited OCR's strength on Chinese documents is not simply that a Chinese company built it. Baidu is China's largest search engine, with decades of large-scale Chinese document processing experience embedded in its infrastructure and training data.

Chinese documents present specific OCR challenges: character complexity, simplified/traditional mixing, vertical text orientation, Han-Latin mixed notation, and table formatting conventions that differ from Western documents. OmniDocBench includes Chinese-English mixed documents, making its SOTA result an indirect indicator of Chinese parsing capability. Domain-specific performance — legal classical Chinese, technical jargon — still needs separate validation.

The paper also describes R-SWA as a "general-purpose parsing attention mechanism" applicable beyond OCR to speech recognition, translation, and multimodal processing — any task requiring long output generation while maintaining access to a fixed source. This positions Unlimited OCR as a potential infrastructure layer for document AI, not merely a specialized OCR tool.

5. RAG Pipeline Integration — Where Parsing Quality Compounds

As RAG (Retrieval-Augmented Generation) has become the dominant enterprise AI pattern, the quality of document preprocessing determines everything downstream. No matter how capable the LLM, if the input text is structurally corrupted, the answers will be too.

5.1 How Parsing Errors Propagate

A table flattened by page-by-page OCR becomes individual text lines that the chunker treats as separate units. A scrambled multi-column reading order embeds semantically wrong sequences into vectors. These corrupted chunks get indexed, and retrieval surfaces the wrong passages. Fixing this at the LLM layer is impossible — the corruption is in the data. Better parsing at the source fixes it upstream.

5.2 Self-Hosting Advantage

The documents entering a RAG pipeline are typically confidential: contracts, financial reports, internal research. Sending them to an external OCR API introduces data security exposure. Unlimited OCR's MIT license enables fully self-hosted deployment with no data leaving your infrastructure. SOTA-class parsing quality without external API dependency is a meaningful enterprise differentiator.

5.3 Integration Paths

Two integration routes: HuggingFace Transformers for direct Python calls (simplest), and SGLang server for an OpenAI-compatible API that reuses existing LLM client code. PDF inputs are converted to images via PyMuPDF at 300 DPI before processing. Batch processing via infer_multi() supports high-volume workflows.

7. Honest Limitations

A one-sided analysis is useless. Three limits deserve explicit attention.

7.1 Hallucination Risk

LLM-based OCR can generate text not present in the source image — a risk rule-based OCR does not share. Degraded scans and damaged documents amplify this. GeekNews discussion thread participants flagged this as a production concern. Confidence thresholds or cross-verification with the source image are necessary for high-stakes deployments.

7.2 The 32K Token Ceiling

The maximum context of 32,768 tokens sits awkwardly with the name "Unlimited." It handles 40+ pages comfortably, but truly thick documents — multi-hundred-page regulatory filings, comprehensive technical manuals — still require splitting. The name overclaims; the actual scope is "long" not "unlimited."

7.3 Maturity and Hardware Demand

CUDA 12.9 is a recent requirement, and the 3B model at 1024px resolution on long documents has substantial GPU memory needs. Released in late June 2026, community optimizations — quantization, smaller variants — have not yet accumulated. Benchmark your target hardware before committing to production deployment.

8. The Broader Signal — Documents as Wholes

Unlimited OCR is not just a benchmark improvement. It signals a shift in how document AI treats its fundamental unit of processing.

Every prior pipeline architecture split documents because infrastructure constraints demanded it — not because documents are naturally page-sized. Documents are semantically whole: tables require context, layouts carry logical structure, sections reference each other. R-SWA is one architectural answer to removing the infrastructure constraint that forced the split.

If this approach matures and scales, the downstream effects are significant. RAG quality improves as parsing errors decrease. Document automation becomes more reliable as structural integrity is preserved. Regulatory and legal document processing — where precision matters — becomes more tractable. The weakest link in a data pipeline sets its ceiling. A better parsing layer raises the ceiling for everything built on top.

9. Three Things to Do This Week

9.1 Test on Your Document Types

Download the model from HuggingFace and run it on 10–20 samples of your actual document types: contracts, academic papers, financial statements — whatever your pipeline handles. Prioritize documents with tables crossing page boundaries, multi-column layouts, and embedded formulas. Your domain benchmark is more useful than any published number.

9.2 A/B Your RAG Parsing Stage

If you use existing OCR or PDF text extraction (pdfplumber, PyMuPDF text mode), swap in Unlimited OCR on a held-out set and measure downstream LLM response quality against a golden set. Quantifying the quality lift — if any — on your data makes the adoption decision concrete rather than theoretical.

9.3 Calculate Self-Hosting TCO

If you currently pay for an external OCR API and process confidential documents, compute the total cost of ownership for self-hosted Unlimited OCR against API costs at your actual volume. Factor in GPU capital, power, and engineering overhead. For high-volume or security-sensitive workloads, the MIT license creates a real TCO advantage worth quantifying.
