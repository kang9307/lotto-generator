The bytes and output shown here are copied from runs of powershell.exe -NoProfile in Windows PowerShell 5.1.19041.6456 on Korean Windows 10 with console code page 949. PowerShell 7 (pwsh) was not available in the environment, so statements about 7 are limited to sentences in the official documentation and are not presented as executed. What a BOM is and why cp949 text breaks are covered in the BOM guide and the cp949 mojibake guide; this article stays with the per-cmdlet byte measurements for 5.1 and the workarounds. Paths in the output were replaced with C:\demo.

How it was measured - one string written many ways, then read as bytes

Encoding problems are invisible on screen. Notepad, VS Code and terminals guess an encoding from the BOM and the byte pattern and display the text as if nothing were wrong, so the fact that text looks fine is not evidence. For that reason every item uses the same test string, 한글 ab, and reads the whole file back as hexadecimal bytes. The string is five characters: U+D55C, U+AE00, a space, a and b. It is 9 bytes in UTF-8, 7 bytes in CP949 (each Korean character takes 2 bytes) and 10 bytes in UTF-16LE. Because the cmdlets append a CRLF (0D 0A), the file length also includes 2 more bytes (4 in UTF-16) plus the length of any BOM.

The state of a session started without a profile is shown below. -NoProfile was used because a profile that changes $PSDefaultParameterValues or the console encoding makes the same command write different bytes (section 6).

Console.OutputEncoding : ks_c_5601-1987 (949)
                    Console.InputEncoding  : ks_c_5601-1987
                    $OutputEncoding        : us-ascii
                    Encoding.Default       : ks_c_5601-1987

The console output and input encodings are 949, $OutputEncoding is ASCII and the .NET default encoding is 949. These four values are the background for the whole article, and in sections 9 and 10 they act at different points.

Measurements per cmdlet - which writes UTF-16LE and which writes CP949

Four things can be read from the table.

  • Even inside one session, > writes UTF-16LE while Set-Content writes CP949. There is no single value that can be called the default encoding of 5.1.
  • -Encoding utf8 added a BOM in every cmdlet. Out-File, Set-Content and Export-Csv produced 14, 14 and 21 bytes, each starting with EF BB BF.
  • The default of Export-Csv and -Encoding ascii save characters they cannot represent as 3F (a question mark). Once a file contains 3F, there is no way to recover the original characters.
  • The .NET WriteAllText writes UTF-8 without a BOM unless told otherwise, which is the basis of the workaround in section 7.

Why they differ - the documented rules and the one place that disagrees

The about_Character_Encoding document (5.1 edition) states this inconsistency itself: Windows PowerShell generally uses UTF-16LE, but the default encoding used by cmdlets is not consistent. Condensed, its write rules are as follows. Out-File and > and >> create UTF-16LE, which notably differs from Set-Content and Add-Content. Set-Content and Add-Content use Default, meaning the ANSI legacy code page of the active system locale, when the target file is empty or does not exist. Export-Csv creates Ascii files. And from 5.1 on, the redirection operators call Out-File. Every row of the table above agrees with these sentences.

The disagreement is in the Notes section of the about_Redirection document (5.1 edition). It says that the redirection operators use UTF8NoBOM encoding, while the measurement on 5.1.19041 was UTF-16LE starting with FF FE. The about_Character_Encoding document of the same 5.1 edition says UTF-16LE, so the measurement matches the latter and disagrees with the former. The document does not say which version that sentence describes, so the reason cannot be stated with certainty. It is explicit in about_Character_Encoding that PowerShell 6 and later default to utf8NoBOM, so the possibility that the description of that side leaked into the 5.1 page remains a presumption.

The practical conclusion is a single one. Behavior that differs between versions has to be confirmed in bytes rather than from one documentation page, and a script that creates files should state the encoding explicitly instead of leaving it to the default.

-Encoding utf8 means BOM, and utf8NoBOM does not exist in 5.1

In the table, -Encoding utf8 started with EF BB BF. The 5.1 about_Character_Encoding describes the UTF8 value as UTF-8 with BOM and states that in Windows PowerShell every Unicode encoding except UTF7 always creates a BOM. In the value list for PowerShell 7.1 and later, by contrast, utf8 is UTF-8 without a BOM and utf8BOM is used when a BOM is needed. The same word utf8 therefore produces different bytes depending on the version.

That raises the question of whether utf8NoBOM can simply be used in 5.1, and it is rejected as shown below.

PS> $t | Set-Content bad.txt -Encoding utf8NoBOM
                    Unknown, String, Unicode, Byte, BigEndianUnicode, UTF8, UTF7, UTF32, Ascii, Default, Oem, BigEndianUTF32

The error message on a Korean locale says the value cannot be converted to the type Microsoft.PowerShell.Commands.FileSystemCmdletProviderEncoding and lists the accepted values on its last line; the output above is that last line. Neither utf8NoBOM nor utf8BOM is in the list. In summary:

  • In 5.1, -Encoding utf8 is UTF-8 with a BOM. The cmdlets have no switch that turns the BOM off.
  • utf8NoBOM fails at parameter binding, so it cannot be used unchanged in a script that must run on both 5.1 and 7.
  • When UTF-8 without a BOM is needed, the .NET call in section 7 is the method confirmed in this environment.

Appending - the cmdlets that follow the existing encoding and those that do not

More dangerous than the default for a new file is appending to a file that already exists. These are the results of creating a first line, 한글 ab, in several ways and then appending one line, x.

The result agrees with the sentences in the official documentation. Out-File -Append and >> make no attempt to match the encoding of the existing file and use the default encoding, while Add-Content, absent an encoding parameter, detects the existing encoding and applies it to the new content. The document also says that Default (ANSI) is used when the existing file has no BOM.

  • A script that accumulates a log with >> creates a file whose encoding changes from the second line on. When CP949 and UTF-16LE are mixed in one file, one section is garbled whichever encoding it is read with.
  • When appending is needed, use Add-Content, or give Out-File -Append the encoding of the existing file. The latter is the approach the documentation requires, but it was not executed here.

Changing the default - what works and what does not

According to the documentation, the redirection operators call Out-File from 5.1 on, so the default encoding can be changed with $PSDefaultParameterValues. This is the result of changing it and then running a redirection.

PS> $PSDefaultParameterValues['Out-File:Encoding'] = 'utf8'
                    PS> $t > redir2.txt; hx redir2.txt
                    redir2.txt     len=14  EF BB BF ED 95 9C EA B8 80 20 61 62 0D 0A

> changed from UTF-16LE to UTF-8. However, the first 3 of the 14 bytes are EF BB BF, so the BOM remains. What this method achieves is making redirection UTF-8; it does not remove the BOM.

The value is a session-wide setting. The documentation also warns that putting it in a profile affects every command and script that does not specify an encoding, and recommends setting it inside the scripts or modules that need the behavior. That is also why the measurements here use -NoProfile. A script that creates files is safer if it states the encoding in code, so that its result does not depend on the caller's profile. The form $PSDefaultParameterValues['*:Encoding'] that the documentation introduces was not run, so its effect is not vouched for.

Writing UTF-8 without a BOM - .NET calls and raw bytes

In 5.1 the way to produce UTF-8 without a BOM lies outside the cmdlets. Three methods were measured.

[IO.File]::WriteAllText("$dir\net_nobom.txt", $t, (New-Object Text.UTF8Encoding($false)))
                    [IO.File]::WriteAllLines("$dir\wal.txt", [string[]]@('한글 ab'), (New-Object Text.UTF8Encoding($false)))
                    [byte[]]$bytes = (New-Object Text.UTF8Encoding($false)).GetBytes("한글 ab`n")
                    Set-Content bytes.txt -Value $bytes -Encoding Byte
                    # each call is followed by: hx 
net_nobom.txt  len= 9  ED 95 9C EA B8 80 20 61 62
                    wal.txt        len=11  ED 95 9C EA B8 80 20 61 62 0D 0A
                    bytes.txt      len=10  ED 95 9C EA B8 80 20 61 62 0A
  • WriteAllText with UTF8Encoding($false) gives 9 bytes, with no BOM and no newline added.
  • WriteAllLines appends a CRLF to each line and gives 11 bytes. It cannot be used when only LF is wanted.
  • Set-Content -Encoding Byte writes a byte array as it is; Byte is in the 5.1 value list. Because the newline was put in by hand, only the single byte 0A remains.

There is one more trap with .NET calls: a relative path is resolved against the current directory of the process, not against the current location of PowerShell.

PS> New-Item -ItemType Directory -Force sub | Out-Null
                    PS> Set-Location sub
                    PS> [IO.File]::WriteAllText('rel.txt', 'x')
                    PS> (Get-Location).Path
                    C:\demo\work\sub
                    PS> [Environment]::CurrentDirectory
                    C:\demo
                    PS> Test-Path rel.txt
                    False

After Set-Location sub, the .NET current directory stayed at the folder where the process was started, and rel.txt could not be found in sub (False). The file had been written on the .NET directory side. This is why every .NET example above uses an absolute path of the form "$dir\file". Converting to an absolute path before the call, for example Join-Path (Get-Location) name, avoids the problem.

Files with a BOM were read correctly both ways because the reader finds the encoding from the BOM. Without a BOM the default read interpreted the bytes as CP949, so only the BOM-less UTF-8 file was garbled. Conversely, giving -Encoding UTF8 to the CP949 file garbles it. The .NET ReadAllText assumes UTF-8, so it read the BOM-less UTF-8 file correctly and the CP949 file garbled.

The real trouble is writing back what was garbled while reading. A common pattern is to read a configuration file, replace some strings and save it.

PS> Get-Content net_nobom.txt | Set-Content rt.txt -Encoding UTF8
                    PS> hx rt.txt
                    rt.txt         len=13  EF BB BF 3F EC 92 93 3F 20 61 62 0D 0A

The original bytes ED 95 9C EA B8 80 turned into a question mark and unrelated characters at the moment of reading, and the save step recorded that result as UTF-8 with a BOM, leaving 3F EC 92 93 3F. One conversion happened on read and another on write, and the Korean text cannot be restored from this file. Batch-processing a BOM-less file that contains Korean with Get-Content | Set-Content produces exactly this. Give -Encoding UTF8 when reading and state the encoding when writing, as in section 7.

Sending to a native program - $OutputEncoding

$OutputEncoding is not about files. It is the encoding PowerShell uses when it sends data to the standard input of an external program. The documentation says the default is ASCII and that in most cases it should match [Console]::InputEncoding. It was checked by letting Python print the raw bytes it received on standard input.

$py = 'import sys; print(sys.stdin.buffer.read())'
                    $t = '한글'
                    $t | python -c $py
                    $OutputEncoding = [Text.Encoding]::UTF8
                    $t | python -c $py
                    $OutputEncoding = New-Object Text.UTF8Encoding($false)
                    $t | python -c $py
b'??\r\n'
                    b'\xef\xbb\xbf\xed\x95\x9c\xea\xb8\x80\r\n'
                    b'\xed\x95\x9c\xea\xb8\x80\r\n'
  • With the default, the two Korean characters arrived as 3F 3F. The conversion had already happened on the sending side, and the receiver cannot recover it.
  • Assigning [Text.Encoding]::UTF8 delivers the Korean as UTF-8 but with EF BB BF at the very beginning. If the receiving program interprets the first line as it is, the BOM becomes part of the data.
  • Assigning UTF8Encoding($false) delivered only ED 95 9C EA B8 80 with no BOM.
  • In every case a 0D 0A follows at the end. As the documentation states, $OutputEncoding has no effect on the encoding of redirection or of cmdlets that save to files.

Capturing native output - [Console]::OutputEncoding

The opposite direction is decided by [Console]::OutputEncoding. PowerShell interprets the bytes an external program wrote using this encoding, turns them into a string, and then stores the string in a variable or saves it with >. It was checked by alternating Python and node output. Python writes in the locale encoding (CP949 here) when its output is piped, and this can be changed with PYTHONIOENCODING.

$x = python -c "print('한글')"
                    'Length=' + $x.Length + ' ' + (codes $x);  $x > cap1.txt; hx cap1.txt
                    $env:PYTHONIOENCODING = 'utf-8'
                    $x = python -c "print('한글')"
                    'Length=' + $x.Length + ' ' + (codes $x);  $x > cap2.txt; hx cap2.txt
                    $y = node -e "console.log('한글')"
                    'Length=' + $y.Length + ' ' + (codes $y)
                    [Console]::OutputEncoding = [Text.Encoding]::UTF8
                    $x = python -c "print('한글')"
                    'Length=' + $x.Length + ' ' + (codes $x);  $x > cap3.txt; hx cap3.txt
                    Remove-Item Env:PYTHONIOENCODING
                    $x = python -c "print('한글')"
                    'Length=' + $x.Length + ' ' + (codes $x)
python default stdout -> Length=2 codepoints=D55C AE00
                    cap1.txt       len=10  FF FE 5C D5 00 AE 0D 00 0A 00
                    PYTHONIOENCODING=utf-8 -> Length=3 codepoints=003F C493 003F
                    cap2.txt       len=12  FF FE 3F 00 93 C4 3F 00 0D 00 0A 00
                    node -> Length=3 codepoints=003F C493 003F
                    after Console.OutputEncoding=UTF8 -> Length=2 codepoints=D55C AE00
                    cap3.txt       len=10  FF FE 5C D5 00 AE 0D 00 0A 00
                    python default stdout, console now UTF8 -> Length=3 codepoints=FFFD 0471 FFFD
  • When the console is 949 and Python writes CP949, the two Korean characters are correct. Saving them with > in this state preserves the Korean as UTF-16LE (cap1).
  • When Python is made to write UTF-8, or when node is used, the same text arrives as three characters, 003F C493 003F. The cap2 file that saved this string contains 3F 00 93 C4 3F 00, so the original characters cannot be recovered.
  • Changing [Console]::OutputEncoding to UTF8 makes the Python that writes UTF-8 correct (cap3).
  • With the same setting, the Python that writes CP949 is now garbled as FFFD 0471 FFFD. This value is not something to set to UTF-8 always; it has to equal the output encoding of the other program.

For a flow that continues to saving, it is safer to separate the two steps: match the output encoding, receive the string, and write the file with a .NET call that states the encoding, as in section 7. Other environment variables such as PYTHONUTF8 were not run here.

When bash, python and git read the resulting files

  • A UTF-16LE file has 00 between the letters, so grep ab finds nothing. This is the symptom of seeing ab in the file while the search comes back empty.
  • A UTF-8 BOM file is read with U+FEFF at the start, and the JSON loader rejects it with Unexpected UTF-8 BOM (decode using utf-8-sig). Opening it with utf-8-sig resolves it.
  • git treats a UTF-16LE file as binary and does not show what changed. Even when only a BOM is added, the whole first line is shown as changed, and there is no visible difference.

The general principles behind these symptoms are covered in the BOM guide linked above and in the line-ending guide (CRLF and LF guide). An article that deals with Korean names together with the default encoding of PowerShell 5.1 is the shell quoting and Korean file name guide.

Choosing by situation

From the measurements above, this is how to choose by purpose in 5.1. Measured means the bytes were confirmed in this article.

PurposeUseBasis
Text read by bash, git, python, JSON or YAML[IO.File]::WriteAllText or WriteAllLines with UTF8Encoding($false)Measured; UTF-8 without a BOM, 9 and 11 bytes
CSV to open in ExcelExport-Csv -Encoding utf8Measured; UTF-8 with a BOM. The default is ASCII and Korean becomes 3F
Appending to an existing fileAdd-ContentMeasured; detects the existing encoding. Avoid >>
Making redirection UTF-8$PSDefaultParameterValues['Out-File:Encoding']Measured; becomes UTF-8 including the BOM
Reading a BOM-less file with Korean textGet-Content -Encoding UTF8Measured; the default read is garbled
UTF-8 input to a native program$OutputEncoding = New-Object Text.UTF8Encoding($false)Measured; arrives without a BOM
Capturing native output and saving itMatch [Console]::OutputEncoding to the program output encoding, then save with .NETMeasured; a mismatch damages the text before it is saved
Binary dataSet-Content -Encoding Byte or .NET byte writesThe documentation says redirected binary data is treated as strings and corrupted

Some values are specific to Korean Windows. The default of Set-Content is the ANSI code page of the system locale, so other locales produce other bytes. When the environment is uncertain, stating the encoding in code, as in the first row, is the most portable approach.

What could not be confirmed

  • PowerShell 7 (pwsh): it was not in the environment and could not be run. The statements that the default in 7 is utf8NoBOM and that the values utf8BOM and utf8NoBOM exist are sentences from the official documentation.
  • Which version the sentence about UTF8NoBOM in about_Redirection (5.1 edition) describes: the document does not say. Only the fact that it disagrees with the 5.1 measurement was confirmed.
  • The defaults of Set-Content and Get-Content on a system locale other than Korean: the code page in this environment was 949 only, and any other value is known only from the documentation phrase ANSI code page.
  • An environment with the Windows 10 option to use Unicode UTF-8 for worldwide language support turned on: it was not tested.
  • Windows Terminal or other hosts: only a powershell.exe started from Git Bash was used. For a session with console code page 65001, only one Python case (the last line of section 10) was checked.
  • $PSDefaultParameterValues['*:Encoding'], and appending in the original encoding with Out-File -Append -Encoding: both appear in the documentation but were not run.
  • The git working-tree-encoding setting that handles UTF-16 files as text, and the git diff output for a CP949 file: not covered.
