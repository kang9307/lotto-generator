Malware Hidden in Fake Take-Home Interviews: How LinkedIn Hiring Scams Target Developers

A single "coding assignment" repository can hand over your PC, wallet, and credentials - here's how the scam works, and how to defend against it

Jul 18, 2026 Tech & IT

Introduction: When the "Job Offer" Ships Malware Instead of an Offer Letter

It starts with a LinkedIn message. A recruiter from an unfamiliar company offers an attractive role, and as part of the process sends over a take-home coding assignment as a private GitHub repository. For a candidate, this is an entirely familiar flow - plenty of legitimate companies evaluate hands-on skill this way, so there's little obvious reason to be suspicious.

That familiarity is exactly the attack surface. Throughout 2026, security researchers have repeatedly flagged campaigns that plant obfuscated malware inside otherwise normal-looking React or Web3 frontend assignments to steal a candidate's machine and crypto wallet. In one documented incident, what looked like a routine "improve the wallet-connect UI" NFT platform task concealed more than 30,000 bytes of malicious code appended behind a build config file a developer would rarely open closely. This post breaks down how the scam works and, more importantly, lays out defenses you can apply today - not a scare piece, a playbook. Current as of July 2026.

1. The Attack Playbook - From Trust-Building to Code Execution

This scam works not because of clever exploits, but because of careful social engineering. Breaking it into stages shows exactly why each step slips past suspicion.

1.1 Approach - A Convincing Recruiter

The attacker builds a realistic-looking LinkedIn profile and reaches out first, using a real or plausibly invented company name - blockchain, fintech, and AI startups are reported to be common cover stories. The conversation follows a normal hiring flow: role description, a scheduled call, and the assignment presented as a natural next step. It's genuinely hard to distinguish from a real hiring process.

1.2 Building Trust - A Repository That Actually Works

This is the crucial part. The repository handed over isn't a sloppy lure - it's a real, functioning project that builds and runs. It comes with a concrete, realistic task ("improve the wallet-connect UI"), and the code quality reads like ordinary production work. As a result, not just candidates but even AI coding agents reviewing the code have reportedly missed the warning signs. A genuinely working project does the trust-building for the attacker.

1.3 Triggering Execution - Installing Is Infecting

The final step is a perfectly mundane request: run npm install or yarn install, then start the dev server. No elevated permissions, no unusual prompts - just a single install-and-run step is enough to trigger infection. The candidate believes they're doing a coding exercise; in reality, they've just executed the attacker's chain exactly as designed.

2. Why Developers Are Specifically Targeted

The same playbook works far better on developers than on most other professions, for structural reasons.

2.1 Running Code Is a Normal Part of the Job

Where most people would hesitate before running an unfamiliar executable, cloning a repo and running install, build, and start is simply what developers do every day. Their guard is structurally lower.

2.2 Dependency Trust Is Already Extended

Ecosystems like npm and PyPI resolve hundreds of transitive dependencies from a single install command and execute whatever lifecycle scripts they define, with no manual review by default. Developers already trust this automated chain - an attacker only needs to insert one link into it.

2.3 Wallets and Credentials Live on the Same Machine

Developer machines, especially those of Web3 and blockchain engineers, often hold source code, SSH keys, cloud credentials, API tokens, and sometimes a cryptocurrency wallet holding real funds - all in one place. One bad code execution can hand over personal assets and company infrastructure access simultaneously.

3. Where the Malicious Payload Hides

Documented incidents show the hiding spots are strikingly ordinary. Here's what to scrutinize specifically.

3.1 Config Files Are Code, Too

Build and config files - Tailwind, Webpack, ESLint - are among the least-reviewed parts of any codebase. In one documented incident, 97 lines of ordinary config were followed by more than 30,000 bytes of obfuscated code, while the editor's line view still looked short and unremarkable. A mismatch between a file's actual byte size and what an editor displays is itself a strong red flag. As one researcher who analyzed such a case put it, in short: 「config files are code」 - and so are dependencies and build tools.

3.2 Postinstall Hooks and the Dependency Chain

Lifecycle hooks in package.json - preinstall, install, postinstall - run automatically at install time with no user confirmation. Legitimate packages use them for things like compiling native modules, but they're equally a silent code-execution channel for an attacker. Bury a malicious package deep in the dependency tree and a glance at the top-level package.json won't reveal it.

3.3 After Execution - The Second-Stage Payload

The initial script is usually just a dropper. On execution, it commonly fetches an encrypted second-stage payload from a remote server, decrypts it, and runs it. The categories of capability documented in later stages include: a remotely controllable backdoor, a stealer that targets browser-stored data and cryptocurrency wallet extension storage, a file scanner that sweeps for patterns like .env, .pem, .ssh, .aws, and seed-phrase-related keywords, and a clipboard monitor that captures anything copied - passwords, private keys, recovery phrases - in real time. Notably, in documented incidents, neither traditional antivirus nor the AI coding agent reviewing the project flagged the code as malicious. Automated detection alone isn't enough to rely on.

4. Defense Checklist - What to Apply Today

The core principle behind every defense here is simple: never run untrusted code in an environment that holds real assets. Here's how to put that into practice.

4.1 Run It Only in an Isolated Environment

Clone, install, and run any take-home assignment you can't fully vet inside a disposable virtual machine or container - one with no real SSH keys, cloud credentials, or logged-in browser sessions. Make it a rule to discard the environment entirely once you're done.

4.2 Review Before You Install

Before running npm install or yarn, open package.json's scripts section and any build config files - Tailwind, Webpack, Vite - first. If a file's size looks disproportionate to the number of lines your editor shows, treat that as a warning sign on its own. Get in the habit of cross-checking actual byte size with a command like ls -la or wc -c.

4.3 Cut Off Network Access and Keep Secrets Separate

Block, or at minimum monitor, outbound network traffic from the isolated environment so connections to unfamiliar IPs stand out. Never connect a real wallet - even to a testnet - to an unverified project. The safest approach is to keep seed phrases and private keys off development machines entirely.

4.4 Disable npm Lifecycle Scripts by Default

Installing with npm install --ignore-scripts blocks automatic execution of preinstall/install/postinstall hooks. Making this a global default (npm config set ignore-scripts true) is a reasonable habit. The industry itself is moving this direction in response to supply-chain attacks, disabling install scripts by default and requiring explicit opt-in. Only allow a specific package's hook once you've confirmed it's genuinely necessary.

4.5 Red-Flag Checklist

  • The recruiter's profile has very few connections or was created recently
  • Only a single private repository is shared, with weak or missing links to an official company page
  • Commit history or license information in the repo feels inconsistent with the stated task
  • A file's actual size doesn't match the number of lines your editor displays
  • The process is unusually rushed, pressuring quick execution and a fast reply
  • Connecting a real wallet or entering a seed phrase is presented as part of the assignment

5. How to Verify a Hiring Process Is Legitimate

Separate from technical defenses, verifying the hiring process itself is your first line of defense. Check whether communication continues on an official company email domain, and whether the recruiter is a verifiable person on the company's official careers page or LinkedIn account. Ask for a video call to confirm identity, and search the company name separately for recent scam reports. Above all, use this as your baseline: legitimate hiring processes almost never require connecting a real, funded wallet or granting access to production infrastructure as part of a coding assignment.

6. Not an Isolated Incident - The Broader Threat Pattern

This kind of campaign isn't a one-off scam against a single company - it's reported as part of an ongoing, organized threat cluster that has run for years. Security researchers have tracked this category of campaign since roughly 2022 under the name "Contagious Interview," linking it to North Korean-aligned threat actors, including groups tracked as Lazarus and related sub-clusters. Public analysis describes hundreds of malicious packages repeatedly uploaded to the npm and PyPI registries, delivering infostealer and backdoor malware, with blockchain, fintech, and Web3 developers as the primary targets. Through 2026, the tradecraft kept evolving: hiding payloads inside SVG images via steganography, abusing VS Code task configurations, and using commit-tampering tools. The takeaway is that this isn't a single scam to block once - it's a continuously updated toolkit, and a technique defended against today may return tomorrow in a different form.

7. Incident Response - If You Already Ran It

If you've already executed a suspicious assignment, speed determines the blast radius.

  • Disconnect immediately: Cut network access to stop further data exfiltration and remote control.
  • Check for processes and dropped files: Look for unfamiliar node processes and executables written to temp folders, and terminate/delete them.
  • Rotate every credential: Reissue SSH keys, GitHub/npm/cloud tokens, and saved passwords; revoke the old ones.
  • Revoke browser sessions: Invalidate all active logins and sign back in fresh.
  • Move wallet funds: If a seed phrase or private key ever touched that machine, migrate funds to a new wallet without delay.
  • Delete the repo and node_modules, consider a reimage: Remove the infected project entirely, and reimage the OS if the infection's scope is unclear.
  • Report to your security team: If you're employed, assume company account and CI/CD access may be exposed too, and notify security immediately.

Conclusion: Isolate, Don't Panic

What makes this threat effective isn't a novel vulnerability - it's trust abused through a familiar process. A take-home coding assignment, something most developers encounter multiple times a year, has become an attack surface. You can't simply avoid the hiring process altogether. The realistic answer isn't fear - it's changing habits. Run unfamiliar code only in isolated environments, keep real secrets out of those environments from the start, and make pre-install review and script-blocking your default. Those three habits alone neutralize most attacks of this type. As of July 2026, this campaign category keeps evolving. Next time a take-home assignment lands in your inbox, run through this checklist first.
