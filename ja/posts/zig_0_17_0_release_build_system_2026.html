契機 — 5か月間にわたり蓄積されたビルドシステムと仕様改定

Zig開発チームは2026年10月、バージョン0.17.0を公式に発表した。公式リリースノートによれば、当初の想定を超えて5か月に及んだ開発期間において、206人の貢献者から925件のコミットが反映された。この期間中に329件のバグレポートがクローズされ、言語の安定化に向けた大規模な提案審査が実施された結果、約25件の提案が採択され、約125件の提案が却下された。

0.17.0は単なる機能追加にとどまらず、プロジェクトの根幹をなす構造に劇的な改編をもたらした。特にビルドシステムが全面的に再設計されたほか、基本的組み込み関数である@bitCastの仕様が再定義され、長年にわたりC言語との連携を支えてきた@cImport構文がコンパイラ本体から削除された。既存の大規模プロジェクトを更新する場合、ビルドスクリプトからアプリケーション本体に至るまで多岐にわたる修正が必要となる。とりわけ変更点を確認せずに機械的な更新を行うと、コンパイルエラーを伴わずにビット配置解釈が変化し、潜在的な不具合を抱え込む危険性がある。

本稿では、0.17.0公式リリースノートで確認された事実に基づき、ビルドスクリプトおよびC連携コードにおいて直ちに影響を受ける変更点を点検表としてまとめ、移行に必要な手順を整理する。破壊的変更を伴うアップデートの選別基準についてはリリースノートトリアージ解説でも触れている。

ビルドシステムのプロセス分離 — configurerとmakerの独立

0.17.0におけるビルドシステム刷新の中核は、ビルド構成(configuration)とビルドグラフ実行(making)のプロセス分離である。従来、zig buildは単一の実行可能ファイル（ビルドランナー）内でbuild.zigの評価からパッケージ管理、依存グラフの実行までを一括して処理していた。このため、build.zigをわずかに編集しただけでもランナー全体の再コンパイルが要求され、外部ツールによるグラフの事前把握も困難であった。

0.17.0では、build.zigを実行してグラフを生成する構成プロセス(configurer)と、パッケージ取得や実際のコンパイルステップを担う実行プロセス(maker)が、完全に独立した別個のバイナリとして分割された。公式文書に記された利点は以下の通りである。

  • makerバイナリはプロジェクト固有のbuild.zigから独立しているため、Zigツールチェーン導入後に一度ビルドされれば、スクリプト変更時に再ビルドされない。
  • makerバイナリを最適化モードでビルドできるため、--watchや--fuzz実行時におけるグラフ走査オーバーヘッドが大幅に削減される。
  • 渡されたコマンドライン引数に応じて、キャッシュされたグラフが存在する場合はbuild.zigの構成処理自体の呼び出しを完全に省略できる。
  • 外部ツールがランナーをフォークして情報を取得する手法を廃止し、バイナリ直列化規格とBuild Server Protocolに統合した。

生成された構成情報はコンパクトなバイナリ形式で直列化され、ディスクに保存される。開発者がビルドグラフの構成出力を目視確認したい場合は、--print-configurationオプションを指定することで、標準出力にZON形式のグラフを出力させることができる。

ビルドスクリプトの破壊的変更 — API名置換と引数受け渡し

プロセスの分離に伴い、std.Buildモジュールの広範なAPIに変更が加えられた。0.16.x向けに書かれた既存のbuild.zigは0.17.0でビルドエラーとなる。最も直接的な変化は、プロジェクトのルートディレクトリを指していたb.build_rootフィールドが、Directory構造体からPath型のb.rootに変更された点である。さらに、生成物引数を追加する一連の関数がバージョン2へ置き換えられた。

APIおよび構造体0.16.0以前0.17.0以降変更内容と対処
ビルドルートパスb.build_rootb.rootDirectory構造体からPath型へ変更
実行時引数の伝達b.argsの参照run_cmd.addPassthruArgs()スクリプトから実行引数を直接観測できないよう隔離
外部コマンド検索b.findProgramfindProgram / findProgramLazy即時実行（キャッシュ汚染）と遅延実行（LazyPath）に分離
パスオプション登録単一のaddOptionPathaddOptionPath[Directory|Untracked]ファイル、ディレクトリ、追跡除外を明示的に区別
フォーマット対象文字列スライスb.pathList(&.{...})Fmtステップのパス指定がLazyPathリストへ変更

特に配慮を要するのがRunステップへの引数受け渡し規則である。従来はif (b.args) |args|のようにスクリプト内で引数を読み取り、条件分岐を行うことができた。0.17.0ではこの機能が取り払われた。スクリプトが引数を観測できない構造にすることで、引数を変更して再実行するたびにbuild.zigを再コンパイルする必要性を排除している。

// 以前 (0.16.0):
                    if (b.args) |args| {
                        run_cmd.addArgs(args);
                    }
                    
                    // 以降 (0.17.0):
                    run_cmd.addPassthruArgs();

また、LazyPath.basenameは生成物のファイル名がmake段階以前に確定しないという設計原則に基づき削除された。引数追加関数についても、addArtifactArgからaddArtifactArg2、addOutputFileArgからaddOutputFileArg2への切り替えが必要となる。

Build Server Protocol導入とZLS互換性の現況

0.17.0以前の環境において、言語サーバであるZLSはZigのビルドランナーを独自ランナーで上書き(override)し、プロジェクトの構成情報を吸い上げていた。しかしプロセスの分離とともにランナーの上書き機能が完全撤廃された。これに代わる標準プロトコルとして導入されたのがBuild Server Protocol(BSP)である。

コンパイラに--listen=-オプションを付与して起動すると、ビルドシステムは標準入出力を通じてIDEやエディタプラグインと通信するプロトコルサーバとして振る舞う。リリースノートに明記された初期実装の機能は以下の通りである。

  • 構成完了後の静的ビルドグラフ情報へのアクセス：利用可能なステップ、設定されたオプション値、依存関係の取得。
  • ステップ実行状況の通知：各ステップの開始と終了、発生したエラー内容、生成されたファイルパスの伝達。
  • 外部クライアントからの特定ステップのビルド要求受付と実行制御。

ただし、この抜本的な刷新により、0.17.0公開時点で既存ZLSとの互換性が一時的に途切れる事態が生じた。公開モジュール一覧の通知など、一部の必須インターフェースがプロトコルに未整備であったためである。リリースノートでは、Zig開発チームとZLSチームが連携して仕様拡張を進めており、単なる復旧にとどまらず従来以上の解析能力を提供できるよう整備を進めていると説明されている。

キャッシュシステムの再設計と構成キャッシュ汚染の防止

0.17.0ではキャッシュ機構全体が刷新された。キャッシュのメタデータが従来のテキスト形式からバイナリ形式へ移行したことでファイルサイズが約25%縮小し、ファイルシステムへの負荷軽減によりキャッシュヒット時の処理速度が5〜10%向上した。キャッシュ内部を調査するためのzig cache-catサブコマンドも追加されている。

さらに重要な概念として「構成キャッシュ汚染(configure cache poisoning)」が導入された。build.zig内のロジックが任意のファイルを読み書きしたり、環境変数を監視せずに副作用を伴う処理を行ったりすると、キャッシュ管理外の要素に依存したとみなされキャッシュが汚染される。汚染された構成情報は再利用されず破棄される。キャッシュを健全に維持するため、依存関係は専用APIで明示する必要がある。

  • std.Build.dependOnFileContents: 特定ファイルの内容変化に対する依存を明示。
  • std.Build.dependOnFileMetadata: ファイルサイズ、inode、変更時刻(mtime)に対する依存を明示。
  • std.Build.dependOnDirectoryContents: ディレクトリ内のファイル追加・削除・名前変更への依存を明示。
  • std.Build.dependOnDirectoryMetadata: ディレクトリ構造全体の更新日時に依存することを明示。

プログラム検索関数findProgramも即時に環境を探索してキャッシュを汚染する。実行時にのみ必要なバイナリであれば、遅延探索を行ってLazyPathを返すfindProgramLazyを使用しなければならない。キャッシュ汚染時の挙動は--cache-poison=[pure|poisoned|disallowed|ignored]フラグで制御できる。

言語仕様の破壊的変更 — @bitCast論理ビット再解釈と構文整理

言語仕様においても極めて重大な変更が実施された。最大の焦点は@bitCast組み込み関数の再定義である。従来、@bitCastはターゲットマシンのメモリ配置を再解釈する操作であったが、0.17.0より値の論理ビット表現(logical bit representation)を別型として解釈する仕様へと改められた。

整数および浮動小数点数は最下位ビット(LSB)から並び、配列やベクトルはインデックス0の先頭要素から順に論理ビットが連結される。リトルエンディアン環境では従来とおおむね同一の結果となるが、エンディアンに依存しない動作へと厳格化された。公式リリースノートは、この変更がコンパイルエラーを伴わずに既存コードの実行結果を変化させる潜在的危険性をはらんでいると明記している。配列やベクトルを含むキャスト箇所は入念な点検を要する。

また、extern structやextern unionに対する@bitCast呼び出しが全面的に禁止された。メモリ上の配置をそのまま別型として扱うタイプパニングが目的であれば、@ptrCastまたはextern unionを用いなければならない。

// 0.16.0以前 (0.17.0ではコンパイルエラー):
                    const int: u16 = @bitCast(bytes);
                    
                    // 0.17.0以降 (@ptrCastを用いた移行):
                    const int_ptr: *align(1) const u16 = @ptrCast(&bytes);

列挙型(enum)の数値変換も刷新された。従来の@intFromEnumと@enumFromIntが非推奨となり、@backingIntと@fromBackingIntが導入された。列挙型のほか、明示的な基底整数を持つビットパックやタグ付き共用体のタグ取得に対応する。空の列挙型には基底型としてnoreturnが要求される。この置き換えはzig fmtで自動適用可能である。

// 以前 (0.16.0):
                    return @enumFromInt(graph.generated_files.items.len - 1);
                    const generated_owner_step = graph.generated_files.items[@intFromEnum(gen.index)];
                    
                    // 以降 (0.17.0):
                    return @fromBackingInt(@intCast(graph.generated_files.items.len - 1));
                    const generated_owner_step = graph.generated_files.items[@backingInt(gen.index)];

その他の構文変更点として以下の整理が行われた。

  • 配列の繰り返し構文a ** bが削除され、@splatに統一された。
  • void{}構文が無効化され、単に{}と記述する形式に変更された。
  • errdefer |err|によるエラー捕捉構文が廃止された。エラーに応じた処理が必要な場合は関数を分割し、外側のcatch |err|で捕捉する。
  • 0ビット符号付き整数型i0が削除された。必要な箇所はu0へ置き換える。

C言語連携コードの移行 — @cImport削除とtranslate-cパッケージ

C言語ライブラリを組み込んでいるプロジェクトにとって最も直接的な影響を及ぼすのが、@cImport構文の完全削除である。0.16.0で非推奨警告が出されていたこの構文はコンパイラから抹消され、ビルドステップのstd.Build.Step.TranslateCも非推奨扱いとなった。

0.17.0でCヘッダーファイルを読み込むには、Zigソフトウェア財団(ZSF)が提供する公式translate-c外部パッケージへの明示的な依存関係をbuild.zig.zonに記述し、ビルドスクリプト内でTranslatorを初期化してモジュールを取得する必要がある。

// 0.16.0以前:
                    const translate_c = b.addTranslateC(.{
                        .root_source_file = b.path("src/c.h"),
                    });
                    
                    // 0.17.0以降:
                    const translate_c = b.dependency("translate_c", .{});
                    const translator: Translator = .init(translate_c, .{
                        .c_source_file = b.path("src/c.h"),
                        .target = target,
                        .optimize = optimize,
                    });
                    // 生成されたtranslator.modをターゲットモジュールへ接続

C変換機能を別パッケージへ切り離したことで、コンパイラ本体のリリースサイクルに縛られずに変換器の改修が可能となり、細かな構成オプションの指定にも柔軟に対応できるようになった。言語境界の相互運用性に関する知見は商用コンパイラフロントエンド分析やRust可変長引数FFIでも扱われている。

標準ライブラリとリンカの進展 — SafeAllocatorとELF増分ビルド

標準ライブラリでは、長らくデバッグ時のメモリ検証を担ってきたDebugAllocatorに代わり、新設計のSafeAllocatorが導入された。SafeAllocatorは完全なスレッドセーフを備え、厳格なメモリ安全検証を実施する。

  • deinit呼び出し時に未解放の全リークを報告し、確保領域をすべて破棄する。
  • 割り当て情報の不整合を検知した場合、直ちにパニックまたはセグメンテーション違反を発生させる。
  • 二重解放やリサイズ競合などの不正操作を厳格に捕捉する。
  • 割り当て領域の末尾にチェックサム保護されたAllocFooterを配置し、スタックトレースやカナリア破壊を監視する。

公式ベンチマークによると、-Osafeモードで標準ライブラリテストをビルドした場合、所要時間は29.4秒から22.1秒へ24.7%短縮され、ピークRSSは2.24GBから1.11GBへ50.3%削減された。

さらにリンカ分野では、新設された独自ELFリンカがx86_64およびSPARC64に完全対応し、静的・共有ライブラリ生成やDWARFデバッグ情報の出力をサポートした。これにより、大半のx86_64-linuxプロジェクトにおいてzig build -fincremental --watchを用いた増分再ビルドが実用的に動作する環境が整った。

確認できなかったこと

  • ZLSの0.17.0完全対応版のリリース予定日および詳細な機能復旧時期は公式文書上で未確定である。
  • ARM64(aarch64)における自作バックエンドのデフォルト化完了時期はロードマップの記載にとどまり、具体的日程は示されていない。
  • @bitCastの論理ビット化によってビッグエンディアン環境で顕在化した具体的リグレッション事例の数値は文書に記載がない。
  • LLVM 22.1.8のループベクトル化無効化回避策が一般バイナリの実行性能に与える定量的影響は測定値が示されていない。
  • クローズされたバグ報告329件の個別内容すべてについて実機検証を行ったわけではない。
  • WindowsのCOFFリンカにおける一部COMDAT未対応が具体的にどの外部ライブラリとの結合で問題となるかは明記されていない。
