「PR을 3개까지만」으로는 리뷰 대기가 줄지 않는다 - 상한 규칙과 큐의 동역학

상한값 3·5·10·20을 900일 대기열 모형에 걸어 차단율과 대기 시간의 꼬리를 직접 측정했다

2026-07-31 개발/인프라

서론: 「3개까지만」으로 바꿨는데 대기 목록은 그대로다

어느 저장소의 리뷰 대기 목록이 200건을 넘었다고 하자. 회의에서 나오는 결론은 대개 익숙한 모양이다. 「한 사람이 동시에 열어 둘 수 있는 것을 3개로 제한하자.」 규칙이 들어가고, 한 달이 지나고, 대기 목록의 길이는 그대로다.

이런 일이 생기면 반응은 보통 둘 중 하나다. 규칙이 느슨했다고 보고 상한을 더 조이거나, 원래 이런 규칙이 그렇다며 없던 일로 한다. 이 글은 세 번째 가능성을 다룬다. 상한을 건 그 지점이 애초에 병목이 아니었을 가능성이다.

2026년 7월 30일 news.hada.io에 올라온 토픽이 출발점이었다. 제목은 「GitHub의 PR 개수 제한, 실제 큐에서는 2~13%만 막는다」였다. 나는 그 보고를 옮겨 적는 대신 같은 질문을 내 손으로 돌려 보기로 했다. 특정 제품이 내부에서 무엇을 어떻게 판정하는지는 바깥에서 알 수 없으므로, 이 글은 일반적인 대기열 모형을 하나 세우고 그 안에서만 이야기한다. 아래의 모든 숫자는 「이 모형에서」라는 단서를 달고 읽어야 한다.

결론부터 적는다. 차단율이 낮게 나오는 것은 규칙이 느슨해서가 아니다. 대기열이 길어지는 이유는 도착이 많아서가 아니라 처리가 느려서이고, 상한은 도착의 시점을 늦출 뿐 처리를 빠르게 하지 않는다. 그래서 상한을 조여도 대기는 줄지 않는다. 다만 상한이 늘 무용한 것은 아니다. 어떤 조건에서는 분명히 문다. 그 조건도 숫자로 특정했다.

이 글은 PR을 여는 법이나 리뷰 예절을 다시 설명하지 않는다. 그쪽이 필요하면 Pull Request와 코드 리뷰에 정리해 두었다. 여기서 다루는 것은 대기열의 동역학이다.

1. 모형 - 무엇을 세웠는가

모형은 일부러 단순하게 잡았다. 그래야 어떤 숫자가 어디에서 나왔는지 끝까지 추적할 수 있다.

  • 작성자 40명이 있다. 각자 작업을 만들어 공용 대기열에 넣는다
  • 새 작업은 하루 평균 9.6건 들어온다. 푸아송 분포를 썼다
  • 누가 그 작업을 냈는지는 지프 분포(s=1.0)로 뽑는다. 소수가 많이 여는 편중을 현실에 맞춰 만들기 위해서다
  • 리뷰 측은 동시에 30건을 붙들 수 있고, 한 건은 평균 3.0일 동안 슬롯을 차지한다. 기하 분포를 썼다
  • 따라서 처리율은 하루 10.0건(30 나누기 3.0)이고, 이용률은 0.96(9.6 나누기 10.0)이다
  • 상한은 「한 작성자가 동시에 열어 둘 수 있는 최대 건수」로 정의했다. 이 지점 말고 다른 어디에서도 작동하지 않는다
  • 900일을 돌리고 앞의 300일은 예열로 버린다. 남은 600일만 센다
// sim.js - node v22.16.0 / win32. fixed seed, so every number below reproduces.
const SEED = 20260731;

function mulberry32(a) {                        // deterministic PRNG
  return function () {
    a |= 0; a = (a + 0x6D2B79F5) | 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
function poisson(rng, lambda) {                 // Knuth
  const L = Math.exp(-lambda); let k = 0, p = 1;
  do { k++; p *= rng(); } while (p > L);
  return k - 1;
}
function geom(rng, p) {                         // support 1,2,3,... mean 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

// A       how many authors
// lambda  new items per day          R  concurrent review slots
// S       mean days one review occupies a slot   =>  service rate mu = R / S
// cap     how many items one author may have open at the same time
function simulate({ A = 40, s = 1.0, lambda = 9.6, R = 30, S = 3.0,
                    days = 900, warmup = 300, cap = Infinity,
                    retry = false, seed = SEED }) {
  const rng = mulberry32(seed), cum = zipfCum(A, s), p = 1 / S;
  const open = new Int32Array(A);
  let queue = [], active = [], deferred = [];

  for (let d = 0; d < days; d++) {

    // 1. reviews whose duration has elapsed give their slot back
    const still = [];
    for (const it of active) {
      if (it.endsAt <= d) { open[it.author]--; record(it, d); }
      else still.push(it);
    }
    active = still;

    // 2. today's items, plus anything blocked earlier if retry is on.
    //    author and review duration are drawn HERE and never re-drawn, so
    //    changing cap does not shift the random stream.
    const todays = retry ? deferred.splice(0) : [];
    for (let i = 0, n = poisson(rng, lambda); i < n; i++)
      todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

    // 3. the cap is applied here and nowhere else
    for (const ev of todays) {
      if (open[ev.author] >= cap) {             // blocked
        ev.tries++;
        if (retry) deferred.push(ev);           // comes back tomorrow
        continue;                               // otherwise dropped
      }
      open[ev.author]++;
      ev.opened = d;
      queue.push(ev);
    }

    // 4. free review slots pull from the head of the shared FIFO
    while (active.length < R && queue.length) {
      const it = queue.shift();
      it.started = d;
      it.endsAt = d + it.dur;
      active.push(it);
    }
  }
}

[3, 5, 10, 20, Infinity].forEach(cap => report(simulate({ cap })));

설계에서 한 가지를 특별히 신경 썼다. 상한값을 바꿔도 도착열과 리뷰 소요일이 어긋나지 않게 만든 것이다. 작업이 만들어지는 순간에 작성자와 리뷰 소요일을 함께 뽑아 두면, 이후에 상한이 그 작업을 막든 통과시키든 난수 소비량이 달라지지 않는다. 이렇게 하지 않으면 상한값마다 서로 다른 세계를 비교하게 되고, 차이가 상한 때문인지 우연 때문인지 구분할 수 없다. 실제로 첫 판본에서 이 실수를 했고, 상한을 바꿀 때마다 총 도착 건수가 5,645에서 5,793 사이로 흔들리는 것을 보고 알아차렸다.

model   : 40 authors, new items ~ Poisson(9.6 per day), author drawn from Zipf(s=1.0)
          review side holds 30 items at once, each for Geometric(mean 3.0 days)

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 Node.js v22.16.0 (win32)으로 실제 실행한 결과다. 난수 발생기는 mulberry32이고 시드는 20260731로 고정했다. 같은 시드로 다시 돌리면 같은 숫자가 나온다. 스크립트는 셸 인자나 히어독이 아니라 파일로 저장해 실행했다.

이 글이 주장하지 않는 것. 이 모형은 어떤 제품의 구현도 아니다. 특정 서비스가 어떤 조건에서 무엇을 막는지, 상한을 누구에게 적용하는지는 여기서 다루지 않는다. 다루는 것은 「작성자별 동시 오픈 상한」이라는 형태의 규칙이 일반적인 대기열에서 어떻게 행동하는가뿐이다.

2. 상한값별로 실제 몇 퍼센트가 막히는가

먼저 새 작업 열이 다섯 행 모두 5,764로 같다. 앞에서 말한 설계가 이 열에서 확인된다. 같은 도착열에 상한만 바꿔 끼운 것이므로 아래 차이는 전부 상한 때문이다.

상한 20은 5,764건 중 8건을 막았다. 규칙이 있는 것과 없는 것의 차이가 처리 완료 기준 3건이다. 상한 10도 2.52%이고, 처리 완료는 5,584건으로 기준선의 98%다. 이 두 값은 규칙이 아니라 장식에 가깝다.

상한 3까지 내려가면 22.62%가 막힌다. 여기서 같은 행의 처리 완료 열을 반드시 같이 봐야 한다. 5,699건에서 4,436건으로 줄었다. 막은 만큼 일이 통과하지 못한 것이지 대기가 빨라진 것이 아니다. 이 표에서는 막힌 작업을 버렸기 때문인데, 버리지 않고 다시 시도하게 하면 어떻게 되는지는 5절에서 본다.

시드를 다섯 개로 바꿔 돌린 아래 표도 중요하다. 상한 3은 20~23%, 상한 5는 10~12%, 상한 10은 1~3%, 상한 20은 0~0.4%다. 순서와 크기가 유지된다. 특정 난수열이 만든 우연이 아니다.

3. 왜 이렇게 낮은가 - 아무도 상한 근처에 없다

이제 진짜 질문이다. 왜 상한 10이 2.52%밖에 막지 못하는가. 답은 작성자별 동시 오픈 수의 분포에 있다.

이것이 낮은 차단율의 정체다. 규칙이 느슨한 것이 아니라 규칙이 닿는 대상이 적은 것이다. 전체 대비 비율로 보고하면 이 사실이 「효과가 미미하다」로 번역되는데, 정확히는 「효과가 미치는 인구가 좁다」가 맞다. 그리고 그 좁은 인구가 처리량의 상당 부분을 만들고 있다는 점이 뒤에서 문제가 된다.

4. 편중을 극단까지 밀어 보면

여기서 자연스럽게 나오는 반론이 있다. 「우리 팀은 훨씬 더 편중돼 있다」는 것이다. 지프 지수를 0.4에서 2.4까지 바꿔 확인했다.

  • 기준값 1.0에서는 1위가 24.4%를 내고 차단율이 11.57%다
  • 지수 2.4에서는 1위가 72.7%를 내고 차단율이 57.76%다

편중을 키우면 차단율은 확실히 오른다. 그런데 오르는 구간을 보라. 차단율이 30%를 넘으려면 한 사람이 전체 작업의 40% 이상을 내야 한다. 40명 조직에서 한 사람이 전체의 40%를 낸다면 그것은 대기열 설계 문제가 아니라 다른 문제다. 현실적인 편중 구간, 즉 1위가 6~25%를 내는 범위에서는 차단율이 1~12%에 머문다.

그리고 p90 열이 반대 방향으로 움직이는 것이 흥미롭다. 편중이 커질수록 p90은 3에서 1로 내려간다. 일이 한 사람에게 몰릴수록 나머지 대부분은 0건에 머물기 때문이다. 평균적인 작성자는 상한에서 더 멀어지고 한 사람만 매일 부딪힌다. 전체 차단율은 그 인구를 평균한 값이므로, 「한 명이 매일 벽에 부딪히는 상황」과 「모두가 조금씩 불편한 상황」을 같은 숫자로 뭉갠다. 상한을 논할 때 전체 비율만 보면 안 되는 이유가 여기 있다.

같은 함정을 지표 쪽에서 다룬 글이 여러 대의 p99를 평균하는 오류다. 분포가 다른 집단을 하나의 숫자로 접으면 정보가 사라진다는 점에서 구조가 같다.

5. 막는 것과 줄이는 것은 다르다

지금까지의 표에서는 막힌 작업을 버렸다. 현실에서는 버려지지 않는다. 나중에 다시 연다. 막힌 작업이 다음 날 다시 시도하도록 바꿔 돌렸다.

  • 상한 10: 628건이 막혔는데 처리 완료는 5,695건이다. 기준선과 4건 차이다. 그런데 개시-완료 평균이 4.05일에서 3.80일로 좋아졌다. 같은 실행의 종단 지연은 4.05일에서 4.06일로, 사실상 그대로다
  • 상한 3: 처리 완료가 4,450건으로 떨어졌고 종단 지연 평균은 31.66일이 됐다

8. 포화 근처에서는 조금만 늘려도 크게 준다

그러면 처리 용량을 늘리는 쪽은 얼마나 효과가 있는가. 리뷰 슬롯 수만 바꿔 봤다.

슬롯 하나를 더했을 때, 즉 처리 용량을 3.4% 늘렸을 때 픽업 전 평균 대기가 3.16일에서 1.04일로 줄었다. 67% 감소다. 그다음 하나는 41%, 그다음은 35%다.

  • 이용률 0.993에서 0.960으로: 큐 평균이 30.7에서 10.2로 떨어진다
  • 이용률 0.900까지 가면 큐 평균이 3.9다. 슬롯을 두 개 더한 것뿐이다
  • 이용률 0.800 아래로 내려가면 개선 폭이 급격히 작아진다. 이미 대기가 거의 없기 때문이다

이 비선형성에는 이름이 있다. 대기 시간이 대략 1 나누기 (1 빼기 이용률)에 비례해 커지기 때문이다. 이용률이 0.993이면 이 계수가 143이고 0.960이면 25다. 용량을 3% 늘렸는데 계수가 5분의 1이 됐다. 포화 근처에서 작은 변화가 큰 효과를 내는 이유가 이것이다. 반대로 이용률이 0.8인 곳에서 같은 3%를 늘리면 거의 아무 일도 일어나지 않는다.

마지막 등가 비교가 이 글의 요약이다. 상한 3(슬롯 30개) 대 상한 없음(슬롯 32개)을 나란히 놓으면, 상한 쪽은 개시-완료 3.02일에 종단 지연 31.66일이고 처리 완료가 4,450건이다. 슬롯 두 개를 더한 쪽은 개시-완료 3.40일에 종단 지연도 3.40일이고 처리 완료가 5,723건이다. 개시-완료만 보면 상한이 근소하게 앞서고, 나머지 모든 지표에서 진다.

9. 그러면 상한은 언제 쓸모 있는가

여기서 규칙 하나가 나온다. 상한은 작성자별 동시 오픈 수의 p90 아래에 있을 때만 문다. 기준 설정에서 p90은 3이었고, 그래서 상한 3은 22.62%를 막고 상한 5는 11.57%, 상한 10은 2.52%였다. 6명 팀에서는 p90이 15여서 상한 5도 34.21%를 막았다. 상한값을 정하기 전에 이 분포를 먼저 재야 한다는 뜻이다.

그리고 이 모형이 재현하지 않는 상한의 용도가 있다. 아래 표에서 그 구분을 정리했다.

네 번째 행이 중요하다. 상한이 사람의 행동을 바꾸는 효과는 이 모형이 측정할 수 없다. 이 모형의 작성자는 상한에 걸려도 작업을 더 작게 쪼개지 않는다. 그저 다음 날 같은 것을 다시 시도할 뿐이다. 실제 조직에서 상한이 「하나를 끝내고 다음을 열자」는 규율로 작동한다면, 그것은 이 시뮬레이션이 잡아내지 못하는 진짜 효과다. 다만 그 효과를 기대하고 상한을 건다면 목적을 대기열 단축이라고 적어서는 안 된다.

규칙 문서를 늘리는 것과 강제 지점을 늘리는 것이 다르다는 이야기는 긴 정책 문서로는 에이전트가 통제되지 않는다에서 따로 다뤘다.

10. 무엇을 재야 하는가

상한값을 몇으로 할지 논쟁하는 대신 아래를 재면 논쟁 자체가 사라진다.

지표정의이 모형의 값왜 재는가
처리율단위 시간당 리뷰가 끝나는 건수10.0건/일큐 길이를 결정하는 쪽이다
도착률단위 시간당 새로 열리는 건수9.6건/일처리율을 넘으면 큐는 무한히 자란다
이용률도착률 나누기 처리율0.960.9를 넘으면 대기가 비선형으로 튄다
대기 시간 꼬리개시-완료의 p90 / p998일 / 13일평균은 최악의 사례를 숨긴다
종단 지연준비된 시점부터 완료까지기준선 4.05일, 상한 3에서 31.66일상한이 밀어낸 시간까지 포함한다
동시 오픈 분포작성자별 p50 / p90 / p990 / 3 / 10상한이 닿을 인구의 크기를 알려준다
큐 길이 추세주 단위 기울기이용률 1.04에서 우상향스냅샷 하나로는 발산을 못 본다

점검 목록으로 옮기면 이렇게 된다.

  • 상한을 논하기 전에 처리율과 이용률을 먼저 쟀다
  • 작성자별 동시 오픈 수의 p90을 알고 있고, 상한을 그 아래에 두었는지 확인했다
  • 큐 길이를 주 단위 기울기로 본다. 스냅샷 한 장으로 판단하지 않는다
  • 대기 시간을 평균이 아니라 p90과 p99로 본다
  • 개시-완료와 종단 지연을 따로 잰다. 상한은 앞의 것만 좋게 만든다
  • 상한에 걸린 작업이 어디에 쌓이는지 볼 수 있는 화면이 있다
  • 이용률이 0.9를 넘으면 처리 용량 증설을 먼저 검토한다
  • 상한의 목적이 큐 단축인지 집중 강제인지 문서에 적었다

11. 이 모형이 재현하지 않은 것

모형의 한계를 적지 않으면 위의 숫자가 실제보다 강하게 읽힌다. 재현하지 않은 것을 그대로 나열한다.

  • 리뷰어 배정과 전문 영역. 여기서는 하나의 공용 선입선출 큐다. 특정 영역을 볼 수 있는 사람이 한 명뿐이라 생기는 병목은 재현되지 않았다
  • 우선순위와 긴급 처리. 새치기가 없다. 실제로는 급한 것이 앞으로 가면서 나머지의 꼬리가 더 길어진다
  • 리뷰 후 수정과 재리뷰. 재작업 루프가 없다. 이것이 있으면 실효 처리율이 떨어지고 이용률이 올라간다
  • 작업 크기의 차이. 모든 건이 같은 분포에서 소요일을 뽑는다. 큰 작업과 작은 작업이 섞이는 효과는 없다
  • 상한이 사람의 행동을 바꾸는 효과. 이 모형의 작성자는 상한에 걸려도 작업을 작게 쪼개지 않는다. 상한의 가장 그럴듯한 장점이 여기서 빠져 있다
  • 오래 열린 작업이 스스로 늦어지는 효과. 충돌, 기준 변화, 맥락 소실이 없다. 실제로는 오래 열려 있을수록 완료가 더 어려워진다
  • 요일 주기와 휴가. 도착과 처리가 모든 날에 같은 분포로 일어난다

이 중 세 번째와 다섯 번째가 결론에 반대 방향으로 작용할 수 있다. 재작업 루프는 처리율을 떨어뜨려 상한의 필요성을 높이고, 행동 변화 효과는 상한의 이득을 이 글이 과소평가하게 만든다. 그래서 이 글의 결론은 「상한은 나쁘다」가 아니다. 「상한은 대기열 길이를 줄이는 도구가 아니고, 그 목적으로 쓰면 지표만 좋아진다」이다.

# 상한 규칙과 대기열 — 무엇을 재고 무엇을 고칠 것인가

> 출처: braindetox.kr — 「PR을 3개까지만」으로는 리뷰 대기가 줄지 않는다
> 검증: node v22.16.0 / win32, 고정 시드 20260731, 900일 모의(앞 300일 폐기, 600일 측정)
> 이 문서의 모든 숫자는 아래 모형 안에서만 성립한다. 특정 제품의 내부 동작이 아니다.

## 1. 모형 한 줄 요약

```
작성자 40명 · 새 작업 Poisson(9.6건/일) · 작성자 선택 Zipf(s=1.0)
리뷰 측 동시 30건 · 건당 Geometric(평균 3.0일)
처리율 mu = 30 / 3.0 = 10.0건/일 · 이용률 rho = 9.6 / 10.0 = 0.96
상한(cap) = 한 작성자가 동시에 열어 둘 수 있는 최대 건수
```

## 2. 재현 코드 (핵심 루프)

```js
const SEED = 20260731;

function geom(rng, p) {                  // 지지집합 1,2,3... 평균 1/p
  const u = rng();
  return Math.max(1, Math.ceil(Math.log(1 - u) / Math.log(1 - p)));
}

for (let d = 0; d < days; d++) {
  // 1. 기간이 끝난 리뷰가 슬롯을 반납
  const still = [];
  for (const it of active) {
    if (it.endsAt <= d) { open[it.author]--; record(it, d); }
    else still.push(it);
  }
  active = still;

  // 2. 오늘의 새 작업. 작성자와 리뷰 소요일을 여기서 한 번만 뽑는다.
  //    그래야 cap 을 바꿔도 난수열이 어긋나지 않는다.
  const todays = retry ? deferred.splice(0) : [];
  for (let i = 0, n = poisson(rng, lambda); i < n; i++)
    todays.push({ author: pick(rng, cum), dur: geom(rng, p), born: d, tries: 0 });

  // 3. 상한은 오직 여기서만 작동한다
  for (const ev of todays) {
    if (open[ev.author] >= cap) {         // 차단
      ev.tries++;
      if (retry) deferred.push(ev);       // 내일 다시 시도
      continue;                           // 아니면 폐기
    }
    open[ev.author]++;
    ev.opened = d;
    queue.push(ev);
  }

  // 4. 빈 리뷰 슬롯이 공용 FIFO 앞에서 꺼내 간다
  while (active.length < R && queue.length) {
    const it = queue.shift();
    it.started = d; it.endsAt = d + it.dur;
    active.push(it);
  }
}
```

## 5. 왜 낮게 나오는가

작성자별 동시 오픈 수의 분포 (상한 없음, 8,000표본)

```

0건  57.03%     상한이 닿지 않는 구간
1건  24.31%
2건   8.50%     여기까지 89.84%
3건   3.72%     상한 3 이 처음 닿는 지점
```

상한 3 이상인 작성자-일은 전체의 **10.16%**뿐이다. 상한은 인구의 꼬리에만 닿는다.

## 7. 재야 할 지표 — 상한값 대신 이것을 본다

| 지표 | 정의 | 왜 재는가 |
|---|---|---|
| 처리율 mu | 단위 시간당 리뷰가 끝나는 건수 | 큐 길이를 결정하는 쪽 |
| 도착률 lambda | 단위 시간당 새로 열리는 건수 | mu 를 넘으면 큐는 무한히 자란다 |
| 이용률 rho | lambda / mu | 0.9 를 넘으면 대기가 비선형으로 튄다 |
| 대기 시간 꼬리 | 개시-완료의 p90 / p99 | 평균은 이상을 숨긴다 |
| 종단 지연 | 준비된 시점부터 완료까지 | 상한이 밀어낸 시간까지 포함한다 |
| 작성자별 동시 오픈 분포 | p50 / p90 / p99 | 상한이 닿을 인구가 얼마인지 |
| 큐 길이 추세 | 주 단위 기울기 | 우상향이면 rho 가 1을 넘었다 |

## 8. 점검 목록

- [ ] 상한을 논하기 전에 **처리율(mu)과 이용률(rho)**을 먼저 쟀다
- [ ] 작성자별 동시 오픈 수의 **p90**을 알고 있고, 상한을 그 아래에 두었는지 확인했다
- [ ] 큐 길이를 **주 단위 기울기**로 본다 (스냅샷 하나로 판단하지 않는다)
- [ ] 대기 시간을 **평균이 아니라 p90 / p99**로 본다
- [ ] **개시-완료**와 **종단 지연**을 따로 잰다 (상한은 앞의 것만 좋게 만든다)
- [ ] 상한에 걸린 작업이 **어디에 쌓이는지** 볼 수 있다
- [ ] 이용률이 0.9를 넘으면 **처리 용량 증설**을 먼저 검토한다
- [ ] 상한의 목적이 **큐 단축**인지 **집중 강제**인지 문서에 적었다

## 9. 하지 말 것

- 큐가 길다는 이유만으로 상한을 거는 것 — 큐 길이는 도착이 아니라 처리가 결정한다
- 차단율이 낮다고 상한을 더 조이는 것 — 낮은 이유는 그 지점이 병목이 아니어서다
- **개시-완료 시간만 보고 개선됐다고 보고하는 것** — 시계 시작점이 옮겨졌을 뿐일 수 있다
- 이용률이 1을 넘은 상태에서 상한으로 대응하는 것 — 보이는 큐만 줄고 총량은 그대로다
- 상한을 소수의 다작 작성자 처벌로 쓰는 것 — 그 사람이 처리율의 상당 부분을 만들고 있다

## 10. 이 모형이 재현하지 않은 것

- 리뷰어 배정과 전문 영역 (여기서는 하나의 공용 FIFO)
- 우선순위, 긴급 처리, 새치기
- 리뷰 후 수정과 재리뷰 (재작업 루프)
- 작업 크기의 차이 (모든 건이 같은 분포의 소요일을 갖는다)
- 상한이 사람의 행동을 바꾸는 효과 (작게 쪼개기, 컨텍스트 전환 감소)
- 오래 열린 건이 스스로 늦어지는 효과 (충돌, 기준 변화)
- 요일 주기와 휴가
