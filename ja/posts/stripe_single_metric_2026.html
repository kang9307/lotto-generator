2026-08-01 IT・技術

序論: 指標が十二個あるのに何から見るべきか誰も知らない

月曜の朝、会議室の画面に指標が十二個並んでいる。新規登録、アクティブユーザー、転換率、離脱率、応答時間、障害件数、デプロイ回数、サポートチケット、再購入率、売上、利益率、満足度。どれも重要な数字だ。そしてどれがより重いのかはどこにも書かれていない。

その週に決めるべきことが一つ出てくる。ある機能を進めると登録は増えるが応答時間は悪くなる。会議は四十分にわたって二つに割れる。一方は登録数を掲げ、もう一方は応答時間のグラフを掲げる。どちらも指標を根拠にしており、どちらも間違っていない。相反したときに何を選ぶかを決めておかなかったので、根拠では結論が出ない。結局その場で声の大きい人か役職の高い人が決める。

「指標を一つに絞ろう」はこのもどかしさから出てくる。そしてこの処方は実際に効く。ただ何を代償にして効くのかがあまり語られない。この記事はその代償を数字で計算してみた記録である。

出発点は2026年7月28日に公開されたあるエンジニアリング記事だ。決済連携の構造を扱いながらこう書いている。「どのみちStripeは数字を一つ求めるだけだ。我々がそこへどう到達したかは気にしない。」原文の文脈は組織管理ではなく課金システムの設計である。決済事業者側へ渡すのは最終的な数量一つだけなのだから、その数量を計算するロジックを製品コードのあちこちに埋め込まず、下流で別途突き合わせよ、という話だ。

ところがこの一文はコードの外でより頻繁に引用される。組織も数字を一つだけ見ればよいのか。この記事はその問いだけを扱う。そして答えは「よい」でも「だめ」でもない。よい、ただし何が代償かを正確に知ったうえで、に近い。

この記事が何を主張しないかを先に明示する。私はStripeという会社が内部で指標をいくつ使っているのか、どんな基準で意思決定しているのかをまったく知らないし、この記事はそれについて何の主張もしない。上に引用した一文は外部の開発者が自分のブログに書いたものであり、その文が指しているのは課金APIへ渡す入力の形である。特定企業の内部運営に関する推測はこの記事のどこにもない。

この記事の数字はすべて仮定に基づく模型が出した値である。いかなる組織も測定していない。Python 3.13.3、Windows 10 (win32)、標準ライブラリのみ、固定シード 20260801 である。同じコードを走らせれば同じ数字が出る。模型が現実と違えば数字も違う。仮定は各節に書き、最後にもう一度まとめてある。

扱わないこと。「測り方が変われば人の振る舞いが変わる」という命題そのものは生産性の蜃気楼で扱ったのでここでは繰り返さない。この記事の問いはその次だ。変わると分かったうえで、指標をいくつ置くのか。何を測定対象にするかを選ぶ一般的な手順は導入の成果は何で測るのかに、意思決定の質と速度が組織に及ぼす影響はバーンではなく意思決定の問題にある。

1. なぜ指標を減らすのか - 相反したとき決まらない

指標が多いことで生じる問題の正体を正確に押さえる必要がある。よくある説明は「気にすることが多くて散漫になる」だが、これは副次的だ。本当の問題は、指標が互いに反対方向を指したとき何を選ぶかが決まらないことである。

模型で数えてみた。仮想の提案を4,000個つくり、各提案が三つの軸(成長、品質、費用効率)へ与える影響を引いた。提案ごとに全般的な優秀さの成分と相反の成分を別に置き、ある提案はすべての軸に良く、ある提案は成長を得る代わりに品質を差し出すようにした。そのうえで無作為に二つの提案を選び、規則ごとに決着するかを数えた。

三行目がこの記事の方向を決める。指標が三つでも重みをあらかじめ書いておけば決着率は100パーセントに戻る。意思決定を止めていたのは指標の数ではなかった。優先順位の不在だった。

  • 指標が一つなら常に決着する。比べる値が一つしかないので当然だ
  • 指標が三つで優先順位がないと、一方が三軸すべてで勝るときだけ決着する。模型ではその割合が35.8パーセントだった。残る64.2パーセントは上に上がるか会議が長くなる
  • 成長基準の選択と品質基準の選択が58.7パーセントで食い違った。つまり相反はまれな例外ではなく半分以上で起きる既定値である
  • 同じ三指標に 0.5 / 0.3 / 0.2 の重みを付ければ決着率は100パーセントになる。指標を減らさずに決着する
  • 決着しないと上に上がり、上がると三周期余計にかかると仮定すると、平均所要は1.00から2.93周期へ増えた。この三周期は私が置いた仮定であり測定値ではない

1.1 「一つに絞る」が実際にしていること

上の表を読み直すと「指標を一つに」という処方が何なのかがはっきりする。それは優先順位を定めるいくつかの方法のうち、最も粗い方法である。重み 1.0 / 0.0 / 0.0 を与えたのと同じだ。

方式決着率表現される優先順位捨てる情報
指標12個、規則なし低いなしなし。ただし結論も出ない
指標3個、規則なし35.8%なしなし。64.2%が未決
指標3個、重み明示100%連続的 (0.5/0.3/0.2)重みを決める議論の費用
指標1個100%極端 (1.0/0/0)残る二軸のすべて

最終行の「捨てる情報」がこの記事の残り全部だ。模型では成長単独の基準と重み付き基準が24.3パーセントの場合に別の選択をした。つまり四回に一回は、一つに絞った代償として別の決定を下すことになる。その24.3パーセントが悪い決定だという意味ではない。ただそれだけ別の決定であり、他の軸がその中に入っているという意味だ。

2. 単一指標の力 - 力はどこから来るのか

単一指標の効果を「集中」という言葉で説明することが多いが、上の模型はもう少し具体的な答えをくれる。力は意思決定規則が完全になることから来る。完全とは、どんな二つの選択肢を持ってきても規則が答えを出すという意味だ。

そしてこの効果には組織の中で増幅される性質がある。規則が不完全だと決定は上へ上がり、上がった決定は文脈を失ったまま判断される。規則が完全なら決定は現場に残る。同じ指標を見る人であれば、上で下そうと下で下そうと同じ答えが出るからだ。

得るもの模型での根拠同時に生じる代償
常に決着する決着率 35.8% から 100%測らない軸は決定に入らない
所要時間が減る平均 2.93周期 から 1.00周期 (仮定模型)誤った決定も同じ速さで出る
下で決められる規則が完全なので委譲できる委譲した分だけ操作の余地も下へ行く
説明が短くなる根拠が一軸なので反対の根拠を語る言葉が消える
チーム間の調整が楽になる共通の軸が一つチームごとに別の軸を与えると逆効果 (7節)

表の右列を併せて読むことが重要だ。単一指標の長所と短所は別々の性質ではなく、同じ性質の表と裏である。規則が完全だから速いのであり、完全とは規則の外の軸をまったく見ないという意味だ。「速く、しかし他の軸も面倒を見よう」という要求は、規則をふたたび不完全にしようという話と同じである。その折り合いをどうつけるかが6節のガードレールだ。

3. 消えるもの - 測らない軸が崩れる経路

ここからは代償の側だ。「測らなければ悪くなる」という言い方はよく聞くが、どれだけ、いつ悪くなるのかを書き残す例はまれである。模型で計算した。

仮定はこうだ。毎周期の労力の総量は1で、三つの軸に配分する。各軸は放っておくと自然に下がる(品質 -2.0、費用効率 -1.4)。品質には負債が負債を呼ぶ項を入れた。品質が基準線を下回るとその負債の分だけ追加で削られる(係数 8.0)。手戻りが増えれば改善に使う時間が減る状況を真似たものだ。そして品質負債は三周期後に成長軸の獲得量を削る(係数 5.0)。遅れを入れたのは、現実ではこの跳ね返りが即座には見えないからである。

読む順序が重要だ。序盤の8周期だけを見れば寄せた側が圧倒的である。155.1 対 125.4 だ。この時点で成績表を提出すれば「集中が正しかった」という結論になる。そしてその結論はこの時点までは事実である。

  • 品質軸は一度も急激には落ちない。毎周期少しずつ下がる。だからどの周期でも警報が鳴らない
  • 16周期の時点で品質は66.6 対 125.6、差は59.0ポイントだ。出発が100だったので一方は三分の一を失い、一方は四分の一を得た
  • 目標軸である成長は12周期に164.9で頂点を打って下りてくる。16周期には159.7だ。放置した軸が結局は目標軸を引き下げた
  • 均等配分の側は16周期で157.5だがまだ上昇中である。寄せた側は下降中だ。この二本の曲線は交差の直前にある
  • この模型の地平が16周期なので逆転そのものは中では起きなかった。コードで期間だけ延ばせばいつ覆るかを見られる

3.1 なぜこれが目に見えないのか

この模型が再現しようとしたのは大きさではなく形である。三つの性質が重なってこの崩壊を見えなくする。

  • 遅い。毎周期1パーセント程度ずつ下がるなら、どの周期の報告書でも有意には見えない
  • 遅れる。品質負債が成長に反映されるまで三周期かかる。だから原因と結果が別の四半期に現れ、互いに結び付かない
  • 初期の信号が逆である。最初の数周期は目標指標が実際によく上がる。その成果が方針を強化する

だから「指標を一つに絞ったらうまくいった」という報告はほとんど事実である。ただその報告が出る時点がおおむね6周期から10周期の間だというだけだ。単一指標の危険は誤った結果ではなく、正しい結果が先に来て代償が後から来るところにある。

4. グッドハートの法則 - 二つの異なる故障

広く引用される文はこれだ。「ある尺度が目標になると、それは良い尺度であることをやめる。」この文の出所を確認しておくとよい。よく経済学者グッドハートの言葉として引用されるが、この形の文がそのまま現れるのは1997年のヨーロピアン・レビューに載ったマリリン・ストラザーンの論文308ページである。その論文は、この名を「グッドハートの法則」と呼んだのはホスキンであり、通貨管理の手段に関するグッドハートの観察を指していると述べている。

この区別は実務で役に立つ。グッドハートの法則という名の下には互いに異なる二つの故障が入っており、対応が違うからだ。

故障原因誰かが不正をするか模型での大きさ対応
選択損失代理指標に雑音があるいいえ忠実度0.80で21.0%の損失結果により近い指標へ替える
操作指標に報酬が結び付くはい圧力0.8で相関 -0.18ガードレール、見直し周期、圧力調整

4.1 誰も不正をしなくても損が出る

一つ目の故障はあまり知られていない。代理指標に雑音が混ざっていれば、その指標の上位を取るだけで真の値から損が出る。操作がまったくなくてもそうなる。項目を2万個つくり上位200個を取ってみた。

------------------------------------------------------------------------
    rho = 0.95      +2.528 sd                        5.2%
    rho = 0.90      +2.357 sd                       10.7%
    rho = 0.80      +2.088 sd                       21.0%
    rho = 0.70      +1.795 sd                       33.0%
    rho = 0.50      +1.294 sd                       51.5%
    rho = 0.30      +0.862 sd                       68.6%
------------------------------------------------------------------------
  nobody games anything here. this loss is pure noise in the proxy.

忠実度が0.80なら21パーセントを失う。0.80はかなり良い代理指標だ。それでも上位だけを取る方式が損を生む。理由は単純である。上位に来た項目は、本当に良くて来たものと、たまたま雑音が大きく出たものが混ざっている。極端だけを選び出すほど後者の比重が大きくなる。

  • この損失は指標を一つに絞ることとは無関係に生じる。代理指標を使うあらゆる場所にある
  • ただし単一指標はこの損失を一つの軸に集める。指標が複数なら異なる雑音が部分的に相殺されるが、一つならその一つの雑音がすべてだ
  • 対応は「少なく取る」ではなく結果により近い指標を選ぶことである。忠実度を0.80から0.90へ上げれば損失は21.0から10.7パーセントへ半減する
  • だから5節の候補判断で結果への近さに最も大きな重みを与えている

4.2 圧力がかかると指標が結果から離れる

二つ目の故障がふつう言われるグッドハートだ。ここで模型の要点は操作の能力を実際の実力と独立に引いたことである。この一行が結果を分けた。操作能力が実力に比例するなら指標と結果はくっついたままだが、独立なら離れていく。圧力が上がるほど操作に使う比重が増えると仮定した。

真ん中の二列を並べて見ればよい。指標の平均は1.00から2.48へ二倍半になるのに、本当の結果の平均は1.00から0.29へ落ちる。ダッシュボードはよくなり続け、実際は悪くなり続ける。これがグッドハートの法則が実務で見せる姿だ。

  • 相関は圧力0.4までは0.73で持ちこたえる。0.6で0.23へ崩れ、0.8で負になる。徐々にではなく、ある区間で急に折れる
  • 最後の列が最も痛い。指標上位10パーセントの本当の値である。圧力がないとき1.58だったものが圧力1.0では0.14になる。全体平均の0.29より低い
  • つまり指標が報いる人々のほうが結果の悪い集団になる。昇進と報奨がちょうど逆方向へ出ていく
  • ここで「人が悪い」という結論を出すと間違える。模型の行為者は与えられた規則に最適に反応しただけだ。壊れているのは人ではなく規則である

5. どんな指標が候補になるのか

ここまでの計算は候補を選ぶ基準を与えてくれる。良い単一指標は三つを同時に満たさねばならない。結果に近く、操作が難しく、チームが実際に動かせること。ここにどれだけ速く確認できるかを四つ目として入れた。フィードバックが遅いと3節の遅れの問題が大きくなるからだ。

候補十個に1から5までの点を付け、重みを掛けて計算した。細目の点は私の判断であって測定値ではない。自組織では数字が変わる。ここで見るべきは順位そのものではなくどんな性質が点を押し上げ、押し下げるのかである。

表からいくつかの規則が読み取れる。

  • 結果に最も近い指標が常に最善とは限らない。月次経常収益は結果への近さが満点なのに総合3.55にとどまる。チームが直接動かせないからだ。チームが動かせない指標を目標に与えると、人々は指標ではなく指標を説明する物語をつくるようになる
  • 動かしやすい指標はそれ自体が危険信号である。デプロイ回数は制御力と速さが満点なのに総合は最下位圏だ。分割してデプロイすれば即座に上がり、その上昇は結果と何の関係もない
  • 納期遵守率はとくに悪い。見積りを膨らませば上がる。指標を改善する最も安い方法が見積りを壊すことである指標は候補から外すべきだ
  • 最初の成功までの時間が一位である理由は、どの軸も弱くないからだ。結果との因果が近く、短くするには実際に何かを直さねばならず、チームが直接動かせて、数日で確認できる
  • 4.1節の計算を思い出せば結果への近さに大きな重みを置く理由がはっきりする。忠実度が0.80から0.90へ上がれば選択損失は半分になる

6. ガードレール - 制約はいくつまで置けるのか

3節の崩壊に対する標準的な処方は単一目標に制約を付けることである。「転換率を上げる。ただし応答時間のp95は400ミリ秒を超えない」といった形だ。この方式はよく働く。ところが制約を付け続けるとある瞬間にふたたび多指標になる。その地点を計算した。

仮定はこうだ。各ガードレールは意思決定の18パーセントで実際に効く。そしてガードレール同士に相関が0.30ある。難しい決定では複数の制約が同時に効きやすい傾向を入れたものだ。

   2                   69.6%                30.4%        1.36

  • ガードレール五つで、単一目標が単独で決める割合が48.0パーセントになる。半分を超える決定が制約によって覆る
  • ガードレール六つで、一つの決定で生きている判断軸の平均が2.09になる。名は単一指標なのに実際には二つ以上で判断している
  • 実務上の上限は三つ程度だ。このとき目標が単独で決める割合が60.2パーセント残る。「おおむね目標が決め、たまに制約が止める」が保たれる
  • ガードレールは目標ではなく線でなければならない。「超えない」であって「上げる」ではない。上げ始めたその瞬間に二つ目の目標になる
  • ガードレールに掛かった決定は記録しておくべきだ。掛かる割合が上がり続けるなら、目標そのものが誤っているという信号である

ここでよくある誤解を一つ整理する。ガードレールによって多指標へ戻ること自体は悪いことではない。1節で見たとおり、重みを明示した三指標も決着率100パーセントだ。問題になるのは単一指標と呼びながら実際には六軸で判断している状態である。そうなると単一指標の長所である委譲可能性が消えるのに、組織は依然として委譲できていると信じている。

7. 組織の大きさ - チームごとに単一指標を置くと

ここまでは一つのチームの話だった。チームが複数になると新しい問題が生じる。「チームごとに自分の単一指標を一つずつ持つ」という方式は、規模が大きくなると全体を食い違わせる。

模型はこうだ。チームiが自分の指標を上げると自チームには利得であり、他のチームには小さな費用が移る。共有資源の競合、統合の費用、互いのリリースを待つ時間といったものだ。チームあたりの費用はごく小さく(平均0.020)置いた。チームは自分の指標しか見ないので常に最大まで押す。一方、全体指標を共有する場合は全体の合計が上がる方向にだけ動く。

E. One metric per team   assumed spillover model
------------------------------------------------------------------------
  teams   active (local)  active (shared)   total (local)  total (shared)  loss
------------------------------------------------------------------------
      2               2                2            1.76            1.76    0.0%
      4               4                4            2.98            2.98    0.0%
      8               8                8            6.98            6.98    0.0%
     16              16               16           12.96           12.96    0.0%
     32              32               22           11.75           15.96   26.4%
------------------------------------------------------------------------
  nobody misbehaves. every team maximizes the metric it was handed.

この表の形が重要だ。16チームまでは損失が0である。それが32チームで急に26.4パーセントになる。徐々に悪くなるのではなくある線を越えると急に食い違う。

  • 理由は、移る費用がチーム数に比例して積み上がるからだ。チームあたりの費用はそのままなのに相手チームが増える。8チームでは無視できたものが32チームではチーム一つ分の寄与を超える
  • 全体指標を共有した場合、32チームのうち22チームだけ押して10チームは止まるのが最適だった。ところがチーム別指標の体制では止まれという信号がどこからも来ない。各チームの指標は押し続けろと言う
  • 誰も間違っていないという点が核心だ。すべてのチームが与えられた数字を誠実に最大化し、その結果、全体は4.21だけ損をした
  • 実務でこの状態は「各チームのダッシュボードはすべて緑なのに全体の結果が出ない」として現れる。チーム別の報告をいくら集めても原因が見えない。原因がチームの中ではなくチームの間にあるからだ
  • 小さな組織で単一指標がよく効く理由も同じ表から読める。チームが少なければ移る費用が小さく、局所最適が全体最適と一致する。成功体験が規模とともに無効になる

だからチームが複数の組織で使える形は「全体に一つ、チームにはそれを分解した項」である。チーム別の指標を別に発明するのではなく、全体指標を分解するのだ。分解できないチーム指標を見つけたら、そのチームは全体目標との接続が切れている可能性が高い。

8. 導入手順と点検表

計算の結果を手順に移すとこうなる。順序が重要だ。候補を選ぶより先に廃棄基準を決めておくのがこの手順の特徴である。

段階やること成果物やらないと起きること
1いま相反で止まっている決定を五つ書き出す実例の一覧指標を好みで選ぶことになる
2候補を四軸で点数化する (5節)候補判断表動かしやすい指標が選ばれる
3選んだ指標を最も安く上げる方法を書く操作経路の一覧その経路を三か月後に発見する
43の経路をふさぐガードレールを最大3個立てる越えない線測らない軸が崩れる (3節)
5見直し周期をカレンダーに打ち込む日付「あとで見よう」が永遠になる
6廃棄基準を先に書く捨てる条件指標を捨てられない (下記)
7チーム別指標は全体指標の分解としてのみ作る (7節)分解表規模が大きくなると食い違う

6段階を先に書く理由がある。指標は導入したあとでは捨てるのが非常に難しい。すでにその指標で評価された人がいて、その指標で成功したチームがあり、その指標をよく見せるための投資がある。だからまだ誰もその指標に利害を持たないうちに廃棄条件を書かねばならない。

8.1 見直し周期は実際に価値がある

見直し周期が形式的な手続きではないことを計算で示した。仮定はこうだ。指標を固定しておくと周期ごとに操作の比重が0.06ずつ増え0.80で止まる。指標を入れ替えると操作の比重は0へ戻るが移行費用として0.5周期分の産出を失う。24周期の累積産出を計算した。

G. Review cycle   24 periods, drift 0.06/period, reset cost 0.5, assumed
------------------------------------------------------------------------
   review every   cumulative true output   vs never   resets
------------------------------------------------------------------------
   never                       10.54           -        0
   12 periods                  15.58        +48%        1
   8 periods                   17.96        +70%        2
   6 periods                   18.90        +79%        3
   4 periods                   19.34        +83%        5
   3 periods                   19.06        +81%        7
   2 periods                   17.78        +69%       11
------------------------------------------------------------------------
   best in this model: review every 4 periods (19.34, +83% vs never)
   too often is also worse: the reset cost eats the gain.
  • 一度も見直さないと累積産出は10.54だ。四周期ごとに見直すと19.34で83パーセント高い。見直し周期一つがこれだけの価値を持つ
  • 一度だけ見直しても48パーセント上がる。12周期の行だ。完璧な周期を探す前にとりあえず一つ入れるほうがはるかによい
  • 頻繁なほど良いのではない。二周期ごとに変えると17.78へ再び下がる。移行費用が利得を食う。最適が内側にあるU字型だ
  • ここで「入れ替え」ではなく「見直し」である点が重要だ。見直しの結論が維持であってもよい。そのときはなぜ維持するのかを書き残せば次の見直しが楽になる
  • 周期の長さは操作が積もる速さによる。操作が容易な指標ほど短く取るべきだ。5節で操作の難しさの点が低かった指標がこれに当たる

8.2 点検表

  • この指標を最も安く上げる方法を書いてみて、それが我々の望む振る舞いか
  • その指標を担当するチームが実際にその数字を動かせるか
  • ガードレールが三つ以下か。四つを超えると多指標へ戻る途中だ
  • ガードレールがすべて「超えない」の形か。「上げる」が混ざれば二つ目の目標だ
  • 見直しの日付がカレンダーにあるか。「四半期ごと」という言葉ではなく日付か
  • 廃棄条件を指標の導入前に書いたか
  • 指標が数日で確認できるか。四半期後に確認されるなら3節の遅れが大きくなる
  • チーム別指標があるなら、それは全体指標の分解か、それとも別に発明したものか
  • ガードレールに掛かった決定を数えているか。掛かる割合が上がれば目標が誤りという信号だ
  • この指標で上位の成果者を選ぶとき、4.2節の最後の列を確認したか
  • 指標を替えるとき以前の指標で評価された人をどうするか決めたか
  • ダッシュボードで指標とガードレールが区別されて見えるか。同じ大きさで並んでいればすでに多指標だ

9. この記事で確認できなかったこと

模型は模型である。確認していないことを確認したかのように書けば次の人を誤らせる。

  • すべての数字は仮定から出た。いかなる実在の組織も測定していない。仮定が違えば結論の大きさが変わる。方向が覆る可能性も排除しない
  • 操作の反応曲線は純粋な仮定である。圧力が上がるとき人々がどれだけ操作へ移るかについての実測を持っていない。4.2節の急な折れ曲がりはこの仮定の産物だ
  • 3節の係数も仮定である。品質負債がどれだけ速く積もり、何周期後に成長へ反映されるかは組織ごとに違う。頂点が12周期に来たのは係数をそう置いたからだ
  • 7節の移る費用も仮定である。16チームと32チームの間で折れたのは費用の平均を0.020に置いたからだ。その値が違えば折れる地点が変わる。読むべきは32という数字ではなく「ある線で急に折れる」という形である
  • 単一指標を実際に導入した組織の成果は調査していない。この記事はどの方式が実際によい結果を出したという主張をしない
  • 特定企業の内部運営はこの記事の対象ではない。序論で引用した一文は課金APIの設計に関する外部開発者の記事から来ている
  • 人が複数の指標を同時に扱う認知的な限界に関する研究は確認していない。「指標が多いと散漫になる」という通念はこの記事で検証しておらず、だから根拠としても使っていない

結論: 数の問題ではなく優先順位の問題である

計算して得たものを一行に縮めるとこうなる。「指標を一つに」は測定の問題ではなく優先順位の問題である。

1節の三行目がその根拠だ。指標が三つでも重みを書いておけば決着率は100パーセントへ戻った。意思決定を止めていたのは指標の数ではなかった。何がより重いのかを誰も書いていなかったという事実だった。指標を一つに絞ることは優先順位を定める最も粗い方法であり、粗いからこそ速い。

そしてその粗さには値札が付いている。測らないものは必ず悪くなる。3節で品質は16周期に66.6となり、その負債は結局12周期の頂点から目標指標を引き下げた。これは事故ではなく設計に含まれていた帰結だ。規則が完全だから速くなったのであり、完全とは規則の外を見ないという意味だからである。

だから単一指標は単独では歩けない。ガードレールと見直し周期を一緒に持たねばならない。ガードレールは三つまでだ。それ以上は名だけ単一指標の多指標になり、そうなると委譲可能性という長所が消えたまま単純さという錯覚だけが残る。見直し周期は形式ではない。模型で一度も見直さない場合と四周期ごとに見直す場合の累積産出が10.54対19.34だった。

そしてチームが複数なら計算がもう一度変わる。7節では16チームまで何の損失もなかったのに32チームで26.4パーセントになった。小さな組織で単一指標がよく効いたという経験は規模とともに無効になる。チームごとに各自の単一指標を発明する代わりに、全体指標一つをチーム単位へ分解するほうが安全だ。

いますぐできることが一つある。いま使っている指標を最も安く上げる方法を三つ書き出してみよ。そしてそれが組織の望む振る舞いかを見よ。違うなら、その経路はすでに使われている可能性が高い。4.2節が示したのは結局これである。ガードレールと見直し周期なしに指標へ圧力だけをかければ、グッドハートの法則は起きるかどうかの問題ではなく、いつかの問題になる。

# 単一指標の設計 - 候補判断表、ガードレール、見直し周期

> 出典: braindetox.kr — 指標を一つに絞ると何が良くなり何が消えるのか
> 以下の数字はすべて**仮定に基づく模型**の結果である。いかなる組織も測定していない。

## 1. 一行まとめ

- 「指標を一つに」は**測定の問題ではなく優先順位の問題**である
- 一つに絞れば意思決定が速くなる。そして**測らない軸は必ず悪化する**
- だから単一指標は**ガードレールと見直し周期**と一緒でのみ成立する

## 3. ガードレールの設計

| ガードレール数 | 目標が単独で決める | 平均で生きている軸 | 判断 |
|---|---|---|---|
| 0 | 100.0% | 1.00 | 純粋な単一指標 |
| 1 | 82.0% | 1.18 | 安全 |
| 2 | 69.6% | 1.36 | 安全 |
| **3** | **60.2%** | **1.55** | **実務上の上限** |
| 4 | 53.3% | 1.73 | 警告 |
| 5 | 48.0% | 1.89 | 半分以上が制約で決まる |
| 6 | 43.2% | 2.09 | **事実上の多指標** |

規則:

- ガードレールは**「この線を超えない」**の形のみ。「上げる」が混ざれば二つ目の目標だ
- **最大3個。**4個からは多指標へ戻る途中である
- ダッシュボードで**目標とガードレールを視覚的に区別**すること
- ガードレールに掛かった決定の数を**数える。**割合が上がれば目標が誤りという信号

## 4. 見直し周期

| 見直し間隔 | 24周期の累積産出 | 比較 |
|---|---|---|
| しない | 10.54 | - |
| 12周期 | 15.58 | +48% |
| 8周期 | 17.96 | +70% |
| 6周期 | 18.90 | +79% |

- 「入れ替え」ではなく**「見直し」**。維持が結論なら、なぜ維持するのかを書く

## 5. シミュレーションのコード (中核部分)

```python
# 固定シード。標準ライブラリのみ。Python 3.13.3 / Windows 10

# B. 品質負債が負債を呼び、3周期後に成長を削る

# C2. 操作の能力を実際の実力と独立に引く。
#     この一行が指標と結果を引き離す。

gam   = abs(gauss(1.0, 0.50))          # 独立に抽出
g     = min(0.90, 0.80 * pressure ** 2 * will)
true  = (1.0 - g) * skill
proxy = true + g * gam * 3.0 + 0.10 * gauss(0.0, 1.0)

# E. 全体指標はチームを止められる。チーム別指標は決して止められない。
local  = [1] * M                       # 全チームが自分の数字を最大化
shared = greedy_flip(total_value)      # 全体の合計が上がるならチームを止める
```

## 6. 導入手順

1. いま**相反で止まっている決定を5つ**書き出す
2. 候補を四軸で点数化する (2節の表)
3. 選んだ指標を**最も安く上げる方法**を書く
4. その経路をふさぐ**ガードレールを最大3個**立てる
5. **見直しの日付**をカレンダーに打ち込む (「四半期ごと」ではなく日付)
6. **廃棄基準を先に**書く — 誰も利害を持たないうちにしか書けない
7. チーム別指標は**全体指標の分解**としてのみ作る

## 7. 点検表

- [ ] この指標を**最も安く上げる方法**が望む振る舞いか
- [ ] 担当チームが**実際にその数字を動かせるか**
- [ ] ガードレールが**3個以下**か
- [ ] ガードレールがすべて**「超えない」**の形か
- [ ] 見直しの**日付**がカレンダーにあるか
- [ ] **廃棄条件**を導入前に書いたか
- [ ] 指標が**数日で**確認できるか
- [ ] チーム別指標が**全体指標の分解**か
- [ ] ガードレールに掛かった決定を**数えているか**
- [ ] 上位成果者の**実際の結果**を確認したか
- [ ] 指標を替えるとき**以前の指標で評価された人**をどうするか決めたか
- [ ] ダッシュボードで**目標とガードレールが区別**されるか

## 8. やってはいけないこと

- ❌ ガードレールを**目標のように**上げること — その瞬間に二つ目の目標になる
- ❌ **チームごとに別の単一指標**を発明すること — 規模が大きくなると食い違う
- ❌ **廃棄基準なしに**指標を導入すること — あとでは捨てられない
- ❌ 「集中したらうまくいった」を**6〜10周期で**結論すること — 代償は後から来る
- ❌ 操作が見えたとき**人を責めること** — 壊れているのは規則だ
- ❌ この表の数字を**自組織の値として使うこと** — すべて仮定模型である
