画面とサーバーがずれる瞬間

状態はひとかたまりではない - 寿命と持ち主で分ければ、どこが難しいのかが見えてくる

2026年8月28日 開発・インフラ

はじめに: 戻るを押したら古いタイトルがそのまま残っている

詳細画面でタイトルを直して保存した。戻るを押して一覧に帰ると、古いタイトルがそのまま並んでいる。再読み込みすれば消える種類の不具合だ。再現は不安定で、スタックトレースもなく、直しても一か月後に別の画面で同じ形をして現れる。フロントエンドで最も時間を吸い取る欠陥は、たいていこの顔をしている。

先日 hackers.pub に載った FL の記事は、状態管理ツールがいまだ解けていないものとして四つを挙げた。状態の共有範囲をあとから変えにくいこと、共有状態の寿命を表す手立てが乏しいこと、派生状態をひとつの値のように共有しにくいこと、そしてひとつの機能を構成するコードが複数の場所へ散らばること。著者はこの四つが、実はひとつの問題が別の顔で現れたものだと見ている。

ここではその一覧を引き写す代わりに、少し違う位置から同じ問題を眺めたい。ツールが何をしてくれないかではなく、画面に見えているものとサーバーにあるものがいつずれるのかだ。ずれが生まれる場所を先に数えておくと、どのツールを使うにせよ、そのツールが何を肩代わりし、何をそのまま残すのかが見えてくる。

先に断っておくことがひとつある。この記事にこうすれば解決するはない。四つが難所と呼ばれるのは完全な解法が存在しないからで、ここで紹介する対策はすべて何かを代償に持っていく。その代償を併記することがこの記事の目的だ。

1. 「状態」というひとつの言葉が覆い隠すもの

状態管理は難しいと言うとき、その言葉の中には性質のまるで違う値が混ざっている。それらをひとつの入れ物に入れるところから問題が始まる。

区分の軸は二つだ。原本がどこにあるかといつまで生きるべきか。この二つで割ると四つの群れが出てくる。

  • サーバーが原本を持つデータ — 注文一覧、利用者プロフィール、在庫。画面にあるのは複製で、原本は他人も書き換えられる
  • この画面でだけ生きる値 — 開いているアコーディオン、入力中のテキスト、ドラッグ座標。画面が閉じれば一緒に消えるのが正しい
  • URL にある値 — 検索語、ページ番号、選択中のタブ。他人にリンクとして手渡せる値だ
  • ブラウザに残る値 — ログイントークン、ダークモード設定、閉じた案内バナー。タブを閉じても生き残る
種類原本のある場所自然な寿命消す主体ずれたときの症状
サーバーデータの複製サーバー再び問い合わせるまで無効化ルール古い値をもとに判断・表示する
画面の中の値その画面画面が消えるまで画面自身別の項目の状態が引き継がれる
URL パラメータアドレスバーそのアドレスが保たれる間ナビゲーション共有したリンクが別の画面を開く
ブラウザストレージ端末消すまで無期限人が書いたコード配信後も古い形式が残る

表で注目したいのは消す主体の列だ。画面の中の値だけが、自分の寿命をすでにコードの構造の中に持っている。残る三つは、いつ捨てるかを人が別途決めてやらなければならない。決めなければ値はただ残り、残った値はいつか間違った値になる。

2. 難所その一 — 原本が向こう側にある

画面に描かれた注文ステータスは、サーバーにある注文ステータスではない。数秒前に写し取った複製だ。その間に別の管理者が変えたかもしれないし、配送会社の Webhook が飛んだかもしれない。複製は取ってきた瞬間から古くなり始める。だから問いはひとつだ。いつもう一度尋ねるのか。

2.1 もう一度尋ねる時点の候補

  • 画面に最初に入るとき — 基本だが、すでに画面にいる間の変化は取り逃す
  • 取得から一定時間が過ぎたとき — その時間を何で決めるかが結局はドメイン判断になる
  • タブが再び前面に戻ったとき — 席を外して戻ってきた利用者には効果が大きい
  • 自分が何かを変えた直後 — 自分が起こした変化だけが反映され、他人の変化は依然として分からない
  • サーバーが先に知らせてくれるとき — 常時接続を保つ費用と、切れたときの復旧設計がついてくる

2.2 どちらへ傾けても代償がある

頻繁に尋ねればリクエスト数が増え、応答が届くたびに画面が微妙に揺れる。読んでいた一覧が並び替わり、スクロール位置が飛ぶ。まれにしか尋ねなければリクエストは減るが、古い値を根拠に利用者が判断を下す。残り在庫が一個と表示された画面で注文を押したのに、すでに売り切れているという状況はこうして作られる。

だから更新間隔を技術的な好みで決めてはいけない。基準はこの値が間違っていたときに取り消せるかだ。プロフィール名が数秒古いのは何でもないが、残高・在庫・権限が古ければ、利用者は取り消せない行動を取る。取り消せない側は画面に入った時点の複製を信じず、実行の直前にサーバーが改めて判定するようにしたほうがよい。画面はどのみち複製なのだから、最終判定を画面に任せないことが唯一確実な対策になる。

3. 難所その二 — 待っている間に何を見せるか

ボタンを押した。応答は 300 ミリ秒後に来る。その 300 ミリ秒のあいだ、画面は何を言うべきか。選択肢は事実上三つだ。

  • 塞いで待つ — スピナーを出して操作を止める。正直だが、短いリクエストでも画面が瞬いて体感速度が落ちる
  • 古い値を残したまま表示だけ変える — 一覧を保ったまま端をぼかす。画面が動かないので落ち着くが、表示に気づかない利用者は古い値を新しい値と取り違える
  • 楽観的更新 — 成功を仮定して画面を先に変える。体感の遅延が消える

3.1 楽観的更新が実際にくれるもの

楽観的更新の効果は速さではなく連続性だ。いいねを押せばハートが即座に埋まり、利用者は次の項目へ移る。実際の往復時間は変わらないのに、待つという経験が消える。一覧をなぞりながら連続で操作する画面では、この差は大きい。

3.2 巻き戻すときに払う代償

問題は失敗したときだ。巻き戻しは画面の値を元に戻せば終わり、ではない。

  • 利用者がすでに次の操作をしている — 戻した値の上に新しい操作が積まれ、どの時点へ戻すのかが曖昧になる
  • 巻き戻る場面を誰も見ていない — スクロールで画面外に出たり別のタブへ移ったあとなら、利用者は成功したと信じたまま去る
  • サーバーが部分的に成功した — 保存はできて通知の送信だけ失敗した場合、画面を丸ごと戻すとかえって事実から遠ざかる
  • 巻き戻しが一覧の順序を変える — 項目が元の位置へ跳ね上がり、利用者が押そうとしていた別の項目を押し間違える

だから楽観的更新はすべての操作に一律で適用するものではなく、条件をつけて使う。失敗率が低く、失敗の影響がその要素ひとつにとどまり、巻き戻る様子が利用者の視界の中で起きる操作だ。逆に削除・決済・並び替えのように、巻き戻しが目に入りにくかったり他の項目を揺らす操作は、素直に待たせるほうがよい。すべてのフレームが一貫して見えてこそ信頼が生まれるという話と、この地点は正面からかみ合う。速い画面と正直な画面は、いつも同じ画面ではない。

4. 難所その三 — 同じデータが複数の画面にあるとき

ひとつの注文が三か所に現れる。一覧の行、詳細画面、そしてヘッダーの未処理件数バッジだ。詳細でステータスを変えたとき、残りの二つはその事実をどうやって知るのか。冒頭の不具合が生まれるのはこの場所である。

4.1 三つの方針とそれぞれの代償

  • 一箇所に置いて残りが参照する — ずれる余地が原理的に減る。代わりにその一箇所が複数画面の要求を同時に満たさねばならず、画面ひとつを直すたび共有の形に手を入れることになる
  • それぞれが持ち、変更を通知する — 画面同士の結合がゆるい。代わりに購読をひとつ取りこぼすと、その画面だけが静かに古くなる。取りこぼしたという事実は利用者が先に見つける
  • キーで識別されるキャッシュに置き、変更後に無効化する — ルールが明示的で追いやすい。代わりに無効化するキーを取り違えると、何のエラーもなく古い値が残る。キー設計がそのまま整合性の設計になる

4.2 正規化という分かれ道

同じ実体が複数の応答に重複して載ってくると、それを実体単位に展開してひと組だけ持つ方式を考えたくなる。こうすれば一箇所を直すだけですべての画面が同じ値を見る。代わりにサーバーが渡した形と、保存する形と、画面が欲しい形がすべて別々になる。応答を展開するコードと、画面用に組み立て直すコードが生まれ、その二つが新しいフィールドに追いつけなければ、今度は組み立ての段階で値が抜け落ちる。

重複をなくせば不一致が消える代わりに変換の費用が生まれ、重複を残せば変換がない代わりに不一致を見張ることになる。どちらも無料ではない、というのが要点だ。ひとつの実体が三つ以上の画面に同時に見えていて、そのうちひとつが編集できるなら正規化のほうがおおむね痛みが少ないが、二つの画面が読むだけならその費用を払う理由は薄い。

5. 難所その四 — 順序は保証されない

検索欄に ser まで入力し、続けて serv と入力した。リクエストは順番に出ていった。応答も順番に返るという保証はどこにもない。serv の応答が先に届き ser の応答が遅れて届けば、画面には入力欄の文字と合わない結果が残る。

5.1 最後のものだけを採用する

最も単純な防御は、リクエストに番号を振り、応答が返ってきたときにその番号がまだ最新かどうかを確かめることだ。

latest = 0

on_input(query):
    latest = latest + 1
    my_seq = latest
    result = await fetch(query)
    if my_seq != latest:
        return            # その間により新しいリクエストが出ている
    render(result)

この数行が、画面と入力のずれの大半を防ぐ。代償は捨てられる応答だ。利用者が一文字消してまた打ったなら事実上同じ問い合わせなのに、先の応答は破棄される。そしてこの方式は画面しか守らない。サーバーはすでに五回検索している。

5.2 中断にできないこと

新しいリクエストを送るときに前のリクエストを中断する方法も広く使われる。ただし中断は応答を受け取らないという宣言であって、リクエストがなかったことになるという意味ではない。リクエストがすでにサーバーへ届いていれば、処理も副作用もそのまま起きる。読み取りでは問題にならないが、書き込みを中断で扱い始めると、画面は取り消したつもりなのにサーバーには反映済みという状態が作られる。

5.3 書き込みが重なるとき

トグルを素早く二回押したとしよう。オンとオフが出ていき、応答が入れ替わって返ればサーバーの最終状態と画面の最終状態が分かれる。ここで最後の応答だけを採用する規則はむしろ有害だ。先に届いたものが、あとから送ったものかもしれないからである。書き込みではリクエストを直列に並べるか、利用者の最後の意図だけを残して一度だけ送るか、サーバーが判定できるようバージョンを添えて送る方向へ進む。どちらにせよ画面だけでは決められず、サーバーと規約を合わせる必要がある。オフラインで切った設定が戻ってしまう同期の問題も、根は同じ場所にある。

6. 派生状態と重複保存

カートの項目があり、合計金額がある。合計は項目から計算できる値、つまり派生状態だ。ところが画面のあちこちで合計を使ううち、いつしか合計を別に保存したくなる。ここで分かれ道が現れる。

  • 保存すればずれる — 項目だけ変えて合計の更新を落とす経路が必ずひとつは生まれる。しかもその経路は、たいてい後から追加された機能の中にある
  • 毎回計算すれば高くつく — 項目が数千あったり、計算に並べ替えやグループ化が含まれれば、画面が更新されるたび同じ計算を繰り返す
  • 覚えておけばキーが問題になる — 計算結果をキャッシュすると、入力が変わったかを判定する基準が要る。その基準が実際の依存より狭ければ、古い値が静かに残る

判断の基準は二つの問いに絞られる。この値は原本から常に導けるか、そして利用者がこの値を直接書き換えられるかだ。常に導けて利用者が触れない値なら、保存しないのが既定でよい。逆に利用者が手を入れられる値 — 自動計算された送料を担当者が上書きできる場合 — はもはや派生ではなく、それ自体が原本なので保存しなければならない。ここで派生と原本を取り違えると、利用者が入力した値が再計算に上書きされて消える事故になる。

きっかけとなった記事が指摘した三つ目の問題も、まさにこの場所だ。同じ入力から作られる派生値を複数の画面がひとつのように共有するのが難しいということ、とりわけ計算に副作用が混ざると — 値を求めるにはサーバーへ一度尋ねなければならない、といった場合 — 純粋計算を前提にした道具がそのままでは当てはまらないということである。計算と取得が混ざった値は派生状態の顔をしているが、実際には前に見たサーバーデータの複製に近く、古くなることと再取得の問題をそっくり引き継ぐ。

7. URL を状態として使うということ

検索語とフィルタとページ番号をアドレスに入れると、いくつかが無料でついてくる。リンクをコピーして同僚に送れば同じ画面が開き、戻るが利用者の期待どおりに動き、再読み込みしても画面が保たれ、ブックマークと新しいタブがそのまま使える。この四つを自前で実装すればかなりの量になるのに、アドレスバーはすでにそれをやってくれている。

代わりに制約がつく。

  • 文字列だけだ — オブジェクトや日付は直列化が要り、その形式がそのまま公開された契約になる
  • 他人に見える — サーバーのアクセスログ、リファラーヘッダー、肩越しに見えた画面にそのまま残る。個人を識別する情報やトークンを置く場所ではない
  • 長さに現実的な上限がある — 選んだ項目を数百個アドレスに詰める設計は、どこかで切れる
  • スキーマを変えると古いリンクが壊れる — パラメータ名を変えた瞬間、すでに共有されたリンクは静かに別の画面を開く
  • 履歴が汚れる — 検索語を一文字打つたびに記録を積めば、戻るを二十回押さないと前の画面に出られない

最後の項目は実務で最もよくぶつかる。判断は単純だ。利用者が戻るで帰ってきたい地点かを問い、そうなら記録を積み、そうでなければ現在の項目を置き換える。入力の途中は置き換え、フィルタの確定とページ移動は追加のほうが、おおむね期待に合う。

もうひとつ。サーバーレンダリングを使う構成では、URL はサーバーが知りうる唯一のクライアント状態だ。最初の画面をサーバーで描くには、何を描くのかがアドレスに入っていなければならない。この事実は、どの値をアドレスに載せるか決めるとき思ったより大きな重みを持つ。

8. グローバルストアが実際に解くものと先送りするもの

ここまで来ると自然にグローバルストアを思い浮かべる。値を一箇所に集めればずれが減りそうだからだ。実際に解けるものはある。

  • 途中のコンポーネントを経由して値を手で降ろさなくてよくなる
  • 変更地点が一箇所なので、何がいつ変わったのかを観察できる
  • 画面の外で起きた変化 — 通知の受信、トークンの失効 — を受け止める場所ができる

先送りされるものも明確だ。きっかけとなった記事の四項目のうち三つが、まさにこの場所にある。

  • 寿命 — 画面の中の値は画面が消えるとき一緒に消えるが、グローバルに上げた値には自然な消滅時点がない。ログアウトするとき、別の組織へ切り替えるとき、画面を離れるとき、何を消すのかの一覧を手で管理することになる。この一覧は機能が増える速さと同じだけ古くなる
  • 共有範囲 — 最初は画面ひとつでしか使わなかった値を二つが使うようになれば位置を上げ、あとから再び狭めようとすれば表現方法そのものを書き換えることになる。範囲は一度広げると戻しにくく、だからたいてい広げたまま残る
  • 凝集 — ひとつの機能を構成する値・更新ロジック・初期化が別々のファイルへ散らばる。機能を消すとき何を一緒に消すべきか誰も確信できない状態は、ここで作られる

ツールの名前をいくつか挙げても助けにはならない。単一のストアに集める系統、小さな単位に割って組み合わせる系統、サーバーデータのキャッシュを別の層として切り出す系統があり、それぞれ上の三つのうちどれを楽にするかが違うだけだ。どれもずれ自体をなくしはしない。どのツールを検討するにせよ、問うべきことは同じである。この値は誰が消すのか、範囲を変えるには何を直すのか、機能を丸ごと消すとき何が残るのか。この三つに答えが出れば、ツール選びはその次の問題だ。

9. よくある誤解

チームで繰り返し出てくる言い回しがある。たいてい半分は正しく、間違っているほうの半分があとで高くつく。

よく言われること実際には代わりに問うべきこと
グローバルに置けば楽だ受け渡しは楽になり、破棄が難しくなるこの値はいつ誰が消すのか
キャッシュは勝手に管理される取得は自動で、捨てる時点は人が決める何が変わればこの値は古くなるのか
ローディング表示があれば十分だスピナーは遅延を告げるだけで、失敗・部分成功・中断は語らない失敗したとき画面は何を見せるのか
楽観的更新は無条件によい UX だ巻き戻しが見えなければ、かえって嘘になる巻き戻る場面は利用者の目に入るのか
グローバルなら画面の同期は終わりだ同じ値を見るだけで、いつ取り直すかはそのまま残るこの値の原本は誰なのか
ツールを変えれば片づく寿命・範囲・凝集はツールではなく設計にあるいまずれている場所は正確にどこか

表の最後の行が最もよく繰り返される。ツールの入れ替えはコードを整理し直す機会をくれるので、実際に良くなったように見える。良くなったのはたいていそのとき一緒に引き直した境界であって、ツールそのものではない。同じ境界を古いツールで引いても、似たように良くなっていた可能性が高い。

10. テストが難しくなる場所

状態まわりの欠陥が長く生き残る理由のひとつは、テストがうまく付かないことだ。難しさはほとんど時間と順序から来る。

  • 応答の順序を入れ替えながら確かめる必要があるのに、実際のネットワークではその順序を再現しにくい
  • 実際のタイマーを待つテストは遅く、遅いテストは結局オフにされる
  • キャッシュがテストの間に生き残ると、実行順によって結果が変わる。単独では通り、まとめて回すと落ちる型だ
  • 楽観的更新の途中フレームは、最終状態しか見ないテストには捉えられない。巻き戻しが正しいかは、わざと失敗を作らなければ確かめられない
  • ブラウザストレージに残った値はテスト環境にもそのまま残り、たった今消した機能の古い値が影響し続ける

対策にもそれぞれ代償がある。時間とネットワークを差し替え可能にすれば順序を自在に組めるが、コードに層がひとつ増え、その層は実際の環境と微妙に違うのでテストだけが通る区間を作る。偽のサーバーを立てれば実際に近づくが、契約がずれたときに沈黙する。完全に安全な組み合わせはなく、何を取り逃すかを選ぶことになる。

それでも優先順位は比較的はっきりしている。巻き戻しの経路と無効化のルールを先にテストする。この二つは失敗してもエラーにならず、静かに間違った値だけを残すので、自動検査がなければ利用者の申告が唯一の発見手段になる。逆にローディング表示やスピナーの有無は目で見てすぐ分かるので、検査の優先度は低い。

11. 確認できなかったこと

  • 各方式の性能差を示す一般化された数値 — 画面規模・データ量・更新頻度によって結果が変わるため、条件を明示していないベンチマークは引用していない
  • 特定ライブラリの現在の既定動作と API — 更新時点の既定値や無効化の方式は版が上がるたび変わるので、実際の値は各自が使う版の公式文書で確かめるほうが正確だ
  • きっかけとなった記事の著者が示した解法の細部 — 四つの問題提起の部分だけを確認しており、その後の議論と反応はこの記事の範囲に入れていない

12. まとめ — なくす代わりに扱う方へ

画面とサーバーはずれる。これは不具合ではなく構造だ。原本が別のコンピュータにあり、その原本を他人も書き換え、あいだをつなぐネットワークが順序も成功も保証しない以上、複製を持っている画面はいつも少しずつ間違っている。状態管理はこのずれをなくす技術ではなく、ずれをどこで表に出すか選ぶ技術に近い。

だから実務でまずやることは、ツールを選ぶことではなく値を分けることだ。いまのコードから値をひとつ選んで三つ問えばよい。この値の原本はどこにあるのか、いつ消えるべきか、間違っていたとき利用者は取り消せるか。三つとも即答できる値は、たいてい問題を起こさない。ひとつでも詰まる値があれば、そこが次の不具合の生まれる場所だ。

完全な解法がないという事実は、悪い知らせばかりではない。解法がないなら残るのは選択であり、選択は条件に応じて違えられる。取り消せない値はサーバーに最後の判定をさせ、巻き戻しが目に見える操作にだけ楽観的更新を使い、無効化のキーを画面ではなくデータの単位で取り、戻るで帰ってきたい地点だけをアドレスに記録する。この四つを守るだけで、冒頭の不具合の大半はそもそも生まれない。残るものはそのとき一つずつ見ればよい。要件が足し算ではなく掛け算になる UI がそうであるように、ここでも難しいのは項目ひとつひとつではなくその組み合わせだ。
