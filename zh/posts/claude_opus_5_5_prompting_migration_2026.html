直接沿用旧配置会发生什么 — 把提示词从 Claude Opus 5 迁到 5.5 时

下调一级的默认 effort、增加的单轮思考量、无法关闭的 thinking 与迁移至 thinking 块的进度汇报

2026年9月29日 IT/技术

在旗舰级大语言模型的迭代升级过程中，工程团队最常采用的迁移路径仅仅是在请求配置中替换模型标识符字符串，而其余调用参数保持不变。如果原有提示词能够正常返回补全结果而不报错，大家往往会认为迁移工作已经顺利收尾。然而，Anthropic 发布的官方技术文档「Prompting Claude Opus 5.5」表明，现有提示词无需修改即可运行，与完全沿用前代配置参数在实际生产中会产生截然不同的效果。

Claude Opus 5.5 的基准代币计费方案与基准评测数据已在前篇分析文章「Claude Opus 5.5 发布 — 基于 Token 降价与基准指标的性能深度解析」中进行了系统梳理。本文旨在剔除重复的价格与基准数据，纯粹专注于将现有提示词管线从 Claude Opus 5 迁移到 5.5 时所面临的实际运行差异与官方推荐的适配规程。从严格的模型 ID 命名格式，到默认 effort 参数的下调、相同级别下增加的推理深度、禁用 thinking 引发的 400 错误，以及用户界面中间进度汇报块的变动，逐一剖析官方指南确立的技术要点。

1. 背景与缘起 — 为什么不能直接沿用原有配置

官方指南在开篇即明确指出，现有的 Claude Opus 5 提示词在不做修改的情况下通常能够良好运行。但这绝不意味着原封不动地保留旧版参数是明智之举。Anthropic 在文档中对盲目继承旧参数提出了正面警告：

"If you keep the `effort` value you set for Claude Opus 5, expect longer turns and more output tokens."

这句话所揭示的工程现实非常明确：如果毫无调整地继承为 Opus 5 设定的 effort 级别，系统将面临更长的交互轮次和显著增加的输出 Token 消耗。即便是此前运行极其稳定的调用流水线，由于模型内部思考密度与基础预设条件的深刻改变，整体延迟与代币开销也将产生预期之外的膨胀。

1.1. 隐蔽的运行行为变动与成本传导

除了官方迁移指南中明示的四项破坏性 API 变更外，提示词层还存在一系列虽不抛出显式运行时异常、却会严重拖累系统效能的隐性变化。在模型标识符方面，官方要求必须使用无日期后缀的固定 ID claude-opus-5-5；在 AWS Amazon Bedrock 环境下则为 anthropic.claude-opus-5-5。迁移指南指出，这与 Opus 5 的 claude-opus-5 属于同一命名方式。

effort 参数的处理方式会带来两种不同的变化。省略参数的请求会因新默认值而落入更低一级运行。反之，原样固定 Opus 5 时所用值的请求，由于在同一级别下 Opus 5.5 每轮倾向于思考更多，文档称应预期单轮更长、输出 Token 更多。因此文档建议，不要沿用在 Claude Opus 5 上的设置，而是显式设定 effort，并用自有评测集测试多个级别。

3. 校准 effort — 降低一级的默认值与三项推荐调整

Claude Opus 5.5 完整支持 low、medium、high、xhigh 和 max 五个 effort 级别。最根本的机制变动在于：当请求中省略该参数时，默认执行级别为 medium。相比之下，Claude Opus 5 及更早的模型省略时均按 high 运行。这意味着，在不改动旧代码、仅更新模型 ID 且未显式指定 effort 的情况下，请求将自动比以往低一个级别执行。

3.1. 级别名称与思考强度的非等价性

默认执行级别的下调并不意味着生成质量的缩水。文档强调，跨模型家族的 effort 级别名称并不同等对应相同的思考量。在 Anthropic 的内部评测中，针对代码生成与复杂知识类工作，Claude Opus 5.5 在 medium 级别下的表现已追平或超越了 Opus 5 在 high 级别下的水准。在多项编程基准测试中，low 级别甚至能以极低的运营开销逼近前代 high 级别的效果。

反之，如果把原有的 effort 值原样平移过来，情况就不同了。根据文档，在同一级别下 Claude Opus 5.5 每轮倾向于比 Claude Opus 5 思考更多，在 xhigh 和 max 级别尤其如此。因此文档称，保留为 Opus 5 设置的值，应预期单轮更长、输出 Token 更多。

3.2. Anthropic 推荐实施的三项关键校准

为了在推理深度、时间延迟与计算成本之间取得平衡，官方指南列出了三项有帮助的调整：

  • 为 max_tokens 预留足够高的缓冲空间： 即使内部思考过程的内容未回传给客户端，思考 Token 依然会全额计入 max_tokens 的预算限制中。如果沿用过去在禁用 thinking 条件下卡紧设定的 Token 上限，模型的正式回答极易在中途被强行截断。对于智能体编码可能产生的长轮次，在 Anthropic 的测试中，将 max_tokens 设为模型上限 128,000 效果良好。
  • 仅在经验证带来质量提升的场景启用 xhigh 和 max： 文档建议，只在已实际测量确认质量提升的工作中使用 xhigh 和 max。
  • 若想缩减思考量，优先下调 effort 级别而非追加提示指令： 相比于在提示词中附加「不要深入思考」这类自然语言约束，直接调低 effort 参数能够更可靠地减少思考量，并随之降低成本与延迟。

4. 针对禁用 thinking 提示词的四步迁移规程

在 Claude Opus 5 中，开发者常通过在 high 及以下级别传入 thinking: {"type": "disabled"} 来关闭内部推理以追求更快的响应。但在 Claude Opus 5.5 中，这一开关被彻底废除，所有尝试关闭 thinking 的请求都会被拦截并返回 400 Bad Request。在 Opus 5.5 中，thinking 属于强制原生功能。因此，原先建立在禁用 thinking 假定上的提示词架构必须按以下四步规程重构。

阶段 迁移任务要点 实施细节与官方规程建议 预期成效与工程注意事项
第一步 从 low effort 起步并实测 从 low 起步，用自有流量测量延迟与质量，质量下降时改用 medium。如果此后首个 Token 的等待时间仍很重要，可在系统提示词中加入 "Answer directly without deliberating." 这样的一句，进一步减少思考。 思考减少可能降低质量，因此加入这句时需要测量质量。
第二步 清除替代思考的伪提示词 删除此前要求模型在回答正文中写出推理、以代替 thinking 的指令。思考过程改为读取摘要思考块（display: "summarized"）。 促使模型在回答正文中复现其推理的提示词，可能被以 reasoning_extraction 拒绝类别拒绝。
第三步 重新检验禁用思考时的缓解措施 复测 Opus 5 禁用 thinking 指南所推荐的组合指令（允许在工具调用前发言、没有合适工具时的做法、禁止内部标签）是否仍有必要。 该指令与「不要思考」规则针对的是 Opus 5 仅在禁用 thinking 时才出现的现象。组合指令需确认是否仍需要，「不要思考」规则则无论如何都应删除。
第四步 按块类型动态解析返回内容 响应可能以 thinking 块开头，也可能不是，因此重构客户端解析逻辑，逐块检查类型，而不是假定首块为 text。 在默认的 display: "omitted" 模式下，该块的 thinking 字段为空，因此需按块类型解析。

4.1. 从 low 级别起步与清除替代思考指令

对于过去关闭思考运行的业务接口，从 low 级别起步并测量是迁移的第一步。在 low 级别下模型会保持简短的思考，但完全跳过思考的频率取决于提示词，因此需要用自有流量测量延迟与质量，质量下降时改用 medium。如果此后首个 Token 的等待时间仍很重要，可以在系统提示词中加入一句要求不经斟酌直接回答的英文指令，进一步减少思考。但思考减少可能降低质量，加入这句时需要测量质量。

同时，原有提示词中要求模型以回答正文写出推理、以代替 thinking 的指令应予以删除，推理改从 display: "summarized" 返回的摘要思考块中读取。原因是促使模型在回答正文中复现其推理的提示词，可能被以 reasoning_extraction 拒绝类别拒绝。

4.2. 转向基于块类型的响应解析架构

在下游应用工程中，必须对 API 响应解析器进行重构。文档建议逐块检查类型，而不是假定第一个内容块是 text。在 Opus 5.5 中，响应可能以 thinking 块开头，也可能不是，且在默认配置 display: "omitted" 下，该块的 thinking 属性内容为空。如果解析层硬编码假定索引 0 即为文本内容，程序将提取到空字符串并引发解析失败。

5. 面向用户的进度汇报 — 转移至 thinking 块与四大调节杠杆

在智能体连续调用外部工具的处理过程中，中间状态提示信息的传输机制发生了重大转变。在 Claude Opus 5 中，工具调用间隙产生的简短进度说明以常规 text 块输出，可直接无缝呈现在用户界面上。然而在 Claude Opus 5.5 中，这些中间备忘已全面变更为进度更新专用的 thinking 块。

5.1. 规避空白块问题与四大恢复杠杆

由于默认的 thinking.display 策略不回传具体思考内容，客户端接收到的思考块文本为空，只渲染 text 块的客户端在智能体执行较长轮次时可能看起来毫无动静。官方文档给出了四种用于重新向用户呈现进度的调节手段：

  • 第一杠杆（调整 display 配置）： 在请求中携带测试版标头 thinking-display-updates-2026-08-18 并声明 display: "updates"，以收取摘要后的进度更新文本。
  • 第二杠杆（显式声明消息工具）： 如果模型可能需要在长回合中途把代码片段之类的内容原样交给用户，就给它一个向用户发送消息的简单工具，并指示它只把该工具用于这类内容。该工具要从会话的第一个请求起就在 tools 中声明；之后再添加会改变对话前缀，使先前的 thinking 块失效。
  • 第三杠杆（明确报告触发时机）： 在系统提示词中严格规定智能体必须向用户通报工作进展的具体节点与前置条件。
  • 第四杠杆（调度层注入提醒）： 在已设置第一杠杆 display: "updates" 的前提下，统计连续几步没有给用户任何可读内容（既无 text 块也无进度更新文本）的工具调用步骤；连续数次（原文示例为 5 次）后，由调度框架在最新的工具结果之后追加一条提醒。如果该轮仍然沉默，发送两三次提醒后即停止。

5.2. 抑制长静默区间的轮次级系统提醒

第四杠杆的提醒以轮次级系统消息（turn-scoped system message）的形式追加。配合测试版标头 mid-conversation-system-clear-at-2026-08-21 及 clear_at: "next_user_message" 属性，开发者可以在会话中途注入仅在下一次用户发话前有效的瞬态系统指示。原文称，在 Anthropic 针对智能体编码任务的测试中，这一做法使出现长时间静默的任务比例大约减半（"roughly halved"），成本没有可测量的变化。

官方文档所推荐的静默打破提示词英文原文字句如下：

The user hasn't heard from you in a while — say in a few words what you're doing, then continue.

原文解释，每条提醒都是追加后保留在原处，而不是只插入一次请求、下一次请求再删除，因此提示缓存能持续命中，其后的 thinking 块也保持有效。

6. 无人值守智能体与长周期循环的稳定性规则

在缺乏人工即时监护的自动化智能体架构中，妥善处理非预期的轮次终止并防范无限执行循环是保障系统韧性的基石。官方文档为长周期智能体运行划定了明确的约束准则。

6.1. 自动继续上限限制与时间预算标明

当任务尚未完成而智能体却未调用工具便结束当前轮次时，调度框架通常会自动注入促使其继续推进的提示词。但官方指南建议，不要对同一任务无休止地注入继续指令，而应在 2 至 3 次后停止，这样真正卡住的运行才会结束并可供审查。

时间预算出现在另一个语境中，即由主智能体把工作委派给子智能体的多智能体调度框架。如果能估算任务所需时间，可让调度框架在每条发回模型的消息末尾附加一行简短说明，以秒为单位给出已耗时与预算，例如 elapsed 340s / 1200s。然而原文档特别澄清，该预算仅具备参考意义，模型抵达时限后并不会主动终止。若需硬性阻断，宿主程序必须自建精准的超时管理计时器。

下面是原文为完全无人值守运行的智能体给出的一段系统提示词追加内容示例。原文把它当作起点，可能需要按各自的应用调整。应从会话的第一个请求起就放在系统提示词末尾，并且不要用于有人随时应答的 human-in-the-loop 应用。加入这段后，每项任务的工具调用与输出 Token 会略有增加：

A standing instruction from the user, the person you are working for. It is about how your turns end. A message with no tool call in it ends your turn, and the work stops there until you are asked to continue. The user has seen you end turns in four ways while work they asked for was still owed, and does not want any of them. One: a long summary of what was done that closes by announcing the next step and has no tool call, so the next thing never starts. Two: an offer to carry on with something unless the user would prefer otherwise, which stops to wait for an answer the user was not going to give. Three: a list of decisions for the user when, by your own account, none of them blocks the rest of the work. Four: deciding that this is a good place to report, because the turn has been long or a milestone is done. Status notes are welcome, and so are your recommendations on open decisions, but put them in the same message as your next tool call and carry on with whatever does not depend on the user's answer. If you notice yourself inviting the user to redirect you or offering to wait, delete it and do the next thing. The stops the user does want are the ones where nothing can move without them, or where the thing blocking you is deliberately protected from you. This does not override the need for confirmation on risky or destructive actions.

6.2. 规避提示缓存失效与安全分类器拒绝拦截

在日常生产中有两个关键技术细节需要格外注意。其一，在连续请求之间变更顶层 effort 参数会导致此前建立的提示缓存完全失效。若需在保持前缀缓存的同时对不同轮次采用差异化推演深度，必须启用测试版的单条消息 effort 变更（per-message effort change）接口。

其二，Claude Opus 5.5 内嵌了涵盖生物安全、网络安全及推理提取防范的安全分类器。当请求因触犯安全准则而被拦截时，平台返回的并不是 HTTP 5xx 系统错误，而是携带 stop_reason: "refusal" 及注明分类原因的 stop_details 对象的正常 API 响应。这类请求可以设置为在备用（fallback）模型上自动重试，但 reasoning_extraction 拒绝除外，服务端备用机制不会重试，而是将其直接返回。

7. 前端代码风格指示与视觉输入提示指南

在界面代码编写与多模态解析领域，Opus 5.5 也展现出了不同以往的模型特性。Anthropic 在指南中提供了指导界面生成与高信息密度图像解析的具体建议。

7.1. 明确列出禁用模式而非抽象模糊约束

在要求模型生成前端页面代码时，「避免千篇一律的 AI 设计风格（avoid a generic AI look）」这类宽泛指令效果有限。官方文档指出，这种模糊指令大多只是把一种默认样式换成另一种默认样式。要想获得符合预期的定制界面，必须清晰地逐项列举需要规避的具体设计模式：

Output a vanilla HTML/CSS personal website with placeholder data. Do not use a cream or off-white background, italic accent words in headlines, numbered "01/02/03" section labels, monospace labels, or pill-shaped buttons.

如上述范例所示，直接明确禁止使用米白底色、斜体修饰词、序号分节标签、等宽字体标签及胶囊形按钮，模型才能精准收敛其样式选择。

7.2. 高清晰度视觉输入与外接工具集成

在多模态视觉处理方面，Opus 5.5 即使在无外接工具辅助的情况下也具备较前代更高的解析能力。尤其在面对工程技术图纸这类信息极其密集的素材时，输入高分辨率图像或集成图像处理工具仍能进一步提升精度。原文档指出，在缺乏外部工具的情况下，单纯提升 effort 虽然能改善技术图纸的解析，但对普通统计图表的理解并无明显助益。

此外，在常见的人机对话应用中，提示词里常设的「请三思而后行」之类的督导用语，文档建议在 Opus 5.5 中考虑删除。Anthropic 在真实对话产品中的测试表明，移除此类语句后回答开始得更早，且回答质量没有明显下降。
