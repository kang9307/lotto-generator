The Decision Behind Every Moving Graphic

Using the ThorVG 1.1 release as a baseline to rethink how we pick web animation formats

Jul 28, 2026 Dev & Infra

Introduction: the spinner was the heaviest thing on the page

Anyone who has run a few performance audits keeps meeting the same scene. It is not the hero image and not the web font. It is the little animation spinning in the loading state, and it is the largest resource on that page. The reason is usually mundane. A designer delivered an asset, an engineer dropped it in as delivered, the asset happened to be a GIF, it had a lot of colors, and it ran for a lot of frames. Nobody made a bad decision, yet the outcome is bad.

ThorVG 1.1.0 shipped on 22 July 2026. It is a C++ vector graphics engine that renders SVG and Lottie, and it compiles to WebAssembly so it also runs in a browser. A browser demo made the rounds on GeekNews. News like that naturally pushes people toward the question should we move to Lottie then?, and I think that question arrives in the wrong order.

Putting motion on a web page is not a library selection problem, it is a constraint problem. What has to be expressed, whether the user needs to be able to control it, how many times it repeats, how many extra kilobytes a mobile connection can absorb, and what people who do not want motion will see instead. Once those five are settled, the format is nearly determined. You do not pick an engine because it is good. You pick it only when your constraints demand it.

So this is not an introduction to ThorVG. ThorVG 1.1 is used here purely as a baseline, a coordinate for checking how far browser vector animation has come. The rest of the space goes to how to separate the six available approaches, what adoption actually costs, and when not to adopt at all. That last question is the most important part of this article.

1. Vector versus raster: the split is not about resolution

1.1 The difference is what gets stored

The usual explanation stops at vectors do not pixelate when you scale them up. That is true but insufficient for making decisions. The real difference is what the file stores.

  • Raster stores the resulting pixels. File size roughly follows resolution multiplied by frame count multiplied by color complexity. Simple or complex, filling the screen costs you
  • Vector stores instructions for drawing. File size follows the number of shapes and keyframes. Double the display resolution and the file is unchanged
  • So vectors win decisively for simple forms displayed large: icons, logos, line art, progress indicators
  • They lose for complex forms displayed small. Recomputing thousands of paths every frame is more expensive than baking pixels once
  • Vector defers cost to draw time. The download is light, but CPU or GPU work continues for the entire playback
  • Raster front-loads cost into transfer. Once downloaded there is only decoding, so playback is predictable

Understanding that trade shows why vector is always better is a dangerous sentence. Vector is a choice to reduce bytes by moving computation onto the user's device. If your audience is mostly low-end Android hardware, that relocation can be a net loss.

1.2 There are options on the raster side too

People reflexively equate animated images with GIF, but MDN's image format guide tells a different story. GIF is 8-bit indexed color, so 256 colors per frame, compressed losslessly with LZW. Introduce a gradient and it bands; add dithering to hide the banding and compression degrades, so the file grows.

MDN recommends PNG for lossless still images and says to consider WebP, AVIF or APNG for animation sequences. The characteristics back that up.

  • APNG extends PNG into lossless animation and, per MDN, is supported from Chrome 59, Edge 12, Firefox 3, Opera 46 and Safari 8. Color freedom and alpha are intact in a way GIF cannot match
  • WebP supports both lossy and lossless and can carry animation. MDN notes lossy WebP images average 25 to 35 percent smaller than JPEG at visually similar quality
  • AVIF supports 8, 10 and 12-bit depth with wide color gamut and HDR, and handles animation. MDN flags a real limitation: it does not support progressive rendering, so the file must download fully before it displays
  • Animated AVIF support varies across browsers, so MDN advises pairing it with fallbacks via <picture>

The false dichotomy is if you are leaving GIF you must go to Lottie. A large share of these problems is solved simply by converting GIF to APNG or animated WebP. No runtime added, no change to the design workflow, and accessibility handling stays identical to any other image.

2. Putting the options in one table

Six approaches actually come up in practice. This table is not a ranking. It exists to show which column disqualifies which row once a constraint is applied.

Approach Weight behavior Quality and scaling Runtime control Accessibility handling Good fit for
GIF Grows sharply with frames. Worst with many colors 256-color ceiling, degrades when scaled Essentially none. Cannot pause or rewind Alt text only. Hard to honor reduced motion Short loops with flat colors where compatibility rules
APNG and animated WebP Better than GIF but still frame-proportional Full color with intact alpha Essentially none Same as images. A still fallback is easy to supply Drop-in replacement for GIF, lowest effort available
Video (MP4, WebM) Scales with duration. Overwhelmingly efficient when long Fixed resolution, degrades when scaled Play, pause and seek all available Captions and description tracks. Autoplay policy applies Live-action footage and scenes lasting several seconds
CSS and Web Animations No additional file. A few lines of code Fully vector or DOM based Complete control, easy to bind to state Cleanest possible via media query UI transitions, emphasis and micro-interactions
SVG (SMIL or CSS) Scales with shape count. Icons land in single-digit KB Lossless at any size DOM accessible, controllable per element Providing a pause mechanism is recommended Icons, line art and data visualization
Lottie and dotLottie Small file but large runtime Lossless at any size Playback control, segment jumps, dynamic properties Must be implemented against the player API Designer-authored motion reused across platforms

The column most often skipped is runtime control. Once a GIF or APNG starts, the user cannot touch it. Honoring a reduced-motion preference means swapping in a still image, which means maintaining two sets of assets. CSS, by contrast, is done in one media query. That is precisely why the stronger the accessibility requirement, the more valuable code-driven animation becomes.

3. What Lottie actually is: the price of choosing JSON

3.1 What is stored inside

The official Lottie documentation defines the format as a vector animation format that uses JSON to represent its data. The key point is that it holds structured layers, shapes, keyframes and interpolation rather than pixels. Two properties follow from that design.

  • It is human-readable and tool-processable. Recoloring or swapping text is possible at runtime
  • One file serves every platform while only the player is swapped. That is a real advantage for organizations shipping the same motion to web, Android and iOS
  • In exchange, without a player it is nothing. Unlike an image format, no browser supports it natively
  • JSON is repetitive and verbose, and it balloons once images are embedded as base64

dotLottie exists to fix that last problem. Per the specification, a .lottie file is a ZIP archive compressed with Deflate, carrying the MIME type application/zip+dotlottie. Inside are a required manifest.json and an animations/ directory, plus an optional images/ directory holding PNG, JPG, SVG, WebP or GIF. Because images sit as compressed files rather than base64 strings, the biggest savings appear in animations that include imagery. LottieFiles describes files as 2 to 10 times smaller depending on complexity, but that comes from the format's own proponents, so measuring your own assets is the more reliable route.

3.2 Format support and player support are different claims

This is where most Lottie adoptions go wrong. A file exported from a design tool does not look identical in every player. Some features exist only in specific players, and some exist nowhere.

ThorVG is relatively honest about this. Its official wiki page on Lottie support lists shapes, strokes, fills, transforms, interpolators, masks, mattes, layer effects and text as supported, while stating outright that Expressions sit at a 75 percent overall support rate, 72 percent fully and 3 percent partially. It then documents concrete limits.

  • Only cycle and pingpong loop modes work
  • propertyGroup(level) supports level 1 only
  • Layer name access is disabled owing to a conflict in the scripting engine
  • footage(), coordinate conversion, path creation, posterize time, velocity properties, smooth(), offset and continue loop modes, marker access, camera properties, lookAt(), audio level sampling and path tangent arrays are unsupported
  • On the SVG side, the repository states that SVG Tiny animation, interactivity and multimedia are not supported

The right reading is not ThorVG is lacking. It is confirmation that Lottie looks like a single specification but is in practice an ecosystem where each player supports a different subset. So the adoption question is not should we use Lottie but does the support table of the player we will ship include the features our designers actually use.

4. What ThorVG 1.1 changed, limited to what the release notes state

This section sticks to facts verifiable in the official repository and release notes. No marketing copy is carried over.

ThorVG is a C++ vector graphics engine distributed under the MIT license. The official overview states the core library maintains a binary size of approximately 170KB, described as small relative to engines designed primarily for desktop environments. Accepted inputs are SVG and Lottie JSON, PNG, JPEG, WebP and raw bitmaps, plus TTF and OTF fonts. The rendering backends are CPU software with SIMD, OpenGL/ES, WebGL and WebGPU.

Version 1.0.0 shipped on 31 January 2026 and 1.1.0 on 22 July 2026. The 1.1.0 release notes describe the following.

  • GPU rendering performance improvements through rendering pipeline optimizations and batching enhancements
  • More accurate and consistent stroke rendering across the CPU and GPU engines
  • Experimental OpenType (OTF) font support alongside an enhanced font loading architecture for WebCanvas
  • Expanded Lottie capabilities including experimental Dynamic Tweening and faster Expressions processing
  • Improved Lottie and SVG specification compliance for better real-world content compatibility
  • Platform additions including Android OpenGL support, WebCanvas multi-threading and pluggable font providers

Take the experimental labels seriously. The release notes explicitly mark OpenType font support and Dynamic Tweening as experimental. That label does not mean it fails to work; it means the behavior may change. Build a product-critical screen on top of one of these and you have no grounds to complain when a minor release renders it differently.

Two paths lead to the browser. One is WebCanvas, provided by ThorVG itself, where the C++ engine is compiled to WebAssembly and wrapped in a JavaScript interface. The other is going through a player that uses ThorVG as its internal renderer, such as LottieFiles' dotlottie-web. The second has a lower barrier and ships framework wrappers, so most teams evaluate it first.

For adoption, the official repository lists Canva, Godot, LVGL, Tizen, Espressif-class embedded targets and dotLottie among others. An adopter list is best read as evidence of the diversity of deployment contexts rather than a quality guarantee. Being used in both a game engine and an embedded UI signals few dependencies and high portability.

5. How to read performance numbers: measured where, on what?

Marketing material in this field loves multipliers. But a multiplier with its conditions stripped away means nothing. Here are the four most frequently quoted numbers with their conditions attached.

Quoted figure Who measured Measurement conditions What it cannot tell you
About 80 percent faster rendering, about 70 percent lower peak memory Canva, an adopting company measuring itself, published via the LottieFiles blog On iOS, compared against the previously used rLottie. Workload is the video export and playback pipeline Browser performance. The baseline is another native library, not a browser renderer
CPU rasterization comparison against Skia ThorVG project's own measurement Apple M1 on macOS 15, rendering at 2560×1440, 5,000 semi-transparent primitives per test, ThorVG 1.0.0 against Skia v144 Typical web content. Five thousand semi-transparent primitives is a synthetic compositing load, not an average UI
More than 150 percent GPU rendering improvement ThorVG project's own measurement Only the comparison baseline, versus v0.15, is disclosed. Hardware, resolution and test content are not confirmable in published material Absolute performance. It is a delta against an older in-house version, not a cross-engine comparison
WebGPU roughly 1.8 times OpenGL on average ThorVG project's own description A statement on the official overview page. The measurement method is not confirmable What to expect on specific content. Variance across browsers, drivers and GPUs is wide

The takeaway is not these numbers are inflated. It is that all four are vendor or adopter self-measurements, and only the second discloses its conditions in full. That is not necessarily dishonesty. Graphics performance is so content-dependent that building a universal benchmark is genuinely hard.

The practical stance is simple. Do not decide on someone else's numbers; measure your own heaviest asset yourself. Thirty minutes is enough. And the comparison baseline should not be another engine but whatever you are shipping today. A new engine beating an old engine is not a reason to adopt. A new engine winning on total cost against your current approach is.

5.1 Does WebGPU automatically mean faster?

No. Per MDN, WebGPU is designed to map onto modern native APIs such as Direct3D 12, Metal and Vulkan, makes per-object rendering significantly cheaper on the CPU side, and supports GPGPU computation as a first-class capability. All of that is a genuine advantage.

But MDN also states plainly that the feature is not Baseline because it does not work in some of the most widely-used browsers, and that it is available only in secure contexts over HTTPS. In practice that means the following.

  • Even on a WebGPU path you must keep a fallback to WebGL or CPU
  • Preparing that fallback either adds another binary to download or adds conditional loading code
  • GPU paths carry initialization cost, so they can be a net loss for a short animation played once
  • The benefit grows when you play several animations simultaneously and for a long time, or when the animation occupies a large share of the screen

6. The real cost of a runtime: bundle and WASM

I regularly see teams debating whether an animation file is 40KB or 60KB while omitting the several hundred kilobytes of player entirely. Here are the actual numbers, taken from public package data as of July 2026.

Item Version Size Notes
lottie-web (JavaScript renderer) 5.13.0 About 305KB uncompressed, about 76.8KB gzipped Zero dependencies. Pure JavaScript, so no separate binary
dotlottie-web (JavaScript layer) 0.78.2 About 152KB uncompressed, about 29.1KB gzipped Zero dependencies. WASM is not included in this figure
dotlottie WASM (CPU renderer) 0.78.2 About 1.81MB uncompressed File size within the package. Server compression applies in transit
dotlottie WASM (WebGL renderer) 0.78.2 About 1.94MB uncompressed A separate binary per renderer
dotlottie WASM (WebGPU renderer) 0.78.2 About 1.97MB uncompressed Preparing a fallback means budgeting for two of these
ThorVG core library (native) Per official overview About 170KB A native binary figure, distinct from browser WASM size

The most important row is the last one. Do not mistake the roughly 170KB core figure for a browser cost. That number describes the native core binary, whereas in a browser you add the compiled WASM output, glue code and the player layer on top. No official WASM size figure for WebCanvas from the ThorVG project could be confirmed, so the browser cost has to be measured against the build you will actually ship.

6.1 If you adopt anyway, do at least this much

A high cost does not make adoption wrong. It means you need a structure that recovers what you paid. The minimum measures are these.

  • Lazy load. Defer the player for anything below the fold until it enters the viewport
  • Self-host. Do not fetch from a third-party CDN each time; serve it from your domain so you control caching
  • Verify server compression. Confirm from response headers that brotli or gzip is actually applied to the WASM
  • Ship exactly one. Ending up with two different Lottie players in one project is a surprisingly common accident
  • Pin the renderer. Decide whether a GPU fallback path is genuinely required; if not, ship a single binary
  • Write down the recovery threshold. Record in team documentation how many animations justify this fixed cost
// Minimal pattern: load the player only when it enters the viewport
const target = document.querySelector('#hero-anim');

const io = new IntersectionObserver(async (entries, obs) => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    obs.unobserve(entry.target);

    // For users who asked for reduced motion, never fetch the player at all
    if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) {
      entry.target.innerHTML = '<img src="/img/hero-still.webp" alt="Product overview still frame">';
      continue;
    }

    const { DotLottie } = await import('@lottiefiles/dotlottie-web');
    new DotLottie({ canvas: entry.target.querySelector('canvas'), src: '/anim/hero.lottie', autoplay: true, loop: true });
  }
}, { rootMargin: '200px' });

io.observe(target);

What matters in this pattern is not performance but ordering. Users who want reduced motion never download the player. Handle accessibility before loading rather than after playback starts, and accessibility and performance start pulling in the same direction.

7. What to settle with designers before work starts

Lottie adoptions usually fail at handoff rather than at engineering. A designer produces something that looks right inside the tool, and an engineer discovers later that it renders differently in the player. By then reversing course is expensive. Settling the following before work starts is far cheaper.

Item to agree on Why it becomes a problem Form of the agreement
Pin the player The same file has different support coverage in each player Record the player name and version, and circulate that player's official support table
Scope of effects Many design-tool effects are dropped or approximated on export Use an allowlist. Anything not on it gets re-expressed with shapes and keyframes
Whether expressions are allowed Expression coverage differs by player and some functions are absent entirely Disallow by default; if truly needed, confirm the specific function appears in the support list first
Cap on masks and mattes Each compositing step raises per-frame cost steeply Set a numeric cap per file and flag anything over it for review
Whether bitmaps are embedded Embedding bitmaps erases the weight advantage of vector If unavoidable, package as dotLottie and fix a resolution ceiling
Still fallback frame Reduced-motion users and playback failures both need something to show Have the still frame delivered together. Requesting it later usually stalls
Duration and looping Infinite loops consume battery and attention alike Put a loop cap or a stop condition into the spec

Resistance to this table is understandable. From a designer's seat it reads as a document that narrows the expressive range up front. So it helps to reframe the conversation. This is not a list that restricts expression; it is a list that guarantees what you made is what ships. Motion built on unsupported features gets cut during implementation anyway, and the person who loses in that scenario is the designer.

8. The conditions under which performance collapses

The load from vector animation correlates weakly with file size. A file of a few dozen kilobytes dropping frames on modest hardware is routine. The factors that inflate per-frame cost are generally these.

  • Layer count. Each layer brings transform math and compositing. Helper layers you cannot even see still cost
  • Masks and mattes. Alpha and luma mattes draw into a separate buffer and then combine, so cost climbs steeply with screen area
  • Expressions. Scripts are evaluated every frame. The fact that ThorVG's documentation lets you compile expressions out entirely tells you the cost is not negligible
  • Path vertex count. Auto-traced curves often carry far more vertices than needed, and that returns as rasterization cost on every frame
  • Trim paths and repeaters. Convenient to author, but they regenerate geometry at execution time
  • Screen area occupied. The same file blown up to full screen has vastly more pixels to fill, which hurts most on CPU rasterization
  • Concurrent playback count. A list view with an animation per card accumulates cost linearly with the number of cards
  • High refresh rate displays. On a 120Hz device your frame budget is cut by more than half

It helps to fix a diagnostic order too. This sequence is usually the fastest.

  1. Reproduce on real low-end hardware. The problem is invisible on a development laptop
  2. Swap the animation for a still image and see whether frame rate recovers, which narrows the cause
  3. If it recovers, the file is the problem. Count layers, mattes and expressions and find what exceeded your cap
  4. If it does not recover, the problem lives outside the animation. Look at layout recalculation and main-thread contention
  5. If shrinking the display size helps, you are fill-rate bound. Reducing display area may beat swapping renderers

9. Accessibility: prefers-reduced-motion is not optional

According to MDN, prefers-reduced-motion has been widely available across browsers since January 2020. It takes two values, the default no-preference and reduce, and @media (prefers-reduced-motion) is equivalent to reduce.

What matters is not the syntax but why the setting is on. MDN explains that animation can cause discomfort for users with vestibular motion disorders and notes that scaling or panning large objects are particularly likely triggers. This is not a taste preference; it is a symptom-avoidance setting. The user already declared their situation to the operating system, and the page only has to read it.

The per-OS locations MDN lists are worth knowing for QA. On Windows 11 it is under Accessibility, Visual Effects, Animation Effects. On macOS it is Accessibility, Display, Reduce motion. On iOS it is Accessibility, Motion. On Android 9 and later it is Accessibility, Remove animations.

/* 1) Code-driven animation is finished by a media query */
@media (prefers-reduced-motion: reduce) {
  .hero-anim { animation: none; transition: none; }
  .hero-anim__still { display: block; }
}

/* 2) Player-driven animation must read the same value from JavaScript */
const mq = window.matchMedia('(prefers-reduced-motion: reduce)');

function applyMotionPreference(player) {
  if (mq.matches) {
    player.pause();
    player.setFrame(0);          // hold a representative frame
  } else {
    player.play();
  }
}

// The preference can change while the page is open
mq.addEventListener('change', () => applyMotionPreference(player));

A few more items belong on the list.

  • Provide a stop control. MDN's documentation for SVG animation elements recommends offering a way to pause or disable animation, and that applies doubly to anything autoplaying for more than five seconds
  • Alternative text. If it is decorative, hide it with aria-hidden; if it carries information, deliver the same information as text
  • Pick the right still frame. The frame shown when paused should not be frame zero but the frame that best conveys the content
  • Server hints. MDN also mentions the Sec-CH-Prefers-Reduced-Motion client hint, which makes it possible to serve entirely different assets from the server
  • Autoplay policy. If you fall back to video, Chrome's documentation states muted autoplay is always allowed while autoplay with sound requires user interaction or engagement criteria. Always handle rejection of the promise returned by play()

10. Licensing and legal review

Sometimes a technical evaluation passes and then release gets blocked at the last step. Animation is an area where code and creative work sit in the same file, so the review list does not end at the engine.

What to check What to look at What happens if missed
Rendering engine ThorVG is marked MIT in its repository, which carries an obligation to preserve the copyright notice on distribution Missing notice. Dropping out of the open-source acknowledgment screen is a common slip
Player wrapper Engine and player licenses can differ, and framework wrappers are separate again Checking only the engine and missing the terms of what you actually ship
Bundled fonts Shipping a font instead of converting text layers to outlines brings the font license into play Distributing a font whose license does not permit web embedding
The animation assets themselves Files from public marketplaces can be free yet still carry usage-scope or attribution conditions Exceeding permitted commercial use
Embedded images Bitmaps placed inside a dotLottie are each their own rights object Provenance breaks during packaging
Trademarks and brand assets Logo motion carries both copyright and trademark exposure Assets linger in use after a partnership ends

The practical answer is managing animation assets like dependencies. Record provenance and license per file, and confirm that the engine and player appear in your open-source notice generation. This takes ten minutes at adoption time and days to reconstruct after release.

11. When you should not use it

This is the part I most wanted to write. In the situations below, I believe you should not ship a vector animation runtime at all.

  • When there are only one or two animations. Player cost dwarfs content cost. Downloading a megabyte-class binary to move one icon does not pay back under any arithmetic. Finish it in CSS or SVG
  • When the content is live-action or photographic. The premise of vector does not hold. Anything that cannot be reduced to shapes is far better served by a video codec
  • When your audience runs low-end devices on slow networks. Vector moves computation onto the user's device, and that trade only pays when the device can absorb it
  • When the motion carries information. If something the user must understand exists only as movement, that information disappears for anyone with reduced motion enabled. Information has to survive as text or a still
  • When ownership of maintenance is unclear. Animation files are effectively uneditable without the original design-tool project. If nobody owns that original and its location, in six months you have an asset nobody can change
  • When you would depend on a feature labeled experimental. Building a core screen on something the release notes call experimental turns every version bump into a regression-testing event
  • When it is momentum rather than a brand requirement. Everyone is doing it does not justify a budget. Without a measurement plan for conversion or comprehension, skipping it is the better call

The conditions that do justify adoption are comparatively clear. The same motion has to ship to web, Android and iOS together; animations keep being added; designers need to update them without going through an engineer; and runtime control such as segment jumps, recoloring or state binding is genuinely required. When those four converge, the player cost becomes a fixed cost and unit cost falls as the count rises. Before that point it is a straight loss.

12. A decision order you can actually use

Read top to bottom and stop at the first item that matches. That resolves most cases.

  1. Is it live-action footage? Then it is video. Prepare muted autoplay, playsinline, and rejection handling for play() together
  2. Is it a UI state change such as hover, transition or emphasis? Then CSS or Web Animations. Zero extra files and the cleanest accessibility story
  3. Is it a loop of a few simple shapes? Then inline SVG. DOM access makes per-element control and theming easy
  4. Are you only trying to improve an existing GIF? Then APNG or animated WebP. Better quality and smaller files with no runtime added
  5. Is it complex designer-authored motion reused across platforms? Only here does Lottie become a candidate. Pin the player and circulate its support table first
  6. Having chosen Lottie, check whether images are embedded and consider dotLottie packaging, lazy-load the player, and skip loading it entirely for reduced-motion users
  7. If frames still fall short, put the content on a diet before swapping renderers. Cutting layers, mattes and vertices usually helps more

An engine like ThorVG earns its place at steps five and six of that tree. Dragging a problem that steps one through four already solve up to step five is the most common mistake.

Conclusion: format is a function of constraints, not taste

ThorVG 1.1 is a good coordinate for seeing how far this field has come. MIT licensing, a small core, backends covering both CPU and GPU, and a willingness to publish what is not supported as a list. That last item is genuinely rare. Most projects advertise what works and bury what does not in an issue tracker. Documentation that discloses coverage with numbers means you can actually run an evaluation.

But the existence of a good engine is not a reason to use it. Gathering what this article established: of four widely quoted performance figures, only one disclosed its conditions in full, while the rest were self-measurements or disclosed only a baseline. Adopting a browser player attaches WASM binaries measured in megabytes uncompressed. Lottie feature support is decided by the player, not the format, which is why agreement with designers precedes technology selection. And whatever you choose, handling the reduced-motion preference is not negotiable.

So the conclusion is plain. For most screens the answer is CSS and SVG, and if you are on GIF today, converting to APNG or WebP resolves a large share of the problem by itself. Lottie and the engines that drive it earn their keep in organizations that repeatedly supply the same motion to multiple platforms, where the animation count keeps growing. Outside those conditions, a strong new engine is news worth celebrating, not a reason to adopt.

One last thing. The most expensive mistake in this area is not picking the wrong engine; it is making something move that did not need to move. That case where the loading spinner was the heaviest resource on the page was not a failure of technology selection. The failure was that nobody asked whether an animation belonged there at all.
