When the Same Header Arrives Twice - What May Be Combined and What Must Never Be

Every field gives a different meaning to several, and the runtime decides before you do

2026-08-01 Dev & Infra

The symptom: two cookies were sent, one was stored

The login response set a session cookie and a theme cookie together. Both appear in the server log. Yet the browser holds only the session cookie. Reading the code, nothing is wrong with the part that builds the cookies. So the usual next move is to suspect browser settings or the domain, and half a day disappears.

A large share of this symptom is decided much further upstream. Somewhere, a header that was two lines became one. And that joining is usually not a mistake. For most fields, joining is exactly the behaviour the specification prescribes. The trouble starts when the same treatment reaches a field the specification did not define that way.

So this article is not about blocking duplicate headers. You cannot block them and you have no reason to. The real questions are these.

  • What does a name arriving twice mean for that particular field? Did a list gain members, are there two values, or is this a state that should not exist
  • Who decides whether to combine? Not the developer, in many cases. The runtime decides first
  • Is what your code sees what arrived, or something already processed? By the time you hold a single string, information may already be gone

All three were answered by running them. The same bytes were pushed into different runtimes, and what the receiving side ends up holding was printed. The result compresses into one sentence. Each field gives a different meaning to several, and each runtime handles that meaning differently.

Test environment. Every output below was produced by actually running it on Windows 10 Pro (10.0.19045). The runtimes are Node.js v22.16.0 (win32) and Python 3.13.3 (win32), with servers started directly from each language's built-in HTTP module. Requests were written byte by byte over a raw socket, so that no client library could normalise the headers before transmission. Ports 18090 to 18094 were used and all of them were shut down when the measurements finished.

This article makes no claim about any particular product. The relay in section 7 is a twenty-line minimal implementation written for this article; it does not represent the behaviour of any commercial proxy, load balancer, or web server. How your components handle this must be measured in your own environment. What this article offers is not a conclusion but a method and a set of criteria.

What this article does not cover. The separate trap created by the case of a header name is covered in field names ignore case, code does not. Here the names are always identical. The meaning of cookie attributes lives in SameSite Lax, Strict, None. Section 3 covers one thing only: joining the lines destroys the value.

1. What arrives when the same name is sent twice

Start with the plainest reproduction. One request was built with several names repeated on two lines each, and those exact same bytes were sent to two different servers. Here is what went out.

Three APIs give three different pictures of the same request. The most widely used one returns a single string with the two lines joined by a comma and a space. The other two preserve the lines. And note that Cookie was joined with a semicolon rather than a comma. That field is a semicolon-separated list by definition, so the runtime applied a per-field rule.

The same bytes then went to the Python server.

  headers.get(accept          )     = 'text/html'

  headers.get_all(x-forwarded-for ) = ['203.0.113.9', '198.51.100.4']

    X-Forwarded-For: 198.51.100.4
    Cookie: sid=A1
    Cookie: theme=dark
    Connection: close

Here the first key result appears. The bytes are identical, yet the string API answers differently in the two runtimes.

  • One joins the two lines. The information survives but the boundary is gone
  • The other returns the first line only. The second is discarded quietly. No exception, no warning
  • Both runtimes ship a separate API that returns every line as an array. Only the names differ; the capability is the same
  • Neither raised an error. A duplicate header is not in itself a protocol violation
  • Which means the question 「what happens on a duplicate header」 cannot be answered by looking at one server

There is a place where this difference turns nasty in production. Suppose one team writes the front tier in a language whose string API joins, and another team writes the back tier in a language whose string API takes the first. For the same request, the front sees 「two values joined into one string」 and the back sees 「the first value alone」. Both are correct behaviour and neither leaves a trace in any log.

2. List-based fields are meant to be combined

I do not want to leave the impression that combining is always wrong. It is the opposite. A great many fields should be combined. RFC 9110 Section 5.2 defines it this way.

When a field name is repeated within a section, its combined field value consists of the list of corresponding field line values within that section, concatenated in order, with each field line value separated by a comma. (RFC 9110, Section 5.2)

So 「send two lines」 and 「put commas in one line」 ought to mean the same thing for a list field. That was verified. The same three fields were sent both ways and the results compared.

EXP 2. list-based fields: two lines vs one comma line

 [Node.js v22.16.0]
   accept          via req.headers
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     parsed two lines : ['text/html', 'application/json']
     parsed one line  : ['text/html', 'application/json']
     SAME MEANING     : True
   cache-control   via req.headers
     two lines -> 'no-cache, max-age=0'
     one line  -> 'no-cache, max-age=0'
     parsed two lines : ['no-cache', 'max-age=0']
     parsed one line  : ['no-cache', 'max-age=0']
     SAME MEANING     : True
   accept-encoding via req.headers
     two lines -> 'gzip, br'
     one line  -> 'gzip, br'
     SAME MEANING     : True

 [Python 3.13.3]
   accept          via join(get_all())
     two lines -> 'text/html, application/json'
     one line  -> 'text/html, application/json'
     SAME MEANING     : True
   cache-control   via join(get_all())
     SAME MEANING     : True
   accept-encoding via join(get_all())
     SAME MEANING     : True

Both runtimes, all three fields, resolved to the same list. For a list field it makes no difference whether the members arrived split across lines or joined by commas on one. Combining here is not a loss.

There is a precondition, though. The same Section 5.3 is blunt about it.

A sender MUST NOT generate multiple field lines with the same name in a message, or append a field line when a field line of the same name already exists in the message, unless that field's definition allows multiple field line values to be recombined as a comma-separated list. (RFC 9110, Section 5.3)

In other words, only fields the specification defined as lists may be combined, and combining anything else because the names happen to match sits on the wrong side of that rule. On ordering, the same section is equally explicit.

The order in which field lines with the same name are received is therefore significant to the interpretation of the field value; a proxy MUST NOT change the order of these field line values when forwarding a message. (RFC 9110, Section 5.3)

That order carries meaning is routinely ignored in practice. Code that sorts values or turns them into a set to remove duplicates is common, and for a list field that is throwing away priority information.

2.1 When one line and several lines are mixed

In the real world the two forms mix. Two lines arrive and one of them contains another comma. Counting only the lines gets the number wrong.

request sent:
  > Accept: text/html
  > Accept: application/json, text/plain

readList(accept) = ["text/html","application/json","text/plain"]
  note: 2 field lines, 3 members.

Two field lines, three list members. So reading a list field correctly takes two steps: take every line through the array API, then flatten each line on commas. Code that counts only lines and code that splits only one string are both half a solution.

3. Set-Cookie is destroyed by combining

Now the exception, and it is not a small one. The symptom from the opening comes from precisely here.

Two cookies sent properly, one line each, arrive like this.

3-A. server sent TWO Set-Cookie lines (correct)
 res.headers["set-cookie"] type : Array
 value:
   [0] sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly
   [1] theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 cookies the client will store : ["sid=A1","theme=dark"]
 count = 2

Both cookies are stored. Now the exact same two cookies were glued together with a comma and a space into one line. For a list field this would have been entirely harmless.

3-B. the SAME two cookies glued with ", " into one line
 raw value on the wire:
   sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly, theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT
 now split it back on "," the way a list-based field is split:
   [0] sid=A1; Path=/; Expires=Wed
   [1] 20 Aug 2026 10:00:00 GMT; HttpOnly
   [2] theme=dark; Path=/; Expires=Fri
   [3] 22 Aug 2026 10:00:00 GMT
 pieces = 4   (we started with 2 cookies)
 cookies the client would store : ["sid=A1","20 Aug 2026 10:00:00 GMT","theme=dark","22 Aug 2026 10:00:00 GMT"]

Two cookies shattered into four pieces. The cause is plain. The expiry timestamp carries a comma after the weekday, so the moment a comma is treated as the separator, a single cookie gets cut in half from the inside. And the trailing half looks like a brand new cookie.

RFC 9110 anticipated this and wrote it into Section 5.5.

Fields that expect to contain a comma within a member, such as within an HTTP-date or URI-reference element, ought to be defined with delimiters around that element to distinguish any comma within that data from potential list separators. (RFC 9110, Section 5.5)

The cookie field is not defined that way. There are no quotes wrapping the comma in the expiry timestamp. So there is no principled way to tell, from a comma alone, which is a separator and which is data. Section 5.3 of the same document names this field as an explicit exception.

In practice, the Set-Cookie header field often appears in a response message across multiple field lines and does not use the list syntax, violating the above requirements on multiple field lines with the same field name. (RFC 9110, Section 5.3)

3.1 Dropping the expiry attribute does not make it safe

You might think the fix is to stop using an expiry attribute. Measured, that path is worse.

3-D. even without Expires, joining loses a cookie boundary
 two lines  -> ["sid=A1; Path=/","theme=dark; Path=/"]
   stored   -> ["sid=A1","theme=dark"]  count=2
 one line   -> "sid=A1; Path=/, theme=dark; Path=/"
   a cookie parser reads ONE cookie from ONE line:
     name/value = sid=A1
     attributes = ["Path=/, theme=dark","Path=/"]
   -> "theme=dark" arrived as an ATTRIBUTE of sid, not as a cookie.
   -> stored cookies = ["sid=A1"]   count=1   (one cookie silently vanished)

Here the opening symptom reproduces exactly. Two cookies were sent and only one was stored. The second cookie did not disappear; it was absorbed as an attribute of the first. To the parser, one line is one cookie and everything after a semicolon is an attribute. Unrecognised attributes are ignored, so no error is raised.

  • The server log records that two cookies were created. That is why staring at the server side never reveals the cause
  • The browser storage panel shows one cookie. The response headers panel shows one long line
  • What disappears is always the trailing cookie. So the report arrives as 「only the last cookie I set does not work」
  • With an expiry attribute present, phantom cookies can appear too, because a severed date fragment looks like a cookie name
  • The meaning of the cookie attributes themselves is a separate matter, covered in SameSite behaviour

3.2 Coercing to a string brings the damage back

There is a path that ruins this after receiving the array correctly.

3-E. what the array API vs the string API report
 res.headers["set-cookie"]         = Array(2)
 res.headersDistinct["set-cookie"] = Array(2)
 res.rawHeaders set-cookie lines   = 2
 String(res.headers["set-cookie"]) = "sid=A1; Path=/; Expires=Wed, 20 Aug 2026 10:00:00 GMT; HttpOnly,theme=dark; Path=/; Expires=Fri, 22 Aug 2026 10:00:00 GMT"
   <- the moment you coerce it to a string, the "," is back and the damage is done

An array becomes a single comma-joined string the instant it is converted. Printing it to a log, dropping it into a template literal, or copying it verbatim into another response all qualify. This one field has to stay an array all the way through.

4. Two Host lines - which one does each hop believe

Now a field that is not a list. Host is a single-value field that determines which target a request is aimed at. Sending two lines was measured.

EXP 4-A. two Host lines, different authorities
  > GET /who HTTP/1.1
  > Host: front.example.test
  > Host: back.example.test
  > Connection: close

 Node.js v22.16.0:
  status : HTTP/1.1 200 OK
    req.headers[host]         = 'front.example.test'
    req.headersDistinct[host] = ['front.example.test', 'back.example.test']

 Python 3.13.3:
  status : HTTP/1.1 200 OK
    headers.get(host)     = 'front.example.test'
    headers.get_all(host) = ['front.example.test', 'back.example.test']

The measurement says this. Neither server refused. Both returned 200, and asked through the string API both give the first value. Both also still hold both values in the array API.

The interesting part is Node's behaviour. In section 1 X-Trace-Id was joined with a comma, but Host was not joined; only the first value came back. The same runtime applies different rules per field. How widely that applies was checked.

EXP 4-B. single-value fields sent twice

  > Authorization: Bearer SECOND
  > Content-Type: application/json
  > Content-Type: text/plain
  > User-Agent: agent-one
  > User-Agent: agent-two
  > X-Trace-Id: aaa
  > X-Trace-Id: bbb

    req.headersDistinct[authorization] = ['Bearer FIRST', 'Bearer SECOND']
    req.headers[content-type]          = 'application/json'
    req.headersDistinct[content-type]  = ['application/json', 'text/plain']
    req.headers[user-agent]            = 'agent-one'
    req.headersDistinct[user-agent]    = ['agent-one', 'agent-two']
    req.headers[x-trace-id]            = 'aaa, bbb'
    req.headersDistinct[x-trace-id]    = ['aaa', 'bbb']

    headers.get(authorization)     = 'Bearer FIRST'
    headers.get_all(authorization) = ['Bearer FIRST', 'Bearer SECOND']
    headers.get(x-trace-id)        = 'aaa'
    headers.get_all(x-trace-id)    = ['aaa', 'bbb']

Node keeps an internal list of fields known to be single-valued, and for those it does not join but keeps only the first value. So when two auth tokens arrive, the string API shows only the first. The second token is out of sight before your code ever runs.

4.1 Why it is dangerous when more than one layer decides

This is dangerous not because the values look strange. It is structural. Picture a shape in which several layers examine one request in turn. The front decides something, then the back examines the same thing and decides again.

  • When a name arrives on two lines, which one is authoritative is settled by the implementation, not by the specification. Both runtimes above happened to take the first, but that cannot be used as evidence that every implementation does
  • If a combination arises where the front believes the first value and the back believes the last, the two layers are judging different targets. Neither raises an error
  • Another combination is a front that joins and passes it on, with a back that treats the whole joined string as one value. The string the back sees is then literally different from the one the front judged
  • This divergence is hard to trace through logs, because each layer's log records only the value that layer picked. Nothing looks wrong until the two logs are placed side by side
  • The response, therefore, is not to pick better. It is to make sure there is nothing to pick — normalise or refuse at the boundary

The practical rule is simple. If a field that determines the target arrived on more than one line, that request is already abnormal. Rather than agonising over which value is right, the outermost boundary should count the lines, refuse or normalise to one if it is not one, and stop the inner layers from deciding again. The moment inner layers are left to decide for themselves, different layers can arrive at different answers.

5. Duplicate Content-Length - here refusal is the right answer

Content-Length decides where the body ends. If that value becomes ambiguous, the boundary of the message itself becomes ambiguous. Differing values and identical values were measured separately.

EXP 5. duplicate Content-Length, measured

 Node.js v22.16.0 http server
  baseline: one Content-Length             -> HTTP/1.1 200 OK    headers['content-length']='5'  headersDistinct=['5']
  two Content-Length, SAME value           -> HTTP/1.1 400 Bad Request
  two Content-Length, DIFFERENT values     -> HTTP/1.1 400 Bad Request
  one Content-Length holding a comma list  -> HTTP/1.1 400 Bad Request

 Python 3.13.3 http.server
  baseline: one Content-Length             -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5']
  two Content-Length, SAME value           -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '5']
  two Content-Length, DIFFERENT values     -> HTTP/1.1 200 OK    get('content-length')='5'      get_all=['5', '7']
  one Content-Length holding a comma list  -> HTTP/1.1 200 OK    get('content-length')='5, 5'   get_all=['5, 5']

 --- node server error log ---
 [clientError] code=HPE_UNEXPECTED_CONTENT_LENGTH msg=Parse Error: Duplicate Content-Length
 [clientError] code=HPE_UNEXPECTED_CONTENT_LENGTH msg=Parse Error: Duplicate Content-Length
 [clientError] code=HPE_INVALID_CONTENT_LENGTH   msg=Parse Error: Invalid character in Content-Length

The two runtimes take opposite stances. In summary:

  • Node refuses even when the values are identical. Two lines of 5 and 5 still produced 400. The stance is not 「no contradiction, so pass」 but 「the duplicate itself is the error」
  • The refusal happens before application code is reached, at the parser stage. The request handler was never called
  • The comma-list-in-one-line case was refused with a different error code. What it objected to was the comma inside the value
  • The Python standard library server passed all four cases, and the common lookup method returned 5. Whether the second value is 7 or 5, the code cannot see any difference
  • So the same request is a 400 on one runtime and a 200 on the other. For this field there is no such thing as 「typical server behaviour」

The specification is clear about commas in the value.

A sender MUST NOT send a Content-Length header field with a field value that contains a comma. (RFC 9110, Section 8.6)

The takeaway is single. A field that defines the body boundary must never quietly resolve to one of several values. That holds even when the values look identical, because confirming that they are identical is itself only possible through the array API. Code using only the string API cannot even tell whether the values agreed. On this field, the strict runtime is the correct one.

6. The shape the runtime hands you - a string arrives too late

Tie the observations together and this comes out. When the runtime decides whether to combine on your behalf, the developer only ever sees a decision already made. Why that decision cannot be undone was proven.

6-B. the proof: a joined string cannot tell you what arrived
 case A: two lines  -> ["aaa-111","bbb-222"]
 case B: one line   -> ["aaa-111, bbb-222"]
 joined A           = "aaa-111, bbb-222"
 joined B           = "aaa-111, bbb-222"
 joinA === joinB    : true
 -> two different wire shapes collapse to the same string.

The case that arrived as two lines and the case that arrived as one line containing a comma produced exactly the same string. Code holding that string has no way to know how many lines came in. The information is not hidden, it is gone. No amount of careful parsing afterwards restores it.

The same trap runs in the opposite direction when the value itself contains a comma.

6-C. a value that legitimately contains a comma
 one line whose value has a comma : ["Wed, 20 Aug 2026 10:00:00 GMT"]
 joined                           : "Wed, 20 Aug 2026 10:00:00 GMT"
 naive split(",")                 : ["Wed","20 Aug 2026 10:00:00 GMT"]
 pieces = 2  from 1 original line(s)

A one-line value became two pieces under a comma split. So splitting on a comma is valid only where the grammar of that field says it is a list. A utility function that applies it to every header goes quietly wrong right here.

6.1 The header object shared by browsers and servers

The web standard header object is used on both sides. What it hands back was checked too.

6-A. WHATWG Headers (the fetch API object)
 h.get("x-trace-id")      = "aaa-111, bbb-222"
   typeof                 = string
 h.get("set-cookie")      = "sid=A1; Path=/, theme=dark; Path=/"
   typeof                 = string
 h.getSetCookie()         = ["sid=A1; Path=/","theme=dark; Path=/"]
   length                 = 2
 [...h.entries()]         = [["set-cookie","sid=A1; Path=/"],["set-cookie","theme=dark; Path=/"],["x-trace-id","aaa-111, bbb-222"]]

The second line is the one that matters. The general lookup method returns a single joined string for the cookie field as well. That is precisely the shape that shattered in section 3. Which is why the object carries a dedicated array accessor for cookies. Skip that accessor and the destruction from section 3 happens intact.

Iterating the entries, by contrast, produced the cookie field as two separate entries. Within one object, the answer depends on which accessor you reach for. That is the point.

7. One hop through a hand-written relay - the API you read decides what the back sees

To show that 「the information disappears」 does not stay inside one process, one more hop is needed. So two twenty-line relays were built. They differ in exactly one thing: the API used to read the headers.

The relay in this section is a minimal implementation written for this article. It does not represent the behaviour of any commercial proxy, load balancer, API gateway, or web server, and it cannot be used as evidence that any of them behaves this way. What is being shown is not product behaviour but a single causal structure: which API a relay reads headers with decides what the back tier sees. How the products you run handle it is something you can measure directly with the method in this article.

=== EXP 7. one hop through a hand-written relay ===
client sends (same bytes in every case):
  > GET /through HTTP/1.1
  > Host: shop.example.test
  > X-Trace-Id: aaa-111
  > X-Trace-Id: bbb-222
  > Accept: text/html
  > Accept: application/json
  > X-Note: first
  > X-Note: second

7-A. NO relay: straight to the origin
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2
   x-note     lines at origin : 2

7-B. relay reading req.headers (the string API)
   origin saw  x-trace-id: aaa-111, bbb-222
   origin saw  accept: text/html, application/json
   origin saw  x-note: first, second
   x-trace-id lines at origin : 1   value="aaa-111, bbb-222"
   x-note     lines at origin : 1   value="first, second"

7-C. relay reading req.rawHeaders (the array API)
   origin saw  X-Trace-Id: aaa-111
   origin saw  X-Trace-Id: bbb-222
   origin saw  X-Note: first
   origin saw  X-Note: second
   x-trace-id lines at origin : 2   value="aaa-111, bbb-222"
   x-note     lines at origin : 2   value="first, second"

Summarised:

  • With no relay, two lines arrive as two lines. That is the original state
  • Through the relay that reads with the string API, two lines arrive as one. The relay did not alter a value. It simply could not forward what it never held — by the time it read, it was already a single string
  • Through the relay that reads with the array API, the line count survives end to end. Same relay, one API apart
  • Note the last two lines of 7-C. At the origin there are two lines, yet asked through the string API it is still one joined value. So even when the front forwards faithfully, the loss can happen again depending on which API the back reads with
  • Which means only when both layers use the array API do the two layers see the same thing. Fixing one side is not enough

Here is one of the central conclusions. When someone says 「our front tier does not touch headers」, they usually mean it does not modify values. But without modifying a single value, the line structure changes purely as a consequence of how it was read. Nobody touched anything and the shape is different. That is the nature of this problem.

8. Design rules - what to combine and what to keep apart

The measurements turned into working rules. Start by sorting fields into three kinds. This classification is where every decision begins.

KindExamplesWhat several lines meanHow to readMay you send several lines
List-basedAccept, Cache-Control, Accept-Encoding, Vary, Viathe list gained memberstake every line as an array, then split each line on commasYes. Same meaning as commas on one line
SingletonHost, Content-Length, Content-Type, Authorization, Locationa state that should not existtake the array, count the lines, refuse or normalise if not 1No. Combining is not the answer either

That classification was turned into code and run against a live request. Below is the result for a request mixing list fields, singletons, and a private header.

8-A. classify every field that actually arrived
 field             lines  class       string API gave

The key is that readSingleton refused instead of returning a value. That is the spot where the string API would have quietly handed back Bearer FIRST. The refusal is the feature. Code should not settle 「which one is right」 on its own; it should hand that back to the caller.

8.1 Three functions that read safely

The implementation used is short. One per kind is enough.

// List-based: take all lines, then flatten each on commas (two steps)
function readList(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  return lines.flatMap(v => v.split(',').map(s => s.trim())).filter(Boolean);
}

// Singleton: refuse rather than return a value unless there is exactly one line
function readSingleton(distinct, name) {
  const lines = distinct[name.toLowerCase()] || [];
  if (lines.length === 0) return { ok: true, value: null };
  if (lines.length > 1)   return { ok: false, reason: 'arrived ' + lines.length + ' times', lines };
  if (lines[0].includes(',')) return { ok: false, reason: 'single line contains a comma', lines };
  return { ok: true, value: lines[0] };
}

// Never combine: keep the array, never make it a string
function readCookies(distinct) {
  return (distinct['set-cookie'] || []).slice();
}

Python has the same shape. Changing the lookup method is the whole job.

# lossy: only the first line arrives
value = headers.get('x-trace-id')

# lossless: every line arrives
lines = headers.get_all('x-trace-id') or []

# list-based fields take two steps
members = [p.strip() for line in lines for p in line.split(',') if p.strip()]

# singletons check the line count first
if len(lines) != 1:
    raise ValueError('singleton field arrived %d times' % len(lines))

8.2 Making the front and back see the same value

As section 7 showed, fixing one side is not enough. In order:

  • Normalise once, at the outermost boundary. If a singleton field arrives on more than one line, refuse or reduce it to one right there. Inner layers must be able to assume they receive something already tidy
  • Do not decide again on the inside. Several layers each interpreting the same field is the source of divergence. Decide in one place only
  • Values used for decisions are always read with the array API. Not to get the value, but to see how many lines arrived alongside it. Without the line count you can neither normalise nor refuse
  • Relay code forwards exactly what it read. Receiving a string and passing a string removes the back tier's options
  • Private headers get their kind written down. With no definition of list versus singleton, every layer interpreting it differently is the expected outcome
  • Log the line count. A log that prints only the value cannot record the fact that two lines arrived at all. Logging the name together with the count makes after-the-fact tracing possible
  • Carry the cookie field as an array to the very end. If any code copies or reassembles responses, check that spot in particular

8.3 Checklist

  • Every place that reads a header has been found and sorted into string API and array API
  • Fields used for decisions — auth, target, body length — have all been moved to the array API
  • A test confirms that a singleton field arriving on two or more lines does not pass silently
  • List fields are read with both the line array and the comma split (doing one only miscounts)
  • No code converts the cookie field to a string. Logs, templates, and response copying were all checked
  • Relay and copy code forwards headers in the shape it read them
  • Private headers have their kind written into a document and both tiers read the same document
  • When a duplicate is detected, the name and the line count reach the log
  • The duplicate handling of every production component has been measured and recorded directly, not taken from docs or guessed
  • Header name case is a separate problem, so that audit was done on its own

# Duplicate Header Decision Guide — Field Type Table and Safe Reads

> Source: braindetox.kr — When the Same Header Arrives Twice
> Verified on: Windows 10 / Node.js v22.16.0 / Python 3.13.3 (bytes written directly over a raw socket)
> Paste this file into an AI and say «audit our header handling against this» to get a concrete review.
> ⚠ The «per-product behaviour» below must be measured in YOUR environment. Do not guess.

## 1. Field type decision table

| Type | Examples | What several lines mean | How to read | May the lines be combined |
|---|---|---|---|---|
| List-based | Accept, Accept-Encoding, Accept-Language, Cache-Control, Vary, Via, TE, Content-Encoding | The list gained members | Take every line as an array, then split each line on commas | Yes (that is the spec) |
| Singleton | Host, Content-Length, Content-Type, Authorization, Location, Date, ETag, Retry-After | A state that should not exist | Take the array, count the lines, refuse if the count is not 1 | No |
| Never combine | Set-Cookie | Normal. There are several items | Use the array-only accessor and keep it an array | Never (combining destroys it) |
| Your own header | X- fields you invented | Whoever defined it must decide | Write the definition down and have both sides read the same one | Whatever you decided |

## 2. Runtime behaviour, measured

| API | Returns | What duplicates become | Verdict |
|---|---|---|---|
| Node req.headers[name] | string | joined with comma+space / singleton fields keep the first value only | lossy |
| Node req.headersDistinct[name] | array | one entry per line | lossless |
| Node req.rawHeaders | flat array | name and value pairs, order and spelling kept | lossless |
| Headers.get(name) | string | joined with comma+space (cookies get joined too) | lossy |
| Headers.getSetCookie() | array | one entry per line | lossless (cookies only) |
| Python headers.get(name) | string | first line only, the rest is discarded | lossy |
| Python headers.get_all(name) | list | one entry per line | lossless |

## 3. Measurement summary

- Same request bytes, two runtimes: one joins the two lines, the other returns only the first. Neither raised an error
- Three list fields (Accept / Cache-Control / Accept-Encoding): two lines = one comma line. Meaning confirmed identical
- Two Set-Cookie lines joined on a comma and split again: 4 pieces (the comma in the expiry date cuts a cookie in half)
- Two simple cookies without an expiry attribute, joined: 1 cookie stored. The second was absorbed as an attribute of the first
- Two Host lines: both runtimes answered 200, the string API gave the first value. Both values survive in the array API
- Two Content-Length lines: one runtime returned 400 at the parser stage even when the values were identical, the other returned 200 in all four cases
- A joined string cannot recover the original line count (two lines and one line with a comma produce the same string)
- One hop through a hand-written relay: reading with the string API turned 2 lines into 1, reading with the array API kept 2

- [ ] Fields used **to make decisions** (auth, target, body length) are all read with the array API

## 7. Do not

- ❌ A utility that splits every header on commas — it will cut a comma that lives inside a value
- ❌ Gluing Set-Cookie into a string — cookies get shredded or vanish entirely
- ❌ Quietly taking the first value of a singleton — it creates room for two layers to see different values
- ❌ Assuming «our front tier does not touch headers» — the line structure changes even when no value does
- ❌ Sorting or de-duplicating a list field — the order of arrival is significant to the interpretation
- ❌ Declaring behaviour from product docs alone — it varies by version and configuration. Measure it
- ❌ Logging only the value — the fact that two lines arrived is never recorded

Frequently asked questions

Why not just block duplicate headers?

You cannot, and there is no reason to. For list fields, several lines is a legitimate representation, and for the cookie field several lines is the norm. Blanket blocking breaks valid requests. What is needed is not a block but different handling per field. The three-way classification in section 8 is where that starts.

Does switching to the array API complicate the code?

You do not have to switch everywhere. Change only the fields used for decisions. For printing to a log or showing on a screen, the string API is fine. But wherever the value drives a branch — authentication, target selection, body length, access control — the line count has to be visible too. In practice these spots are usually few enough to count on one hand.

Is it acceptable to sort the values or drop duplicates?

Not for list fields. RFC 9110 Section 5.3 states that the order in which field lines with the same name are received is significant to the interpretation, and that a proxy must not change that order when forwarding. For fields carrying preference or priority, sorting changes the meaning. Turning the values into a set to remove duplicates is dangerous for the same reason.

Can I trust the behaviour written in the product documentation?

As a starting point, yes; as a conclusion, no. Even within this article, the same request was a 400 on one runtime and a 200 on the other. It also varies with version and configuration. So the recommendation is to reuse the method here directly. Write the bytes over a raw socket and count the lines on the receiving side with the array API. Twenty lines of code will do.

Can I apply these results to my infrastructure as they are?

No. The figures here were measured on the two named runtimes at those specific versions, and they do not represent any other product or version. In particular, the relay in section 7 is a twenty-line implementation written for this article and bears no relation to any commercial product. What transfers is the method and the classification, not the numbers. Run the same measurements against your own components and fill your results into the table in section 8.
