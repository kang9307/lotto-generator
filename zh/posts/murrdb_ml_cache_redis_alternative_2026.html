murrdb - 替代 Redis 的 ML/AI 工作负载亚毫秒缓存 2026

建立在 RocksDB、NVMe 与 S3 之上的零拷贝缓存，重新设计 AI 推理的数据瓶颈

2026年6月15日 开发/基础设施

引言：AI 推理的瓶颈不在模型，而在数据

无论 GPU 多快，只要推理服务器前端无法及时喂入数据，那块昂贵的加速器就会闲置。加载嵌入向量、获取推荐特征、拉取已计算的 LLM KV 张量，这些数据搬运合起来占据了推理延迟相当大的一部分。而我们习惯性塞进这个位置的工具，往往是 Redis，因为十多年来它一直是缓存的默认选项。

2026 年 6 月，在 GeekNews（news.hada.io）引发热议的 murrdb（项目名 Murr，仓库 shuttie/murr）正是对这一习惯发问：「AI 推理工作负载与普通 Web 缓存的数据形态不同，为何还用同一个工具？」murrdb 是一个把 RocksDB 系存储引擎与本地 NVMe、S3 结合起来的列式缓存，主打无需转换地整体收发张量的零拷贝协议与亚毫秒级延迟。

本文从开发者视角解剖 murrdb 的结构：它与 Redis 有何不同，「零拷贝」与「NVMe 分层」实际节省了什么，AI 推理中缓存所承担的负担是如何产生的，以及哪里可以信任、哪里需要谨慎。我们会把来自介绍材料的主张与普遍验证过的原理区分开来。

本文一句话总结。 murrdb 并非说「Redis 错了」，而是从一个观察出发：「AI 推理数据不是单键值，而是大型张量的批次」。列式批量 I/O ＋ 零拷贝 ＋ NVMe/S3 分层，正是其核心——在降低 RAM 成本的同时提升张量传输吞吐。

1. murrdb 概览：用一句话定义

murrdb 把自己描述为「面向 AI 推理的列式内存缓存」。从定位看，它是位于批量数据管道与推理应用之间的缓存层，也就是在模型推理时快速供给所需嵌入、特征与中间张量的那个位置。

核心设计决策可归纳为三点。第一，它以列（column）而非行（row）为单位处理数据。ML 数据通常是「同类型数字组成的长数组」，列式布局更利于压缩、传输与计算。第二，分层存储把热数据放内存、冷数据放本地 NVMe、持久状态放 S3。第三，零拷贝传输协议直接从网络响应构建 NumPy 数组、Pandas DataFrame 与 PyTorch 张量，无需转换。

它由 Rust 实现，以 Apache 2.0 开源，Python 客户端通过 pip install murrdb 安装。据介绍，节点采用状态存放于 S3 的无状态设计，重启时从块存储自举恢复。

2. 为何要替代 Redis：AI 推理缓存的特殊性

Redis 是出色的工具，但它的强项闪光之处在于「小值、高频、快」的场景。AI 推理缓存的数据在多个方面偏离了这个前提。

2.1 数据并不小

LLM 的 KV 缓存单个分块从数百 KB 到数十 MB 不等。例如 8B 级模型，一次 1 万 token 的请求就可能产生超过 1 GB 的 KV 数据。嵌入表、排序特征矩阵同样庞大。若把这些全部常驻 RAM，内存成本会陡然上升。

2.2 是批量而非单键

推理通常一次读取数百到数千个键（例如待排序的 1000 篇文档的特征）。在 Redis 以单键为中心的模型里，即便做流水线，序列化与反序列化的开销也会累积。murrdb 把列式批量读写当作一等公民，甚至把通过 API 整体灌入一个 1 GB 的 Parquet 文件都视为正常场景。

2.3 最终都要变成张量

从缓存取出的字节，最终都要成为 NumPy 数组或张量。普通缓存返回序列化后的字节，应用再解析、复制成张量。对大型数据而言，这一转换成本不可忽视。murrdb 的零拷贝目标正是跳过这一步。

核心洞见很简单：AI 推理缓存的工作负载不是「小值 × 大量请求」，而是「大张量 × 批量传输」。当工具的数据模型与工作负载的数据形态错位时，无论怎么调优，结构性开销都会残留。

3. 零拷贝：去掉复制后什么变快了

「零拷贝（zero-copy）」是一种把网络收到的字节原样使用、无需额外内存复制与反序列化的技术。在 murrdb 语境下，它意味着把收到的字节缓冲区直接映射到 np.ndarray 或 pt.Tensor 的内存。

为什么重要？传统路径通常是：① 网络缓冲区 → ② 反序列化（解析 JSON/Protobuf）→ ③ 分配新对象内存 → ④ 复制数值。若数据有数十 MB，仅这复制与解析就会堆叠 CPU 周期与时间，在 Python 中还会叠加 GC 压力。零拷贝实质上省去了 ②~④，因此张量越大，效果越显著。

为此，murrdb 被介绍为利用列式内存格式（Apache Arrow 系）以及 Arrow IPC、Arrow Flight（gRPC）等传输路径。Arrow 的内存布局本身跨语言通用，使收到的数据可原样解释为张量。这正是「收到即张量」这一图景得以成立的基础。

4. NVMe 分层与 S3：如何不烧 RAM

第二条主线是存储分层。murrdb 不把所有数据放进 RAM，而是按访问频率分层。

  • 热（hot）数据：当前频繁使用的张量放在内存，最快但最贵的一层。
  • 冷（cold）数据：一段时间未用的数据下沉到本地 NVMe SSD，比 RAM 便宜得多，而如今的 NVMe 可提供个位数到数十微秒级的随机读取。
  • 持久（durable）层：真正的状态放在 S3。把对象存储当作「新的文件系统」，即便节点宕机，数据仍留在 S3，新节点从那里恢复自身。

这种结构的实际收益很明确：同样预算下能缓存大得多的数据集；而且 S3 成为单一可信来源，跨节点复制协调的复杂度随之降低。像 RocksDB 这样的嵌入式 LSM 引擎正擅长这类基于磁盘的分层与压缩，因此 murrdb 以该系为基础运营冷层是自然的选择。这也与「把缓存与可信来源分离」的通用原则相通，相同脉络的分析在 Shopify 为何把库存从 Redis 迁到 MySQL 一文中也有探讨。

5. 缓存在 AI 推理中的角色：KV 缓存、嵌入、特征

要理解 murrdb 瞄准的位置，需要看清缓存在 AI 推理中具体做什么。大体有三类。

5.1 KV 缓存卸载

LLM 每生成一个 token，都会计算该 token 的键（Key）、值（Value）张量。当相同的提示前缀重复出现时，可复用这些 KV 以避免重复计算，但麻烦在于其体量会迅速吞噬 GPU 显存。于是把 KV 移到 GPU 之外（CPU RAM、本地磁盘、远程存储）的「KV 缓存卸载」十分活跃。这里重要的是尾延迟（所有分块到齐推理才能继续）与 GB/s 吞吐，因此擅长大型张量批量传输的缓存更具优势。

5.2 嵌入缓存

检索、推荐与 RAG 会反复使用同一文档、条目、查询的嵌入向量。与其每次重跑编码器，不如把嵌入缓存起来，能节省可观成本。嵌入是固定维度的 float 数组，与列式存储天然契合。

5.3 特征缓存

推荐与排序模型在推理时会大批量获取用户、条目特征。传统特征存储路径常因序列化与网络往返的累积而变慢。在 murrdb 介绍的基准里（1000 篇文档 × 10 列 float32、1000 万行规模的排序工作负载），Murr 展现约 104µs 的延迟，并声称「相比最优 Redis 布局约快 2.5 倍，相比 Feast 式存储约快 36 倍」，正是在这一特征服务环节。

请谨慎阅读。 上述数值来自 murrdb 介绍材料中的特定工作负载。基准高度依赖数据形态、硬件与访问模式，因此在你用自己的工作负载复现之前，宜将其视为「特定条件下的上限」。

7. 应用场景

那么，哪里值得一试？整理一下 murrdb 设计可能闪光的具体场景。

  • 推荐/检索排序的特征服务：一次请求读取数百到数千条目的特征并喂给模型的路径。批量、列式、零拷贝恰好契合。
  • 嵌入缓存层：在 RAG、语义检索中把反复出现的嵌入向量，不烧光 RAM 地大规模保存在 NVMe 层。
  • LLM KV 缓存后端：把移出 GPU 的 KV 分块以高吞吐存储并再供给的卸载后端候选。
  • 批量管道 ↔ 在线推理的桥梁：把离线产出的大型 Parquet 成果原样灌入并在在线侧快速服务的桥梁。

8. 局限与风险：冷静看待

前景之外，把新兴基础设施放上关键路径时，必须诚实地核算成本。

8.1 成熟度与生态

Redis 积累了十多年的运维经验、客户端、托管服务与监控工具，层层叠叠。murrdb 这层厚度尚薄。故障处理、可观测性、HA 运维模式是否经过充分验证，需要你亲自确认。

8.2 通用性的代价

专注 ML 意味着通用命令、数据结构与事务语义可能不如 Redis 丰富。想用一个缓存搞定一切的冲动，反而可能成为毒药。

8.3 依赖 S3/NVMe 的运维现实

把 S3 当持久层，就要按其特性设计成本、延迟与一致性模型。若冷数据被频繁调用，NVMe/S3 的往返可能放大尾延迟，因此热/冷边界设定与缓存命中率管理将左右性能。

8.4 基准的陷阱

如前所强调，亮眼的倍数是特定工作负载的产物。对像嵌入这种「经零拷贝即成张量」的数据有利，但对随机猛敲大量小键的模式，优势会缩水。

9. 开发者视角：上线前检查清单

若真要评估，建议先问这些问题。

  1. 我的缓存数据真的是「大型张量批次」吗？若以小键值为主，murrdb 的优势就小。这种分类感在 UUID 主键与 SQLite 性能 这类「数据形态决定性能」的案例中也能印证。
  2. 访问模式是批量、列式的吗？若一次请求成批读取多个键，契合度更高。
  3. 能否把零拷贝路径用到底？客户端要以 Arrow/NumPy/张量直接消费才见效，中途再复制优势便消失。
  4. 能否承担 S3/NVMe 运维？需要成本、延迟、命中率的监控体系。
  5. 是否在关键路径前做了隔离验证？替换处理持久数据的基础设施，验证就是一切。

这种「替换存储时的谨慎」不仅适用于缓存，也同样适用于工作流的持久化。相关地，用 PostgreSQL 构建持久化工作流 的讨论也值得一并阅读。

10. murrdb 抛出的更大问题

抛开 murrdb 自身的成败，它所触及的趋势很清晰：AI 工作负载正在改写基础设施的默认选项。曾经是「缓存 = Redis」「队列 = Redis」「特征存储 = 通用数据库」，如今针对工作负载数据形态而定制的专用层正在各处涌现。

这也与同期整个业界的动向相互印证。面向 KV 缓存卸载的专用库、面向 S3 与 NFS 的缓存数据平面、基于 RDMA 的张量传输，这些尝试都指向同一个问题：如何让 AI 推理的数据搬运更便宜、更快？murrdb 等于是对这个问题给出了「列式 ＋ 零拷贝 ＋ 分层」的一种答案。

11. 结论 ＋ 三条可立即应用

murrdb 并不是把 Redis 塑造成「错误工具」的项目。它具体展示了：在 AI 推理缓存这种特殊工作负载下，让工具贴合数据形态（大型张量、批量、列式）会带来什么变化。它前景可观但仍属新兴，亮眼数字是特定条件的产物——把这两点一并记住即可。

以三条今天就能用的建议收尾。

  1. 按「形态」重新分类缓存数据。是小键值还是大型张量批次，决定了最优工具。若是后者，列式、零拷贝缓存值得评估。
  2. 用分层重新审视 RAM 成本。并非所有缓存数据都要在 RAM。把冷数据下沉到 NVMe、把持久性交给 S3 的设计，能用同样预算造出更大的缓存。
  3. 新兴基础设施先隔离验证再引入。用自己的工作负载复现基准，在关键路径之前用影子流量验证，再加大其比重。

下次在推理服务器前塞入缓存时，反射性地敲下 Redis 之前，不妨先问一句：「我的数据是小值，还是大张量？」这个答案会先替你选定工具。

常见问题（FAQ）

Q1. murrdb 是什么？

它是面向 AI/ML 推理的列式内存缓存。采用热数据在内存、冷数据在 NVMe、持久状态在 S3 的分层结构，并提供无需转换直接构建张量的零拷贝协议。由 Rust 实现，以 Apache 2.0 开源。

Q2. murrdb 为何主打替代 Redis？

Redis 将所有数据放在 RAM，缓存大体量嵌入与 KV 时成本陡升，且以单键为中心使张量批量传输开销大。murrdb 把冷数据下沉到 NVMe/S3，并以列式批量零拷贝快速处理大量张量。

Q3. 零拷贝与 NVMe 缓存意味着什么？

零拷贝把收到的字节无需额外复制与解析地直接映射为数组/张量，减少 CPU 复制与 GC 压力。NVMe 缓存是把冷数据放本地 SSD 而非昂贵 RAM 的分层，使同样成本下缓存更大数据。

Q4. 在 AI 推理中缓存扮演什么角色？

主要是 LLM 的 KV 缓存卸载、嵌入向量缓存，以及推荐与排序的特征缓存。它们都要以低尾延迟、高吞吐收发大型张量，因此擅长批量、列式传输的缓存更具优势。

Q5. murrdb 现在可以用于生产吗？

在专门场景（张量批量服务、特征缓存）颇有前景，但因其新兴，兼容性、成熟度与生态可能有限。在关键路径上线前，宜用自己的工作负载复现并验证基准。
