LeafWiki - 서버·DB 없이 단일 바이너리로 띄우는 셀프호스팅 위키

MediaWiki·Wiki.js·DokuWiki·Confluence와 비교해 본 가벼운 위키의 장점과 트레이드오프

2026-07-18 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 왜 지금 다시 '가벼운 위키'인가

지난 몇 년간 지식관리 도구 시장은 두 극단으로 갈라졌다. 한쪽은 Notion·Confluence로 대표되는 '모든 것을 담는' SaaS 올인원이고, 다른 쪽은 Obsidian·Logseq로 대표되는 로컬 우선 개인 노트다. 정작 '여러 사람이 함께 쓰지만 무겁지는 않은 위키'라는, 원래 '위키'라는 단어가 가리키던 중간지대는 오히려 선택지가 줄었다. MediaWiki는 위키피디아를 굴리도록 설계된 스택을 소규모 팀에 욱여넣는 격이고, Confluence는 구독료와 함께 문서까지 벤더 서버에 맡기는 선택이다.

이 틈에서 LeafWiki 같은 프로젝트가 등장했다. 개발자 perber가 만든 이 오픈소스 위키는 2026년 7월 기준 GitHub 스타 837개, 최신 릴리스 v0.11.4까지 나왔고, 스스로를 "단일 Go 바이너리, SQLite, 디스크에 저장되는 마크다운"이라는 한 문장으로 요약한다. 이 글은 GeekNews(hada.io)에 소개된 LeafWiki를 출발점 삼아, 셀프호스팅 위키 생태계 전체를 놓고 무엇이 실제로 달라졌고 무엇이 여전히 트레이드오프인지 짚어본다. 사실관계는 2026년 7월 18일 기준 LeafWiki 공식 사이트·GitHub·GitHub API 데이터를 근거로 한다.

1. LeafWiki란 무엇인가 - 단일 바이너리로 도는 위키

1.1 핵심 사양과 기술 스택

LeafWiki의 백엔드는 Go(저장소 언어 비중 약 60.8%)로 작성됐고, 프론트엔드는 React+Vite 기반 TypeScript(약 35.4%)로 짜여 있다. 상태 저장에는 내장형 SQLite를 쓰지만, 실제 문서 콘텐츠는 일반 마크다운 파일로 디스크에 그대로 저장된다. 즉 LeafWiki 앱이 꺼져 있어도 grep이나 텍스트 에디터로 문서를 읽을 수 있다 - "앱 없이도 콘텐츠는 살아남는다"는 설계가 이 프로젝트의 핵심 철학이다. 기능 목록도 짧지 않다. 트리 기반 폴더 내비게이션, 전문(full-text) 검색과 태그 필터, 백링크와 깨진 링크 추적, 실시간 분할화면 마크다운 에디터, [[위키링크]] 자동완성, 다크모드, Mermaid 다이어그램과 KaTeX 수식(단 인라인 수식 $...$은 아직 미지원, 블록 수식만 가능)을 기본 제공한다. 리비전 히스토리와 페이지 이름 변경 시 링크 자동 리팩토링은 --enable-revision, --enable-link-refactor 플래그로 켜는 옵션 기능이고, v0.11.3부터는 실험적으로 Git 백업도 지원한다.

1.2 설치와 배포 - 도커 한 줄, 바이너리 하나

설치 경로는 세 가지다. 도커 한 줄(포트·데이터 볼륨·관리자 비밀번호만 지정), 리눅스/라즈베리파이OS용 설치 스크립트(curl로 받아 실행), Linux·Windows·macOS용 바이너리 직접 다운로드다. 데모는 demo.leafwiki.com에서 바로 체험할 수 있고, 라이선스는 MIT다. 접근 제어는 로그인 필수·공개 읽기+로그인 편집·인증 비활성화의 3단계이고, 권한은 admin·editor·viewer 역할 기반으로 나뉜다. 흥미로운 점은 2026년 9월부터 10자리 한정 무료 호스팅 베타를 예고했다는 것이다. 완전 셀프호스팅 도구가 관리형 옵션까지 실험하는 모습은, "셀프호스팅이냐 SaaS냐"가 더 이상 이분법이 아니라는 신호로 읽힌다.

2. 셀프호스팅 위키 수요가 다시 뜨는 이유

2.1 팀 지식관리와 개인 노트의 재부상

Notion은 팀 규모가 커질수록 비용이 좌석 단위로 불어나고, Obsidian은 애초에 팀 협업을 1급 시나리오로 설계하지 않았다. 이 공백을 메우려는 시도가 최근 다시 늘고 있는데, LeafWiki 외에도 브레인디톡스가 다룬 Chatto(셀프호스팅 팀 채팅)나 Odysseus(셀프호스팅 AI 워크스페이스) 같은 도구들이 비슷한 시기에 잇따라 등장한 것은 우연이 아니라고 본다. '여러 사람이 함께 쓰지만 운영은 가벼운' 도구에 대한 수요가 노트·채팅·위키 전반에서 동시에 올라오고 있다.

2.2 AI 시대의 역설 - 검색·요약할 지식은 내가 갖고 있어야 한다

역설적으로 AI 도구가 일상화될수록 '내 지식을 어디에 둘 것인가'라는 질문은 더 무거워졌다. 로컬 LLM이나 RAG(검색 증강 생성)로 자신의 문서를 검색·요약·질의하려는 개발자가 늘면서, 문서가 평문 마크다운으로 디스크에 있는지 아니면 SaaS의 폐쇄된 API 뒤에 있는지가 'AI 파이프라인에 얼마나 쉽게 연결할 수 있는가'를 좌우하게 됐다. LeafWiki처럼 콘텐츠가 그냥 .md 파일인 도구는 grep은 물론 로컬 임베딩 인덱싱, 개인 RAG 파이프라인에 곧바로 물릴 수 있다. 이는 단순한 복고 취향이 아니라 AI 활용이라는 실용적 이유에서 오는 회귀에 가깝다.

3. 기존 위키의 무게 - MediaWiki·Wiki.js·DokuWiki·Confluence

3.1 MediaWiki - 위키피디아 엔진이라는 오버킬

MediaWiki는 PHP와 MySQL/MariaDB 위에서 도는, 세계에서 가장 유명한 위키 엔진이다. 위키피디아를 실제로 떠받치는 소프트웨어라는 사실 자체가 신뢰의 증거지만, 동시에 신뢰의 대가이기도 하다. 웹서버, PHP 런타임, 별도 DB 서버, 확장(extension) 관리까지 챙겨야 하는 스택은 수백만 문서·수천 동시접속을 감당하도록 설계된 것이지, 팀 8명이 쓰는 런북용이 아니다. 소규모 팀이 MediaWiki를 들이면 대개 설치 자체보다 확장 생태계와 권한 모델을 이해하는 데 더 많은 시간을 쓴다.

3.2 Wiki.js - 모던하지만 무겁고, 최근 둔화된 개발

Wiki.js는 Node.js와 Vue.js, PostgreSQL(또는 다른 RDB) 조합으로 만들어진 비교적 최신 위키다. 마크다운·WYSIWYG·HTML 등 여러 에디터를 지원하고 Git 동기화까지 가능해 한동안 'DokuWiki의 현대적 대안'으로 꼽혔다. 다만 Node 런타임과 SQL 데이터베이스를 별도로 운영해야 한다는 점에서 무게는 MediaWiki보다 가벼울 뿐 여전히 여러 구성요소로 이뤄진 스택이고, 2026년 상반기 들어 핵심 저장소의 커밋 빈도가 눈에 띄게 줄었다는 관찰도 나온다. 채택을 고려한다면 짚어볼 만한 유지보수 리스크다.

3.3 DokuWiki - 가장 가까운 선배, 그러나 PHP는 여전히 필요하다

DokuWiki는 사실 LeafWiki의 철학적 원조에 가깝다. 20년 가까이 별도 DB 없이 페이지를 평문 파일로 저장해 왔고, '백업은 곧 디렉토리 복사'라는 단순함으로 오래 사랑받았다. 그러나 DokuWiki도 PHP 런타임과 웹서버(Apache/Nginx)는 필요하다 - 런타임 설치가 필요 없는 진짜 단일 바이너리는 아니라는 뜻이다. UI도 20년 묵은 만큼 클래식하다. LeafWiki는 DokuWiki의 'DB 없음' 철학을 계승하면서, PHP·웹서버 설치 단계 자체를 Go 바이너리 하나로 더 압축한 다음 세대로 볼 수 있다.

3.4 Confluence - SaaS의 편리함과 맞바꾸는 데이터 주권

Atlassian Confluence는 클라우드형과 데이터센터형을 함께 파는 상용 위키다. 설치 부담은 사실상 없고(가입하면 끝) 승인 워크플로, 세분화된 권한, Jira 연동 같은 엔터프라이즈 기능이 강력하다. 대가는 구독료와, 클라우드형을 쓰는 한 문서가 벤더 서버에 상주한다는 점이다. 소규모 팀·개인, 그리고 정부·의료처럼 데이터 반출에 민감한 조직에는 이 지점이 곧 진입장벽이 된다.

4. '단일 바이너리' 접근이 실제로 주는 것

4.1 배포가 파일 하나 옮기는 일이 된다는 것

전통적인 웹앱 배포는 런타임 설치(Node·PHP·Python 등), 의존성 관리(패키지 매니저·버전 충돌), DB 프로비저닝, 리버스 프록시 설정까지 여러 단계를 거친다. Go로 컴파일된 단일 바이너리는 이 단계 대부분을 컴파일 타임으로 밀어 넣는다. 실행 시점에 필요한 것은 바이너리 파일 하나와 데이터 디렉토리뿐이다. LeafWiki의 도커 실행 명령이 한 줄로 끝나고 설치 스크립트가 curl 한 번으로 끝나는 것도 이 덕분이다. 서버 운영 경험이 적은 1인 팀이나 사이드 프로젝트에는 이 차이가 '해볼까 말까'를 가르는 실제 진입장벽 차이로 작동한다.

4.2 의존성 제로와 이식성 - 라즈베리파이부터 에어갭까지

Go는 크로스 컴파일이 쉬운 언어라 같은 소스에서 Linux·Windows·macOS·ARM(라즈베리파이 포함) 바이너리를 모두 뽑아낼 수 있다. LeafWiki가 실제로 Raspberry Pi OS 설치 스크립트를 공식 제공하는 것은 이 이식성을 실전에서 쓰고 있다는 뜻이다. 인터넷이 차단된 에어갭 환경에서도 바이너리 파일 하나만 옮기면 실행할 수 있다는 점은, 외부 패키지 저장소 접근이 막힌 폐쇄망 조직(제조 현장·연구소 등)에서 특히 매력적이다. 이는 LeafWiki만의 이야기는 아니고 Go·Rust 계열 도구 전반의 공통 강점이지만, 위키라는 카테고리에서는 아직 흔치 않다.

4.3 백업이 디렉토리 복사인 이유

LeafWiki는 SQLite로 메타데이터(구조·권한·태그)를 관리하되 문서 본문은 평문 마크다운으로 저장한다. 결과적으로 백업은 데이터 디렉토리 전체를 복사하는 것으로 끝난다. 별도 mysqldump나 DB 익스포트 스텝이 필요 없다. v0.11.3부터 실험적으로 지원되는 Git 백업 기능은 여기서 한 걸음 더 나아가, 문서 변경 이력 자체를 Git 커밋으로 남길 수 있게 한다. DokuWiki가 20년간 증명해온 '백업은 곧 복사'라는 단순함을, LeafWiki는 Git이라는 익숙한 도구까지 얹어 계승한다.

5. 트레이드오프 - 확장성·동시편집·플러그인 생태계

5.1 확장성의 한계

LeafWiki 공식 문서 스스로도 엔터프라이즈급 권한 관리나 Confluence·Notion 규모의 요구사항에는 적합하지 않다고 명시한다. SQLite는 훌륭한 임베디드 DB지만 대규모 동시 쓰기나 수만 페이지 규모에서 검증된 사례는 아직 많지 않다. MediaWiki가 20년간 축적한 대규모 운영 노하우와 비교하면, LeafWiki는 아직 실전 검증 초기 단계(v0.x, 별 837개)에 가깝다.

5.2 실시간 동시편집의 부재

공식적으로 실시간 협업 편집(real-time collaborative editing)은 지원 대상이 아니라고 밝힌다. 자동 저장과 충돌 감지는 있지만, 이는 구글독스·Notion류의 동시 커서 편집과는 다르다. 여러 사람이 동시에 같은 문서를 고치는 팀이라면 이 지점에서 막힐 수 있다.

5.3 플러그인 생태계가 없다는 것

MediaWiki에는 수천 개의 익스텐션이 있고 Wiki.js도 여러 렌더러·인증 모듈을 지원한다. LeafWiki는 반대로 '코어 기능만 잘한다'는 미니멀리즘을 택했다. 확장 포인트가 거의 없다는 것은 유지보수 부담이 적다는 뜻인 동시에, 특정 워크플로(SSO 연동, 커스텀 승인 프로세스 등)가 필요한 조직에는 선택지가 되기 어렵다는 뜻이기도 하다.

6. 어떤 팀·용도에 맞는가

6.1 잘 맞는 경우

개인 지식베이스·엔지니어링 노트, 5~30명 규모 팀의 내부 런북·운영 매뉴얼, 이미 마크다운이나 Obsidian으로 쌓아온 자산을 구조화하려는 경우에 잘 맞는다. 저전력 엣지 장비(라즈베리파이 등)나 인터넷이 끊긴 에어갭 환경 - 설치 스크립트 하나와 바이너리 하나로 오프라인 배포가 쉽다는 점은 이런 환경에서 특히 유효하다.

6.2 신중해야 할 경우

승인 워크플로가 필요한 규제 산업 문서, 수백 명이 동시에 넘나드는 대규모 조직 위키, 실시간 공동편집이 업무 방식 자체인 팀, 수년간 검증된 성숙도가 필수인 미션크리티컬 문서라면 아직은 MediaWiki·Confluence 같은 검증된 도구를 유지하는 편이 안전하다.

7. 셀프호스팅 vs SaaS 위키 - 데이터 주권과 비용

셀프호스팅과 SaaS 위키의 선택은 결국 '누가 무엇을 책임지는가'의 문제로 귀결된다. SaaS(Confluence·Notion 등)는 가용성·백업·보안 패치를 벤더가 책임지는 대신, 문서가 벤더 서버에 상주하고 비용이 좌석 수에 비례해 늘어난다. 규제 산업이나 데이터 반출을 꺼리는 조직, 혹은 단순히 '내 문서가 어디 있는지 내가 알고 싶은' 개인·소규모 팀에는 이 구조가 부담이다. 셀프호스팅은 반대로 데이터가 자신이 통제하는 인프라를 벗어나지 않고 비용도 서버 임대료 수준으로 평평하게 유지되지만, 가용성·백업·보안은 전적으로 운영자 책임이 된다. LeafWiki처럼 단일 바이너리로 도는 도구는 이 '운영자 책임'의 실제 부담을 크게 낮춘다는 점에서, 셀프호스팅을 이전보다 훨씬 현실적인 선택지로 만든다. 다만 프라이버시가 공짜는 아니다 - 백업을 실제로 주기적으로 돌리고 서버 보안 패치를 챙기고 장애 시 복구할 사람은 여전히 필요하다.

8. 마크다운 기반 문서 도구 트렌드와 LeafWiki의 위치

브레인디톡스가 다뤄온 최근 흐름들을 나란히 놓아 보면 패턴이 보인다. Files.md·Logseq·Excalidraw를 둘러싼 Obsidian 생태계 갈등 분석은 '노트 자산을 오픈 포맷으로 지킬 것인가'라는 질문이었고, Odysseus 셀프호스팅 AI 워크스페이스 분석은 AI 워크스페이스 자체를 로컬에 두려는 시도였으며, Chatto 셀프호스팅 팀 채팅 분석은 같은 문제의식을 팀 채팅에 적용한 사례였다. LeafWiki는 이 흐름을 위키라는, 어쩌면 가장 오래되고 무거웠던 카테고리에 적용한다. 공통분모는 명확하다 - 콘텐츠는 평문·마크다운·오픈 포맷으로, 실행은 최소 의존성으로. 이 조합이 노트 앱을 넘어 팀 채팅, AI 워크스페이스, 이제 위키까지 번지는 것은 단발성 유행이 아니라 로컬 우선(local-first) 소프트웨어라는 더 큰 흐름의 한 갈래로 보는 것이 맞다.

결론: 누가 오늘 LeafWiki를 써야 하는가

LeafWiki는 "위키가 이렇게까지 무거워야 하나"라는 실무 좌절에서 나온, 정직한 범위의 도구다. 개인 지식베이스, 5~30명 팀의 런북, 이미 마크다운 자산이 쌓여 있는 조직, 저전력·에어갭 환경에는 지금 당장도 매력적인 선택지다. 반대로 실시간 공동편집이 필수이거나 승인 워크플로·세분화된 권한이 필요한 조직, 수년간 검증된 성숙도가 요구되는 미션크리티컬 문서에는 아직 이르다 - MediaWiki나 Confluence 같은 검증된 도구를 유지하는 편이 안전하다. 별 837개, v0.11.4라는 숫자가 말해주듯 LeafWiki는 아직 1.0 이전 프로젝트다. 그러나 '단일 바이너리 + 평문 마크다운'이라는 조합이 DokuWiki 이후 위키 카테고리에 제시된 가장 설득력 있는 다음 세대 답 중 하나라는 점은 분명해 보인다. 2026년 7월 기준, 데이터를 내 손에 쥐고 싶은 소규모 팀이라면 데모(demo.leafwiki.com)에서 짧게 테스트해봐도 이 도구가 자신에게 맞는지 판단할 수 있을 것이다.
