検証した後に値を変えると検証は無効になる - 正規化と検証の順序

検査した値と実際に使う値が違えば、その検査は最初から無かったのと同じである

2026-08-01 開発・インフラ

はじめに: 検査は通ったのに、入ってきた値が違う

ログを見ていて妙な値に気づく。保存された名前に改行が混じっていたり、開けてはいけない形の文字列がファイルパスの位置に座っていたりする。コードを開くと入力検査は確かにある。正規表現も細かく、禁止文字のリストも長い。検査を飛ばす分岐も無い。それでも値が入っている。

こういうとき多くの対応は 検査規則をもっと細かくすること になる。正規表現に文字を足し、リストを伸ばし、例外ケースを付け足す。ところが数日後に似た値がまた入ってくる。規則をいくら直しても再発するなら、問題は規則ではない。

この記事が扱うのはただ一つ、検査器が判定した文字列とプログラムが実際に使った文字列が別物である場合 だ。この状況で検査器には何の落ち度もない。自分が受け取った値について正確に答えている。ただしその答えが最終的な値についての答えではなかった、というだけである。

だからこの記事の主張は「検証しましょう」ではない。検証はすでにある。重要なのは 何を検証したか だ。そしてその「何」を決めるのは規則ではなく 順序 である。

実行環境. 以下の出力はすべて Windows 10 Pro (10.0.19045) で実際に実行した結果である。ランタイムは Node.js v22.16.0 (win32) で、一部の結果は Python 3.13.3 で交差確認した。スクリプトはすべてファイルに保存してから実行している。

この記事がしないこと. ここには 攻撃手順も侵入方法も無い。 例はすべて無害な文字と、基準ディレクトリの内側に留まるパスだけを使う。示したいのは「こう破る」ではなく 「この順序では検査が無意味になる」 という構造一つである。だからパスの節を含め、すべての例は 検査時点の値と使用時点の値が違う という事実までしか見せない。

この記事が扱わないこと. 同じ文字がユニコードの中で複数のコードポイント列になる原理は NFC と NFD で扱った。ここでは正規化を 配置の問題 としてのみ見る。ウェブ入力処理の全般は ウェブセキュリティ基礎 にある。許可リストと禁止リストのどちらを使うか、検証をどの層に置くかはこの記事の主題ではない。この記事は 順序 の一点だけに留まる。

1. 同じ検査器、順序を変えただけなのに

まず最も多い形から再現する。禁止文字の検査を先にして、通過した値を後でデコードする順序だ。このコードを読んでも何も問題が無いように見える。検査が前にあり使用が後にあるので順序は合っているように見える。実際に何が起きるかを 検査時点の値と使用時点の値を並べて 出力した。

node v22.16.0 / win32
--- 1-1. ORDER A: validate first, decode afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a%3Cb           PASS      a<b             NO
note%3Bnext     note%3Bnext     PASS      note;next       NO
x%26y           x%26y           PASS      x&y             NO
line%0Asecond   line%0Asecond   PASS      line\nsecond    NO
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-2. ORDER B: decode first, validate afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a<b             REJECT    (never used)    -
note%3Bnext     note;next       REJECT    (never used)    -
x%26y           x&y             REJECT    (never used)    -
line%0Asecond   line\nsecond    REJECT    (never used)    -
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-3. the gap, counted ---
order A  passed check but dirty at use : 4 of 6
order B  passed check but dirty at use : 0 of 6
the checker function is identical in both runs. only the order changed.

表の二列目と四列目を比べるのが、この記事全体を通じた要領である。順序 A で a%3Cb は検査時点では a%3Cb だった。この文字列には禁止文字が一つも無い。検査器は正直に通過判定を出した。ところが使用時点の値は a<b である。検査器はこの文字列を見たことがない。

  • 六つの入力のうち四つがこの経路を通った。 通過判定を受けた後、最終値で禁止文字が現れた
  • 最後の行だけが正常だ。 エンコードされていない plain<bad> は検査時点でも禁止文字を持っていたので拒否された。つまりこの検査器は 目に見える形だけ を捕まえる
  • 順序 B では通過後の汚染がゼロ件である。 検査器の関数は二回の実行で一文字も違わない
  • 改行の行が特に重要だ。line%0Asecond はログやヘッダのように 行単位で意味が決まる場所 に入ると値一つが二行になる
  • この欠陥は 検査器を直しても消えない。 規則をいくら増やしても検査器が見るのは依然としてエンコードされた文字列だ

1.1 検査器は自分が無意味になったことを知り得ない

この構造の悪いところは 誰もエラーに遭遇しない ことだ。例外は出ず、ログに警告も残らず、検査器は自分の仕事を正確にやったと報告する。統合テストを回しても通過する。テストが入れる値はたいていすでにデコードされた普通の文字列なので、両方の順序で同じ結果になるからだ。

つまりこれは テストで捕まりにくくレビューでも捕まりにくい 種類の欠陥である。レビュアーが見るのは「検査がある」と「使用がある」であり、その二つの順序まで疑うには 間に挟まった行が値を変える という事実を先に知っている必要がある。

2. ユニコード正規化 - 検査の後に置くと判定がひっくり返る

二つ目の経路はユニコード正規化だ。前節のデコードよりずっと静かである。デコードは少なくとも % という目立つ痕跡を残すが、正規化は すでに正常に見える文字列 を別の文字列に変える。一度通すと何が起きるかをまず見た。

node v22.16.0 / win32
--- 2-1. one NFKC pass changes the string itself ---
before      len  after NFKC  len  codepoints after
--------------------------------------------------------------------------
report      6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
ｒｅｐｏｒｔ 6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
a／b        3    a/b         3    U+0061 U+002F U+0062
ﬁle         3    file        4    U+0066 U+0069 U+006C U+0065
①           1    1           1    U+0031
㎡          1    m2          2    U+006D U+0032
ｎｏ＜op    5    no<op       5    U+006E U+006F U+003C U+006F U+0070

注目すべきは 長さが変わる行 である。ﬁle は 3 文字だったのが正規化後に 4 文字になり、㎡ は 1 文字から 2 文字になった。長さ制限の検査を正規化の前に置くと 制限を通過した値が制限を超えた状態で保存される。

そして最後の二行がこの節の核心だ。全角文字で書いた値が正規化を経て 半角スラッシュと半角不等号 になった。検査時点には存在しなかった文字が使用時点で生まれたのである。判定が実際にどうひっくり返るかを二つの方式で確認した。

--- 2-2. allowlist verdict before vs after normalization ---
input       allow(before)  allow(after)  flipped?
--------------------------------------------------------
report      true           true          no
ｒｅｐｏｒｔ false          true          YES
a／b        false          false         no
ﬁle         false          true          YES
①           false          true          YES
㎡          false          true          YES
ｎｏ＜op    false          false         no

--- 2-3. denylist verdict before vs after normalization ---
input       deny hit(before)  deny hit(after)  flipped?
------------------------------------------------------------
report      false             false            no
ｒｅｐｏｒｔ false             false            no
a／b        false             true             YES
ﬁle         false             false            no
①           false             false            no
㎡          false             false            no
ｎｏ＜op    false             true             YES

二つの表が 正反対の方向に間違える ことが重要だ。

  • 許可リストでは正常な値が拒否される。 全角で入力した ｒｅｐｏｒｔ は正規化後に完全に有効な report になるのに、正規化の前に検査すると拒否される。利用者から見れば「まともな名前を受け付けてくれない」というバグだ
  • 禁止リストでは弾くべき値が通る。 正規化の前には禁止文字が無く、正規化の後に生まれる
  • どちらの場合も 検査器自体は正確である。 間違っているのは検査器ではなく検査器に渡した値だ
  • 実務では前者の誤りが先に見つかる。利用者が抗議するからだ。後者の誤りは誰も抗議しないので長く残る
  • この二つの表は 同じ原因の二つの顔 である。片方だけ直すともう片方が残る

2.1 冪等なら前に移してよい

では正規化はいつやるべきか。答えは「一番前」なのだが、そう言い切れる根拠がある。正規化は何回回しても結果が同じだから だ。これを冪等と呼ぶ。実際に三回続けて回してみた。

--- 2-4. NFKC is idempotent, so doing it FIRST is safe ---
report      n1==n2 true   n2==n3 true
ｒｅｐｏｒｔ n1==n2 true   n2==n3 true
a／b        n1==n2 true   n2==n3 true
ﬁle         n1==n2 true   n2==n3 true
①           n1==n2 true   n2==n3 true
㎡          n1==n2 true   n2==n3 true
ｎｏ＜op    n1==n2 true   n2==n3 true
a normalizer you can run twice with no change can always be moved to the front.

--- 2-5. NFC vs NFKC are not the same job ---
input       NFC         NFKC        NFC==NFKC
--------------------------------------------------
ｒｅｐｏｒｔ ｒｅｐｏｒｔ report      false
ﬁle         ﬁle         file        false
㎡          ㎡          m2          false
á          á           á           true

2-4 の意味は単純だ。正規化を前に移しても 失うものが無い。 後ろのどこかでまた正規化が起きても値はそれ以上変わらないので安全である。これが「正規化を先に」という規則が危険なく成立する理由だ。

2-5 は罠を一つ見せている。NFC と NFKC は別の仕事をする。 最後の行のアクセント文字は両方が同じ結果を出したが、その上の三行はすべて違う。全角を半角に変えたり合字をほどいたりするのは NFKC だけの仕事だ。だから「正規化している」という言葉だけでは どの正規化か分からない。 原理そのものが気になるなら NFC と NFD を見てほしい。ここで必要な結論は一つだ。どの形式を使うか決め、それを文書に書き、すべての層に同じものを使わせる。

3. 空白と大文字小文字 - 最も多く最も見えにくい食い違い

前の二節は特殊な文字が登場する話なのでまだ疑いやすい。この節はそうではない。trim と小文字化はあまりに平凡で、誰もこれを「値を変える演算」として認識しない。 予約語リストの検査を例に取り、順序を変えて回した。

node v22.16.0 / win32
--- 3-1. ORDER A: check the raw value, canonicalize when storing ---
requested       value AT CHECK  reserved?  value STORED  stored value reserved?
--------------------------------------------------------------------------------
[alice]         [alice]         false      [alice]       no
[admin]         [admin]         true       [(rejected)]  -
[Admin]         [Admin]         false      [admin]       YES  <- mismatch
[ admin]        [ admin]        false      [admin]       YES  <- mismatch
[ADMIN ]        [ADMIN ]        false      [admin]       YES  <- mismatch
[  support  ]   [  support  ]   false      [support]     YES  <- mismatch
[billing\t]     [billing\t]     false      [billing]     YES  <- mismatch

--- 3-2. ORDER B: canonicalize first, then check ---
requested       value AT CHECK  reserved?  value STORED  stored value reserved?
--------------------------------------------------------------------------------
[alice]         [alice]         false      [alice]       no
[admin]         [admin]         true       [(rejected)]  -
[Admin]         [admin]         true       [(rejected)]  -
[ admin]        [admin]         true       [(rejected)]  -
[ADMIN ]        [admin]         true       [(rejected)]  -
[  support  ]   [support]       true       [(rejected)]  -
[billing\t]     [billing]       true       [(rejected)]  -

順序 A では予約語リストが ちょうど一つの綴りにだけ 反応した。前後に空白が付いたり大文字が一つ混じったりするとリストをすり抜ける。ところが保存されるときにはそれらの値がすべて同じ形に整えられるので、リストにある名前がリストを通過した状態で保存 される。順序 B では同じリスト、同じ入力ですべて弾かれた。

3.1 一意性検査と保存キーが分かれるとき

同じ欠陥がはるかに静かに現れる形がある。重複検査だ。ここではセキュリティ問題というより データ整合性の問題 として現れる。

--- 3-3. uniqueness checked on one value, stored as another ---
order A: unique-check on raw, store canonical
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? false  stored [alice@example.com]
  [ALICE@EXAMPLE.COM]     dup at check? false  stored [alice@example.com]
  distinct values checked : 3
  distinct values stored  : 1   <- three rows collapsed into one key
order B: canonicalize first, then unique-check
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? true   rejected
  [ALICE@EXAMPLE.COM]     dup at check? true   rejected

順序 A は 三回とも「重複ではない」と答えた。 検査時点の三つの文字列は互いに違うのだからその答えは正しい。ところが保存キーに変えると三つが同じ値になる。だから互いに異なる三つのリクエストが 同じキー一つ をめぐって重なる。例外は出ない。後で「同じアドレスでアカウントが二つある」とか「先に作ったものが消えた」という報告として現れる。

3.2 trim は一つの規則ではなく一つのリストである

trim が何を消すのかを実際に確認すると考えと違う。空白に見える文字が全部消えるわけではない。

--- 3-4. what exactly trim removes, and what it does not ---
input codepoints          trim() result     length change
------------------------------------------------------------
U+0061 U+0020 U+0062      3 -> 3            untouched
U+0020 U+0061             2 -> 1            trimmed
U+0061 U+00A0             2 -> 1            trimmed
U+0061 U+200B             2 -> 2            untouched
U+0061 U+FEFF             2 -> 1            trimmed
U+0061 U+3000             2 -> 1            trimmed
U+00A0 and U+3000 are removed, U+200B and U+FEFF are not.
so trim is not one rule. it is one specific list, and it must run before the check.

--- 3-5. lowercase is locale sensitive ---
input U+0130            : İ
toLowerCase()           : U+0069 U+0307
toLocaleLowerCase(tr)   : U+0069
length after each       : 2 vs 1
two layers using different locales produce two different canonical values.
  • 改行なし空白と全角空白は消える。 目に見えないので保存された値を目で見ても分からない
  • 幅ゼロ空白は消えない。 空白に見えるがこの関数のリストに無い。この文字が付いた値は別の値として扱われる
  • つまり trim は「空白を消す」ではなく 「特定のリストの文字を消す」 である。そのリストが何かを知らなければ何が通るかも分からない
  • 3-5 はもっと微妙だ。小文字化の結果がロケールによって違う。 ある文字は片方で二文字になり、もう片方で一文字になる
  • 層ごとに違うロケールを使うと 同じ入力に対して層ごとに違う正規形 が生まれる。これは 7 節で改めて扱う
  • 結論は同じだ。これらの変換はすべて 値を変える演算 であり、値を変える演算は検査の前にあるべきである

4. パス結合 - 合わせた瞬間に文字列が書き直される

パスはこの問題が最もよく知られている領域だ。だからむしろ 見せないものから明確にしておく。 以下の例はすべて基準ディレクトリの内側に留まる正常なパスである。脱出の事例も成功した迂回も無い。ここで示したいのはただ一つ、結合という作業が文字列を書き直す という事実だ。

node v22.16.0 / win32
--- 4-1. the string the checker saw vs the string join produced ---
user segment          joined result                   identical tail?
------------------------------------------------------------------------
q1.csv                /srv/data/reports/q1.csv        true
sub//q1.csv           /srv/data/reports/sub/q1.csv    false
./q1.csv              /srv/data/reports/q1.csv        false
sub/./q1.csv          /srv/data/reports/sub/q1.csv    false
sub/inner/../q1.csv   /srv/data/reports/sub/q1.csv    false
sub/                  /srv/data/reports/sub/          true
a/b/../../q1.csv      /srv/data/reports/q1.csv        false
every row above stays inside the base directory. only the SPELLING changed.

--- 4-2. what join collapsed, step by step ---
q1.csv                unchanged
sub//q1.csv           duplicate separator collapsed
./q1.csv              current-dir segment dropped
sub/./q1.csv          current-dir segment dropped
sub/inner/../q1.csv   current-dir segment dropped, parent segment resolved
sub/                  trailing separator dropped
a/b/../../q1.csv      current-dir segment dropped, parent segment resolved

七つの入力のうち五つが 単純な連結とは違う結果 を出した。何が変わったかは 4-2 に並んでいる。重複した区切りが一つにまとまり、カレントディレクトリの表記が消え、上位移動の表記が解消され、末尾の区切りが落ちる。公式文書も結合関数が結果を整えると明示している。

  • この整理は選択肢ではない。 結合関数を使う以上つねに起きる
  • したがって利用者入力の断片を検査してから結合すると、検査した文字列はディスクに触れる文字列ではない
  • すべての例が基準の内側に留まった点が重要だ。食い違いは危険な入力でのみ生じるものではない
  • 正常な入力でも値が変わるということは、この食い違いが 平常時に常時存在する という意味である

4.1 層ごとに区切りの意味が違う

同じ断片を二つのパス方式で結合すると結果が分かれる。

--- 4-3. same segment on the windows path flavour ---
user segment          posix.join                    win32.join
----------------------------------------------------------------------------
q1.csv                /srv/data/reports/q1.csv      C:\srv\reports\q1.csv
sub/q1.csv            /srv/data/reports/sub/q1.csv  C:\srv\reports\sub\q1.csv
sub\q1.csv            /srv/data/reports/sub\q1.csv  C:\srv\reports\sub\q1.csv
sub//q1.csv           /srv/data/reports/sub/q1.csv  C:\srv\reports\sub\q1.csv
a forward slash is an ordinary character to posix.join but a separator to win32.join.
so one segment has two different meanings depending on which layer joins it.

三行目を見てほしい。逆スラッシュを含む断片を、片方は 普通の文字 として残し、もう片方は 区切り として解釈した。同じ文字列が層によって違う構造に読まれるという意味だ。開発は一方の方式で、運用はもう一方の方式で回る構成なら、開発で通過した検査が運用では違う値を判定 することになる。

4.2 綴りについての問いとファイルについての問い

ここからが核心だ。同じ「このパスは基準の内側にあるか」という問いを二つの値に対して投げてみた。

--- 4-4. the containment test, run on the two different values ---
user segment          test on RAW   test on RESOLVED  same answer?
----------------------------------------------------------------------
q1.csv                true          true              true
sub//q1.csv           true          true              true
./q1.csv              true          true              true
sub/./q1.csv          true          true              true
sub/inner/../q1.csv   false         true              false
sub/                  true          true              true
a/b/../../q1.csv      false         true              false
the RAW column answers a question about spelling.
the RESOLVED column answers a question about the file that will actually be opened.
only the second question is the one the program cares about.

--- 4-5. resolve is idempotent, so it belongs in front of the check ---
q1.csv                r1 == r2 : true
sub//q1.csv           r1 == r2 : true
./q1.csv              r1 == r2 : true
sub/./q1.csv          r1 == r2 : true
sub/inner/../q1.csv   r1 == r2 : true
sub/                  r1 == r2 : true
a/b/../../q1.csv      r1 == r2 : true

二つの列で答えが食い違った行が二つある。そして 食い違った方向が興味深い。 元の綴りを見る検査はこの二つのパスを拒否したが、最終的なパスはきちんと基準の内側にあった。つまりこの例で綴りの検査は 正常なファイルを開けなくした。

これが順序の問題を理解するよい角度だ。綴りを検査することとファイルを検査することは別の問い であり、プログラムが関心を持つのは二番目の問いだけである。一番目の問いの答えは二番目の問いの答えを どちらの方向にも ずらす。4-5 は解決が簡単であることを示している。結合と整理は冪等なので 検証の前に移しても何も失わない。

5. デコードは冪等ではない

ここまでに出てきた正規化ステップはすべて冪等だった。だから「前に移せばよい」という処方が通った。ところが一つのステップは違う。パーセントデコードだ。何回回すかによって結果が変わり続ける。

node v22.16.0 / win32
--- 5-1. one decode, two decodes, three decodes ---
raw           after 1       after 2       after 3
----------------------------------------------------------------
a%3Cb         a<b           a<b           a<b
a%253Cb       a%3Cb         a<b           a<b
a%25253Cb     a%253Cb       a%3Cb         a<b
100%25        100%          URIError: URI malformed URIError: URI malformed
a%2520b       a%20b         a b           a b
plain         plain         plain         plain

--- 5-2. decoding is NOT idempotent ---
a%3Cb         d1 == d2 : true
a%253Cb       d1 == d2 : false   a second layer changes the value again
a%25253Cb     d1 == d2 : false   a second layer changes the value again
100%25        d1 == d2 : false   a second layer changes the value again
a%2520b       d1 == d2 : false   a second layer changes the value again
plain         d1 == d2 : true
a step you cannot repeat safely cannot be moved around freely.
it must happen exactly once, at a place both sides agree on.

四行目が特に重要だ。100%25 は一回デコードすると 100% になるが、これをまたデコードすると 例外が出る。 パーセント記号で終わる文字列は有効なエンコードではないからだ。つまり二回デコードする構造では 正常な値がエラーで死ぬ場合 まで生じる。

5.1 層ごとに自分のデコーダを持っている

なぜ二回デコードが起きるのかが問題だ。誰も二回デコードしようと決めていない。各層が自分の場所で 一回ずつ やるだけである。

--- 5-3. the same string through two different decoders ---
raw           decodeURIComponent    URLSearchParams     same?
----------------------------------------------------------------
a+b           a+b                   a b                 false
a%20b         a b                   a b                 true
a%2Bb         a+b                   a+b                 true
a%3Cb         a<b                   a<b                 true
the plus sign is where the two disagree. one layer sees a space, the other a plus.

--- 5-4. a value that survives a check and then changes at the next layer ---
raw           layer1 out    deny at L1?  layer2 out    deny at L2?
----------------------------------------------------------------------
a%253Cb       a%3Cb         false        a<b           true
a%2526b       a%26b         false        a&b           true
a%3Bb         a;b           true         (rejected)    -
ok-value      ok-value      false        ok-value      false
layer 1 checked the value layer 1 had. layer 2 uses a different string.

--- 5-5. counting decodes across a chain ---
start value : a%25253Cb
gateway     a%25253Cb      -> a%253Cb       (changed)
router      a%253Cb        -> a%3Cb         (changed)
handler     a%3Cb          -> a<b           (changed)
three layers each doing their own decode is three decodes, not one.
nobody wrote that down anywhere. it is the sum of three local decisions.
  • 5-3 は 同じ名前の作業が道具によって違う ことを示している。プラス記号を片方は空白に変え、もう片方はそのまま残す
  • だから「デコードを一回した」という記述だけでは 結果の文字列が何かは決まらない
  • 5-4 は 1 節の構造が層の間でも同じように再現されることを示す。1 層が検査した値と 2 層が使う値が違う
  • 5-5 では三つの層がそれぞれ一回ずつデコードして結果的に三回デコードされた。この決定を下した人はいない。 三つの局所的判断が合わさった結果である
  • 標準もこの点を明確にしている。URL 標準はパースの過程で パーセントデコードを一回 行い、反復デコードを規定していない
  • したがってデコードは ちょうど一回、合意された位置で 起きなければならない。「念のためもう一回」はここでは防御ではない

7. 正規化は境界で一度だけ

順序を直したら終わりではない。二つ目の規則が要る。正規化をする場所が一箇所でなければならない。 そうしないと層ごとに違う値が存在することになる。四つの層がそれぞれ「もっともらしい」整理を一つずつする構成を作り、値を追跡した。

7.1 層ごとに検査すれば層ごとに違う答えが出る

値が層ごとに違えば検査結果も層ごとに違う。同じ禁止文字の検査を四つの層でそれぞれ回してみた。

four checks, four different answers, all of them honest about their own layer.

--- 7-3. normalize once at the boundary, then nobody else touches it ---
[ Ｒeport%2Ename ]  final [report.name]    distinct values downstream of the boundary : 1
[q1.csv]            final [q1.csv]         distinct values downstream of the boundary : 1

7-2 で四つの答えが出て すべて正しい。 各層は自分が持っている文字列について正確に答えた。ところがシステム全体で見ると「このリクエストは通過か」という問いに答えが一つに定まらない。これが散らばった正規化の本当のコストだ。判定が位置の関数になる。

7-3 は処方を示している。境界で一度だけ正規化して下の層が手を触れなければ、三つの入力すべてが境界より下で値が一つだった。7-4 はその境界関数自体に付く警告だ。デコードを含む境界関数は 二回回すと結果が変わる。 だから「境界で一度」は推奨ではなく 必須条件 になる。

7.2 静かな版 - キャッシュが分かれる

この欠陥がセキュリティ問題として現れないときは、性能問題として現れる。

--- 7-5. cache keys computed at two layers ---
key hashed at layer 1 : dcd41471
key hashed at layer 3 : 845e9183
same request, same user, two cache entries : true
a split cache is the quiet version of this bug. nothing errors, the hit rate just drops.
  • 同じリクエストなのに 層ごとに違うキャッシュキー が作られた。項目が二つできてヒット率が下がる
  • エラーが出ないので 監視には引っかからない。 指標には「キャッシュ効率が思ったより低い」としか見えない
  • 同じ原理が ログ集計 にも当てはまる。同じ対象が二つの名前で集計されると統計が分かれる
  • レート制限や重複防止の仕掛けも キーが分かれると無力になる
  • だからキャッシュキーもログキーも保存キーも、すべて 境界から出たその値 で作らなければならない

8. コードの中でこの順序を見つける方法

診断は消費地点から始めるのが最も確実だ。ファイルを開く行や問い合わせを組み立てる行や外部を呼ぶ行をまず探し、そこに入る変数を 上へ遡る。 検証呼び出しに出会ったらその間のすべての行を読む。値を変える行が一つでもあれば欠陥である。

この作業のかなりの部分は機械的だ。サンプルモジュールを対象にテキスト検索だけで走査してみた。

node v22.16.0 / win32

----------------------------------------------------------

this second pattern is the one code review misses. the checked variable is still
untouched, so the diff looks fine. a different variable is what reaches the sink.
  • 一つ目の形は 検証した変数へ再代入する ものだ。比較的目に付く
  • 二つ目の形のほうがずっと危ない。検証した変数はそのままにして派生変数を作り そちらを使う
  • 二つ目の形では差分が正常に見える。検証もあり、検証した変数は触っていない。レビューはここを素通りする
  • 検索語はコードベースに合わせて決めればよい。検証関数の名前リストと 値を変える関数の名前リスト の二つで十分だ
  • 値を変えるリストにはデコード、正規化、空白除去、大文字小文字変換、置換、パス結合を入れる
  • 完璧である必要はない。候補リストを作って人が読むこと が目的である

8.1 実行時のトリップワイヤー

静的な検索で確信が持てなければ、実行中に確かめる方法がある。検査器が受け取った文字列を記録しておき、消費地点で同じかを比べる ことだ。

--- 8-3. runtime tripwire: does the sink receive the value the checker approved? ---
order A under the tripwire:
  A0    checked [report]        used [report]       match
  A1    checked [a%3Cb]         used [a<b]          MISMATCH
  A2    checked [note%0Aline]   used [note\nline]   MISMATCH
  A3    checked [q1.csv]        used [q1.csv]       match
order B under the tripwire:
  B0    checked [report]        used [report]       match
  B1    rejected at check
  B2    rejected at check
  B3    checked [q1.csv]        used [q1.csv]       match

the tripwire is a few lines and it turns an invisible ordering bug into a failing test.

この仕掛けの値打ちは 見えなかった欠陥を失敗するテストに変える ところにある。順序 A では二件の不一致が捕まり、順序 B ではゼロ件だった。開発環境でだけ有効にして、不一致が出たら即座に失敗させればよい。

8.2 ステップの性質を先に確かめる

どのステップをどこに置くかは そのステップが冪等かどうか で決まる。これは直接確かめられる。

--- 8-4. property check: normalize is a fixed point, decode is not ---
step                  idempotent on all probes?   safe to run at more than one layer?
------------------------------------------------------------------------------------
trim                  true                        yes
toLowerCase           true                        yes
NFKC                  true                        yes
decodeURIComponent    false                       NO - must run exactly once

--- 8-5. the checklist, as executable assertions ---
[ ]  static scan finds no mutation after a check             FAIL
[ ]  static scan finds no derived variable after a check     FAIL
[ ]  runtime tripwire reports zero mismatches                FAIL
[x]  every mutation step used at 2+ layers is idempotent     pass
the sample module fails the first three. that is the point of running it on your own code.

8-4 の検査は数行で済む。標本の文字列いくつかについて 二回適用した結果が一回適用した結果と同じか を見れば終わりだ。同じなら複数の層にあっても無害で、違うならちょうど一回だけ実行されなければならない。

8-5 は点検リストを実行可能な形に変えたものだ。サンプルモジュールは三項目で失敗した。このリストを自分のコードに回してみることがこの節の要点 である。文書として読む点検リストは守られにくいが、失敗する検査は直される。

9. 点検リストとしてはいけないこと

ここまでの内容を実務でそのまま使える形にまとめる。

点検項目確認方法失敗の兆候
正規化関数が一つに定まっている名前を検索して定義が一つか見る層ごとに似た関数が別々にある
正規化関数が冪等である標本に二回適用して比較デコードが関数の中に入っている
デコードが一箇所でだけ起きるデコード呼び出しを全数検索ゲートウェイとハンドラの両方にある
検証関数が最終的な値を受け取る検証の引数と消費地点の引数を対照二つの引数が別の変数である
検証と使用の間が空であるその間の行をすべて読む代入や加工が一行でもある
パスは整理の後に判定する包含検査が最終パスに掛かっているか見る元の断片に対して記号を探している
一意性と保存キーが同じ値である重複検査の引数と保存キーを比較片方だけ正規化されている
ロケールが固定されている大文字小文字変換の呼び出しを検索ロケール指定なしで呼んでいる
  • ❌ 検証を「追加した」で終わらせること。 どの値を検証したかが本質である
  • ❌ 層ごとに防御的にもう一度整えること。 層ごとに違う値が生まれ、判定が位置の関数になる
  • ❌ デコードを複数箇所で行うこと。 何回デコードされるか誰も分からなくなり、正常な値がエラーで死ぬこともある
  • ❌ パス文字列の綴りで包含関係を判定すること。 正常なパスまで一緒に拒否される
  • ❌ 正規化を「どうせ後でやるから」と先送りすること。 その間に挟まった検証が丸ごと無効になる
  • ❌ 一意性は原文で検査し保存は正規形で行うこと。 キーが静かに衝突しエラーは出ない
  • ❌ 長さ制限を正規化の前に置くこと。 正規化が長さを変えるので制限が最終的な値に適用されない
  • ❌ 「フレームワークがやってくれる」で済ませること。 フレームワークがどこで何をするかを確認しなければ、それも層の一つに過ぎない

おわりに: 何を検証したのか

入力検証についての助言はたいてい「検証せよ」で終わる。ところがこの記事で見た失敗はすべて 検証がすでにあるコード から出てきた。検査器は正確で、規則は細かく、分岐にも漏れが無かった。それでも最終的な値はその規則を通過したことが一度も無かった。

だから問うべき問いは「検証したか」ではなく 「何を検証したか」 である。そしてこの問いの答えはコードの順序が決める。検証した値と実際に使う値が違えば、検証はあってもなくても同じなのではなく 最初から無かったのと同じ である。

実行で確かめたことを一行に縮めるとこうなる。正規化を先に、検証を後に、そしてその間に何も挟まない。 正規化ステップの大半は冪等なので前に移しても失うものが無く、冪等でないステップは境界でちょうど一回だけ実行する。そうすれば検査器が見た値がそのままプログラムの使う値になり、その後は何が起きても検証を無効にできない。

# 正規化が先、検証が後 — 順序点検用コピペカード

> 出典: braindetox.kr — 検証した後に値を変えると検証は無効になる
> 根拠: Windows 10 / Node.js 22.16.0 / Python 3.13.3 での実行検証

## 0. 一行のルール

正規化 → 検証 → 使用。そして **検証と使用の間に何も挟まない。**

検証器が見た値と実際に使う値が同じでなければならない。この等式が崩れた時点で、検証は最初から無かったのと同じになる。

```
atCheck === atUse
```

## 1. 順序が逆になっているかの見分け方

以下のどれか一つでも当てはまれば順序の欠陥である。

- [ ] 検査を通過した後に、その変数へ再代入する行がある
- [ ] 検査を通過した後に、その変数から **新しい変数** を作り、そちらを使っている
- [ ] 検証器に渡した引数と、最終的な消費地点に渡した引数が文字列として一致しない
- [ ] デコード・正規化・トリム・小文字化・パス結合のいずれかが検査の後にある
- [ ] 層ごとに独自の判断で値を整えている (ゲートウェイ・サービス・ストレージ)

## 2. 誤った順序と正しい順序

### 誤り — 検査の後に値を変える

```js
function handle(req) {
  let name = req.query.name;
  if (!isAllowed(name)) return reject();   // 検査した値: エンコード済みの原文
  name = decodeURIComponent(name);         // ここで値が変わる
  return open(name);                       // 使う値: デコード結果
}
```

### 誤り — 検査の後に派生変数を作る (レビューが見落とす形)

```js
function handle(req) {
  const label = req.body.label;
  if (!isAllowed(label)) return reject();  // label 自体は無傷
  const key = label.trim().toLowerCase();  // 検証器が見たことのない値
  return store(key);
}
```

### 正しい — 境界で一度だけ正規化し、その値を検証し、その値を使う

```js
function normalize(s) {
  let out = String(s == null ? '' : s);
  try { out = decodeURIComponent(out); } catch (e) { /* 原文のまま */ }
  return out.normalize('NFKC').trim().toLowerCase();
}

function handle(req) {
  const name = normalize(req.query.name);  // 正規化
  if (!isAllowed(name)) return reject();   // 検証
  return open(name);                       // 使用 — 同じ変数、再加工なし
}
```

## 3. 正規化ステップごとの性質

| ステップ | 冪等か | 複数の層で実行してよいか | 配置 |
| --- | --- | --- | --- |
| trim | はい | はい | 境界 |
| toLowerCase | はい | はい (ロケール固定が必要) | 境界 |
| NFKC | はい | はい | 境界 |
| パーセントデコード | **いいえ** | **いいえ** | 境界でちょうど一回 |
| パス結合・整理 | はい | はい | 検証の直前 |

冪等でないステップは **ちょうど一回だけ** 実行されなければならず、その位置を文書に書き残す必要がある。

## 4. 層への配置の原則

- 境界は一つである。リクエストが入る最初の地点でのみ正規化する
- 境界より下のすべての層は、値を **最終形とみなして** 手を触れない
- 層ごとに正規化すると層ごとに値が変わり、層ごとに検査結果も変わる
- キャッシュキー・ログキー・保存キーはすべて **境界が生んだその値** から作る

## 5. 点検リスト

- [ ] 正規化関数が存在し、名前が一つに定まっている
- [ ] 正規化関数は二回実行しても結果が同じである (デコードを除く)
- [ ] デコードは境界で一回だけ起きる
- [ ] 検証関数は正規化済みの値を引数に受け取る
- [ ] 検証と使用の間に代入や加工がない
- [ ] 検証した変数と使用した変数が **同じ変数** である
- [ ] パスは結合・整理の後に包含関係を判定する (綴りで判定しない)
- [ ] 一意性検査と保存キーが同じ値を使う
- [ ] ロケール依存の変換はロケールを明示している
- [ ] テストに「検証器が受けた値 == 消費地点が受けた値」という表明がある

## 6. 診断手順

1. 消費地点 (ファイルを開く・問い合わせる・外部呼び出し) をまず探す
2. そこに入る変数を上へ遡る
3. その経路上に検証呼び出しがあるか見る
4. あれば **検証呼び出しと消費地点の間のすべての行** を読む
5. その間に値を変える行が一つでもあれば欠陥である
6. 確信が持てなければランタイムのトリップワイヤーを付ける — 検証器が受け取った文字列を記録し、消費地点で同じか比べる

## 7. してはいけないこと

- ❌ 検証を「追加した」で終わらせること — どの値を検証したかが本質である
- ❌ 層ごとに防御的にもう一度整えること — 層ごとに違う値が生まれる
- ❌ デコードを複数箇所で行うこと — 何回デコードされるか誰も分からなくなる
- ❌ パス文字列の綴りで包含関係を判定すること — 正常なパスまで拒否される
- ❌ 正規化を「どうせ後でやるから」と先送りすること — その間の検証が無効になる
- ❌ 一意性は原文で検査し保存は正規化形で行うこと — キーが静かに衝突する
