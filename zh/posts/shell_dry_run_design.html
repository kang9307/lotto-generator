如何做出真正的 --dry-run - 要验证而不是模仿

用真实输出复现五类假 dry-run，再用三次一致的计划哈希给出证明

2026年7月29日 开发/基础设施

引言：dry-run 承诺的事，执行却做不到

给清理脚本加上 --dry-run。跑一遍输出了十二行 would delete，列表也和预期一致。于是放心地真正执行，结果中途报错，目录里有的文件没了、有的还在。dry-run 明明说了要做什么，执行却做不到。

这件事之所以特别糟糕，不在于答案错了，而在于跑 dry-run 的人在这中间安心了。要是完全没做任何验证，他会小心翼翼地执行；正因为相信自己已经确认过，才一路推了下去。错误的验证比没有验证更危险。这就是假 dry-run 的根本危害。

底下压着一个流传很广的误解：「dry-run 就是把要执行的命令打印出来而已」。不是。打印只是产物。dry-run 要想有价值，就必须走与真实执行相同的判断路径：评估同样的条件、通过同样的检查、按同样的顺序选出目标，只是最后一步「写入」不做。这最后一步放在哪里，决定了它是验证还是模仿。

本文不从定义讲起，而是从在临时目录里实际复现的五类假 dry-run 输出开始，一路讲到怎么修。顺序是：先逐个击破五类，再构造 plan 与 apply 分离的形态并用三次运行的哈希证明其确定性；接着整理退出码约定与 CI 接线；最后为 git clean -n、rsync -n 这类现成工具的 dry-run 划一条可信边界。

先把范围收窄。「跑两次结果是否一样」不是本文的主题。那一面写在跑两次也安全的脚本里。本文只问一个问题：「能否在运行之前就知道结果。」两种性质互相帮衬，但并不是同一件事。一个完全幂等的脚本，照样可以配一个说谎的 dry-run。

1. 运行环境与验证方式

本文所有结论都来自真实运行的输出。复现环境如下。

  • 操作系统：Windows 10 Pro 10.0.19045 上的 MSYS2 系 Unix 环境（Git Bash）
  • Shell：GNU bash 5.2.37(1)-release (x86_64-pc-msys)
  • 工具：GNU coreutils 8.32、GNU tar 1.35、GNU Awk 5.0.0、git 2.48.1
  • 工作位置：一个临时目录，每个实验单独建子目录隔离

用 MSYS2 而非 Linux 发行版只是因为手边就是它，而这里呈现的行为几乎都来自shell 语法与 POSIX 工具语义，换个环境同样成立。以下两项属于环境相关，因此没有纳入。

  • 由文件权限与属主引发的失败 —— 该环境并未完整模拟 POSIX 权限位，复现不可信
  • rsync 的真实行为 —— 该环境没有安装，无法运行。第 11 节只引用官方文档写明的边界，并改用 git 复现同一类分歧
⚠ 警告 —— 本文示例仅限临时目录。
正文出现了 rm、sed -i、git clean -f 等不可撤销的命令。它们全部在新建的临时目录内执行，也不是为指向其他位置而写的。若您要自行验证，请新建一个空的临时目录并只在其中运行，不要在真实服务器路径或家目录下执行。尤其是 git clean 系列会不可恢复地删除未被跟踪的文件。

2. 第一类：只打印，不判断

最常见的写法。在每个执行点用 if 分开：dry 时打印一句话，否则真的去调用。

clean() {
  for f in "$@"; do
    if [ -n "${DRY:-}" ]; then
      echo "would delete $f"
    else
      rm "$f"
    fi
  done
}

目标目录里创建 a.log 和 c.log，故意不创建 ghost.log，三个一起作为参数传入。

### 目标目录状态
a.log
c.log

### DRY=1（假 dry-run）
would delete a.log
would delete ghost.log
would delete c.log
exit=0

### 真实执行
rm: cannot remove 'ghost.log': No such file or directory
exit=0

### 执行后剩下的
（无）

dry-run 声称要删除一个根本不存在的文件。原因很简单：echo 那条路径从未询问文件是否存在，而 rm 会真正查找目标。两条路径本来就在回答不同的问题。

  • dry-run 回答的问题：「循环里进来了哪些参数」
  • 真实执行回答的问题：「这些参数指向的对象此刻是否存在且可删除」

换句话说，这个 dry-run 展示的是参数列表的复述，而不是执行结果的预测。列表正确与执行会成功是两个完全不同的命题，但 would ... 的措辞会把人引向后者。

输出里还藏着一点。真实执行同样返回了退出码 0，尽管 ghost.log 上报了错。循环里最后一条 rm c.log 成功了，而函数的退出状态取自最后执行的命令。这个问题第 6 节单独讲。

修复方向不是「把检查复制到 dry 那一侧」，而是只计算一次判断，让两种模式共享这份结果。复制一份就有了两套条件语句，下一个人只会改其中一套。

3. 第二类：条件只存在于执行路径上

被第一类坑过的人通常会加检查。可一旦检查落在执行分支内部，情况反而更糟：dry-run 看起来更像回事，却依旧不准。

for f in src/*.dat; do
  base=${f#src/}
  if [ -n "${DRY:-}" ]; then
    echo "would archive $base"
    continue                 # ← 这里跳过了后面所有检查
  fi
  # ↓ 下面两个检查只存在于执行路径
  if ! mkdir "$LOCK" 2>/dev/null; then
    echo "ERROR: another run holds $LOCK" >&2; exit 3
  fi
  size=$(wc -c < "$f")
  if [ $((used + size)) -gt "$QUOTA" ]; then
    echo "ERROR: quota exceeded at $base (used=$used +$size > $QUOTA)" >&2
    rmdir "$LOCK"; exit 4
  fi
  cp "$f" "dst/$base"
  ...
done

把五个 200 字节的文件放进总量上限为 500 字节的目标。

### DRY=1 —— 报告五件全部可行
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0

### 真实执行 —— 相同输入，相同顺序
archived f1.dat (used=200)
archived f2.dat (used=400)
ERROR: quota exceeded at f3.dat (used=400 +200 > 500)
exit=4

### dst 的实际结果
dst/f1.dat
dst/f2.dat

dry-run 承诺五件，实际停在第二件，还留下了部分应用的状态。锁也一样。在另一个实例已持有锁的情况下再跑一次：

### 锁已被持有时（另有实例在运行）
-- DRY=1 --
would archive f1.dat
would archive f2.dat
would archive f3.dat
would archive f4.dat
would archive f5.dat
exit=0
-- 真实 --
ERROR: another run holds .archive.lock
exit=3

dry-run 甚至没能告诉你这个脚本此刻根本无法启动，因为锁检查位于执行路径之内。实务中这类条件比想象中常见。

  • 磁盘剩余空间、inode、配额 —— 很容易写成写入前才检查
  • 并发锁 —— 「只有真的要做事才需要加锁」这种想法会把它推进执行分支
  • 目标服务的健康检查 —— dry 路径通常不会特意接上
  • 凭证与令牌有效性 —— dry-run 不连远端就发现不了过期
  • 累积状态 —— 如上例，处理完前面的条目才能定下后面的判定

结论很清楚：决定可行性的检查应该在执行分支之前，而不是之内。把锁与配额检查提升为循环之外的预检，两种模式就会通过同样的关卡。第 8 节的 plan 结构正是把这一点变成强制。

4. 第三类：dry-run 留下副作用

一个名为「什么都不改」的模式却在创建和删除文件，那这个名字就是谎言。可这多半不是粗心，而是从 shell 的求值顺序中自然长出来的事故。下面这个脚本只用 dry 模式跑。

WORK=$(mktemp -d "./tmp.XXXXXX")     # ① 与模式无关，必然创建
mkdir -p logs                         # ② 同样
exec 3>> logs/run.log                 # ③ 文件不存在就在这里生成
echo "start $$" >&3

collect() {                           # ④ 重定向在分支之外求值
  if [ -z "${DRY:-}" ]; then
    printf 'row-%s\n' 1 2 3
  else
    echo "would write 3 rows" >&2
  fi
} > report.csv

collect
### 执行前状态
./report.csv
./report.sh
--- report.csv 内容 ---
old-report-do-not-lose-me

### 仅以 DRY=1 执行
would write 3 rows
exit=0

### 执行后状态（这可是 dry-run）
./logs
./logs/run.log
./report.csv
./report.sh
./tmp.XlPBYU
--- report.csv 内容 ---
（0 字节 —— 内容没了）
--- logs/run.log ---
start 1945
done

一次 dry-run 就建出了临时目录、日志目录和日志文件，更要紧的是把原本有数据的 report.csv 截成了 0 字节。关键在 ④。挂在函数上的 > report.csv 是函数一开始执行时 shell 就先打开的，与内部走哪条分支无关，文件照样被截断。「没东西要输出就不会动它吧」这个直觉恰好在这里失效。

同样的坑也出现在包装函数上。写一个 run 函数包住执行，并在调用处加重定向：

run(){ if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }
run printf 'migrated=%s\n' 3 > state.txt
--- 执行前的 state.txt ---
migrated=99
--- DRY=1 执行后的 state.txt ---
+ would run: printf migrated=%s\n 3

提示文字被写进了状态文件。下一次运行读到这个文件会发生什么，就留给想象了。dry-run 不该留下的东西可以列成一张清单。

  • 目标文件的截断、创建、删除 —— 把重定向挪进分支里
  • 临时目录 —— 需要的话只在 apply 阶段创建，并用 trap 清理
  • 日志文件 —— dry-run 的输出走标准输出与标准错误，不落盘
  • 锁文件 —— 只读的计划不需要；「能否拿到锁」只做检查
  • 远端状态变更 —— 令牌刷新、会话创建、队列消费这类看似读取实则改动的调用
  • 缓存与索引 —— 会改变下次运行的判断，因此属于副作用
怎么检查。在 dry-run 前后分别列出工作树的文件清单以及各文件的大小与哈希，然后对比即可。只要有一行不同，这个 dry-run 就名不副实。这套对比可以原样放进 CI。

5. 第四类：后一步依赖前一步的结果

前三类改代码就能消掉，这一类不行。只要步骤连成链条，dry-run 在原理上就无法预测后面。我做了一个三步迁移：第一步解包，第二步替换解出来的配置文件，第三步按第二步的件数记录状态。

run() { if [ -n "${DRY:-}" ]; then echo "+ would run: $*"; else "$@"; fi; }

echo "[1/3] 展开发布包"
run mkdir -p release
run tar -xf release.tar -C release

echo "[2/3] 替换配置"
n=0
for c in release/*.conf; do
  [ -e "$c" ] || continue
  n=$((n+1))
  run sed -i 's/^mode=old$/mode=new/' "$c"
done
echo "    目标 ${n} 个"

echo "[3/3] 后处理"
if [ "$n" -gt 0 ]; then ... else echo "    没有需要变更的对象，跳过"; fi
### DRY=1（询问它打算做什么）
[1/3] 展开发布包
+ would run: mkdir -p release
+ would run: tar -xf release.tar -C release
[2/3] 替换配置
    目标 0 个
[3/3] 后处理
    没有需要变更的对象，跳过
exit=0

### 真实执行
[1/3] 展开发布包
[2/3] 替换配置
    目标 3 个
[3/3] 后处理
    记录 state
exit=0

### 实际被改动的文件
release/app.conf:mode=new
release/db.conf:mode=new
release/web.conf:mode=new
--- migrate.state ---
migrated=3

dry-run 回答的是「第二步 0 个，第三步跳过」，真实执行却改了 3 个文件并写了状态文件。包装函数工作得毫无瑕疵，问题不在包装而在结构：第一步没执行，第二步就没有可看的输入；第二步计数为 0，第三步的分支便整个翻转。

最糟的是沉默。dry-run 没有说「我不知道」，而是断言「没有事情要做」，给使用者的印象恰好相反。处理这一类只有三种办法，每种都有代价。

办法做法代价
收窄范围声明 dry-run 只预测到第一步，之后一律标为 (无法预测)信息量减少，但不再说谎
建模状态在计划阶段先读归档清单，算出「解包后会存在的文件」模型可能与实际脱节，模型本身需要验证
隔离执行在一次性工作区里真正执行第一步，再在其上规划第二、三步最准确，但成本高且要重画副作用边界

实务上多数情况选第一种才对。会说「我不知道」的 dry-run，比不懂装懂的有用得多。解包这个例子还可以用 tar -tf 只读清单，廉价地模拟第二种办法。

6. 第五类：永远返回 0

前面每次运行都顺带打印了退出码。回头看会发现一处怪异：第 2 节的真实执行报了错却是 exit=0，而所有 dry-run 无一例外都是 exit=0。

dry-run 永远返回 0，就意味着只有人盯着屏幕看，信息才传得出去。以人来阅读为前提的工具接不进自动化。要在 CI 里做到「配置漂移就停下构建」，漂移与否必须以退出码的形式出现。

这里有个容易犯的错。只用 0 和 1，会让「有变更」和「计划失败」变成同一个值。这两件事在 CI 里要往相反方向处理：前者等人批准即可，后者说明流水线坏了。所以需要三个值。具体约定与接线见第 10 节。

7. 五类一览：看哪里能认出来

把至此复现的内容折进一张表。这是五分钟内判断别人脚本时用的表。

类型症状代码中的信号复现出的结果
1. 只打印不判断对不存在的目标也说要动手每个执行点都重复 if DRY对缺失文件输出 would delete，真实执行报错
2. 只在执行路径上的条件无法提前告知锁或容量问题dry 分支后紧跟 continue、returndry 预测 5 件成功，实际 2 件后 exit=4
3. 残留副作用明明是 dry-run 文件却变了分支外的重定向、mktemp、exec N>已有文件被截为 0 字节
4. 链式依赖把后续步骤误报为 0 件后一步用 for、find 重读前一步产物dry 说 0 件并跳过，实际改 3 件并写状态
5. 无意义的退出码在 CI 里用不了永远 exit 0，没有取值区分打印了错误仍然 exit=0

五类有一个共同点：它们都不报错。从第一类到第五类，没有任何一处会由脚本主动告诉你「这个 dry-run 并不准确」。所以它们在代码评审里逃过一劫，直到出事才被发现。

8. 正确的形态：把 plan 与 apply 分开

有一种结构能一次性消掉这五类：先把「要做什么」算出来变成一份清单，执行模式只负责消费这份清单。这正是基础设施工具所说的 plan 与 apply。

要点只有两条。

  • plan 只读状态。没有写入、创建、删除、取锁。输出经过排序，不掺时间戳与随机数
  • apply 不做判断。读取计划行并执行对应动作。内部没有条件语句，两种模式就没有分歧的余地
# ---------- plan：只读，不创建任何东西 ----------
make_plan() {
  [ -d "$REQ_DIR" ] || printf 'MKDIR\t%s\tarchive 目录缺失\n' "$REQ_DIR"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp)  printf 'DELETE\t%s\t临时文件\n' "$f" ;;
      *.log)  if [ -s "$f" ]; then printf 'ARCHIVE\t%s\t有内容\n' "$f"
              else                 printf 'DELETE\t%s\t0 字节\n' "$f"; fi ;;
      *.conf) if grep -qxF 'mode=old' "$f"; then
                printf 'PATCH\t%s\tmode=old\n' "$f"; fi ;;
    esac
  done
}

# ---------- apply：只消费计划，自己不判断 ----------
do_apply() {
  local plan="$1" action path reason
  while IFS=$'\t' read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)   mkdir -p -- "$path"  && echo "ok MKDIR   $path" ;;
      DELETE)  rm -f -- "$path"     && echo "ok DELETE  $path" ;;
      ARCHIVE) mkdir -p -- "$REQ_DIR"; mv -- "$path" "$REQ_DIR/" && echo "ok ARCHIVE $path" ;;
      PATCH)   sed -i 's/^mode=old$/mode=new/' -- "$path" && echo "ok PATCH   $path" ;;
      *)       echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)  make_plan | LC_ALL=C sort
         n=$(make_plan | grep -c . || true)
         [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply) do_apply "${2:?需要提供计划文件}" ;;
esac

跑三次，用哈希证明

光说没用。我在同一状态下连续生成三次计划并逐字节比较。

三次都是 072c4bfb98ee...，运行之后目录里一个文件都没有多出来。第 4 节那种副作用在这里结构上不可能发生，因为 plan 里根本没有写入命令。

ok ARCHIVE data/access.log
ok DELETE  data/build.tmp
ok DELETE  data/cache.tmp
ok DELETE  data/empty.log

apply 之后再生成计划，得到空计划与退出码 0。这是该结构最后一个好处：「计划为空」本身就是已达到目标状态的证据，不需要另写验证脚本。

让 plan 保持确定性。输出里不要放 date、$RANDOM、进程号或遍历顺序。for f in dir/* 的顺序可能随区域设置变化，用 LC_ALL=C sort 固定。加一列原因既方便人读，也不影响哈希比较。

9. 计划过期时：用哈希把它锁住

拆开 plan 与 apply 会出现新的缝隙：制定计划与执行计划之间，状态可能发生变化。一旦加入审批环节，这个间隔可能长达数小时。若期间有人添了文件，被批准的计划与实际发生的事就对不上了。

解法上一节已经写好：把计划的哈希一并保存，apply 在执行前依据当前状态重新计算计划并比对哈希，不一致就拒绝。

apply)
  want=$(sed -n '1p' "$p.sha" 2>/dev/null || echo '')
  have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
  if [ -n "$want" ] && [ "$want" != "$have" ]; then
    echo "ERROR: 计划之后状态已变化 (plan=$want / now=$have)" >&2
    exit 1
  fi
  do_apply "$p" ;;
### 1) 制定计划
plan exit=2
988ca65d91ce2783486a7216bdfb8dca47db67b8e1af3c0a664080c127aeab83
DELETE  data/cache.tmp  临时文件
MKDIR   data/archive    archive 目录缺失
PATCH   data/app.conf   mode=old

### 2) 计划与执行之间有人加了文件
app.conf cache.tmp late.tmp

### 3) 用过期计划 apply
ERROR: 计划之后状态已变化 (plan=988ca65d... / now=84f56a62...)
exit=1

### 4) 重新制定计划就能通过
plan exit=2
ok DELETE  data/cache.tmp
ok DELETE  data/late.tmp
ok MKDIR   data/archive
ok PATCH   data/app.conf
apply exit=0

第 3 步里 apply 拒绝了执行，因为被批准的计划中没有 late.tmp。第 4 步重新制定后它被纳入并通过。这一层带来的收益不小。

  • 审批重新有了意义 —— 人批准的清单与实际执行的清单一致，由机器来保证
  • 竞态能被及早抓住 —— 两条流水线同时跑，后者会被拒绝
  • 事后分析可复现 —— 计划文件与哈希留存，「做了什么、为什么做」都有记录

也有要注意的地方。哈希比对会再算一遍计划，对象很大时成本不低。而且它会拒绝一部分无关变化。上例中 late.tmp 确实影响了计划，但如果新增文件并不改变计划内容，哈希就仍然相同并通过。哈希锁的是计划，不是目录。正是这一区分让这套做法可用而不至于处处添堵。

10. 退出码约定与 CI 接线

回到第 6 节推迟的问题。被广泛采用的约定用三个值。

码值含义CI 行为人要做的事
0无变更 —— 与目标状态一致通过无
2有待应用的变更判失败，或等待审批读计划，批准或修改
1未能生成计划（错误）立即失败并告警修复流水线

把 2 分配给「有变更」是惯例。诊断类工具长期以来把正常、有差异、执行失败分成 0、1、2，思路一脉相承；这里把错误常用的 1 留出来，于是用 2 表示漂移。无论选哪套数字，重要的是三种状态可区分。

接线上真正会翻车的三处

约定定好了，shell 接线仍会把它毁掉。我复现了三处。

### A) 在 set -e 之下直接调用
exit=2
   （「走到这里了」没有输出 —— 后续步骤整段没跑）

### B) 用 if 包住就区分不了 2 和 1
有变更（或错误）     ← 正常的「有变更」(2)
有变更（或错误）     ← 错误子命令导致的错误 (1)
exit=0

### D) 进入管道后退出码变成 tee 的
$?=0  PIPESTATUS=2 0

A 是最常见的事故。set -e 把一切非 0 视为失败，于是表示「有变更」的 2 直接杀掉脚本。B 更安静。if 只看是否为 0，2 和 1 落进同一分支；上面两行分别是正常漂移与真实错误，消息却一模一样。D 在用 | tee 顺便把计划存成文件时出现：管道的退出状态取自最后一段，于是 tee 的 0 留了下来。

能同时避开这三处的写法是：

#!/usr/bin/env bash
set -uo pipefail
rc=0
./tidy.sh plan > plan.txt || rc=$?          # ← 不让脚本被杀掉，取回状态码
case "$rc" in
  0) echo "OK: 与目标状态一致（变更 0 项）"; exit 0 ;;
  2) echo "DRIFT: 待应用 $(grep -c . plan.txt) 项"; sed 's/^/    /' plan.txt; exit 1 ;;
  *) echo "FAIL: 计划生成失败 (rc=$rc)" >&2; exit 2 ;;
esac
### C) 按约定分成三支
DRIFT: 待应用 3 项
    DELETE  data/cache.tmp  临时文件
    MKDIR   data/archive    archive 目录缺失
    PATCH   data/app.conf   mode=old
CI 退出=1

### E) 应用之后再跑同一个 CI
apply exit=0
OK: 与目标状态一致（变更 0 项）
CI 退出=0

出现漂移时把计划原样展开到日志里并让构建失败；应用之后同一个任务就通过了。接入 CI 时实务上要注意的点如下。

  • 不要改参数 —— 生成计划的命令行与执行的命令行，目标、过滤与排除规则必须完全一致
  • 把计划保存为产物 —— 存成构建产物后，审批、审计与事后分析都归到这一个文件
  • PR 上只跑 plan，合并后再 apply —— 把审批环节挂到退出码 2 上
  • 用定时任务监控漂移 —— 每天跑一次 plan，出现 2 就告警。没人部署却出现 2，说明有人手工改过
  • 定时任务里不要把 2 升级为失败 —— 发告警即可；长期亮红灯就没人再看了
  • pipefail 与 PIPESTATUS —— 接入管道时明确规定要看哪一段的状态

11. 现成工具的 dry-run 能信到什么程度

讲完自己写的，就该看看现成的工具。先说结论：广泛使用的工具，其 dry-run 大体可信，更重要的是它们把边界写进了文档。问题不出在工具，而出在人在两次运行之间更换参数的那一刻。

复现：同一工具，不同参数

建一个临时仓库，放入未被跟踪的文件与目录、被忽略规则命中的目录，以及一个嵌套的独立仓库。

### git clean -n（默认）
Would remove .gitignore

### git clean -nd（含目录）
Would remove .gitignore
Would remove work/

### git clean -ndx（含被忽略的文件）
Would remove .gitignore
Would remove ignored/
Would remove work/

### 真实执行：git clean -fd
Removing .gitignore
Removing work/

### 剩下的
./ignored  ./ignored/c.txt  ./nested  ./nested/.git  ./nested/n.txt

三次 dry-run 的答案各不相同，而每一次都与相同参数真正执行的结果精确一致。官方文档写得很清楚：-n 是「不实际删除任何东西，只显示将会做什么」，-d 则是「通常为避免删除过多，git clean 不会递归进入未被跟踪的目录；指定 -d 会让它也递归进入这类目录」。

于是事故这样发生：用 git clean -n 确认，却用 git clean -fd 执行。上面的输出里 -n 只显示了 .gitignore 一行，而 -fd 把含有两个文件的 work/ 整棵树都删了。dry-run 并没有说谎，它回答的是另一个问题。还有一点：-nd 给出的 Would remove work/ 是一行，并不告诉你里面有几个文件。想知道会删多少个，数 dry-run 的行数是不够的。

嵌套仓库也很有意思。-ndx 完全没把 nested/ 列出来，直到加上 -ndxff 才出现。文档写道：「除非给出第二个 -f，否则 Git 拒绝修改带有 .git 子目录的、未被跟踪的嵌套仓库」。这说明 dry-run 如实映射了真实行为，并不是遗漏。

工具自己写明的边界

本环境没有 rsync，无法运行。这里改为引用其官方文档划出的边界。本段是文档引用而非执行验证，特此说明。

rsync 文档把 --dry-run 描述为一次试运行，会产生「与真实运行大体相同的输出」。随后指出 dry run 并不真正发送数据，因此 --progress 不起作用，bytes sent、bytes received、literal data、matched data 等统计会偏小，而 speedup 的值等同于无需任何传输的那种运行。与此同时它明确写道，--itemize-changes 的输出在 dry run 与随后的真实运行中应当完全一致，若不一致那就是缺陷。

这段话本身就是一个好 dry-run 该有的样子：逐项划线说明「要改什么」完全一致，「要花多久、走多少字节」则不同。我们自己动手时也需要同样的态度。把能预测的维度与不能预测的维度写进帮助信息，这件事本身就构成可信度。

使用现成工具时的实务规则很短。

  • 用同一条命令行 —— 确认时只加 -n，执行时不再添别的参数
  • 把清单留成产物 —— 把 dry-run 输出存成文件，事后与真实结果对照
  • 看条目而不是数量 —— 一行目录可能是几百个文件
  • 读文档的「例外」段落 —— 好工具会写明自己预测不了什么
  • 牵涉远端时再多疑一层 —— 权限、路径与时间戳的解释在两端可能不同

12. dry-run 终究预测不了的事

设计得再好也总有留白。把这份清单写进帮助信息，是「诚实的 dry-run」的最后一个条件。

预测不了的为什么缓解
时间流逝制定与应用不在同一时刻，保留期、有效期、cron 边界会在这中间跨过把判定基准时刻固定进计划并传给 apply
并发变更其他进程或人在动同一批对象第 9 节的计划哈希比对，外加应用期间加锁
资源耗尽磁盘、inode、内存只有在使用的瞬间才会不够在计划阶段汇总总量并与余量比较（标注为估算）
权限与策略执行用户、安全模块、挂载选项会在写入时介入对一个代表性路径做试写，或直接标为无法预测
远端状态API 响应、服务端校验、限流只有调用了才知道如果提供，就使用服务端的只校验模式
链式产物第 5 节 —— 前一步的产出是后一步的输入把范围钉死在第一步，或提前只读清单
部分失败之后中途停下，计划剩余部分将在另一种状态上执行失败即中止并重新制定计划

表的最后一行尤其重要。计划只在「制定它时的那个状态」上有效。如果应用到一半失败了，不要把剩下一半硬推下去。丢弃计划重新制定才是对的，而在第 8 节的结构里这只是一条命令。

结论：dry-run 是函数，不是模式

本文复现的五类有一个共同点：它们都是安静地出错。说要删一个并不存在的文件；说有 5 件却停在第 2 件；说什么都不改却把已有文件清空；断言无事可做随后改了 3 个文件；而且退出码始终是 0。没有任何一类会说「我的预测不可靠」。

于是判断标准收敛成一个问题：「这个 dry-run 是否走过了与真实执行相同的判断。」若它评估了同样的条件、按同样的顺序选出目标，那份输出就是预测；若只是复述参数列表，那就是模仿。而要对这个问题给出确定的「是」，迄今只有一条路：把判断只放在一个地方 —— 让 plan 独自判断，让 apply 只做消费。

这个结构好在三点。第一，不存在会让两种模式分歧的代码，第一类与第二类在结构上无从发生。第二，验证是白送的：三次哈希比对证明确定性，应用后的空计划证明收敛。第三，审批与审计归到一个文件：计划文件与它的哈希就是记录。

最后是今天就能做的一件事。把手头脚本的 dry-run 放进一个空的临时目录里跑一遍，对比运行前后的文件清单与哈希。只要有一行不同，这个 dry-run 就已经在改动什么了。然后再打印它的退出码。如果永远是 0，那它就只是一个需要有人盯着屏幕才生效的安全装置。没人看的安全装置不算安全装置。

# dry-run 设计指南 — 动手之前先过一遍的清单

> 出处: braindetox.kr — 如何做出真正的 --dry-run
> 依据: POSIX Issue 8 (Shell Command Language), Bash Reference Manual, git-clean(1), rsync(1)
> 把这个文件直接贴给 AI，写上「按这些标准改一下我们的脚本」即可使用。

## 1. plan / apply 分离骨架 — 直接照抄的形态

```bash
#!/usr/bin/env bash
# usage: tool.sh plan|apply [计划文件]
#   退出码  0=无变更 · 2=有变更 · 1=错误
set -uo pipefail
TAB=$(printf '\t')          # 用变量代替 ANSI-C 引用（可移植）

make_plan() {               # ★只读。禁止创建、删除、取锁
  [ -d "$REQ_DIR" ] || printf 'MKDIR%s%s%s缺失\n' "$TAB" "$REQ_DIR" "$TAB"
  for f in "$ROOT"/*; do
    [ -f "$f" ] || continue
    case "$f" in
      *.tmp) printf 'DELETE%s%s%s临时文件\n' "$TAB" "$f" "$TAB" ;;
    esac
  done
}

do_apply() {                # ★不做判断。case 里没有的动作即为错误
  local plan="$1" action path reason
  while IFS="$TAB" read -r action path reason; do
    [ -n "${action:-}" ] || continue
    case "$action" in
      MKDIR)  mkdir -p -- "$path" ;;
      DELETE) rm -f -- "$path" ;;
      *) echo "unknown action: $action" >&2; return 1 ;;
    esac
  done < "$plan"
}

case "${1:-}" in
  plan)
    make_plan | LC_ALL=C sort
    n=$(make_plan | grep -c . || true)
    [ "$n" -eq 0 ] && exit 0 || exit 2 ;;
  apply)
    p="${2:?需要提供计划文件}"
    want=$(cat "$p.sha" 2>/dev/null || echo '')
    have=$(make_plan | LC_ALL=C sort | sha256sum | cut -d' ' -f1)
    [ -z "$want" ] || [ "$want" = "$have" ] || {
      echo "计划已过期 (plan=$want now=$have)" >&2; exit 1; }
    do_apply "$p" ;;
  *) echo "usage: tool.sh plan|apply [planfile]" >&2; exit 1 ;;
esac
```

- [ ] plan 里 **一行写入命令都没有**
- [ ] apply 里 **没有查看状态的条件语句**
- [ ] 计划的每一行都带 **原因列**（人要能据此批准）
- [ ] 用 `LC_ALL=C sort` 固定了输出顺序

## 2. 退出码约定

| 码值 | 含义 | CI 行为 |
|---|---|---|
| `0` | 无变更 — 与目标状态一致 | 通过 |
| `2` | 有待应用的变更 | 判失败，或等待审批 |
| `1` | 未能生成计划 | 立即失败并告警 |

- [ ] 在 `set -e` 之下是否用 `rc=0; cmd || rc=$?` 取回状态码
- [ ] 是否用 `if cmd; then` **把 2 和 1 混成一谈**
- [ ] 进入管道时是否查看 `PIPESTATUS`
- [ ] 是否把码值含义写进帮助信息
- [ ] 定时任务是否只对 2 告警而不长期亮红灯

## 3. plan 阶段禁止的副作用

- [ ] 创建、删除或截断目标文件（含 `>` 重定向）
- [ ] 由 `mktemp`、`mkdir -p` 建出的工作目录
- [ ] 打开日志文件（`exec 3> ...` **在打开的瞬间** 就会创建文件）
- [ ] 获取锁文件或锁目录（「能否拿到锁」只做检查）
- [ ] 远端状态变更（令牌刷新、会话创建、队列消费）
- [ ] 缓存与索引更新（会改变下次运行的判断即为副作用）

★ **重定向在分支之外求值。** `f(){ ...; } > out` 即使在 dry 模式也会截断 `out`。
★ 在包装函数上写 `run cmd > state`，提示文字会被写进 **状态文件内部**。

## 4. 验证步骤 — 三次哈希与零副作用

```bash
snap(){ find "$1" -type f | LC_ALL=C sort | xargs -r sha256sum | sha256sum; }

before=$(snap target)
for i in 1 2 3; do ./tool.sh plan > "p.$i"; echo "run$i $(sha256sum < "p.$i")"; done
cmp -s p.1 p.2 && cmp -s p.2 p.3 && echo DETERMINISTIC || echo "★输出不稳定"
after=$(snap target)
[ "$before" = "$after" ] && echo "NO SIDE EFFECT" || echo "★plan 改动了状态"
```

- [ ] 三次哈希一致
- [ ] before 与 after 快照一致
- [ ] apply 之后再次 plan 得到 **空计划 + 退出码 0**
- [ ] 用过期计划 apply 会 **被拒绝**

## 5. dry-run 会说谎的条件 — 命中任意一条就写进帮助信息

- [ ] **只存在于** 执行分支内部的检查（锁、容量、权限、健康检查）
- [ ] 后一步读取前一步产物的 **链式结构**
- [ ] 计划与应用之间 **会流逝时间** 的运维流程（审批、批处理）
- [ ] 依据远端 API 响应或服务端校验分支
- [ ] 执行用户、安全策略或挂载选项不同的环境
- [ ] **部分失败后的续跑**（剩余计划将在另一种状态上运行）
- [ ] 时间戳、随机数或遍历顺序混入结果

## 6. 使用现成工具时

- [ ] 确认与执行的命令行是否只差一个 `-n`
- [ ] 是否把 dry-run 输出 **存成文件** 并与结果对照
- [ ] 是否把一行目录当成一个文件来数（一行可能是几百个）
- [ ] 是否读过文档的 **例外段落**（统计与进度常常不在保证范围内）
- [ ] 牵涉远端时，是否再次核对权限、路径与时间戳的解释

## 7. 帮助信息文案模板

```
--dry-run   只输出计划，不应用任何变更。
            可预测   : <在此填写>
            无法预测 : <在此填写>
            退出码   : 0 = 无变更 / 2 = 有变更 / 1 = 错误
            该模式不创建也不删除任何文件。
```

★ 试验破坏性命令时，请 **务必只在新建的空临时目录内** 运行。

复制后可直接粘贴到笔记应用或 AI 工具中。
