1. 텍스트 상자를 넘어선 인터페이스 — 왜 에이전트 네이티브인가

AI 에이전트를 애플리케이션에 붙이는 가장 흔한 방식은 화면 한쪽에 채팅 창을 두는 것이다. 이 글의 관점으로는, 이 방식에서는 에이전트가 다루는 맥락과 사용자가 보는 화면이 따로 놀기 쉽다.

Builder.io 의 오픈소스 프로젝트 BuilderIO/agent-native 의 README 는 이렇게 시작한다. 「Coding agents work with more than a text box. Their environment provides context, tools, files, tests, and previews that make their capabilities and results visible.」 README 는 이 관점을 에이전트와 사람이 함께 보는 전용 UI 로 이어 간다.

이 글의 정리로는, 앞선 글들(MCP 무상태 전환, Claude Code MCP 서버 선택 기준, OmniRoute AI 게이트웨이)이 에이전트 클라이언트와 도구 서버 사이의 프로토콜·라우팅을 다루는 반면 Agent-Native 는 애플리케이션 내부에서 하나의 액션을 UI 와 에이전트가 함께 쓰는 프레임워크를 다룬다.

README 는 이 프로젝트를 자율적인 작업과 전용 UI 를 결합한 에이전트를 만들기 위한 오픈소스 TypeScript 프레임워크라고 소개한다. 아래에서는 README 가 밝힌 범위의 세 원칙과 여섯 표면을 정리하고, 도입 시 따져 볼 트레이드오프를 이 글의 해석으로 덧붙인다.

2. 화면과 도구의 괴리 — 핸들러 중복과 로직 불일치 문제

이 절은 README 가 아니라 이 글이 정리한 일반적인 설계 배경이다. 풀스택 웹 애플리케이션 아키텍처에서 사용자 경험의 중심은 화면 이벤트 핸들러였다. 버튼 클릭 이벤트가 발생하면 컴포넌트의 클릭 핸들러가 트리거되고, 폼 데이터 유효성을 프론트엔드에서 1차 검증한 뒤 HTTP 클라이언트를 통해 백엔드로 요청을 보낸다. 백엔드는 비즈니스 로직을 수행하고 데이터베이스를 갱신한 뒤 성공 응답을 돌려주고, 상태 저장소가 갱신되면서 화면 렌더링이 완료된다.

여기에 LLM 기반 에이전트 기능을 추가하려고 할 때 별도의 보조 경로를 구축하는 경우가 있다. 에이전트가 호출할 수 있는 도구 정의를 스키마 형태로 별도 작성하고, 모델의 함수 호출 요청을 받아 처리할 전용 엔드포인트를 신설하는 방식이다. 그러나 이러한 이원화 구조에서는 다음과 같은 관리 부담이 생길 수 있다.

  • 기능 명세와 유효성 검증의 중복: 화면 버튼 핸들러에서 검증하는 입력 규칙과 에이전트 도구의 스키마 정의가 서로 다른 위치에 작성되면서, 비즈니스 규칙이 변경될 때 한쪽의 수정이 누락되는 사태가 일어날 수 있다.
  • 실행 경로와 권한 검사의 분리: 화면 조작 시 통과하는 인증 및 세션 검사와 에이전트 경로를 통해 인입되는 도구 실행 경로의 인가 로직이 갈라져 보안 사각지대가 생길 수 있다.
  • 화면 상태와 모델 인지의 시차: 에이전트가 도구 호출을 통해 데이터를 변경했음에도 사용자의 브라우저 메모리에 올라와 있는 상태가 이를 바로 감지하지 못하면 화면에 이전 데이터가 남는 불일치가 생길 수 있다.
  • 테스트와 회귀 검증의 비용 증가: 동일한 작업에 대해 UI 상호작용 테스트와 에이전트 도구 호출 테스트를 각각 작성해야 할 수 있어 테스트 유지보수 부담이 늘 수 있다.

이 절에서 정리한 문제의 배경에 대해, README 는 이 문제를 하나의 액션이 모든 표면을 구동한다는 형태로 다룬다.

3. 핵심 원칙 3가지 — Shared Actions, Data, State

공식 저장소 README 는 에이전트 네이티브 애플리케이션을 지탱하는 3가지 핵심 원칙을 다음과 같이 정의하고 있다.

공유 원칙 공유 대상 README 서술
Shared actions 에이전트 도구와 UI 코드의 기능 에이전트는 각 기능을 도구로 호출하고 UI 는 코드에서 호출한다. 두 경로가 같은 유효성 검사, 권한, 구현을 쓴다.
Shared data 에이전트와 UI 에서 수행된 작업 결과 에이전트가 한 작업은 UI 에 나타나고, UI 에서 한 작업은 에이전트가 쓸 수 있다.
Shared application state 현재 페이지, 선택된 레코드, 활성 뷰 에이전트가 현재 페이지, 선택된 레코드, 활성 뷰 같은 관련 UI 상태를 받는다.

세 가지 원칙에 대한 README 의 서술 내용은 다음과 같이 정리된다.

  • 첫째, Shared actions: README 에 따르면 에이전트는 각 기능을 도구로 호출하고 UI 는 코드에서 호출하며, 두 경로가 같은 유효성 검사, 권한, 구현을 쓴다. 비즈니스 로직과 검증이 같은 경로를 공유하므로 불일치를 줄일 수 있다.
  • 둘째, Shared data: README 는 에이전트가 한 작업이 UI 에 나타나고, UI 에서 한 작업은 에이전트가 쓸 수 있다고 밝힌다. 양쪽 표면에서 데이터 작업 결과가 서로 전달되는 구조다.
  • 셋째, Shared application state: README 는 에이전트가 현재 페이지, 선택된 레코드, 활성 뷰 같은 관련 UI 상태를 받는다고 설명한다. 이 글의 예시로, 선택된 레코드 정보가 에이전트에 전달되면 사용자의 지시가 짧아질 수 있다. README 가 이 예를 든 것은 아니다.

4. 하나의 액션이 노출되는 6개 표면 — UI부터 CLI까지

README 는 한 액션이 UI, 에이전트, HTTP, MCP, A2A, CLI 의 여섯 표면을 구동한다고 밝힌다.

표면 (Surface) 호출 주체 동작 방식과 역할
UI UI 화면 코드 (React) React 에서 useActionQuery 로 호출
Agent tools AI 에이전트 에이전트가 액션을 도구로 받음
HTTP API HTTP 클라이언트 액션의 http 항목으로 메서드를 지정(예시는 GET)
MCP MCP 클라이언트 Model Context Protocol 표면으로 노출
A2A 외부 에이전트 agent-to-agent 표면으로 노출
CLI 명령줄 환경 명령줄 표면으로 노출

아래는 README 를 바탕으로 이 글이 정리한 해석이다.

  • 구현 지점의 단일화(이 글의 해석): README 에 따르면 한 액션이 여섯 표면을 구동하므로 같은 기능을 표면마다 따로 만들지 않아도 된다.
  • 검증·권한의 공유: README 는 에이전트 경로와 UI 경로가 같은 유효성 검사, 권한, 구현을 쓴다고 밝힌다.
  • 외부 프로토콜 표면: MCP 와 A2A 가 표면 목록에 들어 있다. 어떤 클라이언트와 연동되는지는 README 가 밝히지 않는다.
  • CLI·HTTP 호출(이 글의 해석): 같은 액션을 명령줄이나 HTTP 로도 호출할 수 있으므로 재현과 자동화에 쓸 수 있을 것으로 보인다.
  • 스키마 공유(이 글의 해석): 액션이 description 과 schema 를 가지므로 표면 사이에서 입력 규칙을 맞추기 쉬울 수 있다. README 는 문서 자동 생성을 언급하지 않는다.
  • 이관 방식: 기존 애플리케이션을 액션 단위로 옮길 수 있는지는 README 가 다루지 않으며, 이관 사례도 나오지 않는다.

5. defineAction 코드 구조 — 단일 선언과 런타임 바인딩

README 의 예시 코드는 다음과 같다(import 문은 생략했다).

export default defineAction({
  description: "Return a friendly greeting.",
  schema: z.object({
    name: z.string().default("world").describe("Name to greet"),
  }),
  http: { method: "GET" },
  run: async ({ name }) => {
    return { message: `Hello, ${name}!` };
  },
});

README 는 이 예시를 이렇게 설명한다. 「The agent receives hello as a tool. React calls the same function with useActionQuery("hello", { name: "Alex" }). Agent-Native also exposes it through HTTP, MCP, A2A, and the CLI.」 코드 구성은 description(설명 문자열), schema(Zod 객체, name 의 기본값 "world" 와 설명), http(메서드 지정, 예시는 GET), run(실행 함수)이다. 각 필드가 런타임에서 구체적으로 어떻게 쓰이는지는 README 예시 밖의 일이다.

이 글의 관찰로는 한 번의 선언에 설명, 입력 스키마, HTTP 메서드, 실행 로직이 함께 들어 있다.

6. 프레임워크 종속의 대가 — TypeScript와 Zod 스키마 전제

모든 아키텍처적 선택에는 대가가 따른다. README 는 이 프로젝트를 TypeScript 프레임워크라고 소개하고 예시에서 Zod 를 쓴다. 아래는 그로부터 이 글이 추론한 트레이드오프이며 README 의 서술이 아니다.

  • 타입스크립트 환경: Agent-Native 는 TypeScript 프레임워크다. 다른 언어로 작성된 기존 백엔드가 있다면 TypeScript 계층을 따로 두는 방안을 검토해야 할 수 있다.
  • Zod 스키마: README 의 예시가 Zod 스키마를 쓴다. 다른 스키마 라이브러리를 지원하는지는 README 에 나오지 않는다.
  • 성능: README 에는 지연 시간이나 오버헤드를 다룬 서술이나 벤치마크가 없다. 저지연 시스템에서는 직접 측정해 보아야 한다.
  • 생태계 규모: MIT 라이선스이며 확인 시점 기준 스타 4.9k, 포크 462 이다. 커뮤니티 플러그인이나 서드파티 통합 사례의 규모는 README 에 나오지 않는다.

이 글의 판단으로는, 기존 코드베이스가 크고 프론트엔드-백엔드 계약이 확고한 환경에서는 전체 전환보다 에이전트 상호작용이 집중되는 신규 기능부터 시험해 볼 수 있다.

7. 직접 검증하는 방법 — 템플릿 생성과 실행 경로

README 는 다음 명령으로 독립형(standalone) 채팅 에이전트 템플릿을 시작할 수 있다고 안내한다.

npx --yes @agent-native/core@latest create my-agent --standalone --template chat

README 는 이 명령이 독립형 채팅 에이전트 템플릿을 시작점으로 만든다고 설명한다. 생성물의 구성과 동작은 이 글이 직접 실행해 보지 않았다.

저장소 지표를 살펴보면(확인 시점 기준) 스타 수 4.9k, 포크 수 462, 오픈 이슈 12건, 풀 리퀘스트 66건을 기록하고 있다. 라이선스는 MIT 라이선스다. 다만 4.9k 수준의 스타 수는 관심의 한 지표일 뿐, 대규모 엔터프라이즈 환경에서의 안정성이나 장기적인 품질을 보증하는 척도는 아니다. 따라서 실무에 도입하기 전에는 위 템플릿 명령어로 프로젝트를 직접 생성해 요구사항을 충족하는지 확인하는 과정이 권할 만하다.

8. 값을 하는 자리와 못 하는 자리 — 적합한 적용 영역과 한계

어떤 프레임워크도 모든 문제에 적합한 만능 해결책이 될 수는 없다. 이 절은 README 의 권고가 아니라 이 글이 정리한 해석이다. 에이전트 네이티브 설계가 가치를 낼 수 있는 자리와 그렇지 않은 자리를 이 글의 관점에서 나눠 본다.

  • 값을 하는 자리 ① — 에이전트와 인간이 협업하는 대화형 도구: 디자인 도구나 데이터 분석 화면처럼 사용자가 화면 요소를 다루면서 동시에 에이전트에게 관련 작업을 지시하는 환경에서는 단일 액션과 상태 공유가 개발 작업을 줄일 수 있다.
  • 값을 하는 자리 ② — 다중 인터페이스를 필요로 하는 시스템: 웹 화면뿐 아니라 명령줄(CLI)이나 외부 에이전트(MCP/A2A) 연동을 함께 고려하는 시스템이라면 6개 표면 지원이 도움이 될 수 있다.
  • 값을 못 하는 자리 ① — 화면 상호작용이 없는 순수 백엔드 파이프라인: 배치 데이터 처리나 크롤러처럼 UI 가 아예 없는 시스템에서는 이 프레임워크의 화면 관련 기능이 필요하지 않을 수 있다.
  • 값을 못 하는 자리 ② — 정적 사이트 및 타 프레임워크 종속 프로젝트: 단순 블로그나 문서 사이트, 또는 다른 에이전트 프레임워크에 깊이 묶인 기존 프로젝트에는 이 구조가 맞지 않을 수 있다.

  • 공식 README 에는 액션 호출 시의 처리량이나 지연 시간, 메모리 점유율을 측정한 표준 벤치마크 수치가 공개되어 있지 않아 대규모 트래픽 인입 시의 성능 특성은 확인하지 못했다.
  • 대규모 상용 프로덕션 환경에서 Agent-Native 를 전면 도입해 장기간 운영한 실사례 및 장애 보고 데이터는 공개 출처에서 확인하지 못했다.
  • UI 와 에이전트 사이의 데이터 반영이 실시간인지, 수동 새로고침 없이 이루어지는지는 README 가 밝히지 않으며, 다른 도구 바인딩 라이브러리와의 정량 비교도 없다.
