Safari MCP 서버 공개 - WebKit이 AI 에이전트에게 브라우저를 내준 이유

AI 에이전트가 실제 Safari 브라우저로 디버깅·검사·자동화를 하는 시대 - MCP란 무엇이고 무엇이 달라지나

2026-07-06 개발/인프라

서론: 브라우저 벤더가 조종간을 내주다

2026년 7월 1일, Apple은 Safari Technology Preview 247에 눈에 띄지 않는 항목 하나를 밀어 넣었다. WebKit 공식 블로그가 발표한 이름은 Safari MCP 서버다. 겉으로는 개발자 도구 업데이트 한 줄이지만, 실제로는 AI 코딩 에이전트에게 진짜 Safari 브라우저 창의 조종간을 내주는 결정이다.

이 글은 발표 내용을 그대로 옮기는 대신 세 가지를 순서대로 짚는다. 먼저 Model Context Protocol(MCP)이 정확히 무엇이고 왜 브라우저 제어와 유난히 잘 맞는 조합인지, 다음으로 Safari MCP가 실제로 여는 것과 열지 못하는 것, 마지막으로 이미 자리 잡은 Playwright MCP·Chrome DevTools MCP와 무엇이 다른지를 본인의 시각으로 분석한다. 팩트는 WebKit 공식 발표와 관련 보도를 근거로 하고, 해석은 본인 몫으로 명확히 구분한다. 2026년 7월 기준으로 정리한다.

1. MCP란 무엇인가 - AI 에이전트와 도구를 잇는 개방 표준

1.1 무엇이 문제였나

MCP 이전에는 AI 코딩 에이전트가 외부 도구 하나를 쓰려면 그 도구 전용의 맞춤 연동 코드가 필요했다. 슬랙 연동, 깃허브 연동, 브라우저 제어 연동이 각각 따로 만들어졌고, 에이전트를 바꾸면 연동도 다시 짜야 했다. Anthropic이 2024년 11월 공개한 MCP는 이 문제를 정면으로 겨냥한다.

1.2 USB-C에 비유되는 이유

MCP는 흔히 AI 애플리케이션을 위한 USB-C 포트에 비유된다. 도구를 제공하는 쪽(서버)이 자신이 할 수 있는 일을 Tools(호출 가능한 함수)·Resources(읽기 전용 데이터)·Prompts(사전 정의된 지시 템플릿)라는 표준 형식으로 노출하면, 그 형식을 이해하는 어떤 에이전트(클라이언트)든 별도의 맞춤 코드 없이 연결해 쓸 수 있다. 이후 OpenAI가 2025년 말 ChatGPT에 MCP 클라이언트 지원을 넣고, Google이 2026년 중반 Gemini용 관리형 MCP 서버를 내놓으면서, 경쟁 관계인 벤더들이 한 회사가 만든 프로토콜을 나란히 채택하는 흔치 않은 그림이 만들어졌다. 이 표준화 자체가 이번 Safari MCP 서버 발표의 배경이다.

1.3 왜 "브라우저 제어"가 유난히 잘 맞는 조합인가

본인이 보기에 MCP가 다른 어떤 영역보다 브라우저 제어와 궁합이 좋은 이유는 단순하다. 코드를 읽는 것과 코드가 실제로 어떻게 렌더링되는지는 완전히 다른 문제이기 때문이다. 소스만 보는 에이전트는 "이 CSS가 이론적으로 이렇게 보여야 한다"까지만 말할 수 있지만, 실제 브라우저 엔진에 눈과 손을 가진 에이전트는 "실제로 이렇게 보이고, 이 지점에서 어긋난다"를 직접 확인하고 가설을 검증할 수 있다. 이 차이가 디버깅에서는 결정적이다. MCP를 통해 브라우저 자체가 도구로 노출되는 순간, 에이전트는 추측이 아니라 관찰에 근거해 일하게 된다.

2. Safari MCP 서버가 여는 것

2.1 설치와 연결 - Technology Preview와 safaridriver

Safari MCP 서버는 아직 정식 Safari가 아니라 Apple이 오랫동안 운영해 온 공개 베타 채널인 Safari Technology Preview(247)에서만 제공된다. 사용자는 설정에서 "웹 개발자 기능 보기"와 "원격 자동화 및 외부 에이전트 활성화"를 켜야 하고, 이는 기존에 셀레니움 같은 WebDriver 기반 테스트에 쓰이던 자동화 권한 모델을 에이전트에게로 확장한 것이다. 연결은 새 인프라를 만드는 대신 기존 자동화 드라이버인 safaridriver 실행 파일에 --mcp 플래그를 붙이는 방식이다. Claude Code라면 claude mcp add 명령으로, 다른 클라이언트는 mcp.json 설정 파일 수정으로 등록한다. 어떤 MCP 호환 클라이언트든 원칙적으로 연결할 수 있다.

2.2 무엇을 할 수 있나

공개된 도구 모음은 스크린샷 촬영, DOM 요소 클릭·입력·스크롤·호버 같은 상호작용, 콘솔 메시지와 네트워크 요청 확인, 페이지 내용 추출, 탭 생성·전환·종료, 페이지 내 자바스크립트 실행, 뷰포트 크기 조정과 CSS 미디어 타입 에뮬레이션을 통한 반응형 디자인 점검, 레이블 누락·ARIA 속성·명도비 같은 접근성 문제 확인, 셀렉터 기반 요소 조회와 폼 상태 검증까지 아우른다. 요컨대 "브라우저를 실제로 조작해 무엇이 보이고 무엇이 깨지는지"를 에이전트가 직접 확인하도록 하는 도구 세트다.

2.3 보안 설계 - 로컬 전용, 신뢰 경계

이 서버는 로컬 머신에서만 실행되며 자체적으로 외부 네트워크 호출을 하지 않는다. Safari의 자동완성 정보나 브라우징 히스토리 같은 개인정보에는 접근하지 못하도록 범위가 제한돼 있고, 캡처된 스크린샷·콘솔 로그 같은 데이터는 연결된 에이전트로 직접 전달될 뿐 Apple로 보내지지 않는다. 다만 그 데이터를 이후 어떻게 처리하는지는 전적으로 사용하는 에이전트와 모델에 달려 있다. Apple은 신뢰하는 에이전트에게만 브라우저 접근 권한을 부여하라고 명시적으로 권고한다.

2.4 실제 시나리오

공개된 예시 흐름은 이렇다. 개발자가 "내 항공편 예약 페이지에 Safari에서만 나는 버그가 있다"고 요청하면, 에이전트는 Safari에서 해당 페이지를 열고, 버그를 재현·분석하고, 애니메이션 오류나 콘솔 경고 같은 부가 문제까지 함께 짚어내고, 수정안을 제안한다. 사람이 하던 "일단 사파리 켜서 확인해 보자"는 수작업 단계가 에이전트 루프 안으로 들어온 셈이다.

3. 기존 브라우저 자동화 MCP와의 차이 - Playwright·Chrome DevTools·Puppeteer

3.1 철학의 차이 - 주행 대 관찰

브라우저 제어 MCP 서버는 이미 여럿 있었다. 크게 두 철학으로 나뉜다. Playwright MCP는 접근성 트리를 구조화된 텍스트 스냅샷으로 노출해, 에이전트가 픽셀이 아니라 구조를 "읽고" 대규모 크로스브라우저 E2E 테스트를 안정적으로 반복 실행하는, 말하자면 브라우저를 주행하는 쪽에 최적화돼 있다. 반면 Google이 2025년 9월 공개 프리뷰로 내놓은 Chrome DevTools MCP는 Chrome DevTools 프로토콜에 직접 연결해 성능·콘솔·네트워크 진단 도구를 두텁게 제공하는, 브라우저를 관찰하는 쪽에 가깝다. Safari MCP는 스크린샷·콘솔·네트워크·접근성 점검이라는 도구 구성만 놓고 보면 후자, 즉 관찰·디버깅 철학 쪽에 더 가깝게 설계됐다고 본인은 읽는다.

3.2 구조의 차이 - 무엇 위에 얹었나

더 흥미로운 차이는 구조다. Chrome DevTools MCP는 CDP라는 브라우저 내부 디버깅 프로토콜 위에 새로 지었고, Playwright MCP는 자체 접근성 트리 스냅샷 엔진을 갖고 있다. Safari MCP는 그와 달리 오래전부터 셀레니움 같은 크로스브라우저 WebDriver 테스트에 쓰이던 기존 자동화 드라이버(safaridriver) 위에 --mcp 플래그 하나로 얹혔다. 새 인프라를 짓지 않고 검증된 자동화 계층을 재활용한 실용적 선택으로 보인다. 다만 이는 동시에, Playwright가 토큰 소모를 줄이려 구조화된 스냅샷과 별도 CLI 모드까지 마련한 것과 달리, Safari MCP도 스크린샷·DOM 덤프 중심의 도구 구성상 Chrome DevTools MCP가 겪는 것과 비슷한 토큰 비용 문제(도구 정의만으로 상당한 토큰을 먹는 것으로 보고된 사례)를 마주할 가능성이 있다는 추정이다. 이는 아직 공개 벤치마크로 확인된 사실이 아니라 구조적 유사성에서 나온 본인의 추론임을 밝혀 둔다.

3.4 WebMCP와 헷갈리지 말 것

여기서 짚고 넘어갈 개념이 하나 있다. Chrome이 함께 밀고 있는 WebMCP는 Safari MCP와 정반대 방향의 아이디어다. Safari MCP·Chrome DevTools MCP·Playwright MCP는 모두 에이전트가 브라우저를 원격 조종하는 도구인 반면, WebMCP는 웹사이트 자체가 스스로를 MCP 도구 제공자로 노출하는 실험이다. 전자는 "에이전트가 브라우저를 붙잡는다"이고 후자는 "웹사이트가 에이전트에게 자기 기능을 도구로 내준다"이다. 이름이 비슷해 자주 섞이지만, 이 둘을 구분하지 못하면 이번 발표의 위치를 오해하기 쉽다.

4. 웹개발자 실무 활용 시나리오

당장 의미가 있는 활용처는 세 가지로 좁혀진다. 첫째, Safari·WebKit 전용 렌더링 버그 헌팅이다. Chromium 계열에서는 멀쩡한데 Safari에서만 깨지는 CSS·애니메이션 문제는 오랫동안 "맥이 있는 사람이 직접 열어봐야" 잡을 수 있었는데, 이제 에이전트가 그 첫 단계를 대신할 수 있다. 둘째, 배포 전 접근성 점검이다. 레이블·ARIA·명도비 확인을 코드 리뷰 단계에서 자동으로 훑게 할 수 있다. 셋째, 반응형 QA다. 뷰포트를 바꿔가며 레이아웃을 확인하던 수작업 루틴을 에이전트 루프에 편입할 수 있다. 다만 이 셋 모두 macOS에서 Safari 자체를 띄울 수 있어야 한다는 전제는 그대로 남는다. Safari MCP가 없애는 것은 "직접 클릭해 가며 확인하는 수고"이지, "맥 하드웨어가 있어야 한다"는 제약이 아니다.

5. 한계와 주의점

5.1 아직 Technology Preview

Safari MCP 서버는 정식 Safari가 아니라 개발자 프리뷰 채널에서만 동작한다. 프로덕션 QA 파이프라인에 지금 바로 못 박아 넣기보다는, 정식 Safari로 넘어오는 시점과 안정성을 지켜보며 도입 범위를 넓혀가는 것이 안전하다.

5.2 Safari·macOS 종속

WebKit 엔진 하나만 다루므로 크로스브라우저 테스트를 대체하지 못한다. Chrome·Firefox까지 아우르는 검증에는 여전히 Playwright MCP 같은 별도 도구가 필요하다. 또한 Safari 자체가 macOS(및 iOS) 전용이라, 팀에 Mac이 없다면 이 도구를 쓸 방법 자체가 없다는 점도 그대로다.

5.3 신뢰 경계와 거버넌스 공백

에이전트에게 브라우저 제어를 준다는 것은 원격 페어 프로그래머에게 키보드와 마우스를 통째로 맡기는 것과 비슷하다. Apple이 자동완성 접근 차단과 로컬 전용 실행으로 기술적 안전장치를 마련했지만, "어떤 에이전트에게 이 권한을 줄 것인가"라는 조직 차원의 통제와 로그 관리는 도구가 대신해주지 않는다. Apple 스스로 신뢰하는 에이전트에게만 권한을 부여하라고 못박은 것도 이 지점을 겨냥한다. 이는 Safari MCP만의 문제가 아니라 브라우저 제어권을 넘기는 모든 벤더 MCP 서버가 공통으로 안고 있는, 아직 표준화되지 않은 숙제다.

6. 브라우저 벤더가 직접 MCP를 내는 흐름의 의미

6.1 연대기

순서를 짚어보면 흐름이 뚜렷하다. Google이 2025년 9월 Chrome DevTools MCP를 공개 프리뷰로 내놓았고, Chromium 기반인 Microsoft Edge 147이 2026년 3월 이를 물려받아 지원을 넓혔고, Apple이 2026년 7월 WebKit 엔진 진영에서 Safari MCP 서버로 합류했다. 탐색한 범위 안에서는 Firefox·Gecko 진영의 공식 MCP 서버 소식은 확인되지 않았지만, 3대 렌더링 엔진 중 최소 둘(Blink·WebKit)이 벤더 자체 MCP를 갖추게 된 셈이다.

6.2 왜 벤더가 직접 내는가

커뮤니티가 CDP나 WebDriver를 감싸 만든 서드파티 MCP 서버도 이미 여럿 있었다. 그럼에도 벤더가 직접 내는 것이 갖는 의미는 다르다고 본인은 본다. 엔진 내부와 직접 붙어 있어 브라우저 업데이트에도 함께 유지보수되고, Apple처럼 개인정보 접근 범위를 엔진 차원에서 설계해 넣을 수 있으며, 제3자 도구보다 신뢰 신호가 강하다. 이는 "설정만 하면 아무 MCP나 붙일 수 있던" 시기에서 "프로토콜이 브라우저 자체에 내장되는" 시기로 넘어가고 있다는 뜻이다.

6.3 경쟁사 프로토콜을 채택하는 역설

가장 흥미로운 대목은, 이 모든 흐름이 결국 Anthropic이라는 한 회사가 만든 프로토콜 위에서 벌어진다는 점이다. Google도, 이제 Apple도, 경쟁 관계에 있는 회사가 설계한 개방 표준을 그대로 받아 자사 브라우저에 심었다. John Gruber가 지적했듯 MCP는 여러 벤더가 실제로 채택했다는 점에서 이름만 개방이 아니라 실질적으로 개방적인 드문 사례다. 브라우저 전쟁이 여전히 뜨거운 와중에도, 에이전트가 붙는 인터페이스만큼은 공통 표준으로 수렴하고 있다는 것은 2026년 AI 개발 도구 지형에서 눈여겨볼 신호다.

7. 결론 - 오늘 적용 가능한 3가지

Safari MCP 서버는 단발성 기능 추가가 아니라, MCP가 브라우저라는 가장 기본적인 개발 인프라에까지 스며들고 있다는 신호다. 다만 아직 Technology Preview 단계이고, Safari·macOS라는 범위 안에 갇혀 있으며, 신뢰 거버넌스는 도구가 대신 풀어주지 않는다는 점을 함께 봐야 한다.

7.1 STP를 설치해 본인 사이트의 Safari 전용 버그부터 잡아보라

Safari Technology Preview를 설치하고 설정을 켠 뒤, 쓰는 에이전트에 claude mcp add 방식으로 연결해 본인 프로덕트에서 Safari에서만 나는 버그가 있는지 먼저 확인하라. 가장 빠르게 가치를 확인할 수 있는 진입점이다.

7.2 Playwright·Chrome DevTools·Safari MCP의 역할을 나누어 배치하라

크로스브라우저 E2E는 Playwright MCP, Chrome 성능·디버깅은 Chrome DevTools MCP, Safari 전용 이슈는 Safari MCP로 나눠 쓰는 것이 현재로선 합리적이다. 하나의 도구가 전부를 대체한다고 기대하지 말라.

7.3 에이전트 신뢰 경계를 조직 차원에서 먼저 정하라

어떤 에이전트에 브라우저 제어 권한을 줄지, 캡처된 화면·로그를 어떻게 보관·폐기할지를 도구 도입 전에 팀 규칙으로 정하라. 벤더의 기술적 안전장치와 별개로, 이 부분은 여전히 사람이 채워야 할 몫이다.
