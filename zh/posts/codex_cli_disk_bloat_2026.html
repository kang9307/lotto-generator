Codex CLI 会话日志膨胀至数百GB

从子智能体会话日志吞噬整块磁盘的事件,看AI编程CLI的日志卫生

2026年7月21日 开发/基础设施

引言:编程智能体留下的不只是代码

最近 GeekNews 上一条话题引起了开发者社区的关注:有人在使用 Codex CLI 调用子智能体处理任务时,发现会话日志膨胀至数百GB,把本地磁盘吃满了。乍一听会觉得"一个日志文件怎么可能大到这种地步",但 GitHub issue 追踪器中确实记录了具体数字:一个父会话派生出的数千个子会话,合计超过了700GB。

进入2026年下半年,一名开发者同时打开多个 Claude Code、Codex、Cursor 这类CLI型编程智能体已不是什么特别的事。问题在于,这些工具会把对话、规划、工具执行的整个过程原样记录为会话文件。代码会被审查、删除,但记录这些代码是如何产生的日志,却在无人留意间悄悄堆积起来。本文不打算复述这起事件本身,而是分析这种膨胀为何在结构上几乎是必然的,以及现在应该检查和调整哪些地方。

1. 事件曝光了什么 - 用数字看膨胀规模

openai/codex 仓库中的 GitHub issue #34061("Insane Codex Disk Usage from Subagents")详细记录了复现过程。一个父会话派生出的子会话文件多达2,393个,仅这些子会话就占用约731.5GiB。~/.codex/sessions 目录整体约为755GiB,~/.codex 整个目录约达760GiB,使一块1.8TiB的卷占用达到99%~100%。单个子会话文件中,有的在3分19秒内写入了483.7MB、35万3255条JSONL记录(约每秒1,770条)。报告时使用的是 Codex CLI 0.144.6(受影响范围0.142.4~0.144.6),macOS arm64 环境,截至查证时该issue仍处于开放状态,未见维护者的官方回应。

同一仓库的issue #24948指出,反复的压缩(compaction)历史与原始工具输出未被清理而持续累积,使会话日志膨胀到700MB~2GB量级;OpenAI开发者社区中也有用户报告,长时间保持 Codex 会话打开会导致磁盘耗尽。会话文件路径通常呈 ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl 形式,另有 ~/.codex/logs_2.sqlite 之类的日志数据库文件同步累积。不过具体路径与行为可能因版本而异,实际排查时最好直接核对所用版本的官方文档与本地目录。

2. 为何会膨胀到数百GB - 结构性原因

单纯归结为"日志堆得多了"无法解释这种增长幅度。综合各方报告,几个结构性原因叠加在一起。

2.1 子智能体扇出(fan-out)

每当一个父会话把任务拆分给多个子智能体时,父会话的状态或累积上下文的一部分往往也会被写入每个子会话。子智能体数量一旦扩大到数百甚至数千,同样的上下文就被复制了那么多次,总容量的增长不是线性的,而近乎倍数级。

2.2 压缩历史的重复保存

维持长对话需要对旧上下文做压缩(摘要)以节省token。但如果压缩过程本身和压缩前的原始记录都被写入日志,对话越长,"原文+摘要"就会持续叠加。

2.3 恢复会话时的历史重新构建

有报告指出,在中断后恢复会话、重新加载并处理整段历史对话的过程中,先前的记录会被重复写入或复制。恢复的频率越高,这种重复累积的空间就越大。

2.4 原始工具输出无限制存储

编程智能体需要完整记录文件读取、命令执行、测试结果等工具输出,才能用于下一步判断。如果这些输出没有上限或摘要地按原文保存,仅一次涉及大型日志或庞大文件的任务,就可能让会话文件瞬间膨胀。轮转、容量上限、自动删除策略默认缺失,放大了上述所有原因。

3. 并非 Codex 独有 - 其他AI编程CLI的类似案例

本文无意针对某一款产品。事实上,同类问题在其他厂商身上也有报告,这恰恰更能说明问题的本质。Claude Code 的 GitHub 仓库中也有一条issue,指出 ~/.claude 目录在缺乏专门管理机制的情况下无限膨胀;此外还分别记录了调试日志陷入无限循环导致单个文件超过20GB、后台任务输出文件16分钟内膨胀到324GB、macOS环境下 ~/.claude/debug 与 MCP 日志缓存路径累积至约472GB等案例。社区中也有要求对会话日志(~/.claude/projects/*.jsonl)进行自动压缩的功能请求,甚至出现了专门用于清理 ~/.claude 磁盘占用的开源TUI工具。

换言之,这更应被解读为多家公司在相近时期采用相似架构、犯下相似错误的信号,而非某一家厂商的孤立缺陷。智能体越是自主地规划和执行,记录"做了什么"所需的数据就越呈指数级增长,而管理这些记录的策略,尚未跟上工具成熟度的步伐。

4. 实际引发的问题 - 从磁盘耗尽到备份污染

会话日志膨胀远不止"占用一些空间"那么简单,还会牵连出多个实际问题。

4.1 磁盘耗尽与任务中断

最直接的后果是磁盘空间耗尽。一旦卷占满,编程智能体本身会停止运行,共享同一磁盘的其他应用,严重时甚至操作系统的登录或启动都可能受到影响。

4.2 系统性能下降

数百GB规模的文件持续生成与修改,会通过文件系统索引开销、备份软件的变更检测、磁盘碎片化等途径拖慢整体系统响应速度。有媒体报道称,某个时期的日志记录方式引发了远超预期的写入频率,可能影响SSD寿命,但这一说法尚未经过广泛的独立验证,与其断言为事实,不如将其视为"写入频率可能异常升高"的一种可能性来看待。

4.3 备份污染与备份成本上升

如果使用会整体备份主目录的个人备份工具或云同步服务,一个数百GB的日志文件夹就会原样被纳入备份范围,同时拉长备份耗时、推高存储成本。真正需要恢复数据时,无用的会话日志占据备份容量的大部分,这种情况完全可能发生。

4.4 隐私与安全暴露面扩大

会话日志中可能原样保留智能体读写过的文件内容、执行过的命令,有时甚至包括环境变量或API响应。日志越大、放置时间越长,可能暴露敏感代码或凭证的文件就在无人主动管理的状态下越积越多。日志容量问题归根结底也是数据处理范围的问题。

5. 应对与防御守则 - 现在就该检查和设置的事项

彻底解决要靠厂商,但用户这一端也有能立即采取的措施。

5.1 先弄清日志存放在哪里

首先确认所用的AI编程CLI把会话、日志、缓存存放在何处。在官方文档或配置文件中找到存储路径,再用 du -sh 或交互式工具 ncdu 定期查看该文件夹的实际占用,是最基本的第一步。

5.2 定期清理,但不要触碰正在运行的会话

先清理没有恢复计划的旧会话。若在写入进程仍存活时强行删除,文件可能损坏或无法恢复,因此应先终止相关进程,再进行清理。

5.3 自行设置轮转与保留策略

如果工具本身未默认提供,可用 logrotate 这类通用日志轮转工具定期压缩、归档旧日志,或设置在一定期限后自动删除。依赖手动删除,最终往往会被遗忘。

5.4 通过配置将日志记录降到最低

如果工具提供降低或关闭详细(verbose/trace)日志级别的选项,平时应保持在最低级别,只有确实需要调试时才临时调高。具体的配置项与环境变量因工具和版本而异,应先查阅所用版本的官方文档确认。

5.5 持续监控磁盘占用

设置磁盘使用率达到80%~90%时发出提醒的阈值,即便膨胀正在发生,也能避免"磁盘占满导致无法进行任何操作"的最坏局面。若是团队协作,也可以把开发者工作站的磁盘指标接入已经在使用的基础设施监控体系,比如 Prometheus 搭配 node_exporter 的组合。

5.6 用符号链接隔离到独立磁盘卷

如果预计会话、日志文件夹会持续增长,可以一开始就把实际目录放在空间充裕的独立分区或外接磁盘上,主目录中只保留符号链接,从而保护系统卷不受影响。

5.7 用 .gitignore 阻止误提交

如果某个工具会在项目文件夹内部或附近生成会话、日志、缓存目录,务必将该路径加入 .gitignore,以防大体积日志文件被误提交。一旦大文件被提交,后续从历史记录中清除会麻烦得多。

6. 可观测性债务与日志卫生 - AI智能体时代的一般教训

这起事件留下的更大教训,并非某一工具的bug,而是「可观测性债务(observability debt)」这个概念。在传统软件里,日志是人用来诊断问题的辅助材料,以相对可预测的速度累积。而一个自主进行规划、执行、重试的智能体,人很难提前估算它会生成多少事件——会派生多少子智能体、工具输出会被重复利用多少次,很大程度上取决于具体任务内容。

正如放任技术债不管,日后需要偿还的成本会越滚越大,放任日志与缓存管理不管,某一刻就会以磁盘耗尽的形式收到账单。AI智能体时代的日志卫生,已不再是"偶尔删一个文件夹的习惯",而应作为开发环境运维的正式事项来对待——这是本次事件留下的实务结论。

7. 厂商需要改进的方向

仅靠用户端的应对难以从根本上解决问题。梳理社区issue追踪器中反复被提出的诉求,大致包括:为会话、日志目录设置默认的保留期限与容量上限;超过阈值时向用户发出警告;默认内置能自动清理压缩历史与重复事件的轮转、压缩功能;以及将诊断与清理命令作为官方CLI功能内置提供。目前的现状是用户必须自己翻查目录才能发现问题,但随着自主智能体日益成为标准开发工具的一部分,这些安全机制应当从"可选项"变为"默认值"。

8. 与并行智能体、会话可视化工具的关联

这一问题也与近期讨论过的其他话题相互呼应。正如把多个AI智能体放进同一个仓库并行运行的模式一文所指出的,扩大并行会话数量在提升处理速度的同时,也会以相近的倍数提高会话日志的累积速度。工作树(worktree)、容器可以阻止文件冲突,但日志膨胀是需要单独管理的另一条轴线。

另一方面,像把 Claude Code、Cursor、Codex 会话汇总一处以搜索并追踪成本的 AgentsView 这类本地看板,解决的是"一眼看清多个工具会话"的可见性问题,但它本身并不能阻止磁盘膨胀。更现实的做法,是把引入这类工具当作一个契机,先确认"我目前的会话日志到底累积了多少"。可视化工具与清理、轮转策略并非彼此替代,而是相辅相成的关系。

结论:日志也应像代码一样被管理

Codex CLI 子智能体会话日志膨胀事件,并非某一款工具的一次失误就能画上句号的故事。如今自主规划、执行的AI编程智能体已成为标准工作流程,记录这一过程的日志与缓存在缺乏控制的情况下持续累积的结构,正在多家厂商身上共同出现。今天可以采取的实用行动可归纳为三点:第一,亲自确认目前使用的AI编程CLI把会话、日志存放在何处、堆积了多少;第二,现在就设置好轮转、保留策略与磁盘监控;第三,定期查阅厂商文档与issue追踪器,留意新版本中是否改进了默认设置。像审查代码一样审视"自己的开发环境留下了什么",正在成为AI智能体时代的一项新的基本功。
