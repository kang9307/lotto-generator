序論: 2026年のシグナル - 「速いAIコーディング」の幻想から覚める人たち

本記事が公開された2026年5月ごろ、開発者コミュニティで再びよく見かけるようになった問いは「AIツールでどう速くコードを書くか」ではなく、「AIを使っているのになぜコード品質は期待ほど良くならないのか」だった。しばらくの間、多くの技術イベントのメッセージは「AIで開発速度を何倍に」だったが、今はまさにその速度が残した運用欠陥・説明できない抽象化・一貫性が壊れたコードベースに直面した開発者たちが、正反対方向の問いを立てている。「同じAIツールをより遅く、より意図的に使ってより良いコードを書く方法は何か」がその問いである。速いという体感と実際の測定が食い違いうることを示す公開研究もある。その内容は下の「速度 vs 品質」の節にまとめた。

本記事の直接の契機は、2026年5月26日に韓国の技術コミュニティGeekNews(news.hada.io)で紹介された「AIを使ってより良いコードをより遅く書く」だ。原文は開発者Nolan Lawsonが2026年5月25日に自身のブログに書いた "Using AI to write better code more slowly" で、Hacker NewsとLobstersでも議論が続いた。原文の要旨は、AIコーディングを「かろうじて通るコードを大量に吐き出し、検証せずにマージすること」とだけ捉える必要はなく、LLMは柔軟なので品質の高いコードをより遅く書くことにも同じようにうまく使える、というものだ。原文が紹介する方法は、Claudeのサブエージェント、Codex、Cursor Bugbotなど複数のモデルでPRを相互レビューして誤検知を除き、深刻度criticalとhighの項目だけを直し、エージェントに変更がどう動きどう失敗しうるかを尋ねるというものだ。興味深いのは、この流れがAI懐疑論ではないという点だ。AIを多く使う人が先に「速くより遅く」を口にしている。これが本記事がこの流れを真剣に受け取る理由である。

本記事は二つのことを行う。第一に、速いAIコーディングが生む5つの落とし穴を整理する。第二に、同じAIツールで遅く深く使う7つの原則、実践を点検する3つの個人指標、AI委任と人間責任の境界マトリクス、そして日本のSI・スタートアップ環境に合わせた適用方法を提示する。5つの落とし穴と7つの原則は原文の要約ではなく、原文の問題意識をもとに本記事が整理した経験則と推奨であり、効果を数値で測ったものではない。本記事は「AIを使うな」と言っているのではない。正反対だ。「AIをより良く使う方法は、より速くではなく、より深く」という主張であり、1986年にイタリアで始まったスローフード運動がファストフードへの反対から出発し、「良い食事の定義」を書き換える方向へ進んだのと似ている。

AIコーディングの「速さの罠」5つ

速いAIコーディングが生むコストは、次の5つのパターンに整理できる。同じ根から出るが、それぞれの落とし穴が単独でも十分な損失を生む。

落とし穴1) 検証なき高速マージ

最も多く、最も高くつく落とし穴だ。AIが作ったコードが「動くように見える」のでそのままマージされる。ユニットテストが通ったことを理由に疑いなくメインへ送る。チーム単位の統計にも同じ方向のシグナルがある。DORAの2025年レポートは、AI導入がデリバリーのスループットとは正の関係に転じたものの、デリバリーの安定性とは依然として負の関係にあると報告した。速いマージは欠陥率を直接押し上げ、欠陥はホットフィックスPRとロールバックPRを生んで再びマージ速度の統計を膨らませる。ダッシュボードの速度の数字は良く見えても、実際の価値は足踏みしていることがある。

落とし穴2) 知らない抽象化の導入

二つ目の落とし穴は、AIが提案したライブラリ・デザインパターン・抽象化を開発者が十分に理解しないまま導入することだ。AIは「この問題にはStrategyパターンが適しています」と提案し、開発者はなぜ適しているのかを検証せずに受け入れる。6カ月後にその抽象化を修正または除去する必要が生じたとき、導入した開発者も他のメンバーも、なぜそれが存在するのかを説明できない。コードベースに「理由なきパターン」が蓄積し、保守コストは急速に上がる。

落とし穴3) AIが作ったパターンがコードベースの一貫性を壊す

三つ目の落とし穴は、AIが毎回異なるパターン・命名規則・エラー処理を提案することだ。AIは「各問題に対する合理的な答え」を出すが、「このコードベースの中で他コードと一貫した答え」は出さない。結果として同じ仕事をする関数がコードベースの場所により全く異なる姿になる。一貫性はコードベース最大の資産であり、管理されないAI利用はその資産を速く侵食する。ファイルごとに姿が違えば、新規入社者がコードベースに慣れる時間もそれだけ長くなる。

落とし穴4) 学習脱落(理解せず使う)

四つ目の落とし穴は最も長期的に高いコストだ。AIが速くコードを作ってくれるほど、開発者は「なぜこれが動くのか」を尋ねなくなり、学習が止まる。ジュニア開発者は短期産出量は増えるが、2〜3年後にシニアへ飛躍する力量が追いつかない。シニア開発者は自分の強み領域(設計・ドメイン理解)外の技術をもはや学ばなくなる。AI時代の本当のリスクは「AIが仕事を奪うこと」ではなく「AIのせいで学ばなくなること」である。

落とし穴5) トークンコスト増 + 利得は増えず

五つ目の落とし穴は運用コスト側だ。速いAIコーディングを追求するほどトークン使用量が増える。一回で決めず、AIにより頻繁に、より長く尋ね、コンテキストを毎回新たに注入する。だがトークンコストが2倍になってもコード品質は2倍にならない。原文の筆者もトークンを大量に使うと明かしているが、そのトークンを機能を速く出すためではなく、計画そのものが誤っていると早く気づくために使っている。トークンコスト増は活動の増加であり、それだけでは価値の増加ではない。差を生むのはトークンをどこに使うかだ。

「遅く、よりよく」の7原則

上記5つの落とし穴から抜け出す方法は何か。本記事が推奨する7原則を整理する。全て同じAIツールをそのまま使いながら、使用パターンだけを変えて適用できる。

原則1) AI出力を必ず一度書き直す

最も単純だが最も強力な原則だ。AIが作ったコードをそのままマージせず、自分の手で一度書き直す。変数名一つ、関数分割一つ、コメント一行でも手が入る。この一サイクルが二つを同時に行う。第一に、AI出力の欠陥を見つける機会がもう一度生まれる。第二に、そのコードを「理解した」状態でマージすることになる。6カ月後に修正が必要なとき、自分で説明できるコードだけがコードベースに残る。

原則2) コンテキストを事前に明示的に与える

二つ目の原則はAIに尋ねる前に5分使ってコンテキストを整理して与えることだ。「このコードベースは関数型スタイルに従う」「エラーはResult型で扱う」「外部HTTPはaxiosだけを使う」など制約を最初のプロンプトに刻む。AIにコンテキストを与えないとAIは毎回異なるパターンを提案し、その結果が落とし穴3(コードベース一貫性破壊)を作る。コンテキスト提供は一回の5分投資で長期間の一貫性を買う。

原則3) 小さな単位で検証

三つ目の原則は一度に大きなコードを受け取らないことだ。「APIエンドポイント全体を作って」ではなく「この関数のシグネチャだけ」「次に本文を」と段階を区切る。各段階で検証し、理解した後に次へ進む。大きな単位のAI出力は欠陥が埋もれて見えず、小さな単位のAI出力は欠陥が即座に見える。単位が大きくなるほど検証が急に難しくなる、というのがこの原則の根拠だ。

原則4) AIに「なぜ」を尋ねる

四つ目の原則はAIが作ったコードに対して「なぜこの方式か」を明示的に再質問することだ。「なぜMapを使ったのか」「なぜtry-catchをこう配置したのか」「なぜこのライブラリか」とAIに投げて答えを得て、その答えに自分が同意するか確認する。AIの答えが弱ければ別方式で再生成させる。原文が勧めるように「この変更はどう失敗しうるか」を尋ねるのも同じ原則だ。この一サイクルが落とし穴4(学習脱落)を直接防ぐ。理解しないままマージしたコードは自分のコードではない。

原則5) 規約を強制せず推論させる

五つ目の原則は少し逆説的だ。AIに規約を明示的に指示する(「このコードベースはcamelCase」)よりも、コードベースの一部を見せてAIに推論させる(「これらのコードを見て規約を整理し、その規約に従って新規コードを作って」)方が一貫性を保ちやすい、というのが本記事の判断だ。規則リストから漏れた細部まで実際のコードが示してくれるからだ。規則リストより実際のコード例の方が、AIにとってより明確なシグナルになることが多い。

原則6) 新パターン導入前に正当化を要求

六つ目の原則は落とし穴2(知らない抽象化導入)の直接対応だ。AIが新しいデザインパターン・ライブラリ・抽象化を提案したら即座に受けず、「なぜコードベースの既存パターンが不十分か」をまず説明させる。AIが説得力のある答えを出せなければ導入しない。本記事が推奨するルールのうち、技術負債の蓄積を遅らせるのに最も直接的なのがこれだ。「なぜ必要か説明できなければやらない」というシニアの基本姿勢をAI提案にも同じく適用する。

原則7) 毎週自分のAI使用パターンを点検

七つ目の原則はメタ原則だ。毎週金曜15分、その週にAIをどう使ったかを振り返る。「そのままマージしたPRが何件か」「AIに『なぜ』を尋ねた回数は何回か」「AI出力を一度書き直した割合は何%か」を数える。この点検がなければ上の6原則は簡単に崩れる。スローAIコーディングをしていると言うことと実際にしていることは違い、その差は測定なしにはなかなか見えない。

速度 vs 品質 - 公開研究が示すこと

上記7原則を適用すると短期速度は本当に落ちるか。本記事は公開当初、独自の比較表を載せていたが、出典を示せない数値だったため2026-09-29の更新で削除した。代わりに公開研究を整理する。いずれも「速いと感じること」と「実際のデリバリー成果」は違いうることを示している。

研究 対象・方法 結果 読むときの注意点
METR (2025-07)熟練オープンソース開発者16人、課題246件のランダム化比較試験AIを許可した課題の方が19%長くかかった。参加者は事前に24%の短縮を予想し、終了後も20%速くなったと信じていたMETRはこの結果をソフトウェア開発全般や別の使い方に広げて読まないよう述べている
DORA 2024レポート (2024-10)技術職への調査に基づく統計的推定AI導入の増加とともにデリバリーのスループットが約1.5%、安定性が約7.2%低下と推定。AI導入が25%増えるとドキュメント品質7.5%、コード品質3.4%、コードレビュー速度3.1%向上と推定調査に基づく推定で因果を断定するものではない。回答者の3分の1以上はAIで生産性が中程度以上上がったと回答
DORA 2025レポート (2025-09)約5,000人への調査と100時間以上の定性データAI導入はデリバリーのスループットとは正の関係に変わったが、安定性とは依然として負の関係。回答者の90%が業務でAIを使用80%以上が生産性が上がったと考える一方、30%はAI生成コードをほとんど、または全く信頼していない
METR追加発表 (2026-02)2025年後半の新しい実験(開発者57人、課題800件以上)約20%の減速という以前の結果は古くなり、現在は速度向上の可能性が高そうだと表明AIなしで働きたくないと参加を断る開発者が増えた選択バイアスのため新しい結果は信頼しにくいとして、実験設計を変更中

この表から本記事が読み取るのは二つだ。第一に、体感は信頼できる測定手段ではない。METRの参加者は遅くなっていたのに速くなったと感じていた。第二に、個人が速くなったという感覚とチームのデリバリー成果は別の層だ。DORA 2025はスループットが伸びる流れの中でも安定性は依然として下がる関係を報告し、AIは自動テスト・バージョン管理・速いフィードバックといった土台が弱いチームの問題を増幅すると説明した。逆に、METRの2026年の発表のように、ツールが良くなるにつれて速度の利得が大きくなっている可能性もある。だから結論は「AIは遅くする」ではなく「1日の体感ではなく、より長い期間のデリバリー成果で測れ」だ。本記事がAI効果測定の基本単位を四半期以上にするよう勧める理由である。

高品質AIコーディング時のROI測定 - 1週・1カ月・1四半期

スローAIコーディングを追求するときROIをどう測るか。本記事が推奨する時間単位別の指標を整理する。

1週: 学習指標中心

1週単位はコード産出量を測らず学習指標を見る。(a)新たに理解した概念・ライブラリ・パターン数、(b)AIに「なぜ」を尋ねた回数、(c)AI出力を一度書き直した割合。この3指標が毎週安定していればスローAIコーディングが実際に作動しているシグナル。

1カ月: 価値PR比率

1カ月単位はマージされたPRのうち「価値PR」(新機能、ユーザーに見える変化)と「ホットフィックスPR」(自分が作った欠陥の修正)の比率を見る。全てのチームに当てはまる正解の比率はない。チームの過去の値と比べて、ホットフィックス側に傾いていないかを見る。同じマージ数でも比率が違えばビジネス価値は全く違う。

1四半期: 運用欠陥率とビジネスKPI

1四半期単位は運用欠陥率の推移と会社のコアビジネスKPI(売上転換、リテンション、NPS)との相関を見る。スローAIコーディングが作動していれば期待される姿は、欠陥率の推移が平坦または低下し、ビジネスKPIが上昇基調を保つことだ。欠陥率が四半期ごとに急上昇しているのにKPIが横ばいなら、速いAIコーディングに傾いたシグナルだ。

AIに委任する仕事 vs 人間が責任を持つ仕事マトリクス

スローAIコーディングの本質は「AIを使わないこと」ではなく「AIに委任する領域と人間が責任を持つ領域を明確に分けること」だ。本記事が推奨する4象限マトリクスを示す。

高価値/低頻度(設計・コアロジック) 低価値/高頻度(ボイラープレート・テスト)
人間主導人間が直接決定、AIは検証・代替案提示のみ(ここに時間を使わない)
AI主導(絶対委任禁止)AI完全委任、人間は結果検証のみ

このマトリクスの核心は左上(高価値・人間主導)と右下(低価値・AI主導)だ。左下は時間の無駄、右上はAI時代の最も危険な落とし穴だ。AIが最も得意な領域で人間が時間を使わず、人間が最も得意でなければならない領域でAIに委任しないことがスローAIコーディングの本質だ。

「slow code」運動の意味 - 1980 vs 2026

本記事がこの流れを「スローコード」運動と呼ぶのは、1986年にイタリアで始まったスローフード運動と構造が似ているからだ。スローフードは、カルロ・ペトリーニがローマのスペイン階段近くにマクドナルドが開店することに反対して作った前身団体Arcigolaから始まった。しかし反対にとどまらなかった。地域の食と伝統的な調理を掲げて「良い食事の定義」を書き換え、1989年には15カ国の代表がパリで国際宣言に署名して国際運動となった。

2026年のスローコードも似た道をたどる。速いAIコーディングへの反省から出発するが、AIコーディングそのものは否定せず、「良いコードの定義」を書き換える。良いコードは速くマージされたコードではなく、6カ月後にも自分で説明できるコード、新規入社者が理解できるコード、運用で欠陥を生まないコードだ。AIはこの定義の脅威ではなく、この定義を達成する最も強力な道具になりうる。ただし、その道具を遅く、意図的に、学習しながら使うときに限る。

シニア vs ジュニア - 同じ原則、異なる適用

上記7原則は全ての開発者に同様に適用されるが、シニアとジュニアが強調すべき原則は異なる。

シニアが最も強調する原則

シニアは原則2(コンテキスト明示)、原則5(規約推論)、原則6(新パターン正当化)を強調する。シニアは既にコードベースをよく知っているため、コンテキストを明示的にAIに渡すことが最も大きな効果を生む。またシニアは「このコードベースの規約」を最もよく知る者なので、その規約をAIに推論させるプロンプト設計で最大の価値を生む。新パターン導入の正当化はシニアの基本責務だ。

ジュニアが最も強調する原則

ジュニアは原則1(一度書き直す)と原則4(なぜを尋ねる)を強調する。ジュニアの最大リスクは学習脱落であり、この2原則が学習脱落を直接防ぐ。AI出力を一度書き直す過程でそのコードがなぜそう書かれたかを学び、「なぜ」を尋ねる過程でAIを学習ツールに変える。原文の筆者も、AIレビューが見つけた競合状態が実際の問題か理論上の問題かを見分けるのは経験の浅い開発者には難しいと指摘している。だからAIが見つけた問題は一人で判定せず、シニアと一緒に分類する方がよい。AIを学習ツールとして使うジュニアは、AIなしで働くときより速く学べる、というのが本記事の判断だ。

日本SI・スタートアップ環境への適用

日本IT市場にはスローAIコーディングを適用しにくくする構造的圧力がある。3つの圧力とそれぞれの対応を提示する。

第一に、SI市場の人月・行単価構造だ。行数が売上に直接結びつくため、速いAIコーディングが短期売上を膨らませる。対応は社内ででも「行数以外の指標一つを並行して報告する」ことだ。欠陥率、レビュー時間、運用事故数のうち一つでも並べれば、速いAIコーディングのコストが可視化される。

第二に、スタートアップの短い意思決定サイクルだ。四半期単位の測定を待つ時間がなく、1週・1カ月指標だけを見る。対応は1週単位では学習指標を、1カ月単位では価値PR比率を見ることだ。四半期単位の欠陥率推移は四半期ごとに一度確認すれば十分だ。

第三に、階層的意思決定文化だ。役員が「AI効果報告書」を要求すると実務者は役員が聞きたい行数と満足度を作る。対応は本記事の「速度 vs 品質」の表を報告書に併載することだ。「参加者は20%速くなったと感じたが、実際には19%長くかかった」(METR 2025)のような公開データをチームの1日指標の横に置けば、意思決定者も体感の数字に揺らぎにくくなる。

落とし穴 - 「遅く」が怠慢の正当化に化ける5パターン

スローAIコーディング最大のリスクは「遅く」が怠慢の正当化に化けることだ。5つのアンチパターンを事前に示しておく。

  1. 「慎重だから遅い」と言いながら学習はしない: 原則4(なぜを尋ねる)と原則7(週次点検)をしないまま「自分は慎重」と言うパターン。
  2. 「検証中」と言いながら検証結果を記録しない: 原則1(一度書き直す)のサイクルは回したが何を発見したかの記録がない。
  3. 「品質優先」と言いながらビジネスKPIに無関心: スローAIコーディングの目的はビジネス価値であってコードそのものではない。ビジネスKPIを見なければスローコーディングがスロービジネスになる。
  4. 「AIに頼らない」と言いながらボイラープレートも自分で書く: マトリクス右下(低価値・AI主導)を人間が直接やれば時間の無駄。
  5. 「学習中」と言いながら産出物がない: 学習は産出物の中で起こるのであって産出物の代替物ではない。1週でマージされたPRが0件なら学習ではなく停滞。

個人測定 - 3つの指標(コード品質、学習量、満足度)

自分のAI使用パターンを測る最も単純な方法は、毎週金曜に3指標を1行ずつ記録することだ。公開された基準値はないので、絶対値より自分の推移を見る。

指標1) コード品質(24時間ホットフィックス率)

今週マージしたPRのうち、マージ後24時間以内にホットフィックスPRが付いた割合。この比率が4週の推移で上がれば速いAIコーディングに傾いているシグナルであり、低く保たれていれば検証サイクルが機能しているということだ。

指標2) 学習量(新概念数)

今週新たに理解した概念・ライブラリ・パターン数。1行ログで十分(「今週: TanStack QueryのstaleTimeとcacheTimeの違いを理解」)。スローAIコーディングが作動していれば着実に積み上がり、何週も0が続くなら学習が止まったシグナルだ。

指標3) 満足度(自己説明可能性)

金曜に「AIなしで今週マージしたコードを書き直せるか」を1〜10点。10点なら完全理解、点数が低いほどAIに頼っているということだ。この点数が数カ月にわたって下がれば、力量がAI依存で弱まっているという最速のシグナル。

結論 + 即時適用可能な3つ

本記事の一文結論はこうだ。AI時代の正しい問いは「どれだけ速くなったか」ではなく「同じ時間をどこに再投資するか」だ。AIが作った時間を検証と学習に再投資すれば6カ月後により良いコードとより良い開発者が残る。その時間をより多くのマージに使えば6カ月後により多くの欠陥とより浅い開発者が残る。同じツール、異なる結果を作るのは道具ではなく使用パターンだ。

本記事が推奨する即時適用可能な3つは次のとおり。

  1. 今週マージする全てのPRに原則1(一度書き直す)を適用する。AIが作ったコードをそのままマージせず、変数名・関数分割・コメントのうち一つでも手が入るようにする。本記事の推奨の中で最も小さく、すぐに始められるものだ。
  2. 毎週金曜15分、上記3つの個人指標を1行ずつ記録する。24時間ホットフィックス率、新概念数、自己説明可能性1〜10点。4週記録するだけで自分のパターンが明確になる。
  3. 次の四半期AI効果報告書に1日指標と1四半期指標を併記する。単一時点比較ではなく時間単位別推移を並べると、意思決定者が短期数字に揺らがなくなる。

本記事はコントラリアンだが反対意見ではない。AIコーディングの本当の価値を見るには測定単位を変える必要があるという主張であり、測定単位を変えれば自然に使用パターンが変わる。公開当時(2026年5月)の本記事の見通しは、2026年後半に生き残る開発者とチームは最も速くAIを使った側ではなく最も深くAIを使った側だろう、というものだった。本記事がスローAIコーディングに見る最大の価値は結局これだ。同じ道具を一度多く遅く使うことが、最速の学習であり最速の品質である。

# スローAIコーディング - 週次チェックリストと判断表

基準日: 2026-09-29

以下の原則と指標は測定された効果ではなく、本記事の推奨である。公開研究の数値は4節に出典とともにまとめた。

---

## 1. PRマージ前チェックリスト(7原則)

- [ ] AIが作ったコードを一度手で書き直した(変数名・関数分割・コメントのいずれか一つ以上)
- [ ] 最初のプロンプトにコードベースの制約を書いた(スタイル、エラー処理、使用可能ライブラリ)
- [ ] 大きな塊ではなく小さな単位(シグネチャ → 本文)で受け取り、段階ごとに検証した
- [ ] AIに「なぜこの方式か」と「この変更はどう失敗しうるか」を尋ねた
- [ ] 規約をルールで指示せず、既存コードを見せて推論させた
- [ ] 新しいパターン・ライブラリ・抽象化は「既存パターンはなぜ不十分か」への答えを得てから入れた
- [ ] このコードをAIなしで説明し直せる

---

## 2. 金曜15分の記録フォーム

公開された基準値はない。絶対値より自分の4週の推移を見る。

| 週 | 24時間ホットフィックス率 | 新たに理解した概念数 | 自己説明可能性(1〜10) | そのままマージしたPR数 | 「なぜ」を尋ねた回数 |
|---|---|---|---|---|---|
| 1週目 | | | | | |
| 2週目 | | | | | |
| 3週目 | | | | | |
| 4週目 | | | | | |

読み方:
- ホットフィックス率が上昇傾向 → 速いAIコーディングに傾いている
- 新概念数が何週も0 → 学習が止まっている
- 自己説明の点数が数カ月かけて下がる → 力量がAI依存で弱まっている

---

## 3. 委任の判断表

| | 高価値・低頻度(設計、コアロジック) | 低価値・高頻度(ボイラープレート、テスト) |
|---|---|---|
| 人間主導 | 人間が決定、AIは検証・代替案提示のみ | 時間の無駄 - やらない |
| AI主導 | 委任禁止 | AIに委任、人間は結果だけ検証 |

---

## 4. 報告書に併載する公開研究(2026-09-29確認)

| 研究 | 主な結果 | 注意点 |
|---|---|---|
| METR 2025-07(16人、246件のRCT) | AI許可の課題が19%長くかかった。事前予想は24%短縮、事後の体感は20%短縮 | ソフトウェア開発全般に広げて読まない |
| DORA 2024 | AI導入の増加とともにスループット約1.5%、安定性約7.2%低下と推定 | 調査に基づく推定 |
| DORA 2025 | スループットとは正の関係に変わったが、安定性とは依然として負の関係 | 回答者の30%はAI生成コードをほとんど、または全く信頼していない |
| METR 2026-02 | 以前の減速の結果は古くなり、速度向上の可能性が高そうだと表明 | 選択バイアスで新結果は信頼しにくいとして設計変更中 |

報告の原則: 1日の体感の数字と四半期単位のデリバリー成果(欠陥率・安定性)を同じページに置く。

---

## 5. 「遅く」が怠慢になっているサイン

- [ ] 「慎重」と言いながら「なぜ」も尋ねず、週次点検もしない
- [ ] 「検証中」と言いながら何を見つけたかの記録がない
- [ ] 「品質優先」と言いながらビジネスKPIを見ない
- [ ] 「AIに頼らない」と言ってボイラープレートまで手で書く
- [ ] 「学習中」と言いながら一週間にマージしたPRが0件

---

正しい問いは「どれだけ速くなったか」ではなく「AIがくれた時間をどこに再投資したか」だ。
