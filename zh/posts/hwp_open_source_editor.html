打开HWP与HWPX的开源桌面应用HOP - 以及封闭文档格式的替代方案地图

写给必须在macOS上、在Linux上、在自动化脚本里处理韩文文档的人：把眼下可用的选择画成一张地图

2026年8月16日 IT/技术

引言：一个附件让一天停摆的瞬间

一份扶持项目的公告发来了，扩展名是.hwp。手上的笔记本是MacBook，办公室的服务器跑Linux，此刻拿着的是平板。折腾几分钟之后，最后还是去找人要一张截图。凡是与韩国打交道的人多半都遇到过这一幕，而令人意外的是，2026年它依然在发生。

自2026年5月18日起，韩国行政机关新建的电子文档开始适用开放文档格式，方向已经明确。但规定改变并不会让共享盘里堆着的旧文件自动打开，学校、协会与业务伙伴之间往来的文档更在规定之外。所以现在真正需要的不是又一篇政策解读，而是一张地图：哪种工具能走到哪里，从哪里开始走不动。

本文就来画这张地图。先简要交代格式的结构，再按性质把替代方案分门别类，然后把最近公开的开源桌面应用HOP放进这张地图，只写能够确认的范围。结尾回到实务问题：要长期保存一份文档，或者要把它发给别人时，究竟该选什么。

1. HWP与HWPX只是名字相近

很多人把这两个扩展名当成同一样东西的新旧版本，实际上它们是容器本身不同的两种格式。缺了这个区分，你既解释不了「换成HWPX了怎么还是打不开」，也解释不了「是HWPX啊怎么一下就开了」。

1.1 HWP 5.0 — 二进制容器一系

HWP 5.0建立在称为CFB(Compound File Binary)的容器之上。可以把它想成一个文件里装着一套微型文件系统：若干数据流按目录结构排列，每个流里放二进制记录，压缩与加密可以作为选项加上去。以当年的桌面文字处理器而言，这是合理的工程选择。问题在于，要取出内容就必须先有实现那套二进制规则的代码。用文本编辑器打开，什么都看不到。

1.2 HWPX — XML包一系

HWPX遵循国家标准KS X 6101所定义的开放文字处理标记语言，即OWPML。物理上它就是一个ZIP归档，里面装着XML文档。把扩展名改成.zip解压开，正文就以文本形式呈现。这与ODF(.odt)和OOXML(.docx)是同一种思路。

这里先厘清一个误解。格式开放与所有工具渲染出同样的版面，是两回事。读XML把文字和表格取出来并不难，但要让这些文字落在与原程序相同的位置、按相同的方式换行，那是排版引擎的领域。格式公开解决的是前半段，后半段由每个实现各自去打。本文后面所有关于「能走到哪一步」的判断，都建立在这个区分之上。

格式容器标准依据仅解压即可取文本主要用途
HWP 5.0CFB(二进制复合文件)厂商规格不可既有韩文文档的大多数
HWPXZIP + XMLKS X 6101(OWPML)可以公共新建文档与自动化
ODF(.odt)ZIP + XMLISO/IEC 26300可以国际通行的开放办公文档
OOXML(.docx)ZIP + XMLISO/IEC 29500可以民间与跨境往来文档
PDF固定版面ISO 32000有限分发、打印与保存

2. 为什么这种格式在公文里留了下来

只从技术角度看会觉得难以理解：明明有更开放的格式，为什么不换。答案不在文件里，而在公文格式与办事流程里。

行政文档不是自由写作。签批栏有几格、附件清单怎么编号、表格里再套表格、页码与骑缝章的位置，全都固化成了公文样式，而这些样式是在某一款文字处理器的排版能力之上设计出来的。在这种情况下换格式，换的不是文件，而是几十年积累下来的样式资产，以及围绕这些样式接上去的文档管理系统。这不是一个经办人拍板就能定的规模。

这也不必看作韩国独有的怪现象。在日本，一太郎长期深入政府机关与教育现场；在中国，WPS一系占据着类似位置。凡是本国文字排版更讲究的语言区，本土办公软件往往在早期就跑在了前面，随之形成的样式惯性到哪里都同样沉重。锁定不是格式造成的，而是建立在格式之上的业务流程造成的。

  • 样式资产 — 各机关积累的签批、公函、台账样式依赖特定排版能力。
  • 系统耦合 — 文档管理与电子签批系统是按某种格式接上去的。
  • 培训与习惯 — 经办人手上已经练熟的快捷键与工作流本身就是迁移成本。
  • 对外提交 — 受理方要求什么格式，什么格式就是标准，提交者没有选择权。
  • 历史文档 — 新格式切换之后，既有归档仍旧停在原处。

3. 2026年5月18日，规定真正改变了什么

《关于行政业务运营与革新的规定》修订案于2026年5月12日通过国务会议，并自5月18日起施行。要点有两条：行政机关制作电子文档时须遵循开放文档格式；中央与地方的On-Nara文档系统上传的附件仅限开放格式。官方同时提出的目标之一是让人工智能能够直接提取并分析数据，同一次修订还包含为外籍居民努力提供表单与文档外文版本的条款。

这些是改变了的部分。在实务上，弄清楚没有改变的部分更有用。

  • 已经产生的几十年文档仍保持原格式，并没有溯及既往的转换义务。
  • 学校、协会、企业与个人之间往来的文档不在该规定适用范围内。
  • 即便格式变成了XML，也不等于你的MacBook就能把文件渲染出来。读取工具依然必不可少。
  • 各机关落地速度并不一致，提交之前查一下受理方的说明仍是稳妥做法。

政策背景与AI处理视角在AI时代的韩国文档格式与开放标准课题里另有讨论。本文站在那之上，专注于工具地形。

4. 格式封闭时真正付出的代价

说「不方便」是不够的。代价分成四支，各自记在不同人的账上。

4.1 跨平台 — 挡在门外的是人，不是设备

macOS、Linux与移动端用户打不开文档，并不是口味问题。读不到扶持项目公告就少了一次申请机会，家长打不开学校通知，信息就在那里断掉。看上去是开发者个人的烦恼，实质上是信息获取上的落差。

4.2 长期保存 — 二十年后还有人打得开吗

保存的核心永远归结为一个问题：二十年后还存在能读这个文件的代码吗。规格已公开、且有多个独立实现的格式，答案更接近「有」。只依赖某个产品某个版本的格式，则把文档的寿命与产品的寿命绑在了一起。档案管理机构之所以额外准备固定版面归档规格PDF/A，原因正在于此。

4.3 无障碍 — 有没有可以交给读屏软件的文本

读屏软件必须拿到结构化文本才能朗读。表头是否被标记为表头、标题是否具备标题层级，直接决定朗读质量。扫描成图片的公文自然不行，而文本虽在却没有工具能取出来，结果是一样的。

4.4 自动化 — 最后总有人要用眼睛抄一遍

从几百份公函里抽出日期与金额做成表格，程序五分钟就能干完，前提是它读得了文件。读不了，就只能一份份打开手工誊写，错字随之混入。近来还多了一项：把文档交给对话式AI做摘要与分析，同样要能取出文本才谈得上。

5. 替代方案的地形 — 各自能走到哪一步

选择分成五支，性质各不相同，所以要问的不是「哪个最好」，而是「我的情况落在哪一格」。

5.1 官方查看器与办公产品

还原度最高的自然是定义了这个格式的产品线。这是明摆着的事实，谈不上什么指责：定义排版规则的一方，按自己的规则来画当然最准。不过发行策略与支持平台一直随时期变动，因此眼下究竟提供了什么，最好直接到发行方处确认。本文不去断定某一时点的产品阵容。

5.2 网页办公与云端查看器

有浏览器就行、无需安装，这是最大的优点。代价是文件要上传到外部服务器。涉密公函、含个人信息的名册、合同走这条路上传，很容易违反组织规定；在内外网隔离环境中它根本不是选项。方便多少，可用文档的种类就受限多少，这两面必须一起看。

5.3 办公套件的导入过滤器

这里最容易白跑一趟。LibreOffice确实内置了名为hwpfilter的HWP导入过滤器，但它实际覆盖的范围是韩文97一代，也就是3.x系列。2002年以后文档结构大幅变化的HWP 5.0系列不在其目标之内。支持更高版本的诉求以tdf#90513挂着，而与其静默读错不如检测并拒绝不兼容版本的讨论则记在tdf#70097。把「如今收到的多数文件走这条路解决不了」当作前提，反而省时间。

5.4 转换与提取库

如果目的不是给人看，而是让程序读，那么答案往往在这里。Python一侧有处理HWP系的pyhwp与专攻HWPX的python-hwpx；Rust一侧有hwp-rs、openhwp等实现。HWPX是ZIP加XML这件事在此意义重大，标准XML工具就能覆盖相当一部分工作。版面无法原样还原，但要取出文本、表格与元数据，多数场合已经够用。

5.5 开源查看器与编辑器实现

这一支不止于读，还要画到屏幕上并且能改。技术上这是最难的一支。解析只是起点，换行、字距、表格拆分、分页等排版规则得重新做一遍，屏幕才会接近原稿。HOP及其引擎rhwp就在这一格里。

分支代表读取编辑版面还原文件外传适用场景
官方产品线厂商查看器与办公套件最高视产品而定基准点无还原度优先时
网页办公与云端浏览器型服务可以视服务而定中等有临时查看内容
办公套件导入过滤器LibreOffice hwpfilter仅3.x系列转换后编辑低无很旧的文件
转换与提取库pyhwp, python-hwpx, hwp-rs文本与结构用脚本生成非目标无自动化、检索、索引
开源查看器与编辑器rhwp, HOP可以部分支持开发进行中无macOS、Linux、隔离网

6. HOP在尝试什么 — 为什么偏偏是桌面应用

HOP是一款以在macOS、Windows与Linux上查看并编辑HWP与HWPX文档为目标的开源桌面应用。它以MIT许可证公开，按2026年8月16日的确认，最新发布版本为v0.4.1，日期是2026年7月21日。

既然已经有在浏览器里跑的查看器，为什么还要另做桌面应用？答案在于与操作系统的接触面。有些事情网页查看器在结构上就做不到。

  • 文件关联 — 双击.hwp或.hwpx就直接打开的体验，浏览器坐不上这个位置。
  • 系统预览集成 — 像macOS的快速查看那样，不打开文件就先扫一眼。社区讨论中也把这一点列为优势。
  • 拖放、多窗口与打印 — 把多份文档并排比对，并直接使用操作系统自身的打印栈。
  • 内外网隔离环境 — 文件不能外传的场合，除了本地应用别无选择。

安装路径也已理顺。macOS可用brew install hop，Arch系有AUR包，直接下载则提供.dmg、.msi、.deb、.rpm与.AppImage。macOS同时支持Apple Silicon与Intel，Linux有x64与arm64构建。

7. 把引擎与应用分开看 — rhwp

评价HOP时常见的错误，是把应用与引擎当成一整块。真正解析并绘制文档的工作由另一个项目rhwp承担，HOP在外面包一层并加上系统集成。要判断某个问题出在哪一侧，就需要这个区分。

7.1 rhwp覆盖的范围

rhwp是用Rust与WebAssembly写成的HWP、HWPX查看器兼编辑器，采用MIT许可证，确认时的版本为v0.8.4。读取一侧覆盖HWP 5.0二进制格式、HWPX，以及在结构已验证的范围内的HML(HWPML 2.9/2.91)。写入一侧支持HWP、HWPX与HML，但以无损保存为原则：文档中若含有它不支持的要素，就发出警告并阻止会造成丢失的保存。这个设计对使用者很重要。说一声做不到然后停下，比悄悄压平再保存更能保护文档。

编辑功能方面列出了文本插入与删除、撤销与重做、字符与段落格式、表格创建与操作、单元格公式。渲染方面涉及行距、缩进、对齐与制表位，单元格合并与边框样式，分栏拆分以及表格按行分页。导出目标是SVG、PNG与PDF。由于会编译为WebAssembly，同一套引擎也能在浏览器中运行。

7.2 版本各走各的

HOP v0.4.0集成的rhwp版本是0.7.19，而引擎一侧此后又往前走了。也就是说，引擎里已经解决的问题，可能还没进到应用里。遇到问题时不要只看应用仓库，也要一并确认引擎仓库的最新状态。

7.3 一句诚实的话

rhwp的文档中有这样一层意思：并不把某个产品的PDF输出当作标准答案，因为输出会随工具版本与导出路径而变化，所以不把逐字节一致设为目标。我认为这种态度是这一领域里最值得信赖的信号，比标榜「兼容率百分之多少」准确得多。还原度因文档而异，你手上那类文档的数值，只能用你自己的文件才测得出来。

8. 眼下能做与不能做的(2026-08-16确认)

版本停在0.x这件事本身就说明了项目的性质：能用的区间与还不行的区间界线分明。

8.1 仓库中列为可用的

  • 打开HWP与HWPX文档
  • 以HWP格式保存与另存为
  • 导出PDF
  • 打印对话框
  • 拖放打开文件
  • .hwp与.hwpx的文件关联
  • 多窗口查看文档

8.2 不在清单上或附带条件的

  • 以HWPX格式保存 — 并未列入可用的保存功能之中，读与写并不对称。
  • Linux环境差异 — AppImage是需要时才运行的便携式分发，说明中提示某些Wayland与输入法环境下语言切换或窗口显示可能不稳定。
  • 复杂文档的还原 — 文本框相互叠压、公式与图表混排、还盖着印章图像的签批文档，对任何独立实现都是最难的一段。
  • 0.x意味着什么 — 发布说明里有修复桌面编辑回归问题的条目。这既说明它在被积极修补，也说明它还没有定型。

8.3 所以该这样用

  • 编辑与保存之前务必另存一份原件副本，这是与工具可靠性无关的基本功。
  • 重要的提交文档，最终确认要放在受理方所用的环境里做。
  • 只是查看内容、打印、导出PDF的话，眼下已经是足够实用的区间。
  • 如果必须编辑格式复杂的文档再发回去，目前仍以原产品线更稳妥。
  • 遇到打不开或显示错乱的文档，去仓库提交问题是最有效的贡献。但不要把含个人信息的真实文档直接上传，做一个能复现的最小示例附上去。

9. 未能确认的部分

把本文刻意没有下断言的项目集中放在一处。

  • 各工具的还原度与兼容率数值。未能确认公开的测定值，也没有用任何形式的估算去填补。
  • 官方查看器与办公产品在2026年8月时点的支持平台与发行策略。这一项一直随时期变动，以发行方处的确认为准更准确。
  • HOP的HWPX保存与自动保存路线图及其时间点。只确认到它不在可用功能清单中。
  • 修订规定的例外与过渡条款细节，以及各机关系统落地的进展。
  • 著作权与许可关系的法律判断。独立实现具有何种法律地位，不是本文该下结论的领域。若在商业上事关重大，应当经由专业人士评估。

10. 要长期保存或发给别人时 — 判断标准

把工具的话题讲到这里，是为了回答这一个问题，而标准可以压缩成一句话：今后是谁、用什么、为了做什么而打开这份文档。

目的首选格式同时保留理由
只要能读就行PDF原始文件在任何设备上都以同样的样子打开
对方需要编辑HWPX确认对方环境属XML一系，可处理的工具更多
十年后仍须打得开PDF/AXML系原件外观固定与内容复用两头都保住
由程序读取HWPX文本提取版解析成本低，可选工具多
向公共机关提交受理方指定格式提交件的留底受理系统比规定先生效

10.1 实务上守住就不吃亏的几条

  • 不要删掉原件。只留转换件的话，丢掉的要素再也找不回来。
  • 转换件用另一个文件名。名字里带上格式与日期，日后会救你自己一把。
  • 转换完成后立刻用眼睛核对表格、公式、文本框与印章图像，出问题的地方大体是固定的那几处。
  • 用邮件发送之前先问一句对方用什么环境，问一句的成本比重发低得多。
  • 多人传阅的文档要把编辑用与分发用分开，分发用做成PDF能减少事故。
  • 打包发送时顺手检查一下中文与韩文文件名在ZIP里乱码的编码问题；如果需要服务器自动生成文档，与其做格式转换，不如直接设计生成流水线，长期更好维护。

11. 结论：格式不是工具，而是承诺

选择文档格式与选择编辑器不同。编辑器随时可以换，格式却是与今后所有会打开这个文件的人立下的承诺。能守住这个承诺的人有多少，决定了格式的价值。

开源实现改变的并不是格式本身，而是选项。你能在Mac上打开公函，在Linux服务器上批量抽取文本，在隔离网里本地完成处理。反过来，它改变不了的也很清楚：排版引擎的细节规则、已在机构里固化的样式惯例，以及维护人力这个现实。把整条业务流程交给一个0.x版本的项目，仍然为时过早。

今天可以做的有三件。第一，挑一类你经常处理的文档，亲自确认它在你的环境里能不能打开。第二，给正在保存的重要文档再加一份PDF或PDF/A留底。第三，今后要发给别人的文档，以收件方的环境为准来选格式。仅这三件，就能大幅降低下一次因为一个附件而停摆一天的概率。
