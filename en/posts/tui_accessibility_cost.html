Looking Like Text Is Not Being Readable - Why Terminal UIs Have No Structure

Why full-screen redraws, color and box-drawing characters are not information to a machine, and what tool authors can do about it today

Aug 25, 2026 Dev & Infra

Introduction: the belief that a terminal solves accessibility

There is an old belief among developers. Web apps need accessibility work, but terminal tools are text already, so nothing extra is required. It is a convenient belief, because it asks for nothing. Recently a piece arguing the exact opposite circulated widely in developer communities, and its claim is blunt: a modern decorated terminal interface can be harder to read than a badly built graphical one, and the cause is not laziness but the rendering model itself.

The contrast the original draws is this. A traditional command-line tool is a chronological flow that appends results downward, while a terminal interface built with modern frameworks treats the window as a two-dimensional canvas and moves the cursor to many positions on every update. The original singles out a family of reactive UI frameworks, but the subject of this article is not which library is well made. It is why a gap opens between what looks like text and what a machine can read, and where that gap structurally comes from. Naming one tool as the accessibility offender and stopping there guarantees that the next tool repeats the same mistake in the same place.

The conclusion up front: a terminal screen is a grid of stamped characters, not a structure. And that single fact specifies, quite precisely, what a tool author can change in code today.

1. A terminal screen is a grid of stamped characters

It helps to picture the data structure a terminal emulator actually keeps. There is a grid of rows and columns, and each cell holds one character plus that cell's display attributes: foreground color, background color, bold, underline, reverse video. That is the whole inventory.

Counting what is not there is faster. There is no fact recording that these five cells are one button. No fact recording that this line is a heading. No fact recording that these twelve lines are one table whose first line is a header row. Nothing about which item currently has focus, which items are selectable, which are disabled. If something on screen looks bold and important, that means the bold attribute is set on those cells. It does not mean heading.

The way an application paints also carries this property straight through. It moves the cursor to a given row and column and writes characters, over and over. Those operations specify screen position and nothing else. What looks like a table did not become a table by being declared one; the cells were simply filled so that a human eye reads a table.

One line: the shape you see on screen is an interpretation your eyes produce. The grid itself does not hold that interpretation.

2. A GUI has an accessibility tree; a terminal has no counterpart

This asymmetry is where the argument starts. Reading a web page or a desktop application works not because something reads the pixels well, but because a separate structure of meaning is built alongside the pixels.

Browsers and application toolkits construct, independently of what they draw, a tree that carries a name, a role and a state for every element, and they hand that tree to the operating system. Each platform defines the channel that receives it: UI Automation on Windows, NSAccessibility on macOS, AT-SPI on Linux desktops. Assistive technology does not look at pixels. It queries that tree, builds its own model, and re-presents that model as speech or braille.

The key point is that this tree does not appear for free. It exists only because elements carry names and roles, which is exactly why sloppy markup on the web produces an empty tree. Accessibility work, in practice, is the work of filling that tree.

In a terminal, that slot is empty. There is no standardized channel by which a terminal application can tell the emulator about the meaning of its own screen. The discussion around the original article returned to this repeatedly: there is no standard for terminal sequences or terminal interfaces to pass accessibility information to the emulator, so something analogous to web markup attributes would be needed, and building it requires simultaneous buy-in from terminal interfaces, emulators, assistive technology and operating systems.

So the shape of the situation is this. In a graphical application, if the developer does not fill the tree, accessibility is bad. In a terminal, there is no tree to fill. The first is a question of effort; the second is a question of plumbing. Treating them as the same conversation is why the conversation keeps missing.

3. Why older CLIs were actually better

Traditional command-line tools have no tree either, yet they read well. The reason is that time substitutes for structure.

You type one command and the result attaches below. Lines already printed stay where they are; new lines attach underneath. The reading rule collapses into something extremely simple: read what was appended, in order. Completion needs no separate signal, because the prompt returning is the signal. The order of output is the logical order, and that order never has to be recorded anywhere, because the stream is the order.

Repainting the whole screen throws that property away. When an update happens, many cells in the grid take new values at once. From outside, there is no way to distinguish one number changing from the entire screen changing. There is no channel for saying what changed, why, or which part of this update the user needs. And there is no channel is the precise phrasing. It is not that nobody bothered; there is no slot for it in the specification.

Full-screen applications commonly add the alternate screen buffer on top of this. A full-screen interface typically switches to a separate screen buffer, draws there, and restores the original screen on exit. That leaves scrollback clean, which is the point. Turned around, it also means nothing exchanged during that session survives in the stream. Scrolling back to re-read later simply does not work.

4. Where it breaks - and why, at the level of mechanism

Here is what breaks and where, stated as mechanism. All four share one property: they are information to a human eye and not information in the grid.

Breaking pointWhat happens on screenWhat a machine receivesWhy it is a problem
Layout built by cursor movement The cursor is moved to many coordinates and cells are filled to compose a two-dimensional arrangement Coordinates and characters. The fill order bears no relation to logical order There is no basis for reconstructing reading order. Nothing indicates whether the left column and the right column are a label and its value or two unrelated blocks
Status animations The same cells are overwritten many times per second to produce a spinner or a progress bar Cells changing continuously. Many updates, essentially zero new information Noise monopolizes the only channel that signals change. The one line that mattered gets buried inside it
Information carried only by color Success is painted green, failure red, warnings yellow A cell display attribute. The characters themselves carry no mark Copy it or save it to a file and the distinction vanishes. The same happens with color vision deficiency, low-contrast themes and monochrome logs
Box-drawing characters Line and corner glyphs draw borders so the output reads as a table or a panel A run of line-shaped characters. The fact that it is a table exists nowhere Nothing licenses reading the border as a table, and nothing licenses skipping it either, so it gets read out as noise

The fourth row is the cruel one. Border characters are a structural signal to a person and content to a machine. They work exactly backwards. On the web, a table's border is styling and the fact of tablehood lives in markup; in a terminal, the border is the only evidence that a table exists, and that evidence is precisely what does not reach the machine.

The third row is in better shape. Not using color as the sole means of conveying information is already a criterion in international accessibility standards, and the W3C document explaining how to apply those guidelines to non-web information and communications technology states that this criterion applies as written, without modification. Being a terminal does not buy an exemption.

5. Accessibility is not only about blindness

If this topic narrows to screen readers, it becomes somebody else's problem for most developers. But the same structural defect reaches much further.

  • Low vision and magnification — Magnifying reduces the number of visible columns. A two-dimensional layout that assumes a fixed width overlaps or truncates at that point. Stream output absorbs it through line wrapping; a grid layout does not.
  • Color vision deficiency — Distinguishing success from failure using only green and red fails to reach a substantial share of users. Terminal themes that redefine the palette add another variable on top.
  • Low-contrast environments — On a laptop screen in bright light, on a projector, or through the color degradation of a remote desktop session, dim gray hint text is effectively absent.
  • Cognitive load and attention — A perpetually moving screen raises the cost of reading. That applies to everyone, disability or not.
  • Automation and scripting — A tool that paints screens emits control characters and borders when its output is piped. The moment someone strips those with a regular expression, that script is scheduled to break on the tool's next release.
  • Logs and post-mortems — A build log with a progress bar recorded verbatim is an unreadable log. Anything exchanged only on the alternate screen leaves no trace at all.
  • Translation and search — Characters scattered across a grid do not group into sentences. That is the same reason on-screen messages resist being searched verbatim or pasted into a translator.
  • Repetitive strain injury — There is a case pointing the other way, too. Keyboard-centric interfaces raise accessibility for people who find mouse use painful. This topic does not run in only one direction.

One practical conclusion follows. Improving accessibility and improving automation friendliness are mostly the same work. Making output machine-readable and making it assistive-technology-readable demand nearly identical things. That overlap is also the most realistic argument for funding it.

6. What tool authors can do

Missing plumbing does not mean nothing can be done. If meaning cannot be loaded into the grid, then provide a path that does not go through the grid. Six principles.

PrincipleWhat it means in practiceWhy it works
Provide a non-interactive output path When standard output is not an interactive terminal, paint nothing and emit line-oriented plain text. Offer a structured machine-readable format as an option alongside it The grid is never used, so all four failure modes above disappear at once. Automation and logs are rescued in the same stroke
Pair every color with a non-color mark Keep the color, but also leave it in the characters. A short prefix word for success and failure at the start of the line is enough Color is lost in copying and saving; characters survive. It satisfies the international criterion directly
Announce state changes in text as well Instead of spinning a glyph, emit one new line when a meaningful state actually changes. On stage transitions, not dozens of times per second What rides the change channel becomes information rather than noise. Progress stays legible in the log too
Respect the signals the environment gives Check the standard environment variable that requests color be suppressed, and the case where the terminal type is declared as a dumb output device The user already made this choice in their own environment. Ignoring it disables every mitigation available on the user's side
Redraw less and put the cursor at the focus Update only the region that changed, and place the hardware cursor where focus currently is. Offer an option to hide the cursor entirely Cursor position is the one focus signal that exists as a standard in a terminal. It is the cheapest resource available right now
Keep the alternate path functionally equal Do not build capabilities that exist only inside the full-screen interface. Leave the same job reachable through flags and subcommands A half-featured alternate path is not a choice, it is an inferior detour. Without equivalence, the other five principles weaken as well

The first principle appears in the same form in command-line interface design guidance: whether standard output is a terminal is treated as the simplest heuristic, and animations are not to be emitted when it is not. Color, likewise, is to be turned off when output is not an interactive terminal, when the environment variable requesting no color is set, when the terminal type is declared as a dumb device, and when the user passes an option to disable it.

The environment variable in the fourth principle has a specification that is short and unambiguous. If the variable is present and not an empty string, then regardless of its value, no color is added. It even carries the caveat that software which does not emit color by default has no need to implement the standard at all. The implementation burden is effectively one conditional.

If you must order them, the first principle alone is worth roughly as much as the other five combined. Where an output path does not paint a screen, the limits of the grid simply do not apply.

7. The other side, stated honestly - what TUIs gave us

If you read this far and conclude that full-screen interfaces should be abolished, that is the wrong conclusion. The form is widespread for reasons, and those reasons largely hold.

  • Information density — Status, list and detail can occupy one screen simultaneously. In output that scrolls away, seeing what just passed means scrolling back for it.
  • Remote access — This is the biggest one. Only characters travel, so it stays usable over narrow links and high latency, and no remote screen transport is required. Entire categories of work that happen inside a server session rest on this.
  • Keyboard first — Never leaving the keyboard is fast for practiced users, and it raises accessibility outright for people for whom mouse use causes pain. This is the same point made in the previous section.
  • Resource efficiency — There is no need to carry an entire graphics stack, so it stays light. On remote servers and older hardware, that difference is not small.
  • Immediacy — Nothing sits between installing and running; no window has to be opened.
  • Environment independence — The same interface appears on a server with no desktop environment at all. A graphical tool would not even start there.

So the precise shape of the problem is not that full-screen interfaces exist but that they become the only entrance. The discussion around the original piece landed on the same weighting: valuable as an option, troublesome as the sole interface. Alongside it came the observation that editors and chat programs built with older cursor-control techniques tend to read well. That is evidence the problem lies in choices individual implementations made, not in the format.

To be clear about scope, this argument sits in a different register from terminal performance work such as startup latency and shell initialization time. That side is about getting the same information faster. This side is about whether the information arrives at all.

8. How far do standards go on this

Within what can be checked, the landscape looks like this.

DocumentScopeWhat it says about terminals
WCAG Web content Does not address them directly. Its subject is the web
WCAG2ICT (W3C guidance) Non-web information and communications technology broadly Contains a section on text, command-line and terminal applications. Treats the software itself as playing the user agent role, with interaction with assistive technology resting on platform accessibility services
EN 301 549 (Europe) Web, non-web documents, non-web software, hardware Gives non-web software its own chapter and applies the guidelines' success criteria to it
Revised Section 508 (United States) Electronic information technology procured and used by federal agencies Applies the guidelines' success criteria to both web and non-web electronic content, with scoping provisions covering non-web software

Read the table down its length and one thing surfaces. The standards already state what must be true. The requirement that name, role and state be programmatically determinable reaches non-web software, and the method named for achieving it is platform accessibility services.

The problem is that the method does not exist in a terminal. A desktop application loads its tree onto a channel the operating system already provides; a terminal application has no standardized channel to load anything onto. The standard names a destination while the road to it has not been laid. That gap is the ground this entire discussion stands on.

There is one encouraging precedent. Conventions that mark where a shell prompt begins and ends already ride the terminal without appearing on screen, and they are in real use. That is proof the idea is not impossible in principle. Extending such a channel to accessibility, though, requires terminal interfaces, emulators and assistive technology to move at once, which is also why the problem has stayed unsolved for so long.

9. What to watch next

The state of this topic will show itself in a few places. A signal on any of them means the board has moved.

  • Whether the terminal protocol gains semantic extensions — whether a specification for carrying this is a table or this has focus, invisibly, moves past the discussion stage
  • What terminal emulators expose — how much of the text they hold reaches platform accessibility services. Changes in rendering approach shift this point along with them
  • Whether non-interactive output becomes standard equipment — whether a structured format option and a plain mode appear in the initial feature list of new tools
  • Whether a screen reader mode flag becomes convention — whether tools converge on an option that switches to flat, undecorated output
  • How explicitly standards documents address terminals — whether sentences accumulate at the requirement level and not only in explanatory guidance
  • How issues in tool repositories get handled — whether requests filed on this subject are classified as feature requests or as defects, which reveals how the ecosystem understands the problem
  • Whether frameworks change their defaults — individual tools each solving it separately is a different order of impact from rendering libraries shipping a flat output path by default

What I could not confirm

Collecting in one place the parts of this article that rest on incomplete ground.

  • I could not open the full body of the appendix in the W3C guidance that covers text and command-line applications. I confirmed that the section exists and the higher-level description around it; specific recommendation wording is not reproduced here.
  • How much text individual terminal emulators expose to platform accessibility services varies by product and operating system, and I did not survey them exhaustively. The claims above are confined to protocol-level limits, not to any individual product.
  • I found no published comparison of which screen updates each assistive technology reads and which it skips.
  • I found no published measurement establishing a quantitative relationship between update frequency and announcement failure. The account above is a structural explanation of a change channel filling with noise, not a number.
  • I did not confirm whether national accessibility guidelines outside the documents cited treat terminal software separately. The landscape above is drawn from international documents.

Conclusion: text is a medium, not meaning

One sentence is what this article wants to leave behind. Looking like text is a fact about the medium, not a fact about meaning. What a terminal handles is a grid of stamped characters, and that grid does not carry which part is a heading, which is a button, or where one table starts and ends. The more decorated the screen, the more structure a human eye sees and the less a machine does. That mismatch is the whole problem.

So this is not a story about who was lazy. A graphical application is bad when the developer does not fill the tree; a terminal has no tree to fill. Where the plumbing is absent, the answer is design that routes around the plumbing. Provide one output path that paints nothing. Do not speak in color alone. Leave state changes in characters as well. Respect what the user already declared in their environment. That this list, which fits in five lines, is still not standard equipment is exactly why the argument keeps recurring.

And like the other items you handle when designing a command-line tool, this list is expensive to bolt on later and nearly free to include at the start. Adding one more output path is overwhelmingly easier while the tool is still small.
