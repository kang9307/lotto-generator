5年与500万美元的教训 - 创造一门新编程语言是错误的(Wasp 回顾分析)

YC 创业公司 Wasp 从 DSL 转向 TypeScript 带来的5条教训与个人验证清单

2026年5月24日 IT/技术

Wasp 最早出现在2020年代初,带着一句具有传染性的宣言:在一个 .wasp 文件里声明整个全栈 Web 应用,编译器自动生成 React 前端和 Node.js 后端,认证、数据库、任务和邮件都被折叠到几行声明式语法里。作者当时看完早期演示也短暂相信这可能是全栈抽象的下一阶段。5年过去,结论出来了——语言是错的包装,但里头的想法是对的。

1. Wasp 是什么 - 一家 YC 创业公司的全栈 Web DSL

Wasp 是一门用于声明全栈 Web 应用的领域特定语言。用户在 .wasp 文件里声明路由、页面、数据库模型、认证和后台任务,Wasp 编译器随即生成由 React 前端和 Node.js 后端组成的应用骨架。最让 Wasp 出圈的演示是:一屏的声明就能生成一个带认证、数据库和邮件通知的可运行 SaaS 雏形。

这背后有三个真实存在的优势。第一,对样板代码的诚实削减:Wasp 在 Next.js 和 Remix 之上再叠加一层,把认证、持久化、后台任务等横切关注点收进声明式表达里,而不是散落在代码各处。第二,起步学习曲线短:新用户可以在一个文件里就开始工作,这是所有开发者工具最强的"第一日信号"。第三,Y Combinator 的背书以及一支经营得不错的社区。

然而5年后的结局却是转型。采用率始终没能越过那个让工具成为"该领域默认候选"的门槛。在我看来,造成这一结果的原因约有八成不在抽象本身,而在外包装。把同样的抽象换成 TypeScript 库形态,会撞到的障碍少得多,也几乎肯定能越过那道门槛。下面几节把这些障碍逐一命名。

2. 为什么会选 DSL - 早期逻辑曾经合理

把创始团队的早期选择简单贬为"错误决定"会丢掉真正的教训。在2020年的语境里,做 DSL 这个决定是站得住脚的,有四条理由。

2-1) 抽象更清晰

全栈应用本质上就横跨多种语言(JavaScript、SQL、HTML、CSS)与多种系统(前端、后端、数据库、任务队列)。要把这种复杂性压缩进单一声明式文件里,全新语法在视觉上确实比任何宿主语言的构建器模式都干净。试图在 JavaScript 里用库做同样的事,最后通常落到很别扭的链式 API。

2-2) 编译期校验

DSL 让编译器有权在前期校验用户的声明。路由冲突、悬空模型引用、缺失权限这些典型的全栈错误都能在运行前被捕获,对应于全栈开发最常见的失败模式,这是一个实打实的胜利。

2-3) 差异化信号

早期创业公司需要强烈的"为什么是我们"信号。新语言本身就是一种声量极大的营销资产。对用户说"这家公司在认真重定义这个领域",对投资人说"这是周末抄不来的护城河"。这种信号在长期经济模型不成立的时候也是真实的。

2-4) 对学习成本的乐观

创始人通常假设,只要回报清晰,用户就会愿意承担学习成本。但实际学习成本永远是创始人估算的 3 到 5 倍,而用户的耐心常常只有一两天。这种"假设与现实"的差距会在头一年悄悄复利。

这四条理由在2020年都成立。如果当时我坐在他们的位置,我大概率会做同样的决定。这恰恰是 Wasp 复盘的价值所在——它示范了一个在当时看起来合理的决定如何在5年后长成一个陷阱。

3. DSL 给用户带来的5个陷阱 - 作者的归纳

把 Wasp 复盘与作者观察到的其他 DSL 失败结合,可以归纳出新语言会强加给用户的5个陷阱。

3-1) 学习曲线 - 每个开发者都得重学语法

即便是很简单的 DSL,用户在接触的第一秒就会产生"我真的得再学一套吗"的本能抗拒。在已知宿主语言里用库,代价大致等于记住几个 API 名字;而新 DSL 需要你重学语法、语义、惯用法、错误信息样式和心智模型。两者的成本不在一个数量级。

3-2) 工具生态缺失 - 没有 IDE,没有 Linter,没有调试器

JavaScript 带着 30 年累积的 IDE 支持(VSCode、WebStorm)、Linter(ESLint、Biome)、调试器(Chrome DevTools、Node Inspector)和格式化工具(Prettier)直接进场。新 DSL 必须把这一切从零造或模拟出来。用户不会容忍工具链残缺超过一周。 Wasp 在这一层投入了大量人力,但仍然没追上 TypeScript 的基线。

3-3) 招聘市场约束 - 没有"Wasp 开发者"这个职位

一旦创业公司在 Wasp 上构建,团队心智里会出现"Wasp 开发者"这个角色,可它在真实招聘市场里并不存在。结果只能招 JavaScript 开发者再做再培训,而每次有人离职这笔成本就重复一次。在作者观察的中韩创业公司里,超过九成采用自建 DSL 的公司在三年内回退,主因正是招聘问题。

3-4) 库兼容性 - 不能直接用 npm

JavaScript 生态最核心的资产是 npm 上超过 200 万个包。新 DSL 要么够不到,要么必须通过 FFI(外部函数接口)间接调用。每个支付 SDK、邮件客户端、分析库、数据库驱动都要包一层自制 shim,生产力直接腰斩,微妙 Bug 也成倍增加。

3-5) 迁移成本 - 退出很难

悖论的是,DSL 最大的营销弱点恰恰是"难走"。用户在采用的第一天就已经在心里算"我5年后怎么从这里出去?"。如果答案不明,他们就不采用。没有透明退出路径的工具拿不到信任。 Wasp 用户也感受到这种焦虑,而这种焦虑直接抑制了采用率。

4. 为什么 TypeScript 库形态会赢 - 库的5项优势

Wasp 团队在官方说明里给出的转型理由,核心就是 TypeScript 库形态一次性解掉了上述5个陷阱。作者总结的5项结构性优势如下。

  • 学习曲线归零:用户已经会 TypeScript,只需熟悉这个库的 API 表面。
  • 继承全部工具链:VSCode、ESLint、Prettier、tsc strict 模式开箱即用。
  • 招聘池无限:TypeScript 开发者在任何市场都有。
  • 直接使用 npm:200 万个包成为一等公民,而不是外部进口品。
  • 迁移成本透明:用户随时可以把库去掉,退回纯 TypeScript。

这5项优势在结构上是任何 DSL 都拿不到的,也是任何寄生在主流宿主语言里的库结构性保证的。Wasp 复盘最短的概括就是:如果同样的抽象可以用库交付,那库总是更好的答案。

库也有真实劣势:编译期校验弱一些、语法不那么干净、差异化信号更弱。Wasp 团队明确接受这些劣势,以换取采用速度,而在我看来,2026年这个交易方向正确。

5. 创造新语言之前的5个验证标准

把 Wasp 复盘吸收完之后,作者写下了在任何"是否要做新语言"决定之前要回答的5个问题。5个全部为"是"才放行,否则一律改做库。

5-1) 现有语言里真的解不掉吗?

最重要的问题。设计新语法前要先把现有宿主语言中的库、框架、宏、内嵌 DSL 工具箱搜个底朝天。对 Wasp 而言,2020年时诚实的答案应当是"能,在 TypeScript 库里能解",绕了5年还是回到了这个答案。

5-2) 市场愿意为学习成本买单吗?

回报必须远大于学习成本。Solidity 把回报与"价值数十亿美元、否则无法进入的以太坊智能合约市场"绑死。Wasp 的回报只是"少写一些全栈样板",而 TypeScript 库同样能提供,新语法的"税"就永远收不起来。

5-3) 能撑5年的维护者池吗?

需要3到5位核心贡献者持续活跃5年以上。开源维护者池总是比创始人估计的小,职业倦怠总是比预期来得快。 即使有公司背书,一旦关键工程师离职,语言数月之内就会停滞。

5-4) 5年后市场还需要这门语言吗?

把5年后的市场结构画出来,看看这门语言还有没有座位。2020年时,"TypeScript 会成为全栈默认"的信号已经很强,Wasp 选择押注反方向,每过一年都更糟。这套练习对今天 AI 编程浪潮同样适用。

5-5) 语言本身是公司的核心价值吗?

如果抽象是核心价值、语言只是包装,库就够了。只有当语言本身是核心价值,也就是说"没有这个特定运行时就根本无法解决问题",新语言才被合理化。Solidity 与 CUDA 通过了这一关,Wasp 没通过。

6. DSL 成功的地方 - Solidity、Terraform、CUDA 的共同模式

并非所有 DSL 都失败。活下来的那些共享一组很小且很一致的属性,正好对应上面的5个验证标准。

6-1) Solidity - 以太坊智能合约

Solidity 面向以太坊虚拟机。没有任何通用语言能安全发出 EVM 字节码,同时还把交易语义、Gas 计费和状态修改约定表达得像母语。问题从外部根本够不到。

6-2) Terraform - 基础设施即代码

Terraform 的 HCL 用同一套语法在 AWS、GCP、Azure 上声明云基础设施。通用语言能做,但 HCL 天然贴合 plan→diff→apply→destroy 的四步生命周期,而这正是基础设施代码的本质。多云可移植的单一声明格式拿下了这个细分市场。

6-3) CUDA - GPU 并行计算

CUDA 是暴露 NVIDIA GPU 的 warp、block 与显存层级的 C 扩展。CPU 语言无法高效驱动 GPU 上数千个核心,而 CUDA 的硬件感知抽象在 AI 与科学计算爆发的浪潮中变成了事实标准。

6-4) 三者的共同模式

三者都满足同一组四条件:问题在现有语言里真正解不掉;回报大到足以吸收学习成本;有大公司或强社区做持久后盾;5年后市场结构仍然需要这门语言。Wasp 一条都没干净地满足。

7. DSL 失败的地方 - CoffeeScript、早期 Dart、Elm 的共同模式

失败的 DSL 也共享一种模式,正好是成功者的镜像。

7-1) CoffeeScript - 消失的爱

2010 年代初,CoffeeScript 把丑陋的 JavaScript 语法重写得很漂亮,赢得了 Ruby on Rails 圈层的真心喜爱。然后 ES6 来了,JavaScript 自己把自己修好了,CoffeeScript 的价值主张一夜蒸发。建立在"宿主语言还能自我修复"的领域里的 DSL,永远暴露在风险之下。

7-2) 早期 Dart - Chrome 集成失败

Google 设计 Dart 是为了取代 JavaScript,计划在 Chrome 里塞一个 Dart VM。其他浏览器厂商不跟,计划崩溃,Dart 漂泊直到 Flutter 用一个新领域救活了它。在没有任何单一厂商能强制标准的市场里,DSL 难以存活。

7-3) Elm - 函数式前端的承诺

Elm 凭"纯函数式前端"赢得了一批死忠,但在三方面同时受阻:维护者基础薄,与 JavaScript 生态集成的成本高,回报不足以正当化学习曲线。

7-4) 共同模式

三者至少在以下之一上失败:宿主语言能自我修复、没有单一行为者能强制标准、回报无法正当化学习成本。Wasp 三条都失败了。

8. AI 时代的 DSL - Vercel 的 Zero 真的不同吗?

2026年5月,Vercel Labs 发布了 Zero(zerolang.ai),这门语言把 AI 智能体而非人类设为第一用户。作者在另一篇文章里专门写过 Zero 的5条设计原则。把 Wasp 那把"尺子"放上去,Zero 是什么处境?

8-1) 学习成本 - 部分不同

智能体在分钟尺度上吸收语法学习成本。历史上扼杀新语言采用的"人类学习曲线"门槛在第一用户非人类时确实显著松动。这是 Wasp 五大陷阱里唯一在 AI 时代真正缓解的一条。

8-2) 库、工具、维护者、生存 - 问题照旧

库兼容性、工具生态、维护者池稳定性和5年生存率这四条都没变。Zero 代码要支付、邮件、分析依然得包 npm;IDE 支持依然得从零造;维护者池依然脆弱于一两个工程师的离开。

8-3) 作者的预测

要让 Zero 活下来,只有两条路。其一是 Vercel 把 Zero 与 v0、AI SDK 强绑定,让 Zero 借自家生态被拽着采用;其二是 某个更大的厂商把 Zero 的设计原则吸收进自家既有语言,届时活下来的只是"原则"而非"品牌"。作者个人估计,Zero 作为语言5年后存活的概率低于30%,但它提出的设计原则在某处被吸收的概率高于80%。

AI 时代的 DSL 摆脱了 Wasp 的一个陷阱,却仍然暴露在另外四个之下。Wasp 教训具有可推广性。

9. 个人开发者造工具时可以应用的5条教训

作者从 Wasp 复盘里抽取出5条具体习惯,并在自己的副业项目与开源维护中持续应用。

  1. 如果库就是答案,就发库。 在一秒内掐掉"做新语法"的冲动,默认选择宿主语言的库。
  2. 学习成本永远乘以3。 你以为"一小时"的工具会吃掉3到5小时;你以为"一天"的会吃掉3到5天。从第一天起就这么校准。
  3. 把迁移成本明示出来。 提前告诉用户5年后从这个工具迁走要花多少人月。没说明的迁移成本,被持怀疑态度的潜在采用者一律假设为最差情况。
  4. 把招聘池当作设计输入。 用户在采用你这个工具时,能否在一秒内回答"这工具的人去哪儿招?"。如果答不上来,就重做外包装。
  5. 画出5年后的市场。 在发布前画一遍5年后的市场结构图。从那张图里消失的工具,今天就不值得做。

10. 教训本地化 - 中韩创业公司与开源维护者

Wasp 教训在中韩开发者市场可以直接落地,只有一个本地侧重值得专门讲清楚。

10-1) 中韩创业公司 - 库优先

考虑到中韩创业市场的资源和招聘池规模,自建 DSL 几乎总是一个结构性风险。中国的字节、阿里,韩国的 Toss、Daangn、LINE 这类现代创业公司都刻意停留在 TypeScript、Kotlin 库与内部 SDK 上,而不去做新语言。作者观察的样本里,自建 DSL 的中韩创业公司九成以上在三年内回退。

10-2) 中韩开源维护者 - 内嵌 DSL 更安全

对维护者来说,在宿主语言里通过内嵌 DSL 表达新抽象是最安全的。JavaScript 构建器模式、Python 装饰器型 DSL、Ruby 块式 DSL 都属于这一类。这条路径避开了学习曲线陷阱、工具缺口陷阱、招聘池陷阱,同时仍能给抽象一个干净的形状。

10-3) 作者本人的决策顺序

每当考虑做一个新工具,作者严格按下面的优先级走。

  1. 第1层:复用现成库或框架。能不造就不造。
  2. 第2层:在现有语言里写一个内部库或 SDK。
  3. 第3层:在宿主语言里做宏或内嵌 DSL。
  4. 第4层:带自有解析器与编译器的外部 DSL。
  5. 第5层:一门全新的编程语言。

只有当第1到3层被明确证伪之后,才考虑第4、第5层。Wasp 是从第4层起步、花掉5年和约500万美元、最终回退到第3层的真实案例。从一开始坚持这个顺序,本可以省下5年里的大部分。

11. 结论与3份可立即使用的清单

作者从 Wasp 复盘里留下的那一句话是:不要做新语言。如果同样的抽象可以用库交付,库永远是正确答案。 下面是把这一句话落进日常决策的3份清单。

11-1) 清单1:做新工具前的5分钟自测

当"我要发明新语法"的冲动出现时,5分钟内回答这5个问题。

  • 这个问题用现有库或框架真的解不掉吗?(一秒内冒出"不,能"就别做。)
  • 同样的抽象能不能换成库或 SDK?
  • 市场愿意承担你估算学习成本的3倍吗?
  • 你能保3位核心维护者在这上面持续5年吗?
  • 这个工具是公司核心价值,还是只是附属资产?

11-2) 清单2:采用外部工具前的5分钟风险测

在考虑把某个外部 DSL 或新语言带到生产环境前。

  • 你能用具体的"人月"数字说清这工具的迁移成本吗?
  • 你能在一周内在本地招聘市场找到会这工具的人吗?
  • 有信号显示这工具的库与工具链一年后依然存在吗?
  • 有信号显示维护者或赞助公司5年后依然活跃吗?
  • 采用时的回报至少是采用成本的3倍吗?

11-3) 清单3:6 个月与 5 年两个时间点的复盘问题

把这些问题写进日历,在你做出或采用任何工具的第6个月和第5年自动跳出来。

  • 6 个月:这个工具真的提高了生产力,还是只消耗了学习成本?
  • 6 个月:从1到10打分,用户会把它推荐给同行吗?
  • 5 年:你当年假设的市场结构,今天还真存在吗?
  • 5 年:如果能穿越回去,你会做同样的决定吗?
  • 5 年:这个决定里有没有你应该像 Wasp 那样公开承认的部分?

收尾的一句话很简单。每一个工具决定都是一笔5年期的赌注。 几乎没有哪种决定能在12个月内见分晓,即便第一年看起来很合理的决定,常常在第五年长成陷阱。Wasp 团队有纪律把这笔5年、500万美元的复盘公开,这本身就是一份赠礼,因为它能让下一批创始人省掉那5年。作者写这篇文章、提供上面这些清单,理由也在这里。
