How to Choose MCP Servers for Claude Code - Six Axes Instead of a List

What you gain and what you hand over - deciding by transport, scope, exposure, trust, and context cost

2026-08-06 IT & Technology

Introduction: Recommendation Lists Go Stale in Six Months

Attaching an MCP server to Claude Code takes one command. The hard part was never the attaching. It is the choosing.

Recommendation lists for MCP servers are everywhere already: category roundups, awesome lists, an official directory. What those lists carry, though, is an expiration date. A sizeable share of the early reference servers has already been moved into a separate archived repository, and the @modelcontextprotocol/server-github package that once appeared in nearly every tutorial is among them. Follow a six-month-old list literally and you plant unmaintained code in your own development environment.

Criteria outlast lists. And with MCP there is a second reason criteria matter more than usual. Attaching an MCP server is not switching on a convenience feature; it is handing over an access grant. A filesystem server pulls your disk into the agent's reach. A database server pulls your data in. An issue tracker server pulls the full text of internal tickets in. A badly chosen server is not slow. It is dangerous.

So this article replaces the list with six axes for judging. First, is there a reason to attach anything at all? Second, which transport does it arrive on? Third, which scope do you write it into? Fourth, what does that server make you hand over? Fifth, what grounds do you have for trusting it? Sixth, how much context does it eat once it is there? For each axis, what the options are and what each one costs. This is not an article that stamps a safety seal on particular servers; it is an article that leaves you able to judge your own.

1. Start by Deciding Whether to Attach Anything - the Copy-Paste Signal

1.1 When to attach

The signal the official documentation offers is surprisingly modest. The moment to attach a server is when you catch yourself copying content out of another tool and pasting it into the session window. Ticket bodies from an issue tracker, stack traces from a monitoring dashboard, result tables from a query — if you keep ferrying those across, that system is a candidate. Once attached, the agent reads and acts on the system directly instead of waiting for your paste.

1.2 When not to attach

Inverting the test sharpens it. A system you never copy from is a system you have no reason to attach.

  • A system you open once or twice a month: setup, authentication, and upkeep outweigh the gain
  • A system an existing CLI already covers: wrapping a working shell command in a protocol layer buys little
  • Content that is identical every time: that belongs in a project document, not in a server
  • A read-only need served by a server that ships write tools too: permissions you never asked for come along for the ride
  • A service that requires a fresh credential you have no way of narrowing

1.3 Five sentences that filter candidates

  • Have you moved content from that system into a session five or more times in the past two weeks?
  • Was the content different each time?
  • Does the agent need to write to that system, or would reading be enough?
  • Can the credential that server demands be narrowed to read-only?
  • Is attaching and detaching cheap? If so, attaching and observing is a legitimate way to decide

2. What MCP Actually Standardized - You Need the Spec to Choose Well

2.1 Where the protocol sits

MCP is an open standard for connecting AI applications to external systems, often described as a USB-C port for AI applications. When the server side exposes what it can do in a standard shape, any client that understands that shape can connect without bespoke integration code. Claude Code shares servers with a range of other editors and agents. That interoperability is a precondition for every choice below, because it means the server you pick today is not welded to one tool.

2.2 How to read the version string

MCP versions its specification with a YYYY-MM-DD date string, and that date means something specific: it is the last date on which a backwards-incompatible change was made. Backwards-compatible improvements do not bump it. The current specification version is 2026-07-28. If a server's documentation still claims support for a version dated far earlier, read that as a signal — the server has not followed the compatibility breaks since.

2.3 What version negotiation changed

Each request declares its protocol version through the io.modelcontextprotocol/protocolVersion key in the _meta field, and the server accepts or rejects each request independently. Over Streamable HTTP the same value also travels in the MCP-Protocol-Version header. If a server does not support the requested version it returns an error listing the versions it does support, so the client can retry. A client that prefers to settle this up front can call server/discover once and receive supported versions, capabilities, and identity in a single response. The practically important detail is that the specification documents a compatibility path for servers still on the older handshake-based revisions (2025-11-25 and earlier). Older servers do not break overnight — but unmaintained ones show trouble at this boundary first.

3. Which of the Four Transports Should Carry It

3.1 There is really only one fork in the road

Transport choice comes down to whether the server code runs on your machine or on someone else's. That single difference rewrites the whole trust model. A local process runs with your account's permissions; a remote server routes your credentials through infrastructure you do not operate.

TransportRuns whereAuthWhy pick itWatch out for

3.2 The commands you actually run

A remote HTTP server needs a name and an address.

claude mcp add --transport http <name> <url>

A local stdio server takes its run command after --. That double dash matters: it is the separator that stops the client from parsing the trailing arguments as its own options and passes them to the server untouched.

claude mcp add --transport stdio <name> -- npx -y <package>

After adding, claude mcp list shows status, claude mcp get <name> shows detail, and claude mcp remove <name> removes it. Inside a session, the /mcp panel puts connection state, tool counts, and pending authentication on one screen. The add command does not validate credentials, so a wrong value still registers successfully and fails only at connection time. Not mistaking a successful add for a successful connection is the first practical trap.

4. The Three Scopes - Where You Write It Decides Who Holds the Permission

4.1 What actually separates them

ScopeLoads inTeam sharingFitsRisk
local (default)Only the project you added it in, only for youNoPersonal experiments, servers carrying credentialsTeammates never learn why it only works on your machine
projectEveryone on that projectYes, via version controlShared team tooling, reproducible environmentsThe permission you granted is now held by the whole team
userAll of your projectsNoPersonal utilities you want everywhereThe server stays live even in unrelated projects

4.2 The decision project scope conceals

Project scope writes into a .mcp.json at the repository root and ships with the repository. The convenience is obvious: whoever clones gets the same tooling automatically. Turn the same sentence toward permissions, though, and it reads differently. A server you chose now runs on every teammate's machine. That is why project-scoped servers are designed to require approval before first use, and why a separate command exists to reset those approval choices. It is also why a cloned repository cannot approve its own servers on your behalf.

4.3 Precedence, and the absence of merging

When the same server name is defined in more than one place, exactly one definition survives. The order runs local, then project, then user, then plugin-provided servers, then connectors. The rule that trips people up is the second half: fields are not merged. The whole entry from the winning source is used. Putting headers in a user-scope entry and expecting a project-scope entry to override only the URL will not work. The three scopes match duplicates by name, while plugins and connectors match by endpoint.

4.4 Keeping credentials out of the repository

For a shared .mcp.json, use environment variable expansion. ${VAR} expands to the variable's value and ${VAR:-default} falls back when the variable is unset. Expansion applies to command, args, env, and, for remote servers, url and headers. If a referenced variable is unset with no default, the config does not collapse: a warning is reported and the literal text stays as written. Declaring a default is the way to avoid quietly connecting with a wrong value.

{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": { "Authorization": "Bearer ${API_KEY}" }
    }
  }
}

5.2 Browser servers are their own problem

The browser row is the strangest cell in this table. Every other server opens one specific system; a browser opens every service already logged in inside it. That peculiarity is exactly why browser vendors shipping their own MCP servers started building in local-only execution and blocked access to stored personal data. If you want to go deep on that one category, the Safari MCP server analysis covers the vendor-by-vendor design differences and the trust-boundary argument separately.

5.3 The official recommendation sitting in the database row

There is one place where the official documentation states the principle outright, inside an example: when connecting a database server, use a read-only account in the connection string. The reason is stated plainly — so the queries the agent runs cannot modify data. That single line compresses this whole article. Choosing a server is not a question of whether you trust it. It is a question of keeping the damage bounded when the trust fails.

6. Grounds for Trusting a Server - Eight Quality Signals

6.1 What directory listing does and does not mean

This point is widely misread, so it is worth stating precisely. Anthropic reviews connectors against listing criteria before adding them to its directory, but the documentation states plainly that it does not security-audit or manage any MCP server. A directory listing is a signal that a minimum formal review was passed, not a safety certification. The official registry is likewise a meta-registry that stores metadata and installation commands while the actual artifacts stay in package registries such as npm and PyPI. It verifies namespace ownership, but it does not provide governance in the sense of access control or audit trails.

6.2 The signals worth reading

6.3 The extra layer stdio servers deserve

A remote server runs on someone else's infrastructure; a stdio server runs on your machine with your account's permissions. That adds a software-supply-chain dimension to the choice. Which package manager fetches it, whether the version can be pinned, and what the package executes at install time are all evidence. An always-latest invocation is convenient, but it also means the code running on your machine changes quietly the moment upstream does.

7. Prompt Injection and Tool Poisoning - the Risks Unique to This Thing

7.1 Two risks, two defensive positions

The risk sits in two layers, and blurring them leads to defenses aimed at the wrong place.

  • Prompt injection: instructions hide inside the data the server fetched. Issue bodies written by outsiders, crawled pages, user-submitted logs are the channels. The defensive position is to distrust the data.
  • Tool poisoning: the tool definition itself is contaminated. Malicious instructions placed in tool description metadata are read by the model while the user sees little more than a tool name. The defensive position is to distrust the server.

What makes the second type harder is precisely that it is not visible. A string never rendered to the user still lands whole in the model's input. That is why this class is identified as the most prevalent and impactful client-side vulnerability in the ecosystem's threat analyses.

7.2 What the client already blocks for you

These are the mitigations sitting in Claude Code. They are not grounds for relaxing, but knowing what is already covered prevents duplicated effort.

  • Permissions default to read-only, and sensitive operations require explicit approval
  • New MCP servers and first-time codebases go through trust verification (this verification is disabled in non-interactive -p runs)
  • Shell commands that fetch content from the web are not auto-approved by default
  • Web fetch runs in a separate context window, reducing the chance that malicious instructions bleed into the main conversation
  • Suspicious command shapes require approval again even if previously allowlisted, and unmatched commands fail closed to manual approval

7.3 What is left to you

The documentation itself states that these protections reduce risk without making any system immune. What remains is mostly human. Do not pipe untrusted content straight in, read proposed commands before approving them, and run work that touches external services in an isolated environment. It sounds banal, but those three prevent the largest share of real incidents.

8. Narrowing to Least Privilege in Practice

8.1 Narrowing at the credential layer

This is the outermost layer and the highest-leverage one. Narrowing here is more reliable than any tool rule.

  • Build database connection strings around a read-only account
  • Issue code-hosting tokens as fine-grained tokens covering only the target repositories
  • For OAuth services, keep only the scopes actually needed in the request
  • Reference tokens through environment variable expansion instead of writing them into config files
  • Prefer credentials that expire — forgotten ones close themselves

8.2 Narrowing with per-tool rules

MCP tools carry names in the form mcp__servername__toolname, and permission rules are written against those names. There is one asymmetry in the rule syntax worth knowing.

  • Deny and ask rules accept globs in the tool-name position. mcp__* means every MCP tool from every server
  • Allow rules are different. A glob is accepted only after a literal mcp__servername__ prefix; the server segment cannot be a glob
  • mcp__servername__* auto-approves every tool from that server, while mcp__servername__get_* approves only the read-shaped ones
  • An unanchored allow glob, such as a bare wildcard, is skipped with a warning and auto-approves nothing

The combination that pays off in practice is allowing only the read-shaped tools and leaving the rest to approval. Attaching a server does not have to mean opening all of it. Automate the reads that genuinely repeat and the round trips fall without the exposure rising.

8.3 Narrowing at the exposure layer

For file-access servers it is worth confirming that the server respects the working roots the client advertises. The specification includes a request through which a server can ask for and confine itself to the allowed range, and Claude Code answers with the session's launch directory plus any additional directories the user granted, sending a change notification when that set moves. A server that implements this flow sees only what the user opened. A server that does not sees as much as it happens to know. That distinction is a line item to check in the server's documentation.

8.4 Tools where the approval is the point

There is a server-author-side control too. Marking a tool's metadata as requiring user interaction makes that tool show its permission prompt on every call, even in auto-approving permission modes, with no offer to stop asking. Allow rules do not bypass it either. It exists for actions like granting access, where auto-approval would mean no human ever consented. If you are writing a server, putting this marker on destructive tools is the most honest safeguard you can give your users.

9. Context Cost and Latency - Where More Servers Start Losing You Money

9.1 The room tool definitions occupy

Each attached server puts its tool definitions and server instructions into the model's input. More servers, less room for the conversation. Claude Code counters this by enabling tool search by default: only tool names and server instructions load at session start, and actual definitions are fetched when needed. That is why adding servers has limited context impact. There is no fixed per-server tool cap; the practical limit is your context budget.

9.2 The dials

  • Tool search behaviour is controlled by an environment variable, choosing between loading upfront, deferring everything, or a proportional threshold
  • A small number of servers needed every turn can be exempted with an always-load option, at the cost of briefly blocking startup until that server connects
  • Tool output above 10,000 tokens raises a warning; the default ceiling is 25,000 tokens and an environment variable raises it
  • Server instructions and tool descriptions are each truncated at 2KB, so server authors should front-load the essentials
  • Tool calls carry a per-server wall-clock limit and a separate idle limit, defaulting to five minutes for remote and thirty for local servers

9.3 The real reason to prune periodically

The more practical problem is not token cost but selection error. When similarly named tools are scattered across servers, the odds of the model reaching for the wrong one rise. Removing the server you tried once three months ago, the half-finished experiment, and the one belonging to a service you no longer use is a security measure and an accuracy measure at the same time. Opening the list and flagging anything not actually called in the past thirty days is enough of a routine.

10. When Not to Attach, and What to Use Instead

10.1 Cases where MCP is not the answer

Not every integration should be a server. In these cases something else is cheaper.

  • Systems with a good CLI already: putting a protocol layer over a one-line shell command only adds failure points
  • Repetitive work with a fixed procedure: pinning it into a project document or a script reproduces better than re-describing it each time
  • One-off lookups: attaching and detaching costs more than the single lookup
  • Services whose credentials cannot be narrowed: if only a full-access token exists, exposure is uncontrollable
  • Sources with oversized output: hitting the ceiling on every call means a human ends up trimming anyway

10.2 Things to try before committing

  • Attach at local scope, use it for two weeks, and judge promotion to project scope by actual call frequency
  • Auto-approve only the read tools, leave writes to approval, and watch what happens
  • Connect with staging or replica credentials before production ones
  • Skim the tool list once and learn by name which tools are destructive
  • Deliberately break the server once to see its failure message — authentication failure and connection failure call for different fixes

Frequently Asked Questions (FAQ)

Q1. How do I decide whether to attach an MCP server?

If you keep copying content from another tool into the session, that system is a candidate. Conversely, a system you check once or twice a month, a job an existing CLI covers, or content identical enough to pin into a document are all better left unattached. Every server brings setup, authentication, context cost, and permission exposure with it.

Q2. What separates the local, project, and user scopes?

Local is the default and stays private to you inside that project. Project lives in the repository's config file, is shared with the whole team, and requires approval on first use. User opens across all of your projects but stays private to you. When names collide, precedence runs local, project, user, plugin, connector, exactly one wins, and fields are not merged.

Q3. How do prompt injection and tool poisoning differ?

Injection means instructions hide in the data a server fetched; poisoning means the tool definition itself is contaminated. The first tells you to distrust the data, the second to distrust the server. Poisoning is nastier because a string never rendered to the user still lands whole in the model's input.

Q4. What actually narrows permissions to a minimum?

Narrow in three layers: credentials through read-only accounts and fine-grained tokens, tools through rules naming a specific server and tool, and exposure through working-directory limits and environment variable references. Of the three, the credential layer has the greatest effect.

Q5. Is a server safe because it appears in a directory or registry?

No. Review against listing criteria happens, but the documentation states plainly that it is not a security audit. The official registry stores metadata without providing governance such as access control or audit trails. Listing is a starting point, not a conclusion.

Conclusion - Five Steps to Apply Today

Choosing MCP servers is not a problem of finding a better list. It is a problem of holding your own criteria. Lists spoil in six months; criteria stay. In the order you can apply today:

  • Step 1 — Count what is attached right now. Open the list and flag servers you have not genuinely used lately. Pruning is a security measure and an accuracy measure
  • Step 2 — Write one line per server about what it hands over. Any server you cannot write that line for is a server you do not yet understand
  • Step 3 — Narrow the credentials first. Read-only accounts, fine-grained tokens, tight OAuth scopes. Narrowing here beats narrowing with rules
  • Step 4 — Re-pick the scopes. Separate what the whole team should hold, what only you should hold, and what should open only in this project, then move each accordingly
  • Step 5 — Trial new servers at local scope for two weeks. Auto-approve reads only, watch the call frequency, then decide on promotion

One last thing this article deliberately did not do. There is no verdict here declaring any server safe, because no list can render that verdict for you. What exists are the axes to judge along, and holding them up against your own environment remains the job of the person doing the attaching.
