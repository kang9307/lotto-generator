NOT IN 列表里混进一个 NULL，结果就整个变空 - 不报错却返回0行的 SQL 三值逻辑

把0行和8行分开的，是列表里的一个 NULL。来自 SQLite 与 DuckDB 上的实际执行输出

2026-07-30 开发与基础设施

症状：查询结果是空的，可数据明明还在

线上服务里有一条查询，用来取出「一次都没申请过退款的客户」名单。到昨天为止一直正常。今天跑出来是0行。客户表里依然有几万条记录，退款申请表也完好。查询成功了。连一行错误信息都没有。

面对这种情况，人最先想到的结论通常是同一个：「大概是没有符合条件的数据吧。」而这个结论随后会变成什么都不显示的仪表盘、谁也收不到的推送批处理、一片0的报表，被就这么放上好几天。因为它不是失败了，而是在成功的状态下变空了，所以任何告警都不会响。

罪魁祸首通常就是这一行。

SELECT id, name FROM customers
WHERE id NOT IN (SELECT customer_id FROM refund_requests);

而 refund_requests.customer_id 里恰好有一行是 NULL。仅此而已。剩下的一万条再怎么正常，结果也是0行。

这篇文章不是要说「别用 NOT IN」。它讲的是为什么会被设计成这样，以及什么时候该用什么。先把结论摆出来：这个行为不是缺陷，而是逻辑上正确的结果。它之所以成为事故，恰恰是因为这份正确性是不报错、悄无声息地出现的。

执行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际执行得到的。用了两个引擎：SQLite 3.49.1（经由 Python 3.13.3 的 sqlite3 驱动）和 DuckDB 1.5.5（PostgreSQL 系的 SQL 方言）。同一份脚本在两边都跑过，以便区分一致的地方和分歧的地方。关于规格的叙述只与 SQLite 和 PostgreSQL 的官方文档核对过；对于没有打开确认的引擎（MySQL、Oracle、SQL Server 等）不作断言。

示例表结构。customers 有10行（id 从 1 到 10），refund_requests 有4行。4条申请里只有1条的 customer_id 是 NULL。全部是虚构的表，可以照抄下来在自己的数据库上复现。

本文不涉及的内容。如果 SQL 本身对你是全新的，请先看 SQL 入门指南。这里只深挖一个点：NULL 的三值逻辑。连接中 ON 与 WHERE 的边界不是本文主题，第6节和第7节的 NOT EXISTS、LEFT JOIN 仅作为反连接的替代写法来处理。

1. 三分钟复现 - 往列表里放一个 NULL

解释之前先执行。需要的只是一张10行的表。

同一份脚本也在 DuckDB 1.5.5 上跑了一遍。

--- 1. basic reproduction ---
  NOT IN (1, 2, NULL) -> 0 rows
  NOT IN (1, 2)       -> 8 rows
  IN (1, 2, NULL)     -> 2 rows

数字完全一致。这不是某个引擎的缺陷。它是遵循 SQL 标准定义的结果，所以在哪里都会一模一样地复现。

2. 为什么 IN 却毫发无损

有意思的是 IN。给它完全相同的列表，IN 却正常工作。

--- 2-1. IN with the same list ---
  SQL: SELECT id, name FROM customers WHERE id IN (1, 2, NULL)
  rows returned: 2
  id | name
  1 | aria
  2 | brio

--- 2-2. IN without the NULL ---
  SQL: SELECT id, name FROM customers WHERE id IN (1, 2)
  rows returned: 2
  id | name
  1 | aria
  2 | brio

有没有 NULL 都是2行。那么 NOT IN 为什么不一样？要看答案，把每一行上条件表达式实际取什么值打印出来就行。SQLite 用 1 表示真、0 表示假，而第三个值用 NULL 表示。

--- 2-3. the expression value per row (1 = true, 0 = false, NULL = unknown) ---
  id | in_expr | not_in_expr | in_clean | not_in_clean
  1 | 1 | 0 | 1 | 0
  2 | 1 | 0 | 1 | 0
  3 | NULL | NULL | 0 | 1
  4 | NULL | NULL | 0 | 1
  5 | NULL | NULL | 0 | 1
  6 | NULL | NULL | 0 | 1
  7 | NULL | NULL | 0 | 1
  8 | NULL | NULL | 0 | 1
  9 | NULL | NULL | 0 | 1
  10 | NULL | NULL | 0 | 1

这张表就是本文的核心。请竖着读 not_in_expr 这一列。没有一格的值是 1。id 为 1 和 2 的是 0（假），其余8行全是 NULL。而用去掉 NULL 的列表算出的 not_in_clean 列里，有8个 1。

DuckDB 用真正的布尔类型展示同一件事。只是写法不同，结构完全一样。

--- 1-1. the expression value per row - booleans, not 1/0 ---
  id | in_expr | not_in_expr | not_in_clean
  1 | true | false | false
  2 | true | false | false
  3 | NULL | NULL | true
  4 | NULL | NULL | true
  5 | NULL | NULL | true
  ... (rows 6-10 identical in shape)

为什么会这样，下一节从原理上讲清楚。

3. NULL 不是「没有」，而是「不知道」

大多数人把 NULL 理解成「值是空的」。这样一来 NULL = NULL 看着就该是真，1 <> NULL 看着也该是真。实际执行一下，并非如此。

--- 3-1. comparisons against NULL ---
  eq | neq | null_eq_null | null_neq_null | gt | is_null | one_is_null
  NULL | NULL | NULL | NULL | NULL | 1 | 0

读法是这样：1 = NULL 是 NULL，1 <> NULL 也是 NULL，NULL = NULL 还是 NULL，1 > NULL 同样是 NULL。给出确定值的只有 IS NULL（NULL IS NULL 得 1，1 IS NULL 得 0）。

这里的 NULL 不是「结果为空」的意思，而是第三个逻辑值 UNKNOWN。把类型打印出来就一清二楚了。

--- 3-2. typeof() of each result - NULL is a value, not an error ---
  t_eq | t_true | t_false | t_nn
  null | integer | integer | null

真和假是 integer，而与 NULL 比较的结果是 null 类型。它是一个值，不是错误。正因如此，它才会悄无声息地混进计算里。

3.1 为什么要这样定义

把 NULL 读作「不知道的值」，一切就都顺理成章了。

  • 某个人的年龄不知道。那个年龄是 30 吗？不知道。不是假，而是不知道。所以 age = 30 是 UNKNOWN
  • 那个年龄不是 30 吗？这也不知道。所以 age <> 30 同样是 UNKNOWN
  • 两个人的年龄都不知道。这两人同岁吗？不知道。所以 NULL = NULL 也是 UNKNOWN

按「值是空的」来读，第三条会显得古怪；按「不知道」来读，它就是理所当然的结论。两个都不知道的值是否相等，你要怎么断定呢？

3.2 UNKNOWN 穿过 AND 和 OR 的方式

--- 3-3. NOT of unknown is still unknown ---
  not_unknown | unknown_or_true | unknown_or_false | unknown_and_true | unknown_and_false
  NULL | 1 | NULL | NULL | 0

把这一行展开成表格就是这样。

表达式结果为什么
UNKNOWN OR TRUETRUEOR 只要有一个真就能确定
UNKNOWN OR FALSEUNKNOWN不知道的那个可能是真，无法确定
UNKNOWN AND TRUEUNKNOWN不知道的那个可能是假，无法确定
UNKNOWN AND FALSEFALSEAND 只要有一个假就能确定
NOT UNKNOWNUNKNOWN不知道的东西的反面，也不知道

规则只有一条。只有在能确定结论的时候才确定，其余情况下「不知道」会传染。而 NOT UNKNOWN 依然是 UNKNOWN，正是杀死 NOT IN 的致命一击。

3.3 WHERE 只放行 TRUE

最后一块拼图。直接数一数三个逻辑值在过滤时分别被怎么处理。

--- 3-4. what WHERE does with each of the three values ---
  WHERE TRUE     -> 1 row(s)
  WHERE FALSE    -> 0 row(s)
  WHERE UNKNOWN  -> 0 row(s)
WHERE 子句的值该行执行确认
TRUE通过1行
FALSE淘汰0行
UNKNOWN淘汰0行

陷阱在这里合拢了。在过滤这一步，UNKNOWN 和 FALSE 无法区分。「不知道」和「不是这样」受到同等待遇。在逻辑表达式内部把三个值分得清清楚楚，往外输出结果时却把它们折成了两个。

3.4 现在重新读一遍 NOT IN

x NOT IN (1, 2, NULL) 会这样展开。

x NOT IN (1, 2, NULL)
  = NOT (x IN (1, 2, NULL))
  = NOT (x = 1 OR x = 2 OR x = NULL)

x = 1  -->  NOT (TRUE  OR FALSE OR UNKNOWN) = NOT TRUE    = FALSE    -- dropped
x = 7  -->  NOT (FALSE OR FALSE OR UNKNOWN) = NOT UNKNOWN = UNKNOWN  -- dropped

不管走哪条路都到不了 TRUE。在列表里就是 FALSE，不在列表里就是 UNKNOWN。WHERE 只放行 TRUE，所以结果是0行。前面 2-3 的输出里一个 1 都没有，原因就在这里。

反过来 IN 能活下来，是因为在 x = 1 的那一行上会得到 TRUE OR FALSE OR UNKNOWN = TRUE。OR 只要有一个真就能确定，所以即便混进 NULL，通往真的路径也没有被堵死。

PostgreSQL 官方文档也明确规定了这个行为。文中写道：如果左侧表达式产生 null，或者不存在相等的右侧值且右侧至少有一行产生 null，那么 NOT IN 的结果将是 null 而不是真，这符合 SQL 对 null 值进行布尔组合的通常规则。也就是说，是规格这样定的。

4. 实战中真正的事故现场 - NOT IN (SELECT ...)

几乎没有人会往字面量列表里直接写一个 NULL。事故发生在子查询里，因为那里的列表在代码上是看不见的。

--- 0-1. refund_requests contents ---
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | 1200

4行里只有1行的 customer_id 是 NULL。在这个状态下取出「没有申请过退款的客户」。

--- 4-1. customers who never requested a refund - the naive query ---
  SQL: SELECT id, name FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
  rows returned: 0
  id | name

--- 4-2. how many NULLs are in that subquery column ---
  total | non_null | nulls
  4 | 3 | 1

--- 4-3. same query after deleting the single NULL row ---
  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  ...
  10 | juno

--- 4-4. one NULL row is enough - inserting it back ---
  rows in rr_clean before insert : 3
  rows in rr_clean after insert  : 4
  NOT IN result now              : 0 rows
  after removing it again        : 8 rows

删掉 NULL 那一行就是8行，放回去就是0行，再删掉又是8行。它像开关一样工作。

4.1 规模完全无关

「我们表里有一万条，少一个 NULL 能怎样」这种直觉行不通，下面用数字确认了这一点。

=== B. one NULL among ten thousand rows ===
  blocklist rows                  : 10000   (values 1001..11000, none overlap customers)
  NULLs in blocklist.v            : 0
  SELECT id FROM customers WHERE id NOT IN (SELECT v FROM blocklist)
  rows returned                   : 10

  -- one single NULL row inserted --
  blocklist rows                  : 10001
  NULLs in blocklist.v            : 1
  NULL share of the table         : 1 / 10001 = 0.00999 percent
  rows returned                   : 0

  NOT EXISTS on the same table    : 10 rows
  LEFT JOIN / IS NULL             : 10 rows

一万行里1行 NULL，占比 0.01 个百分点。结果从10行变成了0行。起作用的不是比例，而是存不存在。一个就够了，一万个结果也一样。

4.2 子查询里的 WHERE 偶然把 NULL 挡住的时候

还有更麻烦的情况。当子查询上挂着的另有用途的过滤条件碰巧把 NULL 滤掉时，查询会正常工作。而一旦有人动了那个条件，它就炸了。

=== B-2. a WHERE clause in the subquery can hide the NULL by accident ===
  NOT IN (SELECT v FROM blocklist)                             -> 0 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000)              -> 10 rows
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v IS NULL) -> 0 rows

  the middle query works only because v > 5000 is UNKNOWN for the NULL row
  and therefore drops it. Change the filter and the query breaks again:
  NOT IN (SELECT v FROM blocklist WHERE v > 5000 OR v <= 5000)  -> 10 rows

中间那条查询之所以给出10行，是因为 v > 5000 在 NULL 那一行上是 UNKNOWN，于是那一行早已从子查询结果里被淘汰了。也就是说 NULL 作用了两次，偶然相互抵消。这种查询只要改动一个条件，就会莫名其妙地变成0行。

4.3 外层的列也可能是 NULL

到目前为止我们只看了列表这一侧的 NULL。被比较的那一列是 NULL 时，那一行同样会消失，哪怕列表里一个 NULL 都没有。

=== D. SQLite: when the OUTER value is NULL ===
  rows: 3, one of them region = NULL
  WHERE region NOT IN ('seoul')  -> 1 rows
  id | region
  2 | busan
  the NULL-region row disappeared even though the list has no NULL
  WHERE region NOT IN ('seoul') OR region IS NULL -> 2 rows

3行里有1行的 region 是 NULL，但取出「非首尔地区」时只出来了1行。对于地区未知的客户，无法断定「不是首尔」，于是变成 UNKNOWN 被淘汰了。想把它包含进来，就必须显式写上 OR region IS NULL，这样就变成2行。DuckDB 上的数字也一样。

5. 为什么谁都没察觉

这个缺陷真正可怕的地方不在逻辑，而在发现不了。它藏在三层后面。

  • 不报错。没有异常，没有警告，也没有慢查询日志。监控本该捕捉的信号根本不存在
  • 0行看起来像正常结果。它和「没有符合条件的数据」无法区分
  • 在开发库上能通过。手写的固定数据里没有 NULL
  • 代码看不出任何毛病。只读查询语句的话逻辑是准确的。改变结果的不是代码，而是那一刻表里装着的值
  • 复现是间歇性的。制造出 NULL 的那一行一旦被删掉，查询又恢复正常，所以等你接到报告去查的时候，可能已经看不出问题了

把第三层做成数字看看。

=== B-3. the dev-versus-prod illusion ===
  dev fixture  (3 rows, hand-written, no NULL)       -> 10 rows   test PASSES
  prod data    (4 rows, one NULL from an old import) -> 0 rows    silently empty

测试通过了。因为开发者手写固定数据时没有理由往里塞 NULL。而生产库里的 NULL，多半是早年的迁移、中断的批处理、外部对接失败留下的痕迹。代码评审也看不见，因为子查询返回什么，是由数据而不是由代码决定的。

就这个缺陷而言，往单元测试里加一行含 NULL 的固定数据，比十次代码评审都管用。

6. 替代方案之一 - NOT EXISTS 不会死

把同样的意图用 NOT EXISTS 写出来会怎样，在同一份数据上跑了一遍。

--- 5-1. the same intent written with NOT EXISTS ---
  SELECT c.id, c.name FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)

  rows returned: 8
  id | name
  3 | cedar
  4 | delta
  5 | echo
  6 | flux
  7 | gale
  8 | hive
  9 | iris
  10 | juno

8行。数据没变，NULL 也还在，结果却出来了。原因是判定的依据不同。

  • NOT IN 要比较值并产生一个逻辑值，所以受三值逻辑支配
  • NOT EXISTS 只看内层查询有没有返回哪怕一行。「有还是没有」只有两个值，UNKNOWN 没有容身之处

直接数一下那个 NULL 行的下场。

--- 5-3. why - the NULL row never matches r.customer_id = c.id ---
  id | matching_rows
  1 | 2
  2 | 1
  3 | 0
  4 | 0
  5 | 0
  6 | 0
  7 | 0
  8 | 0
  9 | 0
  10 | 0

customer_id 为 NULL 的第 103 号申请没有挂到任何客户上。NULL = 3 是 UNKNOWN 所以匹配不上，而匹配不上就只是让那个子查询返回0行而已。NULL 污染不到结论，它就在那里停住了。

DuckDB 上也一样。两个引擎的 NOT EXISTS 都是8行。

7. 替代方案之二 - LEFT JOIN 之后接 IS NULL

第三种写法。连接之后只留下匹配失败的行。

--- 6-1. anti-join written as LEFT JOIN + IS NULL ---
  SELECT c.id, c.name FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL

  rows returned: 8

--- 6-2. the three forms side by side, same table, same intent ---
  NOT IN (subquery)     -> 0 rows
  NOT EXISTS            -> 8 rows
  LEFT JOIN / IS NULL   -> 8 rows

这三行就是本文的摘要。同样的数据，同样的意图，同样的正确答案。可偏偏只有第一个是0行。

7.1 这种写法也有陷阱

把 IS NULL 加在哪一列上，决定了答案是对还是错。加在可能为 NULL 的普通列上，就会静静地出错。把第 104 号申请的 amount 改成 NULL 后重跑了一次。

=== A. SQLite: the LEFT JOIN trap, done properly ===
  req_id | customer_id | amount
  101 | 1 | 5000
  102 | 2 | 3000
  103 | NULL | 7000
  104 | 1 | NULL

  WHERE r.req_id IS NULL  (primary key, never NULL in a matched row) -> 8 rows
  WHERE r.amount IS NULL  (nullable column - WRONG choice)           -> 9 rows

  the wrong version leaked customer 1, who DID request a refund:
  id | name | req_id | amount
  1 | aria | 104 | NULL
  3 | cedar | NULL | NULL
  4 | delta | NULL | NULL
  ...
  10 | juno | NULL | NULL

本该是8行的变成了9行，而且确实申请过退款的1号客户混进了「没申请过的客户」名单。匹配其实是成功的，只是那一行的 amount 恰好是 NULL 而已。

规则很明确。IS NULL 的检查只加在连接键或主键这类绝不可能出现 NULL 的列上。用了匹配成功后仍可能为 NULL 的列，就无法区分「匹配失败」和「匹配上了但值是空的」。

8. 防护手段 - 加个 IS NOT NULL 不就行了

最省事的应对是在子查询里加一道护栏。它确实能用。

--- 7-1. the defensive rewrite ---
  SELECT id, name FROM customers
  WHERE id NOT IN (SELECT customer_id FROM refund_requests WHERE customer_id IS NOT NULL)

  rows returned: 8

出来8行。但有三个理由说明不能把它叫作根本的解决。

  • 必须重复。凡是用了 NOT IN 的地方都得一处不漏地加上，漏掉一处那条查询就会悄悄变成0行。需要人每次都记得的防护，迟早会失效
  • 看不见。只读外层查询的人看不到这道护栏。不知道它为什么在那儿，重构时就容易被删掉
  • 会改变含义。如果那个 NULL 本身是信息，删掉的瞬间事实也就消失了

第三点尤其重要。来看看示例里那个 NULL 究竟是什么。

--- 7-3. what the NULL actually meant here ---
  req_id | customer_id | amount
  103 | NULL | 7000
  a 7000 refund with no customer attached - dropping it hides a data bug

一笔金额 7000、却没有关联客户的退款请求。这不是可以忽略的杂音，而是某处参照完整性已被破坏的证据。用 IS NOT NULL 滤掉的那一刻，这个事实就从报表里永远消失了。

所以顺序应该是这样。

  1. 先看那个 NULL 为什么在那里。SELECT * FROM t WHERE col IS NULL
  2. 如果是不该进来的值，就给列加上NOT NULL 和外键约束，从源头堵住
  3. 如果是可能进来的值，就把写法改成 NOT EXISTS，走出 NULL 的影响范围
  4. IS NOT NULL 护栏只在救火时用，并留下注释说明为什么可以丢掉它

9. NULL 藏身的其他地方之一 - 聚合函数

出问题的不只是 NOT IN。同样的三值逻辑在聚合里以另一种形式出现。customers.credit 的10行中有4行是 NULL。

--- 8-1. COUNT(*) vs COUNT(col) on customers.credit ---
  count_star | count_credit | count_distinct_credit | sum_credit | avg_credit | min_credit | max_credit
  10 | 6 | 6 | 1230 | 205.0 | 60 | 420

COUNT(*) 是 10，COUNT(credit) 是 6。前者数行，后者只数有值的那些。而平均值的分母到底是哪一个，在实战中一直是个麻烦。

--- 8-2. AVG denominator - it divides by the non-null count, not the row count ---
  s | n_nonnull | n_all | avg_builtin | s_div_nonnull | s_div_all
  1230 | 6 | 10 | 205.0 | 205.0 | 123.0

--- 8-3. COALESCE changes the answer, and that is the point ---
  avg_ignoring_nulls | avg_nulls_as_zero
  205.0 | 123.0

205.0 和 123.0。同一份数据算出的两个「平均值」。AVG(credit) 把 1230 除以 6，而 AVG(COALESCE(credit, 0)) 把 1230 除以 10。

哪个才对，取决于 NULL 的含义。如果它表示「额度还没审核」，从分母里剔除才对；如果它表示「额度是 0」，放进去才对。这两者 SQL 都不会替你决定。这正是滥用 COALESCE 危险的原因：它没有消除眼前的 NULL，而是改变了你在测量的东西。

空集合上又是另一回事。

--- 8-4. aggregates over an empty set ---
  c | s | a | m
  0 | NULL | NULL | NULL
  COUNT returns 0, SUM/AVG/MAX return NULL - a SUM of nothing is not 0

COUNT 返回 0，而 SUM 返回 NULL。「什么都没有的总和是 0」看起来像常识，SQL 却不这么做。所以把聚合结果直接塞进应用的整数类型里，就会在那一点上触发空引用。要防住，就得有意识地写 COALESCE(SUM(x), 0)。DuckDB 上完全相同。

表达式对 NULL 的处理执行确认值
COUNT(*)数行10
COUNT(col)排除 NULL6
SUM / MIN / MAX忽略 NULL1230 / 60 / 420
AVG(col)分母是非 NULL 的个数205.0
AVG(COALESCE(col,0))分母是总行数123.0
空集合的 SUM/AVG/MAX返回 NULLNULL

10. NULL 藏身的其他地方之二 - UNIQUE 约束

「这一列是 UNIQUE，所以没有重复」这句话在 NULL 面前不成立。

--- 9-1. inserting several NULLs into a UNIQUE column ---
  insert 'A' -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert NULL -> OK
  insert 'A' again -> IntegrityError: UNIQUE constraint failed: u_test.code
  rows now: 4
  id | code
  1 | A
  2 | NULL
  3 | NULL
  4 | NULL

三个 NULL 全都进去了。而第二次插入同一个字符串 'A' 时，则被准确地拒绝了。因为唯一约束把 NULL 之间视为不同的值。NULL = NULL 是 UNKNOWN，所以没有依据判定「这是重复」。

复合 UNIQUE 也一样。

--- 9-2. same thing on a multi-column UNIQUE ---
  insert ('x', 'y') -> OK
  insert ('x', NULL) -> OK
  insert ('x', NULL) -> OK
  insert (NULL, NULL) -> OK
  insert (NULL, NULL) -> OK
  rows now: 5

('x', NULL) 进了两次，(NULL, NULL) 也进了两次。总共5行全部插入成功。在 DuckDB 1.5.5 上同样是三个 NULL 都进去了，只有重复的 'A' 被拒绝。也就是说两个引擎表现一致。

SQLite 官方文档自己承认了这种不一致。它明确写道：在 UNIQUE 列上 NULL 之间是相互区分的，但在 SELECT DISTINCT 和 UNION 中则不区分；并记录说这多少有些武断，但这是为了与 Oracle、PostgreSQL、DB2 的行为保持一致而做出的决定。在同一个引擎内部规则相反，是一种有意为之的状态。

实战含义。如果你写下「营业执照号是 UNIQUE，所以放心」，而那一列却允许 NULL，那么营业执照号为空的行可以无限量地进来。要真正防住重复，必须把 UNIQUE 和 NOT NULL 一起加上。另外据称 PostgreSQL 15 起新增了让 UNIQUE 把 NULL 视为相同值的选项，但本文没有实际执行确认过，因此不作断言。

11. NULL 藏身的其他地方之三 - GROUP BY 与 DISTINCT

规则在这里翻转了。用 = 判定为不相等的那些 NULL，在分组时却合成了一个。

--- 10-1. GROUP BY region ---
  region | n
  busan | 3
  seoul | 3
  NULL | 2
  jeju | 2
  the two NULL-region rows landed in ONE group

--- 10-2. but = says they are not equal ---
  eq_test | is_test
  NULL | 1

region 为 NULL 的第 8 号和第 10 号客户被归成了一组（2行）。可就在下一行，把这两个值用 = 比较得到的是 UNKNOWN，要用 IS 比较才得到真。同一份数据上并存着两套相等性标准。

--- 10-3. DISTINCT collapses NULLs the same way ---
  all_rows | distinct_region
  10 | 3
  region
  NULL
  busan
  jeju
  seoul

--- 10-4. UNION also dedupes NULLs ---
  n
  2

COUNT(DISTINCT region) 是 3，因为它不数 NULL。可是 SELECT DISTINCT region 的结果行是 4个，其中一个是 NULL。同样是 DISTINCT，在聚合函数里面还是外面，数字就不一样。UNION 也把两个 NULL 折成一个，给出了2行。

操作NULL 之间算相等吗执行确认
col1 = col2不相等（UNKNOWN）返回 NULL
col1 IS col2相等1（真）
GROUP BY相等NULL 组 1 个（2行）

COUNT(DISTINCT col)不计入3

UNIQUE 约束不相等成功插入3个 NULL

12. NULL 藏身的其他地方之四 - ORDER BY，以及各引擎不同之处

到目前为止两个引擎的数字全部一致。从这里开始分道扬镳。同样的数据用同样的语句排序，结果却不同。

SQLite 3.49.1
--- 11-1. default placement, ascending ---
  id | credit
  2 | NULL
  4 | NULL
  7 | NULL
  10 | NULL
  9 | 60
  6 | 90
  3 | 150
  8 | 210
  1 | 300
  5 | 420

--- 11-2. default placement, descending ---
  id | credit
  5 | 420
  1 | 300
  8 | 210
  3 | 150
  6 | 90

SQLite 在升序时把 NULL 放在最前面，降序时放在最后面，也就是把 NULL 当成比任何值都小的东西来处理。DuckDB 不一样。

DuckDB 1.5.5
=== 8. ORDER BY NULL placement ===
  ORDER BY credit ASC               -> 60 90 150 210 300 420 NULL NULL NULL NULL
  ORDER BY credit DESC              -> 420 300 210 150 90 60 NULL NULL NULL NULL

--- 8-1. the configured default ---
  default_null_order | default_order
  NULLS_LAST | ASCENDING

DuckDB 无论升序还是降序都把 NULL 放在最后。而且这是一个配置项。改一下试试。

=== E. DuckDB: the default NULL order is a setting ===
  default_null_order = NULLS_LAST
  as shipped                         ORDER BY v ASC -> 1 5 9 NULL
  default_null_order = NULLS_FIRST
  after SET NULLS FIRST              ORDER BY v ASC -> NULL 1 5 9
  the same query text produced two different orders on one engine

PostgreSQL 官方文档规定的又是另一套规则。文中写道：默认情况下 null 值排序时被当作比任何非 null 值都大，因此 NULLS FIRST 是 DESC 排序的默认值，其余情况下默认是 NULLS LAST。把三者汇成一张表就是这样。

引擎ORDER BY col ASCORDER BY col DESC依据
SQLite 3.49.1NULL 在前NULL 在后执行确认
DuckDB 1.5.5（默认设置）NULL 在后NULL 在后执行确认
PostgreSQLNULL 在后NULL 在前官方手册

三个引擎互不相同。而这个差异一旦碰上 LIMIT，立刻变成真实的事故。「最新一条」「前十条」「分页的第一页」——凡是截取排序结果头尾来用的代码，在换引擎或改配置的那一刻就会悄悄给出不同的答案。

解决办法是写明。两个引擎都支持 NULLS FIRST 和 NULLS LAST。

--- 11-3. explicit NULLS FIRST / NULLS LAST (SQLite 3.49.1) ---
  ORDER BY credit ASC NULLS FIRST     -> NULL NULL NULL NULL 60 90 150 210 300 420
  ORDER BY credit ASC NULLS LAST      -> 60 90 150 210 300 420 NULL NULL NULL NULL
  ORDER BY credit DESC NULLS FIRST    -> NULL NULL NULL NULL 420 300 210 150 90 60
  ORDER BY credit DESC NULLS LAST     -> 420 300 210 150 90 60 NULL NULL NULL NULL

在不支持这个子句的引擎上，再加一个由布尔表达式构成的排序键这种绕法是管用的。

--- 11-4. the portable workaround when NULLS FIRST/LAST is unavailable ---
  SELECT id, credit FROM customers ORDER BY (credit IS NULL) ASC, credit ASC

  id | credit
  9 | 60
  6 | 90
  3 | 150
  8 | 210

顺带一提，排序和 MIN、MAX 的行为彼此不同。这一点也确认过了。

=== C. SQLite: where NULL sorts, and what MIN/MAX think ===
  ORDER BY v ASC  -> NULL 1 5 9
  ORDER BY v DESC -> 9 5 1 NULL
  min_v | max_v | n | n_nonnull
  1 | 9 | 4 | 3
  so NULL sorts as if smaller than every value, yet MIN() skips it entirely

排序时 NULL 像最小的值一样排在最前面，而 MIN() 却完全无视它，返回 1。「排序后取第一行」和 MIN() 不是一回事。

13. 诊断法 - 从已有的查询里把这个风险找出来

原理弄明白了，接下来就该排查已经在线上跑的查询了。这是有顺序的。

13.1 第一步 - 三十秒出结论的 SQL

对可疑的子查询列，只要跑这一条就够了。

SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;

下面是在示例表上跑出来的结果。

--- 12-1. does this subquery column contain NULL at all ---
  total_rows | non_null | null_rows | verdict
  4 | 3 | 1 | DANGEROUS - NOT IN will return 0 rows

--- 12-2. the same check on a NULL-free column ---
  total_rows | non_null | verdict
  4 | 4 | SAFE for NOT IN

判定标准很简单。只要 COUNT(*) 和 COUNT(列) 的数字不同，针对那一列的所有 NOT IN 就已经是坏的。这条判定在 DuckDB 上给出了同样的结果。

13.2 第二步 - 确认表结构是否作了保证

现在 NULL 有0条，和表结构禁止 NULL，是完全不同的两件事。前者明天就会坏。

--- 12-3. is the column even declared NOT NULL - read the schema ---
  name | type | notnull | pk
  req_id | INTEGER | 0 | 1
  customer_id | INTEGER | 0 | 0
  amount | INTEGER | 0 | 0

customer_id 的 notnull 是 0，也就是说表结构允许 NULL。即使今天没有 NULL，也不能说是安全的。在 PostgreSQL 系里用下面这条看同样的东西。

SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';

13.3 第三步 - 看清那个 NULL 到底是什么

删之前一定要先做这一步。

SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;

正如第8节所示，那个 NULL 往往是数据缺陷的证据。在抹掉症状之前先看病因。

13.4 第四步 - 三种写法并排跑，比数字

这是最可靠的确认方式。把同一个意图写成三种，看数字是否分歧。分歧了，NOT IN 就是罪犯。

  step 1  SELECT COUNT(*) FROM t;                 -- 4
  step 2  SELECT COUNT(col) FROM t;               -- 3
  if the two numbers differ, every NOT IN against that column is already broken

13.5 第五步 - 执行计划也会给线索

把三种写法的计划打印出来看看差别。

--- 13-7. query plan of the three anti-join forms (SQLite) ---
  NOT IN     : SCAN customers / USING INDEX ix_rr_cust FOR IN-OPERATOR
  NOT EXISTS : SCAN c / CORRELATED SCALAR SUBQUERY 1
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?)
  LEFT JOIN  : SCAN c
               SEARCH r USING COVERING INDEX ix_rr_cust (customer_id=?) LEFT-JOIN

三者都用到了索引。也就是说改用 NOT EXISTS 并不是牺牲性能的选择。在这个示例的规模下，只是计划的形态不同，索引的利用是等同的。顺带一提，IS NULL 条件也是用索引处理的。

--- 13-6. index scan still finds NULLs - IS NULL is indexable here ---
  WHERE customer_id IS NULL : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)
  WHERE customer_id = 1     : SEARCH refund_requests USING INDEX ix_rr_cust (customer_id=?)

14. 其他陷阱 - CHECK、CASE、字符串、空集合

又确认了几处同样原理会浮现的地方。

14.1 CHECK 约束会放 UNKNOWN 过去

--- 13-2. CHECK constraint passes when the result is UNKNOWN ---
  insert qty=5 -> OK
  insert qty=NULL -> OK
  insert qty=-1 -> IntegrityError: CHECK constraint failed: qty > 0
  rows now: 2

明明加了 CHECK (qty > 0)，NULL 却通过了。-1 则被准确拒绝。因为 NULL > 0 是 UNKNOWN，而约束只在条件为假时才拒绝。DuckDB 上也一样。如果数量必须为正，只靠 CHECK 是不够的，必须另外加上 NOT NULL。

14.2 CASE WHEN col = NULL 永远不会命中

--- 13-1. CASE WHEN col = NULL never fires ---
  id | credit | branch
  1 | 300 | has-value
  2 | NULL | matched-is
  10 | NULL | matched-is

WHEN credit = NULL THEN 'matched-eq' 这个分支一次都没有被选中。连 NULL 的行都流到了下一个分支 WHEN credit IS NULL。因为 = NULL 不是语法错误，它会静静地变成死代码。这就是代码评审中看到这个模式必须指出来的理由。

14.3 一次字符串拼接就能抹掉整句

--- 13-3. string concatenation with NULL ---
  concat_result | with_coalesce
  NULL | fallback

'total: ' || NULL 的结果不是 'total: '，而是整体为 NULL。在拼装报表字符串时只要有一列是空的，整句话就消失了。这里正是正当使用 COALESCE 的典型场景。

14.4 列表为空时 NOT IN 会返回全部

--- 13-5. an empty subquery makes NOT IN return everything ---
  NOT IN (SELECT customer_id FROM refund_requests WHERE 1=0) -> 10 rows
  NOT EXISTS on the same empty set                           -> 10 rows

子查询返回0行时，NOT IN 会返回全部10行。这在逻辑上是对的（不属于一个空列表的东西就是全部）。不过值得记住的是，在0行和全部行这两个极端之间，摆着一个 NULL 作为开关。在删除批处理或权限过滤里，这两个极端会造成性质完全不同的事故。

14.5 左侧是 NULL 时 IN 和 NOT IN 都是 UNKNOWN

--- 13-4. NOT IN with NULL on the LEFT side ---
  left_null_notin | left_null_in
  NULL | NULL

这是 4.3 节内容的浓缩。NULL NOT IN (1,2) 和 NULL IN (1,2) 都是 UNKNOWN。即使列表里没有 NULL，只要左侧是 NULL，那一行两边都通不过。

14.6 空值安全的比较运算符

想把 NULL 之间判定为相等时，有可用的运算符。在 SQLite 3.49.1 上确认过。

--- 3-5. null-safe comparison operators available here ---
  is_ | is_not | isnd | isnd2 | isd
  1 | 0 | 0 | 1 | 1
  • NULL IS NULL 得 1（真）。在 SQLite 里 IS 起到空值安全等号的作用
  • NULL IS NOT DISTINCT FROM NULL 得 1（真）。把 NULL 之间视为相等
  • 1 IS NOT DISTINCT FROM NULL 得 0（假）。是确定的假，不是 UNKNOWN
  • 1 IS DISTINCT FROM NULL 得 1（真）

DuckDB 上结果相同（false、true、true）。IS DISTINCT FROM 这一族的结果绝不会变成 UNKNOWN。即便两个值里含有「不知道」，答案也会落定为真或假。在需要比较两列、并把两边的 NULL 当作「相同」来处理的变更检测逻辑里，这很有用。

15. 判断表 - 什么时候用什么

把前面所有的执行结果折成一张表。这张表就是实战中真正要用的成果物。

意图用什么理由与注意点
找子查询结果里没有的行（最常见的情况） NOT EXISTS 与 NULL 无关地正常工作。意图能当句子读，而且确认过的执行计划里照样用索引。把它当默认选项
反连接的同时还要 SELECT 对方表的列 LEFT JOIN ... IS NULL 连接结果可以直接用。IS NULL 必须加在主键或连接键上 — 加在普通列上时8行变成了9行
排除少量硬编码的字面值 NOT IN ('a','b') 列表里没有 NULL，这一点用眼睛就能确认。仅限这种情况下是安全的
子查询的列声明为 NOT NULL NOT IN 也可以 由表结构保证。但一次改表就会坏掉。请用注释留下这层依赖
希望值为 NULL 的行也包含在结果里 显式写出 ... OR col IS NULL 外层列如果是 NULL，那一行也会被淘汰。这是1行和2行的差别
把两个值连同 NULL 一起判定相等或不等 IS NOT DISTINCT FROM 结果不会变成 UNKNOWN。适合变更检测和比较逻辑
临时救火 WHERE col IS NOT NULL 护栏 是护栏，不是解决。必须在所有地方重复，而且 NULL 若是信息，事实就消失了

压缩成一句话就是：要找集合里没有的东西时，把 NOT EXISTS 当默认；NOT IN 只用在列表是字面值、或者列声明为 NOT NULL 的场合。

16. 总结 - 这不是缺陷

把这篇文章确认过的东西再数一遍。

  • 列表里一个 NULL 就是 0行，去掉就是 8行。两条查询都没报错、都成功了
  • 同样的列表下 IN 是 2行，工作正常
  • 逐行的条件表达式取值里一个 1 都没有：两个假，其余八个全是 UNKNOWN
  • 一万行里1行 NULL（0.01 个百分点）就让10行变成了0行
  • NOT EXISTS 8行，LEFT JOIN IS NULL 8行，只有 NOT IN 是 0行
  • 在 LEFT JOIN 里选错检查的列，就变成 9行并混入错误答案
  • 开发固定数据以10行通过，生产数据是 0行 — 测试抓不住
  • 两个平均值 205.0 和 123.0，空集合的 SUM 是 NULL
  • UNIQUE 列上 NULL 成功插入3个，CHECK (qty > 0) 也成功插入了 NULL
  • ORDER BY 中 NULL 的位置在三个引擎上互不相同

这一切都出自同一个定义。NULL 不是「没有值」，而是「不知道」。无法断定一个不知道的值是否在列表之内，所以是 UNKNOWN；而 WHERE 只放行 TRUE，所以是0行。SQL 选择了宁可不给答案，也不给一个错的答案。这就是这套设计的一致性。

问题在于，这份一致性是不带报错出现的。类型错误会在编译时被抓住，语法错误会在执行时被抓住。可这一个是在成功的状态下变空的。于是人就用「大概是没数据吧」把它打发过去了。

应对只需两行。第一，找集合里没有的东西时，把 NOT EXISTS 设为默认。第二，往测试固定数据里放一行 NULL。第二条尤其便宜又有力。本文里所有的失败案例，只要有一行含 NULL 的固定数据，都能在上线前被抓住。

常见问题

Q. NOT IN 返回0行却不报错，为什么？

只要列表或子查询结果里有哪怕一个 NULL 就会这样。确认过：10行的表上 id NOT IN (1, 2, NULL) 是 0行，只去掉 NULL 的 id NOT IN (1, 2) 是 8行，而且两条都正常结束。因为 SQL 的逻辑值不是真、假两个，而是真、假、不知道三个。与 NULL 的比较全都变成不知道，NOT 不知道 依然是不知道，而 WHERE 只放行真。这不是语法错误，而是按定义算出的结果，所以不报错。

Q. 为什么 IN 好好的，只有 NOT IN 出问题？

区别在匹配的行上能不能得到真。IN (1, 2, NULL) 是 2行，去掉 NULL 的也是 2行，一样。IN 是用 OR 把等号比较串起来，而 OR 只要有一个真，其余是不知道也能确定为真。反过来 NOT IN 里没有一行能变成真。把逐行的值打印出来是 id 1 和 2 为 0，其余8行全是 NULL，一个真都没有。

Q. 改写成 NOT EXISTS 真的能解决吗？

能解决。同一份数据上 NOT IN 是 0行，NOT EXISTS 是 8行，LEFT JOIN IS NULL 是 8行。NOT EXISTS 看的是行存不存在而不是值的比较，所以 UNKNOWN 没有容身之处。引用列为 NULL 的行满足不了等号，只是匹配不上而已；实际数每个客户的匹配数，那一行没有挂到任何客户上。不过 LEFT JOIN 形式另有陷阱：把 IS NULL 加在非主键的普通列上，结果是 9行并混入了错误答案。

Q. 在子查询里加个 IS NOT NULL 不就行了吗？

确实能用（8行）。但它是护栏，不是解决。第一，必须在用了 NOT IN 的所有地方重复，漏一处那条查询就悄悄变成0行。第二，只读外层查询的人看不见，重构时容易被删。第三，那个 NULL 若是信息，含义就变了。示例里那一行是金额 7000、没有关联客户的申请，也就是参照完整性被破坏的证据。根本对策是加 NOT NULL 约束，或把写法改成 NOT EXISTS。

Q. 还有哪些地方会因为 NULL 悄悄算错？

至少五处执行确认过。聚合里 COUNT(*) 是 10 而 COUNT(credit) 是 6，平均值分成 205.0 和 123.0。空集合上 COUNT 是 0，但 SUM、AVG、MAX 都是 NULL。UNIQUE 约束里进了 3个 NULL。GROUP BY 中用 = 判定不相等的 NULL 却归成了一组。ORDER BY 里 SQLite 把 NULL 放升序最前，DuckDB 放最后，答案因引擎而异。

> 依据: 在 SQLite 3.49.1 / DuckDB 1.5.5 / Windows 10 上实际执行验证，并与 PostgreSQL 官方手册核对
> 把这个文件直接贴给 AI，写上「按这些标准检查我们的查询」即可。
> 关键只有一句：**NULL 不是「没有值」，而是「不知道」。** 无法断定一个不知道的值是否在列表里，所以结果是 UNKNOWN，而 WHERE 只放行 TRUE，于是变成 0 行。

## 0. 症状卡 — 什么时候需要这个文件

- 查询成功了。**没有报错。**
- 但结果是 **0 行**。
- 昨天还有结果。或者在开发库上有结果。
- 查询里有 `NOT IN (SELECT ...)`。

→ 去跑 §3 的诊断 SQL。三十秒就够。

## 1. 三值逻辑真值表

SQL 的逻辑值不是 TRUE / FALSE 两个，而是 **TRUE / FALSE / UNKNOWN 三个**。

### 1-1. 比较运算符遇到 NULL

| 表达式 | 结果 | 备注 |
|---|---|---|
| `1 = 1` | TRUE | |
| `1 = 2` | FALSE | |
| `1 = NULL` | **UNKNOWN** | 不是 FALSE |
| `1 <> NULL` | **UNKNOWN** | 不是 TRUE |
| `NULL = NULL` | **UNKNOWN** | 连「不相等」都说不了 |
| `1 > NULL` | **UNKNOWN** | 所有比较运算符都一样 |
| `NULL IS NULL` | TRUE | 只有 `IS` 给出确定值 |
| `1 IS NULL` | FALSE | |

### 1-2. AND / OR / NOT

| 表达式 | 结果 |
|---|---|
| `UNKNOWN OR TRUE` | **TRUE** |
| `UNKNOWN OR FALSE` | UNKNOWN |
| `UNKNOWN AND TRUE` | UNKNOWN |
| `UNKNOWN AND FALSE` | **FALSE** |
| `NOT UNKNOWN` | **UNKNOWN** |

读法是这样：OR 只要有一个 TRUE 就确定了。AND 只要有一个 FALSE 就确定了。**除此以外，「不知道」会传染。**

### 1-3. WHERE 只放行 TRUE

| WHERE 子句的值 | 该行 |
|---|---|
| TRUE | 通过 |
| FALSE | 淘汰 |
| **UNKNOWN** | **淘汰** |

UNKNOWN 在过滤这一步被当作 FALSE 处理。就是这一条规则，成了这类缺陷全部的出口。

### 1-4. 所以 IN 活着而 NOT IN 死了

`x IN (a, b, c)` 会展开成 `x = a OR x = b OR x = c`。

| 情形 | `IN (1, 2, NULL)` | `NOT IN (1, 2, NULL)` |
|---|---|---|
| x = 1（在列表中） | `TRUE OR ... OR UNKNOWN` = **TRUE** → 通过 | `NOT TRUE` = **FALSE** → 淘汰 |
| x = 7（不在列表中） | `FALSE OR FALSE OR UNKNOWN` = **UNKNOWN** → 淘汰 | `NOT UNKNOWN` = **UNKNOWN** → 淘汰 |

- `IN` 在匹配的行上会得到 TRUE，所以**工作正常**。
- `NOT IN` 在任何行上都得不到 TRUE。匹配则 FALSE，不匹配则 UNKNOWN。**所以永远是 0 行。**

## 2. 三种反连接对比表

求「在 A 里而不在 B 里」的三种写法。以下是在同一份数据上执行的结果：客户 10 行，请求 4 行，其中引用列为 NULL 的有 1 行。

| 写法 | 结果 | NULL 安全 | 判定依据 | 注意点 |
|---|---|---|---|---|
| `NOT IN (SELECT col FROM t)` | **0 行** | 否 | 三值逻辑 | col 里只要有一个 NULL 就全灭。不报错 |
| `NOT EXISTS (SELECT 1 FROM t WHERE t.col = a.id)` | **8 行** | 是 | 行是否存在 | NULL 行满足不了 `=`，就只是匹配不上而已 |
| `LEFT JOIN t ON t.col = a.id WHERE t.pk IS NULL` | **8 行** | 是 | 匹配失败的行 | **`IS NULL` 必须检查 NOT NULL 的列（主键）** |

只有 `NOT IN` 给出了不同的答案。另外两个一致。

### 2-1. LEFT JOIN 写法里的陷阱

在 `WHERE` 里选错了检查的列，就会静静地出错。

| 检查的列 | 结果 | 判定 |
|---|---|---|
| `r.req_id IS NULL`（主键，匹配上的行绝不为 NULL） | 8 行 | 正确 |
| `r.amount IS NULL`（值可能为 NULL 的普通列） | **9 行** | 错误 — 真的提过请求的客户混进来了 |

**规则：LEFT JOIN 反连接的 `IS NULL` 只能加在连接键或主键上。**

### 2-2. 按意图的判断表

| 想做的事 | 用什么 | 理由 |
|---|---|---|
| 找子查询结果里没有的行 | **`NOT EXISTS`** | 不受 NULL 影响，而且意图能当句子读 |
| 反连接的同时还要 SELECT 对方表的列 | **`LEFT JOIN ... IS NULL`** | 连接结果可以直接用 |
| 排除少量硬编码的字面值 | `NOT IN ('a','b')` | 列表里没有 NULL，用眼睛就能确认 |
| 子查询的列**声明为 `NOT NULL`** | `NOT IN` 也可以 | 但改一次表结构就可能坏掉 |
| 意图就是「值为 NULL 的行也要包含」 | **显式**写出 `... OR col IS NULL` | 外层列如果是 NULL，那一行也会被淘汰 |

## 3. 诊断 SQL — 直接复制使用

### 3-1. 这一列对 NOT IN 安全吗（三十秒）

```sql
SELECT COUNT(*)                       AS total_rows,
       COUNT(the_column)              AS non_null,
       COUNT(*) - COUNT(the_column)   AS null_rows,
       CASE WHEN COUNT(*) = COUNT(the_column)
            THEN 'SAFE for NOT IN'
            ELSE 'DANGEROUS - NOT IN returns 0 rows' END AS verdict
FROM the_table;
```

如果 `COUNT(*)` 和 `COUNT(列)` 的数字**不一样，那么针对这一列的所有 `NOT IN` 都已经是坏的。**

### 3-2. 表结构是否保证了 NOT NULL

```sql
-- SQLite
SELECT name, type, "notnull", pk FROM pragma_table_info('the_table');

-- PostgreSQL 系
SELECT column_name, is_nullable, data_type
FROM information_schema.columns
WHERE table_name = 'the_table';
```

除非看到 `is_nullable = 'NO'`（或 SQLite 的 `notnull = 1`），**今天没有 NULL 并不等于安全。**明天就会进来。

### 3-3. 看清这个 NULL 实际代表什么

```sql
SELECT * FROM the_table WHERE the_column IS NULL LIMIT 20;
```

删之前先看这个。NULL 往往是**数据缺陷的证据**。在示例里它是一笔没有关联到客户的退款请求。

### 3-4. 三种都跑一遍，比数字

```sql
SELECT 'not_in'     AS form, COUNT(*) AS n FROM (
  SELECT id FROM customers WHERE id NOT IN (SELECT customer_id FROM refund_requests)
)
UNION ALL
SELECT 'not_exists', COUNT(*) FROM (
  SELECT c.id FROM customers c
  WHERE NOT EXISTS (SELECT 1 FROM refund_requests r WHERE r.customer_id = c.id)
)
UNION ALL
SELECT 'left_join', COUNT(*) FROM (
  SELECT c.id FROM customers c
  LEFT JOIN refund_requests r ON r.customer_id = c.id
  WHERE r.req_id IS NULL
);
```

三个数字不一致的话，第一个就是罪犯。

### 3-5. 不要忘了外层的列

即使列表里没有 NULL，**被比较的那一列**如果是 NULL，那一行也会被淘汰。

```sql
-- region 为 NULL 的行会从这个条件里消失
SELECT * FROM t WHERE region NOT IN ('seoul');

-- 想包含就必须写出来
SELECT * FROM t WHERE region NOT IN ('seoul') OR region IS NULL;
```

## 4. NULL 藏身的其他位置 — 汇总表

| 位置 | 行为 | 实测值（10 行，4 个 NULL） |
|---|---|---|
| `COUNT(*)` | 数行 | 10 |
| `COUNT(col)` | **排除 NULL** | 6 |
| `SUM` / `AVG` / `MIN` / `MAX` | **忽略 NULL** | AVG = 205.0 |
| `AVG(COALESCE(col, 0))` | 把 NULL 当 0 来数 | **123.0** — 答案变了 |
| 空集合上的 `SUM` / `AVG` / `MAX` | **返回 NULL**（不是 0） | NULL |
| `UNIQUE` 约束 | **允许多个 NULL** | 成功插入 3 个 NULL |
| `GROUP BY` | **NULL 之间归为一组** | NULL 组 1 个（2 行） |
| `SELECT DISTINCT` / `UNION` | **对 NULL 去重** | distinct 3 个 |
| `CHECK` 约束 | 结果为 UNKNOWN 时**放行** | `CHECK (qty > 0)` 成功插入了 NULL |
| `CASE WHEN col = NULL` | **永远不会命中** | 必须用 `IS NULL` |
| 字符串拼接 `'a' \|\| NULL` | **NULL** | 整个串都消失 |

`UNIQUE` 认为 NULL 之间互不相同，`DISTINCT` 认为它们相同。**在同一个引擎里，规则是相反的。**

## 5. ORDER BY 里 NULL 的位置 — 各引擎不同

| 引擎 | `ORDER BY col ASC` | `ORDER BY col DESC` | 依据 |
|---|---|---|---|
| SQLite 3.49.1 | **NULL 在前** | NULL 在后 | 执行确认 |
| DuckDB 1.5.5（默认设置） | NULL 在后 | **NULL 在后** | 执行确认 |
| PostgreSQL | NULL 在后 | **NULL 在前** | 官方手册 |

三个引擎互不相同。**任何把 `ORDER BY` 结果掐头去尾的代码（LIMIT、分页、取最新一条），在换引擎的那一刻答案就会悄悄改变。**

可移植的做法：

```sql
-- 显式写出 NULLS FIRST / NULLS LAST（SQLite 3.30+、PostgreSQL、DuckDB 都支持）
SELECT * FROM t ORDER BY col ASC NULLS LAST;

-- 不支持该子句的引擎上的绕法
SELECT * FROM t ORDER BY (col IS NULL) ASC, col ASC;
```

## 6. 代码评审检查语句 — 直接贴进评审意见

- [ ] **你在表结构里确认过这个 `NOT IN` 子查询的列声明为 `NOT NULL` 了吗？** 现在没有 NULL，和表结构禁止 NULL，是两件事。
- [ ] **这个 `NOT IN (SELECT ...)` 能改写成 `NOT EXISTS` 吗？** 能改就该改。性能通常相当或更好。
- [ ] **如果你在子查询里加了 `WHERE col IS NOT NULL` 的护栏，注释里写明了为什么可以丢掉那个 NULL 吗？** 护栏遮住的是症状，不是病因。
- [ ] **LEFT JOIN 反连接的 `IS NULL` 加在主键或连接键上了吗？** 加在可能为 NULL 的普通列上，匹配上的行会混进结果。
- [ ] **被比较的外层列可能为 NULL 吗？** 如果可能，请确认让那些行从结果中消失是有意的；否则显式写上 `OR col IS NULL`。
- [ ] **有没有写成 `= NULL` 或 `<> NULL` 的条件？** 它们永远是 UNKNOWN。请改成 `IS NULL` / `IS NOT NULL`。
- [ ] **`COUNT(col)` 和 `COUNT(*)` 之间，你用的是想用的那个吗？** 前者会排除 NULL。
- [ ] **`AVG` 的分母应该是总行数，还是排除 NULL 后的行数？** 默认是后者。想要前者就用 `COALESCE` 写明。
- [ ] **如果你在用 `LIMIT` 截取 `ORDER BY` 的结果，写明 `NULLS FIRST/LAST` 了吗？** 各引擎的默认值互不相同。
- [ ] **测试的固定数据里有 NULL 吗？** 手写的固定数据通常没有 NULL，所以这个缺陷能通过测试，只在生产环境发作。
- [ ] **如果你说用 `UNIQUE` 防住了重复，那列为 NULL 的时候也防住了吗？** 大多数引擎里可以进多个 NULL。
- [ ] **你是不是假设 `CHECK` 约束也会挡住 NULL？** 条件为 UNKNOWN 时会放行。请另外加 `NOT NULL`。

## 7. 一段话总结

`NOT IN` 不是坏掉的功能。它是把 NULL 意为「不知道」这个定义贯彻到底的结果。**无法断定一个不知道的值是否在列表之内，所以答案是 UNKNOWN；而 WHERE 只放行 TRUE，所以得到 0 行。**这在逻辑上是正确的。问题在于，这份正确性是**不带报错**出现的，于是所有人都用「大概是没数据吧」把它打发过去。所以规则只有一条：**要找集合里没有的东西时，把 `NOT EXISTS` 当默认选项；`NOT IN` 只留给列表是字面值、或者列声明为 `NOT NULL` 的场合。**
