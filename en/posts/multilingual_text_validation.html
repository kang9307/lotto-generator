Translation is done, they say, and yet something is still in there

Say you ship product documentation in five languages. There are four thousand files, half translated by people and half by machine. A reviewer opens perhaps twenty of them, decides they look fine, and signs off. Two months later somebody finds a Korean sentence sitting in the middle of an English page. By then nobody can say which batch it came in with.

What makes this defect annoying is not that it is hard. It is the asymmetry: a machine finds it in seconds and a human essentially never will. People do not read four thousand documents. They read twenty, fix the one thing that jumped out, and the remaining three thousand nine hundred and eighty ship as they are.

So this is not a review problem. It is a checker problem. And the hard part of building the checker is not finding contamination. It is deciding which of the things you found were supposed to be there. Product names stay in the original. String literals inside code samples must not be translated. Glossed terms deliberately put two languages side by side. A checker that cannot make those distinctions emits hundreds of warnings, and by day three nobody is reading them.

Here is the conclusion up front. Character codes get you further than you would expect, and the common practice of hand-writing Unicode block ranges misses roughly half of it while simultaneously flagging perfectly good sentences. Switching to script properties removes both problems. What remains after that is exception design, and from there on you are not picking a correct answer, you are picking which cost to pay.

1. Why human eyes cannot catch this

Foreign script does not appear where it is easy to see. A whole heading in the wrong language gets noticed by everyone. That is not the problem.

  • One sentence in the middle of a paragraph. The text before and after flows normally, so scrolling readers pass right over it
  • The third row of a table. If one row out of ten still holds source text, a sweep of the table does not register it
  • Places that never render. Image alt text, form hints, error messages and accessibility labels do not appear in the normal reading path at all
  • Words where only part changed. Glossary-substitution translation sometimes rewrites only a fragment inside a word, leaving a single token whose writing system changes mid-word. Skimming will not catch it
  • Characters that read as punctuation. A prolonged sound mark or a middle dot left behind gets read as formatting rather than as text, so nobody suspects anything

And there is one more. Reviewers only review the languages they read. If Russian leaks into a Thai page, neither the Korean reviewer nor the English reviewer will catch it. Machine translation pipelines emitting an unexpected language is not a rare event, and if nobody on the team reads that language it ships. Script checking is overwhelmingly better than humans in exactly this gap, because it works without understanding a word.

2. Characters do not carry a language

The vocabulary matters here. What this check deals with is not language but writing system. They are not the same. English and French are different languages written in the same script, Latin. No amount of code point inspection separates those two.

Conversely, combinations like Korean, Japanese and Russian differ at the script level, so code points alone separate them cleanly. That narrows what this check actually does to a single question: does this document contain a writing system that cannot legitimately occur in the target language? Machines answer that narrow question close to perfectly.

2.1 Unicode already has the answer

Every code point carries a Script property. UAX #24 defines the values, which include Hangul, Hiragana, Katakana, Han, Cyrillic and Latin. JavaScript regular expressions address them directly as \p{Script=Hangul}. As MDN documents, the u or v flag is mandatory, and without it \p is simply parsed as the literal character p. That failure is silent, which makes it worth watching for.

Two special values need to be understood. Common is assigned to characters shared across writing systems, such as digits and punctuation, and Inherited to combining marks that take their identity from the base character. UAX #24 points out that many characters assigned Common or Inherited are not in fact used with all scripts but only with a limited set, and it defines the Script_Extensions property to record those narrower relationships.

That yields a practical judgment. Use Script for contamination checks and do not use Script_Extensions. Script_Extensions expresses the broad relation of «this character may be used in this writing system», so applying it to leak detection catches every piece of punctuation that several languages share. The measured table in section 3 shows exactly that difference.

2.2 Han tells you nothing about the language

This is the most important section in the article. The presence of Han characters is not evidence that a document is Chinese.

Unicode encoded the Han characters used in Chinese, Japanese and Korean as a single unified set. Chapter 18 of the Unicode Standard states that it contains a set of unified Han ideographic characters used in written Chinese, Japanese and Korean, and that the standard does not attempt to encode the language of the Han characters, leaving language tagging and word recognition to a higher level of software. The code point does not tell you whether the glyph is Japanese or Chinese. That information was deliberately left out.

Concretely: the Japanese shinjitai 国 and the Chinese simplified 国 are the same code point, U+56FD. 会 is likewise U+4F1A in both. Put Japanese and Chinese documents side by side, extract only the Han characters, compare code points, and there is nothing to separate.

// Confirm that shinjitai and simplified share code points
for (const ch of ['国', '会', '發', '发']) {
  console.log(ch, 'U+' + ch.codePointAt(0).toString(16).toUpperCase(),
              /\p{Script=Han}/u.test(ch));
}
// 国 U+56FD true   ← Japanese shinjitai = Chinese simplified
// 会 U+4F1A true   ← identical in both
// 發 U+767C true   ← traditional only
// 发 U+53D1 true   ← simplified only

So the rules split like this.

  • Han in an English document — treat as contamination. Han has almost no legitimate reason to appear in Latin-script prose
  • Han in a Japanese document — obviously normal. Do not write the rule at all
  • Han in a Chinese document — normal. What you check instead is which variant family it belongs to (section 6)
  • Han in a Korean document — normal. Korean uses Han for glosses. A rule forbidding it produces a flood of false positives in legal and academic text

For the same reason, a stretch of Japanese text made entirely of Han is an undecidable region. A short string like a company name or a heading with no kana in it has no feature that distinguishes it from Chinese. That is a property of the encoding design, not a defect in your checker, so do not try to solve it with a rule. Mark the region as out of scope instead.

3. Block ranges versus script properties

The code you see most often in the wild writes Unicode block ranges by hand. Hangul as AC00–D7A3 plus 1100–11FF, kana as 3040–30FF, Cyrillic as 0400–04FF, Han as 4E00–9FFF. Those ranges are correct as far as they go. The problem is that they are simultaneously too narrow and too wide.

Here is what the two approaches produce for the same characters on Node 22. To reproduce it, save this to a file and run it.

const BLOCK  = { hangul: /[가-힣ᄀ-ᇿ]/u, kana: /[぀-ヿ]/u };
const SCRIPT = { hangul: /\p{Script=Hangul}/u,
                 kana:   /[\p{Script=Hiragana}\p{Script=Katakana}]/u };

for (const ch of ['한', 'ㄱ', '㉮', 'ｻ', '・', 'ー', 'の']) {
  console.log(ch,
    'U+' + ch.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'),
    'block:',  BLOCK.hangul.test(ch)  || BLOCK.kana.test(ch),
    'script:', SCRIPT.hangul.test(ch) || SCRIPT.kana.test(ch));
}

Two things to take from the table. Block ranges miss scattered characters. Halfwidth kana is the headline case. Documents that have been through an automatic converter carry halfwidth kana more often than you would guess, and a checker that only looks at 3040–30FF waves them through. And block ranges flag shared characters. The middle dot U+30FB sits inside the kana block but Korean and Chinese documents use it as a list separator. That single character is enough to have hundreds of Korean documents reported as Japanese contamination.

Run the two approaches over fourteen samples, six contaminated and eight clean, and they separate like this. The contaminated samples had Hangul, kana and Cyrillic remnants planted after otherwise normal text; the clean samples included middle dots and wave dashes, the characters that invite false positives.

The three that block ranges missed were compatibility jamo, a circled form and halfwidth kana. The one it wrongly flagged was a Korean sentence using a middle dot. Fourteen samples is far too small a set to read the ratios as accuracy, but the failure modes transfer directly. Block ranges break on characters scattered outside the boundary and on shared characters inside it, and enlarging the sample does not move where they break.

UTS #18 points the same way. It states that there are very significant caveats to the use of Unicode blocks for the identification of characters, and directs implementers away from treating blocks as a substitute for script identification. Hand-written ranges may be working code, but the standard defined a separate Script property for a reason.

There are still places where block ranges are the only option. Regex engines without script property support, older runtimes, some database regex dialects and shell tooling leave you no choice. When that is the case, at minimum add halfwidth kana FF65–FF9F and Hangul compatibility jamo 3130–318F to your ranges, and explicitly exclude U+30FB and U+30FC. Those three edits alone remove four of the five places the block approach went wrong above. The one that remains is the circled form, which is rare enough in body text to live with.

4. What kills a checker is false positives, not misses

This is where the real difficulty starts. Everything up to now was mechanical work that needs nothing but character codes. From here you have to identify source-language text that is supposed to remain, and that involves judgment.

There are more legitimate cases than people expect.

  • Proper nouns and brands. Company, product, person and place names are frequently correct left untranslated
  • Quotations. Translate a quoted sentence and it stops being a quotation
  • Code samples. Identifiers, string literals and commands are not translation targets. Translating them breaks the code
  • Term glosses. Writing «kana (かな)» with the original in parentheses is a sign of translation quality, not a defect
  • Articles about characters themselves. As in this one, having several writing systems in the examples is the content
  • Deliberately untranslated UI strings. Legal notices and trademark forms sometimes require the original wording

What happens when you cannot separate those is the whole point. The checker emits 300 warnings, somebody opens them, and 280 are brand names and code samples. By day three nobody opens them. By the end of the first week the check comes out of CI. And the 20 real defects ship.

These two failures do not carry equal weight. One miss ruins one document; accumulated false positives disable the checker entirely. When you build a checker this asymmetry should be the default assumption you start from. The direction is not to widen what gets caught but to tighten until every single thing reported is real. A missed category can be handled later by adding one more rule. A checker that has been switched off does not come back on.

5. Four instruments for exceptions and what each costs

There are four. None is free, and the design consists of choosing how much of each to use.

InstrumentWhat it doesWhat it costsWhen to use it
Scope reduction Strips code blocks, URLs, attribute values and metadata before scanning Whatever you strip becomes a permanent blind spot First. Cheap and high impact
Allowlists Exempts specific strings from the scan Humans must keep feeding it, and length starts hiding real defects Proper nouns and brands, where the list is finite
Ratio thresholds Reports only above a share of total characters A single untranslated sentence in a long document slips under Detecting bulk untranslated output from a machine batch
File level exclusions Removes an entire file from the scan The most dangerous. That file is never seen again Last resort, and only with an expiry date attached

5.1 Scope reduction comes first

Stripping code blocks and URLs alone removes a large share of the false positives. Order matters: strip first, then scan.

function stripUncheckable(text) {
  return text
    .replace(/```[\s\S]*?```/g, ' ')            // fenced code blocks
    .replace(/`[^`\n]*`/g, ' ')                 // inline code
    .replace(/<code[\s\S]*?<\/code>/gi, ' ')   // HTML code
    .replace(/<pre[\s\S]*?<\/pre>/gi, ' ')
    .replace(/https?:\/\/\S+/g, ' ');           // URLs
}

One warning. What you strip you never look at again. An untranslated comment inside a code block will not be caught. So keep the strip list minimal and write the decision down — that comments inside code blocks are out of scope. When a defect eventually surfaces there, it needs to be verifiable as an agreed boundary rather than a bug in the checker.

5.2 Allowlists, only when finite

Allowlists are precise but they consume human attention indefinitely. Two rules cut the maintenance cost.

  1. Scope the list per rule, not globally. «Han allowed in en documents» and «kana allowed in ko documents» are different lists. Merge them and an entry approved for en silently passes in zh as well
  2. Record a reason with every entry. An entry without a reason can neither be removed nor confidently kept six months later, and that is how lists grow forever
const ALLOW = {
  en: [
    { term: '任天堂',  why: 'brand name, kept in original' },
    { term: '한글',    why: 'subject of the article itself' },
  ],
  ko: [
    { term: 'かな',    why: 'term gloss in parentheses' },
  ],
};

The results separate cleanly. An English sentence containing a brand name reports 3 Han characters without an allowlist and nothing with one. A Korean sentence with a parenthesized gloss drops from 2 Hiragana to zero the same way. A regular expression inside a code sample reaches zero from scope reduction alone, no list required.

5.3 Ratio thresholds are steadier than raw counts

The same two characters mean entirely different things depending on document length. Suppose two Hangul characters remain in an English document.

  • In an 815-character document → 0.25 percent. Probably a brand or a quotation
  • In a 6-character document → 33.33 percent. Nothing was translated at all

So set thresholds as ratios rather than counts. A ratio alone is not enough, though, because a single untranslated sentence inside a long document is buried by it. Running two rules together is the arrangement that works in practice. If the ratio exceeds a level, report it as bulk untranslated content and block. Regardless of ratio, if the length of a contiguous contaminated run exceeds a threshold, report that separately. A whole sentence left behind produces a long run and trips the second rule.

// Reporting contiguous runs gives you positions as well
const doc = 'The runner reads the tree. 접근성 트리를 읽고 반환한다. Then it exits.';
const re = /\p{Script=Hangul}+/gu;
let m;
while ((m = re.exec(doc)) !== null) {
  console.log(`offset ${m.index}: ${JSON.stringify(m[0])}`);
}
// offset 27: "접근성"
// offset 31: "트리를"
// offset 35: "읽고"
// offset 38: "반환한다"

One note about report format. Do not report character counts; report positions and the offending fragment. «12 Hangul characters found» is information nobody can act on. «offset 27: 접근성» can be fixed immediately. The cheaper it is for a human to look, the longer the checker survives.

5.4 Never add a file exclusion without an expiry

Removing a whole file from the scan is the last resort. Once added, that file is never checked again, and within six months the reason for adding it is gone. If you must use them, make an expiry date a required field and have the checker report the existence of expired entries as a finding in itself. An exclusion list that is not itself managed becomes a list of blind spots.

5.5 When the writing system changes inside a word

One category needs separate handling: glossary-substitution translation rewriting only part of a word. Document-wide rules cannot catch it, because normal Korean documents contain Han and obviously contain Hangul. What is anomalous is that the two are adjacent.

There is a trap here. Splitting into words and checking whether one word contains two writing systems looks like the natural approach, and it does not work. Word segmenters treat a change of writing system as a word boundary.

const seg = new Intl.Segmenter('ko', { granularity: 'word' });
console.log([...seg.segment('会원 가입')].map(p => p.segment));
// [ '会', '원', ' ', '가입' ]   ← 会 and 원 land in different tokens

So check adjacency rather than words. Look directly for a Han character immediately followed by Hangul or the reverse.

const adj = /(\p{Script=Han}\p{Script=Hangul}|\p{Script=Hangul}\p{Script=Han})/gu;

[...'会원 가입 절차'.matchAll(adj)];    // [ '会원' ]   ← caught
[...'新규 등록'.matchAll(adj)];         // [ '新규' ]   ← caught
[...'민법(民法) 제839조'.matchAll(adj)]; // []          ← gloss not flagged
[...'한자 漢字 병기'.matchAll(adj)];     // []          ← spaced gloss not flagged

What makes this rule good is that it steps around legitimate glosses automatically. Parenthesized glosses and space-separated glosses both put something between the two scripts, so the adjacency condition never holds. It is a rare rule that reaches zero false positives without a single allowlist entry, which makes it worth building.

5.6 Characters the eye cannot distinguish

Cyrillic and Latin contain several pairs that look identical. Capital А (U+0410, Cyrillic) and A (U+0041, Latin) are indistinguishable on screen. When such characters enter through a machine translation pipeline or a copy-paste round trip, no amount of human review will find them.

Machines find these easily, on the other hand. A single rule forbidding Cyrillic in a Korean document catches it. Adding a check for Latin and Cyrillic inside the same token raises precision further, because there is no legitimate reason for one word to be built from two alphabets.

function scriptsOf(token) {
  const s = new Set();
  for (const ch of token) {
    if (/\p{Script=Latin}/u.test(ch))    s.add('Latin');
    if (/\p{Script=Cyrillic}/u.test(ch)) s.add('Cyrillic');
  }
  return [...s];
}
scriptsOf('Аpple');  // [ 'Cyrillic', 'Latin' ]  ← first letter is U+0410
scriptsOf('Apple');  // [ 'Latin' ]

6. Contamination inside one writing system

Everything so far only works when the writing systems differ. Yet a defect that shows up constantly in real localization happens inside a single writing system: traditional forms leaking into simplified text, Japanese character forms surviving in Chinese output, translation memory returning a mixture of both families.

As section 2 established, code points cannot tell you the family. So use a different method. Collect glyphs that exist in only one family and count them. Take characters where simplified and traditional differ, build two sets, and count how many of each the document contains.

const HANS = new Set([...'这么无发国际会议们个东车马门问题时间实现体系统计龙凤业务产资总']);
const HANT = new Set([...'這麼無發國際會議們個東車馬門問題時間實現體系統計龍鳳業務產資總']);

function variant(t) {
  let s = 0, r = 0;
  for (const c of t) { if (HANS.has(c)) s++; if (HANT.has(c)) r++; }
  return { simplified: s, traditional: r };
}
variant('这是国际会议的问题');  // { simplified: 7, traditional: 0 }
variant('這是國際會議的問題');  // { simplified: 0, traditional: 7 }
variant('这是國際会议的问题');  // { simplified: 5, traditional: 2 }  ← mixed
variant('中文');                // { simplified: 0, traditional: 0 }  ← undecidable

Know the properties of this method precisely so you do not over-claim.

  • Mixing is caught well. A marker from the opposite family in a document that expects only one is itself the defect location
  • An undecidable region always remains. A short string made only of characters shared by both families cannot be classified. 中文 above is exactly that
  • Sample size is sensitivity. With only twenty marker characters, most short documents fall into the undecidable bucket. For production use, build a table on the order of hundreds of characters
  • Japanese shinjitai is a separate problem. Some shinjitai forms match simplified Chinese and some do not. Catching Japanese character forms left in Chinese output requires a third sample set of glyphs that exist in shinjitai but not in simplified

A judgment to record. Keep this rule at warning level and do not promote it to blocking. Original-family text inside quotations, proper nouns that have settled into traditional forms, and marker characters that happen to be used with a different meaning are all legitimate exceptions. Unlike cross-script contamination, the share of findings here that genuinely need a human verdict is meaningfully high.

7. Broken characters and foreign script are different problems

These two defects frequently end up bundled into one checker. Separate them. The causes differ and so do the fixes.

  • Foreign script — the characters are entirely valid, just in the wrong place. The cause lives in the translation pipeline
  • Mojibake — the characters themselves were manufactured incorrectly. The cause lives in encoding handling

Distinguishing them is not hard. Breakage leaves fingerprints.

On U+FFFD, Chapter 5 of the Unicode Standard sets out the handling principles for ill-formed byte sequences. A replacement character in a document is definitive evidence that a decode failed somewhere, which makes it one of the very few rules you can always block on, independently of any language check.

Pinpointing which stage an encoding error came from is covered separately in Locating Where Hangul Breaks. This article goes only as far as insisting that you keep the rules and the report messages separate, so encoding defects do not bleed into language checks. If both are reported under one name, whoever fixes them looks in the wrong place first every time.

8. Where normalization goes relative to the check

The same checker returns different answers depending on normalization form. This genuinely flips verdicts.

const doc = 'The word 한글 appears here.'.normalize('NFD');

/[가-힣]/.test(doc);              // false  ← missed
/\p{Script=Hangul}/u.test(doc);   // true   ← caught
/[가-힣]/.test(doc.normalize('NFC'));  // true  ← caught after NFC

The reason is simple. Hangul decomposed into NFD is a sequence of individual jamo, not precomposed syllables. [가-힣] only covers the precomposed syllable area, so nothing matches. Script properties carry Hangul on the jamo as well, so they catch it either way. Which of the four forms defined by UAX #15 your text arrives in decides the outcome.

Compatibility normalization works in the opposite direction.

const s = 'a ko document containing ｻｰﾊﾞｰ';
/[぀-ヿ]/.test(s);                   // false  ← halfwidth, so missed
/[぀-ヿ]/.test(s.normalize('NFKC')); // true   ← NFKC folds it to fullwidth

'ｻｰﾊﾞｰ'.normalize('NFKC');  // 'サーバー'
'ＡＢＣ'.normalize('NFKC');   // 'ABC'
'㈱'.normalize('NFKC');      // '(株)'

Which gives the working rules.

  1. Normalize the text to NFC immediately before scanning. This prevents decomposed text from sliding past the rules
  2. If you are stuck with block ranges, apply NFKC too. Halfwidth kana folds to fullwidth and enters the range
  3. If you use script properties, NFKC is unnecessary. Halfwidth kana already carries the Katakana script and is caught without normalization
  4. Never write the normalized text back. Apply it to the scanning copy only. NFKC is a lossy transform and cannot be undone once applied to the source

That last item is a special case of a general principle. When the moment you change a value and the moment you validate it are ordered wrongly, the validation result becomes meaningless, an axis covered in Change the Value After Validating It and the Validation Is Void. How Hangul itself differs between NFC and NFD, and which boundaries change the form, is treated in detail in When Hangul Falls Apart Into Jamo.

9. To trust a checker, plant contamination in it

When the checker reports nothing you need a way to tell whether that means the corpus is clean or the checker is broken. This failure happens often. Drop a regex flag, get a file extension filter slightly wrong, widen scope reduction until it eats the entire body, and the result reads identically: no findings.

There is one fix. Plant contamination deliberately and confirm the checker catches it. This is not a unit test of the checker, it is a sensitivity test, and the samples must be the types that actually occur.

  1. One sentence in a different writing system — the most common type by far
  2. Halfwidth kana — the representative case block ranges miss
  3. Hangul compatibility jamo — missed by checkers that only cover the jamo range
  4. An NFD-decomposed string — exposes normalization ordering defects
  5. One Cyrillic word — the pipeline accident pattern
  6. A word with Han and Hangul adjacent — confirms the adjacency rule is alive
  7. A sentence mixing simplified and traditional — confirms the marker sample is large enough

Then plant the other side too. Insert legitimate exceptions and confirm silence. A sentence with a brand name, a parenthesized gloss, a regex inside a code block, a list using middle dots. If even one false positive appears, that rule is not ready to ship.

The point is to nail this test down as a regression suite. Keep the sample files in the repository and verify on every run that the checker catches every contaminated sample and passes every clean one. Fixing one rule and losing detection of something it used to catch is a real occurrence, and without this test it does not surface.

One thing when building samples. If the contaminated sample files sit inside the scanned directory, the checker reports them as defects. Keep samples outside the scan scope, or exclude them by an unambiguous filename convention. Then check once more that the exclusion rule is not quietly swallowing real documents as well.

10. What to block and what to merely warn about

Do not treat all rules with the same weight. Three conditions govern promotion to blocking, and all three must hold at once.

  1. False positives are effectively zero. You must be unable to describe a clean document that trips it
  2. The evidence is immediately inspectable. Positions and the offending fragment must be in the report
  3. The fix is obvious. The action must resolve to one thing, such as «translate this sentence»
RuleVerdictReason
U+FFFD replacement character presentBlockDefinitive evidence of a failed decode. No legitimate case exists

Kana in a zh documentBlockSame as above

Simplified and traditional mixedWarnQuotations and proper nouns are genuine exceptions

Language of a short Han-only stringNo ruleUndecidable region. Exclude it from scope

The last two rows matter most. Deciding not to write a rule is also a design decision. Trying to catch what cannot be caught guarantees the rule comes back as false positives, and false positives, as section 4 showed, drag the whole checker down with them.

It also helps to attach one condition to the warning tier. Treat the warning count itself as a metric. If last week had 12 warnings and this week has 80, you know something changed in some batch without opening a single finding. Using warnings as a gauge you read trends from, rather than a list to get to later, slows the rate at which they get ignored.

10.1 The order to roll this out in

Switch everything on at once and day one produces hundreds of warnings, after which it comes right back off. Stage it.

  1. Report only at first. Run for a week or two without blocking to see the actual size of the current state
  2. Classify the false positives. Sort into brands, code, glosses and other, and make absolutely sure you know what «other» contains
  3. Drive false positives to near zero with scope reduction and allowlists. This stage consumes most of the time
  4. Clean up the existing backlog in one pass. Turning on blocking while it remains blocks every unrelated change
  5. Promote only the zero-false-positive rules to blocking. Everything else stays at warning
  6. Attach the regression samples. Do it at this point so sensitivity survives later rule changes

Step four is the one people skip, and it is the most common cause of a failed rollout. Turning on blocking while old defects remain blocks every change that has nothing to do with them. People then start writing suppression comments instead of fixing the checker, and the moment those comments multiply the rule is already dead.

11. What could not be confirmed

The following were left without figures or firm claims because the evidence could not be pinned down.

  • Script property behaviour on other runtimes. The results in this article are from Node 22. Regex \p{Script=…} depends on the Unicode data version the runtime embeds, and how it behaves in builds compiled with reduced internationalization data was not checked
  • Equivalent expressions in Python, Java and Go. Which syntax each regex engine uses for script properties, and whether coverage is identical, was not compared
  • Comparison against statistical language identification libraries. How accurate n-gram identifiers are on short strings, and how much combining them with script checks adds, was not measured
  • The right size for a simplified and traditional marker set. The example uses roughly twenty characters. How many are needed for short documents to be classifiable depends on document type, so no figure is given
  • A complete shinjitai-only character set. A full list of forms that exist in shinjitai but not in simplified Chinese could not be confirmed
  • Exception types for Southeast Asian and Arabic script. Which additional legitimate exceptions arise for scripts without word spacing, such as Thai and Khmer, or for bidirectional text, was not covered
  • Absolute false positive rates. The fourteen samples in section 3.1 exist to show failure modes, not to measure accuracy. Real rates depend heavily on the nature of the corpus

Conclusion: tighten the reporting instead of widening the net

Checking multilingual documents for foreign script splits into two halves. The first is mechanical. Unicode has already recorded a writing system on every character, so you read the script property and look for values that cannot occur in the target language. This is clearly better than hand-written block ranges and the cost of switching is small.

The second half is design. If you cannot separate proper nouns, code and glosses, the checker becomes a pile of false positives, and a checker that has become a pile of false positives gets switched off. So the default direction when writing rules is not «catch more» but «tighten until everything reported is real». A missed category can be handled later with one more rule. A checker that has lost trust is hard to revive.

Two things worth doing right now. One is to add halfwidth kana and Hangul compatibility jamo to whatever rules you are already running. If anything turns up, you have been missing that entire category. The other is to run the checker over ten known-good documents. Whatever it emits there is the life expectancy of that checker, and if it emits anything at all it is time to tighten.
