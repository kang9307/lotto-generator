Bun构建耗时24分钟的真正原因 - buildprof揭开的链接器瓶颈

自制性能分析工具追踪Bun的Zig构建为何比Rust慢四倍以上

2026-09-14 开发/基础设施

「我们的新构建比旧版快5倍」，这样的开发团队公告通常是值得庆祝的好消息。但对某些工程师来说，它反而留下了一个相反的疑问：那旧的构建到底为什么会这么慢？当JavaScript运行时Bun的构建系统从Zig迁移到Rust、在Linux上快了5倍以上的消息传开后，开发者Lalit Maganti决定不去猜测，而是亲自实测这个差距的真相。他为此自制的工具就是buildprof。

本文基于Maganti在自己博客上公开的实测结果，梳理Bun旧版基于Zig的构建为何耗时如此之长，以及这一瓶颈究竟能被压缩到什么程度。

本文基于Lalit Maganti在其博客（lalitm.com）发布的buildprof相关文章中的实测数据与说明。不编造原文中不存在的具体数字或结论，仅陈述原文实际给出的测量结果。

1. buildprof是什么

buildprof是一款开源工具，能在Linux上追踪构建命令运行期间生成的整个进程树，并将每个子进程的启动与结束时间重新整理成一份时间线。使用方法非常简单：只需在原本的构建命令前加上buildprof --即可。

需要这类工具的原因很直接。像make -j16或ninja这样的构建系统，内部会同时启动数百个编译器和链接器进程，仅靠肉眼浏览日志几乎无法判断到底是哪一个在拖慢整体构建时间。「感觉构建很慢」与「究竟是哪个阶段、哪一个具体进程是瓶颈」之间存在相当大的距离，而buildprof正是用实测数据来填补这段距离。

  • 使用示例：像buildprof -- make -j16、buildprof -- cargo build、buildprof -- ninja -C out/target这样，原样包裹现有的构建命令来运行。
  • 利用ptrace（与调试器使用的相同Linux接口）追踪进程的创建与终止。
  • 还能一并解析Clang、LLD以及nightly版Rust编译器留下的追踪信息。
  • 由于无需修改现有构建命令，即便是大型构建脚本也能毫无负担地直接应用。

2. 起因 - 「Rust比Zig快5倍」的公开发言

故事始于Bun开发公司创始人Jarred Sumner发布的一条推文。内容称，用Rust重写的Bun构建系统在Linux上比旧版基于Zig的构建快5倍以上。Maganti觉得这一说法有悖直觉：Zig通常以编译速度快著称，而且事实上Zig构建使用的是较重的Full LTO，Rust构建反而使用相对轻量的ThinLTO。为了确认差距是否真有这么大、如果有又究竟出在哪里，他决定亲自对两种构建进行性能分析。

这种「反直觉的基准测试说法」在开源世界里并不罕见。问题在于，无论是接受这一说法的人还是反驳它的人，往往都只是凭感觉在争论，缺乏依据。Maganti的做法之所以引人注目，是因为他没有加入争论，而是选择在相同条件下实际运行两种构建，并以进程为单位测量时间。

  • 起因：Bun创始人公开表示Rust构建在Linux上比Zig构建快5倍以上。
  • 疑点：Zig本以编译速度快著称，为何这次会慢到这种程度。
  • 方法：不凭感觉判断，而是自制buildprof工具进行实测。

3. 实测 - Zig 24分24秒 vs Rust 5分40秒

Maganti在自己的单台机器上重现两种构建，结果如下：旧版基于Zig的构建（Bun 1.3.14）耗时24分24秒，新版基于Rust的构建（Bun 1.4.0）仅用5分40秒就完成。作为参考，实际CI环境中测得的中位数分别约为30分6秒（Zig）和约5分37秒（Rust），与本地重现的数值大致一致。

类别单机重现时间CI环境中位数主要链接方式
基于Zig的构建（Bun 1.3.14，旧版）24分24秒约30分6秒Full LTO
基于Rust的构建（Bun 1.4.0，现行版）5分40秒约5分37秒ThinLTO

也就是说，Bun最初是用Zig构建的，后来转向基于Rust的构建系统才变快。本文真正深入探究的问题是：Zig构建为何会慢到这种程度？

4. 拆解瓶颈 - Full LTO链接阶段占用了三分之二的时间

用buildprof拆解Zig构建的时间线后发现，原因并不在编译本身，而在最后的链接阶段。一次ld.lld链接器调用单独运行了16分35秒，约占整体构建时间（24分24秒）的三分之二。其中，执行LTO优化的OptModule阶段本身就耗费了10分钟以上。

  • 编译阶段本身并不算慢——问题集中在最后的链接阶段。
  • ld.lld链接器调用：16分35秒（约占整体的三分之二）。
  • 其中OptModule（LTO优化）阶段单独消耗了10分钟以上。
  • 该阶段作为一个难以拆分并行执行的单一操作运行。

5. 优化实验 - 改用ThinLTO会发生什么

确认瓶颈后，Maganti实际进行了两次实验，将Zig构建的链接方式从Full LTO改为ThinLTO。第一次实验只将Bun二进制文件本身改为ThinLTO，第二次实验则更进一步，连WebKit和ICU也一并用ThinLTO重新构建。

配置整体构建时间链接器耗时相较基准
基准线（Full LTO，原始Zig构建）24分24秒16分35秒—
实验1：仅Bun二进制文件用ThinLTO20分20秒12分55秒约缩短4分钟
实验2：Bun + WebKit + ICU 全部ThinLTO15分11秒7分22秒约缩短38%（9分13秒）

在连WebKit和ICU也一起改为ThinLTO的第二次实验中，整体构建时间降至15分11秒。相比原始的Full LTO构建（24分24秒），约缩短了38%，虽然仍未达到优化后的Rust构建（5分40秒）的水平，但已经清楚地揭示了瓶颈的真面目。

6. 结构性原因 - 90多个Rust crate对单一Zig模块

即便进行了ThinLTO实验，仍未能追上Rust的速度，原因在于两种语言之间根本性的结构差异。Rust构建被细分为90多个crate，因此编译工作可以分散到多个核心上并行执行。而Zig构建则将全部代码编译为单一模块，从一开始就几乎没有并行化的空间。

这一差异与链接方式（Full LTO还是ThinLTO）是两个不同的问题。将链接器改为ThinLTO，解决的是「已经生成的多个片段该以多松散的方式优化并拼接起来」的问题；而crate数量决定的则是「一开始能拆分成多少个独立片段来同时编译」。像Zig构建那样把所有代码都绑定在单一模块中，无论怎样调整链接器设置，能将编译阶段本身分散到多个核心上的空间从根本上都很有限。

  • Rust：分散到90多个crate中 → 结构上便于并行处理编译工作。
  • Zig：全部代码为单一模块 → 并行化在结构上受到限制。
  • 这一差距并不能仅靠把链接器改为ThinLTO就完全消除。
  • 也就是说，实验2（见第5节表格）中38%的缩短属于链接阶段的改进，并不能替代crate拆分本身。

7. buildprof究竟如何运作

buildprof是一款仅支持Linux的工具，利用ptrace记录构建命令生成的每一个子进程的启动与结束时刻。这种方式的优势在于，无需对构建系统或编译器做任何特殊改动，仅凭「谁在何时运行」这一进程级别的事实就能定位瓶颈。不过，追踪进程这一行为本身是否会拖慢构建速度，也是一个自然会被提出的疑问。

Maganti也确认了这款工具自身的开销是否会扭曲实测结果。追踪Redis构建时，原本26.78秒的构建增加了约5秒的开销；而在追踪ripgrep构建时，12.27秒与12.43秒几乎没有差别。也就是说，当同时追踪文件系统事件时，开销可能会随项目规模有所增加，但就本文所讨论的Bun构建这种规模的瓶颈（数分钟到数十分钟级别）而言，Maganti得出的结论是这一开销可以忽略不计。

  • 追踪方式：基于ptrace的进程树追踪（截至本文写作时，macOS与Windows尚不支持，仅作为未来计划被提及）。
  • 开销验证1：Redis构建基准约26.78秒 → 追踪时增加约5秒。
  • 开销验证2：ripgrep构建基准12.27秒 → 追踪时为12.43秒，几乎可以忽略。
  • 此外还测得，仅WebKit的冷下载与解压本身就需要约20秒。

8. 实务启示 - 构建变慢时不要凭感觉下手

这一案例给开发团队的启示，与其说在于工具本身，不如说在于方法论。只有把「构建太慢」这种模糊的抱怨，逐阶段拆解为实测数据之后，才能明确到底该修复哪里。

如果Maganti没有实测，只是简单归结为「Zig本来就慢吧」，那么链接阶段占用三分之二时间这一事实，以及仅靠改用ThinLTO就能缩短38%这一事实，都不会被发现。一次构建耗时20分钟的团队，与只需5分钟的团队，一天之内能完成的迭代次数根本不同。这一案例把这种差距从「一种感觉」精确收窄到「时间线上某一个具体进程」，这正是它超越普通基准测试文章的实务价值所在。

  • 不要仅凭「感觉慢」就开始优化。首先应通过实测区分瓶颈到底在编译阶段还是链接阶段（见第4节）。
  • 要认识到Full LTO虽有利于最终运行性能，但会带来较大的构建时间成本。改用ThinLTO可以大幅缩短构建时间（见第5节）。
  • 单一模块结构会直接限制并行构建的上限。在设计大型代码库时，如何划分编译单元也会对构建时间产生重大影响（见第6节）。
  • 如果没有合适的性能分析工具，自己动手做一个也是可行的方案。像buildprof这样目标明确的小工具，能把模糊的猜测变成有依据的结论。

未能确认的事项

  • Bun项目实际最终采用了哪种ThinLTO配置：原文给出了ThinLTO实验的结果，但Bun团队是否将这些实验结果应用到了实际的生产构建中，原文中无法确认。
  • macOS与Windows支持的具体时间表：原文仅将这两个平台的支持列为「未来计划」，并未给出具体的时间安排。
