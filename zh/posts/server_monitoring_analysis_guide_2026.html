原文的骨架 - 先看症状，再看原因

关于监控的文章，大多讲如何搭建仪表盘，很少讲搭好之后如何读图并解读。原文针对的就是这个空白。它的主题是如何读图、诊断并采取行动。本文沿着原文的脉络，把先看什么、按什么顺序看、最终得出什么结论，重新排成一套流程。

原文的出发点是把指标归为四类的框架：来自 Google SRE 的四个黄金信号，即流量、延迟、错误和饱和度。随后的关键区分是症状与原因。延迟和错误是用户感受到的症状，CPU、内存、线程池、连接池则是基础设施的状态，也就是原因的候选。原文的句子是：必须先掌握症状，再通过原因缩小嫌疑范围。

  • 流量。进入系统的请求量。它是此后所有指标的分母。
  • 延迟。从请求到响应所花的时间。用户感到的慢就体现在这里。
  • 错误。失败请求的占比。用户遇到的失败就体现在这里。
  • 饱和度。资源被占满的程度。这是用来缩小原因候选的一侧指标，后面要讲的CPU、连接池和队列都属于这一类。

这一区分也延伸到告警设计。原文说，如果把告警设在「CPU 80%」这类任意的资源阈值上，误报会很多；告警应当设在症状上，比如错误率超过阈值，这样才与真实的用户影响吻合。资源指标单独读会说谎，这是后面各节共同的前提。

流量 - 进来了多少

第一个问题是进来了多少。没有特殊活动的服务，会保持稳定的流量形状。原文说，熟悉这种平时的形状，是识别异常的前提。指标如果只有平时的一半，即使在正常范围内也是出了问题，这句话就是一个例子。

  • 垂直下跌。信号是请求没有到达服务器。应怀疑负载均衡器、DNS、网关等上游问题。与直觉相反，此时服务器侧的指标是干净的。
  • 垂直飙升。突然涌入。候选有走红、爬虫访问、攻击；如果是周期性重复的飙升，则联想到批处理作业或 cron。
  • 作为分母的流量。同样是500个错误，放在一天100万个请求里，与放在1,000个请求里，意义完全不同。错误要按相对于流量的比例来读，而不是看个数。

本节给出的流程很简单。在打开其他指标之前，先看请求量的形状与平时是否一致。如果请求量断了，就把深入服务器内部的排查往后放。

延迟 - 平均值掩盖的东西

第二个问题是花了多长时间。原文说，平均响应时间会掩盖分布的形状，因为平均同为100ms的两台服务器，可能有完全不同的性能特征。所以要用百分位数。P50 是典型用户的体验，P95 和 P99 用来设定目标并捕捉早期预警。原文说，异常迹象几乎总是先出现在 P99 上。

  • 换算成规模。每秒1,000个请求时，P99 意味着每秒有10位用户收到缓慢的响应，一天就是86.4万次。百分之一并不是小数字。
  • 调用会相乘。在一个画面用到40多次API调用的服务里，即使每次调用都有99%在目标时间内完成，40次全部在目标内完成的概率也会降到约67%。
  • 长尾属于谁。积累了大量数据的重度用户，自然会落入缓慢的长尾。原文的说法是，P99 很可能就是服务最优质客户所经历的响应时间。

把同一主题扩展到多台服务器时的聚合问题，已在对10台服务器的p99取平均一文中讲过。本文只沿着原文讲到为什么要读 P99。

错误 - 快速失败与缓慢失败

第三个问题是有多少失败。原文先把状态码分开。5xx 是服务器侧的失败，始终是值得担忧的对象。4xx 是客户端的无效请求，但也可能是旧版应用与新版服务器版本错位、API契约被破坏的信号。接下来的区分是失败的速度。

  • 缓慢失败。像超时那样等待数秒后才失败的类型。等待期间会占住线程和连接，所以错误和饱和会同时出现。
  • 快速失败。像 connection refused，或来自已死亡的依赖服务的 null 引用那样，在毫秒内失败的类型。资源使用率保持完好。
  • 幸存者偏差。存在一个悖论：错误率飙升，P99 反而看起来更好。原因是立即失败的请求以毫秒级样本混入。这时只看延迟图会让人放心。

本节的流程是：错误增加时，先分清失败是快还是慢。快速失败就不看资源指标，而看依赖对象是否还活着；缓慢失败则下沉到下一节的资源与连接池指标。

资源指标 - 不要单独解读CPU和内存

原文的句子是：资源指标单独读会说谎。CPU 必须叠加在延迟上一起读。原文按 CPU 形态与延迟的组合列出三种情形。

CPU 的形态延迟原文的诊断
平缓上升低且稳定健康的扩展。继续观察
20%到30%的水平飙升I/O 等待。数据库延迟、锁、连接池耗尽、超时。看被堵住的资源，而不是 CPU
平直地贴在 100%偏高容量超限或死循环。若流量正常，则审查代码

原文说，容器环境还有一个这张表遗漏的陷阱：Kubernetes 的 CPU 限制造成的节流。容器默认每100ms一个周期领取一份 CPU 时间配额，限制为0.5核时每个周期为50ms。配额用完后，会被强制暂停到下一个周期。但 CPU 使用率图里看不到暂停的时间，所以使用率正常，只有 P99 长尾在变长。

  • 正常信号，锯齿。在 JVM 或 Node.js 这类带垃圾回收的运行时里，内存上升后在 GC 时急剧回落的锯齿，是如同心跳般的正常模式。
  • 泄漏要看谷底。看谷底而不是峰值。谷底水平就是正常，谷底像台阶一样悄悄上升，则说明每次都有 GC 回收不了的对象残留。
  • 台阶状的飙升。在锯齿之上垂直跳升，说明一次性把大量数据加载进了内存。全表查询、大文件处理、Excel 下载都是例子。要在发生 OOM 之前改成分页或流式处理。

连接池与队列 - 并发数的算术

原文的一道算术是本节的核心。利特尔法则：同时处理中的请求数，等于每秒流入量乘以平均处理时间。每秒进来1,000个请求、平均处理50ms，则并发请求为50个，200个线程的池绰绰有余。但如果数据库变慢、平均变成2秒，并发请求就成了1,000乘以2，即2,000个，池被耗尽，1,800个请求排队。流量没有变，系统却崩溃了。

  • 连锁崩溃。所有线程都在等数据库时，就没有线程处理新请求。健康检查超时，负载均衡器摘掉服务器，剩下的服务器承受更多流量而更快崩溃。一条慢查询就会蔓延成整个集群的故障。
  • 重试风暴。客户端重发失败的请求，流量会增加两到三倍，堵住恢复的空隙。
  • 看斜率而不是池本身。线程池使用量看斜率而不是绝对值。随流量平缓上升是正常的，垂直上升说明别处的延迟造成了等待。
  • 事件循环型服务器。Node.js 和 WebFlux 不为每个请求配一个线程，而是由一个执行线程转动循环。一处堵塞，整个进程就会停下。指标是事件循环延迟，要按最大值或 P99 而不是平均值来读，按相对平时的趋势而不是绝对标准来读。8个进程的平均 CPU 40% 可能掩盖其中一个达到100%的进程，所以要看每个进程的最大值。

连接池里也出现同样的原理。原文的例子是 HikariCP 默认的10个连接，对应200个应用线程。数据库变慢时，会出现连接超时错误。错误的应对是调大连接池，正确的应对是追问「为什么归还变慢了」。原文的句子是：原因通常不是连接池本身，而是某处的延迟。

瓶颈、饱和、缓存与超时 - 当两张图互相矛盾时

当多个指标一起变动时，原文还给出了几个最后的工具。第一是瓶颈的形状。瓶颈之前堆积着等待，瓶颈之后则很空闲。系统的吞吐量由最弱的一环决定。第二是饱和曲线不是直线。使用率越高，等待时间越呈非线性膨胀。

使用率等待时间（相对基准）原文的解读
50%1倍基准
80%4倍从这里开始变陡
90%9倍觉得还剩10%是危险的想法
95%19倍剩下的5%会以19倍的等待时间还回来
  • 队列不是免费的。队列吸收暂时的涌入时是健康的，但当流入持续超过吞吐量时，它就成了延迟的债务。吞吐量为每秒100个时，积压100个意味着下一个请求多等1秒，积压1万个则多等100秒。资源还会花在客户端早已放弃的请求上。
  • 背压与负载卸除。队列长度持续上升而没有回落，说明缺少流量控制。队列溢出时用 429 明确拒绝，就不会所有人都变慢一点，而是一部分快速失败，其余的正常处理。
  • 缓存命中率崩溃时。命中率97%意味着数据库只接收3%的流量，缓存一旦崩溃，数据库会承受30多倍的负载。热门键的 TTL 到期时，数百个请求同时涌向数据库，就是缓存击穿。首先看数据库负载激增的时间与命中率下降的时间是否重合。
  • 超时不一致。如果网关超时为3秒、后端查询超时为5秒，用户在3秒时收到504，而后端在5秒时悄悄记录成功。就会出现后端指标没有错误、网关却有504的矛盾。解决办法是越往内层越短的超时预算。原文的例子是网关3秒、HTTP 客户端2.5秒、数据库2秒。

本节的诊断规则归结为一条。如果看到某一层报错而下一层显示成功的矛盾，首先怀疑超时是否对齐。

超时预算的目的，是让内层比外层先干净地失败，从而使错误能正确地向上传递。如果外层先放弃，内层就会继续生成没有人读取的响应，在过载期间仍然消耗 CPU 和连接。3秒、2.5秒、2秒是原文的例子，自己服务的数值要根据真实的响应分布来定，原文并没有给出各服务的具体数值。

三种时间轴 - 平时、部署刚结束、故障中与故障后

原文归纳说，同一张图，什么时候看，读法不同。平时是学习基准线，部署刚结束要留意30分钟，故障中恢复优先于根因分析。

  • 平时的5分钟。每天花5分钟把仪表盘转一圈。熟悉了流量形状、CPU 节奏和正常的 P99 范围，那句「不知道平时是什么样，也就认不出哪里不对劲」所指的问题就消失了。把告警设成越过基准线就响。每天恶化1%、持续4周的变化不会触发告警，所以需要一个把今天的 P99 与上周同一个星期几叠在一起的面板。
  • 部署后30分钟。在图表上给部署时间留一个标记。这样「是部署之前还是之后」这个问题就不需要其他信息，原文说这是性价比最高的做法。新进程可能因为 JIT 编译尚未完成、本地缓存为空、连接池重建，而让 P99 暂时翻倍。如果用几分钟恢复，就是预热；如果持续偏高超过10分钟，就是回归。
  • 回滚标准与金丝雀。提前约定这样的规则：部署后错误率超过 X% 或 P99 在10分钟内没有恢复趋势，就不经讨论直接回滚。金丝雀是先部署到一两台服务器，在相同流量条件下，按版本标签区分，把金丝雀和稳定版并排比较。
  • 故障中与故障后。先确定范围：是整个系统、某个特定 API，还是某个地区或客户。接着查找最近30分钟到数小时内的变更，即部署、配置、功能开关、基础设施作业和营销带来的流入。恢复优先，顺序是回滚、重启、扩容、用开关关闭功能，而作为证据的指标、日志和堆转储在恢复后仍然保留。事后复盘以第一次症状、告警、人员开始响应、恢复这四个时刻画出时间线，并把检测上的空白与响应速度上的空白转化为行动项。原因描述中不写人名。

本节流程的概括是三行。平时建立基准线，部署后看是否恢复来区分预热与回归，故障中先恢复，再用一个假设对应一张图来验证。

套用到你自己服务器上的六个步骤

下面六个步骤，是把原文的脉络转成读者可以在自己的服务器上重复的顺序。每个步骤的依据都在前面各节。

  1. 看请求量的形状。与平时相同吗，是否垂直断裂，是否飙升？如果断了，先看上游，再看服务器内部。
  2. 用百分位数读延迟。看 P50、P95、P99，而不是平均值。分清是只有特定 API 慢，还是全部都慢。
  3. 按比例读错误并区分速度。看相对于流量的比例而不是个数，并区分是快速失败还是缓慢失败。
  4. 把资源指标叠加到延迟上。CPU 低而延迟高，就怀疑在等待；CPU 平直贴顶，就怀疑容量或循环。在容器里，把节流也列入候选。
  5. 找出等待堆积的位置。看连接池、队列、缓存命中率和超时是否对齐。瓶颈之前堆积等待，之后则很空闲。
  6. 把最近的变更与基准线对照。把部署标记与上周同一星期几的面板并排放好，如果没有恢复，就按事先约定的标准回滚。

原文的结论清单，把这六个步骤缩成四个问题：进来多少，花多久，失败多少，什么被占满。告警响起时，停下来问这四个问题。
