Introduction: What Codex Goals Is and Where It Stands Now

Codex Goals lets you give Codex, once, a description of what should be true when the work is done. Codex stores that goal on the thread and keeps working toward it across multiple turns. It all starts with a single /goal command. The feature first landed in Codex CLI 0.128.0, released on April 30, 2026 (as an experimental feature), and became on by default and no longer experimental in 0.133.0 on May 21, 2026. This article first went out on May 20, 2026, in between those two releases. Korean developer communities such as GeekNews (news.hada.io) picked it up quickly, and community wrappers like goal-setter were introduced, which raised the practical question: is this actually useful in production work?

This article is not a translation of OpenAI's official docs. It is a practical analysis of where Codex Goals helps, where it tends to spin its wheels, and how it differs from the way Claude Code works. In the 2026-09-29 update, the explanation of how it works was rewritten against OpenAI's official docs and GitHub release notes. The short answer: it fits migrations and refactors whose completion can be judged by tests or measurements, and it does not fit work where you cannot say what "done" means.

1. Why Codex Goals Exists - the Limit of One-Shot Generation

Through 2023 and 2024, GPT-4-era coding assistants were essentially "a friend who writes one function at a time". Ask for a "JWT decoder function" and you get clean Python, but the assistant has no idea where that function plugs into your auth middleware or how it conflicts with your existing session code. The user paid the cost of re-explaining context on every prompt.

In 2025, as tools like Cursor, Windsurf, and Claude Code spread, whole-repo context awareness improved dramatically. But you still had to drive the assistant step by step: "do this, now do that". When that step-by-step driving cost piles up, using the AI ends up taking longer than writing the code by hand.

Codex Goals tackles this limit with a different approach: set the goal and its completion condition once, and let Codex decide the next step as it sees how things are going. The OpenAI Cookbook says to use Goals when the finish line is clear but the path to it is uncertain. Its examples are tasks where the next step depends on what was learned in the previous one: profiling, patching, benchmarking, and reproducing a flaky test.

2. How Goals Works (Per the Official Docs)

When first published, this section described four stages: "goal input, automatic sub-task decomposition as a checklist (4 to 10 items), a verification loop that escalates after a set number of failures, and a retrospective report". Checking against OpenAI's official docs on 2026-09-29, the checklist-style decomposition, escalation after a failure count, and the retrospective report could not be confirmed. The flow the official docs describe is as follows.

  1. Set a goal: Use /goal <objective>. The official example is /goal Finish the migration and keep tests green.
  2. Check and control it: /goal on its own shows the current goal, and /goal pause, /goal resume, and /goal clear pause, resume, and remove it.
  3. Carry on across turns: The goal is stored on the thread and persists across turns. Codex does not continue while another turn is active, while user input is queued, or while other thread work is pending.
  4. When it stops: It stops on success, pause, clear, interruption, a budget limit, or a blocker that requires user input.
  5. Turning it on: It is on by default from 0.133.0. If /goal does not appear in the slash command list, the official docs say to add features.goals = true to config.toml or run codex features enable goals.

The crux is who defines the verification criteria. The official Cookbook lists six things a good goal includes: the Outcome (what should be true when done), the Verification surface (the test, benchmark, report, or other evidence that proves it), Constraints (what must not regress while Codex works), Boundaries (which files, tools, and repositories Codex may use), an Iteration policy (how to decide what to try next after each attempt), and a Blocked stop condition (when to stop and report that no path remains). In other words, the verification loop is not something the system builds for you; you write it into the goal.

The ChatGPT desktop app's slash command docs describe /goal as a command that sets a persistent goal, and advise shaping it with /plan first. While a goal is active, the app shows its progress above the composer, with buttons to pause, resume, edit, or clear it. The trade-offs of planning first are covered separately in Is Plan Mode Dead?.

3. Three Practical Scenarios (Hand-Built Examples)

The scenarios below are not OpenAI's official examples. They assume patterns common in Korean SI projects, startups, and side projects. They were first presented as "expected sub-task decomposition", but there is no official description of Codex splitting a goal into a list like this. The lists are a human sketch of the work order, and each goal line now includes a completion condition and a way to verify it.

Scenario A. Legacy REST API v1 to v2 migration

Goal: "Migrate v1 REST API to v2. Keep v1 clients working for six months. Done when the existing integration tests pass on both v1 and v2."

Example work flow (assumed):

  1. Scan all v1 endpoints (extract file list under routes/v1/*.py and similar)
  2. Generate a v1-vs-v2 diff matrix (request/response schema comparison)
  3. Scaffold the v2 router (FastAPI prefix=/v2)
  4. Build the v1-to-v2 adapter layer (old clients call v1, internally routed to v2)
  5. Add compatibility test cases (replicate existing integration tests under v2 prefix)
  6. Write a migration guide in Markdown

Caution: A wrong mapping in the adapter layer turns into a production incident, so a human must code-review that part separately.

Scenario B. JWT auth to session-based auth

Goal: "Migrate user auth from JWT tokens to session cookies. Use Redis as the session store. Done when the login and logout integration tests pass."

Example work flow (assumed):

  1. Locate current JWT issuance and verification code
  2. Add a Redis client module and connection settings
  3. Implement session ID generation, storage, and verification
  4. Replace the JWT verification middleware with a session verification middleware
  5. Update login and logout endpoints (token response becomes Set-Cookie)
  6. Summarize required frontend changes (remove Authorization header, add credentials option)
  7. Document the migration strategy (gradual vs. cutover, with trade-offs)

Caution: This is security-sensitive, so passing automated tests is not enough. Do not put areas that need a separate security review into the goal and hand them off.

Scenario C. Push type safety above 95 percent

Goal: "Raise TypeScript type coverage from 60 percent to 95 percent or higher. Remove any first. Done when type-coverage reports 95 percent or more and existing tests still pass."

Example work flow (assumed):

  1. Analyze type-coverage output (measure current coverage)
  2. Prioritize any usages (library boundaries > core business logic > test code)
  3. Patch missing external library types (add @types or write ambient declarations)
  4. Tighten utility function signatures (extract candidates for generics)
  5. Enable strict mode incrementally (noImplicitAny then strictNullChecks then full strict)
  6. Final coverage measurement and a report of remaining any cases

This is the type of work that best matches how Goals is designed. The completion condition can be written as a number, which makes it easy to judge when to stop and when to keep going.

5. Production Adoption Pitfalls

Four common traps when you first use Codex Goals:

  • Goals scoped too broadly: A goal like "make the whole codebase clean" has no way to judge completion, so there is no reason to stop. The official docs also say to define what "done" means before starting. Keep a single goal to a unit whose completion you can state as a test or a measurement.
  • Handing it off with no way to verify: In a repo with no tests, there is no way to confirm the goal was met, and work can keep heading the wrong way. A minimum set of integration tests or a measurement command is a prerequisite.
  • Secret exposure risk: Repos with hardcoded API keys or DB passwords risk sending those values to an external model during the work. Audit .gitignore and environment variable usage first.
  • No rollback plan: If you do not work on a dedicated branch, a long run that goes sideways is hard to undo. Always create a fresh branch first, and write the Boundaries of what may be touched into the goal.
Recommended workflow: Start small, verify results, then expand. A first goal like "add missing test coverage" is low-risk, has a clear completion condition, and gives a smooth learning curve.

6. Fit by Korean Developer Scenario

6.1 Government and public-sector SI projects

External AI services are often blocked by security policy. Running Codex Goals as-is inside network-separated environments is hard; consider on-prem alternatives such as a local-LLM-based custom agent. Non-code work like RFP drafting and technical specifications may still benefit partially.

6.2 Startups and B2B SaaS

This is where benefits show up most easily, because saving a senior engineer's time is worth a lot. The right moment to adopt is when "consistency of code quality" outweighs "raw development speed". At the MVP stage it can be more than you need; it becomes more useful when paying down technical debt.

6.3 Side projects and solo developers

Value for money depends on how you use it. Codex is primarily used as part of a ChatGPT plan, and the "per-goal surcharge" mentioned when this article was first published could not be confirmed in the official docs. That said, the official docs list a budget limit as one of the stop conditions, so it is safer to decide how much budget a task may use before starting a long goal. If you already use another tool, trying Goals only on large tasks with a clear completion condition keeps the commitment low.

7. Community Wrappers Like goal-setter, and Your Options

goal-setter and similar community wrappers were introduced on GeekNews around the time of first publication. This article originally described them as "an abstraction layer between raw OpenAI API calls and Codex Goals", but this update could not confirm the tool's current state or features. Instead, the options are regrouped around facts that the official docs confirm.

There are three ways to run goal-driven work:

  • Direct API calls: You have to implement goal retention, iteration, and stop logic yourself. Building the tooling takes time.
  • Codex Goals: Goal storage, continuing across turns, and pause, resume, and clear are built into Codex, so you can start immediately. You still have to write the verification criteria into the goal.
  • Wrappers: Helper tools for writing goals or estimating cost. Before using one, check in its repository what it runs and with what permissions.

The official way to connect external tools to Codex is MCP. Codex documents connecting MCP servers through [mcp_servers.name] tables in config.toml and the codex mcp command, so it can be compared with Claude Code's MCP ecosystem on the same standard.

8. Conclusion - Who Should Use It and Who Should Wait

Good fit:

  • Senior engineers with frequent migrations and large refactors
  • Tech leads modernizing legacy codebases
  • Solo operators managing many repos by themselves

Hold off for now:

  • Juniors who mostly write one-off functions (more tool than needed, fewer learning opportunities)
  • Repos with little or no test coverage (no way to judge completion)
  • Network-separated or compliance-restricted environments where external AI is blocked

Outlook at the time (May 2026): The article expected the feature gap between Codex Goals and Claude Code task to narrow, and the deciding factor to shift from "features" to "pricing-model stability". As of 2026-09-29, Goals became a default feature on May 21, and the Codex app has merged into the ChatGPT desktop app. Codex is primarily used as part of a ChatGPT plan, so the original framing of "flat rate vs. usage-based" was not accurate.

Whichever tool you pick, the most durable skill is "the ability to design verification criteria yourself". That is also why the official docs list outcome, verification surface, constraints, and boundaries first among a good goal's elements. The more autonomously the tool works, the more the human role shifts from "issuing instructions" to "designing the definition of done". Why existing instructions do not carry over cleanly when you switch models is covered in What Happens When You Carry Over Opus 5 Settings.

# Codex Goals Checklist - What to Check Before You Set a Goal

## 3. Goal wording checklist (six elements recommended by the docs)

- [ ] **Outcome**: one sentence on what should be true when done
- [ ] **Verification surface**: the test, benchmark, command output, or report that proves it
- [ ] **Constraints**: what must not regress (for example, existing tests keep passing)
- [ ] **Boundaries**: which files, tools, and repositories may be used
- [ ] **Iteration policy**: how to decide the next attempt after each one
- [ ] **Blocked stop condition**: stop and report when no path remains

## 4. Before you start

- [ ] The repo has at least minimal integration tests or a measurement command (otherwise completion cannot be judged)
- [ ] You are on a new branch
- [ ] No API keys or DB passwords sit in plain text in the code (check .gitignore and environment variables)
- [ ] Parts that need a security review are left out of the goal
- [ ] You decided the budget for this task first (a budget limit is one of the stop conditions in the docs)

## 5. When it stops (official docs)

| Condition | Meaning |
|---|---|
| Success | Goal achieved |
| Pause / clear | The user ran `/goal pause` or `/goal clear` |
| Interruption | The run was interrupted |
| Budget limit | The set budget was reached |
| Blocker | User input is required |

It does not continue while another turn is active, while user input is queued, or while other thread work is pending.

## 6. Good fit / poor fit

| Good fit | Poor fit |
|---|---|
| Clear finish line, uncertain path | Work where you cannot say what "done" means |
| Legacy API migration, raising type coverage | Broad goals like "make the whole codebase clean" |
| Performance work, reproducing a flaky test | Repos with almost no tests |
