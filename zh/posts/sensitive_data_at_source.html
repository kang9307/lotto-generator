在输出阶段脱敏已经太晚 - 在产生点就拦住敏感数据的结构

在输出处遮挡的方式只能挡住你已知的格式，而那时副本早已增多

2026-08-01 开发/基础设施

引言：日志里删掉了，备份里却还在

最常见的顺序是这样的。有人在看日志时发现了一个不该出现的值。匆忙加上脱敏规则并发布。第二天日志界面干干净净。然后大约一个月后，某人为了排查故障解开了旧备份，又一次看到了同样的值。

在这个故事里脱敏规则做了它该做的事。问题在于规则开始生效的那个时点。那个值早就进了标准输出、写进了文件、被送到采集器、被轮转、进了备份。在输出阶段遮挡，意味着在已经复制出好几份之后只修其中一份。

所以本文的主张不是「我们来脱敏吧」。脱敏是最后一道防线，真正的解法是让那个值一开始就不进入日志路径。而要做到这一点，就得把规则的方向翻过来。不要挑要去掉的，要挑要放进去的。

  • 在输出处遮挡只能挡住你知道的模式。 格式稍有不同就原样通过，而且什么都不会失败
  • 把整个对象丢进去，后来新增的字段会自动跟着来。 日志代码一行没改，泄露的项目却变多了
  • 等你决定要修的时候，副本已经有好几份了。 没有人知道哪些副本里还留着
  • 把值包起来，出错也不会露出原值。 放进字符串拼接里、放进日志里，结果都一样

运行环境。 下面所有输出都是在 Windows 10 Pro (10.0.19045) 上用 Node.js v22.16.0 (win32) 实际运行的结果。脚本全部保存为文件后执行，并且只在临时目录里创建文件。

★示例值全部是只对上格式的假数据。 只对齐位数，数字全部填零（000000-0000000、0000-0000-0000-0000、010-0000-0000），邮箱使用实际无法投递的保留域名。这些都不是真实存在的个人信息。 本文只讲值如何泄露的结构，不涉及任何绕过或提取的方法。

本文不涉及的内容。 哪些数据可以放进外部工具、边界在哪里，这类判断标准与内部规程属于企业内部数据能否输入LLM那篇。什么内容用什么级别输出这类级别约定已经在WARN 为什么会变成垃圾桶里讲过，这里不再重复。翻转成白名单的一般步骤在禁止清单永远慢一步。本文是把那个原理落到日志路径这一个点上的实现。

关于法律。 处理个人信息的组织在收集、保管、销毁方面负有义务。不过本文不引用任何条文和金额。 适用范围和保留期限随业务形态和国家而不同，请查阅相关法律法规和公司内部规程后确定。本文涉及的只是技术实现。

1. 把整个对象丢进去，后来新增的字段会跟着来

先看最重要的复现。只要理解这一个，本文就懂了一半。问题不是「把敏感值打进了日志」，而是「没有人把会进日志的范围固定下来」。

放一段把整个对象序列化后输出的代码，然后让时间往前走，制造出另一个团队为另一个功能新增字段的情形。日志调用不动。

node v22.16.0 / win32
--- 1-1. release v1: the object has 3 fields ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z"}

--- 1-2. release v2: product adds fields. the log call is UNCHANGED ---
signup ok {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","cardNumber":"0000-0000-0000-0000","nationalId":"000000-0000000"}

--- 1-3. diff: what the log gained without a code change ---
fields logged in v1 : 3  id,nickname,createdAt
fields logged in v2 : 6  id,nickname,createdAt,phone,cardNumber,nationalId
newly leaking        : phone,cardNumber,nationalId
lines of code changed to cause this : 0

最后一行就是全文的摘要。为造成这个变化而改动的代码行数是零。 加字段的人没读过日志代码，写日志代码的人不知道有这些字段。两边都没做错，值却泄露了。

这类缺陷在代码评审里抓不到。评审人看到的只是「新增了三个字段」这个改动，而单看这个改动完全没有问题。问题存在于两次改动之间的距离里。

1.1 展开和嵌套是一回事

「只要别把对象原样丢进去不就行了」，这个想法很自然。但常用的两种绕法根本不是绕法。

--- 1-4. the same happens through spread, nesting and ORM rows ---
spread into context  : {"requestId":"r-0001","id":"u-0001","nickname":"tester","createdAt":"2026-08-01T00:00:00Z","phone":"010-0000-0000","card ...
nested one level     : nationalId still present
depth does not help  : JSON.stringify walks the whole tree
  • 用展开运算符并进上下文并不等于挑选了字段，只是同样的字段往上抬了一层
  • 往下包一层也没用。序列化函数会遍历整棵树，所以深度不是防线
  • 把数据库行对象原样传过去最危险。加一列日志就跟着变宽，而加列的人跟日志毫无关系
  • 把整个请求体挂到上下文上是同一种结构。客户端会发什么，不是服务端代码决定的
  • 共同点只有一个。决定范围的主体不是写日志的人。 这就是这个缺陷的定义

2. 在输出处遮挡只能挡住已知的格式

最先想到的应对是在输出前用正则遮挡，实际中也很常用。这种方式在哪里崩掉，我们只用无害的值做了确认：电话号码形状和工号形状，数字全是零。

九个里七个原样通过了。 而且它们通过的理由个个都很琐碎。

  • 分隔符从连字符换成了空格或点。上游系统一改归一化方式，规则从那天起就闲置了
  • 干脆没有分隔符。 这是存进数据库时常见的形态
  • 前面加了国家代码。 经过一层归一化成国际写法就会变成这样
  • 大小写不同。 全部原因就是正则少了一个标志位
  • 工号位数多了一位。 只是编号策略变了，规则就失手了
  • 共同点是什么都不会失败。没有任何信号告诉你脱敏没生效

2.1 在相反方向上也会出错

还有一种较少被提及的失效方式：规则抹掉了不该抹的东西。

--- 2-2. why the rule cannot be finished ---
the masker matches shapes. the data is defined by MEANING.
every upstream format change is a silent hole, and nothing fails loudly.

--- 2-3. and the rule can be too greedy in the other direction ---
order 010-0000-0000 shipped           order 010-****-**** shipped   <- masked, but this was not personal data
build EMP-000000 finished             build EMP-****** finished   <- masked, but this was not personal data

a pattern rule has two failure modes at once: it misses, and it destroys.

订单编号和构建标签碰巧符合那个形状。这时脱敏就成了抹掉非敏感值、妨碍排障。于是人们把规则放宽，放宽后的规则又开始漏。这个钟摆运动没有尽头。

根本原因一句话就能说清。正则匹配的是形状，敏感信息是按含义定义的。 同样的十一位数字，在某个语境里是个人信息，在另一个语境里是订单号。这个差别并不在值本身里面。

拦截位置拦住什么出现新字段时对副本的覆盖范围回退
产生点（包装类型）值本身不以字符串形式存在无影响（只处理被包装的值）不会产生新副本回退代码
事件组装（白名单）除选定字段外的全部自动排除日志器以下的全部区间回退代码
日志器序列化器知道名字的字段不认识名字就放行只覆盖用该日志器的地方回退配置
采集器规则符合模式的值模式不同就放行立刻全局，但不含已有副本立刻
输出后集中清洗只清你找到的不知道你动过的那一份副本不可（原件已失）

4. 错误对象会替你把值带走

不管你把日志调用整理得多干净，总有一条路径会留下来。那就是异常。 异常不需要有人决定「记一条日志」就会被打印出来。

node v22.16.0 / win32
--- 4-1. route A: the value goes into the message ---
e.message           : invalid nationalId: 000000-0000000
first stack line    : Error: invalid nationalId: 000000-0000000

--- 4-2. route B: the value rides on a property ---
e2.message          : payment declined   (clean)
JSON of e2.context  : {"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}

--- 4-3. what each common serializer emits ---
JSON.stringify(e2)            : {"name":"AppError","context":{"request":{"userId":"u-0001","phone":"010-0000-0000","nationalId":"000000-0000000"},"attempt":2}}
  -> CONTAINS nationalId
String(e2)                    : AppError: payment declined
  -> clean
util.inspect(e2) contains     : CONTAINS nationalId
console.error path uses inspect, so the terminal shows it too

两条路径性质不同。

  • 路径 A 看得见。 在校验失败信息里带上值是一个体贴的习惯，因此非常常见，也因此非常常泄露。放进信息的那一刻，它也进了栈的第一行
  • 路径 B 看不见。 信息是干净的，但上下文属性上挂着整个请求。而且这个习惯是被推荐的习惯，所以传播得更广
  • 只看信息就下判断会错。序列化器遍历什么才决定真正流出去的内容
  • 终端输出走的是同一条检视路径，所以屏幕上也会原样显示

4.1 原因链、未处理异常，以及看上去安全的陷阱

--- 4-4. the cause chain carries it further ---
outer.message                 : checkout failed   (clean)
inspect(outer) contains       : CONTAINS nationalId
a wrapper error looks innocent while dragging the original context

--- 4-5. why JSON.stringify(err) looks safe and is not ---
JSON.stringify(new Error(payload.phone)) : {}
message and stack are non-enumerable, so plain JSON drops them,
which is exactly why teams add a custom error serializer,
and the custom serializer is what puts message, stack and context back in.

--- 4-6. an unhandled rejection prints it with no logging code at all ---
uncaught handler saw : AppError: payment declined
full text contains   : CONTAINS nationalId

nobody called a logger here. the runtime did.

4-5 尤其有启发。默认序列化会把错误变成空对象，因为信息和栈是不可枚举属性。于是团队遇到「错误打不进日志」的不便，就加上专用的错误序列化器。那个序列化器又把信息、栈和上下文塞了回去。等于自己把看上去安全的默认行为拆掉了。

  • 用原因链包起来的外层错误因为信息干净反而更让人放心，但它把内层上下文原样拖着走
  • 未处理异常不需要任何人调用日志器，运行时就会打印。审计日志调用永远列不到这条路径
  • 因此需要一条规则：错误上下文里只放标识符，比如请求 ID、用户 ID、订单 ID
  • 校验失败信息里写哪里不对，而不是值本身。「格式不匹配，字段 nationalId」就够了
  • 有了第 5 节的包装类型，这条规则会自动得到遵守，因为把包装值放进信息里也不会出现原值

5. 在产生点拦住 — 不取就不出来的包装类型

现在讲解法。想法很简单。不要把敏感值当成字符串带着走。 而是用必须显式调用取值才会给出原值的类型把它包起来。包起来之后，失误暴露的是占位符而不是值。

const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // 显式且可检索的唯一出口
  expose() { return this[RAW]; }
  // 所有隐式路径都返回同一个占位符
  toString() { return '[' + this.label + ' redacted]'; }
  toJSON()   { return '[' + this.label + ' redacted]'; }
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }
}

const phone = new Secret('010-0000-0000', 'phone');

要点是把四个钩子一起覆盖。少一个，东西就从那个洞全跑出去。我们挑了十三条可能出错的路径全部跑了一遍。

5.1 只实现一半，还不如不做

--- 5-5. what happens if you implement only half of it ---
  toString only, template : [redacted]
  toString only, JSON     : {"v":"010-0000-0000"}   <- LEAK
  toString only, inspect  : HalfSecret { v: '010-0000-0000' }   <- LEAK
  a partial wrapper is worse than none: it reads as safe.

--- 5-6. the strict variant: refuse instead of substituting ---
  concat -> TypeError: Secret must be unwrapped with .expose() before use
  JSON  -> "[phone redacted]"   (toJSON still substitutes, so logs never crash)
  throwing catches mistakes in tests; substituting keeps production quiet.
  a common split: throw in dev and test, substitute in production.

--- 5-7. the wrapper does not survive the network boundary ---
  after JSON round trip : {"contact":"[phone redacted]"}
  the type is a source-side guard. across a boundary you must re-wrap on parse.
  • 只实现了字符串转换的包装类在屏幕上是遮住了，但在序列化和检视输出里把原值原样吐了出来。而那边才是真正的日志路径
  • 半截包装类比没有更危险，因为读代码的人会判断「这个已经包起来了所以安全」
  • 严格变体在你试图当字符串用时抛出异常。它能在测试里立刻抓住失误，但也可能在生产上制造新事故
  • 常见的折中是开发和测试里抛出、生产里替换成占位符。序列化钩子两边都保持替换，这样日志不会崩
  • 包装类型跨不过边界。 序列化发出去，对方收到的是占位符字符串。接收方需要重新包装，所以这套做法要各服务各自建立
  • 补充一点，有类型系统会更强。 在要求字符串的位置放入包装值，编译阶段就会被拦下

6. 定要放进去的字段，而不是要去掉的字段

包装类型保护的是值。可是第 1 节的问题不是值而是范围。把范围固定下来就是本节的事。这里只看一个问题：怎样把敏感字段排除掉。

// 方向 1. 定要去掉的字段
const DENY = ['phone', 'cardNumber', 'nationalId'];
function denylist(obj) {
  const out = { ...obj };
  for (const k of DENY) delete out[k];
  return out;
}

// 方向 2. 定要放进去的字段
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];
function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

在最初编写它们的那个模式上，两个函数分辨不出来。这正是这个缺陷能长期存活的原因。

--- 6-2. now the schema moves. neither rule is edited ---
  denylist (v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","national_id":"000000-0000000","backupPhone":"010-0000-0000","kyc":{"documentNo":"D-000000000"}}
  allowlist(v3)  : {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic"}

  sensitive values present in denylist output  : id-shaped value, phone-shaped value, document-shaped value
  sensitive values present in allowlist output : none

我们把模式往三个方向推了推。同样的数据换了一种命名风格进来，挂上了没人通知过的新字段，还多了一层嵌套结构。要去掉的清单三项全放行，要放进去的清单三项全拦住。这跟第 1 节正好对照。第 1 节里自动泄露的东西，在这里自动被挡住。

--- 6-3. the asymmetry, stated plainly ---
  denylist  fails OPEN : an unknown field is emitted
  allowlist fails CLOSED: an unknown field is dropped
  a new field is added by someone who has never read the logging code.
  so the rule has to be safe when nobody updates it.

--- 6-4. what you lose, and how to notice ---
  fields dropped from the log : phone, cardNumber, nationalId, national_id, backupPhone, kyc
  a field you needed for debugging is now missing, and that is the cost.
  make it visible instead of silent:
  {"id":"u-0001","nickname":"tester","createdAt":"2026-08-01","plan":"basic","_dropped":6}
  the count tells you the schema moved, without telling you what moved.

--- 6-5. the allowlist has to be applied at build time, not at write time ---
  event object keys : ["id","nickname","createdAt","plan"]
  the wide object never reaches the logger, so no later stage can widen it.
  narrowing inside the logger is one layer too late: everything upstream
  of the logger, including error handlers, still sees the wide object.
  • 失效方向相反。 去掉清单会放出不认识的字段，放进清单会丢掉不认识的字段。规则必须在没人更新时依然安全，所以后者才对
  • 是有代价的。 排障需要的字段会悄悄消失。这是白名单的真实成本，不该藏起来
  • 让代价不再无声的廉价做法在 6-4：只把被丢弃字段的个数一起记下来。它不说变了什么，但会告诉你模式动过了
  • 这个数字哪天突然变大，就是上游发生了变更的信号，也是检讨要不要更新白名单的契机
  • ★应用位置是决定性的。 在日志器内部收窄就晚了一层。日志器上方的一切，尤其是错误处理器，看到的仍是宽对象
  • 所以收窄要放在构造事件对象的那一刻。宽对象不到达日志器，后面任何阶段都无法把它再变宽

7. 只能显示后四位时，该在哪里截断

现实中确实存在部分显示的需求。客服要看到卡号后四位才能确认对方身份。这个需求本身是正当的。问题是在哪里截断。

node v22.16.0 / win32
--- 7-1. the requirement: a support screen shows the last 4 digits ---
  requested display value : ****-****-****-0000

--- 7-2. attempt A: keep both on the same record ---
  record  : {"userId":"u-0001","cardNumber":"0000-0000-0000-0000","cardLast4":"0000"}
  the display value exists, and so does the original, one key apart.
  every whole-object log, error context and API response carries both.
  the partial value did not reduce anything. it added a field.

--- 7-3. attempt B: cut at the source, keep only the derived value ---
  record  : {"userId":"u-0001","cardLast4":"0000","card":"[card redacted]"}
  inspect : { userId: 'u-0001', cardLast4: '0000', card: [card redacted] }
  the screen gets cardLast4. the logger gets cardLast4. nothing else is reachable
  without calling .expose(), and .expose() is greppable.

--- 7-4. the two attempts under the same accidental log line ---
  A : {"msg":"checkout","data":{"userId":"u-0001","cardNumber":"0000-0000-0000-0000","cardLast4":"0000"}}
      -> ORIGINAL PRESENT
  B : {"msg":"checkout","data":{"userId":"u-0001","cardLast4":"0000","card":"[card redacted]"}}
      -> derived value only

7-2 是非常常见的错误。把截断值和原值并排放在同一个对象里。 界面用截断值，需求是满足了。可是这个对象整体进日志的那一刻，原值也跟着走了。 部分显示什么都没减少，只是多了一个字段。

7-3 才是答案。在边界处截断一次，只留派生值，原值保持被包装的状态。 这样界面和日志器拿到的都只是截断值。

--- 7-5. cutting late produces drift ---
  input                : "0000 0000 0000 0000"
  last4  (digits only) : 0000
  last4v2(naive slice) : "0000"
  same field name, two values, depending on which layer computed it.
  cutting once at the boundary makes the answer single-valued.

--- 7-6. a partial value is still personal data ---
  one record may hold several partials : {"u-0001":["0000","010-0000","a***@example.invalid"]}
  each is harmless alone. joined on the same subject they narrow the set.
  so a partial is a display format, not a declassification.
  keep the same retention and access rules on it.
  • 7-5 是截断太晚带来的第二个问题。截断代码出现在多个层里，同一个字段名就会装着不同的值。一边先只留数字再截，另一边直接截字符串末尾
  • 在混有空格的输入上两个结果分道扬镳。一个是四位数字，另一个是包含空格的四个字符。于是出现了随界面不同而不同的值，然后变成客服工单回到你这里
  • 在边界只截一次，这个问题在定义上就消失了，因为产生派生值的地方只有一处
  • 7-6 是最后的提醒。部分值仍然是个人信息。 单看一个是无害的，但同一主体身上挂了多个部分值，范围就会收窄
  • 因此部分显示是展示格式，不是解密降级。请把保留期限和访问权限按与原值相同的标准来设
  • 具体的位数和展示范围随行业和合同而不同。请查阅相关法律法规、公司内部规程以及支付网络的规定后确定

8. 在已有日志里找危险点，以及落地顺序

到这里为止讲的是「今后怎么做」，这一节讲的是「已经堆下的怎么办」。诊断要扫两遍。

node v22.16.0 / win32
--- 8-1. build a sample log tree ---
  api.log       3 lines
  worker.log    2 lines
  auth.log      2 lines
  batch.log     3 lines

--- 8-2. pass 1: key names, not value shapes ---
  file          lines   risky keys found
  ----------------------------------------------------------------------
  api.log       3       phone(1) context.cardNumber(1)
  worker.log    2       -
  auth.log      2       authorization(1) password(1)
  batch.log     3       national_id(1) nationalId(1) email(1)

--- 8-3. pass 2: key inventory, to catch names you did not list ---
  distinct keys in the sample : 14
  matched the risk list       : 7
  NOT on the risk list        : 7
  lvl, msg, path, userId, context, jobId, durationMs
  read this list by hand once. that is the review, and it is finite.
  a value-shape scan cannot produce this list at all.

第一轮按键名而不是值的形状来找。正如第 2 节所示，值的格式随上游变化，而键名相对稳定。嵌套的键要连路径一起抓，context.cardNumber 就是这样被抓到的。

不过第二轮更重要。 把没有命中风险清单的其余键全部列出来，让人读一遍。样本里不同的键有十四个，其中七个在清单之外。这份清单是有限的。 读一次就结束。而且它是只扫描值格式的方式根本产不出的清单。

--- 8-4. rank by blast radius, not by count ---
  file          keys   retain   copies   score
  ----------------------------------------------------------
  batch.log     3      365d     3        3285
  auth.log      2      365d     4        2920
  api.log       2      90d      4        720
  worker.log    0      14d      1        0
  score = risky keys x retention days x number of destinations.
  a low-volume line kept for a year in four places outranks a noisy one kept for two weeks.

--- 8-5. order of work, by how hard each step is to undo ---
  # action                                cost      undo                  buys you
  ------------------------------------------------------------------------------------------------------------
  1   collector-side drop rule              minutes   fully reversible      stops NEW copies today
  2   shorten retention on the worst file   minutes   reversible            shrinks the window
  3   purge existing copies                 days      NOT reversible        needs an owner list first
  4   allowlist the event builders          weeks     reversible by revert  the actual fix
  5   wrapper type on the fields            weeks     reversible by revert  makes step 4 hold
  6   remove the collector rule             minutes   reversible            only after 4 and 5 are verified

8-4 把优先级按波及范围而不是条数来排，用风险键数量乘保留天数乘副本目的地数量。结果一条安静但保留一年、复制到三处的日志排到了吵闹但只留三个月的日志之上。要是按条数排，顺序就反了。

落地顺序上有一个争议点：先动采集器还是先动代码。 8-5 的答案是先动采集器，理由并不是「那样更好」。

步骤生效范围耗时回退局限
1. 采集器拦截规则立刻全局分钟完全可回退第 2 节的模式局限照旧
2. 缩短保留期该条日志分钟可回退已有副本不受影响
3. 销毁已有副本只限已销毁的天不可要先有责任人清单
4. 事件组装处加白名单已发布的服务周回退代码每个服务各自做
5. 字段应用包装类型被包装的字段周回退代码跨不过边界
6. 移除采集器规则立刻全局分钟可回退4 和 5 验证前禁止
  • 采集器规则排在最前，是因为它是止血带。 不用发布就立刻全局生效，错了也能立刻撤掉
  • 同时止血带不是治疗。 它对已经生成的副本毫无作用，而且它本身就是第 2 节验证过并不完备的模式匹配
  • 不要急着销毁。 那是唯一不可回退的步骤，没有责任人清单就执行，你说不出「已经删了」这句话
  • 代码改造之所以按 4、5 的顺序，是因为白名单固定范围，包装类型维持这个固定。反过来做，没被包装的新字段会源源不断进来
  • 最后的第 6 步只在验证之后做。验证方法很简单：关掉采集器规则，在预发环境跑同一套扫描，看风险键是不是零
  • 新服务顺序是反的。 一开始只做 4 和 5 就行，不需要采集器规则

8.1 检查清单

  • 找出了日志调用中整体传入对象的地方（包含展开、嵌套、数据库行、请求体）
  • 在构造事件对象的位置明确列出了要放进去的字段，没有指定要去掉的字段
  • 白名单应用在事件组装时刻而不是日志器内部
  • 把被丢弃字段的个数一起记下，以便发现模式变更
  • 对敏感字段应用了包装类型，并且四个钩子全部实现
  • 检索了包装类型的取值调用，确认了全部使用点
  • 立下了错误上下文只放标识符的规则
  • 校验失败信息写的是字段名而不是值
  • 确认了专用错误序列化器会遍历什么
  • 部分显示只在边界截断一次，没有和原值放在同一个对象里
  • 部分值也适用与原值相同的保留和访问标准
  • 按键名扫描了已有日志，并让人读完了清单之外的全部键
  • 优先级按键数 × 保留天数 × 目的地数来排
  • 把日志副本的目的地清单和责任人写成了文档
  • 依据相关法律法规和公司内部规程确认了处理范围和保留期限

结论：不要挑要去掉的，要挑要放进去的

把实际验证到的东西一行一行重新摆一遍就是这样。把整个对象丢进去的代码，在代码零行改动的情况下多泄露了三个字段。输出阶段的正则在九个无害的格式变体里漏掉了七个，同时又抹掉了两个非敏感值。一行日志仅凭平凡的运维就变成了九份，而脱敏修好的是其中一份。

另一侧也用运行验证过。覆盖四个钩子的包装类型在十三条失误路径上泄露为零。定了要放进去哪些字段的序列化，在模式往三个方向移动之后仍然什么都没放出去。同样的情形下，定要去掉哪些字段的那一侧三项全放行了。

所以结论不是「把脱敏做得更好」。脱敏是最后一道防线。 在输出处遮挡只能挡住你知道的模式，而那时复制早已完成。真正的解法在值进入日志路径之前，而在那个位置要用的规则只有一条。不要挑要去掉的，要挑要放进去的。 只有在遇到不认识的字段时倾向于丢弃的规则，才能撑过没有人更新它的那几年。

现在就能做的事有一件。在日志代码里找出一处整体传入对象的调用，把那个对象的字段清单现在打印出来看看。 如果你想不起上一次确认这份清单是什么时候，那就说明这期间多出了什么你也并不知道。第 8 节的第二轮扫描，正是为了把这项确认一次做完而设计的步骤。

# 在产生点拦住敏感数据 — 包装类型、白名单、排查步骤

> 来源: braindetox.kr — 在输出阶段脱敏已经太晚
> 依据: Windows 10 / Node.js v22.16.0 实际运行验证
> 可以把这个文件原样贴给 AI，写上「按这个标准帮我检查我们的日志路径」。
> 下面的示例值都是只对上格式的假数据。只对齐位数，数字全部是零。
> 个人信息的处理范围和保留期限请查阅相关法律法规和公司内部规程后确定。

## 0. 一句话原则

脱敏是最后一道防线。真正的解法是让那个值不进入日志路径，
而在那个位置要用的规则只有一条。**不要挑要去掉的，要挑要放进去的。**

| 方式 | 遇到不认识的字段 | 判断 |
|---|---|---|
| 要去掉的字段清单 | 放出去 (fail open) | 模式一动就泄露 |
| 要放进去的字段清单 | 丢掉 (fail closed) | **用这个** |
| 输出正则 | 格式不同就放行 | 止血带，不是解决方案 |

## 1. 包装类型 — 不取就不出原值

四个钩子要**全部**覆盖。少一个，东西就从那个洞全跑出去。

```js
const util = require('util');
const RAW = Symbol('raw');

class Secret {
  constructor(value, label) {
    this[RAW] = value;
    this.label = label || 'secret';
  }
  // 唯一出口。因为有名字，代码检索就能列出全部使用点
  expose() { return this[RAW]; }

  toString() { return '[' + this.label + ' redacted]'; }   // 模板、拼接
  toJSON()   { return '[' + this.label + ' redacted]'; }   // 序列化
  [util.inspect.custom]() { return '[' + this.label + ' redacted]'; }  // console.log
  [Symbol.toPrimitive]() { return '[' + this.label + ' redacted]'; }   // 隐式转换
}
```

验证过的 13 条路径泄露为零:
模板字符串 / 字符串拼接 / String() / 数组 join / JSON.stringify /
嵌套 JSON / util.inspect / 嵌套 inspect / format %s / format %j /
format %o / String.prototype.concat / + 运算符

注意:
- **只实现一半还不如不做。** 只有 toString 时，序列化和检视输出照样泄露
- 常见折中是开发测试里抛出、生产里替换。toJSON 两边都保持替换
- **跨不过边界。** 序列化发出去对方收到的是占位符。接收方要重新包装

## 2. 白名单序列化 — 在构造事件的那一刻收窄

```js
const ALLOW = ['id', 'nickname', 'createdAt', 'plan'];

function allowlist(obj) {
  const out = {};
  for (const k of ALLOW) if (k in obj) out[k] = obj[k];
  return out;
}

// 收窄的位置是决定性的。在这里，不是在日志器内部。
function buildEvent(user) {
  const picked = allowlist(user);
  const droppedCount = Object.keys(user).length - Object.keys(picked).length;
  return { event: 'signup', user: picked, _dropped: droppedCount };
}
```

- 在日志器内部收窄就晚了一层。错误处理器等日志器上方仍然看到宽对象
- 记下被丢弃的个数，就能**在不说变了什么的前提下**知道模式动过了
- 那个数字突然变大就是上游变更的信号，检讨是否更新白名单

## 3. 错误上下文规则

- **不要把值放进校验失败信息。**「格式不匹配，字段 nationalId」就够了
- 错误上下文里**只放标识符**：请求 ID、用户 ID、订单 ID
- 用原因链包起来的外层错误信息看着干净，却**把内层上下文拖着走**
- 未处理异常**不用调用日志器**运行时就会打印。审计日志调用抓不到
- 别因为默认序列化把错误变成空对象就放心。**专用序列化器会把它塞回去**

## 4. 排查步骤 — 扫两遍

1) **第一轮：按键名扫描**（不是按值的形状）
   - 嵌套键连路径一起：context.cardNumber
   - 值的格式随上游变化，键名相对稳定
2) **第二轮：把清单之外的键全部列出来让人读**
   - 这份清单是有限的。读一次就结束
   - 只扫描值格式的方式根本产不出这份清单
3) **优先级 = 风险键数 × 保留天数 × 副本目的地数**
   - 不要按条数排。安静但留得久、散得广的日志排在上面

## 5. 落地顺序 — 越难回退的越靠后

| # | 步骤 | 耗时 | 回退 | 换来什么 |
|---|---|---|---|---|
| 1 | 采集器拦截规则 | 分钟 | **完全可回退** | 从今天起阻断新副本 |
| 2 | 缩短保留期 | 分钟 | 可回退 | 收窄暴露窗口 |
| 3 | 销毁已有副本 | 天 | **不可** | 先要有责任人清单 |
| 4 | 事件组装处加白名单 | 周 | 回退代码 | **真正的解决** |
| 5 | 字段应用包装类型 | 周 | 回退代码 | 让第 4 步守得住 |
| 6 | 移除采集器规则 | 分钟 | 可回退 | 只在 4、5 验证后 |

- 采集器排在最前不是因为它更好，而是因为它是**止血带**
- 新服务顺序相反。只做 4 和 5 就行，不需要采集器规则

## 6. 检查清单

- [ ] 找出了日志调用中**整体传入对象的地方**（展开、嵌套、数据库行、请求体）
- [ ] 在事件组装处**明确列出了要放进去的字段**（不是指定要去掉的）
- [ ] 白名单应用在**事件组装时刻而不是日志器内部**
- [ ] 把被丢弃字段的**个数**一起记下了
- [ ] 对敏感字段应用了包装类型，并且**四个钩子全部**实现
- [ ] 检索了取值调用，确认了**全部使用点**
- [ ] 立下了错误上下文**只放标识符**的规则
- [ ] 校验失败信息写的是**字段名而不是值**
- [ ] 确认了专用错误序列化器**会遍历什么**
- [ ] 部分显示**只在边界截断一次**，没有和原值放在同一个对象里
- [ ] 部分值也适用**与原值相同的保留和访问标准**
- [ ] 按**键名**扫描了已有日志，并读完了**清单之外的全部键**
- [ ] 优先级按**键数 × 保留天数 × 目的地数**来排
- [ ] 把日志副本的**目的地清单和责任人**写成了文档
- [ ] 依据**相关法律法规和公司内部规程**确认了处理范围和保留期限

## 7. 不要做的事

- ❌ 把对象、数据库行、请求体**整体**丢进日志 — 新字段会以零行代码跟进来
- ❌ 把输出正则脱敏**当成解决方案** — 格式变体能突破它，还会抹掉无害的值
- ❌ 把截断值和**原值放在同一个对象里** — 一次整体日志两个都会出去
- ❌ 把**值**写进校验失败信息 — 它也会进栈的第一行
- ❌ 没有责任人清单就**先做销毁** — 那是唯一不可回退的步骤
- ❌ 只加了采集器规则就**认为完事** — 对已经生成的副本毫无作用
- ❌ 包装类型**只实现一半** — 因为看上去安全反而更危险
