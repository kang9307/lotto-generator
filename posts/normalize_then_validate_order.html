검사한 값과 실제로 쓰는 값이 다르면, 검사는 처음부터 없었던 것과 같다

2026-08-01 개발/인프라

서론: 검사는 통과했는데, 들어온 값은 다르다

로그를 보다가 이상한 값을 발견한다. 저장된 이름에 줄바꿈이 들어 있거나, 열려서는 안 되는 형태의 문자열이 파일 경로 자리에 앉아 있다. 코드를 열어 보면 입력 검사가 분명히 있다. 정규식도 촘촘하고, 금지 문자 목록도 길다. 검사를 건너뛰는 분기도 없다. 그런데도 값이 들어와 있다.

이럴 때 대부분의 대응은 검사 규칙을 더 촘촘하게 만드는 것이다. 정규식에 문자를 추가하고, 목록을 늘리고, 예외 케이스를 붙인다. 그런데 며칠 뒤 비슷한 값이 또 들어온다. 규칙을 아무리 고쳐도 재발한다면 문제는 규칙이 아니다.

이 글이 다루는 것은 딱 한 가지다. 검사기가 판정한 문자열과 프로그램이 실제로 사용한 문자열이 서로 다른 경우다. 이 상황에서 검사기는 아무 잘못이 없다. 자기가 받은 값에 대해 정확하게 답했다. 다만 그 답이 최종 값에 대한 답이 아니었을 뿐이다.

그래서 이 글의 논지는 「검증하세요」가 아니다. 검증은 이미 있다. 중요한 것은 무엇을 검증했는가다. 그리고 그 「무엇」을 결정하는 것은 규칙이 아니라 순서다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 런타임은 Node.js v22.16.0 (win32)이고, 일부 결과는 Python 3.13.3으로 교차 확인했다. 스크립트는 전부 파일로 저장해 실행했다.

이 글이 하지 않는 것. 여기에는 공격 절차나 침투 방법이 없다. 예시는 전부 무해한 문자와 기준 디렉터리 안에 머무는 경로만 쓴다. 보여 주려는 것은 「이렇게 뚫는다」가 아니라 「이 순서면 검사가 무의미해진다」는 구조 하나다. 그래서 경로 절을 포함해 모든 예시는 검사 시점의 값과 사용 시점의 값이 다르다는 사실까지만 보여 준다.

이 글이 다루지 않는 것. 같은 글자가 유니코드 안에서 여러 코드포인트열이 되는 원리는 NFC와 NFD에서 다뤘다. 여기서는 정규화를 배치 문제로만 본다. 웹 입력 처리 전반은 웹 보안 기초에 있다. 허용목록과 금지목록 중 무엇을 쓸지, 검증을 어느 계층에 둘지는 이 글의 주제가 아니다. 이 글은 순서 한 점에만 머문다.

1. 같은 검사기, 순서만 바꿨을 뿐인데

먼저 가장 흔한 형태부터 재현한다. 금지 문자 검사를 먼저 하고, 통과한 값을 나중에 디코딩하는 순서다. 이 코드를 읽으면 아무 문제가 없어 보인다. 검사가 앞에 있고 사용이 뒤에 있으니 순서가 맞아 보인다. 실제로 무슨 일이 일어나는지 검사 시점의 값과 사용 시점의 값을 나란히 찍었다.

node v22.16.0 / win32
--- 1-1. ORDER A: validate first, decode afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a%3Cb           PASS      a<b             NO
note%3Bnext     note%3Bnext     PASS      note;next       NO
x%26y           x%26y           PASS      x&y             NO
line%0Asecond   line%0Asecond   PASS      line\nsecond    NO
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-2. ORDER B: decode first, validate afterwards ---
raw input       value AT CHECK  verdict   value AT USE    clean at use?
----------------------------------------------------------------------------
hello           hello           PASS      hello           yes
a%3Cb           a<b             REJECT    (never used)    -
note%3Bnext     note;next       REJECT    (never used)    -
x%26y           x&y             REJECT    (never used)    -
line%0Asecond   line\nsecond    REJECT    (never used)    -
plain<bad>      plain<bad>      REJECT    (never used)    -

--- 1-3. the gap, counted ---
order A  passed check but dirty at use : 4 of 6
order B  passed check but dirty at use : 0 of 6
the checker function is identical in both runs. only the order changed.

표의 두 번째 열과 네 번째 열을 비교하는 것이 이 글 전체의 요령이다. 순서 A에서 a%3Cb는 검사 시점에 a%3Cb였다. 이 문자열에는 금지 문자가 하나도 없다. 검사기는 정직하게 통과 판정을 내렸다. 그런데 사용 시점의 값은 a<b다. 검사기는 이 문자열을 본 적이 없다.

  • 여섯 개 입력 중 네 개가 이 경로를 지났다. 통과 판정을 받은 뒤 최종 값에서 금지 문자가 나타났다
  • 마지막 행만 정상이다. 인코딩되지 않은 plain<bad>는 검사 시점에도 금지 문자를 갖고 있었으므로 거절됐다. 즉 이 검사기는 눈에 보이는 형태만 잡는다
  • 순서 B에서는 통과 후 오염이 0건이다. 검사기 함수는 두 실행에서 문자 하나 다르지 않다
  • 줄바꿈 행이 특히 중요하다. line%0Asecond는 로그나 헤더처럼 줄 단위로 의미가 정해지는 자리에 들어가면 값 하나가 두 줄이 된다
  • 이 결함은 검사기를 고쳐서는 사라지지 않는다. 규칙을 아무리 늘려도 검사기가 보는 것은 여전히 인코딩된 문자열이다

1.1 검사기는 자기가 무의미해졌다는 것을 알 수 없다

이 구조의 나쁜 점은 아무도 오류를 만나지 않는다는 것이다. 예외가 나지 않고, 로그에 경고가 남지 않고, 검사기는 자기 일을 정확히 했다고 보고한다. 통합 테스트를 돌려도 통과한다. 테스트가 넣는 값은 대개 이미 디코딩된 평범한 문자열이라 두 순서 모두 같은 결과를 내기 때문이다.

즉 이것은 테스트로 잘 안 잡히고 리뷰로도 잘 안 잡히는 종류의 결함이다. 리뷰어가 보는 것은 「검사가 있다」와 「사용이 있다」이고, 그 둘의 순서까지 의심하려면 사이에 낀 줄이 값을 바꾼다는 사실을 먼저 알고 있어야 한다.

2. 유니코드 정규화 - 검사 뒤에 두면 판정이 뒤집힌다

두 번째 경로는 유니코드 정규화다. 앞 절의 디코딩보다 훨씬 조용하다. 디코딩은 적어도 %라는 눈에 띄는 흔적을 남기지만, 정규화는 이미 정상으로 보이는 문자열을 다른 문자열로 바꾼다. 한 번 통과시키면 어떤 일이 일어나는지 먼저 봤다.

node v22.16.0 / win32
--- 2-1. one NFKC pass changes the string itself ---
before      len  after NFKC  len  codepoints after
--------------------------------------------------------------------------
report      6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
ｒｅｐｏｒｔ 6    report      6    U+0072 U+0065 U+0070 U+006F U+0072 U+0074
a／b        3    a/b         3    U+0061 U+002F U+0062
ﬁle         3    file        4    U+0066 U+0069 U+006C U+0065
①           1    1           1    U+0031
㎡          1    m2          2    U+006D U+0032
ｎｏ＜op    5    no<op       5    U+006E U+006F U+003C U+006F U+0070

여기서 눈여겨볼 것은 길이가 바뀌는 행이다. ﬁle은 3글자였는데 정규화 후 4글자가 됐고, ㎡는 1글자에서 2글자가 됐다. 길이 제한 검사를 정규화 앞에 두면 제한을 통과한 값이 제한을 넘긴 상태로 저장된다.

그리고 마지막 두 행이 이 절의 핵심이다. 전각 문자로 쓴 값이 정규화를 거치면서 반각 슬래시와 반각 부등호가 됐다. 검사 시점에는 존재하지 않던 문자가 사용 시점에 생겨난 것이다. 판정이 실제로 어떻게 뒤집히는지 두 방식으로 확인했다.

--- 2-2. allowlist verdict before vs after normalization ---
input       allow(before)  allow(after)  flipped?
--------------------------------------------------------
report      true           true          no
ｒｅｐｏｒｔ false          true          YES
a／b        false          false         no
ﬁle         false          true          YES
①           false          true          YES
㎡          false          true          YES
ｎｏ＜op    false          false         no

--- 2-3. denylist verdict before vs after normalization ---
input       deny hit(before)  deny hit(after)  flipped?
------------------------------------------------------------
report      false             false            no
ｒｅｐｏｒｔ false             false            no
a／b        false             true             YES
ﬁle         false             false            no
①           false             false            no
㎡          false             false            no
ｎｏ＜op    false             true             YES

두 표가 정반대 방향으로 틀린다는 것이 중요하다.

  • 허용목록에서는 정상 값이 거절된다. 전각으로 입력한 ｒｅｐｏｒｔ는 정규화 후 완벽하게 유효한 report가 되는데, 정규화 전에 검사하면 거절된다. 사용자 입장에서는 「멀쩡한 이름을 안 받아 준다」는 버그다
  • 금지목록에서는 걸러야 할 값이 통과한다. 정규화 전에는 금지 문자가 없다가 정규화 후에 생겨난다
  • 두 경우 모두 검사기 자체는 정확하다. 틀린 것은 검사기가 아니라 검사기에게 넘긴 값이다
  • 실무에서는 앞쪽 오류가 먼저 발견된다. 사용자가 항의하기 때문이다. 뒤쪽 오류는 아무도 항의하지 않아서 오래 남는다
  • 이 두 표는 같은 원인의 두 얼굴이다. 하나만 고치면 다른 하나가 남는다

2.1 멱등이면 앞으로 옮겨도 된다

그러면 정규화를 언제 해야 하나. 답은 「가장 앞」인데, 그렇게 말해도 되는 근거가 있다. 정규화는 몇 번을 돌려도 결과가 같기 때문이다. 이것을 멱등이라고 부른다. 실제로 세 번 연속 돌려 봤다.

--- 2-4. NFKC is idempotent, so doing it FIRST is safe ---
report      n1==n2 true   n2==n3 true
ｒｅｐｏｒｔ n1==n2 true   n2==n3 true
a／b        n1==n2 true   n2==n3 true
ﬁle         n1==n2 true   n2==n3 true
①           n1==n2 true   n2==n3 true
㎡          n1==n2 true   n2==n3 true
ｎｏ＜op    n1==n2 true   n2==n3 true
a normalizer you can run twice with no change can always be moved to the front.

--- 2-5. NFC vs NFKC are not the same job ---
input       NFC         NFKC        NFC==NFKC
--------------------------------------------------
ｒｅｐｏｒｔ ｒｅｐｏｒｔ report      false
ﬁle         ﬁle         file        false
㎡          ㎡          m2          false
á          á           á           true

2-4의 의미는 단순하다. 정규화를 앞으로 옮겨도 잃는 것이 없다. 뒤쪽 어딘가에서 또 정규화가 일어나더라도 값은 더 이상 변하지 않으므로 안전하다. 이것이 「정규화를 먼저」라는 규칙이 위험 없이 성립하는 이유다.

2-5는 함정 하나를 보여 준다. NFC와 NFKC는 다른 일을 한다. 마지막 행의 악센트 문자는 두 방식이 같은 결과를 냈지만, 앞의 세 행은 전부 다르다. 전각을 반각으로 바꾸거나 합자를 풀어 쓰는 것은 NFKC만 하는 일이다. 그래서 「정규화를 하고 있다」는 말만으로는 어느 정규화인지 알 수 없다. 원리 자체가 궁금하면 NFC와 NFD를 보라. 여기서 필요한 결론은 하나다. 어느 형식을 쓸지 정하고, 그것을 문서에 적고, 모든 층이 같은 것을 쓰게 한다.

3. 공백과 대소문자 - 가장 흔하고 가장 안 보이는 어긋남

앞의 두 절은 특수 문자가 등장하는 이야기라 그나마 의심하기 쉽다. 이번 절은 그렇지 않다. trim과 소문자화는 너무 평범해서 아무도 이것을 「값을 바꾸는 연산」으로 인식하지 않는다. 예약어 목록 검사를 예로 잡고 순서를 바꿔 돌렸다.

[admin]         [admin]         true       [(rejected)]  -

순서 A에서는 예약어 목록이 정확히 한 가지 철자에만 반응했다. 앞뒤에 공백이 붙거나 대문자가 하나 섞이면 목록을 빠져나간다. 그런데 저장될 때는 그 값들이 전부 같은 형태로 정리되므로, 목록에 있는 이름이 목록을 통과한 상태로 저장된다. 순서 B에서는 같은 목록, 같은 입력으로 전부 걸러졌다.

3.1 유일성 검사와 저장 키가 갈릴 때

같은 결함이 훨씬 조용하게 나타나는 형태가 있다. 중복 검사다. 여기서는 보안 문제라기보다 데이터 무결성 문제로 나타난다.

--- 3-3. uniqueness checked on one value, stored as another ---
order A: unique-check on raw, store canonical
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? false  stored [alice@example.com]
  [ALICE@EXAMPLE.COM]     dup at check? false  stored [alice@example.com]
  distinct values checked : 3
  distinct values stored  : 1   <- three rows collapsed into one key
order B: canonicalize first, then unique-check
  [Alice@Example.COM]     dup at check? false  stored [alice@example.com]
  [ alice@example.com ]   dup at check? true   rejected
  [ALICE@EXAMPLE.COM]     dup at check? true   rejected

순서 A는 세 번 다 「중복 아님」이라고 답했다. 검사 시점의 세 문자열은 서로 다르니 그 답은 맞다. 그런데 저장 키로 바꾸고 나면 셋이 같은 값이 된다. 그래서 서로 다른 세 요청이 같은 키 하나를 두고 겹친다. 예외는 나지 않는다. 나중에 「같은 주소로 계정이 두 개 있다」거나 「먼저 만든 것이 사라졌다」는 신고로 나타난다.

3.2 trim은 하나의 규칙이 아니라 하나의 목록이다

trim이 무엇을 지우는지 실제로 확인하면 생각과 다르다. 공백처럼 보이는 문자가 전부 지워지지는 않는다.

--- 3-4. what exactly trim removes, and what it does not ---
input codepoints          trim() result     length change
------------------------------------------------------------
U+0061 U+0020 U+0062      3 -> 3            untouched
U+0020 U+0061             2 -> 1            trimmed
U+0061 U+00A0             2 -> 1            trimmed
U+0061 U+200B             2 -> 2            untouched
U+0061 U+FEFF             2 -> 1            trimmed
U+0061 U+3000             2 -> 1            trimmed
U+00A0 and U+3000 are removed, U+200B and U+FEFF are not.
so trim is not one rule. it is one specific list, and it must run before the check.

--- 3-5. lowercase is locale sensitive ---
input U+0130            : İ
toLowerCase()           : U+0069 U+0307
toLocaleLowerCase(tr)   : U+0069
length after each       : 2 vs 1
two layers using different locales produce two different canonical values.
  • 줄바꿈 없는 공백과 전각 공백은 지워진다. 눈에 보이지 않으므로 저장된 값을 눈으로 봐서는 알 수 없다
  • 너비 없는 공백은 지워지지 않는다. 공백처럼 보이지만 이 함수의 목록에 없다. 이 문자가 붙은 값은 다른 값으로 취급된다
  • 즉 trim은 「공백을 지운다」가 아니라 「특정 목록의 문자를 지운다」이다. 그 목록이 무엇인지 모르면 무엇이 통과할지도 모른다
  • 3-5는 더 미묘하다. 소문자화 결과가 로케일에 따라 다르다. 어떤 문자는 한쪽에서 두 글자가 되고 다른 쪽에서 한 글자가 된다
  • 층마다 다른 로케일을 쓰면 같은 입력에 대해 층마다 다른 정규형이 생긴다. 이것은 7절에서 다시 다룬다
  • 결론은 같다. 이 변환들은 전부 값을 바꾸는 연산이고, 값을 바꾸는 연산은 검사 앞에 있어야 한다

5. 디코딩은 멱등이 아니다

지금까지 나온 정규화 단계는 전부 멱등이었다. 그래서 「앞으로 옮기면 된다」는 처방이 통했다. 그런데 한 단계는 다르다. 퍼센트 디코딩이다. 몇 번 돌리는지에 따라 결과가 계속 달라진다.

5.1 층마다 자기 디코더를 갖고 있다

왜 두 번 디코딩이 일어나는지가 문제다. 아무도 두 번 디코딩하겠다고 결정하지 않는다. 각 층이 자기 자리에서 한 번씩 할 뿐이다.

--- 5-3. the same string through two different decoders ---
raw           decodeURIComponent    URLSearchParams     same?
----------------------------------------------------------------
a+b           a+b                   a b                 false
a%20b         a b                   a b                 true
a%2Bb         a+b                   a+b                 true
a%3Cb         a<b                   a<b                 true
the plus sign is where the two disagree. one layer sees a space, the other a plus.

--- 5-4. a value that survives a check and then changes at the next layer ---
raw           layer1 out    deny at L1?  layer2 out    deny at L2?
----------------------------------------------------------------------
a%253Cb       a%3Cb         false        a<b           true
a%2526b       a%26b         false        a&b           true
a%3Bb         a;b           true         (rejected)    -
ok-value      ok-value      false        ok-value      false
layer 1 checked the value layer 1 had. layer 2 uses a different string.

--- 5-5. counting decodes across a chain ---
start value : a%25253Cb
gateway     a%25253Cb      -> a%253Cb       (changed)
router      a%253Cb        -> a%3Cb         (changed)
handler     a%3Cb          -> a<b           (changed)
three layers each doing their own decode is three decodes, not one.
nobody wrote that down anywhere. it is the sum of three local decisions.
  • 5-3은 같은 이름의 작업이 도구마다 다르다는 것을 보여 준다. 더하기 기호를 한쪽은 공백으로 바꾸고 다른 쪽은 그대로 둔다
  • 그래서 「디코딩을 한 번 했다」는 진술만으로는 결과 문자열이 무엇인지 정해지지 않는다
  • 5-4는 1절의 구조가 층 사이에서도 똑같이 재현된다는 것을 보여 준다. 1층이 검사한 값과 2층이 쓰는 값이 다르다
  • 5-5에서는 세 층이 각자 한 번씩 디코딩해 결과적으로 세 번 디코딩됐다. 이 결정을 내린 사람은 없다. 세 개의 지역적 판단이 합쳐진 결과다
  • 표준도 이 지점을 명확히 한다. URL 표준은 파싱 과정에서 퍼센트 디코딩을 한 번 수행하며, 반복 디코딩을 규정하지 않는다
  • 따라서 디코딩은 정확히 한 번, 합의된 위치에서 일어나야 한다. 「방어적으로 한 번 더」가 여기서는 방어가 아니다

7.1 층마다 검사하면 층마다 다른 답이 나온다

값이 층마다 다르면 검사 결과도 층마다 다르다. 같은 금지 문자 검사를 네 층에서 각각 돌려 봤다.

--- 7-2. a check placed at each layer answers a different question ---
layer     value it checks       deny hit?  meaning
------------------------------------------------------------------
(client)  [ Ｒeport%2Fname ]    false      the string as typed
edge      [Ｒeport%2Fname]      false      the string after edge
gateway   [Ｒeport/name]        true       the string after gateway
service   [Report/name]         true       the string after service
storage   [report/name]         true       the string after storage
four checks, four different answers, all of them honest about their own layer.

--- 7-3. normalize once at the boundary, then nobody else touches it ---
[ Ｒeport%2Ename ]  final [report.name]    distinct values downstream of the boundary : 1
[q1.csv]            final [q1.csv]         distinct values downstream of the boundary : 1
[ ﬁle%20A ]         final [file a]         distinct values downstream of the boundary : 1

--- 7-4. is the boundary function repeatable? ---
[ Ｒeport%2Ename ]  n1 [report.name]  n1==n2 true   n2==n3 true
[q1.csv]            n1 [q1.csv]       n1==n2 true   n2==n3 true
[ ﬁle%20A ]         n1 [file a]       n1==n2 true   n2==n3 true
[a%2520b]           n1 [a%20b]        n1==n2 false  n2==n3 true
the last row is the warning. a boundary that decodes is not repeatable,
which is exactly why it must run in one place and only one place.

7-2에서 네 개의 답이 나왔고 전부 맞다. 각 층은 자기가 가진 문자열에 대해 정확히 답했다. 그런데 시스템 전체로 보면 「이 요청은 통과인가」라는 질문에 답이 하나로 정해지지 않는다. 이것이 흩어진 정규화의 진짜 비용이다. 판정이 위치의 함수가 된다.

7-3은 처방을 보여 준다. 경계에서 한 번만 정규화하고 아래 층은 손대지 않으면, 세 입력 모두 경계 아래에서 값이 하나였다. 7-4는 그 경계 함수 자체에 붙는 경고다. 디코딩을 포함한 경계 함수는 두 번 돌리면 결과가 달라진다. 그래서 「경계에서 한 번」이 권고가 아니라 필수 조건이 된다.

7.2 조용한 버전 - 캐시가 갈린다

이 결함이 보안 문제로 나타나지 않을 때는 성능 문제로 나타난다.

--- 7-5. cache keys computed at two layers ---
key hashed at layer 1 : dcd41471
key hashed at layer 3 : 845e9183
same request, same user, two cache entries : true
a split cache is the quiet version of this bug. nothing errors, the hit rate just drops.
  • 같은 요청인데 층마다 다른 캐시 키가 만들어졌다. 항목이 두 개 생기고 적중률이 떨어진다
  • 오류가 나지 않으므로 모니터링에 잡히지 않는다. 지표에는 「캐시 효율이 생각보다 낮다」로만 보인다
  • 같은 원리가 로그 집계에도 적용된다. 같은 대상이 두 이름으로 집계되면 통계가 갈린다
  • 속도 제한이나 중복 방지 장치도 키가 갈리면 무력해진다
  • 그래서 캐시 키, 로그 키, 저장 키는 전부 경계에서 나온 그 값으로 만들어야 한다

8. 코드에서 이 순서를 찾아내는 법

진단은 소비 지점에서 시작하는 것이 가장 확실하다. 파일을 열거나 질의를 만들거나 외부를 호출하는 줄을 먼저 찾고, 거기 들어가는 변수를 위로 거슬러 올라간다. 검증 호출을 만나면 그 사이의 모든 줄을 읽는다. 값을 바꾸는 줄이 하나라도 있으면 결함이다.

이 작업의 상당 부분은 기계적이다. 샘플 모듈을 대상으로 텍스트 검색만으로 훑어 봤다.

node v22.16.0 / win32

  • 첫 번째 형태는 검증한 변수에 다시 대입하는 것이다. 비교적 눈에 띈다
  • 두 번째 형태가 훨씬 위험하다. 검증한 변수는 그대로 두고 파생 변수를 만들어 그쪽을 쓴다
  • 두 번째 형태에서는 변경 내역이 멀쩡해 보인다. 검증도 있고, 검증한 변수는 손대지 않았다. 리뷰가 여기서 넘어간다
  • 검색어는 코드베이스에 맞춰 정하면 된다. 검증 함수 이름 목록과 값을 바꾸는 함수 이름 목록 두 개면 충분하다
  • 값을 바꾸는 목록에는 디코딩, 정규화, 공백 제거, 대소문자 변환, 치환, 경로 결합을 넣는다
  • 완벽할 필요는 없다. 후보 목록을 만들어 사람이 읽는 것이 목적이다

8.1 런타임 트립와이어

정적 검색으로 확신이 안 서면 실행 중에 확인하는 방법이 있다. 검사기가 받은 문자열을 기록해 두고, 소비 지점에서 같은지 비교하는 것이다.

--- 8-3. runtime tripwire: does the sink receive the value the checker approved? ---
order A under the tripwire:
  A0    checked [report]        used [report]       match
  A1    checked [a%3Cb]         used [a<b]          MISMATCH
  A2    checked [note%0Aline]   used [note\nline]   MISMATCH
  A3    checked [q1.csv]        used [q1.csv]       match
order B under the tripwire:
  B0    checked [report]        used [report]       match
  B1    rejected at check
  B2    rejected at check
  B3    checked [q1.csv]        used [q1.csv]       match
mismatches : order A 2   order B 0
the tripwire is a few lines and it turns an invisible ordering bug into a failing test.

이 장치의 값어치는 보이지 않던 결함을 실패하는 테스트로 바꿔 놓는다는 데 있다. 순서 A에서 두 건의 불일치가 잡혔고, 순서 B에서는 0건이었다. 개발 환경에서만 켜 두고 불일치가 나오면 즉시 실패시키면 된다.

어떤 단계를 어디에 둘지는 그 단계가 멱등인지로 결정된다. 이것은 직접 확인할 수 있다.

8-4의 검사는 몇 줄이면 된다. 표본 문자열 몇 개에 대해 두 번 적용한 결과가 한 번 적용한 결과와 같은지 보면 끝이다. 같으면 여러 층에 있어도 무해하고, 다르면 정확히 한 번만 실행되어야 한다.

8-5는 점검 목록을 실행 가능한 형태로 바꾼 것이다. 샘플 모듈은 세 항목에서 실패했다. 이 목록을 자기 코드에 돌려 보는 것이 이 절의 요점이다. 문서로 읽는 점검 목록은 잘 안 지켜지지만, 실패하는 검사는 고쳐진다.

9. 점검 목록과 하지 말 것

지금까지의 내용을 실무에서 바로 쓸 수 있는 형태로 정리한다.

점검 항목확인 방법실패 신호
정규화 함수가 하나로 정해져 있다이름을 검색해 정의가 하나인지 본다층마다 비슷한 함수가 따로 있다
정규화 함수가 멱등이다표본에 두 번 적용해 비교디코딩이 함수 안에 들어 있다
디코딩이 한 곳에서만 일어난다디코딩 호출을 전수 검색게이트웨이와 핸들러 양쪽에 있다
검증 함수가 최종 값을 받는다검증 호출 인자를 소비 지점 인자와 대조두 인자가 다른 변수다
검증과 사용 사이가 비어 있다그 사이 줄을 전부 읽는다대입이나 가공이 한 줄이라도 있다
경로는 정리 후에 판정한다포함 검사가 최종 경로에 걸려 있는지 본다원문 조각에 대해 기호를 찾고 있다
유일성과 저장 키가 같은 값이다중복 검사 인자와 저장 키를 비교한쪽만 정규화돼 있다
로케일이 고정돼 있다대소문자 변환 호출을 검색로케일 지정 없이 호출한다
  • ❌ 검증을 「추가」하는 것으로 끝내는 것. 어느 값을 검증했는지가 본질이다
  • ❌ 층마다 방어적으로 한 번 더 다듬는 것. 층마다 다른 값이 생기고 판정이 위치의 함수가 된다
  • ❌ 디코딩을 여러 곳에서 하는 것. 몇 번 디코딩되는지 아무도 모르게 되고 정상 값이 오류로 죽기도 한다
  • ❌ 경로 문자열의 철자로 포함 여부를 판정하는 것. 정상 경로까지 함께 거절된다
  • ❌ 정규화를 「어차피 나중에 하니까」라며 미루는 것. 그 사이에 낀 검증이 통째로 무효가 된다
  • ❌ 유일성은 원문으로 검사하고 저장은 정규형으로 하는 것. 키가 조용히 겹치고 오류는 나지 않는다
  • ❌ 길이 제한을 정규화 앞에 두는 것. 정규화가 길이를 바꾸므로 제한이 최종 값에 적용되지 않는다
  • ❌ 「우리는 프레임워크가 알아서 해 준다」고 넘기는 것. 프레임워크가 어느 지점에서 무엇을 하는지 확인하지 않으면 그것도 층 하나일 뿐이다

마무리: 무엇을 검증했는가

입력 검증에 대한 조언은 보통 「검증하라」에서 끝난다. 그런데 이 글에서 본 실패들은 전부 검증이 이미 있는 코드에서 나왔다. 검사기는 정확했고, 규칙은 촘촘했고, 분기도 빠짐없었다. 그런데도 최종 값은 그 규칙을 통과한 적이 없었다.

그러니 물어야 할 질문은 「검증했는가」가 아니라 「무엇을 검증했는가」다. 그리고 이 질문의 답은 코드의 순서가 결정한다. 검증한 값과 실제로 쓰는 값이 다르면, 검증은 있으나 마나가 아니라 처음부터 없었던 것과 같다.

실행으로 확인한 것을 한 줄로 줄이면 이렇다. 정규화를 먼저, 검증을 나중, 그리고 그 사이에 아무것도 끼우지 않는다. 정규화 단계 대부분은 멱등이라 앞으로 옮겨도 잃는 것이 없고, 멱등하지 않은 단계는 경계에서 정확히 한 번만 실행한다. 그러면 검사기가 본 값이 곧 프로그램이 쓰는 값이 되고, 그 뒤로는 어떤 일도 검증을 무효로 만들지 못한다.

# 정규화 먼저, 검증 나중 — 순서 점검용 복붙 카드

> 출처: braindetox.kr — 검증하고 나서 값을 바꾸면 검증이 무효가 된다
> 근거: Windows 10 / Node.js 22.16.0 / Python 3.13.3 실행 검증

## 0. 한 줄 규칙

정규화 → 검증 → 사용. 그리고 **검증과 사용 사이에 아무것도 끼우지 않는다.**

검증기가 본 값과 실제로 쓰는 값이 같아야 한다. 이 등식이 깨지면 검증은 처음부터 없었던 것과 같다.

```
atCheck === atUse
```

## 1. 순서가 뒤바뀌었는지 보는 법

아래 중 하나라도 해당하면 순서 결함이다.

- [ ] 검사를 통과한 뒤에 그 변수에 다시 대입하는 줄이 있다
- [ ] 검사를 통과한 뒤에 그 변수로부터 **새 변수**를 만들고, 그 새 변수를 쓴다
- [ ] 검사기에 넘긴 인자와 최종 소비 지점에 넘긴 인자가 문자열로 같지 않다
- [ ] 디코딩·정규화·트림·소문자화·경로 결합 중 하나가 검사 뒤에 있다
- [ ] 층마다 자기 판단으로 값을 다듬는다 (게이트웨이·서비스·저장소)

## 2. 잘못된 순서와 올바른 순서

### 잘못됨 — 검사 뒤에 값을 바꾼다

```js
function handle(req) {
  let name = req.query.name;
  if (!isAllowed(name)) return reject();   // 검사한 값: 인코딩된 원문
  name = decodeURIComponent(name);         // 값이 바뀐다
  return open(name);                       // 쓰는 값: 디코딩된 결과
}
```

### 잘못됨 — 검사 뒤에 파생 변수를 만든다 (리뷰가 놓치는 형태)

```js
function handle(req) {
  const label = req.body.label;
  if (!isAllowed(label)) return reject();  // label 은 그대로다
  const key = label.trim().toLowerCase();  // 검사기가 본 적 없는 값
  return store(key);
}
```

### 올바름 — 경계에서 한 번 정규화하고, 그 값을 검증하고, 그 값을 쓴다

```js
function normalize(s) {
  let out = String(s == null ? '' : s);
  try { out = decodeURIComponent(out); } catch (e) { /* 원문 유지 */ }
  return out.normalize('NFKC').trim().toLowerCase();
}

function handle(req) {
  const name = normalize(req.query.name);  // 정규화
  if (!isAllowed(name)) return reject();   // 검증
  return open(name);                       // 사용 — 같은 변수, 재가공 없음
}
```

## 3. 정규화 단계별 성질

| 단계 | 멱등인가 | 여러 층에서 돌려도 되나 | 배치 |
| --- | --- | --- | --- |
| trim | 예 | 예 | 경계 |
| toLowerCase | 예 | 예 (로케일 고정 필요) | 경계 |
| NFKC | 예 | 예 | 경계 |
| 퍼센트 디코딩 | **아니오** | **아니오** | 경계에서 정확히 1회 |
| 경로 결합·정리 | 예 | 예 | 검증 직전 |

멱등하지 않은 단계는 **정확히 한 번만** 실행되어야 하고, 그 위치를 문서에 적어 두어야 한다.

## 4. 층별 배치 원칙

- 경계는 하나다. 요청이 들어오는 첫 지점에서만 정규화한다
- 경계 아래의 모든 층은 값을 **최종형으로 간주**하고 손대지 않는다
- 층마다 정규화하면 층마다 값이 달라지고, 층마다 검사 결과도 달라진다
- 캐시 키·로그 키·저장 키는 모두 **경계에서 나온 그 값**으로 만든다

## 5. 점검 목록

- [ ] 정규화 함수가 존재하고, 이름이 하나로 정해져 있다
- [ ] 정규화 함수는 두 번 돌려도 결과가 같다 (디코딩 제외)
- [ ] 디코딩은 경계에서 한 번만 일어난다
- [ ] 검증 함수는 정규화된 값을 인자로 받는다
- [ ] 검증과 사용 사이에 대입·가공이 없다
- [ ] 검증한 변수와 사용한 변수가 **같은 변수**다
- [ ] 경로는 결합·정리 후에 포함 여부를 판정한다 (철자로 판정하지 않는다)
- [ ] 유일성 검사와 저장 키가 같은 값을 쓴다
- [ ] 로케일 의존 변환은 로케일을 명시했다
- [ ] 테스트에 「검증기가 받은 값 == 소비 지점이 받은 값」 단언이 있다

## 6. 진단 절차

1. 소비 지점(파일 열기·질의·외부 호출)을 먼저 찾는다
2. 거기 들어가는 변수를 위로 거슬러 올라간다
3. 그 경로에 검증 호출이 있는지 본다
4. 있으면 **검증 호출과 소비 지점 사이의 모든 줄**을 읽는다
5. 그 사이에 값을 바꾸는 줄이 하나라도 있으면 결함이다
6. 확신이 안 서면 런타임 트립와이어를 붙인다 — 검증기가 받은 문자열을 기록하고, 소비 지점에서 같은지 비교한다

## 7. 하지 말 것

- ❌ 검증을 「추가」하는 것으로 끝내는 것 — 어느 값을 검증했는지가 본질이다
- ❌ 층마다 방어적으로 한 번 더 다듬는 것 — 층마다 다른 값이 생긴다
- ❌ 디코딩을 여러 곳에서 하는 것 — 몇 번 디코딩되는지 아무도 모르게 된다
- ❌ 경로 문자열의 철자로 포함 여부를 판정하는 것 — 정상 경로도 함께 거절된다
- ❌ 정규화를 「나중에 어차피 하니까」라며 미루는 것 — 그 사이의 검증이 무효가 된다
- ❌ 유일성은 원문으로 검사하고 저장은 정규화형으로 하는 것 — 키가 조용히 겹친다
