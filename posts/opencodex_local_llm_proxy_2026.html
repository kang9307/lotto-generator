opencodex — Codex에서 아무 LLM이나 쓰는 로컬 프록시

OpenAI Codex CLI를 특정 모델에 묶이지 않고 로컬·타사 LLM으로 연결하는 프록시 — 벤더락인 회피, 비용절감, 프라이버시 실용 분석

2026-06-22 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: Codex를 자유롭게 쓰고 싶다면

OpenAI Codex CLI는 터미널에서 동작하는 AI 코딩 에이전트로, 2026년 기준 Terminal-Bench 2.1 리더보드 1위(83.4%)를 기록한 강력한 도구다. 문제는 단 하나다. OpenAI 모델에만 묶인다. ChatGPT Plus($20/월) 또는 Pro($200/월) 구독 없이는 쓸 수 없고, Claude나 Gemini, DeepSeek, Ollama 같은 로컬·오픈소스 모델은 Codex와 연결할 방법이 없다.

이 문제를 해결하는 도구가 opencodex다. GeekNews에 46점으로 올라온 이 프로젝트는 한 문장으로 설명된다. "OpenAI Codex에서 아무 LLM이나 쓸 수 있게 해 주는 로컬 프록시." 이 글은 opencodex가 어떻게 동작하는지, 왜 이 방식이 기술적으로 유효한지, 그리고 어떤 개발자에게 진짜 쓸모가 있는지를 본인 관점에서 분석한다. 단순한 기능 소개가 아니라, LLM 프록시 생태계 전체에서 이 도구가 갖는 의미를 짚는다. 2026년 6월 기준 정보다.

1. 왜 이 문제가 생겼나 — Responses API라는 벽

opencodex를 이해하려면 먼저 OpenAI가 왜 이런 상황을 만들었는지 파악해야 한다.

1.1 Responses API의 등장

OpenAI는 2025년 초 Responses API를 도입했다. 기존 Chat Completions API는 단순한 메시지 왕복을 처리했다면, Responses API는 멀티턴 대화, 도구 호출(tool_calls), 추론 토큰(reasoning tokens), 이미지 처리를 더 정교하게 다루는 인터페이스다. Codex CLI는 이 Responses API 위에서 동작하도록 설계됐다. 에이전트 루프에서 도구를 호출하고, 추론 과정을 토큰으로 다루고, 스트리밍으로 결과를 받는 작업이 Responses API에 최적화돼 있기 때문이다.

1.2 타사 공급자는 Responses API를 모른다

문제는 Anthropic(Claude), Google(Gemini), Ollama 등 대부분의 타사 LLM 공급자가 Responses API를 지원하지 않는다는 것이다. 각자의 네이티브 API 형식이 있다. Anthropic은 Messages API, Google은 Gemini API, 로컬 모델은 Chat Completions 호환 엔드포인트를 쓴다. 결국 Codex는 "Responses API 말고는 말을 못 하는 클라이언트"고, 타사 공급자는 "Responses API를 이해 못 하는 서버"다. 이 프로토콜 간극이 opencodex가 메워야 할 공백이다.

1.3 커뮤니티가 보낸 신호

openai/codex 리포지토리의 Issue #26 "Support for local / other LLMs"는 이 요구가 얼마나 강했는지를 보여준다. 벤더락인이 싫고, 비용이 부담되고, 코드베이스를 외부 API로 내보내기 꺼려지는 개발자들이 처음부터 이 기능을 원했다. opencodex는 OpenAI가 공식 지원하지 않는 이 요구를 커뮤니티가 직접 해결한 결과다.

2. opencodex의 작동 원리 — 프로토콜 번역기

opencodex는 구조적으로 단순하다. 로컬에서 띄우는 번역 프록시다.

2.1 흐름 도식

Codex CLI / App / SDK
        │  (Responses API 요청)
        ▼
   opencodex (로컬 프록시)
        │  (프로토콜 번역)
        ▼
   대상 LLM 공급자
   (Claude / Gemini / DeepSeek / Ollama 등)

Codex가 보내는 Responses API 요청은 opencodex를 거쳐 각 공급자가 이해하는 프로토콜로 변환된다. 응답도 역방향으로 번역돼 Codex에 돌아온다. Codex 입장에서는 자신이 항상 OpenAI Responses API와 대화하는 것처럼 보인다. 실제로는 다른 모델과 얘기하고 있을 뿐이다.

2.2 5가지 프로토콜 어댑터

opencodex는 5개의 어댑터를 제공한다.

어댑터 이름대상커버 범위
anthropicClaude Messages APIClaude 3.5/3.7 등 Anthropic 전 모델
googleGemini APIGemini 2.0/2.5 등 Google 모델
azure-openaiAzure OpenAIAzure에 배포된 OpenAI 모델
openai-responsesOpenAI Responses 직접OpenAI 공식 엔드포인트 통과
openai-chatChat Completions 호환 엔드포인트DeepSeek / GLM / Kimi / Qwen / Groq / OpenRouter / Ollama 등 40개 이상

여기서 openai-chat 어댑터가 가장 파급력이 크다. Chat Completions API를 흉내 내는 공급자라면 무엇이든 opencodex를 통해 Codex에 연결된다. OpenRouter 같은 집계 게이트웨이를 쓰면 사실상 수백 개의 모델을 Codex에 붙일 수 있다.

2.3 스트리밍·도구 호출·추론 토큰 양방향 지원

프록시가 단순히 텍스트만 옮기는 것이 아니라, Codex 에이전트가 실제로 쓰는 기능들을 양방향으로 번역해야 한다. opencodex는 스트리밍(streaming), 도구 호출(tool calls), 추론 토큰(reasoning tokens), 이미지를 모두 양방향 번역한다고 밝히고 있다. 이는 단순한 텍스트 릴레이가 아니라 프로토콜 수준의 번역이 이뤄진다는 뜻이다. Codex 에이전트가 파일을 편집하거나 터미널 명령을 실행하기 위해 도구를 호출할 때 그 도구 호출 구조가 대상 모델에게도 올바르게 전달돼야 한다.

3. 설치와 사용 — 세 줄이면 된다

opencodex의 진입 장벽은 낮다. Bun 1.1 이상을 사전 설치해야 하고, 이후 세 명령으로 끝난다.

npm install -g @bitkyc08/opencodex   # 또는 bun install -g @bitkyc08/opencodex
ocx init    # 대화형 설정: 공급자·모델·API 키 선택
ocx start   # 로컬 프록시 시작 (백그라운드 서비스로 실행)

ocx init은 대화형으로 공급자와 모델, API 키를 설정하고 Codex CLI에 자동으로 주입한다. Codex CLI, TUI, App, SDK 모두에 자동 주입된다. 별도의 Codex 설정 파일 수동 편집 없이 프록시를 활성화할 수 있다. ocx start로 시작하면 백그라운드 서비스로 동작한다. 실시간 웹 대시보드도 제공해 요청 흐름을 시각화할 수 있다. MIT 라이선스 오픈소스다.

4. 벤더락인 회피 — 왜 중요한가

기술적 작동 원리를 넘어서, 이 도구가 왜 지금 등장하는지가 더 중요한 질문이다.

4.1 Codex CLI의 구조적 종속

Codex CLI는 Apache 2.0 오픈소스지만, 실행하려면 OpenAI 구독이 필요하다. 도구 자체는 열려 있어도, 그 도구를 돌리는 연료(모델 API)는 잠겨 있다. 이것이 현대 AI 도구 생태계의 전형적인 락인 패턴이다. 무료로 공개한 도구가 상용 서비스의 수요를 끌어당기는 구조다. 개발자 입장에서 이 종속은 세 가지 실질 문제를 만든다. 첫째, 비용이다. Pro 구독($200/월)은 헤비 유저에게도 부담이다. 둘째, 코드 프라이버시다. 코드베이스가 OpenAI 서버를 통과한다. 셋째, 모델 선택권 부재다. 특정 작업에 더 나은 모델이 있어도 쓸 수 없다.

4.2 opencodex가 뚫는 벽

opencodex는 이 세 문제를 동시에 건드린다. 비용 측면에서 DeepSeek V3나 Qwen 같은 저렴한 OpenAI 호환 공급자로 전환하면 같은 Codex 인터페이스를 훨씬 낮은 단가로 쓸 수 있다. Ollama로 로컬 모델을 연결하면 추론 비용이 하드웨어로 귀속되고 토큰당 한계 비용이 0에 수렴한다. 프라이버시 측면에서 로컬 모델(Ollama 등)을 연결하면 코드가 외부로 나가지 않는다. 모델 자유 측면에서는 특정 언어나 도메인에 강한 모델을 골라 쓸 수 있다.

4.3 공급자 비종속 설계의 실용성

본인이 보기에 opencodex의 진짜 가치는 특정 모델보다 잘 동작한다는 주장이 아니라, 공급자를 설정 변경으로 교체할 수 있다는 설계다. 오늘은 DeepSeek으로 시작하고, 내일 더 나은 모델이 나오면 ocx init으로 공급자만 바꾸면 된다. Codex 사용법, 워크플로, 스크립트를 바꿀 필요가 없다. 이것은 코드 레벨에서 LLM 추상화 계층을 구현한 LiteLLM의 철학과 같다. 도구 레이어에도 같은 원칙을 적용한 것이 opencodex다.

5. LiteLLM과의 비교 — 계층이 다른 도구

비슷해 보이지만 LiteLLM과 opencodex는 해결하는 문제의 계층이 다르다.

5.1 LiteLLM의 역할

LiteLLM(v1.83.8, MIT)은 100개 이상의 공급자를 OpenAI Chat Completions 형식으로 통일해 주는 Python SDK이자 게이트웨이 프록시다. 내가 만드는 애플리케이션이 LiteLLM을 통하면, 코드 변경 없이 공급자를 교체할 수 있다. 이건 내 코드가 LLM을 호출할 때의 추상화다. 2026년 3월 공급망 보안 인시던트가 있었으나 팀이 전면 공개 대응했고, 여전히 가장 널리 쓰이는 오픈소스 LLM 게이트웨이다.

5.2 opencodex의 역할

opencodex는 내 코드가 아니라 Codex라는 기존 도구가 LLM을 호출할 때의 추상화다. Codex가 Responses API를 쓰는 클라이언트라면, opencodex는 그 클라이언트가 보내는 요청을 중간에서 가로채 번역한다. 나는 Codex 코드를 고칠 수 없지만, 프록시를 통해 그 동작을 바꿀 수 있다.

5.3 조합 시나리오

둘을 조합할 수 있다. opencodex의 openai-chat 어댑터 엔드포인트를 LiteLLM 프록시 서버 주소로 지정하면, opencodex → LiteLLM → 100개 이상의 공급자라는 연쇄가 가능하다. 즉 Codex에서 LiteLLM이 지원하는 모든 모델을 쓸 수 있다. 이 조합이 실용적인지는 본인 인프라 상황에 달려 있지만, 계층 분리가 유연성을 만든다는 원칙은 명확하다.

6. 유사 프로젝트와 생태계

opencodex가 혼자 이 문제를 해결하는 것은 아니다. 2026년 기준 유사한 접근이 여러 형태로 존재한다.

6.1 codex-relay

Rust로 작성된 경량 프록시로, Responses API를 Chat Completions API로 번역하는 데 특화돼 있다. opencodex보다 기능이 좁지만 Rust의 성능 이점이 있다. OpenAI 호환 엔드포인트가 목표라면 더 가볍다.

6.2 codex-glm-proxy

GLM-5.2(Zhipu)에 특화된 단일 목적 프록시다. Responses API와 Chat API 사이를 번역한다. 특정 모델 하나만 연결하면 되는 경우에 복잡도가 낮다.

6.3 OpenCode (대안 선택지)

프록시가 아닌 다른 길도 있다. 168,000 GitHub 스타를 돌파한 OpenCode는 Codex CLI 자체를 대체하는 오픈소스 대안으로, 75개 이상의 공급자를 네이티브로 지원한다. "Codex 인터페이스에 집착할 필요가 없다"는 팀이라면 도구 자체를 바꾸는 것이 더 깔끔한 선택이다. opencodex는 "Codex 생태계를 유지하면서 모델만 바꾸고 싶다"는 팀을 위한 도구다.

7. 주의점과 한계 — 솔직하게

도구를 평가할 때 장점만 나열하는 것은 부정직하다. 명확한 주의점이 있다.

7.1 이용 약관 리스크

opencodex 저자가 직접 경고한 내용이다. "일부 공급자 — 특히 Anthropic(Claude) — 는 제3자 프록시를 통해 API 트래픽을 라우팅하는 계정을 정지하거나 제한할 수 있다. Use at your own risk(자기 책임하에 사용하라)." 각 공급자의 이용 약관을 반드시 확인해야 한다. Anthropic의 Claude를 opencodex로 연결할 경우 계정 위험이 있다는 것을 인지해야 한다.

7.2 모델 호환성 격차

프로토콜 번역이 항상 완벽하지는 않다. Codex가 Responses API의 특정 기능(추론 토큰 구조, 특정 도구 호출 형식)을 사용할 때, 대상 모델이 동등한 개념을 지원하지 않으면 번역이 불완전하거나 기능이 무시될 수 있다. 예를 들어 추론 토큰을 지원하지 않는 모델에게 추론 토큰 요청을 번역하면 해당 기능은 사실상 손실된다. 각 어댑터의 번역 완성도는 공급자와 모델에 따라 다르다.

7.3 로컬 API 키 통과

opencodex는 로컬 프로세스로 API 키를 처리한다. 신뢰할 수 있는 자체 환경에서는 문제가 없지만, 공유 서버나 다중 사용자 환경에서는 키 노출 위험을 점검해야 한다.

7.4 유지보수 미지수

커뮤니티 프로젝트의 숙명이다. opencodex는 개인 개발자가 주도하는 프로젝트로, OpenAI가 Responses API를 변경하거나 Codex 프로토콜을 업데이트하면 opencodex의 어댑터도 업데이트가 필요하다. 공식 지원이 없으므로 이 시간 간격이 얼마나 될지는 관리자의 활동성에 달려 있다.

8. 어떤 개발자에게 맞는가

opencodex가 모든 개발자에게 필요한 도구는 아니다. 맞는 사람과 맞지 않는 사람을 정직하게 구분한다.

8.1 잘 맞는 경우

첫째, Codex CLI 워크플로를 이미 쓰고 있고 모델만 바꾸고 싶은 팀이다. Codex의 에이전트 루프, 단축키, TUI에 익숙한 팀이라면 도구를 갈아엎지 않고 모델만 교체할 수 있다. 둘째, 코드 프라이버시가 요구되는 환경이다. Ollama로 로컬 모델을 연결하면 코드가 외부로 나가지 않는다. 사내 코드베이스, 고객 코드, 규제 산업 프로젝트에 해당한다. 셋째, 비용 최적화가 목표인 헤비 유저다. OpenAI Pro $200/월 대신 저렴한 OpenAI 호환 공급자를 연결하면 같은 인터페이스를 더 낮은 단가에 쓸 수 있다.

8.2 맞지 않는 경우

첫째, Codex가 아닌 다른 에이전트 도구를 쓰는 팀이다. Claude Code, Cline, OpenCode를 쓴다면 opencodex는 직접 관련이 없다. 둘째, Anthropic Claude를 연결하고 싶은데 약관 위험을 피하고 싶은 경우다. 저자의 경고를 무시하고 Claude에 연결하는 것은 권장하지 않는다. 셋째, Codex보다 더 유연한 에이전트 도구를 원하는 경우다. 처음부터 다중 공급자를 네이티브 지원하는 OpenCode가 장기적으로 더 깔끔한 선택일 수 있다.

9. 결론 — 프로토콜 추상화가 자유를 만든다

opencodex는 화려한 도구가 아니다. 하지만 그 단순함이 핵심이다. Codex가 Responses API만 말한다는 사실, 그리고 타사 공급자가 다른 언어를 쓴다는 사실 사이에 정확히 번역기를 끼워 넣었다. 이 아이디어 자체는 새롭지 않다. LiteLLM이 코드 레이어에서 한 일을 도구 레이어에서 반복한 것이다. 새로운 것은 실행이다. 세 줄 설치, 5가지 어댑터, 대시보드, MIT 라이선스.

2026년 6월 기준 AI 코딩 도구 시장의 핵심 긴장 중 하나는 오픈소스 도구와 상용 모델 종속의 모순이다. Codex CLI는 Apache 2.0이지만 사실상 OpenAI 구독 없이는 무의미하다. opencodex는 이 긴장을 한 단계 완화한다. 완전히 해소하지는 못한다 — 약관 리스크, 번역 완성도 한계, 유지보수 미지수가 남는다. 그러나 커뮤니티가 "우리가 쓰는 도구의 자유를 우리가 챙기겠다"는 입장을 취할 때 만들어지는 결과물의 좋은 예다.

오늘 당장 쓸 수 있는 행동 두 가지다. 첫째, Codex CLI에 이미 투자돼 있고 비용·프라이버시 문제가 있다면 opencodex로 DeepSeek나 Ollama 연결을 실험해 보라. 단, 연결하려는 공급자의 이용 약관을 먼저 확인하라. 둘째, 처음부터 다중 공급자를 고려한다면 OpenCode를 함께 검토하라. 도구 선택이 모델 선택보다 먼저다.
