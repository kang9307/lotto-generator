The trigger - the GPU that "one GPU" refers to

Upstage announced Solar Mini 4 on October 1, 2026, and on October 4 GeekNews introduced it under a title that translates as "Upstage announces Solar Mini 4, which runs on a single GPU". The phrase "one GPU" in the title calls to mind a graphics card in a local PC, but the sentence the announcement actually wrote is "on-premises, a quantized model can be deployed starting from a single H100 80GB".

That difference decides the judgment. Whether a model can run on a consumer GPU or can be built into a service on one data-center-class GPU changes who the audience is. This model's announcement belongs to the latter, and it does not mention weight release or a license.

Three questions are addressed.

  • How far can the expression "one GPU" be taken in terms of specification numbers
  • Until exactly when, and where, does the 70% launch discount apply
  • Where should vendor-published benchmarks be placed when they are read

Among the price sentences, the discount deadline matches what has been widely summarized. The statement that the launch discount runs until October 10 UTC is there as is, but the fact that the sentence is limited to Upstage Console is the part that tends to drop out of summaries. Titles and summary phrases usually shorten exactly this kind of qualifier.

Specs the announcement states - 35B total, 3B active, 512K context

The announcement introduces Solar Mini 4 as "a model Upstage pretrained on its own and optimized for agent tasks". Gathering the values it gives as specifications yields the following.

Whether weights are open and what the license is are not mentioned in the announcement, so they are left as "—" in the table. That on-premises deployment is among the access paths does not mean the weights can be obtained; it is a statement that Upstage supports deployment, and its terms are not in the announcement.

The announcement introduces the model's purpose as handling, with little compute and cost, repeated work of looking up information, producing results in a set format and calling tools, and the line at the head of the page is "Make repeated agent work lighter" in translation. The later price and use-case sections should be read against this introduction.

"Independently pre-trained" is the wording in the announcement's first sentence. The body of the announcement shows no explanation of training data or training method, so actually measured accuracy and cost, rather than the model's origin, serve as the basis for judgment.

What total 35B and active 3B each determine - memory and compute

The announcement states the structure this way (in translation): "It is an MoE model made up of 35B parameters in total, but only 3B are activated when each token is processed." On memory it says: "A small number of active parameters does not mean the memory needed for deployment shrinks by the same ratio. Computation per token activates 3B, but deploying the model requires loading all 35B weights into memory." These two sentences let us read Solar Mini 4's "one GPU" and its "repeated-work cost" separately.

  • Total 35B - the announcement: deploying the model requires loading all 35B weights into memory
  • Active 3B - the announcement: the part activated when each token is processed, which it says reduces per-token computation and provides high throughput and cost efficiency
  • The ratio of the two is about 8.6% (3/35, calculated)

The weights-only size follows from multiplying by the precision. The table below holds values not in the announcement; it is 35B multiplied by bytes per parameter at each precision. A real deployment adds a KV cache and runtime overhead on top of the weights, so these values are lower bounds.

Storage precision (assumed)Bytes per parameterWeights-only sizeAgainst an H100 80GB
16-bit2About 70GBOnly about 10GB remains
8-bit1About 35GBAbout 45GB remains
4-bit0.5About 17.5GBAbout 62.5GB remains

The table does not say which precision is actually used. The announcement too writes only "on the basis of a quantized model" and gives no precision, so the table is read only as arithmetic for comparison with 80GB.

Dissecting the sentence "from one H100 80GB"

The deployment sentence in the announcement is short, but four conditions are attached to it. Each narrows or defines what "one GPU" means.

  1. "On-premises" - the statement is limited to on-premises deployment.
  2. "On the basis of a quantized model" - the precision (8-bit or 4-bit) is not given.
  3. "H100 80GB" - the GPU model and memory capacity the announcement gives as the minimum deployment configuration.
  4. "From one" - a minimum configuration. The performance figure came from a different configuration (two GPUs), not this one.

The last condition matters especially. The announcement's speed figure is a value measured on a two-H100 configuration and is not a measurement of the same configuration as the statement that deployment is possible from one. Throughput and latency for a one-GPU configuration are not in the announcement. Nor are memory requirements by context length stated, so whether "one" is enough for long-context service cannot be known from the announcement alone.

In summary, to apply the expression "one GPU" to your own situation, three things have to be asked of the provider. Which quantization precision, at which context length that configuration is valid, and what latency comes out at how many concurrent requests. Only with these three values can one tell whether one GPU is a test-environment configuration or a service configuration.

Speed of 70 tok/s or more - measurement conditions and how to read them

The announcement states the speed as "in actual internal measurement, even when processing 32 concurrent requests on two H100s, a generation speed of 70 tokens/s or more per request was maintained". The measurement conditions are written as follows.

  • Hardware: two H100 GPUs
  • Concurrent requests: 32
  • Input of 4K tokens, output of 1K tokens
  • Prefix caching off
  • Continuous load of 600 seconds or more
  • Measured by: Upstage's internal measurement

Converting the numbers gives the following. All are calculations and not values in the announcement.

  • If 70 tok/s per request holds across 32 simultaneous requests, aggregate generation throughput is at least 2,240 tok/s (32 x 70).
  • Generating 1K output tokens (assumed to be 1,000 tokens) at 70 tok/s takes about 14 seconds (generation time only, excluding time to first token).
  • The announcement's footnote says this measurement applied a continuous load of 600 seconds or more without prefix caching, and that the throughput measurement used two H100s, a configuration separate from the minimum deployment specification.

The figure tells us a lower bound on per-request generation speed under limited conditions. What it does not tell us is the time to first token (TTFT), the speed when input is far longer than 4K, the drop when concurrency exceeds 32, and the value on a one-H100 configuration. These are items to measure directly against your own service's input length and concurrency.

Converting these numbers into service capacity is also possible. Looking at generation time alone, one request takes about 14.3 seconds (1,000/70) and 32 concurrent requests hold, so about 2.2 requests per second finish (32/14.3). Per hour that is about 8,000 requests (calculated). This is an upper-bound approximation that leaves out input processing time and first-token latency, and real throughput should be assumed lower.

Pricing and the launch discount - deadline and scope

The announcement's price sentence reads, in translation: "The API list price is $0.10 per million input tokens, $0.01 for cached input and $0.40 for output. On Upstage Console, a 70% discounted price applies through October 10 UTC, and the regular price takes over from October 11." Dividing what the sentence settles from what it does not gives the following.

ItemList price (announcement)With 70% discount (calculated)
Input, per million tokens$0.10$0.03
Cached input, per million tokens$0.01$0.003
Output, per million tokens$0.40$0.12
  • Settled: a 70% rate, the deadline "through October 10 UTC", October 11 as the switch to regular price, and Upstage Console as where it applies
  • Not settled: whether the discount covers all three items (input, cached input, output); the sentence says only "70% discounted price", so the discounted prices in the table follow from that assumption
  • Not settled: up to what hour of October 10 (UTC). "Through" and "from October 11" connect, so it can be read as the end of the 10th, but no time is given
  • In Korean time, which is nine hours ahead of UTC, the end of the UTC day on the 10th falls at around 9 a.m. on the 11th (calculated; the definition of the hour is not in the announcement)
  • Scope: since the sentence is limited to "on Upstage Console", prices and discounts on other channels such as OpenRouter and Solar Chat cannot be known from the announcement alone

The discount is a launch promotion, so it is safer to base a cost plan on the list price and treat the discount as headroom for the trial period. Using a unit-price table built on the discounted prices unchanged after the switch to regular prices makes costs balloon by about 3.3 times (1/0.3, calculated).

Scaling up, if requests of the same shape (4K input, 1K output) number one million a month, that is about $800 a month at list price and about $240 assuming the 70% discount (calculated). These values cover model call costs only and exclude retries, extra calls in verification stages and infrastructure costs.

Converting to the cost of a single request

Turning unit prices into per-request figures makes comparison easier. The example is a request shaped like the speed measurement: 4,000 input tokens and 1,000 output tokens (calculated; the input token count is approximate).

ScenarioOne request (list)1,000 requests (list)1,000 requests (70% discount assumed)
4K input all uncached + 1K output$0.0008$0.80$0.24
4K input all cached + 1K output$0.00044$0.44$0.132
512K uncached input in one request (input only)$0.0512——

Two points can be read from the table. First, in a request of this shape input and output carry equal weight at $0.0004 each (4,000 x $0.10 / million = 1,000 x $0.40 / million). The longer the input, the more the input price dominates, and the longer the output, the more the output price dominates. Second, cached input is one tenth of the input price, so for workloads that repeat the same long system prompt the input cost falls sharply. The announcement does not say under what conditions the cache is hit, so the actual hit rate should be measured directly.

The announcement's "initial internal test" comparison belongs to the same context. Three Korean-language tasks (including code analysis and review and schedule coordination across several tools) were each run three times per model, and both models passed the quality checkpoints of all three tasks. The completion cost of 1,000 sets of the three tasks, at list price, is $1.25 for Solar Mini 4 and $2.20 for MiMo-V2.5, about 43% lower (1.25/2.20 calculates to about 43.2% lower). According to the footnote the condition is temperature=0, cost was converted as if prompt caching were not applied for either model, and latency was excluded from the comparison because MiMo V2.5 went through an external router. For the scheduling task alone (looking up events on a calendar and messaging attendees), the cost of 1,000 runs is $0.36 against $0.61. The announcement adds that results may differ with the real operating environment and task difficulty.

Reading the benchmarks - the nature of vendor-published values

The evaluation values the announcement presents are collected in one table, with a note on what each scale measures. All the scores are values Upstage published.

The reading order is as follows.

  1. The overall index of 24.1 is read together with its comparison targets. The announcement says it is 9.1 points higher than Gemma 4 31B, whose active parameters are 31B (about one tenth of the active parameters), 1.1 points higher than Nemotron 3 Ultra, whose active parameters are 55B, and 0.9 points lower than MiMo-V2.5 (Solar Mini 4's active parameters are about one fifth of MiMo-V2.5's).
  2. The statement "the highest among active-3B models" carries the qualifier "whose scores were confirmed in this evaluation". Which models within the active-3B category were compared is not listed in the body.
  3. The index is an outside body's scale, but whether this score was evaluated and posted by the outside body, or measured by the vendor using the index's method, cannot be told from the announcement alone.
  4. The announcement explains AutomationBench-AA's 22.3% as a measure of work in which information lookup, structuring, state checking and follow-up execution continue across several steps. Other models' scores on this benchmark are not presented alongside it.
  5. The announcement says the model does not use reasoning by default and that the reasoning level is adjusted with reasoning_effort, but it does not say which setting applied when the evaluation scores were produced.

In practice, this table is used not as grounds for a choice but as a starting point for narrowing candidates. Measuring accuracy and cost directly on dozens to hundreds of representative samples of your own task (information extraction, document validation and so on) carries more information than reconfirming the same numbers.

When designing your own evaluation, put accuracy, cost per request and failure types in one table rather than accuracy alone. If failure types are tallied as format violations (broken JSON), omissions, wrong values and tool-call errors, candidates with the same score but different post-processing costs can be told apart. The announcement lists structured output and parallel tool calling as supported features but does not state the failure rate of those features.

Recommended uses and the limits the announcement states

The use cases the announcement lists are three.

  • Information extraction and structuring
  • Repetitive work connected to internal systems
  • Validation stages of document pipelines

The announcement describes the three use cases as follows. Information extraction and structuring means pulling key items out of a contract, classifying customer inquiries, or converting text into JSON and tables. Repeated work connected to internal systems means looking up approval status, judging whether processing is allowed under internal rules, and organizing the result. The verification step of a document pipeline means cross-checking results obtained with Document Parse and Information Extract, checking for missing fields, or deciding follow-up processing under set rules.

On limits, the announcement left a sentence of its own. In translation: "For work that affects real decisions, we recommend not using the model's output as the final judgment and putting a separate verification procedure in place." In the same paragraph the announcement also asks readers to evaluate accuracy and failure types on real data before applying the model to an operating environment.

  • Even for a validation-stage use, the model's verdict is not left as the final decision
  • Information extraction results are paired with sampling review or rule-based verification
  • For repetitive work that uses tool calls, a failure and retry policy is set first

Finally, looking again at the announcement's AutomationBench-AA 22.3%, this measure is described as evaluating work spanning several steps, so it is a different scale from single-call accuracy. This is also why the self-evaluation recommended in the previous section should be designed with accuracy, per-request cost and failure types in one table, and the announcement's safety wording asks for that evaluation.

The order for evaluating adoption

  1. First see whether the task belongs to the announcement's uses (information extraction and structuring, repetitive work, validation stages).
  2. Choose the access path. Whether it is an API (Upstage Console, OpenRouter) or on-premises changes cost, security and operational responsibility.
  3. If on-premises, know that one H100 80GB is the floor, and measure memory and throughput directly at the context length and concurrency you will use. The announcement's speed figure is from a two-GPU configuration.
  4. If using the API, check the current value on the price page. Build the unit-price table on the list price and use the discount only as headroom for the trial period.
  5. Measure accuracy on representative samples. The announcement's benchmarks are vendor-published values, so use them only for shortlisting.
  6. Check whether the prompt structure (a fixed system prompt followed by variable input) can take advantage of the cached-input price.
  7. Attach a separate verification procedure to any path where the output affects decisions.
  8. Recalculate the expected monthly cost at the regular price after the discount ends.

What matters in this order is the order itself. The cost calculation (step 4) and the accuracy measurement (step 5) are independent of each other, but it is a common mistake to decide on adoption after passing only one of them. The trade-off between a cheap model that errs and an accurate but expensive one shows up only when both values sit in the same table.

  • Whether the discount applies to all three items (input, cached input, output), and up to what hour of October 10 UTC.
  • Prices on other channels such as OpenRouter and Solar Chat. A search result summary showed the OpenRouter listing at a price lower than list (around $0.05 input and $0.20 output), but it could not be confirmed directly on that page.

Artificial Analysis's original table and version were not opened.
