TypeScript 7 正式リリース - Go ネイティブコンパイラが変えるものと変えられないもの

RCから3週間、移行・互換性・esbuildとの関係を実務目線で検討する

2026年7月9日 開発・インフラ

序論: コンパイラの置き換えが「正式」になる瞬間

2026年7月8日、MicrosoftはTypeScript 7の正式リリース(GA)を発表した。6月18日にRCが出てから約3週間後だ。本人はRC段階ですでにこの書き換えの構造と技術的背景を分析したことがある。今回の焦点は異なる。RCは「予告編」で、GAはその予告がどこまでそのまま確定したのか、そして実際にプロジェクトへ適用する際に何に注意すべきかを示す「確定版」だ。

本稿は2026年7月時点の公式発表と出版直後の報道を根拠に、三つの問いに答える。なぜコンパイラ全体をGoに移す必要があったのか、その結果開発者が実際に得るものは何か、そして何より今すぐ移行すべきかどうかだ。最後の問いが最も実務的でありながら、最も省略されがちだと考える。

1. tscはなぜ限界にぶつかったのか

コンパイラ全体を別言語に移した理由を「速い言語が好きだから」と読むと本質を見失う。問題はアルゴリズムではなく実行モデルだった。

1.1 二つの構造的な壁

従来のtscはTypeScript自身(実質JavaScript)で書かれ、JavaScriptエンジン上で動いていた。これは二つの天井を作る。一つ目、ネイティブコードでない以上、JITを経ても実行オーバーヘッドを完全には消せない。二つ目、事実上シングルスレッドのモデルで、マルチコアが当たり前になった今でも大規模プロジェクトの型検査を並列に分割する手立てがなかった。コードベースが数十万行を超えると型チェックに数十秒かかり、エディタの自動補完・エラー表示が入力に追いつかなくなる現象は、まさにこの天井の症状だった。

1.2 なぜRustではなくGoなのか

興味深いのはGoを選んだ理由だ。性能だけ見ればRustも候補だっただろう。しかし公開された説明によれば、既存のコンパイラのコードベースは共有可変状態やポインタの多いグラフ走査構造に大きく依存している。こうした構造を所有権モデルの厳格なRustに移すには設計をかなり書き直す必要があるが、GC方式のGoなら既存のロジックとデータ構造をほぼそのまま維持した方法論的ポート(methodical port)が可能だった。新規に書く代わりに移す方を選んだ理由は明確だ。数十年分のテストスイートで「新実装が旧実装と同じ答えを出すか」を検証できてこそ、信頼こそが命であるコンパイラを安全に置き換えられるからだ。

2. 開発者が実際に得るもの - ビルドとエディタ

公式に示された事例は二つある。VS Codeのコードベース(約150万行)はビルド時間が約78秒から約7.5秒へ、Sentryは約133秒から約16秒へ短縮したと報告された。おおよそ8~10倍の範囲だ。この速度向上は二つの要因の合計だ。ネイティブコンパイルによる約3~4倍、そして従来は不可能だった並列処理による約3~4倍。副次的に、Goのインライン構造体がJavaScriptの割り当て中心のオブジェクトよりメモリを使わないため、大規模プロジェクトでのメモリ使用量が半分程度に減ったとされる。

本人がより大きく評価する体感ポイントはビルド時間よりエディタの反応性だ。言語サーバが遅いと、「入力中に赤い波線が遅れて出る」程度ではなく、自動補完自体が遅延し、開発者がツールを信用できず回避するようになる。ネイティブ言語サーバがこの遅延を根本的に減らすなら、体感の生産性はCI時間短縮よりはるかに即座に感じられる。ただしこれらの数値はベンチマークプロジェクト基準であり、自分のコードベースでの実際の効果は構成やハードウェアによって変わりうる点は明記しておく。

3. 移行の本当の落とし穴 - Compiler APIの空白

ここが今回のGAで最も実務的に重要な部分だと判断する。tscの型検査結果自体は6.0と最大限同一に保つのが目標だが、プログラマティックなCompiler APIは7.0のネイティブコンパイラにまだ存在しない。7.1で提供予定という点がGAでも改めて確認された。

3.1 何が壊れるのか

影響は「コードをコンパイルし型を検査する」一般的な用途ではなく、ts.createProgramやts.transpileModuleのようなAPIを直接呼び出してASTを操作するツールに集中していると報告される。例えばAST基盤のコード生成・リファクタリングツール、宣言ファイル(.d.ts)をプログラマティックに生成するバンドラープラグイン、tscをネイティブバイナリにそのままエイリアスしたテストランナー設定などが候補として挙げられる。一方、エディタ拡張が使うLanguage Service Plugin APIは7.0にもそのまま残っており、大半のIDE自動補完・Lintプラグインはこの空白と無関係に動作し続けると見られる。

3.2 セーフティネット - 旧バージョンの並行運用

この空白を埋めるため、旧APIをそのまま公開する互換パッケージが併せて提供される。新しいtscは高速なネイティブコンパイラを指し、別の実行ファイルで従来のJavaScriptベースのコンパイラとAPIをそのまま使えるようにする方式だ。つまりビルド・型検査は新コンパイラに移しつつ、APIに依存するツールだけ旧実行ファイルに残す二重運用が公式に推奨される過渡期の戦略だ。

3.3 予告されていた破壊的変更

API空白とは別に、TypeScript 7はstrictのデフォルト有効化、target: es5の廃止(最低ES2015)、moduleのAMD・UMD・SystemJS形式の廃止、moduleResolution: node10の廃止といった整理も併せて確定した。これらはRC段階から予告され、TypeScript 6.0で事前に警告が出るよう設計されているため、6.0に真面目に上げておけば大半は予測可能な種類だ。

4. esbuild・swcとの関係 - 競合ではなく役割の再整理

自然に出てくる疑問がある。「すでにesbuildやswcでビルドが速いのに、なぜTypeScript 7が必要なのか」。この問いには一つの前提が隠れている。esbuildとswcはそもそも型を検査しない。型注釈を取り除いて通過させるだけのトランスパイラだから速いのだ。だからこそ実務では、この二つで変換だけ高速に行い、肝心の遅い型検査は別途(エディタで、あるいはCIでのみ、時にはまったく省略して)行う二重構成が広く普及した。

TypeScript 7はこの二重構成の必要性そのものを減らす。型検査を担うtsc本体が速くなれば、「ビルドは速く、検査は後で」と分ける理由が弱まる。とはいえesbuild・swcが押し出されるわけではない。両者はバンドリング・ミニファイ・JSX変換まで担うが、これはtscがそもそも担ったことのない役割だ。本人の解釈はこうだ。TypeScript 7は「型検査が遅いから仕方なく迂回していた」ワークフローを見直させるが、バンドラーとしてのesbuild・swcはそのまま残る。競合というより、それぞれの領域が改めて明確になる方向に近い。

5. 実務導入の時期判断

結局、最も重要な問いに戻る。今移行すべきか、待つべきか。本人はワークロード別に判断することを勧める。

5.1 今すぐ移行してよい場合

tscとエディタ中心にしか使っておらず、ts-morph系のAST操作ツールやtsup --dtsのようなAPI依存のビルド段階がないチームなら、今移行してもリスクは低いと判断する。特にCI時間や大規模モノレポの型チェックがボトルネックだったチームには、体感効果がすぐ現れる可能性が高い。

5.2 待った方がよい場合

社内コード生成器、カスタムトランスフォーマー、スキーマ・型ベースのコード生成ツールを運用中なら、急がない方が安全だ。Compiler APIが7.1でどのような形で出るか確認してから移行しても遅くない。その間はビルド・型検査だけ新コンパイラに移し、API依存ツールは並行提供される旧実行ファイルに残す二重運用が現実的な折衷案だ。

5.3 共通のチェックリスト

どちらにしても最初のステップは同じだ。まずTypeScript 6.0に上げて非推奨警告をすべて確認し、その後新旧コンパイラをCIで並走させ出力差分がないか検証してから切り替える順序だ。ベンダーが強調する速度数値より、自分のコードベースの実際の差分とツールチェーンの互換性確認の方がはるかに信頼できる根拠だ。

結論: ネイティブ化は始まりであって完成ではない

TypeScript 7のGAは、「JavaScriptエコシステムのツールが自分の言語を離れてネイティブへ移行する」というより大きな流れの一場面だ。Vite・esbuild・SWC・Rspackといったツールはすでにこの流れの上にあり、TypeScriptはその中で最も長く持ちこたえた部類が隊列に加わった事例に近い。ただし今回のGAが示すのは速度だけではない。速度を得る代わりに、プログラマティックAPIという拡張性の一部を一時的に手放したという事実も同時に露わになった。この均衡を理解し自分のツールチェーンを点検してから移行するチームと、速度数値だけを見てとりあえずアップグレードするチームの結果は違うはずだ。
