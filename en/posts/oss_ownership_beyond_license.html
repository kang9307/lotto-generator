The Code Is Open, the Name Is Not - Trademarks, Domains and Release Access an Open Source License Never Grants

A license sets the terms for using the code. Who the project belongs to is decided outside the license

2026-09-12 Dev & Infra

Every open source project keeps a license file at the top of its repository. Read that one file and a set of questions is answered: whether this code may be copied, whether it may be modified, whether the modified version may be shipped onward, and what has to travel alongside it when it is. Yet there is one question that file never answers, no matter how carefully it is read. Who does this project belong to?

One distinction carries the whole discussion. A license is a document that sets the terms for using a copyrighted work. It is not a document that settles who owns the project as an organisation, or the assets attached to it. That is not an abstract claim invented for the sake of argument; several foundations have already written it into their published policies as a single sentence. The Linux Foundation trademark usage guidelines put it this way: A copyright license, even an open source copyright license, does not include an implied right or license to use a trademark that may be related to the project developing the licensed software.

Which is why a fork is only ever half a move. The code can be taken in its entirety, and the name cannot. Neither can the domain, nor the address people download from, nor the channel that pushed updates to installed copies. No amount of careful license reading produces that list, because the list is not the sort of thing a license governs.

The sources relied on below are two license texts, the Open Source Definition, four published trademark policies, and the name retention policy of the Python Package Index. Quotations stay inside what those documents actually say. The projects used as examples were chosen because they publish policy documents, and no party to an ongoing dispute is assessed here, nor the rights and wrongs of any such dispute. Adjudicating a particular matter is not the work being done here; documents are quoted only as far as seeing the structure requires.

The trigger - where the ownership question comes from

The prompt for this piece was a public post asking, about one widely used open source project, who the project belongs to. Run down the items that post lists and one thing stands out. Ownership of the code was never the contested part. Everything raised as contested sits outside the code: which legal entity holds the trademark, who operates the infrastructure behind the official site, who opens and closes the channel through which extensions reach users, and who appoints the board.

That matter itself has processes still running, and parts of it are still to be decided. Standing in for those decisions is not the work being done here. Exactly one thing is carried across: the shape of the question.

The shape looks like this. The license has already answered. Anyone may copy, modify and redistribute the code. And yet, once that answer is given, roughly six boxes are still blank. None of them appear anywhere in a license file, and each is held down by a different body of law, a different contract, or a different account.

What matters is that this shape is not peculiar to one project. A project with a foundation behind it, a project where one company writes most of the commits, and a project one person maintains at weekends all have the same six boxes. The only difference is which names are written in them, and whether those names appear in a public document at all.

What a license actually decides

What a license does is narrow and clear. A party holding the exclusive rights of copyright declares that some portion of those rights is granted to others under stated conditions. The grant is defined across roughly four areas.

  • Copying — may copies be made? Every open source license answers yes here.
  • Modification — may the work be changed, and may the changed version be shipped onward?
  • Distribution — may the original or the modified version be handed to someone else, and what must accompany it?
  • Conditions — keep the notices, ship the notice file, provide source to the recipient under copyleft, and whether a patent grant travels with it.

That is the whole territory. The ten items of the Open Source Definition contain no clause about trademarks, governance or an owning party either. That document deals only with rights of distribution and use.

There is one sentence about names, sitting at the end of item 4, and its direction is worth noticing. The license may require derived works to carry a different name or version number from the original software. This is not a clause that hands over a name. It is a clause that permits a license to demand a different name on derivative work. Even the Open Source Definition anticipates that the name is the part which does not travel.

How license texts cut trademarks away

Saying that licenses do not deal with trademarks is imprecise. A number of them deal with trademarks explicitly, by excluding them. It is exclusion, not silence.

Section 6 of the Apache License 2.0 is headed Trademarks outright. This License does not grant permission to use the trade names, trademarks, service marks, or product names of the Licensor, except as required for reasonable and customary use in describing the origin of the Work and reproducing the content of the NOTICE file. Two exceptions survive: customary use in describing where the work came from, and reproducing the contents of the notice file as they stand.

Section 2.3 of MPL 2.0 lands on the same spot. This License does not grant any rights in the trademarks, service marks, or logos of any Contributor. Here too the exception is confined to what compliance with the notice requirements demands.

What repays attention is that a duty to preserve notices and a permission to use a mark are not the same thing. Section 4 of the Apache License 2.0 requires that copyright, patent, trademark and attribution notices be retained in the source form on redistribution, and that the contents of a notice file, where one exists, be included. That is an obligation to keep something, not a permission to use it. Read the two sentences as one and the direction flips entirely.

Some short permissive licenses carry no trademark clause at all. The absence of a clause is not a grant. A trademark arises from a different legal basis than copyright, so a copyright license's silence leaves that right untouched. The Linux Foundation policy pushes the same reasoning one paragraph further: open source licenses permit unrestricted modification of the copyrighted software and the foundation has no intention of interfering with that right, but a right to use any specific trademark is not determined by the fact that the software arrived under an open source license.

The six slots a license leaves empty

Gather the boxes that remain outside the license and there are six. The important part is that each is held down by a completely different basis.

  • Trademark and name — decided by trademark law and by whatever trademark policy the holder has published. An entirely different area of law from the code.
  • Domain and official website — decided by the registrar agreement and the name on the registration. When the agreement ends, the slot ends with it.
  • Package registry account and distribution channel — decided by that registry's terms, its name retention and transfer policy, and the list of account owners.
  • Repository admin rights — decided by the hosting organisation's settings. Merge rights, tag creation, release asset uploads and pipeline secrets all hang off this.
  • Foundation and corporate structure — decided by articles of incorporation and board rules. Which assets the entity owns and who appoints directors is the content of this box.
  • Community infrastructure — forums, issue trackers, documentation sites, translation platforms, mailing lists. Usually tied to whoever pays.

The six share one property. Each is anchored in a single account or a single legal entity, and none of them copy the way code copies. A repository produces a duplicate in seconds; a domain produces no duplicate at all. A registry has exactly one slot under a given name. Which is why, the moment these boxes come into question, each becomes an exclusive choice immediately.

Trademarks - fork the code, and the name stays behind

Of the six boxes, the trademark is the one most often misread, because the free movement of the code invites the assumption that the name moves with it. The published trademark policies say the reverse.

The Apache Software Foundation policy opens like this. The Apache Software Foundation (ASF) owns all ASF-related trademarks, service marks, and graphic logos on behalf of our project communities, and the names of all ASF projects are trademarks of the ASF. The project name is itself declared to be the foundation's mark, and the stated basis for holding it is on behalf of the community.

The Python Software Foundation records that it holds the registered language name, the logos and several event names. It then compresses the principle into one line. All trademarks, even those that apply to open source software, must be used according to certain legal requirements. The policy does not merely prohibit, either: it sets out, with examples, the product-name forms that are allowed when they refer to use with or suitability for the language. Using the name in a company name carries a separate requirement of prior written permission.

The WordPress Foundation policy records that the foundation owns and oversees the trademarks for the names and logos, that a separate event mark is held by a subsidiary entity of the foundation, and that anyone seeking commercial use should contact the party holding an exclusive commercial license. What this arrangement demonstrates is that holding a mark and holding the right to exploit it commercially can rest with different parties.

The Linux Foundation policy differs from the other three in that it states the principle first: a copyright license, even an open source one, includes no implied right to use a related trademark. Its prohibition on registration is explicit as well. Do not attempt to register any of the foundation's trademarks as a trademark, trade name, domain name or doing-business-as name.

The four documents differ in arrangement but fill the same box. All four also give domains a paragraph of their own. The reason sits in the next section.

Domains - the slot that owns the default path

A domain matters not because of search rankings but because it is the default path. The first line of the install instructions, the links throughout the documentation, the address an update check reaches for, the location a trust store points at — all of them converge on one domain. When an official site also serves as the download page, the documentation and the extension directory, that single domain is doing three jobs at once.

A domain is not owned; it is registered. It persists on the strength of an agreement with a registrar, it is anchored to the registrant's name, and that name lives inside a single account. It does not divide the way code divides. Whoever holds this seat decides which software leaves from that address, and where existing installations keep polling it, that relationship lasts a very long time.

This is why the trademark policies treat domains separately. Put a name into a domain and it becomes simultaneously a use of the name and an occupation of the path. Two distinct things overlap in one string, and policies generally resolve that by not letting them overlap.

The name slot in a package registry

The path users actually receive software along is often the registry rather than the repository. A single line with a name sits in a configuration file, and every build resolves it. So the slot under that name in the registry is what the distribution path actually is.

That slot is anchored to an account. A name carries a list of owners; only owners publish new versions; only owners hand access on. And how the registry behaves when a name becomes contested is written down in a public policy.

The Python Package Index name retention policy is the clearest example. It separates active projects from abandoned ones first. Only in the abandoned case, and only when every listed condition is satisfied, does a name transfer. For active projects it draws a line in a single sentence. The maintainers of the Package Index are not arbiters in disputes around active projects.

The path of decision is tiered as well. The index maintainers come first, the packaging workgroup after them, and that workgroup has the final say in the disputes the document covers. Trademarks reappear here too: the same document treats a project using a third party's trademark beyond nominal or fair use under its intellectual property infringement section, and provides a separate reporting address.

The conclusion is plain. A registry name is not settled by technology; it is settled by procedure. And the bar for that procedure is generally high. Creating a new slot under a new name is often faster than working the process, which is why real forks almost always take a new name. The cost of that is that every configuration file spelling out the old name knows nothing about the new slot. How a deleted name and the references left pointing at it come apart was covered layer by layer in Why deleted package names keep getting requests.

Repository admin rights and release signing

A repository copies. The rights arranged around a repository do not. The list attached to it runs like this.

  • Merge rights — decide which changes enter the mainline. A fork inherits the history but not the future merge point.
  • Tags and releases — the place version numbers are attached and artefacts are uploaded. Downstream automation polls exactly this.
  • Pipeline secrets — registry publish tokens, signing keys, deployment credentials. They live in settings, not in repository contents.
  • The security reporting channel — the route private reports arrive on, and the list of people who can read them.
  • The organisation owner account — the seat above all of the above, able to undo any of it. Usually the smallest group of all.

Among these, the release signing key behaves differently from the rest. The others can simply be moved, but with a signing key the trust of every verifier is bound to that key. Distribution packagers, internal mirrors and lockfile verification settings all know it. Signing with a new key means planting a new anchor in every one of those places, and that work is nothing like copying a repository in scale.

What follows and what stays behind when the hosting itself moves was set out item by item in Keeping code hosting portable. A situation where ownership splits is closer to the case where that same list arrives as a condition rather than a choice.

Three different structures behind one word

The existence of a foundation is not itself an answer. Put the public documents side by side and it is immediately visible that the same word points at different arrangements.

  • Held on behalf of the community — the foundation owns all the marks, with the stated basis resting on the project communities. The Apache Software Foundation policy uses exactly that phrasing.
  • Holding split from commercial exploitation — the foundation owns the mark, while commercial use runs through a party holding a separate exclusive license. Some event marks are held by a subsidiary entity instead.
  • A separate legal vehicle per project — individual projects sit under an umbrella as a series of an LLC. OpenTofu, which began as a fork of Terraform, is run in that form according to its own documentation.

So the questions that come before the existence of a foundation are three. Which assets does the entity hold? Who appoints the board? What contract connects the entity to the main commercial party? Published policy documents usually answer only the first. The second and third live in articles or separate rules, and frequently are not published at all.

An unpublished answer is not in itself a defect. What remains, though, is that there is no basis for judgement. At the point where a dependency is being decided, that distinction makes a practical difference.

Community infrastructure - forums, issues, docs

The last box is the easiest to overlook. Forum archives, the historical record in an issue tracker, documentation sites, translation platforms, mailing lists, chat spaces. None of these is a trademark or the object of a contract, yet they are where a project's memory is stored.

What holds these seats is mostly money. Whoever pays the hosting fees and holds the admin account decides how long the records live and who may reach them. And the moment they move, most of the links break. Broken links quietly disappear from search results, and the discussion that explained why a decision was made disappears with them.

The practical impact is larger than it looks, because old issue numbers are embedded in commit messages and code comments. When the thing a number pointed at is gone, the reference left in the code no longer means anything.

The lower half of that table is the real cost of a fork. Copying the code costs effectively nothing; the entire bill arrives from the lower half. And those items do not yield to money on demand. Most of them need time.

What has to follow for a fork to hold ground

A fork succeeding technically and a fork holding ground in an ecosystem are different problems. Holding ground requires several things besides code to come along.

  • Maintainers who carry context — not commit access, but people who know why the code looks the way it does. This asset moves, but it does not duplicate.
  • A distribution path — a new registry name, container image tags, download addresses. It only counts when it reaches users without them doing anything.
  • Downstream packagers — distribution maintainers and internal mirror operators. Their adoption of the new name is what reaches the majority automatically. This is the most underrated seat in open source.
  • A compatible route — do existing configuration files still parse, does the extension interface hold, is there a migration document? Where this friction is high, users do not move.
  • Someone to pay — infrastructure bills, trademark registration, a minimum of legal review. Without this in year one, the next split repeats the same sequence.
  • Evidence of stability — releases and security patches on a stated cadence. Trust is built by the record, not the promise.

Essentially none of the six has anything to do with code. The difficulty of a fork is not the difficulty of the code but the difficulty of the ecosystem. The separate axis of who keeps a thing running was treated on its own in Who keeps the infrastructure running. Ownership and maintenance overlap, but they are not the same question.

What to settle before anyone else arrives

Seen from the other side, the same list becomes a set of design decisions. And these are decisions where later is worse. The moment one becomes necessary is usually the moment interests have already diverged, and by then the same sentence stops producing agreement.

DecisionOptionsWhy it gets harder later
Who holds the name and logoAn individual, a company, a separate entityOnce value attaches to the name, the transfer itself becomes a negotiation
How contributor agreement worksContributor license agreement, certificate of origin, neitherApplying it retroactively requires consent from every past contributor
How release access is spreadOne person, a small group, split key custodyIf one person disappears without handover, releases stop
Whose name holds the domain and registry accountsA personal account, a shared account, an entity accountA personal account loses its access alongside the person
Whether a governance document existsNone, a short set of principles, a full written procedureRules written after a dispute begins read as rules for that dispute
How far commercial use is allowedFully permitted, conditional, a separate licenseAttaching conditions after people already rely on it is hard
The stance toward forksSilence, a rename requirement, permitted friendly attributionLeave it unwritten and the general rules of trademark law answer instead

The cheapest rows in that table are the first and the fifth. Settling who holds the name on the day the name is chosen costs essentially nothing, and a governance document at the start can fit on one page. An agreement that was never written down does not survive a change of people.

Changing the license itself is a separate axis, and the asymmetry with copies already shipped makes it its own calculation. That calculation is set out in What changing a license actually changes.

The other side - concentration is not always the wrong shape

Assets gathered in one place is not, on its own, a bad structure. The arrangement in which one party holds the mark has a purpose that the public documents themselves record. The WordPress Foundation policy puts the rationale this way: in projects where the code and all of the traditional intellectual property are open, the thing everyone can rely on as a marker of quality and trust is where the trademark is allowed to be used.

Seen from the user's side that reasoning is practical. If a name can attach to anything, the name guarantees nothing. A trademark policy is what makes it possible to tell an official build from something else.

Dispersal has its own bill. Widening release access reduces the risk of releases stopping, but increases the number of doors open onto the supply chain. Spreading signing keys means one location can vanish, at the price of more places to manage. Tightening governance procedure reduces arbitrary decisions and slows decisions down with it.

So the question to ask is not concentration versus dispersal. It is how much of it is written down, and what the procedure for changing that document is. With those two present, any arrangement is predictable; without them, no arrangement is.

Five sentences

Reduced to five sentences, it comes out like this.

  • A license governs use of the code and does not settle ownership of the project. Several license texts exclude trademarks explicitly, and the Open Source Definition carries no clause on ownership or governance either.
  • Six boxes remain, each anchored to a different basis. Trademark law, the registration agreement, the registry's own policy, account settings, the legal entity, and whoever pays for the community infrastructure.
  • A fork takes every copyrighted work and none of the things anchored in accounts and registrations. The name, the domain, the registry slot, the signing key, the links to the record, and user habit are what stay behind.
  • Before depending on something, five documents come after the license. Trademark policy, governance document, the list of people who can release, the entity holding the assets, and the alternative for the day it has to end.
  • For the people building it, the cheapest moment is the day the name is chosen. Anything not settled that day never gets cheaper on any later day.

Carried into practice, one sentence survives. If a dependency inventory has only a license column, it is one column short. Adding a single column beside it for whether a trademark policy and a governance document exist is the cheapest measure described here.

What could not be confirmed

The items below were not settled from primary sources within this scope. Until the basis is there, nothing is asserted about them.

  • The facts and merits of any ongoing matter — the matter behind the post that prompted this piece has processes still running. The truth of each assertion and where responsibility lies is not the sort of thing a published policy document can settle, and it is not the subject here. Only the shape of the question was carried across.
  • The former name of the Terraform fork — several places state that OpenTofu used a different name early on and changed it, but no sentence recording that sequence was found in the project's own published documents. Only the current name and the operating form appear in the text above.
  • The individual trademark policy text for Linux Foundation projects — the project documentation points at a policy collection address, but that document itself was not opened this time. The Linux Foundation material quoted above is limited to the one trademark usage policy.
  • How other language ecosystems handle name disputes — how the JavaScript, Rust and Java registries treat contested names on active projects was not included in this scope. The procedural description above is the policy of one index.
  • The relationship between contributor agreements and trademark ownership — whether contributor license agreements ever cover trademarks in addition to copyright was not established from primary documents. The two are treated above only as separate items.
  • Application under Korean law — domestic trademark registration status for open source project names, and domestic dispute procedure, sit outside this scope. The policies quoted above are conditions of use each foundation set for itself, not an interpretation of the law of any particular jurisdiction.
