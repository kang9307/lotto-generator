What the extension is for — bringing external data into PostgreSQL

A common layout has PostgreSQL as the operational database and the analytical raw data piling up as Parquet in S3. There have long been several ways to connect the two worlds: install a foreign data wrapper, run a separate ETL job that downloads CSV and loads it with COPY, or stand up a separate analytics engine altogether. Each pays a different price in installation difficulty, format support and speed.

pg_chdb is ClickHouse's answer for that slot. The core idea is to run chDB, the embedded ClickHouse engine, inside the PostgreSQL process. Reading external files, parsing them and converting formats is what ClickHouse is already good at; the extension only handles the seam through which the result flows into PostgreSQL tables. The repository's one-line description is "PostgreSQL extensions for executing chDB queries and copying data from external sources into PostgreSQL tables".

This article lays out the extension's structure, coverage, installation, performance figures and constraints within what the README states, and ends by judging where it fits against the existing options. The license is Apache-2.0, and as of 15 September 2026 the repository has 16 stars, 84 commits and 4 open issues. It should be said up front that this is an early project, not a mature one.

Two parts — chdb_query() and chdb_hook

The extension consists of two parts. Their roles differ, so they are treated separately.

  • The chdb_query() function. It takes ClickHouse SQL as a string, runs it on the chDB engine and returns the result as a PostgreSQL row set. ClickHouse table functions such as s3() can be used as they are, so an external file becomes a table. The types of the returned columns are declared on the calling side with AS (…).
  • The chdb_hook module. Loaded with LOAD 'chdb_hook', it intercepts COPY … FROM. Write an external URL such as S3 after FROM instead of a local path, and the hook reads the file through chDB and loads it into the table. The existing COPY syntax stays; only the source changes to external.
  • Division of labour. The function when only a query is needed; the hook when the data must be loaded permanently into a table. The extension also offers a path that, given only a file URL, infers the column structure and handles table creation and loading in one step.

The design point worth noting is that the extension invents no new SQL syntax. It sits on two existing PostgreSQL constructs, the function call and COPY. The learning cost is low, and it drops straight into existing toolchains — psql scripts, schedulers.

The breadth of the format list is chDB's achievement, not the extension's; it inherits whatever ClickHouse supports as an input format. Conversely, the README does not cover what is lost when a format on the list is mapped to PostgreSQL types. Where the two engines' type systems diverge — dates, time zones, decimal precision — cannot be known until data is actually loaded.

Installation — PostgreSQL 15, chDB 26.7, Linux and macOS

  • PostgreSQL 15 or higher. 14 and below are not on the supported list.
  • chDB v26.7.0 or greater. Installed first, separately from the extension. The README's method is curl -sL https://lib.chdb.io | bash. Since that pipes a remote script into a shell, on a production server it is better to download the script and read it before running it.
  • Linux and macOS only. Built from source; Windows is not listed.
  • Build order. make, then make installcheck, then make install. Systems that use gmake or a different pg_config path specify it as env PG_CONFIG=/path/to/pg_config make.

The practical catch in the requirements is the chDB dependency. As an embedded engine, it brings a ClickHouse runtime into the PostgreSQL process. Memory footprint and library conflicts are not README items, and they belong on a separate instance before anything goes near production.

Usage — direct queries and COPY loads

The README's first example reads a CSV in S3 directly through the function. The ClickHouse SQL is wrapped in dollar quoting ($$ … $$) and the returned columns are declared.

SELECT * FROM chdb_query($$
                      SELECT * FROM s3('s3://bucket/file.csv')
                    $$) AS (id int, months int, days int);

The second example loads several files at once with COPY after loading the hook. The glob pattern combines two prefixes with the numbers 1 to 3 — six files in one statement.

LOAD 'chdb_hook';
                    COPY times FROM 's3://bucket/{prefix1,prefix2}/file_{1..3}.csv';

The difference between the two examples is the difference in usage. The first is a one-off query that leaves nothing in PostgreSQL; the second loads into a table. With the schema-inference path the table need not exist in advance, but inferred types can differ from what was intended, so for production tables it is safer to load into an explicit schema.

Performance — 2-3x versus pg_duckdb and pg_lake on one million rows

The README compares import time against competing extensions on about one million rows of the NYC Taxi dataset. The results it states are as follows.

ComparedREADME statement
chdb_hook (pg_chdb)The most consistent performance
pg_duckdb and pg_lake2-3x longer for CSV, JSON and Parquet imports
aws_s3Approaches chDB performance but supports a much more limited array of formats

Two things have to be kept alongside these figures. First, the measurer is the project itself. A vendor's own benchmark tells you the direction but does not guarantee the magnitude. Second, conditions such as hardware, network, file size and the versions of the competing extensions are absent from the README. One million rows is small for an analytical workload, and whether the same multiple holds at tens of gigabytes is a separate question.

The direction itself is plausible, though. ClickHouse's input parsers have been optimized for years for bulk reads of column-oriented formats, and embedded execution removes network round trips. "There is a reason it would be fast" and "this multiple will appear in my environment" are different sentences, and the latter has to be measured on your own data.

Constraint — every query runs in complete isolation

The README states one known limitation. Each query runs in complete isolation from all other queries. In the original's words: do not create a table and expect to query it in a subsequent query.

  • No state persists on the chDB side. Temporary tables, settings and views created inside chdb_query() vanish when the call ends. A transformation split into stages has to be merged into the SQL of one call, or the intermediate result written down to a PostgreSQL table and handed to the next stage.
  • State on the PostgreSQL side is normal. The isolation concerns chDB execution. A table loaded with COPY naturally remains.
  • Most likely a consequence of the design. Starting each call from a clean engine state means no interference between concurrent calls and simple resource reclamation. It is inconvenient for workloads that need persistent state, but not a large problem while the extension is used as a loading tool.

What the table shows is not a ranking but a difference in grain. The embedded-engine family (pg_chdb, pg_duckdb) hands parsing and conversion to the engine — pg_chdb's 14 formats are the result. A native extension (aws_s3) has light dependencies and focuses on one storage backend. FDWs suit viewing external data as tables without loading. Which is right mostly comes down to two questions: how many formats, and load or query.

Where to use it and where not to

  • A fit — a pipeline that periodically loads external files in several formats into PostgreSQL. Loading a data lake where Parquet, ORC and Avro arrive mixed, with a single COPY statement, is what this extension is for.
  • A fit — a team without the capacity to operate a separate analytics engine. ClickHouse's parsers inside PostgreSQL, without a separate ClickHouse cluster.
  • Not a fit — a workload that wants to chain multi-stage transformations inside chDB. Query isolation leaves no intermediate state.
  • Not a fit — Windows servers, PostgreSQL 14 and below. Outside the supported list.
  • Not a fit — putting it straight onto a production instance without validation. It is an early project with 16 stars and 84 commits, and the embedded engine's memory and stability are not README items. Measuring on your own data on a separate instance comes first.

What could not be verified

  • The benchmark's hardware, network, file sizes and the versions of the competing extensions. Not in the README.
  • The memory ceiling of the chDB engine inside the PostgreSQL process and its behaviour under concurrent calls.
  • The mapping rules from ClickHouse types to PostgreSQL types and whether anything is lost (time zones, decimals, nested structures).
  • How S3 credentials are passed — the README examples contain no authentication.
  • The current feature scope of pg_duckdb, pg_lake, aws_s3 and FDWs. Outside the README's comparison.
  • The project's maintenance plans and release cadence.
