MCPは死んだのか? - Model Context Protocolの限界と2026年AIエージェント統合の未来

挑発的なタイトルの裏にある均衡の取れた真実 - 熱狂から1年、約束は守られたか

2026年6月1日 IT・技術

1. 序論: MCP熱狂から1年 - 約束は守られたか

2026年5月31日、news.hada.ioの人気記事に「Is MCP Dead?(MCPは死んだのか)」という挑発的なトピックが上がった。Model Context Protocol、略してMCPは、2024年末にAnthropicが公開して以降、「AIエージェントのUSB-C」というあだ名とともに2025年の一年を丸ごと盛り上げた標準だ。そのMCPに対して「死んだのか」と問う記事が人気欄に上がったこと自体が、1年の間に期待と現実の隔たりが人々の口に上るほど広がったという信号である。

正直に明かして始める。BrainDetoxではこれまでエージェント基盤を扱う際にMCPを何度も好意的に言及してきた。だからこそ今回はより客観的に書きたい。「死んだ」というタイトルは刺激的だが、結論を先に言えばMCPは死んでいない。万能だという幻想が死んだだけだ。本稿はその幻想がどこで崩れ、それでもMCPがどこで今なお輝くのかを均衡よく分解する。

本稿はhada.ioのトピックを出発点としつつ、その要約を写し取ることはしない。私が実際にMCPサーバーを立ててクライアントに接続して使ってみて経験した5つの限界、function callingおよび直接統合との比較、MCPが適する領域と適さない領域、代替案、そして韓国の開発環境での実情まで13章で整理する。結論から言えば、MCPを使うかどうかは「流行だから」ではなく「自分の統合構造に合うか」で判断すべきだ。

2. MCPとは何だったか - AnthropicのModel Context Protocol概要

MCPは、AIモデル(正確にはモデルを包むクライアント)が外部ツール・データソース・システムと接続する方式を標準化するためのオープンプロトコルだ。核心の発想は単純だ。モデルごと、アプリごとにばらばらだったツール接続方式を、一つの共通規約に統一しようというものである。だからよく「AI時代のUSB-C」と例えられる。どんな機器も同じポートに挿さるように、どんなモデルも同じプロトコルでツールに挿さるようにしようという構図だ。

構造はクライアント・サーバーモデルだ。MCPホスト(Claude Desktop、Cursor、VS Codeなど)が内部にMCPクライアントを持ち、このクライアントが外部のMCPサーバーと通信する。サーバーは三つを公開する。モデルが呼び出せるtools(関数)、読み込めるresources(ファイル・DBレコードなどのコンテキスト)、再利用可能なprompts(プロンプトテンプレート)だ。通信はローカルでは標準入出力(stdio)、リモートではHTTP/SSEベースの転送を使う。

例えればMCPサーバーはツールの「アダプター」だ。GitHub、Slack、ローカルファイルシステム、データベースごとにアダプターを一度作っておけば、それに対応するどのクライアントからも同じツールを使える。この「一度作ればどこでも」という約束が2025年のMCP熱狂の核心的な原動力だった。

3. MCPが約束したもの - 標準化されたツール・コンテキスト接続

MCPが登場したとき、私が最も魅力的に見た約束は三つだった。

  • N×M問題の解消 - モデルN個とツールM個をそれぞれ別々に接続するとN×M個の統合が必要になる。MCPはその間に標準の一層を挟みN+Mに減らすと約束した。ツール提供者はMCPサーバー一つ、モデル提供者はMCPクライアント一つ作ればよい。
  • 再利用可能なツール生態系 - 誰かが作ったGitHub MCPサーバーを自分のCursorにも、同僚のClaude Desktopにもそのまま挿せる。ツールがアプリに従属せず生態系の資産になる。
  • コンテキスト供給の標準化 - 単なる関数呼び出しだけでなく、モデルに必要なコンテキスト(ファイル、DB、文書)を一貫した方式で注入する道を開いた。エージェントの「何ができるか」と「何を知っているか」を同じ規約で扱う。

これらの約束は今見ても正しい方向だ。問題は、約束の方向が正しいことと、その約束があらゆる状況でコスト対効果を出すこととはまったく別の話だという点だ。ここから現実の限界が始まる。

4. MCPの5つの実際の限界

私が実際にMCPサーバーを立てて運用しながらぶつかった5つの限界を整理する。これは誰かの要約ではなく実測の経験だ。

4-1) 複雑な設定 - 参入障壁

最初にぶつかる壁だ。ツール一つを使うために別のサーバープロセスを立て、実行コマンド・環境変数・認証トークンをクライアント設定ファイル(JSON)に正確に書かねばならない。function callingなら数行のコードで済むことが、MCPではサーバーのインストール・パス設定・ランタイム依存確認という複数段階を経る。非開発者には事実上参入が不可能で、開発者にも「このツール一つのためにこれを?」という瞬間が来る。

4-2) セキュリティ - 露出面の拡大

MCPはモデルに外部ツールを実行する権限を与える。これは強力な分だけ危険だ。サーバーがローカルファイルシステム・DB・社内APIにアクセスすると、モデルがプロンプトインジェクションに揺さぶられた場合、その権限がそのまま攻撃面になる。信頼できない出所のMCPサーバーをインストールするのは、事実上第三者のコードを自分の権限で実行させることだ。認証情報がサーバー設定に平文で入るパターンも多く、危険を増幅する。

4-3) デバッグ - 追跡の難しさ

呼び出しの流れがホスト → クライアント → サーバー → 外部システムと複数プロセスにまたがるため、何かが間違ったときどこで切れたか追跡するのが難しい。モデルがツールを呼ばないのか、クライアントがサーバーを立てられないのか、サーバーがエラーを出したのにメッセージがモデルに伝わらないのか、区別が容易でない。標準化された可観測性・ロギングがまだ弱く、stdioログを漁る原始的なデバッグに頼りがちだ。

4-4) 標準分裂 - 実装間の不一致

「標準」と言うがクライアントごとに対応範囲が異なる。あるクライアントはresourcesに対応し、あるクライアントはtoolsのみ対応する。転送方式(stdio vs HTTP/SSE)、認証、権限モデルの詳細が実装ごとに分かれる。だから「一度作ればどこでも」が現実には「作ってからクライアントごとに別々にテスト」に変質する。標準の価値は一貫性から生まれるのに、分裂はその価値を直接削る。

4-5) 性能オーバーヘッド

MCPは別プロセス・プロトコルの往復を経るため、同じ関数をモデル内で直接呼ぶより遅延が増える。ツール一覧を取得し、直列化し、プロセス間通信をし、結果を再び直列化して受け取る段階が呼び出しごとに積み重なる。単発の作業では体感が小さいが、エージェントがツールを数十回呼ぶ長いループでは累積オーバーヘッドが無視できなくなる。

5つの限界の共通点は「一層を追加した代償」だ。標準という抽象化の層を挟み込んだ瞬間、設定・セキュリティ・デバッグ・互換・性能のコストが一緒についてくる。これはMCPの欠陥というより、あらゆるミドルウェアが抱える本質的なトレードオフだ。

5. 「死んだ」は誇張か - 実際の採用状況

では本当に死んだのか。私の答えは明確に「いいえ」だ。限界が明らかでもMCPの採用曲線は依然として右肩上がりだ。主要なコーディングエージェントとIDE(Claude Desktop、Cursor、VS Code、その他多数)がMCPを一次統合方式として対応し、公開されたMCPサーバー数は1年の間に急速に増えた。ツール提供企業が「公式MCPサーバー」を出すことが一つの慣行のように定着した。

「死んだ」という表現は二つを混同したところから来る。第一はハイプサイクルの正常化だ。ガートナーのハイプサイクルで見るとMCPは2025年の「過剰な期待の頂点」を過ぎ、2026年の「幻滅の谷」へ下りている最中だ。この区間では「やはり大したことなかった」という声が大きくなる。しかし幻滅の谷は死ではなく成熟への通過儀礼だ。第二は適用範囲の誤解だ。MCPがあらゆる統合を置き換えるという期待が過剰だっただけで、適する領域での採用はしっかり伸びている。

私が見るに、死んだのはMCPではなく「MCP一つでエージェント統合のあらゆる問題が消える」という物語だ。技術は生きていて、死んだのは誇張された期待だ。この区別ができないと、まともに使えるツールを流行が冷めたという理由で投げ捨てる過ちを犯す。

6. MCP vs Function Calling vs 直接統合の比較

MCPを評価するには代替案と並べて見る必要がある。三つのアプローチを比較する。

基準Function CallingMCP直接統合(OpenAPIなど)
設定難易度低い高い中
再利用性アプリ従属高い(複数クライアント)中
ツール生態系なし共有サーバー生態系API別個別
セキュリティ露出面小さい大きい(別権限)中
性能(遅延)最速オーバーヘッドあり中
適する規模単一アプリ複数クライアント既存REST資産

表を一文に要約すると、function callingは単一アプリに最も簡単で、MCPはツールを複数のクライアントが共有するとき輝き、直接統合はすでによく定義されたREST API資産があるとき合理的だ。三者は競合というより異なる層にある。function callingがモデルとツールをつなぐ「神経」なら、MCPはその神経を複数の身体に再利用させる「標準コネクター」だ。

よくある誤解を一つ正す。MCPはfunction callingを置き換えない。むしろMCPサーバーのツールをモデルが呼ぶとき、内部的にはfunction callingの仕組みを使う。両者は敵ではなく層が異なる協力者だ。

7. MCPが輝く領域 vs 適さない領域

私が整理した、MCPを使うべきときと使うべきでないときだ。

7-1) MCPが輝く領域

  • IDE・デスクトップエージェントのローカルツール接続 - CursorでローカルなDBを照会したりファイルシステムを扱うなど、同じツールを複数のクライアントで再利用するとき最も強い。
  • ツール提供者とモデル提供者の分離 - こちらはツールだけよく作り、どのモデルが使うかはユーザーに任せたいとき。SaaSが「公式MCPサーバー」を出すパターンがこれに当たる。
  • 複数のエージェントが共有するツールプール - 組織内の標準ツールセットを一度作りチーム全体のエージェントが使えるようにするとき。

7-2) MCPが適さない領域

  • 単一バックエンド内の単純なツール呼び出し - 一つのアプリでモデルが関数を二、三個呼ぶだけなら、MCPの設定・運用コストは明らかに過剰だ。function callingが正解だ。
  • 超低遅延が核心の作業 - 1ミリ秒が重要なリアルタイム経路ではプロトコル往復のオーバーヘッドが負担だ。
  • セキュリティ境界が極度に敏感な環境 - 外部MCPサーバーの権限拡大が許されない閉域網では導入のハードルが非常に高い。

核心の判断基準は一つだ。「このツールを複数のクライアントが共有するか?」答えがイエスならMCP、ノーならfunction callingだ。

8. 代替と補完 - 次世代エージェント統合標準

MCPだけがあるわけではない。私が見る代替と補完の地形はこうだ。

  • ネイティブfunction calling / ツールAPI - 各モデル提供者が提供する最も基本的で速い統合。単一アプリには依然として最善だ。
  • OpenAPIベースの直接統合 - REST APIがすでによく定義されていれば、モデルに仕様を与えて直接呼ばせる方式が単純だ。
  • フレームワークのツール抽象化 - LangChain、LlamaIndexなどは独自のツール抽象化を提供し、MCPをアダプターとして吸収することもある。
  • エージェント間通信(A2A系)プロトコル - MCPが「エージェント↔ツール」を扱うなら、A2A系は「エージェント↔エージェント」を狙う。両者は競合ではなく異なる層を埋める。

重要な洞察はこれだ。これらの代替はおおむねMCPを殺すのではなく補完する。2026年の現実的な絵は単一の勝者ではなく多層構造だ。アプリ内ではfunction calling、ツール共有層ではMCP、エージェント協働層ではA2A系がそれぞれの場所を占める形だ。

9. 開発者は今MCPを使うべきか - 率直な判断

最も多く受ける質問に率直に答える。「今MCPを学んで導入すべきか?」

私の答えは「用途が合えば今が好機」だ。理由は三つ。第一に主要クライアント対応が安定し、初期より設定がずっと容易になった。第二に公開サーバー生態系が大きくなり、最初から作る必要なく持ってきて使えるツールが多くなった。第三に幻滅の谷の区間で誇張された期待が払拭され、実際の有用性を中心に資料が整理された。

ただし導入の仕方は慎重であるべきだ。私の推奨は段階的アプローチだ。最も価値の高いツールを一つか二つだけ先にMCPで包んで効果を測定せよ。設定コスト対再利用利益が実際に出たかをデータで確認した後に拡張する。最初からすべてのツールをMCPで標準化するというビッグバンのアプローチは、第4章の5つの限界を一度に抱える道だ。

10. 韓国の開発環境におけるMCPの実情

韓国の開発組織にMCPを適用するとき考慮すべき三つがある。

第一に閉域網とセキュリティ審査だ。金融・公共・通信は外部出所コードの持ち込みと外部権限拡大に対する審査が厳格だ。外部MCPサーバーのインストールはセキュリティ審査で止まりやすく、自前で検証した社内MCPサーバーのみ許す形に狭まる。私は韓国の閉域網では「信頼された社内サーバーのみ、権限最小化」を基本原則として勧める。

第二にオンプレミス・国産LLMとの結合だ。HyperCLOVA X、KT Mi:dmのようなオンプレミスモデルを使う環境では、MCPクライアント対応の有無が変数になる。グローバルなクライアントが先に対応する分、国産スタックではMCP採用が一拍遅れて追ってくる傾向がある。導入前にクライアント互換を必ず確認すべきだ。

第三に小規模チームの比重だ。1〜5人の開発チームが多い韓国のスタートアップ・SI現場では、MCPサーバーを立てて維持する余力が乏しい。こうしたチームは単一アプリならfunction callingで十分で、本当にツールを複数箇所で共有せねばならない瞬間にだけMCPに移るのがコスト対効果で合理的だ。

11. リスク - 標準戦争の不確実性

MCPをめぐる最大の不確実性は技術的限界ではなく標準ガバナンスだ。私が懸念する三つを整理する。

  • 主導権の集中リスク - MCPはオープンだが事実上Anthropicが主導する。特定の企業が主導する標準はその企業の戦略によって方向が揺れうる。真の中立ガバナンスへ移れるかが長期生存の鍵だ。
  • 競合標準の登場 - 別の陣営が代替プロトコルを押せば「標準戦争」が起きる。ツール提供者は複数の標準を同時に対応する負担を抱え、標準化本来の利益が薄まる。
  • バージョン断片化 - 第4章で見た実装分裂がバージョン差で悪化すれば、「標準なのに互換しない」最悪の状況が来うる。

これらのリスクはMCPだけの問題ではなく、あらゆる新生標準が通過せねばならない関門だ。私は導入時、特定の標準にコードを深く従属させるより、ツールロジックとプロトコルアダプター層を分離しておくことを勧める。標準が変わってもアダプターだけ差し替えればよいように。

12. 結論 + 今すぐ適用できる3つ

本文の核心を一文に整理する。MCPは死んでいない。死んだのはMCP一つであらゆるエージェント統合が解決するという幻想であり、MCPはツールを複数のクライアントが共有する領域で依然として事実上の標準として生きている。その上で今すぐ適用できる三つを提示する。

  1. 「複数のクライアントが共有するか」で判断せよ。ツールが一つのアプリだけで使われるならfunction calling、複数のエージェント・クライアントが共有するならMCP。流行ではなくこの一つの問いで決める。
  2. 最も価値の高いツールを一つか二つでパイロットせよ。全面標準化の代わりに、再利用利益が最も大きいツールだけ先にMCPで包み、設定コスト対効果を測定して拡張する。
  3. ツールロジックとプロトコルアダプターを分離せよ。標準戦争の不確実性に備え、MCPに深く従属せずアダプター層だけ差し替えられるよう設計する。
