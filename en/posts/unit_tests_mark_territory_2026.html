Unit testing is a widely practiced testing methodology across modern software engineering. On September 18, 2026, programmer Yossi Kreinin, who has extensive experience in hardware engineering, published an essay arguing that unit tests function primarily as territorial markers (marking territory) to prevent code from being arbitrarily altered by colleagues rather than as tools for squashing complex bugs.

This article reviews Kreinin's arguments structurally. By comparing software testing with hardware verification practices, we examine why unit tests show fundamental limits in uncovering complex defects, how unit tests acquired a social role in environments lacking code ownership, how their rise coincided with distributed version control systems (DVCS), and the economic logic prioritizing velocity over quality. We also examine the author's recommended alternative of deterministic randomized testing and the role of tests in codebases edited by AI coding agents.

1. Author Background and Hardware Engineering Perspective

Yossi Kreinin introduces his vantage point as a programmer who has worked extensively in hardware development environments. When evaluated from the viewpoint of physical chip and circuit design, software testing exhibits serious contradictions. As Dan Luu noted in his writings, real-world software remains full of bugs (software is full of bugs).

Kreinin attributes this phenomenon to differences in release pressure between software and hardware. In software, organizations push programmers to ship buggy code because bugs can always be fixed later. As a result, software is constantly full of bugs waiting to be addressed. In physical hardware, by contrast, bugs are often catastrophic (often catastrophic). Flaws on silicon cannot be patched remotely after release, so organizations have no choice but to let engineers take the time needed to fix them.

From this angle, a central question is whether decision-makers are correct in believing bugs are not a critical problem, or whether they are losing more money due to defects than it would cost to prevent them. Kreinin notes that while decision-makers may sometimes be right, when they are wrong, persuading them is unlikely without a visceral, visual argument—such as a pile of chips thrown in the garbage—or statutory regulatory mandates.

2. Two Reasons Unit Tests Fail to Squash Complex Bugs

If an organization does not prioritize bug prevention, it could operate with no automated tests at all. Kreinin notes that prior to the 2010s, codebases completely lacking tests were fairly common. Today, however, unit tests roughly double the size of codebases on average (roughly doubling the size of the code base on average). The author asserts that unit tests do very little to squash non-trivial bugs, citing two primary reasons:

  • Omission of Component Interaction Defects: Many tough bugs and performance issues stem from the way components interact (the way components interact). Finding these requires integration tests that execute multiple components from different teams, yet such tests are very rare. Instead, developers construct abstract classes, mock objects, and per-test API stubs to strictly avoid touching anything outside their unit (outside their unit). This introduces architectural rigidity, as modifying an API requires updating not only call sites but also numerous stubs.
  • Narrowness of Hardcoded Inputs: Finding tricky bugs requires a wide variety of input combinations. However, the unit test approach relies on hardcoding a handful of inputs and their respective outputs (hardcode a handful of inputs and their respective outputs). In hardware, engineers generate random inputs to the design under test, analyzing input distributions and determining external correctness criteria, rather than simply running the code once and hardcoding the resulting output as correct.

3. Shared Ownership Culture and Unit Tests as Territorial Markers

If unit tests are less effective at detecting defects than integration tests or input randomizers, why did they become universally pervasive during the 2010s? Kreinin writes that the main purpose of unit tests is keeping your code from being violently altered by others in an environment where everything changes uncontrollably all the time (keeping your code from being violently shat on).

Because software code can always be edited, a culture evolved where individual code ownership was replaced by the euphemism of shared ownership. In an environment where everyone is told to change everything, developers required a mechanism to prevent colleagues from breaking their work. The author notes that breakage is a social construct: something is only broken if someone is forced to fix it before pushing changes.

The original essay identifies five factors that make unit tests an effective mitigation for this environment:

  • They are very easy to write: Developers can construct them quickly with minimal friction.
  • They are cheap and fast to run: Because they execute rapidly, they can serve as commit gates without substantial pushback.
  • They satisfy the quality checkbox at acceptable cost: They tick the quality box at precisely the cost organizations are willing to spend to feel they are addressing quality.
  • They establish social deterrence: Anyone can modify code as long as tests do not fail. Removing another person's tests or brutally modifying them to pass without talking to the author is viewed as unacceptable conduct, compelling contributors to keep tests passing or consult the author.
  • They receive enthusiastic support from programmers: Not because they find tricky bugs, but because they provide assurance that code will still be there after being committed.

4. Proliferation of DVCS and Explosion of Test Code Size

Kreinin notes that the rise of unit testing coincided with the mainstream adoption of distributed version control systems (DVCS) in the 2010s. The ease of branching and merging across entire codebases enabled many developers to contribute simultaneous changes to shared repositories.

Without CI and unit tests, widespread branching and merging would lead to severe coordination issues. The Linux kernel, an early high-profile user of DVCS, operated for years without unit tests and only recently began adding them. Meanwhile, unit tests, which had been popularized by agile advocates prior to DVCS, exploded in adoption alongside continuous integration and distributed version control.

The author explains that unit tests roughly double codebase size because writing tests resembles writing the code twice: first as production code that anyone can modify under shared ownership, and second as protective tests preventing arbitrary disruption. Because marking territory is proportionate to the territory's size, test code volume naturally expands in tandem with production code.

5. Organizational Trade-Offs Between Software Quality and Velocity

From a hardware engineering perspective, one might ask why software companies do not establish dedicated verification teams to author integration tests and input randomizers. Finding defects systematically could prevent substantial downstream costs.

Kreinin outlines the software organization's response: teams do not want a verification group filing bugs for code already committed, as developers have already moved on. Running integration tests and randomizers requires stable APIs, but freezing interfaces to accommodate testing conflicts with the goal of changing everything continuously. Above all, slowing down delivery velocity is strictly forbidden.

The author summarizes this as the general principle of software quality: quality improvements are perceived as worthwhile if and only if they accelerate the rate at which the program is changed (quality improvements are perceived as worthwhile if and only if they accelerate the rate at which the program is changed). Proposals that improve robustness at the expense of velocity encounter immediate resistance. While hardware prioritizes squashing bugs, software prioritizes the rate of change.

6. Author's Practical Alternative: Module-Level Random Testing

For engineers seeking genuine software reliability, Kreinin recommends module-level randomized testing (randomizers). Rather than running tests continuously on large server clusters, generating tens of thousands of inputs within manageable resources offers meaningful verification benefits.

A critical technical requirement is using deterministic seeds. If random inputs are truly non-deterministic, CI builds fail intermittently, leading developers to re-run pipelines until they pass. This reflects the challenge noted by Uber engineers regarding running ThreadSanitizer (TSan) in CI. Fixing random seeds ensures reproducible test execution within automated pipelines.

The author describes four specific characteristics of module-level randomized testing:

  • Targeting Stable Module Boundaries: Tests should focus on modules spanning several thousand to tens of thousands of lines with stable APIs rather than frequently changing internal functions.
  • Approximating Hardware-Grade Reliability: Writing a randomizer can take one to several weeks, but once built, it can approximate hardware-grade reliability for the code tested.
  • Proactively Finding Rare Bugs: Running the harness continuously for periods of time helps locate rarely reproducing bugs (for engineers seeking proactive bug fixes, though this is rarely incentivized).
  • Feasible for Individual Implementation: While comprehensive integration testing requires organizational backing that is usually absent, an individual engineer can build and benefit from randomized module tests independently.

7. Rise of AI Coding Agents and Minimum Guardrail Functions

Kreinin concludes by examining the intersection of unit testing and AI coding agents. Current coding agents learned primarily from human codebases rather than reinforcement learning for rigorous verification. Consequently, agents replicate human habits, generating simplistic tests that roughly double codebase size.

When asked whether unit tests are better than nothing in codebases primarily edited by agents, the author answers yes. An agent resembles a quick-witted, experienced new hire knowing nothing about your code whom you have just onboarded (a quick-witted, experienced new hire knowing nothing about your code). Where such contributors perform most changes, codebases can quickly lose features and architectural structure.

Because agents are configured to treat test failures with respect, existing unit tests serve as guardrails against destructive changes. While tests cannot prevent agents from adding complex, redundant structures protected by new tests, human programmers have long done the same. Agents simply accelerate the rate at which teams arrive at their destination.

8. Stated Limitations and Realistic Conditions for Persuasion

Kreinin's discussion notes realistic constraints. The author acknowledges that management's decision to deprioritize bug fixes can sometimes be economically justified.

When decision-makers are mistaken, the conditions under which engineers can persuade them remain narrow:

  • Absence of Visual Proof of Loss: Without visceral, visual arguments like a pile of discarded chips, demonstrating software defect costs is difficult.
  • Absence of External Regulatory Mandates: Without legal or regulatory compliance requirements, organizations will rarely slow development velocity.
  • Absence of Incentives for Proactive Fixing: Traditional management structures rarely reward engineers for proactively identifying and fixing latent defects.
