Introduction: a word on screen that is nowhere in the code

You are building a file manager, you open the home folder, and the system tells you the app is trying to access your photo library. There is nothing photo-related in the code. No framework linked, no image processing, and searching the entire source turns up nothing. Yet every time the home folder opens, the same dialog returns. A developer who hit exactly this recently published their trace. To give away the ending, the culprit was a directory named ~/Library/Photos, and the app had done nothing but open a folder.

The interesting part is not the ending. It is how the shape of the question changed. The first question was why is my app trying to look at photos. That question yields nothing. You already confirmed there are no photos in the code, so every additional check pushes you deeper into the fog. The question that produced an answer was a different one. Which code path touched a protected resource? That switch is the whole of this article.

And it is not a macOS story. The same confusion repeats on Android, in browsers, and on Windows. The app name is on screen while the cause lives well below the code that app actually wrote. A prompt is not a cause. It is an effect. To find the cause you do not follow where the effect points; you go underneath it.

One thing up front. This article contains no method for stopping permission dialogs from appearing, and it does not cover disabling or working around privacy protections. It goes the other way. It is about finding out what summoned the dialog once it appeared, and what you can fix afterward. Making a dialog disappear without knowing the cause is not a fix. It is a cover.

1. The prompt is an effect, and something else pulls the trigger

Many developers understand a permission prompt as a screen that appears because the app asked. You call the request function, the dialog shows, the user taps, and the result comes back in a callback. That model is half right. The right half is explicit request APIs. The wrong half is that dialogs genuinely do appear when nothing asked.

From the operating system side, the structure looks different. The privacy subsystem on macOS and iOS, commonly abbreviated TCC, does not exist to take requests from apps and show dialogs. It exists to intercept the moment a process reaches a resource marked as protected. Resources are grouped by service identifier, and photo-related access sits under an identifier named kTCCServicePhotos. In the trace mentioned above, the system log revealed exactly one thing: that identifier.

What matters is that membership in that identifier is defined by a list of resources, not by framework name. Calling the photo framework triggers it, of course. But so does opening a path on the list, with no photo framework anywhere in sight. A file open syscall carries no intent to handle photos. Yet once it crosses into the kernel and reaches that path, the ruling is made on the target, not on the intent.

That is where the gap opens between the sentence on screen and the code on disk. The user reads that the app wants photo library access. What the app did was enumerate directories inside a home folder. Both statements are true and they do not contradict each other. They are the same event described at two different layers.

What actually happenedWhat the user seesCan the app know?
A query call into the photo frameworkPhoto access requestYes. You called it
A file access on a listed protected pathPhoto access requestNo. You opened a file
A query a dependency made at init timeA request under your app nameNo. The call is not in your code
Use of a system-provided pickerUsually nothing at allYes. No permission is taken

Rows two and three are the problem. In both, the app has no idea what it touched. Rereading your own code will not resolve this, because the word really is absent from it.

2. Why why is this app never produces an answer

Why is this app trying to read photos. It is a natural question, but the sentence assumes the app is a single actor with a single intent. The investigation stalls because that assumption does not hold.

Inside a single process, code from many origins runs together. Your code, the language runtime, the UI framework, libraries your package manager pulled in, and the libraries those pulled in. Components the system injects into the process are there too. All of it shares one permission boundary. To the operating system they are indistinguishable. It is one process, and the process carries an app name.

So the app name in a permission dialog identifies which boundary the event occurred inside, not who requested it. Ask why is this app and you are interrogating intent, and intent is not in the code, so the investigation ends on the spot. Ask it this way instead and the investigation continues.

  • Which code path reached that resource? An execution path, not an intent. That is observable.
  • When does that path run? At startup, on a particular screen, or in a background job.
  • What did it target? A framework call or a file path. If a path, which one.
  • Why was that included in the path? Only here do you earn the right to ask about design intent.

Change the question and the method changes with it. The first version tries to answer by searching source, and fails because the word is not there. The second answers from the state of a running process. And there is one decisive fact here. While a permission prompt is on screen, the execution flow that raised it is parked, waiting for the answer. The evidence has not evaporated. It is pinned to the screen.

This property carries over to other kinds of debugging. Whenever you can freeze state at the instant a symptom reproduces, the difficulty of root-causing drops a level. Chasing a duplicate delivery that will not reproduce ends up using the same principle, which I covered separately in a redeploy resent yesterday notifications.

3. Your dependencies ask on your behalf

A library uses a feature you never used. In permission work that sentence is especially annoying, because the origin of the request and the responsibility for it come apart. Android official documentation is explicit about this. It advises reviewing the permissions required by third-party libraries and SDKs, and states that a permission request coming from a library appears to the user as coming from your app rather than from the library. What the user sees is always the app name.

In practice this happens along three routes.

  • General-purpose utilities do not discriminate — folder size calculation, file listing, indexing, backup scanning. These features walk everything by nature. If nobody ever thought to exclude protected paths, protected paths get walked too. The case that opens this article is exactly this type.
  • Linking alone wakes things up — put a framework in your dependencies and related components can be prepared at initialization time, with a query happening alongside. This occurs even when your code never calls it.
  • Out-of-process components get involved — system-provided pickers and share sheets run outside your app. These are usually designed not to require permission, but if you do not know which side you are on, you cannot predict the result.

One emphasis is due here. Concluding that the library is secretly doing something is usually wrong. Code that walks folders was written to walk folders, and it simply did not anticipate a protected path sitting inside its range. In the opening case the offending directory was not even the standard photo library location. Apple documents the default photo library as living in the Pictures folder under home, and the path in question was somewhere else. There was no particular reason for the walker to know about it.

So the conclusion of this section is not suspicion but inventory. Know the full list of permissions your app ends up requiring, and be able to map each entry to the dependency it came from. If there is an entry you cannot map, that is when you start investigating.

4. The order that narrows down the culprit

From here the work is real. The key is not tool usage but order. Follow the order and any tool gets you there. Skip it and no tool saves you.

Step 1 - Pin down reproduction

The first job is building the smallest set of steps that reproduces it. When does it appear? Every launch, only on a specific folder, after some elapsed time? At this stage you remove conditions one at a time and check whether the dialog still comes. The tighter the condition, the easier everything downstream.

Skipping this is the most common mistake. If reproduction is flaky, the moment you need to catch in the next step never arrives, and without catching it all you have is guesswork.

Step 2 - Establish which kind of request it is

Next you determine what the request is for, using what the system records rather than what the dialog says. On macOS, watching the log the privacy subsystem emits tells you which service identifier is being requested. That is exactly the level the trace above reached.

The important thing here is knowing where that record stops. It gives you the service identifier but not the path that pulled the trigger. That is not a defect, it is the design. The log does not exist to help an app developer debug; it exists so the system can record a ruling. A ruling needs a subject and a service, not a path.

Step 3 - Freeze at the boundary

This is the turning point. If the log will not say more, look at the parked execution flow itself. While the prompt is up, the thread that raised it is stuck inside a system call waiting for an answer. Attach a debugger to the process without dismissing the dialog and that moment is preserved intact.

That is precisely what the author of the opening trace did. They kept the dialog up, held the process, found which threads were blocked inside a file-open call, and read the argument that had been handed to it. Sitting in there was the path of the offending directory.

Step 4 - Read the call stack upward

Knowing the path is not the end. Who handed that path over remains. Reading the parked thread's call stack from the bottom upward shows how far your own code sits above the system call. This step gives one of three answers. Your code passed it directly, a utility you called expanded a list that contained it, or your code appears nowhere on the stack.

StepWhat you establishSignal that you are stuck
1. Pin reproductionWhen it appears and the minimal conditionThe same action sometimes triggers it, sometimes not
2. Identify the kindWhich resource the request is forThe record names a service and stops
3. Freeze at the boundaryWhich call is blocked and on what targetYou attached after dismissing, so no evidence
4. Walk the stackHow far up the caller is still your codeNone of your code is on the stack at all

The last column is the signal. Attaching in step three after the dialog is gone is already too late. If step four shows none of your code, the cause lives in another component inside the process, and the investigation moves from your source to your dependency list.

5. What a call stack tells you and what it cannot

A stack is powerful but not universal. You need to know how far it can be trusted so you do not draw the wrong conclusion from it.

What it tells you:

  • The calling relationship at this instant — who sits beneath the frame that is currently parked is fact, not inference.
  • The argument at the boundary — the value handed to the system call is right there. The target is settled here.
  • Whether your code is present — the presence or absence of your own functions on the stack is what decides your next direction.

What it cannot:

  • Why that argument — how the path entered the list is not on the stack. That comes from reading source.
  • History before an async hop — a flow that crossed a work queue loses its origin, because whoever enqueued it already returned.
  • Optimized-away frames — inlined or tail-called frames are simply not there, and absent is indistinguishable from erased.
  • Unsymbolicated regions — with only addresses you can name the module but not the function.

The practical conclusion is a two-part division of labor. Settle the target with the stack, confirm the reason in the source. Trying to reach a conclusion from the stack alone will produce a wrong answer at the first async boundary. Reading only source drops you back at the starting point, where the word is not in the code.

6. Why the permission model is scoped to the app

By now a natural complaint forms. If a process holds code from many origins anyway, why not ask per library? Then nothing could hide behind the app name.

The answer is not technical laziness. It is about where a boundary can actually be drawn. For a permission ruling to hold, the boundary needs three properties.

  • It must be enforceable — the system has to be able to stop what is inside from reaching resources outside. Code sharing an address space can read and write its neighbors freely. Withholding a permission from a library does not stop that library from calling into app code to do the same thing.
  • It must be legible to a human — a person makes the decision in the end. An app name is something the user recognizes; an internal library name is not. A screen asking for dozens of separate rulings on names nobody has seen is not defense, it is noise.
  • It must be stably identifiable — an app is pinned by its signature and bundle identifier. Dependencies change with every version, names included. You cannot attach a stored decision to a target that keeps changing.

The unit that satisfies all three in practice is a process and the signed identity attached to it. The model converged on app scope for that reason, not for lack of imagination about finer granularity.

The design does carry a clear cost. When there are several processes, or when a single process is internally heterogeneous, the subject of the ruling blurs. It blurs in two directions.

StructureWhat the permission attaches toWhat blurs
One process, many dependenciesOne appWho asked. The inside looks like one thing
An app split across processesEach executableOne app to the user, but decisions can diverge
A picker the system runs for youThe system, not the appAlmost nothing. The app gets only the result
A launcher that starts other binariesWhatever actually touches the resourceMay differ from what the user remembers allowing

Row three is the most practical item in this section. A component the system runs on your behalf barely blurs at all. The choice happens outside the app and the app receives only what the user selected. It is the one structure where the feature works without granting the app anything, so it comes back later.

Seen from the user side, this boundary discussion connects to the split between ownership and control. On which parts of a device fall in whose decision space, I wrote separately in the part you bought that is not yours.

7. What that sentence actually means to the user

Now the other side of the screen. How does a user read this app is trying to access your photos? Mostly as this app wants to look at my pictures. The real scope is both narrower and wider than that.

Narrower first: the sentence is about this attempt, at this moment. It guarantees nothing about how the app will use photos, where it will send them, or how long it will hold them. The dialog asks only whether to open the door. What happens inside is a separate matter.

Wider: an allow decision generally persists. The next time the same access happens, no dialog appears. That makes a momentary judgment last a lot longer than it feels. And as the opening case shows, the thing being allowed may be broader than, or simply different from, what the user pictured. The user imagined a photo album; the actual target was one directory tagged with that service.

What happens if you deny

Denial does not terminate the app. Only access to that resource fails and the rest keeps running. But the shape of the failure differs by resource, and so does what the user ends up seeing.

  • A well-built app — leaves that feature disabled and serves everything else, then explains again when it becomes relevant.
  • An app that did not plan for it — the list is empty or the progress bar stalls. The worst case is when it looks like nothing happened at all rather than an error.
  • An app that keeps asking — it does not handle the failure and retries the same access. That is why the dialog returned on every folder open in the opening case.

The decision can be reversed at any time in the privacy section of system settings. Note that the change often requires restarting the app before it takes effect. If you turned it on and nothing changed, check that first. One more rule of thumb: if you are not using the feature, denying costs you nothing. You will be asked again the moment it matters, and at that point the context is obvious.

8. What builders can do

What you can do here is not remove the dialog but make the moment it appears make sense. Four items.

Say why in advance

Apple requires apps that access the photo library to declare a purpose string explaining the reason in the app information file. Without it, the app exits at the point of access. So this is not optional, it is a precondition. Android documentation likewise recommends explaining the reason before requesting, citing research that users are far more comfortable with a permission request when they know why it is needed.

The common failure is filling the string as a formality. Photo access is required explains nothing. What the user needs to know is which feature it is for.

Ask at the moment of need

Android documentation states plainly that you should request at runtime when the user starts using the feature, not at app startup. Ask for the microphone when the microphone button is pressed. The reason is simple. With context there is material for a judgment; without it, the user either taps through or refuses on reflex.

The usual culprit for early timing is initialization code. Preparing everything at launch is convenient, but if permission-gated resources get prepared alongside, the dialog fires the instant the app opens. That placement lowers grant rates and creates a second problem. If the user never ends up using that feature, the permission sits open for no reason.

Do not link permissions you will not use

This is the highest-leverage item. Android documentation advises requesting only when the app genuinely needs the service or data, noting that reducing the total number of requests lowers the probability of denial. And it explicitly includes permissions required by third-party libraries and SDKs in what you should review.

Often a better option exists. Android's photo picker requires no runtime permission at all. The system grants temporary read access only for the items the user selected. The app receives the chosen photos without ever holding a permission over the whole library. When a permission-requiring implementation and a permission-free one sit side by side, checking whether the latter exists comes first.

Keep protected locations out of code that walks

This was the actual fix in the opening case. The offending directory was removed from the target list of the background job that calculated folder sizes. Other protected photo locations were already excluded, so it amounts to applying the same rule to one more place.

Reading this as a trick for avoiding permission dialogs gets the direction backward. What was done here is not bypassing an access ruling but deciding not to read data that was never needed. The permission is still there, and if the user asks for a photo feature the app asks properly at that point. Least privilege in practice usually looks like this. You do not touch the mechanism that blocks; you shrink what you reach for. How the same principle translates into tiers for agent tooling is covered in what should an AI agent be allowed to do.

9. The same shape on other platforms

This is not specific to macOS. It shows up in the same shape on every platform that asks per app. At the level of principle:

  • Mobile runtime permissions — the app requests, but the actual trigger is frequently a library. Frequent enough that official documentation warns about it.
  • Browser permissions — what appears in the tab is the site address, while the actual caller may be a third-party script embedded in that page. The ruling unit is the origin, not the script file.
  • Desktop file access — the program performed a directory walk, and protected targets were mixed in. The walking code knows nothing about the targets.
  • Server-side credentials — no dialog, same structure. One process holds many libraries, and credentials attach to the process. Which library used which key is not recorded by default.

Compressed into one sentence: the unit of ruling and the unit of causation are different. A ruling has to attach to something enforceable and stable, so it is drawn coarsely, while the cause sits somewhere inside. That gap is not a design failure. It is the limit of practically enforceable isolation boundaries.

Which is why the investigation order is the same everywhere. Establish what the request is for from the ruling record, drop into live state when that record stops talking, settle the target, then find the reason in the source. Only the tool names change.

Whether an approval screen holds up as a defense at all, and where that condition collapses, is a separate topic. I covered that side in when the person pressing approve is the defense line. This article sits one layer below it, on why the screen appeared in the first place.

10. What I could not confirm

Items this article cannot state definitively, gathered in one place.

  • The exact expansion of the TCC abbreviation — Apple does not document it under that name, so sources disagree on the wording. This article uses only the abbreviation.
  • Documentation for the offending directory — Apple documents the default photo library location as the Pictures folder under home. I could not find public documentation for the other path in the opening case. The claim that it is protected under that service rests on the original trace alone.
  • Differences across OS versions — which release began tagging that path this way is unconfirmed. The account here reflects the observation at the time of the original write-up.
  • The full list of other service identifiers — which paths each non-photo resource covers is not laid out in public documentation.
  • Decision-sharing rules for multi-process apps — the blurring in the table follows from the structure; I did not cross-check per-platform rules in detail.

Conclusion: the screen is the effect, the cause is below it

The least useful reaction to a permission prompt is suspicion. Why is this app trying to see this assumes the app is one actor with one intent, and a process is not built that way. Inside it, your code and other people's code run sharing a single boundary, and the operating system simply attaches an app label to that whole blob and shows it to the user.

Only one question produces answers. Which code path touched that resource? Reframed that way, the investigation proceeds over observable things. Narrow the reproduction, sort the kind from the ruling record, catch the parked execution flow at the point where the record stops talking, and read the stack upward. What comes out at the end is usually a missed scope, not malice. The opening case was that. Code that walks folders was walking places it did not need to walk.

The principle to keep as a builder is short. Do not link permissions you will not use, ask at the moment of need, say why in advance, and exclude protected locations from the targets of code that walks. All four point the same direction. Not making the dialog disappear, but actually shrinking what you reach for. Do that and the dialogs left over appear only when they genuinely matter, and that is the first time the user actually reads one.
