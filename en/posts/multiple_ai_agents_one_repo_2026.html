What Happens When You Unleash Multiple AI Agents on One Repo

Branch conflicts, orphan commits, and staging pollution from parallel coding agents - and how worktrees, sandboxes, and orchestrators fix it

Jul 20, 2026 Dev & Infra

Introduction: What Happens When You Unleash Multiple AI Agents on One Repo

As of July 2026, "attach one coding agent and watch it work" already feels like an old workflow. Now that Claude Code, Codex, and Cursor all natively support running several sessions at once, developers naturally arrived at the next question: if you let multiple agents loose in parallel, won't things just go faster? A recent GeekNews post captured exactly that experiment gone wrong - running several coding agents on one repository at the same time led to branches overwriting each other's work, orphan commits piling up with no owner, and a staging area that turned into a mess.

Instead of retelling that anecdote, this piece breaks down why this chaos is structurally inevitable, and which isolation and coordination patterns actually hold up in practice. The short version: the problem isn't agent capability. It's an architecture where multiple execution actors share one piece of mutable state - the working directory. This is the same shared-state problem parallel programming has wrestled with for decades, wearing a new face.

1. Why Parallel Agents Are So Tempting - Speed and Division of Labor

1.1 Speed: the feeling of multiple things happening at once

Run a single agent, and you wait while it plans, writes code, and runs tests. Attach three or four at once - one fixing a bug, one refactoring, one filling in test coverage - and perceived throughput jumps noticeably. Teams with solid isolation have reported running a dozen sessions in parallel on a single 48GB Mac and merging into main with no conflicts.

1.2 Division of labor: splitting concerns per agent

The second draw is division of labor. Just as a human team splits ownership by feature, agents can be assigned by module, layer, or ticket. Run a frontend agent, a backend agent, and a test agent separately, and it starts to feel like you assembled a small team.

2. The Problems You Actually Run Into

2.1 Shared working tree conflicts

The first problem is the simplest. When several agents write files in the same directory at the same time, one agent's save overwrites another's, or an agent reads a file mid-write and bases its next step on half-finished code.

2.2 Branch and commit contention - hijacking and orphan commits

Git was designed on the assumption that one person works in one working directory. When several agents switch branches inside the same checkout, one agent working on branch A can find another agent has switched the checkout to branch B - branch hijacking. Committing in that state either stacks commits onto the wrong branch or, in the worst case, produces an orphan commit attached to no branch at all (a detached-HEAD commit).

2.3 Staging area pollution

Worse still is index pollution. While one agent has staged its own changes with git add, another agent adding its own temp files or unrelated edits into the same index means the next commit mixes in changes nobody intended. For a reviewer, one commit tangling two or three unrelated pieces of work makes even a clean revert difficult.

2.4 Context interference and duplicate work

An agent builds its context by reading the current state of the code when it starts. If another agent changes files at that same moment, the plan gets built on state that's already stale. The result: two agents fixing the same bug in different ways, or one calling a function the other just deleted - duplicate, contradictory work.

2.5 Merge hell

Leave the problem unaddressed and keep working in parallel, and you eventually face merging several tangled changesets at once. Per-agent diffs collide on overlapping files, and resolving those conflicts falls right back on an agent or a human - handing back, at the merge stage, exactly the time parallelism was supposed to save.

3. Why This Happens - The Missing Atomicity and Isolation

The root cause boils down to two things. First, agents don't know each other's state. Each agent plans and executes only within its own session, with no way to know another agent is touching the same file at the same moment. Second, the filesystem and the git working directory provide no built-in atomicity or isolation. A database would stop this with transactions; local files and the git index have no such mechanism. What's really happening is that coding agents are reproducing, under a new name, the race-condition problem concurrency theory named decades ago - multiple parallel processes writing to the same resource without locks.

4. Isolation and Coordination Patterns That Actually Work

4.1 A separate git worktree/branch per agent

As of 2026, the most widely adopted fix is git worktree. A worktree shares a single .git repository while giving each agent a fully independent working directory and index. Claude Code offers a --worktree flag that automatically creates a worktree-<n> branch under .claude/worktrees/ at the repo root, and Codex and Cursor natively support similar parallel-session isolation. Because it removes conflict potential at the filesystem layer, it's the first thing worth trying.

4.2 Container and sandbox isolation

If worktrees stop file conflicts, containers and sandboxes go further and isolate the execution environment itself. Wrap an agent in a Docker container, a devcontainer, or a microVM, and it can't step on other agents' processes, network access, or credentials either. Codex CLI ships with an OS-level sandbox that disables network access by default. The more security- and permission-sensitive the organization, the more this layer matters beyond just worktrees.

4.3 Work queues and locks

Lock files or modules so that while one agent is working an area, no other agent can touch it. Stack tickets in a work queue and let agents pull one at a time, and you cut down the odds of multiple agents grabbing the same file simultaneously.

4.4 Orchestrator - hub and spoke

Instead of letting agents talk directly to each other, a central orchestrator splits work and collects results. This structure sidesteps the risk of a "mesh" pattern, where agents acting as peers on partial information produce semantically contradictory changes at the same time.

4.5 File ownership boundaries

Like code ownership on a human team, explicitly assign which directories or modules each agent may touch. Draw the line - "this agent only touches the API layer, that one only touches frontend components" - and the conflict surface shrinks sharply even without worktrees.

4.6 PR-based integration and CI gates

Finishing work on an isolated branch doesn't mean merging straight to main. Each agent's output goes up as a PR, and only what passes CI's build, test, and lint checks is eligible to merge. The principle - don't keep branches in a shared state, resolve conflicts only at merge time - is far easier to manage than real-time synchronization. Add a branch naming convention like agent/<ticket>-<description>, and reviewers know before they even open the diff that this is agent output, and can calibrate their scrutiny accordingly.

5. Connecting to Yesterday - Supervision Burden Grows With Parallelism

The supervision fatigue problem covered in The Human in the Loop Is Tired gets sharper the more agents you run in parallel. Supervising one agent is already tiring; supervise three or four at once and the diffs, PRs, and logs you need to review multiply just as fast. Isolation patterns cut down conflicts, but they don't reduce the total review load. So the more you scale parallelism, the more you need to strengthen first-pass filters that don't require a human - CI gates, automated linting, automated tests - or the gains from parallelism get eaten alive by supervision fatigue.

6. From a Tooling Angle - Worktree Automation and Orchestration

Creating and cleaning up worktrees by hand gets tedious fast. So 2026 has brought a wave of wrapper tools that automate worktree creation, cleanup, port separation, and branch naming. The Claude Code desktop app spins up a worktree automatically for every new session, and some open-source tools run Claude Code, Codex, and Gemini side by side, each in its own worktree, coordinating multiple vendors' agents from one screen. On the orchestration side, more tools are adding layers that automate task distribution and PR consolidation. When choosing a tool, there's one question that matters: does it enforce isolation for you, or does isolation still depend on a human remembering to do it?

7. When Parallelism Pays Off, and When It Backfires

Parallelism pays off when work units are genuinely independent - different modules, different files, different tickets with little inherent overlap - because worktree isolation alone keeps conflicts near zero. It backfires when multiple agents need to touch the same core files at once: shared configuration, shared type definitions, entry points. In those cases, sequential processing or a single agent with a wide context window is actually faster. Parallelism also loses more than it gains in a brand-new codebase or one whose architecture is still shifting, simply because the boundaries haven't been drawn yet.

8. A Practical Checklist

  • Does every agent get its own git worktree and branch?
  • Does branch naming flag agent-generated work (e.g. agent/...)?
  • Are agents blocked from committing or pushing directly to a shared branch (main)?
  • Are file- and module-level ownership boundaries documented up front?
  • Does every merge go through a PR plus CI gate?
  • Is work touching security or credentials isolated one layer further with a container/sandbox?
  • Is there a cap on how many agents can run concurrently? (Unbounded scaling means supervision collapse.)
  • Do you periodically check whether the total review load is still sustainable?

Conclusion

Turning multiple agents loose on one repo isn't the wrong idea by itself. The problem is turning them loose without isolation. Eliminate file conflicts with git worktrees, split the execution environment further with containers where needed, and resolve conflicts only at merge time through PRs and CI gates - do that, and parallel agents genuinely raise throughput. But that gain is a trade: the effort of building isolation infrastructure, and the stamina to handle a larger total review load. The judgment needed to carry that review load is close to the same systems-level thinking covered in Will Senior Developers Cash In on AI's Mess?. Go in knowing that trade-off up front.
