2026-09-03 開発・インフラ

依存関係の一覧を開くと、自分で書き入れた行は二十ほどしかないのに、ロックファイルには数百が入っている。そのうち活発なものは数週間に一度は新しいバージョンを出す。二つの数を掛ければ、毎週届くリリースノートの量は一人が読んで判断できる範囲をすでに超えている。かといって読まなければ、ある日デプロイが壊れ、壊れてからノートを開くとその内容はそこに書かれている。

だから現場で起きることはたいてい二つのうちどちらかだ。最初から誰も読まないか、一人が全部読んで疲れ果て、結局誰も読まなくなるか。この記事はその間を扱う。全部読むことが不可能なら、何だけを選んで読めばアップグレードを決められるのか。答えは思ったより短く、そのうち一つはほとんどのチームがそもそも探していない項目である。

この記事は特定のツールやサービスの利用を勧めたり評価したりするものではなく、導入や設定の手順も扱わない。引用した仕様と方針は2026年9月時点で各発行主体の一次文書から確認した内容であり、以後改定されうる。

きっかけ - リリースノートを選り分けるというサービス

2026年9月初め、韓国の開発者コミュニティで、CNCF プロジェクトのリリースノートからセキュリティ修正と破壊的変更、非推奨予定の項目を自動で抜き出すというサービスが紹介された。対象は CNCF の卒業・インキュベーティング段階の76プロジェクトだという。CNCF のプロジェクトページには2026年9月時点で卒業38、インキュベーティング38が並んでいるので、その数字は合っている。

公開されている付属リポジトリは Go で書かれた MCP サーバー一つだ。Apache-2.0 ライセンス、コミット102件、最新タグ 0.8.0、スター2、フォーク0。始まったばかりの個人プロジェクトである。だからこの記事はそのサービスを勧めも評価もしない。ただこういうものが作られるという事実自体が信号だ。リリースノートを読む仕事が、人の手では回らない作業になったという信号である。

サービスの web ページはアクセスを拒否され(HTTP 403)、直接開けなかった。したがって以下では特定のツールの動作ではなく、この種のツールが何を肩代わりでき、何が最後まで人の担当として残るのかだけを見る。

全部読むことはすでに不可能である

リリースノートを読まない理由は怠慢ではなく算数だ。自分で宣言した依存が三十あり、そのそれぞれがさらに十を引き連れてくれば、実行経路に入るパッケージは数百になる。ここに基盤プラットフォームが加わる。コンテナランタイム、オーケストレーター、データベース、リバースプロキシ、そしてその下のディストリビューション。一人が全部読んで判断できる量は、どの組織においても成り立たない。

ここに三つの錯覚が重なって問題が固まる。

  • 重要なものはどうせ目に付く — 最も危険な変更はたいてい目立たない文で書かれる。「既定のタイムアウトを調整した」 の一行がそれだ
  • メジャーが上がるときだけ見ればよい — 後で見る SemVer の仕様は、この期待をそこまでは保証してくれない
  • CI が通ったなら大丈夫 — テストは自分たちが使っていると知っている挙動しか検証しない。たまたま依存していた挙動はそもそもテストにない

だから必要なのは、もっと真面目に読む習慣ではなく読む対象を減らす基準である。基準がなければ真面目さは数週間しかもたない。

探すべきものは四つだけ

リリースノートには性能改善、ドキュメント修正、誤字、内部リファクタリング、コントリビューター一覧が混ざっている。アップグレードの可否を決めるのに要るのはそのうち四種類だ。残りはデプロイした後に読んでも遅くない。

何を探すかノートでよく使われる表現見落としたときに起きること機械が代わりに探せるか
セキュリティ修正Security, CVE-, GHSA-, advisoryすでに公開された脆弱性を抱えたまま運用するおおむね可能
破壊的変更Breaking, Removed, no longerデプロイが即座に壊れる。代わりに即座に分かるおおむね可能
非推奨予告Deprecated, will be removed in今は無事で、二バージョン後にまとめて爆発する部分的に可能
静かに変わった挙動Changed, Fixed, now defaults toエラー一つ出ずに結果だけが変わる最も難しい

セキュリティ修正 - 最もよく表示され、最もよく見落とす

セキュリティ修正は表記の約束が最も整っている。CVE や GHSA の識別子が付き、別の勧告ページが伴い、脆弱性データベースに索引される。それでも見落とす理由は表記ではなく到着経路にある。自分で宣言したパッケージのセキュリティリリースには通知が来るが、そのパッケージが内側で引き連れてくるものは通知設定の外にあることが多い。実際の事故はたいていそちらから起きる。

破壊的変更 - 危険だが正直である

破壊的変更は恐ろしく聞こえるが、実務的には最も扱いやすい部類だ。コンパイルが失敗するか、起動しないか、最初のリクエストで例外が出る。費用は大きいが検出は無料である。ここにかかる時間は 「直す時間」 であって 「探す時間」 ではない。

非推奨予告 - 今日の警告、来年の障害

非推奨予告は今日は何も起こさない。だから読んでも流す。問題はこの項目が期限の付いた負債だという点だ。その都度イシューとして登録しなければ、数年後に何件かが同じ週にまとめて満期を迎える。

静かに変わった挙動 - 誰も印を付けてくれない

四つ目は前の三つと性格が違う。表記の約束がなく、リリースノートでは 「Changed」 や 「Fixed」 の項目の中の一文として通り過ぎる。バージョン番号はマイナーかパッチなのに既定値が変わっていたり、並び順が変わっていたり、丸め方が変わっていたりする場合だ。デプロイは成功しテストも通る。ただ結果が変わっている。

四つ目がなぜ最も危険なのか

前の三つはどこかの時点で信号をくれる。セキュリティ修正は勧告文書が出て、破壊的変更はデプロイが壊れ、非推奨予告はログに警告が残る。四つ目だけが何の信号もくれない。だから発見の時点がデプロイ直後ではなく、数週間後に数字が合わなくなったとき、あるいは利用者が問い合わせを入れたときになる。

この類型がどう生まれるかは SemVer の仕様自体にヒントがある。仕様はパッチバージョンを 「後方互換のあるバグ修正のみが導入されたとき」 に上げると定めながら、バグ修正を「誤った挙動を直す内部変更」と定義する。ところが自分たちのコードがその 「誤った挙動」 に依存していたなら、その修正は定義上パッチでありながらこちらには破壊的変更である。上流では直したことで、下流では壊れたことだ。この非対称は、規約をどれだけよく守っても消えない。

ノートからこの類型を拾う方法は、いくつかの語を疑うことだ。下の左の表現が出てきたら、その文は 「性能改善」 の項目にあっても読み直さなければならない。

ノートの表現実際に問うべきことこちら側で確認する場所
既定値がこれから X になるその値を明示的に書いてあったか設定ファイルとコードでそのオプションを検索する
もう Y をしないY を前提にして使っていたか暗黙の前提はテストにない可能性が高い
並び順を安定化した順序に依存するロジックがあるか先頭要素を使うコード、ページネーション
精度や丸めを直した金額や数量の計算に使われるか保存済みの過去の値と新しい計算値がずれる
これからエラーを投げる黙って通っていた入力があったか例外処理なしに通り抜けていた経路

表の最後の行は特によく来る。誤った入力を黙って無視していたライブラリが、これから例外を投げるように 「直される」 場合だ。リリースノートには 「Fixed」 と書かれる。

セマンティックバージョニングが約束することとしないこと

Semantic Versioning 2.0.0 の仕様は三桁の数字それぞれに意味を与える。メジャーは後方互換のない API 変更があるとき、マイナーは後方互換のある機能が追加されるとき、パッチは後方互換のあるバグ修正があるときに上げる。そして仕様はマイナーの項目に一行を足す。公開 API のいずれかの機能が非推奨として表示されたなら、マイナーを必ず上げなければならないというものだ。非推奨予告そのものがバージョン番号に反映されるように設計されている、ということである。

ここまでが約束だ。約束でないもののほうが多い。

SemVer が約束すること約束しないこと
メジャーが上がったなら非互換の変更があるメジャーが上がっていないなら壊れないということ
公開 API の非推奨表示はマイナー以上に反映される文書化されていない挙動、エラーメッセージ、ログ形式
メジャーを上げるとマイナーとパッチは 0 に戻す性能、遅延、メモリ使用量の連続性
0.y.z はいつでも何でも変わりうると先に明示する推移的依存が一緒に上がって生じる変化
規約に従うと宣言したプロジェクトに限っての話であるそのプロジェクトが 「公開 API」 をどこまでと見るか

右側の一行目が実務では最も高くつく。仕様の FAQ はこの状況を直接扱う。誤って後方互換のない変更を出してしまったとき、戻す影響が大きいなら「厳密にはパッチリリースとみなせる修正であってもメジャーリリースを出すほうがよいことがある」と書く。つまり仕様を作った側も、バージョン番号と実際の影響がずれうることを前提にしている。

0.x の特例もそのまま読んでおく価値がある。仕様は 0.y.z を初期開発用と定めながら 「いつでも何でも変わりうるので、公開 API を安定しているとみなすべきではない」 と釘を刺す。1.0.0 をいつ出すべきかという FAQ の答えはもっと率直で、プロダクションで使われているならすでに 1.0.0 であるべきだと書かれている。だから運用に入っている 0.x の依存は、規約上は何も保証されない場所だ。

セキュリティ勧告の読み方 - スコアは順序ではない

セキュリティ修正を見つけたら、次の問いは 「先に直すか」 だ。ここでよくある誤りが CVSS のスコアで並べることである。FIRST の CVSS v4.0 ユーザーガイドはこの用法を明示的に止める。「CVSS Base スコアは脆弱性の深刻度を測るために設計されており、リスクの評価に単独で用いてはならない」という一文がそれだ。同じ文書は Base スコアが脆弱性固有の性質だけを反映し、脅威の状況やそのシステムが置かれた環境とは無関係だと付け加え、環境指標と脅威指標で補わなければならないと書く。

順序を実際に変えるのは現に悪用されているかどうかである。CISA の KEV カタログはその目的で運用されている。登載基準は三つで、CVE 識別子が付与されていること、実際に悪用されたという信頼できる証拠があること、そしてベンダー提供の更新のような明確な対処方法があることだ。カタログのページは自らを「実際に悪用された脆弱性についての権威ある出典」と紹介しつつ、組織はこの目録を 「脆弱性管理の優先順位付けの枠組みへの入力として」 使うようにと書く。2026年9月時点の登載件数は1,694件である。

米国の連邦民間行政機関に適用される指針は、2026年6月10日付の BOD 26-04 として更新された。この指針は KEV の登載基準をそのまま引き継ぎつつ、対処期限をスコアではなく四つの二択の問いで定める。他国の企業に直接適用される規定ではないが、優先順位付けの関数の形としてはそのまま参考になる。

何を問うかなぜそれを問うのか
資産が外部に公開されているか攻撃者が到達できて初めて悪用が成立する
KEV の目録に載っているか理論上の可能性と実際の悪用は別の出来事である
悪用を自動化できるか自動化されれば標的でなくても順番が回ってくる
部分的な制御か完全な掌握か同じ到達でも結果の大きさが違う

指針の表に書かれた例を挙げると、外部に公開されていて KEV に載っており自動化が可能で完全な掌握につながる組み合わせは、3日以内に対処しフォレンジックの選別も併せて行うことになっている。同じ条件で影響が部分的な制御なら6日だ。反対の端で、KEV になく外部露出もなく影響が部分的な制御である組み合わせは「システムのアップグレード時に修正」に分類される。期限は暦日基準であり、事実関係が変われば期限も変わると明記されている。

ここから得るべきは期限の数字ではなく構造だ。スコア一つを閾値と比べる代わりに、到達可能性、実際の悪用、自動化、影響の大きさをそれぞれ別に問う。四つの問いのうち三つは外部の資料で答えられ、一つ目だけが自分たちのインフラを知る人が答える。パッチが出た後に守る側へ残る時間は修正したという事実が信号になるで別に扱った。

機械が読めるように作られた仕掛け

リリースノートを自動で走査するツールは、何もない真空で動くわけではない。この十数年のあいだに人が読む文章に機械が掛けられるフックを埋め込む慣例が何層にも積み上がってきた。それぞれが答える問いが違う。

形式・データベース答える問い限界
Keep a Changelogこのリリースにセキュリティ項目があるかプロジェクトが従うときにだけ成立する
Conventional Commits破壊的変更がコミットに表示されたか表示漏れを検証する手段がない
GitHub Releases APIどのタグがいつ出たか本文は自由形式のマークダウンである
OSVこのバージョンが影響範囲に入るか影響範囲はパッケージ単位である
GitHub Advisory Databaseどのバージョンで最初に直ったか未レビュー項目は通知を出さない
SBOM自分たちが何を載せているか載せていることと実行することは違う

Keep a Changelog は 1.1.0 版で変更の種類を六つに固定する。Added(新機能)、Changed(既存機能の変更)、Deprecated(まもなく削除される機能)、Removed(削除された機能)、Fixed(バグ修正)、Security(脆弱性に関するもの)。この六つのうちSecurity という区画が別にあることがこの慣例の実質的な価値だ。前節の一つ目の問いに区画の名前一つで答えが出るからである。ただし同じ文書は 「変更履歴は機械ではなく人のためのもの」 という原則を前面に置き、コミットログの diff を変更履歴として使うのは 「雑音だらけで悪い考え」 だと書く。

Conventional Commits 1.0.0 はコミットメッセージ側にフックを掛ける。構造はこうだ。

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

フッターに大文字の BREAKING CHANGE とコロンを書く方式が一つ、タイプやスコープの後、コロンの直前に ! を付ける方式がもう一つである。仕様は ! を使うならフッターを省略してよく、そのときはコミットの説明自体が破壊的変更を説明する文になると定める。そしてタイプにかかわらず BREAKING CHANGE の入ったコミットはメジャーリリースに対応させるべきだと書く。

変更履歴側の形はこうなる。区画の名前が固定されているので構文解析ができ、そのため前の四つのうち三つを機械が候補として抜き出せる。

## [2.4.0] - 2026-08-14
### Added
### Changed
### Deprecated
### Removed
### Fixed
### Security

収集側では GitHub のリリース REST API がよく使われる。リリース一覧、最新リリース、タグ別の取得エンドポイントがあり、応答には tag_name・body・prerelease・draft・published_at といったフィールドが入っている。ノートを自動生成するエンドポイントもあり、文書はその結果を 「前回のリリース以降の変更と貢献者の情報を含むマークダウン本文」 と説明する。prerelease と draft を無視すると、まだ正式でないタグを取り込むことになる。タグそのものが消えたとき下流が何を失うのかはタグが消えると下流は何を失うのかで扱った。

脆弱性側は二つのデータベースが軸になる。OSV は自らを 「オープンソースのための分散型脆弱性データベース」 と紹介し、そのスキーマが「人と機械の双方が読める形式で、オープンソースパッケージのバージョンやコミットハッシュに正確に対応するように」脆弱性を記述すると述べる。ここで重要な語は 「正確に対応」 だ。「1.x 系のどこかに脆弱性がある」 という記述では自動判定ができないからである。

GitHub Advisory Database は項目を三つに分ける。GitHub がレビューして生態系とパッケージの情報を確認したもの、NVD のフィードから自動で入ってきてレビューされていないもの、そして悪意あるパッケージに関するものだ。未レビューの項目は Dependabot の警告を発生させないことが文書に明記されている。つまり通知が来なかったという事実は 「該当なし」 を意味しない。各項目は GHSA-xxxx-xxxx-xxxx 形式の識別子を持ち、問題が存在するリリースバージョンの範囲と最初に修正されたバージョンを併せて収める。実務では後者のほうがよく使われる。どこまで上げればよいかがすぐ出るからだ。

SBOM は別の層で答える。CISA は SBOM を 「ソフトウェア構成要素をなす材料の一覧、入れ子になったインベントリ」 と定義し、ソフトウェアサプライチェーンのリスク管理における中核的な構成要素と説明する。同じページが併せて紹介する VEX は「ある製品が既知の脆弱性の影響を受けるかどうかを示す証明であり、セキュリティ勧告の一形態」である。次節の問題、つまり 「では自分たちが影響を受けるのか」 を供給側であらかじめ答えておこうという試みがこれだ。

最後に、リリースノートの外で答えを得る方法もある。Kubernetes は v1.19 以降、非推奨の REST エンドポイントへの要求に対して応答に Warning ヘッダーを付け、監査イベントに k8s.io/deprecated のアノテーションを残し、apiserver_requested_deprecated_apis のゲージ指標を 1 に設定する。この指標にはどのリリースで提供が止まるかを示すラベルまで付く。ノートを読む代わりに稼働中のシステムに直接尋ねる方式であり、非推奨に関する限りこちらのほうがはるかに正確だ。自分たちが実際にその API を呼んでいるかまで教えてくれるからである。

自動化が効く場所と止まる場所

前述の形式を全部貼り付けると、どこまでできるのかがかなり鮮明になる。境界は一行で引ける。上流のリポジトリの中に情報があれば機械が答え、自分たちのコードの中にあれば答えられない。

  • 機械が答えられること — このリリースに Security 区画があるか。コミットに破壊的の表示があるか。自分たちが固定したバージョンがこの勧告の影響範囲に入るか。どのバージョンで最初に直ったか。前回以降いくつのタグが通り過ぎたか
  • 機械が答えられないこと — そのコード経路を実際に通るか。変わった既定値を明示的に指定してあったか。削除された関数が自分たちのコードでどんな引数で呼ばれるか。この変更が自分たちのデータの形で問題になるか
  • 中間にかかること — そのパッケージを載せているか。SBOM はここまでは答えるが、載せていることと実際に実行することの間の隙間は残す
  • 供給側が代わりに答えようとする試み — VEX は 「この製品はその脆弱性の影響を受けない」 を文書として残す方式だ。ただし作ってくれるところがあってはじめて使える
  • 残るもの — 判断は移らない。自動化がするのは候補を作り順序を付けるところまでだ

だから自動化導入の成否は 「どれだけ多く拾ってくれるか」 ではなく「人が見るべき一覧をどれだけ短くしてくれるか」である。一日に四十件を投げてくるツールは、何も投げてこないツールと実質的に同じだ。どちらも読まれないからである。

要約でデプロイを決めてはいけない理由

要約は文を短くする作業ではなく何を捨てるかを選ぶ作業である。そしてリリースノートで真っ先に捨てられるのが、よりによって条件節と否定語だ。「A のオプションを有効にした場合にだけ B が変わる」 が 「B が変わる」 に縮む、という具合である。人が要約しても起きる事故だが、長さを目標にする自動要約では構造的にもっと頻繁に起きる。

リリースノートの要約で繰り返される損失は、おおむね五つに分かれる。

  • 条件の脱落 — 特定の設定、プラットフォーム、バージョンの組み合わせにだけ該当する変更が全面的な変更として読まれる
  • 否定の反転 — 「しない」 が 「する」 に、「影響を受けない」 が 「影響を受ける」 に変わる
  • 主体の取り違え — サーバー側の既定値変更がクライアント側の変更に、あるいはその逆に移る
  • バージョンの取り違え — 脆弱なバージョンと修正が入ったバージョンが混ざる。この類型は対処の方向を正反対にする
  • 強度の歪み — 「推奨する」 が 「必要だ」 に、「既知の事例はない」 が 「ない」 に固まる

だから要約は読むものを選ぶことにだけ使い、デプロイの判断は原文で行う。この区別を固めるには表示の規則が三つあれば足りる。要約の隣に必ず原文のリンクとタグ名を置く。「セキュリティ項目なし」 と 「確認していない」 を別の表記で区別する。要約が根拠にした文をそのまま引用して添える。

チームで回すやり方

規則が重ければ二か月ももたない。実際に維持される形はたいていこの程度だ。

  • 対象をまず減らす — ロックファイル全体ではなく、自分で宣言した依存と基盤プラットフォームだけを定期の対象にする。残りは脆弱性の通知に任せる
  • 週次の走査は一人で30分 — 持ち回りにし、成果物は 「今週人が見るべきもの N 件」 の一覧一つにする。読んだ人が判断まではしない
  • 緊急と定期を分ける — 緊急経路の条件はあらかじめ文で書いておく。外部に露出した資産であり、かつ実際の悪用が確認された脆弱性、という程度がよくある基準線だ。残りは全部定期経路に送る
  • ボットの PR は自動マージの範囲を先に決める — パッチ水準で、テストが通っていて、破壊的の表示がない場合まで。その外は人が見る。GitHub の文書も、提案された更新を判断するときはPR の要約に含まれる変更履歴とリリースノートを確認するようにと書く
  • 溜まった PR は方針の失敗の信号として読む — 二十件が滞っているならそれは怠慢ではなく、自動マージの範囲が狭すぎるか対象が広すぎるという意味だ
  • 見送ったものを記録する — 今週保留したアップグレードは期限を付けてイシューに残す。記録されない保留は来週には存在しない

ボットが開く PR を扱うときにもう一つ触れておくことがある。自動更新ツールは、脆弱性のない依存も最新に保つことを目的にしている。だから PR が開いたという事実そのものはセキュリティの出来事ではない。セキュリティの PR と最新化の PR を同じ列に並べると、本当に緊急なものが埋もれる。ラベルであれチャンネルであれ、二つの流れは目に違って見えなければならない。そしてこの収集パイプラインはたいていリポジトリのアクセストークンを持ち歩くが、そのトークンが漏れる場所はリモートURLにトークンが埋まっているに整理してある。

リリースノートを書く側にできること

ここまでが読む側の話だ。書く側にできることのほうがずっと安く、効果が大きい。リリースノートは何をコミットしたかではなく何をすべきかを書く文書である。

  • Security の区画を空けたままにしない — 該当がなければないと書く。区画がそもそもないことと空であることは、読む側にはまったく別の情報だ
  • 破壊的は見出しの行に置く — 本文の二十行目にある破壊的はないのと同じである。コミット規約の ! の表示やフッターがその場所を作ってくれる
  • 既定値の変更は破壊的として扱う — バージョン番号ではマイナーでも、下流では破壊的だ。前で見た四つ目の類型はここでほとんどが生まれる
  • 非推奨は予告と削除の時期を併せて書く — 「後で削除される予定」 は期限ではない。Kubernetes の API 非推奨方針がその形に近い。GA のバージョンは非推奨の表示はできても同じメジャーの中では削除できず、ベータのバージョンは導入から9か月またはマイナーリリース3回のうち長いほうの期間内に非推奨となり、非推奨からさらに同じ期間が過ぎてはじめて提供が止まる。アルファは予告なくどのリリースでも削除されうる
  • 実行時の警告を残す — ノートを読まなかった人に届く唯一の経路である。先に見た Warning ヘッダーと非推奨 API 呼び出しの指標がその例だ
  • 移行ガイドはコードで書く — 「何が変わった」 ではなく 「このコードをこのコードに」。文章の説明十行より before と after の二行のほうが速く読める

同じ方針文書にもう一つ規則がある。API の要素は API グループのバージョンを上げることによってのみ削除できるというものだ。すでに特定のバージョンに入った要素は、そのバージョンから外したり挙動を大きく変えたりできない。この規則が下流に与えるのは 「このバージョンを使い続ける限り足元は変わらない」 という保証であり、その保証があってはじめてアップグレードを計画として扱える。

先送りには利息が付く

アップグレードを先送りする判断自体はしばしば正しい。今は要らず、今は手を付ける人がおらず、今リスクを作る理由がない。問題は先送りしている間に何が積み上がるのかが見えにくい点だ。

  • 非推奨警告をまるごと失う — 警告はそのバージョンを実際に通り過ぎるときにだけ出る。メジャーを三つ一度に飛ばすと中間のバージョンが出したはずの警告を一度も見られず、それらの警告が知らせようとした変更を全部まとめて受ける。これが先送りしたアップグレードの最大の実質費用である
  • 移行ガイドが噛み合わなくなる — ガイドは一段ずつ登る前提で書かれている。三段飛ばすと各段の前提条件が互いにずれ、結局どのガイドもそのままでは適用できない
  • セキュリティ修正が最新ブランチにしか入らない — こうした方針は珍しくない。すると遅れているほど、脆弱性一つのために計画外の大規模アップグレードを強いられる
  • 他のアップグレードまで止まる — 古い一つが上限を掛けていると、それと噛み合ったパッケージが一緒に縛られる。一行が上がらないために十行が止まる

だから実務の規則は一つでよい。先送りするという判断を記録に残し、期限を付ける。期限のない保留は判断ではなく忘却であり、忘却の費用は後でまとめて請求される。この請求書が届く時点は、たいてい自分たちで選べない。

まとめ

リリースノートを全部読むことは不可能だ。だから目標は真面目さではなく選別である。選ぶべきものは四つ。セキュリティ修正、破壊的変更、非推奨予告、そして何の印もなく挙動だけが変わった項目。前の三つは表記の約束があるので機械が候補を作ってくれ、四つ目は約束がないので人が語を疑うほかない。事故はたいてい四つ目から起きる。

バージョン番号は信号であって保証ではない。SemVer はメジャーが上がったなら非互換の変更があることは教えてくれるが、メジャーが上がっていないなら安全だということまでは教えてくれない。セキュリティ側も同じだ。スコアは深刻度を測る値であって順序を決める値ではなく、順序を変えるのは実際の悪用の有無と自分たちの環境の露出の度合いである。

自動化の境界もはっきりしている。上流のリポジトリの中にある情報は機械が答え、自分たちのコードの中にある情報は答えられない。「このリリースにセキュリティ修正がある」 は見つけられても「自分たちのコードが影響を受ける」 は見つけられない。だからツールを付けるときに期待すべきは一覧が短くなることであって、判断が消えることではない。

確認できなかったこと

  • きっかけとなったサービスの web ページはHTTP 403 でアクセスを拒否され、直接開けなかった。そのサービスの収集周期、分類方式、正確さについては何も記述しておらず、リンクも張っていない。確認したのは公開されている付属リポジトリのメタデータだけである
  • LLM の要約が否定語や条件節を落とす頻度については、数値を引用できる一次資料を確認できなかった。該当の節は要約という作業の性格から出る構造的なリスクとしてだけ書き、発生率を主張していない
  • 「毎週数百件」 のような総量の数字は組織の依存構成によって変わるため、一般化した数を使っていない。OSV が生態系別に表示する件数も、集計の基準を確認できなかったので引用していない
  • 自動依存更新ツールの同時 PR 件数の既定値とまとめ処理は、参照した文書で確認できなかったので数値を書いていない
  • CISA の SBOM 最小要素の一覧と VEX の四つの状態値は別の PDF 文書に入っており確認できなかった。二つの概念の定義だけを引用している
  • CNCF のサンドボックス段階のプロジェクト数は参照したページに表示されていなかったため、卒業38とインキュベーティング38だけを書いた
