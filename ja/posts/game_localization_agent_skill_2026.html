レトロゲーム翻訳をAIエージェントスキルに

クラシックゲームのファン翻訳ノウハウを再利用可能な方法論にまとめたOSSエージェントスキルが投げかける問い

2026年7月10日 開発・インフラ

序論: なぜ今このGitHubプロジェクトに注目するのか

GeekNewsのShow GN欄にcreate-retro-game-kr-patchという名のリポジトリが投稿された。SNES、メガドライブ、セガサターン、PS1、ドリームキャスト、PCエンジン、PC-98、ゲームギア、ニンテンドーDSまで9つのレトロプラットフォームを横断するこのプロジェクトは、複数のクラシックゲームの韓国語パッチを実際に制作した経験をAIエージェントスキルという形にまとめた成果物だ。特定の完成品ツールではなく、「この作業をどんな順序でどう進めるべきか」という方法論そのものをパッケージ化した点が注目に値する。

レトロゲームの翻訳は、韓国のゲーマーコミュニティで既に20年以上続く自生的な趣味活動だ。その長い時間で積み重なったノウハウ - どのゲームがどんな落とし穴を抱えているか、フォントをどう詰め込むべきか、何を検証すればパッチが安全か - は、大抵は個人の頭の中や散らばったフォーラム投稿に留まっていた。このプロジェクトが興味深いのは、翻訳そのものよりも、そうした暗黙知を再利用可能なスキル形式に移そうとした試みにある。この記事はGeekNewsの紹介文をそのまま繰り返す代わりに、ROMハックという古くからの作業の実際の難題は何か、それをエージェントスキルとして体系化することがどんな意味を持つか、AI翻訳が実際に何を変え何を変えないか、そして著作権の問題までを自分の視点で掘り下げる。(2026年7月時点)

1. レトロゲーム翻訳の古くからの難題

1.1 そもそも外国語の文字が入る余地がなかった

1980〜90年代に作られたゲームの大半は、ラテン文字や仮名程度しか表示しない前提で設計されていた。完全なハングルや漢字のセットは組み合わせ可能な文字数が数千字に及び、数十字のアルファベットや百字程度の仮名とは桁が違う。これを表示するには新しいフォントタイルセットを描き起こし、そのタイルを指すエンコーディング表を新たに設計しなければならない。問題はROMカートリッジの容量がそもそもそうした拡張を想定せずぴったり設計されていたことだ。新しいフォント1つ分の空き容量を確保することからすでにパズルである。

1.2 可変幅フォントと膨らんだテキストの容量問題

原作ゲームの多くは、すべての文字を同じ幅で描く固定幅レンダリングを採用している。ハングルのような正方形に近い文字を入れる分には悪くないが、翻訳の過程で原文より文が長くなると画面からはみ出したり会話ウィンドウが崩れたりする。これを避けるには各文字が必要な分だけ幅を占める可変幅フォント(VWF)を新たに実装する必要があり、これはフォントのグラフィックだけでなく文字を描く低レベルコードにまで手を入れる作業だ。ここにROM全体の容量制限が重なると、圧縮方式を新設計したりバンクを再配置したりして空き容量を作り出す別の工学的作業が加わる。

1.3 テキスト抽出・再挿入とポインタの壁

テキストは大抵圧縮された形でROM内に散らばっており、各文字列の開始位置はポインタテーブルが指し示す。翻訳文を挿入する際に原文と長さが変わると、ポインタの値も併せて更新しなければならず、一つでもずれるとゲームが停止したり誤った文字列を出力したりする。ここにイベントスクリプトを実行する低レベルコード(ASM)に手を入れるフック作業まで必要な場合が多く、翻訳はこの長いパイプラインの一工程に過ぎない。実際create-retro-game-kr-patchも、テキストエンジンのリバースエンジニアリング、ポインタ再配置、ASMフック、ビルドとパッチ生成、検証という段階を明示的に区別して扱っている。

2. 「エージェントスキル」に方法論を込めることの意味

2.1 スキルとは何か - 反復作業の知識カプセル化

エージェントスキルとは、特定の作業に必要な指針、スクリプト、参考資料を一つの束にまとめ、AIエージェントが必要な時に呼び出せるようにするパターンだ。毎回ゼロから説明する代わりに、「この領域ではこの順序で確認し、この落とし穴に注意せよ」という手続き的知識を再利用可能な形で保存しておくわけだ。このプロジェクトがその器としたのが、テキスト抽出・翻訳・再挿入という、繰り返されるが標準化されていなかったROMハックのワークフローである。

2.2 なぜよりによってROMハックなのか - 定型化されていない作業の定型化

ROMハックはゲームごとにフォント構造、圧縮アルゴリズム、ポインタ配置がまちまちで、一つの標準ツールでは突破できない領域だ。そのため長らく、人が毎回リバースエンジニアリングから始めなければならなかった。このプロジェクトが選んだアプローチは、特定ゲーム専用のツールを事前に作って配布する代わりに、AIが対象ゲームに合わせたツールをその都度自ら開発して使うよう設計することだ。完成品ではなく問題解決の手順そのものをカプセル化した点で、標準化が難しい領域にスキルパターンを適用した事例として読める。

2.3 リスクを減らす仕組み

興味深いのは安全装置だ。チェックサムと自動テストで静的エラーを何重にも検出し、コストの高い実装に着手する前に小さなPoC(概念実証)実験でリスクを先に洗い出すという原則を明示している。ROMハックのように一つのミスがゲーム全体を壊しかねない領域で、AIに全権を委ねるのではなく検証手順を何層にも重ねる設計は注目に値する。

3. AI翻訳がゲームローカライズに与えるものと限界

3.1 確実に速くなること

テキストをゲームデータから抜き出し、翻訳が終わった後に正確な位置・エンコーディングで再び挿入する抽出・再挿入の工程は、本質的に機械的な作業だ。ここにポインタの再計算や繰り返しのフォント描画検証まで、AIがコードを自ら書いて処理するよう任せれば、人が手作業でこなしていた退屈な反復作業のかなりの部分が減る。実際GeekNewsのコメント欄でも、ゲームの種類と翻訳量によって短くて1週間、長くて2週間以上の作業時間がかかるという言及があった。これは依然として少なくない時間だが、人が全工程を手作業で行うより明らかに短縮された数字と見られる。

3.2 依然として人の目が必要なこと

ただし翻訳の質自体は別の問題だ。キャラクターごとに異なる口調、時代劇特有の言い回し、狭い会話ウィンドウに収めるべき圧縮表現、文化的背景のある言葉遊びは機械的処理だけでは終わらない。翻訳エンジンが出した下訳をそのままROMに詰め込むと、文法は合っていてもゲームの雰囲気とずれた台詞になりやすい。このプロジェクトの価値は、AIが翻訳まで全て完結させることにあるというより、反復的な抽出・再挿入・検証工程を自動化して人が本来注力すべき翻訳品質の検証により多くの時間を割けるようにする点にあると見るのが正確だろう。

4. 著作権と法的グレーゾーン

4.1 ファン翻訳がなぜ原則として曖昧なのか

ベルヌ条約など国際的な著作権体系では、翻訳権は原著作権者に留保された排他的権利だ。つまり無許可の翻訳は形式上、著作権侵害のリスクを伴う。ただし原本ファイルではなく原本との差分のみを含むバイナリパッチを配布する方式がそれ自体安全だという考えは、コミュニティ内で長く通用してきただけで、裁判所で明確に検証されたことはない通念に近い。

4.2 執行の現実 - 完全な安全地帯ではない

ここ数年、一部の大手ゲーム会社がエミュレータやROM配布サイトを相手取って訴訟を起こし、高額の賠償判決や和解を勝ち取った事例が報じられている。これはファン翻訳パッチそのものを狙い撃ちした事例ではないが、著作権者が関連エコシステム全体に対して法的対応の意志を明確に示しているという信号として読める。それだけに、パッチの制作・配布を「慣行的に黙認されてきたこと」と断定するより、依然として法的不確実性が残る領域として扱う方が現実的だ。

4.3 このプロジェクトが引く線

注目すべきは、このリポジトリが自ら「原本のROM・ディスクイメージ・著作物は絶対にリポジトリにコミットしない」という原則を明示している点だ。リポジトリにはパッチ生成スクリプトと方法論のみを収め、原本のゲームデータや完成したROMファイルは配布しない構造になっている。この記事も同じ原則に従い、ROM配布や違法ダウンロード経路は一切紹介せず、あくまで技術的方法論とそれが投げかける問いにのみ焦点を当てる。

5. エージェントスキルパターンの一般的価値 - ROMハックを超えて

このプロジェクトをゲーム翻訳という狭い枠の外から見ると、示唆はさらに広がる。エージェントスキルは結局、「標準ツールはないが経験豊富な人の頭の中には明確な手順がある」領域に適したパターンだ。ROMハックはそうした領域の極端な例に過ぎず、レガシーシステムの移行、特殊ハードウェアの障害対応ランブック、特異なデータ形式の変換のように、標準化が乏しく毎回人が判断してその場でツールを作らねばならなかった他の専門作業にも同じアプローチがそのまま適用できる。重要なのは完成品のツールを作ることではなく、「この問題をどんな順序で解き、何を検証すべきか」を再利用可能な知識としてカプセル化するという発想そのものだ。

6. 韓国レトロゲームコミュニティの視点

韓国のレトロゲームファン翻訳文化は根が深い。個人や少人数のチームが趣味として始め、正式に発売されなかった名作を長い時間をかけて韓国語化してきた歴史がある。ただしそれだけ参入障壁も高かった。フォントグラフィック編集、アセンブリコード解析、圧縮アルゴリズムのリバースエンジニアリングをすべてこなせる人は少数で、そのため一部の翻訳者に作業が集中したり、手つかずのまま放置されたゲームも多かった。この文脈で見ると、反復工程をAIエージェントが代行するツールは参入障壁を下げ、より多くの人が翻訳品質そのものに集中できる余地を広げるという点で意味がある。ただしだからといって、コミュニティが長年積み上げてきた検証文化 - 複数人で一緒にプレイテストし、誤字や不自然な訳をフィードバックし合う過程 - をAI一つが代替できると見るのは時期尚早だ。むしろ人の役割は機械的な反復作業から品質とニュアンスの検証へと移っていく方が近い。

結論

create-retro-game-kr-patchは完成した翻訳ツールではなく、長らく一部の人の頭の中にだけあったROMハックのノウハウをエージェントスキルという再利用可能な形に移そうとした試みだ。フォント・エンコーディング・可変幅・容量制限という古くからの技術的難題は依然として残っており、AIはそのうち反復的で機械的な部分をかなり軽減するだけで、翻訳のニュアンスや検証まで代行するわけではない。著作権の問題も、このプロジェクトが原本の資産を配布しないという原則で線を引いているに過ぎず、ファン翻訳自体が置かれた法的グレーゾーンが消えたわけではない。それでもこのプロジェクトが示す方法論をスキルとしてカプセル化するというアプローチ自体は、標準ツールのない他の専門領域でも噛みしめる価値のあるパターンだ。
