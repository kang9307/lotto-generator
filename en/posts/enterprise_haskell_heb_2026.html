Why H-E-B Runs Its Supply Chain on 1 Million Lines of Haskell

From the "academic language" myth to what 8 years of production Haskell actually proves about enterprise functional programming

Jul 20, 2026 Dev & Infra

Intro: What Haskell Is, and Why It's Seen as an "Academic Language"

In July 2026, the official Haskell blog (blog.haskell.org) published a striking case study. H-E-B, the largest privately held company in Texas and a major grocery retailer, modernized the supply chain systems behind more than 435 stores and distribution centers using Haskell. Eight years later, roughly 1 million lines of Haskell code, split across multiple teams, now run as core production systems.

What makes this notable is simple. Haskell is usually thought of as a language you meet in a university lecture hall or a programming-languages paper. Terms like pure functional, monad, and type class are often a barrier to entry for working developers. That a language with that reputation has powered consumer-facing supply chain features - curbside pickup, real-time inventory, in-store search - for eight years, replacing a legacy mainframe in the process, collides head-on with the "academic language" stereotype.

Rather than simply relay the announcement, I want to work through why Haskell earned that academic reputation, what it actually means for an enterprise to adopt a language like this, and what the real tradeoffs of functional-language adoption look like. My conclusion up front: this case is not an unconditional victory lap for functional programming. It reads more like an honest case study of what you pay, under what conditions, and what you get in return.

1. The H-E-B Case - 435+ Stores, 1 Million Lines, 8 Years

1.1 How It Started

H-E-B adopted Haskell around 2018. By most accounts, consultants proposed it as part of a new initiative to replace the company's largest mainframe application. What began as a single experimental project expanded over time into multiple production systems.

1.2 The Scale Today

As of July 2026, H-E-B operates roughly 1 million lines of Haskell code, maintained across several teams. That code replaces legacy mainframe functionality and drives the supply chain applications behind curbside pickup, home delivery, real-time inventory management, and in-store search. Eight years of runtime, a footprint of 435-plus stores and distribution centers, and the fact that multiple teams - not one - own the code all point to the same conclusion: this is not a side project by one enthusiastic engineer, but infrastructure that became organizationally embedded.

2. Why Haskell Is Seen as an "Academic Language"

To understand the stereotype, it helps to unpack four traits of the language.

2.1 Pure Functional Style and Controlled Side Effects

Haskell is a purely functional language. A function always returns the same output for the same input, and side effects - writing a file, making a network call, mutating state - are explicitly marked and controlled through the type system. Most mainstream languages (Python, Java, JavaScript) are imperative, letting side effects happen anywhere. That difference changes how you read code: you can tell what a function might do simply from its type. But for a developer new to the paradigm, it also means retraining how you think about a program in the first place.

2.2 A Strong Static Type System

Haskell's type system is strong and static. It catches type errors at compile time and rules out entire classes of runtime failure - null-pointer exceptions among them - by design. Advanced features like GADTs, type families, and tagless-final encodings let teams encode business rules so the compiler enforces them. That power cuts both ways: expressiveness grows, but if a team overuses these techniques, the code can become so abstract that it raises the barrier for newcomers rather than lowering it.

2.3 Lazy Evaluation

Haskell evaluates lazily by default: a value isn't computed until it's actually needed. This enables elegant abstractions like infinite lists, but it also makes memory usage harder to predict. H-E-B's own account mentions space-leak incidents that required expert-level debugging - cases where deferred computations pile up and consume far more memory than expected. That's a fascinating research topic in academia; in production, it's a real operational risk.

2.4 The Learning Curve

Combine these three traits and the learning curve gets steep. A developer used to imperative languages has to internalize side-effect-free functions, state expressed through types, and the memory model of lazy evaluation - all at once. That is the root reason Haskell is a staple of university programming-language courses yet carries an "academic-only" image in industry. Ironically, that same curve is the toll booth you must pass through to fully capture what a strong type system offers.

3. Why Enterprises Choose Haskell

3.1 Type Safety Eliminates Entire Bug Classes

The most common justification for adopting Haskell is that it reduces entire classes of runtime failure by default. Null-reference exceptions and type-confusion bugs get filtered out at compile time. H-E-B's case study cites this as a core rationale. That doesn't mean bugs disappear - it means certain categories of bugs can never enter the codebase in the first place. In a domain like supply chain, where data consistency around inventory counts, order status, and pricing is directly tied to the business, that difference compounds over time.

3.2 Safe Refactoring

Joshua Miller, who led the Haskell effort at H-E-B, describes GHC (the Haskell compiler) as giving teams the tools for painless refactoring. Change a type, and the compiler flags every location that depends on it as an error. On a multi-year legacy migration where the codebase must keep changing, the psychological safety of "it's OK to make mistakes - the compiler will catch what you missed" has a real effect on how fast a migration can move.

3.3 Concurrency

Haskell's concurrency model - lightweight threads, software transactional memory (STM), and the like - makes it comparatively safer to write parallel programs that touch shared state. Standard Chartered cites ease of writing concurrent programs, alongside strong typing, as a reason it adopted a Haskell dialect. Meta's spam-fighting system Sigma used a framework called Haxl so engineers could focus on logic rather than performance tuning while the system extracted concurrency automatically. In a system handling over a million requests per second, that property delivers real value.

3.4 Domains Where Correctness Matters

All of these reasons converge on one point: domains where correctness is directly tied to the business. In financial transactions, large-scale supply chains, or spam classification - areas where a mistake immediately costs money or trust - every bug class the type system prevents translates into a real reduction in risk. For prototypes or experimental products meant to be built fast and thrown away, that investment doesn't pay off the same way.

4. What 1M Lines, 8 Years, and Multiple Teams Actually Show

4.1 Evidence of Maintainability

Writing "Hello World" in a language and operating 1 million lines that multiple teams keep changing and extending for eight years are entirely different problems. That the latter was possible is itself strong evidence of maintainability. In particular, the fact that the system survived eight years - almost certainly outliving many of the engineers who built the original version - means the codebase didn't depend on knowledge locked in one person's head; it could be handed off to new hires.

4.2 The Reality of Onboarding and Hiring

Here the story diverges from conventional wisdom. Miller says hiring for a Haskell role has never been the problem leaders feared it would be - candidates actively sought out the position specifically because it used Haskell. That seems to contradict the well-known concern about a small Haskell talent pool, but it doesn't, really: the pool is small, but the developers inside it are actively looking for a chance to work in the language. The catch is that this only holds up when a company invests in onboarding infrastructure - internal libraries, biweekly meetups, cross-team rotation. Using Haskell doesn't automatically make hiring easy; the more accurate reading is that hiring isn't hard, but onboarding must be deliberately engineered.

4.3 There Were Failures, Too

Fairness requires naming this. H-E-B's case includes failure: two projects reportedly failed due to insufficient Haskell expertise and confusion during team transitions. That means using Haskell doesn't guarantee success automatically - without cultural commitment and real expertise on the team, the expressiveness that makes functional languages powerful can revert into complexity. Bus-factor risk is real, and it materializes unless an organization manages it deliberately.

5. The Tradeoffs of Enterprise Functional-Language Adoption

5.1 Talent Pool, Ecosystem, Build Tooling

The most concrete cost of Haskell, and functional languages generally, is a small talent pool - and the resulting need to train new hires for weeks or months. The ecosystem isn't as vast as Java's or Python's, either. That said, recent years brought maturity: the Haskell Language Server, ghcup, OpenTelemetry support, and battle-tested libraries like warp, servant, and aeson have pushed the tooling from "usable in a pinch" toward "genuinely competitive in production." Some rough edges remain - integrating with build systems like Bazel is still reported to lean heavily on nixpkgs.

5.2 Interoperability

No enterprise environment runs on a single language. You have to integrate with legacy C/C++ systems and other teams' Go or Java services. H-E-B's case actually reports this as a strength: Haskell's foreign function interface (FFI) is well suited to legacy C/C++ integration, and its strong parser libraries make handling old legacy data formats easier. But the FFI boundary is where Haskell's safety guarantees can break down. The case study reports double-free bugs tied to custom reference counting - a class of defect that can't occur in pure Haskell code, but can reappear the moment you cross the FFI boundary.

5.3 The Payoff: Reliability and Expressiveness

Despite all these costs, the reason organizations keep functional languages around is clear. Bug classes the type system rules out from the start, long-term maintainability from safe refactoring, and comparatively safer concurrent programs all compound like interest. The pattern reported across multiple cases is the same: the bigger the codebase and the team, the wider this gap grows.

6. Other Cases - Functional Adoption in Finance and Big Tech

H-E-B is unusual, but it isn't isolated. Similar choices repeat across other industries where correctness and reliability matter.

6.1 Standard Chartered's Mu

The global bank Standard Chartered built its own Haskell dialect, Mu, and uses it in the core software library that underpins its entire Markets division - a business generating billions of dollars in operating income. Typed functional programming spans the whole stack: APIs and CLIs for deal valuation and risk analysis, server components for long-running batch jobs and sub-second RESTful services, and end-user GUIs. What stands out is who uses it - not just software developers, but financial modelers and even some traders work directly in Mu. Strong typing, plus the ease of writing concurrent programs, is cited as the reason it was adopted.

6.2 Meta's Sigma

Meta (then Facebook) spent two years rewriting Sigma - its system for detecting spam, phishing, and malicious links - from an in-house language called FXL into Haskell. The system ran in production handling more than a million requests per second, with dozens of engineers working across hundreds of thousands of lines of Haskell. Through an in-house framework called Haxl, engineers could focus purely on logic while the system extracted parallelism automatically, without them worrying about performance tuning. Meta's team also improved GHC itself in the process and contributed those changes back upstream.

6.3 Jane Street and OCaml in Finance

Not Haskell, but a close relative: OCaml is used in finance for similar reasons. Trading firm Jane Street adopted OCaml as its primary development language back in 2005, and uses it for everything from research tools to trading systems, infrastructure, and accounting - safely handling billions of dollars in trades every day. Jane Street's stated rationale is strikingly similar to H-E-B's and Standard Chartered's: an expressive type system that catches bugs early, and strong static analysis that lets the firm adapt safely to fast-changing market conditions. As a side effect, Jane Street also says using OCaml has been a recruiting advantage, drawing strong engineers to the firm.

7. Which Organizations and Problems Fit Functional Programming

Lay these three cases side by side and a common pattern emerges. The conditions under which a functional language fits well look roughly like this.

  • The cost of a correctness failure is high. The more a single bug - a supply chain inventory error, a financial trade error, a missed or false spam flag - translates directly into lost money or trust, the better the type system's investment pays off.
  • The codebase has a long lifespan and keeps evolving. A short-lived script or throwaway prototype has little reason to absorb the upfront cost of a strong type system. But a system meant to survive eight years and handle billions of dollars, one that must be continuously revised, sees safe refactoring pay back as a cumulative gain.
  • The organization is willing to deliberately invest in hiring and onboarding. Like H-E-B's biweekly meetups and internal library maintenance, or Meta's investment in its own framework, the benefits of a functional language don't come for free just by adopting one - they only materialize when the organization keeps investing in onboarding and knowledge transfer. Without that commitment, you're left with H-E-B's two failed projects and nothing but added complexity.
  • Concurrency and parallelism are a core system challenge. Both the Standard Chartered and Meta cases cite the need to write concurrent programs safely as a reason for adoption. If a single thread is enough, this benefit matters far less.

Conversely, organizations in an early startup phase that pivot often and prioritize fast experiments, teams that can't absorb the constraints of a small talent pool in their hiring market, and organizations whose workloads are mostly short-lived are all more likely to find that the upfront learning-curve cost of a functional language outweighs the benefit.

8. Practical Takeaways - Conclusion

Reading the H-E-B case and jumping straight to "so we should use Haskell too" misses the point of the story. Stated honestly, here is where things stand.

Haskell, and functional languages more broadly, earned their "academic language" reputation because pure functional style, strong typing, and lazy evaluation together create a steep learning curve - and that is a real barrier, not an unfounded prejudice. At the same time, organizations that clear that barrier see type safety reduce runtime bug classes, safe refactoring improve long-term maintainability, and a strong concurrency model raise the reliability of parallel systems - a pattern H-E-B, Standard Chartered, Meta, and Jane Street all report in common.

What the numbers - 1 million lines, 8 years, multiple teams - actually prove isn't that Haskell is the best language. It's a conditional conclusion: in a domain where correctness matters and lifespans are long, if an organization is willing to invest in onboarding, the upfront cost of a functional language can be recovered. At the same time, the two failed projects prove that without those conditions, all that's left is added complexity.

There are three practical takeaways. First, diagnose your own domain honestly: is the cost of a correctness failure high, and is your codebase's lifespan long? Second, be honest about whether your organization is actually willing to invest in onboarding, internal libraries, and knowledge transfer - not just the language itself. Third, if a full rollout feels too risky, consider a localized trial: use an FFI or microservice boundary to introduce a functional language into one system where correctness matters most. Functional programming isn't a universal solution - it's the right tool under the right conditions.
