SameSite Lax·Strict·None - 어느 요청에서 쿠키가 사라지는가

결제가 끝나고 돌아왔더니 로그아웃돼 있던 이유를, 요청 유형별 판정표로

2026-07-31 개발/인프라

서론: 결제가 끝나고 돌아왔더니 로그아웃돼 있었다

사용자가 장바구니에서 결제 버튼을 누른다. 외부 결제사 화면으로 넘어가 카드 정보를 넣고 승인을 받는다. 그리고 우리 사이트로 돌아온다. 그런데 로그인이 풀려 있다. 결제는 정상으로 처리됐는데 정작 주문 내역 화면에 들어갈 수가 없다.

이런 신고는 대개 세션 만료 시간을 늘리거나, 결제사에 문의하거나, 재현이 안 된다는 이유로 조용히 닫힌다. 그런데 서버 로그를 보면 답이 이미 나와 있는 경우가 많다. 돌아온 요청의 Cookie 헤더에 세션 이름이 아예 없다. 인증이 실패한 것이 아니라 쿠키가 애초에 실려 오지 않았다.

쿠키를 보낼지 말지 결정하는 것은 서버가 아니라 클라이언트다. 그 결정에 쓰이는 속성이 SameSite이고 값은 셋뿐이다. 그런데 이 세 값은 「강하다·중간이다·약하다」의 일직선이 아니다. 요청의 종류마다 다르게 갈린다.

  • Strict는 다른 사이트에서 시작된 요청에 무조건 안 붙는다. 사용자가 직접 링크를 눌러 들어와도 안 붙는다
  • Lax는 주소창이 바뀌는 이동이면서 안전한 메서드일 때만 예외로 붙인다. 이 두 조건이 이 글의 핵심이다
  • None은 전부 붙인다. 대신 Secure가 없으면 쿠키가 저장조차 되지 않는다

이 글은 「그럼 None으로 바꾸세요」로 끝내지 않는다. 그것은 원인을 안 보고 문을 열어 두는 일이다. 대신 어떤 요청에서 이 쿠키가 붙어야 하는지 먼저 목록으로 적는 절차를 만든다. 목록이 정해지면 값은 저절로 결정된다.

실행 환경. 아래 출력은 Windows 10 Pro (10.0.19045)에서 Node.js v22.16.0 (win32)로 실제 실행한 결과다. 로컬 서버 두 대를 임의 고번호 포트(18081, 18082)에 띄워 확인했고 실험이 끝난 뒤 모두 종료했다. 규격 근거는 RFC 6265bis(draft-ietf-httpbis-rfc6265bis-22, 2025-12-01)와 MDN이다. 스크립트는 셸 인자나 히어독이 아니라 전부 파일로 저장해 실행했다.

★이 글이 직접 확인하지 못한 것. 브라우저를 띄워 쿠키 저장소를 관찰하지는 않았다. 그래서 「이 요청에 쿠키가 붙는다·안 붙는다」는 판정은 규격 문언을 코드로 구현해 계산한 값이고, 실제 브라우저 동작을 관측한 값이 아니다. 아래 표에서 어느 줄이 규격 근거이고 어느 줄이 실측인지 열을 따로 만들어 표시했다. 도입 전에 대상 브라우저로 재확인할 것을 권한다.

이 글이 다루지 않는 것. 웹 보안 일반론과 CSRF 대책 전반은 웹 보안 기초와 IDS·IPS에서 다뤘다. 여기서는 SameSite 값의 동작 한 점만 파고든다. 등장하는 도메인·포트·쿠키 이름은 전부 가상이다.

1. 세 값이 실제로 무엇을 가르는가

규격의 문장은 짧다. RFC 6265bis는 Strict를 「같은 사이트 요청에만 보낸다」, Lax를 「같은 사이트 요청과, 교차 사이트 최상위 탐색에 보낸다」, None을 「같은 사이트와 교차 사이트 요청 모두에 보낸다」로 정의한다. 문제는 이 세 문장만으로는 내 페이지의 어떤 요소가 어디에 해당하는지 알 수 없다는 것이다. 이미지 태그는 최상위 탐색인가? form 제출은? iframe은?

그래서 규격의 판정 규칙을 그대로 코드로 옮기고, 페이지가 만들어 낼 수 있는 요청 형태를 전부 통과시켰다.

node v22.16.0 / win32
cookie set by https://app.example.com , request initiated from https://portal.other-site.com

cross-site link click             no       YES      YES      YES

  Lax-allowing-unsafe window: only for cookies with NO explicit SameSite,
  and only while very young. treat it as absent, never as a feature.

표를 세로로 읽으면 「None이 제일 관대하다」밖에 안 보인다. 가로로 읽어야 쓸모가 생긴다. 각 값이 어디서 갈리는지만 따로 뽑았다.

--- 3-2. the same table, but only the differences that matter ---
  shapes where Strict and Lax disagree:
    - cross-site link click
    - cross-site form GET
    - cross-site 302 landing as GET
  shapes where Lax and None disagree:
    - cross-site image load
    - cross-site script/css load
    - cross-site form POST
    - cross-site fetch / XHR
    - cross-site iframe load
    - cross-site 307 landing as POST
  • Strict와 Lax가 갈리는 곳은 세 줄뿐이다. 링크 클릭, form GET, 그리고 302로 돌아와 GET으로 착지하는 경우. 셋 다 주소창이 바뀌는 이동이라는 공통점이 있다
  • Lax와 None이 갈리는 곳은 나머지 전부다. 이미지, 스크립트, fetch, iframe, 그리고 POST
  • 즉 Lax는 「부속 자원에는 안 붙는다」로 요약된다. 남의 페이지가 우리 서버의 이미지를 불러도 우리 세션은 실리지 않는다. 이것이 Lax가 기본값이 된 이유이기도 하다
  • 같은 사이트 안에서는 세 값이 전부 동일하게 동작한다. 그래서 자기 사이트만 눌러 보는 테스트로는 차이가 영원히 드러나지 않는다

1.1 이 표에서 무엇이 실측이고 무엇이 문서인가

여기서 정직하게 구분해야 한다. 이 글은 브라우저를 띄워 쿠키 저장소를 직접 관찰하지 않았다. 위 판정은 규격 문언을 코드로 옮겨 계산한 값이다. 반면 서버가 실제로 무엇을 내보내고 무엇을 받는지, 그리고 리다이렉트가 메서드를 바꾸는지는 로컬 서버 두 대를 띄워 직접 측정했다. 그 구분을 표의 마지막 열에 적었다.

요청 유형StrictLaxNone+Secure값 없음이 줄의 근거
같은 사이트 안에서 페이지 이동붙음붙음붙음붙음규격
다른 사이트에서 링크 클릭안 붙음붙음붙음붙음규격

다른 사이트가 스크립트·CSS 로드안 붙음안 붙음붙음안 붙음규격

마지막 두 줄만 「규격 + 실측」이다. 리다이렉트가 메서드를 바꾸는지 아닌지는 이 기계에서 HTTP로 직접 측정했고 그 출력이 6절에 있다. 나머지 줄의 판정은 규격 해석이므로, 구현마다 다를 수 있다는 전제로 대상 브라우저에서 확인하는 편이 안전하다.

2. 값을 안 적으면 무엇이 되나

가장 흔한 사고가 여기서 시작된다. SameSite를 아예 안 적은 쿠키는 「제한 없음」이 아니다. RFC 6265bis는 속성이 없거나 값을 알아볼 수 없을 때 「Lax에 해당하는 기본 시행 모드」를 적용한다고 적는다. MDN도 「SameSite 속성이 설정되지 않으면 쿠키는 기본적으로 Lax로 취급된다」로 같은 말을 한다.

그래서 코드를 한 줄도 안 고쳤는데 어느 날 결제 복귀가 깨지는 일이 벌어진다. 서버 쪽은 그대로인데 그 쿠키를 해석하는 쪽의 기본 정책이 달라졌기 때문이다. 값을 안 적는 것은 결정을 안 한 것이 아니라 결정을 남에게 맡긴 것이다.

더 나쁜 것은 적었는데 안 적힌 경우다. 값에 오타가 나면 어떻게 되는지 파서를 만들어 확인했다.

--- 2-3. the silent-typo trap, side by side ---
  SameSite=Strict     -> Strict
  SameSite=strict     -> Strict
  SameSite=Strick     -> Default(Lax)   <- NOT what the author typed
  Samesite=Strict     -> Strict
  SameSite =Strict    -> Strict
  • SameSite=Strick은 오류가 아니다. 알아볼 수 없는 값이므로 기본 시행 모드, 즉 Lax로 조용히 떨어진다
  • 반면 속성 이름의 대소문자와 등호 주변 공백은 무해하다. Samesite도 SameSite =Strict도 정상 처리된다
  • 즉 위험한 것은 값의 오타 하나뿐이고, 그것만이 아무 경고 없이 정책을 바꾼다
  • 그래서 값 문자열을 상수로 두고 코드 리뷰에서 눈으로 확인하는 것이 실질적인 방어가 된다. 문법 검사기는 이 오타를 잡아 주지 않는다

기본값에는 조건이 하나 더 붙는다. 규격은 「Lax-allowing-unsafe」라는 선택적 호환 모드를 허용한다. 명시적으로 SameSite를 적지 않은 쿠키에 한해, 아주 최근에 만들어진 경우에는 교차 사이트 POST에도 붙일 수 있다는 것이다. 규격은 「2분 이하가 합리적인 한계로 보인다」고 적는다.

--- 3-3. the 2-minute window applied to a cross-site POST ---
  cookie age   10s  ->  maybe*   (explicit Lax would be: no)
  cookie age  119s  ->  maybe*   (explicit Lax would be: no)
  cookie age  121s  ->  no   (explicit Lax would be: no)
  cookie age 3600s  ->  no   (explicit Lax would be: no)
  a cookie that works in testing and fails in production may simply be older.

이것이 「제 컴퓨터에서는 되는데요」의 정체인 경우가 많다. 개발자는 로그인하고 곧바로 결제를 눌러 본다. 쿠키가 갓 만들어진 상태다. 실제 사용자는 로그인해 둔 채 한참 뒤에 결제한다. 같은 코드가 시간에 따라 다르게 동작하는 것처럼 보인다. 이 모드는 선택 사항이므로 되면 다행인 것이지 설계의 근거로 삼을 수 없다.

3. None을 쓰면서 Secure를 빼면 쿠키가 버려진다

증상만 보고 SameSite=None으로 바꾸는 대응이 흔하다. 그런데 여기에 함정이 있고, 이 함정은 아무 오류도 내지 않는다. RFC 6265bis의 저장 알고리즘에 이런 문장이 있다. 쿠키의 same-site 플래그가 None이면, secure-only 플래그가 참이 아닌 한 알고리즘을 중단하고 쿠키를 통째로 무시한다.

서버가 그 헤더를 실제로 내보내는지, 그리고 그때 응답이 어떻게 보이는지 직접 확인했다.

node v22.16.0 / win32   server 127.0.0.1:18081

--- 7-1. server emits it, the jar decides ---
recipe             HTTP status   what left the server                    jar verdict
-----------------------------------------------------------------------------------------------
None, no Secure    200 OK        sid=abc; SameSite=None                  REJECTED  (None without Secure)
None + Secure      200 OK        sid=abc; SameSite=None; Secure          stored  (None + Secure)
Lax, no Secure     200 OK        sid=abc; SameSite=Lax                   stored  (Lax)
Strict + Secure    200 OK        sid=abc; SameSite=Strict; Secure        stored  (Strict + Secure)
none + secure      200 OK        sid=abc; samesite=none; secure          stored  (None + Secure)
None; Secure=1     200 OK        sid=abc; SameSite=None; Secure=1        stored  (None + Secure)

  every row returned 200. the server never objects.
  row 1 is thrown away before it is ever stored, so no request will carry it.
  row 6 shows Secure is a valueless flag: Secure=1 still reads as present.

여섯 줄 전부 200 OK다. 서버는 이 조합에 아무 불만이 없다. 서버가 하는 일은 문자열을 헤더에 실어 보내는 것뿐이고, 버릴지 말지의 판정은 반대편에서 일어난다.

--- 7-2. the failure you will actually observe ---
  HTTP/1.1 200 OK
  Set-Cookie: sid=abc; SameSite=None
  Date: Thu, 30 Jul 2026 20:33:11 GMT
  Connection: close
  Content-Length: 3

  response looks perfect. no 4xx, no log line, no exception.
  the symptom surfaces one request later, as a missing session,
  in a completely different part of the code. that is why it costs a day.

--- 7-3. why the rule exists, in one line ---
  SameSite=None means: send me on requests I did not initiate.
  Secure means: only over a protected transport.
  the spec refuses to let a cookie be maximally exposed and unprotected at once.
  • 실패가 응답에 나타나지 않는다. 상태 코드는 200이고, 로그에도 예외에도 아무것도 남지 않는다
  • 증상은 한 요청 뒤에, 전혀 다른 코드 구역에서 「세션 없음」으로 나타난다. 그래서 원인 추적이 하루를 잡아먹는다
  • Secure는 값이 없는 표식이다. 위 다섯째·여섯째 줄처럼 소문자로 적든 Secure=1처럼 값을 붙이든 「있음」으로 읽힌다
  • 규칙 자체는 단순한 논리다. None은 「내가 시작하지 않은 요청에도 나를 보내라」는 뜻이고 Secure는 「보호된 전송로에서만」이라는 뜻이므로, 규격은 가장 넓게 노출되면서 보호는 없는 상태를 허용하지 않는다

실무에서는 순서가 중요하다. None은 https가 전제다. 사내 도구가 아직 평문으로 서비스되고 있다면 None은 선택지가 아니라 먼저 해결해야 할 선행 조건이다. 그리고 __Host- 접두사를 쓰면 Secure와 Path=/, Domain 미지정을 강제할 수 있어 실수를 구조적으로 막는다.

4. Set-Cookie 문자열은 어떻게 읽히나

Set-Cookie 한 줄이 어떻게 해석되는지 알면 위의 함정들이 왜 조용한지 이해된다. 규격의 파싱 절차를 그대로 구현해 열 가지 문자열을 통과시켰다.

node v22.16.0 / win32

--- 2-1. parsing ten Set-Cookie strings ---
input                                                              -> SameSite      Secure  note
---------------------------------------------------------------------------------------------------------
[sid=abc123; Path=/; HttpOnly; SameSite=Lax]                       -> Lax           false
[sid=abc123; path=/; httponly; samesite=lAx]                       -> Lax           false
[sid=abc123;SameSite=Strict;Path=/]                                -> Strict        false
[sid=abc123;    SameSite   =   None   ;   Secure  ]                -> None          true
[sid=abc123; SameSite=None]                                        -> None          false   DISCARDED (None without Secure)
[sid=abc123; SameSite=Loose; Path=/]                               -> Default(Lax)  false
[sid=abc123; SameSite; Path=/]                                     -> Default(Lax)  false
[sid=abc123; SameSite=Strict; SameSite=None; Secure]               -> None          true
[sid=abc123; Path=/; Flavour=vanilla; Priority=High; SameSite=Lax] -> Lax           false   ignored attrs: Flavour=vanilla, Priority=High
[sid=; Path=/; Max-Age=0]                                          -> Default(Lax)  false

--- 2-2. what the parser proved ---
  case of attribute name and value is irrelevant : true
  attribute order is irrelevant                  : true
  surrounding whitespace is stripped             : true
  unknown attribute drops the ATTRIBUTE only     : true  (ignored: Flavour=vanilla)
  duplicate attribute: last one wins             : None
  typo in the VALUE is not an error, it degrades : Default(Lax)   <- raw was [Loose]
  • 속성 이름은 대소문자를 가리지 않는다. 규격이 직접 「CamelCase로 표기했지만 어떤 대소문자도 받아들인다」고 적는다
  • 순서는 무관하다. Secure를 앞에 쓰든 뒤에 쓰든 결과가 같다
  • 공백은 제거된다. 이름과 값의 앞뒤 공백을 떼어 내는 것이 절차에 명시돼 있다
  • 모르는 속성은 그 속성만 버린다. Flavour=vanilla 같은 것이 섞여도 쿠키 자체는 살아남는다. 그래서 새 속성이 표준에 추가돼도 옛 클라이언트가 깨지지 않는다
  • 같은 속성이 두 번 나오면 마지막이 이긴다. 여덟째 줄은 Strict가 먼저 나왔는데 결과가 None이다. 미들웨어 두 곳이 같은 쿠키를 건드릴 때 여기서 사고가 난다
  • 알아볼 수 없는 값은 오류가 아니라 강등이다. 여섯째와 일곱째 줄이 그것이고, 2절의 오타 함정이 여기서 나온다

마지막 줄도 눈여겨볼 만하다. sid=; Max-Age=0은 쿠키를 지우는 관용적인 방법인데, 이때도 SameSite가 기본값으로 떨어진다. 삭제용 Set-Cookie에 원래 쿠키와 같은 속성 조합을 맞춰 주지 않으면 삭제가 먹지 않는 현상이 여기서 생긴다. 로그아웃이 안 되는 버그의 흔한 원인이다.

5. Domain·Path, 그리고 「사이트」의 기준

SameSite만 보면 반쪽이다. 어떤 요청에 쿠키가 붙을지는 세 개의 필터를 모두 통과해야 정해진다. 도메인이 맞아야 하고, 경로가 맞아야 하고, 그다음에 SameSite 판정이 온다. 앞의 둘을 먼저 확인했다.

node v22.16.0 / win32

--- 5-1. host-only cookie vs Domain cookie ---
request host              no Domain attr   Domain=example.com
---------------------------------------------------------------
example.com               true             true
www.example.com           false            true
api.a.example.com         false            true
notexample.com            false            false
example.com.evil.net      false            false
  omitting Domain is the TIGHTER setting. adding it widens the blast radius.

--- 5-2. Path matching ---
Path=/app   request path        match
------------------------------------------
            /app                true
            /app/               true
            /app/orders         true
            /application        false
            /                   false
            /x/app              false
  /application does not match /app. the boundary is a slash, not a prefix.
  • Domain을 생략하는 쪽이 더 좁다. 생략하면 쿠키를 내려준 호스트에만 간다. 「기본값이 느슨하겠지」라는 직관과 정확히 반대다
  • Domain=example.com을 적으면 모든 서브도메인에 간다. api.a.example.com처럼 몇 단계 아래여도 마찬가지다
  • 비슷한 이름은 안 걸린다. notexample.com도 example.com.evil.net도 매칭되지 않는다. 접미사 비교 앞에 점 경계가 있어야 하기 때문이다
  • Path의 경계는 슬래시다. Path=/app은 /application에 매칭되지 않는다. 다만 MDN이 못박듯 Path는 보안 장치가 아니다

그리고 「사이트」라는 단어가 문제다. 일상어로는 「우리 서비스」쯤이지만 여기서는 스킴 + 등록 가능 도메인이라는 정확한 뜻이 있다. 흔히 같이 쓰는 「출처(origin)」와 다르다.

--- 5-4. what "same site" actually compares ---
A                              B                              same site?
---------------------------------------------------------------------------
https://app.example.com/       https://api.example.com/       YES
https://app.example.com/       https://example.com/           YES
https://app.example.com:443/   https://app.example.com:8443/  YES
https://app.example.com/       http://app.example.com/        no
https://app.example.com/       https://app.example.net/       no
https://shop.example.co.kr/    https://pay.example.co.kr/     YES
https://a.github.io/           https://b.github.io/           no
http://localhost:18081/        http://localhost:18082/        YES
http://localhost:18081/        http://127.0.0.1:18082/        no

--- 5-5. site vs origin, side by side ---
  URL    : https://app.example.com:8443/orders?x=1
  origin : https://app.example.com:8443        <- scheme + host + PORT
  site   : https://example.com     <- scheme + registrable domain, no port
  these two words are not interchangeable, and cookies use the second one.
  • 포트가 달라도 같은 사이트다. 쿠키는 출처 단위가 아니다. 8443에 띄운 개발 서버가 운영과 쿠키를 공유해 버리는 것이 이 때문이다
  • 스킴이 다르면 다른 사이트다. http와 https가 갈린다
  • 공개 접미사 아래에서는 한 칸이 더 붙는다. shop.example.co.kr과 pay.example.co.kr은 같은 사이트지만, a.github.io와 b.github.io는 다른 사이트다. 정적 페이지 호스팅에서 서로의 쿠키를 못 읽는 이유가 이것이다
  • localhost와 127.0.0.1은 다른 사이트다. 로컬에서 교차 사이트를 흉내 낼 때 이 둘을 섞으면 의도치 않게 교차 사이트가 되고, 반대로 포트만 바꾸면 교차 사이트 재현에 실패한다

설계에 미치는 영향이 하나 있다. 서브도메인을 나누는 것은 SameSite 관점에서 아무 격리도 만들지 않는다. 결제 도메인을 따로 떼어 놓아도 같은 등록 가능 도메인 아래라면 여전히 같은 사이트이고, 그 사이의 이동에는 Strict 쿠키까지 그대로 붙는다. 격리를 원한다면 도메인 자체를 분리하거나 Domain 속성을 걷어내는 쪽을 봐야 한다.

6. 로그인이 풀리는 경로를 단계별로

이제 서론의 증상으로 돌아간다. 외부 결제사나 인증 제공자로 나갔다가 돌아오는 흐름에서 정확히 어느 지점에서 쿠키가 사라지는지가 핵심이다. 갈림길은 딱 하나, 돌아올 때의 메서드다.

이 부분은 규칙이 아니라 실측이다. 로컬에 서버 두 대를 띄워 한쪽이 다른 쪽으로 리다이렉트하게 만들고, POST로 나갔을 때 어떤 메서드로 착지하는지 상태 코드별로 측정했다.

node v22.16.0 / win32
provider 127.0.0.1:18082  ->  app 127.0.0.1:18081/return

--- 4-1. we POST to the provider; it redirects us back. which method lands? ---
redirect status   we sent   we landed with   Lax cookie would ride?
---------------------------------------------------------------------------
301               POST      GET              yes - safe method
302               POST      GET              yes - safe method
303               POST      GET              yes - safe method
307               POST      POST             NO  - unsafe method
308               POST      POST             NO  - unsafe method

  measured with an HTTP client on this machine, not with a browser.
  the method rewrite on 301/302/303 is the whole ballgame:
  307 and 308 preserve POST, and a Lax cookie is withheld on arrival.
  • 301·302·303은 메서드를 GET으로 바꿔 착지시킨다. 그러면 Lax의 두 조건(최상위 이동 + 안전한 메서드)을 모두 만족해 쿠키가 붙는다
  • 307·308은 POST를 그대로 유지한다. 착지 요청이 교차 사이트 POST가 되고, Lax에서는 쿠키가 안 붙는다
  • 이 차이는 우리 코드가 아니라 상대 설정 화면의 숫자 하나다. 우리 쪽이 그대로여도 상대가 바꾸면 증상이 생겼다 사라진다
  • Strict라면 메서드와 무관하게 안 붙는다. 302로 GET 착지해도 마찬가지다
  • form을 자동 제출해 결과를 POST로 돌려주는 방식도 결과가 같다. 겉모습이 리다이렉트가 아닐 뿐 교차 사이트 POST라는 점이 변하지 않는다
--- 4-2. the redirect chain, step by step ---
  step 1  POST http://127.0.0.1:18082/go?code=307
          <- 307 Location: http://127.0.0.1:18081/return?via=307
  step 2  the client repeats the request at the new URL
          this second request is cross-site AND it is a POST
          -> Strict: withheld.  Lax: withheld.  None+Secure: sent.

--- 4-3. same chain, but the provider returns us with 303 ---
  landed method : GET   (the body was dropped)
  -> Strict: still withheld (cross-site).  Lax: sent.  None+Secure: sent.
  one number in the provider config moves the session between present and absent.

--- 4-4. and the second hop, once we are back on our own site ---
  same-site GET landed with method GET
  this is why the bug looks intermittent: reload the page after landing
  and the next request IS same-site, so Strict starts working again.

6.1 여섯 단계로 끊어 보기

  1. 사용자가 우리 사이트에서 결제 버튼을 누른다. 여기까지는 전부 같은 사이트이고 세 값 모두 정상 동작한다
  2. 결제사 도메인으로 이동한다. 이 구간에 우리 쿠키는 관여하지 않는다
  3. 결제사가 승인 결과를 우리 복귀 URL로 되돌린다. 이 요청이 교차 사이트다
  4. 되돌리는 방식이 GET이면 Lax 쿠키가 붙어 로그인 상태가 유지된다
  5. 되돌리는 방식이 POST면 Lax 쿠키가 안 붙는다. 서버는 비로그인 사용자의 요청으로 보고 로그인 화면을 띄운다
  6. 사용자가 그 화면에서 뭔가를 누르면 그때부터는 같은 사이트라 쿠키가 다시 붙는다. 그래서 「새로고침하니 되던데요」라는 보고가 따라붙고, 재현 실패로 티켓이 닫힌다

대응 순서도 여기서 나온다. 값을 None으로 낮추는 것은 마지막 수단이다. 먼저 복귀 지점을 GET으로 받는 얇은 엔드포인트로 바꾸는 것을 검토한다. 결제 결과 본문이 필요하면 그 본문은 서버 대 서버 통지로 받고, 사용자의 브라우저는 GET으로만 돌려보내면 된다. 이러면 쿠키 정책을 넓히지 않고도 증상이 사라진다.

7. 크기와 개수, 천장은 두 개다

세션이 사라지는 또 다른 경로가 있다. 쿠키가 너무 커서 저장되지 않는 것이다. 규격의 문장은 명확하다. 이름과 값의 길이 합이 4096 옥텟을 넘으면 알고리즘을 중단하고 Set-Cookie 문자열을 통째로 무시한다.

node v22.16.0 / win32
max HTTP header size this runtime accepts: 16384 bytes

--- 6-1. the 4096-octet line, name + value together ---
name len   value len   sum     jar keeps it?
-----------------------------------------------
3          4093        4096    true
3          4094        4097    false
3          4095        4098    false
500        3596        4096    true
500        3597        4097    false
  the limit counts the NAME too. renaming session_identifier to sid buys you bytes.

--- 6-2. an oversized cookie is dropped whole, not truncated ---
  value length          : 5000
  jar keeps it          : false
  what the app receives : nothing at all
  no error, no warning, no half-value. the next request simply has no session.
  • 이름도 길이에 포함된다. session_identifier를 sid로 줄이면 값에 쓸 수 있는 바이트가 그만큼 늘어난다
  • 잘리지 않고 통째로 버려진다. 앞부분만 남는 것이 아니라 아예 없는 것이 된다
  • 그래서 증상이 「값이 이상하다」가 아니라 「쿠키가 없다」로 나타난다. 크기를 의심하기까지 시간이 걸리는 이유가 이것이다
  • 한글이나 이모지가 들어가면 계산이 또 달라진다. 옥텟 단위이므로 글자 수가 아니라 인코딩 후 바이트 수를 세야 한다

천장은 하나가 아니다. 쿠키 저장소의 한계 위에 HTTP 헤더 크기라는 별개의 한계가 있다. 이쪽은 실제 서버에 부딪혀 봤다.

--- 6-3. many cookies at once, measured against a real server ---
count   Cookie header bytes   server response
-------------------------------------------------------
10      856                   200 OK  cookies=10 bytes=848
50      4296                  200 OK  cookies=50 bytes=4288
100     8596                  200 OK  cookies=100 bytes=8588
180     15556                 200 OK  cookies=180 bytes=15548
300     25996                 431 Request Header Fields Too Large
  past the runtime header budget the request dies before your code runs.
  the cookie jar has its own per-domain cap on top of this. two ceilings, not one.

--- 6-4. every cookie rides on EVERY matching request ---
  one 1.2 KB cookie             : 1204 bytes per request
  60 requests to render a page  : 72240 bytes uploaded, per page view
  and Domain=example.com sends it to the image host and the API host too.
  this is the real argument for keeping an identifier in the cookie and state on the server.

180개(15,556바이트)까지는 통과했고 300개(25,996바이트)에서 431이 돌아왔다. 여기서 중요한 것은 애플리케이션 코드가 실행되지 않았다는 점이다. 우리 로그도, 우리 예외 처리도, 우리 오류 페이지도 나오지 않는다. 그래서 「특정 사용자만 사이트 전체가 안 된다」는 신고가 되고, 그 사용자의 쿠키를 지우면 낫는다. MDN이 「쿠키는 모든 요청과 함께 전송되므로 성능을 떨어뜨릴 수 있다」고 적은 것이 바로 이 이야기다.

8. 서버는 왜 이유를 알 수 없나

진단이 어려운 데에는 구조적인 이유가 있다. 서버가 보내는 것과 받는 것이 대칭이 아니다.

node v22.16.0 / win32
server A 127.0.0.1:18081   server B 127.0.0.1:18082

--- 1-1. exact Set-Cookie bytes the server puts on the wire ---
recipe            Set-Cookie line as received
---------------------------------------------------------------------------
no-attr          Set-Cookie: sid=abc123; Path=/; HttpOnly
lax-explicit     Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Lax
strict           Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Strict
none-no-secure   Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None
none-secure      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=None; Secure
bogus-value      Set-Cookie: sid=abc123; Path=/; HttpOnly; SameSite=Loose
weird-case       Set-Cookie: sid=abc123; path=/; httponly; samesite=lAx

--- 1-3. what the server sees when a client sends a Cookie header ---
  with Cookie header : cookie-header-seen: sid=abc123; theme=dark
  without            : cookie-header-seen: (none)
  the server cannot tell WHY a cookie is missing. absent == never-sent == blocked.

--- 1-4. no SameSite attribute survives into the Cookie header ---
  cookie-header-seen: sid=abc123
  Cookie: carries name=value only. no Path, no Domain, no SameSite.
  the server gets no evidence of which policy was applied.
  • Set-Cookie에는 속성이 전부 실린다. Path, HttpOnly, SameSite까지 그대로 나간다
  • 돌아오는 Cookie 헤더에는 이름과 값만 있다. 어떤 정책으로 저장됐는지에 대한 정보가 하나도 없다
  • 그래서 서버는 쿠키가 없는 이유를 구별할 수 없다. 로그아웃한 사용자인지, SameSite에 막힌 것인지, 크기 초과로 저장이 안 된 것인지, 사용자가 직접 지운 것인지가 전부 같은 모양이다
  • 결국 요청 쪽 정보로 추정할 수밖에 없다. Origin과 Referer로 어디서 왔는지, 메서드가 무엇인지 확인하고, 그 조합이 우리 정책에서 쿠키를 허용하는지 1절 표와 대조하는 것이다

그래서 실용적인 대책은 로그다. 세션 없이 도착한 요청에 대해 메서드·Origin·Referer를 함께 기록해 두면, 판정표와 대조하는 것만으로 원인이 크게 좁혀진다. 이 로그 한 줄이 없으면 재현 시도에 며칠을 쓰게 된다.

9. 무엇을 어디에 담고, 값을 어떻게 고를 것인가

여기까지 오면 질문이 바뀐다. 「어느 값이 좋은가」가 아니라 「무엇을 쿠키에 담을 것인가」가 먼저다.

원칙은 두 줄이다. 쿠키에는 식별자만 담는다. 상태는 서버에 둔다. 7절의 두 천장이 그 근거이고, 그렇게 하면 크기 문제와 대역폭 문제가 동시에 사라진다. 그다음 그 식별자가 어떤 요청에 실려야 하는지를 목록으로 적으면, 값은 목록에서 자동으로 나온다.

쿠키에 담긴 것교차 사이트에서 필요한가권장 값함께 붙일 것
로그인 세션 식별자 (일반 웹앱)아니오LaxSecure HttpOnly Path=/
로그인 세션 + 외부 결제·OAuth 복귀복귀 지점만Lax + 복귀를 GET으로Secure HttpOnly
관리자 콘솔·내부 도구아니오StrictSecure HttpOnly __Host- 접두사
CSRF 토큰 (이중 제출용)아니오Strict 또는 LaxSecure, HttpOnly 없음
타사 페이지에 심는 위젯·SSO iframe예NoneSecure 필수 + Partitioned 검토
광고·분석 식별자예NoneSecure, 차단을 전제로 설계
언어·테마 같은 화면 설정아니오LaxSecure, 로컬 저장소도 검토
  1. 이 쿠키가 다른 사이트에서 시작된 요청에 붙어야 하는 경우를 전부 적는다. 없으면 없다고 적는다
  2. 목록이 비어 있으면 Lax를 쓴다. 최상위 이동에서도 필요 없다고 확신하면 Strict로 좁힌다
  3. 목록이 비어 있지 않을 때만 None을 쓰고, 그때는 Secure를 함께 적는다. 그리고 그 목록을 주석이나 문서에 남긴다. 다음 사람이 이유를 몰라 다시 넓히는 일을 막는다

마지막으로 선을 분명히 긋는다. SameSite는 CSRF 완화 장치이지 CSRF 대책 전부가 아니다. MDN도 「교차 사이트 요청 위조 공격에 대해 어느 정도의 보호를 제공한다」고 적지 해결한다고 적지 않는다. 값이 무엇이든 상태를 바꾸는 요청에는 별도의 토큰 검증이 있어야 한다. 웹 보안 전반의 얼개는 웹 보안 기초에, 탐지 계층은 IDS·IPS에 정리해 뒀다.

값한 줄 정의대표 증상
Strict같은 사이트 요청에만 붙는다외부 링크로 들어온 첫 화면이 로그아웃 상태
Lax같은 사이트 + 최상위 이동의 안전한 메서드결제·OAuth가 POST로 돌려보내면 세션 증발
None모든 요청에 붙는다Secure를 빼면 쿠키 자체가 저장되지 않음
(값 없음)Lax와 같게 취급된다「코드를 안 건드렸는데 어느 날 깨졌다」

표의 「대표 증상」 열이 실전에서 가장 쓸모 있다. 증상을 먼저 보고 값을 역추적하는 것이, 값을 바꿔 가며 배포해 시험하는 것보다 훨씬 빠르다.

10. 점검 목록

  • 세션 쿠키의 SameSite 값을 명시했다 (기본값에 기대지 않는다)
  • None을 쓴 쿠키에 Secure가 붙어 있다
  • None을 쓴 이유를 요청 목록으로 적을 수 있다
  • 외부 결제·OAuth 복귀 지점의 상태 코드와 메서드를 확인했다
  • 복귀 지점이 POST라면 얇은 GET 엔드포인트를 따로 뒀다
  • Domain 속성을 정말 필요할 때만 붙였다 (생략이 더 좁다)
  • 서브도메인이 같은 사이트로 묶인다는 것을 설계에 반영했다
  • 로컬 테스트에서 localhost와 127.0.0.1을 의도 없이 섞지 않았다
  • 쿠키 하나의 이름+값이 4096 옥텟 미만이다
  • 도메인당 쿠키 개수와 총 바이트를 실제로 재 봤다
  • SameSite 값 문자열에 오타가 없다 (오타는 조용히 기본값이 된다)
  • 세션 없이 도착한 요청의 메서드·Origin·Referer를 로그에 남긴다

11. 오해와 하지 말 것

  • ❌ 증상이 보이자마자 None으로 바꾸는 것 — 어느 요청에서 필요한지부터 목록으로 정한다
  • ❌ None을 쓰면서 Secure를 빠뜨리는 것 — 쿠키가 저장 단계에서 버려진다
  • ❌ 기본값에 의존하는 것 — 명시하지 않은 쿠키는 해석하는 쪽의 기본 정책을 따라간다
  • ❌ localhost에서만 확인하고 끝내는 것 — 포트만 바꾼 로컬 환경은 교차 사이트 조건을 재현하지 못한다
  • ❌ 서브도메인 분리로 격리했다고 믿는 것 — 같은 등록 가능 도메인 아래는 같은 사이트다
  • ❌ SameSite를 CSRF 대책 전부로 취급하는 것 — 완화 장치이지 방어의 전부가 아니다
  • ❌ 세션 상태를 쿠키 안에 통째로 넣는 것 — 4096 옥텟 상한과 매 요청 대역폭을 함께 태운다

마지막으로 한 가지. 브라우저 버전별 동작을 단정하지 말자. 기본값의 적용 범위, 「Lax-allowing-unsafe」의 채택 여부, 분할 저장소의 처리는 구현마다 다를 수 있고 시간이 지나며 바뀐다. 규격은 무엇이 허용되는지를 정할 뿐 모든 구현이 똑같이 동작한다고 보장하지 않는다. 도입 전에 대상 브라우저로 직접 확인하는 절차를 넣는 것이 유일하게 늙지 않는 대책이다.

# SameSite 쿠키 — 값 선택 판단표와 요청 유형별 판정표

> 출처: braindetox.kr — SameSite Lax·Strict·None, 어느 요청에서 쿠키가 사라지는가
> 근거: RFC 6265bis (draft-ietf-httpbis-rfc6265bis-22, 2025-12-01) + MDN
> 실행: Windows 10 Pro 10.0.19045 / Node.js v22.16.0 (win32) / 로컬 서버 2대
> **한계 고지**: 브라우저 쿠키 저장소의 실제 동작은 이 문서에서 직접 확인하지 않았다.
> 아래 판정 칸은 **규격 문언을 코드로 구현해 계산한 값**이다. 도입 전 대상 브라우저로 재확인할 것.

## 1. 요청 유형별 판정표

쿠키를 심은 곳: `https://app.example.com`
요청을 시작한 곳: `https://portal.other-site.com`

| 요청 유형 | Strict | Lax | None+Secure | 값 없음 | 근거 |
|---|---|---|---|---|---|
| 같은 사이트 안에서 페이지 이동 | 붙음 | 붙음 | 붙음 | 붙음 | 규격 |
| 다른 사이트에서 링크 클릭 | **안 붙음** | 붙음 | 붙음 | 붙음 | 규격 |
| 다른 사이트가 이미지 로드 | 안 붙음 | 안 붙음 | 붙음 | 안 붙음 | 규격 |
| 다른 사이트가 스크립트·CSS 로드 | 안 붙음 | 안 붙음 | 붙음 | 안 붙음 | 규격 |
| 다른 사이트에서 form GET | **안 붙음** | 붙음 | 붙음 | 붙음 | 규격 |
| 다른 사이트에서 form POST | 안 붙음 | **안 붙음** | 붙음 | 안 붙음 | 규격 |
| 다른 사이트에서 fetch·XHR | 안 붙음 | 안 붙음 | 붙음 | 안 붙음 | 규격 |
| iframe 안에서 로드 | 안 붙음 | 안 붙음 | 붙음 | 안 붙음 | 규격 |
| 같은 사이트 fetch | 붙음 | 붙음 | 붙음 | 붙음 | 규격 |
| 302로 돌아와 GET으로 착지 | **안 붙음** | 붙음 | 붙음 | 붙음 | 규격 + 착지 메서드 실측 |
| 307로 돌아와 POST로 착지 | 안 붙음 | **안 붙음** | 붙음 | 안 붙음 | 규격 + 착지 메서드 실측 |

읽는 법 두 줄로 요약:

- **Strict와 Lax가 갈리는 곳은 오직 「최상위 이동 + 안전한 메서드」 세 줄뿐이다.**
- **Lax와 None이 갈리는 곳은 부속 자원과 POST, 즉 나머지 전부다.**

## 2. 값 선택 판단표

| 쿠키에 담긴 것 | 다른 사이트에서 이 쿠키가 필요한가 | 권장 값 | 함께 붙일 것 |
|---|---|---|---|
| 로그인 세션 식별자 (일반 웹앱) | 아니오 | `Lax` | `Secure` `HttpOnly` `Path=/` |
| 로그인 세션 + 외부 결제·OAuth 복귀가 있음 | 복귀 지점만 | `Lax` + 복귀를 **GET**으로 | `Secure` `HttpOnly` |
| 관리자 콘솔·내부 도구 | 아니오 | `Strict` | `Secure` `HttpOnly` `__Host-` 접두사 |
| CSRF 토큰 (이중 제출용) | 아니오 | `Strict` 또는 `Lax` | `Secure`, `HttpOnly` 없음 |
| 타사 페이지에 심는 위젯·SSO iframe | 예 | `None` | **`Secure` 필수** + `Partitioned` 검토 |
| 광고·분석 추적자 | 예 | `None` | `Secure`, 차단을 전제로 설계 |
| 언어·테마 같은 화면 설정 | 아니오 | `Lax` | `Secure`, 쿠키 대신 로컬 저장소도 검토 |

**선택 절차는 세 문장이다.**

1. 이 쿠키가 **다른 사이트에서 시작된 요청**에 붙어야 하는지 목록으로 적는다.
2. 목록이 비어 있으면 `Lax`, 최상위 이동에서도 필요 없으면 `Strict`.
3. 목록이 비어 있지 않을 때만 `None`을 쓰고, 그때는 `Secure`가 **필수**다.

## 3. 세 값 요약

| 값 | 한 줄 정의 | 대표 증상 |
|---|---|---|
| `Strict` | 같은 사이트 요청에만 붙는다 | 외부 링크로 들어온 첫 화면이 로그아웃 상태 |
| `Lax` | 같은 사이트 + **최상위 이동의 안전한 메서드**에 붙는다 | 결제·OAuth가 POST로 돌려보내면 세션 증발 |
| `None` | 모든 요청에 붙는다 | `Secure`를 빼면 쿠키 자체가 저장되지 않음 |
| (값 없음) | `Lax`와 같게 취급된다 | 「코드를 안 건드렸는데 어느 날 깨졌다」 |

## 4. Set-Cookie 작성 규칙 (파서로 확인한 것)

- 속성 **이름과 값의 대소문자는 무시**된다. `samesite=lax`도 `SameSite=Lax`와 같다
- 속성 **순서는 무관**하다. `Secure; SameSite=Lax`와 `SameSite=Lax; Secure`가 동일
- 등호 주변 **공백은 제거**된다. `SameSite = None`도 파싱된다
- **모르는 속성은 그 속성만 버린다.** 쿠키 전체가 죽지는 않는다
- **같은 속성이 두 번이면 마지막이 이긴다**
- **값의 오타는 오류가 아니다.** `SameSite=Strick`은 조용히 기본값(Lax)이 된다
- `Set-Cookie`는 서버 → 클라이언트, `Cookie`는 클라이언트 → 서버다. **`Cookie` 헤더에는 이름=값만 실린다.** 서버는 어떤 정책이 적용됐는지 알 방법이 없다

## 5. 로그인 풀림 진단 순서

1. 실패한 요청의 **`Cookie` 헤더에 세션 이름이 있는지** 서버 로그에서 확인한다. 없으면 인증이 아니라 쿠키 문제다
2. 그 요청이 **다른 사이트에서 시작됐는지** 확인한다. 같은 사이트면 SameSite는 범인이 아니다
3. 그 요청의 **메서드**를 확인한다. `POST`면 `Lax`에서 안 붙는 것이 정상 동작이다
4. 외부 서비스가 우리를 **몇 번 상태 코드로 돌려보내는지** 확인한다. 301·302·303은 GET으로 착지하고, **307·308은 POST를 유지한다**
5. 착지 지점을 **GET으로 받는 얇은 엔드포인트**로 바꾼다. 값을 `None`으로 낮추는 것보다 이쪽이 먼저다
6. 그래도 안 되면 착지 페이지에서 **같은 사이트 요청 한 번**을 더 태워 세션을 확인한다

## 6. 크기·개수 한계 (실측)

- 쿠키 하나의 상한은 **이름 길이 + 값 길이 ≤ 4096 옥텟**이다. 이름도 계산에 들어간다
- 넘치면 **잘리는 게 아니라 통째로 버려진다.** 오류도 경고도 없다
- 실행 환경의 HTTP 헤더 예산은 **16384 바이트**였고, 쿠키 300개(25996 바이트)에서 **431 응답**이 났다. 애플리케이션 코드는 실행되지 않았다
- 쿠키는 **일치하는 모든 요청에 매번 실린다.** 1.2 KB 쿠키 하나로 페이지당 60요청이면 회당 약 72 KB를 업로드한다
- 그래서 원칙은 하나다. **쿠키에는 식별자만, 상태는 서버에.**

## 7. 점검 목록

- [ ] 세션 쿠키의 `SameSite` 값을 **명시**했다 (기본값에 기대지 않는다)
- [ ] `None`을 쓴 쿠키에 **`Secure`가 붙어 있다**
- [ ] `None`을 쓴 이유를 **요청 목록으로** 적을 수 있다
- [ ] 외부 결제·OAuth **복귀 지점의 상태 코드와 메서드**를 확인했다
- [ ] 복귀 지점이 `POST`라면 얇은 **GET 엔드포인트**를 따로 뒀다
- [ ] `Domain` 속성을 **필요할 때만** 붙였다 (생략이 더 좁다)
- [ ] 서브도메인이 **같은 사이트로 묶인다**는 것을 설계에 반영했다
- [ ] 로컬 테스트에서 `localhost`와 `127.0.0.1`을 **섞어 쓰지 않았다** (서로 다른 사이트다)
- [ ] 스킴이 다르면 다른 사이트라는 점을 확인했다 (http ↔ https)
- [ ] 쿠키 하나의 **이름+값이 4096 옥텟 미만**이다
- [ ] 도메인당 쿠키 **개수와 총 바이트**를 재 봤다
- [ ] `SameSite` 값 문자열에 **오타가 없다** (오타는 조용히 기본값이 된다)
- [ ] `HttpOnly`를 세션 쿠키에 붙였다
- [ ] CSRF 대책을 **SameSite 하나에만** 걸지 않았다

## 8. 하지 말 것

- ❌ 증상이 보이자마자 **`None`으로 바꾸는 것** — 어느 요청에서 필요한지부터 정한다
- ❌ `None`을 쓰면서 **`Secure`를 빠뜨리는 것** — 쿠키가 저장 단계에서 버려진다
- ❌ **기본값에 의존**하는 것 — 명시하지 않은 쿠키는 구현의 기본 정책을 따라간다
- ❌ **`localhost`에서만 확인**하고 끝내는 것 — 로컬은 교차 사이트 조건을 재현하지 못한다
- ❌ **브라우저 버전별 동작을 단정**하는 것 — 구현마다 다를 수 있으니 대상 브라우저로 확인한다
- ❌ SameSite를 **CSRF 대책 전부로** 취급하는 것 — 완화 장치이지 방어의 전부가 아니다
- ❌ 세션 상태를 **쿠키 안에 통째로** 넣는 것 — 크기 상한과 대역폭을 함께 태운다
