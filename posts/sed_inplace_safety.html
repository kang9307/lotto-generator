sed -i 는 제자리 수정이 아니다 — 대량 치환 전에 미리 보기·백업·diff 순서

파일 ID 변화·하드링크 단절·CRLF 줄끝 변경 실측과 안전한 치환 파이프라인

2026-09-29 개발/인프라

수많은 자동화 스크립트와 배포 파이프라인에서 파일 안의 설정값을 변경할 때 가장 흔히 호출되는 명령어가 sed -i 이다. 옵션 이름인 --in-place 때문에 대부분의 작업자는 이 명령어가 디스크 상의 원본 파일을 직접 열어 해당 바이트를 덮어쓸 것이라고 기대한다. 그러나 실측 결과와 공식 문서가 증명하는 실체는 정반대다. sed -i 는 원본 파일을 고치는 도구가 아니라, 새로운 임시 파일을 생성해 치환 결과를 기록한 뒤 원본 파일 이름으로 바꿔치기하는 교체 도구다.

이 교체 방식을 모른 채 대량 치환을 하면 예상하지 못한 결과가 나온다. 하드 링크로 이어져 있던 다른 이름에는 바뀐 내용이 가지 않고, 파일 ID 가 바뀐다. 특히 Windows 의 Git Bash 에서는 치환할 패턴이 하나도 맞지 않은 파일까지 줄끝이 CRLF 에서 LF 로 바뀌어, 손대지 않은 파일이 변경으로 잡힌다. 이 글은 직접 실행한 기록으로 교체의 결과를 보여 주고, 대량 치환 전에 거칠 5단계 절차를 정리한다.

이 분석은 다음 환경에서 직접 실행하여 확인한 측정 기록을 바탕으로 한다: Windows 10 Pro 10.0.19045, Git Bash(GNU sed 4.9, GNU Awk 5.0.0), curl 8.12.1(Schannel), git 2.48.1.windows.1, Windows PowerShell 5.1, Python 3.13.3, Node 22.16.0 (관리자 권한 아님). 일반적인 줄끝 차이 배경은 CRLF와 LF 가이드를, 셸 인용 규칙은 셸 인용부호 규칙 가이드를, 정규표현식 이식성은 정규표현식 호환성 가이드를, 스크립트 멱등성 설계는 스크립트 멱등성 설계 가이드를 각각 참고할 수 있다.

1. sed -i 의 작동 원리 — 왜 제자리 수정이 아니라 새 파일 교체인가

명령어 이름 뒤에 붙는 -i 옵션은 영단어 in-place 의 약자다. 사용자는 단어 그대로 제자리에서 해당 파일의 블록을 직접 수정한다고 믿기 쉽지만, 내부 구현은 완전히 다르다. 스트림 에디터로 탄생한 sed 는 근본적으로 표준 입력에서 들어온 텍스트를 한 줄씩 패턴 스페이스로 읽어 변환한 뒤 표준 출력으로 밀어내는 필터 프로그램이다. 디스크 파일의 특정 오프셋을 임의로 찾아가(seek) 바이트를 직접 고치는 구조가 아니다.

임시 파일 생성과 rename 교체 메커니즘

GNU sed 매뉴얼의 Command-Line Options 항목은 -i 의 동작을 이렇게 설명한다. GNU sed 는 출력을 표준 출력 대신 임시 파일로 보내고, 파일 끝에 이르면 그 임시 파일의 이름을 원래 파일 이름으로 바꾼다.

즉 원래 파일의 데이터를 그 자리에서 고치는 것이 아니라, 새로 쓴 파일이 원래 이름을 차지하는 구조다. 백업 확장자를 주면(-i.bak) 바뀌기 전 내용이 app.conf.bak 처럼 확장자가 붙은 이름으로 남는다(6장 실행 결과). 이 교체 구조가 하드 링크·줄끝과 얽힐 때 무슨 일이 생기는지는 아래 실행 결과가 보여 준다.

리다이렉트 덮어쓰기(>)와의 본질적 차이

셸에서 printf 'y\n' > keep.txt 처럼 리다이렉트로 덮어쓰면 같은 파일에 새 내용을 쓴다. 실행 결과 keep.txt 의 inode 번호는 덮어쓰기 전후가 같았다. 반면 sed -i 는 새 파일로 이름을 바꿔치기하므로 번호가 바뀐다. 이 차이가 하드 링크와 줄끝에서 어떤 결과를 내는지 다음 장에서 실행 결과로 본다.

2. 실측 검증: 파일 ID 변화와 하드 링크 단절의 실체

이 교체 동작이 실제 시스템 환경에서 어떻게 발현되는지 구체적인 명령과 출력으로 검증했다.

inode 및 NTFS 파일 ID 의 변경 실측

Git Bash 환경에서 원본 설정 파일 conf.txt 를 생성하고, 치환 전후의 inode 번호 및 Windows NTFS 파일 ID 를 stat 및 fsutil 명령어로 측정했다.

printf 'host=old.example\nport=80\n' > conf.txt
ls -i conf.txt; stat -c 'ino=%i links=%h mtime=%y' conf.txt
sed -i 's/old/new/' conf.txt
ls -i conf.txt; stat -c 'ino=%i links=%h mtime=%y' conf.txt
# 비교: > 로 덮어쓰기
printf 'x\n' > keep.txt; ls -i keep.txt; printf 'y\n' > keep.txt; ls -i keep.txt
# Windows 파일 ID
fsutil file queryfileid conf.txt; sed -i 's/new/newer/' conf.txt; fsutil file queryfileid conf.txt

실제 터미널 출력 결과는 다음과 같다:

=== before
57702370226752894 conf.txt
ino=57702370226752894 links=1 mtime=2026-09-29 07:44:07.786669900 +0900
=== after sed -i
314689023964208355 conf.txt
ino=314689023964208355 links=1 mtime=2026-09-29 07:44:08.149979700 +0900
host=new.example
port=80
=== compare: in-place write via > redirect keeps id?
57983845203463550 keep.txt
57983845203463550 keep.txt
=== fsutil file id (before)
파일 ID: 0x0000000000000000045e00000019dce3
=== fsutil file id (after sed -i)
파일 ID: 0x000000000000000000230000001f9069

치환 전 conf.txt 의 inode 번호는 57702370226752894 였으나 sed -i 실행 직후 314689023964208355 로 변경되었다. fsutil 로 확인한 NTFS 파일 ID 역시 0x0000000000000000045e00000019dce3 에서 0x000000000000000000230000001f9069 로 바뀌었다. 반면 리다이렉트(>)로 덮어쓴 keep.txt 는 두 번의 쓰기 작업 모두 57983845203463550 으로 동일한 번호를 유지했다. 즉 sed -i 는 완전히 다른 새 파일로 이름을 바꿔치기한 것이다.

하드 링크 동기화 단절 실험

동일한 파일 데이터를 참조하는 하드 링크가 존재하는 상태에서 sed -i 를 수행하면 어떤 참사가 일어나는지 실험했다.

printf 'a=1\n' > orig.txt; ln orig.txt hard.txt
stat -c '%n ino=%i links=%h' orig.txt hard.txt
sed -i 's/1/2/' orig.txt
stat -c '%n ino=%i links=%h' orig.txt hard.txt
echo "orig: $(cat orig.txt) / hard: $(cat hard.txt)"

출력 결과는 아래와 같다:

orig.txt ino=314970498940919011 links=2
hard.txt ino=314970498940919011 links=2
orig.txt ino=28147497673134196 links=1
hard.txt ino=314970498940919011 links=1
orig: a=2 / hard: a=1

처음에는 두 파일 모두 inode 가 314970498940919011 로 일치하고 링크 수가 2였으나, sed -i 를 거치자 orig.txt 는 새로운 inode(28147497673134196)를 가진 단독 파일(links=1)로 분리되었다. 그 결과 orig.txt 는 a=2 로 수정되었지만 hard.txt 는 여전히 이전 파일 데이터인 a=1 을 가리키며 완전히 갈라졌다. 하드 링크를 통해 동기화되던 설정 파일 구조가 통째로 깨진 것이다. 운영체제 레벨에서 두 파일의 연결 고리가 영구히 단절된 상태가 된다.

표 1. 파일 수정 방식에 따른 파일 식별자 및 하드 링크 보존 실측 비교
수정 방식 수정 전 식별자 (inode) 수정 후 식별자 (inode) 하드 링크 상태 변화 결과 판정
리다이렉트 덮어쓰기 (>) 57983845203463550 57983845203463550 같은 번호 유지 (links 는 재지 않음) 같은 파일에 덮어씀
sed -i 's/.../.../' 57702370226752894 314689023964208355 번호 바뀜 (하드 링크 실험에서는 links 2 → 1) 새 파일 교체 (링크 단절)

3. 줄끝 문자 함정: 치환 대상이 없어도 CRLF 가 LF 로 바뀌는 현상

Windows 에서 작업할 때 흔한 사고 중 하나가 줄끝 문자(Line Ending)의 의도하지 않은 대량 변환이다. Git Bash 의 GNU sed 는 이 부분에서 함정이 있다. 아래는 CRLF 파일에 sed 를 실행한 결과다.

Git Bash sed 의 CR 무시 동작과 -b 옵션

CRLF 줄끝을 가진 파일에 대해 치환 작업을 수행하고 바이트 단위로 덤프했다.

printf 'line1=a\r\nline2=b\r\n' > crlf.txt
file crlf.txt; od -c crlf.txt
sed -i 's/a/A/' crlf.txt
file crlf.txt; od -c crlf.txt
sed -i -b 's/a/A/' crlf_b.txt; file crlf_b.txt; od -c crlf_b.txt      # -b(binary)
sed 's/a$/Z/' crlf_c.txt | od -c | head -2                           # $ 앵커
sed 's/\r$//' crlf_c.txt | od -c | head -2
printf 'p=a\r\n' | sed 's/a$/Z/' | od -c                               # 파이프에서도

실제 출력 결과는 다음과 같다:

=== CRLF before
crlf.txt: ASCII text, with CRLF line terminators
0000000   l   i   n   e   1   =   a  \r  \n   l   i   n   e   2   =   b
0000020  \r  \n
=== after sed -i 's/a/A/'
crlf.txt: ASCII text
0000000   l   i   n   e   1   =   A  \n   l   i   n   e   2   =   b  \n
=== sed -i -b (binary)
crlf_b.txt: ASCII text, with CRLF line terminators
0000000   l   i   n   e   1   =   A  \r  \n   l   i   n   e   2   =   b
0000020  \r  \n
=== $ anchor test: s/a$/Z/ on CRLF
0000000   l   i   n   e   1   =   Z  \n   l   i   n   e   2   =   b  \n
=== s/\r$// strip
0000000   l   i   n   e   1   =   a  \n   l   i   n   e   2   =   b  \n
(파이프) 0000000   p   =   Z  \n

측정 결과에서 두 가지가 드러난다. 첫째, Git Bash 의 sed 는 캐리지 리턴(CR, \r)을 보지 않는다. 그래서 정규식 끝 앵커 $ 가 CR 앞에서도 맞았다(a$ 가 a\r 줄에 맞아 Z 로 바뀜). 둘째, sed -i 한 번에 치환이 없던 line2 줄까지 CR 이 빠져 파일 전체 줄끝이 LF 가 됐다. -b(--binary)를 주면 CRLF 가 그대로 남았다. GNU sed 매뉴얼은 MS-DOS, Windows, Cygwin 처럼 텍스트 파일과 바이너리 파일을 구분하는 환경에서는 텍스트 파일의 줄이 CR 과 LF 로 나뉘고 sed 가 끝의 CR 을 보지 않는다고 적고, --binary 는 그런 구분이 있는 운영체제에서만 효과가 있다고 적는다. 따라서 이 결과는 Windows(MSYS) 빌드의 동작이다. Linux 의 GNU sed 에서도 같은지는 8장에 적었다.

매칭 0건 파일의 불필요한 줄끝 변환 실측

치환할 대상 문자열이 전혀 없는 파일에 sed -i 를 실행했을 때의 결과는 더욱 치명적이다.

printf 'x=1\r\ny=2\r\n' > nomatch.txt
stat -c 'ino=%i' nomatch.txt; sed -i 's/ZZZ/QQQ/' nomatch.txt; stat -c 'ino=%i' nomatch.txt; file nomatch.txt

출력 결과:

ino=153685337286086914
ino=10977524093784323
nomatch.txt: ASCII text

일치하는 줄이 하나도 없었는데도 inode 가 153685337286086914 에서 10977524093784323 으로 바뀌었다. printf 로 CRLF 를 넣어 만든 파일인데 file 출력은 ASCII text 였다(with CRLF line terminators 표시 없음). 줄끝이 LF 로 바뀐 것이다. 여러 파일에 한꺼번에 sed -i 를 돌리면 바꿀 필요가 없던 파일까지 줄끝이 바뀌어, 치환하지 않은 파일이 git diff 에 전부 변경으로 뜬다.

표 2. Windows Git Bash 환경에서 CRLF 파일 대상 sed 동작 및 줄끝 보존 실측표
실행 명령 치환 대상 존재 여부 줄끝(EOL) 변화 inode 변경 여부 비고
sed -i 's/a/A/' file 있음 (1건) CRLF → LF (전체 줄) 이 파일에서는 재지 않음 치환되지 않은 줄의 CR 도 삭제
sed -i -b 's/a/A/' file 있음 (1건) CRLF 유지 이 파일에서는 재지 않음 -b 로 CRLF 유지
sed -i 's/ZZZ/QQQ/' file 없음 (0건) CRLF → LF (전체 줄) 변경됨 (새 파일) 매칭 0건이어도 파일 교체 및 줄끝 파괴

4. 옵션 결합 오류와 빈 파일 참사: -iE 와 -n -i

명령줄 옵션을 지정하는 방식에서도 치명적인 함정이 존재한다. 유닉스 계열 도구는 흔히 여러 옵션을 한 글자로 묶어 쓰는 단축 표기를 지원하지만, 인자를 취하는 옵션 뒤에 다른 플래그를 붙일 때는 전혀 다른 파싱 규칙이 적용된다.

-iE 가 백업 확장자 E 로 인식되는 함정

확장 정규식(ERE)을 활성화하는 -E 옵션과 제자리 수정을 뜻하는 -i 옵션을 묶어 쓸 때 순서가 어긋나면 어떻게 되는지 실측했다.

printf 'a=1\n' > ie.txt
sed -iE 's/(a)=1/\1=2/' ie.txt; echo "exit=$?"; ls ie.txt*
sed -Ei 's/(a)=1/\1=2/' ie.txt; cat ie.txt
sed -iE 's/a=2/a=3/' ie.txt; ls ie.txt*; echo "ie.txt: $(cat ie.txt) / ie.txtE: $(cat ie.txtE)"
printf 'k1\nk2\n' > n.txt; sed -n -i 's/k1/K1/' n.txt; echo "size after: $(wc -c < n.txt)"

실제 출력 결과는 다음과 같다:

sed: -e expression #1, char 13: invalid reference \1 on `s' command's RHS
exit=1
ie.txt
---
a=2
exit=0
ie.txt
ie.txtE
ie.txt: a=3 / ie.txtE: a=2
size after: 0

GNU sed 매뉴얼에 명시되어 있듯이 -i 옵션 뒤에 공백 없이 붙은 문자는 백업 확장자로 해석된다. 따라서 -iE 는 확장 정규식을 켜는 것이 아니라 --in-place=E 와 동등하게 파싱되어 백업 파일 확장자를 E 로 지정해 버린다. 그 결과 정규식이 기본 정규식(BRE)으로 동작하여 (a) 그룹 캡처가 작동하지 않고 invalid reference \1 에러가 발생한다. 만약 단순 치환 문법을 썼다면 에러조차 없이 조용히 ie.txtE 라는 기괴한 백업 파일이 생성된다. 반드시 -Ei 또는 -E -i 로 작성해야 한다.

-n 과 -i 결합 시 파일이 0바이트로 비워지는 현상

더 끔찍한 실수는 미리 보기를 위해 사용하던 -n 플래그를 지우지 않은 채 -i 를 덧붙이는 경우다. 위 출력의 마지막 줄을 보면, sed -n -i 's/k1/K1/' n.txt 를 실행하자 파일 크기가 0 바이트로 완전히 비워졌다. -n 은 자동 출력을 억제하고, 치환 명령어 끝에 p 지시자가 없었으므로 아무것도 출력하지 않은 채 새 파일로 교체해 버렸기 때문이다. 백업 옵션도 없이 파일 내용이 통째로 증발한 것이다. GNU sed 매뉴얼도 -n 은 자동 출력을 끄고 -i 는 백업 없이 파일을 바꾸므로 둘을 함께 쓸 때 조심하라고 적고 있다.

표 3. 옵션 조합 방식에 따른 sed 실행 결과 및 위험도 분석
옵션 조합 실제 해석 실행 결과 위험 등급
-iE --in-place=E (백업 확장자 E) 확장 정규식 미적용 에러 또는 .txtE 백업 파일 생성 경고 (의도와 다른 동작)
-Ei 또는 -E -i 확장 정규식 켬 + 제자리 교체 정상적인 캡처 그룹 치환 수행 안전 (권장 문법)
-n -i (p 없음) 자동 출력 억제 + 제자리 교체 파일 내용 전체 삭제 (0바이트 파일 생성) 치명적 (데이터 즉시 유실)

5. 치환 문자열 속 & 와 경로 구분자 충돌

치환 표현식 자체의 문법에서도 스크립트를 파괴하는 함정들이 도사리고 있다. sed 치환 명령은 강력한 만큼 특수 문자의 의미를 정밀하게 통제하지 못하면 의도하지 않은 데이터 변형을 낳는다.

치환부 앰퍼샌드(&)의 전체 매칭 확장과 변수 오염

sed 치환 명령 s/패턴/대체문자열/ 에서 대체 문자열에 포함된 & 문자는 글자 그대로의 기호가 아니라 검색 패턴에 일치한 전체 문자열을 가리키는 특수 참조 문자다.

echo 'name=Tom' | sed 's/Tom/Tom & Jerry/'
echo 'name=Tom' | sed 's/Tom/Tom \& Jerry/'
echo 'root=/usr/local/app' | sed 's/\/usr\/local/\/opt/'
echo 'root=/usr/local/app' | sed 's//usr/local//opt/'; echo "exit=$?"
NEW=/opt/app; echo 'root=OLD' | sed "s/OLD/$NEW/"; echo "exit=$?"
echo 'root=OLD' | sed "s|OLD|$NEW|"
V='A&B'; echo 'x=OLD' | sed "s|OLD|$V|"
echo 'ab' | sed -E 's/(a)(b)/[\10]/'
echo 'port=80' | sed -E 's/(port)=([0-9]+)/\1=8\2/'

출력 결과:

name=Tom Tom Jerry
name=Tom & Jerry
root=/opt/app
sed: -e expression #1, char 8: unknown option to `s'
exit=1
sed: -e expression #1, char 8: unknown option to `s'
exit=1
root=/opt/app
x=AOLDB
[a0]
port=880

echo 'name=Tom' | sed 's/Tom/Tom & Jerry/' 의 결과는 Tom Tom Jerry 가 되었다. & 가 일치한 문자열인 Tom 으로 치환되었기 때문이다. 글자 그대로의 & 를 넣으려면 반드시 \& 로 이스케이프해야 한다. 이 문제는 셸 변수를 치환 문자열로 전달할 때 가장 치명적으로 번진다. 변수 V='A&B' 를 전달했을 때 x=AOLDB 로 치환되어 기존 매칭인 OLD 가 가운데 끼어든 현상이 이를 입증한다. 셸 변수를 sed 치환부에 주입하기 전에는 변수 내부의 & 문자를 \& 로 변환하는 전처리 작업이 필수적이다.

경로 치환 시 슬래시(/) 에러와 세로줄(|) 구분자

파일 경로 치환 시 변수 NEW=/opt/app 를 s/OLD/$NEW/ 에 넣으면 경로의 슬래시가 구분자로 읽혀 unknown option to `s' 오류와 함께 종료 코드 1이 나왔다. GNU sed 매뉴얼에 따르면 s 명령의 / 는 다른 한 글자로 통일해 바꿀 수 있다. 세로줄(|)을 쓴 s|OLD|$NEW| 는 root=/opt/app 을 정상 출력했다. 한편 역참조에서 \10 은 10번째 그룹이 아니라 첫 번째 그룹 \1 뒤에 글자 0 이 붙은 것으로 처리됐다([a0]). 또한 \1=8\2 는 8과 80이 붙어 880 이 되므로 역참조 바로 뒤에 숫자를 붙일 때 주의해야 한다.

표 4. 치환 문자열 특수 기호 및 구분자 충돌 실측 정리
입력 패턴 및 명령어 실제 출력 결과 오류 원인 올바른 해결책
s/Tom/Tom & Jerry/ Tom Tom Jerry & 가 매칭된 'Tom' 으로 자동 확장 s/Tom/Tom \& Jerry/
V='A&B'; s|OLD|$V| AOLDB 변수 속 & 가 'OLD' 로 확장되어 삽입 변수 전달 전 & 를 \& 로 선제 치환
s/OLD//opt/app/ unknown option to `s' (exit 1) 경로의 슬래시가 구분자와 겹쳐 문법 파괴 구분자 변경: s|OLD|/opt/app|

6. 대량 치환의 안전 5단계 절차

앞의 실행 결과를 바탕으로, 파일을 바꾸기 전에 거칠 5단계 순서를 정리한다. 한 번에 sed -i 를 돌리는 대신 단계마다 결과를 확인한다.

1단계부터 5단계까지의 단계별 파이프라인

아래 명령은 미리 보기 → 맞는 줄 수 → 백업 적용 → diff 순서로 실제 실행한 것이다.

printf 'root=/usr/local/app\nlog=/usr/local/app/log\nname=Tom\n' > app.conf
sed -n 's|/usr/local/app|/opt/app|gp' app.conf          # 1) 미리 보기
grep -c '/usr/local/app' app.conf                        #    맞는 줄 수
sed -i.bak 's|/usr/local/app|/opt/app|g' app.conf        # 2) 백업 두고 적용
ls app.conf*
diff app.conf.bak app.conf; echo "diff exit=$?"          # 3) 확인

실제 출력 결과:

=== 1) preview
root=/opt/app
log=/opt/app/log
=== match count
2
=== 2) apply with backup
app.conf
app.conf.bak
=== 3) diff
1,2c1,2
< root=/usr/local/app
< log=/usr/local/app/log
---
> root=/opt/app
> log=/opt/app/log
diff exit=1

이 파이프라인의 핵심은 다음과 같다:

  • 1단계 (매칭 줄 수 확인): grep -c '패턴' 파일 로 몇 줄이 치환 대상인지 센다. 0건이면 그 파일은 건너뛴다. 맞는 줄이 0개여도 sed -i 는 파일을 새로 만들었고, Git Bash 에서는 줄끝까지 바꿨다.
  • 2단계 (미리 보기 출력): sed -n 's|패턴|대체문자열|gp' 파일 로 변경될 줄만 터미널에 띄운다. 출력된 줄 수가 1단계 카운트와 일치하는지 육안 및 기계적으로 대조한다.
  • 3단계 (줄끝 검사): file 파일 및 od -c 파일 | head 로 CRLF 존재 여부를 확인한다. 윈도우 환경이라면 -b 플래그를 붙일지 결정한다.
  • 4단계 (백업 동반 적용): sed -i.bak 's|패턴|대체문자열|g' 파일 로 백업을 남기며 치환을 실행한다.
  • 5단계 (diff 검증): diff 파일.bak 파일 로 의도한 줄 외에 다른 줄(줄끝, 인접 텍스트 등)이 변하지 않았는지 최종 검증한다. diff 종료 코드 1은 차이가 발생했음을 나타내는 정상 신호다.

실전 대량 치환 점검표와 증상 대응표

현장에서 발생하는 이상 증상과 실측에 기반한 원인 및 대처법을 표로 정리했다.

표 5. 안전한 대량 치환 5단계 실행 점검표
단계 실행 명령어 확인 목적 판정 기준
1단계: 매칭 계수 grep -c '패턴' 파일 치환 대상 존재 여부 및 줄 수 파악 0건이면 즉시 작업 건너뜀

ie.txtE 같은 이상한 파일이 생긴다 -iE 옵션 결합으로 E 를 백업 확장자로 인식 -Ei 또는 -E -i 로 순서 변경
파일이 0바이트로 사라진다 -n -i 결합 시 p 지시자 누락으로 공백 교체 미리 보기용 -n 은 -i 와 절대 함께 쓰지 않음
ln -s 로 만든 링크가 따로 논다 Git Bash 기본 ln -s 가 링크 대신 복사본 생성 [ -L 파일 ] 로 실제 심볼릭 링크인지 사전에 확인

7. GNU sed 와 BSD sed 의 문법 차이와 이식성

리눅스(GNU sed)와 macOS·FreeBSD(BSD sed)를 오가는 스크립트에서는 -i 의 인자 처리 방식이 다르다. 이 장의 BSD 쪽 내용은 macOS 에서 실행하지 않았고, 문서에 따른 것이다.

-i 옵션 인자 처리 방식의 차이점

문서에 따르면 차이는 다음과 같다:

  • GNU sed: -i 뒤 백업 확장자는 붙여 쓰는 선택 인자다. 백업 없이 고치려면 sed -i 's/.../.../' file, 백업을 두려면 sed -i.bak 's/.../.../' file 처럼 붙여 쓴다(이 글의 실행도 이 형태다). 매뉴얼은 sed -iE 가 --in-place=E 와 같다고 적는다 — -i 에 붙은 글자는 확장자로 읽힌다.
  • BSD sed (FreeBSD·macOS): FreeBSD 매뉴얼은 -i extension 형식을 적고, 확장자를 빈 문자열로 주면 백업을 남기지 않는다고 한다. 문서의 예시는 sed -i '' -e 's/foo/bar/g' test.txt 다. 같은 문서는 디스크 공간이 모자라는 등의 상황에서 파일이 손상되거나 일부만 남을 수 있으므로 빈 확장자를 권하지 않는다고 적는다.

크로스 플랫폼 스크립트 작성 전략

두 쪽에 같이 쓸 수 있는 형태는 sed -i.bak 이다. GNU 는 붙여 쓴 확장자를 받고 BSD 는 확장자를 인자로 받으므로, 백업을 만든 뒤 diff 로 확인하고 필요 없으면 지우는 방식이 두 문서와 맞는다. 다만 이 부분은 문서에 따른 것이며 macOS 에서 실행하지 않았다.

표 7. GNU sed 와 BSD sed (macOS) 의 제자리 수정 문법 비교
동작 목적 GNU sed (Linux / Git Bash) BSD sed (macOS / FreeBSD) 공통 호환 권장 문법
백업 없이 제자리 수정 sed -i 's/.../.../' file sed -i '' 's/.../.../' file 비권장 (문법 분기 필요)
백업 남기며 제자리 수정 sed -i.bak 's/.../.../' file sed -i.bak 's/.../.../' file sed -i.bak 적용 후 필요시 rm file.bak

8. 확인하지 못한 것

본 실측 검증 환경 및 제약으로 인해 확인하지 못한 사항은 다음과 같다:

  • 심볼릭 링크에 대한 sed -i 의 직접 변환 실측: 테스트 시스템 환경(Windows 10 일반 사용자 권한, 개발자 모드 미활성화)에서는 Git Bash 기본 ln -s 가 심볼릭 링크 대신 단순 복사본을 생성하고(NOT a symlink), 네이티브 심볼릭 링크 생성 명령이 Operation not permitted 및 관리자 권한 요구로 실패하여 실제 심볼릭 링크 파일이 일반 파일로 바뀌는 현상을 실측하지 못했다. 대신 GNU sed 매뉴얼은 기본 동작이 심볼릭 링크를 끊는 것이어서 링크 대상은 수정되지 않는다고 적고 있다.
  • Linux 네이티브 환경에서의 CRLF 보존 여부: 본 실험의 줄끝 자동 변환(CRLF → LF) 및 CR 무시 동작은 Windows MSYS/Cygwin 기반의 Git Bash 빌드에서 실측된 것이다. 운영체제 차원에서 텍스트 모드 구분이 없는 순수 Linux 환경의 GNU sed 에서도 동일하게 동작하는지는 Linux 환경에서 직접 돌려보지 못했으므로 확인하지 못했다.
  • macOS/FreeBSD 네이티브 환경에서의 BSD sed 실측: BSD sed 의 -i '' 문법 및 동작 특성은 FreeBSD 맨페이지 문서에 근거한 것이며, 실제 macOS 터미널에서 직접 실행하여 종료 코드 및 디스크 변경을 확인하지는 못했다.

# sed -i 대량 치환 안전 점검표와 실무 참조표

검증 환경: Windows 10 Pro 10.0.19045, Git Bash(GNU sed 4.9, GNU Awk 5.0.0), curl 8.12.1(Schannel), git 2.48.1.windows.1, Windows PowerShell 5.1, Python 3.13.3, Node 22.16.0 (관리자 권한 아님).
아래 내용은 이 환경에서 실행한 결과와 GNU sed·FreeBSD 매뉴얼에 근거한 것이다. 줄끝(CRLF) 관련 항목은 Git Bash(Windows) 빌드에서 본 동작이다.

---

## 1. 대량 치환 안전 5단계 파이프라인

파일을 직접 수정하기 전에 반드시 다음 순서를 거친다.

1. **대상 줄 수 확인**: `grep -c '패턴' 파일` 로 치환될 대상 줄 수를 센다. 0이면 그 파일은 건너뛴다.
2. **바뀔 내용 미리 보기**: `sed -n 's|패턴|대체문자열|gp' 파일` 로 실제 변경될 줄만 출력해 1번 줄 수와 일치하는지 대조한다.
3. **줄끝 문자(CRLF/LF) 확인**: `file 파일` 또는 `od -c 파일 | head` 로 줄끝 형식을 확인하고, Git Bash 라면 줄끝 보존을 위해 `-b` 옵션 사용 여부를 결정한다.
4. **백업 파일 생성 후 적용**: `sed -i.bak 's|패턴|대체문자열|g' 파일` 명령으로 원본 백업(`파일.bak`)을 남기며 치환을 실행한다.
5. **diff 검증**: `diff 파일.bak 파일` 로 의도한 줄만 변경되었는지 확인한다(종료 코드 1은 차이가 있다는 뜻이며 오류가 아님).

---

## 2. 증상별 원인 및 대응표 (실측 기반)

| 증상 | 원인 | 대처 |
|---|---|---|
| 치환하지 않은 파일까지 git diff 에 전부 변경으로 잡힘 | Git Bash sed 가 CRLF 를 LF 로 변환 (치환 매칭 줄이 0개여도 발생) | `sed -i -b` 사용, 또는 변경 대상 파일만 선별하여 실행 |
| 하드 링크로 연결된 다른 이름의 내용이 갱신되지 않음 | `sed -i` 는 기존 파일 수정이 아닌 임시 파일 생성 후 rename 교체 | 하드 링크를 유지해야 하는 파일이면 `sed -i` 로 교체하지 말고 다른 방법을 쓴다 |
| ``unknown option to `s'`` 오류 발생 | 경로 문자열 등에 슬래시(`/`)가 포함되어 구분자와 충돌 | 치환 구분자를 `s|패턴|대체문자열|g` 처럼 세로줄(`|`)로 변경 |
| 치환 결과 중간에 원문이 끼어듦 (`A&B` 치환 시 `AOLDB`) | 치환 문자열에 포함된 `&` 가 일치한 전체 매칭으로 확장됨 | 치환 문자열 내 `&` 를 `\&` 로 이스케이프 처리 후 치환 |
| `ie.txtE` 같은 원치 않는 백업 파일이 생성됨 | `-iE` 로 옵션을 결합하여 sed 가 `E` 를 백업 확장자로 인식함 | `-Ei` 순서로 작성하거나 `-E -i` 처럼 분리 |
| 파일 내용이 0바이트로 사라짐 | `-n` 과 `-i` 를 함께 쓰면서 출력 지시자(`p`)를 누락함 | 미리 보기용 `-n` 과 파일 수정용 `-i` 를 함께 실행하지 않음 |
| `ln -s` 로 생성한 「링크」가 원본과 따로 동작함 | Git Bash 기본 `ln -s` 는 심볼릭 링크 대신 파일 복사본을 생성함 | `[ -L 파일 ]` 조건으로 실제 링크 여부를 사전에 검증 |

---

## 3. sed -i 주요 함정 체크리스트

- [ ] `sed -i` 는 inode 번호와 파일 ID 를 바꾸므로 하드 링크가 끊어진다(Git Bash 실측).
- [ ] Git Bash(MSYS) 환경에서는 치환 대상이 0건이어도 파일 줄끝이 LF 로 바뀐다.
- [ ] Git Bash 에서 CRLF 줄끝을 유지하려면 `-b`(--binary) 옵션을 붙인다.
- [ ] 확장 정규식을 함께 쓸 때는 `-iE` 가 아니라 `-Ei` 순서로 작성한다.
- [ ] 치환 문자열에 변수를 전달할 때는 변수 값 내부의 `&` 문자가 `\&` 로 치환되었는지 검증한다.
- [ ] (문서 근거) BSD/FreeBSD sed 에서 백업 없이 고치려면 `sed -i ''` 로 빈 확장자를 넘긴다. 매뉴얼은 빈 확장자를 권하지 않는다.
- [ ] (문서 근거) GNU sed 와 BSD sed 양쪽에서 쓰려면 `sed -i.bak` 로 백업을 남긴 후 필요 없으면 백업을 지운다.
