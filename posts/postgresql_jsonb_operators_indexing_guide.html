PostgreSQL의 JSONB는 관계형 테이블 안에서 문서 지향적인 유연성을 제공하지만, 연산자의 반환 타입과 인덱스 오퍼레이터 클래스를 정확히 이해하지 못하면 쿼리 문법 오류와 전체 테이블 풀 스캔(Seq Scan)이 발생한다. 본 글에서는 Roxana-Maria Haidiner가 제시한 고객 지원 티켓 실무 스키마와 40,004건 벤치마크를 바탕으로, ->와 ->> 연산자의 차이, jsonb_set()을 통한 안전한 부분 갱신, 그리고 GIN (jsonb_path_ops) 인덱싱 전략을 분석한다.

관계형 데이터베이스에서 JSONB를 다루는 전제와 경계

관계형 데이터베이스 관리 시스템(RDBMS)인 PostgreSQL에 구조화되지 않은 JSON 문서를 저장할 수 있는 능력은 개발자에게 큰 편의를 제공한다. 그러나 모든 유연성에는 구조적 대가가 따른다. PostgreSQL은 두 가지 JSON 저장 타입을 제공한다. json 타입은 입력된 텍스트 공백과 키 순서를 그대로 보존하지만 매 조회마다 구문 분석(Parsing)을 다시 수행한다. 반면 JSONB 타입은 입력을 분해된 바이너리 트리 포맷으로 변환하여 저장하므로 쓰기 시점에 약간의 파싱 오버헤드가 발생하지만, 조회 연산이 압도적으로 빠르고 인덱스를 적용할 수 있다.

실무 엔지니어링에서 흔히 범하는 안티 패턴은 데이터 모델링 단계의 고민을 회피하기 위해 테이블의 모든 가변 필드를 단일 data JSONB 컬럼에 몰아넣는 일이다. 이러한 설계는 다음과 같은 치명적인 한계를 드러낸다:

  • 외래키 및 무결성 제약 부재: JSONB 문서 내부의 개별 필드는 다른 테이블의 기본키를 참조하는 외래키(FOREIGN KEY) 제약 조건을 걸 수 없다.
  • 고유성(UNIQUE) 보장의 어려움: 특정 하위 경로에 유니크 인덱스를 생성할 수는 있으나, 복합 제약 조건이나 부분 인덱스 관리가 복잡해진다.
  • TOAST 오버헤드와 쓰기 증폭: 행의 크기가 페이지 경계를 초과하면 PostgreSQL은 데이터를 TOAST(The Oversized-Attribute Storage Technique) 영역으로 분리한다. 작은 필드 하나만 수정해도 내부적으로는 압축된 TOAST 청크 전체가 다시 복사되고 이전 버전이 데드 튜플(Dead Tuple)로 남아 진공(Vacuum) 부하를 유발한다.
  • 통계 수집의 한계: 쿼리 플래너는 일반 관계형 컬럼에 비해 JSONB 내부 값의 히스토그램이나 빈도 통계를 수집하는 정밀도가 떨어져 최적 실행 계획 수립에 실패할 확률이 높다.

따라서 성공적인 아키텍처는 고정된 관계형 컬럼과 가변적인 JSONB 필드의 경계를 엄격히 나누는 것에서 출발한다. status, priority, created_at처럼 상태 전이, 정렬, 범위 필터링이 빈번하게 일어나는 컬럼은 일반 SQL 데이터 타입으로 정의하고, 클라이언트의 운영 환경이나 에러 스택 트레이스처럼 형식이 다변화되는 메타데이터만을 JSONB에 위임해야 한다.

지원 티켓 스키마 설계: 일반 컬럼과 JSONB의 분리

Roxana-Maria Haidiner가 제시한 고객 지원 티켓 시스템(support_tickets)은 관계형 컬럼과 JSONB의 이상적인 분리 기준을 보여준다. 티켓의 수명주기 동안 절대적으로 불변하거나 일관된 처리가 요구되는 속성은 일반 컬럼으로 배치되었으며, 고객의 런타임 환경과 오류 세부 내역은 details라는 JSONB 컬럼에 격리되었다.

해당 테이블의 DDL 정의는 다음과 같다:

CREATE TABLE support_tickets (
                        ticket_id  BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
                        status     TEXT NOT NULL,
                        priority   TEXT NOT NULL,
                        created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
                        details    JSONB NOT NULL
                            CHECK (jsonb_typeof(details) = 'object')
                    );

이 DDL에서 주목해야 할 핵심 설계 요소들이 존재한다:

  • 정체성 컬럼(IDENTITY): ticket_id는 BIGINT GENERATED ALWAYS AS IDENTITY로 선언되어 분산 환경에서도 안정적인 64비트 단조 증가 키로 쓸 수 있다.
  • 관계형 필터링 컬럼: status와 priority는 티켓 대기열 뷰에서 항상 WHERE status = 'open' ORDER BY priority 형태로 필터링되므로 독립 컬럼으로 존재해야 인덱스 활용과 B-tree 스캔이 직관적이다.
  • CHECK 제약 조건: CHECK (jsonb_typeof(details) = 'object') 구문은 최상위 루트가 반드시 JSON 객체({}) 형태여야 함을 강제한다. PostgreSQL JSONB는 최상위에 원시 스칼라 값(예: "hello")이나 배열([])도 저장할 수 있으므로, 잘못된 형태의 페이로드가 유입되는 것을 데이터베이스 레벨에서 원천 차단한다.

이 테이블에 저장되는 실제 데이터 예시는 다음과 같은 복합 구조를 갖는다:

INSERT INTO support_tickets (status, priority, details)
                    VALUES (
                        'open',
                        'high',
                        '{
                          "customer": {
                            "name": "Trevor Lisbon",
                            "plan": "Professional"
                          },
                          "environment": {
                            "browser": "Chrome",
                            "os": "Windows 11",
                            "appVersion": "4.8.2"
                          },
                          "tags": ["sync", "postgresql"],
                          "error": {
                            "code": "SYNC_TIMEOUT",
                            "retryable": true
                          }
                        }'::jsonb
                    );

여기서 중요한 점은 CHECK 제약 조건이 details의 최상위 형식이 객체인지만 검증할 뿐, customer.plan 필드가 존재하는지, 또는 tags가 반드시 배열인지와 같은 세부 내부 스키마를 보장하지는 않는다는 사실이다. JSONB는 데이터 포맷 유효성만을 검증하므로 내부 데이터 계약(Contract) 관리는 여전히 애플리케이션 계층이나 스키마 유효성 검사기의 책임으로 남는다.

->와 ->> 연산자의 본질적 차이와 타입 오류

PostgreSQL에서 JSONB 데이터를 쿼리할 때 개발자들이 가장 빈번하게 마주치는 난관은 화살표 연산자(Arrow Operators)의 타입 반환 규칙이다. 외관상 유사해 보이는 두 연산자는 반환하는 SQL 데이터 타입이 완전히 다르다.

연산자 PostgreSQL 구문 반환 데이터 타입 주요 사용 용도
-> details -> 'customer' JSONB JSON 객체나 배열 구조를 유지한 채 하위 경로로 체이닝 탐색
->> details -> 'customer' ->> 'plan' text 스칼라 값을 일반 텍스트로 추출하여 SQL WHERE 조건이나 정렬에 사용

-> 연산자는 결과를 항상 JSONB 타입으로 유지한다. 따라서 details -> 'customer'를 실행하면 {"name": "Trevor Lisbon", "plan": "Professional"}라는 JSONB 객체가 반환되며, 이를 다시 -> 연산자로 연결하여 깊은 중첩 구조를 탐색할 수 있다.

반면 ->> 연산자는 해당 키의 값을 일반 SQL text 타입으로 역직렬화하여 추출한다. 실무에서 가장 흔히 발생하는 버그는 경로의 마지막 단계에서도 습관적으로 -> 연산자를 사용하는 경우다:

-- 잘못된 쿼리: 타입 불일치 오류 유발
                    SELECT ticket_id FROM support_tickets
                    WHERE details -> 'customer' -> 'plan' = 'Professional';
                    
                    -- 올바른 쿼리: text 타입 추출 후 비교
                    SELECT
                        ticket_id,
                        details -> 'customer' AS customer,
                        details -> 'customer' ->> 'plan' AS plan
                    FROM support_tickets
                    WHERE details -> 'customer' ->> 'plan' = 'Professional';

첫 번째 잘못된 쿼리에서 좌변은 JSONB 타입이고 우변의 'Professional'은 SQL 문자열 리터럴이다. PostgreSQL은 두 타입 간의 직접 동등 비교 연산자(=)를 지원하지 않거나 내부 형변환을 시도하다가 다음과 같은 에러를 발생시킨다:

  • ERROR: invalid input syntax for type json
  • DETAIL: Token "Professional" is invalid.

따라서 경로를 연속 탐색할 때는 ->로 파고들어가고, SQL 수준에서 비교하거나 정렬해야 하는 최종 리프 노드에서는 반드시 ->>를 사용해야 한다. 또한 특정 행에 error 객체나 해당 키가 존재하지 않을 때, PostgreSQL은 에러를 던지지 않고 안전하게 SQL NULL을 반환한다. 이는 WHERE details -> 'error' ->> 'code' = 'SYNC_TIMEOUT' 같은 필터링에서 누락된 행이 자동으로 제외됨을 의미한다.

배열 요소 검사와 존재 여부 확인 (? 연산자의 동작)

JSONB 컬럼 내부에는 단순 키-값 쌍뿐만 아니라 문자열이나 숫자의 배열(Array)이 자주 포함된다. 예제 스키마의 details -> 'tags'는 ["sync", "postgresql"]과 같은 문자열 배열을 담고 있다. 특정 태그가 포함되어 있는지 확인하려면 물음표(?) 연산자를 사용한다.

-- 태그 배열에 특정 문자열 존재 여부 확인
                    SELECT ticket_id, status, details -> 'tags' AS tags
                    FROM support_tickets
                    WHERE details -> 'tags' ? 'postgresql';

물음표(?) 연산자는 최상위 JSONB 객체에 특정 키가 존재하는지 검사하거나, JSONB 배열 내부에 지정한 텍스트 요소가 포함되어 있는지 확인할 때 boolean 결과를 반환한다. 이 연산자는 기본 GIN 인덱스(jsonb_ops)를 통해 고속 검색이 가능하다.

그러나 이 방식에는 스키마 강제성이 없는 NoSQL 스타일 저장 구조 특유의 취약점이 내포되어 있다:

  • 데이터 형상의 불일치 위험: 만약 어떤 클라이언트가 버그로 인해 "tags": "postgresql"과 같이 단일 문자열 형태로 저장했다면, 문법상 유효한 JSONB이지만 ? 연산자는 기대와 다르게 동작할 수 있다.
  • 연산자 오버로딩 혼선: 객체에 대해 ?를 쓰면 '키의 존재 여부'를 확인하고, 배열에 대해 쓰면 '문자열 원소의 존재 여부'를 확인하므로 데이터 타입의 동질성이 보장되지 않으면 예상치 못한 조회 누락이 발생한다.
  • 복수 조건 연산자: 여러 태그 중 하나라도 일치하는지 확인할 때는 ?|(OR 매칭)를 사용하고, 모든 태그가 동시에 포함되어야 할 때는 ?&(AND 매칭) 연산자를 사용해야 한다. 예: details -> 'tags' ?& array['sync', 'postgresql'].

@> 포함 연산자와 계층 구조 매칭

다단계로 중첩된 JSONB 문서에서 특정 구조가 완전히 포함되어 있는지 확인하려면 포함(Containment) 연산자인 @>를 사용한다. A @> B는 좌변의 JSONB 문서 A가 우변의 JSONB 문서 B의 모든 구조와 값을 온전히 포함하고 있는지를 평가한다.

-- 중첩된 에러 코드 일치 여부 확인
                    SELECT ticket_id, status, details -> 'error' AS error
                    FROM support_tickets
                    WHERE details @> '{
                      "error": {
                        "code": "SYNC_TIMEOUT"
                      }
                    }'::jsonb;

포함 연산자는 화살표 연산자로 경로를 일일이 지정하는 방식에 비해 강력한 장점을 갖는다. 첫째, 조건식 자체가 온전한 JSON 조각이므로 애플리케이션의 DTO나 JSON 객체를 직렬화하여 바인딩 변수로 주입하기 매우 용이하다. 둘째, 이후 살펴볼 GIN (jsonb_path_ops) 인덱스의 최적화 혜택을 온전히 누릴 수 있다.

하지만 @> 연산자를 다룰 때는 루트 경로의 구조 일치 규칙을 반드시 준수해야 한다:

  • 구조 일치 필수성: WHERE details @> '{"code": "SYNC_TIMEOUT"}'::jsonb와 같은 쿼리는 동작하지 않는다. code는 루트 키가 아니라 error 하위에 중첩된 필드이므로, 우변의 JSONB 리터럴 역시 반드시 {"error": {"code": ...}} 형태로 중첩 계층을 일치시켜야 한다.
  • 배열 부분 포함: 우변에 {"tags": ["postgresql"]}을 제공할 경우, 좌변의 tags 배열에 다른 요소들이 섞여 있더라도 "postgresql" 원소가 포함되어 있다면 true로 판정된다.
  • 반대 방향 연산자: 포함 관계의 방향을 반대로 검사할 때는 <@(is contained by) 연산자를 사용할 수 있다.

jsonb_set 함수를 이용한 부분 갱신과 상위 키 누락 대응

전통적인 NoSQL 문서 저장소나 초기 RDBMS 환경에서는 문서의 한 필드만 수정하더라도 애플리케이션이 전체 문서를 읽어 메모리에서 수정한 후 전체를 다시 덮어쓰는(Replace) 방식을 취했다. 이는 동시성 업데이트 시 경쟁 상태(Race Condition)를 유발하고 네트워크 대역폭을 낭비한다. PostgreSQL은 문서의 특정 경로 값만 지정하여 갱신할 수 있는 jsonb_set() 함수를 제공한다.

예를 들어 1번 티켓의 environment.appVersion 필드만 4.8.4로 갱신하는 쿼리는 다음과 같다:

-- jsonb_set을 이용한 특정 중첩 필드 부분 갱신
                    UPDATE support_tickets
                    SET details = jsonb_set(
                        details,
                        '{environment,appVersion}',
                        to_jsonb('4.8.4'::text),
                        false
                    )
                    WHERE ticket_id = 1
                    RETURNING
                        ticket_id,
                        details -> 'environment' AS environment;

이 함수 호출에서 주의 깊게 살펴봐야 할 인자 규칙이 있다:

  • 경로 배열: 둘째 인자인 '{environment,appVersion}'은 텍스트 배열(text[])로서 루트부터 리프까지의 경로를 단계별로 명시한다.
  • 명시적 타입 변환: 셋째 인자에는 반드시 to_jsonb('4.8.4'::text)처럼 명시적 캐스팅을 거쳐야 한다. 만약 캐스팅 없이 리터럴을 전달하면 PostgreSQL 엔진은 could not determine polymorphic type because input has type unknown 에러를 발생시킨다.
  • create_if_missing 플래그: 넷째 인자인 불리언 값은 대상 키가 존재하지 않을 때 새로 생성할지(true), 아니면 무시할지(false)를 결정한다. 원문 예제에서는 이미 존재하는 버전을 갱신하는 의도이므로 false를 전달했다.

그러나 jsonb_set()에는 결정적인 한계가 존재한다. 바로 '상위 부모 객체가 누락된 경우'다. 예를 들어 특정 티켓에 아직 error 객체 자체가 존재하지 않는 상황에서 '{error,firstSeenAt}' 경로로 jsonb_set을 호출하면, 넷째 인자가 true여도 상위 error 객체를 자동으로 만들어주지 않으므로 아무런 변경도 일어나지 않는다.

이를 안전하게 해결하려면 상위 객체의 존재 여부를 COALESCE로 보장하고 ||(병합) 연산자나 jsonb_build_object()를 결합해야 한다:

-- 부모 객체가 없을 때도 안전하게 하위 필드를 생성하는 패턴
                    UPDATE support_tickets
                    SET details = jsonb_set(
                        details,
                        '{error}',
                        COALESCE(details -> 'error', '{}'::jsonb)
                            || jsonb_build_object(
                                'firstSeenAt',
                                '2026-08-03T11:05:00Z'
                            ),
                        true
                    )
                    WHERE ticket_id = 3
                    RETURNING details -> 'error' AS error;

이 쿼리는 details -> 'error'가 NULL인 경우 빈 객체 '{}'::jsonb로 대체한 뒤, 새 속성을 병합하여 {error} 경로 전체를 덮어쓴다. RETURNING 절을 붙여 실제로 필드가 정상 추가되었는지 결과를 즉시 반환받아 검증할 수 있다.

GIN 인덱스 설계: jsonb_ops와 jsonb_path_ops의 갈래

JSONB 컬럼에 대한 조회가 빈번해지면 인덱스 구성이 필수가 된다. 일반 관계형 B-tree 인덱스는 컬럼 전체 값의 정렬과 동등 비교에는 유효하지만, 내부 하위 키나 요소를 탐색할 수는 없다. PostgreSQL은 이를 위해 GIN(Generalized Inverted Index)을 제공한다. GIN은 하나의 행 안에 포함된 여러 개의 키와 값을 역색인(Inverted Index) 구조로 분해하여 저장한다.

PostgreSQL은 GIN 인덱스를 생성할 때 두 가지 상이한 연산자 클래스(Operator Class)를 제공한다:

구분 기본 jsonb_ops 특화 jsonb_path_ops
인덱싱 대상 모든 개별 키, 값, 배열 원소를 독립적으로 색인 루트부터 리프 노드까지의 전체 경로-값 쌍을 해시 색인
지원 연산자 @>, ?, ?|, ?& 전체 지원 오직 포함 연산자(@>)만 지원
인덱스 크기 키와 값이 분리 색인되므로 상대적으로 큼 해시 기반 단일 항목 색인이므로 크기가 현저히 작음
포함 검색 성능 경로 조합을 위해 여러 항목을 조합하므로 보통 경로 전체 해시 매칭으로 매우 빠름

원문에서 Roxana-Maria Haidiner는 details 컬럼에 대해 jsonb_path_ops를 채택했다:

-- containment 검색에 특화된 GIN 인덱스 생성
                    CREATE INDEX idx_support_tickets_details_gin
                    ON support_tickets
                    USING GIN (details jsonb_path_ops);
                    
                    -- 통계 갱신
                    ANALYZE support_tickets;

이 선택의 전략적 이유는 명확하다. 주된 쿼리 패턴이 WHERE details @> '{"error": {"code": "SYNC_TIMEOUT"}}'::jsonb와 같은 중첩 객체 포함 검사이기 때문이다. jsonb_path_ops는 각 경로의 해시를 생성하므로 인덱스 크기를 작게 유지하면서도 @> 연산자의 탐색 속도를 극대화한다. 그러나 이 인덱스를 생성하면 details -> 'tags' ? 'postgresql'과 같은 단일 키/배열 존재 확인 쿼리는 인덱스를 타지 못하고 풀 스캔으로 떨어진다는 점을 반드시 기억해야 한다.

실무 운영 관점에서 jsonb_path_ops 도입 시 고려해야 할 핵심 요소는 다음과 같다:

  • 인덱스 물리적 크기 절감: 개별 키와 값을 분리 색인하지 않고 경로 단위의 단일 해시로 압축하므로 기본 jsonb_ops 대비 디스크 사용량이 현저히 줄어든다.
  • 포함 검색 성능 극대화: @> 연산자를 사용한 다계층 중첩 문서 검색 시 단일 해시 일치 판정으로 인덱스를 빠르게 순회한다.
  • 지원 연산자의 제한: ?, ?|, ?&와 같은 단일 키 존재 검사나 배열 원소 탐색 연산자는 지원하지 않으므로 전용 인덱스가 필요하다.

40,004건 벤치마크와 EXPLAIN 쿼리 플랜 분석

인덱스의 실제 효용성을 증명하기 위해 원문에서는 4건의 기초 레코드 외에 프로그래밍 방식으로 생성한 40,000건의 합성 티켓 데이터를 추가하여 총 40,004건의 환경을 구성했다. 그런 다음 @> 조건 검색을 실행하고 PostgreSQL의 EXPLAIN 도구로 실행 계획을 추적했다.

-- 실행 계획 추적 쿼리
                    EXPLAIN
                    SELECT ticket_id
                    FROM support_tickets
                    WHERE details @> '{
                      "error": {
                        "code": "SYNC_TIMEOUT"
                      }
                    }'::jsonb;

벤치마크 실행 결과, 40,004건 중 SYNC_TIMEOUT 에러를 포함하는 매칭 레코드는 정확히 402건(전체 데이터의 약 1%)이었다. PostgreSQL 옵티마이저가 수립한 실행 계획은 다음과 같이 확인되었다:

  • Bitmap Index Scan: 먼저 idx_support_tickets_details_gin 인덱스를 탐색하여 조건을 만족하는 튜플의 물리적 위치(TID)를 비트맵(Bitmap) 메모리 구조에 수집했다.
  • Bitmap Heap Scan: 생성된 비트맵을 바탕으로 실제 테이블 힙(Heap) 블록에 접근하여 일치하는 행들을 읽어 들였다. 이는 랜덤 I/O를 최소화하고 순차 I/O 형태로 페이지를 읽기 위한 전형적인 최적화 동작이다.
  • 비용 평가: 40,004건 전체를 순차적으로 읽는 Seq Scan 대신 비트맵 스캔이 선택됨으로써 I/O 비용이 대폭 절감되었다.

그러나 데이터베이스 옵티마이저는 항상 인덱스를 고집하지 않는다. 만약 테이블의 전체 행 수가 수백 건 이하로 매우 적거나, 쿼리 조건에 부합하는 결과 행의 비율(선택도, Selectivity)이 30%를 초과할 경우, 인덱스 블록을 읽고 다시 힙을 방문하는 비용이 전체 테이블을 한 번에 읽는 비용보다 비싸지므로 옵티마이저는 인덱스가 존재하더라도 Seq Scan을 선택한다. 인덱스 생성 후 반드시 ANALYZE를 수행하여 데이터 분포 통계를 갱신해야 하는 이유가 여기에 있다.

JSONB 도입 판단 표: 유연성과 무결성의 균형

PostgreSQL에서 데이터를 설계할 때 일반 관계형 컬럼을 사용할 것인지, 아니면 JSONB로 격리할 것인지를 결정하는 원칙은 명확하다. Roxana-Maria Haidiner의 가이드와 데이터베이스 설계 이론을 통합한 의사결정 매트릭스는 다음과 같다.

설계 요구 조건 권장 저장 방식 선택 근거 및 기술적 영향
레코드마다 속성 목록이 크게 다르거나 수시로 추가됨 JSONB 컬럼 스키마 마이그레이션(DDL) 없이 유연하게 키-값 추가 가능
데이터가 중첩된 객체나 다차원 배열 구조를 가짐 JSONB 컬럼 별도의 1:N 조인 테이블을 생성하지 않고 단일 행에 계층 구조 저장
고유성(UNIQUE)이나 외래키(FK) 참조가 필수적인 속성 일반 관계형 컬럼 RDBMS 엔진 레벨의 엄격한 참조 무결성 및 제약 조건 적용 보장
WHERE 필터링, 범위 검색, 정렬(ORDER BY)이 극도로 빈번함 일반 관계형 컬럼 표준 B-tree 인덱스 활용 극대화 및 정확한 통계 기반 쿼리 플래너 최적화
다른 비즈니스 테이블과의 빈번한 JOIN 조건에 사용됨 일반 관계형 컬럼 해시 조인 및 머지 조인 시 타입 변환 오버헤드 방지
오류 로그, 요청 헤더, 외부 서드파티 웹훅 페이로드 스냅숏 JSONB 컬럼 가공되지 않은 페이로드 보존 및 필요 시점에 부분 검색 수행

데이터베이스 설계의 핵심은 양자택일이 아니다. 엔티티의 뼈대가 되는 식별자와 상태 값은 관계형 컬럼으로 굳건히 세우고, 확장이 필요한 맥락 정보에 한해 JSONB를 배치하는 '하이브리드 모델링'이야말로 유지보수성과 성능을 동시에 잡는 최선의 경로다. 관련 내부 데이터 아키텍처에 대한 추가 내용은 PostgreSQL AT TIME ZONE 타임존 처리 가이드를 참고할 수 있다.

확인하지 못한 것

  • 실행 시간(Execution Time)의 밀리초 수치: 원문 저자는 VisuaLeaf Explain 뷰를 통해 Bitmap Index Scan이 사용되었음을 명시했으나, 하드웨어 사양, 캐시 적중률, 구체적인 실행 시간(ms) 및 I/O 비용 수치를 밝히지 않아 정량적 개선율을 수치로 특정하지 못했다.
  • 인덱스 크기 비교 데이터: 40,004건 기준 jsonb_ops와 jsonb_path_ops 간의 정확한 물리적 디스크 점유 용량(MB) 수치는 원문에 기재되지 않았다.
  • PostgreSQL 서버 버전 및 work_mem 설정: 테스트에 사용된 데이터베이스의 정확한 메이저 버전과 메모리 설정값(work_mem 등)은 본문에 명시되지 않았다.
