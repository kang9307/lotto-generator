用TypeScript编译器打造代码图谱MCP，把Claude Code的Token消耗降低10倍

让智能体查询图谱而不是通读代码，Token为何能大幅下降——原理与局限分析

2026年7月2日 开发/基础设施

引言：智能体「阅读」代码的方式本身就是问题

GeekNews上一篇简短的帖子引起了本人的注意。有开发者用TypeScript编译器构建代码图谱，再以MCP（Model Context Protocol）服务器的形式提供给Claude Code，结果在同样的任务上，Token消耗降低了约10倍。原帖内容相当精炼，但它触及的问题却一点也不小。任何在实际项目中长期使用AI编程智能体的人都会遇到类似场景：一个看似简单的问题，智能体却要打开五六个文件、跑好几次grep，最后把大半个上下文窗口耗在「找代码」上，而不是真正解决问题。这正是这类工具试图正面回应的痛点。

本文不是对原帖的简单翻译或摘要，而是本人在查阅MCP协议规范、TypeScript编译器机制以及现有代码索引类工具后，形成的独立分析。截至2026年7月，代码图谱类MCP工具已经出现了不止一种，各自在实现方式和宣称的降幅上都有差异。本文会在这个背景下，拆解「基于编译器构建图谱」这一选择为何关键，以及Token消耗降低的机制究竟是什么。

一、代码图谱与MCP：两者如何协同工作

用一句话概括代码图谱MCP：把代码库预先读懂、整理成地图，再交给智能体使用的工具。拆成两个部分来看会更清楚。

1.1 代码图谱：把结构变成坐标

代码图谱是一种数据结构，把代码库里的符号（函数、类、类型、变量）当作节点，把它们之间的调用、继承、导入、类型引用关系当作边。面对「谁调用了这个函数」「这个类型在哪里被使用」这类问题，不需要翻遍文件，沿着图谱的边就能直接得到答案。关键在于，这张图谱不是在智能体提问的那一刻现算的，而是在离线索引阶段就预先构建好。智能体每次收到问题时，面对的不是要重新分析的源代码，而是一份已经画好的地图，只需要查询。

1.2 MCP：把地图交给智能体的标准通道

Model Context Protocol是Anthropic于2024年11月发布的开放标准，用于规范LLM智能体与外部工具、数据源之间的通信方式。把代码图谱包装成MCP服务器后，Claude Code这类智能体就能按统一协议向图谱发起查询，并获得结构化的返回结果。截至2026年，MCP已经成为事实标准，Claude Code、Cursor、Codex、Windsurf、Zed、Continue.dev、Cline、Goose等主流编程工具几乎都已支持，社区中已有超过5000个MCP服务器。代码图谱本身并非新概念——静态分析工具早在数十年前就已存在——但正是MCP这个标准接口的出现，才让「智能体直接查询图谱」这种组合真正落地为可用的工程实践，这是本人的判断。

1.3 本案例的核心设计

原帖强调的设计有两点。第一，图谱返回的内容不包含源码正文，只给出名称、边、签名、file:line范围等紧凑坐标。第二，通过某种机制强制智能体按照固定的推理顺序行动，避免它拿到图谱后仍然漫无目的地探索。作者在8个仓库与4个模型的组合上做了基准测试，宣称Token消耗降低约10倍，同时保持了回答质量。这个数字来自特定基准环境，不宜当作放之四海而皆准的固定值，更合理的解读是「借助图谱作为中介，量级上的Token节省是可能的」这一方向性结论。

二、Token消耗为何能降低：探索成本才是真正的根源

这是本人认为最值得深挖的部分。Token节省的来源不是「生成」环节，而是「探索」环节。

2.1 智能体的探索成本远比想象中高

Claude Code这类智能体在陌生代码库中工作时，消耗的Token有相当一部分花在「找代码」上：用grep筛出候选文件、用glob列出文件清单、打开其中几个看看、发现不是想要的又重新查找，如此循环。这个循环本身不断填满上下文窗口。据观察，在一个约200个文件规模的代码库中，一小时的工作里，仅探索环节消耗的Token就可能达到8万到15万——这部分成本花在「认路」上，而不是真正的「做事」上。没有代码图谱时，智能体每次都要从零重复这套探索流程。

2.2 压缩后的返回结果带来的差异

代码图谱MCP的核心在于，它返回的不是整份文件，而是目标位置的坐标。面对「谁调用了这个函数」这样的问题，如果返回的是5个相关函数的名称与文件位置，智能体可以直接跳转到那些坐标，只读取需要的那几行。相比反复通读整份文件，直接命中精确坐标所节省的Token，会随代码库规模增大而呈近乎指数级扩大。10倍这个数字之所以出现，合理的解释是：在大型仓库里，探索环节原本的往返次数就多，图谱消除了这部分低效，效果自然被放大。

2.3 强制推理顺序的作用

仅仅提供图谱数据并不够。如果智能体拿到图谱后仍然习惯性地重新通读整份文件，或者在无关节点之间漫游，节省效果就会打折扣。原帖提到的「强制系统化推理」，本人理解为通过提示词或工具设计，强制智能体遵循「查询图谱→缩小目标范围→只读取必要片段」这样固定的顺序。这与本人另外查阅到的Chain-of-Thought相关研究结论相呼应——例如「Focused Chain-of-Thought」一类研究表明，把信息检索与推理步骤分离、强制结构化的推理顺序，能在保持推理质量的同时把生成的Token减少2到3倍。也就是说，这类工具的节省效果，是图谱这种数据结构与强制使用方式的工具设计两者共同作用的结果，而不是单靠图谱数据本身。

三、为什么specifically要用TypeScript编译器API

截至2026年，代码图谱类MCP工具已经不止一种。本人查阅到的方案大致分为三类：基于Tree-sitter等解析器支持多语言的工具、基于向量嵌入寻找语义相似代码的工具，以及像本案例这样直接调用特定语言编译器的工具。这里值得深入分析为什么选择编译器API这条路。

3.1 启发式解析器的局限

Tree-sitter一类语法解析器能快速且准确地识别代码的语法结构——括号在哪里打开闭合、哪个节点是函数声明。但「这个变量的实际类型是什么」「这条导入经过几层re-export之后到底来自哪里」「泛型如何被具体化」，这些属于语义解析层面的问题，语法分析本身回答不了，只能靠堆叠启发式规则去近似。近似必然带来误报和遗漏。

3.2 编译器已经掌握了正确答案

TypeScript编译器为了真正构建项目，会解析所有模块、推断所有类型、确定所有引用关系。这个过程结束后，类型检查器内部状态中已经包含了「谁精确引用了谁」这个问题的答案。把代码图谱构建在编译器API之上，意味着直接复用这个已有答案，而不是重新去猜测它。无论re-export链条有多少层，类型别名有多复杂，因为这些关系都是编译器已经解析确定的，图谱中的边与代码实际行为出现偏差的概率很低。这与AutoBE等其他TypeScript生态AI编程工具的思路相呼应——它们把编译器嵌入到API层面，用来校验AI生成代码的正确性。两者背后是同一个原则：在需要确定性判断的地方，用编译器给出的真相，而不是近似值。

3.3 成本转移到了索引阶段

不过这不是没有代价的。基于编译器的分析比Tree-sitter更重、更慢。但这份成本不是每次智能体请求时都要支付，而是集中在索引阶段一次性（或代码变更时增量）支付。换句话说，把繁重的运算提前放到离线阶段完成，线上只留下轻量级的查询。本人认为，这种成本时点的转移，正是代码图谱MCP这类工具整体的设计哲学所在。

四、在大型代码库中的价值

这种方法的价值与代码库规模成正比。小型个人项目里，读几个文件和查询图谱之间的差别微乎其微。但实际工程中面对的代码库通常不是这个量级。

4.1 文件数量增长时，探索往返呈组合式增长

文件数从200增长到2000，「看起来相关的候选文件」集合也会随之膨胀。一次grep命中的行数、需要逐一查看的候选文件数都会同步增加。代码图谱把这种组合式增长吸收进预先整理好的边列表里。规模越大，「提前整理好」与「每次重新查找」之间的差距就越明显，因此本人预期，大型单体仓库、历史悠久的遗留代码库，从中获益的幅度会更大。

4.2 对重构与影响范围分析尤其有效

「修改这个函数会影响到哪些地方」本质上是一个图遍历问题。有了代码图谱，回答这类问题不需要翻遍文件，只需沿着图谱的反向边精确追踪。这与本人查阅到的其他同类工具（例如面向代码评审场景的图谱工具，号称能把评审场景的Token消耗降低约49倍）不谋而合——它们都把「影响范围（blast radius）分析」列为核心使用场景。在大规模重构或代码评审这类需要反复追问「这次改动会波及哪里」的工作中，图谱带来的收益最为明显。

4.3 在新人上手与文档缺失的代码库中的作用

文档不完善、原作者已经离开的代码库，新加入者（无论是人还是智能体）摸清结构的成本都相当高。代码图谱把这种隐性结构变成显性数据。这对人类同样有用，但对上下文有限的AI智能体而言尤为关键——智能体没有「花时间慢慢熟悉代码库」这个选项，图谱实际上承担了替代性记忆的角色。

五、与相似方案的比较：LSP、向量索引

代码图谱MCP并非唯一解法。据本人查阅，至少有三条路线在同时演进，各自的权衡取舍并不相同。

5.1 与LSP（Language Server Protocol）的差异

LSP是编辑器与语言服务器通信、实现跳转到定义或自动补全的标准协议，TypeScript的tsserver本质上也扮演这个角色。但LSP的设计目标是「某一时刻的单次请求-响应」——询问光标所在位置的定义在哪里、当前可用的补全有哪些。智能体若想借助LSP掌握整个代码库的结构，就必须发起数以百计的往返查询，每一次都叠加协议开销与网络延迟。代码图谱MCP消除了这种往返，预先把「整体结构」构建成可以一次性查询的形式。可以说LSP更像是一问一答式的对话，代码图谱则更接近直接交出一整份预先画好的地图。

5.2 与向量嵌入索引的差异

RAG（检索增强生成）风格的代码嵌入索引也被广泛使用，它把代码片段转成向量，用来寻找语义相似的内容，擅长回答「帮我找类似的代码」这类模糊查询。但对「谁精确调用了这个函数」这类需要确定性关系的问题，向量嵌入就显得力不从心，因为嵌入相似度只是近似值，不是确定的事实。代码图谱恰好相反：擅长确定性关系，弱于模糊检索。本人认为，实际工程中这两种方式更可能是互补关系而非竞争关系——「找相似代码」交给嵌入索引，「精确追踪依赖关系」交给图谱。

5.3 语言通用性上的取舍

基于Tree-sitter的工具优势在于能用同一套框架支持多种语言。相比之下，基于编译器API的方案精度更高，却需要为每种语言单独实现。还要指出的是，TypeScript恰好是编译器在API层面完全开放、类型系统足够强大的语言，这类方案对它格外友好。要在其他语言上达到同等精度，需要该语言的编译器与类型检查器同样在API层面充分暴露，而并非所有语言都具备这样的基础设施。

结语：规模越大、精度要求越高，越值得关注

截至2026年7月，代码图谱MCP与其说是一个成熟标准，不如说是一个正在快速扩张的实验性生态。这次基于TypeScript编译器的案例之所以值得关注，并不只是因为「预先建图、只做查询」这个想法本身，而是因为它选择了把编译器已经确定的答案直接搬进图谱这条路径。用确定性取代近似，用离线索引取代每次请求重新计算，这两个转变才是Token节省真正站得住脚的依据，这是本人的判断。

不过，也需要对10倍这个数字保持必要的怀疑。它来自特定仓库与模型组合的基准测试，在小型项目或探索成本本来就低的任务中，节省幅度很可能小得多。此外，额外运维一条索引流水线的负担，以及基于编译器方案固有的语言锁定问题，同样需要纳入考量。如果日常工作是在大型TypeScript代码库中反复用AI智能体做重构或影响范围分析，值得亲自接入这类代码图谱MCP，在自己的工作流里同时测量Token消耗与回答质量的变化。如果已经在使用LSP或向量索引，更现实的做法是考虑并行使用，而非直接替换。
