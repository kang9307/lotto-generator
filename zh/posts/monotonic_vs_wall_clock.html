用墙上时钟测量经过时间会得到负数 - 该用单调时钟的地方

两个时钟回答的是不同的问题 - 现在几点,以及过了多久

2026-07-30 开发/基础设施

症状:处理时间日志里印着一个负数

设想某天早上仪表盘上出现 duration_ms: -2760。这条日志说一次请求花了负 2.7 秒才处理完。打开代码却看不出任何问题。开始时记一次时刻,结束时再记一次,相减。没有比这更简单的计算了。

然而这个简单的计算依赖于一个假设:第二次读到的时刻必然大于第一次。墙上时钟并不保证这一点。在这期间可能有人把时钟改了。

本文的结论不是「请使用单调时钟」。那样的建议只会作为一条规则留下,而规则会被忘掉。换个说法来整理。两个时钟回答的是不同的问题。

  • 墙上时钟回答「现在几点」。它是人读的时刻,是可以和别的机器比较的时刻,是可以写在日历上的时刻。代价是它可以被外部修正
  • 单调时钟回答「过了多久」。它的参考点是任意的,所以那个数值本身没有任何含义。只有读两次相减得到的差才有含义。代价是谁也无法把它往回拨
  • 所以墙上时钟不能作为经过时间的依据。一旦把它当作依据,「可以被外部修正」这个性质就会原样渗入测量值
  • 反过来,单调时钟不能成为给人看的时刻。用它给日志打时间戳会印出 1970 年,而且无法和另一台服务器的日志对齐

把这个区分刻进身体的最快途径是亲眼看到负数出现的那一刻。所以本文从运行开始。十二组实验分别在 Node、Python 和 shell 里跑过,下面所有代码块都是那些输出的原样照录。

运行环境。所有输出都是在 Windows 10 Pro (10.0.19045) 上真实运行的结果。运行时为 Node.js v22.16.0 (win32) 与 Python 3.13.3,shell 为 GNU bash 5.2.37 (MSYS2/MinGW64)。所有脚本都保存为文件后执行。

系统时刻一次也没有改动。那需要管理员权限,而且会破坏环境。取而代之的是把时刻跳变注入进去。在程序读取墙上时钟的位置放一个 Date.now() + offset 形式的函数,并在测量过程中改变那个 offset。这与时间同步阶梯式移动时钟时程序所看到的形状相同。单调时钟一侧读的是未加改动的真实值。

本文不涉及的内容。时钟为什么会偏、如何诊断同步状态,都不在范围内。这里只讲到「时钟可能往回走」这个事实为止,然后集中在一个点上:测量经过时间该用哪个时钟。时区规则以及对过去时刻的重新解释也在本文范围之外。

2. 结束减开始变成负数的那一刻

现在是本文的心脏。下面这段代码做 120 毫秒的工作,注入一次把时刻往回拨 3 秒的修正,再做 120 毫秒的工作,然后用结束时刻减去开始时刻。同一段区间也用单调时钟量了一遍。

--- 2-1. THE BUG: elapsed measured on a wall clock that gets corrected ---
start (wall)   : 1785385665815
end   (wall)   : 1785385663055
elapsed  WALL  : -2760 ms
elapsed  MONO  : 239.265 ms
wall elapsed is negative : true

--- 2-2. the same code, printed the way a service logs it ---
{"msg":"request done","duration_ms":-2760,"clock":"wall"}
{"msg":"request done","duration_ms":239.3,"clock":"monotonic"}

--- 2-3. forward jump: the request looks 10 minutes long ---
elapsed WALL : 600050 ms   (10.00 min)
elapsed MONO : 49.368 ms

elapsed WALL : -2760 ms。实际干了 240 毫秒的活,墙上时钟却回答负 2.76 秒。同一段区间用单调时钟量出来是 239.265 ms。服务如果照原样打日志,留下的那一行就是 duration_ms:-2760。就是开头那一行。

  • 结束时刻小于开始时刻。1785385663055 小于 1785385665815,因为时钟在这期间往回走了
  • 代码里没有 bug。减法是准确的。错的是「第二个值大于第一个」这个假设
  • 单调时钟对同样的注入毫无反应。因为注入只加在读墙上时钟的位置,单调时钟读的是原样的真实值。按规范,这个时钟不是调整的对象
  • 反方向也是同一个缺陷。下面 2-3 把时钟往前拨 10 分钟,一个 50 毫秒的作业被记成 600050 ms,也就是 10 分钟。这比负数更危险。负数会被注意到,10 分钟看起来却很合理
--- P-4. THE BUG: elapsed on a wall clock that gets corrected ---
start (wall)  : 1785385835.713235
end   (wall)  : 1785385832.953251
elapsed WALL  : -2759.984 ms
elapsed MONO  : 240.017 ms
wall elapsed is negative : True

what a handler would log:
{"msg": "job finished", "elapsed_ms": -2760.0, "clock": "wall"}
{"msg": "job finished", "elapsed_ms": 240.0, "clock": "monotonic"}

在 Python 里做同样的实验,连数值都几乎一样:-2759.984 ms。这说明它不是语言的问题,而是时钟性质的问题。Python 官方文档对 time.time() 写着「如果在两次调用之间系统时钟被往回调整过,它可能返回比前一次更小的值」。也就是说这不是 bug,而是规范里写明的行为。

关于注入方式。系统时刻并未改动。做法是在程序读取墙上时钟的函数上加一个偏移量,造出「这个程序看到的墙上时钟突然移动了」的状态。这与时间同步做阶梯式修正、或者有人手工改时刻时程序所看到的形状相同。单调时钟一侧没有加偏移,读的是真实值,所以两列的对比如实反映了两个时钟的真实差异。

不过,不这样做也能确认。Python 的 time.get_clock_info() 会自己报告 time 是 adjustable=True、monotonic=False。这两个值本身就等于「这个时钟可以被移动,而且可能往回走」这句陈述。注入实验只是展示这句陈述落到代码里是什么样子。

2.1 时钟往回走的那些情形

「时钟往回走」听起来像稀奇事,实际上却是寻常运维活动的结果。下面整理了在哪种情形下往哪个方向移动多少。移动的幅度很关键。毫秒级的修正会悄悄过去、日志里什么都不留;秒级的阶梯式修正会立刻造出负数。

触发原因方向幅度在测量中呈现的样子
时间同步的阶梯式修正两个方向都有数百毫秒 至 数十秒经过时间变成负数或被夸大。本文复现的就是这一种
时间同步的渐进式修正两个方向都有把频率略作调整单调时钟也会受影响。clock_gettime(2) 写着它「会受到频率调整的影响」。但它不会往回走
有人手工修改两个方向都有分钟 至 小时 至 天最大的跳变。在开发机和新建服务器上很常见
虚拟机暂停后恢复通常向前与暂停时长相同恢复之后墙上时钟一次性跳过去
容器或虚拟环境更换时间源两个方向都有取决于配置宿主与客户机原本报告不同的值,然后被对齐的那一刻
开机后立刻从硬件时钟读取通常向前秒 至 小时在开机早期启动的测量会在第一次同步时被破坏

3. 分辨率是另一个问题 - 而且流行说法是错的

经常能看到这样的解释:「墙上时钟分辨率低,所以要用单调时钟」。这句话只对了一半。实际量了一下。用统计连续调用中数值不变的次数的办法,求出最小刻度。

--- 3-1. resolution measured by counting repeats  (node) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
Date.now()           400000   38              14402               1 ms
performance.now()    400000   292699          1                   0.000100 ms
hrtime.bigint()      400000   400000          0                   100 ns

--- P-5. resolution measured by counting repeats  (python) ---
clock                calls    value changed   max identical run   smallest step
-------------------------------------------------------------------------------
time.time()            300000   199586          2                   0.000238 ms
time.monotonic()       300000   300000          0                   0.000100 ms
time.perf_counter()    300000   300000          0                   0.000100 ms
time.monotonic_ns()    300000   300000          0                   100 ns
time.perf_counter_ns() 300000   300000          0                   100 ns
  • Node 的 Date.now() 在 40 万次调用里数值只变了 38 次。同一个值最多连续出现 14,402 次,最小变化幅度是1 毫秒。比毫秒更短的东西用这个时钟量不出来
  • 同一环境下 Python 的 time.time() 在 30 万次里变了 199,586 次。最小变化幅度是0.000238 毫秒,也就是 238 纳秒。get_clock_info() 报告的实现是 GetSystemTimePreciseAsFileTime()
  • 也就是说「墙上时钟很粗」这个流行说法会因语言和平台而错。在同一台机器的同一瞬间,一个墙上时钟的刻度是 1 毫秒,另一个是 238 纳秒
  • 然而分辨率高也解决不了问题。Python 的 time.time() 分辨率足够,却在第 2 节里同样给出了负数。分辨率与可调整性是相互独立的性质
  • 单调时钟一侧两种语言都是100 纳秒,而且同一个值一次都没有重复出现。在这个环境里 Python 报告 monotonic 和 perf_counter 都使用 QueryPerformanceCounter()

归纳起来就是:分辨率低就量不了短区间;可被调整就任何区间都不能信。前者是不便,后者是缺陷。所以使用单调时钟的第一个理由不是分辨率,而是adjustable=False。分辨率是顺带的赠品。

4. 量一个短于 1 毫秒的作业

分辨率在实务中长什么样,量一个短作业就立刻看出来。把一段约 0.1 毫秒的计算量了八次,墙上时钟和单调时钟并排打印。

--- 4-1. timing a sub-millisecond job  (node) ---
run   wall (ms)   hrtime (ms)
-------------------------------
  0           0        0.0936
  1           0        0.1429
  2           0        0.1023
  3           1        0.0722
  4           0        0.0920
  5           0        0.0800
  6           0        0.0703
  7           0        0.0704
wall reported 0 ms in 7 of 8 runs; hrtime never did

--- P-6. the same shape in python  (the job is slower here, so nothing rounds to 0) ---
run   time.time (ms)   monotonic (ms)   perf_counter (ms)
----------------------------------------------------------
  0          8.4169           8.4145              8.4111
  1          6.5217           6.5193              6.5173
  2          3.9151           3.9138              3.9123
  3          5.2114           5.2096              5.2072
  4          4.4210           4.4193              4.4176
  5          5.6825           5.6805              5.6788
  6          4.7274           4.7255              4.7237
  7          2.3925           2.3920              2.3909
time.time() gave exactly 0 in 0 of 8 runs; monotonic() gave 0 in 0 of 8
  • 在 Node 里八次中有七次是 0 ms。剩下一次是 1 ms,正好越过毫秒刻度的那一次。真实开销每次都是 0.07 至 0.14 毫秒
  • 也就是说透过这个时钟看,这个作业是「0 毫秒或 1 毫秒」。实际上有些次的差距达到两倍,而那些差距全部消失了
  • Python 一侧一个 0 都没有。同样的计算在 Python 里要 2 至 8 毫秒,已经爬到毫秒刻度之上,而且它的墙上时钟分辨率本来就高得多。也就是说这个症状会随语言和作业规模显现或隐藏
  • 有一个实务上的含义。「我们的代码里没出现过 0,所以没事」这个判断很危险。一旦作业变快或运行时换了,0 就开始出现。等于性能优化把测量搞坏了

5. 同一区间量 100 次,分布就塌了

量一次就完事的代码很少见。通常会反复测量再算平均值和分位数。把同一个作业量了 100 次,比较两个时钟给出的分布。

--- 5-1. same interval, 100 samples, two clocks  (node) ---
clock                 mean       min        max        median    distinct values
---------------------------------------------------------------------------------
Date.now()           0.0700     0.0000     1.0000     0.0000    2
performance.now()    0.0738     0.0702     0.1177     0.0703    24
wall samples that came out exactly 0 : 93 / 100

--- P-7. same interval, 100 samples, three clocks  (python) ---
clock                   mean      min       max       median    distinct   zeros
------------------------------------------------------------------------------
time.time()             3.1561    2.1367    9.7034    2.3899    98         0
time.monotonic()        5.3347    2.1219    47.3406   3.3695    100        0
time.perf_counter()     4.1934    2.1830    12.9886   3.2359    100        0
  • 在 Node 里平均值几乎相同:墙上时钟 0.0700,高分辨率时钟 0.0738 毫秒。所以只看平均值,好像什么问题都没有
  • 但墙上时钟一侧不同的取值刚好只有 2 个,即 0 和 1,而且 100 个样本里有 93 个正好是 0。高分辨率时钟给出了 24 个不同的取值
  • 最小值 0、最大值 1 意味着没有分布。中位数是 0,读起来就是「这个作业不花时间」
  • Python 一侧三个时钟都给出了合理的分布。有一点值得注意:time.monotonic() 的最大值跳到了 47.34 毫秒。这不是时钟的缺陷,而是测量期间真的发生了调度延迟的证据。时钟诚实地把它记下来了

6. 把短测量累加起来 - 结果和预期不同

直觉上,把粗时钟量出的值不断相加,误差应该会累积。实际量了一下。把同一个作业单独测量 2000 次后累加,并一并给出分位数。

--- 6-2. what quantization destroys: the shape, not the sum ---
metric over 2000 identical jobs      wall(Date.now)   perf(performance.now)
-----------------------------------------------------------------------------
total ms                             168.00           166.54
mean ms                              0.0840           0.0833
p50 ms                               0.0000           0.0743
p95 ms                               1.0000           0.1076
p99 ms                               1.0000           0.1519
distinct values                      2                562
samples equal to 0                   1832             0
the totals nearly agree. every percentile is wrong

--- 6-3. spending a 20 ms budget on the same job, two clocks ---
clock                iterations   budget left   hit the cap
---------------------------------------------------------------
Date.now()           221          0.000         false
performance.now()    238          -0.120        false

总和几乎一致:168.00 对 166.54 毫秒。原因是这样的。作业约需 0.084 毫秒,所以大约 8% 的次数会越过毫秒边界,那些次被记为 1 ms,从而把被丢掉的小数部分补了回来。舍入误差不会偏向一侧。在 Python 里累加 1500 次的结果误差也在 0.1% 之内。

--- P-8. summing many short measurements  (python) ---
1500 iterations of the same tiny job
sum of per-iteration time.time() deltas      5310.879 ms
sum of per-iteration monotonic() deltas      5309.157 ms
sum of per-iteration perf_counter() deltas   5306.933 ms
one outer perf_counter() measurement         5311.884 ms
  error of time.time() sum                   -1.005 ms  (-0.0 %)
  error of monotonic() sum                   -2.727 ms  (-0.1 %)
  error of perf_counter() sum                -4.952 ms  (-0.1 %)
  • 所以「累积误差会让总和偏掉」这个预期在这个环境里没有得到确认。与预期不符,就照实写下来
  • 塌掉的是分布。中位数是 0.0000,p95 和 p99 并排停在 1.0000。既然只有 2 个不同的取值,分位数这个概念本身就不成立
  • 在实务中这一点更痛。总和与平均值在仪表盘上看起来很合理,而一张写着「p99 延迟贴在 1 毫秒上」的图,看的是测量刻度,而不是服务
  • 6-3 是用单独测量去扣减 20 毫秒预算的实验。墙上时钟跑了 221 次,高分辨率时钟跑了 238 次,相差约 7%。总和可以一致,但一旦把单独测量当作判断条件,结果就分岔了

7. 超时与重试 - 事故在这里变大

到这里讲的都是数字变得不对。接下来转向行为变得不对。把 500 毫秒的重试预算钉在墙上时钟的绝对时刻上,并在第二次尝试之后注入一次把时钟往前拨 1 小时的修正。

--- 7-1. a wall-clock deadline expires the instant the clock is corrected ---
budget 500 ms of retries, clock steps +3600 s (1 h forward) after attempt 2
 WALL deadline:
  attempt 1: ok, remaining=500 ms
  attempt 2: ok, remaining=470 ms
  << clock stepped 3600 s >>
  attempt 3: ABORT deadline exceeded, remaining=-3599560 ms
  -> attempts completed: 2 of 6, aborted=true
 MONOTONIC deadline:
  attempt 1: ok, remaining=500.0 ms
  attempt 2: ok, remaining=470.8 ms
  << clock stepped 3600 s >> (monotonic unaffected)
  attempt 3: ok, remaining=440.8 ms
  attempt 4: ok, remaining=410.9 ms
  attempt 5: ok, remaining=380.9 ms
  attempt 6: ok, remaining=350.8 ms
  -> attempts completed: 6 of 6, aborted=false

墙上时钟那一侧在第三次尝试时立刻放弃了,因为剩余预算算出来是 -3599560 ms。实际只花了 60 毫秒,500 毫秒的预算却被当成已经耗尽。单调时钟那一侧六次全部跑完。反方向更糟。

--- 7-2. and a backward step makes the same deadline unreachable ---
deadline was set 200 ms out, then the clock stepped -86400 s
remaining according to the wall clock : 86399880 ms  (24.00 h)
real time actually spent waiting      : 319.6 ms (loop cut off by a guard)
without the guard this loop waits a full day for a 200 ms deadline

--- 7-3. sleep-until-instant vs sleep-for-duration ---
sleep until wall instant 1785385765471 :
  if the clock is stepped +1000 s first -> wakes immediately, 0 ms of real waiting
  if the clock is stepped -1000 s first -> waits ~1001 s of real time
sleep for 1000 ms (setTimeout, libuv timer) :
  setTimeout(1000) fired after 1013.7 ms of monotonic time
  the -50000 ms wall step did not move it
  • 向前跳 → 立刻到期。一次重试都不剩就结束了。在故障处理过程中校准时刻,那一瞬间所有重试逻辑会同时放弃
  • 向后跳 → 永远不会结束。本来设在 200 毫秒之后的截止时间,等于被推到了 24 小时之后。墙上时钟算出的剩余时间是 86399880 ms,即 24 小时。实验里靠保护措施切断了循环;没有保护就要等一整天
  • 「睡到某个时刻」和「睡这么长」是两条不同的指令。前者会被时钟修正裹走,后者不会
  • 在 7-3 里,即使把墙上时钟往回注入 50 秒,setTimeout(1000) 仍然在单调时间 1013.7 毫秒后准确触发。这说明运行时的定时器本来就架在单调时钟之上
  • 也就是说运行时给你的定时器是安全的,自己算出来的截止时间才危险。只要能把「N 秒之后」交给框架,就交给它

这一节最危险的原因。前面几节的症状是数字变得不对,看日志就能发现。这一节的症状是行为变得不对,而日志里只留下「超时」两个字。于是排查自然而然地转向网络和对端服务器。从那里走到「原因是自己代码里选错了时钟」这一步,路非常远。

8. 缓存过期与限流 - 同一缺陷的另一张脸

与超时完全相同的计算也存在于缓存和限流里:存下「现在 + TTL」,之后再拿它和「现在」比较。放入 5 个 TTL 为 60 秒的条目,在真实时间完全没有流动的状态下只移动时钟。

--- 8-1. a TTL cache keyed on wall instants ---
5 entries, ttl 60 s, nothing has actually elapsed
  before step   wall-cache live=5   mono-cache live=5
  clock +3600 s wall-cache live=0   mono-cache live=5   get(k0)=(expired)
  -> the whole cache evaporates in one tick. every caller goes to the origin at once
  clock -3600 s wall-cache live=5   mono-cache live=5   get(k0)=v0
  -> entries now outlive their ttl by an hour. stale data served as fresh

把时钟往前拨一小时,存活条目数从 5 个变成 0 个。缓存在一个时钟节拍里被清空了。往后拨则相反,本该过期的条目继续活着。限流的结构也一样。

--- 8-2. a fixed-window rate limiter on the same clock ---
 WALL limiter, 3 req / 1000 ms:
   r1 window_age=0ms count=1 -> ALLOW
   r2 window_age=0ms count=2 -> ALLOW
   r3 window_age=0ms count=3 -> ALLOW
   r4 window_age=0ms count=4 -> REJECT
   << clock stepped +5 s, no real time passed >>
   r5 window_age=0ms count=1 -> ALLOW   <- quota reset for free
   << clock stepped back to where it was >>
   r6 window_age=-5000ms count=2 -> ALLOW   <- window frozen, it will never roll again
 MONOTONIC limiter, same sequence:
   r1 window_age=1ms count=1 -> ALLOW
   r2 window_age=1ms count=2 -> ALLOW
   r3 window_age=1ms count=3 -> ALLOW
   r4 window_age=1ms count=4 -> REJECT
   << clock stepped +5 s >>
   r5 window_age=1ms count=5 -> REJECT   <- still rejected, correctly
  • 向前跳 → 缓存被清空。问题不是「缓存空了」,而是所有调用方同时涌向源站。它表现为时刻修正之后源站负载突然抬升
  • 向后跳 → 过期被推迟。get(k0)=v0 原样返回了。本该过期的值被当作新鲜的提供出去。这一侧不会报任何错误。只是旧数据流了出去
  • 限流会白送配额。把时钟往前拨 5 秒,原本被拒绝的请求变成了 ALLOW,因为被算成开了一个新窗口
  • 拨回来窗口就冻住了。window_age=-5000ms。窗口年龄是负数,于是永远无法满足让窗口继续滚动的条件,此后计数器只会一直往上涨
  • 换成单调时钟的那一侧在同样的顺序下正常地继续拒绝。时钟注入完全没有触及判断

9. 日志时间戳必须是墙上时钟

这里把方向翻过来。前面讲的都是不该用墙上时钟的地方。也有不该用单调时钟的地方。下面把单调时钟的值直接当时间戳打出来。

--- 9-1. the reverse mistake: a monotonic value cannot be a timestamp ---
monotonic reading                  : 20810933.933
formatted as if it were epoch ms   : 1970-01-01T05:46:50.933Z
wall reading                       : 1785385762171
formatted                          : 2026-07-30T04:29:22.171Z
a log line stamped with the monotonic value says 1970 and cannot be compared to any other machine

--- 9-2. the line that carries both ---
{"ts":"2026-07-30T04:29:22.176Z","duration_ms":44.628,"route":"/v1/orders"}
ts is orderable across hosts and readable by a human; duration_ms cannot go negative
  • 把单调时钟的值格式化成时间戳,得到 1970-01-01T05:46:50.933Z。既然参考点不是纪元,这是必然的结果
  • 无法和别的机器对齐。两台服务器的参考点互不相同,比较这两个数字毫无意义。分布式追踪就在这里崩掉
  • 人读不了。「故障在 20810933.933 开始」这句话支撑不了任何行动
  • 保留策略也会卡住。「删除超过 30 天的日志」这类规则需要绝对时刻才能判断

所以答案不是「挑一个」,而是两个各就各位一起用。9-2 里的那一行就是这个形状。ts 用墙上时钟写「什么时候」,duration_ms 用单调时钟写「多久」。这样时间戳既能与其他主机排序又能被人读懂,而耗时绝不会变成负数。一行里出现两个时钟并不奇怪,而是正确的。

10. 进程重启之后参考点就变了

单调时钟参考点任意这一事实还有一个实务后果:那个值不能保存。把同一个脚本作为两个连续进程跑了一遍,比较取值。

--- 10-1. the monotonic origin is per boot and per process ---
field                   previous process     this process         delta
---------------------------------------------------------------------------------
pid                     14920                17368                -
Date.now()              1785386114435        1785386117740        3305 ms
hrtime.bigint()/1e6     21163198.428         21166503.246         3304.818 ms
performance.now()       1869.676             1882.334             12.658 ms
performance.timeOrigin  1785386112566.207    1785386115858.01     3291.803 ms

--- 10-2. so a persisted monotonic deadline is meaningless after restart ---
saved by the previous process : performance.now() + 30000 = 31869.676
this process reads it back and compares to its own performance.now() = 1885.058
  remaining, as computed      : 29984.557 ms
  real time between the runs   : 3305 ms (from the wall clock)
  the two numbers are unrelated. performance.now() restarts near 0 in every process
  • Date.now() 在两个进程之间增加了 3305 毫秒,这是真实流过的时间。不同进程看的是同一个坐标系
  • hrtime.bigint() 也增加了 3304.818 毫秒。这个时钟的参考点是开机而不是进程,所以能跨过重启延续下来
  • performance.now() 只增加了 12.658 毫秒。流过了 3.3 秒,它却只走了 12 毫秒,因为这个时钟在每个进程里都从 0 重新开始。文档里那句 0 表示当前进程的起点,被这个数字证实了
  • 10-2 就是它的后果。后一个进程读回前一个进程保存的截止时间并计算,得到剩余 29984 毫秒。实际上已经过了 3.3 秒,它却回答「还剩 30 秒」。这两个数字毫无关系
数值是否可以保存或传输原因
Date.now() / ISO 字符串可以所有机器都以同一含义读取的绝对时刻
performance.now()不可以参考点是本进程。重启就回到 0
process.hrtime.bigint() / time.monotonic()不可以参考点是本次开机。重启机器就失去意义
用单调时钟量出的区间长度可以两个读数之差只是一个毫秒计数,没有参考点
performance.timeOrigin可以它本身就是墙上时钟的值。与偏移量配对即可还原绝对时刻

11. 挂起期间由谁来计数

单调时钟内部也有分支:机器挂起期间计数器是停住还是继续走。只在这个环境能确认的范围内量了一下。把单调时钟的读数,和根据操作系统报告的开机时刻算出的墙上时钟经过时间并排放在一起。

--- P-9. does the monotonic clock count time spent suspended? ---
time.monotonic() here            : 20892.159 s  (5.80 h)
implementation                   : QueryPerformanceCounter()
OS-reported last boot time       : 2026-07-30T07:42:31.500000+09:00
wall seconds since that boot     : 20892.807 s  (5.80 h)
difference (wall-since-boot minus monotonic) : 0.648 s

POSIX names for the distinction (not reproducible on this host):
  CLOCK_MONOTONIC  - does not step; on Linux it does NOT include suspend
  CLOCK_BOOTTIME   - same, but DOES include suspend
  CLOCK_REALTIME   - the wall clock, may be stepped
  time.CLOCK_MONOTONIC      available in this build : False
  time.CLOCK_BOOTTIME       available in this build : False
  time.CLOCK_MONOTONIC_RAW  available in this build : False
  time.CLOCK_REALTIME       available in this build : False
  • 两个值相差 0.648 秒。单调时钟读数为 20892.159 秒,以开机时刻为基准的墙上时钟经过为 20892.807 秒。5.8 小时里差 0.6 秒
  • 这台机器在测量窗口内从未进入挂起状态,所以这个方法无法观察挂起是如何处理的。0.6 秒在开机时刻报告精度与开机后时刻修正所能解释的范围内
  • 挂起与休眠的区间在这个环境里无法直接复现。所以下面的区分仅依据文档写出。这是本文唯一没能直接复现的项目
  • clock_gettime(2) 文档对 CLOCK_MONOTONIC 写着「这个时钟不计入系统处于挂起状态的时间」,对 CLOCK_BOOTTIME 写着它「与 CLOCK_MONOTONIC 相同,但也包含系统处于挂起状态的时间」。Python 文档对 time.CLOCK_BOOTTIME 的说明也是同一含义

实务上的判断。对服务器进程来说这个区分几乎不成问题,因为它不会挂起。会成问题的是跑在笔记本和手持设备上的代码。在合盖再开盖之间,基于 CLOCK_MONOTONIC 的超时不会计入那段时间。它的形状就是「5 分钟后会话过期」熬过一整夜也没过期。如果挂起的时间也必须算作已经流过,那么 CLOCK_BOOTTIME 才对;而如果过期本来就是以人所认知的绝对时刻为准,那么一开始就该用墙上时钟的绝对时刻。这种情况请看第 14 节表格里的「过期」那一行。

12. shell 里没有单调时钟

shell 脚本几乎没有工具能回避这个问题。把 shell 能读到的时钟全部打印了出来。

bash 5.2.37(1)-release / msys

--- S-1. the clocks a shell can read ---
date +%s          : 1785385886
date +%s%N        : 1785385886351968200
EPOCHSECONDS      : 1785385886
EPOCHREALTIME     : 1785385886.364763
SECONDS           : 0
all of these trace the wall clock. bash exposes no monotonic clock.

--- S-3. SECONDS advances with the wall clock, not with work done ---
SECONDS after sleep 2        : 2
date delta                   : 2132 ms

timeout available here : /usr/bin/timeout
Usage: timeout [OPTION] DURATION COMMAND [ARG]...

date、EPOCHSECONDS、EPOCHREALTIME、SECONDS 全都跟着墙上时钟走。也就是说纯 shell 语法没有任何途径能碰到单调时钟。这就让 shell 里最常见的下面这个写法在结构上很危险。

# the deadline loop everyone writes - both date calls are on an adjustable clock
end=$(( $(date +%s) + 30 ))
while [ "$(date +%s)" -lt "$end" ]; do
    check_ready && break
    sleep 1
done

# the portable fix: stop computing the deadline yourself
timeout 30 sh -c 'until check_ready; do sleep 1; done'
  • 不要自己算截止时间,这才是答案。把「N 秒内」交给 timeout,截止时间的运算就离开了 shell。这个环境里也有 /usr/bin/timeout
  • 调用 date 本身也很贵。S-2 里 200 次调用的最小变化幅度是48 毫秒。这不是时钟分辨率,而是创建进程的开销。在循环里读时刻的脚本每一轮都要付这笔钱
  • 不要把等待表达成绝对时刻。写成「N 秒内」而不是「到几点」
  • 如果真的需要精确测量,就不要在 shell 里做。哪怕只有一行,交给有单调时钟的运行时更好

13. 在既有代码里找出用错的时钟

接下来是诊断。好在这个缺陷用搜索几乎能全部找到,因为错误用法会以语法形状显露出来。用四个模式来做。

# A. elapsed  -  the subtraction of two wall readings
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. deadline / expiry  -  a wall reading with something added to it
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. the reverse mistake  -  a monotonic reading assigned into stored state
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. everything already monotonic, to confirm it is used as a difference
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/

实际跑了一遍。造了两个混有各种时钟用法的示例文件,再套上上面的模式。下面就是那些输出。

--- 12-1. pattern A: subtraction of two wall readings (the smoking gun) ---
./src/handler.js:7:  const ms = Date.now() - t0;                   // can go negative
./src/worker.py:10:    elapsed = time.time() - start             # can go negative

--- 12-2. pattern B: a deadline built by adding to a wall reading ---
./src/handler.js:13:  const deadline = Date.now() + budgetMs;       // wall-clock deadline
./src/handler.js:28:  CACHE.set(key, { value, expiresAt: Date.now() + ttlMs });   // wall instant
./src/worker.py:15:    deadline = time.time() + timeout_s        # wall-clock deadline

--- 12-4. pattern D: the reverse mistake, a monotonic reading assigned into state ---
./src/worker.py:51:    state["saved_at"] = time.monotonic()
--- 12-5. every monotonic reading, to confirm the ones that are fine ---
./src/handler.js:32:  const t0 = process.hrtime.bigint();           // correct: monotonic
./src/handler.js:34:  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
./src/worker.py:33:    start = time.monotonic()                  # correct: monotonic
./src/worker.py:36:    emit_metric("batch_seconds", time.monotonic() - start)
./src/worker.py:51:    state["saved_at"] = time.monotonic()

--- 12-6. triage counts ---
files with a wall-clock subtraction   : 2
wall-clock deadline sites             : 3
monotonic readings already present    : 5

模式 A 是最强的信号。把一个墙上时钟值减去另一个,几乎无例外地就是经过时间计算,也几乎无例外地是错的。模式 B 需要判断。截止时间和 TTL 必须改,但令牌过期、预定时刻这类绝对时刻本来就正确的情况也会一起命中。所以搜索只是开始,还需要评审。评审时该问的句子如下。

  • 这个值是要给人看,还是要把两个值相减?要相减就用单调时钟。这一句就能分开大部分情况
  • 这个时刻会离开进程吗?只要被保存、被传输,或者要和别的机器比较,就必须是墙上时钟
  • 这个截止时间是「到几点」还是「持续这么久」?后者就用单调时钟。如果是用户指定的「到下午 6 点」,那就该用前者
  • 这个值变成负数会发生什么?如果答案是「不知道」或者「不可能」,那个位置就是危险位置
  • 这个过期需要跨过进程重启继续有效吗?如果需要,就不能保存由单调时钟造出的值
// before - the duration can come out negative
const t0 = Date.now();
const out = doWork(req);
log({ ts: new Date().toISOString(), duration_ms: Date.now() - t0 });

// after - wall clock names the instant, monotonic clock measures the span
const t0 = process.hrtime.bigint();
const startedAt = new Date().toISOString();
const out = doWork(req);
log({ ts: startedAt, duration_ms: Number(process.hrtime.bigint() - t0) / 1e6 });
# before
start = time.time()
run_batch(items)
emit_metric("batch_seconds", time.time() - start)

# after
started_at = datetime.datetime.now(datetime.timezone.utc)
start = time.monotonic()
run_batch(items)
emit_metric("batch_seconds", time.monotonic() - start, ts=started_at)

修法就像上面两段那样简单。用墙上时钟把开始时刻记一次留下「什么时候」,区间测量另外用单调时钟做。多了一行,换来的是负数消失。有一点值得回头看。12-5 把所有单调时钟用法都抽出来时,四处正确用法之外还一起命中了一处保存单调时钟值的地方。「我们在用单调时钟」并不是安全的证据。还得看是怎么用的。

  • Node 的 process.hrtime.bigint() 与 performance.now() 参考点不同:前者是开机,后者是进程。第 10 节用实测确认过。测量区间两者都能用,但两者都不能保存
  • Python 的 monotonic 与 perf_counter 在这个环境里是同一个实现,都是 QueryPerformanceCounter()。在别的平台上可能分岔,所以精确测量用 perf_counter更稳妥
  • 「单调」和「高分辨率」是不同的性质。正如第 3 节所见,墙上时钟分辨率更高的组合确实存在。这两个性质要分别确认
  • 如果语言不在表里,只需确认两件事:这个时钟的参考点是什么,它会不会被外部调整。这两个答案就决定了时钟的用途

15. 这个缺陷为什么总是很晚才爆

这个缺陷最糟的性质不是技术性的,而是它被发现的方式。

  • 它平时是完全准确的,因为两个时钟并排走。第 1 节的增量就说明了这一点。所以它通过测试、通过评审,活好几年
  • 出错的瞬间很短。时刻修正是一瞬间的事,而且测量区间必须正好跨在那一瞬间上才会出症状。概率很低
  • 它复现不了。要调查就得移动时钟,而那是调查者不故意去做就不会发生的事
  • 症状不指向原因。「超时」「缓存未命中激增」「p99 异常」全都指向别处。在怀疑到时钟之前会走好几次弯路
  • 于是它就以「偶尔会不对」的形式留下来。工单以无法复现结案,下次又发生一遍

正因为这个性质,应对的顺序要反过来。通常是出了症状再修。这个缺陷不能等症状,因为从症状走到原因的概率很低。相反,把第 13 节的搜索跑一遍,在预算之内清理掉要便宜得多。模式足够简单,即使在很大的仓库里也是几分钟的事。

最后再用一句话写一遍判断标准。这个数字是要给人看,还是要从另一个数字里减掉?给人看就用墙上时钟,要相减就用单调时钟。这一个问题就替代了本文所有的表格。

16. 检查清单

下面每一项在前面的运行里都有依据。按顺序过一遍即可。

  • 测量经过时间的地方已经把墙上时钟的相减全部清掉(第 13 节模式 A)
  • 超时与重试预算表达为「持续这么久」,而不是绝对时刻截止
  • 缓存 TTL 与限流窗口以单调时钟为基准
  • 日志时间戳来自墙上时钟,耗时来自单调时钟,两者在同一行里
  • 没有任何地方保存或传输单调时钟的值(第 13 节模式 D)
  • 耗时指标有对负数的防御,而且出现负数时不是把它藏起来,而是留下告警
  • 量短区间的地方用的是高分辨率时钟。分位数没有贴在刻度上
  • 如果是跑在笔记本或手持设备上的过期逻辑,已经定好了挂起区间如何计数(第 11 节)

最后一件事。发现负数时不要给它套绝对值,也不要压成 0。那是在擦掉证据。负数是这个缺陷真的发生过的唯一明确信号,而正如本文所见,向前跳的情况连这样的信号都不会留下。如果你能看到负数,反而算是运气好的一侧。在那个位置把时钟换掉就是了。

参考资料

# 墙上时钟 vs 单调时钟 — 用途选择表与代码检查模式

> 出处: braindetox.kr — 用墙上时钟测量经过时间会得到负数
> 依据: 在 Windows 10 / Node 22.16.0 / Python 3.13.3 / bash 5.2.37 (MSYS2) 上运行验证
> 把这份文件原样贴给 AI,写上「按这些标准检查一下我们代码里的时钟用法」即可。

## 0. 大前提 — 两个时钟回答不同的问题

| | 墙上时钟 (wall clock) | 单调时钟 (monotonic clock) |
|---|---|---|
| 回答的问题 | **现在几点** | **过了多久** |
| 数值的含义 | 相对纪元的绝对时刻 | 距任意参考点的距离 |
| 是否受外部调整 | **会** | 不会 |
| 是否可能往回走 | **可能** | 不可能 |
| 能否跨机器比较 | 能 | **不能** |
| 能否保存或传输 | 能 | **不能** (只有差值可以) |

**这个数字是要给人看,还是要从另一个数字里减掉?**
给人看就用墙上时钟,要相减就用单调时钟。这一句话替代了下面所有的表格。

## 1. 按用途选择

| 用途 | 时钟 | 典型错误与症状 |
|---|---|---|
| **测量经过时间** | 单调 | 墙上时钟相减 → **耗时变成负数** |
| **超时与重试预算** | 单调 | 绝对时刻截止 → 立刻到期或无限等待 |
| **限流窗口** | 单调 | 墙上时钟窗口 → 白送配额、窗口冻结 |
| **缓存 TTL** (进程内) | 单调 | 墙上时钟过期时刻 → 缓存被清空或提供旧值 |
| **重试退避间隔** | 单调 | 以墙上时钟为准等待 → 间隔乱掉 |
| **日志与审计时间戳** | 墙上时钟 | 单调值 → **印出 1970 年** |
| **计划任务**「每天 09 时」 | 墙上时钟 | 单调时钟根本无法表达 |
| **过期** (令牌、会话、证书) | 墙上时钟 | 保存单调值 → 重启之后失去意义 |
| **性能剖析** | 单调且高分辨率 | 粗的墙上时钟 → 分位数贴在刻度上 |

## 2. 按语言的 API 对照表

| 用途 | Node.js | Python | POSIX / C | shell |
|---|---|---|---|---|
| 测量经过时间 | `process.hrtime.bigint()` | `time.perf_counter()` | `CLOCK_MONOTONIC` | **无** |
| 测量经过时间 (替代) | `performance.now()` | `time.monotonic()` | `CLOCK_MONOTONIC_RAW` | **无** |
| 当前时刻 | `Date.now()` | `time.time()` | `CLOCK_REALTIME` | `date`, `EPOCHREALTIME` |
| 包含挂起的经过 | 无标准 API | `time.CLOCK_BOOTTIME` | `CLOCK_BOOTTIME` | **无** |
| 进程 CPU 时间 | `process.cpuUsage()` | `time.process_time()` | `CLOCK_PROCESS_CPUTIME_ID` | `times` |
| 等待一段时长 | `setTimeout` | `time.sleep()` | `clock_nanosleep` | `sleep`, `timeout` |
| 查看时钟性质 | 查文档 | **`time.get_clock_info()`** | `clock_getres` | 不适用 |

- Node 的 `hrtime.bigint()` 参考点是**开机**,`performance.now()` 参考点是**进程** (已实测确认)
- Python 里 `time.get_clock_info('time')` 会直接告诉你 `adjustable=True`, `monotonic=False`
- 如果语言不在表里,只确认两件事: **参考点是什么 / 会不会被外部调整**

## 3. 代码搜索模式

```bash
# A. 经过时间 — 墙上时钟值的相减 (最强信号,几乎全是错的)
grep -rnE 'Date\.now\(\) *- *|time\.time\(\) *- *' src/

# B. 截止与过期 — 往墙上时钟值上加东西 (需要评审)
grep -rnE '(Date\.now\(\)|time\.time\(\)) *\+' src/

# C. 反向错误 — 单调时钟值被赋给会被保存的结构
grep -rnE '(\[[^]]+\]|\.[a-zA-Z_]+) *= *(time\.)?(monotonic|perf_counter|performance\.now|process\.hrtime)' src/

# D. 所有单调时钟用法 — 确认每一处都只作为差值使用
grep -rnE 'monotonic\(\)|perf_counter\(\)|hrtime\.bigint\(\)|performance\.now\(\)' src/
```

- **A 几乎全部需要修改。** 墙上时钟相减实际上就是经过时间计算
- **B 需要判断。** 截止时间与 TTL 要改,令牌过期与预定时刻则保持原样
- **在 D 里命中也不能放心。** 使用单调时钟和正确使用单调时钟是两回事

## 4. 评审检查句

- [ ] **这个值是要给人看,还是要把两个值相减?** 相减就用单调时钟
- [ ] **这个时刻会离开进程吗?** 被保存、被传输或跨机器比较就必须用墙上时钟
- [ ] **这个截止时间是「到几点」还是「持续这么久」?** 后者用单调时钟
- [ ] **这个值变成负数会发生什么?** 如果答案是「不可能」,那个位置就危险
- [ ] **这个过期需要跨过进程重启继续有效吗?** 需要的话就不能保存单调值
- [ ] **区间是不是很短?** 毫秒刻度的墙上时钟会给出 0
- [ ] **是否跑在会挂起的设备上?** `CLOCK_MONOTONIC` 不计入挂起时间

## 5. 修改后的形状

```javascript
// before — 耗时可能变成负数
const t0 = Date.now();
const out = doWork(req);
log({ ts: new Date().toISOString(), duration_ms: Date.now() - t0 });

// after — 墙上时钟负责「什么时候」,单调时钟负责「多久」
const t0 = process.hrtime.bigint();
const startedAt = new Date().toISOString();
const out = doWork(req);
log({ ts: startedAt, duration_ms: Number(process.hrtime.bigint() - t0) / 1e6 });
```

```python
# before
start = time.time()
run_batch(items)
emit_metric("batch_seconds", time.time() - start)

# after
started_at = datetime.datetime.now(datetime.timezone.utc)
start = time.monotonic()
run_batch(items)
emit_metric("batch_seconds", time.monotonic() - start, ts=started_at)
```

```bash
# before — 两次 date 调用都架在可被调整的时钟之上
end=$(( $(date +%s) + 30 ))
while [ "$(date +%s)" -lt "$end" ]; do check_ready && break; sleep 1; done

# after — 把截止时间的运算推出 shell
timeout 30 sh -c 'until check_ready; do sleep 1; done'
```

## 6. 实测参考值 (Windows 10 / Node 22.16.0 / Python 3.13.3)

| 时钟 | 最小刻度 | 备注 |
|---|---|---|
| Node `Date.now()` | **1 ms** | 40 万次调用中数值只变了 38 次,同一值最多连续 14,402 次 |
| Node `performance.now()` | 0.0001 ms | — |
| Node `hrtime.bigint()` | 100 ns | 40 万次调用彼此各不相同 |
| Python `time.time()` | **0.000238 ms** | 实现为 `GetSystemTimePreciseAsFileTime()` — **墙上时钟也可能是高分辨率的** |
| Python `monotonic` / `perf_counter` | 100 ns | 两者都是 `QueryPerformanceCounter()` |
| shell `date +%s%N` 往返 | 约 48 ms | 不是时钟分辨率,而是**创建进程的开销** |

**分辨率与可调整性是相互独立的性质。** 分辨率足够的 Python 墙上时钟,遇到时刻修正照样给出负数。

## 7. 不要做的事

- ❌ 把耗时的负数**套上绝对值或压成 0** — 这是在擦掉证据,而向前跳的情况连这样的信号都没有
- ❌ 把单调时钟的值**保存到文件、数据库或响应体里** — 进程一换就失去意义
- ❌ 用「到几点」表达的**重试截止时间** — 时刻修正会让它立刻到期或永远不结束
- ❌ 在日志时间戳里用**单调值** — 会印出 1970 年,而且无法和其他主机对齐
- ❌ **只看平均值就了事** — 在粗时钟上总和是对的,塌掉的只是分位数
- ❌ 在 shell 循环里**自己计算截止时间** — 它架在可被调整的时钟上,`date` 的调用开销也不小
- ❌ 抱着「我们不会改时刻」的前提 — 时间同步、虚拟机恢复、手工修改都是寻常运维活动
