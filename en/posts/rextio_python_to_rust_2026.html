Moving Python to Rust - The Line an Automatic Converter Draws

The boundary a conversion tool drew, and how to redraw it for your own codebase

Jul 29, 2026 Tech & IT

Introduction: the condition dropped from 「it converts Python to Rust」

Tools that promise to carry Python code across into Rust have been arriving for several years now, and July 2026 produced another one: a project called Rextio. The reflex on reading an announcement like that is to ask 「so can it move our code?」, and that question is almost always the wrong one. The question that actually leads somewhere is which parts of my code possess the property of being movable at all, and the answer is settled by the nature of the code rather than by the capability of the tool.

Open the Rextio repository documentation and you find that the tool states this before the reader has to. It does not move a codebase. It lowers into Rust and PyO3 only those type-annotated functions that fall inside a predefined subset, and it leaves everything else exactly as it was in Python. The contract sentences the repository publishes are short. When it is not certain, it does not guess; it falls back. And a function is either natively compiled with semantics equivalent to CPython, or it is rejected with a diagnostic and stays in the Python fallback.

One boundary of my own before going further. This article does not recommend or evaluate the specific tool called Rextio. The repository marks itself as alpha stage, several features carry an experimental label, and at the time I checked the star count was still in single digits. This is not something to put into production today. What interests me is one thing only: where the line falls between what a machine can move and what it cannot, and how the position of that line changes practical judgment.

1. What Rextio actually does - only what the documentation confirms

First, be precise about the category of tool. Rextio is not the kind of thing where you hand code to a conversational LLM and ask it to rewrite the file in Rust. It is a deterministic tool built from a static analyser and a code generator. It reads the Python AST, accepts only the functions that land inside its supported range, and rejects the rest while emitting a diagnostic message. The artifact is not a pure Rust program but a hybrid package in which a native extension and a Python fallback ship together.

The execution flow is correspondingly simple. It scans the source for native candidates, rejects the ineligible ones, generates Rust and PyO3 code for the accepted ones, builds a Python fallback wrapper for everything else, and packages the whole thing as an import-compatible artifact.

python -m pip install rextio

rextio check .                      # diagnostics only: what lowers to native, what gets rejected
rextio build . --fallback=cpython   # build the hybrid package

REXTIO_NATIVE_MODE=fallback python app.py   # turn native off at runtime, take the pure Python path

The third line is the one to notice. A switch that turns native off at any moment is present in the design from the beginning. The repository documentation compresses this into a single sentence: native is an optimisation, not a requirement. If the native module is missing, or fails to load, the package keeps running through the Python fallback. I will come back to this later, but it deserves stating early: this switch is an item you must reproduce yourself even if you never touch this tool.

The operating requirements are CPython 3.11 or newer, with the documentation claiming verification up to 3.14, and a Rust minimum supported version of 1.83 or newer. The licence is MIT. The benchmarks the repository publishes are reproduced below. Every figure in this table is copied directly from the repository documentation and is not something I reproduced on my own hardware.

WorkloadMedian speedup over 3 runsHow to read it
Core hybrid57.729xA pure computation loop running entirely inside the supported subset
pandas Series.map66.143xA stretch where a user-defined function call repeated per element
NetworkX Dijkstra3.679xOnce graph library calls enter the mix, the multiple drops sharply

The lesson to take from this table is not the large numbers at the top but the numbers near 1x at the bottom. The repository documentation says so itself: results vary by workload, and values near 1x represent parity rather than a meaningful improvement. Where the heavy computation has already been lowered into C or into a native library, the time the Python interpreter was burning is small to begin with, so there is nothing left to reclaim. That single observation is the theme of this entire article.

2. What automatic conversion cannot do, on principle

Read the list of things Rextio says it does not support and the character of the problem separates out cleanly. Classes and instance methods, dynamic attribute access, generators, async and await, context managers, aliased mutation of mutable collections, iteration over set[float], star expressions and star imports, dynamic code execution, and most third-party calls without a plugin.

That list is not an accident. It is not a roadmap of features a young project has yet to reach; it is the wall that the static-conversion approach itself runs into. Setting out why each item is a wall produces the table below.

Property on the Python sidePoint of collision in RustWhy mechanical conversion is impossible
Duck typing and dynamic attribute accessStatic types and trait resolutionWhat is only decided at call time cannot be fixed at compile time
Generators and coroutinesState machines that own their dataThe lifetime of every reference alive at each suspension point has to be proved statically
Aliased sharing of mutable objectsThe borrow checkerCode where several names mutate the same object simultaneously collides head-on with the ownership model
Control flow driven by exceptionsResult return valuesReconstructing the flow requires globally tracing which exception is caught where
Atomicity assumptions that presuppose the GILExplicit synchronisationCode that was accidentally safe thanks to the GIL becomes a race the moment it moves
Arbitrary precision integersFixed width integersThe same int has different overflow boundary behaviour on each side
NaN inside a set of floatsHashing and equality rulesNaN is not equal to itself, so deduplication results diverge

The last two rows of that table are the most practically dangerous. The fact that a type with the same name does not carry the same meaning is what produces the quietest accidents in automatic conversion. This is the class of failure where the code compiles cleanly, the tests pass, and values diverge only on a specific input.

From all of this, one summary is available. The territory an automatic converter can handle is Python in appearance and, in substance, a statically typed language subset. Complete type annotations, local variables only, pure functions where nothing crosses the boundary but scalars and simple containers. Code of that shape was already easy to move to Rust by hand. Conversely, the code you most desperately want to move, the business logic that grew over years, is generally outside that subset.

  • Do not read a rejection as a failure — a tool rejecting a function is correct behaviour. A tool that accepts everything without ever rejecting anything is the one you should be nervous about.
  • The diagnostics are the real product — the value of a command like rextio check is not the conversion but the measurement of how static your code actually is. If the rejection rate is 90 percent, that codebase is not a candidate for this approach.
  • The cost starts the moment you reshape code to fit the subset — unrolling classes into functions and turning generators into lists to satisfy the tool moves that code away from Python idiom. That price has to go into the calculation.
  • Third-party calls are effectively a wall — one call into a library that is not on the supported list drops the whole function to fallback. In real business code the number of functions that satisfy this condition is smaller than intuition suggests.

3. Establish the cause of 「it is slow」 first

There is a gate every language-change decision has to pass before anything else happens. Is the reason it is slow actually the language? A large share of the issues that arrive labelled as performance problems have nothing to do with interpreter speed, and splitting them by cause changes the prescription completely.

Symptom and causeHow to confirm itExpected effect of moving to RustWhat to do first
Network and disk waitingGap between wall clock time and CPU timeAlmost noneConcurrency, connection pooling, batching
N+1 queriesLog the query count per requestNone, and possibly worseJoins, prefetching, caching
Serialization and deserializationMeasure payload size and parse time separatelyModerate, and much of it recoverable by swapping the parser aloneFormat, column pruning, streaming
Algorithmic complexityDouble the input size and observe the growth rateConstant factor only, the order stays the sameChange the data structure
GIL contentionThroughput does not rise as thread count risesLarge, but only after the cause is confirmedProcess separation, evaluate free threading
Interpreter overheadTop functions by self time are pure Python loopsLarge. This is the only justified caseIdentify the hot path, then an extension module

The order of confirmation starts with a profiler. Sorting by self time rather than cumulative time is what makes the actual burn site visible, because cumulative time only tells you that everything near the top of the call stack is slow.

# Sort by self time; cumulative time hides the real burn site
python -m cProfile -o prof.out run_workload.py

# In the interactive browser, type: sort tottime, then stats 20
python -m pstats prof.out

What comes next matters even more. Measure what share of the total the hot path represents, and compute the ceiling on the improvement before writing any Rust. Skipping this arithmetic is how teams spend several weeks to buy a single-digit percentage gain.

# Overall speedup when a hot function is a fraction p of total time and gets s times faster
def upper_bound(p: float, s: float) -> float:
    return 1.0 / ((1.0 - p) + p / s)

print(upper_bound(0.20, 50))   # 1.2437...  -> a 20% overall reduction is the ceiling
print(upper_bound(0.70, 50))   # 3.2051...  -> this is where the investment starts paying
print(upper_bound(0.20, 1000)) # 1.2496...  -> infinite speed still cannot beat 1.25x

The third line is the conclusion. When the hot path is a small share of the total, making it infinitely fast still does not make the system fast. If you want one operational threshold to carry away, use this one: when the sum of the top functions by self time is under 40 percent of total execution time, remove language change from consideration entirely. Above 60 percent it is worth evaluating, and above 80 percent it is usually the right thing to do.

4. The practical answer is a hot-path extension module, not a full port

If you have made it this far, there are two options on the table. Rewrite the whole application in Rust, or carve out only the hot path as a native extension module and leave the rest in Python. The conclusion first: for most organisations the second is correct, and the conditions that justify the first are very narrow indeed.

The reason lies in boundary cost. Between Python and native code there is a conversion cost paid every time a value crosses. That cost is incurred per function call and grows with the complexity of the data being moved. This is why a badly designed extension module ends up slower than pure Python. Rextio itself reflects this problem explicitly in its design: containers are not permitted to cross the native boundary at all, and only immutable scalars such as int, float, bool, str and None may be passed into a fallback function. It even carries a rule that demotes to fallback any function that would repeatedly cross the boundary.

The design principles for an extension module follow directly from that constraint.

  • Do not call per element — calling a million times for a million elements makes the boundary cost dominate the computation cost outright. Hand the whole array across in a single call.
  • Keep the data that crosses the boundary simple — nested dictionaries and user-defined objects carry heavy conversion cost. Numeric arrays, byte buffers, and flat lists of strings are the ideal shapes.
  • Do not pass callbacks across — if the native code calls back into a Python function, you round-trip the boundary once per element. When this structure appears, the boundary has been drawn in the wrong place.
  • Make the boundary a pure function rather than a stateful object — putting long-lived mutable state on the native side brings ownership problems and thread safety problems at the same time.
  • Do not place the boundary where the interface changes often — lowering a function whose signature changes weekly means re-running the entire build matrix weekly.
  • Do not delete the pure Python implementation — the cost of maintaining two implementations side by side is far smaller than the risk of arriving at a state you cannot reverse out of.

The same problem viewed through a different pair of languages is written up in the Go to Rust migration guide. That case turns on a choice between two compiled languages, so the axes of judgment differ, but the coexistence patterns and the anti-signals overlap almost exactly with what is described here.

5. PyO3 and maturin - drawing the boundary in code

Once you have decided to carve out the hot path, the actual tools are PyO3 and maturin. PyO3 is the binding layer that connects Rust and Python, and maturin builds the result into a Python wheel. What follows uses the declarative module syntax from the 0.29 line, the most recent release on the official PyO3 repository. PyO3 0.29 supports CPython 3.9 and newer, and its minimum supported Rust version is 1.83.

# Cargo.toml
[package]
name = "hotpath"
version = "0.1.0"
edition = "2021"

[lib]
name = "hotpath"
crate-type = ["cdylib"]

[dependencies]
pyo3 = "0.29.0"

// src/lib.rs
#[pyo3::pymodule]
mod hotpath {
    use pyo3::prelude::*;

    /// Takes the whole array and processes it in one pass.
    /// Not calling per element is the entire point of this design.
    #[pyfunction]
    fn clip_and_scale(values: Vec<f64>, lo: f64, hi: f64, k: f64) -> PyResult<Vec<f64>> {
        Ok(values
            .into_iter()
            .map(|v| v.clamp(lo, hi) * k)
            .collect())
    }
}

maturin new -b pyo3 hotpath   # generate the project skeleton
cd hotpath
maturin develop               # install straight into the current virtualenv (iterative development)
maturin build --release       # produce a distributable wheel under target/wheels

On the Python side, wrap the native and the pure implementation under the same name, but keep the road back open. This is the environment variable switch from the earlier section, built by hand rather than inherited from a tool.

# myapp/kernel.py
import os

from myapp import kernel_py   # the original pure Python implementation

_impl = kernel_py

if os.environ.get("MYAPP_NATIVE", "1") != "0":
    try:
        import hotpath as _native
        _impl = _native
    except ImportError:
        pass   # keeps working on platforms where no wheel was built

clip_and_scale = _impl.clip_and_scale

Swallowing the ImportError is the crucial detail here. The package must install and run even on platforms where the native extension does not exist, and that single property simplifies distribution enormously. With this structure in place you can compare both implementations by flipping one environment variable when you suspect a performance regression, and you can revert during an incident without cutting a new release.

6. How far down to push native code - a decision table

Whether to lower a given function to native is not a question to settle by instinct. Run it through the six conditions below in order, and adopt the rule that a single no anywhere means it does not get lowered. In practice that rule survives contact with reality better than any weighted scoring scheme.

CheckPassing thresholdPrescription when the answer is no
Share of total execution timeAt least 20 percent by self timeLook somewhere else first
Work per callMilliseconds or more of computation per single callBatch it up to cut the number of calls
Shape of the data crossing the boundaryScalars, flat arrays, byte buffersFlatten the interface before anything else
Frequency of interface changeOnce per quarter or lessDefer until the design has settled
People who can read and fix RustTwo or moreSecure the people first. One person is organisational debt
Pure Python alternative retainedAlways retained, plus a revert switchIf you cannot revert, do not ship it yet

The fifth item is the one most often waved away. An extension module turns into a black box the instant the person who wrote it leaves. When a bug appears in a Rust extension inside a team that is now entirely Python developers, there are exactly two options: find someone who can fix it, or revert to pure Python. Honour the sixth item and the second option is a thirty-second job. Skip it and the same situation becomes a multi-week incident.

For balance, let us also write down the conditions under which a full port is worth evaluating. All four must hold at once. The artifact must itself be the unit of distribution, meaning a tool or a library core. The external interface must be narrow and stable. The bulk of execution time must be CPU computation. And the team must already contain people who work in Rust as a primary language.

7. What the Rust rewrites actually proved

A handful of projects get cited constantly as success stories for Rust rewrites in the Python ecosystem. Reproducing only the figures their own official materials claim, the picture looks like this.

ProjectWhat the official material statesTarget area
ruffThe repository states it is 10-100x faster than existing linters (Flake8) and formatters (Black). Written in Rust, MIT licensedStatic analysis tooling
uv8-10x faster than pip and pip-tools without a cache, and 80-115x with a warm cache. Virtualenv creation is roughly 80x faster than python -m venv and 7x faster than virtualenvPackage management tooling
pydanticThe official documentation describes the core validation logic as written in Rust and, as a result, among the fastest data validation libraries in PythonLibrary core
CPython itselfThe official blog announced that the Rust for CPython plan is running a proof of concept implementing one extension module in Rust, targeting 3.16, with a PEP in preparationInterpreter internals

What matters in this list is not the multiples but the shared characteristics. None of the four is a business application. Each is a development tool, or the validation core of a library, or interpreter internals. They share three properties.

  • The interface is narrow and has been stable for years — a linter takes source files and returns a list of diagnostics. That contract has not moved in years.
  • Most of the execution time is CPU computation — parsing, rule matching and dependency resolution are all time the interpreter was burning.
  • The distribution unit is already a binary wheel — the user has no need to know what language the source is written in. Per-platform wheels are the whole contract.

Stated in reverse, there is no basis for expecting the same outcome from code that does not satisfy those three conditions. A web application that makes three database round trips per request sits on the opposite side of all three. When you cite a success story, look also at which territory that story belongs to.

For completeness, attempts to move entire large codebases into Rust using AI agents also appeared several times during 2026, and what those attempts proved versus what they did not is handled separately in the Grit rewrite of Git in Rust. The point is the same: having been moved and having been verified are two different sentences.

8. The other side of the ledger - learning curve, build time, ecosystem gaps

Migration discussions usually calculate the benefits and stop. The costs on the other side get ignored because they are not billed at adoption time; they arrive starting about six months later. Splitting them by category makes them concrete enough to argue about in advance.

8.1 Build time is a measured problem

The 2025 compiler performance survey results published on the official Rust blog collected more than 3,700 responses, and overall satisfaction was reported at 6 out of 10. The figures worth noting are these.

  • Roughly 45 percent of respondents who had stopped using Rust cited long compile times as one of their reasons for stopping.
  • 55 percent reported waiting 10 seconds or more for a rebuild after editing code. The bottlenecks were summarised as three things: unnecessary rebuilds triggered by workspace changes, a slow link step, and incremental compilation within a single crate.
  • About 33 percent named waiting for IDE inline annotations as a major obstacle, and more than 35 percent called the problem of the IDE and Cargo blocking each other a major issue.
  • Among the 1,495 respondents using CI, roughly 25 percent named CI build performance as a major problem, and of those, about 36 percent were using no caching in CI at all.
  • Roughly 42 percent of all respondents said they had never tried a single build performance improvement measure.

The last two items deserve to be read backwards. A substantial share of the complaints comes from headroom that has not been touched yet. Concluding that 「Rust is slow」 without having applied caching, a faster linker, or workspace splitting is drawing a conclusion from an unconfigured baseline. That said, if nobody on your team is going to perform those measures, the real cost stays exactly where the survey found it.

8.2 Distribution gains an extra axis

A pure Python package needs one wheel and it is done. The moment a native extension is attached, you need builds for the product of platform times architecture times Python version. Using the stable ABI collapses the Python version axis, but in exchange restricts which APIs you may call. On top of that come cross compilation, code signing, and registration with any internal mirror. None of this is a one-time build: it repeats every time a new Python version ships.

8.3 People are the most expensive item

  • Someone who can read it is not the same as someone who can fix it — the threshold for fixing is being able to meet an ownership or lifetime error and resolve it independently.
  • It has to enter the on-call rotation — if exactly one person can respond when that module breaks at four in the morning, the module is a single point of failure.
  • A review bottleneck appears — if one person can review Rust code, that person's holiday is a deployment freeze.
  • Hiring conditions change — turning one Python position into a position requiring both Python and Rust shrinks the candidate pool and stretches the time to fill.

8.4 Ecosystem gaps

There are things that already exist on the Python side and either do not exist on the Rust side or exist at lower maturity. Domain-specific numerical libraries, a particular vendor's client SDK, an internal standard logging and tracing layer. This is another reason the carve-out-the-hot-path approach wins. Draw the boundary narrowly and the set of Rust libraries you need shrinks in proportion. The argument that pushes rewrites on memory safety grounds, and the counterargument to it, are written up separately in the memory safety absolutists debate.

9. How to verify the generated Rust code

Whether the code came from a tool or from a person, whether the two implementations really produce the same answer has to be proved separately. Successful compilation guarantees nothing. Organised into an executable form, verification is three steps.

9.1 Differential testing - same input, two implementations

# tests/test_parity.py
import math
from hypothesis import given, settings, strategies as st

from myapp import kernel_py            # the original pure Python implementation
import hotpath                          # the native implementation

FINITE = st.floats(allow_nan=False, allow_infinity=False, width=64)

@settings(max_examples=1000)
@given(st.lists(FINITE, max_size=4096), FINITE, FINITE, FINITE)
def test_same_output(values, lo, hi, k):
    if lo > hi:
        lo, hi = hi, lo
    expected = kernel_py.clip_and_scale(values, lo, hi, k)
    actual = hotpath.clip_and_scale(values, lo, hi, k)
    assert len(expected) == len(actual)
    for a, b in zip(expected, actual):
        assert math.isclose(a, b, rel_tol=1e-12, abs_tol=0.0)

The moment you introduce a tolerance when comparing floating point values, you must record in the documentation that you are verifying approximation rather than equality. For domains where the last digit carries meaning, such as accounting or settlement, do not set a tolerance at all. Move the computation to integer or decimal types instead.

9.2 Edge cases do not appear at random

Property testing broadens coverage, but the most dangerous inputs generally do not get drawn. Keep them in a separate fixed list.

EDGE_CASES = [
    [],                       # empty input
    [0.0], [-0.0],            # zero and negative zero differ at the bit level
    [float("inf"), float("-inf")],
    [float("nan")],           # not equal to itself; sorting and dedup diverge here
    [1e308, -1e308],          # just short of overflow
    [1.0] * 1_000_000,        # large enough to expose the cost of copying across the boundary
]
  • Integer overflow — Python integers are arbitrary precision and Rust's i64 is fixed width. In a release build the overflow wraps around and silently produces a wrong value. Confirm without fail whether large integers can reach the function you are moving.
  • Sign of the remainder operation — Python's % follows the sign of the divisor while Rust's % follows the sign of the dividend. -7 % 3 is 2 in Python and -1 in Rust. Use rem_euclid to match Python's behaviour.
  • Sort stability — check whether the original order is preserved when two elements compare equal on the key. Different stability guarantees mean the order of the result list diverges.
  • Dictionary insertion order — Python dictionaries preserve insertion order. Rust hash maps do not. If any consumer depends on that order, you have an incident waiting.
  • Unicode length — the length of a Python string is a count of code points while Rust's len() returns a byte count. Port slicing indices across unchanged and the result is broken strings.
  • Exception types and messages — if the caller branches on the exception type, that type has to match as well. Check also whether any code depends on the message string.

9.3 Test the revert path before release

The environment variable switch built in the earlier section is not finished once it exists. Run the full test suite against the pure Python path once per release, and only then is that path guaranteed to still be alive. The failure mode I see most often in practice is a switch that was built, never exercised for a year, and had already drifted out of interface compatibility by the time somebody actually needed it.

Verification itemMethodPassing criterion
Result equivalenceDifferential testing plus property testingZero mismatches across 1,000 or more random cases
Edge casesFixed list plus a review of rule differences between the two languagesEvery entry passes, exception types included
PerformanceMedian of 3 benchmark runs on a representative workloadFalling short of the target multiple means revisiting the boundary design
Fallback pathFull test suite with native disabledConfirmed passing on every release
Wheel distributionImport check on every supported platformInstalls and runs on unsupported platforms too

10. The variable that the GIL is going away

If parallelism is the reason you are evaluating Rust, factor in that the premise is currently shifting under you. CPython has shipped a free threading build with the GIL disabled since 3.13. It is not free, though. The official documentation states that the free threading build carries overhead relative to the default build, with average overhead in the range of roughly 1 percent on macOS aarch64 and roughly 8 percent on x86-64 Linux as measured by pyperformance.

There is one further clause that anyone building extension modules has to know. The official documentation records that some third-party packages with extension modules may not be ready for the free threading build and will re-enable the GIL. Importing a C-API extension module that has not declared free threading support automatically switches the GIL back on and prints a warning.

  • My extension module can kill someone else's parallelism — one extension that has not declared support revives the GIL for the whole process. If you distribute an extension module, that declaration is not optional.
  • If parallelism is the goal, the order is worth inverting — measuring how existing code behaves on the free threading build before changing language is the cheaper move.
  • Single-thread overhead varies by workload — the range quoted above is an average across a benchmark suite. You have to measure it against your own workload.
  • The interpreter itself is bringing Rust in — the official blog stated that the Rust for CPython plan is running a proof of concept implementing one extension module in Rust, targeting 3.16, with a PEP in preparation. Over the long run the surface where the two languages meet widens.

11. A procedure for deciding whether to adopt

Finally, here it is in transferable form. Follow this sequence as written and most evaluations reach a conclusion at step 3 or step 4.

  1. Fix one representative workload — it has to come from real production traffic. Synthetic benchmarks make the conclusion optimistic.
  2. Measure wall clock time and CPU time separately — a large gap between the two means the cause is waiting, and the language question ends right here.
  3. Extract the top functions by self time — looking at cumulative time only shows you the upper part of the call stack.
  4. Compute the ceiling from the combined share of those top functions — under 40 percent, stop here. It is time to fix something else.
  5. Look at algorithms and data structures first — if there is any change left that reduces the order of growth, that change always comes first.
  6. Check whether the code has already been lowered into C — time spent inside a numerical library leaves almost nothing to reclaim.
  7. Flatten the interface of the candidate boundary functions — finish this work in pure Python, with no Rust involved.
  8. Measure subset fit with a static analysis tool — a high rejection rate means automatic conversion is off the table and only manual porting remains worth evaluating.
  9. Move exactly one function, the highest-share one, and measure — one. Move several at once and you will not know which one produced the effect.
  10. Ship only after differential tests and a fallback path are in place — release only after confirming that the revert switch actually works.
  11. Re-measure with production metrics — confirm against the real latency distribution rather than the benchmark. If tail latency has not moved, another cause remains.
  12. Revert if there is no effect — keeping something because of how much work went into it is the most expensive choice available.

Conclusion: a tool can show you the boundary, it cannot set it

The largest value a tool like Rextio actually delivers is probably not the conversion but the diagnosis. Simply learning what percentage of your codebase is statically pinnable, and which functions are rejected and for what reason, is decision material you did not have before. The opposite scenario, taking whatever the tool generated and putting it into production as is, is not something to evaluate at all where an alpha-stage tool is concerned.

Reduce the sentence this article kept repeating to one line and it is this. The practical answer lies between rewriting everything and doing nothing, and which answer you get is determined by where you draw the boundary. Draw it well and you move 5 percent of the code, solve the majority of the performance problem, and keep Python's productivity across the remaining 95 percent. Draw it badly and you assemble a system that collects the disadvantages of both languages: builds are slow, exactly one person can fix the native module, and there is no way back.

And do not invert the order. Profiling comes first, algorithms come second, and language comes last. Follow that order and you discover that in most cases you never reach the language step at all, which is both the most common conclusion of this kind of evaluation and the cheapest one.
