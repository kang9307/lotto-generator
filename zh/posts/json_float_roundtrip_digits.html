引言 - 数变得不再相同的两个方向

double在内存中是64位，但在文件、日志、JSON和CSV中是文字。写出文字的瞬间与读回文字的瞬间之间用了几位，决定了值是否保持相同。这里的“往返”有两个方向，各自保证的位数不同。

  • 文字 → double → 文字：人写下的十进制字符串能否原样恢复。保证的位数是15。
  • double → 文字 → double：计算得到的值能否以相同的位恢复。需要的位数是17。
  • 把两个方向混在一起说“15位以内是安全的”，会让用15位保存计算结果的代码悄悄改变值。

本文要回答的问题如下。

  • 用6、9、15、16、17位写出的文字读回后，有多少个值的位不同。
  • Python的repr和JavaScript的toString选择的“最短往返表示”保证了什么。
  • 需要17位的值是什么样子。
  • Python、Node、PowerShell 5.1、awk和SQLite在不做任何设置时输出几位。
  • 工具之间值发生变化的情形，出在写入一侧还是读取一侧。

JSON数字精度文章的第8节用20万个样本统计了15、16、17位的失败个数。本文不重复那张表，而是讨论位模式、运算结果、15位以内输入这三种样本的对比，float32的6位和9位，工具的默认输出位数，以及工具间传递时变量的分离。

从位看0.1与0.1+0.2

Python官方教程的浮点数页面写道，IEEE 754 binary64的值有53位精度，0.1被近似为3602879701896397 / 2 ** 55。同一页说明0.1、0.10000000000000001和0.1000000000000000055511151231257827021181583404541015625都指向同一个近似值，所以显示其中任何一个都能保持eval(repr(x)) == x。下面的代码用位和十六进制来验证这一说明。

从输出可以读到的内容如下。

  • 0.1+0.2的位是3FD3333333333334，0.3的位是3FD3333333333333。最后一位不同，两者是不同的double。
  • 用%.15g写出0.1+0.2得到文字0.3，把这个文字读回会回到0.3的位(...333)，与原值不同。
  • 用%.17g写出得到0.30000000000000004，读回后回到原来的位(...334)。
  • 0.3周围相邻的double是0.29999999999999993、0.3和0.30000000000000004。17位是区分相邻值所需要的位数。
  • 用17位写0.1得到0.10000000000000001，repr给出0.1。两个字符串回到同一个double。

6、9、15、16、17位往返表 - 三种样本

下面的代码生成三种样本，把每个值用%.Ng写成文字，再读回float，并比较全部64位。A是随机64位模式中的有限值(整个指数范围)，B是常规范围内的运算结果(乘法和除法)，C是由有效数字1到15位输入的十进制文字生成的值。float32也用同样的方法统计。

import random, struct, math, sys
                    def bits(x): return struct.unpack('<Q', struct.pack('<d', x))[0]
                    def f32(x): return struct.unpack('<f', struct.pack('<f', x))[0]
                    def f32bits(x): return struct.unpack('<I', struct.pack('<f', x))[0]
                    print(sys.version.split()[0], 'float_info.dig =', sys.float_info.dig, ' mant_dig =', sys.float_info.mant_dig)
                    rnd = random.Random(20261006)
                    N = 100000
                    A = []
                    while len(A) < N:
                        x = struct.unpack('<d', struct.pack('<Q', rnd.getrandbits(64)))[0]
                        if math.isfinite(x): A.append(x)
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(N)]
                    C = [float('%.*g' % (rnd.randint(1, 15), rnd.uniform(-1e6, 1e6))) for _ in range(N)]
                    def fails(S, n):
                        return sum(1 for x in S if bits(float('%.*g' % (n, x))) != bits(x))
                    print('double, %d values per set; text = %%.Ng, then float(text), compare all 64 bits' % N)
                    print('%-4s %10s %10s %10s' % ('N', 'A:bitpat', 'B:arith', 'C:<=15dig'))
                    for n in (6, 9, 15, 16, 17):
                        print('%-4d %10d %10d %10d' % (n, fails(A, n), fails(B, n), fails(C, n)))
                    F = [f32(rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000)) for _ in range(N)]
                    def f32fails(n):
                        return sum(1 for x in F if f32bits(f32(float('%.*g' % (n, x)))) != f32bits(x))
                    print('float32, %d values; text = %%.Ng, then back to float32' % N)
                    for n in (6, 7, 8, 9):
                        print('N=%d  failures=%d' % (n, f32fails(n)))

从表中读到的规则如下。

  • 在A和B中，17位的失败为0个。15位约有94%、16位约有42%到45%以不同的位读回。在把double写成文字的一侧，15位不是安全线。
  • 在C中，15、16、17位全部为0个。这与Python文档对sys.float_info.dig的说明一致，即有效数字不超过15位的十进制字符串转成float再写回会恢复相同的十进制值。同一页还举了16位字符串9876543211234567用.16g写回后变成9876543211234568的例子。
  • C在6位和9位上的失败(59411、39308)是因为输入文字最多有15位，截成6位或9位的那一刻值就变了。写入位数比原文字短时，哪个方向都无法恢复。
  • float32在9位时为0个，在8位时有1568个失败。Microsoft Learn的标准数字格式文档建议Double用G17、Single用G9，与此表一致。
  • 样本中失败为0个并不是对所有double的证明。需要17位的依据是这个样本与Microsoft Learn的建议指向同一方向。

最短往返表示 - repr和toString做了什么

每次都写17位会让0.1变成0.10000000000000001，不便阅读。Python文档写道，从3.1起repr在候选中选最短的字符串，并说明当sys.float_repr_style为short时float(repr(x)) == x成立。ECMAScript规范的Number::toString在确定s、n、k时要求k尽可能小，MDN则写道toString使用能与相邻数值区分开所需的最少有效数字。下面的代码统计这种“最短”对每个值需要几位。

import random, collections
                    rnd = random.Random(20261006)
                    def need(x):
                        for n in range(1, 18):
                            if float('%.*g' % (n, x)) == x: return n
                    B = [rnd.uniform(-1000, 1000) * rnd.uniform(0.001, 1000) / rnd.uniform(1, 97) for _ in range(100000)]
                    h = collections.Counter(need(x) for x in B)
                    print('smallest N with float(%.Ng) == x, 100000 arithmetic values:')
                    for n in sorted(h): print('  N=%2d  %6d' % (n, h[n]))
                    print('examples (digits needed, repr):')
                    for x in (0.1, 0.1 + 0.2, 0.1 * 3, 1.1 * 1.1, 0.1 + 0.7, 1 / 3, 2 / 3, 100 * 1.1, 1e23, 5e-324):
                        print('  %2d  %s' % (need(x), repr(x)))

工具之间的传递 - 决定值的是写入一侧

工具之间值发生变化是出在写入一侧还是读取一侧，只有把变量分开才能判定。下面的实验中，Python把2000个值的位模式(十六进制)写入文件，三个写入工具用各自的方式把同样的值写成8个文本文件，三个读取工具读取这8个文件并与原来的位比较。写法有8种，读取工具有3个，数据相同。

写什么、怎么写 - 选择标准

把运行得到的结果按写入目的整理如下。

目的写法本文中看到的依据
供人阅读的显示，无需还原%g、G15、toLocaleString等短格式第5节的输出，会丢弃部分值
必须还原的double(JSON、日志、CSV)最短往返(repr、JSON.stringify)或17位有效数字(%.17g、G17)第3节17位为0个，第6节的表
float329位有效数字(G9)第3节9位为0个，Microsoft Learn建议
从PowerShell 5.1导出到CSV的doubleToString("G17", InvariantCulture)第6节G17为0个，默认ToString()为1870个
在PowerShell 5.1中把JSON数字接收为double把值转成字符串后用[double]::Parse(InvariantCulture)第7节类型转换222个，Parse为0个
确认值在工具之间是否变化用两个工具读取同一个文件并比较位(十六进制)第6节的构成
  • 以还原为目的时，先确认是不是最短往返或17位，而不是先问用几位。
  • 15位是文字 → double → 文字这个方向的保证，所以适合显示人输入的值，不适合保存计算结果。
  • 写入工具的默认位数因工具和输出路径而异。即使在同一个PowerShell 5.1里，插值和ConvertTo-Json也不同。
  • 比较值时用位而不是文字。Python可以用struct，Node用DataView，PowerShell用BitConverter取出64位。
  • 接近整数的大数值和64位ID的问题与这里讨论的小数位数无关，请参阅JSON数字精度的文章。

未能确认的内容

  • PowerShell 7和较新的.NET。这台电脑上没有pwsh。Microsoft Learn把Double的G默认位数写成“可往返的最少位数”，并把.NET Framework单独标为G15，但没能通过运行进行比较。
  • Java、Go、Rust、C等其他语言以及Node以外的JavaScript引擎的默认输出位数。
  • 17位能还原所有double的穷尽证明。样本是三种，每种10万个。
  • ConvertTo-Json对哪些值写15位、对哪些值写17位的规则。只有一个反例和2000个值样本的结果。
  • PowerShell 5.1的Decimal类型转换偏差一位的原因，以及double.Parse对-6667.211341195974读法不同的原因。
  • 无穷大、NaN、负零和次正规数(subnormal)的往返。样本A中是否含有次正规数没有统计。
  • 向ConvertTo-Json传入对象或数组时的位数。只传入了标量double。
  • Linux和macOS上的行为，以及用逗号作小数点的区域设置。PowerShell代码固定使用InvariantCulture。
  • SQLite的printf用%.17g没有输出17位的现象。运行中输出了0.3，但没有调查原因。
