백업은 파일 복사가 아니다 — Docker 권한·DB 정합성·S3 메타데이터의 3대 기술적 함정

2026-09-18 개발/인프라

인프라 환경을 구축할 때 가장 흔히 범하는 오해는 디렉터리를 다른 스토리지로 복사하거나 동기화 도구를 걸어두면 백업이 끝났다고 여기는 관행이다. 셸 스크립트에 주기적인 파일 복사 명령을 등록하고 대시보드가 정상 종료를 가리키면 운영자는 데이터가 안전하게 보호되고 있다고 믿기 쉽다. 그러나 이러한 믿음은 재난이 실제로 닥쳤을 때 참담한 현실로 귀결되곤 한다.

백업 검증의 중요성과 백업 성공 코드가 지닌 한계에 대해서는 이전 글인 「백업이 있다」와 「복원된다」는 다른 명제다에서 복원 파이프라인의 종단 검증을 중심으로 상세히 다룬 바 있다. 당시 글이 복원 단계의 검증 조건을 분석했다면, 이번 글은 그 논의의 선행 단계에 집중한다. 즉 백업 아카이브를 구성하고 데이터를 수집하는 과정 자체에서 발생하는 기술적 결함의 층위들을 추적한다.

소프트웨어 엔지니어 Aleksandar Filipovski가 2026년 9월 16일 게시한 기술 에세이 「Backups aren't simple」은 백업을 단순한 파일 복사로 취급했을 때 직면하는 실무적 실패들을 생생하게 짚어낸다. 저자는 과거 외장 하드 드라이브에 모아둔 가족 사진이 TV 셋톱박스의 예고 없는 포맷 과정에서 유실될 뻔했던 개인적인 경험을 화두로 던진다. 데이터를 단일 물리 장치에만 보관하고 스냅샷 분리를 하지 않았던 사소한 설계 부재가 복구 불가능한 재앙으로 이어질 뻔했던 사례다.

이 일화가 시사하는 기술적 함의는 명확하다. 데이터 손실은 디스크 하드웨어 장애뿐 아니라 사용자 실수, 악성 소프트웨어 감염, 비동기 시스템의 메모리 버퍼 증발, 파일 권한 불일치 등 다층적인 경로를 통해 발생한다. 백업 파이프라인은 단순히 바이트를 이동시키는 작업이 아니라, 시스템의 각 계층이 가진 고유한 제약 조건을 방어하는 종합적인 엔지니어링 설계다.

계기 — 「파일 복사」라는 말이 감추는 실무의 간극

데이터 관리 분야에서 널리 회자되는 격언이 있다. 세상에는 이미 치명적인 데이터 손실을 겪은 사람과, 앞으로 겪게 될 사람이라는 두 종류의 사람만이 존재한다는 명제다. 대다수의 엔지니어는 자신이 충분히 방어하고 있다고 믿지만, 실제 손실은 예상치 못한 가장 취약한 지점을 파고든다. 하드 드라이브의 자성 입자가 시간이 지남에 따라 변위하거나 SSD의 NAND 트랜지스터에서 전하가 누설되어 발생하는 비트 로트(bit rot) 같은 물리적 열화는 물론이고, 랜섬웨어나 부주의한 스크립트 실행에 의한 일괄 덮어쓰기까지 위협의 양상은 다양하다.

Aleksandar Filipovski의 분석에 따르면 단순히 원본 디스크의 내용을 다른 디스크로 미러링(예컨대 RAID 1 구성)하는 것은 진정한 의미의 백업이 될 수 없다. 미러링은 물리적 디스크 한 대의 고장을 방어할 뿐, 원본에서 발생한 삭제나 데이터 오염, 파일 암호화 같은 논리적 오류를 실시간으로 똑같이 복제하기 때문이다. 실수로 삭제된 파일은 미러 대상에서도 즉시 사라지며, 손상된 바이트 역시 복제 디스크에 즉각 기록된다.

따라서 백업 시스템이 갖추어야 할 본질적인 요건은 과거의 특정 시점으로 상태를 되돌릴 수 있는 시점 분리성, 즉 스냅샷(snapshot)의 보존이다. 하지만 스냅샷을 주기적으로 유지하려 할 때 저장 공간의 선형적 증가, 권한 격리 실패, 애플리케이션의 비동기 버퍼링 등 파일 복사라는 추상화 아래 숨겨져 있던 복잡한 기술적 문제들이 고개를 든다.

목표의 기준선 — 3-2-1 원칙과 RPO 스펙트럼의 현실

백업 체계를 논의할 때 가장 기본이 되는 아키텍처 규칙은 원문에서도 강조된 3-2-1 원칙이다. 이 원칙은 단일 장애점(Single Point of Failure)을 원천 차단하기 위한 3중 방어 메커니즘을 규정한다.

  • 3개의 데이터 복사본 유지: 운영 중인 원본 데이터 외에 최소 2개의 독립적인 복사본을 유지하여 단일 사본 손상에 대비한다.
  • 서로 다른 2종류의 저장 매체 활용: 동일한 제조사나 동일한 미디어 기술(예: 동일 모델의 HDD)을 피하고 외장 스토리지, 테이프, 클라우드 등 상이한 매체에 분산하여 특정 하드웨어 결함의 연쇄 발생을 차단한다.
  • 최소 1개의 사본을 원격지(Offsite)에 보관: 화재, 홍수, 정전 서지(power surge), 도난 등 물리적 위치 전체를 파괴하는 국지적 재난으로부터 데이터를 격리한다.

이 원칙과 더불어 백업 주기와 아키텍처를 결정하는 핵심 척도는 복구 시점 목표(RPO, Recovery Point Objective)다. RPO는 장애 발생 시 조직이 감내할 수 있는 최대 데이터 유실 시간을 의미한다. Filipovski의 관찰에 따르면 RPO의 스펙트럼은 극단적인 양극단을 형성한다.

초 단위의 금융 거래를 처리하는 핵심 금융기관의 경우 RPO는 30초 미만으로 설정되며, 이는 실시간 동기 복제와 트랜잭션 로그 선행 기록(WAL) 아키텍처를 요구한다. 반면 일 단위 갱신이 주를 이루는 소규모 기업이나 개발 프로젝트의 경우 24시간 이상의 RPO도 충분히 허용 가능하다. 저자 본인의 가족 사진 보관 시나리오에서는 1주일 단위(weekly)의 백업 주기로도 데이터 손실 위험을 합리적으로 통제할 수 있었다고 진단한다.

그러나 RPO를 달성하기 위해 스냅샷을 생성할 때 보관 주기 정책(Retention Policy)의 딜레마가 발생한다. 24시간 RPO를 맞추기 위해 매일 백업을 수행할 경우 1년에 365개의 스냅샷이 누적된다. 최근 데이터일수록 세밀한 복구 시점이 필요하지만, 수개월 전의 데이터는 일 단위의 세밀함이 무의미해진다. 따라서 조부-부-자(Grandfather-Father-Son)와 같은 백업 순환 스키마(예: 최근 14일은 일간, 7주는 주간, 12개월은 월간 유지)를 도입하게 되며, 이로 인해 스토리지 파이프라인의 관리 복잡도는 급격히 증가한다.

함정 층위 1: 컨테이너와 권한 — 루트 소유권의 은밀한 실패

현대 인프라에서 도커(Docker)와 같은 컨테이너 환경이 표준으로 자리잡으면서, 파일시스템 권한과 관련된 새로운 장애 유형이 빈번하게 발생한다. 과거 단일 호스트 시스템에서는 특정 서비스 계정(daemon user)이 파일 소유권을 일관되게 관리했으나, 컨테이너화된 환경에서는 호스트와 컨테이너 내부 간의 사용자 ID 매핑 차이로 인해 권한 파편화가 발생한다.

컨테이너 내부에서 구동되는 다수의 서비스는 기본적으로 루트(UID 0) 권한으로 실행되거나 볼륨 마운트된 디렉터리에 루트 소유의 파일을 생성한다. 반면 호스트 시스템에서 백업을 수행하는 cron 작업이나 백업 데몬은 최소 권한 원칙(Principle of Least Privilege)에 따라 권한이 제한된 일반 사용자 계정으로 실행되는 경우가 많다. 이 간극에서 치명적인 실패가 배태된다.

  • 백업 에이전트의 권한 거부(Permission Denied): 컨테이너가 루트 소유로 생성한 파일 및 디렉터리에 대해 일반 사용자 백업 스크립트가 접근하지 못해 백업 대상에서 누락된다.
  • 조용한 부분 백업(Silent Partial Backup): 스크립트가 오류 처리 없이 실행될 경우, 권한이 있는 일부 설정 파일만 복사되고 핵심 데이터 디렉터리가 비어 있는 채로 정상 완료 코드를 반환한다.
  • 전체 파일시스템 권한 요구: Docker 볼륨과 호스트 마운트 경로를 완전하게 백업하기 위해서는 백업 작업에 호스트 수준의 전체 파일시스템 접근 권한(root 권한 또는 특수 기능)이 강제된다.

보안 관점에서 백업 에이전트에게 루트 권한을 부여하는 것은 침해 사고 시 공격 표면을 넓히는 트레이드오프를 수반한다. 반대로 컨테이너 내부의 프로세스 UID를 호스트 사용자와 정렬하거나 사용자 네임스페이스(User Namespace)를 적용하는 것은 컨테이너 이미지 재빌드와 배포 파이프라인의 복잡성을 가중시킨다. 단순한 파일 복사 명령이 호스트와 컨테이너 간의 보안 및 권한 모델 충돌로 비화하는 지점이다.

함정 층위 2: 데이터베이스 정합성 — 메모리 플러시와 비동기 I/O

파일 수준 백업이 가장 무력하게 무너지는 영역이 바로 데이터베이스(RDBMS 및 NoSQL) 스토리지다. 관계형 데이터베이스 엔진은 고성능 입출력을 달성하기 위해 디스크에 즉각적으로 모든 데이터를 쓰지 않는다. 메모리 내 버퍼 풀(Buffer Pool)에 변경 사항을 임시로 유지하며, 트랜잭션 커밋 시점에는 쓰기 로그(WAL/Redo Log)만 먼저 기록한 뒤 실제 데이터 페이지는 배치 단위로 디스크에 플러시(flush)한다.

이러한 비동기 I/O 아키텍처 상태에서 외부 백업 스크립트가 데이터 디렉터리(예: `/var/lib/mysql` 또는 `/var/lib/postgresql/data`)를 그대로 복사하면 어떤 현상이 일어나는가? 복사 명령이 실행되는 동안에도 데이터베이스 엔진은 끊임없이 메모리와 디스크 사이에서 페이지를 교체하고 포인터를 갱신한다. 파일 복사 도구는 디스크의 블록들을 순차적으로 읽어 들이지만, 앞부분 블록을 읽는 시점과 뒷부분 블록을 읽는 시점 사이에 엔진이 이미 데이터를 변경해 버린다.

결과적으로 생성된 백업 파일은 메모리 버퍼의 최신 트랜잭션이 누락되고, 인덱스 루트 노드와 리프 노드의 포인터가 서로 다른 시점을 가리키며, 데이터 페이지의 체크섬이 어긋난 구조적 손상(corruption) 상태가 된다. 이 상태의 파일은 복원 단계에서 데이터베이스 엔진을 기동하려 할 때 복구 불가능한 충돌을 일으키거나 조용히 트랜잭션을 롤백하여 유실을 초래한다.

따라서 데이터베이스는 파일 복사로 백업할 수 없으며, 반드시 데이터베이스 엔진이 제공하는 전용 덤프 도구(예: `mysqldump`, `pg_dump`)나 일관성 있는 스냅샷 메커니즘을 사용해야 한다. 이러한 도구들은 활성 트랜잭션 간의 일관성을 보장하기 위해 전체 접근 권한을 요구하며, 읽기 락이나 MVCC 스냅샷 트랜잭션을 통해 메모리 버퍼와 디스크 상태를 논리적으로 정렬된 단일 시점으로 추출한다.

함정 층위 3: 오브젝트 스토리지 — POSIX 메타데이터 유실과 API 비용

클라우드 컴퓨팅과 저렴한 오브젝트 스토리지(Amazon S3, MinIO, Wasabi 등)의 등장은 백업을 원격지에 보관하는 비용을 획기적으로 낮췄다. 그러나 로컬 파일시스템의 데이터를 S3 버킷으로 직접 전송하는 파이프라인에는 두 가지 치명적인 복병이 도사리고 있다.

  • POSIX 파일 메타데이터의 소멸: S3와 같은 객체 스토리지는 계층형 파일시스템이 아닌 플랫한 키-값 저장소다. 객체는 바이트 본문과 몇 가지 HTTP 헤더만 저장할 뿐, 리눅스 파일시스템의 파일 소유자(UID), 그룹(GID), 접근 권한 모드(chmod), 심볼릭 링크(symlink), 확장 속성(xattr)을 기본적으로 보존하지 않는다. 이를 그대로 복원하면 모든 파일의 권한이 엉뚱하게 바뀌거나 서비스 실행이 거부된다.
  • 소형 파일 대량 업로드 시 API 비용 폭증: 클라우드 스토리지는 기가바이트당 저장 비용보다 API 요청 횟수(PUT, GET)에 따른 과금이 더 가혹할 수 있다. 소규모 프로젝트라도 수십만 개의 소형 웹 에셋이나 소스코드를 개별 파일 단위로 동기화하면, 저장 비용은 불과 수십 원인데 업로드 API 호출 비용으로 수만 원 이상이 청구되는 비용 전도가 발생한다.
  • 원격 동기화 도중의 속도 저하: 수십만 번의 독립적인 HTTP 요청은 네트워크 왕복 지연시간(RTT)과 핸드셰이크 오버헤드로 인해 백업 창(Backup Window)을 지나치게 연장시켜 백업 완료 전 시스템 부하를 유발한다.

이 문제에 대한 원문의 명쾌한 해법은 데이터를 사전에 50MB 단위의 tarball(tar 아카이브)로 묶어 전송하는 방식이다. 파일을 tar로 패키징하면 파일 소유권, 권한, 타임스탬프, 디렉터리 구조 등 POSIX 메타데이터가 단일 아카이브 파일 내부에 고스란히 캡슐화된다. 동시에 수만 개의 소형 파일이 소수의 50MB 덩어리로 압축 통합되므로 S3 PUT 요청 횟수가 수천 분의 일로 급감하여 API 비용과 전송 지연을 동시에 극복할 수 있다.

백업 방식의 트레이드오프 — 하드링크 증분과 팻 테일 분포

백업 대상을 식별하고 정합성을 확보했다면 다음 질문은 「어떻게 효율적으로 저장할 것인가」로 귀결된다. 전체 데이터를 매번 처음부터 끝까지 복사하는 전체 백업(Full Backup)은 신뢰성이 높지만, 저장 공간과 대역폭 소모가 너무 커 실시간 운영에 적합하지 않다. 여기서 증분 백업(Incremental Backup) 기법이 필연적으로 등장한다.

Filipovski는 유닉스 계열 파일시스템에서 오랜 기간 검증된 하드링크(Hard link) 기반의 증분 백업 구조를 집중 조명한다. 하드링크 방식은 새로운 스냅샷 디렉터리를 생성할 때, 이전 스냅샷과 내용이 동일한 파일에 대해서는 실제 데이터를 디스크에 중복 기록하지 않고 기존 파일의 inode를 가리키는 하드링크만 생성한다. 오직 내용이 수정되거나 새로 생성된 파일만 새로운 데이터 블록에 기록된다.

이 설계가 놀라운 효율을 발휘하는 이유는 실무 환경의 파일 변경 패턴이 나타내는 통계적 특성 때문이다. 저자의 관찰에 따르면 파일의 변경 빈도는 전형적인 "팻 테일(fat-tailed) 분포"를 따른다. 시스템에 존재하는 파일의 압도적인 대다수(시스템 라이브러리, 과거 사진, 문서 아카이브, 정적 에셋 등)는 시간이 흘러도 거의 수정되지 않으며, 변경이 집중되는 파일은 전체의 극히 일부분(로그, 세션 캐시, 활성 데이터베이스 파일 등)에 불과하다.

그러나 증분 백업은 저장 효율을 얻는 대가로 복원 및 관리 단계에서 무거운 트레이드오프를 요구한다.

  • 스냅샷 체인의 의존성: 증분 스냅샷은 이전 기준 스냅샷의 데이터 블록에 종속되므로, 중간 링크나 블록이 손상될 경우 후속 스냅샷 복원이 연쇄적으로 불가능해질 수 있다.
  • inode 고갈 및 메타데이터 부하: 수백만 개의 하드링크를 관리하면 파일시스템의 inode 소모량이 급증하며, 백업 검사 도구가 링크 수를 추적하는 메모리 부담이 커진다.
  • 비POSIX 파일시스템 복사 제약: 하드링크 구조는 이를 지원하지 않는 FAT32, exFAT 또는 오브젝트 스토리지로 전송할 때 모든 하드링크가 개별 파일로 풀려 저장 공간이 기하급수적으로 폭발할 위험이 있다.

도구 생태계 비교 — Borg, Restic, rsnapshot, ZFS의 지향점

현대 엔지니어링 생태계에는 이러한 기술적 함정들을 극복하기 위해 설계된 다양한 백업 소프트웨어들이 존재한다. 각 도구는 해결하고자 하는 문제의 핵심 층위에 따라 상이한 아키텍처를 채택하고 있다.

전통적인 유틸리티인 rsnapshot은 앞서 설명한 `rsync`와 파일시스템의 하드링크 메커니즘에 기반한다. 별도의 독자적인 아카이브 포맷을 사용하지 않으므로 임의의 파일 관리자나 터미널에서 즉각 디렉터리를 탐색하고 개별 파일을 복사해 올 수 있다는 직관성이 최대 강점이다. 그러나 데이터 압축과 암호화가 내장되어 있지 않고, 파일 내부의 일부 바이트만 바뀌어도 파일 전체를 다시 저장해야 하는 블록 단위 중복제거의 한계를 지닌다.

반면 현대적인 백업 도구인 BorgBackup(Borg)과 Restic은 데이터의 내용 기반 청크 분할(Chunking)과 중복제거(Deduplication), 종단 간 암호화를 핵심 철학으로 삼는다. 파일이 이름이 바뀌거나 디렉터리가 이동하더라도, 심지어 가상 머신 이미지나 대용량 파일 내부의 일부 바이트만 변경되었더라도 청크 단위로 해시를 대조하여 변경된 조각만 저장한다. 데이터는 저장소에 쓰여지기 전 클라이언트 측에서 강력한 암호화 알고리즘으로 보호되며 무결성 검증을 위한 체크섬이 부여된다. Restic은 특히 S3를 포함한 다양한 클라우드 백엔드를 단일 바이너리로 네이티브 지원한다는 점에서 현대 인프라에 적합하다.

마지막으로 파일시스템 계층에서 이 문제를 근원적으로 해결하는 ZFS가 있다. ZFS는 CoW(Copy-on-Write) 트랜잭션 모델과 종단 간 체크섬(End-to-end Checksum)을 파일시스템 핵심에 내장하고 있다. 스냅샷 생성이 메타데이터 포인터 조작만으로 거의 0초에 가깝게 완료되며, 백그라운드 스크러빙(scrubbing)을 통해 비트 로트 현상을 스스로 탐지하고 패리티 블록으로 자가 복구(self-healing)한다. `zfs send`와 `zfs receive` 파이프라인을 이용하면 파일 수준을 거치지 않고 블록 수준에서 안전하고 극도로 빠른 원격 복제를 수행할 수 있다.

스케줄링과 운영의 맹점 — DST 전환과 6개월 복원 훈련

백업 아키텍처를 완벽히 구축했다 하더라도 이를 스케줄링하고 검증하는 운영 단계에서 간과하기 쉬운 실무적 함정들이 여전히 도사리고 있다. 원문에서 제시하는 가장 직관적이면서도 치명적인 권고는 「새벽 2시나 새벽 3시에 백업 작업을 예약하지 마라」는 지침이다.

이는 일광절약시간제(DST, Daylight Saving Time)가 적용되는 글로벌 인프라 및 서버 환경에서 기인한다. 봄철 DST 전환 시점에는 시계가 새벽 2시에서 3시로 1시간을 건너뛰기 때문에, 2시 30분에 예약된 cron 작업은 실행 기회 자체를 잃고 침묵 속에 증발한다. 반대로 가을철 전환 시점에는 새벽 2시가 두 번 반복되므로 백업 작업이 중복 기동되어 리포지토리 락 경합이나 I/O 부하 폭증을 초래할 수 있다. 백업 스케줄은 반드시 협정 세계시(UTC) 기준으로 설정하거나 시간 왜곡이 없는 새벽 4시 이후 또는 업무 외 시간대로 분산해야 한다.

그리고 모든 백업 논의의 종착점은 복원 훈련(Restore Drills)이다. Filipovski는 최소 6개월에 한 번씩 실제 복원 테스트를 수행할 것을 강력히 권고한다. 이는 엔지니어링 관점에서 대단히 중요한 원칙을 상기시킨다. 백업 시스템의 가치는 「백업 아카이브를 만드는 행위」에 있는 것이 아니라, 「실제 장애 상황에서 데이터를 되살려 서비스를 기동시키는 능력」에 있기 때문이다.

  • 백업과 복원의 명제 분리: 백업 로그의 정상 종료는 단순히 백업 프로그램이 쓰기를 마쳤음을 보증할 뿐, 저장된 데이터가 암호화 키 분실, 아카이브 손상, 스키마 불일치 없이 온전히 풀려나는지는 전혀 보증하지 않는다.
  • 복구 시간 목표(RTO)의 실측: 6개월마다 격리된 테스트 환경에 데이터를 실제로 복원해 보아야만, 장애 발생 시 운영 체계가 감당해야 할 복구 소요 시간(RTO)을 정확히 산정할 수 있다.
  • 운영 절차와 자격증명의 갱신: 복원 과정에서 암호화 비밀번호 만료, 백업 리포지토리 접근 토큰 유효성, 복원 매뉴얼의 낡은 단계를 미리 발견하고 갱신할 수 있다.

확인하지 못한 것

  • 원문 에세이는 저자의 가족 사진 유실 위기 사례를 언급하였으나, 당시 셋톱박스 모델 및 복구에 사용된 세부적인 포렌식 데이터 카빙 도구의 명칭은 원문에 기술되지 않아 확인하지 못했다.
  • 오브젝트 스토리지 비용 절감을 위한 아카이브 단위로 저자가 제시한 50MB tarball 규격 외에, 클라우드 제공업체의 청크 멀티파트 업로드 임계값에 맞춘 다른 최적 단위에 대한 정량적 벤치마크 데이터는 원문에 수록되지 않았다.
  • 부록에서 언급된 ZFS 외에 Btrfs나 bcachefs와 같은 현대 Linux CoW 파일시스템 환경에서 동일한 스냅샷 백업 파이프라인을 운영했을 때의 성능 차이는 원문에서 구체적으로 다루어지지 않았다.
