Conventional Commits は本当に役立つのか - コミットメッセージ規約への批判 2026

Are Conventional Commits Actually Worth It - 形式と価値のあいだで

2026年6月7日 IT・技術

はじめに: feat: の前で手が止まる瞬間

コードを書き終え、最後にコミットを残そうとした瞬間、手が止まります。「これは feat か fix か。それとも refactor？ scope は何と書く？」たった一行の変更なのに、コミットメッセージの種類を選ぶのに少し頭をひねってしまいます。Conventional Commits を使うチームなら誰もが一度は経験する場面です。ある人にとってこの「ためらい」は良い規律の証であり、別の人にとっては無駄な形式主義の証です。

本記事は、2026年になっても議論が続く問い ―― 「Conventional Commits は本当に役立つのか？」 ―― を、どちらかに肩入れせず冷静に検討します。規約とは何で、どんな利点を約束したのか、どんな批判があるのか、いつ有用でいつ過剰かを、実務の視点で整理します。結論を一行で先に言うと、Conventional Commits はそれ自体が良いものでも悪いものでもなく、自動化パイプラインがコミットを実際に消費する時にだけコストが回収される道具です。

1. Conventional Commits とは ― 規約の基本構造

まず土台を固めます。Conventional Commits は、コミットメッセージを人だけでなく機械も読める固定の形式で書こうという規約です。Angular プロジェクトのコミット慣習から出発し、別の仕様として整理され、現在は v1.0.0 が事実上の標準として通用しています。基本構造は次のとおりです。

<type>[optional scope]: <description>

[optional body]

[optional footer(s)]

実例を見ると直感的です。

feat(auth): ソーシャルログイン対応を追加

fix(api): null 応答で発生していたクラッシュを修正

docs: README にインストール手順を補足

feat(parser)!: 設定ファイル形式を YAML に変更

BREAKING CHANGE: 既存の JSON 設定ファイルは動作しなくなります。

核心は先頭の type です。何が変わったかを一語で分類し、括弧内の scope でどの領域かを絞り、コロンの後の description で内容を書きます。type の後に ! を付けたりフッターに BREAKING CHANGE: を書くと、互換性を壊す変更であることを明示します。

2. コミット種類の語彙 ― feat、fix、そして残り

規約で意味が明確に固定されている type は二つだけです。feat（機能追加）と fix（バグ修正）です。この二つが特別なのは、後で見るセマンティックバージョニングと直結するからです。残りの type は慣習的に広く使われますが、仕様が明確に定義したものではありません。

type 意味 バージョンへの影響
feat新しい機能MINOR 増加
fixバグ修正PATCH 増加
docsドキュメントのみなし
refactor動作変化のない構造改善なし
testテストの追加・修正なし
choreビルド・ツール等の雑務なし
BREAKING CHANGE互換性の破壊MAJOR 増加

ここで最初の摩擦が生じます。仕様は type の「推奨リスト」を自前で提供せず、Angular の定義を参照せよと案内します。そのため chore と refactor の境界、style と format の違いといった論争がチームごとに繰り返されます。議論によれば、この曖昧さが GitHub の issue や Stack Overflow の質問に頻出する混乱の一因です。

3. 導入の狙い ― なぜこんな規約を作ったのか

規約を批判する前に、それが解こうとした問題を公正に見るべきです。Conventional Commits が登場した背景は、自由形式コミットメッセージの混沌でした。「修正した」「asdf」「最終_本当に最終」のようなメッセージで埋まった履歴では、何が変わったかを人が一つひとつ読むしかなく、ツールが自動処理する余地がありません。

規約の真の目標は、コミットメッセージを構造化されたデータに変えることです。いったんコミットが機械で解析できる形式になれば、その下流の changelog 生成、バージョン計算、リリースノート、CI 判断がすべて自動化可能になります。つまり規約はそれ自体が目的ではなく、自動化のための入力形式として設計されたものです。この点を見落とすと規約の価値を誤解しやすくなります。

Conventional Commits の本質は「きれいなコミットメッセージ」ではなく「機械が読むコミットメッセージ」だ。その機械がなければ形式だけが残る。

4. 約束された利点 1 ― 自動 changelog

規約が約束する最初の具体的な利点は自動 changelog 生成です。コミット type が構造化されているので、ツールは履歴をたどって feat コミットを「新機能」セクションに、fix コミットを「バグ修正」セクションに、互換性破壊を独立した目立つセクションに自動で配置します。

リリースごとに手で変更内容を整理する作業が消えることは、決して小さな利点ではありません。特に外部ユーザーがいるライブラリでは、changelog 自体が製品の一部です。手で書くと漏れたり不正確になりやすいですが、コミットから生成すれば「実際に何が変わったか」が漏れなく反映されます。

5. 約束された利点 2 ― セマンティックバージョニングの自動化

二つ目の利点が最も強力です。それがセマンティックバージョニング（SemVer）の自動化です。セマンティックバージョンは MAJOR.MINOR.PATCH の三桁で互換性情報を表しますが、Conventional Commits はこの三桁に正確に対応します。

  • fix コミット → PATCH 増加（例: 1.2.3 → 1.2.4）
  • feat コミット → MINOR 増加（例: 1.2.3 → 1.3.0）
  • BREAKING CHANGE → MAJOR 増加（例: 1.2.3 → 2.0.0）

この対応のおかげで、ツールは最後のリリース以降のコミットだけを分析して次のバージョンを人の介入なしに計算できます。「今回のリリースはマイナーかパッチか」をめぐる感情的で一貫性のない議論が、規則に置き換わります。バージョン番号が、誰がどう感じたかではなく「何が変わったか」をそのまま反映するようになるのです。

6. 約束された利点 3 ― semantic-release と完全自動リリース

changelog とバージョニングが合わさると、リリース全体の自動化が可能になります。代表的なツールが semantic-release で、同じ趣の release-please も広く使われます。流れは次のとおりです。

main ブランチにマージ
   │
   ▼
コミット分析 (commit-analyzer)   → feat/fix/BREAKING を集計
   │
   ▼
次バージョン計算                 → SemVer 規則を適用
   │
   ▼
changelog 生成 + git タグ + パッケージ公開
   │
   ▼
リリースノート発行（全工程が無人）

理想的に動けば、開発者はただ規約に沿ってコミットし main にマージするだけで、バージョンを決めたりリリースを押したりする手動ステップが0になります。これが Conventional Commits 擁護論の頂点です。実際、ある調査では上位 NPM ライブラリの相当数がこの規約を採用しており、自動化エコシステムが規約の上で回っていることを示しています。

7. 批判の論点 1 ― 形式主義と重複情報

ここから反対側に移ります。最もよく出る批判は形式主義です。feat: や fix: のような接頭辞は本当に情報を加えているのか。批判者は「fix: ログイン時のクラッシュを修正」の fix: は蛇足だと見ます。後ろの説明を読めば、それがバグ修正だと誰でも分かります。つまり type が説明と重複している、というのです。

scope への批判も同様です。feat(auth): の auth scope はどの領域に触れたかを教えますが、その情報はすでに git log -- path/to/auth で得られます。変更されたファイルパスがすなわち scope なのに、わざわざ人が手で書き直す必要があるのか、という指摘です。

良いコミットメッセージは「何を変えたか」ではなく「なぜ変えたか」を説明すべきだ。だが type 接頭辞を選ぶのに使うエネルギーは、本来その「なぜ」に使われるべきエネルギーを奪う。

2026年に入っても Hacker News や Lobsters のようなコミュニティで「Conventional Commits は間違ったことに集中させる」という批判が繰り返し投稿されます。核心は、形式を埋めることに気を取られ、コミットメッセージで最も価値ある部分 ―― 変更の意図と文脈 ―― がおろそかになるという懸念です。

8. 批判の論点 2 ― 自動化を使わなければ純粋なオーバーヘッド

二つ目の批判が最も致命的です。Conventional Commits のすべての利点は、コミットを消費する自動化が存在するという前提の上に立っています。changelog を自動生成せず、semantic-release でバージョンを上げないチームなら、規約は約束された利点を一つも残さず形式コストだけを残します。

現実にこうしたチームは意外に多いです。commitlint でコミット形式は強制するのに、その形式を読んで changelog を作ったりリリースを自動化したりするパイプラインがない場合です。このとき開発者は毎コミット type を選ぶ認知コストを払いますが、その対価として戻る自動化の利得は0です。これは規約の最もよくあるアンチパターンです。

遵守率のデータもこの緊張を示します。ある研究によれば、規約を公式採用していないプロジェクトでは、2023年のコミットの約10%しか規約に従っていませんでした。強制しなければ人々は自然に規約から離れていくので、形式を保つにはツールで強制せざるを得ず、強制はまた摩擦を生むという循環ができます。

9. 批判の論点 3 ― 分類の認知負担と曖昧さ

三つ目は分類そのものの負担です。規約をきちんと使うにはコミットを十前後のカテゴリに分けねばなりませんが、現実の変更はそんなにきれいに割り切れません。バグを直しつつリファクタリングもしてテストも追加したコミットは fix なのか refactor なのか test なのか。こうした「絡み合ったコミット（tangled commit）」は分類規則と正面から衝突します。

学術研究もこの点を指摘します。既存研究の多くは feat・fix・その他の3分類に集中しており、細分化されたカテゴリをどう定義し適用するかは、いまだ合意されていない空白として残っています。仕様が type リストを固定しないため、同じ変更でも開発者ごとに違う type を選ぶことが頻発します。一貫性のために導入した規約が、逆に「何が一貫性か」をめぐる新たな論争を生む逆説です。

10. バランスを取る ― いつ有用でいつ過剰か

批判を十分に聞いたので、いまバランス点を取ります。核心の問いは「規約が良いか悪いか」ではなく、「自分のプロジェクトで自動化がコミットを実際に消費するか」です。この一つの基準で大半の判断が分かれます。

状況 Conventional Commits 理由
公開ライブラリ・パッケージ強く推奨changelog・バージョンが利用者に直接重要
semantic-release で自動リリース強く推奨コミットがリリース入力、コスト即回収
多人数協業の大規模リポジトリ推奨一貫した履歴・履歴探索の価値が高い
社内サービス（リリース無関係）任意自動化があれば得、なければ曖昧
個人・小規模プロジェクトたいてい過剰オーバーヘッドが利点を超える

要するに規約のコストは「コミットを読む機械」がある時に回収されます。ライブラリを公開したりリリースを自動化するなら、規約はほぼ常に得です。逆に一人で使うリポジトリやリリースの概念がない社内ツールなら、規約は埋めるべき空欄を増やすだけの形式になりがちです。この技術導入判断の一般原則は、退屈な技術を選べ ― AI 時代の技術選択で扱った保守的な姿勢とも通じます。

11. 代替案 ― 規約なしでも良いコミットメッセージ

規約を使わないと決めたからといって、コミットメッセージを適当に書いてよいわけではありません。厳格な形式の代わりに良いコミットメッセージの原則に従えば、規約の核心的価値の多くをコストなしで得られます。古くから検証された原則は次のとおりです。

  • 件名は短く命令形で: 「Add」「Fix」のように命令形動詞で始め、50字前後で終えます。「Added」「Fixes」のような過去形・現在形の混用を避けます。
  • 本文は「何」ではなく「なぜ」: コードの diff を見れば何が変わったかは分かります。コミットメッセージが本当に担うべきは、その変更がなぜ必要だったか、どの代替案を捨てたかです。
  • 1コミットに1つの論理的変更: 絡み合ったコミットを避けると分類の悩み自体が消え、取り消しとレビューが楽になります。
  • 課題・文脈を結ぶ: 関連する課題番号や背景リンクを付け、未来の読者が決定の文脈を追えるようにします。

興味深いことに、これらの原則は Conventional Commits と衝突しません。むしろ規約を使うとしても、これらの原則を守ってこそ良い履歴になります。つまり規約は良いコミットの必要条件でも十分条件でもありません。形式を守った悪いコミットも、形式のない素晴らしいコミットも、いくらでもあり得ます。

12. 実務導入ガイド ― 5段階の漸進適用

では実際にどう決めて導入すべきでしょうか。一度に commitlint で全チームを強制するのは摩擦を大きくします。次の5段階の漸進的な道を勧めます。

  1. まず自動化を決める: 規約を導入する前に「我々は changelog を自動生成するか、リリースを自動化するか」をまず答えましょう。答えが「いいえ」なら規約は保留してよいです。
  2. type を最小化する: 導入するなら十を全部使わず、feat・fix・chore・docs 程度に絞りましょう。分類の曖昧さの大半が消えます。
  3. 強制は後で: 最初から commitlint フックで止めず、合意と例から始め、文化が根付いた後にツールを載せましょう。
  4. ツールを実際に接続する: semantic-release や release-please を付けて、コミットが本当にバージョン・changelog につながるようにしましょう。そうしてこそコストが回収されます。
  5. 定期的に再評価する: 規約が自動化につながらず形式だけ残ったなら、廃止を恐れないでください。ツールは目的ではなく手段です。

この漸進的な姿勢は開発ツール全般に有効な原則です。ツールの隠れた設定とトレードオフを理解して使う姿勢は、Claude Code 隠れた設定の完全解説で扱ったアプローチとも通じます。

13. 結論 + すぐ適用できる3つ

「Conventional Commits は本当に役立つのか？」への正直な答えは「状況による」であり、その「状況」を分ける基準は明確です。コミットを消費する自動化があるかです。自動 changelog とセマンティックバージョニング、semantic-release のようなパイプラインがコミットを実際に読むなら、規約は一貫性と自動化という大きな利得を返します。逆にそうした消費者がいなければ、規約は形式主義批判が正確に当てはまる純粋なオーバーヘッドになります。

すぐ適用できる3つで締めくくります。

  1. 「我々はコミットを自動で消費するか？」をまず問え。 この一つの問いの答えが規約導入の9割を決めます。自動化がないなら、規約より「良いコミットメッセージの原則」が先です。
  2. 導入するなら type は最小に、強制は後で。 feat・fix・chore・docs 程度に絞り、ツールの強制は文化が根付いた後に載せましょう。曖昧さと摩擦を同時に減らす道です。
  3. 形式より「なぜ」を書け。 規約を使おうが使うまいが、コミットメッセージの最大の価値は変更の意図と文脈です。type 接頭辞を選ぶのに使った5秒を、「なぜこう変えたか」の一行に使うほうが、未来の同僚へのずっと大きな贈り物です。
