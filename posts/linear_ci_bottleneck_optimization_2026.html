1. AI 에이전트 코딩 시대의 CI 병목 — 왜 테스트가 급증했는가

소프트웨어 엔지니어링 환경에서 AI 코딩 에이전트의 활용이 일반화되면서 기능 구현과 코드 작성에 소요되는 시간은 극적으로 단축되었다. 일반적으로 개발자가 수동으로 타이핑하던 단위 테스트와 통합 테스트 코드를 에이전트가 병렬로 생성해 내기 시작하면서 저장소에 쌓이는 테스트의 양은 이전과는 다른 단위로 늘어났다. 하지만 작성 속도가 빨라진 것에 비해 작성된 변경 사항을 검증하고 통과시키는 지속적 통합(CI) 파이프라인의 물리적 처리 용량은 같은 속도로 확장되지 않았다.

이슈 추적 및 협업 도구를 개발하는 Linear의 엔지니어링 블로그에 따르면, 2026년 초부터 개발 현장에 에이전트 기반 코딩이 본격적으로 녹아들면서 저장소 내 테스트 스위트 규모가 불과 수개월 만에 4배 가까이(almost quadrupling) 급증했다. 매주 약 2,000개에 달하는 새로운 테스트 케이스가 지속적으로 추가되는 환경에서 모든 풀 리퀘스트(PR)는 CI 파이프라인을 통과해야만 머지될 수 있었다. 검증 체계가 테스트의 양적 팽창을 감당하지 못하면서 개발자와 에이전트 모두 피드백을 받기 위해 장시간 대기해야 하는 병목 현상이 심화되었다.

원문 기고자인 Mufeez Amjad 엔지니어는 2026년 초 Linear의 최고기술책임자(CTO)인 Tuomas로부터 "CI 비용이 지나치게 높다"는 이슈를 배정받은 일화를 소개한다. 단순히 비용을 줄이는 데 그치지 않고 개발 생산성을 유지하기 위해 파이프라인의 실행 속도까지 동시에 끌어올려야 하는 복합적인 과제였다. Linear 개발팀이 직면했던 핵심 문제는 다음과 같이 요약된다.

  • 에이전트 도입으로 인한 테스트 코드 생성량 폭증과 주간 약 2,000건의 지속적인 테스트 누적
  • 단일 PR 검증 시 러너가 소모하는 머신 시간 증가로 인한 클라우드 인프라 청구 비용의 급상승
  • 피드백 루프 지연으로 인해 변경 사항 머지 큐가 지체되고 개발자 및 AI 에이전트의 작업 정체 유발
  • 기존 GitHub Actions 호스팅 러너의 하드웨어 한계와 반복적인 설정 오버헤드의 누적

이 글의 해석으로는, AI 코딩 도구가 생산한 대량의 코드를 검증하는 일은 단순히 컴퓨팅 자원을 선형적으로 늘리는 것만으로는 경제성을 맞추기 어렵다. Linear 개발팀은 CI 파이프라인을 구성하는 하부 인프라부터 도구 체계, 의존성 격리, 작업 스케줄링까지 전 과정을 하나의 시스템으로 다시 조망하며 전방위적인 최적화를 단행했다.

2. 핵심 지표 요약과 최적화 성과 비교

Linear 팀이 CI 파이프라인 최적화 과정에서 설정한 핵심 목표는 두 가지였다. 첫째는 개발자와 에이전트가 PR을 제출한 뒤 결과를 받아보기까지 대기하는 절대적인 시간(PR wait time)을 줄이는 것이었고, 둘째는 각 테스트가 소비하는 러너 머신 시간(runner time per test)을 감축하여 비용 구조를 개선하는 것이었다. 테스트 수가 4배 가까이 늘어나는 상황에서 두 지표를 동시에 개선하는 것은 파이프라인의 기본 구조를 완전히 개편해야만 가능한 목표였다.

원문이 공개한 실측치에 따르면, Linear 팀은 이러한 종합 최적화를 통해 PR CI 대기시간을 종전의 6분 초과 상태에서 5분 조금 넘는 수준(from more than 6 minutes to just over 5)으로 낮추었다. 동시에 테스트 1건당 소모되는 머신 러너 사용 시간을 약 절반(roughly in half)으로 줄이는 성과를 거두었다. 만약 이러한 체계적 개편 작업이 진행되지 않았다면, 현재 규모의 테스트 스위트를 검증하는 데 걸리는 시간은 약 11분(roughly 11 minutes)에 달했을 것으로 추산되었다.

원문이 제시한 주요 성과 지표에서 주목할 점은 다음과 같은 기술적 맥락이다.

  • 파이프라인 전체의 처리 효율을 개선함으로써 테스트 수가 4배 급증했음에도 실제 대기 시간은 오히려 단축되었다.
  • 단순히 머신 코어를 증설해 시간을 줄인 것이 아니라, 테스트당 러너 소모 시간 자체를 절반으로 줄여 비용 증가를 억제했다.
  • 테스트 스위트의 규모 팽창에 비례해 선형적으로 증가하던 큐 대기 시간이 상한선 내에서 안정적으로 제어되었다.
  • 개별 단계의 미세한 지연 요소들을 제거함으로써 CI 실행 결과의 편차(jitter)가 눈에 띄게 완화되었다.

Linear는 이러한 성과를 달성하기 위해 최적화 작업을 크게 4개 영역으로 구분하여 단계적으로 실행했다. 인프라 및 도구 체계의 최적화, 후속 작업을 막아서는 게이트 작업의 단축, 작업 간 반복되는 설정 비용의 제거, 그리고 테스트 실행 자체의 효율화가 그것이다.

3. 인프라와 컴파일러의 현대화 — 서드파티 러너와 tsgo

Linear 개발팀이 가장 먼저 추진한 조치는 파이프라인 내부 로직을 크게 수정하지 않고도 즉각적인 성능 이득을 얻을 수 있는 컴퓨팅 인프라 교체였다. 기존에는 GitHub Actions가 기본 제공하는 호스팅 러너 위에서 모든 CI 작업이 실행되었다. 하지만 고성능 CPU, 고대역폭 스토리지, 최적화된 캐시 레이어를 제공하는 전문 서드파티 러너 인프라로 워크로드를 이전하면서 동일한 파이프라인 스크립트를 훨씬 빠른 하드웨어에서 구동할 수 있게 되었다.

원문에 따르면 러너 인프라 전환 전후 이틀간의 동일 워크로드를 비교 분석한 결과, 전체 작업 실행 속도가 평균 34% 빨라졌다. 특히 CPU 연산 집중도가 높은 TypeScript 타입 검사(tsc) 작업의 경우 소요 시간이 단숨에 52%나 감소하는 극적인 개선이 나타났다. 하드웨어의 클럭 속도와 I/O 성능 향상이 컴파일러와 런타임의 병목을 자연스럽게 덜어준 셈이다.

인프라 전환에 이어 개발팀은 TypeScript 도구 체인의 핵심인 타입 검사 컴파일러 자체를 현대화했다. 기존 Node.js 런타임 기반의 표준 tsc 대신, 네이티브 코드로 재작성된 tsgo 컴파일러를 선제적으로 도입했다. Go 언어로 포팅된 네이티브 TypeScript 컴파일러는 인터프리터 오버헤드와 가비지 컬렉션 부담을 크게 낮춘 도구다.

  • 서드파티 고성능 러너 도입으로 전체 워크로드 평균 34% 성능 향상 달성
  • 고속 I/O 및 고클럭 CPU 환경 덕분에 순수 컴파일 작업(tsc) 소요 시간 52% 단축
  • Go 기반 네이티브 컴파일러 tsgo 도입으로 타입 검사 주간 중앙값 73% 감소
  • 타입 검사가 차지하던 시간이 급감하면서 전체 CI 파이프라인의 최대 병목 위치가 다른 단계로 이동

원문은 tsgo 도입만으로 tsc 검사의 주간 중앙값 소요 시간이 73%나 단축되었다고 밝힌다. 이 조치를 통해 기존에 CI 전체의 완료 시점을 지배하던 무거운 타입 검사 병목이 해소되었으며, 엔지니어링 팀은 다음 단계의 구조적 병목에 집중할 수 있는 여유를 확보했다.

4. 타입 검사 없는 린팅 — ESLint 정적 분석과 Oxlint 도입

컴파일러 최적화 이후 다음으로 병목이 드러난 곳은 코드 린팅(Linting) 단계였다. Linear의 코드베이스는 TypeScript 중심으로 구성되어 있었는데, 개발팀이 작성한 일부 커스텀 린트 규칙들이 타입 정보(type information)를 요구하고 있었다. 코드 스타일이나 제약 사항을 강제하고 자동 수정(autofix)을 적용하기 위해 타입 시스템의 메타데이터를 끌어다 쓴 것이다.

문제는 타입 정보가 필요한 린트 규칙이 단 몇 개만 포함되어 있어도, ESLint는 검사를 시작하기 전에 전체 소스 코드의 복잡한 타입 그래프를 완전히 빌드해야 한다는 점이었다. 이로 인해 린트 작업은 CI 파이프라인에서 가장 많은 메모리를 소모하고 오랜 시간 러너를 점유하는 고비용 단계로 변질되어 있었다.

개발팀은 타입 정보에 의존하던 커스텀 규칙들을 추상 구문 트리(AST) 수준의 순수 구문 정적 분석으로 전면 재작성했다. 타입 메타데이터를 조회하는 대신 함수 형태의 구조적 패턴과 가드(guard) 형태의 문법적 구성을 식별하도록 로직을 재설계한 것이다. 그 결과 ESLint 실행 과정에서 TypeScript 타입 체커와의 결합을 완전히 끊어낼 수 있었다.

  • 타입 정보를 요구하던 ESLint 커스텀 규칙을 AST 기반의 순수 구문 분석 로직으로 전환
  • 타입 그래프 생성 단계가 제거되면서 린트 실행 시 러너의 메모리 점유량이 대폭 감소
  • API 패키지 린트 소요 시간 68% 단축 및 저장소 전체 린트 소요 시간 55% 단축 달성
  • 구문 기반 규칙 구조를 확보함으로써 고성능 Rust 린터인 Oxlint로의 후속 마이그레이션 발판 마련

원문에 따르면 타입 정보 의존성을 제거한 것만으로 API 린트 소요 시간이 68% 감소했고, 전체 저장소 린트 시간도 55% 줄어들었다. 또한 구문 기반으로 정돈된 규칙들은 추후 Rust 기반 초고속 린터인 Oxlint로 전환하는 과정을 매우 단순하게 만들어 주었으며, Oxlint 도입을 통해 린트에 투입되는 러너 시간은 추가로 더욱 절감되었다.

5. 병목 게이트의 임계 경로 단축 — 체크아웃과 캐시 마크 분리

개별 작업들의 실행 속도를 높인 Linear 팀은 시야를 넓혀 전체 워크플로의 연결 구조를 점검했다. 특히 모든 후속 작업의 시작을 가로막고 있는 전위 게이트(Gating) 작업들이 임계 경로(Critical Path)에 미치는 영향에 주목했다. PR이 생성되면 어떤 파일이 수정되었는지 감지하고, 동일한 입력값에 대해 이미 통과한 테스트가 있는지 판별하는 사전 점검 작업이 대표적이었다.

이 변경 감지 작업은 스킵 가능한 불필요한 테스트가 러너를 예약하지 않도록 막아주는 중요한 역할을 하지만, 동시에 8개에 달하는 API 테스트 샤드가 시작조차 하지 못하고 대기하게 만드는 단일 진입점이기도 했다. 원문에 따르면 이 변경 감지 작업들은 전체 워킹 트리가 필요하지 않음에도 전체 저장소를 풀 체크아웃하고 있었다. Linear 팀은 fetch depth를 엄격히 제한하여 가장 느렸던 게이트 작업 시간을 94초에서 20초로 줄였다.

아울러 워킹 트리가 전혀 필요 없는 작업에서는 체크아웃 단계를 완전히 제거하여 27초에서 7초로 단축했다. 커밋 푸시 및 머지 큐 이벤트처럼 경로 비교가 필수적인 경우에도 최소한의 히스토리만 포함하는 성긴(sparse), 블롭 없는(blobless) 체크아웃을 적용해 11초가량을 추가로 절감했다. 변경 감지 작업의 중앙값은 26초에서 8초로, p90 기준 31초에서 12초로 단축되었다.

또한 서드파티 러너 전환 직후 러너와 GitHub 네트워크 간의 간헐적 링크 불안정으로 인해 표준 actions/checkout이 멈추거나 지연되는 현상이 발생했다. Linear 팀은 이를 극복하기 위해 지수 백오프 기반 재시도(retried with backoff)를 수행하고, GIT_HTTP_LOW_SPEED_LIMIT 및 GIT_HTTP_LOW_SPEED_TIME 환경변수를 설정해 네트워크 정체 시 30초 내에 연결을 종료하고 재시도하는 자체 커스텀 컴포짓 액션을 구축했다. 영구 디스크에 로컬 미러를 유지하는 체크아웃 캐시도 병행 적용했다.

  • 체크아웃 깊이(fetch depth) 제한으로 변경 감지 게이트 소요 시간을 94초에서 20초로 단축
  • 워킹 트리가 불필요한 작업에서 체크아웃을 전면 배제하여 27초에서 7초로 시간 절감
  • 커스텀 체크아웃 액션에 백오프 재시도와 저속 연결 타임아웃(약 30초)을 적용해 멈춤 현상 방지
  • 스티키 디스크 기반 체크아웃 캐시를 활용해 임계 경로 작업의 유휴 대기 시간 최소화
  • 머지 직전 수행되던 캐시 마크 기록 작업을 테스트 완료 후 비차단 병렬 작업으로 재배치하여 42초 절감

머지 경로의 임계 작업도 재배치되었다. 이전에는 머지 직전 최종 단계에서 캐시 마크를 기록하느라 테스트를 이미 통과한 PR조차 머지 큐에서 대기해야 했다. 개발팀은 이 쓰기 작업을 테스트 샤드가 끝난 직후 비차단(non-gating) 백그라운드 작업으로 분리 실행하도록 변경하여, 모든 API PR과 머지 큐 진입 경로에서 42초의 시간을 걷어냈다.

6. 반복 설정 비용의 제거 — 베이스 이미지, pnpm 필터, DB 스냅샷

CI 파이프라인에서 실제 유의미한 작업은 수초에 불과함에도 러너 부팅, 패키지 설치, 빌드 의존성 구성 등으로 인해 수분을 소모하는 현상은 흔히 발생한다. Linear 팀은 매 작업마다 반복되는 셋업 오버헤드를 근본적으로 줄이기 위한 세부적인 다이어트를 단행했다.

첫째로, API 테스트 샤드들은 매번 실행될 때마다 apt 패키지 관리자를 통해 동일한 Postgres 클라이언트를 설치하느라 샤드당 7~8초를 낭비하고 있었다. 개발팀은 Node.js 런타임과 해당 Postgres 클라이언트가 사전에 설치된 경량 CI 베이스 이미지를 구축하여 각 샤드가 즉시 실행 가능한 환경에서 기동되도록 만들었다. 추후 네이티브 빌드 헤더 다운로드 시 발생하던 간헐적 정체까지 방지하기 위해 필수 빌드 헤더도 베이스 이미지에 미리 포함시켰다.

둘째로, Linear의 모노레포를 관리하는 pnpm 워크스페이스 설치 범위를 정밀하게 한정했다. 기존 워크플로는 API 패키지와 직접적인 의존성만 필요한 상황에서도 전체 모노레포 워크스페이스를 통째로 설치하고 있었다. 설치 대상을 API 패키지 관련 범위로 필터링하여 제한하자, 44~73초에 달하던 pnpm 설치 시간이 16~18초로 대폭 단축되었다.

셋째로, 개발팀은 관행적으로 사용하던 node_modules 디렉터리 캐싱을 시험한 뒤 이를 과감히 배제했다. 락파일이 빈번히 변경되는 프로젝트 특성상 캐시 키가 자주 무효화되었고, 캐시 히트가 발생하더라도 압축된 아카이브를 내려받아 복원하는 데 약 28초가 걸렸다. 반면 필터링된 pnpm 설치는 약 7.5초 만에 완료되었다. 캐시 저장은 오히려 불필요한 저장 시간과 실행 편차만 키우고 있었기에 이를 끄는 편이 훨씬 빨랐다.

  • Postgres 클라이언트와 필수 네이티브 빌드 헤더를 사전 탑재한 전용 CI 베이스 이미지 운용
  • pnpm 워크스페이스 설치 대상을 해당 패키지 종속성으로 필터링해 44~73초에서 16~18초로 단축
  • 복원 시간(28초)이 설치 시간(7.5초)보다 느렸던 node_modules 캐시 저장을 과감히 배제
  • 컨테이너 기동 시 전체 DB 마이그레이션 재생 대신 사전 생성된 스키마 스냅샷을 적용해 12초에서 1~2초로 단축
  • 수초 단위의 짧은 독립 검사 7개를 2개 러너 작업 내 동시 프로세스로 통합하여 월 87,000분 절감

넷째로, 데이터베이스 준비 과정에서 변경 사항이 없을 때의 마이그레이션 이력 전체 재생을 걷어냈다. 스키마 변경이 없는 PR에서는 미리 빌드된 스키마 스냅샷과 부트스트랩 파일을 즉시 로드하도록 전환함으로써 컨테이너당 12초가 걸리던 DB 초기화를 1~2초 수준으로 압축했다. 마지막으로 7개의 단기 독립 검사를 2개의 러너 작업으로 묶고 그 안에서 병렬 실행하도록 통합하여, 6월 사용량 기준 월간 약 87,000 러너-분(전체 CI 사용량의 11.8%)을 절감했다.

7. 테스트 실행의 고효율화 — 8분할 샤딩과 isolate false 적용

각 테스트 샤드의 고정 셋업 오버헤드가 대폭 줄어들면서 Linear 팀은 가장 무거운 API 테스트 스위트를 적극적으로 병렬화할 수 있는 여건을 마련했다. 샤드 수를 2배로 늘리면 셋업에 드는 머신 시간도 2배가 되기 때문에 이전에는 샤드를 무작정 늘리는 것이 비용상 비효율적이었으나, 셋업 비용이 낮아진 덕분에 샤딩 확장이 현실적인 해결책이 되었다.

TypeScript 테스트 러너인 Vitest는 개별 테스트의 소요 시간이 아니라 테스트 파일 단위로 작업을 분배한다. 이로 인해 소수의 거대한 테스트 파일이 특정 샤드에 몰리면 다른 샤드가 일찌감치 끝나더라도 전체 스위트의 완료가 지연되는 문제가 발생했다. 개발팀은 테스트 구조를 유지하면서 비정상적으로 거대했던 파일들을 작고 집중도 높은 단위로 쪼갰다.

이후 샤드 수를 기존 4개에서 8개로 확대했다. 초기 벤치마크에서 임계 작업의 속도가 약 19% 빨라졌을 뿐만 아니라 머신 비용도 19% 절감되는 결과를 얻었다. 샤드 증설 적용 1주일 후 가장 느린 샤드의 실행 시간은 5.25분에서 4.33분으로 줄어들었다. 셋업 시간이 기존 110~140초에서 40초 안팎으로 내려갔기 때문에, 8개 샤드가 소모하는 총 셋업 머신 시간(7.5분)은 과거 4개 샤드가 쓰던 셋업 시간(8.3분)보다도 오히려 짧았다.

파이프라인 최적화의 대미를 장식한 가장 큰 개선은 모듈 격리 완화였다. Vitest는 기본적으로 모든 테스트 파일마다 독립된 모듈 환경을 격리(isolate)하여 실행한다. 이는 안전하지만 매 파일마다 엔티티 매핑, GraphQL 스키마, 데코레이터 그래프를 처음부터 다시 빌드해야 함을 의미했다. Linear 팀은 isolate: false 설정을 허용하는 옵트인 Vitest 프로젝트를 신설하여, 상태 오염 위험이 없는 안전한 파일들이 동일 워커 내에서 모듈 레지스트리를 공유할 수 있도록 했다.

이 모듈 공유 최적화는 전체 프로젝트에서 단일 항목으로는 가장 큰 성과를 냈다. 월간 기준 약 17%의 러너 비용을 절감시켰으며, 가장 느린 샤드의 실행 시간을 300~379초에서 약 195초로 줄였고, 총 API 러너 소모 시간은 회당 32.8분에서 22분으로 떨어졌다. 물론 상태 오염을 방지하기 위해 파일 상단에 옵트인 주석을 명시하도록 규정하고 티어다운(teardown) 로직을 정교화했다. AI 에이전트가 대부분의 테스트를 작성하는 환경에 맞춰, 생성되는 테스트가 기본적으로 이 제약 조건을 준수하도록 에이전트 스킬 세트도 함께 업데이트되었다.

8. 시스템 관점의 최적화 — 지속적인 복리 효과를 만드는 접근법

Linear의 CI 개선 작업이 보여주는 가장 중요한 교훈은 파이프라인 최적화가 어느 한 단계의 플래그 튜닝으로 끝나지 않는다는 점이다. 고성능 인프라 이전이 기반을 다지고, 컴파일러와 린터의 구문 단순화가 선행되었으며, 전위 게이트와 체크아웃의 고정 비용이 깎여 나간 뒤에야 비로소 샤딩 확대와 모듈 레지스트리 공유라는 고수준 최적화가 유효하게 작동할 수 있었다.

만약 셋업 오버헤드를 40초대로 줄이지 않은 상태에서 테스트 샤드만 8개로 늘렸다면, Linear 팀은 테스트를 실행하기도 전에 셋업에만 15~19분에 달하는 러너 시간을 낭비했을 것이다. 앞단의 사전 최적화들이 뒷단 병렬화의 한계 비용을 낮춰 준 덕분에 시스템 전반의 성능이 복리(compound)로 누적될 수 있었다.

AI 에이전트가 실시간으로 코드를 양산하는 환경에서 CI는 단순한 정적 검사 도구가 아니라 엔지니어링 조직의 배포 처리량(Throughput)을 결정짓는 핵심 생산 설비다. Linear 개발팀은 현재도 매주 약 2,000개의 테스트가 새로 누적되는 성장을 경험하고 있으며, 이번 최적화 과정에서 축적한 시스템적 분석 체계를 활용해 새롭게 발생하는 병목에 지속적으로 대응하고 있다.

  • 단일 기법에 의존하지 않고 인프라, 도구, 게이트, 셋업, 실행 단계를 상호 연계하여 개선
  • 샤딩을 늘리기 전에 사전 셋업 비용을 먼저 깎아내어 병렬화 증설의 경제성을 확보
  • AI 에이전트가 코드를 생산하는 속도에 맞춰 검증 제약 조건과 에이전트 스킬을 동기화
  • 정량적 프로파일링과 데이터에 기반해 실질적인 병목 지점을 추적하고 복리적 효과 달성

이 글의 해석으로는, AI 에이전트 도입으로 개발 속도를 높이려는 조직일수록 코드 생성 자체보다 생성된 코드가 통과해야 하는 테스트와 빌드 인프라의 확장성에 먼저 투자해야 한다. Linear의 사례는 도구의 현대화와 정교한 엔지니어링 규율이 결합될 때 폭증하는 워크로드 속에서도 빠른 개발 주기와 비용 통제를 동시에 달성할 수 있음을 입증한다.

9. 확인하지 못한 것

Linear 공식 발표 문서와 기술적 세부 사항에서 아래 항목들은 명확한 추가 자료를 특정할 수 없어 본 절에 기록한다.

  • Linear 개발팀이 GitHub Actions 기본 러너에서 이전한 서드파티 고성능 러너의 구체적인 호스팅 제공업체 사명 및 머신 규격(vCPU 종류, 메모리 세부 용량)은 원문 블로그에 명시되지 않아 확인하지 못했다.
  • isolate: false 적용 대상에서 제외되고 격리 프로젝트에 잔류한 일부 테스트 파일의 구체적인 목록 및 페이크 타이머(fake timers) 사용의 세부 구현 코드는 공개 저장소 코드가 아니어서 특정하지 못했다.
  • 네트워크 저속 연결 대응 및 백오프 재시도를 위해 자체 구축한 체크아웃 커스텀 컴포짓 액션의 전체 YAML 소스 코드는 원문 글에 전문이 실리지 않아 확인하지 못했다.
  • 주간 약 2,000개의 신규 테스트가 추가되는 과정에서 각 AI 코딩 도구(Cursor, Claude 등)별 생성 테스트 비중이나 정량적 기여율 통계는 원문에서 공개하지 않아 확인하지 못했다.
