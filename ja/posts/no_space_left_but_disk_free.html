ディスクは空いているのに No space left on device - inode と開いたままのファイル

症状は一つでも原因は四つある。その四つを順に切り分ける方法

2026年9月1日 開発・インフラ

サービスがログを書けないという通知を受けてサーバーに入る。習慣どおり df -h を打つ。空きは 30 パーセント以上残っている。ところが同じシェルで touch を一度打つだけで No space left on device が返ってくる。この瞬間に時間の大半が浪費される理由は一つだ。df が嘘をついていると考えるからである。

df は嘘をつかない。ただ訊かれていないことには答えないだけだ。容量を訊けば容量を答え、ルートを訊けばルートを答える。書き込みが失敗した本当の理由が容量でないか、ルートでないなら、df の答えは正確なまま役に立たない。この記事では、その食い違いが生まれる四つの場所を切り分け、どの順に当たれば最も早く終わるのかを整理する。

症状は一つ、原因は四つ

ENOSPC は、カーネルがアプリケーションに この書き込みは受け付けられない と伝える一つの信号だ。信号が一つだからといって事情が一つとは限らない。人間でいえば熱が出るのと同じで、熱そのものは診断ではなく診断を始めよという合図だ。ところが現場では ENOSPC を見た途端に 消せるものを探す 作業へ移ることが多く、原因が容量でないときその作業はすべて無駄になる。

切り分けるべき場所は四つだ。次の表の右端の列、すなわち 区別できる信号 がこの記事の実質的な中身である。左の二列だけ覚えても、順序はやはり組み立てられない。

原因実際に埋まったもの確認コマンド区別できる信号
① inode 枯渇ファイル数の上限df -iUse% は低いのに IUse% だけ 100%
② 削除済みだが開いたファイル返されていないブロックlsof +L1 ・ /proc/<pid>/fddf は満杯、du の合計ははるかに小さい
③ 予約ブロックroot 専用に取り置かれた分tune2fs -l一般アカウントだけ失敗し、root は成功する
④ 別のマウント自分が見ていないファイルシステムdf -h <パス>ルートには空きがあり、そのパスだけ 100%
  • ①と④は 確認がそれぞれ一行 だ。だからこの二つを先頭に置くのが最も時間を節約する
  • ②は df と du を 一緒に見て初めて 表に出る。片方だけ見ていては永遠に見えない
  • ③はまれだが、同じサーバーを見ている人によって結果が違う という奇妙な状況を作り、時間を長く食う

この記事の実行環境と検証の範囲

この記事の主題は Linux サーバーだが、ここに貼った出力を実際に生み出した環境は Windows 10 上の Git Bash だ。これを先に明かす理由は謙虚に見せるためではなく、どの出力はそのまま信じてよく、どの出力はここに無いのか を読者が区別できる必要があるからだ。

$ bash --version | head -1
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)

$ uname -a
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64 2025-01-30 11:14 UTC x86_64 Msys

$ df --version | head -1
df (GNU coreutils) 8.32

coreutils は Linux と同じ GNU 8.32 なので、df・du・stat・sort の オプションの挙動と計算方法は同一 だ。異なるのはその下のファイルシステムが NTFS だという点だけで、あとで見るとおり、その違い自体がむしろ inode を理解する助けになる。

  • 実際に走らせたもの - df -h、df -i、df --output、stat -f、stat -c、du の各種組み合わせ、find -printf、そして 削除済みだが開いたファイルの再現一式
  • 走らせられなかったもの - lsof +L1(この環境に lsof 自体が無い)、tune2fs・debugfs・resize2fs(ext4 専用)、コンテナのオーバーレイ関連すべて
  • 作り話をしていないもの - 走らせられなかったコマンドの出力は、この記事に一行も無い。コマンドと 読み方 だけを書いた
  • 手を入れたもの - 出力に出たユーザーのパスだけを /tmp/demo と <user> に縮めて書いた。数字は一つも直していない
  • ブロックサイズはこの環境で 4,096 バイト と報告される。この記事のブロック計算はすべてこの値が基準だ
  • 他のシェル(dash・zsh)や BSD 系の df・du ではオプション名と出力形式が異なる。以下のコマンドは GNU coreutils 基準 だ

まず訊くこと - 本当にそのファイルシステムか

順序としてはこれが一番目だ。原因の一覧では④番だが、確認が最も安いから である。df -h を引数なしで打つとマウントの一覧が出るが、人の目はたいてい一番上のルートの行で止まる。実際に失敗したパスが別のファイルシステムに付いていれば、その行は画面の下のどこかにある。

直す方法は df にパスを直接与えること だ。この環境でも、同じ物理ディスクを二つの別々のマウントとして報告する。

$ df -h . /
Filesystem                        Size  Used Avail Use% Mounted on
C:/Users/<user>/<temp>  931G  600G  332G  65% /tmp
C:/Program Files/Git                931G  600G  332G  65% /

# 要点 - 現在のディレクトリは / ではなく /tmp に付いている。
# Linux でも同じだ。失敗したパスを df に直接与える。
$ df -h /var/log

Linux サーバーでこの落とし穴に最もよく掛かる場所は決まっている。次の一覧は ルートに空きがあるのに書き込みが失敗する 典型的な配置だ。

  • /var が別パーティションの構成 - ログとパッケージのキャッシュがここに積もるので、ルートよりはるかに早く埋まる
  • /boot - たいてい数百 MB で切られているので、カーネルのパッケージが数個積もるだけで埋まる。症状が カーネル更新の失敗 として現れ、ディスクの問題に見えない
  • /tmp が tmpfs の構成 - メモリを使うので実際のディスクとは無関係に埋まる。再起動すると消えて原因が蒸発する
  • コンテナの中 - 書き込み可能レイヤーとマウントされたボリュームは 互いに別のファイルシステム だ。ボリュームに空きがあってもレイヤーが埋まれば失敗する
  • バインドマウントや NFS が重なったパス - パスの文字列だけ見ると同じツリーのようだが、装置が違う

原因 ① inode 枯渇 - 容量は残っているのに個数が埋まった

ファイルシステムはデータだけを保存するのではなく、ファイル一つ一つに対するメタデータ項目 も別に管理する。所有者、権限、時刻、そして実際のデータブロックがどこにあるかを収めた構造が inode だ。ファイル名はここに無い。名前はディレクトリが持っており、ディレクトリは 名前と inode 番号を組にした一覧 だ。この構造のおかげで一つの inode に複数の名前を付けられ、それがハードリンクである。

重要なのは この項目の個数に上限があり得る という点だ。上限が埋まると、ブロックがいくら残っていても新しいファイルは作れない。確認は df -i の一行だ。ところがこの環境で、そのコマンドはこう答える。

$ df -i .
Filesystem                       Inodes IUsed IFree IUse% Mounted on
C:/Users/<user>/<temp>    -     -     -     - /tmp

$ stat -f .
  File: "."
    ID: ea1df1ef00000000 Namelen: 255     Type: UNKNOWN
Block size: 4096       Fundamental block size: 4096
Blocks: Total: 244041727  Free: 86972107   Available: 86972107
Inodes: Total: 18446744073709551615 Free: -1

すべて - だ。そして stat -f がその理由を見せてくれる。inode の総数として報告された 18,446,744,073,709,551,615 は符号なし 64 ビット整数の最大値、すなわち 上限が無いという意味の表示値 であり、Free は -1 だ。NTFS には ext4 のような固定 inode テーブルが無いので、報告すべき数字そのものが無い。

この空欄は失敗ではなく、最も重要な事実をそのまま見せている画面 だ。inode の上限はファイルシステムの普遍的な性質ではなく、実装ごとに異なる設計上の選択 である。だから ext4 のサーバーで通じる対応が、XFS のサーバーではそのまま通じない。Linux で実際の数字が埋まった画面と、そのとき続けて打つコマンドはこうだ。

# ① どのマウントの inode が埋まったのか
df -i

# ② そのマウントの中でファイルが集中しているディレクトリ (まず粗く見る)
du --inodes -x -d 2 /var 2>/dev/null | sort -n | tail -20

# ③ ディレクトリ別のファイル数を直接数える (du --inodes が無い古い環境)
find /var -xdev -type f -printf '%h\n' 2>/dev/null \
  | sort | uniq -c | sort -rn | head -20

# 上の三行はこの環境では実行できなかった。
# NTFS が inode 数を報告せず、①が空欄になるためだ。

小さなファイルが数百万個ずつ積もる場所はおおむね決まっている。次は 容量のグラフには何の変化も無いのに inode だけが静かに満ちていく 典型的な位置だ。

  • セッションファイル - 期限切れの掃除を仕掛けていないと訪問者の数だけファイルが積もり、それぞれは数百バイトだ
  • メールキューと Maildir - メッセージ一通がファイル一つだ。送信が止まればキューがそのまま個数として残る
  • キャッシュの断片 - ハッシュをディレクトリに分けるキャッシュは、ディレクトリも inode を使う という点で二倍に膨らむ
  • ログの断片 - ローテートの周期が短く保管個数が大きいと、圧縮版が残り続ける。それぞれは小さいが、個数で勝負が決まる
  • 依存関係のディレクトリ - ビルド環境ごとに一つずつ作られるパッケージのツリーは、ファイル数だけで数十万の単位に増える

inode はいつ決まるのか - ext4 ・ XFS ・ btrfs

ここで分かれる。mke2fs の文書は -i オプション、すなわち inode 一つあたり何バイトを割り当てるかについてこう釘を刺す。ファイルシステムが作られたあとはこの比率を変更できないので、値を慎重に決めよ ということだ。予約ブロックの比率の既定値が 5 パーセントだというのも同じ文書にある。

この一文が実務で意味するところは重い。ext4 で inode が埋まったなら、増やす選択肢は無い。 ファイル数を減らすか、データを移してファイルシステムを作り直すかだけだ。障害の真っ最中に知るには遅すぎる事実なので、ストレージを設計するときにあらかじめ決めておくほうがよい。

ファイルシステムinode の割り当て方式あとで増やせるか実務で意味すること
ext4mkfs の時点で個数が固定。-i 比率または -N 個数で指定不可。文書が明示的に変更不可と書いている小さなファイルが多いと分かっているなら 作るとき に比率を下げておく
XFS動的割り当て。上限だけを maxpct で管理可能。xfs_growfs -m で上限を変更枯渇しても上限を上げて時間を稼ぐ余地がある
btrfsカーネル文書の機能一覧に 動的 inode 割り当て が挙がっている固定上限という概念そのものが異なるdf -i の数字を ext4 と同じ意味で読んではいけない
  • XFS の maxpct の既定値はファイルシステムの大きさによって異なる。文書によれば 1TB 未満は 25 パーセント、50TB 未満は 5 パーセント、それ以上は 1 パーセント だ
  • maxpct を 0 にすると事実上ファイルシステム全体が inode ブロックになり得ると文書は書いている。上限を外すということであり、同時にデータ領域を守る仕掛けが無くなるということ でもある
  • だから df -i の IUse% は ファイルシステムの種類を知らないと読めない数字 だ。同じ 90 パーセントでも、ext4 では警報、XFS では上限を上げるかを判断する材料になる

原因 ② 削除したのに開いたままのファイル

rm はデータを消す命令ではない。ディレクトリから名前を一つ外す unlink だ。名前がすべて消えてリンク数が 0 になっても、そのファイルを 開いたままのプロセスが一つでも残っていれば カーネルはブロックを返さない。最後の参照が閉じられる瞬間になって初めて領域が戻る。

この挙動自体は欠陥ではなく、POSIX が定めた安全装置だ。読んでいる途中にファイルが消えてプロセスが壊れることを防いでくれる。問題は、このとき 観測の道具が互いに異なる答えを返す ことだ。df はファイルシステムのブロックの帳簿を読むので、つかまれた領域を 使用中 と見る。du はディレクトリを歩き回ってファイルを数えるので、名前の無いファイルはそもそも見えない。だから二つが食い違う。

この環境でそのまま再現された。1GiB のファイルを作り、tail -f でつかんだまま消し、空きブロック数を段階ごとに読んだ。以下は実際の出力だ。

$ cd /tmp/demo
$ free() { stat -f -c %f .; }          # 空きブロック数 (1 ブロック = 4096 バイト)

STEP 0  空のディレクトリ       空きブロック: 86970141
$ head -c 1073741824 /dev/zero > big.log
STEP 1  1GiB 作成              空きブロック: 86707994   du -sh: 1.0G
$ ( tail -f big.log > /dev/null & )
STEP 2  tail がつかんでいる
$ rm big.log
STEP 3  rm 直後                空きブロック: 86708010   du -sh: 1.0K
STEP 3b 2 秒後                 空きブロック: 86708010
$ kill <tail の pid>
STEP 4  プロセス終了後         空きブロック: 86970153

数字をそのまま読むとこうだ。ファイルを作るとき 262,147 ブロック が減った。4,096 バイトを掛けると約 1.0GiB で、作った大きさと合う。ところが rm の直後に戻ったのは 16 ブロック だけだ。1GiB を消して 64KiB が戻ったのだから事実上 0 である。一方、同じ時点で du はすでに 1.0K と答える。df と du が 1GiB 分だけ食い違った状態 がここで作られる。

そしてプロセスを終了させると 262,143 ブロック が一度に戻った。消したのは rm だったが、領域を返したのは kill だった。解決はファイルをもう一度消すことではなく、つかんでいる側に放させること だという言葉の根拠が、この二行である。

犯人を探すのは別の問題だ。標準の道具は lsof +L1 で、文書はこの形が 名前が消えたまま開いているファイルを選ぶ と説明している。ただしこの環境には lsof が入っていないので走らせられなかった。代わりに /proc のほうはそのまま動き、カーネルが付ける (deleted) の表示がはっきり出た。

# この環境で実行したもの - /proc で確認
$ ls -l /proc/<pid>/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/big.log (deleted)

# この環境で実行できなかったもの - lsof が未インストール
$ sudo lsof +L1                  # リンク数が 1 未満の開いたファイルだけ
$ sudo lsof -nP +L1 /var         # 特定のマウントに絞る
注意 - プロセスを再起動できないとき、> /proc/<pid>/fd/<n> でファイル記述子を切り詰める方法が広く知られている。領域はすぐ戻るが、番号を選び間違えるとそのプロセスが開いている別のファイルが丸ごと空になる。 取り消せず、確認の手順も無い。再起動が可能なら、再起動が常に安全な側だ。
  • この状況を最も多く作るのは ログローテーションの設定ミス だ。ファイルを移すか消したあとにプロセスへ開き直せという信号を送らなければ、プロセスは名前の無い古いファイルに書き続ける。ログローテーションが静かに失敗するのはここだ
  • つかんでいるプロセスを特定する手順そのものはこの記事の範囲外だ。ここでは 領域が戻らない理由 までを見る
  • ディスク使用量が階段状に減らないグラフ はこの原因のよい信号だ。整理作業を回したのにグラフが平らなら、消したものがまだ開いている
  • 再起動の対象はたいていログを書く側だ。ログをファイルに残すアプリケーションと、そのログを読んで転送する収集器の 両方とも が同じファイルをつかんでいることがある

原因 ③ 予約ブロック - root にだけ見える空き

ext 系は全体のブロックの一部を 特権プロセス専用 に取り置く。tune2fs の文書はその理由を二つ挙げている。ファイルシステムの断片化を避けるため、そして 非特権プロセスが書き込みを拒まれたあとでもシステムデーモンが正常に動作し続けられるようにするため だ。既定値は 5 パーセントである。

だからこういう場面が生まれる。アプリケーションのアカウントでは書き込みが失敗するのに、管理者で入って同じ場所にファイルを作ると成功する。二人が同じサーバーを見ながら互いに違う結論を出す状況が、ここで生じる。df の Use% が 100 パーセントではなく 95 パーセント前後で止まっているのに 書き込みが失敗するなら、この原因を疑う価値がある。

# 予約ブロックの確認 (ext2/3/4) - この環境では実行できなかった
$ sudo tune2fs -l /dev/sda1 | grep -iE 'block count|reserved'
# Block count:              全体のブロック数
# Reserved block count:     予約されたブロック数
# 二つの値の比率がそのまま予約比率だ。

# 比率の調整 - 戻せるが慎重に
$ sudo tune2fs -m 1 /dev/sda1    # 5% -> 1%
注意 - tune2fs -m 0 で予約を完全に無くすという助言をよく見かけるが、文書が明かした二つの目的がともに消える。空きが 0 に近づくと 連続したブロックを見つけられず断片化が急激に進み、ログを書くデーモンまで一緒に止まって 障害の原因を記録する手段 を失う。マウントされた状態で誤って指定すると、戻すまでそのまま適用される。
  • 予約比率は パーセント だ。だからディスクが大きくなるほど取り置かれる絶対量が大きくなる。数 TB のボリュームで 5 パーセントはかなりの量になる
  • データ専用のボリューム、すなわちシステムデーモンがログを書かないボリュームでは比率を下げる根拠がある。ただし 0 ではなく 1〜2 パーセント程度は残す
  • 逆に / と /var では既定値をそのままにしておくほうがよい。ここがまさに文書の言う デーモンが動き続けねばならない場所 だ
  • XFS には同じ名前の概念が無く、別の方式で空きを管理する。ext 系の習慣をそのまま持ち込んではいけない

小さなファイルが領域をより食う理由

ファイルシステムはバイト単位で領域を与えず、ブロック単位 で与える。1 バイトのファイルもブロックを一つ丸ごと受け取る。余った部分は他のファイルが使えず、この無駄を内部断片化と呼ぶ。言葉だけ聞くと些細に見えるが、個数が掛かった瞬間に性格が変わる。

実際に測ってみた。du の --apparent-size は 論理的な大きさ を、既定の挙動は 実際の割り当て量 を報告する。二つの値を並べれば差がそのまま見える。

$ du -b --apparent-size one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1        one_byte.txt
100      b100.bin
4096     b4096.bin
4097     b4097.bin
1048576  b1m.bin

$ du --block-size=1 one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1024     one_byte.txt
1024     b100.bin
4096     b4096.bin
8192     b4097.bin
1048576  b1m.bin

最も注目すべき行は b4097.bin だ。論理サイズ 4,097 バイト に対して実際の割り当ては 8,192 バイト。ブロックの境界を 1 バイト越えたという理由で 4,096 バイトが丸ごと余計に付いた。4,096 バイトのファイルはきっかり 4,096 を使うというのに。

論理サイズ実際の割り当て(測定)無駄倍数
1 B1,024 B1,023 B1,024 倍
100 B1,024 B924 B約 10 倍
4,096 B4,096 B01 倍
4,097 B8,192 B4,095 B約 2 倍
1,048,576 B1,048,576 B01 倍

ここで一つ正直に断っておくことがある。1 バイトのファイルの割り当てが 4,096 ではなく 1,024 と出たのは、NTFS がごく小さなファイルをメタデータのレコードの中に一緒に保存するからだ。ext4 はこの最適化を既定では使わないので 同じ実験では 4,096 が出ると予想されるが、その画面はこの記事には無い。 一方、ブロックの境界で二倍に跳ねる b4097.bin の挙動は、ブロック単位の割り当てを使うファイルシステムに共通だ。

個数を掛けるとどうなるかも測ってみた。1 バイトのファイル 2 万個だ。

$ time ( for i in $(seq 1 20000); do printf 'x' > "f$i"; done )
real    0m25.766s

$ ls -1 | wc -l
20000

$ du -sb --apparent-size .
20000     .          # 論理合計 = 20,000 バイト (約 20KB)

$ du -s --block-size=1 .
24674304  .          # 実際の占有 = 24,674,304 バイト (約 23.5MiB)

論理 20KB が実際には 23.5MiB を占める。約 1,233 倍 だ。この値にはファイル自体の割り当て分と、2 万個の名前を収めるために大きくなったディレクトリ構造が一緒に入っている。ディレクトリも領域を使う という事実が、ここで目に見える。

  • ext4 で 4KiB ブロックにして同じことをすると、算数はこうなる。1 バイトのファイル 100 万個は論理 1MB、実際には 4,096,000,000 バイトすなわち約 3.8GiB だ。この値は 測定ではなくブロックサイズによる計算 であり、ディレクトリ構造を除いた値だ
  • だからファイルの多い場所では 容量と inode が同時に 減っていく。どちらが先に底を突くかはファイルサイズの分布次第だ
  • 小さなファイルをまとめて一つにするのが根本的な対応だ。ログはローテート後に圧縮し、キャッシュには期限を設け、アーカイブは 個別のファイルではなくまとまり で保管する

何が食ったのかを探す - du の定型句

マウントを特定し、容量の問題で間違いないところまで確認できたら、次は上から下へ絞り込んでいく作業だ。定型句は一つあれば足りる。

$ du -h -x --max-depth=1 . | sort -h
1.0K    ./deleted_open
1.0K    ./demo2
24M     ./tiny
25M     .

# 大きいものが下に来るので、最後の行から読む。
# Linux では普通こう始める。
$ sudo du -h -x --max-depth=1 / | sort -h

三つのオプションがそれぞれ仕事をする。--max-depth=1 は 一段階だけ 見せる。深さを与えないと数万行が流れ出て読めない。sort -h は 24M のような人が読む表記を 大きさの順に 並べる。文字列の並べ替えでは 9K が 24M より後ろに来る。

そして -x がこの定型句の核心だ。別のファイルシステムへ渡らないように 止めるオプションである。これを外して / から舐めると、マウントされたネットワークストレージやコンテナのレイヤーまで追って入っていき、時間は何倍もかかり、いま探しているファイルシステムと無関係な数字が結果に混ざる。

ただしここでも正直に書いておくことがある。この環境では -x が実際に何かを止める場面を作れなかった。

$ stat -c %d / /tmp .
3927831023
3927831023
3927831023
# 三つとも同じ装置 ID -> -x が止まる境界がそもそも無い。
# オプションが受け付けられ、結果が同じであることまでを確認した。

# ファイル数で絞る版 (inode 枯渇のとき)
$ find . -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head -5
  20000 ./tiny
      5 .
      1 ./demo2
      1 ./deleted_open
  • sort -h は GNU の拡張だ。この環境のヘルプに -h, --human-numeric-sort として実在することを確認したが、BSD 系や最小構成のコンテナイメージには無いことがある。そのときは du -k で取り出して sort -n を使う
  • du --inodes は大きさではなく 項目の個数 を数える。inode 枯渇のときは、上の定型句から -h だけ外してこれに替えればそのまま使える
  • find はファイルを一つ一つ舐めるので、ファイルの多いファイルシステムでは時間がかかる。稼働中のサーバーでは負荷を見込んで範囲を絞って始める
  • 結果が 合計と合わなければ 原因②を疑う。du でいくら足しても df の使用量に届かないなら、名前の無いファイルがどこかで開いている

診断の順序 - 四段階

ここまでの内容を実行の順序に畳むと四段階になる。各段階は 次の段階へ進むかどうかを決める ためにある。順序を守る理由は、前の段階が後の段階より圧倒的に安いからだ。

段階何を訊くかコマンドこう出たら次
1どのマウントかdf -h <失敗したパス>その行の Use% が低い別のパスを見誤っていた。失敗したパスを確認し直す
2容量か inode かdf -i <失敗したパス>IUse% だけ 100%原因①。ファイルが集中したディレクトリを探す
3du と食い違うかdu -sh -x <マウント> を df と照合du の合計がはるかに小さい原因②。つかんでいるプロセスを探して再起動
4何が食ったかdu -h -x --max-depth=1 | sort -h大きい項目が特定される一段階ずつ下りながら繰り返す
+root だけ通るか一般アカウントと root でそれぞれ touchroot だけ成功する原因③。予約ブロックを確認
  • 1 段階と 2 段階は 合わせて二行 で、負荷は事実上無い。ところがこの二つだけで終わる場合が実際にかなり多い
  • 3 段階を飛ばすと、4 段階で時間を使い切っても何も見つけられない。du が犯人を見つけられない状況 が存在すると知っていることが、この表の要点だ

コンテナとクラウドで変わること

同じ症状がコンテナの中ではもっと紛らわしい。コンテナの中の df は そのコンテナが見ているマウント を答えるが、実際に埋まっているのはホストノードのディスクである場合が多い。逆にノードには空きが余っているのに、コンテナの書き込み可能レイヤーに掛かった上限だけが埋まっている場合もある。どちら側で df を打ったのか をまず決める必要がある。

状況勘違いしやすいこと実際に見るべき場所
イメージレイヤーが埋まったボリュームに空きがあるから大丈夫だ書き込み可能レイヤーはボリュームとは 別のファイルシステム だ
停止したコンテナと古いイメージが積もった稼働中のものだけ数えれば大した量ではない停止したコンテナ、未使用のイメージ、ビルドキャッシュをすべて合算する
コンテナのログが無限に育つアプリケーションがログを残していないランタイムが標準出力をファイルに積む。サイズ上限の設定を確認
クラウドのディスクを増やしたのに変わらないコンソールで増やしたのだから終わりだパーティションとファイルシステムは 別々に広げねばならない
ノードの inode が埋まった容量のグラフが平らだから問題ないイメージレイヤーは小さなファイルの塊だ。inode を別に監視する

最後の行は特によく掛かる。resize2fs の文書は このプログラムはパーティションの大きさを操作しない と明記している。すなわちブロック装置を増やしたなら、まずパーティションを拡張し、そのあとにファイルシステムを拡張しなければならない。この二段階を一つと取り違えると、コンソールでは容量が増えたのにサーバーの中では変わらないままという状態になる。

# クラウドのディスク拡張後 - 順序がある (この環境では実行できなかった)
# ① カーネルが新しい大きさを見たか
lsblk

# ② パーティションの拡張 (パーティションを使う構成のときだけ)
sudo growpart /dev/sda 1

# ③ ファイルシステムの拡張
sudo resize2fs /dev/sda1        # ext2/3/4
sudo xfs_growfs /               # XFS はマウントポイントを与える

# コンテナ側 - 何が場所を取っているかを種類別に合計
docker system df
docker system df -v
  • オーバーレイ方式はファイルを修正するとき 原本を上のレイヤーへ複写してから 直す。大きなファイルの一行を直しても、そのファイルの大きさだけ領域が余計に必要になり得る
  • コンテナの中で消したファイルは 下のレイヤーからは消えない。削除の印が上に載るだけなので、イメージの大きさは減らない
  • 整理コマンドは便利な分だけ危険だ。使っていないボリュームまで一緒に消すオプション があり、そのボリュームにデータが入っていることがある
  • ノード全体が埋まった状況では、スケジューラが ポッドを他のノードへ押し出す。症状がディスクではなく再起動として先に現れ、原因の特定が遅れる

急ぐとき - 消してよいものと駄目なもの

サービスが止まっていると判断する時間が無い。だから あらかじめ決めておいた一覧 が必要だ。ただし最初の一手は消すことではない。つかまれた領域があるかをまず確認すること が最初の一手だ。原因②なら何を消しても回収されないので、確認せずに消し始めると時間だけを失い、取り消せない削除だけが残る。

区分対象なぜ
比較的安全ローテート後に圧縮された古いログすでに閉じられたファイルだ。保管期間だけ確認すればよい
比較的安全パッケージ管理者のキャッシュまた落としてこられる。再インストールの時間だけで済む
比較的安全ビルド成果物と一時ディレクトリ再生成が可能。ただし 進行中のビルドが無いか を確認
注意コアダンプ消してもよいが 障害原因の分析資料 だ。先に移す
絶対禁止いま開いているログ本体領域は戻らずログだけを失う。原因②を作る
絶対禁止データベースファイル・ロックファイル・ソケット破損や起動不能につながる
絶対禁止中身の分からないディレクトリ急ぐときほど確認せずに消す。取り消せない
注意 - rm -rf は確認を求めず、取り消せない。パスを変数にして使うと 変数が空のときに最上位から消す事故 が起きる。実行前に同じ引数で ls -d を先に回し、対象を目で確認する習慣は安上がりだ。truncate -s 0 はファイルを残したまま空にするので開いているログにも使えるが、中身はそのまま消える。移すべき値があるなら先に移す。
  • 空きが完全に 0 だと 消す作業自体が失敗 し得る。ログを残したり一時ファイルを作ったりする道具は、このとき動作しない
  • だから truncate -s 0 や : > ファイル のように 新しいファイルを作らない空にし方 が、この状況では役に立つ
  • 急場をしのいだあとは必ず原因を辿り直す。消して解決したということは、なぜ埋まったのかを説明しない。 同じことが同じ周期で戻ってくる

そもそも防ぐ方法

この症状は監視項目が一つ抜けているために起きることが多い。容量はほとんどの場所で見ているが、inode の使用率は既定のダッシュボードに無いことがよくある。 だから容量のグラフが平らなまま障害になる。

しきい値を超えたマウントだけを取り出すスニペットを一つ作って回してみたところ、ここで よくある定型句が実際に間違う場面 が出た。記録しておく価値のある失敗なので、そのまま写す。

# よく使われる版 - この環境では誤答を出した
$ df -P | awk 'NR>1 && $5+0 >= 80 {print $6, $5}'
65% 347611880          # 値が逆さまに出た

# 理由 - 装置名に空白があってフィールドが一つずれた
$ df -P | awk 'NR>1 {print "NF=" NF "  $5=[" $5 "]  $6=[" $6 "]"}'
NF=7  $5=[347583704]  $6=[65%]

# 直した版 - フィールドを数えず、指定して受け取る
$ df --output=pcent,target | awk 'NR>1 && $1+0 >= 60 {print "DISK", $2, $1}'
DISK / 65%

$ df --output=ipcent,target | awk 'NR>1 && $1+0 >= 60 {print "INODE", $2, $1}'
(出力なし - このファイルシステムが inode の比率を報告しない)

df -P の出力をフィールド番号で切る方式は、装置名やマウントポイントに空白が無いという仮定 の上に立っている。その仮定が崩れると静かに別の列を読み、条件式はそのまま真になって 間違った警報が正常のように流れる。 df --output= で必要な列だけ受け取れば、この仮定そのものが要らなくなる。

  • inode の使用率を監視項目に追加する。 容量と同じしきい値にしておけば十分だ。無いよりましという水準ではなく、この記事の原因①はこれ一つで全部予防できる
  • ログのローテーションは 保管個数と圧縮の有無 を一緒に決める。個数だけ大きく取ると容量は平気でも inode が埋まる
  • 一時ファイルには 期限切れの掃除 を仕掛ける。セッションとキャッシュは、作るコードが消すコードまで持っていなければならない
  • コンテナのログには ファイルサイズの上限と保管個数 を明示する。既定値が無制限の構成がよくある
  • 警報は 残りのパーセントではなく残りの時間 で見るほうがよい。一日に何 GB ずつ増えているかが分かれば、いつ埋まるかを計算できる

まとめ

No space left on device は診断ではなく診断の始まりだ。その背後には少なくとも四つの事情があり、どれなのかによって やるべきことが正反対 になる。inode が埋まっているなら大きなファイルを探しても無駄だし、消したのに開いたままのファイルが原因なら、もっと消すことが害になる。

だから覚えるべきはコマンドの一覧ではなく順序だ。失敗したパスを df に直接与え、df -i で容量か個数かを分け、du の合計を df と突き合わせ、そのあとで初めて何が食ったのかを探す。三番目の段階がこの順序の値打ち だ。ここで食い違いが見えれば、残りの探索がすべて無駄だと前もって分かる。

そして、この記事で実際に測った数字二つは覚えておく価値がある。消した 1GiB がプロセスを殺すまで 16 ブロックしか戻らなかった こと、そして 1 バイトのファイル 2 万個が 23.5MiB を占めた ことだ。どちらも df を一度だけ見る習慣では絶対に見えない数字である。

確認できなかったこと

  • inode が実際に枯渇した画面 を作れなかった。この環境の NTFS は inode 数を報告しないので df -i がすべて - で出る。IUse% が 100 パーセントの出力はこの記事には無く、代わりに なぜ空欄が出るのか を stat -f で見せた
  • lsof +L1 を走らせられなかった。 この環境に lsof が入っていない。オプションの意味は文書で確認し、同じ目的の /proc/<pid>/fd のほうは実際に走らせて (deleted) の表示まで確認した
  • tune2fs・debugfs・resize2fs・xfs_growfs は実行できなかった。 ext4/XFS 専用の道具であり、この環境に対象のファイルシステムが無い。予約ブロック比率 5 パーセント、XFS の maxpct の既定値、resize2fs がパーティションに触れないという点は 公式の man 文書で確認 した
  • ext4 での 1 バイトのファイルの割り当て量 を直接測れなかった。この環境では 1,024 バイトと出たが、これは NTFS の小型ファイルの保存方式によるものだ。4KiB ブロック基準の計算値は本文に 計算だと明かして 書いた
  • du -x がファイルシステムの境界で止まる場面 を作れなかった。/・/tmp・作業ディレクトリの装置 ID がすべて同じで、渡る境界が無かった。オプションが受け付けられることまでを確認した
  • btrfs の df -i の出力形式 は確認できなかった。カーネル文書の機能一覧に動的 inode 割り当てが挙がっているという事実だけを確認し、その数字をどう読むべきかはこの記事では扱っていない
  • コンテナとクラウドの節はすべて未実行 だ。オーバーレイの挙動、整理コマンドの出力、ディスク拡張の手順のうち、この環境で走らせたものは一つも無い。コマンドの順序と根拠だけを書いた

参考資料

  • mke2fs(8) - man7.org - 予約ブロックの既定値が 5 パーセントだということ、そして -i の bytes-per-inode 比率は ファイルシステムの作成後には変更できない という警告
  • tune2fs(8) - man7.org - -m オプションの説明。ブロックを予約する二つの理由が 断片化の回避 と 非特権プロセスが止められたあともシステムデーモンが動作し続けられるようにすること だと書かれている
  • mkfs.xfs(8) - man7.org - maxpct の意味と大きさ別の既定値(1TB 未満 25%、50TB 未満 5%、それ以上 1%)、そしてこの値を xfs_growfs で変更できるという説明
  • xfs_growfs(8) - man7.org - -m で inode に割り当て可能な最大比率を新たに指定するというオプションの説明
  • lsof(8) - man7.org - +L のうしろに数字を与えるとリンク数がそれより小さいファイルだけを列挙し、+L1 の形は 名前が消えたまま開いているファイル を選ぶという説明
  • resize2fs(8) - man7.org - このプログラムはパーティションの大きさを操作しない という一文。ディスクを増やしたあとパーティションとファイルシステムを別々に拡張しなければならない根拠
  • BTRFS - The Linux Kernel documentation - 機能一覧に 動的 inode 割り当て が含まれているということ
