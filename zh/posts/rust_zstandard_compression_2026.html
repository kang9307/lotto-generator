引言：为什么要用Rust重写压缩库

2026年6月初在GeekNews（news.hada.io）上引发讨论的用Rust实现的Zstandard，是Trifecta Tech Foundation于2026-06-01发布的「Announcing Zstandard in Rust」。对应的项目是libzstd-rs-sys，做法是先用c2rust把zstd的C参考实现转成Rust，再逐步清理代码。把一个多年来用C运行良好的压缩库特意重写，并不是语言偏好之争，而是解析不可信外部输入的系统软件正在迁往内存安全语言这一大趋势中的一个场景。

压缩库平时不显眼，却在几乎所有系统的背后运行。Web服务器压缩响应、数据库向磁盘写数据、容器镜像仓库传输镜像、备份工具归档文件时，都会调用压缩编解码器。而这些编解码器大多要解压从网络或文件接收的、无法控制的数据。解压过程中只要有一个内存缺陷，攻击者就可能用一个精心构造的压缩文件接管服务器。

本文依次讨论：(1) Zstandard是什么，(2) 为什么偏偏是Rust，(3) C压缩库的漏洞历史，(4) Rust重写的五大好处，(5) gzip·lz4·zstd·brotli对比，(6) zstd流行的原因，(7) Rust中的三类实现，(8) Rust与C的性能，(9) 五个实战场景，(10) 在实际开发现场的落地，(11) 结论与三条可立即采用的建议。crate版本、实现状态与基准数据均于2026-09-29对照各项目的仓库、crates.io与README核对。

1. Zstandard是什么 - zstd压缩算法概览

Zstandard（简称zstd）是Facebook（现Meta）开发、2016年公开的通用无损压缩算法。参考实现的仓库是github.com/facebook/zstd，许可证为BSD与GPLv2二选一的双重许可。格式已稳定并以RFC 8878成文，截至2026-09-29参考实现的最新版本是v1.5.7（2025-02-19）。README将zstd介绍为「面向实时压缩场景、压缩率达到zlib水平或更好的快速无损压缩算法」。

zstd区别于其他算法的特点有三。第一是压缩级别的跨度。按Rust zstd crate的文档，常规级别为1到22；用--fast=#指定的负级别以牺牲压缩率换取更快的压缩与解压。提高级别则以压缩速度换取压缩率，而据README所述，解压速度在各种设置下大致相同。第二是字典（dictionary）训练。README指出数据越小越难压缩，并说明用样本训练出的字典能让小数据的压缩率大幅提升。第三是流式API设计简洁，可以不把大文件全部读入内存就进行处理。

从内部看，zstd是在由Huff0与FSE（Finite State Entropy）构成的高速熵编码阶段之上，叠加LZ77系匹配的结构。不必深入理论，需要强调的是zstd已成为2020年代压缩的事实标准。Linux内核、RocksDB、Parquet、ZFS、btrfs以及多个包管理器都采用了zstd。

2. 为什么用Rust重写 - 内存安全的价值

把运行良好的C库特意用Rust重写，理由可以归结为一个词：内存安全。

C和C++强大而快速，但内存需要手动管理。指针运算、手动分配与释放、缺少边界检查，会直接导致缓冲区溢出、use-after-free、double free、整数溢出。这些不只是缺陷，而是安全漏洞。微软和谷歌公布的统计显示，其安全漏洞约70%源于内存安全问题。

Rust通过所有权（ownership）与借用检查器（borrow checker）在编译期检查这类问题，无需垃圾回收、没有运行时开销，就能静态验证安全代码的内存访问。因此用安全的Rust重写zstd这类编解码器，可以从结构上减少「解析不可信输入时发生内存破坏」这一类CVE。不过这一效果只适用于unsafe块之外的代码。用c2rust转换的代码起步时满是unsafe，重写的真正价值取决于清除了多少unsafe（见第7节）。

要点 - 压缩库几乎总是在解压「从外部收到的、不可控的数据」。这正是内存安全语言最能发挥价值的地方。

3. C实现的风险 - 压缩库的安全漏洞历史

这不是抽象的风险。压缩库确实反复出现过严重问题。下面整理几种典型类型。

3-1) zlib与解压炸弹

使用最广的zlib经过数十年打磨，但建立在它之上的众多封装和解析器中仍不断发现与解压相关的漏洞。像「zip炸弹」这样让小压缩文件在解压时占用巨量内存的攻击至今有效，而且内存安全语言也挡不住。纯Rust解码器ruzstd在README中也提醒解压结果可能非常大，建议先检查帧大小或以流式方式读取；其0.9.0源码把窗口大小上限默认设为100MB（1024×1024×100字节），拒绝声明更大窗口的帧。这个上限约束的是内存分配，而不是解压结果的总大小，因此输出大小的限制仍需调用方另行设置。

3-2) 整数溢出与堆破坏

压缩格式要处理长度、偏移等字段。在C中不加校验地对这些值做乘法或加法会引发整数溢出，进而以错误的大小分配堆缓冲区，导致堆破坏。这是压缩编解码器中反复被报告的典型模式。

3-3) XZ Utils后门事件（2024年）

2024年发现的XZ Utils（liblzma）后门事件，令人震惊地表明压缩库可能成为供应链攻击的目标。这与内存安全是不同层面的问题（供应链与信任），但它让所有人记住了一点：压缩库深嵌在系统之中，一旦被攻破，影响范围极广。

结论是：压缩编解码器不属于「能用就别动」的范畴，而是最应优先确保内存安全的安全核心组件。Rust重写正是这一认识的自然结果。

4. Rust重写的五大好处

以下是用Rust重写压缩库的五个实际好处。

4-1) 内存安全

这是最大的好处。在安全的Rust代码中，编译器会阻止缓冲区溢出、use-after-free与double free。但这一好处并不会因为「用Rust写」就自动获得。截至2026-09-29，libzstd-rs-sys的README自己写道，编码器「大部分仍是c2rust的原始转换，因此充满unsafe代码」。清除了多少unsafe，就决定了实际能获得多少安全性。

4-2) 安全的并发

Rust的所有权模型在编译期防止数据竞争。压缩天然适合按块并行，在Rust中借助rayon之类的库，很容易实现安全的多线程压缩。

4-3) 易于集成

Rust crate只需cargo一行即可加入依赖。Trifecta的发布文章指出，现有的zstd crate要从源码编译C代码，因此需要C工具链；纯Rust实现则免去这一要求，在Windows和WebAssembly等环境中更方便。

4-4) 可维护性

Rust的强类型系统与模式匹配，让压缩格式解析器这类状态复杂的代码更安全、更易读。编译器能检查的范围更广，重构的负担随之减轻。

4-5) 信任

以上四点汇合起来，最终形成信任。支撑「这个库即使收到恶意输入也不会发生内存破坏」这一主张的证据越多，安全敏感基础设施的采用决策就越快。libzstd-rs-sys在参考实现测试套件之外还使用模糊测试和Miri，也是在积累这种信任。

6. Zstandard为何流行 - 速度与压缩率的平衡

下面整理zstd在短时间内成为事实标准的原因。

6-1) 平衡感

如第5节表格所示，即便只比较最快设置，zstd -1的压缩率也高于zlib -1（2.896对2.743），压缩快约5倍、解压快约4倍，压缩率还远高于lz4。多数工作负载需要「压缩率和速度都还不错」，zstd恰好占据这个位置。

6-2) 级别调优的自由

一个级别参数就能用同一个工具覆盖从实时（级别1至3或负级别）到归档（级别19至22）的全部需求。运行中只改级别就能调整速度与体积的取舍，而解压速度几乎不受级别影响，这是最实用的优势。

6-3) 字典训练

在大量压缩小消息的环境（如微服务之间的JSON消息、IoT传感器数据）中，字典训练的效果最明显。ruzstd README中的测量显示，github-users样本（7,484,607字节；据zstd README说明约1万条、每条约1KB的记录）不用字典时压缩到原始大小的34.99%，使用官方实现生成的字典后再缩小到该结果的16.16%。zstd README说明，字典越针对某一类数据效果越好，收益主要出现在最初的几KB。

6-4) 生态采用

Linux内核（initramfs与模块压缩）、ZFS与btrfs文件系统、RocksDB与Parquet、Arch与Fedora包管理器以及众多容器镜像仓库，都把zstd作为默认或可选方案。采用带动更多采用的良性循环已经形成。

7. 在Rust生态中的应用

截至2026-09-29，在Rust中使用zstd有三条路：对C参考实现的绑定、从零编写的纯Rust实现，以及把C代码转成Rust再逐步清理的实现。

7-1) 发布的实质 - libzstd-rs-sys

Trifecta Tech Foundation的libzstd-rs-sys采用先用c2rust转换参考实现、再进行清理的方式。发布时（2026-06-01）的版本是v0.0.1-prerelease.2：解压（decompression）与字典生成器已完成清理，压缩部分的清理工作大多尚未进行。解压工作由Chainguard、Astral与NLnet Foundation资助，字典生成器由Sovereign Tech Agency资助，压缩部分仍在寻找资金。截至2026-09-29，README对现状的描述是：解码器经过大量清理、大部分已是安全代码；字典生成器在调用编码器处仍残留unsafe；编码器可以工作，但大部分仍是c2rust的原始转换。解码器处于「可以实验性使用，但尚未经过实战检验」的阶段。

它的用法也与普通crate不同。README给出的主要用法是构建成静态库链接进C项目（cargo build --features=export-symbols -p libzstd-rs-sys --release --lib），而接入zstd crate（zstd-rs）以便在Rust中方便使用，则是今后的目标。发布文章提到他们有一个使用libzstd-rs-sys的自有分支，但2026-09-04发布的zstd 0.14.0的功能开关列表中，并没有选择它作为后端的选项。截至2026-09-29，GitHub发布与crates.io最新版本仍是0.0.1-prerelease.2，仓库当天仍有变更推送，处于活跃状态，许可证为BSD-3-Clause。

注意名称混淆 - 名为「zstd-rs」的仓库有两个。gyscos/zstd-rs是C绑定crate zstd的仓库，KillingSpark/zstd-rs是纯Rust crate ruzstd的仓库。这次发布的Rust实现是与二者都不同的第三个项目（libzstd-rs-sys）。cargo add zstd装上的是C绑定，而不是Rust重写版。

7-2) 添加cargo依赖

使用最广的zstd crate是对C参考实现的绑定，截至2026-09-29最新为0.14.0（2026-09-04）；同日发布的zstd-sys 2.1.0+zstd.1.5.7在版本名中标明了C库版本1.5.7。按crates.io元数据，许可证字段从0.13.3的MIT变为0.14.0的BSD-3-Clause。纯Rust实现ruzstd最新为0.9.0（2026-07-26，MIT，最低Rust 1.87）。据其README，解压已实现完整标准；压缩可以使用，但速度、压缩率和可配置性尚不及原版。0.9.0源码中已实现的压缩级别只有Uncompressed与Fastest（约相当于级别1），Default、Better、Best均标注为「UNIMPLEMENTED」。

[dependencies]
# C绑定（最成熟的选择，截至2026-09-29为0.14.0）
zstd = "0.14"

# 或纯Rust实现（解压完整，压缩支持到Fastest级别）
# ruzstd = "0.9"

7-3) 基本的压缩与解压代码

下面的代码与zstd 0.14.0源码中encode_all(source, level)和Decoder::new(reader)的签名一致。

use std::io::Read;

fn main() -> std::io::Result<()> {
    let data = b"Hello, Zstandard in Rust! ".repeat(1000);

    // 压缩（级别3 = 均衡，19+ = 归档）
    let compressed = zstd::encode_all(&data[..], 3)?;
    println!("原始 {} bytes -> 压缩后 {} bytes", data.len(), compressed.len());

    // 解压
    let mut decompressed = Vec::new();
    zstd::Decoder::new(&compressed[..])?.read_to_end(&mut decompressed)?;
    assert_eq!(data, decompressed);
    Ok(())
}

用纯Rust的ruzstd 0.9.0完成同样的事，写法如下。函数名compress_to_vec与StreamingDecoder直接取自其README与源码。

use ruzstd::decoding::StreamingDecoder;
use ruzstd::encoding::{compress_to_vec, CompressionLevel};
use ruzstd::io::Read;

fn main() {
    let data = b"Hello, pure-Rust zstd! ".repeat(1000);

    // 压缩：0.9.0中已实现的级别只有Uncompressed与Fastest
    let compressed = compress_to_vec(&data[..], CompressionLevel::Fastest);

    // 解压
    let mut decoder = StreamingDecoder::new(&compressed[..]).unwrap();
    let mut out = Vec::new();
    decoder.read_to_end(&mut out).unwrap();
    assert_eq!(data, out);
}

7-4) 在系统编程中的位置

用Rust编写的存储引擎、日志采集器、网络代理常用zstd作为压缩方式。纯Rust解码器一旦成熟，就能在没有FFI边界（C绑定）的情况下让整条解压路径保持内存安全，这是最大的吸引力。

8. 性能 - Rust与C实现的取舍

最常见的问题是「Rust重写版会不会比C慢」。答案很大程度上取决于实现方式。

8-1) 理论上限相同

Rust通过LLVM后端生成与C/C++同级的原生代码。没有垃圾回收、没有运行时开销，因此理论性能上限与C相同。

8-2) 实际差距取决于实现方式

C参考实现经过多年极致优化。转换并清理这份代码的libzstd-rs-sys在发布文章中表示，默认设置下解压性能比C慢几个百分点，启用实验性功能开关unsafe-performance-experimental后可与C持平；正如名字所示，这是使用unsafe的实验功能。相比之下，从零编写的ruzstd据其README，在解压enwik9.zst时比C慢约3.5倍，在较难压缩的数据（如Ubuntu安装iso）上慢约1.4倍（用time工具测量）。差距来自投入优化的时间与设计方式，而非语言本身。

8-3) 缩小差距的手段

Rust同样可以通过core::arch的intrinsics使用SIMD，安全的并行化也更容易获得多核收益。libzstd-rs-sys在公开基准页面（trifectatechfoundation.github.io/libzstd-rs-sys-bench）上跟踪性能，可以直接查看差距的变化。

注意 - 以上数据由各项目在各自条件下测得，会随工作负载、级别与数据大幅变化。不要把单一基准数字当作绝对值，请用实际数据亲自测量。

结论是：如果只是几个百分点的性能取舍，「即便遇到恶意输入也不会发生内存破坏」的安全价值足以抵消。但如果实现慢了数倍，就需要按工作负载逐一评估这笔交换是否成立。

9. 五个实战应用场景

以下是采用zstd合理的五个场景。

9-1) 日志采集与存储

日志量大、重复模式强，压缩率表现很好。zstd压缩率高，能降低存储成本；解压快，日志检索与分析时延迟小。Elasticsearch、Loki等工具都支持zstd。

9-2) 备份与归档

长期保存的备份，压缩率就是成本。zstd的高级别（19至22）以压缩速度换取更高压缩率，而解压速度几乎与级别无关。恢复时间短在归档场景中尤为重要。

9-3) 网络传输

在API响应、消息队列与流式传输中，低级别（1至3）的zstd能在保持实时性的同时节省带宽。结合字典训练，小型JSON消息的压缩率会明显提升。

9-4) 存储与数据库

RocksDB、Parquet、ClickHouse、ZFS、btrfs都把zstd作为默认或推荐压缩。在磁盘I/O成为瓶颈的环境中，压缩实际上就是性能提升手段 - 因为需要读写的字节变少了。

9-5) 容器镜像与软件包

容器镜像仓库和包管理器（Arch、Fedora等）用zstd同时缩短传输时间、减少存储空间。镜像拉取更快，整条部署流水线都更轻快。

10. 在实际开发现场的落地

从开发现场的视角，整理zstd与Rust重写的意义。

10-1) 成本节省效果

各大云的存储与传输成本都不容忽视。把日志、备份、数据库压缩从gzip换成zstd，可以减少存储用量与传输量，从而可能降低账单。节省幅度因数据而异，请先用实际数据测量。

10-2) 应对安全合规

金融与公共部门的安全要求很强。「解析不可信输入也不会破坏内存」的依据，对于安全审查与漏洞排查负担沉重的现场，是颇具说服力的采用理由。不过审查材料中应同时写明所用实现的unsafe清理状态与发布阶段（例如截至2026-09-29，libzstd-rs-sys仍是预发布版），以免夸大。

10-3) 渐进式引入策略

稳妥的做法是不要一次全换，而是从新的日志流水线或新的备份任务开始用zstd，渐进引入。出于兼容性保留既有gzip资产，但把zstd设为新建部分的默认，就能在控制风险的同时逐步累积收益。

11. 结论 + 三条可立即采用的建议

用一句话概括用Rust实现的Zstandard：「在均衡出色的标准压缩zstd之上，逐步加入内存安全这一安全价值的、仍在进行中的演进」。以下是可以马上采用的三种做法。

11-1) 立即采用1：新压缩一律以zstd为默认

新建的日志、备份、传输路径，没有特殊理由就把zstd级别3（均衡）设为默认。即便只比较README基准表中的最快设置，它也比zlib更快、压缩得更好。

11-2) 立即采用2：以测量决定各数据的最优级别

实时路径从级别1至3（或负级别）开始，归档从级别19至22开始，再用实际数据测量压缩率与速度，找到最佳点。如果要压缩大量重复的小消息，一定要试试字典训练。

11-3) 立即采用3：Rust项目优先考虑内存安全解码器

如果在Rust中解压不可信输入，请优先评估实现了完整标准的纯Rust解码器ruzstd，以缩小FFI边界。若解压速度很关键，可以使用C绑定（zstd crate），但要把接口抽象出来，这样等libzstd-rs-sys正式发布或接入zstd crate时就容易迁移。压缩方面，截至2026-09-29纯Rust的选择仍然有限（ruzstd只到Fastest级别），C绑定是现实的选择。

最后要强调的是：压缩既是「看不见的降本杠杆」，也是「看不见的安全攻击面」。zstd最均衡地提供了降本杠杆，而Rust重写正在逐步缩小这一攻击面。如果你在2026年设计新系统，这个组合值得认真评估一次。

# 在Rust中选择zstd - 实现选择表与引入检查清单

基准日: 2026-09-29。版本与状态依据各项目的仓库、crates.io与README。

---

## 1. Rust可用的三类zstd实现

| crate | 仓库 | 方式 | 版本（基准日） | 解压 | 压缩 | 许可证 |
|---|---|---|---|---|---|---|
| `zstd` | gyscos/zstd-rs | 对C参考实现的绑定 | 0.14.0（2026-09-04） | 完整 | 级别1至22 | BSD-3-Clause（0.13.3及以前为MIT） |
| `ruzstd` | KillingSpark/zstd-rs | 从零编写的纯Rust | 0.9.0（2026-07-26） | 实现完整标准 | 仅 `Uncompressed` 与 `Fastest` | MIT |
| `libzstd-rs-sys` | trifectatechfoundation/libzstd-rs-sys | 用c2rust转换C代码后清理 | 0.0.1-prerelease.2（2026-06-01） | 大部分安全，处于实验性使用阶段 | 可用但大部分是unsafe | BSD-3-Clause |

- 名为「zstd-rs」的仓库有两个。`cargo add zstd` 装上的是C绑定。
- `libzstd-rs-sys` 的主要用法是构建成静态库链接进C项目。`zstd` 0.14.0 没有选择它作为后端的功能开关。

---

## 2. 该用哪个 - 决策表

| 情形 | 建议选择 | 理由 |
|---|---|---|
| 要解压不可信输入，希望缩小FFI边界 | `ruzstd` | 解压实现完整标准，纯Rust |
| 解压速度很关键 | `zstd` | 据README，ruzstd解压比C慢约1.4至3.5倍 |
| 需要以级别3以上压缩 | `zstd` | ruzstd尚未实现 `Default`、`Better`、`Best` |
| 想在C项目中试着用Rust实现替换C库 | `libzstd-rs-sys`（实验） | 主要用法是构建静态库，仍是预发布版 |
| 以后可能更换实现 | 无论用哪个都抽象出接口 | 为libzstd-rs-sys正式发布或接入zstd crate做准备 |

---

## 3. 引入前检查清单

- [ ] 所用crate的仓库URL是否指向预期的项目（查看crates.io上的repository字段）
- [ ] 基准日之后是否重新确认过版本（`zstd` 0.14、`ruzstd` 0.9）
- [ ] 是否为解压结果大小设置了上限（内存安全语言也挡不住解压炸弹）
- [ ] 若使用ruzstd，是否了解其默认100MB的窗口大小上限（调高会重新带来大块分配风险）
- [ ] 是否用实际数据测量后确定级别（实时用1至3或负级别，归档用19至22）
- [ ] 若小消息很多，是否试过按数据类型训练的字典
- [ ] 安全审查材料中是否写明了实现的unsafe清理状态与发布阶段
- [ ] 引用性能数据时，是否同时写明测量条件（项目、数据、设置）
