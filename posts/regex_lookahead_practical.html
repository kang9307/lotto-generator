룩어헤드는 자리만 본다 - 너비 0으로 푸는 정규식 문제

매치에 포함되지 않기 때문에 가능한 것들 - 조건 겹치기, 경계만 남기는 치환, 겹치는 매치, 그리고 한글에서 먼저 무너지는 자리

2026-08-11 개발/인프라

서론: 조건은 걸어야 하는데, 결과에는 넣고 싶지 않다

로그에서 ERROR가 든 줄만 뽑되 timeout이 든 줄은 빼야 한다. grep을 파이프로 잇는다. 그다음엔 그 줄에서 host= 뒤의 값만 필요하다. 파이프를 또 잇고 sed로 앞부분을 잘라 낸다. 파이프가 네 개쯤 되면 그 명령은 다시 읽어도 무슨 일을 하는지 알 수 없게 된다.

치환에서는 문제가 더 노골적이다. password=hunter2를 password=***로 바꿔야 한다. password=까지 같이 매치시키지 않으면 hunter2만 골라낼 방법이 없는데, 매치시키면 치환할 때 그것까지 사라진다. 그래서 캡처 그룹으로 붙잡아 $1로 도로 붙인다. 키가 하나일 때는 견딜 만하고, 셋이 되면 번호를 세기 시작한다.

두 상황의 공통점이 있다. 조건으로는 필요하지만 결과로는 필요 없는 부분이 있다는 것이다. 룩어라운드는 정확히 이 지점을 위해 있다. 조건을 검사하되 매치에 포함하지 않고, 다음 매치가 시작될 위치도 옮기지 않는다. 이 성질을 너비 0(zero-width)이라고 부른다.

대부분의 설명은 여기서 기호 네 개를 소개하고 끝난다. 그런데 실무에서 값어치가 나오는 부분은 기호가 아니라 너비가 0이기 때문에 파생되는 결과들이다. 조건을 몇 개든 같은 자리에 겹쳐 쌓을 수 있고, 경계를 건드리지 않고 값만 바꿀 수 있고, 서로 겹치는 매치를 셀 수 있다. 이 글은 그 쪽에 지면을 쓴다.

실행 환경. 아래 출력은 Windows 10 Pro 위의 Node.js v22.16.0, Python 3.13.3과 3.11.9, Perl 5.38.2, GNU grep 3.0 기준이다. 한글이 든 패턴은 셸 인자로 넘기면 이스케이프가 벗겨지므로 전부 스크립트 파일로 저장해 실행한 결과다.

범위. 엔진마다 문법이 갈리는 문제 전반은 어디서나 동작하는 정규표현식에서 다룬다. 여기서는 룩비하인드 한 지점만 짧게 짚는다. 한글 정규식의 함정 자체는 한글 정규식 함정이 본진이고, 이 글은 룩어라운드라는 도구가 한국어에서 어디서 헛도는지만 본다.

1. 너비 0 - 검사는 하되 먹지 않는다

말로 하면 추상적이니 길이를 재 보면 된다.

A1 match = "foo" | length = 3 | index = 0
A2 lastIndex after exec(g): 3
A3 replace = Xbar
A4 without lookahead = X
A5 consuming = "foobar"

패턴은 /foo(?=bar)/, 입력은 foobar다. bar가 뒤따르는지 확실히 검사했는데도 매치 문자열은 foo 세 글자다. 더 중요한 건 lastIndex다. 소비했다면 6이어야 하는데 3이다. 커서가 bar 앞에 멈춰 있다는 뜻이고, 다음 매치는 거기서부터 다시 시작한다.

그래서 치환 결과가 Xbar가 된다(A3). 조건으로 쓴 bar는 원본에 그대로 남는다. 소비하는 패턴 /foobar/로 같은 치환을 하면 X만 남는다(A4). 조건에 쓴 부분을 결과에서 되살리려고 캡처 그룹을 쓸 필요가 없다는 것, 이것이 첫 번째 실용적 가치다.

너비가 0이라는 말은 문자 그대로다. 룩어라운드만으로 이루어진 패턴은 빈 문자열에 매치된다.

C1 split by zero-width = [ 'one', 'Two', 'Three' ]
C2 empty match array = [ '' ]
C3 empty match str  = ""

'abc'.match(/(?=b)/)의 매치 문자열은 길이 0의 빈 문자열이다. 위치 정보만 있고 내용이 없다. 'oneTwoThree'.split(/(?=[A-Z])/)가 글자를 하나도 잃지 않고 셋으로 갈라지는 것도 같은 이유다. 구분자를 소비하지 않으니 대문자가 그대로 남는다.

2. 네 가지 룩어라운드와 그것이 서는 자리

기호는 넷이고, 축도 둘뿐이다. 어느 쪽을 보는가(앞/뒤)와 있어야 하는가 없어야 하는가(긍정/부정)의 조합이다.

기호이름보는 방향성공 조건
(?=...)긍정 전방탐색현재 위치의 오른쪽오른쪽이 ...로 시작한다
(?!...)부정 전방탐색현재 위치의 오른쪽오른쪽이 ...로 시작하지 않는다
(?<=...)긍정 후방탐색현재 위치의 왼쪽왼쪽이 ...로 끝난다
(?<!...)부정 후방탐색현재 위치의 왼쪽왼쪽이 ...로 끝나지 않는다

같은 문자열에 넷을 걸어 보면 각자 무엇을 골라내는지가 선명해진다.

입력: price: 100USD, 200EUR, 300USD

B1 /\d+(?=USD)/g       = [ '100', '300' ]
B2 /\d+(?!\d)(?!USD)/g = [ '200' ]
B3 /(?<=price: )\d+/g   = [ '100' ]

입력: a1 b2 c3
B4 /(?<![ab])\d/g      = [ '3' ]

2.1 부정 룩어헤드가 백트래킹으로 뚫리는 자리

B2에 (?!\d)가 왜 하나 더 붙어 있는지가 이 절의 핵심이다. 그것 없이 /\d+(?!USD)/g만 쓰면 이렇게 된다.

입력: 100USD 200EUR

K1 /\d+(?!USD)/g       = [ '10', '200' ]
K2 /\d+(?!\d)(?!USD)/g = [ '200' ]
K4 첫 매치 = "10"

USD가 붙은 100을 걸러 내려던 패턴이 10을 돌려준다. 엔진은 먼저 \d+로 100을 잡고 (?!USD)를 검사했다가 실패하자, 포기하지 않고 소비 길이를 줄여 가며 조건을 피할 방법을 찾는다. 10까지 줄이면 그 오른쪽은 0USD이고, 이것은 USD로 시작하지 않으므로 부정 조건이 통과해 버린다.

부정 룩어헤드는 바로 그 위치에 대한 판정일 뿐, 「이 숫자 덩어리 전체 뒤에 USD가 없다」는 뜻이 아니다. 그래서 오른쪽 끝을 (?!\d)로 못 박아 \d+가 짧아질 여지를 없애야 한다. 부정 조건을 걸 때는 매치의 경계가 고정돼 있는지를 먼저 확인하라. 이것이 룩어라운드에서 가장 자주 나는 논리 오류다.

2.2 캡처는 긍정 쪽에서만 살아남는다

L1 /(?!(\d+))X/ 의 그룹 1 = undefined
L2 /(?=(\d+))\d+/ 의 그룹 1 = 123 | 전체 매치 = 123

부정 룩어헤드 안의 그룹은 값이 남지 않는다. 부정 조건은 내부 매치가 실패해야 성공하므로, 성공한 시점에는 그룹에 채울 것이 없다. 반대로 긍정 룩어헤드 안의 그룹은 정상적으로 캡처된다. 5절의 겹치는 매치가 이 성질 위에 서 있다.

3. 「A는 있고 B는 없는 줄」 - 조건을 같은 자리에 쌓기

서론의 로그 문제다. 룩어라운드는 위치를 옮기지 않으므로 여러 개를 이어 붙이면 전부 같은 지점에서 판정된다. 줄 첫머리에 조건을 몇 개든 겹쳐 쌓을 수 있다는 뜻이다.

$ grep -P '^(?=.*ERROR)(?!.*timeout)' app.log
2026-08-11 10:00:01 ERROR db connect failed host=db01 retry=1
2026-08-11 10:00:04 ERROR auth rejected user=svc_batch
2026-08-11 10:00:06 ERROR db connect failed host=db02 retry=2

ERROR upstream timeout 줄은 두 번째 조건에서 떨어졌고, INFO timeout tuning applied 줄은 첫 번째 조건에서 떨어졌다. 조건을 하나 더 얹는 것도 그냥 하나 더 쓰면 된다.

D2 /^(?=.*ERROR)(?!.*timeout)(?=.*(db|auth))/ 매치 = 2건
D3 순서를 바꿔도 같은 결과 = true
D4 소비형 /ERROR.*db/ : 'db ERROR' → false, 'ERROR db' → true

D3이 이 절의 요점이다. 조건들 사이에 순서 의존이 없다. 룩어헤드는 커서를 움직이지 않으니 첫 번째를 검사하고 나서도 커서는 여전히 줄 첫머리에 있다. 그래서 순서를 바꿔 써도 결과가 같고, 조건을 나중에 추가할 때 어디에 끼워 넣을지 고민할 필요가 없다.

소비하는 패턴으로 같은 일을 하려면 이 자유가 사라진다(D4). /ERROR.*db/는 문서에 ERROR가 db보다 먼저 나올 때만 맞는다. 로그 포맷이 바뀌어 필드 순서가 뒤집히면 조용히 아무것도 잡지 못한다.

3.1 필터와 추출을 한 번에

조건 조합과 \K를 붙이면 파이프 네 개짜리 명령이 하나로 접힌다.

$ grep -oP '^(?=.*ERROR)(?!.*timeout).*?host=\K\S+' app.log
db01
db02

$ grep -oP '(?<=retry=)\d+' app.log
1
2

$ grep -oP '\w+(?==)' app.log | sort -u
host pool retry user

마지막 것은 등호 앞의 키 이름만 뽑는다. (?==)는 눈에 설지만 「등호가 뒤따르는 자리」라는 뜻이고, 등호 자체는 소비하지 않으므로 출력에 나오지 않는다.

4. 치환에서 경계만 잡는다

값은 바꾸되 키는 남겨야 하는 치환이다. 후방탐색으로 왼쪽 경계를 「검사만」 하면 캡처 그룹이 필요 없다.

입력: user=admin&password=hunter2&host=db01&token=abc123def

E1 /(?<=password=)[^&]+/g  → '***'
   user=admin&password=***&host=db01&token=abc123def
E2 /(password=)[^&]+/g     → '$1***'
   user=admin&password=***&host=db01&token=abc123def
E3 /(?<=(?:password|token)=)[^&]+/g → '***'
   user=admin&password=***&host=db01&token=***

E1과 E2는 결과가 같다. 캡처 그룹으로도 되는 일이라는 뜻이고, 그러니 여기서만 보면 취향 문제다. 차이는 E3에서 벌어진다. 키가 여러 개로 늘어도 치환문은 여전히 *** 한 덩어리다. 캡처 방식이라면 그룹 번호를 세어 가며 $1을 관리해야 하고, 나중에 그룹을 하나 더 넣는 순간 번호가 밀려 조용히 깨진다.

4.1 소비를 아예 하지 않는 치환

더 극단적인 쪽은 매치 문자열이 빈 문자열인 치환이다. 아무것도 지우지 않고 자리에 끼워 넣기만 한다.

F1 '1234567'      .replace(/\B(?=(\d{3})+(?!\d))/g, ',') = 1,234,567
F2 '999'          .replace(같은 패턴, ',')              = 999
F3 '1000'         .replace(같은 패턴, ',')              = 1,000
F4 '123456789012' .replace(같은 패턴, ',')              = 123,456,789,012

V1 'oneTwoThreeID'  .replace(/(?<=[a-z])(?=[A-Z])/g, '_') = one_two_three_id
V2 'HTTPServerError'.replace(/(?<=[A-Z])(?=[A-Z][a-z])/g, '_') = HTTP_ServerError

천단위 구분자 패턴을 뜯어보면 조건이 셋이다. 단어 경계가 아닐 것(\B, 맨 앞에 콤마가 붙는 것을 막는다), 오른쪽에 세 자리 묶음이 이어질 것, 그 묶음 뒤에 숫자가 더 없을 것. 셋 다 너비 0이라 매치 문자열은 빈 문자열이고, 치환은 순수한 삽입이 된다.

V2는 약어 처리다. HTTPServerError를 대문자마다 자르면 H_T_T_P_...가 되어 버린다. 「대문자 뒤이면서, 대문자 다음에 소문자가 오는 자리」로 조건을 좁히면 약어 덩어리는 붙어 있고 단어 경계에서만 갈라진다. 왼쪽과 오른쪽을 동시에 보는 이런 조건은 소비형 패턴으로는 표현하기 어렵다.

4.2 이미 처리된 곳은 건너뛰기

입력: see http://a.example and <a href="http://b.example">b</a>
패턴: /(?<!href=")http:\/\/\S+?(?=[\s<])/g → '[LINK]'
결과: see [LINK] and <a href="http://b.example">b</a>

맨 URL만 링크로 바꾸고 이미 태그 안에 있는 것은 두는 흔한 요구다. 부정 후방탐색으로 href=" 뒤가 아닐 것을 걸고, 전방탐색으로 오른쪽 경계를 잡되 그 문자는 소비하지 않는다. 소비했다면 결과에서 공백이나 꺾쇠가 사라졌을 것이다.

4.3 마스킹

$ echo '카드 4111111111111111 로 결제' | perl -pe 's/\d(?=\d{4})/*/g'
카드 ************1111 로 결제

「뒤에 숫자가 네 개 이상 남아 있는 숫자」만 별표로 바꾼다. 자릿수를 세거나 길이를 계산하지 않는다. 조건이 위치로 표현돼 있어서 카드번호 길이가 열여섯이든 열넷이든 같은 패턴이 그대로 동작한다.

5. 겹치는 매치 - 너비 0이라서 되는 것

정규식 엔진은 매치를 찾으면 그 끝으로 커서를 옮긴다. 그래서 겹치는 매치를 찾지 못한다.

H1 'AAAA'.match(/AA/g)                    = [ 'AA', 'AA' ]
H2 [...'AAAA'.matchAll(/(?=(AA))/g)]      = [ 'AA', 'AA', 'AA' ]
H3 그 위치                                 = [ 0, 1, 2 ]

H4 'ABABABA'.match(/ABA/g)                = [ 'ABA', 'ABA' ]
H5 [...'ABABABA'.matchAll(/(?=(ABA))/g)]  = 위치 [ 0, 2, 4 ]

AAAA에 들어 있는 AA는 위치 0, 1, 2에 셋이다. 그런데 소비형 패턴은 둘만 센다. 0에서 찾고 커서가 2로 가면서 위치 1을 건너뛰기 때문이다.

(?=(AA))는 이 문제를 우회한다. 바깥 매치는 너비 0이라 커서가 한 칸씩만 전진하고, 실제로 찾고 싶은 문자열은 룩어헤드 안쪽 캡처 그룹에서 꺼낸다. 2.2절에서 본 「긍정 쪽 캡처는 살아남는다」가 여기서 쓰인다.

5.1 너비 0 매치의 무한 루프

이 기법에는 함정이 하나 붙어 있다. exec를 직접 돌리면 커서가 전진하지 않아 멈추지 않는다.

const r = /(?=a)/g;
let m;
while ((m = r.exec('aaa')) !== null) {
  // ...
  if (m.index === r.lastIndex) r.lastIndex++;   // 이 줄이 없으면 끝나지 않는다
}
M1 결과 = 3
M2 [...'aaa'.matchAll(/(?=a)/g)].length = 3

매치 길이가 0이면 lastIndex가 그대로라 같은 자리를 영원히 다시 찾는다. matchAll과 replace(/.../g)는 내부에서 이 처리를 해 주므로 안전하다. 너비 0 패턴에 exec 루프를 직접 쓰지 말고 matchAll을 써라. 이 함정은 다른 언어에도 그대로 있어서, 펄에서도 pos()를 손으로 밀어 줘야 한다.

$ echo 'AAAA' | grep -oP '(?=(AA))'
(출력 없음 - 매치가 빈 문자열이라 -o 가 찍을 것이 없다)

$ echo 'AAAA' | perl -ne 'while (/(?=(AA))/g) { print "$1 at ", pos(), "\n"; pos() = pos() + 1 }'
AA at 0
AA at 1
AA at 2

6. 단어 경계를 직접 정의하기

\b도 너비 0 조건이다. 다만 단어 문자의 정의가 고정돼 있어서, 그 정의가 내 데이터와 안 맞으면 손댈 방법이 없다. 룩어라운드는 그 정의를 직접 쓰게 해 준다.

패턴매치 수잡히는 것
/cat\b/g3cat, cat-x의 앞, concat의 뒤
/cat(?!s)/g4위 셋 + catx의 앞
/cat(?![a-z])/g3cat, cat-x, concat
/(?<![a-z])cat(?![a-z])/g2cat, cat-x만

입력은 cat cats catx cat-x concat이다. \b는 하이픈을 경계로 보기 때문에 cat-x를 잡고, concat의 꼬리도 잡는다. 그것이 원하는 동작이 아니라면 양쪽을 부정 룩어라운드로 직접 막는 것이 유일한 방법이다.

한글에서는 이 차이가 취향이 아니라 동작 여부를 가른다.

입력: 고양이 고양이들 왕고양이

T6 /\b고양이\b/g                    = null
T7 /(?<![가-힣])고양이(?![가-힣])/g = [ '고양이' ]

\b는 한 글자도 잡지 못한다. \b의 단어 문자 정의가 [A-Za-z0-9_]라서 한글은 애초에 단어 문자가 아니고, 공백과 고 사이에는 양쪽 다 비단어 문자라 경계가 성립하지 않는다. 예외도 경고도 없이 null이 나온다. 한국어 텍스트에서 낱말 단위 검색이 필요하면 \b를 버리고 룩어라운드로 경계를 직접 정의해야 한다.

7. 비밀번호 규칙 - 되는 것과 되지 않는 것

룩어헤드가 가장 널리 복사·붙여넣기 되는 용도다. 「문자 종류가 섞여 있는가」를 조건 여러 개로 쌓는다.

/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9]).{12,}$/

PASS | Passw0rd!1234
FAIL | passw0rd!1234     (대문자 없음)
FAIL | PASSW0RD!1234     (소문자 없음)
PASS | Password!1234
PASS | Pw0!aaaaaaaaaaaa

목적한 대로 동작한다. 그런데 실제로 쓸 때 걸리는 한계가 셋 있고, 셋 다 룩어헤드의 잘못이 아니라 이 도구로 하려던 일이 원래 정규식의 일이 아니라서 생긴다.

7.1 어디서 떨어졌는지 알려 주지 못한다

결과가 참 아니면 거짓 하나다. 사용자에게 「대문자와 특수문자가 빠졌고 네 자 더 필요합니다」라고 말해 줄 정보가 없다. 조건을 쪼개면 그 정보가 생긴다.

규칙을 조각으로 나눠 각각 판정:
I7 'passw0rd' 미충족 = 대문자, 특수문자, 12자 이상

정규식 하나에 조건을 다 쌓는 것은 검사 결과를 버리는 설계다. 판정만 필요한 서버 측 최종 확인이라면 한 줄이 낫고, 사용자에게 안내해야 하는 화면이라면 쪼개는 쪽이 낫다. 두 곳 모두에서 쓸 거라면 조각 배열 하나를 진실의 원천으로 두고 필요할 때 합치는 편이 어긋나지 않는다.

7.2 길이를 세는 단위가 사람과 다르다

J1 'Passw0rdAB😀'  사람이 센 글자 = 11 | .{12,} 가 센 것 = 12 | 통과 = true
J2 'Passw0rdABc!'  사람이 센 글자 = 12 | .{12,} 가 센 것 = 12 | 통과 = true
J3 이모지가 특수문자 조건을 충족시킨다 = true
J5 같은 J1 입력에 u 플래그를 붙이면      = false

J1이 문제다. 사용자는 열한 글자를 입력했는데 「12자 이상」 규칙을 통과했다. 자바스크립트의 .가 UTF-16 코드 단위를 세기 때문에 이모지 하나가 둘로 계산된 것이다. 덤으로 이모지의 반쪽이 [^A-Za-z0-9]에 걸려 특수문자 조건까지 채워 준다. u 플래그를 붙이면 코드포인트 단위가 되어 정상으로 돌아온다(J5).

한글은 정규화 형식에 따라 갈린다.

K1 '비밀번호입니다'  NFC 길이 = 7 | NFD 길이 = 17
K2 /^.{12,}$/       NFC = false | NFD = true

화면에 똑같이 보이는 문자열이 어떤 형태로 들어왔느냐에 따라 같은 규칙을 통과하기도 하고 떨어지기도 한다. 입력 경계에서 normalize('NFC')를 한 번 걸어 두는 것이 대책이고, 이 문제의 전모는 한글 정규식 함정 쪽에 정리돼 있다.

7.3 규칙을 통과한다고 좋은 비밀번호가 아니다

I2 통과 = true  | Password1234!
I3 통과 = true  | Qwerty12345!
I4 통과 = false | correct horse battery staple   (28자)

가장 흔한 유출 목록 상위권이 통과하고, 28자짜리 문장은 떨어진다. 문자 구성 규칙은 엔트로피를 재는 도구가 아니라 형태를 재는 도구다. 룩어헤드로 아무리 정교하게 쌓아도 이 간극은 좁혀지지 않는다. 길이 하한을 올리고 유출 목록 대조를 붙이는 쪽이 실효가 크다. 통과시킬 형태를 먼저 정하는 사고방식 자체는 금지 목록은 항상 뒤늦다에서 다룬 허용 목록 논의와 같은 줄기다.

8. 후방탐색과 가변 길이 - 엔진이 갈리는 한 지점

룩어헤드는 어지간한 역추적 엔진이면 다 있다. 갈리는 것은 후방탐색의 길이가 고정이어야 하는가 하나다. 이유는 구현에 있다. 앞을 볼 때는 현재 위치에서 오른쪽으로 읽어 나가면 되지만, 뒤를 볼 때는 어디서부터 읽기 시작할지를 먼저 알아야 한다. 길이가 고정이면 그만큼 왼쪽으로 물러나면 되고, 가변이면 물러날 거리를 하나씩 시도해 봐야 한다.

엔진(확인 버전)룩어헤드고정 길이 후방탐색가변 길이 후방탐색근거
JavaScript (Node.js 22.16)OOO — 제한 없음실행

* 마지막 행의 가변 길이 지원 여부는 이 환경에서 실행해 확인하지 못했다. 11절에 모아 두었다.

오류 메시지를 직접 보면 각 엔진이 어디에 선을 긋는지가 분명해진다.

[Python 3.13.3]
(?<=price: )\d+     → ok
(?<=price:\s+)\d+   → error: look-behind requires fixed-width pattern
(?<=ab|abc)\d       → error: look-behind requires fixed-width pattern
(?<=a{1,3})\d       → error: look-behind requires fixed-width pattern

[Perl 5.38.2]
(?<=price: )\d+     → compiled
(?<=price:\s+)\d+   → ERROR: Lookbehind longer than 255 not implemented
(?<=ab|abcd)\d      → compiled
(?<=a{1,3})\d       → compiled
(?<=a{1,300})\d     → ERROR: Lookbehind longer than 255 not implemented

[Node.js 22.16]
(?<=price:\s+)\d+   → 'price:    100' 에서 100
(?<=ab|abc)\d       → 'xab7 yabc8' 에서 7, 8
(?<=a{1,3})\d       → 'aaa9' 에서 9

선이 세 군데에 다르게 그어져 있다. 파이썬은 길이가 다른 교대조차 거부한다. 펄과 PCRE는 유계이면 받아들이고 무한 수량자에서 멈춘다. 자바스크립트는 전부 받는다. 이식성을 생각한다면 후방탐색은 고정 길이로만 쓰는 것이 안전한 하한선이다.

8.1 가변 길이가 필요할 때의 대안

  • \K를 쓴다. PCRE와 펄에는 「여기까지는 매치에서 빼라」는 표시가 있다. password=\K[^&]+는 password=를 소비한 뒤 결과에서 버린다. 앞으로 읽어 나가므로 길이 제약이 없다.
  • 캡처 그룹으로 되돌린다. 어디서나 통하는 최소공배수다. (password=)[^&]+를 $1***로 치환하면 파이썬·POSIX sed·Go까지 전부 같은 결과가 나온다.
  • 두 단계로 나눈다. 넓게 잡아서 매치한 뒤 프로그램 쪽에서 잘라 낸다. 패턴이 짧아지고 읽기 쉬워지는 부수 효과가 있다.
  • 파이썬이라면 서드파티 regex 모듈이 가변 길이 후방탐색을 지원한다. 다만 표준 라이브러리가 아니므로 의존성이 하나 는다.
  • 후방탐색을 아예 쓰지 않는 설계도 있다. 로그나 설정처럼 내가 포맷을 통제하는 데이터라면 구분자를 유일하게 만들어 두는 것으로 끝난다. 패턴이 정교해질수록 그것은 대개 데이터가 모호하다는 신호이지 정규식 실력이 필요하다는 신호가 아니다.
$ perl -pe 's/password=\K[^&]+/***/'     → user=a&password=***&x=1
$ sed -E 's/(password=)[^ ]+/\1***/'    → user=a&password=***&x=1
  Python: re.sub(r'(password=)[^&]+', r'\1***', s) → user=a&password=***&x=1

8.2 POSIX ERE는 오류를 내지 않는다

표에서 가장 위험한 칸이다. 룩어라운드가 없는 것 자체는 문제가 아닌데, 없다고 말해 주지 않는다.

입력 파일: foobar / foobaz
의도: bar 가 뒤따르는 foo 만

$ grep -oE 'foo(?=bar)' input.txt
(출력 없음)
$ echo $?
1
$ grep -oP 'foo(?=bar)' input.txt
foo

# ERE 가 (?=bar) 를 무엇으로 읽었나
입력에 foo?=bar / foo=bar / foobar 를 넣고 같은 ERE 패턴을 돌리면
$ grep -oE 'foo(?=bar)' input2.txt
foo=bar

ERE에서 (?=bar)는 「등호로 시작하는 =bar가 있을 수도 없을 수도 있는 그룹」쯤으로 해석된다. 그래서 foo=bar라는 전혀 다른 문자열에 맞고, 원래 의도한 foobar에는 맞지 않으며, 종료 코드는 그냥 1이다. 스크립트에서 grep -E와 grep -P를 바꿔 쓰면 「매치가 없다」는 정상적인 결과처럼 보이는 침묵이 돌아온다. 룩어라운드를 쓸 거면 -P를 명시하고, 그 스크립트가 -P 없는 빌드에서 돌 가능성을 확인하라.

8.3 후방탐색은 오른쪽에서 왼쪽으로 맞춘다

R1 /(?<=(\d+))$/.exec('1234')[1]  = "1234"
R3 /(?<=(\d+))/ .exec('1234')[1]  = "1"

같은 룩비하인드인데 결과가 다르다. R3은 앵커가 없어서 가장 왼쪽의 성공 위치인 인덱스 1에서 매치되고, 거기서 왼쪽으로 읽으면 1 하나뿐이다. R1은 $ 때문에 끝에서만 성공하고, 거기서 왼쪽으로 탐욕적으로 읽어 1234 전부를 가져간다. MDN도 같은 성질을 설명하면서 /(?<=([ab]+)([bc]+))$/가 abc에서 a와 bc를 캡처한다는 예를 든다. 뒤쪽 그룹이 먼저 탐욕을 부린다는 뜻이다. 후방탐색 안에 그룹을 둘 이상 두면 탐욕성의 방향이 직관과 반대로 보인다.

9. 룩어헤드로 한국어 어미를 배제하려 할 때

「아니」를 찾되 「아니요」는 빼고 싶다. 자연스러운 시도는 /아니(?!요)/다.

HIT  이것은 사실이 아니다
miss 이것은 사실이 아닙니다      ← 의도하지 않은 누락
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요        ← 의도한 배제
miss 이것은 사실이 아님          ← 의도하지 않은 누락

배제하려던 「아니요」는 잘 빠졌다. 그런데 「아닙니다」와 「아님」도 함께 빠졌다. 여기서 룩어헤드를 고치기 시작하면 시간을 버린다. 룩어헤드는 아무 잘못이 없다. 앞의 아니가 애초에 매치되지 않아서 부정 조건은 검사될 기회조차 없었다.

N2 '아닙니다'.indexOf('아니') = -1
N3 '아님'.indexOf('아니')     = -1
N4 니 = U+B2C8  닙 = U+B2D9  님 = U+B2D8

한글 음절은 초성·중성·종성을 합성해 만든 하나의 코드포인트다. 종성이 붙으면 앞 글자가 다른 글자로 교체된다. 그래서 어간이 부분문자열로 남지 않는다. 원리는 한글 정규식 함정에 정리돼 있고, 여기서 볼 것은 이 성질이 룩어라운드 사용법에 미치는 영향이다.

순서가 뒤집힌다. 영어라면 어간을 잡아 두고 룩어헤드로 원하지 않는 활용형을 깎아 내면 된다. 한국어에서는 먼저 종성 자리를 열어 매치가 성립하게 만든 다음에야 룩어헤드가 의미를 갖는다.

/아[니닙님](?!요)/ 로 자리를 연 뒤:
HIT  이것은 사실이 아니다
HIT  이것은 사실이 아닙니다
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요
HIT  이것은 사실이 아님

이제 룩어헤드가 제 일을 한다. 배제 조건을 손보기 전에 포함 조건이 한 번이라도 맞은 적이 있는지부터 확인하라. 부정 룩어헤드의 실패는 결과가 줄어드는 모양으로 나타나는데, 매치 자체가 0건인 것도 똑같이 결과가 없는 모양이라 구분되지 않는다.

9.1 룩어라운드로 종성을 판정할 수는 없다

관형사형 어미 「ㄹ」이 붙은 자리를 찾고 싶다고 하자. [을ㄹ]로 열면 될 것 같다.

miss 할 수 있다
miss 갈 예정이다
HIT  먹을 만하다
miss 하는 중이다

네 개 중 하나만 잡힌다. 「먹을」은 「을」이 독립된 음절이라 맞았지만, 「할」과 「갈」의 ㄹ은 음절 안에 들어앉은 종성이라 별도의 문자가 아니다. 문자 클래스로도 룩어라운드로도 접근할 수 없다. 종성 판정은 문자 비교가 아니라 산술이다.

종성 인덱스 = (코드포인트 - 0xAC00) % 28

할 = 8 (ㄹ)   하 = 0 (없음)   갈 = 8 (ㄹ)

산술로 판정하면:
HIT  할 수 있다   (종성 = ㄹ)
HIT  갈 예정이다  (종성 = ㄹ)
HIT  먹을 만하다  (종성 = ㄹ)
miss 하는 중이다  (종성 = ㄴ)

정규식이 할 수 있는 일이 아니다. 한국어 형태 조건은 룩어라운드로 밀어 넣지 말고 코드로 빼라. 룩어라운드를 쓸 수 있는 자리는 음절이 통째로 경계 노릇을 하는 경우에 한정된다.

P1 '재고가 있음, 재고가 없음'.match(/(?<=재고가 )있음/g) = [ '있음' ]
P2 '재고가 있음, 재고가 없음'.match(/(?<!없)음/g)        = [ '음' ]

이 정도, 즉 음절 단위로 딱 떨어지는 조건이면 룩어라운드가 잘 맞는다. 고정 길이라 어느 엔진에서나 돌아간다는 장점도 있다.

10. 성능 - 무엇이 진짜 위험한가

「룩어헤드는 느리다」는 말이 자주 돌아다니는데, 측정해 보면 위험의 소재가 다른 데 있다. 50만 자 입력에 조건 수만 늘려 본 결과다.

입력 길이 500,004자

조건 1개  : 0.276 ms
조건 2개  : 0.422 ms
조건 4개  : 0.734 ms
한 번 훑기 : 5.291 ms   ← 같은 판정을 손으로 구현
길이 가드 : 0.00004 ms  ← 128자 넘으면 정규식을 돌리지 않음

조건을 넷으로 늘려도 하나일 때의 세 배를 넘지 않는다. 입력을 여러 번 훑는 것은 맞지만 훑는 횟수가 조건 수에 비례할 뿐이다. 더 눈에 띄는 것은 같은 판정을 문자 루프로 직접 짠 쪽이 일곱 배 느리다는 사실이다. 문자 클래스 스캔은 엔진 내부에서 최적화된 경로를 타므로, 「정규식이 느릴 것 같아 손으로 짰다」가 오히려 손해가 되는 경우가 많다.

10.1 진짜 위험 - 룩어라운드 안의 중첩 수량자

패턴: /^(?=(a+)+$)/     입력: 'a' * n + 'b'

n=20    6.6 ms
n=22   27.2 ms
n=24  108.6 ms
n=26  431.4 ms
n=28 1764.6 ms
n=30 7104.6 ms

두 글자 늘 때마다 네 배다. n=30에서 7초가 걸리는 패턴은 n=40이면 사람이 기다릴 수 있는 시간이 아니다. 이것이 ReDoS의 전형이고, 원인은 룩어헤드가 아니라 그 안에 있는 (a+)+다. 수량자가 붙은 그룹에 수량자를 또 붙이면 같은 문자열을 나누는 방법이 지수적으로 늘어나고, 매치가 실패할 때 그 모든 경우를 다 시도한다.

룩어헤드가 상황을 나쁘게 만드는 지점은 하나 있다. 룩어헤드는 매번 실패해야 하는 조건을 만들기 쉽다. 부정 룩어헤드는 정의상 내부 매치가 끝까지 실패해야 성공하므로, 안에 폭발하는 패턴을 넣으면 최악 경로가 항상 실행된다. 반면 중첩 없이 쓴 /^(?=a+$)/는 10만 자 입력에서도 0.15밀리초다.

10.2 대책

  • 길이 상한을 정규식보다 먼저 검사한다. 가장 값싸고 가장 확실하다. 위 표에서 0.00004밀리초짜리 줄이다. 비밀번호·아이디·파일명처럼 상한이 자명한 입력이라면 이것만으로 사실상 끝난다.
  • 중첩 수량자를 만들지 않는다. (a+)+, (a|a)*, (\s*)+ 형태를 패턴 리뷰의 체크 항목으로 둔다.
  • 사용자가 패턴을 입력하는 자리라면 역추적 엔진을 쓰지 않는다. Go의 regexp나 Rust의 regex는 입력 길이에 선형인 시간을 보장하는 대신 룩어라운드를 제공하지 않는다. 이 맞바꿈은 우연이 아니라 같은 설계 결정의 앞뒷면이다.
  • 타임아웃이 있으면 건다. .NET처럼 정규식 실행에 시간 제한을 걸 수 있는 런타임이 있다. 근본 해결은 아니지만 장애를 지연으로 바꿔 준다.
  • 부정 룩어헤드 안은 특히 단순하게 유지한다. 그 안은 정상 입력에서도 매번 끝까지 탐색되는 구간이다.
  • 패턴을 상수로 고정한다. 문자열을 이어 붙여 정규식을 만들면 사용자 입력이 패턴 자체에 섞여 들어가 폭발하는 형태가 우연히 만들어진다. 값은 패턴이 아니라 인자로 넘긴다.

11. 확인하지 못한 것

  • Java java.util.regex의 가변 길이 후방탐색. 이 환경에 JDK가 없어 실행으로 확인하지 못했다. 8절 표의 해당 칸을 비워 둔 이유다.
  • .NET의 가변 길이 후방탐색. 같은 이유로 실행 확인을 하지 못했다. 룩어라운드 자체를 지원한다는 것까지만 문서 기준으로 적었다.
  • Go regexp, Rust regex, 파이썬 서드파티 regex 모듈. 셋 다 이 환경에 없어 문서 근거로만 적었다. 표의 Go 행은 regexp/syntax 문서가 열거하는 영폭 조건 목록(^ $ \A \b \B \z)에 룩어라운드가 없다는 사실에 근거하며, 10.2절의 Rust 언급과 8.1절의 regex 모듈 언급도 같다. 파이썬은 표준 re가 거부한다는 것까지만 실행으로 확인했다.
  • 최신 PCRE2의 가변 길이 후방탐색. 표의 PCRE 행은 GNU grep 3.0에 링크된 빌드 기준이다. PCRE2는 이후 릴리스에서 이 제약을 완화한 것으로 알려져 있으나 이 환경에서 확인할 수 없었다. PCRE라고 뭉뚱그리지 말고 쓰는 빌드에서 직접 컴파일해 보라.
  • ReDoS 수치의 이식성. 10절 측정치는 V8 기준이다. 지수적으로 늘어난다는 성질은 역추적 엔진에 공통이지만, 구체적인 밀리초와 임계 n은 엔진과 하드웨어에 따라 달라진다. 절대값이 아니라 증가율을 보라.
  • 유니코드 속성 이스케이프와 룩어라운드의 조합. 6절의 한글 경계 예는 [가-힣]로 썼는데 이것은 완성형 음절만 덮는다. 자모 단독이나 분해된 형태까지 필요한 경우의 동작은 이 글에서 다루지 않았다.

결론: 무엇을 잡을까가 아니라 어디서 잡을까

룩어라운드를 「조건을 더 붙이는 문법」으로 배우면 비밀번호 검증 한 줄을 복사해 쓰는 데서 멈춘다. 그 자리에서는 사실 캡처 그룹으로도 대개 된다. 도구가 값을 하는 곳은 조건과 결과를 분리해야 하는 자리다.

  • 조건에 쓴 글자가 결과에 남아야 할 때 — 경계만 잡는 치환
  • 조건 여러 개가 같은 지점에서 판정돼야 할 때 — 순서에 묶이지 않는 필터
  • 커서가 전진하면 안 될 때 — 겹치는 매치
  • 엔진이 정한 경계 정의가 내 데이터와 맞지 않을 때 — 직접 쓰는 \b
  • 왼쪽과 오른쪽을 동시에 봐야 할 때 — 약어 경계처럼 양방향 조건이 필요한 자리

판단 기준을 하나로 줄이면 이렇다. 매치 결과에 포함되면 안 되는 조건이 있는가. 있으면 룩어라운드고, 없으면 대개 더 단순한 패턴으로 충분하다.

그리고 두 가지를 습관으로 두면 사고가 줄어든다. 첫째, 후방탐색은 고정 길이로 쓴다. 파이썬은 길이가 다른 교대조차 거부하고, 펄과 PCRE는 무한 수량자에서 멈춘다. 가변 길이가 정말 필요하면 \K나 캡처 그룹으로 내려오는 편이 옮겨 다니기 쉽다. 둘째, 부정 조건을 걸 때는 매치 경계를 함께 고정한다. \d+(?!USD)가 10을 돌려주던 자리가 그 이유다.

마지막으로, 한국어를 다룬다면 순서를 뒤집어야 한다. 룩어헤드로 활용형을 깎아 내기 전에 포함 조건이 한 번이라도 매치된 적이 있는지부터 확인하라. 매치 0건과 배제가 잘 된 상태는 결과 화면에서 똑같이 생겼다.
