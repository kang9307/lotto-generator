Kubernetes Gateway API 2026 - Life After the NGINX Ingress Controller Retirement

Ending the era of annotations, governing traffic with standard resources

Jun 9, 2026 Tech

Introduction: An Event That Shook Half the Clusters

In November 2025, the Kubernetes project made a heavy announcement. A piece of critical infrastructure that roughly half of all cloud-native environments depended on - ingress-nginx (the NGINX Ingress Controller) - would be retired in March 2026. SIG Network and the Security Response Committee had exhausted their efforts to find additional people and support to make the project sustainable, and ultimately decided to retire it to prioritize user safety. Per the official statement, after March 2026 there will be no new releases, no bug fixes, and no patches for security vulnerabilities.

This is not the routine end-of-life of one more library. ingress-nginx served as the gateway between the internet and the inside of clusters in so many places that its retirement poses the same question to countless operations teams at once: what do we move to? At the center of the migration path the Kubernetes project recommends sits the Gateway API. Starting from the ingress-nginx retirement as our anchor, this article works through why Ingress hit its limits, how Gateway API solves those limits as a standard, and how to migrate in practice.

Note: what is being retired is the open-source community project kubernetes/ingress-nginx. F5's (formerly NGINX Inc.) commercial NGINX Ingress Controller is an entirely separate codebase with its own lifecycle and remains maintained. Confusing the two leads to bad decisions.

1. What Ingress Was - and Why It Hit a Wall

Let us set the foundation. Ingress was the standard Kubernetes resource for routing external HTTP/HTTPS traffic to internal services. It defines, based on host name and path, which service traffic goes to - a kind of L7 routing rule. The concept is simple.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ingress
spec:
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80

The problem is that this simple spec could not keep up with real-world needs. In practice you need timeouts, rewrites, header manipulation, canary splitting, mTLS, and rate limiting - none of which the Ingress standard spec had a place to express. As a result, each controller patched the missing expressiveness with annotations.

metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$1
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20"

Three chronic problems of Ingress surface here.

  • Annotation sprawl: Core routing behavior hides in controller-specific annotation strings rather than the standard spec. It is hard to validate, and a single typo can silently break behavior.
  • Vendor lock-in: nginx.ingress.kubernetes.io/... annotations are ingress-nginx only. Switching to Traefik or HAProxy means rewriting every annotation. The word "standard" rings hollow.
  • No role separation: Host, path, TLS, and rewrite are crammed into one resource, so the platform team and app teams must touch the same object. Drawing permission boundaries in multi-tenant environments is hard.

This structure also underlies the growing security burden on ingress-nginx. Converting annotation-supplied config strings into NGINX configuration internally is inherently a wide attack surface and hard to maintain. Patching what the standard could not express with workarounds let complexity accumulate.

2. What Gateway API Is - The Traffic Gateway, Redesigned as a Standard

To solve these limits head-on, SIG Network designed the Gateway API. It is the successor to Ingress, but not a mere version bump - it remodels traffic routing from scratch. Two core ideas drive it. First, express the features you actually need (headers, rewrites, traffic splitting, cross-namespace routing) as standard fields, not annotations. Second, split one giant resource into several resources by role.

The most important fact: Gateway API's core resources already reached GA (Generally Available) in v1.0. Per the official docs, GatewayClass, Gateway, and HTTPRoute graduated to v1 and are stable APIs with backwards-compatibility guarantees. This is not an experiment - it is a standard ready for production.

2.1 The Three Core Resources

Resource What it defines Analogy
GatewayClass Which controller (implementation) handles traffic. A cluster-scoped template. Like StorageClass
Gateway An actual traffic-entry instance. Defines listeners, ports, protocol, TLS. The load balancer itself
HTTPRoute HTTP routing rules from a Gateway listener to backends. A path/header routing table

The relationships are intuitive. Each Gateway is bound to one GatewayClass, which sets "who handles this traffic," and routing resources like HTTPRoute attach to a Gateway to set "how to route it." Beyond HTTP there are sibling resources - TCPRoute, TLSRoute, GRPCRoute - so per-protocol routing can be expressed in the same standard way.

2.2 The Same Thing Expressed in Gateway API

# 1) Cluster operator: define the traffic entry point
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
spec:
  gatewayClassName: envoy        # which implementation handles it
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls:
      mode: Terminate
      certificateRefs:
      - name: shop-tls
---
# 2) App developer: define routing rules (standard fields, no annotations)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-route
spec:
  parentRefs:
  - name: shop-gateway
  hostnames:
  - "shop.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    filters:
    - type: URLRewrite        # standard filter: no annotation needed
      urlRewrite:
        path:
          type: ReplacePrefixMatch
          replacePrefixMatch: /
    backendRefs:
    - name: api-svc
      port: 80

See the difference? The rewrite is expressed not as a vendor-only string like nginx.ingress.kubernetes.io/rewrite-target, but as a standard URLRewrite filter inside filters. This manifest works the same on Envoy Gateway, Istio, and NGINX Gateway Fabric. Swap the implementation and the routing definition stays intact.

3. Role-Oriented Design - The Real Innovation

The deepest change in Gateway API is not added features but role separation. The official design splits resources to match the real roles of organizations involved in Kubernetes networking.

  • Infrastructure providers: Cloud or platform providers deploy GatewayClasses - cluster-scoped resources that act as templates defining the behavior of Gateways derived from them.
  • Cluster operators: Use GatewayClasses to deploy Gateways and define where and how traffic enters the cluster. Ports, TLS, and listeners are their responsibility.
  • Application developers: Define only how traffic routes to their services via HTTPRoute. They need not know the infrastructure details.

Why does this matter? In Ingress, TLS certificate config and app routing rules mixed in one object, so app developers touched infrastructure or, conversely, the platform team had to own all routing. In Gateway API the platform team manages Gateways (entry points and TLS), while each team manages only its own HTTPRoutes. A safe permission boundary for multi-tenant environments is baked into the resource model itself. This aligns precisely with platform engineering's "self-service with safe guardrails" philosophy. For the wider context, see Platform Engineering Complete Guide 2026.

4. Why "Standardization" Matters

Press the value of Gateway API into one word and it is portability. When the standard itself is expressive, routing intent is no longer tied to a particular vendor's annotation dictionary. That yields three concrete benefits.

  1. Much lower switching cost: Change only the controllerName on the GatewayClass and the same HTTPRoute runs on a different implementation. If an event like the ingress-nginx retirement comes again, sitting on the standard softens the blow.
  2. Validatability: Because routing is expressed as typed fields, schema validation works in kubectl and CI. Silent outages from annotation typos shrink.
  3. Ecosystem focus: Every implementation competes to pass conformance against the same standard, so feature innovation stacks on the standard instead of fragmenting.

In short, standardization is not "forcing one implementation." It is building a common language that many implementations can speak compatibly. That is fundamentally different from Ingress's annotation Tower of Babel.

There is a subtler organizational benefit too. When routing intent lives in standard, reviewable resources, it becomes a first-class part of GitOps and CI pipelines. A pull request that changes an HTTPRoute can be diffed, policy-checked, and approved like any other code change, instead of relying on a reviewer to recognize the meaning of an obscure annotation string. Over time this turns traffic configuration from tribal knowledge held by a few NGINX experts into shared, auditable infrastructure - which is exactly the kind of leverage that matters as teams and clusters grow.

5. Major Gateway API Implementations - What to Choose

One standard, many implementations. Here are the major ones and their character as of 2026. The crucial premise: whichever you pick, manifests (HTTPRoute, etc.) are mostly reusable.

Implementation Data plane Strength Good fit
Envoy Gateway Envoy High conformance and feature velocity, Envoy-native The common choice for broad L7 features
Istio Envoy (Ambient) Service mesh integration, ms-level config propagation Already on a mesh or mTLS/traffic policy is core
Cilium eBPF Top L4 throughput, avoids kernel overhead Using Cilium as CNI and L4 performance matters
NGINX Gateway Fabric NGINX Familiar to ingress-nginx users, Go control plane The closest migration path from NGINX
Kong Kong/NGINX API gateway features, fast config propagation Need API management and a plugin ecosystem

Recent industry analysis suggests the "Envoy-native" ecosystem (Envoy Gateway, Istio Ambient) shows the highest conformance and feature velocity and has become the dominant architectural pattern. If L4 throughput is absolutely critical, Cilium with its eBPF data plane stands out. Meanwhile, for teams starting from ingress-nginx, NGINX Gateway Fabric - which rewrites the NGINX control plane in Go to natively speak Gateway API - is the closest both psychologically and technically.

6. Migration - ingress2gateway and Phased Cutover

Now the most practical question: "I already run dozens of Ingresses - how do I move?" Fortunately, SIG provides an official conversion tool.

6.1 ingress2gateway

ingress2gateway is a Kubernetes SIG project that reads existing Ingress resources and auto-converts them into Gateway and HTTPRoute. It supports provider-specific annotation handling for NGINX, Istio, Kong, Apisix, GCE, and more. Manually translating complex Ingress rules and annotations is error-prone, and this tool automates that process.

# Read all Ingresses and emit Gateway API resources
ingress2gateway print --input-file=ingress.yaml --providers=ingress-nginx

# Output (conceptual): Gateway + HTTPRoute YAML is generated
# Do NOT apply blindly - always review (the conversion is a "draft")

Key caveat: the conversion output is a draft. Some rules map cleanly to standard fields, but some vendor-only annotations have no 1:1 standard equivalent. Review the differences after conversion and, where needed, fill gaps with implementation-specific extensions (e.g., Envoy Gateway policy resources).

6.2 A Phased Migration Roadmap

  1. Inventory: List every Ingress in the cluster and the annotations attached to each. First confirm which annotations map to standard fields.
  2. Choose and install an implementation: Based on the comparison above, pick a Gateway API implementation and install it alongside the existing ingress-nginx. Do not rip and replace at once.
  3. Generate the conversion draft: Use ingress2gateway to produce Gateway and HTTPRoute drafts, then review and adjust.
  4. Move non-critical first: Migrate low-traffic, low-risk services to the new Gateway first and validate behavior.
  5. Shift traffic gradually: Move traffic to the new path step by step via DNS weighting, canary, or blue-green. Roll back instantly on trouble.
  6. Remove ingress-nginx: Once all routing is validated, decommission the old controller.

This phased attitude matches the core principles of reliable operations. A big-bang cutover looks like the fastest route but is the riskiest. Always keeping a rollback path for automation and migration mirrors the principles covered in AI in SRE - The Future of Reliable Operations.

7. Migration Considerations - A Trap Checklist

To make the cutover smooth, know a few traps in advance.

  • Annotations with no 1:1 standard mapping: Fine-grained NGINX tuning (special timeouts, custom config snippets) may not be fully expressible in standard fields. Fill gaps with implementation-specific policies, but be aware that part re-introduces vendor coupling.
  • Changed TLS/certificate model: The Ingress TLS block moves to per-listener certificateRefs on the Gateway. Re-check your cert-manager integration too.
  • Cross-namespace routing: Gateway API explicitly permits cross-namespace references via ReferenceGrant. Strong for security, but a common early source of "why won't this connect?"
  • Per-implementation conformance gaps: Not every implementation supports 100% of standard features. Confirm the feature you want is within your chosen implementation's conformance. In the Gateway API v1.5 review, stale implementations will be dropped from the list.
  • Observability re-work: Dashboards and alerts tuned to ingress-nginx metrics must be re-built for the new data plane (e.g., Envoy).

One practical way to de-risk the whole list is to treat the first migration as a deliberate learning exercise rather than a production cutover. Stand up the new Gateway implementation on a staging cluster, run ingress2gateway against a representative slice of your real Ingresses, and read the conversion diff line by line with the team that owns those services. The annotations that fail to map cleanly are precisely the places where your traffic behavior is most implementation-specific - and therefore the places most likely to cause a surprise in production. Surfacing them early, in a low-stakes environment, converts what would have been a 3 a.m. incident into a calm design discussion.

8. Implications for Korea's Infrastructure

Mapping this to the Korean operations reality surfaces a few practical points.

  • Managed Kubernetes users: Teams on domestic clouds (NHN, NAVER, KT) or global managed K8s should first check which GatewayClass the platform provides by default. When the infra provider installs the GatewayClass, the operations team's burden shrinks.
  • Security requirements in finance/telecom: Keeping an internet-facing controller with no security patches after March 2026 is a regulatory and audit risk. Raise the migration priority.
  • Small operations teams: In the many domestic organizations where infra engineers wear several hats, role separation becomes "delegating operational load." When app teams self-service HTTPRoutes, the platform team's bottleneck eases.
  • Phased-cutover culture: Given large domestic services where zero-downtime is essential, a phased cutover built on canary and parallel operation is effectively the only safe road.

9. Correcting Common Misconceptions

9.1 "Ingress dies immediately"

No. What dies is the open-source ingress-nginx controller. The Ingress resource (networking.k8s.io/v1) remains in Kubernetes, and other Ingress controllers exist. But the future points to Gateway API.

9.2 "Gateway API is still experimental"

No. The core resources (GatewayClass, Gateway, HTTPRoute) reached GA in v1.0 and are stable APIs. They are production-ready.

9.3 "F5's commercial NGINX product is ending too"

No. Only the community project is retiring. F5's commercial NGINX Ingress Controller is maintained separately.

9.4 "Pick the wrong implementation and start over"

Mostly no. As long as you use standard resources, routing definitions like HTTPRoute are largely reusable. The switching cost is far lower than in the Ingress era.

10. Conclusion + 3 Things You Can Apply Today

The retirement of ingress-nginx looks like a crisis, but more precisely it is a turning point that forces the standardization we kept postponing. Ingress survived a decade on the workaround of annotations, and that workaround hit its limits in vendor lock-in, lack of validatability, and security burden. Gateway API answers the same problems with standard fields and role separation - a from-scratch redesign. The core resources are already GA, implementations are many, and on the standard your manifests are reusable whichever you pick.

Three things you can apply today:

  1. Inventory first. List every Ingress and annotation in your cluster, and prioritize the internet-facing ones. You cannot plan a migration if you do not know what to move.
  2. Generate a draft with ingress2gateway. Do not translate by hand; produce a conversion draft with the official SIG tool and review it. Once you can see which annotations do not map to the standard, you are halfway done.
  3. Migrate gradually with parallel operation. Run the new implementation alongside ingress-nginx and move non-critical services first via canary to validate. Always keeping a rollback path is the key to a zero-downtime cutover.

One line to sum it up: "What retired is one controller; what you must move to is not a vendor but a standard." For every team wondering what comes after ingress-nginx, Gateway API is not just a replacement - it is a foundation that will not shake at the next retirement.
