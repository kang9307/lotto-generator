この記事は、Fernando Simõesの「A 40ms Go GC pause caused by swap」（2026年9月13日、9月14日の更新を含む）を、リポジトリgo-gc-swap-costのbpf/stw.bt、Go 1.26のリリースノート、GoブログのGreen Teaの記事と照らし合わせて整理したものである。

問題提起 — スワップを有効にした環境で観測された40msの停止

原文は、著者がメモリの急増を吸収するために本番環境でスワップを使うことにして、危うく額を叩きそうになった経験から始まる。著者は、読者が同じ目に遭わないようにこの文章を書いたと述べている。実験の構成は単純で、cgroupを1つ用意してプロセスを2つ入れた。1つはio.ReadAllでバイト列を読み、proto.Unmarshalでblobとグラフ構造体を作るGoプロセスで、グラフ構造体はGoのアロケーターがscanとして印を付けるオブジェクトである。もう1つは、ほとんど静かにしているHTTPサーバーだ。

著者の最初の予想はこうだった。コレクターは実行されるたびにscanスパンをポインタ1つずつ読んで扱いを決める。メモリ圧迫が来るとカーネルはページをスワップデバイスへ追い出すが、退避はプロセス単位ではなくcgroup単位なので、2つのプロセスのページが一緒に追い出される。だからカーネルとガベージコレクターの間でスワップインとスワップアウトが悲しく繰り返される可能性は小さいと考えた。著者は、この予想は間違っていたと書いている。

実験中に見つけた問題はこうだ。Goのガベージコレクターは、ヒープの外にあり解放されない領域のメタデータを、世界が止まる区間（stop-the-world）で読む。そのメタデータがスワップにあることがありうる。著者は、カーネル6.8でMGLRUを有効にしたHetznerのサーバーでモック実行を行い、停止時間の中央値は約51µsで、メタデータがNVMeにあるときの最悪の停止は40msだったと報告している。

  • 中央値と最悪値：中央値は約51µs、最悪は40ms（詳細な測定値39,902µs）である。原文は40msが中央値の800倍だと書く。39,902を51で直接割ると約782倍になる（計算）。
  • 測定条件：最悪値は原文の表現で「メタデータがNVMeにあるとき」の値である。中央値51µsを測ったときにスワップが使われていたかどうかは、原文に明示されていない。
  • 全体の停止：すべてのPが止まるので、たとえばI/Oを待っていたゴルーチンのI/Oが停止中に完了して戻っても、それを処理する主体がいないというのが原文自身の説明である。

原文が強調するのは、この40msが特定のゴルーチンではなく世界が止まった区間で生じるという点である。著者は、最初はこの長さが無害に見えうると認めつつ、それがSTWだという事実を指摘する。同じ急増の間にこうした停止が2〜3回繰り返されたことも原文に書かれている。

STWの2点とフォルトが起きたGC内部の呼び出し箇所

原文によれば、Go GCは2つの時点で世界を止める。1つはスイープ終了（sweep termination）を行うとき、もう1つはマーク終了（mark termination）を行うときだ。著者の実験では、30分の間にこうした停止が312回あった。

著者は、世界が止まっている間のページフォルトを数える小さなbpfスクリプトを書いた。最悪の1件の出力は次のとおりだった。停止39,902µs、その間のフォルト228回、フォルトの中で費やした時間39,013µs。著者はこれを「40msのうち39msが228回のページフォルトに使われた」と要約する。それらのフォルトはGCの帳簿処理（bookkeeping）の中で起き、原文はaddr2lineの出力で10行の呼び出し箇所を示している。

  • runtime.(*spanSet).reset — internal/runtime/atomic/types.go:194
  • runtime.finishsweep_m — mcentral.go:71、もう一方のスタックではmgcsweep.go:268
  • runtime.gcStart.func2 — mgc.go:724
  • runtime.systemstack — asm_amd64.s:518
  • runtime.gcStart — mgc.go:722
  • runtime.nextMarkBitArenaEpoch — mheap.go:2481

10行は、5フレームずつの2つのスタックとして読める。一方はspanSet.resetから始まり、もう一方はnextMarkBitArenaEpochから始まり、どちらもfinishsweep_m、gcStart.func2、systemstack、gcStartへと続く。リポジトリのスクリプトがustack(5)で5フレームを取っていることと一致する。原文は各関数の役割や、これらの呼び出し箇所がどのSTW時点に対応するかを説明していないので、この記事も名前と位置までにとどめる。

原文が説明するカーネル側の経路 — 退避からメジャーフォルトまで

原文が挙げる理由はこうだ。ランタイムはそれらのページを割り当てる。それらは解放されずに再利用される。そしてGCサイクルで読まれる。カーネルは古さの順にページを退避させるので、最も長くアクセスされていないページをスワップへ送る。GCが世界を止めてそのページを読もうとすると、すでにスワップにあるのでメジャーページフォルトが起きる。

著者は、フォルト1回の処理を「手短に言えば」として次のように並べる。カーネルがPTEを読み、do_swap_pageを呼び、新しいフレームを探し、それをcgroupに課金し、ページを読むためにbioを投入し、ディスクを待ってからメモリに戻す。原文はこれらの段階の横に、Linux 6.8のソース（mm/memory.c、mm/swap_state.c、mm/page_io.c）の該当行へのリンクを付けている。

  • 退避の基準：アクセス時刻である。最も長くアクセスされていないページが先にスワップへ行く。
  • 退避の単位：著者の前提ではプロセスではなくcgroupである。そのため静かなHTTPサーバーのページも同じ圧迫の下に置かれる。
  • メタデータのアクセスパターン：原文の表現では、それらのページはGCサイクルで読まれる。サイクルの合間には触られないことがありうる。
  • フォルト1回のコスト：上の並びの最後にディスク待ちがあるため、原文の最悪ケースでは228回のフォルトが1回の停止の中で起きた。

同じフォルトでも、どこで起きるかによって影響の及ぶ範囲が異なる。著者は511KiBのメッセージを作るゴルーチンの遅延を述べる中で、そのコストは割り当てを行うゴルーチンだけが払うので、メタデータの停止のように全体ではなく局所的だと書いている。逆にメタデータのフォルトは世界が止まった中で起きるため、すべてのPが一緒に待つことになる。

実験環境とbpftraceスクリプト — stw.bt全文

原文のモック実行は、カーネル6.8でMGLRUを有効にしたHetznerのサーバーで行われた。グラフ、モックアロケーター、bpfスクリプト、Pythonスクリプトなど実験のすべてがリポジトリgo-gc-swap-costにある。観測は30分で、その間にSTWが312回あった。以下はそのリポジトリのbpf/stw.btの全文で、コメントも含めて文字どおり写した。

// BIN: path of the Go binary as seen by bpftrace, e.g. /proc/<pid>/root/tmp/pagefault
                    // both processes run the same binary, so everything is keyed by pid: a fault counts only
                    // against a pause of its own process
                    uprobe:BIN:runtime.stopTheWorldWithSema /comm == "pagefault"/ {
                      @stw_start[pid] = nsecs; @stw_faults[pid] = 0; @stw_fault_ns[pid] = 0;
                    }
                    uprobe:BIN:runtime.startTheWorldWithSema /@stw_start[pid]/ {
                      $d = (uint64)(nsecs - @stw_start[pid]);
                      @stw_us = hist($d / 1000); @stw_n[pid] = count(); @stw_ns[pid] = sum($d);
                      printf("stw t=%d pid=%d %d us, faults during it %d, %d us in faults\n",
                             elapsed / 1000000, pid, $d / 1000, @stw_faults[pid], @stw_fault_ns[pid] / 1000);
                      delete(@stw_start[pid]);
                    }
                    // swap-in and file-backed faults both: the binary's own code pages can be evicted too
                    kprobe:do_swap_page, kprobe:filemap_fault /comm == "pagefault" && @stw_start[pid]/ {
                      @f_start[tid] = nsecs; @stw_faults[pid]++; @stw_stack[ustack(5)] = count(); // five frames reach gcStart
                    }
                    kretprobe:do_swap_page, kretprobe:filemap_fault /@f_start[tid]/ {
                      @stw_fault_ns[pid] += (uint64)(nsecs - @f_start[tid]); delete(@f_start[tid]);
                    }
                    END { clear(@stw_start); clear(@f_start); clear(@stw_faults); clear(@stw_fault_ns); }

スクリプトの構造は4つの部分からなる。第一に、stopTheWorldWithSemaに掛けたuprobeはpidごとに開始時刻を記録し、フォルト回数とフォルト時間を0にする。第二に、startTheWorldWithSemaに掛けたuprobeは停止時間$dを計算してマイクロ秒のヒストグラムに入れ、停止時間、フォルト回数、フォルト時間を1行で出力したあと、そのpidの開始時刻を消す。第三に、kprobeはdo_swap_pageとfilemap_faultへの突入時に時刻を記録し、フォルト回数を増やし、ustack(5)で呼び出しスタックを集計する。第四に、kretprobeはその2つの関数が終わるときに経過時間をフォルト時間に加える。

スクリプトのコメントが教えてくれることが2つある。2つのプロセスが同じバイナリを実行しているため、すべての値をpidで区別し、フォルトが自分のプロセスの停止にだけ数えられるようにしている点。そして、スワップインとファイルバックのフォルトの両方を数える点だ。バイナリ自身のコードページも退避されうるからである。スクリプトを読むと、原文の228回がdo_swap_pageとfilemap_faultの呼び出しを合わせた値であることがわかる。

  • 観測：30分の間にSTWが312回。
  • 最悪ケース：停止39,902µs、フォルト228回、フォルト処理の合計39,013µs。
  • フォルトの割合：39,013 ÷ 39,902 ≈ 97.8%である（計算）。原文の記述は「40msのうち39ms」だ。
  • フォルト以外の時間：39,902 − 39,013 = 889µsである（計算）。この時間の内訳は原文にない。
  • 反復：テストでは、メモリ急増1回につきこうした停止が2〜3回出た。

メッセージ生成の遅延 — 割り当てゴルーチンだけが払うコスト

著者はもう1つのことに気づいた。511KiBのメッセージを1つ作るのに普通は3〜5msかかるが、スワップがNVMeにあるときは105msに、Hetznerのネットワークボリュームにあるときは903msに延びた。著者は、メッセージ1つあたりのコストはメタデータの停止より大きいと書く。ただし、割り当てを行うゴルーチンだけがその代価を払うので、少なくとも局所的で、メタデータのように全体に及ぶものではないと付け加えている。

  • 範囲：遅延は割り当てを行うゴルーチンに限られる。全体のSTWと違って、他のPを止めるものではない。
  • 媒体による差：105msに対する903msは約8.6倍である（903÷105の計算）。同じ作業がスワップの媒体でこれだけ変わった。
  • 時間の内訳：著者は、この時間がどこに使われたかを確認できていないと自ら述べている。

著者がこの項目を文章に入れた理由は、「払うことになるかもしれないもう1つのコスト」だからである。著者はこの時間をメタデータのフォルトと同じ原因だとは説明していない。したがってこの記事も、メッセージ生成の遅延をSTWのフォルトと同じメカニズムの結果とは読まない。

Green Tea GCの再測定とGo公式の説明

原文の9月14日の更新は短い。誰かが、Go 1.26のGreen TeaガベージコレクターがGCのメタデータの読み方を変えたのかと尋ね、著者が測定したところ影響は無視できる程度（negligible）だったというものだ。測定環境と数値は公開されていない。

Go公式の資料はGreen Teaを次のように説明している。Goブログ（2025年10月29日）によれば、中心となる考えは「オブジェクトではなくページで作業する」ことである。オブジェクトをスキャンする代わりにページ全体をスキャンし、作業リストにもオブジェクトではなくページを載せ、マーク済みのオブジェクトはヒープ全体ではなく各ページの中で局所的に追跡する。ブログはこれをキャッシュの局所性と結びつけて説明している。Goではページはハードウェアの仮想メモリのページとは無関係に8KiBである。

  • Go 1.25：GOEXPERIMENT=greenteagcで有効にする実験機能だった。ブログは、多くのワークロードでGCに費やす時間が約10%減り、最大40%減るものもあると書いている。
  • Go 1.26：リリースノートによれば、実験だったGreen Teaが既定で有効になり、小さなオブジェクトのマークとスキャンを局所性とCPUスケーラビリティで改善する。GCを多用する実際のプログラムでGCオーバーヘッドが10〜40%減ると見込んでいる（Go公式の数値）。
  • さらなる改善：新しいamd64のCPU（Intel Ice Lake、AMD Zen 4以降）では、小さなオブジェクトのスキャンにベクター命令を使い、GCオーバーヘッドがさらに約10%減ると見込んでいる。
  • 無効化：ビルド時にGOEXPERIMENT=nogreenteagcで無効にでき、この設定はGo 1.27で削除される見込みである。

公式の数値の性格は区別しなければならない。10〜40%はGCのCPUオーバーヘッドに関するベンチマーク上の期待値であり、原文の問題はSTW中のメタデータ読み取りで起きたフォルトである。両者は測る対象が異なるため、一方の数値で他方を推定することはできない。この記事が確認できたのは、著者がGreen Teaでメタデータ読み取りへの影響は無視できる程度だと測定した、という一文だけである。

原文の結論と読む際の注意

原文の結論は1文半である。著者はChris Downに同意して、スワップは悪ではないと書く。しかしスワップはガベージコレクションとは相性がよくなく、自分の本番環境ではGCを大量に回していると付け加える。スワップを切れという推奨や、何らかの設定を変えよという推奨は、原文にはない。

  • 著者が直接確認したこと：世界が止まった区間でメタデータのフォルトが起き、そのフォルトが停止の大部分を占めた事例があった。
  • 著者が未確認と書いたこと：511KiBのメッセージ生成の遅延における時間の内訳である。
  • 著者が短く触れただけのこと：Green Teaでの再測定は、数値なしで結果だけが書かれている。
  • 原文にないこと：運用上の推奨、設定値、他の環境での再現である。

この事例から引き出せる一般的な教訓は、慎重にしか言えない。停止時間が短い区間でも、その区間が読むメモリがスワップにあれば、ディスクの遅延が停止にそのまま乗るということだ。それがどのような運用環境でどのくらいの頻度で起きるかについては、原文は答えていない。

確認できなかったこと

  • 中央値51µsを測った条件。スワップが使われていたときの値かどうかは、原文に明示されていない。
  • 511KiBのメッセージ生成にかかった105msと903msの時間の内訳。原文の著者も、どこに使われたかは確認できていないと書いている。
  • メタデータがネットワークボリュームにあるときのSTW最悪値。原文はNVMeの場合の40msだけを書いている。
  • Green Tea GCの再測定の数値と実行条件。原文は影響が無視できる程度とだけ書いている。
  • Hetznerのサーバー以外の環境や、カーネル6.8以外のカーネルでの再現結果。
  • 228回のフォルトのうち、スワップイン（do_swap_page）とファイルバックのフォルト（filemap_fault）の内訳の比率。スクリプトは両者を合わせて数える。
