Agent-Blackbox: Analyzing Claude Code and OpenCode via Session Maps and Token Waste

Opening the black box of AI coding agents — visualizing session flow, token spend, and waste points, and why agent observability matters in 2026

2026-06-23 Dev & Infra

Introduction: What Is the Agent Actually Doing?

You give Claude Code or OpenCode a complex task and walk away. Ten minutes later the tool call log is scrolling and the API usage dashboard shows a number that makes you pause. The problem is you have no idea why it consumed that much. Which file read looped unnecessarily? Did a subagent recalculate something the orchestrator already handled? Once the session ends, there is no record. The agent is a black box.

Agent-Blackbox attacks this problem directly. Featured on GeekNews in June 2026 with 38 points, the tool visualizes Claude Code and OpenCode execution sessions as session maps and breaks down token consumption at each step to identify waste points. The key contribution is not usage tracking — that already exists — but bringing the concept of agent observability to AI coding agents specifically.

This post starts from the Agent-Blackbox concept and works outward: how token waste structurally accumulates in AI coding agents, what session maps actually enable for debugging, and why agent observability has become a real infrastructure concern in 2026 rather than a nice-to-have. As of June 2026, the tool is early-stage. The direction is right, but the more important thing Agent-Blackbox gives us is the question it poses, not a finished answer.

1. The Agent Black Box Problem — Why Now

Traditional software debugging assumes determinism. Same input, same output; trace the logs backward and find where it broke. AI agents break this assumption. At temperature zero, non-determinism still persists. A single agent run produces dozens of tool calls and subagent spawns, and the context and rationale behind each token consumed at each step leave no trace in the output files.

This problem became acute in 2026 for a structural reason: AI coding agents moved into actual development workflows, and per-session costs crossed a threshold developers care about. Community reports indicate that Claude Opus 4.x series agents consume close to 1.5 times more tokens than the previous version on identical agent configurations. A CI pipeline that runs an agent for four hours can generate 180-plus tool calls and tens of dollars in token spend in a single session. If you cannot see where that cost came from, you cannot reduce it.

Agent-Blackbox frames this precisely: if you do not know what the agent did, you cannot know why it spent so much. After the session ends, you have a total token count and a dollar figure. You do not have which tool call took 40% of the budget, which file read repeated three times unnecessarily, or where two subagents duplicated context. Those details are in the black box.

2. What Is a Session Map — Dissecting Agent Execution

The core concept Agent-Blackbox introduces is the session map. This is a timeline or tree representation of an agent session. Each node represents one tool invocation — file read, bash execution, web search, subagent spawn, and so on. Edges between nodes show call order and causal relationships. Each node carries its input token count, output token count, cache hit status, and latency.

With this structure, several diagnostic patterns become immediately visible:

  • Repeated read detection: If the same file path appears three or more times in the session map, the agent lost track of content it already read and re-requested it. This signals that context compaction settings or caching configuration need adjustment.
  • Token concentration: If 60% of total tokens came from two nodes, those tool calls are generating excessive output. This gives concrete grounds to set CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS or BASH_MAX_OUTPUT_LENGTH limits.
  • Subagent duplication: If two subagents each read similar sets of files independently, the orchestration design is inefficient. Restructuring to pass one subagent's results to the other can eliminate the duplication cost.
  • Idle MCP overhead: Registered MCP server tool definitions attach to the system prompt on every turn whether the tools are used or not. A session map showing which MCP tools were actually called versus never called is the data to justify removing unused MCP servers and reducing fixed overhead.

Claude Code provides PreToolUse and PostToolUse hook events that external tools can intercept by registering hook commands in ~/.claude/settings.json. Agent-Blackbox reads this event stream to construct the session map. OpenCode, being open source, allows direct parsing of session file formats for custom analysis. The ability to provide a unified view across both agents is a meaningful differentiator.

3. The Structure of Token Waste — Where It Leaks

Before reading a session map, it helps to understand the structural categories of token waste that appear in AI coding agents in 2026. Four patterns account for most of what the map will reveal.

3.1 Fixed Overhead: System Prompts and Tool Definitions

Every agent turn includes the full system prompt and all registered tool definitions in context. Claude Code ships with around 20 built-in tools. Connecting 10 MCP servers adds thousands of additional tokens of tool definitions per turn. This cost is paid on every turn regardless of what the task actually requires. Community measurements suggest unused MCP servers connected to a live agent session can account for 20–30% of total session cost as pure overhead.

3.2 Conversation History Accumulation

As an agent session extends, prior tool outputs, assistant responses, and file read results pile up in conversation history and get carried in context on each subsequent turn. A short agent loop run 100 times generates a turn 100 with exponentially more input tokens than turn 1. When context compaction fails or cache reads miss, the cost can spike suddenly. One widely-shared community case reported 67,374 tokens of cached content being reprocessed from scratch on every conversation turn due to a cache read failure, despite the initial cache write succeeding.

3.3 Unnecessary External Connections

Running an agent with IDE auto-connect (autoConnectIde enabled), web search active, and global documentation auto-loading adds session overhead that has nothing to do with the coding task. Practical measurements shared in the community show that disabling web search (web_search = disabled) and MCP apps (features.apps = false) in OpenCode meaningfully reduces per-session token count for straightforward coding tasks.

3.4 Subagent Redundant Context

In multi-agent configurations, when an orchestrator passes the same file contents or background information to each subagent independently, context duplication multiplies the base cost by the number of subagents. This is an orchestration design problem, not an agent limitation — but without a session map, you cannot even tell whether the duplication is happening.

4. Agent Observability as a Category — Why 2026

Agent observability is the practice of capturing AI agent execution as structured traces — recording every model call, tool invocation, and reasoning step as a span — and making those spans available for monitoring, evaluation, and debugging. It is application performance monitoring (APM) extended to AI agents, and in 2026 it has solidified into its own category with a fast-consolidating tool landscape.

Two structural shifts drove this. First, agents moved from single-call utilities to multi-step autonomous executors running for minutes or hours. A single chatbot call needs one log line. A four-hour agent session with 180 tool calls needs trace-level visibility across the full execution tree to diagnose a failure. Second, costs became non-negligible. Monthly agent API spend in the hundreds of dollars is now routine for teams using agentic coding in their workflows, and the question of where that money went has a real financial answer to find.

Agent observability has four dimensions:

  • Execution traces: Tool calls, subagent spawns, and model responses recorded with temporal and causal ordering
  • Token and cost attribution: Per-step breakdown of what was spent where
  • Output evaluation: Quantitative assessment of whether each step's output met expectations
  • Agent identity tracking: In multi-agent setups, attribution of which agent handled which task

Agent-Blackbox concentrates on the first two: execution traces and token cost attribution. This narrower scope differentiates it from general-purpose observability platforms like Langfuse or Arize Phoenix. The focus on Claude Code and OpenCode session file formats and hook events specifically makes it a lighter-weight, local-first tool rather than a full observability platform — a tradeoff that favors simplicity and data security over breadth.

5. Claude Code vs OpenCode — An Observability Lens

Agent-Blackbox supports both agents. This is interesting because the two agents present structurally different surfaces for observability tooling.

5.1 Claude Code's Observability Architecture

Claude Code exposes an official hook system. Hook points including PreToolUse, PostToolUse, and Stop allow external tools to register hook commands in the settings file and intercept all tool call events. From an observability tool's perspective this is convenient: no proxy layer needed, no agent code modification, just register with the official extension point. The limitation is that hook events provide tool-call-level information but do not expose the agent's internal reasoning process. Extended thinking tokens — which can represent a meaningful fraction of session cost — are not visible through hooks.

5.2 OpenCode's Observability Architecture

OpenCode being open source means session file formats can be parsed directly and custom instrumentation can be inserted into the source. This gives observability tool developers deeper access but also creates fragility: if OpenCode changes its session file format in a version update, the parser breaks. There is no stable hook API contract to rely on the way Claude Code's hook system provides.

5.3 Shared Blind Spots

Both agents share a common opacity: internal reasoning tokens from extended thinking modes are not surfaced to external tools. For both Claude Code and OpenCode, a portion of per-session token spend — potentially significant in complex tasks — remains inaccessible to the current generation of observability tools. Agent-Blackbox can show you the tool-call layer of the execution; the reasoning layer beneath it is still a black box.

6. Practical Application — How to Use This in 2026

Here is the priority order for bringing agent observability into a real workflow as of June 2026.

6.1 Start With Local-First Tools

Session logs contain raw prompts and code content. Sending them to a SaaS observability platform creates a data security exposure that conflicts with most engineering team policies. Agent-Blackbox, AgentProf, CodeBurn, ccusage, and similar local-first tools keep analysis on the local machine. Start with local-first collection to establish baseline patterns before considering any cloud observability layer.

6.2 Reduce Fixed Overhead First

Before investing time in session map analysis, there are confirmed quick wins. For Claude Code: set includeGitInstructions: false, set autoConnectIde: false, and disable all MCP servers that the current task does not need. For OpenCode: set features.apps = false and disable web search. These settings reduce fixed per-turn overhead immediately without requiring session map analysis to justify.

6.3 Use Session Maps to Find Patterns, Not Single Sessions

A session map for one run tells you what happened that run. Session maps for ten similar runs laid side by side show you which high-cost patterns repeat consistently. "This agent always reads file X three times" or "tool call Y is consistently followed by a redundant search" are actionable findings that justify prompt changes or tool configuration adjustments. Single-session analysis is often noise; pattern-level analysis gives signal.

6.4 Prioritize Multi-Agent Setups

The value of session-map observability scales with orchestration complexity. In a single agent, you have one execution thread to trace. In a multi-agent setup with Claude Code subagents or OpenCode parallel agents, you have multiple concurrent threads whose costs and context overlaps are invisible without a unified trace. If your team is running multi-agent configurations, session map observability moves from useful to essential.

8. Honest Limits

Listing only advantages is not analysis. Current-generation agent observability tools share real limitations worth being clear about.

Reasoning token opacity: As noted, extended thinking tokens are not captured through hook events. If reasoning tokens account for a significant share of session cost — which they can in complex tasks — the session map has a meaningful gap in its accounting.

Observation overhead: Adding hooks and event logging introduces minor latency. For most workloads this is negligible. For latency-sensitive pipelines, always-on observability may not be appropriate.

Log security: Storing session logs means raw prompts and code snippets accumulate on disk. Even with local-first tools, the log files themselves need explicit access control and retention policies.

Version fragility: Session file formats change with agent version updates. A parser built against one format may break after an update. Long-term tool reliability depends on how well this maintenance problem is managed.

9. Conclusion — The Question Matters More Than the Tool

The question Agent-Blackbox poses is more important than the tool itself: do you know what your agent did? As of June 2026, most teams would answer honestly: not really. They see a cost number. They do not see where it came from.

Agent observability is becoming infrastructure, not a feature. For teams running agents in production workflows, the cost of remaining blind to execution — in debugging time, in wasted token spend, in orchestration inefficiencies that repeat silently — exceeds the cost of operating an observability layer. Session maps, token attribution, and execution traces are the primitives that make agent execution predictable, cheaper, and debuggable.

Agent-Blackbox is an early tool in the right direction. It is not a finished solution. But the category it represents — AI coding agent observability — is not going away. The agents are here to stay; the tooling to understand them is just catching up.
