Introduction - the same pipe symbol, a different thing flows

Both bash and PowerShell join commands with |. What travels along that line, however, is different. The Microsoft Learn topic about_Pipelines explains that the pipeline operator sends the results of the preceding command to the next command, and it makes clear that what is sent is objects. The objects emitted by the first command go to the second, and the objects the second command has processed go to the third. The same topic also states that PowerShell's pipeline is object-oriented and does not support raw byte data, and that standard input (stdin) is not connected to the PowerShell pipeline for input. This contrasts with a bash pipe, which connects the output text of one process to the input of the next.

The consequences are large. In a text pipeline every tool interprets column positions and delimiters on its own. The $5 in ls -l | awk '{print $5}' depends on the convention that it is the fifth column. In an object pipeline the value is taken out by a property name, Length. Once this difference is understood, most translations follow without memorizing a command map. Without it, you type a name that exists as an alias and its options do not work, or the output looks similar while sorting and comparison results differ.

The axis covered here is the concept (objects versus text) and the correspondence table. The syntax and option catalog of grep and awk are in Linux Grep and AWK Usage Guide, and recipes for aggregating incident logs are in The Complete Guide to Linux Log Analysis Commands. A beginner's introduction to automation that widens to batch files and Task Scheduler is in Windows Task Automation for Beginners, and the problem of names colliding with PowerShell aliases when UNIX utilities are brought natively to Windows is in Microsoft Coreutils for Windows.

The log file app.log used for practice has 12 lines. Every aggregation below targets this file. The same folder holds old.log (3 lines), readme.txt (one line, hello), a 2,000-character notes.md, file[1].txt with square brackets in its name, and a subfolder sub (containing deep.log).

The differences checked repeatedly below boil down to five.

  • What flows through the pipe is objects, not strings.
  • The party that interprets wildcards and options is each cmdlet, not the shell.
  • The default for case is the opposite of grep. Select-String and the comparison operators ignore case by default.
  • Even when an alias has the same name as a bash command, its option scheme is not bash.
  • The moment an object is converted to a string, values can be cut off by the display width.

Why ls | grep becomes Where-Object - the output is not a string

The first correspondence selects only the entries ending in .log from a file listing. In bash, lines are selected from the text of the listing.

$ ls | grep '\.log$'
                    app.log
                    old.log

In PowerShell, the Name property of the objects emitted by Get-ChildItem is filtered.

Get-ChildItem | Where-Object { $_.Name -like '*.log' } | Select-Object Name, Length | Format-Table -AutoSize
Name    Length
                    ----    ------
                    app.log    532
                    old.log     36

The printed table is text, but while travelling through the pipe it was objects. What Where-Object did was not to scan line strings but to compare the Name property of each object against a wildcard pattern. This can be confirmed by execution.

$first = Get-ChildItem | Select-Object -First 1
                    $first.GetType().FullName
                    (Get-ChildItem | ForEach-Object { $_.GetType().Name } | Group-Object | ForEach-Object { $_.Name + ' x' + $_.Count }) -join ', '
                    Get-ChildItem -File | Get-Member -MemberType Property | Where-Object { $_.Name -in 'Name','Length','LastWriteTime','Extension' } | Select-Object Name, Definition | Format-Table -AutoSize
System.IO.DirectoryInfo
                    DirectoryInfo x1, FileInfo x5
                    
                    Name          Definition
                    ----          ----------
                    Extension     string Extension {get;}
                    LastWriteTime datetime LastWriteTime {get;set;}
                    Length        long Length {get;}
                    Name          string Name {get;}

The first element is System.IO.DirectoryInfo, and the whole listing is one directory object and five file objects. The file objects carry typed properties such as Length (long) and LastWriteTime (datetime) instead of strings. Two things follow from this. First, there is no need for awk to count columns. Second, comparison and sorting by size are done in numeric order, not character order.

The second correspondence extracts only the size column. In bash, the fifth column of ls -l is taken with awk (directory lines were excluded).

$ ls -l | awk '$1 !~ /^d/ && NF > 2 {print $5}'
                    532
                    9
                    2002
                    36
                    7
Get-ChildItem -File | Select-Object -ExpandProperty Length
532
                    9
                    2002
                    36
                    7

The values are the same, but the way of obtaining them differs. The former breaks when the output format of ls -l changes, while the latter is unaffected by format as long as the property name exists. The difference is clearer in size ordering. When sorting a numeric column, bash sort defaults to character order, so -n must be added.

$ printf '10\n9\n100\n' | sort
                    10
                    100
                    9
                    $ printf '10\n9\n100\n' | sort -n
                    9
                    10
                    100

PowerShell's Sort-Object follows the type of its input. The strings '10','9','100' are sorted in character order, and values converted to numbers are sorted in numeric order. Since the Length of a file object is already a long, it sorts numerically without any option.

'10','9','100' | Sort-Object
                    '10','9','100' | Sort-Object { [int]$_ }
                    Get-ChildItem -File | Sort-Object Length -Descending | Select-Object -First 2 Name, Length | Format-Table -AutoSize
10
                    100
                    9
                    9
                    10
                    100
                    
                    Name     Length
                    ----     ------
                    notes.md   2002
                    app.log     532

The first two results are in the same order as bash for strings (10, 100, 9), and after changing the type they match -n sorting (9, 10, 100). The third result shows the two largest files by name and size. Conversion of an object to a string happens only at the place where the conversion takes place. Putting a file object inside a string leaves only the name.

$f = Get-ChildItem -Filter app.log
                    '"$f" = ' + "$f"
                    'Name  = ' + $f.Name
"$f" = app.log
                    Name  = app.log

The rules that can be read from the table are as follows.

  • Filtering a file listing is a property comparison, not a search of name strings. The extension is reached directly through Extension and the size through Length.
  • awk '{print $N}', which extracts a column, becomes Select-Object -ExpandProperty PropertyName.
  • Sorting follows the type of the input. To sort numerically the value must be a number, and for strings a conversion such as [int] is needed.
  • Written as just find, the name runs the Windows find.exe (in a session without Git's usr\bin on PATH; section 9).

Select-String is not grep - MatchInfo and different defaults

The Select-String documentation introduces the cmdlet as usable similarly to grep in Unix or findstr.exe in Windows. It is similar but not the same. Searching the same file for ERROR shows the two sides diverging. bash distinguishes case and finds 3 matches.

$ grep -n ERROR app.log
                    3:2026-10-05 09:01:12 ERROR db timeout after 30s
                    7:2026-10-05 09:03:02 ERROR upstream 502
                    10:2026-10-05 09:05:00 ERROR db timeout after 30s
Select-String -Path .\app.log -Pattern 'ERROR'
app.log:3:2026-10-05 09:01:12 ERROR db timeout after 30s
                    app.log:5:2026-10-05 09:01:20 INFO  retry succeeded after error in cache
                    app.log:7:2026-10-05 09:03:02 ERROR upstream 502
                    app.log:10:2026-10-05 09:05:00 ERROR db timeout after 30s

The PowerShell side finds 4. Line 5 contains a lowercase error. For the -CaseSensitive parameter, the Select-String documentation says that by default matches are not case-sensitive. grep is the opposite: the default is case-sensitive and you need -i to ignore case. Matching the counts on the two sides gives this.

$ grep -c error app.log
                    1
                    $ grep -ci error app.log
                    4
'matches for error (no flag): ' + @(Select-String -Path .\app.log -Pattern 'error').Count
                    'matches for error -CaseSensitive: ' + @(Select-String -Path .\app.log -Pattern 'error' -CaseSensitive).Count
matches for error (no flag): 4
                    matches for error -CaseSensitive: 1

The app.log:3: at the front of the output is the file name and line number. That this is the display format of a MatchInfo object, not text, can be seen by reading its properties.

$m = Select-String -Path .\app.log -Pattern 'ERROR' | Select-Object -First 1
                    $m.GetType().FullName

                    'Filename   = ' + $m.Filename
                    'Line       = ' + $m.Line
                    'Pattern    = ' + $m.Pattern

                    Filename   = app.log
                    Line       = 2026-10-05 09:01:12 ERROR db timeout after 30s
                    Pattern    = ERROR

The documentation also says Select-String returns a MatchInfo object for each match, with properties such as Filename and Line. So grep -c, which counts, becomes wrapping the result in an array and reading .Count, and grep -o, which extracts only the matched part, becomes reading Matches.Value. The behavior when file objects are piped in also differs from grep. The Select-String documentation says that when a FileInfo object is given as input, it searches the contents of that file, not the string representation of the object. This is the exact opposite of ls | grep app, which searches names.

These four lines were run in the temporary folder created earlier (the one holding app.log, old.log, readme.txt and so on). The 1 on the last line comes from app.log being in that folder's listing, so the number changes in a folder with no entry whose name contains app.

Set-Location C:\demo\t
                    'files whose NAME has app (Where-Object): ' + @(Get-ChildItem | Where-Object { $_.Name -match 'app' }).Count
                    'FileInfo objects | Select-String app (searches contents): ' + @(Get-ChildItem -File | Select-String -Pattern 'app').Count
                    'FileInfo objects | Select-String hello (readme.txt content): ' + @(Get-ChildItem -File | Select-String -Pattern 'hello').Count
                    'listing as text | Select-String app: ' + @(Get-ChildItem | Out-String -Stream | Select-String -Pattern 'app').Count

                    FileInfo objects | Select-String app (searches contents): 0
                    FileInfo objects | Select-String hello (readme.txt content): 1
                    listing as text | Select-String app: 1

One file has app in its name, but piping the file objects as they are searches the contents for app, so 0 matches came out. hello is the content of readme.txt, so it gives 1. To search for a name in the textual representation of the listing, it has to be converted into line-by-line strings with Out-String -Stream before being passed on. This is the trap met most often by people who think in terms of grep.

The default for case is not unique to Select-String. about_Comparison_Operators says string comparisons are case-insensitive unless an explicit case-sensitive operator is used, and that -replace is case-insensitive by default as well. The difference shows up as-is when carrying sed 's/error/X/g' over.

$ echo 'Error ERROR error' | sed 's/error/X/g'
                    Error ERROR X
                    $ echo 'a.b.c' | sed 's/./-/g'
                    -----
'ERROR' -eq 'error'      -> True
                    'ERROR' -ceq 'error'     -> False
                    'ERROR db' -match 'error'  -> True
                    'ERROR db' -cmatch 'error' -> False
                    'ERROR db' -like 'error*'  -> True
                    'Error ERROR error' -replace 'error','X' -> X X X
                    'Error ERROR error' -creplace 'error','X' -> Error ERROR X
                    'a.b.c' -replace '.','-'    -> -----
                    'a.b.c' -replace '\.','-'   -> a-b-c
                    'a.b.c'.Replace('.','-')    -> a-b-c

The block above is the output of running PowerShell one line at a time and printing it in the form expression -> result. As in sed, the first operand of -replace is a regular expression, so '.' matches every character; only the default for case is reversed. Adding c as in -ceq, -cmatch and -creplace makes them case-sensitive.

  • Even when concepts share a name, the default case rule can be reversed, so for any aggregation that compares counts, decide first whether -CaseSensitive is used.
  • Giving Select-String a file object searches contents, while giving it strings or the result of Out-String -Stream searches those lines.
  • The pattern is a regular expression by default, and a literal search is -SimpleMatch. It corresponds to -F of grep.

Replacing sort | uniq -c | wc with Group-Object, Sort-Object and Measure-Object

An aggregation that counts log levels (INFO, WARN, ERROR) is written like this in bash. It extracts the third column, sorts, counts identical values, and sorts again by count.

$ awk '{print $3}' app.log | sort | uniq -c | sort -rn
                          6 INFO
                          3 WARN
                          3 ERROR

In PowerShell, -split with an index takes the place of extracting the column, and Group-Object and Sort-Object take the place of counting and then sorting.

Get-Content .\app.log | ForEach-Object { ($_ -split '\s+')[2] } | Group-Object | Sort-Object Count -Descending | Select-Object Count, Name | Format-Table -AutoSize
Count Name
                    ----- ----
                        6 INFO
                        3 ERROR
                        3 WARN

In the two outputs, the order of WARN and ERROR, which have the same count, is reversed. The order among equal counts is not a defined convention, so it is safer to avoid processing that depends on order. What Group-Object returns is also an object, not a string, so the count column is reached through the Count property.

$g = Get-Content .\app.log | ForEach-Object { ($_ -split '\s+')[2] } | Group-Object | Select-Object -First 1
                    $g.GetType().FullName
                    $g | Get-Member -MemberType Property | Select-Object Name | Format-Table -AutoSize
Microsoft.PowerShell.Commands.GroupInfo
                    
                    Name
                    ----
                    Count
                    Group
                    Name
                    Values

The Group property of GroupInfo holds the original items collected under that value, so beyond the count, the content of each group can be processed further. Line counts and sums are the job of Measure-Object. wc -l becomes Measure-Object -Line or the .Count of an array, and awk '{sum += $5}' becomes -Property Length -Sum.

'wc -l       -> ' + (Get-Content .\app.log | Measure-Object -Line).Lines
                    'count       -> ' + @(Get-Content .\app.log).Count
                    Get-ChildItem -File | Measure-Object -Property Length -Sum -Average -Maximum -Minimum | Format-List Count, Sum, Average, Maximum, Minimum
wc -l       -> 12
                    count       -> 12
                    Count   : 5
                    Sum     : 2586
                    Average : 517.2
                    Maximum : 2002
                    Minimum : 7

bash wc -l < app.log also returns the same 12. Getting count, sum, average, maximum and minimum all in one Measure-Object call is where it is more convenient than a one-line awk aggregation. De-duplication with sort -u is Sort-Object -Unique, and the result of 'b','a','b','c','a' | Sort-Object -Unique is a, b, c.

The one-at-a-time rule of about_Pipelines decides the result in aggregation. Piping in sends objects one by one so they are counted, but passing an array whole as a parameter treats it as a single object.

'[1,2,3] | Measure-Object            -> ' + (1,2,3 | Measure-Object).Count
                    'Measure-Object -InputObject @(1,2,3) -> ' + (Measure-Object -InputObject @(1,2,3)).Count
                    '@{a=1;b=2} | Measure-Object          -> ' + (@{a=1;b=2} | Measure-Object).Count
[1,2,3] | Measure-Object            -> 3
                    Measure-Object -InputObject @(1,2,3) -> 1
                    @{a=1;b=2} | Measure-Object          -> 1

The result is the same as the example in the documentation. The array is unrolled and gives 3, but the hash table is not unrolled and gives 1. To flow a hash table item by item, the documentation says GetEnumerator() has to be called.

Counterparts of head, tail, cat, awk, cut, xargs and tee

The remaining tools have a counterpart cmdlet with a similar name, or resolve into a combination of basic cmdlets of the object pipeline. The results of running them on the same app.log are collected here. head -n 2 and tail -n 2 are parameters of Get-Content.

'head -n 2   ->'
                    Get-Content .\app.log -TotalCount 2
                    'tail -n 2   ->'
                    Get-Content .\app.log -Tail 2
                    'cat type    -> ' + (Get-Content .\app.log).GetType().FullName
                    'cat -Raw    -> ' + (Get-Content .\app.log -Raw).GetType().FullName + ', length ' + (Get-Content .\app.log -Raw).Length
head -n 2   ->

                    2026-10-05 09:05:44 INFO  service stopped
                    cat type    -> System.Object[]
                    cat -Raw    -> System.String, length 532

bash head -n 2 app.log and tail -n 2 app.log return the same four lines. The difference is the return type of cat. Get-Content reads a file as an array of line strings, and -Raw is added when a single whole string is needed. The line array flows through the pipe so that ForEach-Object runs once per line. awk '{print $3}' is carried over with -split and an index, and xargs becomes ForEach-Object.

Get-Content .\app.log | Select-Object -First 3 | ForEach-Object { ($_ -split '\s+')[2] }
                    'app.log','old.log' | ForEach-Object { $_ + ' has ' + @(Get-Content $_).Count + ' lines' }
                    Get-ChildItem -File -Filter *.log | Tee-Object -Variable seen | Measure-Object | Select-Object -ExpandProperty Count

                    WARN
                    ERROR
                    app.log has 12 lines
                    old.log has 3 lines

xargs turns input into command arguments, whereas ForEach-Object receives the input object as $_ and runs a script block. tee is Tee-Object, which also has -Variable to store into a variable instead of a file. The behavior of .Count for one result and for zero results is also worth knowing.

$one = Get-ChildItem -Filter app.log
                    'one object .Count -> ' + $one.Count
                    $none = Get-ChildItem -Filter nomatch*
                    'no result is $null -> ' + ($null -eq $none)
                    '@() wrap .Count   -> ' + @($none).Count

                    no result is $null -> True
                    @() wrap .Count   -> 0

Variables and environment variables - $x does not reach child processes

The counterpart of bash export FOO=bar is $env:FOO = 'bar'. An ordinary variable $x exists only inside the PowerShell session, while an environment variable $env:Y is inherited by child processes. This split is the same as the one drawn by the presence of export in bash. The same test was run on both sides.

$ x=shell-only
                    $ export Y=exported
                    $ bash -c 'echo "x=[$x] Y=[$Y]"'
                    x=[] Y=[exported]
$x = 'shell-only'
                    $env:Y = 'exported'
                    'bash $PATH -> [' + $PATH + ']   (the PowerShell variable $PATH is empty)'
                    '$env:PATH has entries: ' + (($env:PATH -split ';').Count -gt 3)
                    'child process sees:'
                    powershell.exe -NoProfile -File C:\demo\child.ps1
                    (Get-ChildItem Env: | Where-Object { $_.Name -eq 'Y' }).Value
                    Remove-Item Env:\Y
                    'after Remove-Item Env:\Y -> [' + $env:Y + ']'
bash $PATH -> []   (the PowerShell variable $PATH is empty)
                    $env:PATH has entries: True
                    child process sees:
                    x=[] Y=[exported]
                    exported
                    after Remove-Item Env:\Y -> []

What the child process (child.ps1 prints $x and $env:Y on one line) saw was x=[] Y=[exported], the same as bash. One trap is the name. In bash $PATH is an environment variable, but in PowerShell $PATH is just an undefined ordinary variable and is empty. Read the environment variable as $env:PATH, with ; as the separator. Deleting an environment variable is Remove-Item Env:\Y, and all environment variables are listed by Get-ChildItem through the Env: drive.

  • Create values that need export as $env:name, and keep values used only inside the script as ordinary variables.
  • A name familiar from bash such as $PATH can be an empty variable in PowerShell. Do not forget the $env: prefix.
  • Environment variables can be listed and deleted like files through the Env: drive.

Who expands the wildcard - the cmdlet, not the shell

In bash, *.log is expanded by the shell into a file list before the command runs and is passed as arguments. The same input was checked in bash.

$ echo *.log
                    app.log old.log
                    $ node -e "console.log(JSON.stringify(process.argv.slice(1)))" *.log
                    ["app.log","old.log"]

PowerShell is different. about_Wildcards explains that wildcards are used with the -like operator or with any parameter that accepts wildcards, and that the help topic of each cmdlet says which parameters accept them. So an unexpanded string goes as it is to a native program.

'Get-ChildItem *.log ->'
                    (Get-ChildItem *.log).Name
                    'Write-Output *.log ->'
                    Write-Output *.log
                    'native program (node) args for *.log ->'
                    node -e "console.log(JSON.stringify(process.argv.slice(1)))" *.log
                    'cmd /c echo *.log ->'
                    cmd /c echo *.log
Get-ChildItem *.log ->
                    app.log
                    old.log
                    Write-Output *.log ->
                    *.log
                    native program (node) args for *.log ->
                    ["*.log"]
                    cmd /c echo *.log ->
                    *.log

Get-ChildItem *.log has the cmdlet interpret the pattern itself and returns the two files. By contrast, Write-Output *.log, a native program (node) and cmd /c echo received the characters *.log as they were. Since no shell expands them on their behalf, passing a file list to a native program requires obtaining the names with Get-ChildItem and passing them as arguments. The difference in who interprets wildcards has one more consequence. Square brackets are wildcard characters, so a file whose name contains square brackets is not found as it is.

'Test-Path file[1].txt              -> ' + (Test-Path 'C:\demo\t\file[1].txt')
                    'Test-Path -LiteralPath file[1].txt -> ' + (Test-Path -LiteralPath 'C:\demo\t\file[1].txt')
                    'Get-ChildItem file[1].txt (count)   -> ' + @(Get-ChildItem 'file[1].txt' -ErrorAction SilentlyContinue).Count
                    'Get-ChildItem file[[]1].txt (count)  -> ' + @(Get-ChildItem 'file[[]1].txt' -ErrorAction SilentlyContinue).Count
                    'Get-ChildItem -LiteralPath (count)  -> ' + @(Get-ChildItem -LiteralPath 'file[1].txt').Count
                    'Get-ChildItem -Filter file[1].txt   -> ' + @(Get-ChildItem -Filter 'file[1].txt').Count
Test-Path file[1].txt              -> False
                    Test-Path -LiteralPath file[1].txt -> True
                    Get-ChildItem file[1].txt (count)   -> 0
                    Get-ChildItem file[[]1].txt (count)  -> 1
                    Get-ChildItem -LiteralPath (count)  -> 1
                    Get-ChildItem -Filter file[1].txt   -> 1

about_Wildcards says that square brackets are wildcards matching a range of characters or a set of specific characters, that wildcard characters in a file or directory name must be escaped to access it, and that one way is the -LiteralPath parameter. The pattern file[1].txt matches file1.txt, so it gives 0 matches in this folder. The -LiteralPath and [[] forms found 1, and -Filter also gave 1. The same document also says that wildcard matching for filesystem items works differently from matching for strings. Finally, the behavior of -Include.

'-Include *.log alone      -> ' + @(Get-ChildItem -Include *.log).Count
                    '-Include with C:\demo\t\* -> ' + @(Get-ChildItem C:\demo\t\* -Include *.log).Count
                    '-Filter *.log             -> ' + @(Get-ChildItem -Filter *.log).Count
-Include *.log alone      -> 0
                    -Include with C:\demo\t\* -> 2
                    -Filter *.log             -> 2

Using -Include alone gave 0 matches in this folder, and appending \* to the path gave 2. When only a name pattern is used, -Filter returned the same 2. The simplest form that carries bash ls *.log over is Get-ChildItem -Filter *.log.

  • To pass a wildcard list to a native program, build the arguments yourself from the result of Get-ChildItem, because PowerShell does not expand it.
  • Access a file whose name contains [ or ] with -LiteralPath.
  • The results of -Include differed between use together with a path pattern and use alone, so for a simple name pattern -Filter is easier to predict.
  • Even for the same *, the documentation says the matching rules differ between the -like operator and filesystem items.

At the end of an object pipeline, the table seen on screen is the result of turning an object's properties into characters according to a format. When the console is too narrow at that point, columns are cut. The object used for the check has four columns and two rows with a Path value of 117 characters. The console width was 120.

At console width 120, the longest line of the file is 119 characters, while the actual length of the Path property is 117. Only a string for display went into the file; the value of the object was not stored. If you intend to do post-processing that needs the values, do not make a table: select the properties directly and export them in a data format such as CSV.

Get-ChildItem -File -Filter *.log | Select-Object Name, Length | ConvertTo-Csv -NoTypeInformation
"Name","Length"
                    "app.log","532"
                    "old.log","36"

The two forms of Out-String should also be told apart. The default form turns the whole formatted result into a single string, while -Stream makes one string per line. To pass lines to Select-String one by one, -Stream is required.

$s = Get-ChildItem -File -Filter *.log | Out-String
                    $s.GetType().Name + ', lines = ' + ($s -split "`r?`n").Count
                    $l = Get-ChildItem -File -Filter *.log | Out-String -Stream
                    $l.GetType().Name + ' of ' + $l.Count + ' lines'
String, lines = 12
                    Object[] of 11 lines

What formatting cmdlets (such as Format-Table) emit is not the original object that can be used for sorting or filtering but formatting-directive objects. For this reason Format-* is used only at the very end of a pipeline. The type of the objects produced by applying Format-Table Name to a two-item file listing, and their Name property, were checked.

$ft = Get-ChildItem -File | Select-Object -First 2 | Format-Table Name
                    ($ft | ForEach-Object { $_.GetType().Name }) -join ', '
                    'Name property on those objects: [' + (($ft | ForEach-Object { $_.Name }) -join '') + ']'
FormatStartData, GroupStartData, FormatEntryData, FormatEntryData, GroupEndData, FormatEndData
                    Name property on those objects: []
  • The table seen on the console is a display, not the values. If you need values, finish Select-Object or Where-Object before using Format-*.
  • When a wide column is needed, avoid truncation with one of Out-String -Width, -Wrap or Format-List.
  • When passing values to a file or another tool, use a data format such as ConvertTo-Csv instead of a table format.

Where bash habits fail

When options are attached out of bash habit, PowerShell blocks them at the parsing stage or the parameter binding stage. These are the results of running against a nonexistent path to check safely.

  • For a command that cannot be undone (such as Remove-Item -Recurse -Force), first run it against a nonexistent path to check only the parameter interpretation. The ls -l and rm -rf tests above were done that way.

What Could Not Be Verified

  • PowerShell 7 (pwsh). pwsh is not installed on this PC, so differences from 5.1 could not be compared by execution. Items that may change in 7, such as the && operator, the curl alias and the default encoding handling of Select-String, are not covered by the five official documents consulted and could not be confirmed.
  • bash and GNU tools on Linux. The comparison output was obtained in Git Bash on Windows (MSYS build, GNU grep 3.0), so distribution-specific behavior of grep and sort and the influence of locale could not be confirmed.
  • The position of Format-Table truncation at console widths other than 120. This run used only width 120.
  • Aliases outside the -NoProfile session on this PC. If a user profile or a module adds or overrides aliases, the list can differ.
  • Encoding handling when Select-String searches Korean text or UTF-8 files without a BOM. The practice files contained only ASCII, and the BOM-based encoding detection described in the documentation was not run.
  • Whether the sort order of Group-Object results with equal counts is always the same. Only the fact that ERROR came before WARN in one run was confirmed.
  • Performance differences on large files. The processing speed of Get-Content, Select-String and bash tools was not measured.
