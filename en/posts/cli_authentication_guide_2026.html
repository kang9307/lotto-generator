CLI Authentication Done Right: Secure Auth Design for Command-Line Tools

OAuth Device Flow, PKCE, Token Storage, API Key Handling, Refresh Strategy, and Security Pitfalls — A Practical Guide for CLI Builders and Users

2026-06-22 Dev & Infra

Why CLI Authentication Deserves Its Own Playbook

Web app authentication and CLI authentication share the same OAuth specs on paper, but the execution context is entirely different. A web app has a browser, cookies, and session storage. A CLI has a terminal. That single difference rewrites the entire authentication design. As of June 2026, tools like Claude Code, GitHub CLI, AWS CLI, and Stripe CLI are installed on millions of developer machines, each handling credentials in its own way — and when that handling is wrong, the damage is quieter and wider than a typical web XSS incident.

GitGuardian's 2026 State of Secrets Sprawl report found approximately 28.65 million hardcoded credentials in public GitHub commits in 2025 alone, with AI service key leaks up 81% year-over-year. A significant portion traces back to developers building or using CLI tools without understanding the authentication patterns specific to that environment. Getting CLI auth right at the design level prevents most of these incidents before they happen.

This guide targets two audiences simultaneously: developers building CLI tools (with selection criteria and implementation patterns) and developers using CLI tools (to understand how their credentials are handled and manage risk accordingly). My core position: security is not a trade-off against convenience. Choosing the right abstractions — PKCE, OS keychains, token rotation — delivers both.

1. The Four CLI Authentication Patterns — A Decision Map

There are four main ways a CLI authenticates with a service. Each fits a specific context, and using the wrong one in the wrong context creates security holes.

1.1 OAuth 2.0 Authorization Code + PKCE (Browser Delegation)

The CLI opens a local TCP port (e.g., localhost:8484) and launches the browser to an Authorization endpoint configured with that port as the redirect URI. The user logs in via the browser, the auth server returns a code to the local port, and the CLI exchanges it for access and refresh tokens.

PKCE (Proof Key for Code Exchange, RFC 7636) is the essential component here. A CLI is a public client — there is no safe way to embed a client_secret in a distributed binary. PKCE solves this: the CLI generates a cryptographically random code_verifier per session, sends its SHA-256 hash as the code_challenge, and proves same-session ownership at exchange time by submitting the original verifier. An intercepted code alone cannot be exchanged for a token.

This pattern fits when: the user is at the same machine, a browser can be opened, and the CLI can bind a local port. GitHub CLI's gh auth login uses this approach — fast, no polling, high phishing resistance.

1.2 OAuth 2.0 Device Authorization Grant — RFC 8628 (Headless Delegation)

Designed for environments where opening a browser is impossible: SSH remote sessions, containers, TV/embedded devices. The CLI requests a device code from the auth server. The server returns a device_code (internal identifier), a user_code (short human-readable code), and a verification_uri. The CLI prints "go to this URL on any device and enter this code," then polls the token endpoint at the prescribed interval while the user completes authentication in a separate browser.

The security premises of this flow: the user_code expires quickly, the verification_uri enforces HTTPS, and the client respects the interval field to avoid DoS-ing the auth server. Claude Code uses this pattern for its authentication flow.

1.3 API Keys (Automation and Service Accounts)

Appropriate for CI/CD pipelines, cron jobs, and service accounts where interactive login is structurally impossible. Simple and universally supported — but if issued without expiry, the blast radius of a leak is unbounded. For local development, OAuth flows are significantly safer: access tokens typically expire in one hour, while API keys remain valid until explicitly revoked.

1.4 Workload Identity / Instance Credentials (Cloud Environments)

AWS IMDSv2, GCP Workload Identity Federation, Azure Managed Identity — the cloud infrastructure grants short-lived tokens to the machine itself. In CI/CD, GitHub Actions OIDC tokens combined with AWS assume-role eliminate the need to inject long-lived secrets entirely. This is the most recommended CI/CD pattern as of 2026.

2. PKCE Implementation — What Gets Missed at the Code Level

Treating PKCE as "just append code_challenge" misses several critical details.

2.1 Generating code_verifier Correctly

RFC 7636 specifies the verifier must be a cryptographically secure random 43–128 character URL-safe string. In Python: secrets.token_urlsafe(96). In Node.js: crypto.randomBytes(96).toString('base64url'). Math.random() and uuid() are not cryptographically secure. Generate a new verifier per session — reuse allows pattern learning by an attacker.

2.2 S256 Only — Never Plain

code_challenge_method=plain sends the verifier directly as the challenge, making it vulnerable to MITM between the CLI and auth server. Always use S256 (SHA-256 of the verifier, base64url encoded). The OAuth 2.1 draft mandates S256 and deprecates plain. If an auth server only supports plain, that server itself is misconfigured.

2.3 state Parameter for CSRF Defense

Without a state parameter, the redirect receiver is open to CSRF. The CLI generates a cryptographic random state at Authorization request time and validates it matches at redirect receipt. Another tab or an attacker-crafted redirect could otherwise inject a code.

2.4 Graceful Fallback When Local Port Binding Fails

Port 8484 may already be in use. The CLI should try multiple ports in sequence or gracefully fall back to device flow on failure. Silent failure where the port doesn't open and authentication hangs invisibly causes users to blame themselves — poor UX and a support burden.

3. Token Storage — Where You Put It Is 90% of the Security

A perfect authentication flow becomes meaningless if the resulting token is stored insecurely. Here is an honest risk comparison by storage location.

3.1 OS Encrypted Credential Store — First Choice

macOS Keychain, Windows Credential Manager, and Linux Secret Service (D-Bus, libsecret/gnome-keyring) are OS-provided encrypted stores. Their shared properties: OS-level encryption (macOS can use Secure Enclave), ACL-based access control per application, and optional hardware security module integration.

Rather than writing platform-specific code directly, use language-level abstraction libraries: zalando/go-keyring for Go, keyring for Python, keytar for Node.js. GitHub CLI delegates to such a library rather than implementing its own crypto. That is the right approach.

3.2 File-Based Storage — Conditionally Acceptable

In environments where a keychain daemon is unavailable (minimal containers), file storage is acceptable with strict conditions: file permissions must be enforced at 600 (owner read/write only), the token file directory must be in .gitignore, and encryption — at minimum passphrase-based — should be considered. AWS CLI's ~/.aws/credentials follows this pattern. Convenient, but always at risk of being included in backups or accidentally committed.

3.3 Environment Variables — CI/CD Only

Environment variables are visible in process listings (/proc/PID/environ), auto-inherited by child processes, and can be captured by crash reporters. Long-lived API keys in environment variables for local development flow into more places than developers realize. In CI/CD, they represent short-lived injected values from a secrets store — a different risk profile.

3.4 What You Must Never Do

Hardcoding in source is the absolute prohibition. Even unintentionally, once TOKEN=abc123 appears in a commit, it lives in git history permanently. Other common failures: .env files without gitignore, tokens logged to output (including debug logs), tokens passed as command-line arguments visible in ps aux.

4. API Key Handling — Where 90% of Mistakes Happen

Practical guidelines for building or using CLIs that rely solely on API keys.

4.1 Key Design Principles

Issue API keys with minimum necessary privileges. "One admin key for everything" is convenient to the exact degree it is dangerous. A read-only workload should not use a key that can write or delete. Keys must have expiry dates — 90-day rotation is the industry recommendation. A key without expiry has unlimited blast radius on leak. Where possible, restrict keys by IP range or resource scope.

4.2 Incident Response When a Key Leaks

The first action when a key leaks is revocation, not file deletion. A committed secret removed by git rm is still findable via git log -S 'KEY_VALUE'. Even after git history rewrite, clones, forks, caches, and third-party scanners may retain it. The correct sequence: revoke immediately, issue a new key, then audit logs for requests made with the exposed key.

4.3 Pre-Commit Scanning as Preventive Infrastructure

Adding a pre-commit scanner (GitGuardian, truffleHog, detect-secrets) to the team's standard pre-commit configuration catches secrets at commit time. Adding a detect-secrets hook takes five minutes. This single defense eliminates the most common class of CLI credential incidents.

5. Token Refresh — The Intersection of UX and Security

Short-lived access tokens are good for security. Forcing users to re-login on every command makes a tool unusable. Refresh tokens resolve this tension.

5.1 Transparent Renewal

The CLI checks token expiry before API calls or detects a 401 response and silently uses the refresh token to obtain a new access token. The user never sees this. Re-authentication is only triggered when the refresh token itself expires or has been revoked. Implementation note: parallel requests can trigger simultaneous refresh attempts. Use a mutex or single-renewal goroutine pattern to prevent races.

5.2 Refresh Token Rotation

On each use, the server issues a new refresh token and revokes the old one. If the old refresh token is used again, the server treats it as a theft signal and invalidates the entire session. This "refresh token rotation with reuse detection" is natively supported by Auth0, Okta, and Keycloak.

5.3 Practical Token Lifetime Values

Access tokens: 1 hour (industry standard). Refresh tokens: 30–90 days with rotation. With rotation, active users maintain indefinite sessions while inactive ones auto-expire. This simultaneously achieves "seamless login" convenience and "bounded stolen token lifetime" security.

6. Security Pitfall Catalog — Patterns That Actually Fail

These are the flawed patterns I check for when auditing CLI tools in practice.

6.1 client_secret Embedded in the Binary

A CLI is a public client. Extracting a client_secret from a distributed binary using the strings command takes ten seconds. CLIs must not use client_secret. PKCE is the solution. If an auth server requires client_secret from a public CLI client, that server has a design flaw.

6.2 Tokens in Log Output

Debug mode logging full HTTP request headers prints Authorization: Bearer {token} verbatim. Logs are typically written to files and forwarded to log aggregation systems. Any token output must be masked (Bearer sk-...XXXX).

6.3 Stale Tokens Retained After Expiry

Expired tokens left in local storage can be read by an attacker with access to the machine. Technically, the server will reject them — but timestamp manipulation or clock drift can create reuse opportunities. Expired tokens should be overwritten immediately on renewal; on logout, they should be explicitly deleted.

6.4 Ignoring the Device Code Polling Interval

RFC 8628 specifies an interval field (default 5 seconds) and a slow_down response when polling too frequently. Ignoring this imposes unnecessary load on the auth server. Implement exponential backoff and increment the interval by 5 seconds on each slow_down response.

6.5 No Redirect URI Validation

Auth servers that accept redirect URIs without pre-registration or that allow wildcards (http://localhost:*) allow attackers to intercept codes on alternate ports. Exact redirect URI matching must be enforced in auth server configuration.

7. CLI Authentication in CI/CD — Different Rules

Many teams copy local development patterns into CI/CD and create problems. The two contexts require different approaches.

7.1 OIDC Tokens to Eliminate Long-Lived Secrets

GitHub Actions OIDC tokens connected to AWS/GCP/Azure trust relationships eliminate the need to store long-lived access keys in repositories. Each workflow run receives a platform-issued short-lived token; the cloud provider verifies the signature and issues temporary credentials. GitGuardian's finding that 59% of compromised credential machines in 2025 were CI/CD runners makes this shift urgent.

7.2 Environment Separation

Without dev/staging/production key separation, test pipelines can touch production data. Maintain separate secret stores per environment and configure automatic injection of the correct credentials based on the pipeline's execution context.

8. CLI Authentication in the Age of AI Agents — New Variables

A new variable specific to 2026: AI coding agents calling CLI tools programmatically has grown dramatically.

Claude Code, GitHub Copilot agent mode, and Cursor call tools like gh, aws, and stripe inside agent loops. These agent subprocesses inherit environment variables — meaning any API key in the environment flows into the agent's execution context. If the agent runs third-party code or calls external tools via MCP servers, credentials may cross trust boundaries.

Two defense patterns: first, isolate the agent's CLI credentials to minimum-privilege tokens scoped to exactly what the agent needs. Second, use the apiKeyHelper pattern — the agent requests a fresh short-lived token on demand from a helper script rather than holding a long-lived key. Claude Code natively supports this pattern. Short-lived tokens bound to specific agent sessions minimize blast radius even if they leak.

9. Conclusion — Three Actions for Today

CLI authentication is a sequence of choices: which flow to use, where to store credentials, how to renew them. At each decision point, "convenient" and "secure" can diverge. My core argument: the right abstractions — PKCE, OS keychains, token rotation — make convenience and security converge. Retrofitting security after the fact always costs more than designing it in from the start.

9.1 Audit Where Your Current CLI Tools Store Tokens

Check where the CLI tools you use daily store their tokens. If there is a JSON file under ~/.config/tool/, check its permissions. Verify 600 with ls -la and confirm it is in .gitignore. If OS keychain integration is available, consider migrating to it.

9.2 Add Pre-Commit Secret Scanning to Your Team Standard

Adding a detect-secrets or gitleaks hook to your pre-commit configuration takes five minutes and eliminates the most common class of CLI credential incidents. Make it a habit even on personal projects.

9.3 If Building a New CLI Tool, Design PKCE In From the Start

Do not add authentication later. Define the flow choice (PKCE vs Device Flow), token storage (OS keychain library), and refresh logic at initial design time. And embedding client_secret in a binary is a design error, not a permissible "for now" convenience.
