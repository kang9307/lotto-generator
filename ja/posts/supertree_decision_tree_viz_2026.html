supertree - 決定木をズーム・パンで探索するインタラクティブ可視化ツール

MLJAR製Pythonライブラリで見る説明可能なAIの次のステップ - plot_tree・graphviz・dtreevizと何が違うのか

2026-07-03 開発・インフラ

序論: 静的画像で描いた木を、これからはインタラクティブに読み解く

決定木(decision tree)は機械学習の中でも最も古くから愛されてきたホワイトボックスモデルの一つだ。回帰でも分類でも、予測の過程を人間の目で追える点が最大の武器である。問題は、その木を実際に「見る」方法だ。これまでPythonのエコシステムで決定木を可視化する標準的な手段といえば、sklearn.tree.plot_tree()やGraphvizで静的画像を1枚書き出すことだった。ノードが数十を超えるだけで画像は手に負えないサイズに膨れ上がり、結局はキャプチャして切り出したり、PDFに書き出して拡大したりするしかなかった。

2026年7月時点、この不便さに正面から挑むPythonライブラリsupertreeがGeekNewsを通じて改めて注目を集めている。AutoMLツールmljar-supervisedで知られるポーランド企業MLJARが手がけたオープンソースプロジェクトで、決定木をJupyterノートブック上でズーム・パン・ノードの折りたたみが可能な、生きたウィジェットとしてレンダリングする。本稿はsupertreeの機能をそのままなぞる紹介記事ではなく、決定木解釈(XAI)ツールとして何が実質的に変わったのか、どこまでが本当の価値でどこからが誇張なのかを検証する分析である。

1. supertreeとは何か

1.1 基本概要

supertreeはGitHubのmljar/supertreeリポジトリで公開されているApache License 2.0のオープンソースライブラリだ。pip install supertreeでインストールし、scikit-learn・XGBoost・LightGBM・ONNXで学習した木構造モデルを受け取って可視化する。2026年7月時点でGitHubスターは600件ほど、最新リリースは2026年6月上旬に登場したv1.0.0で、正式なメジャーバージョン1.0にちょうど到達したところだ。リポジトリの言語構成を見るとJavaScriptが80%以上を占めており、これはレンダリングの核心がPythonの計算処理ではなく、ブラウザ上で動くD3.jsベースの可視化エンジンにあることを示している。

1.2 コア機能

機能そのものはシンプルにまとめられる。木を拡大・縮小(ズーム)し移動(パン)させながら、下位のサブツリーを折りたたんだり展開したり(collapse)できる。さらに特定のサンプルがルートからリーフまでどの経路をたどったかを追跡することも可能だ。GitHubリポジトリはこれを短く「Zoom, pan, collapse」と表現している。この4つの操作だけで、静的画像にはできなかったことが可能になる。深さ8〜10の木をまず縮小した全体像として眺め、興味のある枝だけを展開・拡大するという探索的なワークフローである。

1.3 実行環境

Jupyter Notebook、JupyterLab、Google Colab、VS Code、そしてMLJAR自身の製品であるMLJAR Studio上で動作すると案内されている。HTMLをレンダリングできるノートブック環境であれば、おおむね互換性があるということだ。別途サーバーやダッシュボードを用意する必要がなく、コードセル1つでウィジェットが立ち上がる点が導入のハードルを下げている。

2. 決定木の解釈がなぜ重要か - 説明可能なAIの入り口

2.1 ホワイトボックスモデルの位置づけ

説明可能なAI(XAI)の議論において、決定木はほぼ常に「設計上解釈可能(interpretable-by-design)」なモデルの代表例として挙げられる。線形回帰・ロジスティック回帰と並び、予測ロジックを事後近似ではなくモデル構造そのものから直接読み取れる数少ないモデルの一つだ。深層学習や大規模アンサンブルのように、SHAPやLIMEといった事後説明手法を追加で組み合わせる必要があるモデルとは出発点が異なる。

2.2 しかし「見る方法」が解釈可能性を蝕む

ここで筆者が強調しておきたい点がある。決定木が構造的に解釈可能であることと、その構造を人間が実際に快適に読み取れることは別の問題だ。木が深くなり、ノードが増えるほど、静的画像は実質的に読めない図になってしまう。理論上は「ホワイトボックス」なのに、実務では再び「読みにくい箱」になってしまうという逆説である。supertreeのようなツールが存在する理由は、まさにこの隙間 ― モデルの理論上の解釈可能性と、人間が実際に消化できる解釈可能性との間のギャップを埋めることにある。

2.3 規制・信頼・監査の観点

金融の与信審査、医療診断の補助、採用スクリーニングのように判断根拠の説明が求められる領域では、モデル選定の段階から決定木やルールベースモデルが優先的に検討される。こうした領域で実際に木を検証する人は、データサイエンティストだけでなく監査・コンプライアンス担当者やドメイン専門家であることが多い。彼らにコードを読み込ませるより、ブラウザ上でズーム・パンしながら直接探索させる方がはるかに現実的である。

3. 既存の可視化ツールと何が違うのか

3.1 plot_tree - 最も手軽な既定値、しかし静的

scikit-learn内蔵のplot_tree()は、追加インストールなしでmatplotlibだけで動く最も手軽な選択肢だ。ただしノードごとに閾値・ジニ不純度・サンプル数・クラス分布をテキストで詰め込むため、深さが増すと文字が重なり図全体が読み取りにくくなる。出力は1枚の固定されたPNG/SVGであり、大きな木では事実上、拡大鏡なしでは見られない図になってしまう。

3.2 Graphviz(export_graphviz) - 柔軟だが依然として静的

Graphvizはdotファイルを直接操作してスタイルを細かく調整でき、レイアウトも自動で組んでくれるという利点がある。しかしシステムにGraphvizバイナリを別途インストールする必要があり、出力は依然として静的画像だ。木を探索するには結局、画像ビューアの拡大・縮小機能に頼るしかない。

3.3 dtreeviz - 情報密度は最高、インストールは難しい

dtreevizは3つの中で最も情報量が豊富だ。各分岐ノードにクラス別の分布を重ねたヒストグラムを表示し、特定のサンプル1つがたどった経路を木全体の中で太線でハイライトしてくれる。「なぜこのサンプルがこのクラスに分類されたのか」を視覚的に説明する力は3つのツールの中で最も強い。ただしこれも出力は静的画像であり、Graphviz依存とPATH設定の問題によりインストールでつまずく事例が繰り返し報告されている。

3.4 supertreeの実質的な差別化ポイント

3つのツールがいずれも「1枚の画像をより美しく、より情報密度高く描く」競争をしていたとすれば、supertreeはまったく別の軸で動いている。出力そのものが画像ではなく、ブラウザ内で状態を保持するウィジェットである点だ。大きな木をまず縮小した全体ビューで見て、興味のある枝だけを展開・拡大し、また折りたたんで全体構造に戻ることができる。dtreevizの情報密度やGraphvizのスタイルの柔軟性をそのまま上回るわけではないが、「大きな木を実際に探索可能な状態で維持する」という点では、3つのツールが埋められなかった空白を埋めている。

ツール出力形式インストール情報密度大規模ツリー対応

4. モデルデバッグ・教育・ステークホルダーコミュニケーションでの実務的価値

4.1 デバッグのシナリオ

筆者が木ベースのモデルをチューニングしていて最ももどかしい瞬間は、特定のリーフがなぜ奇妙な予測を返すのかを逆にたどるときだ。静的画像では、そのリーフに至る経路を探すために画像を何度も保存し直して拡大しなければならなかった。インタラクティブなウィジェットであれば、問題のあるサンプルの経路を追跡してそのリーフまで直接掘り下げられるため、過学習した分岐やデータリークが疑われる条件をはるかに素早く見つけられる。

4.2 教育での活用

決定木は機械学習入門講義で最初に登場するモデルの一つだ。学生が自ら木を拡大・縮小しながら「なぜこの条件で左に分岐するのか」を目で追えれば、静的なスライド1枚よりもはるかに早く概念が身につく。ノートブック1つで実習と説明が同時にできることも、講義資料作成の負担を軽くしてくれる。

4.3 非開発者のステークホルダーとのコミュニケーション

プロダクトオーナーやドメイン専門家に「このモデルがなぜこのような判断を下すのか」を説明する場面では、コードやSHAP値の表よりも、リアルタイムで操作できる木の図の方がはるかに説得力がある。ただしこの利点は木があまり深くない場合に成り立つ。深さが過度に大きければ、非開発者にとっては結局「複雑な図」でしかないという点は明確にしておく必要がある。

5. 木ベースアンサンブル(ランダムフォレスト・XGBoost)解釈における意義と限界

5.1 アンサンブルはなぜ解釈が難しいのか

ランダムフォレストは数百本、XGBoostは数十〜数百ラウンドのブースティング木を合算して予測する。木1本1本は解釈可能でも、その合計はもはや人間が手で追える対象ではない。これが木ベースのアンサンブルが「性能は良いが解釈は深層学習並みに不透明だ」と評される理由である。

5.2 supertreeで個々の木を見ることの意味

supertreeはアンサンブル内の個々の木を1本選んでインタラクティブに表示できる。これは明らかに有用だ ― 特定の木がどのような分岐を学習したかを把握したり、木同士の構造がどれほど多様かを目で確認したりする用途には適している。しかしここで明確にしておくべき限界がある。個々の木を1本見ることは、アンサンブル全体の意思決定を説明することにはならない。最終的な予測は数百本の木の投票または加重和であり、木1本の分岐構造だけでは「なぜこのサンプルがこのように予測されたのか」に答えることはできない。

5.3 SHAP・LIMEとの役割分担

アンサンブル全体の予測根拠を説明するには、SHAP(シャープレイ値に基づく)やLIME(局所近似)のようなモデル非依存の事後説明手法が必要になる。筆者が整理する役割分担はこうだ ― supertreeは木の構造を理解し個々の木をデバッグするためのツールであり、SHAP・LIMEはアンサンブル全体の特定の予測1つを説明するためのツールである。両者は競合関係ではなく補完関係にあり、「アンサンブルも解釈可能になった」というふうにsupertreeを過大評価することは避けるべきである。

6. 実務導入時の考慮事項

6.1 いつ有用か

単一の決定木を実際の意思決定根拠として使う場合(与信審査ルール、トリアージルール)、木ベースモデルの講義・ワークショップ、ランダムフォレストから代表的な木をいくつか選んで構造を点検するデバッグセッションでは、supertreeは確実に時間の節約になる。

6.2 限界

いくつかは明確にしておく必要がある。第一に、極端に深い木(完全に成長した枝刈りなしの木など)は、インタラクションがあっても結局人間が一度に消化できる情報量を超えてしまう。第二に、ブラウザ上でD3.jsを使って多数のノードを描画する仕組み上、木の規模が大きくなるとレンダリング性能が低下する可能性がある(公開されたベンチマーク数値は確認できていない)。第三に、supertreeはあくまでノートブック内の探索ツールであり、本番監視ダッシュボードや自動化されたモデル文書化ツールではない。v1.0.0が2026年6月に登場したばかりの比較的若いプロジェクトであることも踏まえておくべきだ。

6.3 導入ガイド

筆者が勧める手順はこうだ。まず、すでに使っている木ベースモデルのノートブックにpip install supertreeを1行加え、最小限の例で感覚をつかむ。次に、デバッグや発表資料が必要な場面でplot_treeの代わりに使ってみて、実際に時間が短縮されるかを確認する。アンサンブル全体の説明が目的であればSHAPを主力に据え、supertreeはその中の個々の木を覗き込む補助ツールとして位置づけるのが正確な使い方である。

結論 - 小さなツールだが、XAIワークフローの隙間を埋める

supertreeは決定木のアルゴリズム自体を変えるものではない。変わるのは「その木をどう見るか」だけだ。それでもこの変化に意味があるのは、決定木最大の強みである解釈可能性が、実務では静的画像の限界によってしばしば無駄にされてきたからである。2026年7月時点でv1.0.0にようやく到達したばかりの若いプロジェクトであり、アンサンブル全体を説明してくれる万能の解決策でもないが、「決定木を実際に探索可能にする」という狭く明確な問題の1つは確実にうまく解いている。単一の木を扱う機会や、アンサンブルの中の個々の木を点検する必要があるなら、ノートブックに1行加えてみる価値は十分にある。
