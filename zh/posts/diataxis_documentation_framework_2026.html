文档没人读不是因为篇幅不够 - 用 Diátaxis 分成四类的判断标准与实操

分开四类的那两个提问,要问的是句子而不是文档

2026年8月4日 开发/基础设施

引言:文档明明有,却总有人问有没有文档

新人上手文档有四十页,API 参考由代码自动生成,内部维基上连架构讲解都写了。可是这周入职的同事在同一个地方卡了两天,三年经验的工程师最后还是跑来群里问。他们不是没读。他们读了,但没找到自己需要的那一句。

到这一步通常得出的结论是「文档还要再多写点」。往这个方向走,下个季度会变成六十页,同样的问题照旧。因为缺的从来不是篇幅。

真正的问题是性质不同的四类文字挤在同一篇文档里。把一份常见的「安装指南」拆开看,四类通常都在:照着做就行的操作步骤、生产环境推荐的配置、全部选项清单,还有当初为什么设计成这样。需要其中每一样的是不同的人,挤在一页上就四个人一起落空。第一次来的人卡在推荐配置那一段,只想确认一个数值的人要划过十二行操作步骤。

Diátaxis 是一套给出这四类分界线的框架。作者是 Daniele Procida,以 CC BY-SA 4.0 发布在 diataxis.fr。它把文档分成教程、操作指南、参考和说明四类,而这套框架的全部力量在于:划分依据不是「内容的种类」,而是读者打开这篇文档那一刻所处的状态。

本文讲五件事:四类各自预设的读者状态,混在一起时出现的症状及其成因,判定一句话该归哪一类的操作步骤,只有一个 README 的仓库该如何折中,以及这套框架在哪里会变得牵强。

句子本身该怎么写,也就是限制词汇、统一句式那一侧,是另一个问题,已经在强制用受控语言写技术文档会改变什么里讲过。本文讲的是文档该怎么分。两者不互相替代。先分类,再对每一类强制相应句式,这个顺序才顺。

1. 四类各自预设的读者状态

先要清掉一个误解:四类不是按题材分的。「认证」这个题材可以出现在四类里的每一类。同一个事实也一样,比如重试间隔默认1000毫秒。在参考里它就是那个数值,在教程里通常压根不提,在操作指南里它是特定情形下要改的一个动作,在说明里它是选定这个数值的理由。分开的不是事实,而是读到这个事实的读者的状态。

类别读者此刻读者要的东西失败时说的话标题示例
教程第一次接触,连自己不懂什么都不知道一次完整走通的成功体验「照着做第三步就报错」做出你的第一个通知机器人
操作指南会用,眼下卡在一个任务上穿过这个情形的路径「我这个情况不是这一种」在企业代理后面发送通知
参考正在干活,来查一个数值准确的事实,立刻拿到「默认值最后还是去翻源码」环境变量完整清单
说明没在干活,想弄明白来龙去脉脉络、理由、方案比较「为什么这么做没人说得清」为什么要放两个队列

1.1 教程:是一堂课,不是一份说明

官方定义很短。教程是一堂课,是学习者在老师引导下动手做着学的一段经历。目的不是把活干完,而是让学习发生。驾驶课的目的不是从甲地开到乙地。

由此引出四条要求。你让学习者做的练习必须有意义(要有成就感)、能成功(必须能走到终点)、合逻辑(路径说得通)、有用地完整(该熟悉的动作、概念和工具都得碰到一次)。

接着是这一类里最出名的一句话:教学的第一条规则就是「别想着去教」。老师会有一种把知识传出去的焦虑,而一旦向这种焦虑投降、用讲解来教,学习体验本身就毁了。官方文档把打断教程的诱惑归为四种:抽象与概括、讲解、选项、信息。

换成实务指标就是:教程的成功指标不是「读者学到了什么」,而是「有没有走到最后」。学到什么无法测量,走完能测量。如果你有内部教程,让新人做一遍,只记录他在第几步停下来,要改的地方就出来了。另外教程是四类里维护成本最高的。别的文档可以局部修改,教程必须从头到尾是一个连贯的故事,所以改一步会连锁改到后面全部。

1.2 操作指南:菜谱

操作指南面对的是已经熟练的人。菜谱这个类比很准。菜谱不教做菜。做过几百次同一道菜的厨师,为了做准确照样看菜谱。反过来,把菜谱给一个从没下过厨的人,他一定失败,因为菜谱不是烹饪课的替代品。

官方文档在这一类里最强调的规则是「从用户视角写,而不是从机器视角写」。它举的反例很扎心:「要关水,请顺时针拧水龙头。」形式上是指引,实际上没有任何价值。在这个领域干活的人本来就知道,而且它和目的是断开的。用户真正需要知道的更接近为了某个用途,水要开多大、流多久。

企业文档里最常见的破损正在这里:按功能单位写操作指南。「调用用户注册 API」是机器的动作,不是人的任务。「为新商户完成入驻」才是任务,里面三个 API 只是材料。把自动生成的清单丢进操作指南目录,文档数量涨了,读的人是零。

还有一个范围感。官方文档明确说「怎么做一个 Web 应用」不是操作指南,因为它指的不是具体目标或问题,而是一整片技能领域。操作指南要有起点和终点,并且实际可用性比覆盖完整更重要。留出让读者接到自己工作上的余地,好过把所有情况罗列一遍。

1.3 参考:海图,以及中立

参考是用来查的文档,不是用来读的文档。官方用来形容它的词是严苛:不能有疑义和含糊,必须完全权威。而且中立。海图这个类比很好。同一张海图,航海员用来规划航线,调查事故的法官也用得上。海图不关心读者打算干什么。

核心规则是「描述,并且只描述」。麻烦在于中立的描述并不是人类自然的表达方式。自然的是解释、指示、讨论和发表意见,这四样全都和参考的要求冲突。光是描述常显得太单薄,于是别的东西就往里钻,而官方给的处方是:不要写进去,链接出去。

还有一条结构规则:文档的结构应当映射产品的结构。如果某个方法属于某个类,而这个类属于某个模块,那么文档里也应该看得见同样的关系。地图之所以有用,正因为它像地形。示例是允许的:给一条命令配一个用法示例,既能帮助理解,又不至于滑进解释或指示。

这里最常被误解的一点。参考里禁止的是指示、解释和意见,不是警告。「必须使用 a」「除非满足 c,否则不得应用 b」这类句子,官方文档把它们列为参考的正常语法,性质等同于食品包装上的「可能含有小麦」。条件明确的禁止接近事实,条件模糊的推荐接近判断。要守的就是这条线。

1.4 说明:可以在浴缸里读的那一类

官方文档形容说明的那句话,一下子把这一类的性质点透了:它是四类里唯一一种在浴缸里读也说得通的文档。不坐在产品前面也读得下去,和眼下这份活也没有直接关系。

说明是允许回味的文字。它的视角比另外三类更高更宽,既不是操作指南那种读者视线的高度,也不是参考那种贴着机器的近景。它回答的是「能跟我讲讲这个吗」。

  • 建立连接。连到题材之外的东西也可以。理解来自一张网,而不是一堆孤立的事实
  • 给出脉络和背景。设计决策、历史原因、技术约束,回答「为什么是这样」
  • 是「关于」某个题材在说话。标题前面应该能加上「关于」两个字,比如「关于用户认证」
  • 允许观点和立场。这是四类里唯一一处观点是正当的地方。官方的要求还更进一步:说明可以而且必须讨论替代方案和反例
  • 把边界守窄。说明有吸走别的东西的性质。为了把题材讲全而把操作步骤和技术规格拉进来,说明本身会糊掉,而那些东西又从它们该在的位置上消失了
  • 名字不一定叫「说明」。Discussion、Background、概念指南、专题都可以

说明是四类里最不急、也最常缺席的一类。不急不等于不重要。没有说明,实践者的知识就停留在碎片状态,而靠碎片干活的人总是在不安中工作。而且说明往往不是整体缺席,而是以小块的形式散落在别的文档里——教程第三步里三句话,参考脚注里两句话。

2. 两个坐标轴 —— 地图给会议室用,罗盘才是干活用的

介绍 Diátaxis 时必然出现的那张 2×2 图,这套框架称之为地图,并且在地图之外另设了一个罗盘。这个区分在实务里是决定性的。地图告诉你四类之间是什么关系,但不会告诉你该做什么,因为地图本身就是参考。

坐标轴有两个。

  • 行动还是认知。教程和操作指南处理读者做的事,参考和说明处理读者知道的事
  • 习得还是应用。教程和说明服务于技能的习得,也就是读者的学习;操作指南和参考服务于技能的应用,也就是读者的工作
如果这段内容……服务于读者的……那它属于
告知行动技能的习得(学习)教程
告知行动技能的应用(工作)操作指南
告知认知技能的应用(工作)参考
告知认知技能的习得(学习)说明

用罗盘只需要两个提问:行动还是认知?习得还是应用?答完类别就定了。官方对这件工具的形容是「平淡得出奇」。

可这件平淡的工具里装着本文的核心。官方文档明确说,这两个提问既要用在整篇文档上,也要凑近了用在句子和词的层面上。绝大多数团队在这里走偏:只看地图,给某一页贴上「这是教程」的标签,建四个目录,然后就完了。标签修不好任何东西。真正改变文档的,是按段落逐段拿罗盘去比对,比对的结果是某些段落搬到别的文件里去。

3. 混在一起会出现的症状 —— 诊断表

官方文档说,越过或模糊地图上的这些边界,「正处在文档领域大量问题的核心位置」。听上去抽象,实际上会以非常具体的症状表现出来。从症状倒推成因的这张表,在实务里更好用。

表面症状什么混进了哪里处方
新人在某一步卡住半小时教程里混进了说明压成一行,链到说明文档
「照着做了但做不出来」反复出现教程里混进了选项和分支只留一条路径,其余移到操作指南
操作指南写了三十页操作指南里混进了教程第一行声明前置能力,砍掉前半段
操作指南清单和 API 清单一模一样操作指南是按功能写的按人的任务单位重新归并
最后还是翻源码去确认默认值参考不完整或表述含糊用表格补齐取值、类型、默认值、约束
连参考里的事实也被怀疑参考里混进了无条件的推荐推荐移到操作指南,只留条件明确的警告
架构文档里贴着配置样例说明吸走了参考数值归参考,说明里只留理由
「为什么这么做没人说得清」说明以碎片散落着把碎片收拢成一篇说明文档
从搜索进来每次都落到不对的页标题不显示类别套用第 7 节的标题规则

3.1 为什么偏偏是说明混进教程

这是发生最频繁、也最难改掉的一种。官方文档把成因归到老师身上:说明是老师最难抵抗的诱惑,连经验丰富的老师也很难接受「学生的学习并不依赖讲解」这个事实。人一旦想通某件事,就会用抽象把它握住,并且想把这个抽象原样递给别人。

企业文档还要多一层成因:写文档的人就是造这套系统的人。造的人想为自己做过的决策辩护,于是它出现在教程第三步里,变成「这一块本来打算用 A,后来因为并发问题改成了 B」。对作者来说这是最重要的一段,对今天第一次安装的人来说,它是打断心流的障碍物。

改法不是删掉,而是搬走。教程里只留「这里我们用 HTTPS,因为更安全」这种最低限度的一句,其余链到说明文档。说明只有在读者想要的那一刻才是恰当的。那一刻不是由写文档的人来定的。

3.2 推荐混进参考会削掉什么

假设页面上写着:「timeout:默认30秒。生产环境推荐5秒。」一行里并排放着事实和判断。读者会立刻追问是哪种生产环境。流量多大?上游什么性质?参考里没有答案,而确认了没有答案的读者会连前面那个「30秒」也开始怀疑。判断吃掉了紧挨着它的事实的可信度。

官方文档用食品包装来比这件事。来看营养信息的人不想撞见意见、猜测、指示和解读,而把菜谱或宣传语混进去可能是字面意义上的危险。食品标示通常受法律规范正是这个原因,同样的严肃性也应当适用于技术参考。

处方很简单:不是删掉推荐,而是把它挪到能写条件的地方。挪到操作指南,条件就升进标题里:「在高并发环境下调整超时」。在参考里毫无价值的那个「推荐」,变成了一篇仅凭标题就能筛选读者的文档。

4. 一句话该送到哪里 —— 判定步骤

这才是真正的工作。按页贴标签半小时就能做完,而且什么都不会改变。改变发生在段落被搬走的时候。

  1. 随便打开哪一页都行。不要去搜罗有问题的文档。刚才在看的文件、眼前开着的页面就可以。官方的工作方法明确推荐这种做法
  2. 对每一段抛出两个提问。这一段讲的是行动还是认知?读者是在学习还是在工作?
  3. 把类别与本页主类别不同的段落标出来。做到这一步,大多数页面会露出自己混着两三类
  4. 标出来的只搬走一个。想全搬当天就做不完,留下一篇拆了一半的文档
  5. 搬完就提交。把这一步算作完成。下一个下次再说

第 2 步拿不准时,有几条辅助规则。罗盘不涵盖这部分,所以在实务里单独立起来会让判定变快。

  • 「删掉这句,读者还能不能执行下一步?」不能就是行动,能就是认知
  • 「读者此刻是不是坐在键盘前?」是就是应用(工作),不是就是习得(学习)
  • 以「为什么」开头的句子几乎永远是说明。很难找到例外
  • 「要做到 X 就……」是操作指南,「X 是 Y」是参考。光看句式就分得差不多
  • 「先做 X,再做 Y」两边都可能。只有这时候才真的需要第二个提问
  • 出现「通常」「一般」「推荐」就不是参考。那是把条件藏起来的判断
  • 出现「可以这样也可以那样」就不是教程。选项会让学习者停住

实际比对一下是这样分的。

句子行动/认知习得/应用类别
「现在执行 npm run dev。稍后 3000 端口会有响应」行动习得教程
「如果走企业代理,先设置 HTTPS_PROXY」行动应用操作指南
「retryDelay 的默认值是 1000(毫秒)」认知应用参考
「之所以选指数退避,是因为早期版本里重试会挤在一起」认知习得说明
「生产环境下这个值最好设到 5000 以上」行动应用操作指南(不是参考)
「该 API 自 v3 起废弃,v4 中移除」认知应用参考

最后两行挨着放是有原因的。废弃预告是事实,所以属于参考;「所以现在就迁移吧」是动作,所以属于操作指南。差一个分句,类别就跨过去了。要看到这个分辨率,文档才会真的改变。

5. 拆分既有文档的顺序 —— 别从建四个目录开始

官方文档罕见地用强硬语气禁止了一件事:先把教程、操作指南、参考、说明这四个空壳结构建起来。原文写的是别这么做,这很糟糕。而这恰恰是引入失败中占压倒性多数的形态:建四个目录,把既有文档随手塞进去,其中三个空着放半年。

这套框架的工作方针正相反:不要把力气花在把结构摆正上,持续做改进,结构会从内部改变。到某个时点,是那些改动本身开始要求「这块得挪到别处去」,上层结构就是这样成形的。把它当作向导而不是计划,说的就是这个意思。

但从哪里下手总要定,所以这里写下关于顺序的判断。

  1. 先把参考抽出来。判定最容易,只看是不是事实,几乎不会有分歧。而且抽出来之后,就有了切换成从代码自动生成的余地
  2. 接着抽说明。说明以碎片形式散落在别的文档里,抽走之后其余文档会明显变轻。这一步体感最强
  3. 操作指南会从剩下的部分自然浮出来。去掉上面两类之后,剩下的步骤里标题想变成「怎么做某事」的那些就是
  4. 教程放到最后新写。它是四类里唯一无法靠剪贴拼出来的。「一条走到底都能成功的路径」是设计出来的东西,把既有文档的碎片凑起来是凑不出来的

大规模落地的参照点是:Canonical 在 2021 年 12 月公开宣布把 Diátaxis 作为自家文档的基础,并应用到 Anbox Cloud、Charmed Kubeflow、Juju、OpenStack Charms 指南和 Ubuntu Core 的文档上。那篇文章里最值得引用的不是成果而是警告:Diátaxis 做的第一件事不是让既有文档看起来更好,而是看起来更糟,因为问题变得更难藏起来、更难忽视。如果引入一个月后有人说「用了之后反而更乱」,那说明你走在正常路径上。

永远未完成,却时时完整。这是官方文档借植物打的比方。植物永远不会「完成」,但从种子到成树,每个阶段它都是完整的。文档也一样,它不会结束,但在每一个时点都可以是完整的。有了这个感觉,就不会再去立「全面重构项目」了。

6. 只有一个 README 的项目 —— 小仓库的折中

看完这套框架,大家问的通常是同一个问题:我的仓库只有一个 README,那要我怎么办。先给答案:不需要拆成四个文件。对多数仓库来说,搭一个文档站是过度设计。

决定是否拆分的不是文档数量,而是读者种类的数量。使用这个仓库的人,会不会分成「第一次用的人」和「已经在用的人」?像团队内部脚本这样不会分的,一个 README 就够。改为用章节顺序把四类分开。

  1. 一句话简介。四类里的哪一类都不是,这是识别信息。这个仓库是什么,一行说完
  2. Quick start —— 教程的位置。只给一条路径,禁止条件分支,给出可以直接粘贴的命令,最后再加上怎么确认成功了。这最后一行在多数 README 里都是缺的
  3. Usage / Recipes —— 操作指南的位置。「怎么做某事」形式的短条目。分支和条件到这里才被允许
  4. Configuration / API —— 参考的位置。用表格而不是散文。名称、类型、默认值、约束
  5. Design notes / Why —— 说明的位置。放最下面。这里变长了,才到了把它拆成文件的时候

拆成文件的时机靠形状判断,不靠长度。五个信号里出现任何一个,就把那一部分拆出去。

  • Quick start 里出现了两个以上条件分支。「用 Docker 的话……,本地安装的话……」→ 把操作指南拆出去。有分支的那一刻它就已经不是教程了
  • 配置表格超过一屏。→ 挪到 docs/configuration.md。参考可以长,但不能吃掉第一屏
  • 以「为什么」开头的段落超过三段。→ 挪到 docs/design.md 或 ADR
  • 同一个问题在 issue 里出现了三次。→ 直接用提问者的原话做标题,建一篇操作指南。不要润色措辞,用户写出来的词就是搜索词
  • README 超过五屏。→ 拆开,而不是加目录。目录是缓解症状,不是治疗

而且在拆文件之前,还有一个便宜得多的做法:让章节标题显示出类别。「Usage」看不出是四类里的哪一类,「Quick start」「How to ……」「Configuration reference」「Design notes」则看得出来。文件结构一个不动,只改四个标题,读者停下滚动的位置就变了。

7. 标题占一半

官方文档给操作指南的标题举了三档例子。好的是「如何接入应用性能监控」;差的是「接入应用性能监控」(也可能这篇讲的是该不该接);非常差的是「应用性能监控」(可能讲怎么做,也可能讲该不该,甚至只是解释它是什么)。文中还补了一句:搜索引擎和人一样喜欢好标题。

把这条规则铺到四类上,大致是这样。

类别标题句式差的例子好的例子
教程「做出你的第一个……」「上手……」入门指南做出你的第一个通知机器人
操作指南「如何……」通知设置如何在企业代理后面发送通知
参考名词短语 +「完整清单」「规格」配置技巧环境变量完整清单
说明「关于……」「为什么……」架构为什么要放两个队列

中文里有一个特别碍事的词:「指南」。这个词把四类全盖住了。「安装指南」可能是教程,可能是操作指南,也可能是参考;「运维指南」四类都可能。光是把标题里的「指南」拿掉,就不得不去决定它到底属于哪一类。「手册」也是同样的性质。打开内部文档清单,数一数标题里带「指南」「手册」的有多少条,那个数字大致就是未分类文档的数量。

8. 哪里会变得牵强 —— 局限与反驳

这套框架对自己写得格外谦逊:不必相信它,也没有考试,如果里面有一条洞见你觉得有用,拿走那一条就好。反复叮嘱把它当向导而不是计划,也出自同一个立场。照这个态度来看,牵强的地方有这些。

  • 发布说明与变更记录。四类里哪一类都不是。它是事实的罗列,看着像参考,但参考应当映射产品结构,而变更记录是按时间排的,轴不一样。别硬塞,单列一类更好。碰到四类装不下的东西时,造一个第五格比破坏框架的代价小
  • 故障排查。官方文档把「解决部署问题」列为操作指南的例子。可现实中的故障排查文档是「症状 → 原因 → 处置」的结构,也就是说诊断(认知)和处置(行动)黏在同一个条目里。在条目内部拆开,文档反而没法用。判断:条目内部保持黏着,只在文档层面把它放进操作指南
  • 迁移指南。读者已经熟练,但这件事本身是第一次做,是少见的同时要求两类性质的体裁。判断:归入操作指南,但借用教程的纪律——单一路径、每一步都有成功确认方法、以及怎么回滚
  • 只有一个维护者的团队。维持四类本身就是成本。在没有文档专职的组织里拆成四类,得到的是四篇没人维护的文档。判断:标准不是人数,而是更新主体是否分离。把随代码一起更新的(参考)和由人手工更新的(其余三类)分开,一半问题就解决了
  • 只有自动生成的参考。官方文档也指出,把自动生成的参考当成文档全部的开发者太多了。但反方向也有陷阱:手写的参考会和代码脱节。判断:参考尽量从代码里生成,把手写的力气花在其余三类上。如何让 API 规格不脱节,在API 文档为什么总是落后于代码里单独讲过

还有一条反驳要诚实地写下来:「读者并不知道自己处于什么状态」。第一次来的人从搜索进到操作指南、卡住,甚至意识不到这篇文档本来就不是写给他的。类别分得再好,入口是由搜索决定的。

这与其说是框架的缺陷,不如说是框架不涵盖的部分,而补上的办法很便宜:在每篇文档最上面加一行。「本文假设你已经安装好 X。如果是第一次,请从快速上手开始。」分完类却不加这一行,分类收益的一半会在搜索流量的入口处漏掉。

9. 这种区分在智能体读的文档里怎么起作用

人类读者会在学习期和工作期之间来回。智能体不会,它每次被调用时几乎永远在工作中。这意味着罗盘的第二个轴实际上被钉死在一侧,剩下的就是操作指南和参考这两类。

  • 教程几乎没有价值。「建立信心」这个目的不成立。把人类用的教程原样放进上下文文件,只是花掉词元而已
  • 参考对智能体的价值比对人更大。智能体会用一句像模像样的话去填补事实的空缺。没写清准确的名称、默认值和约束,它就会编。人不懂会问,智能体通常不问
  • 操作指南要比人类版本更窄。人能「按自己的情况调整」,给智能体留出这块余地,余地就直接变成了出错的空间
  • 说明只留结论。哪怕只有一行讲清为什么是这个结构,智能体在没被指示到的情形下也会少做怪事;但把人类用的整篇背景讲解塞进去,代价会以上下文成本回来

归纳起来:面向智能体的文档,把四类里的两类写到极高密度,说明只留判断标准,教程去掉。这就是一个真正好用的上下文文件的实际形状。人类用文档和智能体用文档为什么是两种体裁,在OpenWiki 来了 - 面向AI智能体的代码库文档与面向人类的文档有何不同里讲过;往那份文档里堆多少规则都管不住的原因,在长篇政策文档管不住智能体里讲过。

再补一点:把类别分开对检索质量也有直接作用。企业知识库里,步骤、背景和事实混在同一篇文档时,任何查询都会命中它,而命中之后真正需要的那一句往往落在切块边界之外。再加上这篇文档还在悄悄变旧,话题就接到企业知识库在悄悄腐坏那边去了。

10. 在开发组织里特别容易卡住的地方

10.1 维基的目录树是按组织架构而不是按类别搭的

内部文档堆在 Confluence 或类似工具上时,目录树通常长这样:「平台组 > 2024 > 部署」。这是按作者、团队和时间搭出来的路径,和读者的状态毫无关系。某篇文档是教程还是参考,不打开就不知道,而打开之前你只看得到搜索结果里的标题。

重搭目录树是大工程,通常需要审批。但只把标题改成能看出类别,不需要任何审批。顺序也应该是这样:标题改完,哪篇属于四类里的哪一类就开始在列表里显形,那时候你才有依据去动目录树。

10.2 交接文档是四类全混的典型体裁

换负责人时把所有东西塞进一篇文档,是很常见的做法:接入信息、操作步骤、背景和注意事项全在一页里。结构性的问题在于:交接文档从写完那一刻起就失去了更新主体。写的人走了,接的人不把它当成自己的文档。没人更新的文档一定会变旧。

判断:把交接文档做成索引,内容分送到各个类别。接入信息和资源清单归参考,定期作业归操作指南,为什么是这样运转归说明。交接文档里只留链接,外加一件事——这套系统的负责人是谁。这样即使交接文档变旧,损失也就是几条链接。

10.3 外包与甲方项目的交付物名称写死在合同里

当合同里明确写着需求规格说明书、界面设计文档、用户手册这类交付物名称时,你没法把四类映射到交付物清单上,也改不了名字。

判断:这种情况下,把 Diátaxis 用在每份交付物内部的章节结构上,而不是用在交付物清单上。在一本用户手册里把「初次使用」「按业务的处理步骤」「界面与字段规格」分开,交付物名称不变,里面三类却分离了。这是不碰验收标准就能拿到的改善。

10.4 英文原文和中文译文并存的时候

引入开源项目的同时把官方文档翻译一份放在内部,是很常见的。这里反复出现的破损是原文的四类在译文里被压成一页摘要。上游分成教程、操作指南和参考的内容,变成了一篇「某某使用说明」。这样一来译文比原文还差:能读原文的人去读原文,读不了的人只剩下那篇差文档。

判断:如果译不完,减少篇幅,不要减少类别。建四个文件、每个都写短一点,好过一个文件装下全部。而且这样还留出了以后往里补的位置。

11. 没能核实的部分

以下几项因为拿不到依据,没有在正文里作为数字或断言使用。

  • 引入前后的量化效果。没有找到把搜索跳出率、支持工单量、新人上手耗时等指标在引入 Diátaxis 前后做对比的一手资料。Canonical 那篇文章止步于宣布采用、列出适用范围,以及「先看起来更糟」这句经验性描述,没有数字
  • 四分类的实验性验证。diataxis.fr 上有讨论理论的章节,但没有找到设了对照组、证明这种分类比别的分类更能提升读者成效的公开研究
  • 智能体文档中的效果测量。没有找到公开结果去测量「按类别分离的上下文文档」能把工具调用成功率或任务完成率改变多少。第 9 节全部是从结构推出的判断,不是测量值
  • 非英语文档体系的落地报告。没有找到某个组织把这套框架用在非英语文档体系上并公开结果的资料。第 10 节是对反复出现的形态所作的判断

12. 结论:今天能做的只有一件事

文档的问题多半不是不足,而是混杂。四十页没人读不是因为不够四十一页,写到六十页也一样。原因是把四个处于不同状态的读者摁在同一篇文档里坐着。

读完这篇今天能做的只有一件事:把眼前已经开着的那篇文档再打开一次,对每一段抛出两个提问,给类别不同的那一段做个记号,只搬走这一段。不要去搜罗,不要立计划,不要建目录。尤其是先建四个目录,这是这套框架里唯一明确写着「别做」的一条。

还有,如果头一个月文档看起来更乱了,那是正常的。这套框架做的第一件事不是让文档变好,而是让哪里坏了藏不住。原本藏着的东西露出来,和新长出来的问题,是两回事。

最后只留一个顺序:先分类别,再打磨句子。反过来做,写得再好的句子还是会留在不该待的位置上。修文风是下一步的事,那是受控语言那一侧的话题。
