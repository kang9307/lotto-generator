1. GA 확정 경위 — 빌드 35와 9건의 JEP

자바 플랫폼의 최신 표준 구현체인 JDK 27이 2026년 9월 15일 정식 출시(General Availability, GA)를 맞이했다. OpenJDK 프로젝트의 수석 아키텍트인 Mark Reinhold는 announce 메일링 리스트를 통해 Java SE 27 플랫폼의 레퍼런스 구현체인 JDK 27의 정식 출시를 공식 공지했다. 이번 릴리스는 OpenJDK의 6개월 주기 정기 릴리스 모델에 맞춰 예정된 일정 그대로 공개되었다.

공식 공지에 따르면, 이번 GA 릴리스의 토대가 된 것은 2026년 8월 20일에 배포되었던 두 번째 릴리스 후보(Release Candidate 2)인 빌드 35(build 35)였다. 릴리스 후보 단계에서 최우선 순위 결함인 P1 버그 보고가 접수되지 않음에 따라, 빌드 35가 바이너리 수정 없이 그대로 최종 GA 빌드로 확정되었다. 현재 Oracle이 제공하는 GPLv2 기반 오픈소스 프로덕션 바이너리는 공식 다운로드 페이지를 통해 Linux(x64, AArch64), macOS(x64, AArch64), Windows(x64) 아키텍처별로 즉시 내려받을 수 있다. 공지는 다른 벤더의 빌드도 곧 나올 것이라고만 적었을 뿐, 벤더 이름이나 배포 시기는 밝히지 않았다.

JDK 27에는 총 9건의 JEP(JDK Enhancement Proposal)가 포함되었다. 정식 기능으로 반영되어 런타임의 기본 동작을 바꾸는 기능이 2건, 보안 및 런타임 진단 강화가 2건 포함되었으며, 나머지 5건은 프리뷰(Preview) 및 인큐베이터(Incubator) 상태의 API들이다. 공식 공지는 9건의 핵심 JEP 외에도 「수백 건의 소규모 개선과 수천 건의 버그 수정("hundreds of smaller enhancements and thousands of bug fixes")」이 이번 릴리스에 함께 반영되었다고 밝혔다. 이번 배포는 겉보기에는 언어 문법의 극적인 변화가 적어 보이지만, 내부적으로는 런타임의 오랜 기본값을 두 가지 축에서 뒤바꾼 중대한 전환점을 이룬다.

2. JDK 27 JEP 9건 전체 현황

JDK 27에 포함된 9건의 JEP는 플랫폼 핵심 런타임, 언어 기능, 라이브러리, 보안 체계에 걸쳐 폭넓게 분포되어 있다. 새로운 릴리스를 도입하려는 엔지니어링 팀은 어떤 항목이 프로덕션에서 즉시 기본 적용되는 정식 기능이고, 어떤 항목이 명시적 플래그가 필요한 프리뷰 또는 인큐베이터 기능인지를 명확히 구분해야 한다.

JEP 번호 명칭 분류 및 상태 운영 영향 및 프로덕션 기본 여부
JEP 523 Make G1 the Default Garbage Collector in All Environments HotSpot GC (정식 기능) 기본 적용. 단일 CPU나 소형 메모리 환경에서도 Serial 대신 G1이 기본 동작함
JEP 527 Post-Quantum Hybrid Key Exchange for TLS 1.3 보안 라이브러리 (정식 기능) 기본 지원. TLS 1.3 연결 시 양자내성 하이브리드 키 교환 메커니즘을 지원함
JEP 531 Lazy Constants (Third Preview) 코어 라이브러리 (3차 프리뷰) 프리뷰. 지연 상수 연산 최적화 API 제공, 컴파일 및 실행 플래그 필요
JEP 532 Primitive Types in Patterns, instanceof, and switch (Fifth Preview) 자바 언어 (5차 프리뷰) 프리뷰. 기본형 타입을 패턴 매칭, instanceof, switch에서 처리하도록 확장
JEP 533 Structured Concurrency (Seventh Preview) 동시성 라이브러리 (7차 프리뷰) 프리뷰. StructuredTaskScope 예외 타입 매개변수 추가 등 API 개선 지속
JEP 534 Compact Object Headers by Default HotSpot Runtime (정식 기능) 기본 적용. 64비트 환경에서 객체 헤더를 96비트에서 64비트로 기본 축소함
JEP 536 JFR In-Process Data Redaction HotSpot 진단 (정식 기능) 기본 지원. JFR 레코딩 시 프로세스 내부에서 민감 데이터 필터링 및 비식별화
JEP 537 Vector API (Twelfth Incubator) 코어 라이브러리 (12차 인큐베이터) 인큐베이터. 하드웨어 SIMD 가속 API, 장기 인큐베이션 유지
JEP 538 PEM Encodings of Cryptographic Objects (Third Preview) 보안 라이브러리 (3차 프리뷰) 프리뷰. 암호화 키 및 인증서 PEM 인코딩/디코딩 표준 API

위 표에서 보듯, 엔지니어링 관점에서 프로덕션 배포 시 즉각적인 영향을 미치는 변경 사항은 단연 JEP 523(G1 기본 GC 지정)과 JEP 534(컴팩트 객체 헤더 기본화)다. 별도의 옵션을 주지 않고 JVM을 실행하더라도, 메모리 할당 패턴과 GC 수집 주기, 그리고 객체 하나가 메모리 힙에서 차지하는 바이트 크기 자체가 달라지기 때문이다.

3. 기본값이 바뀐 첫 번째 축 — JEP 523 모든 환경에서 G1 기본 GC 지정

HotSpot JVM은 수십 년간 런타임이 기동될 때 호스트 환경의 물리적 사양을 검사하여 서버급 머신(Server-class machine) 여부를 판정해 왔다. 전통적인 기준에 따르면 물리 메모리가 1792MB 이상이고 2개 이상의 물리 CPU 코어가 장착된 환경에서는 G1(Garbage-First) GC가 기본으로 선택되었다. 반면 단일 코어 환경이나 메모리가 1792MB 미만인 소형 장비에서는 단일 스레드로 동작하는 Serial GC가 기본 수집기로 할당되었다.

JEP 523(소유자: Thomas Schatzl)은 이 오래된 분기 규칙을 완전히 폐지했다. 이제 명령줄에서 가비지 컬렉터를 명시하지 않은 경우, HotSpot JVM은 실행 환경의 CPU 코어 수나 메모리 크기와 무관하게 항상 G1 가비지 컬렉터를 기본으로 선택한다. JEP 523의 목표는 과거 Serial GC가 선택되던 환경에서도 처리량(Throughput), 지연 시간(Latency), 메모리 풋프린트(Footprint), 기동 시간(Startup time)의 심각한 저하 없이 현대적인 세대별 가비지 컬렉션을 제공하는 데 있다.

이 변경의 기술적 비목표(Non-Goals) 또한 명확히 문서화되어 있다. JEP 523은 기존에 존재하던 Serial, Parallel, ZGC 등의 수집기를 결코 사용 중단(Deprecate)하거나 제거하지 않는다. 또한 사용자가 명령줄 옵션을 통해 명시적으로 가비지 컬렉터를 지정한 경우 JVM의 기본 선택보다 사용자 설정이 항상 우선한다. G1 컬렉터 자체의 알고리즘이나 기본 동작 파라미터가 이번 JEP로 인해 수정된 것은 아니다.

# Java 27 기본 동작: 환경과 무관하게 G1이 자동 선택됨
java -jar application.jar

# 기존 단일 스레드 경량 동작을 강제 유지하려는 경우
java -XX:+UseSerialGC -jar application.jar

# 고처리량 일괄 처리를 위해 Parallel GC를 유지하려는 경우
java -XX:+UseParallelGC -jar application.jar

# 초저지연 처리를 위해 ZGC를 사용하려는 경우
java -XX:+UseZGC -jar application.jar

소형 컨테이너나 단일 vCPU 환경에서 기본 GC가 Serial에서 G1으로 바뀐다는 사실은 운영 관점에서 매우 큰 의미를 갖는다. Serial GC는 GC 동작 중 모든 애플리케이션 스레드를 멈추고 하나의 스레드만으로 메모리를 회수하므로 백그라운드 스레드 오버헤드가 거의 없었지만, G1은 병렬 수집 스레드와 동시 마킹(Concurrent Marking) 스레드를 동반하기 때문이다.

4. 기본값이 바뀐 두 번째 축 — JEP 534 컴팩트 객체 헤더 기본 적용

JDK 27의 두 번째 핵심 변경점은 64비트 아키텍처에서 모든 자바 객체의 물리적 구조를 변경한 JEP 534(소유자: Roman Kennke)다. 컴팩트 객체 헤더(Compact Object Headers)는 64비트 시스템에서 객체당 헤더 크기를 96비트(12바이트)에서 64비트(8바이트)로 축소한다.

전통적인 64비트 HotSpot JVM에서 객체 헤더는 두 개의 워드로 구성되었다. 첫 번째는 객체의 락 상태, 해시코드, GC 연령(Age) 정보를 담는 64비트 마크 워드(Mark Word)이고, 두 번째는 객체의 메타데이터 클래스를 가리키는 클래스 워드(Klass Word)였다. 압축 클래스 포인터(Compressed Class Pointers)를 사용할 때 클래스 워드는 32비트를 차지하므로, 합산 헤더 크기는 96비트(12바이트)가 되었다. 그러나 64비트 JVM은 8바이트 경계 정렬(Alignment)을 유지하므로, 필드가 없는 객체라도 최소 16바이트로 올림 처리되어 메모리를 소비했다.

컴팩트 객체 헤더는 클래스 포인터를 마크 워드 내부의 사용되지 않는 비트 영역으로 이동시켜 인코딩함으로써 별도의 Klass Word를 제거했다. 결과적으로 마크 워드 하나(64비트, 8바이트) 안에 클래스 정보와 런타임 메타데이터를 모두 수용하게 되었다. 이 기능은 JDK 24의 실험적 도입(JEP 450)과 JDK 25의 정식 기능화(JEP 519)를 거쳐 광범위한 안정성 검증을 마쳤으며, JDK 27에 이르러 마침내 기본 활성화(Default)로 전환되었다.

# Java 27 기본 동작: 컴팩트 객체 헤더(64비트)가 자동 활성화됨
java -jar application.jar

# 만약 네이티브 인터페이스(JNI)나 특수 프로파일러 호환성 문제로 구형 헤더(96비트)로 되돌릴 경우
java -XX:-UseCompactObjectHeaders -jar application.jar

JEP 534는 이전의 96비트 객체 헤더 레이아웃을 완전히 제거하는 것은 아니라고 명시했다. 필요시 위와 같이 -XX:-UseCompactObjectHeaders 플래그를 통해 이전 레이아웃으로 되돌릴 수 있다. 객체 헤더가 4바이트 줄어들면 객체 수가 수천만 개에 이르는 대형 힙 애플리케이션에서 순수 메모리 공간 절약뿐 아니라, CPU L1/L2/L3 캐시에 더 많은 객체 데이터가 적재되는 데이터 지역성(Data Locality) 개선 효과를 기대할 수 있다. 다만 OpenJDK 공식 문서에는 워크로드별 절감률 수치가 별도로 기재되어 있지 않으므로, 애플리케이션의 객체 분포에 따라 실측해야 한다.

5. 컨테이너 인프라와 결합할 때의 운영 영향 — 힙 계산과 CPU 스로틀링

현대 클라우드 인프라에서 JVM은 베어메탈 서버가 아니라 쿠버네티스 Pod나 Docker 컨테이너 환경에서 실행되는 경우가 대부분이다. 이미 이전 글인 JVM은 컨테이너 한도를 어떻게 보는가에서 다루었듯, JVM은 컨테이너 한도(Limit)를 기계적으로 따르는 것이 아니라 cgroup 메트릭을 읽고 내부 휴리스틱에 따라 자체적인 스레드 수와 힙 크기를 계산한다.

Java 27의 두 가지 기본값 변화는 이러한 컨테이너 리소스 제어 메커니즘과 즉각 충돌하거나 맞물린다. 특히 마이크로서비스 아키텍처에서 경량 처리를 위해 CPU 코어를 0.5 또는 1로 제한하고 메모리를 1GiB 미만으로 설정한 소형 Pod에서 주의가 필요하다.

  • CFS CPU 쿼터와 G1 백그라운드 스레드: Serial GC는 단일 스레드로만 수집 작업을 수행했기 때문에 리눅스 CFS(Completely Fair Scheduler) 쿼터 초과로 인한 CPU 스로틀링 위험이 적었다. 그러나 Java 27에서 기본으로 동작하는 G1 GC는 병렬 작업 스레드와 동시 마킹 스레드를 기동한다. Pod 배포 설정에서 CPU Limit이 너무 타이트하게 걸려 있다면 GC 마킹 주기에 순간적으로 CPU 사용량이 튀며 스로틀링이 발생해 애플리케이션 응답 지연(Tail Latency)이 길어질 수 있다.
  • 컴팩트 객체 헤더에 따른 힙 밀도 상승: 객체당 헤더가 8바이트로 줄어들면서 같은 크기의 힙 안에서 더 많은 객체가 수용된다. 이는 작은 메모리 컨테이너에서 힙 압박을 완화하는 긍정적 효과를 낸다.
  • 힙 밖 메모리(Off-Heap) 계산의 지속적 중요성: G1 GC는 Serial GC에 비해 RSet(Remembered Set) 등 내부 관리용 카드 테이블과 버퍼 메모리를 추가로 소비한다. -Xmx를 컨테이너 메모리 Limit과 거의 동일하게 설정하면, G1의 네이티브 오버헤드와 맞물려 리눅스 OOM Killer에 의해 컨테이너가 강제 종료(OOMKilled)될 위험이 커진다.

따라서 코어 1개 이하의 소형 컨테이너를 운영 중인 팀은 Java 27 업그레이드 시 CPU 스로틀링 발생 추이와 컨테이너 RSS 메모리 점유율을 모니터링해야 한다. 지연 시간보다 최소 리소스 점유가 최우선인 환경이라면 -XX:+UseSerialGC를 명시적으로 선언하는 것이 여전히 합리적인 선택지다.

6. 프리뷰와 인큐베이터가 뜻하는 현실 — 531·532·533·537·538

JDK 27에 포함된 9개의 JEP 중 5개는 프리뷰(Preview) 및 인큐베이터(Incubator) 항목이다. 자바 플랫폼의 진화 과정에서 프리뷰는 언어 또는 라이브러리 명세가 거의 완성 단계에 이르렀으나 개발자 피드백을 수집하기 위해 의도적으로 프로덕션 기본 채택을 보류한 상태를 뜻한다. 인큐베이터는 그보다 이전 단계로, 별도의 모듈 네임스페이스를 통해 실험적인 API를 제공하는 단계다.

  • JEP 531 지연 상수(Lazy Constants, 3차 프리뷰): 대규모 프레임워크나 런타임에서 비용이 큰 객체나 설정값의 초기화를 필요한 시점까지 안전하게 지연시키는 메커니즘을 제공한다.
  • JEP 532 기본형 패턴 매칭(5차 프리뷰): instanceof와 switch 표현식에서 참조형뿐만 아니라 기본형 타입(int, long, double 등)에 대해서도 손실 없는 변환과 패턴 매칭을 허용하도록 언어 문법을 확장한다.
  • JEP 533 구조적 동시성(7차 프리뷰): 비동기 서브태스크들의 수명 주기를 단일 스코프로 묶어 관리하는 동시성 제어 API다.
  • JEP 537 Vector API(12차 인큐베이터): x64의 AVX나 AArch64의 NEON/SVE 같은 하드웨어 SIMD 벡터 명령을 고수준 자바 코드로 직접 다룰 수 있게 해주는 API다.
  • JEP 538 암호화 객체 PEM 인코딩(3차 프리뷰): X.509 인증서나 PKCS#8 개인키를 외부 라이브러리(Bouncy Castle 등) 없이 표준 API로 PEM 형식 인코딩/디코딩할 수 있도록 지원한다.

이들 5개 기능은 기본 상태에서는 코드에서 임포트하거나 호출할 수 없으며, 컴파일과 실행 시점에 특수 플래그를 요구한다. 커뮤니티(GeekNews 토픽 등)에서는 Vector API가 12차 인큐베이터에 도달할 정도로 장기화되고 있는 점과, 값 객체(Value Objects)를 다루는 Project Valhalla의 본 릴리스 제외에 대해 아쉬움을 표하는 의견이 지속적으로 나오고 있다.

7. 심층 분석 — JEP 533 구조적 동시성의 진화와 제약

구조적 동시성(Structured Concurrency)은 자바 가상 스레드(Virtual Threads, JEP 444)의 장점을 극대화하기 위해 설계된 핵심 동시성 패러다임이다. Alan Bateman, Viktor Klang, Ron Pressler가 작성한 JEP 533(소유자: Alan Bateman)은 JDK 19 및 JDK 20의 인큐베이션을 거쳐 JDK 21부터 프리뷰를 이어왔으며, JDK 27에서 7차 프리뷰(Seventh Preview)를 맞이했다.

기존의 ExecutorService 기반 비동기 프로그래밍은 서로 연관된 하위 작업들이 각각 독립된 스레드에서 실행되므로 스레드 누수(Thread Leak)와 취소 지연 문제를 구조적으로 안고 있었다. 예를 들어 하나의 요청을 처리하기 위해 사용자 정보를 조회하고 주문 목록을 가져오는 두 개의 작업을 분기(Fork)했을 때, 사용자 조회가 실패하더라도 주문 목록 조회 작업은 백그라운드에서 끝까지 실행되어 시스템 리소스를 낭비하거나 엉뚱한 부작용을 낳았다.

JEP 533은 이러한 작업들을 단일 코드 블록 단위로 묶어주는 StructuredTaskScope 메커니즘을 제공한다. JDK 27에서 도입된 주요 변경 사항은 다음과 같다:

  • 세 번째 타입 파라미터 R_X 추가: StructuredTaskScope와 Joiner 인터페이스에 join() 메소드가 던질 수 있는 예외 타입을 명시하는 제네릭 매개변수 R_X가 추가되어 컴파일 타임 타입 안정성이 한층 강화되었다.
  • open() 정적 팩토리 메소드 추가: UnaryOperator를 전달받아 기본 조인 정책과 스코프 설정을 유연하게 구성할 수 있는 새로운 open 팩토리가 도입되었다.
  • Joiner 팩토리 예외 처리 개선: allSuccessfulOrThrow(), anySuccessfulOrThrow(), awaitAllSuccessfulOrThrow() 메소드가 실패 시 ExecutionException을 기본으로 던지도록 통일되었으며, 커스텀 예외로 변환할 수 있는 Function 오버로드가 제공된다.
  • 구형 메소드 정리: 기존의 Joiner.awaitAll() 메소드가 제거되었고, onTimeout() 메소드는 타임아웃 발생 시 원인을 명확히 추적하는 timeout() 메소드로 대체되었다.
// JEP 533 StructuredTaskScope 기본 사용 예제 (프리뷰 API)
Response handle() throws ExecutionException, InterruptedException {
    try (var scope = StructuredTaskScope.open()) {
        StructuredTaskScope.Subtask<String> user = scope.fork(() -> findUser());
        StructuredTaskScope.Subtask<Integer> order = scope.fork(() -> fetchOrder());

        scope.join(); // 두 서브태스크가 완료될 때까지 대기

        // 서브태스크 결과를 취합하여 반환
        return new Response(user.get(), order.get());
    }
}

이 코드는 try-with-resources 블록을 벗어나는 순간 미완료된 서브태스크가 남아 있다면 자동으로 취소(Cancel) 신호를 보내 스레드 누수를 원천 차단한다. 그러나 7차 프리뷰에 이르렀음에도 세부 인터페이스가 계속 다듬어지고 있다는 사실은, 이 API가 아직 정식 표준으로 확정되지 않았음을 시사한다.

8. 보안 영역의 2건 — JEP 527 양자내성 하이브리드 키 교환과 JEP 536 JFR 비식별화

JDK 27에 포함된 2건의 정식 보안/진단 기능은 최신 보안 표준 준수와 운영 환경에서의 개인정보 보호에 중요한 진전을 제공한다.

JEP 527(TLS 1.3용 양자내성 하이브리드 키 교환): 미래에 등장할 양자 컴퓨터는 쇼어(Shor) 알고리즘을 이용해 현재 널리 쓰이는 RSA 및 ECC 기반 공개키 암호 체계를 무력화할 수 있다. 공격자가 지금 암호화된 트래픽을 대량으로 수집해 둔 뒤 미래에 양자 컴퓨터로 복호화하는 「지금 도청하고 나중에 해독(Harvest Now, Decrypt Later)」 공격에 대응하기 위해, JEP 527은 TLS 1.3 핸드셰이크에 포스트 퀀텀 하이브리드 키 교환을 정식 지원한다. 이는 기존의 검증된 고전 키 교환(ECDH)과 양자내성 암호 알고리즘(ML-KEM 등)을 결합하여 양쪽 모두의 안전성을 동시에 확보하는 방식이다.

JEP 536(JFR In-Process Data Redaction — JFR 데이터의 프로세스 내 편집): Java Flight Recorder(JFR)는 JVM 런타임의 프로파일링과 문제 해결에 가장 강력한 도구 중 하나다. 그러나 프로덕션 환경에서 JFR 레코딩 파일을 수집할 때 쿼리 스트링, 환경 변수, 시스템 속성, 네트워크 페이로드에 민감한 개인정보나 인증 토큰이 그대로 노출될 수 있다는 보안 우려가 존재했다. JEP 536은 레코딩 데이터를 디스크에 쓰거나 외부 수집기로 전송하기 전, JVM 프로세스 내부에서 사전에 정의된 규칙에 따라 민감 데이터를 마스킹하거나 필터링하는 기능을 기본 지원한다.

9. 프로덕션 업그레이드 전 점검표

기존 LTS 버전(JDK 17 또는 JDK 21)이나 이전 중간 버전에서 Java 27로 런타임을 전환하기 전에, 인프라 엔지니어와 개발팀이 반드시 대조해야 할 핵심 점검 항목을 정리했다.

점검 영역 점검 항목 및 JVM 플래그 영향도 및 권장 조치 관련 JEP
가비지 컬렉터 기본값 명시적 GC 플래그 누락 여부 확인 소형 컨테이너에서 Serial 대신 G1이 기동됨. CPU 스로틀링 관찰 및 필요시 -XX:+UseSerialGC 지정 JEP 523
메모리 레이아웃 -XX:+UseCompactObjectHeaders (기본) 객체 헤더가 64비트로 축소됨. JNI 네이티브 메모리 직접 접근 라이브러리가 있다면 호환성 검증 필수 JEP 534
컨테이너 힙 한도 MaxRAMPercentage 및 cgroup Limit G1의 RSet 등 네이티브 메모리 증가분 고려. 힙 한도를 컨테이너 메모리 Limit보다 여유 있게 낮춰 보수적으로 설정 JEP 523
보안 통신 TLS 1.3 하이브리드 키 교환 포스트 퀀텀 키 교환 시 핸드셰이크 패킷 크기 증가에 따른 레거시 방화벽 패킷 분할 문제 확인 JEP 527
진단 및 모니터링 JFR 레코딩 비식별화 설정 운영 환경 덤프 수집 시 마스킹 규칙을 적용하여 감사 및 컴플라이언스 요건 충족 JEP 536
프리뷰 의존성 배제 --enable-preview 플래그 존재 여부 CI/CD 파이프라인에서 프로덕션 아티팩트에 프리뷰 플래그가 들어가지 않도록 차단 JEP 531~538

위 점검표에서 가장 실수가 잦은 영역은 컨테이너 배포 매니페스트다. 개발 환경에서는 리소스 제약이 없으므로 G1과 컴팩트 헤더가 원활히 작동하지만, 리소스가 극도로 타이트하게 설정된 프로덕션 쿠버네티스 노드에서는 스케줄러 쿼터와 결합하여 예상치 못한 지연을 유발할 수 있다.

10. 프로덕션에서 프리뷰 기능을 켜면 안 되는 이유

JDK 27에 포함된 구조적 동시성(JEP 533)이나 기본형 패턴 매칭(JEP 532)은 코드 작성을 비약적으로 간결하게 만들어 주므로, 개발자가 프로덕션 서비스에 조기 도입하고 싶은 유혹을 느끼기 쉽다. 그러나 프리뷰 기능은 본질적으로 프로덕션 배포용이 아니다.

# 프리뷰 기능 활성화 컴파일 (프로덕션 배포용 빌드에서는 금지)
javac --release 27 --enable-preview MyApplication.java

# 프리뷰 기능 활성화 실행
java --enable-preview -jar application.jar

프리뷰 기능을 프로덕션 환경에서 금기시해야 하는 이유는 다음과 같다:

  • 클래스 파일 호환성 차단: --enable-preview로 컴파일된 클래스 파일은 바이트코드 헤더의 마이너 버전이 65535로 고정된다. 이 파일은 해당 버전의 JVM에서 오직 --enable-preview 옵션이 주어졌을 때만 로딩되며, 다른 버전이나 일반 모드에서는 로딩 자체가 거부된다.
  • API 파괴적 변경의 일상화: 구조적 동시성 API가 JDK 25(팩토리 메소드 변경), JDK 26, JDK 27(제네릭 파라미터 추가 및 awaitAll 제거)을 거치며 지속적으로 변경된 것처럼, 다음 버전에서 메소드 시그니처가 완전히 바뀔 수 있다. 이는 상위 버전 업그레이드 시 대규모 코드 재작성을 요구한다.
  • 서드파티 라이브러리 및 APM 충돌: ByteBuddy, cglib, Spring, Datadog/NewRelic 등의 바이트코드 조작 라이브러리와 APM 에이전트는 프리뷰 바이트코드를 처리하는 과정에서 파싱 에러를 일으키거나 기동에 실패할 위험이 높다.

11. 확인하지 못한 것

  • LTS(장기 지원) 여부: 이번 OpenJDK 공식 공지(Mark Reinhold)에는 JDK 27이 주요 벤더들에 의해 장기 지원(Long-Term Support, LTS) 버전으로 지정될 것인지에 대한 언급이 없다. 벤더별(Oracle, Eclipse Adoptium, Red Hat 등) 지원 로드맵은 OpenJDK 코어 프로젝트와 별도로 발표된다.
  • 차기 릴리스(JDK 28) 일정 및 스펙: 공지에는 다음 6개월 뒤 릴리스될 JDK 28의 상세 개발 일정이나 타깃 JEP 후보군이 명시되어 있지 않다.
  • 워크로드별 컴팩트 헤더 실측 메모리 절감률: JEP 534 본문과 출시 공지는 64비트 아키텍처에서 헤더가 96비트에서 64비트로 축소된다는 사실만을 명시하고 있으며, 실제 전체 힙 메모리 절감률 수치는 애플리케이션의 객체 수와 크기 비율에 따라 달라지므로 공식적인 단일 수치는 확인되지 않았다.
  • Project Valhalla의 정식 도입 시점: 값 객체(Value Objects)를 통해 메모리 레이아웃을 혁신하려는 Project Valhalla와 Vector API(JEP 537)의 최종 통합 시점은 이번 공지에 포함되어 있지 않다.
