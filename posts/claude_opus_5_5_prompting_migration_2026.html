설정을 그대로 옮기면 생기는 일 — Claude Opus 5에서 5.5로 프롬프트를 이관할 때

한 단계 낮아진 기본 effort, 늘어난 턴당 사고량, 비활성화 불가한 thinking, thinking 블록으로 옮겨 간 진행 보고

2026년 9월 29일 IT/기술

플래그십 대규모 언어 모델이 판올림될 때 엔지니어링 현장에서 가장 흔하게 선택하는 경로는 호출 코드의 모델 식별자 문자열만 바꾸고 나머지 설정을 그대로 두는 방식이다. 기존 프롬프트가 에러 없이 응답을 반환하면 마이그레이션이 문제없이 완료된 것으로 간주하기 쉽다. 그러나 Anthropic이 공개한 공식 문서인 「Prompting Claude Opus 5.5」에 따르면, 기존 프롬프트가 수정 없이 동작한다는 점과 이전 세대의 설정값을 그대로 승계하는 것은 전혀 다른 결과를 낳는다.

Claude Opus 5.5의 기본 요금 정책이나 벤치마크 지표는 앞선 Claude Opus 5.5 출시 — 토큰 가격 인하와 벤치마크 지표로 본 성능 분석 글에서 상세히 정리된 바 있다. 본 글에서는 모델의 가격과 벤치마크 점수를 배제하고, 순수하게 기존 프롬프팅 파이프라인을 Claude Opus 5에서 5.5로 이관할 때 실제로 겪게 되는 동작 차이와 권장 대응 절차에 집중한다. 모델 ID 표기 규칙부터 기본 effort 값의 하락, 동일 레벨에서 증가한 추론 토큰량, thinking 비활성화 시 발생하는 400 에러, 그리고 사용자 인터페이스로 노출되던 중간 진행 보고의 블록 변경까지 문서에 명시된 원문 지침을 바탕으로 분석한다.

본문의 설정값, 파라미터 규격, 원문 인용 문장은 Anthropic의 공식 문서(Prompting Claude Opus 5.5, Migration Guide, What's New)에서 1차 확인된 내용을 기준으로 정리했다. 원문에 확인되지 않는 성능 우열 판정이나 제3자 수치는 배제했으며, 명시적인 근거가 없는 항목은 본문 끝의 「확인하지 못한 것」 절에 별도로 기록했다.

1. 계기와 배경 — 왜 이전 설정을 그대로 옮기면 안 되는가

공식 문서의 첫머리는 기존 Claude Opus 5 프롬프트가 별도의 수정 없이도 잘 동작할 것이라는 문장으로 시작한다. 그러나 이것이 기존 시스템에 설정해 둔 파라미터를 그대로 유지해도 좋다는 뜻은 아니다. Anthropic은 공식 문서에서 명시적으로 다음과 같은 경고 문구를 제시하고 있다.

"If you keep the `effort` value you set for Claude Opus 5, expect longer turns and more output tokens."

이 문장이 시사하는 바는 명확하다. Claude Opus 5에서 사용하던 effort 수준을 아무런 검증 없이 그대로 승계하면 시스템의 턴 길이가 길어지고 출력 토큰 소비량이 증가하게 된다. 이전 세대에서 안정적으로 동작하던 호출 구조라 하더라도, 모델이 내부적으로 수행하는 사고의 밀도와 기본 전제 조건이 달라졌기 때문에 파이프라인의 시간 지연과 토큰 비용 구조가 예상치 못하게 변화할 수 있다.

1.1. 겉으로 드러나지 않는 동작 변화와 비용 영향

마이그레이션 안내 문서가 규정하는 4가지 파괴적 API 변경 사항 외에도, 프롬프팅 계층에서는 에러를 발생시키지 않으면서 시스템의 효율을 떨어뜨리는 조용한 변화들이 존재한다. 모델 ID의 경우 날짜 접미사가 없는 고정 식별자인 claude-opus-5-5를 사용하며, AWS Amazon Bedrock 환경에서는 anthropic.claude-opus-5-5로 표기된다. 마이그레이션 안내는 이것이 Opus 5의 claude-opus-5와 같은 방식이라고 적는다.

effort 파라미터를 다루는 방식에 따라 두 갈래의 변화가 생긴다. effort 파라미터를 생략한 요청은 모델의 새로운 기본값에 따라 이전보다 한 단계 낮은 레벨로 실행된다. 반대로 Opus 5에서 쓰던 값을 그대로 고정해 둔 요청은, 같은 수준에서 Opus 5.5가 턴당 더 많이 생각하는 경향이 있어 턴이 길어지고 출력 토큰이 늘어난다고 문서는 말한다. 그래서 문서는 Opus 5에서 쓰던 설정을 옮겨 오는 대신 effort를 명시적으로 지정하고 자체 평가셋으로 여러 레벨을 시험해 보라고 권한다.

2. 핵심 비교 — Claude Opus 5와 Claude Opus 5.5의 동작 차이

두 세대 간의 주요 사양 및 런타임 특성을 공식 문서에 명시된 원문 문장과 함께 비교하면 아래 표와 같다. 이 표에 수록된 항목들은 추정에 의한 값이 아니며, Anthropic의 공식 마이그레이션 가이드와 프롬프팅 문서가 직접적으로 밝힌 기술 사양이다.

항목 Claude Opus 5 Claude Opus 5.5 원문 문장 (공식 문서)
모델 식별자 (Model ID) claude-opus-5 (날짜 접미사 없음, 같은 방식) claude-opus-5-5 (고정 식별자, 날짜 접미사 없음) "Use claude-opus-5-5, a fixed model ID with no date suffix."

동일 레벨 사고량 기준선 턴당 사고량 증가 (특히 xhigh, max) "At a given level, Claude Opus 5.5 tends to think more per turn than Claude Opus 5, especially at xhigh and max."

3. effort 보정 — 한 단계 낮아진 기본값과 세 가지 권장 조정

Claude Opus 5.5는 low, medium, high, xhigh, max의 총 다섯 가지 effort 레벨을 모두 지원한다. 가장 결정적인 변화는 파라미터를 생략했을 때 적용되는 기본값이 medium이라는 점이다. Claude Opus 5를 비롯한 이전 Opus 모델들은 파라미터를 생략할 경우 high로 동작했다. 따라서 코드를 변경하지 않고 모델만 교체한 상태에서 effort 값을 명시하지 않는다면, 요청은 이전 세대보다 한 단계 낮은 레벨로 실행된다.

3.1. effort 레벨과 사고량의 불일치

한 단계 낮아진 기본값이 성능 저하를 의미하는 것은 아니다. 공식 문서는 서로 다른 모델 간에 effort 레벨의 명칭이 동일한 사고량에 대응하지 않는다고 명시한다. Anthropic의 자체 테스트 결과에 따르면 코딩 및 지식 작업 평가에서 Claude Opus 5.5의 medium 레벨은 Claude Opus 5의 high 레벨과 대등하거나 이를 능가하는 성과를 보였다. 또한 복수의 코딩 평가에서는 low 레벨만으로도 훨씬 저렴한 비용으로 이전 세대 high에 근접하는 성능을 나타냈다.

반대로 기존에 사용하던 effort 값을 그대로 가져오면 사정이 달라진다. 문서에 따르면 같은 수준에서 Claude Opus 5.5는 Claude Opus 5보다 턴당 더 많이 생각하는 경향이 있고, 특히 xhigh와 max에서 그렇다. 그래서 Opus 5에서 설정했던 값을 유지하면 턴이 길어지고 출력 토큰이 늘어난다고 문서는 말한다.

3.2. Anthropic이 권장하는 세 가지 조정 사항

문서에서는 effort를 적절히 보정하기 위해 도움이 되는 세 가지 조정을 제시한다.

  • max_tokens 상한을 충분히 높게 확보하기: 사고 과정에서 생성되는 추론 토큰은 클라이언트에 반환되지 않더라도 max_tokens 예산에 포함되어 계산된다. 따라서 Claude Opus 5에서 사고 기능을 끄고 타이트하게 맞춰 두었던 토큰 한도를 그대로 유지하면 모델의 최종 응답이 도중에 잘릴 수 있다. Anthropic은 긴 턴이 빈번하게 발생하는 에이전트 코딩 환경의 경우 모델의 최대 허용치인 128,000으로 max_tokens를 설정하는 것이 효과적이라고 안내한다.
  • xhigh와 max는 실측된 품질 향상이 확인된 영역에만 한정하기: 문서는 품질 향상을 직접 측정해 확인한 작업에만 xhigh와 max를 쓰라고 권한다.
  • 사고량을 줄이고자 할 때는 프롬프트 문구보다 effort 레벨부터 낮추기: 프롬프트에 「길게 생각하지 말라」는 지시문을 추가하는 방식보다, effort 파라미터를 낮추는 조치가 사고량과 그에 따른 비용, 지연 시간을 더 확실하게 줄인다.

4. thinking 비활성화 프롬프트의 네 가지 변경 절차

Claude Opus 5에서는 high 이하 레벨에서 thinking: {"type": "disabled"} 파라미터를 전달하여 모델의 사고 기능을 명시적으로 끄는 것이 가능했다. 하지만 Claude Opus 5.5에서는 이 설정이 전면 차단되었으며, 해당 옵션을 전달하는 모든 요청은 400 Bad Request 에러를 반환한다. 즉, Opus 5.5에서는 thinking 기능을 끌 수 없다. 따라서 과거에 thinking을 비활성화한 상태로 최적화해 두었던 기존 프롬프트는 아래 표에 정리된 네 가지 절차에 따라 구조를 개편해야 한다.

단계 마이그레이션 과제 세부 작업 내용 및 원문 권장 사항 적용 시 기대 효과 및 주의점
1단계 low effort에서 시작하여 측정 low에서 시작해 자체 트래픽으로 지연과 품질을 측정하고, 품질이 떨어지면 medium으로 올린다. 그 뒤에도 첫 토큰까지의 시간이 중요하면 시스템 프롬프트에 "Answer directly without deliberating." 같은 줄을 넣어 사고량을 더 줄일 수 있다. 사고를 줄이면 품질이 낮아질 수 있으므로, 이 줄을 넣을 때는 품질을 측정해야 한다.
2단계 사고 대체 지시문 제거 thinking 대신 응답 본문에 추론을 써 달라고 요구하던 지시를 삭제한다. 추론 과정은 요약된 thinking 블록(display: "summarized")으로 확인한다. 응답 본문에 추론을 재현하도록 미는 프롬프트는 reasoning_extraction 거절 범주로 거절될 수 있다.
3단계 비활성화 완화책 재검증 Opus 5의 thinking 비활성화 가이드가 권하던 결합 지시(도구 호출 전 발화 허용, 맞는 도구가 없을 때의 행동, 내부 태그 금지)가 아직 필요한지 재시험한다. 이 지시와 「생각하지 말라」 규칙은 Opus 5에서 thinking을 껐을 때만 나타나던 현상을 다룬 것이다. 결합 지시는 필요 여부를 확인하고, 「생각하지 말라」 규칙은 어느 경우든 지운다.
4단계 응답 블록 타입 기반 파싱 응답 데이터가 텍스트 블록으로 바로 시작하지 않고 thinking 블록으로 시작할 수 있음을 고려하여 클라이언트 수신 로직을 수정한다. 기본 display: "omitted" 환경에서는 첫 블록의 thinking 필드가 비어 있을 수 있으므로 블록 타입을 식별해 파싱해야 한다.

4.1. low effort 시작과 프롬프트 내 대체 지시 제거

과거에 thinking을 끄고 운영하던 API 엔드포인트라면, low 레벨로 시작해 측정하는 것이 이관의 첫걸음이다. low에서 모델은 사고를 짧게 유지하지만, 사고를 아예 건너뛰는 빈도는 프롬프트에 따라 다르다. 그래서 자체 트래픽으로 지연과 품질을 측정하고 품질이 떨어지면 medium으로 올린다. 그 뒤에도 첫 토큰까지의 시간이 중요하다면, 시스템 프롬프트에 숙고 없이 바로 답하라는 영문 문구를 넣어 사고를 더 줄일 수 있다. 다만 사고가 줄면 품질이 낮아질 수 있으므로 이 줄을 넣을 때는 품질을 측정해야 한다.

또한 thinking 대신 응답 본문에 추론 과정을 써 달라고 요구하던 지시문은 지우고, 추론은 display: "summarized"로 받는 요약 thinking 블록에서 읽는다. 응답 본문에 추론을 재현하도록 미는 프롬프트는 reasoning_extraction 거절 범주로 거절될 수 있기 때문이다.

4.2. 응답 블록 타입 기반 파싱 구조로의 전환

클라이언트 애플리케이션 관점에서는 API 응답 구조의 파싱 로직을 점검해야 한다. 문서는 첫 번째 블록이 text라고 가정하지 말고 각 블록의 타입을 확인하라고 권한다. Opus 5.5의 응답은 thinking 블록으로 시작할 수도 있고 그렇지 않을 수도 있으며, 기본 설정인 display: "omitted" 상태에서는 해당 블록의 thinking 필드가 비어 있다. 클라이언트 파서가 블록의 인덱스 순서에 의존하여 첫 번째 블록을 곧바로 텍스트로 처리하도록 작성되어 있다면 공백 화면이 출력되거나 파싱 오류가 발생할 수 있다.

5. 사용자 대상 진행 보고 — thinking 블록 이전과 네 가지 레버

에이전트가 복수의 도구를 연쇄적으로 호출하는 과정에서 남기던 상태 메모의 전달 방식이 전면적으로 변경되었다. Claude Opus 5에서는 도구 호출 사이에 짧은 진행 메모가 일반 text 블록으로 생성되어 사용자 인터페이스에 바로 노출될 수 있었다. 하지만 Claude Opus 5.5에서는 이러한 중간 메모들이 텍스트 블록이 아니라 진행 업데이트용 thinking 블록으로 반환된다.

5.1. 빈 텍스트 블록 방지와 진행 보고 네 가지 레버

기본 thinking.display 설정 아래에서는 thinking 블록의 내용이 비어서 전달되므로, text 블록만 렌더링하는 클라이언트는 에이전트가 긴 작업을 수행하는 동안 아무 말이 없는 것처럼 보일 수 있다. 원문 문서는 사용자에게 진행 보고를 다시 정상적으로 전달하기 위해 조작할 수 있는 네 가지 레버를 규정한다.

  • 첫 번째 레버 (display 설정 변경): 요청 헤더에 베타 식별자인 thinking-display-updates-2026-08-18을 지정하고, display: "updates" 파라미터를 활성화하여 요약된 진행 업데이트 텍스트를 수신한다.
  • 두 번째 레버 (도구 명시적 선언): 긴 턴 중간에 코드 조각처럼 사용자에게 그대로 전달해야 할 내용이 있을 수 있다면, 사용자에게 메시지를 보내는 간단한 도구를 주고 그 내용에만 쓰도록 지시한다. 이 도구는 세션의 첫 요청부터 tools에 선언한다. 나중에 추가하면 대화의 접두부가 바뀌어 앞선 thinking 블록이 무효가 된다.
  • 세 번째 레버 (보고 시점 명시): 시스템 프롬프트에 에이전트가 사용자에게 현황을 보고해야 하는 구체적인 시점과 조건을 명시적으로 규정한다.
  • 네 번째 레버 (하네스 수준의 리마인더 추가): 첫 번째 레버인 display: "updates"를 켠 상태에서, 사용자에게 읽을 것이 없는(text 블록도 진행 업데이트 텍스트도 없는) 도구 호출 단계가 연속으로 몇 번(원문 예시: 5회) 이어지면 하네스가 최신 도구 결과 뒤에 리마인더를 덧붙인다. 그래도 턴이 조용하면 리마인더를 2~3회 보낸 뒤 멈춘다.

5.2. 긴 침묵 구간을 줄이는 턴 범위 리마인더

네 번째 레버의 리마인더는 턴 범위 시스템 메시지(turn-scoped system message)로 붙인다. 베타 헤더인 mid-conversation-system-clear-at-2026-08-21과 함께 clear_at: "next_user_message" 속성을 지정하면, 사용자의 다음 입력이 들어오기 전까지만 유효한 시스템 지시를 대화 중간에 삽입할 수 있다. 원문은 에이전트 코딩 작업에 대한 Anthropic의 테스트에서 이 방식이 긴 침묵 구간이 있는 작업의 비율을 대략 절반으로 줄였고("roughly halved"), 비용에는 측정 가능한 변화가 없었다고 밝힌다.

원문에서 권장하는 침묵 방지 리마인더의 실제 영문 지시문 예시는 다음과 같다.

The user hasn't heard from you in a while — say in a few words what you're doing, then continue.

각 리마인더는 한 요청에만 넣었다가 다음 요청에서 지우는 것이 아니라 덧붙인 채로 남겨 두므로, 프롬프트 캐시가 계속 일치하고 그 뒤의 thinking 블록도 유효하게 유지된다고 원문은 설명한다.

6. 무인 에이전트와 장기 실행 루프의 안정화 규칙

사람의 직접적인 개입 없이 백그라운드에서 동작하는 자율 코딩 에이전트 환경에서는 턴이 부적절하게 종료되거나 무한 루프에 빠지는 현상을 제어하는 것이 매우 중요하다. 공식 문서는 장기 실행 에이전트의 안정성을 확보하기 위해 구체적인 운영 지침을 제시한다.

6.1. 2~3회 자동 계속 제한과 시간 예산 표기

에이전트가 도구 호출 없이 턴을 마쳤으나 아직 완결해야 할 작업이 남아 있는 경우, 시스템이 자동으로 계속 진행을 명령하는 프롬프트를 주입할 수 있다. 그러나 문서는 동일한 작업에 대해 자동 계속 지시를 무한정 반복하지 말고 2~3회에서 멈추라고 권한다. 그래야 정말로 막힌 실행이 끝나고 검토될 수 있기 때문이다.

시간 예산 표기는 이와 다른 맥락, 곧 리드 에이전트가 서브에이전트에 작업을 위임하는 멀티에이전트 하네스에서 다루어진다. 작업에 걸릴 시간을 추정할 수 있다면, 하네스가 모델에게 돌려보내는 각 메시지 끝에 elapsed 340s / 1200s와 같이 경과 시간과 예산을 초 단위로 적은 짧은 줄을 붙일 수 있다. 다만 원문은 이러한 예산 표기가 단지 모델에게 참고용으로 제공되는 권고 사항일 뿐이며, 한도에 도달했다고 해서 모델이 스스로 실행을 중단하지 않는다는 점을 명확히 한다. 강제적인 실행 중단이 필요하다면 호출 하네스 측에서 자체적인 타임아웃 타이머를 유지해야 한다.

아래는 원문이 완전 무인으로 도는 에이전트용으로 제시한 시스템 프롬프트 추가 문구의 한 예시다. 원문은 이를 출발점으로 삼아 각자의 애플리케이션에 맞게 고치라고 한다. 세션의 첫 요청부터 시스템 프롬프트 끝에 넣어야 하며, 사람이 응답하는 human-in-the-loop 애플리케이션에는 넣지 말라고 한다. 이 문구를 넣으면 작업당 도구 호출과 출력 토큰이 다소 늘어난다.

A standing instruction from the user, the person you are working for. It is about how your turns end. A message with no tool call in it ends your turn, and the work stops there until you are asked to continue. The user has seen you end turns in four ways while work they asked for was still owed, and does not want any of them. One: a long summary of what was done that closes by announcing the next step and has no tool call, so the next thing never starts. Two: an offer to carry on with something unless the user would prefer otherwise, which stops to wait for an answer the user was not going to give. Three: a list of decisions for the user when, by your own account, none of them blocks the rest of the work. Four: deciding that this is a good place to report, because the turn has been long or a milestone is done. Status notes are welcome, and so are your recommendations on open decisions, but put them in the same message as your next tool call and carry on with whatever does not depend on the user's answer. If you notice yourself inviting the user to redirect you or offering to wait, delete it and do the next thing. The stops the user does want are the ones where nothing can move without them, or where the thing blocking you is deliberately protected from you. This does not override the need for confirmation on risky or destructive actions.

6.2. 캐시 무효화 방지와 안전 분류기 거절 응답 처리

운영 환경에서 간과하기 쉬운 두 가지 기술적 세부 사항이 있다. 첫째는 프롬프트 캐시의 보존 여부다. 요청과 요청 사이에 최상위(top-level) effort 값을 동적으로 변경하면 기존에 쌓여 있던 프롬프트 캐시가 무효화된다. 캐시 히트를 유지하면서 개별 턴마다 서로 다른 effort 레벨을 적용하고자 한다면, 베타 사양인 메시지별 effort 변경(per-message effort change) 방식을 채택해야 한다.

둘째는 안전 분류기에 의한 거절 응답이다. Claude Opus 5.5는 생물학, 사이버 보안, 추론 추출(reasoning extraction) 등을 감시하는 안전 분류기를 내장하고 있다. 특정 요청이 안전 정책에 걸려 거절될 경우, 이는 시스템 에러(HTTP 5xx 등)로 반환되는 것이 아니라 stop_reason: "refusal"과 분류 카테고리를 명시한 stop_details 객체를 포함한 정상 API 응답으로 도착한다. 이런 요청은 폴백 모델로 자동 재시도하게 할 수 있다. 다만 reasoning_extraction 거절은 서버 측 폴백이 재시도하지 않고 그대로 돌려준다.

7. 프론트엔드 스타일 지정과 시각 입력 프롬프트 지침

코드 작성 및 멀티모달 입력 처리 영역에서도 이전 세대와 구별되는 거동 특성이 확인된다. Anthropic의 프롬프팅 문서는 시각 디자인 지시와 이미지 분석 작업에서 실질적인 성과를 내기 위한 가이드라인을 함께 다루고 있다.

7.1. 구체적 금지 패턴 명시와 막연한 지시 배제

웹 페이지나 인터페이스 코드를 생성할 때 "일반적인 AI 스타일을 피하라(avoid a generic AI look)"와 같은 막연하고 포괄적인 지시문은 기대만큼 듣지 않는다. 원문은 이러한 일반적인 지시가 대개 모델의 한 기본값을 다른 기본값으로 바꿀 뿐이라고 지적한다. 모델로부터 차별화된 결과물을 얻기 위해서는 피해야 할 구체적인 디자인 패턴을 명시적으로 나열해야 한다.

Output a vanilla HTML/CSS personal website with placeholder data. Do not use a cream or off-white background, italic accent words in headlines, numbered "01/02/03" section labels, monospace labels, or pill-shaped buttons.

위의 원문 예시처럼 피하고자 하는 배경색, 이탤릭 강조어, 번호 매김 형식, 폰트 종류, 버튼 형태를 직접적으로 명시할 때 모델은 지시 사항을 정밀하게 반영한다.

7.2. 고해상도 이미지와 외부 도구 결합

시각적 입력 처리의 경우 도구의 지원 없이도 이전 세대보다 향상된 판독 정확도를 보인다. 특히 기술 도면(technical drawings)과 같이 정보 밀도가 높은 이미지를 분석할 때는 고해상도 이미지를 제공하거나 별도의 이미지 처리 도구를 연동하는 것이 정확도를 더 높여 준다. 원문은 외부 도구가 없는 상태에서 effort를 높이는 조치가 기술 도면의 인식률은 개선하지만 차트 판독에는 큰 영향을 주지 못한다고 밝히고 있다.

또한 일반적인 챗봇 대화 환경에서 흔히 삽입하던 「신중하게 생각하고 답변하라」는 취지의 프롬프트 지시문은 Opus 5.5에서 제거를 고려하라고 문서는 권한다. Anthropic이 실제 채팅 제품에서 수행한 테스트에 따르면 해당 문구를 제거했을 때 답변 품질의 뚜렷한 저하 없이 답변이 더 빨리 시작되었다.

8. 확인하지 못한 것

본 문서 작성 시점 기준으로 공식 문서를 통해 명확히 검증하지 못한 사항은 다음과 같으며, 자의적인 추정이나 지어낸 수치는 일절 배제했다.

  • 공식 가이드 문서의 발행 및 최종 갱신 시각: 원문 HTML 웹페이지 및 마크다운 소스 코드 전반에 정확한 게시일이나 타임스탬프가 표기되어 있지 않아 구체적인 게시 시점을 확인할 수 없었다.
  • 메시지별 effort 동적 변경(beta)의 구체적인 API 파라미터 명세: 본 프롬프팅 가이드 본문에서는 기능의 존재와 캐시 유지 효과만 언급하고 있으며, 구체적인 요청 스키마 명칭은 별도의 effort 문서 링크로 안내하고 있어 본 문서 단독으로는 전체 필드 규격을 확정하지 못했다.
  • 자체 사내 벤치마크 평가셋과의 개별 지연 시간 편차: 원문은 「30% 이상 빠른 출력 토큰 생성 속도」를 측정 조건 없이 단정 문장으로 제시하고, 「medium 레벨의 이전 세대 high 대등 성과」는 Anthropic의 자체 테스트 결과로 제시한다. 개별 기업이나 특정 도메인의 사설 프롬프트 환경에서 발생하는 실제 지연 시간과 비용 증감 폭은 직접 측정하기 전까지 확인할 수 없다.
