AI가 짜준 Next.js + Supabase, 나중에 터지는 자리

경계에서 새는 키, 켠 채로 열려 있는 RLS, 요금이 튀는 구간까지 배포 전에 확인하는 순서

2026-08-03 개발/인프라

서론: 돌아가는 코드와 안전한 코드는 다른 상태다

화면은 다 나온다. 로그인도 되고 글도 써지고 배포도 끝났다. 여기까지 오는 데 걸린 시간은 예전 기준으로는 말이 안 되게 짧다. Next.js와 Supabase의 조합이 AI로 뭔가를 빨리 만들 때 사실상 기본값이 된 이유가 그것이다. 인증, 데이터베이스, 스토리지, 실시간, 배포까지 한 묶음으로 오고, 생성 모델이 이 조합의 코드를 가장 많이 봤다.

문제는 이 스택이 나쁘다는 것이 아니다. 이 조합은 실제로 좋은 선택지다. 문제는 편리한 추상화가 감춰 놓은 동작 원리가 몇 군데 있고, 그 몇 군데가 하필 사고가 나는 자리라는 데 있다. 키가 어디까지 나가는지, 정책이 켜졌다는 표시와 실제로 막혔다는 상태가 어떻게 다른지, 서버 렌더링이 세션을 어떻게 다루는지, 연결이 몇 개까지 늘어나는지. 이런 것들은 화면이 잘 나오는 것과 아무 상관이 없어서 배포 직후에는 티가 나지 않는다. 티가 나는 시점은 사용자가 늘었을 때, 또는 누군가 브라우저 개발자 도구를 열었을 때다.

아래는 그 자리들을 하나씩 짚은 것이다. 항목마다 생성 도구가 흔히 내놓는 형태, 그게 왜 나중에 터지는지, 내 프로젝트에서 어떻게 확인하고 무엇으로 바꾸는지를 붙였다. 공격 방법이 아니라 자기 프로젝트를 점검하는 방향으로만 썼다. 스택 선택 자체를 어떤 기준으로 할지는 지루한 기술을 선택하라, 다시 보기에서 따로 다뤘다.

1. 경계 하나가 번들 전체를 바꾼다

AI가 내놓는 형태

상호작용이 필요한 컴포넌트에 'use client'를 붙이고, 그 파일에서 데이터 접근 유틸을 그대로 import한다. 유틸 안에는 프로젝트 URL과 키를 읽는 코드가 들어 있다. 잘 돌아가므로 그대로 남는다.

왜 나중에 터지나

'use client'는 파일 하나의 성격을 바꾸는 표시가 아니다. Next.js 공식 문서는 이 지시문을 두고 서버와 클라이언트 모듈 그래프 사이의 경계를 선언하는 것이라고 설명한다. 파일에 이 표시가 붙는 순간 그 파일이 import한 것과 직접 렌더링하는 컴포넌트가 전부 클라이언트 번들에 포함된다. 컴포넌트 하나를 클라이언트로 돌린 것이 아니라, 그 아래로 딸린 모듈 그래프 전체를 클라이언트로 옮긴 것이다.

여기서 살려 주는 안전장치가 하나 있다. 환경 변수 규칙이다. 문서는 NEXT_PUBLIC_ 접두어가 붙은 변수만 클라이언트 번들에 포함되고, 접두어가 없는 변수는 빈 문자열로 치환된다고 적는다. 그래서 서버 전용 유틸이 실수로 클라이언트에 딸려 가더라도 비밀 키 값 자체가 번들에 박히지는 않는다. 대신 그 함수는 조용히 동작하지 않는다.

진짜 사고는 이 규칙을 사람이 우회했을 때 난다. 로컬에서 undefined가 떠서 이름 앞에 NEXT_PUBLIC_을 붙여 해결한 경우가 대표적이다. 이 한 번의 수정으로 비밀 키가 빌드 산출물에 문자열로 박힌다. AI에게 오류 메시지를 그대로 주면 이 수정을 제안하는 일이 드물지 않다.

덜 알려진 함정이 둘 더 있다.

  • 공개 변수는 빌드 시점에 동결된다. 문서는 빌드가 끝난 뒤에는 앱이 이 환경 변수의 변경에 반응하지 않는다고 적는다. 하나의 이미지를 여러 환경에 올리는 구성이라면 모든 환경이 빌드 때 값을 그대로 쓴다. 키를 회전해도 재빌드 전까지는 옛 값이 나간다.
  • 동적 조회는 치환되지 않는다. process.env[varName]처럼 변수로 키 이름을 만들거나 const env = process.env로 받아서 접근하면 인라인 대상이 아니다. 설정을 깔끔하게 정리한다는 이유로 이런 리팩터링을 하면 런타임에 값이 사라진다.

확인과 수정

확인은 빌드 산출물을 직접 뒤지는 것이 가장 확실하다. 코드 리뷰로는 import 사슬 세 단계를 놓치기 쉽다.

# 빌드 후 클라이언트 번들에 비밀 키 값이 들어갔는지 본다
npm run build
grep -rF "$SUPABASE_SECRET_KEY" .next/static/ && echo "LEAK" || echo "clean"

# 공개돼서는 안 될 변수 이름이 공개 접두어로 선언돼 있는지
grep -rn "NEXT_PUBLIC_.*\(SECRET\|SERVICE_ROLE\|PRIVATE\)" .env* next.config.*

수정은 서버 전용 모듈에 표식을 박아 두는 쪽이다. server-only 패키지를 import하면 클라이언트 컴포넌트에서 그 모듈을 끌어다 쓰는 순간 빌드 타임 오류가 난다. 런타임에 조용히 빈 값이 되는 대신 빌드가 멈추므로, 사고가 배포 전에 드러난다.

// lib/supabase/admin.ts
import 'server-only'
import { createClient } from '@supabase/supabase-js'

// 이 함수는 RLS를 우회한다. 서버 밖으로 나가면 안 된다.
export function createAdminClient() {
  return createClient(
    process.env.SUPABASE_URL!,
    process.env.SUPABASE_SECRET_KEY!, // 공개 접두어를 붙이지 않는다
    { auth: { persistSession: false } }
  )
}

구조로 푸는 방법도 있다. 클라이언트 컴포넌트를 서버 컴포넌트가 감싸고, 데이터는 서버에서 읽어 직렬화 가능한 props로만 내려보내는 형태다. 문서가 소개하는 children 슬롯 패턴이 여기 해당한다. 클라이언트 컴포넌트에 children으로 넘긴 서버 컴포넌트는 클라이언트 모듈 그래프에 들어가지 않고 서버에서 렌더된 결과만 전달된다.

2. RLS는 켰다고 끝나지 않는다

AI가 내놓는 형태

테이블을 만들고 RLS를 켜는 문장 바로 다음에, 읽기 정책 하나가 딸려 온다. 이름은 대개 모두에게 읽기 허용 같은 것이고 조건은 using (true)다.

alter table public.posts enable row level security;

create policy "Enable read access for all users"
  on public.posts for select
  using (true);

왜 나중에 터지나

RLS를 켜면 정책을 만들기 전까지는 아무것도 나가지 않는다. 공식 문서는 RLS를 켠 뒤 정책을 만들기 전까지 공개용 키로는 API를 통해 어떤 데이터에도 접근할 수 없다고 적는다. 안전한 기본값이다. 문제는 그다음에 붙는 정책이다. using (true)는 RLS를 켠 채로 테이블을 다시 전부 여는 정책이다. 대시보드에서 RLS 배지는 켜짐으로 보이고, 실제로는 익명 롤이 전 행을 읽는다. 켜짐과 막힘은 다른 상태인데 눈으로는 같아 보인다.

정책을 쓸 때 자주 어긋나는 지점이 몇 개 더 있다.

  • 명령별로 따로 걸린다. 읽기 정책만 있으면 쓰기는 막힌다. 반대로 갱신 정책만 만들면 갱신이 동작하지 않는데, 문서는 갱신을 수행하려면 대응하는 읽기 정책이 필요하다고 명시한다. 로컬에서 되던 기능이 운영에서만 실패하면 이 조합을 먼저 본다.
  • USING과 WITH CHECK는 보는 대상이 다르다. USING은 이미 있는 행이 보이는지를 정하고 읽기·갱신·삭제에 적용된다. WITH CHECK는 삽입·갱신 결과 행이 조건을 지키는지 본다. 삽입 정책에 with check (true)를 쓰면 남의 소유자 값을 넣은 행을 만드는 것을 막지 못한다. 소유자 컬럼이 있는 테이블에서는 여기가 가장 흔한 구멍이다.
  • 비로그인 요청에서 auth.uid()는 null이다. 문서는 이 경우 조건이 조용히 거짓이 되어 접근이 막힌다고 설명하면서, 인증 여부를 명시적으로 확인하는 형태를 권한다. 막히는 쪽이라 위험하지는 않지만, 원인 모를 빈 목록의 정체가 대개 이것이다.
  • 사용자 메타데이터를 권한 판단에 쓰면 안 된다. 문서가 흔한 실수로 직접 지목하는 항목이다. 사용자 메타데이터는 사용자가 갱신할 수 있으므로, 여기에 담긴 역할 값을 보고 관리자 여부를 결정하는 정책은 권한 상승 경로가 된다. 앱 메타데이터를 쓰라고 문서가 대안을 명시한다.
  • 뷰는 기본적으로 정책을 우회한다. 뷰는 만들 때 지정하지 않으면 정의자 권한으로 동작해서 기반 테이블의 RLS를 건너뛴다. Supabase의 Security Advisor는 이 항목을 오류 등급 린트로 분류한다. 대시보드에서 뷰를 하나 만들어 목록 화면을 빠르게 처리한 프로젝트가 여기 걸린다.

확인과 수정

확인은 손으로 하지 말고 Advisor를 돌린다. Supabase 대시보드의 데이터베이스 항목에 Security Advisor와 Performance Advisor가 있고, 문제를 고친 뒤 다시 실행할 수 있다. 아래는 이 글의 주제와 직접 얽히는 린트다.

린트무엇을 잡나등급
0013_rls_disabled_in_public공개 스키마 테이블에 RLS가 꺼져 있음. 프로젝트 URL을 아는 사람이 전 데이터를 읽고 고치고 지울 수 있는 상태오류
0010_security_definer_view뷰가 정의자 권한으로 동작해 기반 테이블의 정책을 우회함오류
0002_auth_users_exposed인증 사용자 테이블 내용을 공개로 노출하는 뷰오류
0007_policy_exists_rls_disabled정책은 만들어 놨는데 테이블의 RLS가 꺼져 있음정보
0008_rls_enabled_no_policyRLS는 켜졌는데 정책이 없어 API 접근이 전부 막힘정보
0015 계열사용자가 고칠 수 있는 메타데이터에 의존하는 정책-

수정은 소유자 기준으로 명령별 정책을 나눠 쓰는 형태가 기본이다. 여기에 성능 조치가 하나 붙는다. 문서는 auth.uid()를 (select auth.uid())로 감싸면 Postgres가 문장 단위로 결과를 캐시해 벤치마크 기준 약 95퍼센트 개선이 있었다고 적는다. 정책에 쓰이는 컬럼에 인덱스를 거는 것과 TO 절로 대상 롤을 좁히는 것도 함께 권한다.

-- 명령별로 나누고, 소유자 조건을 두 방향 모두에 건다
create policy "owner reads own rows"
  on public.posts for select to authenticated
  using ((select auth.uid()) = user_id);

create policy "owner inserts own rows"
  on public.posts for insert to authenticated
  with check ((select auth.uid()) = user_id);

create policy "owner updates own rows"
  on public.posts for update to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);

create policy "owner deletes own rows"
  on public.posts for delete to authenticated
  using ((select auth.uid()) = user_id);

-- 정책이 보는 컬럼에는 인덱스를 건다
create index if not exists posts_user_id_idx on public.posts (user_id);

-- 뷰를 쓴다면 호출자 권한으로 돌린다
create view public.post_summaries with (security_invoker = on) as
  select id, user_id, title, created_at from public.posts;

공개 읽기가 실제로 필요한 테이블은 물론 있다. 공지 목록이나 공개 프로필이 그렇다. 그때도 using (true)를 쓰기 전에 그 테이블에 공개하면 안 되는 컬럼이 섞여 있는지를 먼저 본다. 이메일이나 내부 상태 값이 같은 테이블에 있다면 정책이 아니라 테이블을 나누는 것이 답이다. 정책은 행 단위로만 걸리고 컬럼을 가려 주지 않는다.

3. anon key로 할 수 있는 일의 정확한 범위

AI가 내놓는 형태

프로젝트 URL과 공개 키를 NEXT_PUBLIC_ 접두어로 선언하고 브라우저에서 클라이언트를 만든다. 이건 맞는 코드다. 문제는 이 코드를 근거로 키 관리가 끝났다고 생각하는 쪽이다.

왜 나중에 터지나

공식 문서는 공개용 키를 온라인에 노출해도 안전하다고 적는다. 다만 그 근거가 중요하다. 문서가 드는 이유는 공개 구성요소에서는 키 회수가 언제나 가능하다는 것이다. 숨길 수 없으니 숨기는 것을 방어선으로 삼지 않았다는 뜻이지, 그 키로 아무것도 할 수 없다는 뜻이 아니다. 이 키를 가진 요청은 익명 롤로, 로그인한 사용자의 토큰이 붙으면 인증 롤로 동작한다. 그 뒤로 무엇이 보이는지는 전적으로 RLS 정책과 스키마 권한이 정한다.

그래서 정리는 이렇게 된다. 공개 키의 노출은 사고가 아니다. 공개 키와 RLS가 없는 테이블의 조합이 사고다. Advisor의 오류 린트가 이 상태를 두고 프로젝트 URL을 아는 사람이 전 데이터를 읽고 고치고 지울 수 있다고 적는 이유가 그것이다.

반대편의 비밀 키는 성격이 다르다. 문서는 이 키가 RLS 우회 속성을 갖고 있어 프로젝트 데이터에 완전한 접근 권한을 준다고 설명하고, 웹 페이지나 소스 코드나 실행 파일에 넣지 말고 대화나 메일로 보내지도 말라고 적는다. 브라우저에서 쓰면 401이 돌아오지만 문서는 여기에 단서를 단다. 그것이 공격자가 다른 곳에서 그 키를 쓰는 것을 막지는 못한다. 401은 방어가 아니라 실수 방지 장치다. 유출됐다면 즉시 삭제하고 회전하라는 것이 문서의 안내다.

구분공개 키(publishable / anon)비밀 키(secret / service_role)
둘 자리브라우저, 모바일 앱, CLI 등 공개 구성요소서버, 엣지 함수 등 비공개 구성요소만
동작 롤비로그인 익명 롤, 로그인 시 인증 롤RLS 우회 속성을 가진 롤
RLS 적용받는다. 이것이 유일한 방어선우회한다
노출됐을 때설계상 전제. 다만 RLS가 비어 있으면 그대로 사고즉시 삭제하고 회전
Next.js 환경 변수NEXT_PUBLIC_ 접두어를 붙인다접두어를 붙이지 않는다

확인과 수정

  • 브라우저에서 쓰는 키가 공개 키가 맞는지 확인한다. 프로젝트 설정의 API 항목에서 키 종류를 구분해 보여 준다.
  • Data API에 노출되는 스키마 목록을 본다. 기본은 공개 스키마다. REST로 나갈 필요가 없는 테이블은 별도 스키마로 옮기고 노출 목록에서 뺀다. 키가 있어도 API 경로 자체가 없어진다.
  • 권한 상승용 함수를 만들었다면 그 함수가 노출 스키마에 있는지 본다. 문서는 정의자 권한 함수를 노출 스키마에 만들지 말라고 명시적으로 경고한다.
  • 키를 회전했다면 클라이언트 번들도 다시 빌드한다. 공개 변수는 빌드 시점에 박히므로 재배포 전까지 옛 키가 나간다.

4. 세션이 서버 렌더링과 만나는 자리

AI가 내놓는 형태

서버 컴포넌트나 미들웨어에서 세션을 읽고, 없으면 로그인 페이지로 보낸다. 클라이언트에서 쓰던 호출을 그대로 서버로 옮긴 형태다.

// 서버에서 이렇게 쓰면 안 된다
const { data: { session } } = await supabase.auth.getSession()
if (!session) redirect('/login')

왜 나중에 터지나

Supabase의 Next.js 서버 사이드 인증 가이드는 이 지점에 위험 표시를 달아 놨다. 서버는 쿠키에서 세션을 가져오는데 그 쿠키는 누구나 위조할 수 있다는 것이 첫 문장이고, 서버 코드에서 getSession()을 절대 신뢰하지 말라는 것이 두 번째다. 이유도 함께 적혀 있다. 이 호출은 인증 토큰의 재검증을 보장하지 않는다. 현재 가이드는 페이지와 사용자 데이터를 보호할 때 getClaims()를 쓰라고 안내하며, 이 호출은 공개된 공개키로 JWT 서명을 매번 검증한다. 서버에 직접 물어 사용자를 확인하는 getUser()도 같은 목적에 쓸 수 있다.

여기서 끝이 아니다. 서버 렌더링과 세션이 만나면 함정이 세 개 더 생긴다.

  • 서버 컴포넌트는 쿠키를 쓸 수 없다. 그래서 토큰 갱신과 전달을 맡는 미들웨어 계층이 필요하다. 가이드는 이 계층이 토큰을 갱신하고, 갱신된 토큰을 요청 쪽과 응답 쪽에 각각 넘기는 세 가지 일을 한다고 설명한다. 이 계층이 빠지면 세션이 조용히 만료되고, 사용자는 이유 없이 로그아웃되는 경험을 한다. 재현이 어려워 버그 리포트로 잡기 힘든 종류다.
  • 캐시가 세션을 넘겨 준다. 로그인 상태로 렌더된 페이지가 CDN에 캐시되면 다음 사람이 그 화면을 받는다. 가이드의 쿠키 설정 코드가 캐시 관련 헤더를 함께 넘기고, 그 헤더를 응답에 반드시 적용하라고 하는 이유가 이것이다. 개인화된 페이지에 정적 캐시가 붙지 않도록 하는 것은 인증 설정이 아니라 렌더링 설정 쪽 일이다.
  • 라우트 보호는 데이터 보호가 아니다. 미들웨어에서 경로를 막아도 Data API는 그 경로와 무관하게 열려 있다. 매처 목록에서 빠진 경로 하나, 새로 추가하고 등록을 잊은 경로 하나가 곧바로 데이터 유출이 되지 않으려면 데이터 쪽을 RLS가 다시 막고 있어야 한다. 이것이 2번 항목과 4번 항목을 따로 점검해야 하는 이유다.

확인과 수정

// app/dashboard/page.tsx
import { redirect } from 'next/navigation'
import { createClient } from '@/lib/supabase/server'

export default async function DashboardPage() {
  const supabase = await createClient()

  // 서버에 확인을 요청하는 호출을 쓴다
  const { data: { user }, error } = await supabase.auth.getUser()
  if (error || !user) redirect('/login')

  // 여기서도 RLS가 다시 걸린다. 두 겹으로 둔다.
  const { data: posts } = await supabase
    .from('posts')
    .select('id, title, created_at')
    .order('created_at', { ascending: false })

  return <PostList posts={posts ?? []} />
}
  • 로그아웃 상태로 보호 경로에 요청을 보내 200이 아니라 리다이렉트가 나오는지 본다. 브라우저 말고 curl로 본다. 클라이언트 측 리다이렉트는 서버 응답을 가려 준다.
  • 같은 요청의 응답 헤더에서 캐시 관련 값을 확인한다. 개인화된 페이지에 공용 캐시가 붙어 있으면 그것부터 고친다.
  • 미들웨어 매처 목록과 실제 라우트 목록을 나란히 놓고 비교한다. 수동 목록은 반드시 어긋난다. 보호가 기본이고 공개가 예외인 방향으로 매처를 짜면 새 경로를 잊어도 안전한 쪽으로 실패한다.
  • 코드베이스에서 서버 파일의 getSession 호출을 전부 찾아 확인한다.

5. 커넥션은 서버리스에서 다르게 샌다

AI가 내놓는 형태

대시보드에서 복사한 연결 문자열을 DATABASE_URL에 넣고 ORM을 붙인다. 포트는 5432다. 로컬에서 잘 돌고 배포해도 잘 돈다. 사용자가 적은 동안에는.

왜 나중에 터지나

서버리스 환경은 요청이 늘면 인스턴스가 늘어난다. 인스턴스마다 자기 연결 풀을 들고 있으므로 동시 요청 100개는 그대로 연결 100개가 된다. 데이터베이스는 연결 수 상한이 있고, 상한에 닿으면 새 요청이 연결을 얻지 못해 대기하거나 실패한다. 애플리케이션 로그에는 타임아웃만 남아서 원인이 데이터베이스라는 것도 잘 안 보인다. 커넥션 고갈이라는 현상 자체와 풀러의 일반 이론은 스타트업의 Postgres 생존 가이드에서 다뤘으므로, 여기서는 Supabase와 서버리스가 겹칠 때만 생기는 선택 문제를 본다.

공식 문서가 제시하는 세 가지 경로는 목적이 다르다.

경로포트맞는 곳제약
직접 연결5432오래 사는 VM·컨테이너 등 지속 서버기본이 IPv6. IPv4는 애드온이 필요
풀러 세션 모드5432IPv4 전용 망에서 직접 연결을 대신할 때문서가 그 경우에 한해 권한다
풀러 트랜잭션 모드6543서버리스·엣지 함수처럼 짧은 연결이 많은 곳프리페어드 스테이트먼트를 지원하지 않는다

문서는 트랜잭션 모드를 두고 많은 일시적 연결을 필요로 하는 서버리스나 엣지 함수에 이상적이라고 적으면서, 곧바로 제약을 붙인다. 이 모드는 프리페어드 스테이트먼트를 지원하지 않으므로 오류를 피하려면 연결 라이브러리에서 그 기능을 꺼야 한다는 것이다. 이 스위치를 안 끄면 부하가 낮을 때는 아무 일도 없다가, 연결이 재사용되기 시작하는 지점부터 간헐적인 오류가 난다. 재현이 안 되는 오류의 전형적인 출처다.

주소 계열도 조용한 실패 요인이다. 직접 연결은 기본이 IPv6이고 공용 풀러는 모든 요금제에서 IPv4 전용이다. 배포 대상 환경이 IPv6로 나가지 못하면 직접 연결 문자열은 연결 단계에서 실패한다. 생성된 코드만 봐서는 알 수 없는 조건이고, 로컬에서는 잘 되므로 더 헷갈린다.

확인과 수정

  • 배포 환경의 연결 문자열 포트를 확인한다. 서버리스 함수가 5432로 나가고 있으면 그 자체가 점검 대상이다.
  • 트랜잭션 모드를 쓴다면 라이브러리의 프리페어드 스테이트먼트 스위치를 껐는지 확인한다. 스위치 이름은 라이브러리마다 다르다. Prisma는 연결 문자열의 pgbouncer=true, postgres.js는 prepare: false가 그 자리다.
  • 마이그레이션 연결은 분리한다. 스키마 변경 도구는 세션 수준 상태를 쓰는 경우가 있어 트랜잭션 모드와 잘 맞지 않는다. 애플리케이션은 트랜잭션 모드, 마이그레이션은 직접 연결이나 세션 모드로 두는 편이 안전하다.
  • 모듈 최상위에서 클라이언트를 한 번만 만들고 재사용한다. 요청 핸들러 안에서 매번 새 풀을 만드는 코드는 인스턴스 하나가 연결을 여러 개 잡게 만든다.
  • 연결 수와 대기 상태를 지표로 본다. 무엇을 봐야 이상이 보이는지는 데이터베이스를 「보이게」 만든다는 것에서 정리했다.

6. 마이그레이션과 스키마 드리프트

AI가 내놓는 형태

대시보드의 SQL 편집기에 붙여 넣을 SQL 블록이 채팅 답변으로 나온다. 붙여 넣고 실행하면 바로 된다. 파일로는 아무것도 남지 않는다.

왜 나중에 터지나

운영 데이터베이스의 실제 스키마와 저장소의 마이그레이션 파일이 갈라진다. 이 상태가 만드는 결과는 넷이다.

  • 새 환경을 만들 수 없다. 스테이징을 하나 띄우려는데 거기까지 오는 SQL이 어디에도 없다.
  • 되돌릴 근거가 없다. 무엇을 언제 왜 바꿨는지 기록이 채팅 로그에만 있다.
  • 리뷰가 없다. 스키마 변경은 애플리케이션 코드보다 되돌리기 어려운데 정작 승인 절차를 안 거친다.
  • 보안 설정이 버전 관리 밖에 있다. RLS 정책은 스키마의 일부다. 정책이 마이그레이션 파일에 없으면 누가 언제 using (true)를 넣었는지 확인할 방법이 없고, 새 환경에는 정책 없이 테이블만 생긴다.

마지막 항목이 이 글의 다른 항목과 이어진다. 2번에서 정책을 아무리 잘 짜도, 그 정책이 코드로 남아 있지 않으면 다음 배포에서 사라진다.

확인과 수정

확인은 차이를 뽑아 보는 것이다. 원격 스키마와 로컬 마이그레이션 사이의 차이가 SQL로 나온다. 결과가 비어 있어야 정상이다.

# 프로젝트 연결
supabase link --project-ref <project-ref>

# 드리프트 확인. 출력이 비어 있어야 한다
supabase db diff --linked

# 이미 손으로 바꿔 놓은 것을 파일로 회수한다
supabase db diff --linked -f recover_manual_changes

# 이후로는 파일이 먼저다
supabase migration new add_posts_rls
supabase db reset          # 로컬에서 처음부터 재생해 재현성을 확인
supabase db push           # 원격에 적용
  • CI에 차이 확인을 넣고 출력이 비어 있지 않으면 실패시킨다. 드리프트는 생긴 날 잡아야 회수가 쉽다.
  • 정책과 인덱스와 함수도 마이그레이션 파일에 넣는다. 테이블 정의만 넣으면 절반만 관리되는 것이다.
  • 로컬 재생을 습관으로 만든다. 처음부터 다시 돌려서 같은 결과가 나오지 않는 마이그레이션은 새 환경에서 반드시 실패한다.
  • 큰 스키마 변경은 한 번에 올리지 말고 쪼갠다. 나눠 올리는 방식 자체는 GitHub 스택 PR 공개 프리뷰에서 다뤘고, 무중단 변경에서 잠금이 어떻게 걸리는지는 Postgres 생존 가이드 쪽이다.

7. 요금이 튀는 구간

AI가 내놓는 형태

조회는 전 컬럼이다. select('*')가 기본값처럼 나온다. 이미지는 스토리지에 올린 원본을 그대로 img 태그에 건다. 실시간 구독은 컴포넌트 안에서 열고 정리 코드는 없다.

왜 나중에 터지나

요금이 뛰는 자리는 대개 데이터베이스 크기가 아니다. 아웃바운드 전송량이다. 2026년 8월 기준 공개 요금표를 정리하면 이렇다.

여기서 읽어야 할 것은 절대 금액이 아니라 무엇이 과금 단위인가이다. 전송량이 GB 단위로 과금되는데 목록 화면 하나가 큰 텍스트 컬럼이나 JSON 컬럼을 통째로 내려보내고 있다면, 화면은 멀쩡한 채로 청구서만 자란다. 이미지도 같다. 원본 해상도 파일을 목록 썸네일 자리에 그대로 걸면 방문 한 번에 수 MB가 나간다.

운영 조건도 두 가지 확인해 둔다. Free 요금제는 1주간 활동이 없으면 프로젝트가 일시정지되고 활성 프로젝트는 2개까지다. 검증용으로 만든 프로젝트를 그대로 운영으로 올린 구성이라면 이 조건이 어느 날 서비스 중단으로 나타난다. Pro 요금제는 지출 상한이 기본으로 켜져 있고, 한도를 넘겨 쓰려면 직접 꺼야 한다. 상한을 켠 채로 두면 요금이 튀지 않는 대신 한도에서 서비스가 제한되고, 끄면 반대가 된다. 어느 쪽이든 모르고 있는 상태가 가장 나쁘다.

확인과 수정

  • 대시보드의 사용량 화면에서 항목별로 본다. 전송량이 예상보다 크면 어떤 요청이 큰지부터 찾는다.
  • 조회에 컬럼을 명시한다. 목록 화면에 필요한 컬럼은 대개 서너 개다.
  • 이미지는 변환을 거치거나 크기를 나눠 저장하고, 캐시 헤더를 붙인다. 같은 파일을 매번 새로 내려보내지 않게 하는 것만으로 전송량이 크게 줄어든다.
  • 실시간 구독은 정리 함수에서 반드시 해제한다. 화면을 오갈 때마다 구독이 쌓이면 연결과 전송량이 함께 늘어난다.
  • 지출 상한 설정을 확인하고, 어느 쪽으로 두기로 했는지 팀 안에서 합의해 둔다.
// 목록 화면에서 필요한 컬럼만
const { data } = await supabase
  .from('posts')
  .select('id, title, thumbnail_url, created_at')
  .order('created_at', { ascending: false })
  .range(0, 19)
2026년 8월 기준. 요금 항목과 단가는 바뀐다. 위 표는 확인 시점의 공개 요금 페이지 값이며, 결제 판단은 반드시 공식 요금 페이지에서 다시 확인한다.

8. 배포 전에 한 번씩 도는 순서

순서에 의미가 있다. 위쪽 항목이 아래쪽 항목의 전제이기 때문이다. 정책이 없는 상태에서 라우트 보호를 아무리 정교하게 해도 소용이 없고, 마이그레이션에 정책이 없으면 정책을 고쳐도 다음 배포에서 되돌아간다.

순서확인할 것보는 방법통과 기준
1공개 스키마 테이블의 RLSSecurity Advisor 실행오류 등급 린트 0건
2using (true) 정책정책 목록을 읽고 대상 테이블 확인공개가 의도된 테이블에만 존재
3소유자 컬럼의 삽입·갱신 조건WITH CHECK 절 확인두 방향 모두 소유자 조건이 걸림
4비밀 키의 번들 유입빌드 후 산출물 문자열 검색일치 0건
5서버 코드의 세션 판단getSession 호출 검색권한 판단 자리에 없음
6보호 경로의 캐시 헤더로그아웃 상태로 curl 요청개인화 페이지에 공용 캐시 없음
7서버리스 연결 포트와 옵션배포 환경 변수 확인트랜잭션 모드면 프리페어드 꺼짐
8스키마 드리프트supabase db diff --linked출력이 비어 있음
9전송량 상위 요청사용량 화면과 조회 코드 대조목록 조회에 전 컬럼 조회 없음
10요금제와 지출 상한결제 설정 확인선택한 상태를 팀이 알고 있음

이 열 줄은 한 번에 다 하려고 만든 것이 아니다. 1번부터 4번까지가 급한 것이고, 나머지는 사용자가 붙기 시작한 뒤에 해도 늦지 않다. 다만 4번은 오늘 하는 편이 좋다. 키가 이미 나가 있다면 시간이 지날수록 회수 비용만 커진다.

확인하지 못한 것

  • 요금 항목·포함량·초과 단가는 2026년 8월 기준 공개 요금 페이지 값이다. 요금제 구성은 바뀌므로 결제 판단 시점에 다시 확인해야 한다. 한도를 넘겼을 때의 구체적인 제한 동작은 요금제와 설정에 따라 달라 일반화하지 않았다.
  • getClaims()의 반환 구조와 비대칭 키 검증 적용 여부는 프로젝트 설정과 라이브러리 버전에 따라 달라진다. 본문 예제에는 형태가 안정적인 getUser()를 썼다.
  • Advisor 린트 번호와 등급은 목록이 갱신될 수 있다. 번호가 아니라 대시보드가 표시하는 설명을 기준으로 판단한다.
  • 어떤 AI 코딩 도구가 어떤 기본 템플릿을 내놓는지는 도구와 버전마다 다르다. 본문의 「AI가 내놓는 형태」는 특정 제품의 출력을 특정한 것이 아니라 이 스택에서 반복적으로 관찰되는 형태를 정리한 것이다.
  • 연결 라이브러리별 프리페어드 스테이트먼트 옵션은 라이브러리 문서가 우선이다. 본문에 적은 두 예시 외의 조합은 각 라이브러리 문서에서 확인해야 한다.

결론: 추상화를 걷어야 하는 지점은 정해져 있다

이 스택을 쓰지 말라는 이야기가 아니다. 반대다. 이 조합이 좋은 이유는 인증과 데이터베이스와 정책이 한 자리에 모여 있어서 확인할 지점이 적다는 것이고, 위의 열 줄이 그 적은 지점의 목록이다. 직접 붙여 만들었다면 같은 것을 확인하기 위해 훨씬 여러 곳을 봐야 한다.

AI가 짜준 코드의 문제도 코드 품질이 아니다. 생성 모델은 돌아가는 코드를 만들도록 최적화돼 있고 실제로 잘 만든다. 다만 돌아가는 것과 안전한 것과 싼 것은 서로 다른 목표이고, 뒤의 둘은 화면에 나타나지 않는다. 그래서 확인은 사람이 남겨 둔 몫으로 남는다.

기준을 하나만 남긴다면 이것이다. 이 코드가 무엇을 막고 있는지 한 문장으로 말할 수 없으면 아직 아무것도 막고 있지 않다고 본다. RLS를 켰다는 사실은 문장이 아니다. 어떤 롤이 어떤 조건으로 어떤 행에 접근하는가가 문장이다. 그 문장을 쓸 수 있게 되는 데 드는 시간은 반나절 정도고, 그걸 미뤘을 때 드는 시간은 예측할 수 없다.
