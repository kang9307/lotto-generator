1. mimalloc とは何か - Microsoft Research 産、MIT ライセンス

mimalloc は 2019 年頃に Microsoft Research が公開した汎用メモリアロケータです。公式リポジトリは github.com/microsoft/mimalloc、ライセンスは MIT です。C/C++ 標準の malloc・free・realloc・calloc セマンティクスをそのまま踏襲しながら、より速くより断片化が低くなるよう設計されています。Windows・Linux・macOS・FreeBSD のすべてでビルドでき、静的ライブラリ・動的ライブラリ・ヘッダ単独利用すべてに対応します。

筆者の視点で mimalloc が他のアロケータと区別される最大の特徴は3つです。第一に drop-in 互換です。既存バイナリを再コンパイルせずに LD_PRELOAD=/path/to/libmimalloc.so を挟むだけで即適用できます。第二に free list sharding という設計哲学です。スレッド別に free list を持ち、ページ単位でオブジェクトをまとめてロック競合を最小化します。第三に secure モードです。-DMI_SECURE=ON でビルドすると、ヒープオーバーフロー・double free・use-after-free の一部を追加コストなしで防御します。

バージョンは 2026 年 5 月時点で v2.x ラインが安定版、v3.x が開発ラインです。Rust バインディング(mimalloc crate)、Go の cgo バインディング、Node.js の一部ネイティブアドオンで採用されており、GitHub Star は1万を優に超えています。筆者が適用してみた環境でもビルドがシンプルで依存がほぼなく、統合コストが非常に低いと感じました。

2. アロケータ比較マトリクス - glibc / jemalloc / tcmalloc / mimalloc / rpmalloc

本格的に mimalloc を評価する前に、主要アロケータ5つを1つの表に整理します。筆者が適用・観察した経験と公開ベンチマークを総合した比較マトリクスです。

glibc malloc(ptmalloc2)GNULGPL標準・汎用一般 Linux ワークロード
jemallocMeta(旧 Facebook)BSD断片化最小化長期実行 DB・キャッシュ
tcmallocGoogleApache 2.0マルチスレッドに強い大規模サーバワークロード

筆者が整理した選択基準は単純です。一般 Linux サービスは glibc で始める、DB・キャッシュなど断片化が大きい長期実行ワークロードは jemalloc、大規模マルチスレッドサーバは tcmalloc または mimalloc、セキュリティと性能を同時に求めるなら mimalloc-secure、ゲームエンジン・リアルタイムは rpmallocです。5つのいずれもすべてのワークロードで最速ではありません。

3. mimalloc の核心設計5つ - 筆者整理

mimalloc の公式論文と README に散らばる設計哲学を筆者視点で5つに整理します。

3-1) Free list sharding(スレッドキャッシュ)

各スレッドが自分専用の free list を持ち、ページ単位(64KB・512KB など)でオブジェクトをまとめて管理します。同じスレッド内で起きる確保・解放はロックなしで進みます。他スレッドが送った free 要求は別の「thread-free」キューに積まれて定期的にマージされます。ロック競合がほぼ消えるため、マルチスレッドワークロードで大きな利得が出ます。

3-2) 小オブジェクト最適化

16 バイト単位の小オブジェクトはページ単位で分離管理されます。小オブジェクトがワークロードの 70~90% を占める一般的なサーバでは、この最適化だけで確保パスが平均数十サイクルに短縮されます。筆者が見た事例で短寿命オブジェクトが多いワークロードは、mimalloc 適用後 CPU の 5~15% が解放されました。

3-3) Secure モード(ヒープオーバーフロー防御)

-DMI_SECURE=ON でビルドすると次の防御が追加されます。(a) free list pointer 暗号化 - 攻撃者が free list を上書きしても次の確保先を予測しにくくなります。(b) guard page 追加 - ページ境界の overflow が即座に SIGSEGV で捕捉されます。(c) double free 検出強化。secure モードのオーバーヘッドは一般に 3~5% 程度と言われ、筆者が測定した事例も同様でした。セキュリティ要求の高い環境では有効化する価値が十分あります。

3-4) 低断片化(low fragmentation)

ページ単位管理と sharding により外部断片化が非常に低く保たれます。長期実行ワークロードで時間と共に RSS が急増する典型的問題(特に glibc malloc)への良い代替です。jemalloc が同領域で強く、mimalloc も一般的に同等水準まで到達します。

3-5) Drop-in 互換(LD_PRELOAD)

最も魅力的な部分です。既存バイナリを再コンパイルせずに LD_PRELOAD=/usr/lib/libmimalloc.so myserver 一行で即時に mimalloc が適用されます。「試して気に入らなければ戻すコストが 0」という点は本番適用判断で最大の優位性です。jemalloc・tcmalloc も同じ方式が可能ですが、mimalloc のビルド・インストールが最もシンプルだという点が筆者が見た最大の違いです。

4. ベンチマーク分析 - どのワークロードで速いか

公式 mimalloc-bench の結果と筆者が直接測定した事例を合わせて整理します。

4-1) 短寿命オブジェクトが多いワークロード - 最強

JIT コンパイラ、インタプリタ、RPC サーバのように毎秒数十万~数百万個の小オブジェクトを確保・解放する環境で、mimalloc は glibc malloc 対比 1.5~3 倍速い結果がよく出ます。tcmalloc とは互角か、一部のマイクロベンチマークで mimalloc が上回ります。

4-2) マルチスレッドサーバ - 強い

スレッド数が増えるほど free list sharding の利得が大きくなります。32~64 スレッド環境で mimalloc が glibc malloc の 2 倍以上のスループットを出すケースが多いです。Redis 系の単一スレッドサーバでは利得が小さいですが、ScyllaDB・Cassandra 系のマルチスレッド DB では明確です。

4-3) 巨大オブジェクトワークロード - 普通

数 MB 以上の巨大オブジェクト確保が主体のワークロード(例: 動画エンコードバッファ)では mimalloc の利得は大きくありません。すでに system mmap パスが使われるためアロケータ選択の影響が小さくなります。

4-4) 非常に長寿命オブジェクト - jemalloc 優位の可能性

オブジェクト寿命が数時間~数日に及ぶワークロード(データベースインデックスなど)では、jemalloc が断片化安定性の面でやや信頼されます。筆者が見たデータベース運用事例の多くが jemalloc を選んだ理由はここにあります。

4-5) まとめ

一行で要約すると 「短寿命・小オブジェクト・マルチスレッド = mimalloc、長寿命・巨大オブジェクト・断片化安定性 = jemalloc」です。筆者の推奨は単一の数値で比較せず、本人のワークロードトレースで直接マイクロベンチマークを回す方法です。

5. mimalloc に切り替える価値がある5つのシナリオ - 筆者整理

筆者が整理した「mimalloc の置き換えが正当化される5つのシナリオ」です。いずれか1つでも該当すれば staging 負荷テストを進める価値があります。

5-1) マルチスレッドサーバ(Redis Stack・ScyllaDB・高同時実行 API)

スレッド数が16以上で、リクエスト毎に多数の小オブジェクトを確保・解放する環境です。ロック競合が CPU プロファイルで目立つなら、mimalloc がほぼ確実に役立ちます。

5-2) JIT コンパイラ環境(Node.js・V8・JVM の native 領域)

JIT コード自体が短寿命オブジェクトを爆発的に作ります。Node.js サイドカー、V8 組み込み環境、JVM の native 領域(JNI 呼び出しなど)で mimalloc がよく推奨されます。

5-3) メモリ断片化が大きい長期実行ワークロード

数日~数週間単位で再起動なしに動作するサービスで時間と共に RSS が増えるパターンが見えるなら、mimalloc または jemalloc の置き換えを検討する時期です。

5-4) セキュリティが重要なシステム(mimalloc-secure)

ネットワーク公開サービス、ユーザ提供入力をパースするサービスでは mimalloc-secure が追加コスト 3~5% でヒープオーバーフロー防御を提供します。筆者の視点でセキュリティコスト対比で最も合理的な選択です。

5-5) Rust・C++ プロジェクトのグローバルアロケータ置き換え

Rust プロジェクトは #[global_allocator] 一行で mimalloc をグローバルアロケータに指定でき、C++ プロジェクトはリンク段階で置き換えればよいです。コンパイル時統合のため LD_PRELOAD よりも一貫した動作が保証されます。

6. 言語別統合方法 - C/C++・Rust・Go・Java

筆者が適用してみた経験を基準に言語別統合難度を整理します。

6-1) C/C++ - LD_PRELOAD またはリンク

最も簡単です。ビルド済みバイナリに LD_PRELOAD=/usr/lib/libmimalloc.so 環境変数を付けるだけで即動作します。ビルド時統合したい場合は -lmimalloc でリンクするか、mimalloc の mi_malloc・mi_free を直接呼ぶこともできます。

6-2) Rust - GlobalAlloc 置き換え

Rust 統合が最も優雅です。Cargo.toml に mimalloc = "0.1" を追加し、main.rs に #[global_allocator] 一行を宣言すれば終わりです。詳細コードは7章で扱います。

6-3) Go - cgo(限定的)

Go は独自のメモリアロケータ(tcmalloc 派生)を使うため、一般のユーザコードでは mimalloc 置き換えが困難です。cgo で呼ぶ C ライブラリ領域のみ LD_PRELOAD で置き換えられる程度です。Go コア領域まで置き換えるにはランタイムを直接パッチする必要があり、推奨しません。

6-4) Java - JNI / 利用困難

JVM は独自の GC と native heap を持ちます。mimalloc は JNI 呼び出し領域の native 確保にのみ影響を与え、一般 Java オブジェクトには適用されません。JVM 本体に mimalloc を組み込む試みが一部 OSS で進行中ですが、本番に推奨するには時期尚早です。

7. 実戦統合例 - Rust でグローバルアロケータ置き換え

最もよく使われる Rust 統合をコードで示します。筆者がサイドプロジェクト2件で適用した形と同じです。

7-1) Cargo.toml 依存追加

[dependencies]
mimalloc = "0.1"

# オプション: secure モードを有効化する場合
# mimalloc = { version = "0.1", features = ["secure"] }

7-2) main.rs でグローバルアロケータ宣言

use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;

fn main() {
    // この時点から Box, Vec, String などすべての標準確保が mimalloc を経由する
    let v: Vec<i32> = (0..1_000_000).collect();
    println!("sum = {}", v.iter().sum::<i32>());
}

7-3) ビルドと確認

cargo build --release
./target/release/myapp

# RSS 確認(Linux)
ps -o pid,rss,command -p $(pgrep myapp)

ビルド時に C コンパイラ(gcc または clang)が必要なため、CI では apt install build-essential などのパッケージが事前にインストールされている必要があります。ビルド時間は平均 5~10 秒追加されます。筆者が測定した RSS はワークロードによって 5~15% 減少または 5% 以内の増加の間でした。

ヒント - 同じバイナリで mimalloc と glibc malloc の結果を比較したい場合は、LD_PRELOAD 方式で一度、GlobalAlloc 方式で一度ビルドして同じワークロードで測定してください。環境変数の変更だけで直接比較が可能な点が最大の強みです。

8. 本番採用事例 - Microsoft 内部 / GitHub OSS

筆者が確認した公開事例を整理します。

  • Microsoft 内部: Azure の一部コンポーネントと .NET Core の一部領域で mimalloc を採用しています。Microsoft Research が直接作っただけに、親会社レベルの検証が十分という信号です。
  • Rust 生態系: 少なくない Rust サーバ・DB・観測ツールが #[global_allocator] として mimalloc を採用しています。GitHub で mimalloc = "0.1" を検索すると数千の Cargo.toml が出てきます。
  • ゲーム・リアルタイムシステム: 一部ゲームエンジンが mimalloc または rpmalloc を評価中です。2つの候補がゲームワークロードでよく比較されます。
  • 高性能データベース: 一部 ScyllaDB・DuckDB ユーザが mimalloc を試行中ですが、データベース本流は依然として jemalloc 比重が大きいです。

筆者の見るところ mimalloc の採用曲線は 2026 年により急になる可能性が高いです。Microsoft の後方支援、MIT ライセンスの自由度、drop-in 互換性という3要素が合わさり参入障壁が低いためです。

9. リスクと限界 - 正直な点検

mimalloc も完璧ではありません。筆者が見た主要リスクは次の通りです。

9-1) メモリ使用量(RSS)増加の可能性

スレッド別キャッシュがメモリを先取りするため RSS が glibc malloc より増えることがあります。スレッド数が多く idle 状態が長いワークロードでは特に目立ちます。MIMALLOC_PURGE_DELAY・MIMALLOC_SHOW_STATS などの環境変数でチューニングできますが、デフォルトがすべての環境で最適ではありません。

9-2) デバッグツールとの相互作用

Valgrind・AddressSanitizer は自前のアロケータを差し込むため、mimalloc と同時に使うと一部の検出機能が弱くなります。mimalloc はデバッグビルド(-DMI_DEBUG=ON)を提供しますが、標準ツールとの統合経験は glibc malloc が依然として最も滑らかです。

9-3) glibc 特化動作に依存するコード

glibc malloc の非標準動作(特定アライメント保証、mallopt チューニングなど)に依存するレガシーコードは mimalloc に切り替えると壊れることがあります。通常は問題ありませんが、組み込み・ドライバ領域では事前検証が必要です。

9-4) マルチプロセス fork() 時のキャッシュ無効化

fork() 直後の子プロセスの mimalloc キャッシュは無効化処理が必要です。一般的に自動処理されますが、fork-heavy なワークロード(例: Apache prefork)では別途検証が必要です。

9-5) まとめ

リスクはすべて管理可能なレベルですが、「本番適用前に staging で1週間の負荷テスト」は筆者の視点で交渉不可です。RSS・latency・p99 を glibc 対比で定量比較してから決定してください。

10. 2026 メモリアロケータトレンド - mimalloc 以外の流れ

筆者が整理した 2026 年メモリアロケータトレンド3つです。

10-1) Hardware-aware allocator の台頭

NUMA・HBM・persistent memory(Optane 後継)のような新しいメモリ階層を認識するアロケータが徐々に増えています。mimalloc も NUMA 対応強化の方向で v3.x を開発中です。jemalloc はすでに NUMA 認識が強いです。

10-2) mimalloc 派生(mi variants)拡散

mimalloc コードをベースにした派生が増えています。snmalloc(Microsoft Research の後続作)、ゲーム用 mi-game のような fork・派生が GitHub に登場します。筆者は派生を本番に使う前にメンテナの活動状況とパッチ周期を必ず確認します。

10-3) Rust 生態系のグローバルアロケータ標準化圧力

Rust 陣営で「標準アロケータを mimalloc または jemalloc に変えよう」という議論が定期的に登場します。標準は変わらない可能性が大きいですが、実務では #[global_allocator] 宣言が次第に一般化しています。筆者の推奨は新規 Rust プロジェクトで mimalloc を標準選択にするパターンです。

11. 結論 + 今週できる3つのアクション

mimalloc を一行で要約すると、「戻すコストが 0 に近い drop-in malloc 置き換えで、マルチスレッド・短寿命オブジェクトワークロードではほぼ常に利得」です。筆者が自分の環境ですぐに適用する3つのパターンを共有します。

11-1) 即適用1: LD_PRELOAD で30分の PoC

運用中のバイナリに LD_PRELOAD=/usr/lib/libmimalloc.so を挟んで30分負荷を流してください。RSS・CPU・latency を glibc 対比で比較し、利得が明確なら staging 負荷テストへ、利得が小さければそのまま戻せばよいです。筆者が見た最も速い意思決定経路です。

11-2) 即適用2: 新規 Rust プロジェクトは標準で mimalloc

Rust で新規サービスを作るなら Cargo.toml に mimalloc = "0.1" を追加し #[global_allocator] を宣言してください。5分で済みます。損する可能性はほぼなく、利得はワークロード次第で 5~30% です。

11-3) 即適用3: セキュリティ重視サービスは mimalloc-secure を検討

ネットワーク公開・ユーザ入力をパースするサービスは mimalloc-secure ビルドで追加 3~5% のコストでヒープオーバーフロー防御を得てください。セキュリティコスト対比で最もコスパの高い防御策の1つです。

最後に筆者が強調するメッセージはこれです。メモリアロケータは「見えない性能レバー」です。コード一行、環境変数一行で p99 latency を二桁%変えられる領域は珍しいです。mimalloc はその珍しい領域で最も参入障壁が低いツールです。筆者の視点で 2026 年の新規システム設計者なら一度は必ず評価すべきコンポーネントです。
