Where LLM-Generated Charts Break - What a Semantics-Driven Spec Decides for You, and What It Costs

Axis type errors, integer dates, color overuse, and specs where 'just this part' never lands

Aug 3, 2026 Tech & IT

Introduction: 'Just change the bar color' repaints the whole chart

You send the model one line. 'Just make the bars blue.' The chart comes back blue. But the canvas width you tuned by hand yesterday has reverted, the axis tick interval has shifted, and a few labels now overlap. You got one fix in exchange for three regressions you did not notice.

That is not bad luck, and that is where this article starts. The places where things break are remarkably predictable. Once in deciding whether an axis is continuous or categorical. Once in deciding how to read an integer that looks like a date. Once in deciding how many colors to spend. And again in which line of the spec an instruction like 'just this part' actually lands on.

None of these four come from a lack of intelligence in the model. They come from the fact that there are too many slots for the model to fill, and those slots are entangled with each other. A single well-made Vega-Lite chart pins down scale domains, time units, mark widths, canvas width, label angles, color schemes and legend placement, all by hand. Change one and six others go out of alignment. Humans hit this too. A model that rewrites the whole thing from scratch every turn hits it harder.

In July 2026 Microsoft Research published Flint. You declare what each field means, and a compiler derives parsing, axes, formatting, colors and layout from that declaration. The point of this article is not to introduce Flint, but to look at what problem it is actually solving and what that approach gives up. Tools change; this problem does not.

Here is the conclusion up front. What a semantics-driven spec reliably buys you is not a prettier chart but a short, editable chart definition. Quality improvement is measurable but narrow, and, interestingly, the benefit shrinks as models get stronger. The reduction in specification length, however, holds regardless of model. That is where the adoption decision splits.

1. The failures are predictable - five of them

Anyone who has handed chart generation to an LLM will recognise this list. These five repeat in nearly identical form whether the grammar is Vega-Lite, ECharts or Matplotlib.

FailureWhere in the spec it originatesHow it shows on screenDo people catch it?
Wrong axis typePicking the wrong scale among quantitative, ordinal and nominalA continuous measure scatters into twenty bars, or categories get joined by a lineUsually yes
Temporal parsing failureFeeding integer or string dates straight into a time axisEverything lands somewhere in the 1970s, or the order scramblesHard to catch
Stacking non-additive valuesStacking ratios, averages or ranks in a bar chartTotals exceed one hundred percent, or the height means nothingAlmost never
Color misuse and overuseSequential ramps on diverging fields, rainbows across twenty categoriesZero lands on an off-center color, and the legend eats the canvasOveruse is visible; misuse is not
Edits landing on the wrong propertyOne request spread across several propertiesSomething other than what you asked for changesVisible instantly, cause is not

The third and fourth are the bad ones, because the output looks fine. A broken axis just gets redrawn, but a bar chart stacking ratios goes straight into the meeting deck. The value of a visualization comes not from beauty but from the time it takes to notice something is wrong, and those two failures push that time toward infinity. The underlying question of what you have to look at before an anomaly becomes visible is one I have worked through separately for database observability.

The fifth has a different character. Where the first four are generation-time problems, this one is a repair-time problem. And in an LLM workflow charts are almost never finished in one shot. The conversation always continues with 'nice, but just this one thing'.

2. One column of 202001 splits three ways

Abstractions do not land, so take a concrete case. The Flint paper uses the same situation, and it is one you meet constantly in corporate data warehouses. The period column of a monthly metrics table stores 202001, 202002 and so on as a six-digit integer.

A person reads that instantly as January 2020. So does the model. The problem is that the moment the model translates what it read into a specification, the path splits three ways.

The model's choiceWhat ends up in the specResultWhy it happens
Straight to a time axisField typed as temporalYears collapse or the axis tangles202001 read as UNIX seconds or as a year value
Escape into categoriesField typed as nominalSeventy-two slots appear and labels collideSix years is seventy-two months, each an independent category
Parse it by handCalculate transform, time unit, mark width, canvas width, label angleComes out correctlyFive values must agree with each other

The third is correct, and the shape of that correctness is the problem. Written properly in Vega-Lite it looks roughly like this.

{
  "transform": [
    { "calculate": "datetime(floor(datum.Period/100), datum.Period%100-1)",
      "as": "PeriodDate" }
  ],
  "mark": { "type": "bar", "width": { "band": 0.9 } },
  "encoding": {
    "x": {
      "field": "PeriodDate", "type": "temporal", "timeUnit": "yearmonth",
      "axis": { "format": "%Y-%m", "labelAngle": -45, "labelOverlap": "greedy" }
    },
    "y": { "field": "Users", "type": "quantitative", "aggregate": "sum",
           "scale": { "zero": true } }
  },
  "width": 504
}

Count the places the model can get this wrong. The division and modulo combination, whether the month index is zero-based or one-based, the time unit string, the format string, the label angle, the overlap strategy, the band ratio, the canvas width. Eight of them. And several depend on each other. Widen the canvas to 720 and you can reset the label angle to zero, and the band ratio needs another look.

Here is the core of it. The model already knows this is January 2020. The breakage happens while translating what it knows into eight low-level parameters. So stop asking for the translation and let it write down what it knows. That is the premise of a semantics-driven specification.

3. Write it short and it looks poor; write it long and it breaks

Visualization grammars carry an old dilemma, and it is exactly where the Flint paper and the official blog begin.

  • Short specs lean on system defaults. Three lines produce a chart, but the axis format is flat, labels collide, and colors are whatever the library ships.
  • Long specs give you what you want. In exchange they are verbose, brittle, and hard for a person to open and understand why each choice was made.
  • People move between the two by iterating. Draw it, fix one line, look again.
  • Models struggle with that loop. Because they regenerate the whole thing each turn, they oscillate rather than converge.

One more thing rides on top. Long specs consume tokens. A pipeline that rewrites a sixty-line JSON document every turn grows linearly in cost as the conversation lengthens. And of those sixty rewritten lines, exactly one actually changed.

Compressing structure before handing it to a model is a point already validated on the code side. Turning a codebase into a queryable graph aims at the same thing: do not throw everything at the model, give it a representation that leaves only what the model must decide.

4. What semantic types decide - a three-level hierarchy

A Flint specification splits in two. One part declares what the fields are, the other declares which chart goes on which channels. The minimal shape shown in the repository looks like this.

import { assembleVegaLite } from 'flint-chart';

const spec = assembleVegaLite({
  data: { values: myData },
  semantic_types: { weight: 'Quantity', mpg: 'Quantity', origin: 'Country' },
  chart_spec: {
    chartType: 'Scatter Plot',
    encodings: { x: { field: 'weight' }, y: { field: 'mpg' },
                 color: { field: 'origin' } },
    baseSize: { width: 400, height: 300 },
  },
});

Declaring origin as Country carries several decisions with it. It is categorical, unordered, bounded in cardinality, naturally distinguished by color, labelled by name in the legend, and must not receive a sequential color ramp. One word standing in for six low-level settings.

The type system is not flat but a three-level hierarchy. The paper describes it as follows.

LevelWhat it decidesCountExamples
Level 1 - domainParsing strategy. What the value is read as in the first place6Temporal, categorical, measure, discrete, identifier, geographic
Level 2 - familyAggregation behaviour, the meaning of zero, domain structure15DateTime, duration, entity, binned, amount, proportion, rating, rank, coordinate
Level 3 - typePresentation. Formatting, ordering, default color family44YearMonth, month, percentage, revenue, profit, latitude, status, direction

The hierarchy matters because of inheritance. Adding a new type does not require defining parsing and aggregation rules from scratch; it inherits the parent's behaviour and narrows only the presentation. For an organisation that already maintains a metrics dictionary, that structure maps cleanly.

Why there are two numbers. The repository documentation says more than seventy semantic types; the paper says forty-four at level three. They count different layers. Include families and aliases and you get the first number; count only leaf types and you get the second. Quote either without saying which basis you used and they look contradictory.

Level two is where the practical value sits. Separating amounts from proportions means the decision of whether stacked bars are permissible happens at the type level. The non-additive stacking failure I marked 'almost never caught' is structurally blocked right there. Something a human reviewer used to have to catch is caught by a type instead.

5. What the compiler does - three stages

Getting from a declaration to an actual chart spec takes three stages. Knowing the structure tells you which stage to suspect when the output is wrong.

  1. Semantics resolution. Field properties are settled by looking at the semantic types together with the raw data. Parsing, scale kind, formatting and aggregation come out here.
  2. Optimization. Layout is solved as a constraint problem. Axis span, item step size, padding and facet configuration are decided against data cardinality and canvas limits together.
  3. Code generation. The library-agnostic property set is stamped through per-backend templates: Vega-Lite, ECharts, Chart.js, Plotly, and native Excel charts through Office.js.

Stage two is the least discussed part of this design. The paper treats each axis, group and facet panel as a compressible container with a preferred size and a minimum readable threshold. Discrete layouts expand or compress items until the constraints are satisfied; continuous layouts stretch the canvas to reduce overlap. Globally it tunes aspect ratio using the banking to forty-five degrees principle and balances facet wrapping.

This is the important part. A seventy-two-month axis avoids collisions not because the model happened to pick a canvas width of 504 pixels, but because the optimizer worked backwards from a minimum readable width. The model does not need to know that number. Which raises the opposite question: how do you intervene when you want to set that number yourself? That is the next section.

Multiple backends matter more in practice than they sound. The same spec going out as ECharts on the web and as a native Excel chart in a deliverable means the recurring argument about whether to send a screenshot or the source file disappears. The Excel side is produced as an editable native chart, not an image.

6. A spec you can edit in place - this is the real fork

Here is the central claim of this article. In an LLM workflow, the value of spec design comes not from first-shot generation quality but from where the second instruction lands.

The reason is simple. No conversation finishes a chart in one turn. Real ones go like this.

  • 'Make it monthly' - time unit change
  • 'Start the y axis at zero' - scale baseline
  • 'Move the legend below' - placement
  • 'Highlight only this region' - conditional color channel
  • 'Flip it horizontal' - channel swap

In a low-level grammar each of those five touches two or three different places in the spec at once. 'Start the y axis at zero' alone moves the scale domain, the axis tick configuration and sometimes the canvas height together. The model cannot handle that as a partial edit, so it rewrites everything. And rewriting means the previous four edits are probabilistically lost.

AreaWhat the user or model writesWhat the compiler decides
FieldSemantic type, fixed value range, reference pointParsing rules, scale kind, formatting, ordering
ChartChart type, channel bindings, aggregation functionMark properties, axis ticks, legend configuration
LayoutBase sizeAxis span, step size, padding, facet placement, aspect ratio
Color(indirectly, through the semantic type)Color family, domain mapping, neutral value position

The left column is the edit surface. A small surface means 'change only this' lands on one line and everything else stays put. The reported result that specifications are on average eighty-five percent shorter than native backend code is not a story about saving space; it is a measurement of that surface.

But what you lose appears in exactly the same place as what you removed. The right column is also the column you cannot touch.

7. The cost of handing over control

Automatic decisions are not free. In practice the bill arrives in three forms.

7.1 When the default is not what you meant

The compiler decides that a field is a proportion and therefore runs from zero to one hundred, when what you actually need to show is the fine difference between ninety-two and ninety-eight. That request is not wrong; it comes from context. The schema does include an override entry at the encoding level, and there are optional fields for intrinsic domains and reference values, but how far overriding is opened up is thinly documented. If you hit a wall there, you fall back to pulling out the compiled output and editing it by hand, and at that moment the partial-edit advantage is gone.

7.2 When presentation is the requirement

In an organisation where the design system pins color codes, font sizes and grid spacing as specification, automatic decision-making is itself a violation. 'Make it look good on its own' becomes a cost rather than a value. Those teams should keep using a low-level grammar. So should work where presentation is the subject, such as binding font axes directly to data with variable fonts.

7.3 When type inference is wrong

This entire design rests on the premise that fields get the correct semantic type attached. And the thing attaching that type is, again, a model. Whether a column named score is a rating, a measurement or a rank is not decided by the column name. Get it wrong and the failure does not disappear; it moves up one level.

That move has value on its own, though. Eight misaligned low-level parameters are hard to diagnose, but 'this column has the wrong type' is one line to identify and one line to fix. Not reducing the number of failures but collecting failures into a diagnosable shape - that is what intermediate language design actually sells.

The paper itself notes that it assumes a one-to-one mapping between fields and semantic types, and that this assumption is insufficient for ambiguous fields.

8. Reading the numbers - what a 41 to 45 percent win rate means

The evaluation is public. Here it is as reported. From 63 tables of TidyTuesday 2025 data (median 952 rows, 8 columns), a question generation agent produced 315 queries; the Flint path and a direct backend generation path each produced charts; a vision-language grader scored the rendered images. Scoring covers relevance, chart errors, clarity and design quality at five points each, for twenty total.

ModelFlint winsTiesDirect winsp-valueMean score (of 20)
GPT-5.1129 (41%)65 (21%)118 (38%)0.0516.27 vs 15.91
GPT-5-mini140 (45%)65 (21%)106 (34%)0.00116.16 vs 15.60
GPT-4.1135 (43%)70 (23%)106 (34%)0.00415.91 vs 15.34

How you read this table decides the adoption question. Three points.

  • The difference is real but small. Mean score gaps run from 0.36 to 0.57 points out of twenty, roughly two to four percent. 'Chart quality takes a leap' is not supported by these numbers.
  • The stronger the model, the narrower the gap. GPT-5.1 has the weakest p-value at 0.05 and the closest split at 129 to 118, while GPT-5-mini and GPT-4.1 sit at 0.001 and 0.004. The natural reading is that the quality benefit of an intermediate language declines as models improve.
  • The most robust number is length, not quality. Eighty-five percent shorter holds independently of model capability, and it feeds directly into token cost and the possibility of partial edits.

So adopting this as 'a way to get prettier charts' will disappoint. Adopting it as 'a way to hold the same quality in a definition one fifth the length, and to make that definition something a person can open and fix' matches what the numbers say.

The measurement itself has limits. Because the grader is a vision-language model, the gap between charts a model likes and charts a person finds useful is not captured by this score. That 'visible' and 'knowable' are different problems is a pattern that recurs across observability tooling generally.

9. What could not be confirmed

These are the items the public material does not answer. If you are evaluating adoption, this list is your pre-flight checklist.

  • Width calculation for Korean, Japanese and Chinese labels. Layout optimization assumes a minimum readable width, but how CJK character widths are measured is not documented. CJK axis labels are wider than Latin ones at the same character count.
  • Locale-specific numeric formatting. Whether East Asian myriad-based abbreviations or currency symbols beyond the common ones are covered by standard semantic types, or must be supplied through overrides.
  • The scope of overrides. The presence of an encoding-level override entry in the schema is confirmed; a list of which properties are open and which are closed is not.
  • Semantic type inference accuracy. Final chart quality was evaluated, but no separate figure for the accuracy of the type inference step itself was found.
  • Accessibility defaults. Whether automatically chosen color schemes meet color vision deficiency contrast criteria, and which criteria are used.
  • Compilation cost. How long constraint optimization takes at high cardinality, and whether that latency fits inside a server-side rendering pipeline.
  • Human evaluation. Automated grading results are published; a separate study with human raters was not found.
  • Production references. With a first release in July 2026, no operational deployment case studies are public yet.

10. The adoption call - when to use it and when to stay with your grammar

The version is 0.4.0 and the first release was July 2026. Treat pre-1.0 as a premise of the decision. The API can change, and when it does you rewrite specs. The license is MIT, so there is no constraint on that side.

SituationCallReason
An agent or chatbot makes charts and a person fixes them afterwardsUse itA small edit surface is the value itself
The same metrics must ship to both web and ExcelUse itNative output per backend from a single spec
You want chart definitions in code reviewUse itSixty lines of JSON cannot be reviewed; ten can
You maintain a metrics dictionary and field meanings are stableUse itSemantic type mapping is a one-time job
Brushing, zooming or cross-filtering is a requirementDo notThe paper states interaction is not a first-class target yet
Multi-layer charts and annotations are centralDo notOut of scope for the same reason
Design system pixel specifications are contractualDo notAutomatic decisions become a cost, not a value
Your data pipeline is Python-firstHoldThe Python package is still a source preview
A one-off job with one or two chartsDo notThe dependency costs more than it returns

If you want to try it, run the trial in this order.

  1. Pick a table you actually use. A table with integer keys that look like dates exposes the difference most sharply.
  2. Put it side by side with the spec your current grammar produces and count lines and tokens.
  3. Fire five consecutive 'just change this' instructions and see at which turn earlier edits get lost. That is the real evidence.
  4. Check whether the formats your organisation uses most often exist as standard semantic types, or need overrides.
  5. The package installs with npm install flint-chart, and in an agent environment you attach the MCP server with npx -y flint-chart-mcp.

Conclusion: the window where spec design substitutes for model capability

To pull it together: when you hand chart generation to an LLM, the failures land in predictable places, and a large share of them occur while translating what the model already knows into low-level parameters. A semantics-driven spec moves that translation into a compiler. What you gain is a short definition and an edit surface that supports partial changes. What you lose is direct control over the values that get decided automatically.

The numbers are equally clear. The quality improvement is real but modest, and it shrinks as models get stronger. The five-fold reduction in specification length, by contrast, holds regardless of model. So the lifespan of this approach splits into 'what better models will make unnecessary' and 'what survives better models'. The former is quality correction. The latter is an editable representation.

Three things you can apply today.

  • Put field meanings into the prompt you already use. You do not have to change tools. One line reading 'Period is a YYYYMM integer, Users is an additive count, Ratio is a proportion so never stack it' prevents a large share of axis type errors and non-additive stacking.
  • Fire five consecutive chart edits. The turn at which your current pipeline loses an earlier edit is the size of the improvement available to you.
  • Separate 'make it look good' from the requirements. That is what decides whether automatic decisions belong here at all. If presentation is contractual, automation is a cost.
