序論: cloneで付いてくるもの

プルリクエストの画面が開かない。ところが端末ではgit pushが通り、git fetchも問題ない。こういう日に開発者が最初に言うことはだいたい同じだ。移すべきか。

答える前に一つ押さえることがある。移すという言葉が何を移すという意味なのか、たいてい定義されていない。リポジトリを移すのはコマンド一行だ。分散バージョン管理の設計がもともとそうなっている。問題は、チームが三年かけて積み上げたもののうちリポジトリの中に入っているのがコードとコミットログだけだという事実である。イシュー800件とそこに付いた議論、レビューでどの行をなぜ直したのか書かれたコメント、ワークフローが参照するシークレットとランナー、タグごとに付いたインストーラ、Wiki 40ページ、誰が何にアクセスできるかを定義したチーム構造。ロックインはリポジトリではなく、その周辺に積み上がる。

だからこの記事はどこが良いかという比較ではない。資産を一つずつ並べて何が機械で出てきて、何は出はするが形式が崩れ、何はそもそも出てこないのかを採点する。移せる状態を作っておけば、移すかどうかはその時に決めても遅くない。ロックイン一般論はAIサービスの層別従属と保管を委託した際のアクセス権で扱ったので、ここでは繰り返さない。

1. 障害が示すのは可用性ではない

2026年8月17日、ステータスページにインシデントが一件上がった。注目すべきは継続時間ではなく影響コンポーネントの一覧だ。コーディング補助ツール、APIリクエスト、Git操作、イシュー、プルリクエスト、ページ、Webhook、アクションが一行に並んだ。前の数日も似ている。8月13日のWebhookインシデントにはGit操作・イシュー・パッケージ・プルリクエストが一緒に掛かり、8月12日にはログインとリリース資産のダウンロードが揃って揺れた。

この一覧が語るのは、どの会社がどれだけ頻繁に止まるかではない。自分の一日がいくつの機能に同時に載っているかだ。コードを取り、レビューを読み、ビルドを回し、リリースファイルを取り、ログインする作業がすべて一事業者の一インシデントの中に入りうるなら、それは可用性以前に結合度の問題である。

同じ日のコミュニティスレッドの観察一つがこの区別を正確に見せた。ウェブ画面でプルリクエストが開かない間もコマンドラインではマージが通ったというのだ。分散されたコード層は生きていて、その上に載った協業層が止まった。偶然ではなく構造であり、その構造こそこの記事の主題だ — 生き残った側が移しやすい側である。

  • ステータスページの緑は正常の証拠ではなく、まだ等級が付いていないという情報だ。利用者の症状報告はおおむね告知より早い
  • 可用性だけを理由に移す判断はたいてい失望で終わる。どのサービスにもインシデント履歴はあり、移せば履歴の見え方がゼロから始まるだけだ
  • 逆に結合度を理由に整理する作業はどこにいても残る。移さないと決めてもそのまま得になる

2. 資産ごとの移行難易度と備え

まず全体地図を置く。下の表は資産を機械で出てくるかと移した時に何が残るかで分けたものだ。難易度の低い行を上に置いた。

資産どう取り出すか移す時に残る問題今日やる備え
コード・ブランチ・タグ・履歴ミラークローン、バンドルファイル事実上なしミラーのコピー一部
Wiki別リポジトリとしてクローンほぼなしミラーに含める
イシュー本文・状態・ラベルAPI、アーカイブ、インポータ番号の振り直しで相互参照がずれる生レスポンスを保管
イシュー・PRコメント同上非常に古いもの、数万件のイシューで欠落報告定期スナップショット
リリース成果物資産一覧APIダウンロード先が変わる。他人が張ったリンクが死ぬバイナリの写しとチェックサム
大容量ファイルオブジェクト別経路アーカイブの除外項目個別にバックアップ
PRレビューコメント出るが位置フィールドが付いてくる行位置とスレッド構造がそのまま座らない差分断片まで保管
ファイル単位コメントアーカイブの除外項目着地先そのものが無いことがある結論をイシューへ昇格

必須ステータスチェック移管しないと文書に明記ルールが静かに消えるルール一覧を文書化

フォーク関係移行されない復元方法なし受け入れる

一行に要約するとこうだ。上の四行は費用がほぼゼロの備えで解決し、下の五行はどれだけ準備しても損失が残る。ところが議論で時間を使う場所はたいてい上の方だ。ミラーをどこに置くかは長く話しながら、レビューコメントの行位置がどうなるかは移してから気づく。

2.1 コードと履歴は本当に簡単だ

この項目が短いことがこの記事の論旨だ。分散バージョン管理でコードは既に全員のノートパソコンにあり、残る仕事はすべての参照を漏れなく取ってくることだけである。

# ブランチ・タグ・リモート参照まで全部
git clone --mirror https://host.example/org/repo.git

# 一ファイルに固めておく
cd repo.git
git bundle create ../repo-full.bundle --all

# Wikiは別リポジトリだ
git clone https://host.example/org/repo.wiki.git

バンドルは見ておく価値がある。公式文書が挙げる用途がリポジトリ全体のバックアップとネットワーク無しでの移送だ。成果物がファイル一つなのでどこに置いてもよく、後でそのファイルを対象にそのままクローンできる。最後のバンドル以降の変更だけを含む増分バンドルも作れる。Wikiが別リポジトリである点も知られていない — リポジトリアドレスの後ろにWiki接尾辞を付けるとクローンでき、既定ブランチへプッシュすれば反映される。移行難易度が最も低いのにバックアップ一覧からはほぼ常に抜ける。リポジトリ一覧に見えないからだ。

3. イシューと議論 - 出はするが、その先がある

ここから性格が変わる。イシューとコメントはAPIでよく出る。問題は出た後だ。

最も正確な情報源は意外にも受け取る側の文書である。移す先のインポート文書には何が入らないかがたいてい明記されている。GitLabのGitHubインポート文書は、イシュー・プルリクエスト・コメント・レビュー・ラベル・マイルストーン・Wiki・リリースノート・大容量ファイルオブジェクトまで幅広く入ると記す。そして同じ文書にこういうことが併記されている。

  • 組織やグループ単位は移らない。プロジェクトを取り込むのであって組織構造を取り込むのではない
  • 必須ステータスチェックは入らない。手動で作り直す必要があると文書が直接書いている
  • 2017年より前のコメントの一部はAPI制約で抜けうるし、コメントが数万件のイシューで問題が報告される
  • 本文に埋め込まれたプルリクエスト相互参照は、取り込み時点で対象番号が確定しないため保持されない

最後の行が実務では一番痛い。イシュー本文に別のイシュー番号を参照として書く習慣はどこにでもある。新しいインスタンスで番号が振り直されるとその参照は違う場所を指すか、どこも指さない。文字は残っているので壊れた様子も見えない。三年分の議論を手で直せるチームはない。

送る側の文書も併せて見る。GitHubの移行アーカイブ文書は、イシュー・プルリクエスト・Wiki・リリース・コメント・レビュー・マイルストーン・保護ブランチ設定・デプロイキー・有効なWebhookを移すと記しつつ、フォーク関係と大容量ファイルオブジェクトと外部認証マッピングは除外と書いている。出るものより出ないものを先に読む方がよい。結論は単純だ。インポータを計画の中心に置くな。道具は移行当日に一度使われ、成績は相手の実装次第である。自分が統制できるのは生レスポンスを一部持っているかどうかだけだ。

4. レビューコメント - 形式が消える場所

ここがデータは出るのに意味が出ない唯一の資産なので、この記事で最も重要な節だ。

レビューコメント一件が持つのは文字だけではない。どのファイルの何行目か、差分のどちら側か、複数行なら開始がどこか、基準コミットが何か、返信なら親が誰かが一緒に付いている。フィールド名ではpath、line、side、start_line、commit_id、in_reply_to_id、そして文脈として切り出した差分断片diff_hunkがある。

核心はこれらの値が特定コミット時点の差分を前提とする点だ。だから文書にこういう趣旨の警告が付いている。指定した行に後のコミットが触れると、そのコメントは古いものとして表示される。旧方式のpositionフィールドは実際の行番号ではなく差分ヘッダから何行下かを数える値で、今はlineへ移行中である。これを他サービスへ移すとはそのサービスの差分計算とスレッドモデルの上にこの座標を座らせ直すことだ。座標系が違えば正確には座らない。

  • コメント本文は生き残る。文字はどこへでも移せる
  • どの行に付いていたかがぼやける。ファイルまでは残っても行単位の正確さは保証されない
  • 返信関係が平らになりうる。スレッド三つがコメント十二件の一覧に寝る
  • 複数行範囲の選択は、移す先に同じ概念が無ければ開始行一つに畳まれる
  • ファイル全体に付いたコメントは着地先が無いことがある。アーカイブ文書がファイル単位コメントを除外項目と明記した

備えは二つだけで、どちらも移す前にやる。第一に、エクスポート時にdiff_hunkを必ず含める。差分断片があれば行番号がずれても人が読んで文脈を復元できる。第二に、レビューで出た結論はコメントに残さず昇格させる。どのルールをなぜ決めたのかをイシューやリポジトリ内の文書に書いておけば、座標系と無関係に生き残る。レビュースレッドはもともと揮発性の媒体だ — そこだけに存在する決定は時間にも弱い。

5. CI - 移すのは構文ではなく結合だ

CI設定ファイルはリポジトリの中にあるのでミラーを取れば付いてくる。だから簡単に見える。実際には書き直し費用が最も大きい部類に入る。移すべきものがファイルではなく、そのファイルが前提とするものだからだ。

  • 外部アクション参照。他人が作った段階を一行で呼べる利便性は、その生態系の中でだけ成り立つ
  • ランナーイメージに既に入っているツール。入れた覚えのないコマンドが動くのはランナーのおかげで、それは設定ファイルに書かれていない
  • シークレットの注入方式と名前。値はもちろん、注入時点とスコープ規則がサービスごとに違う
  • キャッシュキーと成果物の保持規則。ビルドが半分だった理由がここにあったなら、移した初日に倍になる
  • トリガー条件の意味。どのイベントがいつ発生するかの定義が微妙に違う

解法は古く、特別でもない。実際の作業をリポジトリ内のスクリプトへ降ろし、CI設定はそれを呼ぶ薄い殻だけにする。

# CI設定にはこの程度だけ残す
steps:
  - run: ./scripts/build.sh
  - run: ./scripts/test.sh
  - run: ./scripts/package.sh

# 判定基準: ネットワークの無いノートパソコンで
./scripts/build.sh   # 同じ成果物が出れば移植可能だ

判定基準が一つなら論争が終わる。ノートパソコンで同じコマンドから同じ結果が出れば移植可能であり、CI画面の中でしか回らない段階があればその分が縛られている。スレッドでCI構文の複雑さがよく不満の的になるが、不満の対象が構文ならそれは結合の症状だ。構文が単純な先へ移しても、ロジックが設定ファイルの中にある限り次の移行で同じ費用をまた払う。ここに必須ステータスチェックを足す。インポータがこれを運ばないと文書に書かれている。移した翌日にマージ規則が消えていることがあり、消えた規則は画面に何の表示も残さない。ルール一覧を文書に書くことが備えのすべてで、費用は十分だ。

6. リリース・Wiki・権限 - 漏れ方がそれぞれ違う

リリースに添付されたバイナリはAPIで一覧を取り、個別にダウンロードできる。リリース識別子で資産一覧を照会し、各資産はブラウザ用ダウンロードアドレスで受けるか、リクエストヘッダをバイナリ受信用に変えて受ける。応答がリダイレクトで来ることもあるので両方の場合を扱えと文書が記している。

技術的には難しくない。本当の問題はアドレスだ。ダウンロードアドレスはホスト名を含み、そのアドレスをこの五年間、他人が文書とスクリプトとインストール案内に埋め込んできた。ホスティングを移せばファイルは付いてくるがそのリンクは全部死ぬ。配布物があるなら自分のドメインの下に安定したダウンロード経路を置き、そちらを公表する方がよい。裏でどこを指していても外から見えるアドレスは変わらない。

権限は性格がまた違う。機械ではなく人がやる仕事が残る区間だ。

  • アーカイブにチームと組織は含まれるが外部認証マッピングは除外だ。IDプロバイダと紐づけていたならその接続は作り直す
  • 取り込む側も組織・グループ単位は移さないと明記する。役割名と権限の粒度が違い、一対一で対応しない区間が必ず生じる
  • 結局アカウント突合は人がやる。40人なら一日、400人ならプロジェクトになる。備えは権限構造をリポジトリ内のファイルに書いておくことだ
  • フォーク関係は移行されないと文書が明言している。備える方法が無いので受け入れる。ただしオープンソースなら貢献の流れ自体がフォークの上に立つので損失は大きい

7. 名前を自分の側に置く

この節は備えの中で最も安く最も長持ちするものだ。そしてたいてい遅すぎる時期にやる。

パッケージを配布するプロジェクトでは名前がすなわちアドレスである場合が多い。Goモジュールが代表例だ。公式文書はモジュールパスをモジュールの正式名と定義しつつ、そのパスがリポジトリ位置の特定に使われると記し、パスの先頭要素は慣例上ドメイン名である。つまりホスティングアドレスをそのままモジュールパスにしていると移した瞬間、世界中のインポート文が誤りになる。解決は古い慣行だ。自分のドメインをモジュールパスに使い、そのドメインが実際のリポジトリを指すようにする。他の言語生態系も原理は同じ — 名前の所有権がどこにあるかを確認すればよい。

  • ドメイン。文書サイト、ダウンロード経路、イシュートラッカ案内を自分のドメインの下に集める。裏が変わっても表は変わらない
  • パッケージ名前空間。組織名の範囲を先に押さえる。個人アカウントに紐づく名前は後で一緒に移しにくい
  • インポートパス。ホスト名がコードに埋まっていないか確認する。埋まっていればそれが最も強いロックインだ
  • メールアドレスとコミット署名。ホスティングが発行したアドレスでコミットしてきたなら、履歴の著者識別がそのサービスに縛られる

この四つは移す計画が無くても今やる方がよい。費用がほぼゼロで、後からでは既に配布されたものが邪魔をしてできない。

8. 定期エクスポートを実際に回す方法

ここまでの内容を一つの作業に圧縮すると定期エクスポートになる。一度取るバックアップではなく周期的に回るものであり、何よりたまに実際に復元してみる必要がある。

対象周期形式かかる費用
リポジトリミラー毎日すべての参照を含むクローンほぼゼロ
バンドルスナップショット週1回ファイル一つほぼゼロ
Wiki毎日別リポジトリのミラーほぼゼロ
イシュー・PR・コメント週1回API生レスポンスそのまま低い
レビューコメント週1回差分断片を含む低い
リリース資産リリースごとバイナリとチェックサム低い
権限・チェック規則月1回人が読む表低い
復元リハーサル半年1回空のインスタンスに実際に載せてみる中程度

最後の行だけ費用が中程度で、残りはスクリプト一式と予約実行で終わる。ところが実際の価値の半分がその最後の行にある。復元したことのないバックアップはバックアップという名前のファイルだ。半年に一度、空のインスタンスにミラーを流し込みイシュースナップショットから何件か作ってみれば、何が動かないかがその日に全部出る。

よくある失敗が一つ。エクスポートをCIの中で回すと、そのCIが止まった日にエクスポートも一緒に止まる。そしてエクスポートが必要な日はまさにその日だ。予約実行は移そうとしている対象の外に置くのが原則である。

9. セルフホスティングが請求するもの

ここまで来るとセルフホスティングが結論のように見える。統制権を取り戻すのは事実だ。ただし費用は消えず移動する。何がどこへ行くのかを表に置くと判断しやすい。

項目委託した場合自分で運用する場合
セキュリティパッチ事業者が対応する自分の日程。何年も運用した側はほぼ週単位の対応を語る
可用性事業者の責任。こちらは待つ自分のオンコール。深夜の通知が自分の電話に来る
アップグレードおおむね自動自分の計画。ダウンタイムをチームと調整する
バックアップ・復元事業者の写しと自分の写し全部自分のもの。復元検証も自分の担当
スパム・悪用対応事業者公開インスタンスなら常時業務になる
貢献者の流入大きなネットワークに乗る自分で作る必要がある。最も高くつく
統制権低い高い。対価を払って買うのはこれだ

下の二行が判断の中心だ。コミュニティ効果は移行されない。スレッドで繰り返し出た指摘でもある — 移したプロジェクトが貢献の減少を経験したという話、生態系全体が一箇所に住んでいて個人が抜けても意味が無いという話。人がどこを覗くかの問題なので、道具をうまく選んでも解決しない。

だから基準をこう置くとだいたい合う。セルフホスティングの正当な理由は規制要件、社内網アクセス、データ統制、費用構造だ。可用性と移行可能性はその一覧にない。移行可能性はどこにいても定期エクスポートとスクリプト化で確保する方がはるかに安く、エクスポートの無いセルフホスティングはバックアップの無い単一障害点が一つ増えただけである。この二日スレッドで名前の挙がった選択肢は、自己設置型・マネージド型・連合型・分散型にわたり複数あった。どちらが良いという話はしない。ただし選択肢があることと移せることは別の問題であり、この記事が扱ったのは後者だ。

結論: 今日持ち帰る三つ

第一に、移せる状態はリポジトリの写しではなく一覧で判定される。コードは既に安全だ。危ないのはイシュー番号がずれること、レビュー座標がぼやけること、マージ規則が音もなく消えること、リリースリンクが死ぬことである。一覧を一度書くのに三十分あればよく、書けば何を準備するかは自ずと決まる。

第二に、最も安い備え四つは今日のうちに終わる。リポジトリとWikiのミラー、イシューとレビューコメントの生スナップショット、CIロジックのスクリプト化、ドメインと名前空間を自分の側へ。四つとも移す計画が無くても得で、後からでは高くつく。特に最後の一つは配布が広がった後では事実上できない。

第三に、障害は移せという信号ではなく数えろという信号だ。一つのインシデントにコードとレビューとビルドとデプロイとログインが一緒に掛かるなら、問題はその事業者の稼働率ではなく自分の一日が一箇所に何本結ばれているかである。その結合をほどく作業は移さないと決めても残る。移行可能性の目的は移行ではなく選択肢を持つことであり、選択肢があれば急な時に急いで決めなくて済む。

  • サービス別の稼働率数値。どちらが安定しているか比較できる公開統計は確認できなかった。この記事はその比較をしない
  • インポータの実際の損失率。文書上の制約は確認したが、大規模リポジトリでの公開測定値は見つからなかった
