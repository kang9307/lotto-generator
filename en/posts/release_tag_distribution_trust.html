When the build stops in front of a form

A pipeline that ran fine yesterday comes back empty this morning. The script is unchanged, the repository address is unchanged, but git fetch --tags pulls nothing new. The remote still has last release and nothing for the version you need. Upstream is not down and your access is not revoked. That name simply stops appearing.

Instead there is a notice. Fill in a form, and in a few days, sometimes a few weeks, a link arrives for a single file. The file is complete and the code is all there. The pipeline is still stopped.

That mismatch is the subject here. Changing a distribution path looks from the outside like swapping one download method for another. In practice, everything that was riding on the old path comes down with it. The pinned reference, the verification that hashes made possible, the address automation used to fetch from, the assumption that a third party can obtain the same thing. Those four came as defaults of the tag and release-archive format rather than being built separately, which is exactly why they disappear quietly when the format changes. What follows is that list.

What is confirmed

On 8 August 2026 the GrapheneOS project published a short post on its own Mastodon account. The substance is that Google replaced the practice of pushing Git tags for certain source code with obtaining it via Drive after a Forms request, that request handling has grown steadily slower, and that in the project's view this now constitutes a GPLv2 violation. The core sentence was Google replaced pushing Git tags for certain source code with obtaining source code via Google Drive after making a request through Google Forms.

Two days later an Android trade publication covered it. The affected material was identified as Pixel device kernel source, the process as a Google Form submission followed by a Drive link, and the report carried the project's description that something taking a couple of hours now takes weeks, along with the observation that the update history is squashed into a single hard-to-read file. The publication stated it had contacted Google and had no response by the time of publication.

A Hacker News thread surfaced a further technical layer. Pixel kernel and userspace driver repositories were discussed together, and commenters noted that the Android build system expects a Git repository per component and runs Git commands, so a monolithic tarball does not drop in cleanly.

A tag is not a URL, it is a pinned reference

If you think of a Git tag as a label stuck on each release, the size of this change is hard to see. What a tag actually does is bind an entire body of content to a single value through one name.

Unpack the structure. A tag points at a commit, the commit is identified by a SHA hash, that commit points at a tree object, and the tree points at subtrees and file blobs by hash again. One top-level hash covers everything beneath it in a Merkle structure. Two people who both know the name v1.2.3 can therefore confirm they hold identical content without exchanging a single file. Change one byte and the value changes. Add annotated tags and signatures and you gain another layer, namely who decided to call this snapshot by this name. Whether the content is right and whether the origin is right are separate questions, and you need both.

So a public tag delivers four things at once.

  • Name-to-content pinning — every tool operates on the convention that the same tag name resolves to the same commit whenever it is queried
  • Self-proving content — the hash is computed from the content, so integrity holds without a separate manifest
  • Proof of origin — a signed tag lets you confirm the publishing party cryptographically
  • Symmetry — whoever asks, whenever they ask, gets the same thing from the same address, which is what makes verification reproducible by a third party

Move to request-based distribution and the file survives. The other three drop from default to optional. If the publisher posts public checksums, attaches signatures and guarantees an identical artifact to every requester, much of it is restored, but that is something you have to design in rather than something the format hands you.

What an archive hash actually guarantees

To anyone who has done packaging, source is not a file but an address-plus-checksum pair. The shape differs per ecosystem, the structure does not.

  • Arch-family PKGBUILD — source=() and sha256sums=() are declared side by side
  • Homebrew formula — sha256 sits directly under url
  • Nix — the fetchurl family takes a hash as an argument and the build will not even start if it is wrong
  • RPM and Debian packaging — Source0 or debian/watch names upstream, with per-file hashes recorded
  • Language ecosystems — a module proxy or lock file pins a hash per dependency

A distinction gets blurred here routinely. A checksum handles both transport integrity, meaning nothing broke on the way down, and agreement on identity, meaning these are the bytes that were reviewed and approved. The first works whether or not distribution is request-based. The second only means something when other people can arrive at the same value from the same address.

That second one is the point. A packager bakes a hash into a recipe not to confirm their own download survived, but to confirm that build servers worldwide obtain the same value. If an upstream file is quietly swapped, every one of them fails at once, and that failure is the alarm.

Seen this way, auto-generated archives were always fragile. A tarball a hosting service synthesises on the fly from a tag can differ byte for byte if the compression implementation or the generation logic changes, even when the content is identical. That is why careful packagers have preferred release assets uploaded by a human over generated ones. The latter is fixed once.

Request-based distribution pushes this one step further. The premise of a shared address does not hold at all. Each requester gets a different link, and a repeat request may yield a different artifact. The hash is still computed, but it is no longer a shareable standard. A hash verifies an agreement, not a file. With nothing public to agree on, the hash slides from being a verification device to being a private note.

Where the reproducible build chain snaps

Reproducible builds are not a romantic goal, they are a chain. Break one link and the conclusion shifts from we verified it to we decided to trust it.

  1. Source pinning — which bytes did we start from
  2. Toolchain pinning — which compiler and library versions ran
  3. Environment pinning — how were paths, timestamps, locales and other nondeterminism suppressed
  4. Output comparison — do two independent parties obtain the same artifact

Modern supply chain attestation sits on top of that chain. Build provenance records in a signed document which source and which builder produced an artifact, an SBOM records the parts list along with each component's origin location, and signing tools attach an identity to those documents. All three layers assume link one is public.

The SBOM case is the sharpest. Put a request form address in a component's download-location field and it is no longer the address of the material, it is the address of a procedure. An SBOM exists to answer what went into an artifact and where it can be obtained again, and the second half becomes conditional. Format validation passes while only half the purpose is met.

Output comparison is blocked more directly. The definition of reproduction verification is an independent third party obtaining the same result from the same input. If that third party needs weeks to obtain the input, verification stops being a standing activity and becomes an event. Verification that is not standing does not catch regressions.

Where history is the evidence

Filing the difference between a bare snapshot and full commit history under convenience understates the scale. History is used as evidence, not comfort. There are five places where it is consumed in practice.

  • Regression bisection — you are looking for which change broke it, not which version. If the gap between two snapshots is tens of thousands of lines in one lump, bisection does not apply
  • Security patch identification and backporting — you need to know which commit fixes which vulnerability before you can move it to an older branch. A snapshot tells you it was fixed and never where or why
  • Root cause analysis — commit messages together with the scope of a change are what let you answer why a line ended up the way it did. Code alone loses intent
  • Authorship and licence tracing — establishing where code came from and what conditions attach to it usually means walking the history
  • Upstream re-contribution — sending local changes back requires separating upstream state from your own work. When the base is one lump, the cost of separation spikes

This is where the licence text enters naturally. Section 3 of GPLv2 defines source code as follows. The source code for a work means the preferred form of the work for making modifications to it. Whether history belongs to that preferred form is the technical core of the whole dispute, resting on that one sentence.

One side holds that if upstream develops commit by commit internally and modifies the work in that form, a squashed single snapshot is by definition not the preferred form. The other holds that the text requires complete source that can be built and modified without specifying version control history, and that distributing source without history has a long precedent. Which reading is right is a matter of textual interpretation and jurisdiction, and this article does not rule on it. What is unambiguous is what disappears technically, listed in those five items.

Who gets hurt - four groups, four different reasons

Lumping this under inconvenience produces no response. The nature of the difficulty differs per group, and so do the substitutes.

Distribution packagers - detection dies first

What a packager loses first is not a file but a signal. The widespread arrangement is that a tool, not a person, notices a new version exists. Something reads the upstream release page or tag list periodically, detects a new version, and raises an update alert or even a draft commit. Remove the public listing and that whole layer stops, and when noticing runs late, security fixes reach the distribution late.

The second loss is the permanent address to put in a recipe. Packaging recipes must be public and the source address inside them must be followable by anyone, which a per-request link is not. The distribution then has to mirror the source on its own infrastructure, which is a storage cost and a redistribution rights question. Fine for components whose licence permits redistribution, impossible for a tree with components that do not.

CI and automation - waiting does not match the cycle

Pipelines are not designed to tolerate waiting on human approval. If a nightly build runs daily while one input takes weeks to obtain, that input has to leave the pipeline. In practice it settles into a human uploading the received file to an internal artifact store and pointing the pipeline there. It works. The moment it does, though, the source's origin becomes an internal cache rather than upstream.

From an audit perspective that single step is heavy. The answer to where the source in this release came from shifts from an upstream coordinate to an internal path, and the link from that path back to upstream survives only as one file plus one person's notes. Unless it is written down, nobody can reconstruct it a few quarters later.

Air-gapped environments - the procedure moves from script to person

Network-separated environments already have a procedure for moving external material inward. What matters is whether that procedure can be frozen. With tags it hardens into a script. Fetch from a fixed address, verify against a fixed hash, keep the verification log as the import review record. A reviewer can reproduce it, so approval is fast.

Request-based means a person is attached to every version. The harder point is the proof of origin the review demands. With a public address and a public hash, the proof is self-contained. Without them, an inbox message and a link become the evidence. The stronger an organisation's security requirements, the harder it is to accept that as grounds for approval. The result is either delayed adoption or a decision not to use the component at all.

Archiving and long-term preservation - it drops out of crawl scope

Long-term software preservation works by machines sweeping public repositories and taking copies. Make access application-only and it falls out of scope. Nothing shows immediately and the problem arrives years later. Retrospective vulnerability analysis asking whether an old version carried a flaw, legal disputes where a third party must establish what was distributed at a given moment, academic reproduction of code a paper referenced, community maintenance picking up devices past end of support. All four were possible because somebody made a copy at the time, and when copying is not possible there is no substitute.

The other side - there are real reasons to change distribution

Anyone who has actually operated a public repository knows the costs involved. Which organisation changed what and why is unknowable unless it is announced, and this article does not speculate about it. What can be set out is the general pressures that push a publisher to change distribution.

  • Bandwidth and automated traffic — a large share of public Git repository traffic is machines rather than people. Pipelines that do not use shallow clones pull the entire history repeatedly, costs rise linearly, and the effect is felt most on large repositories
  • The scrubbing burden of publishing history — commit-level history mixes in internal paths, unannounced codenames, personally identifying author information and intermediate experimental code. Pre-publication scrubbing is hard to automate and mistakes are expensive
  • Third-party licence boundaries — when a tree mixes in code under different redistribution conditions, the scope of publication has to be adjusted component by component, which takes far more work than publishing the whole thing
  • Repackaging and provenance confusion — every ecosystem has cases where public archives get redistributed as is and origin or integrity gets muddied. Narrowing distribution points is one of the responses actually used against that

These pressures are real. A framing where public is always right and application-only is always wrong is not accurate. One thing can be said plainly, though. Cost does not vanish, it moves. The bandwidth and scrubbing cost the publisher carried moves to downstream waiting time, mirror operation and rebuilt verification. Whether the total went down is a separate question, and it is usually not measured, because the cost on the receiving side is scattered across many organisations and nobody adds it up.

What a consumer can do today

The upstream decision is outside your control. Inside your control is how many days that decision takes to stop your build. In order:

  1. List every external dependency address first — gather everything the build fetches over the network into one table. The first time anyone builds this table it usually comes out about twice as long as expected
  2. Attach hashes to entries that have none — a line with an address and no checksum is the fragile line. This is the cheapest measure available and the effect is immediate
  3. Write down a source retention policy — keep the archive actually used in a build along with a retention period, and record acquisition date, acquisition path, hash and owner rather than the file alone. What you need later is not the file but a statement about what the file is
  4. Check the licence before you mirror — put only redistributable components in an internal mirror. Do not wave it through on the grounds that it is open source; check the specific conditions and clear it with your legal function. An internal-only cache and a public mirror carry different requirements
  5. Decide vendoring per component — putting source in your repository raises self-sufficiency but increases repository size and update friction and moves security patch tracking onto you. Vendoring everything is not the answer. Start with the components that would block a release outright
  6. Monitor upstream tag freshness and register irreplaceable components as risk — a distribution change shows up as tags going quiet before any announcement does. Tracking days since the last tag buys you weeks. And if you have no answer to what happens to the product if this component cannot be obtained next quarter, that is not technical debt, it is supply chain risk

Be explicit about what is not on the list. Ways to sidestep a procedure the publisher set are not included here. That is not an operational measure but a way of creating a separate problem, and at organisational scale especially so.

Availability and licensing are different problems

The part of this that will outlast the specific repository is the distinction itself. A licence governs what the recipient may do; availability governs whether they can obtain it at all. The two are routinely treated as one thing and they are in fact separate layers.

The structure of GPLv2 section 3 shows the difference. Option 3a accompanies the binary with complete source on a medium customarily used for software interchange, and 3b supplies it on request under a written offer valid for at least three years. In other words the text itself recognises responding to requests as one distribution method. A requirement to operate a permanently public repository for everybody is not in the text.

So a state where the licence obligation is met while practical availability drops sharply is possible in principle. Conversely, in this matter the project holds that the delay and the form fall outside what the text asks for. Which reading prevails is not for this article to settle, and no authoritative interpretation or decision has been confirmed. The conclusion that matters to a practitioner lies elsewhere.

  • The assumption that open source is always obtainable is not guaranteed by the licence. Most open source licences do not require a publisher to operate permanently public infrastructure
  • A pipeline built on that assumption was in fact depending on the publisher's operational policy rather than the licence. Operational policy changes far more often than licences do
  • The ecosystem has closed this gap in exactly one way. Public mirrors, archives, source caches in package repositories. All of them work because somebody made a copy
  • Copying while copying is possible is therefore the only defence that scales. There is no copy you can make after access closes

Getting this distinction into a team is surprisingly simple. Add one more column next to the licence column in your dependency review sheet: acquisition path. Public repository, release asset, application-only, internal mirror. With that column present, the next policy change takes a day to scope.

What could not be confirmed

The material behind this article is a public post, press coverage, a public discussion and the licence text. Beyond that, the following remain open.

  • The precise scope of 「certain source code」 — reporting identified Pixel kernel and the discussion raised userspace driver repositories alongside it, but no public specification listing the affected repositories was found. There is no basis for treating AOSP as a whole the same way
  • The effective date and the actual turnaround — the post describes handling growing slower without naming a transition date. The weeks figure is one project's stated experience, and no public material gives a mean or a median
  • An official explanation from the publisher — the report recorded no response by publication time. Whether an official explanation followed could not be confirmed
  • The exact form of the artifact provided — the description that history is squashed into a single file exists, but no primary material confirming how far that squashing goes was found
  • Licence judgement and spread — no authoritative interpretation or court decision on the GPLv2 question is confirmed to exist, only the arguments on both sides. There is likewise no basis for judging whether other vendors will follow or whether this change will be reversed

Conclusion - pin the promise, not the address

The longer you have used tags and release archives, the easier it is to treat them as download links. In practice that format was quietly doing four things for you. It bound a name to content, it let integrity prove itself, it created a place for a signature to attach to origin, and it let a third party obtain the same thing. Because those four existed, checksums became a shareable standard, SBOMs had coordinates to record, and reproduction verification could be a standing activity. Change the distribution path and all four wobble together. The file still arrives. What wobbles is what you can say about the file.

So before filing this under someone else's repository problem, put three questions to your team. First, can you produce the complete list of external addresses your build fetches from within the next thirty minutes. Second, how many of those entries have no hash attached. Third, if one of those addresses turns application-only tomorrow, how many days until your release stops.

If the third answer is that nobody knows, this is not somebody else's problem but one that has not arrived yet. And building answers to these questions costs nothing regardless of what upstream does. A list, a set of hashes and a set of copies keep their value even if no distribution policy ever changes. That is a rare kind of investment.
