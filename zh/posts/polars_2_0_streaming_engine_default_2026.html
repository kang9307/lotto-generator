起因 — 改默认值而不是加功能的大版本

Polars 在 2026 年 10 月 6 日发布了「Release of Polars 2.0」，作者是 Ritchie Vink。GeekNews 在同一天做了介绍。发布文章把提升版本号的理由交给 9 月 2 日的预发布公告「Pre-release of Polars 2.0」，自己则讲 2.0 带来的功能。预发布公告给出的理由是这样的。团队并不打算把 2.0 做成一个大的功能版本，希望它对用户来说是一次平淡的体验，提升大版本号是为了去掉过去做出的设计决定，并把默认值改成对更多用户有利的设置。

最大的默认值变化是 LazyFrame 查询改在流式引擎上运行。发布文章写道，这一切换让大多数查询的内存和性能有很大改进。文章把这称为 2.0 中影响最大的变更之一，并用一句话写出需要大版本的原因。流式引擎对某些操作默认不保证行顺序。这意味着同样的代码可能不报错却以不同的顺序返回结果，迁移指南给这一项附上了可能悄悄影响管道结果的警告。

发布文章列出的 2.0 亮点有五项。

  • out-of-core。 溢写到磁盘(spill-to-disk)支持的初始版本已经启用。
  • 性能。 加入了许多核心层面的性能改进。文章在优化器和引擎方面点出的是连接重排、改进很大的公共子计划消除，以及动态谓词和布隆过滤器。
  • SQL。 SQL 成为一等支持。文章写道，加上性能改进，Polars 在从 TPC-H、TPC-DS 派生的基准中领先 DataFusion 和 DuckDB。
  • Map。 新增了 Map dtype。
  • 严格。 在 dtype 和显式性上更严格。文章把结果写成更快的反馈和更快的 AI 迭代。

预发布公告曾写道，总体上预期流式引擎「轻松快 5 倍」。这句话说的是预期，不是测量值。这个倍数没有再出现在发布文章里，取而代之的是一份写明条件的基准。

collect() 的默认引擎 — engine="auto" 指向哪里

迁移指南的第一项就是这个变更。LazyFrame.collect 和 collect_async 的 engine 参数和以前一样，默认值是 "auto"。变的是 "auto" 指向哪里。对惰性查询，"auto" 以前解析为内存引擎，现在解析为流式引擎。调用处不用改，底下的引擎就换了，所以从没提过引擎的代码也会受影响。

指南也写了不受影响的地方。即时执行(eager)的 DataFrame 操作在内部继续使用内存引擎。通过 sink_* 写文件的路径，不论 engine 取什么值，原本就已经交给流式引擎，所以没有变化。explain() 和以前一样输出优化后的 IR 计划。show_graph() 的 plan_stage 默认值从 "ir" 改为 "physical"，不带参数调用时画出的是流式物理图。

SQL 也跟着变。SQLContext.execute(eager=True) 和 pl.sql(..., eager=True) 以前通过内存引擎收集，现在和其他惰性查询一样经过 LazyFrame.collect()。指南写道，要让 SQL 查询继续使用内存引擎，可以用 eager=False 让结果保持惰性，在收集时再选择引擎。指南还补充说，engine affinity 的设置同样适用于 SQL。

即时读取函数也转到了惰性路径上。pl.read_csv 被转交给 pl.scan_csv(...).collect()，pl.read_ipc 在不使用 use_pyarrow 的输入上也被转交给 pl.scan_ipc(...).collect()。因此 read_csv 失去了 n_threads、batch_size、sample_size、rechunk 参数，read_ipc 失去了 memory_map 和 rechunk。指南补充说，read_csv 的行为现在与 scan_csv 完全一致。选择列时按请求的顺序返回，而不是排序后的顺序。

  • 旧参数。 collect(streaming=...) 在 1.25 被标为弃用，在 2.0 被移除，替代写法是 engine="streaming"。
  • 性能剖析。 LazyFrame.profile() 是为内存引擎设计的，理由是流式引擎的并发执行会让按节点统计的时间产生误导，因此被移除。指南写道，团队正在为开源版 Polars 准备查询剖析的办法。

行顺序 — 不保证顺序的操作与恢复的办法

发布文章的句子是这样的。流式引擎对某些操作(join、group_by、unpivot 等)默认不保证行顺序，如果在这些操作中需要可观察到的行顺序，可以通过设置 maintain_order=True 来选择。迁移指南划定范围的方式略有不同。它写的是，流式引擎对不要求顺序的操作(unpivot, group_by, joins, ...)不保证行顺序。两句话都没有把列表封口，所以不能把这三种操作读成全部。

在应对办法上，两份文档的说法不同。发布文章只写了 maintain_order=True。指南写的是，如果代码依赖偶然形成的顺序，就显式排序，或者在操作支持的情况下传入 maintain_order，并举了 join(..., maintain_order="left") 作为例子。在连接的例子里，值不是 True，而是字符串 "left"。预发布公告里的连接示例用的也是 maintain_order="left"。对于 unpivot 的例子，指南给出的替代办法不是 maintain_order，而是收集之后再排序。

指南里的 unpivot 例子显示了变化是什么样子。把列 b 和 c 展开时，2.0 之前先输出 b 的三行，再输出 c 的三行。在 2.0 的示例输出中，顺序是 x 的 b 和 c、y 的 b 和 c、z 的 b 和 c。指南在这里加了一条但书。示例中显示的顺序本身并不被保证，被保证的只有一点，即它不再是 2.0 之前的顺序。关于连接，指南写道很容易漏掉，因为查询里看不出哪一处对顺序敏感。指南的连接示例是对键 k 顺序相反的两个帧做左连接，并带有一条注释，说结果的行顺序不再与左侧的帧一致。

>>> lf.unpivot(pl.selectors.numeric(), index="a").collect().sort(pl.all())
                    >>> left.join(right, on="k", how="left", maintain_order="left").collect()
                    >>> pl.Config.set_engine_affinity("in-memory")  # process-wide
                    >>> lf.collect(engine="in-memory")  # per query

上面四行是从迁移指南的示例中各取一行得到的。它们在指南里属于不同的示例，lf、left、right 是各个示例中定义的帧。第一行是依赖顺序的 unpivot 的替代写法，第二行是依赖左侧帧行顺序的连接的替代写法，其余两行是在整个进程范围或单个查询范围内恢复以前默认引擎的办法。引擎名称的拼写带连字符，是 "in-memory"。

  • 原文点名的操作。 join、group_by、unpivot。两份文档都没有把列表封口。
  • 不会报错。 指南的警告措辞是「This change may silently impact the results of your pipelines」。
  • 连接时的值。 maintain_order="left"。
  • 排序这个选项。 指南先写的是需要顺序时显式排序。
  • 恢复。 回到以前引擎的办法有三种，即进程范围的设置、单个查询的参数和环境变量。

out-of-core — 默认启用、RAM 约 80%、磁盘 64GB

发布文章写道，out-of-core(spill to disk)现在默认启用。它在 RAM 的约 80% 处开始向磁盘溢写，文章在这个值旁边用括号加了一条但书，即「可能需要调整(this may need tuning)」。默认磁盘预算是 64GB。

支持范围写得很窄。目前支持 out-of-core 的操作是 sort、window functions 以及「许多表达式(many expressions)」，这些操作现在可以为了完成查询而开始向磁盘溢写。连接和 group-by 还不在范围内。文章写道「今后(in the coming time)」也会为连接和 group-by 启用 out-of-core，结语里也把更好的 out-of-core 列为接下来的工作。没有写时间。

发布文章的亮点列表把它称为「初始版本(initial version)」。一个月前的预发布公告，把面向流式引擎的像样的 out-of-core 支持算作还没有公开谈够的进行中工作。发布文章的评价是，流式默认和 out-of-core 这两项变更会让 Polars 在高内存负载下稳健得多，并把受益对象写成普通的数据从业者(casual data practitioners)。

因此，发布文章没有给出依据，让人可以假定大于内存的连接或 group-by 在 2.0 中会转到磁盘上完成。支持列表里有的是排序、窗口函数，以及没有列举范围的「许多表达式」。单节点引擎能承担多大规模，这个更宽的问题已在2026年数据工具版图中讨论过。

Map dtype — 直接支持 Arrow MapType

Polars 现在把 Arrow MapType 直接支持为 Polars 的 Map dtype。发布文章解释说，可以把 Map 想成把键映射到值的 Python 字典。在 2.0 之前，Arrow MapType 在 Polars 中被读成 List(Struct({"key": ..., "value": ...}))。文章写道，成为受支持的 dtype 之后，它会有专门的表达式，例如键查找、遍历值等字典式的方法。

# Key lookups and dictionary-like methods:
                    df.select(
                        "user",
                        pl.col("scores").map.get("math").alias("math"),                # fixed key
                        pl.col("scores").map.get(pl.col("subject")).alias("by_subject"),  # key from another column
                        pl.col("scores").map.contains_key("art").alias("has_art"),
                        pl.col("scores").map.len().alias("n"),
                        pl.col("scores").map.keys().alias("keys"),
                        pl.col("scores").map.values().alias("values"),
                    )

这里只引了发布文章示例中的查找部分。示例的帧有 user、scores、subject 三列，scores 列声明为键是字符串、值是整数的 pl.Map(pl.String, pl.Int64)。输出中这一列的 dtype 显示为 map[str, i64]。map.get 既接受固定的键，也接受取自另一列的键。在示例输出中，bob 没有 art 这个键，所以 by_subject 是 null，has_art 是 false。

迁移指南给这项变更也附上了悄悄影响的警告。来自 Arrow(pl.from_arrow 等)、Parquet 和 Iceberg 的 map 列，以前被展平成 List(Struct)，现在加载为 Map，其 Python 值是 dict，而不是键值结构体的列表。不会报错，变的是模式，以及 to_list()、to_dicts()、rows() 返回值的形状。在这些列上使用 list 或 struct 命名空间的代码会失败。

指南写道，需要以前的形状时可以用 map.entries() 恢复，扫描时也可以在 schema 里指定 List(Struct) 类型，从一开始就按 entries 读取。

  • 推断没有变。 pl.Series([{"a": 1}]) 仍然是 Struct。Map 只会来自显式的 dtype、list.to_map()，或 Arrow、Parquet、Iceberg、IPC 输入。
  • 键的约束。 键在一行之内唯一，且不会为 null。Parquet map 中的重复键在读取时被修复，保留第一个位置和最后一个值。
  • 导出。 to_arrow()、write_parquet()、write_ipc() 把 Map 列导出为真正的 Arrow map，并以 Map 往返。
  • 命名空间。 Expr.map 和 Series.map 提供 entries()、keys()、values()、len()、contains_key()、get()。
  • 查找键时的类型转换。 get() 和 contains_key() 会把要查找的键转换成 Map 的键类型，转换后无法精确表示的键被视为不存在。

更严格的行为 — 悄悄改变的结果与改为报错的调用

发布文章写道，Polars 的目标是严格并且尽早失败。错误应当在一开始就抛出，而不是在管道跑了 20 分钟之后，对数据不匹配的隐式处理应当是可选项，而不是默认行为。它给出的理由是，这类不匹配可能掩盖 bug。

文章写道，随着 AI 驱动的开发兴起，这种严格变得更有价值。智能体可以调用 collect_schema() 尽早验证查询的结构，这个调用不实例化任何数据就能解析类型并捕获模式层面的不匹配。并非所有错误都能在编译查询计划时捕获，有些取决于数据。文章写道，在这种情况下 Polars 默认采用更严格的行为，以确保捕获不一致，而不是悄悄给出不同的结果。AI 编码工具与数据系统设计的关系已在Wes McKinney谈AI时代数据系统的未来中讨论过。

预发布公告举了三个例子。is_in 以前会把不同 dtype 的操作数转换成共同的上位类型再比较，现在只在转换无损时才转换，否则报错。例子是 Int64 值 9007199254740993 被转换成 Float64 后悄悄舍入为 9007199254740992.0，造成假阳性。水平 concat 在高度不同时抛出 ShapeError，不再用 null 填充。整数与 Enum、Categorical 之间的 cast，以及从字符串到日期时间类型的 cast 被移除，改用专门的方法(.cat.to(dtype)、.cat.physical()、.str.to_date()、.str.to_datetime())。

调用已移除的功能时，会抛出指明替代办法的新异常。被移除的属性和方法对应 AttributeRemovedError，被移除或改名的参数对应 ArgumentRemovedError。指南说明覆盖并不完整。有些条目仍然抛出内置的 AttributeError 或 TypeError。

变成报错的变更，一运行就会暴露。更费工夫的是不报错而结果不同的变更。在指南正文里，「This change may silently impact the results of your pipelines」这句警告出现了 12 次。其中六项如下。

  • 流式默认。 不要求顺序的操作，行顺序发生变化。
  • explode()。 空列表展开成 0 行，而不是一个 null 行。列表列里只要有空列表，行数就会变。以前的行为用 empty_as_null=True 得到。
  • 整数的上位类型。 有符号整数与 UInt64 相加得到 Int128，而不是 Float64。输出的 dtype 和计算出的值都会变。
  • 选择器与 pl.col 的运算。 用 &、|、^ 把选择器和 pl.col(...) 组合时，现在被解释为逐元素运算，而不是列的集合运算。对兼容的 dtype，这种切换不会报错。
  • Map 列。 Arrow、Parquet、Iceberg 的 map 列加载为 Map。
  • 水平 concat。 高度不同时不再填充，而是报错。需要填充时使用 how="horizontal_extend"。

基准的条件 — 测了什么、怎么测的

发布文章里的基准是 Polars 自己运行、Polars 自己发布的。文章写道，Polars SQL 是在从 TPC-H 和 TPC-DS「派生」的数据上运行的，并在脚注中说明，这些结果不符合 TPC-H、TPC-DS 基准的规定，因此不能与已公布的 TPC-H、TPC-DS 结果相比。基准仓库的 README 里也有同样的声明。

这些条件里有三条直接关系到结果怎么读。第一，数值是 hot 设置下 5 次中最好的一次。平均值和首次运行的时间不在表里。第二，有被排除的查询。Polars 和两个 DuckDB 版本完成了所有查询，DataFusion 在 TPC-DS q72 上超时(在 q67 上也有一次)，在 c7a.4xlarge 的 TPC-H q18 上内存耗尽。这些查询从所有引擎的结果中排除。第三，查询语句是由 DuckDB 生成的，数据的 row group 大小是 tpcgen-cli 的默认值。文章写道，团队确认这些默认值与 Polars 的 scan_csv 接到 sink_parquet 的产物以及 DuckDB COPY 的产物大致相近。

  • 仓库。 复现用的命令和原始结果是公开的。

基准的结果 — 附录的合计表与 192 线程

发布文章的结论句带有条件。它写的是「默认设置的 Polars 在除一项之外的所有基准中最快(default Polars is fastest on all but one benchmarks)」，紧接着写道，扩展到 192 线程时存在固定开销，对小数据的查询不利。它还写道，限制为 32 核的 Polars 在所有基准中都有竞争力或者领先，原因已经诊断，希望在下一个版本修复(will hopefully fix)。

附录里有两张以秒为单位的数值表，分别是查询时间的总和与几何平均。下面是其中合计表的值，它把所有引擎都完成的查询的最好时间按配置相加。每一行中最小的值对应最快的引擎，32 线程的 Polars 只在 c7a.metal 上运行过。

在 16 vCPU 机器的四行里，默认设置的 Polars 的合计最小。192 vCPU 机器的两行 SF100 也是如此。在 192 vCPU 机器的两行 SF10 里，默认设置的 Polars 不是最小的值。TPC-H 上是 3.10 秒，大于 DuckDB 1.5.6 的 2.46 秒，TPC-DS 上是 23.16 秒，大于两个 DuckDB 版本的 12.25 秒和 12.92 秒。在同样这两行里，固定为 32 线程的 Polars 以 1.97 秒和 9.63 秒成为最小。原文所说的固定开销就显现在这里。

附录还写了随核数的扩展情况。在 SF100 上从 16 vCPU 换到 192 vCPU，按合计算，Polars 在 TPC-H 上快 3.8 倍，在 TPC-DS 上快 2.2 倍。同样条件下，DuckDB 1.5.6 是 3.2 倍和 1.9 倍，DuckDB 2.0 alpha 是 2.2 倍和 1.5 倍，DataFusion 是 1.7 倍和 1.0 倍。在 SF10 上，更多的核对默认设置的 Polars 没有帮助。附录写道，它在 TPC-H 上速度相同，在 TPC-DS 上慢 1.8 倍，而 DuckDB 1.5.6 仍然快了 1.8 倍和 1.3 倍。

因此，能从这份基准里带走的是一句有条件的话。在 Polars 发布的测量中，在这些机器和这些规模上，按去掉 DataFusion 没能完成的查询之后的合计，默认设置的 Polars 在八个配置中的六个里最快。多核机器处理小数据的情况，原文自己就写成了例外。

  • 16 vCPU。 合计表的四行里，默认设置的 Polars 都是最小。
  • 192 vCPU、SF100。 两行里默认设置的 Polars 都是最小。TPC-H 为 9.85 秒，TPC-DS 为 42.33 秒。
  • 192 vCPU、SF10。 默认设置的 Polars 不是最小，固定为 32 线程的运行是最小。
  • 扩展倍数。 在 SF100 上从 16 vCPU 到 192 vCPU 的倍数，在附录列出的四个引擎里 Polars 最大。在 SF10 上，更多的核对默认设置的 Polars 没有帮助。
  • 修复的预告。 措辞是「希望在下一个版本修复」，不是确定的日程。

迁移的顺序 — 迁移指南写了什么

迁移指南把变更分成六组。分别是破坏性变更(Breaking changes)、不再支持的 cast 与操作、API 形态的调整、CSV 读取的变更、已弃用功能的移除，以及新的弃用(Deprecations)。

预发布公告写道，被移除的功能大多已经弃用了很长时间，希望一直跟进新版本的管道没有受到影响。指南的移除表里一并写了各项被标为弃用的版本。例如 melt() 在 1.0、group_by(...).count() 在 0.20、collect(streaming=...) 在 1.25 被标为弃用。

新的弃用也有三项。read_avro() 和 write_avro() 被标为 unstable。水平 concat 的 strict=True 因为高度相等已成为固定要求而不再起作用，被标为弃用。cut() 和 qcut() 将由 bin_intervals()、bin_quantiles()、bin_ranks() 取代。

检查顺序的依据可以取自指南里的警告标记(解读)。以报错形式出现的变更一运行就能看到，而带有悄悄影响警告的条目要对照结果才看得出来。下面把指南中写的应对办法，从带警告的条目开始排列。

  • 依赖顺序的惰性查询。 显式排序，或者给支持的操作传入 maintain_order。迁移期间可以通过 engine affinity 保留以前的引擎。
  • 用到 explode 的地方。 列里有空列表时行数会变，所以要决定是否传 empty_as_null=True。
  • 有符号整数与 UInt64 混用的运算。 输出变为 Int128。
  • 读取 map 列的地方。 用 map.entries() 或在扫描时指定 schema 来保留以前的形状，或者改用 Map 命名空间。
  • 水平 concat。 高度必须相等。填充用 how="horizontal_extend"。
  • 读取函数的参数。 把 read_csv 和 read_ipc 不再接受的参数从调用处去掉。指南写道，需要 rechunk 时改为对返回的帧调用 .rechunk()。

未能确认的事项

  • 「除一项之外」的单位。 发布文章没有写它把什么算作一项基准。在附录的合计表里，默认设置的 Polars 不是最小的行是 c7a.metal 上 SF10 的两行。
  • 「许多表达式」的范围。 发布文章没有列出哪些表达式支持 out-of-core。
  • out-of-core 的配置办法。 修改 80% 阈值和 64GB 预算的配置项名称，以及临时文件放在哪里，在发布文章和迁移指南中都没有找到。
  • 连接与 group-by 支持 out-of-core 的时间。 除了「in the coming time」之外没有写日程。
  • 192 线程开销的原因。 发布文章只写了已经诊断，没有说明内容。
  • 不保证顺序的操作的完整清单。 发布文章和指南都没有把列表封口。
  • 内存用量。 发布文章提到了内存方面的改进，但没有登出内存用量的数值。
  • 独立复现。 仓库是公开的，但未能确认有在 Polars 之外复现的结果。
