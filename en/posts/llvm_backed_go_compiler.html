What It Costs to Reach for Another Language's Libraries - The Bill an LLVM-Backed Go Compiler Makes Visible

From why a cgo call is not merely a function call, to the new line items that appear once the runtime is swapped out

2026-09-07 Dev & Infra

Calling NumPy from a program written in Go, running a PyTorch model, drawing a window through raylib. The sentence sounds appealing, because it promises that an entire foreign ecosystem simply comes along with the code you already have. But what that sentence actually instructs is one thing. Two different execution models get layered into a single process.

Layer them and a boundary appears. A boundary always has a price attached. Who frees the memory, whether the collector can see that pointer, whether one side's exception becomes the other side's panic, whose threading contract applies. Every one of those has to be decided again, on that boundary, by hand. They are exactly the things the compiler and the runtime were quietly guaranteeing for you as long as you stayed inside one language.

An implementation that compiles Go through LLVM and calls C and Python libraries directly has now reached a stable version number. What deserves attention here is not how to use that tool. It is what a decision to use another language's libraries actually takes on. That implementation happens to be an unusually clear specimen of the resulting bill, because it did not dodge the problem. It met it head on, and it wrote down what meeting it head on cost.

Everything below that describes standard Go behavior stays inside what the official documentation and the runtime source commentary actually say. Figures and declarations about the implementation come from the repository documentation and from public API queries, and the query timestamp is 2026-09-07 11:56 KST. The performance and size numbers come from continuous integration runs the project executes on itself, so they must be read as self-measurement. They are not third-party reproductions.

The trigger - what the phrase 「Go compiler」 hides

Introductions are usually short. When something is labelled an LLVM-based Go compiler, most readers take it to mean a thing that accepts standard Go unchanged and only emits different machine code. That reading is exactly half right.

Here is the scope the repository sets for itself. It is compatible with Go 1.20 and later source, it supports the complete Go 1.27 language syntax, and it accepts cgo as well. On supported native platforms it fully supports the Go standard library. Read only that far and the word subset is simply wrong.

Then the same document says something else one section later. The runtime differs from the standard toolchain. Native goroutines map one to one onto operating system threads, stacks are fixed-size native stacks, and the default collector is the conservative Boehm-style collector. Bare-metal targets use a different conservative mark-and-sweep collector instead. All of the syntax is accepted, but the floor that syntax runs on is a different floor.

So a one-line summary of this thing cannot be 「a subset of standard Go」, and it cannot be 「standard Go compatible」 either. The accurate summary is all of the syntax and the standard library, different runtime guarantees. Some write-ups list only Linux and macOS as supported platforms, while the repository documentation lists Windows on amd64 and arm64 in two flavours, one for MSVC and one for MinGW, and goes on to name WebAssembly targets and embedded boards. Summaries always lag.

Why Go was built this way - the price of a custom backend

The Go team considered LLVM early in the project and did not adopt it. The official FAQ preserves the reason in a single sentence. They decided it was too large and slow to meet their performance goals. The performance in question is not the speed of the generated code. It is the speed of the compiler itself. Elsewhere the same document states the goal outright, that building a large executable on a single computer should take at most a few seconds.

That single choice went on to shape the character of the language. A custom backend and a custom linker keep the toolchain small. Static linking by default keeps deployment to one file. Two environment variables switch the target operating system and architecture, which makes cross compilation cheap. In exchange, the depth of optimization does not match a general-purpose backend refined over decades, and the breadth of supported architectures does not match it either.

The same choice also fixed the character of cgo. In a runtime with its own calling convention, its own stack management and its own scheduler, calling a C function means stepping briefly into someone else's contract and stepping back. The procedure for stepping over and returning is the cost.

What the standard toolchain choseWhat it boughtWhat it gave up
A custom compiler backendBuilds measured in seconds even for large executablesThe optimization depth a general-purpose backend has accumulated
A custom linker with static linking by defaultDeployment that ends with a single fileSmall binaries. The runtime and type information are always along for the ride
Target platform chosen by environment variableCross compilation with no C toolchain involvedThe moment a C library enters, that simplicity is gone
Growable goroutine stacksConcurrency that survives hundreds of thousands of goroutinesThe ability to run C code directly on those stacks
A collector driven by precise pointer mapsExact liveness and predictable finalizer timingMemory the collector does not know about needs a contract instead

The last two rows foreshadow the rest of this article. The very design that made concurrency and automatic memory management cheap is the design that starts charging the moment code crosses a boundary.

Why a cgo call is not merely a function call

The top of the cgocall file in the Go runtime source carries a long comment describing the whole call path. That comment is the substance behind the word expensive.

When Go code calls a C function, generated code calls the runtime's cgocall. The first thing cgocall does is call entersyscall, so as not to block other goroutines or the collector. The comment spells out the purpose. It is to tell the scheduler that it should create another thread to run goroutines while this one is off in foreign code.

Next, the assembly-layer asmcgocall leaves the current goroutine stack and switches onto the g0 stack. The comment states the reason as well. The g0 stack is assumed to be an operating-system-allocated stack, which makes it safe to run compiler-generated C code on it. Turn that around and it reads: C code cannot be run on a goroutine stack as it stands. A stack that grows on demand is not a place to execute a C function.

When the C function finishes, control returns to the original goroutine stack and cgocall calls exitsyscall. The comment describes that function in one clause. It blocks until this thread can run Go code without violating the parallelism limit. In other words the return is not immediate. It is a procedure that waits for the scheduler's permission.

If the C side calls back into Go, the staircase runs in reverse one more time. An adapter converts the C calling convention to the Go one, the stack switches from g0 back to the original goroutine stack, and there the code waits on the parallelism limit again. A single callback stacks two layers of round-trip transition.

StageWhat the runtime doesWhy it is needed
Entry announcementMarks entry into a system callSo another thread can be arranged to run goroutines while this one is tied up
Stack switchMoves from the goroutine stack to the operating system stackBecause C code cannot run on a growable stack
The actual callUnpacks arguments from a frame and invokes the C functionThe two calling conventions differ, so something has to broker between them
Return switchRestores the original goroutine stackGo code can only continue on its own stack
Exit waitBlocks until the parallelism limit permitsTo keep the accounting of concurrently running work intact
If there is a callbackThe same staircase once more, in the other directionC calling into Go crosses the same boundary

Laid out this way, it becomes clear that expensive is not a story about a constant delay measured in microseconds. Scheduler accounting and stack ownership change hands on every single call. That is why handing off one large computation is barely affected, while calling small functions in a tight loop is a structural problem rather than a tuning problem.

Pointer passing rules - enforced by contract, not by the compiler

More dangerous than the cost are the rules. The cgo documentation nails down the conditions for passing pointers. Go code may pass a Go pointer to C provided the memory it points to does not contain any Go pointers to memory that is unpinned. And C code may not keep a copy of a Go pointer after the call returns, with the sole exception of memory held down by a pinner.

Go pointers passed as arguments are implicitly pinned only for the duration of the call. The moment the call returns, so does the guarantee. Strings are simpler still. C.CString makes a copy on the C heap, and the documentation states that it is the caller's responsibility to arrange for it to be freed.

// Standard Go cgo - values crossing the boundary are copied, and freeing stays with the caller
cs := C.CString(s)                  // makes a copy on the C heap
defer C.free(unsafe.Pointer(cs))    // without this one line it simply leaks
n := C.strlen(cs)                   // from here on this is C's memory

When C has to hold a Go pointer beyond the call, a pinner is the mechanism. The standard library's Pinner holds an object so that the collector can neither move it nor reclaim it. If a pinned object points at further Go objects and C follows those too, each of those has to be pinned separately.

// When C must hold a Go pointer past the end of the call
var pinner runtime.Pinner
pinner.Pin(p)            // holds it so the collector can neither move nor reclaim it
defer pinner.Unpin()     // the C-side reference is valid only until this releases

What matters here is who enforces the rules. None of them is checked by the type checker. Compilation succeeds either way, and violating them does not fail immediately. Symptoms appear only when the collector actually moves or reclaims that memory. It is the class of defect that first surfaces under load, or once the heap has grown.

  • What may be passed — the memory pointed at must contain no unpinned Go pointers. A struct holding a slice or a string falls foul of this condition
  • What may not be retained — for C to hold a Go pointer past the call, pinning is required, and the moment pinning is released that reference loses its footing
  • Where freeing belongs — what was allocated on the C heap is freed by C's contract. The Go collector does not count that memory, so leaks accumulate silently

How the same problem can be narrowed at the language level is the axis covered in Where Safety Guarantees End at the Rust FFI Boundary. That approach shrinks the boundary itself. What is on the table here is the approach that changes the floor in order to remove the boundary.

The choice to swap out the runtime

Every step of the staircase in section three follows from one premise. The goroutine stack and the scheduler do not belong to C. Erase the premise and the staircase goes with it. That is precisely the road the LLVM-backed implementation took.

The repository documentation puts it concisely. Native goroutines map one to one onto operating system threads with fixed native stacks, so direct C calls require no Go-to-C stack transition and no scheduler transition. The binding mechanism skips wrappers as well. A single Go declaration is bound directly to a C ABI symbol.

import _ "unsafe" // required in order to use the go:linkname directive

//go:linkname Sqrt C.sqrt
func Sqrt(x float64) float64

The directive itself exists in the standard compiler too. The official documentation describes its nature this way. It determines the object-file symbol used for a Go variable or function declaration, allowing two Go symbols to alias the same object-file symbol, and it is only enabled in files that import unsafe. The same page states that this directive can subvert the usual encapsulation of unexported declarations, or even type safety. The documentation itself tells you what the convenience is made of.

The call path is not the only thing that changed. The default collector became a conservative one. Without precise pointer maps it scans the stack and registers and treats every pointer-shaped value as live. That choice is what makes it easy to hold memory created by C code and memory created by Go code in one heap. The bill for it is the list in the next section.

Between 「fully supported」 and 「out of scope」

What is interesting is that this project manages compatibility as a list rather than as prose. It runs the compiler test suite from the standard distribution as it stands and files whatever does not pass into two separate files. One holds what has not been matched yet. The other holds what was never intended to be matched.

The not-yet-matched file holds eleven entries. Six of them concern the wording of diagnostics the parser emits. For a malformed package clause, a malformed name, a byte order mark and similar situations, the message differs from the standard one. The remaining five concern sampled heap profiling, and two of those name a pending proposal number as the reason.

The never-intended file holds one hundred and thirty-six entries. This is the real boundary line. One hundred and ten of them end with the same clause: supporting that toolchain-specific behavior is not a compatibility goal. The rest give more specific reasons. Roughly eighteen say that because the collector is conservative, exact liveness and finalizer timing are not goals. Several say that because there are no garbage collector write barriers, the diagnostics tied to them are not reproduced. And some say that because stacks are fixed-size native stacks, growable-stack behavior is not reproduced.

  • Syntax compatibility and runtime compatibility are different axes. That the same source compiles and that the same source produces the same observations at the same moment are separate facts
  • Code that leans on finalizers and weak references is the first risk group. Under a conservative collector, reclamation timing can drift away from the standard
  • Designs that spawn enormous numbers of goroutines are the second risk group. Under a one-to-one mapping, that count is a thread count

What changes when you build on LLVM

What you gain

Adopting a general-purpose backend brings along everything that backend has accumulated. The optimization pass pipeline, link-time optimization, per-architecture code generators, and the debuggers and analysis tools built on top of them. Target expansion arrives the same way. This implementation can emit several flavours of WebAssembly and reach embedded boards because the backend already knows those architectures.

Binding directly through the C ABI comes from the same place. The same backend compiles C, so calling conventions and type layouts are expressed in the same language from the start. That is why no wrapper layer is required.

What you pay

A large backend means a large toolchain. The official LLVM documentation states the disk requirement plainly. An LLVM-only build needs roughly one to three gigabytes, and a full build of LLVM and Clang needs around fifteen to twenty gigabytes. This implementation requires the LLVM 22 compiler, linker and debugger as prerequisites, and adds a conservative collector library, a foreign function interface library, a cryptography library and a compression library on top.

That list is the build reproducibility bill. Cross compilation in standard Go is cheap precisely because no C toolchain for the target platform is needed. Open the boundary and that premise collapses. The version numbers of system libraries on the developer machine, on the continuous integration machine and on the deployment target all become inputs to the result.

Swapping in LLVM as a Go backend is not new to this project either. The official Go FAQ mentions both a front end coupled to the GCC back end and an experimental LLVM back end using the same front end. Lowering TypeScript the same way was covered in Perry - The Native TypeScript Compiler That Lowers TS Straight to LLVM Machine Code, and one trap from that article repeats here. A better backend does not automatically mean a faster result. Whether the language's semantics lower well onto that backend comes first.

The project runs a size comparison continuously in a dedicated repository and publishes the results. The conditions are published alongside them, which makes the numbers quotable. What must still be carried into the reading is that the party doing the measuring is the project itself.

Note also that this table measures file size, not execution speed. Size and speed are different axes, and a build tuned for size need not be favourable on the speed axis.

What actually breaks at the boundary

This is the centre of the article. Whichever language crosses into whichever other language, the list of things that break at the boundary is largely the same. What matters is the symptom each item produces. You need the symptom in order to suspect the right cause.

What breaksWhy it breaksThe symptomWhere to look first
Memory ownershipThe side that allocates and the side that frees follow different contractsResident memory climbs monotonically over long uptime. A restart clears itWhether every string or buffer crossing the boundary has a matching free
Pointers the collector cannot seeThe only surviving reference lives somewhere the collector does not scanCrashes only under load. Stack traces point at objects already reclaimedThread local storage, the C heap, context pointers handed to callbacks
Object movementThe collector relocates the object while C still holds the old addressIntermittently wrong values, reproducible only once the heap has grownWhether pointers that outlive the call are actually pinned
Exceptions versus panicsOne side's unwinding contract does not exist on the other sideThe process terminates outright instead of returning an error, leaving no logWhether a panic can escape a callback that crosses the boundary
Threading modelOne side attaches conditions to the threadThe same code works on one goroutine and dies on anotherWhether lock acquire and release are paired on the same thread
Error conventionsReturn value, global variable or exception, they disagree on the channelA failure is read as a success. The defect surfaces much laterHow the C function signals errors, and when that value is read
Type representationTypes with the same name differ in width and layoutStruct fields shift. Results diverge between 32-bit and 64-bitInteger widths, arrays as parameters versus as fields, function pointers
Build reproducibilitySystem library and tool versions become inputs to the resultIt works on my machine but not in continuous integrationWhether the prerequisite list has pinned versions

The second row is not an abstract warning. It is recorded in this implementation's own documentation as an actual incident. The head of the deferred-call chain was kept as a raw pointer in thread local storage only, where the conservative collector could not see it. In a stress test that queues a million deferred calls, the collector reclaimed those nodes, and the code executing inside the deferred closures died. The diagnosis is stated crisply. It was a root registration gap, not logical corruption. The fix matched the diagnosis: allocate that state from a root the collector does know about.

The seventh row has concrete documentation behind it as well. The type mapping table for this implementation treats a C function pointer differently as a parameter than as a struct field. In parameter position it is received as a Go function type, while inside a struct it is received as a plain pointer. A C function pointer is only the address of one function, whereas a Go function value may be a closure. Arrays behave the same way, decaying to a pointer in parameter position and remaining an array only inside a struct. For Windows callbacks the documentation states the same consequence explicitly: pass a direct function reference rather than a capturing closure, and carry state through an explicit context pointer.

Calling Python - a lock comes with it

Calling a C library and calling a Python library are not the same difficulty. The second one means bringing an entire stateful interpreter into the process. That state machine has contracts of its own.

The sentence in the official Python C API documentation is short and flat. Unless on a free-threaded build the interpreter is generally not thread-safe, which is why there is a global interpreter lock, and only a thread that holds it may operate on Python objects or invoke Python's C API. A thread entering from outside must acquire and release that state in matched pairs, and the documentation states that every acquire call must be matched by a release call on the same thread.

// Calling a Python library straight from Go code
x := math.Sqrt(py.Float(2))       // hands the value to Python's math.sqrt
std.Print(py.Str("sqrt(2) ="), x) // prints through Python's print

On the surface these are two function calls. But for those two lines to hold, the interpreter must already be initialized inside the process, the thread running this code must hold the lock, and the values handed over must have been built into Python objects that follow the reference counting contract. Three layers of invisible premise.

Seeing how that condition meets Go's execution model makes the one-to-one thread mapping easier to understand. In standard Go a goroutine is not nailed to a thread. The scheduler moves it. If a goroutine holding the lock migrates to another thread, the contract is broken. Pin one goroutine to one thread and the problem disappears structurally.

Free-threaded builds are not a universal solvent either. The official documentation states that even there detaching the thread state is still required, because the interpreter periodically needs to block all threads to get a consistent view of Python objects. Running the collector is given as an example.

  • The ceiling on parallelism is set by somebody else. However many goroutines the Go side spawns, the stretches that touch Python objects queue behind one lock
  • The locking contract is not checked by the compiler. Mismatched acquire and release pairs compile perfectly well
  • Third-party libraries are a separate install. The interpreter and its packages have to be present in the deployment artifact, and their versions become inputs to the result

When this choice is the right one

When the existing library is effectively the only implementation

The judgment usually compresses into one question. Is there a native implementation that could replace that library? If there is not, the boundary cost is not an option, it is a premise. A particular numerical kernel, a codec refined over decades, a vendor's official driver for specific hardware, a cryptographic module mandated by regulation. In those cases the argument stops being 「should we use it」 and becomes 「how few places should the boundary live in」.

The way to reduce the boundary is generally the same. Gather the call sites into one place and cross coarsely once inside it. Hand over a batch instead of calling small functions in a tight loop. The staircase from section three attaches to every call, so reducing the number of calls is what reduces the cost.

When a native implementation exists

With a native implementation available the arithmetic changes. The comparison is no longer performance but total cost of operation. Open the boundary and system libraries ride along in the artifact, cross compilation gets harder, incident investigation requires knowledge of two languages, and the standard profiler and race detector only see half the picture.

That last row overturns decisions most often in practice. An incident in a system with an open boundary is hard to follow to the end with knowledge of only one language. How to read maturity - not by star count

What the star count does not tell you

A public repository's star count is an indicator of attention, not of trust. At the time of the query this repository shows 749 stars, 50 forks and 151 open issues. It was created in December 2023 and was taking commits on the day of the query. None of those numbers yields anything an adoption decision needs.

What to look at instead is four things. The trajectory of release tags, the kind of open issues, the shape of the compatibility claim, and the project's own account of standard conformance.

The four things actually worth reading

Start with the release trajectory. The first tag is April 2024 and the stable 1.0.0 landed on 24 August 2026. Five pre-releases were pushed out inside little more than a week before the stable one, and maintenance releases followed on 29 August and 6 September. Forty-nine releases in total. That it took two years and four months to reach a stable version number, and that two maintenance releases followed immediately after, says far more than the star count does.

The fourth row is the most valuable one in that table. Most projects write their compatibility claim as prose. A sentence saying 「mostly compatible」 cannot be verified, whereas an exception list with attached reasons can be read and argued with. It means you can check directly whether the behavior your own code leans on appears in that list. What opening a language project actually changes and does not change was covered along the governance axis in Mojo Goes Open Source. The axis here is the verifiability of a compatibility claim.

Five questions to answer before adopting

Choosing a tool is mostly a matter of choosing the questions. Answer these five and the decision follows.

  1. How many times does the code cross the boundary? Few calls with a large amount of work per crossing means standard cgo is enough. Only when tight, frequent calls are structurally unavoidable does swapping the runtime become the argument
  2. How many goroutines get spawned? Under a one-to-one mapping, concurrency scale is thread count. A design that presumes tens of thousands is not a fit for this path
  3. Does any code lean on finalizers and reclamation timing? A conservative collector shifts that timing away from the standard. Code that delegates resource release to finalizers is the first thing to inspect
  4. How many deployment targets are there? Whether an LLVM-family toolchain and its system libraries can be provisioned and version-pinned for every target is most of the real adoption cost
  5. Who looks at it when it dies at three in the morning? An incident in a system with an open boundary demands knowledge of two languages. Whether that person exists in the organization comes before the technical judgment

Notably, none of the five asks about performance. In a decision to open a boundary, performance is usually the axis whose answer is already settled, and what actually sinks projects is the other four. The same class of trade-off appears when interactive execution is bolted onto a compiled language, and that axis is laid out in Adding Interactive Execution to a Compiled Language.

What could not be established

  • A speed comparison could not be established. The published continuous integration measurement is the byte count of emitted WebAssembly files, and no execution-time comparison in the same published format was found. The multiples in section eight must not be read across to speed
  • The native-target size table could not be opened. The result file points at native entries through a separate summary and tabular form, but that content was not brought into this article as evidence
  • The actual saving on the C call path could not be established numerically. The absence of stack and scheduler transitions is a design-level statement, and no published figure comparing per-call latency against standard cgo under identical conditions was obtained
  • Third-party reproduction could not be established. Every figure in section eight comes from runs the project executes on itself, and no independent measurement report was found
  • The composition of the 151 open issues could not be established. Defects, feature requests and documentation items were not separated, so that number must not be read as a quality indicator
  • The exact total number of contributors could not be established. The first page of the list shows 19, but the remaining pages were not summed
  • How this implementation behaves on a free-threaded Python build could not be established. The repository documentation states only a requirement of 3.12 or later, and no separate account of lock-free builds fell within what was reviewed
