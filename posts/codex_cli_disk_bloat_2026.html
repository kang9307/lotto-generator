Codex CLI 세션 로그가 수백 GB로 폭증 - 원인과 대응 수칙

서브에이전트 세션 로그가 디스크를 통째로 삼킨 사건에서 배우는 AI 코딩 CLI 로그 위생

2026-07-21 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 코딩 에이전트가 남긴 것은 코드만이 아니다

최근 GeekNews에 올라온 한 토픽이 개발자 커뮤니티에서 눈길을 끌었다. Codex CLI로 서브에이전트를 활용해 작업을 돌리던 중, 세션 로그가 수백 GB까지 불어나 디스크를 소진했다는 사례다. 처음 접하면 "설마 로그 파일 하나가 그렇게까지 커질까" 싶지만, 실제로 GitHub 이슈 트래커에는 부모 세션 하나에서 파생된 자식 세션 수천 개가 합쳐 700GB를 넘는 사례가 구체적인 숫자와 함께 보고돼 있다.

2026년 하반기 현재 개발자 한 명이 Claude Code, Codex, Cursor 같은 CLI형 코딩 에이전트를 동시에 여러 개 띄워두는 것은 특별한 일이 아니다. 문제는 이런 도구들이 대화·계획·툴 실행 과정을 세션 파일로 고스란히 남긴다는 점이다. 코드는 리뷰하고 지우지만, 그 코드를 만들어낸 과정을 기록한 로그는 아무도 신경 쓰지 않는 사이 조용히 쌓인다. 이 글은 그 사건을 그대로 옮기는 대신, 왜 이런 폭증이 구조적으로 일어날 수밖에 없는지, 그리고 지금 당장 무엇을 점검하고 바꿔야 하는지를 정리한다.

1. 무슨 일이 보고됐나 - 숫자로 보는 폭증

GitHub의 openai/codex 저장소에 등록된 이슈 #34061("Insane Codex Disk Usage from Subagents")에는 재현 상황이 상세히 기록돼 있다. 부모 세션 하나에서 파생된 자식 세션 파일이 2,393개였고, 이 자식 세션들만으로 약 731.5GiB를 차지했다. ~/.codex/sessions 디렉터리 전체는 약 755GiB, ~/.codex 디렉터리 전체는 약 760GiB에 달해 1.8TiB 용량의 볼륨이 99~100%까지 찼다고 보고됐다. 자식 세션 파일 하나만 보면, 3분 19초 동안 483.7MB, JSONL 레코드 35만 3,255건(초당 약 1,770건)을 써 내려간 경우도 있었다. 보고 시점 기준 Codex CLI 0.144.6(0.142.4~0.144.6 영향권), macOS arm64 환경이었고, 확인 시점까지 유지관리자의 공식 대응 없이 이슈가 열려 있는 상태였다.

같은 저장소의 이슈 #24948은 반복되는 컴팩션(compaction, 대화 요약·압축) 기록과 원본 툴 출력이 그대로 누적돼 세션 로그가 700MB~2GB 단위로 불어난다고 짚었고, OpenAI 개발자 커뮤니티에도 Codex를 오래 켜두면 디스크가 소진된다는 사용자 보고가 올라와 있다. 세션 파일 경로는 대체로 ~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl 형태이며, 별도로 ~/.codex/logs_2.sqlite 같은 로그용 데이터베이스 파일이 함께 쌓이는 구조로 보고된다. 다만 정확한 경로와 동작은 버전마다 달라질 수 있으므로, 실제 점검 시에는 사용 중인 버전의 공식 문서와 로컬 디렉터리를 직접 확인하는 편이 안전하다.

2. 왜 수백 GB까지 부풀 수 있나 - 구조적 원인

단순히 "로그가 많이 쌓였다"로 넘기기엔 증가 폭이 비정상적이다. 보고된 사례들을 종합하면 몇 가지 구조적 원인이 겹쳐 있다.

2.1 서브에이전트 팬아웃(fan-out)

하나의 부모 세션이 작업을 쪼개 여러 서브에이전트를 생성할 때마다, 부모의 상태나 누적 맥락 일부가 각 자식 세션에도 함께 기록되는 경우가 있다. 서브에이전트 수가 수백~수천 개로 늘어나면, 같은 맥락이 그만큼 여러 번 복제되는 셈이라 총 용량이 산술급수가 아니라 사실상 배수로 불어난다.

2.2 컴팩션 이력의 중복 저장

긴 대화를 이어가려면 오래된 맥락을 요약(compaction)해 토큰을 아끼는 처리가 필요하다. 그런데 이 요약 과정 자체와 요약 이전의 원본 기록이 모두 로그에 남으면, 대화가 길어질수록 "원본 + 요약본"이 계속 누적되는 구조가 된다.

2.3 세션 재개(resume) 시 과거 맥락 재구성

세션을 중단했다가 다시 이어갈 때, 과거 대화 전체를 다시 불러와 처리하는 과정에서 이전 기록이 중복 기록되거나 복제되는 경우가 지적된다. 재개를 자주 반복할수록 이 중복이 누적될 여지가 커진다.

2.4 원본 툴 출력의 무제한 저장

코딩 에이전트는 파일 읽기, 명령 실행, 테스트 결과 같은 툴 출력을 통째로 기록해야 다음 판단에 활용할 수 있다. 이 출력에 상한이나 요약 없이 원문 그대로 저장되면, 대용량 로그나 방대한 파일을 다루는 작업 하나만으로도 세션 파일이 순식간에 불어난다. 회전(rotation)이나 용량 상한, 자동 삭제 정책이 기본값으로 갖춰져 있지 않다는 점이 이 모든 원인을 증폭시킨다.

3. Codex만의 문제가 아니다 - 다른 AI 코딩 CLI의 유사 사례

특정 도구를 저격하는 글로 읽히길 원치 않는다. 실제로 같은 유형의 문제가 다른 벤더에서도 보고돼 있다는 점이 오히려 이 문제의 본질을 더 잘 보여준다. Claude Code의 GitHub 저장소에도 ~/.claude 디렉터리가 별도 관리 메커니즘 없이 무한정 커진다는 이슈가 등록돼 있고, 디버그 로깅이 무한 루프에 빠져 단일 파일이 20GB를 넘어선 사례, 백그라운드 태스크의 출력 파일이 16분 만에 324GB로 불어난 사례, macOS 환경에서 ~/.claude/debug와 MCP 로그 캐시 경로에 472GB가 누적된 사례가 각각 별개의 이슈로 보고돼 있다. 세션 로그(~/.claude/projects/*.jsonl) 자동 압축을 요청하는 기능 제안도 커뮤니티에 올라와 있으며, 이 문제를 겨냥해 ~/.claude 디스크 사용량을 정리해 주는 오픈소스 TUI 도구까지 등장했다.

즉 이것은 특정 벤더의 버그 하나가 아니라, 여러 회사가 비슷한 시기에 비슷한 아키텍처로 비슷한 실수를 반복하고 있다는 신호로 읽는 것이 정확하다. 자율적으로 계획하고 실행하는 에이전트일수록 "무엇을 했는지" 기록할 데이터가 기하급수적으로 늘어나는데, 그 기록을 관리하는 정책은 아직 도구 성숙도를 따라가지 못하고 있다.

4. 실제로 발생하는 문제 - 디스크 풀부터 백업 오염까지

세션 로그 폭증은 단순히 "용량을 좀 차지한다"는 수준을 넘어 여러 실무 문제로 이어진다.

4.1 디스크 풀과 작업 중단

가장 직접적인 결과는 디스크 공간 고갈이다. 볼륨이 가득 차면 코딩 에이전트 자체가 멈추는 것은 물론, 같은 디스크를 쓰는 다른 애플리케이션, 심하면 운영체제 로그인이나 부팅까지 영향을 받을 수 있다.

4.2 시스템 성능 저하

수백 GB 규모의 파일이 계속 생성·수정되면 파일시스템 인덱싱, 백업 소프트웨어의 변경 감지, 디스크 조각화 등으로 전반적인 시스템 반응 속도가 떨어질 수 있다. 일부 보도에 따르면 특정 시점의 로깅 방식이 예상보다 훨씬 잦은 쓰기를 발생시켜 SSD 수명에 영향을 줄 수 있다는 우려도 제기됐는데, 이 부분은 아직 독립적으로 폭넓게 검증된 수치는 아니므로 단정하기보다 "쓰기 빈도가 비정상적으로 높아질 수 있다"는 가능성으로 받아들이는 편이 안전하다.

4.3 백업 오염과 백업 비용 증가

홈 디렉터리를 통째로 백업하는 개인용 백업 도구나 클라우드 동기화 서비스를 쓰는 경우, 수백 GB짜리 로그 폴더가 그대로 백업 대상에 포함돼 백업 시간과 저장 비용이 함께 늘어난다. 정작 복구가 필요할 땐 쓸모없는 세션 로그가 백업 용량 대부분을 차지하고 있는 상황도 충분히 가능하다.

4.4 프라이버시·보안 노출면 확대

세션 로그에는 에이전트가 읽고 쓴 파일 내용, 실행한 명령, 때로는 환경변수나 API 응답까지 그대로 남을 수 있다. 로그가 커지고 오래 방치될수록, 민감한 코드나 자격 증명이 노출될 수 있는 파일이 통제 범위 밖에서 쌓여간다는 뜻이다. 로그 용량 문제는 결국 데이터 취급 범위의 문제이기도 하다.

5. 대응·방어 수칙 - 지금 확인하고 설정할 것

완벽한 해결은 벤더 몫이지만, 사용자 쪽에서도 지금 바로 취할 수 있는 조치가 있다.

5.1 로그 위치부터 파악하라

사용 중인 AI 코딩 CLI가 세션·로그·캐시를 어디에 저장하는지부터 확인한다. 공식 문서나 설정 파일에서 저장 경로를 찾고, du -sh 또는 대화형 도구 ncdu로 해당 폴더의 실제 용량을 주기적으로 확인하는 것이 출발점이다.

5.2 주기적으로 정리하되, 실행 중인 세션은 건드리지 마라

다시 이어 쓸 계획이 없는 오래된 세션부터 지운다. 다만 파일을 쓰고 있는 프로세스가 살아있는 상태에서 강제로 지우면 파일이 손상되거나 재개가 불가능해질 수 있으므로, 관련 프로세스를 먼저 종료한 뒤 정리하는 편이 안전하다.

5.3 로테이션·보존 정책을 직접 걸어라

도구가 기본 제공하지 않는다면, logrotate 같은 범용 로그 회전 도구로 오래된 로그를 주기적으로 압축·보관하거나 일정 기간이 지나면 자동 삭제되도록 설정한다. 수작업 삭제에 의존하면 결국 잊히기 마련이다.

5.4 설정으로 로깅을 최소화하라

도구에 상세(verbose/trace) 로깅 레벨을 낮추거나 끄는 옵션이 제공된다면 평소에는 최소 레벨로 유지하고, 디버깅이 꼭 필요할 때만 일시적으로 올리는 방식이 안전하다. 정확한 설정 키·환경변수는 도구와 버전마다 다르므로, 사용 중인 버전의 공식 문서를 확인하는 것이 우선이다.

5.5 디스크 사용량을 상시 모니터링하라

디스크 사용률이 80~90%를 넘으면 알림이 오도록 임계치를 걸어두면, 폭증이 진행 중이어도 "볼륨이 꽉 차서 아무것도 못 하는" 최악의 상황을 피할 수 있다. 팀 단위라면 Prometheus와 node_exporter 조합처럼 이미 쓰고 있는 인프라 모니터링에 개발자 워크스테이션의 디스크 지표를 추가하는 것도 방법이다.

5.6 심볼릭 링크로 별도 볼륨에 격리하라

세션·로그 폴더가 계속 커질 것으로 예상된다면, 처음부터 여유 공간이 넉넉한 별도 파티션이나 외장 볼륨에 실제 디렉터리를 두고, 홈 디렉터리에는 심볼릭 링크만 남기는 방식으로 시스템 볼륨을 보호할 수 있다.

5.7 .gitignore로 실수 커밋을 막아라

세션·로그·캐시 디렉터리가 프로젝트 폴더 안이나 근처에 생성되는 도구라면, .gitignore에 해당 경로를 반드시 등록해 대용량 로그 파일이 실수로 커밋되는 사고를 막아야 한다. 한 번 커밋된 대용량 파일은 히스토리에서 지우기가 훨씬 번거롭다.

6. 관측성 부채와 로그 위생 - AI 에이전트 시대의 일반 교훈

이 사건이 남기는 더 큰 교훈은 도구 하나의 버그가 아니라 "관측성 부채(observability debt)"라는 개념이다. 전통적인 소프트웨어에서는 로그가 사람이 문제를 진단하기 위한 보조 자료였고, 상대적으로 예측 가능한 속도로 쌓였다. 반면 자율적으로 계획·실행·재시도를 반복하는 에이전트는 스스로 얼마나 많은 이벤트를 생성할지 사람이 미리 가늠하기 어렵다. 서브에이전트를 몇 개나 띄울지, 툴 출력을 몇 번이나 재사용할지가 작업 내용에 따라 크게 달라지기 때문이다.

기술 부채를 방치하면 나중에 갚아야 하는 비용이 커지듯, 로그·캐시 관리를 방치하면 어느 순간 디스크 풀이라는 형태로 청구서가 날아온다. AI 에이전트 시대의 로그 위생은 더 이상 "가끔 폴더 하나 지우는 습관"이 아니라, 개발 환경 운영의 정식 항목으로 다뤄야 한다는 것이 이번 사건이 주는 실무적 결론이다.

7. 벤더에게 필요한 개선

사용자 쪽 대응만으로는 근본 해결이 어렵다. 커뮤니티 이슈 트래커에서 반복적으로 제기되는 요구를 정리하면 다음과 같다. 세션·로그 디렉터리에 기본 보존 기간과 용량 상한을 두는 것, 임계치를 넘으면 사용자에게 경고하는 것, 컴팩션 이력과 중복 이벤트를 자동으로 정리하는 로테이션·압축 기능을 기본값으로 제공하는 것, 그리고 진단용 정리 명령을 공식 CLI 기능으로 내장하는 것이다. 지금은 사용자가 직접 디렉터리를 뒤져 문제를 발견해야 하는 구조이지만, 자율 에이전트가 표준 개발 도구로 자리 잡을수록 이런 안전장치는 선택이 아니라 기본값이 되어야 한다.

8. 병렬 에이전트·세션 가시성 도구와의 접점

이 문제는 최근 다룬 다른 흐름과도 맞닿아 있다. 여러 AI 에이전트를 한 레포에 병렬로 풀어놓는 패턴을 다룬 글에서 짚었듯, 병렬 세션 수를 늘리는 것은 처리 속도를 높이는 만큼 세션 로그가 쌓이는 속도도 그만큼 늘린다는 뜻이다. 워크트리·컨테이너로 파일 충돌은 막을 수 있어도, 로그 폭증은 별개로 관리해야 하는 축이다.

한편 Claude Code·Cursor·Codex 세션을 한곳에 모아 검색·비용을 추적하는 AgentsView 같은 로컬 대시보드는 여러 도구의 세션을 한눈에 파악하는 가시성 문제는 풀어주지만, 그 자체가 디스크 폭증을 막아주는 것은 아니다. 오히려 이런 도구를 도입할 때 "지금 내 세션 로그가 총 얼마나 쌓여 있는가"를 먼저 확인하는 계기로 삼는 편이 현실적이다. 가시성 도구와 정리·로테이션 정책은 서로 대체재가 아니라 보완재로 봐야 한다.

결론: 코드만큼 로그도 관리 대상이다

Codex CLI 서브에이전트 세션 로그 폭증 사례는 특정 도구의 실수 하나로 끝날 이야기가 아니다. 자율적으로 계획하고 실행하는 AI 코딩 에이전트가 표준 워크플로가 된 지금, 그 과정을 기록하는 로그·캐시가 통제 없이 쌓이는 구조는 여러 벤더에서 공통으로 나타나고 있다. 오늘 할 수 있는 실용적인 조치는 세 가지로 요약된다. 첫째, 지금 쓰는 AI 코딩 CLI가 세션·로그를 어디에 얼마나 쌓고 있는지 직접 확인한다. 둘째, 로테이션·보존 정책과 디스크 모니터링을 지금 설정한다. 셋째, 벤더 문서와 이슈 트래커를 주기적으로 확인해 새 버전에서 개선된 기본값이 나왔는지 챙긴다. 코드 리뷰만큼이나 "내 개발 환경이 무엇을 남기고 있는가"를 점검하는 습관이, AI 에이전트 시대의 새로운 기본기가 되고 있다.
