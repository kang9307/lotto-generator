原文の骨格 - 症状が先、原因はその次

監視に関する文章の大半はダッシュボードの作り方を扱い、作ったグラフを読んで解釈する方法を扱う文章は少ない。原文はこの空白を狙っている。グラフを読み、診断し、行動する方法が主題だ。この記事は原文の流れに沿って、何をどの順序で見てどんな結論に至るかを、一つの手順に並べ直す。

原文の出発点は、指標を四つに束ねる枠組みだ。Google SRE に由来する四つのゴールデンシグナル、すなわちトラフィック、遅延時間、エラー、飽和度である。これに続く核心の区別が症状と原因だ。遅延とエラーは利用者が体験する症状で、CPU・メモリ・スレッドプール・コネクションプールはインフラの状態、つまり原因の候補である。原文の文は「症状を先に把握し、原因で犯人を絞り込まなければならない」だ。

  • トラフィック。 システムに入ってくるリクエストの量だ。以降のすべての指標を割る分母の役割を持つ。
  • 遅延時間。 リクエストから応答までにかかる時間だ。利用者が感じる遅さがここに現れる。
  • エラー。 失敗したリクエストの割合だ。利用者が出会う失敗がここに現れる。
  • 飽和度。 資源がどれだけ埋まっているかだ。原因候補を絞る側の指標で、後で扱う CPU・プール・キューはここに属する。

この区別はアラート設計にもつながる。原文は、「CPU 80%」のような任意の資源しきい値にアラートを掛けると誤報が多く、エラー率がしきい値を超えたときのように症状にアラートを掛けてこそ実際の利用者への影響と一致すると言う。資源の指標は単独で読むと嘘をつく、というのが後続の節に共通する前提だ。

トラフィック - どれだけ入ってくるか

最初の質問は、どれだけ入ってきているかだ。特別なイベントのないサービスは一定のトラフィックの形を保つ。原文は、その平常時の形を身につけておくことが、異常に気づく前提だと言う。指標が平常時の半分なら、正常範囲内でも何かがおかしいという文がその例だ。

  • 垂直の低下。 リクエストがサーバーに届いていないという信号だ。ロードバランサー、DNS、ゲートウェイのような上流の問題を疑う。直感に反して、この瞬間サーバー側の指標はきれいだ。
  • 垂直の急上昇。 突然の殺到だ。話題になった場合、クローラーのアクセス、攻撃が候補で、周期的に繰り返される急上昇ならバッチ作業や cron を思い浮かべる。
  • 分母としてのトラフィック。 同じ500件のエラーでも、1日100万件のうちか1,000件のうちかで意味がまったく違う。エラーは件数ではなくトラフィックに対する割合で読む。

この節が与える手順は単純だ。他の指標を開く前に、リクエスト量の形が平常時と同じかをまず見る。リクエスト量が折れているなら、サーバーの内部を探る作業は後回しにする。

遅延 - 平均が隠すもの

二つ目の質問は、どれだけかかるかだ。原文は、平均応答時間が分布の形を隠すと言う。平均が同じ100msの二台のサーバーが、まったく違う性能特性を持ちうるからだ。そこでパーセンタイルを使う。P50 は典型的な利用者の体験で、P95 と P99 は目標を定めて早期警告を捉えるために使う。原文は、異常の兆候はほぼ必ず P99 に先に現れると言う。

  • 規模に換算する。 毎秒1,000件なら、P99 は毎秒10人が遅い応答を受けるという意味で、1日では86万4千件だ。1パーセントは小さな数字ではない。
  • 呼び出しが掛け算になる問題。 画面一つを描くのに40回を超える API 呼び出しが使われるサービスでは、呼び出しごとに99パーセントが目標時間内に終わるとしても、40回すべてが目標内に終わる確率は約67パーセントに下がる。
  • 尾の持ち主。 データを多く蓄積したヘビーユーザーは、自然と遅い尾に入る。原文は、P99 がサービスの最優秀顧客が体験する応答時間である可能性が高いと表現する。

同じ主題を、サーバーが複数台のときの集計問題に広げた文章は、サーバー10台の p99 を平均したで扱った。この記事では、P99 を読む理由までを原文に沿って述べる。

エラー - 速い失敗と遅い失敗

三つ目の質問は、どれだけ失敗するかだ。原文は、まずステータスコードを分ける。5xx はサーバー側の失敗なので、常に懸念の対象だ。4xx はクライアントの誤ったリクエストだが、古いアプリと新しいサーバーのバージョンがずれて API の契約が壊れた信号であることもある。次の区別が失敗の速度だ。

  • 遅い失敗。 タイムアウトのように数秒待ってから失敗する型だ。待っている間スレッドとコネクションをつかむので、エラーと飽和が同時に現れる。
  • 速い失敗。 connection refused や、死んだ依存サービスから来た null 参照のように、ミリ秒以内に失敗する型だ。資源の使用率は健全なまま保たれる。
  • 生存者バイアス。 エラー率が跳ね上がるのに、P99 はむしろよく見えるという逆説がある。即座に失敗したリクエストがミリ秒の標本として混ざり込むからだ。このとき遅延のグラフだけを見ると安心してしまう。

この節の手順は、エラーが増えたら失敗が速いか遅いかを先に分けることだ。速い失敗なら、資源の指標ではなく依存先が生きているかを見る。遅い失敗なら、次の節の資源とプールの指標に降りる。

表の複数の行が同時に当てはまるときは、原文の仮説主導の調査に従う。二十個のグラフを流し見る代わりに、仮説を一つ立てて、それを確かめるか反証するグラフを一つ見る。原文の例は「DB が遅いなら、コネクション待ちが高いはずだ」だ。確認できれば症状チェックリストの次の項目へ進み、反証されれば次の仮説へ移る。こうすると、ダッシュボードを目的なく歩き回る時間が減る。

資源の指標 - CPUとメモリを単独で読まない

原文の文は「リソース指標は単独で読むと嘘をつく」だ。CPU は必ず遅延と重ねて読む。原文は、CPU のパターンと遅延の組み合わせで三つの場合を挙げる。

CPU の形遅延原文の診断
なだらかに上昇低く安定健全なスケーリング。見守る
20〜30%の水準跳ね上がるI/O 待ち。DB の遅れ、ロック、プール枯渇、タイムアウト。CPU ではなく詰まった資源を見る
100%に平らに張り付く高い容量超過か無限ループ。トラフィックが平常ならコードを見直す

コンテナ環境には、この表が見落とす罠がもう一つあると原文は言う。Kubernetes の CPU 制限が生むスロットリングだ。コンテナは既定で100msの周期ごとに CPU 時間のクォータを受け取り、0.5コアの制限なら周期あたり50msだ。クォータを使い切ると次の周期まで強制的に止まる。ところが CPU 使用率のグラフには止まった時間が現れないので、使用率は正常なのに P99 の尾だけが長くなる。

  • 正常な信号、のこぎり歯。 JVM や Node.js のように GC のあるランタイムで、メモリが上がっては GC で急に下がるのこぎり歯は、心拍と同じ正常なパターンだ。
  • リークは底を見る。 山ではなく谷を見る。谷が水平なら正常で、階段のようにじわじわ上がるなら、GC が回収できないオブジェクトが毎回残っているという信号だ。
  • 階段状の急上昇。 のこぎり歯の上へ垂直に跳ねたなら、大量のデータを一度にメモリへ載せたということだ。全テーブル照会、大きなファイルの処理、Excel ダウンロードが例に出る。OOM が起きる前にページネーションかストリーミングに変える。

プールとキュー - 同時処理数の算数

原文の算数一つがこの節の中心だ。リトルの法則、すなわち同時に処理中のリクエスト数は、毎秒の流入量に平均処理時間を掛けたものだ。毎秒1,000件が入ってきて平均処理に50msかかるなら、同時リクエストは50個で、スレッド200個のプールで足りる。ところが DB が遅くなって平均が2秒になると、同時リクエストは1,000に2を掛けた2,000個になってプールが底をつき、1,800個が列をなす。トラフィックはそのままなのにシステムが崩れる。

  • 連鎖崩壊。 すべてのスレッドが DB を待つと、新しいリクエストを処理するスレッドがない。ヘルスチェックがタイムアウトし、ロードバランサーがサーバーを外し、残ったサーバーがより多くのトラフィックを受けてより早く崩れる。遅いクエリ一つがクラスター全体の障害に広がる。
  • リトライ嵐。 クライアントが失敗したリクエストを再送すると、トラフィックが2〜3倍に増えて回復する隙をふさぐ。
  • プール自体より傾き。 スレッドプールの使用量は絶対値より傾きを見る。トラフィックに応じてなだらかに上がるなら正常で、垂直に上がるなら他の場所の遅れが待ちを作っている。
  • イベントループのサーバー。 Node.js や WebFlux はリクエストごとにスレッドを置かず、一つの実行スレッドがループを回す。一か所が詰まるとプロセス全体が止まる。指標はイベントループの遅延で、平均ではなく最大値か P99 で、絶対的な基準ではなく平常時と比べた傾向で読む。8プロセスの平均 CPU 40%が、100%の一つを隠しうるので、プロセスごとの最大値を見る。

コネクションプールでも同じ原理が出る。原文の例は、HikariCP の既定値10個のコネクションに、アプリケーションスレッド200個だ。DB が遅くなるとコネクションタイムアウトのエラーが出る。誤った対応はプールを大きくすることで、正しい対応は「なぜ返却が遅くなったのか」を問うことだ。原文の文は「原因は多くの場合プール自体ではなく、どこかの遅れだ」である。

ボトルネック・飽和・キャッシュ・タイムアウト - 二つのグラフが食い違うとき

複数の指標が一緒に動くとき、原文が与える最後の道具がいくつかある。第一はボトルネックの形だ。ボトルネックになる場所の前には待ちが積み上がり、その後ろは閑散としている。システムのスループットは最も弱い輪が決める。第二は、飽和曲線が直線ではないという点だ。使用率が上がるほど、待ち時間は非線形に膨らむ。

使用率待ち時間（基準比）原文の解釈
50%1倍基準
80%4倍ここから急になる
90%9倍まだ10%残っているという考えは危険だ
95%19倍残りの5%は待ち時間19倍になって返ってくる
  • キューはただではない。 キューは一時的な殺到を吸収するときは健全だが、流入がスループットを超え続けると遅延の借金になる。スループットが毎秒100件のとき100個が溜まれば次のリクエストは1秒、1万個が溜まれば100秒余計に待つ。すでにクライアントが諦めたリクエストに資源を使うことも起きる。
  • バックプレッシャーとロードシェディング。 キューの長さが回復せず上がり続けるなら、フロー制御がないという信号だ。キューが溢れたとき429で明示的に拒否すれば、全員が少しずつ遅くなる代わりに、一部は速く失敗し、残りは正常に処理される。
  • キャッシュヒット率が崩れるとき。 ヒット率97パーセントは DB がトラフィックの3パーセントだけを受けるという意味で、キャッシュが崩れると DB は30倍を超える負荷を受ける。人気キーの TTL が切れたとき数百のリクエストが同時に DB へ向かうのがキャッシュスタンピードだ。DB 負荷が急増した時刻とヒット率が下がった時刻が重なるかをまず見る。
  • タイムアウトの不一致。 ゲートウェイのタイムアウトが3秒、バックエンドのクエリのタイムアウトが5秒なら、利用者は3秒で504を受けるのに、バックエンドは5秒に静かに成功を記録する。バックエンドの指標にはエラーがなく、ゲートウェイには504があるという矛盾が生じる。解決策は、内側へ行くほど短くするタイムアウト予算だ。原文の例は、ゲートウェイ3秒、HTTP クライアント2.5秒、DB 2秒である。

この節の診断規則は一つに集まる。ある階層はエラーなのに次の階層は成功という矛盾が見えたら、タイムアウトの整合をまず疑う。

タイムアウト予算の目的は、内側の階層が外側の階層より先にきれいに失敗するようにして、エラーが上へきちんと伝わるようにすることだ。外側が先に諦めると、内側は誰も読まない応答を作り続け、過負荷の最中にも CPU とコネクションを使う。3秒、2.5秒、2秒という値は原文の例なので、自分のサービスの値は実際の応答分布を見て決める必要があり、原文はサービスごとの値を示していない。

三つの時間軸 - 平常時、デプロイ直後、障害中とその後

原文は、同じグラフでもいつ見るかで読み方が違うと整理する。平常時は基準線を学び、デプロイ直後は30分に注意し、障害中は復旧が原因分析より先に来る。

  • 平常時の5分。 1日5分ずつダッシュボードを一巡する。トラフィックの形、CPU のリズム、正常な P99 の範囲を身につければ、「平常時を知らなければ何かおかしいことにも気づけない」という文が意味する問題は消える。基準線を超えたらアラートが鳴るように設定する。1日1パーセントずつ4週間悪化する変化ではアラートが鳴らないので、今日の P99 を先週の同じ曜日と重ねるパネルが要る。
  • デプロイ後30分。 デプロイ時刻をグラフに目印として残す。「デプロイの前か後か」に答えるのに他の情報が要らなくなり、費用対効果が最も大きいと原文は言う。新しいプロセスは、JIT コンパイルが未完了、ローカルキャッシュが空、コネクションプールの再構築のために、P99 が一時的に2倍になることもある。数分かけて回復すればウォームアップで、10分以上高ければ回帰だ。
  • ロールバック基準とカナリア。 デプロイ後のエラー率が X パーセントを超えるか、P99 が10分以内に回復傾向を見せなければ議論なしでロールバックする、といった基準を事前に合意する。カナリアはサーバー一、二台に先にデプロイし、同じトラフィック条件で、カナリアと安定版をバージョンのラベルで分けて並べて比較する。
  • 障害中とその後。 まず範囲を確定する。全体か、特定の API か、特定の地域や顧客かだ。次に、直近30分から数時間以内の変更、つまりデプロイ、設定、機能フラグ、インフラ作業、マーケティングによる流入を探す。復旧が先だ。ロールバック、再起動、スケールアウト、フラグで機能を切る順で、証拠である指標・ログ・ヒープダンプは復旧後も残る。事後分析は、最初の症状、アラート、人の対応の開始、復旧の四つの時刻でタイムラインを描き、検知の空白と対応速度の空白をアクションアイテムに変える。原因の記述に人を書かない。

この節の手順の要約は三行だ。平常時は基準線を作り、デプロイ後は回復するかどうかでウォームアップと回帰を分け、障害中は復旧を先にして、仮説一つにグラフ一つで確認する。

自分のサーバーに当てはめる六段階

次の六段階は、原文の流れを、読者が自分のサーバーで繰り返せる順序に移したものだ。各段階の根拠は前の節にある。

  1. リクエスト量の形を見る。 平常時と同じか、垂直に折れたか、急上昇したか。折れたなら、サーバーの内部より上流を先に見る。
  2. 遅延をパーセンタイルで読む。 平均ではなく P50、P95、P99 を見る。特定の API だけが遅いのか、すべて遅いのかを分ける。
  3. エラーを割合で読み、速度を分ける。 件数ではなくトラフィックに対する割合で見て、速い失敗か遅い失敗かを区別する。
  4. 資源の指標を遅延に重ねる。 CPU が低いのに遅延が高ければ待ちを、CPU が平らに張り付いていれば容量かループを疑う。コンテナならスロットリングも候補に載せる。
  5. 待ちが積み上がる場所を探す。 プール、キュー、キャッシュヒット率、タイムアウトの整合を見る。ボトルネックの前には待ちが積み上がり、後ろは閑散としている。
  6. 直近の変更と基準線を突き合わせる。 デプロイの目印と先週の同じ曜日のパネルを並べ、回復しなければ事前に合意した基準でロールバックする。

原文の結論のチェックリストは、この六段階を四つの問いに縮める。どれだけ入り、どれだけかかり、どれだけ失敗し、何が埋まっているかだ。アラートが鳴ったら立ち止まって、この四つを問う。

次の三行は、原文にはないものだ。上の順序のうち資源の指標をシェルで読み取り専用で確かめたいときに使える負荷のない命令で、原文がこの命令を勧めているわけではない。システムの負荷平均、プロセスの待ちと CPU 状態の標本、ディスク使用量を、それぞれ読むだけだ。

# 原文にはない: 読み取り専用、無負荷
                    uptime
                    vmstat 1 5
                    df -h

これらの命令の出力を読むコツは、別の記事で扱う。ログを絞って読む方法は Linux ログ分析コマンドガイド、観測の仕組みを自作しない選択は Sentry と PostHog の記事、アラートをコードで標準化する方法は アラートシステム標準化の記事を参照する。

この手順には前提がある。原文の事例は、JVM や Node.js のようなランタイム、Kubernetes のコンテナ、スレッドプールとコネクションプールを持つ Web サービスを背景にしている。バッチ処理やストレージのように構造が異なるシステムで同じ表をそのまま使えるかは原文にないので、各行の原理である症状が先と待ちが積み上がる場所探しだけを持ち帰り、指標の名前は自分の環境に合わせて読み替える必要がある。
