Topcoat — 「API層をなくす」という発想が実際になくすもの

Rustフルスタックフレームワークが消した境界線は、消滅したのではなく移動したものだ

2026年7月29日 開発・インフラ

序論: 「API層がない」という文を分解すると

2026年7月22日、TokioチームがRustのフルスタックWebフレームワークTopcoatを公開した。発表文の中心的な主張は簡潔だ。すべてのマークアップをサーバーでレンダリングし、コンポーネントをasync関数にしてデータベースを直接照会させれば、別途のAPI層に必要だったボイラープレートがすべて消えるというものである。

この一文は魅力的だが、技術選定を行う場面では危険な種類の魅力だ。「なくす」という言葉は二つのことを意味しうるからである。一つは本当に不要になって消えることであり、もう一つは依然として必要だが別の場所へ移ることだ。前者は純粋な利益だが、後者は帳簿上の項目移動に近い。目に見えるコードが減るだけで、そのコードが担っていた責任はどこかで再び処理されなければならない。

本稿はTopcoatを紹介する記事ではない。「API層をなくす」という発想そのものを実務の視点から解剖する記事である。サーバーレンダリングが再び戻ってくる2026年の流れの中で、この選択がいつ正しく、いつ誤りなのかを検討する。確認手段は公式リポジトリと発表記事、そしてCargo.tomlとdocs.rsのメタデータだ。確認できなかったものは確認できなかったと記した。特に性能の数値は公式資料に存在しないため、本稿にも存在しない。フレームワーク紹介記事でよく見かける「速い」という類の主張を本稿は行わない。

サーバーレンダリングがどのような経路で再び主流の候補になったのかについては、フロントエンド20年の循環を整理した記事で別途扱った。ここではその流れの最新事例を一つ深く掘る。

1. Topcoatとは何か — 公式資料で確認できたものだけ

まず事実関係を固定する。以下は2026年7月末時点で公式リポジトリ・発表記事・docs.rsから直接確認したものだ。

  • 主体と所在: tokio-rs/topcoatリポジトリ。非同期ランタイムTokioを作ったチームの組織アカウント配下にある。
  • ライセンス: MIT。Cargo.tomlのlicenseフィールドとリポジトリ表記が一致する。
  • バージョン: docs.rs基準で0.5.0が2026年7月27日付で掲載されている。つまり発表から5日でマイナーバージョンが上がった。
  • 自己表記: READMEが「Early-stage and experimental. Expect breaking changes.」と自ら明示している。ベンダーがマーケティングで書いた文言ではなく、著者が付けた警告だ。
  • 要求ツールチェーン: Cargo.tomlのrust-versionが1.95。社内ビルドイメージが固定されていると、この一行が導入スケジュールを左右しうる。
  • 構成: ワークスペースが30を超えるクレートに分割されている。セッション・クッキー・メール・アイコン・フォント・アセット・Tailwind・UIがそれぞれ別クレートで、htmx・Alpine AJAX・Datastar統合もクレートとして分離されている。

動作方式の骨格は三つだ。第一にすべてのマークアップはサーバーでレンダリングされる。コンポーネントはasync関数なので、その中でDBを照会したり権限を確認したりできる。第二に、ブラウザで生きて動く必要がある部分は$(...)式で書く。発表記事の説明によれば、この式は型検査されたRust式の部分集合をJavaScriptへ相互コンパイルしたものであり、そのためWebAssemblyバンドルも別途のクライアントビルド段階も不要になる。第三に、サーバーが描き直す必要のある更新は#[shard]で標記したコンポーネントが担当する。

最小形はこうだ。以下は公式READMEの冒頭例を最小限に写したものである。

#[page("/")]
async fn home() -> Result {
    view! { <h1>"Hello, World!"</h1> }
}

ルートが関数の上の属性一つで終わる。ルーター登録コードも、ハンドラのシグネチャを合わせる作業もない。発表記事は、モジュール構造からルートツリーを推論する方式も併せて提供すると述べている。

ここで重要なのは、確認できたものと確認できなかったものを分けておくことだ。

2. 「API層の除去」が消すものと移すもの

ここからが本論だ。画面一つを描くために今日よく使う構造を思い浮かべてほしい。バックエンドにエンドポイントを作り、レスポンスDTOを定義し、フロントに同じ形の型を再度宣言し、フェッチ関数を包み、ローディングとエラーの状態をコンポーネントへ配線する。この配線作業が画面ごとに繰り返される。

Topcoatの主張は、この反復がサーバーとブラウザの間に境界線があるために生じるというものだ。境界があるからシリアライズが必要になり、シリアライズが必要だから型が二度宣言され、型が二組あるからドリフトが生じる。コンポーネントをサーバーで実行すればこの連鎖が丸ごと切れる。論理は正確である。

// コンポーネントの中で直接照会する — 別途エンドポイントはない
#[component]
async fn user_profile(cx: &Cx, user_id: &str) -> Result {
    let user = load_user(cx, user_id).await?;
    view! { <div>{user.name}</div> }
}

問題は、その境界線がシリアライズだけをしていたわけではない点だ。HTTPエンドポイントはボイラープレートであると同時に複数の関心事が貼られていた掲示板でもあった。掲示板を外せば、貼られていた紙は消えるのではなく床に落ちる。

区分項目その後どうなるか

クライアントのフェッチラッパーとローディング・エラー配線コンポーネントがawaitすれば済む

表の下半分を一つずつ解いてみる。

2.1 認可 — 利点と危険が同じ根から出る

発表記事は、コンポーネントの中でデータを直接保護できる点を利点として提示している。コードベースの全く別の場所にあり、実行されるかどうか分からないミドルウェアに頼るよりよいという論理だ。実務経験上、この指摘は妥当である。認可ミドルウェアがルート登録順序のせいで特定パスで飛ばされる事故はよくある。

ところが同じ性質が逆方向にも働く。チェック地点がミドルウェア一箇所なら監査範囲はファイル一つだ。コンポーネントごとにチェックするなら監査範囲はコンポーネント全数になる。見落とす確率が地点数に比例して増えるという意味ではないが、見落としを見つける費用は確実に増える。「この照会は権限チェックを通ったか」を人が目で確認する場所が十倍になるということだ。

実務的には二つの方式のどちらかを選ぶ必要がある。データアクセス関数そのものを権限コンテキストなしには呼べないよう型で強制するか、コンポーネント内での生のDBアクセスを禁じ、チェックが内蔵されたドメイン関数だけを呼ぶ規約を立てるかだ。後者が現実的であり、これは結局9章で述べるドメインクレート分離と同じ結論につながる。

2.2 照会回数 — メモ化が防ぐものと防げないもの

コンポーネントがそれぞれDBを照会すれば、レンダーツリーに沿ってクエリが増える。Topcoatはリクエスト単位のメモ化を提供しており、発表記事はこれをReactのキャッシュ概念から着想を得たと述べている。同じリクエスト内で同一の照会が繰り返されれば一度だけ実行するという意味だ。

この仕組みは重複を防ぐ。多数は防げない。一覧画面で行ごとにコンポーネントがそれぞれ異なるキーで照会すれば、それは重複ではなく互いに異なるN個の照会である。メモ化はここに関与しない。従来のN+1問題がSQL層からビュー層へ席を移した形であり、解法も従来と同じだ。親でまとめて照会して子へ渡すか、データローダー系のバッチングを導入するかである。

ここでの実質的な危険は性能そのものではなく発見時点だ。エンドポイントがあれば遅いAPIがダッシュボードに名前で現れる。コンポーネント内部の照会には名前がない。導入するならコンポーネント単位のトレーシングを初期から付けておく方がよく、これは「ボイラープレートが減った」という利益の一部を返す費用になる。

2.3 キャッシュ — URLは無料のキャッシュキーだった

あまり議論されないが実務では大きく響く項目だ。GET /api/products/123はそれ自体でCDNとリバースプロキシとブラウザが共有するキャッシュキーである。このキーは誰も設計していないのに存在した。HTTPが与えたものだ。

コンポーネントが内部で照会すればこのキーはない。サーバーレンダリング結果全体をページ単位でキャッシュするか、アプリケーション層で自前のキャッシュを設計する必要がある。パーソナライズされた画面が混ざればページ単位のキャッシュはすぐに難しくなる。Topcoatのロードマップに静的エクスポートが入っているのは、この地点の需要を認識している信号として読めるが、2026年7月末時点ではロードマップ項目だ。

3. shard — 消えたのではなく自動生成された境界

本稿で最も強調したい箇所だ。クライアント状態が変わったときサーバーがUIの一部を描き直す必要がある場合、Topcoatは#[shard]で標記したコンポーネントを使う。そして発表記事の説明によればshardはエンドポイントを公開する。

つまりAPI層は消えたのではなく手で書かなくなったのだ。HTTP境界はそのまま存在し、その上のリクエスト・レスポンスもそのまま行き交う。変わったのは、その境界を人が宣言せずマクロが生成する点である。

  • これは悪い設計ではない。むしろよい設計だ。反復作業を道具が行うのはコンピュータを使う理由そのものである。
  • ただしセキュリティレビューの対象が消えるわけではない。生成されたエンドポイントもインターネットに開かれたエンドポイントだ。何がどのパラメータで公開されているかは依然として知る必要がある。
  • レート制限、濫用防止、認証トークン検証といったポリシーは自動生成された境界にも適用されなければならない。手で書いたエンドポイントなら自然に付けていたはずのものだ。
  • 「APIがない」と信じてAPIゲートウェイのポリシーを立てないことが実際の危険である。抽象化は存在を隠しただけで、存在を消してはいない。

ボイラープレートが減るとき一緒に消えるものがもう一つある。ボイラープレートが果たしていた標識の機能だ。エンドポイントを手で書く行為は「ここが信頼境界だ」という事実を開発者に強制的に認識させる。その行為が消えれば認識も一緒に薄れる。これはTopcoat固有の問題ではなく、サーバーアクションやRPC自動生成系が全般に共有する構造的性質である。

4. クライアント操作が増えたときにぶつかる壁

Topcoatのクライアントモデルは二層になっている。サーバー往復なしにブラウザで完結するものと、サーバーが描き直して部分置換するものだ。前者はsignal宣言と$(...)式で、後者はshardで処理する。トグルやドロップダウンを開くようなローカル状態は往復が要らない。

操作が単純なときこのモデルは優雅だ。問題は密度が上がるときである。

  • 部分集合の壁: $(...)は型検査されたRust式の部分集合をJavaScriptへ移す。部分集合の外へ出るとコンパイル時点で止められる。静かに壊れるよりはるかによいが、複雑なクライアントロジックではこの壁に頻繁に出会うことになる。
  • 往復の壁: 部分集合の外のロジックはshardへ渡る。その瞬間ネットワーク遅延が操作遅延になる。ドラッグで図形を動かしたりキャンバスを描いたりする操作には構造的に不利だ。
  • 公式文書が認めた壁: 発表記事はクライアントリアクティビティシステムがまだ開発初期段階でいくつかの制約があると明記している。そしてその間はhtmxとAlpine.jsの統合を使えると案内している。
  • モデル混在の壁: 上の案内に従うと一つの画面に三つの操作モデルが混ざりうる。Rustの$()、htmxのHTML属性、Alpineのディレクティブだ。「振る舞いの局所性」を設計原則に掲げたフレームワークが、まさに複雑な画面で局所性を失うという逆説が生じる。
  • オフラインの壁: サーバーが真実の源である構造では、オフライン優先や楽観的UIは別途の設計を要求する。フレームワークが代わりにやってくれるわけではない。

公平に付け加えると、フレームワークが自らの中核機能の限界を文書に記し代替案を案内するのは信頼の信号だ。初期プロジェクトがよくやる誇張の代わりに現状を明かした。ただし導入を検討する側はこの一文を額面どおり受け取るべきである。「近く改善されるだろう」という期待をスケジュールに入れてはいけない。

5. サーバーレンダリング回帰 — 同じ問題を解く別の答え

Topcoatが突然現れたアイデアではないことを押さえてこそ公平な評価になる。「データはサーバーにあるのに、なぜロジックをクライアントへ移すのか」という問いは、この数年いくつかの生態系がそれぞれの答えを出してきた。概念的な違いだけを整理する。

  • Phoenix LiveView（Elixir）: 状態をサーバーの持続接続されたプロセスに置き、変更分をソケットで押し出す。操作ごとに往復があるが接続が維持されるので遅延は小さい。代わりにサーバーがユーザー数だけ状態を保持する必要がある。Topcoatのリクエスト単位モデルとは資源使用の性格が異なる。
  • htmx: サーバーがHTML断片を返し、クライアントはどこを置換するかを属性だけで宣言する。フレームワークというより規約に近い。Topcoatのshardが概念的にここに最も近く、実際Topcoatはhtmx統合を別クレートとして提供している。
  • サーバーコンポーネント系: コンポーネントをサーバーで動くものとクライアントで動くものに分け、サーバー側はデータへ直接アクセスする。問題意識はTopcoatのasyncコンポーネントと事実上同じだ。違いはクライアントランタイムを依然として配送するかどうかである。Topcoatはクライアントビルド段階そのものをなくす方を選んだ。
  • 共通の原因: 三つの方向はすべて同じ圧力から生まれた。クライアントへ移したロジックの費用（バンドルサイズ、ハイドレーション、型の二重宣言、ビルドパイプライン）が得るものより大きくなった地点があったという認識だ。

Topcoatの位置を一文で置けば、htmxのサーバー中心モデルをRustの型システムの中へ引き入れ、クライアントビルド段階までなくした試みである。新しい発想というより既存の発想の組み合わせをRust生態系へ持ち込んだものに近く、その組み合わせ自体がこのプロジェクトの寄与だ。

6. この方式が合うアプリと合わないアプリ

技術選定はフレームワークの優劣ではなくアプリの性質で決まる。以下の表は本稿の分析を判断基準として整理したものだ。

軸合う側合わない側

7. RustをWebに使うときの現実的なトレードオフ

フレームワークの話から一段下りる。言語選択そのものの問題だ。Rustをサーバーに使うことと既存スタックからRustへ移る判断はすでに多くの組織が経験した主題だが、Web画面層までRustに上げるのは少し性格が異なる。

7.1 得るもの

  • 型システムが一組: DBの行からHTML属性まで同じコンパイラが検査する。バックエンド型とフロント型を合わせるコード生成パイプラインが丸ごと消える。
  • 実行時エラーの相当数がコンパイルエラーへ移動: フィールド名の打ち間違いやnullable処理の漏れのように、デプロイ後に発見されていたものがビルドで止まる。
  • デプロイ成果物が単純: NodeツールチェーンもWASMバンドルもない構成なら、コンテナイメージとCI段階が目に見えて短くなる。
  • メモリ使用の予測可能性: GC停止のないランタイムはサイドカーの密集配置や低スペックインスタンスで有利だ。

7.2 払うもの

  • フィードバックループ: Web UI開発は秒単位の反復が命なのにRustのビルドはそのリズムとかみ合わない。マクロが重いフレームワークでは特にそうだ。Topcoatの具体的なビルド時間の数値は公式資料で確認できなかったため、本稿では数値を提示しない。導入を検討するなら実プロジェクト規模で自ら測定することが唯一信頼できる方法だ。
  • マクロ層の診断品質: view!、#[page]、$()がすべてマクロだ。Rustの最大の強みの一つがコンパイラの診断メッセージだが、マクロ内で出たエラーは元の位置を正確に指せないことがある。
  • 0.xの表面積: 30を超えるクレートで構成されたワークスペースで破壊的変更が来れば影響範囲が広い。バージョンを上げるたびに画面コード全般に手を入れる必要が生じうる。
  • ツールチェーンの新しさの要求: rust-version 1.95は社内標準ビルドイメージが保守的な組織では実際の障害物になる。

整理すると、RustをWebに使う決定はデプロイ後の安定性を開発中の速度と引き換える取引だ。運用負担が大きくリリース周期が長いシステムではよい取引であり、画面を毎日変える必要があるプロダクト初期には悪い取引になりやすい。

8. チームの力量と採用 — 最も高くつく項目

技術文書がほとんど扱わないが、実際には最大の費用がここで発生する。

  • 人材プールの二重の狭さ: Rust開発者のプールはすでに狭く、その中でWeb画面の仕事をしようとする人はさらに狭い。ここに新興フレームワークの経験まで要求すれば、事実上採用条件ではなく教育計画になる。
  • 学習曲線の主体はフレームワークではなく言語: すでにRustでサーバーを運用しているチームにとってTopcoatの追加学習費用は大きくない。逆にRustを使わないチームにとってこの決定はフレームワーク導入ではなく言語導入だ。二つの決定を一つにまとめて議論すると判断が歪む。
  • バス係数: 社内でRustを読める人が一人二人なら、その人員が離脱した瞬間にサービス全体が読めないコードになる。フレームワークが新しいほど外部から人を連れてきて埋めることも難しい。
  • AI支援の逆説: 発表記事は人間もAIも小さな領域での推論の方が得意だという点を設計根拠に挙げている。方向は妥当だが、新興フレームワークは学習データがほとんどないためコーディングツールの支援効果が広く使われるスタックよりはるかに弱い。設計意図と現実が当面は反対方向へ進む。
  • オンボーディング資料の不在: Stack Overflowの回答、ブログ記事、講座、社内の先例がすべてない状態で始める。問題に詰まったとき頼れるのが公式文書とリポジトリのissueだけという意味だ。

これらの項目はフレームワークの品質と無関係だ。いくらよく作られた道具でも組織が支えられなければ導入は失敗する。新興フレームワークの評価で技術的完成度だけを見るのはよくある誤りであり、別の新興フレームワークを検討した記事でも同じ結論に至った。

9. 導入前に確認すること — ライセンス・成熟度・脱出経路

それでも検討すると決めたなら、以下の六つはコードを書く前に確認する方がよい。

  • 推移的ライセンスの確認: 本体はMITと確認された。ただしワークスペースが多数のクレートに分かれ、それぞれが外部依存を持つ。社内ポリシーが厳しいならcargo denyのようなツールで推移的依存のライセンスを一度ざっと見ておくのが安全だ。
  • 成熟度表記をそのまま受け取る: READMEの「experimental, expect breaking changes」は謙遜表現ではなく仕様だ。0.5.0が発表から5日で出たという事実も同じ方向の信号である。
  • バージョン固定ポリシー: 0.x区間ではマイナーバージョンが破壊的変更を含みうる。Cargo.lockをコミットし、アップグレードは別作業として計画するのが基本だ。
  • ドメインクレート分離: これが事実上唯一の脱出経路だ。ビジネスルールとデータアクセスをTopcoatに依存しない別クレートに置き、コンポーネントはそのクレートの関数だけを呼ぶようにする。ビューはマクロDSLなので移せないが、ドメインが分離されていれば最悪の場合でも画面だけ作り直せばよい。
  • 脱出経路と長所の衝突を認識する: ところがTopcoatが掲げる最大の長所は「コンポーネントがDBを直接照会する」ことだ。これをそのまま従えばドメイン分離が壊れる。長所を最大限享受する方式と脱出費用を下げる方式が正面から衝突する。この緊張を知ったうえで、どちらへ行くかをチームが先に決める必要がある。
  • 外部契約面の確保時期: ロードマップにOpenAPIエンドポイントがある。モバイルやパートナー連携が予定されているなら、この項目が入る時期が導入時期を決める。2026年7月末時点ではまだロードマップだ。

四番目と五番目の項目が本章の核心だ。フレームワークが与える便利さを最大限使うほどそのフレームワークから出にくくなるのはTopcoat固有の性質ではない。ただ「API層をなくす」という設計はその結合度をデータアクセス層まで引き下げるため、結合の深さが一般的なビューフレームワークより深い。

10. いつ使うべきでないか

これまでの分析をひっくり返して整理する。以下のうち一つでも該当するなら、2026年7月末時点では別の選択を勧める。

  • チームにRustを常時保守できる人員が二人未満の場合。一人はバス係数ではなく単一障害点だ。
  • モバイルアプリやパートナーAPIのような二つ目の消費者がすでにあるか12か月以内に予定されている場合。API層をなくして再び作ることになる。
  • 操作密度の高い画面がプロダクトの中核である場合。エディタ、キャンバス、リアルタイム共同編集、オフライン優先アプリがここに属する。
  • SLAがかかっているか外部監査を受けるシステムの場合。0.xの破壊的変更周期を支える余裕がない。
  • Rust導入とフレームワーク導入を同時に決める必要がある場合。二つの大きな変更を一度に行うと失敗原因を分離できない。
  • 締め切りの決まった書き直しプロジェクトの場合。新興フレームワークの未知数と固定された締め切りは一緒に置いてはいけない組み合わせだ。

逆に先に試してみる価値のある場所も確かにある。社内管理ツール、運用ダッシュボード、すでにRustサービスがあるチームの補助画面のように、失敗費用が低くユーザー数が制御される場所だ。こうした場所で一四半期ほど回してみれば、上の項目が自社で実際にどう働くかのデータが積み上がる。そのデータなしに主力サービスへ載せることが危険なのであって、道具自体が危険なのではない。

結論: 境界線を消す決定は元に戻しにくい

Topcoatはよく整理された問題認識の上に立っている。画面一つのためにエンドポイントを作り型を二度宣言しフェッチを包む作業が反復だという指摘は正しい。その反復をサーバーレンダリングとasyncコンポーネントで取り除くアプローチも、この数年いくつかの生態系がそれぞれ到達した方向と一致する。Tokioチームが作った点、MITライセンスである点、そしてREADMEが自ら実験段階だと明かした正直さはすべて肯定的な信号だ。

ただ本稿が確認したのは、そのアプローチが除去ではなく再配置だという事実である。認可はコンポーネントへ散らばり、キャッシュキーは消え、可観測性の地点は名前を失い、shardはエンドポイントを依然として公開している。ボイラープレートが減った分だけ「ここが境界だ」と知らせていた標識も一緒に減った。この取引が利益か損失かはフレームワークではなくアプリの性質とチームの状態が決める。

そしてこの決定は元に戻しにくい。データアクセスがビュー層へ下りたコードベースで後からAPI層を復元しようとすると、画面を作り直すだけでは済まず、ドメインロジックを散らばった場所から集め直す必要がある。だから導入を検討するなら最初の画面を書く前にドメインクレートを先に切り出す方がよい。フレームワークが与える最大の便利さの一部を諦める選択だが、0.x段階の道具を扱うときに払う合理的な保険料だ。

整理するとこうだ。2026年7月末時点のTopcoatは見守る価値があり、低リスクの場所で試す価値があり、主力サービスへ載せるには早い。次の四半期の判断材料は二つだ。クライアントリアクティビティシステムの制約がどこまで解消されるか、そしてOpenAPIエンドポイントのように外部契約面を再び開くロードマップ項目が実際に入るかである。
