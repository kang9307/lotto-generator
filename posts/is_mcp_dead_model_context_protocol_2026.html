도발적 제목 뒤의 균형 잡힌 진실 - 열풍 1년 후, 약속은 지켜졌나

2026-06-01 IT/기술

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

1. 서론: MCP 열풍 1년 후 - 약속은 지켜졌나

2026년 5월 31일 news.hada.io 인기 글에 "Is MCP Dead?"라는 도발적인 토픽이 올라왔다. Model Context Protocol, 줄여서 MCP는 2024년 말 Anthropic이 공개한 뒤 2025년 한 해를 "AI 에이전트의 USB-C"라는 별명과 함께 통째로 달궜던 표준이다. 그런 MCP를 두고 "죽었느냐"고 묻는 글이 인기 글에 오른 것 자체가, 1년 사이 기대와 현실 사이의 간극이 사람들 입에 오르내릴 만큼 벌어졌다는 신호다.

본인은 솔직하게 밝히고 시작한다. BrainDetox에서 그동안 에이전트 인프라를 다룰 때 MCP를 여러 번 우호적으로 언급해 왔다. 그래서 이번 글은 더더욱 객관적으로 쓰려 한다. "죽었다"는 제목은 자극적이지만, 본인 결론을 먼저 말하면 MCP는 죽지 않았다. 다만 만능이라는 환상이 죽었을 뿐이다. 이 글은 그 환상이 어디서 깨졌고, 그럼에도 MCP가 어디서 여전히 빛나는지를 균형 있게 분해한다.

이 글은 hada.io 토픽을 출발점으로 삼되, 그 요약을 옮기지 않는다. 본인이 실제로 MCP 서버를 세우고 클라이언트에 붙여 써 보면서 겪은 다섯 가지 한계, function calling 및 직접 통합과의 비교, MCP가 적합한 영역과 부적합한 영역, 대안, 그리고 한국 개발 환경에서의 현실까지 13개 챕터로 정리한다. 결론부터 말하면, MCP를 쓸지 말지는 "유행이라서"가 아니라 "내 통합 구조에 맞느냐"로 판단해야 한다.

2. MCP란 무엇이었나 - Anthropic의 Model Context Protocol 개요

MCP는 AI 모델(정확히는 모델을 감싼 클라이언트)이 외부 도구·데이터 소스·시스템과 연결되는 방식을 표준화하기 위한 개방형 프로토콜이다. 핵심 아이디어는 단순하다. 모델마다, 애플리케이션마다 제각각이던 도구 연결 방식을 하나의 공통 규약으로 통일하자는 것이다. 그래서 흔히 "AI 시대의 USB-C"라고 비유된다. 어떤 기기든 같은 포트로 꽂히듯, 어떤 모델이든 같은 프로토콜로 도구에 꽂히게 하자는 그림이다.

구조는 클라이언트-서버 모델이다. MCP 호스트(Claude Desktop, Cursor, VS Code 등)가 내부에 MCP 클라이언트를 두고, 이 클라이언트가 외부의 MCP 서버와 통신한다. 서버는 세 가지를 노출한다. 모델이 호출할 수 있는 tools(함수), 읽어 들일 수 있는 resources(파일·DB 레코드 등 컨텍스트), 그리고 재사용 가능한 prompts(프롬프트 템플릿)다. 통신은 로컬에서는 표준입출력(stdio), 원격에서는 HTTP/SSE 기반 전송을 쓴다.

비유하면 MCP 서버는 도구의 "어댑터"다. 깃허브, 슬랙, 로컬 파일시스템, 데이터베이스마다 어댑터를 한 번 만들어 두면, 그 어댑터를 지원하는 어떤 클라이언트에서든 같은 도구를 쓸 수 있다. 이 "한 번 만들면 어디서나"라는 약속이 2025년 MCP 열풍의 핵심 동력이었다.

3. MCP가 약속한 것 - 표준화된 도구·컨텍스트 연결

MCP가 등장했을 때 본인이 가장 매력적으로 본 약속은 세 가지였다.

  • N×M 문제의 해소 - 모델 N개와 도구 M개를 각각 따로 연결하면 N×M개의 통합이 필요하다. MCP는 그 사이에 표준 한 층을 끼워 N+M으로 줄이겠다고 약속했다. 도구 제공자는 MCP 서버 하나만, 모델 제공자는 MCP 클라이언트 하나만 만들면 된다.
  • 재사용 가능한 도구 생태계 - 누군가 만든 깃허브 MCP 서버를 내 Cursor에도, 동료의 Claude Desktop에도 그대로 꽂을 수 있다. 도구가 앱에 종속되지 않고 생태계 자산이 된다.
  • 컨텍스트 공급의 표준화 - 단순히 함수 호출만이 아니라, 모델에 필요한 컨텍스트(파일, DB, 문서)를 일관된 방식으로 주입하는 길을 열었다. 에이전트가 "무엇을 할 수 있는가"와 "무엇을 아는가"를 같은 규약으로 다룬다.

이 약속들은 지금 봐도 옳은 방향이다. 문제는 약속의 방향이 옳다는 것과, 그 약속이 모든 상황에서 비용 대비 이득을 낸다는 것은 전혀 다른 이야기라는 점이다. 여기서부터 현실의 한계가 시작된다.

4. MCP의 5가지 실제 한계

본인이 직접 MCP 서버를 세우고 운영하며 부딪힌 다섯 가지 한계를 정리한다. 이건 누군가의 요약이 아니라 실측 경험이다.

4-1) 복잡한 설정 - 진입 장벽

가장 먼저 부딪히는 벽이다. 도구 하나를 쓰기 위해 별도 서버 프로세스를 띄우고, 실행 명령·환경 변수·인증 토큰을 클라이언트 설정 파일(JSON)에 정확히 적어야 한다. function calling이라면 코드 몇 줄로 끝날 일이, MCP에서는 서버 설치·경로 설정·런타임 의존성 확인이라는 여러 단계를 거친다. 비개발자에게는 사실상 진입이 불가능하고, 개발자에게도 "이 도구 하나 쓰자고 이걸?" 싶은 순간이 온다.

4-2) 보안 - 노출면의 확대

MCP는 모델에 외부 도구를 실행할 권한을 준다. 이건 강력한 만큼 위험하다. 서버가 로컬 파일시스템·DB·내부 API에 접근하면, 모델이 프롬프트 인젝션에 휘둘릴 경우 그 권한이 그대로 공격 표면이 된다. 신뢰할 수 없는 출처의 MCP 서버를 설치하는 것은 사실상 제3자 코드를 내 권한으로 실행시키는 일이다. 자격 증명이 서버 설정에 평문으로 들어가는 패턴도 흔해 위험을 키운다.

4-3) 디버깅 - 추적의 어려움

호출 흐름이 호스트 → 클라이언트 → 서버 → 외부 시스템으로 여러 프로세스에 걸쳐 있다 보니, 무언가 잘못됐을 때 어디서 끊겼는지 추적하기가 어렵다. 모델이 도구를 안 부르는 건지, 클라이언트가 서버를 못 띄운 건지, 서버가 에러를 냈는데 메시지가 모델에 안 전달된 건지 구분이 쉽지 않다. 표준화된 관찰성·로깅이 아직 약해 stdio 로그를 뒤지는 원시적 디버깅에 의존하기 일쑤다.

4-4) 표준 분열 - 구현체 간 불일치

"표준"이라지만 클라이언트마다 지원 범위가 다르다. 어떤 클라이언트는 resources를 지원하고 어떤 클라이언트는 tools만 지원한다. 전송 방식(stdio vs HTTP/SSE), 인증, 권한 모델의 세부가 구현체마다 갈린다. 그래서 "한 번 만들면 어디서나"가 현실에서는 "만들고 나서 클라이언트마다 따로 테스트해야"로 변질된다. 표준의 가치는 일관성에서 나오는데, 분열은 그 가치를 직접 갉아먹는다.

4-5) 성능 오버헤드

MCP는 별도 프로세스·프로토콜 왕복을 거치므로, 같은 함수를 모델 안에서 직접 호출하는 것보다 지연이 늘어난다. 도구 목록을 가져오고, 직렬화하고, 프로세스 간 통신을 하고, 결과를 다시 직렬화해 돌려받는 단계가 매 호출마다 쌓인다. 단발성 작업에서는 체감이 작지만, 에이전트가 도구를 수십 번 호출하는 긴 루프에서는 누적 오버헤드가 무시할 수 없다.

다섯 한계의 공통점은 "한 층을 추가한 대가"다. 표준이라는 추상화 층을 끼워 넣는 순간 설정·보안·디버깅·호환·성능 비용이 함께 따라온다. 이건 MCP의 결함이라기보다 모든 미들웨어가 안고 가는 본질적 트레이드오프다.

5. "죽었다"는 과장인가 - 실제 채택 현황

그렇다면 정말 죽었는가. 본인의 답은 명확히 "아니다"이다. 한계가 분명함에도 MCP의 채택 곡선은 여전히 우상향이다. 주요 코딩 에이전트와 IDE(Claude Desktop, Cursor, VS Code, 그 외 다수)가 MCP를 1차 통합 방식으로 지원하고, 공개된 MCP 서버 수는 1년 사이 빠르게 늘었다. 도구 제공 회사들이 "공식 MCP 서버"를 내놓는 것이 하나의 관행처럼 자리 잡았다.

"죽었다"는 표현은 두 가지를 혼동한 데서 온다. 첫째는 하이프 사이클의 정상화다. 가트너의 하이프 사이클로 보면 MCP는 2025년 "부풀려진 기대의 정점"을 지나 2026년 "환멸의 골짜기"로 내려오는 중이다. 이 구간에서는 "역시 별거 아니었다"는 목소리가 커진다. 하지만 환멸의 골짜기는 죽음이 아니라 성숙으로 가는 통과 의례다. 둘째는 적용 범위의 오해다. MCP가 모든 통합을 대체할 것이라는 기대가 과했을 뿐, 적합한 영역에서의 채택은 멀쩡히 늘고 있다.

본인이 보기에 죽은 것은 MCP가 아니라 "MCP 하나로 에이전트 통합의 모든 문제가 사라진다"는 서사다. 기술은 살아 있고, 죽은 건 과장된 기대다. 이 구분을 못 하면 멀쩡히 쓸 만한 도구를 유행이 식었다는 이유로 내다 버리는 실수를 하게 된다.

6. MCP vs Function Calling vs 직접 통합 비교

MCP를 평가하려면 대안과 나란히 놓고 봐야 한다. 세 가지 접근을 비교한다.

기준Function CallingMCP직접 통합(OpenAPI 등)
설정 난이도낮음높음중간
재사용성앱 종속높음(여러 클라이언트)중간
도구 생태계없음공유 서버 생태계API별 개별
보안 노출면작음큼(별도 권한)중간
성능(지연)가장 빠름오버헤드 있음중간
적합 규모단일 앱다중 클라이언트기존 REST 자산

표를 한 문장으로 요약하면, function calling은 단일 앱에 가장 간단하고, MCP는 도구를 여러 클라이언트가 공유할 때 빛나며, 직접 통합은 이미 잘 정의된 REST API 자산이 있을 때 합리적이다. 셋은 경쟁자라기보다 서로 다른 층위에 있다. function calling이 모델과 도구를 잇는 "신경"이라면, MCP는 그 신경을 여러 몸에 재사용하게 하는 "표준 커넥터"다.

흔한 오해 하나를 짚는다. MCP는 function calling을 대체하지 않는다. 오히려 MCP 서버의 도구를 모델이 호출할 때 내부적으로는 function calling 메커니즘을 쓴다. 둘은 적이 아니라 층위가 다른 협력자다.

7. MCP가 빛나는 영역 vs 부적합 영역

본인이 정리한, MCP를 써야 할 때와 쓰지 말아야 할 때다.

7-1) MCP가 빛나는 영역

  • IDE·데스크톱 에이전트의 로컬 도구 연결 - Cursor에서 로컬 DB를 조회하거나 파일시스템을 다루는 등, 같은 도구를 여러 클라이언트에서 재사용할 때 가장 강하다.
  • 도구 제공자와 모델 제공자의 분리 - 우리는 도구만 잘 만들고, 어떤 모델이 쓸지는 사용자에게 맡기고 싶을 때. SaaS가 "공식 MCP 서버"를 내놓는 패턴이 여기에 해당한다.
  • 여러 에이전트가 공유하는 도구 풀 - 조직 내 표준 도구 세트를 한 번 만들어 팀 전체 에이전트가 쓰게 할 때.

7-2) MCP가 부적합한 영역

  • 단일 백엔드 안의 단순 도구 호출 - 한 앱에서 모델이 함수 두세 개만 부르면 되는 경우, MCP의 설정·운영 비용은 명백한 과잉이다. function calling이 정답이다.
  • 초저지연이 핵심인 작업 - 매 밀리초가 중요한 실시간 경로에서는 프로토콜 왕복 오버헤드가 부담이다.
  • 보안 경계가 극도로 민감한 환경 - 외부 MCP 서버의 권한 확대가 허용되지 않는 폐쇄망에서는 도입 문턱이 매우 높다.

핵심 판단 기준은 하나다. "이 도구를 여러 클라이언트가 공유하는가?" 답이 예면 MCP, 아니면 function calling이다.

8. 대안과 보완 - 차세대 에이전트 통합 표준

MCP만 있는 건 아니다. 본인이 보는 대안과 보완 지형은 이렇다.

  • 네이티브 function calling / 도구 API - 각 모델 제공자가 제공하는 가장 기본적이고 빠른 통합. 단일 앱에는 여전히 최선이다.
  • OpenAPI 기반 직접 통합 - REST API가 이미 잘 정의됐다면 모델에 명세를 주고 직접 호출하게 하는 방식이 단순하다.
  • 프레임워크 도구 추상화 - LangChain·LlamaIndex 등은 자체 도구 추상화를 제공하며 MCP를 어댑터로 흡수하기도 한다.
  • 에이전트 간 통신(A2A류) 프로토콜 - MCP가 "에이전트↔도구"를 다룬다면, A2A류는 "에이전트↔에이전트"를 노린다. 둘은 경쟁이 아니라 다른 층을 메운다.

중요한 통찰은 이것이다. 이 대안들은 대체로 MCP를 죽이는 것이 아니라 보완한다. 2026년 현실적 그림은 단일 승자가 아니라 다층 구조다. 앱 안에서는 function calling, 도구 공유 층에서는 MCP, 에이전트 협업 층에서는 A2A류가 각자의 자리를 차지하는 식이다.

9. 개발자가 지금 MCP를 써야 하나 - 솔직한 판단

가장 많이 받는 질문에 솔직히 답한다. "지금 MCP를 배우고 도입해야 하나?"

본인의 답은 "용도가 맞으면 지금이 좋은 시점"이다. 이유는 세 가지다. 첫째, 주요 클라이언트 지원이 안정화돼 초기보다 설정이 한결 수월해졌다. 둘째, 공개 서버 생태계가 커져 처음부터 만들 필요 없이 가져다 쓸 수 있는 도구가 많아졌다. 셋째, 환멸의 골짜기 구간이라 과장된 기대가 걷히고 실제 쓸모 중심으로 자료가 정리됐다.

다만 도입 방식은 신중해야 한다. 본인 권고는 단계적 접근이다. 가장 가치가 큰 도구 한두 개만 먼저 MCP로 감싸 효과를 측정하라. 설정 비용 대비 재사용 이득이 실제로 났는지 데이터로 확인한 뒤에 확장한다. 처음부터 모든 도구를 MCP로 표준화하겠다는 빅뱅 접근은 4장의 다섯 한계를 한꺼번에 떠안는 길이다.

10. 한국 개발 환경에서의 MCP 현실

한국 개발 조직에 MCP를 적용할 때 고려할 세 가지가 있다.

첫째 폐쇄망과 보안 심사다. 금융·공공·통신은 외부 출처 코드 반입과 외부 권한 확대에 대한 심사가 엄격하다. 외부 MCP 서버 설치는 보안 검토에서 막히기 쉽고, 자체 검증한 사내 MCP 서버만 허용하는 형태로 좁아진다. 본인은 한국 폐쇄망에서는 "신뢰된 사내 서버만, 권한 최소화"를 기본 원칙으로 권한다.

둘째 온프레미스·국산 LLM과의 결합이다. HyperCLOVA X, KT 믿:음 같은 온프레미스 모델을 쓰는 환경에서는 MCP 클라이언트 지원 여부가 변수다. 글로벌 클라이언트가 먼저 지원하는 만큼, 국산 스택에서는 MCP 채택이 한 박자 늦게 따라오는 경향이 있다. 도입 전 클라이언트 호환을 반드시 확인해야 한다.

셋째 소규모 팀 비중이다. 1~5인 개발팀이 많은 한국 스타트업·SI 현장에서는 MCP 서버를 세우고 유지할 여력이 부족하다. 이런 팀은 단일 앱이면 function calling으로 충분하고, 정말 도구를 여러 곳에서 공유해야 하는 순간에만 MCP로 넘어가는 것이 비용 대비 합리적이다.

11. 위험 - 표준 전쟁의 불확실성

MCP를 둘러싼 가장 큰 불확실성은 기술적 한계가 아니라 표준 거버넌스다. 본인이 우려하는 세 가지를 정리한다.

  • 주도권 집중 위험 - MCP는 개방형이지만 사실상 Anthropic이 주도한다. 특정 회사가 주도하는 표준은 그 회사의 전략에 따라 방향이 흔들릴 수 있다. 진정한 중립 거버넌스로 넘어가느냐가 장기 생존의 관건이다.
  • 경쟁 표준의 등장 - 다른 진영에서 대안 프로토콜을 밀면 "표준 전쟁"이 벌어진다. 도구 제공자는 여러 표준을 동시에 지원해야 하는 부담을 떠안고, 표준화의 본래 이득이 희석된다.
  • 버전 파편화 - 4장에서 본 구현체 분열이 버전 차이로 악화되면, "표준인데 호환이 안 되는" 최악의 상황이 올 수 있다.

이 위험들은 MCP만의 문제가 아니라 모든 신생 표준이 통과해야 하는 관문이다. 본인은 도입 시 특정 표준에 코드를 깊게 종속시키기보다, 도구 로직과 프로토콜 어댑터 층을 분리해 두라고 권한다. 표준이 바뀌어도 어댑터만 갈아 끼우면 되도록.

12. 결론 + 즉시 적용 가능한 3가지

본문의 핵심을 한 문장으로 정리한다. MCP는 죽지 않았다. 죽은 것은 MCP 하나로 모든 에이전트 통합이 해결된다는 환상이며, MCP는 도구를 여러 클라이언트가 공유하는 영역에서 여전히 실질적 표준으로 살아 있다. 그 위에서 지금 바로 적용할 수 있는 세 가지를 제시한다.

  1. "여러 클라이언트가 공유하는가"로 판단하라. 도구가 한 앱에만 쓰이면 function calling, 여러 에이전트·클라이언트가 공유하면 MCP. 유행이 아니라 이 한 질문으로 결정한다.
  2. 가장 가치 큰 도구 한두 개로 파일럿하라. 전면 표준화 대신, 재사용 이득이 가장 큰 도구만 먼저 MCP로 감싸 설정 비용 대비 효과를 측정하고 확장한다.
  3. 도구 로직과 프로토콜 어댑터를 분리하라. 표준 전쟁의 불확실성에 대비해, MCP에 깊게 종속되지 말고 어댑터 층만 갈아 끼울 수 있게 설계한다.
