Intro: The Pain of Hand-Editing ~/.ssh/config

The moment the number of servers you manage climbs past five, your ~/.ssh/config file quietly starts to weigh you down. Remembering a couple of IP addresses is easy, but once cloud instances, internal servers and bastion hosts begin to pile up, the picture changes. You end up memorizing long commands like ssh user@10.x.x.x -p 2222 -i ~/.ssh/some_key, or you open the config in an editor, hunt for the alias, and copy it back into the terminal - over and over. The real cost of this is not the typing. It is the break in flow. You are deep in a task, you cannot recall a server alias, so you open the config, scroll, find it, and come back to the terminal. Those few seconds, repeated dozens of times a day, add up to a friction that is anything but trivial.

On May 29, 2026, "Show GN: sshc, a Rust-based TUI SSH host manager" reached number nine on GeekNews (news.hada.io), and it targets exactly this friction. The repository is github.com/hang-in/sshc and the license is MIT. This article goes beyond an introduction and lays out what sshc does differently from existing approaches, how its install paths and config files actually behave, and how you can apply it in real engineering environments. To state the conclusion up front: sshc is not a tool everyone needs, but for the developer whose config has grown unwieldy it delivers clear value.

Commands, paths and key bindings are aligned with the repository README and CHANGELOG as of 2026-09-29 (latest release v0.13.1). The structure of this guide is: (1) an overview of sshc, (2) five core features, (3) why Rust and a TUI, (4) a comparison table of existing SSH management approaches, (5) an install and getting-started guide, (6) its relationship to ~/.ssh/config, (7) five real-world scenarios, (8) how it complements the BrainDetox SSH Config Generator, (9) applicability to engineering environments, (10) risks and limits, (11) a conclusion with three immediately actionable steps, followed by the update history and references.

1. What sshc Is - A Rust TUI SSH Manager

The README's one-line pitch is "Manage and connect to your SSH hosts from a fast Rust TUI." Spelled out, it is a single-binary TUI tool that reads ~/.ssh/config and the files it Includes, and lets you pick and connect to a host from a picker that opens right under your shell prompt. Three ideas carry the weight here: TUI, single binary, and respect for your existing config.

TUI stands for text-based user interface - an interface that lives inside the terminal's character grid rather than in a graphical window. You navigate, search and select with the keyboard, no mouse required. sshc's default mode is an inline picker that does not take over the whole screen, so after you pick, connect and return to the shell, your scrollback is still there. Only when you need to add, edit or delete do you open the full-screen manage mode with sshc -m.

The single-binary nature is decisive operationally. The README says "Single-binary, no daemon" and lists recent release artifacts at about 810 KB for macOS arm64, about 1.16 MB for Linux x64 and about 1.10 MB for Windows x64. No interpreter or packages to install - one executable in a directory on your PATH is enough.

Finally, sshc never edits your hand-written ~/.ssh/config beyond a single optional Include line. Hosts you add in manage mode are written only to a separate file, ~/.ssh/config.d/sshc.conf. Section 6 covers the details. As a side note, the project was called sshs in its first releases (v0.1.0 to v0.4.0) and was renamed to sshc in v0.4.1 because the name collided with an unrelated CLI.

2. Five Core Features

Here are the features the README describes, grouped into five.

2-1) An inline picker under your shell prompt

Type sshc and the host list appears below your prompt. Hosts you pinned as favorites in manage mode (f) and recently connected hosts float to the top, so for your usual servers the whole interaction is "open sshc, press Enter." Navigate with ↑/↓ or j/k.

2-2) Connect with Enter, or straight in with sshc <alias>

Press Enter in the picker and the ssh connection starts; when the session ends you are back in your shell. If you already know the alias, sshc <alias> skips the picker. According to the CHANGELOG, this direct mode looks the alias up in your config and runs ssh <alias> as-is; an unknown alias exits with code 1 without invoking ssh. That makes it a good fit for shell aliases and scripts.

2-3) / search and @tag filtering

The inline picker is modal. It starts in navigation mode, and you press / to enter search mode and type to narrow the list. Pressing Esc in search mode leaves search while keeping the picker open. In manage mode's filter, @tag (for example @prod) filters by tag only.

2-4) Add, edit and delete in manage mode (sshc -m)

Manage mode is a full-screen TUI. a adds a host, d deletes (with confirmation), t edits tags, e opens $EDITOR at the host's line, v shows the resolved ssh -G <alias> output, c copies the connect command, g probes TCP reachability for the selected host, r re-probes every host, and ? opens help. The edit form holds lists of LocalForward, RemoteForward and DynamicForward entries and multiple IdentityFile entries (added in v0.9 to v0.12).

2-5) Grouping with tags and favorites

Groups are not a separate database - they are comments placed right above a Host block, like # @tags: prod, db. Because tags live inside the config file, they travel with it. Add favorite pinning and the sort toggle (S: alias → recent → reachability) and navigation stays quick even on long lists.

3. Why Rust + TUI - Speed, Single Binary, Cross-Platform

sshc being written in Rust and choosing a TUI form is a choice that fits the tool's purpose well.

3-1) Startup speed

An SSH management tool gets opened and closed dozens of times a day. If startup is slow, that itself is friction. A natively compiled binary needs no runtime warm-up, in contrast to a heavy GUI app that takes several seconds. sshc uses ratatui and crossterm for the interface and nucleo for list matching (Cargo.toml).

3-2) Single-binary distribution

There is no daemon and the whole thing is one executable, so there is no need to match interpreter versions per server. When you install the same tool across many environments, operational cost drops considerably. The same property helps when bringing the tool into an air-gapped network (section 9).

3-3) Cross-platform

Besides macOS and Linux, native Windows builds ship from v0.7.0. Windows has x64 and ARM64 (from v0.8) zips and needs Windows 10 1809 or later, or Windows 11, plus the OpenSSH client. Inside WSL2 the Linux build works as-is. Note that on Windows sshc skips the file-permission (0600/0700) checks.

3-4) Memory safety and stability

An SSH manager is an infrastructure-grade tool you install once and use for a long time. Rust catches a large class of memory-safety bugs at compile time, which makes it a sound foundation for a long-lived tool. If that angle interests you, this site's Go to Rust Migration Guide 2026 is worth a read too.

5. Install and Getting-Started Guide

Caution - cargo install sshc does not install this tool. The sshc name on crates.io belongs to a different project published in 2017 (netvl/sshc 1.0.0, an SSH connections and tunnels manager), as of 2026-09-29. Install the sshc covered here through the paths below.

The README lists four install paths.

# 1) Homebrew (macOS and Linux) - brew upgrade sshc follows new releases
brew install hang-in/tap/sshc

# 2) cargo from a git tag (Rust 1.85 or later)
cargo install --git https://github.com/hang-in/sshc --tag v0.13.1

# 3) Build from source
git clone https://github.com/hang-in/sshc
cd sshc
cargo install --path .

# Verify the install and run it
sshc --version
sshc --doctor
sshc
# 4) Windows (PowerShell) - installs into %CARGO_HOME%\bin and updates PATH
irm https://github.com/hang-in/sshc/releases/latest/download/sshc-installer.ps1 | iex

On Windows you can also download sshc-x86_64-pc-windows-msvc.zip or sshc-aarch64-pc-windows-msvc.zip from the releases page and place it in a directory on your PATH. --version (-V) and --help (-h) exist since v0.4.2.

Tip - run sshc --doctor once before your first real session. It is a read-only report on ~/.ssh, sshc.conf, the Include line, the ssh binary, agent connectivity and new-release availability, and it exits non-zero only on FAIL. If the list looks empty, start with the config path and permissions (600 on Unix).

Key bindings and options have grown release by release, so it is safest to read sshc --help for your installed version alongside the repository README.

6. Its Relationship to ~/.ssh/config - Reads, and Isolated Writes

This compatibility is the most essential part of sshc's design. sshc builds its list by reading your existing ~/.ssh/config and the files it Includes. An ordinary config like the one below simply becomes the list, and # @tags: comments above a Host are read as tags.

# @tags: prod, web
Host prod-web
    HostName 10.0.1.10
    User deploy
    Port 22
    IdentityFile ~/.ssh/prod_key

Host bastion
    HostName bastion.example.com
    User jump
    Port 2222

# @tags: prod, db
Host prod-db
    HostName 10.0.2.20
    User dbadmin
    ProxyJump bastion

Writes are isolated. The behavior the README documents is:

  • Hosts added with sshc -m are written only to ~/.ssh/config.d/sshc.conf (mode 0600). The file starts with a comment warning that manual edits inside Host blocks may be overwritten on the next save.
  • The first run of manage mode asks whether to append Include ~/.ssh/config.d/sshc.conf to ~/.ssh/config, and makes a dated .bak.sshc-YYYYMMDD backup first. If you decline, manage mode goes read-only while browsing and connecting still work.
  • State such as the Include decision, the last-connected alias and the sort axis is stored in ~/.config/sshc/state.toml.

Thanks to this design, the exit cost is small. Remove sshc and your hand-written config is untouched; sshc.conf is itself a standard OpenSSH-syntax file, so commands like ssh prod-db keep working. If you stop using sshc, clean up the Include line, sshc.conf and state.toml.

Taking one more backup with cp ~/.ssh/config ~/.ssh/config.bak before adoption also protects any carefully curated comment structure.

7. Five Real-World Scenarios

Here are the five situations where sshc shines most.

7-1) Operating many servers

For SRE and infrastructure engineers hopping across dozens of servers, search-based fast connect is productivity itself. Pressing /, typing part of a hostname to narrow the list and pressing Enter removes friction that otherwise accumulates all day.

7-2) Bastion and jump-host environments

In setups that reach an internal network through a bastion via ProxyJump, defining ProxyJump once in config means picking an internal server from the sshc list performs the multi-hop connection. sshc runs ssh with the alias, so OpenSSH handles ProxyJump. Press v to see the ssh -G output and check the values actually applied.

7-3) Managing cloud instances

AWS, GCP and other cloud instances are created and destroyed often, so their IPs change. Combined with a workflow that refreshes config, sshc becomes a window onto the current instance list. Probing TCP reachability with g (selected host) or r (all hosts) quickly exposes instances that are gone.

7-4) Sharing config across a team

Because it is a standard config file, it is easy to share via a Git repository or team docs, and tags travel inside the file as comments. A teammate who receives the same config (or fragments split out with Include) sees the same list in sshc. Be clear, though, that credentials (key files) are not what gets shared.

7-5) DevOps and CI checks

When you need to inspect several nodes right after a deploy, defining per-node aliases in config makes cycling through nodes with sshc to check logs smooth. In scripts, use the direct mode, sshc <alias>.

8. How It Complements the BrainDetox SSH Config Generator

The web-based SSH Config Generator from BrainDetox pairs well with sshc. If sshc is the tool that consumes an existing config (reads it and connects), the SSH Config Generator is the tool that produces that config in the first place. The two are not competitors but complements covering the front and back of the same workflow.

The combination goes like this. When setting up a new server environment, use the SSH Config Generator to fill in HostName, User, Port, IdentityFile and ProxyJump through a form, generate a standard config block, and paste its output into ~/.ssh/config. From then on, handle daily connections with sshc. In other words: generate with the web tool, consume with the TUI. For adding just a few hosts you can also use a in sshc -m, in which case the entries go into sshc.conf.

9. Applicability in Real Engineering Environments

Here is how sshc fits into real engineering setups.

9-1) Internal networks and the bastion pattern

Many companies, for security reasons, forbid direct access to internal servers and route everything through a bastion (jump server). In this environment ProxyJump-based config and sshc fit together well. Define the bastion once and subsequent multi-hop connections happen by selecting the internal server, which also cuts the cost of explaining "how do I connect" during onboarding.

9-2) Multi-cloud (a mix of providers and on-prem)

Environments mixing multiple cloud providers and on-prem servers are common. If you split config by environment with Include and adopt a naming convention (prefixes like aws-, gcp-, onprem-) or tags like # @tags: aws, search or an @aws filter narrows to a specific cloud's server group immediately.

9-3) Practical adoption considerations

The practical constraint is installation on air-gapped networks. With no internet, both Homebrew and cargo install --git are blocked, so you need a path to bring in a prebuilt binary from the releases page. Only one file has to clear the import process, which is an advantage. Also, sshc --doctor makes a network call to check for new releases, so on an air-gapped network set SSHC_NO_UPDATE_CHECK=1 to skip it.

10. Risks and Limits

These are the limits to know before adopting sshc.

10-1) The one Include line and sshc.conf overwrites

The only thing sshc does to your hand-written config is add one Include line, but where that line lands matters. A bug fixed in v0.8.4: if your config ended with a Host block, the appended Include became part of that last Host block, and sshc-managed hosts went invisible to ssh <alias> (OpenSSH does not end a Host block at a blank line or comment). From v0.9, --doctor checks for such nested Includes and for CRLF in the config. Also, manual edits inside Host blocks of sshc.conf may be overwritten on the next save, and promoting an external host into sshc.conf with M leaves the original entry in place, so delete it yourself if you do not want duplicates.

10-2) The absence of GUI features

SFTP file browsing, session recording and mobile access are not in the README's feature list. If those features are central, sshc is not the fit - a tool like Termius is. sshc is a deliberately reduced tool.

10-3) Credentials are still managed separately

sshc only handles the host list; it does not store key files or passwords. It uses whatever agent your environment provides (SSH_AUTH_SOCK on Unix, the Windows OpenSSH agent or Pageant on Windows). Security hygiene like key permissions and key rotation remains the user's responsibility.

10-4) Ecosystem maturity and maintenance status

sshc is a young tool: it started at v0.1.0 on May 19, 2026 and shipped 24 GitHub releases (v0.2.0 to v0.13.1) in about five weeks up to v0.13.1 on June 26. As of 2026-09-29 both the latest release and the latest commit date from 2026-06-26, the CHANGELOG's Unreleased section is empty, and the repository is not archived. Key bindings and behavior have changed across versions, so before wiring it deeply into a work workflow, read the README and CHANGELOG and judge by whether the core behavior - calling standard ssh - is preserved.

11. Conclusion + Three Immediately Actionable Steps

Summarized in one sentence, sshc is this: a tool that leaves your hand-written ~/.ssh/config untouched, lays a thin layer of fast search and instant connect on top of it, and isolates new entries in a separate file. Not everyone needs it, but for the person whose config has grown unwieldy it noticeably reduces friction. Here are three things you can apply right away.

11-1) Step 1: Back up the config and just run it once

Back up first with cp ~/.ssh/config ~/.ssh/config.bak, install with Homebrew or cargo install --git, then run sshc --doctor followed by sshc. Just seeing your existing hosts appear in the list is enough to gauge the tool's value.

11-2) Step 2: Group with naming conventions and tags

Give host aliases environment and cloud prefixes (prod-, dev-, aws-, gcp-) and add # @tags: comments above Host blocks, and search plus the @tag filter become a group filter. One small convention dramatically lowers the navigation cost of dozens of hosts.

11-3) Step 3: Divide labor - generate with the web tool, consume with sshc

Create new config blocks with the BrainDetox SSH Config Generator via a form and paste them in, while handling daily connections with sshc. Separating generation from consumption makes config management much simpler.

The closing message is this. Good tools do not replace standards - they lay thinly on top of them. sshc is appealing not for flashy features but because it respects the proven standard that is OpenSSH while removing exactly the friction of the most frequent task.
