背景 — グラフ・ベクトル・全文検索を1ファイルに収める組み込みデータベース

ローカル知識ツールやGraph RAGパイプライン、AIエージェントの永続メモリを設計する開発環境において、ストレージの断片化は常に厄介な課題でした。コンテキスト間の意味的類似度を判定するためのベクトルデータベース、エンティティ間の多段関係をたどるためのグラフデータベース、特定のキーワードや識別子を抽出するための全文検索（FTS）エンジンの3系統をそれぞれ別個に立ち上げる必要があったためです。ローカル環境で1つの試作アプリを作るだけでも、3つのバックエンドデーモンを管理するか、別々のストレージライブラリを束ねてアプリケーション層で擬似分散トランザクションを組む必要がありました。

2026年9月にオープンソースとして公開されたLatticeDBは、この断片化を根本から解消することを目的とした組み込み型データベースです。公式ドキュメントによると、LatticeDBは単一のローカルファイルの中にリレーションデータ、意味的ベクトルデータ、テキストインデックスをすべて格納し、単一のクエリ層を通じて横断的に照会できるように設計されています。外部サーバーや設定ファイルなしでアプリに組み込んで動作し、ファイル単位でバックアップや移動が完結するローカルファースト（local-first）な運用を前提としています。

複数モデルを統合するデータベースは分散クラウドの領域でも開発されていますが、LatticeDBはSQLiteのような「単一ファイル・組み込み型」を採用した点に強い独自性があります。組み込み環境はプロセス間通信（IPC）やネットワーク通信による遅延を物理的にゼロにできる反面、オペレーティングシステムのファイルロック機構やプロセス単位のメモリ制約という明確な境界を持ちます。本稿では、LatticeDBが採用した複合エンジンの設計、Cypherクエリの拡張方式、公式ベンチマークの前提条件、そしてシングルライターモデルが持つトレードオフについて整理します。

エンジニアリングの観点から見て、ローカル単一ファイルデータベースの最大の価値は運用の単純さにあります。クラウド上のマネージドデータベースやマイクロサービス構成のストレージ群は、継続的な運用保守と安定したネットワーク環境を前提とします。一方、単一ファイル構成であれば、ファイルシステム上の任意のパスにファイルを作成するだけで初期化が完了します。バックアップはファイルのコピー操作そのものであり、テスト環境の立ち上げも一時ディレクトリに空ファイルを割り当てるだけで済みます。LatticeDBはこのSQLite的な簡潔さを、現代的なRAGの要件であるグラフとベクトル、テキスト検索に適用しようとしています。

分離されたストレージ構造がもたらす断片化と同期コスト

AIワークロードにおいて複数の検索エンジンを分けて運用する場合、構造的な問題はデータ整合性とトランザクション境界の欠落から生じます。一般的なローカルRAG構成では、以下のような同期オーバーヘッドが日常的に発生します。

  • 文書チャンクの埋め込みベクトルは専用のベクトルインデックスファイルに保存されます。
  • チャンクと親ドキュメント、作成者、引用関係はグラフDBにノードとエッジとして保存されます。
  • 固有名詞検索のための形態素解析インデックスは別の全文検索ライブラリに送られます。
  • ストレージごとにファイル形式と更新パスが異なるため、全体を通じたACIDトランザクションが保証されません。
  • いずれか1つの更新が失敗するとインデックス間の参照整合性が崩れ、孤立データが残ります。
  • スキーマ変更時に各エンジン用のマイグレーションスクリプトを個別に作成・実行する必要があります。
  • デスクトップ向けクライアント配布時に各エンジンに依存する複数のネイティブバイナリを同梱しなければなりません。

この分離型アーキテクチャはクエリ実行時にも大きな負担となります。ベクトル検索で候補チャンクIDを取得し、グラフDBを開いて親ノードをたどり、さらにテキスト検索で絞り込むといった多段階のパイプラインコードを記述しなければなりません。ステップごとにメモリコピーや直列化・逆直列化のオーバーヘッドが生じ、エンジン間の不整合を修復するための再インデックス処理も定期的に必要になります。特にプロセスが不意に強制終了した場合、それぞれのストレージが持つ障害復旧ルーチンが個別に走るため、再起動時にどこまでが整合しているかを把握するのが困難です。

メモリ消費の観点からも分離運用は無駄を生みます。各エンジンは独自のバッファプールやキャッシュ領域を別個に確保します。OSから見れば複数のプロセスが限られた物理メモリを取り合う形になり、メモリ容量が限られた端末では激しいスワップが発生します。各エンジンが静的にメモリプールを確保しようとすると、実際のデータ量よりもはるかに大きなメモリが常時占有されてしまいます。

LatticeDBはノード、エッジ、ベクトル、BM25転置インデックスを同一のファイル構造に配置することでこの摩擦を取り除きました。単一ファイル内でWAL（Write-Ahead Log）を共有するため、グラフ変更、ベクトル更新、テキストインデックスの追加が1回のコミットで不可分に処理されます。これにより、アプリケーション側で複雑な同期コードを維持する必要がなくなります。

単一ファイル内の3つの検索モデルとCypher拡張構文

LatticeDBはグラフクエリのデファクトスタンダードであるCypher言語を採用し、そこにベクトル類似度検索と全文検索のための専用演算子を統合しました。異なる検索モデルが別々の関数呼び出しに分断されず、1行のクエリとして流れるように記述できます。

// 類似チャンクの検索後、ドキュメントおよび著者ノードへ多段探索し、キーワードで絞り込む
                    MATCH (chunk:Chunk)-[:PART_OF]->(doc:Document)-[:AUTHORED_BY]->(author:Person)
                    WHERE chunk.embedding <=> $query_vector < 0.3 AND doc.content @@ "neural networks"
                    RETURN doc.title, chunk.text, author.name
                    ORDER BY chunk.embedding <=> $query_vector
                    LIMIT 10

このクエリには2つの拡張演算子が含まれています。<=>演算子はベクトル間のコサイン距離を計算し、HNSWインデックスを用いた近似最近傍探索をWHERE句やORDER BY句に直接組み込みます。@@演算子はBM25アルゴリズムに基づく全文検索演算子であり、ステミング処理を経た転置インデックスによる適合度スコアを評価します。クエリ実行プランナーはこれらの条件を統合的に解釈し、ベクトル条件で候補を絞り込んでからグラフエッジを展開するなど、最適化された走査を行います。

Pythonバインディングにおける標準的な利用手順も、シンプルなコンテキストマネージャで完結するように設計されています。以下は公式READMEに掲載されている基本的なコード例です。

from latticedb import Database
                    from latticedb.embedding import hash_embed
                    
                    with Database("knowledge.db", create=True, enable_vectors=True, vector_dimensions=128) as db:
                        db.create_node_fts_index("Chunk", "text")
                        with db.write() as txn:
                            alice = txn.create_node(labels=["Person"], properties={"name": "Alice", "field": "ML"})
                            doc = txn.create_node(labels=["Document"], properties={"title": "Attention Is All You Need"})
                            chunk = txn.create_node(labels=["Chunk"], properties={"text": "The transformer architecture uses self-attention..."})
                            txn.set_vector(chunk.id, "embedding", hash_embed("transformer", dimensions=128))
                            txn.create_edge(chunk.id, doc.id, "PART_OF")
                            txn.create_edge(doc.id, alice.id, "AUTHORED_BY")
                            txn.commit()
                    
                        results = db.query("""
                            MATCH (chunk:Chunk)-[:PART_OF]->(doc:Document)-[:AUTHORED_BY]->(author:Person)
                            WHERE chunk.embedding <=> $query < 0.5
                            RETURN doc.title, chunk.text, author.name
                            ORDER BY chunk.embedding <=> $query LIMIT 5
                        """, parameters={"query": hash_embed("attention", dimensions=128)})

コード内のhash_embed関数は外部APIへの接続なしにサンプルを動作させるための決定論的ハッシュ関数です。意味的な類似度を反映しないため、実運用の際はOpenAIやOllamaなどの本格的な埋め込みモデルを使用する必要があります。開発者はcreate_node_fts_indexによって対象プロパティの転置インデックス作成を宣言でき、この設定も同一トランザクションの中で確実に保持されます。

言語バインディングもCヘッダー（lattice.h）を共通基盤として、Python、TypeScript/Node.js、Go、Java向けに公式に整備されています。Electronのようなデスクトップ環境では、メインプロセスからネイティブバインディングを直接呼び出す構成が推奨されています。

ベンチマーク測定条件と公開数値の解釈境界

LatticeDBのREADMEには各種ワークロードにおける性能数値が公開されています。測定値は環境に依存するため、提示されたテスト条件を正しく把握することが重要です。すべてのテストはApple M1プロセッサ上で単一スレッド、自動拡張バッファプール環境下で実行されています。

これらの数値を解釈する際は3つの点に注意が必要です。第1に、SQLiteとの比較は同一マシン上の同一ハーネスで測定されていますが、Neo4jやKuzuに関する数値は他者のブログ記事を引用した桁感の目安に過ぎません。測定環境のスペックやキャッシュ設定が異なるため、厳密な直接対決の記録ではありません。

第2に、WeaviateやQdrant等の分散DBとの比較では、ネットワーク通信やソケットの遅延を含まない組み込みライブラリならではの優位性が反映されています。クライアント・サーバー構成の製品は0.5〜2ミリ秒程度の通信オーバーヘッドを避けることはできませんが、マルチノードへのスケールアウトが可能です。LatticeDBの0.83ミリ秒は同一プロセス内のメモリアクセスに特化した値です。

第3に、0.13マイクロ秒のポイントルックアップはバッファプールが温まったキャッシュヒット時の測定値です。ストレージからの物理読み出しが発生するコールドスタート環境や、メモリを超えるランダムアクセスでは当然ディスク性能に律速されます。したがって、この数値はインメモリ最適化の理論値に近い上限として捉えるべきです。

ストレージエンジンの内部構造 — B+Tree、HNSWパッキング、WALとイベントログ

LatticeDBが複数モデルを統合しながら高い性能を維持できる理由は、Zig言語で独自開発されたストレージエンジンにあります。外部のC/C++ランタイムに頼らず、メモリ配置とディスクレイアウトを直接制御しています。

  • HNSW接続ページのパッキング: ベクトルインデックスのメモリ浪費を抑えるため、ヒューリスティック近傍選択を適用し、隣接リストをページ単位でパッキングしてメモリ消費を約4.5倍削減しました。
  • 事前正規化による内積計算: 128次元ベクトルのコサイン距離計算負荷を低減するため、格納時にベクトルを正規化し、スキャン時は高速な内積演算で処理します。
  • ビットセット訪問追跡によるBFS探索: 隣接リストキャッシュとビットセットによる訪問管理を組み合わせ、SQLiteの再帰CTEで問題となる中間テーブルの作成やUNION重複排除コストを回避します。
  • 統合WALと永続イベントログ: すべての更新は単一のWALに書き込まれます。データ更新と同時に名前付きストリームやグラフ変更通知（changefeed）を同じトランザクションで発行し、状態とイベントのズレを防ぎます。
  • オンライン空き領域再利用とホットバックアップ: フラグメンテーションを防ぐフリーリスト管理を備え、lattice compactによる末尾領域の回収が可能です。また、DBを稼働させたままスナップショットを取得できるlattice backupをサポートします。
  • インメモリ揮発性データベースのサポート: ファイルを生成せずRAM上だけで完結する:memory:指定が可能で、高速な単体テストや一時的なデータ処理に利用できます。
  • バイトストリーム直列化とクラウド連携: データベース状態を丸ごとバイト配列として書き出し・復元できるため、S3等のオブジェクトストレージとの連携が容易です。

既存のRDBMSに拡張機能としてベクトルやグラフを乗せる手法とは異なり、LatticeDBはノードID、ベクトルID、テキストトークンを最初から1つのB+Treeアドレス空間にマッピングすることで、異種インデックス間のポインタ参照コストを極小化しています。バッファプール管理も単一のLRU/Clockポリシーで統一されており、特定インデックスによるメモリ枯渇を防ぎます。

障害耐性の面でも、単一のWALログは強力な一貫性をもたらします。クラッシュ後の復旧時には1つのログを巻き戻すだけで、グラフの辺、ベクトル、全文検索トークンの不整合を完全に解消できます。複数のDBを組み合わせた構成で生じる「ベクトルだけが残りグラフが消える」といった不整合は構造上起こり得ません。

導入判断の基準 — 適したワークロードと他ツールを選ぶべき条件

LatticeDBの公式ドキュメントには、このシステムを採用すべきでないケース（When to Use Something Else）が明確に記載されています。ツールの選定において適材適所の境界を把握することが不可欠です。

  • ローカルエージェントメモリ・個人ナレッジ基盤: デスクトップアプリ（Electron等）に組み込み、ノートの関連付け、引用グラフ、テキスト検索、類似度判定を1つのファイルで完結させたい場合に最高の選択肢となります。
  • 単一マシンでのRAGプロトタイピング: クラウドサービスや重厚なサーバーを用意せず、単一バイナリでCypherパイプラインを素早く検証したい開発・CI環境に適しています。
  • 複数プロセスからの同時書き込み: LatticeDBは1つのプロセスがファイルを占有するシングルライター構成です。複数のWebサーバーから同時に書き込む構成にはNeo4jやPostgreSQL、Qdrantを採用すべきです。
  • 定型的な表形式データ: 売上ログやユーザー一覧など、行と列で表現すべきデータに対してグラフ構造を適用するとインデックスのオーバーヘッドが生じます。この場合はSQLiteが適しています。
  • 単一マシンを超える分散スケーリング: シャーディングやマルチノードレプリケーション、億単位の分散クエリが必要なワークロードは設計対象外です。DgraphやAWS Neptune等の分散エンジンを検討してください。
  • Cypher完全準拠の要求: OPTIONAL MATCHやストアドプロシージャ（CALL）を多用する既存クエリ資産がある場合、LatticeDBでは未対応の構文でエラーとなる可能性があります。
  • 充実した管理GUI・監視ツールの必須性: Neo4j Bloomのような商用可視化ツールや、確立されたAPM監視エコシステムを前提とする場合、新興のLatticeDBは運用面で不利になります。
  • 極小フットプリントのマイコン環境: 数十キロバイト単位でバイナリサイズが制限され、グラフやベクトルを必要としない組み込み環境では、長年研鑽されたSQLiteのほうが適しています。

総じてLatticeDBは、万能の分散データベースを目指したものではなく、単一マシン環境におけるAIアプリ開発の摩擦を最小化するために設計を研ぎ澄ませた特化型エンジンと言えます。分散機能を手放す代わりに、単一ファイルの簡潔さと低レイテンシを手に入れた点が本アーキテクチャの本質です。

導入を検討する開発チームは、自社アプリケーションの実行トポロジをまず見極める必要があります。単一ホスト上で独立して動作するローカルファーストな製品であれば、インフラ管理コストを大幅に削減できます。一方で、Web APIの背後で多数のワーカーから並行書き込みを行う構成であれば、単一ライターのファイルロックが大きな制約となることを理解しておく必要があります。

確認できていない事項

  • x86_64 Linuxサーバー環境など、Apple M1以外のハードウェアにおける公式ベンチマーク数値。
  • 1億件を超える大規模ベクトルセットにおけるバッファプールの自動スケール動作とメモリ限界。
  • OPTIONAL MATCHおよびCALLプロシージャの実装ロードマップと対応予定時期。
  • Windows環境におけるZigネイティブビルドの挙動およびJNI/cgoバインディングの長期安定性。
