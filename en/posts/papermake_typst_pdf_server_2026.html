Papermake and Typst - Can a Self-Hosted PDF Server Replace LaTeX and Headless-Browser PDF?

For anyone who has to turn invoices, reports, and certificates into PDFs on a server, a look at Papermake - an open-source document-generation server built on Typst

Jul 15, 2026 Dev & Infra

Intro: There Is Always a Moment When a Server Must Spit Out a PDF

When an order completes, an invoice has to go out. When a batch job finishes, reports have to pile up. When an application is approved, a certificate has to be issued. When a shipment leaves the warehouse, a label has to print. At every one of these moments, a pipeline somewhere on a server is quietly generating PDFs on the fly. It is unglamorous infrastructure, but indispensable. As of July 2026, a fresh attempt at this old problem has caught my eye: Papermake, a self-hosted, open-source server that renders Typst templates through a REST API. This post does not stop at introducing Papermake - it analyzes, from a practical standpoint, why server-side PDF generation is still painful, how Typst eases that pain, and whether self-hosting or a commercial API is the better call.

Four Recurring PDF Needs in Practice

  • Invoices - must be generated the instant an order or payment completes, and often must comply with country-specific e-invoice formats.
  • Reports - hundreds to thousands rendered in a single batch job, where layout consistency is the whole point.
  • Certificates - low-frequency documents like employment or completion certificates, where trust elements such as signatures and watermarks matter.
  • Labels - logistics labels that demand ultra-low latency at high frequency, with small, repetitive layouts.

1. The Pain of Existing Approaches - Why Everyone Struggles With This

1.1 LaTeX - High Quality, but Heavy and Slow

LaTeX has been the standard for high-quality typesetting for decades. But bolting it onto an automation pipeline creates real friction. A full distribution runs several gigabytes, and once a monolithic .tex file gets mixed with images and complex diagrams, compilation slows down noticeably. Every single request means spinning up a heavy typesetting process from scratch, and the logs it produces on failure are a steep climb for an ops person who isn't a LaTeX developer. You can architect automation code to inject values into a template - invoice line items, say - but maintaining that architecture is its own ongoing cost.

1.2 HTML-to-PDF via Headless Browser - Flexible, but Resource-Hungry

The HTML-to-PDF approach, represented by Puppeteer and wkhtmltopdf, has real appeal: you get to keep the CSS and templating engines web developers already know. But the trade-off is stark. Headless Chrome consumes 200-300MB of memory just to boot, and pages heavy with images and fonts can easily push past 500MB. Concurrent rendering has been reported to leave processes that never get cleaned up, driving CPU usage hard. On the other side, wkhtmltopdf's aging WebKit engine is lighter but fails to render modern CSS Grid and Flexbox properly. In practice, teams have long been forced to choose between "lightweight" and "renders modern web standards correctly."

2. What Is Typst - A Third Path for Typesetting

Typst is a markup-based typesetting language released in 2023. Instead of LaTeX's dense thicket of backslashes and braces, it uses a syntax closer to Markdown, and it was designed to erase the seam between computation and typesetting so that variables, loops, and conditionals can be woven directly into a document. The performance gap is especially striking: a benchmark reports a document that takes LaTeX 90 seconds for a full compile taking about 15 seconds in Typst, with incremental recompiles after a small edit finishing in under a second. It also ships with compiler-grade, clear error messages, and an ecosystem called "Typst Universe" that bundles packages for chemistry notation, sheet music, circuit diagrams, and more.

2.1 Why It Is Attractive as a Backend PDF Engine

Because Typst is implemented in Rust, it can be embedded as a plain library directly inside a server process, with no browser required. That means a document can be rendered right inside the server, without spinning up several heavy browser subprocesses the way a headless-browser approach does. This property maps precisely onto the "server-side PDF generation" use case - and it is exactly why a project like Papermake chose Typst as its rendering engine.

3. Papermake - Turning Templates Into an API

Papermake is an open-source project by German developer Erik Steiger (rkstgr), who describes it as "a Docker registry, but for document templates." It stores Typst templates content-addressably by SHA-256 hash, with tags like invoice:latest pointing to a specific version. Once a template is published, it is immutable, and every render request logs the input and output hashes, so the entire history can be reproduced and audited.

3.1 Architecture

The system has four pieces. The core papermake is a Typst rendering engine with a virtual filesystem; papermake-registry ties together S3-compatible storage (for templates) and ClickHouse (for render history); papermake-server is an Axum-based HTTP API layer exposing endpoints for publishing templates, rendering, and fetching PDFs; and papermake-worker handles queue-based rendering, though it is still early-stage. Support for not just PDF 1.7 but PDF/A-2b and PDF/A-3b - the standards used for e-invoicing - reads as a design choice made with real invoice automation in mind. The project ships under the Apache 2.0 license.

3.2 The Value of Centralized Templates Plus a REST API

What this architecture means in practice is clear. First, in a microservices setup, multiple services - orders, billing, customer support - can share a single invoice template through nothing more than an API call, so template logic never gets duplicated across services. Second, multi-language and multi-format support gets easier: tag template versions by language or country, and you can ship a new version without touching application code. Third, immutable versions plus a render audit log let you reproduce, later, exactly why a given invoice came out the way it did - not a nice-to-have in regulated industries or wherever documents are subject to accounting audit, but a core requirement.

4. Self-Hosting vs. a Commercial PDF API

Between self-hosted open source like Papermake and a managed commercial API such as CraftMyPDF or APITemplate.io, the trade-off is stark. Self-hosting's advantage is that data never leaves your infrastructure, and unit cost can fall at high volume. One commercial vendor has in fact published comparison material pricing browser-based self-hosting at roughly $27,000 a year while positioning its own managed API as far cheaper (this is a vendor's own comparison, so treat it as directional and verify against your own workload rather than at face value). The advantage of a commercial API, conversely, is zero operational burden: no need to worry about Docker image bloat, serverless size limits, or browser process crashes. The conclusion is straightforward - if your send volume is low and you have no dedicated ops staff, a managed API is the sensible choice; if data sovereignty matters or you must process high-frequency, structured documents (invoices, labels) at volume, a self-hosted option like Papermake is worth weighing seriously.

5. What to Weigh Before Adopting - Fonts, CJK, Performance, Security

5.1 CJK (Chinese/Japanese/Korean) Font Support Is Still Immature

This is the point that calls for the most caution. The Typst project itself has a public issue acknowledging that CJK typesetting support is lacking: switching between font styles (Mincho vs. Gothic), adjusting spacing between CJK and Latin characters, vertical writing, and ruby (pronunciation) annotations are all reported as unsupported or incomplete. If you are considering moving CJK-centric documents - Korean invoices or certificates, say - onto Papermake/Typst, verify actual font rendering and line-wrap quality in a pilot before you commit.

5.2 Performance and Security

On performance, the Rust implementation and the lack of a browser process should favor high-frequency rendering, though independent public benchmarks are still scarce. On security, because this is self-hosted, you carry the burden of designing and auditing the template itself (an injection path where user input flows into rendering), S3 storage access permissions, and the data-retention policy for the render-history database.

Conclusion: Where Should You Actually Use It

As of July 2026, Papermake is an early-stage project - version 0.3.0, 166 GitHub stars. Rather than a full production cutover right away, it makes more sense to pilot it on low-risk workloads first: internal reports, internal certificates - documents where a failure is not a big deal. On the other hand, if you must stamp out high-frequency, structured documents (invoices, labels) at volume, and the weight of LaTeX or a headless browser has been a real burden, the Typst-plus-Papermake combination is a genuinely worthwhile option to evaluate. Just be sure to verify CJK font quality and the project's maturity against your own data before adopting it.
