1. PBR and Consistent Hashing: Background of the 100TB Memory Optimization

Generally, in large-scale distributed reverse proxy architectures, resource management and memory isolation across daemon processes directly dictate overall operational stability and physical infrastructure capacity.

According to the official Cloudflare engineering blog, Cloudflare operates an extensive global network consisting of thousands of servers worldwide with petabytes of RAM and millions of CPU cores. Because every edge service is required to execute across every server node, eliminating wasted memory overhead is critical to preserving fleet capacity. The original post notes that following a recent optimization where the DNS team shed 100TB of memory from their DNS cache, the performance and routing teams achieved an additional global recovery of more than 100TB of RAM by refining a single consistent hashing algorithm.

The catalyst for this project was an internal engineering ticket filed by performance engineer Ivan. The ticket stated: "Excessive memory usage from pingora-ketama in Pingora Backend Router". As reported in the post, Cloudflare's internal load-balancing service, Pingora Backend Router (commonly known as PBR), was consuming substantially more memory than anticipated. This excessive footprint was specifically concentrated inside the data structures managed by pingora-ketama, Cloudflare's open-source library responsible for consistent hashing.

The original post highlights three foundational elements driving this memory footprint:

  • PBR process instances were observed consuming excessive memory, reaching up to 6GB per instance in certain operational environments.
  • Consistent hashing is fundamentally required within PBR to route cacheable HTTP requests by URL so that only a single copy of an asset is cached per data center.
  • A combinatorial explosion of feature flags, caching behaviors, and compliance boundaries required maintaining dozens of distinct hash rings simultaneously.

In this article's interpretation, when a routing daemon caches millions of virtual node mappings, the multiplicative effect across thousands of globally distributed production nodes transforms minor struct padding into dozens of terabytes of wasted memory. The original post explains that by applying two distinct levers—one rooted in statistical modeling and the other in low-level Rust struct compaction—Cloudflare reduced struct size by 25% and trimmed per-server hash points by 90%, successfully liberating over 100TB of RAM.

2. Basic Principles of Consistent Hashing and Load Imbalance

Generally, traditional hash-based modulo load balancing causes severe cache invalidation across distributed clusters whenever upstream servers are added or removed, as nearly every key remaps to a new node.

The original post explains that consistent hashing is an established distributed systems algorithm designed to map workloads across multiple target servers in a manner that avoids massive key churn when servers join or leave the topology. Internally, PBR utilizes consistent hashing to route cacheable web requests based on their URL. This routing guarantees that only one authoritative cached copy of any given file is stored within a single data center, establishing a deterministic mechanism to locate assets without inter-node chatter.

The core concept of consistent hashing relies on hash functions that accept arbitrary keys and map them into a fixed unsigned integer range (such as 32-bit, 64-bit, or 128-bit integers depending on the algorithm). While popular technical literature visualizes this integer space as a continuous circular ring wrapping from the maximum integer back to zero, the original post represents the 32-bit output range simply as a linear number line to demystify integer range boundaries.

The original post describes the basic consistent hashing assignment mechanism as follows:

  • Servers (such as A, B, and C) are placed onto the number line according to the hash of their identifier, such as their IP address.
  • Tasks or requests (such as t through z) are similarly placed onto the number line according to the hash of their cache keys.
  • Each task is assigned to the nearest server located to its left, with the final segment assigned to server C wrapping around to the start of the line.

However, the original post emphasizes that this primitive baseline suffers from immediate structural flaws. Because hash outputs behave like pseudo-random numbers, the segment sizes assigned to individual servers vary drastically. In the visual example provided in the post, server A covers a significantly larger range than servers B or C. Because request volume is directly proportional to range length, servers receive wildly uneven workloads, leading to statistical imbalance.

3. Coefficient of Variation (CV) Formula and Initial Statistical Modeling

To quantify the degree of workload imbalance, the original post introduces two fundamental statistical metrics: expected value (Exp) and standard deviation (SD). Expected value indicates the central tendency around which range sizes are centered, while standard deviation measures how closely individual range lengths cluster around that center.

According to the original post, when distributing workloads across N servers where each server is represented by exactly one single hash point (k=1), the expected fractional range size and its corresponding standard deviation are expressed by the following formulas:

Exp = 1/N

SD = (1/N)√((N-1)/(N+1))

The original post illustrates this behavior with a concrete scenario featuring N=100 servers. In this setting, the expected value is Exp = 1/100 = 1%, while the standard deviation is SD = (1/100)√(99/101) ≈ 0.99%. The post explains that while having standard deviation sit at approximately 0.99% might sound acceptable at first glance, that 0.99% is measured relative to the total length of the entire number line.

To measure the true magnitude of the error relative to the target expected partition size, the standard deviation must be normalized by dividing it by the expected value. This ratio is defined as the coefficient of variation (CV):

CV = SD/Exp = √((N-1)/(N+1))

The original post extracts three vital conclusions when evaluating this formula for N=100 servers:

  • At N=100 servers, the coefficient of variation evaluates to CV ≈ 99%.
  • A 99% variation coefficient indicates that certain servers will be subjected to nearly double their intended workload (99% over capacity).
  • Conversely, other servers on the ring will receive virtually no traffic, languishing in prolonged underutilization.

In this article's interpretation, this statistical baseline reveals that unaugmented consistent hashing cannot guarantee production-grade load balancing in large clusters. Without introducing multiple virtual tokens per physical node, load skew alone would trigger persistent server hot-spotting and tail-latency degradation.

4. The Diminishing Returns of Adding Virtual Nodes

To resolve extreme load imbalance, systems engineers traditionally assign multiple virtual points (hashes) to each physical server. The original post notes that while individual intervals exhibit large standard deviations, summing multiple random segments tends to balance total allocated volume, following the intuition of the law of large numbers.

The author of the original post, noting their background with a calculus teacher for a mother, avoided crude asymptotic approximations and derived the exact mathematical formulation for k hashes per server. The complete formulas for expected value, standard deviation, and coefficient of variation are stated as follows:

Exp_k = 1/N

SD_k = √[(k+1)/(N(kN+1)) − 1/N²]

CV_k = SD_k / Exp_k = √((N-1)/(N*k+1))

The post references NGINX's upstream hash module, where the baseline number of hashes per server is hardcoded to 160 points, a default inherited directly by Pingora. In a cluster of N=100 servers, increasing points from k=1 to k=160 causes the coefficient of variation (acting as an error margin) to plummet from approximately 99% down to roughly 8%, representing substantial leveling.

However, plotting CV_k highlights a severe flaw in the unconstrained expansion of virtual hashes. The original post articulates this key insight: 「each step down in error margin requires (almost) an order of magnitude increase in the number of hashes per server, so adding more hashes yields less and less improvement」. Lowering error bounds demands exponential node inflation.

The original post presents three stark realities regarding virtual hash scaling:

  • When servers are weighted by disk storage, a typical weighting factor such as w=625 causes the per-node hash count to surge to k = 160 × 625 = 100,000 points.
  • The original post notes that expanding points from k=10,000 to k=100,000 yields a minuscule error reduction of only 0.7%.
  • Consuming an order of magnitude more RAM for less than a single percent of balance improvement represents an unsustainable engineering trade-off.

In this article's calculation, evaluating the exact formula for N=100 and k=160 yields √(99 / (100 * 160 + 1)) = √(99 / 16001) ≈ 7.87%. If virtual points are scaled down by 90% to k=16, the resulting variation coefficient is √(99 / (100 * 16 + 1)) = √(99 / 1601) ≈ 24.87%.

5. 32-Bit Discrete Hash Ring and Collision Limits from the Birthday Paradox

The original post reveals that theoretical mathematical derivations hold true only when hashes exist along a continuous real-valued ring. In production systems, software implementations operate on discrete 32-bit unsigned integers, introducing an inescapable vulnerability to hash collisions.

In a 32-bit space, generating hundreds of thousands of hashes per server causes collision probability to increase quickly due to the birthday paradox. In consistent hashing, an ideal topology expects every hash token to contribute to its node's routing partition. When a collision occurs, one token is silently overwritten and dropped, injecting unpredictable variance into the routing table.

The original post details three critical operational findings regarding 32-bit discrete rings:

  • In an ideal continuous model, each virtual node expands capacity, but in discrete 32-bit space, collisions randomly discard node contributions.
  • In simulated runs matching data centers with 2048 servers, the measured error rate actually increased when hash points scaled between 10,000 and 100,000 hashes per server.
  • Over-allocating virtual tokens past the collision threshold actively degrades routing precision rather than improving it.

The post observes that this unexpected physical limit was welcome news for the memory reduction initiative. Because empirical data demonstrated that exceeding a conservative point threshold actually degraded routing fidelity due to 32-bit collisions, Cloudflare engineers established rigorous theoretical justification to slash per-server virtual node generation by 90% without measurable operational penalty.

6. Struct Memory Compaction: Overcoming Rust Alignment Rules from 8 to 6 Bytes

Alongside statistical pruning, engineer Zaidoon discovered an optimization within PBR's internal memory struct used to store hash points along the consistent hashing ring.

According to the original post, PBR historically stored ring points using the following 8-byte Rust struct:

struct Point {
    hash: u32,
    index: u32,
}

In this structure, 4 bytes represent the 32-bit hash value, while the remaining 4 bytes store an index referencing the target server within an adjacent array. Zaidoon observed that PBR is never expected to coordinate more than 2^16 ≈ 65k servers simultaneously in a single routing instance. Consequently, replacing the 32-bit index with a 16-bit unsigned integer (u16) would be structurally sufficient.

However, the original post notes that Rust language semantics complicate this reduction: 「Rust doesn't make it that easy」. Merely altering the struct field to `index: u16` produces no reduction in memory footprint. Under Rust's standard data layout rules, a struct's alignment and size must be an integer multiple of its largest (most aligned) member. Because `hash` requires 4-byte alignment, the struct is padded to 8 bytes.

The post analyzes the potential solutions and their eventual implementation decision:

  • The compiler attribute `#[repr(packed)]` can remove padding, but the post emphasizes that 「`#[repr(packed)]` is controversial for good reasons」 due to undefined behavior from unaligned references.
  • A safer and robust alternative is storing the data as a raw byte array `[u8; 6]` while exposing access via getter methods that assemble integers safely.
  • Compacting the struct to exactly 6 bytes achieved an immediate 25% reduction in raw consistent hash memory consumption across all instances.

The original post presents the final production code for the compacted struct and its accessor methods:

struct Point([u8; 6]);

impl Point {
   fn hash(&self) -> u32 {
	u32::from_ne_bytes(self.0[0..4].try_into().unwrap())
   }

   fn index(&self) -> u16 {
	u16::from_ne_bytes(self.0[4..6].try_into().unwrap())
   }
}

In this article's interpretation, eliminating 2 bytes of padding across the point array directly minimizes unnecessary memory overhead during contiguous vector allocations.

7. Server Weights and Ring Explosion: Combinatorial Growth Across Feature Sets

The original post explains that in heterogeneous production topologies, balancing requests according to individual hardware capacity inflates virtual node populations across multiple independent hash rings.

Within Cloudflare's fleet, storage capacities vary across server generations. To ensure servers with larger NVMe/SSD pools service proportionally more requests, the Ketama algorithm scales node presence. As stated in the post, for two servers S_1 and S_2, if S_1 must handle w times the requests of S_2, its hash allocation must satisfy H_1 = w * H_2. While storage disk size serves as weight for cache routing, compute workloads scale weights by CPU or GPU count.

However, the post stresses that server weights were not the sole cause of memory bloat. Three combinatorial factors accelerated process memory exhaustion:

  • In production environments, arbitrary servers cannot service arbitrary traffic; compliance mandates and specialized cache features constrain routing to specific subsets.
  • Feature segregation cannot be resolved by injecting more tokens into a shared ring; each permutation of features requires an independent, isolated ring instance.
  • As characterized in the post, a handful of distinct features produced 2^(handful) = dozens of coexisting hash rings, driving PBR instance memory up to 6GB.

In this article's interpretation, when dozens of discrete rings coexist inside a process, every point in every ring multiplies baseline memory overhead, transforming sub-optimal struct layout into an acute infrastructure bottleneck.

8. Zero-Cache-Churn Rollout: Two-Dimensional Safe Migration Strategy

The original post notes that reconfiguring consistent hash parameters introduces the grave risk of melting upstream origin servers. Altering ring topology changes the target destinations for cached URLs. Swapping hash rings globally in a single atomic cutover would instantaneously invalidate cached contents worldwide, converting an internal memory optimization into catastrophic origin traffic overload.

To eliminate this risk, Cloudflare executed an incremental, layered rollout governed by four architectural controls:

  • PBR maintained both routing engines simultaneously in memory: the legacy large Ketama ring and the new compacted small ring.
  • Routing choices were governed by an internal migration framework that made deterministic, stable decisions based on request hash values.
  • An instantaneous rollback mechanism allowed directing requests back through the legacy ring without redeploying PBR binaries if anomalies arose.
  • Rollout blast radius was isolated by decoupling global percentage thresholds from geographical data-center-scoped deployment stages (two dimensions).

Throughout migration, telemetry systems monitored backend selection traces, ring version counters, connection errors, process resident memory, initialization latency, cache hit ratios, and origin traffic rates. Once traffic reached 100% across all facilities, the legacy ring path was permanently decommissioned. Resident memory dropped sharply, securing more than 100TB of reclaimed RAM globally.

9. Key Changes in the pingora-ketama Crate v2 and Practical Takeaways

The original post confirms that all structural improvements discussed have been published directly to the open-source `pingora-ketama` crate as an unadvertised Cargo feature flag, enabling community adoption.

The original post outlines the architectural capabilities delivered across both ring versions:

  • The `v2` ring introduces the 6-byte compacted storage layout, an accelerated sorting algorithm, and dynamic scaling of base hash tokens per node.
  • The `v1` ring preserves exact backwards compatibility with the legacy consistent hashing implementation historically deployed within Pingora.
  • The crate allows executing both ring implementations concurrently within the same process, supporting seamless request-level switching.

The post concludes by encouraging software engineers to re-examine baseline assumptions within their production systems. While low-level programming languages like Rust provide powerful control over hardware, applying rigorous mathematical analysis to foundational design choices often yields the most dramatic efficiency gains.
