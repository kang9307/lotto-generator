ハングル正規表現の罠 - 「아닙니다」の中に「아니」は無い

音節の算術、語尾ごとの安全なパターン、NFC と NFD、シェルのエスケープ、가-힣 の限界、回帰テストまで実行出力とともに

2026年7月29日 IT・技術

序論: 検査器は二か月間ずっと「指摘なし」を返していた

本文に免責文言が入っているかを確認する検査器があった。規則は単純だ。/자문이 아니/ というパターンが文書から見つかれば合格、無ければ警告。毎日回り、毎日静かだった。警告が出たことが一度も無かったので、すべての文書に免責文言がきちんと入っているものと思っていた。

実際には正反対だった。その規則は一度も一致したことが無かった。サイトの本文がすべて丁寧体、つまり「자문이 아닙니다」だったからである。規則が探していた 아니 は 아닙니다 の中に存在しない。検査器は文書を忠実に読み、規則を忠実に回し、忠実に何も見つけられないまま「指摘なし」を返していた。

この事故が恐ろしいのは、結果が失敗ではなく成功の形をしていたことだ。例外も無く、終了コードも 0、ログもきれいだ。検査器が壊れているという事実を知らせる合図がどこにも無い。こうしたものを静かな失敗と呼ぶ。そして韓国語を扱うコードでは、静かな失敗がとりわけ頻繁に起こる。

原因は一つだ。英語で身についた習慣が、ハングルではそのまま崩れる。英語で advis を探せば advise、advisor、advisory が一度に引っ掛かる。語尾が後ろに付け足される構造なので、語幹が常に部分文字列として残るからだ。ハングルはそうではない。語尾が付くとき前の文字そのものが変わる。아니 に終結語尾が付くと 아니 + ㅂ니다 ではなく、아 + 닙 + 니 + 다 になる。二文字目が別の文字に置き換わるのだ。

この記事はその原理と、そこから派生する五つの罠を扱う。特徴が一つある。すべての主張に実際に回した出力が付いている。説明だけ読むと「そうだろうな」で流れてしまうが、-1 という数字を自分の目で見ると忘れられない。

実行環境。以下のすべての出力は Windows 10 Pro / Node.js v22.16.0 (win32) で実際に実行した結果をそのまま写したものである。例はすべて .js ファイルに保存して実行した。理由は 5 節で説明する。

この記事が扱わないもの。正規表現エンジンごとに文法が異なる問題、つまり方言と移植性は どこでも動く正規表現 で扱った。この記事はエンジンではなくハングルという文字体系の側の問題だけを掘る。二つの記事は重ならない。

1. 「아닙니다」の中に「아니」が無い理由 - 音節は合成済みの一文字だ

まず事実確認から始めよう。主張ではなく出力である。

node v22.16.0 / win32
--- 1-1. indexOf ---
'아닙니다'.indexOf('아니') = -1
'아닙니다'.includes('아니') = false
'아니다'.indexOf('아니')   = 0
'아니라'.indexOf('아니')   = 0
--- 1-2. コードポイント ---
아닙니다 : 아=U+C544 닙=U+B2D9 니=U+B2C8 다=U+B2E4
아니     : 아=U+C544 니=U+B2C8
아니다   : 아=U+C544 니=U+B2C8 다=U+B2E4

아니다 と 아니라 では 0 番目の位置ですぐに見つかる。ところが 아닙니다 では -1 である。コードポイントを並べれば理由は一目でわかる。

  • 探す文字列 아니 = U+C544、U+B2C8
  • 対象の文字列 아닙니다 = U+C544、U+B2D9、U+B2C8、U+B2E4
  • 二番目の位置が U+B2C8 ではなく U+B2D9 だ。したがって連続した部分列が成立しない

1.1 終声が付くと別の文字になる

なぜ二番目の位置が変わったのか。Unicode のハングル音節領域 (U+AC00~U+D7A3) は、初声・中声・終声の組み合わせを算術式であらかじめ計算して配置したものだ。Unicode 標準が定義する合成の式は次のとおりである。

音節コードポイント = 0xAC00 + (初声インデックス * 21 + 中声インデックス) * 28 + 終声インデックス

この式を逆に回して 니 と 닙 を分解すると、こうなる。

--- 1-3. なぜ違うのか (音節の算術) ---
니 U+B2C8 {"初声":2,"中声":20,"終声":0}
닙 U+B2D9 {"初声":2,"中声":20,"終声":17}
終声(パッチム)が付くと全く別のコードポイントになる → '니' ≠ '닙'

初声 (ㄴ) も同じ、中声 (ㅣ) も同じだ。違うのは終声だけなのに、終声が 0 から 17 (ㅂ) に変わった瞬間コードポイントが 17 だけ移動する。文字列検索器から見れば、これはアルファベットの a と r ほどに無関係な二文字である。「パッチムが一つ付いただけ」という人間の直観は、コードポイントの並びには一切反映されない。

1.2 英語と何が違うのか

違いを対比で整理すると、こうなる。この対比が記事全体の根である。

  • 英語 - 屈折が文字の追加で起こる。advise → advisor。前の部分 advis は損なわれずに残る
  • ハングル - 屈折が文字の置換で起こる。아니다 → 아닙니다。二文字目そのものが別の文字に変わる
  • したがって英語で通用する前方一致の戦略は、ハングルでは原理的に成立しない
  • 同じ理由で startsWith、LIKE '아니%'、検索索引の前方一致もすべて同じ罠を踏む

2. 静かな失敗 - 語幹だけの規則は丁寧体を一度も捕まえない

1 節が原理なら、2 節は被害の規模だ。五つの活用形に対して悪い規則と良い規則を並べて回してみた。

node v22.16.0 / win32
文                                               語幹のみ (BAD)     文字クラス (GOOD)   選択肢 (GOOD)
--------------------------------------------------------------------------------------
이 글은 법률 자문이 아닙니다.                        取りこぼし         一致              一致
이 글은 법률 자문이 아니다.                          一致              一致              一致
이 글은 법률 자문이 아니라 정보 제공입니다.             一致              一致              一致
이 글은 법률 자문이 아님을 밝힙니다.                   取りこぼし         一致              一致
이 글은 법률 자문이 아녜요.                          取りこぼし         一致              一致
--------------------------------------------------------------------------------------
語幹のみ (BAD)             2/5 検出
文字クラス (GOOD)          5/5 検出
選択肢 (GOOD)              5/5 検出

使った規則はそれぞれ /자문이 아니/、/자문이 아[니닙님녜냐]/、/자문이 아(?:니|닙|님|녜|냐)/ である。

2.1 なぜこれが最悪の失敗類型なのか

検出率 2/5 は「性能がやや物足りない」という水準ではない。実務でこの規則がどう動いていたかを見ると性格が変わる。

  • 公式文書はほとんどが丁寧体で書かれる。つまり実務で最も多い形が、まさに捕まえられない側にある
  • 規則が引っ掛からなければ、検査器は「違反なし」ではなく事実上「検査していない」状態になる。両者の出力が同じだ
  • 検査器が回っているという事実そのものが偽の安心を与える。検査器が無ければ人が直接見たはずなのに、有るから誰も見ない
  • 検出率が 0% ではなく40% だという点がさらに悪い。平叙体の文書では時々引っ掛かるので、「規則はちゃんと動く」という証拠が周期的に生産される

2.2 規則を疑う前に検査器を疑え

ここで学んだ実務原則が一つある。ある規則が長い間一件も捕まえていないなら、それは違反が無いという意味ではなく、規則が死んでいるという意味である可能性が高い。とくに韓国語のテキストならなおさらだ。検査器を作るとき一致件数も併せて記録し、長期間 0 件の規則に警告を出す仕掛けを入れれば、こうした事故を早期に捕まえられる。8 節で扱う回帰テストが根本的な処方なら、こちらは安価な保険である。

3. 語尾ごとの安全なパターン - 何を文字クラスで開くか

ではどう書くべきか。核心はパッチムが付く位置をあらかじめ開いておくことだ。韓国語で活用が起こる位置はおおむね決まっているので、その位置を文字クラスにすればほとんどが覆われる。

探したい表現よくある活用形危険なパターン安全なパターン
아니다 系列 (~でない) 아닙니다 / 아니다 / 아니라 / 아님 / 아녜요 아니 아[니닙님녜냐]
없다 系列 (無い) 없습니다 / 없다 / 없어요 / 없음 / 없이 없다 없[다습어음이는]
하다 系列 (する) 합니다 / 한다 / 해요 / 함 / 하는 하다 (?:합|한|해|함|하)
이다 系列 (繋辞) 입니다 / 이다 / 예요 / 임 / 인 이다 (?:입|이|예|임|인)
않다 系列 (否定) 않습니다 / 않다 / 않아요 / 않음 않다 않[다습아음는]
수 있다 / 없다 (できる / できない) 할 수 있습니다 / 할 수 없다 수 있다 수 (?:있|없)[다습어]

3.1 この表をそのまま信じないこと

上の表は出発点であって完成ではない。韓国語の活用形は列挙では覆いきれない。表を使いながら必ず併せて覚えておくべき限界がある。

  • 不規則活用は文字クラスでは覆えない。돕다 → 도와、듣다 → 들어 のように語幹そのものが変わる
  • 分かち書きの揺れが規則を突き抜ける。할 수 있습니다 と 할수 있습니다 は別の文字列だ。空白の位置は \s* で開かねばならない
  • 助詞の挿入も突き抜ける。자문이 아닙니다 と 자문은 아닙니다 と 자문이 결코 아닙니다 がいずれも有効な文である
  • クラスを広げ続けると誤検出が急増する。아 で始まる無関係な単語が引っ掛かり始める

3.2 正規表現で支えきれない地点

そこである時点からは接近そのものを変えるほうがよい。実務で使える順序はこうだ。

  1. 第 1 段 - 活用しない中心的な名詞だけを探す。자문、면책 のように変形の無い語彙がアンカーとして使いやすい
  2. 第 2 段 - アンカーが引っ掛かった文単位で切り出し、その中で否定表現の有無を判定する。正規表現一つで文全体を一致させようとしない
  3. 第 3 段 - 精度がさらに必要なら形態素解析器で語幹を正規化してから比較する。아닙니다 と 아니다 が同じ語幹に正規化されれば問題そのものが消える
  4. 第 4 段 - それでも残る曖昧な事例は人が確認するよう一覧に出す。自動で通すよりましだ

正規表現で韓国語の活用形をすべて覆おうとする試みは、たいてい失敗する。規則は膨らみ続け、ある瞬間誰も手を出せない一行になる。正規表現は候補を絞るのに使い、判定は別の層に任せるほうが長持ちする。

4. NFC と NFD - 見た目が同じ文字が同じでないとき

二つ目の罠はもっと巧妙だ。同じ 한 なのに、コンピュータが別の文字列として見る場合がある。Unicode 標準附属書 15 が定義する正規化形式の問題である。

node v22.16.0 / win32
--- 3-1. 長さとコードポイント ---
'한'.length              = 1 | U+D55C
'한'.normalize('NFD').length = 3 | U+1112 U+1161 U+11AB
画面出力はどちらも: 한 / 한

NFC は結合された形だ。한 が U+D55C の一文字である。NFD は分解された形で、初声 ㅎ (U+1112)・中声 ㅏ (U+1161)・終声 ㄴ (U+11AB) の三つのコードポイントに割れる。画面にはどちらも同じ「한」に見える。目では絶対に区別できない。

4.1 比較がすべて失敗する

--- 3-2. 比較がすべて失敗する ---
nfc === nfd            : false
'한국'.indexOf(nfd)     : -1
'한국'.normalize('NFD').indexOf('한') : -1
/한/.test(nfd)          : false
/[가-힣]/.test(nfd)      : false
--- 3-3. 正規化すれば解決する ---
nfc.normalize('NFC') === nfd.normalize('NFC') : true
'한국'.normalize('NFC').indexOf(nfd.normalize('NFC')) : 0

一致比較、indexOf、正規表現の判定、文字クラスの検査がすべて失敗する。そして正規化一回ですべて解決する。問題と処方がこれほどきれいに対応する例も珍しい。

4.2 集合と整列も一緒に壊れる

--- 3-4. 整列・重複除去も壊れる ---
Set([nfc, nfd]).size = 2 ← 同じ文字なのに 2 個
正規化後の Set.size   = 1
--- 3-5. ファイル名の事例 ---
二つのファイル名は同じか : false
NFC 長さ 7 / NFD 長さ 10
filter(f => f.startsWith('보고서')) の結果件数 : 1 ← 2 件のはずが

重複除去ができず、ファイル名のフィルタが半分しか引っ掛からない。보고서.txt が二つあるうち一つだけが漉し取られたのだ。重複除去のロジックが静かに失敗すると、原因を突き止めるのに何日もかかる。目で見れば完全に同じ文字列が並んでいるのに、プログラムは違うと言い張るからである。

4.3 どこで正規化するのか

原則は一つだ。外部から文字列が入ってくる境界で一度正規化し、内部は正規化済みと仮定する。あちこちで正規化すると性能の無駄にもなるし、やる箇所とやらない箇所という穴ができる。

地点正規化理由
ファイルシステムの一覧取得必須プラットフォームとプロトコルによって分解形が混ざって入り得る
ネットワーク受信 / API 応答の解析必須送信側がどの形式で送るか制御できない
フォーム入力の受信必須入力機と貼り付け経路ごとに結果が異なり得る
データベース保存の直前推奨保存時点で統一しておけば照会条件が単純になる
比較・検索の直前次善策動きはするが正規化の漏れが生じやすい
画面出力の直前無意味比較が既に終わった後なので手遅れ

どの形式に統一するか。ウェブと保存層ではおおむね NFC が無難だ。文字列が短く、ほとんどのシステムが結合形を期待し、長さの計算も人間の直観に近いからである。ただし初声検索のように字母単位の処理が必要な機能を作るときは、その区間だけ意図的に NFD を使うほうが楽だ。大事なのは形式の選択より一つのシステムの中で一つに決めておくことである。

5. シェルを経由すると正規表現が静かに死ぬ

三つ目の罠は文字体系ではなく層の境界で生じる。ところが結果が前の事故とまったく同じくらい静かなので、併せて扱う価値がある。

空白を消そうと node -e で一行実行したとしよう。命令をシェルに渡した瞬間バックスラッシュが一枚剥がれ、残った文字列が JavaScript の文字列リテラルとして再解釈される。バックスラッシュ一つが二度消費されるのだ。実際に回した結果である。

$ node -e "console.log(JSON.stringify('\s'))"
"s"

$ node -e "console.log(String(new RegExp('\s+')))"
/s+/

$ node -e "console.log(JSON.stringify('less  space'.replace(new RegExp('\s+','g'),'')))"
"le  pace"

三行目を見よう。元は less space、結果は le pace だ。空白はそのまま残り、アルファベットの s だけがすべて消えた。空白を消そうとしたコードが、まさに正反対に動いたのである。

同じ命令を Git Bash と Windows PowerShell 5.1 の両方で実行し、出力は同一だった。特定のシェルの問題ではなく、層をもう一つ経由すれば起こる一般的な現象だという意味である。

5.1 正確には何が起きたのか

犯人はシェルだけではない。JavaScript の文字列リテラルの規則も共犯だ。ファイルに保存して実行すると原因が分離して見える。

node v22.16.0 / win32
--- 4-1. 正規表現リテラル vs 文字列からの生成 ---
リテラル /\s+/          : /\s+/
new RegExp('\s+')      : /s+/
new RegExp('\\s+')     : /\s+/
--- 4-2. 同じ入力、三つの結果 ---
元の文字列               : "less  space"
リテラル使用 (正常)       : "lessspace"
new RegExp('\s+') (破損) : "le  pace"
new RegExp('\\s+') (正常): "lessspace"

整理するとこうなる。

  • JavaScript の文字列リテラルで '\s' は認識されないエスケープなのでバックスラッシュが捨てられ、ただの 's' になる
  • その文字列で正規表現を作ると /s+/ になる。空白の文字クラスがアルファベットの s に変わったのだ
  • 正規表現のリテラル /\s+/ は文字列リテラルの段階を経ないので安全だ
  • 文字列から作る必要があるならバックスラッシュを二度書かねばならない。'\\s+'
  • シェルを経由すればここにもう一枚必要になり得る。層ごとに一枚ずつ増える

5.2 なぜ誰も気づかないのか

--- 4-3. ハングルでも同じことが起こる ---
元の文字列              : 자문이 아닙니다
new RegExp('\s') で除去  : "자문이 아닙니다"
リテラル /\s/ で除去     : "자문이아닙니다"
--- 4-4. 静かな失敗である理由 ---
投げられる例外なし。RegExp の生成は成功 : true

ハングルの文字列では消すべき空白がそのまま残った。そして最後の行がこの節の核心だ。new RegExp('\s+') は例外を投げない。完全に有効な正規表現オブジェクトが作られる。ただしあなたが意図したものとは違う正規表現だというだけだ。エラーが無いのでログもきれいで、テストが無ければデプロイまでそのまま行く。

5.3 実務規則

  • 正規表現とハングルが入ったコードをシェル引数で渡さない。ファイルに保存して実行する
  • 文字列から正規表現を作る必要があるなら作った結果を一度出力して目で確認する。console.log(String(re)) の一行で足りる
  • パターンを設定ファイルやデータベースから読む構造ならバックスラッシュ二重化の規則を文書に明記する
  • ユーザー入力をパターンに差し込むときはメタ文字をエスケープする。しないと誤動作を超えて性能事故になる
  • インライン実行がやむを得ないならシングルクォートで囲むシェルの作法を使い、その場合でも結果を検証する

6. [가-힣] が捕まえられないものと、代わりに使うもの

ハングルを検査するときほとんど反射的に使う [가-힣] は、完成形音節の領域だけを指す。残りはすべて漏れる。九つの標本で確認した。

------------------------------------------------------------------------

子音単独              ㄱ        U+3131                     X
母音単独              ㅏ        U+314F                     X
組み立て中の字母       ㄱㅏ       U+3131 U+314F              X
NFD 分解状態          한        U+1112 U+1161 U+11AB       X
古ハングル 옛이응      ㆁ        U+3181                     X
古ハングル 中声拡張    ힰ        U+D7B0                     X
互換字母              ㅘ        U+3158                     X
半角ハングル          ﾠﾡ        U+FFA0 U+FFA1              X

完成形の一文字を除けば八つの標本がすべて通り抜ける。つまり [가-힣] で「ハングルでない文字」を漉し取る検証器を作れば、上の八つがすべてハングルでないと判定される。組み立て中の入力や分解形のファイル名が拒まれる事故はここから出る。

6.1 代案二つの比較

--- 5-2. 広く開く代案 ---
区分                  広い範囲     \p{Script=Hangul}
----------------------------------------------------
完成形音節            O            O
子音単独              O            O
母音単独              O            O
組み立て中の字母       O            O
NFD 分解状態          O            O
古ハングル 옛이응      O            O
古ハングル 中声拡張    O            O
互換字母              O            O
半角ハングル          X            O

比較した二つのパターンは次のとおりである。

  • 広い範囲の列挙 - [ᄀ-ᇿ㄰-㆏ꥠ-꥿가-힣ힰ-퟿]。字母・互換字母・拡張領域まで手で開いた。八つの標本を捕まえたが半角ハングルで漏れた
  • スクリプトプロパティ - /\p{Script=Hangul}/u。九つの標本をすべて捕まえた。Unicode 文字データベースの Script プロパティを直接参照するので、ブロック境界を手で管理する必要が無い
  • プロパティエスケープは u フラグが必須だ。抜けると文法エラーではなく別の意味で解釈され、また静かに間違う

6.2 個数を数えると差が出る

--- 5-3. ハングルの個数を数える比較 ---
対象文字列のコードポイント数 : 7
match(/[가-힣]/g)            : 2
match(/\p{Script=Hangul}/gu) : 7

同じ文字列で 2 と 7 が出た。「ハングルの比率が何パーセントか」といった指標を作るなら、どちらを使うかによって 3 倍以上の差が出る。

6.3 広く開くことが常に正解ではない

ただしここで均衡を取らねばならない。目的によっては狭いほうが正しいときがある。

  • 本文にハングルが混じったかを検出する用途 (多言語の汚染検査など) なら広く開くのが正しい。取りこぼせば検査器が無力になる
  • ユーザー名の入力を検証する用途なら狭く行くほうがよいことがある。組み立て中の字母 ㄱㅏ が名前として保存されると困る
  • 検索索引を作るなら正規化を先にして、その次に広い範囲を使う。順序が逆だと分解形が索引から漏れる
  • どちらにせよ何を通すかを先に文章で書いてからパターンを選ぶのが順序だ。パターンから選ぶと意図が事後的に正当化される

7. 長さは一つではない - 正規表現の外側の罠

正規表現でなくても同じ根から出る問題がある。「文字数」という言葉に答えが四つあるということだ。

node v22.16.0 / win32
対象           .length   [...s].length   byteLength(utf8)   Intl.Segmenter
------------------------------------------------------------------------
한글             2            2                  6                    2
NFD 한글         6            6                  18                   2
abc              3            3                  3                    3
家族の絵文字      8            5                  18                   1
한글+英字        5            5                  9                    5

한글 はどの基準で数えるかによって 2、2、6、2 だ。分解形で入ってくれば 6、6、18、2 になる。同じ二文字なのに保存単位の長さが 2 から 6 に跳ね上がる。

数え方数える単位適した用途間違える場合
s.lengthUTF-16 コードユニットメモリ推定、インデックス指定分解形・絵文字で人間の感覚とずれる
[...s].lengthコードポイント文字単位の走査分解形では依然膨らみ、結合絵文字を割る
Buffer.byteLengthバイト (エンコーディング依存)保存容量、転送量、列サイズエンコーディングを明示しないと答えが変わる
Intl.Segmenter書記素クラスタ利用者に見える文字数遅く、ロケール依存で、古い環境に無い

7.1 保存容量はエンコーディングごとに異なる

--- 6-2. エンコーディング別バイト数 ---
'한글' utf8 バイト  : 6 (一文字あたり 3 バイト)
'한글' utf16 バイト : 4

UTF-8 でハングル一文字は 3 バイト、UTF-16 では 2 バイトだ。データベースの列をバイト基準で取る環境なら、「10 文字まで」が何バイトなのかをエンコーディングと併せて計算せねばならない。文字基準の長さ制限をそのままバイト列に写すと、ハングル入力で切れる。

7.2 切り詰めが文字を半分に割る

--- 6-3. slice が文字を半分に割る ---
NFD 文字列 slice(0,2) : "하" ← 初声+中声だけ残った壊れた文字
NFC 文字列 slice(0,1) : "한"

分解形の文字列を切ったら終声が落ちて「한」が「하」になった。プレビューのテキストを作ったり要約を切り詰めたりするときにこうしたことが起こる。切る前に正規化せよという原則がここでも成り立つ。絵文字・国旗・家族の絵文字まで安全に扱うには、書記素クラスタ単位で切らねばならない。

  • プレビュー・要約の切り詰め → NFC 正規化の後に書記素クラスタ単位
  • データベースの列設計 → バイト基準、エンコーディングを明示
  • 入力文字数の制限案内 → 利用者に見える書記素クラスタ基準
  • ハッシュ・署名の対象 → 正規化形式を取り決めとして固定。しないと同じ文字が別のハッシュを生む

8. 回帰テストの作り方 - 誤通過を捕まえる唯一の仕掛け

ここまでの罠はすべて静かだ。例外も無くログもきれいである。ではどうやって捕まえるのか。検査器そのものを検査することのほかに方法は無い。

核心はテスト項目を二種類に分けることだ。

  • MUST_HIT - この文では規則が必ず引っ掛からねばならない。丁寧体・平叙体・接続形・名詞形をそれぞれ入れる
  • MUST_MISS - この文で引っ掛かれば誤検出だ。規則を広げていくとここで壊れる
  • どちらか一方だけでは半分だ。MUST_HIT だけなら規則を /./ にしても通ってしまう

実際に二つの規則を同じテストに掛けてみた。

[悪い規則] /자문이 아니/
  [FAIL] MUST_HIT  丁寧体    본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  平叙体    본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  接続形    본 글은 법률 자문이 아니라 일반 정보입니다.
  [FAIL] MUST_HIT  名詞形    본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS 無関係    전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS 部分語彙  자문위원회가 심의했습니다.
  => pass 4 / fail 2

[良い規則] /자문이 아[니닙님녜냐]/
  [PASS] MUST_HIT  丁寧体    본 글은 법률 자문이 아닙니다.
  [PASS] MUST_HIT  平叙体    본 글은 법률 자문이 아니다.
  [PASS] MUST_HIT  接続形    본 글은 법률 자문이 아니라 일반 정보입니다.
  [PASS] MUST_HIT  名詞形    본 글은 법률 자문이 아님을 알려드립니다.
  [PASS] MUST_MISS 無関係    전문가 자문을 받아 작성했습니다.
  [PASS] MUST_MISS 部分語彙  자문위원회가 심의했습니다.
  => pass 6 / fail 0

=== 要約 ===
悪い規則の失敗件数 : 2 ← 回帰テストがあれば初日に捕まった
良い規則の失敗件数 : 0

六行のテストが二か月間誰も知らなかった欠陥を即座に露わにした。序論の事故はこのテスト一つで初日に防げただろう。

8.1 テスト項目に必ず入れるもの

  1. 丁寧体 - 「~습니다 / ~ㅂ니다」。公式文書で最も多く、最も取りこぼしやすい形だ
  2. 平叙体 - 「~다」。語幹がそのまま残る場合が多いので悪い規則も通してしまう。だからこれだけ入れても意味が無い
  3. 接続形・名詞形 - 「~라」「~ㅁ을」。終声の変化が実際に起こる位置である
  4. 口語・縮約形 - 「~예요 / ~네요」。ユーザー生成コンテンツを扱うなら必須だ
  5. 誤通過の標本 3 種 - ①規則と無関係な文 ②中心語彙が別の意味で使われた文 ③アンカー語彙が別の単語の一部である文

8.2 検査器を作るときの追加の仕掛け

  • 回帰テストをインライン実行で回さない。5 節で見たエスケープ事故がテストコードで起これば、テスト自体が嘘をつく。必ずファイルに保存する
  • わざと欠陥を仕込んで検出力を確認する。規則を壊したときテストが赤にならないなら、そのテストは何も守っていない
  • 規則ごとの一致件数を記録する。長期間 0 件の規則は死んでいる可能性が高い
  • 標本の文は実際の本文から取る。想像で作った文は実際の文体を反映しない
  • 規則を直すたびにテスト項目を先に追加する。取りこぼした事例を見つけたなら、それがそのまま新しいテスト項目だ

9. この記事の方法でも防げないもの

均衡のために限界を明かす。上の処方をすべて適用しても残る問題がある。

  • 不規則活用 - 語幹がまるごと変わる場合は文字クラスで覆えない。形態素解析器が必要だ
  • 分かち書きの自由度 - 韓国語は分かち書きの誤りに寛容なので、実際の文書にはあらゆる揺れが混じる
  • 意味の判定 - 자문이 아닙니다 と 자문이 아니라고 할 수는 없습니다 は正反対なのに文字列は似ている。正規表現では原理上区別できない
  • 形態素解析器の費用 - 精度は上がるが、辞書の管理、処理速度、配布サイズという代価が付く。検査器一つのために導入する価値があるかは別の判断だ
  • 正規化の副作用 - まれだが正規化は元のバイト列を変えるので、署名検証や原本保存が要求される箇所では正規化前の原本を別に保管せねばならない
  • Script プロパティの広さ - \p{Script=Hangul} は広くてよいが、狭い検証が必要な画面ではむしろ過剰だ

だからこの記事の結論は「正規表現を上手に使おう」ではない。正規表現が担える範囲を知り、それを超える地点で別の道具に乗り換えようというほうに近い。

結論: 規則を疑う前に検査器を疑え

この記事の出発点は二か月間静かだった検査器だった。原因は正規表現の文法でも、ライブラリのバグでも、エンコーディングの設定でもなかった。ハングルの音節が合成済みの一文字だという、一行で説明が付く事実だった。英語で身についた前方一致の習慣をハングルにそのまま移した瞬間規則は死に、死んだという事実を知らせる合図が無かった。

もう一度整理すると六つだ。①ハングルは語尾が付くとき前の文字が変わるので語幹一致は成立しない。②パッチムの位置を文字クラスで開きつつ、列挙では覆いきれないことも知っておく。③外部の境界で一度正規化し、内部は正規化済みと仮定する。④正規表現をシェルに渡さず、作った正規表現を出力して確認する。⑤[가-힣] は完成形だけなので目的によって \p{Script=Hangul} を検討する。⑥そしてこのすべてを回帰テストで固定する。

六つのうち最後が最も重要だ。前の五つは知識であり、最後は知識が忘れられても持ちこたえさせる構造である。人は必ず忘れる。新しく加わった人はそもそも知らない。テストだけが残る。

今すぐできることが一つある。韓国語のテキストを検査する規則の一覧を開き、直近 3 か月間一件も引っ掛からなかった規則があるか見よ。あればその規則に丁寧体の文を一つ入れて回してみればよい。違反が無くて静かだったのか、死んでいて静かだったのかは、その一行で分かれる。

> 標準根拠: Unicode UAX #15(正規化)、UAX #29(書記素クラスタ)、UAX #44(Script プロパティ)
> 使い方: 韓国語テキストを扱う検査器・パーサ・検索コードをレビューする前に、上から順に流し読みする。
> このファイルをそのまま AI に貼り、「うちのコードを基準に点検して」と頼んでもよい。

## 0. 30秒判定 — 一つでも当てはまれば以下を全て見る
- [ ] 韓国語の文字列を正規表現や `indexOf` で検査している
- [ ] ユーザー入力・ファイル名・外部 API からハングルが入ってくる
- [ ] 「文字数」を数える、または文字列を切り詰める
- [ ] パターンを設定ファイル・環境変数・CLI 引数から受け取る

## 1. パターン作成 — 語尾の位置をどう開くか
- [ ] 語幹だけのパターンが残っていないか(`아니`、`없다`、`하다`、`이다`、`않다`)
- [ ] パッチム(終声)が付く位置を文字クラスまたは選択肢で開いたか
- [ ] 丁寧体(`~ㅂ니다` / `~습니다`)を明示的に含めたか
- [ ] 名詞形(`~ㅁ` / `~음`)を含めたか
- [ ] 口語・縮約形が必要なサービスか(ユーザー生成コンテンツなら必要)
- [ ] 空白位置を `\s*` または `\s+` で開いたか(分かち書きの揺れ)
- [ ] 助詞の変化を考慮したか(`이/은/는/가`)
- [ ] クラスを広げた分だけ誤検出が増えていないか測り直したか

### 語尾位置のクイックリファレンス
| 系列 | 開くべき位置 | 最低限の候補 |
|---|---|---|
| 아니다(~でない) | 2文字目 | 니 닙 님 녜 냐 |
| 없다(無い) | 2文字目 | 다 습 어 음 이 는 |
| 않다(否定) | 2文字目 | 다 습 아 음 는 |
| 하다(する) | 1文字目 | 합 한 해 함 하 |
| 이다(繋辞) | 1文字目 | 입 이 예 임 인 |

### 正規表現で支えきれなくなったときの移行順序
1. 活用しない**中心となる名詞**をアンカーにする
2. アンカーを含む**文単位で切り出し**、その中で判定する
3. さらに精度が要るなら**形態素解析器**で語幹を正規化する
4. 残る曖昧な件は**人が見る一覧**に出す(自動で通さない)

## 2. 正規化 — どの境界で一度だけ行うか
- [ ] 正規化形式を一つに決めたか(通常は NFC)
- [ ] ファイルシステムの一覧取得直後に正規化しているか
- [ ] ネットワーク受信・API 応答の解析直後に正規化しているか
- [ ] フォーム入力の受信直後に正規化しているか
- [ ] DB 書き込み直前に統一しているか
- [ ] 比較・整列・重複除去の前に同じ形式であることが保証されているか
- [ ] 切り詰め(`slice`、`substring`)の前に正規化しているか
- [ ] ハッシュ・署名の対象なら形式を**取り決めとして固定**したか
- [ ] 原本保存が必要な箇所で正規化前の値を別に保持しているか

## 3. シェル・ツール経由 — バックスラッシュは何層か
- [ ] 正規表現をシェル引数(`-e`、`--pattern`)で渡していないか
- [ ] 渡すなら層ごとにバックスラッシュが一段増えることを反映したか
- [ ] 文字列から正規表現を作るときバックスラッシュを二重にしたか
- [ ] 生成された正規表現を**一度出力して目で確認**したか
- [ ] パターンに差し込むユーザー入力をメタ文字エスケープしているか
- [ ] 回帰テストのコードをインラインではなく**ファイルに保存**して回しているか

### 一行の自己診断
正規表現オブジェクトを作った直後に、その文字列表現をログに残す。
意図と違えばその場で露見する。例外は決して発生しない。

## 4. 文字範囲 — 何をハングルと見なすか
- [ ] `[가-힣]` を使っているなら**完成形音節のみ**を捕まえると理解しているか
- [ ] 次のうち通すものと拒むものを文章で書き出したか
  - [ ] 子音・母音の単独(`ㄱ`、`ㅏ`)
  - [ ] 組み立て中の入力
  - [ ] 分解形(NFD)の文字列
  - [ ] 古ハングル字母
  - [ ] 互換字母
  - [ ] 半角ハングル
- [ ] 広く開く必要があるなら `\p{Script=Hangul}` を検討したか
- [ ] プロパティエスケープに `u` フラグを付けたか(欠けると静かに意味が変わる)
- [ ] 検索索引なら**正規化 → 範囲検査**の順か(逆だと分解形が落ちる)

### 目的別の推奨
| 目的 | 推奨範囲 | 理由 |
|---|---|---|
| 混入・汚染の検出 | 広く(`\p{Script=Hangul}`) | 取りこぼすと検査器が無力になる |
| 入力値の検証 | 狭く(`[가-힣]` など) | 組み立て中の字母の保存を防ぐ |
| 検索索引 | 正規化後に広く | 分解形の流入に備える |
| 統計・比率の計測 | 広く | 狭いと数値が数倍ずれる |

## 5. 長さと切り詰め — どの単位で数えるか
- [ ] 「文字数」の単位を定義したか(コードユニット / コードポイント / バイト / 書記素クラスタ)
- [ ] DB の列がバイト基準ならエンコーディングを明記して計算したか
- [ ] 利用者に示す文字数は**書記素クラスタ**基準か
- [ ] プレビューの切り詰めが終声を切り落としていないか
- [ ] 絵文字・結合文字が混じり得る項目か

## 6. 回帰テスト — コードではなく検査器を試す
- [ ] MUST_HIT の項目があるか(必ず引っ掛かるべき文)
  - [ ] 丁寧体
  - [ ] 平叙体
  - [ ] 接続形
  - [ ] 名詞形
  - [ ] 口語形(必要な場合)
- [ ] MUST_MISS の項目が3種以上あるか(引っ掛かれば誤検出)
  - [ ] 規則と無関係な文
  - [ ] 中心語が別の意味で使われた文
  - [ ] アンカー語が別の単語の一部になっている文
- [ ] 標本の文を**実際の本文**から取ったか(想像で作った文は文体が違う)
- [ ] 規則をわざと壊したときテストが失敗するか確認したか
- [ ] 規則ごとの一致件数を記録しているか
- [ ] 長期間0件の規則に警告を出しているか

### テストの骨格
```
MUST_HIT  = [丁寧体, 平叙体, 接続形, 名詞形, (口語形)]
MUST_MISS = [無関係, 別の意味, 別語の一部]
結果 = MUST_HIT 全件一致 かつ MUST_MISS 全件不一致
```

## 7. 出荷前の最後の3行
- [ ] この規則は**丁寧体の文を一つ**実際に捕まえるか
- [ ] このコードは**分解形の入力を一つ**実際に処理するか
- [ ] 生成された正規表現を**出力して見たか**
