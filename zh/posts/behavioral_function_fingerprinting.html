「输出相同」不等于「是同一个函数」 - 用行为而非字节判定函数时留下的误报与漏报

形状垮掉之后还剩下什么，以及把函数真跑一遍来比较这个决定所收取的代价

2026-09-10 开发/基础设施

面对一个符号名被剥掉的可执行文件，首先要定的不是「这个函数是什么」，而是凭什么说两个东西是同一个。依据不定下来，答案也就定不下来；依据一换，同一个文件会给出另一个答案。

依据历来分两支。一支量的是形状：字节重合了多少，控制流图长得有多像。另一支量的是行为：给函数喂进值，看出来什么，看它一路上读了什么写了什么。两支各有所长，更要紧的是，它们出错的样子不一样。

下面顺着走的是第二支。特别是选了这条路之后必然跟来的两种失败 — 把两个不同的函数叫成同一个的误报，和把同一个函数叫成两个的漏报 — 各自在哪里产生，又靠什么变少。

缘起 - 用运行时行为去对函数的工具

起因是一个叫 fnprint 的工具。仓库的 README 这样界定自己：它按函数做了什么去匹配二进制里的函数，而不是按字节或控制流图长什么样。每个函数都在一个小模拟器里用随机输入跑一遍，跑出来的副作用被记录下来，再哈希成指纹。

README 列出的用途有三个。给符号被剥掉的二进制挂名字；指出两个构建之间的行为变化；以及把身份不明的函数对照已知有漏洞的代码集与已修补的代码集排出名次。目前只处理 x86-64 ELF，ARM64 与 MIPS、以及 PE 和 Mach-O 加载器都写在计划里。用 Rust 写成，采用 MIT 许可证。

比工具本身更值得看的，是它挑中的判定依据。跑起来再比较这个决定不是白来的。它买到什么、又付出什么，才是正题。

按形状判定 - 字节与图

量形状这条路很老，今天仍是实务里的默认。大体上数三样东西。

  • 字节序列 — 直接比对函数开头的机器码。只是放地址和重定位的位置每次构建取值都不同，于是把那些位置标成可变，再看剩下的部分是否重合。
  • 控制流的形状 — 以基本块为顶点、以分支为边构出图，再给两个函数的图打相似度分。改动一条指令往往骨架还在，所以它比字节比对更耐得住。
  • 附带的标记 — 字符串常量、魔数、所调用外部符号的名字之类。优化很少去动它们，作为线索价值很高，但对一个什么标记都不带的函数就无从下手。

这些方式的长处很清楚：快，不执行任何东西，命中的时候极准。要在同一构建环境下认出同一个库，很难找到比它们更好的。问题出在构建环境一变的那一刻。

形状为什么会垮 - 同一份源码走向不同机器码的路径

「找出同一个函数」之所以难，不是因为函数难，而是因为同一份源码并不总是变成同一段机器码。编译是从源码到机器码的单向变换，而这个变换里塞满了源码根本没写下来的决定。优化级别、编译器的种类与版本、目标架构、链接时刻的选择，全都在摇动结果。

把到底是什么在拆字节分开列一下，是这样。

变换发生了什么对字节比对的影响对图比对的影响
内联小函数被摊进调用处独立函数直接消失，没有可比对的对象调用方的图变大，原来的形状融进去了
指令重排互不依赖的指令换了位置同样的指令序列因顺序不同而对不上只在块内换顺序的话骨架还在
寄存器分配同一个值落到别的寄存器操作数字节整个变掉几乎没有影响
循环展开与向量化迭代被摊开或折进宽指令长度和内容都变了块数与边数变化很大
尾调用与块合并调用变成跳转，块被并到一起尾部的形状变了顶点减少，相似度分数下滑
换编译器同样的级别下判断不同同一份源码重合的片段变短骨架相近但细节分岔
换架构指令集本身就不一样比对根本不成立只剩图的骨架，其余无从比较

值得盯住的是右边两列的分岔。看图这条路比看字节更能扛住这些变换。但扛也有限度。展开循环、把条件改成无分支代码，这类优化会把骨架本身重画一遍。所有量形状的方式最终都堵在同一处，因为编译器改动形状的自由度，比人所说的「相同」这个范围要宽。

按行为判定这个思路

于是冒出另一个问题：形状会晃，那么不晃的是什么。优化是在不改变程序所做之事的前提下改动形状的。那么直接去量「所做之事」不就行了。

这就是按行为判定的思路。给函数喂值跑一遍，再把过程中浮到外面的效果记录下来压成摘要。fnprint 的 README 把它记录的东西称为不依赖架构的效果流，并逐条列出：读写了参数缓冲区和结构体的哪些位置，写进去的值属于哪一类 — 是输入的副本、是小常量、还是指针 — 做了哪些调用，走了哪些分支，返回了什么。

这条效果流随后被切成片段，转成摘要签名。两个函数的相似度，就是签名格位对上的比例，用来估算两者行为重叠了多少。为了免去把候选拿去两两全比，前面还架了一层分桶索引。只把概念画出来的话，一个函数的观测结果大致是这个样子。

读    arg0[0 .. n)        连续访问
写    arg1[0 .. n)        输入的副本
调用  1 次                只记录，不进去
分支  2 次                零长度检查 / 对齐检查
返回  arg1                原样返回输入指针

这份摘要里既没有指令顺序，也没有寄存器名字，更没有绝对地址。README 写明绝对地址被丢掉，只留下偏移和形状。它下沉到了摇动形状的那些变换够不着的一层。作为交换，这一层索取的是另一种代价。

决定去执行所收取的四笔账

给输入、比输出，意思就是把函数真的跑起来。静态分析里没有的问题，从那一刻起全冒出来了。分成四笔。

副作用 - 分析把世界改了

函数不只是返回值。它删文件、开套接字、改全局变量、结束进程。把一个身份不明的函数照原样放到真机上跑，分析这个动作就改动了观测对象之外的东西。所以这条路一般选的不是真执行，而是模拟执行：在一层模仿指令的东西上面跑，并把通向外面的口子堵上。

输入空间 - 必须先定喂什么进去

能作为参数进来的取值种类实际上是无穷的。从中挑几个喂进去，决定了判定的质量。随便丢些值进去，执行通常只走过函数的前半段：那种看看长度是不是零就返回的函数，那种把空指针挡掉的函数。输入浅，观测就浅。反过来想把输入做得精细，就得知道函数期待什么，而知道这一点恰恰是最初要解的那个问题。

环境依赖 - 同一个函数跑出不同结果

执行结果并不只属于这个函数。读到未初始化的内存，那块地方原先是什么就掺进结果里。读时钟或取随机数的函数每次调用都给出不同的值。栈上留着的上一次调用的痕迹、对齐的位置、映射到的地址，全都插进观测里。这份晃动不消掉，就会把同一个函数量两遍，然后判成两个不同的函数。

隔离成本 - 跑一段你并不了解的代码

执行身份不明的代码，这件事本身就带成本。碰到坏地址不能让执行死掉；陷进死循环时要有东西把它掐断；一个函数的执行不能给下一个留下痕迹。而这些机关全都在削速度。字节比对一秒扫过几万个函数的地方，模拟执行得对每个函数跑上好几遍。

代价为什么会有常见应对应对之后仍然剩下的
副作用函数在返回值之外改动世界模拟执行，堵住向外走的调用被堵住的调用之后的行为永远观测不到
输入空间可能的输入实际上无穷多定下样本并重复若干次深层条件后面的代码始终到不了
环境依赖内存初值、时钟、随机数掺进来给未设置内存一个定值，把流程固定确定性是可复现，不是正确的保证
隔离成本跑的是身份不明的代码吸收坏访问，设定执行上限吞吐远远赶不上静态比对

缘起的那个工具怎么处理这四笔账

怎么对付这四笔账，就成了评价整条路线的尺子。只把 fnprint 的 README 里确实写着的搬过来，是下面这些。

  • 未设置的内存 — 从没准备过的地方读，会返回一个确定的值，那一页则当场被映射。把未初始化内存这份晃动，用一条关于取值的规则按了下去。
  • 野指针 — 指到不知哪里的指针不会让运行崩掉，而且同样的输入永远给出同样的轨迹。隔离和可复现被绑进了一句话里。
  • 对其他函数的调用 — 向外走的调用会被打桩，也就是记录下来然后跳过。这让运行不会一头扎进标准库，观测始终停在这个函数上。
  • 绝对地址 — 绝对地址被丢掉，只留偏移和形状。这是让同一段代码换个位置摆放仍然给出同样轨迹的机关。

以上是文档里有的。文档里没有的同样重要。碰到系统调用指令时做什么，隔离保证到哪个水平，README 里都没有相应说法。一个函数要喂几个输入、这些值按什么规则构造，也没有。安装要求里点了一个广泛使用的 CPU 模拟框架和一个反汇编器；而那个模拟框架只把自己介绍成模仿指令的框架，它自己的仓库页面也没有把是否连操作系统层一并模仿这件事分开写。

文档里没有，不等于没处理。它的意思是光凭文档判不了。要把一个会运行身份不明代码的工具搬进实务，需要另找来源填上的，正是这一栏。

相同的层次 - 「观测重合」与「是同一个函数」

现在进到这条路线的核心问题。两句话处在不同的层。

第一句，在挑出来的这些输入上观测结果重合。这是关于观测的陈述。它是关于喂进去什么、出来什么的事实，而且只在喂进去的取值范围内为真。第二句，这两个是同一个函数。这是关于身份的陈述，它包含着一个主张：在任何输入上都表现一致。

前者并不蕴含后者。这道缝就是误报诞生的地方。两个当真不同的函数，在挑出来的输入上恰好给出同样的观测，并不罕见。README 也把纯计算列为薄弱之处，并写得很直白：两个都读缓冲区、都返回一个数的校验和看着很像，因为从外面看它们本来就几乎一样。

函数 A   读 buf[0..n)   不写   返回 4 字节整数
函数 B   读 buf[0..n)   不写   返回 4 字节整数

从外面观测到的摘要完全一致。
里面乘了什么、加了什么，不会留在外面。

反方向也存在：同一个函数因为观测条件不同而看着像两个。把两个都被重度优化的构建拿来比，浮到外面的行为本身就很薄。内联把调用吞掉、分支折成无分支代码之后，就没有效果可记了。而可记的东西一少，所有函数就都开始互相像。

误报和漏报并不对称

误报 - 把不同的叫成相同的

误报是安静的。一个挂了错名字的函数，此后正因为它有名字而不会再被打开。旁边的函数以这个名字为前提被解读，再有别的判断以那些解读为前提堆上去。一次错误的判定会污染架在它上面的一切，而被污染的成果从外表看却是完整的。在自动挂了几千个名字的场合，这份风险随个数成比例地放大。

漏报 - 把相同的叫成不同的

漏报不吵，但它会留着。在与有漏洞的代码集比对时漏掉一个函数，那个函数就那样留在原地。不过漏报有一个误报没有的性质：它大多在人再看一遍时就会浮出来。只要流程里挂着一步、由人扫一眼候选列表的头几名，相当一部分漏报就被捞了回来。README 恰好点到这一处：在某一组上，最高分候选正确的概率是 93%，而正确函数落在前五名之内的概率是 96.6%，并补了一句，很小的复核预算就能补上这道缝的大部分。

由此得出的结论很简单。误报和漏报不是同一个重量。在挂着人工复核的流程里，漏报是可以捞回来的失败，而误报捞不回来。反过来，在没有人工复核的自动流程里，这份不对称消失了，只剩下误报的代价。

可信度取决于在多少个输入上达成了一致

只对上一次，跟碰巧撞上没有区别。拿一个输入去比两个函数、得到同样的结果，那几乎不算信息。输入越多，一路碰巧重合下去的概率就越小，一致也就越靠近身份的证据。判定的可信度来自观测的量，而不是函数的某种属性。

而观测的量并不只由输入个数决定。更占分量的是这个函数有多少东西可显露。一个收三个参数、扫过缓冲区、依条件写入不同值的函数会留下很多痕迹；一个把值原样传出去的单行函数则一点痕迹都不留。README 把这个属性称作信号量，并写明信号少的函数会被搁置而不做判定。

同一份文档公开的测量值把这个结构直接摆了出来。对象是 zlib 1.3.1 的 84 个函数，比的是同一份源码在不同条件下构建出的两个产物。

相比的两个构建首位候选正确率精确率该怎么读
同一编译器，无优化到第 1 级97.1%93.8%有一侧未经优化，行为就留得丰富
同一编译器，无优化到第 2 级93.1%83.3%正确率保住了，确信的质量却下滑
同一编译器，无优化到第 3 级91.3%100.0%搁置变多，凡是敢下结论的全对了
不同编译器，两侧都未优化97.7%97.1%换编译器是这条路线扛得很好的一个轴
同一编译器，第 2 级到第 3 级56.5%66.7%两侧都被优化，可观测的东西就薄了
不同编译器，两侧都是第 2 级59.1%50.0%难的条件叠在一起，两个数一起往下掉

要从表里读出来的不是单个数字，而是那个走势。只要有一侧优化得轻，数就高；两侧都被重度优化，数就掉到接近一半。README 自己也是这样总结的：只要有一侧还留着行为上的丰富度，就落在 80 到 98 个百分点的区间；两侧都被重度优化时，可观测的行为变薄，成绩就朝着掷硬币的方向滑下去。这句话与其读成性能汇报，不如读成关于这条路线依赖什么的说明，那才准确。

各识别方式的强弱与失败的样子

把上面的内容折成一页，就是下面这张表。没有哪种方式在所有轴上都赢，要点在于它们各自朝不同方向出错。

识别方式强在哪里弱在哪里主要呈现的失败
字节序列比对同一构建环境下的同一个库；速度优化、换编译器、换架构，一概不行漏报 — 明明是同一个函数却对不上而溜掉
控制流图比较指令层面的细微变动、局部修改内联、循环展开、分支折叠以漏报为主 — 骨架被重画就溜掉
字符串与常量标记对带标记函数的确定力不带标记的函数、标记被抹掉漏报 — 压根没有可判的对象
行为指纹换优化级别与编译器、跨架构小函数、纯计算、深层条件后的代码误报 — 把外面看着像的叫成同一个
行为指纹加搁置敢下结论那部分的质量召回率、判不出来的函数所占比例转嫁成漏报 — 含糊的一律不作答

最下面两行才是实务里真正要挑的位置。允许搁置，敢下结论那部分的质量会上去，答不上来的函数会变多。两条路线并跑，失败的样子彼此不同，能盖住相当一部分，但两个结果打架的那些函数会作为新的复核队列留下来。无论选哪种，失败都不会消失，只是换了个地方。

用途不同，贵的失败也不同

哪怕用的是同一个工具，判定门槛也该随着你要做什么而摆在不同位置，因为两种失败中哪一种更贵，是按任务而变的。

用途误报带来的损失漏报带来的损失往哪边偏
给静态链接进来的库函数挂名字一个错名字污染其后的全部解读留下一些没有名字的函数压误报 — 拿不准就不挂名字
用补丁前后的比对找出改动点没变的函数被当成变了，复核量膨胀真正的改动被看漏压漏报 — 候选放宽，交给人去收窄
重复代码检测把毫不相干的函数扯到一起找不出重复，错过整理的机会取平衡 — 出成候选列表，由人来裁
分辨是有漏洞的版本还是已修补的版本把安全的当成危险的，白费对应工夫危险的那个原封不动留着压漏报 — 漏掉的代价高得多
大批量自动分类没人看，所以结果就那样成立了没分好类的条目越堆越多压误报 — 没有复核就没有回收

表的最后一行接回上一节的那份不对称。人工复核在不在流程里，会把两种失败的相对价格整个翻过来。在定工具的阈值之前该定的，是流程的形状。

搁置这第三种答案

在相同和不同之间，还有不说。这个选项并不减少失败，但它让你能挑要承受哪一种失败。README 也写着，对没把握的组它宁可搁置也不猜，所以精确率保持得高，而同一门槛下的召回率偏低。

把搁置写进流程时，有三样东西值得分开。

  • 不要把搁置和漏报记在同一栏 — 没作答的函数不是答错的函数，而是还没有答案的函数。把两者并成一个数字，流程里该修哪一段就看不见了。
  • 先定好搁置的函数往哪儿送 — 是送进人工队列，是交给另一条路线的判定，还是就那样放着。不先定，搁置就只是一次安静的遗漏。
  • 把因信号太少而搁置的，和因候选咬得太紧而搁置的分开 — 前者加输入也不会变好，后者多加观测倒有分开的余地。应对方式不同。

法律与合同所附的条件

分析二进制这件事，没有一个统一的答案挂在上面。同样的工作，在哪里做、为什么目的做，评价就会分岔。所以这一节不写「可以做」或者「不可以做」，只写判断所悬挂的那些点。

法律和合同是两个不同的层。关于程序使用的规范，各国条文不同，什么条件下允许什么目的的分析也随之不同。而在法律划定的范围之外，拿到这个程序时同意过的使用条款与许可证还会另外附加条件。法律那一侧开着而合同那一侧关着的情况有，反过来也有。这两层要分别确认，一层的结论没法搬到另一层上用。

技术保护措施又是另外一层。为控制访问或复制而设下的措施，把它解除这个行为与分析本身的合法性是分开对待的。越过那种措施的具体步骤，这里不写。上面谈的，是针对已经在手、也已经能跑的代码，判断这个函数和那个函数是不是同一个这一方法的性质，而不是撬开什么东西的办法。

在实务里，这条边界通常靠目的和记录来管。为什么做这次分析，产出留给谁、以什么形式留，被分析的对象是通过什么途径拿到的，这些都会留下来。真要做决定的事项，流程是把法域和合同摆在一起走法务审查。

收束 - 缩成五句话

  1. 「找出同一个函数」之所以难，不是因为函数难，而是因为同一份源码并不总是变成同一段机器码。内联、重排和寄存器分配会拆掉字节签名。
  2. 形状晃动的地方，行为晃得少。可是要量行为就必须真的执行，而这个决定会收四笔账：副作用、输入空间、环境依赖、隔离成本。
  3. 「在挑出来的输入上观测重合」和「是同一个函数」是处在不同层的命题。前者不蕴含后者，那道缝就是误报诞生的地方。
  4. 判定的可信度来自在多少个输入上达成了一致，以及那个函数本来有多少东西可显露。两边都变薄，任何方式都会滑向掷硬币。
  5. 误报和漏报不是同一个重量，哪一个更贵由流程里有没有人工复核来定。先定流程再定阈值，才是对的顺序。

没能确认的部分

  • 碰到系统调用时的行为 — 模拟执行走到系统调用指令时做什么，README 里没有相应说法。只有向外走的函数调用会被记录后跳过这一条。
  • 每个函数的输入个数与生成规则 — 有「往参数寄存器里塞垃圾值」这样的说法，但塞几个、这些值按什么规则构造，README 里没写。而这个数字直接左右判定的可信度。
  • 隔离的保证水平 — 有「野指针不会让运行崩掉」这样的说法，但它意味着到什么范围为止的隔离，文档没有分开写。对一个处理身份不明代码的工具来说，这一栏需要另做评估。
  • 公开测量值范围之外的表现 — 公开的数字覆盖的是一个库的 84 个函数。换个规模、换用别的语言写的代码、换别的优化组合，相应的数值文档里没有。
  • 字节比对系工具的内部规格 — 那套广泛使用的库函数识别技术，其详细规格文档这里没有打开。上文的描述仅限于该系方法共有的性质，并不是照搬某一具体实现的规格。
