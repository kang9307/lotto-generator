Still Working Is Not the Same as Still Right - Moving Prompts From Claude Fable 5 to 5.1

The effort sweep, the vanished progress updates, and the append-only history. What a migration actually asks you to re-measure

Sep 4, 2026 Tech & IT

When a model version goes up by a decimal point, most teams do nothing. They change the name, watch it seem to run, and leave it. The danger in that is not that something breaks. It is that nothing does. With no visible failure there is no occasion to look again, and meanwhile half the prompt turns into sentences whose reason for existing is gone.

The Claude Fable 5.1 prompting guide concedes this in its opening line: existing Fable 5 prompts should perform well without changes, but a handful of behavioral differences are worth knowing about. This piece takes that handful and looks at it through migration only. Not what the model got better at, and not how it ranks against anyone else's. The axis is which parts of a prompt you already run need re-measuring.

Every spec, price, model ID, and default below was read from the official documentation as of September 4, 2026. Values like these go stale within weeks. Before acting on any of them, re-check the current value on the source page, and re-test vendor performance claims against your own evals. Items that could not be verified are collected in their own section near the end.

The trigger - a document that opens with it already works

In early September 2026 the guide was passed around a Korean developer community, and one reaction argued roughly that you have to write elaborately, and writing simply is expensive. That reading catches something real about the document's shape. It is not a feature announcement so much as a symptom index. It opens with entries like: little or no text between tool calls, go to this section; one tool call per turn in agent loops, go to this section.

The format itself tells you something. None of the changes listed there throw errors. If they did, no index would be needed. They surface as a screen going quiet, an extra turn, prose getting denser. This is the kind of difference that gets discovered weeks after deployment, as a vague sense that things feel slower lately.

Background on the Fable 5 generation itself already lives on this site. Launch specs are in the fifth-generation model analysis, workloads worth pointing it at are in Fable 5 in practice, plan integration is in the Max and Team Premium limits piece, and the access-control history is split across the export directive and the lifting of it. This one adds the migration angle on top.

Three breaking changes - the only places that actually break

Earlier I said the danger in this migration is that nothing breaks. Precisely three places do. These differ in kind from everything in the symptom index. The rest quietly raise cost; these three make requests fail with a 400 or data disappear silently. The sentence about existing prompts performing well without changes is a statement about everything except these three.

What breaksHow it surfacesWhat to do
Forced tool use is not supportedtool_choice set to {"type": "any"} or {"type": "tool", "name": "..."} returns a 400 invalid_request_error. The same validation applies to the token counting endpoint. auto (the default) and none are unchangedFor schema enforcement, keep auto and move to strict tool use or structured outputs. Thinking blocks are bound to the model that produced themEvery thinking block records which model wrote it, and preservation runs one way only. Fable 5.1 reads blocks from Opus 5, Fable 5, Mythos 5, and earlier models, but no earlier model reads Fable 5.1'sConversations moving up onto 5.1 keep their reasoning. A router or fallback that drops back to an older model loses it for the turns that run there. Design fallback paths in that direction

The second item carries a qualifier — it happens silently — that is worth its own look. When a request carries a block the target model cannot read, the API drops it before the model sees it. Dropped blocks do not count toward input_tokens and are not billed. The problem is notification. With the thinking-binding-controls-2026-08-01 beta header the drop is reported in a top-level input_transformations array; without it, the drop is silent. So if you run a router that swaps models, reasoning can be thrown away on every request with no trace in either the invoice or the response.

Refusal handling is not a breaking change — it carries over from Fable 5 unchanged — but it belongs on the same checklist. A declined request returns HTTP 200 with stop_reason: "refusal" and a stop_details object naming the policy area that fired. Because it is not an error code, it never reaches an exception path, so you need code that checks stop_reason before reading the response body. A refusal arriving before any output is not billed, and the permitted fallback targets for Fable 5.1 are Claude Opus 4.8 and Claude Opus 5.

Effort - the first dial a migration touches

effort controls how many tokens the model spends on a response. A common misreading is that it governs only thinking blocks. The documentation is explicit that effort affects all tokens in the response: text responses and explanations, tool calls and their arguments, and thinking. So it still works on requests where nothing is thought through, and at lower effort tool calls themselves get fewer and terser.

There are five levels, with the descriptions the documentation attaches to each.

LevelDocumented descriptionDocumented use case
maxAbsolute maximum capability with no constraints on token spendingTasks requiring the deepest possible reasoning and most thorough analysis
xhighExtended capability for long-horizon workLong-running agentic and coding tasks over 30 minutes with token budgets in the millions
highHigh capability. Equivalent to not setting the parameterComplex reasoning, difficult coding problems, agentic tasks
mediumBalanced approach with moderate token savingsAgentic tasks that require a balance of speed, cost, and performance
lowMost efficient. Significant token savings with some capability reductionSimpler tasks needing the best speed and lowest cost, such as subagents

One caveat the documentation adds matters a great deal. Effort is a behavioral signal, not a strict token budget. At lower levels the model still thinks on sufficiently difficult problems; it simply thinks less than it would at a higher level on the same problem. So low should not be read as thinking off. There is no switch that turns thinking off on this model at all.

What grows and what shrinks as you raise the level is also spelled out. Higher levels make more tool calls, explain the plan before acting, give detailed summaries of changes, and write more comprehensive code comments. Lower levels combine operations into fewer calls, proceed straight to action without preamble, and use terse confirmations. Effort is less a quality dial than a total-volume-of-talking-and-doing dial. If a UI was leaning on the model's explanations, lowering effort empties the screen along with the token count.

The exact conditions on medium is cheaper for similar results

This is the passage that gets truncated most often in retelling. The original runs like this. Fable 5.1's capability gains over Fable 5 show up across effort levels and are largest at the higher settings. And at medium, results roughly match Claude Fable 5 at lower cost, so step down to medium or low where your evals show quality holds.

Three qualifiers are attached.

  • The comparison target is the previous generation. What medium matches is Fable 5, not Fable 5.1 at high. The offer is Fable 5 quality for less, not all of 5.1 for less
  • The word is roughly. That is an approximation, not a declaration of parity. Safest read: it can go either way depending on the shape of the task
  • The clause where your evals show quality holds is right there. The sentence hands verification to whoever runs the workload. Stepping down without an eval set is outside what it licenses

The same section also has a line about low: that Fable 5.1 at low effort is often competitive with Claude Opus and Sonnet models on cost per task while scoring higher, so include it wherever you would otherwise run a smaller model at a higher effort level. This is the vendor assessing its own lineup, and which benchmarks were run under which conditions does not appear in this document. So the sentence is useful up to the point of add it to your candidate list, and no further. Past that, measure it on your own workload.

If you do evaluate low, one side effect travels with it. At low effort, Fable 5.1 calls search and retrieval tools less often than Fable 5 and answers from memory more. A product that leans on retrieval and drops to low for cost trades saved tokens for staleness. The documented responses are two: raise effort for the affected turns only, or add a system prompt line to the effect that recognizing a name in a fast-moving area is not the same as knowing its current state, so such names should be searched exactly as the user wrote them.

Why the sweep has to start over

The cheapest lesson available in this migration sits here. The guide puts it plainly: re-run the sweep even if you already ran one on Claude Fable 5, because effort level names do not correspond to the same amount of thinking across models.

The implication is simple and the consequence is not. medium is not an absolute scale but a relative one that means something only inside a given model. Fable 5's medium and Fable 5.1's medium share a name, not a quantity. So a note saying we concluded last time that medium was optimal expires as evidence the moment the model changes. The trap is that the value sitting in the config file still looks valid. Because nothing broke, nobody looks again.

The migration guide repeats the point from another angle: start at high and sweep, and run a fresh sweep on your own evals rather than carrying over a setting tuned for Fable 5. It then adds that while 5.1's gains are largest at xhigh and max, those levels also add thinking time and time-to-first-response. The gain and the cost are bolted to the same dial.

Fable 5.1 also gained a way to change effort mid-session. Insert a role: "system" message carrying only output_config and no text, and the new level takes effect from the next user turn without invalidating the prompt cache. It needs the beta header mid-conversation-output-config-2026-07-01.

{"role": "system", "content": [], "output_config": {"effort": "low"}}

The documentation prefers this form over changing the top-level value on Fable 5.1, for two reasons, the second of which is the interesting one. A top-level change not only restarts the cache but also steers the model less reliably: its earlier replies were written at the previous level, and it tends to stay consistent with them. Style has inertia inside a conversation.

Fewer progress updates - and the price of buying them back

This is probably the change teams notice first in practice. Fable 5.1's default behavior is to write fewer user-facing updates than Fable 5 during long tool-calling turns, and the effect becomes more pronounced at higher effort and in longer tool chains. Users see the agent go quiet for minutes, or get a final message covering only the last step rather than the whole task.

Order matters here. The first step the documentation recommends is not to edit the prompt.

  1. Check that the client receives updates at all. The short notes the model writes between tool calls, what it just found and what it is doing next, come back as progress-update thinking blocks. Under the default thinking.display of omitted, those blocks arrive empty. You may simply never have been requesting them
  2. Turn the display setting on. Set display: "updates" (beta header thinking-display-updates-2026-08-18) to receive the progress updates as text while reasoning stays hidden. Any thinking block with non-empty text can then be rendered directly as a status line. "summarized" returns them mixed with summarized reasoning
  3. Find and remove the old suppression lines. Prompts often still carry lines like hold all findings for the final response, written back when earlier models were too eager to narrate. Take that out before adding anything
  4. Only then ask. Specify when and what: a line up front about what it is about to do, brief updates while working, and a closing recap that stands on its own so a reader who sees only the last message still has the full picture

The order matters because the trade-off is real. Asking for more updates adds output tokens and lengthens turns. If the display setting alone would have solved it, or if the silence came from a leftover suppression line, that cost never needed paying. Skip to step four and you pay twice: the updates that were already there, plus the ones you asked for.

A related trap sits next to it. If your product collapses or hides tool output, tell the model. Otherwise it runs commands to show the user output your UI never displays. The documentation recommends delivering that note as a turn-scoped system message (clear_at: "next_user_message").

Batching independent tool calls into one response

Fable 5.1 usually issues parallel tool calls as expected: when a request explicitly names several things to fetch, those calls go out in parallel. The failure zone is narrow and specific. When the next independent calls are implied by the task rather than explicitly requested — custom coding agents, bash-and-editor harnesses, computer-use loops — it may issue them one per turn.

The documentation is clear on one point: this does not reduce answer quality. The entire cost is that each extra turn spends tokens, a round trip, and wall-clock time. Which means it never shows up as a quality regression, only on the invoice and in perceived speed. The fix is one sentence appended to the current request.

{
  "role": "system",
  "clear_at": "next_user_message",
  "content": "First privately list what you need next; then request every item that doesn't depend on another's result in this one response."
}

The problem arrives when an ordering dependency is hidden. The only guardrail in that sentence is the clause that doesn't depend on another's result, and the model makes that judgment. Mix in tools that genuinely have an order which the schema does not expose — one that takes a lock before writing, one that reads a file an earlier call created, one that mutates state and another that queries it — and a batching instruction can walk straight over the dependency. The durable defense sits in the tools, not the prompt: state prerequisites in the description, and have the tool return an error on out-of-order calls.

There is also a rule about where the instruction goes. Each time you send tool results back, append a fresh copy after that user message as a turn-scoped system message, and leave the earlier copies byte-for-byte where they are. Once a later user message exists the API clears the earlier copies, so the model reads only the newest one, and cleared copies cost no input tokens. Deleting or rewriting them is an edit to earlier turns, which is the subject of the next section.

The conversation history became append-only

This is the item most likely to require actual code changes. The rule fits in a line: append each assistant turn exactly as the API returned it, thinking blocks included, and do not edit earlier turns between requests.

The enforcement boundary is explicit. For accounts created on or after August 31, 2026, Fable 5.1's thinking blocks are valid only in the exact conversation that produced them. A request that replays a thinking block after its prefix — the system prompt, the tool list, or any earlier message — has changed returns a 400 whose message says the block is bound to a different conversation. Accounts created earlier are not enforced yet, but the documentation says future models are expected to enforce the check for all accounts and to adopt the pattern now. Passing today is not evidence about tomorrow.

What trips the check and what does not is split into lists.

Invalidates every later thinking blockDoes not invalidate
Editing, reordering, or removing an earlier turn while keeping later onesRemoving a leading run of thinking blocks, oldest first
Injecting per-request reminders or status lines into an earlier turn and removing them next requestLetting server-side compaction or context editing trim the history
Rebuilding the top-level system prompt or tools array mid-conversationMoving cache_control markers
An image or document URL serving different bytes on a later request (the check covers bytes, not the URL)Changing effort between requests

A condition rides on the first row of the right column. Removing a thinking block from anywhere other than the start of the run invalidates every thinking block after it. The condition is oldest-first and contiguous, not merely old. Optimizations that snip out the middle do not hold on this model.

There is also a method for finding out what your own harness already edits. With the beta header thinking-binding-controls-2026-08-01 and the setting below, run one session and log input_transformations in the responses; it enumerates what was dropped and why. Model-binding mismatch entries after a model switch are expected. Prefix-binding mismatches are the ones to fix.

"thinking": {
  "block_binding": { "prefix_mismatch_behavior": "drop_block" }
}

A simpler check is offered alongside it. Capture the exact requests your harness sends over a few normal turns and confirm that consecutive requests are byte-identical up to the appended turns. It is faster than reading the code and it catches edits nobody knew they were making.

What to keep and what to drop in a long session

Making history append-only raises the obvious follow-up: then how do you shrink a growing conversation? The documentation's first answer is to let the server do the trimming. Server-side compaction and context editing do not count as edits, because the check compares the conversation as you sent it, so nothing they remove invalidates later thinking blocks.

If you keep compaction on the client, three shapes are sanctioned.

  • Simple compaction (recommended). Replace the whole history with one summary message plus the new user turn and replay nothing else. No thinking blocks carry over, so nothing can fail, and the model thinks afresh on the compacted conversation. The documentation notes that Claude models are trained on long-horizon tasks with this scheme and that it performs comparably to more elaborate ones for most workloads
  • Keep-tail compaction. If you keep the most recent turns verbatim behind a summary, you must strip the thinking and redacted_thinking blocks from those turns (text and tool calls can stay). That reasoning was produced against the full history and does not hold behind a summary
  • Background compaction. If the summary is built off the critical path and swapped in later, every turn produced in the meantime carries thinking that predates the swap. Send drop_block on every request still carrying pre-swap blocks, or compact synchronously instead

One thing is forbidden across all three. Do not snip individual turns out of the middle of the transcript. No client-side shape avoids it, the documentation states flatly.

There is a reversal in the cost calculus. Because Fable 5.1's cache reads dropped to 0.025x the base input price, the documentation says that compacting early to save cost may no longer be the right trade-off and suggests experimenting with later compaction points. If the pre-migration answer was cut long sessions early, the premise behind that answer has shifted. How to read plan limits and what actually drives cost is covered separately in how to read AI plan usage limits, and the design question of what belongs in the agent at all is in context engineering in practice.

If you build the summary yourself, the guide supplies a full summarization instruction. The gist is that six things must survive: difficulties that came up and how they were handled; options raised, tried, or set aside and why; anything asked for, decided, agreed, ruled out, or established as a constraint, stated exactly; exactly where things stand now; anything still open or promised; and specifics hard to reconstruct (names, numbers, dates, exact wording, links). It adds an instruction to weight the two voices differently. Keep what the user said close to their own words, and condense the model's own explanations and reasoning much further, down to what they concluded or produced.

Formatting - old suppression rules now cut the wrong way

The formatting change is unusual in that the direction flipped. Earlier models overused bullets and bold in chat, and many prompts still carry anti-formatting rules written to hold that down. Fable 5.1 leans the other way: it uses bold less and is less likely to reach for headers, lists, or quotation marks. Stack an old suppression rule on top of that and it presses down structure the content actually needs.

The prescribed fix is to remove those lines, or rewrite them from prohibitions into conditions: use lists when asked to or when the content is multifaceted enough that they help clarity; if the person explicitly requests minimal formatting, honor that; and keep to plain prose in conversational, personal, or emotional exchanges. Moving from do not use to use it when is the whole point.

Prose density is a separate item. Fable 5.1's writing carries fewer stock phrases and less unexplained jargon, but in some cases runs denser than Fable 5's, with longer sentences and fewer paragraph breaks. The prescription here is interesting: not write shorter but define the anti-pattern. Explain why mannered prose fails — it makes the reader work harder so the writer can perform, and metaphors drag in connotations the writer did not choose — and close with, when a literal phrase is available, use it. A short version reportedly works too.

Reproducing source text without marking it as a quotation is filed under formatting as well. When summarizing documents, Fable 5.1 is more likely than Fable 5 to reproduce passages unmarked. The fix is not a rule but one complete example: the user's request, the correct response, and a sentence explaining why that response is correct, all placed in the system prompt.

The remaining default changes the guide names

The remaining items are each short, but it pays to skim which of them lands on your workload.

  • The turn ends before the work does. On complex asynchronous workloads the model sometimes describes the next step instead of doing it, or stops to ask permission for a step the original request already covered. The documentation recommends two system prompt blocks together, noting that if you must cut length, the first alone keeps most of the effect. Within it, the opening sentence — that the user is not watching in real time — carries much of the weight
  • Unrequested fixes and tests come along. It may fix nearby code, extend behavior the task never mentioned, or commit more test files than the change warrants. Stating what to leave out drops unrequested additions substantially with no measurable change in task success, per the documentation
  • Whole files rewritten for small changes. The result is usually the same, but the rewrite costs more output tokens and time. One line — that tokens used to edit files are best minimized, all else being equal — brings small and medium changes back in line with Fable 5
  • Long deliverables truncated at xhigh and max. When a single request asks for a long deliverable, the model may draft much of it in thinking and then write it out again as the reply. Longer waits, double the output tokens. The first prescription is to run such requests at the recommended starting point, high; if you do go higher, size max_tokens for thinking plus reply, not the reply alone
  • Safeguard false positives. Three situations make them likelier: compile-check phrasing (ask are there any bugs in this program instead), lesser-known programming languages, and base64 data arriving through tool output. Finding vulnerabilities in source code is itself permitted

The migration procedure - what to hold constant for an A/B

Apply everything above at once and you will not know what changed what. There is one principle that makes a migration measurable: move one axis at a time.

StageWhat changesWhat is heldWhat is measured
0Nothing. Collect a baseline on current Fable 5EverythingQuality score, turn count, input and output tokens, time to first response, total wall-clock
1Model ID only, to claude-fable-5-1Prompt, effort, tool definitions, eval setThe same five metrics. The gap that opens here is the default behavior change
2effort only, swept across all five levelsPrompt, tool definitions, eval setQuality against cost and latency per level. This table becomes the basis for the production level
3Prompt, one item at a timeModel, effort (stage 2 conclusion), eval setPer-item effect. Removals of old suppression lines first, additions later

Stage one is the row most often violated, because changing the model makes it feel natural to touch the prompt while you are in there anyway. But only a clean stage one tells you whether the documented default changes actually appear in your workload. In one organization the drop in progress updates is a non-issue; in another it is the headline problem.

Not reducing the comparison to a quality score matters just as much. Many of the documented changes are designed not to show up in quality. Tool-call batching is described as not affecting answer quality, and the whole-file rewrite is described as usually producing the same result. Look at quality alone and both pass as no regression while cost quietly climbs. That is why the migration guide insists on re-baselining cost and latency on your own workloads alongside the re-evaluation. Token counts are roughly unchanged, but the cache read rate moved, so workloads with different session lengths and cache hit rates do not move in the same direction.

What pinning a model ID actually buys

Teams that care about reproducibility usually carry a rule: use the dated version ID, not the alias. If the alias silently repoints at a new snapshot, an eval that passed yesterday breaks today. In this generation the premise behind that rule has changed.

A footnote in the models overview states it. Every Claude model ID is a pinned snapshot, including the dateless IDs used from the 4.6 generation on. For models before 4.6 the alias was a convenience pointer resolving to a dated ID, but dateless IDs are their own pinned snapshot and the alias row merely repeats them.

So claude-fable-5-1 is not a name pointing at whatever is newest; it is the snapshot. There is no separate dated ID to hunt down for reproducibility, and hunting will not turn one up. Other rows in the same table still show dated forms (Haiku 4.5 has a dated API ID and a dateless alias), which makes it easy to skim the table and assume Fable 5.1 has one too. The trap in that table is that the rule differs by generation.

What deserves attention instead is elsewhere. A pinned ID does not mean the model is permanent. The retirement commitment is not sooner than September 1, 2027 on Anthropic-operated platforms, and Amazon Bedrock and Google Cloud set their own dates. The same ID has a different lifespan on a different platform. And reproducibility is not settled by the ID either: this model returns a 400 for any non-default temperature, top_p, or top_k, so there are no sampling dials to fix in the first place. The real version axes are effort, the system prompt, the tool list, and the conversation history. Without pinning those four, pinning the model ID buys little.

Wrapping up

The character of this migration compresses into one sentence: it is dangerous because nothing breaks. Swap the model ID and most of it keeps running, so no occasion to look again ever arrives. Meanwhile the prompt keeps sentences whose reason for existing is gone — old anti-formatting rules, hold-until-the-final-response suppression lines — and turn counts and output tokens climb somewhere nobody is watching.

The documentation has effectively set the order of work. Organization settings first (data retention, service tier), then whether your code edits the conversation history, then the effort sweep starting at high, and adding prompt sentences last. And the values here will not last long. The prices, IDs, and defaults were read on September 4, 2026, and the features behind beta headers — turn-scoped system messages, per-message effort, progress-update display, thinking block binding controls — are by definition the parts that can move. When the version number goes up by a decimal, the thing to reopen is not the release notes but your own prompt.

What I could not verify

  • The release date of Claude Fable 5.1 could not be confirmed. No launch date appears on the prompting guide, the what's-new page, the migration guide, or the models overview. The dates that do appear are different things. August 31, 2026 is the account creation boundary for enforcement of the thinking block conversation check, and the dates in beta headers (2026-07-01, 2026-08-01, 2026-08-18, 2026-08-21) identify individual betas. None of them were repurposed as a release date here
  • There is not a single benchmark score in this piece. The official pages referenced describe capability gains across six areas (long-session coding, documents and spreadsheets and slides, research and search, vision, long context, computer use) but give neither figures nor measurement conditions. Scores without conditions do not get used, so none were included
  • No supporting data was found for the claims that medium roughly matches Fable 5 or that low outscores other model families. Which eval sets, at which effort combinations, is not in the documents. Both are marked in the body as vendor claims and neither is used as a conclusion
  • A dated pinned version ID could not be shown to exist. The Claude API ID and alias columns of the models overview both read claude-fable-5-1, and the footnote describes the dateless ID as a pinned snapshot in itself. The assumption that a dated form exists somewhere was left out
  • Effect sizes are absent from the sources too. Unrequested additions dropping substantially, or average time to completion going down, are stated without percentages, so the body stays at the same level of precision
  • Claude Mythos 5.1 is limited to approved participants, so its behavior could not be observed. What the documents establish is that its specs and pricing match Fable 5.1 and that it alone does not run the conversation-binding check on thinking blocks
  • This piece was written by cross-reading documentation, not by reproducing each prescription against an eval set. The effect of prompt sentences in particular varies a great deal by workload
