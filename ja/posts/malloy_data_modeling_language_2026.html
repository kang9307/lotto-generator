Malloyとは何か - SQLの繰り返す結合と重複ロジックを解くデータモデリング言語

Looker創業者Lloyd Tabbが手がけた関係宣言型言語、SQLにコンパイルされ既存エンジン上で動く - dbt・LookML・Cubeと比較し、AI時代のセマンティックモデルの価値を分析する

2026-07-23 開発・インフラ

序論: SQLは今も痛い - なぜ再びデータモデリング言語なのか

データを扱ったことのある開発者なら、例外なく経験している場面がある。ダッシュボードごとに微妙に異なる「売上」の数字、結合を一つ間違えて2倍に膨らんだ集計、200行にも及ぶCTEの塊をスクロールしながら、そもそも何を求めるクエリだったのかを辿り直す瞬間。SQLは今もデータ世界の共通言語だが、「関係」と「意味」を一箇所に宣言して再利用することには今なお不器用だ。

最近hada.io(GeekNews)で紹介されたMalloyは、この長年の痛みへの答えを自任するオープンソース言語だ。本稿はプレスリリースをなぞる代わりに、公式ドキュメントとリポジトリを直接確認して文法を検証し、「セマンティックレイヤー」というより大きな潮流の中でMalloyがどこに位置するのか、そしてAIエージェントがデータを扱う今、なぜこの種の言語が改めて注目されるのかを筆者の視点から分析する。

1. Malloyとは何か - Looker創業者の二作目の言語

1.1 Lloyd Tabb、LookMLからMalloyへ

Malloyを理解するには、まず作った人物を見る必要がある。Lloyd Tabbは2012年にBen Porterfieldとともに Lookerを共同創業し、Lookerのデータモデリング言語LookMLを設計した人物だ。LookMLは「指標定義をバージョン管理下に置く」というアイデアを初めて商用化した言語であり、以降のセマンティックレイヤー論議全体の原型となった。2019年にLookerがグーグルに買収された後、TabbはグーグルのチームとともにNew言語の実験を始め、それが2022年に公開されたMalloyである。つまりMalloyは素人の趣味プロジェクトではなく、セマンティックモデリング言語を商用規模まで押し上げた経験を持つ人物が、その経験をもとに再設計した二作目の試みだ。

1.2 核心アイデアを一言で

Malloyは公式に「データの関係と変換を記述するオープンソース言語」であり、セマンティックモデリング言語とクエリ言語を兼ねる。決定的な違いは、これが新しいデータベースや実行エンジンではないという点だ。Malloyで書いたモデルとクエリはコンパイルされ、BigQuery・Snowflake・PostgreSQL・MySQL・Trino・Presto・Databricks・DuckDB・MotherDuckなど、すでに使っているSQLエンジンの上でそのまま実行される。現在malloydataのもとMITライセンスのオープンソースとして開発されており、GitHubで2,500以上のスターを獲得している。

2. SQLの長年の痛み - 何が問題だったのか

2.1 繰り返される結合と重複ロジック

SQLは関係を表現する言語というより、クエリのたびに関係を新たに書き下す言語に近い。同じ三つのテーブルを結合するクエリを、今週も来週も、別のメンバーもそれぞれ書き直す。結合条件を一箇所に定義しておき継続的に再利用する方法が、SQL自体には存在しない。その結果、結合ロジックは数十のクエリファイルにコピーされ、スキーマが変われば、そのコピーを一つひとつ探して修正しなければならない。

2.2 セマンティクスの不在 - 同じ指標名、異なる数字

より根本的な問題は、SQLには「意味」を置く場所がないことだ。「アクティブユーザー」や「定時到着率」のように組織が合意すべき指標も、SQLではその都度SELECT句に改めて書き下さなければならない。分析者Aがキャンセル分を除いて計算し、分析者Bが含めて計算すれば、同じ名前の指標がダッシュボードごとに異なる数字を出す。これはミスではなく、SQLがそもそも「指標の定義」という概念自体を持っていないために生じる構造的な問題だ。

2.3 長く読みにくいクエリ、そしてファンアウトの罠

結合が何重にも重なると、集計結果が静かに膨らむファンアウト(fan-out)・カズム(chasm)の罠もSQLの持病だ。例えば注文テーブルと配送イベントテーブルを結合してSUMを取ると、一つの注文に複数の配送イベントが紐づいている場合、売上が重複して合算される。SQL自体はこの危険を警告してくれない。結果の数字はもっともらしく見えるため、間違っていると気づくまでに時間がかかる。

3. Malloyのアプローチ - 関係をモデルとして宣言し、再利用する

3.1 sourceとextend - 一度定義して、ずっと使う

Malloyの出発点はsourceだ。一つのテーブルを指すsourceを定義し、extendブロックの中にそのテーブルに属する測定値(measure)・ディメンション(dimension)・結合(join)をまとめて束ねる。公式ドキュメントが示す例は次の通りだ。

source: airports is duckdb.table('airports.parquet') extend {
  measure:
    airport_count is count()
    avg_elevation is elevation.avg()
}

こうして定義されたsourceは、一つのファイルに生きた再利用可能なモデルになる。以降このモデルでクエリを書く人は、airport_countが正確に何を数えているのか改めて考える必要がない。

3.2 measure - 指標を名前の後ろに封じ込める

SQLなら毎回CASE WHENとフィルタを繰り返さなければならなかった「定時到着率」のような指標も、Malloyでは一度定義すれば名前で呼び出せる。公式リポジトリが示す例がまさにこの点を突いている。

measure: on_time_rate is
  count() { where: cancelled = 'N' and diverted = 'N' and arr_delay < 15 }
  /
  count() { where: cancelled = 'N' and diverted = 'N' }

キャンセル・迂回の有無と遅延基準というビジネスロジックが、たった一箇所に固定される。以降は誰でもon_time_rateを呼ぶだけでよく、定義を変えたければこの一箇所だけを直せば、その指標を使うすべてのクエリに反映される。

3.3 join_one・join_many - 結合をモデルに刻み、ファンアウトを言語レベルで防ぐ

join_one: carriers with carrier
join_many: flights2 on code = flights2.origin

結合をソース定義の中で一度宣言しておけば、以降のクエリは結合キーを書き直す必要がなく、関係でつながったフィールドを名前で参照するだけでよい。さらに重要なのは集計の方式だ。Malloyは複数のテーブルが結合された状態でも集計が重複計算されないよう、対称集計(symmetric aggregate)方式で計算する。結合が何重に積み重なっても、ファンアウトによって数字が膨らむ事故を言語レベルで防いでくれるということだ。SQLであれば開発者がDISTINCTやサブクエリで自ら防がなければならなかった問題である。

3.4 runとnest - クエリの中にクエリを、一つの結果の中に複数のグループを

run: airports -> {
  group_by: state
  aggregate: airport_count
  nest: by_facility_type is {
    group_by: fac_type
    aggregate: airport_count
  }
}

run:の後に続く->パイプラインは、ソースからクエリへとデータが流れる構造をそのままコードの形に移したものだ。nestは、SQLであれば別々のクエリを何度も投げるか複雑なGROUP BY ROLLUPを書く必要があった「一つの結果の中にサブグループ別の詳細を一緒に収める」ことを、一つのブロックで表現する。実行結果もフラットな表ではなく入れ子構造で返ってくるため、上位グループと下位グループの関係が結果そのものにそのまま残る。すでに作ったクエリはviewとして保存し、+ { }でつなげてさらに調整することもできる。この短い文法の断片一つひとつは、派手な新技術ではない。ただSQLが毎回最初から書き直させていたことを「一度定義して名前で再利用する」方向へ移しただけだ。その「だけ」が積み重なると、数十のクエリファイルが一つのモデルと短い呼び出しに集約される。

4. SQLにコンパイルされるということの意味 - 新エンジンではなくレイヤー

Malloyチームはこの言語をSQLの代替ではなくその上に載せるレイヤーだと説明しており、JavaScriptとTypeScriptの関係に例える。TypeScriptが最終的にJavaScriptにコンパイルされてブラウザで実行されるように、Malloyも最終的に各データベースに合わせたSQLにコンパイルされて実行される。この設計が重要な理由は導入コストにある。新しいデータベースや新しい実行クラスターを導入する必要がない。すでに使っているBigQuery・Snowflake・Postgres・MySQLの上にMalloyのモデルファイルを載せるだけでよく、ローカルでは別途サーバーなしでDuckDBによりParquet・CSVファイルを直接クエリできる。VS Code拡張機能を入れれば、スキーマエクスプローラー、ビジュアルクエリビルダー、結果プレビューまでエディタの中でそのまま使える。

5. 「セマンティックレイヤー」潮流の中のMalloy - dbt・LookML・Cubeと比較

5.1 系譜 - Lookerの遺産が分かれた三つの道

「指標を一箇所で定義し複数の場所で再利用しよう」というアイデア自体は新しくない。LookMLがその商用化の原型であり、以降セマンティックレイヤーという潮流が複数の道に分かれた。dbtは変換パイプラインの上にSemantic Layerを載せ、YAMLで指標を定義しdbt Cloud APIで配信する。Cubeは定義と配信を併せ持つヘッドレスセマンティックレイヤーで、API・埋め込み分析・AIエージェント連携を狙う。Malloyはこの潮流と系譜を共有しつつも、特定のBI製品や変換フレームワークに縛られない独立したオープンソース言語である点で異なる道を歩む。

5.2 何が違うのか

ツール形態依存関係実行方式
LookML独自言語Looker(BI)専用Looker内部でSQL生成
dbt Semantic LayerYAML指標定義dbtプロジェクトに依存dbt Cloud APIで配信
Cubeヘッドレスレイヤー別途配信インフラYAML/JS定義+API配信
Malloy独立オープンソース言語なし(MIT)SQLにコンパイル、既存エンジンで実行

5.3 冷静に見るべき点

hadaの議論で出た指摘のように、C# LINQのような既存言語も似た宣言的クエリ体験を提供するという反論は妥当だ。Malloyの差別化点は「まったく新しいものを発明した」というより、「セマンティックモデリングとクエリを一つの短い言語にまとめ、その結果をSQLエコシステムの上にそのまま載せた」という統合に近い。個々の断片は目新しくなくとも、まとめ方が異なる。

6. 実際に何が良くなるのか

再利用: 一つのsourceに測定値・ディメンション・結合を定義しておけば、以降のすべてのクエリがその定義をそのまま継承する。新しいクエリを書く人が毎回結合条件やフィルタロジックを再発明しない。一貫した指標: on_time_rateのような指標が一箇所にしか定義されていないため、ダッシュボードごとに数字が異なって出る事故が構造的に減る。定義を変えれば、その指標を使うすべてのクエリに一度に反映される。入れ子の結果: nestにより一つのクエリ結果の中にサブグループ別の詳細をそのまま収められるため、SQLであれば何度もクエリを投げてアプリケーション側で再結合しなければならなかった作業が減る。可読性: 対称集計のおかげで何重の結合の上でもSUM・COUNTを手作業で防御する必要がなく、クエリ自体が「何を求めているのか」をそのまま示す。レビュアーはサブクエリの塊を解読する代わりに、クエリの意図を直接読める。

7. 限界と導入の壁

エコシステム: SQLは数十年分のツール・チュートリアル・人材プールを持つ。Malloyは2022年に登場した言語で、VS Code拡張機能とmalloy-composer程度が主なツールであり、サードパーティのBI連携やコミュニティ規模はまだSQL・dbtのエコシステムに比べるべくもない。学習曲線: source/extend、measure/dimension、join_one/join_many、run/nestといった新しい概念とキーワードをチーム全体が改めて習得しなければならない。SQLをすでによく知るチームほど「なぜ新しい言語を学ぶ必要があるのか」という抵抗が生まれやすい。チーム標準の不在: セマンティックモデルは誰かが所有し保守しなければならない。これを立て守る担当者やプロセスがなければ、モデルファイルが新たなスパゲッティになるリスクがある。既存のSQL資産: すでに数百のビュー・ストアドプロシージャ・BIダッシュボードがSQLで組まれている組織であれば、それをMalloyモデルへ移す作業自体がコストになる。SQLを置き換えるのではなくその上に載せるという設計のおかげで段階的導入は可能だが、全面移行は別のプロジェクト級の決定だ。

8. AI時代、セマンティックモデルが再び重要になる理由

最近取り上げたWes McKinneyインタビュー分析と「データこそ唯一の堀である」分析で共通して指摘したように、AIがコード作成そのものを安くするほど、「何を作るか、何が正しい定義か」を判断する層がより重要になる。セマンティックモデルはまさにその判断をコードとして固定しておく層だ。

LLMに生のデータベーススキーマをそのまま開放すると、毎回新たにSQLを推論し結合を組み直し指標を定義し直す。この過程で存在しないカラムを参照したり、結合が誤って組まれファンアウトで数字が膨らんだり、指標の定義が毎回微妙に異なったりする誤りが繰り返される。結果のSQLは文法的には問題なく見えるため、誤っているという事実に気づくのがより難しい。

Malloy陣営から出たmalloyyoのようなプロジェクトは、この問題に直接答える。Malloyで定義しておいたセマンティックモデルをMCP(Model Context Protocol)経由でAIエージェントにそのまま提供し、エージェントがSQLを最初から新たに組む代わりに、すでに検証済みの測定値・ディメンション・結合を名前で要求するようにする。AIがアクセスできる範囲そのものがモデルの中に限定され、計算ロジックはすでに一度検証された状態で再利用されるため、結果は「たまたま正しい」ではなく「構造的に正しい」に近づく。

筆者の解釈はこうだ。モデルとコード生成が安くなるほど競争力はその上に積み上げた定義と判断に移るという論旨は、データ領域で特にはっきりと現れる。Malloyのようなセマンティックモデリング言語がAI時代に再び注目される理由は、機能が増えたからではなく、AIが参照する「すでに正しいと合意された定義」を作るためのツールだからだ。

9. どんなチームに向いているか、どう始めるか

9.1 どんなチームに向いているか

複数の分析担当者が同じ指標を毎回異なる方法で計算していたり、ダッシュボードごとに数字が微妙に異なったりする組織。結合が何重にもなったスキーマの上でファンアウト事故を頻繁に経験するチーム。AIエージェントにデータアクセスを開放しつつも、結果の正確性を統制したいチームに特に有効だ。逆にクエリが単発的でチーム標準化に割く余力がなければ、今すぐの利点は大きくないかもしれない。

9.2 始め方 - DuckDBでローカルに

始めるハードルは低い。VS CodeにMalloy拡張機能を入れ、ローカルのParquetまたはCSVファイルをduckdb.table()で指すsourceを一つ.malloyファイルに書くだけで十分だ。別途サーバーやクラスター、アカウントなしでノートPC上ですぐモデルを定義しrun:クエリを実行して結果を確認できる。感触がつかめれば、同じモデル定義をBigQueryやPostgresのような実際の運用エンジンへそのまま移して拡張すればよい。

結論

MalloyはSQLを押しのけようとする言語ではなく、SQLがそもそも得意でなかったこと - 関係の再利用、指標の一貫性、安全な集計 - を短い文法で埋めようとする試みだ。LookerとLookMLを商用化まで押し上げた人物が再設計した言語という経歴、SQLエンジンを置き換えずその上に載せる設計、そしてAIエージェントが参照する検証済みの定義を提供するという時代的な有用性まで重ねて見ると、Malloyは一度きりの実験を超えた潮流の一地点に見える。ただしエコシステムとチーム標準化という導入の壁は実在し、全面導入よりもファンアウトと指標の不一致が繰り返されるチームからローカルのDuckDBで軽く試してみる方が合理的だ。2026年7月時点、この言語がセマンティックレイヤー論争の勝者になるかはまだ早い。しかしSQLの長年の痛みを正確に突いている点だけは確かだ。
