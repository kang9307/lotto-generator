The Rise of Static Typing - Why It Has Been Back Since the Mid-2010s

Type Inference, Gradual Typing, and the AI-Coding Pressure Toward Types

Jun 13, 2026 Tech & IT

Introduction: The Typing Pendulum Swings Back

Take a long view of programming-language history and one question keeps swinging like a pendulum: how much should the language force you to declare types? From the late 1990s through the early 2010s, this was unmistakably the era of dynamic typing. Python, Ruby, JavaScript, and PHP became the default languages of the web and of startups, and a widespread sentiment formed that "type declarations are cumbersome ceremony." Then, around the mid-2010s, the current turned - quietly but decisively. TypeScript took over the JavaScript ecosystem, Rust rose as the darling of systems programming, and even Python embraced type hints.

This article takes as its starting point an analysis that circulated on GeekNews (news.hada.io): that the sharp rise of static typing since the mid-2010s is not a mere repetition of fashion but a reflection of genuine improvements in language systems themselves. We will calmly work through what separates static and dynamic typing, why dynamic typing once dominated, and what changed to bring static typing back. The short version up front: the static typing that returned is not the static typing of old. Two inventions - type inference and gradual typing - removed almost all of the friction, and the new pressures of large codebases and AI coding did the rest.

1. Static vs Dynamic Typing - The Basics

Let us set the foundation. The difference between the two reduces to one sentence: when are types checked?

  • Static typing: Before the program runs, at compile or type-check time, the types of all variables and functions are fixed and verified. If types do not match, the program will not even run. C, C++, Java, Go, Rust, and TypeScript belong here.
  • Dynamic typing: Types are decided at run time, based on the actual values. You run the code, and when it hits an operation with mismatched types, that is when the error appears. Python, Ruby, JavaScript, and PHP are the classic examples.

A commonly confused axis is "strong vs weak typing," which is something different: it concerns how much implicit type coercion the language allows. JavaScript is dynamic and weakly typed, so "3" + 1 becomes "31"; Python is dynamic but comparatively strongly typed, so the same operation raises an error. This article is about the static-vs-dynamic axis.

A minimal example to build intuition:

# Dynamic typing (Python) - looks fine before running
def add(a, b):
    return a + b

add(1, 2)        # 3
add("a", "b")    # "ab"  -- same function, entirely different meaning
add(1, "b")      # TypeError, only at run time!

// Static typing (TypeScript) - caught before running
function add(a: number, b: number): number {
  return a + b;
}

add(1, 2);     // OK
add(1, "b");   // compile error: Argument of type 'string' is not assignable to 'number'

The crux is the last line. In dynamic typing, add(1, "b") hides until it actually executes, then blows up; in static typing, the editor draws a red underline the moment you write it. This difference - when you meet the error - is the root of everything that follows.

2. Why Dynamic Typing Was Once the Fashion

To understand why static typing came back, we must honestly account for why dynamic typing was so beloved. Its popularity was no accident.

First, speed of writing and flexibility. Turning an idea into running code without any type declarations was an overwhelming advantage for prototyping and scripting. In the late 2000s, when startups shipped fast and validated faster, the "just make it run" culture meshed perfectly with dynamic languages.

Second, the pain of static typing at the time. The dominant static languages then were Java and C++, which required declaring every type by hand. Verbose declarations like Map<String, List<Integer>> m = new HashMap<String, List<Integer>>(); seared the impression that "static typing equals tedious ritual." What people rejected was not static typing itself so much as the terrible developer experience of static typing in that era.

Third, the explosion of the web. JavaScript, the browser's only language, was dynamic, and on the server PHP, Ruby on Rails, and Django lifted web-development productivity. Dynamic languages rode the defining wave of their time.

What people turned away from in the 2000s was not "types" but "the cost of declaring types." Remove that cost, and the whole story changes.

3. The Cost Dynamic Typing Revealed - When Code Grows

The advantages of dynamic typing shine when code is small. The problems surfaced as codebases grew to tens and hundreds of thousands of lines, as teams expanded, and as code survived for years. The cost dynamic typing had deferred started arriving with compound interest.

  • Refactoring fear: When you want to rename a function or change an argument, the compiler does not guarantee where and how it is used. You cannot tell whether the change will silently break something, so in a large dynamic codebase refactoring itself becomes frightening.
  • Absent documentation: What types a function accepts and returns is not stated in the code. A new engineer has to dig through call sites or run things to guess.
  • Bugs that explode late: Type-mismatch errors surface not during development but in production, often on a rarely traveled code path. A None/undefined flows somewhere unexpected and triggers an incident at 3 a.m.

All three are problems of scale. They are barely felt in a 200-line script you write alone, but they are deadly in a 500,000-line service maintained by fifty people over five years. By the mid-2010s, many companies' codebases were crossing exactly that threshold. It is no coincidence that Facebook built Flow (a type checker for JavaScript), Microsoft built TypeScript, Dropbox built mypy for Python, and Stripe released Sorbet for Ruby. Companies saddled with huge dynamic codebases reached, as if by agreement, for the same prescription.

4. Decisive Invention 1 - Type Inference

So why was static typing accepted this time without resistance? The first answer is type inference: the ability of the compiler to figure out types from context, so the developer does not have to spell them out everywhere.

The idea itself is not new. Hindley-Milner type inference, used by the functional languages ML and Haskell, is a decades-old algorithm that can reconstruct the types of an entire program with almost no annotations. As analysts note, it sits at a sweet spot of language design: highly expressive, yet inferable automatically. The new languages of the 2010s pulled this old wisdom into the mainstream.

// Rust - type inference makes declarations light
let count = 42;                 // inferred as i32
let name = "BrainDetox";        // inferred as &str
let scores = vec![90, 85, 88];  // inferred as Vec<i32>

// at function boundaries we annotate -> it becomes documentation and a contract
fn average(scores: &[i32]) -> f64 {
    let sum: i32 = scores.iter().sum();
    sum as f64 / scores.len() as f64
}

The sense of balance matters here. Modern languages typically infer local variables but require annotations at function boundaries (arguments and return types). The fussy types inside a function are left to the compiler, keeping the code light, while boundary types are stated explicitly to serve as documentation and contract. This compromise decisively demolished the old impression that "static typing is verbose." The code is as terse as a dynamic language, yet the safety net stays.

Type inference is not omnipotent, though. Generally, in highly expressive areas such as higher-rank polymorphism, inference hits its limits and explicit annotations are required. So modern type inference aims for a pragmatic balance: not "all automatic" but "the tedious parts automatic."

5. Decisive Invention 2 - Gradual Typing

The second answer is gradual typing, and it may matter even more. If type inference lowered the cost of static typing, gradual typing tore down its barrier to entry.

Gradual typing lets you freely mix statically and dynamically typed code in a single program. You do not have to annotate everything at once. You type the most important and most dangerous parts first and leave the rest dynamic, migrating slowly over time. As analysts put it, the core value of this approach is enjoying the safety of static typing and the flexibility of dynamic typing within one codebase.

Why is this revolutionary? Because it opened a path to introduce safety incrementally into existing dynamic codebases of millions of lines. Had TypeScript demanded "convert all your JS to types at once before you can use it," no one would have adopted it. Instead, TypeScript accepts existing JavaScript as-is and lets you add types one file, one function at a time.

// gradual typing - start with any, then narrow
function parseConfig(raw: any) {   // any at first (no better than dynamic)
  return JSON.parse(raw);
}

// later, add types to raise safety
interface Config {
  port: number;
  host: string;
  debug?: boolean;
}
function parseConfigTyped(raw: string): Config {
  return JSON.parse(raw) as Config;
}

Python's type hints (PEP 484) follow exactly the same philosophy. Type hints are optional. Code runs without them, and when you attach an external checker like mypy or pyright, verification begins. It is a clever compromise that borrows the benefits of static typing without violating the soul of a dynamic language.

6. Gradual Typing Has Traps Too

For balance, the other side. Gradual typing is not free. Subtle dangers lurk at the boundary between static and dynamic code.

The biggest problem is that types can lie. TypeScript's types vanish after compilation (type erasure) and are not enforced at run time. If you assert an external API response with as Config but the actual data differs, the type checker says "safe" while the runtime quietly passes wrong values through. Researchers generally warn about these "unexpected dangers of gradual typing": the static-dynamic boundary can create an illusion of safety.

The practical lesson is clear. At boundaries where untrusted input arrives (network, files, users), you need actual runtime validation (e.g., zod, pydantic) rather than a type assertion. The type system preserves the consistency of "the code I wrote"; it does not guarantee that "data coming from outside" keeps its promises.

7. Back to Static - TypeScript, Rust, and Type Hints

Now let us confirm the trend with concrete cases. The "return to static" since the mid-2010s shows up clearly along three strands.

7.1 TypeScript - Becoming the Web's Standard

TypeScript, released by Microsoft in 2012, adds gradual static typing to JavaScript. By analysis, its usage roughly tripled, from about 12% in 2017 to 34% in 2022, and in 2025 it is reported to have overtaken both JavaScript and Python by GitHub contributor count to reach first place. That the front end - the home turf of dynamic languages - moved to static typing is a symbolic event.

7.2 Rust - A New Standard for Systems Programming

Rust, which reached 1.0 in 2015, achieved "memory safety without a garbage collector" through strong static typing and an ownership system. In the systems domain long held by C/C++, the fact that types and a borrow checker guarantee memory safety at compile time drove adoption. Rust's popularity spread the perception that static typing is tied directly to safety. For deeper context, continue with the guide to migrating from Go to Rust.

7.3 Python Type Hints - Optional Armor for a Dynamic Language

Python introduced type hints with PEP 484 (2015) and grew an ecosystem of external checkers like mypy and pyright. In one survey, mypy is reported as the most widely used checker at around 58% adoption. Even the flagship dynamic language opened a path to "borrow static typing when needed."

Language/Tool Arrived Approach Problem solved
TypeScript 2012 Gradual static typing Maintaining large-scale JS
Rust 2015 Strong static typing + ownership Memory safety without GC
Python type hints 2015 Optional gradual typing Documentation and checking for dynamic code
Sorbet (Ruby) 2019 Gradual typing Safety for large Ruby codebases

8. A New Pressure - AI Coding and Types

If the 2010s return was driven by "large codebases," the 2020s added an entirely new pressure: AI coding. And this pressure tilts strongly in favor of static typing.

The crux is simple: LLM-generated code is often wrong. It calls functions that do not exist, confuses argument order, or passes the wrong types. Here the static type system acts as a safety net that filters that wrong code out before it runs. One study reports that about 94% of compilation errors in LLM-generated code were type-check failures. Put the other way, the type system automatically catches most of the AI's mistakes at the compile stage.

GitHub analyzes this more directly: types provide "guardrails" for LLMs, and this even shapes developers' language choices. The reported interpretation is that the spread of AI tools is part of why TypeScript reached first place among GitHub contributors in 2025. Code with clear types is easier for AI to understand and easier to verify. The proposition that "types matter more in the AI era" is increasingly backed by data.

Key point
The more AI writes code, the more it matters to have a way to verify that code before it runs. Static typing turns compilation into a first-class safety filter, blocking the AI's mistakes before they become production incidents.

9. The Real Benefits of Static Typing

Let us recast the trend from the angle of "what developers actually gain." The benefits of static typing are not abstract elegance but concrete productivity.

  • Early bug detection: Type errors are caught at writing time, not in production - the cheapest moment to fix the most common class of mistakes.
  • Fearless refactoring: Change a function signature and the compiler red-lines every affected call site. A large structural change shifts from "gamble" to "checklist."
  • Living documentation: The type signature is documentation that is always current. def fetch(url: str) -> Response is more precise than a comment and never drifts out of sync with the code.
  • Powerful IDE support: With types, autocompletion, go-to-definition, and safe renaming become accurate. Everyday coding speed rises noticeably.

What these benefits share is that they all grow as time passes and scale increases. In a short-lived prototype, dynamic typing's speed wins; in a long-lived system, the compound interest of static typing wins. This dovetails with a conservative approach to technology choice; for the broader discussion, see choose boring technology in the AI era and the native rewrite of the TypeScript compiler.

10. Do Not Over-Trust - Types Are Not a Silver Bullet

Now let us firmly hang the counterweight on the other side. If the revival of static typing curdles into blind faith - "just add types and it is safe" - that itself becomes a new trap. You must know precisely what types do not catch.

  • Logic errors: Types will not catch using - where you meant +. If both values are number, the type checker is satisfied. Errors in business rules are outside the realm of types.
  • Race conditions and side effects: Concurrency bugs, wrong state mutations, and mismatches with external systems are mostly not expressible in types.
  • Wrong modeling: If your types model reality incorrectly, the type checker happily passes "consistently wrong" code. Types only preserve the consistency of the rules you defined.
  • Lies at the boundary: As section 6 showed, if you assert external data without validating it, types give false reassurance.

So static typing does not replace testing. Types handle the consistency of "shape," tests the correctness of "behavior," code review the soundness of "intent," and observability the reality of "operations." These four are not competitors but layered lines of defense. Trying to solve all quality with types alone is as unbalanced as the old sentiment that blindly rejected dynamic typing.

11. The Balance a Developer Should Strike - Practical Guidance

So what stance should a developer take amid this trend in 2026? There is no need to turn "static vs dynamic" into a religious war. Here is a pragmatic, context-fitted balance.

  1. The longer code will live, the more it should be typed. A throwaway script can stay dynamic and fast; a service maintained for years should be hardened with static types. The expected lifespan of the code is the first criterion.
  2. Adopt incrementally. Do not try to convert an existing dynamic codebase all at once. Type the most dangerous, most frequently changed core modules first, then narrow any over time. That is the realistic path.
  3. Add runtime validation at boundaries. Where external input arrives, use actual validation (zod, pydantic), not a type assertion. Types and validation play different roles.
  4. Use types as documentation and a design tool. Boundary types are the most accurate documentation. Good type design makes invalid states unrepresentable, structurally removing the room for bugs to enter.
  5. But do not lean everything on types. Passing the type checker does not make code correct. Keep tests and review alongside. A successful compile is a "start," not a "guarantee."

12. Conclusion + 3 Things You Can Apply Today

The rise of static typing is not a simple swing of the pendulum. It is the result of type inference removing the cost of static typing, gradual typing tearing down the barrier to entry, and large codebases plus AI coding newly raising the value of types. The static typing that returned is not the verbose static typing of the 2000s but a new species that holds both the terseness of dynamic languages and the safety net of static ones. And in an era where AI writes more and more code, the value of types - as the ability to verify before running - is likely to grow further.

Three things you can apply today:

  1. Type the core modules first. Not everything - the most frequently changed and most dangerous parts. That is where gradual typing yields the greatest effect for the least effort.
  2. Put runtime validation at the boundaries. Data from outside is not made safe by a type assertion alone. Verify it "for real" with a validation library.
  3. Do not treat types as a silver bullet. Even when types pass, you still need tests and review. Types are one of several lines of defense, and they work best alongside the others.
