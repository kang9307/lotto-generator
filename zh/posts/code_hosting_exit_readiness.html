引言：一次clone究竟带来了什么

合并请求页面打不开。可是在终端里git push照样通，git fetch也毫无问题。碰上这种日子，开发者最先说的话大体相同：要不要搬走。

回答之前有件事得先定住。搬走这个词指的到底是搬什么，通常没有被定义过。搬仓库只是一条命令，分布式版本控制的设计本来就是如此。问题在于，团队三年里积累的东西当中，装在仓库里的只有代码和提交日志。八百条议题以及挂在上面的讨论、评审里写清了某一行为何要改的评论、工作流引用的密钥与运行器、每个标签上挂的安装包、四十页Wiki、定义谁能访问什么的团队结构。锁定不在仓库里，而是堆积在仓库周围。

所以本文不是在比较哪家更好。它把资产一件件摆开，给哪些能由机器导出、哪些导得出来但格式被压坏、哪些根本导不出来打分。先把自己弄到能搬的状态，至于搬不搬，到时候再决定也不迟。锁定的一般原理已在AI服务的分层依赖和把保管外包后的访问权里讲过，这里不再重复。

1. 故障暴露的不是可用性

2026年8月17日，状态页上挂出了一起事件。值得留意的不是持续时长，而是受影响组件的清单。编码助手、API请求、Git操作、议题、合并请求、页面、Webhook、动作并排列在同一行。前几天也类似。8月13日的Webhook事件把Git操作、议题、软件包和合并请求一并牵进去，8月12日登录和发布资产下载一起出现波动。

这份清单说明的不是某家公司多久停一次，而是你的一天同时压在多少种不同功能上。取代码、读评审、跑构建、下载发布文件、登录，这些事若都能落进同一家厂商的同一起事件里，那在可用性之前先是耦合度的问题。

同一天社区讨论串里的一条观察把这个区分说得很准：网页界面上合并请求打不开的那段时间，命令行里合并照样能完成。分布式的代码层活着，叠在它上面的协作层停了。这不是巧合而是结构，而这个结构正是本文的主题 — 活下来的那一层，就是容易搬走的那一层。

  • 状态页上的绿灯不是正常的证据，而是尚未定级的信息。用户的症状反馈大体早于公告
  • 只因为可用性就搬家，多半以失望收场。任何服务都有事件历史，搬过去只是把你看到的历史清零重来
  • 反过来，为降低耦合度而做的整理，无论人在哪里都留得下。就算最后决定不搬，收益照样在

2. 按资产梳理迁移难度与应对

先把地图铺开。下表按能否由机器导出和搬过去之后还剩什么问题把资产分开，难度低的行排在上面。

资产怎么取出来搬迁时残留的问题今天就能做的准备
代码、分支、标签、历史镜像克隆、bundle文件基本没有留一份镜像副本
Wiki作为独立仓库克隆几乎没有纳入镜像
议题正文、状态、标签API、归档、导入工具重新编号会让交叉引用错位保存原始响应
议题与PR评论同上非常旧的评论，超大议题有缺失报告周期性快照
发布产物资产列表API下载地址会变，别人挂的链接会死二进制副本与校验和
大文件对象单独路径归档的排除项另行备份
PR评审评论导得出，但位置字段一起跟来行位置与讨论串结构无法原样安放连差异片段一起保存
文件级评论归档的排除项可能根本没有落脚点把结论升格为议题
CI配置文件在仓库里，会跟着走语法、运行器、密钥、外部动作都属于对方把实际工作下沉为脚本
必需状态检查文档明确写着不会迁移规则会悄无声息地消失把规则清单写进文档
权限与团队结构团队包含在内，外部认证映射排除账号比对最终还是人工活把权限表写成仓库内文件
派生关系不会迁移没有恢复办法接受它

用一句话概括：上面四行靠几乎零成本的准备就能彻底解决，下面五行无论准备得多好都会留下损失。可是讨论迁移时，时间大多花在上半部分。镜像放哪里能聊很久，评审评论的行位置会变成什么样，往往搬完之后才发现。

2.1 代码和历史真的很容易

这一段之所以短，正是本文的论点。在分布式版本控制里代码早已在每个人的笔记本上，剩下的只是把所有引用一个不落地取回来。

# 分支、标签、远程引用，全都要
git clone --mirror https://host.example/org/repo.git

# 固化成一个文件
cd repo.git
git bundle create ../repo-full.bundle --all

# Wiki是独立仓库
git clone https://host.example/org/repo.wiki.git

bundle值得一看。官方文档给出的用途就是整个仓库的备份和无网络搬运。产物是单个文件，放哪里都行，日后还能直接以该文件为对象克隆；也能生成只含上次bundle之后变更的增量包。Wiki是独立仓库这一点同样鲜为人知 — 在仓库地址后面加上Wiki后缀就能克隆，本地改完推到默认分支即生效。它是迁移难度最低的资产，却几乎总是从备份清单里漏掉，因为它不出现在仓库列表里。

3. 议题与讨论 - 导得出来，但后面还有事

从这里开始性质变了。议题和评论用API导得很顺，问题出在导出之后。

最准确的信息源反而是接收方的文档。要搬去的那家服务的导入文档，通常会写明什么进不来。GitLab的GitHub导入文档写着，议题、合并请求、评论、评审、标签、里程碑、Wiki、发布说明、大文件对象都能广泛导入。同一份文档里还并列写着下面这些。

  • 组织或群组层级不会迁移。你导入的是项目，不是组织结构
  • 必需状态检查进不来。文档直接写明需要手动重新创建
  • 2017年之前的部分评论可能因API限制而丢失，评论数以万计的议题上也有问题报告
  • 正文中嵌入的合并请求交叉引用无法保留，因为导入时目标编号尚未确定

最后一行在实务上最疼。在议题正文里写上另一条议题编号作为引用，这是到处都有的习惯。一旦在新实例上重新编号，那些引用要么指向错误的地方，要么什么都不指。文字还在，所以连坏掉的迹象都看不出来。没有哪个团队能用手工修完三年的讨论。

发送方的文档也要一起看。GitHub的迁移归档文档写明会迁移议题、合并请求、Wiki、发布、评论、评审、里程碑、保护分支设置、部署密钥和启用中的Webhook，同时记着派生关系、大文件对象和外部认证映射属于排除项。先读导不出来的部分，比先读导得出来的部分更有用。结论很简单：不要把导入工具放在计划的中心。工具在搬迁当天用一次，成绩取决于对方的实现。你能掌控的只有手里是否留着一份原始响应。

4. 评审评论 - 形式消失的地方

这里是数据导得出来、意义导不出来的唯一一类资产，因此是本文最重要的一节。

一条评审评论带着的不只是文字。位于哪个文件的第几行、差异的哪一侧、若是多行则起点在哪、以哪次提交为基准、若是回复则父级是谁，全都一起挂着。用字段名来说就是path、line、side、start_line、commit_id、in_reply_to_id，以及作为上下文截取的差异片段diff_hunk。

关键在于这些值以某次提交时刻的差异为前提。因此文档里附着这样意思的警告：后续提交一旦碰到你指定的那一行，该评论就会被标记为已过时。旧写法的position字段数的不是文件真实行号，而是从差异标头往下数第几行，如今正在转向line。把这些搬到别的服务，意味着要把这套坐标重新安放到该服务的差异计算和讨论串模型之上。坐标系不同，就安不准。

  • 评论正文能活下来。文字搬到哪里都行
  • 挂在哪一行会变模糊。文件层面或许还在，行级精度得不到保证
  • 回复关系可能被压平。三条讨论串躺成十二条评论的列表
  • 多行范围的选择，若目标方没有同样的概念，就会折叠成单一起始行
  • 挂在整个文件上的评论可能没有落脚点。归档文档把文件级评论列为排除项

应对只有两条，而且都得在搬迁之前做。第一，导出时务必包含diff_hunk。有了差异片段，即使行号错位，人也能读着把上下文还原回来。第二，把评审里得出的结论从评论中升格出去。定了哪条规则、为什么这么定，写进议题或仓库内的文档，就能与坐标系无关地活下来。评审讨论串本来就是易失介质 — 只存在于其中的决定，连时间都扛不住，更别说迁移。

5. CI - 搬的不是语法而是耦合

CI配置文件在仓库里，取镜像就跟着走，所以看上去很容易。实际上它属于重写成本最高的一类，因为要搬的不是文件，而是这个文件所预设的一切。

  • 外部动作引用。一行就能调用别人写好步骤的便利，只在那个生态内部成立
  • 运行器镜像里已经装好的工具。你没装过的命令能跑，全靠运行器，而这件事配置文件里没写
  • 密钥的注入方式与命名。值就不说了，注入时机和作用域规则各家都不一样
  • 缓存键与产物保留规则。如果构建时间减半的原因在这里，搬过去第一天就会翻倍
  • 触发条件的含义。某个事件何时发生，定义上存在微妙差别

解法很旧，也不特别：把实际工作下沉到仓库里的脚本，CI配置只留下调用脚本的薄壳。

# CI配置里只留这么多
steps:
  - run: ./scripts/build.sh
  - run: ./scripts/test.sh
  - run: ./scripts/package.sh

# 判定标准：在断网的笔记本上
./scripts/build.sh   # 产物相同即可移植

判定标准只有一条，争论就结束了。在笔记本上用同一条命令得到同样结果就是可移植的，只在CI界面里才跑得起来的步骤，有多少就被绑住多少。讨论串里经常有人抱怨CI语法复杂，但抱怨的对象若是语法，那就是耦合的症状。换到语法更简单的地方，只要逻辑还留在配置文件里，下次搬迁照样要再付一遍同样的成本。这里还要补上必需状态检查。导入工具的文档写明不会搬运它。也就是说搬完第二天合并规则可能已经没了，而消失的规则不会在任何画面上留下痕迹。把规则清单写成文档就是全部的应对，成本是十分钟。

6. 发布、Wiki、权限 - 各有各的漏法

挂在发布上的二进制文件可以用API取列表并逐个下载。用发布标识符查询资产列表，每个资产要么走浏览器下载地址，要么把请求头改成接收二进制流。文档提醒响应可能以重定向的形式返回，客户端两种情况都要处理。

技术上不难，真正的问题是地址。下载地址里含有主机名，而过去五年别人把这个地址写进了文档、脚本和安装说明。托管一搬，文件跟得走，但那些链接全都会死。如果项目有分发物，更好的做法是在自己的域名下放一条稳定的下载路径并对外公布。无论背后指向哪里，外面看到的地址都不变。

权限的性质又不一样，这是留给人而不是留给机器的一段。

  • 归档里包含团队和组织，但外部认证映射被排除。如果之前绑定了身份提供方，那条连接要重新搭
  • 接收方也写明不迁移组织与群组层级。角色名称和权限粒度不同，必然存在无法一一对应的区段
  • 最终账号比对是人来做的。四十人是一天，四百人就成了一个项目。应对办法是把权限结构写进仓库里的文件
  • 派生关系不会迁移，文档说得很死。既然无从准备就接受它。不过对开源项目而言损失不小，因为贡献流程本身就建在派生之上

7. 把名字握在自己手里

这一节是所有准备里最便宜也最耐久的一项，而人们往往做得太晚。

对于要分发软件包的项目，名字往往就是地址。Go模块是最典型的例子。官方文档把模块路径定义为模块的正式名称，同时写明这个路径用于定位仓库，而路径的首段按惯例是域名。也就是说，如果你把托管地址直接当作模块路径，搬迁的那一刻，全世界的导入语句就都错了。解法是个老做法：用自己的域名当模块路径，再让这个域名指向真实仓库。别的语言生态原理相同 — 只要确认名字的所有权在谁手里就行。

  • 域名。把文档站点、下载路径、议题跟踪入口都收拢到自己的域名之下。后面换了，前面不变
  • 软件包命名空间。提前占下以组织名命名的作用域。绑在个人账号上的名字，日后很难一起搬走
  • 导入路径。检查主机名是否被写死在代码里。若是，那就是你最强的锁定
  • 邮箱地址与提交签名。如果一直用托管方签发的地址提交，历史里的作者身份就被绑在那个服务上

这四件事即便没有搬迁计划，现在做也更划算。成本几乎为零，而拖到以后，已经扩散出去的东西会让你做不成。

8. 让定期导出真正跑起来

把前面所有内容压缩成一项工作，就是定期导出。不是备一次的备份，而是周期性运转的东西，最重要的是偶尔真的拿它恢复一次。

对象周期形式成本
仓库镜像每天包含所有引用的克隆近乎为零
bundle快照每周一次单个文件近乎为零
Wiki每天独立仓库的镜像近乎为零
议题、PR、评论每周一次API原始响应原样保存低
评审评论每周一次含差异片段低
发布资产每次发布二进制与校验和低
权限与检查规则每月一次给人读的表格低
恢复演练每半年一次真的往空实例里装一遍中等

只有最后一行成本算中等，其余靠一套脚本加定时任务就完事。可是真正价值的一半就在最后那一行。从没恢复过的备份，只是一个叫作备份的文件。每半年一次，把镜像推进空实例，再用议题快照造几条出来，什么跑不通当天就全暴露了。

一个常见错误。把导出放在CI里跑，那么CI停摆的那天，导出也跟着停。而你需要导出的正是那一天。定时任务的原则是放在你打算离开的那个对象之外。

9. 自托管向你收取的账单

讲到这里，自托管看上去像是结论。拿回控制权确实成立，只不过成本不会消失，只会转移。把它去了哪里摆成表格，判断就容易了。

项目外包时自己运维时
安全补丁厂商负责处理你的排期。运维多年的人说几乎是按周应对
可用性厂商的责任，你等着就行你的值班。凌晨的告警打到你的手机上
升级大体自动你的计划，停机窗口要和团队协商
备份与恢复厂商的副本加你的副本全是你的，恢复验证也归你
垃圾内容与滥用厂商公开实例的话，这会变成常态工作
贡献者流入搭上大网络的便车要自己造，这一项最贵
控制权低高。你付代价买的就是这个

下面两行才是判断的核心。社区效应不会迁移。这也是讨论串里反复出现的指摘 — 有人讲搬走的项目遭遇了贡献下滑，也有人讲整个生态都住在一个地方，个人退出没有意义。这是人往哪里看的问题，选个好工具解决不了。

所以标准这样定，多半不会错：自托管站得住的理由是合规要求、内网访问、数据管控和成本结构。可用性和可迁移性不在这份清单上。可迁移性无论人在哪里，用定期导出和脚本化来保障都便宜得多，而没有导出的自托管，不过是多了一个没有备份的单点。这两天讨论串里被提到的选项，横跨自建型、托管型、联邦型和分布式型，有好几路。哪一路更好，本文不做评判。但有得选和搬得走是两回事，本文谈的是后者。

结论：今天带走的三点

第一，能不能搬，是靠一份清单来判定的，不是靠仓库副本。代码早已安全。危险的是议题编号错位、评审坐标变模糊、合并规则无声消失、发布链接失效。写这份清单只要三十分钟，写完之后该准备什么自然就定下来了。

第二，最便宜的四项准备，今天之内就能做完。仓库与Wiki的镜像副本、议题与评审评论的原始快照、把CI逻辑下沉为脚本、把域名与命名空间握在自己手里。这四件事即便没有搬迁计划也是净收益，而且都是拖得越久越贵。尤其最后一件，等分发铺开之后就基本做不成了。

第三，故障是叫你去数一数的信号，不是叫你搬家的信号。如果一起事件能把代码、评审、构建、部署和登录一并牵进去，问题就不是那家厂商的在线率，而是你的一天有多少根线拴在同一个地方。而解开这份耦合的工作，即使决定不搬也照样留得下。争取可迁移性的目的不是迁移，而是拥有选项；有了选项，紧急时刻就不必仓促决定。
