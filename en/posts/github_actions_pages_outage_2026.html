Introduction: worse than a red workflow

When a large outage hits, the screen usually turns red. Failed jobs, retry buttons, jobs wedged in a queue that will not move. And yet the most expensive loss in the GitHub Actions outage of 6 August 2026 was not anything marked red. It was the run that never showed up in the list at all.

Closing the incident, GitHub said that some workflow-triggering events, including push and pull request events, had not been processed and cannot be replayed automatically. Failure is visible; absence is not. A commit with an empty checks list is hard to distinguish on screen from a commit that passed. And once such a commit is merged, the outage ends but the result stays.

This is not an outage report. The incident itself is summarised quickly, and the rest goes to what it actually costs to hang your whole deployment path on a single company. What stops and what keeps running, how to separate a provider problem from your own when the status page says everything is fine, and why a hobby site building multi-cloud is a net loss.

This is not an Actions how-to. Workflow syntax, trigger types, jobs and steps are covered in GitHub Actions & CI/CD - Git & GitHub Master Part 5. What follows deals only with the judgement calls for when the platform those workflows run on has stopped.

1. A timeline built only from the official record

Later articles and community summaries disagree slightly on times. What follows is drawn only from the incident updates left on the GitHub status page. All times are UTC; add nine hours for Korean time.

1.1 Opening and closing

  • Incident opened: 15:22 UTC on 6 August 2026. The first wording said reports of degraded performance for Actions were being investigated
  • Impact level: critical. Two components were recorded, Actions and Pages
  • Mitigation declared: 00:05 UTC on 7 August. Immediately before it, at 00:01, an update said system-wide queues had drained and new jobs were being processed
  • Incident closed: 02:04 UTC on 7 August. The full window is 10 hours 42 minutes
  • In Korean time that is an opening at 00:22 on 7 August and a close at 11:04 the same morning. By the time the Korean working day began, the incident was already in its recovery tail

1.2 The stretch where Pages went down twice

Pages was not in the incident from the start. It joined about half an hour later, returned to normal once, and then went down again.

1.3 What the recovery curve tells you

A success rate that climbed from 30-40 percent to 65, then to 97 and 99, means this was not a recovery you get by flipping a switch back on. It was a drain-the-queue process that lifted the share of successful processing bit by bit, which is why individual users at the midpoint experienced pure luck.

  • During recovery GitHub deliberately throttled webhook throughput. It was a measure to aid recovery, and an update put throughput at roughly 15 percent of normal at one stage
  • While webhooks were throttled, pushes and pull requests were not producing new workflow runs
  • Other affected areas named during recovery included Copilot code review, the Copilot coding agent, hosted runners, self-hosted runners, webhook deliveries, and migrations using GitHub Enterprise Importer
  • A separate note said customers running self-hosted runners might see errors or rate limiting when runners register. That single line shows that putting runners on your own side does not remove the dependency on the control plane

2. What actually stops when Actions and Pages stop

To design any preparation you first have to draw the blast radius accurately. The common mistake runs in two directions. One is assuming that if GitHub is down, everything is down. The other is assuming that a static site is unaffected. Both are wrong.

2.1 What stops

  • New deployments. If Pages deploys run through an Actions workflow, deployment is CI. When Actions stops, no new post and no new version goes up
  • Merge gates. Repositories with required status checks cannot merge while checks are not running. This is the safety mechanism working correctly, not a bug
  • Release automation. The flow where a tag triggers a build, a signature and an artifact upload halts as a whole
  • Scheduled jobs. Cleanup, backup and report workflows on a cron schedule simply lose that window. They do not queue up and run later
  • Monitoring built on the Actions API. Dashboards that read run status through the API start receiving errors
  • Container image build and push flows. The registry may be alive, but if Actions is what builds and pushes the image, the outcome is the same

2.2 What does not stop

  • Artifacts already deployed and served elsewhere. If your build output sits on your own server or another CDN, that serving path keeps running regardless of Actions
  • Local development. Branching, committing and running tests in a cloned repository all work locally. Git was designed as a distributed version control system
  • Dependencies you already fetched. With a lock file and a cache, the build reproduces on your machine as long as the external registry is up
  • Pipelines wired to another CI. If the repository lives on GitHub but the build runs on a different runner, source access alone keeps you going

2.3 The boundary this incident did not settle

The most interesting question is exactly the one the public record does not answer. Did the Pages degradation mean only that new deployments were blocked, or that serving of already-published sites was affected too? The status wording never separated the two situations. Reports in the community thread skewed heavily towards deployment failures, but that is the distribution of user reports, not proof that serving was untouched.

In practice that distinction changes the whole design of your preparation. The table below splits the two cases.

AspectOnly deployment blockedServing affected too
What users seeThe site opens, the content is staleThe site fails to open or errors intermittently
Nature of the lossFreshness. Usually recoverableRevenue and trust. Not recoverable
Reasonable countermeasureArtifact retention and retries are enoughDuplicating the serving path becomes justifiable
Cost profileEffectively zeroDNS, certificates and sync all cost you
The question to askCan this content wait half a day?Does an hour offline leak money?

The summary is this. Until a serving failure is actually confirmed, do not spend budget on the assumption that serving goes down. Making your setup survive half a day of blocked deployment, by contrast, costs almost nothing.

3. The real bill of this outage - the triggers that vanished

Workflows that failed for ten hours can simply be run again. The real cost arrives afterwards.

3.1 The quiet failure created by webhook throttling

Workflows do not run by themselves. Events such as a push or a pull request create the run. That delivery path was throttled to aid recovery, and many of the events that occurred while it was throttled were not stacked in a queue for later delivery, they were simply not processed.

The consequence looks like this.

  • The commit is in the repository, perfectly intact. No code was lost at all
  • But the checks list attached to that commit is empty. Not failing. Absent
  • In a repository without required checks, that state merges. A reviewer sees no red mark and senses no problem
  • A commit that skipped lint, tests and security scanning altogether lands on the default branch
  • Days later CI runs for some other reason, the problem surfaces, and the blame lands on an unrelated recent change

GitHub's guidance was explicit: push a new commit, update the pull request, or manually re-run the workflow where applicable, so that the triggering action itself is repeated. The sentence about no automatic replay sits right next to it.

3.2 What to sweep once the outage ends

A closed incident does not mean the work is done. Below is what a human has to check afterwards.

  • Commits that landed inside the outage window. Line your clock up to UTC and pull the default-branch commits for that stretch
  • Commits with an empty checks list. Look for the ones with nothing attached, not the ones that failed. This is the core of it
  • Pull requests merged during the window. Human approval may have happened while automated checks did not run
  • Gaps in scheduled workflows. Check whether a daily backup or cleanup lost a day. Nothing alerts you about this one
  • Agreement between deployment state and what is actually served. Confirm the last successful deployment really carries the newest source
  • Cleanup after jobs you cancelled or force-killed. Lock files, temporary resources and half-uploaded artifacts may still be lying around

The cheapest move is to push a single empty commit to the default branch right after the window and run the whole set of workflows once. That at least establishes that the current HEAD passes its checks. It will not catch problems in individual commits merged mid-window, though, so the list above still needs a pass.

4. When the status page is green but only your workflow fails

An incident escalated to critical, like this one, makes the call easy. The hard case is a green status page while only your side is broken. In day-to-day work that situation is far more common.

4.1 Narrowing down in order

  • Step 1. Check whether the same workflow succeeded recently. If it never has, your change is the likely cause
  • Step 2. Run an unrelated workflow in another repository. If that fails too, the problem is at account or organisation scope
  • Step 3. Separate failures before the job starts from failures after. Before means runner assignment and queueing; after means your own script
  • Step 4. Run the same commands locally. If it reproduces locally, this is not an infrastructure outage
  • Step 5. Only if you get this far with no answer should you open the status page and community incident thread

The reason for that order is simple. The status page is always late. This time too there was a gap between user symptoms and the first investigation notice, and more than an hour passed before the impact level reached its final grade. A green status page is not evidence that nothing is broken; it is information that nothing has been tallied yet.

4.2 Signals that the cause is on your side

  • Failures cluster in one specific job or one specific step
  • The error message is concrete: a module not found, a permission denied, that kind of thing
  • Re-running the same commit dies at the same point with the same message
  • You recently changed one of the action versions, the runner image, or the dependency lock file
  • Workflows in other repositories run perfectly well

4.3 Signals that the cause is on the provider side

  • Jobs sit in the queue for a long time without ever starting
  • Errors are vague, along the lines of a runner failing to acquire the job
  • Each re-run fails at a different point. Non-determinism is a strong clue
  • Workflows unrelated to your code fail at the same time
  • The web UI or API responses are slower than usual or error intermittently

The behaviour that makes an outage worse. Reflexively re-running everything the moment something fails. While recovery proceeds in steps, mass retries reinflate the queue and slow down your own recovery. In this case recovery worked by draining queues while pushing the success rate up. Retries are better batched until after the success rate has visibly climbed.

5. How many single points your deploy path really has

Here is the heart of it. Hanging your deployment on GitHub is not a bad decision. What you do have to count is how many boxes that decision puts inside one company.

5.1 Splitting it into four boxes

A deployment path generally divides into these four.

  • Source storage. Where the code lives. The remote repository
  • Trigger. The layer that turns an event into a run. Webhooks and the scheduler
  • Compute. The machines that actually build and test. The runners
  • Distribution. Where the finished artifact reaches users. Hosting and CDN

Look at how those four are placed in a typical setup and it becomes obvious why one company's outage stops the whole deployment.

  • Source storage = GitHub
  • Trigger = GitHub webhooks
  • Compute = GitHub hosted runners
  • Distribution = GitHub Pages
  • All four in one company. In this arrangement the count of single points is not one, it is four

5.2 Which box self-hosted runners actually remove

Moving runners onto your own infrastructure looks like it removes the compute box, and this incident refuted that expectation precisely. Errors and rate limiting were reported at runner registration for self-hosted setups, and Actions Runner Controller runners on private Kubernetes clusters froze in an idle state, requiring a human to delete pods or redeploy the application.

  • Even with runners on your own infrastructure, the control plane that assigns jobs is still GitHub
  • Self-hosting is therefore a way to own compute capacity and environment, not a way to cut the control-plane dependency
  • If anything it adds one more thing to recover during an outage. Cleaning up frozen runner pods is your job
  • The valid reasons for self-hosting are security boundaries, internal network access, special hardware and cost. Availability is not on that list

6. Cost and effect of each countermeasure

Preparation is not all-or-nothing. There are tiers, from things that cost essentially nothing to things that cost a great deal, and most setups are finished by the first three lines below.

6.2 The one line to read out of that table

The top four rows cost effectively nothing and have high effect. The bottom two cost a lot and have limited effect against this class of incident. Yet what people start discussing right after an outage is almost always the bottom two. The order is backwards.

  • Artifact retention means adding one upload step to a workflow. Even mid-outage, the output of the last successful build is in your hands
  • Local build reproducibility is not a tool, it is a habit. Avoid magic procedures that only exist inside CI and it maintains itself
  • Required status checks structurally block the exact loss this outage produced, the commit with no checks. If checks cannot run, the merge cannot happen, and a human notices
  • Pull deploy scripts out of CI-specific syntax and you can run the same script from a laptop for an urgent release

7. Where overreaction begins - drawing the line by scale

Overreaction always follows a large outage. Multi-cloud is a net loss in most cases. The discussion only ends when you can say precisely why.

7.1 Hobby and personal sites

  • Half a day of delayed deployment costs you nothing. When the loss is near zero, spending money and time on preparation is a straight net loss
  • Keeping dual hosting permanently online makes the arrangement itself a new failure source. DNS switching, two sets of certificates, redirect rules and sync scripts accumulate
  • In practice most incidents come from those parts, not from the provider. An unused standby path quietly rots
  • The sensible ceiling here is three things: artifact retention, a working local build, and status notifications. All free, all finishable today
  • If you insist on one more, periodically drop a compressed copy of the static output into a separate repository or cloud storage

7.2 Small services with revenue attached

  • The criteria change. You have to price deployment being blocked and the service being unreachable separately
  • Delayed deployment is usually survivable. It is rare for a company to wobble because a feature shipped half a day late
  • Serving downtime is different. Duplication becomes justifiable there. But in that case the thing to protect is hosting and DNS, not CI
  • Which means even at this scale, duplicating CI is usually waste. The money belongs on the serving path
  • What genuinely pays off is separating deploy scripts from CI syntax so a human can execute the same procedure mid-outage

7.3 Team and company scale

  • From here the loss is measured per hour. Developer headcount times hours is the cost
  • Even so, the first investment is process, not duplication. Deciding in advance who calls it and in what order things get swept removes a large share of the loss
  • Putting slack into the release schedule is cheaper and more reliable than duplication
  • If you do evaluate CI duplication, the realistic form is one critical path that can also run on another runner, not a full pipeline clone
  • A duplicated path has to be exercised regularly. A standby path that never runs will certainly fail on the day of the outage

8. Does bringing your own runners fix this?

This came up above, but the evidence here is unusually clean, so it deserves its own section. In this outage, the people running self-hosted runners did not have an easier time.

  • Errors and rate limiting were reported at the registration stage. The runner process may live on your server, but registration still has to talk to GitHub
  • Those running runners on Kubernetes through Actions Runner Controller hit pods frozen in an idle state
  • GitHub's guidance was to delete those pods with kubectl or redeploy the ARC application, after which replacement runners are created automatically
  • In other words, in the final stretch of recovery, the people who needed hands on keyboards were the ones with their own clusters
  • Anyone on hosted runners only had to wait for the queues to drain

This contrast is not an argument against self-hosting. It is an argument for deleting availability from the list of reasons to self-host. If you need access to internal network resources, specific GPUs, cheaper long-running jobs, or a build environment you control for compliance, self-hosting is right. What goes wrong is adopting it for those reasons and then expecting availability to improve as a bonus.

9. Putting slack into the release schedule

The cheapest preparation is not technical, it is scheduling. And this is a different conversation from no-deploy Fridays.

9.1 The idea of a retry budget

  • Write into the release plan an explicit allowance of time that assumes the deployment fails the first time. A few hours is enough
  • With slack in place, nobody makes the decision to force something through mid-outage. Forced decisions mostly come from having no slack
  • For releases tied to external announcements, separate the deployment time from the announcement time. Deploy early, flip to public later
  • For a static site the natural shape is to build the output first and publish it afterwards
  • The larger the release, the more pipeline retries it takes. Scale the slack to the size of the release

9.2 Decisions not to make during an outage

  • Turning checks off temporarily. Disabling required status checks because you are in a hurry manufactures exactly the loss this outage caused
  • Major pipeline surgery. Heavily editing workflows mid-outage destroys your ability to tell later what the cause actually was
  • An improvised migration to another CI. An unprepared migration will not finish that day, and if it does you are left with an unvalidated pipeline
  • Mass re-runs. They reinflate the queue during recovery
  • Leaving manual deployments untraced. If you pushed something out by hand, record what you deployed and from which commit. The next automated deploy can overwrite it

10. What could not be confirmed

Everything without solid grounding is collected here.

  • The root cause. GitHub said in the 15:45 UTC update that it had identified the source of the disruption, but never disclosed what that source was before the incident closed
  • The standing of phrases used during recovery. Runners being assigned jobs that were no longer valid, and ARC pods stuck idle, were mentioned as symptoms and mitigation targets, not confirmed as descriptions of the cause
  • Serving impact on already-published Pages sites. Whether only deployment was blocked or serving was affected is not separable from the public wording
  • Explanations circulating in the community. Claims pointing at load growth or infrastructure migration do not originate from GitHub. This article does not treat them as fact
  • Absolute figures for the blast radius. No public numbers were confirmed for how many repositories or how many runs were affected
  • Whether SLA credits apply. How any credit policy applies to this incident could not be confirmed from the public record
  • Whether and when a detailed post-incident report appears. None was available at the time of writing. This may be updated later
  • Exact start and end times of the webhook throttle. The 15 percent figure appears in a recovery update, but the minute the throttle began and the minute it was fully lifted are not stated

11. Frequently asked questions

When did this GitHub outage start and when did it end?

On the GitHub status page the incident opened at 15:22 UTC on 6 August 2026 and was closed at 02:04 UTC on 7 August. The full window is 10 hours and 42 minutes. That number should not be read as pure downtime, though. Mitigation came earlier: an update at 00:05 UTC on 7 August said system-wide queues had drained and the degradation was mitigated. The roughly two hours after that were spent clearing a tail in which Actions Runner Controller runners were slow to recover. Converted to Korean time the incident opened at 00:22 on 7 August and closed at 11:04 the same morning, so for a Korean working day it was largely over before people sat down.

Did GitHub publish the root cause?

No. An update at 15:45 UTC said engineers had identified the source of the disruption and were working on a mitigation, but what that source actually was never appeared in writing before the incident closed. The phrases that surfaced during recovery, such as runners being handed jobs that were no longer valid, or Actions Runner Controller pods stuck in an idle state, describe symptoms and mitigation targets rather than a stated root cause. Several explanations circulating online come from community speculation rather than GitHub, so it is safer not to promote them into fact.

What happens to a commit I pushed during the outage that never ran CI?

It does not come back on its own. In its final update GitHub said some workflow-triggering events, including push and pull request events, were not processed during the incident and cannot be replayed automatically. The remedy is to repeat the triggering action itself: push a new commit, update the pull request, or manually re-run the workflow where that is possible. The dangerous case in practice is not the workflow that failed but the workflow that never appeared in the list. A red mark is easy to spot, while a commit with no runs at all leaves no visual trace and looks exactly like a commit that passed.

Did already-published GitHub Pages sites keep serving?

The public record does not settle this. Pages was listed as an affected component and moved between degraded and normal, but the published wording never separated two very different situations: new deployments being blocked, and serving of already-published sites being affected. Symptoms reported in the community thread were overwhelmingly deployment failures. That is only the distribution of user reports, however, and not evidence that serving was untouched. This article therefore makes no judgement that assumes serving was fine, and files the question under items that could not be confirmed.

Should a personal blog keep a second hosting provider ready?

Usually not. For hobby and personal sites, keeping dual hosting permanently online turns the arrangement itself into a new source of failure. DNS switching, two sets of certificates, redirect rules and sync scripts pile up, and in practice those parts break long before the provider does. If half a day of delayed deployment costs you nothing, three measures are enough. First, keep build artifacts so you never have to rebuild from scratch. Second, occasionally check that the same command still builds locally. Third, subscribe to status page notifications so you spend less time deciding whether it is an outage or your own mistake.

Conclusion: three things to take away

First, the loss in this outage was absence, not failure. Ten hours of red workflows can simply be re-run. The problem is the commit whose trigger was never processed, leaving nothing at all in the run list, and that does not come back by itself. Whether you have a procedure for a human to sweep those commits after the outage is what decides the actual loss.

Second, count single points by boxes, not by companies. When source, trigger, compute and distribution all sit inside one company, that company's outage stops the entire deployment. And moving only the runners to your own infrastructure leaves the trigger and the control plane exactly where they were. The proof this time is that the people with their own clusters were the ones cleaning up pods by hand.

Third, do not invert the value order of your preparation. Artifact retention, local build reproducibility, required status checks, a post-outage sweep procedure. Those four are effectively free and block most of this class of loss. Duplicated distribution paths and repository mirrors are expensive and, for an outage that blocks deployment like this one, of limited effect. Yet the expensive option is always what comes up first in the meeting afterwards.

One last thing. A green light on a status page is not evidence that things are fine, it is information that nothing has been tallied yet. This time too there were gaps between user symptoms and the first notice, and between the notice and the escalation. So diagnosis always has to start on your side. The few minutes it takes to run the same command locally beat an hour spent refreshing someone else's status page.
