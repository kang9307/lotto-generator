In Order, Once, and Fast - Three Hard Problems Kafka Solves at Scale

What Airbridge's (ab180) real-time ad event matching reveals about ordering, exactly-once processing, and low-latency trade-offs

Jul 15, 2026 Dev & Infra

Introduction: Why "In Order, Once, and Fast" Is Hard to Achieve Together

Systems that process large volumes of events in real time - ad attribution, payments, IoT sensor logs, order processing - all face the same three demands at once. Events must be processed in the order they happened, each event must be reflected exactly once, with no duplication or loss, and all of this must happen fast enough that users never notice a wait. The problem is that these three demands push against each other. Preserving order means lining processing up in a single file, which means giving up parallelism. Adding retries to prevent loss creates duplicates. Adding workers for speed scrambles order.

As of July 2026, a case published on the engineering blog of ad-tech company Airbridge (ab180) is a real-world record of trying to catch all three at once. The company's core function is matching ad clicks, app installs, and purchases in real time to attribute which ad actually drove a purchase - and if an install event gets processed before its corresponding click event, the attribution judgment itself breaks. Using that case as a starting point, this piece works through why ordering, exactly-once, and speed are hard together in large-scale real-time event processing, the principles Kafka uses to ease the problem, and what teams facing similar issues can actually take into their own systems.

1. The Root Cause - Why Parallel, Distributed Processing Breaks Ordering

1.1 A Problem That Wouldn't Exist on a Single Thread

If you pile events into one queue and have a single worker pull them out in order, ordering takes care of itself, because arrival order is processing order. The ordering problem begins the moment you add more workers to raise throughput. When workers A and B each pull events from the same queue, which one finishes first depends on unpredictable factors like network latency, CPU load, and GC timing. As a result, event 3 can finish processing before event 2.

1.2 Why "Exactly Once" Isn't the Natural Default

Networks lose messages (loss), cause senders to resend when a response is late (duplication), or occasionally deliver exactly once by chance - all mixed together. Distributed systems theory separates these into at-most-once, at-least-once, and exactly-once delivery. The catch is that guaranteeing true exactly-once delivery purely at the infrastructure layer, over an unreliable network, is theoretically very hard. That's why most real-world systems default to at-least-once delivery and add application-level mechanisms on top to get effectively exactly-once behavior.

1.3 What Actually Breaks When Order Is Wrong

Airbridge's case makes this concrete. If an install event is processed before its ad click event, the system has to make an attribution decision before the evidence of which click drove the install has even arrived. The result is either a wrong attribution or a missed one. This isn't just about order looking neat - when business logic is built on the assumption of a specific order, breaking that assumption breaks the result itself.

2. How Kafka Guarantees Ordering - Partitions and Keys

2.1 There Is No "Global Order," Only "Partition Order"

Kafka splits a single topic into multiple partitions. A partition is both the unit of parallel processing and the unit of ordering. What Kafka actually guarantees is order within a single partition. Order across the entire topic is never a guarantee target in the first place - this is by design, not a limitation. Because the scope of ordering is narrowed to the partition level, work can be split and parallelized across as many partitions as you have.

2.2 Key-Based Partitioning - Grouping "Events of the Same Subject" Together

So how do you get events that need ordering into the same partition? A Kafka producer can attach a key to a message, and the default partitioner hashes that key (with the murmur2 algorithm) and takes the remainder over the number of partitions to decide the target partition. The same key always produces the same hash, so it always routes to the same partition. Using a user ID or device ID as the key means every click-install-purchase event for the same user piles into one partition, and that partition is read in order by exactly one consumer within a consumer group. Order is preserved at the per-user level, while events from different users are processed freely in parallel across different partitions.

2.3 A Catch - Increasing Partition Count Breaks the Mapping

There's a trap in this design. Because the mapping divides a hash value by the partition count, increasing the partition count in production can send the same key to a different partition than before. From that point, past and new events for the same key scatter across different partitions, and ordering guarantees quietly break. Partition counts should be set carefully upfront with throughput ceilings in mind, and if you must increase them later, you need a migration plan that accounts for the possibility of broken ordering.

3. The Trade-off Between Ordering and Throughput

3.1 Perfect Order Demands Full Serialization

Taken to the extreme, the only surefire way to keep 100% of events in order is to process them one at a time on a single thread - which caps throughput at roughly one CPU core. In practice, ordering and throughput are always a trade-off. Widening the scope of ordering (toward global order) reduces parallelism; narrowing it (toward per-entity order) increases parallelism.

3.2 The Microbatch Trap - Why Adding Servers Didn't Speed Things Up

Airbridge reports that it originally used a microbatch approach that processed event types sequentially - the click-processing stage had to finish before the install-processing stage began, forcing order through a strict pipeline. This preserved order logically, but in practice the whole system got stuck at the pace of its slowest stage. If traffic spiked or processing slowed for one event type, the workers handling later stages had nothing to do but wait, even though they were idle. Adding more servers (workers) couldn't push overall throughput past the speed of the slowest stage - a familiar case of "scaling out that doesn't actually scale."

3.3 The Fix Is Narrowing the Scope of Ordering

The key insight here matters. What a business actually needs is usually not "global order across all events" but "order among events belonging to the same subject" (say, the same user). Airbridge's reported approach was to give each event type an independent consumer, prevent a downstream consumer handling the same subject's events from overtaking an upstream consumer's processing position, and relax that check from strict locking to a short, event-time-based tolerance of a few seconds - a "safety margin." Instead of perfect global order, it allows just enough slack that it never actually causes a problem, and in exchange each consumer can process at its own pace. The exact implementation will differ company to company, but the principle - narrow the scope of ordering down to what's actually needed - generalizes.

4. What Exactly-Once Processing Really Means

4.1 There Is No True "Exactly-Once Delivery" - Only "Effectively Exactly Once"

The term "exactly-once," as commonly used in the industry, is a bit misleading. Perfectly guaranteeing, at the pure infrastructure layer, that a broker delivers a message physically exactly once over an unreliable network is difficult. What's called exactly-once in practice is usually the combination of at-least-once delivery + idempotent processing. That is, you accept that messages can arrive duplicated, but design the processing logic so that handling the same message twice produces the same result as handling it once - arriving at effectively exactly-once behavior.

4.2 Kafka's Idempotent Producer and Transactional API

Kafka offers an idempotent producer to reduce duplication on the producer side. The broker assigns each producer a unique ID (PID) and a sequence number to every message; if a message with the same PID and sequence number arrives again, it's recognized as a duplicate and applied only once. Even if a producer retries the same message after a network timeout, the broker filters out the duplicate. When writes across multiple partitions need to be grouped as a single unit, Kafka's transactional API comes in: a transactional.id preserves a producer's logical identity across process restarts, allowing writes across partitions to be committed atomically or aborted as a group.

4.3 Idempotent Processing and Offset Management on the Consumer Side

Producer-side mechanisms alone aren't enough. A consumer can crash or restart while applying the results of processing a message, causing the same message to be read and reprocessed. The common pattern for handling this is the idempotent consumer: record the unique ID of each processed event separately, and skip the side effect (crediting a payment, incrementing a counter, and so on) if an already-processed ID shows up again. On top of that, when you commit the offset matters. Committing before processing finishes means a crash midway makes the message look lost; committing after processing finishes means a crash right before the commit causes the same message to be reprocessed. The latter is generally considered the safer default, because paired with idempotency, duplication is absorbed harmlessly while loss cannot be undone. In a pipeline with multiple stages (entering a buffer, processing, committing), it's common to track the progress of each stage separately so the system can determine exactly how far it's safe to commit.

5. Preventing Loss - Acks and Rebalancing

5.1 On the Producer Side - Ack Configuration

When a producer sends a message to a broker, when the broker sends its acknowledgement determines the risk of loss. Setting acks=all (or -1) means a write is only considered successful once every in-sync replica, not just the leader partition, has received the message. Even if the leader fails right after acking, data survives on other replicas, preventing loss - at the cost of added latency while waiting for those acks. For payment or attribution data with low tolerance for loss, accepting that latency is the reasonable choice.

5.2 On the Consumer Side - Commit Timing and Rebalancing

Rebalancing happens when members join or leave a consumer group, reassigning partitions to different consumers - and this moment is where loss and duplication are both easy to introduce. If a message finished processing but wasn't committed right before a rebalance, the consumer that newly receives that partition reprocesses it from that message, creating a duplicate. Conversely, if an auto-commit cycle lands out of sync with the rebalance timing, the offset of a not-yet-processed message can already be committed, causing that message to be skipped and lost. In practice, teams typically use manual commits instead of auto-commit, and force a synchronous commit of everything processed so far inside the rebalance listener, right before partitions are handed off.

6. The Design Principles Airbridge's Case Illustrates

6.1 "Partition-Level Order + Tolerance" Instead of Global Order

Summarizing what Airbridge published, in the author's own reading: the team had multiple independent consumers each read the same topic and pick out only their own event type, passing along events that don't belong to them to the next consumer. Order was preserved by a single rule - a downstream consumer can never overtake an upstream one - and whether that's happening was judged not through strict synchronization but a short, event-time-based tolerance (a safety margin). Giving up perfect synchronization let each consumer process at its own pace instead of waiting on anyone else.

6.2 Eliminating Idle Time and Improving Throughput

The practical effect of this change was eliminating the idle time that plagued the microbatch approach. Even if traffic spikes for one event type, the consumer handling a different type doesn't stop - it keeps going at its own pace, switching temporarily to reading directly from Kafka only when its buffer fills up. After moving to this structure, Airbridge reports confirming more than a 10x improvement in throughput compared to the previous microbatch approach, with no event loss or duplication observed.

6.3 The Principle, Not the Implementation, Is What Transfers

Specifics like buffering modes or commit-state tracking are the product of optimizing for ab180's own traffic patterns and organizational structure - not code you can lift and drop in elsewhere. What transfers to other teams is the underlying principle: narrow the scope of ordering to the smallest unit the business actually requires, define an acceptable tolerance instead of demanding perfect synchronization, and make sure processing stages don't wait on each other within that tolerance.

7. Implications for Teams Facing Similar Problems

7.1 Question Whether You Really Need Global Order

Most systems, in practice, only need order at the level of an entity - per user, per order, per device - not globally. Before you start designing, defining exactly what concrete outcome breaks if order is violated helps you avoid the mistake of setting the scope of ordering far wider than it needs to be.

7.2 Partition Key Design Is Most of the Battle

Choosing a key simultaneously determines correctness (ordering) and scalability (the parallelism ceiling, which equals the partition count). A key with too little cardinality (a fixed constant, say) funnels all traffic into one partition and creates a bottleneck; a key sliced finer than the unit that actually needs ordering breaks the very order you were trying to preserve. The starting point is finding the exact smallest unit that needs ordering and using that as the key.

7.3 Don't Rely Only on Infrastructure Exactly-Once - Build Idempotency Into the Processing Layer Too

Kafka's idempotent producer and transactional API solve duplication and atomicity problems inside Kafka itself (between broker and producer, and across partition writes), but they don't make exactly-once out of the side effects a consumer writes to external systems (a database, a payment gateway, an external API). Every point where a side effect leaves the system needs its own idempotency mechanism - a unique ID check, an upsert, a unique constraint.

7.4 Look for "Good Enough," Not Perfect

Trying to satisfy perfect global order and perfect exactly-once at the same time causes throughput to collapse. What matters in practice is clearly defining the tolerance the business can actually accept - a few seconds of delay, occasional reprocessing - and maximizing parallelism within that tolerance. Airbridge's case shows that finding that balance point can show up as a 10x difference in throughput.

Conclusion

Ordering, exactly-once, and speed are each familiar requirements on their own, but satisfying all three at once, at scale, is a distinct hard problem. Kafka provides building blocks - partition-level ordering, key-based routing, an idempotent producer, and a transactional API - but these alone don't automatically solve it. The real solution always comes from narrowly defining exactly how much ordering guarantee this business needs, and then layering idempotency within that boundary so duplication becomes harmless. Airbridge's case validated this principle against real traffic, achieving more than 10x throughput improvement with no loss or duplication - making it, as of July 2026, a useful reference for teams facing a similar problem.
