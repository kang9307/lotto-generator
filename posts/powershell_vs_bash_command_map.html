서론 - 같은 파이프 기호, 다른 것이 흐른다

bash와 PowerShell은 모두 |로 명령을 잇는다. 그러나 그 선을 타고 흐르는 것이 다르다. Microsoft Learn의 about_Pipelines는 파이프라인 연산자가 앞 명령의 결과를 다음 명령으로 보낸다고 설명하며, 보내는 것이 객체라고 밝힌다. 첫 명령이 내보낸 객체가 두 번째 명령으로 가고, 두 번째 명령이 처리한 객체가 세 번째 명령으로 간다. 같은 문서는 PowerShell의 파이프라인이 객체 지향이어서 원시 바이트 데이터를 지원하지 않으며, 표준 입력(stdin)은 PowerShell 파이프라인의 입력에 연결되지 않는다고도 적는다. bash의 파이프가 프로세스의 출력 텍스트를 다음 프로세스의 입력으로 잇는 것과 대비된다.

결과가 크게 갈린다. 텍스트 파이프라인에서는 모든 도구가 열 위치와 구분자를 직접 해석한다. ls -l | awk '{print $5}'의 $5는 「다섯 번째 열」이라는 약속에 기댄 값이다. 객체 파이프라인에서는 Length라는 속성 이름으로 값을 꺼낸다. 이 차이를 이해하면 명령 대응표를 외우지 않아도 대부분의 번역이 나온다. 반대로 이 차이를 모르면 같은 이름의 별칭을 쳤는데 옵션이 통하지 않거나, 출력은 비슷한데 정렬과 비교 결과가 달라지는 일을 겪는다.

다루는 축은 개념(객체 대 텍스트)과 대응표이다. grep·awk의 문법과 옵션 모음은 리눅스 Grep과 AWK 사용 가이드가, 장애 로그를 집계하는 레시피는 Linux 로그 분석 명령어 완벽 가이드가 다룬다. 배치 파일·작업 스케줄러까지 넓힌 자동화 입문은 윈도우 작업 자동화 입문 가이드에, 윈도우에 UNIX 유틸리티를 네이티브로 들일 때 PowerShell 별칭과 이름이 겹치는 문제는 Microsoft Coreutils for Windows에 있다.

실습에 쓴 로그 파일 app.log는 12줄이다. 이후의 모든 집계는 이 파일을 대상으로 한다. 같은 폴더에는 old.log(3줄), readme.txt(hello 한 줄), 2,000자짜리 notes.md, 이름에 대괄호가 든 file[1].txt, 하위 폴더 sub(그 안의 deep.log)가 있다.

이 글에서 반복해서 확인하는 차이는 다섯 가지로 요약된다.

  • 파이프로 흐르는 것이 문자열이 아니라 객체이다.
  • 와일드카드와 옵션을 해석하는 주체가 셸이 아니라 각 cmdlet이다.
  • 대소문자 기본값이 grep과 반대이다. Select-String과 비교 연산자는 기본이 대소문자 무시이다.
  • 별칭이 bash 명령 이름과 같아도 옵션 체계는 bash가 아니다.
  • 객체를 문자열로 바꾸는 순간 표시 폭 때문에 값이 잘릴 수 있다.

ls | grep이 Where-Object로 바뀌는 이유 - 출력은 문자열이 아니다

첫 번째 대응은 파일 목록에서 .log로 끝나는 것만 고르는 것이다. bash에서는 목록 텍스트에서 줄을 고른다.

$ ls | grep '\.log$'
                    app.log
                    old.log

PowerShell에서는 Get-ChildItem이 내보낸 객체의 Name 속성을 걸러낸다.

Get-ChildItem | Where-Object { $_.Name -like '*.log' } | Select-Object Name, Length | Format-Table -AutoSize
Name    Length
                    ----    ------
                    app.log    532
                    old.log     36

출력된 표는 텍스트이지만, 파이프로 흐르는 동안에는 객체였다. Where-Object가 한 일은 줄 문자열을 훑는 것이 아니라 객체 하나하나의 Name 속성을 와일드카드 패턴과 비교하는 것이다. 이 점은 실행으로 확인된다.

$first = Get-ChildItem | Select-Object -First 1
                    $first.GetType().FullName
                    (Get-ChildItem | ForEach-Object { $_.GetType().Name } | Group-Object | ForEach-Object { $_.Name + ' x' + $_.Count }) -join ', '
                    Get-ChildItem -File | Get-Member -MemberType Property | Where-Object { $_.Name -in 'Name','Length','LastWriteTime','Extension' } | Select-Object Name, Definition | Format-Table -AutoSize
System.IO.DirectoryInfo
                    DirectoryInfo x1, FileInfo x5
                    
                    Name          Definition
                    ----          ----------
                    Extension     string Extension {get;}
                    LastWriteTime datetime LastWriteTime {get;set;}
                    Length        long Length {get;}
                    Name          string Name {get;}

첫 요소는 System.IO.DirectoryInfo이고, 목록 전체는 디렉터리 객체 1개와 파일 객체 5개이다. 파일 객체에는 문자열이 아니라 Length(long)와 LastWriteTime(datetime) 같은 형식 있는 속성이 있다. 이 사실에서 두 가지가 따라 나온다. 첫째, 열 번호를 세는 awk가 필요 없다. 둘째, 크기 비교와 정렬이 문자 순서가 아니라 숫자 순서로 이루어진다.

두 번째 대응은 크기 열만 뽑는 것이다. bash에서는 ls -l의 다섯 번째 열을 awk로 꺼낸다(디렉터리 줄은 제외했다).

  • 파일 목록의 필터링은 이름 문자열 검색이 아니라 속성 비교이다. 확장자는 Extension, 크기는 Length로 직접 접근한다.
  • 열을 꺼내는 awk '{print $N}'은 Select-Object -ExpandProperty 속성이름이 된다.
  • 정렬은 입력의 형식을 따른다. 숫자로 정렬하려면 값이 숫자 형식이어야 하고, 문자열이면 [int] 같은 변환이 필요하다.
  • find는 이름을 그대로 쓰면 Windows의 find.exe가 실행된다(PATH에 Git의 usr\bin이 없는 세션 기준, 9절).

Select-String은 grep이 아니다 - MatchInfo와 기본값의 차이

Select-String 문서는 이 cmdlet을 「Unix의 grep이나 Windows의 findstr.exe와 비슷하게 쓸 수 있다」고 소개한다. 비슷하지만 같지 않다. 같은 파일에서 ERROR를 찾아 보면 두 쪽의 결과가 갈린다. bash는 대소문자를 구분하여 3건을 찾는다.

$ grep -n ERROR app.log
                    3:2026-10-05 09:01:12 ERROR db timeout after 30s
                    7:2026-10-05 09:03:02 ERROR upstream 502
                    10:2026-10-05 09:05:00 ERROR db timeout after 30s
Select-String -Path .\app.log -Pattern 'ERROR'
app.log:3:2026-10-05 09:01:12 ERROR db timeout after 30s
                    app.log:5:2026-10-05 09:01:20 INFO  retry succeeded after error in cache
                    app.log:7:2026-10-05 09:03:02 ERROR upstream 502
                    app.log:10:2026-10-05 09:05:00 ERROR db timeout after 30s

PowerShell 쪽은 4건이다. 5번 줄에는 소문자 error가 들어 있다. Select-String 문서는 -CaseSensitive 매개 변수에 대해 「기본적으로 일치는 대소문자를 구분하지 않는다」고 적는다. 반대로 grep은 기본이 대소문자 구분이고 -i를 붙여야 무시한다. 두 쪽의 건수를 맞춰 보면 이렇다.

$ grep -c error app.log
                    1
                    $ grep -ci error app.log
                    4
'matches for error (no flag): ' + @(Select-String -Path .\app.log -Pattern 'error').Count
                    'matches for error -CaseSensitive: ' + @(Select-String -Path .\app.log -Pattern 'error' -CaseSensitive).Count
matches for error (no flag): 4
                    matches for error -CaseSensitive: 1

출력의 앞에 붙는 app.log:3:은 파일 이름과 줄 번호이다. 이것이 텍스트가 아니라 MatchInfo 객체의 표시 형식이라는 점은 속성을 읽어 보면 알 수 있다.

$m = Select-String -Path .\app.log -Pattern 'ERROR' | Select-Object -First 1
                    $m.GetType().FullName
                    'LineNumber = ' + $m.LineNumber
                    'Filename   = ' + $m.Filename
                    'Line       = ' + $m.Line
                    'Pattern    = ' + $m.Pattern
Microsoft.PowerShell.Commands.MatchInfo
                    LineNumber = 3
                    Filename   = app.log
                    Line       = 2026-10-05 09:01:12 ERROR db timeout after 30s
                    Pattern    = ERROR

문서도 Select-String이 일치마다 MatchInfo 객체를 돌려주고 Filename, Line 같은 속성이 있다고 적는다. 그래서 건수를 세는 grep -c는 결과를 배열로 감싸 .Count를 읽는 것이 되고, 일치한 부분만 뽑는 grep -o는 Matches.Value를 읽는 것이 된다. grep 옵션과의 대응을 같은 파일로 실행한 결과가 아래 표이다.

파일 객체를 파이프로 넣을 때의 동작도 grep과 다르다. Select-String 문서는 FileInfo 객체가 입력되면 객체의 문자열 표현이 아니라 그 파일의 내용을 검색한다고 적는다. ls | grep app이 이름을 검색하는 것과 정반대이다.

이 네 줄은 앞서 만든 임시 폴더(app.log, old.log, readme.txt 등이 들어 있는 곳)에서 실행한 결과이다. 마지막 줄의 1건은 그 폴더 목록에 app.log가 있어서 나온 값이므로, 이름에 app이 든 항목이 없는 폴더에서는 이 숫자가 달라진다.

Set-Location C:\demo\t
                    'files whose NAME has app (Where-Object): ' + @(Get-ChildItem | Where-Object { $_.Name -match 'app' }).Count
                    'FileInfo objects | Select-String app (searches contents): ' + @(Get-ChildItem -File | Select-String -Pattern 'app').Count
                    'FileInfo objects | Select-String hello (readme.txt content): ' + @(Get-ChildItem -File | Select-String -Pattern 'hello').Count

                    FileInfo objects | Select-String app (searches contents): 0
                    FileInfo objects | Select-String hello (readme.txt content): 1
                    listing as text | Select-String app: 1

이름에 app이 든 파일은 1개이지만, 파일 객체를 그대로 파이프하면 내용에서 app을 찾으므로 0건이 나왔다. hello는 readme.txt의 내용이어서 1건이다. 목록의 텍스트 표현에서 이름을 찾으려면 Out-String -Stream으로 줄 단위 문자열로 바꾼 뒤 넘겨야 한다. 이는 grep 기준으로 생각하는 사람이 가장 자주 만나는 함정이다.

대소문자 기본값은 Select-String에만 있는 것이 아니다. about_Comparison_Operators는 문자열 비교가 명시적 대소문자 구분 연산자를 쓰지 않는 한 대소문자를 구분하지 않는다고 적고, -replace도 기본이 대소문자 무시라고 적는다. sed 's/error/X/g'를 옮길 때 이 차이가 그대로 드러난다.

$ echo 'Error ERROR error' | sed 's/error/X/g'
                    Error ERROR X
                    $ echo 'a.b.c' | sed 's/./-/g'
                    -----
'ERROR' -eq 'error'      -> True
                    'ERROR' -ceq 'error'     -> False
                    'ERROR db' -match 'error'  -> True
                    'ERROR db' -cmatch 'error' -> False
                    'ERROR db' -like 'error*'  -> True
                    'Error ERROR error' -replace 'error','X' -> X X X
                    'Error ERROR error' -creplace 'error','X' -> Error ERROR X
                    'a.b.c' -replace '.','-'    -> -----
                    'a.b.c' -replace '\.','-'   -> a-b-c
                    'a.b.c'.Replace('.','-')    -> a-b-c

위 블록은 PowerShell을 한 줄씩 실행해 「식 -> 결과」 형태로 찍은 출력이다. -replace의 앞 인수가 정규식이어서 '.'이 모든 문자에 일치하는 점은 sed와 같고, 대소문자 기본값만 반대이다. -ceq·-cmatch·-creplace처럼 c를 붙이면 구분한다.

  • 같은 이름의 개념이라도 기본 대소문자 규칙이 반대인 경우가 있으므로 건수 비교가 필요한 집계는 항상 -CaseSensitive 사용 여부를 먼저 정한다.
  • Select-String에 파일 객체를 넘기면 내용 검색이고, 문자열이나 Out-String -Stream 결과를 넘기면 그 줄 검색이다.
  • 패턴은 정규식이 기본이고 리터럴 검색은 -SimpleMatch이다. grep의 -F에 해당한다.

sort | uniq -c | wc를 Group-Object·Sort-Object·Measure-Object로

로그의 수준(INFO·WARN·ERROR)별 건수를 세는 집계는 bash에서 다음과 같이 쓴다. 세 번째 열을 뽑아 정렬하고, 같은 값을 세어 개수 순으로 다시 정렬한다.

$ awk '{print $3}' app.log | sort | uniq -c | sort -rn
                          6 INFO
                          3 WARN
                          3 ERROR

PowerShell에서는 열을 뽑는 자리에 -split과 인덱스를, 센 뒤 정렬하는 자리에 Group-Object와 Sort-Object를 쓴다.

Get-Content .\app.log | ForEach-Object { ($_ -split '\s+')[2] } | Group-Object | Sort-Object Count -Descending | Select-Object Count, Name | Format-Table -AutoSize
Count Name
                    ----- ----
                        6 INFO
                        3 ERROR
                        3 WARN

두 출력에서 개수가 같은 WARN과 ERROR의 순서가 반대이다. 같은 개수끼리의 순서는 정해진 약속이 아니므로 순서에 의존하는 처리는 피하는 것이 안전하다. Group-Object가 돌려주는 것도 문자열이 아니라 객체이다. 그래서 개수 열은 Count 속성으로 접근한다.

$g = Get-Content .\app.log | ForEach-Object { ($_ -split '\s+')[2] } | Group-Object | Select-Object -First 1
                    $g.GetType().FullName
                    $g | Get-Member -MemberType Property | Select-Object Name | Format-Table -AutoSize
Microsoft.PowerShell.Commands.GroupInfo
                    
                    Name
                    ----
                    Count
                    Group
                    Name
                    Values

GroupInfo의 Group 속성에는 그 값으로 묶인 원본 항목이 들어 있어서, 개수만이 아니라 묶음의 내용까지 이어서 처리할 수 있다. 줄 수와 합계는 Measure-Object가 맡는다. wc -l은 Measure-Object -Line이나 배열의 .Count가 되고, awk '{sum += $5}'는 -Property Length -Sum이 된다.

'wc -l       -> ' + (Get-Content .\app.log | Measure-Object -Line).Lines
                    'count       -> ' + @(Get-Content .\app.log).Count
                    Get-ChildItem -File | Measure-Object -Property Length -Sum -Average -Maximum -Minimum | Format-List Count, Sum, Average, Maximum, Minimum
wc -l       -> 12
                    count       -> 12
                    Count   : 5
                    Sum     : 2586
                    Average : 517.2
                    Maximum : 2002
                    Minimum : 7

bash의 wc -l < app.log도 같은 12를 돌려준다. Measure-Object 한 번으로 개수·합·평균·최댓값·최솟값을 모두 얻는다는 점이 awk 한 줄 집계보다 편한 대목이다. 중복 제거 sort -u는 Sort-Object -Unique이고, 'b','a','b','c','a' | Sort-Object -Unique의 결과는 a, b, c이다.

about_Pipelines의 「하나씩 처리」 규칙은 집계에서 결과를 가른다. 파이프로 넣으면 객체가 하나씩 흘러 개수가 세어지지만, 매개 변수로 배열을 통째로 넘기면 하나의 객체로 취급된다.

'[1,2,3] | Measure-Object            -> ' + (1,2,3 | Measure-Object).Count
                    'Measure-Object -InputObject @(1,2,3) -> ' + (Measure-Object -InputObject @(1,2,3)).Count
                    '@{a=1;b=2} | Measure-Object          -> ' + (@{a=1;b=2} | Measure-Object).Count
[1,2,3] | Measure-Object            -> 3
                    Measure-Object -InputObject @(1,2,3) -> 1
                    @{a=1;b=2} | Measure-Object          -> 1

문서가 든 예와 같은 결과이다. 배열은 풀려서 3이 되지만 해시 테이블은 풀리지 않아 1이다. 해시 테이블을 항목별로 흘리려면 GetEnumerator()를 호출해야 한다고 문서는 적는다.

head·tail·cat·awk·cut·xargs·tee의 대응

나머지 도구들은 이름 그대로의 대응 cmdlet이 있거나, 객체 파이프라인의 기본 cmdlet 조합으로 풀린다. 같은 app.log로 실행한 결과를 모았다. head -n 2와 tail -n 2는 Get-Content의 매개 변수이다.

'head -n 2   ->'
                    Get-Content .\app.log -TotalCount 2
                    'tail -n 2   ->'
                    Get-Content .\app.log -Tail 2
                    'cat type    -> ' + (Get-Content .\app.log).GetType().FullName
                    'cat -Raw    -> ' + (Get-Content .\app.log -Raw).GetType().FullName + ', length ' + (Get-Content .\app.log -Raw).Length
head -n 2   ->
                    2026-10-05 09:00:01 INFO  service started
                    2026-10-05 09:00:07 WARN  cache miss ratio high
                    tail -n 2   ->
                    2026-10-05 09:05:01 INFO  retry 1
                    2026-10-05 09:05:44 INFO  service stopped
                    cat type    -> System.Object[]
                    cat -Raw    -> System.String, length 532

bash의 head -n 2 app.log와 tail -n 2 app.log는 같은 4줄을 돌려준다. 다른 점은 cat의 반환 형식이다. Get-Content는 파일을 줄 단위 문자열 배열로 읽고, 통째 문자열이 필요하면 -Raw를 붙인다. 줄 단위 배열이 파이프로 흘러 ForEach-Object가 줄마다 실행된다. awk '{print $3}'은 -split과 인덱스로 옮기며, xargs는 ForEach-Object가 된다.

Get-Content .\app.log | Select-Object -First 3 | ForEach-Object { ($_ -split '\s+')[2] }
                    'app.log','old.log' | ForEach-Object { $_ + ' has ' + @(Get-Content $_).Count + ' lines' }
                    Get-ChildItem -File -Filter *.log | Tee-Object -Variable seen | Measure-Object | Select-Object -ExpandProperty Count
                    'tee variable holds ' + @($seen).Count + ' objects'
INFO
                    WARN
                    ERROR
                    app.log has 12 lines
                    old.log has 3 lines
                    2
                    tee variable holds 2 objects

xargs는 입력을 명령 인수로 바꾸는 도구이지만, ForEach-Object는 입력 객체를 $_로 받아 스크립트 블록을 실행한다. tee는 Tee-Object이며 파일 대신 변수에 저장하는 -Variable도 있다. 결과가 1개일 때와 0개일 때의 .Count 동작도 알아 둘 만하다.

$one = Get-ChildItem -Filter app.log
                    'one object .Count -> ' + $one.Count
                    $none = Get-ChildItem -Filter nomatch*
                    'no result is $null -> ' + ($null -eq $none)
                    '@() wrap .Count   -> ' + @($none).Count
one object .Count -> 1
                    no result is $null -> True
                    @() wrap .Count   -> 0

결과가 없을 때 변수는 빈 배열이 아니라 $null이므로, 개수를 안전하게 읽으려면 @(...)로 감싼다. 아래 표는 이 절의 대응이다.

tail -n NGet-Content -Tail Napp.log의 뒤 2줄이 같다

  • Get-Content의 결과가 줄 배열이므로 줄 수는 .Count로 바로 읽는다. 결과가 없으면 $null이므로 @(...)로 감싸 개수를 읽는다.
  • 인덱스 규칙이 다르다. awk의 $3이 -split의 [2]이다.
  • 파이프로 넣느냐 매개 변수로 넘기느냐에 따라 한 번에 처리되는 단위가 달라진다. 개수가 어긋나면 이 차이를 먼저 의심한다.

변수와 환경 변수 - $x는 자식 프로세스에 가지 않는다

bash의 export FOO=bar에 해당하는 것은 $env:FOO = 'bar'이다. 일반 변수 $x는 PowerShell 세션 안에만 있고, 환경 변수 $env:Y는 자식 프로세스까지 상속된다. 이 구분은 bash에서 export 유무로 갈리는 것과 같다. 두 쪽에서 같은 시험을 했다.

$ x=shell-only
                    $ export Y=exported
                    $ bash -c 'echo "x=[$x] Y=[$Y]"'
                    x=[] Y=[exported]
$x = 'shell-only'
                    $env:Y = 'exported'
                    'bash $PATH -> [' + $PATH + ']   (the PowerShell variable $PATH is empty)'
                    '$env:PATH has entries: ' + (($env:PATH -split ';').Count -gt 3)
                    'child process sees:'
                    powershell.exe -NoProfile -File C:\demo\child.ps1
                    (Get-ChildItem Env: | Where-Object { $_.Name -eq 'Y' }).Value
                    Remove-Item Env:\Y
                    'after Remove-Item Env:\Y -> [' + $env:Y + ']'
bash $PATH -> []   (the PowerShell variable $PATH is empty)
                    $env:PATH has entries: True
                    child process sees:
                    x=[] Y=[exported]
                    exported
                    after Remove-Item Env:\Y -> []

자식 프로세스(child.ps1은 $x와 $env:Y를 한 줄로 출력한다)가 본 것은 bash와 같은 x=[] Y=[exported]이다. 한 가지 함정은 이름이다. bash의 $PATH는 환경 변수이지만, PowerShell에서 $PATH는 그냥 정의되지 않은 일반 변수이어서 비어 있다. 환경 변수는 $env:PATH로 읽고, 구분자는 ;이다. 환경 변수를 지우는 것은 Remove-Item Env:\Y이며, 환경 변수 전체는 Env: 드라이브로 Get-ChildItem에 목록화된다.

  • export가 필요한 값은 $env:이름으로 만들고, 스크립트 내부에서만 쓰는 값은 일반 변수로 둔다.
  • $PATH처럼 bash에서 익숙한 이름이 PowerShell에서는 빈 변수일 수 있다. $env: 접두사를 잊지 않는다.
  • 환경 변수는 Env: 드라이브를 통해 파일처럼 나열하고 삭제할 수 있다.

와일드카드는 누가 푸는가 - 셸이 아니라 cmdlet

bash에서 *.log는 명령이 실행되기 전에 셸이 파일 목록으로 풀어 인수로 넘긴다. 같은 입력을 bash에서 확인했다.

$ echo *.log
                    app.log old.log
                    $ node -e "console.log(JSON.stringify(process.argv.slice(1)))" *.log
                    ["app.log","old.log"]

PowerShell은 다르다. about_Wildcards는 와일드카드가 -like 연산자나 「와일드카드를 받는 모든 매개 변수」에서 쓰이며, cmdlet마다 어느 매개 변수가 와일드카드를 받는지 도움말에 적혀 있다고 설명한다. 그러니 네이티브 프로그램에는 풀리지 않은 문자열이 그대로 간다.

'Get-ChildItem *.log ->'
                    (Get-ChildItem *.log).Name
                    'Write-Output *.log ->'
                    Write-Output *.log
                    'native program (node) args for *.log ->'
                    node -e "console.log(JSON.stringify(process.argv.slice(1)))" *.log
                    'cmd /c echo *.log ->'
                    cmd /c echo *.log
Get-ChildItem *.log ->
                    app.log
                    old.log
                    Write-Output *.log ->
                    *.log
                    native program (node) args for *.log ->
                    ["*.log"]
                    cmd /c echo *.log ->
                    *.log

Get-ChildItem *.log는 cmdlet이 패턴을 스스로 해석해 두 파일을 돌려준다. 반면 Write-Output *.log와 네이티브 프로그램(node)과 cmd /c echo는 *.log 글자를 그대로 받았다. 셸이 대신 풀어 주는 일이 없으므로, 네이티브 프로그램에 파일 목록을 넘기려면 Get-ChildItem으로 이름을 얻어 인수로 넘겨야 한다. 와일드카드를 해석하는 주체가 달라서 생기는 결과가 하나 더 있다. 대괄호는 와일드카드 문자이므로 이름에 대괄호가 든 파일은 그대로는 찾아지지 않는다.

'Test-Path file[1].txt              -> ' + (Test-Path 'C:\demo\t\file[1].txt')
                    'Test-Path -LiteralPath file[1].txt -> ' + (Test-Path -LiteralPath 'C:\demo\t\file[1].txt')
                    'Get-ChildItem file[1].txt (count)   -> ' + @(Get-ChildItem 'file[1].txt' -ErrorAction SilentlyContinue).Count
                    'Get-ChildItem file[[]1].txt (count)  -> ' + @(Get-ChildItem 'file[[]1].txt' -ErrorAction SilentlyContinue).Count
                    'Get-ChildItem -LiteralPath (count)  -> ' + @(Get-ChildItem -LiteralPath 'file[1].txt').Count
                    'Get-ChildItem -Filter file[1].txt   -> ' + @(Get-ChildItem -Filter 'file[1].txt').Count
Test-Path file[1].txt              -> False
                    Test-Path -LiteralPath file[1].txt -> True
                    Get-ChildItem file[1].txt (count)   -> 0
                    Get-ChildItem file[[]1].txt (count)  -> 1
                    Get-ChildItem -LiteralPath (count)  -> 1
                    Get-ChildItem -Filter file[1].txt   -> 1

about_Wildcards는 대괄호가 문자 범위나 특정 문자 집합에 일치하는 와일드카드이며, 와일드카드 문자가 든 파일 이름에 접근하려면 이스케이프해야 하고, 한 방법이 -LiteralPath 매개 변수라고 적는다. file[1].txt 패턴은 file1.txt에 일치하므로 이 폴더에서는 0건이다. -LiteralPath와 [[] 형태는 1건을 찾았고, -Filter도 1건이었다. 같은 문서는 파일 시스템 항목의 와일드카드 일치가 문자열의 경우와 다르게 동작한다고도 적는다. 마지막으로 -Include의 동작이다.

'-Include *.log alone      -> ' + @(Get-ChildItem -Include *.log).Count
                    '-Include with C:\demo\t\* -> ' + @(Get-ChildItem C:\demo\t\* -Include *.log).Count
                    '-Filter *.log             -> ' + @(Get-ChildItem -Filter *.log).Count
-Include *.log alone      -> 0
                    -Include with C:\demo\t\* -> 2
                    -Filter *.log             -> 2

-Include만 단독으로 쓰면 이 폴더에서 0건이었고, 경로 끝에 \*를 붙이면 2건이 나왔다. 이름 패턴만 쓸 때는 -Filter가 같은 2건을 돌려주었다. bash의 ls *.log를 옮기는 가장 단순한 형태는 Get-ChildItem -Filter *.log이다.

  • 네이티브 프로그램에 와일드카드 목록을 넘기려면 PowerShell이 풀어 주지 않으므로 Get-ChildItem의 결과를 인수로 직접 만든다.
  • 이름에 [ 또는 ]가 든 파일은 -LiteralPath로 접근한다.
  • -Include는 경로 패턴과 함께 쓴 경우와 단독으로 쓴 경우의 결과가 달랐으므로, 단순한 이름 패턴에는 -Filter가 예측하기 쉽다.
  • 같은 *라도 -like 연산자와 파일 시스템 항목은 일치 규칙이 다르다고 문서가 적는다.

객체가 문자열이 될 때 - Format-Table 폭 잘림과 Out-String

객체 파이프라인의 끝에서는 화면에 보이는 표가 객체의 속성을 서식에 맞춰 글자로 바꾼 결과이다. 이때 콘솔 폭이 모자라면 열이 잘린다. 확인에 쓴 객체는 열이 넷이고 Path 값이 117자인 두 행짜리이다. 콘솔 폭은 120이었다.

$rows = 1..2 | ForEach-Object { [pscustomobject]@{ Id = $_; Name = 'item' + $_; Path = ('C:\very\long\path\segment' + $_ + '\') + ('x' * 90); Note = 'note-' + ('y' * 40) } }
                    $rows | Format-Table | Out-String
Id Name  Path
                    -- ----  ----
                     1 item1 C:\very\long\path\segment1\xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx...
                     2 item2 C:\very\long\path\segment2\xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx...

네 열 가운데 Note 열은 아예 사라졌고, Path 열은 ...로 잘렸다. 데이터가 없어진 것이 아니라 표시에서 빠진 것이다. 폭을 넓히는 Out-String -Width로 다시 문자열로 만들면 Note 열이 보인다.

$rows | Format-Table -Wrap -AutoSize | Out-String

                     1 item1 C:\very\long\path\segment1\xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

파일로 저장해도 같은 일이 벌어진다. 같은 객체를 Out-File로 파일에 쓰고 다시 읽은 결과가 표시 형식의 잘림을 그대로 담았다.

$rows | Out-File C:\demo\t\table.txt
                    Get-Content C:\demo\t\table.txt
                    'file width (longest line): ' + ((Get-Content C:\demo\t\table.txt | Measure-Object -Property Length -Maximum).Maximum)
                    $rows[0].Path.Length
Id Name  Path
                    -- ----  ----
                     1 item1 C:\very\long\path\segment1\xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx...
                     2 item2 C:\very\long\path\segment2\xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx...
                    file width (longest line): 119
                    117

콘솔 폭이 120일 때 파일의 가장 긴 줄은 119자이고 Path 속성의 실제 길이는 117자이다. 파일에는 표시용 문자열이 들어갔을 뿐 객체의 값이 저장된 것이 아니므로, 값이 필요한 후처리를 할 거라면 표로 만들지 말고 속성을 직접 선택해 CSV 같은 데이터 형식으로 내보낸다.

Get-ChildItem -File -Filter *.log | Select-Object Name, Length | ConvertTo-Csv -NoTypeInformation
"Name","Length"
                    "app.log","532"
                    "old.log","36"

Out-String의 두 가지 형태도 구분해야 한다. 기본형은 서식을 입힌 결과 전체를 문자열 하나로 만들고, -Stream은 줄마다 문자열 하나씩으로 만든다. 줄 단위로 Select-String에 넘기려면 -Stream이 필요하다.

$s = Get-ChildItem -File -Filter *.log | Out-String
                    $s.GetType().Name + ', lines = ' + ($s -split "`r?`n").Count
                    $l = Get-ChildItem -File -Filter *.log | Out-String -Stream
                    $l.GetType().Name + ' of ' + $l.Count + ' lines'
String, lines = 12
                    Object[] of 11 lines

서식 지정 cmdlet(Format-Table 등)이 내보내는 것은 정렬이나 필터에 쓸 수 있는 원래 객체가 아니라 서식 지시용 객체이다. 이 때문에 Format-*는 파이프라인의 맨 끝에서만 쓴다. 두 줄짜리 파일 목록에 Format-Table Name을 적용해 나온 객체의 형식과 Name 속성을 확인했다.

$ft = Get-ChildItem -File | Select-Object -First 2 | Format-Table Name
                    ($ft | ForEach-Object { $_.GetType().Name }) -join ', '
                    'Name property on those objects: [' + (($ft | ForEach-Object { $_.Name }) -join '') + ']'
FormatStartData, GroupStartData, FormatEntryData, FormatEntryData, GroupEndData, FormatEndData
                    Name property on those objects: []
  • 콘솔에 보이는 표는 값이 아니라 표시이다. 값이 필요하면 Format-*를 쓰기 전에 Select-Object나 Where-Object를 끝낸다.
  • 폭이 넓은 열이 필요하면 Out-String -Width, -Wrap, Format-List 중 하나로 잘림을 피한다.
  • 파일이나 다른 도구로 값을 넘길 때는 표 형식 대신 ConvertTo-Csv 같은 데이터 형식을 쓴다.

별칭의 정체 - ls·cat·curl·wget은 무엇을 부르는가

about_Aliases는 별칭을 cmdlet이나 함수·스크립트·실행 파일의 다른 이름이라고 정의하고, 내장 별칭으로 cd와 ls·dir을 예로 든다. 이 PC의 5.1 세션(-NoProfile)에서 bash에 익숙한 이름 21개를 조회했다.

Get-Alias ls, dir, gci, cat, type, cp, mv, rm, echo, pwd, cd, sort, where, tee, diff, man, ps, kill, sleep, curl, wget -ErrorAction SilentlyContinue | Select-Object Name, Definition | Format-Table -AutoSize

눈에 띄는 것이 두 가지이다. 첫째, curl과 wget이 둘 다 Invoke-WebRequest의 별칭이다. 5.1에서 curl을 치면 curl.exe가 아니라 cmdlet이 실행된다. 실제 실행 파일은 .exe 확장자를 붙여 따로 불러야 한다. 둘째, 이름이 같아도 의미가 다르다. sort는 Sort-Object, diff는 Compare-Object, kill은 Stop-Process, man은 help이다. 별칭이 아닌 이름은 이렇게 나왔다.

그 세션에서는 grep·sed·awk 등이 Git의 실행 파일로 잡히고, find도 Git의 find.exe, curl.exe도 Git의 mingw64 폴더로 잡힌다. 따라서 이 절의 「찾을 수 없음」 목록과 find·curl.exe의 경로는 PATH 구성에 달린 값이며, 아래 표의 「이 PATH에서는 없음」도 같은 조건이다. 별칭이 가리키는 cmdlet은 두 세션에서 같았다.

grep·sed·awk·head·tail·uniq·wc·cut·xargs·which·touch는 첫 출력의 PATH에서 찾아지지 않았다. 이름이 있는 것은 find(Windows의 find.exe), mkdir(함수), curl.exe와 where.exe(실행 파일)이다. where는 5.1에서 Where-Object의 별칭이어서 Windows의 where.exe를 부르려면 where.exe로 써야 한다. 이름 해석의 우선순위도 실행으로 확인했다. 함수를 별칭과 같은 이름으로 정의해도 별칭이 먼저 실행된다.

function r { 'my function ran' }
                    r
                    (Get-Command r -All | ForEach-Object { $_.CommandType.ToString() + ' ' + $_.Name }) -join ' | '
                    function ls { 'my ls function' }
                    (Get-Command ls -All | ForEach-Object { $_.CommandType.ToString() + ' ' + $_.Name }) -join ' | '
                    '(Get-Command ls).CommandType = ' + (Get-Command ls).CommandType

함수 r을 정의하고 불렀지만 실행된 것은 Invoke-History이다. r이 Invoke-History의 별칭이기 때문이다. about_Command_Precedence 문서(5.1 판)는 경로를 지정하지 않으면 Alias, Function, Cmdlet, External executable files 순서로 실행할 명령을 정한다고 적는다. 이 실행에서 Get-Command -All이 나열한 순서(Alias, Function)와 실제로 실행된 것(별칭)은 그 문서와 일치했다. 확인한 것은 r과 ls 두 이름뿐이다. 아래 표는 bash 습관별로 5.1에서 실제 호출되는 것을 정리한 것이다.

bash 손버릇이 실패하는 자리

bash 습관대로 옵션을 붙이면 PowerShell은 구문 분석 단계나 매개 변수 바인딩 단계에서 막는다. 존재하지 않는 경로를 대상으로 실행해 안전하게 확인한 결과이다.

ls -l 2>&1 | Select-Object -First 1 | ForEach-Object { "$_" }
                    rm -rf C:\demo\t\nonexistent 2>&1 | Select-Object -First 1 | ForEach-Object { "$_" }

ls -l에서 -l은 옵션이 아니라 -LiteralPath의 축약형으로 해석되어 인수가 없다는 오류가 났다. rm -rf는 한 덩어리 -rf를 매개 변수 이름으로 읽어 존재하지 않는다는 오류가 났다. 위험한 쪽으로 어긋나지 않고 막혔다는 점은 다행이지만, -Recurse -Force를 정확히 써야 한다. 연산자도 다르다. 5.1에서는 &&가 구문 오류이다.

powershell.exe -NoProfile -Command 'Get-Date && Get-Date'
At line:1 char:10
                    + Get-Date && Get-Date
                    +          ~~

같은 연산자가 Git Bash에서는 정상으로 동작한다(true && echo "and-list ran"이 and-list ran을 출력했다). PowerShell에서는 명령을 ;로 잇고, 앞 명령의 성공 여부는 $?로 검사한다. 한눈에 볼 수 있도록 지금까지 만난 어긋남을 표로 모았다.

확인하지 못한 것

  • PowerShell 7(pwsh). 이 PC에 pwsh가 없어 5.1과의 차이를 실행으로 비교하지 못했다. && 연산자, curl 별칭, Select-String의 기본 인코딩 처리 등 7에서 달라질 수 있는 항목은 열람한 공식 문서 다섯 건에서 다루지 않아 확인하지 못했다.
  • 리눅스의 bash와 GNU 도구. 대조 출력은 Windows의 Git Bash(MSYS 빌드, GNU grep 3.0)에서 얻었으므로 배포판별 grep·sort의 동작과 로캘 영향은 확인하지 못했다.
  • 콘솔 폭 120 이외의 폭에서의 Format-Table 잘림 위치. 이번 실행은 폭 120에서만 했다.
  • 이 PC의 -NoProfile 세션 밖의 별칭. 사용자 프로필이나 모듈이 별칭을 추가하거나 덮어쓰면 목록이 달라질 수 있다.
  • 한글이나 BOM 없는 UTF-8 파일을 Select-String으로 검색할 때의 인코딩 처리. 실습 파일은 ASCII만 담았고, 문서가 적은 BOM 기반 인코딩 추정은 실행하지 않았다.
  • 개수가 같은 Group-Object 결과의 정렬 순서가 항상 같은지. 한 번의 실행에서 ERROR가 WARN 앞에 나왔다는 것만 확인했다.
  • 큰 파일에서의 성능 차이. Get-Content와 Select-String, bash 도구의 처리 속도는 측정하지 않았다.
