sed -i Is Not an In-Place Edit — Preview, Backup, and diff Sequence Before Bulk Substitution

File ID Changes, Broken Hard Links, and CRLF Alterations with a Safe Replacement Pipeline

2026-09-29 Dev & Infra

In countless automation scripts, deployment pipelines, and configuration updates, the command most frequently invoked to alter text inside files is sed -i. Because of the option name --in-place, engineers naturally assume that this tool opens the existing file on the physical disk and modifies its byte stream directly in place. However, empirical measurements and official documentation demonstrate the exact opposite reality: sed -i is not an in-place editor. Instead, it generates an entirely new temporary file, writes the transformed stream into it, and then renames it to the original file name.

Running bulk substitutions without knowing about this swap produces surprises. The other name of a hard-linked file does not receive the change, and the file ID changes. In Git Bash on Windows in particular, even files where no pattern matched had every CRLF line ending turned into LF, so files nobody meant to touch show up as modified. This guide shows those results from recorded runs and lays out a 5-step routine to follow before a bulk substitution.

All empirical measurements documented herein were recorded directly within the following environment: Windows 10 Pro 10.0.19045, Git Bash (GNU sed 4.9, GNU Awk 5.0.0), curl 8.12.1 (Schannel), git 2.48.1.windows.1, Windows PowerShell 5.1, Python 3.13.3, Node 22.16.0 (non-administrator privilege). For general line ending fundamentals, refer to the CRLF vs LF Guide. For shell expansion behaviors, review the Shell Quoting Rules Guide. For cross-dialect regular expressions, see the Portable Regular Expressions Guide. For idempotent automation architecture, consult the Idempotent Script Design Guide.

1. How sed -i Works — Why It Replaces Rather Than Modifies In Place

The flag -i stands for in-place. Users intuitively assume that it manipulates the physical disk blocks allocated to the target inode. However, sed was conceived as a stream editor designed to read lines sequentially from standard input, process them inside an internal pattern space buffer, and emit output to standard output. It does not perform random access or file seeking operations on disk blocks.

Temporary File Creation and Rename

The Command-Line Options section of the GNU sed manual describes -i this way: GNU sed creates a temporary file and sends output to it rather than to standard output, and when the end of the file is reached, the temporary file is renamed to the original file name.

So the original data is not edited where it sits; a newly written file takes over the original name. With a backup extension (-i.bak), the pre-edit content remains under the suffixed name, such as app.conf.bak (see the run in section 6). The runs below show what this swap does to hard links and line endings.

Fundamental Differences from Redirection Overwriting (>)

Overwriting with shell redirection, as in printf 'y\n' > keep.txt, writes new content into the same file. In the run, keep.txt kept the same inode number before and after the overwrite. sed -i, by contrast, swaps in a new file, so the number changes. The next section shows, with recorded runs, what that difference does to hard links and line endings.

2. Empirical Verification: File ID Shifts and Severed Hard Links

To demonstrate this replacement behavior definitively, concrete test commands were executed and recorded on real storage targets.

Measuring Inode and NTFS File ID Alterations

Under Git Bash, a sample configuration file conf.txt was created, and its inode numbers and NTFS file IDs were measured before and after running sed -i using stat and fsutil.

printf 'host=old.example\nport=80\n' > conf.txt
ls -i conf.txt; stat -c 'ino=%i links=%h mtime=%y' conf.txt
sed -i 's/old/new/' conf.txt
ls -i conf.txt; stat -c 'ino=%i links=%h mtime=%y' conf.txt
# compare: overwrite with >
printf 'x\n' > keep.txt; ls -i keep.txt; printf 'y\n' > keep.txt; ls -i keep.txt
# Windows file ID
fsutil file queryfileid conf.txt; sed -i 's/new/newer/' conf.txt; fsutil file queryfileid conf.txt

The terminal emitted the following output:

=== before
57702370226752894 conf.txt
ino=57702370226752894 links=1 mtime=2026-09-29 07:44:07.786669900 +0900
=== after sed -i
314689023964208355 conf.txt
ino=314689023964208355 links=1 mtime=2026-09-29 07:44:08.149979700 +0900
host=new.example
port=80
=== compare: in-place write via > redirect keeps id?
57983845203463550 keep.txt
57983845203463550 keep.txt
=== fsutil file id (before)
File ID: 0x0000000000000000045e00000019dce3
=== fsutil file id (after sed -i)
File ID: 0x000000000000000000230000001f9069

Before modification, conf.txt held inode 57702370226752894. Immediately following sed -i, the inode jumped to 314689023964208355. Similarly, the NTFS file identifier observed through fsutil changed from 0x0000000000000000045e00000019dce3 to 0x000000000000000000230000001f9069. Meanwhile, the control file keep.txt rewritten via shell redirection operator (>) retained its exact inode 57983845203463550 across both write operations. This proves conclusively that sed -i replaces the physical file.

Hard Link Synchronization Severance Test

When multiple directory entries point to the same inode via hard links, executing sed -i silently breaks their synchronization.

printf 'a=1\n' > orig.txt; ln orig.txt hard.txt
stat -c '%n ino=%i links=%h' orig.txt hard.txt
sed -i 's/1/2/' orig.txt
stat -c '%n ino=%i links=%h' orig.txt hard.txt
echo "orig: $(cat orig.txt) / hard: $(cat hard.txt)"

The resulting terminal trace was recorded as follows:

orig.txt ino=314970498940919011 links=2
hard.txt ino=314970498940919011 links=2
orig.txt ino=28147497673134196 links=1
hard.txt ino=314970498940919011 links=1
orig: a=2 / hard: a=1

Initially, both paths pointed to inode 314970498940919011 with a link count of 2. After running sed -i against orig.txt, orig.txt received a fresh inode (28147497673134196) with a link count of 1. Consequently, orig.txt reflected a=2, while hard.txt remained stranded on the old inode holding a=1. The file edited through one name is no longer the file seen through the other.

3. Line Ending Traps: CRLF Forced to LF with Zero Matching Lines

A common accident when working on Windows is an unintended mass conversion of line endings. The GNU sed in Git Bash has a trap here. Below is what happened when sed was run on a CRLF file.

Git Bash sed Carriage Return Handling and -b Flag

A CRLF text file was processed with various sed substitution commands, and byte-level octal dumps were examined via od -c.

printf 'line1=a\r\nline2=b\r\n' > crlf.txt
file crlf.txt; od -c crlf.txt
sed -i 's/a/A/' crlf.txt
file crlf.txt; od -c crlf.txt
sed -i -b 's/a/A/' crlf_b.txt; file crlf_b.txt; od -c crlf_b.txt      # -b(binary)
sed 's/a$/Z/' crlf_c.txt | od -c | head -2                           # $ anchor
sed 's/\r$//' crlf_c.txt | od -c | head -2
printf 'p=a\r\n' | sed 's/a$/Z/' | od -c                               # also in a pipe

The execution output reveals critical behaviors:

=== CRLF before
crlf.txt: ASCII text, with CRLF line terminators
0000000   l   i   n   e   1   =   a  \r  \n   l   i   n   e   2   =   b
0000020  \r  \n
=== after sed -i 's/a/A/'
crlf.txt: ASCII text
0000000   l   i   n   e   1   =   A  \n   l   i   n   e   2   =   b  \n
=== sed -i -b (binary)
crlf_b.txt: ASCII text, with CRLF line terminators
0000000   l   i   n   e   1   =   A  \r  \n   l   i   n   e   2   =   b
0000020  \r  \n
=== $ anchor test: s/a$/Z/ on CRLF
0000000   l   i   n   e   1   =   Z  \n   l   i   n   e   2   =   b  \n
=== s/\r$// strip
0000000   l   i   n   e   1   =   a  \n   l   i   n   e   2   =   b  \n
(pipe) 0000000   p   =   Z  \n

Two things stand out. First, Git Bash's sed does not see the carriage return (CR, \r). So the end anchor $ matched in front of the CR (a$ matched the a\r line and became Z). Second, a single sed -i stripped the CR even from line2, which had no substitution, so the whole file ended up with LF endings. With -b (--binary), CRLF stayed intact. The GNU sed manual says that where the system distinguishes text files from binary files, as MS-DOS, Windows, and Cygwin do, text lines are separated by CR and LF and sed does not see the ending CR, and that --binary is only effective on such systems. This result is therefore the behavior of the Windows (MSYS) build. Whether GNU sed on Linux behaves the same is covered in section 8.

Line Ending Corruption on Zero-Match Files

The hazard escalates dramatically when sed -i is run against files that contain zero instances of the target search string.

printf 'x=1\r\ny=2\r\n' > nomatch.txt
stat -c 'ino=%i' nomatch.txt; sed -i 's/ZZZ/QQQ/' nomatch.txt; stat -c 'ino=%i' nomatch.txt; file nomatch.txt

The resulting output was:

ino=153685337286086914
ino=10977524093784323
nomatch.txt: ASCII text

Not a single line matched, yet the inode changed from 153685337286086914 to 10977524093784323. The file had been created with CRLF by printf, but file reported plain ASCII text (no with CRLF line terminators), meaning its line endings became LF. Running sed -i across many files at once changes the line endings of files that needed no change, so files you never substituted all show up in git diff.

Table 2. Empirical Verification of CRLF Line Ending Alterations Under Windows Git Bash
Executed Command Matching Targets Present EOL Format Result Inode State Practical Impact
sed -i 's/a/A/' file Yes (1 match) CRLF → LF (all lines) Not measured for this file Untouched lines lose CR characters
sed -i -b 's/a/A/' file Yes (1 match) CRLF preserved Not measured for this file -b kept CRLF
sed -i 's/ZZZ/QQQ/' file No (0 matches) CRLF → LF (all lines) Altered (new file) Zero-match files silently corrupted to LF

4. Option Syntax Hazards: The -iE Extension Trap and Empty Files (-n -i)

Command line option ordering rules in GNU sed present dangerous pitfalls when flags taking optional arguments are bundled together.

The -iE Flag Collision and Backup Suffix E

Combining extended regular expressions (-E) with in-place editing (-i) requires precise ordering.

printf 'a=1\n' > ie.txt
sed -iE 's/(a)=1/\1=2/' ie.txt; echo "exit=$?"; ls ie.txt*
sed -Ei 's/(a)=1/\1=2/' ie.txt; cat ie.txt
sed -iE 's/a=2/a=3/' ie.txt; ls ie.txt*; echo "ie.txt: $(cat ie.txt) / ie.txtE: $(cat ie.txtE)"
printf 'k1\nk2\n' > n.txt; sed -n -i 's/k1/K1/' n.txt; echo "size after: $(wc -c < n.txt)"

The resulting output was recorded as follows:

sed: -e expression #1, char 13: invalid reference \1 on `s' command's RHS
exit=1
ie.txt
---
a=2
exit=0
ie.txt
ie.txtE
ie.txt: a=3 / ie.txtE: a=2
size after: 0

Under GNU sed parsing rules, any characters directly appended to -i without an intervening space are interpreted as the backup extension. Therefore, -iE is parsed identically to --in-place=E. Instead of enabling extended regular expressions, sed treats the letter E as the backup file extension, leaving BRE active and causing invalid reference \1 syntax errors. If a basic substitution pattern without groups is used, sed silently generates an unwanted backup file named ie.txtE. The correct ordering is -Ei or separated flags -E -i.

Catastrophic File Truncation Under -n and -i

A catastrophic failure occurs when an operator converts a preview command using -n into an execution command by appending -i while omitting the print instruction (p). As demonstrated by sed -n -i 's/k1/K1/' n.txt, the resulting file size dropped to exactly 0 bytes. Because -n suppresses default pattern space output and no p command emitted text, sed streamed zero bytes into the replacement file and swapped it into place, erasing the original data with no backup. The GNU sed manual likewise tells readers to be cautious when using -n with -i, since the former disables automatic printing and the latter changes the file in place without a backup.

Table 3. Analysis of Option Bundling Combinations and Failure Hazards
Option Combination Internal Parser Interpretation Execution Outcome Risk Classification
-iE --in-place=E (backup suffix E) ERE disabled error or .txtE file created Warning (Faulty Execution)
-Ei or -E -i ERE enabled + in-place swap Successful regex substitution Safe (Recommended Syntax)
-n -i (without p) Suppress output + in-place swap Complete truncation to 0 bytes Critical (Instant Data Loss)

5. Replacement String Collisions: Ampersands (&) and Path Delimiters

Beyond invocation options, substitution expression syntax contains inherent parsing rules that cause silent data corruption when handling dynamic strings.

Ampersand (&) Expansion and Shell Variable Pollution

In the replacement section of s/pattern/replacement/, an unescaped & is a special meta-character representing the entire matched substring.

echo 'name=Tom' | sed 's/Tom/Tom & Jerry/'
echo 'name=Tom' | sed 's/Tom/Tom \& Jerry/'
echo 'root=/usr/local/app' | sed 's/\/usr\/local/\/opt/'
echo 'root=/usr/local/app' | sed 's//usr/local//opt/'; echo "exit=$?"
NEW=/opt/app; echo 'root=OLD' | sed "s/OLD/$NEW/"; echo "exit=$?"
echo 'root=OLD' | sed "s|OLD|$NEW|"
V='A&B'; echo 'x=OLD' | sed "s|OLD|$V|"
echo 'ab' | sed -E 's/(a)(b)/[\10]/'
echo 'port=80' | sed -E 's/(port)=([0-9]+)/\1=8\2/'

The recorded terminal output was:

name=Tom Tom Jerry
name=Tom & Jerry
root=/opt/app
sed: -e expression #1, char 8: unknown option to `s'
exit=1
sed: -e expression #1, char 8: unknown option to `s'
exit=1
root=/opt/app
x=AOLDB
[a0]
port=880

When executing s/Tom/Tom & Jerry/, the output became Tom Tom Jerry because & expanded into the matched string Tom. To insert a literal ampersand, it must be escaped as \&. This behavior causes subtle bugs when interpolating shell variables: passing V='A&B' transformed x=OLD into x=AOLDB, injecting the matched text into the middle of the variable value. All dynamic shell variables injected into sed substitution strings must have their ampersands pre-escaped.

Path Substitution Collisions and Delimiter Selection

When a variable holding a path, NEW=/opt/app, is placed into s/OLD/$NEW/, the slashes in the path are read as delimiters and sed fails with unknown option to `s' (exit code 1). According to the GNU sed manual, the / characters in an s command may be uniformly replaced by any other single character. Using a vertical bar, s|OLD|$NEW| printed root=/opt/app correctly. Separately, the backreference \10 was treated as \1 followed by a literal 0 rather than a tenth group ([a0]), and \1=8\2 joined 8 and 80 into 880, so take care when a digit follows a backreference.

Table 4. Empirical Behavior of Replacement Meta-characters and Delimiter Collisions
Input Pattern & Command Actual Output Failure Mechanism Correct Implementation
s/Tom/Tom & Jerry/ Tom Tom Jerry & expands to matched 'Tom' s/Tom/Tom \& Jerry/
V='A&B'; s|OLD|$V| AOLDB Variable & expands to 'OLD' Replace & with \& before passing the variable
s/OLD//opt/app/ unknown option to `s' (exit 1) Path slash terminates command prematurely Switch delimiter: s|OLD|/opt/app|

6. The 5-Step Safe Bulk Substitution Pipeline

Based on the runs above, here is a 5-step order to follow before changing files. Instead of firing a single sed -i, check the result at each step.

The Step-by-Step Verification Pipeline

The commands below were actually run in the order preview → matching line count → apply with backup → diff.

printf 'root=/usr/local/app\nlog=/usr/local/app/log\nname=Tom\n' > app.conf
sed -n 's|/usr/local/app|/opt/app|gp' app.conf          # 1) preview
grep -c '/usr/local/app' app.conf                        #    matching line count
sed -i.bak 's|/usr/local/app|/opt/app|g' app.conf        # 2) apply with backup
ls app.conf*
diff app.conf.bak app.conf; echo "diff exit=$?"          # 3) check

The resulting output was:

=== 1) preview
root=/opt/app
log=/opt/app/log
=== match count
2
=== 2) apply with backup
app.conf
app.conf.bak
=== 3) diff
1,2c1,2
< root=/usr/local/app
< log=/usr/local/app/log
---
> root=/opt/app
> log=/opt/app/log
diff exit=1

The core disciplines of this pipeline include:

  • Step 1 (Verify Match Count): Execute grep -c 'pattern' file. If the count is 0, skip the file. Even with zero matching lines, sed -i created a new file, and in Git Bash it also changed the line endings.
  • Step 2 (Preview Output): Run sed -n 's|pattern|replacement|gp' file to emit only modified lines. Confirm that the emitted line count matches Step 1.
  • Step 3 (Inspect Line Endings): Check file formatting with file file and od -c file | head. If running under Windows Git Bash on CRLF files, attach the -b flag.
  • Step 4 (Execute with Backup): Run sed -i.bak 's|pattern|replacement|g' file to preserve file.bak.
  • Step 5 (Diff Verification): Execute diff file.bak file. An exit status of 1 indicates expected differences.

7. GNU sed vs BSD sed Dialect Differences and Portability

Scripts that move between Linux (GNU sed) and macOS or FreeBSD (BSD sed) face different -i argument handling. The BSD side of this section was not run on macOS; it follows the documentation.

Argument Handling Differences in In-Place Editing

According to the documentation, the difference is as follows:

  • GNU sed: The backup extension after -i is an optional argument attached to the flag. To edit without a backup, write sed -i 's/.../.../' file; to keep one, attach it as in sed -i.bak 's/.../.../' file (the form used in this article's runs). The manual states that sed -iE is equivalent to --in-place=E, so characters attached to -i are read as the extension.
  • BSD sed (FreeBSD / macOS): The FreeBSD manual lists the form -i extension and says that if a zero-length extension is given, no backup will be saved. Its example is sed -i '' -e 's/foo/bar/g' test.txt. The same page says a zero-length extension is not recommended, because a file may be corrupted or left with partial content in situations such as exhausted disk space.

Cross-Platform Scripting Implementation Strategy

The form usable on both sides is sed -i.bak. GNU accepts an attached extension and BSD takes the extension as an argument, so creating a backup, checking with diff, and deleting the backup if it is not needed fits both documents. This part follows the documentation only and was not run on macOS.

Table 7. Syntax Comparison Between GNU sed and BSD sed (macOS)
Target Operation GNU sed (Linux / Git Bash) BSD sed (macOS / FreeBSD) Recommended Portable Syntax
In-place edit without backup sed -i 's/.../.../' file sed -i '' 's/.../.../' file Not recommended (requires OS branching)
In-place edit with backup sed -i.bak 's/.../.../' file sed -i.bak 's/.../.../' file sed -i.bak followed by rm file.bak

8. Unverified Items

Due to testbed constraints, the following specific behaviors were not verified through direct execution:

  • Direct Empirical Verification of Symlink Severance Under sed -i: Within the test environment (Windows 10 standard user privilege, developer mode disabled), Git Bash ln -s created file copies rather than true symbolic links (NOT a symlink), and native symlink creation commands failed with Operation not permitted. Therefore, the physical replacement of a symbolic link by a regular file was not directly observed. The GNU sed manual states: "The default behavior is to break the symbolic link, so that the link destination will not be modified."
  • CRLF Behavior in Native Linux Environments: The automatic line ending conversion (CRLF → LF) and CR ignoring behavior documented in Experiment 3 were measured in Windows MSYS Git Bash. Whether GNU sed on native Linux kernels exhibits identical line ending conversions was not tested directly on a Linux host.
  • Native BSD sed Execution on macOS/FreeBSD: The sed -i '' syntax and backup requirements documented for BSD sed derive strictly from official FreeBSD manual pages and were not verified via direct execution on macOS hardware.

## 1. 5-Step Safe Bulk Substitution Pipeline

Always execute the following sequence before modifying files directly:

1. **Verify target line count**: Count matching lines using `grep -c 'pattern' file`. If it is 0, skip the file.
2. **Preview replacement lines**: Use `sed -n 's|pattern|replacement|gp' file` to print only the lines that will change, comparing the count with step 1.
3. **Inspect line endings (CRLF/LF)**: Check the file format with `file file` or `od -c file | head`. Under Git Bash, decide whether `-b` is required to preserve CRLF.
4. **Apply substitution with backup**: Execute `sed -i.bak 's|pattern|replacement|g' file` to perform the substitution while keeping `file.bak`.
5. **Inspect diff**: Check modifications with `diff file.bak file` (an exit status of 1 means differences exist; it is not an error).

## 2. Symptoms, Causes, and Mitigations (Empirical)

| Symptom | Cause | Mitigation |
|---|---|---|
| Untouched files appear fully modified in git diff | Git Bash sed converts CRLF to LF (even when 0 lines match) | Use `sed -i -b`, or run it only on the files that need changing |

## 3. Core sed -i Pitfalls Checklist

- [ ] `sed -i` changes inode numbers and NTFS file IDs, breaking hard links (measured in Git Bash).
- [ ] In Git Bash (MSYS), line endings are converted to LF even if 0 lines match.
- [ ] To preserve CRLF line endings in Git Bash, add the `-b` (--binary) flag.
- [ ] When using extended regular expressions, write `-Ei` rather than `-iE`.
- [ ] When injecting shell variables into substitution strings, ensure `&` characters are escaped to `\&`.
- [ ] (Documentation only) In BSD/FreeBSD sed, editing without a backup requires an empty extension: `sed -i ''`. The manual does not recommend a zero-length extension.
- [ ] (Documentation only) For use across GNU and BSD, run `sed -i.bak` and delete the backup file afterward if not needed.
