智能体在代码里该是什么 - 类、图与配置文件各自遮住了什么

选定抽象的那一刻，调试、恢复与迁移的成本也一并定下

2026年9月1日 开发/基础设施

做智能体时最先要选的既不是模型也不是工具，而是在代码里把智能体叫作什么。是类，是图上的一个节点，是配置文件里的一项，还是写着提示词的一份文本文件。第一天它看上去像语法偏好，两个月后会以账单的形式回来。

账单的项目大体是固定的：确认到底有什么发给了模型要花多久，中断的任务能不能接上，读日志是否得同时打开框架文档，换到别的东西时要丢掉什么。抽象会悄悄把这四项预先定好。引出这篇文章的仓库只是把四类里的一类推得最鲜明，适合当起点，介绍那个项目并不是目的。

本文比较几种智能体框架的设计方式，但不评判孰优孰劣。引用的设计事实来自各项目官方文档与仓库，为2026年9月初的状态，这个领域在版本之间变动频繁。

缘起 - 当智能体成为一个 Python 类

NVIDIA-NeMo 组织下的 labs-OO-Agents 仓库正如其名。字段是状态，方法是能力，文档字符串就是提示词，类型标注就是契约。函数体为 ... 的方法在运行时由模型填上，有代码的方法则留作确定性的 Python。

from nooa import Agent

class SupportAgent(Agent):
    """You are a support agent."""
    order_db: OrderDB

    def is_refund_eligible(self, order: Order) -> bool:
        return order.delivered and order.days_since_delivery <= 30

    async def triage(self, message: str, order: Order) -> Ticket:
        """Create a typed support ticket."""
        ...

这十二行里聚了通常分散在三处的东西：系统提示词、工具模式、回调。方法名、参数与文档字符串本身就是提示词，改文档字符串就等于改指令。模型则在能访问 self 与已导入模块的 Jupyter 式 REPL 里写 Python 来行动。

  • PyPI 包 nooa 的公开版本从7月30日的 0.0.7 到8月18日的 0.0.9
  • 许可证是 Apache-2.0，LICENSE 里的版权署名是 NVIDIA CORPORATION & AFFILIATES。这不是个人实验，是内部实验室的产物
  • 文档自称研究性软件。AST 检查与模块阻断清单只是纵深防御的一层，并非隔离边界，隔离边界被明确写作容器或虚拟机这类操作系统层面的手段
  • 同名论文于7月22日发布在 arXiv 上。作者15人，列出六个概念：带类型的输入输出、对活对象的引用传递、作为行动的代码、循环设计、显式的对象状态、模型可调用的宿主 API

以上是从仓库与论文摘要直接确认到的。本文关心的是接下来的问题：为什么偏偏是类，以及一旦决定叫它类，六个月后有什么已经定死了。拆解某一个框架的工作已经在谈 TypeScript 沙箱框架的那篇里做过，这里看的是表达方式本身。

表达方式收敛为四类

把眼下能用的东西摆开，表达智能体的方式大体收敛为四类。每一类让自然的代码形态不同，因此让什么变得别扭也不同。

类别智能体是什么变得自然的代码变得别扭的事
对象类的实例。字段是状态，方法是能力用继承复用共通行为，用类型钉住契约把流程展示成一张图
图与状态机节点与边。状态在图中流动用结构表达分支、并行与中断点智能体的身份被打散到各节点
声明式配置YAML 或 JSON 条目，罗列角色、目标与工具非开发者也能改，变更记录短条件逻辑，最终会逃向代码
提示词文件一页 Markdown，正文即系统提示词原样读提示词并用 diff 审阅类型、复用与组装

真实实现很少纯粹停在四类中的某一类。不过主要那一类在文档首屏就能看出来。第一个示例是类，就偏对象；是注册节点的代码，就偏图。

  • Pydantic AI 的 Agent 是对依赖类型与输出类型泛型的类。文档举出 Agent[Foobar, list[str]] 这样的写法为例
  • OpenAI Agents SDK 的 Agent 以名称、指令、模型、工具、交接与输出类型为字段，并对上下文类型泛型。指令的位置也可以放一个函数
  • LangGraph 以由用户定义的 State 参数化的 StateGraph 为核心。节点接收状态并返回更新，边决定下一个节点
  • CrewAI 以角色、目标与背景故事界定智能体。新项目采用把智能体放在 agents/<名称>.jsonc 的配置优先方式，旧的 config/agents.yaml 仍受支持
  • AutoGen 的核心文档把智能体定义为通过消息通信、维持自身状态、并对收到的消息作出行动的软件实体。消息是唯一的接触点
  • Claude Code 的子智能体是带 YAML 前置元数据的 Markdown 文件，正文原样成为系统提示词
---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep
model: sonnet
---

You are a code reviewer. When invoked, analyze the code and provide
specific, actionable feedback on quality, security, and best practices.

前面那个类的示例与这份文件就是光谱的两端。一端把类型与继承尽量拉过来用，另一端用一份文本文件就收工。要点不在于哪一端正确，而在于每个位置付出的代价不同。

用对象包起来能得到什么

面向对象这一侧的好处不是优雅，而是来自工具替你做的那些事。

  • 编辑器知道。补全生效，参数名打错在保存时就被抓住，改名会一路跟到调用处。提示词只以字符串常量存在时，这些都不会发生
  • 类型钉住边界。声明了输出类型，模型吐出奇怪东西时当场就被拦下，不会跑到三层之上莫名炸开
  • 共通行为汇到一处。重试、预算上限、审计日志在基类里写一次，所有子类都生效
  • 测试替身容易塞进去。只覆写调用模型的方法，其余部分就能不带模型地测试。能不能在 CI 里跑智能体，就在这里分野
  • 确定性代码与模型判断在同一个文件里。退款资格判定用 Python 写，来件分类交给模型。两者散开，责任边界就模糊了

最后一项其实最大。智能体代码能否长久存活，多半取决于有没有把本可以写成规则的东西交给模型。问模型配送是否在三十天内，大多数时候答对，偶尔答错，而那个偶尔就成了退款事故。有函数体即确定、函数体是 ... 即归模型，这条约定把那道边界直接刻进了语法。

用对象包起来会遮住什么

代价集中在一处：真正发给模型的提示词，在源码里任何地方都不再被完整写出。它是文档字符串、签名、基类追加的片段以及运行时注入合起来的结果，最终形态必须算出来才知道。

这个问题与继承深度成正比。在基类里放一行共通指令是复用，但读往下三层的类的人并不知道那一行挂在上面。工具清单也一样。一旦由装饰器注册、由混入合并、在运行时被过滤，只读源码就数不出挂了几个工具。

Anthropic 关于智能体工程的文章也指向同一处。框架常常增加一层遮住底下提示词与响应的抽象，使调试变难；而对底层实际发生什么的错误假设，是常见的出错来源。这是对堆叠层次这一行为本身的评论，不是针对某个产品。

  • 遮蔽变危险的时刻是事故发生三十分钟后。那时需要的是模型收到的全文
  • 所以第一天要确认的不是功能清单，而是把最终载荷落到文件里的方法。若一行就能做到，继承再深也扛得住
  • 默认是否开启追踪也是选型标准。上面那个仓库写明所有调用默认被追踪。默认开着与可以打开是两回事
  • 把继承保持得浅也是办法。两层还读得动，四层往下基本没人读
  • 与其把共通的提示词片段当字符串埋在类里，不如抽到文件中按名引用，至少还能搜索

图展示了什么，又打散了什么

图这一侧的强项在于流程变成了数据结构。是数据结构就能画出来、能检查、能用结构定义在何处停下。散在命令式函数里的 if 分支，这三件事一件也做不到。

LangGraph 的文档把这个结构讲得很干净：节点干活，边告诉你接下来做什么。状态模式成为所有节点与边的输入模式，每个键上挂一个归约器。不显式指定归约器，该键的更新一律是覆盖。这个默认值是微妙缺陷的常客。本该累积的对话记录被设成覆盖，就只剩最后一条，而症状表现为上下文丢失，很容易被误判成提示词问题。

图付出的代价是身份。要看一个智能体在做什么，得沿着节点与边走一遍。流程越复杂图越占优，单个智能体越厚重对象越占优。该拆成几个，写在谈子智能体数量的那篇里。

  • 图倾向于让代码掌握流程。节点必须事先注册，运行中很难冒出未定义的路径
  • 这个性质有利于可复现性，却不利于意料之外的输入。未定义的情形也会被引到已定义的路径上
  • 图定义里框架专有词汇很多，属于最难搬走的资产
  • 反过来，能用结构定义中断点是图独有的优势，在有人工审批介入的流程里差别很大
  • 显式写出归约器这个习惯便宜且有效。即使覆盖才是对的键也写上，后来的人就能分辨是有意还是疏忽

声明式配置撞上的天花板

配置文件方式的好处是社会性的。非开发者能打开、读懂并修改，变更记录短而清楚，评审时容易讨论。如果是产品经理直接改提示词措辞的组织，这个好处压过其他一切。

天花板来自条件。当出现只在这种情况下才用那个工具的需求时，配置语言就开始模仿编程语言。接下来只有两条岔路：把表达式语法塞进配置，或者开一个通往代码的出口。前者等于新造一门没有调试器也没有类型检查器的小语言，后者制造出必须同时读配置与代码才看得到全貌的状态。

  • 适合留在配置里的 — 人经常调整、且没有分支的值。角色说明、温度、模型名称、工具许可清单
  • 该送进代码的 — 条件、循环、计算、查询外部状态。在配置里模仿这些，一定会变得难读
  • 最糟的状态是同一个概念被拆到两处。工具清单一半在文件里一半在装饰器里，就没有人知道全貌
  • 配置优先的方式仍留着通往代码的入口，正是知道这层天花板的设计

提示词文件 - 最薄的抽象

让一页 Markdown 直接成为智能体，等于把前面的问题整个消掉一个。什么发给了模型不再成为问题，因为文件里写的就是发出去的。前置元数据写名称、说明与工具许可清单，下面的正文成为系统提示词。

Claude Code 的文档把这条边界写明：子智能体只收到这份系统提示词以及工作目录之类的基本环境信息，不会收到完整的系统提示词。连什么不会被放进去都写了出来，这一点很能说明这种方式的性格。

代价出在编程上。没有类型，输出形态只能在提示词里请求；要抽出共通部分就需要文本包含功能，而那一刻又回到上一节的问题。分角色的构成能成立到什么程度，写在谈角色分工模拟的那篇里。

  • 合适的场合 — 人经常动手、流程是一条线、产物是文本的工作
  • 不合适的场合 — 输出要作为另一个系统的输入，且不能违反模式的工作
  • 隐藏的优点是与版本管理的契合。提示词的改动以 diff 呈现，回退就是回退一个文件
  • 隐藏的缺点是搜索。同一条指令被复制到十处，你改了一处却以为已经改完

最大的分岔 - 流程由谁掌握

到此为止的四类是表达方式的差别。但真正决定系统性质的，是底下那个问题：接下来做什么，由代码决定还是由模型决定。Anthropic 用名称把两者分开。工作流是让大模型与工具沿着预先定义的代码路径被编排的系统，智能体是让大模型自行指挥其过程与工具使用的系统。

各个框架把这个开关放在哪里并不相同，而它的位置对结果的影响比表达方式更大。同样基于类，流程全由代码掌握就接近工作流；模型在 REPL 里造出下一个行动，就接近另一端。

流程的主人相配的表达做得好的事崩塌的地方失败时的症状
代码全掌握图、命令式函数可复现、成本可预测、可测试来了未定义的输入沿着错误路径静静跑完全程
模型全掌握提示词文件、单一循环没见过的情形、探索循环与重复调用、预算把同一个工具叫八次然后停住
代码搭骨架，模型管区段对象（确定性方法加生成方法）实务的大部分边界画在哪里只在画错的区段上失败
模型写代码来造流程REPL 与代码执行环境一次处理完分支与循环没有隔离时事故发生在沙箱之外

把第三行与第四行一起用，是眼下设计的走向。表达力上去了，但执行环境本身就成了攻击面。上面那份文档之所以特意强调 AST 检查与阻断清单不是隔离边界，原因就在这里。这不是那个项目的弱点，而是选了第四行的所有人共同承担的负担。

行动写成 JSON 还是写成代码

模型调用工具的方式也有两条路，而这个选择与上一节的分岔连在一起。smolagents 把两者并排实现。CodeAgent 把工具调用做成 Python 代码片段，ToolCallingAgent 则写成 JSON。文档说两者按需都可用，并指出网页浏览这类每次交互后都要等待的工作，与 JSON 调用相合。

  • 代码一侧的好处 — 一次行动里就能放进循环、条件与中间变量。扫二十条清单从二十个来回变成一个
  • 代码一侧的成本 — 整个执行环境进入信任边界之内。可导入的模块、文件系统、网络全都成为要考虑的对象
  • JSON 一侧的好处 — 参数能用模式校验，审计日志整齐，事后好数也好重放
  • JSON 一侧的成本 — 来回变多。词元与延迟增加，上下文被截断的概率也跟着上升
  • 与表达方式的关系 — 把对象暴露给 REPL 的设计偏向代码，把工具当作独立函数清单的设计偏向 JSON

用代码行动并非本质上更聪明。它是用更高的表达密度换取更少的校验点。工具越接近纯计算，代码一侧越占优；工具越是改变外部世界，JSON 一侧的校验点越值钱。

状态与恢复 - 序列化反问的东西

短任务里任何抽象都转得不错。真正反问回来的是长时间运行的任务。三十分钟的活在第二十五分钟死掉，还剩下什么。四类给出的答案各不相同。

图这一侧是正面处理的。LangGraph 在编译时可以指定检查点器，检查点在超级步边界保存，使中断或失败之后能够恢复。因为流程是数据结构，所以停在哪里可以用值表达出来。

在对象这一侧，这个问题变成实例该怎么序列化。对活对象传引用的设计获得了表达力，但那个引用出不了进程，因为打开的套接字与文件描述符是句柄而不是值。上面那个包在 PyPI 摘要里自称是带事件溯源与序列化执行的系统，可以读作它在设计阶段就在处理这个问题的信号。

提示词文件那一侧的回答是干脆不持有状态。对话记录就是状态，恢复就是把记录再喂一遍。简单又结实，但记录一长就直接变成词元成本。

  • 状态是值还是句柄。是值就能保存，是句柄就不能。若恢复是需求，这条线要在早期画好
  • 保存点在哪里。是每次工具调用之后还是节点边界，决定了最坏情况下的损失区间
  • 重跑是否幂等。从检查点重启时会不会把同一个支付 API 调用两次。框架不会替你保证
  • 保存格式能否跨越发布。读不了的话，每次发布都会抹掉进行中的任务

确认办法只有一个：接入的第一周在第三次工具调用之后强行杀掉进程。这一次实验告诉你的比文档多得多。

可观测性 - 当日志变成框架的行话

抽象层多起来，日志也会跟着长层。节点3上归约器如何如何的那一行，只对懂那个框架文档的人是句子，对其他人是噪音。想象一下凌晨被叫起来的人第一次打开那份文档，就明白这为什么是成本。

需要的日志有两种。一种是与模型往来的原始记录：最终提示词、完整响应、传给工具的参数、工具返回的结果。另一种是框架的执行记录。只有后者，调试就变成猜测。你问的是为什么出来这个答案，得到的却是经过了哪些节点。

  • 好的信号 — 追踪默认开启，各次调用保持父子关系被保留下来。上面那个仓库在文档里写明这一性质，并用 CLI 打开查看器
  • 要留意的信号 — 要看追踪就得注册外部服务的结构。数据外流的路径多了一条，服务一挂，当天的事故调查就停摆
  • 底线 — 一次运行的原始记录能落到本地文件。仪表盘是之后的事
  • 值得数一数 — 理解一行日志需要几个框架概念。超过三个，那份日志就只有内行读得懂

把多个智能体接在一起，这份成本会相乘。编排本身的成本写在谈编排税的那篇里。

锁定的真实大小

选型时最让人担心的是锁定，但担心的大小与实际大小往往对不上。迁移的成本不来自代码行数，而来自它究竟是文本还是框架专有格式。

资产搬迁难度原因
提示词文本容易就是文本，粘贴即可
工具函数的函数体容易大多是普通函数，换个装饰器就行
输出模式中等架在标准类型库上就能原样带走，自造类型则要重写
流程结构难图定义、继承链、交接规则都是那个框架的词汇
已保存的检查点非常难格式属于框架，进行中的任务基本上要丢掉
追踪与评测记录非常难模式不同，会失去比较回归的基线
团队的思维习惯最难人开始用那个框架的概念去切分问题

最后两行才是真正的锁定。代码重写就是了，可一旦失去评测基线，就没有办法证明新的构成比原来更好。用上半年之后，人们开始用那个框架的概念来谈问题，而这笔成本从不会写进迁移文档。

  • 把提示词从类里的字符串抽到文件或常量模块中。迁移成本的相当一部分就此消失
  • 工具写成不带框架装饰器的纯函数，注册放在一层薄适配器里。只重写适配器即可
  • 评测数据集与判定标准放在框架之外的文件里。这一条就能划掉最后两行中的一行

不用框架反而更对的条件

Anthropic 的建议很明确：先从直接调用大模型 API 开始，许多模式几行代码就能实现。它还补了一句，框架可能让人在更简单的构成本已够用的地方去添加复杂度。

messages = [{"role": "user", "content": task}]
while True:
    reply = client.messages.create(model=MODEL, tools=TOOLS, messages=messages)
    messages.append({"role": "assistant", "content": reply.content})
    calls = [b for b in reply.content if b.type == "tool_use"]
    if not calls:
        return reply
    results = [run_tool(c) for c in calls]   # 从这里往下全是我自己的代码
    messages.append({"role": "user", "content": results})

这九行里没有任何被遮住的东西，什么出去什么回来都写在变量名上。代价是重试、预算上限、恢复与并行全得自己写。问题在于，这九行六个月后不会还是九行。

  • 自己写循环就够用的条件之一 — 流程是一条线，分支掰着手指就能数完
  • 之二 — 工具在十个以内，彼此不共享状态
  • 之三 — 任务在一次请求里结束，恢复不是需求
  • 之四 — 参与的人只有一两位，约定不写文档也维持得住
  • 之五 — 你想自己定日志格式，并且有这么做的理由
  • 框架体现价值的条件之一 — 多人各自添加智能体，共通约定必须由代码强制
  • 之二 — 恢复与人工审批介入是需求。自己造，最后就是造出一个框架
  • 之三 — 要在多个提供方与多个模型之间切换
  • 之四 — 追踪与评测必须从一开始就均匀积累，这是最难回补的一项

实际上常见的答案在中间：循环自己写，只在追踪与评测上用库；或者用框架，但把提示词与工具放在框架之外的文件里。把它看成全用或全不用的选择，本身就已经是框架的词汇。

选之前先回答的六个问题

功能对比表帮不上忙，因为哪一边最终都做得到。不如拿候选用上几天，先回答下面六个，半年后哪里会疼就看得见了。

  • 把提示词全文落到文件里要几分钟。超过十分钟，事故响应时间就会同样拉长
  • 只读源码能不能数出工具清单。不能的话，权限审查就变成执行日志审查
  • 在第三次工具调用之后杀掉进程还剩什么。什么都不剩，就别用这套构成跑长任务
  • 流程的分支由代码掌握还是模型掌握，这个答案文档里写了吗。没写就是两者混着，混着的地方日后会成为事故点
  • 不懂这个框架的同事只读日志，能不能说出哪里错了。说不出，运维就被绑在一个人身上
  • 如果把这个框架拆掉，要重写什么。清单只有提示词与工具函数，锁定就浅；夹着评测记录，就深

抽象是在挑选让什么变得容易，而变容易的事会大量发生。叫它类，人就开始用继承共享；叫它图，人就开始拆节点；叫它文件，文件就会变多。选定的那一刻，团队接下来半年会频繁做的动作就定下了。框架不会替你定这个答案，但它把什么做容易了，全写在第一个示例里。把文档首屏当作设计宣言来读，能看到的比对比表多得多。
