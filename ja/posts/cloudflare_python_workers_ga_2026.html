1. 正式リリースの背景と第1級言語サポート

一般的に、サーバーレス実行環境は軽量な分離機構と迅速な起動速度を実現するため、JavaScriptやWebAssemblyの実行エンジンを中心に発展してきました。このようなアーキテクチャ上でPythonのようなリッチなランタイムを運用する場合、従来は独立したコンテナを起動するか、肥大化したパッケージバンドルを作成する必要があり、導入時の摩擦が生じていました。2026年9月21日、Cloudflareは自社のエッジコンピューティング環境においてPythonを第1級市民言語（first-class language）として完全サポートする「Python Workers」の正式リリース（GA）を発表しました。

発表原文によると、Cloudflare Workersは2018年からWebAssemblyをサポートしており、これがWasmコンパイルされたPythonインタプリタを稼働させる理想的な実行基盤を提供したと説明されています。CloudflareチームはオープンソースプロジェクトであるPyodideを活用し、WebAssembly上でのPythonランタイム統合に長年取り組んできました。今回のGA発表は、単なる実験的機能の提供にとどまらず、本番環境の本格的なワークロードを堅牢に処理できる成熟度に達したことを示しています。

プレビュー段階では、PythonコードがCloudflareのプラットフォームリソース（Queues、D1データベース、KV、R2など）と通信する際、JavaScriptオブジェクトとの相互型変換を行う明示的なグルーコード（glue code）が必要でした。原文では、Pythonの辞書データをCloudflare Queueに送信するためにpyodide.ffi.to_jsやjs.Object.fromEntriesを呼び出さなければならなかったコード例を挙げ、開発体験の課題を指摘しています。今回の正式版では、この型変換処理の全工程がWorkersランタイムおよびPython SDK内部に完全にカプセル化されました。

その結果、Python開発者は背後にあるJavaScript環境やRPC境界を意識することなく、純粋なPythonらしい表現（Pythonic way）でプラットフォームバインディングを直接操作できるようになりました。辞書オブジェクトをそのままキューに渡す処理などが、JavaScriptコードを1行も書くことなく完結します。

# Before: Explicit JS type conversion required
from pyodide.ffi import to_js
import js

self.env.QUEUE.send(to_js({"key": "value"}, dict_converter=js.Object.fromEntries))

# After: Native Pythonic binding support in GA
self.env.QUEUE.send({"key": "value"})

公式発表では、今回のPython Workers GAを支える主要な技術的進展を4つの柱に分類して詳述しています。Webアプリケーションフレームワークを動かすためのASGI/WSGI標準インターフェース対応、リレーショナルデータベース接続を可能にする低水準TCPソケットシステムコールの実装、WebAssembly向けC拡張モジュール配布の標準化を推進したPEP 783の策定、そしてAIエコシステムと直結するネイティブAIライブラリのサポートです。

以下の表は、公式発表記事に記載された4大機能の発表文、原文引用、および技術的詳細を整理したものです。

この記事の解釈としては、これら4つの柱は単にPythonを実行可能にするだけでなく、既存の広大なPython Web・データエコシステムの資産を改修なしにエッジへ移行させるための構造的ボトルネックを的確に解消した施策です。標準インターフェース、生ソケット、バイナリ互換性、通信クライアントという4つの関門が同時に突破された点に意義があります。

3. ASGI・WSGIコネクタ — サーバーレスWebフレームワークの稼働

一般的に、従来のPython Webサーバー運用ではUvicornやGunicornといったアプリケーションサーバープロセスを常時起動し、その前段にNGINXなどを配置して同時接続を分散制御します。しかし、エッジのサーバーレス環境においてワーカーごとに個別のWebサーバープロセスを常駐させることは、メモリフットプリントや起動遅延の観点から合理的ではありません。

原文によると、Cloudflare Workersプラットフォーム自体がグローバルネットワーク上で負荷分散や自動スケーリングを処理しているため、ランタイム内部でWebサーバーを再実装する必要がありませんでした。その代わりに、Cloudflareチームは軽量で高速なブリッジ層であるworkers.asgiおよびworkers.wsgiコネクタを開発しました。

  • これらのコネクタは、着信したネイティブJavaScript Requestオブジェクトを、Pythonフレームワークが受け入れ可能な標準ASGI/WSGI構造体へオーバーヘッドを抑えて変換します。
  • フレームワークが生成したレスポンスのボディやヘッダーを、ネイティブのResponseパイプラインへ効率的に返却します。
  • FastAPI、Django、Flaskはもちろん、PEP 3333仕様に準拠したWSGIまたはASGIインターフェースを持つあらゆるPython Webフレームワークに対応します。
  • 開発者はサーバー環境の個別設定を行うことなく、わずか1行のエントリポイント記述のみで既存のコード資産をエッジへ展開できます。
from fastapi import FastAPI
from workers import asgi

app = FastAPI()

@app.get("/")
async def root():
    return {"message": "Hello, world!"}

# Export the worker entrypoint
Default = asgi.entrypoint(app)

Djangoのような同期型Webフレームワークについても同様に、Default = wsgi.entrypoint(app)と指定することで、既存のWSGIアプリケーションオブジェクトをエッジワーカーの起点として接続できます。インフラ運用の複雑さがプラットフォーム層に完全に移譲されます。

4. TCPソケットシステムコール実装とリレーショナルDB連携

これまでPython Workersで外部データベースと連携する際の最大の障壁となっていたのが、生ソケット通信の制約でした。Pythonの標準的なデータベースドライバであるaiomysqlやasyncpgは、標準ライブラリのsocketモジュールを使用してTCP接続を確立します。

通常のオペレーティングシステム環境では、socketモジュールがOSカーネルのPOSIXシステムコールを呼び出してネットワーク接続を開設します。しかし、WebAssemblyサンドボックスの内部では、セキュリティ上の隔離とブラウザ起因の制約により、これらのPOSIXネットワークシステムコールは常に例外を送出するスタブ（stub）となっていました。そのため、標準ドライバが接続を試みると即座に失敗していました。

原文は、この課題を克服するためにWorkersのconnect APIを活用し、WebAssemblyサンドボックス層で直接ソケットシステムコールを実装したことを明かしています。Pythonドライバがソケットのオープンやデータの送受信を実行すると、このカスタムシステムコール層が透過的にWorkersランタイムの非同期JavaScript呼び出しへと変換します。

  • システムコール層での透過的な変換により、上位のデータベースドライバライブラリのソースコードを一切変更する必要がありません。
  • このソケットブリッジの実装によって、CloudflareのコネクションプーリングサービスであるHyperdriveとの完全な連携が可能になりました。
  • Wrangler設定ファイルでHyperdriveバインディングを定義し、生成された接続情報を使い慣れたドライバに渡すだけで安全に接続できます。
  • PostgreSQLやMySQLなどの主要なリレーショナルデータベースへの直接クエリ実行がエッジ環境内で完結します。
import aiomysql
from workers import WorkerEntrypoint

class Default(WorkerEntrypoint):
    async def fetch(self, request):
        hd = self.env.HYPERDRIVE_MYSQL
        conn = await aiomysql.connect(
            host=hd.host,
            port=int(hd.port),
            user=hd.user,
            password=hd.password,
            db=hd.database,
            ssl=None,
        )
        cur = await conn.cursor()
        await cur.execute("SELECT username FROM user")
        r = await cur.fetchall()
        await cur.close()
        conn.close()
        return r

5. PEP 783とPyEmscripten — WebAssemblyエコシステムの標準化

純粋なPython（Pure Python）で記述されたパッケージであれば、WebAssembly環境へのロードは比較的容易です。しかし、NumPyやcryptographyをはじめとする高パフォーマンスなPythonライブラリの大半は、C、C++、Rustなどのネイティブ拡張を含んでいます。これらをPython Workersで動かすには、WebAssemblyバイナリとしてクロスコンパイルする必要があります。

原文では、これまでPythonパッケージをWebAssembly向けにクロスコンパイルするための公式な標準仕様が存在しなかった事実が指摘されています。そのため、従来はCloudflareのエンジニアが個別パッケージを手作業でコンパイルし、独自のホスティングリポジトリに配置せざるを得ず、利用可能なパッケージの拡大における重大な障壁となっていました。

Cloudflareはこの問題を自社閉域の独自仕様で終わらせず、PythonおよびPyodideコミュニティ全体と協調して解決する道を選択しました。ブラウザやWasmランタイム向けのパッケージ配布規格を策定するPEP 783（Emscripten Packaging）を提案し、1年以上の議論と改訂を経て公式に承認（Accepted）されました。

  • PEP 783は、WebAssembly実行環境向けの標準バイナリプラットフォームタグ系列であるpyemscriptenを正式に定義します。
  • 既存のPyodideビルドツールチェーンを安定化させ、OSSパッケージメンテナが導入しやすい汎用的なビルドパイプラインへと昇華させました。
  • Python公式のホイール自動ビルドツールであるcibuildwheelにPyEmscriptenプラットフォーム対応を寄贈し、CI環境でのWasmホイール発行を容易にしました。
  • EuroPython 2026カンファレンスにて「Python Everywhere: The State of Python on WebAssembly」と題した講演を行い、標準化の成果をコミュニティに還元しました。

この記事の解釈としては、CPythonの公式標準であるPEP階層でプラットフォームタグを確立したことは、将来的にPyPI全体がWebAssemblyをx86やARMと並ぶ正規のターゲットアーキテクチャとして包摂するための決定的な転換点となります。

6. ネイティブAIライブラリの稼働とWorkers AIオーケストレーション

機械学習やデータサイエンス分野においてPythonが築き上げた膨大なライブラリエコシステムは、AIエージェントやオーケストレーション処理の実装言語としてPythonを第一候補に位置付けています。しかし、従来のエッジ環境ではopenaiやlangchainなどの代表的ライブラリをそのまま稼働させることが困難でした。

これらのAIフレームワークは、外部APIとの通信基盤としてrequestsやhttpxといった標準的なHTTPクライアントライブラリに依存しています。従来のWasm環境ではソケット制約によりこれらのクライアントが正しく通信できませんでした。Cloudflareチームはこの問題を解決するため、WebAssembly環境においてHTTPクライアントがJavaScriptのfetch APIを透過的に利用できるよう上流リポジトリへ直接貢献を行いました。

  • 低水準ソケット実装とfetchルーティングの最適化が融合し、openai、langchain、mcp（Model Context Protocol）がPython Workers上でネイティブに動作します。
  • Cloudflareのグローバルネットワーク上に配置されたGPU基盤であるWorkers AIと直接連携し、サーバーレスなモデル推論をエッジ上で完結できます。
  • 公式提供のlangchain-cloudflareパッケージを利用することで、ChatCloudflareWorkersAIクラスを介してWorkers AIの大規模言語モデルを宣言的に呼び出し可能です。
  • Cloudflare AI Gatewayを経由させることで、コード本体を変更することなくリクエストのプロキシ、キャッシュ、レート制限、可観測性の統合管理が行えます。
from langchain_cloudflare import ChatCloudflareWorkersAI
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import PromptTemplate
from workers import Response, WorkerEntrypoint

class Default(WorkerEntrypoint):
    async def fetch(self, request):
        prompt = PromptTemplate.from_template(
            "In one sentence, describe a great day in the life of an {profession}."
        )
        llm = ChatCloudflareWorkersAI(
            model_name="@cf/meta/llama-3.3-70b-instruct-fp8-fast",
            binding=self.env.AI,
            max_tokens=64,
        )
        chain = prompt | llm | StrOutputParser()
        result = await chain.ainvoke({"profession": "electrician"})
        return Response.json({"result": result})

以下の表は、公式サンプルリポジトリに収録された代表的なユースケースと、連携するCloudflare製品群をまとめたものです。

非同期AI画像生成処理 Queues, Workflows, Workers AI, R2 ユーザー要求をQueueに投入し、WorkflowsでWorkers AIの推論ステップを制御して生成画像をR2に永続化
