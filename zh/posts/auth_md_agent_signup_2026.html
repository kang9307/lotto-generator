auth.md — AI智能体代替用户注册的开放协议

域名根目录一个Markdown文件实现注册认证自动化——分析安全困境、同意空白与智能体Web标准竞争

2026-06-27 IT/技术

引言：注册表单终结的开始

截至2026年6月，Web最古老的惯例之一正在悄然动摇——注册表单。姓名、邮箱、密码，有时还要填写地址和信用卡号。在AI智能体代替用户浏览网络的时代，这一程序是瓶颈也是障碍。智能体并不擅长滚动表单或识别验证码。

auth.md正面解决这一问题。WorkOS于2026年5月以MIT许可证开源发布的这一协议极为简单：服务在域名根目录（如https://yourapp.com/auth.md）放置一个Markdown文件，AI智能体读取该文件后即可理解如何注册用户，并自主执行认证流程——无需表单、浏览器点击，也无需OAuth同意界面。

本文不只是归纳规格说明，而是分析auth.md究竟改变了什么、在哪里会出现问题，以及它在更大的智能体Web（agentic web）标准竞争中处于什么位置。如果说robots.txt为爬虫指路，llms.txt为语言模型导航，那么auth.md就是递给智能体的一把钥匙。

1. auth.md是什么——文件结构与工作原理

首先只讨论已确认的事实范围。auth.md的核心是智能体可读的服务元数据。服务在域名根目录发布一个Markdown格式的文件，声明三件事：

  • 该服务支持的认证流程（Agent Verified / User Claimed）
  • 智能体可请求的权限范围
  • 智能体将获得的凭证类型（API密钥、短期令牌等）

重要的是，这个文件以Markdown格式编写，人类和语言模型都能轻松读取。它不发明新的二进制协议或专有API，而是在现有OAuth标准之上叠加一个面向智能体的发现层。

1.1 两种认证流程

Agent Verified流程由智能体的身份提供商（OpenAI、Anthropic、Cursor等可信平台）证明用户身份。智能体获取签名的ID-JAG（智能体身份证明）令牌，发送至服务的/agent/auth端点。服务验证签名后同步返回凭证，全程无需人工介入。速度最优，但完全依赖身份提供商的可信度。

User Claimed流程包含人工确认步骤。智能体向用户展示一次性验证码，用户直接登录服务并确认授权。速度较慢，但留有明确的用户同意记录，适用于金融交易、敏感数据访问等对问责要求高的场景。

服务可同时支持两种流程，接受哪种流程完全由服务运营方决定。这一设计在单一框架内同时容纳了"智能体自动化"与"人工同意"两种需求。

1.2 凭证设计

auth.md发放的凭证是短期有效、可撤销、范围受限的令牌。服务运营方完全掌控允许哪些权限范围、发放何种凭证，协议将控制权牢牢置于服务方手中。

2. 智能体Web标准竞争——从robots.txt到auth.md

2024至2026年间，Web正迅速转变为智能体读取并行动的Web。在这一过程中，一系列基于文件的协议相继涌现。

协议位置目的主导方
robots.txt域名根目录爬虫访问控制W3C非正式标准（1994年至今）
llms.txt域名根目录引导AI读取有价值内容Anthropic + 社区
AGENTS.md代码仓库根目录为编程智能体说明仓库规则Anthropic主导（开放）
auth.md域名根目录智能体注册认证自动化WorkOS主导（MIT）
MCP服务器端智能体与服务的结构化交互Anthropic主导

规律清晰可见：每个协议针对智能体-Web交互的不同层次。这些协议是互补的基础设施层，而非竞争关系。robots.txt回答"哪里不能去"，llms.txt回答"读什么"，auth.md回答"如何注册和认证"，MCP回答"如何与服务交互"。

2.1 与llms.txt的实质差异

llms.txt告诉语言模型"网站哪些页面最有价值"——处理的是发现与路由问题。auth.md处理更重的步骤：从账户创建到获取凭证再到调用API的完整流程。可以理解为读权限（llms.txt）与写/执行权限（auth.md + MCP）的区别。

2.2 与MCP的关系

MCP是更通用、功能更丰富的智能体-服务结构化交互框架。auth.md专注于更狭窄的问题——智能体首次向服务注册的那一刻。将这个入口标准化，可以让MCP等上层协议运作得更加简洁。将auth.md视为MCP的前处理步骤是合理的视角。

3. 采用现状——真的在用吗？

截至2026年6月，Cloudflare、Firecrawl、Resend、Monday.com、Zuplo、NanoGPT、AgentMail等在WorkOS发布协议约一个月内完成了实现。Ora.ai在其"智能体就绪评分卡"中加入了auth.md合规检查项。

Cloudflare的参与尤为值得关注。Cloudflare不只是放置了一个文件，而是将auth.md与其Protected Resource Metadata标准在基础设施层面深度整合，显示出auth.md从厂商工具演变为真正Web基础设施的潜力。

冷静审视这份采用名单，会发现大多数是基础设施和开发者工具企业。消费类服务和受监管行业（金融、医疗）的参与依然极为有限，原因与下文的安全与同意问题直接相关。

4. 安全困境——自动化的祝福与诅咒

auth.md解决的问题是明确的，但解决方式创造了新问题。这是理解该协议最重要的张力所在。

4.1 智能体能注册，恶意智能体也能注册

这是协议设计者们也承认的最尖锐风险：一旦智能体能自动注册，恶意行为者的智能体就能瞬间创建数千个账户。阻挡机器人的验证码和表单摩擦，对诚实智能体和恶意智能体的消失是完全一样的。

三个具体风险：第一，垃圾账户批量生成——服务条款滥用、免费层盗用、声誉操控。第二，凭证收割——Agent Verified流程中若可信提供商被污染或智能体遭劫持，可一次性大规模创建账户。第三，预算超支循环——智能体陷入错误恢复逻辑，反复触发付费服务注册。

4.2 服务必须构建的防线

auth.md规范将这些防护责任交给服务运营方。实际部署中以下措施不可缺少：速率限制是基本前提；可信提供商白名单需在Agent Verified流程中明确管理；最小权限原则要求只授予智能体所需的最小范围权限并使用短期令牌；异常检测需实时识别短时间大量注册、重复模式和异常权限请求。

构建这些防线的成本与auth.md的表面简单性形成鲜明对比。放置文件很容易，但安全管理这扇门所打开的通道远比这复杂。这种不对称性是受监管行业观望的核心原因。

5. 同意问题——用户到底同意了什么？

除技术安全问题外，还有一个更根本的问题：用户将注册权限委托给智能体时，究竟同意了什么？

5.1 委托同意的模糊性

用户告诉AI智能体"帮我注册这个服务"。智能体通过Agent Verified流程创建账户，勾选了邮件营销订阅、数据处理条款、第三方共享同意。用户真的读了并同意那些内容吗？这在法律上是有效同意吗？目前尚无任何国家对此给出明确答案。

User Claimed流程部分缓解了这一问题，但Agent Verified流程完全没有这一步骤。即使服务条款有数千字，智能体也可以在未向用户充分说明的情况下直接点击确认。

5.2 GDPR与个人信息保护法背景

欧盟GDPR要求个人数据处理同意须"自由、具体、知情且明确"。智能体代为签订的条款是否满足这一标准，目前是法律空白。这种法律不确定性是限制auth.md扩散速度最大的非技术因素，尤其对面向欧盟市场或受监管行业的服务而言。

6. 智能体Web的更大格局——什么会成为标准？

auth.md不是孤立项目，而是以智能体成为Web主要用户为前提的一系列协议之一。如果这一前提成立，智能体Web标准的竞争就不仅是技术争论，而是决定未来互联网权力结构的较量。

6.1 标准提案者的利益关系

目前主导智能体Web标准的组织都有强烈的利益关系。Anthropic主导MCP和AGENTS.md，围绕Claude智能体生态系统设计。WorkOS通过auth.md争夺认证基础设施市场。Cloudflare在基础设施层处理智能体流量以强化守门人地位。这些组织提出的"开放协议"是否真正开放，还是特定厂商的生态锁定手段，值得批判性审视。

auth.md在这方面表现更好：MIT许可证，无需注册或审批。但ID-JAG可信提供商列表由谁管理，可能导致实质权力集中。如果只有OpenAI或Anthropic能成为Agent Verified流程的可信提供商，管理这份列表的主体就成了智能体Web的守门人。

6.2 成为标准的条件

互联网历史表明，最简单、部署成本最低的协议往往胜出。robots.txt存活30年的原因正是一个文件、几行文字就足够。auth.md忠实遵循这一方向。但安全防线的构建成本、法律不确定性、消费类服务的缺席构成了三重摩擦，解决这些问题之前，auth.md还无法成为真正的通用标准。

7. 对开发者和服务运营方的实践指引

7.1 现在应该实施的服务

已有大量智能体流量进入的开发者工具、API服务、基础设施平台值得今天就评估auth.md。Cloudflare、Resend等早期采用者均为基础设施和开发者工具企业，这不是偶然——这些场景中智能体创建API密钥的用例已经真实发生。

7.2 应该等待的服务

受监管行业（金融、医疗、教育）、面向消费者的服务、欧盟市场服务，在法律指引明确前等待是合理选择。注册自动化的便利可能抵不过同意纠纷、账户滥用责任和隐私合规风险。

7.3 对智能体开发者

构建智能体的开发者应优先考虑对用户的责任，而非急于利用auth.md开启的可能性。智能体代替用户注册账户、获取权限、产生费用，需要智能体侧也有清晰的通知和同意机制。auth.md标准化了服务侧如何打开门，智能体侧如何获得用户同意的标准尚不存在。在这一空白填补之前，智能体开发者的伦理设计选择是保护用户的第一道防线。

8. 结论——简单文件开启的复杂世界

auth.md技术上简单：一个Markdown文件，OAuth标准上的薄薄一层。但它开启的可能性与风险并不简单。

智能体Web的方向是明确的：从人类直接操作每个界面，到智能体代替人类与服务交互。auth.md试图标准化这一转变中最根本的关口——认证本身。

截至2026年6月，该协议前景可期但仍处初期。基础设施和开发者工具领域的采用是实质性的，WorkOS和Cloudflare主导的实施速度令人印象深刻。但安全防线的实际构建成本、法律同意的不确定性、受监管行业的缺席正在阻挡其成为通用标准的道路。

最终判断：auth.md将成为智能体Web基础设施的实质性组成部分。但要达到robots.txt那种普遍存在的程度，还需要更多时间来建立法律明确性和用户信任。谁来塑造这段时间，将决定智能体Web的权力格局。
