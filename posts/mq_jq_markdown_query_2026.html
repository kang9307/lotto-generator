mq - jq 스타일의 Markdown 쿼리 언어 2026

jq가 JSON에 했던 일을, 이번엔 Markdown에

2026-06-10 IT/기술

서론: 마크다운은 많은데, 다루는 도구는 빈약하다

개발자의 하루를 떠올려 보면 마크다운(Markdown)은 거의 모든 곳에 있습니다. README, 위키, 이슈, 설계 문서, 블로그 초안, 그리고 2026년 현재는 LLM의 프롬프트와 응답까지 — 텍스트로 된 구조화 문서의 사실상 표준이 되었습니다. 그런데 막상 이 마크다운을 '프로그램처럼' 다루려고 하면 도구가 빈약합니다. grep으로 헤딩을 찾으려다 코드블록 안의 # 주석까지 걸리고, sed로 링크를 바꾸려다 표 안의 파이프 기호와 충돌합니다. 마크다운은 사람이 읽기 좋은 포맷이지만, 기계가 구조적으로 다루기에는 의외로 까다롭습니다.

이 빈자리를 정확히 겨냥한 도구가 GeekNews에서도 화제가 된 mq입니다. mq는 한마디로 "마크다운을 위한 jq"입니다. JSON을 다루는 표준 도구 jq의 철학 — 점 표기로 요소를 고르고, 파이프로 변환을 잇고, 필터를 합성하는 — 을 그대로 마크다운에 가져왔습니다. 이 글에서는 jq가 무엇인지 가볍게 복습한 뒤, mq가 어떤 문제를 풀고 어떤 원리로 동작하는지, 실전에서 어떻게 쓰는지, 그리고 pandoc·remark·mdq 같은 이웃 도구들과 무엇이 다른지를 차분히 정리하겠습니다.

1. 먼저 jq 복습 - JSON을 위한 쿼리 도구

mq를 이해하려면 그 원형인 jq부터 짚어야 합니다. jq는 명령줄에서 JSON을 다루는 경량 프로세서로, 흔히 "JSON을 위한 sed/awk" 또는 "JSON용 SQL"이라고 불립니다. 핵심 개념은 필터(filter)입니다. jq 프로그램은 입력을 받아 출력을 내는 필터이며, 가장 단순한 필터인 .은 입력을 그대로 통과시키는 항등 연산자입니다.

jq의 강력함은 작은 필터들을 파이프(|)로 잇는 데서 나옵니다. 셸 파이프와 똑같이, 앞 필터의 출력이 뒤 필터의 입력이 됩니다.

# 객체에서 name 필드만 추출
echo '{"name":"Ada","age":36}' | jq '.name'
# => "Ada"

# 배열을 순회하며 age가 30 초과인 항목만 선택
echo '[{"n":"A","age":36},{"n":"B","age":20}]' \
  | jq '.[] | select(.age > 30)'
# => {"n":"A","age":36}

여기서 기억할 점은 세 가지입니다. 첫째, 점 표기(.name)로 구조를 파고든다. 둘째, 파이프로 단계를 잇는다. 셋째, select() 같은 함수로 거른다. 다른 언어라면 반복문과 조건문으로 짤 일을, jq에서는 필터를 풀처럼 이어 붙여 해결합니다. 바로 이 사고방식이 mq에 거의 그대로 이식되어 있습니다.

2. 그런데 마크다운은 JSON이 아니다 - 문제의 본질

jq가 그토록 편한 이유는 JSON이 처음부터 기계가 파싱하기 좋은 구조를 갖고 있기 때문입니다. 키와 값, 객체와 배열이 명확하게 중첩되어 있어, 점 표기로 어디든 정확히 짚을 수 있습니다.

마크다운은 다릅니다. 마크다운은 사람이 읽고 쓰기 좋게 설계된 평문 텍스트입니다. 겉보기에는 단순하지만, 그 안에는 헤딩·문단·목록·인용·표·링크·코드블록이라는 암묵적 구조가 숨어 있습니다. 문제는 이 구조가 텍스트 줄 단위로는 잘 드러나지 않는다는 점입니다.

  • grep의 한계: grep '^#'로 헤딩을 찾으면, 코드블록 안에 들어 있는 셸 주석 #까지 함께 걸립니다. grep은 텍스트 줄만 볼 뿐 '이 줄이 코드블록 내부인지'를 모릅니다.
  • sed의 한계: 링크를 일괄 치환하려 해도, 정규식만으로는 중첩 괄호나 표 안의 파이프(|)와 충돌하기 일쑤입니다.
  • 구조 무지(無知): 결국 grep·sed·awk는 마크다운의 구조에 대해 '눈이 멀어' 있습니다. 그들에게 문서는 그저 줄의 나열일 뿐입니다.

반대편 끝에는 pandoc이 있습니다. pandoc은 문서를 통째로 다른 포맷으로 변환하는 강력한 도구지만, "이 문서에서 h2 헤딩만, 혹은 rust 코드블록만 뽑아 줘" 같은 외과적 추출에는 과합니다. 바로 이 '줄 단위 도구'와 '전체 변환 도구' 사이의 빈 공간이 mq가 노리는 자리입니다.

3. mq란 무엇인가 - 마크다운을 위한 jq

공식 소개에 따르면 mq는 jq와 유사한 문법으로 마크다운을 처리하는 명령줄 도구이며, Rust로 작성되어 있습니다. 데이터를 자르고(slice), 거르고(filter), 매핑하고(map), 변환(transform)하는 작업을 마크다운에 대해 수행합니다. jq가 JSON 객체와 배열을 다뤘다면, mq는 헤딩·문단·코드블록 같은 문서 노드를 다룹니다.

mq의 정체성을 한 문장으로 요약하면 이렇습니다.

grep과 sed는 마크다운의 구조에 눈이 멀어 있고, pandoc은 문서를 통째로 변환한다. mq는 그 사이에서, 마크다운 안의 요소를 외과적으로 쿼리하고 변형한다.

소개 자료에서 강조되는 mq의 주요 쓰임새는 다음과 같습니다.

  • LLM 워크플로: LLM 프롬프트와 출력에 쓰이는 마크다운을 효율적으로 가공·정제합니다. 2026년 들어 가장 주목받는 용도입니다.
  • 문서 관리: 여러 문서 파일에 걸쳐 콘텐츠를 추출·변환·정리합니다.
  • 콘텐츠 분석: 특정 섹션이나 패턴을 마크다운 문서에서 빠르게 뽑아냅니다.
  • 일괄 처리: 여러 마크다운 파일에 일관된 변환을 적용합니다.

도구 지원도 풍부하게 소개됩니다. 대화형 실험을 위한 REPL, VSCode 확장과 LSP(Language Server Protocol) 지원, 그리고 쿼리를 단계별로 들여다보는 디버거까지 갖췄다고 합니다. ~/.local/bin/에 mq-로 시작하는 실행 파일을 두면 커스텀 서브커맨드로 확장할 수도 있습니다.

4. 동작 원리 - 마크다운을 AST로 보기

mq가 grep과 근본적으로 다른 지점은 바로 여기에 있습니다. mq는 마크다운을 줄의 나열이 아니라 구조화된 트리, 즉 AST(Abstract Syntax Tree, 추상 구문 트리)로 파싱합니다.

예를 들어 다음과 같은 짧은 마크다운이 있다고 합시다.

# 설치

다음 명령으로 설치합니다.

```bash
cargo install mq-run
```

## 사용법

자세한 내용은 [문서](https://mqlang.org/)를 참고하세요.

사람의 눈에는 그냥 텍스트지만, mq는 이를 다음과 같은 구조로 이해합니다.

Document
├─ Heading(level=1)  "설치"
├─ Paragraph         "다음 명령으로 설치합니다."
├─ CodeBlock(lang=bash)  "cargo install mq-run"
├─ Heading(level=2)  "사용법"
└─ Paragraph
   └─ Link(url="https://mqlang.org/")  "문서"

이렇게 구조가 명시적으로 드러나면, '헤딩만', '레벨 2 헤딩만', 'bash 코드블록만', '모든 링크만' 같은 선택이 정확해집니다. 코드블록 안의 #은 더 이상 헤딩으로 오인되지 않습니다. mq가 jq처럼 동작할 수 있는 비밀이 바로 이 'AST 위에서의 쿼리'입니다. jq의 입력이 JSON 트리였다면, mq의 입력은 마크다운 AST인 셈입니다.

5. 기본 선택자 - 헤딩, 코드블록, 링크

이제 실제 문법을 보겠습니다. mq의 선택자는 jq의 점 표기를 닮았지만, 대상이 마크다운 요소입니다. 아래 예시는 공식 문서와 소개 자료에서 제시된 패턴을 정리한 것입니다.

5.1 헤딩 추출 (.h)

# 모든 헤딩 추출
mq '.h' README.md

# h1 헤딩만
mq '.h(1)' README.md

# h1, h2 헤딩만
mq '.h(1, 2)' README.md

# 레벨 1~3 헤딩 (범위)
mq '.h(1..3)' README.md

5.2 코드블록 추출 (.code)

# 모든 코드블록
mq '.code' example.md

# rust 코드블록만
mq '.code("rust")' example.md

# javascript 코드블록만
mq '.code("javascript")' example.md

여기에 jq에서 본 select()와 contains()를 결합하면 조건 필터링이 됩니다.

# "install"이 들어간 헤딩만
mq '.h | select(contains("install"))' README.md

# "name"이 들어간 코드블록만
mq '.code | select(contains("name"))' example.md

점 표기, 파이프, select — jq를 써 본 사람이라면 즉시 친숙함을 느낄 구조입니다. 다른 언어의 반복문 대신 필터를 이어 붙이는 jq의 사고방식이 그대로 살아 있습니다.

6. 변환과 합성 - 텍스트로 펼치기

mq는 추출에 그치지 않고 변환도 합니다. 추출한 노드를 평문 텍스트로 펼치거나, 대소문자를 바꾸거나, 링크로 감싸는 식입니다.

# 모든 헤딩을 텍스트로 변환
mq '.h | to_text()' README.md

# 코드블록을 텍스트로 변환
mq '.code | to_text()' example.md

# 파이프라인으로 도구 연결 (대화형 편집 후 소문자화)
cat README.md | mq '.h' | mq 'downcase()'

jq와 마찬가지로, mq의 진짜 힘은 작은 조각들을 이어 붙이는 합성에 있습니다. 셸 파이프와 mq 내부 파이프를 함께 쓰면, "헤딩만 뽑아 → 소문자로 → 다음 도구로 넘기기" 같은 흐름이 한 줄로 완성됩니다.

7. 실전 활용 사례

그래서 이걸로 무엇을 할 수 있을까요? 추상적인 문법보다 구체적인 시나리오가 도구의 가치를 더 잘 보여 줍니다.

7.1 목차(TOC) 자동 생성

문서의 h1·h2 헤딩만 모아 앵커 링크가 달린 목차를 만들 수 있습니다. 공식 소개에서도 헤딩을 모아 to_link()로 링크화하는 목차 생성 예시를 제시합니다. 긴 README나 위키 문서를 자동으로 정리할 때 유용합니다.

7.2 README에서 코드 예시만 뽑아 검증

mq '.code("bash")'로 README의 셸 예시만 추출해, 실제로 동작하는지 CI에서 돌려볼 수 있습니다. 문서에 적힌 명령이 실제와 어긋나는 '문서 부패(rot)'를 방지하는 좋은 장치입니다.

7.3 LLM 프롬프트·응답 정제

LLM이 길게 쏟아낸 마크다운 응답에서 헤딩 구조와 링크만 뽑아 요약 컨텍스트로 쓰거나, 불필요한 코드블록을 걸러 토큰을 아낄 수 있습니다. 헤더와 링크를 추출해 LLM 입력을 가볍게 만드는 활용은 소개 자료에서도 핵심 용도로 꼽힙니다.

7.4 문서 일괄 변환·검증

수십 개의 마크다운 파일에 동일한 쿼리를 적용해, 깨진 링크를 찾거나 특정 섹션의 존재 여부를 검사하는 문서 린팅 파이프라인을 만들 수 있습니다. grep으로는 구조를 몰라 어려웠던 일들입니다.

8. CLI 사용 예시 한눈에 보기

지금까지의 패턴을 실전 명령으로 모아 보겠습니다.

# 설치 (공식 안내 기준)
cargo install mq-run

# 1) 문서의 모든 h2 헤딩을 텍스트로
mq '.h(2) | to_text()' docs/guide.md

# 2) python 코드블록만 추출
mq '.code("python")' docs/guide.md

# 3) "deprecated"가 포함된 문단 찾기
mq 'select(contains("deprecated"))' CHANGELOG.md

# 4) 파이프라인: 헤딩 추출 → 소문자
cat README.md | mq '.h' | mq 'downcase()'

패턴이 보이시나요? 선택 → 필터 → 변환이라는 jq의 3단 구조가 마크다운 위에서 그대로 반복됩니다. 한 번 익히면 새 쿼리를 짜는 비용이 매우 낮아집니다. 압축·시스템 도구를 Rust로 구현하는 흐름이 궁금하다면 Rust로 구현한 Zstandard 글도 함께 참고할 만합니다.

9. Python 바인딩과 MCP

mq는 CLI로만 쓰는 도구가 아닙니다. PyPI에 markdown-query라는 패키지로 Python 바인딩이 제공되어, 파이썬 스크립트 안에서 마크다운을 같은 문법으로 쿼리할 수 있다고 소개됩니다. 데이터 파이프라인이나 문서 처리 자동화를 파이썬으로 짜는 팀에게 유용합니다.

2026년의 맥락에서 특히 흥미로운 점은 MCP(Model Context Protocol) 연동입니다. 소개 자료에 따르면 mq를 MCP 서버로 노출해, AI 애플리케이션이 마크다운을 구조적으로 가공하도록 붙일 수 있습니다. LLM이 긴 문서를 통째로 삼키는 대신, mq로 필요한 부분만 정밀하게 잘라 넘기는 방식입니다. AI 도구 생태계의 더 넓은 흐름은 2026년 개발자들이 실제로 쓰는 도구에서 정리했습니다.

10. 유사 도구 비교 - mq vs mdq vs pandoc vs remark

마크다운을 다루는 도구는 mq만 있는 것이 아닙니다. 각자 노리는 자리가 다릅니다. 소개·비교 자료를 토대로 정리하면 다음과 같습니다.

도구 성격 잘하는 일 한계/특징
mq jq 스타일 쿼리 CLI (Rust) 요소 추출·변환, REPL·LSP·디버거, MCP·Python 바인딩 기능이 풍부한 만큼 학습할 표현이 많음
mdq jq 스타일 쿼리 CLI (Rust) 문서에서 특정 요소를 단순·집중적으로 선택 mq보다 가볍고 단순한 선택 도구로 소개됨
pandoc 범용 문서 변환기 포맷 간 통째 변환(MD↔HTML↔PDF 등) 외과적 요소 추출에는 과함
remark JS 마크다운 처리 프레임워크 플러그인 기반 변환·린팅, 빌드 통합 CLI 한 줄 쿼리보다 프로그래밍 지향

요약하면, mq와 mdq는 같은 계열의 jq 스타일 쿼리 도구입니다. mq는 도구 지원(REPL·LSP·디버거)과 통합(MCP·Python)이 풍부한 쪽으로, mdq는 더 단순하고 집중적인 선택 도구로 소개됩니다. pandoc은 '변환', remark는 'JS 생태계의 프레임워크'라는 점에서 결이 다릅니다. 즉 mq를 쓸지 말지는 '문서를 변환할 것이냐, 문서 안에서 골라낼 것이냐'로 갈립니다.

11. mq를 도입할 때의 고려사항

좋은 도구도 맥락에 맞아야 빛납니다. mq를 도입하기 전 현실적으로 따져 볼 점들입니다.

  • 러닝 커브: jq 경험이 있으면 진입이 빠르지만, jq 자체가 낯설다면 점 표기·파이프·필터 합성이라는 사고방식부터 익혀야 합니다.
  • 설치 의존성: Rust 기반이라 cargo install이 가장 간편한 경로로 안내됩니다. 바이너리 배포 여부는 사용하는 플랫폼에 따라 확인이 필요합니다.
  • 성숙도: 활발히 개발 중인 비교적 새로운 도구이므로, 일부 표현이나 기능은 버전에 따라 달라질 수 있습니다. 미확인 동작은 공식 문서로 확인하는 편이 안전합니다.
  • 적합한 작업: 한 번 쓰고 끝나는 일회성 추출에는 과할 수 있습니다. 반복적인 문서 자동화·검증·LLM 전처리처럼 '같은 쿼리를 여러 번' 돌리는 상황에서 가치가 커집니다.

12. 개발자와 문서 작업자에게 주는 의미

mq의 등장은 단순한 '편리한 CLI 하나'를 넘는 의미가 있습니다. 그것은 마크다운을 데이터로 대하는 사고방식의 확산입니다. 그동안 마크다운은 '사람이 읽는 문서'였지, '기계가 질의하는 데이터'는 아니었습니다. jq가 JSON을 일급 데이터로 만들었듯, mq는 마크다운을 쿼리 가능한 구조로 끌어올립니다.

이 변화는 두 부류에게 특히 와닿습니다. 개발자에게는 문서가 코드 파이프라인의 일부가 됩니다. README의 코드 예시를 테스트하고, 변경 로그를 검증하고, 문서 린팅을 CI에 넣는 일이 자연스러워집니다. 문서 작업자에게는 수십 개 문서를 손으로 손보던 반복 노동이 한 줄 쿼리로 줄어듭니다.

그리고 2026년의 결정적 맥락은 역시 LLM입니다. AI가 마크다운을 대량으로 생산하고 소비하는 시대에, 그 마크다운을 정밀하게 자르고 거르는 도구의 수요는 커질 수밖에 없습니다. mq가 LLM 워크플로와 MCP를 전면에 내세우는 것은 우연이 아닙니다. 마크다운이 AI와 인간 사이의 공용어가 될수록, 그 공용어를 다루는 'jq 같은 도구'의 자리는 더 분명해집니다.

13. 결론 + 지금 시도해 볼 3가지

mq는 'jq의 마크다운 버전'이라는 한 줄 설명으로 충분히 요약되지만, 그 한 줄이 가리키는 것은 꽤 넓습니다. grep·sed가 구조에 눈멀고 pandoc이 과한 그 빈 공간에서, mq는 마크다운을 AST로 파싱해 외과적으로 쿼리·변환합니다. jq를 써 본 사람이라면 점 표기·파이프·필터라는 익숙한 문법으로 곧장 출발할 수 있습니다.

당장 시도해 볼 수 있는 세 가지로 마무리합니다.

  1. 가장 긴 README로 헤딩부터 뽑아 보라. mq '.h' README.md 한 줄이면 문서의 뼈대가 한눈에 들어옵니다. 효과를 가장 빨리 체감하는 출발점입니다.
  2. 코드블록을 추출해 검증 파이프라인에 넣어라. mq '.code("bash")'로 문서 속 명령을 뽑아 CI에서 돌리면, 문서와 현실의 어긋남을 자동으로 잡습니다.
  3. LLM 전처리에 끼워 보라. 긴 마크다운 응답에서 필요한 요소만 mq로 잘라 넘기면, 토큰을 아끼고 컨텍스트를 깔끔하게 유지할 수 있습니다.

도구가 늘 말하는 진실은 같습니다. 사람이 반복해야 했던 구조적 작업을 기계에 넘길수록, 우리는 더 본질적인 판단에 집중할 수 있습니다. mq는 마크다운이라는 익숙한 텍스트를 그 대상으로 끌어올린 작지만 영리한 도구입니다.
