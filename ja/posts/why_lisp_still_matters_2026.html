なぜ今も Lisp なのか - マクロ・REPL の力と双極性プログラマーの逆説

括弧の文法を超えて、言語を問題に合わせる思考と、優れた言語が主流になれなかった理由

2026年7月12日 開発・インフラ

序論: Lisp が今も語られる理由

2026年7月、GeekNews(news.hada.io)に数日の間隔を置いて Lisp を扱う記事が2本相次いで掲載された。一つは開発者 Elia Scotto が書いた「Lisp への道: なぜ Lisp なのか」であり、もう一つは Qi 言語の作者 Mark Tarver が書いた「双極性 LISP プログラマー」だ。どちらも古い話の焼き直しではない。前者は Lisp が今も学ぶ価値がある理由を言語設計の観点から説明し、後者はそれほど優れた言語がなぜ結局主流になれなかったのかを、言語ではなく人に求める。一つの言語について「なぜ優れているのか」と「なぜ失敗したのか」を同じ時期に並べて問うこと自体が、2026年7月時点で Lisp が置かれた立ち位置を正確に映し出している。

Lisp は 1958年にジョン・マッカーシーが設計して以来、Fortran に次いで長く現役であり続ける言語とされる。しかし今日の商用開発の現場で Lisp から新規プロジェクトを始めるチームはごく少数だ。それでもマクロ、REPL、条件システムといった Lisp のアイデアは、他言語のデコレータやマクロ実験、構造化された例外処理、さらには最近の AI エージェント設計の議論にまで流れ込み続けている。古いが死なず、主流ではないが無視もされない。本稿は2つの原文の視点をそれぞれ尊重しながら、その交差点 - 強さと疎外が同じ根から生まれるという逆説 - を筆者なりの視点で整理する。

1. 二つのレンズ - 技術と人

Scotto の記事は技術の内側を見る。彼の核心的主張は、Lisp の本質は括弧の多い文法ではないということだ。マクロの役割を彼は「language toward your problem」という短い表現で要約する。言語を問題の方へ拡張し、そうして作られた言語でプログラムを書くという意味だ。この一言に、本稿が扱う技術的核心が凝縮されている。

Tarver の記事は技術の外側、人を見る。彼は Lisp コミュニティに際立って多く現れるタイプ - 優れた知的能力を持ちながら退屈に耐えられず、完成より新しいアイデアに惹かれる気質 - を観察し、Lisp がこうした人々を特に強く引き付けると主張する。彼の結論は簡潔だ。「no problem with Lisp」という一文から始まり、問題は言語ではなくそれで何を作るかにあると締めくくる。言語自体の欠陥ではなく、その言語が引き付ける人々の社会的な行動様式が標準化と協業を難しくしているというわけだ。

二つの記事を並べると興味深い対称性が見える。Scotto は Lisp がなぜ強力なのかを説明し、Tarver はその強さがなぜ同時に弱点になるのかを説明する。本稿はこの二つの視点を順に追い、最後に AI コーディング時代という新しい文脈で再び出会わせる。

2. Lisp の核心 - コードがそのままデータである言語

2.1 ホモイコニシティ - 括弧が多い理由

Lisp のソースコードは S式と呼ばれる入れ子のリストで構成される。初めて見る人には括弧が異様に多い奇妙な文法に映るが、この構造こそが Lisp の正体だ。Lisp のコード自体が、Lisp の基本データ構造であるリストと同じ形を持つという性質をホモイコニシティ(homoiconicity)と呼ぶ。コードをリストとして読み、リストを操作し、そのリストを再びコードとして評価できるという意味だ。文法とデータ構造の間に別途のパース段階がほとんど要らない。

多くの言語で「コードをコードに扱わせる」ことは、別途のリフレクション API や AST 操作ライブラリを必要とする難しい作業だ。Lisp ではそれが既定の姿だ。プログラムがプログラムを読み書きすることが例外ではなく日常であるという点で、ホモイコニシティは単なる文法的な特異点ではなく、次に説明するマクロ・メタプログラミング全体を可能にする土台である。

2.2 マクロ - 言語を拡張する道具

関数は呼び出される前に引数がまず評価される。マクロは違う。評価されていないコード(リスト)をそのまま受け取り、コンパイル時点でそれを別のコードへ変換する。Common Lisp に while ループが標準で無ければ、プログラマがマクロで自作して組み込める。新しい文法を言語設計者ではなく言語の利用者が追加するわけだ。

これが Scotto の言う「言語を問題の方へ育てる」という表現の実体である。他の言語では新しい制御構造や DSL が必要になると、言語自体の次のバージョンを待つか、プリプロセッサのような外部ツールに頼らなければならない。Lisp ではその拡張が言語の内部で、同じ文法で、第一級の機能として起こる。AutoCAD が AutoLISP で、Emacs が Emacs Lisp でユーザーに拡張性を直接手渡したのも、このマクロの力による。

2.3 REPL - 生きたプログラムと交わす対話

多くの言語はコードを書き、コンパイルし、実行し、結果を見て、再びコードへ戻るという循環をたどる。Lisp の REPL(Read-Eval-Print Loop)はこの循環を取り除く。関数を一つ直せば、その場で実行中のプロセスの中で再定義され、プログラムを最初から再起動しなくても次の呼び出しから新しい定義が適用される。Smalltalk のイメージベース開発と精神的に通じるこの方式は、プログラムを「組み立てる」というより「教え、進化させる」に近い。

この違いは些細に見えて体感は大きい。初期化や大容量データの読み込みに時間がかかるプログラムを毎回最初から再起動せず、生きたプロセスの状態を保ったままコードだけを変えて探索的に開発できる。今日の多くの言語のホットリロードやノートブック型開発環境が真似ようとしている体験を、Lisp は設計段階から既定値として持っていた。

2.4 条件・リスタートシステム - 例外処理を超える復旧

Common Lisp の条件システムは、多くの言語の例外処理(try-catch)より一歩先を行く。一般的な例外処理は問題が起きるとスタックを即座に巻き戻し(unwind)、上位へ投げる。問題発生地点の実行文脈はすでに失われた後だ。Common Lisp の条件システムは条件がシグナルされた時点でスタックを巻き戻さず、その場で直接ハンドラを呼び出す。ハンドラはあらかじめ定義された複数のリスタート(restart)の中から一つを選んで実行を続けられる。

これが生む実質的な違いは、「復旧手段を用意すること」と「復旧手段を決定すること」を分離できる点だ。低レベルの関数は複数の復旧戦略をリスタートとして登録しておくだけで、実際にどの戦略を使うかは上位の呼び出し元や最終利用者が実行中に選べる。ファイルが見つからない時にプログラム全体を落とす代わりに、別の経路を試す、既定値を使う、再度尋ねるといった選択肢を、実行を止めないまま提示できるという意味だ。例外を「失敗の通知」としてのみ扱う多くの言語とは根本的に異なる発想である。

3. 「なぜ Lisp なのか」の思考法 - 言語を問題に合わせる

Scotto の記事で筆者に最も残るのは、個々の機能ではなく態度だ。多くの開発は「この言語が提供する道具で問題をどう解くか」を問う。Lisp 的思考は順序を逆にする。「この問題を最もよく表現する言語はどんな姿であるべきか」を先に問い、マクロでその言語を作った上で、その言語で問題を解く。道具に問題を合わせるのではなく、問題に道具を合わせる順序だ。

この考え方は実務的にも見慣れないものではない。設定ファイル DSL、クエリビルダー、ルーティング規則、ステートマシン定義といったものは、すでに「内部 DSL」という形で多くの言語に定着している。ただし多くの言語では、こうした DSL を作るために別途のパーサーやフレームワーク、デコレータ、コード生成ツールが必要になる。Lisp ではそれがマクロという言語の基本機能一つで解決される。「なぜ Lisp なのか」という問いへの答えは結局、他の言語ではフレームワークで真似なければならないことを、Lisp は文法として提供しているという点に尽きる。

4. ではなぜ主流になれなかったのか - 双極性プログラマーの逆説

ここで Tarver の記事が割って入る。技術的にこれほど強力な言語が、なぜ Java や Python、C++ ほど広く使われなかったのか。Tarver は言語の欠陥ではなく、その言語に惹かれる人々の気質に答えを求める。

4.1 強さが断片化を生む

同じ問題を複数の方法で解けるようにする柔軟性は長所だが、同時に標準を作りにくくする。Rudolf Winestock が先にまとめた「Lisp の呪い(Lisp curse)」という概念がこの逆説をよく説明する。他の言語では技術的な限界のために標準ライブラリ一つに収束せざるを得ない問題が、Lisp では個人が容易に自分だけの解法を作れるためにむしろ標準へ収束しない。1990年代の Scheme コミュニティでオブジェクト指向拡張パッケージが乱立した事例がよく引用される。作りやすいから各自が作り、各自が作るから何一つ標準にならない構造だ。

4.2 個人主義と協業の緊張

Tarver が語る - 優れているが浮き沈みの激しい気質の - プログラマーは、完成した成果より新しいアイデアを追うことから動機を得る。文書化、テスト、保守といった退屈だが協業に必要な作業は後回しにされやすい。一方で Tarver は、C や C++ のような言語は複雑さと低レベルの制御ゆえに、むしろ複数人が規律を守って共に働く文化を自然に強制すると指摘する。言語が個人に与える自由が大きいほど、その自由を組織の規律で再び束ねることが難しくなるという意味だ。

4.3 Lisp マシンという象徴

両記事にひそかに重なる事例が Lisp マシンだ。1980年代に Symbolics のような会社が作った Lisp 専用ハードウェアは、技術的には当時最高水準の開発環境だった。しかし市場の方向(汎用ワークステーション、その後 PC)と折り合えず姿を消した。技術的理想と市場の要求がずれた時、Lisp 陣営は概して市場の側へ譲らない道を選んできたというのが、Tarver の苦い診断だ。

5. 二つの視点の交差点

Scotto の記事が示す「言語を問題に合わせる」という自由と、Tarver の記事が示す「その自由が組織化を妨げる」という診断は、実は同じコインの両面だ。マクロで誰もが自分だけの方言を作れるということは、技術的祝福であり社会的呪いでもある。個人プロジェクト、研究、プロトタイプのように一人または少人数のチームが素早く問題に合った道具を作らなければならない場所では、Lisp は今も最上級だ。逆に、数百人が長期間ともに保守しなければならない大規模商用ソフトウェアでは、個人が自由に言語を拡張できるというまさにその自由が、コードベースの一貫性を損なうリスク要因になる。Lisp が学界・研究所・少数精鋭チームでは着実に生き残りながらも大衆的な商用開発の主流には上がれなかった理由は、技術と社会という二つの層を合わせて見て初めて説明できる。

6. AI コーディング時代に Lisp が与える教訓

2026年7月現在、ソフトウェア開発の話題の中心は AI コーディングエージェントだ。興味深いことに、エージェントが自ら計画を立て、コードを生成・修正・実行する構造は、Lisp が長らく扱ってきた問題と重なる。エージェントが自分自身の実行計画をデータとして扱い、その計画を再びコードへ変換して実行する流れは、ホモイコニシティが60年以上前から解いてきた「コードをデータのように扱う」という問題の変奏である。実際、最近では LLM を Lisp ベースの持続的なメタプログラミングループへ組み込む研究も現れており、これは AI エージェント設計と Lisp 的発想が偶然ではなく構造的に出会っているという信号として読める。

条件・リスタートシステムも新しい目で見る価値がある。AI エージェントがツール呼び出しに失敗した際、その場で別のツールを試す、利用者に確認する、既定動作へ進むといった復旧経路をスタックを巻き戻さずに選べるとすれば、これは今日ほとんどのエージェントフレームワークがリトライやフォールバックという名で苦労して真似ていることを、Lisp は言語レベルですでに備えていたという意味だ。REPL 的開発 - プロセスを再起動せず状態を保ったままコードだけを変えて対話するように開発する方式 - もまた、AI とやり取りしながらコードを段階的に磨いていく今日の作業方式と情緒的に似ている。

ただしここで Tarver の警告を忘れてはならない。AI がコードを生成する時代には、誰もがマクロを使うように容易に自分だけの解法とパターンを大量に生み出せる。柔軟性と生成速度がむしろコードベースの断片化と非標準化を加速させる危険は、Lisp の呪いが AI 時代に新しい規模で再現されうるということでもある。Lisp が与える教訓はメタプログラミングの力だけでなく、その力を組織的に統制できなければ何を失うかについての警告でもある。

結論: Lisp は学ぶ価値があるか

筆者の結論は、両方の原文に同意しつつも折衷する立場だ。Lisp を毎日使う主力言語として選ぶ開発者は今も少数派だろう。しかしホモイコニシティ、マクロで言語を拡張する思考、REPL ベースの対話型開発、条件・リスタートが示す柔軟なエラー復旧は、言語を問わず学ぶ価値のあるアイデアだ。これらのアイデアはすでにデコレータ、マクロシステム、ホットリロード、構造化された例外処理という名で多くの現代言語に吸収されている。同時に Tarver の診断も無視できない。強力な道具は、それを扱う人と組織の規律が伴わなければ断片化に帰結するという教訓は、Lisp だけでなく AI がコード生成速度を劇的に高めた今日のあらゆるチームにそのまま当てはまる。Lisp が今も語られる理由は懐古ではなく、それが提起した問い - 言語を問題に合わせるか、その自由をどう組織するか - が2026年になってもなお解けていないからだ。
