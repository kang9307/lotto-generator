EF BB BF 这三个字节在哪里弄坏什么，全部实际跑过一遍

2026年9月1日 IT/技术

昨天还在跑的脚本，今天吐出 No such file or directory。文件还在，首行也还是 #!/bin/bash，用编辑器打开也看不出哪里不对。这种时候有一个地方值得怀疑：文件开头的三个字节。

UTF-8 的 BOM 是 EF BB BF。屏幕上什么也不画，大多数编辑器甚至没法把光标放到它前面，diff 会一边说两行不同、一边给你看一模一样的字符。这篇文章记录的是这三个字节在哪里弄坏了什么，全部实际建好并跑过。输出比解释多。

BOM 本来是字节顺序的标记

名字就是答案。Byte Order Mark，字节顺序标记。它是为 UTF-16、UTF-32 这类把多个字节当作一个单位来读的编码而造的。在那些编码里，同一个值先存高位还是先存低位，字节就会颠倒。于是在文件开头放一个 U+FEFF，读取方看它是以 FE FF 还是 FF FE 到来，就能判断顺序。

Unicode 联盟的 FAQ 把这一点写得很清楚。BOM 是数据流开头的 U+FEFF，用作定义字节顺序和编码形式的签名。紧接着它把 UTF-8 单独拎出来说明。UTF-8 是面向字节的，因此根本不存在那个问题。它的字节顺序永远相同。所以 UTF-8 里开头的 BOM 并不是在宣告顺序，只是一个签名，表示这个没有标记的文本文件是 UTF-8。同一份文档随即附上一条提醒：有些接收 UTF-8 数据的一方并不预期出现 BOM。

那它为什么这么常见？源自 Windows 系工具的老习惯。在代码页因地区而异的年代，光凭扩展名无从判断一段文本是 UTF-8 还是本地代码页。在前面加三个字节，至少自家工具之间能分辨。记事本就是这么保存的，PowerShell 的 -Encoding utf8 长期以来也是这个意思。Linux 一侧从一开始就把 UTF-8 定为默认，不需要这个签名。两种习惯在同一个仓库里相遇，事故就从那里开始。

  • UTF-16 / UTF-32 — 字节顺序问题真实存在。BOM 本来要干的活就在这里
  • UTF-8 — 没有顺序问题。加上去的 BOM 不是顺序标记，只是个签名
  • 需要签名的场合 — 没有别的途径告知编码时。那些只能靠扩展名和本地代码页去判断的工具
  • 签名碍事的场合 — 首字节本身就是语法的格式。shebang、JSON、XML 声明、CSV 表头全都属于这一类

看不见究竟意味着什么

造两个内容相同的文件，只给其中一个加 BOM，并排放着看，就能立刻明白这个问题为什么长期无人察觉。cat 把两者显示得一模一样，只有大小差了三个字节。

$ printf 'hello\n'              > plain.txt
$ printf '\xef\xbb\xbfhello\n'  > bom.txt

$ cat plain.txt; cat bom.txt
hello
hello                      # 两行看起来完全一样

$ ls -l plain.txt bom.txt
-rw-r--r-- 1 user user 6 Sep  1 10:25 plain.txt
-rw-r--r-- 1 user user 9 Sep  1 10:25 bom.txt

$ xxd plain.txt
00000000: 6865 6c6c 6f0a                           hello.
$ xxd bom.txt
00000000: efbb bf68 656c 6c6f 0a                   ...hello.

$ od -c bom.txt
0000000 357 273 277   h   e   l   l   o  \n
0000011

$ file plain.txt bom.txt
plain.txt: ASCII text
bom.txt:   Unicode text, UTF-8 (with BOM) text

xxd 右栏那三个点就是 ef bb bf。file 甚至直接写出「with BOM」。到这里为止工具都很贴心。麻烦出在比较类工具上。

$ diff plain.txt bom.txt
1c1
< hello
---
> hello                    # 屏幕上是同样的字，却报为不同
$ echo $?
1

$ cmp plain.txt bom.txt
plain.txt bom.txt differ: char 1, line 1

$ wc -c < bom.txt
9
$ LC_ALL=en_US.UTF-8 wc -m < bom.txt
7                          # 9 字节，7 个字符 (BOM 1 + hello 5 + 换行 1)

diff 的工作完全正确。它说两行不同，事实也确实不同。它做不到的是把这个差异呈现给人看。代码评审里那种「这行怎么算改动了」然后耸耸肩放过去的改动，就是这么产生的。

shebang 不再是 shebang

可执行文件的前两个字节是 #! 时，内核会把后面的内容读作解释器路径。条件是那两个字节必须是文件的首字节。前面插进三个字节，那一行就不再是 shebang，只是普通的第一条命令行。

$ printf '#!/bin/bash\necho ok\n'              > ok.sh
$ printf '\xef\xbb\xbf#!/bin/bash\necho ok\n'  > bomshebang.sh
$ chmod +x ok.sh bomshebang.sh

$ ./ok.sh
ok

$ ./bomshebang.sh
./bomshebang.sh: line 1: #!/bin/bash: No such file or directory
ok
                           # 上面这条消息里，#! 前面原样打印着看不见的 BOM

$ head -c 16 bomshebang.sh | xxd
00000000: efbb bf23 212f 6269 6e2f 6261 7368 0a65  ...#!/bin/bash.e

这段输出里有两处值得读。一处是错误消息指向的是 shebang 那一行本身，而不是文件名。你会以为 bash 没了，去敲 which bash，而 bash 好端端地在那里。没能执行的是一条名叫 <BOM>#!/bin/bash 的命令。

另一处是下一行打印出了 ok。在这个环境（MSYS2 的 bash 5.2.37）里，shebang 解释失败之后，shell 自己接着读完并执行了剩下的部分。也就是说脚本并没有死，只有首行失败，其余照常往下走。这种结果更糟。退出码是 0，CI 也会通过。

$ printf '\xef\xbb\xbf#!/bin/bash\nset -e\necho reached\n' > strict.sh
$ bash strict.sh
strict.sh: line 1: #!/bin/bash: No such file or directory
reached
$ echo $?
0                          # 就算加了 set -e，首行的失败也抓不住

set -e 从它所在的那一行之后才生效，够不到第 1 行的失败。正是这个组合，使得问题常常以「构建成功了但产物不对」的形式在几天后才被发现。

配置文件里只有首行消失

shell 读进去的不只是脚本。像 .env 那样罗列 KEY=value 再用 source 载入的文件也走同一套规则，而这里出现的症状安静得多。恰好只有首行一条进不来。

$ printf 'API_HOST=example.internal\nAPI_PORT=8080\n'             > plain.env
$ printf '\xef\xbb\xbfAPI_HOST=example.internal\nAPI_PORT=8080\n' > bom.env

$ bash -c '. ./plain.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
HOST=[example.internal] PORT=[8080]

$ bash -c '. ./bom.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
./bom.env: line 1: API_HOST=example.internal: command not found
HOST=[] PORT=[8080]
$ echo $?
0                          # 从第二行起都正常，只有首行是空的

API_PORT 好好地进来了，只有 API_HOST 是空字符串。文件里明明写着值，变量却是空的，于是通常会去找拼写错误、怀疑加载顺序，白白花掉时间。就算那条 command not found 飘进了某处日志，屏幕上也看不出那一行的最左端有个看不见的字符。

同样的事在 YAML 里也会发生。如果是自己解析的代码，首个键的名字会变。

$ printf '\xef\xbb\xbfname: demo\nport: 8080\n' > app.yaml
$ node -e "
const s = require('fs').readFileSync('app.yaml', 'utf8');
const m = {};
for (const line of s.split(/\r?\n/)) {
  if (!line) continue;
  const i = line.indexOf(':');
  m[line.slice(0, i)] = line.slice(i + 1).trim();
}
console.log('keys :', JSON.stringify(Object.keys(m)));
console.log('name :', m.name);
console.log('port :', m.port);
"
keys : ["name","port"]     # 首个键前面挂着一个 U+FEFF
name : undefined
port : 8080

打印键列表看到的是 ["name","port"]，可 m.name 是 undefined。这是人眼所见与程序所比之间分岔的典型位置。

JSON - 标准说不要加

JSON 是少见的、标准文档里直接写着答案的情形。RFC 8259 的 8.1 节字符编码把两句话并排放着。一句是强制：实现不得在网络传输的 JSON 文本开头添加字节顺序标记（MUST NOT）。另一句是许可：为了互操作性，解析 JSON 文本的实现可以忽略字节顺序标记而不把它当作错误（MAY）。

这个不对称恰好解释了现场的混乱。写的一方不许加，读的一方可加可不加。也就是说有的解析器放行，有的解析器抛错。同一个文件换个工具就换个行为，原因就在这里。在 Node.js v22.16.0 上，同一个运行时内部就会分叉。

// jsontest.js
const fs = require('fs');
for (const f of ['plain.json', 'bom.json']) {
  const raw = fs.readFileSync(f, 'utf8');
  console.log(f, 'first char U+' +
    raw.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'));
  try   { console.log('  OK', JSON.stringify(JSON.parse(raw))); }
  catch (e) { console.log('  ' + e.name + ': ' + e.message); }
}

$ node jsontest.js
plain.json first char U+007B
  OK {"name":"demo","port":8080}
bom.json first char U+FEFF
  SyntaxError: Unexpected token '', "{"name":""... is not valid JSON

$ node -e "console.log(JSON.stringify(require('./bom.json')))"
{"name":"demo","port":8080}
                           # 同一个文件，用 require 就能通过

JSON.parse 抛错，require 通过，因为模块加载器会先剥掉 BOM 再交出去。于是它以「本地能跑、部署就挂」的样子出现，可实际分叉的不是环境，而是读这个文件的那一行代码。把 require('./config.json') 换成 JSON.parse(fs.readFileSync(...)) 的那一刻就炸了。

还有一点要补。SyntaxError 消息里 Unexpected token 后面的引号中间看着是空的，那里装的就是 U+FEFF。连错误消息都没法把原因显示给你。

CSV 的悖论 - 这里 BOM 才是解法

读到这里，把 BOM 一律删掉似乎就是答案。可偏偏有一个地方正好相反：用 Excel 打开的 CSV。以 UTF-8 保存的 CSV 在 Excel 里直接双击打开，文字经常显示为乱码，而在文件前面加上 BOM，很多情况下就能被识别为 UTF-8 正常打开。这就是大量 CSV 导出功能里特意写上这三个字节的原因。

所以同样这三个字节，在人打开的文件里是提示，在程序读的文件里是垃圾。问题在于同一个 CSV 往往两种用途都担着。为 Excel 加了 BOM 导出的文件，后来又成了另一个系统的输入，首列的名字就变了。

// csv.js — 不使用 trim() 的解析器
const fs = require('fs');
const text  = fs.readFileSync(process.argv[2], 'utf8');
const lines = text.split(/\r?\n/).filter(l => l.length > 0);
const cols  = lines[0].split(',');
const rows  = lines.slice(1).map(r =>
  Object.fromEntries(r.split(',').map((v, i) => [cols[i], v])));

console.log('cols[0]         :', JSON.stringify(cols[0]));
console.log('cols[0].length  :', cols[0].length);
console.log('cols[0] === "id":', cols[0] === 'id');
console.log('row0.id         :', rows[0].id);

$ node csv.js plain.csv
cols[0]         : "id"
cols[0].length  : 2
cols[0] === "id": true
row0.id         : 1

$ node csv.js bom.csv
cols[0]         : "id"     # 屏幕上看起来一模一样
cols[0].length  : 3        # 可长度是 3
cols[0] === "id": false
row0.id         : undefined

cols[0].length 一个是 2、一个是 3。没有这一行就什么都看不出来。失败的方式也很糟：不抛异常，undefined 安静地往下流。十万行的导入作业最后是「全部成功，首列全是空值」。

该修哪一边，由文件的最终消费者决定。目的是让人用 Excel 打开就加上，程序还要再吃一遍就不加。两种用途都占，那就做两份文件。

为什么有些代码没事 - trim() 的真相

写上面那个例子时，表头一开始是用 text.trim().split('\n') 切的，结果带 BOM 的文件顺利通过了。不是解析器写错了，而是 JavaScript 的 trim() 把 U+FEFF 当作空白剥掉了。

// t7.js — '\ufeff' 是表示 BOM 字符本身的转义
const s = '\ufeffid';
console.log('length          :', s.length);
console.log('trim().length   :', s.trim().length);
console.log('trim() === id   :', s.trim() === 'id');
console.log('/\\s/ matches?   :', /\s/.test('\ufeff'));
console.log('Number()        :', Number('\ufeff42'));
console.log('parseInt()      :', parseInt('\ufeff42'));

$ node t7.js
length          : 3
trim().length   : 2
trim() === id   : true
/\s/ matches?   : true
Number()        : 42
parseInt()      : 42

/\s/ 能匹配 U+FEFF，Number() 和 parseInt() 都会忽略前置的 BOM 返回 42。这份宽容让问题变得时有时无。有的字段经过 trim() 安然无恙，有的没经过就坏掉。同一个文件、同一套代码、不同的结果。

  • 把值当作对象键的路径通常不经过 trim()，所以问题总在表头名上冒出来
  • 转成数字的路径几乎总能通过，所以数值校验抓不到这个 bug
  • 正则校验只要用了 \s 也会通过。「值中不得含空白」这类规则不会标记出 BOM
  • 也就是说普通的校验器抓不住它。必须另外放一个直接看前三个字节的检查

比较、检索和哈希悄悄错位

带 BOM 的那一行，会从任何锚定行首的检索里漏掉，因为 ^ 后面跟着的不是 i 而是 U+FEFF。日志过滤、批处理脚本、迁移校验查询都会在这里安静地返回 0 条。

$ grep -c '^id' plain.csv
1
$ grep -c '^id' bom.csv
0                          # 一加锚点就找不到了
$ grep -c 'id' bom.csv
1                          # 去掉锚点就能找到

$ grep -Fxc 'id' list_a.txt
1
$ grep -Fxc 'id' list_b.txt
0                          # 整行匹配也一样

$ cat v1.txt v2.txt | sort -u | xxd
00000000: 616c 7068 610a efbb bf61 6c70 6861 0a    alpha....alpha.
                           # sort -u 把同一个词留下了两份

$ sha256sum plain.html bom.html
904ee45b2e532f436f4c05f8d809365538b9bf9843030bc01d0f9079deb0cbe7 *plain.html
a3369d9b5f62004281debdaccdc69395cc94af732b19023258576308ce7cbc35 *bom.html

哈希不同会立刻在发布校验上出问题。若流水线是用校验和确认「产物是否与上次一致」，那么有人改了一下编辑器设置，就足以让结果显示全部已变更。

还有一点。BOM 并不只出现在文件开头。把多个带 BOM 的文件直接拼接，就会嵌进中间。

$ cat part1.csv part2.csv > merged.csv
$ grep -c $'\xef\xbb\xbf' merged.csv
2
$ xxd merged.csv
00000000: efbb bf69 642c 760a 312c 610a efbb bf69  ...id,v.1,a....i
00000010: 642c 760a 322c 620a                      d,v.2,b.
                           # 第二个 BOM 卡在了数据正中间

文件中间的 U+FEFF 在旧版 Unicode 里还兼作 zero-width no-break space，渲染出来什么也看不到。日志采集器或者拼接分片下载结果的批处理造出这种文件时，排查会格外漫长。

在网页上表现出来的症状

HTML 文件开头有 BOM 时，文档的第一个字符就不再是 <。从字节上看是这样。

$ head -c 24 bom.html | xxd
00000000: efbb bf3c 2144 4f43 5459 5045 2068 746d  ...<!DOCTYPE htm
00000010: 6c3e 0a3c 6874 6d6c                      l>.<html

$ node -e "
const s = require('fs').readFileSync('bom.html', 'utf8');
console.log('indexOf   :', s.indexOf('<!DOCTYPE'));
console.log('startsWith:', s.startsWith('<!DOCTYPE'));
"
indexOf   : 1
startsWith: false

从这里往后没有实际执行，只写结构。在使用服务端模板的环境里常见的形态有两种。一种是正文最上方多出一个来路不明的空行或留白。文档开始之前已经输出了一个字符，解析器便把它当作正文内容处理。另一种是响应头发送失败。在 PHP 这类把文件内容直接冲进输出流的结构里，<?php 标签之前的三个字节已经是输出，于是其后的头部设置或重定向会伴随「头部已发送」之类的警告而失败。

遇到这种情况，可用的办法是从文件一侧收窄，而不是从症状一侧。就算被包含的文件有几十个，把前三个字节是 EF BB BF 的挑出来，通常也就剩一两个。

怎么确认它在不在

工具有好几种，但做的事是同一件：看文件的前三个字节。按场合挑顺手的用就行。

$ file config.json run.sh clean.txt
config.json: Unicode text, UTF-8 (with BOM) text
run.sh:      POSIX shell script, Unicode text, UTF-8 (with BOM) text executable
clean.txt:   ASCII text

$ xxd config.json | head -1
00000000: efbb bf7b 2261 223a 317d 0a              ...{"a":1}.

$ grep -rlI $'\xef\xbb\xbf' .
./config.json
./sub/run.sh

$ grep -rlI $'^\xef\xbb\xbf' .    # 只要位于行首的
./config.json
./sub/run.sh

$ cat -A bom.txt
M-oM-;M-?hello$

$ sed -n l bom.txt
\357\273\277hello$

cat -A 的 M-oM-;M-? 和 sed -n l 的 \357\273\277，是把同样三个字节分别用元字符记法和八进制显示出来。在终端里用肉眼确认时，这两个最快。不过要知道 grep -rlI 连文件中间的 BOM 也会一起捞上来。加锚点能收窄，但那也是「某一行的开头」而非「文件的开头」。想精确地只看前三个字节，还是用程序打开更好。

// bomcheck.js — 只读前三个字节来确认。适合挂进 CI
const fs = require('fs'), path = require('path');
const BOM = Buffer.from([0xEF, 0xBB, 0xBF]);

function walk(dir, out = []) {
  for (const e of fs.readdirSync(dir, { withFileTypes: true })) {
    const p = path.join(dir, e.name);
    if (e.isDirectory()) walk(p, out); else out.push(p);
  }
  return out;
}

let bad = 0;
for (const f of walk(process.argv[2] || '.')) {
  const fd = fs.openSync(f, 'r');
  const head = Buffer.alloc(3);
  fs.readSync(fd, head, 0, 3, 0);
  fs.closeSync(fd);
  if (head.equals(BOM)) { console.log('BOM: ' + f); bad++; }
}
console.log(bad ? bad + ' file(s) with a UTF-8 BOM' : 'no BOM found');
process.exit(bad ? 1 : 0);

$ node bomcheck.js ./tree
BOM: tree\config.json
BOM: tree\sub\run.sh
2 file(s) with a UTF-8 BOM
$ echo $?
1

$ node bomcheck.js ./cleantree
no BOM found
$ echo $?
0

PowerShell 一侧用 ReadAllBytes 把开头打印出来即可。有一点要留意：用 Get-Content 读回来的是已经剥掉 BOM 的字符串。在 Windows PowerShell 5.1.19041.6456 上，用 Get-Content -Raw 读带 BOM 的文件并打印首字符，得到的是 U+006C，也就是正文的第一个字符。在字符串这一层看不出任何问题，所以确认必须在字节这一层做。

PS> $b = [System.IO.File]::ReadAllBytes('config.json')
PS> ($b[0..2] | ForEach-Object { $_.ToString('X2') }) -join ' '
EF BB BF

PS> (Get-Content -Path config.json -Raw)[0]
{                          # 以字符串读出来时 BOM 已经不在了

怎么删，以及怎么删坏

删本身不难，难的是不去碰那些不该动的文件。批量处理没有撤销，所以先做好备份再开始。

$ sed '1s/^\xEF\xBB\xBF//' in.csv > out.csv     # 输出到新文件 (最安全)
$ sed -i.bak '1s/^\xEF\xBB\xBF//' in.csv        # 就地编辑 + 保留原文件

$ xxd in.csv | head -1
00000000: 6964 2c6e 616d 650a 782c 790a            id,name.x,y.
$ xxd in.csv.bak | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.

$ awk 'NR==1{sub(/^\xef\xbb\xbf/,"")}1' in.txt > out.txt
$ perl -pi -e 's/^\x{ef}\x{bb}\x{bf}// if $.==1' in.txt

用 1s/ 把目标收窄到只有首行很关键。不给范围的话，正文中间可能合法存在的 U+FEFF 也会一并被删。而给 -i 加上后缀，GNU sed 4.9 就会把原文件保留为 .bak。要一次跑几百个文件的作业，应该以它为默认。

接下来是专用工具。这里有一个陷阱。

$ xxd before.csv
00000000: efbb bf61 0d0a 620d 0a                   ...a..b..     # BOM + CRLF

$ dos2unix --remove-bom before.csv
dos2unix: converting file before.csv to Unix format...

$ xxd before.csv
00000000: 610a 620a                                a.b.          # BOM 和 CR 都没了

$ dos2unix -m -n a.csv a.bom.csv          # -m 反过来是加上 BOM
$ xxd a.bom.csv
00000000: efbb bf61 0a62 0a                        ...a.b.

dos2unix --remove-bom 不只删 BOM。正如其名，它连换行也一并改成 LF。上面的输出里两组 0d0a 全变成了 0a。对必须保持 Windows 专用的文件跑这条命令，等于修好一个 BOM 问题、新造一个换行问题。反方向加上去用 -m，再给 -n 就会保留原文件、写到新文件里。

iconv 在这件事上并不像期望的那样管用。

$ iconv -f UTF-8 -t UTF-8 in.csv > out.csv
$ xxd out.csv | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.
                           # 从 UTF-8 转到 UTF-8，BOM 原样留着

$ iconv -f UTF-8-BOM -t UTF-8 in.csv
iconv: conversion from UTF-8-BOM unsupported

$ iconv -f UTF-8 -t UTF-16 ab.txt | xxd
00000000: feff 0041 0042 000a                      ...A.B..      # 会加上 BOM
$ iconv -f UTF-8 -t UTF-16LE ab.txt | xxd
00000000: 4100 4200 0a00                           A.B...        # 不会加

GNU libiconv 1.18 不认识 UTF-8-BOM 这个名字。不过最后两行值得记住。转成 UTF-16 会加 BOM，转成 UTF-16LE 则不会，因为在名字里点明了字节序，就不必再去宣告顺序了。

最后是被提得最多、也最危险的方法。

$ printf '\xef\xbb\xbfhi\n' > a.txt
$ tail -c +4 a.txt | xxd
00000000: 6869 0a                                  hi.           # 删得很干净

$ printf 'hi there\n' > b.txt                                    # 没有 BOM 的文件
$ tail -c +4 b.txt | xxd
00000000: 7468 6572 650a                           there.        # 把 'hi ' 吃掉了

tail -c +4 无条件丢掉前三个字节。只对带 BOM 的文件跑是对的，可一旦用循环扫过整个目录，那些本来没有 BOM 的文件就会少掉开头三个字符。上例里 hi  不见了。要用这个方式，前面必须加上确认有无 BOM 的条件。

也可以从读的一侧解决。改不了文件的时候这条路更好。Python 3.11.9 标准库里就有为此准备的编解码器。

>>> open('bom.json', encoding='utf-8').read()[0]
'\ufeff'
>>> json.load(open('bom.json', encoding='utf-8'))
json.decoder.JSONDecodeError: Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1 (char 0)

# csv.DictReader — 一个编码名就能改变首列的名字
utf-8      fieldnames: ['\ufeffid', 'name', 'qty']   row.get('id') -> None
utf-8-sig  fieldnames: ['id', 'name', 'qty']         row.get('id') -> 1

Python 的错误消息是本文见过的里面最贴心的：原因和解法写在同一行。utf-8-sig 有 BOM 就剥掉、没有就照常放行，因此在无法控制输入文件的代码里可以直接当默认值用。

方法工具、版本顺带发生的事适用场合
sed '1s/^\xEF\xBB\xBF//'GNU sed 4.9只动首行，其余不变默认。配 -i.bak 使用
dos2unix --remove-bomdos2unix 7.5.2CRLF 会变成 LF只用于反正要统一成 LF 的文件
dos2unix -mdos2unix 7.5.2加上 BOM，同时也转换换行制作给 Excel 用的 CSV 时
iconv -f UTF-8 -t UTF-8GNU libiconv 1.18什么也不会发生，BOM 留着不用于这个目的
tail -c +4coreutils 8.32没有 BOM 时会吃掉三个正文字节没有条件判断就不要用
encoding='utf-8-sig'Python 3.11.9不改文件，只在读取时剥掉接收并读取别人的文件时
先比较前三个字节再处理Node.js v22.16.0没有。只会精确选中目标批量作业、CI 检查

该加的地方和绝不能加的地方

规则可以归成一句：首字节本身就是语法的格式，一律不加。shebang、JSON 的左花括号、XML 声明、CSV 的首列名，那个首字节的位置全都带着意义。反过来，若没有别的途径告知编码、而且目的就是给人打开，那加上更好。

文件类型BOM理由
shell 脚本 (.sh、.bash)不加shebang 不再是 shebang。更糟的是只有首行失败、程序继续往下跑
JSON (.json)不加RFC 8259 禁止在传输时添加。解析器并没有替你忽略的义务
YAML、配置文件 (含 .env)不加首个键的名字会变。无一例外地安静失败
源代码总体不加哈希会变，diff 会造出看不见的改动
用 Excel 打开的 CSV加没有它经常打开就是乱码。这是给人打开的文件
程序读取的 CSV不加首列名不再是 id。每次都会流出 undefined
Windows 专用文本 (记事本等)可以加没有别的手段告知编码。仅限没有外传计划时
UTF-16 / UTF-32 文件加字节顺序问题真实存在。BOM 本来的用途就在这里
HTML不加<meta charset> 或 HTTP 头已经告知了编码

模糊情形下的判断标准也能压缩成一条。最后打开这个文件的是人还是程序？是人，加上就有好处；是程序，几乎总是损失。两者都是，就把文件拆开。

在团队里阻止它复发

删一次容易，让它不再出现更难。大多数不是人造出来的，而是工具的设置造出来的，最常见的源头是 PowerShell。

PS> "line one" | Set-Content a_default.txt
PS> "line one" | Set-Content b_utf8.txt   -Encoding utf8
PS> "line one" | Out-File   c_outfile.txt -Encoding utf8
PS> [System.IO.File]::WriteAllText("$pwd\d_nobom.txt", "line one`n",
      (New-Object System.Text.UTF8Encoding($false)))

a_default.txt   len=10   first bytes: 6C 69 6E 65 20 6F 6E 65
b_utf8.txt      len=13   first bytes: EF BB BF 6C 69 6E 65 20
c_outfile.txt   len=13   first bytes: EF BB BF 6C 69 6E 65 20
d_nobom.txt     len= 9   first bytes: 6C 69 6E 65 20 6F 6E 65

PS> "x" | Set-Content f.txt -Encoding utf8NoBOM
Cannot bind parameter 'Encoding'. Cannot convert value "utf8NoBOM" to type
"Microsoft.PowerShell.Commands.FileSystemCmdletProviderEncoding".

在 Windows PowerShell 5.1.19041.6456 上，-Encoding utf8 是会加 BOM 的。而 utf8NoBOM 这个值在这个版本里并不存在，会在参数绑定阶段被拒绝。要在这个版本写出不带 BOM 的 UTF-8，直接传 UTF8Encoding($false) 是可靠的做法。如果部署脚本会生成配置文件，这里就是第一个该查的地方。

编辑器一侧可以靠 .editorconfig 做一定程度的约束。规范里有 charset 属性，取值可用 latin1、utf-8、utf-8-bom、utf-16be、utf-16le，规范本身还写明不建议使用 utf-8-bom。不过这是只有编辑器读取并遵守时才成立的约定，不支持的工具写文件时照样会漏过去。

# .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true

[*.csv]
charset = utf-8-bom          # 只把给 Excel 打开的导出文件设为例外

这里有一点必须说清楚。git 不会帮你规范化 BOM。gitattributes 文档里的 text 和 eol 处理的是换行转换，working-tree-encoding 是给 UTF-16 之类仓库与工作树编码不同的情形用的。没有任何属性负责添加或去掉 UTF-8 的 BOM。换行靠 .gitattributes 一行就能让全队统一，BOM 却没有这样的机关。

所以最后一道防线是检查。上一节的 bomcheck.js 找到 BOM 就返回退出码 1，可以直接挂进 CI 步骤。只有 shell 的环境，一行也够。

# 只要存在一个 BOM 就让它失败 (GNU grep 3.0)
! grep -rlI $'^\xef\xbb\xbf' --include='*.sh' --include='*.json' \
                            --include='*.yaml' --include='*.yml' . \
  || { echo "BOM found in the files above"; exit 1; }
  • 先从源头堵住 — PowerShell 的 -Encoding utf8、记事本、部分 Windows 编辑器造出了绝大多数
  • 把共识写进 .editorconfig — 没有强制力，但工具若支持就会自动对齐
  • 不要指望 git — 和换行不同，仓库不会替你统一
  • 在 CI 里拦住 — 一个看前三个字节的检查就够。按扩展名收窄，给 CSV 留出例外
  • 批量删除单独成一次提交 — 和别的改动混在一起，事后就分不清究竟改了什么

BOM 和换行是两个问题

这两者总被放在一起说，可原因和解法都不同。它们被捆成一团，只是因为常在同一处冒头、又常用同一个工具修。实际上它们的差别有下表这么大。

项目UTF-8 BOMCRLF / LF
位置文件开头三个字节，只有一次每一行的行尾，遍布整个文件
字节EF BB BF0D 0A 或 0A
git 会不会规范化不会。没有对应的属性会。靠 text、eol 属性统一
典型症状只有首行失败：shebang、首个键、首列名bad interpreter: /bin/bash^M 之类的立即失败
发现难度高。屏幕上什么也看不到低。错误消息里会打出 ^M
修复工具sed 1s、utf-8-sig、前三字节检查dos2unix、.gitattributes

实务上重要的差别是第三行。换行可以靠仓库设置让全队一次性对齐，而BOM 会从每个人的编辑器、每个人的脚本里不断重新长出来。所以换行该用策略解决，BOM 该用检查解决。dos2unix 一次把两件事都办了这个事实模糊了这个区分，而正如前面所见，那份便利会顺带拖来不想要的转换。

因编码本身对不上而导致文字变乱码的问题 — 比如把以 cp949 保存的文件按 UTF-8 读出来变成 ????? 或 ìëíì 的那一类 — 属于另一个层面，不是本文的主题。那部分整理在 定位韩文乱码发生的那一点 里。压缩包内文件名损坏的情形见 zip 里的文件名在哪一步坏掉，用正则处理韩文字符串时踩空的问题见 韩文正则陷阱。

未能确认的部分

  • Excel 的实际行为 — 「有 BOM 就能让 Excel 正确打开 UTF-8 的 CSV」是被广泛使用的对策，但本文没有用 Excel 打开验证。也有报告称结果因版本和区域设置而异，因此在采用前最好在实际使用环境的 Excel 上亲自确认。已确认的只是另一侧：程序读那个文件时首列名会变
  • PowerShell 7 系列 — 这个环境没有安装 pwsh，未能确认。正文中「-Encoding utf8 会加 BOM」和「不存在 utf8NoBOM」这两个结果仅限 Windows PowerShell 5.1.19041.6456。版本不同默认值也可能不同，建议在自己用的版本上直接打印字节确认
  • PHP 的响应头发送失败 — 这个环境没有 PHP，未能复现。第 9 节的相应段落是结构说明，不是执行结果。实际确认的只到「HTML 文件里文档的第一个字符不再是 <」为止
  • BSD 系工具 — 这里用的 sed 是 GNU sed 4.9。\xEF 这类十六进制转义以及 -i 的后缀处理方式依赖 GNU 实现，据称在 macOS 自带的 sed 上行为不同，但没有可供确认的环境
  • git 的实际行为 — 「没有属性负责规范化 BOM」是在 gitattributes 文档里确认的内容，并未在仓库中执行命令验证
  • shebang 失败之后的行为 — 首行失败后其余照常执行，是在 MSYS2 的 bash 5.2.37 上观察到的结果。在 Linux 发行版的 shell 或别的内核上是否发生同样的回退，未能确认
