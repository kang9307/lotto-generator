One Emoji Counts as Eleven Characters - ZWJ Sequences and Length Validation

A string does not have one length. How to decide which of the five numbers you are actually counting

2026-07-30 Dev & Infra

Introduction: one emoji punches through a 20 character limit

The nickname field says maximum 20 characters. A user types twelve letters and adds two emoji. The on-screen counter shows 14, but pressing save produces you have exceeded 20 characters. The user counted fourteen. The server counted something else.

A report like this gets closed as not reproducible. The developer tests it with their own name and nothing goes wrong. And that is exactly why this bug survives for years.

There is only one cause. A string does not have one length.

  • UTF-8 bytes — the number storage and transport see
  • UTF-16 code units — the number JavaScript .length returns
  • Code points — the number Python len() returns
  • Grapheme clusters — the one character a human counts
  • Display width — the number of cells it occupies on screen

Five of them. And for most input all five numbers are identical. With only letters and digits, hello world is 11 no matter which ruler you use. Add Hangul and only the byte count diverges. The moment an emoji arrives, all five scatter.

The sentence 20 character limit is not a specification, because it never says which of the five it means. This article counts all five numbers in front of you, and closes with a table for deciding which one to count for each purpose. The conclusion is not just block emoji.

Test environment. Every output below was produced by actually running the code on Windows 10 Pro (10.0.19045). The runtimes are Node.js v22.16.0 (win32/x64, V8 12.4, ICU 77.1, Unicode 16.0) and Python 3.13.3 (unicodedata 15.1.0). Intl.Segmenter was available, and the third-party Python regex module was not installed. Where something was missing, I say so.

Every code point is given in U+XXXX form. The subject of this article is emoji, so if your browser or terminal cannot draw the glyph you cannot verify anything. That is why every sample ships with its code point list. During verification I judged by hexadecimal output rather than by what I saw on screen. All strings were assembled from code points with String.fromCodePoint and chr(), then compared against the source literal to confirm they matched.

What this article does not cover. The normalization mechanics that turn Hangul into two different code point sequences inside Unicode are covered in NFC and NFD. Here, section 5 only shows the numbers where the lengths diverge. Diagnosing encoding damage from reading a charset wrongly lives in cp949 and UTF-8, and section 8 deals only with byte length. The arithmetic of matching Hangul syllables with regex ranges is in the Korean regex trap, and section 7 looks only at the dot and the flags as they apply to emoji.

1. Dissecting one emoji - four different numbers

I took a single family emoji and counted it four ways. The sample is U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466, which appears on screen as one 👨‍👩‍👧‍👦.

node v22.16.0  (win32/x64)   ICU 77.1 / Unicode 16.0
built from code points : U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466
same as source literal : true

(a) .length    UTF-16 code units : 11
(b) code point count             : 7
(c) UTF-8 byte length            : 25
(d) grapheme cluster count       : 1

code points  : U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466
utf-16 units : 0xD83D 0xDC68 0x200D 0xD83D 0xDC69 0x200D 0xD83D 0xDC67 0x200D 0xD83D 0xDC66
utf-8 bytes  : F0 9F 91 A8 E2 80 8D F0 9F 91 A9 E2 80 8D F0 9F 91 A7 E2 80 8D F0 9F 91 A6

11, 7, 25, 1. That is the same thing counted four times. None of the numbers is wrong. Each one counted a different unit.

Break it down per code point and the reason becomes obvious immediately.

per code point
  code point   utf-16 units   utf-8 bytes   name
  --------------------------------------------------------------
  U+1F468      2              4             MAN
  U+200D       1              3             ZERO WIDTH JOINER
  U+1F469      2              4             WOMAN
  U+200D       1              3             ZERO WIDTH JOINER
  U+1F467      2              4             GIRL
  U+200D       1              3             ZERO WIDTH JOINER
  U+1F466      2              4             BOY
  --------------------------------------------------------------
  total        11             25            1 grapheme
  • Each of the four pictographs takes 2 UTF-16 code units. A character like U+1F468 sits above U+FFFF, so it does not fit into a single UTF-16 slot. It is represented by two code units, a surrogate pair. Four times two is eight
  • Each of the three U+200D joiners takes 1. That character is below U+FFFF, so it fits in one slot. Eight plus three is 11
  • In UTF-8 a pictograph is 4 bytes and a joiner is 3 bytes. Four times four plus three times three is 25
  • The code point count is simply the number of items, which is 7
  • The grapheme cluster count is 1. That is the result of splitting by the rules defined in Unicode Standard Annex 29, and it matches what a human counts

Naming each unit precisely here makes everything that follows easier.

2. ZWJ is the glue - remove U+200D and one becomes four

The ZWJ in this article title is U+200D ZERO WIDTH JOINER. It is an invisible character of zero width, and its job is to fuse the pictographs on either side of it into one. The easiest way to prove it is to take it out.

with    U+200D : cps=7  units=11  bytes=25  graphemes=1
without U+200D : cps=4  units=8   bytes=16  graphemes=4
without U+200D code points : U+1F468 U+1F469 U+1F467 U+1F466
grapheme split             : [U+1F468] [U+1F469] [U+1F467] [U+1F466]

one glue character removed -> 1 grapheme becomes 4.
the utf-8 byte count only dropped from 25 to 16.

Removing the three joiners turned 1 grapheme into 4. The family that looked like a single blob on screen scatters into man, woman, girl and boy. And yet the byte count only dropped from 25 to 16. That contrast matters. In storage terms almost nothing changed, but the character count quadrupled.

Growing the chain one link at a time makes the structure even clearer.

growing the chain, one link at a time:
  cps units bytes graphemes  code points
  ----------------------------------------------------------------------
  1    2     4      1          U+1F468
  2    3     7      1          U+1F468 U+200D
  3    5     11     1          U+1F468 U+200D U+1F469
  5    8     18     1          U+1F468 U+200D U+1F469 U+200D U+1F467
  7    11    25     1          U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466

note row 2: U+1F468 U+200D is a DANGLING joiner, an invalid sequence,
and it still counts as 1 grapheme.
  • The grapheme count stays at 1 throughout. While code points go from 1 to 7 and bytes grow sixfold from 4 to 25, the number a human counts never changes
  • The second row is the one that matters in production. U+1F468 U+200D is a joiner hanging off the end with nothing to join. It is not a valid sequence per the Unicode spec, yet the grapheme count is still 1 and no layer raises an error
  • This state really does occur when you truncate a string. Section 5 shows exactly where
  • Rule GB11 in Annex 29 defines this behaviour: do not break between a pictograph, a joiner, and a pictograph. That is why even a dangling joiner attaches to the character before it

Unicode Technical Standard 51 calls this construction an emoji ZWJ sequence and describes it as the mechanism by which implementations treat the sequence as a single glyph. In other words this is neither a bug nor a side effect; it is designed behaviour. Expanding the emoji set otherwise means minting new code points forever, whereas the joiner lets you compose new pictures from existing characters. The price is an explosion in length.

3. Skin tone and flags - other ways characters fuse into one

Besides the joiner there are three more ways multiple code points clump into one. I checked each of them.

3.1 A skin tone modifier is a separate code point

label                  cps  units  bytes  graphemes  code points
------------------------------------------------------------------------------
thumbs up bare         1    2      4      1          U+1F44D
thumbs up tone-2       2    4      8      1          U+1F44D U+1F3FC
thumbs up tone-3       2    4      8      1          U+1F44D U+1F3FD
thumbs up tone-5       2    4      8      1          U+1F44D U+1F3FF
modifier alone         1    2      4      1          U+1F3FD
man + tone-3           2    4      8      1          U+1F468 U+1F3FD

toned couple with a variation selector - the realistic worst case:
  U+1F468 U+1F3FB U+200D U+2764 U+FE0F U+200D U+1F469 U+1F3FF
  cps=8  units=12  bytes=28  graphemes=1
  U+FE0F is VARIATION SELECTOR-16, 3 more bytes that draw nothing.
  • Skin tone does not tint the original character. It appends one more modifier code point after it. That is why the length doubles exactly: code points 1 to 2, bytes 4 to 8
  • The length is the same whichever of the five tones you attach. U+1F3FB through U+1F3FF are all 4 bytes
  • The modifier alone is also a single grapheme. Left without a base character, U+1F3FD renders as something like a colour swatch
  • The last sample is close to the worst case you will meet in production. Two skin tones, two joiners and a U+FE0F add up to 8 code points and 28 bytes in one character
  • U+FE0F is VARIATION SELECTOR-16. It only instructs the renderer to draw the preceding character in emoji form, so it spends 3 bytes while drawing nothing at all. It is the value people most often forget in length calculations

3.2 A flag is two regional indicator characters

label        cps  units  bytes  graphemes  code points
----------------------------------------------------------------------
KR flag      2    4      8      1          U+1F1F0 U+1F1F7
JP flag      2    4      8      1          U+1F1EF U+1F1F5
US flag      2    4      8      1          U+1F1FA U+1F1F8

a single regional indicator U+1F1F0 alone:
  cps=1  units=2  bytes=4  graphemes=1
  it is not half a flag - it is a boxed letter K.

pairing is greedy, left to right:
  2 RI  U+1F1F0 U+1F1F7   graphemes=1   [U+1F1F0 U+1F1F7]
  3 RI  + U+1F1FA         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA]
  4 RI  + U+1F1F8         graphemes=2   [U+1F1F0 U+1F1F7] [U+1F1FA U+1F1F8]

deleting ONE regional indicator re-pairs everything after it.

tag sequence flag (black flag + 5 tag letters + terminator):
  U+1F3F4 U+E0067 U+E0062 U+E0073 U+E0063 U+E0074 U+E007F
  cps=7  units=14  bytes=28  graphemes=1

Flags have no dedicated code points. Put two regional indicator characters corresponding to letters side by side and the renderer draws a flag. The Korean flag is U+1F1F0 for K and U+1F1F7 for R.

  • Leaving only one does not give you half a flag. You get the letter K inside a box. As data it is a perfectly valid single grapheme
  • Pairing is greedy from the left. Place three and the first two become a flag while the third is left alone. That follows from rules GB12 and GB13 in Annex 29, which only allow a break before an odd-numbered indicator
  • So deleting one in the middle turns every flag after it into a different country. One backspace does this in any input that carries several flags
  • The final sample is a tag sequence. A black flag plus five tag characters and a terminator make 7 code points and 28 bytes in one character. Subdivision flags use this construction
  • Technical Standard 51 is explicit that only flag sequences listed in the spec data files are valid. Stick two arbitrary letters together and you see two letters, not a flag

There are four ways an emoji gets long.

ConstructionStructureCode pointsUTF-8 bytesGraphemes
Single emojiOne pictograph141

Modifier sequenceBase + skin tone modifier281

Worst mixed case2 skin tones + joiner + U+FE0F8281

The rightmost two columns are all 1 while the middle scatters from 1 to 8. This is why the phrase character count can never be a specification.

4. This is not an emoji problem - Hangul NFD and combining accents

It is easy to read this far and conclude that blocking emoji fixes it. But lengths diverge without a single emoji present. I checked.

label              .length  cps  bytes  graphemes  code points
--------------------------------------------------------------------------------
hangul NFC         1        1    3      1          U+D55C
hangul NFD         3        3    9      1          U+1112 U+1161 U+11AB
hangul x2 NFC      2        2    6      2          U+D55C U+AE00
hangul x2 NFD      6        6    18     2          U+1112 U+1161 U+11AB U+1100 U+1173 U+11AF
e-acute NFC        1        1    2      1          U+00E9
e-acute NFD        2        2    3      1          U+0065 U+0301
3 stacked marks    4        4    7      1          U+0065 U+0301 U+0323 U+0304

NFC === NFD for the same visible text : false
  .length 2 vs 6   bytes 6 vs 18   graphemes 2 vs 2
no emoji involved. the split between units and graphemes is already there.

Just read the numbers. Two characters that look identical on screen have .length 2 on one side and 6 on the other. The byte counts differ threefold, 6 against 18. And yet the grapheme count is 2 on both sides.

  • The same character is expressible as one precomposed code point or as three jamo. Either form is valid Unicode
  • Why this happens and where it comes from is outside the scope of this article. It is written up in NFC and NFD. All we need here is the fact that the lengths diverge
  • Latin behaves the same way. A single U+00E9 and the pair U+0065 U+0301 look like the same character on screen
  • Combining marks have no count limit. Stack three and the grapheme count is 1; as you will see later, stack two hundred and it is still 1
  • The conclusion is what counts. The gap between code units and graphemes was not created by emoji. Emoji merely widened that gap twenty-fivefold and made it visible

Annex 29 addresses this head on. A single code point is not always the same thing as the one character a user has in mind, and the example the document reaches for is a letter with a combining accent. The grapheme cluster is the unit defined to close that gap.

5. The truncation accident - keep 20 characters and the emoji splits in half

Now let us reproduce the symptom from the introduction. The sample nickname is DevTeam01 followed by a space, the family emoji and 2026. An ordinary nickname with exactly one emoji in it.

nickname     : DevTeam01 👨‍👩‍👧‍👦2026
code points  : U+0044 U+0065 U+0076 U+0054 U+0065 U+0061 U+006D U+0030 U+0031
               U+0020 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466
               U+0032 U+0030 U+0032 U+0036

  utf-8 bytes            : 39
  utf-16 code units      : 25
  code points            : 21
  grapheme clusters      : 15

the rule says "at most 20 characters". which number is that?
  unit              value   verdict
  --------------------------------------
  utf-8 bytes       39      REJECTED
  utf-16 units      25      REJECTED
  code points       21      REJECTED
  graphemes         15      PASS

The same nickname is rejected three times and passes once. By the user's own way of counting, graphemes, it is 15 characters with room to spare, but if the server uses .length it sees 25 and rejects it. That is precisely the report from the introduction.

Something worse happens when the system does not reject at all and silently truncates instead.

NICK.slice(0, 20)
  code points     : U+0044 U+0065 U+0076 U+0054 U+0065 U+0061 U+006D U+0030 U+0031
                    U+0020 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+D83D
  .length         : 20
  final code unit : 0xD83D   (0xD800-0xDBFF is a HIGH SURROGATE)
  isWellFormed()  : false

                    A9 E2 80 8D F0 9F 91 A7 E2 80 8D EF BF BD
  last 6 bytes    : E2 80 8D EF BF BD
                    EF BF BD is U+FFFD. the half emoji became a question mark box.
  utf8 round trip : false
  JSON.stringify  : "DevTeam01 👨‍👩‍👧‍\ud83d"

substring(0,20) identical : true
Array.from().slice(0,20)  : isWellFormed=true  graphemes=14
  no lone surrogate, but the emoji lost its BOY and the family is now 3 people.

The final code unit is 0xD83D. That is not a character but the leading half of a surrogate pair, and its partner was cut away. The name for this state is a lone surrogate.

  • isWellFormed() returns false. This method looks only for lone surrogates. It is the one validation function this article needs
  • Encode that string as UTF-8 and the tail is EF BF BD, the U+FFFD replacement character. The original bytes vanish at that moment, and no information survives about which character was replaced
  • The round trip breaks. Encoding and decoding no longer returns the original. Store it and read it back and you get a different value
  • substring produces the same result. Both of them cut code units
  • Cutting by code point (slice after Array.from) produces no lone surrogate. But this time the joiner is severed, the family of four becomes three people, and the grapheme count drops to 14. The data is valid, but it is a different picture from the one the user typed

5.1 Code point languages are not safe either

In Python a string is an array of code points, so lone surrogates cannot be created. It is still not safe.

python 3.13.3 / win32
slice   len  utf8  last code point  state
----------------------------------------------------------
[:21  ] 21   39    U+0036           family whole
[:20  ] 20   38    U+0032           family whole
[:17  ] 17   35    U+1F466          family whole
[:16  ] 16   31    U+200D           DANGLING JOINER - invalid
[:15  ] 15   28    U+1F467          family severed
[:14  ] 14   24    U+200D           DANGLING JOINER - invalid
[:11  ] 11   14    U+1F468          family severed

now the byte based cut, which is what a byte sized column does
u8(NICK)[:20] : 44 65 76 54 65 61 6D 30 31 20 F0 9F 91 A8 E2 80 8D F0 9F 91
  decode strict  : UnicodeDecodeError - unexpected end of data
  decode replace : U+0044 ... U+1F468 U+200D U+FFFD
  decode ignore  : U+0044 ... U+1F468 U+200D
  • Four of the seven cut points produced broken output. Two left a dangling joiner at the end, and two severed the family
  • A dangling joiner is an invalid sequence per the Unicode spec, and nothing raises an error. It gets stored, transmitted, and passed on to other systems
  • Byte level truncation is more direct. Decoding fails outright in strict mode. If you size the column in bytes and then cut on bytes, you store invalid UTF-8
  • The ignore error option is the most dangerous. It silently drops the severed fragment, so nothing reaches the log and only the data disappears. How to tell encoding errors apart is written up in cp949 and UTF-8

6. The reversal accident - the flag becomes a different country

Reversing a string is a stock interview question, and the array reversal that passes for the right answer falls apart completely on emoji. The sample is ab, then the Korean flag, then c.

input : U+0061 U+0062 U+1F1F0 U+1F1F7 U+0063   graphemes=4

split("").reverse().join("")
  code points  : U+0063 U+DDF7 U+1F1F0 U+D83C U+0062 U+0061
  isWellFormed : false
  utf-8 bytes  : 63 EF BF BD F0 9F 87 B0 EF BF BD 62 61
  -> two lone surrogates, both encoded as EF BF BD

Array.from().reverse().join("")
  code points  : U+0063 U+1F1F7 U+1F1F0 U+0062 U+0061   graphemes=4
  isWellFormed : true
  -> valid, but U+1F1F7 U+1F1F0 is a DIFFERENT flag than U+1F1F0 U+1F1F7

grapheme reverse
  code points  : U+0063 U+1F1F0 U+1F1F7 U+0062 U+0061   graphemes=4
  flag intact  : true

same three ways on A + family + B:
  units     : U+0042 U+DC66 U+D83D U+200D U+DC67 U+D83D U+200D U+DC69 U+D83D U+200D U+DC68 U+D83D U+0041
  cps       : U+0042 U+1F466 U+200D U+1F467 U+200D U+1F469 U+200D U+1F468 U+0041
  graphemes : U+0042 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466 U+0041

All three approaches give different results.

  • Reversing code units reverses the surrogate pair itself. Two lone surrogates appear and each becomes EF BF BD in UTF-8. The data has been destroyed
  • Reversing code points produces a valid string. But the regional indicators swap order, so you get a different country's flag. No error, validation passes, and yet the content changed
  • On the family emoji, code point reversal flips the order of the people. Boy, girl, woman, man is a different emoji
  • Only grapheme reversal preserves the original. The flag stays intact and the family keeps its order
  • The practical conclusion is simple. If you need to reverse a string, do it by grapheme. And in truth, genuinely needing to reverse a string is rare

7. Regex - how many times does one dot match one emoji

The block emoji response usually starts with a regular expression. I checked what those expressions actually count.

v flag supported        : true
\p{RGI_Emoji} supported : true

target        /./g  /./gu  /./gv  \p{RGI_Emoji}/gv  graphemes
------------------------------------------------------------------
family        11    7      7      1                 1
KR flag       4     2      2      1                 1
thumb+tone    4     2      2      1                 1
grinning      2     1      1      1                 1
hangul NFD    3     3      3      0                 1

what /./g captured on the family (raw code units):
  0xD83D 0xDC68 0x200D 0xD83D 0xDC69 0x200D 0xD83D 0xDC67 0x200D 0xD83D 0xDC66
what /./gu captured (code points):
  U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466

A single dot matches one emoji 11 times. Without the u flag the regex engine moves in code units and treats each half of a surrogate pair as its own character.

  • Add the u flag and it becomes code point based, giving 7. An improvement, but still not 1
  • The v flag gives the same 7 as u here. Flags alone do not get you to graphemes
  • The way to count it as one is the v flag together with \p{RGI_Emoji}. Both were supported in my test environment, and that was the first time 1 appeared
  • But look at the last row. \p{RGI_Emoji} matches Hangul NFD zero times. It is an emoji-specific tool, so it does not solve the grapheme problem for ordinary text

7.1 Stripping by emoji property leaves debris behind

property escapes on the family emoji:
  \p{Emoji}                 : 4 matches
  \p{Emoji_Presentation}    : 4 matches
  \p{Extended_Pictographic} : 4 matches
  none of them is 1. they match the PARTS.

a naive emoji filter strips pictographs and leaves the glue behind:
  before : U+0044 ... U+0020 U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466 U+0032 U+0030 U+0032 U+0036
  after  : U+0044 ... U+0020 U+200D U+200D U+200D U+0032 U+0030 U+0032 U+0036
  U+200D left : 3   invisible, unremovable by eye
  .length 25 -> 17   graphemes 15 -> 14

and \p{Emoji} matches things nobody calls an emoji:
  "2026".match(/\p{Emoji}/gu) -> ["2","0","2","6"]
  "#*".match(/\p{Emoji}/gu)   -> ["#","*"]
  a digit-blocking regex written this way rejects order numbers.

There are two traps here, and both go off regularly in production.

Pattern👨‍👩‍👧‍👦 match countWhat it countsPractical verdict
/./g11UTF-16 code unitsDo not use
/./gu7Code pointsUnfit for counting characters
/./gv7Code pointsSame
\p{Emoji}4Characters with the emoji propertyAlso matches digits and symbols
\p{Emoji_Presentation}4Each individual partStripping leaves debris
\p{Extended_Pictographic}4Each individual partStripping leaves debris

  • Strip the parts and the glue remains. After removing only the pictographs, three U+200D characters were still sitting there. Nothing is visible on screen, so manual review will never catch it
  • That debris creates new problems one layer down. Attach another pictograph after it and they clump into an unintended combination, and every length calculation stays wrong
  • \p{Emoji} matched the digits 2, 0, 2 and 6 individually. It also matches the number sign and the asterisk, because Unicode assigns the emoji property to those characters
  • So blocking emoji with \p{Emoji} rejects order numbers and phone numbers as well. The ticket you receive will not say emoji input fails; it will say saving fails when I type a digit

8. Storage and transport - the wall four byte characters hit

Even with the length arithmetic right, the storage layer blocks you again. I checked exactly where the boundary is.

label            cps  max bytes/char  utf8 total  3-byte-max charset
--------------------------------------------------------------------------
ascii            9    1               9           stores fine
2 ideographs     2    3               6           stores fine
grinning         1    4               4           REJECTED - needs 4 bytes
KR flag          2    4               8           REJECTED - needs 4 bytes
family           7    4               25          REJECTED - needs 4 bytes
nickname         21   4               39          REJECTED - needs 4 bytes

the boundary is exact:
  U+FFFF  utf-8 length = 3   last BMP code point
  U+10000 utf-8 length = 4   first code point above it

python 3.13.3 - two legacy charsets asked to hold the same samples
label            utf8 bytes  cp949 encode          shift_jis encode
----------------------------------------------------------------------
ascii            9           ok 9 B                ok 9 B
2 ideographs     6           ok 4 B                ok 4 B
grinning         4           UnicodeEncodeError    UnicodeEncodeError
KR flag          8           UnicodeEncodeError    UnicodeEncodeError
family           25          UnicodeEncodeError    UnicodeEncodeError

The boundary is U+FFFF. Below it, UTF-8 needs at most 3 bytes; above it, 4. And every emoji sits above U+FFFF. That is why a charset that accepts at most 3 bytes per character cannot hold a single emoji. The classic case is an old database charset that is called UTF-8 but stores only up to three bytes, and the legacy charsets cp949 and shift_jis threw encoding exceptions outright.

This is where sizing a column in characters and sizing it in bytes part ways. I ran the arithmetic on the same nickname.

  20 graphemes       15      fits

how many bytes must you reserve for "20 characters"?
  20 code points, worst case utf-8   : 80 bytes
  20 family emoji                    : 500 bytes (cps=140, units=220)
  20 kiss sequences                  : 700 bytes (cps=200, units=300)
  1 grapheme, 200 combining marks    : 401 bytes (cps=201, graphemes=1)
  20 graphemes of stacked marks      : 8020 bytes
  -> "20 graphemes" has NO byte upper bound.

This calculation is the heart of the section.

Definition of 20 charactersUTF-8 bytes requiredIs there an upper boundUsable as a column size
20 bytes20YesUsable (the definition is bytes)
20 UTF-16 code unitsUp to 80YesUsable (size it at 80)

  • There is no safe value if you size a column in graphemes. That is because there is no upper bound on how many code points fit in one grapheme. Stack 200 combining marks and the grapheme count is 1 while the byte count is 401
  • I confirmed a 20-grapheme string growing to 8,020 bytes in practice. That is not a value VARCHAR(20) can hold
  • So you must separate the display limit from the storage limit. The on-screen counter is graphemes, the column size is bytes. Trying to merge them into one is the cause of this bug
  • Validation has to enforce both conditions. Pass only when the value is at most 20 graphemes and also within the byte ceiling
  • When rejecting, tell the user which condition failed. A bare you have exceeded 20 characters means nothing to someone who counted 15

9. JSON and URLs - how far the same emoji inflates

The length changes once more at the transport layer.

  • URL encoding costs three characters per byte. One family emoji becomes 75 characters
  • With a query string budget of 2048, you can fit exactly one 20-grapheme family string. With ASCII nicknames you get 102
  • Base64 is the most efficient but humans cannot read it. Weigh the cost in logging and debugging

9.1 A half emoji behaves differently at every layer

what happens to a half emoji downstream:
  JSON.stringify(lone high surrogate) : "\ud83d"
  JSON.parse of that                  : succeeds, isWellFormed=false
  encodeURIComponent(...)             : THROWS URIError - URI malformed
  Buffer.from(...,"utf8")             : EF BF BD   silently replaced by U+FFFD
  -> JSON accepts it, the URL layer throws, the byte layer corrupts it.
     three layers, three different behaviours, no error at the source.

This is the structure that makes diagnosis hard. Nothing raises an error at the place where the damage happened.

  • JSON lets it through. It serializes and deserializes successfully. The result simply returns false from isWellFormed()
  • The URL layer throws. This is the first place an error becomes visible, and it is far away from the code that did the cutting, which makes tracing the cause hard
  • The byte layer corrupts it silently. It swaps in the replacement character and reports success. That is the most dangerous behaviour
  • So validate immediately after truncating. One line of isWellFormed() catches all three layers of trouble at the point of origin

11.1 Display width is not a property of the data

The width of the family emoji is particularly interesting. Summed per code point, four pictographs at 2 cells each is 8 cells and three joiners are 0, for a total of 8. But a terminal that supports the sequence draws one glyph in 2 cells.

  • The same data is either 2 cells or 8. It depends on whether the renderer knows that sequence
  • No library can settle this. Without knowing the font the calculation is impossible. It is the only one of the five that is not determined by the data alone
  • So monospaced alignment breaks in principle in front of emoji. Try to size table columns around strings containing emoji and some terminal will be misaligned
  • There are two practical responses. Give up monospaced alignment for columns that contain emoji, or swap emoji for a placeholder before display

  the ascii message is 93 characters, GSM-7, ONE segment (limit 160).

how many "characters" fit in one UCS-2 segment of 70 units:
  ascii or ideographs   70 of them

This table maps straight onto billing.

  • With ASCII only, the message is encoded as GSM-7 and one segment holds 160 characters. A 93 character message is one segment
  • One non-ASCII character flips the entire message to UCS-2. At that moment the segment limit drops to 70 units
  • That is why adding one emoji turned a 93 character message into two segments. The user thinks they added one character; the bill doubles
  • A single segment holds 6 family emoji. That looks like six characters to the user, and it fills an entire message
  • What you must count here is UTF-16 code units. Count graphemes and the billing calculation is wrong

12. What should you count - a decision table by purpose

The conclusion of this article is not block emoji. It is decide what the character you are counting actually is. The purpose determines the unit.

The key to using this table is the third row. Real world input validation is not a matter of picking one unit. Keep the display limit and the storage limit separate and check both. The attempt to merge them is what creates the bug from the introduction.

  • Write the unit into the spec document. Not nickname maximum 20 characters, but nickname maximum 20 graphemes, storage limit 80 bytes
  • Verify with the same sample that front end and back end use the same unit. In different languages, length means different things
  • Put the unit and the overage into the rejection message. You have exceeded 20 characters is meaningless to a user who counted 15
  • Reject rather than truncate. Silent truncation damages data and the user never notices. If you have no choice but to cut, cut by grapheme and validate
  • Check first that the storage layer accepts four byte characters. If it blocks here, correct length arithmetic buys you nothing

13. Why it slips through quietly, and the test samples

Finally, a summary of the nature of this bug. Why does it survive for years.

  • For most input, all five numbers agree. Eleven ASCII characters give 11 for bytes, code units, code points and graphemes alike. A developer testing with their own name sees nothing wrong
  • The reproduction window is narrow. It needs a particular kind of emoji, a particular length and a particular cut point to line up. The ticket gets closed as not reproducible
  • The failure is silent. Lone surrogates pass through JSON, and replacement characters get stored without an error. Nothing lands in the log
  • Where it shows and where it breaks are far apart. The code that cut the string and the URL layer that throws are different modules
  • Manual review will not catch it. U+200D debris and U+FEFF draw nothing on screen

What you need, therefore, is samples. Put the following into your test data and every accident in this article is caught during development.

  • A ZWJ sequence — U+1F468 U+200D U+1F469 U+200D U+1F467 U+200D U+1F466 (1 grapheme, 11 code units, 25 bytes)
  • A flag — U+1F1F0 U+1F1F7 plus a sample with three flags in a row (to check re-pairing)
  • A skin tone modifier — U+1F44D U+1F3FD
  • A sequence containing U+FE0F — to check that a zero width 3 byte character is not dropped from the arithmetic
  • Hangul NFD — U+1112 U+1161 U+11AB (1 grapheme, 3 code points)
  • A combining accent — U+0065 U+0301 plus a sample with several stacked marks
  • A tag sequence — the sample that shows the approximation regex getting it wrong
  • A string containing a lone surrogate — to confirm the validation function really catches it
  • Boundary length samples — tuned so the cut point lands mid-emoji just before, at, and just after the limit
  • An ASCII-only sample — as a control. Here every unit should agree

That last item matters more than it looks. A test that only passes ASCII samples verifies nothing. It has only checked the range where all five numbers are the same.

# Emoji Character Counting — Five Lengths Compared, and How to Count and Cut Safely

> Source: braindetox.kr — One emoji counts as eleven characters
> Verified on: Windows 10 / Node.js v22.16.0 (ICU 77.1, Unicode 16.0) / Python 3.13.3
> Paste this file into an AI and say «audit our input validation against this» to get a concrete review.
> ⚠ Bottom line first: a «20 character limit» is not a specification until **you write down the unit.**

## 0. 30-second summary

A string does **not have one length.** Count the same single emoji (👨‍👩‍👧‍👦) and the numbers split like this.

| Unit | Value | Where you see this number |
|---|---|---|
| UTF-8 bytes | 25 | DB storage, the network, len in Go and Rust |
| UTF-16 code units | 11 | JavaScript `.length`, Java, C#, SMS UCS-2 |
| Code points | 7 | Python `len()`, Swift `unicodeScalars` |
| Grapheme clusters | 1 | The «character» a human counts, cursor movement, backspace |
| Terminal display width | 2 (when the renderer supports it) | Monospaced alignment, table layout |

For most input these five numbers agree. **They only split the moment an emoji arrives.** That is why it slips by quietly and then blows up one day.

## 1. Measurements (actually executed)

| String | Bytes | UTF-16 | Code points | Graphemes |
|---|---|---|---|---|
| `hello world` | 11 | 11 | 11 | 11 |
| 漢字 (U+6F22 U+5B57) | 6 | 2 | 2 | 2 |
| é NFC (U+00E9) | 2 | 1 | 1 | 1 |
| é NFD (U+0065 U+0301) | 3 | 2 | 2 | 1 |
| 😀 (U+1F600) | 4 | 2 | 1 | 1 |
| 🇰🇷 (U+1F1F0 U+1F1F7) | 8 | 4 | 2 | 1 |
| 👍🏽 (U+1F44D U+1F3FD) | 8 | 4 | 2 | 1 |
| 👨‍👩‍👧‍👦 (ZWJ family of 4) | 25 | 11 | 7 | 1 |
| `DevTeam01 👨‍👩‍👧‍👦2026` | 39 | 25 | 21 | 15 |

The last row is the whole point. **Feed this nickname to an «at most 20 characters» rule and the outcome depends entirely on which unit you count.**

- Counted in bytes: 39 → rejected
- Counted in UTF-16: 25 → rejected
- Counted in code points: 21 → rejected
- Counted in graphemes: 15 → passes

## 2. The four ways an emoji gets long

| Construction | Structure | Example | Code points |
|---|---|---|---|
| ZWJ sequence | U+200D between pictographs | 👨‍👩‍👧‍👦 | 7 |
| Modifier sequence | Base + skin tone modifier | 👍🏽 | 2 |
| Flag sequence | 2 regional indicators | 🇰🇷 | 2 |
| Tag sequence | Black flag + tag characters + terminator | Scotland flag | 7 |

- **U+200D (ZWJ) is the glue.** Remove the three U+200D from a family of four and the grapheme count grows from 1 to **4.** The byte count only drops from 25 to 16
- **U+FE0F (VS16) is 3 bytes of zero width.** It draws nothing and still adds length
- **Flag pairing is greedy from the left.** Delete one regional indicator and everything after it re-pairs
- Skin tones, flags and tag sequences are all a single grapheme too

## 3. The unit to count, by purpose

**This table is the heart of the document.** What you count is decided by the requirement.

| Purpose | Unit to count | Why | How to verify |
|---|---|---|---|
| The «n characters left» counter shown to users | **Graphemes** | Matches the number a human counts | Check one emoji counts as 1 |
| Sizing a DB column | **Bytes** | Storage capacity is measured in bytes | Calculate the worst case in bytes |
| Hard limit on an input form | **Bytes and graphemes both** | Display limit and storage limit differ | Enforce both conditions |
| SMS billing | **UTF-16 code units** | UCS-2 segments are measured in units | The 70 unit boundary (67 when concatenated) |
| Monospaced screen layout | **Display width** | Cell count decides the layout | Verify visually with the real font |
| Cross-language API contracts | **Bytes** | The only unit identical in every language | Check both sides return the same number |
| Logs, hashes, deduplication | **Bytes after normalization** | NFC and NFD are different bytes | Normalize first |

## 4. Code you can use right now (JavaScript)

`Intl.Segmenter` is available in Node 16 and above and in current browsers. I confirmed it working in the test environment (Node v22.16.0, ICU 77.1).

```js
const seg = new Intl.Segmenter('en', { granularity: 'grapheme' });

// count - one emoji counts as 1
function countGraphemes(s) {
  return [...seg.segment(s)].length;
}

// truncate - never splits an emoji in half
function sliceGraphemes(s, n) {
  return [...seg.segment(s)].slice(0, n).map(function (x) { return x.segment; }).join('');
}

// reverse - the flag does not become another country
function reverseGraphemes(s) {
  return [...seg.segment(s)].map(function (x) { return x.segment; }).reverse().join('');
}

// byte-bounded truncation - respects the column limit while preserving emoji
function sliceByBytes(s, maxBytes) {
  const enc = new TextEncoder();
  let outStr = '';
  let used = 0;
  for (const part of seg.segment(s)) {
    const n = enc.encode(part.segment).length;
    if (used + n > maxBytes) break;
    outStr += part.segment;
    used += n;
  }
  return outStr;
}

// validate - did a half surrogate slip in
function isIntact(s) {
  if (typeof s.isWellFormed === 'function') return s.isWellFormed();
  const paired = s.replace(/[\uD800-\uDBFF][\uDC00-\uDFFF]/g, '');
  return !/[\uD800-\uDFFF]/.test(paired);
}
```

**Verified behaviour**

- `countGraphemes` counts 👨‍👩‍👧‍👦 as **1**
- Truncating `DevTeam01 👨‍👩‍👧‍👦2026` to 12 graphemes leaves the emoji intact and `isWellFormed()` true
- Truncating the same string with `.slice(0, 20)` makes `isWellFormed()` **false**, and the UTF-8 encoding ends in `EF BF BD` (U+FFFD)

## 6. On the Python side

- `len()` counts **code points.** 👨‍👩‍👧‍👦 is **7.** That differs from 11 in JavaScript
- The standard library has **no grapheme API.** Verified in the test environment: `hasattr(str, 'graphemes')` is False, and the standard `re` rejects `\X` (`PatternError: bad escape \X`)
- You need `\X` from the third-party `regex` module. It was **not installed** in the test environment
- Slicing never creates a half surrogate, but it **cuts ZWJ chains right through.** `NICK[:16]` ends in U+200D, a joiner with nothing to join

```python
# graphemes require a third-party module
import regex
def count_graphemes(s):
    return len(regex.findall(r'\X', s))

# truncate within a byte limit (standard library only)
def slice_by_bytes(s, max_bytes):
    b = s.encode('utf-8')[:max_bytes]
    return b.decode('utf-8', 'ignore')   # discards the fragment cut at the boundary
```

`decode(..., 'ignore')` silently discards the severed fragment. If you need a log, catch it with `strict` and handle it yourself.

## 7. Storage and transport arithmetic

- Every emoji sits **above U+FFFF.** U+FFFF is 3 UTF-8 bytes; U+10000 is **4**
- A charset that accepts at most 3 bytes per character **cannot hold a single emoji.** In testing, cp949 and shift_jis both rejected 😀 (`UnicodeEncodeError`)
- When converting «20 characters» into bytes, **always use the worst case**

| What «20 characters» means | UTF-8 bytes required |
|---|---|
| 20 code points | Up to 80 |
| 20 graphemes (family emoji) | 500 |
| 20 graphemes (200 combining marks each) | 8,020 |
| 20 graphemes (general) | **No upper bound** |

**Do not size a column in graphemes.** There is no upper bound on how many code points fit inside one grapheme.

## 8. JSON and URL inflation

| Transformation | Result | Multiplier |
|---|---|---|
| 👨‍👩‍👧‍👦 UTF-8 | 25 bytes | 1.0x |
| JSON `{"nick":"..."}` UTF-8 | 36 bytes | — |
| JSON ASCII escaped | 77 bytes | 2.14x |
| `encodeURIComponent` | 75 ASCII characters | 3.0x (3 per byte) |
| Base64 | 36 characters | 1.44x |

- The `\u` escape in JSON is UTF-16 based, so **one U+1F468 becomes two escapes** (`\uD83D` and `\uDC68`)
- With a 2048 character URL query budget, a 20-grapheme family string fits **once**
- Half surrogates behave differently at every layer: JSON **lets them through**, `encodeURIComponent` **throws URIError**, and UTF-8 encoding **silently swaps in U+FFFD.** Nothing raises an error at the point of origin

## 9. SMS billing (a separate rule)

- ASCII only means GSM-7, **160 characters** per segment
- **A single** non-GSM character flips the whole message to UCS-2, at **70 units** per segment (67 when concatenated)
- Measured: a 93 character ASCII message is 1 GSM-7 segment. **Add one emoji and it switches to UCS-2 and becomes 2 segments**
- How many fit in one segment (70 units): 70 ordinary characters / 35 😀 / 17 🇰🇷 / **6** 👨‍👩‍👧‍👦

The user thinks they added «one character» and the bill doubles.

## 10. When you try to block emoji with a regex

| Pattern | 👨‍👩‍👧‍👦 match count |
|---|---|
| `/./g` | 11 |
| `/./gu` | 7 |
| `/./gv` | 7 |
| `\p{Emoji}` | 4 |
| `\p{Emoji_Presentation}` | 4 |
| `\p{Extended_Pictographic}` | 4 |
| `\p{RGI_Emoji}` (v flag) | **1** |

- Without the `u` flag, `.` counts **code units.** It matches 11 times
- With the `u` flag it becomes code point based and matches 7 times. **Still not 1**
- Counting it as one requires **the `v` flag with `\p{RGI_Emoji}`.** Both were supported in the test environment
- Stripping with `\p{Extended_Pictographic}` **leaves three U+200D behind.** Invisible debris
- `\p{Emoji}` **also matches digits, `#` and `*`.** Block emoji with it and order numbers get rejected

## 11. Checklist

- [ ] The «n character limit» spec document **states the unit** (bytes / code units / code points / graphemes)
- [ ] The on-screen counter and the server validation use **the same unit**
- [ ] Front end (JavaScript) and back end (Python, Java, Go) length calculations were **checked against the same string for agreement**
- [ ] The DB column was sized on the **worst case in bytes** (not sized in graphemes)
- [ ] The storage layer uses **a charset that accepts four byte characters**
- [ ] Truncation does **not use `slice`, `substring` or byte slicing directly**
- [ ] The truncated result is **validated with `isWellFormed()`**
- [ ] Reversal and truncation tests include **ZWJ sequence, flag, skin tone and Hangul NFD samples**
- [ ] The emoji filter **leaves no U+200D debris**
- [ ] The emoji blocking regex **does not false-positive on digits, `#` and `*`**
- [ ] The SMS sending path **calculates the UCS-2 switch and the segment count**
- [ ] **Normalization runs first**, before deduplication and hashing
- [ ] The validation failure message tells the user **which unit and by how many characters**

## 12. Do not

- ❌ **Stopping at «just block emoji»** — without deciding the unit, the rule keeps breaking
- ❌ Calling `.length` the «character count» — it is UTF-16 code units
- ❌ **Sizing a DB column** in graphemes — there is no upper bound
- ❌ Counting graphemes on the front end and bytes on the server while **expecting the same number**
- ❌ **Storing without validation** after cutting with `.slice()` — half surrogates flow downstream
- ❌ Reversing a string by reversing an array — the flag becomes **another country**
- ❌ Blocking emoji with `\p{Emoji}` — it blocks digits
- ❌ **Trusting a regex approximation as a complete grapheme split** — it gets Hangul NFD and tag sequences wrong
- ❌ Putting **only ASCII** in test samples — all five numbers agree there, so it catches nothing
