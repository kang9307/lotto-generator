git bisect - バグが入り込んだコミットを二分探索で見つける

コミット1,000個をテスト10回で。bisect run の自動化と終了コードの規約、skip・terms・マージ履歴まで実際の出力で

2026年9月1日 開発・インフラ

前は動いていたのに今は動かない。 この一文で始まる問題は、原因が分からないのではなくどこを見ればよいのか分からないのだ。コードはどこかで変わっており、そのどこかは数百個のコミットの間にある。git bisect はその区間を半分ずつ切り込んでいく命令である。

二分探索という発想そのものは別に扱ったことがある — カーネルのバグはどう絞り込まれるのかのほうがその話だ。この記事はその発想をgit が実装しておいた命令だけに絞る。どんな引数を与え、どんな出力が出て、どこで間違えるのか、である。

以下の出力はすべて git 2.48.1.windows.1 · Windows 10 Pro (10.0.19045) · Git Bash(GNU bash 5.2.37, MSYS2) で実際に実行して得たものである。2026年9月時点。実験はすべて一時ディレクトリに新しく作ったリポジトリで行い、本文の /tmp/demo はその場所を指す中立的な名前である。他のプラットフォームやシェルで変わりうる箇所はその都度示した。

何を解く道具なのか

git bisect が答える問いは一つだ。今は失敗し以前は成功していたなら、その間のどのコミットで変わったのか。 正常だったコミット一つと壊れたコミット一つを教えるだけで、git がその間の中間コミットをチェックアウトしてくれ、人かスクリプトが判定し、また半分に減らす。

ここで重要なのは犯人コミットの中身を知らなくてよいという点である。判定基準さえあればよい。性能のリグレッションでも、特定のログが出なくなったことでも、あるファイルが作られなくなったことでも、はい/いいえで答えられるテストならすべて対象だ。だからこの道具は、コードを読んで原因を推論するやり方とは性格が違う。推論ではなく測定である。

  • 必要なもの三つ — 壊れたコミット(たいてい HEAD)、正常だったコミット(タグ・リリース・数か月前のコミット)、再現するテスト
  • なくてよいもの — 原因についての仮説。むしろ仮説があるとそちらばかり見て見落とす
  • 探索の対象は区間全体のコミットであってファイルの差分ではない。だから複数ファイルにまたがる相互作用の問題も捕まる
  • 結果はコミット一つである。そのコミットが大きければまた絞り込む必要があるが、履歴全体から一つのコミットまで減っただけでもたいてい局面が変わる

実験用リポジトリを作る

説明だけでは掴めないので、リポジトリを一つ作ってから始める。コミット20個のものだ。total.sh は引数で受け取った数を足し、check.sh はその結果が合っていれば0で、違っていれば1で終わる。13番目のコミットで total.sh をインデックス走査に変えながら最後の引数を落とす不具合が入る。その後も無関係なコミットが七つ積み上がる。

# /tmp/demo で
git init -b main

cat > total.sh <<'EOF'
#!/bin/bash
sum=0
for n in "$@"; do
  sum=$(( sum + n ))
done
echo "$sum"
EOF

cat > check.sh <<'EOF'
#!/bin/bash
out=$(bash ./total.sh 1 2 3 4)
if [ "$out" = "10" ]; then
  exit 0
else
  echo "expected 10, got $out"
  exit 1
fi
EOF

出来上がった履歴と現在の状態はこうである。不具合は c13 にあり、HEAD である c20 でテストは失敗する。

$ git log --oneline

a25093a c01: add total.sh

$ bash ./check.sh; echo "exit=$?"

基本の流れ - セッション一つを最後まで

順序は四つだ。bisect start でセッションを開き、今が壊れていると bisect bad で伝え、正常だったコミットを bisect good で伝える。すると git が中間コミットをチェックアウトしてくれる。テストして good/bad を繰り返し、終わったら bisect reset で抜ける。

正常な地点を c02、故障の地点を c20 とすると候補は c03 から c20 まで18個である。以下がそのセッション全体だ。命令と出力を一つも省いていない。

$ git bisect bad

読み方の要領は Bisecting: の行だ。今回の判定を終えると何個残るかを教えてくれる。18個から8、4、1、0へ減り、テストは四回した。そして bisect start の後ろに引数を二つ付ければ bad・good の二行を省ける。順序は悪いほうが先である。

コミット1,000個は本当にテスト10回なのか

よく引用される計算が正しいのか測ってみるほうがよい。コミット1,000個のリポジトリを新しく作り、674番目のコミットで設定値を一つ壊してから、最初のコミットから HEAD まで全区間を自動探索させた。判定スクリプトが何回実行されたかを数えればよい。

$ git rev-list --count HEAD
1000

$ git bisect start HEAD $(git rev-list --max-parents=0 HEAD)
$ git bisect run bash /tmp/bigtest.sh
Bisecting: 249 revisions left to test after this (roughly 8 steps)
Bisecting: 124 revisions left to test after this (roughly 7 steps)
Bisecting: 62 revisions left to test after this (roughly 6 steps)
...
fe0dcdad953018ee006623208fdde398e98ea338 is the first bad commit
    c0674
bisect found first bad commit

# 判定スクリプトが実行された回数
10

ちょうど10回である。最初のコミットを正常な地点としたので候補は999個であり、999を2で割り続ければ10回で1を下回る。ここで重要な性質は絶対回数ではなく増える速さだ。コミットを2倍にしてもテストはきっかり1回しか増えない。

候補コミット数必要なテスト回数備考
184上の20コミットのリポジトリで実測
999101,000コミットのリポジトリで実測
2,00011コミットが2倍でも1回しか増えない
100,00017大規模リポジトリでも20回未満

表の下二行は実測ではなく同じ規則を延長した値である。要点はコミット数がボトルネックになることはほとんどないということだ。

テスト1回の時間が総時間を決める

ではボトルネックは何か。同じ1,000コミットの探索を二回回した。一度は判定が即座に終わるテストで、一度は sleep 2 を入れてわざと遅くしたテストで行った。答えは同じで、テスト回数も同じだった。

--- 即座に終わるテスト、999コミット
tests run: 10
wall time: 3693 ms

--- 同じ探索、テスト1回あたり2秒
tests run: 10
wall time: 24018 ms

同じ答え? fe0dcdad... / fe0dcdad...

差の20.3秒は2秒 × 10回である。git が使った時間はチェックアウト10回分の3.7秒だけだった。つまり総所要はほぼすべてテスト時間であり、公式は単純だ。総時間 ≒ テスト1回の時間 × log₂(候補数)。

だから bisect をかける前にテストを短くすることが実質的に最大の利益になる。テストスイート全体が5分なら10回で50分だが、問題を再現する最小ケースを作って30秒に減らせば5分になる。最小再現を先に作れという助言は定性的な勧めではなく10倍差の算数である。

  • スイート全体の代わりに失敗するテスト一つだけを回す。フレームワークの大半が単一ケースの指定に対応している
  • ビルドが必要ならインクリメンタルビルドが効くようにする。毎回フルリビルドがかかるとその時間がそのまま10倍になる
  • ネットワークや外部サービスに依存する部分は切り離す。遅いことも問題だが間欠的に失敗すると答えが間違う
  • 区間を狭められるなら狭める。候補を999個から60個に減らせばテストは10回から6回に減る

bisect reset を忘れると起きること

犯人を見つけた直後の状態をそのままにしておくと detached HEAD のまま残る。最後に検査したコミットの上に立っており、どのブランチにも付いていない。幸い git が親切に知らせてくれる。

$ git status
HEAD detached at 4d711a9
You are currently bisecting, started from branch 'main'.
  (use "git bisect reset" to get back to the original branch)

nothing to commit, working tree clean

$ ls .git | grep -i bisect
BISECT_ANCESTORS_OK
BISECT_EXPECTED_REV
BISECT_LOG
BISECT_NAMES
BISECT_START
BISECT_TERMS

$ ls .git/refs/bisect
bad
good-d6e191c941eb0f49e6ad6b88f546215ef538eecf

ここで何気なくコードを直してコミットすると、そのコミットはどのブランチにも属さない。後で reflog で探すことはできるが、経験する必要のない出来事だ。セッションが生きているか確認する最も速い方法は上のように .git の中に BISECT_* ファイルがあるか見ることで、reset すればすべて消える。

$ git bisect reset
Previous HEAD position was 4d711a9 c12: unrelated note 12
Switched to branch 'main'

# 犯人コミットにそのまま留まりたいとき
$ git bisect reset refs/bisect/bad
HEAD is now at f1fec3f c13: refactor total.sh to index-based loop

# 今のコミットから動かずセッションだけ片づける
$ git bisect reset HEAD

付け加えると、作業ツリーが汚れているとセッションは始まらない。 修正中のファイルをコミットするか stash で片づける必要がある。実際にこう終わる。

$ git status --short
 M total.sh

$ git bisect start f2ee06a d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
error: Your local changes to the following files would be overwritten by checkout:
	total.sh
Please commit your changes or stash them before you switch branches.
Aborting

bisect run - 人がいなくても最後まで回る

ここからがこの命令の本体である。判定をスクリプトに渡せば git bisect run がチェックアウトと判定と次の選択を自分で繰り返す。前のセッションとまったく同じリポジトリで、人の介入なしに一行で終わる。

手動セッションとまったく同じコミットを指し、人が打った命令は二行だ。run の後ろにはどんな命令でも来られる — make、npm test、pytest -k some_case、自作のシェルスクリプトすべて可能である。引数を付けてもよく、スクリプトのパスはチェックアウトされるリポジトリの外に置くほうが安全だ。リポジトリの中に置くと古いコミットにはそのファイルがないことがある。

終了コードの規約

自動化のすべては終了コードである。規約を取り違えると静かに間違ったコミットを指す。スクリプトを各コードに固定して回してみた結果をまとめるとこうなる。

終了コードgit の解釈実際に出たもの
0正常(good/old)すべて正常と表示され、悪い端点そのものを犯人として指した
1 ~ 124, 126, 127不具合(bad/new)1・2・124 は同じ挙動。区間の先頭コミットを犯人として指す
125判定不能 - スキップすべてスキップすると We cannot bisect more! の後に bisect run cannot continue any more
126 · 127 (初回)スクリプト実行失敗の疑い正常コミットで再試行した後 bogus exit code 127 for good revision で中断
128 以上探索中断bisect run failed: exit code 128 ... is < 0 or >= 128

文書上の規約は「0なら正常、125を除く1～127なら不具合、それ以外のコードは中断」である。ところが 126・127 を実際に回してみると文書よりもう一枚ある。この二つの値は POSIX シェルが実行不能・コマンドが見つからないに使う値なので、git は初回に限り既知の正常コミットへチェックアウトして同じ命令をもう一度回してみる。そこでも同じコードが出れば、スクリプト自体が間違っていると見て止まる。

$ git bisect run bash /tmp/rc.sh      # スクリプトが常に127で終わる
running 'bash' '/tmp/rc.sh'
[d6e191c941eb0f49e6ad6b88f546215ef538eecf] c02: add check.sh
running 'bash' '/tmp/rc.sh'
error: bogus exit code 127 for good revision
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

真ん中の行で正常コミット c02 へ移ってから元に戻った痕跡が見える。この安全装置のおかげでスクリプトのパスの打ち間違いで全区間が不具合と表示される事故はおおむね防げる。逆にこのメッセージが出たらコードを疑うのではなく、スクリプトが実行可能かどうかから見る。

最も危険な値は 124 だ。テストにタイムアウトをかけたときに出る値だが、規約上は不具合ありと読まれる。

$ timeout 1 sleep 5 ; echo $?
124

つまり遅くて打ち切られたコミットと本当に失敗したコミットが区別されない。 タイムアウトを使うならその値を判定不能に変えておくほうが正確である。

判定スクリプトをうまく書く方法

第一の規則は再現するテストでなければならないということだ。二分探索は各判定を真実として信じ、その半分をまるごと捨てる。判定が一度でも間違えば捨てられた半分の中に犯人がいることがあり、そのとき探索は誤りを知らせない。もっともらしいコミット一つを自信たっぷりに差し出す。

確かめるため、30%の確率で偽の失敗を出すテストを作って同じリポジトリで五回回した。正解は c13(f1fec3f) である。

--- 間欠的に失敗するテスト、5回
round 1  f1fec3f...  (正しい)
round 2  f1fec3f...  (正しい)
round 3  f1fec3f...  (正しい)
round 4  f1fec3f...  (正しい)
round 5  9dc5458...  (c08 - 誤り)

--- 決定的なテスト、3回
f1fec3f...  f1fec3f...  f1fec3f...

五回のうち一回がまったく別のコミットを指した。しかもその出力だけを見ても間違いだという印はどこにもない。間欠的な失敗が疑われるなら、判定を何度も繰り返して一度でも失敗したら不具合として扱うほうがよい。

第二は副作用の片づけだ。bisect はコミットを行き来するだけなので、追跡されないファイルはそのまま残る。古いビルド成果物が残っていると次のコミットの判定が汚染される。

$ echo "stale artifact" > build.out    # 追跡されない成果物
$ git bisect good                       # 別のコミットへ移動
$ cat build.out
stale artifact

実務で使える骨格はこうである。ビルド失敗は 125、タイムアウトも 125、それ以外はテスト結果をそのまま返す。

#!/bin/bash
# /tmp/judge.sh - リポジトリの外に置く
set -u

rm -rf ./build            # 前回の成果物を片づける
make clean >/dev/null 2>&1

if ! make >/dev/null 2>&1; then
  exit 125                # ビルド不可 - 判定せずスキップする
fi

timeout 60 ./run_one_test.sh
rc=$?
if [ "$rc" -eq 124 ]; then
  exit 125                # タイムアウトを不具合と誤解しないように
fi
exit "$rc"
  • スクリプトはリポジトリの外に置く。古いコミットにはそのファイルがない
  • 終了コードを明示的に扱う。最後の命令のコードが漏れ出ると意図と変わる
  • 成果物・キャッシュ・一時ファイルは毎回片づける。残ると次の判定が汚染される
  • 標準出力は減らしてよいが失敗理由の一行は残す。後からログだけを見て判断することになる
  • まず両端点で手で回してみる。 悪い端点で失敗し、良い端点で成功してこそ探索が成立する

bisect skip - 判定できないコミット

区間の中にビルドが壊れたコミットがあると判定できない。そういうときに git bisect skip を使えば、git が近くの別のコミットを代わりに選んでくれる。自動実行中ならスクリプトが 125 で終われば同じ意味になる。

ただしスキップしたコミットが答えの近くに固まると結果が一つに絞られない。不具合の前後4コミット(c11～c14)をすべてスキップさせて回した結果だ。

$ git bisect run bash /tmp/skipper.sh
...
There are only 'skip'ped commits left to test.
The first bad commit could be any of:
4d711a957c98da7528cf727b1db40974a3f9d199
f1fec3fe55804001fae21aaf7b18a6914483662a
71ed7e0a93f0b4029ba06d2d3cb95e019f141bb1
f9194e697f22b03a4aae2ef437dfc2497846eb63
d21c4cae515e9a7c0cfcacc38374c8b127273674
We cannot bisect more!
error: bisect run cannot continue any more

失敗と見るようなことではない。コミット18個が候補5個に減り、その五つは手で見られる量だ。使えない区間をあらかじめ知っているなら、範囲表記で一度に外すこともできる。

$ git bisect skip c10..c14
Bisecting: 8 revisions left to test after this (roughly 3 steps)

$ git bisect log | grep skip
git bisect skip 71ed7e0a...   # c14
git bisect skip f1fec3fe...   # c13
git bisect skip 4d711a95...   # c12
git bisect skip f9194e69...   # c11

ここで引っかかりやすい箇所 — c10..c14 は c10 の次から c14 までである。始点そのものは外れる。始点まで外すには git bisect skip c10 c10..c14 のように別に書いてやる。

bisect terms - good/bad が合わないとき

探すものが常にバグとは限らない。性能がよくなった時点や、ある機能が最初に入った時点を探すとき、「悪いコミット」という言い方は方向を混乱させる。このとき用語を変えられる。組み込みの別名 old/new があり、自分で名付けることもできる。

$ git bisect start --term-old=works --term-new=broken
status: waiting for both good and bad commits

$ git bisect broken f2ee06a
status: waiting for good commit(s), bad commit known

$ git bisect works d6e191c
Bisecting: 8 revisions left to test after this (roughly 3 steps)
[f9194e697f22b03a4aae2ef437dfc2497846eb63] c11: unrelated note 11

$ git bisect terms
Your current terms are works for the old state
and broken for the new state.

$ git bisect run bash ./check.sh
...
f1fec3fe55804001fae21aaf7b18a6914483662a is the first broken commit
bisect found first bad commit

結果の行が first broken commit に変わった。最後の要約行だけは依然として first bad commit であり、スクリプトで出力をパースするつもりなら知っておく価値のある違いだ。セッションの途中で今の用語が何か忘れたら git bisect terms で確認する。

  • バグを探すとき — 既定の good/bad で十分だ
  • 修正が入った時点を探すとき — old/new。「悪いコミット」と呼ばなくてよい
  • 性能のリグレッション — --term-old=fast --term-new=slow のように名付けておくと判定のとき混乱しない
  • 用語を変えてもアルゴリズムは同じだ。言い方だけが変わる

マージコミットが混じった履歴

既定の動作で bisect はマージコミットも、枝の中のコミットもすべて候補と見る。 不具合が機能ブランチの中で入り、そのブランチが後でマージされた履歴を作って確認した。

$ git log --oneline --graph --all
* 1f5a5ab m7: mainline work
* dc8284c m6: mainline work
*   36edf65 m5: merge feature
|\
| * fa26dce f4: feature polish
| * 9c3c4da f3: rewrite total.sh (THE BUG)
| * 13a2a60 f2: feature work
| * efe0833 f1: feature start
* | 0481885 m4: mainline work
|/
* 87b692a m3: mainline work
* 2606564 m2: mainline work
* 342914a m1: base

同じリポジトリを二つの方式で探索すると答えが違って出る。どちらも正しい答えであり、問うている質問が違う。

--- 既定: 枝の中まで入る
running 'bash' './check.sh'   (3回)
9c3c4da9ba2ed3715032525e3699eeae971e583e is the first bad commit
    f3: rewrite total.sh (THE BUG)

--- --first-parent: 本流だけを見る
$ git bisect start --first-parent HEAD 2606564
running 'bash' './check.sh'   (3回)
36edf65d0bd276c62c3fbae15ccab5a28196c39d is the first bad commit
Merge: 0481885 fa26dce
    m5: merge feature

既定の探索は不具合を書いたコミットである f3 を、--first-parent は不具合が本流に入った地点であるマージコミット m5 を指した。原因のコードを直すには前者が必要で、どのリリースから問題があったのかを知るには後者が必要である。

--first-parent が特に有用な場合がもう一つある。枝の途中のコミットがビルドすらできないリポジトリだ。開発中は壊れたままコミットし、マージの直前に整える方式なら、既定の探索はその壊れたコミットで詰まり続ける。本流だけを見れば各コミットはおおむね無事である。

犯人を見つけた後

コミット一つが出たなら半分は終わりだ。まずそのコミットが何を変えたのかを見る。

$ git show --stat f1fec3f
 total.sh | 8 ++++++--
 1 file changed, 6 insertions(+), 2 deletions(-)

$ git log -p -1 f1fec3f
diff --git a/total.sh b/total.sh
@@ -1,7 +1,11 @@
 #!/bin/bash
+# refactor: iterate by index
 sum=0
-for n in "$@"; do
-  sum=$(( sum + n ))
+i=1
+while [ "$i" -lt "$#" ]; do
+  eval "v=\${$i}"
+  sum=$(( sum + v ))
+  i=$(( i + 1 ))
 done
 echo "$sum"

ここでは一目で見える。-lt であるべきところが -le であるべきだったので、最後の引数が抜けた。ところが実務の犯人コミットはたいていこれほど小さくない。ファイルを数十個触ったコミットが出てきたらその中でまた絞り込む必要がある。bisect はコミット単位なので中には入れない。親から始めて、変更されたファイルを一つずつ載せながらテストする。

$ git show --stat HEAD
 alpha.conf | 1 +
 beta.conf  | 1 +
 delta.conf | 1 +
 gamma.conf | 2 +-
 4 files changed, 4 insertions(+), 1 deletion(-)

$ git checkout HEAD~1            # 親へ移動
$ for f in alpha.conf beta.conf delta.conf gamma.conf; do
>   git checkout main -- "$f"
>   bash ./check.sh; echo "  + $f -> $?"
> done
  + alpha.conf -> 0
  + beta.conf -> 0
  + delta.conf -> 0
  + gamma.conf -> 1        <-- ここで壊れる

ファイル一つに絞られ、そのファイルの差分だけを見ればよい。ファイルの中でも大きいなら、同じ要領を git checkout -p でハンク単位に適用すればよい。そして犯人コミットの上ですぐ作業したければ、先に見た git bisect reset refs/bisect/bad がその場所へ連れて行ってくれる。

git blame と何が違うのか

どちらも「いつこうなったのか」に答えるように見えるが問いが違う。blame はこの行を最後に触ったコミットを述べ、bisect は動作が変わった時点を述べる。たいていは同じ場所を指すが、分かれる場合がよくある。

不具合が b3 で入り、その後 b5 で同じファイルをインデントだけ直したリポジトリを作った。動作は b3 以降ずっと同じである。

$ git blame -- total.sh
^4ff6d88 ... 2) sum=0
75a65371 ... 3) i=1
75a65371 ... 4) while [ "$i" -lt "$#" ]; do
b44df25c ... 5)     eval "v=\${$i}"      <-- b5(書式だけ直したコミット)
b44df25c ... 6)     sum=$(( sum + v ))
b44df25c ... 7)     i=$(( i + 1 ))

$ git bisect run bash ./check.sh
75a65371be49176fd1a34827c369875cd78e8a1e is the first bad commit
    b3: switch to an index loop

blame は核心の三行を書式コミット b5 に返し、bisect はロジックを変えた b3 を指した。blame 側も空白無視(-w)や特定コミットの除外(--ignore-rev)で補正でき、実際に両オプションとも b3 に戻してくれる。この周辺のオプションはもっと使うべき Git 履歴コマンドのほうで別に扱った。

状況合う道具理由
この行がなぜこう書かれたのか知りたいgit blame行単位でコミットとメッセージをすぐくれる
動作がいつから変わったのか分からないgit bisectどの行が問題か知らなくてよい
問題の箇所が複数ファイルの組み合わせだgit bisectblame は一行ずつしか答えられない
この文字列がいつ消えたのか探すgit log -S内容の変化でコミットを絞り込む
犯人コミットが分かりその中を見たいgit show · log -pbisect の結果を受けて続けて使う

bisect が合わない場合

すべてのリグレッションに使えるわけではない。合わない条件がいくつかはっきりある。

  • コミット単位でビルドが通らないリポジトリ — スキップするコミットが多くなりすぎると候補が複数のまま終わる。--first-parent で本流だけを見るか、リリースタグ同士でまず絞ってからその区間だけ精密に探索する
  • 環境依存のバグ — ライブラリのバージョン・カーネル・コンテナイメージが変わって生じた問題はコードの履歴の中にない。このときはコードではなく環境を二分探索しなければならない
  • データ依存のバグ — 特定のレコードでしか再現しないなら、テストが再現可能になるようそのデータを先に固定する必要がある。本番データをそのまま使うと判定が揺れる
  • 徐々に悪くなった問題 — 性能が毎コミット1%ずつ悪くなったなら「変わった一つのコミット」が存在しない。閾値を決めて無理やり二分しても、その閾値が答えを決めるだけだ
  • すでに原因が分かっている問題 — スタックトレースがファイルと行を指しているなら blame のほうがずっと速い。bisect は手がかりがないときの道具である
  • 履歴がリベースで書き直された区間 — コミットが実際にその順序でビルドされたことがなければ、中間のコミットがそもそも動作しないことがある

Windows 利用者にだけ当てはまる落とし穴も一つある。bisect は refs/bisect/good-<40桁のハッシュ> という長い名前の参照を作る。リポジトリのパスが深いとこのパスが260文字の制限を超えてセッションが始まらない。パスの長さだけを変えながら確認した結果がこれである。

root=181  refpath=244  -> 正常
root=192  refpath=255  -> 正常
root=203  refpath=266  -> error: update_ref failed for ref
   'refs/bisect/good-27fe9984...': couldn't set
   'refs/bisect/good-27fe9984...'

メッセージがパスの問題だと言ってくれないので原因を見つけにくい。core.longpaths=true を有効にしてもこの参照には効かなかった。リポジトリを浅いパスへ移すのが最も確実だった。Linux・macOS では出ない問題である。

まとめ

まとめると実務で覚えることは多くない。悪いコミットと良いコミットを与え、判定をスクリプトに渡し、終わったら reset する。三行だ。

$ git bisect start <悪いコミット> <良いコミット>
$ git bisect run /tmp/judge.sh
$ git bisect reset

残りはすべて判定スクリプトの品質にかかっている。テストが再現しなければ答えが間違い、テストが遅ければその時間が10倍になり、終了コードを雑に流せばタイムアウトが不具合に化ける。探索アルゴリズムはすでに完成しており手を入れるところがない。人が用意する側は「動いた/動かなかった」を一度も間違えずに言ってくれるテスト一つだけである。

だからこの命令を身につける実際の順序は文法ではない。問題に出会ったらまず両端点を手で確認し、テストを最小再現に減らし、それから run をかける。この順序を守れば、たいていのリグレッションはコーヒー一杯のうちにコミット一つまで絞られる。

確認できなかったこと

  • すべての出力は Windows + Git Bash という一つの環境でのみ得た。Linux・macOS、そして dash・zsh のような他のシェルでメッセージの文言や終了コードの伝達が同じかは確認していない
  • 探索中断時に git bisect run 自体がシェルへ返す値は一定ではなかった。スクリプトが128で終われば128、129で終われば127が出たが、規則は突き止められなかった。判断は終了コードではなくメッセージで行うほうが安全だ
  • 126・127 の再確認の挙動は観測した出力だけで書いた。git のソースで該当の処理を直接確認してはいない
  • コミット1,000個の実測は合成リポジトリである。ファイルが数万個ある大規模リポジトリではチェックアウトのコストが大きくなり、git 自体の時間の比重が変わりうる
  • git bisect visualize は gitk が必要で実行しなかった。--no-checkout は動作を確認したがベアリポジトリでの動作は試していない
  • 長いパスの失敗で core.longpaths がなぜ効かないのかは原因を確認できなかった。 参照ファイルのパスとロックファイルのどちらが引っかかるのかも特定できなかった
