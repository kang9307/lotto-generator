为每个任务定制脚手架 - Claude Code 动态工作流深度解析

A Harness for Every Task - Inside Claude Code's Dynamic Workflows

2026年6月4日 科技

引言：「为每个任务定制脚手架」为何重要

过去两年，围绕 AI 编码工具的争论重心悄然移动。最初是「模型有多聪明」，接着是「能塞进多少上下文」。但进入 2026 年，从业者的话题转向了别处。同样使用一个模型，有的工具干净利落地完成工作，有的却在相同任务上反复打转。差别不在模型，而在包裹模型、使其真正完成工作的脚手架（harness），也就是执行骨架。

Anthropic 近期公开的 Claude Code 动态工作流（Dynamic Workflows）正是直指这一点。核心思想一句话即可概括：不要把一套固定流程强加给所有任务，而要为每个任务即时构建适配的脚手架。本文从我的视角分析这一思想改变了什么、它如何试图突破静态工作流的局限，以及开发现场应如何看待它。先说结论：动态工作流在扩大智能体自主性的同时，也开出了一张名为「可靠性」的新账单。如何支付这张账单，决定了落地的成败。

1. 脚手架是什么 - 模型与执行骨架的分离

先打好讨论的地基。提到「AI 智能体」，人们常想到一个庞大的语言模型，但真正完成工作的系统分为两层：一层是模型，另一层是包裹它的脚手架。

模型近似一个输入文本、输出文本的函数。它本身既不能读文件，也不能跑测试，更不能验证结果。承担这些工作的是脚手架。脚手架是回答下列问题的代码与流程的集合。

  • 授予哪些工具：在读文件、执行 shell、搜索、测试运行器之中，哪些允许用于本任务。
  • 如何验证结果：模型给出的代码是否真能编译、能否通过测试，由谁、何时确认。
  • 失败后怎么办：验证失败时，是重试、换路径，还是交给人。

这个区分之所以重要，是因为即便模型质量相同，脚手架的设计也会让产出可靠性大相径庭。同样的发动机装在不同的车身上，就成了完全不同的车。动态工作流正是宣告：为每个任务重新打造这副「车身」。

2. 静态工作流的局限 - 分支地狱与脆弱

要理解动态工作流，先要看清它想克服什么，那就是静态工作流（static workflow）。静态工作流由人预先固定从第一步到第 N 步的流程，例如「生成代码 → 跑测试 → 失败就修一次 → 开 PR」。

这种方式可预测且安全。流程既定，就知道会发生什么，验证与审计也容易。问题在于，现实中的任务并不那么规整。有的任务根本没有测试，有的任务像数据迁移一样一旦执行就难以回退，有的任务根据外部 API 响应而分岔。

静态工作流的敌人不是复杂，而是意外任务进来时分支与异常处理的爆炸式增长，以及这些分支相互纠缠所造就的脆弱。

长期运维过静态工作流的团队都懂这种「分支地狱」。每来一个新情形就多一个 if，工作流定义膨胀到数百行，到某个时刻无人能理解全貌。动态工作流试图把这种不断累积的复杂，用智能体的即时判断而非工作流定义来吸收。

3. 动态工作流的运作原理 - 看任务、搭脚手架

那么动态工作流具体如何运转？核心是「不预先确定流程，而是看过任务后再组装适配的执行骨架」。简化后可这样解读：

静态工作流： [固定的 1→2→3→4 步骤]  → 把所有任务塞进同一模具
   │
   ▼
动态工作流： 观察任务 → 选择所需工具 → 决定验证方式
            → 执行 → 验证 → （失败时）重构路径 → 迭代

这里的决定性差异在于「决定验证方式」和「重构路径」被内置于流程之中。静态工作流里验证方法是写死的，动态工作流里智能体则根据任务性质当场决定：「这个用测试验证」「这个用类型检查验证」「这个需要人确认」。

这种结构的优点很清楚：能在同一代码库内灵活处理大量非标准化的任务。但同样的原因也带来明显缺点：每次路径都不同，事后复现并验证「这个工具在哪个任务上做了什么」比静态工作流更难。获得灵活性的代价，是让出部分可复现性。

4. 自主性与可靠性的平衡 - 核心张力

围绕动态工作流的一切讨论最终都汇聚于一个张力：自主性（autonomy）与可靠性（reliability）的相悖。把越多判断交给智能体，它能处理的任务就越多样，但代价是「越来越难以预测它会做什么」。

这个张力并不新鲜，是自动化史上反复出现的主题。飞机自动驾驶、自动驾驶汽车、工业控制都面对过同一问题：是让系统更聪明地自行判断，还是约束其行为以保持可预测？答案永远是「取决于场景」。风险越大的领域越收窄自主性，风险越小的领域越放宽。

动态工作流也应遵循同一原理。好的动态工作流不是「把一切都交给智能体」，而是根据任务风险动态调节自主性的范围：在能即时被测试验证的任务上给予宽自主性，在难以回退的任务上给予窄自主性并要求人工审批。缺了这种平衡感的动态工作流，不过是「失控的自动化」。这一主题与探讨智能体自主性与安全张力的另一篇文章AI 之后不再是软件 - harness 时代深度相关。

5. 验证循环 - 动态工作流的心脏

动态工作流中最被低估的要素是验证循环（verification loop）。人们盯着「智能体自己选工具」那部分，但真正创造可靠性的不是工具选择，而是验证其结果的循环。

验证循环的质量取决于「验证信号有多快、多准」。好的验证信号举例如下。

验证信号 特性 适合的任务
测试通过/失败 快速明确的二值信号 逻辑变更、缺陷修复
类型检查/编译 即时捕捉结构性错误 重构、签名变更
Lint/格式化 检测风格与约定违规 代码整理、样板代码
人工评审 慢但需要判断的信号 设计决策、难以回退的变更

动态工作流的威力，在于智能体能自行挑选适配任务性质的验证信号。简单缺陷修复只需测试即可，但数据库 schema 变更则需测试与人工评审并行。在验证信号匮乏的任务上——比如几乎无法自动验证的 UI 微调——动态工作流的优势会急剧缩小。无法验证的任务难以自动化这条古老真理，在此同样成立。

这里还有一个常被忽视的细节：验证信号不仅要快，还要「指向明确」。一个只告诉你「测试失败」却不说明哪条断言、哪个文件出错的信号，对智能体的迭代帮助有限；而一个能精确定位失败位置、给出预期值与实际值差异的信号，才能让智能体在下一轮迭代中真正收敛。换句话说，验证循环的价值不只在于「能否发现错误」，更在于「发现错误后能否引导出正确的下一步」。在为动态工作流准备测试与检查时，与其堆砌大量粗糙的断言，不如精心设计少量定位精准、信息丰富的验证点，这对智能体迭代效率的提升往往更显著。

6. 动态工作流适合与不适合的任务

并非所有任务都适合动态工作流。分辨何处适合、何处不适合的眼力，正是落地的核心。

6.1 适合的任务

验证信号快速明确、即便失败也易于回退的任务，很适合动态工作流。测试完备代码库中的缺陷修复、批量整理 lint 错误、重复性样板代码生成、规格清晰的单元功能实现，都属此类。在这类任务上，智能体可尝试多种路径，验证会即时过滤错误尝试，因此放宽自主性也安全。

6.2 不适合的任务

反之，验证缓慢或不可能、失败代价巨大的任务，动态工作流的风险随之增大。生产数据库迁移、与支付/安全直接相关的逻辑、没有明确正解的架构决策皆是如此。在这些领域，即便使用动态工作流，也应收窄自主性并强制人工审批。多智能体环境下放宽自主性所产生的协调成本，在另一篇文章多智能体的编排税中有更深入的探讨。

7. 与 Claude Code 设置的衔接 - 自主性旋钮

动态工作流不是抽象概念，而是与 Claude Code 的具体设置咬合运转。权限模式、允许/禁止工具清单、自动执行边界等设置，扮演着「自主性旋钮」的角色。动态工作流再灵活，智能体能触及的工具边界仍由这些设置决定。

实务上重要的一点是：打开动态工作流并不意味着放弃控制。恰恰相反，要安全地使用它，反而需要比平时更清晰地设计权限边界。例如把文件写入限制在特定目录，对 shell 命令屏蔽危险模式，外部网络访问只在明确允许时开放。这些设置细节在另一篇文章Claude Code 隐藏设置完全整理中有具体说明，建议在正式引入动态工作流前一并查阅。

核心原则是：放宽自主性之前，先收窄边界。动态工作流给予智能体「做什么」的自由，但「能做到哪一步」的栅栏须由人来设计。栅栏越牢固，就越能放心地放宽自主性。

8. 对开发者的实务意义

那么这一变化对开发者的日常意味着什么？我预见三点变化。

第一，重心从编排工作流转向设计验证。过去「精心编排给 AI 的步骤」是核心技能。在动态工作流时代，步骤由智能体组装，人的角色转向设计「用什么来验证智能体的结果」。好的测试、清晰的类型、快速的 CI，成为前所未有的重要资产。

第二，可观测性成为生产力的前提。动态工作流每次走不同路径，因此必须能事后追踪「智能体做了什么」。若不留下执行日志、工具调用记录、变更历史，动态工作流就会变成无法控制的黑箱。留日志即是信任的基础设施。

第三，开发者的判断力更显珍贵。智能体越是自主处理多样任务，「哪些任务交出去、哪些自己做」「智能体结果中哪些该怀疑」的眼力就越成为核心能力。悖论在于，自动化越多，人的判断不是变得不重要，而是更重要。

9. 落地开发现场 - 现实启示

把这一趋势代入实际开发现场，有几点现实启示。

  • 测试文化是前提：动态工作流的效果与验证信号的质量成正比。在测试匮乏的遗留代码库中，优势会大幅缩水。悖论是，要享受 AI 自动化的收益，必须先投资测试。
  • 合规领域窄自主性：在金融、医疗、公共这类变更追踪与审计严格的领域，即便使用动态工作流，也应收窄自主性，对每个动作都留下日志与审批。「能否证明做了什么」是准入条件。
  • 小团队的杠杆：对人手不足的团队而言，动态工作流是减轻重复劳作的杠杆。但首要选择不是炫目的自动化，而是运行测试、修复 lint 这类低风险、易验证的任务。
  • 母语上下文：在混杂母语注释、工单、文档的代码库里，智能体能否妥善处理上下文，仍是需要验证的领域。与其直接信赖以英语为中心的基准分数，不如先在自己的代码库上用小任务验证更稳妥。

10. 批判性分析 - 动态工作流的阴影

为求平衡，明确指出另一面。动态工作流并非只有玫瑰色。

  • 可复现性减弱：每次路径不同，难以保证同样输入得到同样结果，调试与审计比静态工作流更棘手。
  • 自信满满的错误答案：智能体可能煞有介事地走错路径。在验证信号薄弱的任务上，错误结果有蒙混通过验证的风险。
  • 自动化悖论：智能体越多地自行处理，人就越远离系统，真正需要介入时反而失去上下文。航空与核电领域熟知的风险，也适用于代码。
  • 成本不透明：动态探索路径会使每个任务的 token 消耗与执行时间差异巨大，预算预测变难。

这些阴影的共同解法相同：从一开始就把可观测性、验证关卡、权限边界、回滚路径刻进设计。越是强力使用动态工作流，这层安全护栏的重要性就越发上升。

值得补充的是「影子模式」这一从机器学习部署借来的实践，对动态工作流同样适用。在允许某类智能体动作真正触碰生产环境之前，先让它在影子模式下运行：只记录它「打算做什么」，并与人类实际所做的对照，而不实际执行。几周之后，你就握有一份具体数据——智能体与人类一致的频率、分歧之处，以及这些分歧若执行会有益还是有害。只有到那时，才把一类范围狭窄、被充分理解的动作从影子提升到真实执行。这把「我们是否信任智能体」这个含糊的问题，转化为可度量的问题，也给持怀疑态度的工程师提供证据而非感觉。多数落地失败并非技术原因，而是组织原因：要么从最炫的全自动修复入手，因一次糟糕的自动动作而毁掉多年的信任；要么相反，无休止地试点，却因无人定义晋级标准而始终无法进入生产。上文那条刻意「无聊」的渐进路径，正是为了同时避开这两个极端。

11. 未来展望 - 脚手架成为差异化之轴

从大图景看，动态工作流是一个信号，表明 AI 编码工具竞争的重心正从「模型」移向「脚手架」。模型性能整体拉平后，谁能把同一模型包裹得更好——给哪些工具、如何验证、如何从失败中恢复——就成了差异化之轴。

我预计未来一两年这一趋势会分成两条路。一条把自主性推得更远，走向「智能体全包」；另一条刻意约束自主性，走向「可预测、可验证」。有趣的是，最终存活的工具，很可能是能根据任务风险在二者间动态往返的工具。也就是说，不把「自主性的量」写死、而按任务调节它的能力本身，将成为下一轮竞争的核心。动态工作流正是这种能力的雏形。

12. 结论 + 今天就能落地的三件事

「为每个任务定制脚手架」不是 AI 编码的终点，而是方向的转变。动态工作流把静态工作流的分支地狱吸收进智能体的即时判断，按每个任务的性质重新组装工具与验证。然而所有这些灵活性，只有建立在验证循环与权限边界这层安全护栏之上、并在人的监督之下运转时，才会创造价值。一句话概括：动态工作流在扩大自主性的同时开出一张可靠性账单，唯有以设计支付这张账单的团队才能享受收益。

以今天就能落地的三件事收尾。

  1. 先把验证就位。打开动态工作流之前，先备好快速明确的验证信号——测试、类型检查、CI。验证薄弱时，自主性会变成风险。
  2. 先交出低风险任务。从测试完备代码中的缺陷修复、lint 整理这类易回退的任务起步，待信任积累后再扩大范围。切勿第一天就交出生产变更。
  3. 留下执行日志。动态工作流每次路径不同，必须能追踪智能体做了什么。可观测性不是可选项，而是信任的前提。
