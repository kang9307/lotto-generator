Some Numbers Compare True with is and Some Do Not - Integer Caching and Identity Comparison

Why the test passes and only production takes the wrong branch - an optimisation is not a specification

2026-08-01 Dev & Infra

Introduction: the test passed and only production took the wrong branch

There was a function that checked whether a status code equalled a particular value. Every unit test passed. Then it shipped, and that branch never fired once. Reading the code again reveals nothing wrong with the logic. Log the value and it is plainly the number you expected. And yet the condition is false.

The cause was a single comparison operator. Where == belonged, is had been written. What makes this mistake dangerous is not the mistake itself. It is that the tests passed. The test wrote the number straight into the source. Production received the same number through a socket and a string parser. Same number, different outcome.

The argument of this article is not 「never use is」. is is a perfectly good operator with places where it is required. The precise argument is this.

  • is asks whether two names point at the same object. It does not ask whether two values are equal. Those are different questions
  • Whether equal values are the same object is decided by an interpreter optimisation. Reusing frequently needed objects is an implementation choice made for speed, not a promise the language made
  • An optimisation is not a specification, so you may not rely on its result. Change the implementation and the answer changes
  • Getting a lucky true on small values is the dangerous part. A lucky right answer is exactly what makes the test pass

That last point is the whole story. A bug that is always wrong gets found immediately. A bug that is right sometimes survives all the way to production. What follows is a record of finding where 「sometimes」 begins, by running it.

Environment. Every output below was produced by actually running the code on Windows 10 Pro (10.0.19045). The interpreter is CPython 3.13.3, build tags/v3.13.3:6280bb5, Apr 8 2025, 14:47:33 [MSC v.1943 64 bit (AMD64)]. Every script was saved to a file and executed from there.

The cache range numbers in this article are not a specification. Any claim about 「what range gets shared」 is a result measured on this interpreter, at this version. Other implementations and other versions may differ. This article is not asking you to memorise the numbers. It is showing why code that depends on such numbers is dangerous.

Out of scope. When a function default argument is evaluated is covered in when Python evaluates default arguments. Different topic, but the lesson carries over: do not build on implementation details.

This has to be said plainly. The 「-5 to 256」 above is a measurement, not a rule. The Python language reference is explicit here. It states that after a = 1; b = 1 the two names may or may not refer to the same object, that this depends on the implementation and should not be relied upon. The same document also says that evaluating literals of equal value may obtain the same object or a different object with the same value.

So the takeaway is not two numbers. It is the fact that there exists a range where you get lucky. That luck is what turns the test green.

Next, confirm what is actually inspects. The documentation defines is as testing an object identity, determined using the id() function. So I printed those identities.

The address digits reveal something interesting. Cached values cluster in a region starting 140735…, while values outside the cache live in a different region starting 1406…. The first exists from interpreter start-up; the second is allocated on demand.

But the last line of 2-2 hides a trap. Building the value 777 five times produced only three distinct addresses. On two of the five, a new object moved into the slot a dead one had left. Here it is more starkly.

--- 2-3. id reuse makes id() alone untrustworthy ---
id of a dead 999999 : 1406444443312
id of a fresh 888888: 1406444443312
addresses equal     : True  <- equal ids, different values

--- 2-4. keeping a reference changes the answer ---
both alive at once  : id equal = False  a is b = False

--- 2-6. sys.getrefcount on a cached object ---
refcount of 1  : 4294967295
refcount of 777: 1
  a cached object is referenced from everywhere in the process
  • An object holding 999999 and one holding 888888 reported the same address. The second reused the slot the first had vacated. The documentation states the same thing: id() is unique only during an object lifetime, and two objects with non-overlapping lifetimes may share the same value
  • So code that stores an id() value and compares it later is wrong in principle. The moment you store it, you lose any guarantee that the object is still alive
  • In 2-4 keeping both objects alive at once split the addresses. In other words, the same code answers differently depending on whether a reference is held
  • The reference counts stand out. The cached 1 reports a count in the four-billion range. Permanently reused objects on this interpreter are marked so that they are never collected. The uncached 777 reported 1

Then an unexpected result appeared. A 257, well outside the cache range, compared true when built from an arithmetic expression.

200 + 57 = 257  300 - 43 = 257  p is q = True
  the second pair is OUTSIDE the cache yet still True.
  the cache is not the only thing that makes 'is' true - see experiment 3.
  compare with values built at run time:
  make(257) is make(257) = False

The same 257: true when written as an expression, false when built at run time. The cache alone cannot explain that. There is a second cause.

3. Same code, different answers depending on how you run it

The second cause is how the compiler handles constants. When the same literal appears more than once during compilation, the compiler folds it into a single object stored in the code object constant table. An expression like 200 + 57 is also computed at compile time and becomes a constant. At run time the code merely fetches that constant, so both names end up pointing at one object.

--- 3-1. module level, one file, two statements ---
a = 257 ; b = 257   ->  a is b = True

--- 3-2. inside a function, same code object ---
same function body  -> True
two function bodies -> True

--- 3-3. what the compiler stored ---
co_consts of f() : (None, 257)
g1 const id      : 140735026668016
g2 const id      : 140735026668016
same object      : True

bytecode of f():
 13           RESUME                   0

 14           LOAD_CONST               1 (257)
              STORE_FAST               0 (a)

 15           LOAD_CONST               1 (257)
              STORE_FAST               1 (b)

 16           LOAD_FAST_LOAD_FAST      1 (a, b)
              IS_OP                    0
              RETURN_VALUE

The bytecode tells the whole story. Both lines are LOAD_CONST 1. Reading the same slot of the constant table twice can only produce the same object. Even the constants of two separate functions turned out to be one object, because constants are shared across a module while it compiles.

So what happens when the compilation unit is split up?

--- 3-4. exec: one string vs two strings ---
exec, single string  -> True
exec, three strings  -> False

--- 3-5. compile() separately then exec ---
separate code objects -> False
const in c1 : [257]
const in c2 : [257]
same object : False

--- 3-6. a real REPL, statement by statement (code module) ---
REPL, line by line  -> False
REPL, small number -> True

The results diverge completely. In 3-5 both code objects hold a constant 257, and those two are not the same object. 3-6 matters most in practice. In an interactive interpreter each line is its own compilation unit, so constants are not shared and the answer is false.

I also checked across process boundaries.

--- 3-7. child process: python -c, script file, piped stdin, -i ---
python -c            -> True
script file          -> True
piped stdin (python) -> True
piped stdin (-i)     -> False
  stderr tail of -i  : >>> >>> >>> >>>

--- 3-8. the same test written so the compiler cannot help ---
module level, run-time values -> make(257) is make(257) = False
module level, literal values  -> 257 is 257 (via consts)  = True

Collecting the results for the same two lines gives this table. It is the second most important table in this article.

How it rana is b after a = 257; b = 257Why

The practical consequence is large. What you confirm in a REPL can differ from what a script does. If the REPL gave false and you concluded 「right, must not use this」, fine. But if a script gave true and you concluded 「works」, that code collapses quietly the moment the value changes origin.

4. Strings behave the same way

This is not only about integers. Strings are shared under the same principle, though the conditions differ slightly.

--- 4-1. literals in one compilation unit ---
s1 = "total" ; s2 = "total"      -> s1 is s2 = True
with a space in it               -> t1 is t2 = True

--- 4-2. built at run time ---
"to" + "tal"        is base : True   == base : True
parts[0] + parts[1] is base : False   == base : True
"".join(parts)      is base : False   == base : True
percent format      is base : False   == base : True
f-string            is base : False   == base : True

--- 4-3. length matters for run-time strings ---
built            is-literal   len
----------------------------------------
''               True         0
'x'              True         1
'xx'             False        2
'xxx'            False        3
'xxxx'           False        4
'xxxxx'          False        5

The gap between the first and second rows of 4-2 is the point. Adding two literals is folded into a constant at compile time, while adding two pieces pulled out of a list creates a new object at run time. Identical values, and only the identity check splits.

4-3 shows only the empty string and single characters are shared. That too is a pre-created object optimisation. Now split the compilation unit and look again.

--- 4-4. identifier-shaped vs not, from a REPL (separate units) ---
  identifier-shaped     -> True
  with a space          -> False
  with a hyphen         -> False
  empty string          -> True
  single ascii char     -> True

--- 4-5. sys.intern forces sharing ---
run-time built, two copies       : False
after sys.intern on both         : True
interned is the literal          : True

--- 4-6. slicing produces new objects ---
name[:] is name       : True    (full slice can return self)
name[0:7] is name     : True
name[1:] is "ser_id"  : False
name[1:] == "ser_id"  : True

4-4 is what 「identifier-like strings get interned」 actually means. Even across separate compilation units user_id came out true, and it turned false the moment a space or a hyphen appeared. Only strings shaped like a valid name are shared automatically.

  • So identifier-shaped strings such as key names have a high chance of making is accidentally right. That is exactly what hides this bug
  • User names, sentences and hyphenated codes are almost always false. The same code behaves differently depending on the data
  • To force sharing you must call the interning function explicitly, which flipped 4-5 to true. But that exists to save memory, not as a comparison tool
  • The first line of 4-6 is another trap. A full slice can return the same object. The guess that 「a slice is always a new object」 is also wrong

The last piece is where this bites in practice: the moment a value arrives from outside.

--- 4-7. where this bites: values that came from outside ---
json value  is literal : False   == literal : True
csv  value  is literal : False   == literal : True

--- 4-8. the same for other immutable types ---
() is ()            : True
tuple() is tuple()  : True
(1,2) built vs lit  : False
0.0 is 0.0 (consts) : True
float('0.0') twice  : False

The same string, and a value pulled out of a serialisation format is a different object from the literal. Configuration files, API responses, tabular files and user input all behave this way. That is precisely the scenario from the introduction: the test wrote the value into the source, production received it from outside.

5. == and is ask different questions

Time to consolidate. The two operators are not substitutes. They are different questions.

--- 5-1. the two questions are different ---
a == b : True    same value
a is b : False   different objects
a is c : True    same object
after b.append(4)  a = [1, 2, 3]  b = [1, 2, 3, 4]
after c.append(9)  a = [1, 2, 3, 9]  c = [1, 2, 3, 9]   <- c IS a

--- 5-2. equal but not identical, identical but not equal ---
x = float('nan')
  x is x : True    same object
  x == x : False   a value that is not equal to itself
  x in y : True    'in' tries 'is' first, then '=='
  any(v == x for v in y) : False

--- 5-3. __eq__ can say anything; 'is' cannot be overridden ---
p == q : True   __eq__ decides
p is q : False  identity is not overridable
p == 5 : True
p is p : True

--- 5-4. objects that define no __eq__ fall back to identity ---
m == n : False   default __eq__ IS identity
m is n : False

5-2 proves the two questions are fully independent. A value exists that is the same object yet not equal to itself. The membership operator checks identity first and reports true, while a pure value comparison reports false. If they were the same question, that could not happen.

5-4 explains why this bug surfaces late. A class that does not define equality falls back to identity comparison by default. For such classes the two operators always agree. The day someone adds an equality method to that class, an identity comparison that had worked for years suddenly becomes wrong.

OperatorQuestion askedImplemented asCan a class change itWhere to use it
a == bSame valueThe class equality methodYesAll value comparison
a is bSame objectIdentity comparisonNoSingletons, sentinels, sharing checks
a != bDifferent valueThe class inequality methodYesAll value comparison
a is not bDifferent objectIdentity comparisonNoSingletons, sentinels

「No」 is the one strength of is. And there really are places that need it.

--- 5-5. when 'is' is the right tool: singletons ---
None is None            : True
Ellipsis is Ellipsis    : True
NotImplemented is itself: True
  fetch('a' ) -> None
  fetch('b' ) -> 0
  fetch('c' ) -> ''
  fetch('zz') -> 'MISS'
  note 'a' holds None and 'b' holds 0: a truthiness check would lose both

--- 5-6. the falsy trap that 'is SENTINEL' avoids ---
  bad('a' )   -> 'MISS'
  bad('b' )   -> 'MISS'
  bad('c' )   -> 'MISS'
  bad('zz')   -> 'MISS'
  three stored values were reported as missing

Put the two blocks side by side. Against the same store, one answered exactly and the other lost three entries. When a stored value is absent, or zero, or an empty string, a check that only looks at truthiness declares all of them 「missing」. What you need there is a marker object that exists exactly once, and the only way to test for it is is.

6. Why is None is safe and is True is not

The rule 「use the identity check for None」 is widely known. I confirmed the reason by running it.

--- 6-1. None is a singleton: try to make a second one ---
type(None)          : <class 'NoneType'>
type(None)() worked : True  <- it returns the same object
copy.copy(None) is None      : True
copy.deepcopy(None) is None  : True
pickle round trip is None    : True
id(None) stable in a loop    : True

--- 6-2. None across a process boundary ---
id(None) here      : 140735026668016
id(None) in child  : 140735026668016

--- 6-3. why 'is None' and not '== None' ---
w == None : True   <- a class talked its way into looking like None
w is None : False  <- identity cannot be talked into anything

a column-style 'missing' object:
  m == None : True
  m is None : False
  if m == None: would take the branch; if m is None: would not
  • There is no way to make a second one. Calling the type directly returned the original. Copy, deep copy and a serialisation round trip all returned that same object
  • So x is None is always exact, completely independent of interpreter optimisation. Its character is entirely different from the cache story in section 1
  • 6-3 is the reason not to use the equality operator. A class that redefines equality makes a non-None object claim to equal None. Libraries handling tabular data really do ship such 「missing value」 objects
  • 6-2 is interesting but easy to misread. Parent and child reported the same address because this object has a fixed slot inside the executable. That does not mean comparing id() values across processes is acceptable. As section 2 showed, ordinary object addresses get reused

If the boolean values are also singletons, is is True fine too? Syntactically safe, but semantically wrong.

--- 6-4. True is a singleton too, but the comparison is still wrong ---
bool(1) is True     : True
True is True        : True

value    type           == True    is True    if value:
--------------------------------------------------------
1        int            True       False      True
1.0      float          True       False      True
True     bool           True       True       True
'1'      str            False      False      True
[1]      list           False      False      True

--- 6-5. a function returning 1 instead of True ---
legacy_flag    -> 1      if v:True    v == True:True    v is True:False
modern_flag    -> True   if v:True    v == True:True    v is True:True

Look at the last column. All five values are truthy. Yet only one row passes the identity check. Asking 「is this truthy」 with is True therefore declares most truthy values false.

6-5 is the field scenario. When an old function that returned 1 is changed to return the boolean, or the reverse, the truth test and the equality test stay put and only the identity branch flips. The change log says 「tidied up to use booleans」, and nobody connects it to the outage.

Now reproduce the introduction exactly.

--- 6-6. 'is 0' and friends: run-time values break the spell ---
  value 0       v == 0:True   v is zero:True   | v == 257:False  v is big:False
  value 1       v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 256     v == 0:False  v is zero:False  | v == 257:False  v is big:False
  value 257     v == 0:False  v is zero:False  | v == 257:True   v is big:False
  value 1000    v == 0:False  v is zero:False  | v == 257:False  v is big:False

--- 6-7. the dangerous shape: a test that passes for the wrong reason ---
status_code_ok(200)          : True   <- literal 200, same const pool
status_code_ok(int('200'))   : True   <- 200 is inside the cache
status_code_ok(199 + 1)      : True
status_code_ok2(500)         : True   <- literal, const pool again
status_code_ok2(int('500'))  : False   <- outside the cache: FALSE
status_code_ok2(499 + 1)     : True

6-7 is this entire article in one block. The function written as code is 200 passed all three ways of calling it, because 200 falls inside the cache range. The identically written code is 500 function returned false as soon as the value came from a string.

This is the heart of it. Both functions made exactly the same mistake. One passes and one fails. The only difference is whether the status code number happens to fall inside the cache range.

And here is why that is dangerous. Tests written against 200-range success codes all come out green. If the error-handling paths are untested, a bug that only breaks on 400 and 500 codes ships. Failure paths are exactly where coverage is thinnest, so this bug hides in the single hardest place to find it.

7. Booleans are integers - dictionary keys collide

The relationship between booleans and integers looks like a separate topic, but the root is the same: what counts as the same thing.

--- 7-1. bool is a subclass of int ---
issubclass(bool, int) : True
isinstance(True, int) : True
int(True), int(False) : 1 0
True + True           : 2
sum([True, True, False]): 2

--- 7-2. equality and hashing ---
expression       value    hash
--------------------------------------
True             True     1
1                1        1
1.0              1.0      1
False            False    0
0                0        0
0.0              0.0      0

True == 1     : True
True is 1     : False
False == 0    : True
hash(True) == hash(1) : True

--- 7-3. dict keys collapse ---
d after three assignments : {1: 'float one'}
len(d)                    : 1
type of the surviving key : int
insert True first         : {True: 'int one'}  key type: bool

The documentation defines the boolean class as a subclass of int that cannot be subclassed further, with only two instances. 7-2 is the consequence. Equal values and equal hashes, so they occupy the same dictionary slot.

The last two lines of 7-3 show the exact behaviour. The first key inserted survives and only the value is overwritten. Insert the integer first and the key stays an integer; insert the boolean first and it stays a boolean. In other words, the surviving key type depends on insertion order.

--- 7-4. the same collapse in sets and counters ---
{1, True, 1.0}            : {1}
len({0, False})           : 1
Counter([1, True, 1, True]): Counter({1: 4})

--- 7-5. a config table that quietly loses a row ---
declared 5 entries, got   : 3 -> {0: 'disabled', 1: 'enabled', 2: 'verbose'}
LEVELS[False]             : disabled
LEVELS[0]                 : disabled  <- same slot

--- 7-6. list membership and index ---
True in row               : True
row.index(True)           : 1
False in row              : True
row.count(1)              : 1
[True, 1].count(1)        : 2

7-5 is what the accident looks like in the field. Five lines written, three surviving. No error, no warning. A code review sees all five lines sitting there, which makes it hard to notice. The moment a configuration table mixes 0 and False, this happens.

The counting result in 7-6 also deserves attention. If a list holds both the boolean and the integer 1, the count of 1 comes back as 2. Aggregation logic breaks right there.

--- 7-7. so how do you actually distinguish them? ---
  True   -> is-check:bool    type() is bool:True    isinstance int:True
  False  -> is-check:bool    type() is bool:True    isinstance int:True
  1      -> is-check:int     type() is bool:False   isinstance int:True
  0      -> is-check:int     type() is bool:False   isinstance int:True
  1.0    -> is-check:float   type() is bool:False   isinstance int:False

--- 7-8. JSON round trip keeps them apart, dict keys do not ---
json.dumps({'a': True, 'b': 1}) : {"a": true, "b": 1}
json.dumps({True: 'x', 1: 'y'}) : {"true": "y"}

7-7 is the fix. You have to check whether the type itself is the boolean type. An int check lets booleans through. Write your 「numbers only」 validation that way and booleans flow straight in.

The second line of 7-8 shows the result. Two entries were written and only one survives in the serialised output, with the key turned into the string true. The serialiser did nothing wrong. The dictionary had already collapsed before it ever looked.

--- 8-3. what the built-in warning does NOT catch ---
    a is b           -> warned: False
    flag is True     -> warned: False
    v is SMALL       -> warned: False
    code is CONST    -> warned: False
    x is ()          -> warned: True

Four of five passed silently. Missing the comparison against a name bound to a constant hurts most, because production code tends to use constant names rather than bare numbers. The last line did warn, since an empty tuple counts as a literal.

8.2 Stage two - walk the syntax tree yourself

Covering the blind spot means reading the code structurally. I built a checker on the standard library syntax tree module. The core is this.

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

class Checker(ast.NodeVisitor):
    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None                       # singleton, fine
            return "LITERAL", "literal comparison"
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "display literal"
        if isinstance(node, ast.BinOp):
            return "EXPR", "arithmetic result"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", "conversion result"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None                       # singleton name, fine
            if node.id in self.consts:
                return "CONSTNAME", "name bound to a literal"
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON", "is True/False"))
        self.generic_visit(node)

The key move is collecting module-level NAME = literal bindings first, then checking both sides of every comparison against that list. Run against the sample file:

9. Team rules and a checklist

Tools only find what is already in the code. Keeping new instances out requires a rule. The list below contains only what follows directly from the runs above.

9.1 Rules

  1. is is for singletons only. None, an explicitly created marker object, an enumeration member. Seeing is outside those three should prompt a question in review
  2. Value comparison uses == without exception. Integers, strings, status codes, configuration values. 「It is a small number, so it is fine」 is not a justification
  3. Do not use a truth test to detect absence. As 5-6 showed, zero and the empty string disappear along with it. Create a marker object and check it with is
  4. Use is True only when asking 「is this exactly that object」. If that is the intent, leave a comment saying why. An uncommented is True should be treated as a mistake
  5. Type checks look at the type directly. An int check lets booleans through (7-7)
  6. Never mix 0 with False, or 1 with True, as dictionary or set keys. Lines vanish silently, as in 7-5
  7. Tests must not feed literals only. This is the most important one. Run the same checks with values that went through string parsing, a serialisation round trip, and real I/O. 6-7 is the reason
  8. Never store an id() value or compare it across processes. As 2-3 showed, addresses get reused

9.2 Checklist

  • A step that promotes the interpreter warning to an error is in the build
  • The syntax tree checker has been run across the whole repository and the findings reviewed
  • Every == None has been replaced with the identity check
  • Every remaining is True and is False carries a comment explaining why
  • No comparison uses is against a constant name (the shape the interpreter warning misses)
  • Absence is detected with a marker object, and that object does not leak out of its module
  • Every integer validation point has been judged on whether a boolean passing is acceptable
  • No dictionary or set key set contains both 0 and the false value
  • Aggregation and counting logic never receives booleans mixed with integers
  • Tests exercise the same branch with values that arrived from outside
  • Failure code paths are tested, not only success codes (the trap in 6-7 lives there)
  • No comment or document cites the cache range as justification
  • No script behaviour is justified by a result observed interactively
  • Only deliberate singletons such as enumerations and marker objects still use is

10. What this article did not verify

Writing up unverified things as verified misleads the next reader. The limits, stated plainly.

  • Other implementations. Every measurement came from one interpreter implementation, one version, one operating system. No claim is made that another implementation gives the same result. If anything, the argument of this article is that it may not
  • Other versions. Even the same implementation may change its optimisations between versions. The reference-count behaviour in 2-6 is one such area
  • How static checkers actually behave. As 8-1 stated, none were installed here. That is why no rule identifiers are quoted
  • Multi-threaded and multi-interpreter environments. Object sharing may work differently there, and this article did not cover it
  • Performance impact. The identity check is faster than an equality call, but the difference was not measured. And there is no value in producing a wrong answer quickly
  • Identity comparison in other languages. Similar traps are said to exist, but nothing here was run to confirm it

The unverified items share a trait, though. They are all questions about what the implementation does. And the conclusion of this article does not depend on knowing that. Whatever the implementation does, use == for value comparison. That is the only way to make the implementation something you never have to know.

Conclusion: a passing test is the dangerous one

To summarise: is asks whether two names point at the same object. Use it for value comparison and whether the answer is right is decided by an interpreter optimisation. The shared range measured on this interpreter ran from -5 to 256, and short strings plus identifier-shaped strings were shared as well. But that range is a measurement, not a specification.

What makes this harder is that there is more than one cause. The cache is one; constant sharing inside a compilation unit is another. Because of the second, the same code came out true in a script and false in a REPL. The conclusion flips depending on how you check.

The last point matters most. This bug is not always wrong. It is sometimes right. Tests written around a 200 status code pass, and only the 500 range collapses. Tests that write the value into the source pass, and only values received from outside collapse. So this bug ships through a green test suite and first shows itself on the path that is hardest to check.

The rule is short. Use is only for None, marker objects and enumeration members. Everything else is ==. Follow it and you never need to know where the cache range starts and ends. Making implementation details irrelevant is what a good rule does.

There is one thing you can do right now. Search your repository for is and count the lines that compare against something other than None. If any compare against a constant name, the interpreter warning will never catch them. And if the tests around that code are green, it is worth asking whether they are green because the code is right or because the number is small.

# `==` vs `is` — Decision Table, Repro Code, Detector, Checklist

> Source: braindetox.kr — Some Numbers Compare True with is and Some Do Not
> Measured on: Windows 10 Pro (10.0.19045) / CPython 3.13.3 (MSC v.1943 64bit AMD64)
> Paste this file into an AI tool and say 「audit our codebase against these rules」.
> The cache range numbers below are **values measured on this interpreter**, not a language specification. Other implementations and other versions may differ.

## 0. One-line summary

`is` asks 「is this the same object」. `==` asks 「is this the same value」.
If you want a value comparison but write `is`, whether the answer is right is decided by **the interpreter's optimisation**.
An optimisation is not a specification, so **you may not rely on the result.**

## 1. Decision table — what to use

| What you want | Use | Do not use | Why |
|---|---|---|---|
| Same value | `a == b` | `a is b` | Equal values are not guaranteed to be the same object |
| Is it None | `x is None` | `x == None` | Any class may redefine `__eq__` |
| Is it not None | `x is not None` | `x != None` | Same reason |
| Is it truthy | `if x:` | `x is True` | `1`, `[1]`, `'a'` are truthy but fail `is True` |
| Is it exactly the `True` object | `x is True` | — | Correct if that is really the intent. Leave a comment |
| Is it a bool | `type(x) is bool` | `isinstance(x, int)` | `bool` is a subclass of `int` |
| Distinguish 「absent」 | `x is SENTINEL` | `if not x:` | `0`, `''`, `[]` get mistaken for absent |
| Do two names share an object | `a is b` | `a == b` | This is what `is` is actually for |
| Compare an Enum member | `x is Color.RED` | `x == 'RED'` | Enum members are singletons |
| Compare a string value | `s == 'admin'` | `s is 'admin'` | Run-time strings are not shared |

## 2. Repro code — paste and run

```python
# repro.py
import sys

def make(n):
    """Build the int at run time so no compile-time constant is reused."""
    return int(str(n))

print(sys.version)

for n in (0, 5, 256, 257, 1000):
    a, b = make(n), make(n)
    print(n, "is:", a is b, " ==:", a == b)

def shared(n):
    return make(n) is make(n)

lo, hi = 0, 1 << 20
while hi - lo > 1:
    mid = (lo + hi) // 2
    if shared(mid):
        lo = mid
    else:
        hi = mid
print("last value that IS shared :", lo)

lo2, hi2 = -(1 << 20), 0
while hi2 - lo2 > 1:
    mid = (lo2 + hi2) // 2
    if shared(mid):
        hi2 = mid
    else:
        lo2 = mid
print("first value that IS shared:", hi2)
print("measured range            :", hi2, "..", lo)
```

Measured (CPython 3.13.3 / Windows): shared range `-5 .. 256`, 262 objects.
Again: that is a **measurement**, not a rule.

## 3. The answer changes with how you run it

The same two lines, different results. Measured:

| How it ran | `a is b` after `a = 257; b = 257` |
|---|---|
| Script file | `True` |
| `python -c` | `True` |
| Piped into stdin | `True` |
| `exec()` with one string | `True` |
| `exec()` with three strings | `False` |
| Two separate `compile()` calls | `False` |
| Interactive interpreter, line by line | `False` |
| Value built at run time, `make(257)` | `False` |

Lesson: **identical literals inside one compilation unit collapse into one object.**
What you confirm in a REPL can differ from what a script does.

## 4. Detecting the dangerous pattern

### 4-1. Standard library only — turn the compiler warning into an error

```bash
# comparing a literal with is makes the interpreter emit a SyntaxWarning
python -W error::SyntaxWarning -c "import py_compile,sys; py_compile.compile(sys.argv[1], cfile=None, doraise=True)" target.py
```

- Caught: `x is 200`, `x is 'admin'`, `x is ()`
- **Not caught**: `x is CONST`, `flag is True`, `a is b`
- Fails a build step with no third-party dependency

### 4-2. Walk it yourself with `ast` (`is_lint.py`)

```python
#!/usr/bin/env python3
"""Find dangerous uses of is. Exit code 1 when anything is found."""
import ast, os, sys

SAFE = {"None", "True", "False", "Ellipsis", "NotImplemented"}

def module_consts(tree):
    out = {}
    for stmt in tree.body:
        if isinstance(stmt, ast.Assign) and isinstance(stmt.value, ast.Constant):
            v = stmt.value.value
            if isinstance(v, (int, float, str, bytes)) and not isinstance(v, bool):
                for t in stmt.targets:
                    if isinstance(t, ast.Name):
                        out[t.id] = v
    return out

class Checker(ast.NodeVisitor):
    def __init__(self, consts):
        self.consts, self.hits = consts, []

    def classify(self, node):
        if isinstance(node, ast.Constant):
            if node.value is None or isinstance(node.value, bool):
                return None
            return "LITERAL", "%s literal %r" % (type(node.value).__name__, node.value)
        if isinstance(node, (ast.Tuple, ast.List, ast.Dict, ast.Set)):
            return "LITERAL", "display literal"
        if isinstance(node, ast.JoinedStr):
            return "LITERAL", "f-string"
        if isinstance(node, ast.BinOp):
            return "EXPR", "arithmetic result"
        if isinstance(node, ast.Call):
            fn = getattr(node.func, "id", None)
            if fn in ("int", "float", "str", "bytes", "tuple", "list"):
                return "EXPR", fn + "() result"
            return None
        if isinstance(node, ast.Name):
            if node.id in SAFE:
                return None
            if node.id in self.consts:
                return "CONSTNAME", "name bound to %r" % (self.consts[node.id],)
        return None

    def visit_Compare(self, node):
        for op, right in zip(node.ops, node.comparators):
            if not isinstance(op, (ast.Is, ast.IsNot)):
                continue
            for side in (node.left, right):
                got = self.classify(side)
                if got:
                    self.hits.append((node.lineno, got[0], got[1]))
                if isinstance(side, ast.Constant) and isinstance(side.value, bool):
                    self.hits.append((node.lineno, "BOOLSINGLETON",
                                      "is %r - use a truth test or ==" % side.value))
        self.generic_visit(node)

def scan(path):
    src = open(path, encoding="utf-8").read()
    tree = ast.parse(src, filename=path)
    ck = Checker(module_consts(tree))
    ck.visit(tree)
    return sorted(set(ck.hits))

def main(root):
    total = 0
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames
                       if d not in ("__pycache__", ".git", ".venv", "node_modules")]
        for fn in sorted(filenames):
            if not fn.endswith(".py"):
                continue
            p = os.path.join(dirpath, fn)
            try:
                hits = scan(p)
            except SyntaxError as exc:
                print("%s: parse failed %s" % (p, exc))
                continue
            for lineno, kind, detail in hits:
                print("%s:%d: %s %s" % (p, lineno, kind, detail))
                total += 1
    print("%d finding(s)" % total)
    return 1 if total else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1] if len(sys.argv) > 1 else "."))
```

Finding kinds:

| Label | Meaning | Action |
|---|---|---|
| `LITERAL` | `is` compared against a literal | Replace with `==` now |
| `EXPR` | `is` compared against a computed or converted value | Replace with `==` now |
| `CONSTNAME` | `is` compared against a name bound to a number or string | Use `==` for values, `object()` sentinel for singletons |
| `BOOLSINGLETON` | `is True` / `is False` | Use a truth test or `==`. Comment it if deliberate |

- `pylint`: `literal-comparison`, `singleton-comparison`
- `ruff`: `F632`, `E711`, `E712`

## 5. Booleans and integers — where they overlap

| Expression | Result | Note |
|---|---|---|
| `issubclass(bool, int)` | `True` | bool is a subclass of int |
| `True == 1` | `True` | Same value |
| `True is 1` | `False` | Different objects |
| `hash(True) == hash(1)` | `True` | They land in the same dict slot |
| `{1: 'a', True: 'b', 1.0: 'c'}` | `{1: 'c'}` | **The first key survives, only the value is overwritten** |
| `{1, True, 1.0}` | `{1}` | Sets collapse the same way |
| `sum([True, True, False])` | `2` | Added as integers |
| `type(True) is bool` | `True` | This is the reliable type test |
| `isinstance(True, int)` | `True` | An int check does not filter booleans out |

## 6. Checklist

- [ ] No `is` used for a value comparison (`is_lint.py` passes)
- [ ] `-W error::SyntaxWarning` added to CI
- [ ] `x == None` replaced with `x is None`
- [ ] `x is True` kept only where 「exactly the True object」 is meant, with a comment
- [ ] Absence detected with a sentinel (`object()`), not `if not x:`
- [ ] Every `isinstance(x, int)` check reviewed for whether a bool passing is acceptable
- [ ] No dict or set mixes `0/False` and `1/True` as keys
- [ ] Tests do not feed literals only. Values that went through **parsing, serialisation, or a socket** are covered
- [ ] No comment or document relies on the cache range
- [ ] `id()` values are never stored or compared across processes
- [ ] `is` used only for **deliberate singletons** such as Enums and sentinels
- [ ] The review guideline says 「`is` is for singletons only」

## 7. Do not

- Write the cache range **as if it were a language specification** — it is an implementation detail
- Justify script behaviour with an `is` result you saw in a REPL — the compilation unit differs
- Conclude two objects are the same because `id()` matched — objects with non-overlapping lifetimes may share an `id()`
- Ask 「is it truthy」 with `is True` — most truthy values fail it
- Try to exclude booleans with `isinstance(x, int)` — they pass
- Leave an `is` comparison alone because the tests are green — **it may only have passed by luck on a small value**
