Hexana — JetBrains가 공개한 WebAssembly 바이너리 분석 도구, 무엇을 채우는가

WebAssembly가 브라우저를 벗어난 시대, IDE 안에서 .wasm을 여는 도구가 채우는 공백을 분석한다

2026-07-16 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: WebAssembly와 바이너리 분석 도구가 필요한 이유

2026년 7월 기준 WebAssembly(wasm)는 더 이상 브라우저 안에서 자바스크립트를 보조하는 조연이 아니다. 엣지 컴퓨팅, 플러그인 시스템, 서버사이드 런타임, 심지어 IDE 확장 그 자체까지 wasm 바이트코드가 배포 단위로 쓰인다. 이런 확산은 필연적으로 "이 .wasm 파일 안에 뭐가 들어있나"를 들여다볼 필요를 만든다. JetBrains가 공개한 Hexana(IntelliJ 플러그인 + VS Code 확장)는 그 필요에 대한 답이다.

이 글은 원문 발표를 그대로 옮기는 대신, WebAssembly가 왜 지금 바이너리 분석 도구를 요구하는 상황에 놓였는지, 기존 도구 지형에서 Hexana가 정확히 어떤 공백을 채우는지, 그리고 Kotlin Multiplatform으로 하나의 코어를 두 IDE에 배포하는 선택이 무엇을 의미하는지 본인의 분석으로 정리한다.

1. .wasm이라는 포맷 - 스택 머신 바이트코드와 WAT

1.1 스택 기반 가상머신 바이트코드

WebAssembly는 스택 기반 가상머신을 위한 이진 명령어 포맷이다. 소스가 C/C++, Rust, Kotlin 등 무엇이든 컴파일을 거치면 타입·임포트·함수·테이블·메모리·글로벌·익스포트·코드·데이터 섹션으로 구조화된 이진 바이트코드로 내려온다. 실행 시 레지스터가 아니라 스택에 값을 밀어넣고(push) 빼내는(pop) 방식으로 연산이 이뤄지며, 임의 점프가 아닌 구조적 제어 흐름(블록·루프·분기)만 허용해 난독화 여지를 줄인 것이 설계 특징이다. 이 구조 덕에 wasm은 샌드박스 안에서 예측 가능하게, 거의 네이티브에 가까운 속도로 실행될 수 있다.

1.2 사람이 읽는 대응물, WAT

이 바이트코드는 사람이 직접 읽고 고치기엔 불편하다. 그래서 WebAssembly Text Format(WAT)이라는 S-표현식 기반의 사람이 읽을 수 있는 대응 표현이 함께 정의돼 있다. wat2wasm·wasm2wat 같은 변환이 표준적으로 존재하는 이유도 여기 있다. 문제는 실무에서 이 변환이 대개 "파일 하나를 통째로 텍스트로 뒤집어 보는" 일회성 작업에 머문다는 점이다. 특정 함수만 골라 보거나, 그 자리에서 바로 고쳐 다시 저장하거나, 두 버전을 나란히 비교하는 흐름은 CLI 변환기만으로는 자연스럽게 이어지지 않는다.

2. 기존 도구 지형과 Hexana가 채우는 공백

2.1 wabt·wasm-tools - CLI 중심의 저수준 도구

wabt(WebAssembly Binary Toolkit)는 wat2wasm, wasm2wat, wasm-objdump, wasm-interp, wasm2c, wasm-strip, wasm-validate, wast2json 등 C/C++로 작성된 CLI 도구 모음이다. wasm-tools는 Rust 생태계에서 같은 역할을 하는 저수준 조작 라이브러리·CLI다. 둘 다 정확하고 스크립트 파이프라인에 넣기 좋지만, 본질적으로 "명령 한 줄 실행 → 텍스트 출력"이라는 배치 작업 도구다. 여러 섹션을 넘나들며 탐색하거나, 특정 함수를 고친 뒤 바로 재검증하거나, 두 바이너리의 구조적 차이를 시각적으로 보는 용도로는 설계돼 있지 않다.

2.2 Chrome DevTools - 브라우저에 갇힌 디버깅

Chrome DevTools는 DWARF 디버그 정보가 있으면 wasm을 소스 레벨에서 브레이크포인트로 디버깅할 수 있게 해준다. 그러나 이는 브라우저에서 실행 중인 페이지라는 맥락에 묶여 있다. 서버사이드 런타임(Wasmtime, WasmEdge)에서 도는 모듈, 엣지 함수, 플러그인 시스템에 실려 배포되는 wasm, 혹은 실행 없이 정적으로만 구조를 살피고 싶은 경우엔 DevTools가 답이 되지 않는다.

2.3 Hexana의 포지셔닝 - IDE 안에서 여는 구조적 문서

Hexana는 .wasm 파일을 컴파일된 텍스트 덩어리가 아니라, IDE 안에서 탐색 가능한 구조화된 문서로 연다. 섹션 브라우저, 임포트/익스포트 목록, 함수 타입, 코드 바디, GC 타입, 컴포넌트 모델 인터페이스(WIT)까지 트리 구조로 펼쳐 보여준다. JetBrains 플러그인(v0.13, IntelliJ IDEA 2025.2+ 계열)은 여기에 더해 행 단위로 바로 고칠 수 있는 편집 가능한 WAT 뷰, WIT 언어 지원, MCP 서버 통합, 별도 툴체인 설치 없이 Rust/Wasm 모듈로 번들된 x86·x86-64·ARM·AArch64·RISC-V 32/64 멀티 아키텍처 디스어셈블리를 제공한다. VS Code 확장(v0.6.0, Cursor·VSCodium 포함)은 Compose-for-Web 기반 커스텀 에디터, 가상 스크롤 헥스 뷰어, 11개 구조 분석 탭으로 같은 역할을 한다. 두 버전 모두 Wasmtime·WAMR·GraalVM에서 실행·실험적 디버깅(브레이크포인트, DWARF 소스 매핑)을 지원하고, 두 .wasm 모듈을 나란히 비교하는 diff 에디터(섹션·함수별 바이트 증감을 보는 Size Impact 탭, 추가·삭제·수정·이동으로 항목을 분류하는 Entities 탭)까지 갖췄다.

즉 wabt·wasm-tools가 못 하는 "IDE에 상주하며 탐색·편집·디버깅·비교를 잇는 워크플로"가 Hexana가 채우는 공백이다.

3. Kotlin Multiplatform 코어 하나로 두 IDE - 멀티 IDE 전략의 의미

3.1 무엇을 공유하나

Hexana는 "하나의 Kotlin Multiplatform 코드베이스가 JetBrains 플러그인과 VS Code 확장 모두에 쓰인다"고 밝힌다. 즉 .wasm 파싱, 섹션 해석, 컴포넌트 모델·GC·SIMD·스레딩 같은 최신 제안 지원, 디스어셈블리 연동 같은 복잡한 로직은 한 곳에만 존재하고, IntelliJ 플랫폼용 UI 레이어와 VS Code 확장용 UI 레이어가 그 위에 각각 얹힌다.

3.2 왜 지금 이 전략인가

이는 JetBrains가 2026년 들어 밀고 있는 "공유 코어 + 네이티브 셸" 패턴 - 신규 KMP 기본 프로젝트 구조에서 공유 라이브러리 모듈과 플랫폼별 앱 모듈을 분리하는 것과 같은 결 - 의 개발자 도구 버전이다. 실무적으로는 복잡한 바이너리 포맷 파서를 IntelliJ 플랫폼 API와 VS Code 확장 API 양쪽에 따로 두 번 만들고 두 번 유지보수하는 비용을 없앤다. 전략적으로는 더 크다. wasm·Rust 개발자 상당수가 VS Code(혹은 Cursor 같은 포크)를 쓰고, JVM·엔터프라이즈 개발자는 IntelliJ 계열을 쓴다. 어느 한쪽을 고르는 대신 처음부터 둘 다에 낸다는 것은, JetBrains가 VS Code 확장을 이식판이 아니라 1급 투자 대상으로 대한다는 신호로 읽힌다.

4. 실무 활용 - 리버스 엔지니어링·성능 분석·보안 감사·최적화

4.1 리버스 엔지니어링

소스 없이 배포된 wasm 모듈(레거시 게임을 재컴파일한 결과물, 서드파티 SDK, 클로즈드 바이너리)을 구조적으로 들여다볼 때 섹션 브라우저와 편집 가능한 WAT 뷰가 출발점이 된다. 본 블로그에서 다룬 포켓몬 에메랄드 브라우저 재컴파일 프로젝트처럼 네이티브 코드를 wasm으로 재컴파일·디컴파일하는 작업 자체가, 이런 구조 분석 도구가 왜 필요한지를 잘 보여준다.

4.2 성능 분석과 바이너리 다이어트

의존성 업데이트나 빌드 설정 변경 뒤 번들이 왜 커졌는지 알고 싶을 때, Size Impact 탭이 섹션·함수 단위 바이트 증감을 짚어준다. 어느 함수의 코드 바디가 유독 부풀었는지, 어떤 익스포트가 불필요하게 남아있는지를 손으로 wasm-objdump 출력을 대조하는 대신 시각적으로 확인할 수 있다.

4.3 보안 감사

공급망 의존성으로 들어온 wasm 모듈이 예상 밖의 임포트·익스포트를 갖고 있지 않은지, 릴리스 버전 사이에 눈에 띄지 않는 로직이 주입되지 않았는지는 Entities 탭의 추가·삭제·수정·이동 분류로 점검할 수 있다. wasm의 샌드박스 모델이 신뢰할 수 없는 코드 실행에 유리하다는 바로 그 이유 때문에, 그 안에 무엇이 들었는지 구조적으로 검증하는 절차도 함께 필요해진다.

4.4 wasm 최적화 검증

wasm-opt 같은 최적화 도구를 거친 뒤 DWARF 디버그 정보가 소스 매핑 채로 살아남았는지, 최적화가 실제로 어느 섹션에서 얼마나 바이트를 줄였는지를 diff 뷰로 즉시 확인할 수 있다. 프로덕션 인시던트 트리아지에서 디버그 정보 유무는 원인 추적 속도를 크게 가른다.

5. WASM 생태계 2026 맥락 - WASI와 컴포넌트 모델

5.1 WASI의 진화

WASI(WebAssembly System Interface)는 wasm 모듈이 파일, 네트워크, 시계 같은 시스템 자원에 접근하는 표준 방법을 정의한다. WASI 0.2(프리뷰 2)가 2024년 1월 안정화되며 컴포넌트 모델을 실제 API 대상으로 끌어올렸고, 2026년 7월 기준 WASI 0.3은 Wasmtime 37 이상에서 프리뷰로 제공되며 콜백 기반 우회 없이 네이티브 비동기 I/O를 목표로 한다. 장기 표준인 WASI 1.0을 2026년 목표로 논의하는 흐름도 있다(일부 업계 자료 기준, 확정된 일정은 아니다).

5.2 컴포넌트 모델과 WIT

컴포넌트 모델은 서로 다른 언어로 컴파일된 wasm 모듈을 조립 가능한 컴포넌트로 묶는 표준이고, WIT(WebAssembly Interface Types)는 그 인터페이스를 기술하는 언어다. 2025-2026 사이 이 축이 "실험적 데모"에서 "실제 멀티 언어·멀티 런타임 클라우드 네이티브 시스템"으로 넘어갔다는 평가가 나온다. Hexana가 GC·SIMD·스레딩과 함께 컴포넌트 모델·WIT를 명시적으로 지원 대상에 넣었다는 것은, 이 도구가 레거시 MVP 시절 wasm이 아니라 지금 이 최전선을 겨냥해 설계됐다는 뜻이다. 업계 조사에 따르면 개발자의 70% 이상이 브라우저 밖 wasm을 쓰거나 검토 중이고, 신규 엔터프라이즈 프로젝트의 상당수가 wasm 모듈을 하나 이상 포함한다는 보고도 있다. 엣지 함수, 플러그인 시스템, 신뢰할 수 없는 코드 실행이 특히 wasm이 자리 잡은 영역으로 꼽힌다.

6. 한계와 주의점

Hexana는 아직 초기 버전(플러그인 v0.13, 확장 v0.6.0)이고, 디버깅 기능은 스스로 "실험적"이라 표기한다. 프로덕션 트러블슈팅의 1차 도구로 전면 의존하기보다, wasm-objdump·wasm-tools 같은 검증된 CLI와 병행하며 신뢰도를 확인하는 편이 안전하다. 또한 디스어셈블리 백엔드가 Rust/Wasm 모듈로 번들된다는 점은 설치는 편하지만, 백엔드 자체의 정확도·최신 명령어셋 커버리지는 별도 검증이 필요하다. WASI 0.3·WIT처럼 아직 유동적인 표준을 다루는 만큼, 스펙이 바뀌면 도구의 파싱 결과도 함께 갱신돼야 한다는 점도 염두에 둬야 한다.

결론 - 오늘 확인할 3가지

Hexana는 wasm을 CLI 변환기의 텍스트 덩어리가 아니라 IDE 안의 구조화된 문서로 바꾼다. 이는 wabt·wasm-tools가 저수준에서, Chrome DevTools가 브라우저 안에서 각각 반쪽만 채우던 공백을 IDE 통합·diff·멀티 아키텍처 디스어셈블리로 메운다. 그리고 하나의 Kotlin Multiplatform 코어로 IntelliJ 계열과 VS Code 양쪽에 동시에 내는 방식은, 개발자 도구를 특정 IDE 생태계에 종속시키지 않으려는 실용적 선택으로 읽힌다.

1) 이미 wasm 모듈을 다루고 있다면(리버스 엔지니어링, 성능, 보안 어느 쪽이든) Hexana를 부수 도구로 설치해 기존 CLI 워크플로와 나란히 써보라. 2) 디버깅은 아직 실험적이니 검증된 도구와 교차 확인을 병행하라. 3) 컴포넌트 모델·WIT·WASI 0.3처럼 유동적인 표준을 다루는 프로젝트라면, 이 최전선을 명시적으로 지원하는 도구가 흔치 않다는 점에서 Hexana를 눈여겨볼 가치가 있다.
