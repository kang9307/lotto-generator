The argument lists shown here are the command line and argv printed by the receiving program itself, from runs of powershell.exe -NoProfile in Windows PowerShell 5.1.19041.6456. The program that counts arguments is Python 3.13, and git 2.48.1 and curl.exe were used as real tools. Which curl.exe runs depends on PATH and therefore on the environment; the path and version are those printed by Get-Command curl.exe in section 11. PowerShell 7 (pwsh) was not in the environment, so statements about 7 are limited to sentences in the official documentation. Quoting rules on the bash side are in the shell quoting rules guide, and the basic fact that 5.1 loses double quotes and empty strings is in section 6 of the shell quoting and Korean file name guide. On top of that, this article adds the full list of argument passing from PowerShell to native programs, which escaping methods succeed, trailing backslashes, splatting, --% and here-strings, and cases with git and curl.exe.

How it was measured - the receiving program prints its own command line and argv

How PowerShell splits and passes arguments cannot be learned from PowerShell's own output. The receiving side has to print the string the process actually received. The small program below prints both the original command line returned by the Windows API (raw) and the argv that the C runtime split it into. In every later block, the raw line is the command line PowerShell assembled and the argv line is the arguments the receiving program saw. The argument count line (n) is the length of argv, so it is omitted, and the >>> at the start of a line is the input that was tested.

import sys, json, ctypes
                    ctypes.windll.kernel32.GetCommandLineW.restype = ctypes.c_wchar_p
                    raw = ctypes.windll.kernel32.GetCommandLineW()
                    i = raw.find('argv.py')
                    print('  raw : ' + raw[i + 7:].lstrip().encode('ascii','backslashreplace').decode())
                    print('  argv: ' + json.dumps(sys.argv[1:], ensure_ascii=True))
                    print('  n   : %d' % (len(sys.argv) - 1))

The official documentation describes the process like this. When a native command is called, PowerShell first parses the arguments, joins the parsed arguments into a single string separated by spaces, and assigns that string to the Arguments property of a ProcessStartInfo object. Quotes inside the string have to be escaped with extra quotes or backslashes, and the documentation says the backslash is not an escape character for PowerShell but for the underlying API. This one paragraph is the frame for the whole article: PowerShell builds one line, and the receiving program splits that line again. The result is decided at the point where PowerShell's rules meet the splitting rules of the receiving program.

The basic rules - wrap when there is a space, drop an empty string

The simplest inputs come first. $v holds a b (with a space).

>>> python argv.py a b
                      raw : a b
                      argv: ["a", "b"]
                    
                    >>> python argv.py ''
                      raw : 
                      argv: []
                    
                    >>> python argv.py '' x
                      raw : x
                      argv: ["x"]
                    
                    >>> python argv.py 'a b'
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py "$v"   ($v = 'a b')
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py '$v'
                      raw : $v
                      argv: ["$v"]
                    
                    >>> python argv.py a$v
                      raw : "aa b"
                      argv: ["aa b"]
Inputraw (assembled command line)Received argv

''(nothing)0 arguments
'' xx1 argument, only x remains
'a b'"a b"1 argument
"$v""a b"1 argument
'$v'$v1 argument, literal text
a$v"aa b"1 argument
  • Only an argument that contains a space is wrapped in double quotes. Without a space it is not wrapped.
  • PowerShell strips the single quotes and passes the content as it is. '$v' is not expanded and "$v" is. Even if the expanded value contains a space there is no word splitting, so it is one argument.
  • A form such as a$v, with characters attached to a variable, also continues as one argument. The official documentation likewise says that characters after a simple variable reference are part of the same argument.
  • An empty string leaves no trace in raw. The arguments after it move forward by one position.

The last item is where a silent accident starts. In a call like --name '' --flag, even if an empty value was meant to be passed, the receiving side sees --name --flag.

Double quotes disappear - JSON breaks first

Double quotes inside an argument are not escaped in 5.1. The documentation also says that PowerShell's command line parsing removes the quote characters that were typed.

>>> python argv.py 'say "hi"'   (single-quoted, contains double quotes)
                      raw : "say "hi""
                      argv: ["say hi"]
                    
                    >>> python argv.py 'say"hi'   (no space in value)
                      raw : say"hi
                      argv: ["sayhi"]
                    
                    >>> python argv.py '{"a":1}'
                      raw : {"a":1}
                      argv: ["{a:1}"]
                    
                    >>> python argv.py '{"a": 1}'   (JSON with a space)
                      raw : "{"a": 1}"
                      argv: ["{a: 1}"]
  • 'say "hi"' contains a space and is wrapped in double quotes, but the inner quotes go in unchanged, so raw becomes "say "hi"". The receiving side consumes the quotes as delimiters and gets say hi.
  • With no space, as in 'say"hi', the argument is not wrapped and the quote goes into raw as it is, yet the result is sayhi. The quote is consumed whether or not the argument was wrapped.
  • '{"a":1}' arrives as {a:1}. JSON without its quotes is not valid. '{"a": 1}' with a space is also {a: 1}.

This symptom appears in the same form in every call that passes a value containing quotes, such as curl -d, git commit -m, python -c and node -e. What makes it dangerous is that no error occurs and the value is changed silently.

Keeping double quotes - backslash escapes, doubled quotes and already-wrapped values

The two methods the documentation mentions (doubling the quotes and backslashes) and values that are already wrapped in quotes were tested.

>>> python argv.py 'say \"hi\"'   (backslash-escaped quotes)
                      raw : "say \"hi\""
                      argv: ["say \"hi\""]
                    
                    >>> python argv.py '{\"a\":1}'
                      raw : {\"a\":1}
                      argv: ["{\"a\":1}"]
                    
                    >>> python argv.py '{\"a\": 1}'
                      raw : "{\"a\": 1}"
                      argv: ["{\"a\": 1}"]
                    
                    >>> python argv.py 'say ""hi""'   (doubled quotes inside single quotes)
                      raw : "say ""hi"""
                      argv: ["say \"hi\""]

                      raw : a""b
                      argv: ["ab"]

                      raw : {""a"":1}
                      argv: ["{a:1}"]

                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py 'x "a b"'

                      argv: [""]

  • Replacing each double quote in the value with a backslash and a double quote made it arrive intact whether or not there was a space.
  • Doubled quotes worked in Python only when PowerShell wrapped the argument in double quotes (when it had a space). In an argument that was not wrapped the quotes were consumed, and in git the same form was an error. The same command line can be split differently by different receiving programs.
  • "a b", already wrapped in double quotes, was not wrapped again by 5.1 (this does not hold for every already-wrapped value; the condition was tested in section 10), but those quotes are consumed as delimiters. If the quotes must be part of the value, this method cannot be used.
  • Passing two double quote characters as the value delivers one empty string. It is the way to revive the empty argument that vanished in section 3.

A trailing backslash swallows the next argument

A path containing a space is wrapped in double quotes. If that path ends with a backslash, there is a problem. The argv lines below are in JSON format, so one backslash is written as two.

>>> python argv.py 'C:\Program Files\x'
                      raw : "C:\Program Files\x"
                      argv: ["C:\\Program Files\\x"]
                    
                    >>> python argv.py 'C:\Program Files\x\'   (path ends with backslash)
                      raw : "C:\Program Files\x\" next
                      argv: ["C:\\Program Files\\x\" next"]
                    
                    >>> python argv.py 'C:\Program Files\x\\'   (two backslashes)
                      raw : "C:\Program Files\x\\" next
                      argv: ["C:\\Program Files\\x\\", "next"]
                    
                    >>> python argv.py 'C:\x\' next   (no space in path)
                      raw : C:\x\ next
                      argv: ["C:\\x\\", "next"]
  • A path with a space, C:\Program Files\x, is fine.
  • When the same path ends with one \, raw becomes "C:\Program Files\x\" next, the closing quote is read as an escaped quote, and the following next is merged into the same argument. One argument is received and its value is C:\Program Files\x" next. It is not that an argument was lost; two arguments clumped into one.
  • With two \\ at the end, they are read as one backslash followed by the closing quote, and next arrives separately. One backslash remains at the end of the received path.
  • The path without a space, C:\x\, is not wrapped, so the problem does not occur.

Both conditions have to hold at the same time: the argument has a space, so it is wrapped, and it ends with a backslash. Code that builds a folder path including the trailing separator, for example a variable pointing to a folder with a space under a user folder, is caught here. Trimming the trailing backslash with TrimEnd('\') or doubling it makes it work.

Variables, commas and metacharacters - how much is PowerShell's job

Arguments mix things PowerShell interprets first with things it passes unchanged.

>>> python argv.py 1,2
                      raw : 1,2
                      argv: ["1,2"]
                    
                    >>> python argv.py $env:OS
                      raw : Windows_NT
                      argv: ["Windows_NT"]
                    
                    >>> python argv.py (1+2)
                      raw : 3
                      argv: ["3"]
                    
                    >>> python argv.py '%OS%'
                      raw : %OS%
                      argv: ["%OS%"]
                    
                    >>> python argv.py *.nothing  (no match, wildcard)
                      raw : *.nothing
                      argv: ["*.nothing"]
                    
                    >>> python argv.py 'a & b' 'a | b'
                      raw : "a & b" "a | b"
                      argv: ["a & b", "a | b"]
                    
                    >>> python argv.py a;echo b   (semicolon ends the statement)
                      raw : a
                      argv: ["a"]
                    b
                    
                    >>> python argv.py ('caf' + [char]0xE9) ('x' + [char]0xD55C)
                      raw : caf\xe9 x\ud55c
                      argv: ["caf\u00e9", "x\ud55c"]
  • 1,2 arrives as the single argument 1,2. The official documentation says that commas create arrays for PowerShell commands but are interpreted as part of the expandable string for native applications.
  • Variable and parenthesis expressions such as $env:OS and (1+2) are evaluated by PowerShell first and the value is passed. '%OS%' is left alone by PowerShell and stays literal.
  • The wildcard *.nothing is not expanded and is passed as it is. PowerShell does not expand file names.
  • Metacharacters inside quotes, as in 'a & b', are preserved as one argument. A semicolon outside quotes ends the command. With a;echo b, Python received only the argument a, and echo b ran as a separate command and printed b.
  • Non-ASCII characters appear as \xe9 and \ud55c because the output was printed with ASCII escapes, but the arguments arrived correctly. This is because the command line is passed as Unicode.

The argument-mode metacharacters listed by the documentation are space, single quote, double quote, backtick, comma, semicolon, parentheses, braces, pipe, ampersand, angle brackets, at sign and hash. Of these, angle brackets, at sign and hash are special only at the start of a token. If an argument to be passed without quotes contains such characters, PowerShell takes them first.

Arrays and splatting - one string is one argument

When the argument list is variable it gets held in a variable, and the form it is held in decides the result.

>>> $arr = 'x','y z'; python argv.py $arr
                      raw : x "y z"
                      argv: ["x", "y z"]
                    
                    >>> $s = '--flag "a b"'; python argv.py $s
                      raw : "--flag "a b""
                      argv: ["--flag a", "b"]
                    
                    >>> $sp = @('--flag','a b'); python argv.py @sp
                      raw : --flag "a b"
                      argv: ["--flag", "a b"]
                    
                    >>> $h = @{k=1}; python argv.py @h  (hashtable splat)
                      raw : -k:1
                      argv: ["-k:1"]
  • The array variable $arr becomes one argument per element, and only the element with a space is wrapped.
  • $s, which holds the argument list as one string, becomes a single argument as a whole. It was wrapped because of the space, the inner quotes were consumed, and it split into --flag a and b. This is the typical way the approach of assembling a list into a string goes wrong.
  • Splatting the array (@sp) turns each element held in the variable into one argument. For variable arguments this is the safe approach.
  • Hashtable splatting @h turned a key and value into one argument of the form -k:1. Whether that matches the option format of a native program depends on the program.

--% and -- - the tokens that turn parsing off

The stop-parsing token --% passes the text after it without PowerShell interpretation. The documentation explains that the rest of the line is treated as a literal and only environment variables in Windows notation such as %USERPROFILE% are substituted.

>>> python argv.py --% a "b c" %OS%
                      raw : a "b c" Windows_NT
                      argv: ["a", "b c", "Windows_NT"]
                    
                    >>> python argv.py --% --opt="a b" 'q'
                      raw : --opt="a b" 'q'
                      argv: ["--opt=a b", "'q'"]
                    
                    >>> python argv.py --% "a b" "c
                      raw : "a b" "c
                      argv: ["a b", "c"]
                    
                    >>> python argv.py -x -- y
                      raw : -x -- y
                      argv: ["-x", "--", "y"]
                    
                    >>> python argv.py --opt="a b"
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py --opt=$v
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py -p:val
                      raw : -p:val
                      argv: ["-p:val"]
  • In --% a "b c" %OS% the double quotes served as delimiters, so b c became one argument, and %OS% was substituted with Windows_NT. As the documentation says, the form %name% is always expanded, and stays as it is if the name is not defined.
  • Single quotes after --% are not stripped by PowerShell. 'q' arrived with its quotes as 'q'.
  • Unbalanced quotes are passed as they are. The unclosed "c arrived as the single argument c.
  • According to the documentation, --% is effective only until the next newline or pipeline character, redirection is passed as an argument, and no dynamic element other than environment variables can be embedded.
  • --, which is a token for PowerShell commands, is simply passed as a -- argument to a native program. -x -- y became three arguments.
  • Both --opt="a b" and --opt=$v were assembled into the single argument "--opt=a b", because the option name and value form one token.

Backticks and here-strings - multi-line arguments

A backtick is an escape only inside a double-quoted string. Inside single quotes it is a literal character. A value that contains line breaks can be made with a here-string.

>>> python argv.py 'a`tb' "a`tb"
                      raw : a`tb "a	b"
                      argv: ["a`tb", "a\tb"]
                    
                    >>> python argv.py "line1`nline2"
                      raw : "line1
                    line2"
                      argv: ["line1\nline2"]
                    
                    >>> here-string: python argv.py (@'...'@)  with a double quote inside
                      raw : "first line
                    second "quoted" line"
                      argv: ["first line\nsecond quoted line"]
  • A backtick-t inside single quotes arrived as the literal characters, and a backtick-t inside double quotes became a tab character.
  • An argument that contains a line break carries the line break into raw and arrives as one argument. As with an argument that has a space, it is wrapped in double quotes.
  • Double quotes inside the here-string were consumed as in section 3 and became second quoted line. As the documentation explains, a here-string interprets the quotes inside it literally, but they are stripped again at the step of passing to a native program.

Ways to pass a multi-line value with quotes safely are compared in the curl.exe case in section 11.

Controlling the command line exactly - Start-Process and ProcessStartInfo

To avoid PowerShell's assembly rules, the command line can be built by hand and passed in. First it was checked what happens when -ArgumentList of Start-Process is a string and what happens when it is an array.

>>> Start-Process python -ArgumentList 'argv.py "a b" {\"k\":1}' -NoNewWindow -Wait
                      raw : "a b" {\"k\":1} 
                      argv: ["a b", "{\"k\":1}"]
                    
                    >>> Start-Process python -ArgumentList @('argv.py','a b','c') -NoNewWindow -Wait
                      raw : a b c 
                      argv: ["a", "b", "c"]

When one string is given, raw equals the input string, so the caller controls the double quotes and backslashes directly. When an array is given, the elements are only joined with spaces and not wrapped, so 'a b' split into the two arguments a and b. The array should not be assumed to be safe.

To deliver an arbitrary value exactly, there is a method of keeping a helper that escapes according to the rules of the C runtime and putting its result into ProcessStartInfo.Arguments. The helper below doubles the backslashes that precede a double quote in the value, escapes the double quotes with a backslash, doubles trailing backslashes, and then wraps the whole in double quotes.

function ConvertTo-NativeArg([string]$a) {
                      if ($a -eq '') { return '""' }
                      $r = $a -replace '(\\*)"', '$1$1\"'
                      $r = $r -replace '(\\+)$', '$1$1'
                      '"' + $r + '"'
                    }
                    function Invoke-NativeExact([string]$File, [string[]]$ArgList) {
                      $psi = New-Object Diagnostics.ProcessStartInfo
                      $psi.FileName = $File
                      $psi.Arguments = ($ArgList | % { ConvertTo-NativeArg $_ }) -join ' '
                      $psi.UseShellExecute = $false
                      $psi.RedirectStandardOutput = $true
                      $psi.StandardOutputEncoding = [Text.Encoding]::UTF8
                      $p = [Diagnostics.Process]::Start($psi)
                      $out = $p.StandardOutput.ReadToEnd()
                      $p.WaitForExit()
                      $out
                    }
$cases = @('plain', 'a b', 'say "hi"', '{"a": 1}', 'C:\Program Files\x\', 'tail\\', 'q"', '', 'a\"b c')
                    foreach ($c in $cases) {
                      $json = Invoke-NativeExact 'python' @('-c', 'import sys,json;print(json.dumps(sys.argv[1]))', $c)
                      $back = $json | ConvertFrom-Json
                      '{0,-22} -> received equal: {1}' -f ("'" + $c + "'"), ($back -ceq $c)
                    }

Eight of nine matched; a\"b c, whose value has a backslash and a double quote together, did not. The helper's result for this value already begins and ends with a double quote, yet 5.1 wrapped it once more, so raw began with two double quotes and the received argument split in two. The helper results of the other eight values (such as "say \"hi\"") were passed the same way and were not wrapped again. To find out why only this value was wrapped, the variables were separated. Without the helper, fourteen strings that differ only in where the quotes, backslashes and spaces sit were put in a variable and passed the same way, and whether the received raw was the input wrapped once more in double quotes (rewrapped) was recorded. The rule column is the value computed from a hypothesis made after looking at the observations: wrap if there is any whitespace character that is preceded by an even number of double quotes (zero counts as even).

function Test-Rule([string]$s) {
                      $n = 0
                      foreach ($ch in $s.ToCharArray()) {
                        if ($ch -eq '"') { $n++ }
                        elseif ([char]::IsWhiteSpace($ch) -and $n % 2 -eq 0) { return $true }
                      }
                      $false
                    }
                    $cases = @(
                      '"a b"',
                      '"a\"b c"',
                      '"a\\"b c"',
                      '"a\\\"b c"',
                      '"a\\\\"b c"',
                      '"a\\\"bc"',
                      '"a\\\b c"',
                      '"say \"hi\""',
                      'a\\\"b c',
                      '"a" b',
                      '"a b" c',
                      'a "b c"',
                      'x y',
                      '"x""y z"'
                    )
                    foreach ($v in $cases) {
                      $raw = (python argv.py $v)[0] -replace '^\s*raw : ', ''
                      '{0,-14} raw={1,-16} rewrapped={2,-5} rule={3}' -f $v, $raw, ($raw -ceq ('"' + $v + '"')), (Test-Rule $v)
                    }

  • Eight of the fourteen were wrapped again, and the hypothesis agreed with the observation on all fourteen. Wrapping happened whenever some whitespace was preceded by an even number of double quotes (x y, "a" b, a "b c", and the second space in "a b" c).
  • The number of backslashes (1, 2, 3 or 4) did not change the result. Lines 2 to 5 were all wrapped, the same result as if a quote preceded by a backslash were counted as one quote.
  • The six lines that were not wrapped (the 1st, 6th, 7th, 8th, 9th and 14th) either had no space (the 6th) or had the space preceded by an odd number of double quotes (the rest).
  • Among the nine helper results, only that of a\"b c has two double quotes (the opening one and the escaped one) before its space; the other eight have no space, or an odd number (one or three) before it.

This rule is a hypothesis built to fit the fourteen observations. It was not confirmed in the 5.1 implementation or in the documentation, and the official excerpts this article cites do not contain such a judgment. What is confirmed is only the observation that whether 5.1 wraps again depends on the number of double quotes before the space. That is why the helper's result should not be given to an ordinary 5.1 call but to a path that uses the command line as it is.

Real cases - git commit and curl.exe

A commit message containing double quotes was passed in a temporary repository. The numbers in the output that follows the five calls below are the same as the call order.

git commit -q --allow-empty -m 'fix "x" bug'
                    git commit -q --allow-empty -m 'fix \"x\" bug'
                    git commit -q --allow-empty -m "fix ""x"" bug"
                    git commit -q --allow-empty -m 'fix ""x"" bug'
                    git commit -q --allow-empty -m 'fix "x"'
1) -m 'fix "x" bug'          -> fix x bug
                    2) -m 'fix \"x\" bug'        -> fix "x" bug
                    3) -m "fix ""x"" bug"          -> fix x bug
                    error: pathspec 'bug' did not match any file(s) known to git
                    4) -m 'fix ""x"" bug'        -> fix x bug
                    5) -m 'fix "x"'              -> fix x
  • Number 1 is fix x bug, with the double quotes gone, and number 5 is fix x.
  • Number 2 used the backslash escape, and fix "x" bug was recorded exactly.
  • In number 3 the quotes were doubled inside a PowerShell double-quoted string, but the value that string produces is the same fix "x" bug as number 1, so the result is the same as number 1. Escaping at the PowerShell level does not escape the quotes for the native program.
  • In number 4, putting doubled quotes into the command line made git report the error pathspec 'bug' did not match. The message printed on the line for number 4 is that of the previous commit. The same input worked in Python, so doubled quotes give different results depending on the program.

curl.exe -d, which sends a JSON body, is a more common case. A small local server that saves the POST body to a file was started and the received body was read.

import http.server, sys
                    class H(http.server.BaseHTTPRequestHandler):
                        def do_POST(self):

                            body = self.rfile.read(n)

On this PC the curl bundled with Git comes first on PATH, so which curl.exe runs depends on the environment. Running the same calls with C:\Windows\System32\curl.exe (8.13.0) gave the same received bodies. The calls below were run after $body and body.json were created.

  • JSON written in single quotes arrived as {a: 1}, with all the quotes gone.
  • Escaping the double quotes with backslashes made it arrive exactly as {"a": 1}.
  • Passing the here-string variable as it was not only lost the quotes but also ended the body at b: two. It appears that words} split off as a separate argument when the quotes were consumed; this is a presumption from the same pattern as section 3.
  • Escaping the quotes of the here-string with -replace '"', '\"', or writing the body to a file and passing it with --data-binary '@body.json', delivered the multi-line body exactly.

For a body that is multi-line or full of quotes, passing it as a file is the simplest approach because it steps outside the argument passing rules, rather than fixing the escaping. The file can be written without a BOM as in the 5.1 file encoding article.

PowerShell 7.3 and later is different - only what the documentation says

According to the official documentation (7.4 edition), PowerShell 7.3 changed the way it parses the command line for native commands, and the new variable $PSNativeCommandArgumentPassing controls it. The documentation warns that the change is a breaking change and may break scripts and automation that work around the various issues in invoking native applications.

  • The values are Legacy, Standard and Windows, and Legacy is the historic behavior.
  • On Windows the default is Windows, and on other platforms it is Standard.
  • The Windows mode is the same as Standard except that it uses the Legacy method for cmd.exe, cscript.exe, find.exe, sqlcmd.exe, wscript.exe and files ending in .bat, .cmd, .js, .vbs and .wsf.

pwsh was not available in this environment, so the behavior of 7 was not run. The above is the documentation's wording, and how the 5.1 workarounds of this article (backslash escaping, the helper) behave in 7 was not checked. Before moving a 5.1 workaround to 7, printing raw and argv in the same way is the sure way to check.

Choosing by situation

These are the methods by situation from the results measured in 5.1. Only three receiving programs were tested: Python, git and curl.exe.

SituationMethodBasis
A plain argument with no space or quoteUse it as it isMeasured; raw and argv equal the input
A variable value that contains a spaceUse "$v" or $v as it isMeasured; wrapped into one argument
The value has double quotesReplace each double quote with a backslash and a double quote before passingMeasured; arrived intact in python, git and curl.exe
An empty string argumentPass two double quote characters as the valueMeasured; arrived as one empty string
A path that ends with a backslashTrim the trailing backslash or use twoMeasured; prevents the next argument from merging
A variable argument listBuild an array and splat itMeasured; one string arrives as one argument
A body with many quotes or several linesWrite it to a file and use the program's file argument optionMeasured; the curl.exe file input arrived exactly
The command line must be controlled character by characterProcessStartInfo.Arguments with a hand-built escaping helper, or one string for Start-ProcessMeasured; the helper matched all nine
Untrusted input, or a call through a batch fileDo not pass it directly as an argumentThe documentation's warning; for batch files the arguments reach cmd.exe as a raw command line

All rows share one principle. The arguments a receiving program saw cannot be known unless the receiving program prints them. When calling a new tool, passing the same form first to a program that counts arguments and checking raw and argv is more reliable than any row of this table.

What could not be confirmed

  • PowerShell 7 (pwsh): it was not in the environment and could not be run. The behavior of argument passing from 7.3 on and of the three values of $PSNativeCommandArgumentPassing are sentences from the official documentation.
  • How the 5.1 workarounds (backslash escaping, doubled quotes, the helper) behave in 7.3 and later: not run.
  • Programs other than Python, git and curl.exe: the command line splitting rules of Node, Go, Java, .NET and other MinGW-based tools. Why doubled quotes failed in git was not determined, and only the result was recorded.
  • Calls that go through cmd.exe, .bat or .cmd (npm.cmd and the like): not run. The documentation warns that arguments are passed to batch files as a raw command line.
  • Why the here-string body was cut off partway in curl.exe: it is a presumption that the argument split in two, and the arguments on the curl side were not checked directly.
  • Differences on other Windows builds, locales or console code pages: confirmed only on 5.1.19041 of Korean Windows 10. Non-ASCII arguments were tested in one Python case only.
  • The internal condition under which 5.1 wraps an argument again: only a rule that fits the observations of fourteen strings was confirmed, and it was not confirmed in the 5.1 implementation or documentation. Whether the rule holds for a wider variety of input was not tested.
  • ShellExecute paths such as -Verb of Start-Process, and running through the call operator &: not covered.
