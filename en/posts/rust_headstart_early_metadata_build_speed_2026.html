Context — The headstart Prototype for Slashing Build Wait Times

The README of the repository states the problem in a few sentences. Every crate waits for the crates it depends on to be fully checked, function bodies included, before it starts. It does not need those bodies to type-check itself, because it compiles against the dependency's interface, which is the metadata in its .rmeta file, a compact description of the crate's items that dependent crates read instead of its source code. Headstart makes rustc write an early metadata file as soon as the interface has been checked, and makes cargo start dependents on it. Each crate's bodies are then checked while the crates downstream are already compiling.

The repository was created on September 27, 2026, and its most recent push was on October 4. It was posted to Hacker News on October 4, under a title saying that emitting metadata early makes building and checking Rust up to twice as fast, and it was introduced on GeekNews on October 5. What this article covers is therefore a prototype that is not yet ten days old. In what follows, check means cargo check, which analyzes the code without generating machine code, and build means cargo build, which also generates code and links the result. A clean build starts from an empty target directory.

The most important thing to be careful about is the denominator of each number. The up to 54% and up to 42% in the README are the best values among clean 16-core builds of 13 real projects, and the table in the results document shows that both come from a single project, rust-analyzer: check went from 90.1 seconds to 41.5 seconds, and build from 137.9 seconds to 79.9 seconds. The smallest values in the same table are 2% for check and 0% for build, both for zola. Every figure below has to be read the same way, with the project and the system it belongs to attached.

Architecture and Bottlenecks of Standard Cargo Pipelining

Pipelined compilation means that rustc and cargo overlap the compilation of a crate's dependents with the later stages of the dependency, so that a build is not a strict sequence of whole crates. Starting a dependent crate before its dependency has finished is not new in itself. According to the Rust release notes, pipelined compilation was added to both rustc and cargo in Rust 1.38.0, released on 2019-09-26. The notes say only that it improves compilation times in some cases. The design document adds that cargo already pipelines the libraries of cargo build on the metadata notification.

The limit lies in when that metadata is written. (Borrow checking is the step that verifies the ownership and borrowing rules inside function bodies, and MIR is the compiler's mid-level intermediate representation, which sits between type checking and code generation.) According to design.md, rustc writes metadata only after every function body has been type-checked and borrow-checked. The metadata holds the signatures and types of items, trait implementations, and the MIR of anything a dependent might evaluate at compile time, inline or instantiate, so a dependent ends up waiting for the checking of bodies that it never needs. The design document also says that cargo did not pipeline cargo check at all.

The documents also name earlier work on the same idea. According to design.md, in 2019 Nicholas Nethercote moved the writing of metadata ahead of type checking and borrow checking in rust-lang/rust#64112. His design used a single metadata file that had to carry the MIR needed for code generation, so the early write still forced most of the analysis, and he saw at most a 1.07 times improvement and gave the change up. The reason he gave, quoted in design.md from his blog, was that it was not much of a win and would slightly delay error message emission. Headstart differs in two ways, the document says: early metadata is a separate file holding only what analysis needs, and dependents wait for the full file only just before code generation. It also covers cargo check.

Decoupling Item Interfaces From Function Body Verification

The order of execution that design.md describes is as follows. A new query, analysis_interfaces, runs everything up to and including the checks of item interfaces (well-formedness and coherence), and the existing analysis query runs it first and then checks every body. The driver writes early metadata between the two.

  • New query: analysis_interfaces splits analysis into item interfaces and function bodies.
  • Early metadata write: between the two stages the driver writes .early-rmeta and announces it with an early-metadata artifact notification. Binaries, which nothing can depend on, do not write it.
  • Immediate start of dependents: cargo starts later units on that notification. Every unit that rustc compiles in check, build or test mode is covered, including binaries, tests, proc macros and build scripts, although proc-macro and dylib dependencies still wait for a full build.
  • Overlap with body checking: while the upstream crate checks its function bodies, the downstream crate proceeds with its own analysis on the early metadata.
  • Swap to full metadata: before code generation, rustc swaps in the full metadata of each dependency. If the file does not exist yet, it waits for a lock that the producer holds until the file is written. While waiting, the compilation announces a wait-metadata notification so that cargo can give its job slot to other work, and it announces resume afterwards.

For the metadata to be correct, whatever comes out of bodies has to be computed before the early file is written. The design document calls these the interface bodies. They are the hidden types of impl Trait (opaque types), the MIR of constants, const fns and array lengths, the evaluation of statics, and the coroutines of async code. Conversely, the optimized MIR of functions, deduced parameter attributes, exported symbols, cross-crate inlinability and the panic strategy are read only by code generation, so they are left out of early metadata. The two files carry the same crate hash (SVH). The hash is computed once, from the bytes of the early metadata plus a supplement made of the HIR hash and the tracked options, and the full metadata carries the same value. Because a change to any function body changes the hash, the document explains, the decisions of incremental compilation stay sound.

Under cargo check, a dependent runs to completion on early metadata alone. Under cargo build, it does its analysis on early metadata and waits for the full metadata just before code generation, and a crate that links also waits for rlibs just before linking. The waiting is implemented with locks, and the tokens that limit how many compilations run at once come from cargo's jobserver, which is not touched here: rustc only announces the pause and the resume to the build tool. If the upstream crate fails or crashes, the operating system releases the lock, and the waiting side obtains it without the file being there and stops with an error. The document states that the crate graph has no cycles, so waiting cannot deadlock.

Patch Composition Across rustc and Cargo Components

According to patches/README.md, the repository is a commit series: six commits for rust-lang/rust and three for rust-lang/cargo. Each commit builds on its own and passes the repository's own checks, which are fmt and tidy, the formatting and style checks of the Rust repository. The table below summarizes that document. A commit series is a stack of commits that can be reviewed one at a time, and readiness.md lists it among the things that put the code in the shape upstream expects.

To try it yourself, follow the order in the README. First run the script that checks out rustc and cargo, applies the patches and builds both.

scripts/setup.sh    # check out rustc + cargo, apply the patches, build both

Then, in any Rust project, run with the patched rustc and cargo specified.

RUSTC=/path/to/headstart/rustc/build/host/stage1/bin/rustc \
                      /path/to/headstart/cargo/target/release/cargo check -Zheadstart   # or build

It can also be turned on with CARGO_UNSTABLE_HEADSTART=true or with [unstable] headstart = true in .cargo/config.toml. The README explains that without it the patched cargo behaves like upstream, so the same binaries give a fair baseline. One caution, which the results document records, is that a rustc-wrapper that buffers rustc's output until it exits, as sccache does, hides the early-metadata notification from cargo, and then nothing starts early.

Empirical Analysis of 16-Core and 4-Core Benchmark Results

The parallel front end, enabled with -Zthreads=8, spreads a crate's analysis over up to 8 threads inside one rustc process. Those threads take tokens from cargo's jobserver, so the whole build still runs no more things at once than it has jobs, and the results document says the feature is nightly-only and off by default. The measurement conditions in the results document are these. Clean builds are timed with scripts/bench.sh, alternating headstart off and on with the same patched rustc and cargo, and the tables give medians. The 16-core system is an AMD EPYC 9554P running 16 jobs, with 3 runs for each of the 13 real projects. The 4-core system is a Claude Code container running 4 jobs. The document says that another user's jobs kept the load average of the VM at 3 to 5 during the 16-core runs, and that because off and on runs share that load, the savings can be compared even though absolute times may be a little higher.

A workspace is a set of crates built together, and a deep workspace is one whose own crates depend on one another in a long chain. On the 13 projects at 16 cores with the default front end, the README is right that none became slower. That statement is limited to the default front end. In the table with the parallel front end (-Zthreads=8) turned on as well, there are the three results of -1% to -2% shown above. The results document treats those three as draws within noise, since their run ranges overlap. The parallel front end already covers some of the ground that headstart covers: rust-analyzer's check goes from 90 seconds to 40–42 seconds with either of the two turned on, and to 30 seconds with both.

The 37% that the README quotes for codex-rs is the value of one clean build per mode recorded with cratebank on 16 cores. The results document says that under samply, in this recording, the builds took 511 seconds and 323 seconds, which is about 37%. It is a separate measurement from the 38% median of 3 runs in the same section, and neither should be mistaken for the other. The 14% for codex-rs check on 4 cores is likewise from another system and commit (57a38c1), so these cannot be put in one row. The size of the gain follows the idle cores that a build used to leave. rust-analyzer and polars averaged about 3 compilations running at once out of 16 slots without headstart, and 6 to 7 with it. By contrast, wide builds that end in one big crate gain little: zola's minify_html_common alone takes 81 seconds because of generated tables, and headstart can start a crate earlier but cannot split it.

In the 21 multi-crate rustc-perf benchmarks (16 cores, 5 runs, current version), the savings of cargo build range from 37% for serde_derive-1.0.219, 35% for eza-0.21.2 and 34% for ripgrep-14.1.1 down to 6% for encoding. The results document names proc-macro chains (serde_derive, clap_derive) and the binaries at the end of the dependency graph, which no longer wait for every rlib to finish before they start, as the main place where the gain in build comes from.

Operational Trade-Offs: Discarded Work and Memory Overhead

The costs that the risk section of design.md and the results document describe are as follows.

  • Errors surface a little later: a crate's own body errors come after the early write, the step in which rustc writes the early metadata file once the interfaces have been checked. Across the 280 crates in cargo-0.87.1's build that write early metadata, the delay was 4 ms at the median, 34 ms at p90, 249 ms at p99 and 532 ms at the maximum, where p90 and p99 mean that 90% and 99% of the crates were at or below that value. This was measured on the first, check-only version and has not been measured again after later changes. The document says this delay was one of the two reasons the 2019 attempt (rust-lang/rust#64112) stopped.
  • Discarded work and output: if a crate fails, the work its early-started dependents have done is thrown away. Cargo reports a unit's output only after all its dependencies have finished cleanly and drops it if any fails, so the diagnostics and the exit status stay the same as today. What can differ is output that already depended on timing, such as progress lines and the order of JSON messages across crates.
  • Memory: more compilers are alive at once, and paused ones stay resident. Cargo does not yet cap the number of paused compilers. Peak memory was measured only on the first, check-only version, and it ranged from -4% to +39% (nalgebra, from 0.76 GB to 1.05 GB).
  • Contention for job slots: a resumed compilation does not wait for a free job slot, which is the right to run one more job under cargo's limit on parallel jobs. When it was made to wait, it competed for tokens with the work started in its place and the critical path starved. Because headstart keeps more compilations running at once, the critical path can become slower on a saturated machine, and the document says cargo does not yet adjust its scheduling for that. The readiness document reports 3 to 7% more rustc CPU time on 4 cores for bevy and typst.
  • Incremental compilation: in an incremental cargo check after editing one function body, codex-rs was 16% faster (codex-core from 28.8 s to 24.2 s, codex-protocol from 61.4 s to 51.6 s), and cargo's own workspace, measured on the first, check-only version, was 6 to 8% faster. That is smaller than for clean builds, but it applies to every edit.
  • Known bug: a second incremental session of the same crate can panic with an error saying that early and full metadata disagree on the SVH. It was found on the util crate of zed and has not been fixed yet.

The results document also says that builds of real projects exposed three bugs that the rustc-perf sweeps had missed, all of which were fixed. One was a failure with the message missing optimized MIR in optimized dependencies (typst builds its dependencies at opt-level 2, and zed builds its proc macros at 3). Another was zola under -Zthreads=8 becoming 80% slower with headstart, because the step before the early write evaluated statics in a sequential loop; after the loop was made parallel, small losses on bevy, helix and lldap turned into gains, and typst's gain went from 4% to 22%. The third was cargo check --release asking early crates for MIR, which -Zearly-metadata-verify reported in 2,819 cases.

What the results document itself stresses in this list are the cases where it does not help. Builds that are already CPU-bound (the first version saved just 1% on cargo-0.87.1 on a 12-core Mac), build scripts and the C code inside them, proc macros, and single-crate benchmarks with no dependents gain nothing or almost nothing.

Path to Upstream Integration and Architectural Assessment

The README says the patches are a commit series, that each commit has a message and tests, and that they are meant to become upstream pull requests. The conclusion of readiness.md is a single line: ready for the design conversation, and for a draft PR to show with it, but not yet ready to merge. A draft PR is a pull request marked as not ready to be merged, used to show the code while the design is discussed.

  • Compiler-side procedure: the readiness document says commits 2 to 6 on the rustc side need a compiler MCP (a major change proposal, the way the compiler team approves a large change), because -Zearly-metadata is a new unstable flag and --json=artifacts gains three notification kinds. It says the MCP should state the swap invariant (before code generation, nothing may ask a dependency still loaded from early metadata a question whose answer changes after the swap to full metadata), the notification protocol and the lock files.
  • The invariant is not enforced: it is checked only by a hand-kept list of queries, and only under -Zearly-metadata-verify. One hole involving -Zvalidate-mir is already known.
  • Only cargo can drive it: the loader assumes that the rlib sits next to the .rmeta, and the waiting assumes that the dependency's compilation runs alongside on the same machine. Bazel and Buck2 run rmeta actions sandboxed or remotely, so the document says this part needs an explanation.
  • The jobserver: a resumed compilation runs without a token, so the build can go one job over its limit. Inside make -j that breaks the jobserver's contract and not just cargo's count. The document says it was a deliberate choice and needs to be defended or bounded.
  • Measurement and platforms: it has to be measured again on 16-core and 8-core machines with the current series, and memory and error delay also have to be measured again on the current version. The locks use the file locking of std, but nothing has been run on Windows, nor on macOS since the locks replaced polling. Only Linux has been run.

In the Hacker News thread, the submitter, knuckleheads, wrote that this specific set of changes will not get in because it is LLM written with little to no thinking through of the broader design, while adding the hope that something like it shows up sometime. That is one person's remark on a community board, not the position of the compiler team. The evidence for correctness that the document puts forward is 52 of the 53 benchmarks passing in both modes, identical diagnostics across 312 real-project builds, and a run with -Zearly-metadata forced on for every UI test (the compiler's end-to-end tests, which compare compiler output with expected text), in which 22,168 tests passed and 4 failed, with only timing-dependent output differing.

What Was Not Verified

  • The official reaction of the compiler team and the cargo team, and whether the MCP has been submitted. The submitter in the Hacker News thread says he pasted what he had posted on the Rust Zulip, the chat platform that the Rust teams use, but that post and the team's reply could not be confirmed.
  • Peak memory and error delay figures on the current version, which would show how much the extra resident compilers and the earlier write actually cost today. The values the documents cite are from the first, check-only version.
  • Headline figures re-measured on 16 and 8 cores with the current series. The readiness document says the 16-core figures predate the last fixes.
  • How the current lock implementation behaves on Windows and macOS. According to the documents, only Linux has been run.
  • How the compiler team has actually assessed this design.
