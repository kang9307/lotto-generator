The trigger — comprehensive AI security inspection from servers to agents

As generative artificial intelligence moves beyond single-prompt conversational interfaces into distributed model serving infrastructure, Model Context Protocol (MCP) connectors, autonomous agent skills, and complex multi-agent workflows, the surface area for security exposure has multiplied. Traditional web application security scanners frequently struggle to inspect inference-specific network endpoints, detect agent tool misuse, or evaluate prompt jailbreak resilience.

In autumn 2026, Tencent Zhuque Lab, a dedicated security research unit within Tencent Security Platform Department, open-sourced AI-Infra-Guard (A.I.G). Distributed under the permissive Apache-2.0 license, this red teaming platform was specifically engineered to enable enterprise internal teams to conduct end-to-end self-examinations across the entire AI technology stack.

Technical communities including GeekNews highlighted the platform's reported breadth, noting support for 146 AI components, over 2,000 CVE matching rules, and automated agent workflow evaluations. However, security professionals must evaluate beyond headline metrics: they must understand what each inspection layer actually checks, what falls outside its diagnostic boundaries, and what architectural safeguards are required to operate the scanner safely.

Five inspection layers of AI-Infra-Guard and their diagnostic scope

The architecture of AI-Infra-Guard divides the AI operational stack into five discrete inspection layers, assigning specialized scanning engines and distinct input formats to each. The five core functional pillars documented in the repository encompass AI infrastructure vulnerability scanning, MCP server scanning, agent skills auditing, agent runtime workflow evaluation, and LLM jailbreak / model verification.

The table below summarizes the target environment, inspection mechanisms, and inherent boundaries across the five diagnostic layers as documented in official materials.

As demonstrated in the comparison table, each layer relies on distinct diagnostic techniques, and clean results in one layer do not guarantee security in another. A model server free of known infrastructure CVEs may still execute a poisoned MCP tool, and an LLM with high jailbreak resistance may still misuse privileged agent tools under unexpected inputs.

Layer 1: Live AI service fingerprinting and known CVE matching

The first layer, AI Infra Scan, targets active inference engines and orchestration frameworks running on network endpoints. Operators provide the live IP address and port (such as Ollama on port 11434, vLLM on port 8000, or ComfyUI on port 8188), and the scanner examines HTTP response headers, service banners, and endpoint behavior to identify the running software component and its exact version.

  • Target component coverage. In release v4.6.0, the platform supports over 146 AI components, encompassing vLLM, Ollama, ComfyUI, n8n, LangFlow, llama-cpp, and MLflow.
  • CVE matching rules. Identified version strings are compared against an internal database containing over 2,000 CVE rules to determine if the target running version is susceptible to published vulnerabilities.
  • Non-destructive inspection. The scanner performs signature-based fingerprinting rather than executing destructive exploit payloads against the target server.
  • Operational precautions. When scanning broad network CIDR blocks, the diagnostic traffic can saturate active inference nodes, requiring operators to restrict scans to authorized staging instances.

The fundamental constraint of this layer is that it matches only against documented CVE signatures. Custom-compiled binaries, unpatched zero-day vulnerabilities, or insecure exposed network configurations absent from the rule database cannot be identified through banner matching alone.

Layers 2 and 3: Static source analysis for MCP servers and Agent Skills

The second and third inspection layers address the tool ecosystem that bridges language models with operating systems and external services. Because Model Context Protocol (MCP) servers and Agent Skills frequently hold broad permissions to read files, execute shell commands, and initiate outbound web requests, they represent critical supply chain attack vectors.

  • Input format characteristics. Instead of connecting to active services, these scanners accept remote GitHub repository URLs or local compressed source archives as input.
  • Static pattern and bytecode inspection. Scanners detect hardcoded API keys, command injection vulnerabilities, and attempts to evade static filters via compiled .pyc bytecode smuggling.
  • SkillTrustBench taxonomy alignment. Findings are categorized according to the T01 through T09 threat taxonomy defined by Tencent Zhuque Lab in SkillTrustBench, covering tool poisoning, privilege escalation, and unauthorized network data exfiltration.
  • Standalone CLI for pipeline integration. Beyond the web interface, the project provides standalone CLI utilities such as aig-skill-scan (available on PyPI) and mcp-scan, enabling automated security verification within CI/CD pull request workflows.

Like all static code analysis, these layers face inherent boundaries. They cannot fully detect runtime payload delivery, dynamic code evaluation, or indirect prompt injection where benignly structured tool descriptions mislead an agent during conversational execution.

Layers 4 and 5: Agent workflow runtime auditing and LLM jailbreak evaluation

The fourth and fifth layers examine the dynamic execution phase where models and agents process untrusted inputs in real-world environments.

  • Agent workflow auditing (Agent Scan). For multi-agent frameworks such as Dify and Coze, this engine simulates agent-to-agent task handoffs. Built on research benchmarks including RogueHandoff-20 and FORGE-Bench (arXiv:2609.11024), it assesses whether an autonomous agent violates operational constraints, misuses privileged tools, or leaks sensitive context during execution.
  • Jailbreak resilience evaluation. Operators connect target LLM API endpoints and execute standardized attack datasets including Many-Shot, PAIR, GOAT, and ActorAttack to quantitatively measure the defensive rate of safety guardrails against adversarial prompts.
  • Black-box API relay auditing (Model & API Checker). For third-party proxy relays, the scanner dispatches multi-probe behavioral fingerprints to verify whether the downstream provider is surreptitiously substituting contracted frontier models with cheaper alternatives or exhibiting backdoor response anomalies.

While dynamic benchmarking quantifies defensive posture, high scores against historic datasets do not guarantee absolute protection against novel adversarial strategies. Architecture, standalone CLI utilities, and deployment procedures

AI-Infra-Guard adopts a modular architecture separating its unified web dashboard from specialized, lightweight CLI utilities, allowing organizations to select deployment models that match their automation infrastructure.

The unauthenticated design warning and internal network isolation

The most critical architectural constraint for security engineers to recognize is stated explicitly under the installation notes in the official README:

Note: The AI-Infra-Guard project is positioned as an AI red teaming platform for internal use by enterprises or individuals. It currently lacks an authentication mechanism and should not be deployed on public networks.

The documentation makes clear that the web dashboard lacks built-in session authentication, role-based access control, or user credentials. Exposing this interface to the public Internet introduces severe operational hazards.

  • Weaponization of scanner infrastructure. Unauthorized external actors could access the unauthenticated dashboard and launch non-consensual port scans against arbitrary corporate network ranges.
  • Exposure of diagnostic intelligence. Internal model server inventories, active port maps, and detailed vulnerability scan reports would be readable by any external visitor.
  • Credential exposure. Proprietary LLM API keys entered by administrators for jailbreak or relay checking could be extracted in plain text from the unauthenticated interface.
  • Strict private network isolation. The platform must run exclusively within enterprise intranets, isolated VPC subnets, or behind management VPNs. Any external exposure requires placing reverse proxies with mTLS or corporate single sign-on (SSO) ahead of the dashboard.

Furthermore, red teaming audits must be strictly confined to infrastructure, models, and codebases owned or explicitly authorized in writing. Transmitting diagnostic probes against third-party systems without permission carries severe legal and regulatory liability.

Blue team perspectives on practical utility and structural limitations

For defensive security engineers (blue teams), integrated platforms like AI-Infra-Guard provide significant baseline utility by consolidating disparate AI assets into a single inventory and rapidly identifying obvious hygiene lapses. As discussed in Tencent BrowserSkill Analysis: Permission Boundaries of Browser Agents 2026, strictly bounding tool privileges is the foundational prerequisite for secure agent deployment.

Nevertheless, defenders must remain cognizant of structural limitations when incorporating scanner results into risk management programs.

  • Blind spots in signature databases. While 146 components and 2,000 CVEs represent substantial coverage, the rapid iteration of open-source AI tooling means newly discovered vulnerabilities lag behind repository rule updates.
  • Static analysis false positives and negatives. Source code pattern matching may flag benign development scripts while failing to parse obfuscated logic or dynamically fetched secondary payloads.
  • Quantitative illusions in jailbreak scores. High resilience scores against historical benchmark datasets do not equate to universal immunity against novel prompt injection techniques.
  • Defense-in-depth requirements. A vulnerability scanner is a diagnostic gauge rather than a protective shield; robust security requires network segmentation, least-privilege tool execution, and runtime output filtering.
  • Rule synchronization hygiene. Because the utility of the tool diminishes as rules age, organizations must maintain recurring synchronization schedules for the rule directories (data/vuln/, data/mcp/).

Automated red teaming platforms serve effectively to eliminate low-hanging fruit, but resilient AI infrastructure ultimately depends on rigorous architectural containment and least-privilege operational design.

What could not be confirmed

  • Detailed feature differences and invitation criteria for the online Pro version (aigsec.ai), as access requires an invitation code and its backend engine differences are not detailed in open documentation.
  • The complete raw dataset and live leaderboard scores for SkillTrustBench on matrix.tencent.com, which could not be directly fetched; analysis is limited to the T01-T09 classification documented in the repository.
  • Potential dependency version conflicts when building the scanner directly on bare-metal Linux or Windows hosts outside Docker containers.
  • The exact percentage of the 2,000+ CVE rules that correspond to critical severity ratings (CVSS 9.0 or higher).
  • Support and compatibility coverage for proprietary managed AI cloud platforms (such as AWS Bedrock or Google Cloud Vertex AI) outside standard self-hosted servers.
