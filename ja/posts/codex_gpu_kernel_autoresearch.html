「232倍速くなった」の読み方 - 探索ループで性能を自動最適化するときの成立条件

倍率は分母が決め、ループは判定器が決める

2026年8月16日 開発・インフラ

序論: 倍率より先に分母を問え

性能改善の記事を開くと、見出しには倍率が刻まれている。232倍、40倍、3.5倍。だが倍率は分子と分母からなる値であり、見出しに残るのは分子だけだ。何に対しての値かが抜ければ、その数字は大きさだけあって意味がない。

この区別が特に重要になったきっかけがある。近ごろ性能最適化を人がアイデアを出す仕事からループが候補を吐き出す仕事へ置き換える試みが増えている。コーディングエージェントに目標指標と検査器を渡し、数百から数千回まわす方式だ。こうしたループが生む数字は人が手でチューニングした数字より大きく出やすいが、その理由のかなりの部分は性能向上ではなく分母の選択とルールの構造にある。

この記事が扱うのはそのループだ。自動探索で性能を最適化するというとき何が揃っていればそれが成立するのか、各段階で何が壊れるのか、そしてこの方式がどこまで移り、どこからは移らないのか。

発表された性能数値を検証可能な断片に割る一般的な手順はAI が一か月で二年分より多くのバグを修正した - その発表を検証可能な形に分解するで、測定衛生そのものはMacでローカル LLM が遅い本当の理由 - GPU を使っているか確かめて有効にする方法で扱ったのでここでは繰り返さない。ここで集中するのはループが回るための条件である。

1. 「232倍」は何に対する値か - ベースラインが倍率を作る

題材にするのは、バッチ正方行列のQR分解カーネルを自動探索で最適化した個人の記録だ。原文が明かした条件から整理すると次のようになる。

  • 課題: バッチ正方 compact-Householder QR 分解の実装
  • ハードウェア: Modal 上の NVIDIA B200
  • 入力: FP32 のバッチ正方行列。n = 32, 176, 352, 512, 1024, 2048, 4096。512 が中心
  • 順位指標: 正当性検査を通過した提出のうち、複数の形状と条件数ケースにわたる実行時間の幾何平均
  • ベースライン: torch.geqrf 経路の約 419,000 マイクロ秒
  • 最終: 1,805 マイクロ秒。232倍はこの二つの比である
  • 文脈: 14日間で 1,500 回以上の提出、183名中 12位

注目すべきは最後の二行だ。同じ記事が別の分母も併記している。初期の追跡値が 108,803 マイクロ秒で最終が 1,805 マイクロ秒なので減少率が 98.34% だという記述がある。この分母を使えば同じ成果物が約60倍になる。そして 183名中 12位ということは、同じルール上でより速い提出が十一個あったという意味だ。

倍率三つが同じコードから出てくる。232倍、60倍、そして一位に対しては1より小さい何らかの値。何が変わったのか。コードは一行も変わっておらず、分母だけが変わった。

(教科書的ループ、最適化なし)		「最適化をした」という事実そのもの。性能の情報量はほぼない分母がいくらでも遅くなりうる。下限がないこの参照を実際に使う人がいるのか

今回の事例の分母は二行目に当たる。PyTorch の文書は torch.geqrf をLAPACK の geqrf を直接呼ぶ低水準関数だと自ら記している。つまりベースラインは、コンテストの条件であるバッチ正方・特定のサイズ集合・FP32 を狙って用意された実装ではなく一般経路だ。バッチQRをライブラリ呼び出しで処理するときバッチ次元がどう扱われるかによって、分母は大きく変わる。

引用するときの最小形式。倍率だけを持ち出さず、四つを添えること —ベースラインが何か、どのハードウェアか、入力サイズと分布が何か、どう測ったか。この四つのうち一つでも原文になければ、その倍率は「条件が未確認の値」である。今回の事例で原文が明かしたのは前の三つまでで、ウォームアップ回数・反復回数・クロック固定の有無といった測定手順は書かれていない。それらの項目は10章にまとめた。

2. 自動探索が成立する三つの条件

ループを付けられる問題かどうかは分野ではなく構造が決める。条件は三つで、三つとも必要だ。

2.1 正当性の判定が機械的に可能であること

候補が正しいか誤っているかを人の介在なしに、終了コード一つで答えられなければならない。これがなければループは何を昇格させればよいか分からない。「それらしいコード」を作ることと「正しいコード」を作ることはまったく別の問題であり、その間を分けるのが判定器だ。

ここで重要なのは判定器の厳しさである。判定器が緩ければ探索はその緩さを見つけ出す。最適化器は仕様を尊重せず目的関数を最適化するからだ。機械が検証できるものとできないものの境界そのものはLLMの回答で機械が検証できるものとできないもの - 検証ハーネスが引いた境界線で整理した。

2.2 測定が再現すること

同じコードを二度測って値が大きく揺れるなら改善か雑音かを区別できない。このときループは雑音を追ってさまよう。偶然よく出た候補が昇格し、次の世代はその候補を親にして誤った方向へ伸びていく。

だからループを付ける前に必ず測るべき値が一つある。ノイズフロアだ。何も変えずに同じベンチマークを十回まわし、その振れ幅を見る。振れ幅が3%なのに候補が2%の改善を出したなら、それは改善ではない。

2.3 探索空間が表現可能でサイクルが短いこと

候補がコードとして書けなければならず、生成から測定までの一周が十分に短くなければならない。サイクルが30分なら一日に四十八回だ。その程度では探索と呼べるものは回らない。今回の事例で14日に1,500回以上が出たということは、一周が分単位以下だったという意味である。

  • 探索空間は連続的であるほどよい。タイルサイズ・アンロール係数・ステージ数のように少しずつ動かせる軸があってこそ局所改善が積み上がる
  • 候補どうしの独立評価が可能でなければならない。前の候補が次の候補の測定を汚染してはいけない
  • 失敗が安くなければならない。コンパイル失敗は秒単位で終わるのが望ましい

3. GPUカーネルがこの条件を特によく満たす理由

数値カーネルは右の三条件をほぼ理想的に満たす。だから自動探索の成功例はこの分野に集まる。理由を一つずつ見ていくと、他の分野へ移すとき何が抜けるのかも同時に見えてくる。

  • 正解が数学で定義される。QR分解なら、元の行列がQRとして再構成されるか、Qの転置とQの積が単位行列に近いか、Qの転置と元の行列の積がRに近いか — この三つの性質で終わる。原文に記された採点器もハウスホルダー表現からQを復元したうえでこの三つを確認する方式だった
  • 参照実装がすでにある。ライブラリの結果と照合すればよいので、正解を別途作る必要がない
  • 出力が数値配列である。比較はノルム計算一回で終わる。「近いかどうか」を人が見る必要がない
  • 失敗が騒がしい。コンパイルエラー、メモリアクセス違反、NaN — 大半の失敗は静かに通り過ぎない
  • インターフェースが狭い。入力テンソルが入って出力テンソルが出るだけだ。グローバル状態も副作用もないので、検証範囲が関数一つに閉じる
  • 測定単位がマイクロ秒である。一周が短いので反復が成立する
  • 改善余地が大きい。メモリ階層・タイリング・テンソルコア・融合のように触れる軸が多く、それぞれが性能に実際に大きく効く

最後の項目が特に重要だ。探索は改善余地のある場所でのみ意味を持つ。すでによくチューニングされたコードにループを付ければ、数百回まわしても数%しか出ない。カーネル実行がGPUの中で実際にどんな段階を経るのか、その段階ごとにどの軸が性能を左右するのかはCUDAカーネルを実行するとGPU内部で何が起きるのか — ステップ別完全解析で扱った。

4. ループの構造 - 生成・コンパイル・検証・測定・フィードバック

ループの骨格は単純だ。重要なのはどの段階からどんな情報が次の段階へ渡るかである。

# 目的:  minimize  geomean_runtime(cand)
# 制約:  check(cand) == PASS

beam = 現在の上位候補 3~5個          # 単一の最良ではなく複数の系統を維持する

while 予算が残っている間:
    parent     = beam から一つ選ぶ
    hypothesis = 生成器(parent.src, parent.profile, 失敗ログ)
    src        = 仮説をコードとして具体化する

    ok, log = compile(src)
    if not ok:
        record(FAIL_COMPILE, log);   continue      # 最も安い失敗

    ok, err = check(src)                           # A≈QR, QᵀQ≈I, QᵀA≈R
    if not ok:
        record(FAIL_CORRECT, err);   continue      # 正当性不足はここで死ぬ

    t = benchmark(src)                             # ウォームアップ後に反復測定、幾何平均

    if t < parent.t:
        promote(src, t); beam = 更新(beam)
    else:
        mark_negative(hypothesis.family)           # 系統単位で陰性を記録

    parent.profile = profile(src)                  # 次の仮説の入力になる

この骨格で抜け落ちやすいのが最後の行だ。プロファイル結果が生成器に戻らなければ、これは探索ではなくくじ引きである。次の候補が前の候補の関数であってこそ探索と呼べる。今回の事例でもプロファイリングツールへのアクセスをループの中に入れ、候補ごとにプロファイルを取ってその結果を比較する方式が使われた。

二番目に重要な行は beam だ。現在の最良を一つだけ抱えて改善すると単一の山登りになり、一つのアイデア系統が局所的に悪い結果を出した瞬間にその系統がまるごと捨てられる。原文の著者もビームを最初から置くべきだったという趣旨の回顧を残している。局所的な陰性結果が有用な材料を早期に殺さないよう防ぐ装置だ。

5. 段階ごとに何が壊れるか

ループは五つの段階すべてで異なる形で故障する。故障の性質が違うので、防御も違わなければならない。

段階代表的な失敗どう現れるか防御
候補生成同じアイデアの変奏の繰り返し。局所最適に捕まる改善幅がゼロに収束し、パラメータの数字だけが揺れ続けるビーム維持、アイデア系統のタグ付け、より強いモデルへの相談、ドメイン知識の注入
コンパイル存在しない組み込み命令、型不一致、ハードウェア世代が未対応の命令即座に失敗する。最も扱いやすい失敗だ失敗ログの原文を次のプロンプトへ戻す。対象アーキテクチャを文書で固定する
正当性検証許容誤差の内側で静かに精度を削る検査は通るのに、条件数の悪い入力でだけ誤る病的ケースを検査集合に含める。誤差余裕を合否ではなく連続値の指標として併記する
ベンチマークウォームアップ・キャッシュ・クロック変動のせいで雑音が改善に見える再測定すると順位がひっくり返るウォームアップの分離、反復測定と中央値、同一条件での再測定、ノイズフロアとの比較
フィードバックプロファイルなしにテキストの推測だけで次の仮説を作る根拠のない仮説が繰り返され、同じ失敗を踏み直すプロファイラをループに組み込む。失敗ログを系統別に蓄積する
目的定義指標が実際の目的からずれるリーダーボードは上がるのに実ワークロードは速くならない入力サイズと分布を実運用に合わせる。指標を一つではなく集合にする

最後の行が今回の事例で実際に現れた形が興味深い。原文には上位のカーネルが入力分布を検出して利用したという記述がある。n が 512 と 1024 の場合、入力が密・クラスタ・階数不足・混合といった複数の分布で与えられたのだが、速いカーネルは分布を判別する検出器を入れてそれぞれに合う経路を通ったというのだ。

これはルールの内側では合法であり賢い。ただし読む側が知っておくべきことがある。そのカーネルを自分のデータに持ってきてもその倍率は付いてこない。最適化されたのはカーネルではなく、カーネルと採点入力の組み合わせだからだ。

6. ベンチマークの罠 - 雑音を改善として数えないために

自動探索は測定を数千回行う。だから測定誤差が人手でやるときよりはるかに高くつく。一度誤って測った値が親になり、次の数百候補の方向を決めてしまう。

罠何が起きているか症状最小限の防御
ウォームアップなしカーネル準備、メモリ確保、遅延初期化の費用が初回に集中する最初の値だけ突出して大きく、以降は安定しているウォームアップの反復を測定から除外する
キャッシュ状態の固定同じ入力を繰り返し、キャッシュが温まった状態でだけ測るベンチマークはよいのに実運用が速くならない入力のローテーション、キャッシュ無効化、実運用のアクセスパターン再現
クロック・電力の変動ブーストとスロットリングのせいで同じコードが違う値を出す測定順序によって順位が変わるクロック固定、あるいは順序シャッフル後の反復測定
非同期の未同期CUDA 呼び出しの多くは非同期なので、カーネルが終わる前に時計が止まるありえないほど速い値が出るCUDA イベントで測るか、CPU 時計を使うなら同期後に停止する
入力分布の偏り検査入力が実運用の分布を代表していないその分布にだけ合う候補が勝つ分布を複数置いて幾何平均で合算する。最悪ケースも併せて見る
精度低下の誤認精度を下げて速くなったものを最適化として数える速度は上がり、誤差余裕が静かに縮む許容誤差を明示し、合否とは別に実際の誤差をログに残す

非同期の項目はベンダー文書が直接警告している箇所だ。NVIDIA の CUDA C++ ベストプラクティスガイドは、多くの CUDA API が作業が終わる前に呼び出しスレッドへ制御を返す点を指摘したうえで、CPU タイマーで正確に測るには cudaDeviceSynchronize() で同期する必要があると記す。同時にイベント API がタイムスタンプの記録とミリ秒単位への変換を提供すると案内している。ただし同じ文書は同期点がパイプラインを止めるので節約して使えとも記す — つまり測定区間を狭く取る設計が必要だ。

精度低下の項目は今回の事例のルールと直接かみ合う。原文によれば内部的に低ビット表現を使うことは許されたが、返される因子は FP32 基準の QR 検査を通過しなければならなかった。結局、精度をどこまで下げられるかを決めるのはカーネルではなく検査器の許容誤差である。検査器が緩ければ探索は必ずその緩さを見つけ出す。

7. 探索が止まる場所 - 局所最適とドメイン知識

ループがうまく回っていても、ある地点で必ず止まる。原文の著者は 3,000 マイクロ秒から 1,800 マイクロ秒へ向かう区間でモデルが局所最適に捕まったと記した。症状は果てしないパラメータの手動調整と同じアイデアの小さな変形だった。

この地点が方法論の中で最も正直な部分だ。著者が自ら挙げた上位との差の要因を見ると、性格が一つに揃う。

  • 上位の解答はライブラリ関数をより積極的に取り除いた。たとえば三角求解をライブラリに任せず自前で実装した提出があった
  • 中間行列を低い精度で常駐させたまま置けば表現の間を行き来する費用が消えるのだが、その発想を入れられなかった
  • 当該世代のテンソルコアをより深く使う最新命令を活用できなかった
  • ビームの導入が遅かった

四つのうち三つは探索で発見される種類ではなく知っている人が入れてやる種類だ。ループは与えられた空間をなめるのには強いが、空間そのものを広げる仕事は不得手である。だから自動探索を付けるとき実質的なボトルネックは反復回数ではなく初期空間をどれだけうまく定義したかになる。

実務における含意。ループに入れる前に、その問題の最適化軸を文書に書け。何を変えられるのか、各軸の値の範囲がいくらか、どの組み合わせが物理的に不可能か。この文書がすなわち探索空間であり、文書にない軸はループに見えない。反復回数を二倍にするより軸を一つ足すほうがたいてい安い。

8. 移る場所と移らない場所

この方式を他の問題に付けられるかどうかは、正解の判定が機械化されるかと測定が再現するかという二軸でほぼ決まる。

問題の型正解の判定測定の再現性探索ループの適合度
数値カーネル・数学ライブラリ機械的(数学的性質)高い非常に高い
圧縮・シリアライズ形式機械的(往復の一致)高い高い
ビルド・テストのパイプライン時間機械的(成果物が同一・テスト通過)中(共有ランナーの雑音)中
クエリプラン・インデックス調整部分的(結果集合が同一)中(データとキャッシュに依存)中
一般的なアプリケーションコードテストのカバレッジの分だけ低~中低い
UI・インタラクション設計機械的判定は不可—できない
アーキテクチャ・設計の選択機械的判定は不可—できない

できない側の共通点は一つだ。正解が関数として書けない。良い画面、良い設計、面白いゲームには合否を分ける判定器がない。無理に点数を作れば、その点数が目的になって元の意味が消える。クリック率を目標にすればクリックを誘う画面が勝ち、コード行数を目標にすれば行が短いだけのコードが勝つ。仕様に書けない目標を自動化工程に入れたときどこまで効いてどこで止まるのかは「面白さ」は仕様に書けない - AIが効くゲーム開発工程と効かない工程で扱った。

中間帯の扱い方は決まっている。判定可能な部分だけを切り出してループに入れ、残りは人が見る。たとえばクエリ調整なら結果集合の同一性は機械が見て、インデックス追加が書き込み性能に及ぼす影響は人が判断する。大きな変更を段階に割り、各段階にゲートと中止基準を掛ける方式はAIエージェントで大規模コード移行を行う - 分割・ゲート・中止判断で整理した。

9. 自分のコードベースに探索ループを付けるには

順序が逆になっている場合がほとんどだ。エージェントを先に付けて検査器を後で作る。するとループは検査器の穴を最適化する。順序は判定器 → 測定 → ループである。

9.1 着手前のチェックリスト

  1. 最小化する値を一行で書けるか。単位まで含めて
  2. 正解の判定をコマンド一つで回せるか。終了コードが 0 と 1 に分かれるか
  3. その判定に許容誤差があるならその値を数字で書いてあるか
  4. 検査入力の集合が実運用の分布を代表しているか。病的ケースとエッジケースが入っているか
  5. 同じコードを十回測ると振れ幅は何%か。この値を知らなければ改善の判定ができない
  6. 生成から測定まで一周が何分か
  7. 失敗は騒がしいか静かか。静かな失敗があるなら、まずそれを騒がしくしなければならない
  8. プロファイルの成果物をループが読める形で取り出せるか
  9. 昇格基準と中止基準があるか。いつやめるかがなければ予算だけ燃やす
  10. 計算資源と費用に上限が掛かっているか

9.2 順序どおりに付ける方法

  • 第1段階 — 判定器を先に作る。既存の実装を参照に置き、合否だけを答えるスクリプトを作る。このときわざと誤った実装をいくつか入れて判定器が捕まえるか確認する。この回帰試験を飛ばすと判定器を信じる根拠がない
  • 第2段階 — ノイズフロアを測る。変更なしで十回測って振れ幅を記録する。以後すべての改善判定はこの値の上でのみ行う
  • 第3段階 — サイクルを縮める。失敗が遅れて現れる順序をひっくり返す。コンパイル → 正当性 → 性能の順で、安い検査が前に来るようにする
  • 第4段階 — 軸を文書に書く。変えられるパラメータと範囲、禁止する組み合わせを明示する。これが探索空間だ
  • 第5段階 — そこでようやくループを付ける。最初からビームを置き、プロファイル結果を戻す
  • 第6段階 — 昇格した候補を実運用条件で測り直す。ベンチマークで勝ったこととワークロードで勝ったことは別の出来事だ

費用の軸も先に押さえておくほうがよい。今回の事例で著者が明かした構成は商用コーディングモデルの購読二つと GPU 実行クレジットで、14日間に 1,500 回以上を提出した。原文にはワークスペースの実行クレジットが尽きたことがあるという言及もある。ループのボトルネックはアイデアではなく実行予算になりやすい。AI の成果物を人の手ではなく工程で検収する枠組みそのものはAI生成物の検査体制を作る - 文法チェックが見逃すもので扱った。

10. 確認できなかったこと

この記事は当該カーネルを再現していない。本文の数値はすべて原文に記された値であり、以下の項目は原文からは確認できない。

  • 正当性検査の数値的な許容誤差。検査項目の三つは明かされているが、閾値がいくらかは書かれていない
  • 測定手順の詳細。ウォームアップ回数、反復回数、タイミングがイベントベースか、クロック固定の有無が明示されていない
  • ベースラインの実装詳細。torch.geqrf 経路がバッチをどう処理したか、ベースラインの測定が最終提出とまったく同じ条件で行われたかは確認できない
  • 一位の記録とそれに対する倍率。12位という順位はあるが上位記録の値はない
  • サイズ別・条件数別の個別数値。公開されているのは幾何平均だ
  • 実際にかかった費用の総額。使用したツール構成は明かされているが最終的な支出額はない

そのため本文で 232倍を引用するときは毎回torch.geqrf 経路の約 419,000 マイクロ秒に対して 1,805 マイクロ秒、NVIDIA B200、バッチ正方 FP32、複数の形状・条件数の幾何平均という条件を添えた。条件の抜けた倍率は引用できる値ではない。

結論: ループより判定器が先だ

自動探索で性能を最適化するという話の主役はエージェントではない。判定器と測定器だ。この二つが正確で速ければ、その上に載せる探索器は何であれ相当な結果を出す。逆にこの二つが脆ければ、どれほど優れた探索器でも雑音と検査器の穴を最適化する。

GPUカーネルがこの方式の代表例になったのは、その分野が特別だからではなく正解が数学で定義され、失敗が騒がしく、一周が短いからだ。自分の問題にこの方式を移せるかと問うなら、答えは分野ではなくその三条件にある。

そして数字を読むときはいつも分母から見る。232倍と60倍が同じコードから出てくるのを見れば、倍率を大きくする最も安上がりな方法が何かは明らかだ。他人の倍率を自分の環境に持ち込めると仮定しないこと — 性能の話でこれだけ守れば、誤解の大半は消える。
