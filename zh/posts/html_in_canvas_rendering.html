把 HTML 画进 canvas 的 API，得到什么、失去什么

Chrome 实验功能 HTML-in-Canvas 解决的问题，以及 canvas 上的文字本来就在失去的东西

2026年8月20日 IT/技术

引言：canvas 上的文字为什么总觉得别扭

用过网页版设计工具或白板的人多半遇到过这种情况。屏幕上明明有字，拖动却选不中。Ctrl+F 查找说没有。开着翻译插件，唯独那一块还是原文，屏幕阅读器则整片跳过。

这不是 bug。那些字是图，不是文字。一旦被画进 <canvas>，它就变成一组着色的像素，浏览器无从知道上面原本写了什么。

Chrome 在开关背后实验的 HTML-in-Canvas 正是冲着这一点来的。它提议把真正的 DOM 元素放进 canvas，并把浏览器排版后的结果原样画到画布上。在韩国，这个功能是因为一位做 canvas 编辑器的开发者基于它写了一个小型 UI 库并分享出来才被注意到的。下面依次看：得到什么、要付出什么代价、以及今天该用什么。

这个功能到底要做什么

核心想法一句话就够。真正地对 <canvas> 的子元素做排版，再把结果画到画布表面上。

WICG 的 explainer 定义的部件主要有三个。

  • layoutsubtree 属性 — 加在 canvas 元素上，它的后代就会参与排版与命中测试。此前 canvas 的子元素连排版计算的对象都不是
  • 绘制方法 — 2D 的 drawElementImage()、WebGL 的 texElementImage2D()、WebGPU 的 copyElementImageToTexture()。指定一个元素，它的渲染结果就进入画布或纹理
  • paint 事件 — canvas 子元素的渲染发生变化时触发。它在 intersection observer 阶段之后执行，并带上发生变化的元素列表

还有两个辅助件：captureElementImage() 把元素做成可以传给 worker 的快照，面向 3D 上下文的 getElementTransform() 则把绘制变换矩阵还原成 CSS 变换。explainer 里给出的基本形态是这样的。

<canvas id="canvas" layoutsubtree>
  <form id="form_element">
    <label for="name">name:</label>
    <input id="name">
  </form>
</canvas>

<script>
  canvas.onpaint = () => {
    ctx.reset();
    const transform = ctx.drawElementImage(form_element, 100, 0);
    form_element.style.transform = transform.toString();
  };
</script>

代码很短，但最后一行把这个 API 的性格暴露无遗。drawElementImage() 返回绘制位置对应的变换矩阵，开发者再把它反过来喂回原元素的 style.transform。等于是用手把画出来的像素和真实 DOM 元素的位置对齐，至于为什么必须这么做，留到无障碍那一节再说。

名字改过一次也值得记住。最初叫 drawElement，后来改成 drawElementImage 与 texElementImage2D。这是接口尚未定型的信号。

为什么一直很难 — 像素里没有结构

canvas 2D API 是命令式的绘制表面。fillRect 并不记住一个矩形，它只是把那个位置的像素涂上颜色。fillText 也一样，字形打完之后剩下的只有颜色，既没有文本节点也没有盒子。

这是为性能做的选择。没有场景图要维护所以很轻，很适合每帧全部重画的游戏与可视化。代价是浏览器原本替文档做的事情也一并消失。换行、双向文本处理、字体回退、盒模型、事件目标判定 — 全都要自己实现。

HTML 规范也知道这个问题，所以允许在 canvas 元素内部放备用内容。麻烦在于那份备用内容和真正画出来的东西毫无关系。explainer 说的是同一件事：目前无法保证用于 canvas 无障碍的备用内容与渲染出来的内容始终一致，而且生成这种备用内容本身就很难。

于是实践中造出了绕行方案。一共三条，三条都停在同一个地方。

把 SVG foreignObject 变成图片来画

把 HTML 放进 SVG 的 <foreignObject>，再把 SVG 做成 data URL 用 <img> 加载，然后 drawImage() 画上去。借用浏览器排版引擎这一点，思路和这项提案是一样的。

  • 作为图片加载的 SVG 拿不到外部资源。网页字体和图片都得用 data URI 内联
  • 脚本不会执行，所以动态的东西一样都放不进去
  • 漏掉内联不会报错，而是字体被悄悄替换。这是开发环境与线上结果对不上的典型原因
  • 最关键的是，画出来的结果又是像素。无障碍一点都留不下

用库把 DOM 渲染重做一遍

这是 html2canvas 一类走的路：遍历 DOM 读取计算后的样式，再翻译成画布绘制指令。实际上就是用 JavaScript 重新实现浏览器渲染引擎的一部分。分析这项提案的 Codrops 文章把上限说得很清楚：因为每个 CSS 属性都得手工实现，完整的 CSS 支持根本做不到。支持列表再长，浏览器也走在前面，差距不会消失，而且这里产出的同样是像素。

用手把文字画出来

用得最多、也最费时间的办法。用 measureText() 量宽度，自己断行。短的英文标签半天就能搞定。问题在后面。

  • 中文与日文的禁则处理 — 不能出现在行尾或行首的字符规则
  • 表情符号与组合字符 — 按码位切会把字切坏
  • 阿拉伯语、希伯来语的双向文本 — 逻辑顺序与显示顺序不同
  • 字体回退 — 同一串文字中字体切换时的基线对齐

这个清单没有尽头。文字排版正是不要重造浏览器原生能力这一原则体现得最鲜明的领域。

真正想要它的理由 — 想白嫖排版引擎

把等这个功能的人的诉求归拢，会落到四类上。

  • 游戏 UI — 背包、设置界面、对话框。若在引擎内部另建一套 UI 系统，一行 CSS 就能对齐的事就得写成代码
  • 数据可视化上的标签 — 用 WebGL 画几十万个点的图表里，最费工夫的正是坐标轴标签与提示框。点交给 GPU，文字却不行
  • 地图 — POI 标签排布、多语言字体回退、让路名沿曲线流动。这正是地图渲染器要自带文字引擎的原因
  • 设计工具与白板 — 一个文本编辑框里就装着光标位置计算、选区高亮和输入法组合处理。无限画布类工具越多，这份负担也越重

共同点很清楚。他们要的是排版计算，不是绘制。浏览器里早就装着世界上被检验得最多的文字排版引擎，而 canvas 一直没有通向它的路。explainer 的动机段落说的也是同一件事：没有一个简便的 Web API 能把复杂的文字排版渲染进 canvas，结果基于 canvas 的内容在无障碍、国际化、性能与质量上都吃亏。国际化被摆在无障碍旁边这一点值得留意。对中文、日文、阿拉伯语这一侧来说，这份损失要大得多。

把文字画进 canvas 会失去什么

从这里开始才是评价这个功能时最要紧的部分。用 canvas 画 UI 是一笔交易，换来性能、交出别的东西，而交出去的那份清单比想象中长。

能力DOM 文本画在 canvas 上的字受影响的人
屏幕阅读器朗读默认可用没有视障用户
拖选与复制默认可用没有所有用户
页内查找默认可用没有所有用户
浏览器自动翻译默认可用没有外语读者
放大时重排行会重新排布像素放大低视力用户
最小字号设置会生效被忽略低视力用户
强制颜色与高对比会生效被忽略对比敏感用户
键盘焦点与 Tab 顺序默认可用自行实现键盘用户
搜索引擎收录会收录不会站点运营者

该看的不是单条，而是默认值的方向。DOM 那一列全是「本来就行」，canvas 那一列全是「自己做，或者放弃」。这不是开发者犯错才有的结果，而是正常使用 canvas 就会自动抵达的状态。

所以这个问题靠单个项目的用心解决不了。用心的团队会写备用内容，但它处在与渲染相互独立的代码路径上，时间一长就会错开。这和文档格式那边反复验证过的没有结构的产物给机器留下了什么是同一种形状的问题。

这项提案怎么处理无障碍，以及还没解决的问题

这个 API 在无障碍讨论里之所以有意思，是因为它把病因找在了双份维护上。explainer 说明用这个 API 绘制的元素会与其对应的 canvas 备用内容保持一致。要画的东西本身就是备用内容，两者错开的结构性余地因此缩小。再加上 layoutsubtree 让子元素参与命中测试，canvas 编辑器过去手写的坐标到元素的映射代码也会消掉不少。Chrome 开发者博客更进一步，写明 canvas 内的内容会暴露到无障碍树、与辅助技术兼容，并支持页内查找、复制与右键。

但不能把这读成「无障碍问题已经解决」。一手文档自己写下的限制还在，而且截至写这篇文章时，没有找到在真实辅助技术上验证过的资料。

先看 explainer 明确列出的限制。

  • CSS 变换在渲染时被忽略，却仍然影响命中测试与无障碍。这一行解释了前面例子的最后一行。若不把绘制位置喂回 style.transform，看到的位置就会和无障碍树所指的位置错开。而这道回喂是开发者可能漏掉的
  • 溢出的内容按边框盒裁切。在 DOM 里本会溢出可见的文字，到了画布上就被切掉
  • 滚动依赖 JavaScript。这是 Chrome 文档自己写明的限制，与 canvas 之外由合成器处理的滚动不是一回事。explainer 写道，滚动与动画的线程化处理正作为自动更新画布模式在考虑中 — 意思是现在还没有

还有一条没被确认的轴。文字暴露到无障碍树，与低视力用户用浏览器设置放大字号时画布内部重新排版，完全是两回事。归结起来，这项提案自动帮你接上的是无障碍树与渲染的一致，而不是 canvas UI 的整体可用性。仅此已经是更好的起点，但「画进 canvas 也没关系，无障碍交给 API」这种期待目前还没有依据。

画不出来的东西 — 隐私约束决定了 API 的形状

这个 API 带着一条乍看奇怪的限制，弄懂原因之后它就成了不可商量的条件。关键在于画布是可以被读回的表面。脚本能用 getImageData() 把像素读回来。而 DOM 会把脚本不该读到的东西显示在屏幕上，访问过的链接颜色就是典型例子。把两者直接连起来，读像素反推用户浏览记录那种老攻击就会复活。

所以 explainer 提出了允许读回的渲染这一概念，规定绘制元素图像的方法与 paint 事件不得泄露安全或隐私敏感信息。被排除的对象如下。

  • 跨源数据 — 其他源的 iframe 内容不会被画出来
  • 系统颜色 — 来自操作系统主题的颜色关键字
  • 访问过的链接信息 — :visited 样式不会体现
  • 输入法弹窗 — 输入法的候选窗口

这份清单不是留待补齐的未实现项，而是这个 API 得以存在的条件。落到实践上，烘焙进画布的 UI 里，依赖 :visited 的样式、跨源小组件、使用系统颜色关键字的组件都可能画得和屏幕上不一样。

先把标准化阶段说准。这个功能是处于 WICG 孵化阶段的提案。仓库里的文档自称是根据反馈持续更新的活文档。它没有被纳入 HTML 规范，离 W3C 推荐标准更远。

版本号是故意没放进表里的，因为各处出处写的数字不一样。在韩国介绍它的开发者要求 Chromium 146 以上，浏览器支持文档写的是 147 以上，Chrome 开发者博客则给出了另一个源试用区间与 Canary 版本。可靠的办法是在自己的浏览器里直接确认有没有这个开关。

由此只能得出一个结论。这不是能放进生产的东西。名字已经改过一次，另外两个引擎没有表态，而且只有开了开关的用户才看得见。此时把 UI 结构押上去，反而要多维护一套替代路径，当初想靠它换来的简洁也就没了。

替代方案对比 — 今天该用什么

把选项摆在同一条轴上，判断就容易了。

方式文字质量无障碍与画布像素合成今天能用吗
DOM 覆盖层浏览器原生完整保留不行可以
直接内嵌 SVG foreignObject浏览器原生大体保留有限可以
把 SVG 做成图片再画取决于内联了多少没有可以可以
重做 DOM 渲染的库取决于覆盖了多少 CSS没有可以可以
手工绘制文字取决于自己做了多少没有可以可以
HTML-in-Canvas浏览器原生与备用内容自动一致可以仅开关/试用

判断标准收敛成一个问题。这段文字需要和画布像素混合吗。

  • 不需要的话，DOM 覆盖层就是答案。图表坐标轴标签、提示框、图例、游戏 HUD、地图信息面板大多属于这一类。用绝对定位叠上去，无障碍、选中、查找、翻译全都还在，今天在所有浏览器里都能跑
  • 只有需要混合时才考虑烘焙：文字必须经过着色器、要在三维空间里获得透视、或者要接受画布滤镜与混合模式
  • 决定烘焙了，就在同一个提交里设计好无障碍替代路径。屏幕外的 DOM 副本、ARIA 属性、指向文本版的链接。打算以后再补的，多半补不上
  • 如果问题只是条目太多，在转向画布之前先看看用虚拟滚动减少 DOM 节点数的做法。转向画布很难回头

就算这个 API 正式化，上面的顺序也不会颠倒。在 DOM 覆盖层就够用的地方改用画布，那时候依旧是亏。这个功能改变的是「只能烘焙进画布」那些场景的质量，而不是该用画布的理由的范围。

没能确认的事

这篇文章只写到公开的一手资料能确认的范围。以下是没能填上的空缺。

  • 没有在开了开关的构建上用真实辅助技术做过验证。关于无障碍的表述只到 explainer 与 Chrome 文档写下的范围
  • 没能找到关于 NVDA、JAWS、VoiceOver 等各款屏幕阅读器实际朗读行为的报告
  • 没能找到答案：浏览器放大、强制颜色模式、最小字号设置会怎样体现在画出来的结果上
  • 支持的里程碑版本号各处出处不一，因此没有把任何一方断定为正确
  • 性能对比数字在任何一手资料里都没能确认。所以这篇文章里没有变快或变慢的说法
  • 没能找到 Mozilla 与 WebKit 的正式 standards position 文档。表里的「没有信号」照搬的是 Blink 进展记录中的状态
  • 没能确认中文或韩文输入法组合状态下的输入在画布内的表单元素里如何工作。explainer 只是把输入法弹窗放进了读回排除清单
  • 这个功能是否会走向正式标准无从得知。在孵化阶段收摊的提案并不少见

表现力对无障碍 — Web 平台处理这笔交易的方式

Web 起源于文档。无障碍在早期几乎是免费的，原因是内容以结构的形式表达。机器能读的形态就是人能看的形态。而提升表现力的功能，几乎总是以绕开那套结构的方式到来：插件内容、<canvas>、WebGL，以及用 <div> 做出来的假复选框。形态各异，交易相同 — 换来想要的外观，交出机器能读的结构。每一次都出现了两类应对。

  • 要求另行维护结构 — canvas 备用内容与 ARIA 属性属于这一类
  • 让平台增加自动附上结构的能力 — 让本来就带着无障碍信息的原生元素能被装扮成想要的样子

第一类效果并不好。canvas 备用内容明明写在规范里却几乎无人使用，正是这个原因；ARIA 属性与真实状态对不上的组件屡见不鲜，也是同样的道理。

这项提案引人注目之处就在这里：它选了第二条路。把要绘制的对象与暴露到无障碍树的对象绑在同一个元素上，从结构上压缩了错开的空间。当然它并不完备。漏掉变换回喂照样会错开，隐私约束与滚动处理这些窟窿也还在。即便如此，默认值是「错开」还是「一致」，差别很大。这份张力本身不会消失，但要把它交给开发者个人的用心，还是由平台来扛，是可以选择的。

结论：现在该做什么、不该做什么

这个功能正面瞄准了 canvas 开发的老毛病：把浏览器的排版引擎请进画布，取消手工维护备用内容那套双份结构。方向看起来是对的，但眼下它只是单个引擎开关背后的提案。所以该做的有三件。

  • 数一数你现在用画布画的文字。其中有多少能挪到 DOM 覆盖层。通常是绝大部分，而那是不必等这个 API 的改进
  • 如果有 canvas UI，今天就打开屏幕阅读器试试。确认哪些读不出来，三十分钟足够。这个结果就是判断要不要引入这个功能的依据
  • 在开了开关的构建上打开演示，找找手感就好。是观察不是引入。要以名字和行为都可能变的前提去看

不该做的同样明确。现在还不能上生产。而且不要按照「这个 API 来了无障碍就解决了」的前提做计划。自动接上的是渲染与备用内容的一致，而不是包含放大、强制颜色、滚动与辅助技术行为在内的整体可用性。

就算往画布上写字这件事越来越容易，需要读那些字的人能不能读到，仍然是要持续确认的事。好的 API 只是让这项确认变得轻松，并不会替你去做。
