引言：「Redis更快，为何选MySQL?」的悖论

几乎每个开发者都像本能一样记着一个命题：「Redis快，关系型数据库慢。」作为内存键值存储，Redis的响应通常比要经过磁盘的数据库更快，所以流量涌来的那一刻，我们几乎条件反射地想到Redis。然而运营全球顶级电商基础设施之一的Shopify，却朝相反方向迈出了一步。根据2026年5月12日发表在Shopify Engineering博客上的文章「We replaced Redis with MySQL for inventory reservations—and it scaled」（Emilie Noel），Shopify把支付处理期间暂时锁定库存的库存预留（inventory reservations）从Redis迁移到了MySQL。

先把范围说准确。迁移的不是整个库存系统，而是结算阶段的「预留」。库存数量的总账（inventory ledger）本来就在MySQL中，原文把问题描述为「预留与库存总账位于两个不同的系统」。即便如此，许多开发者想必还是会问同一个问题：「放着更快的不用，为什么要走向更慢的一方?」这个问题里藏着「快就是好」的假设。先说结论：Shopify的选择不是倒退，而是角色的重新定义。

库存是一种有点特殊的数据。搜索结果晚0.1秒显示，和购物车里最后一件商品在付款瞬间同时卖给两个人，是完全不同层次的问题。前者让用户烦躁一下就结束，后者则会引发取消订单、道歉与客户信任下降。本文在区分Shopify原文所述事实与本文解读的同时，拆解缓存与数据库的本质区别，以及对电商环境的启示。

本文一句话总结。 Shopify的决定不是「Redis不好」，而是「预留与库存总账必须在同一个事务之中」的判断。用原文的话说，核心在于跨两个存储的更新「无法包进单一的原子步骤（couldn't be wrapped in a single atomic step）」；吞吐量不是靠缓存，而是靠基于MySQL 8 SKIP LOCKED的设计以及对数据库连接使用的整理来保障的。

1. Shopify库存预留的规模 - 为何这个决定重要

这个决定之所以值得关注，在于Shopify的规模。据原文，Shopify支撑着美国电商的14%以上（原文："powers over 14% of U.S. ecommerce"），2025年黑色星期五，平台商家的销售额在峰值时达到每分钟510万美元，创下纪录；峰值每分钟销售额比上一年增长11%。原文写道「每一笔交易都会触及库存」，而预留会在每一次触及库存的结算中运行。

失败会发生在两个方向。按原文举的例子，往一个方向出错，两位买家会买走同一件最后的商品，商家不得不取消订单、发道歉邮件并承担客服成本；往另一个方向出错，则会把实际还有货的商品告知为售罄，商家失去本该做成的一单。原文写道，在这种规模下「任何一种失败都会迅速放大」。因此，在这种规模下更换预留的数据模型，并非技术偏好，而是重新铺设支撑结算可靠性的地基。

这正是我们应该关注这个案例的原因。一家经历过海量流量的公司，把一个多年来运行良好的快速工具，从核心预留的位置上撤了下来。这里蕴含着关于「比速度更重要的东西」的教训。

2. Redis曾用于库存预留的原因

首先要公平地指出一点。据原文，这项预留功能多年来一直运行在Redis上，原文写道「Redis很好地处理了并发（Redis handled concurrency fine）」。反倒是此前迁往MySQL的尝试失败了，因为带一个数量列的单行无法承受争用。Redis绝不是选错的工具。

2.1 压倒性的速度

Redis把数据放在内存里，不经过磁盘I/O。读写都能以极低的延迟响应，对库存扣减这类高频操作来说，这种速度很有吸引力。这是一般论，原文并未给出Redis的延迟数值。

2.2 原子操作

Redis原生提供DECR、INCR等原子计数器操作。据原文，Shopify的旧模型也是为每个商品设一个数量键，预留用DECR，释放用INCR。把库存减一的动作可以用单条命令完成，并发控制很直观。

2.3 简单的数据模型

「商品→剩余数量」本质上是键值结构，几乎完美契合Redis的数据模型。无需考虑模式设计、连接与索引，拿来就能用。早期这种简单大概提升了开发速度（本文的推测）。

总之，从「库存=快速增减的数字」的视角看，Redis几乎是理想的工具。问题在于库存预留并不只是这样。

3. Redis模型的局限 - 原文列出的三点与一般论两点

原文直接给出的理由有三点，即下面的3.1至3.3。3.4至3.5原文没有提及，是把内存存储当作总账使用时常被提到的一般性局限，属于本文的解读。它们都不是Redis的缺陷，而是使用「角色不同的工具」时产生的结构性摩擦。

3.1 两个系统之间的原子性空白（原文的核心理由）

预留在Redis中，库存总账在MySQL中。付款完成后永久扣减库存的「确认（claim）」步骤需要更新MySQL并清理Redis，原文写道这两个操作「无法包进单一的原子步骤」。视执行顺序不同，可能出现超卖（已卖出但未从总账中扣减）或少卖（总账已扣减却仍显示为已预留）。这相当于多个步骤无法作为一个整体同时成功或失败的问题，发生在两个存储之间。

3.2 无法感知多地点（原文）

据原文，Redis模型无法区分多个地点（仓库、门店）的库存。Shopify的需求中包含「只从能够履约的地点预留」这一条件。每个商品只有一个数量键，很难表达这个条件。

3.3 独立集群的运维成本（原文）

原文写道，Redis模型增加了「需要维护的独立集群的运维成本」。原文把这次切换介绍为在走向统一数据库战略（unified database strategy）的过程中出现的问题，即「MySQL能否承受同样的规模」。把所有数据放进内存会随着数据增长推高内存成本，这一点也常被提及，但原文并未把内存成本列为理由。

3.4 持久性与复制延迟（一般论 - 原文未提及）

Redis是内存存储，可以用RDB快照或AOF日志增强持久性，但视配置不同，仍会留下丢失上次保存之后写入的窗口。复制默认是异步的，故障切换的瞬间，尚未复制的写入可能丢失。对于库存这种一次不一致就会导致超卖的数据，这是有负担的特性。不过，Shopify原文并未把数据丢失或AOF、复制问题列为迁移理由。

3.5 缺少复杂查询（一般论 - 原文未提及）

库存不只是一个数字。「某仓库中低于阈值的商品」「过去24小时的库存变动记录」这类查询不断出现。Redis是键值结构，本身难以很好地支持这些连接、聚合与范围查询，只能在应用代码里补。这同样是一般论，并非原文给出的理由。

4. 为何是MySQL - Shopify选择的设计与关系型数据库的优势

原文的要点是：把预留迁到与总账相同的MySQL数据库，就能用ACID事务把一切包起来，从而「彻底消除这些失败模式（eliminate these failure modes entirely）」。MySQL（InnoDB引擎）提供的，归根结底是「不出错地处理数据的能力」。

4.1 持久性 - 一旦提交就能存活（一般论）

ACID中的D（Durability）承诺：事务一旦提交，即使服务器宕机也会被保留。InnoDB的重做日志（redo log）会先写入磁盘，因此崩溃后也能恢复已提交的扣减。这是区分缓存「可以丢的数据」与数据库「不能丢的数据」的差别。原文没有专门讨论持久性相关配置。

4.2 一件一行与SKIP LOCKED - 减少争用的设计（原文）

Shopify不再为每个商品设一行加数量列，而是为每个可售单位设一行。有10件的商品就有10行，预留3件就在一个事务中选出3行并移走。借助SELECT ... FOR UPDATE SKIP LOCKED，被其他事务锁住的行会被跳过，转而取其他可用的行，因此无需在同一行上等待，争用随之减少。

如果把所有库存都变成行，表会变得很大（原文示例：10个地点共5万件就是50万行），因此Shopify为每个商品与地点的组合维持一个上限为1,000行的池，由补充进程从总账中补足。1,000这个数值是根据闪购期间观测到的各商品、各地点峰值预留速率确定的。池一旦耗尽，预留路径会当场触发补充，并用锁确保同一时间只有一个事务在补充，防止请求蜂拥而上。原文列出的技术决策有以下四项。

  • 复合主键：最初的原型用自增ID作主键，每次预留会加两个行锁。把主键改为(shop_id, inventory_item_id, inventory_group_id, id)后，每行只需一个锁。
  • READ COMMITTED：在需要补充的空表上执行SELECT ... FOR UPDATE SKIP LOCKED时，间隙锁（包括supremum伪记录上的锁）会阻塞补充，并可能引发死锁。于是把这些事务的隔离级别从MySQL默认的REPEATABLE READ改为READ COMMITTED。
  • 统一加锁顺序：预留总是先从单位表DELETE，再向reserved_quantitiesINSERT；确认只触及reserved_quantities，从而消除了循环等待。
  • 用UNION ALL批量获取：对于包含多个商品的购物车，用UNION ALL合并预留查询，一次往返就取回所需的全部单位。

4.3 原子性 - 要么全部，要么全无

据原文，把预留与总账放在同一个数据库中，使预留与确认全程获得ACID，修复了Redis时期可能出现的一类缺陷，例如「付款成功却未确认库存」或反过来的情况。在一个事务内，只要任一步骤失败就会整体回滚，因此「库存减了却没有确认」的幽灵状态在结构上不会出现。

4.4 丰富的查询与完整性约束（一般论）

SQL可以自由表达连接、聚合与范围条件。借助外键、CHECK约束与唯一约束，数据库本身就能强制执行「库存不能为负」这样的规则，业务规则不必只交给应用。这是关系型数据库的一般特性，并非原文列出的优点。

5. 迁移的五大技术挑战 - Shopify是怎么做的

判断迁移是正确的，与真正迁移过去，是完全不同的两回事。更换运行中的巨型系统的核心存储，近乎在飞行中更换引擎。以下是原文披露的做法。

  • 零停机（Zero-downtime）：据原文，Shopify没有一次性拨动开关，而是以「影子模式（shadow mode）」让两套系统并行运行。每一笔预留都同时写入Redis和MySQL，这一期间的事实来源仍是Redis。
  • 数据一致性：由于两套系统都在运行，不存在需要迁移的进行中预留。Redis中的预留继续有效，MySQL则自行积累自己的状态。值得注意的是，这并不是先做快照再搬运的方式。
  • 性能保障：在生产环境中，吞吐量远低于目标，但P90等预留延迟尚可，CPU也未到上限。真正的瓶颈是数据库连接。团队给每条SQL加上业务流程标签（/* conn_tag:checkout_completion */），并在ProxySQL层测量各调用方的连接占用时间，结果发现是结算路径上预留以外的其他代码长时间占着连接。整理结算路径后，主（primary）数据库的读取减少了50%、事务减少了33%；多年前保守设置的InnoDB线程并发配置，也在有余量的地方调高了。在大型闪购期间，写节点CPU保持在50%以下，读节点CPU保持在16%以下。
  • 回滚安全网：在确认正确性与性能之后，才把事实来源切换到MySQL；一旦出问题，可以用紧急开关（kill switch）切回Redis。因为双写路径一直保持运行，Redis始终掌握全部预留。
  • 验证（Validation）：在影子模式下，用真实生产流量并排比较两套系统，确认MySQL能产生正确的业务结果并满足性能要求。切换按pod逐步推进，从低流量的pod开始，一直扩展到交易量最大的商家。

6. 性能取舍 - 速度 vs 正确性

这个案例常被解读为「让出速度、买下正确性」，但原文的说法略有不同。Shopify写道，迁移到MySQL后，在2025年的峰值流量中达成了高吞吐量目标。只看单次响应时内存存储往往更快，这是一般论；但对库存预留而言，真正的问题不是「有多快」，而是「有多不出错」。

原文这样写道：「这不是为了让预留变快，而是为了让它成为安全的邻居（It was about making them safe neighbors）。」预留与购物车更新、支付处理、订单创建共用一个数据库，一个耗尽连接或长时间持锁的系统会危及所有这些工作。标准是在不损害其他所有工作的数据库健康的前提下维持吞吐量。

以下是本文的解读。在一般的大规模服务中，由数据库负责需要正确性的写入、由缓存负责高频读取（库存展示）的分层结构很常见。不过，Shopify原文并没有说在MySQL前面加了Redis缓存，反而以这样一句话收尾：「如果你正为高吞吐量的互斥去找Redis、Kafka或自建的协调层，你现有的数据库可能已经足够。」

在库存里，快1毫秒的响应是值得炫耀的，但1次超卖是事故。正确性一旦崩塌，速度便失去意义。

归根结底，这个案例的平衡点是先确保正确性，再通过行设计、加锁、连接使用等周边整理把速度找回来。这并不是亏本的买卖。

7. Redis vs MySQL 决策框架

下面把在自己的项目中套用这个案例时可用的判断标准整理成表。此表是本文的整理，并非原文中的表格。核心问题只有一个：「这份数据若出错或消失，会发生什么?」

表1. Redis vs MySQL 选择标准

标准适合Redis适合MySQL
速度（低延迟）读取缓存、会话、排行榜—
持久性—库存、订单、支付
一致性—金钱交易、余额
复杂查询—报表、聚合、连接
多步骤事务—订单处理流水线
可易失数据临时队列、限流—

大多数实务结论不是「OR」而是「AND」。需要正确性的单一事实来源交给数据库，为其加速的缓存交给Redis。一旦把两个工具看作分工而非竞争，设计就清晰了。不过正如Shopify的案例所示，如果事实来源与修改它的操作分散在不同的存储中，首先要做的是把它们集中到一处。

8. 原文提到的其他案例与一般模式 - 缓存与持久存储分离

原文中出现的其他公司只有一家。Shopify表示，它是受37signals「基于数据库的负载分配」做法的启发，在MySQL上重建了预留。原文中没有其他企业案例，下面介绍的是业界广泛使用的旁路缓存（cache-aside）或直写（write-through）等一般分层模式。

典型的构成是这样的：数据的真相在关系型数据库中，为了降低读取负载，在其前面放置Redis/Memcached缓存。写入先落到数据库，再使缓存失效或更新缓存。在这种模式下，即使缓存整个被清空，原始数据仍留在数据库中，只是在缓存重新填满之前会暂时变慢。

「快的存储」与「可信的存储」是不同的角色，成熟的架构不会把两者都推给同一个工具。Shopify的库存预留迁移可以被解读为把这一原则应用到最敏感领域的案例（本文的解读）。不过，Shopify应用这一原则的方式不是增加缓存，而是把原本分散在两个存储中的预留与总账合并到一个数据库里。

9. 开发者可学到的五个教训

本文从这个案例中整理出的实务教训如下。第3条和第4条是原文直接写出的教训。

  1. 「快」不是选择标准，只是一种属性。 数据的性质（可否易失、是否必须正确）先决定工具。
  2. 把事实来源与修改它的操作放在同一个事务边界之内。 预留与总账一旦分在两个系统，就会出现只更新了一边的缝隙。缓存是副本，不是原本。
  3. 瓶颈可能不在你预想的地方。 据原文，团队花了几周优化查询与锁，真正的限制却是他们根本没在看的代码的连接使用。CPU很低而排队很长时，就去给整条路径加上观测。
  4. 重新审视旧的决定。 原文写道，五年前不可能的事（用MySQL承担这项工作）可能因SKIP LOCKED之类的新功能而变得可行；线程上限之类的经验性配置，在负载变化后也值得重新检查。
  5. 迁移成败在于验证而非技术。 Shopify也是在备齐影子模式下的双写、并排比较、紧急开关回滚与按pod逐步切换之后，才迁移了事实来源。

10. 应用于电商环境 - 对高并发市场的启示

这场讨论不止于一家公司的案例。许多电商市场频繁出现直播带货、限时特卖、秒杀这类瞬间爆发型流量。许多人同时抢同一热门商品最后库存的情形，在大型购物平台上完全可能发生。以下是本文的判断。

在这样的环境中，如果把预留与总账分放在不同的存储里，Shopify所面对的同一种原子性空白就会以超卖风险的形式暴露出来。对电商基础设施的启示如下。

  • 限时秒杀=极端并发：写入会在瞬间涌向同一行。用数据库锁策略与排队（订单等待队列）串行化，或像Shopify那样用按单位分行加SKIP LOCKED分散争用，是关键所在。
  • 准确的库存展示≠准确的库存扣减：屏幕上的库存用缓存求快，实际扣减用数据库事务求准。应把二者分开认知。
  • 退款与订正成本不容轻视：对快速客服的期待与对平台声誉的敏感度都很高，一次超卖的无形成本可能很大，投入正确性有充分理由。
  • 中小卖家工具同理：若你自建商城，应警惕只用Redis计数器管理库存的诱惑，从一开始就把数据库作为单一事实来源更安全。

11. 风险 - 「越快越好」的错觉

这个案例揭示的更大风险，在于技术选择的心理。我们很容易被基准测试的数字，也就是「X比Y快N倍」这样的句子左右。但基准测试通常不衡量「数据绝不能出错」这个条件。

速度优先之所以危险，是因为它的代价会在事后、而且是在最棘手的时刻结算。流量最集中的促销当天、节点因故障宕机的瞬间、两个存储的更新出现错位的刹那，不一致就会爆发。平时安然无事，却在最输不起的时刻崩塌。

在被「快」迷住之前，应当问的是：这份数据若消失或出错，谁、损失多少、如何损失?

成熟的工程不是炫耀快速的工具，而是诚实地衡量每份数据的失败成本，再据此配置工具。Shopify的选择可以被解读为正是这种诚实计算的结果。

12. 结论 + 可立即应用的三点

Shopify把库存预留从Redis迁移到MySQL的决定，不是一个「Redis错了」的故事，而是「预留与库存总账必须在同一个事务之中」的判断。而且原文并没有说为了正确性放弃了吞吐量，它说的是：靠按单位分行与SKIP LOCKED的设计、以及整理结算路径的连接使用，达成了目标吞吐量。正确性是不可让步的常量，速度是可以靠设计找回的变量。

最后用今天就能应用的三点收尾。

  1. 按失败成本对数据分类。 可丢失的归缓存（Redis），绝不可出错的归数据库（MySQL/PostgreSQL）。仅凭这一行标准，大多数存储决策便能理清。
  2. 库存、支付、余额以事务型数据库为单一事实来源，并把修改它的操作放进同一个事务。 若需要速度，先检查行设计、加锁与连接使用，之后再考虑缓存。
  3. 迁移存储时，先设计影子模式下的双写、并排比较与紧急开关回滚。 记住迁移的成败由验证体系而非新技术决定。

下次再冒出「Redis更快，为什么?」这个问题时，不妨再深入一层。真正的问题不是速度，而是「这份数据若出错，什么会崩塌」。

常见问题 (FAQ)

Q1. Shopify为何把库存预留从Redis迁移到MySQL?

预留在Redis中、库存总账在MySQL中，付款确认时无法用单一的原子步骤同时更新两个系统，视顺序不同可能出现超卖或少卖。无法感知多地点、以及独立Redis集群的运维成本也是原因。把预留迁到与总账相同的MySQL后，用ACID事务把它们包在了一起（Shopify Engineering，2026-05-12）。

Q2. Redis不适合库存系统吗?

Redis并不差，只是角色不同。原文也写道Redis很好地处理了并发。但当事实来源位于另一个存储时，就会出现无法一次同时修改两处的结构性局限。在读取缓存、会话、队列等以速度为核心的领域，它依然出色。

Q3. 何时应该用MySQL而不是Redis?

数据不能丢、必须准确、并需要多步骤事务与复杂查询时，用MySQL。数据可以易失、以简单键值查询和极低延迟为核心时，Redis更合适。

Q4. MySQL也能像Redis一样承受高流量吗?

据原文，Shopify依靠按单位分行、SELECT ... FOR UPDATE SKIP LOCKED、每个商品与地点1,000行的池、复合主键、READ COMMITTED以及对连接使用的整理，在2025年峰值流量中达成了吞吐量目标。一般而言，索引、连接池、只读副本与前置缓存也值得一并考虑。

Q5. 缓存与数据库有什么区别?

数据库作为单一事实来源，负责永久保存、一致性与事务；缓存是为快速再现而存在的临时副本。缓存清空只会变慢，数据库出错却会让业务崩塌。
