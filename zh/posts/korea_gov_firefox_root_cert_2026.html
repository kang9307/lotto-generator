韩国政府再次尝试将政府根证书加入Firefox - GPKI与浏览器信任的意义

把政府根重新放入Mozilla信任库的尝试 - 为何需要、过去为何被拒、应当审视什么

2026-06-16 开发/基础设施

引言：再次叩门的政府证书

韩国政府再次尝试将本国政府根证书加入Mozilla Firefox信任库的消息，在开发者圈引发关注。一句话概括：这是为了让政府域名无需另行安装证书即可在Firefox中顺畅打开的尝试。然而这句话背后，叠压着浏览器信任模型、过去被拒的经过，以及围绕浏览器信任政府运营CA含义的长期安全争论。

先把前提说清楚。本文的事实依据为Mozilla的公开Bugzilla记录、CA政策文档以及相关报道。证书信任是牵涉政治、安全与隐私的敏感议题，因此本文不替任何一方下定论。它以中立的技术视角梳理：到底公开了什么，以及这对用户和开发者意味着什么。需要推测之处，会标明为推测。

1. GPKI是什么 - 政府公钥基础设施

要把握脉络，先要了解GPKI。GPKI（Government Public Key Infrastructure）是韩国政府的公钥基础设施，是签发与管理公务员认证及电子政务、行政服务所用数字证书的体系。依据公开资料，KLID（韩国地域信息开发院）运营GPKI的根CA与下级CA。

1.1 与商用TLS不同的起点

这里有一个关键区分。GPKI最初并非面向公众网站的商用TLS证书，而是作为政府内部系统与面向民众的行政服务身份认证的体系起步的。也就是说，它在用途与治理起点上，不同于为网站加上常见「HTTPS锁标」的商用CA（如DigiCert、Let's Encrypt）。这一差异，对理解下文的收录被拒与再次尝试至关重要。

1.2 为何只有Firefox会出问题

这里常出现一个疑问：「Chrome、Edge都正常，为何只有Firefox弹警告？」答案在于信任库的来源。Chrome、Edge等多数浏览器沿用操作系统持有的证书库。在韩国的环境中，政府与机构证书常被安装进Windows证书库，因此同一政府域名在Windows上往往不弹警告即可打开。而Firefox与操作系统无关，使用由Mozilla直接管理的独立信任库。若GPKI系列根不在Mozilla库中，便只有Firefox用户会遇到信任警告。这就是政府瞄准Mozilla收录的表面原因。

2. 浏览器信任模型 - 根所拥有的权限

要理解此事的分量，先要明白浏览器如何决定信任谁。这是一切争论的起点。

2.1 信任链

在HTTPS连接中，浏览器会验证服务器出示的证书是否可信。该验证沿着根CA → 中间CA → 服务器证书的信任链向上回溯。链条顶端的根CA若已在浏览器信任库中，则该根（直接或间接）签名的证书都会被信任。信任库相当于浏览器预先确定的「我信任的签发机构」名单。

2.2 根CA的巨大权限

这里出现决定性的事实。受信任的根CA实际上拥有为任意域名签发有效证书的权限。从技术上看，无论某个根为example.com还是bank.co.kr签发证书，该证书在所有信任此根的浏览器中都会显示为有效。因此接纳某机构成为根的决定，并非单纯的兼容性问题，而是把全球用户的信任委托给该机构的决定。这正是Mozilla对根收录从严审查的原因。

3. Mozilla的收录流程 - 为何如此严格

Mozilla不依赖操作系统证书库，而运营自有根库，并公开、严格地进行收录审查。依据公开政策文档，整理其核心要求。

3.1 公开审查与CCADB

Mozilla的根收录并非私下交易。申请方CA须通过CCADB（Common CA Database）提交申请，并在公开讨论论坛接受社区审查与质询。申请书、审计报告、运营政策（CP/CPS）会被公开，任何人都可提出问题。这种透明度本身即是信任模型的一部分。

3.2 审计与标准对齐

依据公开政策，寻求网站信任位（TLS）的CA须接受WebTrust或ETSI审计，且审计周期不得出现空档。同时须满足CA/Browser Forum的基线要求（Baseline Requirements）与Mozilla Root Store Policy。近期政策（v3.0前后）持续提高门槛，甚至要求对签发、验证、续期提供自动化支持。一句话：收录门槛并非「政府运营」这一事实本身就能跨过。

4. 过去的被拒 - 问题出在哪里

这并非首次尝试，正是此事的核心。依据公开Bugzilla记录，梳理过去请求如何结案。

4.1 2015年前后的请求

据公开记录，GPKI根收录请求自2015年前后即已出现，典型如Bug 1226100与Bug 1377389被以WONTFIX（不予处理）结案。被拒、结案的理由大致分两条。其一是根下存在未公开的私有下级CA的结构性问题，Mozilla告知下级CA需另行审查。其二是证书误签发（misissuance）的担忧。

4.2 单一下级CA集中与运营可靠性

社区讨论中常被指出的另一担忧，是签发过度集中于某一下级CA的结构，以及OCSP（证书吊销状态查询）应答服务器稳定性等运营可靠性问题。若吊销应答基础设施频繁中断，便难以实时确认证书有效性，从而成为信任模型的薄弱环节。这些指摘以报道与公开讨论为依据，可能反映某一时点的状态，特此说明。

4.3 Mozilla的建议

依据公开记录，Mozilla在结束过去请求时，建议以一个自创建起即符合政策与CA/Browser Forum基线要求的新根重新申请。也就是说，信号并非「请照单全收既有行政用根」，而是需要一个按商用TLS信任标准重新设计的根。

5. 本次再尝试 - 有何变化

那么本次尝试与过去有何不同？依据公开Bugzilla记录（如Bug 1845081）指出差异。

5.1 专为TLS的新层级

依据公开记录，本次的核心并非沿用既有GPKI行政用层级，而是提交一个专为TLS新建的独立层级。在报道与记录中被称为MOIS SSL Root CA的该层级建于2023年，其下设单一签发CA（MOIS SSL Server CA），结构简单。这可读作意在结构上规避过去被指摘的「混入未公开私有下级CA的复杂层级」问题的设计。

5.2 强调审计与标准对齐

公开记录强调，该新层级已接受WebTrust审计，并按CA/Browser Forum的TLS基线要求验证实践运营。运营主体被描述为：在行政安全部（MOIS）之下由KLID承担GSSL CA服务，且不设外部委托的注册机构（RA）。这可读作意在明确签发权限与验证责任。

5.3 仍然存在的变数

不过，结构与审计的改善并不保证收录。Mozilla根收录须经过CCADB流程与公开评审，社区会审视过往经过、运营透明度乃至实际签发实践。截至2026年6月，最终能否获准无法断言，进展状态以公开Bugzilla为准更为准确。

6. 核心争论 - 政府运营的CA可信吗

此事真正的争点不是技术而是信任。当浏览器广泛信任政府运营的CA时会有何担忧、又应如何平衡看待，下面加以梳理。

6.1 担忧的核心

如前所述，受信任的根可为任意域名签发有效证书。若政府运营的根被广泛信任，便存在理论上被滥用于为任意域名签发证书、在中途拦截HTTPS流量的担忧。这正是围绕政府CA的安全争论核心。权力主体握有签发权这一事实本身——即便签发范围限于政府域名——也会引发对监控、审查可能性的警惕。

6.2 哈萨克斯坦先例

表明这一担忧并不抽象的典型案例是哈萨克斯坦。据报道，哈萨克斯坦政府诱导用户安装本国签发的根证书，并借此在中途拦截HTTPS流量的经过被揭露。对此，Mozilla与Google在浏览器中屏蔽了该政府根。这一先例具体地刻画了「广泛信任政府根可能发生什么」，并提高了此后社区对政府系根审查的警惕。

6.3 平衡的视角

然而把哈萨克斯坦案例原样套用到所有政府CA同样不准确。应区分两点。哈萨克斯坦是强制用户安装根并拦截流量的事件。而正常的Mozilla收录须通过公开审查、审计与标准对齐，签发范围与运营会被持续监督。风险的实际大小，与其取决于「是否政府运营」这一二分法，不如说取决于签发范围、审计透明度、吊销与证书透明度（CT）日志运营，以及误签发时的应对。以我的判断，与其在政治上评断收录本身，不如追问这些技术管控是否真正运作来得更有建设性。社区中出现拒绝GPKI信任的工具（如NoGPKI项目）这一事实，表明此信任问题在用户层面亦相当尖锐。

7. 对用户的影响 - 会改变什么

落到实用问题：若GPKI系列根被加入Firefox，以及若未被加入，对用户分别会改变什么？

7.1 若被收录

最直接的效果是便利。在Firefox中打开政府域名时出现的信任警告将消失，用户无需另行安装证书即可顺畅使用政府服务。对政府而言，可统一因浏览器而割裂的访问体验，并摆脱要求用户手动安装证书的做法。这在安全层面也可能是积极的，因为让用户自行安装根这一做法本身就有风险。通过正式流程收录，正是减少这一危险做法的方向。

7.2 若未被收录

反之，若收录落空或延迟，Firefox用户将继续在政府域名遇到警告，或须手动添加例外。更令人担忧的情形是，引导用户自行安装政府根的做法继续存在。这可能导致用户在不了解根的权限与风险的情况下授予广泛信任，从安全角度看反而可能是更糟的结果。因此很难只把「收录尝试本身就是坏事」当作全部。

7.3 开发者与运维者的视角

若你负责政府对接服务，需要在假定客户端多样性（包括Firefox）的前提下做证书信任测试。此事也再次提醒我们：行为会因信任库是操作系统还是浏览器而分化。若你的组织有向内部系统手动分发根的做法，不妨借此机会审视该根的签发范围与吊销流程。

8. 局限与注意事项

最后，明确本文不下定论之处。

其一，进展的可变性。Mozilla收录是公开流程，状态时常变化。本文事实依据为撰写时点（截至2026年6月）的公开记录，最新状态应以相应Bugzilla与CCADB为准。其二，技术与政治的分离。本文仅讨论证书信任的技术结构与公开担忧，不对任何政府政策的意图下定论。其三，避免二分法。「政府CA一律危险」与「官方收录就一律安全」两个极端都不准确。实际的安全取决于签发范围、审计与透明度这些可验证管控是否运作。

9. 结论 - 据何判断

韩国政府再次尝试将根加入Firefox，并非简单的兼容性工作，而是处在浏览器信任模型与政府权限交汇之处的议题。过去的请求因结构缺陷与运营可靠性担忧结案，本次尝试看似以专为TLS的新层级、审计与标准对齐来回应那些指摘。但最终判断仍取决于Mozilla的公开审查与社区评审。

我建议关注三点。其一，签发范围是否受限——新根是否将签发限定于政府域名。其二，审计与透明度的持续性——WebTrust审计、CT日志、吊销基础设施是否无间断运营。其三，误签发的应对体系——出问题时是否有迅速吊销、公开、纠正的流程。若这三点稳固，「政府运营」这一事实本身并不构成淘汰理由。反之若这些动摇，则无论是否收录，信任都存在薄弱环节。归根结底，核心不在主体的身份，而在可验证的管控是否真正运作。
