The factual basis of this article is drawn directly from the technical disclosure published on September 22, 2026, by researcher Peter James of Mouse (mouse.dev), alongside documented chat captures. This article presents the reported export results and Meta's bug bounty determination neutrally, without speculative commentary or standalone security assessments.

1. Incident Overview and Primary Source Scope

As autonomous artificial intelligence agents increasingly operate within isolated operating system runtimes to perform complex computational workflows, managing the runtime environment and governing outbound data movement have become critical architectural topics. When an agent is granted tool access, arbitrary command execution, and file inspection capabilities, the question of whether its internal system files, application templates, and operational secrets remain protected against conversational data exfiltration is a fundamental consideration.

On September 22, 2026, researcher Peter James of Mouse published an analytical write-up detailing how a routine interaction with Meta's AI agent, Muse, allowed him to export an archive of the Linux environment provisioned for his session. The published document outlines the exact method of request, the unpacked file sizes, the structure of internal directories, and the subsequent vulnerability report submitted through Meta's Whitehat bug bounty portal.

This disclosure did not involve bypassing external network firewalls or executing automated exploit scripts against public endpoints. Instead, it examined whether an agent configured with file access and cloud integration capabilities would package and transfer its assigned root environment when instructed to do so via standard user dialogue. The researcher documented the interaction while declining to release sensitive files, session keys, or raw archive artifacts publicly. This review summarizes the confirmed technical facts and official positions of both parties.

2. Conversational Export Experiment and Data Volume

The methodology employed by Peter James was straightforward: he prompted Muse to collect all files visible across its runtime into an archive and transfer the resulting bundle to his connected Google Drive storage. As recorded in the original article, the author asked Muse to archive the files it could see and send them to Google Drive, and the agent completed the task. The interaction relied purely on conversational task delegation.

The exported payload measured approximately 2.7 GB in its compressed zip format and expanded to roughly 6.8 GB when unpacked locally. The researcher noted that the archive appeared to encompass the root filesystem of the assigned Linux environment. Contained within were standard Ubuntu distribution system libraries, internal documentation files, operational integration code, framework templates, agent logs, and long-term memory databases.

The author provided visual evidence from the conversation showing the agent acknowledging archive generation and delivering a downloadable link. In his report, James highlighted the presence of SSH key files, agent transcripts, and memory banks within the delivered filesystem. He explicitly stated that he did not determine whether the SSH keys were active or what specific access privileges they might provide, and withheld all raw credential strings from public release.

3. Core Directory Layout and the hatch Environment

The substantive internal structure was located within /home/hatch, /opt/hatch, and /opt/hatch-image. According to the disclosure, 'Hatch' is the internal project codename used by Meta engineers to represent the Muse agent, as reflected across configurations, system services, and documentation files throughout the runtime image.

Inside the user home directory at /home/hatch/, six foundational Markdown documents were positioned to govern the agent's behavior, operational parameters, and system identity. These files included:

  • SOUL.md: Outlines foundational ethical guidelines, core personality traits, and behavioral guardrails
  • IDENTITY.md: Formally establishes the operational persona and conversational identity of the agent
  • USER.md: Contains user-specific contextual information, communication preferences, and standing commitments
  • MEMORY.md: Serves as a concise summary sheet tracking high-level facts, validated preferences, and commitments
  • AGENTS.md: Specifies multi-agent coordination protocols and delegation parameters for subagents
  • TOOLS.md: Details available CLI tools, programmatic interfaces, and invocation rules

Alongside these baseline instruction files, the home directory contained an agents/ folder housing 113 historical subagent records accompanied by detailed JSONL execution traces. Furthermore, a docs/ directory contained approximately 20 Markdown files documenting runtime capabilities such as headless browser interaction, external API connectors, payment handling, credential storage policies, audio synthesis, goal execution, and background scheduling. Unlike traditional microservices that abstract prompt logic away from runtime disk volumes, Muse maintained its complete operational instructions as plain text files directly accessible within its execution environment.

4. Skills Architecture and the Spaces Application Framework

The integration subsystem under /opt/hatch/skills/ comprised roughly 68 discrete skill directories. In most instances, each folder coupled a SKILL.md file defining operational triggers and usage boundaries with an executable command-line script or supporting runtime code. The documented skills spanned integrations with Google Workspace, Meta social platforms, Microsoft Outlook, travel reservation systems, shopping platforms, personal health services, home automation bridges, and media authoring pipelines.

Configuration manifests including skill-scopes.conf and bin-scopes.conf listed unreleased service connectors under active engineering. These entries referenced external platforms such as Slack, Dropbox, Polymarket, Canva, and Klaviyo, alongside internal administrative utilities.

The largest application codebase discovered within the archive was the Spaces framework, which Muse uses to construct and host custom web applications dynamically. The export included an end-to-end TypeScript starter template equipped with a React front-end client, server actions, a Drizzle-managed SQLite database schema, database migration files, and configuration for the Bun runtime environment. Subdirectories named worker, sdk, cloudflare, and cvm contained supporting runtime modules.

Container configuration artifacts were likewise preserved in the archive. Within /opt/hatch/runtime-cell/, 18 distinct files provided initialization logic for building the root filesystem image, spawning it via systemd-nspawn, and coordinating startup daemons. A separate manifest, runtime-cell.kdl, cataloged the packages and systemd units bundled into the image. Notably, Codex CLI version 0.149.0 was located at /opt/hatch-image/bin/codex; however, James discovered no code invoking Codex as an autonomous programming agent. Instead, Hatch utilized the bundled bubblewrap sandbox binary located at codex-resources/bwrap to execute media utilities such as ffmpeg and ffprobe inside a restricted, non-root sandbox running as user nobody without network connectivity.

5. Muse Memory Storage Mechanisms and Operational Design

A notable technical insight from the disclosure centers on how Muse organizes and persists user memory across distinct conversational sessions. Rather than altering neural network weights, Muse implements a persistent external memory architecture utilizing Markdown files and an embedded relational database.

Immediate conversational memory is written directly to plain Markdown files. Dated files within ~/memory/ record detailed real-time context and raw exchanges during an active chat session. Concurrently, ~/MEMORY.md serves as a high-level, curated reference document maintaining verified facts, explicit user preferences, and standing instructions.

To reconcile immediate observations with long-term memory, background reconciliation routines run on an hourly schedule. These background workers evaluate newly recorded claims against raw conversational turns, extracting relevant quotations, conversation IDs, and assigning unique claim IDs. Structured material is subsequently indexed under memory/bank/, split across categories such as personal circumstances, past experiences, and functional preferences.

A PostgreSQL instance provides relational query and semantic search capabilities across this file corpus. The memory.entries table stores chunked text records and line numbers, while memory.embeddings maintains 384-dimensional dense vectors to support nearest-neighbor retrieval. The memory.claims table tracks empirical evidence, confidence intervals, and verification states, allowing obsolete records to be updated cleanly via supersedes_claim_id. Deletion routines follow a formalized forget protocol that invalidates claim IDs and rebuilds the semantic index, ensuring that future autonomous runs cannot reconstruct discarded facts. Through this hybrid design, the agent adapts its long-term behavior while preserving model immutability.

6. Disclosure Timeline and Meta's Official Bug Bounty Response

Following his analysis of the exported data, Peter James submitted his documentation and findings to Meta through its official Bug Bounty channel. The central vulnerability asserted in the report was that sensitive internal runtime assets, operational documentation, and credentials could be systematically exported from the sandbox via standard natural language instructions paired with authenticated storage endpoints.

Meta evaluated the submission and marked the ticket as "Not Applicable." The automated and formal response provided by Meta's security triage team listed various potential rationales common to bounty assessments without isolating the precise technical ground applied to this case. Simultaneously, the correspondence invited the researcher to submit additional evidence demonstrating direct security compromises or user privacy exposure.

In his published write-up, James explicitly clarified that he did not demonstrate a container breakout. He noted that while he lightly probed the container perimeter to test whether Muse could escape into the host environment, the sandbox isolation held firmly. He also observed approximately 80 active domain sockets within the environment but decided to halt deeper network scanning given the production status of the infrastructure and his stated focus. The factual record thus indicates that hardware virtualization and container boundaries remained intact.

7. Technical Considerations for Agent Sandboxes and Export Boundaries

This disclosure highlights an evolving dilemma in autonomous agent security: the distinction between virtualization-level container isolation and application-level data governance. From a traditional cloud infrastructure standpoint, if an ephemeral container successfully prevents host breakout, memory snooping, or cross-tenant data access, the boundary is frequently considered secure. This architectural perspective likely informed Meta's determination that the submission did not represent an actionable infrastructure vulnerability.

Conversely, from an application architecture perspective, giving an LLM agent sweeping read access across its boot image combined with external cloud sync tools creates an effective data extraction vector. When internal architecture manuals, prompt design files, framework source code, and leftover configuration keys reside within the agent's legible filesystem, the agent can easily convert conversational file requests into complete runtime dumps.

In production environments, addressing this tension generally requires enforcing strict path allowlists on file-reading tools and decoupling user workspace mounts from system configuration trees. Ensuring that external cloud connectors can only read from dedicated, ephemeral staging directories represents a practical mitigation commonly discussed across modern AI engineering teams.

8. Things Left Unverified

This analysis is grounded strictly in facts published in the primary report. Several technical elements could not be independently verified and are documented below as boundaries of the known record:

  • Whether the SSH key files present in the archive represented active, valid credentials for any internal Meta servers or third-party services was not established by the researcher and remains unverified.
  • The specific technical reason among the generalized grounds cited by Meta for marking the bug bounty submission as Not Applicable was not disclosed in the official correspondence.
  • Whether the experimental 'Meta Home Link' documentation and ESP32-C5 references represent an internal prototype, an abandoned exploration, or an upcoming hardware initiative remains unknown.
  • The precise identity, service mapping, and destination endpoints of the 80 internal domain sockets detected within the session runtime were not detailed in the source document.
  • Whether Meta has subsequently adjusted its runtime file permissions, container mount points, or conversational export limits following the disclosure has not been officially confirmed.
