起因 — 文本嵌入模型如何把五种输入放进同一个空间

Google于2026年10月6日在官方博客上发布了EmbeddingGemma 2的公告。作者是Google DeepMind的研究工程师Sahil Dua和Henrique Schechter Vera。公告称，第一代EmbeddingGemma去年推出，是可在消费级硬件上运行的轻量级文本嵌入模型，下载量超过2,000万次，开发者把它用于端侧搜索工具和隐私优先的RAG(检索增强生成)流水线。

第二代把范围扩展到文本之外。公告写道，该模型把代码、图像、视频和音频统一到一个共享的嵌入空间中，模型卡则明确指出这个空间是一个768维的向量空间。它建立在Gemma 4架构之上，总参数量为7.4亿(740M)，按公告的说法，以「商业上宽松的Apache 2.0许可证」发布。公告举的场景是凭语音备忘录找到特定视频片段、用文本查询检索数小时的音频录音，均由同一个原生多模态模型完成。

公告的副标题把该模型称为「端侧多模态嵌入方面能力最强的模型(the most capable)」，正文则写作「同等规模中的同类最佳(best-in-class for its size)」。两者都是Google对自身模型的评价，原文把比较范围限定在10亿参数以下(sub-1B)的多模态嵌入模型。选择端侧嵌入模型时真正要看的是其下的四项数值。

  • 配置：只处理文本时2.7亿(270M)参数即可，1.7亿(170M)的视觉编码器和3亿(300M)的音频编码器为可选。
  • 维度截断：借助MRL(Matryoshka Representation Learning)，768维输出可截断为512、256或128维，存储缩减的表述是「最高6倍」。
  • 内存：应用量化后，在Google Pixel 11 Pro上纯文本权重需约191MB活动内存，完整多模态模型需约567MB。原文措辞是「as little as」，即作为下限给出。
  • 上下文：8K token的上下文窗口是第一代的4倍，可接收最长5.5分钟音频、29张图像、58帧视频，或它们的交错组合。

配置 — 270M文本主干与按需加载的编码器

模型卡把7.4亿参数分成三块。2.7亿的文本主干又分为1.3亿的Transformer和1.4亿的嵌入层，在此之上再加上1.7亿的视觉编码器和3亿的音频编码器。按开发者指南的说明，文本与代码部分是改造过的Gemma 4解码器，上下文窗口为8,192个token；视觉编码器处理图像、视觉文档(PDF、幻灯片、图表)和视频帧；音频编码器专门处理语音和声音，直接接收原始音频。输入先经各自模态的编码器，再经共享主干，落在同一个768维空间中。

视觉编码器和音频编码器是独立组件。在sentence-transformers中，把config_kwargs里的vision_config或audio_config设为None，对应编码器就不会加载。指南写道，被禁用的编码器不会载入内存，节省同时体现在权重和峰值分配上。

配置 config_kwargs(模型卡) 有效大小 活动内存(量化、Pixel 11 Pro，公告)
仅文本 {"vision_config": None, "audio_config": None} 270M 约191MB
文本 + 图像 {"audio_config": None} 440M —
文本 + 音频 {"vision_config": None} 570M —
完整多模态 {} 740M 约567MB

下面是指南中给出的按需加载代码。MODEL_ID在指南的前一个代码块中被定义为"google/embeddinggemma-2"。

# Text only (270M parameters)
                    text_only_model = SentenceTransformer(
                        MODEL_ID,
                        config_kwargs={"vision_config": None, "audio_config": None},
                    )
                    
                    # Text, images, and video (440M parameters)
                    text_image_model = SentenceTransformer(
                        MODEL_ID,
                        config_kwargs={"audio_config": None},
                    )
                    
                    # Text and audio (570M parameters)
                    text_audio_model = SentenceTransformer(
                        MODEL_ID,
                        config_kwargs={"vision_config": None},
                    )

按指南的说法，在sentence-transformers中四种配置都从同一个检查点加载，因此共用一个向量空间。用270M纯文本配置嵌入的查询，可以直接与完整模型嵌入的文档匹配。先建纯文本索引、之后再加入图像或音频嵌入时，只需启用相应编码器重新加载模型，已算好的嵌入不必重算。模型卡附了一条说明：省略部分编码器的配置方式因库而异，应参照各库的文档。

表格的内存一列只有两格有数值。公告给出的是纯文本权重和完整多模态模型的数值，440M和570M两种配置没有数值。指南对配置选择的一般建议是：只加载数据需要的编码器，只有存储空间或检索速度有要求时才截断维度。

维度截断 — 从768到128，缩减时付出的代价

由于模型是用MRL训练的，768维的输出向量可以通过只保留靠前的维度来缩短。支持的维度为768、512、256和128。公告中的「最高6倍的存储缩减」是768维截断到128维时的比例(768÷128=6，计算)，与模型卡表格中1:6的压缩比一致。指南举例说，以bfloat16精度存储100万个768维向量约需1.5GB内存，截断到128维后只需250MB。

向量缩短多少，质量就相应下降多少。模型卡用表格列出了各个维度下的得分，并说明这些数值都是用全精度(full-precision)检查点测得的。

输出维度 压缩比 MTEB 多语言 v2 MTEB 英语 v2 MTEB 代码 v1 MIEB lite MMEB v2 总体 MSEB 检索 MAEB
768d(完整) 1:1 61.36 68.46 78.68 64.64 59.01 69.54 49.39
512d 1:1.5 61.17 68.41 77.24 64.32 58.38 69.18 49.21
256d 1:3 60.41 67.78 76.18 63.13 56.24 66.76 48.91
128d 1:6 57.89 65.68 71.41 59.06 45.65 56.71 46.92

模型卡写道，截断到256维为止对质量影响很小；128维会使多模态质量大幅下降，应先用自己的工作负载验证再采用。表中MMEB v2总体得分从768维的59.01降到128维的45.65，对应的正是这句话。同一列在256维时为56.24，MTEB多语言v2一列在同一区间只从61.36变为60.41。指南给出的维度选择标准如下。

  • 768维或512维：用于多模态检索和视觉文档检索，或召回率比存储更重要的场合。
  • 256维(存储缩减3倍)：用于存储受限的索引。文本和代码保留原始嵌入的大部分质量，图像、视频和语音检索保留约95%。
  • 128维(存储缩减6倍)：用于大规模纯文本索引和重排序之前的第一阶段候选筛选。文本和代码保留约90%的质量，图像、视频和语音检索的质量降到约75%。指南附了一句：把128维用于多模态查询之前，应先在目标数据上验证。

模型卡为截断附加了两条运行时规则。

  • 截断之后重新归一化。对单位长度的向量做切片不能保持单位长度，因此缩短后的向量在用于余弦相似度之前要先做L2归一化。跳过这一步不会报错，而是给出看似合理的分数，排序质量却悄悄变差。
  • 查询和文档使用相同的维度。不能用768维的查询去对128维的语料库打分。

在sentence-transformers中，只要向encode()传入truncate_dim和normalize_embeddings，这两个步骤就会一并完成。指南中的示例如下。

# Truncate the query
                    query_emb = model.encode(
                        query,
                        prompt_name="SearchQuery",
                        truncate_dim=256,
                        normalize_embeddings=True,
                    )

如果希望每次调用都使用同一个维度，可以改为在加载时指定，写法是SentenceTransformer(MODEL_ID, truncate_dim=256)。

输入上限 — 共用8,192个token的规则

上下文窗口为8,192个token，所有模态共用这一份预算。公告称它是第一代的4倍(反推第一代为2,048个token，计算)。每种模态消耗token的比率固定，公告中「5.5分钟音频、29张图像、58帧视频」正是由这些比率得出的。

模态 token成本(模型卡) 最大输入(模型卡) 公告中的表述
文本 每个子词1个token 8,192个token 8K token
图像 每张图像280个token(默认值) 约29张 29张
视频 每帧140个token(默认值) 约58帧 58帧
音频 每秒25个token 约327秒 最长5.5分钟
  • 单一模态的前提：这些最大值假定只放入一种模态且不附带文本。混合输入从同一份预算中扣除，每一种能放进去的数量都会减少。
  • 视频采样：视频默认按每秒1帧采样后交给视觉编码器处理，采样率可以调整。按默认设置，58帧约相当于58秒的画面(计算)。
  • 音频格式：音频应当以16kHz单声道的形式提供。
  • 视觉token预算：用来表示一张图像或一帧视频的「软token」数量可以在70到1120之间选择。调低预算后，最多可以放入约114张图像或约114帧；调高预算则是用延迟和token数量换取质量。
  • 传入方式：媒体可以用文件路径(视频为MP4)、URL(图像和音频)，或者内存中的PIL图像、数组和张量的形式传入。

把文本和媒体混在同一个输入中时，要在文本里放置<|image|>、<|video|>和<|audio|>占位token，标明每个媒体的位置。占位符按顺序用对应键的值填充，调用返回一个同时表示文本和媒体的嵌入。

基准测试 — Google给出的数字及其范围

公告中带具体数字的性能主张只有一项：MTEB Code得分从第一代的68.76升到78.68，提高9.92分；指南和模型卡表述为约14%的提升。公告据此认为该模型适合本地代码库索引、语义代码搜索和编码智能体的检索。多语言文本性能方面，公告的说法是与第一代持平，模型卡中MTEB多语言v2的得分是61.36对61.15。

其余模态的得分都在模型卡里。下表中的数值以全精度检查点、768维为基准；由于第一代是文本模型，它在图像、视频和音频几栏中是空的。

这张表里没有其他公司模型的得分。公告称该模型在10亿参数以下的多模态嵌入模型中分数领先，与许多更大的模型持平或更好，甚至优于一些规模超过它两倍的专用模型，但没有写出被比较模型的名称。因此这些数字要结合以下条件来读。

  • 比较范围：「best-in-class」是和「就其规模而言」「在sub-1B多模态嵌入模型之中」这两个限定语一起使用的。模型卡的措辞则是「10亿参数以下最强的多模态嵌入模型之一」。
  • 测量主体：表中的所有得分都是Google在模型卡中公布的数值。
  • 测量条件：得分以全精度检查点为基准，而约191MB和567MB是应用量化之后的数值。这两组数字出自不同的条件。
  • 语言：模型卡写明支持100多种语言，同时也把「不同语言上的表现可能并不相同」列为局限之一。

用法 — sentence-transformers、任务前缀与数值精度

指南写道，使用sentence-transformers库(v6.1.0或更高版本)就可以处理文本、代码、图像、视频和音频的全部输入，并给出安装命令pip install -U sentence-transformers[image,audio,video] transformers。模型ID为google/embeddinggemma-2。

文本输入要带任务指令前缀。按模型卡的说明，该模型训练时就在文本输入前加了简短的任务指令前缀；用对前缀可以提高质量，省略仍可运行但精度下降。在encode()的prompt_name中给出名称，前缀会自动加上。

  • 非对称任务(例如检索)：对查询使用查询前缀，对语料库中的条目使用文档前缀。提示名称为SearchQuery、QuestionAnswering、FactChecking和CodeRetrieval。
  • 对称任务(例如分类和相似度)：对所有参与比较的输入使用同一个前缀。Classification、Clustering和SentenceSimilarity属于这一类。
  • 文档格式：有标题的文档按title: {title} | text: {content}的格式书写，没有标题时使用title: none。由于prompt_name="Document"套用的是title: none，有标题的文档仍然需要自己手动整理格式。
  • 媒体：前缀只适用于文本。图像、视频和音频在传入时不加任何前缀。
  • 数值精度：用bfloat16或float32推理，不使用float16。模型卡解释说，该模型激活值的范围超出float16的动态范围，在float16下不会报错，而是返回NaN或悄悄变差的嵌入。bfloat16是原生支持它的硬件上的推荐默认值，相对float32内存占用减半；包括大多数CPU在内的其他环境使用float32。

媒体以按模态作为键的字典形式传入。指南中跨模态检索与交错输入的示例如下。其中model是用SentenceTransformer(MODEL_ID)加载的完整模型。

# Cross-modal search: one text query against a photo and a sound recording
                    image_emb = model.encode({"image": "sunset_beach.jpg"})
                    audio_emb = model.encode({"audio": "ocean_waves.wav"})
                    query_emb = model.encode("ocean waves at sunset", prompt_name="SearchQuery")
                    
                    print(model.similarity(query_emb, image_emb))
                    print(model.similarity(query_emb, audio_emb))
                    
                    # Interleaved: one embedding for a product listing with text, photo, and video
                    listing_emb = model.encode({
                        "text": "Waterproof trail shoe. <|image|> Grip test on wet rock: <|video|>",
                        "image": "trail_shoe.jpg",
                        "video": "grip_test.mp4",
                    })
                    query_emb = model.encode("waterproof trail shoes", prompt_name="SearchQuery")
                    
                    print(model.similarity(query_emb, listing_emb))

指南写道，嵌入虽来自不同模态，却位于同一个维度空间，可以按语义相似度比较。上面的示例中，文本查询分别与照片、录音和商品列表的嵌入匹配，正是这种用法。

与Gemma 4的搭配、下载渠道与支持的工具

公告写道，与Gemma 4这样的生成模型搭配，就能构成理解复杂多模态数据的端侧RAG流水线。EmbeddingGemma 2建立在Gemma 4之上，共用其文本分词器和音频编码器，两个模型在同一条流水线中一起运行时合计内存占用更低。指南对同一点的表述是「共用相同的文本分词器和音频编码器架构」。在老旧CPU上运行Gemma 4的条件见用十年前的Xeon跑Gemma 4，扩散方式的文本生成见DiffusionGemma一文，几十MB级别的模型在设备内进行工具调用见Needle 3技术解析。

许可证方面，公告、指南和模型卡写的都是Apache 2.0。模型卡另外写明，部署要遵守Gemma禁止使用政策(Gemma Prohibited Use Policy)。模型卡还指出，这是预训练的嵌入模型，与生成模型不同，没有经过训练后的对齐、安全调优或输出层面的审核，检索过滤、公平性测试等应用层防护由开发者和部署者负责。

公告称Google与合作伙伴密切合作，使该模型在开发者所用的环境中可以直接使用，并列出了以下渠道。

  • 权重：可从Hugging Face和Kaggle获取。Gemini Enterprise Agent Platform Model Garden的表述是「即将提供(coming soon)」。针对端侧优化的模型放在Hugging Face上的LiteRT Community中。
  • 端侧部署：列出的是Google AI Edge的MediaPipe(面向嵌入、检索和决策任务的开箱即用方案)和LiteRT(用于自定义模型集成)。
  • 浏览器：面向浏览器的构建使用transformers.js或WebGPU。
  • 开发工具：列出的是transformers、sentence-transformers、MLX、vLLM、llama.cpp、SGLang、Ollama和LMStudio。
  • 向量存储：列出的是Qdrant，用于存储嵌入向量。
  • 微调：公告指向的是Unsloth提供的指引。

公告举出的体验渠道有：Google AI Edge Gallery中的Instant Media Search(用文本或图像在媒体库中找语义最接近的条目)和Video Moments Finder(用文本或音频查询定位视频中的特定时刻)，与Gemma 4搭配、负责本地文件检索的Google AI Edge Foresight应用，以及用于分类、路由和预测的MediaPipe Decision Task API。

未能确认的事项

  • 量化级别与运行时。公告没有写明测得约191MB和567MB时的量化位数和运行时。其他设备上的数值、440M和570M两种配置的数值也没有。
  • 量化后模型的质量。模型卡的得分以全精度检查点为基准，三份文档中没有找到量化后的得分。
  • 用于比较的模型。「在sub-1B多模态嵌入模型中领先」「优于规模超过它两倍的专用模型」所对应的模型名称和得分，公告、指南和模型卡的正文中都没有。指南里的基准测试图是图片，其中的数值未用作依据。
  • 处理速度。三份文档都没有给出单次嵌入的延迟或每秒处理量的数字。
  • 许可证文档的细节。模型卡中Apache 2.0的标注链接到Gemma 4许可证说明页面，而遵守禁止使用政策的要求是另外写明的。这两份文档之间如何衔接未能确认，因为这些页面没有被纳入本文的依据材料。
  • 与Gemma 4一起运行时的节省幅度。文档中只有「合计内存占用更低」这一表述，没有附带数字。
  • 第一代的上下文窗口。2,048个token是由「4倍」反推出来的数值，没有与第一代的文档进行核对。
