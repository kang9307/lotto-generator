If Coding Is Solved, Why Does Software Keep Getting Worse?

AI solved writing code - production - but understanding, design, and verification are unchanged. The nature of software rot and complexity debt, and what to do about it

Jul 26, 2026 Dev & Infra

Introduction: Code Is Everywhere, So Why Do Apps Crash More?

It's a strange era. It has never been easier to produce code, yet the software we use every day stutters more often, and every update carries a fear that it will get worse. The banking app bounces you three times before login, collaboration tools feel slower than they used to, and the car's infotainment still asks for a reboot. A post I saw on GeekNews (hada.io), if coding has been solved, why does software keep getting worse, hits this paradox head-on. If AI has all but automated writing code, why hasn't the quality of the output improved to match?

This piece isn't a summary of that original article. It's an attempt to dig into the question in my own terms. The core claim is one thing: what AI solved is writing code (production), while the real causes that make software worse live in the hard parts - understanding, design, and verification. And those hard parts remain a human job. Where two decades of frontend history covered the evolution of tools and why AI didn't replace software engineers covered the survival of the role, this piece looks at the third face between them - the quality decline. What software rot is, why AI accelerates it, and how it can be slowed, in that order.

1. The Bottleneck Didn't Vanish - It Moved

First, clear away a misconception. Yes, the speed of writing code went up. The problem is that building software isn't done by writing code alone.

1.1 The Trap in Saying Coding Is Solved

Put the original's counterargument in my own words: the premise that coding is solved is only half true. AI now lets a skilled engineer produce in an hour what used to take a week. But the time to verify whether that code is correct, safe, performant, and free of conflicts with the existing system has not shrunk. If anything, the verification burden grew in proportion to the surge in output. When code was the bottleneck, all that mattered was code arriving fast; now that code is cheap, the real bottlenecks that always sat behind it - understanding, integration, maintenance - are laid bare. The bottleneck didn't disappear; it moved from upstream to downstream.

1.2 What the Data Points To

This isn't sentiment; it's a measured phenomenon. According to GitClear's 2026 analysis of code-change history, duplicated code blocks - five or more consecutive repeated lines - climbed from 40.3 per million changed lines in 2023 to 73.0 in 2026, an 81% rise and a record high. In the same analysis, cross-file function calls (a proxy for reuse) fell 35%, and refactoring line-moves fell 70%. Paste went up; cleanup went down. Meanwhile, in METR's 2025 randomized controlled trial, when 16 experienced open-source developers performed 246 real tasks, the group using AI was actually 19% slower. The striking part: those same developers had expected AI to make them 24% faster. The illusion of speed diverged from the measurement.

2. What Is Software Rot?

What's happening now isn't wholly new. Software engineering named this tendency long ago.

2.1 Software Entropy and Lehman's Laws

Software rot is when software gradually stops working correctly over time even without touching the code itself. It's also called software aging. There are two branches. One is environmental rot, where dependency libraries, operating systems, and APIs keep changing while the code can't keep pace. The other is internal rot, where structure tangles and complexity accumulates as features are bolted on. Lehman's laws of software evolution, laid out in 1974, summarized this as the tendencies of continuing change, increasing complexity, and declining quality. The increasing-complexity law in particular says that unless you deliberately refactor, a system's complexity - its entropy - keeps rising. Rot isn't the exception; it's the default state of neglect.

2.2 How AI Accelerates the Rot

If Lehman is right, software gets worse when left alone by default. So what did AI change? AI didn't create rot; it accelerated it. Once the marginal cost of producing code neared zero, paste slips into places where you'd once have hesitated to paste, and a fresh lump of similar code appears where you'd once have reused a single function. The 81% rise in duplication above is the fingerprint of this mechanism. Attach a powerful generation engine to Lehman's rising entropy, and unless you hit the brake called refactoring, rot only speeds up. GitClear and GitKraken's analysis of 623 million code changes from 2023 to 2026 reports that AI-assisted commits made up about a quarter of all commits, with technical debt rising alongside across eight maintainability metrics.

3. Why AI Solves Only the Writing and Not the Rest

So why did AI solve exactly the easy half? Look at the asymmetric structure of software work.

3.1 The Asymmetry of Writing vs. Reading and Understanding

Writing code is local. It completes within a narrow context - a specific function, a specific screen, a specific API call. This kind of local, patterned work is exactly where large language models excel. Reading and understanding code, by contrast, is global. You have to know what ripple this change sends into a module another team built three months ago, why this odd exception handler is here, and which implicit assumptions run through the whole system. Most maintenance time goes not to writing but to reading existing code and reconstructing context. The more code AI spits out, the more total code there is that someone must later read and understand.

3.2 The Hard Parts: Design and Verification

The genuinely hard parts cluster in two places. One is design: deciding what not to build, where to draw abstraction boundaries, and which trade-offs to accept - judgments that demand defining the problem itself. The other is verification: confirming that generated code meets the requirement exactly, doesn't collapse on edge cases, and holds security and performance requirements. These two are the hardest to automate, and, not coincidentally, they are also what actually determines software quality. AI made the cheap half cheaper while leaving the expensive half expensive. The catch is that as the cheap half explodes, the burden on the expensive half grows with it.

4. The Four Real Causes of the Quality Decline

To sum up, the quality decline isn't an accident AI caused single-handedly. It's closer to AI amplifying four pre-existing pressures by making production cheap.

4.1 Speed Pressure

The first thing to intensify was the expectation of speed. If the person next to you ships a feature in a day with AI, the organization demands that speed from everyone. The problem is that this pressure lands only on visible output (finished features), not on invisible output (tests, docs, cleanup). Speed pressure always cuts the unglamorous quality work first.

4.2 Ignoring the Cost of Verification

This is where the original is sharpest. Many developers take only the speed of generation and ignore the cost of guaranteeing stability, performance, and freedom from bugs. Code arrives in an hour, but no time is set aside to verify it. When unverified code merges, defects aren't gone - they're just deferred. One empirical study reported that code churn - the share of newly added code updated or deleted within two weeks - rose from 33% to 40%. Code shipped in a hurry gets reverted almost immediately.

4.3 Leaky Abstractions and Copy-Paste Debt

Third, the codebase itself gets harder to understand. When paste replaces reuse, the same logic scatters across ten places, and fixing a bug means finding and fixing all ten. A poorly designed abstraction, far from hiding detail, leaks it, forcing an exception onto every layer built on top. One large-scale empirical study (arXiv, "Debt Behind the AI Boom") found that 89.3% of AI-introduced issues were maintainability debt. It's not the kind that fails now; it's the kind that becomes hard to touch later.

4.4 Organization and Incentives

The last is a problem of people and structure. In an organization that measures success by features finished and PRs merged, no one spends time on refactoring and testing. The observation from DORA-lineage data that teams with high AI adoption merged 98% more PRs but saw review time rise 91%, while delivery performance metrics themselves didn't change illustrates the distortion well. More was built, but nothing got better. The declining quality Lehman named is, in the end, also a question of what an organization counts as success.

5. Practical Ways to Slow the Rot

This isn't a story to end in pessimism. If rot is the default of neglect, the response is clear: reinvest the time saved by cheap production into understanding and verification.

5.1 Don't Merge What You Can't Understand

The simplest and most powerful rule. Even AI-generated code is merged only if a reviewer can read it and explain its behavior. The moment you pass code no one understands, it becomes a black box no one can maintain. The review bar has to shift from syntax checking to understandability.

5.2 Allocate Time to Refactoring and Testing

The only brake that reverses entropy is deliberate refactoring. Strip out duplication on a schedule, and require matching tests for new code. The key is to spend the production time you saved right here. Speed isn't the goal; reinvesting the time you bought with speed back into quality is.

5.3 Use AI as a Verification Tool Too

Using AI only as a generator is using half of it. Put AI to work on the verification side too - assisting code review, generating test cases, hunting edge cases, drafting documentation - and you can share a little of the hard half's burden. The principle still holds, though, that a human makes the final call on the verifying AI's output.

5.4 Shift Your Metrics Toward Quality

At the organizational level, redefine success. Look not at feature count and merge count but at stability metrics like defect rate, change failure rate, and mean time to recovery, and you create the justification to spend time on refactoring and testing. What you count decides what you build.

6. Balance: Beware AI Doom-ism Too

To be fair: racing to the conclusion that AI ruins software is also a lazy diagnosis. The METR trial cited above had limited conditions, and a follow-up observation on a subset of the same participants actually showed a speedup. The tools are immature and improving fast, and outcomes diverge sharply with skill and workflow. The point isn't that AI is bad, but that quality gets worse when you let the production AI made cheap flow through without verification. One alternative view the original raises is worth keeping: some open-source and free software that still prioritizes users is less frightening to update. The speed of rot is decided not by the tool but by the discipline of whoever wields it.

7. Conclusion: Three Things to Apply Today

The declaration that coding is solved is only half true. AI made writing code cheap, but it left the real causes that make software worse - the difficulty of understanding, design, and verification - untouched. Software rot is an entropy that has existed since Lehman's day, and AI merely bolted a powerful generation engine onto that entropy. The default that neglect breeds decay hasn't changed; it just got faster.

So today's work is threefold. First, set a review bar that code you can't understand doesn't get merged. Second, reinvest the time bought by production into refactoring and testing. Third, judge success by quality metrics, not headcount of features. However cheap a tool makes production, the hard half of making good software still rests on human discipline.
