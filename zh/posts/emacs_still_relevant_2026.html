还有人在用Emacs吗？——一款50年老编辑器的生命力

VS Code、Cursor与AI原生编辑器盛行的2026年，仍有开发者选择Emacs的理由——可扩展性、org-mode、黑客文化与AI集成深度分析

2026-06-22 开发/基础设施

引言：引发讨论的一个问题

GeekNews上的一个话题——「还有人在用Emacs吗？」——获得了29点赞，引发了出人意料的热烈讨论。2026年6月，VS Code占据开发者使用率的75.9%，Cursor和Claude Code等AI原生编辑器快速崛起，一款50年前的文本编辑器居然能引发如此反响，绝非单纯的怀旧情绪使然。

Emacs由Richard Stallman于1976年在MIT人工智能实验室首创。1984年以GNU Emacs的形式重启，此后持续开发至今。2026年6月现行稳定版为GNU Emacs 30.2（2025年8月14日发布）。一款诞生于半个世纪前的软件仍在发布新版本，仍有新人入门学习——为什么？

本文既非Emacs颂歌，也非批判。目的是认真回答「这款编辑器为何仍在存活」，并探讨在AI编码时代，编辑器选择究竟意味着什么。

一、50年存活的理由——平台，而非编辑器

1.1 伪装成编辑器的Lisp解释器

把Emacs称为文本编辑器已经略显不准确。更精确的说法是：构建在Emacs Lisp解释器之上的文本编辑环境。这一区别正是其50年生命力的核心。

VS Code可以通过JSON设置和扩展改变行为，但无法从根本上重写编辑器的核心工作方式。Emacs则不同。光标移动、按键、保存文件——每个事件都是可以插入Lisp函数的钩子点。编辑器的任何行为都可以通过编程替换或扩展。这就是「Emacs是平台」的真实含义：用户可以按照自己的思维方式重新设计编辑器本身。

这一架构催生了远超普通插件的东西：Magit（Git客户端）、mu4e（邮件客户端）、elfeed（RSS阅读器）、dired（文件管理器）、org-mode（生产力系统）。这些更像是在统一键绑定体系和缓冲区模型下协同工作的独立应用程序。

1.2 把Emacs当操作系统用的人

在GeekNews的讨论中，一位用户描述了自己的工作流：Git → Magit，邮件 → mu4e，RSS → elfeed，笔记/TODO/日历 → org-mode，文件管理 → dired。浏览器以外的几乎所有计算工作都在Emacs内完成。到这个程度，Emacs已不是编辑器，而是个人计算环境本身。

对这类用户而言，「切换到VS Code」不是简单的工具替换，而是放弃数年积累的配置、键绑定肌肉记忆、org-mode数据库和自定义工作流。迁移成本极高。这既是其忠诚度的来源，也是深度投入者留守的理由。

二、org-mode——无可替代的杀手级应用

2.1 org-mode是什么

问Emacs用户最大的吸引力是什么，答案几乎都是org-mode。org-mode是Bastien Guerry等社区成员数十年打磨的纯文本生产力系统。功能概览如下：

  • 结构化笔记（标题、链接、表格）
  • 项目与任务管理（TODO状态、优先级、标签）
  • 时间追踪（CLOCK IN/OUT自动记录）
  • 日历与议程视图（截止日期、周期性日程）
  • 代码块执行（org-babel——支持Python、Shell、SQL等多语言）
  • 多格式导出（HTML、PDF、LaTeX、Markdown、EPUB）

这一切都运行在单一纯文本文件体系中。因为是纯文本，可以用Git版本控制，用grep搜索，用任何编辑器打开。但只有在Emacs的org-mode中，所有功能才会真正活起来。

2.2 为何无法替代

Notion、Obsidian、Roam Research、Logseq——都是优秀的工具。但它们各自只实现了org-mode的一部分。在文档中运行代码并嵌入结果（org-babel）、议程视图与CLOCK计时一体化、以及用Emacs Lisp对整个系统进行完全编程——三者兼备的工具目前仍只有org-mode。

对开发者来说，org-babel尤为重要。用Python获取数据，整理成表格，导出为LaTeX文档——整个流程记录在一个可复现的org文件中。这不是笔记应用，而是文学化编程（literate programming）的实用实现。

三、学习曲线与回报——诚实的计算

3.1 为什么真的很难

Emacs学习曲线声名狼藉有其原因。第一，键绑定体系与现代惯例相差甚远：C-x C-s保存，C-x C-f打开文件——这是几十年前设计的体系，习惯了Ctrl+S和Ctrl+O的手会最初「反叛」。第二，配置是Lisp代码，不像现代工具用JSON或YAML，Emacs配置意味着写Emacs Lisp。越学越强大，但入门门槛实在不低。第三，「正确的起点」太多——原生Emacs、Doom Emacs、Spacemacs或从零配置，不知从哪里开始。

3.2 Doom Emacs和Spacemacs的改变

预配置发行版大幅降低了这一门槛。Doom Emacs提供Vim风格键绑定（Evil模式）和经过优化的软件包配置。Spacemacs将Vim与Emacs以层（layer）模式整合。两者都不需要从一开始就写Lisp。Vim用户可以借助Evil模式，用熟悉的手部动作进入Emacs生态。

2026年又加入了AI助力。用gptel向LLM询问Emacs Lisp配置，曾经需要翻查邮件列表的工作变成了对话式协作。自定义配置的门槛明显降低。

3.3 投资回报的计算

一位开发者的测算给出了现实参考：用Emacs每天节省15分钟，一年约积累65小时（近3天）。10年则是30天。这不是夸张——熟练的Emacs用户通过键盘完成文件导航、搜索、替换、缓冲区切换和Git操作，全程不动鼠标。但要实现这30天的节省，前期需要100小时以上的投入。对着眼长远职业生涯的开发者来说划算，但对需要立即上线交付的场合并不适合。

四、黑客文化与哲学——Emacs象征着什么

4.1 自由软件运动的第一款杀手级应用

GNU Emacs不只是软件，更是一种宣言。1983年Richard Stallman启动GNU计划时，Emacs是他最先构建的工具，也是自由软件能与商业软件媲美甚至超越的最初证明。Stallman将自己描述为1970年代MIT AI实验室黑客文化——源代码开放、任何人都可修改、软件应当共享的哲学——的幸存者。GNU Emacs是这一哲学的具现化。

使用Emacs带有这段历史与哲学。Emacs社区之所以有独特的凝聚力，正是因为选择这款编辑器也意味着认同某种技术伦理。

4.2 键盘自主性与远程工作

Emacs用户普遍强调无需鼠标即可工作。这不是审美偏好，而是生产力问题。手从键盘移到鼠标再移回来的时间，每天反复累积下来相当可观。Emacs的键绑定体系设计用于最小化这种切换。熟练用户描述其为「键盘成为思维的延伸」。

这种自主性在SSH环境中更为突出。通过SSH连接远程服务器，无需GUI，Emacs在终端中照样发挥全部功能。VS Code的Remote SSH扩展大幅弥补了这一差距，但在连接不稳定或资源受限的环境中，基于终端的编辑器仍有实质优势。基础设施工程师和系统管理员在远程服务器上常驻运行Emacs的原因正在于此。

五、当前使用情况——诚实的数字

5.1 市场份额现实

数字很清晰。Stack Overflow 2025年开发者调查中VS Code占75.9%。Emacs在LinuxQuestions民调中约为8至9%——远低于Vim/Neovim的37至38%。在AI原生编辑器领域，Cursor首年就达到17.9%，Claude Code达到9.7%，而Emacs在统计中几乎无迹可寻。以人气指标论，Emacs无从辩护。

5.2 活跃开发讲述另一个故事

开发活动是另一个维度。GNU Emacs 30.2于2025年8月发布，其更新内容体现了持续现代化的投入：

  • 原生编译默认启用：通过libgccjit将Emacs Lisp编译为机器码，Magit和org-mode等包运行速度大幅提升
  • which-key内置：无需第三方包即可显示键绑定提示
  • EditorConfig内置支持
  • Tree-Sitter模式扩展：新增Elixir、HEEx、HTML、Lua、PHP等语言模式
  • 原生Android支持（触摸屏、虚拟键盘）
  • JSON解析和子进程处理性能提升

这不是靠惯性维护遗留代码的项目，而是在积极将曾需第三方包的功能内置化，并向新平台延伸。

六、AI编码时代的Emacs

6.1 AI集成生态

AI编码工具已成为2026年编辑器选择的决定性变量。Emacs的应对出乎意料地扎实：

  • gptel：在任意Emacs缓冲区中以对话形式使用Claude、GPT、Gemini、Ollama等LLM，支持MCP（模型上下文协议）集成。自0.9版起原生支持Anthropic后端。
  • copilot.el：直接连接GitHub Copilot语言服务器，提供内联幽灵文本补全。2025年初升级为官方Node包基础。
  • ellama：基于Ollama等本地LLM的代码摘要、重构、翻译等任务特化命令。
  • aider.el：AI配对编程工具Aider的Emacs集成。
  • Claude Code：基于终端，与编辑器无关。Emacs用户在终端运行Claude Code，在Emacs缓冲区中审查结果。

Emacs「一切皆可扩展」的特性在AI集成中同样适用。将gptel与org-babel结合，可以将AI回答自动记录到org文档，或在缓冲区中即时执行AI生成的代码——这些工作流在更为封闭的环境中难以复现。

6.2 AI原生编辑器的优势

坦率来说，在内联AI编码体验上，Cursor和集成了Copilot的VS Code比Emacs更流畅。Cursor从底层就以AI为核心设计，多文件上下文理解、代码库级查询和一键应用在同一环境中完成闭环。Emacs的AI工具链虽然强大，但需要自行组装，更像「零件套装」而非「成品」。这与Emacs哲学一致，但对于想要开箱即用获取最佳AI编码体验的用户来说，这是一个真实的权衡。

七、2026年谁该选Emacs，谁不该选

7.1 适合选择Emacs的情况

  • 希望像管理代码一样管理知识 → org-mode
  • 希望用Lisp完全重新设计编辑器行为 → Emacs Lisp可扩展性
  • 大量使用SSH或资源受限的环境
  • 希望数十年使用同一工具
  • 认同自由软件哲学（GNU GPL）

7.2 不适合选择Emacs的情况

  • 团队统一使用VS Code，协作扩展很重要
  • 希望开箱即用获得最流畅的AI内联体验 → 选择Cursor
  • 需要立即上手高效工作 → 学习曲线是真实负担
  • 偏好GUI驱动的配置方式 → VS Code的图形设置更合适

7.3 非此即彼，还是光谱选择

「编辑器战争」以VS Code压倒性获胜而告终——这是事实。但这不意味着「Emacs是错的」。工匠为特定工作选择手工具而非自动化机械，并不是非理性——对特定任务和特定工作者而言，那就是最优选择。Emacs为其用户提供「一款终身学习的编辑器」：不是接受一个成品，而是持续构建自己想要的工具的过程。享受这一过程的开发者，对他们而言Emacs不只是生产力工具，而是编程本身的延伸。

八、结语——50年后仍会有人使用Emacs

直接回答GeekNews的问题：是的，还有人在用Emacs。而且以后也会有。原因不是人气，而是Emacs所填补的特定需求并未消失——用org-mode将知识作为可编程文本来管理，用Emacs Lisp将编辑器重塑为自己思维的镜像，在任何环境下用同一套键盘体系工作。

截至2026年6月，GNU Emacs 30.2处于活跃开发中，仍有新人入门，AI集成包持续发布。一款50年老编辑器的生命力并非来自市场份额，而来自不可替代的功能与无限的可定制性。这足以支撑它继续存在，直到下一代AI编辑器让Cursor也显得过时的那一天。
