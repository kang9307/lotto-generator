Specify - AI開発で消える「なぜ」を守るワークスペース

コードは一瞬で生まれるが、決定根拠はチャット画面から蒸発する - 何が問題で、何で埋めるか

2026-07-02 開発・インフラ

序論: コードは残るが理由は消える

AI コーディングエージェントに機能一つを任せると、数分で動くコードが出てくる。ところが翌日そのコードをなぜそう書いたのか改めて尋ねると、答えられる人がいない場合が増えている。なぜこのライブラリを選んだのか、なぜこのパターンを捨てて別のパターンを選んだのか、どんな代案を検討して捨てたのか - この全ての思考過程はエージェントと交わしたチャット画面の中にだけあり、画面を閉じた瞬間に一緒に蒸発する。GeekNews に投稿された Specify というツールは、まさにこの問題、つまり AI で開発するときに消える 「なぜ(why)」を守るワークスペースを掲げる。

本稿は Specify という一つの製品を宣伝しようとするものではない。Specify は 2026年7月時点でオープンベータ段階の小さなスタートアップ製品であり、公開されている情報も限られている。代わりに、この製品が示す大きな流れ - スペック駆動開発(spec-driven development)とアーキテクチャ決定記録(ADR)という古い概念が AI コーディング時代になぜ再び呼び戻されているのか - を本人の実務経験に照らして分析する。ツールの名前は変わり続けるだろう。しかし「AI が作ったコードにはなぜが無い」という問題そのものは当分消えないというのが本人の判断だ。

1. Specify が語る問題 - 繰り返されるオンボーディングとコードレビューの質問

Specify の公式ページが掲げる問題定義は素朴だが的確だ。チーム規模が大きくなるほど、同じオンボーディングの質問、同じコードレビューの質問が繰り返されるというものだ。「この関数はなぜこう書いたのか」「このサービスはなぜこのアーキテクチャを選んだのか」といった質問に、毎回誰かが記憶をたどって答えるか、答えられる人がすでに退職していて誰も分からない状況が繰り返される。

1.1 ワークスペースメモリというアプローチ

Specify が提示する解決策は ワークスペースメモリ(Workspace Memory)だ。GitHub、Notion、Slack、Jira、Linear のような複数のツールに散らばったスペック・リサーチ・意思決定を一箇所に集め、決定の背景(なぜこうしたのか)をコード・イシューと一緒に記録しておくという概念だ。その上で AI エージェントがチームが許可した範囲内で反復業務を処理し、処理結果を再びワークスペースへ書き戻す。PM・PO はスペックと意思決定の追跡に、開発者は反復業務の委任に、リーダーは組織知識の要約と迅速な意思決定にこのメモリを使うというのが公開されているユーザーシナリオだ。

1.2 AI エージェントが文脈へ直接アクセスするということ

ここで本人が注目する点は「AI エージェントがこの文脈へ直接アクセスできるよう設計した」という部分だ。これまでのドキュメント化ツールの多くは人が読むために作られてきた。一方 Specify 型のワークスペースが狙うのは、人とエージェントが同じ文脈を共有する状態だ。Claude Code のようなコーディングエージェントが作業を始める前に「このプロジェクトはなぜこの構造を選んだのか」を照会できれば、毎回最初から説明を入力し直す必要が減る。これはプロンプトエンジニアリングの繰り返しコストを減らす問題であると同時に、エージェントが既存の決定と矛盾するコードを生成する危険を下げる問題でもある。

2. AI コーディング時代に「なぜ」が消える構造的理由

この問題は Specify が最初に指摘したものではない。2025年から続く「バイブコーディング(vibe coding)」論議の延長線上にある。ただ本人は、この現象を三つの層に分けて見る方が実務的に有用だと考える。

2.1 生成速度と思考記録速度の不均衡

人が直接コードを書くとき、悩む時間そのものが思考の記録役を兼ねる。ある方式を試して捨て、なぜ捨てたのかを同僚に説明し、その説明がコミットメッセージや PR コメントに自然に残る。ところが AI エージェントにプロンプトを投げて結果コードを受け取る流れでは、この時間がまるごと消える。エージェントが代案を検討したとしても、その検討は会話ログの中で起きただけで、コードベースのどこにも痕跡を残さない。コード生成速度が人の思考記録速度を追い越すことで、成果物は残り思考過程は蒸発する非対称が構造的に生じる。

2.2 ドリフト - もっともらしいが誤ったコード

本人が調査した 2026年の業界論議で繰り返し登場する言葉が ドリフト(drift)だ。問題はコード生成速度ではなく、自信ありげでもっともらしく見えるが元の問題を静かに誤って解いているコードが積み上がっていく現象だという指摘だ。エージェントは文法的に正しくテストも通るコードを素早く作り出す。しかしそのコードが元々チームが意図した制約 - 例えば「この API は下位互換を必ず維持しなければならない」といった暗黙の要求 - を守ったかどうかは別問題だ。なぜ(rationale)が文書化されていなければ、この逸脱を次のレビュアーも次のエージェントも気づく方法が無い。

2.3 セキュリティ・品質リスクへつながる連鎖

本人が調査過程で確認した数値もこの問題の重みを示す。ベンチマークによって LLM が生成したコードの脆弱性比率は 9.8% から 42.1% まで報告されており、2026年2月時点でプロダクションリポジトリに残る AI 由来のイシューが 11万件を超えたという調査もある。この数値をそのまま鵜呑みにするより方向性として読むのが正確だろうが、決定根拠が残らないコードベースでは、こうしたイシューが積み重なってもなぜその選択をしたのかを追跡する根拠自体が無いという点は明らかだ。「なぜ」の不在は単なる文書化の怠慢ではなく、保守・セキュリティ検討・オンボーディング全体のコストを押し上げる構造的リスクへつながる。

3. スペック駆動開発(spec-driven development)との接続

Specify という名前自体が示唆するように、この問題の一つの軸は スペック駆動開発という流れと直接つながっている。

3.1 定義と目標

スペック駆動開発は、コードではなく実行可能なスペック(仕様)を真実の源とするアプローチだ。チームや AI エージェントがまず何を作るかの詳細なスペックを作成し、そこから実装計画を導き出し、これを原子的なタスクに分割してから初めてコードを生成する。GitHub Spec Kit、AWS Kiro、Claude Code、Cursor、OpenSpec、BMAD、Tessl、Google Antigravity など 2026年の主要 AI コーディングツールがそれぞれこのアプローチの変種を出したという事実は、これが一ベンダーのマーケティングではなく業界全体の対応であることを示す。

3.2 実務効果として報告された数値

本人が確認した業界報告の中で目を引くのは、GitHub が内部プロジェクトで Spec Kit を使ったチームが場当たり的なプロンプティング比で「最初から作り直す」サイクルを桁単位で減らしたと述べた部分と、AWS Kiro が 40時間分の機能をスペック優先で書いたとき人の実作業時間が 8時間以下に減った事例を公開した部分だ。この数値はベンダー発表であるため額面通り受け取るより、「スペックを先に書くと再作業が減る」という方向性の根拠として読むのが安全だ。ただ方向自体は本人の実務感覚とも一致する。スペック無しでエージェントに反復指示を出すより、最初に制約と意図をスペックとして釘付けしておく方が往復回数を減らす。

3.3 スペックと Specify 型ワークスペースの違い

ただしスペック駆動開発と Specify が完全に同じものではない。スペック駆動開発は「コードを生成する前に何を作るか明記せよ」という開発プロセスに近く、Specify は「その明記と決定背景をチーム全体が共有する記憶装置として維持せよ」というワークスペース層に近い。前者が作業単位の規律だとすれば、後者はその規律の成果物を時間が経っても見つけられるよう保管し、エージェントが再照会できるようにするインフラだ。スペックさえきちんと書けば当面のドリフトは減るが、そのスペックと決定背景が次の四半期、次の担当者まで残るには別途の保管・検索層が必要だというのが本人の判断だ。

4. ADR(アーキテクチャ決定記録)との接続

「なぜ」を残す実践は実は AI 以前から存在した。まさに アーキテクチャ決定記録(Architecture Decision Record, ADR)だ。

4.1 ADR の元々の役割

ADR は一つのアーキテクチャ決定とその根拠、検討した代替案、受け入れたトレードオフを短い文書として残す古くからの慣行だ。核心目的は「なぜこのアーキテクチャ決定を下したのか理解する助けとなること」であり、その根拠を知らなければ後で先の決定を無効化する新たな決定が下されるなど災厄的な結果につながりかねないというのが、この慣行が存在する理由だ。伝統的に ADR は承認後は不変として扱われる静的文書だった。

4.2 AI時代、ADR が静的文書から生きた制約へ

本人が調査した 2026年の論議で興味深い点は、ADR の性格そのものが変わりつつあるということだ。AI エージェントが実際に決定ループへ参加してコードを書き、マイグレーションを計画し、アーキテクチャ図まで生成するようになり、静的文書フォーマットがこの流れに自然に馴染まないという指摘が出ている。その結果、AGENTS.md のようなエージェント指示ファイルは ADR と異なり、アーキテクチャが変われば一緒に進化しなければならない生きた文書として定着しつつある。そして実務的な助言として「AI コーディングツールに該当領域を直す前に関連記録をまず読めと指示せよ」というものと、「AI が従えるほど明確に説明できないアーキテクチャ制約なら、そもそも人にも明確に説明できていない可能性が高い」という洞察が出てくる。この二つ目の洞察は本人が特に印象深く見た部分だ。AI のための明確な文書化要求が、逆説的に人のための文書化品質まで引き上げる圧力として働くということだ。

4.3 ADR・スペック・ワークスペースメモリを一つの軸として見る

整理すると、ADR、スペック駆動開発、Specify 型ワークスペースメモリは名前は違うが一つの軸の上にある。ADR は決定一つ一つを記録する最小単位、スペック駆動開発はその記録をコード生成以前の段階へ引き寄せ規律化したプロセス、ワークスペースメモリはこれら全ての成果物をチームとエージェントが一緒に照会できるよう維持するインフラ層だ。三つとも結果ではなく理由を残すという同じ原則を、異なる層でそれぞれ実装しているに過ぎない。

5. 実践法 - ツール無しでも始められること

Specify のような専用ワークスペースが無くても、本人の判断では今すぐ適用できる実践法がある。ツールより習慣が先だというのが本人の見方だ。

5.1 リポジトリ内に軽量な ADR ディレクトリを置く

専用の SaaS が無くても `docs/adr/` のようなディレクトリに決定一つにつきファイル一つ、五、六行の記録(文脈・決定・代案・トレードオフ)を残すだけでかなりの部分を代替できる。重いテンプレートより「なぜこのライブラリを捨てたのか」を一、二文でも残す習慣が核心だ。この記録はコードと同じリポジトリにあるためコミット履歴と一緒に永続保存され、以後 AI エージェントにもそのままコンテキストとして渡せる。

5.2 エージェント指示ファイルに「なぜ」を刻み込む

AGENTS.md や CLAUDE.md のようなエージェント指示ファイルを単なるコーディングスタイルガイドとしてだけ使わず、核心的なアーキテクチャ制約とその理由を一緒に書いておくのが効果的だ。「このモジュールは同期 API を使わない」より「このモジュールは過去の非同期移行中に発生したレースコンディションのため同期 API を使わない」のように、規則と根拠を一緒に書けば、エージェントが規則を回避しようとする試みを自ら減らす可能性が高まる。

5.3 エージェントにコード生成前に「なぜ」一行を先に求める

エージェントに機能実装を任せるとき、コードから受け取らず「この方式を選んだ理由と検討して捨てた代案をまず一、二文で説明せよ」という指示を習慣化すれば、その結果を PR の説明やコミットメッセージにそのまま貼り付けられる。これは Specify がワークスペースメモリとして自動化しようとする手順を、ツール無しでプロンプト習慣だけで真似る方法だ。完全に同じではないが、今日すぐ費用無しで始められる点で実用的だ。

5.4 オンボーディング文書を決定記録と切り離さない

Specify が指摘した元々の問題、すなわち繰り返されるオンボーディングの質問に立ち返ると、オンボーディング文書と決定記録を別々の文書として管理する慣行自体が問題の一部だ。「このコードはなぜこう書いたのか」への答えがオンボーディング資料にも ADR にも無く、特定の人の記憶だけにあるなら、その人がいなくなった瞬間に根拠も一緒に消える。オンボーディング文書から核心決定へ直接リンクを張るだけでも、繰り返される質問のかなりの部分を減らせる。

6. 限界と注意点

長所だけを語るのは正直ではない。押さえるべき限界がある。

6.1 記録そのもののコストと持続可能性

決定根拠を残す習慣はそれ自体が時間コストだ。速度を理由に AI エージェントを使うチームほど、「なぜ」を記録する手順が再びボトルネックに感じられる危険がある。スペック駆動開発陣営が強調するように、この手順は数分単位の短いループで維持されるときのみ持続可能であり、そうでなければ結局最初に省略される段階になる。

6.2 Specify 自体はまだ検証初期段階

Specify は 2026年7月時点でオープンベータであり、公開情報だけでは具体的な統合リスト(MCP サポート範囲、実際の Jira・Linear 連携方式)や価格ポリシーが明確に確認できない。これはこの製品一つを過小評価しようとするものではなく、この範疇のツール全般がまだ初期段階であるため導入前の自己検証が必要だという意味だ。ただしこのツールが狙う問題そのものは実体がある。

6.3 ツールは習慣の代わりにはなれない

ワークスペースメモリであれ ADR ディレクトリであれ、ツールは記録の保管と検索を助けるだけで、そもそも記録しなければ何の役にも立たない。チーム文化に「なぜ」を問い答える習慣が無ければ、どれほど精巧なワークスペースを導入しても空のフォルダが増えるだけだ。ツール導入より先に必要なのは、コードレビューで「これはなぜこうしたのか」という質問が自然に交わされる文化だ。

7. 結論 - 今日から適用できる3つ

AI コーディングエージェントが作るコードの量は増え続けるだろう。問題はそのコードがどれだけ速く作られるかではなく、そのコードの背後にあった判断が数日後、数ヶ月後にも取り出せるかどうかだ。Specify はこの問題をワークスペースメモリという形で解こうとする複数の試みの一つであり、スペック駆動開発と ADR は同じ問題を異なる層で長く扱ってきた概念だ。三つを貫く原則は一つ。結果ではなく理由を残せ。

今週本人が実行する具体的な三つ。

7.1 リポジトリで軽量 ADR 習慣を今日始めよ

重いツールの導入を待たず、`docs/adr/` ディレクトリ一つと五、六行のテンプレートで今日から始めよ。次のアーキテクチャ決定一つにだけ適用しても違いが始まる。

7.2 エージェント指示ファイルに規則ではなく理由を書け

AGENTS.md・CLAUDE.md に「するな」だけ書かず「なぜしてはいけないか」を一行でも付け加えよ。この一行が次のエージェントセッションで、そして次の人間レビュアーから繰り返される質問を減らす。

7.3 コード生成前に「なぜ」一行を先に求めるプロンプト習慣をつけよ

エージェントにコードから求めず、選択理由と捨てた代案を先に短く説明せよと指示せよ。この習慣が定着すれば、Specify のような専用ワークスペースを導入するときも、すでに埋めるコンテンツが積み上がった状態で始められる。
