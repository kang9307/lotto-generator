OpenAI가 10억 사용자의 스토리지를 버티는 법 - 엔지니어 2명이 끝낸 Rust 재작성

초당 7,000만 요청과 500PB 데이터를 지탱하는 온라인 스토리지 Habitat의 설계와 인프라 튜닝 교훈

2026-09-14 개발/인프라

전 세계 10억 명 이상의 주간 활성 사용자가 매일 ChatGPT와 대화하고, Codex에 코딩 지시를 내리며, 복잡한 워크플로를 처리할 때 시스템 이면에서는 어떤 일이 벌어질까? 사용자가 브라우저 창에서 로그인 버튼을 누르고, 프롬프트를 전송하며, 이전 대화 목록을 불러오는 매 순간마다 수십에서 수백 번의 온라인 데이터 조회가 밀리초 단위로 실행된다. 단 하나의 요청이라도 네트워크 지연이나 백엔드 병목으로 흔들리면 사용자는 즉각적인 서비스 버벅거림을 경험하게 된다.

이 거대한 트래픽 폭풍의 최전선에서 OpenAI의 모든 주요 제품 데이터를 전담 처리하는 온라인 스토리지 플랫폼이 바로 Habitat이다. 2026년 9월 OpenAI 엔지니어링 팀이 공식 기술 블로그를 통해 공개한 바에 따르면, Habitat은 현재 전 세계 약 40개 지역(Regions)에 분산 배포되어 초당 7,000만 건(70M+ RPS) 이상의 요청을 처리하고 있으며, 저장 관리하는 데이터 규모만 500페타바이트(PB) 이상에 달한다. 지난 3년간 연간 10배(10x YoY)씩 폭발적으로 성장해 온 이 인프라는 단지 스케일아웃 장비를 무한정 늘리는 것만으로는 결코 버텨낼 수 없었다.

더욱 놀라운 사실은 이 거대한 분산 스토리지 서비스를 밑바닥부터 Rust로 전면 재작성한 주체가 단 2명의 엔지니어였다는 점이다. 이들은 사내의 차세대 AI 코딩 에이전트인 Codex와 GPT-5.5를 적극적으로 활용하여 2026년 2분기 단 몇 개월 만에 전체 마이그레이션을 완수했다. 그 결과 Python 서비스 대비 CPU 효율 6배, 메모리 효율 15배라는 압도적인 성능 향상을 달성했으며, 현재 전체 프로덕션 트래픽의 95%를 Rust 스택으로 처리하고 있다. 이 글에서는 Habitat이 단순한 클라이언트 라이브러리에서 출발해 초대규모 분산 서비스로 발전해 온 아키텍처 진화 과정, Python 환경에서 겪었던 asyncio 꼬리 지연과 커넥션 풀의 준안정 장애(Metastable Failure), 그리고 AI 코딩 에이전트가 완성한 Rust 재작성의 실전 교훈을 가감 없이 짚어본다.

이 글은 OpenAI 엔지니어링 팀이 2026년 9월 11일 공개한 기술 보고서 「Rapidly scaling online storage to serve over 1 billion ChatGPT users」 원문과 공식 발표 자료를 기반으로 작성되었습니다. 원문에서 공식 확인된 지표와 아키텍처 원리만을 다루며, 확인되지 않은 수치나 추측성 서술은 일절 배제하였습니다.

500PB와 초당 7,000만 요청 — Habitat이 마주한 규모의 벽

Habitat의 처리 규모는 일반적인 대규모 웹 서비스의 상상을 아득히 초월한다. 초당 7,000만 건의 요청이란 단 1분 동안 42억 건, 하루 동안 6조 건 이상의 스토리지 읽기·쓰기 연산이 전 세계 40여 개 데이터센터에서 쉼 없이 오간다는 뜻이다. 500PB라는 저장 데이터 역시 단순 백업 파일이나 비정형 로그가 아니라, 매일 10억 명 이상의 사용자가 실시간으로 조회하고 갱신하는 핫(Hot) 온라인 데이터의 총량이다.

OpenAI 제품군에서 발생하는 사용자 상호작용은 단일 요청이라 할지라도 내부적으로 수많은 데이터 종속성을 갖는다. 사용자가 대화를 입력하면 사용자 인증 토큰 검증, 조직별 권한 및 정책 확인, 과거 대화 세션 컨텍스트 로딩, Codex 도구 설정 조회, 안전성 필터링 룰셋 대조 등이 연쇄적으로 일어난다. 평균적인 사용자 요청 1건이 내부적으로 수백 번의 데이터베이스 조회로 증폭되는 구조다. 따라서 온라인 스토리지 계층의 지연 시간이 수 밀리초만 늘어나도, 최상단 사용자가 체감하는 생성 응답 시작 시간(TTFT)은 치명적인 타격을 입게 된다.

이러한 초고성장 국면에서 Habitat 팀이 채택한 엔지니어링 우선순위는 명확했다. 플랫폼의 발전 단계는 철저하게 다음의 3단계 원칙에 따라 조율되었다:

  • 핵심 제품 트래픽을 위한 무조건적 신뢰성 — 서비스 가동 중단이나 데이터 불일치는 어떠한 성능 지표보다 우선하여 방지되어야 했다.
  • 전 세계 사용자를 위한 극한의 응답 속도 — 40개 지역에 분산된 환경에서 꼬리 지연(Tail Latency)을 억제하고 데이터 지역성을 극대화했다.
  • 폭발적 스케일아웃을 감당하는 대규모 운영 역량 — 전년 대비 10배씩 늘어나는 트래픽과 데이터 용량을 엔지니어링 리소스 증가 없이 흡수할 수 있는 구조를 구축했다.
  • 저수준 최적화를 통한 물리적 컴퓨팅 한계 돌파 — 클라우드 벤더의 가용 용량 고갈에 직면하기 전에 소프트웨어 스택 전반의 CPU 및 메모리 효율을 극한으로 끌어올렸다.

Habitat은 처음부터 거대한 분산 시스템으로 기획된 것이 아니었다. 2023년 말 DevDay 행사에서 발표된 맞춤형 챗봇 생태계인 GPTs를 뒷받침하기 위해, 단일 데이터베이스에 붙는 아주 작은 Python 클라이언트 라이브러리로 소박하게 출발했다. 그러나 제품 팀들의 채택이 폭발적으로 늘어나고 ChatGPT가 글로벌 대중 서비스로 자리 잡으면서, 초기 스택의 모든 구성 요소는 근본적인 한계에 부딪히게 되었다.

엔지니어 2명과 Codex·GPT-5.5 — Rust 재작성이 보여준 생산성 혁명

대규모 인프라 운영에서 프로덕션 언어를 완전히 교체하는 재작성(Rewrite) 프로젝트는 엔지니어링 조직의 악몽으로 꼽힌다. 수년간 축적된 방대한 비즈니스 엣지 케이스, 수천 개의 예외 처리 규칙, 복잡한 모니터링 및 메트릭 파이프라인, 그리고 수십 개 제품 팀과의 암묵적인 인터페이스 계약을 새로운 언어로 무중단 전환하는 데는 일반적으로 수십 명의 시니어 엔지니어와 수년의 기간이 소요된다.

그러나 OpenAI는 2026년 2분기, 단 2명의 엔지니어만으로 Habitat 전체 서비스의 Rust 재작성을 성공리에 마쳤다. 이 기적적인 생산성의 핵심 동력은 외부 인력이 아니라, OpenAI가 직접 개발한 차세대 AI 코딩 모델인 Codex와 GPT-5.5였다. 엔지니어들은 시스템 아키텍처 설계, 동시성 모델 정의, 불변성 보장 규칙, 데이터 정합성 검증 등 핵심 엔지니어링 결정에 집중하고, 수만 줄의 Python 코드를 고성능 안전한 Rust 코드로 전환하고 섀도잉 테스트를 구축하는 세부 구현 작업은 AI 코딩 에이전트와 긴밀하게 페어 프로그래밍을 진행했다.

그 결과물은 단순히 코드를 옮겨 적은 수준을 넘어섰다. Rust로 재탄생한 Habitat 서비스는 기존 Python 서비스 대비 비약적인 리소스 절감과 성능 격차를 입증했다:

  • CPU 효율 6배 향상 — GIL(Global Interpreter Lock)의 제약과 인터프리터 오버헤드가 사라지면서 동일한 하드웨어 코어에서 6배 더 많은 트래픽을 처리했다.
  • 메모리 효율 15배 향상 — 파이썬 객체 래핑 비용과 가비지 컬렉션(GC) 압박이 완전히 제거되어 극단적인 메모리 압축 효과를 거두었다.
  • 프로덕션 트래픽 95% 전환 달성 — 2026년 2분기 재작성 직후 빠르게 트래픽을 이관하여 현재 전체 요청의 95%를 Rust 서비스가 직접 처리 중이다.
  • 기존 Python 서비스의 완전 폐기 수순 — 잔여 트래픽에 대한 안정성 검증이 완료됨에 따라 향후 수주 내로 레거시 Python 서비스를 완전히 퇴역(Deprecation)시킬 예정이다.

아래 표는 OpenAI 공식 발표 및 기술 블로그를 통해 공인된 Python 구현체와 Rust 구현체 간의 실측 운영 지표를 요약 대조한 것이다.

이 사례는 소프트웨어 엔지니어링 역사에서 매우 상징적인 변곡점을 시사한다. "AI 에이전트가 생성한 코드는 장난감 프로젝트에나 쓸모 있다"는 회의론을 정면으로 반박하며, 초당 수천만 건의 트래픽을 다루는 미션 크리티컬 글로벌 분산 스토리지조차 AI 코딩 에이전트의 주도로 안전하고 완벽하게 현대화될 수 있음을 세계 최대 규모의 인프라에서 실증했기 때문이다.

라이브러리에서 독립 분산 서비스로 — 롤백 사고가 남긴 교훈

Habitat의 초기 아키텍처는 오늘날과 같은 독립된 원격 마이크로서비스가 아니었다. 2024년 중반까지 Habitat은 각 제품 팀(ChatGPT 서버, Codex 엔진, 사용자 인증 모듈 등)의 애플리케이션 코드베이스에 패키지 형태로 포함되는 Python 공유 클라이언트 라이브러리로 운영되었다.

공유 라이브러리 방식은 도입 초기에 엄청난 속도 이점을 가져다주었다. 제품 엔지니어들은 데이터베이스 연결 풀 관리나 암호화 알고리즘을 고민할 필요 없이 몇 줄의 함수 호출만으로 데이터를 저장할 수 있었다. 게다가 개발자들은 라이브러리 코드에 클라이언트 측 인메모리 캐싱, 압축 로직, 직렬화 로직을 직접 수정하여 기여할 수 있었기 때문에 사내 채택 속도는 상상을 초월할 정도로 빨랐다.

그러나 2025년 중반에 접어들면서, 이 라이브러리 중심 구조는 치명적인 기술적 부채로 변모했다. 수십 개의 서로 다른 독립 서비스가 각기 다른 배포 주기와 릴리스 일정을 가진 상태에서, 공유 라이브러리의 하위 호환성을 유지하며 스토리지 프로토콜을 변경하는 일은 사실상 불가능해졌다. 결정적인 사건은 리전 장애 격리를 위한 데이터베이스 샤딩 프로젝트에서 터져 나왔다.

특정 리전의 Azure Cosmos DB 장애가 전 세계 서비스로 전파되는 반경(Blast Radius)을 줄이기 위해, Habitat 팀은 핵심 데이터셋을 지역별 Cosmos DB 계정으로 분할하는 아키텍처 개편을 단행했다. 이 변경을 안전하게 롤아웃하려면 다음과 같은 고통스러운 절차를 밟아야 했다:

  • 수십 개 클라이언트에 라우팅 로직 선배포 — 기능 플래그(Feature Flag)로 비활성화된 신규 라우팅 코드를 모든 제품 팀의 서비스에 배포하는 데만 수일이 소요되었다.
  • 섀도잉 트래픽 검증과 결함 수정의 지연 — 샤딩 유효성을 검증하기 위한 섀도잉 로직을 추가하고 버그를 패치할 때마다 또다시 모든 제품 팀의 재배포 일정을 동기화해야 했다.
  • 무관한 팀의 롤백으로 인한 연쇄 장애 — 마침내 모든 서비스에 플래그를 켤 준비가 완료된 순간, 한 제품 팀이 스토리지와 무관한 자체 버그로 인해 서비스를 이전 버전으로 롤백했다. 그 결과 해당 서비스는 결함이 있는 구형 Habitat 라이브러리를 실행하게 되었고, 팀이 그토록 피하고자 했던 대규모 프로덕션 장애가 기어이 발생하고 말았다.
  • 중앙 통제력 부재로 인한 보안 및 거버넌스 취약 — 각 파드에 분산된 라이브러리는 세밀한 접근 제어, 감사 로그 집계, 악의적 에이전트로부터의 데이터 격리를 보장하기 어려웠다.

이 쓰라린 장애를 겪은 후, Habitat 팀은 과감한 아키텍처 결단을 내렸다. 스토리지 접근 로직 전체를 애플리케이션 파드에서 완전히 떼어내어, 독자적인 수명 주기와 배포 파이프라인을 갖춘 독립 분산 서비스(Standalone Distributed Service)로 분리한 것이다.

독립 서비스로의 전환은 극적인 거버넌스 향상을 가져왔다. 이제 새로운 라우팅 규칙이나 샤딩 전략, 최적화 패치를 배포할 때 수십 개 제품 팀의 일정을 조율할 필요가 없어졌다. Habitat 클러스터만 단독으로 무중단 롤링 업데이트하면 모든 제품에 즉각 최신 인프라가 적용되었다. 또한 중앙 집중식 감사 로깅과 강력한 인가(AuthZ) 정책을 적용하여, 외부 공격은 물론 내부 프로세스나 자율 AI 에이전트의 오작동으로부터 사용자 데이터를 견고하게 방어할 수 있게 되었다.

Python을 당장 버리지 않은 이유와 꼬리 지연(Tail Latency) 튜닝

Habitat을 독립 서비스로 격리하면서 가장 먼저 직면한 기술적 논쟁은 "어떤 언어로 서비스를 구현할 것인가"였다. 로컬 인메모리 라이브러리 호출과 달리, 원격 서비스로의 전환은 필연적으로 네트워크 홉(Hop), 데이터 직렬화/역직렬화 오버헤드, CPU 및 메모리 사용량 증가를 유발한다. 순수 성능 관점에서 본다면 C++이나 Rust 같은 네이티브 컴파일 언어로 당장 재작성하는 것이 마땅해 보였다.

그러나 Habitat 팀은 전략적 기술 부채(Strategic Technical Debt)를 의도적으로 선택했다. 당시 OpenAI의 최우선 당면 과제는 미지의 성능 최적화가 아니라, 폭발적으로 쏟아져 나오는 신규 제품 기능의 병목을 해소하고 스토리지 플랫폼의 안정적인 인터페이스를 안착시키는 것이었다. 익숙하고 유연한 Python으로 서비스를 빠르게 구축함으로써 비즈니스 요구에 민첩하게 대응하는 것이 기업 전체에 훨씬 큰 가치를 제공했다. 팀은 훗날 트래픽이 100배로 커지면 재작성이 불가피하겠지만, 그때가 되면 진화한 Codex와 GPT 모델들이 언어 전환 비용을 획기적으로 낮춰줄 것이라 계산했고, 이 대담한 베팅은 정확히 적중했다.

문제는 서비스 초기 Python 환경에서 뿜어져 나오는 꼬리 지연(Tail Latency, p99/p99.9)이었다. 단일 사용자 요청이 수백 번의 스토리지 조회를 유발하는 환경에서, 극소수의 꼬리 지연은 전체 서비스 응답 시간을 끌어내리는 주범이 되었다. 팀은 Python 스택의 성능을 한계까지 쥐어짜 내기 위해 집요한 엔지니어링 튜닝에 착수했다.

asyncio 스케줄링 지연과 이벤트 루프 혼잡 측정

Python의 asyncio는 논블로킹 I/O를 처리하는 데 매우 탁월하지만, 단일 스레드 이벤트 루프 모델이라는 근본적인 한계를 지닌다. GIL(Global Interpreter Lock)로 인해 진정한 CPU 병렬성을 제공하지 못하며, 만약 어떤 코루틴이 CPU 연산을 길게 수행하면 이벤트 루프 전체가 멈칫(Stall)하게 된다.

초기 모니터링에서 하위 데이터베이스(Azure Cosmos DB)는 수 밀리초 만에 신속하게 응답을 돌려주고 있었음에도 불구하고, Habitat 클라이언트가 측정하는 p99 요청 지연은 수백 밀리초로 치솟는 기현상이 발생했다. 원인을 분석한 결과, Cosmos DB의 응답 패킷이 커널 네트워크 버퍼에 도착했음에도 불구하고, 이를 읽고 역직렬화해야 할 asyncio 코루틴이 이벤트 루프의 스케줄링을 받지 못해 대기열에서 방치되고 있었던 것이다.

Habitat은 단순한 I/O 프록시가 아니었다. 요청을 중계하는 도중에 스키마 라우팅, 페이로드 압축 및 암호화, 데이터 무결성 체크섬 계산, 백엔드 상태 헬스체크, 요청 섀도잉 및 헤징(Hedging) 등 상당한 CPU 집약적 연산을 동시에 처리하고 있었다. 팀은 기존 시스템 메트릭(CPU/메모리 사용률)만으로는 이 문제를 진단할 수 없음을 깨닫고, 이벤트 루프의 스케줄링 지연(Scheduling Delay)을 실시간 메트릭으로 직접 계측하기 시작했다:

  • 백그라운드 하트비트를 통한 스케줄링 지연 계측 — 일정한 주기로 깨어나는 초경량 타이머 코루틴을 심어 두고, 의도된 실행 시각과 실제 이벤트 루프에 의해 실행된 시각의 차이를 나노초 단위로 측정했다.
  • 극단적 스케줄링 지터의 발견 — CPU 사용률이 높은 파드에서는 동시 요청 수가 그리 많지 않은 상황에서도 수백 밀리초, 극단적인 경우 수초에 달하는 스케줄링 지터가 발생하고 있음을 확인했다.
  • 프로세스당 동시성 제한과 수평 확장 — 단일 Python 프로세스가 감당하는 동시 요청 수를 의도적으로 낮게 제한하고, 파드 내 워커 프로세스 수를 늘려 이벤트 루프의 병목을 완화했다.

Statsig 기능 플래그 JSON 파싱과 지터(Jitter) 부재의 충격

실시간 CPU 프로파일링을 수행하던 엔지니어들은 더욱 충격적인 사실을 발견했다. 주기적으로 모든 워커 프로세스의 CPU가 100%로 치솟으며 수백 밀리초 동안 얼어붙는 현상이 정확히 1분 간격으로 관측된 것이다. 범인은 다름 아닌 사내 기능 플래그 시스템인 Statsig의 설정 갱신 로직이었다.

Statsig SDK는 기본적으로 매분마다 최신 룰셋을 폴링하여 메모리에 반영하고 있었다. 그러나 당시 설정 파일에는 Habitat뿐만 아니라 사내 모든 서비스의 방대한 프로덕션 룰셋이 단일 거대 JSON 파일로 뭉쳐져 있었다. 게다가 파드당 최대 8개의 Python 워커 프로세스가 동작하고 있었는데, 모든 프로세스가 지터(무작위 지연 시간) 없이 매 정각 1분마다 동시에 수십 메가바이트의 JSON을 파싱하기 시작한 것이다.

8개 프로세스가 동시에 무거운 JSON 문자열을 파이썬 딕셔너리로 역직렬화하는 순간 호스트의 모든 CPU 코어가 포화되었고, 그 시간 동안 진행 중이던 모든 실시간 트래픽의 asyncio 이벤트 루프가 완벽히 동결되었다. 팀은 이 문제를 해결하기 위해 다음 조치를 취했다:

  • 타깃 설정 파일 분리 — 전체 사내 룰셋 대신 Habitat 서비스에 실제로 필요한 기능 플래그만 선별하여 극도로 슬림화된 설정 파일을 배포했다.
  • 갱신 주기 연장 및 백그라운드 지터 도입 — 폴링 간격을 늘리고, 각 프로세스가 설정을 조회하는 시점에 무작위 지터(Randomized Jitter)를 강제하여 동시 실행을 원천 분산시켰다.
  • I/O 이벤트 루프의 연산 분리 — 거대 페이로드 파싱과 같은 블로킹 연산이 발생할 경우 별도의 프로세스 풀로 위임하거나 즉시 처리하지 않도록 스케줄링 구조를 개선했다.

커넥션 풀링의 맹점 — LIFO가 초래한 준안정 장애(Metastable Failure)

대규모 분산 시스템에서 TCP 커넥션을 맺고 끊는 핸드셰이크 비용은 극도로 비싸다. 따라서 모든 고성능 HTTP/TCP 클라이언트는 연결을 미리 맺어 두고 재사용하는 커넥션 풀(Connection Pool)을 필수적으로 운용한다. 그러나 이 연결 풀링의 사소한 재사용 순서(Reuse Policy) 결정 하나가 전체 시스템을 붕괴 직전의 준안정 장애(Metastable Failure)로 몰아넣을 수 있다는 사실을 경험해 본 엔지니어는 드물다.

Habitat 클라이언트들은 트래픽 폭증 시에도 안정적인 성능을 유지하기 위해 커넥션 풀을 운영했다. 그러나 트래픽을 관측하던 엔지니어들은 기이한 현상에 직면했다. 특정 백엔드 서버 프로세스들에 전체 평균보다 5~10배나 많은 동시 요청이 집중되는 심각한 부하 불균형이 발생한 것이다. 더욱 기괴한 점은, 트래픽 폭증을 유발한 클라이언트를 찾아내어 차단하거나 요청을 줄였음에도 불구하고, 한번 과부하에 빠진 서버들이 스스로 정상 상태로 회복하지 못했다는 것이다. 프로세스를 강제로 재시작하기 전까지는 고통스러운 부하 집중이 영구히 지속되었다.

이것이 바로 대규모 분산 시스템에서 악명 높은 준안정 장애(Metastable Failure) 상태였다. 원인을 추적하던 팀은 커넥션의 최대 유휴 시간(Max Idle Time)을 제한하자 이상 증상이 급격히 완화되는 현상을 발견하고, 마침내 범인이 Python aiohttp의 TCPConnector 기본 동작 방식에 있음을 밝혀냈다.

aiohttp를 비롯한 수많은 현대 통신 라이브러리는 커넥션 풀에서 연결을 꺼낼 때 기본적으로 LIFO(Last-In, First-Out, 후입선출) 방식을 사용한다. LIFO는 일반적인 상황에서 매우 똑똑하고 효율적인 선택이다. 가장 최근에 사용된 따끈따끈한 연결을 우선 재사용함으로써 CPU 캐시 친화도를 높이고, 트래픽이 줄어들면 오랫동안 사용되지 않은 차가운 연결들은 자연스럽게 타임아웃되어 운영체제 소켓 자원을 깔끔하게 반환하기 때문이다.

하지만 대규모 분산 환경에서 LIFO는 치명적인 양의 피드백 루프(Positive Feedback Loop)를 생성했다. 그 파괴적인 메커니즘은 다음과 같았다:

  • 서버의 일시적 지연 발생 — 여러 백엔드 서버 중 특정 서버(Server A)가 일시적인 GC나 디스크 I/O로 인해 응답이 약간 느려진다.
  • 늦은 연결 반환 — 정상적인 서버들은 5ms 만에 연결을 풀에 반환하는 반면, 지연이 발생한 Server A의 연결은 50ms 뒤에 뒤늦게 풀로 반환된다.
  • LIFO의 역습 — 다음 요청을 보내려는 클라이언트의 커넥션 풀은 LIFO 규칙에 따라 「가장 최근에 풀로 들어온」 Server A의 연결을 가장 먼저 꺼내어 새 요청을 할당한다!
  • 과부하 집중과 준안정 고착 — 이미 과부하로 헐떡이는 Server A에 더 많은 요청이 집중되고, 응답은 더욱 느려지며, 연결은 더 늦게 반환되어 다음 요청에 또다시 선택되는 파멸적인 악순환이 완성된다.

Habitat 팀은 aiohttp의 커넥션 풀 재사용 전략을 LIFO에서 FIFO(First-In, First-Out, 선입선출) 방식으로 전면 교체했다. FIFO 방식은 트래픽 스파이크가 지나간 후 유휴 연결을 유지하는 비용이 LIFO보다 약간 더 들 수 있지만, 모든 가용 서버로 연결 재사용 기회를 균등하게 분산시켜 피드백 루프를 완벽하게 끊어냈다. 그 결과 정상 상태에서의 요청 지연 분산 편차가 극적으로 줄어들었으며, 과부하 서버가 스스로 회복할 수 있는 안정성을 확보했다. 현재 Habitat은 서비스 메시 레이어인 Istio와 Envoy의 지능형 로드 밸런싱 풀링을 통해 이러한 문제를 원천적으로 방지하고 있다.

프로세스 증설의 부작용 — Envoy와 HTTP/2를 통한 Thundering Herd 차단

Python의 asyncio 스케줄링 지연을 해소하기 위해 엔지니어들이 선택할 수 있는 가장 손쉬운 방법은 호스트당 워커 프로세스 수를 대폭 늘리는 것이다. 실제로 Habitat 팀은 파드당 프로세스를 공격적으로 늘려 CPU 활용도를 높였다. 그러나 분산 시스템의 세계에서 공짜 점심은 없다. 한쪽의 병목을 풀자마자 그 여파는 하위 시스템으로 고스란히 전이되었다.

프로세스 수가 급증하자, 하위 스토리지와 내부 서비스들을 향해 수만 개의 TCP 연결이 일제히 쏟아지는 연결 폭증(Thundering Herd) 문제가 폭발했다. 일상적인 소프트웨어 롤링 배포를 진행할 때조차 수많은 프로세스가 동시에 기존 연결을 해제하고 새 연결을 맺는 과정에서 막대한 CPU 오버헤드가 발생했다. 심지어 사내 네트워크의 NAT 게이트웨이 커넥션 추적 테이블(Conntrack Table)이 포화되어 전체 클러스터 네트워크가 마비될 위험까지 초래되었다.

이 문제를 근본적으로 해결하기 위해 팀은 서비스 프록시인 Envoy를 도입하고, 프로토콜 계층을 기존 HTTP/1.1에서 HTTP/2 다중화(Multiplexing)로 전환했다. 개별 Python 프로세스가 하위 시스템과 직접 TCP 연결을 맺는 대신, 로컬 Envoy 사이드카 프록시가 연결 풀을 중앙 집중식으로 대리 관리하도록 만든 것이다.

[ Connection Architecture Comparison ]

1. Independent Connection Pools (Python Processes without Proxy):
   Pod-1 [Proc 1] ----(3 conns)----> [Downstream Service]
   Pod-1 [Proc 2] ----(3 conns)----> [Downstream Service]
   ...
   Pod-6 [Proc 8] ----(3 conns)----> [Downstream Service]
   => Result: 18~144 open TCP connections, high idle waste, connection storms!

2. Centralized Envoy Proxy with HTTP/2 Multiplexing:
   Pod [Proc 1..8] --(local IPC/h2)--> [Envoy Proxy]
                                            |
                                 (1 TCP Connection, 6+ Streams)
                                            v
                                   [Downstream Service]
   => Result: Single long-lived TCP connection, zero idle storms, shared rate-limiting!

이 아키텍처 전환의 효과는 가히 극적이었다. 동일하게 동시 요청 6개를 처리하는 시나리오를 비교해 보면 그 차이가 명확히 드러난다:

  • 독립 커넥션 풀 (초기 Python 모델) — 6개의 파드가 각각 최대 3개의 연결을 맺을 경우 총 18개의 TCP 연결이 열리며, 요청이 끝난 후에도 12개의 연결이 유휴(Idle) 상태로 남아 하위 시스템 자원을 낭비한다.
  • Envoy 공유 HTTP/1.1 풀 — 파드 내 로컬 Envoy가 커넥션을 단일 풀로 통합 관리함으로써 정확히 필요한 6개의 TCP 연결만으로 동시 요청을 완벽히 소화한다.
  • Envoy HTTP/2 다중화 풀 (최종 아키텍처) — 단 하나의 지속적인 TCP 연결 위에 6개의 독립적인 양방향 스트림(Streams)을 다중화하여 전송함으로써, 하위 시스템과의 물리적 TCP 연결 수를 1개로 압축한다.
  • 중앙 집중식 서킷 브레이커 및 레이트 리밋 — 개별 프로세스에 파편화되어 있던 제한 정책을 Envoy 레이어에서 전역적으로 조율함으로써 인프라 전반의 회복 탄력성을 비약적으로 높였다.

아래 표는 커넥션 관리 아키텍처의 진화 단계별 자원 소비와 하위 시스템 충격도를 비교한 것이다.

구성 방식 파드당 설정 동시 요청 6개 처리 시 연결 수 유휴(Idle) 연결 상태 하위 시스템 부하 영향
개별 Python 프로세스 독립 풀 프로세스별 최대 3개 HTTP/1 연결 18개 연결 유지 12개 유휴 연결 상시 낭비 배포 시 Thundering Herd 및 NAT 포화 유발
Envoy 공유 HTTP/1 풀 파드 단위 중앙 연결 풀 6개 연결 유지 유휴 연결 최소화 서버 간 부하 분산 개선, 연결 수 66% 절감
Envoy 기반 HTTP/2 다중화 단일 다중화 TCP 파이프라인 단 1개 연결 (6개 스트림) 유휴 연결 0개 핸드셰이크 비용 제로화, 네트워크 소켓 부하 극소화

단순함이 비용을 통제한다 — SQL을 버리고 제약된 NoSQL API를 택한 설계

인프라의 규모가 초당 수천만 건으로 팽창할 때, 소프트웨어 아키텍처에서 가장 위험한 요소는 "무엇이든 할 수 있는 유연함"이다. 초기 OpenAI의 온라인 데이터 대부분은 널리 검증된 오픈소스 관계형 데이터베이스인 PostgreSQL에 저장되어 있었다.

초기에는 뛰어난 엔지니어들이 모든 쿼리와 스키마 변경 PR을 수동으로 검토하며 적절한 복합 인덱스가 설정되어 있는지 확인할 수 있었다. 그러나 서비스가 폭발적으로 성장하고 수백 명의 제품 엔지니어들이 수십 개의 마이크로서비스를 쏟아내기 시작하자, 이러한 수동 거버넌스는 완전히 붕괴되었다. 제품 기능 하나를 위해 무심코 추가된 비싼 JOIN 쿼리나 조건 없는 테이블 풀스캔 하나가 마스터 DB의 CPU를 100%로 잠식하며 전체 서비스를 셧다운시키는 대형 장애가 빈번하게 반복되었다.

SQL은 표현력이 너무나 풍부하여 개발자가 몇 줄의 텍스트만으로 실행 비용이 천문학적인 쿼리를 손쉽게 작성할 수 있다는 치명적인 비용 불균형(Cost Asymmetry)을 내포한다. 이 문제를 근본적으로 뿌리 뽑기 위해 Habitat 팀은 대담한 결정을 내렸다. 관계형 SQL 인터페이스를 완전히 버리고, 의도적으로 제약된 단순한 NoSQL API만을 제공하기로 선언한 것이다.

TAO 모델에서 영감받은 객체와 간선(Edge) 그래프 파티셔닝

Habitat의 데이터 모델은 Meta(구 Facebook)가 소셜 그래프를 초고속으로 처리하기 위해 고안한 분산 데이터 스토어인 TAO(The Associations and Objects) 아키텍처에서 직접적인 영감을 받았다. Habitat은 임의의 다차원 테이블 조인 대신, 클라이언트가 명시적으로 정의하는 객체(Objects)와 간선(Edges) 중심의 NoSQL API만을 노출한다:

  • 제약된 데이터 조작 모델 — 클라이언트는 객체와 간선 타입을 정의하지만 스키마 내부의 복잡한 계층 관계는 데이터베이스에 위임하지 않는다. 지원하는 쿼리는 특정 객체의 키 조회 및 직접 연결된 단일 홉 간선 조회로 엄격히 제한된다.
  • 파티션 지역성과 그래프 탐색의 의도적 배제 — 각 객체와 그 객체에서 뻗어나가는 직접 간선들은 물리적으로 동일한 스토리지 파티션에 함께 배치된다. 그러나 그 간선이 가리키는 원격 대상 객체까지 같은 파티션에 두도록 조정하지는 않는다.
  • 클라이언트로의 연산 비용 전가 — 여러 홉(Multi-hop)을 건너뛰는 그래프 탐색은 40여 개 글로벌 리전에 분산된 서로 다른 Azure Cosmos DB 계정을 오가야 하므로 매우 비효율적이다. Habitat은 이러한 연산을 서버 내부에서 숨겨서 처리해 주지 않으며, 제품 팀이 직접 클라이언트 측에서 비즈니스 로직으로 풀어내도록 강제한다.

이러한 의도적인 제약 덕분에 Habitat에서 실행되는 모든 단일 요청은 실행 시간과 자원 소모량이 완벽히 예측 가능한 상수 시간(O(1))에 수렴하게 되었다. 어떤 제품 팀도 시스템 전체를 위협할 수 있는 비싼 쿼리를 실수로 실행할 수 없게 된 것이다.

Rockset CDC를 활용한 복잡 분석 쿼리의 철저한 격리

그렇다면 제품 운영에 필수적인 복잡한 분석이나 검색, 어드민 대시보드 쿼리는 어떻게 해결했을까? Habitat 팀은 온라인 트랜잭션 처리(OLTP)와 오프라인 분석 처리(OLAP)를 동일한 데이터 저장소에서 처리하려는 시도 자체를 단호히 거부했다.

복잡한 쿼리가 반드시 필요한 팀을 위해, Habitat은 분산 실시간 검색 엔진인 Rockset 기반의 보조 뷰(Secondary View)를 완전히 분리된 계층으로 제공했다. 변경 데이터 캡처(CDC, Change Data Capture) 파이프라인을 구축하여 온라인 스토리지의 모든 데이터 변경 사항을 거의 실시간으로 격리된 Rockset 인스턴스에 복제했다:

  • 물리적 워크로드의 완전 격리 — 아무리 무겁고 비효율적인 분석 쿼리가 Rockset에서 실행되더라도, 10억 명의 사용자가 사용하는 온라인 Cosmos DB에는 단 1%의 부하도 전달되지 않는다.
  • 인스턴스 비용의 책임 귀속 — 복잡한 분석 조회가 필요한 각 제품 팀은 자신들의 Rockset 인스턴스 용량 산정과 비용을 직접 책임져야 하므로, 무분별한 낭비를 스스로 억제하게 된다.
  • 단순성의 승리 — 온라인 핵심 스토리지는 극도로 단순하고 빠른 읽기/쓰기만을 수행하여 높은 가용성을 사수하고, 복잡한 비즈니스 요구는 격리된 보조 엔진이 흡수하는 완벽한 이원화 체계를 구축했다.

국내 대규모 트래픽 및 AI 도입 팀을 위한 실전 시사점

OpenAI의 Habitat 확장 사례는 실리콘밸리의 거대 기업뿐만 아니라, 대규모 트래픽을 다루는 국내 포털·커머스·게임 개발사와 AI 에이전트 도입을 고민하는 기술 스타트업에게도 매우 강력하고 실질적인 엔지니어링 교훈을 제공한다.

첫째, AI 코딩 에이전트를 활용한 인프라 현대화가 현실의 영역에 진입했다는 점이다. 지금까지 많은 기술 조직은 레거시 시스템의 비효율을 뻔히 알면서도 "전면 재작성은 실패한다"는 오랜 격언에 묶여 마이그레이션을 포기해 왔다. 그러나 단 2명의 엔지니어가 Codex와 GPT-5.5의 도움을 받아 초당 수천만 건의 시스템을 Rust로 단 몇 달 만에 재작성하고 6배의 CPU 효율을 거둔 실증 사례는, 소프트웨어 엔지니어링의 생산성 방정식이 완전히 재정의되었음을 보여준다. 도메인 지식과 시스템 아키텍처를 쥔 소수의 핵심 엔지니어가 최신 AI 모델을 지휘할 때 발휘되는 레버리지는 상상을 초월한다.

둘째, Python 비동기(asyncio) 기반 마이크로서비스를 운영할 때 꼬리 지연을 맹신해서는 안 된다는 교훈이다. 국내 많은 백엔드 팀이 빠른 개발 속도를 위해 FastAPI나 aiohttp를 프로덕션에 적극 도입하고 있다. 하지만 asyncio는 CPU 연산이 끼어드는 순간 이벤트 루프 스케줄링 지연이 발생해 p99 지연이 기하급수적으로 악화된다. 백그라운드 작업에 지터를 필히 부여하고, I/O 스레드와 CPU 바운드 작업을 엄격히 분리하며, 커넥션 풀링에서 LIFO가 유발하는 준안정 장애 피드백 루프를 반드시 점검해야 한다.

셋째, "적게 하는 시스템이 가장 튼튼하다(Why Habitat does less)"는 아키텍처 철학이다. 시스템의 규모가 커질수록 풍부한 기능보다 중요한 것은 예측 가능성이다. 쿼리 유연성을 의도적으로 제약하고, 온라인 스토리지와 분석 스토리지를 철저히 분리하며, 복잡한 연산의 비용을 호출자에게 투명하게 전가하는 설계야말로 초당 7,000만 건의 트래픽 앞에서도 흔들리지 않는 인프라를 지탱하는 진정한 버팀목이다.

  • AI 페어 프로그래밍의 실무 적용 — AI 코딩 에이전트를 단순 스니펫 생성이 아닌, 대규모 언어 변환 및 회귀 테스트 자동화 파이프라인의 핵심 파트너로 활용하라.
  • 커넥션 풀링 재사용 규칙의 재검토 — 통신 라이브러리의 기본 설정(LIFO 등)이 부하 편중을 야기하고 있지 않은지 시스템 메트릭을 통해 검증하라.
  • 이벤트 루프 스케줄링 지연 모니터링 — CPU/메모리 사용률뿐 아니라 비동기 런타임의 이벤트 루프 대기 시간을 독립적인 관측성 지표로 확보하라.
  • API 제약을 통한 데이터베이스 보호 — 온라인 처리 경로에서는 화려한 SQL 조인을 과감히 포기하고, 예측 가능한 최소 단위의 연산만을 허용하라.

확인하지 못한 것

  • Rust 재작성에 투입된 구체적인 프롬프트 엔지니어링 기법 — 원문은 Codex와 GPT-5.5를 사용해 2명의 엔지니어가 재작성을 완료했다고 명시했으나, 구체적으로 어떤 프롬프트 템플릿과 자율 워크플로 툴링을 적용했는지는 상세히 공개되지 않았다.
  • Azure Cosmos DB의 세부 파티셔닝 키 구성 — Habitat의 데이터 모델이 TAO 기반 객체-간선 구조임은 확인되었으나, Cosmos DB 내부의 물리적 파티션 키와 논리적 샤드 매핑 공식은 본문에 서술되지 않았다.
  • Python 레거시 완전 폐기 후의 최종 비용 절감 총액 — 현재 95%의 트래픽을 처리하며 달성한 6배 CPU 및 15배 메모리 효율 향상 수치는 확인되었으나, 클라우드 인프라 청구 비용의 절대 절감 금액은 원문에 언급이 없다.
  • Rockset CDC 파이프라인의 구체적 지연 시간(Lag) — 온라인 Cosmos DB에서 Rockset으로 복제되는 변경 데이터의 평균 동기화 지연 수치는 기술 보고서에 명시되지 않았다.
  • Envoy 프록시의 구체적 CPU 오버헤드 비율 — HTTP/1에서 HTTP/2 다중화로 전환하여 TCP 연결 수를 획기적으로 줄였으나, 사이드카 Envoy 프록시 자체가 소비하는 리소스 지표는 별도로 제시되지 않았다.
  • 후속 2편 블로그의 구체적 발행 일정 — 멀티테넌트 신뢰성, 계층별 읽기 성능, Azure Cosmos DB 스토리지 계층 최적화를 다룰 후속 편이 예고되었으나 정확한 공개 날짜는 밝히지 않았다.
