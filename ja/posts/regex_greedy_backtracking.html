正規表現が終わらない - 貪欲マッチとバックトラック爆発

一文字増えるたびに時間が倍になる構造を実測し、四つの方法で断ち切る

2026-09-01 開発・インフラ

正規表現が間違った結果を返せばすぐに気づく。テストが赤くなり、ログに切り損ねた値が残る。厄介なのは正規表現が答えを返さない場合だ。例外もなくエラーメッセージも出ない。ただその行でプロセスが立ち止まっている。CPU は一コアを100パーセントで掴んだままで、スタックトレースを取ると String.prototype.match のどこかを指している。

この状況で最も多い誤解は、入力が大きいのだろうというものだ。以下で測る例の入力は31バイトで、それを処理するのに7.8秒かかった。原因はデータの大きさではなくパターンの形にある。この記事はその形が何なのか、なぜ指数的に膨らむのか、どう断ち切るのかを、すべて実際に時間を測って確かめる。

この記事の数値は、下の「測定環境」に書いた一台の機械で実際に実行して得た値だ。CPU・ランタイムのバージョン・他プロセスの負荷によって絶対値はいくらでも変わる。見るべきはミリ秒の桁ではなく、入力が少し増えたとき時間がどの比率で増えるかだ。その比率だけは機械が違っても同じ形で出る。

バックトラックという構造

大半のプログラミング言語が使う正規表現エンジンはバックトラック方式だ。動きは名前のとおりで、パターンを左から読みながら文字列に合わせていき、どこかで詰まると直近に選択肢があった地点まで戻って別の選択をしてみる。迷路で分かれ道ごとに印を残し、行き止まりに当たったら最後の印まで戻るのと同じだ。

この方式が遅くなりうるのに広く使われ続けている理由がある。戻れることによってはじめて表現できる機能があるからだ。

  • 後方参照 — (\w+)\s+\1 のように「前で捕まえたものと同じもの」を要求する文法。前のグループが何を捕まえたかを覚えて試し直せなければ成り立たない
  • 先読み・後読み — (?=...) や (?<=...) といった位置の検査。一点で別のパターンを試しに合わせてから元の位置に戻る必要がある
  • 貪欲な量指定子の戻し — .* がいったん最後まで食べ、後ろが合わなければ一文字ずつ吐き戻す動作そのものが戻りだ
  • 選択肢の優先順位 — (a|ab) で左を先に試し、失敗したら右へ行くという規則も戻りの上に乗っている

これらの機能は形式言語理論でいう正規言語の範囲を超える。だから状態機械を一度なぞるだけでは処理できず、探索が必要になる。探索には最悪の場合がある。そしてその最悪は、たいてい思っているよりずっと近くにある。

破滅を再現する - 一文字で倍

教科書的な例は ^(a+)+$ だ。ここに a を n 個並べ、最後に b を付けた文字列を入れる。b は決してマッチしないので、エンジンは可能な分岐をすべて試したあとでなければ失敗を宣言できない。測ったコードはこうだ。

const CAP_MS = 4000;   // 一回が4秒を超えたら中断

for (let n = 10; n <= 34; n++) {
  const s = 'a'.repeat(n) + 'b';
  const re = new RegExp('^(a+)+$');
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  console.log(n, ms.toFixed(3));
  if (ms > CAP_MS) break;
}

比率の列がすべて2の近くに集まっている。これが指数増加の指紋だ。一文字が時間を倍にするということは、十文字で千倍になるということだ。この表をそのまま延ばせば40文字で数時間、50文字で数か月の単位になる。だから「止まった」と感じる。実際に止まったのではなく、終わる時点が人間の時間感覚の外に出ただけだ。

注目すべきは区間が非常に狭いことだ。20文字までは6ミリ秒で、どんなテストも通ってしまう。25文字で0.1秒、29文字で2秒、31文字で7.8秒。開発中に使う短いサンプルでは決して引っかからず、運用で少し長い値が入った瞬間に一気に越える。

なぜ爆発するのか - 分け方の数

病の名前は曖昧さだ。(a+)+ では内側の a+ が a を一個以上食べ、外側の + がそれを一回以上繰り返す。すると aaaa という四文字をこのパターンに合わせる方法は一つではない。4、3+1、1+3、2+2、2+1+1、1+2+1、1+1+2、1+1+1+1 の八通りだ。一般に n 文字をこう刻む方法は2n-1 通りある。

マッチが成功すればエンジンは最初に見つけた方法で止まる。ところが後ろに b があって $ が失敗すると、エンジンは「別の分け方なら通ったかもしれない」と判断してすべて試す。分け方が 2n-1 通りなら試行もその数だけになる。同じ文字列を複数の方法で分けられること、そしてその結果がすべて失敗すること。この二つが重なる場所が爆発点だ。

この診断が正しいかを確かめる方法は、同じ病を持つ別の形を測ってみることだ。見かけはまるで違うが、「分け方が複数ある」という性質は同じである。

パターンn=20n=24n=28n=29
^(a+)+$6.480 ms109.264 ms2233.649 ms3995.791 ms
^(a|a)*$13.354 ms191.011 ms3368.902 ms6640.935 ms
^(a*)*$12.359 ms242.906 ms3675.270 ms7156.893 ms

三つとも同じ曲線を描く。(a|a)* は二つの分岐がまったく同じものを噛む。どちらを選んでも結果が同じなので、n 回繰り返せば 2n 通りの経路ができ、そのすべてが同じように失敗する。(a*)* は内側が空文字列まで食べられるので分割の通り数がさらに増える。文法は違うが病は一つだ。

  • 量指定子の中に量指定子があり、内側が可変長である — (a+)+、(\w+\s?)*、([a-z]*)+
  • 選択の分岐が同じ文字を噛みうる — (a|a)*、(\d|\w)*、(x|xy)*
  • 繰り返しの中に空文字列にマッチしうる要素がある — (a*)*、(\s?)*
  • 三つとも条件は一つに要約できる。同じ入力をパターンに対応させる方法が二通り以上あれば、失敗したときその全部を確認する

失敗するときにだけ弾ける

この性質は診断の決め手になる。同じパターン、同じ大きさの入力でもマッチが成功すれば何も起きない。エンジンは最初の成功で即座に止まるからだ。同じ n=26 で三つの場合を並べて測った。

入力 "a"×26 + "b"   パターン ^(a+)+$    447.897 ms   （失敗）
入力 "a"×26 + "b"   パターン ^(a+)+     0.0005 ms    （即座に成功）
入力 "a"×26        パターン ^(a+)+$    0.0002 ms    （即座に成功）

三行目が特に重要だ。パターンは問題のそれそのままなのに、b が一つないだけで0.0002ミリ秒である。百万倍を超える差が入力の最後の一文字から出ている。二行目は $ を外したものだ。最後まで合う必要がなくなると前のほうですぐ成功して終わる。

ここから実務的な結論が一つ出る。有効な値だけを入れてみるテストではこの欠陥は絶対に捕まらない。正規表現のテストを書くとき成功ケースだけを埋める習慣はありふれているが、この種の欠陥はまさにその死角に隠れる。そして運用で入ってくる値は、たいてい無効な側のほうがはるかに多様だ。

同じ理由でアンカーの有無も時間を変える。先頭アンカー ^ がないと、エンジンは一文字目で失敗したあと二文字目から改めて、三文字目から改めて試す。n=24 で ^(a+)+$ が116.532ミリ秒のとき (a+)+$ は295.768ミリ秒で2.5倍だった。アンカーを付けても指数は消えないが、前に付く係数は消える。

貪欲と怠惰と絶対最大

量指定子には三つの性格がある。三者の違いは「どれだけ食べるか」ではなく「食べたものを返すかどうか」だ。

表記名前動作JS（V8）Python 3.13Perl 5.38
* +貪欲最大限食べ、後ろが詰まれば一文字ずつ返す対応対応対応
*? +?怠惰最小限食べ、後ろが詰まれば一文字ずつ足す対応対応対応
*+ ++絶対最大最大限食べ、決して返さない非対応対応対応
(?>...)アトミックグループグループを抜けたら中の選択は二度と見ない非対応対応対応

まず多い誤解から片づける。怠惰な量指定子に変えれば速くなるという話は半分しか正しくない。怠惰は戻る性質を捨てたのではなく、戻る向きを裏返したものだ。20万文字の文字列では、目標がどこにあるかで結果が完全に分かれる。

パターン目標が文字列の前方目標が文字列の後方
<h2>(.*)</h2>0.2658 ms0.0350 ms
<h2>(.*?)</h2>0.0003 ms0.0357 ms
<h2>([^<]*)</h2>0.0003 ms0.0356 ms

目標が前にあるとき怠惰は900倍近く速い。貪欲はいったん20万文字を最後まで食べ、そこから戻ってくるからだ。ところが目標が後ろにあると三つのパターンは事実上同じになる。怠惰は今度は前から一文字ずつ伸ばしながら20万回試すからだ。怠惰は性能対策ではなく意味の選択である。最短マッチが欲しいときに使うもので、速度はデータの形についてくる。

本当の対策は絶対最大量指定子とアトミックグループだ。この二つはエンジンに「ここで戻ることを諦めろ」と明示的に指示する。a++ は a を最大限食べ、後ろが失敗しても吐き戻さない。吐き戻す選択肢がなければ分岐は生まれず、分岐がなければ指数もない。Python 3.13.3 と Perl 5.38.2 で確かめた値だ。

Python 3.13.3
  ^(a+)+$    n=26        3323.962 ms
  ^(a++)+$   n=100000    0.0398 ms
  ^(?>a+)+$  n=100000    0.0395 ms

Perl 5.38.2
  ^(a++)+$   n=100000    0.0091 ms
  ^(?>a+)+$  n=100000    0.0091 ms

入力が3800倍ほど大きくなったのに時間は0.04ミリ秒だ。ただし注意がある。絶対最大量指定子は意味を変える。"[^"]*+" のように戻る必要のない場所に使えば安全だが、後ろで戻しが必要なパターンにそのまま付けると合っていたものが合わなくなる。性能オプションではなく意味の宣言として扱うべきだ。

JavaScript で戻りを断つ方法

JavaScript にはこの道具がない。Node.js v22.16.0（V8 12.4.254.21-node.26）で三つともコンパイル段階で拒否される。

> new RegExp('^(?>a+)+$')
SyntaxError: Invalid regular expression: /^(?>a+)+$/: Invalid group

> new RegExp('^a*+$')
SyntaxError: Invalid regular expression: /^a*+$/: Nothing to repeat

> new RegExp('^a++$')
SyntaxError: Invalid regular expression: /^a++$/: Nothing to repeat

Nothing to repeat というメッセージが状況をそのまま表している。V8 は a++ を「絶対最大量指定子」とは読まず、「+ を + でもう一度繰り返せ」という文法エラーとして読む。絶対最大という概念自体がないのだ。

代わりに同じ効果を出す慣用句がある。先読みの中にグループを入れ、そのグループを後方参照するやり方だ。(?>X) を (?=(X))\1 に書き換える。先読みは内側で一度確定すると外から返さないので、後方参照でその結果をそのまま消費すればアトミックグループと同じになる。

// ^(a+)+$ をアトミック化
const naive  = /^(a+)+$/;
const atomic = /^(?=(a+))\1+$/;

// "a"×26 + "b"
naive.test(s)    →  528.117 ms
atomic.test(s)   →  0.0005 ms

// 同じ atomic パターンをはるかに大きな入力に
n=1000     0.0009 ms
n=10000    0.0077 ms
n=100000   0.0771 ms

入力が100倍ずつ大きくなるとき時間もおよそ10倍ずつになる。線形に近いということだ。この慣用句は読みにくいという欠点がはっきりしているので、使うならなぜこう書いたのかコメントを必ず残す。あとで誰かが「不要な先読み」と判断して整理すれば、欠陥がそのまま戻ってくる。

指数でなくても遅い

指数爆発は劇的だが多くはない。実務ではるかによく出会うのは多項式的バックトラックだ。.* を何度も使い、その間を区切り文字で分けるパターンが典型である。ログ解析と CSV 処理でほぼ毎回出てくる。

^"(.*)" "(.*)" "(.*)"$ のようなパターンに引用符で囲んだフィールドが複数ある行を入れ、末尾に一文字足してマッチを失敗させた。三つの .* が区切り位置を選ぶ組合せの数だけ働く。

フィールド数行の長さ"(.*)""([^"]*)"
1050 文字0.003 ms0.0001 ms
20110 文字0.024 ms0.0001 ms
40230 文字0.208 ms0.0001 ms
80470 文字1.774 ms0.0001 ms
1601010 文字15.522 ms0.0001 ms

長さが20倍になったとき時間は5000倍になった。倍ごとに8倍前後なのでおよそ三乗だ。指数のように即死させはしないが、ログの一行が長くなったときにパーサ全体が遅くなる原因としてはこちらのほうがはるかに多い。そして右の列に答えが出ている。.* を [^"]* に変えるだけですべての大きさで平らになる。

理由は単純だ。[^"]* は引用符に当たれば必ず止まる。止まる場所が一つに決まるので組合せが生じない。.* は引用符も食べられるので、どこで止まるかをエンジンが試さなければならない。区切り文字を文字クラスから外すことが、この種で最も安上がりな修正だ。

実務でよく出てくる形

危険なパターンはたいてい「危険そうに」見えない。(a+)+ と書く人はいないし、実際に入っている形は下のほうだ。

形実際に見える姿隠れているもの
入れ子の量指定子^(\w+\s?)*$ — 単語が空白でつながった行かの検査\s? が任意なので \w+ 同士が接することができ、分割が複数通りになる
重なる分岐(\d|\w)+ — 数字か文字の繰り返し\d が \w に含まれ、すべての数字が二つの経路を作る
ドットスターの連鎖^(.*) (.*) \[(.*)\] "(.*)"$ — アクセスログ一行区切り位置の組合せ。フィールドが長くなるほど多項式的に増える
緩いメール検証^([\w.-]+)+@([\w-]+\.)+[a-z]{2,}$前半が (X+)+ と同じ形。ドメイン側も繰り返しの中の繰り返しだ
空白の整理^(\s*)+$ または (\s|\t)*$空文字列を食べうる要素の繰り返し。タブと空白が混ざると分かれる

一行目を実際に測ってみた。^(\w+\s?)*$ に文字を n 個並べ、末尾に ! を付けた。空白のない文字列でも \s? が空を食べられるので分割が分かれる。

n=20    8.445 ms
n=24    227.832 ms
n=26    697.181 ms
n=28    2268.459 ms
n=29    4564.045 ms   ← ここで中断

このパターンは「利用者名が単語と空白だけでできているか」を検査する入力検証によく入る。そしてそういう検証は定義上、利用者入力を直接受ける場所にある。

ReDoS - 停止性が可用性の問題になる場所

ここまでは性能の話だった。利用者入力がこうしたパターンに届いた瞬間、性格が変わる。正規表現サービス拒否（ReDoS）は、短い入力ひとつが処理スレッドを長く占有してサービス全体を止める状況を指す。特別な権限も大量のトラフィックも要らないという点がこの問題の性格だ。

単一スレッドのイベントループで動くランタイムでは波及が特に大きい。一つの要求がマッチに7秒を使えばその7秒のあいだ同じプロセスの他のすべての要求が待つ。ヘルスチェックが応答せずインスタンスが入れ替えられ、入れ替わった側に同じ要求が入ればそのまま繰り返す。

この記事は危険な入力の作り方を扱わない。必要なのはどこにどんな形があるかを自分で見つけて塞ぐ側だ。

  • 先に入力長を切る。正規表現に届く前に if (s.length > 200) return false; を置くだけで最悪が定数に縛られる。指数曲線では上限の数文字の差が大きい
  • パターンから形をなくす。これが根本的な修正だ。入れ子の量指定子をほどき、分岐が重ならないようにし、文字クラスから区切り文字を外す
  • 境界に時間上限を置く。利用者入力を処理するマッチを別のワーカーや期限のある経路に移す。JS 標準の正規表現自体にはタイムアウトがない
  • パターンをデータとして受け取らない。利用者が入れた文字列で new RegExp() を作る場所はパターン自体が制御の外に出る。この場合は上のどの検討も役に立たない
  • 依存関係に入っているパターンも対象だ。自分のコードになくても、パーサや検証ライブラリの中にあれば結果は同じになる

一つ目の項目の効果を実際に測った。同じ脆弱なパターンに上限だけ変えて掛けたときの最悪値だ。

maxLength=16   最悪 0.195 ms
maxLength=20   最悪 3.131 ms
maxLength=24   最悪 51.605 ms
maxLength=28   最悪 849.141 ms

上限を28から16に下げるだけで4000倍減る。ただしこれは緩和であって修正ではない。長さの上限はあとで要件が変われば静かに上がり、そのとき欠陥が生き返る。パターン自体を直すほうが常に先だ。

エンジンごとに違う

ここで予想外の結果が一つ出た。同じ ^(a+)+$ を Perl 5.38.2 で回したところ爆発しなかった。n=20 で0.017ミリ秒、n=34 で0.018ミリ秒と平らだった。^(a*)*$ と ^(\w+\s?)*$ も同様だった。Perl のエンジンが失敗した（位置、パターン地点）の組合せを覚えて同じ仕事を繰り返さない最適化を持っているように見える。

だからといって Perl が安全という意味ではない。同じ Perl で前節の多項式パターン ^"(.*)" "(.*)" "(.*)"$ はそのまま遅くなった。フィールド10個で0.011ミリ秒、80個で6.199ミリ秒、320個で323.276ミリ秒だった。最適化が拾ってくれる形とそうでない形があるということだ。

反対側にはオートマトンに基づくエンジンがある。戻る代わりに可能な状態を同時に持って入力を一度だけなぞる。GNU grep 3.0 で同じパターンを測ってみた。

grep プロセスの起動のみ（1バイトのファイル）   0.046 ～ 0.052 s

grep -E '^(a+)+$'
  n=20         0.049 s
  n=100        0.053 s
  n=10000      0.050 s
  n=100000     0.059 s
  n=1000000    0.058 s
  n=5000000    0.104 s

起動時間が0.05秒なのでその下は測れない。意味のある値は最後の行だ。500万文字を実際のマッチ作業およそ0.05秒で終えた。Node が31文字に7.8秒を使ったそのパターンである。曲線そのものが違う。

引き換えるものがある。Go の regexp パッケージの文書は「このパッケージが提供する実装は入力の大きさに対して線形の時間で動くことが保証される（これはほとんどのオープンソース正規表現実装が保証しない性質である）」と明記している。その代償として RE2 の文法文書は、後方参照 \1 と先読み・後読み (?=re)・(?!re)・(?<=re)・(?<!re) をすべて非対応と表示している。

エンジン・バージョン方式^(a+)+$ 観測絶対最大・アトミック備考

ここに微妙な対称がある。前節で JavaScript の爆発を止めた慣用句 (?=(a+))\1 は先読みと後方参照を両方使う。つまりバックトラックエンジンを救うその道具が、そもそも爆発しないオートマトンエンジンには存在しえない道具なのだ。線形時間の保証と表現力は同じ軸の両端にある。

直し方 - 前後を並べて測る

直す方法は四つあり、上で一つずつ出てきた。ここでは前後を同じ表に置く。順序は上のほうがより根本的だ。

入れ子の量指定子をほどく

最も確実な修正だ。(\w+\s?)* のように「繰り返しの中に任意の要素」があるなら、その任意の要素を繰り返しの外に出して分割を一つに確定させる。^\w+(\s\w+)*$ に変えれば空白が必ずないと次の繰り返しが始まらないので、分け方は一通りしかない。

文字クラスを狭める

区切りに使う文字をクラスから外す。"(.*)" → "([^"]*)"、(.*) → (\S+) 。止まる場所が一つに決まれば組合せが消える。意味もたいていより正確になる。

戻りを諦めさせる

Python・Perl・PCRE 系なら絶対最大量指定子かアトミックグループを使う。JavaScript なら先読みの慣用句を使う。これは形をそのままにして症状だけ止める側なので、上の二つが使えないときの選択肢だ。

正規表現を使わない

区切りで切る仕事なら文字列関数のほうが速く、読みやすい。602文字の三フィールドの行を20万回分解した結果である。

同じ条件で String.split(',') は56.1ミリ秒だった。ただしこの差は20万回回さないと見えない大きさだ。一回の呼び出しあたり0.4マイクロ秒と0.03マイクロ秒の差のために読みにくいコードを書く理由はない。指数・多項式の問題とこの問題は扱う桁が違う。

自分のパターンを測る最小スクリプト

パターンを目で見て判定するのは思ったより難しい。代わりに入力長を伸ばしながら時間を測れば目で判定する必要がなくなる。線形なら比率が1の近くに留まり、指数なら比率がずっと2の近くにある。

// redos-probe.js
// 使い方: node redos-probe.js "<パターン>" [繰り返し単位] [末尾]
const [, , src, unit = 'a', tail = 'b'] = process.argv;
const BUDGET_MS = 2000;
const re = new RegExp(src);
let prev = 0;

console.log('n\tms\t直前比');
for (let n = 2; n <= 200000; n = n < 40 ? n + 2 : Math.ceil(n * 1.6)) {
  const s = unit.repeat(n) + tail;
  const t0 = process.hrtime.bigint();
  re.test(s);
  const ms = Number(process.hrtime.bigint() - t0) / 1e6;
  const ratio = prev > 0.05 ? (ms / prev).toFixed(2) : '-';
  console.log(n + '\t' + ms.toFixed(3) + '\t' + ratio);
  if (ms > BUDGET_MS) {
    console.log('\n判定: 超線形。n=' + n + ' で ' + ms.toFixed(0) + ' ms');
    process.exit(2);
  }
  prev = ms;
}
console.log('\n判定: n=200000 まで ' + BUDGET_MS + ' ms を超えなかった');

肝は BUDGET_MS だ。一回がこの値を超えたら即座に中断する。指数曲線では次の段階が倍なので、上限なしで回せば自分で自分の機械を止めることになる。tail の値はマッチを失敗させる文字でなければならない。成功する入力からは何も現れないというのが先ほど見た結果だ。

二つの出力の違いがそのまま診断だ。上は n が2ずつ増えるとき時間が4倍になる。下は n が1.6倍になるとき時間も1.6倍になる。二列目ではなく三列目を見る。絶対時間は機械ごとに違うが、比率はパターンの性質だ。

正規表現を使うべきでないとき

ここまでが直す話で、最後はそもそも使わない場所だ。正規表現が表現できるのは入れ子の深さが決まっていない構造を除いた残りである。この境界を越えるとパターンが長くなり、長くなったパターンには上で見た形がついてくる。

  • HTML・XML — タグが互いを包めるので深さに制限がない。正規表現で開きタグと閉じタグを対にできない。パーサを使う
  • JSON・YAML — 同じ理由。オブジェクトの中のオブジェクトは再帰構造であり、標準ライブラリにパーサがすでにある
  • 括弧の対応 — 正規言語の範囲外だと形式的に証明されている代表例だ。数えながらなぞるコードが正解になる
  • メールアドレスの検証 — 規格に正確に従う正規表現は長く、たいてい危険な形を含む。@ が一つあって前後が空でないか程度の形だけを見て、本当の検証は確認メールで行う
  • URL の解析 — 各言語に URL クラスかそれに相当するものがある。自分で書いたパターンは例外ケースで必ず間違える
  • 決まった区切りで切る — split や indexOf で済む仕事に正規表現を使うと遅く、読みにくい
  • 固定文字列の検索 — includes や grep -F を使う。パターンでないものをパターンエンジンに入れる理由がない

正規表現が合う場所は依然として広い。平らで、長さが制限されていて、構造が再帰的でないテキストにおいて、正規表現ほど短く意図を書ける道具はない。問題はその場所を外れたあとも使い続けることだ。

同じ正規表現でも道具ごとに文法が違うという問題は正規表現の方言互換性で、先読みの実戦的な使い方は先読みの実務活用で、ハングルを扱うときの音節の罠はハングル正規表現の音節の罠で別に扱った。シェルでグロブと正規表現を取り違える問題はシェルのグロブと正規表現の違いにある。

確認できなかったこと

  • Perl 5.38.2 が ^(a+)+$ で爆発しなかった正確な機序は確認できなかった。失敗した組合せを覚える最適化に見えるが、この機械の perldoc が動作せず、公式文書でその名称と条件を確かめられなかった。測定値だけをそのまま記した
  • Go と RE2 はこの機械に導入されておらず実行できなかった。表の該当行は実測ではなく公式文書の記述である。線形時間の保証と後方参照・先読み非対応は文書で確認したが、実際の時間は測っていない
  • GNU grep 3.0 の内部実装をコードで確認してはいない。「オートマトン方式」は広く知られた記述であり測定結果もそれと一致するが、この記事が確認したのは爆発が観測されなかったという事実までだ
  • grep の測定はプロセス起動時間およそ0.05秒に埋もれ、その下の区間の実際のマッチ費用は分解できなかった。500万文字で0.104秒という値から起動分を引いた残りとして推定したにすぎない
  • Python のサードパーティ regex モジュールと re2 バインディングはこの環境になく、比較から外れた。標準の re だけを測った
  • 他の JavaScript エンジン（SpiderMonkey・JavaScriptCore）は測っていない。V8 で出た値が他のエンジンでも同じだという根拠はない
