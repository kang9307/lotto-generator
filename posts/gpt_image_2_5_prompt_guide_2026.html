1. 생성 중심에서 보존 중심 편집으로의 패러다임 전환

인공지능 기반 시각 모델의 초기 발전 과정은 오로지 텍스트로부터 완전히 새로운 픽셀 캔버스를 만들어내는 단발성 텍스트 투 이미지(Text-to-Image) 역량에 집중되어 있었다. 화려한 수식어구와 화풍 묘사를 나열하면 모델이 잠재 공간에서 결과물을 길어 올리는 방식이었다. 그러나 이러한 생성 방식은 실제 상업용 제품 설계, UI 레이아웃 프로토타이핑, 전자상거래 카탈로그 제작과 같은 실무 파이프라인에 편입되는 순간 구조적 한계에 부딪힌다. 실무 엔지니어링에서 요구되는 것은 임의의 변형이 아니라, 승인된 기준 이미지의 구도와 인물의 정체성을 유지하면서 특정 의류나 배경의 일부 요소만을 정밀하게 교체하는 제어력이기 때문이다.

편집 지시가 의도하지 않은 부분까지 바꾸는 문제는 파이프라인에서 신뢰성 문제가 된다. OpenAI의 GPT Image 2.5 프롬프트 가이드는 바로 이 지점에서 중요한 기술적 지침을 제공한다. 이 문서는 편집 지시에서 「change only X」와 보존할 세부 목록을 함께 적으라고 안내한다.

원문은 편집에서 바꿀 것 하나와 보존할 것(정체성, 형태, 레이아웃, 조명, 라벨)을 나누어 적으라고 안내한다. 원문은 또 반복 편집이 보존하려던 세부를 바꿀 수 있다고 밝힌다(7절). 참고로 원문에는 gpt-image-1.5 가 2026년 12월 1일, gpt-image-1 이 2026년 10월 23일 종료 예정이라는 안내가 있다.

2. Flare와 Sunburst의 설계 특성과 모델 선택 기준

OpenAI 공식 문서는 GPT Image 2.5 세대에서 개발자가 선택할 수 있는 두 가지 모델 변형을 명시한다. 바로 gpt-image-2.5-flare와 gpt-image-2.5-sunburst이다. 두 모델은 동일한 프롬프트 문법과 파라미터 규격을 공유하지만, 최적화 방향이 다르다.

  • GPT Image 2.5 Flare: 원문은 「small model, optimized for speed, with image quality comparable to GPT Image 2」 라고 설명하며, 일상적인 빠른 고품질 생성에 고르라고 안내한다.
  • GPT Image 2.5 Sunburst: 원문은 「base model, optimized for quality, with higher image quality than GPT Image 2」 라고 설명하며, 편집 정밀도가 가장 중요한 워크플로에 고르라고 안내한다.

공식 문서는 실무 마이그레이션 및 모델 선택 시 다음과 같은 구체적인 원칙을 제시한다. GPT Image 2 가 이미 품질 요구를 충족하면 Flare 로 시작해 지연 시간 개선을 시험하고, 복잡한 사용 사례에서 GPT Image 2 가 모자라면 Sunburst 로 시작하라. 첫 비교에서는 프롬프트·참조·크기·출력 형식과, 명시적으로 고른 quality 값을 그대로 두어야 한다.

원문은 두 모델 모두 이미지 생성, 편집, 투명 배경을 지원한다고 밝힌다.

3. 공식 파라미터 체계와 제어 범위

GPT Image 2.5는 프롬프트 본문 내부의 자연어 지시와 분리되어 API 요청 페이로드에서 직접 전달되는 4가지 핵심 파라미터를 제공한다. 공식 문서에 명시된 파라미터 체계와 허용값은 시스템 레벨에서 모델의 렌더링 파이프라인을 제어하는 기준이 된다.

표 1: GPT Image 2.5 공식 API 파라미터 및 허용값 규격
파라미터명 공식 허용값 기본값 및 세부 특성 실무 적용 시 고려 사항
model gpt-image-2.5-flare, gpt-image-2.5-sunburst 원문에 나열된 모델 이름. GPT Image 1, 1.5, 2 도 문서에 언급됨 원문은 일상적인 빠른 고품질 생성에는 Flare, 편집 정밀도가 가장 중요한 워크플로에는 Sunburst 를 고르라고 안내한다.
quality auto, low, medium, high, xhigh, max 기본값 auto 원문: quality: low 는 빠른 초안용. xhigh·max 는 지연 시간 예산 안에서 아직 못 채운 품질 요구를 개선할 때만 쓴다.
size auto 또는 사용자 정의 WIDTHxHEIGHT 대표 크기: 1024x1024, 1536x1024, 1024x1536, 2048x2048, 2048x1152, 3840x2160, 2160x3840 임의 해상도 지정 시 아래 4가지 크기 조건을 준수해야 한다.
background auto, opaque, transparent 원문은 기본값을 명시하지 않음 투명 배경은 background: transparent 와 output_format 을 png 또는 webp 로 함께 지정한다. output_compression 은 jpeg·webp 에만 적용된다(0–100%).

원문은 더 높은 quality 설정이 모든 프롬프트에서 더 나은 결과를 보장하지는 않는다고 밝히고, 빠른 초안에는 low 를 쓰라고 한다. xhigh·max 는 지연 시간 예산 안에서 미충족 품질 요구를 개선할 때만 쓰라고 안내한다.

투명 배경이 필요하면 background: "transparent" 를 지정하고 png 또는 webp 로 받는다는 것이 원문의 안내다.

4. 해상도 제약 4대 원칙과 산술적 한계

GPT Image 2.5 API는 사전에 정의된 표준 해상도 외에도 WIDTHxHEIGHT 형태의 사용자 지정 해상도를 전면적으로 지원한다. 원문은 커스텀 크기를 WIDTHxHEIGHT 문자열로 받으며 다음 조건을 둔다.

  • 단일 변 상한: 두 변 모두 3,840픽셀을 넘을 수 없다.
  • 16픽셀 배수: 가로와 세로는 각각 16의 배수여야 한다.
  • 종횡비: 1:3 에서 3:1 사이여야 한다.
  • 총 픽셀 수: 655,360 이상 8,294,400 이하.

공식 문서는 총 픽셀 수가 3,686,400(2560x1440)을 초과하는 출력을 실험적(experimental) 단계로 분류한다. 이러한 제약 조건을 기준으로 실무에서 유효한 해상도와 거부되는 해상도를 산술적으로 계산해 정리하면 다음과 같다.

표 2: GPT Image 2.5 크기 제약 4대 원칙 및 산술 계산 예시 (※ 계산 예시는 본 글의 산술 도출 결과임)
제약 규칙 공식 명세 기준 유효 해상도 계산 예시 무효 해상도 및 거부 사유
단일 변 상한 각 변 ≤ 3,840px 3840x2160 (가로 3,840px로 단일 변 한도 완전 일치) 4000x2000 (가로 4,000px로 단일 변 최대치 3,840px 초과)
16픽셀 배수 단위 가로/세로 mod 16 = 0 1536x1024 (1536=16×96, 1024=16×64로 둘 다 배수 충족) 1530x1020 (1530/16=95.625로 16의 배수 조건 위배)
종횡비 한계 장축 / 단축 ≤ 3.0 3072x1024 (비율이 정확히 3.0:1로 허용 상한 내) 3200x1000 (비율이 3.2:1로 최대 허용 비율 3:1 초과)
총 픽셀 수 범위 655,360px ~ 8,294,400px 3840x2160 (총 8,294,400px로 최대 픽셀 상한선 완전 일치), 1024x1024 (총 1,048,576px) 640x640 (총 409,600px로 최소 픽셀 기준 655,360px 미달)

640x640 은 16의 배수이지만 총 픽셀 수가 409,600 으로 위 총 픽셀 조건(655,360 이상)에 못 미친다. 이 글의 제안으로, 위 네 조건을 클라이언트에서 미리 검사하면 크기 오류를 요청 전에 걸러낼 수 있다.

5. 변경과 제약의 분리 — 라벨 섹션 프롬프트 엔지니어링

OpenAI 공식 문서는 복잡한 시각적 요구를 전달할 때 긴 산문 형태의 프롬프트보다 명시적인 라벨 섹션(labeled sections)을 사용하는 구조화 방식을 안내한다. 가이드가 제시하는 핵심 구조는 장면(Scene), 주제(Subject), 세부 사항(Details), 제약 조건(Constraints)의 4분할 체계이다.

  • 주제와 용도의 명시: 단순한 사물 이름 대신 완성품의 최종 사용 목적을 명시한다. 예컨대 상품 사진, 광고, 다이어그램 같은 용도를 밝힌다.
  • 관측 가능한 세부 사항 기술: 모호한 감성 표현을 지양하고 재질, 조명, 색상, 시각 매체를 직접 기술한다.
  • 표기 텍스트의 정확한 인용: 화면에 인쇄되어야 할 텍스트는 반드시 큰따옴표로 감싸서 표기하고, 해당 문구가 나타날 위치와 타이포그래피 스타일을 명시한다. 불필요한 추가 텍스트를 배제하고 결과물의 철자와 가독성을 확인한다.
  • 변경 사항과 제약 조건의 분리: 생성 단계에서부터 원치 않는 텍스트, 로고, 워터마크 등의 제외 대상을 제약 항목으로 격리하여 프롬프트의 명확성을 높인다.

아래 프롬프트 블록은 OpenAI 공식 가이드의 구조화 지침에 따라 본 글에서 작성한 라벨 섹션 프롬프트 예시이다. 공식 문서의 원문 예시가 아니며, 실무 프로덕션에서 어떻게 라벨을 구분하여 작성할 수 있는지를 보여주는 구현 예시이다.

[Scene]: A bright, modern Nordic kitchen counter with soft morning daylight entering from the left window.
[Subject]: A compact matte-black espresso coffee machine placed on a light oak wood surface.
[Details]: Brushed metal drip tray, visible steam wand texture, warm ambient reflections, shallow depth of field focusing on the portafilter.
[Text Requirement]: The word "AURA" engraved on the front panel in clean minimalist sans-serif capitals, rendered exactly once.
[Constraints]: No human hands or figures, no commercial brand watermarks, no decorative clutter, clean photorealistic finish.

원문은 복잡한 요청을 장면·주제·세부·제약으로 나눈 라벨 섹션으로 정리하라고 안내한다. 라벨 이름과 예시 블록의 구체 문구는 이 글의 구성이다.

6. 실무 편집 워크플로 — 보존 목록의 수립과 적용

GPT Image 2.5 가이드의 가장 핵심적인 통찰은 이미지 편집 API(client.images.edit)를 다루는 원칙에서 드러난다. 공식 문서는 편집 지시를 작성할 때 개발자가 취해야 할 첫 번째 문장 구조로 다음을 명시한다.

Say "change only X" and list the details to preserve, such as identity, geometry, layout, lighting, or labels.

즉, "오직 X만을 변경하라"고 선언한 뒤, 변경되지 않고 유지되어야 할 대상 목록(Preserve List)을 즉시 나열하라는 것이다. 공식 가이드가 제시하는 보존의 5대 핵심 축은 다음과 같다.

  • 정체성(Identity): 피사체가 인물인 경우 이목구비의 형태, 피부 톤, 체형, 고유한 표정을 원본 그대로 고정한다.
  • 기하학적 형태(Geometry): 제품이나 기물의 물리적 비례, 윤곽선, 투시 원근을 왜곡하지 않고 유지한다.
  • 레이아웃(Layout): 전체 캔버스 내에서 피사체의 위치, 카메라 화각, 프레이밍, 여백의 비율을 동일하게 보존한다.
  • 조명(Lighting): 기존 장면에 흐르는 주광의 방향, 색온도, 그림자의 드리움 패턴을 새롭게 변경되는 요소에도 그대로 일치시킨다.
  • 라벨 및 텍스트(Labels): 원본 이미지에 포함되어 있던 텍스트, 설명 라벨, 인포그래픽 화살표의 위치와 서체를 손상 없이 보존한다.

이와 더불어 정밀한 국소 영역 편집에서는 채도, 명암 대비, 화살표, 카메라 각도, 주변 오브젝트의 위치를 불변 요소로 선언해야 한다. 다중 입력 이미지를 활용할 때도 각 입력 이미지에 번호를 부여하고 주제, 스타일, 의류, 배경 등의 역할을 지정해야 한다.

다음 프롬프트 블록은 보존 목록 원칙을 적용하여 특정 인물의 의상만을 교체할 때 사용하는 실무 프롬프트 예시이다. 이 역시 OpenAI 가이드의 규칙을 바탕으로 본 글에서 구성한 예시이다.

[Task]: Edit the input image to change only the clothing of the subject.
[Change Target]: Replace the current gray knit sweater with the dark-navy waterproof trench coat provided in reference image 2.
[Preserve List - Critical]:
- Identity: Keep the subject's face, facial features, eyes, smile, skin texture, and hairstyle completely unchanged.
- Geometry: Retain the existing upper body posture, shoulder angle, and arm placement.
- Lighting: Match the soft golden-hour directional sunlight and shadows of the original photo.
- Layout: Do not alter the urban street background, depth of field, or camera framing.
[Constraints]: Coat must drape naturally according to the body geometry, realistic fabric creases, no added accessories, no brand logos.

원문은 편집에서 「change only X」 와 보존 목록을 함께 적고, 여러 입력 이미지가 있으면 각 이미지를 번호와 역할(피사체, 스타일, 의류, 배경)로 지정하라고 안내한다. 위 프롬프트는 그 안내를 따른 이 글의 예시다.

7. 제약 명시의 대가와 반복 비용 — 남는 드리프트와 대응

그러나 보존 목록을 엄격하게 명시하는 프롬프트 엔지니어링이 항상 공짜로 주어지는 해결책은 아니다. 제약을 정교하게 기술할수록 수반되는 비용과 기술적 한계가 존재한다.

첫째, 제약이 늘어나는 비용. 이 글의 추측으로는, 보존 항목을 많이 적을수록 프롬프트가 길어져 핵심 변경 지시가 묻힐 수 있다. 원문이 이 현상을 다룬 것은 아니다.

둘째, 반복 편집의 드리프트. 원문은 「Repeated edits can still change details you intended to preserve」 라고 밝힌다. 공식 문서 역시 이 문제를 명확히 인정하며 다음과 같은 대처법을 권고한다.

Restate critical constraints if the result drifts. If a region must remain pixel-identical, composite the approved edit into the original image instead of relying on prompting alone.

즉, 반복 편집 중 결과가 원본에서 벗어나기 시작하면 핵심 제약 조건을 다시 강조해 적어야 하며, 만약 특정 영역이 단 1픽셀의 오차도 없이 완벽히 동일하게 유지되어야 한다면 프롬프트에만 의존하지 말고 승인된 편집 영역을 원본 이미지에 마스킹 합성(compositing)하라는 것이다. 모델의 생성 능력과 전통적인 그래픽 합성 파이프라인의 명확한 역할 분담을 요구하는 대목이다.

8. 검증 절차 — 동일 이미지에 대한 보존 프롬프트 비교 평가

실무에서 보존 목록 기반 프롬프트가 미치는 영향을 파악하고자 할 때는 A/B 비교로 확인해 볼 수 있다. 본 글이 제안하는 비교 검증 절차는 다음과 같다.

  1. 기준 원본 에셋 고정: 얼굴 정체성이 뚜렷한 인물 사진, 복잡한 인포그래픽, 텍스트 라벨이 포함된 제품 패키지 사진 등 검증 대상이 되는 기준 에셋을 각각 1장씩 준비한다.
  2. 비교군 A (단순 변경 요청) 실행: 동일한 모델과 파라미터(size, quality) 환경에서 오직 변경 사항만 단순 기술한 프롬프트(예: "남성의 재킷을 베이지색 가죽 재킷으로 바꿔라")로 편집 API를 호출한다.
  3. 비교군 B (보존 목록 분리 요청) 실행: 동일한 환경에서 라벨 섹션과 보존 목록을 엄격히 분리한 프롬프트(예: "오직 재킷만 변경하라. 얼굴, 헤어스타일, 조명, 배경 구도를 원본과 동일하게 유지하라")로 편집 API를 호출한다.
  4. 4대 시각적 무결성 지표 평가:
    • 정체성 보존율: 원본과 편집본 간 피사체 얼굴 및 주요 형태의 유사도 일치 여부 점검.
    • 배경 무결성: 피사체 외곽 배경의 조명 방향, 텍스처, 사물 배치가 원본과 동일하게 유지되었는지 대조.
    • 경계면 아티팩트: 교체된 의상이나 오브젝트의 경계선에 부자연스러운 번짐이나 픽셀 왜곡이 없는지 검사.
    • 원치 않는 부수적 변형: 지시하지 않은 텍스트 생성, 액세서리 추가, 채도 왜곡이 발생했는지 기록.

이 절의 절차는 원문에 있는 것이 아니라 이 글의 제안이며, 이 글은 이 비교를 직접 수행하지 않았다. 결과는 각자의 이미지와 설정에서 확인해야 한다.

9. 확인하지 못한 것

본 분석은 OpenAI 공식 API 개발자 가이드 문서를 바탕으로 작성되었으며, 공식 문서에서 다루지 않거나 확인되지 않은 기술적 사항은 다음과 같다.

  • 공식 가이드 문서는 GPT Image 2.5 Flare와 Sunburst의 토큰당 또는 생성 건당 구체적인 API 호출 요금 및 과금 기준 수치를 원문에서 확인하지 못했다. 실제 운영 비용은 플랫폼의 공식 요금표 페이지를 통해 별도로 대조해야 한다.
  • Flare 와 Sunburst 의 평균 응답 시간(latency) 수치: 원문은 정량 수치를 제시하지 않는다.
  • 연속 편집을 수행할 때 평균 몇 회 차의 루프에서 피사체의 인상이나 배경 구조가 허용 임계치를 넘어 왜곡(drift)되는지에 대한 통계적 수명 데이터는 원문에서 확인하지 못했다.
