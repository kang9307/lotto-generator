输入什么、产出什么

Archify 是安装到智能体里的技能。README 的第一句话是：把想要理解、规划或分享的东西变成可交互的视觉内容。它不局限于系统图，也展示了旅行日程和学习地图之类的案例，但 GeekNews 的介绍和本文关心的是由代码和描述生成系统图这一侧。关键在于分工：不是人来操作绘图工具，而是智能体写出图的源数据，再由渲染器把它变成画面。

输入可以归为三种。第一种是把系统用文字描述出来。README 的例子只有一句话：浏览器调用 API，API 检查 Redis，缓存未命中时查询 PostgreSQL 并回填缓存。第二种是仓库。可以让智能体读取仓库，请它给出有依据的架构图，README 明确说明仓库不是必需的。第三种是对已生成的图做微调的后续请求，比如添加 Redis、把认证移到左边、突出回滚路径。README 说 Archify 会保留带类型的源数据，因此只修改指定的部分。

产出分为以下几类。

  • 单个 HTML 文件。 节点详情和路径探索都在文件里，接收者无需安装 Archify，用浏览器即可打开。只有外部网站和地图链接需要联网。
  • 带类型的 JSON 中间表示。 每个接入渲染器的模式都有模式定义，README 说明同一份源数据可以复现同样的结果。
  • 图片和视频导出。 可以把 PNG 复制到剪贴板，也可以下载静态或动态格式。GeekNews 的介绍提到了 PNG、SVG 和 WebM。
  • 分享卡片。 追踪过的路径或可达范围可以下载为 1200×630 的 PNG，完整的图作为上下文保留。
  • 对比视图。 比较变更前后快照的 Architecture Delta 是单独的模式。

本文的切入点可以压缩成两个问题。智能体读代码并生成图的过程中，哪些是自动处理的，而拿到结果的人必须亲手核对什么。已经写过的相邻主题不再重复。把视觉规则作为后处理套上去的做法在 Diagram Design 技能一文中，结合静态分析与 LLM 提取架构的做法在 CodeBoarding 一文中。Archify 与这两者不同，它是把智能体凭判断写出的 JSON 送过验证关卡，所以关卡保证什么、不保证什么，才是值得读的地方。

安装与调用 — 只用 README 里有的命令

安装默认是一条 npx 技能安装命令。支持对象列出了 Cursor、Claude Code、Codex CLI 和 OpenCode。下面两行是 README 原样给出的命令，第一行是默认安装，第二行是不安装而直接试用。

npx skills add tt-a1i/archify -g
                    npx skills use tt-a1i/archify@archify --agent codex

针对 Cursor，README 另外给出了不做交互提问的明确安装形式。该命令用选项指定技能名称、智能体、全局安装、复制方式和跳过确认。调用不是命令，而是自然语言。请智能体用 Archify 画图即可，README 的第一个例句就是如此，之后可以继续对话，要求添加认证、突出缓存未命中路径或切换到浅色主题。

安装位置因智能体而异。README 的表格概括如下。

  • Claude Code。 ~/.claude/skills/ 或项目内的 .claude/skills/。渲染器与验证流程整体可用。
  • Codex CLI 与 opencode。 各有自己的技能目录，表中写明同样的完整流程可用。
  • Claude.ai。 在设置的技能项里上传 archify.zip。README 明确说可用范围取决于沙箱能否使用 Node.js。
  • 项目知识（Project Knowledge）。 上传同一个 zip 得到的是基于提示词的架构替代路径，与使用渲染器和验证流程的路径不同。

这个列表里实务上最重要的是最后两项。渲染器和验证器用 Node.js 运行，所以在无法执行 Node 的环境里，Archify 所承诺的验证环节本身就缺失了。装上技能与验证流程真正跑起来是两回事，这个差别会在后面的表里再次作为人要核对的项目出现。README 里也有社区维护的 Hermes Agent 和 DeepSeek Harness 集成，都标注为可选加入，并注明不是官方产品、没有遥测。

五种图类型与提示词里该写什么

Archify 把图分为五类。选择类型是技能流程的第一步，而用户在提示词里写什么会左右结果的准确度，所以 README 按类型给出了应写入的信息。

类型适用对象提示词里写什么
Architecture组件、服务、存储、边界范围、核心组件、主路径
WorkflowCI/CD、审批、工具调用、运行手册参与者、顺序、分支、例外
SequenceAPI 调用、缓存回退、认证、异步追踪调用方、被调用方、返回、时序
Data Flow管道、血缘、个人信息、消费方来源、转换、存储、边界
Lifecycle状态、重试、等待、终止结果状态、事件、重试与取消路径

表里值得注意的是右边一列。列为提示词里该写的项目，实际上就是将出现在图里的事实清单。即使由智能体从代码中查明，人事先定下范围和核心组件，图也会更聚焦。README 的仓库分析示例正是把这一原则直接写成了句子。

Analyze this repository, then use archify to create a high-level runtime architecture diagram.
                    Show 8–12 core components, one primary path, external dependencies, and trust boundaries.
                    Put supporting detail in cards instead of adding more edges.

这个示例提出了三点要求：把组件限制在 8 到 12 个，只保留一条主路径，补充信息放进卡片而不是增加连线。限制数量是为了让图好读，但对人来说还有另一层含义。没能挤进 12 个的组件就不在图里，而“不在图里”这一事实不会显示在图上。只有定下范围的人知道漏掉了什么。

  • 在范围句里写明系统名称和边界，技能更容易决定包含什么。
  • 把主路径钉成一条，其余退为补充信息，连线就不会缠在一起。
  • 信任边界和外部依赖不提出要求时图里可能没有，明确写出更稳妥。

生成流程 — JSON 中间表示与验证关卡

Archify 结构上最有特点的一点是写 JSON 而不是直接画图。综合 README 的说明和技能定义，流程如下。

  1. 判别类型。 确定请求属于架构、工作流、时序、数据流还是生命周期。
  2. 读取模式与示例。 分批读取该类型的模式定义和示例。
  3. 编写候选 JSON。 由智能体直接写出完整的候选 JSON。技能定义指出，节点、关系、出处、视图、卡片、边界的数量既不是目标也不是上限，并且不要先画草图或用文字规划坐标。
  4. 最终处理（finalize）。 一次性执行验证与交付。技能定义写明，通过意味着验证、交付、严格检查和真实浏览器检查这几道关卡都通过了。
  5. 修复失败。 若有关卡失败，就修改 JSON 后重新运行。修正机会限制为两轮。

交付阶段是原子的。候选结果在同一目录下渲染并检查，只有通过的结果才会原子地替换现有产物。因此保存到一半时，错误的文件不会覆盖上一个正常版本。README 把检查项列为模式、布局、HTML/SVG、路径以及标签与路径之间的间距。用仓库命令可以分别执行验证和交付，如下所示。

cd archify
                    node bin/archify.mjs validate workflow examples/agent-tool-call.workflow.json --quality showcase --json
                    node bin/archify.mjs deliver workflow examples/agent-tool-call.workflow.json /tmp/workflow.html --quality showcase --open --json

失败时的格式也是固定的。validate --json 和 deliver --json 输出一个 JSON 对象，其中只包含稳定的规则代码、出问题的对象、测得的证据以及受支持的修复手段。智能体只应用每条诊断附带的受支持修复，技能定义禁止在退出码非零时声称成功，也禁止在没有实际截图的情况下声称做过目视检查。这是把智能体的汇报与机器输出绑在一起的装置。

  • 验证失败以规则代码和测量值的形式给出，而不是堆栈跟踪，重试就成了指定的修复而不是猜测。
  • 可选的预览只在 127.0.0.1 的随机端口上打开，且只有最新候选通过全部关卡时画面才会刷新。
  • 动态效果只在被要求时开启，默认输出是静态的。
  • README 写明目视评审与自动检查是分开的。

由代码画出的图的依据 — SRC n 与固定的提交

从仓库画图时，最大的问题是图中每个方框对应代码的哪里。README 把这作为一项可选的依据功能来处理。只在被要求时开启，开启后，有依据的架构节点会标上 SRC n，并打开固定在某个公开提交上的文件和行范围。README 说明这些文件位置经过 Git 核实。没有要求依据的普通产物则保持无出处的状态。

作为实例，README 举了公开仓库 mco-org/mco。它在提交 9f1a1cf 的时点追踪了该仓库，画出运行时架构，并作为经过检查的图予以介绍。结果 HTML 和带类型的 JSON 源数据一并公开在仓库的文档目录里，可以拿图与源数据对照。从这个案例中能读到的是，产物绑定在特定提交上。代码改变后，这张图就是该提交时点的事实，不会自动更新。

依据标记保证什么，必须精确区分。SRC n 会打开节点所引用的文件和行范围。该范围是否支撑节点的描述、关系是否是真实的调用路径，只有人打开阅读才能知道。依据的存在与依据的适当是不同的层面，自动化帮助前者，把后者留给人。

  • 对带标记的节点，打开它指向的文件，读一读是否与描述相符。
  • 对没有标记的节点，视为无依据绘制，向作者追问出处。
  • 确认固定提交与当前分支之间的差异。图是那个提交的快照。
  • 在缩减到 8 至 12 个的图中，被落下的组件由写提示词的人记录下来。
  • 外部依赖和信任边界只在提示词要求的范围内存在于图中。

哪些被自动化，哪些要人来核对

把到这里为止的内容按阶段汇总，就得到下面的表。左起第二列是 README 和技能定义里实际写的内容，第三、四列是依据这些文档整理的、人应做的事和遗留局限，属于解读。文档里没有的项目用—表示。

阶段README 里有的人要核对的局限
安装npx 安装命令、各智能体的安装位置、更新提醒可选能否运行 Node.js，装上的是完整流程还是提示词替代路径Claude.ai 与项目知识取决于 Node 访问
整理输入各类型提示词里该写的项目范围、核心组件、主路径、边界是否由人定下漏掉的要素不会显示在图上
读取仓库智能体读代码，把架构草稿写成 JSON节点和关系是否与真实代码相符，是否要求了依据标记—
验证模式、布局、HTML/SVG、路径、标签间距检查与原子替换看退出码和诊断 JSON 的原文，而不是智能体的摘要是形式一致，不是事实一致
依据标记SRC n 标记与固定提交的文件、行范围打开范围，读它是否支撑描述绑定在某个公开提交上

变更对比Before、Delta、After 快照与机器回执两个快照是否按同一标准编写不推断影响、风险和合并安全性

表的要点是：自动化强在形式和可复现，把内容的真实性交给人。验证关卡证明图没有坏，并不证明图是对的。这不是缺陷，而是文档自己划的线。技能定义把目视评审与自动检查分开，README 在可达范围的导出上加注不主张运行时影响，原因就在这里。

  • 图画得漂亮，与通过验证有关，却与和代码是否一致无关。
  • 退出码和诊断 JSON 优先于智能体最终回复里的成功汇报。
  • 把同一个仓库画两次，比较节点构成是否变化，可以看出判断在哪里摇摆。本文的依据材料里没有这样的复现结果，所以只作为值得尝试的步骤来写。
  • 分享前在图的标题旁写上基准提交和创建日期，可以减少旧图被当作最新的情况。
  • 涉及安全边界或个人信息流的图，另外交由负责人评审。

图没有说的事 — 已写明的关系与运行时影响

Archify 明显在意的一个部分，是交互到底在主张什么。README 把这称为诚实的交互。聚焦、上游与下游的可达范围、精确路径、角色对比、故事讲解，都只复用作者写下的节点和关系，既不虚构拓扑，也不主张运行时影响。选中一个节点并开启下游可达范围时，该节点之后延续的连线会被突出，那是沿着 JSON 里写明的关系走出来的结果，并不是对故障究竟会蔓延多远的预测。

这个区分直接关系到人读图的态度。看到屏幕上某个节点的下游被大片突出，就把它读成影响范围，那就是读了图没有说的东西。实际调用是否有条件、是否异步、是否是不再使用的路径，图里都没有。部署归属配置也是同样的姿态。只要已写明的负责人、区域放置、私有数据库范围、命名的边界穿越中缺少任何一项就会失败，它不会被隐式启用，README 写明它也不检查真实的基础设施。

变更对比遵循同样的原则。Architecture Delta 把经过验证的 Before、Delta、After 快照连同机器回执一起比较，读者可以选中某项已写明的变更，或播放一段有限长度的评审。它不推断影响、风险和合并安全性。对比命令在 README 中如下所示。

node archify/bin/archify.mjs compare architecture base.json head.json architecture-delta.html --json

这条命令以两个 JSON 为输入。两个 JSON 是人或智能体对各时点结构的描述，所以对比的准确度取决于两份描述的质量。若在代码评审中使用这个画面，只用来快速浏览变更的事实，而不作为批准决定的依据，才符合文档划出的线。

  • 可达范围是沿已写明的关系走出的结果，不是运行时影响的预测。
  • 路径追踪只显示图中画出的路径，不是真实流量沿着它流动的证据。
  • 部署归属配置只防止已写明信息的遗漏，不检查与真实基础设施是否一致。
  • Delta 画面列出变更的事实，不评估风险。

被排除在范围外的事与运行上的性质

README 也明确写了不做什么。Mermaid 自动解析、通用自动布局、托管分享和所见即所得编辑，被有意排除在当前范围之外。它把自己定义为既不是通用绘图编辑器，也不是 Mermaid 主题，而是把技术意图变成沟通产物的工具。布局同样不是自动布局算法：由智能体判断层级、间距、路径和强调，只有共用的自动端点会被确定性地分散，避免箭头堆在同一个点上。对已经拥有 Mermaid 或 draw.io 资产的团队来说，这意味着没有直接读入它们的功能，需要把现有资产重新描述一遍。

运行上的一些性质也有记载。

  • 更新检查。 向固定的稳定版清单发出 GET 请求以显示可选提醒，不下载也不安装。成功的检查约等待 24 小时，失败则在 6 小时后重试，之后每隔 24 小时。README 写明，服务器能看到 IP 和时间这类普通 HTTP 元数据，但收不到版本、智能体、项目数据、提示词以及账号和设备标识。ARCHIFY_UPDATE_CHECK_DISABLED=1 可以关闭联网和提醒状态的写入。
  • 语言。 meta.locale 会本地化页面标题、图例、状态与错误、无障碍文案和 HTML/SVG 的 lang 属性，但不翻译已写明的内容。英语和简体中文（zh-CN）为内置，其他语言若不提供翻译表就回退为英语，并会披露这一回退。韩语用户应预期图的标题和图例会以英语显示。
  • 无障碍。 由读者触发的动态效果是有限的，遵循系统的减少动态设置，且不进入默认导出。
  • 查看器操作。 问号键打开帮助，斜杠搜索节点，R 追踪路径，L 对比角色，M 打开概览，F 进入演示模式。链接哈希可以恢复聚焦、关系、路径和透镜的状态。
  • 维护状态。 仓库的版本标记为 3.0.1，许可证为 MIT，社区集成被明确标注为非官方产品。GeekNews 的评论里有人反映在开发过程中要求可视化时会用这个技能来画，但这是个人经验，不能作为性能的依据。

总结来说，引入 Archify 的团队要决定三件事：谁来评审图，如何给图附上基准提交和日期，是否允许更新检查这类联网行为。从文档中能读出的设计，是工具验证形式、人验证内容的分工。

未能确认的事项

  • 在真实仓库上运行该技能的结果。本文只涉及 README、技能定义和介绍文章的记述，没有衡量所生成图准确度的资料。
  • 完整技能定义中仓库编写流程（Repository authoring）的细节。只以概括出的规则为依据。
