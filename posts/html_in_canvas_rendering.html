캔버스에 HTML을 그리는 API, 무엇을 얻고 무엇을 잃나

크롬 실험 기능 HTML-in-Canvas가 푸는 문제와, 캔버스 위 글자가 원래부터 잃고 있던 것

2026-08-20 IT/기술

서론: 캔버스 위의 글자가 늘 어딘가 어색한 이유

웹 기반 디자인 도구나 화이트보드를 쓰다가 한 번쯤 겪는 일이 있다. 화면에 분명히 글자가 보이는데 드래그로 선택이 안 된다. Ctrl+F로 찾으면 없다고 나온다. 번역 확장을 켜도 그 부분만 원래 언어로 남고, 스크린리더는 그 자리를 통째로 건너뛴다.

버그가 아니다. 그 글자는 텍스트가 아니라 그림이기 때문이다. <canvas>에 그려진 순간 글자는 픽셀 배열이 되고, 브라우저 입장에서 거기에 무엇이 적혀 있었는지는 알 길이 없다.

크롬이 플래그 뒤에서 실험 중인 HTML-in-Canvas는 정확히 이 지점을 건드린다. canvas 안에 진짜 DOM 요소를 두고, 그것을 브라우저가 레이아웃한 결과 그대로 캔버스에 그린다는 제안이다. 국내에는 캔버스 에디터를 만드는 개발자가 이 기능으로 작은 UI 라이브러리를 만들어 공유하면서 알려졌다. 무엇을 얻는지, 무엇을 대가로 내주는지, 그리고 오늘은 무엇을 쓰면 되는지 차례로 본다.

무엇을 하려는 기능인가

핵심 아이디어는 한 문장이다. <canvas>의 자식 요소를 진짜로 레이아웃하고, 그 결과를 캔버스 표면에 그린다.

WICG 의 explainer 가 정의한 조각은 크게 셋이다.

  • layoutsubtree 속성 — canvas 요소에 붙이면 자손들이 레이아웃과 히트 테스트에 참여한다. 지금까지 canvas의 자식은 레이아웃 계산 대상이 아니었다
  • 그리기 메서드 — 2D의 drawElementImage(), WebGL의 texElementImage2D(), WebGPU의 copyElementImageToTexture(). 요소를 지정하면 그 렌더링 결과가 캔버스나 텍스처로 들어간다
  • paint 이벤트 — canvas 자식의 렌더링이 바뀌면 발생한다. 인터섹션 옵저버 단계 뒤에 실행되고 바뀐 요소 목록을 전달한다

보조 조각으로 captureElementImage()가 요소를 워커로 넘길 수 있는 스냅샷으로 만들고, 3D 컨텍스트용 getElementTransform()이 그리기 변환 행렬을 CSS 변환으로 되돌려 준다. explainer 에 실린 기본 형태는 이렇다.

<canvas id="canvas" layoutsubtree>
  <form id="form_element">
    <label for="name">name:</label>
    <input id="name">
  </form>
</canvas>

<script>
  canvas.onpaint = () => {
    ctx.reset();
    const transform = ctx.drawElementImage(form_element, 100, 0);
    form_element.style.transform = transform.toString();
  };
</script>

짧은 코드지만 마지막 줄이 이 API의 성격을 보여 준다. drawElementImage()는 그린 위치의 변환 행렬을 돌려주고, 개발자는 그것을 다시 원래 요소의 style.transform에 되먹인다. 그려진 픽셀과 실제 DOM 요소의 위치를 손으로 맞추는 셈인데, 왜 그래야 하는지는 접근성 절에서 다시 다룬다.

이름이 한 번 바뀐 것도 기억해 둘 만하다. 처음에는 drawElement였고 이후 drawElementImage·texElementImage2D로 개명됐다. 아직 이름이 굳지 않은 단계라는 신호다.

왜 지금까지 어려웠나 — 픽셀에는 구조가 없다

canvas 2D API는 명령형 그리기 표면이다. fillRect는 사각형을 기억하지 않고 그 자리의 픽셀을 칠한다. fillText도 마찬가지다. 글리프를 찍고 나면 남는 것은 색뿐이고, 텍스트 노드도 박스도 생기지 않는다.

성능을 위한 선택이었다. 유지할 장면 그래프가 없으니 가볍고, 매 프레임 전부 다시 그리는 게임·시각화에 잘 맞는다. 대신 브라우저가 문서에 대해 해 주던 일이 함께 사라진다. 줄바꿈, 양방향 텍스트 처리, 폰트 폴백, 박스 모델, 이벤트 대상 판정 — 전부 직접 구현해야 한다.

HTML 명세도 이 문제를 알고 있어서 canvas 요소 안에 대체 콘텐츠를 두게 했다. 문제는 그 대체 콘텐츠가 실제로 그려지는 내용과 아무 관계가 없다는 점이다. explainer 도 같은 말을 한다. 캔버스 접근성에 쓰이는 대체 콘텐츠가 렌더된 내용과 항상 일치한다는 보장이 없고, 그런 대체 콘텐츠를 만들어 내는 일 자체가 어렵다는 것이다.

그래서 실무는 우회로를 만들어 왔다. 세 갈래인데 셋 다 같은 지점에서 멈춘다.

SVG foreignObject 를 이미지로 만들어 그리기

SVG 안에 <foreignObject>로 HTML을 넣고, 그 SVG를 데이터 URL로 만들어 <img>로 로드한 뒤 drawImage()로 그리는 방식이다. 브라우저의 레이아웃 엔진을 쓴다는 점에서 발상은 이 제안과 같다.

  • 이미지로 로드된 SVG는 외부 리소스를 가져오지 못한다. 웹폰트도 이미지도 전부 데이터 URI로 인라인해야 한다
  • 스크립트가 실행되지 않으므로 동적인 것은 담을 수 없다
  • 인라인을 빠뜨리면 오류가 아니라 글꼴이 조용히 대체된다. 개발 환경과 배포 환경의 결과가 달라지는 대표적 원인이다
  • 결정적으로 그려진 결과는 다시 픽셀이다. 접근성은 하나도 남지 않는다

라이브러리로 DOM 렌더링을 재현하기

html2canvas 계열이 택한 길이다. DOM을 순회하며 계산된 스타일을 읽고 그것을 캔버스 그리기 명령으로 옮긴다. 사실상 브라우저 렌더링 엔진의 일부를 자바스크립트로 다시 구현하는 일이다. 제안을 분석한 Codrops 글은 한계를 이렇게 정리했다. 각 CSS 속성을 손으로 구현해야 하므로 완전한 CSS 지원은 불가능하다는 것이다. 지원 목록이 길어져도 브라우저가 앞서가므로 격차는 사라지지 않고, 여기서도 결과물은 픽셀이다.

손으로 텍스트를 그리기

가장 많이 쓰이는 방법이자 가장 오래 걸리는 방법이다. measureText()로 폭을 재고 직접 줄을 나눈다. 짧은 영문 라벨이라면 반나절이면 된다. 문제는 그다음에 온다.

  • 한국어와 일본어의 금칙 처리 — 줄 끝이나 줄 처음에 오면 안 되는 문자 규칙
  • 이모지와 결합 문자 — 코드 포인트 단위로 자르면 글자가 깨진다
  • 아랍어·히브리어의 양방향 텍스트 — 논리 순서와 표시 순서가 다르다
  • 폰트 폴백 — 한 문자열 안에서 글꼴이 바뀔 때의 기준선 정렬

이 목록은 끝나지 않는다. 브라우저 native 기능을 다시 만들지 말라는 원칙이 가장 선명하게 들어맞는 영역이 텍스트 레이아웃이다.

이걸 원하는 진짜 이유 — 레이아웃 엔진을 공짜로 쓰고 싶다

이 기능을 기다리는 쪽의 요구를 정리하면 네 갈래로 모인다.

  • 게임 UI — 인벤토리, 설정 화면, 대화 상자. 엔진 안에 UI 시스템을 따로 만들면 버튼 하나 정렬하는 데 CSS 한 줄이면 될 일을 코드로 쓴다
  • 데이터 시각화 위의 라벨 — WebGL로 수십만 점을 그리는 차트에서 제일 손이 많이 가는 부분이 축 라벨과 툴팁이다. 점은 GPU가 알아서 그리지만 글자는 그렇지 않다
  • 지도 — POI 라벨 배치, 다국어 폰트 폴백, 도로명을 곡선을 따라 흘리기. 지도 렌더러가 텍스트 엔진을 자체 구현하는 이유다
  • 디자인 도구와 화이트보드 — 텍스트 편집 상자 하나에 커서 위치 계산, 선택 영역 하이라이트, IME 조합 처리가 전부 들어간다. 무한 캔버스형 도구가 늘수록 이 부담도 는다

공통점은 명확하다. 이들이 원하는 것은 그리기가 아니라 레이아웃 계산이다. 브라우저 안에는 이미 가장 많이 검증된 텍스트 레이아웃 엔진이 들어 있는데 캔버스에서는 그것에 닿을 통로가 없었다. explainer 의 동기 문단도 같은 말을 한다. 복잡한 텍스트 레이아웃을 canvas에 렌더링할 쉬운 웹 API가 없고, 그 결과 canvas 기반 콘텐츠가 접근성·국제화·성능·품질에서 손해를 본다는 것이다. 국제화가 접근성과 나란히 놓여 있다는 점은 눈여겨볼 만하다. 한국어·일본어·아랍어 쪽에서 이 손해는 훨씬 크다.

캔버스에 글자를 그리면 무엇을 잃는가

여기서부터가 이 기능을 평가할 때 가장 중요한 부분이다. 캔버스로 UI를 그리는 선택은 성능을 얻고 무언가를 내주는 거래인데, 내주는 쪽 목록이 생각보다 길다.

기능DOM 텍스트캔버스에 그린 글자영향받는 쪽
스크린리더 낭독기본 동작없음시각장애 사용자
드래그 선택과 복사기본 동작없음모든 사용자
페이지 내 찾기기본 동작없음모든 사용자
브라우저 자동 번역기본 동작없음외국어 독자
확대 시 리플로우줄이 재배치됨픽셀 확대저시력 사용자
사용자 지정 최소 글꼴반영됨무시됨저시력 사용자
강제 색 모드와 고대비반영됨무시됨대비 민감 사용자
키보드 포커스와 탭 순서기본 동작직접 구현키보드 사용자
검색엔진 색인수집됨안 됨사이트 운영자

짚어야 할 것은 개별 항목이 아니라 기본값의 방향이다. DOM 쪽 열은 전부 「그냥 된다」이고 캔버스 쪽 열은 전부 「직접 하거나 포기한다」이다. 개발자가 실수해서 생기는 결과가 아니라, canvas를 정상적으로 사용했을 때 자동으로 도달하는 상태다.

그래서 이 문제는 개별 프로젝트의 성실도로 해결되지 않는다. 성실한 팀은 대체 콘텐츠를 만들지만 그것은 렌더링과 별개의 코드 경로라 시간이 지나면 어긋난다. 문서 포맷 쪽에서 구조 없는 결과물이 기계에게 무엇을 남기는지 반복해 확인된 것과 같은 문제다.

이 제안이 접근성을 다루는 방식과, 아직 남는 질문

이 API가 접근성 논의에서 흥미로운 이유는 문제의 원인을 이중 유지에서 찾았다는 점이다. explainer 는 이 API로 그린 요소가 그에 대응하는 canvas 대체 콘텐츠와 일치한다고 밝힌다. 그릴 대상이 곧 대체 콘텐츠이므로 둘이 갈라질 구조적 여지가 줄어든다. 여기에 layoutsubtree가 자식을 히트 테스트에 참여시키므로 캔버스 에디터가 손으로 짜던 좌표 대 요소 대응 코드도 상당 부분 사라진다. 크롬 개발자 블로그는 한 걸음 더 나아가, 캔버스 안 콘텐츠가 접근성 트리에 노출되어 보조 기술과 호환되며 페이지 내 찾기·복사·우클릭이 지원된다고 서술한다.

다만 이것을 「접근성 문제가 해결됐다」로 읽으면 안 된다. 1차 문서들이 스스로 적어 둔 제약이 남아 있고, 실제 보조 기술에서의 동작을 확인한 자료는 이 글을 쓰는 시점에 찾지 못했다.

explainer 가 명시한 제약부터 보자.

  • CSS 변환은 렌더링에서 무시되지만 히트 테스트와 접근성에는 영향을 준다. 이 한 줄이 앞서 본 예제의 마지막 줄을 설명한다. 그린 위치를 style.transform에 되먹이지 않으면 보이는 자리와 접근성 트리가 가리키는 자리가 갈라진다. 그 되먹임은 개발자가 빠뜨릴 수 있다
  • 넘치는 콘텐츠는 보더 박스 기준으로 잘린다. DOM에서라면 넘쳐 보였을 텍스트가 캔버스에서는 잘려 나간다
  • 스크롤은 자바스크립트에 의존한다. 크롬 문서가 밝힌 제약으로, 캔버스 밖에서 컴포지터가 처리하던 스크롤과 같지 않다. explainer 는 스크롤과 애니메이션의 스레드 처리를 자동 갱신 캔버스 모드로 검토 중이라고 적었다 — 아직 없다는 뜻이다

여기에 확인되지 않은 축이 하나 더 있다. 접근성 트리에 텍스트가 노출되는 것과, 저시력 사용자가 브라우저 설정으로 글자를 키웠을 때 캔버스 안 레이아웃이 다시 계산되는 것은 전혀 다른 문제다. 정리하면 이 제안이 자동으로 붙여 주는 것은 접근성 트리와 렌더링의 일치이지 캔버스 UI의 사용성 전반이 아니다. 그것만으로도 나은 출발점이지만, 「캔버스에 그려도 접근성은 API가 알아서 한다」는 기대는 아직 근거가 없다.

그릴 수 없는 것들 — 프라이버시 제약이 API 모양을 정한다

이 API에는 처음 보면 이상해 보이는 제약이 붙어 있는데, 이유를 알면 협상 불가능한 조건이 된다. 핵심은 캔버스가 읽을 수 있는 표면이라는 점이다. 스크립트가 getImageData()로 픽셀을 되읽을 수 있다. 반면 DOM은 스크립트가 읽으면 안 되는 것들을 화면에는 보여 준다. 방문한 링크의 색이 대표적이다. 이 둘을 그냥 연결하면 픽셀을 읽어 사용자의 방문 기록을 알아내는 오래된 공격이 되살아난다.

그래서 explainer 는 되읽기가 허용되는 렌더링이라는 개념을 두고, 요소 이미지를 그리는 메서드와 paint 이벤트가 보안 또는 프라이버시에 민감한 정보를 드러내서는 안 된다고 규정한다. 제외 대상은 이렇다.

  • 크로스 오리진 데이터 — 다른 출처의 iframe 내용은 그려지지 않는다
  • 시스템 색 — OS 테마에서 오는 색 키워드
  • 방문한 링크 정보 — :visited 스타일이 반영되지 않는다
  • IME 팝업 — 입력기 후보 창

이 목록은 나중에 채울 미구현이 아니라 이 API가 존재할 수 있는 조건이다. 실무로 옮기면, 캔버스에 굽는 UI에서 :visited에 의존하는 스타일, 크로스 오리진 위젯, 시스템 색 키워드를 쓰는 컴포넌트는 화면과 다르게 나올 수 있다.

호환성 현실 — 지금 어디까지 와 있나

표준화 단계부터 정확히 짚자. 이 기능은 WICG 인큐베이션 단계의 제안이다. 저장소 문서는 스스로를 피드백에 따라 계속 갱신되는 살아 있는 explainer 라고 밝히고 있다. HTML 명세에 편입된 상태가 아니고, W3C 권고와도 거리가 멀다.

버전 숫자는 일부러 표에 넣지 않았다. 출처마다 다르게 적혀 있기 때문이다. 국내에 소개한 개발자는 크로미움 146 이상을 요구했고, 브라우저 지원 문서는 147 이상을 적었으며, 크롬 개발자 블로그는 별도의 오리진 트라이얼 구간과 카나리 버전을 안내한다. 확실한 방법은 자기 브라우저에서 플래그가 있는지 직접 확인하는 것이다.

결론은 하나뿐이다. 프로덕션에 넣을 물건이 아니다. 이름이 이미 한 번 바뀌었고, 다른 두 엔진의 공식 입장이 없으며, 플래그를 켠 사용자만 볼 수 있다. 이 상태에서 UI 구조를 이 API에 걸면 대체 경로를 한 벌 더 유지하게 되고, 그러면 도입해서 얻으려던 단순함이 사라진다.

대안 비교 — 오늘 무엇을 쓰면 되나

선택지를 같은 축에서 늘어놓으면 판단이 쉬워진다.

방식텍스트 품질접근성캔버스 픽셀과 합성오늘 쓸 수 있나

판단 기준은 하나로 좁혀진다. 그 텍스트가 캔버스 픽셀과 섞일 필요가 있는가.

  • 섞일 필요가 없다면 DOM 오버레이가 정답이다. 차트 축 라벨, 툴팁, 범례, 게임 HUD, 지도 정보 패널이 대부분 여기 해당한다. 절대 위치로 얹으면 접근성·선택·찾기·번역이 전부 살아 있고 오늘 모든 브라우저에서 동작한다
  • 섞일 필요가 있을 때만 굽는 쪽을 검토한다. 셰이더를 통과해야 하거나, 3차원 공간에서 원근이 적용되어야 하거나, 캔버스 필터·블렌드 모드를 받아야 하는 경우다
  • 굽기로 정했다면 접근성 대체 경로를 같은 커밋에서 설계한다. 화면 밖 DOM 사본, ARIA 속성, 텍스트 버전 링크. 나중에 붙이겠다는 계획은 대체로 붙지 않는다
  • 대량 항목이 문제라면 캔버스로 넘어가기 전에 가상 스크롤로 DOM 노드 수를 줄이는 접근을 먼저 보라. 캔버스 전환은 되돌리기 어렵다

이 API가 정식화된다고 해서 위 순서가 뒤집히지는 않는다. DOM 오버레이로 충분한 자리에 캔버스를 쓰는 것은 그때도 손해다. 이 기능이 바꾸는 것은 「캔버스에 구울 수밖에 없는 경우」의 품질이지, 캔버스를 써야 할 이유의 범위가 아니다.

확인하지 못한 것

이 글은 공개된 1차 문서에서 확인된 범위까지만 적었다. 다음은 채우지 못한 자리다.

  • 플래그를 켠 빌드에서 실제 보조 기술로 검증한 결과가 없다. 접근성 서술은 explainer 와 크롬 문서가 적어 둔 범위까지다
  • NVDA·JAWS·VoiceOver 등 개별 스크린리더의 실제 낭독 동작 보고를 찾지 못했다
  • 브라우저 확대, 강제 색 모드, 사용자 최소 글꼴 설정이 그려진 결과에 어떻게 반영되는지 답을 찾지 못했다
  • 지원 마일스톤 번호가 출처마다 달라 어느 한쪽을 정답으로 단정하지 않았다
  • 성능 비교 수치는 어떤 1차 문서에서도 확인하지 못했다. 그래서 이 글에는 빨라진다거나 느려진다는 서술이 없다
  • Mozilla·WebKit의 공식 standards position 문서는 찾지 못했다. 표의 「신호 없음」은 블링크 진행 기록에 적힌 상태다
  • 한국어 IME 조합 중 입력이 캔버스 안 폼 요소에서 어떻게 동작하는지 확인하지 못했다. explainer 는 IME 팝업을 되읽기 제외 목록에 넣었을 뿐이다
  • 이 기능이 정식 표준으로 갈지는 알 수 없다. 인큐베이션 단계에서 정리된 제안은 드물지 않다

표현력 대 접근성 — 웹 플랫폼이 이 거래를 다루는 방식

웹은 문서에서 시작했다. 접근성이 초기에 사실상 공짜였던 이유는 콘텐츠가 구조로 표현됐기 때문이다. 기계가 읽을 수 있는 형태가 곧 사람이 보는 형태였다. 표현력을 올리는 기능은 거의 언제나 그 구조를 우회하는 방식으로 도착했다. 플러그인 기반 콘텐츠, <canvas>, WebGL, <div>로 만든 가짜 체크박스까지. 형태는 달라도 거래는 같다. 원하는 모양을 얻는 대신 기계가 읽을 수 있는 구조를 버린다. 그때마다 두 갈래 대응이 나왔다.

  • 구조를 따로 유지하라고 요구하기 — canvas 대체 콘텐츠, ARIA 속성이 여기 속한다
  • 플랫폼이 구조를 자동으로 붙이는 기능을 추가하기 — 접근성 정보를 이미 갖춘 네이티브 요소를 원하는 모양으로 꾸밀 수 있게 하는 방향

첫 번째는 잘 작동하지 않는다. canvas 대체 콘텐츠가 명세에 있는데도 실무에서 거의 쓰이지 않는 이유가 그것이고, ARIA 속성이 실제 상태와 어긋난 컴포넌트가 흔한 이유도 같다.

이 제안이 눈에 띄는 이유가 여기 있다. 두 번째 갈래를 택했다. 그리는 대상과 접근성 트리에 노출되는 대상을 같은 요소로 묶어 갈라질 자리를 구조적으로 줄인다. 물론 완전하지는 않다. 변환 되먹임을 빠뜨리면 여전히 어긋나고 프라이버시 제약과 스크롤 처리 같은 구멍은 남는다. 그래도 기본값이 「어긋남」인 것과 「일치」인 것의 차이는 크다. 긴장 자체는 사라지지 않겠지만, 그것을 개별 개발자의 성실함에 맡길지 플랫폼이 떠안을지는 선택할 수 있는 문제다.

결론: 지금 할 일과 하지 말 일

이 기능은 캔버스 개발의 오래된 고통을 정면으로 겨냥한다. 브라우저의 레이아웃 엔진을 캔버스 안으로 들여오고, 대체 콘텐츠를 손으로 유지하던 이중 구조를 없애려는 시도다. 방향은 옳아 보이지만 지금은 한 엔진의 플래그 뒤에 있는 제안이다. 그래서 할 일은 셋이다.

  • 지금 캔버스로 그리고 있는 텍스트를 세어 보라. 그중 DOM 오버레이로 옮길 수 있는 것이 몇 개인지. 대개 대부분이고, 그건 이 API를 기다릴 필요가 없는 개선이다
  • 캔버스 UI가 있다면 오늘 스크린리더를 켜 보라. 무엇이 읽히지 않는지 확인하는 데 30분이면 된다. 그 결과가 이 기능을 도입할지 판단하는 근거가 된다
  • 플래그 빌드에서 데모를 열어 감각만 잡아 두라. 도입이 아니라 관찰이다. 이름과 동작이 바뀔 수 있다는 전제로 본다

하지 말 일도 분명하다. 프로덕션 적용은 아직이다. 그리고 이 API가 오면 접근성이 해결된다는 전제로 계획을 세우지 마라. 자동으로 붙는 것은 렌더링과 대체 콘텐츠의 일치이지, 확대·강제 색·스크롤·보조 기술 동작까지 포함한 사용성 전체가 아니다.

캔버스에 글자를 그리는 일이 더 쉬워지더라도, 그 글자를 읽어야 하는 사람이 읽을 수 있는지는 계속 확인해야 할 일로 남는다. 좋은 API는 그 확인을 쉽게 만들어 줄 뿐, 대신해 주지는 않는다.
