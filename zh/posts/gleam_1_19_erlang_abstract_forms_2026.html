起因 — 「不再编译为Erlang源码」所指的范围

Gleam官方网站于2026年10月5日以「Gleam doesn't compile to Erlang source anymore」为题发布了v1.19.0的发布文章，GeekNews在10月6日作了介绍。标题所说的变化可以归结为一句话：以前的Gleam生成Erlang源代码，现在生成Erlang abstract forms。据发布文章，Giacomo Cavalieri在过去几个月里重写了整个Erlang代码生成器，新生成器的设计和输出格式都不同。

只看标题容易把范围想得过宽。变的是Erlang目标代码生成器产出的格式。Gleam同时面向Erlang虚拟机和JavaScript运行时，JavaScript一侧的变更在发布文章里另有小节。Erlang编译器也没有被拿掉：发布文章把这次变化描述为，从把源代码交给Erlang编译器，改为把中间表示交给Erlang编译器。字节码仍由Erlang编译器生成。

因此要看的是一个编译器把什么交给另一个编译器。交付物从供人阅读的文本换成树形的中间表示后，接收方的工作、错误位置的基准和对待生成物的方式都会跟着变。Gleam在BEAM之上把类型边界移到了哪里是另一条轴线，见在BEAM之上加载静态类型这一选择。

abstract forms是什么 — Erlang文档中的定义

发布文章把abstract forms介绍为Erlang编译器使用的中间表示：它是一棵表示Erlang语法、带有元数据的树，通常由运行Erlang的分词器和解析器得到。Erlang/OTP文档把它称为abstract format，v1.19的changelog也用Erlang Abstract Format这个名字记录这项变更。

Erlang文档「The Abstract Format」（OTP 29.1.1）写明的内容如下。

  • 定义。它是把Erlang程序的解析树表示为Erlang项（term）的标准表示。
  • 模块的形状。模块声明是一串form，每个form要么是函数声明，要么是属性。属性-module(Mod)表示为{attribute,ANNO,module,Mod}，函数声明表示为{function,ANNO,Name,Arity,[Rep(Fc_1), ...,Rep(Fc_k)]}。
  • ANNO。在这些表示中随处出现的ANNO是注解（annotation），在它所包含的若干信息中，有该语法结构在源文件中出现的行号。细节见erl_anno模块的文档。
  • 处理它的函数。compile:forms/1,2以及epp、erl_eval、erl_lint、erl_parse、erl_pp、io这些模块中的函数处理这种解析树。它也用作解析变换（parse transform）的输入和输出。
  • 与调试信息的关系。指定编译选项debug_info之后，abstract code会出于调试目的保存在BEAM文件里。

erl_anno的文档列出了注解可以包含的项目：记号起始的列（column）、合并行与列的位置（location）、记号的文本（text）和由此导出的行（line）；此外还有文件名（file）、标记代码由编译器生成的布尔值（generated）等。文档写明，Erlang编译器不会对标记为generated的代码发出警告。把发布文章说的位置元数据与ANNO对照来读，后文的错误位置变化可以理解为：往这一栏填哪一份源码的行号。

发布文章还补充了一点：abstract forms有一种基于Erlang external term format的二进制编码，用它可以直接加载生成的代码，跳过Erlang编译器的前半部分。按Erlang文档，external term format主要用于Erlang的分布式机制，把项转成这种格式的内置函数是erlang:term_to_binary/1,2，转回来的是erlang:binary_to_term/1。文档写明所有Erlang项都有外部表示；abstract format是由Erlang项构成的解析树，因此可以这样编码。

前后的编译流水线 — 谁生成什么，又跳过了什么

按发布文章和changelog写明的内容把前后并排，就是下面这张表。左边一列是基准测试的比较基线v1.17.0。发布文章说明重写的第一阶段已在v1.18.0中发布，所以前后对比用v1.17.0和v1.19.0。

阶段v1.17.0（输出Erlang源码）v1.19.0（输出abstract forms）

表中可以读出三点。第一，省掉的是Erlang编译器的前一段，不是整个编译器。发布文章提到的Erlang编译器数十年间实现的优化，仍由Erlang编译器负责。第二，跳过的是把源码文本还原成树的工作。展开说，Gleam编译器把程序写成文本、Erlang一侧再读回来重建成树的这个来回没有了。第三，位置信息的基准变了。Erlang的compile模块文档指出，交付Erlang源代码这条路径的主要缺点，是很难或者无法把Erlang代码的每一行对应回原始源文件中的相应行。

发布文章为新的代码生成器列举了四项好处。

  • 编译器的性能有所提高，运行在Erlang上的Gleam项目的构建时间明显缩短。
  • 运行时可以使用的位置元数据对应的是原始Gleam源码，而不是编译器以前生成的Erlang源码。
  • Gleam编译器的代码质量有所提高。Erlang代码生成器属于代码库中最老、最稳定的部分，并没有造成什么问题，但文章的说法是它不符合项目现在的标准和约定。
  • 以后不必再听到有人把「转译器」这个词当作贬义来用。这一项带有脚注。

第四项的脚注与这里的话题有关。发布文章把转译器定义为输出源代码这类人类可读格式的编译器，并写道，编译到人类可读的格式并不会让编译器更容易实现。后面接着的一句是：如果希望输出排版整齐，这甚至可能比使用二进制格式更难。

Erlang文档为其他语言实现者列出的四条路径

这组选项并非Gleam独有。Erlang的compile模块文档有一节叫「Recommendations for Language Implementors」。它的前提是：运行在Erlang运行时系统上的其他语言的编译器，一般产出一个文件或二进制再交给Erlang编译器；随后列出用有文档说明的功能做到这一点的四种方式。

交付的东西文档的说法文档写明的编译方式
Erlang源代码（.erl）最直接、可移植性最好的方式。主要缺点是很难或者无法把Erlang代码的每一行对应回原始源文件中的相应行compile:file/2或erlc <FILE>.erl

Core Erlang虽然有规范，但某些细节通过primop表达式交由实现决定，而primop可能在任何一个主版本中不经通知地被增加、删除或修改。直接生成时，可能构造出Core-to-BEAM后端从未遇到过的代码，无法保证最终的BEAM代码是安全的from_core选项。文件的确切格式没有文档说明，并且可能在不同版本之间变化

这一节的结论只有一句：建议使用abstract format或Erlang源代码。Gleam等于从两个推荐方案中的一个换到了另一个。文档指出的源代码路径的主要缺点，即行的对应问题，与发布文章列为好处的位置元数据正好对上。

同一份文档的选项说明里，有两条走这条路径的实现者应当了解的说明。一条是from_abstr条目的提示：这类项的格式可能在版本之间变化。另一条是no_lint选项。它跳过检查错误和警告的那一遍处理，只能与from_abstr一起使用；文档解释说，它主要面向已自行完成检查、能保证代码正确性的其他语言实现。该选项附有警告：使用后无法保证编译器的输出正确且可安全使用，正确性的责任在于生成abstract format的代码或人。

构建时间 — 数字与测量条件

给出数字之前，发布文章先加了一条说明：基准测试总是人为构造的，讲不出完整的情况。测量用的是基于José Valim的langcompilebench的基准，发布文章和仓库README写明的条件如下。

  • 被测项目。100个模块，每个模块100个函数，每个函数返回一个hello world字符串。
  • 构建类型。不使用任何缓存、从头开始的完整构建。
  • 统计方式。README写明取的是11次运行的中位数。
  • 比较的版本。Gleam v1.17.0与v1.19.0。由于重写的第一阶段已进入v1.18.0，所以比较时跳过了一个版本。
  • 工具版本。README的版本清单里列有Erlang 29.0.6、Elixir 1.20.4-otp-29、Rebar 3.27.0等。

Erlang目标两个数值相差0.092秒，相对v1.17.0约缩短21%（计算）。发布文章正文没有用文字写出这些数字，只给了柱状图；表中数值来自它所链接的基准仓库README。README的表里还有Go、Java、Rust、C#、Elm、TypeScript几行。发布文章解释说，这种比较是为了让人对照自己熟悉的语言，对Gleam的编译速度有个大致感觉，并再次写明，仅凭这一个基准不足以对这些语言下确定的结论。

读这些数字要连同条件带来的局限一起看。如发布文章所写，这种形状的项目便于在多种语言里复现，但各语言只有一小部分特性被编译到。真实项目的代码多样得多，不同特性在不同语言里的编译成本也不同。另外Gleam的编译是增量式的，发布文章写道，通常开发时不会编译整个项目，所以会快得多。完整构建上测到的缩短幅度与反复编辑、构建时的幅度是否相同，这些资料没有给出依据。changelog没有数字，只写了编译到Erlang时典型Gleam包的编译时间缩短了。

错误位置 — 行号指向原始Gleam源码意味着什么

第二项好处是运行维护中才显现的变化。据发布文章，运行时可用的位置元数据现在对应原始Gleam源码。举的例子是BEAM崩溃报告和堆栈跟踪里的行号：此前可能不准确，只能指向最近的函数，现在是准确的（原文用词是perfectly accurate）。changelog对同一件事的写法是：这种格式支持把生成的每一行Erlang对应回原始Gleam源文件中的相应行。

Erlang文档中与这一变化相关的条目有三个。

  • ANNO。它出现在abstract format每个语法结构的表示里，带有源文件中的行号。
  • {source,FileName}选项。覆盖在module_info(compile)和堆栈跟踪中显示的源文件名。
  • {error_location,line | column}选项。取值为column时，调试信息中包含列信息。按照文档，默认值是column，从Erlang/OTP 24.0起支持。

补一句解读：行号从函数一级对齐到行一级，改变的是故障处理的第一步。堆栈跟踪所指的行就是失败位置，这个前提成立，才能从日志直接走到代码。只有函数对得上时，还得由人再缩小范围，找出函数里是哪个表达式失败。

关于调试器，发布文章写得比较保留：这些元数据也许能让edb这类调试器完整支持Gleam，但团队自己没有做这方面的工作。edb仓库的README把edb介绍为面向Erlang的单步调试器，写明需要OTP 29或更高版本，并说明项目需要debug_info、beam_debug_info、beam_debug_stack三个编译选项。发布文章那句话讲的是可能性，不是说v1.19.0已经能用edb调试Gleam代码。

不直接生成BEAM字节码的理由

既然已经下沉到中间表示，接着的问题是：何不绕过Erlang编译器直接生成BEAM字节码？发布文章自己提出了这个问题：能否做出胜过Erlang编译器的字节码生成器，能否利用Gleam的类型信息生成更优化的代码？回答是：这些好处有可能得到，但项目不太可能真的做到。理由如下。

  • 字节码不是固定的。发布文章写道，与Erlang源码和abstract forms不同，BEAM字节码并非固定不变。虚拟机的每个新版本都可能让字节码演进，加入新的功能，有时还会去掉已经变得多余的功能。
  • 跟进的成本没有尽头。项目需要一直跟上这种演进，与Erlang的维护者紧密协作，为即将到来的变更做好准备，并在虚拟机发布新版本时备好相应的Gleam新版本。
  • 已有的优化需要重做。把Erlang编译器数十年间实现的优化全部重现出来，即使有Gleam能力更强的静态分析可以借助，也需要相当大的投入。
  • 财力有限。发布文章写道，Gleam是一个靠赞助支撑的社区项目，与由企业或学术机构支持的语言相比，资金只有一小部分。

发布文章的结论是，编译到Erlang abstract forms是今天的Gleam成本与收益相称的位置（原文用词是cost-benefit sweet-spot）。它举出做了同样选择的Elixir：Elixir也经由abstract forms编译到Erlang。

这个判断与上一节的Erlang文档对象不同，但所举理由的方向一致。文档强烈不建议的是把BEAM assembly code交给Erlang编译器的路径（from_asm），发布文章设想的则是绕过Erlang编译器、直接生成字节码的做法。文档给出的理由是需要持续维护，且每个主版本都会引入新指令。不过对「固定」这个说法，两份文档的轻重不同：发布文章把abstract forms与Erlang源码一起放在固定的一边，compile文档的from_abstr条目则写明这类项的格式可能在版本之间变化。补一句解读：以中间表示为目标，比以源码文本为目标离对方编译器的内部近了一步，OTP发布说明里要跟着读的条目也相应多一些。

使用者能看到的变化与升级后要看的地方

从使用者的角度把前面的内容归拢一下：变的是构建时间和错误位置，不变的是由谁生成实际运行的代码。BEAM字节码仍由Erlang编译器生成。

崩溃报告与堆栈跟踪行号与原始Gleam源码中的行一致发布文章、changelog

升级后值得自己看一看的有下面几项。它们是由发布文章和changelog的说法推出的检查项，是否适用因项目而异。

  • 自己项目的构建时间。基准是含一万个hello world函数（100×100，计算）的合成项目。升级前后分别记下清空缓存的完整构建和平时增量构建的用时，就能知道自己代码上的幅度。
  • 堆栈跟踪里的行。用一段故意让它失败的代码生成崩溃报告，看行号是否与Gleam源码中的相应行一致。
  • 依赖生成物的工具。如果有脚本读取或加工构建目录里的生成文件，就看升级后同样的文件是否还以同样的形状存在。这是代码生成器输出格式变了的版本。
  • 与Mix和rebar3的衔接。如果是调用compile-package的一方，就看一下标志名。按照changelog，rc1中的--src-only在rc2中改名为--no-dev。
  • 新出现的警告。changelog写道，编译器现在能在相互重叠的字符串模式中识别出更多不可达分支，并补充说以前无警告编译通过的代码现在可能发出这条警告。case里接收整个列表的[..x]模式也新增了警告，并写明这种语法可能在将来的主版本中移除。
  • 与OTP 29的命名冲突。生成Erlang类型定义时，名为Record的类型会被改名为record_。changelog写明，这是为了不覆盖OTP 29中引入的Erlang内置record类型。

同一版本的其他变更 — JavaScript目标仍然输出源码

在Erlang目标转向中间表示的同一版本里，JavaScript目标打磨的是所生成的源代码本身。发布文章的例子显示出两种格式的差别。Gleam的流程控制靠case表达式的模式匹配，它被编译成嵌套的if语句。John Downey改进了这一过程，把嵌套的if合并为一个条件并减少中间变量，生成更扁平的代码。对于下面这段Gleam代码，

pub fn go(x) {
                      case x {
                        Wibble(1, 2) -> 1
                        _ -> 2
                      }
                    }

以前会生成下面的JavaScript。发布文章在脚注中写明，为了便于阅读，代码稍作了编辑，但与这项改进有关的部分没有改动。

export function go(x) {
                      if (isWibble(x)) {
                        let $ = x[0];
                        if ($ === 1) {
                          let $1 = x[1];
                          if ($1 === 2) {
                            return 1;
                          } else {
                            return 2;
                          }
                        } else {
                          return 2;
                        }
                      } else {
                        return 2;
                      }
                    }

v1.19.0生成的是下面这段。

export function go(x) {
                      if (isWibble(x) && x[0] === 1 && x[1] === 2) {
                        return 1;
                      } else {
                        return 2;
                      }
                    }

发布文章写道，这一变化对最小化和压缩后的打包体积几乎没有影响，但生成的代码里需要JavaScript引擎优化的分支更少。生成物是人可读的文本，所以改进可以这样用前后两段代码并排展示。此外，发布文章和changelog列出的变更如下。

  • 列表字面量。在JavaScript目标上，较短的列表字面量不再先构造数组再交给转换函数，而是生成为不经过数组转换的、更直接的代码。较长的列表没有记录到改进，所以沿用原来的方式。
  • TypeScript声明。用于判断自定义类型变体的函数新增了重载，以往因类型参数被泛化为unknown而丢失的信息，在可能的情况下得以保留。
  • 其他构建工具。编译到BEAM时，虚拟机所要求的.app资源文件改由gleam生成。export package-information和export package-interface现在可以输出到标准输出。发布文章说明，这些改动的意图是让Elixir的Mix和Erlang的rebar3支持Gleam。
  • 语言服务器。对于字段和参数的标签，支持跳转到定义、查找引用和重命名。
  • 在浏览器里格式化。编译器的WebAssembly构建新增了format_source函数。
  • 错误信息。针对git合并冲突标记、记录更新语法顺序写错、Gleam中不存在的+=这类运算符，以及在模式匹配中使用|等情况，新增了专门的提示信息。
  • 构建缓存。按照changelog，构建工具现在用更紧凑的二进制格式保存构建缓存，缓存文件明显变小。

关于Mix的支持，发布文章的措辞只到希望不久能看到的程度，这个版本不意味着支持已经完成。

未能确认的内容

  • 测量所用的机器。运行基准的硬件和操作系统，发布文章和README都没有写。0.434秒和0.342秒应看作相同条件下的相对比较，而非数值本身。
  • 缩短部分的构成。缩短的0.092秒里，跳过Erlang一侧分词与解析的份额和Gleam代码生成器自身变快的份额各是多少，资料中没有。changelog里同一版本还有一条改写Gleam编译器词法分析器的条目，因素不止一个。
  • v1.18.0包含的范围。发布文章只写了重写的第一阶段已在v1.18.0中发布，没有写明这一阶段包含什么。
  • Erlang源码输出是否还保留。是否仍然输出生成的Erlang源码以供查看，gleam export erlang-shipment的内容有了怎样的变化，在发布文章和changelog中都没有找到说明。
  • 调用Erlang编译器的方式。Gleam是通过compile:forms/2传递abstract forms，还是通过.abstr文件加from_abstr传递，是否使用no_lint，所依据的资料中都没有。Gleam编译器的源代码不在所依据的资料之内。
  • 在真实项目上的幅度。对于合成基准之外的项目，构建时间能缩短多少，没有找到公开的测量。
  • abstract format在版本之间的稳定性。发布文章说的fixed and unchanging，与Erlang文档说的can change between releases，哪一种适用于Gleam所走的路径，仅凭这两份文档无法判定。
  • 列信息。堆栈跟踪里除了行之外，列是否也与Gleam源码一致，发布文章没有说明。
