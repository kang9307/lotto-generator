Slumber - レシピ駆動のターミナルHTTP/RESTクライアント、Postman代替 2026

リクエストをYAMLで定義してターミナルで実行する、軽量でGit親和のAPIクライアント

2026-06-11 IT・技術

はじめに：APIと向き合うもう一つの方法

APIを呼ぶツールはすでに数多くあります。重量級のGUIプラットフォームであるPostmanとInsomnia、一行コマンドの王であるcurl、人に優しい出力で愛されるHTTPie。ところが2026年6月、開発者コミュニティでもう一つの選択肢が話題になりました。Slumberです。Rustで書かれたターミナルベースのHTTP/RESTクライアントで、リクエストをYAMLレシピ（recipe）として定義する点が最大の特徴です。

「もう一つのHTTPクライアントがなぜ必要なのか」という問いは正当です。本記事はSlumberが埋める隙間がどこにあるのかを落ち着いて見ていきます。結論を先に言えば、Slumberの核心的価値は「速度」や「美しい出力」ではなく、リクエストをコードのように扱うワークフローにあります。GUIに閉じ込められず、かといって毎回長いcurlコマンドを手で組み立てもしない、その中間地帯を狙うツールです。公式の紹介によれば、Slumberの目標は「使いやすく、設定可能で、共有可能な」HTTPクライアントであることです。

1. ターミナルHTTPクライアントとは何か

本論の前に用語を整理します。ターミナルHTTPクライアントとは、マウスでクリックするグラフィカルな画面の代わりに、キーボードとテキストでHTTPリクエストを作り送るツールを指します。大きく二つの系統があります。

  • CLI（コマンドラインインターフェース）： curl https://api.example.com/users のように一行コマンドでリクエストを送ります。スクリプト・自動化に強いです。
  • TUI（ターミナルユーザーインターフェース）： ターミナル内にメニュー・パネル・一覧のある対話的な画面を表示します。GUIの利便性とターミナルの軽さを折衷します。

Slumberが興味深いのは、この両方を提供する点です。対話的にリクエストを探索しレスポンスを見るときはTUIを、スクリプトやCIで自動的に呼び出すときはCLIを使います。さらにPythonパッケージとしても提供され、コード内から直接呼び出すこともできます。一つのコレクション（リクエストの集まり）を三つのインターフェースが共有するという設計が、Slumberのアイデンティティです。

2. Slumberの中核概念 - コレクション、レシピ、プロファイル

Slumberを理解する最短の道は、三つの概念をつかむことです。

  • コレクション（Collection）： 通常は一つの slumber.yml ファイルに収まる、リクエストレシピの束です。プロジェクトのリポジトリに一緒にコミットする単位です。
  • レシピ（Recipe）： 実行する個々のリクエストのテンプレートです。メソッド・URL・ヘッダー・ボディ・クエリを定義します。「ユーザー一覧取得」「注文作成」といったリクエスト一つ一つがレシピです。
  • プロファイル（Profile）： 環境ごとの変数集合です。ローカル・ステージング・本番のように、ホストやトークンが異なる環境を簡単に切り替えられます。

この三つが噛み合うと、一組のレシピを書いておき、プロファイルだけを切り替えて複数の環境で同じリクエストを再利用できます。GUIツールで環境変数を画面で管理していた作業を、Slumberはテキストファイルで処理します。

3. 最初のコレクションを作る - slumber.yml の例

百聞は一見にしかず。公式ドキュメントの例をもとにしたシンプルなコレクションを見てみましょう。架空の「魚」APIを扱うコレクションです。

# slumber.yml
profiles:
  local:
    data:
      host: http://localhost:5000
  production:
    data:
      host: https://myfishes.fish

requests:
  list_fish:
    method: GET
    url: "{{ host }}/fishes"
    query:
      big: true

  create_fish:
    method: POST
    url: "{{ host }}/fishes"
    body:
      type: json
      data: { "kind": "barracuda", "name": "Jimmy" }

読めば意図は明確です。profiles の下の local と production がそれぞれ host 変数を異なる値で定義します。requests の下のレシピは {{ host }} テンプレートでその変数を参照します。プロファイルを切り替えるだけで、同じ list_fish リクエストがローカルと本番を行き来します。ヘッダーが長く引用符のエスケープが煩雑なcurl一行と比べると、構造が一目で頭に入ります。

4. TUIとCLI - 二つの使い方

コレクションを作ったら実行する番です。Slumberは二つの方式を提供します。

4.1 TUI：対話的探索

コレクションのあるディレクトリで slumber を実行するとTUIが立ち上がります。左にレシピ一覧、中央にリクエスト詳細、右にレスポンスが配置されるような対話画面で、キーボードでリクエストを選んで送り、レスポンスをその場で確認します。レスポンスの探索には JSONPath セレクターが内蔵されており、jq のように大きなJSONレスポンスから欲しいフィールドだけを選んで見られます。

4.2 CLI：スクリプトと自動化

対話が不要なときはCLIから直接実行します。たとえば特定のレシピを非対話的に送る形です。

# 新しいコレクションを生成
slumber new

# TUIを起動（カレントディレクトリのslumber.ymlを使用）
slumber

# 特定のレシピをCLIで実行（プロファイル指定）
slumber request list_fish --profile production

CLIモードのおかげで、SlumberリクエストをシェルスクリプトやCIステップに組み込めます。レスポンスを標準出力で受け取り別のコマンドにパイプする、典型的なUnix流の組み合わせが可能です。（コマンド名・オプションの正確な形はバージョンによって異なる場合があるため、slumber --help で確認してください。）

5. 動的リクエスト - テンプレート、ファイル、シェル、過去のレスポンス

Slumberが単なる「静的リクエストの保管庫」を超えるのが、動的リクエスト構成です。紹介によれば、Slumberは次のソースからリクエストを動的に組み立てます。

  • テンプレート変数： プロファイルのデータを {{ host }} のように差し込みます。
  • ファイル： 外部ファイルの内容をボディやヘッダーとして読み込みます。大きなペイロードや証明書のような値に便利です。
  • シェルコマンド： シェルコマンドの出力を値として使います。たとえばトークン生成器を呼び、その結果をヘッダーに入れます。
  • 過去のレスポンス： 先のリクエストのレスポンスから値を取り出し、次のリクエストに渡します。ログイン→トークン取得→認証付きリクエストのようなチェーンが可能です。
  • プロンプト： 実行時にユーザーへ値を尋ねます。

この「過去のレスポンスから値を引き出す」機能が実務で特に強力です。認証が必要なAPIを扱うとき、ログインリクエストのレスポンスからトークンを抽出し、後続リクエストのヘッダーに自動で入れる流れをレシピとして固められます。Postmanの「環境変数＋テストスクリプト」の組み合わせでやっていた作業を、Slumberは宣言的な設定で表現します。

6. Git親和 - 設定をコードとして扱うということ

Slumberの哲学を一語で要約すると「ソース優先（source-first）の設定」です。すべての設定とデータがローカルのプレーンテキストYAMLとして存在するので、自然に次の利点が伴います。

  • バージョン管理： slumber.yml をGitにコミットすれば、APIリクエストの変更履歴がコード履歴とともに残ります。誰がいつエンドポイントを変えたかを git blame で追えます。
  • コードレビュー： 新しいエンドポイントの追加やリクエストの変更を、PRのdiffとしてレビューできます。GUIのクリックでは不可能です。
  • 共有： リポジトリをクローンした同僚は、別途のアカウントやクラウド同期なしに同じコレクションを即座に使えます。
  • 再利用： プロジェクト間でレシピをコピー・参照して標準リクエストを再活用します。
APIクライアントの設定がクラウドアカウントの裏ではなくリポジトリの中にあるとき、その設定はようやくコードベースの一部になる。

この点が、重いGUIツールを使う際に感じる微妙な不便さ — 設定がツールの中に閉じ込められチームと同期されない問題 — を正面から解決します。

7. 他形式からのインポート - Insomnia、OpenAPIなど

すでに別のツールで作ったコレクションがあるなら、一から作り直す必要はありません。紹介によれば、Slumberは複数の外部形式のインポートに対応しています。

  • Insomnia コレクション
  • OpenAPI 仕様
  • VSCode .rest ファイル
  • JetBrains .http コレクション

特にOpenAPIインポートは意味が大きいです。よく定義されたAPI仕様があれば、それを出発点にSlumberレシピを生成でき、既存の資産を捨てずに新しいワークフローへ移せます。

8. Postman・Insomnia・curl・HTTPieとの比較

いよいよ本格的な比較です。Slumberの位置を他のツールの間で測ってみましょう。

ツール インターフェース 設定方式 強み 弱み
Slumber TUI + CLI YAMLファイル 軽量、Git親和、環境切替 比較的新しい、GUI協業なし
Postman GUI クラウド/アカウント 豊富な協業・テスト・監視 重い、アカウント依存、バージョン管理が弱い
Insomnia GUI GUI/ファイル すっきりしたUI、プラグイン 依然GUI中心
curl CLI コマンド引数 どこにでもある、即席呼び出し 繰り返し・構造化には面倒
HTTPie CLI コマンド引数 人に読みやすい出力 コレクション・環境管理が弱い

表を見ると、競合は一対一ではないとわかります。Slumberはcurlを完全に置き換えません。即席で一度送って終わるリクエストには、依然curlが速いです。逆にPostmanのチーム協業・監視・モックサーバーのようなプラットフォーム機能も置き換えません。Slumberが正確に狙う場所は、「複数のエンドポイントを繰り返し扱うが、GUIプラットフォームの重さは背負いたくない」開発者の日常ワークフローです。

9. curlコマンドとレシピの関係

興味深いのは、Slumberレシピとcurlコマンドが対立ではなく補完の関係にある点です。同じリクエストを二つの方式で書くと違いが鮮明です。

# curl一行（即席呼び出しに良い）
curl -X POST https://myfishes.fish/fishes \
  -H "Content-Type: application/json" \
  -d '{"kind":"barracuda","name":"Jimmy"}'

上のcurlコマンドは速いですが、ヘッダーが増え環境が複数になった瞬間、手で管理するのが面倒になります。同じリクエストをSlumberレシピとして固めておけば、環境切替と再実行がすっきりします。実際、当サイトのcurlコマンドビルダーのようなツールで一回限りのリクエストを素早く組み立てた後、繰り返し使うリクエストだけをSlumberコレクションに移して整理する方法がよく合います。即席の組み立てはビルダーとcurlに、繰り返し・構造化はSlumberに分けるのです。

10. 活用シナリオ - APIテスト、CI、ドキュメント化

Slumberが実際に輝く場面を整理します。

10.1 日常のAPIデバッグ

開発中のAPIを手で叩くとき、レシピで定義されたリクエストをTUIで選んで送り、レスポンスをJSONPathで確認します。curlより親切で、Postmanより軽いです。

10.2 CI回帰・スモークテスト

同じYAMLコレクションをCIでCLIから実行し、デプロイ後に主要エンドポイントが生きているか確認するスモークテストを回します。開発時に使ったリクエスト定義をそのまま検証に再利用できる点が大きな利点です。

10.3 生きたAPIドキュメント

slumber.yml 自体が「このAPIをどう呼ぶか」についての実行可能なドキュメントになります。READMEの固定されたcurl例と違い、リポジトリのレシピは実際に実行されるので古くなりにくいです。

10.4 スクリプト統合

シェルスクリプトから slumber request を呼び、リクエスト結果を後続処理に渡します。動的リクエスト機能と組み合わせれば、トークン発行・チェーンのような複雑な流れもスクリプトで自動化できます。

11. 限界と注意点

バランスのため、影もはっきり指摘します。Slumberは万能ではありません。

  • 成熟度： 公式の案内によれば、Slumberは比較的新しいツールで、機能はまだ完全に揃った段階ではありません。コマンド・設定の細部がバージョンによって変わることがあるので、公式ドキュメントを基準にすべきです。
  • GUI協業の不在： Postman式のチームワークスペース、モックサーバー、監視、視覚的テストランナーはありません。非開発職と協業したり非技術の関係者へ共有する必要があるなら、GUIツールが適します。
  • 学習曲線： YAMLとターミナルに不慣れなら、初期の入り口がGUIより急かもしれません。ただし一度習得すれば繰り返し作業で回収できます。
  • 適した場所： 即席の一行呼び出しはcurl/HTTPieが、巨大な協業プラットフォームはPostmanが優れます。Slumberはその間、「コードのように扱う繰り返しのAPIワークフロー」に最適です。

12. 結論 + すぐ試せる3つ

Slumberを一文で要約するとこうです。「リクエストをYAMLレシピで定義してGitで管理し、TUIとCLIで実行する、軽量で共有可能なターミナルHTTPクライアント」です。豊富なGUI協業が必要ならPostmanが、即席の一行ならcurlが優れますが、その二つの間で繰り返しのAPIワークフローをコードのように扱いたいなら、Slumberは非常に合理的な選択です。

すぐに試せる3つで締めくくります。

  1. よく使うリクエスト3つをレシピに移す。 毎回手で打っていたcurlコマンドのうち繰り返し度の高い3つを選び、slumber.yml に書いてみてください。小さなコレクション一つがワークフローの体感を変えます。
  2. 環境をプロファイルで分ける。 ローカル・ステージング・本番のホストをプロファイルで分けておけば、環境を取り違えて誤ったサーバーにリクエストを飛ばすミスを構造的に防げます。
  3. コレクションをリポジトリにコミットする。 slumber.yml をコードとともにコミットしておけば、APIの呼び方がそのまま生きたドキュメントになり、同僚はクローンだけで同じリクエストを即座に再現します。

最後に強調したいメッセージはこれです。良いツールは新しい機能を足すより、散らばった作業を正しい場所へ移してくれます。 SlumberはGUIに閉じ込められていたAPIリクエストの設定を、リポジトリへ、つまりコードの場所へ戻します。ターミナルを楽しみ設定をコードのように扱いたい開発者なら、一度真剣に試す価値があります。
