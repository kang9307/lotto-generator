Lookaround Only Looks - Solving Regex Problems With Zero Width

What becomes possible precisely because it never enters the match - stacking conditions, replacing only at the boundary, counting overlapping matches, and the place where Korean breaks first

2026-08-11 Dev & Infra

Introduction: The Condition Has to Be Checked, but It Must Not Land in the Result

You need only the log lines that contain ERROR, minus the ones that contain timeout. So you join two grep calls with a pipe. Then, from those lines, all you actually want is the value after host=. Another pipe, and sed chops off the front. By the time the command has four pipes in it, reading it again tells you nothing about what it does.

In substitution the problem is even more blatant. password=hunter2 has to become password=***. There is no way to isolate hunter2 without matching password= along with it, and the moment you do match it, the substitution wipes it out too. So you grab it with a capture group and paste it back with $1. With one key that is bearable; with three keys you start counting group numbers.

The two situations share a shape. There is a part that is needed as a condition but unwanted in the result. Lookaround exists for exactly this point. It inspects a condition while keeping it out of the match and leaving the position where the next match starts untouched. That property is called zero width.

Most explanations introduce four symbols at this point and stop. Yet the part that earns its keep in real work is not the symbols; it is the consequences that follow from the width being zero. You can stack any number of conditions at the same position, you can change a value without disturbing its boundaries, and you can count matches that overlap one another. This article spends its pages on that side.

Environment. The output below was produced on Windows 10 Pro with Node.js v22.16.0, Python 3.13.3 and 3.11.9, Perl 5.38.2, and GNU grep 3.0. Patterns containing Hangul lose their escaping when they are passed as shell arguments, so every one of them was saved into a script file and executed from there.

Scope. The wider problem of syntax diverging between engines is covered in Regex That Works Everywhere. Here only the single lookbehind point gets a brief mention. The traps of Korean regex belong to The Korean Regex Trap, which is their home ground; this article looks only at where lookaround as a tool spins its wheels in Korean.

1. Zero Width - It Inspects but Does Not Consume

Put into words it sounds abstract, so measure the length instead.

A1 match = "foo" | length = 3 | index = 0
A2 lastIndex after exec(g): 3
A3 replace = Xbar
A4 without lookahead = X
A5 consuming = "foobar"

The pattern is /foo(?=bar)/ and the input is foobar. Even though the engine definitely checked whether bar follows, the matched string is the three characters foo. What matters more is lastIndex. Had it consumed, the value would be 6; it is 3. That means the cursor is parked in front of bar, and the next match restarts from there.

That is why the replacement result is Xbar (A3). The bar used as a condition stays in the original text. Run the same replacement with the consuming pattern /foobar/ and only X remains (A4). You do not need a capture group to resurrect the part you used as a condition - that is the first practical payoff.

Zero width is meant literally. A pattern made of nothing but lookaround matches the empty string.

C1 split by zero-width = [ 'one', 'Two', 'Three' ]
C2 empty match array = [ '' ]
C3 empty match str  = ""

The matched string of 'abc'.match(/(?=b)/) is an empty string of length 0. It carries position information and no content whatsoever. It is for the same reason that 'oneTwoThree'.split(/(?=[A-Z])/) splits into three pieces without losing a single character. The separator is never consumed, so the capital letters survive intact.

2. The Four Lookarounds and Where Each One Stands

There are four symbols, and only two axes: which way it looks (ahead or behind) and whether the thing must be there or must not be (positive or negative).

SymbolNameDirection it looksSuccess condition
(?=...)Positive lookaheadRight of the current positionThe right side starts with ...
(?!...)Negative lookaheadRight of the current positionThe right side does not start with ...
(?<=...)Positive lookbehindLeft of the current positionThe left side ends with ...
(?<!...)Negative lookbehindLeft of the current positionThe left side does not end with ...

Turn all four loose on the same string and it becomes vivid what each one picks out.

입력: price: 100USD, 200EUR, 300USD

B1 /\d+(?=USD)/g       = [ '100', '300' ]
B2 /\d+(?!\d)(?!USD)/g = [ '200' ]
B3 /(?<=price: )\d+/g   = [ '100' ]

입력: a1 b2 c3
B4 /(?<![ab])\d/g      = [ '3' ]

2.1 Where a Negative Lookahead Gets Broken by Backtracking

Why B2 carries one extra (?!\d) is the heart of this section. Drop it and use only /\d+(?!USD)/g and this is what happens.

입력: 100USD 200EUR

K1 /\d+(?!USD)/g       = [ '10', '200' ]
K2 /\d+(?!\d)(?!USD)/g = [ '200' ]
K4 첫 매치 = "10"

The pattern that was meant to filter out the 100 attached to USD hands back 10 instead. The engine first grabs 100 with \d+, checks (?!USD), fails, and then, rather than giving up, shrinks the amount it consumed while hunting for a way to dodge the condition. Shrink it down to 10 and the right side becomes 0USD, which does not start with USD, so the negative condition sails through.

A negative lookahead is a verdict about that exact position and nothing more; it does not mean that there is no USD after this entire run of digits. So you have to nail down the right edge with (?!\d) and remove every bit of room for \d+ to shrink. When you attach a negative condition, first make sure the boundary of the match is pinned. This is the single most frequent logic error in lookaround.

2.2 Captures Survive Only on the Positive Side

L1 /(?!(\d+))X/ 의 그룹 1 = undefined
L2 /(?=(\d+))\d+/ 의 그룹 1 = 123 | 전체 매치 = 123

A group inside a negative lookahead retains no value. A negative condition succeeds precisely when the inner match fails, so at the moment of success there is nothing left to fill the group with. A group inside a positive lookahead, by contrast, captures normally. The overlapping matches in section 5 stand entirely on this property.

3. Lines That Have A but Not B - Stacking Conditions at the Same Position

This is the log problem from the introduction. Lookaround never moves the position, so chaining several of them means all of them are judged at the same spot. In other words you can pile up as many conditions as you like at the start of a line.

$ grep -P '^(?=.*ERROR)(?!.*timeout)' app.log
2026-08-11 10:00:01 ERROR db connect failed host=db01 retry=1
2026-08-11 10:00:04 ERROR auth rejected user=svc_batch
2026-08-11 10:00:06 ERROR db connect failed host=db02 retry=2

The ERROR upstream timeout line was dropped by the second condition, and the INFO timeout tuning applied line was dropped by the first. Adding one more condition on top is simply a matter of writing one more.

D2 /^(?=.*ERROR)(?!.*timeout)(?=.*(db|auth))/ 매치 = 2건
D3 순서를 바꿔도 같은 결과 = true
D4 소비형 /ERROR.*db/ : 'db ERROR' → false, 'ERROR db' → true

D3 is the point of this section. There is no order dependency between the conditions. A lookahead does not move the cursor, so even after the first condition has been checked the cursor is still sitting at the start of the line. Reorder them and the result is identical, and when you add a condition later you never have to think about where to slot it in.

Try to do the same job with consuming patterns and that freedom disappears (D4). /ERROR.*db/ matches only when ERROR appears before db in the document. If the log format changes and the field order flips, it silently catches nothing at all.

3.1 Filtering and Extracting in One Pass

Combine the stacked conditions with \K and a four-pipe command folds down into one.

$ grep -oP '^(?=.*ERROR)(?!.*timeout).*?host=\K\S+' app.log
db01
db02

$ grep -oP '(?<=retry=)\d+' app.log
1
2

$ grep -oP '\w+(?==)' app.log | sort -u
host pool retry user

The last one pulls out only the key names in front of the equals sign. (?==) looks odd on the page, but it means a position that is followed by an equals sign, and since the equals sign itself is never consumed it does not show up in the output.

4. Matching Only the Boundary in a Substitution

This is a substitution that has to change the value while leaving the key alone. If a lookbehind merely inspects the left boundary, no capture group is needed.

입력: user=admin&password=hunter2&host=db01&token=abc123def

E1 /(?<=password=)[^&]+/g  → '***'
   user=admin&password=***&host=db01&token=abc123def
E2 /(password=)[^&]+/g     → '$1***'
   user=admin&password=***&host=db01&token=abc123def
E3 /(?<=(?:password|token)=)[^&]+/g → '***'
   user=admin&password=***&host=db01&token=***

E1 and E2 produce the same result. Which means a capture group can do this job too, and judged on this example alone it is a matter of taste. The difference opens up at E3. However many keys there are, the replacement string is still the single chunk ***. With the capture approach you have to count group numbers and manage $1 by hand, and the moment you slip one more group in later, the numbers shift and it breaks silently.

4.1 A Substitution That Consumes Nothing at All

The more extreme case is a substitution whose matched string is the empty string. It erases nothing and merely inserts something into a position.

F1 '1234567'      .replace(/\B(?=(\d{3})+(?!\d))/g, ',') = 1,234,567
F2 '999'          .replace(같은 패턴, ',')              = 999
F3 '1000'         .replace(같은 패턴, ',')              = 1,000
F4 '123456789012' .replace(같은 패턴, ',')              = 123,456,789,012

V1 'oneTwoThreeID'  .replace(/(?<=[a-z])(?=[A-Z])/g, '_') = one_two_three_id
V2 'HTTPServerError'.replace(/(?<=[A-Z])(?=[A-Z][a-z])/g, '_') = HTTP_ServerError

Take the thousands-separator pattern apart and it holds three conditions. It must not be a word boundary (\B, which prevents a comma being stuck onto the very front), a group of three digits must follow on the right, and there must be no further digit after that group. All three are zero width, so the matched string is the empty string and the substitution turns into pure insertion.

V2 handles acronyms. Cut HTTPServerError at every capital letter and it degenerates into H_T_T_P_.... Narrow the condition to a position that sits after a capital letter and before a capital letter followed by a lowercase letter, and the acronym stays glued together while the split happens only at genuine word boundaries. A condition like this, which looks left and right at the same time, is hard to express with a consuming pattern.

4.2 Skipping What Has Already Been Processed

입력: see http://a.example and <a href="http://b.example">b</a>
패턴: /(?<!href=")http:\/\/\S+?(?=[\s<])/g → '[LINK]'
결과: see [LINK] and <a href="http://b.example">b</a>

Turning only bare URLs into links while leaving alone the ones already inside a tag is a common requirement. A negative lookbehind demands that the position not sit right after href= plus a quote, and a lookahead pins the right boundary without consuming that character. Had it consumed it, the whitespace or the angle bracket would have vanished from the result.

4.3 Masking

$ echo '카드 4111111111111111 로 결제' | perl -pe 's/\d(?=\d{4})/*/g'
카드 ************1111 로 결제

It turns into an asterisk only a digit that still has four or more digits remaining after it. It counts no positions and computes no lengths. Because the condition is expressed as a position, the very same pattern keeps working whether the card number is sixteen digits long or fourteen.

5. Overlapping Matches - Something Only Zero Width Makes Possible

When a regex engine finds a match it moves the cursor to the end of it. That is exactly why it cannot find overlapping matches.

H1 'AAAA'.match(/AA/g)                    = [ 'AA', 'AA' ]
H2 [...'AAAA'.matchAll(/(?=(AA))/g)]      = [ 'AA', 'AA', 'AA' ]
H3 그 위치                                 = [ 0, 1, 2 ]

H4 'ABABABA'.match(/ABA/g)                = [ 'ABA', 'ABA' ]
H5 [...'ABABABA'.matchAll(/(?=(ABA))/g)]  = 위치 [ 0, 2, 4 ]

AAAA contains three occurrences of AA, at positions 0, 1, and 2. Yet the consuming pattern counts only two. It finds one at 0, the cursor jumps to 2, and position 1 is skipped over.

(?=(AA)) routes around this problem. The outer match is zero width, so the cursor advances one step at a time, and the string you actually want is pulled out of the capture group inside the lookahead. The rule from section 2.2, that captures on the positive side survive, is what gets used here.

5.1 The Infinite Loop of a Zero-Width Match

One trap comes attached to this technique. Drive exec directly and the cursor never advances, so the loop never ends.

const r = /(?=a)/g;
let m;
while ((m = r.exec('aaa')) !== null) {
  // ...
  if (m.index === r.lastIndex) r.lastIndex++;   // 이 줄이 없으면 끝나지 않는다
}
M1 결과 = 3
M2 [...'aaa'.matchAll(/(?=a)/g)].length = 3

When the match length is 0, lastIndex stays where it is and the engine keeps finding the same spot forever. matchAll and replace(/.../g) take care of this internally, so they are safe. Do not hand-write an exec loop over a zero-width pattern; use matchAll. The same trap exists in other languages as well, and in Perl you have to push pos() forward yourself.

$ echo 'AAAA' | grep -oP '(?=(AA))'
(출력 없음 - 매치가 빈 문자열이라 -o 가 찍을 것이 없다)

$ echo 'AAAA' | perl -ne 'while (/(?=(AA))/g) { print "$1 at ", pos(), "\n"; pos() = pos() + 1 }'
AA at 0
AA at 1
AA at 2

6. Defining the Word Boundary Yourself

\b is a zero-width condition too. The catch is that its definition of a word character is fixed, and when that definition does not fit your data there is no way to reach in and change it. Lookaround lets you write the definition yourself.

PatternMatch countWhat it catches
/cat\b/g3cat, the front of cat-x, the tail of concat
/cat(?!s)/g4the three above plus the front of catx
/cat(?![a-z])/g3cat, cat-x, concat
/(?<![a-z])cat(?![a-z])/g2cat and cat-x only

The input is cat cats catx cat-x concat. Because \b treats the hyphen as a boundary it catches cat-x, and it also catches the tail of concat. If that is not the behaviour you wanted, blocking both sides yourself with negative lookaround is the only way out.

In Korean this difference decides not a matter of taste but whether the thing works at all.

입력: 고양이 고양이들 왕고양이

T6 /\b고양이\b/g                    = null
T7 /(?<![가-힣])고양이(?![가-힣])/g = [ '고양이' ]

\b catches nothing whatsoever. The word-character definition behind \b is [A-Za-z0-9_], so Hangul is not a word character to begin with, and between a space and 고 both sides are non-word characters, so no boundary comes into existence. You get null, with no exception and no warning. If you need whole-word search in Korean text, drop \b and define the boundary yourself with lookaround.

7. Password Rules - What Works and What Does Not

This is the most widely copy-pasted use of lookahead. It stacks the question of whether several character classes are present as several separate conditions.

/^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9]).{12,}$/

PASS | Passw0rd!1234
FAIL | passw0rd!1234     (대문자 없음)
FAIL | PASSW0RD!1234     (소문자 없음)
PASS | Password!1234
PASS | Pw0!aaaaaaaaaaaa

It behaves exactly as intended. Yet three limits bite once you put it into real use, and not one of the three is the lookahead's fault - they all arise because the job you were trying to do with this tool was never a job for a regex in the first place.

7.1 It Cannot Tell You Which Condition Failed

The result is one bit, true or false. There is no information with which to tell the user that an uppercase letter and a symbol are missing and that four more characters are needed. Break the conditions apart and that information appears.

규칙을 조각으로 나눠 각각 판정:
I7 'passw0rd' 미충족 = 대문자, 특수문자, 12자 이상

Piling every condition into a single regex is a design that throws the inspection results away. For a final server-side check where only a verdict is needed, one line is better; for a screen that has to guide the user, splitting is better. If you need both, keeping one array of fragments as the source of truth and composing them when required keeps the two from drifting apart.

7.2 It Counts Length in Units That Are Not Human Units

J1 'Passw0rdAB😀'  사람이 센 글자 = 11 | .{12,} 가 센 것 = 12 | 통과 = true
J2 'Passw0rdABc!'  사람이 센 글자 = 12 | .{12,} 가 센 것 = 12 | 통과 = true
J3 이모지가 특수문자 조건을 충족시킨다 = true
J5 같은 J1 입력에 u 플래그를 붙이면      = false

J1 is the problem. The user typed eleven characters and still cleared a rule of twelve or more. JavaScript's . counts UTF-16 code units, so one emoji got counted as two. As a bonus, one half of the emoji matched [^A-Za-z0-9] and satisfied the symbol requirement as well. Add the u flag and counting switches to code points, which brings it back to normal (J5).

Korean splits according to the normalization form.

K1 '비밀번호입니다'  NFC 길이 = 7 | NFD 길이 = 17
K2 /^.{12,}$/       NFC = false | NFD = true

A string that looks identical on screen passes or fails the same rule depending on which form it arrived in. Running normalize('NFC') once at the input boundary is the countermeasure, and the full story of this problem is written up over in The Korean Regex Trap.

7.3 Passing the Rules Does Not Make a Password Good

I2 통과 = true  | Password1234!
I3 통과 = true  | Qwerty12345!
I4 통과 = false | correct horse battery staple   (28자)

The top entries of the most common breach lists pass, and a 28-character sentence fails. A character-composition rule is a tool for measuring shape, not a tool for measuring entropy. However finely you stack lookaheads, this gap does not close. Raising the minimum length and checking against a breach list has far more real effect. The very habit of deciding first which shapes you will admit belongs to the same thread as the allowlist discussion in A Denylist Is Always Late.

8. Lookbehind and Variable Length - The One Point Where Engines Diverge

Any halfway decent backtracking engine has lookahead. The one thing that diverges is whether a lookbehind has to be of fixed length. The reason lies in the implementation. Looking ahead just means reading rightward from the current position, but looking behind means you first have to know where to start reading from. If the length is fixed you step back exactly that far; if it is variable you have to try every possible step-back distance one at a time.

JavaScript (Node.js 22.16)OOO — no restrictionExecuted

Perl 5.38.2OO△ — bounded only, cap of 255Executed
PCRE (GNU grep 3.0 -P)OO△ — alternation yes, unbounded quantifier rejectedExecuted
POSIX ERE (grep -E, sed -E)XXXExecuted
Go regexp (RE2)XXXDocumentation
Java java.util.regex, .NETOO(blank)Not verified *

* Whether the last row supports variable length could not be confirmed by execution in this environment. It is collected in section 11.

Read the error messages directly and it becomes obvious where each engine draws its line.

[Python 3.13.3]

(?<=price:\s+)\d+   → error: look-behind requires fixed-width pattern
(?<=ab|abc)\d       → error: look-behind requires fixed-width pattern
(?<=a{1,3})\d       → error: look-behind requires fixed-width pattern

[Perl 5.38.2]

(?<=a{1,3})\d       → 'aaa9' 에서 9

The line is drawn in three different places. Python refuses even an alternation whose branches differ in length. Perl and PCRE accept anything bounded and stop at an unbounded quantifier. JavaScript takes everything. If portability is on your mind, using lookbehind only at fixed length is the safe floor.

8.1 Alternatives When You Need Variable Length

  • Use \K. PCRE and Perl have a marker meaning to drop everything up to this point out of the match. password=\K[^&]+ consumes password= and then discards it from the result. Because it reads forward, there is no length restriction at all.
  • Fall back to a capture group. This is the lowest common denominator that works everywhere. Replace (password=)[^&]+ with $1*** and Python, POSIX sed, and Go all give the same result.
  • Split it into two stages. Match broadly and then slice it up on the program side. It has the side effect of making the pattern shorter and easier to read.
  • On Python, the third-party regex module supports variable-length lookbehind. It is not part of the standard library, though, so it adds one more dependency.
  • There is also a design that never uses lookbehind at all. For data whose format you control, such as logs or configuration files, making the separator unique settles the matter. The more elaborate a pattern grows, the more that is usually a signal that the data is ambiguous rather than a signal that you need better regex skills.
$ perl -pe 's/password=\K[^&]+/***/'     → user=a&password=***&x=1
$ sed -E 's/(password=)[^ ]+/\1***/'    → user=a&password=***&x=1
  Python: re.sub(r'(password=)[^&]+', r'\1***', s) → user=a&password=***&x=1

8.2 POSIX ERE Does Not Raise an Error

This is the most dangerous cell in the table. Not having lookaround is not the problem in itself; the problem is that it does not tell you that it is missing.

입력 파일: foobar / foobaz
의도: bar 가 뒤따르는 foo 만

$ grep -oE 'foo(?=bar)' input.txt
(출력 없음)
$ echo $?
1
$ grep -oP 'foo(?=bar)' input.txt
foo

# ERE 가 (?=bar) 를 무엇으로 읽었나
입력에 foo?=bar / foo=bar / foobar 를 넣고 같은 ERE 패턴을 돌리면
$ grep -oE 'foo(?=bar)' input2.txt
foo=bar

In ERE, (?=bar) gets read as something along the lines of a group holding =bar which starts with an equals sign and may or may not be present. So it matches foo=bar, an entirely different string, does not match the foobar you actually meant, and the exit code is plainly 1. Swap grep -E and grep -P in a script and what comes back is a silence that looks exactly like the perfectly normal result of no matches. If you are going to use lookaround, spell out -P, and check whether that script might end up running on a build without -P.

8.3 A Lookbehind Matches From Right to Left

R1 /(?<=(\d+))$/.exec('1234')[1]  = "1234"
R3 /(?<=(\d+))/ .exec('1234')[1]  = "1"

The same lookbehind, and different results. R3 has no anchor, so it matches at index 1, the leftmost position where it can succeed, and reading leftward from there yields a single 1. R1 succeeds only at the end because of $, and reading leftward from there greedily takes all of 1234. MDN explains the same property with an example in which /(?<=([ab]+)([bc]+))$/ captures a and bc out of abc. That is, the later group gets to be greedy first. Put two or more groups inside a lookbehind and the direction of greediness looks backwards from intuition.

9. When You Try to Exclude a Korean Ending With a Lookahead

You want to find 아니 while excluding 아니요. The natural attempt is /아니(?!요)/.

HIT  이것은 사실이 아니다
miss 이것은 사실이 아닙니다      ← 의도하지 않은 누락
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요        ← 의도한 배제
miss 이것은 사실이 아님          ← 의도하지 않은 누락

아니요, the form you set out to exclude, dropped out cleanly. But 아닙니다 and 아님 dropped out along with it. Start fixing the lookahead at this point and you will burn your time for nothing. The lookahead did nothing wrong. The 아니 in front never matched in the first place, so the negative condition never even got the chance to be evaluated.

N2 '아닙니다'.indexOf('아니') = -1
N3 '아님'.indexOf('아니')     = -1
N4 니 = U+B2C8  닙 = U+B2D9  님 = U+B2D8

A Hangul syllable is a single code point composed out of an initial, a medial, and a final consonant. Attach a final consonant and the preceding character is replaced by an entirely different character. That is why the stem does not survive as a substring. The underlying principle is laid out in The Korean Regex Trap, and what matters here is the effect this property has on how lookaround gets used.

The order flips around. In English you can pin down the stem and then shave off the inflected forms you do not want with a lookahead. In Korean, a lookahead only acquires meaning after you have first opened up the final-consonant slot so that a match can happen at all.

/아[니닙님](?!요)/ 로 자리를 연 뒤:
HIT  이것은 사실이 아니다
HIT  이것은 사실이 아닙니다
HIT  이것은 사실이 아니라고 들었다
miss 이것은 사실이 아니요
HIT  이것은 사실이 아님

Now the lookahead does its job. Before you touch the exclusion condition, check whether the inclusion condition has ever matched even once. The failure of a negative lookahead shows up as the results shrinking, and having zero matches at all looks exactly the same, like no results, so the two cannot be told apart.

9.1 You Cannot Judge a Final Consonant With Lookaround

Suppose you want to find the positions carrying the adnominal ending ㄹ. Opening it up with [을ㄹ] looks as though it ought to work.

miss 할 수 있다
miss 갈 예정이다
HIT  먹을 만하다
miss 하는 중이다

One out of four gets caught. 먹을 matched because 을 is an independent syllable, but the ㄹ in 할 and 갈 is a final consonant seated inside the syllable, not a separate character at all. Neither a character class nor a lookaround can reach it. Judging a final consonant is arithmetic, not character comparison.

종성 인덱스 = (코드포인트 - 0xAC00) % 28

할 = 8 (ㄹ)   하 = 0 (없음)   갈 = 8 (ㄹ)

산술로 판정하면:
HIT  할 수 있다   (종성 = ㄹ)
HIT  갈 예정이다  (종성 = ㄹ)
HIT  먹을 만하다  (종성 = ㄹ)
miss 하는 중이다  (종성 = ㄴ)

This is not something a regex can do. Do not push Korean morphological conditions into lookaround; lift them out into code. The places where lookaround can be used are limited to cases in which a whole syllable plays the role of a boundary.

P1 '재고가 있음, 재고가 없음'.match(/(?<=재고가 )있음/g) = [ '있음' ]
P2 '재고가 있음, 재고가 없음'.match(/(?<!없)음/g)        = [ '음' ]

At this level, that is, conditions that land exactly on syllable units, lookaround fits well. It also carries the advantage of being fixed length, so it runs on any engine.

10. Performance - What Is Actually Dangerous

The claim that lookahead is slow circulates a great deal, but measure it and the danger turns out to sit somewhere else entirely. Here is the result of increasing only the number of conditions against a 500,000-character input.

입력 길이 500,004자

조건 1개  : 0.276 ms
조건 2개  : 0.422 ms
조건 4개  : 0.734 ms
한 번 훑기 : 5.291 ms   ← 같은 판정을 손으로 구현
길이 가드 : 0.00004 ms  ← 128자 넘으면 정규식을 돌리지 않음

Even stretched to four conditions it does not exceed three times the one-condition case. It does scan the input several times, but the number of scans is merely proportional to the number of conditions. More striking still is the fact that hand-writing the same verdict as a character loop turns out to be seven times slower. Character-class scanning takes an optimized path inside the engine, so the instinct that the regex looked slow so it was written out by hand often turns into a net loss.

10.1 The Real Danger - Nested Quantifiers Inside a Lookaround

패턴: /^(?=(a+)+$)/     입력: 'a' * n + 'b'

n=20    6.6 ms
n=22   27.2 ms
n=24  108.6 ms
n=26  431.4 ms
n=28 1764.6 ms
n=30 7104.6 ms

Four times slower for every two extra characters. A pattern that takes 7 seconds at n=30 is, at n=40, no longer within any time a human being would wait. This is the textbook shape of ReDoS, and the cause is not the lookahead but the (a+)+ sitting inside it. Attach a quantifier to a group that already carries a quantifier and the number of ways to divide the same string grows exponentially, and when the match fails the engine tries every last one of them.

There is one point at which lookahead does make the situation worse. A lookahead makes it easy to construct a condition that has to fail every single time. A negative lookahead succeeds, by definition, only when the inner match fails all the way through, so putting an exploding pattern inside it means the worst-case path always runs. By contrast /^(?=a+$)/, written without nesting, takes 0.15 milliseconds even on a 100,000-character input.

10.2 Countermeasures

  • Check the length cap before the regex runs. It is the cheapest and the surest measure. It is the 0.00004-millisecond row in the table above. For inputs with an obvious cap, such as passwords, user IDs, and file names, this alone practically settles the matter.
  • Do not create nested quantifiers. Make the shapes (a+)+, (a|a)*, and (\s*)+ standing items on your pattern-review checklist.
  • Where users supply the pattern, do not use a backtracking engine. Go's regexp and Rust's regex guarantee time linear in the input length, at the price of offering no lookaround. That trade is not a coincidence; it is two sides of the same design decision.
  • Set a timeout if one is available. Some runtimes, .NET among them, let you put a time limit on regex execution. It is not a root fix, but it converts an outage into a delay.
  • Keep the inside of a negative lookahead especially simple. That region gets searched all the way through on every attempt, even for perfectly normal input.
  • Freeze patterns as constants. Build a regex by concatenating strings and user input gets mixed into the pattern itself, accidentally producing an exploding shape. Pass values as arguments, not as pattern text.

11. What Could Not Be Verified

  • Variable-length lookbehind in Java's java.util.regex. There is no JDK in this environment, so it could not be confirmed by execution. That is why the corresponding cell in the section 8 table is left blank.
  • Variable-length lookbehind in .NET. For the same reason there was no execution check. Only the fact that it supports lookaround at all is stated, on the basis of documentation.
  • The behaviour of Go's regexp. With no Go toolchain available, the corresponding row of the table rests on the fact that the list of zero-width conditions enumerated by the regexp/syntax documentation (^ $ \A \b \B \z) contains no lookaround. It was not confirmed by execution.
  • Variable-length lookbehind in recent PCRE2. The PCRE row of the table is based on the build linked into GNU grep 3.0. PCRE2 is understood to have relaxed this restriction in later releases, but that could not be confirmed in this environment. Do not lump everything together as PCRE; compile it yourself on the build you actually use.
  • The portability of the ReDoS numbers. The section 10 measurements are on V8. Growing exponentially is a property common to backtracking engines, but the specific milliseconds and the threshold n vary with the engine and the hardware. Look at the growth rate, not the absolute values.
  • The combination of Unicode property escapes with lookaround. The Hangul boundary example in section 6 is written with [가-힣], which covers only precomposed syllables. Behaviour for cases that also need standalone jamo or decomposed forms is not covered in this article.

Conclusion: Not What to Match, but Where to Match

Learn lookaround as syntax for tacking on more conditions and you stop at copying a one-line password validator. In that particular spot a capture group would usually have done the job anyway. Where the tool truly earns its keep is the places where the condition and the result have to be separated.

  • When the characters used as the condition have to survive in the result - substitutions that match only the boundary
  • When several conditions have to be judged at the same point - filters that are not bound to any order
  • When the cursor must not advance - overlapping matches
  • When the boundary definition the engine chose does not fit your data - a \b you write yourself
  • When you have to look left and right at once - places that need a two-sided condition, such as acronym boundaries

Boil the criterion down to a single question and it comes to this. Is there a condition that must not appear in the match result? If there is, it is lookaround; if there is not, a simpler pattern is usually enough.

And two habits cut down on accidents. First, use lookbehind at fixed length. Python refuses even an alternation whose branches differ in length, and Perl and PCRE stop at an unbounded quantifier. If you genuinely need variable length, dropping down to \K or a capture group travels far more easily. Second, when you attach a negative condition, pin the match boundary along with it. The place where \d+(?!USD) handed back 10 is the reason why.

Finally, if you work with Korean, the order has to be reversed. Before shaving off inflected forms with a lookahead, first check whether the inclusion condition has ever matched at all. Zero matches and a cleanly applied exclusion look identical on the results screen.
