ここに載せた引数の一覧は、Windows PowerShell 5.1.19041.6456でpowershell.exe -NoProfileを実行し、受け取ったプログラム自身が出力したコマンドラインとargvをそのまま写したものである。引数を数えるプログラムはPython 3.13で、実際のツールとしてgit 2.48.1とcurl.exeを使った。curl.exeはPATHで先に見つかるものが実行されるため環境に依存し、パスとバージョンは11節のGet-Command curl.exeの出力に従う。PowerShell 7(pwsh)は環境になかったため、7に関する記述は公式ドキュメントの文言にとどめる。bash側の引用規則はシェル引用規則ガイドに、5.1で二重引用符と空文字列が消えるという基本事実はシェルの引用と韓国語ファイル名のガイドの6節にある。ここではその上に、PowerShellからネイティブプログラムへの引数渡しの全一覧、エスケープ方法ごとの成否、末尾バックスラッシュ、スプラッティング・--%・here-string、gitとcurl.exeの事例を加える。

測定方法 - 受け取るプログラムが自分のコマンドラインとargvを出力する

PowerShellが引数をどう分けて渡すかは、PowerShell側の出力からは分からない。プロセスが実際に受け取った文字列を、受け取る側が出力する必要がある。次の小さなプログラムは、Windows APIが返す元のコマンドライン(raw)と、それをCランタイムが分割したargvを一緒に出力する。以降のすべてのブロックでrawの行はPowerShellが組み立てたコマンドライン、argvの行は受け取るプログラムが見た引数である。引数の個数の行(n)はargvの長さなので省略し、行頭の>>>は試した入力である。

import sys, json, ctypes
                    ctypes.windll.kernel32.GetCommandLineW.restype = ctypes.c_wchar_p
                    raw = ctypes.windll.kernel32.GetCommandLineW()
                    i = raw.find('argv.py')
                    print('  raw : ' + raw[i + 7:].lstrip().encode('ascii','backslashreplace').decode())
                    print('  argv: ' + json.dumps(sys.argv[1:], ensure_ascii=True))
                    print('  n   : %d' % (len(sys.argv) - 1))

公式ドキュメントはこの過程を次のように説明している。ネイティブコマンドを呼び出すとき、PowerShellはまず引数を解析し、解析した引数を空白でつないで1つの文字列にし、その文字列がProcessStartInfoのArgumentsプロパティに入る。内側の引用符は、引用符を重ねるかバックスラッシュでエスケープしなければならず、バックスラッシュはPowerShellのエスケープ文字ではなく下位APIのエスケープ文字だと文書は書いている。この一段落が全体の枠組みである。PowerShellが1行を作り、受け取るプログラムがその1行をもう一度分割する。結果は、PowerShellの規則と受け取るプログラムの分割規則が出会う場所で決まる。

基本ルール - 空白があれば囲み、空文字列は捨てる

もっとも単純な入力から見る。$vにはa b(空白を含む)が入っている。

>>> python argv.py a b
                      raw : a b
                      argv: ["a", "b"]
                    
                    >>> python argv.py ''
                      raw : 
                      argv: []
                    
                    >>> python argv.py '' x
                      raw : x
                      argv: ["x"]
                    
                    >>> python argv.py 'a b'
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py "$v"   ($v = 'a b')
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py '$v'
                      raw : $v
                      argv: ["$v"]
                    
                    >>> python argv.py a$v
                      raw : "aa b"
                      argv: ["aa b"]

a ba b引数2つ
''(何もない)引数0個
'' xx引数1つ、xだけ残る
'a b'"a b"引数1つ
"$v""a b"引数1つ
'$v'$v引数1つ、文字どおり
a$v"aa b"引数1つ
  • 空白を含む引数だけが二重引用符で囲まれる。空白がなければ囲まれない。
  • 単一引用符はPowerShellが外し、内容をそのまま渡す。'$v'は展開されず、"$v"は展開される。展開された値に空白があっても単語分割は起きず、1つの引数である。
  • a$vのように変数に文字が付いた形も1つの引数としてつながる。公式ドキュメントも、単純な変数参照の後の文字は同じ引数の一部だと書いている。
  • 空文字列はrawに痕跡を残さない。その後ろの引数は1つずつ位置が繰り上がる。

最後の項目が、静かな事故の出発点である。--name '' --flagのような呼び出しで空の値を渡したつもりでも、受け取る側は--name --flagを見る。

二重引用符が消える - 最初に壊れるのはJSON

引数の中の二重引用符は、5.1ではエスケープされない。ドキュメントも、PowerShellのコマンドライン解析は入力した引用符を取り除くと書いている。

>>> python argv.py 'say "hi"'   (single-quoted, contains double quotes)
                      raw : "say "hi""
                      argv: ["say hi"]
                    
                    >>> python argv.py 'say"hi'   (no space in value)
                      raw : say"hi
                      argv: ["sayhi"]
                    
                    >>> python argv.py '{"a":1}'
                      raw : {"a":1}
                      argv: ["{a:1}"]
                    
                    >>> python argv.py '{"a": 1}'   (JSON with a space)
                      raw : "{"a": 1}"
                      argv: ["{a: 1}"]
  • 'say "hi"'は空白があるため二重引用符で囲まれるが、内側の引用符がそのまま入り、rawは"say "hi""になる。受け取る側は引用符を区切りとして消費し、say hiを得る。
  • 'say"hi'のように空白がなければ囲まず、引用符がrawにそのまま入るのに、結果はsayhiである。囲まれたかどうかに関係なく、引用符は消費される。
  • '{"a":1}'は{a:1}として届く。引用符のなくなったJSONは有効ではない。空白のある'{"a": 1}'も{a: 1}である。

この症状は、curl -d、git commit -m、python -c、node -eのように、引用符を含む値を渡すすべての呼び出しで同じ形で現れる。エラーが出ずに値が静かに変わる点が危険である。

二重引用符を残す方法 - バックスラッシュ、二重化、すでに囲んだ値

ドキュメントが挙げる2つの方法(引用符の重ね、バックスラッシュ)と、すでに引用符で囲んだ値を試した。

>>> python argv.py 'say \"hi\"'   (backslash-escaped quotes)
                      raw : "say \"hi\""
                      argv: ["say \"hi\""]
                    
                    >>> python argv.py '{\"a\":1}'
                      raw : {\"a\":1}
                      argv: ["{\"a\":1}"]
                    
                    >>> python argv.py '{\"a\": 1}'
                      raw : "{\"a\": 1}"
                      argv: ["{\"a\": 1}"]
                    
                    >>> python argv.py 'say ""hi""'   (doubled quotes inside single quotes)
                      raw : "say ""hi"""
                      argv: ["say \"hi\""]
                    
                    >>> python argv.py 'a""b'
                      raw : a""b
                      argv: ["ab"]
                    
                    >>> python argv.py '{""a"":1}'
                      raw : {""a"":1}
                      argv: ["{a:1}"]
                    
                    >>> python argv.py '"a b"'
                      raw : "a b"
                      argv: ["a b"]
                    
                    >>> python argv.py 'x "a b"'
                      raw : "x "a b""
                      argv: ["x a", "b"]
                    
                    >>> python argv.py '""'
                      raw : ""
                      argv: [""]

  • 値の中の二重引用符をバックスラッシュと二重引用符に置き換えると、空白の有無に関係なく残って届いた。
  • 引用符の重ねは、PowerShellが引数を二重引用符で囲む場合(空白があるとき)だけPythonで通った。囲まれない引数では引用符が消費され、gitでは同じ形がエラーだった。同じコマンドラインでも、受け取るプログラムによって分割規則が違いうるということである。
  • すでに二重引用符で囲んだ"a b"を、5.1はもう一度囲まなかった(すでに囲んだ値がいつもそうとは限らず、条件は10節で実験した)が、その引用符は区切りとして消費される。引用符が値の一部でなければならないなら、この方法は使えない。
  • 二重引用符2文字を値として渡すと、空文字列が1つ届く。3節で消えた空の引数を復活させる方法である。

末尾のバックスラッシュが次の引数を飲み込む

空白を含むパスは二重引用符で囲まれる。そのパスがバックスラッシュで終わると問題が起きる。次のargvの行はJSON形式なので、バックスラッシュ1つが2つで表記される。

>>> python argv.py 'C:\Program Files\x'
                      raw : "C:\Program Files\x"
                      argv: ["C:\\Program Files\\x"]
                    
                    >>> python argv.py 'C:\Program Files\x\'   (path ends with backslash)
                      raw : "C:\Program Files\x\" next
                      argv: ["C:\\Program Files\\x\" next"]
                    
                    >>> python argv.py 'C:\Program Files\x\\'   (two backslashes)
                      raw : "C:\Program Files\x\\" next
                      argv: ["C:\\Program Files\\x\\", "next"]
                    
                    >>> python argv.py 'C:\x\' next   (no space in path)
                      raw : C:\x\ next
                      argv: ["C:\\x\\", "next"]
  • 空白を含むパスC:\Program Files\xは正常である。
  • 同じパスが\1つで終わると、rawが"C:\Program Files\x\" nextになり、閉じ引用符がエスケープされた引用符として読まれ、後ろのnextが同じ引数に合体する。受け取った引数は1つで、値はC:\Program Files\x" nextである。引数が1つ減ったのではなく、2つが1つに固まった。
  • 末尾に\\を2つ置くと、1つのバックスラッシュと閉じ引用符として読まれ、nextが別に届く。届いたパスの末尾にはバックスラッシュが1つ残る。
  • 空白のないパスC:\x\は囲まれないので、この問題は起きない。

条件は2つが同時に満たされたときである。引数に空白があって囲まれ、末尾がバックスラッシュである。フォルダーのパスを末尾の区切りまで付けて作るコード、たとえばユーザーフォルダーの下の空白を含むフォルダーを指す変数が、ここに引っかかる。末尾のバックスラッシュをTrimEnd('\')で取るか、2つに増やして渡せば正常になる。

変数・カンマ・メタ文字 - どこまでがPowerShellの仕事か

引数には、PowerShellが先に解釈するものと、そのまま渡すものが混ざっている。

>>> python argv.py 1,2
                      raw : 1,2
                      argv: ["1,2"]
                    
                    >>> python argv.py $env:OS
                      raw : Windows_NT
                      argv: ["Windows_NT"]
                    
                    >>> python argv.py (1+2)
                      raw : 3
                      argv: ["3"]
                    
                    >>> python argv.py '%OS%'
                      raw : %OS%
                      argv: ["%OS%"]
                    
                    >>> python argv.py *.nothing  (no match, wildcard)
                      raw : *.nothing
                      argv: ["*.nothing"]
                    
                    >>> python argv.py 'a & b' 'a | b'
                      raw : "a & b" "a | b"
                      argv: ["a & b", "a | b"]
                    
                    >>> python argv.py a;echo b   (semicolon ends the statement)
                      raw : a
                      argv: ["a"]
                    b
                    
                    >>> python argv.py ('caf' + [char]0xE9) ('x' + [char]0xD55C)
                      raw : caf\xe9 x\ud55c
                      argv: ["caf\u00e9", "x\ud55c"]
  • 1,2は1つの引数1,2として届く。公式ドキュメントは、カンマがPowerShellコマンドでは配列を作るが、ネイティブアプリケーションでは展開可能な文字列の一部として解釈されると書いている。
  • $env:OSや(1+2)のような変数・括弧の式は、PowerShellが先に評価して値が渡される。'%OS%'はPowerShellが触らず、文字どおりである。
  • ワイルドカード*.nothingは展開されず、そのまま渡される。ファイル名の展開をPowerShellはしない。
  • 'a & b'のように引用符の中のメタ文字は1つの引数として保たれる。引用符の外のセミコロンはコマンドを終わらせる。a;echo bでPythonが受け取ったのは引数aだけで、echo bは別のコマンドとして実行され、bが出力された。
  • 非ASCII文字は、出力をASCIIエスケープで出したため\xe9、\ud55cと見えるが、引数は正常に届いた。コマンドラインがUnicodeで渡されるためである。

ドキュメントがまとめる引数モードのメタ文字は、空白、単一引用符、二重引用符、バッククォート、カンマ、セミコロン、丸括弧、波括弧、パイプ、アンパサンド、山括弧、アットマーク、シャープである。このうち山括弧・アットマーク・シャープは、トークンの先頭でだけ特別である。引用符なしで渡す引数にこうした文字があると、PowerShellが先に取る。

配列とスプラッティング - 1つの文字列は1つの引数

引数のリストが可変のときは変数に入れて渡すことになるが、入れる形が結果を分ける。

>>> $arr = 'x','y z'; python argv.py $arr
                      raw : x "y z"
                      argv: ["x", "y z"]
                    
                    >>> $s = '--flag "a b"'; python argv.py $s
                      raw : "--flag "a b""
                      argv: ["--flag a", "b"]
                    
                    >>> $sp = @('--flag','a b'); python argv.py @sp
                      raw : --flag "a b"
                      argv: ["--flag", "a b"]
                    
                    >>> $h = @{k=1}; python argv.py @h  (hashtable splat)
                      raw : -k:1
                      argv: ["-k:1"]
  • 配列変数$arrは要素ごとに1つの引数になり、空白のある要素だけが囲まれる。
  • 引数のリストを1つの文字列として入れた$sは、全体が1つの引数になる。空白があって囲まれ、内側の引用符が消費され、--flag aとbに分かれた。リストを文字列に組み立てて渡す方式がおかしくなる典型である。
  • 配列をスプラッティング(@sp)すると、変数に入った要素が1つずつ引数になる。可変の引数にはこの方式が安全である。
  • ハッシュテーブルのスプラッティング@hは、キーと値を-k:1の形の1つの引数にした。ネイティブプログラムのオプション形式に合うかどうかはプログラム次第である。

--%と-- - 解析を止めるトークン

stop-parsingトークン--%は、その後ろの文字をPowerShellの解釈なしで渡すトークンである。ドキュメントは、行の残りをリテラルとして扱い、%USERPROFILE%のようなWindows表記の環境変数だけを置換すると説明している。

>>> python argv.py --% a "b c" %OS%
                      raw : a "b c" Windows_NT
                      argv: ["a", "b c", "Windows_NT"]
                    
                    >>> python argv.py --% --opt="a b" 'q'
                      raw : --opt="a b" 'q'
                      argv: ["--opt=a b", "'q'"]
                    
                    >>> python argv.py --% "a b" "c
                      raw : "a b" "c
                      argv: ["a b", "c"]
                    
                    >>> python argv.py -x -- y
                      raw : -x -- y
                      argv: ["-x", "--", "y"]
                    
                    >>> python argv.py --opt="a b"
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py --opt=$v
                      raw : "--opt=a b"
                      argv: ["--opt=a b"]
                    
                    >>> python argv.py -p:val
                      raw : -p:val
                      argv: ["-p:val"]
  • --% a "b c" %OS%では二重引用符が区切りとして使われ、b cが1つの引数になり、%OS%はWindows_NTに置換された。ドキュメントが述べるとおり%名前%の形は常に展開され、定義されていない名前ならそのまま残る。
  • --%の後の単一引用符はPowerShellが外さない。'q'は引用符付きの'q'として届いた。
  • 引用符の対応が取れていなくてもそのまま渡される。閉じていない"cが1つの引数cとして届いた。
  • ドキュメントによれば--%は次の改行かパイプまでしか有効でなく、リダイレクトも引数として渡され、環境変数以外の動的な要素は埋め込めない。
  • PowerShellコマンド用のトークンである--は、ネイティブプログラムではただの--という引数として渡される。-x -- yは3つの引数になった。
  • --opt="a b"と--opt=$vは、どちらも"--opt=a b"という1つの引数に組み立てられた。オプション名と値がつながった1つのトークンだからである。

バッククォートとhere-string - 複数行の引数

バッククォートは二重引用符文字列の中でだけエスケープである。単一引用符の中では文字そのものである。改行を含む値はhere-stringで作れる。

>>> python argv.py 'a`tb' "a`tb"
                      raw : a`tb "a	b"
                      argv: ["a`tb", "a\tb"]
                    
                    >>> python argv.py "line1`nline2"
                      raw : "line1
                    line2"
                      argv: ["line1\nline2"]
                    
                    >>> here-string: python argv.py (@'...'@)  with a double quote inside
                      raw : "first line
                    second "quoted" line"
                      argv: ["first line\nsecond quoted line"]
  • 単一引用符の中のバッククォートtは文字どおり届き、二重引用符の中のバッククォートtはタブ文字になった。
  • 改行を含む引数は、rawに改行がそのまま入り、1つの引数として届く。空白のある引数と同じく二重引用符で囲まれる。
  • here-stringの中の二重引用符は3節と同じく消費され、second quoted lineになった。ドキュメントが説明するとおり、here-stringは中の引用符をリテラルとして解釈するが、ネイティブプログラムへ渡す段階でもう一度外される。

引用符を含む複数行の値を安全に渡す方法は、11節のcurl.exeの事例で比較する。

コマンドラインを正確に制御する方法 - Start-ProcessとProcessStartInfo

PowerShellの組み立て規則を避けるには、コマンドラインを自分で作って渡せばよい。まずStart-Processの-ArgumentListが文字列のときと配列のときに何が起きるかを確認した。

>>> Start-Process python -ArgumentList 'argv.py "a b" {\"k\":1}' -NoNewWindow -Wait
                      raw : "a b" {\"k\":1} 
                      argv: ["a b", "{\"k\":1}"]
                    
                    >>> Start-Process python -ArgumentList @('argv.py','a b','c') -NoNewWindow -Wait
                      raw : a b c 
                      argv: ["a", "b", "c"]

文字列を1つ渡すとrawが入力文字列と同じになるので、呼び出し側が二重引用符とバックスラッシュを直接制御する。配列を渡すと要素を空白でつなぐだけで囲まないため、'a b'がaとbの2つの引数に分かれた。配列が安全だと思い込んではいけない。

任意の値を正確に伝えるには、Cランタイムの規則に合わせてエスケープするヘルパーを用意し、その結果をProcessStartInfo.Argumentsに入れる方法がある。次のヘルパーは、値の中の二重引用符の前のバックスラッシュを2倍にし、二重引用符をバックスラッシュでエスケープし、末尾のバックスラッシュを2倍にしたうえで、全体を二重引用符で囲む。

function ConvertTo-NativeArg([string]$a) {
                      if ($a -eq '') { return '""' }
                      $r = $a -replace '(\\*)"', '$1$1\"'
                      $r = $r -replace '(\\+)$', '$1$1'
                      '"' + $r + '"'
                    }
                    function Invoke-NativeExact([string]$File, [string[]]$ArgList) {
                      $psi = New-Object Diagnostics.ProcessStartInfo
                      $psi.FileName = $File
                      $psi.Arguments = ($ArgList | % { ConvertTo-NativeArg $_ }) -join ' '
                      $psi.UseShellExecute = $false
                      $psi.RedirectStandardOutput = $true
                      $psi.StandardOutputEncoding = [Text.Encoding]::UTF8

function Test-Rule([string]$s) {
                      $n = 0
                      foreach ($ch in $s.ToCharArray()) {
                        if ($ch -eq '"') { $n++ }
                        elseif ([char]::IsWhiteSpace($ch) -and $n % 2 -eq 0) { return $true }
                      }
                      $false
                    }
                    $cases = @(

                      '"a" b',
                      '"a b" c',

実例 - git commitとcurl.exe

一時的なリポジトリで、二重引用符を含むコミットメッセージを渡してみた。次の5つの呼び出しに続く出力の番号は、呼び出しの順序と同じである。

git commit -q --allow-empty -m 'fix "x" bug'
                    git commit -q --allow-empty -m 'fix \"x\" bug'
                    git commit -q --allow-empty -m "fix ""x"" bug"
                    git commit -q --allow-empty -m 'fix ""x"" bug'
                    git commit -q --allow-empty -m 'fix "x"'
1) -m 'fix "x" bug'          -> fix x bug
                    2) -m 'fix \"x\" bug'        -> fix "x" bug
                    3) -m "fix ""x"" bug"          -> fix x bug

                    4) -m 'fix ""x"" bug'        -> fix x bug
                    5) -m 'fix "x"'              -> fix x
  • 1番はfix x bugで二重引用符が消え、5番もfix xである。
  • 2番はバックスラッシュのエスケープを使い、fix "x" bugが正確に入った。
  • 3番はPowerShellの二重引用符文字列の中で引用符を重ねたが、その文字列が作る値は1番と同じfix "x" bugなので、結果も1番と同じになる。PowerShellレベルのエスケープは、ネイティブプログラムに対して引用符をエスケープしてはくれない。
  • 4番はコマンドラインに引用符の重ねを入れたところ、gitがpathspec 'bug' did not matchというエラーを出した。4番の行に出たメッセージは直前のコミットのものである。同じ入力がPythonでは通ったので、引用符の重ねはプログラムごとに結果が違う。

JSON本文を送るcurl.exe -dは、より一般的な事例である。ローカルにPOST本文をファイルへ保存する小さなサーバーを立て、受け取った本文を読んだ。

import http.server, sys
                    class H(http.server.BaseHTTPRequestHandler):
                        def do_POST(self):

PowerShell 7.3以降は違う - ドキュメントに書かれたことだけ

公式ドキュメント(7.4版)によれば、PowerShell 7.3はネイティブコマンドのコマンドラインの解析方法を変え、新しい変数$PSNativeCommandArgumentPassingがそれを制御する。ドキュメントは、この変更が破壊的変更であり、ネイティブアプリケーション呼び出しの種々の問題を回避していたスクリプトや自動化を壊す可能性があると警告している。

  • 値はLegacy、Standard、Windowsで、Legacyが従来の動作である。
  • Windowsでの既定値はWindows、それ以外のプラットフォームではStandardである。
  • WindowsモードはStandardと同じだが、cmd.exe、cscript.exe、find.exe、sqlcmd.exe、wscript.exeと、.bat・.cmd・.js・.vbs・.wsfで終わるファイルにはLegacyの方式を使う。

この環境にはpwshがなく、7の動作は実行できなかった。上の内容はドキュメントの文言であり、本稿の5.1の回避策(バックスラッシュのエスケープ、ヘルパー)が7でどう動くかは確認していない。5.1用の回避策を7へ移す前に、同じ方法でrawとargvを出力してみるのが確実な確認法である。

確認できなかったこと

  • PowerShell 7(pwsh): 環境になく、直接実行できなかった。7.3以降の引数渡しと$PSNativeCommandArgumentPassingの3つの値の動作は、公式ドキュメントの文である。
  • 5.1の回避策(バックスラッシュのエスケープ、引用符の重ね、ヘルパー)が7.3以降でどう動くか: 実行していない。
  • Python・git・curl.exe以外のプログラム: Node、Go、Java、.NET、ほかのMinGW系ツールのコマンドライン分割規則。gitで引用符の重ねが失敗した理由は確認できておらず、結果だけを記録した。
  • cmd.exe、.bat、.cmdを経由する呼び出し(npm.cmdなど): 実行していない。ドキュメントは、バッチファイルでは引数が元のコマンドラインとして渡されると警告している。
  • here-string本文がcurl.exeで途中で切れた原因: 引数が2つに分かれたという推測であり、curl側の引数は直接確認していない。
  • ほかのWindowsビルド、ロケール、コンソールコードページでの違い: 韓国語版Windows 10の5.1.19041だけで確認した。非ASCIIの引数はPythonの1例だけ試した。
  • 5.1が引数をもう一度囲む内部の条件: 14個の文字列の観察に合う規則までしか確認しておらず、5.1の実装やドキュメントでは確認できなかった。より多様な入力でこの規則が成り立つかも試していない。
  • Start-Processの-VerbなどShellExecuteの経路、呼び出し演算子&で実行する場合: 扱っていない。
