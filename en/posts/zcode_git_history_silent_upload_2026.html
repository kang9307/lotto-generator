Inside ZCode's Git History Exfiltration — UI Toggles vs Runtime Reality

Workspace snapshot architecture, server-exclusive asymmetric keys, and the trust boundaries of local AI harnesses

Published: 2026-09-19 Dev & Infra

In modern software engineering practice, artificial intelligence programming assistants have rapidly evolved from basic single-line code completion engines into autonomous desktop agents capable of traversing full project hierarchies, resolving dependency graphs, and orchestrating complex multi-file refactoring workflows. To deliver rich semantic awareness across expansive codebases, these agentic systems fundamentally rely on broad filesystem indexing, ingesting source trees, configuration manifests, build scripts, and documentation files. This pervasive operating system level access allows autonomous harnesses to understand complex software architecture without requiring continuous manual context provision from developers.

However, granting desktop editors and autonomous execution harnesses unrestricted filesystem traversal rights creates severe operational risks if internal telemetry pipelines and remote exfiltration boundaries are not strictly and transparently governed. When proprietary intellectual property, commercial source code, unpublished business logic, and cumulative version control databases are packaged and dispatched to external cloud infrastructure without explicit authorization or granular user consent, the security posture and governance boundaries of entire engineering organizations become critically compromised.

On September 18, 2026, software engineer ferstar published an extensive technical reverse-engineering analysis of ZCode, the official desktop AI coding application developed by Z.ai, the Beijing-headquartered firm responsible for the GLM family of open-weight large language models. According to ferstar's technical teardown, ZCode silently packages not only active source files but the complete internal .git repository directory of any opened workspace whenever an authenticated user session is active, encrypting the resulting archive and uploading it directly to Alibaba Cloud's Aliyun Object Storage Service (OSS). The revelation spread swiftly across technical media platforms, including tokenstead.ai and international developer forums, igniting intense scrutiny regarding the governance and data sovereignty of AI coding tools.

The crux of this engineering revelation extends far beyond the mere presence of cloud telemetry or background synchronization. The central controversy lies in the severe architectural divergence between user interface affordances and actual client runtime execution: configuration toggles marketed to disable data sharing failed to stop the background capture pipeline, and 86.6 percent of the uploaded payload consisted of immutable Git object databases rather than active working tree files. This analysis explores ZCode's background capture pipeline, encryption mechanics, and structural implications for local AI development environments based on verifiable forensic evidence.

1. Reverse-Engineered Workspace Upload Pipeline in ZCode

According to the technical forensics published by ferstar, decompiling the Electron application bundle (app.asar) extracted from the official ZCode desktop client revealed a sophisticated, multi-stage background snapshot architecture designed to harvest local repository state. The client does not merely pass text snippets through standard conversational inference endpoints; instead, it coordinates directly with remote orchestration infrastructure to package and transmit compressed archives directly into high-capacity cloud object storage.

Forensic inspection of the reconstructed client codebase demonstrates that the exfiltration pipeline follows a systematic three-phase workflow during normal operation:

  • The desktop client initiates an authentication handshake with the coordination authority domain at zcode.z.ai, obtaining specialized Aliyun OSS pre-signed form authorization credentials, an assigned target object key, payload quota constraints, and a round-specific ephemeral RSA public key.
  • An asynchronous background worker on the local host packages the entire active workspace into a tar.gz archive, generates a cryptographic symmetric key to encrypt the archive, and encrypts the symmetric key itself using the server-supplied RSA public key to construct an encrypted envelope.
  • The client issues a direct HTTP POST form submission containing the encrypted binary payload to designated Aliyun OSS regional nodes, after which the storage service executes an automated webhook callback to Z.ai's backend to catalog the registered snapshot.

This distributed transmission pipeline was corroborated through dynamic packet capture analysis on actively running systems. Throughout operational test sessions, the desktop client maintained persistent TCP Keep-Alive connections not only with the zcode.z.ai control plane but also with two discrete Aliyun OSS storage endpoints, continuously transmitting high-volume outbound packets during background execution.

Unlike conventional web architectures that route all file traffic through intermediate application servers, ZCode's use of direct pre-signed cloud storage uploads allows the client to bypass application layer proxy bottlenecks. This design enables the background transfer of multi-hundred-megabyte archives efficiently and rapidly, minimizing infrastructure load on coordinator instances while streamlining repository harvesting.

2. Forensic Breakdown of a 42,411-File Snapshot: Git Data Constitutes 86.6%

To quantify the exact contents harvested by ZCode during background synchronization, researchers examined plaintext packaging manifests generated locally by the client before transmission. Analysis of a representative commercial workspace snapshot comprising 42,411 individual files with an uncompressed size of approximately 345.1MB revealed a stark distribution across directory categories:

Table 1: Forensic Manifest Breakdown of a ZCode Snapshot Archive (Source: ferstar reverse engineering analysis)
Directory Path & Content Category Uncompressed Volume Share of Total Payload
.git/lfs/ (Large File Storage asset cache) 196.1 MB 56.8%
.git/objects/ (Core Git content-addressable database) 102.2 MB 29.6%
.git/logs/ (Reference logs and local branch reflogs) 0.6 MB 0.2%
Source code and documentation (Working tree files) 46.2 MB 13.4%

The numerical breakdown establishes that human-readable source code files, configuration scripts, and documentation residing in the active working tree accounted for merely 46.2MB, representing just 13.4 percent of the aggregate snapshot. Conversely, the internal .git version control directory constituted an overwhelming 86.6 percent of the total volume (196.1MB + 102.2MB + 0.6MB = 298.9MB). Following local compression and cryptographic encapsulation, this 345.1MB footprint was transformed into a 313MB encrypted binary artifact prior to upload.

This payload composition yields three critical architectural insights regarding ZCode's underlying data collection strategy:

  • The substantial volume of the LFS cache (196.1MB, representing 56.8% of the payload) indicates that binary assets, pre-trained model weights, and proprietary test datasets were swept into the archive without functional file-type exclusion filters.
  • The core Git object store (102.2MB, or 29.6% of the payload) ensured that every commit, tree, and blob recorded across the entire lifecycle of the repository was captured rather than just current file revisions.
  • The inclusion of the reflog directory (.git/logs/) means that ephemeral local branch checkouts, discarded commits, and private rebase operations were cataloged alongside published project history.

In standard artificial intelligence tooling, semantic code search and context augmentation engines parse active source files (such as .ts, .py, or .rs) to construct Abstract Syntax Trees (AST) or generate embedding vectors. Internal Git databases are structurally useless for direct language model inference and severely degrade archive compression ratios. Packaging the entire .git tree without exclusion rules indicates an architecture designed to replicate complete repository databases rather than extract contextual code snippets.

3. Working Tree vs. Repository Lineage: The Danger of Cumulative History Exposure

For systems engineers familiar with distributed version control internals, the exposure of a .git directory represents a vastly greater security failure than leaking current working files. Developer ferstar emphasized this distinction with precise clarity: "A git object store is not a snapshot of your working tree — it is the complete lineage of the repository since day one."

The working tree exposes only the files currently checked out on the developer's local filesystem. If an engineer inadvertently committed a cloud access token, a database password, or a private certificate several months prior, and subsequently purged that secret in a follow-up commit, the credential no longer appears within the working tree. Any tooling that inspects only active workspace files would never encounter the retired secret.

However, Git's object store functions as an immutable, content-addressable database. Blobs representing past revisions persist indefinitely unless an explicit, destructive repository purge (such as git filter-repo) is executed across all branches. Consequently, harvesting the .git directory exposes every historical secret, deprecated credential, and discarded architectural prototype accumulated throughout the project's entire existence.

Forensic inspection identifies three primary categories of high-risk operational assets exposed through cumulative Git lineage capture:

  • Credentials and private keys that were committed in historical commits and later deleted from current files, yet remain fully recoverable within unpruned Git blob storage.
  • Unpushed local feature branches containing confidential commercial planning, upcoming algorithmic implementations, and proprietary technical designs never intended for external visibility.
  • Internal hostnames, private corporate domain hierarchies, and developer workstation absolute filesystem paths stored in plaintext within the local .git/config file.

Furthermore, when developers execute coding assistants from broad directories such as their user home path (~), the exfiltration perimeter expands catastrophically. In documented historical telemetry incidents across the AI assistant ecosystem, running tools in root home paths resulted in private SSH keys, password manager vault files, personal documents, and family photos being captured into upload queues, demonstrating the immense hazard of unconstrained directory archiving.

4. The Interface Disconnect: Background Capture Operates Irrespective of UI Toggles

From the standpoint of data governance and user autonomy, the most alarming finding in the ZCode teardown is the total failure of user interface controls to govern background exfiltration. Even when software includes aggressive data collection mechanisms, transparent opt-out mechanisms allow organizations to enforce compliance. In ZCode, however, decompilation revealed that user-facing preference toggles failed to disconnect the underlying upload engine.

Table 2: Comparison of ZCode UI Preferences vs. Decompiled Runtime Logic (Source: ferstar reverse engineering analysis)
User Interface Preference (Internal Flag) Expected Operational Behavior Decompiled Code Reality
Optimize Experience (optimizeAgentExperienceEnabled) Completely halt workspace data capture and external transmission Only toggles authorization for model training usage on vendor servers; snapshot packaging and Aliyun OSS uploads continue uninterrupted
Repo Snapshot Indexing (repoSnapshotIndexingEnabled) Block repository snapshot creation and outbound network dispatch Only instructs the server whether to index uploaded archives; local packaging and network uploads execute without modification

Decompilation of ZCode's host assembly layer revealed that the application instantiates the snapshot capture sidecar unconditionally upon startup, completely bypassing user configuration settings. The sole technical prerequisite for sidecar initialization is whether the local token provider can successfully supply a valid JSON Web Token (JWT). In practical terms, logging into a ZCode account unconditionally activates the background upload engine.

This stealthy architectural separation is corroborated by multiple independent engineering observations:

  • Runtime telemetry monitoring across a single active engineering session recorded 62 distinct capture events, triggered predictably prior to prompt dispatch and immediately upon agent task completion.
  • Analysis of ZCode's leaked 131KB system prompt and 31-tool agent surface hosted on OrcaPromptVault revealed that zero tools are exposed to the AI model for snapshot generation, uploads, or telemetry.
  • This confirms that data exfiltration is implemented as a host-level binary sidecar residing outside the agentic tool-execution loop, ensuring the model itself has no visibility into the background transmission pipeline.
  • ZCode's official privacy documentation only discloses the collection of "text, files, and code submitted during conversations," containing no disclosure regarding full workspace compression or entire Git history replication.

5. Envelope Encryption and Key Asymmetry: AES-256-CTR with Server-Exclusive Private Keys

A crucial technical nuance in ZCode's transmission architecture is its utilization of industrial-strength cryptography. The desktop client encrypts outgoing workspace archives using the AES-256-CTR symmetric cipher and subsequently encapsulates the symmetric key using the RSA-OAEP asymmetric scheme, implementing standard envelope encryption.

In enterprise network environments, robust payload encryption is typically championed as an essential control against network eavesdropping and Man-in-the-Middle (MitM) attacks. However, when evaluating cryptographic systems, the central architectural question must always be: "Whose security is being enforced, and against whom?" In ZCode's implementation, the key management hierarchy establishes absolute vendor exclusivity.

During upload credential negotiation, the client receives an ephemeral RSA public key from the zcode.z.ai coordination authority to wrap the symmetric key. Crucially, the matching RSA private key required to decrypt the symmetric key does not exist on the client workstation. It resides solely within Z.ai's cloud backend infrastructure.

The structural ramifications of this asymmetric key design are clear and significant:

  • The 313MB encrypted ciphertext residing on the user's local disk cannot be unwrapped using any key on the local system, meaning neither the developer nor the ZCode client executable can decrypt its own artifact once packed.
  • While the encryption shields the transmission stream from third-party network interception, the recipient cloud server retains absolute unilateral authority to decrypt and inspect the full source repository at will.
  • Researcher ferstar highlighted this dynamic directly: "A key that only the server can use serves exactly one purpose: making sure the server can read your code whenever it wants."

Consequently, rather than providing End-to-End Encryption (E2EE) to defend user privacy, this implementation functions as a vendor-centric black box. It prevents developers from auditing or inspecting the specific files packaged from their machines, effectively locking the user out of verifying their own transmitted data.

6. Observation of 564 Retries and Persistent Checkpoint State Machines

Evidence that ZCode's snapshot exfiltration is an integral architectural component rather than an intermittent error appears in its aggressive network state machine. When forensic investigators severed network routes or deleted pending local archive files, the client demonstrated persistent, autonomous recovery loops.

Forensic monitoring during fault injection revealed specific runtime persistence characteristics:

  • When outbound upload connections were denied, client logs documented a continuous series of 564 failed upload retry attempts, cycling through persistent network reconnection loops.
  • Whenever pending snapshot archives were purged from the local filesystem, the client automatically re-scanned the repository and re-packaged a fresh 313MB archive within 30 minutes, incrementing internal retry counters.
  • The leaked system prompt reveals that ZCode's user-facing checkpoint rollback mechanism ("Workspace rewind applied") is coupled to this snapshot pipeline, explaining the client's aggressive attempts to synchronize state.

To mitigate this background activity, security researchers identified a kernel-level filesystem intervention. By enforcing immutable filesystem attributes (such as chattr +i on Linux or chflags uchg on macOS) across the local checkpoint directory, developers can prevent the unprivileged client process from generating snapshot archives. Applying this lock disables the UI workspace rollback feature but allows regular conversational prompts, code autocompletion, and local editing to function normally without background exfiltration.

7. Open Weights vs. Closed Runtimes: Validating Trust Boundaries in Local AI

The rise of open-weight large language models has encouraged organizations to deploy local AI infrastructure, seeking to eliminate per-token API costs and protect proprietary intellectual property from cloud leakage. Z.ai's GLM model series has garnered widespread adoption within this local AI movement due to strong programming capabilities. However, the ZCode incident demonstrates that open model weights do not guarantee a secure or open desktop runtime.

Developers frequently assume that software distributed under an open model brand inherits the open-source ethos of the underlying weights. Yet while GLM model weights are publicly accessible, the ZCode desktop harness is a proprietary, closed-source binary. Running an open model inside an opaque, telemetry-heavy harness that silently transmits entire repository trees to external storage completely invalidates the air-gapped security advantages that local deployment was intended to deliver.

To prevent similar governance failures, engineering leadership must institute rigorous evaluation standards when adopting AI developer harnesses:

  • Mandate full source code availability and reproducible builds for any desktop AI harness, verifying that no host-level background exfiltration sidecars operate outside standard tool loops.
  • Deploy continuous network monitoring and egress firewall rules to intercept and analyze outbound connections directed toward external cloud object storage and telemetry endpoints.
  • Conduct dynamic binary profiling to verify that privacy toggles presented in the user interface correspond to hard network socket terminations within compiled binaries.
  • Enforce strict OS-level containerization or sandboxing to isolate internal .git directories, environment credential files (.env), and SSH configurations from the tool's filesystem access perimeter.

As of publication, Z.ai has not released an official corporate statement, technical clarification, or rebuttal addressing ferstar's forensic findings. An informal comment from an account affiliated with the ZCode team stating "hey I am sorry to let you find it" was documented on social media, functioning as informal confirmation of the underlying mechanism rather than a refutation. As AI developer tooling continues to advance in autonomy and scope, maintaining absolute technical vigilance over desktop runtime trust boundaries remains an indispensable engineering requirement.
