PythonをRustへ移すという決定

自動変換ツールが引いた境界線と、実務でその線を引き直す方法

2026年7月29日 IT・技術

序論: 「PythonをRustへ変換してくれる」に省略された条件

PythonコードをRustへ移してくれるというツールは何年も前から出ている。2026年7月にもRextioというプロジェクトが公開された。この種の知らせを見るたび反射的に浮かぶ問いは「では自分たちのコードも移せるのか」だが、この問いはほぼ常に間違った問いである。正しい問いは自分のコードのどの部分が移せる性質を持っているかであり、その答えはツールの性能ではなくコードの性質が決める。

Rextioのリポジトリ文書を開くと、この点はむしろツールの側から先に明示されている。このツールはコード全体を移さない。型ヒントの付いた関数のうち、あらかじめ定めた部分集合に入るものだけをRustとPyO3のコードへ落とし、残りは元のPython実装のまま置く。リポジトリが掲げる契約の文は短い。確信がなければ推測せずフォールバックする。そして関数はCPythonと同等の意味でネイティブコンパイルされるか、診断とともに拒否されてPythonフォールバックに残る。

先に線を引いておく。この記事はRextioという特定のツールを推薦も評価もしない。リポジトリは自らをアルファ段階と表記しており、複数の機能に実験的という札が付いていて、確認時点のスター数は一桁だった。今プロダクションへ入れる代物ではない。この記事が関心を持つのは一つだけだ。機械が移せるものと移せないものの境界線はどこに引かれるのか、そしてその境界線が実務の判断をどう変えるのか。

1. Rextioが実際にやること - 公式文書で確認できたものだけ

まずツールの性格を正確にしておこう。Rextioは対話型のLLMへコードを投げてRustで書き直してくれと頼む類ではない。静的解析器とコード生成器で構成された決定的なツールである。Python ASTを読み、サポート範囲に入る関数だけを受け入れ、残りは診断メッセージを出して拒否する。成果物は純粋なRustプログラムではなく、ネイティブ拡張とPythonフォールバックが同居するハイブリッドパッケージだ。

実行の流れも単純だ。ソースからネイティブ候補を探し、不適格なものを拒否し、受け入れたものだけをRustとPyO3のコードへ生成し、残りにはPythonフォールバックのラッパーを作り、インポート互換のアーティファクトとしてビルドする。

python -m pip install rextio

rextio check .                      # 何がネイティブへ降り何が拒否されるかの診断のみ
rextio build . --fallback=cpython   # ハイブリッドパッケージのビルド

REXTIO_NATIVE_MODE=fallback python app.py   # 実行時にネイティブを切り純粋Python経路へ

注目すべきは三行目だ。ネイティブをいつでも切れるスイッチが最初から設計に入っている。リポジトリ文書はこれを「ネイティブは最適化であって必須要件ではない」という一文に要約する。ネイティブモジュールが無い、あるいはロードに失敗してもパッケージはPythonフォールバックで回り続ける。後でまた扱うが、このスイッチはツールを使うかどうかにかかわらず自前で実装するときも必ず作らなければならない項目である。

動作要件はCPython 3.11以上(文書上は3.14まで検証)とRust最小サポートバージョン1.83以上だ。ライセンスはMITである。リポジトリが公開したベンチマークは次のとおりだ。以下の数値はすべてリポジトリ文書に載った値をそのまま移したものであり、筆者が再現した値ではない。

2. 自動変換が原理上できないこと

Rextioがサポートしないと明記した一覧を見ると、性格がはっきり分かれる。クラスとインスタンスメソッド、動的な属性アクセス、ジェネレータ、asyncとawait、コンテキストマネージャ、可変コレクションのエイリアス変更、set[float]の反復、スター式とstar import、動的なコード実行、そしてプラグインの無い大半のサードパーティ呼び出しである。

この一覧は偶然ではない。特定のツールの未完成項目ではなく静的変換というアプローチ自体がぶつかる壁だ。各項目がなぜ壁なのかを整理すると次の表になる。

Python側の性質Rustで衝突する地点機械的な変換が不可能な理由
ダックタイピング・動的な属性アクセス静的型・トレイト解決呼び出し時点で決まるものをコンパイル時点に固定できない
ジェネレータ・コルーチン所有権を持つ状態機械一時停止の地点ごとに生きている参照の寿命を静的に証明しなければならない
可変オブジェクトのエイリアス共有借用検査器複数の名前が同じオブジェクトを同時に書き換えるコードは所有権モデルと正面衝突する
例外で流れを制御Result の返り値どの例外がどこで捕まるかを大域的に追跡しないと流れが再構成できない
GILを前提にした原子性の仮定明示的な同期GILのおかげで偶然安全だったコードは移した瞬間に競合状態になる
任意精度の整数固定幅の整数同じintでもオーバーフロー境界の挙動が異なる
浮動小数の集合のNaNハッシュと同値性の規則NaNは自分自身と等しくないため重複排除の結果が分かれる

表の最後の二行が特に実務的だ。同じ名前の型が同じ意味ではないという事実が、自動変換で最も静かに事故を作る。コンパイルも通りテストも通るのに、特定の入力でだけ値が分かれる類型である。

ここで一つ整理ができる。自動変換器が扱う範囲は見かけだけPythonで、実質的には静的型言語である部分集合だ。型ヒントが完備され、ローカル変数だけを使い、スカラと単純なコンテナだけが行き来する純粋関数。そういうコードはそもそもRustへ移しやすいコードだった。逆に移したい気持ちが切実なコード、つまり長年育ってきた業務ロジックは、たいていこの部分集合の外にある。

  • 拒否を失敗と読まないこと — ツールが関数を拒否するのは正常な動作だ。拒否せずすべてを受け入れるツールがあるなら、そちらのほうが危険である。
  • 診断メッセージこそが実際の成果物だ — rextio checkのようなコマンドの価値は変換ではなく自分のコードがどれだけ静的かを測ってくれることにある。拒否率が90パーセントなら、そのコードベースはこのアプローチの対象ではない。
  • 部分集合に合わせてコードを直した瞬間に費用が始まる — ツールを通すためにクラスを関数へほどき、ジェネレータをリストへ変えると、そのコードはすでにPythonの慣用句から遠ざかっている。その代償を計算に入れなければならない。
  • サードパーティ呼び出しは事実上の壁だ — サポート一覧に無いライブラリを一行でも呼べば、その関数はフォールバックへ降りる。業務コードでこの条件を満たす関数は思ったより少ない。

3. 「遅い」の原因から確定せよ

言語を変える決定の前に必ず通らなければならない関門がある。今遅い理由は本当に言語なのか。実務で性能問題として受け付けられる事例のかなりの部分はインタプリタの速度と無関係だ。原因別に割ってみると処方がまったく変わる。

症状・原因確認方法Rust移行の期待効果先にやること
ネットワーク・ディスクの待ち壁時計時間とCPU時間の差ほとんど無い並行化・コネクションプール・バッチ化
N+1クエリリクエストあたりのクエリ数のログ無い(むしろ悪化しうる)結合・プリフェッチ・キャッシュ
直列化・逆直列化ペイロードのサイズとパース時間を分離して測定中程度(パーサの交換でも相当回収できる)フォーマット・カラム削減・ストリーミング
アルゴリズムの計算量入力サイズを2倍にして時間の増加率を観察定数倍だけ改善、次数はそのままデータ構造の交換
GILの競合スレッド数を増やしてもスループットが伸びない大きい(ただし原因の確定が先)プロセス分離・free threadingの検討
インタプリタのオーバーヘッド自己時間の上位関数が純粋なPythonループ大きい — ここが唯一の正当な区間ホットパスを特定してから拡張モジュール

確認の順序はプロファイラが先だ。累積時間ではなく自己時間の基準で並べ替えて初めて、実際にCPUを燃やしている地点が見える。

# 自己時間の基準で並べ替えて初めて実際の焼却地点が見える
python -m cProfile -o prof.out run_workload.py

# 対話型ビューアで sort tottime を入力した後 stats 20
python -m pstats prof.out

その次がもっと重要だ。ホットパスが全体に占める比率を測り、改善の上限を先に計算する。この計算を飛ばすと、数週間かけて一桁の改善を得ることになる。

# ホット関数が全体のp比率を占め、その部分がs倍速くなったときの全体の改善幅
def upper_bound(p: float, s: float) -> float:
    return 1.0 / ((1.0 - p) + p / s)

print(upper_bound(0.20, 50))   # 1.2437...  -> 全体20%の短縮が上限
print(upper_bound(0.70, 50))   # 3.2051...  -> ここから投資する価値が出てくる
print(upper_bound(0.20, 1000)) # 1.2496...  -> 無限に速くしても1.25倍を超えられない

三行目が結論だ。ホットパスの比重が低ければ、その部分を無限に速くしても全体は速くならない。実務の閾値を一つ決めるならこうだ。自己時間の上位関数の合計が全実行時間の40パーセント未満なら言語の移行を検討対象から外す。60パーセントを超えれば検討する価値があり、80パーセントを超えればたいていやったほうがよい。

4. 実務の正解は全面移植ではなくホットパスの拡張モジュール

ここまで来たら選択肢は二つだ。アプリケーション全体をRustで書き直すか、ホットパスだけをネイティブ拡張モジュールへ切り出して残りはPythonのまま置くか。結論から言えば大半の組織では二番目が正解であり、一番目が正当化される条件は非常に狭い。

理由は境界の費用にある。Pythonとネイティブコードの間には越えるたびに値を変換する費用が付く。この費用は関数の呼び出しごとに発生し、移すデータが複雑なほど大きくなる。だから設計を誤った拡張モジュールは純粋なPythonより遅くなる。実際にRextioもこの問題を設計へ明示的に反映し、コンテナはネイティブ境界を越えられないようにして、int、float、bool、str、Noneのような不変のスカラだけをフォールバック関数へ渡すよう制限している。境界を繰り返し行き来する関数はそもそもフォールバックへ降格するという規則まで置いている。

この制約から拡張モジュール設計の原則がそのまま導かれる。

  • 要素の単位で呼ばない — 100万個の要素を100万回呼べば境界の費用が計算の費用を圧倒する。配列一つを丸ごと渡して一度だけ呼ぶ。
  • 境界を越えるデータを単純に保つ — 入れ子の辞書やユーザー定義のオブジェクトは変換の費用が大きい。数値の配列、バイト列、平坦な文字列のリストが理想的だ。
  • コールバックを渡さない — ネイティブコードが再びPython関数を呼べば、要素ごとに境界を往復する。この構造が出てきたら境界の引き方を誤っている。
  • 境界を状態ではなく純粋関数にする — ネイティブ側に長く生きる可変の状態を置くと、所有権の問題とスレッド安全の問題が同時に付いてくる。
  • インタフェースが頻繁に変わる場所に境界を置かない — 毎週シグネチャが変わる関数をネイティブへ降ろせば、毎週ビルドマトリクスを回し直すことになる。
  • 純粋Pythonの実装を消さない — 二つの実装を並べて維持する費用より、戻せなくなる危険のほうがはるかに大きい。

同じ問題を別の言語の組み合わせで扱った議論はGoからRustへの移行のほうに整理してある。あちらは二つのコンパイル言語の間の選択なので判断の軸が違うが、共存パターンとアンチシグナルはそのまま重なる。

5. PyO3とmaturin - 境界をコードで描く方法

ホットパスを切り出すと決めたなら、実際の道具はPyO3とmaturinだ。PyO3はRustとPythonをつなぐバインディングで、maturinはその成果物をPythonのホイールとしてビルドしてくれる。以下はPyO3公式リポジトリの基準で最新リリースである0.29系列の宣言的モジュール構文だ。PyO3 0.29はCPython 3.9以上をサポートし、Rust最小サポートバージョンは1.83である。

# Cargo.toml
[package]
name = "hotpath"
version = "0.1.0"
edition = "2021"

[lib]
name = "hotpath"
crate-type = ["cdylib"]

[dependencies]
pyo3 = "0.29.0"

// src/lib.rs
#[pyo3::pymodule]
mod hotpath {
    use pyo3::prelude::*;

    /// 配列を丸ごと受け取って一度に処理する。
    /// 要素ごとに呼び出さないことがこの設計のすべてだ。
    #[pyfunction]
    fn clip_and_scale(values: Vec<f64>, lo: f64, hi: f64, k: f64) -> PyResult<Vec<f64>> {
        Ok(values
            .into_iter()
            .map(|v| v.clamp(lo, hi) * k)
            .collect())
    }
}

maturin new -b pyo3 hotpath   # プロジェクトの雛形を生成
cd hotpath
maturin develop               # 現在の仮想環境へ直接インストール(反復開発用)
maturin build --release       # target/wheels に配布用のホイールを生成

Python側ではネイティブ実装と純粋実装を同じ名前で包みつつ、戻せるように作る。先に見た環境変数のスイッチを自前で作る形だ。

# myapp/kernel.py
import os

from myapp import kernel_py   # 純粋Pythonの元実装

_impl = kernel_py

if os.environ.get("MYAPP_NATIVE", "1") != "0":
    try:
        import hotpath as _native
        _impl = _native
    except ImportError:
        pass   # ホイールの無いプラットフォームでもそのまま動作する

clip_and_scale = _impl.clip_and_scale

ここでImportErrorを飲み込むのが肝だ。ネイティブ拡張の無いプラットフォームでもパッケージがインストールされ動作してこそ配布が単純になる。この構造を備えておけば、性能の回帰が疑われるときに環境変数一つで二つの実装を比較でき、事故が起きたときに再配布なしで戻せる。

6. どこまでネイティブへ降ろすか - 判断表

「この関数をネイティブへ降ろそうか」は勘で決める問題ではない。以下の六つの条件を順に通し、一つでもいいえが出たら降ろさないという規則が実務で最もよく持ちこたえる。

確認項目通過の閾値いいえのときの処方
全実行時間に占める比重自己時間の基準で20パーセント以上別の場所を先に見る
呼び出しあたりの作業量1回の呼び出しでミリ秒の単位以上の計算バッチ単位でまとめて呼び出し回数を減らす
境界を越えるデータの形スカラ・平坦な配列・バイト列インタフェースを先に平坦にする
インタフェースの変更頻度四半期あたり1回以下設計が固まるまで先送りする
Rustを読んで直せる人員2名以上人から確保する。1名なら組織の負債だ
純粋Pythonの代替の維持常に維持 + 戻しスイッチ戻せないならまだ入れない

五番目の項目がよく無視される。拡張モジュールはそれを作った人が去った瞬間にブラックボックスになる。Python開発者だけが残ったチームでRustの拡張モジュールにバグが出れば、選択肢は「直せる人を探す」と「純粋Pythonへ戻す」の二つしかない。六番目の項目を守っておけば後者が30秒の作業になり、守っていなければ数週間の事故になる。

逆に全面移植を検討してもよい条件も整理しておこう。四つをすべて満たすときだけだ。成果物そのものが配布の単位となるツールかライブラリのコアであること、外部インタフェースが狭く安定していること、実行時間の大半がCPUの計算であること、そしてチームにRustを主言語として扱う人員がすでにいること。

7. Rustで書き直されたツールが実際に証明したこと

Pythonのエコシステムでは、Rust再実装の成功事例としてよく挙げられるものがある。それぞれの公式文書が実際に主張している数値だけを移すと次のようになる。

プロジェクト公式資料が明かした内容対象の領域
ruff既存のリンタ(Flake8)とフォーマッタ(Black)の比で10〜100倍速いとリポジトリが明記。Rustで記述、MIT静的解析ツール
uvキャッシュ無しでpipおよびpip-toolsの比で8〜10倍、ウォームキャッシュで80〜115倍。仮想環境の生成はpython -m venvの比で約80倍、virtualenvの比で7倍パッケージ管理ツール
pydantic公式文書が、中核の検証ロジックがRustで書かれており、その結果Pythonで最も速いデータ検証ライブラリの部類に入ると記述ライブラリのコア
CPython自体Rust for CPython計画が3.16を目標に拡張モジュール一つをRustで実装する概念実証を進め、PEPを準備中だと公式ブログが告知インタプリタの内部

この一覧で倍率そのものより重要なのは共通点だ。四つとも業務アプリケーションではない。開発ツールか、ライブラリの検証コアか、インタプリタの内部である。三つの性質を共有する。

  • インタフェースが狭く長く安定している — リンタの入力はソースファイルで、出力は診断の一覧だ。この契約は何年もそのままである。
  • 実行時間の大半がCPUの計算だ — パース、規則のマッチング、依存の解決はすべてインタプリタが燃やしていた時間である。
  • 配布の単位がすでにバイナリのホイールだ — 利用者はソースが何の言語かを知る必要がない。プラットフォーム別のホイールさえあればよい。

逆に言えば、この三条件を満たさないコードに同じ結果を期待する根拠は無い。リクエスト一つでデータベースを三往復するウェブアプリケーションは、三条件のすべてで反対側にいる。成功事例を引用するときは、その事例がどの領域に属するのかを併せて見なければならない。

なおAIエージェントで大規模なコードベースを丸ごとRustへ移す試みも2026年に複数出てきたが、何が証明され何が証明されなかったのかはGitをRustへ再実装した試みで別に扱った。要旨は同じだ。移されたということと検証されたということは別の文である。

8. 反対側の費用 - 学習曲線・ビルド時間・エコシステムの空白

移行の議論はたいてい利得だけを計算して終わる。反対側の費用は導入の時点ではなく6か月後から請求されるからだ。項目別に割ってみよう。

8.1 ビルド時間は測定された問題だ

Rust公式ブログが公開した2025年のコンパイラ性能調査の結果は3,700件以上の回答を含んでおり、全般的な満足度は10点満点で6点と報告された。注目すべき数値は次のとおりである。

  • Rustの使用をやめた回答者の約45パーセントが、やめた理由の一つとして長いコンパイル時間を挙げた。
  • 55パーセントが、コードを直した後の再ビルドに10秒以上待つと答えた。ボトルネックは、ワークスペースの変更が誘発する不要な再ビルド、遅いリンク段階、単一クレート内部の増分コンパイルの三つに整理された。
  • 約33パーセントがIDEのインライン注釈を待つことを大きな障害とし、35パーセント以上がIDEとCargoが互いを塞ぐ問題を大きな問題だと答えた。
  • CI利用者1,495名のうち約25パーセントがCIビルドの性能を大きな問題として挙げたが、そのうち約36パーセントはCIでキャッシュをまったく使っていなかった。
  • 全回答者の約42パーセントは、ビルド性能を改善する手段を一つも試したことが無いと答えた。

最後の二項目はひっくり返して読む価値がある。不満のかなりの部分は、まだ手を付けていない余地から出ている。キャッシュ、リンカの交換、ワークスペースの分割といった基本の措置をしないまま「Rustは遅い」と結論づければ誤った結論になる。ただしチームにその措置をやる人がいなければ実質の費用はそのままだ。

8.2 配布が一軸増える

純粋なPythonパッケージはホイール一つで終わる。ネイティブ拡張が付いた瞬間にプラットフォーム × アーキテクチャ × Pythonバージョンの積の分だけビルドが必要になる。安定ABIを使えばPythonバージョンの軸を減らせるが、代わりに使えるAPIが制限される。ここへクロスコンパイル、署名、社内ミラーへの登録が付いてくる。この作業は一度作れば終わりではなく新しいPythonバージョンが出るたびに繰り返される。

8.3 人が最も高い

  • 読める人と直せる人は違う — 所有権と寿命のエラーに出会って自力で解決できて初めて、直せる人である。
  • オンコールのローテーションへ入らなければならない — 深夜にそのモジュールが飛んだとき対応できる人員が一人なら、そのモジュールは単一障害点だ。
  • レビューのボトルネックが生じる — Rustコードをレビューできる人が一人なら、その人の休暇がそのまま配布の停止になる。
  • 採用の条件が変わる — Pythonのポジション一つがPythonとRustを併せて要求するポジションになれば、候補者の母集団が減り期間が延びる。

8.4 エコシステムの空白

Python側にすでにあるものがRust側に無い、あるいはあっても成熟度が低い場合がある。ドメイン特化の数値ライブラリ、特定ベンダのクライアントSDK、社内標準のロギング・トレーシング層といったものだ。ホットパスだけを切り出すアプローチが有利な理由はここにもある。境界を狭く取れば、必要なRustライブラリもその分少なくなる。メモリ安全性を根拠に再実装を推し進める主張とその反論はメモリ安全性の絶対主義をめぐる論争で別に整理した。

9. 生成されたRustコードをどう検証するか

ツールが作ったコードであれ人が書いたコードであれ、二つの実装が本当に同じ答えを出すのかは別に証明しなければならない。コンパイルの成功は何も保証しない。実行可能な形へ整理すると三段階だ。

9.1 差分テスト - 同じ入力、二つの実装

# tests/test_parity.py
import math
from hypothesis import given, settings, strategies as st

from myapp import kernel_py            # 純粋Pythonの元実装
import hotpath                          # ネイティブ実装

FINITE = st.floats(allow_nan=False, allow_infinity=False, width=64)

@settings(max_examples=1000)
@given(st.lists(FINITE, max_size=4096), FINITE, FINITE, FINITE)
def test_same_output(values, lo, hi, k):
    if lo > hi:
        lo, hi = hi, lo
    expected = kernel_py.clip_and_scale(values, lo, hi, k)
    actual = hotpath.clip_and_scale(values, lo, hi, k)
    assert len(expected) == len(actual)
    for a, b in zip(expected, actual):
        assert math.isclose(a, b, rel_tol=1e-12, abs_tol=0.0)

浮動小数を比較するとき許容誤差を置いた瞬間に、「同等」ではなく「近似」を検証しているという事実を文書へ残さなければならない。会計や精算のように最後の桁が意味を持つドメインなら、許容誤差を置かずに整数または十進の型へ計算を移すほうがよい。

9.2 境界値は無作為には出てこない

プロパティテストは幅を広げてくれるが、最も危険な入力はたいてい引かれない。固定の一覧として別に管理する。

EDGE_CASES = [
    [],                       # 空の入力
    [0.0], [-0.0],            # 0と負の0はビットが違う
    [float("inf"), float("-inf")],
    [float("nan")],           # 自分自身と等しくない。ソートと重複排除が分かれる
    [1e308, -1e308],          # オーバーフローの直前
    [1.0] * 1_000_000,        # 境界を越える複製の費用が現れるサイズ
]
  • 整数のオーバーフロー — Pythonの整数は任意精度で、Rustのi64は固定幅だ。リリースビルドではオーバーフローが巻き戻って静かに誤った値になる。移す関数に大きな整数が入りうるか必ず確認する。
  • 剰余演算の符号 — Pythonの%は除数の符号に従い、Rustの%は被除数の符号に従う。-7 % 3はPythonで2、Rustで-1である。Pythonと同じにするにはrem_euclidを使う。
  • ソートの安定性 — 二つの要素のキーが同じとき元の順序が保たれるかを確認する。安定性が違えば結果のリストの順序が分かれる。
  • 辞書の挿入順序 — Pythonの辞書は挿入の順序を保つ。Rustのハッシュマップはそうではない。順序に依存する消費者がいれば事故になる。
  • ユニコードの長さ — Python文字列の長さはコードポイントの数で、Rustのlen()はバイトの数だ。スライスのインデックスをそのまま移すと壊れる。
  • 例外の型とメッセージ — 呼び出し側が例外の型で分岐しているなら、その型まで同じでなければならない。メッセージの文字列に依存するコードが無いかも確認する。

9.3 戻しの経路を配布の前に試験する

前の節で作った環境変数のスイッチは作っておくだけでは終わらない。リリースごとに純粋Pythonの経路で全テストをもう一度回して初めて、その経路が生きていることが保証される。実務でよく見る失敗は、スイッチを作っておいて1年間使わず、いざ必要な瞬間に純粋実装のインタフェースがすでにずれている状況だ。

検証の項目方法通過の基準
結果の同等性差分テスト + プロパティテスト無作為1,000件以上で不一致0件
境界値固定の一覧 + 二言語の規則の差の点検一覧の全件通過、例外の型まで一致
性能代表ワークロードのベンチマーク3回の中央値目標の倍率に届かなければ境界設計を再検討

10. GILが消えつつあるという変数

並列性のためにRustを検討している場合は、前提が変わりつつある点を計算に入れなければならない。CPythonは3.13からGILを切ったfree threadingビルドを提供する。ただし無料ではない。公式文書は、free threadingビルドが既定のビルドよりオーバーヘッドがあり、pyperformanceの基準で平均のオーバーヘッドがmacOS aarch64で約1パーセント、x86-64 Linuxで約8パーセントの範囲だと述べている。

ここへ、拡張モジュールを作る側が必ず知っておくべき条項がもう一つある。公式文書は拡張モジュールを持つ一部のサードパーティパッケージがfree threadingビルドで準備できていない場合があり、GILを再び有効化すると記している。free threadingのサポートが明示されていないC-APIの拡張モジュールをインポートすると、GILが自動的に再び有効化され警告が出力される。

  • 自分の拡張モジュールが他人の並列性を殺しうる — サポートを宣言していない拡張が一つあるだけで、プロセス全体のGILを蘇らせる。拡張モジュールを配布するなら、この宣言は選択肢ではない。
  • 並列化が目的なら順序を変えてみる価値がある — 言語を変える前に、free threadingビルドで既存のコードがどう回るかを先に測るほうが費用が少ない。
  • 単一スレッドのオーバーヘッドはワークロードごとに違う — 上の範囲はベンチマークスイートの平均だ。自分のワークロードで直接測らなければならない。
  • インタプリタ自体もRustを取り入れつつある — Rust for CPython計画は3.16を目標に拡張モジュール一つをRustで実装する概念実証を進め、PEPを準備中だと公式ブログが明かした。長期的には二つの言語の接点は広がる。

11. 導入の可否を判断する手順

最後に移せる形へ整理する。この順序をそのまま踏めば、たいてい3段階か4段階で結論が出る。

  1. 代表のワークロードを一つ固定する — 実際のプロダクショントラフィックから出たものでなければならない。合成のベンチマークは結論を楽観的にする。
  2. 壁時計時間とCPU時間を分けて測る — 二つの差が大きければ原因は待ちであり、言語の移行はここで終わる。
  3. 自己時間の基準で上位の関数を抜き出す — 累積時間で見ると呼び出しスタックの上のほうしか見えない。
  4. 上位関数の合計の比重で上限を計算する — 40パーセント未満ならここで中断する。別の場所を直すときだ。
  5. アルゴリズムとデータ構造を先に見る — 次数を下げる変更が残っているなら、それが常に先だ。
  6. すでにCへ降りている部分かを確認する — 数値ライブラリの内部で回っている時間なら、持ち帰る余地はほとんど無い。
  7. 境界の候補となる関数のインタフェースを平坦にする — この作業はRust無しで、純粋なPythonの状態で先に終える。
  8. 静的解析ツールで部分集合への適合度を測ってみる — 拒否率が高ければ自動変換は諦め、手動の移植だけを検討する。
  9. 最も比重の大きい関数を一つだけ移して実測する — 一つだ。複数を同時に移すと何が効いたのか分からない。
  10. 差分テストとフォールバック経路を備えてから配布する — 戻しのスイッチが動作することを確認してからだけ出す。
  11. 運用の指標で測り直す — ベンチマークではなく実際のレイテンシの分布で確認する。テールのレイテンシが減っていなければ別の原因が残っている。
  12. 効果が無ければ戻す — すでに作ったものが惜しいという理由で維持することが、最も高くつく選択だ。

結論: ツールは境界を見せるだけで、境界を決めてはくれない

Rextioのようなツールが実際に提供する最大の価値は、変換そのものではなく診断である可能性が高い。自分のコードベースの何パーセントが静的に固定できる形なのか、どの関数がなぜ拒否されるのかを教えてくれるだけでも判断の材料になる。逆に、ツールが作った成果物をそのままプロダクションへ入れるシナリオは、少なくともアルファ段階のツールについては検討の対象ではない。

この記事で繰り返した文を一つに縮めるとこうだ。全部書き直すことと何もしないことの間に実務の答えがあり、その答えは境界をどこに引くかで決まる。境界をうまく引けば、コードの5パーセントを移して性能問題の大半を解決し、残りの95パーセントはPythonの生産性をそのまま享受する。境界を誤って引けば、二つの言語の短所だけを集めたシステムになる。ビルドは遅く、直せる人は一人で、戻すこともできない状態だ。

そして順序をひっくり返さないでおこう。プロファイリングが先で、アルゴリズムが次で、言語が最後だ。この順序を守れば、たいていの場合は言語まで行く必要が無いという事実を知ることになるが、それがこの検討の最もありふれた結論であり、最も安価な結論である。
