How to Choose a Web Hosting Type

A decision framework rather than a vendor comparison - what you serve decides the type

2026-07-29 Tech & IT

Introduction: which hosting is best is the wrong question to ask first

Answer that question with a company name and you will almost certainly be wrong, because something is missing from it. If you pick a host without first stating what the thing you are building actually sends out, you discover what that type cannot do only after you have committed to it. The opposite error is just as common. People build a site that needs to hand out a handful of files, rent an entire server out of habit, and unknowingly sign up to maintain that server for life.

So this article does not tell you which company to use. It ranks nothing, recommends no provider and contains no affiliate links. It also quotes no prices. Prices and free allowances change often enough that any figure becomes misinformation shortly after the date it was checked. Instead it covers only the parts that do not change: what each type can and cannot do structurally, and the operational load that comes attached to the choice.

There is one question this article tries to answer. Am I serving files, or am I serving computation? Start there and most candidates eliminate themselves. Every technical fact and limit below was read directly from the relevant official documentation and IETF RFCs on 29 July 2026, and anything that could not be confirmed was left out rather than guessed. Example domains are written as example.com and example addresses as 192.0.2.1 throughout.

1. Four questions that decide the type

Hosting type is decided by requirements, not by taste. And those requirements compress almost entirely into four yes-or-no questions. Answer them in order and the field narrows to one or two candidates.

  • Question 1 — Is there code that must run on the server? If something has to be computed per request, or the result must differ according to the contents of the request, the answer is yes. JavaScript that runs in the browser does not count here.
  • Question 2 — Is there state to store? Accounts, login sessions, orders, comments, view counters — anything the server has to remember means yes. If any screen differs per visitor, you are usually caught by this one.
  • Question 3 — Do visitors upload files? Images, documents or video uploads mean yes. Uploads bring not only storage but a separate cluster of problems: validation, size limits and handling of hostile files.
  • Question 4 — Are you handling data that must not be public? Personal data, payment details or private documents mean yes. Remember that a file placed on static hosting is, in principle, open to anyone who knows its address.

MDN Web Docs draws the line between a static site, which returns the same hard-coded content whenever a particular resource is requested, and a dynamic site, where part of the response is generated only when needed. The four questions above are simply that distinction restated in operational language.

2. What the five types really are - who does what for you

The type names sound like marketing vocabulary, but the actual difference is simple. It is entirely a question of how far up the stack, from operating system to application, somebody else takes responsibility. The standard definitions of cloud service models live in NIST Special Publication 800-145. That document defines IaaS as provisioning processing, storage and networking on which the consumer can deploy and run arbitrary software including operating systems, and PaaS as deploying consumer-created applications using languages and tools supported by the provider while not managing the underlying infrastructure.

  • Static hosting — pre-built files are distributed as they are. You do not run a server process, so no server process of yours can crash or be compromised. In exchange there is no way to compute anything at request time.
  • Shared hosting — one machine is divided among many customers, with a web server, a language runtime and a database already installed and offered to you. It is normally driven through a control panel. Low freedom, less hands-on work.
  • VPS — you receive a whole virtualised machine. Everything above the operating system is yours. The freedom is maximal, and the list of chores grows in exact proportion to it.
  • Cloud (IaaS) — the same freedom as a VPS, plus the ability to create, destroy and scale resources through an API. You can build autoscaling and multi-zone designs, but designing and maintaining that structure comes along with it.
  • PaaS — you push code and the platform owns the runtime environment. You are freed from operating system patching and runtime upgrades, but you must follow the platform way of doing things, and that adherence becomes your migration cost.

3. The real limits of static hosting - what the official docs put in writing

Static hosting is not unlimited. What differs is where the limits bite. GitHub Pages publishes an official usage limits page, and reading it makes clear what you should be checking anywhere. Below is what that documentation stated as of 29 July 2026.

ItemWhat the official documentation saysNatureWhat it means in practice
Source repository sizeRecommended limit of 1 GBRecommendationDo not accumulate original images and video in the repository
Published site sizeMay be no larger than 1 GBCeilingMedia needs a design that keeps it in separate storage
BandwidthSoft limit of 100 GB per monthSoftNot an instant cut-off, but sustained excess draws attention
BuildsSoft limit of 10 builds per hourSoftThe habit of building on every commit hits this first
Server-side codePHP, Ruby, Python and similar are unsupportedStructural constraintForm handling and authentication must live somewhere else
Commercial useNot allowed as free web hosting for running an online business or e-commerce siteTermsOnce a revenue model appears, the type must be reconsidered

The last two rows deserve the most attention. Whether something is technically possible and whether it is permitted by the terms are different questions. There is no technical reason a commerce site cannot be made of static files, but whether that matches the intent of a free offering is a separate matter. The moment a personal site starts carrying a revenue model is the moment to re-examine the type.

One more habit worth forming: distinguish soft limits from hard limits. A soft limit does not sever service the instant you cross it, but sustained excess invites intervention. A hard limit changes behaviour the moment you cross it. Remember both simply as the limit and you will miss the one that actually causes an outage.

4. The character of free tiers - what happens when you hit the ceiling

Most static and PaaS-style platforms offer a free tier. There is a common mistake in comparing them: looking only at the numbers. What matters is the behaviour when the ceiling is reached, and that differs from platform to platform.

  • Limits are designed per plan — the Cloudflare official limits documentation presents files per site, maximum size of a single asset, builds per month and custom domains per project in per-plan tables, and states explicitly that build limits depend on your plan.
  • The behaviour at the ceiling is the real difference — Netlify official documentation explains that notifications go out at fifty, seventy-five, ninety and one hundred percent of a metered feature, and that at one hundred percent new builds are disabled and sites are paused. It also notes that already deployed sites continue to be served to visitors.
  • Limits are split by feature — the Vercel official limits documentation defines deployments per day, maximum build time per deployment, uploadable source file size and domains per project separately, and per plan.
  • Invisible limits hurt operations more — the same document also states that runtime log retention differs by plan. When something breaks, how many hours of logs you can still see matters far more urgently than a storage ceiling.
  • Record figures together with the date you checked them — every item above was read from the respective provider official limits documentation on 29 July 2026. Such values are adjusted without notice, so there is no safer method than opening those pages again immediately before deciding.

In short, the criterion for choosing a free tier is predictability rather than generosity. Does exceeding the allowance lead to a charge, to a service interruption, or merely to a warning? Those three produce completely different situations on the day something goes wrong.

5. Signals that static will not do - when to change type

Treating static as the default does not mean forcing static where it does not belong. If even one of the signals below is definite, going straight to a type with server logic is cheaper than bolting extras onto a static site.

  • Computation is needed at request time — search, filtering, recommendations, stock checks and anything else whose result must vary by visitor and moment. A very small dataset can be handled in the browser, but that ceiling arrives quickly.
  • A secret must stay on the server — external API keys or payment integration secrets that must never reach the browser make static alone impossible. A value embedded in a static file is not hidden.
  • There are logins and permissions — showing different things to different users, and preventing access to someone else data, requires verification on the server side.
  • Visitors upload files — the upload itself is not the hard part, what follows is. Size limits, format validation, storage location, visibility scope and hostile file handling arrive as a bundle.
  • Real-time behaviour is required — chat, notifications and collaborative editing all presuppose a process that stays resident and holds connections open.
  • Content changes far too often — a static site rebuilds and redeploys whenever content changes. Once updates arrive every few minutes, build frequency limits and deployment latency become the immediate problem.

Conversely, if all six are no, very little reason remains to rent a server. Because I might need it later is not a reason. If you need it later, move then. Moving from static to another type is far easier than the reverse.

6. What happens the moment you rent a server - the expensive part is not money

Choosing a VPS or IaaS is not buying a server, it is signing up for server operations as a recurring job. The fee arrives as a monthly invoice; this work never does. That makes it easy to postpone, and the postponed amount is paid in full on the day of an incident. Itemised, it looks like this.

  • Operating system and package patching — a security update only counts once it is applied. Turn on automatic updates and you instead accept unannounced restarts and compatibility surprises. Either way, somebody has to look at it regularly.
  • Firewall and access control — every open port is attack surface. Narrow administrative access to key-based authentication, and simply never start services you do not need.
  • Certificate renewal — covered in detail below, but a renewal scheme is only complete when it also includes a way to learn that the automation failed.
  • Backups and restore drills — taking the backup is half the job and bringing it back is the other half. A backup whose restore has never been rehearsed is not a backup, it is a file named backup.
  • Monitoring and alerting — a full disk that stops logging, or a dead process nobody noticed, is the most common form of long-running outage.
  • Log management — without logs you cannot determine the cause of an incident, and neglected logs fill the disk. Rotation interval and retention period have to be decided in advance.
  • Incident response — if you have not decided in advance what to do first when your server starts being used as someone else tool, the judgement made that night is usually the worst available.

These seven items occur almost identically whether the site has ten visitors a day or a hundred thousand. That they do not shrink with scale is the crux. Which is why running your own server for a small site tends to be the worst possible fixed cost relative to traffic. The fundamentals of the server itself and its hardening are covered separately in Linux server security and web server performance tuning.

7. Domains and DNS - the layer that survives every change of type

Whatever hosting type you pick, the domain and DNS stay where they are. Understanding this layer therefore pays off most when you later switch types. There are not many records you need.

RecordWhat it doesSpecification basisWatch out for
AMaps a name to an IPv4 addressDefined in RFC 1035 as a 32-bit internet addressIf the address changes, you must update it yourself
AAAAMaps a name to an IPv6 addressDefined in RFC 3596 as a type holding a single IPv6 addressFrequently forgotten after IPv4 is configured
CNAMEMakes a name an alias of another nameDefined in RFC 1035 as specifying the canonical nameCannot coexist with other records at the same name
TXTCarries arbitrary text for ownership proof, mail policy and similarDefined in RFC 1035 as one or more character stringsMany purposes pile onto one name and become unmanageable
TTLHow long a response may be cachedRFC 2181 defines TTL as a maximum, not a mandatory, time to liveNot lowered before a cutover, the switchover drags on

The point every beginner collides with at least once is the rule that you cannot put a CNAME at an apex domain. The reason is explicit. RFC 1912 states that a CNAME is not allowed to coexist with any other data, and section 10.1 of RFC 2181 requires that a name carry either a single CNAME or only non-CNAME records. Yet the top of a zone such as example.com necessarily contains SOA and NS records. Placing a CNAME there is therefore a specification violation, and depending on the implementation the NS records can be ignored, escalating into the whole domain failing to resolve.

Workarounds are well established. Several DNS providers offer the same effect under the names ALIAS or ANAME, or through CNAME flattening. Cloudflare official documentation explains that flattening finds the address the CNAME ultimately points to and returns that address instead. In other words only the surface behaviour is CNAME-like; the response actually sent is an address record. GitHub official documentation likewise instructs that an apex domain use one of ALIAS, ANAME or A, while a subdomain uses CNAME.

; excerpt from the example.com zone - all values are illustrative
example.com.        300   IN  A      192.0.2.1
example.com.        300   IN  AAAA   2001:db8::1
www.example.com.    300   IN  CNAME  <name-given-by-your-host>.example.net.
example.com.        300   IN  TXT    v=spf1 -all

; a CNAME at the apex (example.com) violates the specification.
; if you need that effect, use ALIAS/ANAME or CNAME flattening.

Lowering the TTL well before a cutover is the standard move. As RFC 2181 makes clear, TTL is a maximum time to live rather than a mandatory one, so lowering it does not guarantee immediate propagation. It is still incomparably better than switching over with a day-long TTL still in place. The fastest way to see the real state is to ask directly.

# check what address the name resolves to
dig +short example.com A
dig +short www.example.com CNAME

# check which server answers and what headers come back
curl -sI https://<domain-to-check>/ | head -n 20

8. HTTPS - certificates are short and renewal must be automatic

HTTPS is no longer optional. What matters is less how you obtain a certificate than how you keep it alive automatically. The issuance procedure itself is already covered step by step in issuing and applying a free SSL certificate, so this section covers only the parts that bear directly on choosing a hosting type.

  • Validity is short — the Let's Encrypt official FAQ states that standard certificates are valid for ninety days, and that a short-lived option valid for six days also exists. It also states that these lifetimes cannot be adjusted and that there are no exceptions.
  • Renew with margin, not at the edge of expiry — the same document recommends renewing ninety-day certificates every sixty days and short-lived ones every three days. The point is to leave room to retry after a failure.
  • Manual renewal does not survive — RFC 8555, the ACME standard, states that the protocol exists to automate verification and issuance, and notes that the absence of standardised mechanisms had been an obstacle to the wide deployment of HTTPS. A plan to honour a ninety-day cycle by hand will eventually break.
  • Spread renewal times out — the same FAQ asks that ACME clients perform routine renewals at random times rather than at a fixed hour, because everyone converging on midnight creates load on the service side.
  • The type determines whether this chore exists at all — static hosting and PaaS generally handle issuance and renewal on the platform. On a VPS or IaaS the whole item becomes your operational work. GitHub official documentation also notes that enabling HTTPS on a custom domain can take time to become available.

Even with automatic renewal in place, you have done only half the job if there is no way to detect a failure. You need an alert on the outcome of the renewal job, or at minimum a routine that checks the expiry date periodically.

# check the validity window of the certificate currently being served
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -dates

9. Switching costs - where migration actually becomes hard

The most underestimated factor in a hosting decision is the cost of leaving. Getting in is easy for everyone; only on the way out does it become visible where you were tied down. The ties are generally in four places.

  • The domain registrar — transfers involve unlocking, authorisation codes and waiting periods. Attempted for the first time under pressure, something will go wrong.
  • Whoever operates your DNS — having the registrar and DNS provider be the same company is convenient, but it also increases how much must move at once. Keeping them separate makes cutovers far smoother.
  • Data — for anything held in a managed database or a platform-specific store, the export format and the reload time are the migration cost.
  • The build pipeline — the more you depend on platform-specific configuration files, platform-specific environment injection and platform-specific redirect syntax, the more the move becomes a rewrite rather than a copy.
Where you get tiedWhy migration becomes hardHow to reduce it in advance
DomainTransfer procedure, waiting period and auth codes interactKeep registrar and hosting separate, keep contact details current
DNSRecords are scattered and nobody knows what each one doesKeep the record list in a file, lower TTL before a cutover
DataProvider-specific stores are hard to export in a standard formatProduce standard-format exports regularly and rehearse restores

Runtime versionThe offered version is pinned and the upgrade path is blockedCheck the supported-version policy at selection time

In short, lock-in is created by design, not by the contract. Prefer whatever is closest to a standard, and use platform-specific features only when the benefit is clearly larger than the eventual rewrite. The habit of keeping builds and deployments reproducible in a standard way connects directly to the material in CI/CD automation.

10. The operations checklist - work that remains regardless of type

Some items never disappear entirely, whichever type you choose. They only shrink. The eight below are the list on which you should establish who is doing each one before you decide.

  • Backup scope — write down what gets backed up. Content, database, configuration files, certificates, and the sources that produced all of them.
  • Backup location — at least one copy somewhere physically distinct from the original. Keep everything in one account, one provider and one region and a single incident takes it all.
  • Backup frequency — decide by how much time you can afford to lose in an incident. If losing a day is tolerable, daily; otherwise more often.
  • Restore drills — actually bring it back on a set schedule. An untested restore procedure is an unverified procedure being run for the first time on the day of the incident.
  • Automatic certificate renewal and failure alerts — automating renewal and detecting failure are two different jobs. You need both.
  • Availability monitoring — you need something outside checking in periodically. Watch only from inside and a network cut produces no signal at all.
  • Access logs — record who requested what and when, and fix a retention period and rotation interval. Logs cannot be created after the incident.
  • Change history — where configuration and content changes get recorded. If any change cannot be reverted, fix that first.

Apply this list per type and the real weight of the choice becomes visible. On static hosting, backups, restores and change history converge almost entirely into source control, while certificates and availability belong to the platform. On a VPS all eight are yours. Building the same site involves a different number of jobs. Backup design itself is set out separately in cloud backup configuration.

Conclusion: no need to frighten anyone, and no need to pretend it is easy

Choosing web hosting is not difficult. It just has an order. Open a vendor comparison table first and it is hard; decide what you are sending out first and the field usually narrows to one or two.

  • If you are only sending files, static is the default — with server logic, state, uploads and private data all answering no, there is almost no reason to rent a server.
  • The cost of renting a server is operations, not the fee — patching, firewalls, certificates, backups, monitoring, logs and incident response occur almost independently of visitor numbers.
  • Judge a free tier by its character, not its numbers — whether hitting the ceiling means a warning, a stop or a charge, and what the acceptable-use clause says, is what determines the real risk.

One last word on posture. There is no reason to frighten a beginner, and no reason to pretend that anyone can do this easily. What is needed is precise knowledge of the conditions and burdens attached to each choice, and those conditions are written in official and standards documentation rather than in advertising. Those documents also change. That is why no prices appear in this article, and why every figure that does appear carries the date it was checked.
