値がひとつもない型はなぜ必要か

発散する式に型を与えること、そして推論の既定値を変えることの重み

2026-08-28 開発・インフラ

序論: 時間がかかったというその機能を、すでに使っていた

Rust で何かを作ったことがあるなら、こういう関数を一度は書いたはずだ。

fn bail(msg: &str) -> ! {
    eprintln!("{msg}");
    std::process::exit(1)
}

戻り値型の場所に感嘆符がひとつ。この表記はずいぶん前から安定チャネルでそのまま通っていた。ところが 2026 年 8 月末、never 型が十数年ぶりに安定化されたという知らせが回った。すでに使っているものを、いまさら安定化するとはどういうことか。

答えは二重になっている。第一に、これまで安定チャネルで通っていたのは戻り値位置に付く ! だけだった。let x: !、Result<u32, !>、ジェネリック引数としての ! のように通常の型の場所に置くことはナイトリー専用だった。第二に、そしてこちらが本題なのだが、足を引っ張っていたのは構文ではなく型推論が最後まで決められなかったときにどこへ落ちるかという既定値ひとつだった。

この記事はその既定値の話である。値がひとつもない型がなぜ役に立つのか、そしてすでに配布された言語で既定値を変えることがなぜそれほど高くつくのか。Rust の安全モデルを unsafe の側から扱った iddqd で見る Rust の unsafe カプセル化 - borrow-from-value と自己参照構造の落とし穴、型を後から載せるときに生じる境界のコストを扱った BEAM の上に静的型を載せるという選択 - Gleam が動かした境界と残した境界と地続きの話だ。

何が安定化され、いつ入ってくるのか — 2026 年 8 月時点

まず時点をはっきりさせておこう。安定チャネルにはまだない。

  • 安定化 PR rust-lang/rust#155499（題そのまま stabilize never type）が2026 年 8 月 24 日にマージされた。マイルストーンは 1.100.0 である。
  • releases.rs によれば 1.100.0 は 2026 年 9 月 25 日に master から分岐し、2026 年 11 月 12 日に安定チャネルへ出る予定だ。
  • この記事を書いている時点の安定版は 1.98.0、次の 1.99.0 の予定日が 2026 年 10 月 1 日である。

「安定化された」という見出しはマージ時点を指したものだ。ナイトリーを使わないなら手元に届くのは 11 月であり、リリースノートで最終的な範囲が確定するのもそのときである。

この PR がひとまとまりで片づける仕事は四つある。

  • ! を正式な型として安定化 — 戻り値位置の外でも書けるようになる
  • 型推論のフォールバックを全エディションで ! に統一
  • std::convert::Infallible を ! の型エイリアスへ転換
  • 予告用に点けておいた dependency_on_unit_never_type_fallback lint を削除

そして「十数年」という表現の根拠。RFC 1216（bang type）の Start Date は 2015-07-19 だ。マージ日まで11 年 1 か月かかった。見出しの「10 年」は丸めた言い方であり、その間が空白だったわけでもない。後で見るように一度は安定化され、差し戻された。

値がひとつもない型という発想

型を「値の集まり」と見れば勘定が楽になる。bool は値が二つ、u8 は 256 個、() はひとつ。では0 個の型とは何か。

値が 0 個ならその型の値を作れない。作れないのだから、その型の変数に何かを入れるコードには到達しえない。ここで一度ひっくり返る — 「値がない」が「実行がこの場所に来ない」へ翻訳される。値の個数についての言明が制御フローについての言明になるのだ。Rust Reference は ! を「値のない型であり、決して完了しない計算の結果を表す」と記す。

なぜこんなものが必要なのか。型検査器はすべての式に型があってはじめて計算を続けられる。ところがプログラムには、値を返さずに終わってしまう式が山ほどある。

  • panic!("...") — 巻き戻しであれ即時中断であれ、後ろへ続かない
  • loop {} — break のない無限ループ
  • std::process::exit(1) — プロセス自体が消える
  • return — 関数の外へ出るので、この場所に値は残らない
  • break ・ continue — 制御が別の場所へ行く
  • ? 演算子の失敗経路 — 早期リターンなので後がない

RFC 1216 以前の Rust はこうした式に () を付けていた。すると実際には来ない場所に「値がひとつある」と言っていることになる。コンパイラの立場からすると、この嘘はただではない。デッドコードの判定がぼやけ、分岐が合流する地点の型計算に余計なものが混じる。

RFC の表現は簡潔だ。! は「空の列挙型のように振る舞うが、ほかのどんな型へも暗黙に変換されうる」。前半は値がないという事実であり、後半がこの型を実際に役立たせる性質である。

あらゆる型へ流れていく — 分岐の片方が終わってしまうとき

! の核心的な性質はひとつだ。! 型の式はほかのすべての型へ強制変換される。Reference がそのままそう記している。

なぜこれが安全なのか。変換すべき値がそもそも存在しないからである。変換規則を定義する必要すらない。この論理をもっとも露骨に見せているのが Haskell の Data.Void で、そこには absurd :: Void -> a という関数があり、ドキュメントはこれを「偽からは何でも導かれる」という論理原則の実装だと説明する。呼べない関数なのだから、何を返すと約束しても嘘にならない。

実務でこの性質が目につく場所は分岐の片方が終わってしまうときだ。

let port: u16 = match std::env::var("PORT") {
    Ok(v)  => v.parse().unwrap_or(8080),
    Err(_) => {
        eprintln!("PORT is required");
        std::process::exit(1)   // このアームの型は !
    }
};

match のすべてのアームは型が同じでなければならない。上のアームは u16 で、下のアームは ! だ。! が u16 の側へ流れるので二つは噛み合う。プログラマが意味のないダミー値をこしらえて入れる必要がない。この型のない世界では下のアームに 0 とでも書き入れねばならず、その 0 は読む人に「この値が使われることもあるのか」という誤った問いを残す。

関数シグネチャに付くと、情報の向きがもう一度変わる。

fn bail(msg: &str) -> ! { eprintln!("{msg}"); std::process::exit(1) }

let cfg = load_config().unwrap_or_else(|_| bail("config missing"));
//        cfg の型はクロージャが ! を返しても揺らがない

ここで bail が () を返すと宣言されていれば、上のコードは型が合わずコンパイルされない。! と宣言した瞬間に二つのことが同時に成り立つ。

  • 呼び出し側の型が噛み合う — 戻り値が必要な場所にそのまま置ける
  • 後ろのコードが到達不能と判定される — 未初期化変数の診断とデッドコード警告が正確になる
  • 実装が変わればコンパイルが止める — 後で誰かが bail の中で誤って返せば、その場でエラーになる

最後の項目がコメントと分かれる地点だ。// この関数は戻らないというコメントは、実装が変わっても何もしない。

空の列挙型と ! — 自分で作る値のない型

ここまで読むと自然に浮かぶ考えがある。バリアントのない列挙型を自分で作ればよいのではないか。

enum Never {}          // バリアントがないので値を作れない

実際そう書く。標準ライブラリの std::convert::Infallible がまさにその品物で、ドキュメントは「決して起こりえないエラーのためのエラー型」であり「この列挙型にはバリアントがないので、この型の値は実際には存在しえない」と記す。RFC 1216 もユーザー定義の空の型で先に述べた用途をすべてまかなえることを認めている。

では何が違うのか。三つある。

  • 強制変換 — ! はどんな型へもひとりでに流れていく。空の列挙型はそうならないので match x {} のような形で手ずから消去しなければならない
  • 戻り値位置の表記力 — -> ! は「戻ってこない」と語る。-> Never は構文上「Never の値を返す」と読め、その値が存在しえないという事実は一枚裏にある
  • 推論への影響 — 空の列挙型はごく普通のユーザー型なので推論の既定値の議論が付かない。! は言語組み込みなので付く

三つ目がこの記事の残り全部だ。そして Infallible の運命はドキュメントにすでに書かれていた — 「! が安定化されたら Infallible をその型エイリアスにする計画」であり「ゆくゆくは Infallible を廃止する」。今回の PR がそのエイリアス転換を実際に行う。

同じドキュメントが自ら挙げた落とし穴もある。fn() -> ! と fn() -> Infallible にそれぞれトレイト実装を付けたコードは、二つが同じ型になった瞬間に実装が重なる。エイリアスをひとつ作る作業が他人のコードで衝突を生みうるという意味であり、こういうものまで数えねばならないのが安定化作業の実際の体積である。

なぜそれほど時間がかかったのか — 推論が決められないとき

ここからが本題だ。! を型として認める構文は難しくない。難しいのは型推論が最後まで何も決められなかった場所である。

ジェネリック型変数が何の制約も受けずに残ることがある。コンパイラはそのまま諦めるわけにいかないので既定値を埋める。これがフォールバックだ。Rust は歴史的にその値を () に据えてきた。

エディションガイドの記述が問題を正確に突いている。「歴史的にフォールバック型は () だった。このためフォールバックがなければコンパイラが () を推論しなかったはずの場所でも ! がひとりでに () へ強制変換された。これは混乱を招き、! 型の安定化を阻んできた。」

言い換えれば、! を本物の型として遇すると言いながら、いざ決まらない場所では () に寝かせるのは筋が通らなかった。ところがこの既定値を変えるとすでにコンパイルできていたコードがコンパイルできなくなる。エディションガイドが挙げる例を見よう。

fn outer<T>(x: T) -> Result<T, ()> {
    fn f<T: Default>() -> Result<T, ()> { Ok(T::default()) }
    f()?;        // 以前: T = ()  /  いま: T = !
    Ok(x)
}

f()? の成功値は捨てられるので T には何の制約もない。以前は () へ落ち、() は Default を実装しているので通っていた。いまは ! へ落ち、! は Default を実装しないのでエラーになる。直す方法は f::<()>()?; のように人が意図を打ち込むことだけだ。

この程度なら煩わしくはあっても安全だ。コンパイルエラーは騒々しく知らせてくれるのだから。本当の問題は音もなく意味が変わる側である。コンパイラの lint ドキュメントが挙げる例がこれだ。

if true {
    return
} else {
    unsafe { std::mem::zeroed() }   // フォールバックが () なら健全、! なら即 UB
};

mem::zeroed は戻り値型が呼び出し側で決まる。フォールバックが () だったときは () を作り出しており、それは完全に健全だ。フォールバックが ! になると値が存在しえない型の値を作り出したことになり、その場で直ちに未定義動作である。コードはそのままなのに意味が変わる。コンパイルは通る。

この危険が実際どれほど真剣に扱われたかは経緯に残っている。never 型は 1.26 で TryFrom とともに一度安定化され、2018 年 4 月に差し戻された（PR #50121）。フォールバックの意味変化が付いてきたためだ。その後トラッキングイシュー #58184 は「推論には触れず型だけ安定化しよう」という部分安定化を提案した。結局最後には推論に手を入れることになったが、その間に予告用の装置が積み上がった。

既定値をひとつ変えるために必要な装置

安定化された言語で既定値を変えるということは、すでに世に配布されたコードの意味を変えるという意味だ。Rust がこの仕事に動員した装置は三つで、三つとも別の言語・別のプロジェクトでもそのまま使える形をしている。

第一に、エディション。2024 エディションでまずフォールバックを ! に変えた。古いクレートは古いエディションの規則でコンパイルされ、新しいクレートと何の問題もなくリンクされる。ただしエディションは永久の分岐ではなく移行の通路だ。規則がエディションごとに永遠に違えば言語が事実上複数になってしまうので、最後には全エディションの統一が目標であり、今回の PR がその仕事をした。

第二に、警告の段階。許可 → 警告 → 拒否の順に上げる。1.92 で二つの lint を既定拒否へ上げる際、約 500 のクレートが影響を受けると見ており、それでも #[allow] で逃れる道は残した。リリースノートはこの措置を「互換性の変更ではなく、将来 never 型の安定化を可能にするもの」と規定した。壊すことと予告することを文書の上で区別して呼ぶ態度がここにある。

第三に、クレーター（crater）。公開エコシステム全体を実際にビルドし直してみる実験だ。今回の PR の実行結果は 9,024 件中 3,277 件が回帰で、そのうち 1,149 件は意図しないノイズと判断され再試行が勧告された。数字を読むときに注意すべきことがある。

  • クレーターの回帰数は「壊れたクレートの数」ではなく「人が読むべきリストの長さ」である
  • 同じ原因ひとつが数百件として数えられうるし、インフラの問題によるノイズが混じる
  • 逆に公開リポジトリにない社内コードはそもそも数えられない — こちらのほうが重要だ
  • だからクレーターは安全保証ではなく標本調査として読むべきである

もうひとつ。エディションガイドは「自動修正はないが、エディション変更で壊れるコードに対する自動検知はある」と釘を刺す。cargo fix が代わりに直してくれない理由ははっきりしている。正しい修正は「ここでどの型を意図したのか」を人が決める仕事であり、それは道具が代わりに決められる種類のものではない。

ここから残る一般的な教訓がひとつ。既定値は API 表面である。ドキュメントに書かれていなくても、利用者が明示的に選んだことがなくても、人はその上にコードを載せる。設定ファイルの既定値であれライブラリの既定動作であれ同じだ。

ほかの言語は同じ場所をどう埋めたか

この概念の一般名はボトム型（bottom type）である。値がなく、すべての型の下に置かれる。いくつもの言語に対応物があるが、下の表は順位ではない。違いは良し悪しではなくいつ導入したかとそのときどんな互換性を背負っていたかから生まれる。

言語名前提供の仕方確認した文書

表を横に読むと分かれる軸が二つ見える。

  • ライブラリか言語コアか — Haskell の Void と Python の Never はライブラリ側にある。コアに埋め込まれるとサブタイプ関係や推論に影響を与えられる代わりに、変えるのが難しくなる
  • サブタイピングか強制変換か — Kotlin と Scala は「すべての型のサブタイプ」として処理する。Rust はサブタイピングをライフタイムにしか使わないので、同じ効果を強制変換で得る。結果は似ていて、規則の住む場所が違う
  • 実行時に検査されるか — Python の Never は静的検査器に向けた言明であって、インタプリタが強制するわけではない。同じ名前でも守らせる主体が違う

Python のドキュメントが Never と NoReturn を「型システム上は同じ意味であり、静的検査器は両者を同等に扱う」と明かしながら二つの名前をどちらも残したことは目に留めておく価値がある。NoReturn が 3.6.2、Never が 3.11 に入った。名前を取り替えず重ねたこともまた互換性を守るひとつのやり方であり、Rust が Infallible をエイリアスとして残そうとする理由と同じである。

実務でこの型に出会う場所

抽象的に聞こえる型だが、実際のコードで顔を出す場所はかなり具体的だ。

絶対に失敗しないことをシグネチャで語る

標準ライブラリにはこういう実装がある。

  • impl<T, U: Into<T>> TryFrom<U> for T の関連型が type Error = Infallible; である
  • 変換が失敗しうる TryFrom インターフェースを使いながら、この場合には失敗バリアントが存在しないという事実を型で語る
  • ! を通常の型の場所に書けるようになれば Result<T, !> を直接使え、専用のエラー型をもうひとつ作る理由が減る
  • 読む側では「この API は失敗しうるか」がシグネチャだけで決まる — ドキュメントを探しに行く必要がない

戻ってこない関数

  • サーバーのメインループ、プロセス終了ラッパー、致命的エラーのハンドラが典型だ
  • -> ! と宣言すれば呼び出し側の以降が到達不能だとコンパイラが知る — 未初期化診断とデッドコード警告の精度が上がる
  • FFI 境界でも使われる。Reference は unsafe extern "C" { pub safe fn no_return_extern_func() -> !; } という形を例に挙げる。C 側の「戻らない」表記を Rust のシグネチャへ移す場所だ
  • 境界そのものを扱う話は Rust FFI の unsafe を減らす試み - extern fil-c 提案が狙う場所と支払う代価で別に扱った

ジェネリックパラメータを「なし」で打ち込む

  • 状態機械でまだ到達できない状態、イベントを送らないチャネルのメッセージ型のような場所
  • ダミー構造体を用意しておくより意図が正確に伝わる — ダミーは後で誰かが値を入れられるが、値のない型はそうできない
  • ただしこうした設計はライブラリ側で価値が大きく、アプリケーションコードでは過剰になりやすい

網羅性検査

  • TypeScript ではユニオンをすべて処理したか確認する慣用句として never が広く使われる
  • Rust は match の網羅性をもともと強制するので同じ慣用句の必要が薄い — 同じ道具が言語ごとに違う重みを持つ例だ
  • 空のバリアントをパターンで省略する機能は今回の安定化の範囲外で、別のゲートの裏に残っている

知らなくてよい人、知っておくと得な時点

正直に書けばほとんどのコードはこの型を直接使わない。panic! と process::exit はそのまま使えばよく、! はコンパイラが裏で付けたり外したりする。アプリケーションコードを書きながら ! を手で打ち込むことは数か月に一度あるかないかだ。

次の条件がすべて当てはまるなら、この記事の内容は忘れてよい。

  • 単一クレートのアプリケーションであり、公開ライブラリを作らない
  • エラー型をジェネリックで露出する API 設計をしない
  • unsafe ブロックがない
  • 最新のエディションを使っており、ツールチェーンをこまめに上げている
  • コンパイルエラーが出たらそのときメッセージを読んで直せばよい — 実際それでよい

逆に下の条件のどれかひとつでも引っかかるなら、いま知っておくほうが安く済む。

  • unsafe の中で戻り値型が呼び出し側で決まる関数を呼ぶ — mem::zeroed の系統だ。ここで出る警告を #[allow] で覆ってはいけない。コンパイルエラーは後で直してもよいが未定義動作に後はない。lint を拒否等級に上げた理由がまさにこれである
  • ライブラリを作り、エラー型をジェネリックパラメータとして露出する — Infallible のエイリアス転換が他人のコードで実装衝突を生みうる場所だ
  • 古いエディションに留まる大きなコードベースを維持する — 1.100.0 からはエディション境界がもう守ってくれない。いま出ている警告がそのときの作業量である
  • マクロを多用する — マクロが生み出した式でフォールバックがどこへ落ちるかは、ソースを見ただけでは分からない
  • エラーメッセージに ! が飛び出して面食らったことがある — この記事の 3・4 節がその答えだ

型が文書になる条件とならない条件

-> ! は「この関数は戻ってこない」という文をコードに刻む仕事だ。型で書いた文がコメントより優れている理由はひとつしかないが、その一つが決定的である。コンパイラがその主張を強制する。実装が変わって実際に返すようになれば、その場でビルドが止まる。コメントは静かに嘘になる。

型が文書の役割をきちんと果たす条件はたいていこうだ。

  • コンパイラが強制する — 食い違えばビルドが失敗する
  • 呼び出し側のコードの形を変える — Result<T, !> はエラー処理のコードをまるごとなくす
  • 表記が短く慣用句がひとつだ — 複数のやり方が併存すると読む側が毎回解釈しなければならない

逆に型が語れないことも明らかだ。こちらを知るほうが実用的である。

  • 「なぜ」を語れない — -> ! は戻らないという事実だけを語る。終了コードが何か、ログを残すのか、巻き戻しなのか即時中断なのかについては沈黙する
  • 不可能の種類を区別できない — 値のない型は、それがプロトコル上永遠に不可能なのか、まだ実装していないのか、このビルド構成でだけないのかを区別してくれない
  • 書かれていない既定値は文書ではない — フォールバックがまさにそれだった。ソースのどこにも () とは書かれていなかったが、コードの意味はそこにぶら下がっていた。この記事全体がその事例である

だから結論は「型で全部書こう」ではない。型は何が不可能かを強制し、散文はなぜそうなのかを残す。-> ! の隣に一行のコメントが依然として必要な理由だ。

確認できなかったこと

  • 1.100.0 のリリースノートはまだ出ていない。最終的な安定化の範囲がマージ時点と同じかはリリース時に確認する必要がある
  • クレーターの回帰 3,277 件のうち実際に修正が必要なクレートが何個か — ノイズ判定と再試行勧告の状態なので確定した数値がない
  • Infallible の廃止時点 — ドキュメントは「ゆくゆくは」としか記さない
  • 空のバリアントのパターン省略（別ゲート）の安定化スケジュール — 議論中であり今回の範囲外だ
  • 1.92 で見込んだ「約 500 のクレート」が実際にどう現れたかについての事後集計
  • 社内・非公開コードでの影響規模 — クレーターは公開リポジトリしかさらわないので構造的に分からない

まとめ

三つの文に縮めればこうなる。値がひとつもない型は「この場所には到達しない」を型で語る装置だ。その装置が役立つ理由は、どんな型へも流れていくので分岐の片方が終わってしまうときにダミー値をこしらえる必要がなくなるからである。そして十数年かかった理由は構文ではなく、推論が決められなかった場所の既定値を変える作業が、すでに配布されたコードの意味に触れるからだ。

持ち帰るものを三つだけ残す。

  • 既定値は API である。誰も明示的に選ばなかった値の上に世の中のコードが載る。変えるにはエディション・警告の段階・エコシステム実験のような装置が要り、その装置を作るのにかかる時間がすなわち「時間がかかった理由」だ
  • コンパイルエラーと意味の変化は重みが違う。前者は後で直してもよく、後者はいけない。Rust が unsafe と絡む lint だけを拒否等級に上げた判断が、この区別をそのまま見せている
  • 知らなくてよい人が大多数だという事実を伝えることも情報だ。この型を直接使うことは稀である。ただし unsafe・公開ライブラリ・古いエディションの三つのどれかに引っかかるなら、いま警告を読んでおくほうが 11 月に読むより安い
