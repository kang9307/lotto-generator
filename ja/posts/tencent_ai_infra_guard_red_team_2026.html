契機 — モデルサーバーから自律エージェントまでを包括するAIセキュリティ点検

生成AIの活用が単純なプロンプト応答から、大規模推論インフラ、Model Context Protocol(MCP)コネクタ、自律エージェントスキル、複数エージェントによるワークフロー連携へと広がるにつれ、システムが晒される攻撃対象領域も多層化した。従来のWebアプリケーション向け脆弱性診断ツールでは、推論エンジン固有のエンドポイントやエージェントのツール不正利用(tool misuse)、プロンプト脱獄(jailbreak)リスクを十分に捕捉できなかった。

2026年秋、Tencent傘下のセキュリティ研究ラボであるZhuque Lab(腾讯朱雀实验室)は、多層的なAI攻撃対象領域を組織内で自律点検できるよう設計されたオープンソースレッドチーム基盤「AI-Infra-Guard(A.I.G)」を公開した。Apache-2.0ライセンスで提供されるこのツールは、推論基盤からエージェント実行時までの総合点検能力を掲げている。

GeekNewsをはじめとする技術コミュニティでは、146種類のAIコンポーネントと2,000件以上のCVEルールへの対応、エージェントワークフロー自動診断といった数値が注目を集めた。しかし防御実務者の観点では、規模の誇示よりも各診断層が実際に何を検証し、何を見逃すのか、そしてツール自体を安全に運用するための必須要件が何であるかを冷静に区別しなければならない。

AI-Infra-Guardが備える5つの点検階層と診断範囲

AI-Infra-Guardのアーキテクチャは、AIシステムスタックを5つの明確な検査階層に分割し、それぞれに特化した検査エンジンと入力形式を割り当てている。リポジトリ文書に明記された5本柱は、インフラ脆弱性スキャン、MCPサーバースキャン、エージェントスキル監査、エージェントワークフロー実行時評価、LLM脱獄およびモデル改ざん評価である。

以下の表は、公式文書に記載された5つの点検階層の検査対象、診断機構、および検出限界を整理したものである。

点検階層README記載の機能説明実際に確認される事項確認されない事項 (構造的限界)
1. AIインフラ点検稼働中サービスアドレスを入力して既知CVEを探索既知の2000件超のCVEフィンガープリント照合ルール未登録のゼロデイ脆弱性や特殊な設定不備
2. MCPサーバー点検GitHub URLまたはソースコードの静的解析ツール汚染、認証情報漏洩、コマンドインジェクション実行時に動的入力によって誘発される回避動作
3. エージェントスキル点検SkillTrustBench T01〜T09に基づく安全監査バイトコード隠蔽や特権昇格パターンの検出複雑な対話コンテキスト下で生じる論理的不具合
4. エージェント実行時点検DifyやCozeなどのマルチエージェント連携評価制御喪失、ツール不正利用、データ外部流出あらゆる未知プロンプトに対する完全な安全保証
5. 脱獄・API監査攻撃プロンプト耐性試験およびモデル指紋照合ベンチマーク基準の防御率、モデルすり替え兆候評価データセットに含まれない全く新しい敵対手法

表から明らかなように、各階層は独自の検査方式を採用しており、いずれかの層で合格したからといって他の層の安全性が保証されるわけではない。推論サーバーに既知のCVEが存在しないことと、連携するMCPツールが安全であること、あるいはモデルがツールを不正利用しないことは全く別個の課題である。

第1層: 稼働中AIサービスのフィンガープリンティングと既知CVE照合

第1層であるAI Infra Scanは、ネットワーク上で稼働中の推論サーバーやオーケストレーション基盤を対象とする。利用者が対象ホストのIPアドレスとポート(Ollamaの11434、vLLMの8000、ComfyUIの8188など)を入力すると、スキャナーはHTTP応答ヘッダーやエンドポイントの振る舞いを分析して製品種別と稼働バージョンを特定する。

  • 識別対象コンポーネント。 v4.6.0時点でvLLM、Ollama、ComfyUI、n8n、LangFlow、llama-cpp、MLflowなど146種以上の主要AI製品をサポートする。
  • CVEルール照合。 特定されたバージョン情報を内部データベース内の2,000件を超えるCVEルールと突き合わせ、脆弱な版であるかを判定する。
  • 非破壊的検査。 対象サービスに対して破壊的なエクスプロイトペイロードを注入して攻撃を成立させるのではなく、公開バナー情報の照合に基づく非侵入型検査である。
  • 運用上の留意点。 CIDR表記などで広範なIP帯域を一括スキャンすると、社内推論ノードに多量の診断パケットが流入するため、明示的な検証用インスタンスに限定して実行する必要がある。

この層の限界は、既知の脆弱性データベースに登録されたシグネチャのみを検出できる点にある。独自ビルドされたバイナリや未公開の設定不備、ルール未登録のゼロデイ脆弱性はバナー照合だけでは判明しない。

第2・3層: MCPサーバーおよびAgent Skillソースコードの静的解析

第2層と第3層は、言語モデルが外部環境と対話するために装備する拡張ツール(Tool)階層の点検である。MCP(Model Context Protocol)サーバーやAgent Skillはファイル読み書きやシェル実行、外部ネットワーク通信などの高権限を持つことが多く、サプライチェーン攻撃の新たな標的となっている。

  • 入力形式の特徴。 稼働中サービスのアドレスではなく、GitHubリポジトリのURLまたはローカルに保存されたソースコードの圧縮アーカイブを入力とする。
  • 静的パターンおよびバイトコード解析。 Pythonコード内のハードコードされたAPIキー、資格情報漏洩パターン、コマンドインジェクション脆弱性、コンパイル済み.pycバイトコードによる検知回避を探索する。
  • SkillTrustBench分類の準用。 Tencent Zhuque Labが策定したSkillTrustBenchのT01〜T09(ツール汚染、権限昇格、不正ネットワーク転送など)の脅威分類に沿ってリスクを評価する。
  • CI/CD連携用CLIの提供。 Web UIに加えて独立したCLIツール(aig-skill-scanおよびmcp-scan)が提供されており、開発パイプラインのプルリクエスト段階でツールの安全性を自動検査できる。

静的解析である以上、コードの難読化や実行時に外部から取得される動的スクリプト、プロンプトの文脈に応じてモデルが誘導される間接的インジェクションを完全に防ぐことはできない。

第4・5層: エージェントワークフロー実行時監査とLLM脱獄・バックドア評価

第4層と第5層は、モデルやエージェントが実際の入力を受け取って自律動作する実行時(ランタイム)のリスクを検証する。

  • エージェント実行時制御喪失監査 (Agent Scan)。 DifyやCozeなどのマルチエージェント環境において、エージェント間のタスク引き継ぎ時に生じるリスクを診断する。Zhuque Labの研究成果であるRogueHandoff-20およびFORGE-Bench(arXiv:2609.11024)ベンチマクを用い、エージェントが正規タスク実行中に制約を逸脱して非認可ツールを呼び出したりデータを漏洩させたりしないかを評価する。
  • 脱獄耐性評価 (Jailbreak Evaluation)。 対象LLMのAPIエンドポイントを接続し、Many-Shot、PAIR、GOAT、ActorAttackなどの敵対的プロンプトデータセットを順次投入してセーフティフィルターの突破率を測定する。
  • APIリレーのブラックボックス監査 (Model & API Checker)。 サードパーティ製プロキシや中継サーバーを経由して利用するLLM APIに対し、複数回のフィンガープリントプローブを送信して契約モデル(Gemini、GLM等)からの密かなすり替えやバックドア応答の兆候を統計的に検出する。

動的評価はモデルの現時点での耐性を定量化する有効な手段だが、評価データセットでの高得点が未知の攻撃手法に対する絶対的な安全を意味するわけではない。自律エージェントの権限管理と脆弱性悪用に関する一般的知見は、Anthropic GLM-5.3脆弱性攻撃能力分析 2026でも取り上げられている。

アーキテクチャ、個別CLIツールの構成と配備手順

AI-Infra-Guardは、全機能をWebダッシュボードで操作する統合コンテナ環境と、特定の点検目的に特化した軽量CLIツールに分割された構成を採用している。組織の自動化要件やインフラ規模に応じて柔軟に選択できる。

以下の表は、各主要コンポーネントの実行形態、入力対象、運用上の注意点をまとめたものである。

構成コンポーネント実行および配備形態点検対象の入力形式運用セキュリティ留意事項
A.I.G 統合Web基盤Docker Composeコンテナ環境Web UI経由のIP、URL、ファイル認証機構不在のため外部公開は厳禁
aig-skill-scanpip経由で導入する単独CLIローカルディレクトリおよびLLM APIキーCI環境変数内でのAPIキー保護
mcp-scanGo/Python製スタンドアロンCLIGitリポジトリURLまたはローカルパス動的解析モード時のツールホワイトリスト適用
agent-scanコンテナ型ワークフロー評価器エージェント基盤API設定情報サンドボックス隔離環境内での実行
api-checkerGo製CLIおよび専用REST API対象LLMのAPI Base URLとKey検証時の外部データ送信に伴う漏洩防止

標準的なWebダッシュボード環境の構築は、公式READMEに記載されたDocker Composeコマンドに従う。

# 公式ビルド済みイメージを用いた起動手順 (README推奨手順)
                    git clone https://github.com/Tencent/AI-Infra-Guard.git
                    cd AI-Infra-Guard
                    docker compose -f docker-compose.images.yml up -d
                    # 起動後 http://localhost:8088 にアクセス

コンテナが起動すると、ローカルの8088番ポートで管理画面およびSwagger仕様のAPI仕様書(/docs/index.html)が利用可能となる。

「認証機能不在」の警告と社内内部網隔離運用の原則

AI-Infra-Guardの導入を検討するエンジニアが最も留意すべき安全上の制約は、公式READMEのインストール注記に明確に記載された以下の文言である。

Note: The AI-Infra-Guard project is positioned as an AI red teaming platform for internal use by enterprises or individuals. It currently lacks an authentication mechanism and should not be deployed on public networks.

公式文書が警告している通り、このプラットフォームにはユーザーログイン、セッション管理、ロールベースのアクセス制御機能が実装されていない。この管理画面をインターネットや公有ネットワークに公開した場合、極めて深刻なインシデントに直結する。

  • スキャン機能の悪用。 認証不要でアクセスした外部の攻撃者により、社内ネットワークや無関係な第三者サーバーへの無差別スキャン攻撃に悪用される恐れがある。
  • 資産情報および脆弱性レポートの漏洩。 社内AIサーバーの配置、ポート構成、検出されたCVEの詳細レポートが外部から閲覧可能となる。
  • APIキーの盗難。 脱獄評価やモデル監査のために画面に入力された商用LLMのAPIキーが平文で奪取される危険がある。
  • 完全閉域網での運用義務。 本ツールは社内イントラネット、プライベートVPCサブネット、または管理用VPNの背後に限定して配備し、外部からアクセスできないようファイアウォールで厳格に遮断しなければならない。外部接続が必要な場合はリバースプロキシでmTLSやSSO認証を前段に付加する必要がある。

また、点検行為自体の法的・倫理的境界として、本ツールを用いた脆弱性スキャンや敵対的評価は、自社が所有するか事前に書面で正式な許可を得たシステム・モデルに対してのみ実施されなければならない。無許可の対象に対するスキャンパケット送信は不正アクセス行為とみなされる恐れがある。

ブルーチーム(防御側)から見た点検ツールの実効性と盲点

防御側(ブルーチーム)にとって、AI-Infra-Guardのような統合レッドチームツールは、分散しがちな社内AI資産を一元的に棚卸しし、既知の脆弱性や初歩的な不備を迅速に洗い出すベースライン監査として有用である。エージェントに対する権限境界の適切な設定についてはTencent BrowserSkill分析 — ログイン済みブラウザをエージェントに渡す設計と権限境界 2026でも論じた通り、最小権限の徹底が防壁となる。

一方で、防御計画をツールの診断結果だけに依存することには以下の構造的な盲点が存在する。

  • シグネチャ依存の遅延性。 146コンポーネントと2,000件のCVEは網羅的だが、オープンソースAIライブラリの更新速度は極めて速く、最新の未登録脆弱性に対しては無力である。
  • 静的検査の誤検知と見落とし。 コード解析エンジンは文脈を完全に理解できないため、正当な開発用スクリプトを危険と判定したり、巧妙に分割された悪意ある処理を見落とす場合がある。
  • 評価スコアの過信。 ベンチマークで90%以上の防御率を記録しても、実環境で利用者が入力する未知の適応型プロンプトインジェクションを防ぎきれる保証にはならない。
  • 多層防御の不可欠性。 脆弱性検査ツールは現状を可視化する計測器に過ぎず、それ自体が防御機構ではない。ネットワーク分離、APIゲートウェイでのフィルタリング、ツール実行権限の最小化が前提となる。
  • ルールセットの継続的同期。 検出精度を保つためには、リポジトリのルール定義ディレクトリ(data/vuln/、data/mcp/)を定期的に最新状態へ更新する運用規律が求められる。

自動化された検査ツールによって既知の欠陥を速やかに排除しつつ、最終的な安全保障はシステムの構造的隔離とアクセス制御の原則によって確立されなければならない。

確認できなかったこと

  • オンラインプロ版(aigsec.ai)の機能詳細および招待コードの付与基準。ドキュメントには招待制である旨の記載のみがあり、無償版とのスキャンエンジンの差異は確認できなかった。
  • SkillTrustBenchの完全なベンチマーク結果およびリーダーボードデータ。matrix.tencent.comの生データは参照できず、READMEに記載されたT01〜T09の脅威分類枠組みのみを確認した。
  • コンテナ環境を用いず、物理ホストのLinuxやWindows上で直接ビルド・実行する場合の詳細なライブラリ依存関係および競合状況。
  • 内蔵された2,000件超のCVEルールのうち、重大度Critical(CVSS 9.0以上)に該当する具体的な件数と割合。
  • AWS BedrockやGoogle Cloud Vertex AIなど、主要パブリッククラウドが提供するマネージドAIサービス群に対する互換性および直接検査の可否。
