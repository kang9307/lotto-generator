3種類ある - バイトで直接見る

改行の方式は3つだ。Unix 系が使う LF は 0x0A の1バイト、Windows が使う CRLF は 0x0D 0x0A の2バイト、そしてクラシック Mac OS が使っていた単独 CR は 0x0D の1バイトだ。3つ目は今あらたに作られることはほとんどないが、古い資料を引き継ぐときには今も出てくる。言葉で覚えるよりバイトを一度見るほうが早い。

$ printf 'hello\nworld\n'     > lf.txt
$ printf 'hello\r\nworld\r\n' > crlf.txt
$ printf 'hello\rworld\r'     > cr.txt

$ xxd lf.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.
$ xxd crlf.txt
00000000: 6865 6c6c 6f0d 0a77 6f72 6c64 0d0a       hello..world..
$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ file lf.txt crlf.txt cr.txt
lf.txt:   ASCII text
crlf.txt: ASCII text, with CRLF line terminators
cr.txt:   ASCII text, with CR line terminators

xxd の右側の点は、印字できない文字の代わりに置かれたものだ。LF ファイルでは hello の後ろの点が1つなのに、CRLF ファイルでは2つある。その差がこの記事のすべてだ。目に見えるテキストは完全に同じで、ファイルサイズだけが行数の分だけ増える。3行のファイルなら 17 バイトと 20 バイトの差だ。

名称バイトエスケープ主に使われる場所今出会う場面
LF0x0A\nLinux、Unix、現代の macOS、Web、多くの言語のソース既定。特別な理由がなければこちら
CRLF0x0D 0x0A\r\nWindows のメモ帳とバッチファイル、多くのネットワークプロトコルWindows のエディタが新規ファイルによく入れる
CR0x0D\r2001年以前のクラシック Mac OS古い資料を引き継ぐときだけ。新しくは生まれない

なぜ2つに分かれたのか

2つの文字の名前そのものが由来を含んでいる。CR は carriage return、印字ヘッドを行の先頭に戻す動作で、LF は line feed、紙を1行送る動作だ。機械式の印字装置では2つが別物だった。一方の系統はこの慣習をファイル形式にそのまま残し、もう一方は1行に1文字あれば十分だと考えた。

Unix 側の選択は規格に書かれている。POSIX は行を「改行文字でない文字0個以上に、終端の改行文字1つを加えたもの」と定義する。ここでいう改行文字は \n 1つを指し、CR はただデータに含まれる普通の文字だ。だから CRLF ファイルを Unix のツールに渡すと、CR は行の最後の文字として扱われる。取り除かれるべき制御文字ではなく、値の一部として付いてくる。後に出てくる事故はすべてこの一文から派生する。

  • CRLF ファイルの各行は Unix から見ると「中身 + CR」だ。CR は区切りではなく中身の最後の文字である
  • だから "prod" を読んだつもりの変数に、実際には "prod\r" が入る
  • 比較、パスの組み立て、数値変換、ハッシュ計算がすべてずれる。しかも画面には何も現れない
  • 逆方向、つまり LF ファイルを Windows のツールに渡すほうはずっと寛容だ。最近の Windows のツールはたいてい LF をそのまま読む

シェルスクリプトが死ぬ仕組み

いちばん有名な症状から見る。1行目が #!/bin/bash のスクリプトを CRLF で保存すると、その行の実際のバイトは #!/bin/bash\r\n になる。カーネルがシェバンを解釈するとき、インタプリタのパスは改行の直前までを取るので、起動しようとするプログラムの名前が /bin/bash ではなく/bin/bash の後ろに CR が1文字付いた名前になる。そんなファイルはないので失敗する。

バイトを見れば疑う余地はない。

$ printf '#!/bin/bash\r\necho "hi"\r\n' > crlf.sh
$ chmod +x crlf.sh
$ head -c 24 crlf.sh | xxd
00000000: 2321 2f62 696e 2f62 6173 680d 0a65 6368  #!/bin/bash..ech
00000010: 6f20 2268 6922 0d0a                      o "hi"..

6173 68 が ash で、その次が 0d 0a だ。パス文字列 /bin/bash のすぐ後ろに 0x0D が付いている。この状態で実行すると、インタプリタが見つからないというエラーになる。その仕組みはシェバンを経由しなくても再現できる。パスの末尾に CR を直接付けて呼べばよい。

$ "/bin/bash$(printf '\r')" -c 'echo hi' 2>err.txt
$ cat -A err.txt
/usr/bin/bash: line 1: /bin/bash^M: No such file or directory$

$ xxd err.txt
00000000: 2f75 7372 2f62 696e 2f62 6173 683a 206c  /usr/bin/bash: l
00000010: 696e 6520 313a 202f 6269 6e2f 6261 7368  ine 1: /bin/bash
00000020: 0d3a 204e 6f20 7375 6368 2066 696c 6520  .: No such file
00000030: 6f72 2064 6972 6563 746f 7279 0a         or directory.

オフセット 0x20 の 0d が要点だ。エラーメッセージの中に本物の CR バイトが入っている。cat -A がそれを ^M として表示してくれる。よく見る bad interpreter: /bin/bash^M の ^M がまさにこのバイトであって、ないものをシェルが作り出したわけではない。

シェバンに env を使う場合はエラーの形が少し違う。env が引数をそのまま引用して見せるので、かえって親切だ。

$ env "bash$(printf '\r')" --version
env: 'bash\r': No such file or directory

ここでは \r が文字どおり出力される。env で始まるシェバンを使う習慣は、デバッグでは有利ということになる。

Git Bash ではこのバグが見えない

ここで、この問題がなぜそれほど長く生き残るのかがわかる。上で作った crlf.sh を Git Bash でそのまま実行すると、何も起きない。正常に動く。

$ ./crlf.sh
hi

$ printf '#!/usr/bin/cat\r\nhello\r\n' > catshebang.sh
$ chmod +x catshebang.sh
$ ./catshebang.sh | cat -A
#!/usr/bin/cat^M$
hello^M$

2つ目の例が証拠だ。シェバンを /usr/bin/cat にして実行したら、cat が実際に走ってファイルの中身を吐いた。つまり MSYS2 の実行層がシェバン行末の CR を自分で取り除いてインタプリタを見つけてくれている。ファイル内の CR はそのまま残っていることも同じ出力からわかる。中身の行は ^M を付けたままだ。

結果として、開発者のノート PC ではスクリプトはちゃんと動く。コミットもされ、レビューも通り、デプロイのパイプラインに入る。そしてLinux サーバーで初めて死ぬ。これがこのバグがコードレビューを通過する理由だ。なお、CR を無視させる igncr というシェルオプションを持つ bash のビルドもあると言われるが、少なくともこの環境の bash 5.2.37 にはない。

$ shopt igncr
/usr/bin/bash: line 1: shopt: igncr: invalid shell option name

だから「自分のローカルでは動くのに」という言葉は、この主題では情報にならない。ローカルが Windows ならもともと動く。

本当に厄介なのは変数の値の末尾に付く CR

シェバンの問題はそれでも派手に死ぬだけましだ。はるかに長く人を捕まえるのは設定ファイルを読んで変数に入れるときに起きる。スクリプト自体は LF なのに、読み込む .env や設定ファイルだけが CRLF という場合はよくある。このときは死にもせず、ただ条件文が間違う。

$ printf 'ENV=prod\r\nPORT=8080\r\n' > app.conf

$ cat readconf.sh
#!/bin/bash
while IFS='=' read -r k v; do
  export "$k=$v"
done < app.conf
echo "ENV=[$ENV]"
if [ "$ENV" = "prod" ]; then echo "MATCH"; else echo "NO MATCH"; fi
echo "length=${#ENV}"

$ bash readconf.sh
ENV=[prod]
NO MATCH
length=5

画面には ENV=[prod] と出ている。角かっこの中に prod の4文字が見える。それなのに prod と等しくないと言い、長さは5だと言う。この3行が同時に成り立つ状況を目だけで理解しようとすると何時間も使う。cat -A で見ればすぐ終わる。

$ bash readconf.sh | cat -A
ENV=[prod^M]$
NO MATCH$
length=5$

値は prod ではなく、prod の後ろに CR が付いた5文字だ。ここで1つ微妙な違いを押さえておく必要がある。読み方によって CR が残ったり消えたりする。

$ printf 'v2.4.1\r\n' > version.txt

$ read -r VER2 < version.txt
$ echo "len2=${#VER2}"
len2=7
$ printf '%s' "$VER2" | xxd
00000000: 7632 2e34 2e31 0d                        v2.4.1.

$ VER=$(cat version.txt)
$ echo "len=${#VER}"
len=6
$ printf '%s' "$VER" | xxd
00000000: 7632 2e34 2e31                           v2.4.1

read で読むと CR が残って7文字、コマンド置換で読むと6文字だ。この環境の bash はコマンド置換で末尾の改行を落とすときに CR まで一緒に落とす。ただしこれも Windows でだけ静かなほうだ。パイプは CR をそのまま流す。

$ printf 'a\r\nb\r\n' | xxd
00000000: 610d 0a62 0d0a                           a..b..

つまり同じファイルでも、while read で回すか、$(...) で受けるか、パイプで渡すかによって CR の残る場所が変わる。そうしてある行では動き、ある行では動かないスクリプトができあがる。この不整合が原因追跡をいちばん妨げる。

エラーメッセージが妙に切れる理由

CR が値に混ざると、それを出力した瞬間に端末が反応する。CR はもともとカーソルを行の先頭に戻せという制御文字だからだ。メッセージの途中に CR が入ると、その後ろの文字が前の部分を上書きする。消えたのではなく隠れたのである。

ログに deploy failed: version v2.4.1 not supported を出すつもりで、バージョンの値の末尾に CR があったとする。端末は v2.4.1 まで描いてからカーソルを行頭に戻し、not supported を上から描く。残るのは前後が混ざった短い1行で、元の文はどこにもないように見える。ファイルにリダイレクトして cat -A で開けば、完全な原文がそのまま残っている。

  • メッセージが途中で切れたように見えたら CR を疑う。ログ出力側のバグでないことが多い
  • 同じ理由で進捗表示がおかしくなり、プロンプトが重なって見え、grep の結果が短く出たと錯覚する
  • 確認は必ずファイルに受けて行う。端末が描く画面は原本ではない
  • CI のログビューアは CR の扱いがツールごとに違うので、同じログがローカルと Web で違って見えることもある

見つけ方 - grep が 0 を返す落とし穴

確認のコマンドは4つで足りる。file は一目で、cat -A は行単位で、xxd はバイトで、dos2unix -i は個数で教えてくれる。混ざったファイルを1つ作って4つを並べて実行する。

$ printf 'first\r\nsecond\nthird\r\n' > mixed.txt

$ file mixed.txt
mixed.txt: ASCII text, with CRLF, LF line terminators

$ cat -A mixed.txt
first^M$
second$
third^M$

$ dos2unix -i mixed.txt lf.txt crlf.txt cr.txt
       2       1       0  no_bom    text    mixed.txt
       0       2       0  no_bom    text    lf.txt
       2       0       0  no_bom    text    crlf.txt
       0       0       2  no_bom    text    cr.txt

dos2unix -i の3つの数字は、左から CRLF、LF、単独 CR の個数だ。mixed.txt が 2 1 0 なのは作ったとおりである。4番目の欄は BOM の有無、5番目はテキストと判定したかバイナリと判定したかだ。複数のファイルのうち CRLF が混ざったものだけを取り出すには -ic を使う。名前だけが出る。

ところが、いちばん広く勧められている方法がこの環境では偽陰性を出す。

$ grep -c $'\r' mixed.txt
0

$ grep -Uc $'\r' mixed.txt
2

$ awk '/\r$/{n++} END{print n+0}' mixed.txt
0

$ awk -v BINMODE=3 '/\r$/{n++} END{print n+0}' mixed.txt
2

CRLF の行が2つ入っているファイルに対して grep -c $'\r' が0 を返す。この環境の GNU grep 3.0 はファイルをテキストモードで読み、行末の CR を先に取り除いてしまうからだ。-U を付けてバイナリモードで読ませればきちんと2が出る。gawk も同じで -v BINMODE=3 が要る。Linux ではこうした前処理がないので -U なしでも引っかかるが、Windows で確認したという言葉はだから信用できない。検査スクリプトを書くときにこの1文字を落とすと、検査器はいつでも合格を返すようになる。

コマンド何がわかるか注意
file ファイルCRLF・LF・CR の種類を名前で混在していれば両方が並ぶ
cat -A ファイル行ごとの ^M と行末の $いちばん直観的。タブは ^I と出る
xxd ファイル | head実際のバイト。0d0a を目で長いファイルは head で切る
dos2unix -i ファイルCRLF・LF・CR の個数と BOM の有無複数ファイルを一度に表で見る
grep -Uc $'\r' ファイルCR を含む行数-U を抜くとこの環境では 0 が出る
git ls-files --eolリポジトリのインデックスと作業ツリーの状態ファイルではなくリポジトリを見るとき

直し方3つ、そしてそれぞれが壊すもの

変換の方法は3つが広く使われる。普通の CRLF テキストファイルなら3つとも同じ結果になる。

$ dos2unix -q mixed.txt
$ sed -i 's/\r$//' mixed.txt
$ tr -d '\r' < mixed.txt > out.txt

$ cat -A mixed.txt
first$
second$
third$

分かれるのは普通でないファイルだ。tr -d '\r' は行末かどうかをまったく区別しない。ファイル内の 0x0D を残らず消す。進捗を CR で上書きしながら出力したログを例に取るとこうなる。

$ printf 'progress: 10%%\r progress: 100%%\rdone\n' > prog.log
$ xxd prog.log
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

$ tr -d '\r' < prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 2520 7072  progress: 10% pr
00000010: 6f67 7265 7373 3a20 3130 3025 646f 6e65  ogress: 100%done
00000020: 0a                                       .

$ sed 's/\r$//' prog.log | xxd
00000000: 7072 6f67 7265 7373 3a20 3130 250d 2070  progress: 10%. p
00000010: 726f 6772 6573 733a 2031 3030 250d 646f  rogress: 100%.do
00000020: 6e65 0a                                  ne.

tr を通したほうは3段階の進捗表示が1行につながって、元の意図が消えた。sed 's/\r$//' は行末にある CR だけを狙うので、このファイルには手を付けなかった。ただし sed も万能ではない。旧 Mac 形式の単独 CR ファイルにはほとんど手が出せない。そのファイルは Unix のツールには1行に見えるからだ。

$ xxd cr.txt
00000000: 6865 6c6c 6f0d 776f 726c 640d            hello.world.

$ sed 's/\r$//' cr.txt | xxd
00000000: 6865 6c6c 6f0d 776f 726c 64              hello.world

$ tr -d '\r' < cr.txt | xxd
00000000: 6865 6c6c 6f77 6f72 6c64                 helloworld

$ dos2unix -q -c mac cr.txt
$ xxd cr.txt
00000000: 6865 6c6c 6f0a 776f 726c 640a            hello.world.

sed は末尾の CR 1つだけを取り、途中の CR は残した。tr は2行を helloworld という1つの塊にしてしまった。dos2unix -c mac だけが CR を LF に変えて2行を残した。データが失われるかどうかがコマンドの選択1つにかかっている。

バイナリファイルでは差がもっと極端になる。dos2unix は既定でバイナリを飛ばす。

$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ dos2unix bin.dat
dos2unix: Binary symbol 0x00 found at line 1
dos2unix: Skipping binary file bin.dat
$ xxd bin.dat
00000000: 504e 4789 000d 0a1a 0aff d8              PNG........

$ tr -d '\r' < bin.dat | xxd
00000000: 504e 4789 000a 1a0a ffd8                 PNG.......

tr を通ったファイルは1バイト消えている。画像でも圧縮ファイルでも、この時点で使えなくなる。しかも警告は何も出ない。find と組み合わせてリポジトリ全体に tr を回すスクリプトが危険なのはこのためだ。

ツール行末の CRLF行の途中の CR単独 CR のファイルバイナリBOM
dos2unix変換保持-c mac で変換既定で飛ばす既定で除去
sed -i 's/\r$//'変換保持ほとんど手が出ない壊す可能性があるそのまま
tr -d '\r'変換一緒に削除行がつながる破損させるそのまま

表の右端の欄は思わぬ副作用なので、別に確認しておく価値がある。dos2unix はオプションを与えないとファイル先頭の BOM を一緒に消す。

$ printf '\xef\xbb\xbfname,qty\r\nsalt,2\r\n' > bomcrlf.csv
$ xxd bomcrlf.csv
00000000: efbb bf6e 616d 652c 7174 790d 0a73 616c  ...name,qty..sal
00000010: 742c 320d 0a                             t,2..

$ dos2unix -q bomcrlf.csv
$ xxd bomcrlf.csv
00000000: 6e61 6d65 2c71 7479 0a73 616c 742c 320a  name,qty.salt,2.

先頭の3バイト efbbbf が消えた。Excel に渡す CSV のように BOM が必要なファイルなら -b を付けて維持しなければならない。改行だけを直すつもりで別のものも一緒に直してしまう代表的な場面だ。

git が介入する2つの地点 - core.autocrlf

git は改行を2つの地点で触ることができる。コミットするとき(作業ディレクトリからインデックスへ)とチェックアウトするとき(インデックスから作業ディレクトリへ)だ。core.autocrlf の3つの値は、この2地点をそれぞれ違うふうに触る。使い捨てのリポジトリを作って確かめれば迷う余地はない。

まずチェックアウト側だ。LF でコミットされたリポジトリを3つの設定でそれぞれ複製する。

$ cd /tmp/demo/src
$ git ls-files --eol
i/lf    w/lf    attr/                   src.txt

$ git -c core.autocrlf=true  clone -q /tmp/demo/src /tmp/demo/w-true
$ git -c core.autocrlf=input clone -q /tmp/demo/src /tmp/demo/w-input
$ git -c core.autocrlf=false clone -q /tmp/demo/src /tmp/demo/w-false

$ xxd /tmp/demo/w-true/src.txt
00000000: 6c69 6e65 310d 0a6c 696e 6532 0d0a       line1..line2..
$ xxd /tmp/demo/w-input/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.
$ xxd /tmp/demo/w-false/src.txt
00000000: 6c69 6e65 310a 6c69 6e65 320a            line1.line2.

true だけが作業ディレクトリのファイルを CRLF に書き換えた。次はコミット側だ。3つのリポジトリそれぞれに CRLF のファイルを作ってコミットし、インデックスの状態を見る。

$ printf 'new1\r\nnew2\r\n' > added.txt
$ git add added.txt
$ git commit -qm add
$ git ls-files --eol -- added.txt

# core.autocrlf=true
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=input
i/lf    w/crlf  attr/                   added.txt
# core.autocrlf=false
i/crlf  w/crlf  attr/                   added.txt

true と input はインデックスに LF で入れ、false は CRLF をそのまま入れた。つまり2つの値の違いはコミットではなくチェックアウトだけにある。この表が結論だ。

core.autocrlfコミット時 (作業 → インデックス)チェックアウト時 (インデックス → 作業)誰に向くか
trueCRLF を LF に変えて保存LF を CRLF に変えて渡すWindows 専用エディタを使う人。リポジトリはきれいになる
inputCRLF を LF に変えて保存変換しない。LF のままWindows で Linux 向けスクリプトを扱う人
false変換しない。書かれたまま変換しない改行を .gitattributes だけで管理するリポジトリ

ここにもう1つ core.eol がある。値は lf、crlf、native で、既定はプラットフォームの慣習に従う native だ。そして core.safecrlf を true か warn にすると、変換が元に戻せない場合に警告したり止めたりしてくれる。

  • core.autocrlf は個人設定だ。リポジトリを受け取る人ごとに値が違いうる
  • だからチーム全体に同じ値を使えと告知する方式は、新しく加わった人のところで必ず一度は壊れる
  • 公式文書は core.autocrlf=true を「すべてのファイルに text=auto を設定し core.eol を crlf にするのと同じ」と説明している
  • つまり autocrlf は .gitattributes の省略形に近い。それなら省略形ではなく本体を書くほうがよい

.gitattributes のほうがよい理由

違いは1つだ。core.autocrlf は人に付き、.gitattributes はリポジトリに付く。後者はコミットされて一緒に配布されるので、共同作業者の設定に関係なく同じルールがかかる。新しく入った人が何も設定しなくてもルールが働く点が実質的な違いだ。

# .gitattributes
* text=auto

*.sh   text eol=lf
*.py   text eol=lf
*.yml  text eol=lf
*.yaml text eol=lf

*.bat text eol=crlf
*.cmd text eol=crlf
*.ps1 text eol=crlf

*.png binary
*.jpg binary
*.pdf binary

属性の意味はこうだ。text を指定するとチェックインのたびにインデックスの改行を LF に正規化する。text=auto は git がテキストかバイナリかを自分で判断する。eol=lf はチェックアウトのときにインデックスと同じ改行を使えという意味で、eol=crlf は作業ディレクトリのファイルを CRLF に変えろという意味だ。binary は -text -diff の別名で、何も変換するなという印である。

ここに見落としやすい点がある。* text=auto だけでは作業ディレクトリが LF にならない。文書によれば、eol が指定されず core.autocrlf も core.eol も設定されていない場合の既定はWindows では eol=crlf、それ以外のプラットフォームでは eol=lf だ。実際に新しく複製してみるとそのとおりに出る。

$ git clone -q /tmp/demo/repo /tmp/demo/fresh
$ cd /tmp/demo/fresh
$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          .gitattributes
i/-text w/-text attr/text=auto          blob.bin
i/lf    w/lf    attr/text eol=lf        deploy.sh
i/lf    w/crlf  attr/text=auto          notes.md

$ xxd notes.md
00000000: 610d 0a62 0d0a                           a..b..
$ xxd deploy.sh
00000000: 2321 2f62 696e 2f62 6173 680a 6563 686f  #!/bin/bash.echo
00000010: 2068 690a                                 hi.

同じリポジトリから notes.md は CRLF で降りてきて、deploy.sh は LF で降りてきた。違いは *.sh text eol=lf の1行だけだ。Linux で実行されるファイルに eol=lf を明示しなければならない理由がこれである。text=auto だけを信じると、Windows の作業ツリーでシェルスクリプトが CRLF に戻って生き返る。

出力の形式も覚えておく価値がある。git ls-files --eol は3つの欄を見せる。

欄意味出うる値
i/インデックスに保存されたブロブの改行lf、crlf、mixed、-text(バイナリ)
w/今の作業ディレクトリのファイルの改行同じ値。i/ と違っていても正常な場合がある
attr/そのパスに適用中の属性text=auto、text eol=lf、空欄など

.gitattributes は過去を直さない

この節がこの記事でいちばん頻繁に使われることになる。.gitattributes を追加すれば問題は終わったと思いがちだが、ルールを入れる前にすでにコミットされたブロブはそのまま残る。ルールはこれからの変換にだけかかる。

CRLF ファイルを core.autocrlf=false でコミットしておいたリポジトリに .gitattributes を入れて状態を見るとこうなる。

$ git ls-files --eol
i/crlf  w/crlf  attr/                   deploy.sh
i/lf    w/lf    attr/                   notes.md

$ printf '* text=auto\n*.sh text eol=lf\n*.bat text eol=crlf\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm "add gitattributes"

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text eol=lf        deploy.sh
i/lf    w/lf    attr/text=auto          notes.md

$ git check-attr text eol -- deploy.sh
deploy.sh: text: set
deploy.sh: eol: lf

attr/ の欄には新しいルールがきちんと付いている。check-attr も eol: lf と答える。それなのに i/ の欄はいまだに crlf だ。ルールはかかったのにデータは以前のままという状態である。このリポジトリを Linux サーバーにデプロイすれば、スクリプトは相変わらず死ぬ。

もっと紛らわしいのは * text=auto だけを入れた場合だ。文書はこの値について「テキストでありそのファイルがすでに CRLF で git に入っていなければ改行を変換する」と書いている。ではそのファイルを修正して再コミットすれば片付くのか。確かめるとそうではない。

$ git ls-files --eol
i/crlf  w/crlf  attr/                   legacy.txt

$ printf '* text=auto\n' > .gitattributes
$ git add .gitattributes
$ git commit -qm attrs

$ printf 'one\r\ntwo\r\nthree\r\n' > legacy.txt
$ git add legacy.txt
$ git commit -qm edit

$ git ls-files --eol
i/lf    w/lf    attr/text=auto          .gitattributes
i/crlf  w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650d 0a74 776f 0d0a 7468 7265 650d  one..two..three.
00000010: 0a                                       .

修正して再コミットしたのに、インデックスのブロブは CRLF のままだ。text=auto は一度 CRLF で入ったファイルをずっと例外として扱う。ルールを入れて何か月経っても勝手には片付かないということだ。

片付けるには明示的な再正規化が必要になる。公式文書が案内する順番そのままだ。作業ツリーがきれいな状態で実行する。

$ git add --renormalize .
$ git status --short
M  legacy.txt
$ git commit -qm "normalize line endings"

$ git ls-files --eol
i/lf    w/crlf  attr/text=auto          legacy.txt

$ git show :legacy.txt | xxd
00000000: 6f6e 650a 7477 6f0a 7468 7265 650a       one.two.three.

インデックスはこれで LF だ。ところが w/ の欄はまだ crlf のままである。再正規化はインデックスだけを変えて作業ディレクトリのファイルには手を付けないからだ。作業ツリーまで合わせるには、そのファイルを消して受け直せばよい。

$ rm deploy.sh
$ git checkout -- deploy.sh
$ git ls-files --eol
i/lf    w/lf    attr/text eol=lf        deploy.sh
  • 再正規化のコミットは中身は変わっていないのにほとんどの行が変わったように見える。他の作業と混ぜず単独のコミットとして残す
  • 進行中のブランチがあるとマージ衝突が大きく出る。マージすべきものを先にマージしてから正規化するほうがよい
  • git status に予期しないファイルが上がってきたら、そのファイルを -text で除外してから回し直す
  • 正規化のあとも i/crlf が残っていれば、そのパスはルールから漏れている。git check-attr で確認する

CRLF であるべきファイルはどれか

すべて LF に統一しようという助言はよくあるが、Windows 専用ファイルまでそうすると困るという話も同じくらいよく聞く。実際にどれだけ困るのかを確かめてみた。LF だけで作ったバッチファイルにラベルと goto、for ループ、if else ブロック、call によるサブルーチン、最終行に改行がない場合まで入れて cmd.exe で動かした。

C:\> cmd /c lf2.bat
item 1
item 2
item 3
yes
SUB

C:\> powershell -NoProfile -ExecutionPolicy Bypass -File lf.ps1
ps LF ok
block ok

すべて正常に動作した。Windows 10 ビルド 19045.6466 の cmd.exe と PowerShell 5.1 ではLF のバッチファイルが実行された。必ず CRLF でなければならないという話は、少なくともこの構成では再現しなかった。

だからといってバッチファイルを LF にしようという意味ではない。判断の根拠は成否ではなく危険の非対称性にある。Windows 専用ファイルを CRLF にしておいて失うものはない。Linux で実行されることがないからだ。逆に Linux で動くファイルを CRLF にすると確実に壊れる。だからルールは単純になる。どこで実行されるかで決める。

ファイル推奨理由
.sh、.bash、.py、.pl、.rbLFシェバンが CR をインタプリタのパスに含めてしまう
Makefile、systemd ユニット、cron ファイルLF値の末尾に CR が付いてパスやコマンドがずれる
.env、.conf、.yml、.jsonLFパーサーによっては値の末尾の CR がそのまま入る
SSH 公開鍵、authorized_keysLF鍵の文字列が変わって認証が静かに失敗する
.bat、.cmdCRLFこの環境では LF も動いたが、Windows 専用なので CRLF で失うものがない
.ps1どちらでもLF で正常に動いた。こちらは BOM の有無のほうがよく問題になる
画像、圧縮ファイル、フォント変換禁止.gitattributes に binary と指定する

エディタと CI で止める方法

直すより起こさないほうが安い。層は3つだ。エディタで一度、リポジトリで一度、パイプラインで一度止める。エディタの層は .editorconfig が担う。規格上 end_of_line は lf、cr、crlf を受け取り、値は大文字小文字を区別しない。

# .editorconfig
root = true

[*]
end_of_line = lf
insert_final_newline = true
charset = utf-8
trim_trailing_whitespace = true

[*.{bat,cmd}]
end_of_line = crlf

[*.md]
trim_trailing_whitespace = false

2つのファイルは役割が重ならない。前者はエディタが保存するとき、後者はgit がコミットとチェックアウトをするときに働く。両方置いたうえで拡張子の一覧をそろえる。食い違うと保存時とコミット時で値が変わり、毎回変更が出る。

最後の層は検査だ。リポジトリのインデックスに CRLF で入ったテキストファイルがあるかどうかを1行で確認できる。

$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
$ echo $?
1

# 汚染されたリポジトリでは
$ git ls-files --eol | grep -E '^i/(crlf|mixed)'
i/crlf  w/crlf  attr/                   added.txt
$ echo $?
0

きれいなら何も出力せず終了コード 1 を、問題があれば一覧とともに 0 を返す。CI のステップでは前に ! を付けて見つかったら失敗に反転させればよい。ファイルを直接なめる方式よりこの方法がよい理由が3つある。バイナリは i/-text と出て自動的に外れ、.gitattributes で CRLF を許したファイルは正規化されて i/lf と出る。そして何より先ほど見た grep のテキストモードの落とし穴を避けられる。

付け加えると、改行が混ざるとまずコードレビューが崩れる。中身が同じでも全部変わったように出るからだ。

$ diff a_lf.txt a_crlf.txt
1,3c1,3
< alpha
< beta
< gamma
---
> alpha
> beta
> gamma

$ diff --strip-trailing-cr a_lf.txt a_crlf.txt
$ echo $?
0

見える文字は完全に同じなのに3行とも違うと言う。レビュアーは実際の変更を見つけられなくなり、この状態で数日たてばリポジトリ全体が混ざる。--strip-trailing-cr は急ぐときの一時しのぎであって解決策ではない。

最後に、なぜ一部のコードが無事なのかも知っておく価値がある。言語のランタイムが読む段階ですでに変換してくれる場合がある。

$ python nl.py
default  : 'ENV=prod\n'
newline='': 'ENV=prod\r\n'
binary   : b'ENV=prod\r\n'
split    : ['ENV', 'prod']
split raw: ['ENV', 'prod\r']

Python はテキストモードで開くと既定で改行を \n 1つに統一してくれる。だから Python のコードは CRLF ファイルを読んでもたいてい無事だ。逆に newline="" やバイナリモードで開くと CR がそのまま入り、その値を split すると 'prod\r' が出る。同じファイルを2つのコードが違うふうに読む状況が実際に生まれるということだ。

改行と BOM は別の問題だ

この2つはよく一緒に語られるが、原因も位置も解決策も違う。改行はすべての行の末尾にあり、BOM はファイルの先頭に一度だけある。症状が重なって見えるのは、どちらも「見えないバイトが値に混ざる」という形を共有しているからであって、同じ原因から出ているわけではない。

  • 改行は 0x0D 0x0A、BOM は UTF-8 なら 0xEF 0xBB 0xBF だ。重なるバイトはない
  • 直すツールも違う。ただし dos2unix は既定で両方に手を付ける。前の節で確認したとおりだ
  • シェバンが壊れる症状はどちらも作る。1行目の前に BOM があっても、1行目の末尾に CR があってもインタプリタが見つからない
  • 見分けは xxd ファイル | head -1 の1行で終わる。先頭が efbbbf か、行末が 0d0a かだけを見ればよい

BOM 側の詳細は BOM が作るバグ - 見えない3バイトがシェルと JSON と CSV を壊す場所に別途まとめてある。文字が四角や疑問符に見える問題はまた別の層で、そちらは ハングルが壊れる地点を特定する方法 - cp949とUTF-8、2種類のエンコーディングエラーにある。3つが重なっているときはエンコーディング → BOM → 改行の順に1つずつ剥がしていくほうが早い。

まとめ - 順番に

いま壊れたファイルがあるなら手順は短い。file で種類を確認し、dos2unix で変換し、もう一度実行する。ここまでで5分だ。問題はその次である。同じことが来週また起きるなら、直すべきはファイルではなくパイプラインだ。

  1. 診断。file ファイル と xxd ファイル | head -1。行末が 0d0a か、先頭が efbbbf かを区別する
  2. 変換。dos2unix ファイル。CSV のように BOM が必要なら -b、旧 Mac ファイルなら -c mac。tr -d '\r' は使わない
  3. リポジトリのルール。.gitattributes に * text=auto と実行ファイルの拡張子ごとの eol=lf。Windows 専用は eol=crlf
  4. 過去の片付け。きれいな作業ツリーで git add --renormalize . のあと単独コミット。これをしなければルールは飾りだ
  5. エディタ。.editorconfig に end_of_line = lf。拡張子の一覧を .gitattributes とそろえる
  6. 検査。CI に ! git ls-files --eol | grep -E '^i/(crlf|mixed)' の1行

いちばん重要なのは4番だ。この記事で実行して確かめたことのうち、実務でいちばんよく引っかかる事実がルールを入れても過去はそのままだということだった。* text=auto の下でそのファイルを修正して再コミットしてもインデックスは CRLF だった。再正規化はひとりでには起きない。

Windows で確認したという言葉は根拠にならない。この記事で確かめたことだけで3つある。Git Bash は CRLF のシェバンを自分で処理してスクリプトを正常に実行し、grep -c $'\r' は CRLF ファイルで 0 を返し、コマンド置換は値の末尾の CR を落とす。3つとも問題を隠してくれる。検証は実際にデプロイされる環境で、少なくとも git ls-files --eol のようにプラットフォームに依存しない方法で行う。

確認できなかったこと

  • Linux の実機で bad interpreter: /bin/bash^M という原文のメッセージを直接出すことはできなかった。この PC には Linux ディストリビューションが入っていない。本文に貼ったのは同じ仕組みを実行層で再現したものであり、メッセージの文言はシェルやディストリビューションによって異なりうる
  • 同じ理由で、この環境の bash がコマンド置換で CR を落とすことは確認したが、Linux の bash では CR が残るという対比を実行で確認することはできなかった
  • MS-DOS が CRLF を採り Unix が LF を採った経緯を示す一次資料は確認できなかった。本文には2つの制御文字の名前が指す動作と POSIX の行の定義までしか書いていない
  • レジストリファイルや一部の Windows ツールが CRLF を要求するという話は、検証の方法が安全でないため試しておらず、したがって本文には書いていない
  • バッチファイルの試験はこの1台の Windows 10 ビルド 19045.6466 でのみ行った。他の Windows のバージョンや他のバッチ構文で LF が問題を起こす可能性は排除できていない
  • dos2unix の最新配布版は 7.5.7(2026-08-27)だが、この環境のビルドは 7.5.2 だ。新しいバージョンで変わった動作は確認できなかった
  • git 公式文書のうち git-config のページは取得時に本文が途中で切れ、core.autocrlf の項目が読めなかった。そこで kernel.org ミラーの同じ文書で確認し、参考資料には実際に読んだほうを載せた

参考資料

  • gitattributes (Git 公式文書) — text、text=auto、eol=lf、eol=crlf の定義。eol 未指定時の既定が Windows では crlf、それ以外では lf という記述と git add --renormalize . の案内がここにある
