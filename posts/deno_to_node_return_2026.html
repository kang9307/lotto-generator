계기 — SvelteKit 프로젝트에서 다시 만난 Node

글쓴이 David Bushell은 이번 달 SvelteKit 기반 클라이언트 프로젝트에서 Node를 집중적으로 썼다고 적는다. 오랫동안 Deno를 기본 런타임으로 써 와서 Node를 다루는 법을 잊고 있었는데, 돌아와 보니 ECMAScript 문법이 지원되고 예전의 성가신 API가 교체되거나 현대화돼 있었다는 것이 글의 출발점이다. 그가 「가장 중요하다」고 꼽은 것은 require()를 볼 일이 없다는 점이다.

회고는 네 부분으로 이루어진다. 패키지 관리 도구 선택, TypeScript 실행, 자신의 정적 사이트 생성기를 Deno에서 Node로 옮긴 경험, 그리고 Deno를 떠난 이유다. 측정이나 비교 실험을 목적으로 쓴 글이 아니라 짧은 개인 기록이다. 「Deno를 계속 쓴 것은 습관과 익숙함 때문이었다」는 문장도 글쓴이 자신의 것이다.

아래에서는 글쓴이가 Node로 돌아가며 쓴 것들을 하나씩, 해당 공식 문서의 정의와 제한 옆에 놓는다. 런타임을 고를 때 갈리는 일반적인 축은 런타임을 다시 쓴다는 결정에 정리돼 있다.

버전 관리와 패키지 관리 — fnm과 pnpm

글쓴이는 Node 버전 전환 도구로 Fast Node Manager(fnm)를 골랐다. NVM과 npm에 대한 자신의 오래된 경험이 좋지 않았고, 버전 전환에는 fnm이 낫다는 말을 들었다는 것이 이유다. 최신 버전을 쓰는 편이지만 안정성을 요구하는 클라이언트 프로젝트가 있어 버전을 오갈 필요가 있다고 적는다. fnm README가 밝히는 특징은 다음과 같다.

  • 성격. README는 fnm을 Rust로 만든 빠르고 단순한 Node.js 버전 관리자라고 소개하고, 단일 파일이며 설치가 쉽고 즉시 시작된다는 점을 특징으로 든다.
  • 지원 플랫폼. macOS, Windows, Linux다.
  • 버전 파일. .node-version과 .nvmrc 파일을 인식한다.
  • 설치 경로. 설치 스크립트 외에 Homebrew, Winget, Scoop, Chocolatey, Cargo, 릴리스 바이너리를 안내한다.
  • 셸 설정. fnm env의 출력을 셸에서 평가해 환경 변수를 잡아야 쓸 수 있다. --use-on-cd 옵션을 붙인 예시가 Bash, Zsh, Fish, PowerShell별로 실려 있다.

패키지 관리자로는 pnpm을 골랐다. 글쓴이는 그 이유를 침해당하는 일을 피하기 위해서라고 적는다. 자신이 쓰는 스크립트 몇 개가 바이너리 이름을 고정해 두고 있어서 다음 두 별칭을 추가했다고 한다.

alias npm=pnpm
                    alias npx=pnpx

글쓴이는 나중에 덧붙인 주석에서, 이 별칭은 npm이 설치돼 있다고 가정한 설치 안내의 명령을 그대로 복사해 쓸 때 도움이 된다고 설명한다. 설정을 두는 곳은 pnpm 문서가 따로 정해 둔다. pnpm은 명령줄, 환경 변수, pnpm-workspace.yaml에서 설정을 읽고, .npmrc에서는 인증과 레지스트리 설정만 읽는다. 그 밖의 설정은 pnpm-workspace.yaml이나 전역 config.yaml에 둔다. 아래의 설정이 모두 pnpm-workspace.yaml에 들어가는 이유다.

pnpm의 설치 지연과 신뢰 정책 — minimumReleaseAge와 trustPolicy

글쓴이는 pnpm-workspace.yaml에 다음 두 줄을 추가했다.

minimumReleaseAge: 1440
                    trustPolicy: no-downgrade

minimumReleaseAge — 게시 후 경과 시간

pnpm 문서의 정의는 이렇다. minimumReleaseAge는 어떤 버전이 게시된 뒤 pnpm이 그것을 설치하기까지 지나야 하는 최소 시간을 분 단위로 정한다. 직접 의존성뿐 아니라 전이 의존성까지 모든 의존성에 적용된다. 문서는 목적을 「침해됐거나 결함이 있는 패키지를 설치할 위험을 줄이는 것」이라고 적고, 대부분의 경우 악성 릴리스는 한 시간 안에 발견돼 레지스트리에서 제거된다고 덧붙인다.

  • 도입 버전과 기본값. v10.16.0에 추가됐다. 기본값은 v11부터 1440이고 그 이전에는 0이다.
  • 1440의 뜻. 단위가 분이므로 1440은 하루다. 문서의 예시도 같은 값을 「적어도 하루 전에 릴리스된 패키지만 설치」로 설명한다.
  • 예외 목록. minimumReleaseAgeExclude에 패키지 이름을 적으면 그 패키지는 게시 즉시 설치된다. 패턴은 v10.17.0부터, 특정 버전 지정은 v10.19.0부터 쓸 수 있다.
  • 맞는 버전이 없을 때. minimumReleaseAgeStrict(v11.0.0)가 정한다. 값이 false면 조건을 채우지 못한 버전으로 물러나 설치를 이어 가고, true면 의존성 해석이 실패한다. 이 값은 minimumReleaseAge를 직접 설정했을 때 기본으로 true가 되고, 내장 기본값 1440만 쓰는 경우에는 하위 호환을 위해 엄격하지 않게 동작한다.
  • 게시 시각이 없는 레지스트리. minimumReleaseAgeIgnoreMissingTime(v11.0.0, 기본 true)이 켜져 있으면 메타데이터에 time 필드가 없는 패키지는 이 검사를 건너뛴다.

글쓴이는 처음에 이 값을 「한 달」로 잡았다가, pnpm이 맞는 버전을 고르는 데 어려움을 겪는 의존성 문제가 생겨 「하루」로 낮췄다고 적는다. 그가 적은 1440은 문서의 v11 기본값과 같은 숫자다. 다만 값을 파일에 직접 적으면 위의 엄격 모드가 기본으로 켜진다는 점이 다르다. 한 달로 잡았을 때의 문제가 이 엄격 모드와 관련됐을 가능성은 문서 문구에서 나온 해석이며, 원문은 원인을 설명하지 않는다.

trustPolicy — 신뢰 수준이 내려간 버전

pnpm 문서에 따르면 trustPolicy를 no-downgrade로 두면, 패키지의 신뢰 수준이 이전 릴리스보다 낮아졌을 때 설치가 실패한다. 문서가 든 예는 이전에는 신뢰된 게시자(trusted publisher)가 게시했는데 지금은 출처 증명(provenance)만 있거나 신뢰 증거가 전혀 없는 경우다.

  • 도입 버전과 기본값. v10.21.0에 추가됐고 기본값은 off다. 값은 no-downgrade와 off 둘이다.
  • 비교 기준. 신뢰 검사는 semver가 아니라 게시 날짜만을 기준으로 한다. 더 일찍 게시된 버전 가운데 더 강한 신뢰 증거를 가진 것이 하나라도 있으면 그 패키지는 설치할 수 없다.
  • 프리릴리스. v10.24.0부터 정식 버전을 설치할 때 프리릴리스 버전의 신뢰 증거는 평가에서 제외된다.
  • 예외 목록. trustPolicyExclude(v10.22.0)에 적은 패키지나 버전은 검사에서 빠진다.
  • 오래된 버전. trustPolicyIgnoreAfter(v10.27.0)는 게시된 지 지정한 분 수보다 오래된 패키지에 대해 검사를 무시하게 한다.

글쓴이는 자체 호스팅하는 Forgejo 인스턴스로 옮긴 뒤 자신의 패키지가 「provenance」를 잃었고, 자기 패키지를 허용하도록 pnpm의 신뢰 정책을 설정해야 했다고 적는다. 어떤 키를 썼는지는 원문에 없다. 문서에서 그 용도에 해당하는 설정은 trustPolicyExclude다.

설치 스크립트 차단 — allowBuilds와 strictDepBuilds

글쓴이는 「pnpm은 post-install 스크립트도 차단한다」고 한 줄로 적는다. pnpm 문서에서 이 동작을 정하는 설정은 다음과 같다.

  • 기본 동작. allowBuilds에 적히지 않은 패키지는 기본으로 스크립트 실행이 허용되지 않고 「검토되지 않은」 것으로 취급된다.
  • 오류인가 경고인가. strictDepBuilds의 기본값이 true이므로 기본으로는 오류가 출력되고, 검토되지 않은 빌드 스크립트(문서 표현으로 postinstall 스크립트)를 가진 의존성이 있으면 설치가 0이 아닌 종료 코드로 끝난다. false로 두면 경고로 바뀐다.
  • 허용 방법. allowBuilds는 패키지 선택자를 키로 하는 맵이고, true는 허용, false는 불허다. 설치 중 스크립트가 무시된 의존성은 pnpm-workspace.yaml에 자리 표시 값과 함께 자동으로 추가되고, pnpm approve-builds와 pnpm add의 --allow-build 플래그도 같은 곳에 기록한다.
  • 이전 설정. onlyBuiltDependencies, neverBuiltDependencies, ignoredBuiltDependencies 등은 v11에서 제거되고 allowBuilds로 대체됐다.
  • 전부 허용. dangerouslyAllowAllBuilds(v10.9.0, 기본 false)를 true로 두면 의존성의 preinstall, install, postinstall 스크립트가 승인 없이 실행된다. 문서는 전이 의존성까지 포함해 지금과 앞으로의 모든 스크립트가 허용된다는 경고를 붙인다.
  • ignoreScripts와의 차이. ignoreScripts(기본 false)는 프로젝트의 package.json과 의존성에 정의된 스크립트를 일절 실행하지 않는 별개의 설정이다.

원문은 npm 쪽 동작을 물음표가 붙은 한 문장으로만 남긴다. 원문이 이름을 든 공급망 사례는 Shai-Hulud 하나이며, 그 경과는 npm 공급망 공격 분석에서 다루었다.

Node의 타입 제거 — 문서가 정의하는 범위

글쓴이는 Node가 이제 TypeScript를 실행할 수 있다고 적는다. Node.js v26.10.0 문서 「Modules: TypeScript」는 런타임에서 TypeScript를 쓰는 길을 둘로 나눈다. TypeScript의 모든 문법과 기능을 온전히 지원하려면 서드파티 패키지를 쓰고(문서는 tsx를 예로 든다), 가벼운 지원으로는 내장 타입 제거(type stripping)를 쓴다.

내장 기능의 정의는 짧다. Node.js는 기본으로, 지울 수 있는(erasable) TypeScript 문법만 담은 TypeScript 파일을 실행한다. TypeScript 문법은 공백으로 치환한다. 타입 검사는 하지 않는다. 이 기능을 끄려면 --no-strip-types 플래그를 쓴다. 문서의 변경 이력은 다음과 같다.

  • v22.6.0. 타입 제거가 추가됐다.
  • v23.6.0, v22.18.0. 타입 제거가 기본으로 켜졌다.
  • v24.3.0, v22.18.0. 실험 기능 경고를 더 이상 내지 않는다.
  • v25.2.0, v24.12.0. 타입 제거가 안정(stable) 단계가 됐다.
  • v26.0.0. --experimental-transform-types 플래그가 제거됐다. v22.7.0에 추가됐던 플래그다.
항목 Node.js의 동작 문서의 절

parameter properties, import aliases 오류 TypeScript features

.tsx 파일 지원하지 않음 Determining module system

문서는 이 범위가 의도된 것이라고 설명한다. JavaScript 코드 생성이 필요한 문법을 일부러 지원하지 않고 인라인 타입을 공백으로 바꾸기 때문에, 소스 맵 없이 TypeScript 코드를 실행할 수 있다는 것이다. 데코레이터에 대해서는 현재 TC39 Stage 3 제안이어서 변환하지 않으며, JavaScript가 네이티브로 지원하기 전에는 지원하지 않는다고 적는다. 권장 사항으로는 TypeScript 5.8 이상과 다음 tsconfig.json 설정을 든다.

{
                      "compilerOptions": {
                         "noEmit": true, // Optional - see note below
                         "target": "esnext",
                         "module": "nodenext",
                         "rewriteRelativeImportExtensions": true,
                         "erasableSyntaxOnly": true,
                         "verbatimModuleSyntax": true
                      }
                    }

문서의 주석에 따르면 noEmit은 빌드 스크립트처럼 *.ts 파일을 실행만 할 때 쓰고, *.js 파일을 배포할 생각이면 필요 없다. 모듈 체계도 변환하지 않는다. .ts 파일의 모듈 체계는 .js와 같은 방식으로 정해지고, .mts는 항상 ES 모듈로, .cts는 항상 CommonJS로 실행된다. import 문에는 파일 확장자가 필수여서 import './file.ts'처럼 적는다. tsconfig의 paths는 변환되지 않아 오류가 나며, 문서는 가장 가까운 기능으로 #으로 시작해야 하는 subpath imports를 든다. 파일이 아닌 입력 가운데 --eval과 STDIN에서는 타입 제거를 쓸 수 있다.

node_modules 아래에서는 타입을 제거하지 않는다

글쓴이가 부딪힌 것은 위 표의 마지막 줄이다. 그는 TypeScript 패키지를 npm에 그대로 게시할 수는 없다고 적으며 다음 오류를 보여 준다.

error: [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]:
                    Stripping types is currently unsupported for files under node_modules

Node.js 오류 문서는 ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING을 「node_modules 디렉터리의 하위에 있는 파일에는 타입 제거가 지원되지 않는다」고 설명하며, v22.6.0에 추가된 오류 코드라고 적는다. 타입 제거 기능 자체와 같은 버전이다. 이유는 TypeScript 문서의 「Type stripping in dependencies」 절에 한 문장으로 적혀 있다. 패키지 작성자가 TypeScript로 작성된 패키지를 게시하는 것을 막기 위해, Node.js는 node_modules 경로 아래 폴더에 있는 TypeScript 파일의 처리를 거부한다는 것이다.

글쓴이는 이 제한을 「기술적이라기보다 철학적」이라고 평한다. 문서가 밝힌 이유가 구현상의 한계가 아니라 게시 관행에 대한 것이라는 점에서, 그 읽기는 문서 문구와 어긋나지 않는다. 그는 ECMAScript에 가벼운 「네이티브 타입」이 들어오기를 바란다고 적고, 타입 주석 제안이 있다는 점을 언급하면서도 결실을 보기 전에 자신이 은퇴할 것 같다고 덧붙인다. 이 제한이 글쓴이의 작업에 남긴 결과는 세 가지다.

  • 번들러. TypeScript 패키지를 그대로 게시할 수 없으므로 번들 도구가 필요해졌고, 글쓴이는 Tsdown을 썼다. 추가된 설정 파일은 둘이다.
  • 설정 파일 수. 그는 deno.json 등을 지운 것과 합치면 본전이라고 적는다.
  • 출처 증명. 자체 호스팅 Forgejo로 옮긴 뒤 패키지의 provenance가 사라졌고, 앞 절의 신뢰 정책 예외가 필요해졌다.

정적 사이트 생성기 이전 — 바꾼 것과 15%라는 값

글쓴이가 Node에 대한 마지막 시험으로 삼은 것은 자신의 정적 사이트 생성기를 Deno에서 옮기는 일이었다. 그는 Node 버전으로 몇 개 전만 해도 큰 리팩터링이 필요했을 일이, Node v26.10.0에서는 뜻밖에 할 일이 적었다고 적는다.

  • 파일 시스템. 필수 변경의 첫째는 Deno의 파일 시스템 API를 node:fs로 바꾸는 것이었다. 그는 node:fs가 자신이 기억하는 약 10년 전보다 크게 나아졌다고 적는다.
  • HTTP 서버. 둘째는 Deno.serve를 Hono의 node 어댑터로 바꾸는 것이었다. 글쓴이는 이 어댑터를 node:http를 감싼 것이라고 설명한다.
  • 경로 모듈. 그 뒤에 한 추가 변경은 Deno의 @std/path를 node:path로 바꾼 것 하나이며, import만 바꾸면 되는 교체였다고 한다.
  • 빌드 시간. 이 최소한의 이전을 마친 뒤 빌드가 15% 빨라졌다고 적는다.
  • 남은 여지. 코드베이스는 여전히 Deno의 관용적 작성 방식을 따르고 있고, 다른 내장 Node API를 쓰지 않아 성능을 남겨 두고 있을 것이라고 그는 추측한다.

15%는 글쓴이 한 사람의 사이트 생성기 하나에서 나온 값이다. 원문에는 빌드에 실제로 걸린 시간, 사이트 규모, 측정 횟수, 비교한 Deno 버전이 없다. 이 숫자는 같은 코드를 최소한으로 고쳐 옮겼을 때 글쓴이의 환경에서 빌드가 느려지지 않았다는 기록이며, 두 런타임의 일반적인 성능 차이를 말하는 값이 아니다.

글쓴이가 든 이탈 이유와 이 사례의 범위

글쓴이가 Deno를 떠나게 된 직접적인 계기로 든 것은 세 가지다.

  • 몇 주 동안 이어진 ZSH 통합 문제
  • JSR의 「429 (Too Many Requests)」 응답
  • 동시 HTTP 요청에서 Deno가 막히는 버그

세 항목 모두 원문에 한 줄씩만 적혀 있고, 버전이나 재현 조건, 이슈 링크는 없다. JSR 지원팀이 요청에 따라 계정을 빠르게 삭제해 주었고, 자신의 패키지는 보이지 않지만 예전 버전은 여전히 설치할 수 있다는 서술도 있다. 원문에는 이 밖에 Deno를 만드는 회사의 방향에 대한 글쓴이의 평가가 실려 있는데, 그것은 개인의 의견이며 위의 기술 사실과는 별개다. 글쓴이가 쓴 것들을 공식 문서와 나란히 놓으면 다음과 같다.

글쓴이가 쓴 것 공식 문서의 정의 문서가 밝힌 제한·조건
fnm Rust로 만든 Node.js 버전 관리자. .node-version과 .nvmrc를 인식 셸에서 fnm env 출력을 평가하는 설정이 필요
pnpm minimumReleaseAge 게시 후 설치까지 지나야 하는 최소 분. 전이 의존성 포함 직접 설정하면 맞는 버전이 없을 때 해석이 실패(엄격 모드)
pnpm trustPolicy 신뢰 수준이 이전 릴리스보다 낮아진 버전의 설치 실패 semver가 아니라 게시 날짜 기준. 예외는 trustPolicyExclude
pnpm의 설치 스크립트 차단 allowBuilds에 없는 패키지는 스크립트 불허 기본으로 오류와 0이 아닌 종료 코드. 필요한 빌드는 패키지별 승인
Node의 타입 제거 지울 수 있는 문법만 공백으로 치환해 실행 타입 검사 없음. 변환이 필요한 문법은 오류. node_modules 아래는 거부
node:fs, node:path, Hono의 node 어댑터 — —

이 사례가 말해 주는 범위는 좁다. 한 사람이 자신의 정적 사이트 생성기 하나를 Node v26.10.0으로 옮긴 기록이다. 글쓴이 스스로도 Deno를 계속 쓴 이유를 습관과 익숙함이라고 적고, 요즘은 서버 쪽 JavaScript를 쓰는 일에 그다지 의욕이 없었다고 덧붙인다. 다른 종류의 작업이나 다른 규모의 코드베이스에서 같은 결과가 나오는지는 원문만으로는 알 수 없다. Node 쪽에서 얻은 것에도 값이 붙어 있다. 타입 제거는 타입 검사를 하지 않고, 글쓴이의 경우 패키지를 게시하는 데 번들 단계가 필요해졌으며, 신뢰 정책은 자기 패키지를 허용하는 설정을 따로 요구했다.

확인하지 못한 것

  • 15%의 측정 조건. 빌드에 실제로 걸린 시간, 사이트 규모, 측정 횟수, 비교 대상 Deno 버전, 실행 환경은 원문에 없다.
  • 「한 달」로 잡았을 때의 오류. 오류 메시지와 실제로 적은 분 값은 원문에 없어, 문제의 원인을 문서의 어느 설정과 연결할지 확인하지 못했다.
  • 글쓴이의 pnpm 버전. 원문에 적혀 있지 않다. 문서상 trustPolicy는 v10.21.0 이상에서 쓸 수 있다는 점까지만 알 수 있다.
  • 신뢰 정책 예외에 쓴 키. 자기 패키지를 허용했다는 서술만 있고 설정 내용은 없다.
  • Tsdown 설정. 추가됐다는 두 설정 파일이 무엇인지는 원문에 없다.
  • Deno 쪽 세 가지 문제의 상세. 해당 버전, 재현 조건, 이슈 번호가 없어 현재도 재현되는지 확인하지 못했다.
  • NVM 설치 안내에 대한 서술. Node 공식 문서가 스크립트를 bash로 넘기는 방식의 NVM 설치를 권한다는 것은 글쓴이의 서술이며, 해당 안내문은 근거 자료에 포함하지 않았다.
  • npm의 설치 스크립트 기본 동작. 원문은 질문으로만 남겼고, npm 문서는 근거 자료에 포함하지 않았다.
  • 타입 주석 제안의 현재 단계. 원문은 제안이 있다는 사실만 언급한다.
