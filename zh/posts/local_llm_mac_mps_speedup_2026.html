Mac 上本地 LLM 慢的真正原因 - 确认 GPU 是否在工作并把它打开

设备被识别和设备真的在跑，是两回事

2026年8月4日 IT/技术

引言：不是 Mac 慢，是 GPU 在闲置

在 MacBook 上跑本地 LLM，风扇狂转、电池飞速掉电，token 却一个字一个字往外蹦。到这一步接下来的动作基本是固定的：换更小的模型，把量化压得更狠，再不行就得出「Mac 果然不行」的结论。

但在这个状态下打开活动监视器、调出 GPU 历史窗口，经常会看到 GPU 占用率几乎贴着地板。苹果芯片的 GPU 在闲着，只有 CPU 核心全部拉满。不是模型太大，是计算跑在了错误的设备上。

这种情况在自己拼装流水线时尤其容易出现。模型加载的代码是从别处抄来的，那段代码写的是有 CUDA 就用 GPU、没有就退回 CPU。Mac 上没有 CUDA，于是那个分支不报任何错误地走了 CPU 路径。这不是失败，是静默回退，日志里什么都不会留下。

本文处理的正是这个位置：如何确认此刻是否在用 GPU，各框架里真实存在的开关，以及打开之后仍然不变快的五种情况。选新硬件的话题在本地 LLM 硬件选择指南里讲过，量化格式压到什么程度在本地 LLM 运行指南 - 硬件要求与 GGUF 量化取舍里讲过，这里不重复。本文要处理的是让你手上已有的这台 Mac 用起 GPU 来。

顺带一提，这个话题重新被讨论的契机，是某位开发者把自己流水线的优化记录发到了社区：一行代码的改动让总运行时间少了近一半。但把那个倍数直接搬过来毫无意义，理由在后文单独整理。

1. 统一内存 - 为什么在 Mac 上「挪到 GPU」是另一个意思

先把结构弄清楚，后面的话才立得住。在装了 NVIDIA 显卡的 PC 上，用 GPU 意味着把数据复制进显存。系统内存和显存是物理上不同的芯片，两者之间的往返拷贝就是成本。所以 CUDA 代码永远在操心什么东西放在哪里。

苹果芯片在这里不一样。按 MLX 文档的说法，CPU 和 GPU 直接访问同一个内存池。数组不需要指定放在哪里，它就在统一内存里；需要指定的反而是运算要在哪个设备上执行。这个差别在实务上带来三个结果。

  • 没有拷贝成本。CPU 预处理和 GPU 推理混着来，在交界处不会触发传输
  • 模型大小的上限由整机内存决定，而不是显存。单张 16GB 显卡装不下的模型，在统一内存 64GB 的机器上装得下
  • 代价是出现了竞争。浏览器和 IDE 吃掉的内存，就是模型拿不到的内存。显存独立时不存在这个问题

在 PyTorch 的术语里这个设备叫 MPS。官方文档的说法是，它引入了一个新设备，把机器学习的计算图和原语分别映射到 Metal Performance Shaders Graph 框架以及 Metal Performance Shaders 提供的调优内核上。概括起来就是把 PyTorch 接到苹果 GPU 计算栈上的后端。

这里有一个常见的期待偏差。统一内存的意思是「内存可以用得宽裕」，不是「内存带宽宽裕」。LLM 解码每出一个 token 都要把权重扫一遍，是受内存带宽支配的工作，所以同样的统一内存容量下，不同芯片档次的每秒 token 数会拉开很大差距。容量决定装不装得下，带宽决定跑得多快。两个轴不要混。

2. 各框架的开关 - PyTorch、llama.cpp、MLX

只列真实存在的开关。关键在于各框架的默认值不同：有的需要你打开，有的本来就开着。

技术栈GPU 默认状态如何打开如何关掉做对照
PyTorch关闭。不指定就是 CPU设备字符串 "mps"改成 device="cpu" 跑同一份代码
llama.cpp开启。macOS 上 Metal 默认启用无需额外操作--device none
MLXGPU 是默认执行设备无需额外操作给运算传 stream=mx.cpu

2.1 PyTorch - 要挪的东西有两样

PyTorch 不指定就是 CPU，所以必须在代码里直接指定设备。

import torch

print(torch.backends.mps.is_available())  # 这台机器现在能不能用
print(torch.backends.mps.is_built())      # 装的这个构建里有没有 MPS

device = "mps" if torch.backends.mps.is_available() else "cpu"
model = model.to(device)
inputs = inputs.to(device)   # ← 最常被漏掉的就是这一行

最常见的失误就是最后一行。只把模型挪过去、把输入张量留在 CPU 上，要么报设备不匹配的错，要么某个库悄悄帮你对齐，于是每一步都夹进一次传输。用两个检查函数也有明确理由：is_available() 为假是机器或 macOS 版本的问题，is_built() 为假是你装的 PyTorch 构建里没有 MPS。后者重装能解决，前者重装永远解决不了。

失败时 PyTorch 给出的文字，本身就把这两种情况区分开了。一种是 「MPS not available because the current PyTorch install was not built with MPS enabled.」，另一种是 「MPS not available because the current macOS version is not 14.0+ and/or you do not have an MPS-enabled device on this machine.」。把提示读到最后，答案已经写在里面了。

2.2 llama.cpp - 它本来就开着，要学的是怎么关

如果你用 llama.cpp 跑 GGUF 模型，不用去找开关。官方构建文档明确写着macOS 上 Metal 默认启用。这里要学的是反方向，也就是为了做出对照组而关掉它。

# GPU 层数设为 0：GPU 推理关闭，但部分算子仍可能走 GPU
llama-cli -m model.gguf -ngl 0 -p "你好"

# 彻底关闭：禁用全部 GPU 加速
llama-cli -m model.gguf --device none -p "你好"

两个选项的差别很关键。文档指出即使用了 -ngl 0，部分计算仍可能被 GPU 加速。所以想诚实地量出「没有 GPU 要多久」，就得用 --device none。不知道这一点而只拿 -ngl 0 做对比，基准线其实已经吃了 GPU 的好处，算出来的倍数会比真实值小。

也可以在构建阶段直接剥掉。给 CMake 传 -DGGML_METAL=OFF 就会构建出不带 Metal 的版本。如果你自己编的二进制跑得慢，先确认这个标志有没有混进构建里。

2.3 MLX - 不挪设备，而是给运算指定设备

苹果开源的 MLX 是围绕统一内存设计的，思路本身就不同。它没有搬移数组的 API，而是通过 stream 参数给运算指定执行设备。

import mlx.core as mx

a = mx.random.normal((4096, 512))
b = mx.random.uniform(shape=(512,))

c = mx.add(a, b, stream=mx.gpu)   # 在 GPU 上
d = mx.add(a, b, stream=mx.cpu)   # 同样的数组，在 CPU 上

要点是同样的数组 a、b 在两边被使用而不发生拷贝。存在依赖时，MLX 的调度器会在两个流之间自动插入依赖以保证顺序。文档里有一个把重活放 GPU、轻活放 CPU 并行执行的例子，达到了约 2 倍。不过这是文档示例负载下的数字，不代表 LLM 推理也是如此。

3. 确认当前是否在用 GPU 的三个步骤

这是本文的核心。三层必须分开确认。只看其中一层，一定会得出错误结论。

3.1 第一层 - 设备有没有被识别

这是代码层面的确认，把前面的 is_available() 和 is_built() 都打印出来。这一步大多数环境都能过。而过了这一步并不代表你在用 GPU。设备存在，和你的代码用了它，是两件事。

3.2 第二层 - 它是否真的在跑

这是系统层面的确认。让推理跑着，用下面两种方式之一。

  • 打开活动监视器，从顶部菜单的窗口项调出 GPU 历史窗口。推理开始时曲线应该抬起来
  • 在终端运行 sudo powermetrics --samplers gpu_power -i 1000 -n 5 看 GPU 相关数值，需要管理员权限

判读规则很简单：推理正在跑、GPU 曲线却是平的、CPU 核心全被占满，那么无论设备检查是否通过，计算都在 CPU 上。反过来，如果 GPU 曲线抬起来了但占用率在低位反复抖动，就该怀疑下一节讲的 CPU 回退了。

3.3 第三层 - 它有没有占住内存

PyTorch 提供了可以直接查看这一点的函数。三个一起打印，状态一目了然。

import torch

# 张量实际占用的 GPU 内存（字节）
print(torch.mps.current_allocated_memory())

# Metal 驱动为该进程分配的 GPU 内存总量（字节）
print(torch.mps.driver_allocated_memory())

# 推荐的最大工作集大小（字节）
print(torch.mps.recommended_max_memory())
  • current_allocated_memory() 接近零 → 模型没落到 GPU 上，回去检查设备指定
  • driver_allocated_memory() 逼近 recommended_max_memory() → 已经进入下一节说的内存压力区间
  • 两个都正常却还是慢 → 这不是设备问题，去看测量方法或工作负载的形态

按顺序过完这三层，诊断就完成了。「打开 GPU 了却没变快」这类问题，一半以上其实卡在 3.2。

4. 正确测量 - 谈倍数之前要先具备的条件

开关打开之后，接下来要量到底快了多少。而在这一步出错的人，和根本没打开开关的人一样多。MPS 尤其是异步的，表放错位置就会得到远好于现实的数字。

4.1 不做同步，内核没跑完表就停了

torch.mps.synchronize() 的文档说明是等待 MPS 设备上所有流中的所有内核完成。不用它，Python 在把内核塞进队列的一瞬间就走到下一行，表量到的是提交时间。

import torch, time

def timed(fn, warmup=1, runs=3):
    for _ in range(warmup):          # 丢掉首次运行成本
        fn()
    torch.mps.synchronize()

    times = []
    for _ in range(runs):
        torch.mps.synchronize()
        t0 = time.perf_counter()
        fn()
        torch.mps.synchronize()      # 等跑完再停表
        times.append(time.perf_counter() - t0)

    times.sort()
    return times[len(times) // 2]    # 中位数

4.2 必须固定的条件

要谈倍数，下面这些必须全部保持一致，只改设备。有任何一项在晃，那个数字就什么都证明不了。

  • 相同提示词、相同最大生成 token 数。输出长度不同，耗时不同是理所当然的
  • 相同随机种子。PyTorch 里用 torch.mps.manual_seed() 固定
  • 丢掉至少一次预热，取三次以上的中位数。用中位数而不是平均值，是因为一次后台任务就能毁掉整个平均值
  • 固定供电状态。两次测量的电源适配器连接状态和低电量模式要一致
  • 清理后台进程。公司配发设备的安全代理或备份守护进程跑起来的那一轮，直接作废
  • 把预填充和解码分开看。首 token 时间和之后的每秒 token 数瓶颈不同，合成一个数字就看不出到底哪里改善了

4.3 对外报数字时必须一并写清的东西

同理，你在别处看到的倍数，如果没有下面这些信息，那个数字没有参考价值。分享自己的结果时也一样。

  • 芯片档次与 GPU 核心数、统一内存容量
  • 模型名称与参数规模、量化类型
  • 上下文长度、实际生成的 token 数、批大小
  • 对照对象是什么（CPU 执行、-ngl 0，还是 --device none）
  • 如果谈的是整条流水线的时间，其中能挪到 GPU 的区段原本占多少比例

最后一项是决定性的。总共八分钟的流水线里，如果原本有六分钟能挪到 GPU，砍掉一半是可行的；如果只有两分钟能挪，再怎么调也下不到两分钟以下。倍数是那条流水线的构成造出来的，不是开关造出来的。

5. 打开之后仍然不变快的五种情况

还有一种情况：开关确实打开了，GPU 曲线也抬起来了，体感却毫无变化。原因通常是下面五种之一。

原因症状确认方法应对
不支持算子的 CPU 回退GPU 占用率在低位起伏，CPU 也跟着跳把回退环境变量关掉后运行，看哪个算子抛出 NotImplementedError把该算子换成受支持的写法，或升级上游库
首次运行成本只有第一次特别慢，第二次开始正常预热之后重新测测量时丢掉第一次。做成服务就在启动时跑一次空推理
批大小为 1、提示词短跑分变好了，聊天窗口里却感觉不到加大批和提示词长度后重测合并成批处理作业。交互式用法本来收益就小
内存压力与交换一开始还行，中途急剧变慢且硬盘在响比较 driver_allocated_memory() 和 recommended_max_memory()加大量化力度或缩短上下文，关掉其他应用
测量错误倍数好得不像话把计时用 torch.mps.synchronize() 包起来重测修测量代码。结果砍半才是正常的

5.1 CPU 回退 - 方便，但不免费

遇到 MPS 尚未实现的算子时，PyTorch 会报错。这时用到的就是 PYTORCH_ENABLE_MPS_FALLBACK。文档的说明是设为 1 时，该变量会把 MPS 不支持的运算回退到 CPU。

export PYTORCH_ENABLE_MPS_FALLBACK=1
python app.py

打开它，程序就跑得起来了。但跑得起来和跑得快是两回事。每一个被回退的算子都会制造一次 CPU 与 GPU 之间的往返，如果那个算子在循环里，倍数会整个消失。所以正确的顺序是：先把回退关掉跑一遍，拿到出问题的算子名字，再看能不能绕开；只有绕不开时，才带着回退开着运行。一开始就打开，你永远不会知道到底是什么在拖后腿。

这个变量是从进程环境里读的。如果要在 Python 代码里用 os.environ 设置，必须放在 import torch 之前，更稳妥的做法是在 shell 里 export。PyTorch 的 issue 跟踪器和论坛上，反复有人报告在 import 之后设置完全无效。

5.2 批大小为 1 是结构性限制

GPU 大幅甩开 CPU 的条件是同一种运算被大批量并行处理。而交互式的本地 LLM 恰恰相反：批为 1、提示词短、一次一个 token。解码阶段受制的与其说是算力，不如说是从内存里读出权重的速度。

于是同一台机器上会出现不对称：预填充阶段快很多，解码阶段快得有限。喂进长文档、让它简短作答的任务体感明显；简短提问、让它长篇输出的任务体感很小。这是任务的性质，不是靠设置能翻转的东西。从结构上提高解码速度的思路，在投机解码那一侧的技术里讲过。

6. 统一内存容量与模型规模 - 先用算术筛一遍

「16GB 的 MacBook 能跑什么」这个问题可以用算术回答。权重占用的容量是参数量 × 每参数字节数。16 位是每参数 2 字节，8 位是 1 字节，4 位是 0.5 字节。

模型规模16 位8 位4 位想跑得舒服需要
3B约 6GB约 3GB约 1.5GB8GB 以上
7〜8B约 16GB约 8GB约 4GB16GB
13〜14B约 28GB约 14GB约 7GB16GB 吃紧 · 建议 24GB
30〜32B约 64GB约 32GB约 16GB32GB 吃紧 · 建议 48GB
70B约 140GB约 70GB约 35GB64GB 以上

表里的数字是只算权重的算术值。实际使用中还要叠上三样东西。

  • 系统和常驻应用的份额。macOS 本身、浏览器、编辑器长期占着好几 GB
  • KV 缓存。大致随上下文长度成比例增长。喂进长文档的那一刻，最先崩的就是这里
  • 量化类型带来的余量。四比特级的 GGUF 也会把部分张量保留在更高精度上，所以文件比算术值大。请按真实文件大小来算，而不是按公式

所以「32GB 减掉 32B 四比特的 16GB，还剩一半」这个推理不成立。真按这个装上去，这台 Mac 基本干不了别的事。表格最后一列应当读作「还能同时干别的事的那条线」，而不是「最多能装下多少」。各量化档位的质量损失能接受到什么程度，可以参考GGUF 量化取舍的整理。

统一内存后期加不了。苹果芯片的内存封装在 SoC 上，买完之后无法扩容。挑机器时（包括二手），这一项是唯一不可逆的决定。今天觉得 8B 够用而选了最低配，一年后想跑 30B 时就没有办法了。

7. 与 CUDA 的差异在哪里

把在 PC 上养成的直觉原样搬过来，有些地方会错位。按维度整理如下。

维度Mac（Metal / MPS）NVIDIA（CUDA）
内存结构统一内存。CPU 与 GPU 直接访问同一池显存独立。需要主机与设备之间的拷贝
扩大规模的方向内存堆得更大的单台机器多张卡
算子覆盖度仍有缺口，因此单独存在 CPU 回退开关覆盖广到不需要回退开关
状态查看工具活动监视器 GPU 历史、powermetricsnvidia-smi
可调的旋钮以引擎选项为主（-ngl、--device 等）一直开放到内核与编译器层面
二手市场的应对内存不可升级，只能整机更换只换或加显卡即可

由此得出一个实务上的结论：Mac 强在「先把大模型装进去」，弱在「把装进去的模型榨到最快」。在统一内存 64GB 的机器上跑 70B 级模型，是单张卡模仿不了的；但装好之后在内核层面继续拉高每秒 token 数的空间，CUDA 生态要宽得多。知道这个不对称，在 Mac 上该做什么、不该做什么就清楚了。

8. 什么时候该放弃本地转用 API

有时开关全都打开、测量也做对了，仍然达不到目标延迟。这时候在同一台机器上能再榨出来的余地通常不大。剩下的选项只有三个，代价都很明确。

  • 换更小的模型 → 拿质量去换
  • 换机器 → 拿钱去换，而且统一内存无法扩容，只能整机替换
  • 转用 API → 数据会离开你的环境，并产生按调用计费的成本

选哪个取决于条件。符合下面这些就继续留在本地。

  • 数据不能离开组织。在这个条件下速度不是可以谈判的东西
  • 调用频率高、提示词短的重复性工作，比如分类、打标签、抽取
  • 需要离线运行，或者网络本身不稳定
  • 延迟可以慢，但必须可预测。外部 API 在高峰时段的波动才是更大的麻烦

反过来，符合下面这些就交给 API。

  • 模型质量直接决定成果物的价值，比如终稿、面向客户的文案
  • 需要的规模超过机器内存，比如 32GB 的机器上要跑 70B
  • 上下文很长。KV 缓存会吃统一内存，这是本地最先崩掉的那个维度
  • 多人同时使用。单台 Mac 应付并发请求的能力很弱

现实的答案通常是两者混用。预处理、分类、初次摘要放在本地，只把最终生成发出去，既压低了调用量，又只在需要质量的地方花钱。这种配置下如何切换和路由模型，在用 LLM 路由器把多个模型收成单一 API里讲过；把本地模型当作智能体来跑时的另一组约束，整理在本地 LLM 智能体开发为什么需要工具检索与人工介入里。

9. 中文环境下用 Mac 跑本地 LLM 要注意的

9.1 每秒 token 数相同，体感速度也不同

速度指标几乎都以每秒 token 表示，但同一句话被切成多少个 token，取决于语言和分词器。所以把按英文得出的每秒 token 数直接搬到中文任务的体感上会偏。更快的做法是先数一数你实际要输入的中文文本，在自己模型的分词器下变成多少个 token。要粗略估算 token 数，用下面工具列表里的 token 计算器即可。

9.2 内网隔离环境下，检查开关不是性能问题

在金融、政务这类外部 API 调用被封的环境里，本地不是选项而是前提。此时 GPU 有没有被用上，不是「能不能更快」的问题，而是「能不能用」的问题。在 CPU 上跑着做选型评估，会得出性能达不到要求的结论，而那个结论可能来自配置而不是模型。做采纳决定之前，务必先过一遍第 3 章的三层。顺序反了，会把本来合格的候选淘汰掉。

9.3 公司配发设备带来的变量

公司配发的 Mac 上常驻安全代理和资产管理工具的情况很多。它们周期性占用 CPU 时，测量值会一轮一轮地抖。第 4 章建议用中位数而不是平均值，原因也包括这一条。测量过程中出现意外的尖峰，就把那一轮丢掉重测。

9.4 买二手 Mac 时的检查顺序

如果目的是跑本地 LLM，在二手市场挑 Mac 的检查顺序是固定的。

  • 统一内存容量排第一。无法扩容，是唯一不可逆的项目
  • 芯片档次排第二。容量相同时内存带宽不同，解码速度被它锁死
  • 存储排第三。模型文件很大，但外置硬盘能顶上
  • 代际差异是定完上面三项之后才看的。就能装下哪些模型而言，内存大的旧一代胜过内存小的新一代

11. 结论：不是一个开关，而是一个顺序

Mac 上本地 LLM 慢的时候，首先该怀疑的不是模型大小，而是计算跑在哪里。而且这件事不需要猜，三分钟就能确认。

顺序整理如下。

  1. 确认设备是否被识别。PyTorch 里把 is_available() 和 is_built() 都打印出来。两种失败提示的原因完全不同
  2. 看它是否真的在跑。推理进行时活动监视器的 GPU 历史有没有抬起来。绝大多数环境卡在这一步
  3. 看它有没有占住内存。driver_allocated_memory() 接近零就说明模型不在 GPU 上
  4. 正确测量。用 torch.mps.synchronize() 包住，丢掉预热，取中位数。跳过这一步，之后所有判断都会摇晃
  5. 还是不快，就按顺序排除五个原因。CPU 回退、首次运行成本、批大小、内存压力、测量错误

最后把倍数这件事说完。「一行代码快多少倍」这种形式的数字，只取方向、丢掉数量级才是对的。原来不用 GPU 的流水线改成用 GPU 之后会明显变快，这个结论来自结构，不会动摇。但那个倍数，是由那个人的芯片、那个人的模型，以及那个人的流水线里 GPU 区段所占的比重共同造出来的。

现在就该做的只有一件事：在正在跑的推理旁边调出活动监视器的 GPU 历史窗口。如果曲线是平的，该换的不是模型。
