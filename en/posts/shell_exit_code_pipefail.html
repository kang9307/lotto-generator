Shell Exit Codes and set -e - What It Catches and What It Misses

Opening every blind spot of errexit, pipefail and nounset with real execution output

2026-07-29 Dev & Infra

Introduction: CI was green and the deployed value was empty

Here is a script with set -euo pipefail at the top. It reads two values from a config file and assembles a cleanup command. I ran it with those keys missing from the config file. This is the result.

  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

Both unread values became empty strings and flowed straight through. The assembled command line ends at /srv/backup/ and the retention count vanished entirely, leaving a bare -mtime +. Yet the script's exit code is 0. CI went green and nobody looked at that build again.

This script had set -e, set -u and set -o pipefail all enabled. It is the line people call the safety trio for shell scripts. That line does not prevent this accident. Understanding why it cannot, and exactly how far it does reach, is the purpose of this article.

Silent failure is dangerous for a simple reason. A failure reported as exit code 0 is not a failure, it is a success. It is not missed because a human skipped the log, it is missed because the pipeline ruled it a pass. A script that dies loudly can be fixed, but a script that goes green while doing the wrong thing means the very fact that it needs fixing is never discovered.

This article does not tell you to add set -euo pipefail. It shows you how far that line protects you first, and tells you to add it afterward. The rules were checked against the GNU Bash Reference Manual and the POSIX specification, and every behavior was run directly in a temporary directory. All output in this article is what actually appeared on screen. The blind spot table in section 15 is the conclusion.

Let me separate the axis in advance. Whether a script is safe to run twice is covered in Scripts Safe to Run Twice, and whether you can know the outcome before running is in How to Build a Real --dry-run. If that article is about how to communicate the result of a plan and an apply, this one is about the step before it, how to detect failure in the first place. The syntax of quoting variables is in Shell Quoting Rules.

2. Exit code fundamentals - 0, 1, 126, 127, 128+N

Every command leaves behind an integer between 0 and 255 when it ends, and the shell stores it in $?. There is one rule. Zero is success, everything else is failure. The important part is that it is not one means failure but rather anything that is not zero means failure.

$ true;  echo $?
0
$ false; echo $?
1
$ no_such_command_xyz 2>/dev/null; echo $?
127
$ ./sandbox 2>/dev/null; echo $?        # trying to execute a directory
126
$ bash -c 'exit 3'; echo $?
3

127 and 126 are values POSIX specifies directly. Section 2.8.2 of the specification states it plainly.

If the command is not found, the exit status shall be 127. (…) if the command name is found, but it is not an executable utility, the exit status shall be 126.

This means 127 is almost always a typo or a PATH problem. The command did not fail, the command was never found. Separating these two saves a lot of time reading CI logs.

Termination by a signal adds 128. I produced these for real.

$ sleep 30 & pid=$!; kill -9 "$pid"; wait "$pid" 2>/dev/null; echo $?
137
$ sleep 30 & pid=$!; kill -TERM "$pid"; wait "$pid" 2>/dev/null; echo $?
143

137 is 128+9 (SIGKILL) and 143 is 128+15 (SIGTERM). This arithmetic is why a container killed for exceeding memory shows 137. The POSIX wording is looser than people assume, though.

If the command terminated due to the receipt of a signal, the shell shall assign it an exit status greater than 128. The exit status shall identify, in an implementation-defined manner, which signal terminated the command.

In other words the specification only promises greater than 128, and exactly 128+N is a convention the implementation chooses. Every mainstream shell uses 128+N so you can rely on it in practice, but do not mistake it for a rule.

Codes are truncated to eight bits. I measured this too.

$ bash -c 'exit 256'; echo $?
0
$ bash -c 'exit -1' 2>/dev/null; echo $?
255
$ sh -c 'exit 300'; echo $?
44

exit 256 becomes 0. Accidents happen here when someone picks a large number to signal failure and it gets reported as success. Scripts that use the error count directly as the exit code are especially exposed. Exactly 256 errors means a green light.

Finally, 0 and 1 are not universally success and failure either. Each tool has its own convention.

$ printf 'alpha\nbeta\n' > /tmp/demo/data.txt
$ grep -q alpha /tmp/demo/data.txt; echo $?
0
$ grep -q zzzzz /tmp/demo/data.txt; echo $?
1
$ grep -q alpha /tmp/demo/nope.txt 2>/dev/null; echo $?
2

grep uses 0 for found, 1 for not found and 2 for error. Not found is a normal result, not an error. But set -e treats 1 and 2 identically as failure. Calling grep bare under set -e lets the normal result of nothing found kill the script. Section 13 returns to this.

3. The rule for set -e - the manual lists the exceptions itself

The description of set -e (errexit) in one line from help set is this.

-e Exit immediately if a command exits with a non-zero status.

Read only that line and you conclude it stops unconditionally on failure. That conclusion is the starting point of every accident in this article. The full description in the Bash Reference Manual is far longer and lists the exceptions explicitly.

The shell does not exit if the command that fails is part of the command list immediately following a while or until reserved word, part of the test in an if statement, part of any command executed in a && or || list except the command following the final && or ||, any command in a pipeline but the last (subject to the state of the pipefail shell option), or if the command's return status is being inverted with !.

That is five. The command list after while or until, the test of an if, non-final commands in an && or || list, non-final commands in a pipeline, and a command inverted with !. This much is reasonably well known. The real trap is the paragraph that follows.

If a compound command or shell function executes in a context where -e is being ignored, none of the commands executed within the compound command or function body will be affected by the -e setting, even if -e is set and a command returns a failure status.

Unpacked, it means this. The moment you put a function into an if condition, the entire body of that function leaves the protection of set -e. Only one line, the function call, sits in the condition, but the effect reaches every line inside the function. The next section demonstrates it.

4. Where set -e fails to catch - all of it by execution

Rules alone stay abstract. I put every blind spot into a single script with set -e at the top and ran it. If any one of them tripped, the script would die there.

First a baseline, confirming a case where set -e does work.

== A. baseline: set -e DOES stop here ==
  inner script died, rc=1  (NOT REACHED never printed)

A bare false is caught reliably. Now the blind spots. The following is consecutive output from a single run.

== B. condition of if ==
  survived: if-condition

== C. while condition ==
  survived: while-condition

== D. left side of && / || ==
  survived: false &&
  ran RHS of ||
  survived: false ||

== E. negated with ! ==
  survived: ! true

== F. non-final command of a pipeline ==
  survived: false | cat   rc=0

== G. function failing inside a condition ==
  ...function continued past its own false
  survived: function under if

== H. local x=$(failing) hides the status ==
  local v=$(false) -> rc=0  (local's own status wins)
  split declaration caught it -> rc=1

== J. arithmetic that evaluates to zero ==
  (( c++ )) returned nonzero because the OLD value was 0; c is now 1

== ALL BLIND SPOTS PASSED THROUGH; script still alive ==

Not one of them tripped. Reaching the bottom line means set -e was enabled the entire time and let every one of these failures through. Item by item.

  • B and C — if false; then …; fi and while false; do …; done. A condition is a place where failure is allowed. That is natural, because failure is precisely what carries the meaning false
  • D — both false && echo x and false || echo … survived. This is where the || true idiom comes from. Convenient, but the price is high. Section 13 revisits it
  • E — ! true passes even though the final result is failure (1). Inverted commands are named in the exception list
  • F — false | cat has exit code 0. A pipeline reports its last command and cat succeeded. Section 7 is about this
  • G — the most dangerous. The line after the false inside the function executed normally. This is exactly the manual's closing paragraph from section 3. Putting a function into an if leaves its whole body unprotected
  • H — local swallowed the exit code. Section 5 covers it separately
  • J — (( c++ )) returns exit code 1 when the arithmetic result is 0. A counter starting at zero kills the script on its first increment. Use (( ++c )) or c=$((c+1)) to avoid it
⚠ How G shows up in real code
Wrapping work in a function and testing it with if is a completely natural structure. The moment you write if deploy_app; then …, every failure inside deploy_app is ignored. Even if every intermediate step fails, the function returns 0 as long as its last line succeeds, and if judges it true. If you were relying on set -e inside that function, that reliance disappears through the call site alone.

5. local swallows the exit code

Item H from section 4 breaks real code more often than any other set -e trap. The mechanism is simple. local is a builtin command, not assignment syntax, and the exit code of a command is local's own. Whatever the inner command substitution ended with, local returns 0 to mean the variable was created successfully.

First look at how a plain assignment behaves. This side is fine.

== plain assignment: status comes FROM the substitution ==
  v=$(false)      -> rc=1
  v=$(exit 7)     -> rc=7
  v="pre-$(exit 7)-post" -> rc=7  v=[pre--post]

The exit code of an assignment is the code of the command substitution, passed straight up. Even embedded in the middle of a string, the 7 survives. So set -e catches this form correctly. Now put a declaration keyword in front.

== declaration builtins SWALLOW it ==
  local    v=$(exit 7) -> rc=0
  declare  v=$(exit 7) -> rc=0
  typeset  v=$(exit 7) -> rc=0
  export   v=$(exit 7) -> rc=0
  readonly r=$(exit 7) -> rc=0

All five return 0. This is not specific to local, it is a property of declaration builtins as a group. export PATH_X=$(some_command) swallows failure exactly the same way.

I checked which form actually kills the script when combined with set -e.

== under set -e: which one actually kills the script? ==
  rc=7   out=[]
     form: v=$(exit 7); echo ALIVE
  rc=0   out=[ALIVE-in-func
ALIVE]
     form: f(){ local v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE
  rc=7   out=[]
     form: f(){ local v; v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE

Only the middle form survived, printing ALIVE twice. The first and third died correctly with code 7. The only difference is whether declaration and assignment share a line or occupy two.

Declaring several at once is even quieter.

== the multi-declaration variant is worse ==
  three locals, rc=0  b=[]

Only the middle one failed, and there is no way whatsoever to tell which. The exit code is 0 and only the failed variable is quietly empty.

If you remember one rule
Always split local x=$(cmd) into two lines. Create the name with local x, then assign with x=$(cmd) on the next line. The same applies to declare, export and readonly. This single rule removes a large share of set -e accidents.

6. Command substitution does not inherit errexit

There is another blind spot. The inside of $( ) is by default a separate world with set -e switched off. Confirmed by running it.

$ shopt inherit_errexit
inherit_errexit	off

== A. WITHOUT inherit_errexit ==
  out=[LEAKED]  rc=0
  script continued
  rc=0

I ran out=$( false; echo "LEAKED" ) in a script with set -e enabled. The inner false failed to stop the subshell, the following echo executed, and LEAKED landed in the variable. If you habitually chain several commands inside $( ), a value is produced whenever the last one succeeds, no matter how many earlier ones failed.

Bash 4.4 added an option that fixes this. The manual describes it as follows.

If set, command substitution inherits the value of the errexit option, instead of unsetting it in the subshell environment. This option is enabled when POSIX mode is enabled.

Turning it on and running the same code splits the result.

== B. WITH inherit_errexit ==
  rc=1

== C. POSIX mode also turns it on ==
  rc=1

Both died at the inner false. Starting the shell with --posix produced the same effect, exactly as documented. The practical recommendation follows.

set -euo pipefail
shopt -s inherit_errexit    # bash 4.4 and later

But this is not a cure-all either. Section 12 shows a case that passes through even with inherit_errexit enabled, because when local swallows the code first, inherit_errexit never gets a chance to intervene.

7. set -o pipefail - recovering the real pipeline status

By default a pipeline's exit code is that of its last command. Whatever the earlier stages died of is ignored.

== 1. pipeline status = LAST command, by default ==
  false | true   -> rc=0
  true  | false  -> rc=1
  false | cat    -> rc=0

false | true is a success. The front failed and the result is 0. Enabling pipefail changes that.

== 2. same pipelines with pipefail on ==
  false | true   -> rc=1
  true  | false  -> rc=1
  false | cat    -> rc=1

All three turned into failures. The running bash describes the option itself this way.

pipefail — the return value of a pipeline is the status of the last command to exit with a non-zero status, or zero if no command exited with a non-zero status

That means the rightmost non-zero code. Confirmed.

== 3. pipefail returns the RIGHTMOST nonzero ==
  (exit 3)|(exit 4)|true -> rc=4
  (exit 3)|true|true     -> rc=3

In practice the place this bites hardest is tee. The moment you pipe into it to keep a log, the failure disappears.

== 5. the classic: cmd | tee log ==
  no pipefail: rc=0  PIPESTATUS=(1 0)   <- failure vanished
  pipefail   : rc=1  PIPESTATUS=(1 0)

Same pipeline, success above and failure below. Wrapping a build command in | tee build.log is an extremely common pattern, and without pipefail a broken build passes CI.

But pipefail carries a cost in the opposite direction. It turns a normal early exit into a failure.

== 8. pipefail cannot see a head that quits early (SIGPIPE) ==
  yes | head -1 -> rc=141  PIPESTATUS=(141 0)

When head -1 reads one line and closes, yes dies of SIGPIPE and produces 141 (128+13). Nothing is wrong, yet pipefail raises it as a failure. If you use pipelines where grep -q or head cuts the front short, that spot needs separate handling.

8. PIPESTATUS - read every stage, and copy it immediately

pipefail collapses everything into one code. To learn which stage failed, use the bash PIPESTATUS array.

== 4. PIPESTATUS keeps every stage ==
  rc=0  PIPESTATUS=(3 0 4 0)

All four stage codes survived. The exit code follows the last one and is 0, but the array shows plainly that stages one and three failed.

This array has a lethal property, though. It is overwritten by the very next command.

== 6. PIPESTATUS is clobbered by the very next command ==
  first read : PIPESTATUS=(3 4)
  second read: PIPESTATUS=(0)   <- the echo above overwrote it

The moment the first echo succeeded, the array became (0). You cannot read it twice. So always copy it on the line right after the pipeline.

== 7. save it immediately ==
  saved copy : (3 4)  stage0=3 stage1=4

The practical shape is this. Copy the whole array immediately after the pipeline and consult only the copy afterward.

curl -fsS "$url" | gzip -d | psql "$dsn"
st=("${PIPESTATUS[@]}")          # must be the very next line
if [ "${st[0]}" -ne 0 ]; then echo "download failed (${st[0]})" >&2; exit 1; fi
if [ "${st[1]}" -ne 0 ]; then echo "decompress failed (${st[1]})" >&2; exit 1; fi
if [ "${st[2]}" -ne 0 ]; then echo "load failed (${st[2]})"     >&2; exit 1; fi

pipefail alone tells you only that something failed, while this tells you the download failed, in the log. For pipelines of three stages or more that difference is large.

9. set -u - undefined variables and empty arrays

set -u (nounset) exits immediately when an undefined variable is referenced. It is the mechanism that stops an empty value created by a typo from flowing into a command line.

== 1. plain unset reference ==
  echo "[$nope]"     rc=127 bash: line 1: nope: unbound variable
  echo "[${nope}]"   rc=127 bash: line 1: nope: unbound variable

The exit code here is interesting. The same error yields different values depending on how the shell was invoked. I checked all four combinations.

$ bash -u -c 'echo "[$nope]"'   ; echo $?
127
$ bash -u script.sh             ; echo $?
1
$ dash -u -c 'echo "[$nope]"'   ; echo $?
2
$ dash script.sh                ; echo $?
2

Bash gives 127 when invoked with -c and 1 when running a script file. Dash gives 2 in both cases with a different message, parameter not set. Do not try to identify a set -u failure by a specific exit code. It is not portable.

You opt out with default-value syntax, where the presence of a colon matters.

== 2. defaults let you opt out ==
  ${nope:-fallback}        rc=0   [fallback]
  ${nope-fallback}         rc=0   [fallback]
  ${nope:?must be set}     rc=127 bash: line 1: nope: must be set

== 3. set vs empty are different ==
  empty="" then ${empty:-d}   rc=0   [d]
  empty="" then ${empty-d}    rc=0   []

With a colon it means unset or empty, without it means unset only. If an empty string must count as a valid value, drop the colon. ${var:?message} is useful for enforcing required arguments in a single line without writing an if.

Now the frequently confused case of an empty $@ and empty arrays. Behavior here varied across bash versions, so I record it with the version of this environment. The version tested is GNU bash 5.2.37.

== 4. empty $@ and $1 ==
  no args, "$@"        rc=0   argc=0 / REACHED
  no args, "$1"        rc=127 bash: line 1: $1: unbound variable
  no args, "${1:-def}" rc=0   [def] / REACHED

== 5. empty arrays ==
  declare -a arr=(); "${arr[@]}"   rc=0   n=0 / REACHED
  unset arr; "${arr[@]}"           rc=0   REACHED
  declare -a arr=(); "${arr[0]}"   rc=127 bash: line 1: arr[0]: unbound variable
  empty array + ${arr[@]:-}        rc=0   x=[] / REACHED

Summarized: on bash 5.2.37, "$@" with no arguments and "${arr[@]}" on an empty array are safe. By contrast, picking an individual element such as "$1" or "${arr[0]}" blows up. The dividing line is whether you expand the whole thing or reach for a specific element.

A caution about older bash
There was a time when an empty "$@" and empty arrays did error under set -u (before bash 4.4). The results above were confirmed directly on 5.2.37, and since no old bash was available in this environment I did not reproduce the historical behavior. If you target an old shell such as the bash 3.2 shipped with macOS, defending with the "${arr[@]:-}" form is safer.

Finally, note that set -u has nothing to do with failing commands.

== 6. -u alone does not stop a FAILING command ==
  -u only, false   rc=0   REACHED
  -eu, false       rc=1   (no output)

With only -u, a false cannot kill the script. The three options do different jobs and none substitutes for another.

10. trap - find it with ERR, clean up with EXIT

trap is the mechanism for recording failure points and guaranteeing cleanup. Start with the ERR trap.

== 1. ERR trap reports line and command ==
  step one
  ERR: line 5 rc=2 cmd=[grep -q nothing /nonexistent/path]
  outer saw rc=2

With the three variables LINENO, $? and BASH_COMMAND, which line, which command and which code all landed on one line. The log is far cleaner than dumping everything with set -x.

To make it reach inside functions you need -E (errtrace).

== 5. functions need -E (errtrace) to inherit the ERR trap ==
  without -E: trap did not fire inside f
  with -E: trap fired inside f

This is why people write set -eE rather than set -e. Without -E, the ERR trap does not fire inside functions, subshells or command substitutions.

There is a decisive limitation, though. The ERR trap has exactly the same blind spots as set -e. I ran the section 4 blind spots again under an ERR trap.

== 4. ERR trap has the SAME blind spots as set -e ==
  reached the end with no ERR trap firing
  outer saw rc=0

if false, false || true, ! true, false | cat and local v=$(exit 7) all executed, and the trap never fired once. The expectation that attaching an ERR trap catches every failure does not hold.

The EXIT trap is different in character. It always runs, on success or failure, which makes it right for cleaning up temporary files.

== 2. EXIT trap always runs; use it for cleanup ==
  workdir created: yes
  cleanup: removing workdir
  outer saw rc=5  (EXIT trap did not change it)

The script died with code 5, cleanup still ran, and the exit code stayed 5. Here I separated a common misconception by measurement.

== 3. an EXIT trap CAN silently rewrite the exit code ==
  cleanup running
  outer saw rc=9
  cleanup running
  outer saw rc=9
  ...now a cleanup with an explicit exit in the trap:
  cleanup running
  outer saw rc=0   <- the real failure was erased

The distinction matters. The last command in the trap failing or succeeding does not by itself change the exit code. In the first two cases 9 was preserved. Only an explicit exit inside the trap overwrites it. In the third case the real failure 9 was erased to 0.

⚠ Never call exit inside a cleanup function
If the cleanup of trap cleanup EXIT contains exit 0, every failure is reported as success. In the test a script that died with code 9 ended with 0. A cleanup function should clean up and return quietly. If it truly must handle the code, capture it on entry with rc=$? and give it back at the end with exit "$rc".

11. Subshell and function boundaries

Here is what happens when set -e crosses a boundary. The manual states it applies separately to the shell environment and to each subshell environment. Confirmed by running it.

== 1. set -e is inherited by subshells ==
  rc=1

== 2. ...but not if the subshell sits in a condition ==
  subshell CONTINUED past false
  subshell failure absorbed by ||
  script alive, rc=0

A subshell inherits set -e, but once that subshell sits in a condition its entire interior becomes unprotected. Same mechanism as G in section 4.

Command substitution does not inherit it by default, as seen in section 6. This is the run without inherit_errexit.

== 3. command substitution: -e does NOT apply inside by default ==
  out=[SHOULD-NOT-APPEAR]
  rc=0

== 5. the killer: substitution inside a declaration ==
  local out=[SHOULD-NOT-APPEAR] rc=0
  script survived
  rc=0

A function's return value is the code of the last command executed. Without an explicit return, that is what comes back.

== 6. a function without an explicit return ==
  f -> 1       # f(){ true; false; }   ends with false
  g -> 0       # g(){ false; true; }   ends with true
  h -> 0       # h(){ echo "..."; }    echo succeeded

g is the dangerous one. It failed inside, but its last line succeeded, so it returns 0. Habitually appending an echo or log line to the end of a validation function means that function succeeds forever. Such functions must state return explicitly.

== 7. exit inside a subshell only leaves the subshell ==
  after subshell, rc=4  (parent still running)
  parent rc=0

exit 4 inside parentheses ended only the subshell. The parent kept running and the final code is 0. Writing exit on validation failure inside a subshell or pipeline means the script does not stop.

Each pipeline stage is also a subshell, so variable assignments are lost.

== 8. a pipeline runs its stages in subshells ==
  after while-in-pipeline: count=0  (child's copy was discarded)
  with process substitution: count=3

The count from printf … | while read … is 0. It is a variable in a child process and never returns to the parent. Switching to process substitution yields 3. Scripts that count errors and judge at the end fall into this trap often. They always finish with zero errors.

12. set -euo pipefail is on and the wrong value still passes

Back to the script from the introduction. With the pieces assembled, we can explain why it passed. The script was this.

#!/usr/bin/env bash
set -euo pipefail

read_key() {
  local value=$(grep -m1 "^$1=" "$2" | cut -d= -f2)
  echo "$value"
}

target=$(read_key target /tmp/demo/app.conf)
retain=$(read_key retain_days /tmp/demo/app.conf)

echo "  target      = [$target]"
echo "  retain_days = [$retain]"
echo "  would run: find /srv/backup/$target -mtime +$retain -delete"
echo "  DEPLOY OK"

The config file contains only name and owner; target and retain_days are absent. Here is the run.

=== run 1: the 'safe' version ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

The failure was erased in three layers. Point by point.

  • grep failed to find the key and ended with 1, but | cut follows it, so the pipeline code becomes cut's 0. With pipefail enabled it does survive as 1 up to here
  • But that pipeline sits inside local value=$(…). local swallows the code and makes it 0 (section 5)
  • The function ends with echo "$value". echo succeeds, so the function's return value is also 0 (section 11)
  • So target=$(read_key …) receives 0 and set -e has no reason to intervene. set -u does not help either, because the variable is not undefined, it is defined as an empty string

What about adding the inherit_errexit from section 6? I added the single line shopt -s inherit_errexit to the same script and ran it.

=== run 2: same script, inherit_errexit added ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK

Identical result. inherit_errexit restores errexit inside command substitution, but here local swallows the code before that, so it never gets a chance to intervene. Enabling more options cannot prevent this accident.

The fix is not options but validation. After reading a value, check directly whether it was read and whether it is empty.

read_key() {
  local value
  if ! value=$(grep -m1 "^$1=" "$2"); then
    printf 'config key missing: %s\n' "$1" >&2
    return 3
  fi
  value=${value#*=}
  if [ -z "$value" ]; then
    printf 'config key empty: %s\n' "$1" >&2
    return 3
  fi
  printf '%s\n' "$value"
}
=== run 3: validated version ===
config key missing: target
  run3 rc=3

It failed correctly with code 3 and the message names the missing key. Four things changed. Declaration and assignment were split, grep's failure is received directly with if !, the pipeline was removed by slicing with parameter expansion instead of cut, and the empty value is checked explicitly.

⚠ The conclusion of this section
set -euo pipefail is a mechanism for catching a command failed. It cannot catch the command succeeded but the value is wrong. And a large share of real accidents are the latter. Empty strings, unexpected formats and zero-length lists are all perfectly normal output from a successful command. Validating values is something a human has to write.

13. Exit code design - what to tell the caller

Everything so far was about detecting failure. Now comes communicating what was detected. When there are three or more states, 0 and 1 are not enough. The widely used shape has three branches.

CodeMeaningWhat the caller does
0Normal, nothing wrongPass
2Differences found, the check ran and results differReview the content and decide or approve
1Error, the check itself could not runFail immediately and alert
64 and aboveUsage errors and other finer statesFix how it was invoked

I built a checker that emits three states and a caller that receives them, then ran it.

  PASS  : no differences
    -> caller exits 0
  DRIFT : 3 files differ  (gate: fail the build, keep the log)
    -> caller exits 2
  ERROR : checker itself failed
    -> caller exits 1
  USAGE : bad invocation
    -> caller exits 64

The skeleton of the receiving side looks like this. Since calling it bare under set -e lets every non-zero value kill the script, capture the code into a variable and branch with case.

rc=0
out=$(./check.sh "$1") || rc=$?     # capture the code without dying
case "$rc" in
  0)  echo "  PASS  : $out" ;;
  2)  echo "  DRIFT : $out" ;;
  1)  echo "  ERROR : checker itself failed" ;;
  64) echo "  USAGE : bad invocation" ;;
  *)  echo "  UNKNOWN rc=$rc" ;;
esac
exit "$rc"

|| rc=$? is the key. As seen in D of section 4, the left side of || is a blind spot of set -e, so the script does not die and the code remains in the variable. This is where the blind spot becomes a tool rather than a problem.

Conversely, || true destroys information in exactly the same place.

== 3. the anti-pattern: '|| true' erases the state ==
  after || true, rc=0  <- error is gone

== 4. '|| true' vs capturing the code ==
  captured rc=1  <- still known, still recoverable

People add || true to mean this command is allowed to fail, but what it actually declares is I will never know how this command ended. Being allowed to fail and not needing to know about the failure are different things. Capturing with || rc=$? satisfies both.

For tools like grep where not found is 1, wrap it like this.

if grep -q "$pattern" "$file"; then
    echo "found"
elif [ $? -eq 1 ]; then
    echo "not found, which is normal"
else
    echo "grep execution error" >&2; exit 1
fi

When you need to locate a failure quickly, set -x helps by printing commands as they run.

== 5. set -x shows the failing command ==
  + grep -q token /nonexistent/file.txt
  grep: /nonexistent/file.txt: No such file or directory

The advantage is seeing the final form after expansion. Whether a variable was empty and how a path was assembled become immediately visible. Since the output is voluminous, wrapping only the suspect region in set -x … set +x is better.

Finally, do not forget to pass the received code back through. The code survives even with a cleanup trap in place.

== 6. exit with the code you were given ==
  propagating rc=2
  cleaning up
  outer sees 2

How to wire this convention into a structure that separates planning from applying is covered in more detail in the exit code section of How to Build a Real --dry-run.

14. Where POSIX sh diverges

If your first line is #!/bin/sh, half of the above does not exist. I fed the same code to bash and to dash and compared.

Featurebash 5.2.37dashMeasured message
set -o pipefailWorksAbsentIllegal option -o pipefail
PIPESTATUS(3 4)AbsentBad substitution
Arraysn=3AbsentSyntax error: "(" unexpected
trap … ERRFiresAbsenttrap: ERR: bad trap
trap … EXITFires, rc=5Fires, rc=5Identical on both

set -e + function + ifPasses throughPasses throughCONTINUED ALIVE on both
exit 300rc=44rc=44Eight-bit truncation on both

How to read it.

  • There is no pipefail. To catch pipeline failures in a POSIX sh script you must avoid pipes themselves, writing to a temporary file, checking the code, then moving to the next stage
  • No PIPESTATUS and no arrays. There is effectively no way to see per-stage status
  • No ERR trap. The EXIT trap works on both and the exit code was 5 on both. Cleanup logic is portable; failure logging is not
  • local exists in dash too. And it swallows the exit code in exactly the same way. The trap from section 5 holds under #!/bin/sh as well
  • The blind spots of set -e are identical. Putting a function into an if passed through on both. This is not bash-specific behavior, it is the rule of the shell language

In short, the safety mechanisms are bash-only while the traps are common to both. Choosing portability means losing the tools and keeping the traps, so picking #!/bin/sh should have a reason behind it.

15. The blind spot table - from situation to alternative

This is the conclusion of the article. When you meet the situation on the left, set -e does nothing at all. Use the right column instead.

SituationDoes set -e catch itWhat to use instead
A bare failing commandYesLeave it as is
The condition of if cmd; thenNoIntended behavior. To separate error from false inside the condition, read $? directly
The condition of while cmd; doNoCheck separately in the loop body
Left side of cmd && … or cmd || …NoCapture with || rc=$? and branch with case
! cmdNoMake the intent explicit with if ! cmd; then
Non-final command of a pipelineNoset -o pipefail plus an immediate copy of PIPESTATUS
cmd | tee logNoset -o pipefail. Without it a broken build passes
A function placed in if or ||No, the whole body is unprotectedCheck each step inside the function and state return explicitly
local x=$(cmd)NoSplit into two lines, local x then x=$(cmd)
declare, export, readonly assignmentNoSame. Separate declaration from assignment

A function whose last line is echoNo, always 0State the intended code with return

16. A template - what it guarantees and what it does not

Here is a starting skeleton reflecting everything above. The point of this section is to state alongside it what this template does not guarantee.

#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true   # bash 4.4+ only

readonly WORKDIR=$(mktemp -d)
cleanup() {
    rm -rf "$WORKDIR"        # never call exit here (section 10)
}
trap cleanup EXIT
trap 'echo "failed: line $LINENO rc=$? cmd=[$BASH_COMMAND]" >&2' ERR

need() {                     # validate required values (section 12)
    local name="$1" value="$2"
    if [ -z "$value" ]; then
        echo "missing required value: $name" >&2
        return 3
    fi
}

run_stage() {
    local rc                 # declaration and assignment split (section 5)
    local out
    out=$(some_command "$1") || rc=$?
    : "${rc:=0}"
    case "$rc" in
        0) printf '%s\n' "$out" ;;
        *) echo "stage failed: $1 (rc=$rc)" >&2; return "$rc" ;;
    esac
}

main() {
    local value
    value=$(run_stage fetch)
    need "value" "$value"    # validate the value even on success
    echo "completed normally"
}

main "$@"

What this template guarantees is the following.

  • It stops immediately at a bare failing command (-e)
  • A failure in the middle of a pipeline does not disappear (pipefail)
  • It stops at a reference to an undefined variable created by a typo (-u)
  • Failures inside command substitution are caught too (inherit_errexit)
  • The ERR trap fires inside functions as well, leaving the failure point in the log (-E)
  • The temporary directory is cleaned up regardless of how it ends (EXIT trap)
  • The cleanup trap does not overwrite the exit code (no exit in the trap)

What it does not guarantee matters more.

  • Putting a function into if or || takes its entire body out of protection. The template's own run_stage is no exception
  • It cannot catch a command that succeeded with the wrong value. That is why need exists separately. Validation is something you write; no option does it for you
  • Zero rows, empty lists and unexpected formats are all normal successes. The requirement that there must be a result has to be written by hand
  • Because of pipefail, a pipeline where head cuts the front short can fail with 141 (section 7). Handle such places individually
  • set -u does not block empty strings. A variable defined as empty is not undefined
  • If an external command fails yet returns 0, the shell has no way to know. Tools with inaccurate exit codes must be validated by their output

Finally, a few self-check commands for finding the traps from this article in existing scripts.

### declaration and assignment sharing a line
$ grep -rnE '(local|declare|typeset|export|readonly)[[:space:]]+[A-Za-z_]+=\$\(' .

### places where a pipe can erase a failure
$ grep -rn '| *tee' .

### exit inside a cleanup trap
$ grep -rnE 'trap .*(exit|EXIT)' .

### scripts with no safety options at all
$ grep -rLE 'set -[a-zA-Z]*e' --include='*.sh' .

Conclusion: an undetected failure is not a failure but a false success

Compressed into rules, it is four sentences.

  • set -e catches only bare failing commands. Conditions, negation, logical operators and mid-pipeline positions are all exceptions, and this is not a bug but a rule the manual lists itself
  • Putting a function into a condition costs its whole body the protection. In the test the line after a failing command inside a function executed normally. It is the widest blind spot
  • local, declare and export swallow the exit code. All five declaration builtins returned 0. Splitting declaration from assignment across two lines is the entire fix
  • The most dangerous case is a command that succeeded with the wrong value. No set option can catch it and validation has to be written by hand

Restating what was confirmed by execution: nine blind spots were packed into one script and run with set -e enabled, and not one tripped before it reached the end. Prefixing local turned code 7 into 0, and all five declaration builtins behaved the same. false | tee was reported as success without pipefail. PIPESTATUS was wiped by a single following echo. An exit 0 inside a cleanup trap overwrote a real failure of 9 with 0. And a script with set -euo pipefail plus inherit_errexit passed two empty values through and ended with code 0.

That last case is the point of this article. Safety options are a mechanism for catching a command failed, not a guarantee that the result is correct. The moment you treat those as the same thing, the fact that you enabled the options becomes the excuse for skipping validation. In truth, whoever wrote the script in the introduction most likely skipped value checking because they had added set -euo pipefail.

So invert the order. Write down what can go wrong first, write the code that checks for it, and add the safety options afterward. set -euo pipefail is a floor, not a ceiling. If even one row of the table in section 15 with a non-empty right column exists in your script, that row is where the next accident happens.

# Shell Exit Codes and set -e - Practical Reference

Verified on: GNU bash 5.2.37(1)-release, dash, GNU coreutils 8.32.
Every value below was confirmed by actually running it.

---

## 1. Exit code table

| Code | Meaning | Source | Confirmed by |
|---|---|---|---|
| 0 | Success | POSIX | `true` |
| 1 | Generic failure (convention) | Convention | `false` |
| 2 | Usage error or differences found | Convention | `grep` error |
| 126 | Found but not executable | POSIX 2.8.2 | Executing a directory |
| 127 | Command not found | POSIX 2.8.2 | Missing command |
| 137 | 128+9, terminated by SIGKILL | Implementation | `kill -9` |
| 143 | 128+15, terminated by SIGTERM | Implementation | `kill -TERM` |
| 141 | 128+13, SIGPIPE | Implementation | `yes | head -1` |
| 256 and up | Truncated to 8 bits (256 becomes 0) | Measured | `exit 256` |

Tools have their own conventions too. `grep` uses 0=found, 1=not found, 2=error.
Not found is a normal result, but `set -e` treats it as failure.

---

## 2. set -e blind spot checklist

Every item below **passes through** while `set -e` is enabled. Confirmed by execution.

- [ ] Condition of `if cmd; then` -> passes
- [ ] Condition of `while cmd; do` -> passes
- [ ] Left side of `cmd && ...` -> passes
- [ ] Left side of `cmd || ...` -> passes
- [ ] `! cmd` (negation) -> passes
- [ ] Non-final command of a pipeline -> passes (`false | cat` gives rc=0)
- [ ] **A function placed in `if` or `||` leaves its whole body unprotected** <- widest blind spot
- [ ] `local x=(command substitution)` -> local's own status wins, rc=0
- [ ] `declare` / `typeset` / `export` / `readonly` assignment -> all rc=0
- [ ] Inside command substitution `( )` -> errexit not inherited by default
- [ ] A subshell sitting in a condition -> unprotected all the way inside
- [ ] A function whose last line is `echo` -> always returns 0
- [ ] `exit` inside a subshell -> ends only the subshell
- [ ] `exit 0` inside a cleanup trap -> overwrites every failure with 0
- [ ] **Command succeeded but the value is an empty string** <- no option catches this

`(( c++ ))` is a trap in the opposite direction. It returns exit code 1 when the
arithmetic result is 0, so a counter starting at zero kills the script on its
first increment. Use `(( ++c ))` instead.

---

## 3. What each option actually does

| Option | Catches | Does not catch |
|---|---|---|
| `set -e` | A bare failing command | Everything in the checklist above |
| `set -u` | Reference to an undefined variable | Empty strings, failing commands |
| `set -o pipefail` | Failure mid-pipeline | Mistakes SIGPIPE early exit for failure |
| `shopt -s inherit_errexit` | Failure inside command substitution | Useless if local swallows it first |
| `set -E` | Makes ERR trap fire inside functions | Same blind spots as `set -e` |

`set -u` measurements (bash 5.2.37):
- Whole expansion of the argument list and of an empty array are safe
- Picking an individual element such as the first positional or `arr[0]` blows up
- Opt out with `${var:-default}`. With a colon it means unset or empty, without it means unset
- The exit code is not portable: bash script 1, bash -c 127, dash 2

---

## 4. Copy PIPESTATUS immediately

You can read it only once, right after the pipeline. The very next command clobbers it.

```
curl -fsS "url" | gzip -d | psql "dsn"
st=("${PIPESTATUS[@]}")          # must be the very next line
[ "${st[0]}" -ne 0 ] && echo "download failed"
[ "${st[1]}" -ne 0 ] && echo "decompress failed"
[ "${st[2]}" -ne 0 ] && echo "load failed"
```

## 5. A safe template

```
#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true

readonly WORKDIR=(assign the mktemp result)
cleanup() {
    rm -rf "WORKDIR"          # never call exit here
}
trap cleanup EXIT
trap 'echo "failed: line LINENO cmd=[BASH_COMMAND]" >&2' ERR

need() {                      # validate the value even on success
    local name="1" value="2"
    if [ -z "value" ]; then
        echo "missing required value: name" >&2
        return 3
    fi
}

run_stage() {
    local rc                  # declaration and assignment split
    local out
    out=(assign the command result) || rc=?
    case "rc" in
        0) printf '%s\n' "out" ;;
        *) echo "stage failed (rc)" >&2; return "rc" ;;
    esac
}
```

**Guarantees**: stops at a bare failure, keeps pipeline failures, blocks undefined
variables, detects failure inside command substitution, fires ERR trap inside
functions, cleans up the temp directory, preserves the exit code.

**Does not guarantee**: putting a function into a condition takes its whole body out
of protection. Empty or malformed values are not caught. A zero-row result is a
normal success. `set -u` does not block empty strings. External tools with
inaccurate exit codes must be validated by their output.

---

## 6. Exit code design convention

| Code | Meaning | What the caller does |
|---|---|---|
| 0 | Normal | Pass |
| 2 | Differences found (the check ran) | Review and decide |
| 1 | Error (the check itself failed) | Fail immediately and alert |
| 64+ | Usage errors and similar | Fix the invocation |

The receiving side looks like this. Capturing with `|| rc=?` keeps `set -e` from killing it.

```
rc=0
out=(run the checker) || rc=?
case "rc" in
  0)  echo "PASS" ;;
  2)  echo "DRIFT" ;;
  1)  echo "ERROR" ;;
  *)  echo "UNKNOWN" ;;
esac
exit "rc"
```

Do not use `|| true`. It does not declare that the command may fail, it declares
that you will never know how it ended.

## 7. Differences from POSIX sh

| Feature | bash 5.2.37 | dash |
|---|---|---|
| `set -o pipefail` | Works | **Absent** |
| `PIPESTATUS` | Works | **Absent** |
| Arrays | Works | **Absent** |
| `trap ... ERR` | Works | **Absent** |
| `trap ... EXIT` | Works | Works |
| Process substitution | Works | **Absent** |
| `local` | Works | Works |
| `local` swallowing the code | rc=0 | **rc=0 (identical)** |
| `set -e` + function + `if` | Passes | Passes (identical) |

Summary: **the safety mechanisms are bash-only, the traps are common to both.**
