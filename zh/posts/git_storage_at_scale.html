Git 在大规模下变慢的地方 - 深度、宽度、体积是不同的问题

对象存储与增量压缩预设了什么、这个预设在哪里崩塌，以及各种少下载的方法分别交出了什么

2026年8月28日 开发/基础设施

引言：仓库变重的方式不止一种

在新机器上把仓库拉下来要花二十分钟。敲一次 git status 就流走几秒钟。症状看着相似，成因却可能落在完全不同的地方，所以把别人写的对策照搬过来，大多不起作用。

这个话题重新浮上来是有由头的。2026年8月，Cursor 公开了重新设计自家 Git 托管存储层的 Continuity。按该公司的说法，他们不再把本地 Git 仓库当作真相之源，而是把放在 S3 兼容对象存储上的预写日志(WAL)当作源头，本地 NVMe 磁盘上的 Git 仓库则被视为随时可以重建的缓存。推送顺序通过对象存储的原子比较交换(CAS)来排定，这是整套设计的骨架。同一篇文章里，该公司还一并给出了每秒推送吞吐、副本增加到一百个时的读取扩展、副本一致性检查延迟等数字，但那是该公司在自家环境中测量并发布的值，硬件与部署条件并未在文中写明。这也是本文不把这些数字当作性能依据的原因。

产品的部分到此为止。真正有意思的是他们想解决的那个问题。为什么大规模托管 Git 这件事很难，为什么一个巨大的单一仓库和无数个微小仓库会朝相反的方向折磨同一套系统。答案不在某家公司的架构里，而在Git 当初是基于什么前提设计的。下面先顺着这个前提走一遍，再逐个指出它崩塌的地方。如果更关心工具，可以把深挖历史的 Git 命令整理放在旁边；如果关心托管格局，可以参考对 Cursor 的 Git 代码托管发布的分析。

1. Git 实际存储的东西 - 四种对象与内容寻址

如果你把 Git 理解成一串文件变更(diff)的清单，那有一半是错的。Git 存的不是变更而是快照。而且存储的最小单位不是文件，是对象。

  • blob — 只装文件的内容。里面没有文件名，没有权限，也没有路径。
  • tree — 相当于目录。逐条装着模式、类型、名字以及目标对象的哈希。名字在这里。
  • commit — 装着一个顶层 tree、若干父提交、作者与提交者信息，以及提交消息。
  • tag — 指向某个特定对象，可以附上签名和消息的附注标签。

关键在于这些对象的名字是从内容里长出来的。Git 会在内容前面加一小段带类型和长度的头，然后对整体算哈希，再把这个哈希直接当作对象的名字。存储路径也由这个哈希决定 — 前两个字符是目录，其余是文件名。内容用 zlib 压缩后写入。

由此引出一条常让人吃惊的性质。相同的内容在一个仓库里只存一次。同一个文件被复制到十个目录里，blob 依然只有一个。一百次提交里都没动过的文件不会被存一百次。每次提交都会新建 tree，但没有变化的子 tree 和 blob 仍然指向原来的哈希。这里并没有一套专门的去重机制，而是名字就是内容，所以重复根本不会产生。

这个设计也在悄悄收费。因为名字就是内容，所以内容一变，名字就变。提交里装着父提交的哈希，所以只要改动过去的某个点，它之后所有提交的名字都会连锁地改变。后面会讲到的重写历史之所以危险，不是出于什么政策，而是直接从这个存储结构里推出来的。

2. 打包文件与增量压缩 - 打包之后什么变便宜、什么变贵

一个对象就是一个文件的状态叫作松散对象(loose object)。理解起来容易，长期放着却不好。给一个 22KB 的文件加一行再提交，就会多出一个内容几乎相同的 22KB 对象，两者各自压缩、各自占地方。

所以当对象堆到一定程度、跑 git gc 或者往远端推送时，Git 会把对象打成一个打包文件。这时相似的对象之间会加上增量压缩。在前面那个例子里，新版本被完整存下，旧版本只留下指向新版本的几个字节的差异。Git Book 的例子中，22,054 字节的对象被完整保存，22,044 字节的对象则缩成了 9 字节的增量。

方向值得留意。把最新版本完整放着，把过去做成增量。这是照着真实使用形态做的选择 — 人最常翻的是最近的东西。代价同样清楚。

  • 要读一个以增量形式保存的对象，就得沿着链条回溯还原。读取从纯粹的文件读取变成了掺着计算的活。
  • 所以 Git 会限制增量链的深度。无限拉长虽然省磁盘，但读取会变慢。
  • 寻找增量基准这件事本身就要吃 CPU 和内存。大仓库重新打包很重的原因就在这里。
  • 打包文件内部的对象排布遵循逻辑上的相邻性，所以访问模式很容易变成磁盘上的离散读取。

归纳起来，打包文件是拿容量与传输量换CPU 与随机访问的一桩交易。对绝大多数仓库来说，这桩交易是压倒性地划算的。问题在于仓库变大时，交易的两头会一起变大。

3. 变大这个说法有三种 - 深度、宽度、体积

这里是本文的核心。仓库很大这一句话里，混着三条互相独立的轴。三者成因不同、症状不同，最要紧的是对策不同。

  • 历史深度 — 提交以及随之而来的 tree 对象的累计数量。一个存在了十年的仓库，不管文件有几个都是深的。
  • 目录树宽度 — 一次提交里装的文件与目录的数量。昨天新建的仓库，只要文件有五十万个就是宽的。
  • 文件体积 — 单个对象的块头。压缩和增量到底管不管用，在这里分出胜负。
轴什么会变慢通常管用的对策这个对策交出去的东西
历史深度初次克隆、可达性计算、版本遍历、与服务端协商shallow clone、提交图缓存、必要时切分历史追问过去的操作(log、blame、bisect)会卡住，或者引发重新拉取
目录树宽度检出、状态检查、索引刷新、切换分支sparse-checkout、文件系统监视、稀疏索引工具兼容性与运维复杂度，以及碰到范围之外时的混乱
文件体积传输量、磁盘、打包时间、内存把大文件外置(LFS 之类)，或者干脆不放进去要另外运维一套存储的认证与备份，还多了一条工具链依赖

把三条轴混在一起，诊断就会跑偏。嫌克隆慢就加了 --depth 1，结果还是慢，那多半原来就不是深度问题，而是宽度或体积。提交数量不多，但一次提交里有四十万个文件的话，砍掉深度也不会改变要下载的 tree 和 blob 的总量。反过来，文件数量不多却克隆很重，就要先怀疑历史深处的某个大体积二进制文件。

判断标准很简单。先选出占主导的那一条轴，只上那条轴的对策，然后重新测一遍。三条一起上，既不知道是哪一条起了作用，出问题时也不知道该回退哪一个。

4. 大体积二进制文件为什么格外糟糕

文本源代码是 Git 最擅长的对象。按行小幅改动，压缩管用，增量非常管用。大体积二进制文件正好站在对面。

  • 增量不管用。已经压缩过的格式(图片、视频、归档)只要改一个像素，整个字节序列就全变了。于是每次新提交实际上都塞进去一个完整的新文件。
  • 压缩也不管用。把压过的东西再压一遍几乎不会变小，打包文件的一个好处就此消失。
  • 内存开销很大。处理一个对象所需的工作空间会随文件体积成比例增长。
  • 一旦进去就留下了。就算下一次提交把它删掉，那个 blob 依然处在能被过去的提交到达的状态。每一个克隆的人都会一直下载它。

最后一条最贵。误提交进去的 500MB 构建产物，不会因为下一次提交删掉它就消失。删除提交只是造了一棵没有那个条目的新 tree，而更早的提交依然指向那个 blob。要真正把它从仓库里拿掉，只能重写过去。这笔账后面单独讲。

因此对大体积资产，换成指针放到外面的做法被广泛采用。Git LFS 是典型：提交里只放一个轻量的指针文件，真正的内容放在另一套存储里。仓库确实变轻了。代价是要先装扩展，要另外运维那套存储的认证、容量和备份，而那套存储一旦消失，手里就只剩指针。重量并没有消失，只是挪走了。

5. 少下载的三种方法 - 各自不下载什么

大规模仓库的对策里，相当一部分可以归纳成少下载。只是这三种少下载的东西各不相同，而被推迟的账多半会在后面结算。

方法不下载的东西后面什么会变慢要一并注意的点
shallow clone(--depth)指定深度之外的较早提交追问过去的操作。需要时还得再把历史补下来默认会收窄成单一分支
partial clone(--filter)全部 blob 或超过某个体积的 blob，按配置甚至连 tree 一起缺失对象被用到的那一刻的即时拉取。文档写明这种拉取偏慢远端必须活着，而且认证可能会反复发生
sparse-checkout什么都没少下载。它只收窄展开到工作树里的路径扩大范围的那一刻，以及处理范围之外的变更时推荐 cone 模式。非 cone 的模式写法在文档里不被推荐

第三行经常被误读。sparse-checkout 不是省流量的功能。它只是用索引里的 skip-worktree 位不把文件展开到工作树，对象其实早就下载好了。要连下载一起减少，就必须和 partial clone 搭配使用，而那时对面的代价也会跟过来。Git 文档明说这个命令是实验性的、行为可能变化，同时还提醒稀疏索引会以外部工具无法理解的方式改动索引。

partial clone 文档里写下的提醒同样值得照原样读一遍。缺失的对象会在需要时从承诺者远端(promisor remote)取回，但取回是按条目发生的，所以对象一多就会带来相当可观的开销和多次认证请求。离线工作的属性被削弱，在网络不好的地方，初次克隆是快了，日常操作却会不规律地卡住。

6. 从服务端看到的东西 - 引用数量、协商、重新打包

只从客户端看会漏掉一条轴，那就是引用(ref)的数量。分支和标签只是装着一个哈希的小条目，从容量上看可以忽略不计。成本出在别处。

  • 引用广播 — 在旧协议里，每次连接服务端都会把手上所有引用发过来。partial clone 文档也写到，引用一多这一段就可能产生相当可观的开销。
  • 协商 — 客户端和服务端互相交换各自已经有什么，据此决定要发送哪些对象。引用和提交越多，这几个来回就越重。
  • 可达性计算 — 哪些对象还活着，必须从引用出发把图走一遍才知道。清理(gc)和重新打包的真实成本就在这里。

协议 v2 正面改掉了其中的第一项。引用广播改成不请求就省略，并给 ls-refs 加上 ref-prefix，只取需要的前缀下的引用。所以分支放着不管就会让克隆变慢这条老经验，今天是有条件的。两端都跑 v2 时广播成本会大幅下降，但可达性计算和重新打包的负担依然原样留着。

从运维视角看更有意思的是，方向完全相反的两种负载会同时压到同一套系统上。一端是要用几百个副本扛住 CI 的巨大单一仓库，另一端是自动化造出来的、用过几次就被遗忘的小仓库堆积如山。前者要求读取可扩展，后者要求单个仓库的固定成本趋近于零。Continuity 那篇公开文章处理的问题，说到底也是这两个方向的同时要求。把 Git 重写成库的尝试之所以出现，背后也有类似的压力。

7. 文件系统与状态检查 - 与文件数量成正比的工作

git status 很慢的仓库，问题多半不在历史而在宽度。Git 要知道工作树是否与索引不一致，就必须检查文件的状态，而这项检查基本上与文件数量成正比。文件到了几十万个，哪怕什么都没做，检查本身就成了一件苦差事。

Git 备了两套机制来削减这项成本。

  • 未跟踪文件缓存 — 记下目录的修改时间，如果时间没变就不再读里面的内容。这要求操作系统和文件系统正确更新目录的修改时间才能成立，所以 Git 同时提供了事先测试这一点的办法。
  • 文件系统监视 — 直接向外部的监视程序询问什么变了，从而省掉逐个检查全部文件这件事本身。两者一起打开，就能把变更检测和新文件搜索都跳过去。

不过文档附上的但书也要一起读。并不是所有命令都尊重这个标记。有的命令会变快，有的命令原地不动。多出一个常驻的监视进程本身也是成本，而在网络文件系统或容器里，前提条件本身就可能动摇。

8. 单体仓库与多仓库不是答案而是选择

仓库一变重，就会有人提议改结构。可这个决定与其说是性能问题，不如说是关于把成本挪到哪里的决定。哪一边都不会帮你减少总量。

视角单体仓库里会发生什么多仓库里会发生什么
变更单位多个模块在一次提交里被原子地改掉变更按仓库边界被切碎，顺序由人来对齐
依赖关系一张图。版本对齐的问题变少版本锁定与发布顺序成了常态工作
Git 负载宽度和引用数量集中到一处。工具投入变成必需每个仓库都很轻。代价是仓库的数量本身成了管理对象
权限按路径的访问控制得在另一层解决按仓库天然就分开了
构建与 CI影响范围计算是必需的，不做的话每次变更都变成全量构建构建很简单，但做集成验证的位置消失了
发布一个点就能确定整体状态要用若干标签的组合去重建状态

哪一边我都不推荐。要说给一条判断标准的话，去看变更的形状。如果一次功能变更习惯性地同时动到三个以上的仓库，那就是仓库边界与真实耦合度对不上的信号。这时把仓库合并只是选项之一，重新划边界或者把接口稳定下来，往往才是更靠前的一步。反过来，如果每个仓库都独立发布、互相不知道对方的内部，那就没有理由合并进来、把左边那一列的成本重新扛上身。分支方式本身也会随团队规模和发布周期改变价值，那部分在分支策略整理里另外讲过。

9. 削减历史这件事的风险

这一节不是操作指南，写的是动手之前该知道的事。

第 1 节看到的那条性质在这里开账单。因为对象的名字来自内容，所以改动过去的某次提交，它之后所有提交的哈希都会变。git filter-branch 的文档对此有明确警告：被重写的历史会让所有对象都拿到不同的名字，并且不会与原分支汇合。同一篇文档还说这个命令本身坑多、性能差，建议改用 git filter-repo 之类的替代工具。

把实际会坏掉的东西列成清单会更清楚。

  • 签名 — 提交签名是对那次提交内容的签名。内容一变，验证就通不过。
  • 标签 — 原本指向旧提交的标签，会变成指向新历史之外。不一起搬走的话，旧的图就会以引用的形式活下来。
  • 写在外部的哈希 — 问题跟踪系统、发布记录、文档、锁文件里写着的提交哈希，会全部失去指向。
  • 同时在做事的同事 — 文档写明协作者必须把自己的改动重新叠到新历史上，或者删掉仓库重新拉取。人越多，出事的可能性越大。
  • 自动化 — 把提交哈希当作缓存键或发布标识的流水线，会悄无声息地开始指向别的东西。

所以最低前提是这样的。先用完整副本演练一遍，把动手前的状态单独保存，在重写进行期间关闭写入口不让任何人写，结束之后事先约定好所有人要怎么重新拉取。没有回退路径就不要动手。而且这项操作唯一正当的理由，通常只有三种之一 — 秘密信息进去了，有法律上的删除义务，或者嵌进去了别的办法碰不了的大体积资产。如果动机只是想让仓库轻一点，那就先把前面几节的少下载对策全都试过一遍再说。

10. 该测量什么

光凭慢的印象是选不出轴的。要看的是不是总时间，而是时间花在了哪个阶段。

  • 把克隆拆成阶段 — 服务端数对象并压缩的时间、传输的时间、收到之后解开并建索引的时间、最后检出的时间，各自指向完全不同的成因。传输很短而总时间很长，问题就不在网络。
  • 检出与状态检查 — 只有这两项格外慢，那就是宽度在主导。
  • 对象构成 — 打包里是哪些对象在占地方，超大的 blob 有几个，它们又来自哪些路径。
  • 引用与提交的数量 — 判断协商是否吃力的第一个指标。
  • 工作树的文件数量 — 宽度这条轴最简单的代理指标。
  • 可复现的条件 — 不区分缓存已经预热和缓存是冷的两种状态，比较就不成立。

上了对策之后，也要回到同一处再测一遍。一次只改一样东西，把改了什么、测了什么都记下来。没有记录的话，半年后会有人把同一个问题从头再诊断一遍。

未能确认的部分

  • Continuity 公开文章里那些吞吐与延迟数字的测量条件(硬件、对象体积分布、并发水平)在文中没有写明，无法确认。这也是正文没有把这些数字当作比较或依据的原因。
  • 同一篇文章中描述其他系统设计的部分，同样是发布方的叙述，未能用那套系统运营方的资料做交叉确认。
  • 少下载的各种对策实际能省下百分之几，仓库之间差异很大，因此不给出可以一般化的数字。
  • 文件系统监视在哪些命令上有效、在哪些命令上无效，会随版本和平台变化，必须到自己所用 Git 版本的文档里直接确认。

小结

Git 是一个用内容给东西命名的对象存储。正因为这个前提，重复会自行消失；也正因为这个前提，改动过去就会让之后的一切都变。打包文件与增量压缩是拿容量换 CPU 和随机访问的一桩好交易，但仓库一变大，交易的两头就一起长大。

要带走的有三条。第一，把变大这个说法拆成深度、宽度、体积。对策因轴而异，轴挑错了什么都不会改善。第二，少下载的各种方法并不消除成本，只是推迟它。要在知道被推迟的账何时以何种形态回来的前提下做选择。第三，重写历史是最后手段，不是在没有回退路径和共识的情况下能开工的事。

结构的选择也一样。单体仓库与多仓库不是性能处方，而是改变成本所在位置的选择，依据不是潮流而是我们的变更实际长成什么形状。下次再听到有人说仓库很重，先别急着挑对策，试着用一句话回答那到底是哪一条轴。
