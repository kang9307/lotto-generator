계기와 사건의 개요 — 정상적인 프로젝트 문의 뒤에 숨은 브랜치 전환 유도

2026년 10월 초, 오픈소스 생태계에서 활동하는 한 웹 개발자가 외부 잠재 고객을 사칭한 공격자로부터 정교한 표적 공격을 받은 경위를 공개했다. 공격자는 교육 기술 분야의 웹 애플리케이션 외주 개발을 문의하며 일반적인 비즈니스 미팅 절차를 밟는 것처럼 가장했다. 미팅 일정 조율 링크를 전달받은 공격자는 회의를 진행하기 전에 프로젝트 명세서를 검토하고 기밀유지협약(NDA)에 서명해 줄 것을 요구하며 클라우드 저장소 링크를 전달했다.

공유된 클라우드 폴더에는 마크다운 형식으로 작성된 프로젝트 개요 문서들이 여러 하위 폴더에 걸쳐 분산되어 있었다. 문서의 내용은 다소 개괄적이었으나 초기 단계의 시제품(MVP) 요구사항으로 보기에는 충분한 분량을 갖추고 있었다. 그러나 개발자가 문서 폴더 내부에서 서명해야 할 협약서 템플릿을 찾지 못해 이메일 발송을 요청하자, 상대방은 「협약서는 저장소의 NDA 브랜치에 보관되어 있으니 브랜치를 전환하여 작성한 뒤 미팅 전에 전달해 달라」고 회신했다.

평범한 문서 파일 공유처럼 보였던 폴더 내부에 숨겨진 .git 디렉터리가 존재한다는 점, 그리고 일반적인 텍스트 파일 서명을 위해 굳이 특정 브랜치로의 체크아웃을 요구한다는 점에 의구심을 품은 개발자는 Git 명령을 실행하기에 앞서 .git/hooks 디렉터리를 열람했다. 그 결과 기본 예제 파일들 사이에 실제 실행 권한을 가진 단 하나의 post-checkout 스크립트가 숨겨져 있음을 발견했고, 브랜치 전환 명령을 내리기 직전에 작업을 중단함으로써 악성 코드의 실행을 차단했다.

  • 일상적인 비즈니스 문의와 협약서 서명 요청을 미끼로 한 사회공학적 접근 방식.
  • 클라우드 파일 공유 폴더 안에 숨겨진 버전 관리 메타데이터 디렉터리의 존재.
  • 개발자에게 매우 익숙한 브랜치 전환 동작을 악용해 임의 명령 실행을 유도한 메커니즘.

Git 훅의 설계 원칙 — 왜 clone은 훅 디렉터리를 복제하지 않는가

이 공격 시도의 기술적 핵심을 이해하기 위해서는 Git 훅(Git Hooks)의 설계 목적과 분산 버전 관리 시스템으로서의 보안 경계를 살펴보아야 한다. Git 공식 문서(githooks(5))에 명시되어 있듯이, 훅은 커밋, 체크아웃, 병합 등 저장소의 주요 수명주기 이벤트 전후에 자동으로 실행되는 사용자 정의 스크립트다. 훅 스크립트는 각 로컬 저장소의 메타데이터 경로인 $GIT_DIR/hooks(기본값은 .git/hooks)에 위치한다.

Git 설계자들은 초기부터 훅 시스템이 가질 수 있는 심각한 보안 위험을 인지하고 있었다. 만약 원격 저장소를 로컬로 복제할 때 훅 스크립트까지 함께 내려받아 실행 권한을 부여한다면, 신뢰할 수 없는 공개 저장소를 단순히 복제(clone)하는 것만으로도 원격 공격자의 임의 코드가 로컬 시스템에서 무조건 실행되는 치명적인 취약점이 발생하기 때문이다.

이 때문에 Git의 공식 사양(git-clone(1))은 엄격한 보안 경계를 규정하고 있다.

  • 복제 격리 원칙: git clone 명령은 원격 객체 데이터베이스(커밋, 트리, 블롭)와 참조(브랜치, 태그)만을 네트워크로 전송받는다.
  • 로컬 전용 템플릿: 복제 완료 후 생성되는 .git/hooks 디렉터리에는 클라이언트 환경의 템플릿에 정의된 *.sample 예제 파일들만 배치된다.
  • 원격 훅 배제: 원격 저장소에 어떤 스크립트가 설정되어 있든 간에, 그것이 git clone을 통해 복제자의 .git/hooks로 전파되는 경로는 공식 프로토콜 수준에서 완전히 차단되어 있다.

따라서 표준적인 git clone 명령을 사용하는 환경에서는 원격 저장소에 숨겨진 훅 파일이 자동으로 로컬에 안착하여 실행될 수 없다.

아카이브 직접 수령의 위험 — clone 방어를 우회하여 훅을 전달하는 구조

공격자가 일반적인 깃허브나 깃랩 저장소 링크 대신 클라우드 공유 폴더나 압축 아카이브(ZIP, TAR) 형태로 작업 트리를 통째로 전달한 이유가 바로 여기에 있다. git clone 명령이 제공하는 프로토콜 레벨의 훅 차단 방어막을 우회하기 위한 수법이다.

운영체제의 일반 파일 시스템 복사 작업이나 아카이브 압축 해제는 파일의 숨김 속성과 실행 권한을 그대로 유지한 채 모든 디렉터리를 디스크에 기록한다. 공격자가 로컬에서 .git/hooks/post-checkout 파일을 생성하고 실행 권한(chmod +x)을 부여한 뒤 폴더 전체를 압축하거나 동기화 드라이브에 업로드하면, 피해자가 이를 내려받아 압축을 푸는 순간 .git/hooks 내부의 실행 파일이 그대로 디스크에 복원된다.

이러한 전달 기법의 무서운 점은 개발자의 심리적 허점을 찌른다는 데 있다. 개발자는 코드가 담긴 디렉터리를 보면 자연스럽게 터미널을 열고 상태를 확인하거나 브랜치를 이동하려는 관성에 젖어 있다. 일반 파일 브라우저에서는 .으로 시작하는 디렉터리가 기본적으로 숨겨져 보이지 않기 때문에, 일반 텍스트 문서를 열람하고 있다고 착각한 상태에서 습관적으로 Git CLI 명령을 입력하도록 유도하는 것이다.

  • 숨김 디렉터리 속성으로 인해 파일 관리자 화면에서 위험 요소가 시각적으로 은폐됨.
  • 클라우드 저장소나 압축 해제 도구가 파일의 실행 권한 비트를 임의로 제거하지 않음.
  • 저장소 메타데이터가 외부에서 통째로 주입되었음에도 Git 클라이언트는 이를 사용자가 의도한 정상 로컬 저장소로 인식함.

post-checkout 훅의 실행 조건과 파괴적 동작 방식

그렇다면 공격자는 왜 수많은 훅 중 하필 post-checkout을 표적으로 삼았는가. Git 공식 문서에 따르면 post-checkout 훅은 다음과 같은 명확한 조건에서 호출된다.

이 훅은 git checkout <branch> 또는 git switch <branch> 명령이 성공적으로 작업 트리를 갱신한 직후 실행된다. Git 엔진은 이 훅을 호출하면서 세 가지 매개변수를 순서대로 전달한다.

  • 첫 번째 인자: 이전 HEAD가 가리키던 커밋의 참조 해시값.
  • 두 번째 인자: 새로 전환된 HEAD가 가리키는 커밋의 참조 해시값.
  • 세 번째 인자: 브랜치 전환인지 파일 체크아웃인지를 구분하는 플래그(브랜치 전환 시 1, 단순 파일 복원 시 0).

공격자가 상대방에게 「NDA 문서는 특정 브랜치에 있으니 브랜치를 전환해 달라」고 굳이 요청한 이유가 바로 이 세 번째 인자를 1로 만들어 훅 스크립트 내부의 분기문을 정상 통과시키고 악성 행위를 촉발하기 위함이었다. 이 훅의 종료 코드는 git checkout 명령 자체의 성공 여부에 영향을 주지 않지만, 스크립트가 호출되는 순간 이미 시스템 권한 아래에서 악성 코드가 실행을 완료하게 된다.

개발자가 공개한 분석 내용에 따르면, 발견된 악성 훅은 외부 애플리케이션 호스팅 플랫폼을 명령 및 제어(C2) 인프라로 활용하도록 구성되어 있었다. 실행 시 현재 운영체제(macOS, Linux 등)를 판별하여 해당 아키텍처에 맞는 2차 바이너리를 원격 서버로부터 다운로드하고, 실행 권한을 부여하여 백그라운드 프로세스로 구동한 뒤, 흔적을 지우기 위해 훅 파일 자신을 파일 시스템에서 즉시 삭제하는 정형화된 다운로더 동작을 취하고 있었다.

이러한 침해 시도가 노린 궁극적인 목표는 개발자의 노트북에서 임의 코드를 실행하여 셸 환경, SSH 개인키, 클라우드 인증 토큰, 그리고 브라우저나 자격증명 헬퍼에 저장된 GitHub 접근 토큰을 탈취하는 것이었다. 소프트웨어 공급망 보안에서 개발자의 작업 환경은 다른 수많은 고객 및 오픈소스 프로젝트로 이어지는 핵심 연결 고리이기 때문이다.

외부 저장소를 열기 전의 읽기 전용 점검 절차 — 무엇을 보아야 하는가

신뢰할 수 없는 출처나 외부 제3자로부터 전달받은 작업 폴더를 다룰 때에는, 어떠한 Git 명령도 터미널에 입력하기 전에 철저한 읽기 전용 점검을 거쳐야 한다. 검증되지 않은 환경에서 git status, git branch, git checkout 등의 명령을 무심코 실행하는 행위는 지뢰를 밟는 것과 다름없다.

점검 시 반드시 지켜야 하는 원칙은 다음과 같다.

  • 실행 배제: 훅 파일로 의심되는 스크립트를 직접 실행하거나 테스트 목적으로 호출하지 않는다. 검사는 오직 텍스트 파일 뷰어나 정적 열람 도구로만 수행한다.
  • 권한 비트 확인: .git/hooks/ 내부의 파일 중 확장자가 .sample이 아니면서 실행 권한이 켜져 있는 파일이 있다면 즉시 위험 징후로 간주한다.
  • 설정 출처 추적: git config --show-origin 명령을 사용하여 현재 저장소에 적용되는 설정이 시스템(/etc), 글로벌(~/.gitconfig), 로컬(.git/config) 중 어디에서 주입되었는지 투명하게 확인한다.
  • 아카이브 단계 선별: 압축을 해제하기 전에 아카이브 내용물 목록을 먼저 열람하여 .git/ 경로가 포함되어 있는지 사전에 걸러낸다.
  • 이중 확장자 및 트릭 주의: 파일명 뒤에 공백이나 제어 문자를 삽입하여 일반 파일처럼 보이게 위장한 스크립트가 없는지 파일 크기와 해시를 대조한다.

개발 환경 격리와 자격증명 방어선 — 컨테이너와 최소 권한

아무리 꼼꼼한 눈 검사를 거치더라도 인간의 주의력에는 한계가 있다. 가장 안전하고 확실한 방어 전략은 신뢰할 수 없는 외부 저장소를 주 작업 머신의 로컬 환경과 완전히 격리된 샌드박스 내부에서만 열어보는 것이다.

이 사이트의 기존 분석 글인 원격 URL에 토큰이 박혀 있다 - git 자격증명이 새는 자리에서 논증했듯이, 개발자 머신에는 개인 액세스 토큰, SSH 키, 원격 저장소 자격증명이 프로세스 메모리와 환경 변수에 상시 노출되어 있다. 또한 브랜치 조작과 복원 과정에서의 혼선은 git 되돌리기 결정표 - reset·revert·restore·checkout 중 무엇을 쓸 것인가에서 다룬 것처럼 작업 트리와 인덱스의 상태에 즉각적인 파급력을 미친다.

따라서 외부 프로젝트를 검토할 때에는 다음과 같은 환경 격리 원칙을 준수해야 한다.

  • 일회용 격리 컨테이너 활용: 도커(Docker)나 포드맨(Podman)과 같은 컨테이너 환경에서 볼륨 마운트 없이 코드를 복사하여 검토한다. 호스트 머신의 홈 디렉터리나 SSH 에이전트 소켓을 절대 컨테이너 내부로 바인드 마운트하지 않는다.
  • 클라우드 개발 환경 활용: GitHub Codespaces나 격리된 가상 사설 서버(VPS)와 같이 로컬 자격증명과 완전히 단절된 원격 임베디드 샌드박스를 이용한다.
  • 최소 권한의 자격증명 분리: 프로젝트별로 서로 다른 키페어를 운용하고, 외주 및 검토용 장비에는 사내 핵심 인프라나 고객 시스템에 접근할 수 있는 관리자 권한 토큰을 일체 저장하지 않는다.
  • Git 전역 훅 경로 통제: 로컬 저장소의 악성 훅이 실행되는 것을 방지하기 위해 사용자 글로벌 설정에 git config --global core.hooksPath /dev/null과 같이 빈 경로를 지정하거나, 명시적으로 통제된 디렉터리만 바라보도록 고정하는 방안도 고려할 수 있다.

한계와 한 사람의 권고 — LLM 감사 제안의 현실적 위치

사건을 겪은 개발자는 자신의 블로그 글에서 피해 예방을 위한 몇 가지 실무적 권고를 남겼다. 그중에는 신뢰할 수 없는 코드와 설정 파일이 포함된 디렉터리를 접했을 때, 실행 권한을 일체 부여하지 않은 상태에서 대규모 언어 모델(LLM)에 텍스트 형태로 프롬프트를 전달하여 숨겨진 악성 로직이나 이상 스크립트가 존재하는지 정적 감사를 받아보라는 제안이 포함되어 있었다.

그러나 이 권고는 어디까지나 한 개발자의 개인적 제안으로 귀속되어야 하며, 보안을 완벽히 담보하는 기술적 만능열쇠로 단정되어서는 안 된다. 인공지능 모델을 활용한 보안 감사는 다음과 같은 본질적인 한계를 지닌다.

  • 환각과 오탐의 위험: 앞선 커널 분석에서도 확인되었듯이 언어 모델은 난독화된 셸 스크립트나 환경 종속적인 실행 경로를 잘못 해석하여 치명적인 악성 행위를 정상 코드로 오판할 가능성이 상존한다.
  • 민감 데이터 유출 문제: 검토 대상 코드를 외부 상용 인공지능 API에 그대로 업로드할 경우, 프로젝트의 비공개 지적 재산이나 내부 정보가 제3자 클라우드 서비스로 전송되는 또 다른 컴플라이언스 위반을 초래할 수 있다.
  • 보안의 우선순위 역전: 인공지능을 통한 텍스트 분석보다 우선되어야 하는 것은 파일 시스템 레벨에서의 실행 권한 차단과 물리적 컨테이너 격리라는 기본 원칙이다.

결국 사회공학적 기법과 개발 도구의 기본 동작을 결합한 지능형 공격을 막아내는 최선의 방패는, 마법 같은 단일 도구에 기대는 것이 아니라 도구의 자동화 메커니즘을 정확히 이해하고 의심스러운 입력에 대해 읽기 전용 상태를 유지하는 엔지니어링 규율에 있다.
