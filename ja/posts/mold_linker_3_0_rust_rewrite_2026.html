経緯と背景 — C++からRustへの全面再実装とLinuxディストリビューション標準リンカという目標

mold 3.0.0は2026年10月5日にリリースされた、高速リンカmoldの最初のRust版である。リリースノートは、2.42.1のリリースノートで予告したとおりmoldをC++からRustへ書き直したこと、そして2.42.1がC++版の最後のリリースであることを記している。2026年9月11日に公開された2.42.1のノートは、再実装の理由として、2026年のRustはシステムソフトウェアにとって実用的な選択肢になっており、メモリ安全性のような強い安全保証を提供する点を挙げている。同じノートは、利用者から見ればmold 3.0がこれまでと同じように動き、内部の実装だけが変わることが目標だとも述べている。

3.0.0のノートが示すmold 3.xの目標は、GNU ldとの間に残る互換性の差、とくにリンカスクリプト（linker script）対応を埋め、moldがLinuxディストリビューションの標準リンカとして採用される道を整えることである。2.42.1のノートはこれをさらに詳しく説明している。多くのLinuxディストリビューションでシステムのリンカである/usr/bin/ldは今もGNU ldなので、まず不足しているリンカスクリプトの機能を実装してユーザー空間のプログラムだけでなくカーネルやファームウェアもリンクできるようにし、そのうえで広範な互換性テストとディストリビューション開発者との協力により、採用を現実的にするという計画である。

READMEは速度の数値を別に載せている。2026年8月のベンチマークで、moldは中央値でLLVM lldの4.9倍、wildの1.9倍の速さでリンクしたという内容で、結果の全体表はREADMEのBenchmark節にある。この数値は3.0.0のリリースノートではなくREADMEの記述なので、3.0.0と2.42.1の比較として読んではならない。

今回のリリースが示す方向性を、ノートの文言に沿って整理すると次のようになる。

  • ドロップイン代替: 同じコマンドラインオプションと同じターゲットアーキテクチャに対応し、出力はノートに列挙されたバグ修正を除いて同じである。
  • GNU ldとの差の解消: リンカスクリプト対応をはじめ、残る互換性の差を埋めることが3.xの目標である。
  • 標準リンカ採用の土台: moldがLinuxディストリビューションの標準リンカとして採用される道を整えることが目標として記されている。
  • 破損入力に対する安全性: 範囲外の読み取りは境界検査を経てパニックで停止する。
  • ソースビルド方式の変更: CMakeがCargoに置き換わり、Rust 1.95以上が必要になった。

何が変わっていないのか — v2.42.1のドロップイン代替と同等のリンク性能・検証

言語の書き直しで利用者がまず気にするのは、オプションが変わったか、遅くなったかである。リリースノートは、mold 3.0は2.42.1のドロップイン代替を意図したものだと述べている。同じコマンドラインオプションを受け付け、同じターゲットアーキテクチャに対応し、ノートに列挙されたバグ修正を除いて同じ出力を生成する。リンク性能は2.42.1と同等（on par）の水準を保つとされている。ノートにはリンク時間やメモリ使用量の数値は載っていない。

対応アーキテクチャは、READMEがx86-64、i386、ARM 32/64、RISC-V 32/64、PowerPC 32/64、s390x、LoongArch 32/64、SPARC64、m68k、SH-4と列挙している。

互換性の検証としてノートが挙げているのは次の三つで、最後の項目は互換が及ぶ範囲を区別するものである。

  • 全対応ターゲットでのテストスイート実行: 対応する各ターゲットでテストスイートを実行した。
  • 広範な実ワークロードとオプション組み合わせでの出力比較: さまざまな実ワークロードとオプションの組み合わせで、リンカの出力を比較した。
  • Gentooの全パッケージのビルド: Gentooのすべてのパッケージをビルドし、ノートは回帰を見つけなかった（We found no regressions）と記している。
  • 互換の範囲はリンカのオプション・アーキテクチャ・出力: 同じリリースで、ビルドシステムはCMakeからCargoへ、テストの実行はctestからcargo testへ変わった。moldをソースからビルドする側のスクリプトやCI設定はそのままでは使えず、後述のビルドの節にある変更に従う必要がある。

安全性モデルの変化 — セグメンテーション違反（segfault）からパニック（panic）へ

ノートが安全性について述べているのは、破損した入力ファイル（corrupted input files）についてただ一点である。C++版はそのような入力に出会うと、メモリを範囲外から読み取り、セグメンテーション違反で終了することがあった。Rustへ移した3.0では、その読み取りに境界検査が掛かっており、moldは不正なアクセスが起きた箇所でパニックとして停止する。

変わるのは停止のしかたである。ノートの記述によれば、破損した入力でsegfaultにより落ちていた箇所が、パニックで停止する箇所に変わったのであり、損傷を修復してリンクが成功するようになるという記述はどこにもない。通常の入力ではこの変化は表に出ない。3.0の出力は、バグ修正の項目を除けば2.42.1と同じだからである。

同じノートのバグ修正一覧には、不正な入力やオプションの組み合わせに対して、壊れた出力やクラッシュの代わりにエラーを出すよう改めた項目が別にある。これは境界検査とは別個の修正であり、具体的な項目は後の出力の正確性の節にまとめる。

安全性に関する点を、ノートの記述の範囲内で整理すると次のようになる。

  • 対象: 破損した入力ファイルを処理する場合に限った記述である。
  • 以前の動作: C++版は範囲外のメモリを読み取り、セグメンテーション違反でクラッシュすることがあった。
  • 3.0の動作: その読み取りに境界検査が適用され、不正なアクセスの箇所でパニックとして停止する。
  • ノートが述べていないこと: パニックメッセージの形式、境界検査が掛かるコードの範囲、検査による性能コストは記述されていない。性能は2.42.1と同等という一文があるだけである。

ビルドとパッケージング手順の変化 — Cargo導入とRust 1.95+要件

moldをソースからビルドする人やディストリビューションのパッケージを作る人にとって、最大の変化はビルドシステムである。ノートは、moldがCMakeに代わってCargoでビルドされるようになり、Rust 1.95以上とCコンパイラが必要だと述べている。CMakeのオプションはすべて削除された。READMEはさらにGitが必要なこと、システムのRustが古い場合はrustupで安定版（stable）のツールチェーンを入れることを付け加えている。

コンパイル

READMEに書かれたコンパイル手順は次のとおりである。実行ファイルとその付属のpreloadライブラリは、それぞれtarget/release/moldとtarget/release/mold-wrapper.soに作られる。

git clone https://github.com/rui314/mold.git
                    cd mold
                    cargo build --release

インストールとMOLD_LIBDIR

READMEは、sudo ./install-mold.shを実行すると/usr/local以下にインストールされ、別のプレフィックスに入れるにはPREFIXを指定すると案内している。ノートによれば、スクリプトはDESTDIRも受け付ける。mold-wrapper.soは$PREFIX/lib/moldにインストールされ、インストールせずにtarget/release/moldを直接実行することもできる。

sudo ./install-mold.sh
                    sudo PREFIX=/usr ./install-mold.sh

ライブラリを$PREFIX/libではないディレクトリ、たとえば/usr/lib64に入れる場合は、ノートもREADMEも、MOLD_LIBDIR環境変数をそのディレクトリに設定するよう求めている。cargo buildのときとinstall-mold.shでインストールするときの両方で設定する必要があり、そうすることでmold -runがmold-wrapper.soを見つけられる。READMEの説明では、mold -runはLD_PRELOADで付属の共有オブジェクトを読み込ませてexec系の呼び出しを横取りし、ld、ld.bfd、ld.gold、ld.lldの呼び出しをmoldに置き換える機能なので、このファイルの場所が重要になる。

ビルドとテストのツール類に残る変更点は次のとおりである。

  • テストの実行: ctestではなくcargo testで実行する。
  • テスト依存関係のスクリプト: install-build-deps.shがinstall-test-deps.shに置き換わった。後者はテストを実行するときにだけ必要である。
  • ターゲットの選択: MOLD_TARGETSというCMake変数はCargoのfeaturesに置き換わった。ノートは、従来どおりディストリビューションはすべてのターゲットをビルドすべきだと述べている。
  • CMakeオプションの削除: CMakeで使っていたオプションはすべてなくなったので、既存のパッケージングスクリプトでそれを渡している部分は直す必要がある。

依存関係の変化 — oneTBBの排除とmimalloc 3.5.3・圧縮ライブラリの構成

ノートは、moldがoneTBBに依存しなくなったと述べている。oneTBBの代わりに並列処理を担う実装が何なのかは、ノートには記述がない。残る依存関係の構成は、ノートが項目ごとに明記している。

  • mimalloc 3.5.3の静的リンク: 従来どおり、mimalloc 3.5.3を静的にリンクする。
  • システムアロケータの選択: --features system-allocatorを付けてビルドすると、システムのmallocを使う。
  • システムのzlib: システムにzlibがあれば、それをリンクする。
  • zstdとBLAKE3の同梱: この二つのライブラリはmoldに含まれている。
  • システムのzstdのリンク: ZSTD_SYS_USE_PKG_CONFIG=1を設定すると、システムのzstdをリンクする。

出力の正確性とGNU ld・lld互換性の改善項目

3.0.0のノートのBug Fixes and Compatibility Improvementsの節には、共通シンボルの扱い、バージョンスクリプトの優先順位、オプションの解釈など、GNU ldやlldの動作に合わせた項目と、アーキテクチャ別の修正が長く続く。そのうち、オプションとシンボルの扱いに関する代表的な項目を表にまとめる。

項目 3.0.0のノートの記述 該当するオプション・文脈
同名の共通シンボル（Common Symbol） サイズの異なる同名の共通シンボルは、最大のサイズと最も厳しいアラインメントを持つ。GNU ld、lldと同じ方式である。 シンボル解決
出力ファイルが入力ファイルでもある場合 mold -r -o foo.o foo.o bar.oのように使うと起きていたクラッシュと出力の破損を修正した。 -r（部分リンク）
セクションのガベージコレクション --initと--finiで指定した関数を、もう削除しない。 --gc-sections
同一コードの統合 共有ライブラリがエクスポートした関数をもう統合しない。--icf=allを--emit-relocsと使うときのクラッシュも修正した。 --icf=safe、--icf=all
バージョンスクリプトの優先順位 一つのシンボルが複数のバージョンノードにある場合は、最初のノードが優先される。GNU ld、lldと同じである。 バージョンスクリプト
シングルダッシュのオプションの解釈 GNU ldが読むのと同じ方法で読む。たとえば-entry=mainが-e ntry=mainと読まれていた点が修正された。 コマンドライン
起動時の仮想アドレス空間の予約 起動時に8 GiBの仮想アドレス空間を予約しなくなったので、ulimit -vの下でも動作する。 プロセス起動
非決定的な出力 いくつかのケースを修正した。ノートが挙げているのは--dependency-file、--repro、同名のCOMDATグループが多い-r、一部の動的再配置である。 出力の再現性

非決定的な出力の項目は、列挙された複数のケース（several cases）を修正したという記述であり、どんな条件でも出力がバイト単位で一致するという保証はノートにない。また-rは部分リンクであって、インクリメンタルリンクではない。ノートが修正したのは、-rを使ったときのクラッシュと出力の破損である。

表の外にも項目がある。共有ライブラリに定義されたシンボルに対するGOT相対の再配置（R_X86_64_GOTOFF64、R_ARM_REL32）は、以前は黙って誤ったアドレスになっていたが、3.0では正しく処理するか、エラーとして報告する。--defsymが共有ライブラリのシンボルの別名になる場合、64ビットに収まらない--defsymの値、割り当てられながら圧縮されたセクション、--strip-allと--emit-relocsの組み合わせといったケースは、壊れた出力やクラッシュではなくエラーになる。部分リンクでは、二番目以降の入力ファイルのC++例外が壊れていた問題と、--gc-sectionsが再配置の参照するデータを落としていた問題も直された。AArch64、PPC32、ARM32では、範囲拡張サンクを経由した呼び出しが、ChromiumのARM64デバッグビルドのような大きなプログラムで誤ったアドレスにジャンプしていた問題が修正された。

アーキテクチャ別の項目はさらに具体的である。AArch64ではR_AARCH64_TSTBR14やR_AARCH64_GOT_LD_PREL19といった再配置タイプへの対応が増え、ARM32ではR_ARM_ALU_PC_G0とR_ARM_THM_PC12への対応が加わった。PPC32とm68kでは、-fpicコードが使う16ビットのオフセットに対してGOTが大きすぎる場合に、黙って切り詰められる代わりにエラーとして報告される。そのほか、--separate-debug-fileが作るファイルから.gnu_debuglinkセクションが外れ、意味のない__start_EHDR系のシンボルをもう作らず、MOLD_JOBSはXDG_RUNTIME_DIRが空文字列でも動作する。

mold 2.42.1（C++）とmold 3.0.0（Rust）の構成の対照

二つのバージョンの構成の違いを、3.0.0のノートが記述している範囲で対照する。ノートが述べていないところは、記述がないと書いてある。

比較項目 mold 2.42.1（C++の最終リリース） mold 3.0.0（Rustの初リリース）
実装言語 C++ Rust
ビルドシステム CMake Cargo（CMakeのオプションは削除）
ソースビルドの要件 3.0.0のノートに記述なし Rust 1.95以上とCコンパイラ
oneTBBへの依存 依存している 依存しない
メモリアロケータ mimallocを静的リンク（ノートのas before） mimalloc 3.5.3を静的リンク。--features system-allocatorでシステムのmallocを選択
テストの実行 ctest、install-build-deps.sh cargo test、install-test-deps.sh
破損した入力ファイル 範囲外の読み取りとセグメンテーション違反によるクラッシュ 境界検査に掛かった箇所でパニック
起動時の仮想アドレス空間 8 GiBを予約 予約しないのでulimit -vの下でも動作

まとめると、リンカのオプションと出力は引き継がれ、ソースのビルド手順と内部の構成は変わった。この表の2.42.1の欄は3.0.0のノートの記述から逆に読み取ったものなので、2.42.1自身の文書とは表現が異なる可能性がある。

確認できなかったこと

  • 3.0.0のリリースノートにはリンク時間やメモリ使用量の数値がなく、2.42.1と同等という記述までしかない。READMEの4.9倍・1.9倍という数値は、2026-08-28時点のソースからビルドしたリンカを比べたものだが、どのmoldのバージョンを測ったのかはREADMEからは確認できない。
  • Rustコードベースの全体の規模やモジュール構成は、ノートにもREADMEにも記述がない。
  • 再実装に使われたRustのエディションは明記されていない。確認できる要件はRust 1.95以上というツールチェーンの条件だけである。
  • リンカスクリプト対応でどの機能がまだ欠けているのかは、ノートに一覧がなく、残る差を埋めるという目標だけが記されている。
  • Linuxディストリビューションがmoldを標準リンカとして採用する時期や議論の進み具合は記述されていない。
  • 3.0.0で実際のプロジェクトをリンクしたときに2.42.1と出力がどれだけ違うかについての比較結果は公開されていない。ノートは、バグ修正の項目を除いて同じとだけ述べている。
