能活过二十年的软件有什么不同 - 区分完成与荒废的指标

用实测的代码规模、依赖与变更原因，把完成和死亡区分开

2026年8月2日 开发/基础设施

引言：提交停了三年这件事本身说明不了任何问题

你打开一个准备加进依赖列表的库。星标够多，文档齐全，功能也刚好是你要的那一点。可是提交曲线已经平了三年。这一刻手停住了，因为把没人维护的代码放进生产环境让人心里没底。

于是多数人转去找一个提交活跃的替代品。这个判断未必总是错的，但依据是错的。提交频率不是软件的健康状况，它更接近于剩余工作量的指标。可能是剩下的事多才活跃，也可能是没剩什么才安静。光看曲线分不出是哪一种。

这篇文章想把这个区分变成可以测量的东西。它把长寿软件的条件当作数字而不是感受来处理，下面每一个数字都来自真正跑过的脚本。先说结论：长寿代码的条件不是热情也不是人气，而是小、依赖少、范围窄、有文档。而这四点全都是决定不加入某些东西的结果。这不是技术，是拒绝的累积。

运行环境。下面所有测量都在 Windows 10 Pro (10.0.19045) 上实际执行。Shell 是 GNU bash 5.2.37 (MSYS2/MinGW64)，工具为 Python 3.13.3、Node.js v22.16.0、npm 11.5.2。测量对象是该环境中安装的 Python 3.13 标准库，以及从公共仓库只做解析而未安装的依赖树。脚本全部保存为文件后执行，命令原样抄录。

本文不涉及的内容。整理工作的成本何时回收，属于重构的成本何时回收。这里只看判定标准，不做财务测算。一开始就把代码写得可维护的习惯在写出可维护的代码那一篇。本文只处理如何判定与处置已经存在的代码。

1. 死掉和完成画出同一条曲线

提交停滞这一状态，会用同样的形状呈现两个截然不同的事实。一个是事情没做完却没人做，另一个是事情确实做完了。前者危险，后者反而安全，但在仓库首页上二者毫无区别。

要区分它们，看的不是曲线，而是留下来那些东西的性质。下面是实务中真正可用的判别信号。

观察点偏向荒废的信号偏向完成的信号
开着的问题的性质可复现的缺陷报告无人回复地堆积大多是功能请求，并被以超出范围关闭
构建状态在新工具链上构建失败的报告被搁置新运行时出现后只有适配提交安静落地
文档的时点文档描述的是落后几个版本的行为文档与代码在同一个提交里改动
最近的变更原因根本没有变更，或者原因不明缺陷修复与外部环境适配占多数
安全响应漏洞报告后数月无回应功能不增长但补丁照常发布
发布最后一个版本残留已知的严重缺陷间隔虽长但内容清晰明确

这张表的要点是不要把变更少当成问题。问题不在于变更少，而在于应该出现的变更没有出现。而应该出现的变更大致只有两类：修复内部发现的缺陷，以及适配外部已经改变的世界。只要这两类还在出现，这个项目就活着。功能不增长是另一回事，有时甚至是刻意为之的结果。

实务上再补一句：不要只在一个仓库里下结论。发行版是否仍在收录这份软件、其他项目是否仍在链接它，是强得多的信号。上游安静而下游活跃时，那份代码已经成了基础设施。

2. 小代码库能活下来的原因 - 读得懂才修得了

小代码之所以长寿，不是因为优雅，而是因为交接成本落在一个人之内。存在一个规模，能让「这个模块以后归你」这句话变成可执行的指令。为了不靠感觉说这个规模，就得去测。

测法很简单：去掉注释与空行，只数真正的代码行。下面是针对 Python 标准库跑出来的结果。

$ python measure_size.py C:/Python313/Lib/json C:/Python313/Lib/email \
                        C:/Python313/Lib/asyncio C:/Python313/Lib/csv.py C:/Python313/Lib/textwrap.py

target                       files      code   comment     blank      bytes
json                             5      1105        51       172      50103
email                           29      7764      1035      1592     396685
asyncio                         33     11165      1008      2568     533673
csv.py                           1       392        40        81      19691
textwrap.py                      1       355        68        74      20436

这里要读的不是排名，而是数量级。355 行和 11,165 行不是同一类东西。前者一个人一天能读完并接过责任，后者做不到。可维护性与其说是连续的刻度，不如说是一种带阈值的性质。

不过小并不直接等于好。小模块意味着包含的功能少，缺的部分要使用者自己补。功能多的那一边，是把这份成本自己扛下来让使用者省事。哪一边正确，取决于这份代码被多少人用、用多久。使用者越多、寿命越长，推给使用者那一侧的成本总和就越大。

2.1 看规模时要一起看的东西

  • 注释比例。上面的输出里，email 是 7,764 行代码对 1,035 行注释，约 13%。注释极少的大文件，阅读成本高于其行数。
  • 文件数量。同样的行数，散在 33 个文件里和集中在 1 个文件里，检索成本完全不同。
  • 最大单个文件的规模。瓶颈是最大值而不是平均值。如果有一个文件是 3,000 行，那个文件就等于这个模块本身。
  • 是否计入测试代码。算上测试规模会膨胀，但从交接角度看测试也是必须读的资产。把两个数字分开记录更合适。
  • 排除生成代码。解析器生成器的产物之类人不会读的文件必须剔除，否则指标就没有意义了。

顺带一提，有些长期维护的项目会直接把注释比例作为公开指标。SQLite 的文档明确写着自己的源码超过 35% 是注释，并把它列为长期支持的依据之一。注释比例高并不代表代码就好，但它确实是一个信号：这份代码是把接手的人当作常量来写的。

3. 依赖决定寿命 - 你不动它，别人会动

代码损坏的原因里，相当一部分并非出自你自己。你什么都不做，只要别人改了，它就会坏。所以依赖数量不是衡量功能便利性的数字，而是衡量你向外部暴露的面积的数字。

问题在于，多数人是按直接声明的数量去数这个数字的。真实面积要宽得多。下面是不安装、只解析依赖树的实测。

$ cat package.json
{"name":"probe","version":"1.0.0","dependencies":{"express":"4.21.2"}}

$ npm install --package-lock-only --no-audit --no-fund
up to date in 3s

$ node -e "const l=require('./package-lock.json');
           console.log(Object.keys(l.packages).filter(Boolean).length)"
69

只写了一行依赖，锁文件里却出现了69 个条目。用同样的方法又测了几个。表中的 tree 是包含自身的数值。

包直接依赖解析出的树怎么读
express@4.21.23169一行声明拖来68 个别人的仓库
axios@1.7.9323直接数量与真实面积相差七倍以上
chalk@5.4.101外部变化能触及的地方只有它自己
lodash@4.17.2101同样结构。体量虽大，面积却窄
typescript@5.7.301再大的工具只要选择也能保持为零

看这张表不要得出谁更优的结论。树大的一边意味着更多复用别人的成果，从而更快完成更多工作。确实存在这种速度在商业上正确的阶段。树为 1 的一边意味着需要的东西是自己实现的，也意味着那份实现和它的缺陷要自己扛一辈子。二者不是同一根轴的两端，而是选择了不同的成本。

不过若只看寿命这一根轴，方向是明确的。树里的每一个条目都有自己的发布节奏和自己的维护者。其中任何一个停止维护或破坏兼容，你的代码都得响应。你的稳定性与你无法掌控的条目数量成反比。

3.1 没有锁文件的语言怎么测

像 Python 这样导入关系纠缠在标准库内部的情况，需要解析源码求闭包。关键在于限制跳数。

def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels

为什么需要限制，看结果就明白了。下面是在 Python 3.13.3 标准库上测得的数值。mod 是不含自身的模块数，loc 是这些模块的代码行合计。

模块自身代码行1 跳2 跳3 跳完整闭包
textwrap3551 mod / 2,483 loc5 / 5,73916 / 15,697124 / 171,129
csv3923 / 2,8499 / 7,09919 / 16,774124 / 171,129
json1,1053 / 5,87313 / 42,08140 / 63,433125 / 171,436
email7,76418 / 20,76854 / 52,50378 / 106,451180 / 699,430
unittest5,37221 / 36,93372 / 98,229110 / 581,682180 / 699,430

这里得到的最实用的发现是：完整闭包会饱和，没有区分度。不论是 355 行的模块还是 11,165 行的模块，一路追到底都收敛为 124 与 180。而在三跳处截断，数值就从 16 拉开到 174，相差十倍以上。也就是说，依赖指标不是「全部数出来」，而是决定在哪里截断的问题。

这项测量有明确的局限。静态解析会把函数内部和异常处理块内部的惰性导入也全部计入，因此比运行时真正需要的更多。所以这个值是上界。但用于以同一把尺子做比较已经足够。

4. 把范围收窄，就是把功能扔掉

观察寿命长的软件会发现一个共同点：不做的事情列表很长。但这句话经常被误读成「极简主义好」，而实际发生的是拒绝功能请求这项劳动。

一个具体例子是 OpenBSD 的 httpd(8)。手册页只把它描述为支持 FastCGI 与 TLS 的 HTTP 服务器。查发布说明可以看到，这个服务器最早出现在 OpenBSD 5.6，而在同一个版本里 Apache 被从基础系统中移除。该版本的发布日期是 2014 年 11 月 1 日。

在这里得出某一方更优的结论就错了。Apache HTTP Server 2.4 的模块索引里列着大约 140 个模块，认证与授权、代理与负载均衡、缓存、压缩、URL 重写、日志、TLS 全都作为独立模块提供。这个规模不是臃肿，而是设计目标。运维者只挑需要的挂上去，正是这份可扩展性让无数环境至今仍在使用它。刻意做窄的服务器根本做不到的事情就在那份清单里。

所以准确的说法是：收窄范围换来寿命，代价是适用面变小。两边都是代价。判断时该问的不是「功能多不多」，而是「本组织里有没有人因为缺这个功能而用不了」。

  • 决定不加某个功能，就等于一次性抹掉它的缺陷、文档、测试与安全响应。省下的不是代码行数，而是永久性的维护成本。
  • 作为交换使用者必须自己补上。这份成本不会消失，只会转移。
  • 如果范围没有写进文档，就没有拒绝的依据。所以窄范围离开文档无法维持。
  • 留一个扩展点和把功能全都塞进去是两回事。只开一个边界是常见的折中方案。
  • 拒绝会失去人气。必须承认寿命与采用率常常互相拉扯，然后再做选择。

5. 文档为什么必须和代码一起活着

没有文档的代码交接不了。准确地说是可以交出去，但接手的人无法还原原本的意图。所以文档不是代码的附属品，而是可交接性本身。

这里有一条值得参考的惯例。OpenBSD 的 FAQ 把手册页称为该系统信息的权威来源，并说为保持其时效性与准确性投入了相当的努力。更关键的是下一句：修改系统的开发者被要求在改动代码的同时更新手册页。

这条规则的实质不是「请好好写文档」的劝告，而是把文档放进了代码变更的完成条件。这样一来，文档落后于代码的情况在结构上就减少了。前面那张判别表把「文档与代码在同一个提交里改动」列为完成的信号，原因就在这里。

5.1 让文档成为一等公民的最小装置

  • 把文档和代码放在同一个仓库。一旦挪到 wiki，更新主体就分离了，分离之后必然滞后。
  • 把改动公开接口必须同时改文档写进评审规则，作为通过条件。
  • 在文档里写下范围声明。只有写明「这个我们不做」，才有依据关闭请求。
  • 示例要保持可执行的形式。从不运行的示例，时间一长全都会变成谎言。
  • 按版本留下人能读懂的变更记录。提交日志不是它的替代品。
  • 注释用来写为什么这么做。做了什么，代码已经说过了。

文档的篇幅并不等于质量。不过像前面提到的 SQLite 那样把注释比例当作公开指标来管理，或者把手册页更新钉成开发者义务的项目，普遍活得更久，这一点值得留意。两者都是以「人会被替换」为前提造出来的装置。

6. 兼容性承诺 - 决定什么不改

使用者离开的原因，往往不是功能不够，而是升级太痛。反过来说，把不会改动什么钉死，是留住使用者最强的装置。

把这个承诺推到极端的例子是 SQLite。官方文档写明开发者的意图是支持到 2050 年，并承诺让 C 语言 API 与磁盘上的文件格式保持完全向后兼容。文中甚至写着，今天编写的应用应当能与数十年后发布的版本链接并运行。同一份文档还指出，数据库文件在 32 位与 64 位、大端与小端平台上逐字节完全一致。

这项承诺产生的效果有两个方向。

  • 使用者一侧：升级不再是一个事件。当提升版本不会引发代码改动时，继续使用就成了默认选项。
  • 开发者一侧：设计自由度永久缩小。一旦公开的接口，连同其中的错误也要一起背下去。

所以兼容性承诺并不免费，经常破坏兼容的一方也有其理由。错误的设计可以尽早丢弃，因而收敛到更好形态的速度更快。在用户基数薄、变化又快的领域，那样做可能才是合理的。真正的问题是从未做出承诺却频繁破坏。那样使用者每次都会被吓一跳。

整理成实务上可以直接套用的形式如下。

  • 把什么算公开接口写进文档。没写进去的，就意味着可以改。
  • 破坏性变更要同时给出预告期和迁移路径。只有其中一个，使用者跟不上。
  • 文件格式与存储模式的寿命远长于 API。破坏这里，数据就成了人质。
  • 默认值变更要按与 API 变更同等的分量处理。签名没变但行为变了，同样是破坏。
  • 如果兼容无法维持，就换个名字。用同一个名字发布不同的东西是最糟的做法。

7. 交接 - 维护者更替后仍能延续的条件

在活了二十年的软件里，同一个人坚持二十年的情况很少见。所以寿命的实质条件不是热情，而是可替换性，也就是通常所说的降低巴士系数的问题。

前面提到的两个守护进程恰好是有趣的例子。relayd(8) 手册页的 HISTORY 一节记载，这个程序最初以 hoststated 的名字出现在 OpenBSD 4.1，在 4.3 改成了现在的名字。AUTHORS 一节里列着两个人。而 httpd(8) 的手册页则说明，这个服务器派生自 relayd。名字会变，作者不止一人，一个程序的代码会分岔成另一个程序。这样的移动之所以可能，前提是先有文档和边界。

降低巴士系数的装置不是抽象的说法，而是具体的文件与规则。

  • 构建必须一条命令完成。「只能在负责人的笔记本上构建」是最常见的死因。
  • 把运行环境写成代码。需要的运行时版本与外部工具，要钉在配置文件里而不是散文里。
  • 测试要能报告失败。接手的人改完之后没有办法自己知道是否弄坏了，就不敢动手。
  • 部署流程要写进文档。部署被遗忘的频率远高于代码。
  • 留下决策记录。没有「为什么选这个结构」，后任要么全部重想一遍，要么毫无理由地推倒重来。
  • 权威属于仓库而不是某个联系人。靠「那个去问某某」维持的知识，人一走就跟着走了。
  • 名字要可以移交。名称、所有权、托管若绑在特定个人身上，移交本身就不可能。

最容易被忽略的是最后两条。技术上再完美，只要账号与权限绑定在个人身上，这份软件的寿命就等于那个账号的寿命。域名、包仓库的所有权、签名密钥都属于这一类。

8. 什么时候重写才是对的

前面的内容如果被读成「守住旧东西」就麻烦了。年代久远本身既不是价值也不是缺陷。重写变得正当，有另外一套条件。

前面的例子在这里同样有用。OpenBSD 5.6 把既有的服务器从基础系统里拿掉，把新写的服务器放了进来。这与「守住旧东西」正好相反。所以本文主张的不是保存，而是判定。

情形判定依据
需求的前提变了，现有结构无法表达重写这是骨架不匹配，不是少了功能
运行时、语言或核心库结束支持重写或移植代码再好也没有地方可跑
没人读得懂，文档也无法还原重写理解成本已经超过重写成本
安全缺陷从结构本身反复出现重写单个补丁无法收敛
最近的变更以缺陷修复与外部适配为主保留这是代码正常工作的信号
不满集中在代码风格或技术潮流保留那是把能跑的东西换成口味的成本
慢，但瓶颈已被定位局部替换全面重写属于过度反应

如果决定重写，还有一条必须遵守：先还原既有代码为什么长成这样。那个看起来奇怪的分支，很多时候是一次真实故障处理留下的疤痕。不知道原因就重写，会把同样的故障再经历一次。

成本何时回收、如何把整理工作说成投资，这类测算不在本文范围内。那部分在重构的成本何时回收中另行处理。

9. 用在内部代码上 - 该冻结什么

以上条件并非只属于开源项目，它同样适用于内部代码，甚至更为迫切。开源项目的维护者离开还能被分叉，而内部模块的负责人一旦调岗，它就原地变成化石。

内部真正该做的不是「全部保持最新」，而是挑出哪些模块宣布为完成并冻结。冻结不同于荒废。冻结是把剩余维护成本明确写进预算的决定。

检查项可冻结不可冻结
功能需求最近四个季度没有新需求每个季度都有需求进来
契约文档输入输出规格就在仓库里只存在于负责人的脑子里
自动检查有能报告失败的测试在跑依赖人工确认
外部依赖解析出的树一只手数得过来树有几十个条目以上
规模非负责人也能一天读完光是读就要好几天
故障历史最近一年没有生产故障同一原因反复出现
复核时点下一次复核已经钉了日期没有确定的时间点

举个虚构的例子。假设某家公司有一个只做工号格式校验的模块，300 行，没有外部依赖，规格写在内部标准文档里，有测试，两年没有新需求。这就是冻结候选。反过来，结算批处理的规格每个季度都在变，还咬合着外部支付方的响应格式，即使规模很小也不可冻结。判断标准不是规模，而是外面动得有多频繁。

宣布冻结时，有些内容必须一并写下来。

  • 定义冻结的含义。写清范围，例如不接受新功能，但安全补丁与运行时升级继续。
  • 钉住复核日期。没有条件的冻结与荒废无法区分。
  • 写明坏了由谁接。要写角色而不是人名，才扛得住人事调动。
  • 写明替代方案的触发条件。事先约定「满足这个条件就考虑重写」，日后争论会短很多。
  • 把冻结模块清单集中在一处公开。没有清单，就没人知道它被冻结过。

10. 衡量寿命的指标与测法

把前面出现的条件整理成可以定期测量的形式。这不是让你去买一套审计工具，三个数字就能撑起大部分判断。

其中第三个指标变更原因的分布最重要，同时也最少被使用。因为最近的变更究竟是新增功能还是对外适配，直接决定了这份代码的状态。这里做了实测，对象是本环境中安装的 Python 一并分发的变更记录文件。

$ export PYTHONIOENCODING=utf-8
$ python news_entries.py NEWS.txt "3.13.2 final" | python classify_changes.py

reason     count   share
feature        8    8.8%
defect        58   63.7%
external       6    6.6%
doc            1    1.1%
chore          2    2.2%
other         16   17.6%
------------------------
total         91

feature share : 8.8%  (n=91)
shape: maintenance only - freeze candidate
note: keyword rules; always eyeball the 'other' bucket before trusting this

用同一个工具比较三个区间，就能看出这个指标确实有效。下面是从 Python 3.13.3 一并分发的变更记录文件中，分别对三个区间做分类的结果。

区间功能缺陷外部适配其他条目数
3.13.0 alpha 1（开发区间）27.1%37.4%13.4%16.1%634
3.13.2 final（维护区间）8.8%63.7%6.6%17.6%91
3.13.3 final（维护区间）11.7%66.0%15.5%1.9%103

开发区间里 27% 的功能占比，到维护区间掉到 9 至 12%。同一个项目、同一个时期、同一批人，变更的性质却不一样。只看提交数量，维护区间像是「安静下来了」，实际上是性质变了。这就是前面说的「死掉与完成的区分」被写成数字的样子。

这项测量有一些必须坦白的局限。

  • 它是关键词分类。它找的是词而不是理解句子。上面的输出里 other 占 17.6%，这一段必须由人亲自去读。
  • 顺序上先判缺陷再判外部适配。所以「修复某个平台上的缺陷」会被归入缺陷。也就是说外部适配的比例是下界。
  • 结果会随变更记录的书写习惯而变。有提交信息规范的组织，准确率会高得多。
  • 只看一个区间没有意义，必须作为同一项目随时间的变化来读。
  • 正则规则需要按组织自行调整。改规则时，先用正则表达式测试器拿样本句子跑一遍更快。

10.1 三个指标与阈值

指标测法大致解读
代码规模去掉注释与空行的代码行、文件数、最大文件数百行可由一人接手，数千行需要团队
依赖面积锁文件条目数，或三跳导入闭包完整闭包会饱和，因此跳数限制是必需的
变更原因分布把最近的变更记录分成功能、缺陷、外部、文档、其他功能占比高于 25% 是成长中，低于 10% 是冻结候选
注释比例注释行除以代码行没有绝对标准，只看同一仓库内的趋势
文档滞后文档最后改动与代码最后改动之间的时差时差越大，交接成本越高
权限集中度持有部署、签名、域名权限的人数若为 1，那个人就是寿命的上限

阈值不是绝对的。上面写的数字是从本文实测值中导出的起点，应当按各自代码的性质去调整。重要的不是数值本身，而是用同一把尺子反复测量。测一次的值撑不起判定，从第二次开始才有用。

11. 未能确认的部分

下面写明本文未能确认、或根本无从确认的内容。请以与正文同等的分量来读。

  • 作为出发点的那篇文章未能打开。因此其中的主张与表述一概没有引用，只取了主题，重新从一手来源查证。
  • 收窄范围是否为明确意图，文档中无法确认。上面提到的两个守护进程的手册页只写做什么，从未声明不做什么。所谓「窄范围」是从文档记载的功能清单中推断出来的，并非项目的声明。
  • OpenBSD 官方目标文档的原文未曾阅读。只确认了 FAQ 链接到一个单独页面这一点。
  • 用长寿仓库的提交日志跑变更原因分布的计划失败了。该执行环境阻断了仓库克隆，因此改用本地安装的 Python 一并分发的变更记录文件作为对象。需要注意其单位是发布说明条目而非提交。
  • 模块数量是概数。没有清点 Apache 2.4 模块索引的精确总数，只写了在索引页上看到的约 140 个这一量级。
  • 分类器的未分类区间没有逐条审阅。开发区间里有 16.1% 留在 other。粗略浏览样本发现多是性能改进与行为变更的描述，但并未全部读完。
  • 导入闭包是上界。它不区分函数内部或异常处理块内部的惰性导入，实际执行路径所需的数量更少。
  • 没有找到从统计上验证「规模小则更长寿」的资料。本文提供的是指标的定义与测量方法，而不是因果的证明。个案只是个案，反例可能存在。
  • 测量只是一个时点、一个环境的取值。在别的版本或别的操作系统上跑同样的脚本，数字可能不同。

结论：长寿是拒绝的累积

回到开头那一幕。要不要用一个三年没有提交的库，无法靠提交曲线来决定。取而代之，量三件事就够了：它有多大、它被什么绑住、最近那些变更为何发生。

把这三件事量完，判断经常会翻转。一个安静的仓库如果是几百行、只有一个依赖、最近的变更全是运行时适配，那它不是死了，而是做完了。反过来，提交虽然活跃，却拖着几十个条目、文档比代码落后两个版本，那份活跃衡量的不是稳定性，而是剩余的工作量。

而这些条件在动手做的时候就已经定下了。要保持小，就得拒绝功能；要减少依赖，就得拒绝好用的库；要守住范围，就得拒绝使用者的请求；要维持文档，就得拒绝没有文档的合并。寿命由「没放进去什么」决定，而不是由「放进去了什么」决定。

同样的原理原封不动地适用于内部代码。只是在内部，负责拒绝的人往往并不明确，条件因此难以守住。所以才需要冻结声明。当你为某个模块写下「这个模块的职责到此为止，其他请求一律不接」的那一刻，它并不是脱离了管理，而是终于开始被管理。区分荒废与冻结的，正是这一句话。

## 1. 指标一 — 代码规模

```
python measure_size.py PATH1 PATH2 ...
```

`measure_size.py`

```python
import os, sys
SKIP = {".git", "__pycache__", "node_modules", ".venv", "build", "dist"}

def measure(root):
    files = code = blank = comment = size = 0
    targets = [root] if os.path.isfile(root) else []
    if not targets:
        for dirpath, dirnames, filenames in os.walk(root):
            dirnames[:] = [d for d in dirnames if d not in SKIP]
            targets += [os.path.join(dirpath, f) for f in filenames if f.endswith(".py")]
    for path in targets:
        files += 1
        size += os.path.getsize(path)
        for line in open(path, encoding="utf-8", errors="replace"):
            s = line.strip()
            if not s: blank += 1
            elif s.startswith("#"): comment += 1
            else: code += 1
    return files, code, comment, blank, size

for arg in sys.argv[1:]:
    print(os.path.basename(arg.rstrip("/\\")), measure(arg))
```

**要一并记录的内容**

- [ ] 最大单个文件的行数（瓶颈是最大值而非平均值）
- [ ] 计入测试与不计入测试的两个值要**分开记**
- [ ] 是否排除了生成代码（解析器产物之类）
- [ ] 注释行除以代码行得到的注释比例

## 2. 指标二 — 依赖面积

### 2-1. 有锁文件的生态（不安装也能测）

```
mkdir probe && cd probe
printf '{"name":"probe","version":"1.0.0","dependencies":{"PKG":"VERSION"}}' > package.json
npm install --package-lock-only --no-audit --no-fund
node -e "const l=require('./package-lock.json');
         console.log(Object.keys(l.packages).filter(Boolean).length)"
```

- `--package-lock-only` **只解析依赖树**，不下载压缩包，也不安装任何东西
- 得到的数字**包含它自己**。真正被拖进来的别人的仓库是这个数字减一

**参考实测值**

| 包 | 直接 | 树 |
|---|---|---|
| express@4.21.2 | 31 | 69 |
| axios@1.7.9 | 3 | 23 |
| chalk@5.4.1 | 0 | 1 |
| lodash@4.17.21 | 0 | 1 |
| typescript@5.7.3 | 0 | 1 |

### 2-2. 没有锁文件时 — 三跳导入闭包

```python
def closure_by_depth(root, max_depth=8):
    seen = {root}
    frontier = {root}
    levels = [set(seen)]
    for _ in range(max_depth):
        nxt = set()
        for name in frontier:
            for f in package_files(name):
                for dep in imports_of(f, name):
                    if dep not in seen and package_files(dep):
                        nxt.add(dep)
        if not nxt:
            break
        seen |= nxt
        frontier = nxt
        levels.append(set(seen))
    return levels
```

- **不要用完整闭包。**它会饱和，失去区分度（355 行的模块与 11,165 行的模块都收敛为 124 与 180）
- **在三跳处截断。**同样的对象会从 16 个拉开到 174 个，相差十倍以上
- 静态解析会把函数内部的惰性导入也计入，所以这个值是**上界**

## 3. 指标三 — 变更原因的分布

```
git log --since=2.years --format=%s | python classify_changes.py
```

`classify_changes.py` 的核心规则（顺序很重要）

```python
RULES = [
    ("defect",   r"(fix\w*|bug|crash\w*|leak\w*|regress\w*|cve|vulnerab\w*|"
                 r"overflow|incorrect\w*|correctly|properly|avoid\w*|prevent\w*|"
                 r"no longer|wrong\w*|fail\w*|hang\w*|deadlock)"),
    ("feature",  r"(add\w*|introduc\w*|implement\w*|new |now support\w*|"
                 r"support\w*|allow\w*|expose\w*|optimiz\w*|improv\w*)"),
    ("external", r"(update\w*|upgrade\w*|bump\w*|bundled|vendored|deprecat\w*|"
                 r"compat\w*|toolchain|compiler|installer|platform|portab\w*|"
                 r"windows|macos|android|freebsd|openssl|sqlite|zlib)"),
    ("doc",      r"(document\w*|docs?|docstring|comment\w*|typo|readme|man page)"),
    ("chore",    r"(refactor\w*|clean ?up|style|reformat|renam\w*|test\w*|"
                 r"remov\w*|drop\w*|release|version bump)"),
]
```

**怎么读**

- `feature` 占比 **25% 以上** → 成长中，禁止冻结
- `feature` 占比 **10~25%** → 混合，六个月后重测
- `feature` 占比 **低于 10%** → 仅维护，**冻结候选**

**必须遵守**

- [ ] `other` 分组已经**由人亲自读过**（实测中最多有 17.6% 落在这里）
- [ ] `defect` 排在 `external` 之前判定 → 明白**外部适配的比例是下界**
- [ ] 不是只看一个区间，而是按**同一项目随时间的变化**来比较
- [ ] 正则规则已按本组织的提交信息习惯调整

**参考实测值**（Python 3.13.3 随附的变更记录）

| 区间 | 功能 | 缺陷 | 外部 | 其他 | n |
|---|---|---|---|---|---|
| 3.13.0 alpha 1（开发） | 27.1% | 37.4% | 13.4% | 16.1% | 634 |
| 3.13.2 final（维护） | 8.8% | 63.7% | 6.6% | 17.6% | 91 |
| 3.13.3 final（维护） | 11.7% | 66.0% | 15.5% | 1.9% | 103 |

## 5. 冻结判断表

| 检查项 | 可冻结 | 不可冻结 | 判定 |
|---|---|---|---|
| 功能需求 | 最近四个季度没有新需求 | 每季度都有需求 | |
| 契约文档 | 规格就在仓库里 | 只在负责人脑子里 | |
| 自动检查 | 有能报告失败的测试在跑 | 依赖人工确认 | |
| 外部依赖 | 树一只手数得过来 | 几十个以上 | |
| 规模 | 非负责人一天读得完 | 光读就要好几天 | |
| 故障历史 | 最近一年没有生产故障 | 同一原因反复出现 | |
| 外部变动 | 外部规格已固定 | 外面每季度都变 | |
| 复核时点 | 已经钉了日期 | 没有确定时间点 | |

**判定规则**

- 八项中**七项以上「可冻结」** → 宣布冻结
- **四到六项** → 六个月后复检，其间补强文档与测试
- **三项及以下** → 不可冻结，按正常维护对待

**注意：**规模再小，只要**外面动得频繁就不可冻结**。判断标准不是规模，而是外部变动频率。

## 7. 交接检查清单

**交出方确认**

- [ ] 构建**一条命令**完成（不依赖负责人的电脑）
- [ ] 需要的运行时版本与外部工具**钉在配置文件里**
- [ ] 测试能跑，并且**坏了会说坏了**
- [ ] 部署流程有文档，照做就能部署
- [ ] 回滚流程有文档
- [ ] 留有**为什么选这个结构**的决策记录
- [ ] 每一处看起来奇怪的分支都在注释或议题里**写明了缘由**
- [ ] 文档与代码在同一个仓库
- [ ] 示例是**可执行的形式**

**权限 — 这里最容易漏**

- [ ] 仓库管理权限持有者**两人以上**
- [ ] 部署权限持有者两人以上
- [ ] 包仓库的所有权**不是个人账号**
- [ ] 签名密钥的保管位置与访问方式有文档
- [ ] 域名与证书续期的责任**以角色指定**
- [ ] 外部服务账号注册在共用邮箱地址上

**接手方确认**

- [ ] **只看文档**从头到尾构建并部署了一次
- [ ] 故意弄坏一处，确认**测试能抓到**
- [ ] 把最大的那个文件**从头读到尾**
- [ ] 翻了近一年的议题与故障，找出重复出现的模式
- [ ] 把不懂的地方**作为问题写回文档**（没有靠问人了事）

## 8. 重写判定表

| 情形 | 判定 |
|---|---|
| 需求前提变了，现有结构无法表达 | 重写 |
| 运行时、语言或核心库结束支持 | 重写或移植 |
| 没人读得懂，文档也无法还原 | 重写 |
| 安全缺陷从结构本身反复出现 | 重写 |
| 慢，但瓶颈已定位 | 局部替换 |
| 最近的变更以缺陷修复与外部适配为主 | 保留 |
| 不满集中在代码风格或技术潮流 | 保留 |
| 除了年代久远之外没有理由 | 保留 |

**动手重写前的必备步骤**

- [ ] 先还原了**既有代码为什么长成这样**
- [ ] 确认了看起来奇怪的分支是否为故障留下的疤痕
- [ ] 整理出新代码必须通过的**既有行为清单**
- [ ] 确定了数据与文件格式的兼容范围

## 9. 不要做的事

- ❌ **只看提交曲线下判断** — 它衡量的是剩余工作量，不是健康状况
- ❌ **只数直接声明的依赖** — 实测中一行声明解析出 69 个条目
- ❌ **用完整传递闭包做比较** — 它会饱和，什么都区分不出来
- ❌ **原样相信分类器结果** — 不读 `other` 分组会漏掉最多 17.6%
- ❌ **没有日期的冻结** — 那与荒废无法区分
- ❌ **用人名指定责任** — 扛不住人事调动
- ❌ **把安全补丁成本算成零的冻结** — 那不是冻结，是债务
- ❌ **把文档拆到 wiki** — 更新主体一旦分开必然滞后
- ❌ **测一次就下判定** — 指标只有在同一把尺子上反复测量才有意义
- ❌ **仅因为小就断定它好** — 那只是把成本挪到了使用者一侧
- ❌ **仅因为依赖多就断定它差** — 存在速度才是正确答案的阶段
