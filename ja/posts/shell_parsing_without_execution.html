シェルコマンドは実行するまで何をするか確定しない - 構造は読めて結果は読めない境界

パースは安全判定の一次フィルタにはなれても、セキュリティ境界にはなれない

2026-09-10 開発・インフラ

シェルコマンドの一行を目で読んで、それが何をするか言えるだろうか。ほとんどの人は言えると思っている。ところが echo *.json という十一文字を前にしてこのコマンドが引数をいくつ受け取るのかと問われると、答えが出てこない。その数はこの十一文字の中にないからだ。あるリポジトリの最上位でこの行は43語に展開され、その下のディレクトリでは1語に展開される。同じテキスト、違う引数ベクタである。

これがシェルという言語の性格を決めている。シェルのソースはそれ自体がプログラムというより、実行時にプログラムを作り出す指示文に近い。最終的に execve へ渡される引数配列は、テキストだけでなく、その瞬間のファイルシステム・環境変数・先行コマンドの出力・シェルオプションの状態が一緒に作る。テキストだけを見てその配列を確定する作業は原理的に不可能だ。

だからといって静的解析が無用だという結論にはならない。結果が読めないだけで構造は読める。パイプが何段なのか、リダイレクトがどのファイル記述子に掛かるのか、コマンド位置に何が置かれたのか、どこでサブシェルが生まれるのかはテキストだけで確定する。問題はこの二つを区別せずに使うときに起きる。とくにAI エージェントが実行するシェルコマンドを承認したり拒否したりするゲートが、その区別の上に立っている。

きっかけは unbash という TypeScript のパーサだ。bash のソースを実行せずに位置情報つきの構文木へ変換する。興味深いのはこのリポジトリが自分で引いている線である。コードを実行せず、シェル展開を行わず、サンドボックスを提供せず、どのコマンドが安全かを判定しない。この四行がこの記事全体の要約になる。

この記事の実行例はすべて読み取り専用である。出力は GNU bash 5.2.37(1)-release (x86_64-pc-msys) から出たものであり、ファイルを作ったり消したりする例は使っていない。以下のどの行も、読者がコピーしてそのまま走らせることを前提に書かれていない — 文法の性質を見せるための最小の例だ。破壊的なコマンドは例の中で中立的なコマンドに置き換えてある。

「実行せずに解析する」が正確に意味すること

この文は二通りに読める。ひとつは「走らせなくても何が起きるか分かる」であり、もうひとつは「走らせずにテキストの構造だけ把握する」である。シェルで可能なのは二つめだけだ。

差は些細に見えて結果は正反対になる。一つめの読みを前提にゲートを作ると、そのゲートは自分が検査していないものを検査したと報告する。二つめの読みを前提に作ると、ゲートは自分が何を知らないかを知っていて、知らないものに出会えば次の防衛線へ渡す。同じパーサを使っていて結果が分かれる地点がここだ。

構文木を得るというのは、テキストを文法要素へ分けるという意味である。この単語はコマンド名、あの単語は引数、この記号はパイプ、あの塊はサブシェル。各要素に元のソースでの開始位置と終了位置が付けば、エディタは正確な行と列に印を打てるし、入力が途中で切れてもそこまでの部分木と壊れた位置を返せる。これらはテキストについての事実であり、すべて真である。

ところがこれらの事実は実行についての事実ではない。コマンド位置に ls という二文字があるというのは真だ。その二文字が実行時に何になるかは別の問題であり、答えはテキストではなくそのシェルの別名表と関数表と PATH にある。パーサは前者の事実を渡し、人はしばしば後者の事実を期待する。この期待のずれは道具の欠陥として現れず、判定が正しかったのに事故が起きたという形で現れるので、原因が見えにくい。

パーサが自分で引いた線

unbash の README は、何をして何をしないのかを分けて書いてある。こうした境界の記述がある道具は珍しく、あるならそのまま引用する価値がある。

扱う文法として列挙されているのは次のとおりだ。コマンド・制御フロー・パイプライン・リダイレクト・代入、複合コマンド、パラメータ展開と単語展開、プロセス置換と入れ子置換、coproc、ヒアドキュメントとヒアストリング、C 形式の for、select、配列代入、拡張グロブ、case の貫通演算子(;&・;;&)、そして bash 5.3 のコマンド置換形式である。つまりbash 文法の大部分を覆う。

やらないこととして明示されているのは四つだ。コードを実行せず、シェル展開を行わず、サンドボックスを提供せず、コマンドが安全かを判定しない。さらに PowerShell と cmd.exe は対象外だと書いてあり、プロセス引数のパースに使う道具でもないと書いてある。復旧にも限界が明示されている — 深く入れ子になったパラメータ展開と算術展開では誤り復旧が制限される。

セキュリティ関連の文が特に正直だ。セキュリティに敏感な利用者は各スクリプトの単語断片(word parts)・入れ子スクリプト・エラー一覧を自分で検査しなければならないという要求を README が直接かけている。この文を裏返すとこうなる。パーサが木を返したという事実そのものは何も承認しない。木を受け取った側がその木を使って判定規則を立てなければならず、その規則の品質がゲートの品質である。

性能と大きさも書いてある。外部依存のない同期 API であり、最小化基準 80KB・gzip 基準 19KB、ISC ライセンスだ。スループットの数値や他のパーサとの倍率も README にあるが、それらはリポジトリが自分の環境で測った値なので、条件を外して持ち運ぶ値ではない。

シェルが静的解析に抵抗する五つの理由

ここがこの記事の心臓だ。シェルが静的解析を難しくするのは文法が複雑だからではない。文法が意図的に実行時の状態を引き込むよう設計されているからである。対話的に使う道具として、その場のディレクトリや環境を短い記法で呼び出せることが利点になるよう作られており、その利点がそのまま静的解析の障壁になっている。五つに分かれる。

① グロブはその瞬間のディレクトリが決める

パターンが何語に展開されるかはパターンの中にない。ファイルシステムにある。そして一致する名前がひとつもないときの挙動はシェルオプションの状態によって三つに分かれる。

# 同じテキスト、違うディレクトリ - 単語数が違う
$ echo *.json          # リポジトリ最上位
PHASE2_STAGES.json _h2_index.json ... package.json trend_topics.json   # 43語

$ echo *.json          # その下の posts ディレクトリ
index.json                                                             # 1語

# 一致がひとつもないとき - 既定はパターンをそのまま残す
$ echo zzz*.nosuch
zzz*.nosuch

$ ( shopt -s nullglob; echo "[" zzz*.nosuch "]" )
[ ]                                              # 単語が消える

$ ( shopt -s failglob; echo zzz*.nosuch )
bash: no match: zzz*.nosuch                      # コマンド自体が実行されない

三行とも同じパターンである。ところが結果は1語・0語・実行されずに分かれる。どちらになるかはそのシェルインスタンスがどのオプションを有効にしているかに依存し、その状態はテキストにない。

だから静的解析が言えるのはこの程度だ。この位置にパターンがある。この単語は引数の個数が可変である。個数の下限は0で、上限は定まらない。言えないのは個数と値のすべてである。グロブ文法そのものと正規表現の違いは グロブと正規表現は違う - アスタリスクが別の意味になる瞬間で別に扱っている。

② 変数展開とコマンド置換は実行しないと値が決まらない

$VAR の値は環境にあり、$(...) やバッククォートの値はその中のコマンドを実際に走らせないと出てこない。後者がとくに厄介なのは、値が決定的ですらないところにある。同じテキストを二度評価すると違う値が出ることが普通にある。

# コマンド置換 - 内側を走らせないと値が出ない
$ echo "$(echo one two)"
one two

# 同じテキスト、毎回違う値
$ echo $RANDOM; echo $RANDOM
11194
27279

# 展開結果は再パースされない - 演算子にはならない
$ v='echo a; echo b'; $v
a; echo b

$ v='echo a | tr a-z A-Z'; $v
a | tr a-z A-Z

後ろの二例が重要だ。変数の中に ; や | を入れても、それらは演算子にならずただの引数になる。この性質のおかげで静的解析の骨格はおおむね守られる。展開で構造が新しく生まれることはないという意味である。

静的解析が言えるのは置換があるという事実と、その中の入れ子スクリプトの構造だ。$(...) の内側もシェル文法なので、その中のコマンド名やパイプ構造は語彙的に読める。README が入れ子スクリプトを検査せよと要求する理由がこれである。言えないのは値、そしてその値が外側のコマンドの引数境界をどう変えるかだ。

③ 同じ名前が別のものを指す

コマンド位置に置かれた単語が何を実行するかは名前解決の規則が決める。別名が先、次に関数、次に組み込み、最後に PATH の走査だ。同じ名前がこの四層すべてに存在しうる。

# ひとつの名前に四つの候補が同時に存在する
$ type -a echo
echo is aliased to `echo A'
echo is a function
echo is a shell builtin
echo is /usr/bin/echo

# 関数が外部コマンドを隠す
$ printf() { builtin printf "FUNC:%s\n" "$*"; }; printf hello
FUNC:hello

# PATH を狭めるとさっきまで見つかっていたものが見つからない
$ type -p node
/c/Program Files/nodejs/node
$ PATH=/usr/bin; type -p node || echo "not found"
not found

# 別名にはタイミングまである - 同じ行で定義して使うと効かない
$ shopt -s expand_aliases; alias hi="echo ok"; hi
bash: hi: command not found          # 同じ行

$ shopt -s expand_aliases
$ alias hi="echo ok"
$ hi
ok                                    # 次の行

最後の例が静的解析の限界をもっとも鮮明に見せる。別名展開はシェルが行を読む時点で起きるのに、その時点の別名表はそのシェルの実行状態である。つまりパース段階ですでに実行状態が介入する。同じテキストを別のシェルインスタンスに入れれば、パース結果から違いうる。

静的解析が言えるのは「コマンド位置にこのテキストがある」までだ。そのテキストが実行時に何へ解決されるかは言えない。ゲートを作るときこの区別を守ると判定文が正確になる。「このコマンドは ls だ」ではなく「このコマンド位置の単語は ls だ」と書くべきである。

④ eval は文字列をふたたびコードにする

②で展開結果は再パースされないと述べた。eval はその規則の例外だ。引数として受け取った文字列をシェルのソースとして読み直す。

# 展開だけならコマンドはひとつ
$ v='echo a; echo b'; $v
a; echo b

# eval は同じ文字列を二つのコマンドにする
$ v='echo a; echo b'; eval "$v"
a
b

# 文字列は代入や算術展開まで抱えられる
$ s='a=1; echo $((a+1))'; echo "$s"
a=1; echo $((a+1))
$ eval "$s"
2

eval が現れた瞬間、構文木は実行時に新しく生まれる。静的解析が言えるのは「ここで新しいスクリプトが生まれる」までであり、そのスクリプトの中身は文字列の値に依存するので②の問題へ戻る。. と source も性質は同じだ。別のファイルの中身を現在のシェルへ持ち込むので、そのファイルが何を抱えているかがテキストの外にある。

⑤ 単語分割と引用符が引数境界を変える

展開された値がいくつの引数になるかは引用の有無と IFS 変数が決める。引用していない展開結果は分割され、引用した展開結果は分割されず、何を境界と見るかは実行時の変数ひとつが決める。

$ x='a b c'

$ set -- $x;   echo "argc=$#"      # 引用なし - 三つに割れる
argc=3
$ set -- "$x"; echo "argc=$#"      # 引用あり - ひとつのまま
argc=1

# 空の値は引用しないとまるごと消える
$ e=''
$ set -- a $e b;   echo "argc=$#"
argc=2
$ set -- a "$e" b; echo "argc=$#"
argc=3

# 境界を定めるのは実行時の変数だ
$ y='a:b:c'
$ ( IFS=:; for w in $y; do printf ' [%s]' "$w"; done; echo )
 [a] [b] [c]

二つめの例がゲート設計に直接かかる。引数ひとつがまるごと消えうる。テキストには三つの単語があるのに、実行されるのは二つの引数ベクタだ。位置を数えて判定する規則はここで狂う。

静的解析が言えるのは「この単語は引用されていないので分割されうる」という可能性の判定である。引用の有無そのものは語彙的に完全に読めるので、この判定は正確だ。個数は依然として読めない。どの引用符がどの展開を止めるかは シェルのクォート規則 - どの引用符が何を止めるのかに整理してある。

展開順序が定める管轄の境界

五つの枝はばらばらに見えて、ひとつの規定に束ねられている。GNU Bash マニュアルは展開の順序をこう定めている。ブレース展開、次にチルダ展開・パラメータと変数の展開・算術展開・コマンド置換(左から右へ)、次に単語分割、次にファイル名展開、最後に引用符の除去。

単語の個数を増やしうるのはブレース展開・単語分割・ファイル名展開の三つだけであり、他の展開は一単語を一単語に展開する。

この一行が静的解析の管轄の境界を正確に引いてくれる。単語数を変えうる三つの段階のうち二つが実行時の状態に依存する。単語分割は IFS と展開値に、ファイル名展開はディレクトリの中身とシェルオプションに依存する。だから引数ベクタが静的に確定しない。

ところが残るひとつ、ブレース展開は純粋に語彙的である。ファイルシステムも環境変数も見ない。これが唯一の例外であり、だからパーサが結果まで正確に言える唯一の展開だ。

# ブレース展開はファイルシステムを見ない
$ echo {a,b}.txt
a.txt b.txt

$ echo /nonexistent/{p,q}/r          # 存在しない経路でもそのまま展開される
/nonexistent/p/r /nonexistent/q/r

$ set -- {a,b,c}.txt; echo "argc=$#"  # 単語数が静的に確定する
argc=3

# 引用すると展開自体が起きない - これも語彙的に判定される
$ echo "{a,b}.txt"
{a,b}.txt

POSIX シェル仕様は展開順序を少し違うふうに書く。チルダ展開・パラメータ展開・コマンド置換・算術展開が先で、次にフィールド分割、次に経路名展開(set -f が掛かっていなければ)、引用符の除去は行われるならつねに最後である。一覧にブレース展開がない。

段階bash マニュアルの順序POSIX 仕様の順序静的に結果が確定するか
ブレース展開1番 - もっとも先順序一覧にない確定
チルダ展開2番の束1番の束ホームディレクトリの値に依存
パラメータ・変数展開2番の束1番の束未確定
算術展開2番の束1番の束変数を参照すれば未確定
コマンド置換2番の束・左から右へ1番の束未確定
単語分割・フィールド分割3番2番未確定 - IFS に依存
ファイル名・経路名展開4番3番 - set -f なら省略未確定 - ディレクトリに依存
引用符の除去5番 - 最後つねに最後確定

表の最後の列がこの記事の半分だ。確定する二行は文法が自分で閉じている段階であり、残りはすべて外の状態を引き込む。パーサが見るのはこの梯子の一番上で、実行が見るのは一番下である。そのあいだで単語が増え、減り、消える。

それでも実行前に確定するもの

ここまでができない側だったなら、ここからができる側だ。そしてできる側の一覧は思ったより長い。

# パイプライン構造は語彙的に確定する
$ echo hi | tr a-z A-Z
HI

# リダイレクトはコマンド名の前にも来る - 最初の単語がコマンドという規則は誤り
$ 2>/dev/null echo redir-first-ok
redir-first-ok

# 前に付いたものが代入かコマンドかも語彙的に分かれる
$ A=1 B=2 env | grep -E '^(A|B)=' | sort
A=1
B=2

# サブシェル境界 - 丸括弧は新しいシェル、波括弧は同じシェル
$ x=1; ( x=2; echo "inner=$x" ); echo "outer=$x"
inner=2
outer=1
$ x=1; { x=2; echo "brace=$x"; }; echo "after=$x"
brace=2
after=2

リダイレクトがコマンド名の前に来られるという事実は、実務上大きな差を生む。「行の最初の単語がコマンド名だ」という規則で作った検査器は、この形ですぐに狂う。構造パーサはこれをリダイレクトひとつとコマンドひとつに正確に分ける。逆に代入だけあってコマンドがない文もあり、そのとき「コマンド名」という枠自体が空だということも静的に確定する。

サブシェル境界が確定するということは、どの代入が外へ漏れてどの代入が閉じ込められるかを実行せずに言えるという意味だ。この境界が生む実務事故は パイプの中のwhileで変数が消える理由 - サブシェル 2026で別に扱っている。

# フロー演算子 - 候補は確定し、実行の可否は終了コードが決める
$ true && echo ran-A; false && echo ran-B; echo always-C
ran-A
always-C

# ヒアドキュメント本文の展開可否は区切り子の引用で語彙的に判定される
$ v=VALUE; cat <<EOF
plain: $v
EOF
plain: VALUE

$ v=VALUE; cat <<"EOF"
quoted: $v
EOF
quoted: $v

フロー演算子で確定するのは実行されうるコマンドの上限集合だ。どれが実際に走るかは終了コードに依存するので未確定だが、上限が確定するだけでも許可リストの判定には十分である。上限に属するすべてのコマンドが許可リストの中にあれば、どの分岐を通っても安全条件は保たれる。終了コードが実際に何を捕まえて何を逃すかは シェルの終了コードと set -e - 何を捕まえ何を見逃すかに整理してある。

ヒアドキュメント側も綺麗だ。区切り子に引用符が付いているかどうかだけ見れば、本文の中で展開が起きるかが定まる。区切り子が引用されていれば本文は純粋なテキストなので、その中にコマンドらしき文字列があってもコマンドではない。引用されていなければ本文の中の置換が生きているので、入れ子スクリプトとして数えなければならない。この判定は語彙的で正確だ。ヒアドキュメント自体の使い方は ヒアドキュメント実践 - 変数展開を切る・入れる、インデントの罠にある。

ここまでを一文に縮めるとこうなる。構造は読めて結果は読めない。

構成要素ごとの判定表

文字列マッチで濾すと何が漏れるか

「危険なコマンドを遮断する」を文字列マッチで実装すると偽の安心が作られる。理由は三層だ。

  • 表記の集合が開いている。シェルは同じ単語へ到達する方法を複数用意している。この記事はその方法を列挙しない — 要点は一覧の長さではなく一覧が閉じないという性質だからだ。列挙で塞ぐ規則は、列挙されていないひとつがあればそのひとつで崩れる。
  • 検査対象が展開前のテキストだ。実際に実行される引数ベクタは §4 の梯子をすべて下りたあとで作られる。文字列マッチは梯子の一番上でしか見ない。上で無害に見える単語が下で何になるかは検査されていない。
  • 境界がない。正規表現はコマンド位置と引数位置と文字列の内部とコメントの内部を区別しない。だから偽の通過と偽の遮断が同時に起きる。ヒアドキュメント本文の中の単語をコマンドと誤認して正常なスクリプトを塞ぐ側も、リダイレクトが前に付いて最初の単語がコマンドではない形を見逃す側も、同じ原因から出てくる。

三つめがとくに困るのは失敗が双方向だからだ。一方向にだけ失敗する検査器は補正できる。通過が緩すぎれば規則を締め、遮断が厳しすぎれば例外を掘る。双方向に失敗する検査器は、締めるほど正常な作業が塞がれ、緩めるほど判定が緩くなる。二つのダイヤルが同じ軸に縛られている。

そして実務では偽の遮断が先に問題になる。正常なコマンドが繰り返し塞がれると、人はゲートを迂回する方法を探すか規則をまるごと緩くする。偽の遮断が積もれば結局は偽の安心へ帰着する。これが文字列マッチのゲートが時間とともに悪くなる経路だ。規則が増えるほど強くなっているように見えて、実際には運用する側が規則を信じなくなっていくという逆向きの変化が同時に進む。

構造ベースの判定が多く捕まえるものと捕まえられないもの

構文木を受け取ると何が変わるかから整理する。

  • 枠を区別する。コマンド位置と引数位置と文字列の内部が別のノードだ。文字列の中の単語をコマンドとして数えないので、偽の遮断が大きく減る。
  • パイプのすべての段を数える。前段だけ、あるいは後段だけを見て通してしまう誤りが構造的に不可能になる。
  • 入れ子スクリプトを別集合として数える。コマンド置換・プロセス置換・引用されていないヒアドキュメント本文の中のコマンドがそれぞれ自分のノードを持つ。
  • リダイレクトの位置に揺れない。コマンドの前に来ようが後ろに来ようが同じ構造として読む。
  • パース失敗を信号として使える。構文が成立しない入力は拒否するという規則が成り立つ。これは文字列マッチにない軸だ。
  • 位置情報で判定根拠を残す。どの行どの列のどのノードのせいで拒否したかがログに残れば、規則を直せる。

ところが依然として捕まえられないものがあり、その一覧は §3 とぴたりと重なる。

  • 展開結果。グロブが何に展開されるか、置換がどんな値を返すかは木にない。
  • 名前の解決。コマンド位置の単語が別名か関数か実行ファイルかはそのシェルの状態だ。
  • eval・source のあとに生まれるコード。木は「ここで新しい木が生まれる」までしか言わない。
  • 引数の意味論。引数文字列の中に入った別の言語はシェル文法の外だ。
  • 副作用の大きさ。同じコマンドがどのディレクトリで走るかによって影響範囲が完全に変わるのに、作業ディレクトリは実行状態である。
検査方式見るもの偽の通過偽の遮断展開結果に作用するか
文字列・正規表現マッチ展開前のテキスト、枠の区別なし多い - 表記の集合が開いている多い - 文字列やコメントの中を数えるいいえ
構造ベースの判定構文木、枠の区別あり減るが残る - 名前解決と展開大きく減るいいえ

隔離・許可リスト・遮断リストの順序

三つの防御の強さは、何に作用するかで決まる。

  • 隔離は結果に作用する。コマンドが何に展開されようと、ファイルシステムの到達範囲・ネットワークの到達範囲・権限が外から制限されていれば被害の上限が定まる。この上限はテキストを一文字も読まずに成り立つ。
  • 許可リストは余集合に作用する。列挙したものだけ通すので、列挙されていないすべてが塞がれる。表記の自由度が攻撃面ではなく拒否の理由へ裏返る。知らない形に出会えば拒否が既定値だ。
  • 遮断リストは列挙したものにだけ作用する。知られたものだけを塞ぐ。新しい表記ひとつが一覧の外にあれば、そのひとつで抜かれる。

だから順序は隔離 → 許可リスト → 遮断リストである。遮断リストが無用だという意味ではない。明白な誤りを早く捕まえて人へ知らせる役割はある。ただしそれが最初の防衛線になった瞬間に偽の安心になる。

許可リストを構造パースで実装すると形はこうなる。これは「危険なものを濾す」ではなく「受け入れる文法の部分集合を定義する」という作業だ。

  • パースに失敗したか、エラー一覧が空でなければ拒否する。
  • 許可したノード型の外にある構成要素があれば拒否する。eval・source・プロセス置換・coproc・入れ子のコマンド置換は「知らないもの」の側に置くほうが安全だ。
  • コマンド位置の単語が許可リストの外なら拒否する。パイプのすべての段と入れ子スクリプトのすべてのコマンドに同じ規則を適用する。
  • 引用されていない展開が引数にあれば拒否するか、隔離の強度を一段上げたうえでのみ通す。
  • リダイレクト先が展開を含めば同じ扱いをする。
  • 通過したコマンドも隔離の中で走る。ゲートを通過したことが隔離を免除しない。

この一覧ですべての判定が「拒否」の側へ傾いているという点が重要だ。静的解析の不確実性はすべて拒否の側へ載せなければならない。確定しないものを通過の側へ載せれば、その不確実性がそのまま危険になる。

価値を出す場所と出せない場所

シェルパーサが価値を出す場所ははっきりあり、それらには共通点がある。判定の失敗がそのまま事故にならない場所だ。

用途必要なもの失敗したとき適するか

CI でのスクリプト形式検査禁止形式の構造的検出ビルドが一度通る適する - 別のゲートが後ろにある

四行目のログ正規化はあまり語られないが、静的解析がもっとも綺麗に嵌まる場所だ。実行されたコマンド文字列をそのまま集計すると、引数ごとに値が違ってカーディナリティが爆発する。構造でパースしてコマンド名とオプションの形だけ残し、引数の値を場所取りに置き換えると、同じ形のコマンドがひとつの項目にまとまる。ここでは展開結果を知らないことがむしろ利点になる。知りたいのが値ではなく形だからだ。同じ理由で、引数に混ざった一時的な経路や識別子を取り除いても情報が失われず、むしろ傾向が見えやすくなる。

逆に最後の二行はどんなパーサを使っても変わらない。パーサの完成度の問題ではなく、問い自体がテキストで答えられない問いだからである。実行前の検証が何を保証して何を保証しないかの一般的な形は まともな --dry-run の作り方 - まねごとではなく検証をと同じ構造を持つ。

方言 - どのシェルをパースしているのか

最後の軸がひとつ残っている。パーサがどの方言を対象にしているかを確かめないと判定がずれる。

POSIX シェル仕様と bash は相当部分が重なるが同じではない。配列は POSIX 仕様になく、プロセス置換もない。[[ と ]] は現行版が実装が予約語として認識しうる語の一覧に載せただけで、意味を規定していない。一方でドル記号の付いた単引用符の形は現行版に専用の節がある。set -f で経路名展開を切る規定のように両方が同じところもあれば、ブレース展開のように片方にしかないものもある。

ここに名前と実体がずれる問題が加わる。この記事の出力を出した環境では sh は別の実装ではなく bash である。sh -c 'echo $BASH_VERSION' が 5.2.37(1)-release を返す。つまりこの環境で sh で試した結果は POSIX を試した結果ではない。§3 の③が述べた「同じ名前が別のものを指す」がシェル自体にもそのまま当てはまる。

このずれはゲートでどう現れるか。#!/bin/sh で始まるスクリプトを bash 文法のパーサで通すと、実際の実行環境では構文エラーになるものを通してしまいうる。逆方向もある。bash 拡張を使ったスクリプトを POSIX 基準だけで検査するとパース失敗になり、パース失敗を拒否の信号に使うゲートでは正常なスクリプトが塞がれる。

プロセス置換なしあり入れ子スクリプトを見逃せば偽の通過
[[ 条件式予約語として認識しうるとだけ規定意味まで規定挙動が仕様に依拠しない
ブレース展開展開順序の一覧にないもっとも先に実行単語数の予測が方言で分かれる

最後の行は unbash が自分で明かしている範囲でもある。Windows 系のシェルは対象外だ。ひとつのゲートが複数のプラットフォームのコマンドを受けるなら、方言ごとに別のパーサと別の許可リストが必要になる。シェルが違えば同じ文字列の引用規則から違うという点は ファイル名がシェルごとに違って見える理由 - Git Bash と PowerShell のずれた規則で名前の扱いを例に扱っている。

コマンドゲートへの配線順序

ここまでの内容を実際の配線へ移すと、順序はこうなる。

  1. 隔離を先に立てる。パーサを付ける前に、コマンドが何をしようと被害範囲が定まっている状態を作る。この段階がなければ後ろのすべての段階が最善努力にすぎない。
  2. 方言を固定する。どのシェルで実行するのかと、どの文法で検査するのかを同じに合わせる。二つが違えば判定と実行が別の言語を見ることになる。
  3. パース失敗を拒否として扱う。エラー一覧が空でなければ通さない。
  4. 文法の部分集合へ狭める。許可したノード型の外は拒否する。新しい文法が必要になれば規則を明示的に広げる。
  5. コマンド名の許可リストを適用する。パイプのすべての段と入れ子スクリプトのすべてのコマンドへ漏れなく適用する。
  6. 展開が残っていれば格下げする。引用されていない展開やグロブがあれば拒否するか、より狭い隔離へ送る。
  7. 判定根拠を残す。どのノードのどの位置のせいで拒否したかを記録する。根拠のない拒否は結局、規則をまるごと切らせることになる。

この順序を守れば、パーサの役割は自然と収まるべきところへ収まる。パーサはゲートの門番ではなく受付である。形式が合っているか見て、知らないものは差し戻し、通過したものも内側の本当の境界へ渡す。

そしてこの記事の最初の一文へ戻るとこう整理される。シェルコマンドの一行を読んでそれが何をするか言う作業は不可能だ。しかしそれがどんな形なのかを言う作業は可能であり、形が定まった集合の中にあるかを判定する作業も可能だ。ゲートが答えるべき問いを前者から後者へ変えること — 静的解析が実際にしているのはそれである。

確認できなかったこと

  • GNU Bash マニュアルのファイル名展開の項 — 該当ページが二度とも HTTP 429 応答で開かなかった。一致する名前がないときパターンがそのまま残るという挙動と nullglob・failglob の効果は上の実行出力だけで裏づけられており、マニュアルの条項と照合できていない。展開順序の項はマニュアルからそのまま引用した。
  • POSIX 仕様で経路名展開が一致に失敗したときの規定 — 展開順序の節にはこの場合の記述がなく、別の節までは確認の範囲を広げられなかった。
  • unbash の AST ノード型の全一覧と各ノードのフィールド — README が示す例の範囲の外は確定できていない。したがって上の「許可したノード型」の設計は一般的な形であり、このパーサの実際の型名に合わせたものではない。
  • README のスループット数値と他パーサとの倍率 — リポジトリ自身の測定値であり、測定条件と入力集合を再現できていない。条件なしに持ち運べない値として置いておく。
  • unbash が抱える bash 文法のバージョン範囲 — README は 5.3 のコマンド置換形式に触れているが、バージョン別の対応表はなかった。
  • POSIX 仕様の版の違い — 上の記述は現行版を基準にしたものであり、ドル単引用符や予約語一覧が以前の版でどうだったかはここの範囲の外だ。
  • 他のシェル方言のパーサ — zsh・mksh・dash を対象にするパーサが同じ境界をどう扱うかは扱っていない。
