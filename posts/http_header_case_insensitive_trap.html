헤더는 분명히 보냈는데 서버에서 안 보인다 - 이름은 대소문자를 안 가리는데 코드는 가린다

이름은 대소문자 무시, 자료구조는 대소문자 구분 - 그 어긋남에서 사는 버그를 실행으로 잡는다

2026-07-31 개발/인프라

서론: 보낸 것은 확실한데 받은 쪽에 없다

연동 중인 상대 팀에서 연락이 온다. 「요청마다 X-Request-Id를 넣어 보내고 있습니다. 개발자 도구에서 확인도 했습니다.」 그런데 우리 서버 로그에는 그 값이 없다. 코드를 열어 보면 헤더를 읽는 줄은 분명히 있다. 예외도 안 난다. 상태 코드도 200이다. 그냥 값이 없을 뿐이다.

이 상황이 특히 지독한 이유는 아무것도 실패하지 않기 때문이다. 오타가 났으면 에러가 났을 것이고, 네트워크가 끊겼으면 타임아웃이 났을 것이다. 그런데 객체에 없는 키를 읽는 것은 오류가 아니다. 빈 값이 조용히 돌아오고, 그 빈 값이 로그로 흘러가고, 로그에는 아무 줄도 남지 않는다. 며칠 뒤 「추적 아이디가 왜 안 찍히죠」라는 질문이 다시 올라온다.

원인은 규격과 코드 사이의 어긋남 하나다. 이 문장이 이 글의 전부다.

  • HTTP 헤더의 이름은 대소문자를 구분하지 않는다. X-Request-Id와 x-request-id와 X-REQUEST-ID는 같은 헤더다. 규격이 그렇게 정하고 있다
  • 그런데 코드가 그것을 담는 자료구조는 대소문자를 구분한다. 객체의 키, 사전의 키, 집합의 원소, 문자열 비교 연산자 — 전부 X와 x를 다른 것으로 취급한다
  • 그래서 같아야 할 두 이름이 코드 안에서 다른 것이 된다. 이 어긋난 자리가 버그가 사는 곳이다

흔히 나오는 처방은 「그냥 소문자로 쓰세요」다. 틀린 말은 아니지만 이것은 내가 쓰는 코드에서만 성립하는 규칙이다. 상대가 어떤 철자로 보낼지는 내가 정할 수 없고, 규격상 상대는 어떤 철자를 써도 잘못이 아니다. 그래서 이 글은 「소문자로 쓰세요」에서 멈추지 않는다. 이름이 어느 지점에서 누구에 의해 바뀌는지를 실행으로 하나씩 짚고, 값(value)은 왜 다르게 다뤄야 하는지까지 갈라 놓는다.

실행 환경. 아래 모든 출력은 Windows 10 Pro (10.0.19045)에서 실제로 실행한 결과다. 런타임은 Node.js v22.16.0 (win32)과 Python 3.13.3 (win32)이고, 둘 다 표준 라이브러리만 썼다. 외부 패키지는 설치하지 않았다. 서버는 모두 127.0.0.1의 고번호 포트(18080부터)에 띄웠고 실행이 끝나면 닫았다. 스크립트는 셸 인자나 히어독이 아니라 전부 파일로 저장해 실행했다.

측정 못 한 것. 이 환경에는 상용 리버스 프록시나 게이트웨이 제품이 설치돼 있지 않다. 그래서 6절의 중계는 직접 만든 최소 프록시이고, 특정 제품의 동작을 일반화한 것이 아니다. 또 HTTP/2의 이름 규칙에 대한 규격 원문은 열지 못했다. 그래서 5절은 실측 결과만으로 서술하고 조문 인용은 하지 않는다. HTTP/3는 이 환경에 구현이 없어 전혀 측정하지 못했다.

이 글이 다루지 않는 것. 어떤 보안 헤더를 어떤 값으로 켜야 하는지는 웹 보안 기초에서 다뤘다. 리버스 프록시 자체의 설정은 리버스 프록시 구성에 있다. 여기서는 헤더 이름이라는 문자열이 계층을 지나며 어떻게 변형되는가만 본다.

1. 재현 - 보낸 이름과 저장된 키가 다르다

먼저 문제를 눈으로 본다. 바이트를 정확히 통제하려고 클라이언트는 라이브러리를 쓰지 않고 소켓에 직접 요청 줄을 써 넣었다. 서버는 표준 라이브러리의 기본 HTTP 서버다.

node v22.16.0 / win32
server listening on 127.0.0.1:18080

--- 1-0. exact bytes the client sent ---
"GET /order HTTP/1.1\r\nHost: 127.0.0.1:18080\r\nX-Request-Id: req-4821\r\nContent-Type: application/json\r\nACCEPT: */*\r\nConnection: close\r\n\r\n"

--- 1-1. what the server code tried ---
req.headers['X-Request-Id'] : undefined
req.headers['x-request-id'] : req-4821
req.headers['X-REQUEST-ID'] : undefined

--- 1-2. the keys actually stored in req.headers ---
  key=[host]  value=[127.0.0.1:18080]
  key=[x-request-id]  value=[req-4821]
  key=[content-type]  value=[application/json]
  key=[accept]  value=[*/*]
  key=[connection]  value=[close]

세 줄이 전부를 말한다. 클라이언트는 X-Request-Id라고 적어 보냈고, 값은 서버에 무사히 도착했다. 그런데 X-Request-Id로 찾으면 없다고 나오고, x-request-id로 찾아야 나온다. 저장된 키 목록을 보면 이유가 분명하다. 모든 이름이 소문자로 바뀌어 들어 있다.

세 번째 줄도 눈여겨볼 만하다. 전부 대문자로 찾아도 없다. 즉 「대소문자를 어떻게든 맞추면 된다」가 아니라 「정확히 소문자여야 한다」는 것이다. 이 사전에서 유효한 철자는 딱 하나다.

클라이언트가 보낸 ACCEPT도 마찬가지로 accept가 되어 있다. 이 정규화는 특정 헤더에만 적용되는 것이 아니라 전부에 걸린다.

2. 런타임이 이름을 바꾼다 - 원본 철자는 어디로 갔나

그렇다면 원래 철자는 완전히 사라진 걸까. 같은 요청에서 조금 더 파 보면 흥미로운 것이 나온다.

--- 1-3. req.rawHeaders keeps the bytes as they arrived ---
  raw[0]=[Host]  raw[1]=[127.0.0.1:18080]
  raw[2]=[X-Request-Id]  raw[3]=[req-4821]
  raw[4]=[Content-Type]  raw[5]=[application/json]
  raw[6]=[ACCEPT]  raw[7]=[*/*]
  raw[8]=[Connection]  raw[9]=[close]

--- 1-4. lookup by property vs by normalized key ---
  direct  req.headers[X-Request-Id]            : undefined
  normalized req.headers[x-request-id] : req-4821
  Object.hasOwn(req.headers, X-Request-Id)  : false
  Object.hasOwn(req.headers, x-request-id)  : true

정규화된 사전 옆에 도착한 순서 그대로의 이름과 값을 늘어놓은 배열이 따로 있다. 여기에는 X-Request-Id도 ACCEPT도 보낸 철자 그대로 남아 있다. 짝수 자리가 이름, 홀수 자리가 값이다.

이 사실은 두 가지를 알려준다. 첫째, 런타임은 정보를 버린 것이 아니라 한쪽만 정규화한 것이다. 편의를 위해 소문자 사전을 만들어 주면서 원본도 남겨 뒀다. 둘째, 그래서 「상대가 어떤 철자로 보냈는지」를 조사하는 것이 가능하다. 연동 문제를 디버깅할 때 이 배열을 그대로 찍는 것이 가장 빠른 확인 방법이다.

다만 여기에 큰 단서가 붙는다. 이 원본 배열은 직접 연결에서만 신뢰할 수 있다. 6절에서 보듯 중계가 하나만 끼어도 이 배열의 내용이 통째로 달라진다.

2.1 값이 있는지 확인하는 방법도 같이 틀린다

  • 존재 여부 검사도 같은 함정에 빠진다. 소유 속성 검사를 X-Request-Id로 걸면 거짓, x-request-id로 걸면 참이었다
  • 그래서 「헤더가 있으면 A, 없으면 B」 식의 분기가 항상 B로만 흐른다. 값이 왔는데도 안 왔다고 판단한다
  • 이 분기가 인증이나 권한에 걸려 있으면 기능이 통째로 죽는다. 반대로 「없으면 통과」 형태라면 검사가 통째로 무력화된다
  • 테스트 코드가 같은 철자를 쓰면 테스트도 같이 틀린다. 테스트는 통과하는데 실환경에서만 안 되는 전형적인 형태다
  • 가장 나쁜 조합은 테스트 클라이언트가 소문자로 보내고 실제 클라이언트가 대문자로 보내는 경우다. 이때는 방향이 반대여서 원인 추정이 더 오래 걸린다

3. 보내는 쪽은 유지된다 - wire 위의 이름

받는 쪽이 정규화한다면 보내는 쪽은 어떨까. 응답 헤더를 일부러 대문자와 소문자로 섞어 넣고, 클라이언트 소켓에 실제로 도착한 바이트를 그대로 찍었다.

--- 1-5. res.getHeader is case-insensitive (Node normalizes the lookup) ---
  res.getHeader('X-Trace-Id')  : trace-9f2c
  res.getHeader('x-trace-id')  : trace-9f2c
  res.getHeader('X-TRACE-ID')  : trace-9f2c
  res.getHeaderNames()         : ["x-trace-id","x-lower-name","content-type"]

--- 1-6. exact bytes that came back (wire) ---
  |HTTP/1.1 200 OK
  |X-Trace-Id: trace-9f2c
  |x-lower-name: set-in-lowercase
  |Content-Type: text/plain
  |Date: Thu, 30 Jul 2026 20:22:49 GMT
  |Connection: close
  |Content-Length: 3

여기서 같은 런타임이 두 가지 다른 정책을 쓴다는 것이 드러난다.

  • 응답 헤더의 조회는 대소문자를 무시한다. 세 가지 철자 전부 같은 값을 돌려줬다. 요청 헤더는 그렇지 않았는데 응답 헤더는 그렇다
  • 이름 목록은 소문자로 돌아온다. 내부 저장이 소문자 키라는 뜻이다
  • 그런데 실제로 나간 바이트는 내가 적은 철자 그대로다. X-Trace-Id는 대문자로, x-lower-name은 소문자로 나갔다
  • 정리하면 내부 색인은 소문자, 출력 표기는 원본이다. 두 층이 따로 관리된다

같은 코드에서 조회 하나는 대소문자를 가리고 다른 하나는 안 가린다는 사실이, 이 문제가 왜 기억으로 해결되지 않는지 설명한다. 규칙이 API마다 다르다.

3.1 클라이언트 세 종류가 wire에 쓴 이름

보내는 쪽을 더 확인했다. 아무것도 해석하지 않고 바이트만 기록하는 TCP 수신기를 띄우고, 세 가지 클라이언트로 같은 헤더 세 개를 보냈다.

node v22.16.0 / win32
raw TCP sink on 127.0.0.1:18087 (records bytes, never parses them)

--- 7-1. A. node http.request ---
  request line   : GET /a HTTP/1.1
  names on wire  : ["X-Request-Id","X-API-Key","Accept-Language","Host","Connection"]

--- 7-2. B. global fetch (undici) ---
  request line   : GET /b HTTP/1.1
  names on wire  : ["host","connection","X-Request-Id","X-API-Key","Accept-Language","accept","sec-fetch-mode","user-agent","accept-encoding"]

--- 7-3. C. hand-written bytes ---
  request line   : GET /c HTTP/1.1
  names on wire  : ["Host","X-Request-Id","X-API-Key","Accept-Language","Connection"]

--- 7-4. the same three names, side by side ---
  client                    x-request-id      x-api-key         accept-language
  A. node http.request      X-Request-Id      X-API-Key         Accept-Language
  B. global fetch (undici)  X-Request-Id      X-API-Key         Accept-Language
  C. hand-written bytes     X-Request-Id      X-API-Key         Accept-Language

결과가 예상과 조금 달랐다. 세 클라이언트 모두 내가 적은 철자를 그대로 wire에 실었다. 표준 준수 규격 객체를 쓰는 두 번째 클라이언트조차 사용자가 지정한 헤더의 철자는 건드리지 않았다.

대신 두 번째 클라이언트의 목록에서 다른 것이 보인다. 라이브러리가 스스로 붙인 헤더는 전부 소문자다. 사용자가 준 것은 원본, 자기가 만든 것은 소문자다. 그래서 한 메시지 안에 두 가지 표기가 섞여 나간다.

  • 이 혼재는 규격상 아무 문제가 없다. 받는 쪽이 이름을 대소문자 무시로 다루면 되기 때문이다
  • 하지만 「우리 클라이언트는 소문자로 보내니까 서버도 소문자만 보면 된다」는 가정은 여기서 깨진다. 사용자가 지정한 헤더는 소문자가 아니었다
  • 즉 wire의 철자를 근거로 어떤 판단도 하면 안 된다. 그것은 계약이 아니라 우연이다
  • HTTP/1.1에서는 보내는 쪽 철자가 그대로 흐른다는 점만 기억하면 된다. 문제는 그 다음 계층이다

4. 프레임워크마다 자료구조가 다르다

여기서 언어를 바꿔 본다. 같은 요청을 Python 표준 라이브러리 HTTP 서버로 받았다. 전혀 다른 결과가 나온다.

python 3.13.3 / win32 / Windows 10
--- 2-1. self.headers type ---
  type      : http.client.HTTPMessage

--- 2-2. case-insensitive lookup on the SAME object ---
  headers[X-Request-Id]   -> 'req-4821'
  headers[x-request-id]   -> 'req-4821'
  headers[X-REQUEST-ID]   -> 'req-4821'
  headers[x-ReQuEsT-iD]   -> 'req-4821'

--- 2-3. but the stored names keep the original bytes ---
  key=[Host]  value=[127.0.0.1:18081]
  key=[X-Request-Id]  value=[req-4821]
  key=[ACCEPT]  value=[*/*]
  key=[X-Tag]  value=[alpha]
  key=[x-tag]  value=[beta]
  key=[Connection]  value=[close]

--- 2-4. keys() is NOT normalized, so naive set logic still misses ---
  list(headers.keys())        : ['Host', 'X-Request-Id', 'ACCEPT', 'X-Tag', 'x-tag', 'Connection']
  'x-request-id' in keys      : False
  'X-Request-Id' in keys      : True
  headers.get(x-request-id)   : 'req-4821'
  '__contains__' on the object: True True

--- 2-5. duplicate names collapse differently ---
  get_all(X-Tag)              : ['alpha', 'beta']
  get(X-Tag)   [first only]   : 'alpha'

정반대의 설계다. Python 쪽은 헤더를 평범한 사전이 아니라 메일 메시지 객체로 담는다. 그리고 그 객체는 조회할 때 이름을 대소문자 무시로 비교한다. 네 가지 철자가 전부 값을 돌려줬다. 심지어 x-ReQuEsT-iD처럼 섞어 써도 된다.

동시에 저장된 이름은 원본 그대로다. Node가 소문자 사전과 원본 배열을 따로 둔 것을, Python은 객체 하나로 합쳐서 해결했다. 이 설계가 더 안전해 보이는 것이 사실이다.

4.1 그런데 여기에도 같은 함정이 있다

안전한 것은 그 객체를 통해 조회할 때뿐이다. 이름 목록을 꺼내는 순간 다시 평범한 문자열 목록이 된다.

  • 이름 목록을 뽑아 x-request-id가 들어 있는지 보면 거짓이다. 목록의 원소는 원본 철자이기 때문이다
  • 같은 이름을 그대로 객체에 물어보면 참이다. 즉 같은 데이터에서 답이 두 개 나온다
  • 그래서 「목록을 순회하면서 걸러내는」 코드는 Python에서도 똑같이 빗나간다. 언어를 바꾼다고 해결되는 문제가 아니다
  • 중복 이름 처리도 다르다. X-Tag와 x-tag를 각각 보냈더니 둘 다 별개 항목으로 보관되면서도, 전체를 꺼내는 호출은 대소문자를 무시하고 두 값을 모두 돌려줬다
  • 반면 하나만 꺼내는 호출은 먼저 온 것 하나만 돌려준다. 나중 값이 조용히 사라진다

Node는 같은 상황에서 다르게 반응한다. 9절에서 보듯 두 값을 쉼표로 이어 붙인 하나의 문자열로 만들어 준다. 규격은 같은 이름의 여러 줄을 쉼표로 합치는 것을 허용하고 있고, 이 런타임은 그 선택을 한 것이다. 같은 입력에 세 가지 결과가 나온다는 뜻이다.

표를 한 줄로 요약하면 이렇다. 「조회」를 제공하는 쪽은 대체로 안전하고, 「목록」을 노출하는 쪽은 대체로 위험하다. 그리고 어느 쪽이든 한 언어의 규칙을 다른 언어에 옮겨 적용하면 틀린다.

5. HTTP/2에서는 대문자가 프로토콜 오류다

지금까지는 HTTP/1.1이었다. 전송 방식을 바꾸면 이야기가 달라진다. 먼저 보통의 클라이언트 라이브러리로 대문자 이름을 보냈다.

node v22.16.0 / win32  (http2 module, cleartext h2c)

--- 3-1. client sends the name written as X-Request-Id ---
  request({X-Request-Id}) : accepted by the API (no throw)

--- 3-2. what the HTTP/2 server received ---
  key=[:path]  value=[/order]
  key=[:method]  value=[GET]
  key=[:authority]  value=[127.0.0.1:18082]
  key=[:scheme]  value=[http]
  key=[x-request-id]  value=[req-4821]
  stream.session.alpnProtocol : h2c

--- 3-4. response header names the HTTP/2 client sees ---
  key=[:status]  value=[200]
  key=[x-trace-id]  value=[trace-h2]
  key=[content-type]  value=[text/plain]

세 가지가 눈에 띈다. 첫째, API는 대문자 이름을 받아 주고 예외를 던지지 않았다. 둘째, 그런데 서버에 도착한 이름은 소문자였다. 셋째, 서버가 대문자로 넣은 응답 헤더도 클라이언트에는 소문자로 도착했다.

즉 라이브러리가 조용히 소문자로 바꿔 준 것이다. 여기서는 아무 사고도 안 난다. 문제는 이 관대함이 진짜 규칙을 가린다는 데 있다.

5.1 압축 계층에 손으로 대문자를 써 넣으면

라이브러리를 걷어내고 확인했다. HTTP/2는 헤더를 그대로 보내지 않고 전용 압축 형식으로 실어 보낸다. 그 바이트를 직접 만들어 이름에 대문자가 들어간 채로 전송했다. 비교를 위해 같은 요청을 소문자로도 보냈다.

node v22.16.0 / win32  (raw HPACK over cleartext h2c)

--- 8-1. field name written as x-request-id (lowercase) ---
  server stream event  : names = [":method",":scheme",":path",":authority","x-request-id"]
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","HEADERS stream=1","DATA stream=1"]
  server saw a stream  : true

--- 8-2. same request, field name written as X-Request-Id ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

--- 8-3. and as ACCEPT ---
  frames from server   : ["SETTINGS stream=0","SETTINGS stream=0","RST_STREAM stream=1  errorCode=1"]
  server saw a stream  : false

결과가 단호하다. 소문자 이름은 정상 처리되어 응답까지 돌아왔다. 같은 요청에서 이름의 철자만 바꾸자 서버는 스트림을 즉시 끊고 오류 코드 1번을 돌려보냈다. 두 번째 사례에서 이름을 ACCEPT로 바꿔도 같았다.

가장 중요한 줄은 마지막이다. 서버의 요청 처리 함수가 한 번도 호출되지 않았다. 응용 코드는 이 요청이 왔다는 사실조차 모른다.

  • 즉 HTTP/2에서 대문자 이름은 「값이 안 보이는」 문제가 아니라 「요청이 성립하지 않는」 문제다
  • 증상이 헤더 하나가 비는 것이 아니라 연결이 끊기는 것으로 나타난다. 그래서 원인 추정 방향이 완전히 달라진다
  • 정상적인 라이브러리를 쓰면 이 상황을 만나기 어렵다. 라이브러리가 먼저 소문자로 바꿔 주기 때문이다
  • 반대로 바이트를 직접 만들거나, 이름 문자열을 어딘가에서 조립하는 코드가 있으면 여기에 걸린다
  • HTTP/1.1로 잘 되던 연동이 HTTP/2로 바꾼 뒤에만 깨지는 사례의 한 갈래가 이것이다

측정 범위를 명확히 한다. 위 결과는 이 환경의 HTTP/2 구현 하나를 상대로 측정한 것이다. 규격 원문을 열지 못했으므로 「규격이 이렇게 정하고 있다」고는 쓰지 않는다. 확인된 사실은 「이 구현은 대문자가 든 이름을 받으면 스트림을 프로토콜 오류로 끊는다」까지다. HTTP/3는 이 환경에 구현이 없어 전혀 측정하지 못했다. 다만 실무 지침은 어느 쪽이든 같다. 이름을 소문자로 고정하면 세 전송 방식 모두에서 안전하다.

6. 프록시를 한 번 지나면 이름이 통째로 바뀐다

2절에서 원본 철자가 배열에 남아 있는 것을 봤다. 그것을 믿어도 되는지 확인할 차례다. 최소한의 중계 서버를 하나 만들었다. 흔히 쓰는 방식 그대로, 받은 헤더 사전을 그대로 다음 단계로 넘긴다.

node v22.16.0 / win32
origin on 127.0.0.1:18083   proxy on 127.0.0.1:18084

--- 4-0. field names the client put on the wire ---
  X-Request-Id / X-API-Key / ACCEPT

--- 4-1. DIRECT to origin: names as received ---
  ["Host","X-Request-Id","X-API-Key","ACCEPT","Connection"]

--- 4-2. THROUGH one proxy hop: names as received by the SAME origin ---
  ["host","x-request-id","x-api-key","accept","connection"]

--- 4-3. diff ---
  identical name lists : false

--- 4-4. response names the client sees ---
  direct        : |X-Origin-Marker: origin-1
  through proxy : |x-origin-marker: origin-1

같은 클라이언트, 같은 바이트, 같은 최종 서버다. 중계 한 단계를 넣었을 뿐인데 도착한 이름이 전부 소문자로 바뀌었다. 원본 철자가 남아 있다던 배열의 내용까지 함께 바뀌었다.

이유는 단순하다. 중계 코드가 넘긴 것은 이미 소문자로 정규화된 사전이었고, 다음 단계로 보낼 때 그 사전의 키가 그대로 wire에 적혔다. 중계는 바이트를 전달한 것이 아니라 파싱한 결과를 다시 조립한 것이다.

응답 방향도 같다. 최종 서버가 X-Origin-Marker로 붙인 헤더가 클라이언트에는 x-origin-marker로 도착했다.

  • 이것은 버그가 아니라 중계의 정상 동작이다. 이름은 대소문자 무시이므로 어떤 철자로 다시 써도 규격 위반이 아니다
  • 그래서 원본 철자에 의존하는 로직은 프로덕션에서만 깨진다. 개발 환경에서는 프록시 없이 직접 붙기 때문이다
  • 부하 분산기나 CDN, 서비스 메시 같은 중간 계층은 전부 이 자리에 있다. 어느 하나가 표기를 바꿔도 이상하지 않다
  • 더 나아가 중간 계층이 HTTP/2로 받아 HTTP/1.1로 넘기면 원본 철자는 애초에 존재하지 않는다. 5절에서 본 대로다
  • 결론은 하나다. 이름의 철자는 계약이 아니다. 헤더 이름을 대소문자 구분해서 다루는 코드는 언젠가 반드시 틀린다

7. 조용히 빗나가는 비교 코드

이제 실제 코드가 어떻게 빗나가는지 본다. 흔히 쓰는 세 가지 형태를 한 요청에서 동시에 측정했다.

--- 5-1. equality and membership on the NAME ---
  keys                        : ["host","x-request-id","authorization","cookie","x-api-key","content-type","x-tag","connection"]
  seen.includes('X-Request-Id'): false
  seen.includes('x-request-id'): true
  Set built from a written spec: ["X-Request-Id","X-API-Key","Authorization"]
  matched by that Set          : []
  matched after normalizing    : ["x-request-id","authorization","x-api-key"]

--- 5-2. the strip list that does not strip ---
  after delete ['Authorization'] : authorization still present = true
  value that would be forwarded  : Bearer sK9xQz
  cookie still present           : true
  normalized filter -> keys      : ["host","x-request-id","content-type","x-tag","connection"]

첫 블록이 가장 흔한 형태다. 연동 문서에 적힌 철자 그대로 이름 목록을 만들어 집합에 넣고, 도착한 헤더 중 그 집합에 있는 것만 골라낸다. 결과는 빈 배열이었다. 세 개 모두 실제로 도착해 있었는데도 하나도 못 골랐다.

두 번째 블록이 더 위험하다. 외부로 전달하기 전에 민감한 헤더를 지우는 코드다. 문서에 적힌 대로 Authorization과 Cookie를 지웠다. 그런데 실제 키는 소문자였으므로 삭제가 아무것도 하지 않았고, 자격 증명이 그대로 남았다.

이 사고의 성질. 지우기가 실패해도 기능은 정상 동작한다. 요청은 잘 전달되고 응답도 잘 돌아온다. 눈에 보이는 증상이 하나도 없다. 그래서 이 실패는 감시로 잡히지 않는다. 지표에도 로그에도 나타나지 않고, 외부 호출의 요청 내용을 실제로 열어 보기 전에는 알 수 없다. 삭제 목록을 다루는 코드에는 「지운 뒤 남아 있지 않은지」를 확인하는 검사를 함께 두는 것이 안전하다.

7.1 로그가 아무것도 안 남기는 형태

--- 5-3. the log line that logs nothing ---
  log ctx rid = {}
  log ctx rid = {"rid":"Req-4821"}
  fallback chain               : Req-4821
  fallback with ?? (nullish)   : MISSING

--- 5-4. WHATWG Headers vs a plain object, same data ---
  Headers.get('X-Request-Id')  : Req-4821
  Headers.get('x-request-id')  : Req-4821
  Headers.has('X-API-KEY')     : true
  [...Headers.keys()]          : ["authorization","content-type","cookie","host","x-api-key","x-request-id","x-tag"]
  plain object same lookups    : undefined / Req-4821

--- 5-6. duplicate names arriving with different casing ---
  x-tag                        : [alpha, beta]

첫 줄이 이 글의 서론을 그대로 설명한다. 로그 문맥 객체에 값을 넣었더니 결과가 빈 객체다. 값이 빈 속성은 직렬화 과정에서 키까지 통째로 사라지기 때문이다.

그래서 화면에는 「값이 이상하다」가 아니라 「그 항목이 아예 없다」로 나온다. 로그를 뒤지는 사람은 그 줄을 찾지 못하고, 자연히 「헤더가 안 왔나 보다」라고 결론 내린다. 원인과 정반대 방향으로 조사가 흘러가는 지점이다.

  • 흔한 대안인 여러 철자를 늘어놓는 방식은 값을 찾긴 한다. 다만 철자를 몇 개 적어도 전부 적을 수는 없다. 임시방편이다
  • 빈 값만 걸러 주는 연산자를 쓰면 오히려 더 나쁘다. 앞의 조회가 진짜로 빈 값이므로 그대로 대체값으로 넘어간다. 실측에서 그 자리에 대체 문자열이 찍혔다
  • 표준 규격의 헤더 객체를 쓰면 조회는 안전하다. 어떤 철자로 물어도 값이 나왔고, 존재 확인도 정상이었다
  • 그러나 그 객체도 이름 목록은 소문자로 정규화해서 준다. 목록을 원본 철자와 맞춰 보는 코드는 여기서도 빗나간다
  • 중복 이름은 대소문자를 무시하고 하나로 합쳐졌다. X-Tag와 x-tag로 각각 보낸 두 값이 쉼표로 이어진 하나의 문자열이 됐다. 4절의 Python 결과와 다르다

8. 이름은 대소문자 무시, 값은 아니다

여기가 실무에서 가장 자주 뒤섞이는 지점이다. 「HTTP 헤더는 대소문자를 안 가린다」는 문장을 값에까지 적용해 버리는 것이다. 확인해 보면 전혀 그렇지 않다.

--- 5-5. the NAME is case-insensitive, the VALUE is not ---
  value as received            : [Req-4821]
  rid === 'REQ-4821'           : false
  rid === 'req-4821'           : false
  authorization as received    : [Bearer sK9xQz]
  startsWith('Bearer ')        : true
  startsWith('bearer ')        : false
  token                        : [sK9xQz]
  token.toLowerCase() === token: false   <- lowercasing a value destroys it
  content-type                 : [application/json; charset=UTF-8]
  ct === 'application/json'    : false
  ct.split(;)[0].trim().toLowerCase() : [application/json]

세 사례가 각기 다른 교훈을 준다.

  • 식별자 값. 도착한 값은 Req-4821이었다. 위아래 어느 철자로 비교해도 거짓이다. 값은 적힌 그대로가 의미이므로 정규화하면 다른 값이 된다
  • 인증 헤더. 앞의 방식 이름 부분은 대소문자를 무시해도 되지만, 뒤의 자격 증명은 글자 하나까지 그대로다. 실측에서 소문자로 바꾼 자격 증명은 원본과 달랐다. 값 전체에 소문자 변환을 걸면 인증이 통째로 깨진다
  • 매체 유형. 값에 붙은 부가 항목까지 포함해 통째로 비교하면 거짓이다. 실제로 필요한 것은 앞부분만 잘라내고 좌우 공백을 없앤 뒤 비교하는 것이다
  • 정리하면 정규화는 이름에만 무조건 걸고, 값에는 그 헤더의 정의를 확인한 뒤에만 건다
  • 값을 다루는 함수와 이름을 다루는 함수를 아예 분리해 두는 것이 실수를 줄인다. 한 함수 안에서 둘 다 만지면 언젠가 섞인다
대상대소문자실측 결과정규화비고
헤더 이름무시네 가지 철자가 모두 같은 값항상 소문자로아스키만 오므로 단순 변환으로 충분
추적 아이디 값구분위아래 철자 모두 비교 거짓절대 금지바꾸면 다른 값이 된다
인증 방식 이름무시해도 됨대문자 접두만 참비교할 때만뒤 자격 증명과 분리해서 다룰 것
자격 증명 본체구분소문자로 바꾸면 값이 달라짐절대 금지손대는 순간 인증 실패
매체 유형 앞부분무시해도 됨부가 항목 포함 비교는 거짓앞부분만 잘라서부가 항목을 먼저 떼어낼 것
부가 항목 값항목마다 다름이 사례는 대문자 표기로 도착정의 확인 후일괄 변환 금지
경로와 질의 문자열구분측정 범위 밖금지헤더가 아니라 요청 대상

9. 안전하게 읽는 법 - 정규화 후 조회

교정은 간단하다. 조회하는 쪽에서 이름을 항상 정규화하면 된다. 다만 두 가지를 함께 처리해야 실제로 안전해진다.

--- 6-1. one getter, every spelling ---
  getHeader(X-Request-Id)    -> "req-4821"
  getHeader(x-request-id)    -> "req-4821"
  getHeader(X-REQUEST-ID)    -> "req-4821"
  getHeader(x-ReQuEsT-iD)    -> "req-4821"
  getHeader(X_Request_Id)    -> undefined

--- 6-2. the prototype trap of a plain-object lookup ---
  Object.getPrototypeOf(h) === null  : false
  naive h['constructor']             : function Object() { [nat
  naive h['toString']                : function
  getHeader(h,'constructor')         : undefined
  getHeader(h,'toString')            : undefined

첫 블록은 기대한 대로다. 함수 하나로 네 가지 철자가 전부 같은 값을 돌려줬다. 마지막 줄은 정상이다. 밑줄로 적은 이름은 실제로 다른 헤더이므로 값이 없는 것이 맞다.

두 번째 블록이 덜 알려진 함정이다. 헤더 사전은 평범한 객체이고 상위 원형과 연결돼 있다. 그래서 정규화 없이 이름을 그대로 읽으면 실제로 오지 않은 이름에서 함수가 튀어나온다. 참인지 거짓인지만 보는 검사라면 이것이 통과해 버린다.

  • 즉 헤더 이름을 외부에서 받은 문자열로 조회하는 코드는 값 존재 검사가 뜻밖의 결과를 낸다
  • 안전한 조회 함수는 소유 속성인지 먼저 확인해서 이 경로를 막는다. 실측에서 두 이름 모두 빈 값이 나왔다
  • 조회 대상이 표준 규격 헤더 객체일 수도 있으므로, 전용 조회 메서드가 있으면 그쪽을 먼저 쓰는 분기를 넣으면 두 경우를 한 함수로 덮는다
  • 이름 정규화는 단순 소문자 변환으로 충분하다. 헤더 이름에 쓸 수 있는 문자가 아스키로 제한되기 때문이다

9.1 보내는 쪽에서 철자를 섞어 쓰면

--- 6-3. send side: two spellings of one name ---
  after setHeader('X-Tag','first')   : getHeaderNames = ["x-tag"]
  after setHeader('x-tag','second')  : getHeaderNames = ["x-tag"]
  res.getHeader('X-TAG')             : second

--- 6-4. names the runtime refuses outright ---
  setHeader("X Request Id") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id:") : ERR_INVALID_HTTP_TOKEN
  setHeader("X-Request-Id\n") : ERR_INVALID_HTTP_TOKEN
  setHeader("") : ERR_INVALID_HTTP_TOKEN

--- 6-5. what actually went out on the wire ---
  |HTTP/1.1 200 OK
  |x-tag: second
  |X-Trace-Id: trace-9f2c
  |Content-Type: text/plain

보내는 쪽에서 같은 이름을 두 가지 철자로 설정했다. 결과는 헤더가 두 개 생기는 것이 아니라 덮어쓰기였다. 이름 목록에는 항목이 하나뿐이고, 값은 나중 것이다.

그리고 wire에 나간 표기는 마지막으로 쓴 철자였다. 처음에 대문자로 적었어도 나중에 소문자로 다시 쓰면 소문자로 나간다. 즉 출력 표기는 마지막 쓰기가 결정한다.

  • 여러 모듈이 같은 헤더를 각자의 철자로 설정하는 코드베이스에서는 어느 표기로 나갈지 예측할 수 없다
  • 값이 덮어쓰기라는 점도 중요하다. 두 모듈이 서로의 값을 지운다는 사실을 아무도 모른다
  • 공백이나 콜론, 개행이 든 이름은 런타임이 거부한다. 이름 자리에 사용자 입력을 그대로 넣는 코드는 여기서 예외로 죽는다
  • 빈 문자열도 거부된다. 이름을 조립해서 만드는 코드는 조립 결과가 빈 문자열이 되는 경로를 확인해야 한다
  • 거부가 예외로 나타나는 것은 다행한 쪽이다. 이 글의 다른 사고들과 달리 최소한 눈에 보인다

9.2 그대로 가져다 쓰는 조회 함수

// 헤더 이름은 대소문자 무시. 조회하는 쪽에서 정규화한다.
// 평범한 객체와 표준 규격 헤더 객체를 한 함수로 덮는다.
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}

// 걸러내기 목록도 같이 정규화해야 한다. 조회만 고치면 절반만 고친 것이다.
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
# Python. 표준 헤더 객체는 조회가 이미 대소문자 무시다.
# 위험한 것은 이름 목록을 꺼내 문자열로 비교하는 코드다.

DROP = {"authorization", "cookie", "x-api-key"}

def get_header(headers, name):
    return headers.get(name)          # 대소문자 무시로 찾아 준다

def forwardable(headers):
    # keys() 는 원본 철자이므로 반드시 정규화해서 비교한다
    return {k: v for k, v in headers.items() if k.lower() not in DROP}

# 같은 이름이 여러 번 왔을 수 있다. 하나만 꺼내면 나머지가 조용히 사라진다
tags = headers.get_all("X-Tag") or []

10. 팀 규약과 점검 목록

코드를 고치는 것만으로는 재발을 막지 못한다. 이 문제는 사람이 문서를 보고 철자를 옮겨 적는 지점에서 계속 다시 태어나기 때문이다. 규약으로 못박을 것을 정리한다.

  • 이름은 언제나 소문자로 적는다. 연동 문서, 코드 상수, 테스트, 로그 키 전부. 예쁘게 보이려고 대문자를 섞지 않는다
  • 이름 문자열을 코드에 흩어 놓지 않는다. 상수 하나로 모아 두면 철자가 갈라질 자리가 없어진다
  • 헤더를 읽는 통로를 하나로 만든다. 조회 함수 하나만 쓰게 하고, 사전을 직접 인덱싱하는 코드는 검사에서 걸러낸다
  • 걸러내기 목록과 조회는 함께 고친다. 조회만 고치면 민감 헤더가 그대로 흘러가는 쪽이 남는다
  • 값에는 정규화를 걸지 않는다. 값 정규화가 필요하면 그 헤더 하나에 대해서만, 정의를 확인하고 건다
  • 테스트 클라이언트는 일부러 철자를 섞어 보낸다. 전부 소문자로만 보내는 테스트는 이 버그를 절대 못 잡는다
  • 중간 계층이 있는 형태로 한 번은 시험한다. 직접 연결로만 시험하면 6절의 변형을 못 본다
  • 원본 철자에 의존하지 않는다. 원본 배열은 디버깅용이지 로직의 입력이 아니다

10.1 점검 목록

  • 헤더를 읽는 모든 자리가 정규화 후 조회를 쓰는가
  • 사전을 대문자가 든 문자열로 직접 인덱싱하는 곳이 남아 있지 않은가
  • 이름을 비교 연산자로 견주거나 집합에 넣는 코드가 정규화를 거치는가
  • 민감 헤더 삭제 목록이 정규화된 이름으로 되어 있는가
  • 삭제 후 실제로 남아 있지 않은지 확인하는 검사가 있는가
  • 로그 문맥에 넣는 값이 빈 값이면 항목이 통째로 사라진다는 것을 아는가
  • 존재 여부 분기가 상속 속성 때문에 잘못 참이 되는 경로를 막았는가
  • 값에 일괄 소문자 변환을 거는 곳이 없는가
  • 자격 증명이 든 값을 비교 전에 변형하지 않는가
  • 매체 유형 비교가 부가 항목을 먼저 떼어내는가
  • 같은 헤더가 여러 번 올 수 있다는 것을 처리했는가
  • 헤더 이름 자리에 사용자 입력이 그대로 들어가는 경로가 없는가
  • 테스트가 대문자 철자로도 요청을 보내는가
  • HTTP/2 경로에서 이름을 직접 조립하는 코드가 없는가

10.2 하지 말 것

  • 문서에 적힌 철자를 그대로 코드 키로 옮겨 적는 것 — 이 글의 모든 사고가 여기서 시작된다
  • 철자 여러 개를 늘어놓아 막는 것 — 전부 적을 수 없으므로 임시방편이다
  • 원본 철자를 로직의 근거로 삼는 것 — 중계 한 번에 사라진다
  • 값에 일괄 정규화를 거는 것 — 자격 증명과 식별자가 파괴된다
  • 테스트를 소문자로만 도는 것 — 실환경에서만 깨진다
  • 삭제 목록만 두고 결과를 확인하지 않는 것 — 실패해도 증상이 없다
  • 「우리는 다 소문자로 보낸다」는 가정에 기대는 것 — 상대는 그럴 의무가 없다

# HTTP 헤더 이름 대소문자 — 안전한 조회와 점검 목록

> 출처: braindetox.kr — 헤더는 분명히 보냈는데 서버에서 안 보인다
> 근거: Windows 10 / Node.js v22.16.0 / Python 3.13.3 표준 라이브러리 실행 검증 (HTTP/1.1 + h2c)

## 0. 대전제 — 어긋남이 어디에 있나

| 층 | 대소문자 | 근거 |
|---|---|---|
| **헤더 이름** | **무시한다** | RFC 9110 5.1 |
| **헤더 값** | **가린다** (필드별 정의) | RFC 9110 5.5 |
| 코드의 객체 키 · 집합 · 문자열 비교 | **가린다** | 언어 규칙 |

**버그는 「대소문자 무시인 이름」을 「대소문자 구분 자료구조」에 담는 순간 생긴다.**

## 1. 30초 진단 — 값이 없다고 나올 때

1. 실제 저장된 키를 통째로 찍는다 (추측하지 말 것)
2. 소문자 이름으로 다시 조회해 본다
3. 원본 철자 배열이 있으면 같이 찍는다 (직접 연결에서만 신뢰)
4. 중간 계층이 있는지 확인한다 — 있으면 원본 철자는 이미 없다
5. HTTP/2 경로면 이름은 무조건 소문자다

## 2. 안전한 조회 (JavaScript)

```js
function getHeader(headers, name) {
  if (!headers || typeof name !== 'string') return undefined;
  const key = name.toLowerCase();
  if (typeof headers.get === 'function') return headers.get(key);
  return Object.prototype.hasOwnProperty.call(headers, key)
    ? headers[key]
    : undefined;
}
```

- `hasOwnProperty` 확인이 **필수**다. 헤더 사전은 상위 원형과 연결돼 있어서, 정규화 없이 읽으면 오지 않은 이름에서 **함수가 튀어나온다**
- 참·거짓만 보는 검사라면 그 함수가 **통과해 버린다**

```js
// 걸러내기 목록도 정규화. 조회만 고치면 절반만 고친 것이다.
const DROP = new Set(['authorization', 'cookie', 'x-api-key']);
const forwarded = Object.fromEntries(
  Object.entries(req.headers).filter(([k]) => !DROP.has(k.toLowerCase()))
);
```

## 3. 안전한 조회 (Python)

```python
DROP = {"authorization", "cookie", "x-api-key"}

def get_header(headers, name):
    return headers.get(name)          # 표준 헤더 객체는 이미 대소문자 무시

def forwardable(headers):
    # keys() 는 원본 철자다. 반드시 정규화해서 비교한다
    return {k: v for k, v in headers.items() if k.lower() not in DROP}

tags = headers.get_all("X-Tag") or []   # 하나만 꺼내면 나머지가 사라진다
```

## 4. 계층별 동작 대조표 (실측)

| 계층 | 이름 저장 | 조회 대소문자 | 원본 철자 | 중복 이름 |
|---|---|---|---|---|
| Node 요청 헤더 사전 | **소문자 정규화** | **구분** | 별도 배열에 보존 | 쉼표로 합침 |
| Node 원본 이름 배열 | 도착 순서 그대로 | — | **그대로** | 각각 보존 |
| Node 응답 헤더 | 소문자 색인 | **무시** | 출력은 원본 표기 | 덮어쓴다 |
| 표준 규격 헤더 객체 | 소문자 색인 | **무시** | 목록은 소문자 | 쉼표로 합침 |
| Python 헤더 객체 | 원본 철자 유지 | **무시** | **그대로** | 각각 보존 |
| Python 이름 목록 | 원본 철자 문자열 | **구분** | 그대로 | 각각 나열 |
| HTTP/2 전송 | **소문자만** | — | **없음** | 전송 규칙 |

→ **「조회」를 주는 쪽은 대체로 안전하고, 「목록」을 주는 쪽은 대체로 위험하다.**

## 5. 이름 대 값 — 정규화해도 되는 것과 안 되는 것

| 대상 | 정규화 | 이유 |
|---|---|---|
| 헤더 이름 | **항상 소문자** | 대소문자 무시가 규격 |
| 추적 아이디 값 | **금지** | 바꾸면 다른 값 |
| 인증 방식 이름 | 비교할 때만 | 뒤 자격 증명과 분리 |
| 자격 증명 본체 | **금지** | 손대면 인증 실패 |
| 매체 유형 앞부분 | 앞부분만 | 부가 항목 먼저 분리 |
| 경로 · 질의 문자열 | **금지** | 헤더가 아님 |

## 6. 실측으로 확인된 사고 형태

- 문서 철자 그대로 만든 집합으로 걸렀더니 **하나도 못 골랐다** (전부 도착해 있었음)
- 대문자 철자로 쓴 삭제 목록이 **아무것도 못 지웠다** → **자격 증명이 그대로 전달됨**
- 로그 문맥에 빈 값을 넣었더니 **항목이 통째로 사라져** 빈 객체가 찍혔다
- 중계 **한 단계**만에 요청·응답 양쪽 이름이 전부 소문자로 바뀌었다
- HTTP/2에 대문자 이름을 실었더니 **스트림이 프로토콜 오류로 끊겼다** (응용 코드는 요청을 보지도 못함)
- 같은 이름을 두 철자로 설정했더니 헤더가 두 개가 아니라 **덮어써졌다**

## 7. 점검 목록

- [ ] 헤더를 읽는 **모든 자리**가 정규화 후 조회를 쓴다
- [ ] 대문자가 든 문자열로 사전을 **직접 인덱싱**하는 곳이 없다
- [ ] 이름을 비교하거나 집합에 넣는 코드가 **정규화를 거친다**
- [ ] 민감 헤더 **삭제 목록이 정규화된 이름**이다
- [ ] 삭제 후 **남아 있지 않은지 확인하는 검사**가 있다
- [ ] 존재 검사가 **상속 속성으로 잘못 참**이 되지 않는다
- [ ] **값에 일괄 소문자 변환**을 거는 곳이 없다
- [ ] 자격 증명 값을 **비교 전에 변형하지 않는다**
- [ ] 매체 유형 비교가 **부가 항목을 먼저 뗀다**
- [ ] 같은 헤더가 **여러 번 올 수 있다**는 것을 처리했다
- [ ] 헤더 이름 자리에 **사용자 입력이 그대로** 들어가지 않는다
- [ ] 테스트가 **대문자 철자로도** 요청을 보낸다
- [ ] **중간 계층이 있는 형태**로 한 번은 시험했다
- [ ] HTTP/2 경로에서 **이름을 직접 조립**하지 않는다

## 8. 하지 말 것

- ❌ 문서 철자를 **그대로 코드 키로** 옮겨 적는 것 — 모든 사고의 출발점
- ❌ 철자 여러 개를 **늘어놓아 막는 것** — 전부 적을 수 없다
- ❌ **원본 철자를 로직의 근거**로 삼는 것 — 중계 한 번에 사라진다
- ❌ 값에 **일괄 정규화**를 거는 것 — 자격 증명과 식별자가 파괴된다
- ❌ 테스트를 **소문자로만** 도는 것 — 실환경에서만 깨진다
- ❌ 삭제 목록만 두고 **결과를 확인하지 않는 것** — 실패해도 증상이 없다
- ❌ 「우리는 다 소문자로 보낸다」는 **가정에 기대는 것** — 상대는 그럴 의무가 없다
