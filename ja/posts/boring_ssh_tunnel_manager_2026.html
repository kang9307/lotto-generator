boring — TOML設定ベースの軽量SSHトンネルマネージャ 実践分析

毎回打つ長いssh -L/-R/-DコマンドをTOML宣言型設定で解決するツール — フォワーディング3種の違いとautossh比較まで

2026-06-25 開発・インフラ

はじめに：SSHトンネルはなぜいまだに不便なのか

SSHポートフォワーディングは、インフラエンジニアと開発者にとって日常的なツールだ。ファイアウォール内のDBへのアクセス、ローカルの開発サービスをリモートに公開すること、SSHサーバをSOCKS5プロキシとして使うこと——これらはよくある作業だ。しかし2026年6月時点でも、これらを管理するUXは驚くほど原始的なままだ。

典型的なワークフローは、50文字のsshコマンドを思い出してシェル履歴を漁り、貼り付けてPIDを確認し、切断されればまた繰り返す。複数のトンネルが必要な場合はps aux | grep sshで生存確認し、手動で再接続する。チームでは「このトンネルはこう開く」をSlackメッセージに書き出すことになる。

GitHubのalebeckが開発したboringは、この摩擦を正面から狙う。「ただ動くシンプルなCLI SSHトンネルマネージャ」を標榜するこのツールのコアアイデアはひとつだ。すべてのトンネル定義をTOMLファイルで宣言し、一つの短いコマンドで任意のトンネル、またはグループ全体を開閉する。この分析では、そのアイデアが実際に何を解決するか、既存ツールと何が違うかを実務視点で検証する。

1. boringとは — GoベースのSSHトンネルデーモン

boringはGo言語（コードベースの95.5%）で書かれたMITライセンスのオープンソースCLIツールだ。2026年6月時点でv0.16.0、GitHub星数1,600超、266コミット、Coverallsによるテストカバレッジ追跡が続いており、活発にメンテナンスされているプロジェクトの証跡が揃っている。

アーキテクチャはシンプルだ。最初のboring openコマンドでバックグラウンドデーモン（boringd）が起動する。以降のCLI呼び出しはUnixソケット（$BORING_SOCK、デフォルト/tmp/boringd.sock）経由でデーモンに命令を送る。デーモンがすべてのSSH接続と再接続を管理し、CLIはそのフロントエンドに徹する。

1.1 インストール

macOSはbrew install boring一行で完結する。LinuxとWindowsはGitHubリリースページからバイナリを取得して$PATHに置く。ソースビルドはmake（Go 1.25+必要、Windows用はbuild_win.batあり）。Homebrewインストール時はbash/zsh/fishシェル補完が自動設定される。

1.2 設定ファイルの場所

設定は~/.boring.toml（macOS/Windows）または$XDG_CONFIG_HOME/boring/.boring.toml（Linux）に置く。$BORING_CONFIG環境変数でパスを上書きでき、複数環境の設定ファイルを切り替える運用も可能だ。

2. TOML宣言型設定の実体

boringの差別点は、トンネル定義が「コマンドの暗記」ではなく「ファイルの宣言」である点だ。TOMLを選んだ理由は明確だ。YAMLよりもインデントエラーがなく、JSONより可読性が高く、コメントを書ける。

2.1 基本構造

# ~/.boring.toml

[[tunnels]]
name    = "dev-db"
local   = "5432"
remote  = "localhost:5432"
host    = "bastion"
mode    = "local"

[[tunnels]]
name     = "prod-redis"
local    = "6379"
remote   = "cache-01:6379"
host     = "prod-bastion"
user     = "deploy"
identity = "~/.ssh/id_prod"
group    = "prod"

[[tunnels]]
name       = "socks-proxy"
local      = "1080"
host       = "jump-server"
mode       = "socks"
keep_alive = 60

各トンネルは[[tunnels]]配列エントリとして定義する。nameはCLI識別子、localはバインドするローカルアドレス（ポートのみでも可）、remoteはリモート宛先、hostはSSH接続先、modeはフォワーディング種別だ。

2.2 宣言型設定がもたらす実質的メリット

これは「コマンドをファイルに書き移した」以上の意味を持つ。設定がファイルとして存在するためGitでバージョン管理できる。いつトンネルが追加されたかを追跡でき、環境間のdiffも取れる。チームへの共有はファイルのコピーかリポジトリURLで完結する。また、設定は起動時に一度検証されるため、タイポはデバッグの最中ではなく開始前に発見できる。

3. フォワーディング3種の違いと実務での使い方

boringのmodeフィールドはSSHの-L/-R/-Dフラグに直接対応する。各モードの理解がTOMLを正しく書く前提だ。

3.1 ローカルフォワーディング（mode = "local"、SSH -L）

最も一般的なパターンだ。ローカルマシンの特定ポートへのトラフィックをSSHサーバ経由で指定したリモート宛先に転送する。方向：自分のPC → SSHサーバ → リモット宛先。

実務シナリオ：社内ネットワークからしかアクセスできないPostgreSQL（192.168.1.100:5432）にローカルのDBクライアントから接続したい。local = "5432"、remote = "192.168.1.100:5432"、host = "bastion"と設定すればlocalhost:5432が直接DBに繋がる。

[[tunnels]]
name   = "internal-db"
local  = "5432"
remote = "192.168.1.100:5432"
host   = "bastion"
mode   = "local"

等価なsshコマンド：ssh -L 5432:192.168.1.100:5432 -N bastion

3.2 リモートフォワーディング（mode = "remote"、SSH -R）

方向が逆になる。リモートサーバの特定ポートへのトラフィックをローカルサービスに転送する。方向：リモートサーバ → SSHトンネル → 自分のPC。

実務シナリオ：開発PCで動くWebアプリ（localhost:3000）をQAサーバのポートに一時公開してQAチームにURLを渡したい。ファイアウォールルールを開けることも、ngrokを使うことも不要だ。

[[tunnels]]
name   = "expose-dev"
local  = "3000"
remote = "0.0.0.0:9000"
host   = "qa-server"
mode   = "remote"

3.3 ダイナミックフォワーディング / SOCKS5（mode = "socks"、SSH -D）

ローカル・リモートフォワーディングは1ポートを1宛先にマッピングする。ダイナミックフォワーディングはSSHサーバをSOCKS5プロキシサーバに変える。アプリがこのプロキシを経由することで、SSH側で任意のホストとポートへのトラフィックを処理する。事前の宛先指定が不要だ。

実務シナリオ：公共Wi-Fiから信頼できるサーバ経由でWebトラフィックを暗号化したい、または複数の社内サービスにトンネルを個別に開かずアクセスしたい。

[[tunnels]]
name  = "proxy"
local = "1080"
host  = "remote-server"
mode  = "socks"

等価なsshコマンド：ssh -D 1080 -N remote-server。ブラウザのSOCKS5プロキシをlocalhost:1080に設定すれば使える。

3.4 Unixソケットサポート

localとremoteフィールドにhost:portの代わりにUnixソケットパスを指定できる。Dockerソケットのトンネリングに特に有用だ。

[[tunnels]]
name   = "docker-remote"
local  = "/tmp/remote-docker.sock"
remote = "/var/run/docker.sock"
host   = "remote-host"

このトンネルが開いていればDOCKER_HOST=unix:///tmp/remote-docker.sock docker psでリモートDockerデーモンをローカルから制御できる。

4. CLIコマンド — open / close / list

boringのCLIは意図的にシンプルに設計されている。日常的に使うコマンドはわずかだ。

コマンド短縮説明
boring open [名前]o指定トンネルを起動。-aで全体、-g グループでグループ一括起動
boring close [名前]c指定トンネルを停止。-aで全体停止
boring listlトンネル一覧と現在の状態(開/閉)を表示。-g グループでフィルタ可能
boring edite設定ファイルを$EDITORで開く
boring versionvバージョン情報を表示

グループ機能が特に実務で効果を発揮する。group = "dev"でまとめたトンネル群をboring open -g dev一行で全部起動できる。開発環境（DB + Redis + 内部API）と本番環境をグループで分けておけば、環境切り替えが2コマンドで済む。

5. autosshとの比較 — 何が違うか

SSHトンネルの自動化ツールとして最も広く使われているのはautosshだ。両者の哲学の違いを整理する。

5.1 autosshの方式

autosshはSSHプロセスを監視し、落ちたら再起動する単目的ツールだ。使い方はsshコマンドをautosshで包む形で、autossh -M 0 -L 5432:db:5432 -N bastionのように使う。複数トンネルを常時維持するには、トンネルごとにsystemdサービスユニットを作り、ExecStartにautosshコマンドを書き、Restart=alwaysを設定する。堅牢だが、新しいトンネルの追加のたびにユニットファイル作成、systemctl daemon-reload、systemctl enableが必要になる。

5.2 boringの方式

boringはすべてのトンネル定義をTOMLファイル一つに集約し、自身のデーモンがすべての再接続を管理する。新しいトンネルの追加はTOMLに[[tunnels]]ブロックを書くだけで完結する。ユニットファイル作成もreloadもenableも不要だ。ただし、OSブート時の自動起動には別途ランチャー（launchd、systemdユーザサービス等）の設定が必要になる。

5.3 どちらをいつ使うか

シナリオ向いているツール
サーバ — 再起動後も自動復旧する常時稼働トンネルautossh + systemd
開発者ワークステーション — 1日に何度も開閉するトンネルboring
チーム共有・バージョン管理されるトンネル定義boring（TOMLをリポジトリ管理）
追加依存なし・標準ツールのみautossh

6. ssh_configとの統合

boringは独自のSSHスタックを実装せず、システムの~/.ssh/configをそのまま読み込む。hostフィールドにssh_configで定義したHostエイリアスを使える。ProxyJumpチェーン、ProxyCommand設定、IdentityFile指定、HostName書き換えもすべてboringのトンネルに引き継がれる。

これは大きな利点だ。すでに複雑なジャンプホスト構成や証明書ベース認証がssh_configに設定されていれば、boringのTOMLにはそのエイリアスを書くだけでよい。認証ロジックを2か所で管理する必要がない。ssh-agentとも互換性があり、エージェントにキーが登録されていればパスフレーズ入力なしでトンネルが開く。

7. 開発者ワークステーションの実践設定例

2026年6月時点での、開発と本番環境を横断する開発者の実践的な~/.boring.toml例を示す。

# ~/.boring.toml

# 開発環境グループ
[[tunnels]]
name   = "dev-pg"
local  = "5432"
remote = "pg-dev.internal:5432"
host   = "dev-bastion"
group  = "dev"

[[tunnels]]
name   = "dev-redis"
local  = "6379"
remote = "redis-dev.internal:6379"
host   = "dev-bastion"
group  = "dev"

# 本番環境 読み取り専用アクセス
[[tunnels]]
name     = "prod-pg-ro"
local    = "15432"
remote   = "pg-prod.internal:5432"
host     = "prod-bastion"
user     = "readonly"
identity = "~/.ssh/id_prod_ro"
group    = "prod-readonly"

# 汎用SOCKS5プロキシ
[[tunnels]]
name       = "office-proxy"
local      = "1080"
host       = "office-gateway"
mode       = "socks"
keep_alive = 30

朝のワークフロー：boring open -g dev一行で開発環境のDB・Redis・APIトンネルが全部起動する。終業時にboring close -aで全部閉じる。本番調査時はboring open prod-pg-roだけ開いて完了後にboring close prod-pg-ro。40文字のsshコマンドを記憶する必要は一切ない。

8. 限界と注意点

8.1 デーモンのライフサイクル管理

boringのデーモンはOSのinit systemに自動登録されない。ログイン時やシステム起動時にトンネルを自動起動するには、launchd（macOS）またはsystemdユーザサービス（Linux）でboringデーモンを起動する設定が別途必要だ。autossh + systemdがこの点でより自然な統合を提供する。

8.2 シングルユーザ向け設計

boringは個人ワークステーション用に設計されている。チーム横断のトンネルポリシー管理、権限制御、監査ログ要件には対応していない。そういった要件にはVault SSHなどインフラレベルのソリューションが適切だ。

8.3 socks-remoteモードの用途

socks-remoteモード（リモートサーバ側にSOCKS5リスナーを開くモード）は用途が限定的だ。大半のワークフローはlocal・remote・socksで事足りる。存在を知っておくことで混乱を防げるが、頻繁に使うことはないだろう。

9. まとめ — 宣言型設定がもたらす摩擦の削減

boringは大きなパラダイムシフトではない。SSHトンネルの仕組みそのものを変えるわけではない。しかし管理方法を「コマンドを暗記してタイピング」から「ファイルで宣言して名前で呼び出す」に変える。この違いが日常業務で積み重なる摩擦の量は、想像以上に大きい。

2026年6月時点でv0.16.0のboringは安定しており、クロスプラットフォームで活発にメンテナンスされている。複数のSSHトンネルを管理する開発者やインフラエンジニアなら、~/.boring.tomlを一度設定する投資はすぐに回収できる。

正しい位置付けは：autossh + systemdはサーバサイドの常時稼働トンネルインフラを担い、boringは開発者ワークステーションでの頻繁なコンテキスト切り替えを担う。両者は競合ではなく補完関係にある。
