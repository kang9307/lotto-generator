로컬 LLM 에이전트 개발, 툴 검색과 HITL이 필요한 이유

도구가 늘어날수록 커지는 컨텍스트 낭비와 승인 부재 - 로컬 LLM 에이전트 개발 도구가 답하려는 두 가지 문제

2026-07-24 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 로컬 LLM 에이전트 개발 도구가 늘어나는 이유

최근 GeekNews(hada)에 올라온 Show GN 하나가 눈에 띄었다. Spring AI Playground라는, Spring AI 커뮤니티가 인큐베이팅 중인 오픈소스 데스크톱 앱이다. MCP 도구를 만들고 테스트하고 승인 절차를 거쳐 실행까지 한곳에서 처리한다는 설명인데, 핵심 원칙은 「No pass, no run」이다. 로컬 테스트를 통과하지 못한 도구는 MCP 서버로 노출조차 되지 않는다는 뜻이다. 도구 카탈로그 검색, 위험도별(L0~L5) 승인 흐름, Ollama 기반 로컬 모델 지원, 토큰·비용·트레이스를 보여주는 여러 대시보드를 갖췄다.

이 글의 목적은 이 도구 하나를 소개하는 데 있지 않다. 오히려 왜 이런 기능 조합이 지금 나왔는지, 로컬 LLM으로 에이전트를 만들어 본 사람이라면 왜 이 조합이 필연적으로 느껴지는지를 짚고 싶다. 툴 검색, HITL 승인, 로컬 모델 지원은 각각 독립된 트렌드가 아니라, 로컬 에이전트 개발에서 반복적으로 부딪히는 세 가지 벽에 대한 응답이라는 것이 본인의 해석이다. 2026년 7월 기준으로 이 세 가지가 왜 하나의 도구 안에 함께 들어가야 했는지 분석해본다.

1. 로컬 LLM 에이전트를 만들 때 실제로 부딪히는 벽

호스팅 API로 에이전트를 만들 때는 잘 드러나지 않다가, 로컬 모델로 옮기는 순간 갑자기 선명해지는 문제들이 있다. 다섯 가지로 정리해본다.

1.1 툴 정의·호출 디버깅이 유독 어려운 이유

클라우드 플래그십 모델은 툴 콜 포맷을 안정적으로 지키도록 많은 후처리와 파인튜닝을 거친다. 반면 로컬에서 흔히 쓰는 7B~14B급 모델은 같은 툴 스키마를 주어도 인자 이름을 살짝 바꾸거나, JSON을 깨뜨리거나, 존재하지 않는 함수를 지어내는 경우가 드물지 않다. 문제는 이 실패가 조용히 일어난다는 점이다. 모델이 이상한 인자로 도구를 호출해도 에이전트 프레임워크는 일단 실행을 시도하고, 개발자는 로그를 뒤져서야 무엇이 잘못됐는지 알게 된다. 로컬 모델을 쓴다는 것은 이 디버깅 비용을 스스로 떠안는다는 뜻이다.

1.2 프롬프트와 툴의 불일치

시스템 프롬프트에서 도구 사용법을 아무리 잘 설명해도, 모델이 그 설명과 실제 툴 스키마를 다르게 해석하는 경우가 생긴다. 예를 들어 프롬프트에는 "파일을 찾을 때는 search 도구를 써라"라고 되어 있는데, 모델은 비슷한 이름의 다른 도구를 호출하거나, 간단한 인사말에도 불필요하게 검색 도구를 호출하는 식이다. 도구 개수가 늘어날수록, 그리고 모델 크기가 작아질수록 이 불일치는 더 자주 나타난다.

1.3 비결정성 - 같은 입력, 다른 결과

전통적인 소프트웨어 디버깅은 같은 입력이면 같은 경로를 탄다는 전제 위에 서 있다. 에이전트는 이 전제를 깨뜨린다. 온도(temperature)를 0으로 고정해도 완전한 결정성은 보장되지 않고, 같은 요청을 다시 보내도 이전 실패를 그대로 재현하지 못하는 경우가 흔하다. 로컬 모델은 양자화, 배치 크기, 추론 엔진 설정 같은 변수가 더해져 이 비결정성이 한층 커진다. "다시 돌려보니 멀쩡히 됐다"는 보고가 디버깅에 아무 도움이 되지 않는 이유다.

1.4 승인 흐름의 부재 - "일단 실행하고 본다"의 위험

많은 로컬 에이전트 튜토리얼은 툴 콜을 받으면 바로 실행하는 구조로 짜여 있다. 파일 삭제, 셸 명령 실행, 외부 API 호출처럼 되돌리기 어려운 동작도 예외가 아니다. 개발 초기 실험 단계에서는 이 구조가 편하지만, 실제 파일시스템이나 실제 서비스 계정에 연결하는 순간 위험해진다. 승인 절차가 없는 에이전트는 결국 모델이 맞게 판단했기를 바라는 상태로 운영되는 셈이다.

1.5 관측 부족 - 무엇이 잘못됐는지 알 수 없다

에이전트가 여러 단계를 거쳐 실패했을 때, 진짜 원인은 흔히 눈에 보이는 마지막 단계가 아니라 훨씬 앞선 툴 호출이나 컨텍스트 구성에 있다. 단일 호출 로그만 남기는 구조에서는 이 인과관계를 되짚기 어렵다. 로컬 개발 환경일수록 이런 관측 도구를 직접 갖추지 않는 경우가 많아, 실패가 나면 프롬프트를 감으로 고치고 다시 돌려보는 시행착오에 의존하게 된다.

2. 왜 '툴 검색(Tool Search)'이 필요한가

2.1 도구가 늘어날수록 커지는 컨텍스트 비용

MCP 서버를 여러 개 연결하면 도구 설명 전체가 매 요청마다 컨텍스트에 실린다. 최근 보고에 따르면 MCP 서버 일고여덟 개만 연결해도 도구 정의만으로 6만 토큰 이상, 200K 컨텍스트의 3분의 1가량이 소모된다고 한다. 사용자가 아무 말도 하기 전에 컨텍스트의 상당 부분이 이미 채워지는 셈이다.

2.2 선택 오류 - 많을수록 헷갈린다

컨텍스트가 커진다고 끝이 아니다. 도구 목록이 길어질수록 모델이 적합한 도구를 고르는 정확도가 떨어지는 현상이 관찰된다. 흔히 "컨텍스트 로트(context rot)"라고 부르는 이 현상은, 정보가 많아질수록 오히려 추론 품질이 나빠지는 역설을 가리킨다. 로컬의 작은 모델일수록 이 역설에 더 취약하다.

2.3 동적 검색과 선별 주입이라는 해법

이 문제에 대한 업계의 응답이 툴 검색이다. 모든 도구 스키마를 한꺼번에 밀어넣는 대신, 이름과 짧은 설명만 가벼운 인덱스로 올려두고, 실제로 필요한 순간에만 전체 스키마를 불러오는 방식이다. Anthropic이 Claude Code에 적용한 사례에서는 이 방식으로 도구 정의 토큰을 약 85% 줄였다는 결과가 보고됐다. MCP 사양 쪽에서도 도구 목록을 한 번에 다 주지 않고 페이지 단위로 점진적으로 내려주는 방향이 논의되고 있다.

2.4 로컬 개발 도구에서 이 문제가 더 절실한 이유

클라우드 플래그십은 100만 토큰급 컨텍스트를 감당하지만, 로컬에서 흔히 돌리는 모델은 컨텍스트도 좁고 추론 속도도 느리다. 도구 설명에 컨텍스트를 낭비하면 그만큼 실제 작업에 쓸 여유가 줄고, 응답 시간도 늘어난다. 로컬 에이전트 개발 도구가 처음부터 도구 검색·선택 기능을 갖추고 나오는 것은, 자원이 넉넉한 클라우드 환경보다 오히려 자원이 빠듯한 로컬 환경에서 이 낭비가 더 크게 느껴지기 때문이라고 본다.

3. HITL이 왜 필수인가

3.1 자율성과 위험의 트레이드오프

에이전트가 자율적으로 실행할 수 있는 범위를 넓힐수록, 되돌릴 수 없는 실수 하나가 낼 수 있는 피해도 커진다. 파일 삭제, 결제, 프로덕션 배포처럼 비가역적인 동작 앞에서는 "일단 해보고 안 되면 되돌리자"는 접근이 통하지 않는다. HITL(Human-in-the-Loop)은 이 지점에서 사람의 확인을 요구하도록 흐름을 끊는 장치다.

3.2 감독 피로와의 균형

다만 모든 동작마다 사람의 승인을 요구하면 다른 문제가 생긴다. 어제 다룬 감독 피로(supervision fatigue) 글에서 짚었듯, 검토할 것이 너무 많아지면 사람은 내용을 제대로 읽지 않고 습관적으로 승인 버튼을 누르게 된다. 승인 절차가 있다는 사실 자체는 안전을 보장하지 않는다. 실제로 사람이 판단력을 유지한 채 검토할 수 있는 양이어야 의미가 있다.

3.3 리스크 등급화라는 절충안

이 균형을 맞추는 실무적 접근이 위험도 등급화다. 조회처럼 되돌리기 쉬운 동작은 자동 실행하고, 삭제·외부 전송·결제처럼 되돌리기 어려운 동작만 사람의 승인을 거치게 하는 식이다. 도구마다 선언된 능력을 기준으로 위험 등급을 매기고, 그 등급에 따라 승인 요구 여부를 달리하는 설계는, 승인 피로를 줄이면서도 정말 위험한 지점에서는 사람의 눈을 확실히 거치게 한다는 점에서 합리적이다. 승인 게이트를 사람의 습관이 아니라 코드가 강제하는 규칙으로 못박고 싶다면, CLAUDE.md 규칙을 훅으로 컴파일하는 접근도 같은 방향의 시도로 참고할 만하다.

3.4 규제 맥락

이 흐름은 규제와도 맞물린다. EU AI Act 14조(인간 감독)는 고위험 AI 시스템에 대해 개입 권한과 능력을 가진 사람의 감독을 의무화하고 있고, 2026년 8월부터 관련 의무가 시행된다고 알려져 있다. 개발 도구 차원에서 HITL을 기본값으로 갖추는 흐름은 이런 규제 방향과도 맞닿아 있다.

4. 로컬 모델을 쓰는 이유와 한계

4.1 프라이버시·비용·오프라인

로컬 모델을 쓰는 이유는 명확하다. 프롬프트와 코드가 외부 API로 나가지 않는다는 것, 토큰 단가가 아니라 보유 하드웨어 기준으로 비용이 정해진다는 것, 네트워크가 없는 환경에서도 동작한다는 것이다. 사내 코드베이스나 민감한 문서를 다루는 에이전트, 망분리 환경의 개발 도구에는 이 세 가지가 대체 불가능한 조건이 되는 경우가 많다.

4.2 성능 격차와 툴콜 품질의 한계

다만 대가도 분명하다. 툴콜 안정성만 봐도 모델 간 편차가 크다. 최근 벤치마크에서는 Qwen3 계열이 툴 호출을 빠뜨리거나 잘못된 JSON을 반환하는 비율이 낮아 상대적으로 안정적이라는 평가를 받는 반면, 더 작은 모델일수록 존재하지 않는 함수를 지어내거나 불필요한 시점에 도구를 호출하는 실패가 늘어난다는 관찰이 있다. 실무에서는 32B급 이상을 신뢰 가능한 하한선으로 보는 시각이 많고, 8B급 이하는 개발·실험용으로는 충분해도 운영에는 조심스럽다는 평가가 나온다.

4.3 하드웨어와 트레이드오프

컨텍스트가 긴 로컬 모델일수록 메모리와 연산 요구도 커진다. 결국 로컬 모델 선택은 성능이 부족해도 감수할 것인가와 하드웨어 비용을 감수할 것인가 사이의 트레이드오프다. 정답은 워크로드에 달렸다. 민감도가 높고 정확도 요구가 낮은 반복 작업에는 로컬이 유리하고, 정확도가 결정적인 일회성 고위험 작업에는 검증된 클라우드 플래그십을 폴백으로 두는 이원화가 현실적이다.

5. 개발 워크플로 제안 - 스키마 설계에서 재현까지

로컬 LLM 에이전트를 실제로 개발할 때 본인이 권하는 순서는 다음과 같다.

5.1 툴 스키마 설계

도구 이름과 인자 설명을 모델이 오해할 여지가 적도록 구체적으로 쓴다. 비슷한 이름의 도구를 나란히 두지 않는다. 도구 개수가 늘어나기 전에 검색·분류 체계를 먼저 설계해 두면, 나중에 도구가 수십 개로 늘어도 컨텍스트 낭비 없이 대응할 수 있다.

5.2 로컬 테스트로 사전 검증

도구를 에이전트에 연결하기 전에, 샘플 인자로 도구 자체를 먼저 테스트한다. 돌려보지 않은 도구는 노출하지 않는다는 원칙은 로컬 개발에서 특히 유효하다. 로컬 모델은 실패를 조용히 삼키는 경우가 많으므로, 도구 단위의 사전 검증이 문제를 앞단에서 걸러낸다.

5.3 HITL 게이트 삽입

파일 삭제·쓰기, 외부 API 호출, 결제처럼 되돌리기 어려운 동작에는 승인 게이트를 두고, 조회처럼 안전한 동작은 자동 실행되도록 등급을 나눈다. 처음부터 모든 동작에 승인을 요구하면 금방 피로해지므로, 위험도 기준을 먼저 정하고 그 기준에 따라 게이트를 배치한다.

5.4 로그와 재현

각 툴 호출의 이름·인자·반환값·지연시간을 남기고, 실패 지점을 다시 살펴볼 수 있는 타임라인을 유지한다. 완벽한 재현은 어렵더라도, 실패 당시의 컨텍스트와 호출 순서를 기록해두면 원인 추정의 범위를 크게 좁힐 수 있다.

6. 관련 생태계 - Ollama·LM Studio·MCP

로컬 에이전트 개발 생태계는 몇 가지 축으로 정리된다. Ollama와 LM Studio는 로컬 모델을 내려받고 구동하는 런타임 역할을 하고, MCP(Model Context Protocol)는 에이전트와 외부 도구를 연결하는 공통 규격 역할을 한다. Spring AI Playground 같은 도구는 이 둘 사이, 즉 도구를 만들고 검증하고 승인 절차와 함께 노출하는 계층에 자리한다. 어느 한 요소만으로는 완결되지 않고, 런타임·프로토콜·개발 도구가 함께 갖춰져야 로컬 에이전트 개발이 실용적인 수준에 이른다는 점이 최근 흐름에서 드러난다.

7. 실무 적용 시 고려사항 - 누가, 언제 써야 하나

이런 도구는 누구에게 맞을까. 사내 코드나 문서를 외부로 보내기 꺼려지는 팀, 오프라인·망분리 환경에서 에이전트를 돌려야 하는 조직, 그리고 에이전트에 새 도구를 자주 붙이고 떼면서 실험하는 개발자에게 특히 유용하다. 반대로 최고 품질의 툴콜 정확도가 즉시 필요하거나, 검증 시간을 들일 여유가 없는 프로덕션 급 작업이라면 아직은 클라우드 플래그십에 무게를 두는 편이 안전하다. 로컬 도구는 개발·실험 단계의 안전망으로 먼저 들이고, 신뢰가 쌓인 워크로드부터 점진적으로 넓혀가는 순서를 권한다.

8. 한계와 주의점

이런 개발 도구들이 아직 신생 오픈소스 단계라는 점도 짚어야 한다. 대시보드와 리스크 등급이 있다고 해서 완벽한 안전이 보장되는 것은 아니고, 등급 분류 자체가 잘못되면 위험한 동작이 낮은 등급으로 새어나갈 수 있다. 또한 HITL 게이트가 많아질수록 개발자 자신이 승인 피로에 빠질 위험도 여전히 남는다. 로컬 모델의 툴콜 신뢰도는 모델·버전마다 편차가 커서, 특정 모델에서 검증된 워크플로가 다른 모델에서는 그대로 통하지 않을 수 있다. 도구를 들이기 전에 본인의 실제 시나리오로 먼저 검증하는 태도가 필요하다.

9. 결론 - 오늘 적용 가능한 3가지

Spring AI Playground 같은 도구가 툴 검색·HITL·로컬 모델 지원을 한곳에 묶은 것은 우연이 아니라, 로컬 LLM 에이전트 개발에서 반복적으로 드러난 세 가지 벽에 대한 응답이라고 본다. 이번 주 바로 적용해볼 수 있는 것은 다음과 같다.

9.1 도구가 늘어나기 전에 검색·분류 체계부터 설계하라

나중에 도구 목록이 길어졌을 때 컨텍스트를 통째로 낭비하지 않으려면, 처음부터 이름과 설명을 검색 가능하게 써 두는 습관이 필요하다.

9.2 되돌리기 어려운 동작만 골라 승인 게이트를 두어라

모든 동작에 승인을 요구하면 금방 무뎌진다. 위험도 기준으로 먼저 나누고, 정말 위험한 지점에서만 사람이 개입하게 하라.

9.3 로컬 모델을 쓰기 전에 본인의 툴콜 시나리오로 직접 검증하라

모델마다 툴콜 안정성 편차가 크므로, 벤치마크 수치보다 본인 워크로드에서의 실측이 더 믿을 만한 근거다.
