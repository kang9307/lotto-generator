Where the Letter Sits Inside Its Box - Two Vertical Criteria for Choosing a UI Font

Cap-centered alignment and the x-height ratio - the real reason your button text never looks centered

Aug 31, 2026 Dev & Infra

Intro: Where did that one pixel come from

You build a button. You give it padding: 12px 16px and look at the screen. The label rides high. You drop padding-top to 11. Now it looks right. A few days later the same button gets a 14-pixel label, it is off again, and this time 11 is not the number you need.

Almost nobody on the team can say where that pixel came from. It gets filed under eyeballed it and everyone moves on. But this is not a matter of taste. It is a matter of numbers written inside the font file. Once you know those numbers you can pick a font that removes the correction entirely, and if you do not know them you will redo the same work every time the font changes.

What brings this up again is a piece on choosing UI typefaces. It covers what to look at when picking a replacement for Inter, and it names exactly two criteria. The first is cap-centered vertical metrics: the space inside the font's bounding box above the cap height should equal the space below the baseline. The second is a high x-height ratio: the lowercase should reach at least 70 percent of the cap height, ideally 75 percent.

The thing worth noticing is that neither criterion is about how the letters look. Not the strokes, not the curves, not the terminals. Both ask only where a glyph sits inside the box it has been handed, because in a UI that is the job the glyph is doing. To be clear up front: this piece does not recommend or disparage any typeface. Every font named below is attributed as what the source article says, not as a verdict of mine.

1. Every letter comes with a box

This concept has to be in place first or none of the rest works. A font file does not just hold glyph outlines. It carries a set of numbers called vertical metrics, and before the browser draws anything it uses those numbers to decide how tall the box is that the glyph will sit in.

The reference line is the baseline. Capitals and most lowercase letters rest on it. How far above it things reach is set by the ascender, how far below by the descender. A line gap is added on top as space between lines. Those three together give you the line height you get from line-height: normal.

The last two rows are the point. Cap height and x-height do not size the box. The box is set by the ascender and the descender, and the ink you actually see sits somewhere inside that. In other words, a glyph never fills its own box; it floats somewhere within it.

These values differ from font to font. That is exactly the starting problem MDN names when it documents the CSS that trims the box: different fonts have different base line-heights, so lines of text at the same font-size produce line boxes of differing heights. When swapping a font changes your button heights and your spacing, that is not a bug. That is this structure doing what it does.

2. The cap height is not in the middle of the box

Here is the crux. That a glyph floats inside its box is tolerable on its own. The problem is that it does not float evenly.

Why not? Fonts were built to set body text, and body text contains everything. The ascender has to accommodate the risers in b, d, k and l. The descender has to accommodate the tails in g, p and y. The box is sized to hold both extremes. UI labels are a different animal.

  • Labels are short. One or two words, unlikely to contain both an ascender and a descender
  • Labels are usually sentence case, capital on the first letter only — Save, Settings, Delete, Cancel
  • Labels with no descender at all are extremely common — Save, Cancel, Next, OK
  • In scripts like Korean or Chinese, nothing drops below the baseline to begin with

Put a descender-free label in that box and the entire descender region goes unused. Now apply align-items: center. What gets centered? The box. And if the box is centered, the glyphs sitting off-center inside it are not.

The eye does not see boxes. It sees ink. So the label reads as riding high and the gap beneath it looks too big. This is where a human intervenes, trimming padding-top and padding out padding-bottom. That is why designers set top and bottom padding to different values. The correction is not a preference; it is a person manually cancelling out the font's asymmetry.

This is why the source article puts cap-centered metrics first. When the space above the cap height matches the space below the baseline, a label starting with a capital lands optically centered on its own. The same article says the label then aligns precisely with an adjacent icon, and that in practice you get to drive both vertical paddings from a single token, which is far easier to maintain — no reaching into CSS for each font size.

What gets missed is why the corrections accumulate. Metrics are ratios. If the box is three percent asymmetric, that three percent grows with the size. A value tuned at 13 pixels is wrong at 20 and wrong again at 32. So the correction is never done once — it grows with the number of sizes you ship. Choosing a cap-centered font is choosing to delete that multiplication.

3. The x-height ratio - why words read as sitting low

The second criterion is the height of the lowercase. The source article puts x-height at at least 70 percent of the cap height, ideally 75 percent. It calls 75 percent the gold standard for interface typefaces and states that Inter, San Francisco and Innovator Grotesk all sit at that figure.

Why does this bite in UI specifically? Picture the shape of a label. A sentence-case word is a block with one bump at the top left. Every other letter tops out lower. If the lowercase is much shorter, that gap widens and a broad empty band opens above the word.

The eye reads that word as a single mass, and the mass is made by the lowercase, not the capital, because there are far more of them. Short lowercase means a smaller mass, and that smaller mass reads as sitting toward the bottom of the box. In the source article's terms, drop below 70 percent and there is too much empty space above the lowercase, so the eye reads the word as sitting low.

x-height / cap heightHow the word mass readsWhat happens in UI
Below 70 percentOnly capitals rise, the rest sits lowLabels read as sagging in their box
70 percent or aboveThe floor the source article namesEnters the range usable without correction
Around 75 percentThe mass approaches a solid rectangleThe figure that article calls the standard
Approaching 100 percentCap and lowercase heights convergeReads as unicase, word outline collapses

The last row is why this criterion has a ceiling. Bigger x-height is not simply better. The height difference between capitals and lowercase is a cue that builds the outline of a word, and erase it and the word becomes a uniform band of equal-height glyphs. In an interface where short labels have to be told apart at a glance, that is a loss.

The important part is that the two criteria need each other. Cap-centering establishes the reference point; a high x-height fills the space that remains inside it. A cap-centered font with short lowercase still gives you labels that read low. A generous x-height in an asymmetric box still gives you labels that ride high. Check one and you have left the other half in place.

4. Why the gap widens at small sizes

Metrics are ratios, but what reaches the screen is pixels. Rounding happens in between, and the smaller the absolute quantity, the larger rounding's share of it.

Take a 13-pixel label. The cap height lands around nine pixels. The difference between a font at 70 percent x-height and one at 75 percent is under half a pixel here — yet depending on which way the rounding falls, a whole pixel moves. Box asymmetry behaves the same way. Three percent of 13 pixels is 0.4 pixels, and that quantity does not disappear; it rounds somewhere.

  • The same font looks different at different sizes — at one size the rounding falls favourably and it looks right, at another it falls the other way and it looks wrong
  • One pixel does not weigh the same everywhere — it is two percent of a 48-pixel heading and close to eight percent of a 13-pixel label
  • This is the state a designer means by only this size looks off. The font is not broken; the rounding went the wrong way at that size
  • Scaling shifts it again, so a correction tuned at one size proves nothing — browser zoom or a high-density display moves the rounding boundary, which is why every shipping size has to be checked

A different problem often gets mixed in here: thin strokes vanishing at small sizes, counters filling in, pairs like Il1 and O0 collapsing into each other. That is a question of glyph shape, a separate axis from the glyph position question this piece is about. The shape side — stroke contrast, counters, confusable pairs, tabular figures — is covered in How to Choose a Body Text Typeface.

5. Buttons, tabs and inputs - optical alignment inside the box

Saying that the geometric centre differs from the optical centre sounds abstract, but how it surfaces per component is quite concrete.

Buttons

  • Most labels have no descender, so the ink clusters toward the top of the box
  • The bottom padding therefore reads as larger, and the manual correction starts here
  • Put an icon-only button beside a text button and the heights match while the contents inside align on different references
  • Whether you fix the button height or build it from padding changes how the misalignment expresses itself

Tabs and menus

  • Items differ in whether they contain a descender — of Home, Settings and Payments, only the latter two do
  • This is where only the items with descenders appear to sag under identical CSS
  • In a menu mixing scripts, the discrepancy widens further
  • Bolding only the selected tab moves the ink's centre of mass, so the alignment reads as off again

Inputs

  • Placeholder and entered value must occupy the same position, but a fallback puts them on different font metrics
  • That is the cause behind text shifting fractionally the moment a value is typed
  • Stack label, input and helper text and each box's slack accumulates, opening the spacing beyond what you specified

How you push the text around matters too. Pushing with line-height cannot correct asymmetry, because the added leading is split equally above and below. Moving an already-offset glyph toward centre requires adding to one side only, and this method cannot. Pushing with padding can correct it, but you redo it whenever the font changes, and as the previous section showed, the value differs per size. Neither method removes the cause.

6. When an icon sits beside a word

Putting an icon next to text is the most common arrangement in interface work, and it is where the two aligning on different references becomes impossible to ignore.

An icon is usually drawn inside a square with its visual weight at the centre of that square. A glyph is not. A glyph rests on a baseline and sits high inside its box. Place two objects with different references on one line, use only one of those references, and of course they disagree.

  • vertical-align: middle aligns the icon's centre with the text's middle, where the text's middle means the baseline plus half the x-height. Since x-height varies by font, identical CSS gives different results per font
  • Switch to flex with align-items: center and now the boxes get aligned. Whatever offset the glyph has inside its box survives untouched
  • Icon fonts are treated as glyphs and rest on the baseline, so they inherit the font's metrics. Inline SVG does not. Mix them and you are maintaining two alignment rules
  • Match an icon's size to the type size and the icon looks bigger, because the glyph does not fill its box while the icon fills its own
  • Hence icons are usually set slightly smaller, or carry built-in padding as an optical correction

This is the context for the source article's claim that cap-centered metrics let a label align precisely with the icon beside it. When the glyph is centred inside its box, aligning boxes and aligning glyphs become the same operation, and align-items: center is the whole solution. In an asymmetric font they are different operations, which is how you end up hand-writing margin-top per icon.

7. What text-box-trim fixes and what it does not

CSS now has a property aimed squarely at this: trim the slack above and below the glyphs out of the box.

Per MDN, text-box-trim specifies which of the over and under edges of a text element's block container to trim. How much to trim is text-box-edge, and the shorthand that sets both at once is text-box.

PropertyWhat it decidesValues
text-box-trimWhich edge gets trimmednone · trim-start · trim-end · trim-both
text-box-edge (over)How far to trim the toptext · cap · ex · ideographic · ideographic-ink
text-box-edge (under)How far to trim the bottomtext · alphabetic · ideographic · ideographic-ink
text-boxBoth at oncenormal, or a trim value plus an edge value

MDN's own example maps onto this article's subject exactly. text-box: trim-both cap alphabetic trims the over edge to the capitals and the under edge to the baseline. The box shrinks to run from cap height down to baseline and the slack is gone. In the shorthand, omitting the trim value defaults to trim-both and omitting the edge value defaults to auto, while normal is equivalent to none auto.

What this fixes is clear. With the slack trimmed, padding lands directly against the ink. Twelve pixels of padding becomes twelve actual pixels, and the value keeps its meaning when the font changes. One token can drive both sides, and the per-size correction disappears. It removes the cause identified in section 2.

What it does not fix matters more.

  • The x-height does not change. Trim the box to the cap height and a font with short lowercase still produces words that read low. The section 3 problem is a proportion inside the font that CSS cannot reach
  • Descenders leave the box. Trimming the under edge to alphabetic cuts at the baseline, so g, p and y fall outside. If a background or border follows the box, the letters look like they are spilling out. Choosing text instead of alphabetic for the under edge is that trade
  • A Latin baseline does not suit CJK. Which is exactly why ideographic and ideographic-ink exist as separate values — the subject of the next section
  • It does not choose the font for you. What it trims is the box, not the glyphs

Support is worth dating carefully. The source article reports global usage on caniuse at about 79 percent, with Chrome, Edge, Safari and iOS Safari supporting it and Firefox not, which it says keeps the feature out of Baseline; on that basis it recommends sticking with fonts that already have cap-centered metrics. MDN, meanwhile, marks text-box-trim, text-box-edge and text-box alike as Baseline 2026, newly available, stating that since August 2026 the feature works across the latest devices and browser versions.

The two statements are dated differently. And Baseline's newly available means it works in current releases, not that every visitor is on a current release. In practice, keep the padding-based defaults underneath and layer this on top so nothing collapses without it. Either way, there is no state in which sections 2 and 3 stop mattering.

8. Where the boxes drift apart in multilingual UI

Everything so far assumes the Latin alphabet. Bring in Hangul, kana or Han characters and the reference itself changes.

Latin glyphs rest on a baseline with ascender and descender defining the box. Han characters and kana fill a square area almost completely and have essentially nothing below the baseline. Hangul behaves the same way. Trim a box against cap height and baseline and CJK glyphs land somewhere else entirely. That text-box-edge carries separate ideographic and ideographic-ink values is that fact written into the specification.

  • Switch languages and the same button's label shifts subtly up or down
  • Put Save and its translation on one screen and the two sit at different heights
  • Digits and symbols often come from the Latin font, so numerals embedded in a CJK label can drift on their own

Layer font fallback on top and it compounds, but that axis — mismatched sizes, weights and vertical spacing, and fallback happening silently — is already covered in How to Choose a Body Text Typeface. The typesetting side, line breaking and prohibition rules, is in What It Takes to Square Off a Line.

9. A procedure - sit the font in a real button

Turning all of this into a selection procedure gives the following. You cannot judge this axis from a specimen screen. You have to sit the font in a real button and measure.

  1. Decide what you are measuring. Not the font's name — the ratio between the space above the cap height and the space below the baseline
  2. Build one button. Give top and bottom padding the same value. Adding no correction is the entire point
  3. Run three kinds of label through it. One without a descender, one with, one that is only digits
  4. Measure the space above and below the ink, in pixels. Not the box the developer tools draw — the extent the glyphs actually occupy. Measure the box and it always comes out symmetric
  5. Repeat at every size you ship. 12, 13, 14, 16 pixels. Matching at one size is not evidence
  6. Measure the x-height ratio. Set a capital X and a lowercase x at the same size, measure both, divide
  7. Put it next to an icon and look again. Icon alignment is its own check
  8. Rebuild the screen with real labels in every language you ship. Translated labels differ in length and in reference
  9. Then choose. By this point few candidates are left standing

A workable threshold: if the top and bottom gaps differ by no more than one pixel at the smallest size you ship, the font can go in without correction. If the gap is wider you have three options. Split the vertical padding into separate tokens and manage them per size; trim the box in CSS with a fallback underneath; or change candidates. Which one is right is decided by how many sizes you ship. With two or three sizes, separate tokens are cheap. With many sizes and room to change the font, solving it at the font is cheaper.

Conclusion: measure before you choose

Choosing a UI typeface is not choosing how letters look. It is choosing where letters sit inside a box. Which is why a large specimen tells you nothing, and why the judgment has to be made by measuring gaps in a real button at real size.

The two criteria are not independent. Cap-centering sets the reference point and the x-height ratio fills what is inside it. Satisfy one and the other half of the misalignment survives intact.

Manual correction is not free either. Because metrics are ratios, the error grows with the size, so a value tuned once is wrong at the next size. The work multiplies as the size scale grows. The CSS that trims the box removes the box half of the cause while leaving the glyph proportions alone, so it does not retire the job of choosing a font.

Go back to the source and the two criteria read differently. They are not conditions for an attractive typeface but conditions for maintaining a system on one padding token. Select on that axis and the field narrows fast — and among what remains, it is hard to choose badly.

What could not be verified

Collected in one place, the parts not backed by a source.

  • The exact field layout of vertical metrics in a font file — a file carries more than one set of these values and platforms differ in which they read, but the field names and their precedence were not verified here. This piece goes only as far as the outcome: boxes come out differently per font
  • Per-browser version numbers — MDN states only Baseline 2026 and August 2026 for the text-box family, and specific browser versions were not checked. The source article and MDN diverge on Firefox support, and both are reported above with their dates attached
  • The basis for the 70 and 75 percent figures — these are the criteria the source article presents for interface typefaces and are attributed as such. Whether studies measuring reading or targeting performance support them was not verified
  • The pixel figures used here — they are assumed values illustrating how a ratio surfaces at small sizes, not measurements of any typeface. The one-pixel threshold is likewise a starting point, not a validated limit
  • The actual metrics of individual typefaces — whether a given font is cap-centered can only be known by opening the file and measuring, and this piece makes no such ruling. Every font named above is attributed to the source article
