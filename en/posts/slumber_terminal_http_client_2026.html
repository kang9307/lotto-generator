Slumber - A Recipe-Driven Terminal HTTP/REST Client and Postman Alternative 2026

Define requests as YAML and run them from the terminal: a lightweight, Git-friendly API client

Jun 11, 2026 Tech & IT

Introduction: Another Way to Work with APIs

Tools for calling APIs already abound. There are heavyweight GUI platforms like Postman and Insomnia, the one-liner king curl, and the human-friendly favorite HTTPie. Yet in June 2026 another option started circulating in developer communities: Slumber. It is a terminal-based HTTP/REST client written in Rust, and its defining trait is that you define requests as YAML recipes.

"Why do we need yet another HTTP client?" is a fair question. This article calmly identifies the gap Slumber fills. The short version: Slumber's core value is not speed or pretty output, but a workflow that treats requests like code. It targets the middle ground - not trapped inside a GUI, yet not forcing you to hand-assemble long curl commands every time. According to its documentation, Slumber's goal is to be an HTTP client that is "easy to use, configurable, and sharable."

1. What Is a Terminal HTTP Client?

Let us define terms first. A terminal HTTP client builds and sends HTTP requests with the keyboard and text, rather than a graphical screen you click with a mouse. There are two broad flavors:

  • CLI (command-line interface): You send a request with a single command, like curl https://api.example.com/users. Great for scripting and automation.
  • TUI (terminal user interface): An interactive screen with menus, panels, and lists, running inside the terminal. It blends the convenience of a GUI with the lightness of the terminal.

Slumber is interesting because it offers both. Use the TUI to interactively explore requests and inspect responses; use the CLI to call requests automatically from scripts or CI. It is even available as a Python package, so you can invoke it directly from code. A single collection (a group of requests) shared by three interfaces is Slumber's identity.

2. Slumber's Core Concepts - Collection, Recipe, Profile

The fastest way to understand Slumber is to grasp three concepts.

  • Collection: A group of request recipes, usually held in a single slumber.yml file. It is the unit you commit alongside your project repository.
  • Recipe: A template for an individual request to run. It defines the method, URL, headers, body, and query. Each request - "list users," "create order" - is one recipe.
  • Profile: A set of per-environment variables. It lets you switch easily between environments such as local, staging, and production, where hosts or tokens differ.

When these three mesh, you can write one set of recipes and reuse the same requests across multiple environments simply by switching profiles. The environment-variable management you did through screens in GUI tools, Slumber handles in text files.

The separation of concerns here is cleaner than it first appears. Recipes describe what a request is - its shape, its method, its body structure - and that shape rarely changes between environments. Profiles describe where the request goes and with what credentials, which is precisely the part that does change. By keeping these two axes orthogonal, Slumber lets you point the identical recipe at a local mock server, a shared staging cluster, and production without copying, pasting, or editing the request itself. You change one word - the profile name - and the whole collection retargets.

3. Building Your First Collection - A slumber.yml Example

Seeing beats describing. Here is a simple collection based on the official documentation, working with a fictional "fish" API.

# slumber.yml
profiles:
  local:
    data:
      host: http://localhost:5000
  production:
    data:
      host: https://myfishes.fish

requests:
  list_fish:
    method: GET
    url: "{{ host }}/fishes"
    query:
      big: true

  create_fish:
    method: POST
    url: "{{ host }}/fishes"
    body:
      type: json
      data: { "kind": "barracuda", "name": "Jimmy" }

The intent is clear at a glance. Under profiles, local and production each define a different host variable. The recipes under requests reference that variable through the {{ host }} template. Switch the profile and the same list_fish request hops between local and production. Compared with a single curl line full of long headers and messy quote escaping, the structure is immediately legible.

4. TUI and CLI - Two Ways to Use It

Once you have a collection, it is time to run it. Slumber offers two modes.

4.1 TUI: Interactive Exploration

Run slumber in the directory that contains your collection, and the TUI appears. In an interactive screen - typically a recipe list on the left, request details in the middle, and the response on the right - you pick a request with the keyboard, send it, and inspect the response right away. Response browsing has built-in JSONPath selectors, so you can filter just the fields you want from a large JSON response, much like jq.

4.2 CLI: Scripting and Automation

When you do not need interactivity, run it straight from the CLI - for instance, sending a specific recipe non-interactively.

# Create a new collection
slumber new

# Launch the TUI (uses slumber.yml in the current directory)
slumber

# Run a specific recipe via the CLI (with a profile)
slumber request list_fish --profile production

Thanks to the CLI mode, you can slot Slumber requests into shell scripts or CI steps. You can capture the response on standard output and pipe it into another command - the classic Unix-style composition. (The exact form of command names and options may vary by version, so check with slumber --help.)

The deeper point is that the TUI and the CLI are not two separate programs that happen to share a name. They operate on the very same collection file. A request you craft and debug interactively in the TUI today is, without any conversion step, the request a CI job fires non-interactively tomorrow. This single-source design eliminates the all-too-common drift where a GUI tool holds one version of a request and an automation script holds a slightly different, hand-copied version that silently rots out of sync. With Slumber, there is one definition, and everything reads from it.

5. Dynamic Requests - Templates, Files, Shell, Previous Responses

Where Slumber moves beyond a mere "static request store" is dynamic request construction. According to its introduction, Slumber assembles requests dynamically from the following sources.

  • Template variables: Inject profile data, as with {{ host }}.
  • Files: Pull external file contents into a body or header. Useful for large payloads or values like certificates.
  • Shell commands: Use a shell command's output as a value. For example, call a token generator and place its result in a header.
  • Previous responses: Extract a value from an earlier request's response and pass it to the next request. Chains like login -> obtain token -> authenticated request become possible.
  • Prompts: Ask the user for a value at run time.

This "pull a value from a previous response" capability is especially powerful in practice. When working with an API that requires authentication, you can bake into a recipe the flow that extracts a token from a login response and automatically inserts it into subsequent request headers. What you did in Postman with "environment variables plus test scripts," Slumber expresses as declarative configuration.

It is worth dwelling on why declarative chaining matters. In a GUI tool, the logic that grabs a token and stashes it in a variable usually lives in an imperative test script attached to the request - a little snippet of JavaScript that runs after the response arrives. That snippet is invisible until you open the request and scroll to the right tab, and it is easy to break when someone tweaks the response shape. In Slumber, the dependency is written in the open, in the same YAML, as data. Anyone reading the collection can see that get_user depends on the token produced by login. The relationship is reviewable in a diff and reproducible by anyone who clones the repository, with no hidden setup steps to remember.

6. Git-Friendly - Treating Configuration as Code

Slumber's philosophy in one phrase is "source-first configuration." Because all configuration and data live as local, plain-text YAML, the following benefits follow naturally.

  • Version control: Commit slumber.yml to Git and the change history of your API requests lives alongside your code history. You can trace who changed an endpoint and when with git blame.
  • Code review: Adding a new endpoint or changing a request can be reviewed as a diff in a PR - impossible with GUI clicks.
  • Sharing: A teammate who clones the repository uses the same collection immediately, with no separate account or cloud sync.
  • Reuse: Copy or reference recipes across projects to reuse standard requests.
When an API client's configuration lives inside the repository rather than behind a cloud account, that configuration finally becomes part of the codebase.

This squarely solves the subtle discomfort of heavyweight GUI tools - the problem of configuration trapped inside the tool and never synced with the team.

7. Importing from Other Formats - Insomnia, OpenAPI, and More

If you already have collections built with other tools, you need not start over. According to its introduction, Slumber supports importing several external formats.

  • Insomnia collections
  • OpenAPI specifications
  • VSCode .rest files
  • JetBrains .http collections

OpenAPI import in particular is significant. If you have a well-defined API specification, you can use it as a starting point to generate Slumber recipes - moving existing assets into a new workflow without discarding them.

8. Comparison with Postman, Insomnia, curl, and HTTPie

Now for the real comparison. Let us place Slumber among the other tools.

Tool Interface Configuration Strength Weakness
Slumber TUI + CLI YAML files Lightweight, Git-friendly, env switching Relatively new, no GUI collaboration
Postman GUI Cloud/account Rich collaboration, testing, monitoring Heavy, account-bound, weak version control
Insomnia GUI GUI/files Clean UI, plugins Still GUI-centric
curl CLI Command args Ubiquitous, ad-hoc calls Cumbersome for repetition and structure
HTTPie CLI Command args Human-readable output Weak at collection/environment management

The table shows the competition is not one-to-one. Slumber does not fully replace curl; for a request you fire once and forget, curl is still faster. Nor does it replace Postman's platform features like team collaboration, monitoring, or mock servers. The spot Slumber targets precisely is the daily workflow of a developer who repeatedly works with many endpoints but does not want to carry the weight of a GUI platform.

9. The Relationship Between curl Commands and Recipes

Notably, Slumber recipes and curl commands are complementary rather than opposed. Writing the same request both ways makes the difference clear.

# A curl one-liner (good for ad-hoc calls)
curl -X POST https://myfishes.fish/fishes \
  -H "Content-Type: application/json" \
  -d '{"kind":"barracuda","name":"Jimmy"}'

The curl command above is fast, but the moment headers grow and you have several environments, managing it by hand becomes tedious. Solidify the same request as a Slumber recipe and environment switching and re-running become clean. In practice, a tool like our curl command builder works well for quickly assembling a one-off request, after which you move only the requests you reuse into a Slumber collection. Ad-hoc assembly goes to the builder and curl; repetition and structure go to Slumber.

10. Use Cases - API Testing, CI, Documentation

Here are the scenes where Slumber truly shines.

10.1 Everyday API Debugging

While poking at an API you are developing, pick recipe-defined requests in the TUI, send them, and inspect responses with JSONPath. Friendlier than curl, lighter than Postman.

10.2 CI Regression and Smoke Tests

Run the same YAML collection from the CLI in CI to verify that key endpoints are alive after a deploy. Reusing the very request definitions you used during development for verification is a major advantage.

10.3 Living API Documentation

The slumber.yml itself becomes executable documentation of "how to call this API." Unlike the frozen curl examples in a README, recipes in the repository are actually executed, so they are far less likely to go stale.

10.4 Script Integration

Call slumber request from a shell script and pass the result to downstream processing. Combined with dynamic requests, complex flows like token issuance and chaining can be automated in scripts.

Across all four of these scenarios runs a single thread: the same collection serves debugging, testing, documentation, and automation. You are not maintaining a Postman workspace for exploration, a separate bash script for CI, and a stale README for documentation, each drifting independently. There is one slumber.yml, and each context reads what it needs from it. That consolidation is where the everyday time savings actually come from - not from any single feature, but from removing the friction of keeping multiple representations of the same requests in agreement.

11. Limitations and Caveats

For balance, let us be clear about the shadows. Slumber is not a silver bullet.

  • Maturity: According to its own notes, Slumber is a relatively new tool whose features are not yet fully complete. The details of commands and configuration may change between versions, so treat the official documentation as the source of truth.
  • No GUI collaboration: There are no Postman-style team workspaces, mock servers, monitoring, or visual test runners. If you collaborate with non-developers or share with non-technical stakeholders, a GUI tool fits better.
  • Learning curve: If you are not comfortable with YAML and the terminal, the initial ramp can be steeper than a GUI. But once learned, it pays back on repetitive work.
  • The right niche: One-off one-liners are better with curl/HTTPie, and a large collaboration platform is better with Postman. Slumber is best in between - for "repeated API workflows treated like code."

12. Conclusion + Three Things to Try Now

Slumber in one sentence: "a lightweight, sharable terminal HTTP client that defines requests as YAML recipes, manages them with Git, and runs them via TUI and CLI." If you need rich GUI collaboration, Postman is better; for a quick one-liner, curl is better; but if you want to treat repetitive API workflows like code in between those two, Slumber is a very reasonable choice.

Let us close with three things you can try right away.

  1. Move three of your frequent requests into recipes. Pick the three most-repeated curl commands you type by hand and write them into a slumber.yml. One small collection changes how the workflow feels.
  2. Separate environments into profiles. Splitting local, staging, and production hosts into profiles structurally prevents the mistake of confusing environments and firing a request at the wrong server.
  3. Commit the collection to your repository. Commit slumber.yml alongside your code and the way you call the API becomes living documentation, while teammates reproduce the same requests just by cloning.

One final message: good tools tend not to add new features so much as move scattered work to the right place. Slumber returns API request configuration - long trapped inside a GUI - back to the repository, that is, to where code lives. If you enjoy the terminal and want to treat configuration like code, it is worth a serious try.
