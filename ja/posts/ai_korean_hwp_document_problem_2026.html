AIツールで韓国公文書HWPが開けない本当の理由と解決策

30年間蓄積されたバイナリ独自フォーマットのロックイン構造、HWPX移行の本当の意味、そして今すぐ使える開発者・ユーザー向け解決策 — 2026年6月時点

2026-06-21 開発・インフラ

序文：AIが読めない大韓民国の公文書

2026年6月時点、韓国はひとつの逆説を抱えている。スマートフォン普及率は世界最高水準で、開発者たちはAIネイティブな製品を次々とリリースし、政府はAI転換戦略を宣言している。それにもかかわらず、2025年の調査では政府公文書の91.1%がHWPまたはスキャンPDF形式で流通していると報告された。この2つのフォーマットは、標準的なAIテキスト処理パイプラインと根本的に相容れない。

これは単に「韓国のソフトウェアが遅れている」という話ではない。なぜこの状況が30年以上続いてきたのかを正しく理解するには、フォーマット自体の技術設計から、行政調達の慣性、政治経済的背景まで一緒に見なければならない。また、政府が進めているHWPX移行が本当の解決策なのか、それとも別の限界を内包しているのかも冷静に評価する必要がある。

本稿では、問題の根本から現在の実践的解決策まで分析する。ただし、噂やマーケティング資料を転載するのではなく、フォーマット仕様、政府発表、オープンソースパーシングライブラリの実態を直接確認した内容を基に記述する。

1. HWPとは何か、なぜ互換性がないのか

1.1 HWPの技術的構造

HWP（Hangul Word Processor）は1989年にハングルとコンピュータが開発したワードプロセッサ「ハングル」の専用ファイルフォーマットだ。旧来の.hwpファイル（HWP5以下）はバイナリ独自フォーマットである。具体的にはMicrosoft Compound Document File Format（OLE2）ベースの複合文書構造を使っており、内部ストリームの配置とエンコーディング方式が公開された国際標準なしに独自設計されている。

結果として、このファイルを開いて編集し、再び.hwpとして保存するには事実上ハンコムオフィスを購入しなければならない。LibreOfficeやMS WordがHWPをある程度読めるが、レイアウト崩れや特殊機能の欠落が頻繁に起きる。外部パーサーはさらに難しい。pyhwpのようなオープンソースライブラリがHWP5をパースするが、全内部ストリームを完全に解釈はできない。AIが直接バイト単位でファイルを受け取ってテキストを抽出するのは現実的にほぼ不可能だ。

1.2 なぜAIツールが読めないのか

ChatGPT・Claude・GeminiなどのLLMサービスは文書処理に標準化されたパーシング経路を使う。PDFはテキストレイヤー抽出、DOCXはXML展開、TXTは直接読み込み。HWPはいずれにも当てはまらない。ネイティブパーサーがなければ、ファイルを受け取っても内容を取り出す手段がない。

2026年6月時点では、ChatGPTが2026年4月にHWP・HWPXの正式サポートを発表し、Geminiは2024年後半からサポート済みだ。一方、ClaudeとCopilotはまだネイティブサポートがない。この不均衡は、フォーマット自体の複雑さがいかに大きな障壁であるかを示している。

2. 30年間のロックイン形成の構造的理由

2.1 歴史的起源：ハングル処理が生き残らせた

1989年の登場時、ハングルはMS WordやWordPerfectが正確に処理できなかった韓国語の字母結合と縦書きを完璧に扱えた。初声・中声・終声の分離入力方式とハングル特化のレイアウトエンジンは当時唯一の選択肢だった。教育省や政府省庁がハングルを標準ワードプロセッサとして採用したのは技術的に合理的な判断だった。

問題はその後に生じた。1990年代のMSオフィスの世界的普及の中でも、韓国の公共・教育システムはハングルを維持した。数十年分の公文書がHWPに蓄積され、既存文書を開くにはハングルが必要で、ハングルを使うから新文書もHWPで作るという循環が固定化された。

2.2 政府調達と標準の逆説

2007年、政府は国家標準をオープンドキュメント（KS X ISO IEC 26300 ODF）に公式転換した。しかし実際の行政現場ではほとんど変化がなかった。標準は標準、現場は現場だった。オンナラシステムや各地方自治体の電子文書システムがHWPを基盤に構築されており、それを一括で変更するコストと抵抗があまりにも大きかった。

これは単なる技術問題ではない。調達経路の慣性だ。ハンコムオフィスのライセンスが政府調達リストの固定項目となり、年間更新が予算計画に組み込まれた。代替案を導入するには既存予算項目を削除して新項目を追加する行政手続きが必要だ。技術的選択ではなく調達慣性がロックインを維持した核心だ。

2.3 互換ツール不在の悪循環

LibreOfficeのHWP読み込みサポートは不完全だ。表や特殊記号、ハングル固有の段組みレイアウトが崩れる。ユーザーがLibreOfficeでHWPを開いてレイアウトが壊れる経験をすると、結局ハンコムオフィスに戻る。この失敗体験の繰り返しが「どうせハングルを使うしかない」という認識を固める。互換ツールが不完全だからロックインが続き、ロックインが続くから互換ツール開発の商業的誘因も弱い。典型的な悪循環だ。

3. HWPXとは何か、なぜ移行が重要なのか

3.1 HWPXの技術構造

HWPXは2010年頃からハンコムがサポートを始めた新しいフォーマットだ。韓国国家標準KS X 6101として2014年に指定され、内部はOWPML（Open Word Processor Markup Language）仕様に従うXMLファイルをZIPでまとめたパッケージだ。拡張子を.zipに変えれば、アーカイブツールで内部XMLを直接参照できる。

この構造はDOCX(.docx = ZIP + XML)やODF(.odt = ZIP + XML)と技術的に同じアプローチだ。AIや自動化ツールの観点から見ると、これは決定的な違いだ。XMLをパースできるライブラリはどの言語にも存在する。python-hwpx（Apache 2.0）のようなライブラリがHancom Officeなしにhwpxを読み込み・編集・Markdownに変換できるのも、このオープン構造のおかげだ。

3.2 2026年政府移行政策

2026年の政策変更は実質的だ。2026年5月18日から行安部のオンナラシステムで.hwpファイルの添付が制限された。中央省庁と地方政府のオンナラシステムに開放型文書（hwpx）の適用が拡大されており、公務員メールシステム「オンメール」では2026年10月までhwpx移行が完了する予定だ。国家AI戦略委員会が行安部・文体部と合同で全面義務化を宣言したのは今回が初めてだ。

この政策の核心的な動力はAI活用だ。HWPX形式の公文書はAIがパース・インデックス・要約・検索できるパイプラインが開かれる。単なるフォーマット交換ではなく、公共AIインフラの基盤整備として捉えるべきだ。

3.3 HWPX移行の限界

しかしHWPXは万能の解決策ではない。いくつかの限界を指摘する必要がある。

第一にレガシーHWPファイルの山だ。数十年間蓄積された旧型HWP文書は移行政策と無関係に残る。2010年以前の文書、地方機関の古い公文書、学校配布資料の多くは依然として旧型HWPだ。これをHWPXに一括変換する作業は別途の大規模プロジェクトが必要だ。

第二にHWPXはODFではないという点だ。HWPXはオープンXMLフォーマットだが、ODF（オープンドキュメント）のような国際標準ではない。LibreOffice・Google Docs・MS WordなどのグローバルツールがHWPXをネイティブサポートしていない理由だ。海外開発者がHWPXをパースするには依然として別途ライブラリが必要だ。

第三に民間・海外受信者の問題だ。政府機関が民間企業や海外機関にHWPXファイルを送った場合、受け取る側にHWPXを開くツールがなければ問題が再発する。国内公共システム内でのみ通じる標準は半解決策だ。

4. AI時代にHWP互換性問題がより深刻な理由

4.1 RAGパイプラインと死んだ情報

企業と公共機関がLLMを内部文書検索に活用するRAG（Retrieval-Augmented Generation）パイプラインが急速に普及している。文書をエンベディングしてベクターDBにインデックスするこのプロセスはテキスト抽出が前提だ。HWPがテキスト抽出を阻害すれば、数十年分の公文書がRAGから完全に排除される。情報はあるがAIが使えない死んだ情報になる。

4.2 自動化ワークフローの断絶

現代の業務自動化はドキュメントをパイプラインの入力として扱う。N8N・Zapier・Makeのようなワークフローツールが文書を受け取りAIで要約して次のステップに渡す流れが一般化した。HWPファイルがこのパイプラインに入ってきた瞬間、パイプラインが断絶する。公共文書処理の自動化を試みる開発者が最初にHWPの壁に当たる理由だ。

4.3 アクセシビリティの問題：Mac・Linux・海外ユーザー

ハンコムオフィスは基本的にWindows中心だ。macOSバージョンはあるが機能差が大きく、Linux用は事実上存在しない。Macを使う開発者、Linuxサーバー環境、海外パートナー機関はHWPファイルを受け取ると、開くために別途の作業が必要になる。2026年に「このファイルを開くには特定の有料ソフトウェアをインストールする必要がある」という要求はアクセシビリティの設計失敗に近い。

5. 開発者・ユーザー向け実践的解決策（2026年6月時点）

5.1 ClaudeにHWPを読ませる方法：HWP-MCP

Claude DesktopやClaude CodeにHWP-MCPサーバーを接続すると、1行インストールでHWP・HWPXファイルをClaudeが直接読み込む。Hancomライセンス不要でMacとWindowsの両方で動作し、ローカルで実行されるため文書が外部サーバーに送られない。MCP（Model Context Protocol）標準ベースのため、Claude Code・Claude Desktop・Cursor・VS Code Copilot・ChatGPTアプリなどMCPをサポートする環境で同一に動作する。

このアプローチの利点はワークフロー統合だ。Claudeがhwp_readツールを自動的に呼び出して結果をテーブル形式で返すので、ユーザーは変換プロセスを意識する必要がない。企業の閉鎖ネットワーク環境でも外部API露出なしにオンプレミス展開が可能だ。

5.2 Pythonパイプライン構成：pyhwp・python-hwpx・kordoc

独自の文書処理パイプラインを構築する開発者には3つのライブラリが主要な選択肢だ。

  • pyhwp（PyPI, GNU AGPL）：HWP5（旧バイナリ）パーサー。実験的にODFまたはテキストへの変換が可能。古い公文書の一括処理に有用。
  • python-hwpx（GitHub: airmang/python-hwpx, Apache 2.0）：純Python製HWPXパーサー。Markdown（プレーン・書式保存モード両方）への変換、フォーム記入、テンプレート分析をサポート。Hancom Office完全不要。
  • kordoc（GitHub: chrisryugj/kordoc）：HWP3・HWP・HWPX・HWPML・PDF・XLS・XLSX・DOCXをMarkdownに変換するCLIとMCPサーバー統合のオールインワンパーサー。新旧対照・フォーム自動記入もサポート。

これらのライブラリで構成するパイプラインパターンはシンプルだ：HWP/HWPXファイル受信 → Markdown変換 → LLMにテキスト投入 → 結果後処理。MarkdownはどのLLMでも消化できるため、モデル依存性がない。

6. フォーマット比較：HWPXの位置づけ

フォーマットコンテナ公開仕様国際標準グローバルツール対応AIパーシング
HWP（旧）OLE2バイナリ非公開なし限定的非常に困難
HWPXZIP + XMLOWPML（KS X 6101）国内のみ限定的ライブラリで可能
DOCXZIP + XMLOOXML（ISO 29500）国際ISO広範容易
ODTZIP + XMLODF（ISO 26300）国際ISO広範容易

HWPXは旧来のHWPよりはるかに優れているが、DOCXやODTのように国際標準化・グローバルツール対応が実現していない中間段階に位置している。

7. 本当の解決策とは何か

短期（今すぐ）：HWP-MCP・kordoc・python-hwpxなどのパーサーレイヤーをLLMパイプラインに組み込めば即座に互換性を確保できる。完璧ではないが実用的だ。

中期（HWPX移行完了後）：オンナラシステムの移行が完了すれば新規公文書はHWPXで流通する。python-hwpxレベルのパイプラインで大部分の文書を処理できるようになる。しかしレガシーHWPの変換作業なしには過去の文書が依然として排除される。

長期（根本的解決）：国際標準フォーマット（DOCXまたはODT）を公共文書の配布・保存標準として追加指定するのが最も根本的だ。HWPXは内部作成フォーマットとして許可しながら、対外配布・長期保存・AI処理用途にはPDF・DOCX・ODTを並行採用するデュアル標準政策が現実的な方向だ。

8. 結論：今できることから始める

2026年6月時点、状況は2年前より明らかに改善した。政府がHWPX移行を強制し、ChatGPTのHWPネイティブサポートが実現し、HWP-MCPのようなオープンソースブリッジツールが実用化された。しかし構造的問題は完全には解消されていない。レガシーHWPの山、グローバルツールのHWPX未対応、国際標準との乖離が依然として残る。

開発者なら今すぐkordocまたはHWP-MCPをパイプラインに組み込んで実験せよ。政策担当者なら内部標準としてHWPXを固めながら、同時にDOCX・ODTの並行外部配布を検討する時期だ。この問題は30年の慣性が生み出したが、解法は今始めることができる。
