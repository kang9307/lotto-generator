Project Valhalla — 10년의 작업이 JDK 28에 어떻게 반영되었나

값 클래스·스칼라화·힙 플래트닝이 자바의 객체 오버헤드를 해체한다 — 무엇이 바뀌고 개발자에게 무엇을 의미하는가

2026-06-22 개발/인프라

서론: 30년 된 가정을 바꾸는 일

2026년 6월 기준, 자바 역사상 가장 오래된 미완의 프로젝트 하나가 마침내 메인라인에 합류했다. Project Valhalla다. 2014년 Brian Goetz가 제안한 이 프로젝트는 12년의 시간을 거쳐 JDK 28에서 JEP 401(Value Classes and Objects)로 프리뷰 반영됐다. 코드 약 197,000줄, 설계 반복 수십 번 — 왜 이렇게 오래 걸렸고, 그 결과가 무엇인지, 그리고 자바 개발자에게 실질적으로 무엇을 가져오는지를 정직하게 분석한다.

먼저 이 글의 범위를 분명히 한다. JDK 28은 2026~2027년 릴리스 계획(보도·OpenJDK 공개 정보 기준)으로, 이 글은 출시 확정 사실이 아닌 계획·프리뷰 상태를 다룬다. 성능 수치는 보고된 벤치마크를 인용하되, 실제 워크로드에서 결과는 다를 수 있음을 전제로 한다.

1. 왜 10년이 걸렸나 — 자바의 정체성 위기

자바는 1995년 탄생 이래 하나의 근본 가정 위에 서 있었다. "모든 객체는 정체성(identity)을 가진다." 정체성이란 두 객체가 같은 값을 담고 있어도 힙 주소가 다르면 서로 다른 존재라는 뜻이다. == 연산자가 주소를 비교하고, synchronized가 객체 인스턴스를 잠그고, System.identityHashCode()가 의미를 갖는 것이 모두 이 가정 위에서다.

이 가정은 자연스럽게 비용을 낳는다. 모든 객체는 최소 12~16바이트의 헤더를 가진다. x·y 좌표를 담는 Point 객체는 필드 값 8바이트 외에 헤더 16바이트를 더 지불한다. 메모리 점유율이 두 배 이상이다. 더 심각한 것은 간접 참조다. ArrayList<Point>는 Point를 직접 담지 않는다. Point 객체를 가리키는 포인터 배열을 담는다. CPU가 Point의 x에 접근하려면 배열 → 포인터 → Point 객체 → 필드로 두 번의 메모리 간접 참조를 거친다. 캐시 미스가 불가피하고, 수백만 건 이상의 루프에서 이 비용은 누적된다.

Brian Goetz는 이 문제를 "자바의 정체성 위기"라고 불렀다. 해결책은 명확하다. 식별이 불필요한 작은 데이터 타입에서 정체성을 제거하면 JVM이 포인터 없이 데이터를 직접 배치할 수 있다. 그런데 이것이 왜 10년이나 걸렸나? 기존 JVM·컴파일러·언어 스펙·표준 라이브러리의 전 계층이 "모든 객체는 정체성을 가진다"를 가정하고 설계됐기 때문이다. Integer 인스턴스에 synchronized를 거는 코드, ==으로 박스형 정수를 비교하는 코드, 리플렉션으로 객체 주소를 추적하는 코드 — 이것들이 전부 정체성에 의존한다. 수백만 개의 자바 프로젝트와 수십 년의 코드 관성을 존중하면서 근본을 바꾸는 일은 단순한 기능 추가가 아니라 패러다임 수술이었다.

2. 값 클래스(value class)란 무엇인가

Project Valhalla의 슬로건은 처음부터 일관됐다. "codes like a class, works like an int" — 클래스처럼 쓰되 int처럼 동작한다. JEP 401이 제공하는 것이 정확히 이것이다.

2.1 값 클래스 선언

값 클래스는 value 키워드로 선언한다.

value class Point {
    int x;
    int y;
    Point(int x, int y) { this.x = x; this.y = y; }
}

이 선언이 의미하는 것은 두 가지다. 첫째, Point 인스턴스는 정체성이 없다. 둘째, JVM은 이 객체를 포인터 없이 인라인으로 배치해도 된다는 권한을 갖는다. 코드 구조는 일반 클래스와 동일하다. 생성자, 메서드, 인터페이스 구현 모두 그대로다. 그러나 런타임 표현이 근본적으로 달라진다.

value record도 지원된다. record는 이미 불변 데이터 캐리어를 표현하는 데 쓰이므로, 값 레코드는 개념적으로 가장 자연스러운 결합이다.

2.2 정체성 없음이 가져오는 제약

값 클래스에는 일반 클래스에서 당연했던 것들이 허용되지 않는다. synchronized(point) {}는 컴파일 오류다. System.identityHashCode(point)는 의미를 잃는다. 참조 비교 ==는 내용 비교로 동작이 바뀐다. 이 제약들은 동시에 최적화의 열쇠다. 정체성이 없으니 JVM이 인스턴스를 복사하거나 재구성해도 의미가 보존된다. 이것이 힙 플래트닝과 스칼라화를 가능하게 하는 전제다.

3. 힙 플래트닝과 스칼라화 — 성능이 어디서 오나

JEP 401의 핵심 성능 기법은 두 가지다. 두 기법은 서로 다른 레벨에서 작동하지만 같은 방향을 가리킨다. 포인터를 없애고 데이터를 가까이 두라.

3.1 힙 플래트닝 (Heap Flattening)

기존 자바에서 Color[] colors = new Color[1_000_000]를 선언하면, 배열은 백만 개의 포인터를 담고 각 포인터는 힙 전역에 산발적으로 흩어진 Color 객체를 가리킨다. CPU가 colors[0].r에 접근하려면 배열 베이스 → 포인터 → Color 객체 헤더 → r 필드의 경로를 밟는다. 반복 접근 시 CPU 캐시는 무용지물에 가깝다.

Color가 값 클래스라면, 배열은 백만 개의 포인터 대신 r·g·b 값이 빽빽이 채워진 연속 메모리 블록을 직접 담는다. colors[0].r은 배열 베이스 오프셋 하나로 접근된다. 배열 전체를 순회하는 작업은 CPU가 가장 좋아하는 패턴, 즉 순차 메모리 스캔이 된다. 보고된 벤치마크에 따르면 이 차이만으로 일부 시나리오에서 메모리 풋프린트가 40~50% 감소하고 순회 연산에서 최대 3배 가속이 보고된다.

3.2 스칼라화 (Scalarization)

스칼라화는 JIT 컴파일러 수준의 최적화다. 메서드가 Point p = new Point(3, 4)를 생성하고 그 x, y 필드만 사용한다면, JIT는 Point 객체를 힙에 할당하는 대신 x=3, y=4를 CPU 레지스터에 직접 올릴 수 있다. 힙 할당 자체가 사라진다. GC 추적 대상도 줄어든다. 정수를 연산하듯 처리된다는 의미에서 "스칼라"다.

정체성이 있는 일반 객체는 스칼라화할 수 없다. 누군가 그 객체의 주소를 들고 있을 수 있고, 주소가 바뀌면 관찰 가능한 의미 차이가 생긴다. 값 클래스는 정체성이 없으므로 JVM이 복사·재배치·분해를 자유롭게 할 수 있다. 이것이 10년의 설계 반복이 풀어낸 핵심 열쇠다.

4. JDK 28에서 실제로 반영된 것과 아닌 것

공식 OpenJDK 정보와 보도를 기준으로 JDK 28 프리뷰에 포함되는 것과 아직 없는 것을 명확히 구분한다.

4.1 JDK 28 프리뷰에 포함 (보도·계획 기준)

  • value class와 value record 선언 문법 (JEP 401)
  • 값 클래스에 대한 힙 플래트닝과 스칼라화 JVM 최적화
  • Integer·Double·Long 등 기존 프리미티브 래퍼 클래스의 값 클래스 마이그레이션 (프리뷰 범위)
  • 저렴한 박싱(cheaper boxing) — 래퍼 클래스 박싱 오버헤드 감소
  • --enable-preview 플래그로 활성화

4.2 JDK 28에 없는 것 (향후 과제)

  • null-restricted 타입 (비널러블 참조): Point! 같은 표기로 null을 불허하는 타입
  • 특화 제네릭 (JEP 402): List<int>처럼 박싱 없이 프리미티브 파라미터화된 제네릭
  • 128비트 인코딩 지원
  • 완전 성숙한 JEP 402

특화 제네릭이 빠진 것이 아쉬울 수 있다. List<int>는 현재도 List<Integer>로 박싱을 거쳐야 하는데, 이 간극을 없애는 것이 Valhalla 최종 목표의 핵심이다. JEP 401이 "첫 번째 관문"인 이유다. Brian Goetz가 직접 밝혔듯 "정체성 제거가 첫 장벽이고, 그것이 열리면 특화 제네릭이 가능해진다."

5. 래퍼 클래스 마이그레이션의 함정

Integer가 값 클래스가 된다는 것은 들뜬 소식처럼 들린다. Integer[]가 int[]에 가까운 메모리 효율을 가진다면, 제네릭 컬렉션의 오랜 박싱 비용 문제가 상당 부분 완화된다. 그러나 여기에 중대한 부수 효과가 있다.

Integer 인스턴스에 synchronized를 걸던 코드는 예외가 발생한다. 흔한 실수 패턴이 있다. 캐시나 상태 관리를 Integer 인스턴스로 락킹하던 코드, 또는 상수 Integer를 모니터로 쓰던 코드다. 값 클래스는 정체성이 없으므로 모니터(monitor lock)의 대상이 될 수 없다. 이 패턴은 런타임 예외로 이어진다.

또 하나의 미묘한 지점은 == 비교다. JDK 5 이후 Integer.valueOf(-128~127 범위)는 캐시된 인스턴스를 반환해 == 비교가 우연히 true가 됐다. 값 클래스 마이그레이션 이후 이 동작의 의미가 달라질 수 있다. 기존 코드베이스에서 ==로 Integer를 비교하거나 Integer를 락으로 쓰는 패턴은 반드시 사전 점검이 필요하다. 2026년 6월 기준 이는 프리뷰 단계이므로 프로덕션 직접 적용보다는 테스트 환경에서 탐색하는 것이 적절하다.

6. 실질적 성능 영향 — 어떤 코드가 이득을 보나

Valhalla가 모든 자바 코드를 마법처럼 빠르게 만드는 것은 아니다. 이득이 큰 패턴과 그렇지 않은 패턴이 있다.

6.1 최대 이득 패턴

  • 대규모 값 객체 배열 처리: 금융 데이터(거래 레코드), 좌표 처리(게임·시뮬레이션·GIS), 색상 버퍼(이미지 처리), 센서 데이터 스트림
  • 수치 집약 루프: 벡터 연산, 행렬 곱, 통계 집계처럼 CPU 캐시 활용이 중요한 코드
  • 작은 불변 데이터 타입의 고빈도 생성·폐기: Option 타입, 좌표 쌍, RGB 값, 화폐 금액+통화 쌍 등

6.2 이득이 제한적인 패턴

  • 락킹·동기화가 핵심인 공유 가변 상태: 값 클래스는 정체성이 없어 기존 synchronized 패턴을 대체할 수 없다
  • 이미 박싱이 드문 원시 타입 코드: int[]를 이미 잘 쓰고 있다면 추가 이득이 적다
  • I/O·네트워크 바운드 코드: 병목이 메모리 레이아웃이 아니라면 Valhalla 최적화는 무관하다

7. 자바 개발자에게 주는 의미 — 본인의 해석

여기서부터는 사실 전달이 아닌 본인 분석이다. Valhalla가 자바 개발자에게 무엇을 뜻하는지 세 각도에서 본다.

7.1 성능과 메모리 비용의 재계산

자바 성능 튜닝에서 수년간 반복된 조언이 있었다. "작은 객체를 많이 만들지 마라, 배열 대신 객체 리스트를 남용하지 마라, 박싱을 피하라." 이 조언들의 공통 뿌리는 자바의 객체 모델이 가진 구조적 비용이다. Valhalla는 이 비용 자체를 낮춘다. 방어적 설계 원칙 일부가 더 이상 필수가 아니게 된다. 이는 설계의 자유도가 높아진다는 의미다. 작은 불변 데이터 타입을 두려움 없이 값 클래스로 표현할 수 있게 된다.

7.2 Rust·C#·Swift와의 거리 좁히기

C#은 이미 오래 전에 struct로 값 타입을 지원하고, Rust는 소유권 시스템과 함께 스택 배치가 기본이다. Swift도 struct가 값 의미론을 갖는다. 자바는 이 분야에서 뒤늦었고, 그 결과 수치 집약 작업에서는 C나 C++, 경우에 따라 Rust나 C#에 비해 명백한 메모리·성능 불리함이 있었다. Valhalla 이후 자바가 이 격차를 상당히 좁힌다는 것이 본인 판단이다. 정확히 같아지지는 않는다. JVM의 안전망(GC, 경계 검사)은 여전히 비용을 갖는다. 그러나 "자바는 메모리를 낭비한다"는 구조적 약점은 크게 완화된다.

7.3 기존 코드베이스 마이그레이션은 점진적이어야 한다

Valhalla는 기존 코드를 즉시 깨지 않는다. 기존 class Point {}는 그대로 동작한다. 값 클래스로 이득을 보려면 명시적으로 value를 선언해야 한다. 그러나 래퍼 클래스 마이그레이션처럼 표준 라이브러리가 변하면 그 영향은 수동적으로 받게 된다. 실무적 권고는 이렇다: 프리뷰 단계에서는 --enable-preview로 탐색하되 프로덕션 의존을 피하고, LTS(현재 계획상 JDK 29 또는 31)에 정식 포함된 후 전략적으로 적용하라. 그 전에 기존 코드베이스에서 Integer 락킹 패턴과 == 비교를 찾아 제거해 두는 것이 선제적 준비다.

8. 결론 — 10년이 정당화되는 이유

Project Valhalla가 10년 걸린 것은 느림이 아니라 복잡성의 정직한 반영이다. 30년 된 언어의 근본 가정을 기존 생태계를 깨지 않으면서 바꾸는 일은 단순한 기능 추가로 끝나지 않는다. 언어·컴파일러·JVM·표준 라이브러리·생태계의 전 계층이 정렬되어야 한다. JEP 401 하나를 위한 커밋 197,000줄은 그 무게를 숫자로 보여준다.

2026년 6월 기준 JDK 28 프리뷰로 반영된 JEP 401은 Valhalla의 첫 번째 관문이다. 특화 제네릭이 오면 자바의 표현력과 성능 모두에서 더 큰 도약이 온다. 그러나 지금 반영된 것만으로도 의미가 크다. 값 클래스, 힙 플래트닝, 스칼라화 — 이 세 가지가 결합하면 자바의 고질적 메모리 낭비와 캐시 미스 문제를 구조적으로 줄인다. "코드는 클래스처럼, 동작은 int처럼." 12년 된 약속이 이제 코드로 쓸 수 있는 현실이 됐다.
