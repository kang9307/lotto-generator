プロンプトをコードとして管理する - バージョン管理と回帰試験

一行直したら別のケースが壊れる - 運用プロンプトの変更・検証・ロールバック設計

2026年7月27日 開発・インフラ

序論: プロンプトはコードではなく設定として扱われる

プロンプトの書き方を扱う記事はすでにあふれている。役割を与えよ、例示を入れよ、出力形式を明示せよ。ところが、そうして作ったプロンプトが運用に入ったあとの話はほとんど語られない。三か月前に誰がなぜその一文を入れたのか誰も知らない。先週一行直したら、まったく関係なさそうなケースの出力が変わった。ベンダーがモデルを上げたら同じプロンプトの挙動が変わった。この記事はその局面を扱う。

問題の根は単純である。プロンプトはコードとしてではなく設定として扱われている。設定値にはたいてい試験がない。誰かが管理画面でこっそり変えても何も起きないし、変えた本人もそれをデプロイだとは思っていない。しかしプロンプトは設定値とは性質がまったく違う。タイムアウトを30秒から60秒に変えれば影響範囲は予測できるが、プロンプトに表は最大3行に保てという一行を入れると、その指示は表と無関係な要求の応答長・語調・形式まで一緒に揺らす。

つまりプロンプトの変更は局所的ではない。コードでは関数を一つ直しても影響するのはその関数を呼ぶ経路だけだが、プロンプトでは追加した文がすべての入力と一緒に読まれる。この性質があるため、プロンプトに必要なのは「よい保管場所」ではなく「変更の副作用を観測する装置」である。そしてその装置の名前は昔から決まっている。回帰試験だ。

ただしプロンプトの回帰試験は、ソフトウェアのそれをそのまま持ってくることができない。同じ入力に同じ出力が出ないからである。そこでこの記事は三つの筋を一緒に扱う。①プロンプトという生成物そのものの履歴をどう残すか、②非決定的な出力に合否基準をどう立てるか、③モデルが変わったとき何を測り直すか。生成物ができたあとの検査工程 — 構文・実行時・意味の3層検査、誤検知の管理、ゴールデンファイル — はこの記事の範囲ではなく、AI生成物の検査体制を作るで別に扱った。ここで対象になるのは生成物を作り出す指示文そのものである。

1. プロンプトが管理対象から外れる三つの経路

「うちはプロンプトをリポジトリに入れている」という組織でも、実際には履歴が切れていることが多い。切れ方はおおむね三つである。

  • コード内に文字列として埋まっている場合 — 形式上はバージョン管理下にあるが、コミットメッセージがプロンプト改善の一行なので何をなぜ変えたのかが残らない。戻そうとしてもどのコミットに行けばよいのか分からない。
  • 管理画面で編集する場合 — 非エンジニアが直接直せて便利だが、その編集はデプロイ手順を通らない。レビューもなく、試験もなく、反映時刻の記録もない。運用中の無断変更と構造的に区別がつかない。
  • 複数の断片から組み立てられる場合 — システムプロンプト、ツール定義、検索結果テンプレート、ユーザーメッセージのテンプレートがそれぞれ別の場所にある。個々の断片には履歴があるのに、「その日に実際にモデルへ渡された全体の文字列」の履歴はどこにもない。事故が起きても再現できない。

三つ目がもっとも危険である。断片がそれぞれバージョンを持つと組み合わせの数は掛け算で増えるのに、問題を起こしたのは特定の組み合わせだからだ。したがってプロンプトのバージョン管理の単位は断片ではなく「レンダリングされた最終プロンプト」でなければならない。断片はソースであり、最終プロンプトはビルド生成物である。ビルド生成物のハッシュを残さなければ、何を実行したのかを特定できない。

判断基準を一つ。「昨日の午後3時にその要求が受け取ったプロンプト全文をいま再構成できるか」に30秒で答えられなければ、そのチームにプロンプトのバージョン管理はない。ファイルがどこにあるかは二次的な問題である。

2. プロンプトの変更は局所的ではない

回帰がなぜそれほど頻繁に起きるのかを理解すれば、以降の設計はすべてそこから導かれる。プロンプトで回帰が生じる経路は四つに整理できる。

2.1 指示はケースを選ばない

運用でよくある場面。顧客Aから「応答が長すぎる」と苦情が来たのでプロンプトに回答は三文以内にせよを入れる。翌週、顧客Bから「説明が薄くなった」と苦情が来る。Bの要求はもともと長く答えるべき種類だったのに、新しい指示がすべての要求と一緒に読まれたのである。これはモデルの欠陥ではない。プロンプトに条件がなかったので条件なしに適用されたのが正常な動作だ。

2.2 例示は明示的な指示より強く働く

いくつかの例示を添えて形式を固める方法は効果的だが、例示は本文が語っていないことまで一緒に教える。例示三つがすべて丁寧語なら語調が固定され、すべて短ければ長さが固定され、すべて特定業種なら業界語彙が漏れ出す。例示を一つ差し替える変更が、指示文一行の修正より危険な理由がここにある。

2.3 順序と位置が結果を変える

同じ内容でも前に置くか後ろに置くかで反映の強さが変わる。この性質はプロンプト設計全般の主題なのでコンテキストエンジニアリングのほうで詳しく扱ったが、バージョン管理の観点で重要な含意は一つだ。「文を移動させただけの変更」も動作変更である。差分の上では移動にすぎないためレビューを通りやすいが、結果は変わりうる。

2.4 プロンプトの外が変わってもプロンプトが変わった効果が出る

モデルスナップショット、ツール定義、検索結果のチャンクサイズ、出力スキーマ — このどれが変わっても最終的な挙動は変わる。ところがこれらはたいていプロンプトの変更履歴に記録されない。「プロンプトは触っていないのに結果が変わった」という報告の相当数がここに属する。だからプロンプトのバージョンにはプロンプト本文だけでなく、そのプロンプトが実行される環境全体が一緒に束ねられる必要がある。

3. 何を記録するか - プロンプトのメタデータ

前節の結論をそのままスキーマに移せばよい。核となる原則は「この記録だけを見てそのときの実行を再現できるか」であり、再現に必要のない項目は入れない。

# prompts/support_reply/v0007.yaml
id: support_reply            # 論理名。変わらない
version: 7                   # 単調増加。セマンティックバージョンを使わない理由は下記
content_hash: 9f2c1ab4       # 正規化後のハッシュ。同じなら同じ実行とみなす
created_at: 2026-07-27T10:12:00+09:00
author: swkang
status: active               # draft | canary | active | rolled_back | retired

# 実行環境 - これが抜けると再現できない
runtime:
  model: vendor-model-2026-05-14   # 別名ではなくスナップショット識別子
  params: { max_tokens: 1024 }     # サンプリング引数は対応状況がベンダーごとに違う
  tools_version: 3                 # ツール定義もプロンプトの一部である
  output_schema: reply_v2          # 下流パーサーとの契約

# 組み立て情報 - 最終文字列がどう作られたか
compose:
  parts: [system_base@12, policy_ja@4, fewshot_support@6]
  cache_boundary_after: policy_ja  # キャッシュ接頭辞の境界(9節)

# 変更情報 - レビューとロールバック判断に使う
change:
  type: add_constraint       # 4節の変更種別
  risk: high                 # 種別から自動決定する。人が下げて書けないようにする
  reason: "長文応答のクレーム(チケット #4821)"
  reverts: null

# 検証記録 - この数字がないとロールバック判断ができない
eval:
  suite: support_v5          # 評価セットにもバージョンがある
  runs_per_case: 5
  hard_gate: pass
  pass_rate: 0.94            # 180ケース基準
  baseline_version: 6
  delta: +0.01               # 信頼区間の内側なら改善とは呼ばない
  judge: rubric_checklist_v2 # 判定方式もバージョン管理の対象(7節)

いくつかの選択には理由がある。

  • セマンティックバージョンではなく単調増加の整数 — セマンティックバージョンは「後方互換が壊れるか」を人が判断して表記する体系である。プロンプトは一行の修正で互換が壊れうるため、その判断が成り立たない。そこで番号は順序だけを示し、影響範囲はchange.riskが別に示す。
  • モデルは別名ではなくスナップショット識別子 — 別名はベンダーが指す先を変えれば静かに追随する。再現可能な記録を残すには、その日に実際に呼ばれたスナップショット文字列を書く。
  • 評価結果をプロンプトのメタデータに一緒に書く — 別のダッシュボードにだけあると、ロールバックのときに参照されない。戻す先のバージョンのファイルを開いたら、そのバージョンの成績がすぐ見えなければならない。
  • 判定方式(judge)も記録する — 判定基準が変わると過去のスコアと比較できなくなる。7節で扱う。
  • statusにrolled_backを置く — 戻したバージョンを消すと「この方向はすでに失敗した」という情報が消え、数か月後に同じ試みを繰り返す。

4. 変更種別ごとの危険度

すべてのプロンプト修正に全評価セットを回すと、誰もプロンプトを直さなくなる。逆に全部通せば回帰が積もる。そこで変更種別で検証の強さをあらかじめ決めておくのが実用的である。下の表はその対応づけの出発点だ。

変更種別例影響範囲キャッシュ影響危険度最低限の検証
表記の修正誤字、句読点理論上なし(トークン境界は変わる)位置が前なら全体が無効化低ハードゲート + スモーク10ケース
文の移動同じ内容を後ろへ移す中 — 反映の強さが変わる移動地点以降が無効化中全評価セット1回
制約の追加「三文以内」のような禁止・制限広い — 無関係なケースにも適用中高全体 + 反対ケース
例示の追加・差し替えfew-shot を1つ変更広い — 語調・長さ・語彙が一緒に動く大(分量が大きい)高全体 + 反対ケース
出力スキーマの変更フィールド追加・改名下流パーサーまで中非常に高全体 + 結合試験 + 互換確認
ツール定義の変更引数説明の一行修正ツール選択の挙動全般最大 — 以降の全階層が無効化非常に高全体 + ツール呼び出しケース
モデルスナップショットの交換バージョン更新すべてすべて非常に高基準線の測り直し + 並行運用(8節)
サンプリング引数の変更温度・上位確率の調整ばらつきが変わるふつうなし中反復実行の合格率を測り直す

この表で実務的にもっとも価値があるのは「制約の追加」の最低限の検証に付いた反対ケースである。新しい指示を入れるときはその指示が適用されてはいけないケースを必ず一緒に入れなければならない。そうしないと評価セットはいつも「指示がよく効いた」だけを確認し、副作用は運用で顧客が発見する。この一行がプロンプト回帰試験の核心だと言っても大げさではない。

危険度は本人に自分の変更を自己申告させてはいけない。急ぐほど低く書かれる。変更種別を選べば危険度が自動的に決まり、下げるには別途承認を要する仕組みのほうが現実的である。

5. 評価セット - ケースはどこから集め、何件必要か

プロンプト回帰試験の実体は評価セットである。ところが評価セットを作れという話はよく聞く一方、ケースをどこから得るのかへの答えはあまり見かけない。実際に使える出所は五つある。

出所得られるもの注意点推奨比率
運用ログの標本実際の入力分布個人情報の除去が必要。注入の試みが混ざりうる40%前後
障害・クレームのチケットすでに一度壊れたケース失敗側に偏り、合格率が低く出る20%前後
反対ケース新しい指示の副作用作るのが面倒でまっさきに抜ける20%前後
手作りの境界ケース空入力、超長文、矛盾する指示、多言語混在非現実的なケースを入れると合格率が歪むだけ15%前後
合成による変形規模の確保元データの偏りをそのまま増幅する5%前後

比率は絶対値ではなく出発点である。大事なのは比率が管理されているという事実そのものだ。管理しなければ評価セットは時間とともに「過去に壊れたもの」で埋まり、実際のトラフィックに似なくなる。

5.1 評価セットは設計するものではなく育つものである

最初から完成した評価セットを作ろうとする試みはたいてい失敗する。代わりに二つの規則さえ守れば、評価セットは勝手に育つ。

  • 事故一件 = ケース一件。運用で問題が報告されたら、直す前にその入力を評価セットへ入れる。直したあとに入れようとすると永遠に入れない。
  • 指示一行 = 反対ケース一件。制約を追加するたびに、その制約が適用されてはいけない入力を一緒に入れる。

ケースファイルは特定のツールに縛られない形で置くほうが安全だ。一行に一ケースのテキスト形式なら何ででも読める。

// eval/support_v5.jsonl  - 一行に一ケース
{"id":"c101","kind":"positive","input":"返金はいつになりますか?",
 "must":["返金","営業日"],"must_not":["口座番号"],"max_chars":400}

{"id":"c102","kind":"counter","input":"契約書第3条の解釈を根拠とともに説明してください",
 "note":"長文が正しいケース - 三文制限がここに適用されたら回帰",
 "min_chars":600,"must":["第3条"]}

{"id":"c103","kind":"boundary","input":"",
 "note":"空入力","must":["もう一度入力"],"must_not":["エラーコード"]}

{"id":"c104","kind":"schema","input":"注文3件の状況を教えて",
 "expect_json":true,"required_fields":["orders","count"]}

ここでkindがcounterのケースが何件あるかを指標として管理するとよい。反対ケースの比率が0に近づく評価セットは回帰を捕まえられない。

5.2 何件あればよいか - 件数は欲しい精度が決める

「評価セットは何件が適正か」に普遍的な正解はない。代わりに逆から問えば答えが出る。どの程度の大きさの差を区別したいのか。合格率を推定するときの95%信頼区間の半幅はおおよそ1.96 × √(p(1−p)/n)であり、合格率0.9付近で計算すると次のようになる。

評価セットの大きさ n合格率0.9での95%区間の半幅区別できる差使いどころ
20約 ±13.1ポイント大きな破損のみスモーク検査
30約 ±10.7ポイント大きな破損のみ変更直後の素早い確認
50約 ±8.3ポイント10ポイント以上日常の回帰試験
100約 ±5.9ポイント6ポイント以上承認ゲート
300約 ±3.4ポイント3ポイント以上モデル交換の判断
500約 ±2.6ポイント2ポイント以上大規模な移行

表の読み方は簡単である。100件の評価セットで「2ポイント良くなった」と言うのは統計的な根拠がない。改善に見える値が雑音かもしれないし、逆に本当の悪化も雑音に埋もれる。だから4節の表でモデル交換を「非常に高」に置いた。その判断にはより大きな評価セットが要る。

注意点が二つ。第一に、上の近似式は合格率が1に非常に近いと不正確になるため、その領域では別の区間推定法を使うほうがよい。第二に、この計算は「ケースを何件見るか」についてのものであり、「母集団に潜む稀な欠陥を標本で発見する確率」は別の計算である。後者は生成物の検査編に表としてまとめてあるので、そちらを参照するとよい。

ベンダー文書の例示規模も参考になる。Anthropicの評価作成ガイドは課題の性格に応じて数十グループから千件規模までの例を挙げ、原則として「自動採点できる多数の問いのほうが、人手で採点した少数の問いより良い」という趣旨を明記している。ただしこれはベンダー自身の文書による推奨であり、課題と危険度によって変わりうる。

6. 非決定的な出力に合格基準を立てる方法

ここがプロンプトの回帰試験がソフトウェアの回帰試験と分かれる地点である。同じ入力に同じ出力が出ない。

6.1 温度0は再現を保証しない

よくある誤解は「温度を0にすれば決定的」というものだ。実際はそうではない。Thinking Machines Labが公開した技術記事は、同一プロンプトを温度0で1,000回実行したところ異なる完成文が80種類現れ、もっとも多い完成文が78回、最初の分岐が103番目のトークンで起きたと報告している。この記事の中心的な主張は、原因がGPUの並行性でも無作為性でもなくカーネルのバッチ不変性の欠如だという点である。サーバーが同時に処理する要求数によって縮約演算の計算順序が変わり、浮動小数点の加算は結合法則を満たさないので末尾のビットが揺れる。その微小な差がある瞬間にトークン選択をひっくり返す。同じ記事は、バッチ不変カーネルを適用すると1,000回がすべて同一になったと付け加えている。これは学術論文ではなく研究ラボの技術ブログである点を踏まえて読む必要がある。

実務的な含意は二つ。第一に、非決定性は制御可能な性質だが、たいてい我々の手の外にある。マネージドAPIを使うチームはサーバーのバッチ状況を制御できない。第二に、したがって再現性を前提にした試験設計はそもそも成立しない。

さらに温度という引数自体が永続的ではない。Anthropicの文書はtemperature・上位確率・上位kの引数について、Claude Opus 4.7以降のモデルで既定値以外を設定すると400エラーを返す状態と表記し、引数の代わりにプロンプトで挙動を導くよう案内している。「温度を0に固定して再現性を確保する」という戦略は、ベンダーの引数方針の変更だけで消えうるということだ。

6.2 合格基準は一回の出力ではなく分布にかける

そこで判定は同じケースをk回実行した結果の分布に対して下す。項目ごとに性質が違うので、基準の形も違ってよい。

判定対象基準の形反復 k例失敗時
形式の契約ハードゲート(k回すべて)3〜5JSONの解析、必須フィールドの存在即不合格
禁止事項ハードゲート(k回すべて)5以上禁止語、個人情報の露出、断定表現即不合格
事実の一致合格率のしきい値3〜5抽出フィールドの一致率0.95以上原因を分解して判断
主観的な品質基準バージョンとの相対比較3以上前のバージョンより悪くないか観察対象
費用・遅延予算の上限全実行を集計平均トークン、p95遅延反映を保留

設計で三つを強調したい。

  • 絶対点数より相対比較のほうが安定する。「この回答は5点満点で4点」は判定者や時点によって揺れるが、「基準バージョンと新バージョンのどちらが良いか」は相対的に揺れにくい。回帰試験の問いはもともと「良くなったか」ではなく「悪くなっていないか」である。
  • ハードゲートと品質指標を混ぜないこと。禁止語の露出を合格率0.98で管理すると、100回に2回は出てよいという意味になる。形式・安全の項目はしきい値ではなく全通過でなければならない。
  • kを増やすと揺れの代償が大きくなる。各ケースが1%の確率で偶然失敗するとすれば、100ケースの評価セットが一度でも失敗する確率は約63%である(1 − 0.99100)。揺れを0.1%まで下げてやっとこの値が約10%になる。つまり揺れる試験は必ず無視される。揺れるケースは合格率のしきい値に移すか判定基準を狭めるべきで、放置すると評価セット全体の信頼が崩れる。
// フレームワークに依存しない最小の判定ロジック
async function judgeCase(runModel, testCase, k = 5) {
  const outputs = [];
  for (let i = 0; i < k; i++) outputs.push(await runModel(testCase.input));

  // 1) ハードゲート - 一度でも破れば終わり
  for (const out of outputs) {
    if (testCase.expect_json && !tryParse(out)) return fail('schema');
    for (const bad of testCase.must_not || []) {
      if (out.includes(bad)) return fail('forbidden:' + bad);
    }
  }

  // 2) 合格率の基準 - 揺れを許す項目
  const softPass = outputs.filter(out =>
    (testCase.must || []).every(t => out.includes(t)) &&
    (!testCase.max_chars || out.length <= testCase.max_chars) &&
    (!testCase.min_chars || out.length >= testCase.min_chars)
  ).length;

  return { id: testCase.id, hard: 'pass', rate: softPass / k, k };
}

このコードが特定のツールに縛られていない点が重要である。runModelだけ差し替えれば、ベンダーが変わっても評価ツールが変わっても判定ロジックは我々のものとして残る。11節で改めて述べる。

7. 判定者もバージョン管理の対象である

品質判定をLLMに任せる方法は広く使われているが、回帰試験に使うときは固有の落とし穴がある。回帰試験は本質的に二つのバージョンの出力を並べて比べる作業であり、判定者の偏りがもっとも強く現れる状況がまさにその並置だからである。

  • 位置バイアス — プロンプトの中でどちらを先に見せるかによって選択が変わる現象である。判定者15種を二つのベンチマークの22課題にわたって調べ、15万件を超える評価事例を作った研究は、反復安定性・位置一貫性・選好公平性の三指標でこの偏りを測りながら、偶然ではなく体系的であり判定者と課題によって大きく異なるとまとめた。同じ研究は、この偏りがプロンプト構成要素の長さより二つの候補の品質差に強く左右されると報告している。つまりバージョン間の差が微妙なほど順序効果が大きくなるということだが、回帰試験で比べる二つのバージョンはほぼ常に微妙に違う。
  • 自己選好バイアス — 判定者が自分の系統の出力を甘く評価する現象である。ある研究は、この偏りの本質が「自分が書いた文章だから」ではなく低い困惑度、つまり自分にとって馴染みのある文体を人間より甘く評価する傾向にあると説明する。モデル更新の検証で新旧どちらかを判定者に使うと、結果が一方に傾きうるということだ。
  • 判定者のドリフト — 前の二つより実務で事故を起こしやすい。判定に使うモデルが変わると、過去のスコアと新しいスコアを比較できない。プロンプトはそのままなのに合格率が3ポイント下がったとき、それがプロンプトの回帰なのか判定者の交換のせいなのか区別する手段がなくなる。

この記事の観点から結論は一つに収束する。判定者は評価インフラではなくバージョン管理の対象である。3節のスキーマにjudge項目を入れた理由がこれだ。実務規則としては次の程度が無難である。

  • 判定モデルと判定プロンプトを固定し、変えるときは基準線をまるごと測り直す。判定者の交換は4節の表の「非常に高」に当たる。
  • 比較判定は順序を入れ替えて二度尋ね、一致したときだけ採用する。不一致は「差なし」として扱う。
  • 生成モデルと判定モデルを分ける。Anthropicの文書も、採点には生成に使ったモデルとは別のモデルを使うほうが一般的に良いと案内している。
  • 点数ではなく項目ごとのはい・いいえのチェックリストを使う。尺度点数は判定者ごとに目盛りが違い、時系列比較が難しい。
  • LLMの判定は人が見る順序を決める用途に使い、反映の承認そのものはハードゲートと人の検査に残す。

判定の偏り一般とその緩和策は生成物の検査編でさらに扱った。ここで強調しているのは「判定者を替えた瞬間に履歴が切れる」というバージョン管理側の含意である。

8. モデル更新はそれ自体が回帰イベントである

プロンプトを一文字も触らないのに挙動が変わる出来事がある。モデルが変わるときだ。そしてこの出来事は我々の日程ではなくベンダーの日程でやってくる。

8.1 ベンダーが告知するものと告知しないもの

2026年7月時点で、二つのベンダーの公開方針は次のとおりである。

  • Anthropic — モデルのライフサイクルをActive・Legacy・Deprecated・Retiredの四段階で定義し、公開モデルについて提供終了の最低60日前の通知を明記している。提供が終わったモデルへの要求は失敗する。コンソールからAPIキー別・モデル別の使用量を書き出して提供終了モデルの使用箇所を監査できるよう案内している。
  • OpenAI — 一般提供モデルは最低6か月、特殊な派生(チャット派生・Codex・ディープリサーチ系)は最低3か月、プレビューモデルは2週間程度のはるかに短い予告を提示し、プレビューモデルを業務の中核経路に使わないよう勧めている。

重要なのはこの通知が「提供終了」についてのものであって「挙動の変化」についてのものではないという点だ。別名を使うチームは提供終了日にエラーを見る代わりに、ある日静かに別のモデルを使うことになる。エラーには通知が来るが挙動の変化には通知が来ない。だから3節で別名ではなくスナップショット識別子を記録せよと述べた。プロンプトとモデルのロックイン構造全般はベンダーロックイン脱出戦略のほうで層別に整理した。

8.2 モデル交換の6段階

段階やること成果物よくある失敗
0. 棚卸しどのプロンプトがどのスナップショットを使うか一覧化プロンプト×モデルの一覧表バッチや管理画面に隠れた呼び出しを漏らす
1. 凍結検証期間中のプロンプト変更を禁止凍結の通知同時にプロンプトも直して原因を切り分けられなくなる
2. 基準線の測り直し旧モデルでいま改めて評価セットを実行基準線の成績数か月前の数字を基準線に使う
3. 対照実行同じ評価セットを新モデルで実行改善・同等・悪化の分解合計だけ見てケース単位の移動を見ない
4. 局所修正悪化したケースだけを一度に一つずつ修正修正履歴複数箇所を一気に直して何が効いたか分からない
5. カナリア・並行少量のトラフィックから移行し、戻せる経路を維持移行計画提供終了直前に始めて戻す余地がない

2段階を強調したい。基準線は必ずいま測り直す。過去の記録はそのときの評価セット・判定者・実行環境から出た数字である。それを新モデルの成績と比べても何が原因かは分からない。比較は同じ日、同じ評価セット、同じ判定者で並べて回した二つの数字のあいだでのみ意味を持つ。

3段階の分解も重要だ。合計が同じでも内部ではケースが大きく移動しているかもしれない。10件が良くなり10件が悪くなれば合計はそのままだが、悪くなった10件が売上経路にあるケースなら、それは改善ではなく事故である。

# 対照実行は難しくない。難しいのは結果をケース単位で読むことだ。
run_eval --suite support_v5 --model old-snapshot --k 5 --out base.json
run_eval --suite support_v5 --model new-snapshot --k 5 --out cand.json

compare base.json cand.json --group-by segment
# 出力例(形だけ):
#   improved  18  regressed  11  unchanged 151
#   regressed のうち segment=billing が7件  <- 合計ではなくここを見る

9. プロンプトキャッシュがあると前方の一行は値段が違う

プロンプトキャッシュを使うチームでは変更の位置が費用を左右する。この事実はプロンプト管理の規則に直接影響する。

Anthropicの文書によれば、キャッシュはツール → システム → メッセージの順の接頭辞構造を持ち、前の階層が変わるとその後ろの階層が一緒に無効化される。ツール定義の名前・説明・引数を直せばキャッシュ全体が無効化され、システムプロンプトを直せばシステムとメッセージのキャッシュが無効化される。価格構造は次のとおりである。

区分基本入力に対する倍率意味運用上の含意
キャッシュ書き込み(5分)1.25倍新しく保存するとき反映直後の最初の要求群がこの費用を払う
キャッシュ書き込み(1時間)2.0倍長い保持の選択肢変更が頻繁な区間には不利
キャッシュ読み出し0.1倍再利用するとき安定した接頭辞が大きいほど得が大きい
既定の保持時間5分使われるたびに更新トラフィックが薄いとキャッシュがよく冷める

ここから出てくる実務規則は三つである。

  • よく変わるものを後ろへ送る。実験中の指示、セグメント別の分岐、最近の方針文はキャッシュ境界の後ろに置く。前に置くと一文字の修正で接頭辞全体が無効化される。
  • 現在時刻やユーザー名のような変数をシステムプロンプトの前方に差し込まない。要求ごとに接頭辞が変わり、キャッシュが事実上働かなくなる。
  • キャッシュ境界の位置をプロンプトのメタデータに書く。3節のスキーマのcache_boundary_afterがそれだ。この情報がないとレビュアーは「前に一行追加」の費用影響を判断できない。

反映手順にも含意がある。プロンプトの反映直後は費用が一時的に上がる。すべてのキャッシュが書き直されるからだ。この上昇を異常の兆候と誤解してロールバックしないよう、反映時刻と費用グラフを一緒に見る必要がある。上の数値と階層構造はAnthropic自身の文書に基づくものであり、キャッシュの実装と課金はベンダーごとに違うので、他のベンダーを使うなら該当文書で確認し直すべきである。

10. ロールバックの判断基準

ロールバックは失敗ではなく設計された経路であるべきだ。問題は「いつ戻すか」を事故が起きたあとに決めようとすることである。その瞬間にはすでに判断が揺れている。

信号しきい値措置根拠
ハードゲート違反1件即ロールバック形式・安全の項目は確率で管理しない
評価セットの合格率低下信頼区間を外れる低下ロールバック区間の内側なら雑音かもしれない(5.2節)
特定セグメントだけ低下合計が維持されていても部分ロールバックまたは分岐合計は移動を隠す
費用の急増反映後30分以上継続キャッシュ境界を点検してから判断直後の上昇はキャッシュ書き直しかもしれない(9節)
人の検査からの申し立て傾向が折れない観察してから判断単発の申し立てで戻すと履歴が汚れる
再現不能の報告—戻さずにケースにする再現しないものを戻すと原因が永遠に残らない

ロールバックにはあまり語られない前提が一つある。戻す先のバージョンが「そのモデルと一緒に」生きていなければならない。プロンプトv6が旧モデルのスナップショットでしか検証されておらず、そのスナップショットがすでに提供終了なら、v6に戻すのは検証されていない組み合わせへ移ることである。つまりモデルが提供終了になる瞬間、そのモデルに紐づいたロールバック経路も一緒に消える。8節の並行運用期間を十分に取るべき本当の理由がこれだ。

ロールバック後に必ずやることも決めておくとよい。戻したバージョンを消さずにrolled_backと印をつけ、何が壊れたかを評価セットにケースとして追加する。この二つをやらないと、同じ試みが数か月後に繰り返される。

11. ツールを選ぶ前に答えるべき三つのこと

プロンプトの評価・回帰ツールの生態系は2026年時点でおおむね三つに分かれる。どちらが良いという話ではなく、解こうとしている問題が違うという話である。

  • ファイル・CI中心 — 評価セットをリポジトリにテキストで置き、CIで回して終了コードで反映を止める方式。変更の遮断が目的だ。promptfooが代表的である。
  • トレース・観測中心 — 運用トラフィックを収集してデータセットにし、オンラインで採点する方式。何が実際に起きているかを見るのが目的だ。LangSmithやBraintrustがこの系統として紹介される。
  • モデル提供者の内蔵機能 — ベンダープラットフォームが提供する評価機能。手が届きやすい代わりに、そのベンダーのモデルや形式と噛み合う。

ツール選択より重要なのはツールが変わっても残るものである。2026年3月9日、OpenAIはpromptfooの買収を発表し、当該プロジェクトを現行ライセンスの下でオープンソースとして維持すると述べた。買収自体の良し悪しを評価する話ではないが、この出来事は評価ツールの所有構造も変わるという事実をよく示している。モデルのベンダーが変わり、評価ツールの持ち主が変わり、チームも変わる。そのあいだ我々のものとして残り続けるべき資産はツールではなく評価セットと判定基準である。

だからツールを選ぶ前に三つに答えておくと、あとで痛みが少ない。

  • 評価セットを自分のリポジトリから平文テキストとして取り出せるか。画面の中にしかないデータセットはツールと一緒に消える。
  • 判定ロジックは自分たちのコードか。6節のjudgeCase程度は手元に持っていてこそ、ツールを移してもスコアの連続性が保てる。
  • CIで終了コードによって反映を止められるか。止められない評価は報告書であってゲートではない。

12. 最小構成で始める

ここまでの内容をすべて揃えてから始めようとすると、誰も始められない。順序を決めれば一日二日単位に刻める。

  1. 1日目 — 棚卸し。運用中のプロンプトと、それぞれが使うモデルスナップショットを表にする。たいていここで「こんなのあったのか」という声が出る。
  2. 2日目 — 最終プロンプトのログ。組み立てられた最終文字列のハッシュとモデル識別子を要求ログに残す。全文を残すのが難しければハッシュだけでも残す。
  3. 3日目 — ハードゲート10ケース。形式や禁止語のように揺れてはいけないものだけを選んで10件作る。品質評価にはまだ手を出さない。
  4. 4日目 — CIへの接続。プロンプトのファイルが変わったらハードゲートが自動で回るようにする。通らなければマージを止める。
  5. 1週目 — 反対ケース規則の導入。制約を追加する変更には反対ケースを一緒に入れるよう、レビューのチェックリストに載せる。
  6. 2週目 — 事故をケースに。運用の事故が起きるたびに、直す前にケースを追加する。この規則一つで評価セットはひとりでに育つ。
  7. 1か月目 — 基準線と相対比較。ケースが50件を超えたら合格率の追跡を始め、新しいバージョンは基準線との比較で判断する。
  8. 四半期ごと — モデル交換のリハーサル。実際の提供終了通知が来る前に8節の手順を一度回してみる。通知を受けてから初めてやるのでは遅い。

もっとも安い一つだけを選ぶなら3日目のハードゲート10ケースである。品質評価は設計が難しく判定者の問題までついてくるが、「JSONが解析できるか」と「禁止語がないか」は判定が機械的で即座に自動化できる。そして実際の運用事故の相当数がその二つの項目で起きる。

結論

プロンプトをコードとして管理するというのは、プロンプトをリポジトリに入れるという意味ではない。変更に理由が付き、変更の副作用を観測する装置があり、戻せる経路が生きているという意味である。三つのうち一つでも欠ければ、リポジトリはただの文字列の保管庫になる。

プロンプト管理がとりわけ難しいのは三つの性質が重なるからだ。変更が局所的でなく、出力が決定的でなく、実行環境が我々の統制の外で変わる。この三つへの対応はそれぞれ反対ケース、分布に基づく合格基準、スナップショットの固定と基準線の測り直しである。この記事が示した表とスキーマはすべてこの三つから派生している。

最後に限界をはっきりさせておく。ここに書かれたどの手順も、プロンプトの品質や性能を保証しない。回帰試験がやることは「良くなった」を証明することではなく、「前はできていたことができなくなった」を反映前に発見することだけである。それだけでも十分に価値があるのは、AIを組み込んだシステムでもっとも頻繁に起きる事故が新しい失敗ではなく静かに戻ってきた古い失敗だからだ。
