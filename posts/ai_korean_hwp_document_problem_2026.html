AI 시대에 K-공문서 HWP를 못 여는 진짜 이유와 해법

바이너리 독점 포맷이 30년간 쌓아온 락인 구조, HWPX 전환의 진짜 의미, 그리고 지금 당장 쓸 수 있는 개발자·사용자 해법

2026-06-21 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: AI가 못 읽는 대한민국 공문서

2026년 6월 기준, 한국의 주요 AI 코딩 에이전트와 LLM 서비스가 쏟아지는 시대에도 여전히 해결되지 않은 역설이 하나 있다. 대한민국 공공기관이 생산하는 문서 대부분이 ChatGPT도, Claude도, Gemini도 직접 읽지 못한다는 사실이다. 2025년 한 조사에서 정부 공문서의 91.1%가 HWP 또는 스캔 PDF 형태로 유통되고 있다고 나왔다. 이 두 포맷은 표준 AI 텍스트 처리 파이프라인과 구조적으로 맞지 않는다.

이 문제는 단순히 "한국 소프트웨어가 뒤처진다"는 이야기가 아니다. 왜 이런 상황이 30년 넘게 지속됐는지, 포맷 자체의 기술 구조에서 출발해 행정 조달, 정치경제적 맥락까지 함께 봐야 이해된다. 그리고 지금 정부가 추진하는 HWPX 전환이 진짜 해법인지, 아니면 또 다른 한계를 안고 있는지도 냉정하게 평가해야 한다.

이 글은 문제의 뿌리부터 현재 실용 해법까지 분석한다. 단 소문이나 마케팅 자료를 옮기지 않는다. 포맷 스펙, 정부 정책 발표, 오픈소스 파싱 라이브러리의 실태를 직접 확인한 내용을 기반으로 쓴다.

1. HWP란 무엇이며 왜 호환이 안 되는가

1.1 HWP의 기술적 구조

HWP(Hangul Word Processor)는 1989년 한글과컴퓨터가 개발한 워드프로세서 프로그램 한글의 전용 파일 포맷이다. 구형 .hwp 파일(HWP5 이하)은 바이너리 독점 포맷이다. 구체적으로 Microsoft Compound Document File Format(OLE2) 기반의 복합 문서 구조를 쓰는데, 내부 스트림 배치와 인코딩 방식이 공개된 국제 표준 없이 독자적으로 설계됐다.

결과적으로 이 파일을 열고 편집해 다시 .hwp로 저장하려면 사실상 한컴오피스를 사야 한다. LibreOffice나 MS Word가 HWP를 어느 정도 읽을 수 있지만, 레이아웃 손상과 특수 기능 누락이 빈번하다. 외부 파서는 더욱 힘들다. pyhwp 같은 오픈소스 라이브러리가 HWP5를 파싱하지만, 모든 내부 스트림을 완전히 해석하지는 못한다. AI가 직접 파일을 바이트 단위로 받아 텍스트를 추출하는 것은 현실적으로 거의 불가능하다.

1.2 왜 AI 도구가 못 읽나

ChatGPT, Claude, Gemini 같은 LLM 서비스는 문서를 처리할 때 표준화된 파싱 경로를 쓴다. PDF는 텍스트 레이어 추출, DOCX는 XML 압축 해제, TXT는 직독. HWP는 이 중 어디에도 들어맞지 않는다. 네이티브 파서가 없으면 파일을 받아도 내용을 꺼낼 방법이 없다.

실제로 2026년 6월 기준, ChatGPT는 2026년 4월에 HWP·HWPX 정식 지원을 선언했고, Gemini는 2024년 하반기부터 지원해왔다. 반면 Claude와 Copilot은 아직 네이티브 지원이 없다. 이 불균형은 포맷 자체의 복잡성이 얼마나 큰 장벽인지 보여준다.

2. 30년 락인의 구조적 이유

2.1 역사적 기원: 한국어 처리가 살렸다

1989년 출시 당시, 한글은 MS Word나 WordPerfect가 제대로 처리하지 못했던 한국어 자모 조합과 세로쓰기를 완벽하게 다뤘다. 초·중·종성 분리 입력 방식과 한글 특화 레이아웃 엔진은 당시 유일한 선택지였다. 교육부와 정부 부처가 한글을 표준 워드프로세서로 채택한 것은 기술적으로 합리적인 결정이었다.

문제는 그 후에 생겼다. 1990년대 MS 오피스의 세계적 확산 속에서도 한국 공공·교육 시스템은 한글을 유지했다. 수십 년치 공문서가 HWP에 쌓였고, 기존 문서를 열려면 한글이 필요하고, 한글을 쓰니 새 문서도 HWP로 만드는 순환이 굳어졌다.

2.2 정부 조달과 표준의 역설

2007년 정부는 국가 표준을 오픈도큐먼트(KS X ISO IEC 26300 ODF)로 공식 전환했다. 그러나 실제 행정 현장에서는 변화가 거의 없었다. 표준은 표준이고, 현장은 현장이었다. 온나라 시스템, 각 지자체 전자문서 시스템이 HWP를 기반으로 구축됐고, 이를 한꺼번에 바꾸는 비용과 저항이 너무 컸다.

본인이 보기에 이것은 단순한 기술 문제가 아니다. 조달 경로의 관성이다. 한컴오피스 라이선스는 정부 조달 목록의 고정 항목이 됐고, 연간 갱신이 예산 계획에 들어갔다. 대안을 도입하려면 기존 예산 항목을 삭제하고 새 항목을 넣어야 하는 행정 절차가 필요하다. 기술 선택이 아니라 조달 관성이 락인을 유지한 핵심이다.

2.3 호환 도구 부재의 악순환

LibreOffice의 HWP 읽기 지원은 불완전하다. 표나 특수 기호, 한글 특유의 단 나누기 레이아웃이 깨진다. 사용자가 LibreOffice로 HWP를 열었다가 레이아웃이 망가지는 경험을 하면, 결국 한컴오피스로 돌아온다. 이 실패 경험의 반복이 "어차피 한글 써야 한다"는 인식을 굳힌다. 호환 도구가 불완전하니 락인이 지속되고, 락인이 지속되니 호환 도구 개발의 상업적 유인도 약하다. 전형적인 악순환이다.

3. HWPX란 무엇이며 전환이 왜 중요한가

3.1 HWPX의 기술 구조

HWPX는 2010년부터 한컴이 지원하기 시작한 신형 포맷이다. 한국 국가표준 KS X 6101로 2014년 지정됐으며, 내부는 OWPML(Open Word Processor Markup Language) 스펙을 따르는 XML 파일들을 ZIP으로 묶은 패키지다. 확장자를 .zip으로 바꾸면 압축 프로그램으로 내부 XML을 직접 열 수 있다.

이 구조는 DOCX(.docx = ZIP + XML)나 ODF(.odt = ZIP + XML)와 기술적으로 동일한 접근이다. AI와 자동화 도구 입장에서 보면 이는 결정적 차이다. XML을 파싱할 수 있는 라이브러리는 어느 언어에나 있다. python-hwpx 같은 라이브러리(Apache 2.0)가 Hancom Office 없이 HWPX를 읽고 편집하고 Markdown으로 변환할 수 있는 것도 이 개방 구조 덕분이다.

3.2 2026년 정부 전환 정책

2026년 정책 변화는 실질적이다. 2026년 5월 18일부터 행안부 온나라 시스템에서 .hwp 파일 첨부가 제한됐다. 중앙 부처와 지방정부 온나라 시스템에 개방형 문서(hwpx) 적용이 확대됐고, 공무원 이메일 시스템 '온메일'에서는 2026년 10월까지 hwpx 전환이 완료될 예정이다. 국가인공지능전략위원회가 행안부·문체부와 함께 전면 의무화를 선언한 것은 이번이 처음이다.

이 정책의 핵심 동력은 AI 활용이다. HWPX가 되면 공공문서를 AI가 파싱하고, 요약하고, 검색하고, 분석할 수 있는 파이프라인이 열린다. 단순한 포맷 교체가 아니라 공공 AI 인프라의 기반 작업으로 봐야 한다.

3.3 HWPX 전환의 한계

그러나 HWPX가 만능 해법은 아니다. 몇 가지 한계를 짚어야 한다.

첫째, 레거시 HWP 파일의 산이다. 수십 년간 축적된 구형 HWP 문서는 전환 정책과 무관하게 남는다. 2010년 이전 문서, 지방 기관의 오래된 공문서, 학교 배포 자료 상당수는 여전히 구형 HWP다. 이것을 HWPX로 일괄 변환하는 작업은 별도의 대규모 프로젝트를 필요로 한다.

둘째, HWPX가 ODF가 아니라는 점이다. HWPX는 개방형 XML 포맷이지만, ODF(오픈도큐먼트)와 같은 국제 표준은 아니다. LibreOffice, Google Docs 같은 글로벌 도구들이 HWPX를 네이티브로 지원하지 않는 이유다. 해외 개발자가 HWPX를 파싱하려면 여전히 별도 라이브러리가 필요하다. "개방 포맷으로 전환했다"고 해서 크로스플랫폼 문제가 자동으로 풀리지 않는다.

셋째, 민간·해외 수신자 문제다. 민간 기업이나 해외 기관에 HWPX 파일을 보냈을 때, 받는 쪽에 HWPX를 여는 도구가 없으면 문제가 재발한다. 공공 내부에서만 통하는 표준은 반쪽짜리 해법이다.

4. AI 시대에 HWP 호환성이 더 심각한 이유

4.1 RAG와 문서 검색의 벽

기업과 공공기관이 LLM을 내부 문서 검색에 활용하는 RAG(Retrieval-Augmented Generation) 파이프라인이 빠르게 확산 중이다. 문서를 임베딩하고 벡터 DB에 인덱싱하는 이 과정은 텍스트 추출이 전제다. HWP가 텍스트 추출을 막으면, 수십 년치 공문서가 RAG에서 완전히 배제된다. 정보는 있지만 AI가 쓸 수 없는 죽은 정보가 되는 것이다.

4.2 자동화 워크플로의 단절

현대 업무 자동화는 문서를 파이프라인의 입력으로 다룬다. N8N, Zapier, Make 같은 워크플로 도구가 문서를 받아 AI로 요약하고 다음 단계로 넘기는 흐름이 일반화됐다. HWP 파일이 이 파이프라인에 들어오는 순간, 파이프라인이 끊긴다. 공공문서 처리 자동화를 시도하는 개발자들이 제일 먼저 HWP 벽에 부딪히는 이유다.

4.3 접근성 문제: 맥·리눅스·해외 사용자

한컴오피스는 기본적으로 Windows 중심이다. 맥OS 버전이 있지만 기능 차이가 크고, Linux용은 사실상 없다. 맥을 쓰는 개발자, 리눅스 서버 환경, 해외 파트너 기관은 HWP 파일을 받으면 열기 위한 별도 작업이 필요하다. 이것은 파일 포맷의 접근성 문제다. 2026년에 "이 파일을 열기 위해 특정 유료 소프트웨어를 설치해야 한다"는 요구는 설계 실패에 가깝다.

5. 개발자·사용자를 위한 실용 해법 (2026년 6월 기준)

5.1 Claude에 HWP를 읽히는 법: HWP-MCP

Claude Desktop이나 Claude Code에 HWP-MCP 서버를 연결하면, 한 줄 설치로 HWP·HWPX 파일을 Claude가 직접 읽는다. Hancom 라이선스 없이 맥과 Windows에서 모두 동작하며, 로컬에서 실행되기 때문에 문서가 외부 서버로 나가지 않는다. MCP(Model Context Protocol) 표준 기반이라 Claude Code, Claude Desktop, Cursor, VS Code Copilot, ChatGPT 앱 등 MCP를 지원하는 환경에서 동일하게 동작한다.

이 방식의 장점은 워크플로 통합이다. Claude가 hwp_read 도구를 자동으로 호출해 결과를 테이블 형태로 돌려주므로, 사용자는 변환 과정을 신경 쓸 필요가 없다. 기업 내부망 환경에서도 외부 API 노출 없이 온프레미스 배포가 가능하다.

5.2 파이썬 파이프라인 구성: pyhwp, python-hwpx, kordoc

자체 문서 처리 파이프라인을 만드는 개발자라면 세 가지 라이브러리가 핵심 선택지다.

  • pyhwp (PyPI): HWP5(구형 바이너리) 파서. GNU AGPL. ODF 또는 텍스트로 실험적 변환 가능. 오래된 공문서 배치 처리에 유용하다.
  • python-hwpx (GitHub: airmang/python-hwpx): 순수 Python, Apache 2.0. HWPX를 Markdown(평문·서식 보존 모드 모두)으로 변환, 양식 채우기, 템플릿 분석을 지원한다. Hancom Office 완전 불필요.
  • kordoc (GitHub: chrisryugj/kordoc): HWP3·HWP·HWPX·HWPML·PDF·XLS·XLSX·DOCX를 Markdown으로 변환. CLI와 MCP 서버 통합. 신구 대조, 양식 자동 채우기까지 지원하는 올인원 파서다.

이 라이브러리들로 만든 파이프라인 패턴은 단순하다: HWP/HWPX 파일 수신 → Markdown 변환 → LLM에 텍스트 투입 → 결과 후처리. 어떤 LLM이든 Markdown을 소화하므로 모델 종속성이 없다.

5.3 PyMuPDF Pro 상용 경로

상용 솔루션이 필요한 기업 환경이라면 PyMuPDF Pro가 HWP·HWPX를 포함한 한국어 문서 파싱을 지원한다. 엔터프라이즈 수준의 레이아웃 구조 추출이 필요한 경우(표, 단 레이아웃, 이미지 위치 등)에 선택할 수 있다. 다만 오픈소스 옵션이 충분하지 않을 때의 대안으로 봐야 한다.

5.4 Pandoc 경로의 현실

범용 문서 변환기 Pandoc은 HWPX 리더·라이터를 아직 공식 지원하지 않는다. GitHub에 HWPX Writer 제안 이슈(Discussion #11569)가 올라와 있지만 2026년 6월 기준 아직 미구현이다. Pandoc 기반 파이프라인을 쓰는 팀은 kordoc 또는 python-hwpx로 먼저 Markdown 변환을 거친 후 Pandoc에 투입하는 2단계 경로를 써야 한다.

DOCXZIP + XMLOOXML (ISO 29500)국제 ISO광범위용이
ODTZIP + XMLODF (ISO 26300)국제 ISO광범위용이

이 표에서 HWPX의 위치가 명확하다. 구형 HWP보다 훨씬 낫지만, DOCX나 ODT처럼 국제 표준화·글로벌 도구 지원이 이뤄지지 않은 중간 단계다. 국내 공공 시스템 내에서의 AI 호환성은 개선되지만, 해외나 글로벌 도구와의 완전 호환은 여전히 별도 작업이 필요하다.

7. 진짜 해법은 무엇인가: 본인 관점

이 문제를 두고 "한글 파일 포맷을 버려라"는 강경론도 있고 "HWPX로 충분하다"는 낙관론도 있다. 본인 생각은 그 중간 어딘가다.

단기(지금 당장): HWP-MCP, kordoc, python-hwpx 같은 파서 레이어를 LLM 파이프라인에 끼워 넣으면 즉시 호환성을 확보할 수 있다. 완벽하지 않더라도 실용적이다. 공공 AI 서비스를 구축하는 개발자라면 이 경로를 먼저 시험해야 한다.

중기(HWPX 전환 완료 후): 온나라 시스템 전환이 완료되면 신규 공문서는 HWPX로 유통된다. python-hwpx 수준의 파이프라인으로 대부분의 문서를 처리할 수 있게 된다. 그러나 레거시 HWP 변환 작업 없이는 과거 문서가 여전히 배제된다.

장기(근본 해법): 국제 표준 포맷(DOCX 또는 ODT)을 공공 문서의 배포·보존 표준으로 추가 지정하는 것이 가장 근본적이다. HWPX는 작성 포맷으로 허용하되, 대외 배포·장기 보존·AI 처리 용도로는 PDF·DOCX·ODT를 병행 채택하는 이중 표준 정책이 현실적인 방향이라고 본다. 이것은 이미 일부 선진국이 취하는 방식이다.

핵심은 이것이다. 포맷 표준은 기술 문제이기 전에 정치·조달 문제다. HWPX 전환 자체도 기술팀이 아니라 국가인공지능전략위원회와 행안부·문체부의 정치적 의사결정이 이끌었다. 근본 해법 역시 기술 커뮤니티의 제안만으로는 부족하고, 정책 결정자가 "글로벌 표준 호환"을 조달 평가 기준으로 명시할 때 실현된다.

8. 결론: 지금 할 수 있는 것부터

2026년 6월 기준, 상황은 2024년에 비해 명백히 나아졌다. 정부가 HWPX 전환을 강제했고, ChatGPT의 HWP 네이티브 지원이 나왔으며, HWP-MCP 같은 오픈소스 브릿지 도구가 실용화됐다. 그러나 구조적 문제는 완전히 해소되지 않았다. 레거시 HWP 산, 글로벌 도구의 HWPX 미지원, 국제 표준과의 간극이 여전히 남는다.

개발자라면 지금 당장 파이프라인에 kordoc 또는 HWP-MCP를 끼워 넣어 실험하라. 정책 담당자라면 HWPX를 내부 표준으로 굳히면서 동시에 DOCX·ODT 병행 배포를 검토할 시점이다. 이 문제는 30년짜리 관성이 만들었으나, 해법은 지금 시작할 수 있다.
