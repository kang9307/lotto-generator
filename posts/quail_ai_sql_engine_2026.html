계기 — SQL 함수 하나가 행마다 모델을 부른다

GeekNews에 2026년 10월 6일 등록된 Quail은 SQL 안에서 LLM을 부르는 쿼리, 곧 AI-SQL을 실행하는 엔진이다. 원문은 Full Stack Data Lab 블로그에 9월 24일 올라온 글이고 저자는 Shreya Shankar, Charles Frye, Fergus Finn, Arnav Dhariya, Joseph Barrow, Meryem Arik 여섯 명이다. 이름은 QUery-Aware Inference Layer의 머리글자이며, 원문은 목표를 오픈 웨이트 모델을 대상으로 쿼리 계획과 모델 추론을 함께 최적화하는 것이라고 적는다.

AI-SQL은 AI 함수라고도 불린다. 원문의 정의로는 LLM을 호출하는 사용자 정의 함수로 SQL을 확장한 것이고, 사용자는 함수마다 자연어 프롬프트를 적는다. 원문이 든 가장 짧은 예는 다음과 같다.

SELECT *
                    FROM reviews AS r
                    WHERE AI.IF(PROMPT('Does this review discuss the ending?\n\n{0}', r.review));

원문은 이런 기능을 제공하는 곳으로 Snowflake Cortex AISQL, BigQuery AI 함수, Databricks AI Functions, 그리고 최근의 MotherDuck을 든다. 문제는 실행 비용이다. AI 함수는 프롬프트를 행 단위로 평가하므로 SQL 쿼리 하나가 수십만에서 수백만 번의 모델 호출을 만든다. 필터는 행마다 호출 한 번이 필요하고, 단순한 조인은 두 입력 테이블의 모든 행 쌍마다 호출 한 번이 필요하다.

이 비용을 줄이려는 연구는 이미 여럿이다. 원문은 UC Berkeley의 DocETL, Stanford의 LOTUS, MIT의 Palimpzest, Cornell의 ThalamusDB를 들고, 이 시스템들과 데이터베이스 벤더가 주로 쓰는 방법을 두 갈래로 요약한다. 하나는 LLM 호출 자체를 최대한 없애는 것이고(MOAR, Task Cascades, Abacus), 다른 하나는 가능한 곳에 더 싼 모델을 쓰는 것이다(BARGAIN). 원문의 출발점은 그다음 문장이다. 이런 최적화를 거친 뒤에도 쿼리 계획에는 수십만에서 수백만 번의 호출이 남을 수 있다. Quail이 겨냥하는 것은 남은 호출을 어떻게 실행하느냐다.

호출을 데이터프레임 연산으로 선언하는 인터페이스 쪽 논의는 fenic과 시맨틱 연산자에서, 예·아니오 판정에 특화된 모델의 실측은 Jev 실측 평가에서, KV 캐시의 개념은 KV 캐시 공유와 어텐션 압축에서 다뤘다. 여기서는 그 아래층, 곧 호출 수가 정해진 뒤 실행 엔진에서 시간이 어디로 새는지와 원문이 그것을 어떤 조건에서 측정했는지를 본다.

요청을 하나씩 보내면 어디서 시간이 새는가 — BIO-4 사례

자연스러운 발상은 vLLM 같은 범용 추론 엔진에 쿼리 계획을 실행시키는 것이다. 원문은 서로 관련된 수백만 건의 모델 호출을 별개의 요청으로 보내면 비용이 크다고 말하고, 그 근거로 BIO-4라는 쿼리를 든다. 의료 보고서 데이터셋과 이상 반응 용어 데이터셋이 주어졌을 때, 심혈관계 반응과 신경계 반응을 둘 다 언급하는 중대한 이상 사례 보고서를 찾는 쿼리다. BioDEX 데이터셋에 기반하며 SQL 형태는 원문 주석 1에 실려 있다.

SELECT r.id,
                        n.id AS neurological_reaction_id,
                        c.id AS cardiovascular_reaction_id
                    FROM reports AS r
                    JOIN reaction_terms AS n
                        ON AI.IF(PROMPT(
                            'Does the medical report in {0} describe the reaction in {1} as '
                            'something the patient experienced?',
                            r.report,
                            n.term
                        ))
                    JOIN reaction_terms AS c
                        ON AI.IF(PROMPT(
                            'Does the medical report in {0} describe the reaction in {1} as '
                            'something the patient experienced?',
                            r.report,
                            c.term
                        ))
                    WHERE AI.IF(PROMPT(
                        'Does {0} describe a serious or life-threatening adverse event?',
                        r.report
                    ))
                    AND AI.IF(PROMPT(
                        'Is this reaction neurological, affecting the nervous system? {0}',
                        n.term
                    ))
                    AND AI.IF(PROMPT(
                        'Is this reaction cardiovascular, affecting the heart or blood vessels? {0}',
                        c.term
                    ));

입력은 긴 보고서 5,000건과 반응 용어 4,144개이고, 조인이 둘이라 용어 테이블은 두 번 쓰인다. 원문 그림 1의 논리 계획은 세 단계다.

  • 보고서를 중대한 이상 사례인지로 거른다.
  • 두 번 쓰이는 반응 용어 입력을 각각 심혈관계 반응, 신경계 반응인지로 거른다.
  • 살아남은 보고서를 먼저 심혈관계 용어와, 이어서 신경계 용어와 조인한다.

필터가 하나도 없다고 가정하면 조인 하나의 후보 쌍은 5,000 × 4,144 = 2,072만 개다(계산). 필터가 앞에서 입력을 줄이므로 실제 요청 수는 이보다 적고, 원문은 BIO-4가 수백만 건의 요청으로 컴파일된다고만 적는다.

vLLM으로 실행하는 기준선은 데이터베이스가 하는 방식을 따른다. 필터 입력마다 프롬프트 하나, 조인은 후보 보고서·용어 쌍마다 프롬프트 하나를 만들고 각각을 별개의 추론 요청으로 보낸다. 조인 프롬프트에서는 훨씬 긴 보고서를 앞(앵커)에, 용어를 뒤(파트너)에 두어 접두의 KV 재사용을 늘리고, 연산자를 한 번에 하나씩 실행하면서 같은 문서의 요청이 붙어서 평가되도록 순서를 정한다. 기준선도 이미 KV 재사용을 의식하고 짠 구성이라는 뜻이다.

비교의 잣대로 원문은 같은 계획의 이론적 하한을 먼저 계산한다. 토큰 길이로부터 모델의 산술 연산량과 HBM 트래픽을 세고 루프라인 모델로 시간을 추정한 값이며, 원문은 이를 speed of light(SoL) 추정치라고 부른다. 전제는 세 가지다.

  • GPU가 최고 처리량을 낸다.
  • CPU 작업과 GPU 작업이 전부 겹친다.
  • 유지할 KV를 둘 공간에 제한이 없다.

어떤 구현도 이 전제를 다 만족할 수 없으므로 SoL은 낙관적인 하한이다. BIO-4의 SoL 추정치는 894.37초, 곧 14.91분이다. 각 요청은 TRUE 또는 FALSE로 제한된 토큰 하나만 내므로 모델의 일은 전부 프리필이고, 요청이 수백만 건이니 H100에 넣을 큰 배치가 늘 준비되어 있어야 한다. 원문이 기대한 것은 vLLM이 이 조건에서 SoL에 가깝게 가는 것이었다.

측정 결과는 달랐다. vLLM 0.26.0, Qwen3 4B FP8, H100 1장, 스케일 팩터 1.0에서 vLLM 기준선은 6.84시간이 걸렸고 이는 SoL 추정치의 27.55배다. 원문이 든 원인은 둘이다.

  • 호스트 오버헤드(주된 원인). CPU가 요청을 스케줄링하고 추적하는 데 긴 시간을 쓰는 동안 H100이 기다린다. 원문 그림 2는 첫 조인의 3.5초 구간 프로파일러 추적에서 GPU가 비는 틈을 보여 준다.
  • KV regret. vLLM이 나중에 다시 필요한 KV를 버리는 일이 있다. 스케일 팩터 1.0의 BIO-4에서 처리한 토큰은 1억 2,430만이 아니라 1억 7,460만이었다. 5,030만 토큰, 40%의 일을 더 한 것이다.

병목이 모델의 연산 속도가 아니라 요청을 다루는 CPU 쪽과, 다시 필요한 KV를 버리는 데 있었다는 것이 이 사례의 내용이다. 원문의 결론은 두 낭비를 AI-SQL에 맞춘 추론으로 줄일 수 있고 줄여야 한다는 것이다.

범용 추론 엔진과 무엇이 다른가 — 항목별 대조

Quail은 모델과 GPU 연산을 처음부터 다시 구현하지 않았다. forward pass에 필요한 연산은 vLLM의 모델 구현에서 가져오고, 그것을 자체 스케줄러와 KV 관리자로 실행한다. 차이는 쿼리 전체를 아는 쪽이 추론의 순서와 캐시를 정한다는 데 있다. 아래 표는 원문이 범용 추론(기준선으로 쓴 vLLM)과 Quail을 직접 견준 항목만 모은 것이다.

항목요청 단위로 보내는 범용 추론(원문의 vLLM 기준선)Quail
실행 순서의 결정서로 관련된 호출이 별개의 요청으로 들어간다. 원문 기준선은 보내는 쪽에서 연산자를 하나씩 실행하고 같은 문서의 요청이 붙도록 정렬했다계획기가 필터·조인 순서, 조인 앵커, forward pass당 토큰 수를 정하고 실행 엔진이 그 물리 계획을 실행한다

표의 마지막 두 줄은 Quail 쪽이 불리하거나 비어 있는 항목이다. 특히 행 간 접두 재사용은 vLLM에 있고 Quail에 없는 기능이며, 뒤에서 볼 AGENT-1의 결과를 가른다.

계획 단계 — SQL 재작성과 추론 전용 결정을 함께 내린다

Quail은 쿼리 프런트엔드, 쿼리 계획기, 실행 엔진으로 이루어진다. 사용자는 Arrow 테이블이나 데이터셋, AI-SQL 또는 파이썬 쿼리, 쓸 모델과 GPU를 준다. AI-SQL은 Snowflake와 BigQuery의 표기(AI_FILTER와 AI.IF)를 둘 다 받고, pandas와 비슷한 파이썬 쿼리 빌더도 있다. 쿼리는 SQLGlot으로 파싱되어 논리 계획이 된다. 원문은 설계가 확장 가능한 분석 쿼리 엔진인 Apache DataFusion에서 영감을 받았고, 연산자·계획 규칙·실행 백엔드·모델·하드웨어 지원을 추가할 수 있다고 적는다.

데이터베이스 최적화기는 이미 필터 내리기, 술어 재배치, 조인 순서 선택 같은 규칙을 쓴다. 원문에 따르면 AI-SQL은 여기에 새로운 결정을 보탠다. 어느 문서를 조인의 앵커로 둘지, 어느 KV가 뒤 연산자에서 필요할지, forward pass 하나에 모델 작업을 얼마나 넣을지다. Quail은 두 종류의 결정을 함께 계획한다. 논리 계획이 주어지면 다음 네 단계를 거친다.

  1. 데이터셋 통계. 입력 데이터셋마다 행 수, 평균 문서 길이, 최대 문서 길이를 추정한다.
  2. forward pass와 KV 한도. 고른 모델 크기와 GPU 메모리로부터 forward pass 하나가 처리할 최대 토큰 수를 계산한다. HBM에서 모델 가중치와 forward pass 두 번 몫을 떼어 두고 나머지를 KV 캐시에 쓴다. 원문은 이것이 vLLM보다 보수적이며 개선 여지가 있을 것이라고 덧붙인다.
  3. SQL 재작성. 프로젝션과 필터를 원본 데이터셋 쪽으로 내린다. 필터는 추정 비용과 선택도로 순서를 정하는데, 원문은 잘 알려진 선행 연구(Hellerstein과 Stonebraker 등)를 따른다고 밝힌다. 조인은 Selinger식 탐색(System R)으로 조인 순서와 조인별 앵커를 고른다. 비용 모델은 앞의 SoL 추정치를 쓴다.
  4. 추론 전용 재작성. 논리 계획을 물리 연산자의 DAG로 옮긴다. AiFilter는 문서에 대해, AiJoin은 앵커를 공유하는 문서 쌍에 대해 AI 술어를 평가한다. 각 연산자는 프롬프트, 모델, forward pass 토큰 예산, KV 설정을 갖는다. KV 설정의 예로 원문은 뒤에 연산자가 이어지므로 KV를 HBM에 써 둘지 여부를 든다.

사용자가 줄 수 있는 계획 정보는 두 가지다. 선택도(selectivity)는 통과할 것으로 예상하는 문서 또는 문서 쌍의 비율이고, 조인의 앵커(anchor)는 KV 재사용을 위해 프롬프트에서 어느 입력을 앞에 둘지다. 블로그 글은 선택도가 없으면 술어를 적힌 순서대로 두고, 앵커가 없으면 계획기가 고른다고 설명한다.

앵커가 성립하려면 문서가 프롬프트에서 질문보다 앞에 놓여야 한다. 원문 주석 2는 번호 자리표시자({0}, {1})가 질문 안에서 나오는 위치와 문서가 실제로 놓이는 위치가 같을 필요가 없다고 설명하고, 보고서와 용어를 견주는 프롬프트에서 모델이 받는 입력을 다음과 같이 보인다.

DOCUMENT:
                    [contents of r.report]
                    
                    (The document above is DOCUMENT {0}.)
                    
                    Evaluate TRUE or FALSE for the following question:
                    Does {0} mention {1}?
                    
                    DOCUMENT {1}:
                    [contents of n.term]
                    ANSWER:

보고서가 맨 앞에 있으므로 같은 보고서를 다른 용어와 견줄 때 그 KV를 다시 쓸 수 있다. 실행 방식에도 계획의 결과가 반영된다. Quail은 벡터화 쿼리 실행에서 착안해 중간 결과를 디스크나 주 메모리에 통째로 구체화하지 않고 연산자 사이로 바로 흘린다. BIO-4에서는 보고서 배치가 첫 필터를 통과하는 즉시 첫 조인으로 넘어가고, 두 조인이 진행되는 동안 보고서의 KV 캐시가 HBM에 유지되어 걸러진 반응 용어와 견줄 때 KV를 다시 계산하지 않는다.

실행 단계 — KV 되감기와 forward pass의 세 가지 변경

실행 엔진은 물리 계획 실행기, KV 관리자, 추론 프로그램 세 부분이다. 실행기는 Volcano처럼 풀(pull) 기반이되 MonetDB처럼 한 번에 한 배치를 처리한다. 실행 전에 AI 필터나 조인이 참조하는 문서 열을 Gigatoken으로 전부 토큰화하고 GPU마다 모델 사본 하나를 올린다. 실행 중에는 GPU가 한 배치를 처리하는 동안 CPU가 다음 배치를 준비한다.

KV 관리자는 GPU마다 고정 크기의 KV 페이지 풀을 HBM에 두고, 모델 평가가 끝날 때마다 뒤의 평가가 다시 쓸 수 있는 KV만 남긴다. 필터에서는 문서를 술어별 질문보다 앞에 둔다. 술어가 TRUE나 FALSE를 내면 질문 부분의 KV를 버리고 문서 KV의 끝으로 「되감는다(rewind)」. 그 뒤 술어가 TRUE이고 다른 AI 연산자가 그 문서를 쓴다면 되감은 KV를 HBM에 유지하고, 아니면 해제한다. 조인에서도 같은 방식으로 되감은 KV를 유지한다. 공간이 모자라 축출이 필요하면 가장 짧은 문서부터 내보낸다. 어텐션이 이차 연산이라 긴 문서일수록 재계산에 불균형하게 오래 걸린다는 것이 원문의 이유다.

추론 프로그램은 AiFilter나 AiJoin 하나가 GPU에서 실행되는 절차다. 토큰 ID와 위치, 재사용할 KV 페이지의 위치를 받아 행 또는 행 쌍마다 TRUE와 FALSE의 점수를 돌려준다. 원문은 forward pass에 가한 변경을 「작은 변경 세 가지」라고 부른다.

  • 작은 연산의 융합. 정규화와 FP8 양자화, Q/K 정규화와 RoPE, 활성화와 FP8 양자화를 각각 하나로 합친 Triton 커널을 쓴다. 커널 실행 횟수와 중간 HBM 트래픽이 줄어든다. 원문은 이 작업이 AI 에이전트로 매우 쉽게 되며 새로운 커널 설계 아이디어가 필요 없다고 적는다.
  • 조인에 특화한 어텐션. AI 조인은 앵커 하나를 많은 파트너와 견준다. 표준 vLLM은 앵커·파트너 쌍을 각각 별개의 시퀀스로 다루어 파트너마다 같은 앵커 KV를 다시 읽는다. Quail은 앵커를 공유하는 파트너를 묶고 어텐션을 둘로 나눠 계산한다. FlashAttention 3 호출 하나가 각 파트너 안의 인과적 어텐션을 계산하고, 다른 호출이 모든 파트너의 쿼리를 공유 앵커 KV에 적용한다. 두 결과는 log-sum-exp 값과 온라인 소프트맥스 공식으로 합쳐지며, 원문은 이것이 앵커·파트너 전체 시퀀스에 대한 어텐션과 같은 출력을 낸다고 적는다.
  • 출력 헤드를 TRUE와 FALSE로 제한. 보통은 출력 헤드가 어휘의 모든 토큰에 점수를 매긴다. AI 필터와 조인에는 TRUE나 FALSE를 나타내는 토큰 ID의 점수만 있으면 되므로, 최종 은닉 상태에 출력 헤드 행렬의 해당 행만 곱한다. Qwen에서는 답마다 네 가지 표기(TRUE, 앞 공백이 붙은 TRUE, True, 앞 공백이 붙은 True와 그에 대응하는 FALSE 쪽)의 토큰을 점수화한다.

조인 어텐션에 대해 원문은 접두를 공유하는 여러 갈래를 서로 보지 못하게 한 채 함께 평가하는 「트리」 기반 어텐션의 계보를 따른다고 밝히고, 추측 디코딩의 SpecInfer와 공유 접두 어텐션의 Hydragen을 예로 든다. Quail은 같은 구조를 디코딩이 아니라 프리필에 적용한다. 지금까지의 기법을 줄이는 대상과 전제 조건으로 정리하면 다음과 같다.

원문이 보고한 성능 수치는 전부 시스템 전체 단위이고, 위 표의 넷째 열은 원문이 각 기법에 붙인 설명을 옮긴 것이다. 둘째·셋째 열은 원문 서술을 재배열한 것이다. 원문은 성능 목표를 KV regret 최소화, CPU 스케줄링 오버헤드를 줄여 GPU를 계속 일하게 하기, GPU가 일하는 동안 높은 MFU(모델 FLOP/s 활용률)에 이르기 세 가지로 들고, 현재 평가는 앞의 둘에 초점을 두며 MFU 연구는 뒤로 미룬다고 밝힌다.

측정 조건 — 무엇을 같게 두고 무엇을 견주었나

배수 하나를 읽기 전에 그 배수의 분모를 알아야 한다. 원문 4.1절과 주석 11이 밝힌 조건은 다음과 같다.

  • 벤치마크. 연구실이 직접 만든 QUAIL-B. IMDB 리뷰, 의료 보고서, 사실 검증 주장, 법률 문서, 소프트웨어 에이전트 기록을 다루는 AI-SQL 쿼리 29개이며 필터, 연속 필터, 하나 이상의 조인을 포함한다.
  • 스케일 팩터. 데이터셋마다 0.1, 0.5, 1.0이 있다. 29개 쿼리 전체 비교는 0.1에서 했고, BIO-4만 1.0에서 따로 보았다. QUAIL-B README의 표로는 0.1이 IMDB 리뷰 5,000건, BioDEX 보고서 500건과 용어 1,127개, 에이전트 기록 1,772건 규모다.
  • 모델과 하드웨어. 모든 쿼리가 Qwen3 4B FP8, BF16 KV, H100 1장이다. Quail과 각 vLLM 기준선은 같은 물리 GPU에서 차례로 실행했다.
  • 같게 둔 것. 모델, 프롬프트, 논리 쿼리 계획이 같다. 두 기준선 모두 Quail의 쿼리 계획기가 고른 연산자 순서를 쓰고, 연산자마다 요청을 준비해 KV 재사용이 좋아지도록 정렬한다.
  • 토큰화. 공정성을 위해 두 기준선도 vLLM의 Hugging Face 토크나이저 대신 Quail과 같은 Gigatoken을 쓴다.
  • 기준선 ① stock vLLM. 연산자를 한 번에 하나씩 실행하는 구성이다.
  • 기준선 ② pipelined vLLM. 필터나 조인이 여럿인 쿼리에서 연속한 필터 사이, 연속한 조인 사이로 요청을 이어 보내는 구성이다.
  • vLLM 설정. 버전 0.26.0, 자동 접두 캐싱 사용. 최대 배치 토큰 25,305, 시퀀스 4,096, GPU 메모리 사용률 0.91, 8,192토큰용 CUDA 그래프 하나. 원문은 이것이 안정적으로 돌아가는 가장 큰 설정이며 더 키우면 GPU 메모리가 부족했다고 적는다.
  • 비용 환산. 쿼리 실행 시간(시간 단위)에 H100 시간당 3.9492달러를 곱한다. Modal의 H100 가격이다.

지표는 셋이다. KV regret은 반복된 모델 작업으로, 재사용 가능한 접두를 한 번씩만 계산하는 데 필요한 최소치를 넘어선 새 입력 토큰 수다. 쿼리당 비용은 위 환산식 그대로다. 초당 입력 토큰은 요청된 입력 토큰 총량을 실행 시간으로 나눈 값이며, KV에서 꺼내 쓴 토큰까지 포함해 평가된 프롬프트의 전체 길이를 센다. 앞의 둘은 낮을수록, 마지막은 높을수록 좋다.

이 조건에서 읽을 점이 둘 있다. 연산자 순서를 고른 효과와 빠른 토크나이저는 기준선에도 이미 들어가 있으므로, 보고된 배수는 그 나머지, 곧 KV 계획과 실행 방식의 차이를 잰 값으로 읽힌다. 그리고 초당 입력 토큰은 캐시에서 꺼낸 토큰도 분자에 넣으므로 재사용이 많은 쿼리일수록 값이 커진다. 서로 다른 쿼리의 처리량을 맞대어 엔진의 빠르기를 말하기는 어렵다. 둘 다 원문의 정의에서 따라 나오는 해석이며 원문의 문장은 아니다.

BIO-4는 Quail이 현재 잘 다루는 종류의 재사용을 담고 있다. 긴 공유 문서, 조인 둘, 실행 전에 순서가 알려진 수백만 건의 관련 호출이다. Quail은 29.26분으로 stock vLLM의 6.84시간보다 14.04배 빠르고 SoL 추정치의 1.96배다. 파이프라이닝을 넣어도 vLLM은 4.00시간이 걸렸으므로 그쪽과 견주면 약 8.2배다(계산). 재계산한 KV는 1,800만 토큰 대 5,030만 토큰이다.

AGENT-1은 다른 종류의 재사용을 담고 있다. 소프트웨어 에이전트 실행에서 나온 누적 스냅숏 1,772개를 거르는 쿼리로, 원문이 단순화해 실은 형태는 다음과 같다.

SELECT t.id
                    FROM agent_traces AS t
                    WHERE AI.IF(PROMPT(
                        'Did the agent recover after trying an approach that did not work?\n\n{0}',
                        t.trace
                    ));

누적 스냅숏이라 원문 표 3의 예에서 같은 에이전트 기록의 10번째 턴 행은 5번째 턴 행의 내용 전체로 시작한다. 서로 다른 행이 겹치는 접두를 갖는 것이다. stock vLLM의 자동 접두 캐싱은 토큰 접두가 일치하는 행 사이에서 KV를 재사용한다. Quail은 현재 같은 문서가 쿼리 안에서 다시 나올 때만 KV를 재사용하고 서로 다른 문서 사이에서는 하지 않는다. 그 결과 Quail의 KV regret은 1,189만 토큰, stock vLLM은 23,928토큰이고, 실행 시간은 239.12초 대 103.07초로 Quail이 2.32배 걸린다. 이 쿼리에서도 stock vLLM은 SoL 추정치 47.47초의 2.17배다.

원문은 Quail에 자동 접두 캐싱을 넣을 계획이라고 밝히면서 조건을 붙인다. AI-SQL 쿼리가 만들어 내는 요청량에서도 조회가 싸게 유지되어야 한다는 것이다. 29개 중 stock vLLM이 이긴 두 쿼리는 AGENT-1과 AGENT-2이고, 원문은 둘 다 이 빠진 기능이 원인이라고 설명한다.

속도를 잰 것과 판정 품질을 잰 것은 다르다

지금까지의 수치는 전부 같은 모델이 같은 프롬프트에 답하는 속도와 비용이다. 모델의 판정이 맞는지는 별개의 질문이고, 원문에서 이 질문에 닿는 대목은 넷이다.

  • 모델 간 답 일치율. Quail은 토큰당 활성 파라미터가 4B인 더 큰 MoE 모델 DiffusionGemma 26B-A4B FP8도 지원한다. 스케일 팩터 0.1의 IMDB-2에서 DiffusionGemma의 답은 Qwen3 32B의 답과 88.89% 일치했고 Qwen3 4B는 76.41%였다. 실행 시간은 H100 1장에서 32.41초로 Qwen3 4B의 21.20초의 1.53배다. 이 수치는 사람이 붙인 정답과의 비교가 아니라 더 큰 모델의 답과의 일치율이다.
  • 프롬프트 배치. 문서를 앞으로 옮기는 배치가 KV 재사용의 전제인데, 원문 주석 2는 다른 프롬프트 배치가 정확도에 영향을 주는지는 열린 질문으로 남아 있고 모델이 좋아질수록 덜 중요해질 것으로 기대한다고 적는다.
  • 벤치마크의 기준 답. QUAIL-B README는 정확도가 이 벤치마크의 초점이 아니라고 적는다. 대부분의 라벨은 임의로 고른 모델 하나(Qwen3 32B FP8)의 답이어서 그것을 기준으로 정확도를 재는 것은 큰 의미가 없다는 설명이다. 실제 라벨이 있는 것은 조인 두 종류로, FEVER의 주장 주석과 LePaRD의 인용 연결이다.
  • 연산의 동등성. 조인 전용 어텐션에 대해 원문은 전체 시퀀스 어텐션과 같은 출력을 낸다고 적는다. 이는 계산 방식에 대한 서술이다.

비용 비교도 같은 선에서 읽어야 한다. 원문 3.1절의 예제는 IMDB 리뷰 10만 건에 AI 필터 둘을 거는 쿼리다. 계획 출력의 추정 시간은 124초였고 실제 실행은 277.41초, 콜드 부팅 57.65초, 초당 360.5문서였으며, H100 1장에서 모델 시작을 포함해 0.3675달러가 들었다. 선택도 힌트는 25%와 50%였고 실제 통과율은 0.283과 0.568로 찍혔다. 원문은 같은 작업을 GPT-5 nano의 현재 가격으로 하면 약 1.75달러, 곧 4.8배라고 추정한다. 이 추정에는 캐시된 토큰 가격을 쓰고 캐시가 무한하다고 보아 재사용 가능한 문서 토큰 전부에 그 요율을 적용했다는 가정이 붙어 있고, IMDB 데이터셋이 이미 디스크에 있어 내려받는 시간과 비용은 빠져 있다. 두 금액은 같은 일을 하는 비용의 비교이며, 두 모델의 답이 같은 품질이라는 뜻까지 담은 숫자는 아니다.

공개 상태와 지원 범위 — 블로그 시점과 저장소 시점

발표 주체는 Full Stack Data Lab이다. 연구실 홈페이지는 Shreya Shankar가 이끄는 컴퓨터과학 연구실이며 2027년에 Carnegie Mellon University로 옮긴다고 소개하고, 저장소 README는 Quail이 CMU의 Full Stack Data Lab에서 개발되고 있다고 적는다. 원문은 연구에 쓴 컴퓨팅을 Modal이 후원했다고 밝힌다. 공개 상태는 다음과 같다.

  • 라이선스. 원문은 Quail이 MIT 라이선스라고 적고, 저장소의 LICENSE 파일도 MIT License(Copyright (c) 2026 Quail contributors)다.
  • 설치. README에 따르면 PyPI 패키지 이름은 quail-engine이고 파이썬에서는 quail로 임포트한다. Python 3.12와 CUDA GPU가 필요하다. 블로그의 Modal 예제는 quail-engine==0.1.0을 지정한다.
  • 모델. 블로그 글은 Qwen3 4B FP8, Qwen3 32B FP8, DiffusionGemma 세 모델을 H100 GPU에서 지원한다고 적는다. README의 표는 Qwen3 4B와 DiffusionGemma 26B-A4B를 NVIDIA H100 SXM에, Qwen3 32B를 NVIDIA RTX PRO 6000 Blackwell Server Edition에 대응시킨다.
  • GPU 수. README는 쿼리당 1, 2, 4, 8장이라고 적는다. 블로그 글은 다중 GPU 지원이 아직 기초적이라고 설명한다. GPU마다 모델 사본과 KV 풀을 하나씩 두고, 필터 문서와 조인 앵커를 무작위로 균등하게 나눠 독립적으로 실행한 뒤 CPU에서 결과를 합친다.
  • 연산자. 블로그 글 기준 현재 릴리스는 AI 필터와 조인, 관계형 프로젝션과 LIMIT을 지원한다. README는 여기에 EXISTS와 NOT EXISTS, 수치 점수(AI.SCORE), 분류(AI.CLASSIFY)를 더해 적고, AI.EXTRACT와 AI.MAP은 추가 예정이라고 한다.
  • 실행 형태. README는 GPU가 있는 기계에서 도는 선택적 HTTP 서버(Quail Server)를 소개한다. 블로그 글에는 전용 GPU가 없을 때 쿼리 전체를 Modal GPU 함수 안에 넣는 예제와 라이브 데모 링크가 있다.

블로그 글과 저장소의 서술이 다른 곳이 있다는 점도 적어 둔다. 지원 연산자와 Qwen3 32B의 대상 장치가 그렇고, 선택도 기본값도 그렇다. 블로그 글은 선택도가 없으면 술어를 적힌 순서대로 둔다고 했는데 SQL 문서는 기본값이 0.2(20%)이며 이 힌트가 모델의 답을 바꾸지 않는다고 적는다. KV regret도 블로그 글은 토큰 수로, QUAIL-B README는 새로 계산한 토큰 대비 백분율로 정의하고, 쿼리 수도 블로그 글은 29개, README는 50개라고 적는다. 지원 모델도 블로그 글과 README는 세 가지를 적는데, SQL 문서는 Qwen3 reranker와 Decision 2.0 Kai도 든다. 원문 스스로 Quail을 아직 활발히 만드는 중이라고 밝히므로 실제로 쓸 때의 기준은 설치한 버전의 문서다. SQL 문서가 지원하지 않는다고 명시한 것은 다음과 같고, 쓰면 컴파일 오류가 난다.

  • 윈도 함수와 QUALIFY
  • UNION, EXCEPT, INTERSECT
  • 조건 사이의 OR
  • 열 비교에서의 BETWEEN, LIKE, 산술
  • AI 연산자가 없는 쿼리
  • 관계형 술어만 있고 AI 연산자가 없는 JOIN
  • 외부 조인(LEFT, RIGHT, FULL)
  • AI.EXTRACT와 AI.MAP

같은 문서는 한 테이블에 거는 AI 필터가 모두 같은 문서 열을 읽어야 한다는 제약도 적는다.

원문이 밝힌 한계와 향후 과제

원문 3.2절은 서두에서 설계를 높은 수준에서만 설명하며 전체 기술 세부는 향후 보고서로 내겠다고 밝힌다. 현재 구현의 한계로 본문에 직접 적힌 것은 다음과 같다.

  • 행 간 접두 재사용이 없다. AGENT-1과 AGENT-2에서 stock vLLM에 진 이유다.
  • 재사용할 KV는 GPU HBM에 두거나 다시 계산한다. 호스트 메모리나 로컬 SSD로 내렸다가 되올리는 계층 구조는 아직 없다.
  • 주요 GPU 커널은 DeepGEMM과 FlashAttention에 의존하고 커널 자체는 최적화하지 않았다. MFU에 대한 본격적인 평가도 미뤄져 있다.
  • 조인에서 앵커의 KV는 한 번의 조인 루프 안에서 재사용하지만 파트너는 새 앵커마다 다시 계산한다. 같은 문서가 쌍마다 한 번씩 인코딩된다.
  • 29개 쿼리 합계에서 Quail은 SoL 추정치의 3.35배다.
  • 다중 GPU는 무작위 균등 분할 수준이다.

향후 과제로 원문은 더 많은 AI-SQL 연산자·모델·하드웨어 지원을 들고, 특히 MacBook에서 돌릴 수 있도록 작은 하이브리드 모델을 지원하고 싶다고 적는다. 연구 아이디어로는 KV에 전체 메모리 계층을 쓰는 것(행 간 자동 접두 캐싱과, 어쩌면 KV 압축 포함), Modal·Doubleword와 함께 하는 커널 최적화, 실행과 계획을 위한 작은 모델의 학습(필터를 싸게 평가하고 계획기를 위해 선택도를 예측하는 모델), AI 조인을 해시 조인처럼 만들 수 있는지를 든다. 마지막 항목은 모든 문서를 한 번만 인코딩해 그 KV를 위치와 무관한 색인 항목처럼 쓰자는 물음인데, 원문은 RoPE가 KV에 더하는 위치 정보를 없애거나 분리해야 할 수 있다고 덧붙인다.

개발 방식에 대한 언급도 있다. 원문은 현재 버전의 Quail을 만드는 데 AI 코딩 에이전트를 많이 썼다고 밝히고, 에이전트가 쓴 변경마다 답이 올바르게 유지되고 실행 시간이 SoL에 가깝게 유지되는지 확인할 더 나은 방법을 과제로 든다. 비용 모델에 대해서는 10월 1일에 후속 글 「How to Cost Your AI-Powered Filters」가 올라왔다. 필터만 있는 쿼리의 SoL 추정을 유도하는 글로, IMDB 리뷰 5,000건에 필터 셋을 거는 예제의 SoL 추정치가 약 6.86초이며 실제 실행 시간은 훨씬 길 수 있다고 적는다. 필터 순서를 견줄 때 각 필터의 선택도가 앞선 필터와 무관하게 같다고 가정하며, 필터 결과가 서로 상관되면 그 추정이 부정확해질 수 있다는 단서도 붙어 있다.

도입을 검토할 때 가를 질문

원문의 수치와 제약을 워크로드 판단으로 옮기면 다음 질문이 된다. 원문의 문장을 옮긴 것이 아니라 위 사실에서 끌어낸 정리다.

  • 호출이 한 토큰짜리 판정인가. Quail은 긴 생성이 아니라 빠르고 범위가 정해진 판정을 대상으로 한다. 원문은 애플리케이션 백엔드에서 이 패턴의 수요를 보여 준 예로 Jev를 들고, Quail은 한 쿼리가 수천에서 수백만 건의 관련 판정을 만드는 배치·OLAP 쪽을 겨냥한다고 적는다. 원문이 든 용도는 LLM 판정자 워크플로, 기록 압축, 라벨링 같은 대규모 데이터 변환이다.
  • 재사용이 어떤 모양인가. 같은 긴 문서가 여러 필터와 여러 조인 쌍에서 다시 나오면 BIO-4 쪽이다. 서로 다른 행이 긴 접두를 공유하면 AGENT-1 쪽이고, 원문 시점에는 접두 캐싱이 있는 vLLM이 빨랐다.
  • 지금 쓰는 실행 방식이 어느 기준선에 가까운가. 원문의 기준선은 연산자 순서, 요청 정렬, 토크나이저까지 맞춘 vLLM이다. 요청을 정렬 없이 보내는 구성과 견준 수치는 원문에 없으므로, 자신의 현재 구성이 이 기준선보다 나은지 못한지부터 가려야 배수를 대입할 수 있다.
  • 데이터 규모가 어느 스케일에 가까운가. BIO-4의 14.04배는 스케일 팩터 1.0, 29개 쿼리의 1.84배는 0.1에서 나왔다.
  • 하드웨어와 모델이 맞는가. 측정은 전부 H100 1장과 Qwen3 4B FP8이다. 지원 모델은 블로그 글과 README 기준 세 가지이고(SQL 문서는 Qwen3 reranker와 Decision 2.0 Kai도 든다) README는 모델별 대상 장치를 따로 적는다.
  • 필요한 SQL이 미지원 목록에 걸리는가. OR 조건, 외부 조인, 집합 연산, AI 연산자가 없는 쿼리는 컴파일 오류가 난다.
  • 판정 품질을 무엇으로 검증할 것인가. 원문의 평가는 속도와 비용이다. 작은 오픈 웨이트 모델의 판정이 업무에 충분한지는 자체 라벨로 따로 재야 하고, 문서를 앞에 두는 프롬프트 배치가 답에 주는 영향도 원문은 열린 질문으로 남겼다.

확인하지 못한 것

  • 기법별 기여도. 원문의 성능 수치는 시스템 전체 단위이고 KV 되감기, 조인 어텐션, 연산 융합, 출력 헤드 축소가 각각 얼마를 줄였는지 나눈 수치는 원문에 없다.
  • 정답 대비 정확도. 원문에는 모델 간 일치율 한 건만 있고, 기준선과 Quail이 같은 답을 냈는지 쿼리 단위로 대조한 결과도 실려 있지 않다.
  • H100 1장과 Qwen3 4B FP8 밖의 성능. 다중 GPU, Qwen3 32B, 다른 GPU에서의 비교 수치는 원문에 없다. DiffusionGemma는 IMDB-2 한 쿼리의 실행 시간만 있다.
  • 스케일 팩터 0.5의 결과와, BIO-4를 뺀 쿼리의 스케일 팩터 1.0 결과.
  • 조인을 포함한 SoL 추정의 유도 과정. 원문은 계산 코드로 링크를 걸고 설명을 후속 글로 미뤘으며, 10월 1일 자 후속 글은 필터만 있는 쿼리를 다룬다. 코드는 열어 보지 않았다.
  • 표 1의 AGENT 데이터셋 평균(쿼리 2개)과 표 4의 AGENT-1 단일 쿼리에서 초당 토큰과 KV regret이 같은 숫자로 적힌 이유. 원문에 설명이 없다.
  • 블로그 글의 QUAIL-B 쿼리 29개와 README의 50개가 어떤 관계인지, PyPI의 현재 최신 버전, 저자 개인별 소속, 라이브 데모의 동작. PyPI 페이지와 데모는 열지 않았고 소속은 블로그 글에 적혀 있지 않다.
  • Snowflake·BigQuery·Databricks·MotherDuck의 AI 함수나 DocETL·LOTUS 같은 시스템과의 직접 성능 비교. 원문의 비교 대상은 vLLM 기준선 둘과 GPT-5 nano 비용 추정 한 건이다.
