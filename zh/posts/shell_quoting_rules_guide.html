Shell 引号规则 - 哪个引号挡住了什么

用实跑输出把单引号、双引号和 ANSI-C 引用彻底分开

2026-07-29 开发/基础设施

引言：少写两个引号，目录被清空了

新建一个空的临时目录，放进三个文件。两个名字很普通，第三个名字本身就是一个星号。目标是只删掉那个星号文件，于是把名字存进变量交给 rm。结果如下。

$ ls -1
*
keep1.txt
keep2.txt

$ f='*'
$ rm $f
$ ls -1
(空)

本该只删一个文件，整个目录却被清空了。不是打错命令，rm 也没有异常。shell 先把 $f 替换成 *，然后又把这个 * 二次展开成了文件名列表。只要加上两个引号，这一切都不会发生。

出了这种事，最常听到的建议是「给变量加引号」。话没错，但它不是规则。它没有说该用哪种引号，也没有说那种引号挡住什么、放过什么。于是同一个人下一次把 awk 程序包进双引号，眼看着美元符号被吃掉。方向相反，根因一样：不知道每种引号是关掉哪个开关的。

本文不罗列定义。单引号、双引号、反斜杠和 ANSI-C 引用各自挡住什么，全部实跑并用输出呈现。语法依据取自 GNU Bash Reference Manual 和 POSIX 规范，行为则在临时目录里逐条跑出来。文中每一段输出都是真正出现在屏幕上的内容。最后给出一张场景 → 该用的引号 → 理由的判断表。

先划清边界。用 find 和 xargs 处理带空格文件名的实战组合，另见find 与 xargs 的空格换行陷阱。本文关心的是引号语法本身。同一个脚本能否跑第二次，在跑两次也安全的脚本；能否在执行前知道结果，在如何做出真正的 --dry-run。

2. shell 读一行的顺序 - 引号关掉的是哪一步

引号之所以让人困惑，是因为大家以为「引号造出一个字符串」。在 shell 里引号不造字符串，它是把本来就要发生的若干处理步骤关掉的开关。只要知道哪个开关关掉哪一步，一切都可预测。

bash 执行一行命令之前经过的顺序大致如下。

一行输入
  1. 花括号展开            a{1,2}   ->  a1 a2
  2. 波浪号展开            ~        ->  家目录
  3. 参数展开 / 命令替换 / 算术展开
                           $var  $(cmd)  `cmd`  $((1+1))
  4. 单词拆分              按 IFS 切成字段            <- 空格事故在这里
  5. 路径名展开(通配符)     *  ?  [...]  ->  文件名     <- 星号事故在这里
  6. 引号移除              去掉残留的引号字符
  -> 执行

关键在于第 4 步和第 5 步排在第 3 步之后。也就是说变量展开的结果还会再被拆开、再膨胀。引言里的事故正是如此：$f 在第 3 步变成 *，这个 * 在第 5 步变成了文件列表。

引号关掉的就是这个顺序中的某些环节。哪种引号关哪一段，就是本文的全部内容。

形式$ 展开反引号反斜杠! 历史展开单词拆分通配符展开
不加引号放过放过放过放过会发生会发生
单引号 '...'挡住挡住挡住挡住挡住挡住
双引号 "..."放过放过部分放过仅交互式放过挡住挡住
ANSI-C $'...'挡住挡住会解释挡住挡住挡住
反斜杠 \x挡住挡住挡住挡住挡住挡住

表里最该盯住的是最右两列。不管单引号还是双引号，对单词拆分和通配符展开的阻挡是一样的。生产事故九成出在这两列。所以当你开始纠结「这里该用哪种引号」时，一半的问题已经解决了；真正的隐患是压根没加引号的地方。

3. 单引号 - 没有例外的字面量

单引号只有一条规则：里面的每个字符都是字面量。没有例外。Bash Reference Manual 是这样写的。

Enclosing characters in single quotes preserves the literal value of each character within the quotes. A single quote may not occur between single quotes, even when preceded by a backslash.

跑一遍确认。把同样的文字包进单引号交给 printf。

$ printf '%s\n' '$name'
$name
$ printf '%s\n' '`printf ran`'
`printf ran`
$ printf '%s\n' '\n  \t  \\'
\n  \t  \\
$ printf '%s\n' '!!'
!!
$ printf '%s\n' 'a "b" c'
a "b" c
$ printf '%s\n' '${name}  $(printf ran)  $((1+1))'
${name}  $(printf ran)  $((1+1))

一次展开都没有发生。连反斜杠都不特殊这一点很重要：\\ 原样输出成 \\。在双引号里它会缩成一个 \（见第 4 节）。

因此单引号用于把别的程序的语法从 shell 手里保护下来。awk 程序、sed 表达式、正则、find 的模式、要交给另一个 shell 的命令串，全都属于这一类。

代价也很实在：单引号里放不进单引号。用反斜杠转义为什么行不通，跑一遍就清楚了。

$ printf '%s\n' 'it\'"'"'s'
it\'s

$ bash -c "printf '%s\n' 'it\'s'"
bash: -c: line 1: unexpected EOF while looking for matching `''

第一行看着怪，其实很简单：'it\' 的字符串在反斜杠后面那个引号处就结束了，反斜杠作为普通字符留了下来。第二个例子里后面的引号配不上对，解析直接失败。这正是规范所写：反斜杠在单引号里不是转义字符。

所以想在单引号文本里放进一个单引号，只能先闭合、用别的方式补一个字符、再重新打开。共有四种写法，结果完全相同。

$ printf '%s\n' 'it'"'"'s'      # 闭合，用双引号补一个字符，再打开
it's
$ printf '%s\n' 'it'\''s'       # 闭合，用反斜杠补一个字符，再打开
it's
$ printf '%s\n' "it's"          # 干脆整体用双引号
it's
$ printf '%s\n' $'it\'s'        # ANSI-C 引用（第 8 节）
it's

$ printf '%s' 'it'\''s' | od -c
0000000   i   t   '   s
0000004

最后的 od -c 就是证据：shell 实际交出去的字节是 it's 四个字符。常被称作「引号转义惯用法」的 '\'' 不是魔法，只是闭合、一个字符、打开三段拼在一起。

4. 双引号放过的四样东西

双引号在单引号的基础上恰好开了四个口子。Bash Reference Manual 的表述是这样的。

Enclosing characters in double quotes preserves the literal value of all characters within the quotes, with the exception of $, `, \, and, when history expansion is enabled, !.

把第 3 节完全相同的文字换成双引号再跑一遍。

$ name=world
$ printf '%s\n' "$name"
world
$ printf '%s\n' "`printf ran`"
ran
$ printf '%s\n' "\n  \t  \\"
\n  \t  \
$ printf '%s\n' "!!"
!!
$ printf '%s\n' "a "b" c"
a b c
$ printf '%s\n' "${name}  $(printf ran)  $((1+1))"
world  ran  2

逐行来看。

  • $name 变成了 world — 参数展开被放过
  • 反引号里的命令执行后得到 ran — 命令替换被放过
  • \\ 缩成了一个 \ — 反斜杠部分放过
  • \n 和 \t 保持原样 — 反斜杠并不是在任意字符前都特殊
  • "a "b" c" 变成了 a b c — 双引号在中间闭合又重新打开了

第三条和第四条最容易绊倒人。在双引号里，反斜杠只在固定的五个字符前才作为转义符。手册明确列出了这个清单。

The backslash retains its special meaning only when followed by one of the following characters: $, `, ", \, or newline. Within double quotes, backslashes that are followed by one of these characters are removed. Backslashes preceding characters without a special meaning are left unmodified.

所以 "\n" 不是换行，而是反斜杠和 n 两个字符。想放真正的换行，要么交给 printf 的格式串，要么用第 8 节的 ANSI-C 引用。

第四项感叹号是有条件的。历史展开默认只在交互式 shell 里开启，脚本中是关的所以无碍，但直接敲在终端里的命令至今仍会中招。把两行喂给交互式 bash 验证如下。

$ echo hello there
hello there
$ echo "wow!!"
wowecho hello there          <- 双引号里的 !! 被替换成了上一条命令
$ echo 'wow!!'
wow!!                        <- 单引号挡住了

把同样两行喂给 POSIX 模式的交互式 shell，结果就不同了。这正是手册写明的例外。

$ bash --norc -i
$ echo "wow!!"
wowecho hello there

$ bash --norc --posix -i
$ echo "wow!!"
wow!!

归纳起来，双引号是为「值要进来，但不许被拆开」准备的工具。需要在里面放变量或命令替换时用它，其余场合单引号更安全。

5. 不加引号的展开 - 大多数事故就出在这里

这里是本文的核心。前两节谈的是「什么会进来」，这一节谈的是「会分成几份」。生产事故几乎全在这一边。

验证方法很简单：写一个打印参数个数和内容的函数，同一个变量加引号跑一次、不加再跑一次。

count() {
  printf 'argc=%d\n' "$#"
  local i=1
  for a in "$@"; do printf '  [%d] <%s>\n' "$i" "$a"; i=$((i+1)); done
}

目录里有三个文件：my report.txt、notes.txt、keep.txt。

$ f='my report.txt'

$ count $f
argc=2
  [1] <my>
  [2] <report.txt>

$ count "$f"
argc=1
  [1] <my report.txt>

$ wc -c $f
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
exit=1

$ wc -c "$f"
0 my report.txt
exit=0

一个值裂成了两个参数，于是 wc 去找两个不存在的文件，退出码也是 1。这还算好的情况，因为错误看得见。真正危险的是悄无声息地成功。

$ pat='*.txt'

$ count $pat
argc=3
  [1] <keep.txt>
  [2] <my report.txt>
  [3] <notes.txt>

$ count "$pat"
argc=1
  [1] <*.txt>

$ empty=''
$ count $empty
argc=0
$ count "$empty"
argc=1
  [1] <>

三件事同时暴露出来。

  • 没加引号的 $pat 膨胀成了三个文件，而值明明只有一个
  • 有意思的是 my report.txt 没有被拆开，仍是一个字段。单词拆分发生在通配符展开之前，所以通配结果不会被再次拆分
  • 没加引号的空值会从参数列表里消失；加了引号则保留为一个空字符串参数

最后一条在条件判断里怎么炸，是个著名陷阱。

$ empty=''
$ if [ -n $empty ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
NON-EMPTY          <- 错的

$ if [ -n "$empty" ]; then echo 'NON-EMPTY'; else echo 'empty'; fi
empty              <- 对的

$ two='a b'
$ [ -n $two ]
bash: [: a: binary operator expected
exit=2
$ [ -n "$two" ]
exit=0

第一个变成了 [ -n ]。只有一个参数的 test，只要该参数不是空串就为真，于是 -n 这个字符串本身被判成了真。第二个变成 [ -n a b ]，语法错误。同一段代码会随着值的内容在假阳性、语法错误、正常之间来回跳。

然后是引言里的事故。不加引号的展开一旦走到通配符展开，结果就无法挽回。

### 目录状态（星号就是文件名本身）
*
keep1.txt
keep2.txt

### A) rm $f    (f='*')
$ rm $f
$ ls -1
    (空)

### B) rm -- "$f"    值相同，只差引号
$ rm -- "$f"
$ ls -1
    keep1.txt
    keep2.txt

A 和 B 的差别只有两个引号和一个 --，结果却是全部删除与删掉一个。顺带一提，-- 是与引号无关的另一套机制，表示「从这里开始是操作数而不是选项」，用来保护以短横线开头的文件名。

循环变量遵守同样的规则。把列表塞进一个字符串，从一开始就输了。

$ list='keep1.txt keep2.txt'
$ for f in $list; do printf ' <%s>' "$f"; done
 <keep1.txt> <keep2.txt>

$ arr=('quarterly report.txt' 'keep1.txt')
$ for f in "${arr[@]}"; do printf ' <%s>' "$f"; done
 <quarterly report.txt> <keep1.txt>

字符串列表根本无法表达带空格的名字。需要列表就用数组（第 7 节）。另外，文件名里带换行时，按行计数这套方式会整体崩塌。这超出本文范围，交给find 与 xargs 的空格换行陷阱。不过 shell 看到的个数与 ls 打印的行数不一致，这一点先确认下来。

$ ls -1 | cat -A
    *$
    keep1.txt$
    keep2.txt$
    two$
    lines.txt$

$ n=0; for f in *; do n=$((n+1)); done; echo "count=$n"
    count=4

五行，四个文件。Bash 手册的 Word Splitting 一节这样限定拆分对象。

The shell scans the results of parameter expansion, command substitution, and arithmetic expansion that did not occur within double quotes for word splitting. Words that were not expanded are not split.

「没有发生在双引号里的」就是全部条件。一对双引号就能整个跳过第 4 步。

6. 位置参数的四种写法 - 把参数数一遍

把脚本收到的参数原样转给别的命令，是每天都在做的事。但写法有四种，结果各不相同。给一个用 $# 计数的函数传四个参数：'a b'、'c'、''（空串）、'd*e'。

$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a> <b> <c> <d*e>
quoted *:  argc=1 | <a b c  d*e>
bare *:    argc=4 | <a> <b> <c> <d*e>

只有加引号的 "$@" 把原来的四个原样交了出去。不加引号的 $@ 个数也是 4，但内容对不上：a b 裂成两个、空参数消失，个数只是碰巧一致。这种巧合会把 bug 藏很久。

把 IFS 改成逗号再做一次同样的实验。

$ IFS=,
$ pass 'a b' 'c' '' 'd*e'

quoted @:  argc=4 | <a b> <c> <> <d*e>
bare @:    argc=4 | <a b> <c> <> <d*e>
quoted *:  argc=1 | <a b,c,,d*e>
bare *:    argc=4 | <a b> <c> <> <d*e>

### 一个参数都没有时
quoted @:  argc=0 |
bare @:    argc=0 |
quoted *:  argc=1 | <>
bare *:    argc=0 |

浮现出两件事。第一，"$*" 用来连接的字符变成了IFS 的第一个字符。第二，没有参数时 "$@" 是零个参数，而 "$*" 是一个空串参数。这个差别会在 set -u 和参数个数检查里悄悄造成不同结果。

放到真实命令上就是这样。

$ set -- 'my report.txt' 'notes.txt'

$ wc -c "$@"
0 my report.txt
0 notes.txt
0 total

$ wc -c $@
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

$ wc -c "$*"
wc: 'my report.txt notes.txt': No such file or directory
写法产生的字段数空参数带空格的参数使用场合
"$@"与参数个数完全一致保留保留转发参数的默认写法
$@拆分与通配之后的个数丢失被拆开几乎用不上
"$*"永远是 1保留为空位保留拼成一行日志时
$*拆分与通配之后的个数丢失被拆开几乎用不上

规则很短：转发参数用 "$@"，拼给人看的一行用 "$*"。两种不加引号的写法在实战中几乎没有正当用途。

7. 数组与引号 - 只有一种能保住原样

数组的结构完全一样：四种展开方式，只有一种保住原样。用一个四元素的数组验证。

$ arr=('my report.txt' 'notes.txt' '' 'a*b')

"${arr[@]}"      argc=4 | <my report.txt> <notes.txt> <> <a*b>
${arr[@]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>
"${arr[*]}"      argc=1 | <my report.txt notes.txt  a*b>
${arr[*]}        argc=4 | <my> <report.txt> <notes.txt> <a*b>

$ echo "${#arr[@]}"     # 元素个数
4
$ echo "${#arr[0]}"     # 第 0 个元素的字符数
13

顺带看一下 ${#arr[@]} 和 ${#arr[0]} 返回的是完全不同的东西：前者是个数，后者是长度。

拼装命令行时为什么需要数组，下面这组对比说得很清楚。

$ opts=(-c)
$ files=('my report.txt' 'notes.txt')

$ wc "${opts[@]}" "${files[@]}"
0 my report.txt
0 notes.txt
0 total

$ wc ${opts[*]} ${files[*]}
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 notes.txt
0 total

还有一种常见的反模式：不用数组，而把整条命令行塞进字符串变量。它为什么行不通，最能说明引号的本质。

$ cmdline='wc -c "my report.txt"'
$ $cmdline
wc: '"my': No such file or directory
wc: 'report.txt"': No such file or directory
exit=1

引号明明写了，为什么不管用？因为引号不在变量值内部起作用。shell 是在读源码时处理引号的，那一步早就结束了。留在变量里的引号只是普通字符。所以 wc 收到的参数上还挂着引号字符。

要记住的一句话
引号加在代码上，不加在值上。变量值里的引号字符对 shell 毫无意义。必须动态拼装命令行时，用数组而不是字符串；实在不行就用 printf %q（第 12 节）让 shell 自己加引号。

另外，bash 4.4 之前在 set -u 下用 "${arr[@]}" 展开空数组会报错。在本文环境（5.2.37）下则正常。

$ empty=()
$ set -u
$ show "${empty[@]}"
argc=0 |
survived: exit=0

8. ANSI-C 引用 - 单引号上唯一的口子

前面说单引号挡住一切。有一种形式跳出了这条规则：前面加一个美元符号的 $'...'。手册称它为「一种特殊的单引号」，变量依然不展开，但反斜杠转义序列会被解码。

$ printf '%s' 'A\tB\nC' | od -c
0000000   A   \   t   B   \   n   C
0000007

$ printf '%s' $'A\tB\nC' | od -c
0000000   A  \t   B  \n   C
0000005

同一段文字，一个 7 字节一个 5 字节。$'...' 那边变成了真正的制表符和真正的换行。手册列明了支持的写法：八进制 \nnn、十六进制 \xHH、Unicode 的 \uHHHH 与 \UHHHHHHHH，以及 \a \b \e \f \n \r \t \v \\ \' \" \?。实际跑过验证如下。

$ printf '%s' $'\x41\x42' | od -c
0000000   A   B
$ printf '%s' $'\101\102' | od -c
0000000   A   B
$ printf '%s' $'é' | od -c
0000000 303 251
$ printf '%s' $'\e[0m' | od -c
0000000 033   [   0   m
$ printf '%s' $'\cG' | od -c
0000000  \a

变量依然不展开这一点必须牢记。

$ name=world
$ printf '%s\n' $'hello $name'
hello $name

用途很明确：需要把制表符或换行当作分隔符的时候。设置 IFS，以及 sort -t、cut -d、join -t 这些地方。不过 $'...' 不在 POSIX 规范里。在 dash 上跑，展开根本不会发生。

$ dash -c "printf '%s' \$'A\tB' | od -c"
0000000   $   A   \   t   B
0000005

美元符号作为字符留下，\t 也还是两个字符。需要可移植时，改用 printf 生成再存进变量。结果一致，用字节验证过。

$ TAB=$(printf '\t')
$ NL=$(printf '\nx'); NL=${NL%x}
$ printf '%s' "A${TAB}B${NL}C" | od -c
0000000   A  \t   B  \n   C
0000005

造 NL 时先加 x 再去掉，是因为命令替换会把结尾的换行全部删掉（第 9 节）。少了这两步，NL 就是空字符串。

9. 命令替换与反引号 - 里面的引号与外面无关

$(...) 内部的引号与外部的引号完全无关。即使身处双引号之中，里面也是一个全新的上下文。

$ printf '%s\n' "outer $(printf '%s' 'inner literal $HOME') outer"
outer inner literal $HOME outer

$ printf '%s\n' "$(printf '[%s]' "$(printf '%s' 'deep')")"
[deep]

外层是双引号，里层的单引号照常生效，$HOME 活了下来；三层嵌套的双引号也原样通过。嵌套时不用数引号，正是 $(...) 的实用优势。

反引号则不然。同样的嵌套用反引号写，解析会失败。

$ bash -c 'printf "%s\n" "`printf "[%s]" "`printf "%s" deep`"`"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
bash: command substitution: line 1: unexpected EOF while looking for matching `"'
printf %s deep

反引号的开始符和结束符是同一个字符，嵌套边界无从判断。而且反引号内部反斜杠还会再被剥掉一层。这个差异会实实在在改变值。

$ printf '%s\n' "$(printf '%s' 'a\tb')"
a\tb
$ printf '%s\n' "`printf '%s' 'a\tb'`"
a\tb

$ printf '%s\n' "$(printf 'a\\b')"
a\b
$ printf '%s\n' "`printf 'a\\b'`"
a

最后两行分了岔：$(...) 得到 a\b，反引号得到 a。反引号先吃掉一个反斜杠，变成了 printf 'a\b'，printf 又把它解释成退格。归纳起来，避开反引号的理由有三条。

  • 无法嵌套 — 开始符和结束符是同一个字符，边界不可判定，如上所示解析会失败
  • 会多吃一层反斜杠 — 传的是同样的参数，得到的字符串却不一样
  • 难以阅读 — 在很多字体下反引号和单引号几乎分辨不出

POSIX 规范两种形式都有规定，$(...) 在 dash 上也跑得好好的。新代码没有任何理由再用反引号。

命令替换的结果同样不加引号就会被拆开、被膨胀，规则和变量一模一样。

$ show $(printf '%s\n' 'my report.txt')
argc=2 | <my> <report.txt>
$ show "$(printf '%s\n' 'my report.txt')"
argc=1 | <my report.txt>

$ show $(printf '%s\n' '*.txt')
argc=1 | <my report.txt>
$ show "$(printf '%s\n' '*.txt')"
argc=1 | <*.txt>

### 结尾的换行无论是否加引号都会被全部截掉
$ printf '%s' "$(printf 'x\n\n\n')" | od -c
0000000   x
0000001

第三个例子尤其危险。命令输出的是 *.txt 这个字面文本，去掉引号之后它变成了目录里恰好存在的文件名。原始字符串在屏幕上无处可寻。

10. IFS - 决定什么算边界的变量

单词拆分的依据是 IFS，默认值是空格、制表符、换行，改掉它拆分结果就整个变了。但用双引号包住的值，无论 IFS 怎么改都不受影响，因为拆分压根不会发生。

$ line='root:x:0:0::/root:/bin/bash'

### 默认 IFS
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>

### IFS=:
$ IFS=:
$ show $line
argc=7 | <root> <x> <0> <0> <> </root> </bin/bash>
$ show "$line"
argc=1 | <root:x:0:0::/root:/bin/bash>

加了引号那一侧不管 IFS 是什么永远是 1 个。这就是「拿不准就用双引号」成立的理由：无论周围代码把 IFS 改成什么样，加了引号的展开都不会晃动。

空白类 IFS 与非空白 IFS 的行为不同，也值得了解。

$ gaps='a   b'
$ show $gaps
argc=2 | <a> <b>                     <- 连续空白会合并成一个

$ path='/usr/bin:/bin::/usr/local/bin'
$ IFS=:
$ show $path
argc=4 | </usr/bin> </bin> <> </usr/local/bin>   <- 空字段被保留

$ IFS=
$ show $line
argc=1 | <root:x:0:0::/root:/bin/bash>             <- IFS 为空则不拆分

与手册的说明完全一致。IFS 只由空白类字符构成时，一串连续空白就是一个边界，空字段只能由引号产生。IFS 中含有非空白字符时，每一个这样的字符都是边界，连着出现就会产生空字段。

IFS 还决定 "$*" 用来连接的字符。

$ set -- one two three
$ IFS=:
$ printf '%s\n' "$*"
one:two:three
$ for a in "$@"; do printf ' <%s>' "$a"; done
 <one> <two> <three>

实战中使用 IFS 的正确方式是只加在一条命令上。改成全局之后，后面所有不加引号的展开都会受影响。

$ printf '%s\n' "$line" | { IFS=: read -r user pw uid gid gecos home shell
    printf 'user=<%s> uid=<%s> home=<%s> shell=<%s>\n' "$user" "$uid" "$home" "$shell"; }
user=<root> uid=<0> home=</root> shell=</bin/bash>

### 改成全局之后忘了改回来
$ IFS=,
$ files='a,b'
$ show $files
argc=2 | <a> <b>         <- 可能并不是你想要的地方
$ show "$files"
argc=1 | <a,b>

像 IFS=: read -r ... 这样写在命令前面的赋值只对该命令生效。给 read 加 -r 也是和引号同一性质的防守：没有 -r，输入里的反斜杠会被当作转义符而消失。

11. 不需要引号的地方，和反而要去掉的地方

「全都加引号」同样不是规则。有些地方加引号毫无意义，有些地方加引号会改变语义。跑一遍把它们分开。

$ v='my report.txt'
$ star='*.txt'

### A) 赋值右侧：既不拆分也不通配
$ a=$v
$ b=$star
$ printf 'a=<%s>\n' "$a"
a=<my report.txt>
$ printf 'b=<%s>\n' "$b"
b=<*.txt>

赋值右侧不加引号也安全。仍然有不少人主张习惯性加上，理由不是安全而是一致性：一旦造出一个例外，下一个人就得重新判断这个例外的边界在哪里。

反过来，case 和 [[ ]] 的模式位置，加不加引号会改变含义。

$ v='my report.txt'
$ p='my*'

$ case "$v" in
    $p)  echo '模式不加引号 -> 当作通配符，匹配成功' ;;
    *)   echo '不匹配' ;;
  esac
模式不加引号 -> 当作通配符，匹配成功

$ case "$v" in
    "$p") echo '模式加引号 -> 当作字面文本，匹配成功' ;;
    *)    echo '不匹配（字面的 my* 不是这个名字）' ;;
  esac
不匹配（字面的 my* 不是这个名字）

[[ ]] 也一样。左边不会被拆分所以不必加引号，右边是模式，加了引号就变成字面量。

$ [[ $v == 'my report.txt' ]]  && echo '左边不加引号：没问题'
左边不加引号：没问题
$ [[ $v == $p ]]   && echo '右边不加引号：通配匹配'
右边不加引号：通配匹配
$ [[ $v == "$p" ]] || echo '右边加引号：不匹配（符合预期）'
右边加引号：不匹配（符合预期）

### 同样的比较换成单方括号
$ [ $v == 'my report.txt' ]
bash: [: too many arguments

[[ ]] 是 shell 语法，内部不做单词拆分；[ ] 是一条命令，要接收参数。所以同一段代码一边通过，一边报参数个数错误。

通配结果不会被再次拆分这一点也在这里一并确认。

$ show *.txt
argc=2 | <my report.txt> <notes.txt>
$ show "$star"
argc=1 | <*.txt>
$ show $star
argc=2 | <my report.txt> <notes.txt>

直接写在代码里的 *.txt 本就不该加引号，加了它就从通配符变成字面字符串。因此「去掉引号」的正当理由只有两个：有意的单词拆分和有意的通配符展开。其余一律加上。

  • 通配模式直接写在代码里时：for f in *.log — 不加引号
  • 通配模式存在变量里并且想当通配符用时：case 与 [[ ]] 的右侧
  • 想把选项字符串拆成多个参数时 — 不过数组更安全
  • 其余全部：加双引号
去掉了就留一行
故意不加引号的地方，最好写上 # 有意拆分 之类的注释。否则下一个人要么当成漏写而补上引号、改变行为，要么把真正的疏漏当成「本来就该这样」而放过去。

12. eval 与双层 shell - 引号被再剥一层的时候

到这里为止都假定 shell 只把文本读一次。在 eval、远端 shell、容器执行这类同一个字符串被读两次的场景里，引号会被再剥掉一层。

$ greeting=hello
$ v='$greeting'

$ printf 'plain : %s\n' "$v"
plain : $greeting

$ eval "printf 'eval  : %s\n' \"$v\""
eval  : hello

同一个变量，经过 eval 之后值又被解释了一次。如果值里含有命令分隔符，接下来的事就可以预料了。

$ name='keep.txt; echo INJECTED'

$ printf '%s\n' "$name"
keep.txt; echo INJECTED

$ eval "printf '%s\n' $name"
keep.txt
INJECTED

加引号输出时是一个值，放上 eval 之后分号后面的部分作为独立命令执行了。这就是 eval 名声不好的原因。安全条件只有一条：交给 eval 的字符串全部由自己生成时才用。

把命令交给第二个 shell 时也是同一回事。下面用 bash -c 复现，但远程执行和容器执行原理相同：字符串会在对端被重新解析。

$ target='my report.txt'

$ bash -c "wc -c $target"
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total

$ bash -c "wc -c \"$target\""
0 my report.txt

$ bash -c "wc -c $(printf '%q' "$target")"
0 my report.txt

究竟哪一层吃掉了美元符号，也跑一遍就不会再糊涂。

$ name=outer

$ bash -c "printf 'A: %s\n' $name"
A: outer          <- 外层 shell 展开后把值嵌进字符串交了过去

$ bash -c 'printf "B: %s\n" $name'
B:                <- 内层 shell 去展开，而那边没有 name

$ bash -c 'printf "C: %s\n" "$0"' "$name"
C: outer          <- 把值当参数传，根本没有拼装字符串

C 才是正确形态。不把值嵌进字符串而是当参数传，引号问题压根不会出现。

如果非嵌不可，不要用手叠引号，交给 shell 去做。printf %q 和 bash 4.4 以上的 ${var@Q} 就是这两件工具。

$ bad='my report.txt'
$ weird=$(printf 'a b\tc*d')

$ printf 'raw : %s\n' "$bad"
raw : my report.txt
$ printf 'q   : %q\n' "$bad"
q   : my\ report.txt
$ printf 'q   : %q\n' "$weird"
q   : $'a b\tc*d'

$ printf 'atQ : %s\n' "${bad@Q}"
atQ : 'my report.txt'
$ printf 'atQ : %s\n' "${weird@Q}"
atQ : $'a b\tc*d'

### 往返：加上引号，再解析回来
$ q=$(printf '%q' "$bad")
$ eval "wc -c $q"
0 my report.txt

值得注意的是，对含制表符的值shell 自己选择了 ANSI-C 引用，比人来挑引号形式更准确。不过 %q 和 ${var@Q} 都是bash 扩展，POSIX sh 里没有（第 13 节）。

最后，想亲眼看到展开结果，set -x 最快。它会把 shell 实际传出去的参数连同引号一起显示。

$ set -x
$ wc -c $bad
+ wc -c my report.txt
wc: my: No such file or directory
wc: report.txt: No such file or directory
0 total
$ wc -c "$bad"
+ wc -c 'my report.txt'
0 my report.txt

在跟踪行里，bash 给 'my report.txt' 加上引号显示，说明它是一个参数；若显示成裸的 my report.txt，说明它已经裂成两个。只要知道这一点，调试时间就能大幅缩短。

13. POSIX sh 与 bash 分道的地方

如果脚本以 #!/bin/sh 开头，就不能用 bash 扩展。把同样的东西在 dash 上并排跑一遍，就能看出共同地带到哪里为止。

### ANSI-C 引用
bash : A	B
sh   : $A\tB

### [[ ]]
bash : ok
sh   : dash: 1: [[: not found

### 数组
bash : x|y z|
sh   : dash: 1: Syntax error: "(" unexpected

### printf %q
bash : a\ b
sh   : dash: 1: printf: %q: invalid directive

反过来也有bash 更严格的地方：重定向目标裂成两个词的时候。

$ v="r 1.txt"; echo hi > $v          # 普通 bash
bash: $v: ambiguous redirect
exit=1

$ v="r 2.txt"; echo hi > $v          # bash --posix
exit=0

$ v="r 3.txt"; echo hi > $v          # dash
exit=0

### 实际生成的文件
$ ls
r 2.txt
r 3.txt

普通 bash 拒绝了，POSIX 模式的 bash 和 dash 接受并创建了文件。POSIX 规范对这个位置是这样写的。

Pathname expansion shall not be performed on the word by a non-interactive shell; an interactive shell may perform it, but if the expansion would result in more than one word it is unspecified whether the redirection proceeds without pathname expansion being performed or the redirection fails.

也就是说这一段允许各实现表现不同。那么结论只有一个：重定向目标也要加引号。这样在哪个 shell 上跑都一致。

好在引号的核心规则在哪里都一样。把同一段代码在两个 shell 上跑过确认。

$ v="a b"; set -- $v;   printf 'unquoted=%d ' "$#"
$ set -- "$v"; printf 'quoted=%d\n' "$#"

bash  : unquoted=2 quoted=1
dash  : unquoted=2 quoted=1
特性POSIX shbash可移植替代
单引号与双引号规则相同相同照用
单词拆分、通配、IFS相同相同照用
"$@" / "$*"相同相同照用
ANSI-C 引用 $'...'没有有TAB=$(printf '\t')
数组没有有用 set -- 走位置参数
[[ ]]没有有[ ] 加上严格的引号
printf %q、${var@Q}没有有把值当参数传，避免拼装
两个词的重定向目标允许拒绝一律写成 > "$v"

14. 判断表 - 从场景到引号

把规则压缩成一句：拿不准就用 "$var"。然后把要去掉引号的场合作为例外明确列出。

场景该用的写法理由
把变量作为命令参数传递"$var"同时挡住单词拆分和通配符展开
原样转发脚本自身的参数"$@"个数、空参数、空格全部保留
把参数拼成一行日志"$*"用 IFS 第一个字符连接成的单个字符串
处理列表"${arr[@]}"字符串列表无法表达带空格的元素
重定向目标> "$var"这一段允许各实现表现不同
测试与比较[ -n "$var" ]防止空值从参数列表里消失
传递别的语言的程序'...'把 awk、sed、正则里的美元符号从 shell 手里保护下来
find 的模式-name '*.log'不加引号会被 shell 先吃掉
把制表符或换行放进值里$'\t' 或 $(printf '\t')双引号里的反斜杠不会被解释
直接写在代码里的通配符*.log（不加引号）加引号就从通配符变成字面字符串
case 与双方括号里的模式变量$p（不加引号）加引号就变成字面比较
把命令串交给另一个 shell把值当参数传彻底避开拼装才是最安全的
实在必须拼装时printf %q / ${var@Q}让 shell 而不是人来加引号

用一个脚本收尾，看看差别有多大。下面是把引号全部漏掉的常见写法，没有任何语法错误，所以 bash -n 能通过。

#!/usr/bin/env bash

  cp $f $dst

  echo "copied $f"

结论：引号加在代码上，不加在值上

把引号变成规则，只有三句话。

  • 单引号挡住一切。用于把别的语言的语法从 shell 手里保护下来。里面放不进单引号，绕法是闭合、一个字符、打开
  • 双引号放过四样：美元符号、反引号、特定字符前的反斜杠，以及交互式下的感叹号。作为交换，它对单词拆分和通配符展开的阻挡与单引号完全相同
  • 没加引号的地方才是事故现场。一个值变成好几个，凭空冒出文件名，空值则整个消失

再把实跑验证过的事整理一遍：值里有空格，参数就裂成两个；值里有星号，就膨胀成文件列表，一行 rm 清空了目录；空值从参数列表里消失，让 [ -n ] 判成真；只有 "$@" 把四个参数原样交出，其余三种全都不同；改动 IFS 只让不加引号的展开裂开，加了引号的那侧永远是一个；把命令行塞进字符串后，引号变成了字符并原样传给了 wc。

最后一点正是本文的主旨。引号加在代码上，不加在值上。shell 在读源码时处理引号，此后再也不会去看值里面的引号字符。所以把命令行当字符串拼装这种做法在原理上就补不好，只有用数组或 "$@" 保持结构原样地传递，才是唯一解。

定下一个默认值吧：拿不准就用 "$var"。只在能说清理由时才去掉，并在去掉的地方留一行说明。仅这一条规则，就能让绝大多数 shell 事故消失。

# Shell 引号规则 — 可直接粘贴使用的判断清单

> 出处: braindetox.kr — Shell 引号规则
> 依据: GNU Bash Reference Manual (Single Quotes / Double Quotes / ANSI-C Quoting / Word Splitting)、POSIX Issue 8 (Shell Command Language 2.2.2、2.2.3、2.6.5、2.7)
> 把这份文件原样贴进 AI 工具，写上「按这个标准帮我改脚本」即可使用。

## 0. 一句话默认值

**拿不准就用 `"$var"`。** 去掉引号才是例外，每个例外都要写注释说明理由。

## 1. 每种引号挡住什么

| 形式 | 美元展开 | 反引号 | 反斜杠 | 感叹号(历史展开) | 单词拆分 | 通配符展开 |
|---|---|---|---|---|---|---|
| 不加引号 | 放过 | 放过 | 放过 | 放过 | **会发生** | **会发生** |
| `'...'` | 挡住 | 挡住 | 挡住 | 挡住 | 挡住 | 挡住 |
| `"..."` | **放过** | **放过** | **部分放过** | **仅交互式放过** | 挡住 | 挡住 |
| ANSI-C 引用 | 挡住 | 挡住 | **会解释** | 挡住 | 挡住 | 挡住 |
| `\x` | 挡住 | 挡住 | 挡住 | 挡住 | 挡住 | 挡住 |

- [ ] 我知道单引号和双引号**对单词拆分与通配符展开的阻挡完全相同**
- [ ] 我知道双引号里的反斜杠**只在**美元符号、反引号、双引号、反斜杠和换行**这五个之前**才特殊
- [ ] 我知道 `"\n"` 是两个字符而不是换行

## 2. 场景 → 该用的引号

| 场景 | 该用的写法 | 理由 |
|---|---|---|
| 变量作为命令参数 | `"$var"` | 同时挡住单词拆分和通配符展开 |
| 转发脚本参数 | `"$@"` | 个数、空参数、空格全部保留 |
| 把参数拼成一行日志 | `"$*"` | 用 IFS 第一个字符连接成的单个字符串 |
| 处理列表 | `"${arr[@]}"` | 字符串列表装不下带空格的元素 |
| 重定向目标 | `> "$var"` | 这一段允许各实现表现不同 |
| 测试与比较 | `[ -n "$var" ]` | 防止空值从参数列表里消失 |
| awk / sed / 正则程序 | `'...'` | 把美元符号从 shell 手里保护下来 |
| find 的模式 | `-name '*.log'` | 不加引号会被 shell 先吃掉 |
| 把制表符或换行当值 | `TAB=$(printf '\t')` | 双引号里的反斜杠不会被解释 |
| 直接写在代码里的通配符 | `*.log`（不加引号） | 加引号就变成字面字符串 |
| case 与 `[[ ]]` 的模式变量 | `$p`（不加引号） | 加引号就变成字面比较 |
| 把命令交给另一个 shell | 把值**当参数**传 | 彻底避开字符串拼装 |
| 实在必须拼装 | `printf %q` / `${var@Q}` | 让 shell 而不是人来加引号 |

## 3. 常见翻车写法与修正

```bash
# -- 1) 值里有空格，参数就会裂开
wc -c $f                      # 错  my report.txt -> 2 个参数
wc -c -- "$f"                 # 对  1 个

# -- 2) 值里有通配符字符，就会膨胀成文件名
rm $f                         # 错  f='*' 时整个目录被清空
rm -f -- "$f"                 # 对  只删那一个文件

# -- 3) 空值会从参数列表里消失
[ -n $DEBUG ]                 # 错  变成 [ -n ]，恒为真
[ -n "${DEBUG:-}" ]           # 对

# -- 4) 不要把列表塞进字符串
list='a.txt b.txt'; for f in $list      # 错  无法表达带空格的名字
files=('a b.txt' 'c.txt'); for f in "${files[@]}"   # 对

# -- 5) 不要用 for 套 ls
for f in $(ls "$src")         # 错  拆分和通配都会发生
for f in "$src"/*; do [ -e "$f" ] || continue       # 对

# -- 6) 不要把命令行塞进字符串（引号会变成字符）
cmd='wc -c "a b.txt"'; $cmd   # 错  wc 收到的是带引号字符的参数
cmd=(wc -c 'a b.txt'); "${cmd[@]}"                  # 对

# -- 7) 参数转发永远写成这个形状
run() { real_cmd "$@"; }      # 对  ($@ / "$*" / $* 结果都不同)

# -- 8) 重定向目标也要加引号
echo hi > $out                # 错  bash 报 ambiguous redirect，sh 却通过
echo hi > "$out"              # 对  在任何 shell 上都一致

# -- 9) 交给第二个 shell 时把值当参数传
ssh host "wc -c $file"        # 错  会在对端被重新解析
ssh host 'wc -c "$0"' "$file" # 对  不做拼装
```

## 4. 允许去掉引号的仅有两种情形

- [ ] **有意的单词拆分** — 拆开选项字符串（用数组更安全）
- [ ] **有意的通配符展开** — `case` 与 `[[ ]]` 的模式位置，以及直接写在代码里的通配符
- [ ] 不属于以上两种，就**一律加引号**
- [ ] 去掉引号的地方都写了 `# 有意拆分` 之类的注释

## 5. 检查命令 — 帮你指出该看的行

```bash
F=script.sh

# 命令后面出现的不加引号的展开
grep -nE '(^|[[:space:]|(&;])(cp|mv|rm|wc|cat|cd|mkdir|source)[[:space:]]+[^|;&]*\$[A-Za-z_{]' "$F"

# 方括号测试内部不加引号的展开
grep -nE '\[[^]]*\$[A-Za-z_{][^]"]*\]' "$F"

# 用 for 遍历命令输出或变量
grep -nE 'for[[:space:]]+[A-Za-z_]+[[:space:]]+in[[:space:]]+(\$\(|\$[A-Za-z_{])' "$F"

# 没加引号的重定向目标
grep -nE '(^|[[:space:]])[12]?>>?[[:space:]]*\$[A-Za-z_{]' "$F"

# 亲眼确认真实的展开结果
bash -n "$F"                       # 只查语法（漏加引号查不出来）
bash -x "$F" "一个 参数" out         # 看跟踪行里有没有引号来判断
```

**跟踪行的读法**：bash 显示成 `'my report.txt'`，**带引号说明是一个参数**；
显示成裸的 `my report.txt`，**说明已经裂成两个**。

## 6. 复现用测试数据 — 仅限空的临时目录

```bash
d=$(mktemp -d) && cd "$d" || exit 1
: > 'my report.txt'          # 带空格
: > 'keep.txt'
printf 'junk\n' > '*'        # 名字本身就是通配符字符
touch -- "-dash.txt"         # 以短横线开头
./your_script.sh "$d" out    # 在这里翻车就是引号问题
```

★ 上面的测试**务必只在新建的空临时目录里**运行，不要在家目录或真实服务器路径上执行。

## 7. 迁移到 POSIX sh 时

| 特性 | POSIX sh | bash | 可移植替代 |
|---|---|---|---|
| 单引号与双引号规则 | 相同 | 相同 | 照用 |
| 单词拆分、通配、IFS | 相同 | 相同 | 照用 |
| `"$@"` / `"$*"` | 相同 | 相同 | 照用 |
| ANSI-C 引用 | 没有 | 有 | `TAB=$(printf '\t')` |
| 数组 | 没有 | 有 | 用 `set --` 走位置参数 |
| `[[ ]]` | 没有 | 有 | `[ ]` 加上严格的引号 |
| `printf %q` | 没有 | 有 | 把值当参数传，避免拼装 |
| 两个词的重定向目标 | 允许 | 拒绝 | 一律写成 `> "$v"` |

## 8. 最后一句

**引号加在代码上，不加在值上。** 变量值里的引号字符对 shell 毫无意义。
所以把命令行当字符串拼装这种做法在原理上就补不好，只有用数组或 `"$@"` 保持结构原样地传递，才是唯一解。
