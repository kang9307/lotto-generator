OAuthが誤解される場所 - 認証ではなく委譲された認可である

4つのロール、4つのフロー、そして最新のBCPが一覧から外したもの

2026年8月24日 開発・インフラ

会議で「OAuthでログインを付けました」という言葉が出ると、そのあと30分の話はだいたい決まってくる。誰かはアクセストークンを開いてユーザー識別子を取り出して使っており、誰かはそのトークンをブラウザのストレージに置いており、また誰かはスコープを画面上でだけ隠して権限制御と呼んでいる。三つとも珍しくない。そして三つとも同じ根から出ている。

根は規格の名前にある。OAuth 2.0の正式名称はThe OAuth 2.0 Authorization Frameworkであり、ここにauthenticationという語はない。偶然ではない。この規格が解こうとした問題がそもそも「この人は誰か」ではなく「このアプリケーションはあの資源にどこまで手を伸ばせるか」だったからである。この一行を取り落とすと、その上に積む判断が順番に狂っていく。

以下はそのずれが実際に現れる場所を、規格の順に追ったものである。各節は「何が規範か」と「その規範を破ったとき何が崩れるか」までを扱う。攻撃をどう実行するかは扱わない。

1. 最大の誤解 - OAuthは認証プロトコルではない

RFC 6749は2012年10月に出たProposed Standardである。要旨はこの枠組みの仕事を「サードパーティのアプリケーションがHTTPサービスへ限定的なアクセス権を得る」ことと定義している。リソースオーナーの代理としてであれ、アプリケーション自身のためであれ、成果物はつねにアクセス権である。身元の証明ではない。

そうするとアクセストークンの性格も自然に決まる。アクセストークンはリソースサーバーに提示するために作られたものであって、クライアントが読むために作られたものではない。中に何が入っていようと、それは「この要求にどこまで応じてよいか」についての情報であり、「いま画面の前にいる人が誰か」についての情報ではない。RFC 6749のセキュリティ考慮の節にも、アクセストークンを身元の証明のように使うことへの警告が別に置かれている。

ログインが目的なら層をもう一枚載せることになる。OpenID Connect Core 1.0は自らを「OAuth 2.0プロトコルの上に載せた単純なアイデンティティ層」と定義する。この層が新たに持ち込むのがIDトークンである。IDトークンはエンドユーザーの認証に関するクレームを含むセキュリティトークンであり、JWTの形をとり、次のクレームを必須とする。

  • iss - レスポンスを発行した発行者の識別子
  • sub - サブジェクト識別子。発行者の中で一意であり再割り当てされない
  • aud - このIDトークンが向けられた対象。OAuthクライアント識別子を含む
  • exp - この時刻以降はIDトークンを受け入れてはならない有効期限
  • iat - JWTが発行された時刻

この節の核心は二つのトークンの受け手が違うという点にある。アクセストークンはリソースサーバーが受け取り、IDトークンはクライアントが受け取る。プロフィールが必要ならOpenID ConnectはUserInfoエンドポイントを置くが、これはアクセストークンを提示すると認可されたエンドユーザー情報を返す保護資源である。プロフィールの取得さえ認可の文法で行われる。

判断の基準。自分のサービスが必要としているのが「あちらのサービスの自分のカレンダーに予定を入れる権限」なら、OAuthで話は終わる。「この人が自分のサービスのどのアカウントかを確定すること」ならOpenID Connectが要る。二つの要求が混ざっているなら両方の層を使う。アクセストークン一つで両方をやらせようとする瞬間が事故の出発点である。

2. ロールは4つで、信頼の向きは一方向ではない

RFC 6749は参加者を4つに分ける。ここで用語を正確に押さえておくと、以降の節がずっと楽になる。

  • リソースオーナー - 保護資源へのアクセスを許可できる主体
  • クライアント - リソースオーナーの代理として、その認可を受けて保護資源への要求を行うアプリケーション
  • 認可サーバー - リソースオーナーの認証に成功し認可を得たうえで、クライアントにアクセストークンを発行するサーバー
  • リソースサーバー - 保護資源をホストし、アクセストークンを用いた保護資源への要求を受けて応答するサーバー

ここでよく曖昧になるのが信頼の向きである。リソースオーナーが信頼する相手は認可サーバー一つであり、パスワードや二段階認証の手段を入力する場所はそこだけであるべきだ。クライアントはリソースオーナーを信頼せず、認可サーバーが返したものを信頼する。リソースサーバーもクライアントではなく、認可サーバーが発行したトークンの有効性を信頼する。4者が互いを対称に信頼する構造ではないという点がこの規格の骨格である。

もう一つ分岐する軸がクライアントの種別である。自らのクレデンシャルを秘密に保てる機密クライアントと、それができない公開クライアントがある。サーバー上で動くバックエンドは前者、ブラウザで動くシングルページアプリケーションや利用者の端末に入るネイティブアプリは後者だ。以降の規範の多くがこの軸で分かれる。クライアントクレデンシャルグラントを使えるかどうかも、PKCEが必須か推奨かも、リフレッシュトークンにローテーションが求められるかも、すべてここに掛かっている。

ネイティブアプリには規範がもう一つ付く。RFC 8252は2017年10月に出たBest Current Practiceであり、BCP 212の番号を持つ。ネイティブアプリからの認可要求は埋め込みのユーザーエージェントではなく、外部のユーザーエージェント、主として利用者のブラウザを通じてのみ行われるべきだ、というのが核心である。理由は前の段落の信頼の向きで読み直せば明らかだ。埋め込みのウェブビューはクライアントが所有する画面であり、リソースオーナーが認可サーバーにだけクレデンシャルを渡すという前提がその画面では成り立たない。

3. フローごとに何が違うのか

フローを暗記するよりフローを分ける二つの問いを押さえるほうが速い。第一に、リソースオーナーはいまその場にいるか。第二に、クライアントは秘密を守れるか。この二つの答えがフローを決める。

フロー 規格と状態 リソースオーナーはその場にいるか クライアント種別 使われる場所
認可コードフロー RFC 6749 (Proposed Standard, 2012-10) いる。ブラウザで同意する 機密と公開の両方 人が介在するほとんどすべての場合
PKCE (認可コードフローの拡張) RFC 7636 (Proposed Standard, 2015-09) いる 公開は必須、機密は推奨 コード横取りとコード注入への防御を足すとき
デバイス認可グラント RFC 8628 (Proposed Standard, 2019-08) いるが別の端末で承認する 主に公開 スマートテレビ、コンソール、プリンタなど入力が乏しい機器
クライアントクレデンシャルグラント RFC 6749 (Proposed Standard, 2012-10) いない。人が介在しない 機密クライアントのみ サービスが自らの名義で行うサーバー間通信

3.1 認可コードフローが二段階である理由

認可コードフローを初めて見ると、なぜ段階が二つに分かれるのかが引っかかる。ブラウザのリダイレクトで認可コードを受け取り、そのコードをあらためて認可サーバーに送ってアクセストークンに交換する。一度で済みそうなところをわざわざ二往復する。

理由は二つの往復が別々のチャネルだからである。前者は利用者のブラウザを経由する経路だ。リダイレクトURLはアドレスバーに出て、ブラウザ履歴に残り、いくつもの層を通る。後者はクライアントと認可サーバーが直接やり取りする経路である。アクセストークンを後者の経路だけで往復させれば、トークンそのものが前者の経路の痕跡として残らない。この分離が認可コードフローがいまも残っている理由だ。

3.2 デバイスフローとクライアントクレデンシャルフロー

デバイス認可グラントはブラウザを開けない機器のためのものである。機器は利用者にコードを見せ、利用者はスマートフォンなど別の端末で承認を済ませる。そのあいだ機器は、クライアントとユーザーエージェントのあいだの双方向通信を要求する代わりに認可サーバーを繰り返しポーリングする。リモコンでパスワードを打たせる代わりに、認可という行為そのものを別の端末へ移してしまった設計である。

クライアントクレデンシャルグラントは性格がまるで違う。ここにはリソースオーナーがいない。クライアントが自らの管理下にある資源、あるいは認可サーバーとあらかじめ取り決めた資源へアクセスするときに使う。だから規格は釘を刺しておく。このグラント種別は機密クライアントだけが使わなければならない。よくある誤用は、ユーザーデータをこのフローで取ってくることだ。そうすると「誰が許可したのか」に当たる当事者が構造から消え、監査記録に残るのはサービスアカウント一つだけになる。

4. 一覧から外れた二つのフロー - インプリシットとパスワードグラント

2025年1月にRFC 9700が出た。名前はBest Current Practice for OAuth 2.0 Security、状態はBest Current Practice、BCP 240である。この文書はRFC 6749とRFC 6750、そして脅威モデル文書であるRFC 6819を更新する。つまり今日OAuthを設計するなら、基準線は6749ではなくこの文書だ。

この文書がやったことのうち最も目立つのが二つのフローを一覧から下ろしたことである。

4.1 インプリシットグラント

RFC 9700はクライアントがインプリシットグラントを使うべきではない(SHOULD NOT)と記す。認可レスポンスにアクセストークンを載せて返す他のレスポンスタイプも同じ括りに入る。ただし認可レスポンスへのアクセストークン注入が防止される場合は例外として残されている。根拠は二つだ。

  • アクセストークンの漏えいと再利用に脆弱である
  • この方式には送信者結合を施す標準化された手段がない

同じ文書は代案を一行で与える。codeレスポンスタイプを使え。前節のチャネル分離を思い出せば理由が重なる。インプリシットフローはトークンをフロントチャネルに載せる。すると3.1で分けておいたものが再び合わさってしまう。

4.2 リソースオーナーパスワードクレデンシャルグラント

こちらは表現がもっと強い。RFC 9700はこのグラントを使ってはならない(MUST NOT)と記す。理由は四つある。

  • リソースオーナーのクレデンシャルをクライアントに安全でない形で露出させる
  • 攻撃面を広げる
  • 利用者に認可サーバーの外でクレデンシャルを入力する習慣をつけさせる
  • 二要素認証と併せて動くようには設計されていない

三つ目の理由がとくに実務的だ。利用者に習慣をつけさせるという表現は技術的な脆弱性ではなく習慣についての指摘である。アプリの画面でパスワードを入れるのが普通だと学習した利用者は、その画面が誰のものかを見分ける根拠を失う。四つ目はもっと直接的だ。クレデンシャルの組をそのまま受け取る構造には、二要素認証が入り込む余地がない。この点は二段階認証を方式別に整理した記事と併せて読むとさらに鮮明になる。

参考までにOAuth 2.1という名の作業が進行中である。2026年3月2日付の第15版が出ており、状態はインターネットドラフト(Internet-Draft)で、RFC 6749とRFC 6750を統合しつつインプリシットグラントとパスワードグラントを規定から外す。ただしドラフトは標準ではない。今日、規範的な根拠が必要ならば引くべきはRFC 9700のほうである。

5. PKCEが防ぐもの - もう公開クライアントだけの話ではない

RFC 7636の題はProof Key for Code Exchange by OAuth Public Clientsである。2015年9月に出たProposed Standardで、要旨が狙う問題は一つだ。認可コードグラントを使う公開クライアントが認可コード横取り攻撃に対して脆弱であること。

緩和の方式は名前のとおりである。クライアントが要求ごとに動的に暗号学的な鍵を作り、認可要求とトークン要求を互いに結び付ける。認可要求にはその鍵から派生した値を、トークン要求には元の値を送り、認可サーバーが両者を照合する。結果としてコードだけを手にした側はそれをトークンに換えられない。

ここまでが古い理解である。変わったのは適用範囲だ。RFC 9700はこう整理する。

  • 公開クライアントはPKCEを必ず使わなければならない(MUST)。
  • 機密クライアントにもPKCEの使用が推奨される(RECOMMENDED)。認可コードの誤用と注入に対して強い保護を提供するからである。
  • 攻撃者が盗んだ認可コードを注入しようとしても、元の値の照合が食い違ってトークンエンドポイントで交換が成立しない。
  • 同じ文書はPKCEが強い攻撃者のいる状況でもCSRFに対する保護を提供すると記している。

この変化を一文にするとこうなる。PKCEは「秘密を守れないクライアントのための補完」から「コード注入という脅威そのものへの防御」へ位置を移した。バックエンドはクライアントシークレットをきちんと保管しているからPKCEは要らない、という判断は、防御対象を一世代前の基準で捉えていることになる。

同じ節で併せて見るべき規範がリダイレクトURIの照合だ。RFC 9700は認可サーバーが正確な文字列一致を使わなければならない(MUST)と求める。例外はネイティブアプリのlocalhostリダイレクトURIにおけるポート番号だけであり、パターンマッチングは複雑さとセキュリティ上の問題から明示的に退けられている。照合が緩ければ認可レスポンスの戻り先の集合がクライアントの意図より広がる。

認可サーバーを複数つなぐクライアントには規範がもう一つある。RFC 9207は2022年に出たProposed Standardで、認可レスポンスに発行者識別子を明示的に載せるissパラメータを定義する。目的はミックスアップ攻撃(mix-up attack)への対応だ。RFC 9700はクライアントが要求を送った発行者を保存しておき、レスポンスで受け取った値と照合して不一致なら相互作用を中止しなければならないと求めている。

6. トークンをどこに置くか - ブラウザストレージとクッキーの代償

この問いには単一の正解がない。規格もそう言っている。2026年8月に出たRFC 10017はOAuth 2.0 for Browser-Based Applicationsという題のBest Current Practiceで、BCP 212の番号を共有する。この文書はブラウザベースのアプリケーションが取りうる構造を三つ並べる。

  • バックエンドフォーフロントエンド(BFF) - トークンをサーバー側に置き、ブラウザとはセッションクッキーでやり取りする
  • トークン仲介バックエンド - バックエンドは機密クライアントとして動きつつアクセストークンをブラウザに降ろす
  • ブラウザベースのOAuth 2.0クライアント - ブラウザの中のコードがそのままクライアントである

文書が三つの構造を並べながら付けた一文が判断の物差しになる。それぞれの構造はセキュリティと単純さのあいだで異なる折り合いを提示する。機微なアプリケーションにはBFFを勧めつつ、他の構造にも正当な用途があるというのが文書の姿勢だ。

その折り合いを読む軸になる一文がもう一つある。悪意あるJavaScriptコードは正規のアプリケーションコードと同じ権限を持つ。スクリプト実行が破られた状況で「スクリプトが読めないブラウザ内のストレージ」というものはない。ただしアクセスの難度には差があり、文書はローカルストレージのようにどこからでもアクセスできる保存領域は、より隔離された領域より悪意あるJavaScriptから到達しやすいと記している。

保管場所 スクリプト実行が破られたとき ブラウザの自動送信 付いてくる要求
ローカルストレージ 射程内。文書がアクセスしやすい領域に分類する なし スクリプト注入の遮断が事実上唯一の防衛線
セッションストレージ 射程内。寿命がタブに縛られるだけでアクセス制御ではない なし タブ間で共有されないことに伴う体験設計
JavaScriptのメモリ変数 射程内。同じ実行文脈にある なし 再読み込みのたびに再取得の経路が必要
HttpOnlyかつSecureのクッキー (BFF) セッション状態をスクリプトが直接読めない あり。ブラウザが載せて送る 自動送信ゆえのクロスサイト要求の軸の防御

BFF側に付く規範は明示的だ。BFFは自らのクッキーにSecureフラグとHttpOnlyフラグを必ず有効にしなければならない(MUST)。文書はHttpOnlyクッキーが攻撃者がセッション状態へ直接アクセスすることを防ぐと説明する。反対側の代償もはっきりしている。クッキーはブラウザが勝手に付けて送るものなので、「その要求は自分の画面から始まったのか」を別に確かめる軸が必要になる。この代償の勘定は信頼境界とウェブセキュリティ制御を整理した記事でクッキー送信の規則とともに詳しく扱っている。

トークン仲介バックエンドについても文書は両面を併記する。バックエンドは機密クライアントとして動かなければならない(MUST)が、アクセストークンがブラウザへ降りた瞬間にブラウザ内の悪意あるコードによるトークン窃取にさらされる。どの構造を選んでも、消える危険ではなく移る危険である。

7. スコープと最小権限 - 実際に強制される場所

スコープはRFC 6749で空白区切りで大文字小文字を区別する文字列の並びとして定義される。ここで見落とされやすい規範が続く。認可サーバーはクライアントが要求したスコープを全部または一部無視してよい。自らのポリシーやリソースオーナーの指示に従ってそうする。そして発行されたスコープが要求されたものと異なる場合、認可サーバーは実際に付与された範囲を知らせるためにレスポンスにscopeパラメータを含めなければならない。

ここから出る結論が実務では大きい。スコープは要求であって保証ではない。クライアントのコードが「自分たちはこの三つを要求したからこの三つがある」を前提に書かれていると、認可サーバーが一つ削った瞬間にその前提は事実でなくなる。読むべきは要求の一覧ではなくレスポンスのscopeである。

そしてより重要な問い。スコープはどこで強制されるのか。答えはリソースサーバーだ。RFC 9700はこう記す。すべてのリソースサーバーは、すべての要求について、その要求とともに来たアクセストークンがまさにそのリソースサーバーで使われることを意図したものかを検証する義務がある。同じ節はトークンの権限そのものを狭めることも求める。アクセストークンは特定のリソースサーバーに対象を限定すべきであり(SHOULD)、それが現実的でなければ少数のリソースサーバーの集合に限定すべきである。対象の指定はscopeパラメータでも、RFC 8707のresourceパラメータでも可能だと文書は付け加える。

ここで崩れるもの。フロントエンドでスコープを見てボタンを隠すのは強制ではなく案内である。リソースサーバーが要求のたびにトークンの対象と範囲を確かめないなら、そのボタンが画面にあろうとなかろうと当該エンドポイントは開いている。対象の限定をしなければ別のリソースサーバーのために発行されたトークンがそのまま通る。最小権限とはスコープ文字列を短く書くことではなく、検査する地点をリソースサーバーに置くことである。

8. リフレッシュトークンとローテーション - 検知するという言葉の意味

RFC 9700の要求から正確に写しておく。公開クライアントに発行されるリフレッシュトークンは送信者結合されているか、リフレッシュトークンのローテーションを使わなければならない(MUST)。二つに一つだ。機密クライアント側については、RFC 6749がすでにリフレッシュトークンを発行を受けたクライアントでのみ使えるよう求めている。

送信者結合の手段として文書が挙げるのは相互TLSとDPoPの二つである。DPoPはRFC 9449として2023年に出たProposed Standardであり、アプリケーション層で所持証明を付けてトークンに送信者結合を施す方式だ。要旨はこの方式がアクセストークンとリフレッシュトークンの再利用攻撃を検知できるようにすると記している。こうした装置がなぜ別途必要なのかはRFC 6750の定義に戻れば明らかである。ベアラートークンは暗号学的な鍵の所持を証明しなくても、そのトークンに結び付いた資源へのアクセスを許すものだ。持っている者がすなわち権限者ということになる。

ローテーション側の原理は文書にそのまま書かれている。リフレッシュトークンが漏えいし、攻撃者と正規のクライアントの双方がそれを使うと、どちらか一方が無効化されたリフレッシュトークンを提示することになり、その事実が認可サーバーに侵害を知らせる。次の一文が実務ではさらに重要だ。認可サーバーはどちらが無効なトークンを提出したかを判別できないため、有効なリフレッシュトークンを失効させる。

この二文を続けて読むとローテーションの性格が見えてくる。ローテーションは窃取を防ぐ装置ではない。盗まれたトークンが使われる瞬間を検知し、判別が不可能なので両方を一緒に断つ装置である。ここから設計上の負担が二つ付いてくる。

  • 正規の利用者も一緒に切れる。検知が働けば再ログインが必要になり、その体験を設計しておかないとセキュリティ装置が障害として受け取られる
  • クライアントが新しいトークンを確実に保存してこそ成り立つ。更新のレスポンスで受け取った新しいリフレッシュトークンを保存できず古いほうを再び使えば、そのクライアントが自ら無効なトークンを提示する側になる。同じ理由で、複数の要求が同時に更新を試みる構造では更新の経路を一本にまとめる条件が新たに付く

クライアント側の保存の問題はコマンドラインの観点からCLI認証の設計を整理した記事で掘り下げている。

9. 検証はどこで行うか - クライアントが代われないもの

トークンが二つなら検証する側も二つだ。この対応を逆にすると事故になる。

9.1 アクセストークンはリソースサーバーが検証する

RFC 9700の一文をもう一度引く。すべてのリソースサーバーは、すべての要求について、ともに来たアクセストークンがそのリソースサーバーで使われることを意図したものかを検証する義務がある。この検証はトークンの形式によって二手に分かれる。

  • JWT形式なら - RFC 9068が2021年に出たProposed Standardとして、OAuth 2.0のアクセストークンをJWTで発行する際の必須と任意のクレーム、そして検証の手順を定める。このプロファイルができた理由そのものが、製品ごとにばらばらなJWTトークン実装によって相互運用が壊れていたことにある
  • 不透明トークンなら - RFC 7662が2015年10月に出たProposed Standardとして、保護資源が認可サーバーにトークンの有効状態とメタデータを問い合わせるイントロスペクションを定義する。トークンの中に情報が入っていてもいなくても動くというのがこの方式の設計意図だ

9.2 IDトークンはクライアントが検証する

OpenID Connect Core 1.0はIDトークン検証の節で、クライアントが確かめるべきものを列挙している。

  • 発行者が正確に一致するか
  • 対象に自分のクライアント識別子が入っているか
  • 現在時刻が有効期限より前か
  • 認可要求にnonceを送ったならその値が一致するか
  • 発行者が提供する鍵で署名が有効か

9.3 だからクライアントでやってはいけないこと

ブラウザの中のコードがトークンを解釈すること自体は問題ではない。有効期限が近いかを見て更新に備えたり、利用者の名前を画面に描いたりするのは正常な使い方だ。問題はその解釈結果を権限判定の根拠にすることである。

理由は二つある。第一に、6節の一文がここでも成り立つ。ブラウザで動くコードは悪意あるコードと同じ権限の上にあり、そのコードが行った署名検証は同じ実行文脈で無力化されうる。第二に、サーバーはブラウザが何を検証したのかを知る術がない。リソースサーバーに届くのは要求とトークンだけである。

だから署名検証、発行者の確認、対象の確認、有効期限の確認はそのトークンを根拠に何かを渡す側で行われなければならない。アクセストークンならリソースサーバー、IDトークンならそれを根拠にセッションを作るクライアントのサーバーである。ブラウザでのデコードは表示のための便宜であって制御ではない。

10. よくある誤った組み合わせ - この組み合わせで何が崩れるか

下の表は禁止の一覧ではない。それぞれの組み合わせがどの保証を手放すことになるかを規格の文に対応させたものである。

組み合わせ この組み合わせで崩れるもの 対応する規格
アクセストークンを身元の証明として使う 誰のためにどの認証を経て発行されたかを確かめる根拠がない RFC 6749 セキュリティ考慮, OpenID Connect Core 1.0
インプリシットフローの維持 トークンが認可レスポンスに載って出て、送信者結合の標準手段がない RFC 9700 (SHOULD NOT)
パスワードグラントと二要素認証の併用要求 グラント自体が二要素認証と動くように設計されていない RFC 9700 (MUST NOT)
公開クライアントにPKCE未適用 コード横取りとコード注入への防御そのものがない RFC 7636, RFC 9700 (公開クライアントはMUST)
リダイレクトURIの部分一致を許可 認可レスポンスの戻り先の集合が意図より広がる RFC 9700 (正確な文字列一致がMUST)
ブラウザにリフレッシュトークンを置きローテーション未適用 窃取を検知する地点も、送信者を縛る地点もない RFC 9700, RFC 10017
認可サーバーを複数つなぎ発行者を未確認 レスポンスがどの認可サーバーから来たかを確定する根拠がない RFC 9207, RFC 9700
リソースサーバーがトークンの対象を確認しない 別のリソースサーバーのために発行されたトークンがそのまま通る RFC 9700 (すべての要求への検証義務)
ネイティブアプリを埋め込みウェブビューで認可 クレデンシャルを認可サーバーにだけ渡すという前提が成り立たない RFC 8252 (BCP 212)
スコープを画面上でだけ強制 強制の地点がリソースサーバーでなければエンドポイントは開いている RFC 6749 スコープの定義, RFC 9700
クライアントクレデンシャルグラントでユーザーデータにアクセス 許可した当事者が消え、監査記録がサービスアカウントに収束する RFC 6749 (機密クライアントのみ、MUST)

確認できなかったこと

  • この記事の根拠はRFCの原文とOpenID Connect Core 1.0の文書に書かれた規範的な記述だけである。個々の認可サーバー製品やライブラリがその規範をどう実装したかは確認しておらず、特定の実装が規格に適合しているかについては何も主張しない
  • OAuth 2.1は2026年3月2日付の第15版のインターネットドラフトである。ドラフトは標準ではなく、公開までに内容が変わりうる。この記事はドラフトがインプリシットグラントとパスワードグラントを規定から外すという編集方針までを引いており、細かい条項は引いていない
  • RFC 9700が対象の指定手段として言及するRFC 8707のresourceパラメータは、引用関係でのみ扱っており原文と突き合わせていない
  • 相互TLSに基づく証明書結合トークンの規格原文は開いていない。RFC 9700が送信者結合の手段として相互TLSとDPoPの二つを挙げるという事実までを確認した
  • 各フローの実際の採用比率を示す信頼できる公開統計は見つけられなかった。そのため「ほとんどのサービスはこうしている」といった記述はこの記事にはない

読むべき文書の順番

規格を最初から順に読むと時間がかかる。下の順番はまず語彙を押さえ、そのうえで今の基準線で上書きするやり方である。

  1. RFC 6749のロールと用語の節、そして認可コードフローの節。ここで4つのロールとパラメータ名を押さえる。ほかの文書はすべてこの語彙で書かれている
  2. RFC 6750。ベアラートークンが何を保証しないのかを短く確かめる。8節の議論はここから始まる
  3. RFC 7636。PKCE。短く、問題の定義が明快だ
  4. RFC 9700 (BCP 240)。今日の基準線。6749と6750、6819を更新する。6749を先に読んでからこれを読まないと、一覧から何が外れたのかが見えない。順番を入れ替えると理由が見えなくなる
  5. 自分の状況に合うもの一つ。ブラウザアプリならRFC 10017、ネイティブアプリならRFC 8252、入力が乏しい機器ならRFC 8628
  6. ログインが目的ならOpenID Connect Core 1.0のIDトークンの節とIDトークン検証の節
  7. トークンの形式と検証が問題ならRFC 9068かRFC 7662のうち自分のトークン形式に当たるほう
  8. 認可サーバーを複数つないでいるならRFC 9207、ベアラートークンから抜けたいならRFC 9449、エンドポイントのディスカバリが要るならRFC 8414

最後にこの記事の主張を三つにまとめる。第一に、OAuthは委譲された認可の規格であり、ログインはその上に載る別の層である。規格の名前がすでにそう言っている。第二に、検査する地点をどこに置いたかがその制御の実体だ。スコープもトークン検証も、画面で行えば案内であり、リソースサーバーで行ってはじめて強制になる。第三に、今日の基準線はRFC 6749ではなくRFC 9700である。2012年の文書だけを読んで設計すれば、その後13年のあいだに一覧から下ろされたものをそのまま抱えて始めることになる。
