Shell 退出码与 set -e - 它抓住什么又漏掉什么

用实际运行输出逐一打开 errexit、pipefail 与 nounset 的盲区

2026-07-29 开发/基础设施

引言: CI 是绿的，部署下去的值却是空的

有一个脚本，开头写着 set -euo pipefail。它从配置文件读两个值，拼出一条清理命令。我在配置文件里没有这两个键的状态下运行了它，结果如下。

  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

两个没读到的值都成了空字符串并一路流了下去。拼出来的命令行路径停在 /srv/backup/，保留天数则彻底消失，只剩下一个 -mtime +。而脚本的退出码是0。CI 亮了绿灯，没有人再回头看这次构建。

这个脚本里 set -e、set -u、set -o pipefail 全都开着。就是人们常说的 shell 脚本安全三件套那一行。那一行挡不住这次事故。弄清它为什么挡不住、又能挡到哪一步，正是本文的目的。

静默失败之所以可怕，原因很简单。失败一旦以退出码 0 上报，它就不是失败而是成功。它不是因为人跳过了日志而被漏掉，而是因为流水线判定为通过才被漏掉。轰轰烈烈死掉的脚本改掉就行，而亮着绿灯做错事的脚本，连需要改这件事本身都不会被发现。

本文不劝你加 set -euo pipefail。它先告诉你这行能保护到哪里，之后才让你加。规则依据 GNU Bash Reference Manual 与 POSIX 规范核对，行为全部在临时目录里直接运行。正文中的所有输出都是屏幕上真实出现过的。第 15 节的盲区表就是本文的结论。

先把边界划开。同一个脚本能否跑第二遍在跑两遍也安全的脚本，运行前能否预知结果在如何做出真正的 --dry-run。如果说那篇讲的是如何传达计划与应用的结果，这篇讲的就是更前面的一步，失败究竟该怎么被检测到。给变量加引号的语法在Shell 引号规则。

1. 运行环境与本文的依据

正文中的所有输出都是实际运行的结果。复现环境如下。

  • 操作系统: Windows 10 Pro 10.0.19045 之上的 MSYS2 系 Unix 环境
  • bash: GNU bash 5.2.37(1)-release (x86_64-pc-msys)
  • POSIX sh: dash，用作确认 bash 分歧点的对照组
  • 工具: GNU coreutils 8.32
  • 工作位置: 新建的临时目录，每个实验新建子文件夹以隔离

正文中出现的路径全都是 /tmp/demo 这样的占位符。实际运行是在隔离的临时文件夹中进行的。退出码与 set 选项的行为源自 shell 语言本身，因此移到 Linux 或 macOS 上也一样。不过这个环境里有一项没能复现，先写在前面。

环境上出现分歧的地方 — 可执行位
POSIX 规定「找到了但无法执行」为 126。在 Linux 上运行一个去掉可执行位的文件会得到 126。但这个环境位于 NTFS 之上，chmod 644 并不会被真正强制，因此去掉可执行位之后脚本照样运行并返回 0。所以 126 我改用试图执行目录的情形来确认，这一侧正常地返回了 126。这就是正文中 126 的例子用目录而不是权限的原因。

规则核对只用一手资料。本文中没有「通常是这样」这类表述。

  • GNU Bash Reference Manual — The Set Builtin(-e、-u、pipefail)与 The Shopt Builtin(inherit_errexit)
  • The Open Group Base Specifications Issue 8 — Shell Command Language 2.8.2 Exit Status and Errors
  • 正在运行的 bash 自身 — 用 help set 直接查看这个二进制对选项的说明

2. 退出码基础 - 0、1、126、127、128+N

每条命令结束时都会留下一个 0 到 255 之间的整数，shell 把它放进 $?。规则只有一条。0 是成功，其余全是失败。要点在于不是「1 表示失败」，而是「不为 0 就是失败」。

$ true;  echo $?
0
$ false; echo $?
1
$ no_such_command_xyz 2>/dev/null; echo $?
127
$ ./sandbox 2>/dev/null; echo $?        # 试图执行一个目录
126
$ bash -c 'exit 3'; echo $?
3

127 与 126 是 POSIX 直接规定的值。规范 2.8.2 节这样写道。

If the command is not found, the exit status shall be 127. (…) if the command name is found, but it is not an executable utility, the exit status shall be 126.

因此127 几乎总是拼写错误或 PATH 问题。不是命令失败了，而是根本没找到命令。区分这两者能大幅缩短读 CI 日志的时间。

被信号杀死的情形会加上 128。我实际制造出来确认了。

$ sleep 30 & pid=$!; kill -9 "$pid"; wait "$pid" 2>/dev/null; echo $?
137
$ sleep 30 & pid=$!; kill -TERM "$pid"; wait "$pid" 2>/dev/null; echo $?
143

137 是 128+9(SIGKILL)，143 是 128+15(SIGTERM)。容器因内存超限被杀时显示 137 就是这个算法的结果。不过 POSIX 的措辞比想象中宽松。

If the command terminated due to the receipt of a signal, the shell shall assign it an exit status greater than 128. The exit status shall identify, in an implementation-defined manner, which signal terminated the command.

也就是说规范只保证到「大于 128」，而正好是 128+N 属于实现自行决定的惯例。实务中主流 shell 都用 128+N，可以放心依赖，但不要误当成规定。

退出码会被截断成 8 位。这一点也实测了。

$ bash -c 'exit 256'; echo $?
0
$ bash -c 'exit -1' 2>/dev/null; echo $?
255
$ sh -c 'exit 300'; echo $?
44

exit 256 变成了 0。为了表示失败而挑了个大数字，结果被上报为成功，事故就出在这里。把错误条数直接当退出码用的脚本尤其危险，错误正好 256 条就是绿灯。

最后，0 与 1 也并非总是成功与失败。每个工具都有自己的约定。

$ printf 'alpha\nbeta\n' > /tmp/demo/data.txt
$ grep -q alpha /tmp/demo/data.txt; echo $?
0
$ grep -q zzzzz /tmp/demo/data.txt; echo $?
1
$ grep -q alpha /tmp/demo/nope.txt 2>/dev/null; echo $?
2

grep 用0 表示找到、1 表示没找到、2 表示出错。没找到是正常结果而不是错误。但 set -e 把 1 和 2 一视同仁地当作失败。在 set -e 之下裸调用 grep，「没有」这个正常结果就会杀死脚本。第 13 节会再讲。

退出码含义出处实测确认
0成功POSIXtrue
1一般性失败(惯例)惯例false
2用法错误或「存在差异」(惯例)惯例grep 出错

3. set -e 的规定 - 手册自己列出了例外

set -e(errexit)在 help set 里只有一行说明。

-e Exit immediately if a command exits with a non-zero status.

只读这一行，就会理解成「失败就无条件停下」。而这个理解正是本文中所有事故的起点。Bash Reference Manual 的完整表述要长得多，而且自己把例外列了出来。

The shell does not exit if the command that fails is part of the command list immediately following a while or until reserved word, part of the test in an if statement, part of any command executed in a && or || list except the command following the final && or ||, any command in a pipeline but the last (subject to the state of the pipefail shell option), or if the command's return status is being inverted with !.

一共五条。while、until 之后的命令列表，if 的条件，&& 与 || 列表中非最后一条命令，管道中非最后一条命令，以及被 ! 取反的命令。到这里还算广为人知。真正的陷阱是后面那一段。

If a compound command or shell function executes in a context where -e is being ignored, none of the commands executed within the compound command or function body will be affected by the -e setting, even if -e is set and a command returns a failure status.

展开来说就是这样。把函数放进 if 条件的那一刻，这个函数的整个函数体就走出了 set -e 的保护范围。处在条件位置上的只有函数调用这一行，效力却波及函数内的每一行。下一节用运行来展示。

4. set -e 抓不住的位置 - 全部用运行验证

只读规则太抽象。我把所有盲区塞进同一个脚本，开头加上 set -e 后运行。只要有一处被拦住，脚本就会死在那里。

先看基准线，确认 set -e 正常工作的情形。

== A. baseline: set -e DOES stop here ==
  inner script died, rc=1  (NOT REACHED never printed)

裸的 false 确实会被抓住。接下来是盲区。以下是同一次运行中连续输出的内容。

== B. condition of if ==
  survived: if-condition

== C. while condition ==
  survived: while-condition

== D. left side of && / || ==
  survived: false &&
  ran RHS of ||
  survived: false ||

== E. negated with ! ==
  survived: ! true

== F. non-final command of a pipeline ==
  survived: false | cat   rc=0

== G. function failing inside a condition ==
  ...function continued past its own false
  survived: function under if

== H. local x=$(failing) hides the status ==
  local v=$(false) -> rc=0  (local's own status wins)
  split declaration caught it -> rc=1

== J. arithmetic that evaluates to zero ==
  (( c++ )) returned nonzero because the OLD value was 0; c is now 1

== ALL BLIND SPOTS PASSED THROUGH; script still alive ==

一处都没被拦住。能走到最后一行，就意味着 set -e 全程开着却放过了上面所有失败。逐条来看。

  • B 与 C — if false; then …; fi 和 while false; do …; done。条件本来就是允许失败的位置。这很自然，因为失败正是承载「假」这个含义的方式
  • D — false && echo x 和 false || echo … 都活了下来。|| true 这个惯用写法就是从这里来的。方便，但代价很大。第 13 节会再看
  • E — ! true 最终结果是失败(1)却照样通过。被取反的命令写在例外清单里
  • F — false | cat 的退出码是0。管道的退出码取自末尾，而 cat 成功了。这是第 7 节的主题
  • G — 最危险的一条。函数内 false 的下一行照常执行了。这正是第 3 节手册最后那一段。把函数放进 if，整个函数体就变得毫无防护
  • H — local 吞掉了退出码。第 5 节单独讲
  • J — (( c++ )) 在运算结果为 0 时返回退出码 1。计数器从 0 开始的话，第一次自增就会杀死脚本。改用 (( ++c )) 或 c=$((c+1)) 可以避开
⚠ G 在实务中长什么样
「用函数包起来再用 if 检查」是非常自然的结构。写下 if deploy_app; then … 这一行的瞬间，deploy_app 内部的所有失败都被忽略了。即使中间步骤全部失败，只要最后一行成功，函数就返回 0，if 就判定为真。如果你在函数内部依赖着 set -e，这份依赖会仅仅因为调用方式而消失。

5. local 会吞掉退出码

第 4 节的 H 在 set -e 的各种陷阱中最常摧毁实务代码。原理很简单。local 是内建命令而不是赋值语法，而命令的退出码是 local 自己的。无论内部的命令替换以什么结束，local 都会以「变量创建成功」的含义返回 0。

先看普通赋值的行为。这一侧是正常的。

== plain assignment: status comes FROM the substitution ==
  v=$(false)      -> rc=1
  v=$(exit 7)     -> rc=7
  v="pre-$(exit 7)-post" -> rc=7  v=[pre--post]

赋值式的退出码是命令替换的退出码原样传上来。即使夹在字符串中间，7 也活了下来。所以 set -e 能正常抓住这种写法。现在在前面加一个声明关键字看看。

== declaration builtins SWALLOW it ==
  local    v=$(exit 7) -> rc=0
  declare  v=$(exit 7) -> rc=0
  typeset  v=$(exit 7) -> rc=0
  export   v=$(exit 7) -> rc=0
  readonly r=$(exit 7) -> rc=0

五个全是 0。这不是 local 独有的问题，而是声明类内建命令整体的性质。export PATH_X=$(some_command) 同样会吞掉失败。

我确认了与 set -e 搭配时，究竟哪种写法会真正杀死脚本。

== under set -e: which one actually kills the script? ==
  rc=7   out=[]
     form: v=$(exit 7); echo ALIVE
  rc=0   out=[ALIVE-in-func
ALIVE]
     form: f(){ local v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE
  rc=7   out=[]
     form: f(){ local v; v=$(exit 7); echo "ALIVE-in-func"; }; f; echo ALIVE

只有中间那种活了下来，打印了两次 ALIVE。第一和第三种都以退出码 7 正确地终止了。差别仅仅在于声明与赋值是写在一行还是拆成两行。

一行声明多个变量会更加安静。

== the multi-declaration variant is worse ==
  three locals, rc=0  b=[]

只有中间那个失败了，却完全没有办法知道是哪一个失败的。退出码是 0，只有失败的那个变量静静地成了空值。

如果只记一条规则
local x=$(cmd) 永远拆成两行。先用 local x 只创建名字，下一行再写 x=$(cmd) 赋值。declare、export、readonly 同理。这一条规则就能消掉相当一部分 set -e 事故。

6. 命令替换不继承 errexit

还有一处盲区。$( ) 内部默认是一个关掉了 set -e 的独立世界。运行确认如下。

$ shopt inherit_errexit
inherit_errexit	off

== A. WITHOUT inherit_errexit ==
  out=[LEAKED]  rc=0
  script continued
  rc=0

我在开着 set -e 的脚本里执行了 out=$( false; echo "LEAKED" )。内部的 false 没能让子 shell 停下，后面的 echo 执行了，LEAKED 进了变量。如果你习惯在 $( ) 里连写多条命令，前面全部失败也没关系，只要最后一条成功就会产出一个值。

bash 4.4 起有了修正它的选项。手册的表述如下。

If set, command substitution inherits the value of the errexit option, instead of unsetting it in the subshell environment. This option is enabled when POSIX mode is enabled.

打开它再跑同样的代码，结果就分开了。

== B. WITH inherit_errexit ==
  rc=1

== C. POSIX mode also turns it on ==
  rc=1

两者都死在了内部的 false 上。正如手册所述，用 --posix 启动也得到了同样的效果。于是实务上的建议就变成这样。

set -euo pipefail
shopt -s inherit_errexit    # bash 4.4 以上

但这同样不是万能的。第 12 节会给出即使开着 inherit_errexit 也照样通过的例子。因为当 local 更早吞掉退出码时，inherit_errexit 根本没有介入的机会。

7. set -o pipefail - 找回管道的真实状态

管道的退出码默认是末尾那条命令的。前面的无论死于什么都被忽略。

== 1. pipeline status = LAST command, by default ==
  false | true   -> rc=0
  true  | false  -> rc=1
  false | cat    -> rc=0

false | true 是成功。前面失败了结果却是 0。打开 pipefail 就不一样了。

== 2. same pipelines with pipefail on ==
  false | true   -> rc=1
  true  | false  -> rc=1
  false | cat    -> rc=1

三种情形都变成了失败。正在运行的 bash 自己的说明是这样。

pipefail — the return value of a pipeline is the status of the last command to exit with a non-zero status, or zero if no command exited with a non-zero status

意思是「非零退出码中最靠右的那个」。确认过了。

== 3. pipefail returns the RIGHTMOST nonzero ==
  (exit 3)|(exit 4)|true -> rc=4
  (exit 3)|true|true     -> rc=3

实务中这一点咬得最狠的地方是 tee。为了留日志接进管道的那一刻，失败就消失了。

== 5. the classic: cmd | tee log ==
  no pipefail: rc=0  PIPESTATUS=(1 0)   <- failure vanished
  pipefail   : rc=1  PIPESTATUS=(1 0)

同一条管道，上面是成功下面是失败。把构建命令用 | tee build.log 包起来是极常见的写法，没有 pipefail 的话构建坏了 CI 也照样通过。

不过 pipefail 有反方向的代价。它会把正常的提前结束变成失败。

== 8. pipefail cannot see a head that quits early (SIGPIPE) ==
  yes | head -1 -> rc=141  PIPESTATUS=(141 0)

head -1 读一行就关闭时，yes 会因 SIGPIPE 而死，得到141(128+13)。完全没有问题的正常行为，pipefail 却把它当失败上报。如果你用了 grep -q 或 head 截断前段的管道，这个位置需要单独处理。

8. PIPESTATUS - 逐段读取并立即保存

pipefail 会把一切压成一个退出码。要知道是哪一段失败的，就用 bash 的 PIPESTATUS 数组。

== 4. PIPESTATUS keeps every stage ==
  rc=0  PIPESTATUS=(3 0 4 0)

四段的退出码全都保留了下来。退出码跟随末尾因而是 0，但看数组就能直接看出第 1 段和第 3 段失败了。

不过这个数组有一个致命的性质。它会被紧接着的下一条命令覆盖。

== 6. PIPESTATUS is clobbered by the very next command ==
  first read : PIPESTATUS=(3 4)
  second read: PIPESTATUS=(0)   <- the echo above overwrote it

第一个 echo 成功的瞬间，数组就变成了 (0)。没办法读第二次。所以务必在管道之后紧接着的那一行复制下来。

== 7. save it immediately ==
  saved copy : (3 4)  stage0=3 stage1=4

实务写法是这样。在管道之后立刻整体复制数组，之后只看副本。

curl -fsS "$url" | gzip -d | psql "$dsn"
st=("${PIPESTATUS[@]}")          # 必须是紧接着的下一行
if [ "${st[0]}" -ne 0 ]; then echo "下载失败 (${st[0]})" >&2; exit 1; fi
if [ "${st[1]}" -ne 0 ]; then echo "解压失败 (${st[1]})" >&2; exit 1; fi
if [ "${st[2]}" -ne 0 ]; then echo "导入失败 (${st[2]})"     >&2; exit 1; fi

只开 pipefail 的话只能知道「某处失败了」，这样写则能把「下载失败了」留进日志。三段以上的管道里，这个差别很大。

9. set -u - 未定义变量与空数组

set -u(nounset)在引用未定义变量时立即终止。它是阻止拼写错误产生的空值流进命令行的机制。

== 1. plain unset reference ==
  echo "[$nope]"     rc=127 bash: line 1: nope: unbound variable
  echo "[${nope}]"   rc=127 bash: line 1: nope: unbound variable

这里的退出码很有意思。同样的错误，调用方式不同数值也不同。四种组合我全部确认了。

$ bash -u -c 'echo "[$nope]"'   ; echo $?
127
$ bash -u script.sh             ; echo $?
1
$ dash -u -c 'echo "[$nope]"'   ; echo $?
2
$ dash script.sh                ; echo $?
2

bash 用 -c 调用是 127，跑脚本文件是 1。dash 两种都是 2，消息也不同，是 parameter not set。不要试图用特定退出码来识别 set -u 产生的失败。没有可移植性。

规避靠默认值语法，有没有冒号意义不同。

== 2. defaults let you opt out ==
  ${nope:-fallback}        rc=0   [fallback]
  ${nope-fallback}         rc=0   [fallback]
  ${nope:?must be set}     rc=127 bash: line 1: nope: must be set

== 3. set vs empty are different ==
  empty="" then ${empty:-d}   rc=0   [d]
  empty="" then ${empty-d}    rc=0   []

有冒号是「未设置或为空」，没有冒号是「未设置」。如果空字符串必须算作有效值就去掉冒号。${var:?消息} 在强制必填参数时很好用，不用自己写 if，一行就够。

接下来是常被搞混的空 $@ 与空数组。这部分曾随 bash 版本而分歧，所以连同本环境的版本一起记录。确认的版本是 GNU bash 5.2.37。

== 4. empty $@ and $1 ==
  no args, "$@"        rc=0   argc=0 / REACHED
  no args, "$1"        rc=127 bash: line 1: $1: unbound variable
  no args, "${1:-def}" rc=0   [def] / REACHED

== 5. empty arrays ==
  declare -a arr=(); "${arr[@]}"   rc=0   n=0 / REACHED
  unset arr; "${arr[@]}"           rc=0   REACHED
  declare -a arr=(); "${arr[0]}"   rc=127 bash: line 1: arr[0]: unbound variable
  empty array + ${arr[@]:-}        rc=0   x=[] / REACHED

整理一下就是。在 bash 5.2.37 上，无参数时的 "$@" 与空数组的 "${arr[@]}" 是安全的。反之，像 "$1" 和 "${arr[0]}" 这样去取单个元素就会炸。分界线在于「是展开整体，还是去取特定元素」。

曾经有一段时期，空 "$@" 与空数组在 set -u 下会报错(bash 4.4 之前)。上面的结果是在 5.2.37 上直接确认的，由于这个环境里没有旧版 bash，过去的行为并未复现。如果你的目标是 macOS 自带的 bash 3.2 这类旧 shell，用 "${arr[@]:-}" 的写法防御会更保险。

最后确认一点，set -u 与失败的命令毫无关系。

== 6. -u alone does not stop a FAILING command ==
  -u only, false   rc=0   REACHED
  -eu, false       rc=1   (no output)

只开 -u 的话 false 杀不死脚本。三个选项各做各的事，谁也替代不了谁。

10. trap - 用 ERR 定位，用 EXIT 收尾

trap 是记录失败点并保证收尾的机制。先看 ERR trap。

== 1. ERR trap reports line and command ==
  step one
  ERR: line 5 rc=2 cmd=[grep -q nothing /nonexistent/path]
  outer saw rc=2

用 LINENO、$?、BASH_COMMAND 三个变量，第几行、哪条命令、以什么退出码死的都留在了一行里。比用 set -x 全量打印，日志干净得多。

要让它深入函数内部需要 -E(errtrace)。

== 5. functions need -E (errtrace) to inherit the ERR trap ==
  without -E: trap did not fire inside f
  with -E: trap fired inside f

这就是写 set -eE 而不是 set -e 的理由。没有 -E，ERR trap 在函数、子 shell、命令替换内部都不会触发。

但它有一个决定性的局限。ERR trap 拥有与 set -e 完全相同的盲区。我把第 4 节的盲区原样放到 ERR trap 下跑了一遍。

== 4. ERR trap has the SAME blind spots as set -e ==
  reached the end with no ERR trap firing
  outer saw rc=0

if false、false || true、! true、false | cat、local v=$(exit 7) 全部执行了，trap 却一次都没有触发。「挂了 ERR trap 所以失败都能抓到」这种期待并不成立。

EXIT trap 性质不同。无论成功还是失败它都一定会执行，因此适合清理临时文件。

== 2. EXIT trap always runs; use it for cleanup ==
  workdir created: yes
  cleanup: removing workdir
  outer saw rc=5  (EXIT trap did not change it)

脚本以退出码 5 死掉，清理照样执行了，而且退出码保持为 5。这里我用实测区分了一个常见的误解。

== 3. an EXIT trap CAN silently rewrite the exit code ==
  cleanup running
  outer saw rc=9
  cleanup running
  outer saw rc=9
  ...now a cleanup with an explicit exit in the trap:
  cleanup running
  outer saw rc=0   <- the real failure was erased

这个区分很重要。trap 内最后一条命令是失败还是成功，本身并不会改变退出码。前两种情形里 9 都原样保留了。只有在 trap 内显式调用 exit 时退出码才会被覆盖。第三种里真实的失败 9 被抹成了 0。

⚠ 不要在清理函数里调用 exit
如果 trap cleanup EXIT 的 cleanup 里有 exit 0，所有失败都会被上报为成功。实测中以退出码 9 死掉的脚本最终以 0 结束。清理函数应该只做清理然后安静返回。如果确实需要处理退出码，就在入口用 rc=$? 接住，最后再用 exit "$rc" 还回去。

11. 子 shell 与函数的边界

整理一下 set -e 跨越边界时会怎样。手册写明它对 shell 环境和每个子 shell 环境分别生效。运行确认如下。

== 1. set -e is inherited by subshells ==
  rc=1

== 2. ...but not if the subshell sits in a condition ==
  subshell CONTINUED past false
  subshell failure absorbed by ||
  script alive, rc=0

子 shell 会继承 set -e，但一旦这个子 shell 处在条件位置上，它的内部就整个失去防护。与第 4 节的 G 同理。

命令替换如第 6 节所见默认不继承。下面是没开 inherit_errexit 时的结果。

== 3. command substitution: -e does NOT apply inside by default ==
  out=[SHOULD-NOT-APPEAR]
  rc=0

== 5. the killer: substitution inside a declaration ==
  local out=[SHOULD-NOT-APPEAR] rc=0
  script survived
  rc=0

函数的返回值是最后执行的那条命令的退出码。不写 return 的话返回的就是它。

== 6. a function without an explicit return ==
  f -> 1       # f(){ true; false; }   最后是 false
  g -> 0       # g(){ false; true; }   最后是 true
  h -> 0       # h(){ echo "..."; }    echo 成功了

g 是危险的那个。内部失败了，但最后一行成功，于是返回 0。习惯性地在校验函数末尾加一行 echo 或 log，就意味着那个函数永远成功。这类函数必须显式写 return。

== 7. exit inside a subshell only leaves the subshell ==
  after subshell, rc=4  (parent still running)
  parent rc=0

圆括号里的 exit 4 只结束了子 shell。父进程继续跑，最终退出码是 0。把「校验失败就 exit」写在子 shell 或管道里，脚本是不会停的。

管道的每一段也是子 shell，所以变量赋值会丢失。

== 8. a pipeline runs its stages in subshells ==
  after while-in-pipeline: count=0  (child's copy was discarded)
  with process substitution: count=3

用 printf … | while read … 数出来的值是0。那是子进程里的变量，回不到父进程。改成进程替换就得到 3。先数错误条数、最后再判定的脚本经常掉进这个陷阱。它永远以「错误 0 条」结束。

12. 开着 set -euo pipefail，错误的值照样通过

回到引言里的脚本。把前面的碎片拼起来，就能解释它为什么通过了。脚本是这样的。

#!/usr/bin/env bash
set -euo pipefail

read_key() {
  local value=$(grep -m1 "^$1=" "$2" | cut -d= -f2)
  echo "$value"
}

target=$(read_key target /tmp/demo/app.conf)
retain=$(read_key retain_days /tmp/demo/app.conf)

echo "  target      = [$target]"
echo "  retain_days = [$retain]"
echo "  would run: find /srv/backup/$target -mtime +$retain -delete"
echo "  DEPLOY OK"

配置文件里只有 name 和 owner，target 与 retain_days 并不存在。运行结果如下。

=== run 1: the 'safe' version ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK
  script rc=0  <- CI sees GREEN

失败被抹掉了三层。逐条来说是这样。

  • grep 没找到键，以 1 结束，但后面接着 | cut，于是管道的退出码变成 cut 的 0。因为开着 pipefail，到这一步还能作为 1 活下来
  • 但那条管道位于 local value=$(…) 之内。local 吞掉退出码把它变成 0(第 5 节)
  • 函数以 echo "$value" 结束。echo 会成功，所以函数的返回值也是 0(第 11 节)
  • 结果 target=$(read_key …) 收到的是 0，set -e 没有理由介入。set -u 也帮不上忙，因为变量不是「未定义」，而是「被定义为空字符串」

那加上第 6 节学到的 inherit_errexit 会怎样？我在同一个脚本里只加了 shopt -s inherit_errexit 这一行然后运行。

=== run 2: same script, inherit_errexit added ===
  target      = []
  retain_days = []
  would run: find /srv/backup/ -mtime + -delete
  DEPLOY OK

结果完全一样。inherit_errexit 是让命令替换内部的 errexit 活过来的选项，但这里local 比它更早吞掉了退出码，所以它没有介入的机会。这说明靠多开选项是防不住这类事故的。

解决办法不是选项而是校验。读到值之后，直接确认「读到了吗」和「是不是空的」。

read_key() {
  local value
  if ! value=$(grep -m1 "^$1=" "$2"); then
    printf 'config key missing: %s\n' "$1" >&2
    return 3
  fi
  value=${value#*=}
  if [ -z "$value" ]; then
    printf 'config key empty: %s\n' "$1" >&2
    return 3
  fi
  printf '%s\n' "$value"
}
=== run 3: validated version ===
config key missing: target
  run3 rc=3

以退出码 3 正确地失败了，并且消息里留下了缺哪个键。改动有四处。拆开了 local 的声明与赋值，用 if ! 直接接住 grep 的失败，用参数展开代替 cut 从而去掉了管道，以及显式检查了空值。

⚠ 本节的结论
set -euo pipefail 是用来抓住「命令失败了」的机制。它抓不住「命令成功了但值是错的」。而实务事故里相当一部分属于后者。空字符串、与预期不符的格式、0 条的列表，全都是成功命令的正常输出。值的有效性只能由人亲自去检查。

13. 退出码设计 - 要向调用方传达什么

到目前为止讲的是检测失败的问题，接下来是把检测到的东西传达出去的问题。状态有三种以上时，0 和 1 就不够用了。广泛使用的形式是三分支。

退出码含义调用方要做的事
0正常 — 没有问题通过
2存在差异 — 检查成功了但结果不同看内容判断并批准
1错误 — 检查本身没能执行立即失败并告警
64 以上用法错误等更细分的状态修正调用方式

我做了一个会给出三种状态的检查器，以及接收它的一方，然后运行。

  PASS  : no differences
    -> caller exits 0
  DRIFT : 3 files differ  (gate: fail the build, keep the log)
    -> caller exits 2
  ERROR : checker itself failed
    -> caller exits 1
  USAGE : bad invocation
    -> caller exits 64

接收方的骨架是这样。因为在 set -e 之下直接调用会让所有非零值杀死脚本，所以把退出码接进变量再用 case 分开。

rc=0
out=$(./check.sh "$1") || rc=$?     # 不死掉，只接住退出码
case "$rc" in
  0)  echo "  PASS  : $out" ;;
  2)  echo "  DRIFT : $out" ;;
  1)  echo "  ERROR : checker itself failed" ;;
  64) echo "  USAGE : bad invocation" ;;
  *)  echo "  UNKNOWN rc=$rc" ;;
esac
exit "$rc"

这里 || rc=$? 是核心。正如第 4 节 D 所见，|| 的左侧是 set -e 的盲区，所以脚本不会死，退出码则原样留在变量里。这是把盲区当作工具而不是问题来用的场合。

反过来，|| true 在同一个位置上销毁信息。

== 3. the anti-pattern: '|| true' erases the state ==
  after || true, rc=0  <- error is gone

== 4. '|| true' vs capturing the code ==
  captured rc=1  <- still known, still recoverable

人们加 || true 是想表达「这条命令允许失败」，但它实际宣告的是「我永远不会知道这条命令是怎么结束的」。允许失败和不需要知道失败是两回事。用 || rc=$? 接住就能同时满足两者。

对于 grep 这类「没有」是 1 的工具，这样包起来。

if grep -q "$pattern" "$file"; then
    echo "找到了"
elif [ $? -eq 1 ]; then
    echo "没找到 — 属于正常"
else
    echo "grep 执行出错" >&2; exit 1
fi

需要快速定位失败点时 set -x 很有用，它会把实际执行的命令原样打印出来。

== 5. set -x shows the failing command ==
  + grep -q token /nonexistent/file.txt
  grep: /nonexistent/file.txt: No such file or directory

优点是能看到展开之后的最终形态。变量是不是空的、路径是怎么拼起来的，都会立刻显现。不过输出量很大，所以只把可疑区间用 set -x … set +x 包起来更好。

最后，别忘了把接到的退出码原样还回去。即使有清理 trap，退出码也会被保留。

== 6. exit with the code you were given ==
  propagating rc=2
  cleaning up
  outer sees 2

在区分计划与应用的结构中如何接线这套约定，在如何做出真正的 --dry-run的退出码一节里讲得更详细。

14. 与 POSIX sh 分歧的地方

如果脚本第一行是 #!/bin/sh，上面讲的一半都不存在。我把同样的代码分别喂给 bash 和 dash 做了对照。

功能bash 5.2.37dash实测消息
set -o pipefail可用没有Illegal option -o pipefail
PIPESTATUS(3 4)没有Bad substitution
数组n=3没有Syntax error: "(" unexpected
trap … ERR触发没有trap: ERR: bad trap
trap … EXIT触发，rc=5触发，rc=5两边相同
进程替换hello没有Syntax error: redirection unexpected
local可用可用两边都是 v=1
local 吞掉退出码rc=0rc=0两边同样吞掉
set -e + 函数 + if通过通过两边都是 CONTINUED ALIVE
exit 300rc=44rc=44两边都按 8 位截断

该怎么读这张表。

  • 没有 pipefail。要在 POSIX sh 脚本里抓住管道失败，就只能避开管道本身，写进临时文件、确认退出码之后再交给下一步
  • 既没有 PIPESTATUS 也没有数组。实际上没有办法查看分段状态
  • 没有 ERR trap。EXIT trap 两边都能用，退出码也同样是 5。清理逻辑可移植，失败日志则不可
  • dash 里也有 local。而且连吞掉退出码的性质都一模一样。第 5 节的陷阱在 #!/bin/sh 下同样成立
  • set -e 的盲区完全相同。把函数放进 if，两边都通过了。这不是 bash 的特殊行为，而是shell 语言的规定

概括起来就是安全装置是 bash 专有的，陷阱则是两边共通的。需要可移植性就意味着失去工具却只留下陷阱，所以选 #!/bin/sh 时应当有相应的理由。

15. 盲区表 - 从情形到替代方案

这是本文的结论。遇到左侧的情形时 set -e 什么也不会做，必须改用右侧的做法。

情形set -e 抓得住吗该改用什么
裸的失败命令抓得住保持原样即可
if cmd; then 的条件抓不住这是预期行为。要在条件内区分错误与「假」，就直接看 $?
while cmd; do 的条件抓不住在循环体内单独检查
cmd && … / cmd || … 的左侧抓不住用 || rc=$? 接住退出码再用 case 分支
! cmd抓不住用 if ! cmd; then 的写法明示意图
管道中非最后一条命令抓不住set -o pipefail 加上立即复制 PIPESTATUS
cmd | tee log抓不住set -o pipefail。没有它构建失败也会通过
把函数放进 if 或 ||抓不住 — 整个函数体无防护在函数内逐步检查并显式写 return
local x=$(cmd)抓不住拆成两行，local x 与 x=$(cmd)
declare、export、readonly 赋值抓不住同上。把声明与赋值分开
$( ) 内部的失败抓不住(默认)shopt -s inherit_errexit(bash 4.4+)
子 shell 处在条件位置时抓不住在子 shell 内部直接检查
函数最后一行是 echo 时抓不住 — 永远是 0用 return 明示想要的退出码
(( c++ )) 且 c 为 0假阳性 — 会死掉(( ++c )) 或 c=$((c+1))
cmd | while read 内的计数器不适用 — 值会丢失进程替换 done < <(cmd)
命令成功了但值是空字符串抓不住 — 任何选项都不行用 [ -z "$v" ] 之类直接校验
子 shell 内的 exit只结束子 shell在父进程接住退出码后再次 exit
清理 trap 内的 exit 0把所有失败覆盖成 0不要在 trap 里调用 exit

16. 模板 - 它保证什么又不保证什么

下面是反映了以上内容的起步骨架。把这个模板不保证什么也一并写出来，才是本节的要点。

#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true   # 仅限 bash 4.4+

readonly WORKDIR=$(mktemp -d)
cleanup() {
    rm -rf "$WORKDIR"        # 不要在这里调用 exit(第 10 节)
}
trap cleanup EXIT
trap 'echo "失败: line $LINENO rc=$? cmd=[$BASH_COMMAND]" >&2' ERR

need() {                     # 校验必填值(第 12 节)
    local name="$1" value="$2"
    if [ -z "$value" ]; then
        echo "缺少必填值: $name" >&2
        return 3
    fi
}

run_stage() {
    local rc                 # 声明与赋值分开(第 5 节)
    local out
    out=$(some_command "$1") || rc=$?
    : "${rc:=0}"
    case "$rc" in
        0) printf '%s\n' "$out" ;;
        *) echo "阶段失败: $1 (rc=$rc)" >&2; return "$rc" ;;
    esac
}

main() {
    local value
    value=$(run_stage fetch)
    need "value" "$value"    # 即使成功也要校验值
    echo "正常完成"
}

main "$@"

这个模板保证的东西如下。

  • 在裸的失败命令处立即停下(-e)
  • 管道中间的失败不会消失(pipefail)
  • 在拼写错误造成的未定义变量引用处停下(-u)
  • 命令替换内部的失败也能抓住(inherit_errexit)
  • 函数内部 ERR trap 也会触发，失败点会留进日志(-E)
  • 无论以哪条路径结束，临时目录都会被清理(EXIT trap)
  • 清理 trap 不会覆盖退出码(trap 内没有 exit)

不保证的东西更重要。

  • 把函数放进 if 或 ||，整个函数体就走出了保护范围。模板自己的 run_stage 也不例外
  • 命令成功了但值是错的，它抓不住。所以才单独放了 need。校验是人写的，不是选项替你做的
  • 0 条、空列表、与预期不符的格式，全都是正常的成功。「应该要有结果」这个条件必须自己写
  • 由于 pipefail，用 head 截断前段的管道可能以 141 失败(第 7 节)。这类位置要单独处理
  • set -u 不会阻止空字符串。被定义为空的变量并不是未定义
  • 外部命令失败了却返回 0 的话，shell 无从知晓。退出码不准确的工具必须靠输出来校验

最后是几条自查命令，用于在既有脚本里寻找本文提到的陷阱。

### 声明与赋值粘在一起的位置
$ grep -rnE '(local|declare|typeset|export|readonly)[[:space:]]+[A-Za-z_]+=\$\(' .

### 接进管道后失败可能消失的位置
$ grep -rn '| *tee' .

### 清理 trap 内的 exit
$ grep -rnE 'trap .*(exit|EXIT)' .

### 完全没有安全选项的脚本
$ grep -rLE 'set -[a-zA-Z]*e' --include='*.sh' .

结论: 没被检测到的失败不是失败，而是虚假的成功

压缩成规则就是四句话。

  • set -e 只抓「裸的失败命令」。条件、取反、逻辑运算、管道中段全都是例外，而这不是 bug，是手册自己列出的规定
  • 把函数放进条件位置，整个函数体就失去保护。实测中函数内失败命令的下一行照常执行了。这是盲区里最宽的一处
  • local、declare、export 会吞掉退出码。五个声明类内建命令全都返回 0。仅仅把声明与赋值拆成两行就能解决
  • 最危险的是命令成功了但值是错的。任何 set 选项都抓不住，校验只能手写

把用运行确认过的内容再梳理一遍。九处盲区塞进一个脚本、开着 set -e 运行，结果一处都没被拦住就走到了最后。前面加上 local 之后退出码 7 变成了 0，五个声明类内建命令表现一致。false | tee 在没有 pipefail 时被上报为成功。PIPESTATUS 被随后的一个 echo 抹掉了。清理 trap 内的 exit 0 把真实的失败 9 覆盖成了 0。而一个开着 set -euo pipefail 外加 inherit_errexit 的脚本，放行了两个空值并以退出码 0 结束。

最后这个例子就是本文的要点。安全选项是用来抓「命令失败了」的机制，而不是保证「结果是对的」的机制。一旦把这两者当成同一回事，开启了选项这件事本身就会成为跳过校验的借口。事实上，写下引言那个脚本的人，很可能正是因为加了 set -euo pipefail 才省掉了值的校验。

所以把顺序倒过来。先写下什么地方可能出错，再写检查它的代码，最后才加上安全选项。set -euo pipefail 是地板而不是天花板。如果第 15 节表里右列非空的行，在你的脚本中哪怕只出现一行，那一行就是下一次事故发生的地方。

# Shell 退出码与 set -e - 实务参考表

验证环境: GNU bash 5.2.37(1)-release, dash, GNU coreutils 8.32。
以下数值全部是实际运行确认过的。

---

## 1. 退出码表

| 退出码 | 含义 | 出处 | 实测确认 |
|---|---|---|---|
| 0 | 成功 | POSIX | `true` |
| 1 | 一般性失败(惯例) | 惯例 | `false` |
| 2 | 用法错误或「存在差异」 | 惯例 | `grep` 出错 |
| 126 | 找到了但无法执行 | POSIX 2.8.2 | 执行目录 |
| 127 | 找不到命令 | POSIX 2.8.2 | 不存在的命令 |
| 137 | 128+9，被 SIGKILL 终止 | 实现惯例 | `kill -9` |
| 143 | 128+15，被 SIGTERM 终止 | 实现惯例 | `kill -TERM` |
| 141 | 128+13，SIGPIPE | 实现惯例 | `yes | head -1` |
| 256 以上 | 截断为 8 位(256 变成 0) | 实测 | `exit 256` |

工具也各有约定。`grep` 用 0=找到、1=没找到、2=出错。
「没找到」是正常结果，但 `set -e` 把它当作失败。

---

## 2. set -e 盲区清单

以下各项在 `set -e` 开启的状态下全部**会通过**。已用运行验证。

- [ ] `if cmd; then` 的条件 → 通过
- [ ] `while cmd; do` 的条件 → 通过
- [ ] `cmd && ...` 的左侧 → 通过
- [ ] `cmd || ...` 的左侧 → 通过
- [ ] `! cmd`(取反)→ 通过
- [ ] 管道中非最后一条命令 → 通过(`false | cat` 得到 rc=0)
- [ ] **把函数放进 `if` 或 `||`，整个函数体都无防护** ← 最宽的盲区
- [ ] `local x=(命令替换)` → `local` 自己的退出码胜出，rc=0
- [ ] `declare` / `typeset` / `export` / `readonly` 赋值 → 全部 rc=0
- [ ] 命令替换 `( )` 内部 → 默认不继承 errexit
- [ ] 处在条件位置的子 shell → 内部也毫无防护
- [ ] 函数最后一行是 `echo` → 永远返回 0
- [ ] 子 shell 内的 `exit` → 只结束子 shell
- [ ] 清理 trap 内的 `exit 0` → 把所有失败覆盖成 0
- [ ] **命令成功了但值是空字符串** ← 任何选项都抓不住

`(( c++ ))` 是反方向的陷阱。运算结果为 0 时它返回退出码 1，
所以计数器从 0 开始时第一次自增就会杀死脚本。改用 `(( ++c ))`。

---

## 3. 三个选项各自做什么

| 选项 | 抓得住 | 抓不住 |
|---|---|---|
| `set -e` | 裸的失败命令 | 上面清单里的全部 |
| `set -u` | 未定义变量的引用 | 空字符串、失败的命令 |
| `set -o pipefail` | 管道中间的失败 | 把 SIGPIPE 提前结束误判为失败 |
| `shopt -s inherit_errexit` | 命令替换内部的失败 | 若 `local` 先吞掉则无效 |
| `set -E` | 让 ERR trap 在函数内触发 | 与 `set -e` 相同的盲区 |

`set -u` 实测(bash 5.2.37):
- 无参数时对参数列表整体的展开、以及空数组的整体展开都是安全的
- 去取单个元素(第一个位置参数或 `arr[0]`)就会炸
- 用 `${var:-默认值}` 规避。有冒号是「未设置或为空」，没有则是「未设置」
- 退出码没有可移植性: bash 脚本 1、bash -c 127、dash 2

---

## 4. PIPESTATUS 要立即保存

只能在管道之后读一次，紧接着的下一条命令就会覆盖它。

```
curl -fsS "url" | gzip -d | psql "dsn"
st=("${PIPESTATUS[@]}")          # 必须是紧接着的下一行
[ "${st[0]}" -ne 0 ] && echo "下载失败"
[ "${st[1]}" -ne 0 ] && echo "解压失败"
[ "${st[2]}" -ne 0 ] && echo "导入失败"
```

---

## 5. 安全的模板

```
#!/usr/bin/env bash
set -Eeuo pipefail
shopt -s inherit_errexit 2>/dev/null || true

readonly WORKDIR=(把 mktemp 的结果赋进来)
cleanup() {
    rm -rf "WORKDIR"          # 不要在这里调用 exit
}
trap cleanup EXIT
trap 'echo "失败: line LINENO cmd=[BASH_COMMAND]" >&2' ERR

need() {                      # 即使成功也要校验值
    local name="1" value="2"
    if [ -z "value" ]; then
        echo "缺少必填值: name" >&2
        return 3
    fi
}

run_stage() {
    local rc                  # 声明与赋值分开
    local out
    out=(把命令的执行结果赋进来) || rc=?
    case "rc" in
        0) printf '%s\n' "out" ;;
        *) echo "阶段失败 (rc)" >&2; return "rc" ;;
    esac
}
```

**保证的东西**: 在裸的失败处停下、保留管道失败、拦截未定义变量、
检测命令替换内部的失败、函数内 ERR trap、清理临时目录、保留退出码。

**不保证的东西**: 把函数放进条件，整个函数体就走出保护范围。
值为空或格式不符时抓不住。0 条的结果是正常的成功。
`set -u` 不会阻止空字符串。退出码不准确的外部工具必须靠输出来校验。

---

## 6. 退出码设计约定

| 退出码 | 含义 | 调用方要做的事 |
|---|---|---|
| 0 | 正常 | 通过 |
| 2 | 存在差异(检查成功了) | 查看内容后判断 |
| 1 | 错误(检查本身失败) | 立即失败并告警 |
| 64+ | 用法错误等 | 修正调用方式 |

接收方这样写。用 `|| rc=?` 接住，`set -e` 就不会杀掉它。

```
rc=0
out=(运行检查命令) || rc=?
case "rc" in
  0)  echo "PASS" ;;
  2)  echo "DRIFT" ;;
  1)  echo "ERROR" ;;
  *)  echo "UNKNOWN" ;;
esac
exit "rc"
```

不要用 `|| true`。它宣告的不是「这条命令允许失败」，
而是「我永远不会知道它是怎么结束的」。

---

## 7. 与 POSIX sh 的差异

| 功能 | bash 5.2.37 | dash |
|---|---|---|
| `set -o pipefail` | 可用 | **没有** |
| `PIPESTATUS` | 可用 | **没有** |
| 数组 | 可用 | **没有** |
| `trap ... ERR` | 可用 | **没有** |
| `trap ... EXIT` | 可用 | 可用 |
| 进程替换 | 可用 | **没有** |
| `local` | 可用 | 可用 |
| `local` 吞掉退出码 | rc=0 | **rc=0(相同)** |
| `set -e` + 函数 + `if` | 通过 | 通过(相同) |

概括: **安全装置是 bash 专有的，陷阱则是两边共通的。**

---

## 8. 自查命令

```
### 声明与赋值粘在一起的位置
grep -rnE '(local|declare|typeset|export|readonly)[[:space:]]+[A-Za-z_]+=' .

### 接进管道后失败可能消失的位置
grep -rn '| *tee' .

### 清理 trap 内的 exit
grep -rnE 'trap .*(exit|EXIT)' .

### 完全没有安全选项的脚本
grep -rLE 'set -[a-zA-Z]*e' --include='*.sh' .
```

---

## 核心一句话

`set -euo pipefail` 是**用来抓「命令失败了」的机制**，
**而不是保证「结果是对的」的机制。**它是地板而不是天花板。
