서론 - 같은 이름이 가리키는 자리

클래스 본문에 items = []를 쓰면 인스턴스가 모두 같은 리스트를 본다. Python 공식 튜토리얼의 「Class and Instance Variables」 절은 이 형태를 「mistaken use of a class variable」로 표시한 예(Dog.tricks)로 싣고, 인스턴스 변수는 인스턴스마다 고유한 데이터를 위한 것, 클래스 변수는 모든 인스턴스가 공유하는 속성과 메서드를 위한 것이라고 구분한다. 증상 자체의 재현은 기본 인자에 빈 리스트를 뒀더니 호출마다 값이 쌓인다의 7절과 테스트 순서를 섞으면 드러나는 것의 4.2절에 이미 있다.

혼란의 뿌리는 같은 이름이 인스턴스에도 있을 수 있고 클래스에도 있을 수 있다는 점이다. 클래스 속성은 클래스 본문에서 대입된 이름으로 클래스의 __dict__에 있고, 인스턴스 속성은 인스턴스의 __dict__에 있는 이름이다. 같은 이름이 두 곳 중 어디에 있느냐에 따라 읽기·쓰기·삭제의 결과가 갈린다. 아래에서는 그 위치를 직접 들여다보고, 한 동작씩 어느 자리를 건드리는지 가른다.

다루는 질문은 다음과 같다.

  • 값은 인스턴스와 클래스 중 어디에 놓여 있고 그것을 어떻게 알아내는가.
  • 읽기와 쓰기와 삭제는 같은 자리를 보는가.
  • 클래스 쪽 값을 바꾸면 이미 만들어진 인스턴스는 어떻게 되는가.
  • +=는 정수와 리스트에서 각각 무엇을 남기는가.
  • 서브클래스는 부모의 가변 속성을 공유하고, type(self)로 쓰면 값은 어디에 들어가는가.
  • dataclass·ClassVar·__slots__는 이 구분을 어떻게 다루는가.
  • 의도해서 공유하려면 어떤 형태가 읽는 사람에게 분명한가.

값이 놓인 자리 - __dict__와 vars로 보기

이 절의 출력은 기존 글 7절에서 다룬 실험이며 여기서는 vars()·type(obj).__dict__로 값의 위치를 보는 데 쓴다. 데이터 모델 문서는 클래스 속성 참조가 클래스 사전의 조회로 번역된다고 적고(C.x는 C.__dict__["x"]), 클래스 인스턴스에 대해서는 인스턴스의 사전이 속성을 가장 먼저 찾는 자리이고 거기에 없고 클래스에 그 이름이 있으면 검색이 클래스 속성으로 이어진다고 적는다. 두 사전의 출력은 다음과 같다.

class Cart:
                        items = []
                        label = 'cart'
                    
                    a = Cart()
                    b = Cart()
                    print('a.__dict__            :', a.__dict__)
                    print('vars(a)               :', vars(a))
                    print('Cart.__dict__ keys    :', [k for k in vars(Cart) if not k.startswith('__')])
                    print('type(a) is Cart       :', type(a) is Cart)
                    print('type(Cart.__dict__)   :', type(vars(Cart)).__name__)
                    print('a.items is Cart.items :', a.items is Cart.items)
                    a.items.append('x')
                    print('b.items               :', b.items)
a.__dict__            : {}
                    vars(a)               : {}
                    Cart.__dict__ keys    : ['items', 'label']
                    type(a) is Cart       : True
                    type(Cart.__dict__)   : mappingproxy
                    a.items is Cart.items : True
                    b.items               : ['x']

인스턴스 a의 사전은 비어 있다. items와 label은 Cart의 사전에만 있다. a.items is Cart.items가 True이고, a로 리스트에 값을 붙이자 b.items에도 보였다. 인스턴스 어디에도 리스트가 없는 채로 두 인스턴스가 클래스의 리스트 하나를 읽고 있었다. 클래스의 사전은 mappingproxy 형식으로 출력됐고, 값의 위치를 보는 데는 vars(obj)와 vars(type(obj)) 두 호출이면 충분하다.

  • vars(obj)가 인스턴스 사전을 돌려준다. 비어 있으면 인스턴스 속성이 없다.
  • vars(type(obj))가 클래스 사전을 돌려준다. 이름이 여기에만 있으면 클래스 속성이다.
  • obj.name is type(obj).name이 True이면서 인스턴스 사전에 이름이 없을 때 공유가 확정된다.
  • 여기서 is는 리스트 같은 가변 객체에만 쓴다. 작은 정수와 문자열에서 is 결과가 실행 방식에 따라 갈리는 것은 테스트는 통과하는데 운영에서만 조건이 안 맞는 이유가 다룬다.

읽기는 위로 올라가고 쓰기는 인스턴스에서 멈춘다

같은 이름의 읽기와 쓰기는 다른 자리를 본다. 데이터 모델 문서의 문장은 「Attribute assignments and deletions update the instance's dictionary, never a class's dictionary」이다. 읽기는 인스턴스에서 클래스로 올라가지만 인스턴스에 대한 대입과 삭제는 인스턴스의 사전만 고친다. 문자열 속성으로 본 이 비대칭의 출력은 다음과 같다.

class Cart:
                        label = 'cart'
                    
                    a = Cart()
                    b = Cart()
                    a.label = 'mine'
                    print('a.__dict__ after set  :', a.__dict__)
                    print('a.label, b.label, Cart.label:', a.label, b.label, Cart.label)
                    del a.label
                    print('after del a.label     :', a.label, a.__dict__)
                    Cart.label = 'changed'
                    print('after Cart.label=...  :', a.label, b.label)
                    b.label = 'shadow'
                    Cart.label = 'again'
                    print('b shadowed, a not     :', b.label, a.label)
a.__dict__ after set  : {'label': 'mine'}
                    a.label, b.label, Cart.label: mine cart cart
                    after del a.label     : cart {}
                    after Cart.label=...  : changed changed
                    b shadowed, a not     : shadow again

a.label = 'mine' 뒤 a의 사전에 항목이 생겼고 Cart.label은 그대로였다. del a.label 뒤에는 사전이 다시 비고 a.label이 클래스 값으로 돌아왔다. 클래스 쪽에서 Cart.label을 바꾸면 인스턴스 쪽에 자기 값이 없는 a가 따라왔고, 마지막 두 줄에서 자기 값을 가진 b는 클래스의 새 값에 영향받지 않았다. 동작별로 바뀌는 자리를 표로 모았다.

동작바뀌는 자리결과(위 출력 기준)
a.label = va.__dict__a만 달라지고 클래스와 b는 그대로
del a.labela.__dict__에서 항목 제거a가 다시 클래스 값을 읽음
Cart.label = vCart.__dict__자기 값이 없는 모든 인스턴스가 새 값을 읽음
b.label = v 뒤 Cart.label = wb.__dict__에 이미 있음b는 v 그대로, 다른 인스턴스는 w
a.items.append(x)클래스에 붙은 리스트 객체 자체객체를 보는 모든 곳에서 변경이 보임

표의 마지막 줄이 공유 증상의 정체이다. a.items.append(x)는 a.items를 읽은 뒤 그 객체의 메서드를 부르는 것이어서 인스턴스 사전에 대한 대입이 일어나지 않는다. 쓰기 규칙이 적용되는 것은 이름에 대입할 때뿐이고, 객체를 제자리에서 고치는 호출에는 적용되지 않는다.

클래스 쪽을 바꾸면 따라오는 인스턴스와 그렇지 않은 인스턴스

클래스 속성에 새 객체를 대입하는 것과 기존 객체를 고치는 것은 인스턴스에 미치는 범위가 다르다. 클래스 쪽에서 이름을 다시 묶고, 일부 인스턴스에는 자기 값을 둔 뒤 다시 묶었다.

class Box:
                        items = []
                        n = 0
                    
                    a = Box()
                    b = Box()
                    Box.items = ['new']
                    print('class rebinding        :', a.items, b.items)
                    a.items = ['mine']
                    Box.items = ['newer']
                    print('after a has its own    :', a.items, b.items)
                    Box.n = 5
                    a.n += 1
                    Box.n = 9
                    print('a.n, b.n, Box.n        :', a.n, b.n, Box.n)
class rebinding        : ['new'] ['new']
                    after a has its own    : ['mine'] ['newer']
                    a.n, b.n, Box.n        : 6 9 9

Box.items = ['new'] 직후 두 인스턴스가 모두 새 리스트를 읽었다. 클래스 사전의 이름이 가리키는 객체가 바뀌었고 인스턴스에는 자기 값이 없었기 때문이다. 그다음 a.items = ['mine']로 a에 자기 값을 두고 클래스를 다시 바꾸자 a만 따라오지 않았다. 숫자도 같다. Box.n = 5 뒤 a.n += 1은 읽은 5에 1을 더한 6을 a의 사전에 넣었고, 이후 Box.n = 9에서 b.n은 9로 따라갔지만 a.n은 6에 머물렀다.

  • 클래스 속성의 다시 묶기는 자기 값이 없는 인스턴스에만 퍼진다.
  • 인스턴스가 한 번 자기 값을 가지면 그 이름에 대해서는 클래스 변경이 닿지 않는다.
  • 그래서 같은 클래스의 인스턴스 중 일부만 새 설정을 읽는 현상은 어느 인스턴스가 자기 값을 갖게 됐는지에 달려 있다.

+=가 남기는 것 - 정수와 리스트의 차이

정수 부분은 기존 글 7절에서 다룬 실험이며 여기서는 vars()로 인스턴스 사전에 이름이 생기는지 보는 데 쓴다. self.count += 1은 읽기와 쓰기가 한 줄에 겹친다. 오른쪽의 읽기는 클래스까지 올라가고 왼쪽의 쓰기는 인스턴스에 멈춘다. 정수와 리스트에 같은 연산을 적용했다.

class Counter:
                        hits = 0
                        log = []
                    
                    p = Counter()
                    q = Counter()
                    p.hits += 1
                    p.hits += 1
                    q.hits += 1
                    print('p.hits q.hits Counter.hits:', p.hits, q.hits, Counter.hits)
                    print('p.__dict__ :', p.__dict__)
                    p.log += ['p']
                    q.log += ['q']
                    print('p.log      :', p.log, ' Counter.log:', Counter.log)
                    print('p.log is Counter.log:', p.log is Counter.log)
                    print('p.__dict__ :', p.__dict__)
                    p.log = p.log + ['new']
                    print('after p.log = p.log + [...]:', p.log, Counter.log, p.log is Counter.log)
p.hits q.hits Counter.hits: 2 1 0
                    p.__dict__ : {'hits': 2}
                    p.log      : ['p', 'q']  Counter.log: ['p', 'q']
                    p.log is Counter.log: True
                    p.__dict__ : {'hits': 2, 'log': ['p', 'q']}
                    after p.log = p.log + [...]: ['p', 'q', 'new'] ['p', 'q'] False

정수 쪽은 기대대로 갈렸다. p.hits는 2, q.hits는 1이고 클래스의 값은 0이다. 이름 hits가 p의 사전에 생겼기 때문이다. 리스트 쪽은 다르다. p.log += ['p']와 q.log += ['q'] 뒤에 클래스의 리스트에 두 값이 모두 들어 있었고, p.log is Counter.log가 True이다. 그런데 p의 사전에는 log가 생겼다. 리스트의 +=는 클래스에 붙은 리스트를 제자리에서 늘리고, 그 결과로 같은 리스트를 인스턴스 이름에 대입한 것으로 출력과 맞는다. 인스턴스 사전에 이름이 보인다고 해서 인스턴스 소유가 되지 않는다.

마지막 줄의 p.log = p.log + ['new']는 새 리스트를 만들어 대입하므로 p.log가 클래스의 리스트에서 떨어져 나왔다. 클래스 쪽 리스트에는 'new'가 없고 is는 False이다.

  • 정수의 +=는 새 객체를 만들어 인스턴스에 묶으므로 공유가 풀린다.
  • 리스트의 +=는 같은 객체를 늘리고 다시 묶으므로 공유가 남는다.
  • x = x + [...]는 새 리스트를 만들어 묶으므로 공유가 풀린다. 같은 결과처럼 보이는 두 식이 다르게 동작한다.
  • 인스턴스 사전에 이름이 있는지만 보지 말고 obj.name is type(obj).name까지 확인한다.

서브클래스는 부모의 리스트를 그대로 쓴다

서브클래스에서도 같은 규칙이 이어진다. 데이터 모델 문서는 이름이 클래스 사전에 없으면 검색이 기반 클래스로 이어진다고 적는다. 부모 하나와 자식 둘에서 리스트의 위치를 출력한 결과는 다음과 같다.

class Base:
                        tags = []
                    
                    class Child(Base):
                        pass
                    
                    class Other(Base):
                        tags = ['own']
                    
                    c = Child()
                    o = Other()
                    bs = Base()
                    print('Child.tags is Base.tags :', Child.tags is Base.tags)
                    print('Other.tags is Base.tags :', Other.tags is Base.tags)
                    c.tags.append('from child instance')
                    print('Base.tags               :', Base.tags)
                    print('bs.tags                 :', bs.tags)
                    print('o.tags                  :', o.tags)
                    print("'tags' in vars(Child)   :", 'tags' in vars(Child))
                    print('MRO of Child            :', [k.__name__ for k in Child.__mro__])
Child.tags is Base.tags : True
                    Other.tags is Base.tags : False
                    Base.tags               : ['from child instance']
                    bs.tags                 : ['from child instance']
                    o.tags                  : ['own']
                    'tags' in vars(Child)   : False
                    MRO of Child            : ['Child', 'Base', 'object']

Child는 tags를 자기 사전에 갖지 않았고 Child.tags는 Base.tags와 같은 객체였다. 자식 인스턴스로 값을 붙이자 부모 클래스와 부모 인스턴스에서도 그 값이 보였다. 클래스를 새로 만들면서 tags를 다시 선언한 Other는 자기 리스트를 가졌고 부모의 값과 섞이지 않았다. 조회 순서는 MRO 출력(Child, Base, object)대로 자식에서 부모로 올라간다.

  • 서브클래스를 만드는 것만으로는 클래스 속성의 리스트가 복제되지 않는다.
  • 서브클래스 본문에서 같은 이름을 다시 선언하면 그 서브클래스는 자기 객체를 갖는다.
  • 부모 속성을 서브클래스마다 따로 갖게 하려면 서브클래스가 만들어지는 시점에 새로 대입해야 한다. 방법은 10절에 있다.

카운터를 세는 두 방식 - type(self)와 클래스 이름

클래스 쪽 카운터를 올리는 코드는 두 가지로 쓰인다. 인스턴스의 클래스를 가리키는 type(self)와 클래스 이름을 직접 쓰는 방식이다. 서브클래스가 끼면 결과가 갈린다.

class Reg:
                        count = 0
                        def __init__(self):
                            type(self).count += 1
                    
                    class RegChild(Reg):
                        pass
                    
                    Reg(); Reg(); RegChild()
                    print('Reg.count, RegChild.count   :', Reg.count, RegChild.count)
                    print("'count' in vars(RegChild)   :", 'count' in vars(RegChild))
                    
                    class Reg2:
                        count = 0
                        def __init__(self):
                            Reg2.count += 1
                    
                    class Reg2Child(Reg2):
                        pass
                    
                    Reg2(); Reg2Child(); Reg2Child()
                    print('Reg2.count, Reg2Child.count :', Reg2.count, Reg2Child.count)
                    print("'count' in vars(Reg2Child)  :", 'count' in vars(Reg2Child))
Reg.count, RegChild.count   : 2 3
                    'count' in vars(RegChild)   : True
                    Reg2.count, Reg2Child.count : 3 3
                    'count' in vars(Reg2Child)  : False

type(self).count += 1은 읽기에서 부모의 값 2를 가져오고, 쓰기를 RegChild 자신의 사전에 했다. 그 결과 RegChild.count는 3이 되었고 Reg.count는 2로 남았다. 클래스 이름을 직접 쓴 Reg2.count += 1은 자식 인스턴스를 만들어도 부모의 사전만 고쳐 3 하나로 모였고 Reg2Child의 사전에는 이름이 생기지 않았다.

  • 전체 인스턴스 수를 세려면 클래스 이름을 직접 쓰는 쪽이 한 값으로 모은다.
  • 서브클래스별로 따로 세려면 type(self)를 쓰되, 처음 쓰는 순간 부모의 현재 값에서 출발한다는 점을 안다.
  • 두 방식이 한 클래스 계층에 섞이면 같은 이름의 값이 부모와 자식에서 어긋난다.

dataclass가 보는 것 - 필드, ClassVar, 가변 기본값

list의 ValueError는 기존 글 7절에서 다룬 실험이며 여기서는 필드·ClassVar 판정과 나란히 놓고 보는 데 쓴다. dataclass는 이 문제를 선언 단계에서 다룬다. 공식 문서는 기본값이 클래스 속성으로 저장된다는 점을 짚고, 해시할 수 없는 기본값이면 ValueError를 낸다고 적는다. 해시할 수 없으면 가변이라는 가정이며 부분적 해법이라고 스스로 밝힌다. 또 필드 타입이 typing.ClassVar이면 필드에서 제외되고 fields()가 돌려주지 않는다고 적는다. 필드·ClassVar·주석 없는 속성을 한 클래스에 둔 경우와 네 가지 기본값을 준 경우의 출력은 다음과 같다.

from typing import ClassVar
                    from dataclasses import dataclass, field, fields
                    
                    @dataclass
                    class Plain:
                        name: str
                        tags: list = field(default_factory=list)
                        registry: ClassVar[dict] = {}
                        note = 'no annotation'
                    
                    p1 = Plain('a'); p2 = Plain('b')
                    print('fields          :', [f.name for f in fields(Plain)])
                    print('annotations     :', list(Plain.__annotations__))
                    print('registry shared :', p1.registry is p2.registry is Plain.registry)
                    print('tags shared     :', p1.tags is p2.tags)
                    print('p1.__dict__     :', p1.__dict__)
                    print('note is a field :', 'note' in [f.name for f in fields(Plain)], '/ Plain.note =', Plain.note)
                    try:
                        Plain('x', ['q'], {}, 'extra')
                    except TypeError as e:
                        print('TypeError       :', e)
                    
                    for kind, default in [('list', []), ('dict', {}), ('set', set()), ('tuple', ())]:
                        try:
                            @dataclass
                            class Probe:
                                x: object = default
                            print(kind, '-> accepted')
                        except ValueError as e:
                            print(kind, '-> ValueError:', e)

                    annotations     : ['name', 'tags', 'registry']
                    registry shared : True
                    tags shared     : False
                    p1.__dict__     : {'name': 'a', 'tags': []}
                    note is a field : False / Plain.note = no annotation
                    TypeError       : Plain.__init__() takes from 2 to 3 positional arguments but 5 were given

fields()에는 name과 tags만 나왔다. registry는 주석에 있지만 ClassVar여서 빠졌고, 주석이 없는 note는 애초에 필드가 아니라 일반 클래스 속성으로 남았다. 생성자는 매개변수 2개까지만 받아 네 개를 넘기자 TypeError가 났다. 이 메시지는 Python 3.13.3 에서의 것이며 메시지 표기는 버전에 따라 다를 수 있다. tags는 인스턴스마다 다른 리스트이고 registry는 인스턴스와 클래스가 같은 사전을 가리켰다. 기본값 판정은 표와 같다.

  • 메시지가 처방(default_factory)까지 알려 준다.
  • 이 검사는 해시 가능 여부로 판정하는 부분적 해법이다.
  • ClassVar 주석은 공유를 표시할 뿐 막지 않는다. registry가 여전히 공유되는 것이 출력으로 보인다.

__slots__와 클래스 속성의 충돌

__slots__를 쓰는 클래스에서는 같은 이름의 클래스 속성이 허용되지 않는다. 데이터 모델 문서의 __slots__ 절(3.3.2.4)은 「class attributes cannot be used to set default values for slot variables; otherwise, the class attribute would overwrite the descriptor」라고 적는다.

try:
                        class WithSlots:
                            __slots__ = ('x',)
                            x = 1
                    except ValueError as e:
                        print('ValueError:', e)
                    
                    class Ok:
                        __slots__ = ('x',)
                    o = Ok()
                    o.x = 1
                    print('slots instance has __dict__:', hasattr(o, '__dict__'))
ValueError: 'x' in __slots__ conflicts with class variable
                    slots instance has __dict__: False

클래스를 만드는 순간 ValueError가 났다. 메시지는 슬롯 이름과 클래스 변수가 충돌한다고 알린다. 슬롯만 선언한 클래스의 인스턴스에는 __dict__가 없었다. 위 문서 문장이 말하는 범위는 슬롯 변수의 기본값을 클래스 속성으로 줄 수 없다는 것이고, 이 출력이 보여 주는 것도 그 충돌과 __dict__의 부재까지이다. 슬롯 변수의 기본값은 __init__에서 대입한다.

의도해서 공유하기 - 서브클래스별 레지스트리와 기본값 복사

공유가 의도일 때도 있다. 레지스트리나 기본 설정이 그렇다. 이때 문제는 공유 자체가 아니라 서브클래스까지 같은 객체를 쓰게 되는지와 읽는 사람이 의도를 알아보는지이다. 세 가지 형태의 출력은 다음과 같다. 앞의 둘은 서브클래스가 정의될 때 호출되는 __init_subclass__를 쓰며, 하나는 서브클래스별로 새 리스트를 대입하고 하나는 부모의 리스트에 이름을 모은다. 셋째는 클래스 사전의 기본값을 인스턴스가 복사해 쓰는 형태이다.

class Plugin:
                        registry = []
                        def __init_subclass__(cls, **kw):
                            super().__init_subclass__(**kw)
                            cls.registry = []          # each subclass gets its own list
                            Plugin.registry.append(cls.__name__)
                    
                    class A(Plugin): pass
                    class B(Plugin): pass
                    print('Plugin.registry :', Plugin.registry)
                    print('A.registry      :', A.registry, ' B.registry:', B.registry)
                    
                    class Shared:
                        registry = []
                        def __init_subclass__(cls, **kw):
                            super().__init_subclass__(**kw)
                            cls.registry.append(cls.__name__)
                    class C(Shared): pass
                    class D(Shared): pass
                    print('Shared.registry :', Shared.registry, C.registry is D.registry)
                    
                    # per-instance copy of a class-level default
                    class Config:
                        defaults = {'retries': 3}
                        def __init__(self, **over):
                            self.opts = {**type(self).defaults, **over}
                    c1 = Config(retries=5); c2 = Config()
                    print('c1.opts, c2.opts, defaults:', c1.opts, c2.opts, Config.defaults)
Plugin.registry : ['A', 'B']
                    A.registry      : []  B.registry: []
                    Shared.registry : ['C', 'D'] True
                    c1.opts, c2.opts, defaults: {'retries': 5} {'retries': 3} {'retries': 3}

Plugin은 서브클래스가 정의될 때마다 그 서브클래스에 빈 리스트를 새로 대입했다. A.registry와 B.registry는 각자의 리스트이고 부모의 리스트에는 서브클래스 이름 두 개가 모였다. Shared는 cls.registry에 이름을 더해 C와 D가 같은 리스트를 가리켰다. 둘 다 의도에 따라 맞는 설계이지만, 어느 쪽인지가 코드에서 드러나야 한다. 마지막 Config는 클래스 사전의 기본값을 읽기 전용 원본으로 두고 인스턴스마다 새 사전을 만들어 덮어쓸 값만 얹었다. c1에서 바꾼 값이 c2와 Config.defaults에 퍼지지 않았다.

  • 부모 하나에 모으려면 부모의 리스트에 더하고, 서브클래스마다 따로 두려면 새로 대입한다.
  • 클래스 속성을 기본값의 원본으로만 읽고 인스턴스가 복사본을 만들면 공유 사고가 구조적으로 줄어든다.
  • 의도한 공유에는 typing.ClassVar 주석을 붙여 인스턴스 속성이 아님을 표시한다. typing 문서는 이것이 런타임 동작을 바꾸지 않고 정적 타입 검사기가 쓸 수 있는 표시라고 적는다.

증상에서 원인으로 - 판별 표

위 실행을 증상별로 묶었다. 각 행의 확인 코드는 앞 절의 출력이 사용한 것이다.

증상확인할 것출력이 가리키는 것처방
인스턴스 둘이 같은 리스트를 본다a.x is b.x, 'x' in vars(a)True와 False이면 클래스 속성 하나를 읽는 중__init__에서 self.x = []
+= 뒤 인스턴스 사전에 이름이 생겼는데 여전히 공유p.log is Counter.logTrue이면 같은 리스트를 다시 묶었을 뿐새 리스트를 만들어 대입하거나 __init__으로 이동
일부 인스턴스만 클래스 변경을 따라온다vars(obj)에 그 이름이 있는지있는 인스턴스는 자기 값을 가진 것del obj.name으로 가림 해제
서브클래스 카운터가 부모와 어긋난다'count' in vars(Child)True이면 type(self)로 자식에 새로 썼다클래스 이름 직접 지정 또는 서브클래스별로 의도 통일
dataclass 정의에서 ValueError오류 메시지의 필드 이름list·dict·set 기본값field(default_factory=...)
슬롯 클래스에서 ValueError__slots__와 같은 이름의 클래스 변수슬롯과 클래스 변수 충돌기본값을 __init__에서 대입
의도한 공유를 읽는 사람이 인스턴스 속성으로 오해선언에 주석이 있는지주석이 없으면 의도가 코드에 안 보임ClassVar[...] 주석

표의 첫 열에서 마지막 열로 가는 순서가 점검 절차이다. 먼저 값이 어디에 있는지(vars), 같은 객체인지(is), 어느 연산이 그 자리를 만들었는지(대입·+=·type(self))를 차례로 본다.

확인하지 못한 것

  • Python 3.13.3 이외 버전에서의 동작. dataclass의 가변 기본값 판정이 버전에 따라 달랐는지는 실행으로 비교하지 못했다.
  • 프로퍼티·디스크립터(__get__·__set__)가 클래스 속성으로 놓였을 때의 조회 순서. 위 실행은 일반 값만 다루었다.
  • 메타클래스와 클래스 데코레이터가 속성을 바꾸는 경우.
  • mypy·pyright 같은 정적 타입 검사기가 ClassVar와 일반 클래스 속성을 실제로 어떻게 보고하는지. 문서가 정적 타입 검사기가 쓸 수 있다고만 적은 부분이다.
  • 해시 가능한 가변 객체를 dataclass 기본값으로 둘 때의 동작.
  • 여러 스레드가 클래스 속성의 리스트를 동시에 고칠 때의 안전성.
  • __init_subclass__의 호출 규칙은 공식 문서를 열어 확인하지 않았고 출력으로 보인 동작만 적었다.
