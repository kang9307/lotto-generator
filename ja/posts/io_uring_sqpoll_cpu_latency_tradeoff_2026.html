この記事はgg582がoborona.zipに執筆した「SQPOLLは不安型彼女だ」（2026-09-19）およびLinux man-pagesのio_uring_setup(2)に基づいている。ブログ記事はio_uringの基本モードとSQPOLLをアタッチメント理論の比喩で説明しており、sq_thread_idle、NEED_WAKEUP、カーネルバージョン別の権限などの詳細は扱っていない。それらの詳細はmanページから引用した。両資料が明示していない部分は「この記事の解釈」と明記する。

1. 「不安型彼女」の比喩から読み解くio_uringとSQPOLLの登場背景

io_uringは、ユーザ空間とカーネルがリングバッファを介して入出力をやり取りするLinuxの非同期I/Oインターフェースである。動作モードの一つであるSQPOLL（Submission Queue Polling）は、カーネルスレッドが投入キューをポーリングすることで、システムコールを呼ばずにI/Oを投入できる代わりにCPUを消費する。

最近、GeekNewsで紹介され注目を集めたoborona.zipブログの記事「SQPOLLは不安型彼女だ」（gg582）は、この技術を日常的な比喩で解説した。原典は「I/O Uringとはそもそも何なのか？」「基本モード／割り込み駆動モード」「SQPOLLとは何でなぜ『不安型彼女』と呼ばれるのか？」「少し笑えるまとめ」の全4章で構成されている。著者はio_uringの動作をアタッチメントスタイルに喩えて説明している。

ブログは基本モード（割り込み駆動モード）を「自分の生活がある安定型彼女」に、SQPOLLを「不安型彼女」に喩える。manページによると、SQPOLLフラグを指定すると投入キューのポーリングを行うカーネルスレッドが生成され、アプリケーションはシステムコールなしに入出力を投入・回収できる。ブログはこの状態を「ねえ今どこにいるの、私の心は焦げ付いてるのにどこにいるの？」という口調で表現している。

ブログはIORING_SETUP_SQ_AFFについても触れており、「少しストーカー傾向も生じる」「CPUは焦げ付く」といった表現を用いている。この記事が投げかける問いは、システムコールをなくす代わりにCPUコアを差し出す選択がいつ適切なのかという点である。

2. 基本の割り込み駆動モードとポーリングモードの構造的差異

この章の一般的な説明は本記事による整理であり、原典の根拠は後述のSQPOLLに関する段落にある。一般的に基本モードでは、アプリケーションが要求投入後にio_uring_enter(2)でカーネルに通知し、待機中にCPUを他の処理に充てることができる。

本記事の整理によれば、この方式は待機中に他のプロセスがCPUを利用できるためCPU効率に優れる。ブログのまとめでも「性能よりもCPUを燃やしたくなければ安定型彼女」と記されている。

manページはSQPOLLについて次のように説明している。「When this flag is specified, a kernel thread is created to perform submission queue polling. An io_uring instance configured in this way enables an application to issue I/O without ever context switching into the kernel. … the application can submit and reap I/Os without doing a single system call.」システムコールのコストが具体的にどれほどであるかは、両資料ともに数値を提示していない。

すなわちSQPOLLの核心は、カーネルスレッドが投入キューをポーリングすることで、アプリケーションがシステムコールを介さずに投入および回収を行える点にある。このカーネルスレッドの名称はmanページには記載されていない。

3. 共有リングバッファに基づくSQE投入とCQE回収の仕組み

この章におけるリング構造の説明は一般的なio_uringの構造を本記事がまとめたものであり、両資料の直接の文章ではない。io_uringはユーザ空間とカーネルが共有するリングバッファを活用し、投入キュー（Submission Queue, SQ）と完了キュー（Completion Queue, CQ）が存在する。この構造における要求処理の一般的な流れは以下の通りである。

  • アプリケーションは投入キュー（SQ）の空きスロットに作業明細であるSQE（Submission Queue Entry）を書き込む。
  • SQEを書き込んだ後、SQリングのtailを更新して新たな作業の存在を知らせる。
  • SQPOLLでは、カーネルスレッドが投入キューをポーリングして新たなSQEを処理する（manページ: a kernel thread is created to perform submission queue polling）。
  • 作業が完了すると結果は完了キュー（CQ）のCQE（Completion Queue Entry）として返却され、アプリケーションは完了キューを確認する（manページ: watching for completions on the completion queue）。

本記事の整理によれば、SQPOLLでは投入と回収が共有メモリの操作によって行われるため、システムコールを発行する必要がない。ただしカーネルスレッドが休眠している場合は、次章で述べる起床手順が必要となる。

4. sq_thread_idleと起床ハンドシェイク（NEED_WAKEUP）

manページは、カーネルスレッドのアイドル時間がsq_thread_idleミリ秒を超えた場合、struct io_sq_ringのflagsフィールドにIORING_SQ_NEED_WAKEUPビットを設定すると説明している。本記事の推論では、このようなアイドル処理がなければ、ポーリングスレッドは空のキューを確認し続けてCPUを消費することになる。manページがアイドル時のCPU消費に直接言及しているわけではない。

sq_thread_idleはstruct io_uring_paramsのフィールドであり、単位はミリ秒である。manページにデフォルト値の記載はない。

本記事の推論では、スレッドが休眠するとアプリケーションが後からSQに項目を追加してもスレッド自身は検知できないため、起床手順が必要となる。manページに記載された手順は以下の通りである。

  • カーネルスレッドはアイドル時間がsq_thread_idleミリ秒を超えると、flagsフィールドにIORING_SQ_NEED_WAKEUPを設定する。
  • アプリケーションはtailを更新した後にflagsを読み出す。manページは「Ensure that the wakeup flag is read after the tail pointer has been written」として、flagsの読み出しにload-acquireセマンティクスを用いるよう案内している。
  • NEED_WAKEUPが設定されている場合、io_uring_enter(fd, 0, 0, IORING_ENTER_SQ_WAKEUP)を呼び出す（manページのコード例）。
  • この確認を怠った場合にどうなるかはmanページに記述されていない。本記事の推論では、起床を省略すると投入したI/Oが処理されない可能性がある。

manページは、SQPOLLリングではアプリケーションが直接io_uring_enter(2)を呼ぶことは通常なく、それは概ねliburingのio_uring_submit(3)が処理すると記載している。

生のリファレンスシステムコールを直接扱う場合は、上記の手動確認が必要であるというのが本記事の解釈である。

5. IORING_SETUP_SQ_AFFとCPUコア専有がもたらす負荷の代償

manページによると、IORING_SETUP_SQ_AFFはポーリングスレッドをstruct io_uring_paramsのsq_thread_cpuで指定したCPUに束縛し、IORING_SETUP_SQPOLLと併せて指定した場合にのみ意味を持つ。コンテナ環境でcgroupのcpuset.cpusが変更された場合、束縛されたCPUセットも変更される可能性があるとmanページは記している。

本記事の推論では、ポーリングスレッドを特定のコアに固定すると、そのコアを他のタスクに利用することが困難になる。ブログはこの点を「CPUは焦げ付く」と表現している。

本記事の判断では、要求が疎らなサービスにおいては、ポーリングにコアを費やすコストが利益を上回る可能性がある。両資料ともにこれを数値で示してはいない。

6. Linuxカーネル権限要件の変遷 — CAP_SYS_NICEから非特権解放まで

manページは、カーネルのバージョンによってSQPOLLの利用条件が変化してきたと記している。

  • 5.11より前: アプリケーションはio_uring_register(2)のIORING_REGISTER_FILESで利用するファイル群を登録しなければならず、さもなければ投入されたI/OはEBADFで失敗する。この条件がない動作はIORING_FEAT_SQPOLL_NONFIXED機能フラグで確認できる。
  • 5.11: ファイル登録が不要となり、CAP_SYS_NICE機能を持つユーザはrootでなくてもSQPOLLを利用できる。
  • 5.13以降: この要件も緩和され、新しいカーネルでは特別な特権を必要としない。manページは5.13より古い一部の安定（stable）カーネルも非特権SQPOLLをサポートする場合があると記している。

本記事の解釈としては、権限の敷居が下がった分、導入の是非はワークロードに合わせて慎重に判断する責任が利用者にある。実際の採用事例や普及状況は両資料では扱われていない。

基本モードとSQPOLLモードの主要な特性を整理した比較は以下の通りである。

8. アーキテクチャ視点の選定基準 — 価値を発揮する領域と不適合な環境

この章は両資料の推奨ではなく本記事の解釈である。ブログのまとめは「性能よりもCPUを燃やしたくなければ安定型彼女、何が何でも性能なら不安型彼女」である。これはCPU効率を優先するなら基本モードを、性能が最優先ならSQPOLLを検討するという意味として解釈できる。

本記事の推測では、遅延時間が極めて重要であり入出力が途切れないワークロードにおいて、ポーリング用コアのコストが正当化される可能性がある。特定の業界や数値は両資料には存在しない。

逆に以下の場合には、SQPOLLが適さない可能性がある（すべて本記事の推測である）。

  • 要求間のアイドル時間が長いサービス: ポーリングがCPUを消費し、スレッドが休眠すると起床手順が必要となって利点が減少する可能性がある。
  • コア数が少ない環境: 割り当てられたvCPUが少ない場合、ポーリングスレッドがコアを占有し、他のスレッドが利用できるCPUが減少する可能性がある。manページはコンテナでcpuset.cpusが変わると束縛されたCPUセットも変わると記している。
  • CPU使用率がコストに直結する環境: ポーリングスレッドのCPU使用が課金や自動スケーリングの指標に影響を与える可能性がある。両資料はクラウド費用を扱っていない。
  • 電力消費に敏感な機器: 継続的なポーリングは消費電力を増加させる可能性がある。manページは電力を扱っていない。

9. 自身のワークロードで最適なモードを直接検証する方法

以下の手順は両資料にあるものではなく本記事の提案である。ブログにはベンチマーク数値がないため、自身の環境で直接測定を行う必要がある。

  • ステップ1: ベースラインの割り込み駆動モードプロファイリング — 基本モードでCPU使用率とI/Oスループットを記録してみることができる。
  • ステップ2: SQPOLLの適用とsq_thread_idleの調整 — IORING_SETUP_SQPOLLを適用した上でsq_thread_idleを調整し、NEED_WAKEUPの発生頻度を観察してみることができる。
  • ステップ3: システムコール発行頻度の追跡 — io_uring_enter(2)システムコールの呼び出し回数が減少しているかを確認してみることができる。
  • ステップ4: 遅延時間とコアへの影響の評価 — IORING_SETUP_SQ_AFFでコアを固定した際、遅延時間や他のタスクへ与える影響を比較評価してみることができる。

10. 確認できなかった事項

この記事はブログ記事とio_uring_setup(2)の2箇所のみを参照した。確認できなかった事項は以下の通りである。

  • 元記事のブログ（oborona.zip/post/sqpoll）は定性的な比喩と構造的概念のみを扱っており、SQPOLLモードと通常モードの間のIOPS、マイクロ秒単位の遅延時間、CPU占有率などの定量的なベンチマークデータを一切提示していないため、元記事の数値を確認できなかった。
  • Linux公式マニュアルのio_uring_setup(2)には、利用者がsq_thread_idleフィールドを明示的に指定しなかった場合にカーネル内部で適用される具体的な待機時間（ミリ秒単位の初期値）が記載されておらず確認できなかった。
  • manページには5.13より古い一部の安定版カーネルも非特権SQPOLLをサポートする場合があると記載されているが、具体的な一覧は記載されておらず確認できなかった。ポーリングカーネルスレッドの名称もmanページには記載されていない。
  • ネットワークソケットI/OとブロックストレージI/Oの間におけるsq_thread_idleパラメータの差異や、電力消費量との定量的相関関係は両資料の対象範囲外であり確認できなかった。
