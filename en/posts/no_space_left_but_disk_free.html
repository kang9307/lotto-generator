No space left on device While the Disk Is Not Full - Inodes and Open Files

One symptom, four causes - how to separate those four in the right order

September 1, 2026 Dev & Infra

An alert says the service cannot write its log, so you log in to the server. Out of habit you type df -h. More than thirty percent is free. And yet a single touch in that same shell comes back with No space left on device. There is one reason most of the time gets wasted at this moment: you think df is lying.

df does not lie. It simply does not answer what it was not asked. Ask about capacity and it answers about capacity; ask about the root and it answers about the root. If the real reason the write failed is not capacity, or not the root, then df's answer stays perfectly accurate and perfectly useless. This piece pulls apart the four places where that mismatch is created, and sets out the order that gets you finished fastest.

One symptom, four causes

ENOSPC is one signal, the kernel telling an application that it cannot accept this write. One signal does not mean one situation. In human terms it is like a fever: the fever itself is not a diagnosis, it is a sign that diagnosis should begin. In practice, though, people often jump straight from ENOSPC to finding things to delete, and when the cause is not capacity, all of that work is wasted.

There are four places to separate. The right-hand column of the table below, the distinguishing signal, is the substance of this article. Memorise the two left columns only and you will still get the order wrong.

CauseWhat is actually fullCommand to checkDistinguishing signal
① inode exhaustionThe file count limitdf -iUse% is low but only IUse% is 100%
② deleted but openBlocks that were never returnedlsof +L1 · /proc/<pid>/fddf is full, the du total is far smaller
③ reserved blocksThe share set aside for root onlytune2fs -lOrdinary accounts fail, root succeeds
④ a different mountA filesystem you never looked atdf -h <path>Root has room, only that path is at 100%
  • ① and ④ each take a single line to check. That is why putting them at the front saves the most time
  • ② only shows itself when you look at df and du together. Look at one alone and you will never see it
  • ③ is rare, but it creates the strange situation where two people on the same server get different results, and that eats hours

Ask this first - is it really that filesystem

In order of execution this comes first. It is number ④ on the cause list, but it is the cheapest thing to check. Type df -h with no argument and you get a list of mounts, and the human eye usually stops at the root line on top. If the path that failed sits on a different filesystem, its line is somewhere further down the screen.

The fix is to hand the path to df directly. Even this environment reports the same physical disk as two different mounts.

$ df -h . /
Filesystem                        Size  Used Avail Use% Mounted on
C:/Users/<user>/<temp>  931G  600G  332G  65% /tmp
C:/Program Files/Git                931G  600G  332G  65% /

# The point - the current directory is attached to /tmp, not to /.
# It is the same on Linux. Give the failing path to df directly.
$ df -h /var/log

On Linux servers the places where this trap is sprung most often are well known. The list below is the typical layout in which a write fails even though the root has room.

  • Layouts where /var is a separate partition - logs and package caches pile up here, so it fills long before the root does
  • /boot - usually sized in the hundreds of megabytes, so a few kernel packages are enough to fill it. The symptom appears as a failed kernel update, which does not look like a disk problem
  • Layouts where /tmp is tmpfs - it uses memory, so it fills independently of the real disk. Reboot and it disappears, taking the evidence with it
  • Inside a container - the writable layer and a mounted volume are different filesystems. The write fails when the layer fills, even if the volume has room
  • Paths where a bind mount or NFS overlaps - the path string looks like the same tree, but the device is different

Cause ① inode exhaustion - space left, count used up

A filesystem does not only store data; it separately manages a metadata entry for every single file. The structure holding the owner, the permissions, the timestamps and the location of the actual data blocks is the inode. The file name is not in there. Names are held by directories, and a directory is a list pairing names with inode numbers. Because of this structure several names can point at one inode, and that is a hard link.

What matters is that the number of these entries can have a limit. Once the limit is reached, no new file can be created no matter how many blocks remain. Checking it is one line, df -i. And in this environment that command answers like this.

$ df -i .
Filesystem                       Inodes IUsed IFree IUse% Mounted on
C:/Users/<user>/<temp>    -     -     -     - /tmp

$ stat -f .
  File: "."
    ID: ea1df1ef00000000 Namelen: 255     Type: UNKNOWN
Block size: 4096       Fundamental block size: 4096
Blocks: Total: 244041727  Free: 86972107   Available: 86972107
Inodes: Total: 18446744073709551615 Free: -1

Everything is -. And stat -f shows why. The 18,446,744,073,709,551,615 reported as the inode total is the maximum value of an unsigned 64-bit integer, that is, a sentinel meaning there is no limit, and Free is -1. NTFS has no fixed inode table like ext4, so there is no number to report in the first place.

Those blanks are not a failure; they are a screen showing the most important fact directly. An inode limit is not a universal property of filesystems but a design choice that differs per implementation. That is why a response that works on an ext4 server does not carry over to an XFS server. Here is what the screen looks like on Linux with real numbers filled in, and what to type next.

# ① which mount has run out of inodes
df -i

# ② directories where files are concentrated inside that mount (coarse first pass)
du --inodes -x -d 2 /var 2>/dev/null | sort -n | tail -20

# ③ counting files per directory directly (older environments without du --inodes)
find /var -xdev -type f -printf '%h\n' 2>/dev/null \
  | sort | uniq -c | sort -rn | head -20

# The three lines above could not be run in this environment.
# NTFS does not report an inode count, so ① comes back blank.

The places where small files pile up by the million are fairly predictable. Below are the typical spots where the capacity graph shows nothing at all while inodes quietly fill up.

  • Session files - without expiry cleanup you get one file per visitor, each a few hundred bytes
  • Mail queues and Maildir - one message is one file. When delivery is blocked, the queue stays behind as raw file count
  • Cache shards - caches that split a hash into directories swell twice over, because directories consume inodes too
  • Log fragments - a short rotation interval with a large retention count leaves compressed copies lying around. Each is small, but the count is what decides the outcome
  • Dependency directories - a package tree created once per build environment grows to hundreds of thousands of files

When inodes are decided - ext4 · XFS · btrfs

This is where they diverge. The mke2fs documentation is blunt about the -i option, the number of bytes assigned per inode: this ratio cannot be changed after the filesystem is created, so choose the value carefully. The same document also states that the default reserved block percentage is five percent.

That one sentence carries weight in practice. Once inodes are full on ext4, there is no option to increase them. You either reduce the file count or move the data and rebuild the filesystem. That is a fact you do not want to learn in the middle of an incident, so it is better decided while designing the storage.

FilesystemHow inodes are assignedCan it be increased laterWhat that means in practice
ext4Count fixed at mkfs time. Set by -i ratio or -N countNo. The documentation explicitly says it cannot be changedIf you know there will be many small files, lower the ratio when creating it
XFSDynamic allocation. Only the ceiling is managed, via maxpctYes. Change the ceiling with xfs_growfs -mEven after exhaustion there is room to raise the ceiling and buy time
btrfsThe kernel documentation lists dynamic inode allocation among its featuresThe very notion of a fixed limit is differentDo not read the numbers from df -i with ext4 meanings
  • The default for XFS maxpct varies with filesystem size. Per the documentation it is 25 percent below 1TB, 5 percent below 50TB and 1 percent above that
  • Setting maxpct to 0 can effectively let the whole filesystem become inode blocks, the documentation says. That releases the ceiling, and it also removes the mechanism protecting data space
  • So IUse% from df -i is a number you cannot read without knowing the filesystem type. The same 90 percent is an alarm on ext4 and material for deciding whether to raise the ceiling on XFS

Cause ② deleted but still open

rm is not a command that erases data. It is unlink, which removes one name from a directory. Even when every name is gone and the link count reaches zero, the kernel does not return the blocks as long as one process still has that file open. The space comes back only at the moment the last reference is closed.

This behaviour is not a defect but a safeguard defined by POSIX. It prevents a process from breaking because a file vanished while it was being read. The problem is that at this point the observation tools give different answers. df reads the filesystem's block accounting, so it counts the held space as in use. du walks directories and counts files, so a file with no name is invisible to it. Hence the disagreement.

It reproduced exactly in this environment. A 1GiB file was created, held with tail -f, deleted, and the free block count was read at each step. Below is the actual output.

$ cd /tmp/demo
$ free() { stat -f -c %f .; }          # free block count (1 block = 4096 bytes)

STEP 0  empty directory      free blocks: 86970141
$ head -c 1073741824 /dev/zero > big.log
STEP 1  1GiB created         free blocks: 86707994   du -sh: 1.0G
$ ( tail -f big.log > /dev/null & )
STEP 2  tail holds it open
$ rm big.log
STEP 3  right after rm       free blocks: 86708010   du -sh: 1.0K
STEP 3b 2 seconds later      free blocks: 86708010
$ kill <pid of tail>
STEP 4  after the process exits  free blocks: 86970153

Read the numbers as they are. Creating the file consumed 262,147 blocks. Multiply by 4,096 bytes and you get roughly 1.0GiB, which matches what was created. Yet right after rm, only 16 blocks came back. Deleting 1GiB returned 64KiB, which is effectively zero. Meanwhile du at the same moment already answers 1.0K. This is where the 1GiB gap between df and du gets created.

And when the process was killed, 262,143 blocks came back all at once. What deleted the file was rm, but what returned the space was kill. These two lines are the evidence behind the claim that the fix is not to delete the file again but to make the holder let go.

Finding the culprit is a separate problem. The standard tool is lsof +L1, and the documentation explains that this form selects files that are open while their name has been deleted. lsof is not installed in this environment, however, so it could not be run. The /proc side worked as expected, and the (deleted) marker the kernel attaches came out clearly.

# What was run in this environment - checking via /proc
$ ls -l /proc/<pid>/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/big.log (deleted)

# What could not be run in this environment - lsof is not installed
$ sudo lsof +L1                  # only open files with a link count below 1
$ sudo lsof -nP +L1 /var         # narrowing to a specific mount
Caution - when a process cannot be restarted, truncating the file descriptor with > /proc/<pid>/fd/<n> is a widely known trick. The space returns immediately, but pick the wrong number and another file that process has open is emptied entirely. It cannot be undone and there is no confirmation step. If a restart is possible, a restart is always the safer side.
  • What creates this situation most often is a mistake in log rotation settings. If the process is not signalled to reopen after the file is moved or deleted, it keeps writing to the old, nameless file.This is where log rotation fails silently
  • Pinning down the holding process is outside this article. Here we go only as far as why the space does not come back
  • A disk usage graph that does not step down is a good sign of this cause. If you ran a cleanup and the graph stays flat, what you deleted is still open
  • The restart target is usually whatever writes logs. The application that writes logs to a file and the collector that reads and ships them can both be holding the same file

Cause ③ reserved blocks - room only root can see

The ext family sets aside a portion of the total blocks for privileged processes only. The tune2fs documentation gives two reasons for it: to avoid filesystem fragmentation, and to allow system daemons to keep functioning correctly after non-privileged processes are prevented from writing. The default is five percent.

So this scene gets created. Writing fails under the application account, but log in as the administrator and creating a file in the same place succeeds. This is where two people looking at the same server reach different conclusions. If writes fail while df Use% sits around 95 percent instead of 100, this cause is worth suspecting.

# Checking reserved blocks (ext2/3/4) - could not be run in this environment
$ sudo tune2fs -l /dev/sda1 | grep -iE 'block count|reserved'
# Block count:              total number of blocks
# Reserved block count:     number of reserved blocks
# The ratio between the two is the reserved percentage.

# Adjusting the ratio - reversible, but do it carefully
$ sudo tune2fs -m 1 /dev/sda1    # 5% -> 1%
Caution - the advice to remove the reservation entirely with tune2fs -m 0 appears often, but both purposes stated in the documentation disappear with it. As free space approaches zero, contiguous blocks become impossible to find and fragmentation accelerates sharply, and the daemons that write logs stop along with everything else, costing you the means to record why the incident happened. Specify it wrongly on a mounted filesystem and it stays applied until you reverse it.
  • The reserved ratio is a percentage. So the absolute amount set aside grows as the disk grows. On a multi-terabyte volume, five percent is a considerable amount
  • On data-only volumes, that is, volumes where no system daemon writes logs, there is a case for lowering the ratio. But leave one to two percent rather than zero
  • Conversely, on / and /var it is better to leave the default alone. These are exactly the places where the daemons have to keep running, as the documentation puts it
  • XFS has no concept by the same name and manages free space differently. Do not carry ext-family habits over to it

Why small files eat more space

A filesystem does not hand out space by the byte; it hands it out in blocks. A one-byte file receives a whole block. The remainder cannot be used by another file, and this waste is called internal fragmentation. Described in words it sounds trivial, but the character of it changes the moment it is multiplied by a count.

I measured it. du with --apparent-size reports the logical size, while the default behaviour reports the actual allocation. Put the two side by side and the difference is plain.

$ du -b --apparent-size one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1        one_byte.txt
100      b100.bin
4096     b4096.bin
4097     b4097.bin
1048576  b1m.bin

$ du --block-size=1 one_byte.txt b100.bin b4096.bin b4097.bin b1m.bin
1024     one_byte.txt
1024     b100.bin
4096     b4096.bin
8192     b4097.bin
1048576  b1m.bin

The line to look at is b4097.bin. A logical size of 4,097 bytes with an actual allocation of 8,192 bytes. Crossing a block boundary by one byte pulls in another full 4,096 bytes. The 4,096-byte file, meanwhile, uses exactly 4,096.

Logical sizeActual allocation (measured)WasteMultiple
1 B1,024 B1,023 B1,024x
100 B1,024 B924 Babout 10x
4,096 B4,096 B01x
4,097 B8,192 B4,095 Babout 2x
1,048,576 B1,048,576 B01x

One thing has to be stated honestly here. The one-byte file was allocated 1,024 rather than 4,096 because NTFS stores very small files inside the metadata record itself. ext4 does not use this optimisation by default, so the same experiment would be expected to give 4,096 there, but that screen is not in this article. The doubling at the block boundary in b4097.bin, by contrast, is common to any filesystem that allocates in blocks.

I also measured what happens when you multiply by count. Twenty thousand one-byte files.

$ time ( for i in $(seq 1 20000); do printf 'x' > "f$i"; done )
real    0m25.766s

$ ls -1 | wc -l
20000

$ du -sb --apparent-size .
20000     .          # logical total = 20,000 bytes (about 20KB)

$ du -s --block-size=1 .
24674304  .          # actual footprint = 24,674,304 bytes (about 23.5MiB)

A logical 20KB occupies 23.5MiB in reality. About 1,233 times. That figure includes both the allocation of the files themselves and the directory structure that grew to hold twenty thousand names. The fact that directories use space too becomes visible right here.

  • Do the same thing on ext4 with 4KiB blocks and the arithmetic goes like this. A million one-byte files are a logical 1MB and an actual 4,096,000,000 bytes, roughly 3.8GiB. That value is a calculation from the block size, not a measurement, and it excludes the directory structure
  • So in places with many files, capacity and inodes drain at the same time. Which one hits bottom first depends on the file size distribution
  • Bundling small files into one is the fundamental response. Compress logs after rotation, put expiry on caches, and keep archives as bundles rather than individual files

Finding what ate it - the du idiom

Once the mount is identified and it is confirmed that this really is a capacity problem, the next job is narrowing down from the top. One idiom is enough.

$ du -h -x --max-depth=1 . | sort -h
1.0K    ./deleted_open
1.0K    ./demo2
24M     ./tiny
25M     .

# The big items come last, so read from the bottom line up.
# On Linux you usually start like this.
$ sudo du -h -x --max-depth=1 / | sort -h

Each of the three options does a job. --max-depth=1 shows only one level. Without a depth you get tens of thousands of lines, which is unreadable. sort -h orders human-readable notation such as 24M by size. Under string sorting, 9K comes after 24M.

And -x is the heart of this idiom. It is the option that stops it from crossing into another filesystem. Leave it out while sweeping from / and it will follow mounted network storage and container layers, taking several times as long and mixing numbers unrelated to the filesystem you are investigating into the result.

Here too something has to be recorded honestly. In this environment I could not produce a scene where -x actually stopped anything.

$ stat -c %d / /tmp .
3927831023
3927831023
3927831023
# All three have the same device ID -> there is no boundary for -x to stop at.
# All that was confirmed is that the option is accepted and the result is the same.

# The file-count version (when inodes are exhausted)
$ find . -xdev -type f -printf '%h\n' | sort | uniq -c | sort -rn | head -5
  20000 ./tiny
      5 .
      1 ./demo2
      1 ./deleted_open
  • sort -h is a GNU extension. Its help text in this environment confirms it exists as -h, --human-numeric-sort, but it may be absent on BSD systems or in minimal container images. There, extract with du -k and use sort -n
  • du --inodes counts entries rather than size. When inodes are exhausted, drop -h from the idiom above and swap in this option and it works unchanged
  • find walks files one by one, so it takes a long time on filesystems with many files. On a production server, allow for the load and start with a narrow scope
  • If the result does not match the total, suspect cause ②. If no amount of adding with du reaches the usage reported by df, a nameless file is open somewhere

The diagnostic order - four steps

Folding all of the above into an order of execution gives four steps. Each step exists to decide whether to go on to the next one. The reason for keeping the order is that the earlier steps are overwhelmingly cheaper than the later ones.

StepWhat it asksCommandIf it comes out like thisNext
1Which mount is itdf -h <failing path>Use% on that line is lowYou were looking at the wrong path. Recheck the failing path
2Capacity or inodesdf -i <failing path>Only IUse% is 100%Cause ①. Find the directories where files are concentrated
3Does du disagreeCompare du -sh -x <mount> against dfThe du total is far smallerCause ②. Find the holding process and restart it
4What ate itdu -h -x --max-depth=1 | sort -hA large item is identifiedDescend one level at a time and repeat
+Does it only work as roottouch as an ordinary account and as rootOnly root succeedsCause ③. Check the reserved blocks
  • Steps 1 and 2 are two lines together and impose essentially no load. And a fair number of cases really do end with just those two
  • Skip step 3 and you will burn all your time on step 4 and still find nothing. Knowing that a situation exists in which du cannot find the culprit is the point of this table

What changes in containers and the cloud

The same symptom is more confusing inside a container. df inside a container answers about the mounts that container can see, while what actually filled up is often the host node's disk. The reverse also happens: the node has plenty of room and only the limit on the container's writable layer is full. You have to settle where you ran df first.

SituationEasy thing to get wrongWhere to actually look
The image layer is fullThe volume has room, so it is fineThe writable layer is a different filesystem from the volume
Stopped containers and old images have piled upCount only the running ones and it is not muchAdd up stopped containers, unused images and the build cache together
Container logs grow without boundThe application does not write logsThe runtime writes standard output to a file. Check the size limit setting
The cloud disk was enlarged but nothing changedIt was enlarged in the console, so that is doneThe partition and the filesystem have to be grown separately
The node has run out of inodesThe capacity graph is flat, so there is no problemImage layers are masses of small files. Monitor inodes separately

The last row catches people especially often. The resize2fs documentation states plainly that this program does not manipulate the size of partitions. In other words, if you enlarged the block device, expand the partition first and then expand the filesystem. Mistake those two steps for one and you get a state where the console shows more capacity while the server sees none of it.

# After expanding a cloud disk - there is an order (could not be run in this environment)
# ① has the kernel seen the new size
lsblk

# ② expand the partition (only in layouts that use partitions)
sudo growpart /dev/sda 1

# ③ expand the filesystem
sudo resize2fs /dev/sda1        # ext2/3/4
sudo xfs_growfs /               # XFS takes the mount point

# Container side - totals by category of what is taking up room
docker system df
docker system df -v
  • Overlay schemes modify a file by copying the original up to the upper layer first. Changing one line of a large file can require as much extra space as the file's size
  • A file deleted inside a container does not disappear from the lower layer. Only a deletion marker is laid on top, so the image size does not shrink
  • Cleanup commands are as dangerous as they are convenient. There are options that also delete unused volumes, and those volumes may contain data
  • When a whole node fills up, the scheduler pushes pods off to other nodes. The symptom surfaces as restarts rather than disk, so the cause is identified late

In a hurry - what is safe to delete and what is not

When the service is down there is no time to deliberate. That is why a list decided in advance is needed. But the first move is not deleting. The first move is checking whether space is being held. If it is cause ②, nothing you delete is reclaimed, so starting to delete without checking only loses time and leaves irreversible deletions behind.

ClassTargetWhy
Relatively safeOld logs compressed after rotationAlready closed files. You only need to check the retention period
Relatively safePackage manager cachesThey can be downloaded again. It only costs reinstall time
Relatively safeBuild output and temporary directoriesRegenerable. But check that no build is in progress
CautionCore dumpsDeletable, but they are material for incident analysis. Move them first
NeverA log file that is currently openThe space does not come back and the log is lost. It creates cause ②
NeverDatabase files, lock files, socketsIt leads to corruption or a service that will not start
NeverDirectories whose contents you do not knowThe more urgent it is, the more people delete without checking. It cannot be undone
Caution - rm -rf asks for no confirmation and cannot be undone. Build the path out of a variable and you get the accident where an empty variable deletes from the top down. Running ls -d with the same argument first, to see the targets with your own eyes, is a cheap habit. truncate -s 0 empties a file while leaving it in place, so it works on an open log, but the contents are gone all the same. If there is anything worth keeping, move it first.
  • When free space is truly zero, the act of deleting can itself fail. Tools that write a log or create a temporary file will not work at that point
  • That is why emptying without creating a new file, as with truncate -s 0 or : > file, is useful in this situation
  • Once the fire is out, always go back over the cause. Having fixed it by deleting does not explain why it filled up. The same thing returns on the same cycle

Preventing it in the first place

This symptom often arises because one monitoring item is missing. Capacity is watched almost everywhere, but inode usage is commonly absent from the default dashboard. So the incident happens while the capacity graph stays flat.

I built a snippet that pulls out only the mounts over a threshold and ran it, and this is where a common idiom actually turned out to be wrong. It is a failure worth recording, so here it is as it happened.

# The common version - it gave a wrong answer in this environment
$ df -P | awk 'NR>1 && $5+0 >= 80 {print $6, $5}'
65% 347611880          # the values came out reversed

# Why - the device name contains a space, so the fields shifted by one
$ df -P | awk 'NR>1 {print "NF=" NF "  $5=[" $5 "]  $6=[" $6 "]"}'
NF=7  $5=[347583704]  $6=[65%]

# The fixed version - do not count fields, name them
$ df --output=pcent,target | awk 'NR>1 && $1+0 >= 60 {print "DISK", $2, $1}'
DISK / 65%

$ df --output=ipcent,target | awk 'NR>1 && $1+0 >= 60 {print "INODE", $2, $1}'
(no output - this filesystem does not report an inode percentage)

Cutting df -P output by field number rests on the assumption that no device name or mount point contains a space. Break that assumption and it silently reads a different column, the condition still evaluates true, and a wrong alert goes out looking perfectly normal. Take only the columns you need with df --output= and the assumption is no longer needed at all.

  • Add inode usage to the monitoring items. The same threshold as capacity is enough. This is not merely better than nothing: cause ① in this article is prevented entirely by this one item
  • For log rotation, decide the retention count and the compression setting together. Set only the count high and capacity is fine while inodes fill
  • Put expiry cleanup on temporary files. Sessions and caches need the code that deletes them as much as the code that creates them
  • For container logs, specify a file size limit and a retention count. Layouts where the default is unlimited are common
  • Alerts are better read as time remaining rather than percent remaining. Knowing that it grows by a few GB a day lets you calculate when it will fill

Wrap-up

No space left on device is not a diagnosis but the start of one. Behind it lie at least four situations, and what you should do is the exact opposite depending on which one it is. If inodes are full, hunting for large files is useless; if deleted-but-open files are the cause, deleting more does harm.

So what to memorise is not a list of commands but an order. Hand the failing path to df directly, split capacity from count with df -i, reconcile the du total against df, and only then go looking for what ate it. The third step is what this order is worth. If the gap shows up there, you know in advance that all remaining searching would be wasted.

And the two numbers actually measured in this article are worth remembering. A deleted 1GiB returned only 16 blocks until the process was killed, and twenty thousand one-byte files occupied 23.5MiB. Neither number is ever visible to the habit of looking at df once.

What I could not verify

  • I could not produce a screen with inodes actually exhausted. The NTFS in this environment does not report an inode count, so df -i comes back all -. There is no output with IUse% at 100 percent in this article; instead stat -f was used to show why the blanks appear
  • I could not run lsof +L1. lsof is not installed in this environment. The meaning of the option was confirmed in the documentation, and the /proc/<pid>/fd route for the same purpose was actually run, down to confirming the (deleted) marker
  • tune2fs, debugfs, resize2fs and xfs_growfs could not be run. They are ext4/XFS-only tools and there is no such filesystem in this environment. The five percent reserved block ratio, the XFS maxpct defaults and the fact that resize2fs does not touch partitions were confirmed in the official man pages
  • I could not directly measure the allocation of a one-byte file on ext4. It came out as 1,024 bytes in this environment, which is due to how NTFS stores small files. The figure calculated for 4KiB blocks is labelled as a calculation in the body
  • I could not produce a scene where du -x stops at a filesystem boundary. /, /tmp and the working directory all had the same device ID, so there was no boundary to cross. All that was confirmed is that the option is accepted
  • The shape of df -i output on btrfs could not be verified. All that was confirmed is that the kernel documentation lists dynamic inode allocation among its features, and how to read those numbers is not covered here
  • The container and cloud sections were not run at all. Overlay behaviour, the output of cleanup commands, the disk expansion procedure - none of it was run in this environment. Only the order of the commands and the reasoning behind them are written down
