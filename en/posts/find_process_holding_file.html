Finding the Process Holding a File - When Deleting It Frees Nothing

rm removes a name. The order in which you pin down whatever is still holding on, on Linux and on Windows

2026-09-02 Dev & Infra

The sequence is almost always the same. An alert says the disk is full. You find a large log and remove it with rm. It no longer appears in ls. And yet df has not moved by a single digit. You wait a few minutes and it is still the same. So you go looking for more things to delete.

The direction is already wrong at that point. The problem is not that there is too little left to delete, it is that what you already deleted is still alive. This article covers only one thing: the procedure for identifying who is holding it. The four-way classification of why the symptom appears at all lives in No space left on device While the Disk Is Not Full, and this piece picks up one branch of it.

Two of the operations below, killing a process and truncating a file descriptor, cannot be undone. Each carries its own warning box in the relevant section, so on production hardware it is worth reading that paragraph before touching anything. Not mixing read-only commands with state-changing ones is very nearly the whole discipline of this task.

There are two counters - names and references

The whole phenomenon follows from one sentence. rm is not a command that deletes data. The system call it invokes is unlink, and that operation detaches one name written in a directory. The data lives in the inode, not in the name, and the inode does not vanish just because a name did.

The POSIX specification nails this down with no room for misreading: the link is removed before unlink returns, but the removal of the file contents is postponed until all references to the file are closed. So a single file carries two counters of different character, and blocks come back only when both hit zero.

CounterWhat it countsWhat drives it to zeroWhere you see it
Link countDirectory entries pointing at this inoderm · unlink · overwrite by mvstat -c %h · second column of ls -l
Open referencesDescriptors and mappings holding this inodeProcess exit · close() · log reopen signallsof · fuser · /proc/<pid>/fd
Condition for releaseThe moment both reach zeroThe kernel, all at once, at the last closedf free space jumps like a step
What the tools can seedu walks names, df counts blocksWith no name left, du cannot see itThe gap between them is the held capacity

This behaviour is a safety mechanism rather than a defect. It would be intolerable for a reader to break simply because another process removed the file mid-read. The trouble is that the safety mechanism fires silently in production. No error is raised, nothing is logged, and space merely fails to return.

The symptom - df and du disagree

Diagnosis starts from two tools giving different answers. du walks directories and counts files that have names. A file whose name is gone is outside its field of view. df reads the block accounting of the filesystem, so it still counts the held space as used. They diverge, and the width of the divergence is the held capacity.

Here a 200MiB file was created, held open by tail -f, deleted, and df -h printed verbatim at each stage.

--- before rm ---
du -sh . = 200M
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- after rm ---
du -sh . = 0
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- after killing the holder ---
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  600G  332G  65% /tmp

Read the three blocks side by side and the order is unmistakable. rm changed only du, from 200M to 0, while df did not move by a single digit. The shift in df from 601G/331G to 600G/332G came after the process was killed. What returned the space was not rm but kill.

  • In the field this symptom usually shows up first as a graph. If a cleanup ran and the disk usage line stayed flat instead of stepping down, this cause is likely
  • Comparing a du -sh / total against the Used column of df is the cheapest first test. A large gap means unnamed files exist
  • The two values are never identical to begin with. Reserved blocks, journals and directories hidden under mounts make a few percent normal. The signal is a gap measured in tens of gibibytes
  • One trap deserves naming. Running du as a non-root account silently skips directories it cannot read. A gap produced that way has nothing to do with this phenomenon

The name goes, the inode stays

If the previous section was the symptom, this one is the mechanism seen directly. A 512MiB file was created, held open by tail -f, deleted, and then the same inode was inspected again through the file descriptor.

[1] right after creation
    name=app.log inode=4503599629412470 links=1 size=536870912 blocks=524288
    free=86810586   du -sh . = 512M

[2] tail -f (pid=1442) holds it open

[3] right after rm - the name is gone
    ls -A: []
    du -sh . = 0    free=86811452

[4] but through the fd the inode is still alive
    /proc/1442/fd/3  inode=4503599629412470 links=0 size=536870912 blocks=524288
    readlink        /tmp/demo/app.log (deleted)

[5] the held fd still reads
    $ head -c 16 /proc/1442/fd/3 | od -An -tx1
      00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

[6] after kill: free=86939254

Read it in this order. The inode number is the same in [1] and [4]. It is the same object after deletion. The only thing that changed is links, from 1 to 0. Meanwhile size and blocks are still 536870912 and 524288. The name is gone and not one byte of data has been returned.

The free-block figures say the same thing. Across the rm they moved from 86810586 to 86811452, a shift of 866 blocks. Multiplied by 4,096 that is about 3.4MiB, which is noise from other work on the same machine. 512MiB is 131,072 blocks and none of it came back. Then after kill, from 86811452 to 86939254, 127,802 blocks arrived at once.

  • links=0 together with a large size is the fingerprint of this situation. No other state produces that combination
  • The (deleted) tail the kernel attaches is a marker, not part of the path string. Hand that string to cat and you get a missing file
  • As [5] shows, the holder keeps reading and writing without any trouble. That is why the application never reports this as an error
  • The all-at-once nature of the recovery is worth remembering too. Nothing trickles back and stalls; the entire amount arrives at the instant the last reference closes

Route 1 - sweeping /proc by hand

Production machines without lsof are more common than you would think. On minimal images, inside containers, and on air-gapped servers, adding a tool is itself a process. And you do not need one, because the kernel is already exposing the answer. Each process has a /proc/<pid>/fd directory of symlinks pointing at the files it has open, and when a target has been deleted, (deleted) is appended to the destination.

# looking at one process
$ ls -l /proc/1442/fd | grep -i deleted
lrwx------ 3 -> /tmp/demo/app.log (deleted)

# sweeping everything, with nothing but the shell
$ for p in /proc/[0-9]*; do
    pid=${p##*/}
    for fd in "$p"/fd/*; do
      tgt=$(readlink "$fd" 2>/dev/null) || continue
      case "$tgt" in *"(deleted)") echo "pid=$pid fd=${fd##*/} -> $tgt";; esac
    done
  done

pid=318  fd=3  -> /tmp/demo/app.log (deleted)
pid=319  fd=3  -> /tmp/demo/app.log (deleted)

# to see the held size as well
$ stat -L -c '%i %h %s %n' /proc/318/fd/3
16607023627971255 0 268435456 /proc/318/fd/3

The value of this approach is not merely that nothing has to be installed. Adding stat -L gives you the held capacity right there, so when several candidates appear you can order them by size and know which one actually returns space when handled. Its limits are equally clear.

  • Processes belonging to other users are invisible without privilege. The sweep above skips those lines silently, so an empty result is not proof of absence. Run it under sudo where you can
  • Looking only at fd misses memory mappings. A file that was mmaped and then had its descriptor closed remains referenced through the mapping, and that lives in /proc/<pid>/maps
  • If a process disappears mid-sweep, readlink fails. That is why the idiom above tolerates failures, and it is also why running the same command twice can give different results
  • With thousands of processes the sweep itself takes time. Under pressure, narrow the field first. The most common pairing is the application writing the log and the collector reading it for shipment, both holding the same file

Route 2 - lsof, the commands and how to read them

The standard tool is lsof. It is not installed in this environment, so I never ran it. There is therefore no sample output below. What follows is the behaviour the manual specifies and which columns to read.

# only files that are deleted yet open - the exact query for this situation
$ sudo lsof +L1

# narrowing to a mount (a full scan is slow)
$ sudo lsof -nP +L1 /var

# who has this specific path open
$ sudo lsof /var/log/app.log

# what does this specific process have open
$ sudo lsof -p 1234

# an entire directory tree, recursive (can be very slow)
$ sudo lsof +D /var/log

The key option is +L1. The manual says that when +L is followed by a number, only files having a link count less than that number will be listed. So +L1 selects exactly the files with a link count of zero, which is to say files whose every name is gone but which are still open. And specifying +L adds an NLINK column to the output.

  • The default columns are COMMAND, PID, USER, FD, TYPE, DEVICE, SIZE/OFF, NODE and NAME. Reading just PID, SIZE/OFF and NAME gets you there most of the time
  • Because +L inserts NLINK, the column positions shift. Positional handling such as awk '{print $2}' breaks the moment options change. If you automate this, re-check column positions per option set
  • The FD column carries values other than numbers, among them cwd, txt and mem. mem means a memory mapping, precisely the reference a /proc/<pid>/fd sweep would have missed. That is where lsof beats sweeping fd by hand
  • The r, w and u suffixes on the number mean read, write and read-write. Whatever holds the log for writing is usually the thing you act on
  • -n and -P switch off name and port resolution, and the manual cites speed as the reason. On a full disk under time pressure it is worth adding them by reflex
  • +D descends a directory tree recursively. Convenient, but slow on a large target. Try narrowing by mount first

Route 3 - fuser, from a path to a process

fuser is also absent here, so it too was never run. Its character differs from lsof. Where lsof produces listings, fuser takes one path and answers with the processes using it. When the file is already identified, it is faster.

# who is using this file (in ps form)
$ sudo fuser -v /var/log/app.log

# who is using this whole filesystem - when unmount refuses
$ sudo fuser -vm /var

# the two lines below kill processes. do not type them unverified
$ sudo fuser -k  /var/log/app.log     # kill immediately
$ sudo fuser -ki /var/log/app.log     # ask before each kill

With -v, in the manual's own words the processes are shown in a ps-like style with PID, USER and COMMAND, and an ACCESS column sits between them. That column is the whole knack of reading fuser. The manual defines its letters as follows.

LetterThe manual's definitionWhat it means here
fopen file (omitted in default display mode)Open for reading. Collectors and monitors, typically
Fopen file for writing (omitted in default display mode)The prime suspect. It is writing to this file right now
mmmap'ed file or shared libraryHeld through a mapping, the kind an fd sweep misses
ccurrent directoryIt merely runs there. Only blocks unmounting
eexecutable being runThe binary itself sits on that filesystem
rroot directorySeen with chrooted processes
Danger — fuser -k, in the manual's words, kills processes accessing the file. Give it a broad path and everything writing under it becomes a target. Combine -m with -k and every process using that filesystem is terminated. Run -v first, confirm that the list matches exactly what you intend to kill, and only then add -k. If you want confirmation, add -i, though the manual notes that -i is silently ignored unless -k is present too.

When more than one holder exists

This is where most wasted effort happens in practice. If you found one holder, restarted it, and the space is unchanged, the tool was usually not wrong. There was more than one reference. Here a 256MiB file was held by two processes and they were killed one at a time.

[1] created 256MiB          free=86679271
[2] rm complete             free=86680587   ls -A=[]
[3] sweep for remaining references
    pid=318  fd=3  -> /tmp/demo/app.log (deleted)
    pid=319  fd=3  -> /tmp/demo/app.log (deleted)
[4] killed only one (pid 318)  free=86682346   <-- not yet
[5] killed the other (pid 319) free=86748978   <-- now it returns

The movement at [4] is 1,759 blocks, roughly 7MiB of noise. 256MiB is 65,536 blocks, and killing one holder returned none of it. Only at [5] do 66,632 blocks come back in one go. The kernel counts references, not processes.

  • So the working order is complete the list first, then act. Finding one, killing it, and looking again changes the list each time and leaves your judgement unsteady
  • A single process can hold the same file through several descriptors. Handling the process once is enough, but if you respond with descriptor truncation you must cut every number
  • The classic multi-reference combination is fixed: the application writing the log, the collector reading it, and a tail -f session someone opened days ago and forgot
  • A child inheriting a descriptor from its parent is common too. Restart only the parent and the child keeps holding on

Windows - finding who locked it

On Windows the symptom itself presents differently. A deleted file does not sit on the space; the file will not delete in the first place. You get a message saying it is in use, and typically no indication of which program that is.

What actually works here is the Restart Manager API. Microsoft's documentation describes its purpose as shutting down and restarting the applications using the files being updated during installation and servicing, in order to reduce reboots. The information that process needs is exactly what we want: who is holding this file right now. It works without administrator rights and needs nothing installed.

Add-Type -Namespace Rm -Name Api -MemberDefinition @'
[StructLayout(LayoutKind.Sequential)]
public struct RM_UNIQUE_PROCESS { public int dwProcessId;
  public System.Runtime.InteropServices.ComTypes.FILETIME ProcessStartTime; }
[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]
public struct RM_PROCESS_INFO {
  public RM_UNIQUE_PROCESS Process;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 256)] public string strAppName;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 64)]  public string strServiceShortName;
  public int ApplicationStatus; public uint TSSessionId;
  [MarshalAs(UnmanagedType.Bool)] public bool bRestartable; }
[DllImport("rstrtmgr.dll", CharSet = CharSet.Unicode)]
public static extern int RmStartSession(out uint h, int flags, string key);
[DllImport("rstrtmgr.dll")] public static extern int RmEndSession(uint h);
[DllImport("rstrtmgr.dll", CharSet = CharSet.Unicode)]
public static extern int RmRegisterResources(uint h, uint nFiles, string[] files,
  uint nApps, RM_UNIQUE_PROCESS[] apps, uint nSvc, string[] svc);
[DllImport("rstrtmgr.dll")]
public static extern int RmGetList(uint h, out uint needed, ref uint count,
  [In, Out] RM_PROCESS_INFO[] arr, ref uint reasons);
'@

$full = (Resolve-Path $Path).Path
$h = 0
[void][Rm.Api]::RmStartSession([ref]$h, 0, [guid]::NewGuid().ToString())
[void][Rm.Api]::RmRegisterResources($h, 1, @($full), 0, $null, 0, $null)
$needed = 0; $count = 0; $reason = 0
$rc = [Rm.Api]::RmGetList($h, [ref]$needed, [ref]$count, $null, [ref]$reason)
if ($rc -eq 234) {                       # ERROR_MORE_DATA - it told us the real count
    $arr = New-Object 'Rm.Api+RM_PROCESS_INFO[]' $needed
    $count = $needed
    if ([Rm.Api]::RmGetList($h,[ref]$needed,[ref]$count,$arr,[ref]$reason) -eq 0) {
        for ($i = 0; $i -lt $count; $i++) {
            $pi = $arr[$i]
            "  PID {0,-7} {1,-22} restartable={2}" -f `
              $pi.Process.dwProcessId, $pi.strAppName, $pi.bRestartable
        }
    }
}
[void][Rm.Api]::RmEndSession($h)

This is what it actually produced here. The same file was queried twice, the second time while another process held it open with no sharing.

=== A. with nobody holding it ===
holders of: C:\tmp\demo\locked.txt
  (none - no process holds this file)

=== B. with another process holding it ===
holders of: C:\tmp\demo\locked.txt
  PID 25328   Windows PowerShell     restartable=True
  • Getting restartable alongside the PID is the practical part. True means the program is registered to survive being shut down and restarted, which makes the decision about how to act much easier
  • The first RmGetList call returning 234 (ERROR_MORE_DATA) is not a failure but the normal flow telling you the array size required. Treat that value as an error and your results will always look empty
  • When Explorer's file in use dialog names the program, this API is what is behind it. All we are doing is pulling the same information from a script
  • For the GUI equivalent, open Resource Monitor (resmon) and type the filename into the Associated Handles search box on the CPU tab. This article captured no screenshots, so the description of the screen stops there

Windows - the methods that do not work

Two approaches turn up constantly in search results and rarely work. Both were run, and why they fail turns out to be the useful part.

PS> openfiles /Local
ERROR: The logged on user does not have administrative privileges.

PS> openfiles /Query /FO TABLE
INFO: The system global flag 'maintain objects list' needs
      to be enabled to see local opened files.
Files opened remotely via local share points:
ERROR: Access is denied.

PS> # searching Modules - DLLs do show up
PS> Get-Process | Where-Object { $_.Modules.FileName -contains
      'C:\WINDOWS\System32\kernel32.dll' } | Select-Object -First 3 Id,ProcessName
   Id ProcessName
   -- -----------
19744 AMDInstallManager
11128 AMDRSSrcExt
21760 ApplicationFrameHost

PS> # the same search for a data file
PS> Get-Process | Where-Object { $_.Modules.FileName -contains $target }
(0 results)

openfiles is blocked twice over. Seeing the local list requires a system-wide flag called maintain objects list, and turning it on with openfiles /Local ON itself demands administrator rights and a reboot to take effect. In other words it is not a tool you can enable after the incident has already started. With the flag off, all /Query answers about is files opened remotely through shares.

Get-Process and its Modules collection is a different case. It is not that it fails, it is that its subject is something else. That collection holds executable images loaded into the process, meaning EXEs and DLLs. In the output above it found kernel32.dll without difficulty. A log file or a data file is not a module, so the answer will be zero results forever.

  • The rule of thumb, then: if a locked DLL is blocking an update, the Modules search is enough; for anything else, go to the Restart Manager route in the previous section
  • The Sysinternals handle family is widely used, but it is not installed here and I could not run it. This article therefore quotes none of its output
  • In real incidents the culprit behind a lock is quite often antivirus, backup or an indexing service. These open and close files briefly, so running the same query twice a few seconds apart separates them from a persistent holder

Restart is the answer, but when you cannot restart

Once you have found the holder the remedy is simple. A restart is the surest thing. For a log file a reopen signal is often enough instead. But when it is a live service and neither is possible right now, there is one widely known workaround: truncating the open file descriptor directly.

Danger — the method below cannot be undone and has no confirmation step. Pick one wrong descriptor number and a different file that process has open is emptied entirely. Before running it, confirm the destination with your own eyes using readlink /proc/<pid>/fd/<n>, check that it really is the log file carrying the (deleted) marker, and only then act. Whenever a restart is possible, a restart is the safer path. 
# 1) always first - see with your own eyes what you are about to cut
$ readlink /proc/957/fd/3
/tmp/demo/big.log (deleted)

# 2) only then - truncate the descriptor (irreversible)
$ : > /proc/957/fd/3

# what came out in this environment
[A] after rm             free=86771292
    fd: inode=16607023627971255 links=0 size=268435456 blocks=262144
[B] : > /proc/957/fd/3
    tail: big.log: file truncated
    after the attempt: size=0  blocks=262144
    free=86770524                     <-- nothing came back
[C] truncate -s 0 /proc/957/fd/3
    size=0  blocks=262144
    free=86769107                     <-- still nothing
[D] after kill           free=86833972

The result deserves an honest reading. The truncation itself worked. size went from 268435456 to 0, and the tail holding the file reacted with file truncated, which is the proof. Yet free blocks did not come back and blocks stayed at 262144. The actual release happened after kill, at [D].

Do not rush to a conclusion here. The /proc in this environment is not the Linux kernel procfs but an MSYS emulation, and NTFS sits underneath. This is not evidence about what happens on Linux. The lesson the failure does carry is environment-independent, though: whether truncation worked must be confirmed with df, not with size. A size display reaching zero and space actually returning are two separate facts.

And the method has a restricted target. It works on logs and does not work on data files, because the two are handled differently.

  • Log files — usually opened in append mode and written only at the end. Losing the front does not stop the next write from continuing at the new end. Cutting it does not break the application's model of the file
  • Data and DB files — offsets are computed and specific positions are read and written. The moment you cut, the structure the process remembers no longer matches the file. If a later read interprets a zero-filled region as valid data, the damage spreads quietly
  • Logs not opened in append mode — an implementation that keeps its offset will let the file grow back to that offset after a cut, producing a sparse file whose apparent size is large while real usage stays small
  • Files open through several descriptors — cutting one leaves the others holding on, exactly as in the previous section

Locking is a different story

Everything so far concerned files that are deleted yet open. File locking has a similar name and overlapping symptoms but is a separate mechanism. And this is precisely where Linux and Windows part ways.

The Unix flock is advisory. The manual puts it like this: given suitable permissions on a file, a process is free to ignore the use of flock and perform I/O on the file. A lock is an agreement among programs that chose to participate, not a wall the kernel enforces. Which is why on Linux rm never fails because something else holds a lock.

Windows differs, though not in the way it is usually described. Windows does not refuse unconditionally; the process opening the file chooses a share mode at open time and the kernel enforces it. The CreateFile documentation states that when the share parameter is zero the file cannot be shared and cannot be opened again until the handle is closed, and that a conflicting request fails with ERROR_SHARING_VIOLATION. Run it and the same file splits into opposites depending on the share mode.

=== opened with share mode None ===
PS> Remove-Item $target
ERR: IOException
MSG: The process cannot access the file ... because it is being used by another process.
PS> Rename-Item $target renamed.txt      -> same error
PS> Get-Content $target                  -> same error

$ stat -c 'inode=%i links=%h size=%s' locked.txt
inode=6192449489676514 links=1 size=19       # metadata still readable
$ cat locked.txt
cat: locked.txt: Device or resource busy
$ rm locked.txt
rm: cannot remove 'locked.txt': Device or resource busy
$ ls -l
-rw-r--r-- 1 ... 19 Sep  2 09:12 locked.txt  # still sitting there

=== the same file opened with share mode ReadWrite, Delete ===
$ cat shared.txt
share-delete payload
$ rm -v shared.txt
removed 'shared.txt'                          # succeeded. the holder is still alive
$ ls -A
(empty)

What differs between the two blocks is neither the file nor the deleting command. It is one thing: what the opener permitted. The file opened without sharing rejected delete, rename and read alike, while the file whose share list included delete lost its name instantly even with the holder still running. That second case looks essentially the same as Unix.

AspectLinux / UnixWindows
Nature of the lockAdvisory. An agreement among participantsThe kernel enforces the share mode chosen at open
Deleting a file in useAlways succeeds. Only the name goesSucceeds only if the opener permitted deletion
What you see on failureIt does not failAn in-use message · Device or resource busy
The resulting problemSpace quietly fails to returnDeployments and updates are loudly blocked
Tools for finding itlsof · fuser · /procRestart Manager · Resource Monitor
Common misconceptionThat rm deletes the dataThat Windows can never delete a file in use

The practical residue is this. If a deployment on Windows is blocked by a file lock, the place to fix is the opener, not the deleter. Let the code that opens the log permit delete sharing and rotation stops jamming.

Containers - a pid depends on the vantage point

What makes this work hard in containers is not missing tools but the fact that pids and paths differ by vantage point. Take a pid from lsof on the host, hand it to kill inside the container, and you kill the wrong process. The reverse holds too.

Containers themselves were not run here. But a mismatch of the same nature shows up in this environment anyway: MSYS uses its own pids and the Windows kernel uses different ones.

$ tail -f hold.log > /dev/null &
$ echo $!
1410

$ ls -l /proc/1410/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/hold.log (deleted)

$ ps -W | head -1
      PID    PPID    PGID     WINPID  TTY   UID    STIME COMMAND
$ ps -W | grep 1410
     1410    1405    1403        580  ?  197609 09:18:32 /usr/bin/tail

The pid the shell knows is 1410 and the pid the kernel knows is 580. Same process, and neither number is wrong. The point is that you must not hand one side's number to the other without a translation table, and what happens inside a container pid namespace is the same in kind. Below are the places to check in that situation.

  • Moving a host pid to a container pid requires translation. On Linux the NSpid line in /proc/<host-pid>/status lists both values side by side
  • Paths diverge too. The container's /var/log/app.log is, from the host, some long path inside an overlay upper layer. Do not mistake a path from a host-side lsof for a container path
  • Often there is neither lsof nor /proc access inside the container. Then it is faster to look from the host, where that container's filesystem is visible under /proc/<pid>/root/
  • The most frequent mistake is assuming a container restart settles it while leaving the log volume alone. If the holder is a log collector outside the container, restarting the container any number of times returns nothing
  • With an orchestrator in place, a process a human kills comes back. The action is not finished until you have checked whether the newly started process grabs the same file again

The .nfs files on network filesystems

On NFS the same situation appears in visible form. You have probably seen a deleted file refuse to disappear and instead sit there under a name beginning with .nfs. That is not a fault but the NFS client trying to imitate POSIX behaviour, usually called silly rename.

The circumstances are these. On a local filesystem a file whose name is gone can still be read while references remain. The NFS protocol does not support that directly. So the client kernel renames the file to a .nfsXXXX name instead of removing it. As the Linux NFS wiki explains, the client removes that new name when the vnode becomes inactive. There is no NFS mount in this environment, so I could not reproduce this directly.

  • So a .nfs file is a marker, not litter to be scrubbed. It means something still has the file open, so find and clear the holder and the name disappears on its own
  • Trying to delete it does not go well either. While a reference lives, the client protects that name
  • The same wiki notes one exception: if the client dies between the rename and the remove, a garbage file is left on the server. Only then is it genuinely something to delete, and the test is whether it survives a client reboot
  • The imitation holds only while there is a single client. A client cannot know whether another client has the file open, so in layouts where several clients share a file, an open file can be deleted out from under them
  • An rmdir failing on a directory that looks empty has the same cause. Run ls -a and the .nfs file is inside

Keeping it from happening at all

The causes converge on essentially one thing: a log rotation configuration that has quietly gone out of step. Move or delete the file without signalling the process to reopen, and the process keeps writing to the old, nameless file. How rotation manufactures this state is covered separately in where log rotation fails quietly.

There is something to do on the design side too. When you need a temporary file, there is an idiom that removes the name immediately after opening. With no name, no other process can touch it, and however the process ends the kernel returns the space by itself. Cleanup code stops being necessary.

# open then unlink - an anonymous temp file
$ exec 9> tmpdata
$ rm tmpdata                      # the name disappears right here
$ echo "hello anonymous" >&9      # writing still works
$ ls -A
(empty)
$ stat -L -c 'inode=%i links=%h size=%s' /proc/self/fd/9
inode=16325548651260599 links=0 size=16
$ exec 9>&-                       # space returns at close. no cleanup code

# a value to feed monitoring - the gap between df and du
$ used_df=$(df -k --output=used /var | tail -1)
$ used_du=$(du -sk /var 2>/dev/null | cut -f1)
$ echo "gap_kb=$(( used_df - used_du ))"
  • Putting the gap between df and du into monitoring makes this visible before it becomes an incident. Watch the trend, not the absolute value. A gap widening beyond its usual band means held files are accumulating
  • du is expensive on large filesystems, so use a long interval. On something like CephFS, where a full walk is costly, avoid this approach entirely and use the recursive statistics the filesystem provides
  • Verify that the reopen signal reaches both the writer and the reader. If only the application gets it and the collector does not, half the grip remains
  • Rotating by emptying the file instead of renaming it removes the problem at the root. The price is that lines written at the moment of rotation can be lost
  • tail -f sessions left behind by people are a cause as well. Sessions opened for investigation are the kind of thing a single habit, close it when you are done, eliminates

The order to follow under pressure

With a full disk there is no time to deliberate, so it is better to fix the order in advance. What follows runs from the cheapest check to the most dangerous action.

StepWhat to doWhat to readWhat not to do here
1Give the failing path to df directlyIs that path really on that filesystemJudging from the root line alone
2Compare a du -sh total against df UsedIs the gap tens of gibibytesDeclaring the gap to be the cause outright
3lsof +L1 or a /proc sweeppid · held size · pathActing before the list is complete
4Collect every reference to that fileParent, child, collector, human sessionKilling one and re-counting
5Restart, or send the log reopen signalDoes df free space jump like a stepReaching for kill -9 first
6Only if you still cannot, truncate the fdOnly after readlink confirms the targetApplying it to data or DB files
Danger — kill -9 (SIGKILL) gives a process no chance to clean up. It may cost nothing worse than buffered log lines, or it may leave a file that was mid-write in an intermediate state. Send the default termination signal first, wait a few seconds, and only force it if the process is still alive. Either way it is a last resort against a database or any process holding state.
  • If step 3 returns zero candidates, suspect privilege before anything else. Other users' processes drop out silently
  • If df does not move after step 5, go back to step 4. The tool was not wrong; a reference is still there
  • Under pressure, heading in the direction of finding more things to delete usually costs time. If du and df disagree, deleting will not resolve it
  • Once the action is done, look once more at whether the same file gets grabbed again. Leave the rotation config as it was and you will be back in the same place in days
  • When memory is the real cause the symptoms can look similar but the problem is different. That branch lives in how to read what the OOM killer chose

Summary

rm is a command that deletes a name. What deletes the data is the kernel, at the moment the last reference closes. So resolving this is never a matter of deleting the file again but of making the holder let go, and for that you first have to identify who is holding it.

There are three routes to that. lsof +L1 selects exactly the open files with a link count of zero. fuser -v takes one path and answers with processes, its ACCESS column describing the character of each grip. With neither available, sweep /proc/<pid>/fd from the shell and the (deleted) marker stands in for the answer. On Windows the symptom is inverted and the Restart Manager supplies the answer.

Two things are easy to forget. References may not be singular, and descriptor truncation works on logs and not on data files. Miss either and you will act without df moving, or move it and break something else.
