日期变成了 46233 这样的数字 - Excel 序列值与 1900 年闰年缺陷

从未存在过的 1900 年 2 月 29 日至今活在单元格里 - 为兼容性而不修正的缺陷的今天

2026-07-30 开发/基础设施

引言：日期列变成了 46233 这样的数字

打开报表，合同日期那一列全变成了 46233、46235 这样的五位数字。昨天那里明明显示 2026-07-30。第一反应通常是两种：判定文件坏了，向发送方重新索要原件；或者清空这一列手工重新录入。两种都不必要。数据一个字节都没丢。

在电子表格里，日期从一开始就是数字。单元格存的是一个整数，表示距基准日过了多少天，而让它看起来像日期的规则位于单元格格式这个完全不同的层。格式消失，屏幕退回成数字，值却原地不动。看到 46233 不是损坏，而是格式的缺席。

到这里都是广为人知的事。这篇文章要往下挖的是接下来的部分。那套数字体系里藏着一个从未存在过的日子。

  • 序列值 59 是 1900 年 2 月 28 日。这是真实日期
  • 序列值 60 是 1900 年 2 月 29 日。那一天从来没有过。 1900 年不是闰年
  • 序列值 61 是 1900 年 3 月 1 日。从这里往上全部精确

所以 1900 年 3 月 1 日之前的所有日期都差一天。 三十多年前做出的一个兼容性决定，让今天这份文件的星期计算和期间计算出错。而那个缺陷至今没被修正，因为判断上认为留着它更划算。

这篇文章不会说「别用电子表格」。那句建议对已经拿到文件的人毫无帮助。取而代之的是，把为什么会变成这样、边界处究竟什么会出错、应该用什么格式交换数据，全部用亲手跑出来的数字整理清楚。

执行环境。 下面所有输出都是在 Windows 10 Pro (10.0.19045) 上实际运行的结果。计算引擎是 Excel 16.0 (build 20228)，语言一侧是 Python 3.13.3、Node.js v22.16.0、XlsxWriter 3.2.9，Shell 为 GNU bash 5.2.37 (MSYS2)。所有脚本都写成文件后执行。

关于验证方式的坦白说明。 电子表格一侧的输出不是用鼠标操作界面、靠眼睛读取的，而是通过 COM 自动化把值和公式送进同一个计算引擎再读回结果。单元格值、显示字符串、格式代码、函数返回值都是这样实测的。相对地，功能区菜单的位置、选项对话框里的复选框、导入向导的界面构成这类 UI 元素并没有查看。 这类内容本文不做断言，只作为文档依据提及。

本文不涉及的内容。 查找函数的语法与错误在 VLOOKUP 与 XLOOKUP，用 Python 处理表格与 CSV 的库用法在 表格与 CSV 自动化。这里只写序列值转换逻辑。打开 CSV 时文字变乱码的问题交给 编码诊断。本文第 10 节只看同一份 CSV 里日期值本身被改变的那一层。示例数据全部虚构。

2. 从未存在的 1900 年 2 月 29 日

1900 年不是闰年，套一下规则就出来了。能被 4 整除是闰年，能被 100 整除是例外，能被 400 整除又是闰年。

--- 2-1. is 1900 a leap year? ---
year 1896  divisible by 4=True  100=False 400=False  leap=True
year 1900  divisible by 4=True  100=True  400=False  leap=False
year 1904  divisible by 4=True  100=False 400=False  leap=True
year 2000  divisible by 4=True  100=True  400=True   leap=True
year 2024  divisible by 4=True  100=False 400=False  leap=True
year 2026  divisible by 4=False 100=False 400=False  leap=False
year 2100  divisible by 4=True  100=True  400=False  leap=False
proleptic Gregorian says 1900 has 28 days in February
dt.date(1900,2,29)          : ValueError day is out of range for month

1900 能被 4 整除，但也能被 100 整除，且不能被 400 整除。它不是闰年。 2000 年能被 400 整除所以是闰年，2100 年又不是。Python 的日期类型在试图构造 1900-02-29 时会当场抛出异常。意思是这个日期不存在，所以造不出来。

可是电子表格接受它。我直接问了函数。

--- 16-3. the phantom day, in Excel's own words ---
TEXT(59) : 1900-02-28 Tuesday
TEXT(60) : 1900-02-29 Wednesday
TEXT(61) : 1900-03-01 Thursday
DAY(60)=29  MONTH(60)=2  YEAR(60)=1900
DATE(1900,2,29)      -> 60
DATEVALUE(1900-02-29)-> 60
DATEVALUE(1901-02-29)-> ERROR - refused
DATEVALUE(2026-02-29)-> ERROR - refused

这五行是决定性的。对序列值 60，它回答日是 29、月是 2、年是 1900。 不只是显示如此，整个日期函数家族都相信那一天存在。

最后三行把这件事确定为刻意的例外而非显示问题。用字符串传 1900-02-29 会返回 60 并接受。可是把 1901-02-29 或 2026-02-29 交给同一个函数，它以错误拒绝。 也就是说它并不是普遍允许不存在的 2 月 29 日，而是只放行 1900 年这一个。例外被精准地钉在数轴上的一格里。

还有一点。间接询问那个二月的长度，会得到这样的结果。

--- 16-8. DATE() with an out-of-range day ---
DATE(1900,2,30)          : 1900-03-01
DATE(1900,0,1)           : #NUM!
DATE(1899,12,31)         : 3799-12-31
DATE(99,1,1)             : 1999-01-01

输入 1900 年 2 月 30 日会得到 3 月 1 日。 溢出的日子会顺延到下个月，所以 2 月 30 日等于 3 月 1 日就意味着它把那个二月数到了 29 号。真实的 1900 年 2 月只到 28 日，所以 2 月 30 日本该是 3 月 2 日。一个多出一天的月份被直接用在了计算里。

另外第三行在实务上也会出事。把 1899 作为年份传给日期函数，得到的是 3799-12-31，因为小于 1900 的年份会加上 1900 来解释。想处理 1899 年的数据、期待结果落在 1900 年附近，却得到 3799 年，就是从这里来的。

1900 年 1 月 1 日实际是星期一，它却答星期日。 1900 年 2 月 28 日实际是星期三，给出的是星期二。从 3 月 1 日起就精确了。重要的是两份输出给出了相同的答案。这不是某个工具的怪癖，而是序列值体系本身的性质。

3.2 相减期间会多出一天

比星期造成更大实务损害的是期间计算。

--- 14-5. a difference in days across the boundary ---
real day count 1900-01-01 .. 1900-03-01 : 59
serial subtraction       : 61 - 1 = 60
serials count one extra day because the phantom day sits between them

real day count 1900-03-01 .. 1901-03-01 : 365
serial subtraction       : 365
both sides above the boundary, so the difference is correct

--- 15-5. the same subtraction inside the spreadsheet ---
DATE(1900,3,1)-DATE(1900,1,1)    : 60   (real answer 59)
DATE(1901,3,1)-DATE(1900,3,1)    : 365   (real answer 365)
DATEDIF 1900-01-01..1900-03-01 d : 60
DATE(2026,7,30)-DATE(2026,7,1)   : 29
  • 1900-01-01 与 1900-03-01 的真实间隔是 59 天，相减序列值却得到 60。因为幽灵日夹在两个日期之间
  • 专用的期间函数也返回同样的 60。换用专门函数也躲不掉
  • 两端都在边界之上的 1900-03-01 到 1901-03-01 是精确的 365。也就是说只有跨越边界的区间才出错
  • 2026 年之内的计算自然是精确的，因为两个日期之间没有幽灵日
  • 实务含义很明确。跨越 1900 年初的期间计算会多出一天。 工龄、到期、年龄计算都会被卷进来

4. 为什么没有修正 - 这是刻意的缺陷

这一点是本文最重要的角度。这不是一个尚未被发现的缺陷。 官方文档把来龙去脉和判断依据都明确写下来了。

据文档所述，早期的 Lotus 1-2-3 假定 1900 年是闰年，这个假定让该程序处理闰年更简单，并且对几乎所有日期计算都没有造成危害。后来Microsoft Multiplan 和 Excel 发布时采用了同样的假定。 理由也照实写着：为了使用与 Lotus 1-2-3 相同的序列日期体系以提高兼容性，并让用户更容易在程序之间搬移工作表。

现在修正在技术上并非不可能，但文档判断缺点超过优点。它列出的依据如下。

  • 既有工作表和文档里几乎所有日期都会减少一天。 修正这个偏移需要相当多的时间和精力，在使用日期的公式里尤其如此
  • 星期函数等部分函数的返回值会改变。 工作表里的公式可能无法正确工作
  • 会破坏与其他使用日期的程序之间的序列日期兼容
  • 反过来若不修正，问题只有一个：1900 年 3 月 1 日之前的日期上星期函数会返回错误值，而大多数用户不使用那么早的日期，所以文档称之为罕见问题
  • 文档明确写道除 1900 年之外所有闰年都被正确处理，包括能被 100 整除而不是闰年的 2100 年这类世纪年。只有 1900 年被区别对待

总结起来是这样。留下一个不存在的日子是选择，不是失误。 为了和当时广泛使用的程序对齐数字而保留，而这个选择成了标准。成为标准之后，修正的成本就超过了搁置的成本。这是兼容性战胜正确性的案例，三十年后这个判断依然维持着。

从这里该学到什么。 这个缺陷不是「老软件的伤疤」，而是一种格式广泛铺开之后，连它的错误也一起固化的案例。如果你在设计数据格式，这个故事的教训很直白：为了早期便利而做的简化会变成永久的约束。 如果你在消费别人的格式，教训是另一个方向：规范里写着的怪异之处通常有其原因，不要期待它被修好，照它本来的样子应对。

5.1 改变体系，数字不动而日期移动

最危险的行为是这个。我在已有数据的文件上切换了体系。

--- 16-5. flip a workbook to 1904: the number stays, the date moves ---
Date1904 = False
  stored 46233 shows as 2026-07-30
  stored 36526 shows as 2000-01-01
Date1904 = True   (nothing was re-entered)
  stored 46233 shows as 2030-07-31
  stored 36526 shows as 2004-01-02
Date1904 = False   stored 46233 shows as 2026-07-30
  • 没有重新输入任何值，显示的日期却从 2026-07-30 移到了 2030-07-31
  • 保存的数字仍然是 46233。 改变的只有一条解释规则
  • 移动幅度是 1462 天，也就是四年零一天。改回去就恢复原状
  • 实务规则很简单。已有数据的文件绝不改动日期体系。 所有看得见的日期会悄悄滑走四年
  • 这个事故可怕的地方在于没有任何错误提示。所有日期看上去依然是完全合理的日期

9. 亲手写一个修正过的转换器

接下来是代码。核心在于一个基准日不够，60 及以下需要分支。先用 Python 写。

import datetime as dt

EPOCH_SHIFTED = dt.date(1899, 12, 30)   # correct for serial 61 and up
EPOCH_TRUE    = dt.date(1899, 12, 31)   # correct for serials 1..59
EPOCH_1904    = dt.date(1904, 1, 1)

def serial_to_date(n, date1904=False):
    if date1904:
        return EPOCH_1904 + dt.timedelta(days=n)
    if n >= 61:
        return EPOCH_SHIFTED + dt.timedelta(days=n)
    if n == 60:
        raise ValueError('serial 60 is 1900-02-29, a date that never existed')
    if n >= 1:
        return EPOCH_TRUE + dt.timedelta(days=n)
    raise ValueError('serial %r has no calendar date' % n)

def serial_to_datetime(x, date1904=False):
    whole = int(x // 1)
    d = serial_to_date(whole, date1904)
    seconds = round((x - whole) * 86400)      # round, never truncate
    return dt.datetime.combine(d, dt.time()) + dt.timedelta(seconds=seconds)

用 Node 写同样的东西，同时把未修正的朴素实现并列放在旁边做对照。

const MS_DAY = 86400000;

// uncorrected: built only on the fact that 25569 is the Unix epoch
function naiveSerialToDate(n) {
  return new Date(Math.round((n - 25569) * MS_DAY));
}

// corrected: give the day back below 60
function serialToDateUTC(n) {
  if (n < 1)   throw new RangeError('serial ' + n + ' has no calendar date');
  if (n === 60) throw new RangeError('serial 60 is the phantom 1900-02-29');
  const shifted = n < 60 ? n + 1 : n;
  return new Date(Math.round((shifted - 25569) * MS_DAY));
}

function dateToSerialUTC(d) {
  const raw = Math.round(d.getTime() / MS_DAY) + 25569;
  return raw < 61 ? raw - 1 : raw;
}

  • 没有年份的输入会被填入当前年份。 MAR1 变成了 2026-03-01。也就是说明年再打开同一个文件重新输入同样的值，会得到另一个数字。 依赖无年份代码的数据每年都在变
  • 三段式的值会按两位年份解读。 1/2/3 变成了 2003-01-02。版本号和规格代码会掉进这里
  • 月份缩写后面接数字的形态很危险。 简短的英文前缀配上数字很容易长成那个样子
  • 只含一个连字符或斜杠的短代码同样处在危险区间。 有两个以上，或者有两个点，通常就留作字符串了
  • 存活条件很明确。 以字母开头 (A-001)，或者有两个以上的点 (0.1.2)，强制转换就不会发生
  • 数字一侧的损失属于同一系列。 007 的前导零和 1E5 的记法都会消失。邮编、账号、料号会掉进这里
  • 转换之后没有还原的办法。 原文不会被保存，只能重新取一份原始数据

最后一段打破了一个常见的错觉。「选符合业务范围的那个就行」这个办法在这里什么都没筛出来。 两种解读都让五行全部落在合理区间里。这种情况确实很常见。所以顺序很重要。

  1. 读容器里的标志。xlsx 在这里就能定案。 解开后在 xl/workbook.xml 里查找 date1904 属性。不存在或为 0 就是 1900 体系，为 1 就是 1904 体系。这是唯一具有确定性的依据
  2. 用一行锚点核对。 挑一条已知真值的记录，按两种体系换算，看哪一种吻合。像上面的输出一样，一行就能结束
  3. 用业务范围筛选。这是弱依据。 排除掉那个落在业务上不可能的年份的解读。不要单独作为判断依据
  4. 用间隔指标找出边界以下的值。 如果两种体系换算的间隔是 1461 天而不是 1462 天，那个序列值就在 60 及以下，也就是说那一行落在闰年缺陷的区间里
  5. 只有 CSV 而上面都用不上时，不要猜。 应当向发送方询问三件事：基准体系、日期列清单、是否含时刻

还有两件要确认的事。如果数据里出现序列值 60，就把那一行单独标出来上报。 悄悄放过去，日后就无法追踪那一天的差是从哪来的。另外数一次早于 1900 年 3 月 1 日的日期有多少行。 如果是 0，本文有一半内容你可以不必操心。

结论是系统之间用 ISO 8601 字符串交换。不过这个建议有代价，我实际测了这个代价。结果和直觉不一样。

  • 也就是说代价只有体积一项。 以速度为理由选择序列值交换是没有依据的
  • ISO 8601 也有解决不了的。没有偏移量就依然不知道属于哪个时区。 但那份含糊变得看得见了。相对裸数字，这才是真正的收益

# Excel 日期序列值 — 对照表·修正版转换代码·交换规则·诊断流程

> 来源: braindetox.kr — 日期变成了 46233 这样的数字
> 验证环境: Windows 10 Pro 10.0.19045 / Excel 16.0 (build 20228，COM 自动化) / Python 3.13.3 / Node.js v22.16.0 / XlsxWriter 3.2.9
> 把这个文件直接贴给 AI，说「按这个标准检查我们的日期管线」即可。
> 一句话: 序列值 60 是从未存在过的 1900-02-29。所以 1900-03-01 之前的日期都会差一天。

## 0. 前提 — 日期在单元格里就是数字

| 层 | 存的是什么 | 在哪里 |
|---|---|---|
| 值 | 距基准日的天数 (整数) | 单元格的值 |
| 时刻 | 一天的小数部分 (0.5 = 正午) | 同一个数字的小数位 |
| 显示 | 让数字看起来像日期的规则 | 单元格格式，与值无关 |

格式丢了，值仍然完好，只是屏幕退回成数字。**看到 46233 不是数据坏了，而是格式没了。**

## 1. 序列值 ↔ 日期对照表 (1900 体系)

| 序列值 | 日期 | 备注 |
|---|---|---|
| 0 | 1900-01-00 | 不存在的「0 日」。Excel 真的这样显示 |
| 1 | 1900-01-01 | 下限。实际是星期一，Excel 却答星期日 |
| 58 | 1900-02-27 | 边界以下 |
| 59 | 1900-02-28 | 边界以下。实际是星期三，Excel 说星期二 |
| **60** | **1900-02-29** | **从未存在过的一天。问题就在这里** |
| 61 | 1900-03-01 | 从这里往上全部正确 |
| 366 | 1900-12-31 | |
| 25569 | 1970-01-01 | Unix 基准日 |
| 45000 | 2023-03-15 | |
| 46233 | 2026-07-30 | |
| 2958465 | 9999-12-31 | 上限 |

- 负数不是日期。`TEXT(-1,...)` 返回错误
- 在单元格里输入 1899-12-31，留下的是**字符串**而不是日期
- 10000-01-01 同理，也会变成字符串

## 2. 边界三格的算术

| 序列值 | Excel 显示 | 真实公历日期 | 1899-12-30 + n |
|---|---|---|---|
| 58 | 1900-02-27 | 1900-02-27 | 1900-02-26 (早一天) |
| 59 | 1900-02-28 | 1900-02-28 | 1900-02-27 (早一天) |
| 60 | 1900-02-29 | 不存在 | 1900-02-28 |
| 61 | 1900-03-01 | 1900-03-01 | 1900-03-01 (一致) |
| 62 | 1900-03-02 | 1900-03-02 | 1900-03-02 (一致) |

→ **基准日 1899-12-30 只在序列值 61 及以上成立。** 60 及以下会落早一天。这一个差一错误就是全部问题。

实测到的衍生症状:

- `=DATE(1900,3,1)-DATE(1900,1,1)` → **60** (真实天数是 59)
- `=DATEDIF(DATE(1900,1,1),DATE(1900,3,1),"d")` → **60**
- `=DATE(1901,3,1)-DATE(1900,3,1)` → 365 (两端都在边界之上，所以正确)
- `=DATE(1900,2,30)` → 1900-03-01 (证明它把那个二月算成 29 天)
- `=DATEVALUE("1900-02-29")` → 60 (接受) / `=DATEVALUE("2026-02-29")` → 错误 (拒绝)

## 3. 1900 体系 vs 1904 体系

| 项目 | 1900 体系 | 1904 体系 |
|---|---|---|
| 基准 | 1900-01-01 = 1 | 1904-01-01 = 0 |
| 闰年缺陷 | 有 (序列值 60) | 无 |
| 2026-07-30 | 46233 | 44771 |
| 2000-01-01 | 36526 | 35064 |
| 2011-07-05 | 40729 | 39267 |
| 差 | — | 始终小 1462 天 |

- 1462 天 = 4 年加一个闰日
- 切换已有文件的体系，**保存的数字一动不动，显示的日期却移动 1462 天**
  - 46233: 2026-07-30 → 2030-07-31
  - 36526: 2000-01-01 → 2004-01-02
- 两种解读之间的间隔变成 **1461 天**而不是 1462 天，只发生在序列值 60 及以下。这就是识别边界值的指标

## 4. 时刻是小数部分

| 时刻 | 小数 | ×86400 |
|---|---|---|
| 00:00:00 | 0 | 0 |
| 06:00:00 | 0.25 | 21600 |
| 12:00:00 | 0.5 | 43200 |
| 08:00:00 | 0.33333333333333331 | 28800 |
| 09:30:00 | 0.39583333333333331 | 34200 |
| 23:59:59 | 0.99998842592592596 | 86399 |
| 00:00:01 | 1.1574074074074073e-05 | 1 |

- 二进制里精确的只有 0.25、0.5、0.75。其余全是近似值
- 2026-07-30 09:30:00 = **46233.3958333333** (46233 + 34200/86400)

## 5. 小数部分的误差 — 一秒消失的地方

把一天 86400 秒全部往返一遍的实测:

- 四舍五入后出错的秒数: **0 个 / 86400**
- 最大绝对误差: **3.13855707645e-07 秒 (0.313856 微秒)**，出现在第 238 秒
- **截断 (int/INT) 后出错的秒数: 43136 个 / 86400 — 一半**

| 运算 | 结果 | 真值 |
|---|---|---|
| `INT((46233.3958333333-46233)*86400)` | **34199** | 34200 |
| Node `new Date((46233.3958333333-25569)*86400000)` | **09:29:59.999Z** | 09:30:00 |
| Excel `TEXT(46233.3958333333,"hh:mm:ss.000")` | 09:30:00.000 | 09:30:00 |
| 1/24 累加 24 次后减 1 | **−0.00000000000000044** | 0 |

→ **规则: 把小数部分还原成秒时必须四舍五入。截断会让一半的行差一秒。**
→ Excel 在显示阶段会舍入，所以屏幕上看不见。它暴露在取出数值做运算的代码里。

## 6. 修正版转换代码 (Python)

```python
import datetime as dt

EPOCH_SHIFTED = dt.date(1899, 12, 30)   # 序列值 61 及以上正确的基准
EPOCH_TRUE    = dt.date(1899, 12, 31)   # 序列值 1..59 正确的基准
EPOCH_1904    = dt.date(1904, 1, 1)

def serial_to_date(n, date1904=False):
    if date1904:
        return EPOCH_1904 + dt.timedelta(days=n)
    if n >= 61:
        return EPOCH_SHIFTED + dt.timedelta(days=n)
    if n == 60:
        raise ValueError('serial 60 is 1900-02-29, a date that never existed')
    if n >= 1:
        return EPOCH_TRUE + dt.timedelta(days=n)
    raise ValueError('serial %r has no calendar date' % n)

def date_to_serial(d, date1904=False):
    if date1904:
        return (d - EPOCH_1904).days
    if d >= dt.date(1900, 3, 1):
        return (d - EPOCH_SHIFTED).days
    if d >= dt.date(1900, 1, 1):
        return (d - EPOCH_TRUE).days
    raise ValueError('dates before 1900-01-01 have no serial in this system')

def serial_to_datetime(x, date1904=False):
    whole = int(x // 1)
    d = serial_to_date(whole, date1904)
    seconds = round((x - whole) * 86400)        # 禁止截断，必须舍入
    return dt.datetime.combine(d, dt.time()) + dt.timedelta(seconds=seconds)
```

已验证的数值: `date_to_serial(2011-07-05)` = 40729，1904 体系为 39267，差 1462。Excel 与官方文档给出同样的数字。

## 7. 修正版转换代码 (Node)

```javascript
const MS_DAY = 86400000;

// 未修正: 内部往返完美无缺，日期却差一天
function naiveSerialToDate(n) {
  return new Date(Math.round((n - 25569) * MS_DAY));
}

// 修正版
function serialToDateUTC(n) {
  if (n < 1) throw new RangeError('serial ' + n + ' has no calendar date');
  if (n === 60) throw new RangeError('serial 60 is the phantom 1900-02-29');
  const shifted = n < 60 ? n + 1 : n;
  return new Date(Math.round((shifted - 25569) * MS_DAY));
}

function dateToSerialUTC(d) {
  const raw = Math.round(d.getTime() / MS_DAY) + 25569;
  return raw < 61 ? raw - 1 : raw;
}

// 含时刻时: 按毫秒舍入，避免截断误差
function serialToInstantUTC(x) {
  const whole = Math.floor(x);
  const base = serialToDateUTC(whole).getTime();
  return new Date(base + Math.round((x - whole) * MS_DAY));
}
```

| 59 | 1900-02-27 | 1900-02-28 | 否 |

## 8. 导出成 CSV 后剩下什么

六个单元格放同样的数字，只改格式，另存为 CSV 的实测:

| 单元格格式 | 单元格的值 | CSV 里实际写入的内容 |
|---|---|---|
| `yyyy-mm-dd` | 46233 | `2026-07-30` |
| (无格式) | 46233 | `46233` ← **序列值原样漏出去** |
| `mm/dd/yyyy` | 46233 | `07/30/2026` |
| `yyyy-mm-dd` | 58 | `1900-02-27` |
| `yyyy-mm-dd hh:mm:ss` | 46233.3958333333 | `2026-07-30 09:30:00` |
| `@` (文本) | `2026-07-30` (字符串) | `2026-07-30` |

- **CSV 里写什么由单元格格式决定，不是由值决定**
- 最后两行在 CSV 里**字节完全相同**。接收方无法区分原本是数字还是字符串
- 只要有一列没设格式，那一列就以数字形式发出去。这就是「日期列里出现 46233」的源头
- CSV 的每个单元格到接收方都是**文本**。这与字符编码问题是两个不同的层

## 9. 文本被强制变成日期或数字的事故

对输入的字符串不加保留地强制转换的实测 (Excel，2026 年当下):

| 输入 | 结果类型 | 保存的值 | 还原后的日期 | 屏幕显示 |
|---|---|---|---|---|
| `MAR1` | 数字 | 46082 | 2026-03-01 | 01-Mar |
| `SEPT2` | 数字 | 46267 | 2026-09-02 | 02-Sep |
| `12-Jan` | 数字 | 46034 | 2026-01-12 | 12-Jan |
| `1-3` | 数字 | 46025 | 2026-01-03 | (本地日期格式) |
| `3/4` | 数字 | 46085 | 2026-03-04 | (本地日期格式) |
| `1/2/3` | 数字 | 37623 | 2003-01-02 | 2003-01-02 |
| `007` | 数字 | 7 | — | 7 |
| `1E5` | 数字 | 100000 | — | 1.00E+05 |
| `A-001` | 字符串 | A-001 | — | A-001 |
| `0.1.2` | 字符串 | 0.1.2 | — | 0.1.2 |

- **没有年份的输入会被填入「当前年份」。** 明年再打开同一个文件重新输入，得到的是另一个值
- 只要含有一个连字符或斜杠的短代码，都处在危险区间
- 丢掉的信息回不来。`007` 的前导零、`1E5` 的记法、`1-3` 的原文全部消失
- 存活的条件很明确: **有两个点 (`0.1.2`) 或以字母开头 (`A-001`)**，强制转换就不会发生
- 防御必须在输入之前。把列格式设成文本，前面加一个单引号，或在导入向导里把该列指定为文本
- 转换之后没有撤销的办法，只能重新取一份原始数据

```xml
  <xf numFmtId="165" fontId="0" fillId="0" borderId="0" xfId="0" applyNumberFormat="1"/>
</cellXfs>
```

→ **日期单元格和数字单元格唯一的差别就是一个 `s` 属性。** 两者的值都是 `46233`。「这是日期」这条信息不在值里，只在样式里。

日期体系写在 `xl/workbook.xml`:

```xml
<!-- 1900 体系 (默认): 属性根本不存在 -->
<workbookPr defaultThemeVersion="124226"/>

<!-- 1904 体系 -->
<workbookPr date1904="1" defaultThemeVersion="124226"/>
```

## 11. 诊断流程 — 收到的文件用的是哪个体系

按证据强度从高到低尝试。

1. **读容器里的标志 (xlsx 可直接确定)**
   - `unzip -p book.xlsx xl/workbook.xml`，查找 `date1904` 属性
   - 属性不存在或为 `0` 是 1900 体系，为 `1` 是 1904 体系
   - 这是唯一具有确定性的依据
2. **用一行锚点核对**
   - 挑一条你已经知道真实日期的记录
   - 按两种体系各换算一次，看哪一种和真值吻合
   - 一行就能定案
3. **用业务区间筛选 (弱依据)**
   - 看两种解读里哪一种落到业务上不可能出现的年份
   - 两种解读都落在合理区间的情况确实常见。不要单独用它下结论
4. **用间隔指标找出边界以下的值**
   - 如果两种换算的间隔是 **1461 天**而不是 1462 天，那个序列值就在 60 及以下
   - 也就是说那一行落在闰年缺陷的区间里
5. **只有 CSV 而以上都用不上时**
   - 光看数字在原理上无法确定。不要猜，去问发送方
   - 要问清楚: 基准体系、日期列清单、是否含时刻

## 12. 用什么格式交换数据

| 格式 | 自描述 | 需要基准日 | 时区 | 可按文本排序 |
|---|---|---|---|---|
| 序列值 | 否 | 是 | 无 | 仅数字排序 |
| `YYYY-MM-DD` | 是 | 否 | 无 | 可以 |
| `YYYY-MM-DDTHH:MM:SSZ` | 是 | 否 | 自带 | 可以 |
| `MM/DD/YYYY` | 部分 | 否 | 无 | 不可以 |
| Unix 秒 | 否 | 是 (固定) | UTC | 仅数字排序 |

**建议: 系统之间用 ISO 8601 字符串交换。** 代价已经实测过。

- 20 万行一列的体积: 序列值 1,200,000 字节 → ISO 8601 2,200,000 字节 (**+83.3%**)
- 解析耗时: 序列值 0.2127 秒 vs ISO 8601 **0.0554 秒**。**字符串反而快 3.8 倍**
- 也就是说代价**只有体积**，速度反而占优。「数字更轻所以更快」的直觉在这里是错的
- ISO 8601 也解决不了的: 没有偏移量的值仍然不知道属于哪个时区。但那份含糊变得**看得见**了，这才是相对裸数字的真正收益
- 如果时刻本身有意义，就把偏移量 (`Z` 或 `+08:00`) 一并写上
- 把表格发给最终使用者是例外。那时用 xlsx 发送，并把格式一起带上

## 13. 按场景的判断表

| 场景 | 风险 | 应对 |
|---|---|---|
| 数据里有 1900-03-01 之前的日期 | 差一天。星期和期间计算全部出错 | 使用修正版转换，并单独检查、报告 60 及以下的序列值 |
| 相减两个日期 (跨越边界) | 结果比实际多 1 天 | 跨边界的区间用真实日历重算 |
| 含有时刻 | 用截断还原秒数会让一半的行慢一秒 | 小数部分必须舍入；比较到秒先转成整数 |
| 反复累加时刻 | 会留下累积误差 (实测 −4.4e-16) | 用整数秒累加，最后再一次性转成小数 |
| 收到了不同体系的文件 | 差四年零一天 (1462 天) | 检查 `workbook.xml` 里的 `date1904`，再核对一行锚点 |
| 更改文件的日期体系 | 保存的数字不变，只有日期移动 1462 天 | 已经有数据的文件不要改体系 |
| 导出成 CSV | 没设格式的列会漏出序列值 | 导出前确认日期列的格式；与接收方约定格式 |
| 接收 CSV | 无从判断数字列是不是日期 | 用文档拿到列含义。46000 附近的整数要怀疑是日期 |
| 输入或粘贴代码、料号 | 被强制变成日期或数字，且不可逆 | 输入前把列设为文本；导入时指定列类型 |
| 处理没有年份的短代码 | 会被填入当前年份，每年数值都变 | 固定为文本，不要重新输入 |
| 处理 1899 年之前的日期 | 根本没有序列值，只能留作字符串 | 放弃日期类型，改用 ISO 字符串列管理 |
| 格式丢失只看得到数字 | 容易误判成数据损坏 | 值是完好的，重新指定格式就能恢复 |

## 14. 检查清单

- [ ] 序列值转换函数里有**针对 60 及以下的分支**
- [ ] 遇到序列值 60 会**拒绝或告警**，不会默默放行
- [ ] 转换器是**和真实日历值对照**验证过的 (只做往返测试抓不到)
- [ ] 可能收到 1904 体系文件的路径上有 `date1904` **检查步骤**
- [ ] 把小数部分还原成秒时用**四舍五入** (不是 `int()`、`INT()`)
- [ ] 时刻累加用**整数秒**，最后才转成小数
- [ ] 导出 CSV 前**确认过日期列的格式**
- [ ] 接收 CSV 时把 46000 附近的整数列**当作日期候选来检查**
- [ ] 系统间交换规范里写明了 **ISO 8601 和偏移量规则**
- [ ] 代码、料号列在导入时**指定为文本**
- [ ] **数过一次**数据里有多少行早于 1900-03-01
- [ ] 不把只是丢了格式的状态**误判为损坏**

## 15. 不要做的事

- 把基准日固定成 1899-12-30 一个 — 序列值 60 及以下全部差一天
- 只凭往返测试就信任转换器 — 错误的实现也 100% 通过
- 用 `int()` 截断小数部分 — 86400 秒里有 43136 秒会差一秒
- 更改已有数据文件的日期体系 — 数字原地不动，日期却会移动
- 因为「数字更轻更快」而选择序列值交换 — 实测解析是 ISO 字符串更快
- 不设列格式就粘贴代码和料号 — 转换之后无法恢复
- 只看序列值就推断体系 — 两种解读都合理的情况很常见
- 把看起来是数字的日期列判定为损坏并重新索要原文件 — 指定格式即可
