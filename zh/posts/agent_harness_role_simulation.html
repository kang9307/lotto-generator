用智能体模仿一个组织能走到哪一步

上下文隔离与并行化换来了什么，交接损耗、协调成本与验证独立性又要拿走什么

2026年8月23日 IT/技术

引言：把一整间办公室开起来

把一个智能体用得还算顺手之后，下一个念头往往落在同一个地方。一个能跑，五个是不是也能跑。五个能跑，那把开发、设计、产品各安排一位坐好，让它们自己来回传递，是不是就行了。今年出现的这些框架，正是把这个白日梦做成了产品。最近公开的其中一个，宣称在你自己的电脑上运行分别扮演开发、设计、产品经理和销售角色的智能体，让它们互发消息、交接工作。

官方介绍把它们称作「团队成员的自主克隆(autonomous clones of team members)」。这个说法属于该项目，本文不沿用。因为实际发生的并不是复制某个人，而是把若干个各自被指派了角色的执行单元，用一套约定好的接口连起来。所以准确的名字是角色分工模拟。名字叫准了，问题也就跟着准了。它不再是「模仿一个人是否成功」，而是「把工作拆成好几份到底划不划算」。

这个问题有意思，是因为答案违反直觉。画组织架构图很容易。难的不是那张图，而是组织原本真正在做的事。人组成的团队，不走文档传递的东西要多得多：隔壁工位飘过来的一句话、靠表情传达的反对、上个月吃过一次亏的记忆，还有意见分歧时该由谁拍板的那种默契。智能体之间一样都没有。递过去的那段文字就是全部。

所以这不是某个工具的使用记。本文要考察的是，用多个智能体模仿一个组织这个想法，有效到什么程度、又在哪里断裂。拆分换来什么、要付出什么、成本以什么形状增长、验证该放在哪里，以及归根结底该把什么算作成功。先把结论摆出来：既不是「越多越好」，也不是「别碰」，而是拆分划算的任务和不划算的任务，分界其实相当清楚。

1. 它到底是个什么东西 - 只讲已确认的范围

先整理引发这篇文章的项目公开陈述的内容。到这里为止是已确认的事实，往后全是围绕这个想法的讨论。

  • 它是包住既有智能体 CLI 的一层框架。它不卖模型，而是架在你已经在用的 CLI 和订阅之上。官网列出十二家支持方，包括 Claude Code、Codex、Grok、Kimi Code、Antigravity、Qwen、Gemini CLI、OpenCode、Crush、Pi、Copilot 与 Cursor
  • 主打本地优先。在默认配置下，代码和密钥被描述为不会离开使用者的电脑
  • 智能体之间互发消息。这些消息标注使用 X25519 / AES-256-GCM 加密
  • 共享知识与个人上下文分开。组织级知识库由每个智能体继承，而个人的代码仓库、笔记、行文风格留在各自机器上
  • 角色挂在可用命令行处理的工作上。举的例子包括 PR 评审、缺陷修复、界面审查、写规格、CRM 管理
  • 许可与价格。本地开源版为 MIT 免费，另有每月 39 美元的 Pro 与每席位每月 149 美元的 Teams 方案

结构上值得注意的一点是，这是一层卖执行与协调、而不卖模型的东西。这一层在过去一年里明显变厚了。用隔离来解并行执行的工具、管理任务队列的守护进程、给智能体挂角色的框架，都在从不同角度戳同一个问题。这个问题只有一个名字：超出单个智能体承载范围的工作，该怎么分。

2. 为什么不用一个，非要拆成多个

「多个更好」这句话通常被囫囵说出来。但拆分实际换来的好处是四样互不相同的东西，不做区分就会开出错误的处方：明明卡在窗口大小却去加并行度，明明是时间不够却在打磨角色提示词。

2.1 上下文隔离 - 每个都有自己的窗口

这是最实在的一项。用一个智能体做长任务，窗口里会不断堆积无关内容。第三步需要的只是第二步的结论，可第二步翻过的文件清单和失败的尝试全都还在。Anthropic 在介绍自家研究系统时写道，子智能体「通过带着各自的上下文窗口并行运作来促成压缩」，同一篇文章里还把它们称作智能过滤器。也就是说，拆开的理由从来不只是速度。

2.2 按角色写提示词 - 指令会变短

把所有指令塞进一个窗口，相互矛盾的规则就会堆起来。当「写得简洁些」和「每条都要给出处」出现在同一段提示词里，模型每一轮都会倒向不同的一边。拆开角色，各自的指令就短了，也不再打架。这与其说是性能问题，不如说是指令设计问题。一个人能维护的规则集大小同样有上限。

2.3 并行化 - 买的是墙上时钟的时间

五个真正互不相干的任务同时跑，等待会变少。但这和 CPU 并行性质不同，它更接近把等待时间叠起来，而不是分配算力。如果接收并判定结果的只有一个人，那么无论扇出铺得多宽，最后仍会重新收窄成串行。这一点在并行编码智能体到底在哪里划算里另行讨论过。

2.4 验证分离 - 做的人不看

这是价值最大的理由，也是最容易只剩仪式感的一项。让做出结果的智能体去评审自己的产出，它通常会放行。换另一个智能体来看，方向是对的。问题在于那个「另一个」究竟有多不一样，这一点留到第六节单独看。

拆分的维度实际换来的东西相应要付的代价
上下文隔离避免窗口被污染、绕开窗口上限每次交接都得摘要，于是产生交接损耗
按角色写提示词消除指令冲突、规则易于维护掉进角色缝隙里的活没人做
并行化缩短墙上时钟时间调用次数上升，判定瓶颈后移
验证分离跳出生成方自身的偏见没有独立性就只剩形式

3. 一拆就会新生出来的问题

这是本文的核心。拆分的代价常被笼统说成「管理变麻烦」，实际上会分别冒出四种性质不同的故障。

3.1 交接损耗 - 一摘要，信息就少了

组织架构图上的箭头不是免费的。智能体 A 递给 B 的，不是 A 看到的全部，而是 A 摘要出的结论。从那份摘要里掉下去的东西永远是同几样：为什么得出这个结论、排除了什么、假定了哪些前提。B 只收到结论，然后在上面垒自己的工作。A 的假定错了这件事，B 没有任何办法知道。

Cognition 把这个问题钉成了两条原则。第一条是「共享上下文，而且要共享智能体的完整轨迹，而不只是单条消息」。意思是把过程而不只是结论递过去，可这没有听上去那么容易。因为把完整轨迹原样递过去，当初隔离上下文的理由就没了。2.1 拿到的东西和 3.1 失去的东西，争夺的正是同一份资源。

3.2 隐含决定的冲突

Cognition 的第二条原则是「行动携带隐含决定，相互冲突的决定会带来糟糕的结果」。每个智能体在干活时做出的无数细小选择 - 采用哪套命名约定、走哪种风格、接受哪一种解读 - 全都是决定。可这些决定不会被显式记录，它们溶进了产出物里。两个看不见彼此工作的智能体各自做出局部合理的选择，结果就是单看都说得通、合起来却对不上的产物。这不是模型不够聪明造成的，而是信息结构本身带来的。

3.3 错误累积

把步骤串成一条线，各步的成功率就会相乘。单步正确率九成五，走完五步大约是七成七。真实的智能体流水线各步并不独立，这个算式不能照搬，但方向是对的。而且还附带一个更难缠的性质：上一步的错误在下一步不会被当成错误，而会被当成前提。后面的智能体老老实实地处理错误的输入，把错误的结果打磨得很顺滑。这正是人回头看时特别难定位问题的原因。

3.4 最终由谁拍板

人组成的组织里有决策者。意见分歧时由谁来断，是事先定好的；没定好的组织，会议就开不完。在智能体的编排里，这个位置常常空着。就算放了一个编排者，它做的多半是分派任务而不是裁决。没有裁决规则，实际结果就是最后写的那个智能体赢。这是事故，不是设计。

4. 组织隐喻在哪里断裂

「AI 办公室」这个隐喻能让人快速理解。麻烦在于它在完成这项工作之后不肯离场，会让本来不成立的东西看上去也像成立。

在人的团队里，文档是辅助通道。规格里没写的当面问一句就行，甚至常常在开口之前就从对方表情上读出来了。新人走错方向时，没人下指令也会有人拦一下。在智能体之间，文档是唯一通道。规格里没有的就等于不存在，走错方向也没人来拦。隐喻在这里第一次断裂。

第二处断裂是反问。人碰到奇怪的指令会反问一句：「这个真的是要这么做吗？」这一句能省下一整天的损失。智能体面对奇怪的指令，多半会把它执行得像模像样。你可以让它学会反问，但把反问频率调高，自动化的价值就被吃掉；调低，静默失败就变多。这杆秤不会自己找平。

第三处是责任。在人的团队里，角色既是分工也是分责。智能体的角色只有分工，责任无处附着。所以实际情况是角色数越多，一个人要背的责任量不减反增，因为五个产出的东西仍然要由一个人来核。

即便如此，隐喻确实有仍然成立的部分。整理如下。

  • 成立 - 作为把角色边界写清楚的思考框架。把谁负责什么写下来，指令冲突会减少
  • 成立 - 作为暴露交接点的装置。定下在哪里移交，就能在那个位置挂上验证
  • 成立 - 作为产出格式的标准化。每个角色的产物形状固定下来，下一环就稳了
  • 断裂 - 默会知识的共享。没递过去的东西就等于不存在
  • 断裂 - 自发的异议。没有谁会说「我觉得这样不对」
  • 断裂 - 责任归属。结果上不会附着名字
  • 断裂 - 掉在缝隙里的活。人的团队里总有人顺手捡起来，这里没人做

5. 调用是乘着涨的 - 成本结构

智能体一多成本怎么涨，与其凭感觉估，不如看结构。会涨的地方有三处。

  • 智能体数量。起五个，至少就有五次执行开始
  • 往返次数。每个智能体调工具、拿结果、再思考的往返，各自都要好几轮
  • 重新装载的上下文。每次交接都得把对方能看懂的背景重新铺一遍。这部分涨得特别安静

有一些公开数字可以参考。Anthropic 在介绍自家研究系统时披露，智能体大约消耗普通对话四倍的令牌，多智能体系统大约十五倍。同一篇文章还说，以 Claude Opus 4 作主导智能体、Sonnet 4 作子智能体的多智能体配置，在其内部研究评测中比单体 Claude Opus 4 高出百分之九十点二。这两个数字都出自 Anthropic 自家系统与自家评测标准，无法原样搬到别的任务或别的模型上。

真正要紧的是第三句。同一篇文章写道，仅令牌用量一项就解释了性能差异中约百分之八十的方差。这一句会逼你回头重读那个百分之九十点二，因为它意味着多智能体胜出的那部分里，相当一部分可能来自算得更多而非架构本身。所以在实务中比较配置时，如果不把令牌预算拉齐，比较的就不是架构而是预算。

那么什么时候才值这个价。三个条件要同时成立。

  • 结果的价值远高于令牌开销时。必须广撒网才出得来答案的调研型任务是典型代表
  • 并行省下的时间真的被用掉时。如果结果堆进队列、第二天才审，那就不算买到了时间
  • 失败可以廉价丢弃时。五个里扔掉四个也无所谓，扇出才立得住

协调成本如何一点点吃掉收益，本身在编排税 - 管理多个AI智能体的隐藏成本里另有整理。

6. 验证该放在哪里

「我又加了一个验证智能体」这句话让人安心，但那道验证究竟滤掉了什么，得单独掂量。它可以归结为一个问题：验证者是否掌握生成者没有的信息。

只把角色提示词换掉、模型仍是同一个的验证者，对这个问题的回答是否定的。同样的训练分布、同样的先验、同样的盲区。生成方判为合理的，验证方通常也判为合理。在格式没问题、内容却是错的那一类错误上，这个局限尤其明显。一份回答里机器能验证与不能验证的分界线，在LLM回答中机器能验证的与不能验证的里另行讨论过。

验证放置的位置独立性能抓到的抓不到的
机器校验(测试、编译、模式、静态检查)高规范违例、断掉的引用、回归需求本身就是错的情况
外部查询(文档、API、真实数据比对)高事实错误、过时信息无从查证的判断
换一个模型来验中某一模型特有的想当然共同盲区、含糊的需求
同一模型，只换角色低明显的遗漏、格式错误大部分听起来合理的错答
人高违背语境、方向本身就错量一大就成了瓶颈

由此得出的实务规则很简单。至少给验证接上一路来自模型之外的信号。测试运行结果也好，模式校验也好，真实数据查询也好，都行。一个这样的信号都没有的验证环节不是验证，而是第二次生成，而第二次生成只会把成本翻倍。

7. 适合拆的任务和不适合拆的任务

把前面的讨论折进任务性质里，剩下三个条件：能不能分解、能不能验证、失败能不能廉价丢弃。三项都立得住，拆开就划算；有一项塌了，通常就是亏。

任务分解验证判定
按同一标准更新多语言版本文档可以 - 各语言独立可以 - 结构比对拆开划算
给互不重叠的模块补测试可以 - 按文件可以 - 运行结果拆开划算
广泛翻查大量来源的调研可以 - 按问题部分 - 来源比对划算，但需要一个汇总环节
链接、模式与规范审查可以 - 按条目可以 - 机器判定拆开划算
结构化数据的抽取与整理可以 - 按记录可以 - 模式校验拆开划算
架构与设计决策困难 - 判断是一整块困难 - 没有标准答案用一个更好
原因无法收敛的缺陷排查困难 - 前一个判断即是前提可以 - 能否复现用一个更好
语气必须统一的长文困难 - 文风作用于全局困难 - 主观用一个更好
优先级协调与谈判困难 - 标准属于人困难 - 只能事后看由人来做

失败长什么样，也已经有公开的案例。Anthropic 写道，早期出现过「为一个简单查询起五十个子智能体」的情况，同时也披露指令含糊时子智能体之间会重复做同一件事。这两点都是把分解工具用在分解并不成立的地方时会出现的典型症状。

8. 该把什么算作成功

接了多个智能体的配置，评估格外棘手。单个智能体还能顺着步骤看是在哪里出的错，一旦多个走了不同路径，这个办法就失效了。Anthropic 也点到了同一处：智能体可能沿着彼此完全不同、却都成立的路径抵达目标，因此既然事先并不知道正确的步骤是什么，逐步验证就行不通。它把幻觉答案、系统性失败、以及来源选择上的细微偏差列为自动评测漏掉的东西，并写明人工测试是必要的。

由此可以引出四条评估设计原则。

  • 按最终产物打分，而不是按过程。路径多样不是缺陷，评分标准被绑死在某条路径上才是
  • 固定一套回归集。每次都换新题去测，就分不清是变好了还是题变简单了
  • 把成本写进和性能同一张表。不这么做，令牌花得多的那个配置永远赢。性能比较正是在这里悄悄变成预算比较
  • 少量样本由人亲自读。从自动评分放行的结果里抽样，用眼睛看一遍。自动评分抓不到的类型，往往正是设计自动评分的人没想到的类型

还有一点。最好不要把成功定义成「有没有在无人参与下跑完」。用这个标准，留下的只会是简单到不需要人介入的任务，而真正有价值的任务反倒被归进自动化失败。人在最后花五分钟看一眼再放行的结构，通常好过完全没人看的结构。

9. 另一边 - 一个就够的情形

眼下的风向偏向「多个」，所以反面也用同样的分量写下来。Cognition 对大多数任务推荐上下文不断裂的单线程智能体。对于逼近窗口上限的长任务，它建议另设一个把历史压缩成要点、决定与事件的模型，同时承认把压缩做对并不容易、需要相当的投入。那篇文章的结论是，以当下模型的能力，很难在规模上信赖跨智能体的通信与共享决策。

单体配置真正占优的地方是这些。

  • 交接损耗为零。根本没有交接这个动作，也就不会在摘要中漏掉信息
  • 只有一条轨迹。出问题时可以按顺序读出是在哪里偏的，而顺序阅读本来就是人擅长的事
  • 隐含决定不会冲突。前面定下的命名约定，后面照样在用
  • 成本可预测。没有会乘着涨的位置

所以在增加之前，先问三件事更合算。眼下卡住的到底是什么。是窗口不够、是指令互相打架，还是单纯时间不够，处方各不相同。窗口不够的话，先去修检索、压缩和工具设计更便宜。指令冲突的话，把提示词理顺往往就结束了。三者都不是，而是真正互相独立的活确实堆了好几件，那才是该拆的时候。

10. 照着一个人来造这件事

这一类产品一旦用上「团队成员的克隆」这种说法，技术之外的问题就跟着来了。简短说一下。这不是针对某个产品或某个人，而是任何组织在引入这种形态之前都该先理清的条目。

  • 同意。把某人的工作方式、行文风格、判断习惯学下来并长期运行，本人是否同意，事后能否撤回
  • 归属。这套配置做出来的产物记在谁名下。绩效评估和责任追溯都挂在这一条上
  • 误认。用于对外沟通时，对方是否可能以为自己在和人打交道。销售、客户对接这类朝外的角色，风险尤其大
  • 之后。那个人离开团队之后，学到的画像和个人上下文该怎么处理

本地运行和加密确实能减少一部分数据外流的问题。但同意与归属不是靠密码学能解的。它们是约定而非技术决定，而且属于引入之前没写进文档、之后就没法再定的那一类。

没能确认的部分

  • 引发本文的这个框架，并没有在此处安装运行过。因此对其真实运行质量、成功率与体感速度不作任何主张。本文第一节整理的是官网与话题摘要中写明的内容
  • 支持列表上的十二种 CLI 各自实际对接到什么程度，没能确认
  • 消息加密只核对了标注的方式，没有审阅实现
  • 付费方案上写的资源规格，在实际使用中表现为怎样的性能，没能确认
  • 文中引用的令牌倍数与性能数字，全部是发布方自家系统、自家评测的口径。任务类型或模型一变，就无法原样迁移
  • 引发本文的话题在查看时是一分、一条评论，不足以据此判断社区反响的规模

结语：关键是接口，不是组织架构图

用多个智能体去模仿一个组织，与其说是潮流，不如说接近必然。单个智能体能承载的范围有上限，要越过这个上限就总得设法拆。只是一拆开，组织运作本来就带着的那些问题会原封不动跟过来。信息在传递中漏掉，各自的假定彼此错开，最后由谁决定变得模糊。人的团队靠察言观色、靠对话、靠责任把这些补上，而智能体这三样一样都没有。

所以决定这个想法成败的是接口，不是组织架构图。把什么递过去、什么不递，递过去的东西用什么来验，两种答案打架时以什么为准定下来，远比决定要分几个角色重要。如果要开始，建议按这个顺序。

  • 第一步 - 先用一个走完全程。没有基准线就往上加，就没办法衡量到底有没有变好
  • 第二步 - 给卡住的地方起个名字。是窗口、是指令冲突，还是时间。原因不同，处方不同
  • 第三步 - 拆之前先用便宜的办法。靠检索、压缩和工具设计就能解决的情况比想象中多
  • 第四步 - 要拆就先写接口。比角色名字更该先定的，是要递交的条目清单
  • 第五步 - 把验证放到生成者之外。至少接上一路来自模型之外的信号
  • 第六步 - 把成本写在性能旁边。漏掉这一步，留下的就不是判断而是印象

最后把本文没有做的事说清楚。这里没有关于哪个框架更好的裁定。工具选择在这个问题上是最后才登场的变量。把任何工具对准一件分解本身就不成立的活，结果都一样。
