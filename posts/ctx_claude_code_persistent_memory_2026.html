CTX 분석 - Claude Code 세션 간 기억을 잇는 지속 메모리 도구

AI 코딩 에이전트가 세션이 끝날 때마다 맥락을 잃는 문제, CTX는 검색 기반 메모리로 이를 어떻게 메우는가

2026-07-02 개발/인프라

서론: 매번 처음부터 설명해야 하는 피로

Claude Code로 하루 종일 작업하다 보면 반복되는 장면이 있다. 새 세션을 열면 지난 세션에서 무엇을 왜 결정했는지, 어떤 파일을 왜 고쳤는지 처음부터 다시 설명해야 한다. 이 글을 쓰는 지금도 그렇다. 이 블로그를 운영하는 계정 자체가 MEMORY.md라는 파일에 지난 대화의 요약을 기록해 다음 세션에서 불러오는 방식으로 굴러간다. 프로젝트가 수십 개로 늘어나면 이 파일 하나로는 버겁다는 것을 실무에서 매일 체감한다.

CTX는 이 문제를 정면으로 겨냥한 오픈소스 도구다. 2026년 7월 초 기준 GeekNews(news.hada.io)에 소개된 시점에 누적 사용자 98명, 월간 PyPI 다운로드 약 2,726건 규모의 작은 프로젝트지만, 다루는 문제는 AI 코딩 에이전트를 매일 쓰는 사람이라면 누구나 겪는 것이다. 이 글은 CTX가 실제로 무엇을 하는 도구인지, Claude Code가 이미 갖춘 CLAUDE.md·Auto Memory와 무엇이 다른지, MCP 메모리 서버와는 어떻게 구분되는지를 본인 관점에서 정리한다.

1. 세션 메모리가 왜 필요한가

1.1 컨텍스트 윈도는 세션이 끝나면 사라진다

Claude Code를 비롯한 대부분의 AI 코딩 에이전트는 하나의 세션 안에서만 대화 맥락을 유지한다. 세션이 끝나거나 컨텍스트 윈도가 가득 차 압축(compaction)되면, 그 안에 있던 미세한 결정들 - 왜 이 함수를 이렇게 짰는지, 왜 이 라이브러리를 버렸는지 - 은 별도로 기록해두지 않는 한 사라진다. 다음 세션은 사실상 기억상실 상태에서 시작한다.

1.2 반복 설명의 실제 비용

이 비용은 단순히 귀찮음의 문제가 아니다. 매 세션 초반에 프로젝트 구조·컨벤션·최근 이슈를 다시 설명하는 데 드는 토큰과 시간은, 실제 작업에 쓰일 수 있었던 자원이다. 팀 단위로 보면 이 반복은 사람 사이의 인수인계 문서가 없는 것과 비슷한 비효율을 만든다. CTX 제작자가 "세션이 끊기면 이전 결정과 맥락을 잃는 것이 낭비"라고 지적한 지점이 정확히 여기다.

1.3 연속성이 주는 실질 이득

반대로 세션 간 연속성이 확보되면, 에이전트는 "이 프로젝트에서는 왜 이 패턴을 쓰는지"를 매번 재추론하지 않고 곧바로 다음 작업으로 넘어갈 수 있다. 특히 몇 주에 걸쳐 진행되는 리팩토링이나, 여러 세션에 걸친 디버깅처럼 장기 과제에서 이 차이는 누적된다.

2. CTX는 어떻게 동작하는가

2.1 훅 기반 자동 연결

CTX(패키지명 ctx-retriever)는 pip install ctx-retriever로 설치하며, Claude Code의 훅(hook) 시스템에 자동으로 연결된다. UserPromptSubmit 훅이 사용자 질의를 포착하고, PostToolUse 훅이 세션 중 파일 변경을 추적한 뒤, 세션이 끝나면 자동으로 인덱싱한다. 별도 서버나 클라우드 계정 없이 로컬에서 전부 처리된다.

2.2 검색 방식 - BM25 + 벡터 하이브리드

공개된 자료에 따르면 CTX는 키워드 기반 BM25와 벡터 임베딩을 절반씩(α=0.5) 섞은 하이브리드 검색을 쓴다. 질의는 심볼 직접 조회(EXPLICIT_SYMBOL), 개념 키워드 매칭(SEMANTIC_CONCEPT), 임포트 그래프를 타고 들어가는 의존성 탐색(IMPLICIT_CONTEXT), 최근 변경 이력 조회(TEMPORAL_HISTORY) 네 갈래로 분류되어 각기 다른 파이프라인으로 처리된다. 이 구조 자체가 "대화를 통째로 요약해 저장"하는 방식이 아니라 "필요한 조각만 찾아 오는" 검색 엔진에 가깝다는 것을 보여준다.

2.3 별도 LLM 호출이 없다는 점의 의미

CTX는 검색 과정에서 별도의 LLM을 호출하지 않는다고 밝히고 있다. 즉 요약이나 재정리를 위해 추가 API 비용이 들지 않고, 순수 알고리즘 연산이라 지연이 수십~수백 밀리초 단위로 짧다는 것이 특징이다. 이는 메모리 조회 자체가 비용·지연 항목이 되는 다른 접근과 비교했을 때 실무적으로 눈에 띄는 설계 선택이다.

3. CLAUDE.md·Auto Memory와의 관계

3.1 Claude Code의 기본 메모리 체계

Claude Code는 이미 두 가지 메모리 경로를 공식 제공한다. 하나는 사람이 직접 작성하는 CLAUDE.md로, 프로젝트 규칙·빌드 명령·코딩 컨벤션처럼 매번 재설명하기 귀찮은 내용을 정적으로 적어두는 파일이다. 세션 시작 시 현재 디렉터리부터 상위로 올라가며 발견되는 CLAUDE.md·CLAUDE.local.md를 읽어 컨텍스트에 주입한다. 다른 하나는 Auto Memory로, 모델이 작업 중 스스로 유용하다고 판단한 내용(빌드 명령, 디버깅 통찰, 아키텍처 메모, 사용자 교정 사항)을 MEMORY.md 계열 파일에 기록해두는 기능이다.

3.2 "적어두기"와 "찾아오기"의 차이

본인이 CTX 자료를 읽으며 가장 명확하게 느낀 차이는 이것이다. CLAUDE.md와 Auto Memory는 사람이 편집하거나 모델이 요약해 적어두는 정적 파일 방식이다. 세션 시작 시 그 파일 전체(또는 상단 일부)가 통째로 컨텍스트에 들어간다. 반면 CTX는 대화 로그와 코드베이스를 미리 인덱싱해두고, 질의가 들어올 때마다 관련성 높은 조각만 검색해 찾아오는 방식이다. 전자는 사람이 관리 부담을 지고, 후자는 검색 정확도에 품질이 좌우된다는 점에서 트레이드오프가 다르다.

3.3 경쟁이 아니라 계층일 수 있다

둘은 대체재라기보다 다른 층위로 보는 것이 더 정확하다는 것이 본인 판단이다. CLAUDE.md는 "항상 알아야 할 규칙"을 명시적으로 고정하는 데 강하고, CTX 같은 검색 기반 메모리는 "필요할 때만 꺼내 쓰는 과거 세션의 세부 사항"을 다루는 데 강하다. 실제로 이 블로그 운영 방식도 최상위 규칙은 MEMORY.md에, 프로젝트별 세부 이력은 각 프로젝트 문서에 나눠 관리하는 구조인데, 이는 CTX가 자동화하려는 문제와 본질적으로 같은 방향이다.

4. MCP 메모리 서버와의 비교

4.1 MCP 메모리 서버는 프로토콜 계층

MCP(Model Context Protocol)의 공식 참조 구현 중 하나인 메모리 서버는 create_entity, search_memories 같은 표준화된 도구를 통해 지식을 지식 그래프 형태로 저장한다. 핵심은 "표준화"에 있다. MCP를 지원하는 모든 클라이언트(Claude Desktop, Claude Code, Cursor 등)가 동일한 프로토콜로 같은 메모리 서버에 접근할 수 있어, 도구 간 이식성이 크다.

4.2 CTX는 로컬 검색 엔진에 가깝다

이에 비해 CTX는 MCP 프로토콜을 쓰지 않고 Claude Code 훅에 직접 연결되는 로컬 도구다. 저장 구조도 지식 그래프가 아니라 BM25·벡터 인덱스와 임포트 그래프 기반의 코드 구조 검색에 특화되어 있다. 즉 MCP 메모리 서버가 "범용 사실·선호 저장소를 여러 도구가 공유"하는 것을 목표로 한다면, CTX는 "이 코드베이스와 이 세션들에 최적화된 검색"을 목표로 한다는 점에서 설계 철학이 다르다.

4.3 실무에서의 선택 기준

여러 AI 도구(Claude Code, Cursor 등)를 넘나들며 하나의 메모리를 공유하고 싶다면 MCP 메모리 서버 쪽이 구조적으로 맞다. 반면 Claude Code 단일 도구 안에서, 코드 심볼·의존성 관계를 정확히 짚어주는 검색이 필요하다면 CTX처럼 코드 구조에 특화된 검색 엔진이 더 실질적인 이득을 준다. 두 도구를 함께 쓰지 못할 이유도 없다 - 목적이 겹치지 않기 때문이다.

5. 실무 활용 시나리오

5.1 잘 맞는 경우

여러 세션에 걸쳐 진행되는 리팩토링, 규모가 큰 단일 리포지토리에서 심볼·의존성을 반복 조회해야 하는 작업, "지난주에 왜 이 라이브러리를 뺐더라" 같은 결정 이력을 다시 찾아야 하는 상황에서 CTX 같은 검색 기반 메모리는 확실한 시간 절약을 준다. 특히 별도 LLM 호출 없이 로컬에서 처리된다는 점은 API 비용에 민감한 개인·소규모 팀에 매력적이다.

5.2 신중해야 할 경우

공개된 벤치마크를 보면 CTX는 자연어 위주 질의보다 코드 심볼·키워드가 섞인 질의에서 강점을 보이며, 순수 자연어 검색에서는 BM25 단독보다 리콜이 낮게 나오는 구간이 있다고 명시되어 있다. 또한 2,000개 파일을 넘는 대형 코드베이스는 자동으로 인덱싱 대상에서 제외되고, 사전 인덱싱 이력이 없는 낯선 프로젝트에서는 휴리스틱 심볼 추출 품질이 떨어진다는 한계도 공개되어 있다. 무엇보다 누적 사용자 98명 규모의 초기 단계 오픈소스라는 점은 장기 유지보수·보안 검토 측면에서 프로덕션 도입 전 신중한 검토가 필요하다는 뜻이다.

5.3 도입 전 확인할 것

본인이 권하는 절차는 명확하다. 먼저 CLAUDE.md에 프로젝트 핵심 규칙이 이미 잘 정리되어 있는지 점검하고, 그것으로 부족한 "세션을 넘나드는 세부 결정 이력 검색"이 실제로 얼마나 자주 필요한지 스스로 관찰한다. 그 빈도가 높다면 CTX를 사이드 프로젝트에 먼저 설치해 본인 코드베이스에서 체감 효과를 확인한 뒤, 팀 전체 도입 여부를 판단하는 순서가 안전하다.

결론: 메모리는 이제 AI 코딩 워크플로의 인프라다

CTX 자체는 아직 사용자 98명, 월간 다운로드 2,726건 규모의 작은 프로젝트다(2026년 7월 기준). 하지만 이 도구가 겨냥하는 문제 - AI 코딩 에이전트가 세션마다 기억을 잃는다는 것 - 는 결코 작지 않다. Claude Code가 CLAUDE.md와 Auto Memory로 이미 이 문제를 부분적으로 풀고 있고, MCP 메모리 서버가 도구 간 공유 메모리라는 다른 축을 제공하는 지금, CTX는 "코드베이스 검색에 특화된 세 번째 층"으로 자리를 잡으려 하고 있다. 세 접근 모두 완결된 해법은 아니며, 각자의 강점 영역이 다르다는 점을 이해하고 본인 워크플로에 맞게 조합하는 것이 지금 시점에서 가장 현실적인 답이라고 본다. AI 코딩 에이전트를 매일 쓰는 개발자라면, 메모리 전략을 더 이상 "선택 사항"이 아니라 CI 파이프라인처럼 기본 인프라로 다뤄야 할 때가 됐다.
