Where Git Slows Down at Scale - Depth, Width and Size Are Not the Same Problem

What object storage and delta compression assume, where those assumptions break, and what each way of downloading less gives up in return

Aug 28, 2026 Dev & Infra

Introduction: A repository does not get heavy in only one way

Cloning onto a fresh machine takes twenty minutes. A single git status burns a few seconds. The symptoms look alike, but the cause can sit in an entirely different place, which is why lifting someone else remedy usually does nothing for you.

There is a reason the topic resurfaced. In August 2026 Cursor published Continuity, a redesign of the storage layer under its Git hosting. By the company account, instead of treating the local Git repository as the source of truth it puts a write-ahead log in S3-compatible object storage in that role, and treats the Git repository on local NVMe as a cache that can be rebuilt at any time. Push ordering is linearised through atomic compare-and-swap on the object store. The same post states figures for pushes per second, read scaling with replicas taken up to one hundred, and replica consistency-check latency. Those are numbers the company measured and published for its own environment, and the post does not spell out hardware or deployment conditions. That is why this article does not use them as performance evidence.

That is as far as the product goes. The interesting part is the problem they were aiming at. Why is hosting Git at scale hard, and why do one enormous repository and a great many tiny ones stress a system in opposite directions? The answer lives less in any company architecture than in what Git assumed when it was designed. What follows traces that assumption and then walks through the places it breaks. If tooling is what you are after, the guide to Git history commands sits well next to this; for the hosting landscape, see the analysis of the Cursor Git forge announcement.

1. What Git actually stores - four object types and content addressing

If you picture Git as a list of diffs, half of that picture is wrong. Git stores snapshots, not diffs. And the unit of storage is not the file but the object.

  • blob — file content only. No name, no permissions, no path.
  • tree — the directory equivalent. It lists mode, type, name and the hash of each entry. Names live here.
  • commit — one top-level tree, parent commits, author and committer information, and a message.
  • tag — an annotated tag pointing at an object, able to carry a message and a signature.

The crucial part is that the name of each object comes out of its content. Git prepends a short header carrying type and length, hashes the whole thing, and uses that hash as the object name. The storage path follows from the hash as well: the first two characters form a directory, the rest is the filename. Content is deflated with zlib on the way in.

Out of this falls the property that surprises people. Identical content is stored once per repository. Copy a file into ten directories and there is still one blob. A file untouched across a hundred commits is not stored a hundred times; each commit builds a new tree, but the unchanged subtrees and blobs simply point at the same hashes. There is no deduplication machinery. The name is the content, so duplicates never form in the first place.

The design also charges a quiet fee. Because the name is the content, changing the content changes the name. A commit contains the hashes of its parents, so editing anything in the past renames every commit that follows, in a chain. The danger in rewriting history, covered further down, is not a policy stance but a direct consequence of this storage shape.

2. Packfiles and delta compression - what gets cheaper and what gets dearer

An object living as its own file is called a loose object. Easy to reason about, bad to keep. Add one line to a 22KB file and commit, and you get another roughly 22KB object with nearly identical content, each compressed separately and each taking its own space.

So Git bundles objects into a packfile when enough of them pile up, when you run git gc, or when you push. Inside the pack, similar objects get delta compressed. In the example above the new version is stored whole and the previous one shrinks to the few bytes that differ. In the Git Book example a 22,054-byte object is stored in full while the 22,044-byte one collapses to a 9-byte delta.

The direction is worth noting. The newest version is kept whole and the past becomes deltas. That matches how people actually read a repository, reaching for recent state most often. The cost is equally clear.

  • Reading a delta-stored object means walking back up the chain to reconstruct it. A plain file read becomes a read plus computation.
  • Git therefore caps delta chain depth. Unbounded chains shrink the disk but slow reads down.
  • Finding a delta base costs CPU and memory in itself. That is why repacking a large repository is heavy.
  • Objects in a pack are laid out by logical adjacency, so an access pattern easily turns into scattered reads on disk.

In short, a packfile trades space and transfer for CPU and random access. For most repositories that trade is overwhelmingly worth it. The trouble is that as a repository grows, both sides of the trade grow with it.

3. Growth means three things - depth, width and size

This is the centre of the article. The single phrase a large repository hides three independent axes. They have different causes, different symptoms and, above all, different remedies.

  • History depth — the accumulated count of commits and their trees. A ten-year-old repository is deep no matter how few files it holds.
  • Tree width — the number of files and directories in a single commit. A repository created yesterday is wide if it holds half a million files.
  • File size — the bulk of individual objects. Whether compression and delta work at all is decided here.
AxisWhat slows downRemedies that usually workWhat the remedy gives up
History depthInitial clone, reachability, revision walking, server negotiationShallow clone, commit-graph caching, splitting history when unavoidableQuestions about the past (log, blame, bisect) stall or trigger refetches
Tree widthCheckout, status, index refresh, branch switchingSparse-checkout, filesystem monitoring, sparse indexTool compatibility, operational complexity, confusion at the edge of scope
File sizeTransfer, disk, packing time, memoryExternalising large files (LFS and similar), not committing them at allA second store to run, authenticate and back up, plus a toolchain dependency

Mix the axes and the diagnosis goes wrong. If cloning is slow, you add --depth 1, and it is still slow, the problem was probably width or size rather than depth. Few commits but four hundred thousand files in each means cutting depth leaves the volume of trees and blobs untouched. Conversely, few files with a heavy clone points first at a large binary buried somewhere in history.

The rule is simple. Pick the one dominant axis, apply only that axis remedy, then measure again. Apply all three at once and you can neither tell what worked nor which change to back out when something breaks.

4. Why large binaries are especially bad

Text source is what Git is best at. It changes a line at a time, compresses well and deltas extremely well. Large binaries sit at exactly the opposite end.

  • Deltas do not take. In an already compressed format such as an image, video or archive, changing a single pixel scrambles the whole byte array. Each commit effectively adds another whole file.
  • Compression does not take either. Compressing compressed data buys almost nothing, and one of the packfile advantages disappears.
  • Memory demand is high. The working space needed to handle one object grows with the file size.
  • Once in, it stays. Deleting it in the next commit leaves the blob reachable from earlier commits. Everyone who clones keeps paying for it.

That last one is the expensive one. A 500MB build artefact committed by accident does not vanish when the next commit removes it. The removal commit merely writes a new tree without that entry, while the earlier commit still points at the blob. Getting it out of the repository for real means rewriting the past, and that bill is covered separately below.

Hence the widespread approach of replacing large assets with pointers kept outside. Git LFS is the familiar example: the commit carries a light pointer file while the real content lives in a separate store. The repository gets lighter. In exchange the extension has to be installed, the separate store needs its own authentication, capacity and backups, and if that store disappears you are left holding pointers. The weight did not vanish; it moved.

5. Three ways to download less - and what each one skips

Most large-repository remedies boil down to fetching less. The three skip different things, and what you defer is usually billed later.

ApproachWhat it does not fetchWhat slows down laterWhat to watch
Shallow clone (--depth)Commits older than the given depthAnything asking about the past. Deepening means fetching more historyIt narrows to a single branch by default
Partial clone (--filter)All blobs, or those above a size, and trees depending on the filterThe on-demand fetch when a missing object is needed. The docs call that fetch slowThe remote must be reachable, and authentication may happen repeatedly
Sparse-checkoutNothing. It only narrows which paths are materialisedThe moment you widen the scope, and any change outside itCone mode is recommended; the non-cone pattern style is discouraged in the docs

The third row is the one people misread. Sparse-checkout is not a download reducer. It uses the skip-worktree bit in the index to leave files unmaterialised, but the objects are already local. To cut transfer as well you have to pair it with partial clone, and then partial clone bill arrives with it. The Git documentation itself states that the command is experimental and its behaviour may change, and adds a caution that the sparse index modifies the index in ways external tools do not understand.

The warning in the partial clone documentation is worth reading as written. Missing objects come from a promisor remote when needed, one fetch per item, which incurs significant overhead and multiple authentication requests when many objects are involved. Offline work becomes weaker, and on a poor network the fast initial clone is paid back as irregular stalls during ordinary work.

6. What the server sees - refs, negotiation and repacking

Looking only from the client hides one axis: the number of references. Branches and tags are tiny entries holding a hash, negligible as storage. The cost shows up elsewhere.

  • Reference advertisement — under the older protocol the server sent every ref it had on each connection. The partial clone documentation notes that a large number of refs can incur significant overhead here.
  • Negotiation — client and server exchange what each already has to decide what to send. More refs and more commits make those round trips heavier.
  • Reachability — knowing which objects are still alive requires walking the graph from the refs. The real cost of gc and repacking lives here.

Protocol v2 addressed the first of those head on. The reference advertisement is omitted unless requested, and ls-refs accepts a ref-prefix so a client can ask only for refs under a prefix. So the old rule of thumb that neglected branches slow down cloning is conditional today. With v2 on both ends the advertisement cost drops sharply, but reachability and repacking still carry the weight.

Operationally, the more interesting fact is that two opposite loads arrive at the same system. At one end sits a single enormous repository whose CI has to be served from hundreds of replicas; at the other, a heap of small repositories produced by automation, used a few times and forgotten. The first demands read scaling, the second demands that the fixed cost per repository approach zero. The problem the Continuity post addresses is exactly that simultaneous demand from both directions. Similar pressure sits behind attempts to rewrite Git as a library.

7. The filesystem and status - work proportional to file count

A repository where git status drags is usually suffering from width, not history. To know whether the working tree diverges from the index, Git has to inspect file state, and that inspection is fundamentally proportional to the number of files. At hundreds of thousands of files, checking becomes work even when nothing has changed.

Git carries two mechanisms for cutting that cost.

  • Untracked cache — it records directory modification times and skips reading a directory whose time has not moved. This only holds if the operating system and filesystem update directory mtime correctly, so Git ships a way to test that beforehand.
  • Filesystem monitor — it asks an external monitor what changed, removing the need to stat every file. Enabled together, the two skip both change detection and the hunt for new files.

Read the caveat the documentation attaches, though. Not every command honours this bit. Some commands get faster, others do not budge. A permanently running monitor process is itself a cost, and on a network filesystem or inside a container the premises can wobble.

8. Monorepo versus many repos is a choice, not an answer

When a repository grows heavy, someone proposes restructuring. But that decision is less a performance fix than a decision about where to move the cost. Neither option reduces the total.

AngleIn a monorepoAcross many repositories
Unit of changeSeveral modules change atomically in one commitChanges split at repository boundaries and humans sequence them
DependenciesOne graph, fewer version alignment problemsPinning and release ordering become standing work
Git loadWidth and ref count concentrate in one place; tooling investment is mandatoryEach repository stays light, but the count itself becomes something to manage
PermissionsPath-level access control has to be solved in a separate layerBoundaries fall out naturally per repository
Build and CIImpact analysis is required, or every change becomes a full buildBuilds are simple, but the place to verify integration disappears
ReleaseOne point identifies the whole stateState is reconstructed from a combination of tags

I will not recommend either side. If you want one criterion, look at the shape of your changes. When a single feature change habitually touches three or more repositories at once, that is a signal the boundaries do not match actual coupling. Merging repositories is only one option there, and redrawing the boundary or stabilising an interface is often the earlier move. Conversely, if each repository deploys independently and knows nothing of the others internals, there is no reason to merge and take on the left column costs. Branching style also shifts in value with team size and release cadence, which the branch strategy guide covers separately.

9. The risk in shrinking history

This section is not a how-to. It records what you need to know before starting.

The property from section 1 sends its bill here. Because object names come from content, editing any past commit changes the hash of every commit after it. The git filter-branch documentation says so explicitly: rewritten history will have different object names for all objects and will not converge with the original branch. The same page warns that the command carries many pitfalls and poor performance, and recommends an alternative such as git filter-repo.

It helps to keep the breakage as a list.

  • Signatures — a commit signature signs that commit content. Change the content and verification fails.
  • Tags — tags pointing at old commits now point outside the new history. Unmoved, they keep the old graph alive as references.
  • Hashes recorded elsewhere — commit hashes in issue trackers, deploy records, documents and lock files all lose their target.
  • Collaborators — the documentation states that others must rebase their work onto the new history or delete and reclone. Risk scales with headcount.
  • Automation — pipelines using commit hashes as cache keys or deployment identifiers quietly start pointing at something else.

So the minimum preconditions look like this. Rehearse on a full copy, preserve the pre-work state separately, close writes while the rewrite runs, and agree in advance on how everyone will refetch afterwards. With no path back, do not start. And the legitimate reasons usually number three: a secret went in, there is a legal obligation to delete, or an asset is embedded that nothing else can reach. If the motive is merely a lighter repository, exhaust the fetch-less remedies above first.

10. What to measure

An impression of slowness cannot pick an axis. What matters is not the total time but which stage consumes it.

  • Clone broken into stages — server-side counting and compressing, transfer, local unpacking and indexing, and the final checkout each point at different causes. Short transfer with a long total means the network is not the problem.
  • Checkout and status — if only these two drag, width dominates.
  • Object composition — what occupies space inside the pack, how many oversized blobs exist, and which paths they came from.
  • Ref and commit counts — the first indicator of whether negotiation is heavy.
  • Working tree file count — the simplest proxy for the width axis.
  • Reproducible conditions — without separating warm and cold caches, comparison does not hold.

Measure the same place again after applying a remedy. Change one thing at a time and write down what you changed and what you measured. Without that record, someone will rediagnose the same problem from scratch six months later.

What could not be verified

  • The measurement conditions behind the throughput and latency figures in the Continuity post (hardware, object size distribution, concurrency level) are not stated there, so they could not be checked. That is why those numbers are not used here as comparison or evidence.
  • The part of that post describing another system design is likewise the publishing side account, and it was not cross-checked against material from the operators of that system.
  • How much the fetch-less remedies actually save varies widely per repository, so no generalisable figure is offered.
  • Which commands benefit from filesystem monitoring and which do not varies by version and platform; check the documentation for the Git version you run.

Wrapping up

Git is an object store that names things by their content. That premise is why duplicates vanish on their own, and why editing the past rewrites everything after it. Packfiles and delta compression are a good trade of space for CPU and random access, but as a repository grows both sides of the trade grow with it.

Three things to take away. First, split the word large into depth, width and size. Remedies differ per axis, and picking the wrong axis improves nothing. Second, fetching less defers cost rather than removing it. Choose knowing when and in what shape the deferred bill returns. Third, rewriting history is a last resort, not something to begin without a path back and an agreement.

Structure follows the same logic. Monorepo and multi-repo are not performance prescriptions but choices about where cost sits, and the basis is not fashion but the actual shape of your changes. Next time someone says the repository is heavy, before choosing a remedy, see whether you can name the axis in one sentence.
