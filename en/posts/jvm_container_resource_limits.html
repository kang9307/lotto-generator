How the JVM Reads Container Limits - Where Kubernetes Requests and Limits Decide Heap, GC and Latency 2026

Why matching -Xmx to your memory limit kills the pod, and how one availableProcessors value sets GC threads and parallelism

Sep 2, 2026 Dev & Infra

Write limits.memory: 1Gi into a pod spec and the container really will not cross that line. The question is how the JVM inside it reads that number. The JVM is not a program that obeys a limit; it is a program that looks at a limit and makes a plan of its own. When the plan is wrong, the thing that enforces the limit is the kernel, and the way the kernel enforces it is by killing the process.

The CPU side goes wrong more quietly. Average utilisation stays low while p99 spikes. Meanwhile, inside the JVM, the collector choice and the thread pool sizes have shifted to follow a single number in the pod spec.

The basis for this piece is the Java 21 java man page, the Java 25 GC tuning guide, the OpenJDK source and bug database, and the Kubernetes official documentation as of September 2026. I could not run any of it in a Linux container, so no command output is included here. Every default and behaviour below comes from those documents.

The trigger - where a limit still does not line up

In early September 2026 a piece on CPU and memory requests and limits for the Java JVM on Kubernetes made the rounds in the Korean developer community. It had one thesis. A Java process in a container has two memory boundaries. The heap boundary and the container boundary, and treating them as one thing is the moment things break.

The same shape exists on the CPU side. The CPU number in a pod spec is a message to the scheduler and at the same time the input the JVM uses to compute its own parallelism, and the dashboard shows you only one of the two. How to diagnose an OOMKilled container in general is a separate piece, and why control room screens fail to answer during an incident is that one. This one stays on problems specific to the JVM.

The JVM used to look at the host

The root of it is that the JVM sizes its own heap. Oracle's GC tuning guide lists the default selections plainly. Initial heap size of one sixty-fourth of physical memory, maximum heap size of one quarter, the Garbage-First collector on server-class machines and the Serial collector otherwise. It even footnotes what server-class means. Two or more processors and physical memory larger than or equal to 1792MB.

The trouble is that phrase, physical memory. To a JVM from before container awareness, that meant the whole host. Put a pod with a 512Mi limit on a 64GB node and the JVM inside planned for a 16GB maximum heap. Since the plan was wrong, the collector saw plenty of room and postponed collection, and meanwhile the container crossed 512Mi and died at the hands of the kernel.

The point of repair is documented. It is the JDK-8146115 entry in the JDK 10 release notes. The JVM was modified to be aware that it is running inside a container and to extract container specific configuration information instead of querying the operating system. What it extracts is the number of CPUs and the total memory allocated to the container. It works only on Linux, it is enabled by default, and it can be disabled with -XX:-UseContainerSupport.

  • The same change added -XX:ActiveProcessorCount. The release note says this count overrides any other automatic CPU detection logic in the JVM
  • Alongside it, JDK-8186248 added InitialRAMPercentage, MaxRAMPercentage and MinRAMPercentage, replacing the older Fraction forms
  • The same entry also appears in the Oracle JDK 8u191 release notes. Anything on the JDK 8 line at 8u191 or later has container awareness too
  • Which also means 8u190 and below, and JDK 9, do not. On images like that you are back to nailing -Xmx down by hand

What container awareness actually reads

The memory path is spelled out under -XX:MaxRAM. The default is the maximum amount of available memory to the JVM process or 128 GB, whichever is lower, and the next sentence is the important one. That available memory is the minimum of the machine's physical memory and any constraints set by the environment, for example a container. The container memory limit enters here, and the percentage flags sit on top of it.

The CPU algorithm lives in an OpenJDK source comment rather than the man page. The description of active_processor_count in cgroupSubsystem_linux.cpp is three lines. Determine the number of available CPUs from sched_getaffinity. If a quota is specified, divide quota by period. And all results of division are rounded up to the next whole number. The result never exceeds the number of active processors.

That rounding matters in practice. A CPU limit of 500m gives 0.5, which rounds up to 1; 1500m gives 2. Even below one CPU, the JVM still sees at least one. Going the other way, an awkward value like 2100m becomes 3, which encourages more threads than the container can actually run.

The easy thing to miss is having no limit at all. With no quota in the cgroup, the algorithm above simply uses the system's active processor count. Put a pod with nothing but requests.cpu: 500m on a 96-core node and its JVM plans for 96 cores.

Why a percentage beats -Xmx

The difference between an absolute and a percentage is not taste, it is the number of places you have to maintain. -Xmx2g is a number that lives apart from the pod spec. Raise the limit to 3Gi without touching the JVM argument and the extra memory sits idle; drop it to 1Gi without touching it and the pod dies from the moment it rolls out. A percentage leaves one place to edit.

FlagWhat it setsDefault per the Java 21 man pageWatch out
-XX:InitialRAMPercentageInitial heap1.5625 percentThe heap starts very small. It collects often while growing
-XX:MaxRAMPercentageMaximum heap25 percentLeft unset, a 1Gi container caps the heap around 256Mi
-XX:MinRAMPercentageMaximum heap for small heaps50 percentNot a minimum. The docs apply it to a small heap of approximately 125 MB
-XX:MaxRAMThe denominator for the aboveAvailable memory or 128 GB, whichever is lowerAvailable memory here is the container limit

That 25 percent default causes more trouble than anything else in the field. You give a container 4Gi, the heap takes 1Gi, and nobody uses the remaining 3Gi. Half of every complaint that goes we added memory and GC is still bad starts here. MaxRAMPercentage is effectively a mandatory setting in a container.

There is a naming trap too. MinRAMPercentage does not mean at least this share goes to the heap; it is the maximum share in the small-heap range. A 250Mi sidecar Java process where only MaxRAMPercentage was touched, and nobody can work out why it does nothing, is this.

resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    memory: 1Gi          # the denominator for the percentage
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=70.0
      -XX:InitialRAMPercentage=70.0
      -XX:+ExitOnOutOfMemoryError

There is no authority behind the number 70. No official document anywhere recommends a particular heap share of the limit. The piece that prompted this said to start somewhere between 50 and 75 and then verify, and that is about as honest as it gets. What the remainder is for is the next section.

The heap is not all the memory

If you take one section, take this one. Set -Xmx equal to the container limit and that pod will die. Outside the heap sit several other things the JVM uses, and none of them count against -Xmx while all of them count against the container.

RegionWhat sets itDocumented defaultCounts against the container
Java heap-Xmx / MaxRAMPercentage25 percent of MaxRAMYes
Metaspace-XX:MaxMetaspaceSizeBy default the size is not limitedYes
JIT code cache-XX:ReservedCodeCacheSize240MB, or 48MB without tiered compilationYes
Thread stacks-Xss × thread count1024 KB per thread on Linux x64Yes
Direct buffers (NIO)-XX:MaxDirectMemorySizeUnset, the JVM chooses automaticallyYes
GC structures, the JVM itself, native librariesNo flagNo documented fixed valueYes

The line that stands out is that metaspace is unlimited by default. In a framework that mints classes freely, that number grows while the heap looks perfectly healthy and only the container reaches its ceiling. Note though that reservation and commit are different things. The figures above are ceilings, not steady-state occupancy.

The way it dies matters more. When the heap runs short the JVM throws OutOfMemoryError and leaves a stack trace and a heap dump. Cross the container limit and, in the words of the Kubernetes docs, memory limits are enforced by the kernel with out of memory kills. No exception, no dump. The same page adds that these terminations only happen when the kernel detects memory pressure, so a container that over allocates memory may not be immediately killed. Same code, same load, different moment of death.

The JVM's own way of telling you where the non-heap memory went is native memory tracking. -XX:NativeMemoryTracking defaults to off, and summary tracks usage by JVM subsystem.

# non-heap breakdown (only valid if tracking was on at launch)
jcmd 1 VM.native_memory summary

# maximum logging of how the JVM saw the container
java -Xlog:os+container=trace -XX:MaxRAMPercentage=70 -version

# the values the flags actually resolved to
java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|ActiveProcessorCount'

Everything one availableProcessors value decides

The javadoc for Runtime.availableProcessors() is short. It returns the number of processors available to the virtual machine, the value may change during a particular invocation, and it is never smaller than one. In a container that value is the rounded-up figure from the previous section, and this single number sets off a chain.

Collector choice and GC thread count

The server-class test lands here. Fewer than two processors or less than 1792MB and the machine is not server-class, so the default collector becomes Serial rather than G1. A container with a 500m CPU limit counts as one processor and trips exactly this condition. Bolting G1-specific tuning flags onto that does nothing at all.

Even past the server-class bar, the number of GC workers follows the processor count. The guide only says the maximum number of GC threads is limited by heap size and available CPU resources, without giving the formula. The direction is clear regardless. See fewer processors and the collector runs slower.

Overriding with ActiveProcessorCount

The man page states the scope of this flag exactly. It overrides the number of CPUs the VM uses to calculate the size of thread pools it will use for operations such as garbage collection and ForkJoinPool. It adds that the flag is honored even if UseContainerSupport is not enabled, and even names the use case: it is useful for partitioning CPU resources when running multiple Java processes in containers.

  • This flag changes only what the JVM sees. The cgroup quota does not move. Set it to 1 and the container can still use the whole limit
  • So dialling it down shrinks GC workers and parallel work while throttling stays exactly where it was. It is not a throttling fix
  • Dialling it up adds threads against an unchanged quota, which makes throttling worse. Pretending you have more cores does not work
  • Where it earns its keep is a pod with two or more Java processes, so that each one stops counting the whole pod as its own

Parallel streams hang off the same value. The ForkJoinPool javadoc states that the no-argument constructor creates a pool with parallelism equal to Runtime.availableProcessors(), and that the common pool's parallelism can be set through the java.util.concurrent.ForkJoinPool.common.parallelism property. Changing a CPU limit is also changing the parallelism of your application code.

Why a CPU limit creates latency

The Kubernetes sentence is unambiguous. cpu limits are enforced by CPU throttling, and when a container approaches its cpu limit the kernel restricts access to the CPU corresponding to that limit. It is a hard limit the kernel enforces. Unlike memory, this is not cross it and die, it is try to cross it and stall.

The unit of stalling is the crux. The kubelet enforces pod CPU limits with CFS quota by default, and --cpu-cfs-quota-period, which sets that period, defaults to 100ms. Throttling does not spread smoothly across a second; it happens as burn your slice inside a 100ms window and stop until that window ends.

Here is where averages lie. With a CPU limit of 1 and four threads, a 100ms allowance is gone in 25ms and every thread in that container stops for the remaining 75ms. Averaged over a second, utilisation is under 100 percent and the graph looks calm, even though that second contains several stalls of up to 75ms. That is usually the whole story behind low average utilisation with a spiking p99.

Overlap it with GC and it gets worse. If the allowance runs out during a stop-the-world phase, the GC threads stop with everything else and resume only when the next period opens. A pause that would have been short stretches to the period boundary. That is why GC log pause times and throttling metrics have to be read side by side.

To set a CPU limit or not

This one genuinely splits. The two camps are optimising for different things and both have documented backing. Putting them side by side is more accurate than picking one.

Against limitsGroundsFor limitsGrounds
Throttling produces real latencyA hard limit enforced by the kernel with a 100ms default periodIt is the condition for Guaranteed QoSEvery container's CPU limit must equal its request
A pod does not die from lack of CPUEviction signals cover memory, filesystems and pids, never CPUYou move down the eviction orderEviction runs BestEffort, then Burstable, then Guaranteed
An idle node lets you use the spare CPUWith resources to spare, using more than the request is allowedCPU pinning requires itExclusive CPUs go to Guaranteed pods with integer requests
Requests alone still decide placementThe scheduler uses the request to place the podNeighbour latency becomes predictableAn operating preference rather than a documented ground

In short, a handful of latency-critical services and a fleet of density-critical batch jobs arrive at different answers. The first group drops or widens limits to dodge throttling; the second sets them for predictability and eviction ranking. The deciding factor is not taste but data. Are the throttling metrics actually rising?

One distinction has to stay sharp. Dropping a memory limit is not the same kind of decision as dropping a CPU limit. CPU is compressible, so short supply just makes things slower; memory is not. With no memory limit that pod endangers the whole node, and the JVM will plan its heap against node memory.

Requests and limits do different jobs

The Kubernetes definition is short. Specify a request and the kube-scheduler uses that information to decide which node to place the Pod on. Specify a limit and the kubelet enforces it so the running container cannot use more than that. One is a placement-time number, the other a runtime one.

What settles it from the JVM's side is that the JVM never looks at the request. What MaxRAM consults is the constraint set by the environment, which is the cgroup limit. A pod with a generous request and an empty limit looks comfortably placed to the scheduler while the JVM inside it works from memory that is not there.

QoS classConditionEviction orderWhat it means for the JVM
GuaranteedEvery container has CPU and memory limits and requests, and each pair is equalEvicted lastThe heap denominator is fixed. Least room for the plan to drift
BurstableNot Guaranteed, but at least one container has a request or a limitAfter BestEffortWith a limit that is the denominator. Without one, node memory is
BestEffortNo container has any CPU or memory request or limitEvicted firstThe JVM counts the whole node as its own. Effectively banned for Java

One more condition from the docs is worth knowing. When eviction is due to resource pressure, only pods exceeding their resource requests are candidates. That is why setting realistic requests is not paperwork.

Where JIT warm-up breaks readiness

HotSpot starts with the tiered compiler, using both C1 and C2, and compilation costs CPU. So a Java application's CPU usage is at its highest right after startup and falls off in steady state. CPU limits, meanwhile, are usually sized for steady state. The phase that needs CPU most is throttled hardest.

What follows is scripted. Slow startup fails the readiness probe, and as the docs put it the kubelet marks the container as not ready, at which point the endpoint controller removes the Pod's IP address from all Service endpoints that match the Pod. That much is correct behaviour. The problem is a liveness probe wired to the same thresholds. When liveness fails the container is killed per the restart policy, starts again and walks through the same phase again. That is a restart loop.

The documented remedy is the startup probe. The docs say it protects slow starting containers and lets you define startup-specific success criteria without affecting the normal liveness or readiness checks. They even give the shape: use the same check as liveness but with a higher failure threshold. Loosening liveness itself would mean you stop catching real failures.

  • Giving extra CPU only during startup is not possible with standard requests and limits. You either buy time with a startup probe or raise the limit
  • If you would rather not raise it, startup optimisations such as class data sharing or ahead-of-time compilation are the next option. Their effect was not measured here
  • A slow first request from slow startup and a permanently high p99 from throttling are different problems. Read startup and steady state separately or they blur

What to look at before deciding

The commonest mistake is deciding on one number. Sizing a limit from a heap usage graph, or judging throttling from CPU utilisation. The five below say different things.

  • Heap usage right after a collection — this is what heap sizing rests on. The top of the sawtooth is not the size you need, it is the size including garbage about to go
  • Committed heap — what the JVM has actually secured. Depending on the collector, unused portions may be returned to the operating system
  • Process RSS — what is resident in physical memory. Subtract the heap and you get a rough read on everything outside it
  • Container memory usage — what the cgroup sees, and what decides an OOM. Page cache is mixed in
  • CPU throttling metrics — not utilisation but throttled periods and time. Utilisation hides throttling

The order is plain. Set the limit, give the heap as a percentage, watch those five together under real traffic, then go back and fix it. Note in particular that synthetic load rarely exposes non-heap memory. Class loading and the code cache only grow once a variety of real code paths get walked.

These repeat because the symptom shows up a long way from the cause.

The fourth has a trap in the other direction too. Raise only the processor count with -XX:ActiveProcessorCount and the collector choice changes while the quota does not. You get more threads and worse throttling. If you want a different collector, naming it with -XX:+UseG1GC is more honest than lying about processors.

Which versions this is written against

Behaviour here genuinely differs by version. It is a classic place where copying an old article straight across goes wrong, so the basis is worth stating.

  • JDK 8u190 and below, and JDK 9 — no container awareness. Heap and processor count come from the host, so nailing -Xmx down by hand is the only option
  • JDK 8u191 and above, and JDK 10 and above — UseContainerSupport is on by default and the three RAMPercentage flags plus ActiveProcessorCount are available
  • JDK 19 — the OpenJDK issue JDK-8281181, Do not use CPU Shares to compute active processor count, landed in this version. Before it, with no quota set, cpu shares decided the processor count, and in Kubernetes cpu shares come from the CPU request. On older JDKs the request influenced JVM parallelism
  • The flag defaults above are from the Java 21 java man page. Collector selection and the server-class test are from the Java 25 GC tuning guide
  • The Kubernetes side is the official documentation as of September 2026. Differences between cgroup v1 and v2 are not covered

The third is the awkward one. You can raise a runtime, leave the CPU settings alone, and still get different parallelism. Leaving flags untouched can itself be a change.

Summary

The spine is one sentence. A number in a pod spec constrains the container and is at the same time the input the JVM uses to plan. The memory limit becomes the denominator of the heap percentage; the CPU limit becomes a processor count that decides collector selection and thread pool sizes.

Three things survive into practice. Do not set -Xmx equal to the limit; leave no room outside the heap and the kernel kills you quietly. Give it as a percentage; there is one number to maintain and the 25 percent default is usually far too small. Decide the CPU limit together with a latency budget; a stall inside a 100ms period never shows up in a per-second average. And no one else can pick your percentage. Non-heap memory varies by framework and thread count from service to service. Measure it, set it, and look again every time you raise the runtime.

  • The default formulas for -XX:ParallelGCThreads and -XX:ConcGCThreads are not in the man page either. The guide says only that they are limited by heap size and available CPU resources
  • Whether JDK-8281181 was backported I could not confirm. The bug database listed a single fix version, 19
  • How the difference between cgroup v1 and v2 affects the calculations above is not covered. File names and units differ
