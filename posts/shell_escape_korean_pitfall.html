한글 파일명이 셸마다 다르게 보이는 이유

Git Bash가 만든 이름을 PowerShell이 못 찾는 자리

2026-08-10 개발/인프라

서론: 같은 폴더인데 파일 이름이 셸마다 다르다

스크립트는 Git Bash로 돌리고, 배포는 PowerShell로 하고, 빌드는 WSL에서 하는 구성은 한국 개발 팀에서 흔하다. 이 조합에서 한글이나 공백이 든 파일 이름을 다루다 보면 설명이 안 되는 일이 생긴다. Git Bash에서 멀쩡히 보이는 파일을 PowerShell 스크립트가 「없다」고 한다.

# Git Bash 쪽
$ ls -1
x?y.txt

# PowerShell 쪽 — 같은 폴더, 같은 파일
PS> Test-Path -LiteralPath '.\x?y.txt'
False

파일은 거기 있다. 지워지지도 숨겨지지도 않았다. 두 셸이 같은 파일을 서로 다른 이름으로 알고 있을 뿐이다. 이런 종류의 어긋남은 이름 안의 물음표 하나에서만 나오지 않는다. 대소문자, 로케일, 유니코드 정규화, 목록 파일의 인코딩까지 경계마다 규칙이 다르고 그 차이가 조용하다. 오류 메시지가 안 나오고 결과만 틀린다.

이 글은 그 경계들을 하나씩 짚는다. 따옴표 문법 자체는 셸 인용부호 규칙 - 어느 따옴표가 무엇을 막는가에, 공백·개행이 든 이름을 find와 xargs로 넘기는 실무 조합은 find·xargs 공백과 개행 함정에 이미 정리해 뒀다. 여기서 다루는 것은 그다음이다. 인용을 제대로 붙였는데도 도구를 갈아타는 순간 이름이 달라지는 자리다.

이 글에서 다루는 경계
  1. Windows 금지 문자와 사설 사용 영역 치환 — Git Bash와 PowerShell이 갈리는 지점
  2. 대소문자 무시 파일 시스템 — 두 개를 만들면 하나가 된다
  3. Git Bash의 경로 자동 변환 — 인자가 도중에 바뀐다
  4. PowerShell 5.1의 네이티브 인자 전달 — 따옴표와 빈 문자열이 사라진다
  5. 기본 인코딩과 목록 파일 — BOM·CR·CP949
  6. 로케일이 bash 자체를 바꾸는 세 자리
  7. 결합형과 분해형이 한 폴더에 있을 때

1. 실행 환경 - 이 글의 근거

본문의 모든 출력은 아래 환경에서 나온 것이다. 버전이 다르면 결과도 달라질 수 있는 항목이 여럿이라 먼저 못 박아 둔다.

  • OS: Windows 10 Pro, 빌드 19045, 파일 시스템 NTFS
  • 셸 1: Git for Windows의 bash 5.2.37(1)-release, 커널 문자열 MINGW64_NT-10.0-19045 … 3.5.7 … Msys
  • 셸 2: Windows PowerShell 5.1.19041.6456
  • 로케일: LANG·LC_ALL 미설정, LC_CTYPE는 C.UTF-8
  • 시스템 ANSI 코드페이지: ks_c_5601-1987 (한국어 Windows의 CP949)
  • 인자 확인용 외부 프로그램: Node.js v22.16.0 (process.argv를 그대로 찍는 용도)
  • WSL: wsl.exe는 존재하나 설치된 배포판이 없어 이 글에서 확인하지 못했다 (15절 참조)

모든 실습은 빈 임시 디렉터리에서 했다. 본문 예제는 파일을 지우지 않는 형태로만 실었다. 인자가 어떻게 쪼개지는지는 echo와 printf로 드러내면 충분하고, 그편이 따라 해 보기에도 안전하다.

2. 이름은 문자열이 아니라 바이트열이고, 계층마다 규칙이 다르다

파일 이름이 화면에 뜨기까지 최소 세 계층을 지난다. 각 계층이 이름을 저장하고 해석하는 방식이 다르며, 경계에서 변환이 일어난다.

  • 파일 시스템 — NTFS는 이름을 UTF-16 코드 유닛 열로 저장한다. 정규화하지 않고, 몇몇 문자를 금지한다.
  • 셸과 유틸리티 — POSIX 계열 도구는 이름을 바이트열로 다룬다. 어떤 인코딩인지는 로케일이 정한다.
  • 화면 — 폰트가 그린다. 바이트가 달라도 같은 그림이 나올 수 있다.

세 번째 항목이 이 글 전체를 관통한다. 눈으로 보는 것은 증거가 아니다. 이름이 의심스러우면 바이트를 봐야 하고, 그 수단은 어디서든 같다.

$ printf '%s' "회의 자료.txt" | od -An -tx1
 ed 9a 8c ec 9d 98 20 ec 9e 90 eb a3 8c 2e 74 78 74

이름이 안 맞을 때 이 한 줄을 먼저 찍는 습관을 들이면 진단 시간이 확 줄어든다. 글자를 비교하지 말고 바이트를 비교한다.

3. Git Bash가 만든 이름을 PowerShell이 못 찾는다 - 0xF000 치환

Windows는 파일 이름에 쓸 수 없는 문자를 정해 두고 있다. Cygwin 문서는 그 목록을 「ASCII 값 1부터 31까지의 제어 문자, 그리고 Win32 API에서 특별한 의미를 갖는 다음 문자들」로 적고 " * : < > ? | \을 든다. 그런데 Git Bash에서는 이런 이름이 아무 저항 없이 만들어진다.

$ for c in '<' '>' ':' '"' '|' '?' '*'; do printf 'x\n' > "x${c}y.txt"; done
$ ls -1
x"y.txt
x*y.txt
x:y.txt
x<y.txt
x>y.txt
x?y.txt
x|y.txt

Git Bash 쪽에서 이름의 바이트를 찍어 보면 입력한 그대로다. 콜론은 3a, 물음표는 3f다. 그런데 Windows 쪽에서 같은 파일의 이름을 읽으면 다른 코드포인트가 나온다.

PS> Get-ChildItem | ForEach-Object {
      ($_.Name.ToCharArray() | ForEach-Object { 'U+{0:X4}' -f [int]$_ }) -join ' '
    }
U+0078 U+F009 U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F00A U+0079 U+002E U+0074 U+0078 U+0074
U+0078 U+F022 U+0079 U+002E U+0074 U+0078 U+0074

U+0078 U+F07C U+0079 U+002E U+0074 U+0078 U+0074

규칙이 한눈에 보인다. 금지 문자의 코드포인트에 0xF000을 더해 사설 사용 영역으로 옮긴다. Cygwin 문서가 그렇게 적고 있다 — 역슬래시를 제외한 위 문자들은 「파일을 만들거나 접근할 때 금지 문자의 코드포인트에 0xF000을 더해 0xf000부터 0xf0ff 범위의 특수 유니코드 문자로 변환된다」. 역슬래시만 빠지는 이유는 그것이 경로 구분자이기 때문이다.

입력한 문자원래 코드포인트저장된 코드포인트저장된 이름의 UTF-8 바이트

<U+003CU+F03CEF 80 BC
>U+003EU+F03EEF 80 BE

|U+007CU+F07CEF 81 BC

Git Bash가 목록을 읽을 때는 이 변환을 되돌려 보여 주므로 그쪽에서는 아무 문제가 없다. 문제는 되돌리지 않는 도구다.

PS> Test-Path -LiteralPath '.\x?y.txt'
False

PS> Test-Path -LiteralPath '.\x|y.txt'
Test-Path : Illegal characters in path.

PS> $pua = 'x' + [char]0xF03F + 'y.txt'
PS> Test-Path -LiteralPath ".\$pua"
True

세로줄이 든 이름은 거짓이 아니라 예외를 낸다. Windows API가 그 문자를 경로에 허용하지 않으니 조회 자체가 성립하지 않는다. 사설 사용 영역 문자로 조립한 이름만 참을 낸다. 같은 파일에 이름이 두 개 있는 셈이다.

실무에서 이게 문제가 되는 순간
Git Bash로 돌린 스크립트가 로그·리포트 파일을 만들고, 그 파일을 PowerShell 배포 스크립트가 집어 가는 구성에서 터진다. 이름에 시각을 넣으려고 %H:%M 형식을 쓰면 콜론이 들어가고, 그 순간 두 셸이 파일을 다르게 보기 시작한다. 시각을 이름에 넣을 때 콜론 대신 하이픈을 쓰는 관행은 미신이 아니라 이 문제를 피하는 규칙이다.

덧붙이자면 Cygwin 문서는 장치 이름(AUX·COM1·LPT1·PRN 등)과 이름 끝의 마침표·공백도 별도로 다룬다. 장치 이름은 네이티브 Win32 프로그램에서 파일 이름이나 확장자로 쓸 수 없고, 끝의 마침표와 공백은 「파일을 만들기 전에 전부 제거된다」. Cygwin 계열 프로그램은 이 제약을 우회해 만들 수 있는데, 그렇게 만들어진 파일은 탐색기나 일반 Windows 도구로 지우기가 까다로워진다. 실습으로 확인할 일이 아니다. 만들지 않는 것이 답이다.

4. 대소문자 - 두 개를 만들면 하나만 남는다

Linux에서 문제없이 돌던 스크립트가 Windows에서 파일 하나를 잃는 전형적인 자리다.

$ printf '대문자\n' > "README.txt"
$ printf '소문자\n' > "readme.txt"
$ ls -1
README.txt
$ cat README.txt
소문자

파일은 하나다. 그런데 이름은 먼저 만든 쪽이 남고 내용은 나중에 쓴 쪽이 남았다. NTFS 기본 설정이 대소문자를 구분하지 않으면서 원래 표기는 보존하기 때문이다. 두 번째 리다이렉션은 새 파일을 만든 게 아니라 기존 파일을 열어 덮어썼다.

  • 같은 이름을 대소문자만 달리해 쓰는 저장소는 Windows 체크아웃에서 파일 하나를 잃는다.
  • 스크립트가 Config.json을 쓰고 다른 스크립트가 config.json을 읽는 구성은 Linux에서만 실패한다. 실패가 늦게 드러나는 방향이라 더 나쁘다.
  • 한글 이름에는 대소문자가 없으니 이 문제가 없다. 대신 다음 절들의 문제를 전부 받는다.

5. Git Bash의 경로 자동 변환 - 인자가 도중에 바뀐다

Git Bash는 네이티브 Windows 실행 파일을 호출할 때 POSIX 형태로 보이는 인자를 Windows 경로로 바꿔서 넘긴다. 셸 내장 명령에는 이 변환이 없다.

$ node -e 'console.log(JSON.stringify(process.argv.slice(1)))' "/usr/bin" "a/b" "-Dfoo=/bar"
["C:/Program Files/Git/usr/bin","a/b","-Dfoo=C:/Program Files/Git/bar"]

$ printf '%s\n' "/usr/bin"
/usr/bin

세 가지가 한꺼번에 드러난다. 첫째, /usr/bin은 Git 설치 경로 아래로 재해석됐다. 둘째, 슬래시가 앞에 없는 a/b는 건드리지 않았다. 셋째이자 가장 골치 아픈 것 — -Dfoo=/bar처럼 등호 뒤에 붙은 값까지 변환됐다. 경로가 아니라 애플리케이션 옵션 값이었어도 마찬가지다.

컨테이너 볼륨 마운트나 REST 경로를 인자로 넘길 때 이 변환이 조용히 값을 망친다. 끄는 방법은 환경 변수 하나다.

$ MSYS_NO_PATHCONV=1 node -e 'console.log(JSON.stringify(process.argv.slice(1)))' \
      "/usr/bin" "a/b" "-Dfoo=/bar"
["/usr/bin","a/b","-Dfoo=/bar"]
  • 명령 하나에만 걸려면 위처럼 앞에 붙여 쓴다. 스크립트 전체에 걸면 정말 경로여야 할 인자까지 안 바뀌므로 범위를 좁히는 편이 낫다.
  • 슬래시 두 개로 시작하면(//c) 변환을 피해 가는 관용법이 통하는 경우가 있다. 다만 받는 프로그램이 그 형태를 받아들여야 한다.
  • 이 변환은 네이티브 실행 파일 호출에만 적용된다. bash 내장이나 MSYS 빌드 유틸리티에는 적용되지 않아, 같은 문자열이 명령에 따라 다르게 도착한다.

6. PowerShell 5.1 - 단어 분리는 없지만 인자가 사라진다

PowerShell로 넘어오면 bash에서 겪던 문제 하나가 사라진다. 단어 분리가 없다. 공백이 든 변수를 그냥 넘겨도 한 인자다.

PS> $f = '회의 자료.txt'
PS> node -e 'process.argv.slice(1).forEach(function(a,i){console.log(i+String.fromCharCode(32)+a)})' $f 'a b.txt'
0 회의 자료.txt
1 a b.txt

bash에서 인용을 빼면 인자가 둘로 갈라지는 그 값이, 여기서는 인용 없이도 하나로 간다. 그런데 대신 다른 것이 사라진다.

PS> $s = 'a"b'
PS> $s.Length
3
PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' $s
["ab"]

PS> node -e 'console.log(JSON.stringify(process.argv.slice(1)))' '' 'x'
["x"]

길이 3인 문자열이 받는 쪽에서 길이 2로 도착했다. 큰따옴표가 조용히 없어졌다. 빈 문자열 인자는 아예 목록에서 빠졌다. 오류도 경고도 없다.

원인은 문서에 적혀 있다. PowerShell은 네이티브 명령을 호출할 때 「파싱된 인자들을 각 매개변수를 공백으로 구분한 하나의 문자열로 합친다」. 이 합치기 과정에서 따옴표 처리가 어긋난다. PowerShell 7.3에서 인자 전달 방식이 바뀌었고, 그 문서는 이 변경이 5.1 동작에 대한 파괴적 변경임을 명시하면서 새 방식에서는 「임베드된 따옴표가 보존된다」·「빈 문자열 인자가 보존된다」고 적는다. 바꿔 말하면 5.1에서 위 결과는 버그가 아니라 알려진 동작이다.

5.1에 묶여 있다면 선택지는 셋이다.

  • 정지 파싱 토큰 --% — 뒤따르는 문자열을 리터럴로 넘긴다. 다만 문서가 밝히듯 %변수% 형태의 환경 변수 치환은 여전히 일어나고, 다음 줄바꿈이나 파이프까지만 유효하며, 그 안에서는 리다이렉션도 인자로 넘어간다.
  • Start-Process — 인자를 배열로 넘겨 명령줄 조립을 명시적으로 통제한다.
  • PowerShell 7 이상으로 올리기 — Windows에서 기본값이 새 방식이다. 배치 파일과 cmd.exe 호출만 옛 방식으로 되돌아간다.
bash와 정반대라는 점이 함정이다. bash에서는 「인용을 안 붙여서」 인자가 늘어난다. PowerShell 5.1에서는 「인용을 붙였는데」 인자가 줄어든다. 두 셸을 오가며 같은 스크립트를 포팅할 때, 고쳐야 할 방향이 서로 반대다.

7. -Path와 -LiteralPath - 대괄호 하나가 다른 파일을 연다

bash에서 인용하지 않은 변수가 글로브로 부풀어 오르는 사고는 잘 알려져 있다. PowerShell에도 같은 종류의 함정이 있는데, 인용과 무관하게 매개변수 이름으로 갈린다.

내용이 다른 두 파일 star1.txt와 star[1].txt를 두고 대괄호가 든 쪽을 읽어 보면 이렇다.

# bash — 인용 여부로 갈린다
$ g='star[1].txt'
$ cat $g
star1 내용
$ cat "$g"
대괄호 파일 내용
# PowerShell — 매개변수 이름으로 갈린다
PS> Get-Content -Path 'star[1].txt'
star1 내용
PS> Get-Content -LiteralPath 'star[1].txt'
대괄호 파일 내용

양쪽 다 있지도 않은 파일을 요구한 게 아니라 다른 파일을 열어 조용히 성공했다. 이런 실패가 제일 나쁘다. 오류가 났으면 바로 알았을 것이다.

  • PowerShell의 -Path는 와일드카드를 해석한다. * ? [ ]가 전부 패턴 문자다.
  • 사용자 입력이나 목록 파일에서 온 이름은 예외 없이 -LiteralPath로 넘긴다. 한글 이름에도 대괄호는 흔하다 — [최종]보고서.xlsx 같은 이름은 실무에서 매일 만들어진다.
  • bash 쪽에서 같은 방어를 하려면 인용을 붙이거나, 변수 하나를 잠깐 글로빙 없이 다루려면 set -f로 경로명 확장만 꺼도 된다.
$ v='star[1].txt'
$ echo $v          # 글로빙 켜짐
star1.txt
$ set -f
$ echo $v          # 글로빙 꺼짐
star[1].txt
$ set +f

8. 읽고 쓰는 기본 인코딩 - PowerShell 5.1의 CP949

이름을 정확히 넘겼는데 내용이 깨지는 자리도 있다. Git Bash가 UTF-8로 쓴 파일을 PowerShell 5.1이 읽으면 이렇게 된다.

PS> Get-Content -LiteralPath 'star1.txt'
star1 ?댁슜
PS> Get-Content -LiteralPath 'star1.txt' -Encoding UTF8
star1 내용

파일은 멀쩡하다. 읽는 쪽이 인코딩을 잘못 골랐을 뿐이다. Windows PowerShell 5.1은 바이트 순서 표시(BOM)가 없는 파일을 시스템 ANSI 코드페이지로 읽는다. 한국어 Windows에서 그 값은 다음과 같다.

PS> [System.Text.Encoding]::Default.WebName
ks_c_5601-1987

쓰는 쪽도 대칭이다. 같은 문자열을 두 방식으로 저장하고 바이트를 뜯어 보면 차이가 분명하다.

PS> Set-Content -LiteralPath 'a.txt' -Value '한글 저장'
PS> Set-Content -LiteralPath 'b.txt' -Value '한글 저장' -Encoding UTF8

a.txt : c7 d1 b1 db 20 c0 fa c0 e5 0d 0a
b.txt : ef bb bf ed 95 9c ea b8 80 20 ec a0 80 ec 9e a5 0d 0a
  • 기본 저장본은 c7 d1로 시작한다. 한 글자가 2바이트인 CP949다.
  • UTF-8 저장본은 ef bb bf로 시작한다. 바이트 순서 표시가 붙는다. 5.1의 -Encoding UTF8은 BOM 없는 UTF-8이 아니다.
  • 양쪽 다 줄 끝이 0d 0a다. CRLF는 다음 절의 재료가 된다.

깨진 글자 모양에서 원인을 거꾸로 읽는 방법은 한글이 깨지는 지점을 특정하는 법 - cp949와 UTF-8에 표로 정리해 뒀다. 압축 파일 안의 이름이 깨진 경우는 규칙이 또 달라서 zip 파일명 인코딩 쪽이 맞다.

9. 목록 파일로 주고받을 때 - BOM과 CR이 이름에 붙는다

처리할 파일 목록을 텍스트 파일로 만들어 넘기는 방식은 흔하다. 엑셀이나 메모장에서 만든 목록을 bash 루프에 물리면 파일이 하나도 없다고 나온다. 이유는 셋이고, 셋 다 눈에 안 보인다.

$ while IFS= read -r f; do
      printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
  done < list_cp949.txt
읽은 값=[ȸ�� �ڷ�.txt]  존재=없음

$ … < list_utf8.txt      # BOM 붙은 UTF-8
읽은 값=[﻿회의 자료.txt]  존재=없음

첫 줄은 CP949 바이트라 이름이 깨졌다. 둘째 줄은 눈으로는 정상인데 맨 앞에 폭 없는 BOM 문자가 붙어 있어서 다른 이름이 됐다. 셋째 원인인 CR은 따로 보면 이렇다.

$ printf '회의 자료.txt\r\n' > list_crlf.txt
$ while IFS= read -r f; do printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=18 존재=없음

$ while IFS= read -r f; do f=${f%$'\r'}; printf '길이=%d 존재=%s\n' "${#f}" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"; done < list_crlf.txt
길이=17 존재=있음

바이트 하나 차이다. 화면에는 아무것도 안 나타난다. 목록을 받아 처리하는 스크립트라면 세 가지를 한 번에 정리하고 시작하는 편이 낫다.

$ iconv -f CP949 -t UTF-8 list.txt | sed '1s/^\xEF\xBB\xBF//' | tr -d '\r' \
  | while IFS= read -r f; do
        printf '읽은 값=[%s]  존재=%s\n' "$f" "$( [ -e "$f" ] && echo 있음 || echo 없음 )"
    done
읽은 값=[회의 자료.txt]  존재=있음
  • 목록이 이미 UTF-8이면 iconv는 빼되, BOM 제거와 CR 제거는 남겨 둔다. 둘 다 인코딩과 무관하게 붙을 수 있다.
  • 목록을 만드는 쪽을 통제할 수 있다면 애초에 NUL 구분으로 주고받는 편이 낫다. 이름에 들어갈 수 없는 유일한 바이트라 경계가 깨지지 않는다. 그 형태는 find·xargs 공백과 개행 함정에 정리돼 있다.
  • read에서 -r을 빼면 역슬래시가 사라진다. Windows 경로를 다루는 스크립트라면 치명적이다 — C:\temp\새 폴더가 C:temp새 폴더가 된다.

10. 로케일이 bash 자체를 바꾼다 - 세 자리

여기가 가장 덜 알려진 축이다. 같은 bash, 같은 스크립트가 로케일에 따라 다르게 동작한다. 세 자리에서 확인된다.

10.1 ANSI-C 인용의 유니코드 이스케이프

Bash 매뉴얼은 $'string' 안에서 \uHHHH를 유니코드 문자 이스케이프로 규정한다. 그런데 실제 결과는 로케일을 탄다.

$ LC_ALL=C.UTF-8 bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 c3 a9 ed 95 9c

$ LC_ALL=C bash -c "printf '%s' \$'\u00E9\uD55C' | od -An -tx1"
 e9 5c 75 44 35 35 43

UTF-8 로케일에서는 c3 a9와 ed 95 9c, 곧 올바른 두 문자가 나온다. C 로케일에서는 é가 단일 바이트 e9로 떨어지고, 한글은 아예 변환되지 않은 채 \uD55C라는 글자 여섯 개로 남는다(5c 75 44 35 35 43). 오류는 나지 않는다. 조용히 리터럴이 된다.

Git for Windows 기본 설치에서 LANG은 비어 있다. 즉 기본 상태가 이 함정 쪽이다. 스크립트에서 유니코드 이스케이프로 문자를 만들 생각이라면 로케일을 명시해야 한다.

10.2 printf %q의 출력

이름을 안전한 형태로 찍어 두는 관용법인데, 출력 모양이 로케일마다 다르다.

$ LC_ALL=C.UTF-8 bash -c "printf '%q\n' '회의 자료.txt'"
회의\ 자료.txt

$ LC_ALL=C bash -c "printf '%q\n' '회의 자료.txt'"
$'\232\214\235\230 \236\220\214.txt'

둘 다 다시 셸에 먹이면 같은 값으로 돌아오므로 기능적으로는 옳다. 문제는 로그다. 아래쪽 형태로 남은 로그는 사람이 읽을 수 없고, 티켓에 붙여도 무슨 파일인지 아무도 모른다.

10.3 대괄호 안의 한글 범위

한글만 걸러내려고 [가-힣]을 쓰는 습관은 널리 퍼져 있다. 이 범위가 로케일에 따라 코드포인트 범위가 아니라 바이트 범위로 해석된다.

$ for loc in C C.UTF-8 en_US.UTF-8 ko_KR.UTF-8; do
      a=$(printf '%s\n' "$NFC" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      b=$(printf '%s\n' "$NFD" | LC_ALL=$loc grep -cE '^[가-힣]+\.txt$')
      echo "LC_ALL=$loc  결합형=$a  분해형=$b"
  done
LC_ALL=C          결합형=1  분해형=1
LC_ALL=C.UTF-8    결합형=1  분해형=0
LC_ALL=en_US.UTF-8 결합형=1  분해형=0
LC_ALL=ko_KR.UTF-8 결합형=1  분해형=0

C 로케일에서는 자모로 분해된 이름까지 매치한다. 오탐이다. UTF-8 로케일에서는 매치하지 않는다 — 이쪽은 정확한 동작이지만, 분해형 한글을 놓친다는 별개의 문제가 그대로 남는다. 어느 쪽이든 [가-힣] 하나로 「한글 파일만」을 거를 수 없다.

반면 리터럴 검색은 로케일과 무관하다. 같은 두 줄에 grep '한글'을 걸면 어느 로케일에서도 결과가 1/2로 같다. 범위 표현이 아니라 리터럴이 문제가 안 되는 이유는 다음 절에 있다.

동작C 로케일UTF-8 로케일
$'\uHHHH' (BMP 상위)변환 안 됨, 리터럴로 남음올바른 UTF-8 바이트
printf %q 한글8진 이스케이프 덩어리회의\ 자료.txt
[가-힣] 범위바이트 범위, 분해형도 매치코드포인트 범위, 분해형 불매치
리터럴 grep '한글'동일동일

11. 결합형과 분해형이 한 폴더에 있을 때

NTFS는 이름을 정규화하지 않는다. 그래서 화면에 똑같이 보이는 파일 두 개가 한 폴더에 공존할 수 있다.

$ ls -1
한글.txt
한글.txt

$ for f in *; do printf '%s  ' "$f"; printf '%s' "$f" | od -An -tx1 | tr -s ' ' | tr -d '\n'; echo; done
한글.txt   e1 84 92 e1 85 a1 e1 86 ab e1 84 80 e1 85 b3 e1 86 af 2e 74 78 74
한글.txt   ed 95 9c ea b8 80 2e 74 78 74

아래쪽이 결합형(NFC)이다. 한 글자가 3바이트라 이름 전체가 10바이트다. 위쪽은 분해형(NFD)으로 초성·중성·종성이 각각 3바이트씩 들어가 22바이트다. 유니코드 표준 부속서 15가 정규화 형식을 규정하며, 한글은 알고리즘으로 분해·결합되는 특수 케이스로 명시돼 있다.

셸에서 이게 어떻게 드러나는지가 실무적으로 중요하다.

$ find . -maxdepth 1 -name '한글*' | wc -l
1

$ n=0; for f in 한글*; do n=$((n+1)); done; echo "$n"
1

$ ls -1 | sort | uniq | wc -l
2
  • 셸 글로브도 find -name도 결합형 하나만 잡는다. 패턴을 키보드로 친 이상 그것은 결합형이기 때문이다.
  • sort는 분해형을 항상 앞에 놓는다. 자모 코드포인트(U+1100대)가 완성형(U+AC00대)보다 작다.
  • uniq는 둘을 다른 줄로 센다. 중복 제거 스크립트가 「중복 없음」이라고 답한다.
  • 백업 스크립트가 find로 목록을 만들면 분해형 파일이 통째로 빠진다. 실패가 아니라 누락이라 알림도 안 뜬다.

왜 두 형태가 생기는지, 검색·정렬·길이 검증·직렬화 각 경계에서 무엇이 깨지는지는 한글이 자모로 분리되는 순간 - NFC와 NFD에 따로 정리했다. 여기서는 셸 쪽 결론만 두면 된다. 파이프라인 어느 지점에서 정규화할지를 정하고, 그 지점을 문서에 적어 둔다. 안 정하면 도구마다 다른 시점에 다른 형태로 정규화한다.

12. 경계를 넘길 때 확실한 형태

지금까지의 실패는 전부 「이름을 문자열에 담아 다른 도구에 넘기는」 자리에서 났다. 담지 않으면 안 깨진다.

같은 셸 안이면 배열로 받는다. 이름 안에 무엇이 있든 원소 하나가 파일 하나다.

$ mapfile -d '' files < <(find . -maxdepth 1 -type f -print0)
$ echo "${#files[@]}"
$ printf '  [%s]\n' "${files[@]}"

실행 전에 명령이 실제로 받을 인자를 미리 보는 습관도 값싸고 확실하다. 실행 대신 printf를 놓으면 된다.

$ target="회의 자료.txt"
$ printf '  인자[%s]\n' $target       # 인용 없음
  인자[회의]
  인자[자료.txt]
$ printf '  인자[%s]\n' "$target"     # 인용
  인자[회의 자료.txt]

위쪽 결과가 나온 상태로 파일을 옮기거나 지우는 명령을 실행했다면, 그 명령은 존재하지 않는 두 파일을 대상으로 삼는다. 대상이 없어 실패하면 그나마 다행이고, 우연히 같은 이름의 파일이 있으면 엉뚱한 것이 대상이 된다. 파괴적인 명령을 쓰기 전에 같은 줄을 printf로 한 번 돌려 보는 데 드는 비용은 몇 초다.

빈 값과 대시로 시작하는 값도 같은 방법으로 미리 드러난다.

$ empty=""
$ set -- $empty;  echo "미인용 인자 개수=$#"
미인용 인자 개수=0
$ set -- "$empty"; echo "인용 인자 개수=$#"
인용 인자 개수=1

$ opt="-n"
$ echo $opt x
x

마지막 줄에서 -n은 출력되지 않았다. echo가 그것을 값이 아니라 옵션으로 먹었기 때문이다. 값이 대시로 시작할 수 있는 자리에서는 --로 옵션 구간을 닫거나 ./를 앞에 붙인다.

$ touch "-n.txt"
touch: unknown option -- n
$ touch -- "-n.txt"      # 옵션 구간을 닫는다
$ touch ./-n.txt         # 경로로 만든다

15. 확인하지 못한 것

아래는 이 환경에서 실행으로 확인할 수 없었던 항목이다. 짐작으로 채우지 않고 그대로 둔다.

  • WSL의 파일명 처리. wsl.exe는 설치돼 있지만 배포판이 없어(wsl -l -q가 종료 코드 1) 아무것도 실행하지 못했다. WSL이 Windows 드라이브를 마운트할 때 금지 문자와 대소문자를 어떻게 다루는지, MSYS2의 0xF000 치환과 호환되는지는 확인하지 못했다. 세 환경을 섞어 쓴다면 이 조합은 각자 자기 환경에서 위 3절과 같은 방식으로 바이트를 찍어 확인하는 편이 안전하다.
  • macOS의 자동 분해. macOS 파일 시스템이 이름을 분해형 계열로 저장한다는 설명이 널리 통용되지만, 이 환경에는 macOS가 없어 실행으로 확인하지 못했다. 이 글의 11절 결과는 NTFS에서 두 형태가 공존한 경우에 한정된다.
  • 이름 끝의 마침표·공백, 그리고 장치 이름. Cygwin 문서의 서술만 인용했고 재현하지 않았다. 이런 이름은 만들고 나면 일반 Windows 도구로 정리하기 어려워, 실습 대상으로 삼을 이유가 없다.
  • PowerShell 7.x의 새 인자 전달. 이 환경에는 5.1만 있다. 7.3 이후 동작은 공식 문서 서술을 근거로 적었고 실행으로 대조하지 못했다.
  • 네트워크 파일 시스템. Cygwin 문서는 일부 네트워크 파일 시스템에서 끝의 마침표·공백이 다르게 처리된다고 적는다. 로컬 NTFS만 확인했다.

결론: 이름은 도구 사이를 건너면서 바뀐다

정리하면 이 글의 실패들은 종류가 하나다. 이름이라는 데이터가 도구 경계를 건널 때마다 변환을 거치고, 그 변환 규칙이 도구마다 다르다. Git Bash는 금지 문자를 사설 사용 영역으로 옮기고 되돌린다. PowerShell 5.1은 인자를 문자열로 합쳤다가 다시 쪼갠다. 텍스트 파일은 코드페이지를 거친다. 유니코드는 두 가지 형태를 허용한다. 각 변환은 자기 영역 안에서 올바르게 동작하고, 어긋남은 언제나 경계에서만 나타난다.

그래서 진단 순서도 정해진다. 이름이 안 맞으면 셋을 차례로 본다.

  1. 바이트를 찍는다. od -An -tx1이나 코드포인트 나열. 눈으로 비교하지 않는다.
  2. 어느 경계를 건넜는지 센다. 셸이 몇 번 바뀌었고 파일로 몇 번 나갔다 들어왔는가.
  3. 그 경계의 기본값을 확인한다. 로케일, 코드페이지, 와일드카드 해석 여부, 인자 전달 방식.

예방은 더 단순하다. 이름을 문자열로 담아 넘기는 횟수를 줄인다. 배열로 받고, NUL로 구분하고, 목록 파일 대신 직접 파이프한다. 그리고 만들 때부터 콜론·물음표·세로줄을 이름에 넣지 않으면 3절의 문제는 애초에 생기지 않는다. 피할 수 있는 문자를 피하는 것이 가장 싼 방어다.
