Atlassian's DESIGN.md - Portable Design Context AI Agents Can Read

The design-side sibling of AGENTS.md, and the 92%-more-expensive token bill its own real-world test revealed

Jul 2, 2026 Dev & Infra

Introduction: After AGENTS.md, Is DESIGN.md Next

Since late 2025, dropping an AGENTS.md file in a repo root has become common practice, pushed jointly by tool vendors like OpenAI, Google, and Cursor. By early 2026, one tally put adoption above 60,000 open-source repos. The file briefs AI coding agents on build commands, test procedures, and coding conventions before they touch the code. Now a design-side counterpart has entered the conversation: Atlassian's DESIGN.md, published in July 2026.

What drew my attention is simple. If AGENTS.md tells an agent how to run code, DESIGN.md tells it how things should look. The pitch is that a single file can fix the problem of AI agents shipping functional but generic UI - the gradient buttons, the all-caps headings, the interchangeable card layouts often called "AI slop." But when you actually read the benchmark numbers Atlassian published alongside the format, the story is not a simple "adopt it and win." This piece was prompted by a topic shared on GeekNews (news.hada.io); after digging into the primary sources myself, here is my own read on what DESIGN.md actually contains, where it helps, and where it quietly gets expensive.

1. What DESIGN.md Actually Is - Origin and Structure

1.1 Born at Google, Battle-Tested at Atlassian

Interestingly, Atlassian didn't invent DESIGN.md. The format originated at Google Labs for its Stitch design tool. Atlassian's contribution was applying it to a mature, enterprise-scale design system - the Atlassian Design System (ADS) - and publishing what they learned at atlassian.design/DESIGN.md. So what's being discussed here isn't "Atlassian's new invention"; it's closer to a case study of what happens when an existing open format meets a design system with millions of pixels of history behind it.

1.2 A File With Two Distinct Halves

DESIGN.md bundles two very different kinds of content into one file. The first is machine-readable design tokens - color, typography, and spacing values in YAML that an AI can parse directly. The second is prose meant for both humans and AI: design principles and rationale explaining why a color belongs in a given context, or when a component should (and shouldn't) be used. That pairing is the point. Tokens alone tell a model the value but not why to choose it. Prose alone loses precision. Bundling both into one file means a single context injection can supply both at once.

1.3 The File Isn't Small

Atlassian's published DESIGN.md weighs in at 80KB, roughly 19,800 tokens (about 10,700 without frontmatter). That's not a trivial payload - and as it turns out, that size is exactly where the cost problem discussed below originates.

2. Why It's Needed - What Happens When AI Doesn't Know Your Design System

2.1 The "Average Trap"

I'd describe the underlying problem as an "average trap." A model internalizes the statistical average of everything it was trained on. Ask it to "build a dashboard" with zero brand context, and it converges on the most common patterns floating around the internet - purple gradient buttons, all-caps headings, generic card layouts, hover animations nobody asked for. That's what people mean by AI slop: functional output that belongs to no brand in particular.

2.2 The Demo Contrast

Atlassian staged this contrast directly at its Team '26 keynote. Generating a dashboard in Figma Make without DESIGN.md produced generic styling; with it, the output was described as instantly recognizable as Atlassian in color, spacing, and typography. The demonstration is persuasive on its own terms - it visually confirms the unsurprising fact that a model can't infer brand identity that was never given to it.

2.3 Why This Isn't Actually a New Problem

That said, I don't think the underlying problem is new. Long before AI, a junior designer or outsourced contractor handed a brief with no brand guidelines would drift the same way. What's different is that an AI agent repeats that drift instantly and endlessly. A person eventually internalizes feedback; a stateless agent session starts from the statistical average every single time unless context is re-supplied. That's the gap DESIGN.md is trying to close by encoding the context once and re-injecting it repeatedly.

3. What Should Go Into It - Balancing Tokens and Rationale

3.1 Design Tokens Finally Have an Industry Standard

DESIGN.md's machine-readable half is possible largely because of the W3C Design Tokens Community Group's standardization work. After years of effort, the $value/$type syntax stabilized into a de facto standard around 2025, replacing the ad hoc JSON formats every team used to invent independently. In other words, DESIGN.md could encode tokens in a machine-parseable way only because the industry had already agreed on token syntax underneath it. Tokens are typically split into two layers: primitive tokens (raw values like a hex code) and semantic tokens (names like "brand-primary" that convey intent). Semantic tokens matter more to an AI agent - a raw hex value alone doesn't say whether a color is an accent or a warning.

3.2 Why Prose Matters as Much as Tokens

The real difference between a plain token list and DESIGN.md is rationale. Rules like "this button component should never be used for destructive actions" or "this spacing token is reserved for data-dense screens" are things a token value alone cannot convey. Without that prose, an agent can pick the technically correct token and still apply it in the wrong context. In my reading, DESIGN.md's real value isn't the value list - it's the documented judgment behind when and why to use each value.

3.3 Compression Is the Fundamental Trade-off

This is where a structural limit shows up. A mature design system like Atlassian's runs to roughly 2.5MB of guidance documentation. Squeezing that into an 80KB file means cutting it down by roughly 30x. Deciding what to keep and what to drop inevitably means losing a lot of usage nuance along the way. DESIGN.md should be treated - by name and by nature - as a compressed snapshot of a design system, not the design system itself.

4. Lessons From the Real-World Test - A 92% More Expensive Token Bill

4.1 The Numbers Atlassian Published

This is the part I find most important. Atlassian compared the same task (generating a dashboard via Figma Make) across four approaches: no context, ADS MCP server, ADS AI skill, and DESIGN.md. The result cuts against intuition: DESIGN.md was the least efficient of the four. It consumed about 92% more tokens than the ADS MCP server, and results varied by 2.7x across runs. Time and turn count were also highest with DESIGN.md. UI quality (brand alignment) improved, but at a real cost in efficiency, speed, and consistency.

4.2 Why the Reversal Happens

My read on this is straightforward. An MCP server loads only what's needed selectively - ask for a button component, and it fetches just the button-related tokens and rules. DESIGN.md, by contrast, loads the entire file into context all at once, every time - hundreds of icon definitions and unrelated component descriptions included, whether the task needs them or not. That's the direct source of the token waste. The simplicity of a static file comes back around as the cost of losing selective loading.

4.3 A Subtler Trap - Component Reimplementation

Atlassian flagged a second, subtler issue. DESIGN.md describes what a design should look like more than how to import and reuse an actual component. As a result, agents sometimes reimplement something that looks close enough from scratch instead of pulling the real component from the library. That's more than an efficiency problem - it's a maintenance liability. The output may look on-brand while quietly missing the accessibility and state-management logic baked into the real component.

4.4 Where DESIGN.md Still Wins

To be fair, there are scenarios where DESIGN.md is clearly the better choice: rapid prototyping in an unfamiliar environment with no existing design-system infrastructure, cross-tool interoperability, and customer-facing adaptive UI generated fresh each time, like dashboards or auto-generated reports. In those cases, "there's no MCP server to install" makes DESIGN.md the only realistic option in the first place.

5. The Future of Design-Dev-AI Collaboration - My Take

5.1 Context Files Are Going to Layer, Not Consolidate

The real lesson here isn't "should I adopt DESIGN.md or not" - it's that AI context delivery needs to be layered by purpose. README.md introduces a project to humans, AGENTS.md briefs coding agents on execution, llms.txt helps discovery of public site content, and DESIGN.md offers a static snapshot of design context. Each tool was built to solve a different problem; treating any one of them as a universal fix is exactly how you end up with the inefficiency this benchmark surfaced. Atlassian's own conclusion - that DESIGN.md complements richer tooling rather than replacing it - backs this up.

5.2 A Healthy Skepticism Toward "Just Add a Context File"

Interestingly, similar skepticism is emerging around AGENTS.md itself. According to my research, an early-2026 ETH Zurich study concluded that AGENTS.md files can actually hinder AI coding agents, recommending that LLM-generated context files be omitted entirely and that human-written instructions be limited to genuinely non-inferable details. Put that next to DESIGN.md's 92% token overhead, and a pattern emerges across 2026: the goal isn't "having a context file" for its own sake - it's delivering exactly the right context at exactly the right moment. A static file is one waypoint toward that goal, not the destination.

5.3 The Next Step Is Standardized Selective Loading

My prediction: single-file formats like DESIGN.md will likely settle into a role as a fast-start kit for prototyping and onboarding, while production-grade, repeated work converges toward MCP servers or equivalent selective-loading mechanisms. DESIGN.md's real value may end up being less about the file itself and more about the discipline it forces - documenting design principles and tokens in machine-readable form in the first place. Once that material is structured, whether you ship it as one static file or serve it piecemeal through MCP becomes a deployment decision you can make later.

Practical Takeaways

6.1 If You Already Have a Design System

Teams with an existing component library and style guide should prioritize exposing that library to AI in a form it can query selectively (an MCP server or equivalent API) before reaching for DESIGN.md, in line with what Atlassian's own numbers show. DESIGN.md can still run alongside as a bridge until that infrastructure is ready, or as a quick-start tool for new projects.

6.2 If You Don't Have One Yet

For early-stage startups or side projects without the resources to build a full design system, the calculus differs - there's no MCP server to compare against because there's no component library to expose in the first place. Here, a lightweight DESIGN.md covering brand colors, tone, and a handful of core principles clearly beats an agent generating a different look every session. The lesson from this case is to keep it lean - roughly 20-30 core tokens plus a few principle paragraphs - rather than letting the file balloon.

6.3 Don't Take Vendor Claims on Faith

What I take away most from this case is that any context file format - AGENTS.md, DESIGN.md, llms.txt - deserves to be treated as a hypothesis to test, not a given. It's rare and genuinely useful that Atlassian published quantitative data, but there's no guarantee the same numbers hold for your team's workload, model choice, or agent stack. Running a small A/B test on your own tasks before committing is the safest habit here.

Conclusion: DESIGN.md Is a Waypoint, Not a Universal Fix

As of July 2026, my conclusion is this: DESIGN.md is a real, partial answer to the problem of AI-generated UI drifting toward a brandless average, but as Atlassian's own published data shows, it is not free. It comes with concrete costs - 92% more tokens than MCP, 2.7x more variance, and a tendency toward component reimplementation. With research also emerging that questions the value of AGENTS.md-style files, "just drop a file in the repo and call it done" is the wrong instinct. What will actually separate teams going forward is the judgment to match the right context-delivery method to the right situation - not the mere presence of a file.
