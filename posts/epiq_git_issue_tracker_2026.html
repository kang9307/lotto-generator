서론: 왜 다시 "이슈를 Git에" 넣자는 이야기가 나오는가

2026년 7월, 이슈 트래커를 다시 논쟁 대상에 올린 것은 화려한 신제품이 아니라 아주 오래된 질문이었다. 이슈가 왜 코드와 다른 곳에 있어야 하는가. Git 저장소 안에 이슈를 통째로 넣어 터미널에서 다루는 분산 이슈 트래커 epiq가 그 질문을 다시 꺼냈다. GitHub Issues나 Jira에 익숙한 개발자에게는 낯설게 들리겠지만, 이 발상 자체는 새롭지 않다. 2008년 전후로도 여러 팀이 같은 문제의식으로 비슷한 도구를 만들었다가 대부분 조용히 사라졌다.

이 글은 epiq라는 개별 도구의 기능을 나열하는 데 그치지 않는다. 그 도구가 다시 불러온 질문 - 이슈 트래커가 코드 저장소와 분리돼 있을 때 생기는 마찰, 그리고 그 마찰을 없애려고 이슈를 Git으로 옮기는 접근의 장단점 - 을 본인 관점에서 짚는다. hada(GeekNews)에 올라온 소개를 출발점으로 삼되 그대로 옮기지 않고, git-appraise·Fossil·git-issue 같은 유사 시도들과 나란히 놓고 무엇이 반복되는 실패이고 무엇이 2026년에 새로 달라졌는지를 확인한다.

결론을 먼저 말하면, epiq가 마주한 강점과 한계는 10여 년 전 ticgit·Bugs Everywhere가 마주했던 것과 크게 다르지 않다. 다만 달라진 변수가 하나 있다. 이제 저장소 안에서 이슈를 읽고 쓰는 주체가 사람만이 아니라, 터미널에서 함께 일하는 AI 코딩 에이전트라는 점이다.

1. epiq란 무엇인가 - 터미널 안의 분산 이슈 트래커

epiq는 GitHub 저장소에 공개된 오픈소스 프로젝트로, 계정이나 서버 없이 로컬 Git 저장소만으로 동작하는 이슈 트래커를 표방한다.

1.1 핵심 설계 - 이벤트 소싱과 ULID

epiq는 이슈를 하나의 공유 파일에 계속 덮어쓰는 대신, 사용자별로 분리된 파일에 추가 전용(append-only) 이벤트로 기록한다. 각 이벤트는 시간 정렬이 가능한 식별자(ULID)와 직전 이벤트에 대한 참조를 함께 가져, 여러 사람이 각자 오프라인에서 작업한 뒤 나중에 병합해도 이벤트가 발생한 순서를 기계적으로 복원할 수 있다. Git의 기본 3-way merge에 이슈 데이터를 그대로 맡기면 텍스트 충돌이 나기 쉽지만, "누가 무엇을 언제 했는가"를 이벤트 로그로 남기면 병합 시점의 충돌 표면을 상당히 줄일 수 있다는 설계 판단으로 읽힌다.

1.2 이중 인터페이스와 Git worktree 동기화

조작면에서는 vim 스타일 키바인딩(h/j/k/l 이동, : 명령줄, ? 팔레트)을 쓰는 터미널 UI와 브라우저 GUI를 함께 제공한다. 이슈 상태는 별도의 Git 브랜치와 워크트리에 저장되고 자동으로 관리되어, 실제 작업 브랜치를 체크아웃·리베이스하는 일상적 흐름과 이슈 동기화 절차가 서로 부딪히지 않게 격리된다. 과거 이슈 트래킹 도구가 흔히 저지른 실수 - 이슈 커밋이 실제 코드 히스토리에 섞여 로그를 지저분하게 만드는 문제 - 를 워크트리 분리로 피해가려는 설계다.

1.3 MCP 지원 - AI 에이전트를 위한 이슈 트래커

epiq는 별도의 MCP(Model Context Protocol) 서버 바이너리를 제공해 Claude Code 같은 AI 코딩 에이전트가 이슈를 직접 읽고 쓸 수 있게 한다. 뒤에서 다시 다루겠지만, 이 부분이 이 도구를 단순한 "터미널 취향 이슈 트래커"가 아니라 "에이전틱 코딩 시대의 이슈 트래커"로 다시 읽게 만드는 대목이다.

2. 컨텍스트 스위칭이라는 오래된 마찰

epiq가 정면으로 겨눈 문제부터 짚어보자. 이슈 트래커와 코드 저장소가 분리돼 있을 때 생기는 비용이다.

2.1 브라우저 왕복의 비용

이슈 하나를 확인하려고 에디터에서 브라우저로 갔다가 다시 에디터로 돌아오는 왕복은 사소해 보이지만 누적되면 크다. 딥 포커스를 방해받은 뒤 원래 집중 상태로 돌아오는 데 걸리는 시간을 20분 안팎으로 추정하는 연구도 있고, 이런 전환 비용을 연 단위로 환산해 개발자 1인당 상당한 규모의 생산성 손실로 추정하는 업계 분석도 있다. 정확한 숫자보다 중요한 것은 방향이다. 이슈를 보려고 도구를 바꾸는 행위 자체가 이미 비용이라는 것.

2.2 이슈 트래커가 코드와 분리된 이유

그런데 애초에 왜 이슈 트래커는 코드 저장소와 분리된 채 발전해 왔을까. 이유는 단순하다. 이슈 트래커의 핵심 이용자 중 상당수는 코드를 작성하지 않는다. PM·QA·디자이너·고객지원, 때로는 고객 자신이 이슈를 등록하고 상태를 추적한다. 이들에게 Git 저장소에 접근해 커밋을 만들라고 요구하는 것은 애초에 선택지가 아니었다. 그래서 이슈 트래커는 자연스럽게 누구나 로그인해 폼을 채우는 웹 서비스로 자리잡았고, 그 대가로 코드를 다루는 개발자는 매번 창을 하나 더 열어야 하는 처지가 됐다. epiq가 없애려는 마찰은 바로 이 비대칭에서 나온다.

3. 이슈를 코드와 함께 버전관리하는 접근 - 장점

이슈를 Git 객체로 만드는 순간 얻는 이득은 세 가지로 정리된다.

3.1 오프라인에서도 끊기지 않는다

이슈가 로컬 Git 객체로 존재하면 네트워크 연결과 무관하게 읽고 쓸 수 있다. 비행기 안에서, 통신이 불안정한 현장에서, 사내망만 열려 있는 폐쇄 환경에서도 이슈를 등록하고 갱신한 뒤 나중에 push 한 번으로 동기화하면 된다. 클라우드 이슈 트래커가 전제하는 상시 접속을 걷어낸다는 점에서, 이는 단순한 편의 기능이 아니라 설계 철학의 차이다.

3.2 저장소 하나로 이식된다

git clone 한 번으로 코드와 이슈 이력이 통째로 따라온다. 회사 SaaS 계정이 없어도, 심지어 그 SaaS가 서비스를 종료해도 이슈 데이터는 저장소 안에 그대로 남는다. 오픈소스 프로젝트를 포크할 때 이슈까지 함께 딸려오는 경험은 GitHub Issues에서는 사실상 불가능하지만, Git 네이티브 이슈 트래커에서는 기본 동작이다.

3.3 커밋과 이슈의 인과관계가 보존된다

특정 커밋 시점에 어떤 이슈가 열려 있었고 어떤 논의가 오갔는지를, 별도 API 호출 없이 그 시점의 Git 이력만으로 재구성할 수 있다. 오래된 브랜치를 checkout 했을 때 당시의 이슈 상태까지 함께 따라오는 것은, 이슈와 코드가 물리적으로 같은 타임라인 위에 있다는 사실의 자연스러운 결과다. epiq의 time travel 기능도 정확히 이 지점을 겨눈다.

4. 같은 접근의 트레이드오프 - 단점

장점만 보면 불공평하다. 같은 설계가 만드는 대가도 분명하다.

4.1 이벤트 소싱도 충돌을 완전히 없애지 못한다

이벤트 소싱은 병합 충돌의 표면을 줄이지만 완전히 없애지는 못한다. 두 사람이 오프라인 상태에서 같은 이슈를 동시에 고치면, 여러 구현에서 흔히 쓰는 규칙대로 나중에 병합되는 이벤트가 우선하기 쉽고, 그 경우 먼저 반영된 수정이 화면상으로는 조용히 뒤로 밀릴 수 있다. 되돌리는 기능(time travel)이 있다는 것과, 애초에 충돌이 일어났다는 사실을 사용자가 바로 알아채기 쉽다는 것은 서로 다른 문제다.

4.2 저장소가 무거워지고 알림·검색이 약하다

이슈 이력이 쌓일수록 저장소 자체의 용량과 clone 비용이 늘어난다. 별도 브랜치·워크트리로 격리해도 fetch/push 트래픽에서 완전히 자유로울 수는 없다. 더 근본적으로는, 이메일 알림, 전문 검색, 담당자 자동 배정, 번다운 차트 같은 SaaS 이슈 트래커의 관리 기능을 로컬 우선 도구가 같은 수준으로 흉내 내기는 쉽지 않다. 알림이 없다는 것은 사소해 보이지만, 이슈가 열렸다는 사실 자체를 능동적으로 pull 하지 않으면 아무도 모른다는 뜻이다.

4.3 배포 방식에 대한 우려

epiq는 바이너리 설치 스크립트와 npm 패키지 두 경로로 배포된다. 공급망 신뢰가 화두인 시기에 설치 스크립트를 파이프로 바로 실행하거나 npm 전역 설치를 쓰는 방식에 대한 경계심은 흔한 반응이고, 실제로 공개 이후 커뮤니티 논의에서도 배포 방식에 대한 우려가 나왔다. 도구 자체의 설계와는 별개로, 로컬 우선 CLI 도구가 넘어야 할 신뢰의 장벽이다.

5. 기존 방식(GitHub Issues·Jira) 대비 좌표

epiq류의 접근과 SaaS 이슈 트래커를 나란히 놓으면 상충 관계가 뚜렷해진다.

표가 보여주는 것은 우열이 아니라 트레이드오프다. GitHub Issues와 Jira는 조직 규모의 가시성과 성숙한 주변 생태계를 대가로 상시 접속과 계정 종속을 요구한다. epiq는 그 반대편에 서서 접속 독립성과 이식성을 얻는 대신 조직 규모의 가시성을 내준다.

6. 계보 - git-appraise·Fossil·git-issue·그리고 2010년대의 실험들

epiq를 고립된 신제품으로 보면 놓치는 것이 많다. 같은 발상을 시도한 계보가 이미 길다.

6.1 git-appraise - 코드 리뷰를 git-notes에

구글이 공개한 git-appraise는 이슈가 아니라 코드 리뷰를 대상으로 하지만 철학은 같다. 리뷰 요청·코멘트·CI 결과를 별도 서버 없이 git-notes(refs/notes/devtools/*)에 기록해, 저장소를 push/pull하는 것만으로 리뷰 이력이 함께 전파된다. epiq가 이슈에 적용한 "서버 없는 분산 저장"을 코드 리뷰 쪽에서 먼저 증명한 사례로 볼 수 있다.

6.2 Fossil - 올인원이지만 좁은 생태계

SQLite 개발자가 만든 분산 버전관리 시스템 Fossil은 애초부터 티켓 시스템·위키·포럼을 하나의 바이너리에 통합했다. 서버 설정 없이 fossil 하나만 실행하면 버전관리와 이슈 트래킹이 동시에 굴러간다는 점은 지금 봐도 인상적이다. 그러나 이메일 알림을 붙이기 어렵고 GitHub 식의 풀 리퀘스트·코드 리뷰 개념이 티켓 시스템과 맞물리지 않는다는 지적이 꾸준히 나왔다. 통합은 잘 됐지만, GitHub Issues가 제공하는 주변 생태계(알림·통합·검색)에는 미치지 못한다는 평가가 지배적이다.

6.3 git-issue - 텍스트 파일과 양방향 동기화

dspinellis의 git-issue는 이슈를 평범한 텍스트 파일로 저장하면서 GitHub·GitLab과 양방향으로 가져오고 내보낼 수 있게 만든 절충안이다. 서버가 없어도 되고 서버가 죽어도 이슈를 잃지 않는다는 로컬 우선 원칙을 지키면서, 동시에 필요할 때 중앙 플랫폼과 동기화할 통로를 열어 둔 점이 epiq와 결이 다르다. epiq가 아직 이 정도의 양방향 동기화를 전면에 내세우지 않는다는 점은 눈여겨볼 대목이다.

6.4 ticgit·Bugs Everywhere·Ditz·SD·DisTract - 폐허가 된 실험들

2008년 전후 ticgit을 필두로 Bugs Everywhere, Ditz, SD, DisTract 같은 도구들이 거의 동시에 "이슈를 버전관리 시스템 안에" 넣으려 했다. 이 흐름을 되짚은 한 회고 글은 이 생태계를 참호전이 끝난 뒤의 황폐한 벌판에 빗댈 만큼, 대부분이 유지보수자를 잃고 방치됐다고 정리한다. 실패의 공통 원인은 기술이 아니라 두 가지 사회적 조건이었다. 비개발자가 참여할 창구가 없었다는 것, 그리고 팀 전체가 같은 도구를 쓰도록 강제할 수단이 없었다는 것이다. epiq의 이벤트 소싱·워크트리 분리는 이 시절 도구들이 겪은 기술적 결함(충돌·로그 오염)을 상당 부분 개선했지만, 두 가지 사회적 조건은 그대로 남아 있다.

7. 팀 협업의 한계 - 비개발자와 가시성

이 글의 핵심 경고는 여기에 있다. epiq류의 도구가 기술적으로 아무리 정교해져도, 조직 차원의 두 가지 벽은 그대로다.

7.1 비개발자는 터미널로 이슈를 등록하지 않는다

앞선 계보에서 확인한 결론이 그대로 반복된다. 웹 폼에 익숙한 이해관계자에게 vim 키바인딩과 명령줄 모드를 요구하는 순간, 그 사람은 이슈를 등록하지 않거나 다른 채널(메신저·이메일)로 우회한다. epiq는 브라우저 GUI를 함께 제공해 이 장벽을 낮추려 하지만, 그 GUI 역시 계정 기반 중앙 서비스가 아니라 로컬 저장소를 들여다보는 창이라, 이해관계자 각자가 저장소에 접근할 수 있어야 한다는 전제 자체는 바뀌지 않는다.

7.2 대시보드·리포팅·에픽이 없다

Jira의 에픽·스프린트·번다운 차트, GitHub Projects의 칸반과 자동화는 여러 이슈를 조직 단위로 묶어 보고하기 위한 장치다. 로컬 우선 이슈 트래커는 개별 저장소 안에서는 강력하지만, 여러 저장소·여러 팀에 걸친 현황을 한 화면에서 보여주는 중앙 집계 기능은 설계상 후순위로 밀린다. 이슈 수가 적은 소규모 팀에서는 체감되지 않지만, 조직이 커질수록 이 공백은 빠르게 드러난다.

8. 그럼에도 2026년에 다시 주목받는 이유 - 에이전틱 코딩

여기까지만 보면 epiq도 결국 옛 실험들의 반복으로 읽힌다. 그런데 본인이 이 도구를 다르게 보는 지점이 하나 있다.

8.1 협업 대상이 사람만이 아니게 됐다

10년 전 실패의 핵심 원인 - 비개발자 접근성 부재 - 는 지금도 그대로 유효하다. 그런데 2026년에는 새로운 변수가 하나 끼어들었다. 저장소 안에서 함께 일하는 대상이 사람만이 아니라 Claude Code 같은 AI 코딩 에이전트라는 점이다. 에이전트는 vim 키바인딩을 불편해하지 않고, 웹 로그인도 필요 없다. 오히려 로컬 파일·Git 객체로 노출된 상태를 API 호출보다 값싸고 즉각적으로 읽고 쓸 수 있다.

8.2 MCP가 바꾸는 계산

epiq가 별도의 MCP 서버를 제공해 에이전트가 이슈를 직접 다루게 한 것은 이 지점을 정확히 겨눈 설계다. 사람 이해관계자를 위한 웹 GUI가 여전히 필요하다는 결론은 그대로 두되, 에이전트가 반복적으로 이슈를 만들고 상태를 갱신하는 워크플로에서는 "터미널에 있다"는 사실이 더 이상 단점이 아니라 지연 없는 직접 접근이라는 이점이 된다. 이슈 트래커를 코드 저장소 안으로 옮기자는 논의가 코딩 에이전트 시대에 다시 떠오른 이유는, 사람의 컨텍스트 스위칭 문제가 에이전트의 도구 접근성 문제로 다시 쓰였기 때문이라고 본인은 해석한다. 이는 Code as Agent Harness 분석에서 다룬, 코드베이스 자체를 에이전트의 실행 기반으로 보는 관점과도 이어진다.

9. 결론 - 어디에 쓸 것인가

epiq는 진짜 신호이되, 오래된 한계도 함께 상속받은 도구다. 2026년 7월 기준으로 본인이 내리는 실무 판단은 다음과 같다.

9.1 잘 맞는 곳

1인 또는 소규모 개발팀, 오프라인 작업이 잦은 환경, 그리고 AI 코딩 에이전트에 이슈 관리 일부를 맡기려는 워크플로에서는 epiq류의 도구가 즉시 이득을 준다. 특히 이미 터미널 기반 에이전트 도구를 쓰고 있다면, 이슈까지 같은 저장소 안에 두는 편이 파편화를 줄인다.

9.2 신중해야 할 곳

비개발자 이해관계자가 실무에 관여하는 조직, 이메일 알림·리포팅·컴플라이언스 추적이 요구되는 조직이라면 GitHub Issues나 Jira를 주력으로 유지하는 편이 안전하다. 검증되지 않은 배포 채널(npm 전역 설치 등)에 대한 보안 검토도 도입 전에 거쳐야 한다.

9.3 하이브리드라는 절충안

git-issue가 보여준 양방향 동기화 모델처럼, 로컬 이슈 트래커를 주 저장소로 쓰되 필요한 이슈만 중앙 플랫폼으로 내보내는 절충도 가능하다. 정답은 하나의 도구가 아니라, 팀 구성과 협업 대상(사람인지 에이전트인지)에 따라 이슈가 사는 위치를 다르게 설계하는 것이다. Git 워크플로 자체의 변화에 관심이 있다면 Grit의 Git Rust 재작성 분석과 re_gent의 AI 에이전트 버전관리 분석도 함께 참고할 만하다.
