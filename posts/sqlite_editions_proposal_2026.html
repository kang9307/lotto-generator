Rust Editions for SQLite - Opting Into Safer Defaults Without Breaking Old Code

2026-07-17 개발/인프라

이 게시물은 쿠팡 파트너스 활동의 일환으로, 이에 따른 일정액의 수수료를 제공받습니다.

서론: 왜 지금 SQLite의 기본값을 이야기해야 하는가

2026년 7월 기준, SQLite는 세상에서 가장 많이 배포된 데이터베이스 엔진일 것이다. 브라우저, 모바일 앱, 데스크톱 프로그램, 임베디드 기기 안에 조용히 박혀 있다. 그런데 이 성공의 근본 이유 - 지독할 정도의 하위 호환성 - 가 동시에 발목을 잡는다. SQLite는 30년 가까이 쌓인 애플리케이션을 절대 깨지 않겠다는 약속을 지켜 왔고, 그 대가로 지금 기준으로는 안전하지도 빠르지도 않은 기본값을 그대로 물려받았다.

최근 hada.io(GeekNews)에서 화제가 된 mort.coffee의 글 "SQLite should have (Rust-style) editions"는 이 문제를 정확히 짚는다. 글쓴이는 실무에서 겪은 버그들 - 문자열 '1'이 정수 컬럼에 그대로 박혀 있던 사고, 외래 키가 강제되지 않아 발생한 참조 무결성 붕괴, 동시 쓰기 시 애플리케이션이 그냥 죽어버리는 SQLITE_BUSY - 을 근거로, Rust의 '에디션(edition)'과 같은 메커니즘을 SQLite에 도입하자고 제안한다. 이 글은 그 제안을 그대로 옮기는 대신, 왜 하위 호환성이 소프트웨어 진화의 보편적 걸림돌인지, Rust 에디션이 실제로 어떻게 이 문제를 푸는지, 그리고 그 해법을 SQLite라는 완전히 다른 종류의 소프트웨어에 이식할 때 무엇이 실제로 어려운지를 직접 파고든다.

1. 하위 호환성이라는 보편적 문제

1.1 소프트웨어는 늙는다, 그러나 못 바꾼다

모든 성숙한 소프트웨어는 같은 딜레마를 마주한다. 처음 설계할 때 내린 판단이 시간이 지나면 실수로 드러나지만, 이미 그 판단에 기대어 동작하는 코드가 세상에 널려 있어 손을 댈 수 없다. C의 널 종료 문자열, PHP의 느슨한 비교 연산자, JavaScript의 암묵적 타입 변환이 모두 같은 계보에 있다. 문제를 알면서도 고치지 못하는 이유는 단순하다. 기본값을 바꾸는 순간 그 위에 얹힌 수많은 애플리케이션이 예고 없이 깨지기 때문이다.

1.2 SQLite가 유별나게 어려운 이유

SQLite는 이 딜레마를 다른 소프트웨어보다 더 극단적으로 안고 있다. 첫째, SQLite는 서버가 아니라 애플리케이션에 링크되는 라이브러리이자 파일 포맷이다. 데이터베이스 파일 하나가 만들어진 시점의 애플리케이션과 10년 뒤 그 파일을 여는 애플리케이션이 전혀 다른 버전의 SQLite를 쓸 수 있다. 둘째, SQLite 공식 프로젝트 자체가 "장기 지원(long-term support)"을 핵심 설계 목표로 명시하며, 파일 포맷의 초장수명을 최우선 가치로 삼는다. 이 두 특성 때문에 SQLite에서 기본값을 바꾸는 결정은 일반 애플리케이션 라이브러리보다 훨씬 무겁다.

2. Rust 에디션 메커니즘 뜯어보기

2.1 에디션이 바꾸는 것과 바꾸지 않는 것

Rust는 1.0 출시 당시 "1.x에서 컴파일되는 코드는 이후 어떤 1.y에서도 컴파일된다"는 안정성 약속을 했다. 언어가 진화하며 이 약속과 충돌하는 개선이 쌓이자, Rust 팀은 Cargo.toml의 edition 필드(2015, 2018, 2021, 2024)로 크레이트 단위 옵트인 메커니즘을 도입했다. 핵심 보장은 이렇다. 한 에디션에서 한 번 컴파일되는 코드는 그 에디션 안에서 영구히 컴파일된다. 기존 크레이트는 개발자가 명시적으로 edition 필드를 올리기 전까지 자동으로 새 규칙을 적용받지 않는다. 마이그레이션 부담을 줄이기 위해 cargo fix --edition이 기계적으로 처리 가능한 변경 대부분을 자동 적용한다.

2.2 같은 바이너리 안에서 에디션이 섞이는 이유

Rust 에디션 설계에서 가장 정교한 부분은 에디션 간 상호운용이다. 2015 에디션으로 작성된 크레이트가 2024 에디션 크레이트에 의존하거나, 그 반대도 가능하다. 이것이 가능한 이유는 에디션 차이가 컴파일 시점의 파싱과 문법 해석에만 영향을 주고, 컴파일이 끝난 산출물에는 에디션의 흔적이 남지 않기 때문이다. 다시 말해 에디션은 소스 코드를 읽는 방식에 대한 합의일 뿐, 런타임 의미론이나 바이너리 형식을 바꾸는 것이 아니다. 이 좁고 명확한 스코프 덕분에 "옛 코드와 새 코드가 한 프로젝트 안에 공존"하는 것이 원리적으로 보장된다.

3. SQLite의 문제적 기본값들

3.1 느슨한 타입 - type affinity와 STRICT 테이블

SQLite는 컬럼에 선언한 타입을 강제하지 않는다. 대신 TEXT, NUMERIC, INTEGER, REAL, BLOB 다섯 가지 "타입 어피니티(affinity)"라는 개념을 쓴다. 이는 선호하는 저장 형식일 뿐이다. INTEGER로 선언한 컬럼에도 무손실 변환이 불가능하면 문자열이 그대로 저장된다. 이는 실무에서 실제로 정수 컬럼에 문자열 '1'과 '0'이 섞여 들어가는 사고로 이어진다. SQLite 3.37.0(2021-11-27)부터는 CREATE TABLE ... STRICT로 테이블 단위 엄격 타입 검사를 켤 수 있다. STRICT 테이블은 모든 컬럼에 INT, INTEGER, REAL, TEXT, BLOB, ANY 중 하나의 타입 지정을 요구하고, 무손실 변환이 안 되면 SQLITE_CONSTRAINT_DATATYPE 오류를 낸다. 문제는 이것이 새 테이블에만 선택적으로 적용되는 기능이라는 점이다. 기존 테이블, 그리고 무엇보다 이 기능의 존재를 모르는 대다수 개발자에게는 여전히 느슨한 기본값이 그대로다.

3.2 foreign_keys 기본 OFF

SQLite는 오랫동안 외래 키 구문을 파싱만 하고 강제하지 않았다. 나중에 실제 강제 기능을 추가했을 때, 이를 기본으로 켜 버리면 예전부터 느슨한 참조 무결성에 기대 온 애플리케이션이 본 적 없는 오류 코드를 받고 깨질 위험이 있었다. 그래서 PRAGMA foreign_keys는 지금도 기본 OFF이며, 이는 연결 단위 설정이라 매 연결마다 다시 켜야 한다. 이 상태에서는 부모 행이 삭제돼도 자식 행이 고아로 남고, SQLite의 ROWID 재사용 알고리즘과 겹치면 삭제된 사용자의 게시물이 나중에 재활용된 ID를 가진 새 사용자에게 조용히 재배정되는 조용한 데이터 손상까지 이어질 수 있다.

3.3 WAL이 아닌 롤백 저널, 그리고 SQLITE_BUSY

SQLite의 기본 원자적 커밋 방식은 전통적인 롤백 저널이다. 이후 도입된 WAL(Write-Ahead Logging) 모드는 PRAGMA journal_mode = WAL로 옵트인해야 하며, 읽기와 쓰기를 훨씬 잘 동시 진행시켜 성능을 끌어올린다. 그러나 WAL은 네트워크 파일시스템에서 동작하지 않고 추가 -wal·-shm 파일이 붙는다는 제약이 있어 기본값으로 강제되지 않았다. 동시 쓰기 상황에서는 여러 쓰기가 몰리면 즉시 SQLITE_BUSY 오류가 반환된다. PRAGMA busy_timeout으로 일정 시간 재시도하게 완화할 수 있지만, 락 에스컬레이션 국면에서는 이마저도 완전한 해결책이 아니라는 지적이 개발자 커뮤니티에서 꾸준히 나온다.

4. 에디션 방식이 SQLite에 맞는 이유

mort.coffee의 제안은 단순하고 우아하다. PRAGMA edition = 2026; 같은 한 줄로 그 시점의 "권장 기본값 묶음"을 한 번에 옵트인하자는 것이다. 이 묶음에는 foreign_keys = ON, 합리적인 busy_timeout, journal_mode = WAL, 그리고 STRICT 테이블을 표준으로 삼는 변경이 포함될 수 있다. 이 방식의 장점은 명확하다. 기존 애플리케이션은 에디션을 지정하지 않는 한 옛 동작 그대로 유지되므로 아무것도 깨지지 않는다. 반면 새 프로젝트나 마이그레이션을 감당할 여력이 있는 팀은 한 줄로 여러 안전장치를 한꺼번에 켤 수 있다. 개별 PRAGMA를 하나씩 기억해서 켜야 하는 지금 방식보다 "안전한 기본값 세트"를 표준화된 이름으로 부를 수 있다는 것 자체가 인지 부담을 크게 줄인다.

5. 난제 - 임베디드·초호환성 철학과의 충돌

5.1 설정의 스코프가 제각각이다

Rust 에디션은 크레이트라는 명확한 컴파일 단위 하나에 붙는다. 그러나 SQLite의 안전 관련 설정은 스코프가 제각각이다. foreign_keys는 연결 단위, journal_mode는 사실상 데이터베이스 파일 단위, STRICT는 테이블 단위다. hada.io 토론에서도 지적됐듯, 통합 PRAGMA를 파일 단위로 둘지 연결 단위로 둘지부터 정해야 하고, 잘못 설계하면 구버전 라이브러리가 새 에디션 플래그가 붙은 파일을 열었을 때 오동작하거나 파일을 손상시킬 위험이 생긴다.

5.2 파일 이식성과 초호환성 철학의 충돌

SQLite 데이터베이스 파일은 태생적으로 시스템과 애플리케이션 버전을 넘나들며 이동한다. 이는 Rust 크레이트가 컴파일 시점에 한 번 고정되는 것과 근본적으로 다르다. 파일에 에디션 정보를 새겨 넣는 순간, 그 파일을 열 수 있는 SQLite 버전의 하한선이 생긴다. 오래된 임베디드 기기나 레거시 시스템에 박혀 수십 년을 가야 하는 파일 포맷에 이런 하한선을 두는 것은, SQLite가 지금까지 지켜 온 초호환성 원칙과 정면으로 부딪힌다.

5.3 테스트 매트릭스와 조합 폭발

에디션이 여러 개 존재하고 각 에디션이 여러 기능을 묶는다면, SQLite 코어 개발자는 사실상 "에디션 × 플랫폼 × 컴파일 옵션"의 조합 전체를 검증해야 한다. Rust는 컴파일러 하나가 표준을 쥐고 있어 이 부담을 감당할 수 있었지만, SQLite는 수많은 바인딩(Python, Node.js, 각종 모바일 SDK)을 거쳐 쓰이므로 에디션 도입이 그 바인딩 생태계 전체에 파급되는 테스트·문서화 부담을 만든다.

6. 다른 언어·DB의 버저닝 전략과 비교

6.1 Python의 __future__ - 점진적 의무화

Python은 from __future__ import 기능 구문으로 미래 언어 기능을 모듈 단위로 옵트인하게 한 뒤, 정해진 "의무화 릴리스" 시점부터는 그 기능이 기본이 되는 점진적 전환 모델을 오래 써 왔다. 이는 Rust 에디션처럼 옵트인이지만, 결국 특정 시점 이후에는 강제로 기본이 된다는 점에서 SQLite처럼 영구히 옛 동작을 보장하는 방식과는 결이 다르다.

6.2 JavaScript의 "use strict"

ES5는 스크립트나 함수 맨 위에 "use strict"를 선언하는 것만으로 더 엄격한 의미론을 옵트인하게 했다. 기존 ES3 코드는 이 지시문이 없으면 전혀 영향을 받지 않는다. 스코프가 파일·함수 단위로 명확하다는 점에서 Rust 에디션과 유사하지만, 버전이라는 개념 없이 "느슨 모드 대 엄격 모드"라는 이분법 하나만 존재한다는 점에서 더 단순하다.

6.3 MySQL이 실제로 기본값을 바꾼 사례

모든 DB가 SQLite처럼 옵트인 노선을 택한 것은 아니다. MySQL은 5.7.5(2015년)부터 STRICT_TRANS_TABLES를 sql_mode 기본값에 포함시켜, 잘못된 값을 자동 형변환하거나 조용히 자르는 대신 오류를 내도록 기본 동작 자체를 바꿨다. 이는 강제 전환 노선이다. 새로 설치하는 MySQL은 더 안전해졌지만, 예전의 느슨한 동작에 기대 온 애플리케이션은 업그레이드 시점에 실제로 깨졌고, 많은 운영자가 마이그레이션 기간 동안 명시적으로 sql_mode를 낮춰 우회해야 했다. SQLite·Rust식 옵트인 전략과 정확히 대비되는 지점이다. MySQL은 "언젠가는 다 같이 새 기본값으로", SQLite/Rust는 "옛 코드는 절대 안 건드리고 새 코드만 새 기본값으로"를 택한 셈이다.

7. 실무 시사 - 지금 당장 쓸 수 있는 것

7.1 세 줄 PRAGMA로 당장 안전해지기

공식 에디션 메커니즘이 나오기 전이라도, 아래 세 PRAGMA를 매 연결 시작 시 실행하는 것만으로 이 글에서 지적한 문제 대부분을 완화할 수 있다.

PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;

첫 줄은 참조 무결성을 강제해 고아 행과 조용한 데이터 손상을 막는다. 둘째 줄은 동시 읽기·쓰기 성능을 끌어올린다(단, 로컬 파일시스템에서만 유효하고 네트워크 드라이브에서는 동작하지 않는다는 점에 유의해야 한다). 셋째 줄은 동시 쓰기 충돌 시 즉시 실패하는 대신 5초간 재시도하게 만든다.

7.2 신규 테이블은 STRICT로

새로 만드는 테이블에는 STRICT 옵션을 붙여 타입 안전성을 확보할 수 있다.

CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  age INTEGER
) STRICT;

이렇게 하면 age 컬럼에 문자열 '30'을 넣으려는 시도는 조용히 저장되는 대신 오류로 즉시 드러난다.

7.3 여전히 손으로 챙겨야 하는 한계

이 모든 PRAGMA는 애플리케이션 코드가 연결마다 명시적으로 설정해야 하고, ORM이나 커넥션 풀을 거치면 누락되기 쉽다. 에디션 메커니즘이 실제로 나온다면 이 반복 작업을 "한 줄 선언"으로 표준화할 수 있다는 것이 mort.coffee 제안의 핵심 가치다. 다만 5장에서 짚었듯, 그 표준화가 SQLite의 파일 이식성 철학과 충돌하지 않게 설계하는 일은 결코 간단하지 않다.

결론

SQLite의 느슨한 기본값 문제는 SQLite만의 결함이 아니라, 성숙한 소프트웨어가 예외 없이 마주하는 하위 호환성 딜레마의 한 사례다. Rust 에디션은 이 딜레마를 "옛 코드는 절대 안 건드리고, 새 코드만 옵트인으로 새 규칙을 받는다"는 방식으로 풀어 우아한 선례를 남겼다. 이를 SQLite에 그대로 이식하자는 mort.coffee의 제안은 방향은 옳지만, 크레이트 단위로 깔끔히 나뉘는 컴파일 언어와 달리 연결·파일·테이블 단위로 설정이 흩어져 있고 파일 자체가 수십 년을 이동해야 하는 임베디드 데이터베이스 엔진에 옮기려면 스코프 설계와 하위 호환 검증에서 훨씬 많은 난제를 풀어야 한다. 공식 에디션이 나오든 안 나오든, 지금 당장은 foreign_keys, journal_mode, busy_timeout, STRICT 테이블을 프로젝트 표준으로 명시적으로 켜 두는 것이 가장 현실적인 대응이다.
