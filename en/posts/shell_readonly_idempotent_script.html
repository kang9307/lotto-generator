Idempotent Shell Scripts - Six Patterns That Break on the Second Run

Reproduced, not theorized - real execution output and three-run hash comparison

Jul 29, 2026 Dev & Infra

Introduction: The Script That Cannot Answer 'Can I Just Run It Again?'

The deployment script died halfway through. The log shows it made it through five of eight steps. The cause was found quickly, and only one question is left. 'Can I just run this again?'

The moment you cannot answer that question on the spot, the night gets long. You have to read the script from the top and work out, line by line and by hand, what this particular line does on a second run. And in most cases you never finish the exercise, because it ends with 'I will just do steps five through eight manually.' The part you did by hand leaves no record, and the next person has no idea why the server state does not match the script.

Idempotence is the property that lets you answer yes to that question in half a second. It is not a matter of memorising a definition. It is a matter of knowing exactly what each line of your script does on its second execution. That is why this article does not open with a definition. It opens with real output from actually running things twice and watching them break.

The order of business is as follows. First, six patterns that genuinely break, reproduced one at a time, each with its safe form attached. Then marker blocks as a general-purpose remedy, and a procedure for proving with hashes that a re-run produces the same result. Finally, the design for resuming after a partial failure and the conditions under which a lock is actually required.

One piece of terminology first. What engineers casually lump together as idempotent is really three distinct layers. Drawing this distinction up front makes everything that follows much simpler.

LevelWhat it guaranteesWhat it does not guaranteeTypical mechanism
(1) Re-run safeRunning twice does not break (no abort on error)That the result is the samemkdir -p, rm -f
(2) ConvergentAny number of runs reach the same final stateRemoval of human-introduced driftCheck-then-change, marker blocks
(3) Self-healingDrifted state is pulled back to the target stateAnything not declaredWhole-block replacement, whole-file generation

Most incidents happen when someone implements only level 1 and believes they have reached level 2. Swapping in mkdir -p and then declaring the script fixed and idempotent is the classic case. The reproductions below show exactly where that gap sits.

Safety notice before you run anything. Every reproduction in this article was performed inside a freshly created temporary directory only. Wherever rm -rf appears in the text, it deletes that temporary directory or a path beneath it, nothing else. Do not follow along on a real server. In particular, the form rm -rf "$DIR" becomes rm -rf "" when $DIR is empty, which can sweep through somewhere you never intended, so any deletion driven by a variable must be preceded by a guard such as [ -n "$DIR" ] && [ "$DIR" != "/" ]. Before a script goes into cron or CI, running it once in a --check style dry-run mode and reading the target paths with your own eyes is the safer habit.

1. Test Environment and Verification Method

Every block of output below is pasted verbatim from a real run. The reproduction environment was as follows.

===== T0 ENVIRONMENT =====
MINGW64_NT-10.0-19045 3.5.7-882031da.x86_64
GNU bash, version 5.2.37(1)-release (x86_64-pc-msys)
sed (GNU sed) 4.9
grep (GNU grep) 3.0
sha256sum (GNU coreutils) 8.32

This is MSYS2 / Git Bash on Windows 10. Because the toolchain is the GNU family, behaviour matches Linux, but three things are constraints specific to this environment and are declared up front. They are the information you need in order to judge the results for yourself.

  • Symbolic links are handled as file copies under the default configuration. To create real links, the runs were performed with MSYS=winsymlinks:sys set.
  • POSIX permission bits are not reflected faithfully on NTFS. In practice the mode still displayed as 644 after a chmod 600. For that reason no claim about permission idempotence in this article is backed by execution output. Those items appear only as rules in the checklist.
  • There is no crontab or flock binary here. For cron, the text that crontab -l would print was emulated in a file so that only the line manipulation logic was verified, and for locking, the demonstration used the atomicity of mkdir instead of flock.

Verification mixed three signals: exit status (did the command succeed), file contents (what was left behind), and SHA-256 hashes (is the result of repeated runs identical). The hash in particular is the only tool that separates looks the same from is the same, so it recurs throughout.

2. Pattern 1: Appends Accumulate Silently

This is the most common one, and the one discovered last, because it never raises an error. Take a script that adds a single PATH line to .bashrc and run it twice.

-- run 1 --
export PATH=/opt/tool/bin:$PATH
-- run 2 (same command again) --
export PATH=/opt/tool/bin:$PATH
export PATH=/opt/tool/bin:$PATH
lines: 2

The exit status is 0 both times. Nobody tells you anything failed. If the line is a PATH entry, the worst outcome is a duplicated path element, but attach a cron job that grows the same file a little on every tick and the config file is thousands of lines long a few months later. Real incidents usually arrive in exactly this shape.

2.1 The Safe Form: Check for Existence, Then Append

LINE='export PATH=/opt/tool/bin:$PATH'
grep -qxF -- "$LINE" safe.conf || printf '%s\n' "$LINE" >> safe.conf

Here is the result over three runs. Both the line count and the hash stay pinned.

run1 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run2 -> 1 line(s) | sha=0a0746b7d8c9bd1f
run3 -> 1 line(s) | sha=0a0746b7d8c9bd1f

2.2 The Trap: One grep Option Flips the Outcome

The x and the F in -qxF are not decoration. Drop either one and you get an incident in the opposite direction, respectively.

Trap A: a comment is mistaken for already configured. The target file already contains the line, commented out. This is common. Somebody switched it off temporarily and forgot.

file: #export PATH=/opt/tool/bin:$PATH
grep -qF  -> found (skips append) ... setting is never applied
grep -qxF -> not found (correct: a comment is not an active setting)

With only -F, which is a substring match, the commented line matches too. The script quietly reports that it is already done on every single run, and the setting is never applied. Because there is no error, this can persist for months. It is -x (whole-line match) that prevents it.

Trap B: regex metacharacters let duplicates pile up. This is the opposite direction. If the line you want to insert contains characters such as [, ], . or *, then grep -q reads them as a regular expression.

file: PATH=/opt/tool[1]/bin
grep -q   -> NOT found ([1] read as a character class) -> duplicate append
grep -qxF -> found (correct)
after 3 runs: grep -q => 4 lines | grep -qxF => 1 lines

[1] is a character class meaning the single character 1, so it does not match the literal text [1]. The check therefore reports not found every time, and three runs leave four lines. It is -F (fixed string) that prevents this one.

2.3 An Even Quieter Trap: grep Exit Code 2

This one you only learn from the manual. grep returns three different exit codes. These are the values observed directly.

match      -> 0
no match   -> 1
read error -> 2  (|| append treats this like 'no match')

The form grep -qxF ... || append cannot distinguish 1 (no match) from 2 (error). When the file is unreadable or the path is wrong, the script concludes the line is absent and keeps appending. To be precise you have to branch on the exit status.

grep -qxF -- "$LINE" "$F"; rc=$?
case $rc in
  0) : ;;                                   # already present
  1) printf '%s\n' "$LINE" >> "$F" ;;       # absent -> append
  *) echo "grep failed (rc=$rc): $F" >&2; exit 1 ;;   # error -> stop
esac

3. Pattern 2: Exit Codes from mkdir and rm Cut the Script in Half

This is the best known item, so it gets a short treatment, with the space spent on the lesser known side effect.

-- mkdir d1 (run 1) --
exit=0
-- mkdir d1 (run 2) --
mkdir: cannot create directory 'd1': File exists
exit=1
-- mkdir -p d1 (run 3) --
exit=0

-- rm f1 (run 1) --
exit=0
-- rm f1 (run 2) --
rm: cannot remove 'f1': No such file or directory
exit=1
-- rm -f f1 (run 3) --
exit=0

The POSIX specification defines this behaviour. Of mkdir -p it says each dir operand that names an existing directory shall be ignored without error, and of rm -f it says it shall not write a diagnostic message or modify the exit status for operands that do not exist. What the options do is exactly that, and no more.

3.1 The Real Damage Shows Up When set -e Is Involved

Exit code 1 by itself is not a big deal. The problem is that in a script running under set -e, every step after that point disappears. Here is a three-step script run twice.

-- seq.sh run 1 --
  [step 2] place config files
  [step 3] restart service
exit=0
-- seq.sh run 2 --
mkdir: cannot create directory '.../s/stage': File exists
exit=1  <- steps 2 and 3 never ran

On the re-run it is blocked at step 1, the directory creation, so neither the config placement nor the service restart happens. Yet the script only says failed. It does not say how far it got. The operator reads the last line of the log, decides it is a directory problem, and only discovers much later that the service is still running on the old configuration.

3.2 What the Options Do Not Do for You

  • mkdir -p ignores existence only. It does not bring an existing directory's owner or permissions in line with the target values. Since -m applies only at creation time, guaranteeing permissions means nailing down chmod and chown as separate lines. (As stated earlier, permission bits cannot be verified in this environment, so no execution output is offered for them.)
  • rm -f only looks the other way for files that do not exist. If the thing you meant to delete is a directory, it still fails.
  • Neither one has any opinion about content. A directory existing and its interior being in the target state are two different statements.

4. Pattern 3: On the Second Run, ln -s Burrows Inside the Link

This item is the one most worth reproducing in the whole article, because it leaves a wrong result without ever failing. It is the code that moves the current symlink to a new release during a zero-downtime deployment.

-- ln -s rel_a current (run 1) --
exit=0 | readlink=rel_a
-- ln -s rel_b current (run 2) --
exit=0

The second run returns exit code 0. It looks like success. Let us check what was actually created.

## ln -sf on a symlink that points to a directory
ln -sf exit=0
readlink current = rel_a   <- still points at rel_a
ls current/:
FROM_A
rel_b
what was actually created: lrwxrwxrwx 1 Karyu 197121 5 Jul 29 05:13 rel_a/rel_b -> rel_b
  -> it did not repoint the link; it created a new link INSIDE the target directory

The last line is the whole point. When current is a symlink pointing at a directory, ln -sf rel_b current follows current as a directory and creates a new link named rel_b inside it. readlink current still says rel_a.

Think about what that means in production. The deployment script returns success, monitoring is green, and the service keeps running the old version. On top of that, an unexplained link accumulates inside the previous release directory. Once per deployment.

4.1 The Safe Form: ln -sfn

The GNU coreutils manual describes -n in ln as treating the link name as a normal file if it is a symbolic link to a directory. Meaning: do not descend into it. Here is the result over three runs.

run1 -> readlink=rel_b | rel_a contains: FROM_A
run2 -> readlink=rel_b | rel_a contains: FROM_A
run3 -> readlink=rel_b | rel_a contains: FROM_A

All three runs stay pinned to rel_b, and nothing beyond FROM_A was added inside rel_a. The practical rule collapses to one sentence. When you swap a symlink that points at a directory, always add -n. Using -T (--no-target-directory) enforces it even more strictly.

An even safer approach. Making a symlink swap genuinely atomic takes two steps: create the link under a temporary name, then swap it in with mv -T. Internally ln -sfn has a moment where it removes and recreates, and in that instant there can be a point at which current does not exist. On a high-traffic path that difference matters.

5. Pattern 4: sed -i Returns Success and Lies About It

The re-run safety of sed -i splits three ways depending on the pattern. Each was reproduced.

5.1 Case A: Safe When the Result No Longer Matches the Pattern

sed -i 's/^timeout = 30$/timeout = 60/' a.conf

run1 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run2 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3
run3 sha=ca1a53713b3fbd1d | timeout = 60 retries = 3

The substitution result timeout = 60 does not overlap with the pattern ^timeout = 30$. From the second run onward there is no match and the file does not change. The hash is identical across all three runs. This is the case that is idempotent by luck.

5.2 Case B: Unbounded Growth When the Result Matches Again

sed -i 's#PATH=#PATH=/opt/bin:#' b.conf

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/opt/bin:/usr/bin
run3: PATH=/opt/bin:/opt/bin:/opt/bin:/usr/bin

The substitution result still contains PATH=, so the next run matches again. Every run adds another path element. This is far less visible than the append accumulation earlier, because the line count never grows. You only find it by opening the file and reading one line all the way to the end.

5.3 Case C: It Does Nothing and Still Reports Success

sed -i 's/^debug = true$/debug = false/' c.conf
exit=0 | content=debug = false  <- exit code is not evidence that it applied

The file already contained debug = false, so the pattern matched nothing at all. And yet sed returns exit code 0. That is not a defect, it is the design. sed does not report how many substitutions it performed through the exit status.

The practical rule that falls out of this matters. The exit status of sed -i is not evidence that a change was applied. To confirm that a setting really took effect you have to read the result back after the substitution and inspect it. Silent failure is the most frightening kind precisely because a typo in the file path or a mismatched anchor also returns 0.

5.4 The Safe Form: Test the Target State First, Verify Afterwards

TARGET='PATH=/opt/bin:/usr/bin'
grep -qxF "$TARGET" d.conf || sed -i 's#^PATH=/usr/bin$#PATH=/opt/bin:/usr/bin#' d.conf
grep -qxF "$TARGET" d.conf || { echo "not applied"; exit 1; }

run1: PATH=/opt/bin:/usr/bin
run2: PATH=/opt/bin:/usr/bin
run3: PATH=/opt/bin:/usr/bin
post-check: target state reached (0)

Three things happen at once here. (1) The target state is tested first, so if it has already been reached nothing is touched; (2) the pattern is bracketed with ^...$ anchors so the result cannot satisfy the pattern again; and (3) the file is read back after substitution to confirm the state was actually reached. With all three in place, even sed -i can be used safely.

6. Pattern 5: Cron Registration Multiplies on Every Run

There is a widespread idiom: (crontab -l; echo "$JOB") | crontab -. Here is what three runs produce.

run1 -> sync.sh lines: 1
run2 -> sync.sh lines: 2
run3 -> sync.sh lines: 3
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
*/5 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1
  -> a job meant to run every 5 minutes now starts 3 times per tick

The severity of this result is in a different class from the other patterns. The earlier ones were about files getting messy; this one is about multiple copies of the same job starting simultaneously. A sync script means several processes touching the same files; a backup means bandwidth split three ways with all copies running slow; a database cleanup means lock contention. And because the load becomes exactly triple after running provisioning three times, the cause is hard to pin down.

6.1 The Safe Form: Delete, Then Re-Add

The right answer is not skip if present but remove every line that references this script, then insert the new one. The reason follows shortly.

{ crontab -l 2>/dev/null | grep -vF '/opt/app/bin/sync.sh'
  printf '%s\n' "$JOB"; } | crontab -

run1 -> lines: 1 | sha=7352c0d47610f2d1
run2 -> lines: 1 | sha=7352c0d47610f2d1
run3 -> lines: 1 | sha=7352c0d47610f2d1

One line on all three runs, with an identical hash. The reason this beats the skip-if-present approach is schedule changes. An existence-only check will look at */5 changed to */10, decide it is already there, and leave the old line untouched. The delete-and-insert approach does not. It was also checked against unrelated jobs.

-- schedule changed to */10, with an unrelated job present, run twice --
0 3 * * * /opt/other/backup.sh
*/10 * * * * /opt/app/bin/sync.sh >> /var/log/sync.log 2>&1

The backup.sh line survived untouched and only the sync.sh line was refreshed with the new schedule. The critical question here is how narrowly you scope the filter string. Filtering on a common name such as sync.sh could wipe out another team's /opt/legacy/sync.sh as well. Using the full absolute path, or the marker block approach below, is safer.

There is also the option of not writing to crontab directly. Dropping a single complete file into /etc/cron.d/ is itself a whole-file replacement, which makes duplication structurally impossible. Write to a temporary file and swap it in with mv and you get atomicity as well. Do check your distribution's documentation first, because filename rules (names containing a dot are ignored, for example) and whether a user field is required differ between distributions.

7. Pattern 6: Commands That Look Idempotent but Are Not

If everything so far was the category of known traps, this section covers commands most people assume are idempotent.

7.1 cp -r: The First Run and Later Runs Produce Different Structures

cp -r src dst   # three times

run1: dst dst/a.txt
run2: dst dst/a.txt dst/src dst/src/a.txt
run3: dst dst/a.txt dst/src dst/src/a.txt
  -> run 1 produced dst/a.txt; from run 2 on, dst/src/a.txt appeared as well

The cause is that the meaning of cp -r changes depending on whether the destination exists. If dst does not exist, it makes dst a copy of src (dst/a.txt). If dst does exist, it puts src inside dst (dst/src/a.txt). Same command, but a new server and a redeployed server end up different. This is the perennial cause of the symptom described as a clean install works but an update goes strange.

The safe form is to name the contents rather than the directory.

cp -r src/. dst2/   # three times

run1: dst2 dst2/a.txt
run2: dst2 dst2/a.txt
run3: dst2 dst2/a.txt

7.2 mv: The Second Run Simply Fails

run1 exit=0
mv: cannot stat 'mvsrc/data.bin': No such file or directory
run2 exit=1

mv is fundamentally not a repeatable command, because the source disappears. To make it repeatable you either condition it on the source existing, as in [ -e "$SRC" ] && mv ..., or replace mv altogether with an approach that describes the target state (copy then verify, or decide based on the destination).

7.3 The sed Insert Command: a Is Just Another Append

sed -i '/^\[core\]$/a\    autocrlf = input' gitcfg.ini   # three times

run1: [core]|    autocrlf = input|
run2: [core]|    autocrlf = input|    autocrlf = input|
run3: [core]|    autocrlf = input|    autocrlf = input|    autocrlf = input|

Using sed does not make something a substitution. The a (append) command is an append, exactly as its name says, so it behaves the same as >>. The safe form branches two ways: replace if present, insert if absent.

if grep -q '^[[:space:]]*autocrlf[[:space:]]*=' f.ini; then
  sed -i 's/^[[:space:]]*autocrlf[[:space:]]*=.*/    autocrlf = input/' f.ini
else
  sed -i '/^\[core\]$/a\    autocrlf = input' f.ini
fi

run1 sha=94ff19468316c369 | [core]|    autocrlf = input|
run2 sha=94ff19468316c369 | [core]|    autocrlf = input|
run3 sha=94ff19468316c369 | [core]|    autocrlf = input|

7.4 Timestamps and Random Values: They Destroy Verifiability Itself

If date output or $RANDOM ends up inside a file, that file has a different hash on every run. Regardless of whether the logic is idempotent, you have lost the means of verification. The rule is simple. Separate state files from audit logs. Record when and what was done in a separate log, and write only deterministic content into the configuration files the script manages.

7.5 Summary: Re-Reading the Three Levels of Re-Run Safety

  • mkdir -p and rm -f deliver level 1, re-run safety, and nothing beyond it.
  • A grep -qxF guard before an append, and ln -sfn, reach level 2, convergence.
  • Marker block replacement and whole-file generation go all the way to level 3, self-healing. They undo human edits made inside the block.
  • cp -r, mv and sed ... a\ belong to no level at all. Unwrapped, they are incidents waiting to happen.

8. Marker Blocks: Why the Hash Stays the Same Across Three Runs

Every defence so far has been line-oriented. Once you have more than five lines to manage, that approach gets messy fast. That is when you reach for a marker block. It is exactly the mechanism Ansible's blockinfile module uses when it defaults to # BEGIN ANSIBLE MANAGED BLOCK and # END ANSIBLE MANAGED BLOCK.

The idea is simple. Mark the region you own with markers, and swap out everything between them as a unit. There is no longer any need to check for the existence of individual lines.

apply_block(){
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}

This function was applied three times to a file that already contained three hand-maintained lines.

run1 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
run2 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
run3 sha256=5d22eee7c5ef0991451ca494fdff31a15f39c10ab6a1626136c7d990f0beb8b6
-- resulting file --
# hand-maintained section
Port 22
PermitRootLogin no
# BEGIN braindetox-keepalive
ClientAliveInterval 60
ClientAliveCountMax 3
# END braindetox-keepalive
-- content outside the markers --
OK: the hand-maintained 3 lines are untouched

The hash is completely identical across all three runs, and the existing configuration outside the markers was not damaged. That is level 2, convergence.

8.1 When a Value Changes, Only the Block Is Updated

### ClientAliveInterval 60 -> 30, three more runs
run4 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
run5 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
run6 sha256=1a402ffc0e2c088220b5e90471c69c330f6e4925ab579c3f0db1dc17271f3b18
total lines: 7 (no accumulation)

It re-pins to a new hash for the new value. The line count stays at 7. Blocks do not stack up.

8.2 What Append Can Never Do: Removing an Entry

This is where the real value of marker blocks lies. Let us shrink the managed entries from two lines to one.

# BEGIN braindetox-keepalive
ClientAliveInterval 30
# END braindetox-keepalive
  -> append-based approaches cannot do this: a removed entry would linger

ClientAliveCountMax is gone. This is impossible with a skip-if-present approach. Delete the line from the script and it still lives forever in the file on every already-deployed server. Give it a few years and every server accumulates a different set of settings nobody can explain. With a marker block the whole block is the declaration, so the problem cannot arise structurally.

8.3 Cautions When Using Marker Blocks

  • Make the tag unique. Several scripts may insert blocks into the same file. Write the owner and the purpose together, as in # BEGIN myapp-nginx-upstream.
  • Comment characters differ by file format. If the format uses ; or // rather than #, the markers have to follow that syntax too. Otherwise the parser dies.
  • If a human deletes the markers, the next run appends a fresh block and you get duplicates. Putting a do-not-edit notice on the first line of the block helps.
  • Do not use this on structured formats such as JSON or YAML. Line-based insertion breaks them. Read and write those with a proper parser.
  • Manage only what is inside the block. The moment the script starts touching things outside the markers, the advantage of the pattern is gone.

9. Proving Re-Run Safety: State Hashes and Dry Runs

The claim that a script was written idempotently has to be verifiable. The cheapest method is to fold the entire target tree into a single hash.

state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}

Regular files are folded by content hash, symbolic links by their readlink result. Pinning the sort order with LC_ALL=C sort is essential; if the order shifts with the locale, the hash shifts with it. Here is the provisioning function run three times.

provision run1  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526
provision run2  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526
provision run3  state_hash=219dd1b402f930f92ce94faa467761005c47cb12d740c452e7609d3d6d0d4526

9.1 Injecting Drift and Re-Running: The Honest Result

One uncomfortable result came out of this, and it is published as is. The state was deliberately knocked out of alignment and the script re-run.

after drift   state_hash=74c1a29f825801f98c4d235c47df56ad943e386df4697f5ffd3b1709e7d3785b
after re-run  state_hash=3e25756382253f698945962c75d2fd19bc1455d5dc20b79aa672057b3220cb81
app.env:
MODE=production
TZ=Asia/Seoul
MODE=debug

After the re-run the hash did not return to the original value (219dd1...). Let us look at what was restored and what was not.

  • Restored - the human-created obsolete.conf was deleted by rm -f.
  • Restored - the current symlink was repointed at releases/v2 by ln -sfn.
  • Survived - the hand-added MODE=debug line is still there.

The reason is plain. The grep -qxF ... || append approach asks only whether the line I want is present, never whether a line I do not want is present. That is, it reached level 2 convergence but is not level 3 self-healing. If the application reads the file last-wins, this server declares itself production and runs as debug.

Preventing this means abandoning append and declaring either the whole file or a marker block. Stop your re-run verification at the hash is identical three times and you will never see this hole. That is exactly why a procedure that deliberately injects drift and re-runs is necessary.

9.2 Dry Run: See What Will Change Before Changing It

What operations teams actually use more often than hashes is the trial run. A --check mode gives you two things: a preview of what will change and a verdict on whether the script has converged.

-- --check (run 1, nothing exists yet) --
  would add to app.env: MODE=production
  would add to app.env: TZ=Asia/Seoul
  changed=1
-- apply --
  changed=1
-- --check (run 2) --
  changed=0 (already at target state)

The second --check returns changed=0. That is the operational definition of idempotence: can the script tell you itself that it has nothing left to change on a second run. It also drops neatly into CI. Run --check once more immediately after applying, and if it reports changed=1 then the script has not converged, so break the build.

The key to implementing this is funnelling every mutation through a single function. In the example above only want_line needed to look at the CHECK flag. If the mutation points are scattered across the code, the dry run will not stay accurate for long.

10. Resuming After Partial Failure: Step Markers and Their Trap

Back to the question in the introduction. When it dies at step 5 of 8, what should you do?

10.1 The Bad Design: If an Early Step Is Not Idempotent, You Never Get Past It

-- run 1 (forced failure) --
  step 3 failed
exit=3
-- remove the cause, run 2 --
mkdir: cannot create directory 'rbad/data': File exists
exit=1  <- blocked at step 1 forever

The cause of the failure was fixed, and it is still blocked at step 1. In that situation all an operator can do is open the script, comment out the early part and run it. At that moment the premise that deployment happens through the script collapses.

10.2 The Good Design: Idempotent Steps Plus Completion Markers

run_step(){
  local name="$1"; shift
  if [ -f "$S/$name.done" ]; then echo "  [skip] $name"; return 0; fi
  "$@" && : > "$S/$name.done" && echo "  [done] $name"
}
run_step schema s1 && run_step seed s2 && run_step release s3
-- run 1 (step 3 fails) --
  [done] schema
  [done] seed
   markers: schema.done seed.done
-- remove the cause, run 2 --
  [skip] schema
  [skip] seed
  [done] release
  completed
-- run 3 (should do nothing) --
  [skip] schema
  [skip] seed
  [skip] release
  completed
seed.csv lines: 1 | version: v1

The second run picked up from the point of failure and finished, and the third run finished having done nothing at all. It also matters that seed.csv is one line. Because each step is itself idempotent, it is safe even without the markers.

10.3 The Step Marker Trap: A Marker Does Not Guarantee Convergence

This pattern has a trap. A human deleted the output and the script was re-run.

a human deleted 'version'; re-run:
  [skip] schema
  [skip] seed
  [skip] release
  completed
version present? no - the marker made it skip

The script reported completed, and the output is not there. It looked only at the marker and never at the actual state. The principle that comes out of this is clear.

  • Step markers are an optimisation for resume speed, not a convergence guarantee. Use them only to skip heavy steps such as large downloads or migrations.
  • Do not put markers on cheap steps. Checking every time is safer and costs nothing.
  • Invalidate markers when the input changes. Putting an input hash in the filename (release.$(sha256 of config).done) makes the step re-run automatically when the configuration changes.
  • Verify the state directly at the end. Add a final check such as [ -f "$R/version" ] that is independent of the markers.
  • Choose the marker storage location carefully. Keeping it on the target server means it vanishes when the server is replaced; keeping it centrally means it cannot reflect per-server state.

11. When You Need a Lock and When You Do Not

Every defence so far has shared one assumption: that only one copy runs at a time. Break that assumption and check-then-change collapses on its own. This is the classic check-then-act problem.

11.1 Reproduction: Eight Processes Running Create-If-Absent at Once

round1: no lock SEED=5 | mkdir lock SEED=1 (expected 1)
round2: no lock SEED=4 | mkdir lock SEED=1 (expected 1)
round3: no lock SEED=4 | mkdir lock SEED=1 (expected 1)
round4: no lock SEED=5 | mkdir lock SEED=1 (expected 1)
round5: no lock SEED=4 | mkdir lock SEED=1 (expected 1)

All five rounds produced four or five lines. The expected value is one. Another process slipped in between the moment of the grep check and the moment of the >> append. The grep -qxF || append we built so carefully in the earlier sections is powerless in the face of concurrency.

What matters is when this situation actually arises in practice. When a cron job runs every 5 minutes but takes 6 minutes, when a deployment pipeline launches the same job twice through a retry, and when several nodes touch the same file on shared storage. All three are common.

11.2 When No Lock Is Needed: Whole-File Replacement

Not every case needs a lock. The approach of writing the whole file to a temporary path and swapping it in with mv came through unharmed with eight processes racing.

printf 'value=42\n' > ".atomic.$i.tmp" && mv ".atomic.$i.tmp" atomic.txt

lines=1 | content=value=42 | sha=72cc615c7f451bd5

The basis is the guarantee in rename(2). The manual states that if newpath already exists it will be atomically replaced, so that there is no point at which another process attempting to access newpath will find it missing. The only condition to respect is that the temporary file and the destination live on the same filesystem (across filesystems it becomes a copy and atomicity is lost).

11.3 When a Lock Is Mandatory: Read-Modify-Write

### 8 processes increment count by 1 concurrently
final count=2  (expected count=8)

Eight increments were lost down to two. This is the textbook lost update, where the value you read goes stale before you write it back. Summarised as a decision table:

Kind of workLock neededWhyAlternative
Rewrite the whole file and swap it inNorename is atomicTemp file plus mv (same filesystem)
Directory creation with mkdir -pNoThe kernel handles it atomicallyUse as is
Append after checking a line existsYesGap between check and changeLock, or switch to whole-file replacement
Read-modify-write (counters, lists)YesLost updatesLock, or append-only plus aggregation
Preventing duplicate starts of a long jobYesA run can outlast its own intervalAcquire the lock at the job entry point
Marker block replacementYesIt is a read-modify-write structureLock plus temp file mv together

11.4 What to Lock With

On Linux, flock from util-linux is the standard choice. Its manual offers an idiom for a script locking itself.

[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

With -n (non-blocking), failing to acquire the lock returns exit code 1 by default (changeable with -E). When putting this in cron you have to decide whether that value counts as normal duplicate suppression or as a failure, or your alerting gets noisy.

In an environment without flock, you can use the atomicity of mkdir. This is the approach that held at exactly one line in all five rounds of the reproduction.

if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
  ... critical section ...
else
  echo "another instance is running"; exit 0
fi
  • Always release with trap. Without it an abnormal exit leaves the lock behind and blocks every future run forever.
  • Record the PID and a timestamp in the lock directory. That gives you a basis for deciding whether a leftover lock belongs to a live process.
  • Define an orphan lock reclamation policy. Reclaiming automatically on a time threshold is convenient but risks killing a slow but healthy run.
  • Lock semantics differ on network filesystems such as NFS. If multiple nodes participate, consider a dedicated coordination mechanism instead of file locks.
  • A lock is not a substitute for idempotence. A lock only prevents concurrency. Code that breaks on sequential re-runs still breaks with a lock in place.

Conclusion: Idempotence Is a Design Property, Not a Personality Trait

The incidents reproduced in this article share one trait. Most of them raise no error. ln -sf returned 0 and served the old version, sed -i returned 0 and did nothing, and a grep -qF caught on a comment failed to apply a setting for months. Exit status 0 and reaching the target state are two different statements. If this article leaves you with that one sentence, it has paid for itself.

The practical rules therefore reduce to three lines. First, ask of every line what this command does when it runs against a state where it has already been done. Most incidents happen because nobody asked that question even once. Second, test for is it in the target state, not for did we do it. The criterion is current state, not work history. Third, do not assert, prove. Running it three times and comparing hashes costs one minute, and that minute buys back two hours at three in the morning.

At scale you end up reaching for a tool like Ansible. What those tools mean when they say idempotent is precisely what this article built by hand. lineinfile is check-then-change, blockinfile is the marker block, --check is the dry run, and the changed value is the convergence verdict. Even with a tool, not understanding these principles gets you the same incident from a single shell module line. Organisations where incidents continue after tool adoption are usually stuck at exactly this point.

One last thing you can do today. Take the script that runs most often, run it three times in a temporary directory, and print the state hash. If the three values differ, that script is already changing something a little every single day. Nobody has noticed yet.

# Idempotent Script Checklist — run through this before you write

> Source: braindetox.kr — Idempotent Shell Scripts
> Basis: POSIX Issue 8 (mkdir/rm), GNU coreutils (ln -n), rename(2), flock(1)
> Paste this file into an AI and say 「rewrite our script against this checklist」.

## 1. Safe form per command — copy these shapes

| Goal | Write it this way |
|---|---|
| Directory | `mkdir -p "$D"` + set permissions on a separate line: `chmod 0750 "$D"` |
| Delete file | `rm -f "$F"` (use `rm -rf` for a directory — guard the variable first) |
| Add a line | `grep -qxF -- "$L" "$F" \|\| printf '%s\n' "$L" >> "$F"` |
| Remove a line | `grep -vxF -- "$L" "$F" > "$F.t" && mv "$F.t" "$F"` |
| Symlink | `ln -sfn "$TARGET" "$LINK"` |
| Replace a value | `grep -qxF "$WANT" "$F" \|\| sed -i "s#^$OLD\$#$WANT#" "$F"` |
| Insert a line | branch: replace with `sed -i 's/^key=.*/key=v/'` if present, `a\` if absent |
| Cron | `{ crontab -l 2>/dev/null \| grep -vF "$ABS_PATH"; echo "$JOB"; } \| crontab -` |
| Copy a directory | `cp -r "$SRC/." "$DST/"` (NOT `cp -r src dst`) |
| Move a file | `[ -e "$S" ] && mv "$S" "$D"` |
| Write a whole file | `... > "$F.tmp" && mv "$F.tmp" "$F"` (same filesystem) |

## 2. Ask yourself, line by line
- [ ] What does this line do when it runs against an **already-done** state?
- [ ] Am I testing **「is it the target state」** rather than 「did I do it」?
- [ ] Does the `grep` guard have both `-x` (whole line) and `-F` (fixed string)?
- [ ] Do I distinguish `grep` exit code **2 (error)** from 1 (no match)?
- [ ] Can the `sed` replacement result **match the pattern again**?
- [ ] Am I using `sed -i` exit status as evidence that it applied? (It is not.)
- [ ] Does every symlink swap carry **`-n`**?
- [ ] Under `set -e`, does an early failure **swallow all later steps**?
- [ ] Do timestamps or random values in the file **block hash comparison**?
- [ ] When I **remove** a managed item, does it disappear from already-deployed files?

## 3. Marker block template — use this past ~5 managed lines

```bash
apply_block(){                     # apply_block <file> <tag> <body>
  local file="$1" tag="$2" body="$3"
  local begin="# BEGIN ${tag}" end="# END ${tag}"
  [ -e "$file" ] || : > "$file"
  if grep -qxF "$begin" "$file"; then
    awk -v b="$begin" -v e="$end" -v body="$body" '
      $0==b { print b; printf "%s", body; skip=1; next }
      $0==e { print e; skip=0; next }
      skip==1 { next }
      { print }' "$file" > "$file.new" && mv "$file.new" "$file"
  else
    { printf '%s\n' "$begin"; printf '%s' "$body"; printf '%s\n' "$end"; } >> "$file"
  fi
}
apply_block /etc/ssh/sshd_config "myapp-keepalive" \
  $'ClientAliveInterval 30\nClientAliveCountMax 3\n'
```

- [ ] Tag names the **owner and purpose** (`myapp-nginx-upstream`)
- [ ] Marker uses the file's **own comment character** (`#` / `;` / `//`)
- [ ] **Not** used on structured formats (JSON, YAML)
- [ ] The script never touches anything **outside** the markers

## 4. Re-run verification — one minute before you commit

```bash
state_hash(){
  ( cd "$1" && {
      find . -type f | LC_ALL=C sort | xargs sha256sum
      find . -type l | LC_ALL=C sort | while read -r l; do echo "$(readlink "$l")  $l"; done
    } | sha256sum | awk '{print $1}' )
}
for i in 1 2 3; do ./provision.sh "$ROOT"; echo "run$i $(state_hash "$ROOT")"; done
```

- [ ] All three hashes are **identical** (if not, something is accumulating)
- [ ] Sort order pinned with `LC_ALL=C sort`
- [ ] **Deliberately injected drift**, then re-ran (extra config line, repointed symlink, stray file)
- [ ] A second `--check` run reports **changed=0**
- [ ] All testing happened in a **temporary directory**

## 5. When you need a lock

| Situation | Lock | Alternative |
|---|---|---|
| Whole-file replacement | Not needed | temp file + `mv` |
| `mkdir -p` | Not needed | as-is |
| Check-then-append | **Needed** | switch to whole-file replacement |
| Read-modify-write | **Needed** | append-only, aggregate later |
| Cron job slower than its interval | **Needed** | acquire the lock at entry |
| Marker block replacement | **Needed** | lock + temp file `mv` |

```bash
# if flock is available
[ "${FLOCKER}" != "$0" ] && exec env FLOCKER="$0" flock -en "$0" "$0" "$@" || :

# otherwise rely on mkdir atomicity
if mkdir "$LOCKDIR" 2>/dev/null; then
  trap 'rmdir "$LOCKDIR"' EXIT INT TERM
else
  echo "another instance is running"; exit 0
fi
```

- [ ] The lock is always released via `trap`
- [ ] The lock directory records **PID and timestamp**
- [ ] A **stale-lock reclaim policy** is decided
- [ ] Remember a lock only prevents **concurrency** — sequential re-run bugs survive it

## 6. Resuming after partial failure
- [ ] Each step is **idempotent on its own** (safe even without a marker)
- [ ] Markers are attached only to **expensive** steps
- [ ] Marker filenames embed an **input hash**, so config changes invalidate them
- [ ] The final check inspects **actual state**, not the markers
