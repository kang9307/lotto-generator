LeafWiki - 无需服务器和数据库,单一二进制运行的自托管Wiki

与 MediaWiki、Wiki.js、DokuWiki、Confluence 逐一对比,看轻量级 Wiki 的优势与取舍

2026-07-18 开发/基础设施

引言: 为什么「轻量级 Wiki」又回来了

过去几年,知识管理工具市场分裂成了两个极端。一端是 Notion、Confluence 代表的「无所不包」SaaS 全能套件,另一端是 Obsidian、Logseq 代表的本地优先个人笔记。真正被挤出局的,恰恰是「Wiki」这个词本来指代的中间地带 - 多人共用、但运维不重的工具。MediaWiki 把支撑维基百科运转而设计的技术栈硬塞给八人小团队,Confluence 则用订阅费换来文档也一并交给厂商服务器。

正是在这个缺口中,LeafWiki 这样的项目出现了。由开发者 perber 打造的这款开源 Wiki,截至 2026 年 7 月已有 837 个 GitHub star,最新版本到了 v0.11.4,官方用一句话概括自己:单一 Go 二进制、SQLite、存储在磁盘上的 Markdown。本文以 GeekNews(hada.io)介绍的 LeafWiki 为起点,退一步审视整个自托管 Wiki 生态究竟发生了什么变化,以及哪些取舍依然存在。文中事实以 2026 年 7 月 18 日当时 LeafWiki 官网、GitHub 仓库及 GitHub API 数据为准。

1. LeafWiki 是什么 - 单一二进制运行的 Wiki

1.1 核心规格与技术栈

LeafWiki 的后端用 Go 编写(按仓库语言占比约 60.8%),前端是基于 React 与 Vite 的 TypeScript(约 35.4%)。状态管理使用内置 SQLite,但实际的页面内容以普通 Markdown 文件原样保存在磁盘上 - 也就是说,即便 LeafWiki 应用没有运行,也能用 grep 或文本编辑器直接读取文档。「没有应用,内容依然存活」正是这个项目的核心理念。功能列表也不单薄:树状文件夹导航、全文搜索加标签筛选、反向链接与失效链接追踪、实时分屏 Markdown 编辑器、[[wikilink]] 自动补全、深色模式,以及 Mermaid 图表和 KaTeX 数学公式(行内公式 $...$ 尚不支持,仅支持块级公式)均为默认功能。版本历史与页面改名后的链接自动重构是通过 --enable-revision、--enable-link-refactor 参数开启的可选功能,自 v0.11.3 起还提供实验性的 Git 备份支持。

1.2 安装与部署 - 一行 Docker 命令,一个二进制文件

安装路径有三种:一行 Docker 命令(只需指定端口、数据卷和管理员密码)、面向 Linux/Raspberry Pi OS 的安装脚本(curl 下载后执行)、以及直接下载适用于 Linux、Windows、macOS 的二进制文件。demo.leafwiki.com 提供在线演示,许可证为 MIT。访问控制分三档 - 必须登录、公开阅读+登录后可编辑、关闭认证 - 权限则按 admin、editor、viewer 角色划分。值得注意的是,官方预告 2026 年 9 月起将开放 10 个名额的免费托管测试版。一款彻底自托管的工具也在试水托管选项,这本身就是「自托管还是 SaaS」不再是非此即彼的一个信号。

2. 自托管 Wiki 需求为何再度升温

2.1 团队知识管理与个人笔记的再次兴起

Notion 的成本会随团队规模按席位增长,而 Obsidian 从一开始就没有把团队协作当作首要场景来设计。试图填补这块空白的尝试最近又多了起来,LeafWiki 之外,BrainDetox 此前分析过的 Chatto(自托管团队聊天)与 Odysseus(自托管 AI 工作空间)在相近时间段接连出现,我认为并非巧合。「多人共用但运维要轻」这种需求,正同时在笔记、聊天、Wiki 这几个方向上升温。

2.2 AI 时代的悖论 - 想被检索、被总结的知识,反而要握在自己手里

悖论在于,AI 工具越是日常化,「我的知识该放在哪里」这个问题就越沉重。随着越来越多开发者想用本地 LLM 或 RAG(检索增强生成)来检索、总结、查询自己的文档,文档究竟是以纯文本 Markdown 存在磁盘上,还是藏在 SaaS 封闭 API 之后,直接决定了它能多容易地接入 AI 流水线。像 LeafWiki 这样内容本身就是 .md 文件的工具,不仅能被 grep 检索,还能直接接入本地向量索引和个人 RAG 流水线。这与其说是怀旧,不如说是 AI 实际使用场景带来的一种务实回归。

3. 既有 Wiki 的沉重之处 - MediaWiki、Wiki.js、DokuWiki、Confluence

3.1 MediaWiki - 维基百科引擎带来的「杀鸡用牛刀」

MediaWiki 运行在 PHP 与 MySQL/MariaDB 之上,是全球最著名的 Wiki 引擎。它确实支撑着维基百科的运转,这本身就是可靠性的证明 - 但也是这份可靠性的代价。需要照看 Web 服务器、PHP 运行时、独立数据库服务器乃至扩展(extension)管理的技术栈,是为承载数百万文档、数千并发访问而设计的,不是为八人团队的运维手册准备的。小团队引入 MediaWiki,往往花在理解扩展生态和权限模型上的时间,比安装本身还多。

3.2 Wiki.js - 现代但沉重,近期开发有所放缓

Wiki.js 是基于 Node.js、Vue.js 与 PostgreSQL(或其他关系型数据库)构建的相对现代的 Wiki。它支持 Markdown、WYSIWYG、HTML 等多种编辑器,还能与 Git 同步,一度被视为「DokuWiki 的现代替代品」。但仍需单独运维 Node 运行时与 SQL 数据库,这意味着它只是比 MediaWiki 轻一些,本质上仍是多组件技术栈,而且有观察指出 2026 年上半年核心仓库的提交频率明显放缓 - 若考虑采用,这是一个值得关注的维护风险。

3.3 DokuWiki - 最接近的前辈,但 PHP 依然是必需品

DokuWiki 其实更接近 LeafWiki 的思想源头。近 20 年来它一直不依赖外部数据库,把页面存成纯文本文件,「备份即复制目录」的简单性让它长期受到青睐。但 DokuWiki 依然需要单独的 PHP 运行时和 Web 服务器(Apache/Nginx)- 并非无需安装运行时那种真正意义上的单一二进制。它的界面也带着近 20 年的年代感。可以说 LeafWiki 继承了 DokuWiki「无数据库」的理念,又把 PHP、Web 服务器安装这一环节本身进一步压缩进一个 Go 二进制文件里,是这条路线的下一代。

3.4 Confluence - 用数据主权换取 SaaS 的便利

Atlassian Confluence 同时销售云端版与数据中心版商用 Wiki。几乎没有安装负担(注册即可使用),审批流程、精细权限、Jira 集成等企业级功能十分强大。代价是订阅费用,以及只要使用云端版,文档就常驻在厂商服务器上。对小团队、个人,以及政府、医疗等对数据外流敏感的组织而言,这一点就成了进入门槛。

4. 「单一二进制」路线真正带来了什么

4.1 部署变成了搬一个文件

传统 Web 应用的部署要经过安装运行时(Node、PHP、Python 等)、依赖管理(包管理器、版本冲突)、数据库配置、反向代理设置等多个环节。用 Go 编译出的单一二进制,把这些环节大部分推到了编译阶段,运行时只需要一个二进制文件加一个数据目录。这也是 LeafWiki 的 Docker 启动命令能压缩成一行、安装脚本一条 curl 命令就能搞定的原因。对运维经验不多的个人团队或副业项目来说,这个差异就是「要不要试一试」的真实门槛。

4.2 零依赖与可移植性 - 从树莓派到气隙环境

Go 语言的交叉编译很方便,同一份源码可以产出 Linux、Windows、macOS、ARM(含树莓派)等各平台的二进制文件。LeafWiki 官方提供 Raspberry Pi OS 安装脚本,说明这种可移植性正在被实际使用,而不只是纸面能力。在断网的气隙(air-gapped)环境中,只需搬运一个二进制文件即可运行,这对无法访问外部软件仓库的封闭网络组织(制造现场、科研机构等)尤其有吸引力。这并非 LeafWiki 独有,而是 Go、Rust 系工具的共同优势,但在 Wiki 这个品类里仍属少见。

4.3 为什么备份只是复制一个目录

LeafWiki 用 SQLite 管理元数据(结构、权限、标签),但文档正文以纯文本 Markdown 保存。结果是,备份只需复制整个数据目录即可完成,不需要单独的 mysqldump 或数据库导出步骤。自 v0.11.3 起实验性支持的 Git 备份功能更进一步,让文档变更历史本身以 Git 提交的形式留存。DokuWiki 用 20 年验证的「备份即复制」这种简单性,LeafWiki 不仅继承了下来,还叠加了 Git 这个大家熟悉的工具。

5. 取舍 - 扩展性、实时协作、插件生态

5.1 扩展性的局限

LeafWiki 官方文档自己就写明,不适合企业级权限管理或 Confluence、Notion 那种规模的需求。SQLite 是出色的嵌入式数据库,但在大规模并发写入或数万页面规模下,目前还没有太多经过验证的案例。与 MediaWiki 二十年积累的大规模运维经验相比,LeafWiki(v0.x、837 star)更接近实战验证的早期阶段。

5.2 缺少实时协同编辑

官方明确表示不以支持实时协同编辑(real-time collaborative editing)为目标。虽然有自动保存和冲突检测,但这与 Google 文档、Notion 那种多光标同时编辑并不是一回事。如果团队中多人需要同时编辑同一份文档,可能会在这一点上受限。

5.3 没有插件生态

MediaWiki 拥有数千个扩展,Wiki.js 也支持多种渲染器和认证模块。LeafWiki 反其道而行,选择了「只把核心功能做好」的极简主义。扩展点几乎为零,意味着维护负担更小,但同时也意味着需要特定工作流(如 SSO 集成、自定义审批流程)的组织很难把它当作可选项。

6. 适合哪些团队和场景

6.1 适配度高的场景

个人知识库、工程笔记,5~30 人规模团队的内部运维手册、操作文档,以及想把已经积累的 Markdown 或 Obsidian 资产结构化的组织,都很适合。低功耗边缘设备(树莓派等)或断网的气隙环境也是一大适用场景 - 一条安装脚本加一个二进制文件即可离线部署,这一点在这些环境中尤其实用。

6.2 需要谨慎的场景

需要审批流程的受监管行业文档、数百人同时穿梭的大型组织 Wiki、实时协同编辑本身就是工作方式的团队,以及需要多年验证成熟度的关键任务文档,目前保留 MediaWiki、Confluence 这类久经验证的工具会更安全。

7. 自托管 vs SaaS Wiki - 数据主权与成本

自托管与 SaaS Wiki 之间的抉择,最终归结为「谁对什么负责」。SaaS(Confluence、Notion 等)由厂商负责可用性、备份、安全补丁,代价是文档常驻厂商服务器,成本随席位数增长。对受监管行业、忌讳数据外流的组织,或只是想清楚知道「自己的文档究竟放在哪里」的个人与小团队而言,这种结构是一种负担。自托管则相反:数据不会离开自己掌控的基础设施,成本也维持在接近服务器租用费的平坦水平,但可用性、备份、安全全都要自己负责。像 LeafWiki 这样以单一二进制运行的工具,大幅降低了这份「运维责任」的实际负担,这使自托管比以往更接近一个现实可行的选择。不过隐私并非免费 - 定期真正跑一遍备份、及时打好服务器安全补丁、故障时能够恢复,这些依然需要有人来做。

8. Markdown 文档工具的趋势,以及 LeafWiki 的位置

把 BrainDetox 近期分析过的几条线索排在一起,能看出一个模式。围绕 Files.md、Logseq、Excalidraw 的 Obsidian 生态分歧分析,问的其实是「笔记资产要不要留在开放格式里」;Odysseus 自托管 AI 工作空间分析,是把 AI 工作空间本身留在本地的一次尝试;Chatto 自托管团队聊天分析,则把同样的思路用到了团队聊天上。LeafWiki 把这股潮流带进了 Wiki - 或许是这几个品类里最古老、也最沉重的一个。共同点很清楚:内容留在纯文本、Markdown、开放格式里,运行则保持最小依赖。这种组合从笔记应用,蔓延到团队聊天、AI 工作空间,如今又到了 Wiki,与其说是一时流行,不如把它看作本地优先(local-first)软件这股更大潮流的一条支线。

结论: 今天谁应该用 LeafWiki

LeafWiki 源自一句很实际的抱怨 - 「Wiki 真的有必要这么重吗」- 而且它对自己的边界很诚实。对个人知识库、5~30 人团队的运维手册、已经积累了 Markdown 资产的组织,以及低功耗、气隙环境而言,它现在就是一个有吸引力的选项。反过来,如果实时协同编辑是刚需,或者组织需要审批流程和精细权限,又或者文档属于关键任务、需要多年验证的成熟度,那现在还为时尚早 - 保留 MediaWiki 或 Confluence 这类久经验证的工具会更稳妥。837 个 star、v0.11.4 这些数字说明,LeafWiki 仍是一个 1.0 之前的项目。但「单一二进制 + 纯文本 Markdown」这种组合,看起来是 DokuWiki 之后 Wiki 这个品类里最有说服力的下一代答案之一。截至 2026 年 7 月,如果你是想把数据握在自己手里的小团队,不妨在演示站点(demo.leafwiki.com)花点时间试用一下,很快就能判断这款工具是否适合自己。
