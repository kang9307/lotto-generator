Rust 1.99.0 개요와 핵심 변경점

2026년 10월 1일 발표된 Rust 1.99.0은 시스템 프로그래밍과 외래 함수 인터페이스(FFI) 경계에서 오랫동안 미해결 상태로 남아있던 핵심 저수준 기능들을 대거 안정화했다. 가장 두드러진 변화는 C ABI 호환 가변 인자(variadic) 함수를 Rust 코드베이스 내에서 직접 구현할 수 있게 된 점이다. 지금까지 Rust 개발자들은 C 런타임이 요구하는 가변 인자 콜백이나 로깅 인터페이스를 작성할 때 플랫폼 종속적인 인라인 어셈블리 래퍼나 우회 기법에 의존해야 했다. 이번 릴리스를 기점으로 이러한 기술적 부채가 표준 컴파일러 수준에서 공식적으로 해소되었다.

이와 더불어 원시 포인터의 메모리 배치를 안전하게 질의할 수 있는 레이아웃 검사 함수들이 정식 표준 라이브러리 API로 편입되었다. 동적으로 크기가 결정되는 unsized 타입(!Sized)에 대한 안전성 계약이 확정됨으로써, 메모리 할당기와 직렬화 엔진의 내부 구현이 한층 견고해졌다. 또한 Box::leak을 둘러싼 공식 문서 권고의 갱신과 컬렉션·반복자 편의 기능 확장은 실무 개발자들에게 직접적인 설계 지침을 제공한다.

관련 기술적 배경과 메모리 안전성에 대한 논의는 메모리 안전성 절대주의자들과 Rust의 위치 및 C/C++ 시스템 연동 프레임워크를 다룬 Rust 마이그레이션 아키텍처 가이드에서도 공통된 맥락으로 확인할 수 있다. 본 글에서는 1.99.0 발표문에서 실제로 검증된 항목을 중심으로 기술적 함의를 구조화한다.

  • C 호출 규약 가변 인자 함수 직접 정의: "C" 및 "C-unwind" ABI 환경에서 가변 인자 본문을 Rust로 작성 가능.
  • ABI 호환 VaList 타입과 VaArgSafe 트레이트: C va_list와 직접 연동하며 타입 안정성을 컴파일러가 강제.
  • 원시 포인터 레이아웃 3종 안정화: Layout::for_value_raw, size_of_val_raw, align_of_val_raw 확정.
  • 소유권 회수 패턴 지침 개정: Box::leak 해제 패턴을 지양하고 into_non_null이나 into_raw 사용을 공식 권고.
  • 핵심 컬렉션 편의성 개선: Box<[T; N]>의 IntoIterator, VecDeque::retain_back 등 다수 API 안정화.

C ABI 가변 인자 함수 정의의 안정화 — 호출(call)에서 정의(define)로

가변 인자 함수는 전달되는 인자의 개수와 타입이 런타임 호출 시점에 결정되는 C 언어의 전통적인 기능이다. 기존 Rust에서도 extern "C" { fn printf(format: *const c_char, ...) -> c_int; }와 같이 외부 라이브러리에 이미 컴파일되어 있는 가변 인자 함수를 선언하고 호출(call)하는 것은 지원되었다. 그러나 역으로 C 코드나 운영체제 커널이 Rust가 작성한 가변 인자 콜백 함수를 호출하도록 만드는 정의(definition)는 불가능했다. 1.99.0에서는 "C"와 "C-unwind" 호출 규약에 한해 함수 시그니처에 ... 토큰을 사용한 본문 정의가 안정화되었다.

C 가변 인자 함수는 컴파일 시점에 인자 목록의 크기와 타입을 고정할 수 없으므로, 메모리 안전성 보장을 위해 본질적으로 unsafe 컨텍스트를 요구한다. 호출자는 함수가 기대하는 타입과 개수에 부합하는 인자를 올바르게 건네주어야 하며, 피호출 함수는 전달받은 인자 스트림의 끝을 감지하거나 약속된 포맷 문자열에 의존해야 한다. 또한 표준 C ABI가 아닌 naked 가변 인자 함수의 경우 #[unsafe(naked)] 속성을 사용하며 반드시 인라인 어셈블리(inline assembly)로만 구현해야 한다는 제약 조건이 공식 릴리스에 명시되었다.

/// SAFETY: must be called with (at least) 2 i32 arguments.
                    unsafe extern "C" fn sum(mut args: ...) -> i32 {
                        // SAFETY: guaranteed by the caller.
                        let a = unsafe { args.next_arg::<i32>() };
                        let b = unsafe { args.next_arg::<i32>() };
                        a + b
                    }
                    
                    fn foo() -> i32 {
                        unsafe { sum(0i32, 2i32) }
                    }

위 공식 예제에서 확인할 수 있듯이, 매개변수 선언부에 단독으로 위치한 mut args: ...는 함수 본문 내부에서 core::ffi::VaList 타입으로 취급된다. 호출자는 sum(0i32, 2i32)와 같이 일반적인 함수 호출 구문으로 인자를 넘기지만, 내부적으로는 타깃 아키텍처의 C ABI 레지스터 및 스택 전달 규약에 맞춰 인자가 패킹된다. 이는 시스템 라이브러리와 직접 바인딩을 구축하는 FFI 엔지니어들에게 우회 계층 없는 강력한 도구를 제공한다.

  • 호출 규약 범위: extern "C"와 스택 언와인딩을 지원하는 extern "C-unwind"에서만 가변 매개변수 선언 허용.
  • 호출자 책임의 안전성 계약: 호출자가 전달하는 인자의 개수 및 타입 불일치는 미정의 동작(Undefined Behavior)을 유발하므로 unsafe 표기 필수.
  • 인자 목록 바인딩: 함수 선언부의 ... 식별자는 본문 내부에서 가변 인자 제어 구조체인 VaList로 변환.
  • Naked 함수 지원: #[unsafe(naked)] 환경의 가변 인자 함수는 레지스터 보존을 위해 인라인 어셈블리 본문 강제.
  • FFI 브리지 단순화: 기존 C++ 및 C 헤더에서 요구하던 va_list 브리지 C 래퍼 코드 작성 단계의 완전한 생략 가능.

VaList와 VaArgSafe — 가변 인자 추출과 타입 안전성

가변 인자 목록에서 개별 요소를 순차적으로 읽어오기 위해 Rust는 core::ffi::VaList 구조체와 core::ffi::VaArgSafe 트레이트를 제공한다. VaList는 타깃 플랫폼의 C 컴파일러가 사용하는 va_list 메모리 구조와 100% ABI 호환되도록 설계되었다. x86_64 시스템 V ABI, 윈도우 x64 ABI, AArch64 등 각 하드웨어 아키텍처마다 상이한 레지스터 저장 영역(register save area)과 오프셋 계산 메커니즘을 VaList 추상화가 투명하게 캡슐화한다.

이 과정에서 가장 중대한 안전 장치는 VaArgSafe 마커 트레이트다. C 언어 사양에서는 가변 인자로 전달될 때 float가 double로 자동 변환되거나, char 및 short가 int로 승격되는 기본 인자 승격(default argument promotion)이 발생한다. 만약 개발자가 args.next_arg::<u8>()이나 C ABI 승격 규약에 맞지 않는 복합 구조체를 무분별하게 읽으려 시도한다면, 스택 프레임의 바이트 정렬이 깨져 인접 메모리가 오염될 수 있다. Rust 컴파일러는 VaArgSafe가 구현된 타입(예: i32, f64, 원시 포인터 등)에 대해서만 next_arg::<T>() 호출을 허용함으로써 컴파일 단계에서 치명적인 ABI 불일치를 원천 차단한다.

인자를 꺼내는 args.next_arg::<T>() 연산 자체도 여전히 unsafe 블록 내에서 수행되어야 한다. 컴파일러가 타입의 적합성을 보장할 수는 있지만, 호출자가 실제로 해당 순서에 그 타입의 값을 전달했는지는 런타임 데이터에 종속되기 때문이다. 따라서 개발자는 C 표준 라이브러리의 vprintf 류 함수처럼 명시적인 형식 지정자나 프로토콜 헤더를 통해 인자의 정합성을 엄격히 검증하는 방어적 로직을 구축해야 한다.

  • 플랫폼별 ABI 투명성: x86_64, ARM64 등 플랫폼마다 제각각인 레지스터 저장 영역과 스택 오프셋 처리를 단일 VaList로 통합.
  • 기본 승격 규칙의 컴파일 검증: C 표준의 기본 인자 승격 규칙을 반영한 VaArgSafe 트레이트로 부적합한 타입의 인자 추출 차단.
  • 런타임 경계 검사 부재의 한계: C 언어 사양의 한계로 인해 인자 스트림 자체에는 남은 인자의 개수 정보가 없으므로 호출 규약 설계에 유의.
  • 타입 안전 추출 메서드: args.next_arg::<T>() 형태로 명시적 제네릭 타입을 지정하여 메모리에서 값을 역직렬화.
  • 상태 보존과 복사: 복잡한 파싱 흐름을 위해 C의 va_copy에 대응하는 상태 복제 메커니즘의 ABI 일관성 유지.

원시 포인터 레이아웃 조회 API 3종 — Sized와 !Sized 타입의 안전성 요구사항

Rust 1.99.0에서는 원시 포인터(raw pointer)가 가리키는 대상의 메모리 크기와 정렬(alignment)을 안전하게 질의할 수 있는 세 가지 핵심 함수가 공식 안정화되었다. 대상 함수는 core::alloc::Layout::for_value_raw, core::mem::size_of_val_raw, core::mem::align_of_val_raw이다. 기존 Rust 표준 라이브러리에도 Layout::for_value나 mem::size_of_val이 존재했으나, 이들은 반드시 유효한 참조(reference, &T)를 요구했다. 그러나 메모리 할당 해제나 저수준 버퍼 조작 시점에는 아직 유효한 참조를 생성할 수 없는 댕글링 상태이거나 정렬이 어긋난 원시 포인터만을 보유하고 있는 경우가 빈번했다.

이번에 안정화된 _raw 계열 API는 컴파일 타임에 크기가 확정되는 Sized 타입뿐만 아니라, 슬라이스([T])나 트레이트 객체(dyn Trait)처럼 런타임에 메타데이터를 동반하는 !Sized(unsized) 타입에 대해서도 일관된 질의 인터페이스를 제공한다. Sized 타입의 경우 포인터가 가리키는 메모리 주소의 유효성과 관계없이 컴파일러 메타데이터만으로 크기와 정렬이 즉시 계산되므로 안전성 계약(Safety contract)이 자명하다. 반면 !Sized 타입은 포인터 자체에 포함된 팻 포인터(fat pointer) 메타데이터(슬라이스 길이 또는 트레이트 vtable 포인터)를 읽어 계산하므로, 해당 메타데이터가 유효한 상태여야 한다는 명확한 요구조건이 확립되었다.

use std::alloc::Layout;
                    
                    // Sized 타입의 경우 댕글링 포인터라도 레이아웃 조회가 완전히 안전함
                    let dangling_ptr = std::ptr::NonNull::<u64>::dangling().as_ptr();
                    let layout_sized = unsafe { Layout::for_value_raw(dangling_ptr) };
                    assert_eq!(layout_sized.size(), 8);
                    
                    // !Sized 슬라이스의 경우 메타데이터(길이)가 담긴 팻 포인터 유효성이 요구됨
                    let slice_ptr: *const [u8] = std::ptr::slice_from_raw_parts(dangling_ptr as *const u8, 42);
                    let layout_unsized = unsafe { Layout::for_value_raw(slice_ptr) };
                    assert_eq!(layout_unsized.size(), 42);

위 코드에서 볼 수 있듯이, Layout::for_value_raw는 원시 포인터 상태에서 직접 메모리 할당 명세를 복원할 수 있게 해 준다. 이는 커스텀 메모리 풀, 가비지 컬렉터 구현체, 그리고 외부 언어와의 복합 객체 교환 과정에서 불필요하게 &T 참조를 생성함으로써 발생할 수 있던 앨리어싱 규칙 위반이나 미정의 동작의 위험을 완전히 제거한다.

  • core::alloc::Layout::for_value_raw: 원시 포인터로부터 대상 타입의 Layout(크기 및 정렬 제약)을 직접 산출.
  • core::mem::size_of_val_raw: 대상 포인터가 점유하는 메모리 크기(바이트 단위)를 원시 포인터로부터 계산.
  • core::mem::align_of_val_raw: 대상 포인터의 메모리 정렬 요구치를 원시 포인터로부터 계산.
  • 참조 변환 회피를 통한 미정의 동작 방지: 포인터 유효성이 완전하지 않은 중간 단계에서 &*ptr 임시 참조 생성을 방지.
  • Unsized 타입 메타데이터 계약 확정: 슬라이스 길이 및 vtable이 유효한 범위 내에 있어야 한다는 안전성 전제 조건 공식화.

Box::leak 문서 권고 변경과 소유권 회수 패턴의 대안

Rust 1.99.0 표준 라이브러리 문서에서 주목해야 할 중요한 정책적 변화는 Box::leak 메서드의 공식 가이드라인 개정이다. Box::leak은 힙에 할당된 Box<T>의 소유권을 포기하고 'static 라이프타임을 갖는 가변 참조자(&'static mut T)를 획득하는 수단으로 널리 사용되어 왔다. 그러나 일부 라이브러리에서는 이렇게 누출시킨 메모리를 나중에 다시 Box::from_raw 등을 호출해 소유권을 회수하고 해제하는 소위 소유권 회수 패턴(round-trip / unleaking pattern)을 관행적으로 활용해 왔다.

Rust 개발팀은 1.99.0 문서 개정을 통해 이러한 Box::leak 기반의 소유권 회수 패턴을 명시적으로 피하도록 강력히 권고했다. 이는 언어 자체의 의미론(semantics)이 즉각 변경되어 컴파일 에러를 발생시키는 것은 아니지만, 컴파일러가 라이프타임과 앨리어싱 정보를 바탕으로 수행하는 현재 및 향후의 최적화 파이프라인과 충돌을 일으킬 가능성이 높기 때문이다. 특히 향후 예정된 사용자 정의 할당자(custom allocator) 지원이 표준화될 때, Box::leak으로 변환된 정적 참조자가 원본 할당자의 컨텍스트를 상실하면서 메모리 해제 시점에 심각한 런타임 오류를 초래할 수 있다는 점이 지적되었다.

공식 문서는 누출 후 회수가 필요한 워크로드에 대해 Box::leak 대신 Box::into_non_null 또는 Box::into_raw를 명시적으로 사용할 것을 권장한다. 포인터 기반 변환을 활용하면 컴파일러에게 소유권이 라이프타임 시스템을 벗어나 원시 메모리 영역으로 이관되었음을 투명하게 전달할 수 있으며, 차후 Box::from_non_null이나 Box::from_raw를 통해 안전하게 소유권을 복원할 수 있다. 동일한 원칙과 권고는 Vec::leak을 비롯한 표준 라이브러리 내의 다른 모든 누출 관련 API에도 동일하게 적용된다.

  • 언어 의미론 유지 속 지침 변경: 기존 코드가 즉시 컴파일 실패하는 것은 아니나, 향후 버전과의 호환성을 위한 권고 갱신.
  • 컴파일러 최적화 간섭 방지: 'static 참조자가 프로그램 종료 시점까지 유효하다는 컴파일러의 가정을 훼손하지 않도록 보호.
  • 사용자 정의 할당자 대비: 힙 메모리의 할당자 메타데이터 보존을 위한 표준화 준비 작업의 일환.
  • 공식 권장 대안: 메모리 제어권 분리가 필요한 경우 Box::into_non_null 및 Box::into_raw 사용을 채택.
  • 표준 라이브러리 전반 전파: Vec::leak 등 유사한 수명 연장 편의 메서드 전체에 동일한 설계 패턴 적용.

컬렉션·문자열·파일 시스템 추가 안정화 API 상세

가변 인자 함수와 저수준 메모리 레이아웃 외에도, Rust 1.99.0에는 일상적인 애플리케이션 개발 생산성을 크게 높여주는 다양한 표준 라이브러리 API들이 대거 안정화되었다. 컬렉션 영역에서는 배열을 감싼 박스 타입인 Box<[T; N]>에 대해 소유권 및 참조 기반의 반복자 구현(IntoIterator for Box<[T; N]>, &Box<[T; N]>, &mut Box<[T; N]>)이 완비되었다. 이로써 고정 크기 힙 배열을 스택 복사 없이 곧바로 순회할 수 있게 되었다.

또한 양방향 큐 구조체인 VecDeque에 대해 역순 탐색 조건부 제거 메서드인 VecDeque::retain_back이 추가되었으며, 반복자 어댑터 StepBy에 대해 융합 반복자 트레이트인 FusedIterator for StepBy<I>가 구현되어 무한 반복 방지 및 파이프라인 최적화가 가능해졌다. 벡터의 내부 버퍼 요소를 분해하고 재조합하는 Vec::into_parts와 Vec::from_parts, 그리고 널 포인터가 아님을 보장하는 Box::into_non_null과 Box::from_non_null의 안정화는 커스텀 자료구조 개발자의 코드 작성을 크게 단순화한다.

문자열 및 입출력(I/O) 영역에서도 의미 있는 기능 개선이 이루어졌다. 손실 허용 UTF-8 변환 시 불필요한 힙 재할당을 방지하는 String::from_utf8_lossy_owned와 에러 타입에서 소유권을 보존하는 string::FromUtf8Error::into_utf8_lossy가 도입되었다. 운영체제 파일 시스템 인터페이스로는 심볼릭 링크를 추적하지 않고 메타데이터 타임스탬프를 갱신할 수 있는 std::fs::set_times와 std::fs::set_times_nofollow가 안정화되어 백업 도구 및 빌드 시스템 개발 시 보안성과 정확성을 동시에 확보할 수 있게 되었다.

  • Box<[T; N]> 반복자 완성: 고정 크기 힙 배열의 값, 공유 참조, 가변 참조 순회를 별도 벡터 변환 없이 직접 수행.
  • VecDeque::retain_back 안정화: 큐 후방 요소부터 조건을 검사하여 불필요한 메모리 시프트 비용 절감.
  • StepBy의 FusedIterator 구현: 반복이 한 번 종료(None 반환)된 이후 안전하게 None을 지속 반환하도록 보장.
  • Vec 부품 분해 및 재조합: into_parts(포인터, 길이, 용량 추출)와 from_parts로 FFI 버퍼 교환 공식화.
  • UTF-8 소유권 보존 변환: 유효하지 않은 바이트 시퀀스만 대체하고 기존 버퍼를 재활용하는 from_utf8_lossy_owned 추가.
  • 파일 타임스탬프 설정 함수: 심볼릭 링크 보안 공격을 방지하는 set_times_nofollow를 포함한 파일 시간 제어 표준화.

도구체인 업데이트는 공식 패키지 관리자를 통해 즉시 적용할 수 있다. 표준 명령인 rustup update stable을 실행하면 현재 환경의 도구체인이 1.99.0 안정 버전으로 갱신된다. 개별 프로젝트의 Cargo.toml에서 edition = "2024" 또는 기존 에디션을 유지하더라도 표준 라이브러리 API는 컴파일러 버전 갱신 즉시 사용 가능하다.

  • 표준 갱신 절차: rustup update stable 명령을 통한 공식 도구체인 업데이트 수행.
  • 신규 설치 환경: 공식 웹사이트의 설치 스크립트 실행 시 1.99.0 버전이 기본 설치됨.
  • 베타 및 나이틀리 테스트: 차기 기능 사전 검증을 원할 경우 rustup default beta 구성 가능.
  • 빌드 시스템 정리: C 언어로 분리되어 있던 가변 인자 래퍼 파일들을 제거하여 Cargo 단일 빌드로 통합.
  • 레거시 린트 점검: Box::leak의 왕복 회수 패턴이 존재하는 영역을 검색하여 into_non_null로 교체.

확인하지 못한 것

  • 특정 임베디드 타깃(티어 2/티어 3)에서 VaList의 하드웨어 레지스터 저장 영역 세부 레이아웃. 공식 문서는 주요 티어 1 플랫폼(x86_64, AArch64)에 대한 호환성을 명시하나 특수 아키텍처는 개별 타깃 문서를 확인하지 못했다.
  • 사용자 정의 할당자(Allocator API)가 최종 안정화될 시점의 정확한 릴리스 번호. Box::leak 권고 배경에서 할당자 안정화 계획이 언급되었으나 구체적 일정은 본문에 없다.
  • std::fs::set_times_nofollow가 지원되지 않는 구형 파일 시스템 커널에서 반환하는 운영체제별 정확한 오류 코드(errno) 매핑.
  • 가변 인자 함수 호출 시 발생할 수 있는 인라인 전개 최적화(LTO)가 C 컴파일러와의 크로스 랭귀지 환경에서 미치는 바이너리 크기 변화 실측치.
  • 향후 에디션에서 Box::leak의 소유권 회수 패턴에 대한 컴파일 타임 경고나 린트(Clippy) 규칙이 추가될지 여부.
