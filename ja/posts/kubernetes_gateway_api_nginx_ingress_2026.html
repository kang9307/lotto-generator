Kubernetes Gateway APIへの移行 - NGINX Ingress Controller廃止のその先 2026

アノテーションの時代を終え、標準リソースでトラフィックを統べる

2026-06-09 IT・技術

序章: クラスタの半分が揺れた事件

2025年11月、Kubernetesプロジェクトは重い発表を出しました。クラウドネイティブ環境の約半数が依存していた中核インフラ、ingress-nginx(NGINX Ingress Controller)が2026年3月に引退(retirement)するというものです。SIG Networkとセキュリティ対応委員会は、このプロジェクトを持続可能にするための追加人員と支援を探そうと努めましたが叶わず、ユーザの安全を優先してプロジェクトを閉じる決定をしました。公式発表によれば、2026年3月以降は新規リリースもバグ修正もセキュリティ脆弱性のパッチもありません。

これは単なる一ライブラリのEOL(End-of-Life)ではありません。ingress-nginxはあまりに多くの場所でインターネットとクラスタ内部をつなぐ関門の役割を担ってきたため、その廃止は数多くの運用チームに同時に「何に乗り換えるか」という問いを突きつけます。そしてKubernetesプロジェクトが示した推奨経路の中心にはGateway APIがあります。本稿はingress-nginx廃止という事件を起点に、なぜIngressが限界に達したのか、Gateway APIがそれをどう標準として解決するのか、そして実務でどう移行するかを丁寧に整理します。

注意: 廃止されるのはオープンソースのコミュニティプロジェクトkubernetes/ingress-nginxです。F5(旧NGINX Inc.)の商用NGINX Ingress Controllerは完全に別のコードベースで、独自のライフサイクルに沿って維持され続けます。両者を混同すると誤った意思決定につながります。

1. Ingressとは何だったか - そしてなぜ壁にぶつかったか

まず土台を固めます。IngressはKubernetesでクラスタ外部のHTTP/HTTPSトラフィックを内部サービスへルーティングするための標準リソースでした。ホスト名とパスを基準にどのサービスへ送るかを定義する、いわばL7ルーティング規則です。概念そのものは単純です。

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop-ingress
spec:
  rules:
  - host: shop.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80

問題は、この単純な仕様が現実の要求に追いつけなかったことです。実務ではタイムアウト、リライト、ヘッダ操作、カナリア分配、mTLS、レート制限といった機能が必要ですが、Ingress標準仕様にはそれらを表現する場所がありませんでした。結果として各コントローラは足りない表現力をアノテーション(annotation)で補いました。

metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$1
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "20"

ここでIngressの三つの宿痾が露わになります。

  • アノテーションの氾濫: 中核のルーティング動作が標準仕様ではなくコントローラ固有のアノテーション文字列に隠れます。検証が難しく、たった一つのタイプミスが静かに動作を壊します。
  • ベンダロックイン: nginx.ingress.kubernetes.io/...アノテーションはingress-nginx専用です。TraefikやHAProxyに変えるには全アノテーションを書き直す必要があります。「標準」という名が空々しくなります。
  • 役割分離の欠如: ホスト・パス・TLS・リライトが一つのリソースに固まり、プラットフォームチームとアプリチームが同じオブジェクトを触る羽目になります。マルチテナント環境で権限境界を引くのが困難です。

ingress-nginxのセキュリティ負担が増した背景にもこの構造があります。アノテーションで受け取った設定文字列を内部でNGINX設定へ変換する処理は本質的に攻撃面が広く、保守難度も高い。標準が表現できないものを迂回で補ううちに複雑さが積み上がったのです。

2. Gateway APIとは - 標準として再設計されたトラフィック関門

この限界に正面から取り組むためSIG Networkが設計したのがGateway APIです。Ingressの後継ですが、単なるバージョンアップではなく、トラフィックルーティングを一から設計し直した標準です。中核となる考えは二つ。第一に、実務で必要な機能(ヘッダ・リライト・トラフィック分配・名前空間横断ルーティング)をアノテーションではなく標準フィールドで表現する。第二に、一つの巨大なリソースを役割に応じて複数のリソースに分離する。

最も重要な事実は、Gateway APIの中核リソースが既にv1.0でGA(正式版、Generally Available)に到達していることです。公式ドキュメントによれば、GatewayClass・Gateway・HTTPRouteはv1へ昇格し、後方互換性を保証する安定APIです。実験機能ではなく、本番に使える標準です。

2.1 三つの中核リソース

リソース 何を定義するか たとえ
GatewayClass どのコントローラ(実装)がトラフィックを処理するか。クラスタ範囲のテンプレート。 StorageClassと同じ位置
Gateway 実際のトラフィック入口インスタンス。リスナ・ポート・プロトコル・TLSを定義。 ロードバランサそのもの
HTTPRoute GatewayリスナからバックエンドへのHTTPルーティング規則。 パス・ヘッダ基準のルーティング表

関係は直感的です。各Gatewayは一つのGatewayClassに結び付き「誰がこのトラフィックを処理するか」を定め、HTTPRouteのようなルーティングリソースがGatewayに付いて「どうルーティングするか」を定めます。HTTPだけでなくTCPRoute・TLSRoute・GRPCRouteといった兄弟リソースもあり、プロトコルごとの標準ルーティングを同じ流儀で表現できます。

2.2 同じことをGateway APIで表現すると

# 1) クラスタ運用者: トラフィック入口を定義
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shop-gateway
spec:
  gatewayClassName: envoy        # どの実装が処理するか
  listeners:
  - name: https
    protocol: HTTPS
    port: 443
    tls:
      mode: Terminate
      certificateRefs:
      - name: shop-tls
---
# 2) アプリ開発者: ルーティング規則を定義(アノテーション無し・標準フィールドで)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-route
spec:
  parentRefs:
  - name: shop-gateway
  hostnames:
  - "shop.example.com"
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /api
    filters:
    - type: URLRewrite        # 標準フィルタ: アノテーション不要
      urlRewrite:
        path:
          type: ReplacePrefixMatch
          replacePrefixMatch: /
    backendRefs:
    - name: api-svc
      port: 80

違いが見えますか? リライトがnginx.ingress.kubernetes.io/rewrite-targetというベンダ専用文字列ではなく、filters内の標準URLRewriteフィルタで表現されます。このマニフェストはEnvoy Gatewayでも、Istioでも、NGINX Gateway Fabricでも同じように動作します。実装を変えてもルーティング定義はそのままです。

3. 役割分離(Role-Oriented) - Gateway APIの真の革新

Gateway API最大の変化は機能追加ではなく役割分離です。公式設計はKubernetesネットワーキングに関わる組織の実際の役割に合わせてリソースを分けます。

  • インフラ提供者(Infrastructure Provider): クラウド事業者やプラットフォーム提供者がGatewayClassをデプロイします。クラスタ範囲のリソースで、そこから派生するGatewayの動作を定義するテンプレートです。
  • クラスタ運用者(Cluster Operator): GatewayClassを使ってGatewayを立て、「トラフィックがどこからどう入るか」を定義します。ポート・TLS・リスナが彼らの責任です。
  • アプリケーション開発者(Application Developer): HTTPRouteで「自分のサービスへどうルーティングするか」だけを定義します。インフラの詳細を知らなくて構いません。

なぜ重要か。IngressではTLS証明書設定とアプリのルーティング規則が一つのオブジェクトに混ざり、アプリ開発者がインフラを触るか、逆にプラットフォームチームが全ルーティングを抱える羽目になっていました。Gateway APIではプラットフォームチームがGateway(入口・TLS)を管理し、各チームは自分のHTTPRouteだけを管理します。マルチテナント環境で安全な権限境界がリソースモデル自体に刻まれたのです。この構造はプラットフォームエンジニアリングの「セルフサービスと安全なガードレール」という思想と正確に噛み合います。より広い文脈はプラットフォームエンジニアリング完全ガイド 2026で扱います。

4. なぜ「標準化」が重要か

Gateway APIの価値を一語に押し込めば移植性(portability)です。標準そのものが表現力を備えれば、ルーティングの意図が特定ベンダのアノテーション辞書に縛られません。これは三つの実質的な利点につながります。

  1. 乗り換えコストの激減: GatewayClassのcontrollerNameだけ変えれば、同じHTTPRouteで別の実装上で動きます。今回のingress-nginx廃止のような事件が再び来ても、標準の上にいれば衝撃は小さい。
  2. 検証可能性: ルーティングが強型(typed)フィールドで表現されるため、kubectlやCIでスキーマ検証ができます。アノテーションのタイプミスによる静かな障害が減ります。
  3. エコシステムの集中: すべての実装が同じ標準に対して適合性(conformance)テストを通そうと競うため、機能革新が分散せず標準の上に積み上がります。

要するに標準化は「一つの実装を強制する」ことではありません。複数の実装が互換に話せる共通言語を作ることです。これがIngressのアノテーションのバベルの塔と根本的に異なる点です。

5. 主要なGateway API実装 - 何を選ぶか

標準が一つでも実装は複数です。2026年時点の主要な実装と性格を整理します。重要な前提は、どれを選んでもマニフェスト(HTTPRouteなど)は大半が再利用できることです。

実装 データプレーン 強み 適する場合
Envoy Gateway Envoy 高い適合性と機能速度、Envoyネイティブ L7機能を幅広く使う一般的な選択
Istio Envoy(Ambient) サービスメッシュ統合、ミリ秒単位の設定伝播 既にメッシュを使うかmTLS・トラフィックポリシーが核心
Cilium eBPF L4スループット最強、カーネルオーバーヘッド回避 CNIにCiliumを使いL4性能が重要
NGINX Gateway Fabric NGINX ingress-nginxユーザに親しみやすい、Goコントロールプレーン NGINX基盤から最も近い移行経路
Kong Kong/NGINX APIゲートウェイ機能、速い設定伝播 API管理・プラグインエコシステムが必要

最近の業界分析では、「Envoyネイティブ」エコシステム(Envoy Gateway・Istio Ambient)が最も高い適合性と機能速度を示し、事実上の支配的アーキテクチャパターンになっていると評価されています。L4スループットが絶対的に重要ならeBPFデータプレーンを持つCiliumが際立ちます。一方ingress-nginxから出発するチームには、NGINXコントロールプレーンをGoで書き直しGateway APIをネイティブに話すようにしたNGINX Gateway Fabricが、心理的にも技術的にも最も近い存在です。

6. 移行 - ingress2gatewayと段階的切替

最も現実的な問いに入ります。「既に数十のIngressが動いているのにどう移すのか?」幸い、SIGが公式の変換ツールを提供しています。

6.1 ingress2gateway

ingress2gatewayは既存IngressリソースをGateway・HTTPRouteへ自動変換するKubernetes SIGプロジェクトです。NGINX・Istio・Kong・Apisix・GCEなど複数プロバイダのプロバイダ固有アノテーション処理に対応します。複雑なIngress規則とアノテーションを手で翻訳するのは誤りの多い作業ですが、このツールがその過程を自動化します。

# クラスタの全IngressをGateway APIリソースとして出力
ingress2gateway print --input-file=ingress.yaml --providers=ingress-nginx

# 結果(概念的): Gateway + HTTPRoute YAMLが生成される
# → そのまま適用せず必ずレビューすること(自動変換は「下書き」)

核心の注意: 自動変換の結果は下書きです。標準フィールドへ綺麗に対応する規則もありますが、ベンダ専用アノテーションには標準に1対1対応がないものもあります。変換後に差分をレビューし、必要なら実装ごとの拡張(例: Envoy Gatewayのポリシーリソース)で補う必要があります。

6.2 段階的移行ロードマップ

  1. インベントリ把握: クラスタの全Ingressと、そこに付いたアノテーションを一覧化します。どのアノテーションが標準へ対応するかからまず確認します。
  2. 実装の選択・導入: 上の比較を踏まえGateway API実装を選び、既存のingress-nginxと並行導入します。一度に総入れ替えしません。
  3. 変換下書きの生成: ingress2gatewayでGateway・HTTPRouteの下書きを作り、レビュー・補正します。
  4. 非中核から移行: トラフィックが少なくリスクの低いサービスを先に新Gatewayへ移し動作を検証します。
  5. トラフィックの段階移行: DNS重み付け・カナリア・ブルーグリーンでトラフィックを段階的に新経路へ移します。問題があれば即座に戻します。
  6. ingress-nginxの撤去: 全ルーティングが検証されたら旧コントローラを下ろします。

この段階的な姿勢は信頼性運用の基本原則と同じです。「一括全面切替」は最速の道に見えて最も危険です。自動化・移行に常にロールバック経路を置く考え方は、SREにおけるAI - 信頼性ある運用の未来で扱った原則と正確に重なります。

7. 移行時の考慮点 - 落とし穴チェック

切替を滑らかにするには、いくつかの落とし穴を事前に知っておく必要があります。

  • 標準に1対1対応のないアノテーション: 細かなNGINXチューニング(特殊タイムアウト、カスタム設定スニペット)は標準フィールドで全て表現できないことがあります。実装固有の拡張ポリシーで補いますが、その部分は再びベンダ依存が生じる点を認識してください。
  • TLS・証明書管理モデルの変化: IngressのTLSブロックがGatewayのリスナ単位certificateRefsへ移ります。cert-manager連携の方式も点検が必要です。
  • 名前空間横断ルーティング: Gateway APIはReferenceGrantで名前空間間の参照を明示的に許可します。セキュリティ上強力ですが、最初は「なぜ繋がらない?」の原因になりがちです。
  • 実装ごとの適合性の差: すべての実装が標準の全機能を100%サポートするわけではありません。使いたい機能が選んだ実装の適合性(conformance)の範囲内か確認してください。Gateway API v1.5のレビュー過程では、更新が止まった実装は一覧から除外される予定です。
  • 可観測性・メトリクスの再構成: ingress-nginxメトリクスに合わせたダッシュボード・アラートは、新データプレーン(Envoyなど)に合わせて作り直す必要があります。

8. 日本のインフラ環境への示唆

この流れを国内の運用現実に当てはめると、いくつかの実質的なポイントが見えます。

  • マネージドKubernetes利用者: 国内外のマネージドK8sを使うチームなら、そのプラットフォームがどのGatewayClassを既定で提供するかの確認が出発点です。インフラ提供者がGatewayClassを敷いてくれれば運用チームの負担が減ります。
  • 金融・通信のセキュリティ要件: インターネット公開クラスタで2026年3月以降パッチの途絶えたコントローラを維持するのは、規制・監査の観点でリスクです。移行優先度を上げるべきです。
  • 小規模な運用人員: インフラエンジニアが複数の役割を兼ねる国内の多くの組織では、役割分離が即「運用負担の委譲」につながります。アプリチームがHTTPRouteをセルフサービスで管理すれば、プラットフォームチームのボトルネックが緩みます。
  • 段階移行の文化: 無停止が生命線の大規模サービスの特性上、カナリア・並行運用を前提とした段階的切替が事実上唯一の安全な道です。

9. よくある誤解を正す

9.1 「Ingressが即座に死ぬ」

違います。死ぬのはオープンソースのingress-nginxコントローラです。Ingressリソース(networking.k8s.io/v1)自体はKubernetesに残り、他のIngressコントローラも存在します。ただし未来はGateway APIへ向かいます。

9.2 「Gateway APIはまだ実験段階だ」

違います。中核リソース(GatewayClass・Gateway・HTTPRoute)はv1.0でGAに到達した安定APIです。本番で使えます。

9.3 「F5 NGINX商用製品も終わる」

違います。廃止されるのはコミュニティプロジェクトだけです。F5の商用NGINX Ingress Controllerは別途維持されます。

9.4 「実装を間違えると最初からやり直し」

概ね違います。標準リソースを使う限りHTTPRouteなどのルーティング定義は大半が再利用されます。実装乗り換えのコストはIngress時代よりはるかに小さいです。

10. 結論 + すぐ適用できる3つ

ingress-nginxの廃止は危機に見えますが、より正確には先延ばしにしてきた標準化を強制する転換点です。Ingressはアノテーションという迂回路で10年を凌ぎ、その迂回路がベンダロックイン・検証不能・セキュリティ負担で限界に達しました。Gateway APIは同じ問題をアノテーションではなく標準フィールドと役割分離で解く、一から設計し直した答えです。中核リソースは既にGAであり、実装は複数あり、標準の上ではどれを選んでもマニフェストが再利用されます。

すぐ適用できる三つで締めます。

  1. まずインベントリを取れ。 クラスタの全Ingressとアノテーションを一覧化し、インターネット公開のものから優先度を付けましょう。何を移すか分からなければ移行計画も立てられません。
  2. ingress2gatewayで下書きを作れ。 手で翻訳せず公式SIGツールで変換下書きを取りレビューしましょう。標準へ対応しないアノテーションがどこか見えれば、半分は終わったも同然です。
  3. 並行運用で段階移行せよ。 新実装をingress-nginxと並べて立て、非中核サービスからカナリアで移し検証しましょう。ロールバック経路を常に開けておくことが無停止切替の核心です。

最後の一行に要約するとこうです。「廃止されたのは一つのコントローラに過ぎず、移るべき先は特定のベンダではなく標準だ。」 ingress-nginxの次を悩む全てのチームにとって、Gateway APIは単なる代替品ではなく、「次にまた来る廃止」に揺るがない土台です。
