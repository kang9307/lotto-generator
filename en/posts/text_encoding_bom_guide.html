The Bug an Invisible Three Bytes Makes - Where the UTF-8 BOM Breaks Shells, JSON and CSV 2026

Where EF BB BF actually breaks things, every case run and captured

Sep 1, 2026 Tech & IT

A script that ran yesterday now answers with No such file or directory. The file is still there, the first line is still #!/bin/bash, and nothing looks wrong when you open it in an editor. There is one place left to look: the three bytes at the head of the file.

The UTF-8 BOM is EF BB BF. Nothing is drawn for it on screen, most editors will not even let you put a cursor in front of it, and diff will report two lines as different while showing you identical characters. This piece is a record of where those three bytes break things, built and run rather than described. There is more output here than explanation.

Everything below was actually executed in a Git Bash environment on Windows 10 (10.0.19045). The tools used were GNU bash 5.2.37 (MINGW64/MSYS2), GNU sed 4.9, GNU grep 3.0, GNU coreutils 8.32, GNU libiconv 1.18, dos2unix 7.5.2, file 5.46, xxd 2024-12-07, Node.js v22.16.0, Python 3.11.9 and Windows PowerShell 5.1.19041.6456. Wording and behaviour can differ on another platform or version.

The BOM was a byte order marker

The name is the answer. Byte Order Mark. It was made for encodings such as UTF-16 and UTF-32 that read several bytes as a single unit. In those encodings the same value lands differently depending on whether the high byte or the low byte is stored first. Putting one U+FEFF at the head of the file lets the reader see whether it arrives as FE FF or FF FE and decide the order from that.

The Unicode Consortium FAQ is explicit here. A BOM is U+FEFF at the beginning of a data stream, used as a signature defining the byte order and encoding form. Then it separates UTF-8 out. UTF-8 is byte oriented and therefore does not have that issue. It always has the same byte order. So in UTF-8 an initial BOM is not announcing an order at all; it is only a signature, an indication that an otherwise unmarked text file is UTF-8. The same document immediately attaches a caution: some recipients of UTF-8 encoded data do not expect a BOM.

So why is it everywhere? An old habit of Windows-side tooling. Back when code pages varied by region, an extension alone could not tell you whether a text file was UTF-8 or the local code page. Three bytes at the front at least let those tools agree among themselves. Notepad saved that way, and PowerShell's -Encoding utf8 meant exactly that for a long time. The Linux side settled on UTF-8 as the default from the start and never needed the signature. When the two habits meet in one repository, that is where the accidents begin.

  • UTF-16 / UTF-32 — the byte order problem is real. This is the job the BOM was invented for
  • UTF-8 — there is no order problem. A BOM here is not an order marker, just a signature
  • When the signature helps — when nothing else can announce the encoding, and a tool has only the extension and the local code page to go on
  • When the signature is in the way — any format where the first byte is syntax. Shebangs, JSON, XML declarations and CSV headers all qualify

What invisible actually means here

Make two files with the same content, give one of them a BOM, and put them side by side. It becomes clear immediately why this goes unnoticed for so long. cat shows both identically. Only the size differs, by three bytes.

$ printf 'hello\n'              > plain.txt
$ printf '\xef\xbb\xbfhello\n'  > bom.txt

$ cat plain.txt; cat bom.txt
hello
hello                      # the two lines look identical

$ ls -l plain.txt bom.txt
-rw-r--r-- 1 user user 6 Sep  1 10:25 plain.txt
-rw-r--r-- 1 user user 9 Sep  1 10:25 bom.txt

$ xxd plain.txt
00000000: 6865 6c6c 6f0a                           hello.
$ xxd bom.txt
00000000: efbb bf68 656c 6c6f 0a                   ...hello.

$ od -c bom.txt
0000000 357 273 277   h   e   l   l   o  \n
0000011

$ file plain.txt bom.txt
plain.txt: ASCII text
bom.txt:   Unicode text, UTF-8 (with BOM) text

The three dots in the right column of xxd are ef bb bf. file even spells out «with BOM». So far the tools are being helpful. The trouble starts with comparison tools.

$ diff plain.txt bom.txt
1c1
< hello
---
> hello                    # same characters on screen, reported as different
$ echo $?
1

$ cmp plain.txt bom.txt
plain.txt bom.txt differ: char 1, line 1

$ wc -c < bom.txt
9
$ LC_ALL=en_US.UTF-8 wc -m < bom.txt
7                          # 9 bytes, 7 characters (BOM 1 + hello 5 + newline 1)

diff is doing its job exactly right. It said the two lines differ, and they do. What it cannot do is show that difference to a human. This is how a change gets waved through in review with a shrug about why that line is marked as modified.

A shebang stops being a shebang

When the first two bytes of an executable file are #!, the kernel reads what follows as an interpreter path. The condition is that those two bytes must be the first bytes of the file. Slip three bytes in front and that line is no longer a shebang, just the first command line.

$ printf '#!/bin/bash\necho ok\n'              > ok.sh
$ printf '\xef\xbb\xbf#!/bin/bash\necho ok\n'  > bomshebang.sh
$ chmod +x ok.sh bomshebang.sh

$ ./ok.sh
ok

$ ./bomshebang.sh
./bomshebang.sh: line 1: #!/bin/bash: No such file or directory
ok
                           # the invisible BOM sits right before #! in that message

$ head -c 16 bomshebang.sh | xxd
00000000: efbb bf23 212f 6269 6e2f 6261 7368 0a65  ...#!/bin/bash.e

There are two things worth reading in that output. One is that the error message points at the shebang line rather than the file name. You go and type which bash wondering whether bash disappeared, and bash is right where it always was. What failed to run is a command named <BOM>#!/bin/bash.

The other is that ok was printed on the next line. In this environment (bash 5.2.37 under MSYS2) the shell fell back to reading the rest of the file itself after the shebang failed. In other words the script does not die; only line 1 fails and everything continues. That is the worse outcome. The exit status is 0, so CI passes.

$ printf '\xef\xbb\xbf#!/bin/bash\nset -e\necho reached\n' > strict.sh
$ bash strict.sh
strict.sh: line 1: #!/bin/bash: No such file or directory
reached
$ echo $?
0                          # set -e does not catch a failure on line 1

set -e applies from the line it appears on, so it never reaches the failure on line 1. That combination is why this often surfaces days later as «the build succeeded but the artifact is wrong».

In config files, only the first line disappears

Scripts are not the only thing a shell reads. A .env file listing KEY=value pairs and pulled in with source follows the same rules, and the symptom here is much quieter. Exactly one line goes missing.

$ printf 'API_HOST=example.internal\nAPI_PORT=8080\n'             > plain.env
$ printf '\xef\xbb\xbfAPI_HOST=example.internal\nAPI_PORT=8080\n' > bom.env

$ bash -c '. ./plain.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
HOST=[example.internal] PORT=[8080]

$ bash -c '. ./bom.env; echo "HOST=[$API_HOST] PORT=[$API_PORT]"'
./bom.env: line 1: API_HOST=example.internal: command not found
HOST=[] PORT=[8080]
$ echo $?
0                          # everything from line 2 is fine. only line 1 is empty

API_PORT came through and only API_HOST is an empty string. The value is plainly written in the file yet the variable is empty, so the usual next hour goes into hunting typos and suspecting load order. Even if that one command not found line drifted into a log somewhere, nothing on screen tells you there is an invisible character at the left edge of it.

The same thing happens with YAML. In code that parses it by hand, the first key changes its name.

$ printf '\xef\xbb\xbfname: demo\nport: 8080\n' > app.yaml
$ node -e "
const s = require('fs').readFileSync('app.yaml', 'utf8');
const m = {};
for (const line of s.split(/\r?\n/)) {
  if (!line) continue;
  const i = line.indexOf(':');
  m[line.slice(0, i)] = line.slice(i + 1).trim();
}
console.log('keys :', JSON.stringify(Object.keys(m)));
console.log('name :', m.name);
console.log('port :', m.port);
"
keys : ["name","port"]     # there is a U+FEFF in front of the first key
name : undefined
port : 8080

Print the key list and it reads ["name","port"]. Yet m.name is undefined. This is the classic split between what a person sees and what a program compares.

JSON - the standard says do not add one

JSON is one of the rare cases where the answer is written into the standard. Section 8.1 of RFC 8259, on character encoding, places two sentences next to each other. One is a requirement: implementations MUST NOT add a byte order mark to the beginning of a networked-transmitted JSON text. The other is a permission: in the interests of interoperability, implementations that parse JSON texts MAY ignore a byte order mark rather than treating it as an error.

That asymmetry explains the confusion in the field exactly. The writing side must not, and the reading side may or may not. Which means some parsers let it through and some throw. That is why the same file behaves differently once you change tools. On Node.js v22.16.0 the split appears inside a single runtime.

// jsontest.js
const fs = require('fs');
for (const f of ['plain.json', 'bom.json']) {
  const raw = fs.readFileSync(f, 'utf8');
  console.log(f, 'first char U+' +
    raw.codePointAt(0).toString(16).toUpperCase().padStart(4, '0'));
  try   { console.log('  OK', JSON.stringify(JSON.parse(raw))); }
  catch (e) { console.log('  ' + e.name + ': ' + e.message); }
}

$ node jsontest.js
plain.json first char U+007B
  OK {"name":"demo","port":8080}
bom.json first char U+FEFF
  SyntaxError: Unexpected token '', "{"name":""... is not valid JSON

$ node -e "console.log(JSON.stringify(require('./bom.json')))"
{"name":"demo","port":8080}
                           # same file, and require lets it through

JSON.parse throws and require passes, because the module loader strips the BOM before handing the text over. So it presents itself as «works locally, fails in deployment», when what actually changed was not the environment but the single line of code that reads the file. Swap require('./config.json') for JSON.parse(fs.readFileSync(...)) and it blows up.

One more detail. In the SyntaxError message, the quotes after Unexpected token look empty. The U+FEFF is in there. Even the error message cannot show you the cause.

The CSV paradox - here the BOM is the fix

Read this far and removing every BOM looks like the answer. There is exactly one place where the opposite holds: a CSV opened in Excel. A UTF-8 CSV double-clicked open in Excel frequently renders non-Latin text as garbage, and putting a BOM at the front often makes it open as UTF-8 instead. That is why so much CSV export code deliberately writes those three bytes.

So the same three bytes are a hint in a file a person opens and garbage in a file a program reads. The problem is that one CSV usually serves both purposes. Export a file with a BOM for Excel, feed it into another system later, and the first column name changes.

// csv.js — a parser that does not use trim()
const fs = require('fs');
const text  = fs.readFileSync(process.argv[2], 'utf8');
const lines = text.split(/\r?\n/).filter(l => l.length > 0);
const cols  = lines[0].split(',');
const rows  = lines.slice(1).map(r =>
  Object.fromEntries(r.split(',').map((v, i) => [cols[i], v])));

console.log('cols[0]         :', JSON.stringify(cols[0]));
console.log('cols[0].length  :', cols[0].length);
console.log('cols[0] === "id":', cols[0] === 'id');
console.log('row0.id         :', rows[0].id);

$ node csv.js plain.csv
cols[0]         : "id"
cols[0].length  : 2
cols[0] === "id": true
row0.id         : 1

$ node csv.js bom.csv
cols[0]         : "id"     # looks exactly the same on screen
cols[0].length  : 3        # except the length is 3
cols[0] === "id": false
row0.id         : undefined

cols[0].length is 2 in one case and 3 in the other. Without that one line there is nothing to see. The failure mode is bad too: no exception is raised, and undefined flows quietly downstream. A hundred-thousand-row load finishes as «all rows succeeded, first column empty everywhere».

Which side to fix is decided by the final consumer of the file. If a person opens it in Excel, add the BOM. If a program will eat it again, do not. When both are true, produce two files.

Why some code survives - what trim() really does

Writing the example above, the header line was first split with text.trim().split('\n'), and the BOM file passed cleanly. Not because the parser was wrong, but because JavaScript's trim() treats U+FEFF as whitespace and strips it.

// t7.js — '\ufeff' is the escape for the BOM character itself
const s = '\ufeffid';
console.log('length          :', s.length);
console.log('trim().length   :', s.trim().length);
console.log('trim() === id   :', s.trim() === 'id');
console.log('/\\s/ matches?   :', /\s/.test('\ufeff'));
console.log('Number()        :', Number('\ufeff42'));
console.log('parseInt()      :', parseInt('\ufeff42'));

$ node t7.js
length          : 3
trim().length   : 2
trim() === id   : true
/\s/ matches?   : true
Number()        : 42
parseInt()      : 42

/\s/ matches U+FEFF, and Number() and parseInt() both ignore a leading BOM and return 42. That tolerance is what makes the problem intermittent. Some fields go through trim() and survive; others do not and break. Same file, same codebase, different results.

  • Paths that use the value as an object key usually skip trim(), which is why header names are where it surfaces
  • Paths that convert to a number almost always pass, which is why numeric validation never catches this
  • Regex validation passes too if it uses \s. A rule like «the value must contain no whitespace» will not flag a BOM
  • In short, ordinary validators do not catch it. You need a separate check that looks at the first three bytes

Comparison, search and hashing drift apart

A line carrying a BOM drops out of any search anchored to the start of the line, because what follows ^ is U+FEFF rather than i. Log filters, batch scripts and migration verification queries all quietly return zero hits here.

$ grep -c '^id' plain.csv
1
$ grep -c '^id' bom.csv
0                          # the anchor is what loses it
$ grep -c 'id' bom.csv
1                          # drop the anchor and it matches

$ grep -Fxc 'id' list_a.txt
1
$ grep -Fxc 'id' list_b.txt
0                          # whole-line matching behaves the same

$ cat v1.txt v2.txt | sort -u | xxd
00000000: 616c 7068 610a efbb bf61 6c70 6861 0a    alpha....alpha.
                           # sort -u keeps the same word twice

$ sha256sum plain.html bom.html
904ee45b2e532f436f4c05f8d809365538b9bf9843030bc01d0f9079deb0cbe7 *plain.html
a3369d9b5f62004281debdaccdc69395cc94af732b19023258576308ce7cbc35 *bom.html

Different hashes become a problem in release verification straight away. In a pipeline that checks «is this artifact identical to the last one» by checksum, someone changing an editor setting is enough to mark everything as changed.

One more thing. A BOM is not only found at the head of a file. Concatenate several BOM-carrying files and one lands in the middle.

$ cat part1.csv part2.csv > merged.csv
$ grep -c $'\xef\xbb\xbf' merged.csv
2
$ xxd merged.csv
00000000: efbb bf69 642c 760a 312c 610a efbb bf69  ...id,v.1,a....i
00000010: 642c 760a 322c 620a                      d,v.2,b.
                           # the second BOM sits in the middle of the data

A mid-file U+FEFF also served as a zero-width no-break space in older Unicode, so rendering it shows nothing at all. When a log collector or a batch that stitches split downloads produces a file like this, tracing it takes a particularly long time.

How it shows up on the web

With a BOM at the head of an HTML file, the first character of the document is no longer <. In bytes it looks like this.

$ head -c 24 bom.html | xxd
00000000: efbb bf3c 2144 4f43 5459 5045 2068 746d  ...<!DOCTYPE htm
00000010: 6c3e 0a3c 6874 6d6c                      l>.<html

$ node -e "
const s = require('fs').readFileSync('bom.html', 'utf8');
console.log('indexOf   :', s.indexOf('<!DOCTYPE'));
console.log('startsWith:', s.startsWith('<!DOCTYPE'));
"
indexOf   : 1
startsWith: false

From here on nothing was executed; only the structure is described. Two shapes are commonly reported in server-side template environments. One is an unexplained blank line or gap at the very top of the page. A character was emitted before the document began, so the parser treats it as body content. The other is failure to send headers. In a structure like PHP, where file contents flow straight into the output stream, three bytes before the <?php tag are already output, so any header call or redirect after that fails with a warning about headers already being sent.

The useful approach in that situation is to narrow from the file side rather than the symptom side. Even with dozens of included files, pulling out only those whose first three bytes are EF BB BF usually leaves one or two.

How to check whether one is there

There are several tools and they all do the same thing: look at the first three bytes of a file. Use whichever fits the situation.

$ file config.json run.sh clean.txt
config.json: Unicode text, UTF-8 (with BOM) text
run.sh:      POSIX shell script, Unicode text, UTF-8 (with BOM) text executable
clean.txt:   ASCII text

$ xxd config.json | head -1
00000000: efbb bf7b 2261 223a 317d 0a              ...{"a":1}.

$ grep -rlI $'\xef\xbb\xbf' .
./config.json
./sub/run.sh

$ grep -rlI $'^\xef\xbb\xbf' .    # only where it sits at the start of a line
./config.json
./sub/run.sh

$ cat -A bom.txt
M-oM-;M-?hello$

$ sed -n l bom.txt
\357\273\277hello$

M-oM-;M-? from cat -A and \357\273\277 from sed -n l are the same three bytes shown in meta notation and in octal. Those two are the quickest way to confirm it by eye in a terminal. Be aware that grep -rlI also catches BOMs in the middle of a file. Anchoring narrows it, but a line start is still not a file start. To look at exactly the first three bytes, open the file from a program.

// bomcheck.js — reads only the first three bytes. good for CI
const fs = require('fs'), path = require('path');
const BOM = Buffer.from([0xEF, 0xBB, 0xBF]);

function walk(dir, out = []) {
  for (const e of fs.readdirSync(dir, { withFileTypes: true })) {
    const p = path.join(dir, e.name);
    if (e.isDirectory()) walk(p, out); else out.push(p);
  }
  return out;
}

let bad = 0;
for (const f of walk(process.argv[2] || '.')) {
  const fd = fs.openSync(f, 'r');
  const head = Buffer.alloc(3);
  fs.readSync(fd, head, 0, 3, 0);
  fs.closeSync(fd);
  if (head.equals(BOM)) { console.log('BOM: ' + f); bad++; }
}
console.log(bad ? bad + ' file(s) with a UTF-8 BOM' : 'no BOM found');
process.exit(bad ? 1 : 0);

$ node bomcheck.js ./tree
BOM: tree\config.json
BOM: tree\sub\run.sh
2 file(s) with a UTF-8 BOM
$ echo $?
1

$ node bomcheck.js ./cleantree
no BOM found
$ echo $?
0

On the PowerShell side, ReadAllBytes and a look at the head is enough. One thing to watch: reading with Get-Content hands you a string that has already had the BOM removed. On Windows PowerShell 5.1.19041.6456, reading a BOM-carrying file with Get-Content -Raw and printing the first character gives U+006C, the first character of the actual content. At the string level nothing looks wrong, so the check has to happen at the byte level.

PS> $b = [System.IO.File]::ReadAllBytes('config.json')
PS> ($b[0..2] | ForEach-Object { $_.ToString('X2') }) -join ' '
EF BB BF

PS> (Get-Content -Path config.json -Raw)[0]
{                          # read as a string, the BOM is already gone

How to remove it, and how to break things removing it

Removal itself is not hard. What is hard is not touching the files that should be left alone. A bulk pass has no undo, so take a backup before starting.

$ sed '1s/^\xEF\xBB\xBF//' in.csv > out.csv     # to a new file (safest)
$ sed -i.bak '1s/^\xEF\xBB\xBF//' in.csv        # in place, original kept

$ xxd in.csv | head -1
00000000: 6964 2c6e 616d 650a 782c 790a            id,name.x,y.
$ xxd in.csv.bak | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.

$ awk 'NR==1{sub(/^\xef\xbb\xbf/,"")}1' in.txt > out.txt
$ perl -pi -e 's/^\x{ef}\x{bb}\x{bf}// if $.==1' in.txt

Narrowing the target to the first line only with 1s/ matters. Without a range you also delete a U+FEFF that may legitimately sit somewhere in the body. And with a suffix on -i, GNU sed 4.9 keeps the original as .bak. For a pass over hundreds of files, make that the default.

Next, the dedicated tool. There is a trap in it.

$ xxd before.csv
00000000: efbb bf61 0d0a 620d 0a                   ...a..b..     # BOM + CRLF

$ dos2unix --remove-bom before.csv
dos2unix: converting file before.csv to Unix format...

$ xxd before.csv
00000000: 610a 620a                                a.b.          # BOM and CR both gone

$ dos2unix -m -n a.csv a.bom.csv          # -m goes the other way and adds one
$ xxd a.bom.csv
00000000: efbb bf61 0a62 0a                        ...a.b.

dos2unix --remove-bom does not only remove the BOM. As the name says, it converts the line endings to LF as well. In the output above both 0d0a pairs became 0a. Run this on a file that must stay Windows-only and you trade one BOM problem for a new line ending problem. Going the other way is -m, and -n writes to a new file instead of touching the original.

iconv does not behave the way you would hope for this job.

$ iconv -f UTF-8 -t UTF-8 in.csv > out.csv
$ xxd out.csv | head -1
00000000: efbb bf69 642c 6e61 6d65 0a78 2c79 0a    ...id,name.x,y.
                           # UTF-8 to UTF-8 leaves the BOM in place

$ iconv -f UTF-8-BOM -t UTF-8 in.csv
iconv: conversion from UTF-8-BOM unsupported

$ iconv -f UTF-8 -t UTF-16 ab.txt | xxd
00000000: feff 0041 0042 000a                      ...A.B..      # a BOM is added
$ iconv -f UTF-8 -t UTF-16LE ab.txt | xxd
00000000: 4100 4200 0a00                           A.B...        # none is added

GNU libiconv 1.18 does not recognise the name UTF-8-BOM. The last two lines are worth remembering though. Converting to UTF-16 adds a BOM and converting to UTF-16LE does not, because naming the endianness removes the need to announce the order.

Finally, the most frequently suggested and most dangerous method.

$ printf '\xef\xbb\xbfhi\n' > a.txt
$ tail -c +4 a.txt | xxd
00000000: 6869 0a                                  hi.           # removed cleanly

$ printf 'hi there\n' > b.txt                                    # a file with no BOM
$ tail -c +4 b.txt | xxd
00000000: 7468 6572 650a                           there.        # it ate 'hi '

tail -c +4 discards the first three bytes unconditionally. Run only against files that have a BOM, it is correct; put it in a loop over a whole directory and the first three characters vanish from every file that had none. In the example above, hi  is gone. Using this at all requires a condition that checks for the BOM first.

There is also the option of solving it on the reading side, which is better when you cannot change the file. Python 3.11.9 ships a codec for exactly this.

>>> open('bom.json', encoding='utf-8').read()[0]
'\ufeff'
>>> json.load(open('bom.json', encoding='utf-8'))
json.decoder.JSONDecodeError: Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1 (char 0)

# csv.DictReader — one encoding name changes the first column name
utf-8      fieldnames: ['\ufeffid', 'name', 'qty']   row.get('id') -> None
utf-8-sig  fieldnames: ['id', 'name', 'qty']         row.get('id') -> 1

Python's error message is the most helpful one in this whole article: it names the cause and the fix on the same line. utf-8-sig strips a BOM if there is one and passes through if there is not, which makes it a reasonable default in code that does not control its input files.

Where to add one and where never to

The rule collapses to one line: do not add one to any format where the first byte is syntax. A shebang, JSON's opening brace, an XML declaration and a CSV's first column name all give that first byte position a meaning. Conversely, if nothing else can announce the encoding and a person is the one opening the file, adding it is the better call.

File typeBOMWhy
Shell scripts (.sh, .bash)NoThe shebang stops being a shebang. Worse, only line 1 fails and the run continues
JSON (.json)NoRFC 8259 forbids adding one on transmission. Parsers are not obliged to ignore it
YAML and config files (incl. .env)NoThe first key changes its name. It fails silently, without exception
Source code generallyNoHashes change and diff produces changes you cannot see
CSV opened in ExcelYesWithout it the text often opens as garbage. This is a file a person opens
CSV read by a programNoThe first column is no longer id. undefined flows through, every time
Windows-only text (Notepad and such)AcceptableThere is no other way to announce the encoding. Only if it is never leaving that world
UTF-16 / UTF-32 filesYesThe byte order problem is real. This is what the BOM was made for
HTMLNo<meta charset> or the HTTP header already announces the encoding

The judgement call in ambiguous cases reduces to one question too. Is a person or a program the last thing to open this file? A person, and the BOM buys you something. A program, and it almost always costs you. Both, and you split the file.

Stopping it from coming back on a team

Removing them once is easier than keeping them out. Most of them are produced by tool settings rather than people, and the most common source is PowerShell.

PS> "line one" | Set-Content a_default.txt
PS> "line one" | Set-Content b_utf8.txt   -Encoding utf8
PS> "line one" | Out-File   c_outfile.txt -Encoding utf8
PS> [System.IO.File]::WriteAllText("$pwd\d_nobom.txt", "line one`n",
      (New-Object System.Text.UTF8Encoding($false)))

a_default.txt   len=10   first bytes: 6C 69 6E 65 20 6F 6E 65
b_utf8.txt      len=13   first bytes: EF BB BF 6C 69 6E 65 20
c_outfile.txt   len=13   first bytes: EF BB BF 6C 69 6E 65 20
d_nobom.txt     len= 9   first bytes: 6C 69 6E 65 20 6F 6E 65

PS> "x" | Set-Content f.txt -Encoding utf8NoBOM
Cannot bind parameter 'Encoding'. Cannot convert value "utf8NoBOM" to type
"Microsoft.PowerShell.Commands.FileSystemCmdletProviderEncoding".

On Windows PowerShell 5.1.19041.6456, -Encoding utf8 adds a BOM. And the value utf8NoBOM does not exist in this edition, so it is rejected at parameter binding. To write BOM-free UTF-8 here, passing UTF8Encoding($false) directly is the reliable route. If your deployment scripts generate config files, this is the first thing to check.

The editor side is partly controllable through .editorconfig. The specification has a charset property accepting latin1, utf-8, utf-8-bom, utf-16be and utf-16le, and the specification itself says use of utf-8-bom is discouraged. Bear in mind this is a convention that only holds when the editor reads and honours it. A tool that does not support it writes straight through.

# .editorconfig
root = true

[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true

[*.csv]
charset = utf-8-bom          # the only exception: exports opened in Excel

One thing needs stating plainly here. Git does not normalise BOMs. The text and eol attributes documented in gitattributes handle line ending conversion, and working-tree-encoding exists for cases like UTF-16 where the repository and the working tree differ in encoding. There is no attribute that adds or removes a UTF-8 BOM. Line endings unify across a team with one line in .gitattributes; BOMs have no such mechanism.

So the last line of defence is a check. The bomcheck.js above exits with status 1 when it finds one, which drops straight into a CI step. With nothing but a shell, one line also does it.

# fail if a single BOM is present (GNU grep 3.0)
! grep -rlI $'^\xef\xbb\xbf' --include='*.sh' --include='*.json' \
                            --include='*.yaml' --include='*.yml' . \
  || { echo "BOM found in the files above"; exit 1; }
  • Block the source first — PowerShell's -Encoding utf8, Notepad and some Windows editors produce most of them
  • Write the agreement down in .editorconfig — no enforcement, but supporting tools get it right automatically
  • Do not rely on git — unlike line endings, the repository will not unify this
  • Stop it in CI — one check on the first three bytes is enough. Narrow by extension so CSV exports stay exempt
  • Do bulk removal as its own commit — mixed with other changes, nobody can tell later what actually moved

BOMs and line endings are different problems

These two get mentioned together constantly, but their causes and their fixes differ. They ended up bundled because they surface in the same places and are often fixed with the same tool. In practice they are as different as the table below.

AspectUTF-8 BOMCRLF / LF
LocationThree bytes at the head of the file, onceEnd of every line, throughout the file
BytesEF BB BF0D 0A or 0A
Does git normalise itNo. There is no attribute for itYes, through the text and eol attributes
Typical symptomOnly line 1 fails: shebang, first key, first columnImmediate failure such as bad interpreter: /bin/bash^M
How hard to spotHard. Nothing appears on screenEasy. ^M shows up in the error
Fixed withsed 1s, utf-8-sig, a first-three-bytes checkdos2unix, .gitattributes

The row that matters in practice is the third. Line endings can be aligned across a whole team through repository settings, whereas BOMs keep reappearing from each person's editor and each person's scripts. So line endings are a policy problem and BOMs are a checking problem. The fact that dos2unix handles both at once blurs that distinction, and as seen above, that convenience drags an unwanted conversion along with it.

Text turning into garbage because the encoding itself is mismatched — reading a cp949 file as UTF-8 and getting ????? or ìëíì — is a different layer and not the subject here. That one is covered in Locating Where Hangul Breaks. For file names inside archives, see Where Korean File Names Break Inside a ZIP, and for regex over Korean strings, The Korean Regex Trap.

What I Could Not Verify

  • How Excel actually behaves — that a BOM makes Excel open a UTF-8 CSV correctly is a widely used remedy, but nothing here was opened in Excel. Results are reported to vary by version and locale, so confirm it in the Excel your users actually run before relying on it. What was verified is only the other side: the first column name changes when a program reads that file
  • The PowerShell 7 line — pwsh is not installed in this environment, so it was not tested. The findings that -Encoding utf8 adds a BOM and that utf8NoBOM does not exist are specific to Windows PowerShell 5.1.19041.6456. Defaults may differ in another edition, so print the bytes yourself on the one you use
  • PHP header failures — there is no PHP in this environment, so that was not reproduced. The relevant passage in section 9 is a structural description, not an execution result. What was actually confirmed is only that the first character of the HTML document stops being <
  • BSD-family tools — the sed used here is GNU sed 4.9. Hex escapes such as \xEF and the suffix handling of -i depend on the GNU implementation and are known to differ in the default sed on macOS, which there was no environment to check
  • Git's actual behaviour — that no attribute normalises BOMs comes from the gitattributes documentation; no command was run against a repository to confirm it
  • What happens after a failed shebang — the rest of the script running on after line 1 failed was observed under bash 5.2.37 on MSYS2. Whether the same fallback occurs with a Linux distribution's shell or another kernel was not verified
