曜日を求めるのになぜ公式が必要なのか

7と365が噛み合わない場所で、ZellerとSakamotoは何を代わりに計算しているのか

2026年8月28日 開発・インフラ

序論: 今日が金曜日だとコンピュータはどうやって知るのか

2026年8月28日は金曜日である。この一文をコンピュータが作り出すには何をしなければならないのか。カレンダーをめくるのではない。どこかに曜日の書かれた表があってそれを引くのでもない。計算をする。ところがその計算が思ったより厄介だ。

厄介なのは、カレンダーが規則であると同時に不規則だからである。曜日は7日ごとに正確に巡ってくる。一方で一年は365日か366日であり、どちらになるかは4年・100年・400年という三段の条件が決める。月の長さは28、29、30、31が入り混じっており、その並びに算術的な理由はない。完璧に規則的な周期ひとつを、人が千年かけて手を入れてきた不規則な体系の上に載せなければならない。

2026年8月、GeekNewsに「曜日計算をより速くする方法」が上がった。Ben Joffeが同じ月の17日に公開した記事で、基準日からの日数を曜日に変える最後の一歩を掛け算一回とシフトに縮める方法を提案している。7がメルセンヌ数、すなわち2のべき乗から1を引いた数だという性質を使い、7で割った余りを8で割った余りに移すのが着眼点だ。

ここで見るべきはその技法そのものではなく、それが立っている場所である。なぜ公式が必要だったのか、公式は何をあらかじめ計算しておいたのか、そしてなぜ最後に残った割り算ひとつまで消そうとする試みが出てくるのか。最後には正直な問いをひとつ付ける。これは実際に誰かのプログラムを速くするのか。

1. 7と365は割り切れない

すべての問題の出発点は割り算一回だ。365を7で割ると商が52、余りが1になる。だから平年が過ぎると同じ日付の曜日が一日後ろにずれる。うるう年なら366なので余りが2になり、二日ずれる。

このずれが毎年同じ値なら問題ではない。掛け算一回で片づく。問題はずれが1のときと2のときが規則的に混ざっていることであり、その混ざり方を決めるのがうるう年ルールである。

1.1 うるう年の三段ルール — 4、100、400

グレゴリオ暦のうるう年判定は条件が三つ重なっている。

  • 年が4で割り切れればうるう年である
  • ただし100で割り切れれば平年である
  • ただし400で割り切れれば再びうるう年である

1900年が平年で2000年がうるう年なのはこれが理由だ。コードに移すと割り算三回、あるいは剰余演算三回が必要になる。後で見るように、この三つの割り算が曜日計算の費用の大きな割合を占める。

1.2 グレゴリオ暦はなぜこの形になったのか

このルールが恣意的に決められたわけではない。季節が一巡する実際の長さは365日より少し長い。4年に一日を足すユリウス暦はその少しを一日の四分の一と見積もったが、実際より少し多めの値だった。その微細な超過が数百年積もって春分がカレンダー上で前倒しになり、復活祭の基準が揺らいだ。

1582年の改暦は二つのことをした。積もった誤差を取り除くためにカレンダーから十日を切り取り、再び積もらないように100と400のルールを入れた。その結果、400年のあいだのうるう年は100回ではなく97回になり、400年の総日数は146,097日になる。

ここで優雅なことが起きる。146,097を7で割ると20,871で正確に割り切れる。つまりグレゴリオ暦の曜日の配置は400年ごとに完全に繰り返す。2026年の曜日配置は2426年と同じであり、1626年とも同じだ。この性質はこの後に出てくるすべての公式が寄りかかっている土台である。

2. もっとも単純な方法 — 基準日から数える

公式を作る前に、人が最初に思いつく方法がある。基準になる日をひとつ決め、そこから何日過ぎたかを数えたうえで7で割った余りを見るのだ。

基準日は慣例的に1970年1月1日であり、その日は木曜日である。基準日からの日数をrdとすると曜日は(rd + 4) % 7になる。0を日曜日に置いたとき木曜日が4なので4を足す。

2026年8月28日までの日数を実際に数えてみよう。1970年から2025年までで56年であり、そのあいだのうるう年は1972年から2024年まで14回である。2000年は400のルールに掛かってうるう年なので抜けない。したがって2026年1月1日までは56×365+14、すなわち20,454日だ。8月28日はその年の240番目の日なので239を足してrd = 20,693になる。ここに4を足すと20,697であり、7で割った余りは5だ。0が日曜日なので5は金曜日である。合っている。

この方法の問題は三つある。

  • 日数を求める作業がすでに公式を要求する — 上の段落で手でやったことをコードに移すには、うるう年の三条件と月ごとの累積日数がそのまま必要になる。割り算が消えたのではなく前の段階に移っただけだ
  • ループで数えると入力に比例して遅くなる — 年ごとにうるう年を判定しながら足していく実装は1970年から遠ざかるほど時間がかかる。西暦3000年の曜日が2026年より遅く出るプログラムになる
  • 基準日より前が崩れる — C系言語の%は余りの符号を被除数に合わせる

三つめが特に静かで危険だ。1900年3月1日は木曜日だが、この日のrdは−25,508である。(rd + 4) % 7は−25,504を7で割った余りになり、Cではその値が−3だ。曜日名の配列の添字に使えば配列の外を読む。正しい答えである4を得るには((rd % 7) + 7 + 4) % 7のようにもう一度折りたたむ必要がある。−25,508は7で正確に割り切れて余りが0であり、(0 + 7 + 4) % 7 = 4になって木曜日が出る。割り算を二回使ったことになる。

3. 公式に置き換える — Zellerの合同式とSakamotoの方法

ループをなくすには年・月・日からまっすぐ曜日へ向かう閉じた式が必要だ。そうした式が二つあり、二つは互いに違うやり方で同じ不規則を吸収する。

3.1 Zellerの合同式 — 月の長さを直線に伸ばす

グレゴリオ暦用のZellerの合同式はこういう形をしている。qは日、mは月、Kは年の下二桁、Jは上二桁である。

h = (q + ⌊13(m+1)/5⌋ + K + ⌊K/4⌋ + ⌊J/4⌋ + 5J) mod 7
    (m: 3=3月 … 12=12月, 13=1月, 14=2月。1月・2月は年を1減らす)
    (h: 0=土, 1=日, 2=月, 3=火, 4=水, 5=木, 6=金)

この式でもっとも奇妙に見えるのは3月を最初の月に置くことと13(m+1)/5だ。二つは一体である。

3月を始まりに置くと長さの変わる2月が一年の最後尾へ行く。うるう日が後ろのどの月もずらさなくなるので、3月から続く月の長さを7で割った余りが3、2、3、2、3、3、2、3、2、3、3という固定パターンになる。そして⌊13(m+1)/5⌋はmが3から14へ動くとき10、13、15、18、20、23、26、28、31、33、36、39を返す。この数列の差分がまさに同じパターンである。月の長さが作る階段を割り算一回で描き出したものであり、残るKとJの項はうるう年の三段ルールを移したものだ。

実際の日付で検算してみよう。

  • 2026-08-28 — q=28, m=8, K=26, J=20。⌊13×9/5⌋=23、⌊26/4⌋=6、⌊20/4⌋=5、5×20=100。和は28+23+26+6+5+100=188であり188 mod 7 = 6。h=6は金曜日。合っている
  • 2000-02-29 — 2月なのでm=14、年は1999に下げる。q=29, K=99, J=19。⌊13×15/5⌋=39、⌊99/4⌋=24、⌊19/4⌋=4、5×19=95。和は29+39+99+24+4+95=290であり290 mod 7 = 3。h=3は火曜日。2000年2月29日は火曜日で合っている
  • 2026-01-01 — 1月なのでm=13、年は2025。q=1, K=25, J=20。⌊13×14/5⌋=36、⌊25/4⌋=6、⌊20/4⌋=5、5×20=100。和は1+36+25+6+5+100=173であり173 mod 7 = 5。h=5は木曜日。合っている

3.2 Sakamotoの方法 — 十二個の枠に置き換えた同じ発想

Zellerが月の階段を割り算で描いたなら、Sakamotoの方法はその階段をそのまま十二個の枠の表に書いておく。

t = [0, 3, 2, 5, 0, 3, 5, 1, 4, 6, 2, 4]
if m < 3: y = y − 1
w = (y + ⌊y/4⌋ − ⌊y/100⌋ + ⌊y/400⌋ + t[m−1] + d) mod 7
   (w: 0=日, 1=月, … 6=土)

同じ日付で確かめてみよう。2026年8月28日ならmが3以上なのでyはそのまま2026であり、t[7]は1だ。⌊2026/4⌋=506、⌊2026/100⌋=20、⌊2026/400⌋=5。和は2026+506−20+5+1+28 = 2,546であり2,546 mod 7 = 5。w=5は金曜日である。2000年2月29日ならyを1999に下げてt[1]=3を使う。1999+499−19+4+3+29 = 2,515であり2,515 mod 7 = 2、すなわち火曜日だ。1900年3月1日は1900+475−19+4+2+1 = 2,363であり余りは4、木曜日である。三つの日付すべてがZellerとも基準日から数える方法とも一致する。

表の十二個の数字がどこから来たのかがこの方法の核心だ。3月以降の値は、その月より前までに積もった日数を7で割った余りから正確に1を引いた値である。8月より前に積もった日数は212日であり212 mod 7 = 2なのに表の値は1だ。10月より前は273日で余りが0なのに表は6、すなわち−1である。この−1がする仕事はひとつだ。mが3以上のときはyを下げないので⌊y/4⌋の項がまだ来てもいないその年の2月29日を先に数えてしまうのだが、表の−1がその一枠を戻す。1月と2月はyを下げるのでその問題がなく、t[0]=0とt[1]=3が累積日数とそのまま一致する。

二つの方法と基準日から数える方法を並べて置くと違いがはっきりする。

軸基準日から数えるZellerの合同式Sakamotoの方法
月の不規則を処理する場所日数を作る前の段階⌊13(m+1)/5⌋という一項十二個の定数表
必要な割り算前段階のうるう年判定 + 最後のmod 7切り捨て除算3回 + mod 7切り捨て除算3回 + mod 7
戻り値の0が指す曜日基準日の補正によって異なる土曜日日曜日
1月・2月の処理該当なし13月・14月へ移す年を1下げる
日数の値が必要か必須不要不要
負の年余りの符号の問題中間項が負になりうる切り捨て除算の前提が崩れる

ここから判断基準が出てくる。すでに日数を持っているならZellerやSakamotoは損だ。二つの公式は年・月・日から始める代わりに割り算を三、四回払う。逆に年・月・日しかないなら、日数を作ってから余りを求めるより二つの公式のほうが短い。どちらが有利かはアルゴリズムではなく、自分のコードが日付を何として持っているかが決める。

4. 十二個の表が割り算の代わりになる理由

Sakamotoの表は小さく見えるが発想がある。月の長さは計算で導ける値ではない。30日と31日の並びに算術的な根拠がないからだ。計算で作れないものを計算で作ろうとすると⌊13(m+1)/5⌋のような迂回路が必要になり、その迂回路がすなわち割り算である。

表はその割り算をメモリ読み出し一回に変える。十二個の小さな整数はバイト配列なら12バイト、32ビット整数でも48バイトだ。キャッシュ一行はふつう64バイトなので表全体がキャッシュ一行に収まる。

  • 表がキャッシュに常駐すれば参照は割り算より圧倒的に安い
  • 表が大きくなってキャッシュから追い出されると参照一回がメインメモリへのアクセスになり、その費用は割り算数回を超える
  • 表は添字が有効範囲の中になければならない — 計算が間違ったとき誤答ではなくメモリエラーになる
  • 表の値は検算できなければならない — どこから出た数字か説明できない定数表は修正も移植もできない

4.1 分岐とルックアップテーブル — 表がいつも勝つわけではない

表を使う理由はもうひとつある。分岐をなくすことだ。月ごとにifを並べたりswitchを使ったりすると、CPUは毎回どちらへ行くかを予測しなければならない。予測が当たれば費用はほとんどないが、外れると先に実行していた命令を捨ててパイプラインを埋め直す。その罰金は掛け算数回をゆうに超える。

だから入力が無作為に近いほどルックアップテーブルが有利だ。無作為な日付の月は予測できず、予測できない分岐は外れ続ける。逆に同じ月の日付ばかりが続けて入ってくるコードなら予測がほぼ当たるので分岐のほうが速いことがある。

見落としやすいこともある。表が大きいと形勢がひっくり返る。400年分の曜日を全部表にすれば割り算は消えるが、表は14万6千項目になる。キャッシュに入らない表は参照のたびにメモリ待ちであり、その待ち時間のあいだCPUは何もできない。最適化と呼んだものが正確に逆の結果を出す場所だ。

5. 割り算が高くつく理由

ここまでのすべての方法が最後にmod 7を残す。その前にはうるう年ルールから来た割り算が三つ四つある。これらを減らそうとする試みが続けて出てくる理由は、整数除算が日常的な算術演算のなかでもっとも高い部類だからである。

理由は回路の性格にある。掛け算は部分積を一度に作って木の形に足し下ろしていける。各段階が互いを待たないので深くパイプライン化され、乗算器は毎サイクル新しい掛け算を受け取りながら結果を数サイクル後に順に出していく。割り算は逆だ。商の桁を上から一つずつ確定していく逐次的な過程なので、前の段階の結果が出なければ次の段階を始められない。

  • レイテンシが長い — 結果が出るまで掛け算より何倍も時間がかかる
  • スループットも悪い — 多くの実装で除算器は完全にはパイプライン化されておらず、続けて割り算を投げると前のものが終わるまで待つ
  • オペランドによって時間が変わる — 一部の実装は値によってサイクル数が変わるため、割り算が混ざったコードは実行時間が入力に依存する
  • 数値はマイクロアーキテクチャごとに違う — レイテンシとスループットはCPU世代ごとに大きく変わるので、ひとつの数字では言えない。特定のチップの値が必要ならそのチップの命令表を見るしかない

5.1 コンパイラが定数除算に対して行うこと

幸い曜日計算の割り算はすべて割る数が定数だ。7、4、100、400はコンパイル時点ですでに分かっている。この場合コンパイラは除算命令を出さず、逆数を掛けたあとシフトする形に置き換える。

原理は簡単だ。xを7で割りたければ1/7に近い値を掛ければよいのだが、整数の世界に小数はないので2のべき乗を掛けておいて後からシフトで戻す。232を7で割った値を切り上げると613,566,757であり、16進数で0x24924925だ。xにこの数を掛けたあと上位32ビットだけを取ればおおむね⌊x/7⌋が出る。

小さな例で確かめてみよう。216=65,536を7で割って切り上げると9,363である。x=100なら100×9,363=936,300であり65,536で割った商は14、⌊100/7⌋=14なので合っている。x=21なら21×9,363=196,623であり商は3、⌊21/7⌋=3でこちらも合っている。掛け算一回とシフト一回が割り算の代わりを務めた。ただしこの変換はただではない。有効範囲があり、その範囲を超えると静かに間違う。

6. 7はメルセンヌ数である — きっかけの記事がつかんだ点

ここまでが背景だ。きっかけになった記事が触れたのは最後に残ったmod 7である。

6.1 7日週を8日週に移す

7は23−1だ。この形の数をメルセンヌ数と呼び、ここから性質がひとつ出てくる。xを7で割った余りはxに⌊x/7⌋を足した値を8で割った余りと同じである。

x mod 7  =  (x + ⌊x/7⌋) mod 8

証明は一行だ。xを7q+rと書くとx+q = 8q+rになり、8で割ると8qは消えてrだけが残る。rは7より小さいので8で割った余りの位置にそのまま入る。

実際に入れてみよう。先ほど求めた20,697で確かめると⌊20697/7⌋=2,956であり20,697+2,956=23,653だ。23,653を8で割った余りは5である。20,697 mod 7もやはり5だ。小さい数でも同じである。x=13なら⌊13/7⌋=1、13+1=14、14 mod 8 = 6であり13 mod 7 = 6だ。

これがなぜ得なのか。8で割った余りは割り算ではないからだ。下位3ビットを残すマスク一回で済む。そして残る⌊x/7⌋は前節で見たとおり掛け算とシフトに置き換えられる。割り算ひとつが掛け算・シフト・足し算・マスクという短い鎖に変わる。きっかけになった記事はこの変換をMul-Add-Shiftと呼び、7日周期を8日の空間へ移す写像にNundinal Mapという名前を付けた。

6.2 マジックナンバーの有効範囲 — どこから間違い始めるのか

先送りにした問題がここで戻ってくる。切り上げで作った逆数は実際の1/7よりごくわずかに大きい。その微細な超過がxに掛けられて大きくなり、ある地点から商を1だけ膨らませる。

16ビットの例で直接確かめられる。定数9,363はxが13,109までは正確だ。13,109×9,363=122,739,567であり65,536で割った商は1,872、実際の⌊13109/7⌋も1,872である。ところが13,110で初めて崩れる。13,110×9,363=122,748,930であり商は1,873だが、7×1,873=13,111なので実際の商は1,872だ。答えが1大きい。例外もエラーも出ない。ただ間違った曜日が出る。

32ビットでも構造は同じで境界だけが遠くにある。きっかけになった記事は自分が使う切り上げ定数が32ビット入力のおよそ80%でしか正確でないと書き、入力を有効区間の中へ押し込むRange Compressionを付けている。負の側の入力に固定オフセットを足して分布を有効区間へ移す方式だ。技法の半分が速度ではなく正確性の確保に使われている。

  • マジックナンバーはアルゴリズムではなく範囲の付いた契約だ — 範囲を書いておかなければ後で誰も直せない
  • 範囲を外れた失敗は静かだ — クラッシュではなく一日ずれた曜日として現れる
  • 符号付きの入力は特に危険だ — 負の区間で切り捨てと切り下げの差がそのまま誤答になる
  • ビット幅を変えて移植すれば定数も範囲も計算し直さなければならない — 32ビットで正しい定数が64ビットで最適とはかぎらない

7. ところでこれが実際にボトルネックになる場合はあるのか

正直に答えると、ほとんどのプログラムでは違う。

画面に日付をひとつ出すコードで曜日計算は全体の時間の目立たない断片だ。その前後には文字列の解析があり、タイムゾーン規則の参照があり、ロケールに合わせて曜日名を選ぶ仕事がある。ウェブ要求ひとつが数ミリ秒なら、曜日計算を百回節約したところで応答時間の小数点以下の何桁も動かせない。

意味が生まれる場所は条件がはっきりしている。同じ計算が非常に多く繰り返され、周辺の費用がすでに取り払われた場所だ。

  • 大量ログの解析 — 数億行のタイムスタンプから日付フィールドを抜き出して曜日や日単位のバケットに分類するパイプライン。一行あたりのナノ秒の差が全体の処理時間の実際の比率になる
  • 時系列インデックスとパーティショニング — 保存のたびに日付をパーティションキーに変える経路。書き込み経路の熱いループに入る
  • カレンダー規則の大量再計算 — 繰り返し予定を数千回展開したり、営業日基準の満期を大量に計算し直したりするバッチ
  • 日付ライブラリ自体の実装 — 自分が遅ければその上に載るすべてのコードが一緒に遅くなる場所だ
  • 小さくて遅いハードウェア — 除算器が弱いか無い環境では割り算一回の相対的な比重がデスクトップとまったく違う

共通点が見える。すべてが曜日計算のほかにやることがあまりないループだ。そんなループが自分のコードにないなら、この技法は知っておくものであって適用するものではない。

8. 正確さは性能より先だ

標準ライブラリを差し置いて自分で実装すると決めたなら、得るものと失うものを同じ天秤に載せなければならない。得るものは割り算いくつかだ。失いうるものは一覧が長い。

  • 範囲外の入力 — 13月、2月30日、0日のような値が入ってくると公式はエラーを出さずにもっともらしい曜日を返す。検証は呼ぶ側の仕事になる
  • 負の年と紀元前 — 公式の⌊⌋は数学的な切り下げだが、言語の整数除算はたいてい0方向への切り捨てだ。年が負になった瞬間に二つは分かれる
  • ユリウス暦への切り替え — グレゴリオ暦の公式を1582年より前へ押し込むと実際の歴史記録の日付と食い違う。切り替えの時点が国ごとに違うので、どの暦で書かれた日付かがデータの性質になる
  • オーバーフロー — 中間項の和が整数の範囲を超えると結果が無意味になる。符号付き整数のオーバーフローは言語によっては未定義動作だ
  • 曜日番号の規約の不一致 — Zellerは0が土曜日でSakamotoは0が日曜日であり、ISO 8601は1が月曜日だ。互いに違う規約の値を混ぜれば何日かずつ食い違う

順序はこうだ。まず正しく作り、正しいと証明できるように作り、そのあとで速く作る。曜日計算にはこの順序を守りやすい性質がある。400年ごとに繰り返すので146,097日全体を全数検査できる。十数万件は試験としてまったく大きくない。既存の実装と新しい実装を400年の区間全体で一枠ずつ突き合わせれば、最適化が正確性を壊したかどうかを推測ではなく事実として知ることができる。

9. 測らなければ分からない

きっかけになった記事はベンチマークを付けている。その数値の読み方がこの記事の最後の主題だ。まず条件を明かしておく。以下は原文の著者が自分の環境で測った相対時間であり、Neriが2024年に発表した方法を1.00倍に置いた値である。数字が小さいほど速い。

測定方法も原文が明かしている。無作為な日付を大量にメモリへ載せて回し、レイテンシ測定モードでは結果をビットXORで次の計算に食わせて並列実行を防ぐ。各試験は5回繰り返して中央値を使い、ループ自体の基準線を引く。入力範囲は符号付き32ビット全体だ。

これらの条件を抜いて「四倍速い」だけを持ち運べばその一文は間違ったものになる。同じ表のなかで同じ方法が0.25倍と0.55倍のあいだを行き来する。CPUが違いコンパイラが違えば結果が変わるという意味であり、これは特定の実装の欠陥ではなくこの種の測定がもともとそういうものだという意味だ。

マイクロベンチマークが人をだます場所はおおむね決まっている。

  • 入力の分布 — 無作為な日付と整列された日付では分岐予測の結果がまったく違う。実際のデータが整列されているのに無作為で測っているなら、その数値は自分のものではない
  • デッドコード除去 — 結果をどこにも使わなければコンパイラが計算そのものを消す。0に近い時間が出たなら最適化ではなく削除を測ったのだ
  • インライン化 — マイクロベンチマークでインライン化された関数が実際のコードでは呼び出し境界を越えられないことがある。逆もある
  • レイテンシとスループットの混同 — 次の計算が前の結果を待つコードと、独立して注ぎ込むコードでは性能の特性が違う。原文が二つのモードを分けて測った理由がこれだ
  • ウォームアップと周波数 — 初回の実行にはキャッシュの充填が混ざり、持続的な負荷ではクロックが下がる。繰り返しと中央値が必要な理由である
  • 周辺が取り払われた環境 — 配列から整数を取り出して曜日だけを求めるループと、文字列を解析してオブジェクトを作る実際のコードではボトルネックの位置が違う

だから結論は単純だ。他人のベンチマークはその技法が存在するという証拠であって、自分のコードが速くなるという証拠ではない。この計算が本当に自分のボトルネックなら、その事実はプロファイラが先に教えてくれる。プロファイラが何も言わなかったなら変える理由もない。

確認できなかったこと

  • 原文のベンチマーク表はスループットとレイテンシを別々に載せている。上の表の数値がどちらの値なのかは特定できなかった
  • 原文の表には上に移したもの以外のプラットフォームの行やナノ秒単位の絶対値もあるが、一貫して読み取れる行だけを載せた
  • Neriが2024年に発表した方法の原論文は確認できなかった。この記事でNeriの方法は、きっかけになった記事が比較の基準に据えた対象だという事実だけを扱う
  • 主要なコンパイラが定数除算に対して実際にどんな命令列を出すのかはバージョンと対象アーキテクチャごとに違い、特定の組み合わせの出力は確認できなかった
  • 現在広く使われているCPUの整数除算のレイテンシ・スループットの実測値はこの記事に載せていない

まとめ

曜日計算が難しい理由はアルゴリズムではなくカレンダーにある。完璧に規則的な7日周期を、365と366が4・100・400のルールで混ざった体系の上に載せなければならない。その食い違いがコードのなかで割り算として現れる。

公式はその割り算を減らす互いに違う方法だ。Zellerは月の長さの階段を⌊13(m+1)/5⌋ひとつで描き、Sakamotoは同じ階段を十二個の表に書いておいて表の値から1を引く方式でうるう日の一枠を戻した。きっかけになった記事はそれより後ろで、最後に残ったmod 7を7がメルセンヌ数だという性質で8のマスクに変えた。三つの段階すべてが同じことをしている。あらかじめ分かることをあらかじめ計算しておき、実行時点では残ったものだけをやる。

そして最後に残るのは判断だ。この計算が自分のボトルネックでないなら標準ライブラリが正解である。ボトルネックなら、変える前に400年分を全数突き合わせて正確性を固定し、定数の有効範囲をコメントではなく試験として残し、自分の入力分布で直接測らなければならない。順序を変えれば得るものは数サイクルで失うものは一日ずれた日付だ。その取引はたいてい割に合わない。
