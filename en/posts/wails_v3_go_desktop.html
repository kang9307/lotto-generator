Building Desktop Apps with Web Tech

Where system webview and bundled runtime part ways, and what that choice bills you

Aug 16, 2026 Dev & Infra

Intro: comparing framework names gets you nowhere

Picture the situation. An internal tool has to come down from the browser and become a desktop application. You have web people and no native people. At this point most teams write the candidate frameworks into a table and start assigning stars. That table never produces a decision, because the axis is wrong.

Building a desktop app with web technology means choosing four things. Whether the rendering engine ships with the app, which language holds the backend logic, how the artifact is signed and updated, and how deeply it hooks into the OS. The first of those sets the difficulty of the other three at once. Once you decide whether to carry an engine, you have decided the order of magnitude of your payload, when you will meet rendering regressions, and who carries engine security patches to users.

This article stands that first axis upright and arranges the rest around it. Wails v3, which entered beta in August 2026, serves as the worked example, but this is not a pitch for any framework. The point is the trade that survives whichever tool you pick.

1. What the webview approach solves and what it leaves untouched

What the webview approach genuinely solves is a staffing and asset problem. You do not write the UI three times, and the components and design system already sitting in your web codebase come over intact. The iteration loop is short too. Save-and-see is not a common experience in native toolkits.

Here is what remains.

  • Bundle size — if the engine is embedded, one app carries an entire browser. For internal distribution the recurring transfer on every update usually bites before the first download does.
  • Memory — browser engines are multi-process by design. Putting a structure that spawns separate renderer and GPU processes behind a single-window app is heavier than people expect.
  • Startup time — engine initialization and frontend asset parsing happen in sequence. On the web your metric was time to first render. On the desktop, the gap between clicking the icon and seeing a window is read directly as build quality.
  • Native integration — menu bars, tray icons, file associations, system notifications, drag-and-drop from outside the window and the accessibility tree all sit outside web standards, and how far the framework wraps them is where real differences show up. Window state restoration, multi-monitor scaling and launch-at-login registration do not disappear because you chose a webview either; they get attached per platform.

The numbers behind these items shift by orders of magnitude with app composition and build options, which is why no single MB or millisecond figure per framework means much. But there is exactly one decision that moves the order of magnitude.

2. The fork — carry the runtime or borrow the system one

There are two strategies.

2.1 Bundling the runtime

The browser engine and runtime ship inside the app. The Electron family sits here. The benefit is unambiguous: the engine build the developer tested is the engine build that runs on the user machine. A CSS line rendering differently on one particular device does not happen structurally. You also stop reading browser support tables.

The bill is equally unambiguous. Every app carries its own engine. And the duty of shipping engine security patches through your own releases stays with your team. When a Chromium vulnerability goes public, you cut a version containing the fix and get users to take it. No framework carries that for you.

2.2 Using the system webview

You call the engine the OS already provides. Wails and Tauri sit on this side. The Wails repository states the position in one line: it uses native rendering engines, with no embedded browser. The engine leaves your artifact, and engine patching rides the OS or runtime update path.

The bill here is variance. Engine versions differ per device and so does the set of supported web features. That means fixing a support floor before reaching for a recent CSS feature.

2.3 There is middle ground

The important part is that this trade does not live only between frameworks. It lives inside a single platform too. WebView2 on Windows offers two distribution modes: an Evergreen mode that updates itself, and a Fixed Version mode that ships a specific engine build with the app. Microsoft distribution docs state that Fixed Version binaries are over 250 MB and grow the app package by that amount. In Evergreen mode, the bootstrapper that fetches the runtime on demand is about 2 MB.

So, plainly: rendering consistency and payload size are opposite ends of one dial. Whichever framework you choose, the dial remains, and only the product can say where it belongs.

4. Windows — WebView2 and its two distribution modes

The system webview on Windows is WebView2, running the same Chromium-family engine as Edge. Here is what matters in practice.

  • The Evergreen runtime is included as part of Windows 11. Most Windows 10 devices already have it, but not all, which is why checking for its presence at install or launch is recommended; you either read the runtime version value from the registry or check whether the API that returns the available browser version string comes back empty.
  • When it is missing you either fetch the roughly 2 MB bootstrapper and install silently, or for offline environments ship the full standalone installer inside your artifact.
  • Every Evergreen app on a device shares one copy. On eligible systems the docs describe it as hard-linked with the Edge binaries, which saves disk footprint and memory.
  • There is one operational trap. When the runtime updates, a running app keeps using the previous version. Moving to the new one requires restarting the app or releasing the existing environment references. For a long-running app that renders third-party content this becomes a security matter, which is why handling the new-browser-version event and prompting a restart exists.
  • Fixed Version mode carries extra constraints. It cannot run from a network path as a documented known issue, and on Windows 10 from a certain runtime version onward, unpackaged desktop apps must run an additional permission-granting command.
  • A production app may not use the Edge stable browser channel as its backing platform. That is a deliberate design so the app does not depend on whether the browser is installed.

Set the criterion this way. An organization shipping to every internal PC that cannot absorb a rendering regression, especially one deploying into a disconnected network, has a real case for Fixed Version. Everyone else is better served by Evergreen plus a presence check at install time, on both payload and patch burden.

5. macOS and Linux — same idea, different temperament

macOS is the simpler side. The system webview is WKWebView and it moves with OS updates. The OS floor you support becomes the engine floor, so deciding your support range is the same act as deciding your web feature range. Building requires the Xcode command line tools.

Linux is where the variance lives. GTK generations and WebKitGTK versions differ per distribution, and even one distribution renames development packages between releases. The Wails v2 install docs require GTK3 and WebKit2GTK, and tell you that on recent Ubuntu, where the 4.0 development package is absent, you install 4.1 and add a build tag. The fact that this instruction is spelled out in the docs at all tells you the shape of the situation.

That v3 raised the Linux stack to GTK4 and WebKitGTK 6.0 shows the direction. The older GTK3 path stays behind a build tag, but explicitly only until v3.1. And the way the v3 supported platform list names Ubuntu 24.04 and adds that other Linux may work too is an accurate reflection of reality.

So if Linux is a first-class target, order the work like this. Pin which distributions and which releases you will support. That decision fixes the GTK generation and the build tags, and those in turn fix your CI images and package formats. Reverse that order and you will be re-picking the whole stack the week before release.

6. The position Wails takes, and what changed in v3

The Wails position fits in two sentences. Keep the backend in Go, and draw the UI on the native rendering engine of the OS. It is aimed at people who want a web frontend on a Go program without standing up a server and opening a browser. In the taxonomy above it sits on the system webview side.

6.1 Version status, as checked on 16 August 2026

  • The repository lists two active versions explicitly: v2 is Stable, v3 is Beta. The install commands differ too, wails against wails3.
  • In the release list, v2.14.0 is a full release dated 10 August 2026.
  • The latest in the v3 line is v3.0.0-beta.8, a prerelease dated 12 August 2026. The first beta tag, v3.0.0-beta.0, is dated 2 August, and everything immediately before it was in the alpha line. That is nine beta tags in ten days. Fixes land fast, and an unpinned dependency can make your builds move under you.
  • Beta is beta. For production purposes the stable channel is still v2.

6.2 What changed in v3

Placing the announced changes next to what the repository corroborates gives this list.

  • Explicit object lifecycle — the implicit, context-centered arrangement gives way to explicit Application, Window and Service objects.
  • Multi-window as a standard feature — apps that open several windows, like editors or inspector tools, no longer need workarounds.
  • Go service pattern — services take the place of the older bindings, making the boundary between backend capability and frontend API explicit.
  • Type definitions generated by static analysis — frontend type definitions come out preserving parameter names and comments.
  • The build process is public — it is exposed as Taskfile format rather than hidden inside the framework. The file is in the repository, and the install docs tell you to edit the project Taskfiles if you want a different package manager.
  • Server build option — a shape that separates the desktop UI from the backend logic exists as a guide.
  • Experimental mobile — the v3 directory in the repository contains iOS and Android documents, marked experimental.
  • Higher toolchain floor and a setup wizard — v3 requires Go 1.24 or later, against 1.21 or later for v2. npm dropped to optional in v3, though most bundled templates still need it. wails3 setup handles platform dependency checks, project defaults and signing configuration in one pass, with a documented caveat that it is new and primarily tested on Linux.

For migration purposes the first three items are the ones that matter. This is not a rename of APIs; the model for composing an app is different. If you have a product in flight, trying v3 on a new project until the stable release is the cheaper thing to back out of.

7. The boundary in code — conceptual example

What follows is a compressed illustration of the structure and has not been run or verified. Real API signatures and registration mechanics follow the docs for the version you are on.

In the webview approach the boundary between backend and frontend narrows to a handful of function signatures. Suppose the Go side holds a type like this.

// Conceptual example, not verified
type Vault struct {
    root string
}

// Only this method is exposed to the frontend.
func (v *Vault) List(prefix string) ([]string, error) {
    // Filesystem access exists only on the Go side.
    // prefix is normalized and validated instead of being pasted into a path.
    if strings.ContainsAny(prefix, "/\\.") {
        return nil, errors.New("invalid prefix")
    }
    return filepath.Glob(filepath.Join(v.root, prefix+"*"))
}

The frontend sees only that method, through the generated type definitions.

// Conceptual example, not verified
const files = await Vault.List('report-');
render(files);

Two reasons this picture matters.

  • Code running inside the webview is outside your trust boundary. Whatever script the renderer has loaded can only call exposed methods, and that list is your attack surface. Open one convenient general-purpose method that takes a raw file path and you have handed out arbitrary path access. Validation belongs on the Go side, always.
  • Narrowing the boundary produces documentation. When type definitions come from static analysis, the frontend sees function names, parameter names and comments. The hand-maintained interface document disappears.

The structure also enforces a discipline. State changes flow out as events and commands go in as methods; that shape ends up being the standard.

8. Distribution, signing, auto-update — where the schedule actually goes

When the UI work ends, the real schedule begins. Underestimate this stretch and the ship date slips.

8.1 Signing and notarization

The cross-signing relationships laid out in the Wails v3 signing guide translate directly into practical decisions.

  • Windows executables and installer packages can be signed from any host, Windows, macOS or Linux.
  • Linux DEB and RPM packages can likewise be signed with a PGP key from any host.
  • Only macOS app bundle signing and notarization require macOS, because of the Apple tooling chain.
  • The signing backend uses each OS standard tool on its native platform and a built-in implementation when cross-compiling. The v3 setup wizard writes signing configuration to a user config file and puts passwords in the OS credential store, meaning they never sit in plaintext inside build scripts.

The third item hits the budget immediately. The moment macOS is a target, CI needs a Mac runner. And certificate issuance and renewal, notarization waits, and injecting signing keys into CI safely are procedures rather than code, and procedures do not compress under schedule pressure.

8.2 Auto-update

On the web, deploying is a page refresh. On the desktop it is not. You download, verify, replace a running binary and prompt a restart. If you build it yourself, four things cannot be missing.

  • Signature verification — confirm with a public key that what arrived is what you published. Transport encryption alone is not enough.
  • Atomic replacement — a partial download or an interruption must not corrupt the executable. Download to a temporary location, verify, then swap.
  • A rollback path — if the new version fails to launch and there is no way back, remote support becomes a phone call.
  • Forced update policy — security fixes need a tier that cannot be postponed.

Wails v3 lifted this into the framework. The updater attaches to the application object and takes pluggable release providers. The guide enumerates GitHub Releases, a commercial distribution service, a Sparkle-family appcast, an open manifest protocol, and your own implementation. Downloads are authenticated against a configured public key, the binary is swapped safely, and state transitions flow through the framework event bus. The states are defined as values like unconfigured, idle, checking, up-to-date and available, and a default update window is provided and can be replaced.

Now lay section 4 over this again. Using the system webview means engine patches arrive on a path separate from your app updates, which is a benefit. But if users keep the app open for days, that app keeps running the old engine. Independently of app auto-update, something has to prompt a restart for the patch to actually take effect.

The table is not read top to bottom. Find the one thing your product cannot concede, pin that row first, and fit the costs of the remaining rows into what you can absorb. If two rows are both non-negotiable, one of them is usually not a real requirement.

Conclusion: three things to settle before you start

Three questions come before any framework comparison table.

  1. How much rendering consistency are you buying? You pay in payload size and engine patch duty. Settle this and the candidate list halves.
  2. Where does the support floor sit? How far back on Windows 10, which macOS versions, which Linux distributions. The Linux answer is the expensive one.
  3. Who builds the signing and update pipeline, and when? If macOS is a target you need a Mac runner, and auto-update needs public-key verification, atomic replacement, rollback and a forced-update tier at minimum.

Wails is the option that stands on the system webview side of this layout with the backend in Go. v3 is a large change that reworks how an app is composed, and as checked on 16 August 2026 it is beta. The stable channel is v2. Experiment on a new project and ship on the stable channel; that is the safe arrangement at this moment.

One last thing. The webview approach creates an illusion. The UI appears quickly, so the app looks nearly finished. What remains is the installer, signing, notarization, updates, crash collection, launch-at-login and multi-monitor handling. Put that list in the schedule at the start and it will not push the date later.
