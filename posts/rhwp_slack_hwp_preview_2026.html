1. 협업툴 안에서 마주치는 HWP라는 오래된 마찰 지점

한국의 업무 환경에서 협업용 메신저로 슬랙(Slack)을 도입한 팀이라도 문서 유통의 현실 앞에서는 종종 멈춰 서게 된다. 대외 공문서, 지원사업 신청 양식, 제휴사에서 전달해 온 계약 초안, 혹은 외부 협력업체가 전달한 보고서의 확장자가 .hwp나 .hwpx로 끝나는 순간, 매끄럽게 이어지던 메신저 중심의 대화 흐름은 즉시 끊어진다. 글로벌 협업 도구들은 PDF, 이미지, 일반 텍스트나 표준 오피스 포맷에 대해서는 인라인 미리보기와 검색 인덱싱을 지원하지만, 독자적인 복합 문서 구조를 가진 한국형 워드프로세서 포맷은 해석하지 못하기 때문이다.

문서 포맷의 기술적 구조나 역사적 배경에 대한 논의는 이미 많은 지면에서 다루어졌다. 바이너리 기반의 HWP 5.0과 XML 패키지 기반의 HWPX 표준에 얽힌 세부적인 조판 규칙과 공공 도입 현황은 오픈소스 HWP 에디터 분석과 AI 시대의 K-공문서 문제에서 구조적으로 짚은 바 있다. 그러나 제도적 표준화나 거시적 정책 담론과는 별개로, 지금 당장 슬랙 채널에 올라온 첨부파일 하나를 확인해야 하는 실무자에게는 매일 반복되는 미세한 마찰을 줄여 줄 구체적인 도구가 필요하다.

개발자 Taegyu Lee가 공개한 rhwp for Slack은 바로 이 마찰 지점을 정조준한 경량 연동 도구다. 슬랙 안에서 HWP 문서를 내려받지 않고도 스레드에서 즉시 시각적으로 확인하고, 필요하다면 웹 브라우저를 통해 간단한 교정 작업까지 마친 뒤 다시 슬랙 대화로 복귀시키는 파이프라인을 구축했다. 거창한 오피스 스위트 전체를 웹으로 옮겨오겠다는 이상론 대신, 협업 메신저라는 맥락 안에서 실무자가 겪는 가장 번거로운 단계를 어떻게 소프트웨어적으로 메웠는지 그 구조적 설계를 들여다본다.

2. 슬랙 채널에서 HWP 파일이 유발해 온 일상의 피로

슬랙 채널에 HWP 파일이 공유되었을 때 사용자가 겪는 과정은 단순한 불편 이상의 시간적·인지적 비용을 요구한다. 파일 아이콘만 덩그러니 놓인 메시지를 본 팀원은 내용을 파악하기 위해 여러 단계의 수동 작업을 거쳐야만 했다.

이 마찰은 특히 다양한 운영체제가 혼재된 조직이나 모바일 근무 환경에서 극대화된다. 맥(macOS)이나 리눅스를 사용하는 개발팀, 태블릿이나 스마트폰으로 이동 중에 긴급하게 내용을 확인해야 하는 관리자는 뷰어를 구동하는 것조차 난관에 부딪히곤 했다.

  • 로컬 다운로드 강제 — 브라우저나 메신저 내에서 렌더링되지 않으므로 반드시 로컬 디스크의 다운로드 폴더에 파일을 저장해야 한다.
  • 전용 소프트웨어 의존 — 내려받은 파일을 열기 위해 별도의 데스크톱 뷰어나 오피스 프로그램을 찾아 실행해야 하며, 비인가 프로그램 설치가 제한된 환경에서는 열람 자체가 막힌다.
  • 문맥 단절과 재업로드 혼선 — 오프라인에서 오탈자나 단락 하나를 수정한 뒤, 이를 다시 슬랙에 올리는 과정에서 어느 스레드에 올려야 하는지 혼선이 생기거나 채널 전체에 중복 파일이 난립한다.
  • 운영체제 간 접근성 격차 — 윈도우 환경이 아닌 기기에서는 호환 뷰어의 부재나 렌더링 깨짐 현상으로 인해 결국 다른 동료에게 화면 캡처를 부탁하는 우회로를 밟게 된다.

3. rhwp for Slack의 핵심 동작과 변환 메커니즘

rhwp for Slack의 핵심 아이디어는 슬랙의 봇 이벤트 수신과 외부 서버의 변환 파이프라인, 그리고 브라우저 기반 편집기를 묶어 하나의 연속된 사용자 경험으로 엮어낸 데 있다. 사용자가 채널에 문서를 올렸을 때부터 수정본이 등록될 때까지의 전 과정은 슬랙의 기본 상호작용 단위인 스레드(Thread)를 중심으로 전개된다.

3.1 파일 업로드 감지와 스레드 내 PDF·이미지 생성

앱이 초대된 채널에 .hwp 또는 .hwpx 확장자를 가진 문서가 업로드되면, 슬랙의 이벤트 API를 통해 앱이 이를 감지한다. 채널 설정은 기본값인 자동 감지 모드 외에도, 불필요한 자동 처리를 방지하기 위해 @rhwp 멘션 시에만 반응하도록 조정할 수 있다. 변환 엔진은 전달받은 문서를 처리하여 전체 분량이 담긴 PDF 파일과 함께, 직관적인 확인을 위한 첫 3페이지 분량의 페이지 이미지를 생성해 원본 메시지의 스레드 댓글로 즉시 게시한다. 스레드 하단의 버튼을 통해 최대 10페이지까지 이미지를 추가로 열람할 수 있도록 설계되었다.

3.2 브라우저 기반 편집기 연결 흐름

미리보기 응답에 포함된 「rhwp에서 편집」 버튼을 누르면 외부 브라우저 창이 열리며 rhwp-studio 웹 편집 환경으로 전환된다. 사용자는 슬랙 계정의 OpenID 연동을 통해 별도의 회원가입 없이 로그인하며, 데스크톱에 한컴오피스나 전용 워드프로세서가 설치되어 있지 않아도 브라우저 상에서 텍스트 수정, 서식 변경, 오탈자 교정 등의 작업을 수행할 수 있다. 무거운 네이티브 앱을 기기에 설치하지 않고 웹 표준 환경에서 파싱과 편집을 처리하는 구조다.

4. 원본을 덮어쓰지 않는 스레드 추가 설계의 실무적 가치

이 도구의 기능 목록 중 실무 협업 관점에서 가장 주목해야 할 대목은 「편집본을 Slack에 저장」할 때 원본 파일을 절대로 덮어쓰지 않고 새 파일로 추가한다는 설계 원칙이다. 단순해 보이는 이 동작 방식은 협업 도구에서 발생하기 쉬운 치명적인 데이터 유실 사고를 원천적으로 방지한다.

일반적으로 파일 스토리지나 클라우드 드라이브 연동 도구에서 흔히 채택하는 인플레이스(in-place) 덮어쓰기 모델은 실무 협업에서 잦은 사고를 부른다. 여러 구성원이 동일한 문서 링크를 열고 각자 수정하거나, 미리보기 차원에서 열어본 사용자가 부주의하게 저장을 눌렀을 때 최초 작성자가 공들여 작성한 원본 내용이 소실될 위험이 상존한다. 버전 복구 기능이 제공되더라도 히스토리를 추적하고 롤백하는 과정 자체가 업무의 마찰 비용으로 작용한다.

rhwp for Slack은 편집기에서 저장을 실행하면 수정된 파일과 새롭게 렌더링된 PDF 및 페이지 이미지를 원본 메시지의 동일한 스레드에 새로운 첨부물로 게시한다. 이러한 설계는 다음과 같은 명확한 장점을 제공한다.

  • 원본 무결성 보장 — 최초 발송자가 보낸 원본 파일이 그대로 보존되므로 실수로 인한 내용 왜곡이나 삭제 위험이 구조적으로 차단된다.
  • 버전 변화의 시각적 대조 — 스레드 안에서 원본 미리보기 이미지와 수정본 미리보기 이미지가 상하로 나란히 배치되어, 동료들이 어떤 부분이 바뀌었는지 한눈에 비교할 수 있다.
  • 대화 맥락과의 결합 — 메신저 대화의 맥락 안에서 파일 버전이 누적되므로, 특정 수정본이 어떤 피드백과 요구사항에 의해 생성되었는지 타임라인이 온전히 남는다.
  • 롤백 비용의 최소화 — 수정본에 문제가 발생하더라도 스레드 상단에 남아 있는 원본 파일이나 이전 수정본을 언제든지 다시 열어 작업을 재개할 수 있다.

5. 기술적 경계선 — 지원 범위와 명확한 한계들

도구의 유용성을 정확히 판단하기 위해서는 그 도구가 무엇을 할 수 있는가만큼이나 무엇을 할 수 없는가를 냉정하게 파악해야 한다. rhwp for Slack은 개인 개발자가 구축한 경량 서비스인 만큼 명확한 기술적 제약과 처리 경계선을 사전에 공개하고 있다.

가장 먼저 확인해야 할 점은 파일 규격과 용량 제한이다. 현재 서비스는 파일당 최대 20MiB 용량, 최대 200페이지 분량의 문서까지만 처리를 보장한다. 일반적인 사내 공문이나 단문 보고서에는 넉넉한 기준이지만, 수백 장에 달하는 제안서나 고해상도 이미지가 다수 삽입된 책자형 문서는 처리가 실패하거나 거부될 수 있다. 또한 1990년대 레거시 포맷인 HWP 3.0 문서나 비밀번호 암호화가 적용된 보안 문서는 지원 대상에서 제외된다.

편집 경험 측면에서도 데스크톱 오피스와의 간극을 인지해야 한다. 브라우저 편집기에는 변경 사항을 실시간으로 보존하는 자동 저장 기능이 존재하지 않는다. 브라우저 탭을 닫거나 새로고침을 누르면 작업 중이던 텍스트가 사라지므로, 수정이 끝난 즉시 명시적으로 슬랙 저장 버튼을 눌러야 한다. 아울러 웹 기반 렌더링 엔진의 특성상 정밀한 조판 규칙, 다단 배치, 복잡한 표 내부 수식 등은 원본 프로그램과 시각적 차이가 발생할 수 있다.

6. 값을 하는 자리와 도입 전 점검해야 할 보안 경계

소프트웨어 도구의 도입 가치는 적합한 환경에서 사용할 때 극대화된다. rhwp for Slack이 확실하게 값을 하는 영역이 있는 반면, 기업의 보안 거버넌스 관점에서 신중하게 접근해야 하는 경계선도 뚜렷하다.

이 도구가 가장 큰 효율을 발휘하는 자리는 일상적인 대외 공문 확인, 정부 과제 공고문 열람, 사내 행사 안내문 확인처럼 공개된 정보이거나 빠른 내용 파악이 핵심인 일상 업무다. 첨부파일을 내려받아 오피스를 띄우는 2~3분의 지체 시간을 스레드 내 3초 확인으로 압축해 준다. 팀원들이 모바일이나 비-윈도우 환경에서도 즉시 내용을 인지하고 의견을 나눌 수 있다는 점만으로도 협업의 병목을 상당 부분 해소한다.

반면, 보안과 데이터 처리 관점에서는 주의 깊은 검토가 선행되어야 한다. 공식 서비스 페이지의 개인정보 처리 안내에 따르면 원본 및 변환 결과 파일은 슬랙에 저장되지만, PDF와 이미지로의 변환 처리는 구글 클라우드 런(Cloud Run) 기반의 외부 변환 서버를 거치며 브라우저 편집 세션 정보는 파이어스토어(Firestore)에 임시 기록된다. 서비스 제공 측은 문서 본문을 데이터베이스에 영구 저장하지 않는다고 밝히고 있으나, 문서가 사용자의 로컬 머신 경계를 벗어나 외부 인프라로 전송되어 처리된다는 구조적 사실 자체는 변하지 않는다.

  • 외부 유출 금지 문서 취급 주의 — 개인정보가 다량 포함된 명부, 영업 기밀, 법적 분쟁 서류, 미공개 계약서는 공개 클라우드 기반 연동 앱에 업로드를 지양해야 한다.
  • 망분리 환경의 제약 — 외부 네트워크와의 통신이 통제되는 폐쇄망이나 사내 규정상 서드파티 슬랙 앱 승인이 엄격한 금융·엔터프라이즈 환경에서는 기본 SaaS 형태의 즉시 도입이 어렵다.
  • 자체 호스팅 대안 고려 — 소스 코드가 MIT 라이선스로 공개되어 있고 도커(Docker) 기반 실행과 클라우드 배포 가이드가 문서화되어 있으므로, 보안이 중요한 조직은 인프라팀이 직접 사내 프라이빗 클라우드에 호스팅하는 방안을 검토할 수 있다.
  • 워크스페이스 권한 관리 — 채널 초대 시 봇 토큰 권한 범위를 점검하고, 자동 감지 모드 대신 멘션 요청 모드를 활성화하여 필요한 문서만 선택적으로 변환하는 운영 묘수가 권장된다.

7. 오픈소스 저장소 구조와 직접 검증하는 절차

기술적 신뢰성을 담보하는 가장 안전한 방법은 타인의 평가 문구에 의존하지 않고 공개된 코드와 라이선스를 독자가 직접 확인하는 것이다. rhwp for Slack은 전체 프로젝트 구조와 배포 스크립트를 깃허브(GitHub) 상에 투명하게 공개하고 있다.

독자는 GitHub 저장소(github.com/postmelee/rhwp-slack)에 접속하여 최상위의 LICENSE 파일을 통해 프로젝트가 MIT License 하에 배포되고 있음을 직접 확인할 수 있다. 저작권자는 개발자 Taegyu Lee로 명시되어 있으며, 슬랙 이벤트 처리와 웹 스튜디오 연동을 담당하는 애플리케이션 코드가 어떤 기술 스택(Node.js, TypeScript 등)으로 구성되어 있는지 저장소 트리를 통해 검증 가능하다.

또한 저장소 내 docs/self-hosting.md 문서에는 Cloud Run과 Cloudflare Pages를 조합하여 조직의 독자적인 인프라에 앱을 올릴 수 있는 자체 호스팅 절차가 안내되어 있다. 공개 베타 서비스를 직접 사용하기 전에 코드의 의존성 구조를 살피고, 조직의 인프라 표준에 부합하는지 사전 기술 실사(Technical Due Diligence)를 수행할 수 있는 최소한의 투명성이 확보되어 있다.

8. 확인하지 못한 것

본 글은 사실에 근거하여 작성되었으며, 조사 과정에서 객관적인 1차 출처나 공개 문서를 통해 확인하지 못한 항목들을 아래에 명확히 기록한다.

  • GitHub 상에 동일한 명칭으로 존재하는 여러 오픈소스 rhwp 저장소 계정들과 본 연동 앱 간의 구체적인 소스 코드 계보 및 직간접적 의존 관계는 공식 문서에서 특정되지 않아 확인하지 못했다.
  • 변환 서버(Cloud Run) 인스턴스 내부의 메모리나 임시 파일 시스템에 생성된 문서 캐시가 작업 완료 후 몇 초 또는 몇 분 이내에 물리적으로 소멸(wipe)되는지에 대한 세부 수명 주기는 확인하지 못했다.
  • 공개 베타 운영 인프라가 배치된 클라우드 서비스(GCP, Cloudflare)의 구체적인 물리적 데이터센터 리전 위치는 명시되지 않아 확인하지 못했다.
  • 수식, 차트, 복합 글상자 등 고급 조판 요소가 다수 포함된 특수 HWP 문서에 대한 정량적인 렌더링 재현율 및 호환율 벤치마크 수치는 공개된 데이터가 없어 확인하지 못했다.
