"Don't Roll Your Own"原则 2026 - 不应该重新发明浏览器原生功能的7个理由

为什么2026年的Web UI正在回归原生

2026-05-25 IT/技术

引言:所有网站都在重新做同样组件的奇怪现象

随机打开100个网站,亲自打开开发者工具检查会发现一个事实:几乎所有网站都在自己重写同一批组件。下拉菜单、模态框、折叠面板、日期选择器、文件上传、进度条、表单校验。这些组件浏览器都已原生提供,但90%以上的站点仍用div+JavaScript从零再实现一遍。如果所有桌面应用都自己重写操作系统已提供的文件对话框,我们会称之为低效。但在Web上,这是默认惯例。

news.hada.io 2026年5月24日第6条话题"Don't Roll Your Own" Principle 再次为这一现象命名。这条原则最初源于1990年代末密码学领域。"Don't roll your own crypto"──不要自己造加密算法。错误实现会给用户带来"以为安全"的幻觉,实际上更危险。后来同一原则扩展到认证、会话管理、HTML解析器、日期库。而在2026年,它再一次回到Web UI领域。本文不是 hada.io 的简单翻译,而是以那场讨论为起点,加入笔者的观察与对中文区开发者环境的含义,共12章展开分析。

三个核心问题驱动全文。第一,为什么不应该重新实现浏览器原生功能?具体理由是什么?第二,2026年基准下哪些功能已经足够成熟?第三,即便如此,还有哪些情况是自己造的正当例外?围绕这三问,文章还会展开GitHub、Stripe、Linear这类UX一流团队为何选择原生、React/Vue 生态制造的错误习惯,以及与中文区设计师/PM谈判的实战方法。

"Don't Roll Your Own"简史 - 从密码学到UI

先把原则本身的出处理清楚。"Don't roll your own crypto"是 Bruce Schneier 等安全研究者从1990年代末反复重申的警告。自制加密算法未经验证就部署,会让用户误以为安全。标准库(OpenSSL、libsodium 等)是几十年来上百位专家审查的成果。两者的可信度差距大到完全没法相提并论。

第二次扩展是认证与会话管理。PHP 时代手写会话管理产生的无数漏洞,逐渐让OAuth、OpenID Connect、经审验的会话库成为共识。CSRF、会话固定、会话再生这些细微问题在自制系统里几乎100%会出问题。后端社区已经形成共识:别自己造认证,拿成熟方案配置即可。

第三次扩展正是2026年的Web UI领域。这次"不要自己造"的对象是浏览器已提供的原生HTML元素──select、dialog、details、各种 input 类型、progress、video、audio。它们基于W3C/WHATWG标准在所有主流浏览器中打磨数十年。然而开发者仍习惯在div上加JavaScript从头再造。hada.io 讨论的核心,正是要把救了密码学与认证的同一条原则,带回Web UI。

不应该重新发明的10个浏览器原生功能

笔者整理的2026年基准下已经足够成熟、没必要自己造的10个原生功能。每项简短分析"为什么常被重新发明"和"为什么原生更好"。

1) <select> 下拉菜单

最常被重新发明的元素。设计师常以"难以自定义样式"为由要求改成div。但2024年起 appearance: base-select 提案陆续进入浏览器,2026年Chromium和Firefox已经正式支持Customizable Select。一行原生select即可免费获得键盘导航、移动端滚轮选择器、搜索、无障碍树注册。

2) <details> / <summary> 折叠面板

折叠面板和开关用 details/summary 一组即可实现,零JavaScript。open属性切换、键盘Enter/Space响应、内置浏览器查找都自动具备。同等功能的React组件平均需要100~300行代码。

3) <dialog> 模态框

自2022年所有主流浏览器稳定后,dialog成为模态框的正解。一次 showModal() 调用就完成焦点陷阱、ESC关闭、自动生成backdrop、无障碍处理。::backdrop 伪元素让背景样式自由可控。自制模态框常漏掉的"模态内Tab循环"等细节,原生天然具备。

4) <input type="date | time | datetime-local"> 日期/时间

React 生态里 react-datepicker、MUI DatePicker 几乎成为事实标准,但移动端原生输入框直接调用OS滚轮选择器/物质日历,体验通常更好。中国移动端用户大多数对iOS/Android 系统级日期选择器更熟悉。CSS 现在也可以通过 ::-webkit-datetime-edit 等伪元素做精细化样式。

5) <input type="file"> 文件上传

哪怕想做拖拽区,正确做法也是在原生 input type=file 之上叠加 dropzone CSS。multiple/accept/capture 属性是移动端直接调起相机/相册的关键,自制上传器最常漏掉的就是这部分。

6) <progress> / <meter> 进度条

用div+width做的进度条不会注册到无障碍树。屏幕阅读器只会念"区域1"。progress 元素只需 value/max 两个属性就自动入树,朗读时给出准确百分比。比手动加ARIA安全得多。

7) <video> / <audio> 媒体

video.js 之类的库确实强大,但只是普通播放,原生video自带画中画、字幕、播放速度、音量。一行controls属性即可呈现各OS最优的控制条。需要媒体库的真正场景是HLS、DRM、流媒体等专门领域。

8) input type="color | range | search | tel | email | url"

仅仅正确设置type,移动端键盘就会自动切换、校验自动生效、移动端语音输入/自动补全/OS密码管理器联动也自动启用。把 type 留作 text 只改 placeholder 是中文区站点最常见的浪费。

9) 表单校验 (required/pattern/minlength/maxlength)

HTML5 表单校验比手写JS校验更快、无障碍更好。:valid/:invalid 伪类用于样式,novalidate 属性可局部关闭。2026 最佳实践是把原生校验作为基线,JavaScript校验只用于跨字段或异步规则。

10) 滚动行为 (scroll-snap/scroll-behavior/overscroll-behavior)

轮播和滑块也不再需要JS库。CSS scroll-snap实现吸附滚动,scroll-behavior: smooth实现平滑滚动,overscroll-behavior控制弹性。移动端的惯性滚动也由原生自动处理。

重新发明的5项真实成本 - 不只是代码增加

"为什么用原生"之后的下一个问题是"自己造到底失去了什么"。笔者整理的5项成本如下。

  • 无障碍(a11y)损失:原生元素自带ARIA角色、键盘快捷键、屏幕阅读器朗读模式,完全免费。用div重新实现平均需要200~500行JS加上数十小时无障碍测试,而且大多数仍不如原生。
  • 键盘快捷键缺失:在select中按首字母跳转到对应选项、在dialog中Tab循环、在details中Enter开关──这些微妙键盘行为在自制组件里几乎100%缺失。重度用户能感受到,即使你从未测量过。
  • 移动端兼容性问题:原生 input type=date 在iOS弹滚轮选择器、Android弹Material日历,自制datepicker在两个平台都显得别扭。file/color/range也是同理。
  • 包体积膨胀:react-select 约50KB、react-datepicker 约40KB、react-modal 约15KB、react-dropzone 约30KB。一个普通SPA页面常有150~300KB的组件库占位。换成原生这些重量直接归零。
  • 维护负担:库每次大版本升级都会破坏API。React 18→19 升级让 react-select 迁移成本压在数千SaaS团队头上。原生标准不破,你的自制实现会破。

把这5项加总,平均一家中型SaaS每年要为重新发明组件付出大约200~500人时的额外成本。这差不多就是一个全职设计师或工程师的年薪。迁移到原生通常能在一个季度内消除其中大部分。

什么时候重新发明才正当 - 3类例外

如果结论是"所有场景都用原生不留例外",那也对一半。下面三种场景自己造仍然是正解。

  • 原生根本不支持的交互:拖拽排序、无限滚动虚拟化、多列网格、代码编辑器、Canvas白板。原生不提供,自己写或选用经验证的库都合理。
  • 品牌身份是决定性价值的位置:支付页核心卡片、首页Hero、Landing页签名组件。这些地方设计本身就是价值,合理放开原生的约束。
  • 原生结构与需求不匹配:嵌套大菜单、虚拟键盘、上万选项的虚拟下拉。原生select渲染1万项会卡死浏览器。这类场景虚拟化是必需,只有自定义才行。

核心决策规则很简单:"只要原生能满足70%,就用原生"。剩下30%靠CSS或少量JS补足。为了那30%放弃70%,在无障碍、包体积、维护成本上几乎一定是亏。

2026年原生功能的进化 - View Transitions、Anchor Positioning、Popover

2026年原生重新变得有吸引力的一个关键原因是浏览器正在快速补齐过去缺失的能力。笔者认为最有影响力的三项新API:

View Transitions API

仅为SPA平滑切换就引入 framer-motion 或 react-spring 的时代结束了。View Transitions API 自动捕获DOM变更前后并平滑插值。document.startViewTransition() 一行就完成页面切换、元素移动、列表排序动画。Chrome、Safari 支持,Firefox 在2026年初进入稳定版。

CSS Anchor Positioning

提示气泡、下拉、Popover定位也不再依赖Popper.js或floating-ui。CSS anchor-name/position-anchor 让"在某元素旁边自动定位,溢出屏幕则翻向另一边"完全用CSS完成。2025年Chrome稳定,2026年Firefox/Safari也进入稳定阶段。

Popover API

popover 属性配合 popovertarget,无需JS即可实现提示气泡、下拉、菜单。与dialog类似但非模态、更轻量。与Anchor Positioning结合后,几乎所有悬浮UI都能回归原生。

这三个API让2024年还被认定"必须自定义"的场景中有70~80%回到了原生可解决的范围。而且节奏可能继续加快。Interop项目(2022年启动)运行到第四年,四家主流浏览器在同一时间表上发布同样能力的协作模式已经稳定。

用CSS变量与::backdrop做样式 - 保留原生同时做设计

"用了原生就丑"这种反驳在2026年已经站不住脚。CSS的演进让原生元素几乎每个部位都能做样式。笔者常用的三种模式:

首先::backdrop 伪元素。给dialog和popover的背景直接写样式:backdrop-filter: blur(10px)、background: rgba(0,0,0,0.5)。iOS Safari 自2024年起也支持。

其次Customizable Select 的 appearance: base-select。Chromium 130+ / Firefox 135+ 已经允许对原生select的选项区做几乎全面的CSS控制。::picker(select)、option::checkmark 等伪元素能把设计系统的Look&Feel精确还原。

再次color-scheme / accent-color。一行 accent-color: var(--brand) 就让全页的 input type=checkbox/radio/range/progress 统一品牌色。原本几百行的自制复选框被一行CSS取代。

掌握这三种技法基本上就能在原生之上覆盖90%以上设计系统视觉需求。"设计 vs 无障碍"的二分法在2026年基本可以视为历史名词。

案例分析 - GitHub、Stripe、Linear为什么用原生

理论够了,看真实公司怎么做。

GitHub

GitHub 在2020年前后通过设计系统Primer明文规定"原生优先"政策。侧边栏开关用details/summary,PR模态用dialog,可搜索下拉则在原生select之上叠加。结果是GitHub的页面重量比同规模SaaS轻30~40%,键盘快捷键在所有页面都顺手。

Stripe

Stripe Dashboard 积极使用原生 form validation、input type=number/email。仅出于PCI-DSS要求把支付页卡号输入隔离到iframe,其余区域几乎全是原生。Stripe Dashboard 的性能与无障碍评分一直碾压SaaS平均水平。

Linear

Linear 本身是设计系统灵感来源,但内部大量使用details、dialog、原生表单。键盘快捷键在任何位置都顺手的原因之一,正是基础建在原生之上。设计好看不代表必须放弃原生。

三家公司的共同点是拒绝"设计 vs 原生"的二分法。在原生之上叠设计比从零造更快更稳,这个共识在三家公司都已内化。这种共识需要资深工程师与资深设计师之间的互信,需要数年才能建立。

React/Vue 生态系统的错误习惯 - shadcn、MUI 也别无条件信任

React/Vue 组件库分两类:一类是包装原生(Radix UI、Headless UI 一部分、Ariakit),另一类是div从零重写(很多设计系统)。使用前务必确认属于哪类。

shadcn/ui 基于Radix UI,大体上提供良好无障碍起点。但其中一些组件(尤其是Select、Dropdown Menu)是div重写而非原生select,移动端不会弹OS滚轮,键盘行为也略有差异。使用前要确认该组件以哪种元素为基础。

MUI 也一样。MUI 的 Select 是div基础,在移动端与原生行为不同。MUI 的 DatePicker 增加50KB+包体。简单场景下原生select、input type=date 更轻更快。

笔者常用的规则很简单:"只有真正需要 Radix/Ariakit/Headless UI 这类无样式库时才用库,其他都默认原生"。设计系统组件库如果是从零写div,长期使用成本一定高于原生。

开发者立刻可用的5项检查清单

把下面5条用在下一次PR里,任何一条单独使用都立刻见效。

  1. 把一个模态换成 <dialog>。把 react-modal 替换为原生 dialog + showModal()。平均节省15KB包,免费获得焦点陷阱与ESC关闭。
  2. 折叠面板全部换成 <details>/<summary>。删除自制toggle组件,平均删除200~300行JS。
  3. 日期输入换成 <input type="date">。如果移动端占70%以上,可用性几乎一定提升。删除 react-datepicker 节省40KB。
  4. 表单校验把原生 required/pattern 放第一位。JS校验只作为补充。
  5. 新功能PR里先在MDN搜原生元素,再考虑 div+role。一年之后整个代码库的形态会改变。

这5项都不需要设计师同意,开发者自己就能决定。它们会出现在PR、出现在Lighthouse评分上,日后推广更大范围迁移时这些数字就是最好的论据。

与中文区设计师/PM的谈判方法

中文区IT团队里最常见的冲突是"设计系统定的样式原生跟不上"。笔者实战里反复用到的三种谈判模式:

第一,"按组件分批谈判"。不要提议"全面换原生",而是说"先把影响最大的5个组件(模态、下拉、折叠、日期、文件)换原生,其他维持原状"。分阶段提案比正面冲突通过率高得多。

第二,"用数字说话"。把设计变更的成本换算成KB、ms、无障碍评分。"把 react-datepicker 换成原生 input type=date,移动端首屏快700ms,包体减40KB"──这种句子设计师很难否决,远比"原生就是更好"有效100倍。

第三,"把控制权交给设计师"。用CSS变量暴露设计token,让设计师自己调色、调间距、调字体。设计师有了产物的控制权,对原生的抵触感会大幅下降。这是笔者见过最有效的谈判方法。

对中文区PM则先抛出"70%以上用户在移动端,他们更熟悉OS自带选择器"的可用性数据。UX数据胜过设计偏好这件事在中文产品圈也越来越成为共识。

结论与可立即落地的3件事

本文核心压成一句话:2026年的Web UI正在告别"从零造"的时代,进入"在原生之上叠样式"的时代。浏览器在快速填补长期欠缺的能力,CSS提供了为原生做设计的所有工具。自己造的成本在时间、包体、无障碍、维护四个维度上都越来越贵。原生的标准不会破,你的自制实现会破。

三件立刻可以做的事:

  1. 在下一个PR里把一个模态替换为原生 <dialog>。一小时完成,立刻得到约15KB包减小和无障碍评分提升。
  2. 盘点自家SPA使用的组件库清单。一周内列出哪些可被原生替代。这张清单本身就是未来一年的改进路线图。
  3. 在下次设计系统会议上提出"原生优先"政策。配合"用CSS变量把控制权给设计师"作为交换条件,通过率会显著提高。政策一旦落地,每年200~500人时的节省会自动产生。
