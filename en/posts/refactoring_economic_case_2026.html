When Does Refactoring Pay Back - Making the Case as an Investment, Not a Cost

Talking payback period instead of cleanliness - a 12-quarter model, and the code you should leave alone

2026-08-01 Dev & Infra

Introduction: «That is not a feature»

It was a quarterly planning meeting. I asked for two weeks to tidy up the payments module and got this back: «That is not a feature.» Nothing came to mind as a rebuttal, because it was true. What I could show after two weeks was a screen that behaves exactly as it does now.

This article is about what I should have said in that room. But let me set the direction clearly first. That answer did not come from schedule pressure being irrational. Usually there is a contracted delivery date, being second to market counts as late, and this quarter's results decide next quarter's headcount. The person declining the cleanup has their own numbers to return. A conversation that starts by refusing to acknowledge that mostly fails.

So one problem remains. How does cleanup enter that person's numbers? «It will be cleaner» does not enter. «We have accumulated technical debt» does not enter either. The word debt is borrowed from accounting, yet it arrives with no principal, no interest rate and no maturity attached. Only one form enters: spend this many days now and save that many days per quarter starting then.

So this article actually computed whether that sentence can be constructed. The short answer is that it can. And once you compute it, something else falls out alongside: there is more code that should be left alone than you would expect. Those two things are the whole article.

What kind of numbers these are. Every figure here is the output of a model I fed assumptions into. None of it was measured in a real organization, and none of it is an industry average. I could not confirm a value like «cost of change rises N percent per quarter» in any primary source I trust, so instead I wrote the assumptions into a table and shook them to see how the conclusion moves. What to take away is not any specific number but the form of the calculation.

Environment. The model ran on Node.js v22.16.0 (win32). The parts that use randomness fix the mulberry32 generator to seed 20260801, so the same code produces the same values.

The starting point is an experiment posted to martinfowler.com on 30 July 2026. Giles Edwards-Alexander of Thoughtworks took a 150,000-line application built by agents, split a single Rust file that had grown to 17,155 lines across fifteen steps, then had a fresh agent make the same feature change and remeasured input tokens. He reported a drop from 159,564 to 27,360. I will not generalize that value. It came from one codebase and one change, and the token accounting is stated to be an approximation from dividing character counts by four. What this article takes from it is not the number but the question. If the benefit of cleanup can be written in currency, what does that calculation look like for code that humans touch?

1. Why it does not persuade - the output never reaches a screen

Something has to be conceded first. Refactoring is the only work in software development where «nothing happened» is the success report. That single property explains most of the persuasion failure.

PropertyFeature workCleanup
What you show when doneA working screenThe same screen as before
When failure surfacesImmediatelyImmediately (as a regression)
When success surfacesImmediatelyQuarters later, indirectly
Who receives the benefitWhoever asked for itWhoever opens this code next
Certainty of the costCertainCertain
Certainty of the benefitFairly clearProbabilistic
What survives cancellationPartial functionalityHalf-changed code

The last three rows are the point. From the approver's chair, cleanup is a proposal where the cost is certain and now, the benefit is later and probabilistic, and stopping leaves you in between. Proposals of that shape are hard to pass in any domain. This is not a peculiarity of engineering organizations.

And the vocabulary the engineering side reaches for tends to make it worse.

  • «Technical debt» — borrowed from finance, but with no principal, no rate and no maturity. Debt without numbers cannot ground a decision
  • «The code is dirty» — sounds like an aesthetic judgement. And sometimes it genuinely is one
  • «This will hurt us later» — a warning with neither a date nor a magnitude loses weight with every repetition
  • «We need to do it properly» — can be heard as «we have not been doing it properly until now». It only sours the room
  • «It is the industry standard» — ask for a source and most people cannot produce one. I tried to while writing this and failed to find a primary statistic worth citing

Martin Fowler named the claim that design investment eventually returns as faster development the Design Stamina Hypothesis, and labelled it a hypothesis on purpose. He wrote that he calls it a hypothesis because it is a conjecture and there is no objective proof that the phenomenon actually occurs. In the same piece he stated that we can measure neither productivity nor design quality. The most-cited figure in this field opened by saying the proof is not there.

So drop the arguments that begin with «studies show». What remains is building a model from your own organization's numbers, saying out loud that it is a model, and publishing the assumptions.

2. Where the cost hides - you are already paying it

Propose cleanup as «extra budget» and you will almost always lose. It is not extra. The money is already going out; it is simply booked under other line items. Here is where it hides, broken out.

Cost itemWhat actually happensWhat it is called on the booksWho bears it
ComprehensionReading time spent finding where to change. Irrelevant code has to be read tooFeature development effortWhoever is on this task
ModificationFixing one place forces fixing others. The number of files opened together growsFeature development effortWhoever is on this task
Regression riskSomething breaks somewhere unrelated. Verification scope has to widenQA time, incident responseOperations, customers
OnboardingTime before a new joiner ships their first changeOnboarding, trainingHR, the whole team
AvoidanceToo scary to touch, so a new copy goes next to it. The same logic now exists twiceFeature development effortEvery future maintainer
EstimationNobody knows how long it will take, so the quote carries a large bufferSchedule bufferProduct, sales

Read the table vertically and one thing stands out. The third column is a different name every time. Costs arising from one cause are scattered across feature effort, QA time, onboarding and schedule buffer. Look at any single line item and it reads as «a bit high», and there is nowhere they add up in view.

I think that is the real reason a refactoring budget never gets allocated. The spending is already happening, and no account exists that shows it on one line. And most of that spending is billed to whoever touches the code next. No invoice reaches the party moving quickly today.

How to write code so that these costs stay lower is not the subject here. The habits side is covered separately in write code like a human will maintain it. This article only asks whether code that already ended up this way is worth cleaning.

3. The model - twelve quarters cumulative and the breakeven

Now the calculation. Only three inputs are needed. How many changes land in this area per quarter, how many days each takes, and how that number is moving. Add the cleanup cost and its effect and a payback quarter falls out.

The assumptions come first. All of them are invented. In a real organization the first two can be pulled from version control and an issue tracker; the third can only be estimated.

Here is how to read it.

  • The worst drawdown is 24 person-days at the end of Q2. This is the most important number in practice, because it is what evaporates if the plan gets cancelled halfway
  • Breakeven is Q5. Counted from the end of the cleanup, that is three quarters later
  • The twelve-quarter difference is 134.3 person-days, or 5.6 times the 24 person-days invested
  • In A the cost per change went from 3.00 to 5.69 person-days, a factor of 1.9. That is 6 percent per quarter compounding for twelve quarters
  • In B it went from 3.00 to 2.69, barely moving from where the cleanup left it

I want to flag that the least honest value here is the 6 percent in gA. I could not find primary material to support it, and I have no intention of using it as though I had. So in the next section I shook that value. To spoil the result: shaking it does not change much. Growth rate is not what governs the payback.

Read the table horizontally and you see the influence of the growth rate. At eight changes per quarter I moved growth from 1 percent to 10 percent, a factor of ten, and breakeven moved from Q6 to Q4 — two quarters.

Read it vertically and a different picture appears. Holding growth at 6 percent and moving changes from 1 to 16 takes you from never repaid to Q4. That is a qualitatively different conclusion.

  • What governs payback is not how bad the code is but how often you touch it
  • Not knowing the growth rate precisely is less fatal than it looks, because the conclusion does not depend heavily on it
  • Conversely, changes per quarter must be counted. It is the value that flips the conclusion, and fortunately it is a value you can actually count
  • The «never repaid» corner at the top left is half of this article. Code you do not touch is not a candidate no matter how bad it is

The right-hand column is the interesting one. Even when cost per change fell by only 5 percent right after the cleanup, a 24 person-day job repaid by Q7. It repays despite almost no immediate effect because the growth rate bent from 6 percent to 2 percent.

This matters in practice for a specific reason. When proposing cleanup people usually try to promise «we will be N percent faster», and that promise is hard to keep and hard to verify. Whereas «with this shape, adding features will not keep getting heavier the way it has been» is a far more defensible claim, and in the model it was the larger share of the benefit.

5. When it never repays - the code to leave alone

This is the part I most wanted to write. Cleanup is an investment that makes future changes cheaper. With no future changes there is nothing to recover it from. Put «when does this code get retired» into the model and it becomes visible immediately.

The rule comes out in one line. If the remaining lifetime is shorter than the breakeven, cleanup is a straight loss. Making a system beautiful today when it gets torn out in a year is, inside this model, simply throwing away 24 person-days.

  • «It is ugly» is not a justification. There is no cell anywhere in this table for an aesthetic judgement
  • «This one is genuinely severe» is not one either. Severity is already reflected in C0, and by itself it does not fix the payback quarter
  • Conversely, boring, unremarkable-looking code can be the top priority if somebody opens it every week
  • Change frequency can be counted straight out of version control history. It is a fact, not an estimate
  • Remaining lifetime lives in the product roadmap. Engineering does not get to decide it alone, so you have to ask

6. Incremental cleanup - why big rewrites tend to fail

Even when the payback verdict is positive, a question remains. Replace it all at once, or clean only what you touch? I ran both in the same model. Incremental means six person-days per quarter for four quarters, each pass buying a smaller improvement.

Incremental cleanup buys half the exposure by giving up a third of the gain. The reason that trade is usually favourable lives outside the calculation: nothing guarantees the plan runs to the end. The worst drawdown becomes a real loss the moment priorities shift or someone leaves, whereas the twelve-quarter gain only materializes if the organization stays pointed the same way for that long. The first number is certain and the second is conditional.

The risks on the rewrite side are well documented outside the model too. Martin Fowler wrote of wholesale system replacement that he had seen this simple-sounding plan go down in flames most of the time, citing the fact that users cannot wait for new features during the long haul, and that much of the existing behaviour is not worth replicating anyway. He also noted that organizations balk at building the transitional architecture that lets old and new coexist. That burden is the «parallel maintenance» row above.

  • Cancellation risk — a full rewrite creates no value until just before completion. Stopping at 90 percent means zero percent
  • Parallel maintenance — while old and new paths run together, every fix has to be made twice
  • Verification burden — you must prove «behaves exactly as before» across the whole scope, and proof gets harder as scope grows
  • Missing specification — the behaviour to be carried over lives in the code, not a document. So requirements nobody knew about keep surfacing mid-migration
  • Staff turnover — a plan spanning several quarters may not be finished by whoever started it

Incremental cleanup has a weakness too. Regions nobody opens never get cleaned. But look back at the decision table in section 5: regions nobody opens were never candidates to begin with. The weakness of incremental cleanup and the conclusion of the payback calculation point at the same place. How to slice a large change for review is covered separately in stacked pull requests. Here the point is only that the reason for slicing is not reviewer convenience but exposure management.

7. What to count so a conversation can happen

The most common mistake in metric discussions is starting from a target number. The reason not to is stated in the primary material. DORA names setting metrics as a goal and Goodhart's law directly as hazards, warning that teams may end up manipulating results instead of genuinely improving. It also says comparing across different applications or industries is misleading.

So no targets are offered here. Only «what to count so that a conversation becomes possible».

There are only three suggestions about how to use them.

  • Measure before you clean. Claiming an effect later requires a baseline, and most people think of this after the cleanup is finished
  • Measure the same way again. If the aggregation method changes, the before-and-after comparison is meaningless
  • Do not set them as targets; watch the direction. The moment a number becomes a goal, work to produce the number begins
  • Shrinking the unit of change can make lead time look better on its own. Those queue-side effects move independently of cleanup, so keep them separate
  • A line-level diff hides what actually changed. The function-level approach is written up over here

8. How the conversation goes in different org structures

The calculation so far works anywhere. Whether you are in a position to raise it depends on organizational structure. Here are three structures and what changes in each. This is about structures, not about any particular company.

8.1 When the delivery date is contractual

Often the schedule is not an internal goal but a date written into a contract. Then «just give me two weeks» is outside the approver's discretion. You are asking the wrong person.

  • The only form that works in this structure is attaching it to the next feature: «If we tidy this part before adding that feature, this job gets a few days shorter»
  • In that form the payback lands at the next release. No twelve-quarter argument is needed
  • The downside of being wrong is small too. You find out in days, and if it did not work you do not do it again
  • But this route never cleans the structure as a whole. That is the trade already accepted in section 6

8.2 When the builders and the operators are different organizations

Where one party builds and another takes over operations, or the reverse, or where several stages are involved, the party paying the cost and the party receiving the benefit are separated. This is the condition under which refactoring is least likely to happen.

  • During construction, only the cost up to delivery is in scope. In the model of section 3 that is a contract ending at Q1-Q2, and the answer over that window is always «do not clean»
  • Whoever inherits operations starts from an already-elevated cost per change. They have to pay the cleanup out of a budget separate from the build budget
  • So in this structure there is not much beyond deciding it at contract time: writing it into acceptance criteria, or naming cleanup effort in the maintenance agreement
  • When the assigned people change, the baseline disappears. Starting without knowing what the predecessor left and why puts comprehension cost back at maximum
  • So the highest-leverage move in this structure may be recording why things are the way they are rather than the cleanup itself. Comprehension is the one cost item on that list that documentation can reduce

8.3 Changing the vocabulary

The same content lands differently depending on how it is said. On the left is language that only travels inside engineering; on the right is language that becomes a budget conversation.

  • «We have serious technical debt» → «This area takes 8 changes a quarter, and per-change time went from 3 days to 4»
  • «We need to clean up the code» → «24 person-days now returns about 9 person-days per quarter from Q5. It is an estimate»
  • «This will hurt us later» → «At this rate, in two years a change costs 1.9 times what it does today»
  • «We need to do it properly» → «Let me spend 3 days before this feature and check whether it shortens the job»
  • «We need a full rewrite» → «All at once exposes 24 person-days; split up it exposes 11.6»

What the right-hand sentences have in common is that they are stated in a falsifiable form. They carry numbers, so they get checked later. That is the cost of this approach and simultaneously where the trust comes from. Say up front that it is an estimate and the conversation continues even when you turn out to be wrong.

9. When to do it and in what approval unit

Last is the execution shape. The one thing the calculation tells you is cut the approval unit small.

9.1 Fold it into feature work, or carve it out

  • Folding in is the default. Attached to the front of the next feature, the payback lands at that feature's completion. Easiest to approve and easiest to verify
  • Carving it out is necessary when the scope spans several features and cannot be attached to one. That needs separate approval, and the justification only holds if it sits in the «top priority» cell of section 5
  • The risk of folding in is that feature change and structural change land in the same review unit, making it hard to tell which caused a regression. Ordering them separately is better
  • The risk of carving out is the drawdown from section 6. Capping each approved chunk at what fits inside one quarter keeps the exposure managed

9.2 Check before you propose

  • I actually counted how many changes per quarter landed here, in version control
  • I asked product about the remaining lifetime and confirmed there is no retirement plan
  • I scoped the cleanup and produced a person-day estimate. Not «about two weeks», a number
  • I measured today's metrics before starting, so a baseline exists for later comparison
  • I sequenced it so that stopping midway still leaves the improvements made so far
  • I decided how to catch regressions, and put into the estimate that verification scope is wider than cleanup scope
  • The proposal contains a sentence saying these are estimates. Nobody knows the growth rate
  • I removed every «clean», «properly» and «technical debt»
  • I checked that the payback lands inside the approver's attention span. A benefit twelve quarters out is usually nobody's concern

10. What this calculation does not say

Building a model and not writing down its limits would make it the same thing as the «studies show» I criticized earlier. Here is what I could not confirm.

  • I do not know the real growth rate. The 6 percent is invented. I could not find primary material supporting it, which is why I chose to shake it instead
  • The compounding shape itself is an assumption. In reality the curve may bend sharply somewhere or jump in steps
  • Decay of the cleanup effect is not modelled. The lower growth rate holds for all twelve quarters here; in reality things degrade again
  • People changing is not modelled. When whoever did the cleanup leaves, comprehension cost climbs back
  • Person-days are not converted to currency. It varies by organization, and converting moves the argument onto that ground
  • Morale and attrition are not modelled. They are hard to quantify, and quantifying them invites putting in any number you like
  • The model itself is unvalidated. Validating it would require running both scenarios simultaneously in the same organization, which is impossible

That last item is the field's foundational problem. It is the same reason Fowler attached «there is no objective proof» to the Design Stamina Hypothesis. So what this article proposes is not a truth but a form. Write the assumptions, compute, say that they are assumptions, then shake them and see how much the conclusion withstands. That form beats «we need to make it clean» not because it is accurate but because it is refutable.

Conclusion: the criterion is frequency, not the code

To summarize.

  • Refactoring fails to persuade because its output never reaches a screen, and that asymmetry cannot be removed. Start by conceding it
  • The cost is already going out. It is just scattered across feature effort, QA time, onboarding and schedule buffer so that it never appears on one line
  • The payback calculation needs three values: changes per quarter, days per change, and the growth rate. The first two are countable; the last is an estimate
  • What governs the payback is change frequency. Moving growth by a factor of ten shifted breakeven two quarters; moving frequency flipped the conclusion outright
  • So some code is worth cleaning and some is not. Code nobody opens and code about to be retired should be left alone however bad it looks
  • The default strategy is cleaning only what you touch. The gain drops by a third but the exposure halves, and stopping still leaves the improvements made so far
  • Metrics are for conversation, not targets. Measure before, measure the same way after, and watch only the direction

So the language that persuades is not «clean». It is payback period. And once you compute the payback period, in a great many cases the answer comes out as «do not». Being able to produce that answer yourself is, I think, the real usefulness of this calculation. Someone who says first that a particular cleanup is unnecessary is far stronger on the rest of their requests than someone who demands all of them.

## 0. The premise

Cleanup is **an investment that makes future changes cheaper**.
So the deciding factor is not the state of the code but **how often you will touch it from here on**.
The language that persuades is not «clean». It is **payback period**.

## 1. The payback model (runnable as-is)

```js
// All values are assumptions. None of them came from a real organization.
var P = {
  N: 8,        // changes landing in this area per quarter   <- actually count these in version control
  C0: 3.0,     // person-days per change today               <- pull from your issue tracker
  gA: 0.06,    // quarterly growth of cost-per-change if untouched  <- an estimate. nobody knows this
  K: 24,       // one-time cleanup cost, person-days         <- scope it first, then estimate
  spread: 2,   // how many quarters the cleanup is spread over
  rho: 0.75,   // cost-per-change right after cleanup (0.75 = 25% cheaper)  <- an estimate
  gB: 0.02,    // quarterly growth after cleanup             <- an estimate
  Q: 12        // horizon, in quarters
};

function run(p) {
  var A = [], B = [], ca = 0, cb = 0, q, cpcA, cpcB, extra;
  for (q = 1; q <= p.Q; q++) {
    cpcA = p.C0 * Math.pow(1 + p.gA, q - 1);
    ca += p.N * cpcA;
    A.push(ca);
    extra = 0;
    if (q <= p.spread) { cpcB = cpcA; extra = p.K / p.spread; }
    else { cpcB = p.C0 * p.rho * Math.pow(1 + p.gB, q - p.spread - 1); }
    cb += p.N * cpcB + extra;
    B.push(cb);
  }
  return { A: A, B: B };
}

function breakeven(p) {
  var r = run(p), i;
  for (i = 0; i < p.Q; i++) { if (r.B[i] <= r.A[i]) { return i + 1; } }
  return null;   // not repaid within the horizon
}

var r = run(P);
console.log('breakeven : ' + (breakeven(P) === null ? 'never within horizon' : 'Q' + breakeven(P)));
console.log('worst drawdown : ' + Math.min.apply(null, r.A.map(function (a, i) { return a - r.B[i]; })).toFixed(1) + ' person-days');
console.log('gain at Q12 : ' + (r.A[P.Q - 1] - r.B[P.Q - 1]).toFixed(1) + ' person-days');
```

Output under the assumptions above: breakeven Q5 / worst drawdown -24.0 person-days / gain at Q12 +134.3 person-days

## 2. Breakeven sensitivity (change frequency × growth rate)

`-` means not repaid within 12 quarters.

| Changes per quarter | 1% | 2% | 4% | 6% | 10% |
|---|---|---|---|---|---|
| 1 | - | - | - | - | Q11 |
| 2 | - | - | Q11 | Q10 | Q8 |
| 4 | Q10 | Q9 | Q8 | Q7 | Q6 |
| 8 | Q6 | Q6 | Q5 | Q5 | Q4 |
| 16 | Q4 | Q4 | Q4 | Q4 | Q4 |

**How to read it**: moving the growth rate by a factor of ten shifts breakeven by two quarters. Moving the change frequency flips the conclusion entirely.
→ **What governs payback is not how bad the code is. It is how often you touch it.**

## 3. Should you clean this up

| Change frequency | Under 1 year left | 1-3 years | 3+ years |
|---|---|---|---|
| Almost never (1 or fewer per quarter) | No | No | **No** |
| Occasionally (2-4 per quarter) | No | Only while you are in there | Only while you are in there |
| Often (5-8 per quarter) | No | **Incremental cleanup** | **Incremental cleanup** |
| Very often (9+ per quarter) | No | **Incremental, prioritized** | **Top priority** |

- The whole first column is «No» — code with a retirement date is not a candidate
- The whole first row is «No» — code nobody opens is not a candidate
- «It is ugly» has no cell anywhere in this table

## 4. Big-bang rewrite vs incremental cleanup

| Item | All at once (24 pd over 2 quarters) | While you are in there (6 pd × 4 quarters) |
|---|---|---|
| Worst cumulative drawdown | -24.0 person-days | **-11.6 person-days** |
| Breakeven | **Q5** | Q6 |
| Gain at Q12 | **+134.3 person-days** | +89.8 person-days |
| What survives if you stop | A half-changed structure | **Every improvement made so far** |
| Approval difficulty | High | **Low** |

→ You buy half the exposure by giving up a third of the gain. **Nothing guarantees the plan runs to the end, which is usually what makes this a good trade.**

## 5. What to measure (do not set targets)

| Metric | Definition | Where it comes from | Trap |
|---|---|---|---|
| Change lead time | Commit enters version control → deployed to production (DORA) | Version control + deploy history | Approval steps and other non-code factors get mixed in |
| Change fail rate | Share of deployments needing immediate intervention (DORA) | Incident and hotfix records | Swings wildly on small samples |
| Per-file change frequency | How often a path appears in commits per quarter | Version control history | Bulk reformatting commits distort the ranking |
| Files touched per change | How many files a single change modifies | Version control history | Not comparable if feature sizes differ |
| Duration per change | Start → finish for the same class of change | Issue tracker | Defining «the same class» is the hardest part |
| Time to first change | Days for a new joiner to ship their first deploy | Start date + deploy history | Extremely small sample |

**Rules for using them**
1. Measure **before** the cleanup (without a baseline you cannot claim anything later)
2. Measure the same way again (a changed method makes the comparison meaningless)
3. Do not set them as targets — DORA itself names Goodhart's law as a hazard

## 6. Checklist before you propose

- [ ] I **actually counted** changes per quarter in version control (not estimated)
- [ ] I asked product about the **remaining lifetime** and confirmed there is no retirement plan
- [ ] I scoped the cleanup and produced a **person-day estimate** (no «about two weeks»)
- [ ] I measured the metrics **before** starting, so a baseline exists
- [ ] I sequenced the work so that **stopping midway still leaves the improvements made so far**
- [ ] I put in the estimate that the **verification scope is wider than the cleanup scope**
- [ ] The proposal **says out loud that these are estimates**
- [ ] The payback lands **inside the approver's attention span**
- [ ] I removed every instance of «clean», «properly», and «technical debt»

## 7. Rewording table

| Does not land | Becomes a budget conversation |
|---|---|
| We have serious technical debt | This area takes 8 changes a quarter and per-change time went from 3 days to 4 |
| We need to clean up the code | 24 person-days now returns about 9 person-days per quarter from Q5. It is an estimate |
| This will blow up later | At this rate, in two years a change costs 1.9 times what it does today |
| We need a full rewrite | All at once exposes 24 person-days. Split up it exposes 11.6 |

## 8. Do not

- ❌ Quote «industry average» figures without a source — if you cannot open the primary source, do not use the number
- ❌ Set a target number first — that starts the work of manufacturing the number
- ❌ Clean up code that is scheduled for retirement — if the remaining life is shorter than the breakeven, it is a straight loss
- ❌ Clean up code nobody opens — there is nothing to recover it from
- ❌ Request one large separate block of time — the worst drawdown is exactly your exposure
- ❌ Present model output as established fact — say it is an assumption first
