何を入力し、何を出力するか

Archifyはエージェントに導入するスキルである。READMEの最初の文は、理解したいもの、計画したいもの、共有したいものをインタラクティブな視覚資料に変える、というものだ。システム構成図に限らず旅行日程や学習マップの事例も紹介しているが、GeekNewsの紹介とこの記事の関心は、コードと説明からシステム図を作る側にある。要点は分業だ。人が作図ツールを操作するのではなく、エージェントが図の元データを書き、レンダラーがそれを画面に変える。

入力は三つの形に整理できる。一つ目は、システムを言葉にした説明である。READMEの例は一文で、ブラウザがAPIを呼び、APIがRedisを確認し、キャッシュミスならPostgreSQLを照会してキャッシュを埋める、というものだ。二つ目はリポジトリである。エージェントに読ませて根拠のあるアーキテクチャ図を頼むことができ、リポジトリは必須ではないとREADMEは明記している。三つ目は、出来上がった図を整える追加依頼である。Redisを足す、認証を左へ移す、ロールバック経路を強調する、といった依頼で、Archifyが型付きの元データを保持するため指定した部分だけが直るとされている。

成果物は次のように分かれる。

  • 単一のHTMLファイル。 ノードの詳細と経路の探索がファイルの中に入っており、受け取った人はArchifyを入れずにブラウザで開ける。外部サイトや地図リンクだけがネットワークを必要とする。
  • 型付きのJSON中間表現。 レンダラーが付くすべてのモードにスキーマがあり、同じ元データから同じ結果を再現できるとREADMEは説明する。
  • 画像と動画の書き出し。 PNGをクリップボードへコピーでき、静止画や動きのある形式をダウンロードできる。GeekNewsの紹介はPNG、SVG、WebMに触れている。
  • 共有カード。 たどった経路や到達範囲を1200×630のPNGとして書き出す。図全体は文脈として残る。
  • 比較ビュー。 変更前後のスナップショットを比べるArchitecture Deltaが別のモードとしてある。

この記事の切り口は二つの問いに絞られる。エージェントがコードを読んで図を作る過程で何が自動で処理され、結果を受け取った人は何を自分で照合しなければならないのか。すでに扱った隣接テーマは繰り返さない。図の視覚ルールを後処理で当てる方式はDiagram Designスキルの記事に、静的解析とLLMを組み合わせてアーキテクチャを取り出す方式はCodeBoardingの記事にある。Archifyはこの二つと違い、エージェントが判断して書いたJSONを検証ゲートに通す構造なので、ゲートが何を保証し何を保証しないかが読みどころになる。

導入と呼び出し — READMEにあるコマンドだけ

導入はnpxによるスキル導入コマンド一行が基本である。対応先としてCursor、Claude Code、Codex CLI、OpenCodeが挙がっている。次の二行はREADMEがそのまま載せているコマンドで、一行目が標準の導入、二行目が導入せずに試す方式だ。

npx skills add tt-a1i/archify -g
                    npx skills use tt-a1i/archify@archify --agent codex

Cursor向けには、対話的な質問なしで導入する明示的な形が別に載っている。このコマンドはスキル名、エージェント、グローバル導入、コピー方式、確認の省略をすべてオプションで指定する。呼び出しはコマンドではなく自然言語だ。エージェントにArchifyを使って図を描くよう頼めばよく、READMEの最初の例文がそれに当たる。その後は、認証を追加して、キャッシュミスの経路を強調して、ライトテーマに切り替えて、と会話を続ける。

導入先はエージェントごとに違う。READMEの表を要約すると次のとおりである。

  • Claude Code。 ~/.claude/skills/ またはプロジェクトの .claude/skills/。レンダラーと検証の手順が全体として動く。
  • Codex CLIとopencode。 それぞれのスキルディレクトリに置かれ、同じ全体の手順が動くと表に書かれている。
  • Claude.ai。 設定のスキル項目にarchify.zipをアップロードする。動作範囲はサンドボックスでNode.jsを使えるかに左右されると明記されている。
  • プロジェクトナレッジ(Project Knowledge)。 同じzipを上げるとプロンプト駆動のアーキテクチャ代替経路になる。レンダラーと検証手順を使う経路とは異なる。

この一覧で実務上重要なのは最後の二項目である。レンダラーと検証器はNode.jsで動くため、Nodeを実行できない環境ではArchifyが約束する検証の段階そのものが抜ける。導入したことと検証手順が実際に回ることは別であり、この差は後の表で人が確認する項目として再び出てくる。コミュニティによるHermes AgentとDeepSeek Harnessの連携もREADMEにあるが、いずれも公式製品ではなくテレメトリはないという注記付きのオプトインとされている。

五つの図の種類とプロンプトに入れるもの

Archifyは図の種類を五つに分ける。種類を選ぶのはスキル手順の最初の段階であり、ユーザーがプロンプトに何を書くかが結果の正確さを左右するため、READMEは種類ごとに入れる情報を案内している。

種類向いている対象プロンプトに入れるもの
Architectureコンポーネント、サービス、ストレージ、境界範囲、中核コンポーネント、主経路
WorkflowCI/CD、承認、ツール呼び出し、ランブック参加者、順序、分岐、例外
SequenceAPI呼び出し、キャッシュのフォールバック、認証、非同期の追跡呼び出し元、呼び出し先、戻り、タイミング
Data Flowパイプライン、系譜、個人情報、消費者ソース、変換、ストア、境界
Lifecycle状態、再試行、待機、終了結果状態、イベント、再試行とキャンセルの経路

表で注目したいのは右の列だ。プロンプトに入れるものとして挙がっている項目は、そのまま図に載る事実の一覧になる。エージェントがコードから調べる場合でも、人が範囲と中核コンポーネントをあらかじめ決めておくと図は絞られる。READMEのリポジトリ分析の例は、この原則をそのまま文にしたものである。

Analyze this repository, then use archify to create a high-level runtime architecture diagram.
                    Show 8–12 core components, one primary path, external dependencies, and trust boundaries.
                    Put supporting detail in cards instead of adding more edges.

この例は三つのことを求めている。コンポーネントを8個から12個に制限し、主経路を一つだけにし、補足情報は線を増やさずカードに載せる。数の制限は図を読みやすくするためだが、人にはもう一つの意味がある。12個に入らなかったコンポーネントは図から抜けており、抜けたという事実は図には表示されない。範囲を決めた人だけが、何が抜けたかを知っている。

  • 範囲の文にシステムの名前と境界を書くと、スキルが何を含めるか決めやすい。
  • 主経路を一つに固定すると、残りは補足情報に回り、線が絡まない。
  • 信頼境界と外部依存は依頼しないと図にない場合があるため、明示するほうが安全である。

生成の流れ — JSON中間表現と検証ゲート

Archifyの構造でいちばん特徴的なのは、図の代わりにJSONを書くという点だ。READMEの説明とスキル定義を合わせると、流れは次の順である。

  1. 種類の判別。 依頼がアーキテクチャ、ワークフロー、シーケンス、データフロー、ライフサイクルのどれかを決める。
  2. スキーマと例の読み込み。 該当する種類のスキーマと例を分けて読む。
  3. 候補JSONの作成。 完成した候補JSONをエージェントが直接書く。スキル定義は、ノード、関係、出典、ビュー、カード、境界の数は目標でも上限でもないと述べ、事前のスケッチや散文による座標計画を作らないよう求める。
  4. 最終処理(finalize)。 検証と配信を一度に実行する。通ったということは、検証、配信、厳格な検査、実ブラウザでの検査の各ゲートが通ったという意味だとスキル定義が明記する。
  5. 失敗の修復。 失敗したゲートがあればJSONを直して再実行する。修正の機会は二回に制限される。

配信の段階は原子的である。同じディレクトリに候補を描画して検査し、通った結果だけが既存の成果物を原子的に置き換える。そのため、保存の途中で誤ったファイルが直前の正常版を上書きすることはない。READMEは検査項目としてスキーマ、レイアウト、HTML/SVG、経路、ラベルと経路の間隔を挙げる。リポジトリのコマンドでは、検証と配信をそれぞれ次のように実行できる。

cd archify
                    node bin/archify.mjs validate workflow examples/agent-tool-call.workflow.json --quality showcase --json
                    node bin/archify.mjs deliver workflow examples/agent-tool-call.workflow.json /tmp/workflow.html --quality showcase --open --json

失敗したときの形式も決まっている。validate --json と deliver --json はJSONオブジェクトを一つ出力し、その中には安定した規則コード、問題の対象、測定された証拠、対応している修復手段だけが入る。エージェントは診断ごとに付いた対応済みの修正だけを適用する設計で、スキル定義は終了コードが0でないのに成功を主張すること、実際のキャプチャなしに目視で確認したと主張することを禁じている。これはエージェントの報告を機械の出力に結び付ける仕掛けである。

  • 検証の失敗はスタックトレースではなく規則コードと測定値で出るため、再試行が推測ではなく指定された修復になる。
  • 任意のプレビューは127.0.0.1のランダムなポートでのみ開き、最新の候補がすべてのゲートを通ったときだけ画面が更新される。
  • 動きの効果は依頼したときだけ有効になり、標準の出力は静止である。
  • 目視レビューは自動検査とは別だとREADMEは記している。

コードから描いた図の根拠 — SRC nと固定されたコミット

リポジトリを読んで描くとき、最大の問いは図の各ボックスがコードのどこに対応するかである。READMEはこれを根拠表示という任意機能として扱う。依頼したときだけ有効になり、有効なら根拠のあるアーキテクチャのノードがSRC nという印を付け、一つの公開コミットに固定されたファイルと行範囲を開く。ファイルの位置はGitで確認されたものだとREADMEは説明する。依頼しなかった通常の成果物は、出典のない状態のままである。

実例としてREADMEは公開リポジトリmco-org/mcoを挙げる。コミット9f1a1cfの時点でリポジトリをたどり、ランタイムアーキテクチャを描き、検査を経た地図として紹介している。結果のHTMLと型付きJSONの元データはリポジトリのドキュメントのディレクトリに一緒に公開されているので、図と元データを突き合わせられる。この事例から読み取れるのは、成果物が特定のコミットに結び付いていることだ。コードが変わればその図はそのコミット時点の事実となり、自動では更新されない。

根拠表示が何を保証するかは正確に区別する必要がある。SRC nはノードが参照するファイルと行範囲を開く。その範囲がノードの説明を裏付けるか、関係が実際の呼び出し経路かは、人が開いて読んで初めて分かる。根拠の存在と根拠の適合は別の層であり、自動化は前者を助け、後者は人に残す。

  • 印の付いたノードは、指しているファイルを開いて説明と合うか読む。
  • 印のないノードは根拠なしで描かれたものとして扱い、出典を尋ねる。
  • 固定されたコミットと現在のブランチの差を確認する。図はそのコミットのスナップショットである。
  • 8〜12個に絞った図で何のコンポーネントが落ちたかを、プロンプトを書いた人が記録する。
  • 外部依存と信頼境界は、プロンプトで求めた範囲でしか図に存在しない。

自動化されるものと人が確認するもの

ここまでの内容を段階ごとにまとめると次の表になる。左から二列目はREADMEとスキル定義に実際に書かれていることで、三列目と四列目は、その文書を根拠に人がすべきことと残る限界を整理した解釈である。文書にない項目は—にした。

段階READMEにあること人が確認すること限界
導入npxの導入コマンド、エージェント別の導入先、更新通知は任意Node.jsを実行できる環境か、全体の手順とプロンプト代替のどちらで入ったかClaude.aiとプロジェクトナレッジはNodeへのアクセスに左右される
入力の整理種類ごとにプロンプトへ入れる項目範囲、中核コンポーネント、主経路、境界を人が決めたか抜けた要素は図に表示されない
リポジトリの読み込みエージェントがコードを読み、アーキテクチャの初稿をJSONで書くノードと関係が実際のコードと合うか、根拠表示を依頼したか—
検証スキーマ、レイアウト、HTML/SVG、経路、ラベル間隔の検査と原子的な置換終了コードと診断JSONを、エージェントの要約でなく原文で見る形式の整合であり、事実の一致ではない
根拠表示SRC nの印と固定コミットのファイル・行範囲範囲が説明を裏付けるか開いて読む特定の公開コミットに結び付く
探索と共有ノード検索、経路追跡、到達範囲、共有カード、単一HTML受け取る人が図を確定した設計と誤解しないか到達範囲は記述された関係であり、ランタイムへの影響ではない
変更の比較Before、Delta、Afterのスナップショットと機械の受領票二つのスナップショットが同じ基準で書かれたか影響、リスク、マージの安全性は推論しない

表の要点は、自動化が形式と再現性に強く、内容の真実性は人に渡すということである。検証ゲートは図が壊れていないことを証明するが、図が正しいことは証明しない。これは欠陥ではなく、文書が自ら引いた線だ。スキル定義が目視レビューを自動検査と別に置き、READMEが到達範囲の書き出しにランタイムへの影響を主張しないという但し書きを付けるのは、そのためである。

  • 図がきれいに出たことは、検証の通過とは関係があってもコードとの一致とは関係がない。
  • エージェントが最終応答に書いた成功報告より、終了コードと診断JSONが優先する。
  • 同じリポジトリを二度描いてノード構成が変わるか比べると、判断が揺れる箇所が見える。この記事の根拠資料にはそのような再現結果がないため、試す価値のある手順としてのみ書く。
  • 共有前に図の題名の横へ基準コミットと作成日を書いておくと、古い図が最新と読まれることが減る。
  • セキュリティ境界や個人情報の流れを扱った図は、担当者の確認を別に経る。

図が語らないこと — 記述された関係とランタイムへの影響

Archifyが目に見えて気を配っている部分は、インタラクションが何を主張するかである。READMEはこれを誠実なインタラクションと呼ぶ。フォーカス、上流と下流の到達範囲、正確な経路、役割の比較、ストーリーは、作者が書いたノードと関係だけを再利用し、トポロジーを作り出したりランタイムへの影響を主張したりしない。ノードを選んで下流の到達範囲を有効にすると、そのノードの先へ続く線が強調されるが、それはJSONに書かれた関係をたどった結果である。障害が実際にどこまで広がるかの予測ではない。

この区別は、人が図を読む態度に直結する。画面で下流が広く強調されたノードを見て、これが影響範囲だと読めば、図が語っていないことを読んだことになる。実際の呼び出しが条件付きか、非同期か、使われていない経路かは図にない。デプロイの所有権プロファイルも同じ姿勢を示す。記述された所有者、リージョンの配置、非公開データベースの範囲、名前の付いた境界の横断のどれかが欠けると失敗する方式で、暗黙には有効にならず、実際のインフラを調べることもないとREADMEは書いている。

変更の比較も同じ原則である。Architecture Deltaは、検証済みのBefore、Delta、Afterのスナップショットを機械の受領票とともに比べ、記述された変更を選んだり、長さの限られたレビュー再生を見たりできる。影響、リスク、マージの安全性は推論しない。比較コマンドはREADMEに次のように書かれている。

node archify/bin/archify.mjs compare architecture base.json head.json architecture-delta.html --json

このコマンドは二つのJSONを入力に取る。二つのJSONは人やエージェントがそれぞれの時点の構造を記述したものなので、比較の正確さは二つの記述の品質に従属する。コードレビューでこの画面を使うなら、変更された事実を素早く見渡す用途にとどめ、承認判断の根拠にしないほうが文書の引いた線に合う。

  • 到達範囲は記述された関係をたどった結果であり、ランタイムへの影響の予測ではない。
  • 経路の追跡は図に描かれた経路を示すだけで、実際のトラフィックがそこを流れる証拠ではない。
  • デプロイ所有権プロファイルは記述された情報の抜けを防ぐだけで、実インフラとの一致は調べない。
  • Deltaの画面は変更された事実を並べるだけで、リスクを評価しない。

範囲外にされたことと運用上の性質

READMEは、やらないことも明確に書いている。Mermaidの自動解析、汎用の自動レイアウト、ホスティング共有、WYSIWYG編集は意図的に現在の範囲外である。汎用の作図エディタでもMermaidのテーマでもなく、技術的な意図をコミュニケーションの成果物に変えるツールだと自らを定義している。配置も自動レイアウトのアルゴリズムではなく、エージェントが階層、間隔、経路、強調を判断して決め、共有される自動端点だけを決定的に分散させて、矢印が一点に集まらないようにするという説明だ。すでにMermaidやdraw.ioの資産を持つチームにとっては、それを直接読み込む機能がないという意味であり、既存資産を改めて説明する作業が要る。

運用上の性質もいくつか書かれている。

  • 更新確認。 固定の安定版マニフェストにGETして任意の通知を出すだけで、ダウンロードも導入もしない。成功した確認は約24時間待ち、失敗は6時間後に再試行してその後は24時間間隔である。サーバーはIPや時刻といった通常のHTTPメタデータを見るが、バージョン、エージェント、プロジェクトデータ、プロンプト、アカウントやデバイスの識別子は受け取らないと記されている。ARCHIFY_UPDATE_CHECK_DISABLED=1 でネットワークと通知状態の書き込みを止める。
  • 言語。 meta.locale はページタイトル、凡例、状態とエラー、アクセシビリティの文言、HTML/SVGのlang属性をローカライズするが、記述された内容は翻訳しない。英語と簡体字中国語(zh-CN)が組み込みで、それ以外の言語は翻訳テーブルを与えないと英語に置き換わり、その旨が表示される。韓国語のユーザーは図のタイトルと凡例が英語で出ることを見込んでおく必要がある。
  • アクセシビリティ。 読者が操作する動きの効果は有限で、システムの動き軽減設定に従い、標準の書き出しには入らない。
  • ビューアの操作。 ？キーがヘルプ、スラッシュがノード検索、Rが経路、Lが役割比較、Mが概観、Fが発表モードである。リンクのハッシュでフォーカス、関係、経路、レンズの状態を復元できる。
  • 保守の状態。 リポジトリのバージョン表示は3.0.1でライセンスはMIT、コミュニティ連携は公式製品でないと明記されている。GeekNewsのコメントには、開発中に可視化を頼むとこのスキルで描いてくれるという使用感があるが、個人の経験であり性能の根拠にはならない。

まとめると、Archifyを導入するチームが決めるのは三つである。図を誰がレビューするか、図に基準コミットと日付をどう付けるか、更新確認のようなネットワーク動作を許すか。ツールが形式を検証し、人が内容を検証するという分業が、文書から読み取れる設計である。

確認できなかったこと

  • 実際のリポジトリでスキルを実行した結果。この記事はREADME、スキル定義、紹介記事の記述だけを扱い、生成された図の正確さを測った資料はない。
  • スキル定義の全文のうち、リポジトリ作成手順(Repository authoring)の詳細。要約された規則だけを根拠にした。
  • Node.jsの最低要件バージョン。READMEでバージョン条件があるのはコミュニティ連携の項目だけで、基本スキルの条件は見当たらなかった。
  • Claude.aiのサンドボックスで検証手順が実際に動く範囲。READMEはNode.jsへのアクセス次第とだけ書いている。
  • GitHubトレンドの順位とメディア紹介に関するREADMEの記述。作者の投稿に基づく内容なので、この記事では事実として引用していない。
  • GeekNewsの掲載日の正確な値。ページには相対的な時刻しか表示されない。
