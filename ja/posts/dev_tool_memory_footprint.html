開発ツールはなぜメモリを食うのか - 言語サーバーのメモリの原理と代償

補完が即座に返るために何を載せるのか、そしてそれを削ると何を失うのか

2026年8月23日 開発・インフラ

はじめに: 一行も打っていないのにファンが回る理由

エディタを開いたままコーヒーを取りに行って戻ると、ノートパソコンが熱くなっています。ビデオ会議のウィンドウをもう一つ開いた途端、さっきまで快適だった補完が一拍遅れて出るようになります。ブランチを切り替えた直後は三十秒ほどエディタごと固まります。この三つの場面はすべて同じ場所から来ています。ウィンドウの裏で動く言語サーバーが、プロジェクト全体を読み込んで自分用の地図を描き直している最中なのです。

2026年8月、Rust 向けの代替言語サーバーが、メモリを100分の1しか使わないという見出しで開発者コミュニティに現れました。この記事はそのツールの紹介でも宣伝でもありません。その見出しが触れた本当の問いを扱います。開発ツールのメモリはなぜ増え、増えたメモリは正確に何を壊すのか。そしてそれを削ろうとするとき、私たちが静かに差し出しているものは何なのか。

まず発表された内容を確認できた条件とともに短く押さえ、そこからは個別のツールを離れて原理に入ります。

1. 何が発表されたのか - そして100倍とは何と何の比か

話題になっているのは Rust Glancer という Rust 言語サーバーの実装です。プロジェクトのサイトは自らを rust-analyzer とは異なるアプローチだと紹介し、すべてをメモリに置いて動的に再計算する代わりに凍結されたワークスペースを用い、それをファイルシステムへ逃がせると説明しています。性能面の多少の損を認める代わりに極端なメモリ効率と即座の再起動を得るというのがプロジェクト自身の要約で、開発期間は約4か月としています。

見出しの倍率をそのまま持ち出す前に、何を何と比べた値なのかを切り分けておく必要があります。文書で実際に確認できるのは次のとおりです。

  • メモリ側の数字は目標値です。文書は妥当な規模のプロジェクトで100MB未満を目標とすると書いており、その妥当な規模が何を指すのかは明かされていません。
  • 比較対象側の数字は著者の逸話です。複数のプロジェクトを同じエディタ二本で同時に開いた状態で rust-analyzer が16GBを使っていたという記述で、インスタンス一つの常駐量ではなくその構成全体の合計です。
  • プロジェクトが公開した並列比較の表にメモリ列はありません。表は索引の所要時間だけを載せています。
  • したがって100倍は、100MBという目標と16GBという逸話を割った値に近いものです。同じリポジトリを同じマシンで両サーバーから開き常駐メモリを並べて計測した公開数値は存在しません。

公開されている時間の比較表は次のとおりです。あくまでメモリではなく索引時間であり、二台の MacBook で計測したという条件が付きます。

  • MacBook Pro M4 Max 36GB: Glancer は基本5秒・全体8秒、rust-analyzer は基本6秒・全体13秒
  • MacBook Pro M1 8GB: Glancer は基本6秒・全体9秒、rust-analyzer は基本7秒・全体14秒

代償も文書に書かれています。新しく書いた import や構造体、トレイトはドキュメントを保存するまで索引されません。入力中は現在の本文だけを浅く見て以前の索引を再利用します。ビルドスクリプトや手続きマクロを実際に実行して得る情報、nightly 専用機能はまだ扱わないと明記しています。これらの文は欠点ではなく信号です。倍率は条件が付いて初めて意味を持ち、条件を理解するにはそもそもなぜそれほどのメモリが必要だったのかを知る必要があります。

2. 言語サーバーがメモリを使う理由 - 即時性の対価

言語サーバープロトコルは掛け算の問題を割り算に変えるために作られました。M個の言語とN個のエディタの組み合わせごとに言語対応を実装する代わりに、言語ごとにサーバーを一つ置きエディタは標準プロトコルで会話します。補完、定義ジャンプ、参照検索、リネーム、診断がすべてサーバー側の責務になります。

ここで誤解が一つ生まれます。メモリを食っているのはソースコードだろうという思い込みです。rust-analyzer のアーキテクチャ文書はこの点をはっきり書いています。解析器は入力データをすべてメモリに置き入出力をしないが、その入力はソースコードであり大きくてもせいぜい数十メガバイトなので全部抱えていても問題ない、と。ギガバイトを生むのはソースではなくソースから取り出したものたちです。

メモリに載るものこれがあって初めてできることないとどうなるか
構文木カーソル位置の文法的文脈の把握補完が文字列マッチ程度に退化する
名前解決の結果とモジュールスコープ表その識別子がどの定義を指すかの決定定義ジャンプとリネームが当て推量になる
型推論の結果ドットの後に何が来られるかの計算メソッド候補が不正確または空になる
シンボル索引と逆参照索引参照検索、ワークスペース全体の検索問い合わせのたびにプロジェクト全体を走査する
依存グラフ変更時に何を再計算するかの判断一文字直しただけで全体を再解析する
メモ化された中間結果同じ問い合わせを二度計算しないこと打鍵のたびに同じ作業を繰り返す

最後の行が特に重要です。現代の言語サーバーは増分計算エンジンです。rust-analyzer はこの目的で Salsa を使っており、その設計の中核となる不変条件は関数本体の中で入力することが大域的な派生データを無効化しないというものです。この約束を守るために、ファイルごとに関数本体の変更と無関係な要約構造を別に持ち、モジュールスコープを別の表として索引し、構文木は必要になったときだけ解析します。

構造が細かく分かれるほど再計算の範囲は狭くなりますが、その細片と細片のキャッシュこそがメモリです。ここでこの分野の根本的な取引が姿を現します。速い再計算を買うためにメモリを支払っているのです。補完が瞬く間に出るなら、その答えの材料の大半はすでに RAM に用意されていたということです。

3. 精度とメモリの交換 - この記事の中心

全部載せておけば正確で速い。問題は精度と遅延とメモリの三つを同時に最大化できないことです。軽いツールは魔法を使ったのではなく三つのうち一つを手放したのであり、何を手放したかがそのツールの性格を決めます。

3.1 何を手放すのか

  • 遅延ロード — 必要になったときだけ計算します。総メモリは減りますが最初の問い合わせが遅くなります。最初の一回だけ3秒かかる現象は平均応答時間の統計にはほとんど出ませんが、人はまさにその3秒を覚えています。
  • 部分索引 — ワークスペースは精密に、依存ライブラリは要約だけ持ちます。大規模リポジトリでの削減幅は最大ですが、ライブラリ内部へ入っていく定義ジャンプがどこかの深さで途切れます。
  • ディスクキャッシュ — 結果をファイルに逃がし必要なときに読み込みます。再起動が劇的に速くなる代わりにキャッシュがいつ古くなったかを判定する規則が要り、その規則が保守的だと作り直してばかりになり緩いと誤った答えを返します。
  • スナップショット凍結 — 入力中は浅く見て保存時に全体解析を回します。削減幅は最も大きい一方でいま作ったものがまだ存在しない状態が生まれます。

3.2 手放しているのはたいてい時間軸である

四つを並べると共通点が見えます。軽いツールが実際に手放しているのは機能一覧ではなくいまこの瞬間の精度である場合が多いのです。コードは保存と保存の間にも変わり続けるのに索引は最後の保存時点で止まっており、この隔たりが広がるほどツールは少しずつ過去のコードについて答えるようになります。

構造体を新しく定義し保存しないまま別のファイルへ移ってその名前を打っても候補に出てきません。保存を押せばすぐ消えるので不具合として報告されることもありません。だからこの費用はベンチマークに現れず習慣によって体感が完全に分かれます。二、三行ごとに保存する人にはほぼ存在しない費用であり、大きく書いてから後で保存する人には毎日ぶつかる壁です。

3.3 現実的な答えは層を分けることである

C/C++ 向け言語サーバーである clangd の構造がこの折衷の良い例です。索引を一塊にせず複数の層を重ねて一つに見せます。最上層にはいま編集中のファイルを担当する動的索引があり、その下にプロジェクト全体を走査する背景索引があります。設計文書はこの構造のおかげで背景索引がまだ終わっていなくても作業中のファイルの相互参照は利用できると説明しています。

学ぶべきは個別の実装ではなく原則です。最新でなければならないものとそうでなくてよいものを区別した瞬間、メモリに置くものとディスクに置くものが自然に分かれます。カーソルのあるファイルはミリ秒単位で最新である必要がありますが、半年触っていないベンダーディレクトリはそうではありません。すべてを同じ鮮度で保とうとするときにメモリが破裂します。

4. 開発マシンのメモリが足りなくなると実際に起きること

メモリ使用量の数字が大きいこと自体は誰も傷つけません。有害なのはその数字が利用可能量を超えたときに始まる連鎖であり、それには順序があります。

  • 回収とスワップ — カーネルが使用頻度の低いページから追い出します。ここに最初の罠があります。ps のマニュアルは RSS をスワップされていない物理メモリと定義するため、メモリが逼迫するほどプロセスの RSS はかえって減って見えます。
  • 圧縮 — macOS はスワップの前にメモリ圧縮を使います。Activity Monitor の Compressed がより多くの RAM を確保するために圧縮した量です。圧縮されたページは触るたびに CPU を使うため、メモリの問題が CPU 使用率に化けて現れます。
  • ワーキングセットの縮小 — Windows はプロセスのワーキングセットからページを削ります。ワーキングセットとは仮想アドレス空間のうちいま物理メモリに常駐しているページのことで、削られたページに再び触れるとハードページフォールトが起きバッキングストアから読み直します。補完一回がディスク読み取りになる地点です。
  • ツール同士の競合 — エディタ本体と拡張ホスト、型検査器、バンドラの監視プロセス、コンテナランタイム、タブ40個のブラウザが同じ RAM を分け合います。互いに積んだページキャッシュを追い出し合うので、どれか一つを減らすと別のものが速くなります。
  • コンテナの上限 — 開発コンテナや CI では cgroup v2 が壁を立てます。memory.high を超えるとプロセスはスロットルされ強い回収圧力を受けますが、カーネル文書はこの線を越えてもOOM キラーは呼ばれないと明言しています。memory.max に達しこれ以上減らせなくなって初めて、そのグループ内で OOM キラーが動きます。
  • 発熱とバッテリー — 圧縮、回収、再索引はすべて CPU の作業です。メモリの問題はノートパソコンでは熱の問題に翻訳され、ノートパソコンを選ぶときに RAM 容量を先に見よという助言はここから出てきます。

CI で言語サーバーや型検査器が理由もなく消える現象に遭ったなら、ログより先に見る場所があります。cgroup v2 の memory.events ファイルは low、high、max、oom、oom_kill のカウンタを持っており、oom_kill が上がっていればそれで一件落着です。

圧力そのものを直接測る指標もあります。Linux の PSI はシステム全体では /proc/pressure/memory、cgroup 単位では memory.pressure として公開されます。some の行は少なくとも一部のタスクがその資源のせいで止まっていた時間の割合、full の行は非アイドルのタスクがすべて同時に止まっていた時間の割合です。full が上がっているならそれは遅いのではなくスラッシングです。10秒、60秒、300秒の平均が一緒に出るので、瞬間的な跳ねと持続的な傾向を一画面で見分けられます。

5. モノレポと大規模リポジトリ - 規模は線形に増えない

ファイルが二倍になればメモリも二倍になりそうですが、実際にはもっと急に上がります。理由はデータ構造の性質にあります。

  • 参照関係はシンボルの組に近いものです。シンボル数はファイル数に比例しますが、参照検索と安全なリネームを即座に行うには誰が誰を使っているかの逆方向索引が必要で、この索引はファイル数より速く育ちます。
  • 無効化の範囲が広がります。依存グラフが深くなるほど、共通の型を一つ直したときに再計算すべき下流の範囲が大きくなります。だから大きなリポジトリほどキャッシュをより大きく取りたくなります。
  • 生成コードが割り込みます。マクロ展開、コード生成、スキーマから作られる型はソースにありません。解析対象の実際の大きさがリポジトリの見かけの大きさとずれていきます。
  • インスタンスが掛け算になります。rust-analyzer の文書は一つのプロセスが複数のプロジェクトを扱えると書いていますが、エディタの窓をプロジェクトごとに開くとその利点は消え、サーバーも窓の数だけ増えます。1節の16GBの逸話がまさにこの構成です。

この規模で何が起きるかは clangd の設計文書が淡々と記しています。大規模プロジェクトの背景索引は通常数時間かかり数ギガバイトの RAM を使うとのことです。だから clangd はあらかじめ作っておいた静的索引を付ける選択肢を用意し、リモート索引機能は全体索引が招く大きなメモリ負担を別のマシンへ移すために作られました。

ここから規模の答えが出ます。リポジトリが一定の大きさを超えると個人のマシンでのチューニングで凌ぐ段階は終わり、索引を開発マシンの外へ出すことが残る方向になります。索引サーバー一台がメンバー全員の RAM 増設より安くなる時点が来ますが、その計算はメモリ価格が大きく上がる局面で再び揺らぎます。

6. 測り方 - どの数字を見るべきか

メモリの話がすれ違う理由の大半は、異なる数字を同じ名前で呼んでいることにあります。定義が違えば同じ状況から違う結論が出ます。

読む順序があります。順序を守れば誤診の大半は消えます。

  • まずシステムの余裕から — Linux なら available、macOS ならメモリ圧力のグラフを先に見ます。ここに余裕があるなら、プロセス一つが2GBを使っていても問題ではなく設計です。
  • 余裕がなければ持ち分を分ける — PSS の合計で誰がどれだけ占めているかを見ます。RSS を単純合計すると共有分が重複して物理メモリより大きな値になります。
  • 指名したプロセスは RSS と Swap を一緒に — 片方だけ見ると逼迫時に正確に逆の読み方をします。
  • ツール自身の計測を先に探す — Go の言語サーバーである gopls は使用量が1GBを超えると一時ディレクトリへメモリのデバッグ情報を自動的に残し、デバッグサーバーを起動するとプロファイルとメモリ状況をブラウザで見られるようにしています。

エディタが固まった時刻とシステムログの回収記録を並べる作業が残るなら、そのとき使う道具はLinux ログ分析コマンドの側とそのまま重なります。

7. 削る手法とそれぞれが払う代償

メモリを削る方法はすでにいくつもの筋道に整理されており、無料のものは一つもありません。すべて精度、遅延、運用の複雑さのいずれかをメモリと交換します。

手法何をするのか得るもの払うもの
ディスクへ逃がす解析結果をファイルに置き必要なときだけ読み込む常駐メモリの減少、再起動時間の短縮初回アクセスの遅延、キャッシュ無効化規則の複雑さ、ディスク書き込み
保存時索引入力中は浅く、保存時に全体解析メモリと CPU の削減幅が最も大きい保存前の新項目がツールから見えない
部分索引・遅延索引ワークスペースは精密に、依存は要約だけ大規模リポジトリで効果が大きいライブラリ内部の探索がどこかの深さで途切れる
圧縮表現インターン化、ビットパッキング、文字列プール精度の損失がない実装の複雑さ、アクセスごとの若干の CPU

リモート索引共有索引を別サーバーから提供チーム全体が索引の費用を一度だけ払うインフラとアクセス制御、鮮度の管理

実務で順序を付けるなら最後の行が先です。範囲除外は設定一行で終わり、たいていは node_modules や target のようにそもそも解析する必要のないものを外す作業です。次がプロセス分離と上限設定です。圧縮表現や索引構造の変更はツールを作る側の仕事であり、使う側の選択肢ではありません。

8. 反対側も正直に - そのメモリで何を買ったのか

軽いことが無条件に良いのなら、私たちはいまだにテキスト検索で定義を探しているはずです。この十年で開発ツールのメモリ使用量が増えたのは怠慢の結果ではなく機能が増えた結果です。

  • 型に基づく補完 — 名前の似た候補を並べるのではなく、その位置で実際に成り立つものだけを見せます。型推論の結果がメモリにあって初めて可能です。
  • 安全なリネーム — 文字列置換はコメントやリテラルまで壊します。参照グラフに基づくリネームは逆参照索引があって成立します。
  • 保存前の診断 — ビルドを回さず入力中に誤りを見せるのは増分計算キャッシュの仕事です。
  • 構造の探索 — 参照検索、呼び出し階層、実装検索はプロジェクト全体の索引なしには存在できない機能です。
  • リファクタリングの自動化 — メソッド抽出、インライン化、シグネチャ変更は型と参照を同時に知って初めて安全です。

ですから判断基準は使用量の絶対値ではありません。そのメモリで何を買ったのかが見えないときに初めて問題になります。RAM 8GB のマシンで2GBを使う言語サーバーはマシンの半分を持っていくことであり、64GB のマシンでの同じ2GBは優れた取引です。付け加えると、軽いツールが常に速いわけでもありません。キャッシュを少なく持てば繰り返しの問い合わせのたびに計算し直しディスクから読み込む時間が乗ります。索引時間と応答時間とメモリは別々の軸であり、一つを良くすると別の一つが悪くなる区間が必ずあります。

9. ツールを選ぶときに実際に見るもの

宣伝文句を取り除くと判断材料はさほど多く残りません。次の六つで十分です。

  • 倍率ではなく条件 — どのリポジトリを、どのマシンで、どの設定で測ったのか。条件のない倍率は情報ではなく印象です。
  • 目標値と実測値の区別 — 目標100MBと実測100MBは別の文です。文書が二つを混ぜているならそれ自体が情報です。
  • 精度の境界が文書にあるか — 何がいつまで索引されないのかを明かすプロジェクトは信頼に足ります。隠す側のほうがはるかに危険です。
  • 自分の作業習慣との相性 — 保存時索引の体感は、頻繁に保存する人と先延ばしにする人で正反対に出ます。他人の感想より自分の習慣のほうが正確な予測変数です。
  • 平均ではなく最悪の瞬間 — 初回索引中、大量のブランチ切り替え直後、依存更新直後の山を見ます。
  • 逃げ道があるか — 索引範囲の除外、メモリ上限、再起動の費用。上限を掛けられるツールは悪い日にもマシンを生かしておいてくれます。

ツールを替える前に同じ RAM を使っている他のものを先に数えるほうがたいてい速いです。エディタ拡張20個、常駐する監視プロセス三つ四つ、そしてブラウザ。言語サーバーを替えて1GBを節約するより、こちらから3GB出てくることのほうが多いのです。

確認できなかったこと

この記事で根拠を示せなかった項目を一か所にまとめます。

  • 同じリポジトリを同じマシンで二つの Rust 言語サーバーから開き常駐メモリを並べて計測した公開の表。公開されている並列比較は索引の所要時間だけです。
  • 目標値が前提とする妥当な規模のプロジェクトが何であるか。行数、クレート数、依存数のいずれでも定義されていません。
  • rust-analyzer の典型的な常駐メモリについての公式な数値。文書のトラブルシューティングのページにはメモリの項目自体がありません。
  • リポジトリ規模に対するメモリ増加曲線を実際に測った公開ベンチマーク。5節の線形ではないという記述はデータ構造の性質から導いた論であって計測値ではありません。
  • macOS Activity Monitor のプロセス別メモリ列がどの台帳を読んでいるのか。アップルのサポート文書はシステム単位の項目だけを定義しています。

結論: メモリは点数ではなく予算である

言語サーバーのメモリ使用量を、低いほうが勝つ得点表として読むと判断を誤ります。あの数字は点数ではなく予算です。予算の大きいツールはその金で即時性と精度を買い、予算の小さいツールはそのうち一部を買わないことにしたのです。どちらが正しいかは、マシンの RAM 容量、リポジトリの大きさ、そして保存ボタンを押す個人の習慣が決めます。

今日できることは三つです。いま使っているツールがどれだけ使っているかをRSS とスワップを一緒に確認し、システムの余裕が本当に足りないかを available やメモリ圧力で判定し、足りないなら索引範囲の除外のように代償のほとんどないものから手を付けます。ツールの交換はその後の選択肢です。

そして新しいツールが印象的な倍率を掲げて現れるたび、同じ問いを投げればよいのです。何と何の比か、どんな条件で測ったのか、その代わりに何を手放したのか。三つの問いに文書で答えるプロジェクトはおおむね信用でき、答えないプロジェクトは数字がどれほど大きくてもまだ判断する材料がない状態です。
