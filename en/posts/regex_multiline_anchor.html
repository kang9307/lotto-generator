Introduction - the multiline flag is not a switch that adds support for many lines

A regex engine takes a string that contains many lines as one string. By default ^ corresponds to the start of the string and $ to the end of the string (in Python, .NET and Perl, including before an end newline), and when the multiline flag is on (Python re.M, JavaScript m, .NET Multiline, Perl /m) they also correspond at line boundaries. So, despite the name, according to the Python documentation the only thing the flag changes is whether the two anchors recognize line boundaries, not any ability to process many lines. Whether the dot (.) crosses a newline is decided by a separate switch (s), covered in section 8.

Two places catch people in practice. One is where $ corresponds when the input ends with a single newline; the other is the case where, with \r\n (CRLF) instead of \n, $ does not correspond before the \r. The answers differ by tool in both. The overall dialect differences between languages and tools are covered in the article on portable regular expressions, and the trouble the CR byte causes in shell scripts and git is covered in the article on CRLF and LF; here only the line-boundary interpretation of anchors and the results on CRLF input are compared on the same input.

The questions covered are the following.

  • Where do ^ and $ correspond by default, and how does the multiline flag change that?
  • Are the results of $ and ^ before and after a newline at the end of the input the same across tools?
  • Which tools have \A, \z and \Z, and does the multiline flag affect them?
  • Are anchors already per line in grep, sed and awk?
  • Where does $ correspond on CRLF input, and how is it handled?

Two identical inputs - LF and CRLF, and a way to see positions

Every demonstration uses the same two inputs. The LF input is a1\nb2\n (two lines with one newline at the end), and the CRLF input is a1\r\nb2\r\n. The way to see where an anchor corresponded is the same everywhere: a string with < inserted where ^ corresponded and > where $ corresponded is printed in escaped form. For example, 'a1\nb2>\n>' means $ corresponded in two places: after b2 and at the very end of the string. There are three ways to read the output below.

  • Whether a > for $ is also printed before the final \n (correspondence before the end newline).
  • Whether a < for ^ is also printed at the empty position after the final \n (correspondence after the end newline).
  • On CRLF, whether the > is printed before the \r or between the \r and the \n.

The Python 3.13 documentation for re.M reads: "When specified, the pattern character '^' matches at the beginning of the string and at the beginning of each line (immediately following each newline); and the pattern character '$' matches at the end of the string and at the end of each line (immediately preceding each newline). By default, '^' matches only at the beginning of the string, and '$' only at the end of the string and immediately before the newline (if any) at the end of the string." (source: docs.python.org/3.13/library/re.html) The output has the same shape as this passage.

  • LF by default: $ gave 'a1\nb2>\n>', corresponding after b2 (before the end newline) and at the very end. ^ corresponds only at the very start.
  • LF with re.MULTILINE: ^ gave '<a1\n<b2\n<', three places, including the empty position after the final \n. $ gave 'a1>\nb2>\n>', one per line plus the very end.
  • CRLF: $ gave 'a1\r>\nb2\r>\n>', corresponding between the \r and the \n. The \r is treated as a character inside the line.
  • So on CRLF, ^\w\d$ (re.M) gives [], zero matches. ^\w\d\r?$ matches both lines but the values contain the \r, as in 'a1\r'. splitlines() gave ['a1', 'b2'], treating \r\n as one line boundary.
  • \A and \Z: \A corresponds at the very start only, and \Z gave 'a1\nb2\n>', the very end only, with or without re.M. In 3.13, \Z does not correspond before the end newline.
  • \z is re.error: bad escape \z in 3.13. The later documentation describes \z as "Added in version 3.14" and \Z as "The same as \z. For compatibility with old Python versions." (the version notation of docs.python.org/3/library/re.html for 3.14 and later).

The MDN documentation on input boundary assertions reads: "If the m flag is set, ^ also matches if the character to the left is a line terminator character, and $ also matches if the character to the right is a line terminator." (source: the Input boundary assertion page on developer.mozilla.org) A note on the same page reads: "To match the start and end of the entire string in m mode, use the buffer boundary assertions \A, \z, and \Z." The output is as follows.

  • LF by default: $ gave "a1\nb2\n>", the very end only. Unlike Python, it did not correspond before the end newline.
  • LF with the m flag: the same shape as Python. ^ also corresponds at the empty position after the last newline ("<a1\n<b2\n<").
  • CRLF with the m flag: ^ gave "<a1\r<\n<b2\r<\n<", also corresponding between the \r and the \n, and $ gave "a1>\r>\nb2>\r>\n>", corresponding both before the \r and before the \n. The \r is treated as a line terminator character.
  • As a result, even on CRLF, /^\w\d$/gm matched both lines as ["a1","b2"]. By contrast, /^.*$/gm gave ["a1","","b2","",""], with empty strings mixed in. The dot did not pass the line terminator \r, and the position between \r and \n came out as a separate empty-line match.
  • The line terminators of the m flag are not only \n. ^ corresponded after \u2028 and after \r ("<a<LS><b", "<a\r<b") and did not correspond after a vertical tab ("<a<VT>b").
  • \A: in this Node, without the u flag it was treated as the character A and matched 'Aa1\n' (the second value of the false true output), and with the u flag it gave SyntaxError: Invalid regular expression: /\Aa1/u: Invalid escape. Unlike the MDN note, \A did not work as a buffer boundary assertion in this Node v22.16.0.

The Microsoft Learn documentation on anchors states the CRLF situation of $ directly: "Note that $ is satisfied at \n but not at \r\n (the combination of carriage return and newline characters, or CR/LF). To handle the CR/LF character combination, include \r?$ in the regular expression pattern. Note that \r?$ will include any \r in the match." It also defines \Z as "The match must occur at the end of the string, or before \n at the end of the string" and \z as "The match must occur at the end of the string only", and says \Z is "identical to the $ anchor, except that \Z ignores the RegexOptions.Multiline option". (source: the Anchors in regular expressions page on learn.microsoft.com)

  • The default is the same as Python. $ corresponds in two places, before the end newline and at the very end (a1\nb2>\n>), and with Multiline the ^ corresponds in three places, including the empty position after the last newline.
  • \Z corresponds at the same places as $ (a1\nb2>\n>) and gives the same result with Multiline. \z is the very end only. The output agrees with the definitions in the documentation.
  • CRLF: $ corresponds after the \r, as in a1\r>\nb2\r>\n>. ^\w\d$ (Multiline) gave 0 matches, and ^\w\d\r?$ gave 2, with the values a1\r,b2\r including the \r. This agrees with "\r?$ will include any \r in the match" in the documentation.
  • The inline (?m) had the same effect in the PowerShell -replace and -match operators (-match '(?m)^b2$' gave True on LF and False on CRLF).
  • The documentation says that from .NET 11 on, RegexOptions.AnyNewLine lets $ recognize \r\n as one unit. In the list of RegexOptions enumeration names on 5.1 of this PC, that item was absent (the last line of the output).

perlre describes /m as "change "^" and "$" from matching the start of the string's first line and the end of its last line to matching the start and end of each line within the string", \Z as "Match only at end of string, or before newline at the end", and \z as "Match only at end of string". (source: perldoc.perl.org/perlre)

  • The defaults and $, \Z and \z corresponded at the same places as in Python and .NET (a1\nb2>\n>, with \z at the very end).
  • The difference is ^ under /m. On LF it gave <a1\n<b2\n, two places only, and did not correspond at the empty position after the last newline where Python, JavaScript and .NET did.
  • CRLF is the same situation as Python. ^(\w\d)$ gave an empty list and ^(\w\d)\r?$ gave [a1,b2] (the value is a capture group, so it does not include the \r).

grep, sed and awk - on this PC the default mode removes the CR

In the output below, grep, sed and awk applied ^ and $ to each line without any flag. When two lines were joined into one block (when sed joined them with N), giving the M modifier made the anchors correspond at the line boundary. The script below creates files only inside a temporary folder made with mktemp -d and removes it at the end. od -c shows whether the CR remains as a byte.

# Work in a fresh temporary directory and remove it at the end.
                    T="$(mktemp -d)" || exit 1

  • grep -c '^b2$' gave 1 for both the LF and the CRLF file. Reading with grep -U (binary mode), however, gave 0 on CRLF, and the pattern with a CR in it, ^b2\r$, gave 1 on CRLF only. The Git Bash grep on this PC matches with the CR at the line end removed in its default mode.
  • In the default mode sed output no CR byte (<a1>\n), while with sed -b the result was <a1\r>\n, with the > placed after the CR. So with the CR remaining, $ corresponds after the \r and before the \n.
  • awk is the same. The default mode removed the CR, and with -v BINMODE=3 the CR remained.
  • sed 'N;s/^/</g' put the < only at the very start of the two joined lines (a1\nb2), and with the M modifier it was put before the second line as well, giving <a1\n<b2\n. M is the switch that makes ^ recognize line boundaries inside the joined block.
  • With the record separator changed to \001 so that awk reads the whole file as one record, ^ and $ corresponded once each, at the very start and very end of the record (<a1\nb2\n>).

The dot and the s flag - a different switch from the anchors

The output of the four languages ends with the same experiment. The pattern ^a1.*$ is applied to the LF input (a1\nb2\n), changing only the combination of switches. The result is the same in every tool.

SwitchResultMeaning
NoneNo match (Python [], JavaScript null, Perl (no match)).* stops at the end of the first line, and $ corresponds only at the very end (or before the end newline), so they do not connect
s (the dot includes newlines)The whole a1\nb2\n.* crosses the newline and reaches the $ at the very end
m (anchors recognize line boundaries)Only a1$ corresponds at the end of the first line, but the dot still cannot cross the newline
Both m and sThe whole a1\nb2\nThe dot crosses newlines and $ accepts both line ends and the very end, so the match runs to the longest side
  • With only m on, .* ends on the first line, and with only s on it goes to the very end of the string rather than to a line boundary. The two switches are independent.
  • Singleline in PowerShell and re.S in Python play the same role, and the output was the same.
  • So m is for matching line by line, s is for a single match that spans several lines, and both are turned on when both are needed.

Three things can be read down the columns of this table. First, only JavaScript has the very end as the default position of $. Second, only Perl differs on whether the multiline ^ corresponds at the empty position after the last newline. Third, the tools where ^\w\d$ matches the lines on CRLF are JavaScript and the default mode of grep on this PC, which reads with the input's CR removed (sed and awk were not run with this pattern). These three places are where the result changes when the same regular expression string is moved to another tool. General checks for moving patterns that use anchors are in the portability checklist article, and anchoring in shell globs (the difference between ls and grep) is covered in the article on globs versus regular expressions.

When $ misses on CRLF - three ways to deal with it: input, pattern, switch

ToolApproachResult seen in the output
PythonPut \r?$ in the pattern, or split lines first with splitlines()\r?$ matches both lines with the \r in the values; splitlines() gives ['a1', 'b2']
JavaScriptThe m flag treats \r as a line end, so $ is used as it is; patterns that use the dot filter out empty matches/^\w\d$/gm gives ["a1","b2"]; /^.*$/gm has empty strings mixed in
.NET (PowerShell)\r?$, as the documentation suggestsFrom 0 matches to 2, with the \r in the values
Perl\r?$From an empty list to [a1,b2] (the value is a capture group, so there is no \r in it)
grep, sed, awk (this PC)The default mode reads with the CR removed. To keep the CR, use grep -U, sed -b or awk -v BINMODE=3, and in that mode put the CR in the patternUnder grep -U, the pattern with a CR gave 1 match on CRLF
  • Normalizing the input (splitting the lines first, like Python splitlines()) means the pattern need not know the line-end characters, so the same pattern can be used on LF and CRLF as it is.
  • With the pattern side (\r?$), the \r comes along in the value, so it has to be trimmed before the value is compared or stored.
  • The switch side applies to JavaScript only. The same m flag treats \r as a line end, so a pattern written without CRLF in mind passes and breaks for the first time when moved to another language.
  • Where the CR comes from (how the file was saved, git settings, downloads) is covered at the byte level in the article on CRLF and LF.
  • That anchors are themselves zero-width assertions (MDN: "Both are assertions, so they don't consume any characters") puts them in the same family as lookarounds, whose uses are covered in the article on lookahead.

  • Results from PowerShell 7 (pwsh) and the .NET Core line. The only .NET regex run on this PC is that of Windows PowerShell 5.1.
