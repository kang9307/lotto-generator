tts-bench 등장 - 로컬 TTS 55종을 속도·청취·점수 3렌즈로 비교하는 오픈소스 벤치마크

어떤 하드웨어에서든 로컬 음성합성 모델을 고를 수 있게 만든 3가지 관점, 그리고 그 뒤에 있는 평가 방법론 읽기

2026-07-11 개발/인프라

서론: 55종의 목소리를 한 화면에 놓다

2026년 7월 기준, 텍스트를 음성으로 바꾸는 TTS(Text-to-Speech) 기술은 클라우드 API를 호출해 쓰던 시절을 지나, 개인 GPU는 물론 CPU만으로도 꽤 자연스러운 목소리를 만들어내는 로컬 실행 시대로 옮겨가고 있다. 이 흐름 한가운데서 눈에 띄는 오픈소스 프로젝트가 하나 등장했다. GitHub 사용자 5uck1ess가 공개한 tts-bench다. 이 프로젝트는 로컬에서 돌릴 수 있는 TTS 모델 55종을 Windows·macOS·Linux 환경에서 나란히 놓고, 속도(Speed)·청취(Listen)·점수(Scores)라는 세 가지 렌즈로 비교한다. hada(GeekNews)에도 소개되며 개발자 커뮤니티의 관심을 모았다.

이 글은 tts-bench가 무엇을 하는 프로젝트인지 소개하는 데서 멈추지 않는다. 왜 지금 로컬 TTS가 주목받는지, TTS 모델을 평가하는 일이 왜 생각보다 까다로운지, 그리고 그 어려움을 tts-bench가 어떤 접근으로 풀려 했는지를 본인 시각에서 짚어본다. 55종 모델의 순위표를 그대로 옮기는 일은 하지 않는다. 순위는 프로젝트 사이트에서 직접 최신 상태로 확인하는 편이 정확하다. 대신 이 글은 그 순위표 뒤에 있는 평가 방법론과, 로컬 TTS를 실무에 들일 때 무엇을 기준으로 판단해야 하는지에 집중한다.

1. 왜 지금 로컬 TTS인가

로컬 TTS가 다시 주목받는 이유는 네 가지로 요약된다.

1.1 프라이버시

텍스트를 클라우드 API로 보내면 그 내용이 외부 서버를 거친다. 의료 상담 녹취, 법률 문서 낭독, 개인 메모 읽어주기처럼 민감한 텍스트를 다루는 서비스라면, 데이터가 아예 기기 밖으로 나가지 않는 로컬 실행이 근본적으로 더 안전하다. 프롬프트가 어디서 처리되는지는 음질이나 가격과는 별개의, 1순위 고려사항이다.

1.2 비용 구조

클라우드 TTS는 대개 글자 수나 오디오 길이 단위로 과금된다. 팟캐스트 자동 생성, 대량 오디오북 변환, 24시간 돌아가는 안내 음성처럼 사용량이 많은 워크로드에서는 이 단가가 누적돼 비용 부담이 커진다. 로컬 TTS는 초기 하드웨어 투자 이후에는 추가 사용료가 없어, 고볼륨 워크로드일수록 손익분기 이후 단가 이점이 커진다.

1.3 오프라인 동작

네트워크가 불안정하거나 아예 없는 환경 - 임베디드 기기, 차량, 공장 설비, 격리망 - 에서는 클라우드 TTS 자체가 선택지가 되지 못한다. 로컬 TTS는 인터넷 연결 없이도 동작하며, 왕복 네트워크 지연이 없어 응답도 더 빠르다.

1.4 커스터마이징 자유

가중치를 직접 다루면 특정 도메인 용어 발음을 다듬거나, 특정 목소리로 미세조정하거나, 하드웨어에 맞춰 양자화하는 등 클로즈드 API에서는 불가능한 조정이 가능하다. 보이스클로닝 모델이라면 몇 초짜리 레퍼런스 음성만으로 특정 화자의 목소리를 재현하는 것도 자체 통제 아래 할 수 있다.

2. tts-bench란 무엇인가 - 55종을 3렌즈로 보다

tts-bench는 로컬에서 실행 가능한 TTS 모델을 14종의 사전 정의된 목소리 모델과 41종의 제로샷 보이스클로닝 모델, 합해서 55종을 대상으로 삼는다. 파라미터 규모는 수천만 단위의 초경량 모델부터 수십억 파라미터급 대형 모델까지 폭넓게 걸쳐 있고, 공개 시기도 최근 수년에 걸쳐 있다. 벤치마크는 세 대의 실측 장비 - 고성능 데스크톱 GPU, Apple Silicon, 별도의 데스크톱 GPU - 에서 CPU·CUDA·Apple Silicon 세 가지 실행 경로를 각각 측정한다. 설치는 uv 패키지 매니저와 Python 3.11 이상을 기반으로 하며, 전체 모델을 다 내려받으면 가상환경만 수십 기가바이트, 모델 가중치까지 합치면 100기가바이트를 훌쩍 넘는 저장공간이 필요하다. 벤치마크 코드는 MIT 라이선스로 공개돼 있고, 각 모델의 가중치 자체는 Apache 2.0·MIT·GPL-3.0·비상업(CC-BY-NC류) 등 저마다 다른 라이선스를 따른다.

tts-bench가 특히 흥미로운 지점은 결과를 하나의 점수로 뭉뚱그리지 않고, 속도·청취·점수라는 서로 다른 세 렌즈로 분리해 보여준다는 데 있다. 각 렌즈는 아래에서 따로 다룬다. 아울러 프로젝트는 블라인드 A/B 청취 테스트로 사람의 선호를 직접 모으는 보팅 아레나도 함께 운영한다. 어떤 모델인지 모른 채 두 음성 클립 중 하나를 고르는 방식이며, 그 결과는 실시간으로 갱신되는 Elo 선호도 순위에 반영된다. 이는 자동 지표만으로는 잡히지 않는 "그냥 듣기 좋은 목소리"라는 감각을 데이터로 축적하려는 시도로 읽을 수 있다.

3. TTS 모델 평가가 어려운 이유

3.1 속도·자연스러움·정확도의 3중 트레이드오프

TTS 모델 하나를 두고 "좋다"고 말하기 어려운 이유는, 좋음이라는 말 안에 서로 당기는 세 가지 축이 섞여 있기 때문이다. 첫째는 속도다. 텍스트를 넣고 첫 오디오가 나오기까지의 지연, 그리고 오디오 1초를 만드는 데 걸리는 연산 시간이다. 둘째는 자연스러움이다. 억양·리듬·숨소리 같은 운율이 사람 목소리에 얼마나 가까운가다. 셋째는 정확도다. 텍스트에 있는 단어를 빠뜨리거나 잘못 발음하지 않고 그대로 소리로 옮기는가다. 문제는 이 세 축이 대체로 트레이드오프 관계라는 점이다. 연산을 적게 써 빨리 만들면 운율이 단조로워지기 쉽고, 자연스러움을 끌어올리려 더 깊은 모델을 쓰면 실시간성이 떨어진다. 그래서 "가장 좋은 TTS 모델"이라는 단일 정답은 존재하기 어렵고, 워크로드가 무엇을 우선하느냐에 따라 정답이 바뀐다.

3.2 주관적 청취품질을 어떻게 객관화하나 - MOS와 UTMOS

자연스러움은 본질적으로 주관적이다. 이를 측정하는 오랜 표준이 MOS(Mean Opinion Score, 평균의견점수)다. 여러 사람이 합성 음성을 듣고 1점(나쁨)부터 5점(매우 좋음)까지 점수를 매긴 뒤 평균을 낸다. 문제는 이 방식이 사람을 모으고, 듣게 하고, 채점을 취합해야 하는 만큼 비용과 시간이 많이 든다는 점이다. 모델을 55종이나 비교하는 벤치마크에서 매번 사람 패널을 꾸리는 것은 현실적이지 않다.

그 대안으로 자리잡은 것이 UTMOS 같은 신경망 기반 자동 MOS 예측 모델이다. 사람이 실제로 매긴 MOS 데이터로 학습된 이 모델은, 음성 파형을 자기지도학습(SSL) 표현으로 변환한 뒤 여러 회귀 모델을 앙상블해 사람의 평가와 상관관계가 높은 점수를 자동으로 추정한다. 사람이 직접 듣는 것을 완전히 대체하지는 못하지만, 55종 모델을 동일한 잣대로 빠르게 훑어보는 용도로는 충분히 실용적이다. tts-bench의 Scores 렌즈가 자연스러움 지표로 이 UTMOS를 채택한 이유도 여기에 있다.

4. 3렌즈 접근이 갖는 의미

tts-bench의 방법론에서 본인이 눈여겨본 지점은, 세 렌즈를 굳이 하나로 합치지 않고 나란히 병렬로 남겨뒀다는 사실이다. 각 렌즈가 답하는 질문이 다르기 때문이다.

4.1 Speed - 이 모델이 내 하드웨어에서 실용적인가

Speed 렌즈는 콜드/웜 상태에서의 첫 오디오 응답 시간(TTFA), 실시간 대비 처리 배율(RTF), 메모리 사용량을 CPU·CUDA·Apple Silicon 세 경로로 각각 보여준다. 이는 "얼마나 자연스러운가"와 무관하게, 정해진 하드웨어에서 그 모델을 실제로 돌릴 수 있는지를 답하는 실용적 질문이다. 예컨대 초경량 CPU 특화 모델은 웜업 이후 100밀리초 안팎의 응답과 실시간의 수십 배에 달하는 처리 배율을 보인 것으로 프로젝트 결과 페이지에 보고돼 있고, GPU 환경에서는 또 다른 경량 모델이 그보다도 짧은 응답 시간을 기록한 것으로 나타난다. 다만 이런 수치는 모델 버전과 실행 환경에 따라 계속 바뀌므로, 정확한 최신 수치는 프로젝트 사이트에서 직접 확인하는 편이 안전하다.

4.2 Listen - 숫자로 안 잡히는 인상을 직접 듣기

Listen 렌즈는 55종 모델이 동일한 문장을 읽은 오디오를 나란히 모아둔 갤러리다. 문장별로 여러 모델을 한 번에 비교할 수도 있고, 모델 하나를 골라 여러 문장에서 어떻게 들리는지 훑어볼 수도 있다. 기본 목소리 모드와 보이스클로닝 모드를 모두 지원한다. 이 렌즈는 수치로 환원되지 않는 "그냥 들었을 때의 인상"을 남겨둔다는 점에서, 뒤에서 다룰 점수 지표를 보완한다. 실제로 프로젝트는 이 청취 결과를 바탕으로 블라인드 A/B 보팅 아레나를 별도로 운영하며, 모델명을 가린 채 사람의 실제 선호를 모아 Elo 순위로 축적한다.

4.3 Scores - 재현 가능한 객관 지표

Scores 렌즈는 자연스러움을 나타내는 UTMOS, 발음이 텍스트와 얼마나 일치하는지를 나타내는 WER(단어 오류율), 보이스클로닝의 정확도를 나타내는 SIM(화자 유사도) 세 지표를 제공한다. WER은 합성 음성을 다시 음성인식(ASR)에 넣어 나온 텍스트와 원문 텍스트를 비교해 삽입·삭제·치환 오류를 세는 방식으로 계산되며, 값이 낮을수록 발음이 정확하다는 뜻이다. SIM은 화자 임베딩 모델로 레퍼런스 음성과 합성 음성의 화자 특성이 얼마나 비슷한지를 코사인 유사도로 측정하며, 보이스클로닝 모델에서만 의미가 있다. 이 세 지표는 자동으로, 그것도 동일한 절차로 55종 모델 전체에 반복 적용할 수 있다는 점에서 재현성이 높다.

세 렌즈를 합쳐 보면 방법론적 통찰이 하나 나온다. 빠른 모델이 자연스럽다는 보장은 없고, 점수가 높은 모델이 내 하드웨어에서 실시간으로 돌아간다는 보장도 없다. 세 렌즈를 분리해 둔 것 자체가, 단일 순위표로는 이 세 축의 트레이드오프를 정직하게 담을 수 없다는 판단을 반영한 설계로 읽힌다.

5. 로컬 TTS 생태계 개요

55종을 낱낱이 나열하는 대신, 개발자가 실제로 마주치는 로컬 TTS 모델을 성격별로 크게 네 갈래로 정리해 본다. 특정 순위를 단정하기보다 각 갈래가 어떤 트레이드오프를 택했는지에 초점을 둔다.

5.1 초경량 CPU 특화 계열

파라미터 수가 수천만 단위 이하로 작고, GPU 없이 CPU만으로도 실시간보다 훨씬 빠르게 동작하도록 설계된 모델군이다. 라즈베리파이 같은 저전력 엣지 기기에서도 돌아갈 만큼 가볍다. 대가로 목소리의 억양과 표현력은 상대적으로 단조로운 편이라, 안내 방송이나 알림음처럼 짧고 정형화된 문장에 특히 잘 맞는다.

5.2 균형형 범용 계열

파라미터 수가 1억 내외로 초경량 계열보다는 크지만, CPU에서도 실시간 처리가 충분히 가능한 모델군이다. 다국어 지원과 permissive 라이선스(상업적 활용 제약이 적은 라이선스)를 함께 갖춘 사례가 많아, 속도와 자연스러움, 그리고 라이선스 유연성까지 균형 있게 노리는 서비스에 자주 쓰인다.

5.3 보이스클로닝 특화 계열

몇 초 분량의 레퍼런스 음성만으로 특정 화자의 목소리 특성을 재현하는 제로샷 클로닝에 특화된 모델군이다. 여러 언어를 넘나드는 크로스링구얼 클로닝을 지원하는 사례도 있다. 다만 대개 GPU와 수 기가바이트의 VRAM을 요구해 초경량 계열보다 무겁고, 목소리 도용 우려 때문인지 라이선스가 비상업 조건으로 제한된 경우가 흔하다.

5.4 대형 표현력 중심 계열

파라미터 수가 수십억 단위에 이르는 대형 모델군이다. 감정 표현이나 미묘한 억양 조절에서 강점을 보이는 경우가 많지만, 그만큼 연산 자원 요구가 크고 실시간 응답을 확보하기가 상대적으로 어렵다. 실시간 대화형 서비스보다는 콘텐츠 제작처럼 품질이 속도보다 우선하는 용도에 적합하다.

6. 실무 선택 시 고려사항

본인이 로컬 TTS 도입을 검토한다면, 다음 네 가지를 하나의 표로 정리해 두고 판단할 것을 권한다.

고려 요소확인할 질문
하드웨어CPU만 있는가, GPU와 VRAM을 얼마나 쓸 수 있는가
언어 지원목표 언어(예: 한국어)를 실제로 지원하고 품질이 검증됐는가
라이선스상업적 활용이 가능한가, 비상업·카피레프트 조건이 있는가
실시간성대화형처럼 즉시 응답이 중요한가, 배치 생성이어도 되는가

이 중 라이선스는 특히 놓치기 쉽다. 보이스클로닝 계열 모델 중에는 성능이 뛰어나도 상업적 배포가 제한된 라이선스를 쓰는 경우가 있어, 프로토타입 단계에서는 문제없이 쓰다가 서비스 배포 직전에 발이 묶이는 사례가 나올 수 있다. 하드웨어 요구사항도 마찬가지다. 데모에서는 고사양 GPU로 돌려보고, 실제 서비스는 저사양 서버나 엣지 기기에 배포해야 하는 경우가 흔하므로, 처음부터 목표 하드웨어를 기준으로 후보를 좁히는 편이 안전하다.

7. 클라우드 TTS 대비 장단점

로컬 TTS가 만능은 아니다. 클라우드 TTS와 견줘 보면 그 경계가 분명해진다.

항목로컬 TTS클라우드 TTS
데이터 프라이버시기기 밖으로 안 나감외부 서버 경유
비용 구조초기 하드웨어 투자, 고볼륨에서 유리사용량 단가 과금, 소량에서 유리
오프라인 동작가능불가능(네트워크 필수)
초기 설정환경 구축·모델 선택 부담API 키만으로 즉시 사용
최상급 자연스러움모델마다 편차 큼대체로 안정적으로 높음
커스터마이징파인튜닝·양자화 자유제공 옵션 범위로 제한

본인 해석은 이렇다. 데이터를 절대 밖으로 보낼 수 없는 워크로드, 사용량이 많아 단가 누적이 부담스러운 워크로드, 네트워크가 불안정한 환경이라면 로컬 TTS가 명백히 유리하다. 반대로 빠르게 검증하고 최상급 음질을 바로 원하는 소규모 프로젝트라면, 초기에는 클라우드 API로 시작해 볼륨이 커지거나 프라이버시 요건이 생길 때 로컬로 전환하는 것도 합리적인 경로다.

8. 결론 - 오늘 적용 가능한 것들

tts-bench는 55종이라는 압도적인 모델 수 자체보다, 속도·청취·점수를 분리해 보여주는 평가 방법론에 더 큰 의미가 있다고 본인은 판단한다. TTS 모델 선택은 단일 순위표로 끝날 문제가 아니라, 본인 하드웨어·언어·라이선스·실시간성 요구를 각각 확인해야 하는 다차원 문제이기 때문이다.

8.1 목표 하드웨어에서 직접 청취 테스트를 하라

벤치마크 수치는 참고점일 뿐이다. tts-bench의 Listen 갤러리나 직접 내려받은 모델로, 본인이 실제로 쓸 언어와 문장을 넣어 들어보는 과정을 건너뛰지 말아야 한다.

8.2 라이선스를 가장 먼저 확인하라

프로토타입에서 서비스로 넘어가기 전에, 후보 모델의 라이선스가 상업적 배포를 허용하는지부터 확인하라. 특히 보이스클로닝 모델은 비상업 조건인 경우가 흔하다.

8.3 워크로드에 맞춰 계열을 먼저 좁혀라

실시간 대화형 서비스라면 초경량·균형형 계열에서, 콘텐츠 제작이라면 대형 표현력 계열이나 보이스클로닝 계열에서 후보를 고르는 식으로, 55종을 다 보기 전에 워크로드에 맞는 갈래부터 좁히는 편이 효율적이다.
