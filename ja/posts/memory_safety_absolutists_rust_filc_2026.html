メモリ安全性の絶対主義者たち - RustとFil-Cの論争

全面書き換えか漸進的な安全化か、脅威モデルとコード寿命で判断する方法

2026年7月27日 開発・インフラ

序論: 安全性をめぐる純粋さの競争

メモリ安全性の議論が妙な方向へ流れている。出発点はなぜC・C++で書いたコードは30年も同じ種類の脆弱性を繰り返すのかという、きわめて実務的な問いだった。ところが今コミュニティで起きている争いは性質が違う。Rustにはunsafeという抜け穴があるから本物の安全な言語ではない、したがってFil-Cのようにすべての違反を実行時に捕まえる実装だけが正統だ、という主張が出てくる。最近話題になった「メモリ安全性の絶対主義者たち」という記事は、まさにその態度を正面から狙う。要旨は単純だ。Rustの抜け穴は厳しく批判しながら、何の検査もなくコンパイルされる普通のC・C++には同じ物差しを当てないのなら、それは安全への関心ではなく陣営への関心である、と。

本稿ではその批判に同意する点と同意しない点を併せて検討する。ただし感想ではなく数字から始める。メモリ安全性の脆弱性は実際どれほどの比率なのか、Fil-Cは何を代償に安全を買うのか、Rustのunsafeは実際の生態系でどれだけ使われているのか、C++陣営が出したプロファイル方式はどこまで来たのかを公開資料で確認したうえで、レガシーCが特に厚い韓国の組込み・通信・金融コアを具体例として、現場で何が本当に可能かを検討する。結論を先に言えば、正解は言語名ではなくそのコードがどんな入力を受け、あと何年生きるかにかかっている。

1. 議論の前にまず数字 - メモリ安全性は実際どれほど問題なのか

この議論で最も頻繁に引用される数字は70パーセントだ。これは勘ではなく二社の自社集計から出ており、互いに独立して近い値に到達したという点で信頼できる。

1.1 公開されている主要統計

  • マイクロソフト: CVEを割り当てて修正した脆弱性の約70パーセントがメモリ安全性の問題だと述べた。10年以上のセキュリティ更新を集計した値である。
  • グーグルのChromium: 2015年以降に安定版で修正した高・重大深刻度のバグ912件を分析した結果、約70パーセントがメモリ管理・安全性のバグで、そのうち半数ほどが解放後使用(use-after-free)だった。
  • Android: メモリ安全性の脆弱性の比率が2019年の76パーセントから2024年には約24パーセントへ下がり、その後20パーセントを割り込んだと報告された。
  • AndroidのRustコード: 約500万行規模で脆弱性密度が100万行あたり0.2件と推定された。同じ組織のC・C++の歴史的密度である100万行あたり約1,000件と比べると1,000倍以上の差だ。
  • 副次的効果: 同じ報告でRustの変更はロールバック率が4分の1、コードレビュー時間が25パーセント短いと言及された。安全性が開発速度を削るという通念と逆の結果である。

1.2 この数字が語ること、語らないこと

ここで注意すべき点がある。Androidの0.2対1,000という比較は同一条件の実験ではない。Rustで新たに書かれたコードは概ね新機能であり、C・C++側は数十年にわたり攻撃者の集中的な照射を浴びてきた古いコードだ。新規コードが相対的に掘られていない可能性、モジュールごとの危険度の差、発見努力の偏りといった要因が混ざっている。それでも三桁の倍率を測定バイアスだけで説明するのは難しい。そして76パーセントから20パーセント未満へ落ちたAndroidの推移線は、既存コードを全面的に書き直さずとも比率が急落したという事実を示している。この点が後述する実務戦略の中核的な根拠になる。

2. Fil-Cとは何か - Cを残したまま安全にする道

2.1 仕組み: InvisiCapsと並行GC

Fil-Cは「狂信的なまでに互換性のあるメモリ安全なC・C++実装」を標榜する。核心はInvisiCapsというポインタモデルだ。ポインタをプログラムから見えるアドレス値と見えないケイパビリティに分離し、境界と寿命の情報を別のメタデータに保持する。プログラムは従来どおりポインタを整数のように扱えるが、実際に参照する時点で隠れたケイパビリティと突き合わされ、範囲を外れればパニックで即座に停止する。寿命管理は並行・並列のガベージコレクタが担い、そのオブジェクトを指すポインタがすべて消えてからメモリを回収する。だから解放後使用は原理的に成立しない。スレッドは後方制御フロー辺のようなセーフポイントでのみ停止し、シグナルハンドラもセーフポイントで実行されるためGCと衝突しない。

成熟度の面でも玩具ではない。公式サイトによればCPython、OpenSSH、GNU Emacs、Waylandなどが移植され、Pizlixという名でLinuxユーザランド全体をFil-Cでビルドした構成まで存在する。2026年7月初旬時点でバージョン0.681が公開されており開発も活発だ。ただしバージョン番号がいまだに0で始まるという事実も併せて読む必要がある。

2.2 何を代償に払うのか

安全はただではない。Fil-Cが払う代償は明確で、その代償がそのまま適用可能な領域を決める。

  • 実行速度: ポインタ追跡の多いコードでおおむね1～6倍、悪い場合で4倍前後の低下が報告される。逆にシェル(Bash 5.2.32)のようにポインタ密度の低いプログラムでは体感差がほとんどなかったという実測もある。つまりワークロードによる振れ幅が非常に大きい。
  • メモリ使用量: ポインタを含む構造体にはケイパビリティのメタデータが付き、事実上2倍の空間を使う。メモリが逼迫した組込みではこれだけで脱落しうる。
  • ABI非互換: 通常のコンパイラが生成したオブジェクトとリンクできない。依存関係の全体を再ビルドする必要があり、バイナリのみで提供される商用ライブラリが一つでも挟まればその場で行き止まりだ。
  • 言語間リンク: 現時点でRustとのリンクは未対応で、混成スタックでは境界設計が難しくなる。
  • GCの存在: ハードリアルタイム、カーネル・ドライバ、ジッタ規格のある信号処理では、ガベージコレクタの存在そのものが不適格の理由になる。

要するにFil-Cは既存コードを生かす代わりに実行時の資源を支払う設計だ。この交換が成立する領域は確かにあり、成立しない領域も確かにある。

3. Rustの安全モデルとunsafeの現実

3.1 所有権と借用チェッカー

Rustは逆方向から攻める。値ごとに所有者は一つ、参照は可変が一つか、不変が複数かのどちらかのみという規則をコンパイル時に強制する。この規則により解放後使用、二重解放、データ競合が実行前にふるい落とされる。実行時検査もGCも不要なので性能特性はCに近い。代わりに代償は人が支払う。既存Cコードの奔放なエイリアシング慣行はこのモデルにそのまま移らず、実質的にデータ構造の設計からやり直すことが多い。

3.2 同じバグ、三つの結末

解放後使用を一つ取り上げ、三つのアプローチがどう分かれるかを見ると性質の差が明確になる。

/* 標準C: コンパイルは通り、実行も大抵通り、しかし攻撃面になる */
char *buf = malloc(16);
free(buf);
strcpy(buf, "hi");   /* 解放済みメモリへの書き込み - 任意コード実行につながりうる */
/* Fil-C: ソースはそのまま。実行中にパニックで即座に停止する */
/* コンパイラがポインタのケイパビリティを確認し無効なアクセスを遮断する */
// Rust: そもそもコンパイルが通らない
let buf = vec![0u8; 16];
drop(buf);
// buf[0] = 1;  // error[E0382]: borrow of moved value: `buf`

三つの結末の違いはいつ支払うかだ。Cは支払いを先送りし、事故が起きた時に全額を払う。Fil-Cは実行のたびに少しずつ払う。Rustは開発時に一度で払う。どの方式が有利かは、そのソフトウェアの実行頻度、性能の余裕、残りの寿命によって変わる。これが言語の優劣ではなく状況判断である理由だ。

3.3 unsafeは穴か、監査面か

絶対主義者の主要な攻撃点はunsafeである。この批判は完全に的外れではない。unsafeの中で誤って書かれたコードが安全なコード側で発現するバグを生みうるという研究は実際にあり、著名なクレートを分析して多数の勧告とCVEを整理した調査も存在する。しかし規模感が必要だ。Rust Foundationの報告によれば、crates.ioのクレートのうちunsafeキーワードを使う比率は約20パーセントで、その多くはCとの相互運用が用途であり、コード量ベースでは1パーセント前後と推定される。

ここで得られる実質的な利益は安全の有無ではなく監査対象の大きさだ。Cのコードベースではすべての行が潜在的なunsafeである。Rustでは検討すべき地点が構文上で標示され、狭く絞られる。100万行のうち1万行を集中的に検討する作業と、100万行全体を検討する作業は、組織の観点でまったく別の課題だ。「抜け穴があるから無意味だ」という主張は、この差を消してしまう点で論理的に弱い。

4. 「絶対主義」批判の要旨 - 全面書き換え要求は現実的か

原文の筆者の批判は二筋に読める。第一は二重基準だ。Rustのunsafeを致命的欠陥として扱いながら、何の検査もなくコンパイルされる一般のC・C++には同じ強度の非難をしないのなら、その基準は安全ではない。第二は代案の非対称性だ。Fil-Cを唯一の正解として掲げるなら、Fil-Cが担えない領域、すなわちGCを置けず、ABIを変えられず、4倍の低下を吸収できない領域を何で埋めるのか答えなければならない。今その席を埋めているのがまさにRustである。

私はこの批判におおむね同意するが、一つ付け加えたい。絶対主義はRust反対陣営だけのものではない。すべてのCをRustで書き直せという要求もまた同種の絶対主義だ。数百万行規模の検証済みコードを書き直す作業は新言語の学習コストだけの問題ではなく、数十年にわたり現場で磨かれた例外処理と暗黙の要求仕様を丸ごと失う問題である。書き換えの過程でメモリバグが消え、論理バグが新たに入り込む交換が起こりうる。実際にAndroidが示した成果は全面書き換えではなく新規コードから安全な言語でという原則から出た。76パーセントから20パーセント未満への下落は、古いコードを消し去ったからではなく新たに流入する脆弱性の源を断ったために描かれた曲線だ。

5. Rust書き換え vs Fil-C漸進安全化 - コストとリスク

二つの経路を同じ軸で比較すると、選択基準がはるかに鮮明になる。以下は組織が実際に支払う項目を基準にした整理である。

項目Rust書き換えFil-C再コンパイルC維持＋堅牢化

実行時オーバーヘッドほぼなし1～6倍、悪い場合4倍前後なし(堅牢化時は数パーセント)

表を見ると、二つの選択肢が重ならない問題を解いていることが分かる。Fil-Cの最大の強みは性能ではなく人材と資産の連続性だ。既存のC開発者がそのまま残り、コードもそのまま残るのに危険等級だけが下がる。逆にRustの最大の強みは安全性が実行時にはほぼ無料だという点である。一度支払えば以後の実行ごとにコストが乗らない。したがって長く生き残り実行頻度の高い中核コンポーネントほどRust側の算術が有利になり、寿命が残り少ないか性能の余裕が大きいコードほどFil-C側の算術が有利になる。

6. C/C++陣営の反論 - 安全プロファイルとC++26

C++標準化陣営は言語を捨てる代わりに安全プロファイルという経路を選んだ。別個の安全な方言を作る「Safe C++」提案と、既存コードに漸進的に適用できる「プロファイル」提案が競い、投票ではプロファイル賛成19票、Safe C++賛成9票、両方11票、中立6票でプロファイル側が上回りその方向が採られた。2026年3月のロンドン・クロイドン会合でC++26の技術作業が完了し、リフレクションや契約と並んで書き換えなしで適用する安全強化が含まれた。未定義動作をさらに減らす作業と追加プロファイルの議論はC++29を狙って続いている。アップルがWebKitの400万行以上をプロファイル的な部分集合方式で強化し効果を得たという事例も提示された。

ただしこのアプローチの限界も率直に見る必要がある。プロファイルは主に空間的安全性、すなわち境界検査で力を発揮し、解放後使用に代表される時間的安全性ははるかに難しい問題として残る。グーグルは公開見解で、C++が時間的安全性まで含む厳密なメモリ安全言語へ進化する現実的な経路は見えていないと明示した。先に見たChromiumの統計でメモリバグの半数が解放後使用だった点と重ねると、プロファイルがカバーできない領域こそが最も痛い半分でありうるという意味になる。それでもプロファイルには決定的な長所がある。すでにあるコードに今日適用できるということだ。半分を防ぐ措置を今入れるほうが、全部を防ぐ計画を5年後に始めるより概ね良い。

7. 規制という変数 - 勧告が調達要件へ変わりつつある

この議論はもはや趣味の問題ではない。米国のホワイトハウス国家サイバー長官室(ONCD)は2024年2月の報告書「Back to the Building Blocks」でプログラミング言語そのものをセキュリティの基盤要素として名指しし、サイバーセキュリティ・インフラセキュリティ庁(CISA)は2023年の共同指針「メモリ安全ロードマップの必要性」に続き、製品セキュリティ関連文書でソフトウェア製造者に次を促した。

  • メモリ安全性ロードマップを2026年1月1日までに公開すること。すでに過ぎた時点であり、現在は履行の有無が確認される段階だ。
  • ロードマップはネットワーク接点のコードや暗号演算のような優先度の高い構成要素から扱うこと。
  • 単なる宣言ではなく脆弱性の実質的・優先順位に基づく削減につながることを立証すること。
  • 2030年1月1日より前にサポート終了が公表された製品は対象外。
  • CISA自身が移行には相当の時間と資源がかかると認め、短期の緩和と長期の除去を併行せよと勧告している。

注目すべきは最後の二項目だ。規制当局ですら全面書き換えを要求していない。優先順位と期限を要求しているにすぎない。絶対主義論争の両極端よりむしろ規制文書のほうが現実的なのである。輸出企業にとっても他人事ではない。米国の公共・重要インフラへ納入する通信機器、セキュリティアプライアンス、自動車部品、産業制御ソフトウェアは、調達審査でこのロードマップの有無を問われる流れにまもなく晒される。MISRA C、ISO 26262、IEC 62443といった既存の安全・セキュリティ規格をすでに扱っているなら、メモリ安全性ロードマップはその文書体系の上に載せるのが難しくない。

8. レガシーが厚い現場の実務 - 韓国の事例

8.1 三つの異なる戦場

韓国の産業構造でC・C++コードが最も厚く積み上がっている場所はおおよそ三つだ。制約条件がまったく異なるので、同じ処方を下せば失敗する。

  • 組込み・自動車: メモリ数百KBから数MB、ハードリアルタイム制約、機能安全認証の負担。GCが付いた瞬間に認証の論理が揺らぐのでFil-Cは事実上除外される。現実的な経路はMISRA系ルールの強化、静的解析の拡大、そして新規モジュール限定のRust導入だ。
  • 通信機器・ネットワークソフトウェア: パケットパーサとプロトコル状態機械が完全に信頼できない入力を直接受ける。脅威露出度が最も高い位置だ。一方で性能要求は領域ごとの差が大きく、制御プレーンなら安全な言語で書き直す価値が十分にあり、データプレーンのホットパスは依然として難しい。
  • 金融コア・照合処理: 電文解析とバッチ作業が多く、元帳の整合性ゆえに書き換えリスクを極度に忌避する。ところが夜間バッチは性能の余裕が相対的に大きい。Fil-C系のアプローチが最もよく合いうる位置であり、同時に商用バイナリ依存が多くABI問題で塞がれやすい位置でもある。

8.2 人材需給という真のボトルネック

技術的妥当性より組織を実際に止めるのは人の問題だ。国内でシステムプログラミング人材はすでに薄く、Rustを実務水準で扱える人材はさらに薄い。SI・受託開発の比重が高い構造では書き換え期間中の機能凍結を発注側が受け入れがたいという現実的な壁もある。この観点でFil-Cのようなアプローチの魅力は性能ではなく人を替えなくてよい点にある。逆にRust導入を決めるなら、全面転換ではなく新規モジュールを一つ定め、6か月間チームの二、三名が学習と成果物を兼ねるやり方が失敗確率が低い。先に引用したロールバック率4分の1やレビュー時間25パーセント短縮は、学習曲線を越えた後に現れる指標だという点も併せて記憶しておく必要がある。

9. 性能オーバーヘッドはどこまで許容できるか

「4倍遅くなる」という一文はそれ自体では判断根拠にならない。4倍が致命的な場所と、まったく問題ない場所が一つの組織の中に共存するからだ。領域ごとに許容できる幅を分けると、選択は自動的に狭まる。

この表で注目すべきは脅威露出度が高い場所と性能の余裕が大きい場所が相当程度重なるという点だ。ファイルパーサ、画像・文書変換器、ログ処理器のように外部データを直接噛むコードは概ねホットパスではない。まさにこの交わりがFil-C系アプローチの最適な入口である。全面導入を論争する代わりに、この交わりから再コンパイルしてみるほうがはるかに生産的な第一歩だ。

10. 結論に代わる判断フレーム - 陣営ではなく脅威モデルとコード寿命

ここまでの内容を実務の意思決定に圧縮すると、問いは四つに減る。言語名はその後に出てくる。

  1. このコードは信頼できない入力を直接受けるか。 受けるなら最優先対象だ。ネットワーク境界、ファイルパーサ、暗号演算、ユーザアップロード処理の順に一覧を作る。
  2. このコードはあと何年生きるか。 3年以内に廃棄予定なら書き換え投資は回収されない。堅牢化オプションと隔離で凌ぐほうが合理的だ。10年以上生きるコードなら書き換えの算術が成立し始める。
  3. 性能・メモリの余裕は何パーセントか。 余裕が2倍以上あり依存関係をすべてソースで確保できるなら、Fil-C系アプローチが最も安い安全だ。余裕がないならその選択肢は消す。
  4. 人を替えられるか。 チームにRustを習得する余力も採用の見込みもないなら、全面Rust転換の計画は文書として残るだけだ。この場合は新規モジュール一つに絞ったパイロットが唯一機能する形である。

この四つに答え終えると、多くの組織で結論は似た形に収束する。新しく書くコードは安全な言語で、脅威に晒された古いコードは再コンパイルか隔離で、残りはそのまま置いて監視する。 Androidが76パーセントから20パーセント未満へ下りた経路は、まさにこの形だった。

結論: 純粋さは指標ではない

「メモリ安全性の絶対主義者たち」が指摘した二重基準は有効だ。Rustのunsafeを根拠にRustを失格させながら、何の検査もなく回るC・C++を黙認するなら、その基準は安全ではなく所属である。同時に反対方向の絶対主義、すなわちすべてのCを今すぐRustで書き直せという要求も現場では機能しない。二つの陣営が共有する誤りは同じだ。安全を二分法で扱い、そのコードが置かれた条件を見ないことである。

実務者に有用な態度ははるかに乾いている。Fil-Cは既存の資産と人材を維持したまま実行時の資源を支払い、時間的・空間的安全を同時に得る道具であり、ABI再ビルドとGCを引き受けられる場所で強力だ。Rustは開発時にコストをまとめて払い、実行時を空けておく道具であり、長く生き、頻繁に実行され、性能の余裕がない場所で有利である。C++プロファイルは今日すぐ入れられる半分の防御であり、その半分は0よりはるかに良い。三つは競合というより、異なる制約の組み合わせのための装備だ。2026年7月現在、規制当局ですら優先順位と期限を語るだけで全面書き換えを語らない。陣営の旗を選ぶのに使う時間を自分のコードがどんな入力を受け、あと何年生きるかを一覧にすることに使うほうが、どんな論争に参加するよりも脆弱性を一つ多く減らす。
