Nobody Reads Your Docs Because Four Kinds of Writing Are Stuck in One Page - Applying Diataxis

The two questions that split the four modes are asked of sentences, not documents

Aug 4, 2026 Dev & Infra

Introduction: the docs exist, and people still ask whether there are any docs

The onboarding document runs to forty pages, the API reference is generated from the code, and the architecture write-up is sitting on the wiki. Yet the person who joined this week has been stuck in the same place for two days, and the senior engineer gives up and asks on Slack. They did not skip the docs. They read them and could not find the sentence they needed.

The usual conclusion at this point is that more documentation is required. Go that way and next quarter you have sixty pages and the same questions. Length was never the missing thing.

The actual problem is that four kinds of writing with incompatible purposes are sharing one document. Take apart any ordinary install guide and all four are usually in there: the steps you follow in order, the settings recommended for production, the full list of options, and the reasoning behind the architecture. Each of those serves a different person, and stacking them on one page fails all four. The newcomer stalls at the paragraph about production settings, and the person who came to check one value scrolls past twelve lines of procedure.

Diataxis is a framework that gives you the line between those four. Daniele Procida created it and published it at diataxis.fr under CC BY-SA 4.0. It splits documentation into tutorials, how-to guides, reference and explanation, and the whole force of the idea is that the split is not by type of content but by the state the reader is in when they open the page.

This article covers five things: what reader state each of the four modes assumes, the symptoms that appear when they are mixed and where those symptoms come from, a procedure for deciding which mode a single sentence belongs to, the realistic compromise for a repository that only has a README, and the places where this frame becomes a stretch.

How to write the sentences themselves, meaning restricted vocabulary and controlled syntax, is a separate problem. That one is covered in What Changes When You Force Technical Docs Into a Controlled Language. This article is about how to divide documents. The two do not replace each other. Splitting by mode first and then enforcing sentence patterns per mode is the natural order.

1. What reader state each of the four modes assumes

Clear one misconception first. The four modes are not divided by subject. Authentication as a subject can appear in all four. So can a single fact, such as the retry delay defaulting to 1000 milliseconds. In reference it is written as the value. In a tutorial it is usually not mentioned at all. In a how-to guide it appears as something you change under a particular condition. In explanation it appears as the reasoning behind the number. What divides is not the fact but the state of the reader reading it.

1.1 Tutorial: a lesson, not a set of directions

The official definition is short. A tutorial is a lesson, an experience in which the learner does something under the guidance of a teacher. Its purpose is not to get a job done but to make learning happen. A driving lesson is not about getting from A to B.

Four requirements fall out of that. The exercise you put a learner through must be meaningful (they need a sense of achievement), successful (they must be able to complete it), logical (the path must make sense), and usefully complete (they must encounter every action, concept and tool they need to become familiar with).

Then comes the most quoted line in this mode. The first rule of teaching is simply do not try to teach. A teacher feels an anxiety to impart knowledge, and giving in to that anxiety by teaching through explanation wrecks the learning experience. The official documentation lists the temptations that break tutorials as four: abstraction and generalisation, explanation, choices, information.

Translated into a working metric: the success measure of a tutorial is not what the reader learned but whether they reached the end. Learning is not measurable, completion is. If you have an internal tutorial, hand it to a new hire and record only the step number where they stop. That number tells you what to fix. Tutorials are also the most expensive of the four to maintain. Other documents accept partial edits, but a tutorial has to hold together as one story from start to finish, so changing one step cascades through everything after it.

1.2 How-to guide: a recipe

A how-to guide addresses an already-competent reader. The recipe analogy is exact. A recipe does not teach cooking. A chef who has made the dish hundreds of times still follows the recipe to get it right. Hand that same recipe to someone who has never cooked and they fail, because a recipe is not a substitute for a cooking lesson.

The rule the official documentation presses hardest here is to write from the perspective of the user, not of the machinery. The bad example it gives stings: To shut off the flow of water, turn the tap clockwise. It has the shape of guidance and carries no value. Anyone working in the domain already knows it, and it is disconnected from purpose. What the user actually needs is closer to how much water to run, and how vigorously, for a given purpose.

The most common breakage in internal documentation lives exactly here: how-to guides written per feature. Call the user registration API is a machine operation, not a human task. Onboarding a new merchant is a task, and three API calls appear inside it as ingredients. Drop an auto-generated list of operations into a how-to folder and the document count goes up while the readership stays at zero.

There is a scoping instinct here too. The official documentation is explicit that how to build a web application is not a how-to guide, because it names no specific goal or problem but an entire sphere of skill. A how-to guide needs a start and an end, and it values practical usability over completeness. Leaving room for the reader to attach it to their own work beats enumerating every case.

1.3 Reference: a chart, and neutrality

Reference is consulted, not read. The official word for the style is austere: no doubt, no ambiguity, wholly authoritative. And neutral. The marine chart analogy is a good one. The same chart serves a navigator plotting a course and an investigating judge examining an accident. The chart is indifferent to what the reader intends to do.

The governing rule is describe and only describe. The trouble is that neutral description is not a natural way for humans to communicate. What comes naturally is to explain, instruct, discuss and opine, and all four run against what reference demands. Description often feels too thin to be useful, which is exactly when other things creep in. The official prescription is to link rather than include.

There is a structural rule as well. The structure of the documentation should mirror the structure of the product. If a method belongs to a class that belongs to a module, that relationship should be visible in the documentation. A map is useful because it resembles the territory. Examples are allowed and encouraged: showing one usage of a command illustrates it without sliding into explanation or instruction.

The nuance people miss. What reference forbids is instruction, explanation and opinion, not warnings. Sentences of the form you must use a and you must not apply b unless c are presented by the official documentation as normal reference language. They behave like the may contain traces of wheat on a food package. A prohibition with a clear condition is close to a fact; a recommendation with a fuzzy condition is a judgement. That is the line to hold.

1.4 Explanation: the one you could read in the bath

The phrase the official documentation uses for explanation sums the mode up in one stroke: it is the only one of the four that might make sense to read in the bath. It reads fine away from the product and is not directly used by the work in front of you.

Explanation is writing that permits reflection. Its perspective is higher and wider than the other three. It is neither the reader's eye-level view of a how-to guide nor the close-up on the machinery of reference. It answers the question can you tell me about this?

  • It makes connections, including to things outside the immediate topic. Understanding comes from a web, not from isolated facts
  • It provides context and background — design decisions, historical reasons, technical constraints. It answers why
  • It talks about the subject. You should be able to put an implicit about in front of the title, as in About user authentication
  • It admits opinion and perspective. This is the one mode where opinion is legitimate, and the official requirement goes further: explanation can and must consider alternatives and counter-examples
  • It stays closely bounded. Explanation tends to absorb other things. Reach to cover the topic and you pull in procedure and technical description, which blurs the explanation and removes those things from where they belong
  • It does not have to be called Explanation. Discussion, Background, Conceptual guides and Topics all work

Explanation is the least urgent of the four and the one most often missing. Less urgent does not mean less important. Without it a practitioner's knowledge stays fragmented and fragile, and someone working from fragments works anxiously. And explanation is often not absent so much as scattered in small parcels across other documents — three sentences in step 3 of a tutorial, two more in a reference footnote.

2. The two axes: the map is for the meeting room, the compass is for the work

There is a two-by-two diagram that always appears when Diataxis is introduced. The framework calls that the map, and it deliberately keeps a separate tool called the compass. That distinction turns out to be the decisive one in practice. The map shows how the four relate, but it does not tell you what to do, because the map itself is reference.

There are two axes.

  • Action or cognition. Tutorials and how-to guides concern what the reader does; reference and explanation concern what the reader knows
  • Acquisition or application. Tutorials and explanation serve the acquisition of skill, the reader's study; how-to guides and reference serve its application, the reader's work
If the content......and serves the reader's......then it belongs to
informs actionacquisition of skill (study)a tutorial
informs actionapplication of skill (work)a how-to guide
informs cognitionapplication of skill (work)reference
informs cognitionacquisition of skill (study)explanation

Using the compass takes two questions. Action or cognition? Acquisition or application? Answer both and the mode is decided. The official description of the tool is that it is surprisingly banal.

And that banal tool carries the core of this article. The official documentation explicitly says to apply the two questions close up, at the level of sentences and words, as well as across a whole document. This is where most teams go wrong. They look at the map, label a page as a tutorial, create four folders and stop. A label fixes nothing. What actually changes a document is running the compass over it paragraph by paragraph, with the result that some paragraphs move to another file.

3.1 Why explanation ends up in tutorials specifically

This is the most frequent failure and the hardest to correct. The official documentation locates the cause in the teacher. Explanation is the hardest temptation for a teacher to resist, and even experienced teachers find it difficult to accept that their students' learning does not depend on explanation. Once we grasp something we hold it as an abstraction, and we want to hand over the abstraction.

Internal documentation adds a second cause. The person writing the document built the system. Builders want to justify the decisions they made, and that comes out in step 3 as this part was originally going to be A but we switched to B because of a concurrency issue. To the author it is the most important paragraph on the page. To someone installing the thing for the first time it is an obstacle that breaks the flow.

The fix is not deletion, it is relocation. Leave the minimum in the tutorial — we use HTTPS here because it is safer — and link the rest. Explanation is only pertinent at the moment the reader wants it. That moment is not the author's to choose.

3.2 What a recommendation costs inside reference

Suppose the page reads: timeout: default 30 seconds. 5 seconds recommended in production. One line, holding a fact and a judgement. The reader immediately asks which production. At what traffic? Against what upstream? Reference has no answer, and having established that there is no answer, the reader starts doubting the 30 seconds too. The judgement eats the credibility of the fact next to it.

The official documentation puts this in terms of food packaging. Someone reading nutritional information does not want to meet opinions, speculation, instructions or interpretation, and mixing recipes or marketing claims into it could be literally dangerous. That is why food labelling is usually governed by law, and the same seriousness is asked of technical reference.

The fix is simple. Do not delete the recommendation, move it somewhere conditions can be stated. In a how-to guide the condition rises into the title: Tuning timeouts for high-concurrency workloads. The recommendation that carried no value in reference becomes a document that selects its own audience from the title alone.

4. Deciding where a single sentence goes

This is the actual work. Labelling at page level takes half an hour and changes nothing. Things change when paragraphs move.

  1. Open any page. Do not go hunting for the bad ones. The file you were just in, the page open in front of you — that is the right one. The official working method says this explicitly
  2. Ask the two questions of each paragraph. Does this inform action or cognition? Is the reader studying or working?
  3. Mark the paragraphs whose mode differs from the page's main mode. At this step most pages reveal that they hold two or three modes
  4. Move exactly one of them. Try to move all of them and you will not finish today, and a half-dismantled document is left behind
  5. Move it and commit. Treat that single step as complete. The next one happens next time

When step 2 is a close call, a few auxiliary rules speed the judgement up. The compass does not cover these, so it helps to write them down for your own team.

  • If I delete this sentence, can the reader still perform the next step? If not, it is action; if yes, it is cognition
  • Is the reader sitting at a keyboard right now? If they are, it is application (work); if not, acquisition (study)
  • A sentence that starts with why is almost always explanation. Exceptions are hard to find
  • To do X, do Y is a how-to; X is Y is reference. The grammatical shape alone decides most cases
  • First do X, then do Y could be either. This is the only case where you really need the second question
  • Usually, typically and recommended mean it is not reference. Those words hide a condition inside a judgement
  • You could do X or you could do Y means it is not a tutorial. Choices stop a learner

Applied to real sentences, it sorts like this.

SentenceAction / cognitionStudy / workMode
Now run npm run dev. After a moment port 3000 respondsactionstudytutorial
If you are behind a corporate proxy, set HTTPS_PROXY firstactionworkhow-to
The default value of retryDelay is 1000 (milliseconds)cognitionworkreference
Exponential backoff was chosen because early versions saw retries bunch togethercognitionstudyexplanation
In production you are better off setting this above 5000actionworkhow-to (not reference)
This API is deprecated from v3 and removed in v4cognitionworkreference

The last two rows are next to each other for a reason. A deprecation notice is a fact, so it is reference; so migrate now is an action, so it is a how-to. One clause flips the mode. That is the resolution you have to work at for documents to actually change.

5. The order for splitting existing docs: do not start with four folders

There is one thing the official documentation forbids in unusually blunt language: creating empty tutorial, how-to, reference and explanation structures with nothing in them. Do not do that, it says. It is horrible. And this is by far the most common adoption failure. Four folders get made, existing pages get shoved in, and three of them sit empty for six months.

The framework's working stance is the opposite. Do not spend energy getting the structure right; keep improving and the structure changes from the inside. At some point the changes you have made will appear to demand that material move under a certain heading, and that is when the top-level structure forms. This is what using it as a guide rather than a plan means.

You still have to pick a starting point, so here is a judgement about order.

  1. Pull out reference first. It is the easiest call — is this a fact or not — and it draws the least disagreement. It also opens the option of regenerating it from code once it is separated
  2. Pull out explanation next. Explanation is scattered in parcels across other documents, so extracting it makes everything else visibly lighter. This step produces the biggest felt improvement
  3. How-to guides fall out on their own. They are what remains once the first two are gone, specifically the procedures whose titles want to become how to X
  4. Write tutorials last, from scratch. It is the only one of the four you cannot assemble from cuttings. One path that succeeds end to end is a designed object, and it does not emerge from reorganising existing fragments

For a large-scale adoption reference point, Canonical announced in December 2021 that Diataxis would be the foundation of its documentation, applying it to Anbox Cloud, Charmed Kubeflow, Juju, the OpenStack Charms guide and Ubuntu Core. The most quotable part of that post is not a result but a warning: the first thing Diataxis does is make existing documentation look worse, not better, because problems become harder to hide and ignore. If someone says the docs look messier a month after adoption, you are on the expected path.

Never finished, always complete. The official documentation borrows this from plants. A plant is never finished — it can always grow further — but at every stage, seed or mature tree, it is complete for that stage. Documentation is the same. It never ends, but it can be whole at every point. Hold that idea and you stop scheduling a full documentation rewrite.

6. The README-only project: a realistic compromise

Everyone asks the same question after reading this: my repository has one README, so what am I supposed to do? The answer is that you do not need four files. Standing up a documentation site is overkill for most repositories.

What decides a split is not the number of documents but the number of reader types. Do the people using this repository divide into first-time users and existing users? If they do not, as with an internal team script, one README is enough. Instead, separate the four by section order.

  1. A one-line description. None of the four modes. This is identification: what this repository is, in one line
  2. Quick start — the tutorial slot. One path only, no conditional branches, commands you can paste, and at the end how to check that it worked. That last line is missing from most READMEs
  3. Usage or Recipes — the how-to slot. Short entries in how to X form. Branches and conditions are allowed here and only here
  4. Configuration or API — the reference slot. A table, not prose. Name, type, default, constraint
  5. Design notes or Why — the explanation slot. At the bottom. When it grows, that is when it becomes a file

The moment to split into files is judged by shape, not length. Any one of five signals is enough to move that part out.

  • Quick start has grown two or more conditional branches. If you are on Docker do this, if you installed locally do that — pull the how-to out. The moment there is a branch, it is no longer a tutorial
  • The configuration table runs past one screen. Move it to docs/configuration.md. Reference is allowed to be long; it is not allowed to eat the first screen
  • Paragraphs starting with why exceed three. Move them to docs/design.md or an ADR
  • The same question has appeared in issues three times. Create one how-to using the question's wording as the title. Do not polish the wording. What users typed is the search query
  • The README passes five screens. Split it rather than adding a table of contents. A table of contents relieves the symptom without treating it

And before splitting anything there is a far cheaper move: make the section headings reveal the mode. Usage tells you nothing about which of the four it is. Quick start, How to X, Configuration reference and Design notes all do. Change four headings, touch no files, and readers stop scrolling in different places.

7. Titles are half the job

The official documentation gives a three-step example for how-to titles. Good: How to integrate application performance monitoring. Bad: Integrating application performance monitoring — maybe the document is about whether you should, not how. Very bad: Application performance monitoring — maybe it is how, maybe whether, maybe just what it is. It adds that search engines appreciate good titles as much as humans do.

Carried across all four modes, the rule looks like this.

ModeTitle shapeBad exampleGood example
TutorialBuild your first X / Getting started with XSetup guideBuild your first notification bot
How-toHow to XNotification settingsHow to send notifications from behind a proxy
ReferenceNoun phrase + reference / full listConfig tipsEnvironment variable reference
ExplanationAbout X / Why XArchitectureWhy there are two queues

English has its own version of the problem word. Guide covers all four modes at once. An installation guide could be a tutorial, a how-to or reference. An operations guide could be all four. Removing the word guide from a title forces you to decide which mode it is. Manual behaves the same way. Open your internal documentation index and count the titles containing guide or manual — that count is roughly the number of unclassified documents you have.

8. Where it becomes a stretch: limits and objections

This framework is unusually modest about itself. You do not have to believe in it, there is no exam, and if one idea in it seems worthwhile you should help yourself to that one. The repeated instruction to use it as a guide rather than a plan comes from the same place. Taking that attitude at face value, here is where it strains.

  • Release notes and changelogs. They fit none of the four. They look like reference because they are lists of facts, but reference is supposed to mirror the product's structure while a changelog is ordered by time. Different axis. Better to keep them as their own category than to force them in. When something does not fit the four, inventing a fifth box costs less than breaking the framework
  • Troubleshooting. The official documentation offers troubleshooting deployment problems as a how-to example. But real troubleshooting documents are structured as symptom, cause, action, which means diagnosis (cognition) and action are fused inside one entry. Split them within the entry and the document stops working. Judgement: keep entries fused and place the document as a whole under how-to
  • Migration guides. The reader is already competent but is doing this particular thing for the first time. It is a rare genre that demands both modes at once. Judgement: file it as a how-to but borrow the tutorial's discipline — one path, a success check at every step, and a way back
  • Teams with one maintainer. Keeping four modes alive is itself a cost. Split an unowned documentation set into four and you now have four documents nobody maintains. Judgement: the criterion is not headcount but whether the update owner differs. Separating what changes with the code (reference) from what a person edits by hand (the other three) already solves half of it
  • Nothing but auto-generated reference. The official documentation notes that too many developers treat generated reference as all the documentation required. But the opposite trap is real too: hand-written reference drifts from the code. Judgement: generate reference from code wherever possible and spend the writing effort on the other three. Keeping an API contract from drifting is covered separately in Why API Docs Always Lag Behind Code

One honest objection belongs here as well: readers do not know their own state. A first-timer lands on a how-to guide through search, gets stuck, and never realises the page was not written for them. However well you split the modes, search decides the entry point.

That is less a flaw in the framework than something the framework does not cover, and the patch is cheap. Put one line at the top of every document: This page assumes X is already installed. If this is your first time, start with the quick start. Split the modes and skip that line, and half the benefit leaks away at the search-traffic boundary.

9. How the distinction behaves in agent-facing documents

Human readers move between learning periods and working periods. Agents do not. When an agent is invoked it is almost always at work. The compass's second axis is effectively pinned to one side, which leaves how-to guides and reference.

  • Tutorials are worth close to nothing. The goal of building confidence does not apply. Pasting a human tutorial into a context file spends tokens and returns nothing
  • Reference is worth more than it is to a person. An agent fills an empty fact with a plausible sentence. If exact names, defaults and constraints are not written, it invents them. A person who does not know asks; an agent usually does not
  • How-to guides need to be narrower than the human version. A person can adapt guidance to their situation; leave that room for an agent and the slack becomes room to misfire
  • Explanation should be reduced to conclusions. One line about why the structure is what it is makes an agent behave less strangely in unspecified situations, but dropping in a full human background piece comes back as context cost

So an agent-facing document writes two of the four at extreme density, keeps only the decision criteria from explanation, and drops tutorials. That is the actual shape of a context file that works. Why documentation for agents is a separate genre from documentation for humans is covered in OpenWiki Arrives - What Makes 'Agent-Facing Documentation' Different From Docs for Humans, and why piling rules into that document still fails to control anything is covered in A Long Policy Document Will Not Govern Your Agent.

One more thing worth adding: separating the modes acts directly on retrieval quality. When procedure, background and facts share one page in an internal knowledge base, that page matches every query, and the sentence you actually needed sits outside the chunk boundary. Add the fact that the same page is quietly ageing and you are in the territory of Your Internal Knowledge Base Rots Quietly.

10. What tends to get in the way inside engineering organisations

10.1 The wiki tree is an org chart, not a mode split

When documentation accumulates in Confluence or Notion, the tree usually looks like Platform Team > 2024 > Deployment. That path is built from author, team and date. It has nothing to do with the reader's state. Whether a document is a tutorial or reference is only knowable by opening it, and before opening it all you see is the title in the search results.

Restructuring the tree is a big job and usually needs sign-off. Renaming titles so they reveal the mode needs no sign-off at all. That order is also the correct one. Fix the titles and the modes become visible in the index, and only then do you have the evidence to justify moving the tree.

10.2 Handover documents are the canonical all-four-in-one genre

When ownership changes, everything tends to get poured into a single page: access details, procedures, background and cautions. The structural problem is this. A handover document loses its update owner the moment it is written. The author has left, and to the recipient it is not their document. A document nobody updates is guaranteed to go stale.

Judgement: make the handover document an index and send the contents to their modes. Access details and resource inventories to reference, recurring operations to how-to guides, why things run this way to explanation. Leave links and one thing more — who owns this system. Then when the handover page goes stale, the damage is a few broken links.

10.3 Contract projects have deliverable names fixed in the agreement

When the contract names the artefacts — requirements specification, screen design document, user manual — you cannot map the four modes onto the deliverable list, and you cannot rename them either.

Judgement: apply Diataxis to the section structure inside each deliverable rather than to the list of deliverables. Split a single user manual into getting started, task-by-task procedures, and screen and field specifications, and the artefact name stays the same while three modes are separated inside it. That is improvement you can get without touching the acceptance criteria.

10.4 When an English original and a translation coexist

Adopting an open source project and keeping a translated copy internally is common. The breakage that recurs here is that the original's four modes collapse into a one-page summary in translation. Content that was split into tutorial, how-to and reference upstream becomes a single How to use X page. When that happens the translation is worse than the original: anyone who can read the original goes to the original, and only those who cannot are left with the bad document.

Judgement: if you cannot translate all of it, reduce the length, not the number of modes. Four short files beat one file holding everything, not least because they leave the right holes to fill in later.

11. What could not be verified

The following were left out of the body as figures or assertions because the evidence was not available.

  • Quantified before-and-after effects. No primary source was found comparing search bounce rate, support ticket volume or onboarding time before and after adopting Diataxis. The Canonical post goes as far as declaring adoption, listing scope, and the experiential note that things look worse first — no numbers
  • Experimental validation of the four-way split. diataxis.fr contains a section on theory, but no published controlled study was found showing that this classification improves reader outcomes over an alternative one
  • Measured effects in agent-facing documents. No published result was found measuring how mode-separated context files change tool-call success or task completion rates. Section 9 is reasoning from structure, not measurement
  • Reported adoption in non-English documentation sets. No published account was found of an organisation adopting this framework for a non-English documentation corpus and reporting results. Section 10 is judgement about recurring shapes, not a case study

12. Conclusion: the one thing to do today

Documentation problems are usually not scarcity but mixture. Forty pages go unread not because there are not forty-one, and sixty will not change it. The reason is that four readers in four different states have been seated at the same page.

There is one thing to do today. Reopen the document already on your screen, ask the two questions of each paragraph, mark one paragraph whose mode differs, and move that one. Do not go hunting, do not write a plan, do not create folders. Creating four folders up front is the single thing this framework explicitly tells you not to do.

And if the documentation looks worse in the first month, that is correct. The first thing this frame does is not to improve the docs but to make it impossible to hide where they are broken. Exposed problems and new problems are not the same thing.

One ordering to close with. Split the modes first, polish the sentences second. Do it the other way round and you end up with well-written sentences still sitting in the wrong place. Style work comes after, and that is the controlled language conversation.
