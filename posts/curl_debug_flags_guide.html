서론: 요청이 느릴 때 어디서 멈추는지 숫자로 가르기

특정 API나 웹 서버로 보내는 HTTP 요청이 평소보다 눈에 띄게 느려질 때, 개발자나 인프라 엔지니어가 가장 먼저 부딪히는 장벽은 지연의 원인이 속한 계층을 특정하기 어렵다는 점이다. 도메인 이름을 IP 주소로 바꾸는 DNS 조회가 지연되고 있는지, 중간 라우터나 방화벽을 통과해 TCP 3방향 핸드셰이크를 맺는 구간이 밀리고 있는지, TLS 인증서 교환 및 암호 협상에서 시간을 소모하는지, 아니면 서버 애플리케이션의 데이터베이스 쿼리가 오래 걸려 첫 바이트(TTFB)가 늦게 도착하는지 산문적인 감각만으로는 판별할 수 없다.

이러한 의문을 명확한 숫자로 규명할 수 있는 도구가 터미널의 curl이다. 하지만 단순히 curl https://example.com/을 실행하거나 time 명령어로 감싸는 방식은 전체 왕복 시간이라는 단 하나의 숫자만 알려줄 뿐이다. curl이 내장하고 있는 강력한 진단 플래그인 -w(--write-out)와 -v(--verbose)를 올바르게 조합해야만 지연의 각 단계를 밀리초 단위로 분해할 수 있다.

이 글은 흔히 볼 수 있는 옵션 나열식 매뉴얼이 아니다. 요청이 지연되거나 실패할 때 어느 구간에서 몇 밀리초가 걸렸는지 숫자로 정확히 가르는 방법을 다룬다. 특히 -w에 전달하는 형식 파일에서 줄바꿈이 사라지는 뜻밖의 동작 원리, 형식 파일 9항목 중 누적으로 증가하는 6개 시간 지표의 뺄셈 계산법, Windows Schannel 환경에서 관찰되는 상세 로그의 특성, 그리고 실패 상황을 셸 스크립트에 안전하게 전달하기 위한 종료 코드(exit code) 28, 6, 22의 실제 동작을 검증 기록을 바탕으로 분석한다.

이 과정에서 다루는 네트워크 기초 원리는 이미 별도 글들에서 깊이 있게 다루었다. DNS 계층 캐싱 원리는 DNS 캐시가 알려주는 것을, TLS 프로토콜과 암호화 협상 배경은 SSL에서 배운 것이 왜 지금은 틀리나를, 셸 스크립트 종료 코드 감지 체계는 셸 종료 코드와 set -e를, 그리고 대화형 터미널 REST 클라이언트 대안은 Slumber 터미널 HTTP 클라이언트를 함께 참고하면 좋다.

1. 실행 환경과 검증 기준

본문에 수록된 모든 명령어 실행 결과와 출력 문자열은 가상의 예시가 아니며, 제어된 로컬 환경에서 직접 실행하여 얻은 결과다. 독자가 동일한 명령을 재현할 때 참고할 수 있도록 검증 환경의 시스템 사양과 소프트웨어 버전을 명시한다.

  • 운영체제: Windows 10 Pro 10.0.19045
  • 셸 환경: Git Bash (GNU sed 4.9, GNU Awk 5.0.0), Windows PowerShell 5.1
  • curl 버전: curl 8.12.1 (x86_64-w64-mingw32 빌드, TLS 백엔드 Schannel)
  • 버전 관리 및 런타임: git 2.48.1.windows.1, Python 3.13.3, Node 22.16.0
  • 권한: 일반 사용자 권한 (관리자 권한 아님)

이 환경에서 curl -V를 실행했을 때 확인된 기능(Features) 목록은 다음과 같다.

alt-svc AsynchDNS brotli HSTS HTTPS-proxy IDN IPv6 Kerberos Largefile libz NTLM PSL SPNEGO SSL SSPI threadsafe UnixSockets zstd

주목할 점은 이 curl 빌드에는 HTTP2 기능이 없다는 사실이다. 그래서 이후 상세 출력 실험에서는 using HTTP/1.x가 찍혔다. 빌드마다 TLS 백엔드와 기능이 다를 수 있으므로, 진단 전에 curl -V의 첫 줄(버전·TLS 백엔드)과 Features 줄을 먼저 확인한다.

실험 대상으로는 표준 테스트 도메인인 https://example.com/, 301 리다이렉트가 발생하는 http://google.com/, 응답이 없던 사설 IP인 10.255.255.1, 그리고 존재하지 않는 도메인인 nonexistent.invalid를 사용했다. 로컬 파일 시스템 경로는 가독성을 위해 …/tech_lab/ 형태로 정규화하여 표기한다.

2. 형식 파일 줄바꿈의 함정 - 실제 줄바꿈을 버리는 curl

curl의 -w 옵션은 전송이 완료된 후 사용자가 지정한 서식 문자열에 따라 전송 통계를 표준 출력으로 내보낸다. 측정해야 할 지표가 많아지면 명령줄 인자가 길어지므로, 공식 문서가 안내하는 대로 @filename 문법을 사용하여 별도 텍스트 파일에서 서식을 읽어오는 방식을 흔히 선택한다.

2.1 실제 줄바꿈을 넣었을 때의 한 줄 이어붙이기 현상

형식 파일을 처음 작성할 때 많은 개발자가 일반적인 텍스트 에디터에서 작성하듯 각 지표 뒤에 줄바꿈(엔터)을 입력한다. 다음은 실제로 9개 줄로 구성된 curl-format.txt를 생성하고 호출한 실험이다.

printf 'namelookup:    %%{time_namelookup}\nconnect:       %%{time_connect}\n…remote_ip:     %%{remote_ip}\n' > curl-format.txt
cat curl-format.txt
curl -s -o /dev/null -w @curl-format.txt https://example.com/

파일 안에는 분명히 9개의 행이 나뉘어 있었지만, curl 실행 결과 화면에는 전혀 다른 형태의 출력이 나타났다.

namelookup:    %{time_namelookup}
connect:       %{time_connect}
…(파일에는 줄이 9개 있음)
=== run 1
namelookup:    0.023826connect:       0.150990appconnect:    0.571661pretransfer:   0.571741starttransfer: 0.711580total:         0.734726http_code:     200size_download: 713remote_ip:     172.66.147.243=== run 2

파일 내에 존재하던 실제 줄바꿈 문자가 완전히 제거되어 모든 항목이 줄 구분 없이 한 덩어리로 이어붙여졌다. 셸 스크립트나 파서에서 줄 단위로 읽으려던 계획이 즉시 무너지는 순간이다.

2.2 글자 그대로 \n을 적어야 하는 소스 수준의 이유

이러한 동작은 단순한 셸의 간섭이 아니라 curl 내부 구현에서 기인한다. curl 8.12.1 공식 소스 코드 저장소의 src/tool_paramhlp.c에 정의된 file2string() 함수를 분석하면 그 명확한 이유를 찾을 수 있다.

해당 함수는 파일을 메모리로 읽어 들일 때 memcrlf() 함수를 호출하여 줄바꿈 문자를 처리한다. 소스 코드 주석에는 countcrlf FALSE - return number of bytes from the start that DO NOT include any CR or LF or NULL이라고 명시되어 있다. 즉, 파일에서 서식 문자열을 로드할 때 실제 CR(캐리지 리턴)이나 LF(라인 피드) 문자를 건너뛰어 버퍼를 연결한다.

따라서 줄바꿈을 온전히 출력하려면 서식 파일 내에 실제 엔터 키 입력이 아니라, 역슬래시와 영문 n으로 구성된 글자 그대로의 \n 문자열을 명시적으로 작성해야 한다. Everything curl 문서(writeout 절) 역시 You can also output a newline by using \n, a carriage return with \r and a tab space with \t라고 규정하고 있다.

이를 반영하여 curl-format2.txt를 다음과 같이 준비했다.

namelookup:    %{time_namelookup}\n
connect:       %{time_connect}\n
appconnect:    %{time_appconnect}\n
pretransfer:   %{time_pretransfer}\n
starttransfer: %{time_starttransfer}\n
total:         %{time_total}\n
http_code:     %{http_code}\n
size_download: %{size_download}\n
remote_ip:     %{remote_ip}\n

이 파일은 바이너리 검사(od -c)를 통해 \ 문자와 n 문자 두 글자가 물리적으로 기록되어 있음을 확인했다.

3. -w 시간 변수의 본질 - 누적이 만든 값과 차이 계산

수정된 형식 파일 curl-format2.txt를 사용하여 https://example.com/에 두 차례 요청을 보내 측정값을 수집했다.

for i in 1 2; do echo "=== run $i"; curl -s -o /dev/null -w @curl-format2.txt https://example.com/; done

3.1 6개 시간 지표가 그리는 요청 생애주기

출력된 숫자들을 위에서 아래로 살펴보면 값이 일관되게 점진적으로 증가한다는 사실을 알 수 있다. run 1에서 namelookup은 약 0.017초, connect는 약 0.148초, appconnect는 약 0.477초, total은 약 0.620초를 나타낸다.

이것이 의미하는 바는 결정적이다. curl의 time_* 변수들은 해당 단계 자체에 소요된 독립적인 기간이 아니라, 요청 시작 시점(0.000초)부터 해당 단계가 완료된 시점까지 경과한 「누적 시각」이다. 예컨대 time_connect의 0.148093초는 TCP 연결에만 0.148초가 걸렸다는 뜻이 아니라, 요청 시작부터 TCP 연결이 끝날 때까지 흐른 누적 시간이다.

3.2 단계별 소요 시간을 구하는 뺄셈 공식

따라서 순수한 단계별 소요 시간을 계산하려면 바로 앞선 단계의 누적 시각을 빼는 뺄셈 연산이 필요하다. run 1의 실제 수치들을 초 단위에서 밀리초(ms) 단위로 환산하여 뺄셈식을 도출하면 다음과 같다.

  • DNS 조회 소요: time_namelookup = 16.8 ms (run 2: 16.1 ms)
  • TCP 연결 소요: time_connect - time_namelookup = 148.1 - 16.8 = 131.3 ms (run 2: 127.6 ms)
  • TLS 핸드셰이크 소요: time_appconnect - time_connect = 476.8 - 148.1 = 328.7 ms (run 2: 320.1 ms)
  • 클라이언트 요청 준비: time_pretransfer - time_appconnect = 477.0 - 476.8 = 0.2 ms (run 2: 0.1 ms)
  • 서버 첫 바이트 대기(TTFB): time_starttransfer - time_pretransfer = 619.7 - 477.0 = 142.7 ms (run 2: 136.6 ms)
  • 본문 다운로드 전송: time_total - time_starttransfer = 619.87 - 619.74 = 0.1 ms (run 2: 2.6 ms)

이 측정에서 전체 소요 시간 약 0.62초 중 가장 큰 비중을 차지한 구간은 전체의 절반 이상(약 328.7 ms)을 차지한 TLS 핸드셰이크 구간이었다. 앞선 실험 1의 측정에서도 appconnect - connect 구간은 약 0.30~0.42초로 세 번 모두 가장 컸다. 이 숫자는 이 특정 환경과 네트워크 경로에서 단 1회씩 측정한 실측값이며, 모든 인프라에 일반화할 수 있는 고정치가 아니라는 점을 분명히 한다.

4. 단계별 구간 분해와 병목 진단 표

측정된 누적 시각의 차이를 표로 구조화하면 어떤 구간이 지연을 유발하는지 곧바로 범위를 좁힐 수 있다. 다음은 이번 환경의 실측값(1회)과 함께 각 차이가 비정상적으로 커졌을 때 점검해야 할 일반적인 네트워크 배경을 정리한 진단 결정표다.

커진 구간 계산식 (누적값의 차) 이 환경 실측 (run 1, 1회 측정) 지연 발생 시 의심할 배경 요인
DNS 조회 namelookup 16.8 ms 로컬 DNS 캐시 미스, 재귀 리졸버 응답 지연, 외부 DNS 서버 장애
TCP 연결 connect - namelookup 131.3 ms 네트워크 물리적 거리(RTT), 중간 방화벽의 SYN 패킷 지연 또는 패킷 손실
TLS 핸드셰이크 appconnect - connect 328.7 ms 인증서 체인 검증 지연, 암호 스위트 협상 왕복, TLS 버전 차이
서버 응답 대기 starttransfer - pretransfer 142.7 ms 서버 측 애플리케이션 연산 부하, DB 쿼리 병목, 리버스 프록시 캐시 미스
본문 전송 수신 total - starttransfer 0.1 ms (713 B) 응답 페이로드 크기, 네트워크 대역폭 제한, 수신 버퍼 병목

이처럼 계산식을 적용하면 전체 지연 620ms를 막연히 「서버가 느리다」고 치부하는 대신, 「DNS 17ms, TCP 131ms, TLS 329ms, 서버 첫 바이트 대기 143ms」(이 환경 1회 측정)로 분해하여 네트워크 팀이나 인프라 팀에 구체적인 근거 수치를 제시할 수 있다.

5. -v 상세 출력 읽기와 Schannel 환경의 한계

-w가 정량적인 숫자 지표를 제공한다면, -v(--verbose)는 curl이 통신하는 전 과정을 프로토콜 수준의 텍스트 로그로 보여준다.

출력 라인의 맨 앞 기호는 다음 규칙으로 구분된다.

  • *: curl 내부 제어 정보 (DNS 해석 결과, IP 주소, 소켓 상태, SSL 백엔드 동작)
  • >: 클라이언트가 서버로 전송한 요청 헤더 라인
  • <: 서버로부터 전달받은 응답 헤더 라인
  • {: 받은 데이터의 양 (이 출력에서는 { [725 bytes data])

5.2 --trace-time 타임스탬프와 단계 경계 해석

각 라인이 출력되는 절대 시각을 기록하기 위해 --trace-time 플래그를 추가한 출력이다.

07:43:32.016000 * Host example.com:443 was resolved.
07:43:32.018000 * IPv6: (none)
07:43:32.018000 * IPv4: 172.66.147.243, 104.20.23.154
07:43:32.018000 *   Trying 172.66.147.243:443...
07:43:32.146000 * schannel: disabled automatic use of client certificate
07:43:32.450000 * Connected to example.com (172.66.147.243) port 443
07:43:32.450000 * using HTTP/1.x
07:43:32.450000 > GET / HTTP/1.1

이 출력에는 두 가지 중요한 현상이 드러난다. 첫째, --trace-time의 소수점 아래 여섯 자리 중 뒤 세 자리가 모두 000으로 찍힌다. 이 환경의 Windows curl 빌드에서는 마이크로초 대신 밀리초 단위까지만 시간 정보를 제공함을 의미한다.

둘째, 「Connected to」 라인의 출력 시점이다. TCP 연결 시도(Trying)가 .018에 시작되었고, Schannel 관련 줄이 .146에 나온 뒤, Connected to 줄은 TLS가 사실상 마무리된 .450에 찍혔다. 즉, 이 Schannel 빌드에서는 소켓 수준의 TCP 연결 직후가 아니라 TLS 핸드셰이크까지 끝난 시점에 Connected 로그를 내보내는 것으로 읽힌다. 따라서 로그 텍스트 줄 간격으로 단계를 가늠하기보다는, 앞서 살펴본 -w의 time_connect 및 time_appconnect 변수 값을 확인하는 편이 훨씬 정확하다.

또한 이 Windows Schannel 빌드는 -v를 붙여도 협상된 TLS 버전(TLS 1.2/1.3), 암호화 알고리즘 스위트, 서버 인증서 유효기간 등의 상세 내역을 전혀 출력하지 않았다. --trace-config tls,dns를 지정해도 추가 로그가 발생하지 않았다. Linux·macOS에서 쓰이는 OpenSSL 빌드의 -v 출력은 이 환경에서 확인하지 못했으므로, 빌드가 다르면 출력도 다를 수 있다는 점만 염두에 둔다.

6. 두 가지 타임아웃(--connect-timeout vs -m)과 종료 코드

배치 작업이나 스크립트에서 curl을 실행할 때 타임아웃을 올바르게 제어하지 않으면 무응답 서버에 프로세스가 무한정 묶이는 사고가 발생한다. curl은 연결 구간에만 적용되는 --connect-timeout과 전체 요청 생애주기를 제한하는 -m(--max-time)이라는 두 가지 서로 다른 시간 제한 플래그를 제공한다.

6.1 연결 구간만 끊는 --connect-timeout

응답이 없는 사설 IP인 10.255.255.1에 --connect-timeout 2를 지정하여 실행한 결과다.

time curl -sS --connect-timeout 2 -o /dev/null http://10.255.255.1/; echo "exit=$?"
curl: (28) Connection timed out after 2011 milliseconds
real	0m2.122s
exit=28

정확히 2.011초 후 연결 시도가 중단되며 curl은 종료 코드 28을 반환했다. curl manpage에 따르면 --connect-timeout은 오직 연결 단계(connection phase)에 허용되는 최대 시간만을 규정하며, 연결이 성립된 이후의 데이터 전송 단계는 간섭하지 않는다.

6.2 전체 작업을 끊는 -m(--max-time)의 우선순위

반면 -m(또는 --max-time)은 공식 문서에 Maximum time in seconds that you allow the whole operation to take로 정의되어 있듯이, DNS 조회부터 본문 수신 완료까지 전체 작업에 허용되는 총 시간이다.

두 옵션이 동시에 주어졌을 때의 우선순위를 검증하기 위해 --connect-timeout 5와 -m 0.2를 동시에 지정하여 정상 서버에 요청을 보냈다.

curl -sS --connect-timeout 5 -m 0.2 -o /dev/null https://example.com/; echo "exit=$?"
curl: (28) Connection timed out after 204 milliseconds
exit=28

연결 타임아웃을 5초로 넉넉하게 주었음에도 불구하고, 전체 작업 제한인 -m 0.2가 먼저 동작하여 204밀리초 만에 통신을 끊었다. 즉, -m이 --connect-timeout보다 짧으면 연결 단계라 할지라도 -m이 우선하여 강제 종료한다.

흥미로운 점은 같은 종료 코드 28이라도 실패가 발생한 단계에 따라 에러 메시지가 달라진다는 사실이다.

  • 연결 성립 전 타임아웃: curl: (28) Connection timed out after 204 milliseconds
  • 연결 후 응답 대기 중 타임아웃 (-m 0.5 지정 시): curl: (28) Operation timed out after 514 milliseconds with 0 bytes received (이때 http_code는 000 반환)

또한 -m 0.58을 부여하여 총 소요 시간(0.578초) 내에 정상 전송이 완료된 경우에는 종료 코드 0과 HTTP 200이 정상적으로 반환되었다.

7. 스크립트 연동을 위한 -sS, -f, 그리고 JSON 출력

CI/CD 파이프라인이나 감시 스크립트에서 curl을 단독 실행할 때, 플래그 선택의 미세한 차이가 심각한 감시 누락을 만든다.

7.1 오류 출력을 살리는 -sS와 실패 종료 코드를 내는 -f

존재하지 않는 도메인 nonexistent.invalid를 조회했을 때의 실측 결과다.

curl -sS -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl -s  -o /dev/null https://nonexistent.invalid/; echo "exit=$?"
curl: (6) Could not resolve host: nonexistent.invalid
exit=6
=== -s alone hides error
exit=6

진행률 막대만 끄려고 -s(--silent)만 사용하면 오류 메시지까지 함께 사라져 원인을 확인할 수 없다. 스크립트에서는 반드시 조용히 실행하되 에러는 표준 에러로 출력하는 -sS(--silent --show-error) 조합을 써야 한다. 도메인 해석 실패 시 종료 코드는 로컬 매뉴얼 명세대로 6이다.

더 위험한 함정은 HTTP 404 같은 오류 응답이다.

curl -s  -o /dev/null -w '%{http_code}\n' https://example.com/no-such-page; echo "exit(no -f)=$?"
curl -sf -o /dev/null https://example.com/no-such-page; echo "exit(-f)=$?"
404
exit(no -f)=0
exit(-f)=22

이 실험에서 curl은 404를 받고도 -f가 없으면 종료 코드 0(성공)을 반환했다. $?만 보는 스크립트는 멈추지 않고 계속 진행된다. -f(--fail)를 붙여야만 HTTP 400 이상에서 종료 코드 22를 내며 스크립트가 멈춘다. 헤더만 확인할 때는 -I(HEAD 요청 전송)를 쓰고, 리다이렉트를 추적할 때는 -L을 조합하여 최종 %{url_effective}와 %{http_code}를 점검해야 한다.

다음은 실제 테스트를 통해 검증된 종료 코드와 메시지 정리 표다.

상황 지정 옵션 종료 코드 실제 반환된 에러 메시지
응답 없는 사설 IP 연결 시도 --connect-timeout 2 28 Connection timed out after 2011 milliseconds
연결 중 전체 시간 초과 -m 0.2 28 Connection timed out after 204 milliseconds
응답 대기 중 전체 시간 초과 -m 0.5 28 Operation timed out after 514 milliseconds with 0 bytes received
존재하지 않는 도메인 조회 -sS (-s 만 쓰면 문구 없이 6) 6 Could not resolve host: nonexistent.invalid
HTTP 404 응답 수신 (-f 미지정) 0 (에러 없음, 정상 수신으로 처리)
HTTP 404 응답 수신 -f 지정 22 — (-s 로 문구가 숨겨져 출력 없음)

7.2 curl 8.12의 %{json} 및 %{header_json} 활용

별도의 복잡한 서식 파일을 관리하지 않고 구조화된 지표를 다루고자 한다면, curl이 제공하는 JSON 내보내기를 쓸 수 있다. curl 8.12.1 환경에서 %{json}과 %{header_json}을 실측했다.

curl -s -o /dev/null -w '%{json}' https://example.com/ | python -c "…키 개수와 일부 키 출력…"
curl -s -o /dev/null -w '%{header_json}' https://example.com/ | head -c 120

실제 반환된 파싱 결과다.

keys: 67
http_code = 200
time_namelookup = 0.016632
time_connect = 0.144654
time_appconnect = 0.431361
time_starttransfer = 0.568338
time_total = 0.568422
remote_ip = 172.66.147.243
http_version = 1.1
scheme = https
exitcode = 0
errormsg = None
curl_version = libcurl/8.12.1 Schannel zlib/1.3.1 brotli/1.1.0 zstd/1.5.6 libidn2/2.3.7 libpsl/0.21.5 libssh2/1.11.1
=== -w %{header_json} support
{"date":["Mon, 28 Sep 2026 22:43:41 GMT"],
"content-type":["text/html; charset=utf-8"],
"transfer-encoding":["chunked"

curl 8.12.1의 -w '%{json}'은 67개의 키를 가진 단일 JSON 객체를 완전하게 출력한다. 시간 변수뿐만 아니라 exitcode, errormsg, curl_version, remote_ip까지 전부 포함되어 있으므로, jq나 Python 스크립트와 파이프라인으로 연결하여 특정 지연 임계값을 감시하기에 적합하다. %{header_json}도 응답 헤더를 JSON 형태로 냈다(출력 앞 120바이트만 확인).

확인하지 못한 것

본 포스트의 모든 분석은 실제 명령 실행과 공식 문서를 대조하여 검증했으나, 현재 테스트 환경의 한계로 인하여 다음 사항은 직접 확인하지 못했다.

  • OpenSSL 기반 빌드의 상세 TLS 출력 줄: 본 검증은 Schannel 백엔드를 쓰는 curl 8.12.1(x86_64-w64-mingw32 빌드)에서만 수행되었다. Linux나 macOS에서 흔한 OpenSSL 기반 curl의 -v에 TLS 관련 줄이 어떻게 나오는지는 이 환경에서 확인하지 못했다.
  • libcurl manpage 공식 time_* 정의 원문: Everything curl 가이드와 manpage의 옵션 설명은 대조했으나, libcurl C API 레벨의 CURLINFO_* 변수별 공식 정의 문구는 확인하지 못해 실험 2의 누적 시각 관찰로 뺄셈식을 정의했다.
  • HTTP/2 환경에서의 다중 스트림 누적 시간: 테스트에 사용된 curl 빌드가 HTTP/2 기능을 포함하지 않아(using HTTP/1.x), HTTP/2 환경에서 단일 연결 위 다중 스트림 요청 시 각 지표가 어떻게 기록되는지는 직접 측정하지 못했다.

# curl 진단 플래그와 지연 구간 분해 - 실무 참조표

검증 환경: Windows 10 Pro 10.0.19045, curl 8.12.1(Schannel), Git Bash, Python 3.13.3.
표의 값과 메시지는 이 환경에서 실행해 확인한 것이다(시간은 1회 측정값). 4번의 3번 명령은 예시로, 이 조합 자체는 실행하지 않았다.

## 1. 어느 구간이 느린가 — 차이로 읽기

curl 의 `time_*` 변수는 요청 시작부터의 **누적 시각**이다. 단계별 소요 시간은 앞선 단계 값과의 뺄셈으로 구한다.

| 커진 구간 | 계산식 (누적값의 차) | 이 환경 실측 (1회) | 느릴 때 의심할 곳 (일반 배경) |
|---|---|---|---|
| DNS 조회 | `time_namelookup` | 16.8 ms | 로컬 캐시 미스, 재귀 리졸버 응답 지연 |
| TCP 연결 | `time_connect - time_namelookup` | 131.3 ms | 네트워크 왕복 시간(RTT), 방화벽 패킷 지연 |
| TLS 핸드셰이크 | `time_appconnect - time_connect` | 328.7 ms | 인증서 체인 검증, 암호 스위트 협상 (가장 큼) |
| 서버 첫 바이트 대기 (TTFB) | `time_starttransfer - time_pretransfer` | 142.7 ms | 서버 연산 부하, DB 쿼리 병목, 캐시 미스 |
| 본문 받기 전송 | `time_total - time_starttransfer` | 0.1 ms (713 B) | 응답 본문 크기, 네트워크 대역폭 제한 |

## 3. 실무 점검표

- [ ] **형식 파일 줄바꿈 함정**: 형식 파일(`@curl-format.txt`) 안에는 실제 줄바꿈이 아니라 글자 그대로 `\n` 을 적어야 한다 (실제 줄바꿈은 curl 내부 `file2string()` 에서 버려진다).
- [ ] **스크립트 기본 옵션**: 스크립트에서는 진행률을 끄고 에러는 보이게 하는 `-sS`(`--silent --show-error`)를 사용한다.
- [ ] **HTTP 오류 상태 감지**: `-f`(`--fail`) 없이는 404 응답도 종료 코드 0으로 끝났으므로(문서: `-f` 는 400 이상에서 22) 반드시 `-f` 를 붙이거나 `%{http_code}` 를 검증한다.
- [ ] **타임아웃 우선순위 제어**: `--connect-timeout`(연결 한도)과 `-m`(전체 한도)을 함께 둘 때, `-m` 이 더 짧으면 연결 단계에서도 `-m` 이 먼저 끊는다.
- [ ] **Schannel 빌드 특성**: 이 환경의 Schannel 빌드(curl 8.12.1, x86_64-w64-mingw32)의 `-v` 에는 TLS 상세 줄(버전·암호 스위트·인증서)이 나오지 않으므로 TLS 시간은 `-w` 의 `time_appconnect` 로 잰다.
- [ ] **지원 프로토콜 확인**: 빌드마다 기능이 다르므로 진단 전 `curl -V` 로 HTTP2 지원 여부 등을 먼저 확인한다.

## 4. 권장 진단 템플릿

### 정밀 지연 측정용 형식 파일 (`curl-format.txt`)
```text
namelookup:    %{time_namelookup}\n
connect:       %{time_connect}\n
appconnect:    %{time_appconnect}\n
pretransfer:   %{time_pretransfer}\n
starttransfer: %{time_starttransfer}\n
total:         %{time_total}\n
http_code:     %{http_code}\n
size_download: %{size_download}\n
remote_ip:     %{remote_ip}\n
```

### 실행 명령어 예시
```bash
# 1. 단계별 밀리초 측정
curl -s -o /dev/null -w @curl-format.txt https://example.com/

# 2. JSON 통계 추출 (curl 8.12.1 에서 확인)
curl -s -o /dev/null -w '%{json}' https://example.com/

# 3. 안전한 스크립트 호출 예시 (값 3·10 은 예시, 이 조합 자체는 실행하지 않음)
curl -sS -f --connect-timeout 3 -m 10 -o output.dat https://example.com/
```

복사해서 메모 앱이나 AI 도구에 그대로 붙여 넣으세요.
