背景 — AIエージェントにリアルタイムWeb検索の文脈を与えるインターフェース

大規模言語モデル（LLM）を使うAIエージェントが抱える限界は、モデルがある時点までのデータで学習したあと、そのまま固定されていることである。そのため知識カットオフ（knowledge cutoff）より前の情報しか知らず、最近の出来事や変わっていくAPI、動きの速いニュースをモデルと一緒に扱うのは難しい。Aboutページは、検索がない場合にリアルタイム情報を必要とするエージェントが、たいていページのURLを推測して直接取得しようとし、推測が外れれば要求が404 Not Foundを返されてエージェントがやり直すことになると説明している。

2026年10月2日にCloudflareが変更履歴で公開したWeb Search APIは、ベータで利用できる。変更履歴は、このAPIによってAIエージェントやアプリケーションがインターネットを検索し、URLを推測したりモデルの学習カットオフに頼ったりする代わりにリアルタイム情報に根拠づけて応答できると紹介している。人が検索エンジンから作業を始めるように、エージェントがクエリを送ると関連性のある最新の結果一覧が返り、開発者はその結果をモデルのコンテキストに入れて、応答がリアルタイム情報に基づくようにする。

Aboutページが記す処理の順序は4段階である。まず、指定したAI Gatewayを経由してリクエストを送る。次に、選んだ検索プロバイダ（Ceramic.ai、Exa、Linkup）にクエリを転送し、プロバイダを指定しなければCeramic.aiが既定になる。続いて、プロバイダの応答を、結果ごとにURLとタイトル、そして任意の説明・画像・ファビコン・最終更新日を持つ一貫した形式に正規化する。最後に、リクエストをAI Gatewayのログに記録してアカウントに請求する。この流れで目に付く点は、ドキュメントによれば次の4つである。

  • 第一に、Ceramic.ai・Exa・Linkupがすべて同じ結果形式に正規化されるため、ドキュメントの表現どおりパラメータを1つ変えるだけでプロバイダを切り替えられる。
  • 第二に、すべてのリクエストはAIアプリケーションの制御プレーン（control plane）と紹介されるAI Gatewayを経由し、検索要求がモデル推論要求と並んでゲートウェイのログと分析に現れる。
  • 第三に、統合課金（Unified Billing）により、AI Gatewayのクレジット残高から各プロバイダの定価（list API price）どおりに、追加マージンなしで差し引かれる。
  • 第四に、3社はCloudflareの検証済みボット（Verified Bot）クローリング基準を守ると約束（committed）しており、Aboutページはすべての検索結果にクロールしたコンテンツの所在へのリンクが必要だと書いている。

基本設計 — AI Gatewayの単一窓口と統合課金アーキテクチャ

Web Search APIはAI Gatewayの上に作られている。How to useページは、任意のバックエンドから使えるREST APIとWorkerのAIバインディングという2つの呼出方法が、どちらもAI Gatewayを経由してリクエストを送ると書いている。すべてのアカウントにはdefaultという名前のゲートウェイがあり、必要ならゲートウェイを新しく作ることもできる。始めるにはCloudflareアカウントとAI Gatewayが必要で、アカウントにチャージしたAI Gatewayクレジットか、ゲートウェイに保存したプロバイダのAPIキーのどちらかが用意されている必要がある。

Aboutページは、すべての検索要求がゲートウェイを通るために得られるものを次の4点にまとめている。

  • 可観測性（Observability）：検索要求がモデル推論要求と並んで、ゲートウェイのログと分析に現れる。
  • 統合課金（Unified Billing）：検索はAI Gatewayのクレジット残高から差し引かれ、各プロバイダの定価をそのまま支払い、追加マージンはない。料金はProvidersページにある。
  • 独自キー（BYOK）：すでに検索プロバイダのアカウントがあれば、プロバイダのAPIキーをゲートウェイに保存でき、その場合はプロバイダが直接請求する。
  • アクセス制御（Access control）：ゲートウェイが使えるプロバイダと、リクエストを送れる主体を制御する。

Providersページも同じ内容を請求方式として言い直している。AI Gatewayクレジットで支払う場合は各検索がプロバイダの定価で請求され追加マージンはなく、独自キーを持ち込む場合はプロバイダが本人との契約に基づいて直接請求するという説明である。

この構造では、検索呼出の記録と請求がゲートウェイ1か所に集まるというのがドキュメントの要点である。ただし、アクセス制御をどのような規則で設定するのか、ゲートウェイのログにリクエストのどの項目が残るのかは、これらのドキュメントに説明がない。モデル推論のコストと検索のコストを同じクレジット残高で見られるところまでが、ドキュメントで確認できる範囲である。

検索プロバイダ3社の特性とZero Data Retention表記の比較

ベータ公開時点で選択可能な検索プロバイダはCeramic.ai、Exa、Linkupの3社である。リクエスト時にproviderパラメータで指定することで即座に切り替わり、パラメータを省略した場合はデフォルトとしてCeramic.aiが使用される。3社はインデックス規模、検索アルゴリズム、スニペット生成方式、および料金面で明確な差別化が図られている。

以下の表は、公式開発者ドキュメント（Providers）に記載された各プロバイダの仕様と価格をまとめたものである。

ceramic（デフォルト） 400億ページ以上の独自Webインデックス、低遅延・低コスト設計 最大8,000文字の詳細な本文要約説明 Yes（対応） $0.25（1件あたり$0.00025）

ここで公式ドキュメントの記述が食い違う。2026年10月2日付の変更履歴の本文には、3社すべてがCloudflare経由のリクエストについてZero Data Retentionをサポートすると書かれている。ところが同じ日に更新されたProvidersページの属性表では、ExaのZero Data Retentionの値がNoと記載されている。Ceramic.aiとLinkupは表でもYesで一致している。どちらが正確かを示す追加の訂正は確認されていないため、検索クエリがプロバイダのサーバーに残ってはならない環境では、詳細表の値を基準にしてproviderにCeramic.aiかLinkupを指定するのが、両方の文書と矛盾しない選び方である。

Providersページはプロバイダごとの特性を次のように紹介している。どのような用途に合うかという記述は、すべてドキュメントが各プロバイダに付けた文言である。

  • Ceramic.ai：エージェントとLLMアプリケーションのために設計した独自のWebインデックス（400億ページ以上）を運用し、低遅延・低コストの検索に重点を置く。ドキュメントは、1つのタスクで何度も検索するエージェント、チャットボットの回答を最新情報に根拠づける用途、モデル出力をリアルタイムのWeb情報源と照合する用途に向いている（a good fit）と書く。結果にはページごとに最大8,000文字の長い説明が入り、価格は1,000件あたり0.25ドルである。
  • Exa：AIのために作られた検索エンジンで、従来のキーワード検索と埋め込みベースの検索を組み合わせた独自インデックスを使う。リクエストは品質と速度のバランスを狙ったauto検索タイプを使い、クエリに最も関連するテキストの抜粋であるハイライトが結果の説明として返る。ドキュメントは、簡潔でクエリに沿った抜粋をモデルのコンテキストにそのまま渡したい場合に向いていると書き、価格は1,000件あたり7.00ドルである。
  • Linkup：AIアプリケーション向けのWeb検索で、Web全体から出典付きの結果とテキストスニペットを返す。リクエストはfast検索深度と生の検索結果を使うため、回答は生成されない。ドキュメントは、信頼できる情報源からの素早く引用可能な結果が必要なエージェントのツール呼出に向いていると書き、価格は1,000件あたり5.00ドルである。
  • 結果形式：Aboutページは、すべてのプロバイダが同じ結果形式（URL・タイトル、任意の説明・画像・ファビコン・最終更新日）を返すので、providerの値を1つ変えるだけで切り替えられると書く。説明は任意項目なので、すべてのプロバイダが常に埋めると想定しないほうが安全である。

Providersページは、プロバイダごとに属性表を置き、provider値、Zero Data Retentionの可否、価格とともに、プロバイダのドキュメントと利用規約へのリンクを載せている。規約とデータの扱いはプロバイダが定めるため、実際に導入する前に各プロバイダの規約ページを別に開いて確認する必要があるということである。

呼出インターフェース — REST APIとWorkers AIバインディングの仕様

Web Search APIは、任意のバックエンドから呼び出せる標準REST APIと、Cloudflare Workersから直接呼び出せるAIバインディングの2通りの呼出方法を提供する。

REST APIはPOST https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/websearch/のエンドポイントにリクエストを送る。認証には2つの権限を両方持つCloudflare APIトークンを使う。アカウントレベルのWorkers AI > ReadとAI Gateway > Readである。

公式ドキュメントに記載されたREST APIのcurl呼出例は以下の通りである。

curl https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/ai/websearch/ \
                      --request POST \
                      --header "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
                      --header "Content-Type: application/json" \
                      --data '{
                        "query": "What are some fun things to do in Salt Lake City as fall approaches?",
                        "provider": "ceramic",
                        "limit": 5,
                        "options": { "gateway": { "id": "default" } }
                      }'

Workers環境では、Wranglerの設定ファイルにAIバインディング（ai: { binding: "AI" }）を追加したうえで、env.AI.websearch()にゲートウェイIDとクエリを渡す。ドキュメントの設定例はcompatibility_dateを2026-10-05とし、この値をその日の日付に合わせるよう促すコメントを添えている。websearch()は標準のResponseオブジェクトを返すので、response.json()で結果を読む。

export default {
                    	async fetch(request, env): Promise<Response> {
                    		const response = await env.AI.websearch({
                    			gatewayId: "default",
                    			query: "What are some fun things to do in Salt Lake City as fall approaches?",
                    			provider: "exa",
                    			limit: 5,
                    		});
                    
                    		const results = await response.json();
                    		return Response.json(results);
                    	},
                    } satisfies ExportedHandler<Env>;

ドキュメントが記すリクエストパラメータは次のとおりである。RESTの本文ではゲートウェイをoptionsオブジェクトに、Workerの呼出ではgatewayIdに入れる。

  • query（必須、文字列）：検索クエリで、minLengthは1、maxLengthは1,024である。
  • provider（任意、文字列）：ceramic、exa、linkupのいずれかで、既定値はceramicである。
  • limit（任意、整数）：返却する検索結果の最大件数である。最小1、最大10で既定値は10であり、1回のリクエストで返る結果は10件が上限である。
  • options.gateway.id（REST、必須）またはgatewayId（Worker、必須）：リクエストをルーティングするAI GatewayのIDである。既定のゲートウェイを使うときはdefaultを指定する。
  • byokAlias（任意、文字列）：ゲートウェイに保存したプロバイダAPIキーの別名で、パターンは^[A-Za-z0-9_-]{1,64}$である。指定したのに該当するキーが構成されていなければ、AI Gatewayクレジットにフォールバックせずリクエストが失敗する。

返却されるJSONレスポンスは、すべてのプロバイダで共通化された以下の形式を持つ。

{
                      "items": [
                        {
                          "url": "https://example.com/salt-lake-city-fall-guide",
                          "title": "Fall in Salt Lake City: A Local's Guide",
                          "description": "From scenic drives up Big Cottonwood Canyon to pumpkin patches..."
                        }
                      ],
                      "metadata": {
                        "query": "What are some fun things to do in Salt Lake City as fall approaches?",
                        "requestId": "<REQUEST_ID>",
                        "latencyMs": 612
                      }
                    }

応答本文は、どのプロバイダでもitems配列とmetadataオブジェクト（query、requestId、latencyMs）で構成される。結果アイテムにはurlとtitleが基本で入り、説明・画像・ファビコン・最終更新日はプロバイダが返したときだけ含まれる。ドキュメントのレスポンス形式の説明も、任意項目はプロバイダが返すときだけ含まれると書いている。

How to useページは、検索をモデルのツールとして使う例も載せている。web_searchという関数ツールをモデルに定義しておき、モデルがそのツールを呼び出したらwebsearch()で検索を実行して、結果をtoolロールのメッセージとしてモデルに返す流れである。例ではWorkers AIのモデルを呼び出し、検索結果を5件に絞っている。ドキュメントが記す制限は2つだけで、クエリ長1,024文字とリクエストあたり結果10件である。

クローラー基準と情報源の明記 — プロバイダが約束した基準

Aboutページの「Crawler standards」の節は、Cloudflareの立場から始まる。クローラーは正直で透明であるべきで、サイト所有者が定めた規則や希望を尊重すべきであり、サイト所有者は自分のコンテンツがどう使われるかについて意味のある可視性と制御権を持つべきだという立場である。

続いてページは、すべてのWeb Search APIプロバイダが次の基準を満たすことを約束した（has committed）と書いている。

  • 検証済みボットの遵守（Verified bot compliance）：プロバイダが使うクローラーは、Cloudflareが公開した検証済みボットの要件を満たす必要がある。この要件にはクローラーを識別できるようにすることと、robots.txtを尊重することが含まれる。
  • 情報源の明示（Source attribution）：すべての検索結果は、クロールしたコンテンツの所在へのリンクを含まなければならない。
  • ページが結びで要約している目的：このAPIを使うと、エージェントは、コンテンツがどうクロールされるかについてサイト所有者に透明性・制御権・可視性を与える事業者の検索結果を利用することになる。

ここまでがドキュメントが直接書いている内容である。約束が実際にどのように確認されるのか、サイト運営者が個々のプロバイダのクローラーをどう識別して制御するのかは、これらのドキュメントに書かれていない。変更履歴が述べる「約束」とAboutページの2つの基準をそのまま伝えるところで止めるのが、この節の範囲である。

独自APIキー（BYOK）の運用とシークレット管理構造

How to useページによれば、すでに検索プロバイダのアカウントがある場合はAI Gatewayクレジットの代わりに自分のAPIキーを使うことができ、その場合はプロバイダが直接請求する。手順とキーの選択規則は次のとおりである。

  • ダッシュボードへの登録：Cloudflareダッシュボードで AI Gatewayのページに移動し、ゲートウェイを選んでProvider Keysを選択する。Ceramic.ai、Exa、Linkupのいずれかを選んでAPIキーを追加し、別名（alias、たとえばdefault）を付ける。プロバイダが一覧にない場合はConfigure custom providersを選んで追加する。
  • キーの保管：APIキーはリクエストに載せて送られない。AI Gatewayがプロバイダと別名に対応するゲートウェイ保存のキーを取り出して使い、保存されたキーはSecrets Storeで暗号化される。
  • 別名を指定した場合：byokAliasを渡すと、その別名の保存キーを使う。プロバイダまたは別名がゲートウェイに構成されていなければ、クレジットにフォールバックせず400エラーで失敗する。
  • 別名を省略した場合：ゲートウェイにそのプロバイダのdefault別名のキーがあればそのキーを使い、なければ検索はAI Gatewayクレジットに請求される。

ドキュメントのBYOK例は、クエリ「What is Cloudflare Workers?」に対してproviderをexa、byokAliasをdefaultに指定したリクエストである。呼出の形はクレジット方式と同じで、byokAliasの1行が加わるだけである。キー保管の詳細は、AI Gatewayの「Bring your own keys」ドキュメントを参照するようHow to useページが案内している。

公式ドキュメントの記述と未確認事項の対照

技術仕様を評価する上では、ドキュメントに明記された確定事項と、記載がなく未確定な領域を明確に区別することが肝要である。以下の表は、公式文書に記載された仕様と注意すべき未確認事項を対照したものである。

仕様項目 公式ドキュメントに明記された事項 未確認または注意すべき事項
データ保持方針 Ceramic.aiとLinkupはZero Data Retentionに対応と記載 変更履歴本文では3社対応とあるがProviders表ではExaがNoとなっており食い違いが存在
課金体系とマージン プロバイダ定価通りにAI Gatewayクレジットから減額、追加マージンなし 無料クレジット枠の有無やアカウント単位の最低チャージ金額は文書に未記載
リクエスト制約 クエリ最大1,024文字、結果最大10件（デフォルト10件）を上限として明記 アカウント全体の分あたり・日あたりのレートリミット上限値は文書に未記載
サポート対象環境 REST APIとWorkerのAIバインディングを記載、モデルのツール呼出例も掲載 LangChainやLlamaIndex、MCP（Model Context Protocol）向け専用アダプタは、これらのドキュメントでは確認できなかった

この対照結果を踏まえ、実際のシステム導入にあたって事前に検討すべきポイントは以下の通りである。

  • レートリミットの明確な数値が公開されていないため、高並行で大量のリクエストを行うバッチ処理ではリトライ設計を慎重に行う必要がある。
  • 1回のリクエストで最大10件しか取得できないため、広範なWeb調査を行うエージェントでは複数クエリへの分割設計が前提となる。
  • Exaのデータ非保持が表においてNoとされているため、機密情報や個人情報を含むクエリを扱う際はCeramic.aiまたはLinkupに限定して利用するのが安全である。
  • ローカル開発（wrangler dev）実行時に実際の外部API呼出が発生して課金されるのか、モック応答が返されるのかは記載がないため事前確認が必要である。

確認できなかったこと

  • ExaにおけるZero Data Retention対応に関する変更履歴本文（3社すべて対応）とProviders比較表（ExaはNo）のどちらが正確な現状であるかの事実関係。
  • Free、Workers Paid、Enterpriseなどのアカウントプラン別におけるWeb Search APIの分あたり・日あたりの呼出上限（Rate Limit）。
  • AI Gatewayの初期利用時にWeb Search APIに適用可能な無料検索枠やトライアルクレジットが存在するかどうか。
  • プロバイダ各社がWebを巡回する際に使用している固有のUser-Agent文字列およびIPアドレス範囲の詳細情報。
  • wrangler devを用いたローカル開発環境におけるenv.AI.websearch()のローカルシミュレーション対応の有無。
