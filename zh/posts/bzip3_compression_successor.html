换压缩器的决定，通常是靠一行数字做出的。同一个文件小了三成，这句话看上去就够了。那个数字可能是真的。问题在于，它只是决策所需的五块信息里的一块。

压缩器得到一个轴就要交出另一个轴。把压缩率往上推，压缩时间就长；有的设计连解压一起变慢，有的则守住解压这一侧。把块开大，压缩率会涨，但解的那一方所需的内存也同步变大。而且这个要求在压缩的那一刻就定死并写进文件，事后无法反悔。

还有一个轴。读这个格式的工具，在对方手上有没有。这不是算法的性质，而是生态的状态；在长期保存的场景里，它比前面四个加起来还重。

缘起 - 当三个形容词挤进同一句话

BZip3 仓库的第一句话，把自己介绍为 bzip2 更好、更快、更强的精神后继作。做过压缩的人看到这句，会先把它拆开。更好是压缩率；更快分成压缩速度还是解压速度两件事；更强通常指大块和多线程。三个形容词分别在三个轴上为真，而且各自只在各自的条件下为真。

本文取的角度不是工具介绍。跟着一个后继作买进了哪些轴、卖出了哪些轴，目的是立起一件事：选压缩器这个决定，实际上是在拿什么换什么。压缩率与预测精度为什么是同一个数，这类理论侧的问题另有讨论。这里要谈的不是那套理论，而是选择。

压缩器争夺的三个轴，以及后面附着的两个

先有三个轴：压缩率、压缩速度、解压速度。这三者并不粘在一起。要提压缩率就得用更精细的模型，模型一精细压缩就慢，而解压侧会不会跟着慢，取决于是哪一族。LZ 系解压比压缩便宜得多，因为解码端不必重建字典，照着指令复制即可。上下文建模系则要在两个方向上跑同一个模型、同样的顺序，于是两侧成本接近对称。

后面再附上两个轴：内存占用与并行度。这两个长期被当作次要项，但现在实务中真正掀翻决定的往往正是它们。容器的内存上限、CI 执行器的核心数、抢救介质上的内存容量，都会比几个百分点的压缩率更早卡住。

轴量的是什么得到它要交出什么在哪类工作里先卡住
压缩率同一份原件变成多少字节压缩时间，通常连内存一起冷备份、线路昂贵的传输、长期保管
压缩速度每秒吞进多少兆字节压缩率夜间批处理的窗口、实时写入
解压速度每秒吐出多少兆字节多半是压缩率，不过 LZ 系交出得少软件分发、镜像层、缓存还原
内存压缩与解压各自的峰值常驻大小压缩率，预算小就只能把块开小嵌入式、抢救介质、有内存上限的容器
并行度加核心能不能缩短墙钟时间内存，每个线程都要抱一个块多核构建服务器、生成超大归档

表的最后一列才是要害。同一个压缩器，在分发场景是好选择，在日志写入场景可能就是坏选择。不先确定这项工作卡在哪个轴上，比较就会坍缩成关于压缩率的一行字，决定也就选错了。

非对称是一条基础性质

多数无损压缩器解压比压缩快。1994 年原论文在结论里写道，和伦佩尔与齐夫的算法一样，它的算法解压比压缩快。这个非对称在实务中分量很重。分发件压缩一次，被解开成千上万次；因此在分发场景压缩时间几乎不算成本，只有解压时间与解压内存才是成本。反过来，每天要跑的备份，压缩时间直接吃掉维护窗口。

三十二年前的表今天仍然成立，原因是轴的数目没变。绝对数字随硬件变了，但推一个轴另一个轴就退回去的结构没变。

块排序变换在做什么 - 并行容易，流式很难

论文的算法 C 是这样定义的。对长度为 N 的字符串 S，造出 N 个旋转，按字典序排序，取每个旋转的最后一个字符拼成字符串 L。把原字符串 S 在排序表中所处行的序号记作 I。变换的输出只有这一对，而算法 D 仅凭 L 与 I 就能还原 S。

论文的例子本身就是解释。S 为 abraca、N 为 6 时，把六个旋转排序后 L 为 caraab，I 为 1。长度相同，字符构成也相同。变换本身一个字节都没减。

只是换了顺序，为什么就压得动

论文的说明只有两句。排序把首字符相同的旋转聚到一起；而既然是旋转，首字符左边紧挨着的就是末字符。于是 L 中相邻的字符，是在原文 S 里挨着相似字符串的那些字符。若上下文能很好地预测下一个字符，L 就会变成同一字符成团的串，而这种成团可以用移到前端编码这类简单的局部自适应方法廉价地剥掉。

论文点明的限制也在同一处：这个方法只用到每个字符一侧的上下文。论文所述实现是在移到前端编码之后接霍夫曼或算术编码，实际上每 16 千字节输入就重算一次霍夫曼树。

块为单位这一性质带来的两个结果

论文写道，它的算法不按顺序处理输入，而是把一块文本当作单个单位处理。从这一句里能推出两件事。

  • 并行化容易。块与块之间没有依赖，一个线程整块承包即可，加核心墙钟时间几乎线性缩短。bzip3 手册也把并行工作者数量的选项定义为各自处理一个块的工作者数。
  • 部分抢救可行。bzip2 手册写明每块独立处理，48 位模式用来分隔块，每块自带 32 位 CRC。能从损坏文件里挑出完好块的 bzip2recover 之所以成立，正是因为格式本身被切成了独立的片。
  • 流式很难。排序必须等块填满才能开始，也就是说第一个输出字节之前的延迟被块大小绑住。BZip3 的格式概览文档没有绕弯，直接写成块级压缩，没有流。
  • 最后这条性质划分了用途。像实时推日志的管线那样，此刻写下的字节此刻就得出去的地方，压缩率再好，块式设计也出局。反过来，把已经做好的 tar 放到夜里压，这条性质一点成本都不构成。

值得盯住的是倒数第三行。bzip2 即使把块开到最大，解压也用不到四兆字节。一个三十二年前的默认值至今还跑在抢救介质和嵌入式设备上，靠的是这个数字而不是压缩率。反过来，用 bzip3 的最大块，就等于要求解的那一方拿出三吉字节级的内存。

两份手册都强调同一句话：解压所需的内存，在压缩时选定块大小的那一刻就确定了。bzip2 手册说这个值是从文件头里读出来的，BZip3 格式规范也把最大块大小放在头部靠前的四个字节里。压缩看似是为自己方便而做的动作，实际上是此刻就为将来打开这个文件的机器定下配置要求。

所谓「后继作」实际改动的四处

BZip3 手册把自己的流水线概括为先做游程编码与伦佩尔齐夫预测，再做块排序变换与算术编码。仓库说明在此之上补了两点：熵编码是零阶上下文混合，块排序用的是后缀数组。与原论文的构成并排来看，改动的位置就显出来了。

预处理阶段是最显眼的改动。在重复很多的素材上这一步能摆多大，仓库的语料表写得很直接。115,742,720 字节的音频 tar，bzip2 压到 95,526,840 字节，即 82.5 个百分点；bzip3 压到 41,187,299 字节，即 35.6 个百分点。同一张表里，685,619,200 字节的 DNA tar 是 180,075,480 字节对 157,642,102 字节，差距只有一成二左右。同一个工具，会因素材性质不同而以完全不同的幅度取胜。

改了多少，交出去的也一样清楚。后面的基准一节会看到，压同样的素材 bzip2 用八兆字节，bzip3 在某些设定下用十八吉字节。这是把内存这个轴整个交出去，换回压缩率与并行度的设计。

同样的工具，不同的素材，分岔的结论

在 Silesia 这一组里，bzip3 用 16 兆字节块单线程花了17.42 秒，峰值 98 兆字节，得到 47,227,855 字节。同条件下 lzma -9 花了76.88 秒，675 兆字节得到 48,761,670 字节，zstd -19 花了83.43 秒，237 兆字节得到 53,000,145 字节。三个轴全都倒向 bzip3，这种情况并不多见。

可是到了 Linux 内核这一组，方向就变了。bzip3 用 76.93 秒得到 129,023,171 字节，而 lzma -9 花掉 397.30 秒，换来的是更小的 125,725,455 字节。同样两个工具，一换素材就在压缩率上互换了位置。抽掉是在哪个语料上测的，这两句话读起来就像互相矛盾。

Calgary 这一组给出速度轴的次序。bzip2 -9 最快，172.9 毫秒；其次 gzip -9 的 224.3 毫秒、bzip3 -b 3 的 265.3 毫秒、lzma -9 的 787.9 毫秒。同组内存是 gzip 5 兆字节、bzip2 8 兆字节、bzip3 17 兆字节、lzma 95 兆字节。结果大小的次序则是 bzip3 807,959 字节、lzma 853,112 字节、bzip2 891,321 字节、gzip 1,062,584 字节。五个轴里有三个指向三个不同的赢家。

Perl 这一组暴露内存轴的地方

被引用得最多的是 Perl 这一组。压缩结果为：bzip3 用 511 兆字节块得 546,456,978 字节，bzip3 用 256 兆字节块得 1,001,957,587 字节，xz 得 2,056,645,240 字节，zstd 得 3,076,143,660 字节，bzip2 得 3,441,163,911 字节。只看数字确实压倒性。

把同一份记录的内存列一起读，画面就变了。bzip2 用8 兆字节完成了这件事，而 bzip3 在 256 兆字节块十二线程下用了18,301 兆字节，在 511 兆字节块四线程下用了 12,178 兆字节；xz 在十六线程下用了 14,658 兆字节。这张表里 bzip3 赢下的轴是压缩率与墙钟时间，交出去的轴是内存，幅度在两千倍以上。

解压侧的墙钟时间记为：zstd 3 分 51 秒、bzip3 并行 4 分 06 秒、xz 4 分 40 秒、bzip2 9 分 22 秒。不过这些是在 WD Blue 一类机械硬盘上测的，因此其中相当一部分是在磁盘上读写的时间而非 CPU 工作。仓库说明另外给出的吞吐值，是用 clang13 构建的 x64 Linux 版本每线程压缩 17MiB/s、解压 23MiB/s，同一句话还补充说 Windows 与 32 位构建可能慢得多。这里解压快于压缩的非对称同样成立。

格式冻结了吗 - BZ3v1 与校验和事件

要考虑长期保存，比压缩率更该先看的是格式有没有冻结。BZip3 在这个问题上手里的材料不差：格式规范以文档形式公开，带版本号，还附了示例解析代码。

  • 文件头是九个字节：五字节签名 BZ3v1 加四字节最大块大小。库的高层函数所用的帧头在此基础上再加四字节块计数，共十三字节。
  • 整数一律小端且非对齐，规范同时给出了可移植的读写函数。
  • 最大块大小的有效范围是 65,536 字节到 535,822,336 字节。规范规定超出范围解析器必须拒绝。
  • 每个数据块前置四字节压缩大小与四字节原始大小。原始不足 64 字节就不尝试压缩，配上 CRC32 与 0xFFFFFFFF 这个标记原样收下。
  • 块里的 model 字节用比特位告知经过了哪些阶段：0x02 是 LZP，0x04 是 RLE。
  • 手册写明格式的固定开销是每文件九字节、每块九到十七字节，随机数据上的膨胀一般不到 0.8 个百分点。

即便如此，归档还是丢过未来

仓库的发布记录在1.3.2 这一条里写着：由于编程失误，CRC32 校验函数的移位方向弄反了，结果 1.3.0 与 1.3.1 给校验和计算引入了破坏性变更。该变更在 1.3.2 被回退。同一条随后补上后果：那两个版本生成的归档走正常路径解压会因校验和错误而失败，只有加上恢复选项才能取回原内容。

这件事说明的东西很清楚。格式规范就算写成文档，实现一晃动，文件照样丢掉未来。真理在实现而不在文档，那两个版本之间生成的文件成了坚称自己已损坏的正常文件。

记录里还有另一层的变动。1.5.0 写明块级编解码函数的签名改了，与旧版本不再 ABI 兼容；1.5.1 为了标示这个差别改了共享库名。这属于库接口层而非文件格式层，晃动主要发生在这一侧。同一条 1.5.0 另外写道，解码端收紧 LZP 与 RLE 的边界让压缩略有改善，但没有可观测的格式变化。把格式与实现分开记录这件事本身，就是判断材料。

地址也动了。1.5.3 那一条记录项目迁到了新账号。重定向能用，但论文、软件包元数据、旧文档里刻着的老地址仍留在原处。在长期保存里，链接是格式的一部分。

新压缩器为什么推不开 - 问题不在格式而在工具链

这里是全文的心脏。新压缩器推不开，多半不是因为算法差。选一个压缩器，等于把自己的数据绑到一个能读该格式的环境上，而那个环境的移动速度远远慢于代码。

实际可以核查的层有四重。

层看什么gzip / bzip2 / xz / zstdbzip3
标准归档工具GNU tar 1.35 的内置压缩标志都有专用标志没有，只能靠指定外部程序的选项接上
公共库libarchive 的过滤器常量清单在 gzip 到 zstd 的十五项之列不在清单里

发行版软件包各主要发行版收录的版本基本等同于基础安装的一部分收录广泛，但版本跨度达三年

第一重 - 标准归档工具认不认得

GNU tar 1.35 的压缩选项里，有为 gzip、bzip2、xz、lzma、lzop、zstd、compress 准备的专用标志，没有 bz3。逃生口是有的：用指定外部程序作为压缩过滤器的选项，任何压缩器都能接上。但这个选项要成立，解包那台机器上必须已经装了那个二进制。按扩展名自动判定压缩器的选项，也只对内部映射表里有的扩展名生效。

第二重 - 公共库认不认得

libarchive 公开头文件定义的过滤器常量是：无、gzip、bzip2、compress、外部程序、lzma、xz、uuencode、rpm、lzip、lrzip、lzop、grzip、lz4、zstd。没有 bzip3 这一项。这份清单之所以重要，是因为用 libarchive 的不止一家：bsdtar、macOS 上的 tar、构建工具、若干包管理工具都经由这个库来处理压缩格式。不在这里，就意味着上述工具全都不认识那个扩展名。

第三重 - 语言标准认不认得

Python 3.13 标准库里有 gzip、bz2、lzma、zlib，没有 bz3 模块，tarfile 接受的压缩模式也只有 gz、bz2、xz。在用一行脚本打开归档的场合，新格式制造出一道叫作要额外装依赖的门槛。这道门槛在开发环境里低，在生产环境、尤其是别人的环境里高。

第四重 - 手上的版本是不是同一个

按软件包聚合口径，bzip3 登记为 148 个条目，主要发行版大体都收了。问题在版本。Debian 12 稳定版是 1.2.2，Ubuntu 24.04 是 1.4.0，Fedora 43 及以后连同 Arch、openSUSE Tumbleweed、nixpkgs、FreeBSD、MSYS2 是 1.5.3，Homebrew 与 Gentoo 是 1.5.4。最旧和最新之间横着三年。这意味着压缩的机器与解压的机器版本不同才是默认状态，而上一节的校验和事件恰恰就发生在这道缝里。

二十年后还能打开吗

就这个问题而言，BZip3 留下的材料不算差。格式有成文规范，头部结构与整数表示都有定义，示例解析器已公开，源码以 LGPLv3 开放，签名固定五字节因而看文件就能认出格式。理论上仅凭现有文档就能重新实现。

但能重新实现，和到那时手边有工具，是两个不同的命题。gzip 和 bzip2 今天到处都在，靠的不是压缩率，而是它们本来就到处都在这个事实本身。二十年后要打开归档的人需要的不是最优压缩率，而是那台机器上已经装好的一条命令。

所以格式选择不是压缩率的计算，而是一份依赖契约。只在自家范围内流转的数据，契约面窄，版本也可控；一旦出了门或者要活过十年，契约的对手方是谁就说不清了。讨论备份是否真能活着回来的恢复验证一文，以及讲二十年前格式留下的编码遗产的zip 文件名一文，最终指向的是同一个位置。格式留得久，读它的环境留不住。

什么场景选什么 - 从条件走向性质

推荐具体产品的表格活不长，因为版本会变、默认值会跟着变。活得长的是从条件指向性质的那支箭头。

只读命令就能确认的事

下面全部是只读操作，既不创建也不删除文件，也不制造负载。

先看手上这套工具认得哪些格式。下面这组命令，就是在自己的环境里复现上一节四重中的第一重和第三重。

# 这台机器的 tar 内置认得哪些压缩器
tar --help | sed -n '/Compression options/,/^$/p'

# Python 标准库里有哪些压缩模块
python3 -c "import gzip, bz2, lzma, zlib; print('stdlib ok')"

# 不存在的模块会以异常作答，这才是正确结果
python3 -c "import bz3" ; echo "exit=$?"

只读文件开头，就能提前知道格式和解压需求。bzip3 的文件头是五字节签名加四字节最大块大小，所以看前九个字节就够。

# 签名五字节。看到 BZ3v1 就是 bzip3 文件
head -c 5 sample.bz3 | od -An -c

# 接下来四字节是最大块大小，小端无符号 32 位
head -c 9 sample.bz3 | od -An -t u4 -j 5 -N 4

# bzip2 的 BZh 之后那一位数字，是块大小以 100 千字节为单位的数
head -c 4 sample.bz2 | od -An -c

知道块大小之后，解压所需内存就能事先算出来。公式直接照手册。

# bzip3 约为块大小的六倍。511 兆字节的块大约要 3 吉字节
python3 -c "b=511*1024*1024; print(round(b*6/1024/1024), 'MiB')"

# bzip2 是 100k 加块大小的四倍，即便最大块也不到 4 兆字节
python3 -c "b=900*1000; print(round((100*1000+4*b)/1024/1024,2), 'MiB')"

最后还是要用自己的素材去测。挑一个样本，在同一条件下把几个轴一起记下来。只记大小，就会把上一节看到的陷阱原样重演一遍。

# 把输出大小、峰值常驻内存和时间记在一行里
/usr/bin/time -v gzip  -9 -k -c sample.tar | wc -c
/usr/bin/time -v bzip2 -9 -k -c sample.tar | wc -c
/usr/bin/time -v xz    -9 -k -c sample.tar | wc -c

# 解压这个轴要单独测。对分发件来说这是唯一的成本
/usr/bin/time -v gzip  -dc sample.tar.gz | wc -c

未能确认的部分

  • Perl 基准所用的硬件在说明里没有。CPU 型号、核心数、内存容量都没写，只有命令行上的线程数和解压时所用的硬盘型号。这些绝对时间无法作为与其他环境比较的依据。
  • 同一基准里，511 兆字节块四线程那一行的用户 CPU 时间记为 17.65 秒，而同表其他行都在数百到数千秒，且该行自己的墙钟时间是 7 分 08 秒。这个量级对不上的数值，成因在说明的叙述范围之外，无法在此确定。
  • 17 种语料的大小表没有附上块大小、线程数与硬件。同一文档的其他小节给了命令行，但那些条件是否同样适用于大小表，文档层面无法确定。本文只把该表用于大小比较。
  • 第三方复现基准未被采信。说明所指向的外部基准仓库未曾打开，因此本文关于性能的一切叙述都出自开发者本人的测量。
  • 试图从上游源码核对 GNU tar 按扩展名自动判定的映射表，但该路径没有响应。文中涉及 tar 的叙述，限定在 GNU tar 1.35 的帮助输出范围内。
  • 各发行版的软件包版本来自聚合站点的查询结果，并未逐一比对各发行版自己的仓库，查询时点之后可能已经变动。
  • 零阶上下文混合预测器的内部没有展开。上下文如何定义、混合如何进行需要源码级的叙述，而说明与手册给出的范围只到上下文混合与算术编码这两个名字。
  • libsais 实际走的是哪一种变体无法确定。该库的说明只写明以诱导排序一系的四篇论文为基础，而 bzip3 究竟走其中哪条路径并无另外的叙述。
  • 中间编码阶段的移到前端编码被什么取代，文档层面无法确定。说明与手册都未单独提及该步骤，因此本文表格里那一格留作未详。
