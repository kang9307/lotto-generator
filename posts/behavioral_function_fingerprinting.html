「출력이 같다」는 「같은 함수다」가 아니다 - 바이트 대신 행동으로 함수를 판정할 때 남는 오탐과 미탐

모양이 무너진 자리에서 무엇이 남는가, 그리고 실행해서 비교한다는 결정이 청구하는 대가

2026-09-10 개발/인프라

이름이 지워진 실행 파일을 앞에 두었을 때 먼저 정해야 하는 것은 「이 함수가 무엇인가」가 아니다. 무엇을 근거로 「같다」고 말할 것인가이다. 근거를 정하지 않으면 답도 정해지지 않고, 근거가 달라지면 같은 파일에서 다른 답이 나온다.

근거는 오래전부터 두 갈래였다. 하나는 모양을 재는 길이다. 바이트가 얼마나 겹치는지, 제어 흐름의 그래프가 얼마나 닮았는지를 본다. 다른 하나는 행동을 재는 길이다. 함수에 값을 넣고 무엇이 나오는지, 그 과정에서 무엇을 읽고 무엇을 쓰는지를 본다. 두 길은 잘하는 것이 다르고, 그보다 중요하게는 틀리는 모양이 다르다.

아래에서 따라가는 축은 두 번째 길이다. 특히 그 길을 택했을 때 반드시 따라오는 두 가지 실패 — 서로 다른 함수를 같다고 부르는 오탐과, 같은 함수를 다르다고 부르는 미탐 — 이 각각 어디서 생기고 무엇으로 줄어드는지다.

계기 - 실행 동작으로 함수를 맞추는 도구

계기가 된 것은 fnprint 라는 도구다. 저장소의 README 는 스스로를 이렇게 규정한다. 바이트나 제어 흐름 그래프가 어떻게 생겼는지가 아니라 함수가 무엇을 하는지로 바이너리 안의 함수를 맞춘다는 것이다. 각 함수를 작은 에뮬레이터 안에서 아무 값이나 넣어 돌리고, 그 과정에서 남는 효과를 기록해 지문으로 바꾼다.

README 가 밝히는 용도는 세 가지다. 심볼이 지워진 바이너리에 이름을 붙이는 것, 두 빌드 사이의 행동 변화를 짚는 것, 그리고 알려진 취약 코드 묶음과 고쳐진 코드 묶음에 견주어 정체를 모르는 함수의 순위를 매기는 것이다. 현재는 x86-64 ELF 만 다루며 ARM64 와 MIPS, PE 와 Mach-O 로더는 계획으로 적혀 있다. Rust 로 쓰였고 MIT 라이선스다.

도구 자체보다 흥미로운 것은 이 도구가 택한 판정 근거다. 실행해서 비교한다는 결정은 공짜가 아니다. 그것이 무엇을 사고 무엇을 지불하는지가 이 글의 본론이다.

모양으로 판정한다는 것 - 바이트와 그래프

모양을 재는 길은 오래됐고 지금도 실무의 기본이다. 크게 세 가지를 센다.

  • 바이트 시퀀스 — 함수의 앞부분 기계어를 그대로 대조한다. 다만 주소나 재배치가 들어가는 자리는 값이 매번 달라지므로 그 자리를 가변으로 표시해 두고, 나머지가 겹치는지를 본다.
  • 제어 흐름의 모양 — 기본 블록을 꼭짓점으로, 분기를 간선으로 놓은 그래프를 만들어 두 함수의 그래프가 얼마나 닮았는지를 잰다. 명령 하나가 바뀌어도 그래프의 골격은 남는 경우가 많아 바이트 대조보다 견딘다.
  • 붙어 있는 표지 — 문자열 상수, 매직 넘버, 호출하는 외부 심볼의 이름 같은 것들이다. 이 표지는 최적화가 잘 건드리지 않아 단서로서 값이 크지만, 표지가 아예 없는 함수에는 쓸 수 없다.

이 방식들이 잘하는 일은 분명하다. 빠르고, 실행하지 않으며, 맞을 때는 아주 정확하다. 같은 빌드 환경에서 만들어진 같은 라이브러리를 알아보는 일이라면 이보다 나은 것을 찾기 어렵다. 문제는 빌드 환경이 달라지는 순간이다.

왜 모양이 무너지는가 - 같은 소스가 다른 기계어가 되는 경로

「같은 함수 찾기」가 어려운 이유는 함수가 어렵기 때문이 아니라, 같은 소스가 언제나 같은 기계어가 되지 않기 때문이다. 컴파일은 소스에서 기계어로 가는 한 방향의 변환이고, 그 변환에는 소스에 적혀 있지 않은 결정이 잔뜩 들어간다. 최적화 수준, 컴파일러의 종류와 판, 대상 아키텍처, 링크 시점의 선택이 모두 결과를 흔든다.

구체적으로 무엇이 바이트를 무너뜨리는지 갈라 두면 이렇다.

변환무엇이 일어나는가바이트 대조에 미치는 영향그래프 대조에 미치는 영향
인라이닝작은 함수가 호출한 자리에 펼쳐진다독립된 함수가 아예 사라져 대조할 대상이 없다호출자의 그래프가 커지고 원래 형태가 녹아든다
명령 재배치의존이 없는 명령의 순서가 바뀐다같은 명령의 나열인데 순서가 달라 겹치지 않는다블록 안의 순서만 바뀌면 골격은 남는다
레지스터 할당같은 값이 다른 레지스터에 담긴다피연산자 바이트가 통째로 달라진다거의 영향이 없다
반복문 풀기와 벡터화반복이 펼쳐지거나 폭이 넓은 명령으로 묶인다길이와 내용이 모두 달라진다블록 수와 간선 수가 크게 달라진다
꼬리 호출과 블록 병합호출이 점프로 바뀌고 블록이 합쳐진다끝부분의 모양이 달라진다꼭짓점이 줄어 닮음 점수가 떨어진다
컴파일러 교체같은 수준이라도 판단이 다르다같은 소스인데 겹치는 구간이 짧아진다골격이 비슷해도 세부가 갈린다
아키텍처 교체명령 집합 자체가 다르다대조가 성립하지 않는다그래프 골격만 남고 나머지는 비교 불가

표의 오른쪽 두 칸이 갈리는 것에 주목할 만하다. 그래프를 보는 방식은 바이트를 보는 방식보다 이 변환들을 잘 견딘다. 그러나 견딤에도 한계가 있다. 반복문을 펼치거나 조건을 조건 없는 명령으로 바꾸는 최적화는 그래프의 골격 자체를 다시 그린다. 모양을 재는 모든 방식은 결국 같은 곳에서 막힌다. 컴파일러가 모양을 바꾸는 자유도가 사람이 「같다」고 부르는 범위보다 넓기 때문이다.

행동으로 판정한다는 발상

여기서 다른 질문이 나온다. 모양이 흔들린다면 흔들리지 않는 것은 무엇인가. 최적화는 프로그램이 하는 일을 바꾸지 않는 선에서 모양을 바꾼다. 그렇다면 「하는 일」을 직접 재면 되지 않는가.

이것이 행동 기반 판정의 발상이다. 함수에 값을 넣고 돌린 다음, 그 과정에서 밖으로 드러나는 효과를 기록해 요약으로 만든다. fnprint 의 README 는 기록하는 것을 아키텍처에 매이지 않는 효과의 흐름이라고 부르며 이렇게 열거한다. 인자로 받은 버퍼와 구조체의 어느 자리를 읽고 어디에 쓰는지, 쓰는 값이 어떤 부류인지 — 입력의 복사본인지, 작은 상수인지, 포인터인지 — 어떤 호출을 하는지, 어떤 분기를 타는지, 무엇을 돌려주는지다.

그렇게 만들어진 효과의 흐름은 조각으로 잘려 요약 서명으로 바뀐다. 두 함수의 닮음은 그 서명의 칸이 얼마나 맞아떨어지는지의 비율로 계산된다. 후보를 전부 대 전부로 견주는 일을 피하려고 묶음 색인이 앞에 놓인다. 개념만 그림으로 옮기면 한 함수의 관측 결과는 대략 이런 모양이 된다.

읽기   arg0[0 .. n)        연속 접근
쓰기   arg1[0 .. n)        입력의 복사본
호출   1회                 기록만, 안으로 들어가지 않음
분기   2회                 길이 0 검사 / 정렬 검사
반환   arg1                입력 포인터를 그대로

이 요약에는 명령의 순서도, 레지스터의 이름도, 절대 주소도 들어 있지 않다. README 는 절대 주소를 버리고 오프셋과 모양만 남긴다고 적는다. 모양을 흔드는 변환이 건드리지 못하는 층으로 내려간 것이다. 그 대신 이 층은 다른 값을 요구한다.

실행한다는 결정이 청구하는 네 가지 대가

입력을 주고 출력을 비교한다는 말은 함수를 실제로 실행한다는 뜻이다. 정적 분석에는 없던 문제가 그 순간부터 생긴다. 네 가지로 갈린다.

부작용 - 분석이 세상을 바꾼다

함수는 값을 돌려주기만 하지 않는다. 파일을 지우고, 소켓을 열고, 전역 변수를 고치고, 프로세스를 끝낸다. 정체를 모르는 함수를 진짜 기계 위에서 그대로 돌리면 분석 행위가 관측 대상 밖을 바꾼다. 그래서 이 방식은 대개 실제 실행이 아니라 모사된 실행을 택한다. 명령을 흉내 내는 층 위에서 돌리고, 밖으로 나가는 통로를 막는다.

입력 공간 - 무엇을 넣을지 정해야 한다

함수의 인자로 들어올 수 있는 값의 가짓수는 사실상 무한하다. 그중 몇 개를 골라 넣는지가 판정의 질을 정한다. 아무 값이나 넣으면 실행은 대개 함수의 앞부분만 지나간다. 길이가 0 인지 보고 바로 돌아 나오는 함수, 널 포인터를 걸러 내는 함수가 그렇다. 입력이 얕으면 관측도 얕다. 반대로 입력을 정교하게 만들려면 함수가 무엇을 기대하는지 알아야 하는데, 그것을 아는 것이 원래 풀려던 문제다.

환경 의존 - 같은 함수가 다르게 나온다

실행 결과는 함수만의 것이 아니다. 초기화되지 않은 메모리를 읽으면 그 자리에 무엇이 있었는지가 결과에 섞인다. 시각을 읽거나 난수를 뽑는 함수는 부를 때마다 다른 값을 낸다. 스택에 남아 있던 이전 호출의 흔적, 정렬 위치, 매핑된 주소가 전부 관측에 끼어든다. 이 흔들림을 없애지 않으면 같은 함수를 두 번 재고도 다르다고 판정하게 된다.

격리 비용 - 모르는 코드를 돌린다는 것

정체를 모르는 코드를 실행하는 일에는 그 자체로 비용이 붙는다. 잘못된 주소를 건드려 실행이 죽지 않게 해야 하고, 무한 반복에 빠졌을 때 끊어 낼 장치가 있어야 하며, 한 함수의 실행이 다른 함수의 실행에 자국을 남기지 않아야 한다. 그리고 이 모든 장치는 속도를 갉아먹는다. 바이트 대조가 초당 수만 개를 훑는 자리에서, 모사 실행은 함수 하나마다 여러 번 돌아야 한다.

대가왜 생기는가흔한 대응대응해도 남는 것
부작용함수가 값 반환 밖에서 세상을 바꾼다모사 실행, 바깥으로 나가는 호출 차단차단된 호출 너머의 행동은 관측되지 않는다
입력 공간가능한 입력이 사실상 무한하다표본을 정해 여러 번 반복깊은 조건 뒤의 코드는 계속 도달하지 못한다
환경 의존메모리 초기값, 시각, 난수가 섞인다미설정 메모리에 정해진 값 부여, 고정 절차결정성은 재현성이지 정답의 보증이 아니다
격리 비용정체를 모르는 코드를 돌린다잘못된 접근을 흡수, 실행 한도 설정속도가 정적 대조에 크게 못 미친다

계기가 된 도구는 그 대가를 어떻게 처리하는가

네 가지 대가를 어떻게 다루는지가 이 방식을 평가하는 기준이 된다. fnprint 의 README 에 적혀 있는 것만 옮기면 다음과 같다.

  • 미설정 메모리 — 준비해 두지 않은 자리에서 읽으면 정해진 값이 돌아오고, 그 페이지는 그 자리에서 매핑된다고 적혀 있다. 초기화되지 않은 메모리라는 흔들림을 값의 규칙으로 눌러 둔 것이다.
  • 잘못된 포인터 — 엉뚱한 주소를 다루어도 실행이 죽지 않으며, 같은 입력은 언제나 같은 기록을 낸다고 적혀 있다. 격리와 재현성을 한 문장으로 묶어 둔 서술이다.
  • 다른 함수 호출 — 밖으로 나가는 호출은 기록만 하고 건너뛴다고 적혀 있다. 그 덕에 표준 라이브러리 안으로 파고들지 않고 관측이 그 함수에 머문다.
  • 절대 주소 — 절대 주소는 버리고 오프셋과 모양만 남긴다고 적혀 있다. 같은 코드가 다른 자리에 놓여도 같은 기록이 되도록 만드는 장치다.

여기까지가 문서에 있는 것이다. 문서에 없는 것도 그만큼 중요하다. 시스템 호출 명령을 만났을 때 무엇을 하는지, 격리를 어떤 수준으로 보장하는지에 대한 서술이 README 에 없다. 함수 하나마다 몇 개의 입력을 넣는지, 그 값을 어떤 규칙으로 만드는지도 없다. 설치에 필요한 것으로 널리 쓰이는 CPU 모사 프레임워크와 역어셈블러 두 개가 적혀 있는데, 그중 CPU 모사 쪽은 스스로를 명령을 흉내 내는 틀이라고 소개할 뿐 운영체제 층까지 흉내 내는지는 그 저장소의 소개문에서도 갈라 적지 않는다.

문서에 없다는 것은 처리를 안 한다는 뜻이 아니다. 문서만으로는 판정할 수 없다는 뜻이다. 정체를 모르는 코드를 돌리는 도구를 실무에 들일 때 갈라야 할 항목이 정확히 이 자리다.

같음의 층위 - 「관측이 겹친다」와 「같은 함수다」

이제 이 방식의 핵심 문제로 들어간다. 두 문장은 층이 다르다.

첫째, 고른 입력에서 관측한 결과가 겹친다. 이것은 관측의 진술이다. 무엇을 넣었고 무엇이 나왔는지에 대한 사실이며, 넣은 값의 범위 안에서만 참이다. 둘째, 두 함수는 같은 함수다. 이것은 정체에 대한 진술이다. 모든 입력에서 같게 행동한다는 주장을 포함한다.

앞의 것이 뒤의 것을 함의하지 않는다. 이 간격이 오탐이 태어나는 자리다. 서로 다른 두 함수가 고른 입력에서 우연히 같은 관측을 내는 일은 드물지 않다. README 도 순수 계산 함수를 취약한 자리로 꼽으며, 버퍼를 읽고 숫자 하나를 돌려주는 두 개의 체크섬은 밖에서 보면 거의 같다고 적는다.

함수 A   읽기 buf[0..n)   쓰기 없음   반환 4바이트 정수
함수 B   읽기 buf[0..n)   쓰기 없음   반환 4바이트 정수

밖에서 관측되는 요약은 동일하다.
안에서 무엇을 곱하고 무엇을 더했는지는 밖에 남지 않는다.

반대 방향도 있다. 같은 함수인데 관측 조건이 달라 다르게 보이는 경우다. 최적화가 강하게 걸린 두 빌드를 견주면 밖으로 드러나는 행동 자체가 얇아진다. 인라이닝으로 호출이 사라지고 분기가 조건 없는 명령으로 접히면, 기록할 효과가 남지 않는다. 그리고 기록할 것이 적으면 모든 함수가 서로 닮아 보인다.

오탐과 미탐은 대칭이 아니다

오탐 - 다른 것을 같다고 부를 때

오탐은 조용하다. 틀린 이름이 붙은 함수는 그 뒤로 이름이 붙어 있다는 이유로 다시 열리지 않는다. 그 이름을 전제로 인접 함수가 해석되고, 그 해석을 전제로 또 다른 판단이 쌓인다. 하나의 잘못된 판정이 그 위에 얹힌 모든 것을 오염시키는데, 오염된 결과물은 겉으로는 완결돼 보인다. 자동으로 붙인 이름이 수천 개인 상황에서 이 위험은 개수에 비례해 커진다.

미탐 - 같은 것을 다르다고 부를 때

미탐은 시끄럽지 않지만 남는다. 취약 코드 묶음과 견주는 작업에서 한 함수를 놓치면 그 함수는 그대로 남는다. 다만 미탐에는 오탐에 없는 성질이 있다. 대개는 사람이 다시 보면 발견된다. 후보 목록의 상위 몇 개를 사람이 훑는 절차가 붙어 있으면 미탐의 상당 부분이 회수된다. README 도 정확히 그 지점을 짚는다. 한 쌍에서 최상위 후보가 맞을 확률이 93% 인데 상위 다섯 개 안에 정답이 들어 있을 확률은 96.6% 라고 적으며, 적은 검토 예산이 그 간격의 대부분을 메운다고 덧붙인다.

여기서 나오는 결론은 단순하다. 오탐과 미탐은 같은 무게가 아니다. 사람의 검토가 붙는 절차에서는 미탐이 회수 가능한 실패이고, 오탐은 회수되지 않는 실패다. 반대로 사람의 검토가 없는 자동 절차에서는 이 비대칭이 사라지고 오탐의 비용만 남는다.

신뢰도는 「몇 개의 입력에서 일치했는가」에 달려 있다

한 번의 일치는 우연과 구별되지 않는다. 두 함수를 한 개의 입력으로 견주어 같은 결과를 얻었다면 그것은 거의 정보가 아니다. 입력을 늘릴수록 우연히 계속 겹칠 확률이 줄고, 그만큼 일치가 정체의 증거에 가까워진다. 판정의 신뢰도는 함수의 성질이 아니라 관측의 양에서 나온다.

그리고 관측의 양은 입력의 개수만으로 정해지지 않는다. 함수가 드러낼 것을 얼마나 가지고 있는지가 더 큰 몫을 한다. 인자를 세 개 받아 버퍼를 훑고 조건에 따라 다른 값을 쓰는 함수는 남길 흔적이 많다. 값을 그대로 넘겨주는 한 줄짜리 함수는 남길 흔적이 없다. README 는 이 성질을 신호의 양이라고 부르며, 신호가 적은 함수는 판정 자체를 보류한다고 적는다.

같은 문서가 공개한 측정값은 이 구조를 그대로 보여 준다. zlib 1.3.1 의 함수 84 개를 대상으로, 같은 소스를 서로 다른 조건으로 빌드한 두 결과물을 견준 값이다.

견준 두 빌드최상위 후보 정답률정밀도읽는 법
같은 컴파일러, 최적화 없음에서 1 단계로97.1%93.8%한쪽이 최적화 전이면 행동이 풍부하게 남는다
같은 컴파일러, 최적화 없음에서 2 단계로93.1%83.3%정답률은 유지되나 확신의 질이 떨어진다
같은 컴파일러, 최적화 없음에서 3 단계로91.3%100.0%보류가 늘어 확신한 것은 전부 맞았다
다른 컴파일러, 양쪽 다 최적화 없음97.7%97.1%컴파일러 교체는 이 방식이 잘 견디는 축이다
같은 컴파일러, 2 단계에서 3 단계로56.5%66.7%양쪽 다 최적화되면 관측할 것이 얇아진다
다른 컴파일러, 양쪽 다 2 단계59.1%50.0%같은 조건이 겹치면 성능이 함께 내려간다

표에서 읽을 것은 개별 숫자가 아니라 패턴이다. 한쪽이라도 최적화가 덜 걸려 있으면 값이 높고, 양쪽이 모두 강하게 최적화되면 값이 절반 근처로 떨어진다. README 자신도 그렇게 요약한다. 한쪽에 행동의 풍부함이 남아 있으면 80~98% 구간에 들어가고, 양쪽이 모두 강하게 최적화되면 관측할 수 있는 행동이 얇아져 동전 던지기 쪽으로 내려간다는 것이다. 이 문장은 성능 보고가 아니라 이 방식이 무엇에 의존하는지에 대한 설명으로 읽는 편이 정확하다.

식별 방식별 강약과 실패의 모양

지금까지의 내용을 한 장으로 접으면 이렇게 된다. 어떤 방식도 모든 축에서 이기지 않으며, 각자 다른 방향으로 틀린다는 것이 요점이다.

식별 방식무엇에 강한가무엇에 약한가주로 나타나는 실패
바이트 시퀀스 대조같은 빌드 환경의 동일 라이브러리, 속도최적화·컴파일러·아키텍처 교체 전부미탐 — 같은 함수인데 겹치지 않아 놓친다
제어 흐름 그래프 비교명령 수준의 잔변동, 부분적 수정인라이닝, 반복문 풀기, 분기 접기미탐 우세 — 골격이 다시 그려지면 놓친다
문자열·상수 표지표지가 있는 함수의 확정력표지가 없는 함수, 표지 제거미탐 — 대상 자체가 없어 판정 불가
행동 지문최적화·컴파일러 교체, 아키텍처 넘기작은 함수, 순수 계산, 깊은 조건 뒤의 코드오탐 — 밖에서 비슷해 보이는 것을 같다고 부른다
행동 지문 + 보류확신한 판정의 질회수율, 판정을 못 내리는 함수의 비율미탐으로의 전가 — 애매한 것을 답하지 않는다
모양과 행동의 병행서로의 실패를 덮는 조합운영 비용, 두 결과가 어긋날 때의 판단불일치 — 어느 쪽을 믿을지가 다시 문제가 된다

가장 아래 두 줄이 실무에서 실제로 고르는 자리다. 보류를 허용하면 확신한 것의 질은 올라가고 답하지 못한 함수가 늘어난다. 두 계열을 함께 돌리면 실패의 모양이 서로 다르므로 상당 부분이 덮이지만, 두 결과가 어긋나는 함수가 새로운 검토 대상으로 남는다. 어느 쪽이든 실패가 사라지지는 않고 자리를 옮길 뿐이다.

쓰임새마다 비싼 실패가 다르다

같은 도구를 쓰더라도 무엇을 하려는지에 따라 기준선을 다르게 잡아야 한다. 오탐과 미탐 중 무엇이 더 비싼지가 작업마다 다르기 때문이다.

쓰임새오탐이 부르는 손해미탐이 부르는 손해어느 쪽으로 기울이는가
정적 링크된 라이브러리 함수에 이름 붙이기틀린 이름이 이후 해석 전체를 오염시킨다이름 없는 함수가 남는다오탐 억제 — 애매하면 이름을 붙이지 않는다
패치 전후 비교로 변경점 찾기안 바뀐 함수를 바뀌었다고 보아 검토가 늘어난다실제 변경을 못 보고 지나간다미탐 억제 — 후보를 넓게 두고 사람이 좁힌다
중복 코드 탐지남의 코드와 무관한 함수를 얽어 놓는다중복을 못 찾아 정리 기회를 놓친다균형 — 후보 목록으로 넘기고 판단은 사람이 한다
취약한 판인지 고쳐진 판인지 가르기안전한 것을 위험하다고 보아 대응이 낭비된다위험한 것이 그대로 남는다미탐 억제 — 놓치는 쪽이 훨씬 비싸다
대량 자동 분류사람이 안 보는 만큼 그대로 결과가 된다분류 안 된 항목이 쌓인다오탐 억제 — 검토가 없으면 회수도 없다

표의 마지막 줄이 앞 절의 비대칭과 이어진다. 사람의 검토가 절차에 들어 있는지 여부가 오탐과 미탐의 상대 가격을 뒤집는다. 도구의 설정값을 정하기 전에 정해야 하는 것은 절차의 모양이다.

기권이라는 세 번째 답

같다와 다르다 사이에는 말하지 않겠다가 있다. 이 선택지는 실패를 줄이지 않지만 실패의 종류를 고를 수 있게 해 준다. README 도 확신이 서지 않는 쌍에 대해 추측하는 대신 판정을 삼간다고 적으며, 그래서 정밀도가 높게 유지되는 반면 같은 기준선에서의 회수율은 낮다고 설명한다.

기권을 절차에 넣을 때 갈라 두면 좋은 것은 세 가지다.

  • 기권과 미탐을 같은 칸에 넣지 않는 것 — 답하지 않은 함수는 틀린 답이 아니라 아직 답이 없는 함수다. 두 가지를 한 숫자로 합치면 절차의 어느 부분을 고쳐야 하는지가 보이지 않는다.
  • 기권한 함수를 어디로 보낼지 정해 두는 것 — 사람이 볼 목록으로 갈지, 다른 계열의 판정에 넘길지, 그대로 둘지를 미리 정하지 않으면 기권은 그저 조용한 누락이 된다.
  • 신호가 적어서 기권한 것과 후보가 팽팽해서 기권한 것을 구별하는 것 — 앞의 것은 입력을 늘려도 나아지지 않고, 뒤의 것은 관측을 늘리면 갈릴 여지가 있다. 대응이 다르다.

법과 계약이 걸어 두는 조건

바이너리를 분석하는 행위에 하나의 답이 붙지 않는다. 같은 작업이라도 어디에서 어떤 목적으로 이루어졌는지에 따라 평가가 갈린다. 그래서 이 절은 해도 된다거나 하면 안 된다는 문장을 적지 않는다. 판단이 걸리는 지점만 적는다.

법과 계약은 서로 다른 층이다. 프로그램의 이용에 관한 규율은 나라마다 조문이 다르고, 어떤 조건에서 어떤 목적의 분석이 허용되는지도 함께 다르다. 그리고 법이 정한 범위와 별개로, 그 프로그램을 손에 넣을 때 동의한 이용약관과 라이선스가 조건을 따로 건다. 법 쪽이 열려 있어도 계약 쪽이 닫혀 있을 수 있고 그 반대도 있다. 두 층은 각각 확인해야 하는 것이며, 한쪽의 결론을 다른 쪽으로 옮겨 쓸 수 없다.

기술적 보호조치는 또 한 층이다. 접근이나 복제를 통제하려고 걸어 둔 조치를 무력화하는 행위는 분석 자체의 적법성과 별개로 다루어진다. 그 조치를 넘어서는 절차는 여기에 적지 않는다. 위에서 다룬 것은 이미 손에 있고 이미 실행할 수 있는 코드를 놓고 이 함수와 저 함수가 같은가를 판정하는 방법의 성질이지, 무엇을 열어젖히는 방법이 아니다.

실무에서 이 경계는 대개 목적과 기록의 형태로 관리된다. 무엇을 위해 분석하는지, 결과물을 누구에게 어떤 형태로 남기는지, 분석 대상을 어떤 경로로 확보했는지가 남는다. 판단이 필요한 사안이라면 관할과 계약을 함께 놓고 법률 검토를 받는 것이 절차다.

정리 - 다섯 문장으로 줄이면

  1. 「같은 함수 찾기」가 어려운 이유는 함수가 어려워서가 아니라 같은 소스가 언제나 같은 기계어가 되지 않기 때문이다. 인라이닝과 재배치와 레지스터 할당이 바이트 시그니처를 무너뜨린다.
  2. 모양이 흔들리는 자리에서 행동은 덜 흔들린다. 그러나 행동을 재려면 실제로 실행해야 하고, 그 결정은 부작용·입력 공간·환경 의존·격리 비용이라는 네 가지를 청구한다.
  3. 「고른 입력에서 관측이 겹친다」와 「같은 함수다」는 층이 다른 명제다. 앞의 것은 뒤의 것을 함의하지 않으며, 그 간격이 오탐이 태어나는 자리다.
  4. 판정의 신뢰도는 몇 개의 입력에서 일치했는가와 그 함수가 드러낼 것을 얼마나 가지고 있는가에서 나온다. 양쪽이 다 얇아지면 어떤 방식도 동전 던지기에 가까워진다.
  5. 오탐과 미탐은 같은 무게가 아니고, 무엇이 더 비싼지는 절차에 사람의 검토가 들어 있는지가 정한다. 설정값보다 절차를 먼저 정하는 편이 순서에 맞다.

확인하지 못한 것

  • 시스템 호출을 만났을 때의 동작 — 모사 실행 중 시스템 호출 명령에 도달하면 무엇을 하는지에 대한 서술이 README 에 없다. 밖으로 나가는 함수 호출을 기록 후 건너뛴다는 서술만 있다.
  • 함수당 입력의 개수와 생성 규칙 — 인자 자리에 아무 값이나 넣는다는 서술은 있으나, 몇 개를 넣는지와 그 값을 어떤 규칙으로 만드는지는 README 에 적혀 있지 않다. 이 값이 판정의 신뢰도를 직접 좌우한다.
  • 격리의 보장 수준 — 잘못된 포인터로 실행이 죽지 않는다는 서술은 있으나, 그것이 어느 범위까지의 격리를 뜻하는지는 문서에서 갈라 적지 않는다. 정체를 모르는 코드를 다루는 도구에서 이 항목은 별도 평가가 필요한 자리다.
  • 공개 측정값의 범위 밖 성능 — 공개된 수치는 한 라이브러리의 84 개 함수를 대상으로 한 것이다. 다른 규모, 다른 언어로 쓰인 코드, 다른 최적화 조합에서의 값은 문서에 없다.
  • 바이트 대조 계열 도구의 내부 규격 — 널리 쓰이는 라이브러리 함수 식별 기술의 세부 명세 문서는 여기서 열지 않았다. 위의 서술은 그 계열이 공통으로 갖는 성질에 한정한 것이며, 특정 구현의 규격을 옮긴 것이 아니다.
