Windows MAX_PATH 260자 제한과 도구별 실패 양상

경로가 길 때 도구마다 다르게 실패한다 — 특히 오류 없이 조용히 빠지는 경우를 먼저 의심하라

2026-09-29 개발/인프라

서론: 파일은 그 자리에 있는데 도구는 「없다」고 답한다

Windows 환경에서 파일 기반 자동화 작업을 운영하다 보면 상식적으로 이해하기 어려운 현상을 마주친다. 디스크에 분명히 기록되어 있고 다른 도구에서는 멀쩡히 읽히는 파일인데, 특정 스크립트나 명령줄 도구는 「파일을 찾을 수 없다」거나 심지어 오류조차 없이 거짓(False)을 반환한다. 많은 엔지니어가 이 순간 파일 권한이나 동기화 지연, 인코딩 깨짐을 먼저 의심한다. 그러나 그 이면에는 Windows 운영체제의 오랜 유산인 MAX_PATH(260자) 경로 길이 제한이 도구마다 전혀 다른 표정으로 실패를 드러내는 문제가 자리 잡고 있다.

이 글은 흔히 알려진 「긴 경로 활성화 팁 모음」을 전달하려는 것이 아니다. 경로가 260자를 넘어설 때 도구마다 실패하는 방식이 제각각이며, 특히 오류 메시지 없이 조용히 목록에서 빠지는 현상이 시스템의 가장 위험한 사각지대임을 실측 데이터로 규명한다. 실제로 Windows 10 환경에서 전체 경로 322자짜리 파일을 직접 생성한 뒤, PowerShell 5.1, cmd.exe, Python 3.13, Git Bash, Node.js 22, Git 2.48을 순차적으로 교차 실행하여 확인한 결과다.

관련된 선행 주제들과의 경계를 명확히 둔다. Windows 배치와 PowerShell을 통한 작업 자동화 기본기는 윈도우 작업 자동화 입문 가이드에서, 한글 파일명의 셸 치환과 문자셋 왜곡은 한글 파일명이 셸마다 다르게 보이는 이유에서 다루었다. 아카이브 내부의 파일명 인코딩 플래그 문제는 zip 안의 한글 파일명이 깨지는 지점에 정리되어 있다. 이 글은 오직 경로의 물리적 길이 하나에 집중한다.

1. 실행 환경과 MAX_PATH(260자)의 실제 경계

본문에 수록된 모든 실행 결과는 아래의 단일 로컬 환경에서 직접 명령을 수행하여 얻은 출력이며, 관리자 권한 없이 일반 사용자 권한에서 수행했다. 측정값은 이 환경에서 한 번씩 돌린 결과다.

  • 운영체제: Windows 10 Pro (빌드 10.0.19045)
  • 명령줄 셸: Windows PowerShell 5.1.19041.6456 (.NET Framework v4.0.30319), cmd.exe
  • 개발 언어 런타임: Python 3.13.3, Node.js v22.16.0
  • 유닉스 에뮬레이션 및 도구: Git for Windows 2.48.1.windows.1, Git Bash (GNU sed 4.9, GNU Awk 5.0.0), curl 8.12.1 (Schannel)
  • 실행 권한: 관리자 권한 아님 (표준 사용자 권한)
  • 실험 대상 파일: …/tech_lab/lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
  • 실험 대상 경로 길이: 전체 파일 절대 경로 322자, 부모 폴더 경로 294자

1.1 260자의 구성과 248자 디렉터리 한도

마이크로소프트의 공식 기술 문서(Naming Files, Paths, and Namespaces)에 따르면 Windows API에서 전통적인 파일 경로의 최대 길이는 MAX_PATH 상수로 정의되며, 그 크기는 정확히 260자이다. 이 구조는 드라이브 문자(예: C:, 2자), 경로 구분자 역슬래시(\, 1자), 실제 파일 및 폴더 이름 구성 요소들, 그리고 문자열의 끝을 나타내는 널 종단 문자(\0, 1자)로 이루어진다. 따라서 사용자가 실제로 경로 문자열로 입력할 수 있는 실질적인 경로는 259자까지다.

그러나 많은 개발자가 간과하는 대목이 있다. 디렉터리 자체의 생성 한도는 260자가 아니라 248자(MAX_PATH - 12)라는 사실이다. 마이크로소프트 공식 문서는 디렉터리 경로 길이가 MAX_PATH minus 12를 초과할 수 없다고 명시한다. 이는 해당 디렉터리 아래에 전통적인 8.3 형태의 파일(파일명 8자 + 마침표 1자 + 확장자 3자 = 12자)을 최소 하나 이상 생성할 수 있는 공간을 예약해 두어야 하기 때문이다. 아래의 실험 결과에서 실제로 231자 디렉터리 생성은 성공했으나 252자 디렉터리 생성은 즉시 실패하며 WinError 206이 발생한 것이 바로 이 규정과 일치한다.

1.2 레지스트리 LongPathsEnabled 현재 값 확인

현대 Windows 10 및 Windows Server 환경에는 시스템 수준에서 긴 경로 제한을 해제할 수 있는 레지스트리 키(LongPathsEnabled)가 존재한다. 본 실습을 시작하기 전, 시스템의 기본 상태를 확인하기 위해 레지스트리 값을 조회했다.

reg query "HKLM\SYSTEM\CurrentControlSet\Control\FileSystem" /v LongPathsEnabled
Get-ItemProperty -Path 'HKLM:\SYSTEM\CurrentControlSet\Control\FileSystem' -Name LongPathsEnabled | Select-Object LongPathsEnabled

실제 실행 결과 출력은 다음과 같았다.

HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\FileSystem
    LongPathsEnabled    REG_DWORD    0x0

LongPathsEnabled
----------------
               0

확인 결과 이 시스템의 LongPathsEnabled 값은 0이었다. 즉 Windows의 전통적인 260자 경로 길이 제한이 완화 없이 완벽하게 작동하고 있는 표준 상태다. 아래에서 서술하는 모든 실험 결과는 바로 이 조건 아래에서 도출되었다.

2. 도구별 반응 비교 — 오류 메시지인가, 거짓 판정인가, 조용한 누락인가

동일한 322자 길이의 파일과 294자 폴더에 대해 각 도구가 보인 반응은 놀라울 정도로 파편화되어 있었다. 모든 도구가 실패하는 것도 아니었고, 실패하더라도 같은 에러를 내지 않았다. 어떤 도구는 「파일이 너무 길다」고 친절히 알렸지만, 어떤 도구는 「파일이 없다」고 둘러댔고, 심지어 정상 종료하면서 결과를 누락시키는 도구도 있었다.

도구 및 명령 일반 경로 결과 \\?\ 접두사 경로 결과 실패 시 화면에 노출되는 실제 문구 실패 방식 분류

2.1 PowerShell 5.1의 Test-Path와 부재 오인

PowerShell 5.1에서 322자 경로를 일반적인 방식으로 검사하면 어떤 오류도 발생하지 않는다. Test-Path는 예외를 던지지 않고 조용히 False를 반환했다.

Test-Path -LiteralPath $f
Test-Path -LiteralPath ("\\?\" + $f)
Get-Content -LiteralPath $f
Get-Content -LiteralPath ("\\?\" + $f)
(Get-ChildItem -LiteralPath ("\\?\" + (Split-Path $f))).Name
Get-ChildItem -LiteralPath "$b\lp" -Recurse | ForEach-Object { $_.FullName.Length }

실제 실행 결과는 아래와 같다.

--- Test-Path plain
False
--- Test-Path prefixed
True
--- Get-Content plain
System.Management.Automation.ItemNotFoundException
Cannot find path '…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb\cccccccccccccccccccc\long_file_name_for_test.txt' because it does not exist.
--- Get-Content prefixed
hello long path
--- Get-ChildItem prefixed dir
long_file_name_for_test.txt
--- Get-ChildItem -Recurse on lp (plain)
252
273
System.IO.DirectoryNotFoundException
Could not find a part of the path '…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb'.

Get-Content의 에러 문구는 명백히 because it does not exist다. 「경로가 너무 길다」는 안내는 어디에도 없다. 이 때문에 스크립트 작성자는 파일이 삭제되었거나 생성 과정에서 누락되었다고 완전히 잘못된 결론을 내리게 된다. 재귀 탐색인 Get-ChildItem -Recurse 역시 273자 폴더 이름까지는 출력하지만, 그 안으로 진입하려 하자 DirectoryNotFoundException을 일으키며 실행을 멈추었다.

2.2 Python의 FileNotFoundError와 WinError 번호

Python 3.13 환경에서 실행한 스크립트(t1_make.py)의 결과 역시 유사한 양상을 보였다. 오류 번호는 출력에 찍힌 그대로 옮긴다.

# t1_make.py 주요 실행 구간
os.makedirs(deep, exist_ok=True)          # 일반 경로 디렉터리 생성
open(f, "w")                              # 일반 경로 파일 생성
os.makedirs(P + deep, exist_ok=True)      # \\?\ 접두사 디렉터리 생성
open(P + f, "w", newline="\n")            # \\?\ 접두사 파일 생성
open(f).read() / open(P + f).read()
os.path.exists(f) / os.path.exists(P + f)
os.listdir(deep) / os.listdir(P + deep)

실제 스크립트 실행 출력은 다음과 같다.

base len: 228
dir len: 294 file len: 322
  candidate dir len 231
  candidate dir len 252
plain makedirs: FileNotFoundError winerror= 206 filename_len= 252
plain open(w): FileNotFoundError errno= 2 winerror= None
prefixed makedirs: OK
prefixed open(w): OK
plain open(r): FileNotFoundError errno= 2 winerror= None
prefixed open(r): hello long path
exists plain: False | exists prefixed: True
listdir plain: FileNotFoundError winerror= 3
listdir prefixed: ['long_file_name_for_test.txt']

Python에서 확인된 시스템 에러 번호들의 실제 한국어 메시지를 ctypes.FormatError로 대조하여 확인했다.

WinError 번호 운영체제 반환 메시지 (FormatError) 실제 발생한 문맥
WinError 3 지정된 경로를 찾을 수 없습니다. 294자 디렉터리에 대해 일반 os.listdir() 호출 시
WinError 145 디렉터리가 비어 있지 않습니다. 긴 경로 파일이 포함된 디렉터리에 일반 shutil.rmtree() 실행 시
WinError 206 파일 이름이나 확장명이 너무 깁니다. 252자 길이의 디렉터리를 일반 os.makedirs()로 생성하려 할 때

여기서도 os.path.exists()는 아무런 예외 없이 False를 반환한다. 파일을 일반 경로로 열려고 하면 FileNotFoundError errno= 2 winerror= None, 즉 WinError 번호 없이 errno 2만 찍혔다. 유일하게 252자 폴더 생성 시에만 WinError 206이 나와 길이 문제임을 암시했다.

2.3 Git Bash와 Node가 322자를 처리한 이유

흥미로운 점은 모든 도구가 실패한 것은 아니라는 사실이다. Git Bash(MSYS2 런타임)와 Node.js 22는 레지스트리 LongPathsEnabled가 0인 상태에서도 322자 경로를 거침없이 다루었다.

# Git Bash 에서 실행한 명령
ls -R lp
cat lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
find lp -type f
cat "$PWD/lp/…/long_file_name_for_test.txt"
echo bash-made > lp/…/cccccccccccccccccccc/bash_made_file.txt

실제 출력 결과는 다음과 같았다.

lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc:
long_file_name_for_test.txt
exit=0
=== cat (relative)
hello long path
exit=0
=== find
lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
=== cat absolute (posix path)
hello long path
exit=0
=== write new long file via bash
exit=0
bash_made_file.txt
long_file_name_for_test.txt

Git Bash는 상대 경로와 POSIX 절대 경로 모두에서 322자 파일을 문제없이 읽었고, 심지어 echo bash-made > ... 명령을 통해 294자 폴더 안에 새로운 파일(bash_made_file.txt)을 작성하는 데에도 성공했다. Node.js 22도 일반 경로로 읽기와 목록 조회에 성공했다(쓰기는 시험하지 않았다).

len 322
readFileSync plain : "hello long path\n"
readFileSync \\?\ : "hello long path\n"
existsSync plain   : true
toNamespacedPath   : "\\\\?\\C:\\Users..."
readdirSync plain  : ["bash_made_file.txt","long_file_name_for_test.txt"]

path.toNamespacedPath()에 일반 경로를 넣자 \\?\C:\... 형태가 돌아왔다. Node가 내부에서 이렇게 접두사를 붙인 경로로 바꿔 쓰는 것으로 보이지만, 출력으로 확인한 것은 이 변환 결과뿐이다. 따라서 「Windows에서는 260자가 넘으면 프로그램이 무조건 죽는다」는 식의 일반화는 성립하지 않는다.

3. cmd dir /s 의 조용한 누락 — 종료 코드 0이 숨기는 사각지대

이번 실측 실험에서 발견된 가장 치명적인 함정은 명령 프롬프트(cmd.exe)의 재귀 목록 조회 명령인 dir /s에서 나타났다.

cmd /c "dir `"$d`""            # 일반 경로 폴더
cmd /c "dir `"\\?\$d`""        # 접두사 폴더
cmd /c "type `"$f`""
cmd /c "type `"\\?\$f`""
cmd /c "dir /s /b `"$b\lp`""   # 하위 재귀 탐색
# 종료 코드는 $LASTEXITCODE 로 확인

실제 콘솔에 찍힌 출력과 종료 코드는 아래와 같다.

=== cmd dir plain dir
The system cannot find the path specified.
=== cmd dir prefixed dir
 Volume in drive \\?\C: has no label.
 Directory of \\?\C:\…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb\cccccccccccccccccccc
2026-09-29  ?? 07:38                16 long_file_name_for_test.txt
               1 File(s)             16 bytes
=== cmd dir /s lp
…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa
…\tech_lab\lp\aaaaaaaaaaaaaaaaaaaa\bbbbbbbbbbbbbbbbbbbb

dir plain exit=1
dir prefixed exit=0
type plain exit=1
hello long path
type prefixed exit=0
dir /s lp exit=0

3.1 dir 일반 실행과 dir /s /b 의 차이

단일 디렉터리를 대상으로 dir이나 type을 일반 경로로 실행하면 시스템은 exit=1과 함께 The system cannot find the path specified.라는 명확한 에러를 뱉는다. 실패했음이 즉시 드러나므로 후속 대처가 가능하다.

그러나 최상위 폴더에서 하위를 전부 훑는 dir /s /b를 실행했을 때는 완전히 다른 일이 벌어졌다. 252자 폴더(aaaaaaaa...)와 273자 폴더(bbbbbbbb...)까지는 화면에 찍혔지만, 그 아래에 분명히 존재하는 294자 폴더(cccccccc...)와 322자 파일(long_file_name_for_test.txt)은 출력에서 완전히 증발했다. 그리고 명령의 최종 종료 코드는 0이었다.

3.2 검색 스크립트와 배치 작업에서의 위험성

이것이 왜 위험한가? 예를 들어 다음과 같은 반복문(이 글에서 실행하지는 않은 예시 패턴)은 dir /s /b 출력을 그대로 처리 대상 목록으로 삼는다.

FOR /F "delims=" %%F IN ('dir /s /b "C:\Backup\*"') DO (
    call :ProcessFile "%%F"
)

dir /s는 아무런 에러 메시지를 출력하지 않았고 반환 코드도 0이었으므로, 스크립트는 목록이 완전하다고 판단한다. 이 실험의 cccc… 폴더처럼 목록에서 빠진 경로 아래의 파일은 처리 대상에 오르지 않은 채 조용히 건너뛰어진다. 출력과 종료 코드만 봐서는 파일이 빠졌다는 사실을 알 수 없다.

4. Python과 PowerShell에서 \\?\ 확장 경로로 다루기

그렇다면 긴 경로를 반드시 조회하고 제어해야 할 때는 어떻게 해야 하는가? 핵심 해법은 Windows API 유니코드 함수가 받는 확장 길이 경로 접두사 \\?\에 있다.

4.1 \\?\ 접두사의 의미와 절대 경로 제약

마이크로소프트 문서에 따르면 Windows API의 유니코드 함수는 \\?\ 접두사를 붙인 확장 길이 경로를 받으며, 이때 전체 경로 길이는 최대 32,767자까지 허용된다. 문서는 이 접두사가 붙은 경로가 최소한의 수정만 거쳐 시스템에 넘어간다고 설명한다 — 그래서 슬래시(/)를 구분자로 쓰거나 .·..로 현재·상위 폴더를 가리킬 수 없다.

그러나 여기에는 엄격한 제약이 따른다. 상대 경로에는 \\?\ 접두사를 절대로 붙일 수 없다. 문서는 「상대 경로에는 \\?\ 접두사를 쓸 수 없으므로 상대 경로는 언제나 MAX_PATH로 제한된다」고 적고 있다. 따라서 접두사를 사용할 때는 반드시 C:\... 와 같은 드라이브 문자를 포함한 완전한 절대 경로 형태로 조합해야 한다.

4.2 shutil.rmtree 실패와 상향식 삭제

생성된 긴 경로 디렉터리를 청소하는 과정에서도 전형적인 2차 오류가 발생했다. Python의 표준 디렉터리 트리 삭제 함수인 shutil.rmtree()를 일반 경로로 호출한 실험 결과다.

# t1_clean.py 발췌
shutil.rmtree(targets[0])                 # 일반 경로 삭제 시도
os.path.exists(P + targets[0])
for root, dirs, files in os.walk(P + t, topdown=False):
    os.remove(...)
    os.rmdir(...)
os.rmdir(P + t)

실제 출력 결과는 다음과 같았다.

plain rmtree lp: OSError winerror= 145 filename_len= 252
still exists (prefixed check): True
prefixed delete lp files= 2 dirs= 4 exists after= False
prefixed delete g\lp files= 1 dirs= 4 exists after= False
prefixed delete gr1\lp files= 1 dirs= 4 exists after= False

일반 경로로 호출된 shutil.rmtree는 WinError 145(디렉터리가 비어 있지 않습니다)를 내며 중단되었다. 내부적으로 안쪽의 322자 파일을 일반 API로 열거하거나 삭제하지 못해 폴더가 비워지지 않았고, 비워지지 않은 폴더를 삭제하려다 실패한 것이다. 이 실험에서는 접두사를 붙인 \\?\C:\... 경로로 os.walk(topdown=False)를 돌려 가장 깊은 곳의 파일부터 지우고 디렉터리를 거슬러 올라오는 상향식(bottom-up) 삭제를 하자, 세 폴더 모두 남은 것 없이 지워졌다(exists after= False).

5. Git과 core.longpaths — 작업 트리 구제와 깊은 저장소 루트의 한계

형상 관리 도구인 Git에서도 경로 길이 문제는 자주 발생한다. Git for Windows에는 core.longpaths 설정이 있지만, 이 설정이 어디까지 작동하는지는 따로 확인해야 한다.

5.1 core.longpaths 의 기본값과 설정 범위

먼저 Git의 core.longpaths 기본값이 어떻게 설정되어 있는지 확인했다.

git init -q .
git config --show-origin --show-scope --get-all core.longpaths
git config --system --show-origin --get core.longpaths
GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1 git config --get core.longpaths

출력 결과 이 PC에는 사용자가 전역(global) 설정에 true 를 넣어 두었지만, 시스템(system) 수준에는 설정이 없었고(exit=1), 전역·시스템 설정을 모두 제외하자 역시 exit=1로 비어 있었다. 즉 따로 설정하지 않으면 긴 경로 지원은 꺼진 상태(기본값 false)다. Git for Windows 동봉 문서는 탐색기, cmd.exe, Git for Windows 도구 모음(msys, bash, tcl, perl…)이 긴 경로를 지원하지 않기 때문에 기본으로 꺼 두었다고 설명한다.

5.2 작업 트리 긴 경로 파일 add 와 체크아웃

작업 트리에 330자 파일이 존재할 때 core.longpaths의 유무는 결정적인 차이를 만든다. 이 실험은 전역 설정을 끄고(GIT_CONFIG_GLOBAL=/dev/null) 객체 폴더만 GIT_OBJECT_DIRECTORY로 짧은 경로에 돌려, 작업 트리 쪽 긴 파일만 떼어 본 것이다.

--- longpaths unset: add long file
warning: could not open directory 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/': Filename too long
fatal: pathspec 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt' did not match any files
exit=128
--- longpaths=true: add long file
exit=0
lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb/cccccccccccccccccccc/long_file_name_for_test.txt
s.txt
--- restore (checkout) longpaths unset
fatal: cannot create directory at 'lp/aaaaaaaaaaaaaaaaaaaa/bbbbbbbbbbbbbbbbbbbb': Filename too long
exit=128
--- restore longpaths=true
exit=0
hi

설정이 꺼져 있으면 Git은 디렉터리를 열지 못해 Filename too long 경고를 내고 대상 파일을 찾지 못했다며 fatal: pathspec did not match로 종료한다. 반면 -c core.longpaths=true를 지정하면 파일이 정상적으로 스테이징 영역에 등록되고, 삭제 후 체크아웃 복원도 완벽히 성공한다.

5.3 .git/objects 쓰기 실패와 저장소 깊이 문제

그러나 core.longpaths=true가 만병통치약은 아니다. 저장소 루트 폴더 자체가 이미 232자로 깊은 위치에 있을 때 git add를 시도한 결과다. 이 PC의 전역 설정 core.longpaths=true가 켜진 상태 그대로 실행했다.

--- git add (no longpaths)
error: unable to write file .git/objects/45/b983be36b73c0788dc9cbcb76cbb80fc7bb057: No such file or directory
error: lp/…/long_file_name_for_test.txt: failed to insert into database
error: unable to index file 'lp/…/long_file_name_for_test.txt'
fatal: adding files failed
exit=128
--- -c core.longpaths=true add short.txt
error: unable to write file .git/objects/1d/3aaf18909062b31aeeeb3b683f1c2fad3e304e: No such file or directory
error: short.txt: failed to insert into database
error: unable to index file 'short.txt'
fatal: adding files failed
exit=128

놀랍게도 짧은 이름의 파일(short.txt)을 추가하는 데에도 core.longpaths=true 옵션을 주었음에도 실패했다. 원인은 파일 자체가 아니라 저장소 위치에 있었다. Git은 스테이징 시 .git/objects/xx/38자해시 경로에 개체 파일을 쓴다. 저장소 루트가 232자인 이 실험에서 객체 폴더 .git/objects/45는 248자, 객체 파일 경로는 291자로 260자를 넘었다. 이 환경(Git 2.48.1.windows.1)에서는 core.longpaths=true를 줘도 오류 문구만 「Filename too long」에서 「unable to write file … No such file or directory」로 바뀌었을 뿐 실패는 그대로였다.

6. 8.3 짧은 경로(ShortPath)를 활용한 우회와 대조 실험

원인이 오직 경로 길이에 있음을 증명하기 위해, 동일한 디렉터리를 가리키되 경로 문자열의 길이만 획기적으로 줄여 주는 Windows 8.3 단축 경로(ShortPath) 대조 실험을 진행했다.

6.1 8.3 짧은 경로(ShortPath)의 원리

이 환경의 폴더에는 PROGRA~1 같은 형태의 8.3 짧은 이름이 있었다. PowerShell에서 Scripting.FileSystemObject의 ShortPath 속성을 호출하면 230자가 넘던 임시 작업 경로가 C:\Users\<사용자>\…\tech_lab\ctl처럼 87자 수준으로 대폭 축소된다.

6.2 GIT_DIR 환경변수 직접 주입 대조 실험

주의할 점은 작업 폴더를 8.3 경로로 cd 하는 것만으로는 소용없었다는 사실이다. git rev-parse --show-toplevel이 긴 이름으로 되돌려 출력했고 git add도 같은 오류로 실패했다. GIT_DIR을 짧은 이름으로 직접 넘겼을 때만 성공했다.

# (Scripting.FileSystemObject).GetFolder(...).ShortPath → C:\Users\<사용자>\…\tech_lab\ctl  (87자대)
$env:GIT_DIR = "$s\.git"; $env:GIT_WORK_TREE = $s
git add a.txt; "exit=$LASTEXITCODE"
git ls-files -s

실제 콘솔 출력 결과는 다음과 같았다.

exit=0
100644 b88e8890e5b4d028a6d3849b4f4979cad8b07d3c 0	a.txt

저장소 폴더의 내용이나 Git 바이너리를 전혀 바꾸지 않고, 오직 저장소를 가리키는 경로 길이만 줄였을 뿐인데 즉시 완벽하게 성공(exit 0)했다. 이는 앞선 실패의 원인이 권한이나 파일 잠금이 아니라 순수하게 경로 길이에 있었음을 증명하는 결정적 대조군이다.

7. 「파일이 없다」고 결론 내리기 전 5단계 판단 순서

실제 운영 환경에서 특정 파일이나 디렉터리를 찾을 수 없다는 에러를 만났을 때, 엔지니어가 취해야 할 체계적인 점검 절차를 정리한다.

  • 1단계: 전체 경로 문자열의 길이를 측정한다 — 파일 부재나 권한 오류를 의심하기 전, PowerShell에서는 $path.Length, Python에서는 len(path)를 실행하여 절대 경로가 248자 또는 260자에 근접했는지 먼저 확인한다.
  • 2단계: 오류 메시지의 표면적 단어를 의심한다 — does not exist, No such file or directory, The system cannot find the path specified, 그리고 WinError 145(비어 있지 않음)는 모두 긴 경로로 인해 내부 API가 실패했을 때 뱉는 위장된 메시지일 수 있다.
  • 3단계: 재귀 탐색 도구의 종료 코드와 실제 출력을 교차 검증한다 — cmd dir /s /b는 긴 경로 파일을 조용히 누락하면서도 0을 반환하므로, Git Bash의 find나 Node.js 스크립트로 실제 디스크 파일 목록과 비교한다.
  • 4단계: 파일 읽기·삭제 시 \\?\ 접두사를 결합한다 — 일회성 점검이나 긴 폴더 정리 작업 시에는 상대 경로를 피하고, \\?\C:\... 형태의 정규화된 절대 경로를 넘겨 시스템 API를 직접 호출한다.
  • 5단계: Git 저장소의 위치 자체를 점검한다 — core.longpaths=true를 켰는데도 개체 쓰기 오류가 발생한다면 저장소 루트 경로가 깊은지 확인하고, 상위 디렉터리로 저장소를 이동하거나 8.3 단축 경로를 GIT_DIR로 전달한다.

7.1 경로 길이 측정과 도구별 검증 순서

경로 길이를 측정할 때는 상대 경로가 아닌 현재 작업 디렉터리가 포함된 완전한 정규 경로를 기준으로 삼아야 한다. 이 실험도 기준 폴더 자체가 228자였고, 그 길이가 결과(git 저장소 실패)에 그대로 영향을 줬다. 작업 폴더가 깊이 놓이는 환경이라면 작업 시작부에 경로 길이를 출력해 두는 편이 안전하다.

7.2 안전한 자동화 스크립트 작성 수칙

Windows 배치 스크립트(.bat)에서 dir /s를 이용한 파일 탐색에 의존하는 것은 극도로 위험하다. 중요한 배치 작업이라면 이 실험에서 긴 경로를 제대로 나열한 방법 — \\?\ 접두사를 붙인 Get-ChildItem -LiteralPath(단일 폴더)나 접두사를 붙인 Python os.listdir, Git Bash find, Node.js fs.readdirSync — 로 목록을 교차 확인한 뒤 넘기는 방식을 권한다.

8. 자주 묻는 질문 (FAQ)

실무에서 긴 경로 문제를 접했을 때 가장 빈번하게 나오는 의문점들을 정리했다.

  • Q1. Windows에서 경로가 260자를 넘으면 모든 프로그램이 실패하나?
    A. 아니다. 이 환경의 실험에서 322자 경로에 대해 cmd와 PowerShell, Python은 실패했지만, Git Bash(MSYS2)는 오류 없이 읽고 새 파일까지 썼고 Node.js 22는 오류 없이 읽고 목록을 냈다. 도구와 런타임마다 결과가 다르므로 단정할 수 없다.
  • Q2. cmd의 dir /s 명령이 긴 경로 파일 검색에서 왜 특히 위험한가?
    A. 이 실험에서 dir /s /b 명령은 294자 폴더와 322자 파일을 아무런 에러 메시지나 경고 없이 목록에서 뺐고(273자 폴더까지는 나열), 그러면서도 종료 코드(exit code) 0을 반환했다. 자동화 스크립트가 이를 신뢰하면 파일이 존재하지 않는다고 오판하게 된다.
  • Q3. git에서 core.longpaths=true를 설정했는데도 add가 실패하는 이유는?
    A. 이 설정은 작업 트리(working tree)의 파일만 구제한다. 저장소 루트 폴더 자체가 깊으면 Git 내부 개체 파일 경로(.git/objects/xx/...)가 260자를 넘어 내부 쓰기에서 실패한다. 저장소 자체를 짧은 경로에 두거나 8.3 단축 경로를 써야 한다.
  • Q4. \\?\ 확장 경로 접두사는 상대 경로에도 적용할 수 있나?
    A. 적용할 수 없다. 공식 문서에 따르면 \\?\ 접두사는 상대 경로에 쓸 수 없고, 그래서 상대 경로는 언제나 MAX_PATH(260자)로 제한된다.
  • Q5. Windows 레지스트리 LongPathsEnabled를 1로 켜면 모든 문제가 해결되나?
    A. 그렇지 않다. 레지스트리 설정 외에도 응용프로그램 매니페스트에 longPathAware 선언이 포함되어 있어야 하며, 값은 프로세스 수명 중 다시 읽히지 않아 재부팅이 필요할 수 있다. 문서는 이 설정이 새 기능을 쓰도록 수정된 응용프로그램에만 영향을 준다고 적고 있다(이 환경에서는 켜 보지 않았다).

9. 확인하지 못한 것

본 실습과 검증 과정에서 환경적 제약과 안전 수칙으로 인해 직접 확인하지 못한 사항들을 투명하게 기록한다.

  • LongPathsEnabled=1 변경 후의 실측: 이 글에서는 레지스트리 값을 1로 바꿔 보지 않았으므로, 값을 바꾸고 재부팅한 뒤 도구들의 반응이 어떻게 바뀌는지는 직접 확인하지 못했다. 해당 내용은 마이크로소프트 공식 기술 문서(Naming Files, Paths, and Namespaces)의 명세 내용에 근거하여 서술했다.
  • Git Bash 내부 구현의 상세 메커니즘: Git for Windows의 공식 문서(git-config.html)에는 msys 및 bash 툴체인이 긴 경로를 지원하지 않는다고 기술되어 있으나, 실제 실험에서 Git Bash의 ls, cat, find는 322자 경로를 정상 처리했다. MSYS2 런타임 계층이 내부적으로 어떤 방식으로 경로를 변환하여 처리했는지는 바이너리 레벨에서 확인하지 못했다.
  • 이종 운영체제 대조: 동일한 322자 경로에 대한 Linux 및 macOS 환경과의 실측 대조는 본 테스트 머신이 Windows 단일 환경이었으므로 직접 실행 대조하지 못했다.

# Windows MAX_PATH 260자 제한과 도구별 실패 양상 - 실무 참조표

검증 환경: Windows 10 Pro 10.0.19045, PowerShell 5.1, cmd.exe, Python 3.13.3, Git Bash(MSYS2), Node 22.16.0, git 2.48.1.windows.1. LongPathsEnabled=0 (기본 상태). 322자 파일 경로 기준.
표의 값과 출력은 이 환경에서 1회 실행해 확인한 것이고, 248자 경계·32,767자·상대 경로 제약은 Microsoft 문서 인용이다.

## 2. 도구별 실패 증상과 원인 대조표

| 화면에 출력된 증상 | 도구가 내린 표면적 결론 | 실제 내부 원인 | 점검 및 대응 |
|---|---|---|---|
| `False` 반환 (오류 없음) | 파일이 존재하지 않음 | PowerShell·Python 이 260자 초과 경로를 부재로 판단 | `$f.Length` 또는 `len(f)` 로 경로 문자 수 측정 |
| `Cannot find path ... because it does not exist` | 경로를 찾을 수 없음 | 일반 경로가 260자를 넘음 (`\\?\` 를 붙이면 읽힘) | `\\?\` 접두사를 붙여 절대 경로로 접근 |
| `The system cannot find the path specified` | 지정된 경로가 없음 | 일반 경로가 260자를 넘음 (`\\?\` 를 붙인 `dir`·`type` 은 성공) | `\\?\` 접두사 붙이거나 짧은 경로 사용 |
| **exit 0 종료, 목록에 파일 없음** | 검색 완료, 해당 파일 없음 | cmd `dir /s` 가 긴 경로 항목을 예외 없이 건너뜀 | 검색 결과를 맹신하지 말고 재귀 도구를 교차 검증 |
| `winerror= 206` (파일 이름이나 확장명이 너무 깁니다.) | 폴더/파일 이름 초과 | 디렉터리 경로 길이가 248자(MAX_PATH-12) 초과 | 상위 폴더 경로 단축 또는 `\\?\` 접두사 |
| `winerror= 145` (디렉터리가 비어 있지 않습니다.) | 폴더가 비어 있지 않아 삭제 불가 | 안쪽 긴 경로 파일을 일반 API 로 보지 못해 비우지 못함 | `\\?\` 접두사로 `os.walk(topdown=False)` 상향식 삭제 |
| `.git/objects/...: No such file or directory` | Git 내부 개체 파일 없음 | 저장소 루트가 깊어 내부 38자 해시 경로가 260자 초과 | 저장소를 짧은 경로로 옮기거나, `GIT_DIR` 환경변수에 8.3 짧은 경로 직접 전달 |

## 3. 긴 경로 트러블슈팅 5단계 점검표

- [ ] **1. 경로 길이를 센다**: 「파일이 없다」는 오류나 `False` 가 나오면 파일 존재 여부를 따지기 전에 전체 절대 경로 길이를 먼저 측정한다 (`len(path)` 또는 `$path.Length`).
- [ ] **2. 248자 폴더 경계를 확인한다**: Windows API 문서에 명시된 대로 디렉터리 경로는 `MAX_PATH - 12`(248자)에서 먼저 제한된다 (실측 252자 폴더 생성 실패).
- [ ] **3. `dir /s` 결과를 맹신하지 않는다**: cmd 의 `dir /s /b` 는 종료 코드 0으로 정상 종료하면서 294자 폴더와 322자 파일을 목록에서 조용히 빠뜨렸다(273자 폴더까지는 나열).
- [ ] **4. 파일 조작 시 `\\?\` + 절대 경로를 사용한다**: Windows 전용 확장 접두사 `\\?\` 는 최대 32,767자까지 허용하지만 상대 경로에는 적용할 수 없다.
- [ ] **5. 깊은 Git 저장소는 8.3 짧은 경로로 우회한다**: `core.longpaths=true` 는 작업 트리 파일만 구했다. 저장소 루트 자체가 깊으면 저장소를 짧은 경로에 두거나, 이 실험처럼 `GIT_DIR` 과 `GIT_WORK_TREE` 에 8.3 단축 경로를 직접 넘긴다(`cd` 만으로는 실패했다).
