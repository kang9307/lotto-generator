How 180 LLM Agents Audited a 130K-Line iOS App in a Day and Caught 55 Bugs

180 agents, 6 rounds, 55 confirmed bugs — what the "finder + verifier" structure actually controlled, and what it didn't

2026-07-14 Dev & Infra

Introduction: Can an Agent Fleet Break the Code Review Bottleneck?

As of July 2026, an intriguing experiment report surfaced in the Korean developer community involving a 21-language iOS social app with a codebase of roughly 130,000 lines. A handful of human reviewers combing through that much code in a single day is simply not realistic. Yet the author of this case reports deploying roughly 180 LLM agents across six rounds and confirming and fixing 55 bugs within a single day, including three cases where an issue already marked "fixed" turned out to have only been half-fixed.

This piece is not a retelling of that report for its own sake. What caught my attention is the design underneath the headline numbers (180 agents, 55 bugs, 130,000 lines). Why split the work into finders and verifiers instead of simply turning a swarm of agents loose? Why was that split necessary to keep the noise under control? And should "55 bugs in a day" be read purely as a productivity win, or does it need to be reassessed along a separate axis of precision and severity? Placed next to what happened in early 2026, when curl shut down its bug bounty program over a flood of low-quality AI-generated reports and HackerOne paused a major submission program for similar reasons, the reasons this case worked out differently come into sharper focus.

1. What Was Done — 180 Agents, 6 Rounds, One Day

Let's break the case down structurally first. The target was a 21-language iOS social app of about 130,000 lines. Rather than a single giant prompt or one pass of a static analysis tool, the author processed it through an agent pipeline spanning multiple rounds.

1.1 Finders — Hunting Candidates Through Orthogonal Lenses

The finder agents that search for bug candidates were each assigned a non-overlapping lens per round. Round 1 used a domain axis (feed, comments, chat, and other feature areas), round 2 used a failure-mode axis (crashes, data loss, race conditions, and other failure patterns), and round 3 used a family axis (finding similar patterns elsewhere based on bugs already discovered). Rounds 4 through 6 moved on to new lenses and free exploration. The core of this design is having the same code re-examined from different angles repeatedly, so that a bug missed from one angle gets caught from another. At the same time, minimizing overlap between lenses cuts down on the waste of multiple agents redundantly reporting the same bug.

1.2 Verifiers — Survival Requires Failing to Be Refuted

Once a finder submits a candidate, a separate verifier agent is instructed to try to refute that report. Refutation, not confirmation, is the default mission, and that distinction matters. Only items the verifier fails to refute, meaning they still look like real bugs no matter how hard they are picked apart, remain on the confirmed list. This is a considerably stricter bar than simply being told to verify. An agent tasked with confirming tends to drift unconsciously toward confirming, whereas an agent tasked with refuting has to find a flaw to let something through, which makes the pass bar itself far more conservative.

1.3 Results and the Stopping Condition

Across these six rounds, roughly 180 agents in total were deployed, and 55 bugs were ultimately confirmed and fixed. What is interesting is the stopping condition. Once the free-exploration rounds stopped producing newly confirmed bugs in a row, the pipeline halted at that point. In other words, rather than running until a fixed quota was hit, the pipeline used the point where marginal returns dropped off as the signal to stop. That is a practical safeguard against endlessly burning compute on agents.

2. Why a Two-Stage Finder+Verifier Structure Is Necessary — the Core of Noise Control

The first problem you hit when handing a large codebase to an LLM is not volume, it is reliability. This case looks well designed in that it places a specific countermeasure against each of the LLM's typical failure modes.

2.1 Four Failure Modes and Their Countermeasures

  • Hallucination — inventing code or behavior that does not exist. Countered by enforcing a JSON output schema and instructing agents not to report anything they are not confident about.
  • Shallow scanning — vague pointers without a file name or line number. Countered by requiring a file and line to be specified, which filters out unsubstantiated claims.
  • Duplicate discovery — multiple rounds or agents repeatedly reporting the same bug. Countered by continuously injecting the already-confirmed bug list into the next round's prompt.
  • Confidently wrong answers — plausible-sounding but incorrect claims delivered with confidence. Countered by giving the verifier a refutation mission, so only claims that survive an adversarial attempt to disprove them pass through.

2.2 Where This Meets the Broader Research and Industry Trend

This idea is not an isolated invention; it lines up with where recent LLM-based code-audit research has been converging. RepoAudit, a repository-level automated audit agent, uses a separate verifier that re-checks dataflow facts and path-condition satisfiability to filter out false positives, and it reports precision around 65 percent on Claude 3.5 Sonnet, reaching about 78 percent in its best case. QASecClaw, which combines static analysis with an LLM filter in two stages, has the LLM filter agent re-review the candidates a SAST engine produces, and reports cutting false positives from 560 to 64, an 88.6 percent reduction versus a single Semgrep pass, while losing only 3.1 percent recall. The backbone of this case, a dedicated verification gate, points in the same direction these studies commonly arrive at.

2.3 The Counterexample — What Happens When LLMs Are Turned Loose Without a Gate

The value of this structure becomes clearer when you look at the counterexample. In January 2026, the curl project ended its bug bounty program. A large share of submissions were low-quality, AI-written reports, and the share of genuinely valid vulnerabilities had fallen to around 5 percent. That March, HackerOne suspended submissions to its Internet Bug Bounty program, citing an AI-driven volume of reports that had outpaced its triage capacity. In both cases, only half the equation, an LLM finding candidates, was present, without a separate verification gate that requires failing to be refuted before something passes, the way this case has. They serve as a control group showing what happens when you have finders but no verifiers.

3. How to Read "55 Bugs in a Day" — Between Productivity and Precision

The numbers alone are impressive. But separating out a few different axes keeps this result from being over- or under-valued.

3.1 What "Zero False Positives at Deployment" Actually Means

The author states that there were zero false positives at the final deployment and confirmation stage. Even taken at face value, that does not mean the finders never generated any false positives in the first place. Read precisely, it means that among the candidates the finders raised, only the ones that survived the verifier's attempt at refutation made the final list, and that final list happened to contain no false positives. In other words, zero false positives is less a measure of the finders' precision and more an indicator of the verification gate's filtering performance.

3.2 Confirmed Bugs and Critical Bugs Are Different Questions

Whether all 55 items were confirmed as genuine bugs, and how important those 55 items actually are, are separate questions. A defect that crashes the app and a minor UI misalignment that only shows up in one locale both count as one item, but they carry very different weight. The public summary alone does not reveal the severity breakdown (critical, major, minor) across the 55. What makes this pipeline genuinely powerful is not how many critical bugs it caught, but that it swept a broad surface humans tend to miss and narrowed it down to a manageable set of candidates. Judging importance and setting final priority still has to remain a human job.

3.3 Productivity vs. Precision — the Balance This Case Aims For

Having a team of human reviewers comb through the same codebase in a single day is not realistically possible. On the other hand, turning LLM agents loose with no verification at all erodes trust, as the curl case shows. What makes this case interesting is that it aimed simultaneously at coverage (180 agents sweeping all 130,000 lines from multiple angles) and precision (a refutation-survival gate). That said, it also means the team paid a verification cost on par with, or larger than, the finder cost. If you only look at the "55 in a day" headline, it is easy to overweight the productivity story and underweight the cost of the verification rounds behind it.

4. The Value of This Approach — Filling in What Human Review Can't Cover

4.1 Answering a Scale Problem With Scale

A codebase of 130,000 lines across 21 languages is beyond what a small human review team can realistically cover. Deploying agents in parallel across multiple angles (domain, failure mode, family, free exploration) meets that scale problem with scale of its own. Instead of a human prioritizing and only seeing part of it, the machine sweeps the whole thing multiple times, and a human only has to review the narrowed-down candidates.

4.2 Repetition Without Fatigue

Human reviewers get bored and tired re-examining the same code from multiple angles over and over. It is telling that this case caught three half-fixed items that had already been marked resolved. Re-doubting and re-verifying an issue that has already been closed once is work that rarely motivates a person, but to an agent it is just another lens.

4.3 Division of Labor — Triage, Not Replacement

The most important point is the limitation the author states outright: static analysis alone cannot verify type checking or runtime behavior, and real-device verification remains a human job. This pipeline does not replace human review, it functions as a filter that narrows the list of candidates a human needs to check on a real device from 130,000 lines down to 55 items. The value is not that AI did everything, it is that AI shrank the scope of human review down to something manageable.

5. Limitations — Hallucination, Context, Verification Cost, and Severity Triage

5.1 The Blind Spot of Static Analysis

As the author explicitly states, this pipeline is grounded in static analysis. Errors a type checker would catch, or runtime behavior that only reproduces on a real device or network, are hard for a text-reading agent to verify. Reading and reasoning about code is a different kind of evidence from actually running it and observing what happens. This limitation is not a flaw in the tooling, it is a limitation of static auditing as a methodology itself, which is exactly why a separate real-device gate is needed.

5.2 Verification Doesn't Come Free

The more strictly the verifier is designed relative to the finder, the more compute and cost verification consumes. For reference, the RepoAudit research reported an average of about 0.44 hours and $2.54 per project, a figure based on a single agent that includes verification. Separating finders from verifiers and scaling up to six rounds and 180 agents necessarily pushes the total cost higher than that. Behind the "done in a day" headline sits the question of whether an organization can absorb that cost, and the answer will differ from team to team.

5.3 Orchestration Doesn't Guarantee Correctness

Research on agent orchestration frequently draws a distinction worth repeating here: an orchestrator guarantees a coordination contract, not a verification contract. That is, it guarantees the agents followed the defined protocol, not that the resulting output is actually correct. This case's refutation-survival gate looks like an attempt at something closer to a verification contract, but based on the publicly available information alone, there is no way for an outsider to confirm whether the deployed fixes were entirely problem-free afterward. That caveat is worth keeping in mind whenever citing self-reported figures like these.

5.4 The Problem of Separating Truly Severe Bugs

Determining which of the 55 confirmed items are critical defects that drive user churn or crashes, versus which are minor and safe to ignore, appears to sit outside this pipeline's scope. Severity triage needs a separate prioritization gate (business impact, frequency of occurrence, number of affected users), and that is a judgment call for people who understand product and operational context, not an agent that only reads code.

6. Practical Tips — Designing Orchestration, Cost, and Verification Gates

6.1 Always Separate the Finder From the Verifier

Letting a single agent both find and confirm its own findings bakes confirmation bias straight into the result. The minimum viable skeleton is to physically separate the role that proposes candidates from the role that refutes them. Framing the verifier's mission as "try to refute this, and let it through only if you fail" rather than "confirm this" produces a noticeably more conservative outcome.

6.2 Design Rounds Around Orthogonal Lenses

Sweeping the same lens repeatedly just surfaces the same bugs over and over. Assigning non-overlapping perspectives per round, such as domain, failure mode, family resemblance to already-found bugs, and free exploration, widens coverage and cuts down on duplicate reports.

6.3 Structurally Block Hallucination, Duplication, and Weak Evidence

Three simple devices go a long way toward preempting a large share of the common failure modes: enforcing a schema to control the output format, requiring concrete evidence like a file and line number, and cumulatively injecting the already-confirmed list into each subsequent round's prompt.

6.4 Set a Stopping Condition and a Cost Ceiling in Advance

A marginal-returns-based stopping rule, such as ending the pipeline once a round in a row produces no newly confirmed bugs rather than running until a fixed count is reached, prevents cost from leaking out indefinitely. At the same time, budget the verifier's cost separately from the finder's cost. Design the verification step carelessly and false positives creep back in, which can erode trust the way the curl case did.

6.5 Always Keep a Real-Device, Human Gate at the End

To fill the gap this pipeline openly admits it has, namely the runtime and type issues static analysis cannot see, do not remove the final step where a human confirms the confirmed candidates on an actual device. AI-driven auditing should be positioned not as a tool that eliminates human review, but as a tool that shrinks what needs reviewing down to a manageable size.

7. Where AI-Agent-Based Code Auditing Goes From Here

Moving through the first half of 2026, attempts to apply LLM agents to code auditing and QA seem to be splitting into two broad camps. One camp pours out candidates with no verification gate and ends up losing trust the way curl and HackerOne did. The other, this case included alongside RepoAudit and QASecClaw, separates finders from verifiers to defend precision. What this case suggests is that the latter approach can genuinely work even at the scale of a single-day, large-codebase audit, and at the same time it is a warning against oversimplifying the result as "AI did it all." The most accurate way to read this case is to keep three things in mind: static auditing cannot replace a human's real-device check, 55 confirmed bugs is not the same as 55 critical bugs, and zero false positives is a number that only exists after the verification gate.

Conclusion

The idea of auditing a large codebase in parallel with a fleet of LLM agents is already a direction multiple studies and cases have been validating. What makes this particular case stand out is that it paired the finders' orthogonal-lens design with the verifiers' refutation-survival gate, aiming at coverage and precision at the same time. But when reading "55 bugs in a day," it is worth remembering that zero false positives at deployment does not mean the finders were flawless, that bug count and bug severity are different axes, and that static analysis still needs a real-device, human gate to follow it. Any organization looking to bring a pipeline like this into practice should budget verification cost as seriously as finder cost, and design the stopping condition and severity gate up front.
