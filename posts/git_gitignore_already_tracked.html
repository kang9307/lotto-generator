.gitignore에 넣었는데 계속 올라간다 - 이미 추적 중인 파일

규칙이 틀린 것이 아니라 순서가 틀렸다. 빼내는 법과, 빼내도 히스토리에는 남는다는 문제

2026-09-01 개발/인프라

설정 파일 하나가 자꾸 커밋에 딸려 온다. 이름을 .gitignore에 적고, 파일을 고치고, git status를 친다. 그대로 있다. 오타를 의심해 다시 적고, 슬래시를 붙였다 뗐다 하고, 별표를 넣어 본다. 그래도 그대로다.

여기서 대부분은 패턴 문법을 검색하기 시작한다. 그런데 이 증상의 다수는 문법 문제가 아니다. 규칙이 틀린 것이 아니라 규칙을 적은 시점이 늦은 것이다. 이 글은 그 이유를 임시 저장소에서 재현해 보이고, 빼내는 명령과 그 명령이 하지 못하는 일까지 정리한다. 마지막 대목이 가장 중요하다.

아래의 모든 출력은 임시 디렉터리에 새로 만든 빈 저장소에서 실제로 실행해 얻은 것이다. 명령 중 일부는 되돌릴 수 없으므로, 읽으면서 따라 할 때도 실제 작업 저장소가 아니라 버려도 되는 디렉터리에서 하는 편이 좋다.

실행 환경

이 글의 모든 출력은 아래 환경에서 얻었다. Git 자체의 동작은 플랫폼을 크게 타지 않지만, 줄바꿈 처리나 경로 표기처럼 셸과 운영체제에 따라 달라지는 대목이 있으므로 밝혀 둔다.

  • 운영체제 - Windows 10 Pro (빌드 10.0.19045)
  • 셸 - Git Bash (GNU bash 5.2.37(1)-release, x86_64-pc-msys)
  • Git - git version 2.48.1.windows.1
  • 저장소 - 임시 디렉터리에 git init -b main으로 새로 만든 빈 저장소. 실제 작업 저장소는 건드리지 않았다

리눅스나 macOS의 bash·zsh에서도 아래 출력은 거의 그대로 재현된다. 차이가 생길 수 있는 곳은 두 군데다. 파일명 대소문자 구분(Windows와 기본 설정의 macOS는 구분하지 않아 Build/와 build/가 같게 취급될 수 있다), 그리고 core.autocrlf다. 후자는 결과가 흔들리지 않도록 false로 고정했다.

재현 - 이미 커밋된 파일은 규칙을 보지 않는다

말로 설명하는 것보다 한 번 돌려 보는 쪽이 빠르다. 빈 저장소를 만들고, 설정 파일을 하나 커밋하고, 그 다음에 .gitignore를 적는다. 현실에서 벌어지는 순서와 똑같다.

$ git init -b main demo && cd demo
$ echo 'API_KEY=placeholder' > config.local.json
$ git add -A && git commit -m "initial commit"

# 여기까지는 아무 문제가 없다. 이제 규칙을 건다.
$ echo 'config.local.json' > .gitignore
$ git add .gitignore && git commit -m "add gitignore"

# 그리고 그 파일을 고친다.
$ printf 'API_KEY=changed-secret\n' > config.local.json
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
	modified:   config.local.json

no changes added to commit (use "git add" and/or "git commit -a")

규칙은 분명히 적혀 있는데 modified: config.local.json이 그대로 뜬다. 이유는 인덱스를 들여다보면 바로 보인다.

$ git ls-files
.gitignore
README.md
config.local.json
src/app.js

$ git check-ignore -v config.local.json
$ echo $?
1

git ls-files는 인덱스에 등록된 경로, 즉 현재 추적 중인 파일 목록을 출력한다. 여기에 config.local.json이 버젓이 들어 있다. 그리고 git check-ignore는 아무 말도 하지 않고 종료 코드 1을 돌려준다. 규칙이 없어서가 아니라 추적 중인 경로는 무시 판정 대상이 아니어서 검사를 건너뛴 것이다. 이 침묵은 뒤의 진단 절에서 다시 다룬다.

  • 증상은 「규칙을 무시한다」로 보이지만 실제로는 규칙을 읽지도 않는 상태다
  • 패턴을 열 번 고쳐도 결과가 같다면 문법을 더 만지는 것은 시간 낭비다. 인덱스부터 본다
  • 판별은 한 줄이면 끝난다. git ls-files에 그 경로가 있으면 원인은 확정이다

왜 그렇게 설계됐나

공식 문서는 이 동작을 첫 문장에 명시해 두었다. gitignore 문서는 「의도적으로 추적하지 않는 파일을 지정한다. 이미 Git이 추적 중인 파일은 영향을 받지 않는다」로 시작한다. 예외적인 동작이 아니라 선언된 사양이다.

왜 이렇게 정했는지는 반대 경우를 상상하면 납득이 간다. .gitignore에 한 줄을 추가하는 것만으로 이미 저장소의 일부인 파일이 조용히 빠진다면, 텍스트 한 줄이 버전 관리 대상의 삭제 명령이 되는 셈이다. *.conf 같은 넓은 패턴 하나에 수십 개의 추적 파일이 한꺼번에 이력에서 이탈할 수 있다. 게다가 이 파일은 커밋되어 팀 전체에 전파된다. 한 사람의 편의를 위한 한 줄이 남의 저장소에서 파일을 떨어뜨려서는 곤란하다.

그래서 Git은 두 가지를 분리했다. 무엇을 새로 담지 않을 것인가는 설정 파일이 정하고, 이미 담긴 것을 꺼내는 일은 명시적인 명령으로만 하게 했다. 문서의 NOTES 절도 이 순서를 안내한다. 추적을 멈추려면 git rm --cached로 인덱스에서 지우고, 그 다음에 .gitignore에 이름을 적어 다시 들어오지 않게 하라는 것이다.

  • 설정 파일은 미래에 대한 규칙이고, 이미 존재하는 이력에 소급하지 않는다
  • 이력에서 무언가를 빼는 것은 되돌리기 어려운 동작이므로 별도의 명령을 요구한다
  • 이 분리 덕분에 .gitignore를 실수로 넓게 적어도 최악의 결과는 「새 파일이 안 잡힌다」에서 멈춘다

빼내는 법 - git rm --cached

추적을 멈추는 명령은 하나다. git rm --cached다. 인덱스에서만 항목을 제거하고 작업 디렉터리의 실제 파일은 손대지 않는다. 앞의 저장소에서 이어서 실행해 보면 이렇게 된다.

$ git rm --cached config.local.json
rm 'config.local.json'

$ ls -1
README.md
config.local.json
src

$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	deleted:    config.local.json

$ git commit -m "stop tracking config.local.json"
$ printf 'API_KEY=another-change\n' > config.local.json
$ git status --short

$ git check-ignore -v config.local.json
.gitignore:1:config.local.json	config.local.json

순서대로 읽으면 이렇다. rm --cached 직후 파일은 디스크에 그대로 있고(ls -1 출력에 남아 있다), 인덱스에서는 삭제로 스테이징된다. 커밋을 마친 뒤 같은 파일을 고쳐도 git status --short는 아무것도 출력하지 않는다. 그리고 이제야 check-ignore가 입을 연다. 어느 규칙이 이 경로를 잡았는지 줄 번호까지 알려 준다.

주의 - --cached를 빠뜨린 git rm 경로는 인덱스와 작업 디렉터리의 파일을 함께 삭제한다. 커밋되지 않은 내용이 들어 있던 로컬 설정 파일이었다면 복구할 방법이 없다. 이 글에서 다루는 목적으로는 --cached가 반드시 붙어야 한다.

디렉터리를 통째로 빼낼 때는 -r가 필요하다. 붙이지 않으면 Git이 거부한다. 실행하기 전에 --dry-run으로 대상 목록을 먼저 보는 습관이 좋다.

$ git rm --cached node_modules
fatal: not removing 'node_modules' recursively without -r

$ git rm -r --cached --dry-run node_modules
rm 'node_modules/pkg/index.js'

$ git rm -r --cached node_modules
  • --cached - 인덱스에서만 제거한다. 작업 디렉터리의 파일은 남는다
  • -r - 디렉터리를 대상으로 할 때 필요하다. 없으면 fatal로 거부된다
  • --dry-run - 목록만 출력하고 실제로는 아무것도 바꾸지 않는다
  • 제거를 커밋해야 효과가 확정된다. 그 전까지는 인덱스에만 반영된 상태다

한 번에 정리하는 관용구와 그 대가

추적을 멈춰야 할 파일이 여러 개일 때 자주 쓰이는 방법이 있다. 인덱스를 통째로 비우고 다시 채우는 것이다. 비운 다음 git add .로 다시 담으면, 그 시점에 유효한 .gitignore 규칙이 적용되면서 무시 대상만 자연스럽게 빠진다.

$ git rm -r --cached . --dry-run
rm '.gitignore'
rm 'build.log'
rm 'src/app.js'

편리하지만 조건이 하나 붙는다. 커밋되지 않은 변경이 하나도 없는 상태에서만 써야 한다. 인덱스를 비웠다가 다시 채우는 동작은 무시 규칙만 걸러 내는 것이 아니라, 그 순간 작업 디렉터리에 있는 모든 상태를 그대로 담기 때문이다. 아래는 커밋되지 않은 편집이 하나 있는 상태에서 관용구를 실행한 결과다.

$ echo 'app-edited-but-not-committed' > src/app.js
$ git status --short
 M src/app.js

$ git rm -r --cached .
$ git add .
$ git status --short
D  build.log
M  src/app.js

$ git diff --cached --stat
 build.log  | 1 -
 src/app.js | 2 +-
 2 files changed, 1 insertion(+), 2 deletions(-)

의도한 것은 build.log의 추적 해제 하나뿐인데, 아직 검토하지 않은 src/app.js의 편집이 같은 커밋에 섞였다. 파일이 수백 개인 저장소라면 커밋 메시지와 실제 내용이 어긋나고 나중에 원인을 찾기 어려워진다. 그래서 순서는 이렇게 잡는다.

  • 먼저 git status가 깨끗한지 확인한다. 남은 변경은 커밋하거나 따로 보관한다
  • --dry-run으로 목록을 본다. 예상보다 많이 나오면 규칙이 너무 넓다는 신호다
  • 대상이 몇 개뿐이면 관용구 대신 경로를 하나씩 지정한다. 사고 범위가 그 경로로 한정된다
  • 커밋 전에 git diff --cached --stat로 무엇이 담겼는지 확인한다

빼내도 히스토리에는 남는다

여기가 이 글에서 가장 중요한 대목이다. git rm --cached는 그 커밋 이후로만 파일을 제외한다. 과거 커밋에는 내용이 조금도 손상되지 않은 채 그대로 있다. 인덱스에서 사라진 것을 「지워졌다」로 읽으면 위험한 착각이 된다.

아래는 비밀번호가 든 파일을 두 번 커밋한 뒤 추적을 해제하고, 그 다음에 무엇을 읽을 수 있는지 확인한 결과다. 값은 실험용 자리표시자다.

$ git ls-files
.gitignore
src/app.js

$ git log --oneline -- config/secrets.env
295c575 stop tracking secrets.env
dec8b71 update settings
61f23fd initial commit

$ git show HEAD~2:config/secrets.env
DB_PASSWORD=placeholder-not-a-real-secret

$ git rev-list --objects --all | grep secrets.env
c6dd1f3ef86e381a694fa8c4ad29b2ea0463e33e config/secrets.env
934ceb11a04aff62ef5aaa84c79377a41d57ba15 config/secrets.env

현재 추적 목록에는 없다. 그런데 git log는 그 파일을 건드린 커밋을 전부 나열하고, git show 커밋:경로 한 줄이면 당시 내용이 그대로 출력된다. 마지막 명령이 더 분명하다. 두 버전의 블롭 객체가 객체 데이터베이스에 그대로 남아 있고, 저장소를 복제한 사람은 이것도 함께 받는다.

과거 커밋에서까지 파일을 없애려면 이력 재작성이 필요하고, 그것은 성격이 완전히 다른 작업이다. 모든 커밋 해시가 바뀌므로 저장소를 복제해 간 사람이 전부 영향을 받고, 브랜치·태그·병합 요청과의 정합이 깨진다. 이 글에서는 그런 작업이 별도로 필요하다는 사실까지만 짚고 절차는 다루지 않는다. 대부분의 상황에서 그것은 첫 번째로 할 일도 아니다.

  • rm --cached는 미래의 커밋만 바꾼다. 과거는 그대로다
  • 브랜치를 지우거나 커밋을 되돌려도 객체는 즉시 사라지지 않는다. reflog가 남아 있는 동안 계속 읽힌다
  • 이력 재작성은 모든 커밋 해시를 바꾸므로 공유된 저장소에서는 협업자 전원의 조율이 전제다
  • 원격에 이미 올렸다면 로컬에서 무엇을 하든 상대편 사본은 남아 있다고 봐야 한다

자격증명이 들어갔다면 키 교체가 먼저다

비밀번호나 API 키가 커밋에 들어간 것을 발견하면 반사적으로 손이 가는 곳은 파일을 지우는 쪽이다. 순서가 반대다. 파일을 아무리 깔끔하게 지워도 이미 읽힌 값은 되돌아오지 않는다. 원격에 올라갔거나, 누군가 복제했거나, 백업·미러·CI 캐시에 사본이 남아 있다면 그 값은 노출된 것으로 취급해야 한다.

그래서 우선순위는 명확하다. 노출된 자격증명을 폐기하고 새로 발급하는 것이 첫 번째다. 새 값이 유효해지는 순간 옛 값은 쓸모가 없어지고, 이력에 남아 있든 말든 위험이 사라진다. 반대로 이력부터 손대면 그 작업이 진행되는 동안에도 옛 키는 계속 살아 있다.

  • 1순위 - 해당 키·토큰·비밀번호를 폐기하고 새로 발급한다. 발급처 콘솔에서 옛 값을 즉시 무효화한다
  • 2순위 - 그 자격증명으로 접근 가능한 곳의 로그를 확인해 실제 사용 흔적이 있었는지 본다
  • 3순위 - git rm --cached와 .gitignore로 같은 일이 반복되지 않게 막는다
  • 4순위 - 필요하다면 이력 재작성을 계획한다. 협업자 조율이 끝난 뒤에 한다

덧붙이면 자격증명은 애초에 파일로 저장소에 두지 않는 편이 낫다. 환경 변수나 별도의 비밀 관리 수단을 쓰고, 저장소에는 값이 빈 예시 파일만 둔다. config.example.json처럼 이름을 나누면 예시는 추적하고 실제 파일은 규칙으로 막는 구성이 나온다.

안 먹는 이유 1 - 경로 패턴

인덱스 문제가 아닌데도 규칙이 안 먹는다면 다음 후보는 패턴 표기다. 헷갈리는 지점은 두 개로 압축된다. 앞에 붙는 슬래시와 뒤에 붙는 슬래시다.

공식 문서의 규정은 이렇다. 패턴의 처음이나 중간에 구분자가 있으면 그 .gitignore가 있는 디렉터리를 기준으로 한 상대 경로가 되고, 없으면 그 아래 어느 깊이에서든 매칭된다. 패턴 끝에 구분자가 있으면 디렉터리만, 없으면 파일과 디렉터리를 모두 매칭한다.

# build/ 와 src/build/ 두 디렉터리가 있는 상태

$ printf '/build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:/build/	build/out.o
# src/build/out.o 는 출력에 없다 = 무시되지 않았다

$ printf 'build/\n' > .gitignore
$ git check-ignore -v build/out.o src/build/out.o
.gitignore:1:build/	build/out.o
.gitignore:1:build/	src/build/out.o

선행 슬래시 하나가 「최상위의 build만」과 「어느 깊이의 build든」을 갈랐다. 다음은 뒤에 붙는 슬래시다. cache를 디렉터리로 만들었다가 파일로 바꾸면서 같은 규칙을 걸어 본 결과다.

# cache 가 디렉터리일 때
$ printf 'cache\n' > .gitignore
$ git check-ignore -v cache/a.txt
.gitignore:1:cache	cache/a.txt

# cache 가 파일일 때 - 같은 규칙이 그대로 먹는다
$ git check-ignore -v cache
.gitignore:1:cache	cache

# 규칙 끝에 슬래시를 붙이면 파일에는 안 먹는다
$ printf 'cache/\n' > .gitignore
$ git check-ignore -v cache
$ echo $?
1

# 같은 규칙이 디렉터리에는 먹는다
$ git check-ignore -v cache/a.txt
.gitignore:1:cache/	cache/a.txt

아래는 자주 쓰는 표기와 그 결과다.

표기의미매칭되는 예매칭되지 않는 예
buildbuild라는 파일과 디렉터리, 깊이 무관build, src/build이름이 다른 것
build/디렉터리만, 깊이 무관build/, src/build/build라는 이름의 파일
/build/최상위의 build 디렉터리만최상위 build/src/build/
*.loglog 확장자, 깊이 무관a.log, logs/b.loglog.txt
logs/*.loglogs 바로 아래만. 중간 슬래시가 위치를 고정logs/a.loglogs/sub/a.log
logs/**/*.loglogs 아래 모든 깊이logs/sub/a.loglogs 밖의 로그
  • 패턴에 슬래시가 하나도 없으면 위치가 자유롭다. 의도보다 넓게 잡히는 사고가 여기서 나온다
  • 디렉터리만 노린다면 끝에 슬래시를 붙인다. 같은 이름의 파일까지 잡히는 일을 막는다
  • 패턴은 그 .gitignore가 놓인 디렉터리를 기준으로 해석된다. 하위 디렉터리에 놓인 파일의 /foo는 저장소 최상위가 아니라 그 디렉터리의 foo다

안 먹는 이유 2 - 부정 패턴이 살아나지 않는 자리

「이 디렉터리는 다 무시하되 이 파일 하나만 남기고 싶다」는 요구는 흔하다. 그래서 디렉터리를 통째로 제외하고 그 아래 파일 하나에 느낌표를 붙인다. 그런데 이 조합은 작동하지 않는다.

$ printf 'logs/\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/	logs/error.log
# ! 를 적었는데도 1행이 이겼다

$ printf 'logs/*\n!logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ git check-ignore -v logs/debug.log
.gitignore:1:logs/*	logs/debug.log

차이는 logs/와 logs/* 하나다. 앞의 것은 디렉터리 자체를 제외하고, 뒤의 것은 디렉터리 안의 항목들을 제외한다. 공식 문서는 이유를 명확히 적어 두었다. 부모 디렉터리가 제외된 파일은 다시 포함시킬 수 없으며, 성능상의 이유로 Git이 제외된 디렉터리의 내용을 나열하지 않기 때문에 그 안의 파일에 대한 패턴은 어디에 적든 효과가 없다는 것이다. 디렉터리를 통째로 닫으면 Git은 그 안을 들여다보지도 않는다.

두 번째 함정은 순서다. 무시 규칙은 마지막으로 매칭된 패턴이 결과를 정한다. 예외를 먼저 적고 넓은 규칙을 나중에 적으면 예외가 덮인다.

$ printf '!logs/error.log\nlogs/*\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:2:logs/*	logs/error.log

같은 두 줄인데 순서만 바꾸니 결과가 뒤집혔다. 2행의 넓은 규칙이 1행의 예외를 덮었다. 이 때문에 .gitignore는 넓은 규칙을 위에, 예외를 아래에 두는 순서가 사실상의 표준이다.

  • 디렉터리 안의 예외가 필요하면 dir/가 아니라 dir/*로 적는다. 한 글자 차이가 전부다
  • 중첩이 깊으면 단계별로 열어 줘야 한다. dir/*, !dir/sub/, dir/sub/*, !dir/sub/keep.txt 식이다
  • 느낌표 줄은 항상 그것이 뒤집으려는 규칙보다 아래에 온다

안 먹는 이유 3 - 어느 파일의 규칙이 이겼는가

무시 규칙을 적을 수 있는 곳은 한 군데가 아니다. 저장소의 .gitignore, 하위 디렉터리마다 놓인 .gitignore, .git/info/exclude, 그리고 core.excludesFile로 지정한 전역 파일이 모두 동시에 작동한다.

공식 문서가 정한 우선순위는 높은 쪽부터 이렇다. 명령줄로 넘긴 패턴, 해당 경로가 있는 디렉터리와 상위 디렉터리들의 .gitignore(하위에 가까운 파일이 상위를 덮는다), info/exclude, 마지막이 전역 파일이다. 같은 단계 안에서는 마지막 매칭이 이긴다. 네 단계를 차례로 겹쳐 보면 이렇게 나온다.

# 1) 전역 무시만 있을 때 (my_global_ignore 내용은 *.log)
$ git config core.excludesFile my_global_ignore
$ git check-ignore -v logs/error.log
my_global_ignore:1:*.log	logs/error.log

# 2) .git/info/exclude 가 전역을 이긴다
$ printf '!logs/error.log\n' > .git/info/exclude
$ git check-ignore -v logs/error.log
.git/info/exclude:1:!logs/error.log	logs/error.log

# 3) 저장소 .gitignore 가 info/exclude 를 이긴다
$ printf 'logs/error.log\n' > .gitignore
$ git check-ignore -v logs/error.log
.gitignore:1:logs/error.log	logs/error.log

# 4) 하위 디렉터리 .gitignore 가 상위를 이긴다
$ printf '!error.log\n' > logs/.gitignore
$ git check-ignore -v logs/error.log
logs/.gitignore:1:!error.log	logs/error.log

네 번의 실행에서 매번 다른 파일이 판정자로 지목됐다. 규칙을 여러 군데 나눠 적어 놓고 왜 안 먹는지 고민하는 상황이라면 이 출력 자체가 답이다.

적는 곳공유 여부우선순위쓰기 적당한 것
하위 디렉터리 .gitignore커밋되어 공유가장 높음그 디렉터리에만 해당하는 규칙
최상위 .gitignore커밋되어 공유높음빌드 산출물, 의존성, 비밀 파일 이름
.git/info/exclude공유되지 않음중간이 저장소에서 나만 쓰는 임시 파일
core.excludesFile 전역 파일공유되지 않음가장 낮음편집기·OS가 만드는 부산물
  • 같은 경로에 여러 규칙이 걸리면 하위 디렉터리의 파일이 상위를 이긴다. 상위에서 막고 하위에서 여는 구성이 가능하다
  • 전역 파일은 가장 약하다. 저장소가 명시적으로 무시하겠다고 적은 것을 전역 설정이 뒤집지 못한다
  • 규칙이 안 보이는데 파일이 무시된다면 전역 파일과 info/exclude를 의심한다. 둘 다 저장소 안에 보이지 않는 곳이다

진단 - check-ignore가 범인을 지목한다

앞의 절들에서 계속 써 온 git check-ignore -v가 표준 진단 도구다. 경로를 넘기면 어느 파일 몇 번째 줄의 어떤 규칙이 판정했는지를 탭으로 구분해 출력한다. 읽을 때 알아 둬야 할 특성이 셋 있다.

# 1) 추적 중인 파일에는 아무 말도 하지 않는다
$ git check-ignore -v kept.txt
$ echo $?
1

# 2) --no-index 를 붙이면 규칙이 보인다
$ git check-ignore -v --no-index kept.txt
.gitignore:1:kept.txt	kept.txt

# 3) -v 의 종료 코드는 「무시됨」이 아니라 「규칙에 걸림」이다
#    규칙: logs/* 와 !logs/error.log
$ git check-ignore -v logs/error.log
.gitignore:2:!logs/error.log	logs/error.log
$ echo $?
0
$ git check-ignore logs/error.log
$ echo $?
1

첫째, 이미 추적 중인 파일에는 침묵한다. 이 글 앞부분에서 본 그 침묵이다. --no-index 설명이 이 용도를 그대로 적어 두었다. git add . 같은 명령으로 파일이 추적 상태가 된 이유를 디버깅할 때 쓰라는 것이다. 출력이 비었는데 --no-index를 붙이면 나온다면 그 파일은 추적 중이고, 답은 이미 나온 것이다.

둘째, 출력된 규칙이 느낌표로 시작하면 그 경로는 무시되지 않는다. 문서의 -v 설명에도 「패턴이 !로 시작하면 부정 패턴이며 매칭되었다는 것은 그 경로가 제외되지 않는다는 뜻」이라고 적혀 있다. 출력이 있다고 「무시됨」으로 읽으면 정반대가 된다.

셋째, 그래서 종료 코드도 주의해서 읽어야 한다. 위 실행에서 -v를 붙였을 때는 0, 뗐을 때는 1이 나왔다. 판정이 뒤집힌 것이 아니라, -v는 「규칙에 매칭됐다」를 성공으로 보고 -v 없는 형태는 「실제로 무시된다」를 성공으로 본다. 스크립트에서 판정에 쓸 때는 -v 없는 형태를 써야 한다.

보조 도구도 두 개 있다. git status --ignored는 무시된 것까지 !! 표시로 보여 주고, git ls-files -i -c --exclude-standard는 규칙에 걸리는데도 여전히 추적 중인 파일만 골라낸다. 이 글의 주제에 정확히 맞는 목록이다.

$ git status --short

$ git status --short --ignored
!! logs/
!! scratch.tmp

# *.log 규칙을 추가했지만 build.log 는 이미 추적 중인 상태
$ git ls-files -i -c --exclude-standard
build.log
  • git check-ignore -v 경로 - 어느 규칙이 이겼는지 한 줄로 답한다. 첫 번째로 칠 명령
  • --no-index를 붙여야 나온다면 원인은 추적 상태다. git rm --cached로 간다
  • git status --ignored - 무시되고 있는 것이 무엇인지 눈으로 확인한다
  • git ls-files -i -c --exclude-standard - 정리할 목록을 통째로 뽑아 준다

빈 디렉터리는 추적되지 않는다

이 주제와 붙어 다니는 질문이 있다. 디렉터리 구조만 만들어 커밋했는데 다른 사람이 받으면 그 디렉터리가 없다는 것이다. 무시 규칙과는 무관하다. Git은 파일만 기록하고 디렉터리라는 개념을 따로 저장하지 않는다. 경로에 포함된 디렉터리 이름이 부수적으로 재현될 뿐이다.

$ mkdir uploads
$ git add uploads
$ git status --short

$ touch uploads/.gitkeep
$ git add uploads
$ git status --short
A  uploads/.gitkeep

빈 디렉터리를 git add하면 오류도 나지 않고 아무 일도 일어나지 않는다. 안에 파일을 하나 넣어야 비로소 스테이징된다. .gitkeep 관행이 여기서 나왔다. Git이 아는 특별한 이름이 아니라 디렉터리를 유지하려고 넣는 빈 파일에 붙은 통용 이름일 뿐이다. README를 넣어도 결과는 같다.

  • 이름은 관습이다. 도구가 특별 취급하지 않으므로 팀에서 하나로 정해 쓰면 된다
  • 업로드 디렉터리처럼 안의 내용은 무시하되 디렉터리는 남기고 싶은 경우가 전형적이다
  • 그 경우 규칙은 uploads/*와 !uploads/.gitkeep 두 줄이다. 앞 절의 이유로 uploads/로 적으면 예외가 살아나지 않는다

저장소 규칙과 개인 취향을 섞지 않는다

.gitignore는 커밋되는 파일이라 저장소를 받는 모든 사람에게 그대로 전달된다. 여기에 무엇을 적느냐는 혼자 정할 문제처럼 보이지만 실제로는 협업 규약에 가깝다. 개인 편집기 설정을 적는 순간, 그 편집기를 쓰지 않는 사람에게도 의미 없는 줄이 배포된다.

기준은 간단하다. 누가 받아도 똑같이 생기는 것은 저장소 규칙에, 사람마다 다른 것은 개인 설정에 적는다. 빌드 산출물이나 의존성 디렉터리는 어느 기계에서도 같은 이름으로 생기므로 저장소 규칙이 맞다. 반면 어떤 편집기를 쓰는지는 사람마다 다르다.

  • 저장소 .gitignore - 빌드 산출물, 의존성 디렉터리, 로그, 실제 비밀 파일의 이름
  • .git/info/exclude - 이 저장소에서만 나에게 필요한 것. 실험용 스크립트, 개인 메모
  • 전역 파일(core.excludesFile) - 편집기 설정, 운영체제 부산물처럼 모든 저장소에서 반복되는 것
  • 세 곳 모두 앞 절의 우선순위를 따른다. 개인 설정은 가장 약해 저장소 규칙을 뒤집을 수 없다

저장소 .gitignore에 개인 항목이 쌓이는 것은 대개 그것을 적을 다른 곳을 몰라서다. .git/info/exclude가 있다는 사실만 알려도 이 파일은 눈에 띄게 깔끔해진다.

처음부터 넣을 목록과 커밋 전 습관

이 글의 문제는 전부 순서에서 나온다. 규칙이 파일보다 늦게 도착해 생기는 일이다. 예방도 순서로 한다. 저장소의 첫 커밋에 .gitignore를 함께 넣는 것이다. 언어와 프레임워크마다 목록이 다르지만 성격은 네 가지로 갈린다.

성격예왜 넣는가빠뜨렸을 때
빌드 산출물dist/, build/, target/, *.o소스에서 언제든 다시 만들어진다커밋마다 거대한 차이가 생겨 리뷰가 어렵다
의존성node_modules/, vendor/, .venv/잠금 파일로 재현되므로 이력에 둘 이유가 없다저장소 용량이 수십 배가 되고 복제가 느려진다
로그와 임시 파일*.log, *.tmp, .cache/실행할 때마다 달라지는 값이다의미 없는 변경이 계속 쌓여 실제 변경을 가린다
자격증명.env, *.pem, *_rsa, secrets.*한 번 들어가면 이력에서 빼기 어렵다키 교체 외에는 해결 방법이 없다

마지막 줄이 가장 비싸다. 앞의 세 가지는 늦게 알아채도 rm --cached 한 번으로 정리되지만, 자격증명은 그것만으로 끝나지 않는다. .env 계열을 첫 커밋 전에 넣어 두는 일이 가장 큰 값을 한다.

습관도 한 가지 곁들일 만하다. git add .는 편하지만 규칙이 아직 없는 새 파일을 전부 담는다. 규칙이 있으면 Git이 막아 주지만, 없으면 조용히 들어간다.

$ printf 'TOKEN=placeholder-not-a-real-token\n' > .env.local
$ echo 'note' > memo.txt
$ git add .
$ git status --short
A  .env.local
A  memo.txt
A  uploads/.gitkeep

# 규칙이 있으면 이렇게 막아 준다
$ git add logs/error.log
The following paths are ignored by one of your .gitignore files:
logs/error.log
hint: Use -f if you really want to add them.
hint: Disable this message with "git config set advice.addIgnoredFile false"

위쪽 git add .는 .env.local을 아무 경고 없이 담았다. 아래쪽은 규칙이 있어서 거부됐고, 정말 넣으려면 -f를 쓰라고 안내한다. 이 대비가 규칙을 미리 넣어 두는 이유다. 그리고 어느 쪽이든 커밋 직전에 git status를 한 번 보는 습관이 마지막 안전망이다. 몇 줄을 읽는 데 드는 시간은 몇 초다.

  • 새 저장소의 첫 커밋에 .gitignore를 포함시킨다. 이 글의 문제 대부분이 사라진다
  • 자격증명 패턴은 프로젝트가 비어 있을 때 넣는다. 나중에 넣으면 늦다
  • git add . 뒤에는 git status --short로 무엇이 담겼는지 본다
  • 거부 메시지가 뜨면 반사적으로 -f를 붙이지 않는다. 막은 이유가 있을 수 있다

한 장 요약

증상별로 어디를 볼지 정리하면 아래와 같다. 순서대로 위에서부터 확인하면 대부분 두 번째 줄 안에서 원인이 잡힌다.

증상확인할 것명령해결

정리

.gitignore는 추적되지 않는 파일만 무시한다. 한 문장이지만 이 글의 대부분이 여기서 나온다. 규칙이 늦게 도착한 파일은 규칙을 읽지도 않고, 그래서 패턴을 아무리 고쳐도 결과가 바뀌지 않는다. 빼내는 명령은 git rm --cached 경로고, 디렉터리는 -r가 필요하며, --cached를 빠뜨리면 디스크의 파일까지 사라진다.

패턴 자체가 문제인 경우도 있다. 선행 슬래시가 위치를 고정하고, 후행 슬래시가 디렉터리로 한정하며, 부모를 통째로 막으면 안쪽 예외가 살아나지 못하고, 같은 단계에서는 마지막 매칭이 이긴다. 규칙이 네 곳에 흩어져 있을 수도 있다. 이 모든 경우에 git check-ignore -v 한 줄이 범인을 지목한다. 추측으로 패턴을 고치는 대신 이 명령을 먼저 친다.

그리고 다시 한 번, git rm --cached는 이후의 커밋에서만 파일을 뺀다. 과거 커밋에는 그대로 남아 git show 한 줄이면 읽힌다. 비밀번호나 키가 들어갔다면 파일을 어떻게 지울지 고민하기 전에 그 값을 폐기하고 새로 발급하는 것이 첫 조치다.

확인하지 못한 것

  • 실험은 Windows 10의 Git Bash와 git 2.48.1.windows.1에서만 돌렸다. 다른 Git 버전에서는 출력 문구가 다를 수 있다. 특히 hint: 로 시작하는 안내는 버전에 따라 바뀌어 온 부분이다
  • 대소문자를 구분하는 파일 시스템에서의 동작 차이는 직접 확인하지 못했다. Windows에서는 재현할 수 없는 항목이다
  • 이력 재작성 도구들의 실제 동작과 부작용은 범위에서 제외했다. 공유 저장소에서 하는 작업이라 검증에 협업 환경이 필요하고, 복구도 별개의 주제다
  • 대형 저장소에서 git rm -r --cached . 가 걸리는 시간은 측정하지 않았다. 실험 저장소의 파일 수가 적어 의미 있는 수치가 나오지 않는다
