打乱测试顺序才会暴露的东西 - 揪出隐藏依赖的方法

通过不等于「对」，只等于「在这个顺序下对」

2026-07-31 开发/基础设施

从症状说起：CI 上红，我这儿绿

周一早上，CI 是红的。打开日志一看，上周五还好好的一个测试挂了。你把它的名字复制下来在本地跑。过了。再跑一次，还是过。代码翻来覆去看也挑不出毛病。于是你点了重跑按钮，这回绿了，事情就这么过去了。

大多数团队会给这种情况贴上「偶发失败测试」的标签然后走开。可这个标签对成因没有任何解释。本文只讲其中一种成因：执行顺序。

顺序依赖和其他不稳定因素性质不同。因为时间或并发而抖动的东西，在相同条件下结果也可能不一样，而顺序依赖是完全确定的。用同样的顺序跑，永远得到同样的结果。只不过顺序什么时候变了，没人留意过而已。

所以本文的论点不是「请把测试隔离好」。那是结论，不是诊断。我要说的是这句话。

只要测试之间有状态残留，顺序就成了输入。这时通过不再意味着「这是对的」，而是「在这个顺序下是对的」。而这个输入从来没有人验证过。

这样一看，打乱顺序这件事的性质也变了。它不是洁癖也不是个人偏好，而是在拓宽输入的范围。只跑一种顺序，等于只给函数喂了一个值就宣布函数是对的。

运行环境。下面所有输出都是在 Windows 10 Pro (10.0.19045) 上真实跑出来的。工具是 Python 3.13.3 (win32, MSC v.1943 64bit) 的标准库 unittest 和 Node.js v22.16.0 (win32 x64) 的 node:test，shell 是 GNU bash 5.2.37 (MSYS2)。

因为没有而跑不了的东西。这个环境里没有装 pytest（No module named pytest）。Python 3.11 上也一样，nose2 同样没有。所以 pytest 系的顺序行为及其相关插件我没能直接测量。本文提到 pytest 的地方都是以文档为依据，并且已单独标明不是实测。

所有脚本都存成文件后再执行。下面的示例和路径全都改写到了 /tmp/order-demo 这样的占位位置，是虚构代码。

1. 出问题的那四个测试

先看实验对象。形态极其常见：一个模块持有全局字典，测试们共用它。

# /tmp/order-demo/store.py
CONNECTIONS = {}          # 模块级全局量，每个进程只导入一次

# /tmp/order-demo/tests_shared.py
import unittest
import store

class SessionTests(unittest.TestCase):
    # 故意按 d, b, a, c 的顺序定义
    def test_d_close_all(self):
        store.CONNECTIONS.clear()
        self.assertEqual(store.CONNECTIONS, {})

    def test_b_query_uses_connection(self):
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_a_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"
        self.assertEqual(len(store.CONNECTIONS), 1)

    def test_c_registry_has_one_entry(self):
        self.assertEqual(len(store.CONNECTIONS), 1)

这四个单独读都很自然：开连接、查询、数条目、关掉。哪里也没写着「前面的测试会把连接开好」。可实际上就是这么安排的。

2.1 如果顺序是输入，输入空间有多大

只看两种还能推给「运气不好」。所以我把 24 种排列全部用新进程跑了一遍。

    d a b c
    d a c b

RED   (20):
    a b d c   a c d b   a d b c   a d c b   b a c d   b a d c

通过率百分之十七。还有一个决定性的事实：这个工具的默认顺序 a b c d 正是四种绿色排列里的第一种。开发者每天看到的都是绿色，可能已经在「顺序稍一晃动就会变红」的状态下过了好几个月。

  • 看这四种绿色排列能看出共同点：a 在 b 和 c 之前，而 d 在 b、c 之后
  • 这个约束在代码里任何地方都没写。只是名字的字母顺序碰巧满足了它
  • 只要有人把 test_a_open_connection 改名成 test_setup_connection，立刻变红。不是重构弄坏了测试，而是本来就藏着的依赖露了出来
  • 哪怕只加一个测试，位置也会挪。新测试毫无过错，却让别的测试变红了

3. 默认执行顺序因工具而异

这里得先纠正一个最常见的误解：「测试是从上往下依次跑的」。这句话在有的工具上对，在有的工具上错。所以不要一概而论，要在自己用的工具上亲手测。下面是在这个环境里测到的值。

3.1 在 Python 3.13.3 的 unittest 上测到的值

是名字顺序，不是定义顺序。方法和类都一样。文档里也写着：执行顺序由测试方法名按字符串的内置顺序排序决定。

3.2 在 Node.js v22.16.0 的 node:test 上测到的值

接着把完全相同的逻辑搬到另一个工具上。共享状态、断言内容、定义顺序都原样照搬。

// /tmp/order-demo/order_probe.test.mjs
import test from 'node:test';

test('test_a_open_connection',        () => { CONNECTIONS.set('main', 'pg://demo');
                                              assert.strictEqual(CONNECTIONS.size, 1); });
test('test_c_registry_has_one_entry', () => { assert.strictEqual(CONNECTIONS.size, 1); });

不要一概而论。上面的值是在这个工具、这个版本、这个环境下测的。同一个工具换个版本就可能不同，装上一个跟顺序有关的插件立刻就变。pytest 那一行因为没装并没有真正跑过，只是依据文档写的，所以别照单全收，请在各自的环境里自己测。测法很简单：写几个定义顺序故意跟名字顺序不一致的测试，看它实际按哪一种跑就行了。

4. 状态残留的五个位置

顺序要成为输入，就必须有东西在测试之间活下来。我把这些位置分成五类，各自跑了一遍。每次运行都从新进程开始，fwd 是名字顺序，rev 是它的逆序。

4.1 模块级全局变量

case 1  module-level global       order=fwd
  run : a_open_connection -> b_query_uses_connection -> c_close_all
  ==> ALL PASS   (3/3 passed)

case 1  module-level global       order=rev
  run : c_close_all -> b_query_uses_connection -> a_open_connection
  ==> 1 FAILED   (2/3 passed)
      red: b_query_uses_connection
      KeyError: 'main'

最常见的位置。模块每个进程只导入一次，所以里面的变量在整个测试生命周期内一直活着。把文件拆开也没用，只要导入同一个模块，拿到的就是同一个对象。

4.2 类属性

class FeatureFlags:
    enabled = set()          # 类属性：所有实例共用这一个集合

    def on(self, name):
        self.enabled.add(name)     # 改的是类上的集合，不是实例的

case 2  class attribute           order=fwd
  run : a_enable_beta -> b_fresh_object_has_no_flags
  ==> 1 FAILED   (1/2 passed)
      red: b_fresh_object_has_no_flags
      AssertionError: Items in the first set but not the second: 'beta'

case 2  class attribute           order=rev
  run : b_fresh_object_has_no_flags -> a_enable_beta
  ==> ALL PASS   (2/2 passed)

这里方向反了过来：默认顺序挂，逆序反而过。self.enabled.add(...) 看起来像在建实例属性，实际上它会顺着找到类上的那个集合再往里加。所以用 FeatureFlags() 新建的对象里也已经带着之前的值。

4.3 缓存与记忆化

USERS = {}

@functools.lru_cache(maxsize=None)
def find_user(uid):
    return USERS.get(uid)

case 3  cache / memoization       order=fwd
  run : a_created_user_is_found -> b_lookup_again -> c_unknown_user_is_none
  ==> ALL PASS   (3/3 passed)

case 3  cache / memoization       order=rev
  run : c_unknown_user_is_none -> b_lookup_again -> a_created_user_is_found
  ==> 2 FAILED   (1/3 passed)
      red: b_lookup_again              AssertionError: None != 'kim'
      red: a_created_user_is_found     AssertionError: None != 'kim'

这个例子是五个里最阴的。再看一遍 test_a_created_user_is_found 的内容。

def test_a_created_user_is_found(self):
    USERS[7] = "kim"                          # 正确地写入数据
    self.assertEqual(find_user(7), "kim")     # 正确地查询  -> 结果还是失败

这个测试没有一丝一毫的问题。可逆序下它就是红的。因为先跑的 test_b_lookup_again 在数据还不存在时调用了 find_user(7)，那个 None 被烙进了缓存。缓存对「没有」这个答案记得一样牢。

  • 挂了缓存的函数实质上就是全局变量，只不过藏在看不见的地方
  • 就算在夹具里还原了配置值，不清缓存的话旧答案照样原封不动地冒出来
  • 缓存否定结果（找不到、没权限、是空的）尤其危险。反而是后面把状况整理正确的那个测试会挂
  • 不只是自家代码的缓存。导入的库内部的缓存、编译好的正则缓存、连接池，都在同一个位置

4.4 临时文件与目录

case 4  temp file / directory residue  order=fwd
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty
      AssertionError: Lists differ: ['report.csv'] != []

case 4  temp file / directory residue  order=rev
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> ALL PASS   (2/2 passed)

到这里为止和前面的例子一样。可这个位置有一个另外四个都没有的性质。把清理去掉、连着跑两次就露出来了。

$ python -c "清除残留物"
residue cleared

--- run 1: 去掉清理，按 fwd 顺序运行 ---
  run : a_export_writes_report -> b_export_dir_starts_empty
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

--- run 2: 全新进程，rev 顺序（刚才还是 ALL PASS） ---
  run : b_export_dir_starts_empty -> a_export_writes_report
  ==> 1 FAILED   (1/2 passed)
      red: b_export_dir_starts_empty

刚才还是 ALL PASS 的逆序，这回红了，而且是在全新进程里。留在文件系统上的状态会越过进程边界。换句话说，这时坐在「前一个测试」这个位子上的，是上一整轮运行。

  • 所以这一类会表现为「新克隆的仓库里能跑，我的工作目录里就不行」
  • 如果 CI 每次都用干净的容器，就会出现镜像般相反的情况：只在 CI 上绿，本地反而红
  • 一旦用了写死的路径，并行运行时也会互相踩
  • 数据库、缓存服务器、消息队列也是同样的性质。重启进程也清不掉

4.5 没有复原的猴子补丁

def test_a_invoice_with_frozen_clock(self):
    clock.now = lambda: 1700000000.0      # 换掉之后不再还原
    ...

case 5  monkeypatch that is never undone  order=fwd
  run : a_invoice_with_frozen_clock -> b_invoice_uses_real_clock
  ==> 1 FAILED   (1/2 passed)
      red: b_invoice_uses_real_clock
      AssertionError: 85445231.48900342 not less than 5.0 : clock is off by 85445231 seconds

case 5  monkeypatch that is never undone  order=rev
  run : b_invoice_uses_real_clock -> a_invoice_with_frozen_clock
  ==> ALL PASS   (2/2 passed)

误差是 8544 万秒，大约两年八个月。冻结时钟本身是完全正当的技巧，问题在于没有把它放回去。除了时钟，随机数种子、环境变量、替换掉的网络调用、日志配置，全都在同一个位置。

5. 按成因分类的判别表

把上面五类整理成实战中能直接用的形式。如果本文只带走一样东西，就带走这张表。

类型残留在哪里典型症状怎么确认怎么还原
模块级全局量被导入的模块对象后面读到前面填进去的值才通过在测试前后打印模块变量并比对在 setUp 里重置，并登记清理
类属性类对象本身新建的实例里已经带着旧值确认它是实例属性还是类属性把可变默认值移进构造函数
缓存与记忆化挂在函数上的缓存先跑的一方定下答案，其余对不上打印缓存命中统计在 setUp 里清缓存
临时文件与目录文件系统换新进程也照样复现比对运行前后的目录列表每个测试新建临时目录，自动删除
猴子补丁未复原被打补丁的模块属性时钟、随机数、网络返回莫名其妙的值把当前属性和原始值做比较先登记复原，再打补丁

用这张表时有个方向感很有帮助。全局量、缓存、猴子补丁大体上是前面污染后面；类属性因为会累积，往往在默认顺序下更早挂；临时文件则是上一次运行污染这一次。

6. 谁污染的，谁挂掉的

诊断中最常犯的错误就是把变红的测试当成真凶。为了能亲眼看清，我在每个测试前后都打印了共享状态。

order=fwd
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  b_query_uses_connection    state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  c_registry_has_one_entry   state {'main': 'pg://demo'}  -> {'main': 'pg://demo'}    --
  d_close_all                state {'main': 'pg://demo'}  -> {}                     CHANGED
  red tests : (none)

order=rev
  d_close_all                state {}                     -> {}                       --
  c_registry_has_one_entry   state {}                     -> {}                       --
  b_query_uses_connection    state {}                     -> {}                       --
  a_open_connection          state {}                     -> {'main': 'pg://demo'}  CHANGED
  red tests : b_query_uses_connection, c_registry_has_one_entry
  who mutated shared state : a_open_connection, d_close_all

最后两行要叠在一起读。变红的 b 和 c 一个字都没改过共享状态（-- 标记）。而改了状态的 a 和 d 都是绿的。

  • 失败的位置和成因的位置完全分开。所以失败日志里的调用栈根本指不到真凶
  • 逆序下真正的原因是 d_close_all 在最前面把字典清空了。可 d 自己的断言通过了，所以它没留下任何信号
  • 正是这个结构催生了给受害者加防御代码的做法。红是没了，污染源原封不动
  • 该修的地方是改了状态却没放回去的那一侧

7. 用二分查找锁定真凶

四个测试可以用眼睛看，几百个就看不过来了，所以需要一套流程：把放在受害者前面的测试集合逐次砍半。

我做了一个 17 个测试的实验例子。大部分是平平无奇的算术检查，其中一个悄悄改了共享配置。最后那个测试检查含税合计。

CONFIG = {"tax_rate": 0.10, "currency": "KRW"}

    def test_09_tax_exempt_customer(self):
        # 真凶：为了做免税检查改了税率，之后没放回去
        CONFIG["tax_rate"] = 0.0
        self.assertEqual(CONFIG["tax_rate"], 0.0)

    def test_zz_total_includes_tax(self):
        # 受害者：单独放着完全正确
        self.assertAlmostEqual(10000 * (1 + CONFIG["tax_rate"]), 11000.0)

现在假装不知道谁是真凶，照流程收敛。每次尝试都是新进程。

suite size      : 17 tests (16 candidates + 1 victim)
victim          : zz_total_includes_tax

step 0 -- 先钉住两端
  trial 1   before=16 [01_amount_is_positive..16_due_date_offset]        -> RED
  trial 2   before=0  [nothing]                                          -> GREEN

step 1 -- 朝着保持红色的那一侧逐次砍半
  trial 3   before=8  [01_amount_is_positive..08_empty_cart_total]       -> GREEN
  trial 4   before=8  [09_tax_exempt_customer..16_due_date_offset]       -> RED
  trial 5   before=4  [09_tax_exempt_customer..12_zero_quantity_skipped] -> RED
  trial 6   before=2  [09_tax_exempt_customer..10_max_line_items]        -> RED
  trial 7   before=1  [09_tax_exempt_customer..09_tax_exempt_customer]   -> RED

minimal reproducing pair : 09_tax_exempt_customer  then  zz_total_includes_tax
subprocess runs used     : 7
brute force would need   : 16 (one run per candidate)

七次就收敛了。一个一个试的穷举法要十六次，而且候选越多差距越大。候选一千个的话穷举要一千次，这个流程二十次左右就够了。

  • 别跳过第 0 步。「整个前置集合 + 受害者 = 红」和「受害者单独 = 绿」两条都成立才算顺序依赖。如果受害者单独也是红的，那就只是个坏掉的测试
  • 每次尝试都用新进程。在同一进程里连着跑，各次尝试会互相污染，判定会翻过来
  • 如果两半单独都不红，说明真凶不止一个，也就是要两个测试合起来才凑出条件。这时改用逐半剔除的方式收敛
  • 把找到的最小复现对原样留成回归测试。做一个专门按这个顺序跑这两个的测试，同样的事故就再也进不来了
  • 要修的是真凶那一侧。给受害者加防御代码只是急救

8. 隔离运行制造的错觉

把「我这儿是好的」的结构原样复现一下。还用刚才那个 17 个测试的例子，只跑受害者。

zz_total_includes_tax  单独运行             GREEN
全部 17 个（名字顺序）                     RED

就这么简单。开发者看到失败日志、复制那个测试名、在本地一跑，必然是绿的。于是结论就漏向了「环境问题」，然后靠重跑按钮糊过去。

可是拿前面那四个的例子做同样的事，结果却不一样。

a_open_connection                PASS
b_query_uses_connection          FAIL
c_registry_has_one_entry         FAIL
d_close_all                      PASS

这里 b 和 c 单独跑也失败。这个差别在诊断上极其重要。顺序依赖分两种。

类别单独运行整套运行性质发现难度
依赖前置型失败某些顺序下通过本来就不是自足的测试，它把前面的测试当成了准备步骤低。单独跑一下立刻暴露
污染受害型通过某些顺序下失败测试本身是对的，只是踩到了前面测试留下的状态高。「我这儿是好的」就是从这儿来的

实战中吃掉时间的是下面那一行。单独运行能通过并不是平安无事的证据，反而是「你碰上了污染受害型」的症状。所以隔离运行只能是诊断的起点，永远不能当成结论。

9. 随机顺序与固定种子

既然顺序是输入，答案就很明确：多喂几个输入。但不能就这么把随机打开，因为复现不了的红色是没法诊断的。固定种子能同时拿到随机性和可复现性。

seeds tried : 1..40   (order = random.Random(seed).shuffle)
green seeds : 10  -> [1, 3, 9, 11, 12, 13, 17, 26, 27, 33]
red   seeds : 30  -> [2, 4, 5, 6, 7, 8, 10, 14, 15, 16, 18, 19] ...

四十个种子里有三十个是红的。现在挑一个钉住。本文使用的固定种子是 20260731。只要填同一个种子，谁都能得到同样的顺序。

$ python ci_shuffle.py 20260731
==============================================================
TEST ORDER SEED : 20260731      replay with: ci_shuffle.py 20260731
==============================================================
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

$ python ci_shuffle.py 20260731          # 同一个种子再跑一次
order : c -> d -> b -> a
FAILED with seed 20260731 -- rerun that seed to get the same order
   red: test_c_registry_has_one_entry
   red: test_b_query_uses_connection

两次运行的顺序和结果完全一致。这是让随机顺序在实战中可用的唯一条件。

  • 把种子和重跑命令打在失败日志的最上方。拿到日志的人应该能只复制那一行就原样复现
  • 种子要从随机数取，而不是从时钟取。基于时钟的话，同一分钟内跑的两次会得到同样的顺序，搜索范围就窄了
  • Python 标准库就够用。拿到名字列表，用固定种子打乱，再按那个顺序组装测试套件即可
  • pytest 生态里有打乱顺序的插件，也一并提供了关掉注册的选项。不过这个环境里没有 pytest，我没能直接验证

10. 还原状态的规则 - 夹具设计

接下来是修的一侧。我把前面那四个测试的断言原封不动，只改了夹具。

class SessionTestsFixed(unittest.TestCase):
    def setUp(self):
        # 1. 不用继承来的状态，而是到达一个已知状态
        store.CONNECTIONS.clear()
        # 2. 先登记还原。测试中途抛异常也照样会跑
        self.addCleanup(store.CONNECTIONS.clear)

    def given_open_connection(self):
        store.CONNECTIONS["main"] = "pg://demo"      # 需要的前提自己搭

    def test_b_query_uses_connection(self):
        self.given_open_connection()
        self.assertEqual(store.CONNECTIONS["main"], "pg://demo")

    def test_c_registry_has_one_entry(self):
        self.given_open_connection()
        self.assertEqual(len(store.CONNECTIONS), 1)

只改了两件事：进来时先重置状态，需要的前提自己搭。看结果。

10.1 八条规则

  • 不要把准备工作外包。需要的前提由这个测试自己搭。光这一条就能消掉大部分顺序依赖
  • setUp 是用来「到达一个已知状态」的，不是用来查看你继承到了什么
  • 还原要登记在打补丁之前。测试主体被异常打断时，复原也必须照样执行
  • 后登记的清理函数先执行。资源按获取的相反顺序释放，依赖关系自然就守住了
  • 别把清理放在测试主体的末尾。断言一失败就走不到那一行。这就是「坏了一个接着坏十个」的真相
  • 缓存也是全局量。既然还原了配置，就把缓存也清掉
  • 临时文件每个测试新建、自行删除。不共享写死的路径
  • 类级夹具不是默认选项。只在速度实在逼人时用，而且保持只读

10.2 可以共享的与不能共享的

可以共享的不能共享的
不可变常量、冻结的配置值字典、列表、集合等可变容器
纯函数挂了缓存的函数
只读的夹具数据会被写入的数据库和文件
每个测试新建的临时目录固定路径的工作目录
测试类里的辅助方法以类属性形式存放的可变默认值
预计算结果的副本对该值本身的引用

判定标准可以压缩成一句话：测试会往里面写吗。会写就别共享。只读的话共享没问题，但那个「只读」是不是真的只读，得确认。给列表排序是写，查字典时顺手填个默认值也是写。

11. 该往 CI 里装什么

把前面这些运行搬进流水线，就是下面这样。

  • 主线保持固定顺序。每次提交顺序都在晃，就分不清红色的原因是代码还是顺序
  • 把随机顺序拆成单独任务并打印种子。这个任务红了表示「存在顺序依赖」，主线红了表示「代码错了」，信号不会混在一起
  • 在夜间任务里加一条逆序运行。比随机化便宜，而且像本文看到的那样探测力相当强。因为是确定性的，复现也是自动的
  • 把新找到的最小复现对固化成专门的测试。留下一个按那个顺序跑那两个的测试，同样的事故就再也进不来
  • 加一个运行结束后检查临时目录残留物的步骤。光这一条就能抓住 4.4 那一类的大部分
  • 开并行之前先消掉顺序依赖。并行不仅把顺序摇得更厉害，还叠加了并发访问。带着顺序问题走向并行，成因就变成两层了

推荐的推进顺序。突然打开顺序随机化，通常会砸下一大堆红色，最后以团队把这个任务关掉收场。建议从一条逆序运行开始。它是确定性的，容易复现，把冒出来的红一个个收敛成最小复现对再逐个修掉就行。等这些都清完了，再打开随机化。

12. 检查清单

  • 新加的测试单独跑过了
  • 把顺序反过来跑了一次
  • 用固定种子至少跑过一次随机顺序
  • 运行结束后临时目录里没有残留文件
  • 每个猴子补丁都登记了复原
  • 用到缓存的代码在夹具里有清缓存
  • 类属性上没有可变默认值
  • 没有测试依赖别的测试的名字或次序
  • 清理写在夹具里，而不是主体末尾
  • CI 日志里会打印顺序种子

12.1 不要做的事

  • 一上来就给挂掉的测试加防御代码 - 修了受害者，放跑了真凶
  • 给测试名编号把顺序钉死 - 那是把依赖藏起来而不是去掉，而且工具要是不按名字跑，这招连藏都藏不住
  • 靠重跑把红色糊过去 - 变绿只是因为顺序碰巧变了
  • 不带种子就打开随机顺序 - 复现不了就诊断不了
  • 停在「我这儿是好的」 - 如第 8 节所示，单独通过是症状而不是证据
  • 为了速度把共享夹具当成默认 - 不可信的测试比慢的测试贵得多
  • 顺序依赖还带着就打开并行执行

13. 小结

把本文实际跑出来验证过的东西再汇总一遍。

  • 四个共享状态的测试，24 种排列里绿的有 4 种。通过率百分之十七，而且工具的默认顺序正好是这 4 种之一
  • 默认执行顺序因工具而异。测下来 unittest 按名字，node:test 按定义顺序。逻辑相同的测试在一个上全过，在另一个上挂了
  • 状态残留的位置有五处，只有临时文件会越过进程边界
  • 变红的测试一个字都没改过共享状态。真凶反而是绿的
  • 从 16 个候选里七次就收敛到最小复现对
  • 受害者单独跑是通过的。这就是「我这儿是好的」的真面目
  • 钉住种子 20260731 后，顺序和失败都完全复现
  • 断言不动、只改夹具，结果24/24 全部通过

结论跟开头立的论点一致。顺序依赖不是「没做好隔离」这种道德层面的缺陷，而是还存在一个没被验证过的输入这个事实。那个输入的名字叫顺序。

所以最后的问题变了。不是「这个测试过不过」，而是「它在哪些顺序下过」。反过来跑一次只要几秒钟，而这几秒钟能把周一早上的红色挪到此时此地。

# 测试顺序依赖检查清单

只要测试之间有状态残留，**顺序就成了输入**。
这时通过不再意味着「这是对的」，而是「在这个顺序下是对的」。

---

## 0. 三十秒判定

| 问题 | 是 | 否 |
|---|---|---|
| 单独运行这个测试能通过吗 | **确定是顺序依赖**（见第1节） | 自身缺陷，或依赖前置测试 |
| 把顺序反过来会有别的测试挂掉吗 | **确定是顺序依赖** | 另有原因 |
| 挂掉的测试自己会改共享状态吗 | 它也是嫌疑人 | **真凶在前面** |
| 换一个全新进程还能复现吗 | 状态在**进程之外**（文件、数据库） | 状态在进程内存里 |

要点只有一句：**挂掉的测试通常是受害者，不是真凶。**

---

## 1. 按成因分类的判别表

| 类型 | 残留在哪里 | 典型症状 | 怎么确认 | 怎么还原 |
|---|---|---|---|---|
| 模块级全局变量 | 被导入的模块对象 | 后面的测试读到前面填进去的值才通过 | 在每个测试前后打印模块变量并比对 | 在 setUp 里重置，用 addCleanup 登记还原 |
| 类属性 | 类对象本身 | 新建的实例里已经带着旧值 | 确认它是实例属性还是类属性 | 把可变默认值移进构造函数 |
| 缓存与记忆化 | 挂在函数上的缓存 | **先跑的测试定下答案**，其余的对不上 | 打印缓存统计或命中次数 | 在 setUp 里清缓存，把缓存当成普通全局量 |
| 临时文件与目录 | 文件系统 | **换全新进程也照样复现** | 比对运行前后的目录列表 | 每个测试一个临时目录，自动删除 |
| 未复原的猴子补丁 | 被打补丁的模块属性 | 时钟、随机数、网络返回莫名其妙的值 | 把当前属性和原始值做比较 | **先登记复原，再打补丁** |

### 各类型的方向感

- 全局量、缓存、猴子补丁：通常是**前面污染后面**
- 类属性：因为会累积，**在默认顺序下往往更早挂**
- 临时文件：**上一次运行污染这一次**，会越过进程边界
- 缓存里一旦存进「不存在」这种否定结果，后面正确写入数据的那个测试反而会红

---

## 2. 找出最小复现对

目标是找出「A 之后跑 B 就坏」里的那个 A。

### 步骤

1. **先钉住两端**
   - 确认整个前置集合加受害者是红的
   - 确认受害者单独跑是绿的
   - 两条都成立才算顺序依赖
2. **把前置集合砍一半**
   - 跑前一半加受害者
   - 红就保留前一半，绿就保留后一半
3. **重复第2步，直到只剩一个**
4. 剩下的那个就是**真凶**，它和受害者构成**最小复现对**

### 规则

- **每次尝试都用新进程跑**，否则各次尝试之间会互相污染
- 如果两半单独都不红，说明**牵涉的测试不止一个**，改用逐半剔除的方式收敛
- 候选 N 个时，大约 **2 乘以 log2(N) 次**就能收敛。十六个候选约七次，而穷举要十六次

### 找到之后

- 把最小复现对**原样留成回归测试**
- 修真凶那一侧。给受害者加防御代码只是急救，不是治疗

---

## 3. 夹具规则

1. **不要把准备工作外包。** 需要的前提由这个测试自己搭建
2. **setUp 的意思是「到达一个已知状态」**，而不是照单全收前面留下的状态
3. **复原要登记在打补丁之前**，这样测试中途抛异常时复原照样会跑
4. **后登记的清理函数先执行。** 资源按获取的相反顺序释放
5. **类级夹具不是默认选项。** 只在速度实在逼人时使用，并且保持只读
6. **缓存也是全局量。** 既然还原了配置，就把缓存也清掉
7. **临时文件每个测试新建、自行删除。** 不共享写死的路径
8. **别把清理放在测试体的末尾。** 一旦失败就走不到那一行

---

## 4. 可以共享的 / 绝不能共享的

| 可以共享的 | 绝不能共享的 |
|---|---|
| 不可变常量、冻结的配置值 | 字典、列表、集合等**可变**容器 |
| 纯函数 | 挂了缓存的函数 |
| 只读的夹具数据 | 会被写入的数据库和文件 |
| 每个测试新建的临时目录 | 固定路径的工作目录 |
| 测试类里的辅助方法 | 以类属性形式存放的可变默认值 |
| 预计算结果的**副本** | 对该值**本身**的引用 |

判定标准只有一条：**测试会往里面写吗。** 会写就别共享。

---

## 5. 该往 CI 里装什么

- **打乱顺序，但要把种子打印出来。** 没有种子就复现不了红色构建
- 在失败日志最上方同时打出**种子和重跑命令**
- 在夜间任务里加一条**逆序运行**。这是最便宜也最可靠的探测手段
- 主流水线保持**固定顺序**，把随机化拆成单独任务，这样红了就能立刻分清是代码还是顺序的问题
- 每个新发现的最小复现对都**固化成专门的测试**
- 开并行之前先消掉顺序依赖。并行只会把顺序摇得更厉害

---

## 6. 检查清单

- [ ] 新加的测试**单独**跑过了
- [ ] 把顺序**反过来**跑了一次
- [ ] 用**固定种子**至少跑过一次随机顺序
- [ ] 运行结束后临时目录里**没有残留文件**
- [ ] 每个猴子补丁都**登记了复原**
- [ ] 用到缓存的代码在夹具里有**清缓存**
- [ ] 类属性上没有**可变默认值**
- [ ] 没有测试依赖**别的测试的名字或次序**
- [ ] 清理写在**夹具里，而不是测试体末尾**
- [ ] CI 日志里会打印**顺序种子**

---

## 7. 不要做的事

- 一上来就**给挂掉的测试加防御代码** — 修了受害者，放跑了真凶
- **给测试名编号把顺序钉死** — 那是把依赖藏起来，不是去掉
- **靠重跑把红色糊过去** — 变绿只是因为顺序碰巧变了
- **不带种子就打开随机顺序** — 复现不了就诊断不了
- 停在**「我这儿是好的」** — 单独跑能过是症状，不是证据
- 为了速度把共享夹具**当成默认** — 不可信的测试比慢的测试贵得多
- 顺序依赖还没修就**打开并行执行**
