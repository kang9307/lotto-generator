找出正占着文件的进程 - 删了却不释放空间时

rm 删掉的只是名字。在 Linux 与 Windows 两边把仍在占着的那一方揪出来的顺序

2026-09-02 开发/基础设施

最常见的经过是这样的。磁盘满了的告警来了，找到一个大日志用 rm 删掉，ls 里已经看不见它了，可是 df 一位数都没动。等上几分钟还是一样，于是接着去找别的可删的东西。

到这一步方向其实已经偏了。问题不是可删的东西不够，而是已经删掉的东西还活着。这篇文章只讲一件事，就是怎么把占着它的那一方锁定出来。至于这个症状为什么会出现的四类原因分类，在 磁盘没满却报 No space left on device 那边，本文接的是其中一条。

本文出现的命令里，结束进程和截断文件描述符这两件事无法撤销。相应小节都单独加了危险提示，在生产机器上先把那一段读完再动手为好。不要把只做确认的命令和会改变状态的命令混着用，这几乎就是这项工作的全部纪律。

计数器有两个 - 名字的数量与引用的数量

整个现象都从一句话里出来。rm 不是删除数据的命令。rm 调用的系统调用是 unlink，它做的是把目录里写着的一个名字摘掉。数据在 inode 里而不在名字里，inode 不会因为名字没了就跟着消失。

POSIX 规范把这个行为钉得没有误读余地，链接会在 unlink 返回之前被移除，但文件内容的删除要推迟到该文件的所有引用都关闭之后。也就是说一个文件身上挂着两个性质不同的计数器，两个都归零，块才会回来。

计数器数的是什么什么让它归零在哪里能看到
链接数指向这个 inode 的目录项数量rm、unlink、mv 覆盖stat -c %h、ls -l 的第二列
打开引用打开着这个 inode 的描述符与映射数量进程结束、close()、日志重开信号lsof、fuser、/proc/<pid>/fd
归还块的条件两者同时为 0 的时刻最后一个引用关闭的瞬间，内核一次性完成df 的可用量呈台阶式跳升
观测工具的视野du 走名字，df 数块没有名字，du 就看不见两者之间的差额就是被咬住的容量

这个行为本身不是缺陷而是保护机制。一个进程正在读的时候另一个进程把文件删了，读的那一方要是就此崩掉那才叫麻烦。问题在于这个保护机制会在运行中悄无声息地生效，不报错，不留日志，只是空间不回来而已。

  • 没能跑的 — lsof 与 fuser（这个环境里没装），一切与容器和命名空间相关的内容，还有 NFS 挂载
  • 没有编造的 — 没能跑的命令，本文里一行输出都没有。只写了命令形式和读法，依据是各工具的手册

  • 块大小报告为 4,096 字节。下文任何可用块数乘以 4,096 就是字节数

症状 - df 与 du 对不上

诊断的起点是两个工具给出不同的答案。du 走目录、数有名字的文件，名字没了的文件在它的视野之外。df 读的是文件系统的块记账，所以把被咬住的空间仍算作已用。于是两者拉开，拉开的宽度就是被咬住的容量。

造一个 200MiB 的文件，用 tail -f 咬着再删掉，每一步原样打印 df -h。

--- rm 之前 ---
du -sh . = 200M
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- rm 之后 ---
du -sh . = 0
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  601G  331G  65% /tmp

--- 结束持有进程之后 ---
  Filesystem   Size  Used Avail Use% Mounted on
  /tmp/demo    931G  600G  332G  65% /tmp

把三段并排读，顺序就很清楚了。rm 只把 du 从 200M 变成了 0，df 一位数都没动。df 从 601G/331G 变成 600G/332G，是在结束进程之后发生的。把空间还回来的不是 rm 而是 kill。

  • 在现场这个症状通常先在曲线图上露头。清理跑完了但磁盘用量的线没有台阶式下落而是平的，那多半就是这个原因
  • 拿 du -sh / 的合计跟 df 的 Used 比一比，是最便宜的一次判别。差得大就说明存在没有名字的文件
  • 不过这两个值本来也不会完全一致。保留块、日志区、被挂载遮住的目录都会让几个百分点的差异属于正常。信号是差距拉到几十 GiB 这个量级的时候
  • 有一个坑值得点名。用非 root 账号跑 du，读不了的目录会被静静跳过，这样产生的差异跟本文这个现象无关

名字没了，inode 还在

上一节是症状，这一节是把原理直接看在眼里。造一个 512MiB 的文件，用 tail -f 咬住，删掉之后再通过文件描述符去看同一个 inode。

[1] 刚创建
    name=app.log inode=4503599629412470 links=1 size=536870912 blocks=524288
    free=86810586   du -sh . = 512M

[2] tail -f (pid=1442) 打开着它

[3] rm 之后 - 名字没了
    ls -A: []
    du -sh . = 0    free=86811452

[4] 但通过 fd 看，inode 还活着
    /proc/1442/fd/3  inode=4503599629412470 links=0 size=536870912 blocks=524288
    readlink        /tmp/demo/app.log (deleted)

[5] 用咬住的 fd 依然读得到
    $ head -c 16 /proc/1442/fd/3 | od -An -tx1
      00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

[6] kill 之后 free=86939254

读的顺序是这样。inode 号在 [1] 和 [4] 里是同一个，删掉之后仍是同一个对象。变的只有 links 一项，从 1 变成 0。而 size 与 blocks 还是 536870912 和 524288，意思是名字没了但数据一个字节都没归还。

可用块也在说同一件事。rm 前后从 86810586 变成 86811452，只动了 866 块。乘以 4,096 大约 3.4MiB，这是同一台机器上别的活带来的噪声。512MiB 是 131,072 块，其中什么都没回来。然后在 kill 之后，从 86811452 到 86939254，127,802 块一次性回来了。

  • links=0 而 size 很大，这就是这种情形的指纹。任何别的状态都不会给出这个组合
  • 内核附上的 (deleted) 尾巴是一个标记，不是路径字符串的一部分。把那串字符原样交给 cat，得到的是文件不存在
  • 正如 [5] 所示，占着的那一方读写毫无障碍。所以应用程序根本不会把这种情形报成错误
  • 回收是一次完成的，这点也值得记住。不是慢慢回来然后停住，而是在最后一个引用关闭的那一瞬间全部到位

找法一 - 直接扫 /proc

生产机器上没有 lsof 的情况比想象中多。最小化镜像里、容器里、内网隔离的服务器上，装一个新工具本身就要走流程。可是内核已经把答案摆出来了，所以没工具也行。每个进程的 /proc/<pid>/fd 是一串指向它所打开文件的符号链接，目标被删掉时，末尾会附上 (deleted)。

# 只看某一个进程
$ ls -l /proc/1442/fd | grep -i deleted
lrwx------ 3 -> /tmp/demo/app.log (deleted)

# 全量扫描 - 只用 shell
$ for p in /proc/[0-9]*; do
    pid=${p##*/}
    for fd in "$p"/fd/*; do
      tgt=$(readlink "$fd" 2>/dev/null) || continue
      case "$tgt" in *"(deleted)") echo "pid=$pid fd=${fd##*/} -> $tgt";; esac
    done
  done

pid=318  fd=3  -> /tmp/demo/app.log (deleted)
pid=319  fd=3  -> /tmp/demo/app.log (deleted)

# 想连被咬住的大小一起看
$ stat -L -c '%i %h %s %n' /proc/318/fd/3
16607023627971255 0 268435456 /proc/318/fd/3

这个办法的价值不只在于不需要额外安装。加上 stat -L 就能当场看到被咬住的容量，候选有好几个时便可以按大小排序，知道先处理哪一个空间才真的会回来。它的局限同样清楚。

  • 别的用户的进程没有权限就看不到。上面的遍历会静静跳过那些行，所以结果为空并不等于不存在。能用 sudo 就用
  • 只看 fd 会漏掉内存映射。文件 mmap 之后即使关掉描述符，映射仍然作为引用留着，那部分在 /proc/<pid>/maps 里
  • 遍历过程中进程消失，readlink 就会失败。上面的写法容忍失败正是为此，也因此同一条命令跑两遍结果可能不一样
  • 进程数上千时这个遍历本身也要花时间。着急就先缩小范围，最常见的是写日志的应用程序和读日志往外送的采集器两边都咬着同一个文件

找法二 - lsof 的命令与读法

标准工具是 lsof。这个环境里没装，所以我一次都没跑过。因此下面没有示例输出，写的是手册规定的行为，以及输出里该看哪几列。

# 只要已删除却仍打开的文件 - 针对这种情形的精确提问
$ sudo lsof +L1

# 按挂载点收窄（全量扫描很慢）
$ sudo lsof -nP +L1 /var

# 谁打开着这个具体路径
$ sudo lsof /var/log/app.log

# 这个进程打开着什么
$ sudo lsof -p 1234

# 整棵目录树（递归 - 可能非常慢）
$ sudo lsof +D /var/log

核心选项是 +L1。手册写道，在 +L 后面给一个数字时，只列出链接数小于该值的文件。所以 +L1 精确地挑出链接数为 0 的文件，也就是所有名字都没了却仍打开着的文件。而且指定 +L 会在输出里加上一个 NLINK 列。

  • 默认的列构成是 COMMAND、PID、USER、FD、TYPE、DEVICE、SIZE/OFF、NODE、NAME。这里面只看 PID、SIZE/OFF 和 NAME 这三个，大多数时候就够了
  • 因为 +L 会插入 NLINK，列的位置会往后挪。像 awk '{print $2}' 这种按位置取值的写法，选项一变就崩。要自动化就按每套选项重新确认列位置
  • FD 列里除了数字还会出现 cwd、txt、mem 之类的值。mem 表示内存映射，正是 /proc/<pid>/fd 遍历漏掉的那种引用。lsof 胜过手工扫 fd 的地方就在这里
  • 数字后面跟的 r、w、u 表示读、写、读写。以写方式咬着日志文件的那一方，通常就是要处理的对象
  • -n 和 -P 关掉名称与端口的解析，手册也把速度列为理由。磁盘满了的急场上，养成随手加上的习惯更好
  • +D 会递归遍历目录树，省事但对象大时会拖很久。先试按挂载点收窄

找法三 - fuser 从路径到进程

fuser 同样这里没有，所以也没跑过。它的性格与 lsof 不同。lsof 是出清单的工具，fuser 则是拿一个路径来问、回答哪些进程在用它的工具。文件已经锁定时，它更快。

# 谁在用这个文件（以 ps 形式）
$ sudo fuser -v /var/log/app.log

# 谁在用这整个文件系统 - 卸载不掉的时候
$ sudo fuser -vm /var

# 下面两行会杀进程。没确认就不要敲
$ sudo fuser -k  /var/log/app.log     # 立刻结束
$ sudo fuser -ki /var/log/app.log     # 逐个确认后结束

加上 -v，按手册的说法就是以类似 ps 的形式给出 PID、USER、COMMAND，中间夹着一个 ACCESS 列。这一列就是读 fuser 的全部诀窍，手册对其中字母的定义如下。

字母手册的定义在这种情形下的含义
f已打开的文件（默认显示中省略）以读打开，常见于采集器与监控
F以写方式打开的文件（默认显示中省略）头号嫌疑。此刻仍在往这个文件写
mmmap 的文件或共享库靠映射咬着，扫 fd 抓不到的那一类
c当前目录只是在那里跑着，仅妨碍卸载
e正在运行的可执行文件二进制本身就在那个文件系统上
r根目录在 chroot 过的进程上会看到
危险 — fuser -k 按手册所述会杀掉正在访问该文件的进程。路径给得宽，底下所有在写的进程全都会成为目标。-m 与 -k 一起给，使用该文件系统的所有进程都会被结束。先用 -v 看清单，确认要杀的对象与清单完全一致，之后才加 -k。想要逐个确认就再加 -i，不过手册注明不带 -k 只给 -i 会被静默忽略。

占着的不止一个时

这是实务中最容易做无用功的地方。找到一个、重启了、空间却纹丝不动，那多半不是工具错了，而是引用本来就不止一个。让两个进程咬住一个 256MiB 的文件，再一个一个地结束。

[1] 创建 256MiB          free=86679271
[2] rm 完成              free=86680587   ls -A=[]
[3] 全量扫描剩余引用
    pid=318  fd=3  -> /tmp/demo/app.log (deleted)
    pid=319  fd=3  -> /tmp/demo/app.log (deleted)
[4] 只结束一个 (pid 318)  free=86682346   <-- 还不行
[5] 另一个也结束 (pid 319) free=86748978   <-- 这下回来了

[4] 里动了 1,759 块，约 7MiB 的噪声。256MiB 是 65,536 块，可是杀掉其中一个什么都没回来。到 [5] 才有 66,632 块一次性归还。内核数的是引用，不是进程。

  • 所以处理顺序是先把清单做完整，再动手。找一个杀一个再看一遍，每次清单都在变，判断就跟着晃
  • 同一个进程用多个描述符打开同一个文件的情况也有。这时处理一个进程就够了，但若用 fd 截断来应对，就得把每个编号都截
  • 典型的多引用组合是固定的，写日志的应用程序、读它的采集器，再加上有人几天前开了又忘掉的 tail -f 会话
  • 子进程继承父进程打开的文件也很常见。只重启父进程，子进程照样咬着

Windows - 查出是谁锁的

在 Windows 上症状本身就不一样。不是删掉的文件咬着空间，而是它根本删不掉。会弹出正在使用中的提示，而到底是哪个程序，通常不告诉你。

这里真正能用的是 Restart Manager API。微软文档把这个 API 的用途说成是在安装与维护过程中关闭并重启正在使用待更新文件的应用程序，以减少重启次数。那个过程所需要的信息，恰恰就是我们想要的，此刻是谁握着这个文件。它不需要管理员权限，也不需要额外安装。

Add-Type -Namespace Rm -Name Api -MemberDefinition @'
[StructLayout(LayoutKind.Sequential)]
public struct RM_UNIQUE_PROCESS { public int dwProcessId;
  public System.Runtime.InteropServices.ComTypes.FILETIME ProcessStartTime; }
[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]
public struct RM_PROCESS_INFO {
  public RM_UNIQUE_PROCESS Process;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 256)] public string strAppName;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 64)]  public string strServiceShortName;
  public int ApplicationStatus; public uint TSSessionId;
  [MarshalAs(UnmanagedType.Bool)] public bool bRestartable; }
[DllImport("rstrtmgr.dll", CharSet = CharSet.Unicode)]
public static extern int RmStartSession(out uint h, int flags, string key);
[DllImport("rstrtmgr.dll")] public static extern int RmEndSession(uint h);
[DllImport("rstrtmgr.dll", CharSet = CharSet.Unicode)]
public static extern int RmRegisterResources(uint h, uint nFiles, string[] files,
  uint nApps, RM_UNIQUE_PROCESS[] apps, uint nSvc, string[] svc);
[DllImport("rstrtmgr.dll")]
public static extern int RmGetList(uint h, out uint needed, ref uint count,
  [In, Out] RM_PROCESS_INFO[] arr, ref uint reasons);
'@

$full = (Resolve-Path $Path).Path
$h = 0
[void][Rm.Api]::RmStartSession([ref]$h, 0, [guid]::NewGuid().ToString())
[void][Rm.Api]::RmRegisterResources($h, 1, @($full), 0, $null, 0, $null)
$needed = 0; $count = 0; $reason = 0
$rc = [Rm.Api]::RmGetList($h, [ref]$needed, [ref]$count, $null, [ref]$reason)
if ($rc -eq 234) {                       # ERROR_MORE_DATA - 它在告诉你真正的个数
    $arr = New-Object 'Rm.Api+RM_PROCESS_INFO[]' $needed
    $count = $needed
    if ([Rm.Api]::RmGetList($h,[ref]$needed,[ref]$count,$arr,[ref]$reason) -eq 0) {
        for ($i = 0; $i -lt $count; $i++) {
            $pi = $arr[$i]
            "  PID {0,-7} {1,-22} restartable={2}" -f `
              $pi.Process.dwProcessId, $pi.strAppName, $pi.bRestartable
        }
    }
}
[void][Rm.Api]::RmEndSession($h)

这是在本环境里真正跑出来的结果。同一个文件问了两次，第二次是另一个进程以不共享的方式打开着它。

=== A. 没人占着的时候 ===
holders of: C:\tmp\demo\locked.txt
  (none - no process holds this file)

=== B. 另一个进程占着的时候 ===
holders of: C:\tmp\demo\locked.txt
  PID 25328   Windows PowerShell     restartable=True
  • 连同 PID 一起给出 restartable 这点很实用。为真就意味着那个程序已登记为可以被关掉再重启，处置的判断因此容易许多
  • 第一次调用 RmGetList 返回 234（ERROR_MORE_DATA）不是失败，而是在告诉你需要多大的数组，属于正常流程。把这个值当成错误处理，结果就会永远看起来是空的
  • 资源管理器那个文件正在使用的对话框有时会显示程序名，背后就是这个 API。我们做的只是用脚本把同样的信息取出来
  • 想用图形界面做同一件事，打开资源监视器（resmon），在 CPU 选项卡的关联的句柄搜索框里输入文件名即可。本文没有截图，所以界面的说明就到这里

Windows - 那些行不通的办法

搜索时常见但实际上并不管用的办法有两个。两个都跑过了，而为什么不行反倒更有用。

PS> openfiles /Local
错误: 登录的用户不具有管理员权限。

PS> openfiles /Query /FO TABLE
信息: 要查看本地打开的文件，需要启用系统全局标志
      'maintain objects list'。
通过本地共享点从远程打开的文件:
错误: 拒绝访问。

PS> # 用 Modules 查 - DLL 是能查到的
PS> Get-Process | Where-Object { $_.Modules.FileName -contains
      'C:\WINDOWS\System32\kernel32.dll' } | Select-Object -First 3 Id,ProcessName
   Id ProcessName
   -- -----------
19744 AMDInstallManager
11128 AMDRSSrcExt
21760 ApplicationFrameHost

PS> # 用同样的方式去查数据文件
PS> Get-Process | Where-Object { $_.Modules.FileName -contains $target }
(结果 0 条)

openfiles 被堵了两层。要看本地清单就得打开名为 maintain objects list 的系统全局标志，而打开它的 openfiles /Local ON 本身要求管理员权限，生效还要重启。也就是说它不是问题已经发生之后再打开来用的工具。标志关闭时 /Query 能回答的只有通过共享从远程打开的文件。

Get-Process 的 Modules 是另一回事。它不是完全没用，而是对象不同。这个集合里装的是加载进进程的可执行映像，也就是 EXE 与 DLL。上面的输出里 kernel32.dll 查得好好的。但日志文件或数据文件不是模块，所以答案永远是 0 条。

  • 归纳起来就是，若是DLL 被锁住导致更新卡住的情形，Modules 搜索就够了；其他文件则走上一节的 Restart Manager
  • Sysinternals 的 handle 系列工具用得很广，但本环境里没装，所以没能跑，因此本文没有引用它的输出
  • 实际场景里锁定的元凶是杀毒软件、备份或索引服务的情况相当多。它们打开文件很快又关掉，所以同一个查询隔几秒做两次就能把它们和持续占用者区分开

重启是答案，但重启不了的时候

找到占着的那一方之后，处置很简单，重启最靠谱。若是日志文件，很多时候用日志重开信号代替重启就够了。可要是线上服务、两样眼下都做不了，还有一个流传很广的绕行办法，就是直接把打开的文件描述符截断。

危险 — 下面这个办法无法撤销，也没有任何确认步骤。文件描述符的编号挑错一个，那个进程打开的另一个文件就会被整个清空。执行之前先用 readlink /proc/<pid>/fd/<n> 亲眼确认目标，看清它确实是带着 (deleted) 标记的日志文件，之后才动手。只要还能重启，重启永远是更安全的那一边。 
# 1) 必须先做 - 亲眼确认要截的是什么
$ readlink /proc/957/fd/3
/tmp/demo/big.log (deleted)

# 2) 之后才做 - 截断描述符（不可撤销）
$ : > /proc/957/fd/3

# 本环境里跑出来的结果
[A] rm 之后             free=86771292
    fd: inode=16607023627971255 links=0 size=268435456 blocks=262144
[B] : > /proc/957/fd/3
    tail: big.log: file truncated
    截断尝试之后: size=0  blocks=262144
    free=86770524                     <-- 没有回来
[C] truncate -s 0 /proc/957/fd/3
    size=0  blocks=262144
    free=86769107                     <-- 依然没有
[D] kill 之后           free=86833972

结果得老老实实地读。截断本身是成功的，size 从 268435456 变成了 0，咬着它的 tail 也回应了 file truncated，这就是证据。可是可用块没有回来，blocks 也还是 262144。真正的归还发生在 kill 之后的 [D]。

这里不能急着下结论。本环境的 /proc 不是 Linux 内核的 procfs 而是 MSYS 模拟出来的，底下是 NTFS。这不构成 Linux 上会得到同样结果的依据。不过从这次失败里带走的教训与环境无关，截断有没有生效，要用 df 确认，不是用 size。大小显示变成 0 和空间真的回来了，是两件不同的事实。

而且这个办法有对象限制。对日志管用，对数据文件不管用，原因在于两者对待文件的方式不同。

  • 日志文件 — 通常以追加模式打开，只往末尾写。前面的部分没了，下一次写入照样从新的末尾接上，截断不会破坏应用程序对文件的认知
  • 数据文件与数据库文件 — 要计算偏移量、读写特定位置。截断的那一刻进程记住的结构就和文件的实际内容错开了。若后续的读取把补零的区域当成正常数据来解释，损坏会悄悄扩散
  • 不是追加模式的日志 — 若实现保持着偏移量继续写，截断之后文件大小会重新长到原来的偏移量，前段补零，变成稀疏文件，看上去很大而实际占用很小
  • 被多个描述符打开的文件 — 只截一个，其他描述符照样咬着，跟上一节看到的一样

锁是另一回事

到这里为止讲的都是已删除却仍打开的文件。文件锁名字相近、症状看着也重叠，却是另一套机制。而正是在这一点上，Linux 与 Windows 精确地分道扬镳。

Unix 的 flock 是建议性的。手册这样写道，只要对文件有合适的权限，进程完全可以无视别人对 flock 的使用而照常进行输入输出。也就是说锁是选择参与的程序之间的约定，不是内核强制的墙。所以在 Linux 上rm 绝不会因为别人加了锁而失败。

Windows 不同，但也不同于常见的误解。并不是 Windows 一律阻拦，而是打开文件的一方在打开时定下共享模式，由内核强制执行。CreateFile 文档写道，共享参数为 0 时该文件无法被共享，在句柄关闭之前也无法再次打开，冲突的请求会以 ERROR_SHARING_VIOLATION 失败。实际跑一遍，同一个文件会因共享模式而走向相反的结果。

=== 以共享模式 None 打开的文件 ===
PS> Remove-Item $target
ERR: IOException
MSG: The process cannot access the file ... because it is being used by another process.
PS> Rename-Item $target renamed.txt      -> 同样的错误
PS> Get-Content $target                  -> 同样的错误

$ stat -c 'inode=%i links=%h size=%s' locked.txt
inode=6192449489676514 links=1 size=19       # 元数据还读得到
$ cat locked.txt
cat: locked.txt: Device or resource busy
$ rm locked.txt
rm: cannot remove 'locked.txt': Device or resource busy
$ ls -l
-rw-r--r-- 1 ... 19 Sep  2 09:12 locked.txt  # 原样留在那里

=== 同一个文件以共享模式 ReadWrite, Delete 打开时 ===
$ cat shared.txt
share-delete payload
$ rm -v shared.txt
removed 'shared.txt'                          # 成功。持有进程还活着
$ ls -A
(空)

两段之间的差别既不是文件也不是删除命令，只有一样，打开方允许了什么。不带共享打开的文件，删除、改名、读取全被挡住；共享列表里含删除的文件，持有进程还活着，名字却立刻消失了。后一种情形与 Unix 实质上是同一副样子。

方面Linux / UnixWindows
锁的性质建议性的，参与者之间的约定内核强制执行打开时选定的共享模式
删除使用中的文件总能成功，消失的只是名字只有打开方允许删除时才成功
失败时看到什么不会失败正在使用的提示，或 Device or resource busy
由此产生的问题空间悄无声息地不回来发布与更新被吵吵嚷嚷地挡住
查找用的工具lsof、fuser、/procRestart Manager、资源监视器
常见的误解以为 rm 删的是数据以为 Windows 使用中就绝对删不掉

落到实务上剩下的就是这一句。Windows 上发布被文件锁卡住时，要改的地方是打开方而不是删除方。让打开日志的代码允许删除共享，轮转就不会卡。

容器 - pid 因视角而不同

容器里这项工作变难，不是因为没工具，而是因为pid 与路径随视角而不同。在宿主机上跑 lsof 拿到的 pid，拿进容器里交给 kill，杀掉的是风马牛不相及的进程。反过来也一样。

容器本身在本环境跑不了。不过同一性质的错位在这里照样出得来，MSYS 用自己的一套 pid，Windows 内核用另一套。

$ tail -f hold.log > /dev/null &
$ echo $!
1410

$ ls -l /proc/1410/fd | grep -i deleted
lrwxrwxrwx 3 -> /tmp/demo/hold.log (deleted)

$ ps -W | head -1
      PID    PPID    PGID     WINPID  TTY   UID    STIME COMMAND
$ ps -W | grep 1410
     1410    1405    1403        580  ?  197609 09:18:32 /usr/bin/tail

shell 知道的 pid 是 1410，内核知道的 pid 是 580。同一个进程，哪一边都没错。要点是没有对照表就不能把一边的数字交给另一边，容器 pid 命名空间里发生的事，性质完全相同。下面是那种场合下要确认的几处。

  • 把宿主机上看到的 pid 换算成容器内的 pid 需要翻译。在 Linux 上，/proc/<host-pid>/status 的 NSpid 行会把两个值并排写出来
  • 路径也会错位。容器里的 /var/log/app.log 从宿主机看是叠加层上层某处的一条长路径。不要把宿主机侧 lsof 结果里的路径当成容器路径
  • 容器里往往既没有 lsof 也没有访问 /proc 的权限。那时从宿主机看更快，宿主机的 /proc/<pid>/root/ 下就能原样看到那个容器的文件系统
  • 最常见的错误是以为重启容器就能解决，而把日志卷原样留着。若占着的进程是容器之外的日志采集器，容器重启多少次空间都不会回来
  • 有编排系统在，人杀掉的进程会被重新拉起。要确认到新起来的进程会不会再咬住同一个文件，处置才算完

网络文件系统上的 .nfs 文件

在 NFS 上同样的情形是以看得见的形式出现的。你多半见过删掉的文件没有消失，而是留下一个以 .nfs 开头的名字。这不是故障，而是NFS 客户端在设法模仿 POSIX 行为，通常称作 sillyrename。

缘由是这样。在本地文件系统上，名字没了但只要还有打开的引用就能继续读。NFS 协议不直接支持这一点，于是客户端内核不去删除，而是把它改名成 .nfsXXXX 这种形式。按照 Linux NFS wiki 的说明，客户端会在对应的 vnode 变为非活动时删掉这个新名字。本环境没有 NFS 挂载，所以没能直接复现。

  • 所以 .nfs 文件是一个标记，不是该清掉的垃圾。它意味着还有人开着它，先找到并处理掉持有方，名字自己就会消失
  • 想删也删不动。只要引用还活着，客户端就会护着那个名字
  • 同一份 wiki 写了一个例外，若在改名和删除之间客户端崩溃，服务器上会留下一个垃圾文件。只有这种情况才是真该删的对象，判断依据是重启客户端之后它是否还在
  • 这套模仿只在客户端只有一个时成立。客户端无从知道别的客户端是否开着那个文件，所以在多个客户端共享同一文件的部署里，开着的文件被删掉是有可能发生的
  • rmdir 在看上去为空的目录里失败也是同一个原因，用 ls -a 看，.nfs 文件就在里面

从源头上不让它发生

造成这种情形的原因实际上收敛到一件事，日志轮转的配置悄悄错位了。把文件挪走或删掉之后不给进程一个重新打开的信号，进程就会继续往那个没有名字的旧文件里写。轮转究竟怎么制造出这种局面，在 日志轮转悄悄失败的地方 那边另讲。

设计一侧也有能做的事。需要临时文件时，有一个打开之后立刻删名字的惯用写法。没有名字，别的进程就碰不到；进程无论以什么方式结束，内核都会自己把空间还回来，清理代码也就不必写了。

# 打开后立刻 unlink - 匿名临时文件
$ exec 9> tmpdata
$ rm tmpdata                      # 名字在这里就没了
$ echo "hello anonymous" >&9      # 但写入照常
$ ls -A
(空)
$ stat -L -c 'inode=%i links=%h size=%s' /proc/self/fd/9
inode=16325548651260599 links=0 size=16
$ exec 9>&-                       # 关闭的瞬间归还空间，无需清理代码

# 放进监控的值 - df 与 du 的差
$ used_df=$(df -k --output=used /var | tail -1)
$ used_du=$(du -sk /var 2>/dev/null | cut -f1)
$ echo "gap_kb=$(( used_df - used_du ))"
  • 把 df 与 du 的差作为指标放进监控，这种情形在酿成事故之前就看得见。看的是趋势而不是绝对值，偏离平时的幅度并持续拉大，就说明被咬住的文件正在堆积
  • du 在大文件系统上开销很重，周期要拉长。像 CephFS 这类全量遍历代价高的文件系统，干脆避开这种做法，改用文件系统自带的递归统计
  • 确认重开信号是否同时送到了写日志的一方和读日志的一方。只有应用程序收到而采集器没收到，就只松开了一半
  • 把轮转从改名改成清空内容的方式，这个问题从原理上就不会发生。代价是轮转那一瞬间写进来的行可能丢失
  • 人留下的 tail -f 会话也是原因之一。为排查而开的会话，靠用完就关这一个习惯就能消掉

着急时的顺序

磁盘满着的时候没有时间慢慢判断，所以把顺序事先定好更好。下面是从确认最便宜的到最危险的排列。

顺序要做的要看的值此处不该做的
1把出错的路径直接给 df那条路径真的在那个文件系统上吗只看根那一行就下判断
2比较 du -sh 合计与 df 的 Used差距是不是几十 GiB把差距立刻断定为原因
3lsof +L1 或扫 /procpid、被咬住的大小、路径清单没做完就动手
4把同一文件的引用全部收集齐父进程、子进程、采集器、人的会话杀一个再重新数一遍
5重启，或发日志重开信号df 的可用量是否台阶式跳升一上来就用 kill -9
6仍然不行才截断 fd只在 readlink 确认目标之后用在数据文件或数据库文件上
危险 — kill -9（SIGKILL）不给进程任何收尾的机会。代价可能只是缓冲区里的日志丢掉，也可能是正写到一半的文件停在中间状态。先发默认的结束信号，等上几秒仍然活着时才用强制结束。无论哪种情况，对数据库或任何带状态的进程而言，这都是最后手段。
  • 第 3 步候选为 0 条时，先怀疑权限。别的用户的进程会被静静漏掉
  • 做完第 5 步 df 还是不动，就回到第 4 步。不是工具错了，而是还有引用留着
  • 急场上往再去找更多可删的东西这个方向走，通常是在丢时间。du 与 df 对不上时，删是解决不了的
  • 处置完之后再看一眼同一个文件是否又被咬住。轮转配置照旧，几天后还会回到同一个地方
  • 真正的原因在内存那一侧时，症状看着像但问题不同。那条线索在 怎么读懂 OOM Killer 选中了什么 那边

小结

rm 是删名字的命令。真正删掉数据的是最后一个引用关闭那一刻的内核。所以这种情形的解决从来不是把文件再删一遍，而是让占着的那一方松手，为此得先锁定是谁在占着。

锁定的路有三条。lsof +L1 精确挑出链接数为 0 的已打开文件。fuser -v 拿一个路径来问、回答哪些进程在用，ACCESS 列告诉你它们的性质。两样都没有就用 shell 扫 /proc/<pid>/fd，(deleted) 这个标记就替你给出答案。在 Windows 上症状是反过来的，答案由 Restart Manager 给出。

还有两件容易忘的事。引用未必只有一个；文件描述符截断对日志管用，对数据文件不管用。这两点漏掉一个，就会出现处置做了 df 却不动，或者动了却把别的东西弄坏了。

未能确认的部分

  • lsof 与 fuser 在本环境里没有安装，一次都没能执行。相应小节的命令与列说明依据的是各工具的手册，本文没有它们的执行输出。列的构成会随版本与发行版而变，自动化之前最好先在自己的机器上确认一遍
  • 文件描述符截断在本环境里只让 size 变成 0，可用块没有回来。由于 MSYS 的 /proc 不是 Linux 内核的 procfs 且底下是 NTFS，在 Linux 的 ext4 与 XFS 上是否得到同样结果，未能确认。本文不对那种环境的结果下断言
  • 容器与 pid 命名空间未能直接复现。正文里给出的 pid 错位是 MSYS 与 Windows 内核之间的，是作为性质相同的类比写的，不是从容器里取到的输出。/proc/<pid>/status 的 NSpid 行在本环境同样没能确认
  • 因为没有 NFS 挂载，没能自己造出一个 .nfsXXXX 文件。相应小节依据的是 Linux NFS wiki 的说明
  • Sysinternals 的 handle 系列工具没有安装，因而没能运行，所以本文没有引用它的输出。资源监视器是图形界面，没有截图，只写了操作位置
  • 没有真的执行 openfiles /Local ON，因此标志启用状态下的行为未能确认，那需要管理员权限和一次重启。正文里的两条错误消息是标志关闭状态下真实的输出
  • 可用块数值里混着的噪声没有清除。这是因为这台机器上还跑着别的活，几百到几千块量级的抖动由此而来。复现时不会得到相同的数字
