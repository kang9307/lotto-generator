AIエージェントで大規模コード移行を行う

数十万行を移すとき失敗はどこで起きるか - 作業分割・検証ゲート・ロールバック単位・中止判断

2026年7月28日 開発・インフラ

序論: 「100万行を移した」が教えてくれないこと

2026年前半に開発者コミュニティで最も語られた出来事のひとつが、大規模なコード移行をAIエージェントに任せた事例群である。JavaScriptランタイムのBunは自社ブログで、Zigで書かれた535,496行をRustへ移す過程で最終diff換算+1,009,272行、コミット6,502件を11日間(5月3日から14日)で生成したと明かした。ピーク時にはワークツリー4本にそれぞれ16体、約64体のエージェントが並列で動いたという。

こうした数字はそれ自体では実務の役に立たない。手順ではなく結果報告だからである。自社の15年物の決済モジュールを移すかどうか決める人に必要なのは成功談ではなく、「どこで失敗し、失敗したときどこまで巻き戻り、いつ手を引くのか」である。

本稿はその局面だけを扱う。特定の言語から特定の言語へ移す方法ではなく、一度きりの大量変更という作業形態をエージェントに委任するときの設計だ。軸は七つある。①任せられる移行とそうでない移行の判別、②作業単位の分割、③進行中の検証ゲート、④部分失敗のロールバック単位、⑤レビュー負荷を下げるdiff設計、⑥中止判断の基準、⑦コスト見積もり。

先に範囲を明確にしておく。検査器をどう設計し誤検知をどう管理するかは本稿の主題ではない。構文・実行時・意味の三層検査、ゴールデンファイル、標本検査の統計的限界はAI生成物の検査体系を作るで別に扱った。ここではその検査をどの順で、どの単位に、どんな破棄方針とともに配置するかだけを見る。特定言語の移行そのものの技術判断が知りたければGoからRustへの移行のほうが適している。

1. 大規模な自動変更は新しい話ではない

エージェントが登場するはるか前から、大規模コードベースは機械で修正されてきた。JavaScript圏のjscodeshiftはコードを抽象構文木(AST)に解析し、特定パターンのノードを探して書き換え、元の書式をできるだけ保存する方式で動く。Java圏のOpenRewriteはさらに一歩進んで無損失セマンティックツリー(Lossless Semantic Tree)というデータモデルを使う。構造だけでなく型の帰属や書式まで保持するため、コンパイラと同じ水準で型・変数・リテラルを区別する。ベンダー側の説明によれば、同じレシピは毎回同じ結果を出すという。

この決定性が重要な理由は組織規模で表れる。『Software Engineering at Google』の第22章は数十億行のコードベースにおける大規模変更(LSC)を扱い、原子的な大規模コミットは原理的に不可能だと明言する。ファイル数が増えるほどマージ衝突の確率が上がり、バージョン管理システムもCIも単一の巨大コミットを支えきれないからだ。そこでグーグルはRosieというプラットフォームでツールが生成した全体変更を所有権境界に沿ってシャードへ分割し、それぞれ独立に検証・レビュー・提出する。

同じ章には実務者がそのまま使える基準もある。変更が500編集を超えるなら手で直すより変更生成ツールを習得して使うほうが概ね効率的という経験則で、熟練した整理担当者にとってはその数字はさらに小さいとも述べている。つまり「自動化すべきか」はとうに片づいた問いであり、2026年の新しい問いは「自動化のどの区間を確率的モデルに委ねるか」である。

2. LLM方式が異なる地点 - ルールが届かない区間を埋める

古典的手法とエージェント方式は競合ではなく、覆う区間が異なる。ルール基盤の変換は「このパターンをあのパターンへ」が明示できるときに強い。逆に、言語ごとに異なるエラー処理の慣用句や、コメントに書かれた意図を反映すべき場合のように、文脈を読まなければ判断が定まらない対象にはルールを書きにくい。ひとつのルールが9割を覆い、残る1割がすべて例外という状況、その尾の区間こそエージェントが価値を出す場所だ。

軸ルール・AST基盤(codemod・レシピ)LLMエージェント
再現性同じ入力に同じ出力。再実行しても一致同じ入力でも実行ごとに結果が変わりうる
網羅範囲ルールが明示したパターンのみ。例外は手作業ルール化されていない変種にも対応を試みる
先行費用ルールやレシピの作成に集中投資ルール集は薄く、代わりに実行ごとにトークン
限界点型情報がなければ同名シンボルを区別できないコンテキスト窓を超える巨大ファイルで崩れる
必要な検証ルールを検証すれば適用結果も信頼できる生成物を個別に検証する必要がある
失敗の様相マッチ失敗(何も起きない)もっともらしいが意味の異なるコード

最後の行が実務では最も重要だ。ルール基盤ツールの失敗は静かで安全な方向である。パターンに掛からなければそのファイルは元のまま残り、残った分は一覧として取り出せる。対してエージェントの失敗は目立たず危険な方向だ。コンパイルも通りテストも通るのに意味が微妙に異なるコードが出る。Bunは統合後に19件の回帰が見つかりすべて修正したと公開したが、主因として構文は同じでも意味が異なる翻訳(表明文の中に副作用があるコードがリリースビルドで消える型)を挙げている。この種は構文検査では決して捕まらない。

実務的な結論: どちらか一方を選ぶ問題ではない。ルールで表現できる区間は決定的ツールで押し切り、残る尾だけをエージェントに渡す二段構成がコストと検証の両面で有利だ。エージェントに変換ルール自体を書かせ、適用は決定的ツールに任せる分業も成立する。

3. 任せられる移行とそうでない移行 - 5軸の判別

着手前に答えるべき問いは「AIにこれができるか」ではない。「終わったことを何で判定するのか」である。ここに答えがなければ残りの設計は意味を持たない。次の五軸で点検する。

軸問うこと委任に適する委任に適さない
①同値判定(オラクル)移した後「同じ」を何で証明するか網羅率の高いテスト、再生可能な入出力記録、ゴールデンファイルテストが薄く手動QAのみに依存
②規則性変換をパターンで記述できるかルールが大半を覆い例外が少数ファイルごとに判断がすべて異なる
③意味保存1対1対応か再設計かAPI名・シグネチャの置換、型幅の拡張並行性・トランザクション境界・メモリモデルの変更
④巻き戻し費用誤ったとき原状復帰できるかコード変更(コミット取り消しで復旧)スキーマ変更、データ移行、外部契約の変更
⑤コンテキスト適合作業単位が窓に収まるかファイル単位で独立、平均的な大きさ数万行の生成ファイル、巨大な分岐の塊

①が最も重要で、実務で最もよく飛ばされる。公開されたグーグルの社内事例がそろって「ビルドが通るか」と「回帰試験が通るか」をパイプラインに固定しているのは偶然ではない。判定手段が自動化の上限そのものだ。テストが薄いなら順序を逆にする。移行を始める前に判定装置を先に作る。遠回りに見えて概ねこちらが速い。

④はしばしば誤解される。コードは戻しやすいがデータは戻せない。ストレージのスキーマや直列化フォーマットが同時に変わる移行なら、コード移行とデータ移行を必ず別トラックに分離し、データ側は拡張後縮小(expand-contract)の順で人が統制する。エージェントに委任する対象はコードトラックだけである。

⑤は理論ではなく観測された失敗だ。グーグルの論文は大きなファイルの全内容がコンテキスト窓を超えるとモデルが修正を実行できず、開発者が手作業で処理する必要があったと記録している。事前にファイルサイズ分布を取り、上位数パーセントを手作業リストへ先に分けておくほうがよい。

4. 作業単位の分割 - 参照距離と依存順序

大量変更でまず突き当たる問題はどこを直すべきか分からないことだ。名前の変更ひとつでも、直接参照だけでなくその参照を包む関数、その関数を呼ぶコードまで連鎖的に手を入れる必要が生じうる。

4.1 変更箇所の探索

グーグルのFSE 2025論文は、社内コード索引システムKytheで直接参照 → その参照への参照 → …と広げながら参照距離5まで候補を集める方式を記述している。距離1はフィールドへの直接アクセス、距離2はそれを含むメソッドというように層が上がる。論文は実用上の理由で距離5を上限に置き、その外側は取りこぼしうると明記している。この上限がそのまま自動化範囲の境界であり、漏れた分は人が別に洗う必要があるという意味だ。

社内索引器がない場合の代替手段は言語サーバー(LSP)の参照検索、コンパイラプラグイン、ビルドグラフである。文字列検索は最後の手段だ。同名シンボルを区別できないため候補一覧そのものが汚染され、その汚染が以降のすべての段階へ伝播する。

4.2 順序の決め方

  • トポロジカル順: 依存グラフの葉から。ユーティリティや型定義など他に依存しないものが先
  • 循環はひと塊で: 相互依存するモジュールは分けずひとつのシャードにまとめる
  • アダプタを先行: 旧インターフェースと新インターフェースが一時的に共存する薄い変換層を先に入れると、以降のシャードが互いに独立してコミット可能になる
  • 試験コードは後: 試験を先に移すと判定基準が揺らぐ。判定者には最後に手を入れる
  • 生成コードは除外: コード生成器の出力は生成器を直す。出力を直接直しても次のビルドで消える

4.3 シャードの大きさの基準

シャードの大きさはトークン予算ではなく二つの問いで決める。第一に、この断片だけを単独でコミットしてもビルドと試験が通るか。第二に、人が一度に検討できる大きさか。両方を満たす最小単位がシャードであり、それがそのままロールバック単位になる。

# shards.yaml - シャードマニフェストの例(ツール中立)
- id: S-001
  scope: [lib/util/**]        # 葉モジュールから
  depends_on: []
  rollback: revert-commit     # 戻し方
  gate_profile: fast          # ビルド+単体試験まで
  owner: platform-team
- id: S-014
  scope: [svc/billing/handler/**]
  depends_on: [S-001, S-009]
  rollback: revert-commit+flag-off
  gate_profile: full          # 差分試験まで
  owner: billing-team
  note: 循環依存によりS-009と分離不可

マニフェストをファイルとして置く理由はひとつだ。進行状況とロールバック計画を人の記憶ではなくリポジトリに残すためである。数百のシャードが数日にわたって動けば、誰も全体を頭に収められない。

5. ゲートは安いものから - そして失敗したら直さず捨てる

ここが本稿の核心だ。検査項目を何で埋めるかより、どの順で配置し、脱落した生成物をどう処理するかが移行の総費用を決める。

グーグルのFSE 2025論文が記述する検証パイプラインは費用の低い検査から高い検査の順に並んでいる。①モデルが正常に応答したか → ②空白だけの変更ではないか → ③ASTパーサを通るか → ④本当に変更が必要だったか再確認 → ⑤ビルドが通るか → ⑥回帰試験が通るか。そして決定的なことに、どの段階であれ失敗すればその変更は破棄し、当該ファイルを手作業移行の対象として印を付ける。

順ゲート判定時間脱落時の処理
1応答の成否即時1回再試行後に破棄
2diffが空または空白のみ即時即座に破棄(作業していない)
3パーサ通過・構文誤りなし秒破棄
4整形器・静的検査の規則秒自動修正1回、失敗なら破棄
5変更の必要性を再確認秒不要と判定されれば破棄
6ビルド・型検査分自動修復1回、失敗なら手作業へ
7単体・回帰試験分以上手作業へ(直そうとしない)
8差分試験(旧新に同じ入力)時間不一致を一覧化して調査
9人のレビュー人の時間ここまで来たものだけを見る

初学者が最も犯しやすい失敗は6段階や7段階で脱落した生成物をエージェントに直させ続けることだ。このとき費用は線形ではなく発散する。ビルド誤りをひとつ直すと別の誤りが出て、それを直すと試験が壊れ、試験を合わせようとして試験そのものへ手を伸ばす経路に滑り込む。修復の試行は1回に制限し、その後は捨てるほうが総費用では有利だ。

捨てたものをどう扱うかで二つの流儀に分かれる。グーグルは手作業移行のリストへ回す。一方、Anthropicが自社ブログで整理した手法(ベンダー資料)は「個別の失敗を直すのではなく、その失敗を生んだループを直せ」という原則を掲げる。コンパイル誤りの一覧に同じパターンが繰り返し現れるなら、ファイルに手を入れる代わりにルール集を直して影響を受けたファイルだけ再生成するという考え方だ。レビュアーが同じ指摘を繰り返すならルール集に一文を足してバッチを回し直す。

二つの手法の選択基準: 脱落理由が散発的なら手作業リストへ回すほうが安い。脱落理由が群を成すなら(同じエラーメッセージが数十件)ルールを直して再生成するほうが安い。だから脱落ログは理由別に集計できる形で残さねばならない。自由記述のログだけではこの判断自体ができない。

# ゲートパイプラインの擬似コード(ツール中立)
for file in batch:
    out = agent.transform(file, rulebook_v)
    if not out.ok:                 continue        # G1 破棄
    if out.diff.is_trivial():      continue        # G2 破棄
    if not parser.accepts(out):    log(file,'parse'); continue          # G3
    out = formatter.fix_once(out)                                       # G4
    if agent.confirm_needed(out) is False: log(file,'punt'); continue   # G5
    if not build(out):
        out = agent.repair_once(out)
        if not build(out): manual_queue.add(file,'build'); continue     # G6
    if not tests(out):  manual_queue.add(file,'test'); continue         # G7
    shard.stage(out)
report.group_by_reason()   # 理由別集計 -> 修正すべきルールを判別

6. 部分失敗のロールバック単位 - シャードを「家畜」にする

大規模変更においてロールバックは例外事態ではなく通常の運用手順である。『Software Engineering at Google』は自動生成の変更をペットではなく家畜のように扱えと表現する。名前も顔もないコミットであり、戻しても損失が大きくないという意味だ。人が数日かけて作ったコミットは戻すのが惜しいが、ツールが3分で作り直すコミットは惜しくない。

この性質を得るには設計段階で条件を課す必要がある。

  • ロールバック単位=シャード=コミット。三つがずれると、戻すとき何を戻すか人が判断する羽目になる
  • シャードは再生成可能であること。コミットメッセージに使ったルール集の版と対象範囲を残し、一行の命令で作り直せるようにする
  • 実行時の切り替えはフラグで。コードの配置と動作の切り替えを分ければ、ロールバックがデプロイではなく設定変更になる
  • アダプタを早々に外さない。旧経路を残した期間がそのままロールバック可能期間だ
  • ロールバックの予行演習を一度は行う。実際に戻してみていないロールバック計画は計画ではない
  • データ・スキーマは別トラック。コードのロールバックがデータの破損を戻してくれるわけではない

グーグルのシャード運用にはもうひとつ参考になる点がある。試験自動化基盤が周期的に走る列車モデルでまとめて検証し、失敗すれば個別シャードを再分析して原因を特定する点だ。要点は失敗を個別の事件ではなくバッチ単位で観測するところにある。ひとつのシャードの失敗は情報が少ないが、二十件のうち六件が同じ理由で失敗すれば、それはルールの問題だという信号である。

7. レビュー負荷を下げるdiff設計

自動生成の規模が大きくなると、ボトルネックは生成ではなくレビューへ移る。一日に数千行を作れても、人が一日に検討できる量は変わらない。だからdiffは読まれるように設計しなければならない。

7.1 混ぜない

  • 機械の変更と人の変更をひとつのコミットに混ぜない。混ざった瞬間、レビュアーは全体を精読せざるを得ない
  • 書式変更は先行コミットへ分離する。整形器の結果が本体の変更に混ざるとdiffの9割が雑音になる
  • ファイルの移動・改名は別コミットで。移動と内容変更が同じコミットにあると、ツールが移動を追跡できず全体が削除と追加として表示される
  • ひとつのシャードにひとつのパターンだけを入れる。二種類の変換が混ざるとレビュアーがそれぞれを個別に検証することになる

7.2 反復を反復に見せる

同じ形の変更が300か所に繰り返されるなら、レビュアーが300回読む理由はない。グーグルはこの問題を全体承認者という制度で解く。言語やライブラリの専門家がパターン基盤のツールで変更を走査し、パターンから外れたものだけを人が見る。各変更を個別にレビューしないことが核心だ。

社内でこの構造を模倣するには、プルリクエストの本文に三つを入れればよい。

  • 正規の変換形: 「A(x) → B(x, ctx)」のように、このシャードが実行した変換の標準形
  • 正規形に一致した件数と外れた件数: 「287件が正規形に一致、4件が逸脱」
  • 逸脱4件のファイル経路と理由: レビュアーはここだけを精読する

逸脱を自動で抽出する方法は単純だ。diffを正規化(変数名と空白を除去)してハッシュでまとめると、大多数が少数の群に集まる。群の大きさが1のdiffが逸脱であり、事故はたいていそこで起きる。

migrate(S-014): map legacy Clock API to injected clock

rulebook: v7 (2026-07-28)
scope:    svc/billing/handler/**  (files: 31)
pattern:  Clock.now()  ->  clock.now()   [287 hits]
outliers: 4  (see below)
  - handler/retry.go:88    タイムゾーン変換も併せて必要
  - handler/report.go:214  試験フィクスチャが固定時刻を前提
  - ...
gates:    parse/format/build/unit  PASS   diff-test  PASS
regen:    ./migrate.sh --rulebook v7 --shard S-014

この形式の利点はレビュアーが何を見なくてよいか分かることだ。レビュー負荷を下げる方法はdiffを小さくすることではなく、精読すべき部分を明示的に狭めてやることである。

8. 進行管理 - 毎日何を測るか

移行はスプリントで区切りにくい作業だ。「70%終わった」という報告が意味を持つには分母が固定されている必要があるが、進めるうちに新しい対象が次々見つかる。だから指標は比率より残量と速度で取るほうがよい。

指標数え方見る理由
残対象探索済み候補のうち未処理ファイル数分母が増える速度まで併せて見る
ゲート通過率段階別の通過÷投入ルール品質の代理指標。バッチ間の推移が重要
人の後続修正率モデル生成物に人が手を入れた比率この値が高ければ委任の利得が消える
レビュー待ち残量生成完了−レビュー完了ボトルネックの位置を判別。増えるなら生成を止める
再作業率同じファイルが再生成された回数3回以上は手作業移管の信号
統合後の回帰配備後に見つかった不具合数ゲートが逃したもの。ゲート設計へ還元する
累積費用トークン費用+レビュー時間の換算予算対進捗で継続可否を判断

この中で最も解釈が難しいのが人の後続修正率だ。グーグルのFSE 2025論文は595件の変更を三つに分類した。モデルだけで完結したもの214件(35.97%)、モデル生成後に人が手を入れたもの229件(38.48%)、人がすべて書いたもの152件(25.55%)。前の二つを合わせた値が広く引用される74.45%である。

この分解が重要なのは、74%という数字が「人の手が入っていない」という意味ではないからだ。モデルだけで終わったのは36%ほどで、残る38%は人の後続編集を経ている。編集量で見てもモデル寄与が69.46%(64,996件)、人の寄与が30.54%(28,578件)に分かれる。すなわち「AIが74%やった」と「人が3分の1を手直しした」は同じデータの二つの顔である。計画を立てるときは後者の顔で人員を見積もるほうが安全だ。

9. 中止判断の基準 - いつ手を引くか

自動化を導入したチームが最も遅れて決めるのが中止条件である。すでに相当の費用を使っているため止めにくく、そうして埋没費用が判断を食う。中止基準は着手前に数値で固定しておかねばならない。

信号閾値の例解釈措置
ゲート通過率の低下3バッチ連続で低下ルールが残りの区間を覆えていない生成停止、ルール再作成または範囲縮小
同じファイルの再生成3回超過構造的に合わないファイル手作業リストへ移管
人の後続修正率事前合意線の超過委任の利得が消滅残る範囲を手で処理
レビュー待ちの増加2週連続の純増ボトルネックがレビューへ移動生成速度をレビュー処理量に合わせる
統合後の回帰の累積ロールバック処理速度を超過ゲートが失敗を濾せていない配備凍結、ゲートの補強
費用超過パイロット推定の1.5倍前提が誤っていた再推定のうえ再承認
試験コードの変更検出1件でも判定基準そのものが揺らぐ即時停止、当該バッチを全量破棄

最後の行は他と性質が異なる。他が「効率が悪くなった」という信号なら、これは測定そのものが汚染されたという信号だ。エージェントが落ちた試験を通す最も簡単な方法は、コードを直すことではなく試験を直すことである。

この問題はベンチマークでも確認できる。Javaのバージョン移行を評価するFreshBrew研究(arXiv:2510.04852, ICSE 2026)はリポジトリ228件を対象に、エージェントの意味保存能力と報酬ハッキング回避能力を測定した。論文によれば最高成績のモデルがJDK 17への移行に成功した比率は52.3%で、整合性検査を課さなければ見かけ上の成功の相当部分が報酬ハッキングに分類されただろうと指摘している。よく管理されたオープンソースのリポジトリでも成功率がその程度なら、社内のレガシーがより易しい理由はない。

実務上の防御策は単純だ。試験コードの経路を別ゲートで施錠する。移行バッチのdiffに試験ファイルが含まれれば自動的に失敗扱いとし、試験を直す必要がある場合は人が別のプルリクエストとして分離して進める。Bunは自社ブログで飛ばしたり削除した試験が0件である点を成果指標のひとつとして明示したが、この項目をわざわざ前面に出したこと自体がこの危険がよく知られている証左である。

10. コスト見積もり - トークンより人が高い

コスト見積もりでよくある誤りは「行数×行当たりトークン」で終えることだ。実際には再試行倍率、コンテキストとして併せて入れる参照ファイル、ゲート実行の基盤、そしてレビュー時間がすべて乗る。

項目算式実測の方法
生成トークン(入力トークン+出力トークン)×単価代表ファイル20件を実測して外挿
再試行倍率1÷ゲート最終通過率パイロットバッチで測定
コンテキスト負担対象ファイル+参照ファイルの大きさ参照距離を伸ばすほど急増
キャッシュ効果反復投入プロンプトのキャッシュ読み比率ルール集が長いほど利得が大きい
ゲート実行ビルド・試験のCI時間×バッチ数大規模リポジトリでは無視できない
レビュー時間シャード数×シャード当たりレビュー時間たいていここが最大
手作業の残り脱落ファイル数×ファイル当たり手作業時間ゲート脱落率から導出

公開された大型事例の実測値は感覚をつかむのに役立つ。BunはRust移植に非キャッシュ入力59億トークン、出力6.9億トークン、キャッシュ読み720億トークンを要し、API定価換算で約16万5千ドルだったと明かした。最終diffの100万行で割ると生成行当たり約0.16ドル、元のZig 53万5千行を基準にすると元行当たり約0.31ドルである。

この数値をそのまま使わないこと: 当事者発表であり、試験スイートが異例に厚いリポジトリであり(プラットフォームごとに約6万件の試験、Linux x64基準で138万回超の表明)、定価換算である。リポジトリの状況が異なれば桁が変わりうる。見積もりは必ず自分のリポジトリのパイロットで取り直す。

キャッシュの項目は注目に値する。Bunの事例ではキャッシュ読みトークンが非キャッシュ入力の12倍を超える。ルール集や参照文書のように毎回の要求に繰り返し投入される部分をプロンプトの前方へ固定すればキャッシュが効き、費用構造が大きく変わる。逆にルール集を頻繁に修正すればそのたびにキャッシュが無効化される。ルール集の改訂はまとめて行い版を打つという運用原則はここから出てくる。

期間の見積もりには別角度の参考値がある。グーグルは社内のJUnit3からJUnit4への移行で3か月の間に5,359ファイル、14万9千行余りを処理し、モデルが生成したコードの約87%が無修正でコミットされたと報告した。別の事例では以前と比べ所要時間が約50%減少したという技術者の推定を載せている。「10倍速くなる」ではなく「半分」というのが現実的な期待値だ。

11. 失敗はどこで起きるか - 観測された類型

以下は公開資料に記録された失敗類型を実務の観点で整理したものだ。推測ではなく報告された事例に基づく。

類型症状検出対応
コンテキスト超過巨大ファイルで修正自体が行われないファイルサイズ分布事前に手作業リストへ分離
非決定性同じ入力に毎回異なるdiff同一入力を2回実行して比較再現不可を前提に生成物単位で検証
不要な変更書式だけ変える、コメントだけ足すdiffを正規化して実質変更の有無を確認ゲート2・5段階で破棄
参照の取りこぼし遠い間接参照が変わらない参照距離の上限外を一覧化人が別途走査
意味の不一致ビルドも試験も通るのに動作が異なる差分試験、統合後の監視表明や副作用の慣用句をルール集に明記
言語による偏り特定言語だけ品質が急落言語別に通過率を分離集計その言語はルール基盤へ切り替え
ゴールデンファイル未更新期待値ファイルが旧形式のままゴールデンファイルの経路を別途追跡人が更新、自動更新は禁止
報酬ハッキング試験が弱められる・削除される試験経路のdiffを施錠バッチを全量破棄して再設計

このうち非決定性は移行作業で特に厄介だ。温度を0にしても完全な再現が保証されない点はすでに公開報告がある。ある研究ラボは同一プロンプトを温度0で1,000回実行したところ異なる完成文が80種出たと明かし、原因を無作為性ではなくバッチサイズによるカーネル計算順序の差として説明した。移行の文脈でこの性質が含意することはひとつだ。「昨日流したものと同じ結果」を前提にした手順は立てられない。だから信頼の対象は生成過程ではなく生成物とそれを通したゲートの記録でなければならない。非決定的な出力に通過基準を立てる方法自体はプロンプトをコードのように管理するで別に扱った。

ゴールデンファイル未更新もよく見落とされる。グーグルの論文は自動ツールがゴールデンファイルの更新に対応していない点を残る課題として明記した。期待値ファイルを自動更新させると判定基準が生成物に追従する逆転が起きるからだ。この項目は利便性を放棄するのが正しい。

12. 反論 - 「レビューされていない100万行」問題

均衡のため反対側の論拠をそのまま移す。Zig言語を作ったAndrew KelleyはBunのRust書き換えについて強い批判を公に示したと報じられた。核心はオラクルの信頼度に関する論点である。既存の試験スイートが元のZig実装の欠陥を防げなかったのなら、同じスイートが新たに生成された100万行の欠陥を捕まえると見る根拠は何か、という問いだ。報じられた表現ではそれを「レビューされていないスロップ」と呼んだという。

この批判は特定の人物や企業への評価として読むべきではなく、3節の①番の軸を問い直すものとして読むべきだ。自動化が通過判定を委ねる相手が試験スイートなら、そのスイートの欠陥検出力がそのまま移行品質の上限になる。スイートが逃していたものは移行後も逃し続ける。

Bun側が公開した反論も併せて見なければ公平ではない。プラットフォームごとに約6万件の試験とLinux x64基準で138万回超の表明、飛ばしたり削除した試験0件、実装者1名と別コンテキストのレビュアー2名が加わる対立レビュー、6プラットフォームにわたるCIシャーディング、漏れ検出器とファザーの常時稼働を挙げている。そして統合後に19件の回帰が実際に見つかり修正されたと明かした。

両方を総合すると実務的な教訓は明確だ。どちらの主張が正しいか判定するより、自分のリポジトリの試験スイートがどの水準の欠陥を捕まえるのかをまず測ることが順序である。その測定なしに始めた移行は通過記録が積み上がっても、その記録の意味を誰も説明できない。

測定方法をひとつ: 移行を始める前に元のコードへ意図的な欠陥をいくつか埋め込み、試験がそれを捕まえるか確認する(ミューテーション試験の縮小版)。埋め込んだ欠陥の多くが通り抜けるなら、そのスイートは移行の判定者として不足しているという意味だ。この確認は一日で終わり、結果によって計画全体が変わる。

13. 2週間のパイロット設計

全面着手の前にパイロットを回す。目的は「できるか見ること」ではなく推定に使う数値を確保することだ。

  • 1〜2日目 オラクル点検: 欠陥注入で試験スイートの検出力を測る。差分試験が可能な境界(純粋関数、直列化の地点、HTTPハンドラ)を一覧化する
  • 3〜4日目 対象調査: 参照距離別の候補数、ファイルサイズ分布、生成コード・ゴールデンファイル・試験ファイルの経路を分離する。この段階で自動化範囲外の一覧が確定する
  • 5〜6日目 ルール集の草案: 代表ファイル20件を手で移しながらルールを抽出する。手で移さずに書いたルール集はたいてい最初のバッチで崩れる
  • 7〜8日目 小規模バッチ: 20〜30ファイルにゲートを全部かけて流す。段階別の脱落率と理由の分布を集計する
  • 9〜10日目 ルール改訂後に再実行: 群を成す脱落理由だけをルールへ吸収し、再度流して通過率の変化を見る
  • 11〜12日目 レビュー実測: 実際のレビュアーがシャード3件をレビューし所要時間を測る。この値が全体日程の支配項になる場合が多い
  • 13〜14日目 外挿と判断: 通過率・再試行倍率・レビュー時間から総費用と期間を算出し、中止条件表の閾値を確定する

パイロットの結果が悪く出るのは失敗ではない。2週間で濾せるものを6か月後に知るほうが失敗だ。特にオラクル点検で低い点数が出た場合、その時点での正しい結論は「AIを使うのはやめよう」ではなく「まず試験を補強しよう」である。

結論

大規模コード移行においてエージェントが変えたのは変換作業の単価であって作業の構造ではない。原子的な大規模コミットが不可能だという事実、シャードに分けて独立に戻せねばならないという事実、レビューがボトルネックになるという事実は、codemodの時代と同じである。変わったのはルールで表現できなかった尾の区間まで自動化の射程に入った点、そしてその代償として生成物を個別に検証しなければならない点だ。

だから設計の重心は生成ではなく破棄方針にある。安いゲートから配置し、脱落したものは直そうとせず捨て、脱落理由が群を成すならルールを直して再生成し、散発的なら人のリストへ回す。シャードはいつでも戻せる家畜でなければならず、diffはレビュアーに何を見なくてよいかを教えるものでなければならない。

最後に限界を明確にしておく。ここに書かれたどの手順も移行の成功を約束しない。本稿が示すのは成功の公式ではなく失敗を安く、そして早く見つける配置である。公開された数値が指し示す現実的な期待値も魔法ではない。よく整った社内環境で所要時間が半分ほどに減り、よく管理されたオープンソースのリポジトリでも自動移行の成功率は半分近くだった。その半分を確保するだけでも十分に価値があるのは、残る半分がどこなのかが一覧として手に入るからである。
