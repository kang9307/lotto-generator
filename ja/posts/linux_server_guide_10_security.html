はじめに：セキュリティは選択ではなく必須

サーバーセキュリティは単一ソリューションではなく、多層防御（Defense in Depth）戦略が必要です。この最終編では、Linuxサーバーセキュリティ強化の核心を解説します。

この記事のコマンドと設定は、OpenSSH・Linux-PAM・UFW・DNF Automatic・Greenbone の公式ドキュメントで再確認しました（2026-09-29）。ディストリビューションごとに異なる部分（パッケージ名・サービス名・ログの場所）は本文中に示しています。リモートサーバーで SSH・ファイアウォール・PAM を変更するときは、現在接続中のセッションを閉じずに新しいターミナルで試すことが、すべての手順の前提です。また、この記事のコマンドは自分が所有する、または管理権限のあるサーバーでのみ使用してください。

1. システムハードニング基礎

1.1 不要なサービスの無効化

# 実行中のサービス確認
systemctl list-units --type=service --state=running

# 不要なサービスの無効化（未インストールならエラーになるのが正常）
sudo systemctl disable --now cups
sudo systemctl disable --now avahi-daemon
sudo systemctl disable --now bluetooth

# 起動時に開始するサービスの確認
systemctl list-unit-files --type=service --state=enabled

本番サーバーでは、サービスを止める前に、それに依存するものがないか systemctl list-dependencies --reverse サービス名 などで先に確認します。

1.2 セキュリティアップデート

# Ubuntu/Debian
sudo apt update && sudo apt upgrade -y
sudo apt install unattended-upgrades
sudo dpkg-reconfigure unattended-upgrades

# RHEL系（RHEL、Rocky Linux、AlmaLinux）
sudo dnf update -y
sudo dnf install dnf-automatic
# dnf-automatic.timer は automatic.conf に従い、apply_updates の既定は False のためインストールしない
sudo systemctl enable --now dnf-automatic-install.timer

RHEL系では dnf-automatic.timer は automatic.conf の設定にそのまま従い、apply_updates の既定値は False です。そのためこのタイマーだけを有効にしても、更新のダウンロードや通知だけでインストールはされません。インストールまで自動化するには dnf-automatic-install.timer を使います（DNF Automatic ドキュメント）。この記事の旧版は前者を有効にするよう書いており、実際にはインストールされませんでした。

1.3 GRUBセキュリティ

# Debian/Ubuntu の場合。編集前にバックアップし、コンソールアクセス手段を確保しておく
sudo cp -a /etc/grub.d/40_custom /root/40_custom.bak

# GRUBパスワードのハッシュ生成
sudo grub-mkpasswd-pbkdf2
# ハッシュ値をコピー

# /etc/grub.d/40_custom を編集
set superusers="admin"
password_pbkdf2 admin grub.pbkdf2.sha512...

# 設定の適用（Debian/Ubuntu）
sudo update-grub

GRUBパスワードはブートメニューの編集を防ぐ仕組みで、誤って設定するとブートメニューが使えなくなることがあります。40_custom のバックアップとコンソール（仮想マシンコンソール、IPMI など）へのアクセス手段を確保してから進めます。RHEL系はコマンドが異なるため、この記事では扱いません。

2. ユーザーセキュリティ

2.1 パスワードポリシー

# /etc/login.defs
PASS_MAX_DAYS   90    # 最大使用期間
PASS_MIN_DAYS   7     # 最小使用期間
PASS_WARN_AGE   14    # 期限切れ警告

# PAMパスワード複雑性（Debian/Ubuntu: /etc/pam.d/common-password）
password requisite pam_pwquality.so retry=3 minlen=12 dcredit=-1 ucredit=-1 ocredit=-1 lcredit=-1

# 既存ユーザーに適用
sudo chage -M 90 -m 7 -W 14 username

RHEL系には /etc/pam.d/common-password がありません。同じオプション（minlen など）を pwquality の設定に置きます。正確な場所はディストリビューションのドキュメントに従ってください。PAM ファイルを編集するときは、開いている root セッションを閉じず、別のターミナルで passwd を使って試します。

2.2 sudo設定

# /etc/sudoers（必ず sudo visudo で編集 - 構文エラーがあると sudo 自体が使えなくなる）
# ログ記録
Defaults logfile=/var/log/sudo.log
Defaults log_input, log_output

# タイムアウト設定
Defaults timestamp_timeout=5

# 特定のコマンドのみ許可
username ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx

NOPASSWD の例は、コマンド1つに絞った場合にだけ使います。範囲を広げると、そのアカウントが破られたときにそのまま root 権限になります。

2.3 アカウントロック

# RHEL系: authselect で faillock 機能を有効化（pam_tally2 の後継）
sudo authselect current
sudo authselect enable-feature with-faillock

# /etc/security/faillock.conf
deny = 5
unlock_time = 900

# 失敗回数の確認 / ロック解除
sudo faillock --user username
sudo faillock --user username --reset

pam_tally2 は Linux-PAM 1.5.0 で削除されました（1.5.0 リリースノート: 「Removed deprecated pam_tally and pam_tally2 modules, use pam_faillock instead」）。この記事の旧版が使っていた pam_tally2.so deny=5 unlock_time=900 はそれ以降のディストリビューションでは動作せず、後継は pam_faillock です。設定ファイルは /etc/security/faillock.conf で、既定値は deny 3回、fail_interval 900秒、unlock_time 600秒です（faillock.conf(5)）。サービス拒否を防ぐため root は既定ではロックされませんが（pam_faillock(8)）、even_deny_root で変更できます。リモートの root がロックされるとコンソールなしでは復旧が難しいため、有効にする前にコンソールアクセスを確認します。

Debian/Ubuntu では common-auth と common-account に pam_faillock の行を自分で追加する必要があり、順序は man pam_faillock の例（auth の preauth、pam_unix、authfail、そして account）に従います。編集前にバックアップし、開いている root セッションを閉じずに別のアカウントでログインして試します。

3. SSHセキュリティ強化

# 0) 編集前にバックアップ。現在のSSHセッションは最後まで閉じない
sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak

# /etc/ssh/sshd_config

# デフォルトポート変更（任意）。ファイアウォール（4節）とRHEL系ではSELinuxポートラベル（6.1節）を先に用意してから
Port 2222

# rootログイン禁止
PermitRootLogin no

# パスワード認証を無効化 - 新しいセッションで鍵ログインの成功を確認してから
PasswordAuthentication no

# 鍵認証を許可
PubkeyAuthentication yes

# 空パスワード禁止
PermitEmptyPasswords no

# ログイン試行の制限
MaxAuthTries 3
LoginGraceTime 30

# 特定ユーザーのみ許可（AllowGroups と併用する場合の結合規則は sshd_config(5) で確認し、試してから）
AllowUsers admin deploy
#AllowGroups sshusers

# （Protocol 2 はもう不要: OpenSSH 7.4 で SSH v1 サーバーサポートが削除された）

# 1) 構文チェック - 出力がなければ正常
sudo sshd -t
# 2) 実効設定の確認
sudo sshd -T | grep -Ei '^(port|permitrootlogin|passwordauthentication|maxauthtries) '

# 3) 適用（サービス名は Debian/Ubuntu が ssh、RHEL系が sshd）
sudo systemctl restart ssh
sudo ss -tlnp | grep sshd

# 4) 既存セッションは残したまま、新しいターミナルで接続テスト
ssh -p 2222 admin@server

# 5) 失敗したら、残しておいた既存セッションで元に戻す
sudo cp -a /etc/ssh/sshd_config.bak /etc/ssh/sshd_config
sudo systemctl restart ssh

OpenSSH の既定値は PermitRootLogin prohibit-password、MaxAuthTries 6、LoginGraceTime 120秒です（sshd_config(5)）。Protocol 2 の行は、OpenSSH 7.4 が SSH v1 サーバーサポートを削除して以降は意味がないため削除しました（7.4 リリースノート）。sshd -t は設定ファイルの妥当性と鍵を検査し、sshd -T は実効設定を出力します（sshd(8)）。Ubuntu のドキュメントは、再起動前に sudo sshd -t で設定を確認するよう述べ、誤るとサーバーからロックアウトされる可能性があると警告しています（Ubuntu Server ドキュメント）。そのため上記の手順（バックアップ、構文チェック、再起動、新しいターミナルでの確認、失敗時の巻き戻し）を守り、テストが終わるまで既存のセッションは閉じません。

Ubuntu のソケットアクティベーション（ssh.socket）環境で、Port の変更が再起動だけで反映されるかは確認できていません。再起動後に ss -tlnp | grep sshd で実際に待ち受けているポートを確認してください。ポート変更は自動スキャンによるログのノイズを減らすだけで、実際の防御線は鍵認証とアクセス制限です。AllowUsers と AllowGroups を併用する場合は、sshd_config(5) を読み、試してから使います。

4. ファイアウォール設定

4.1 UFW (Ubuntu)

# デフォルトポリシー
sudo ufw default deny incoming
sudo ufw default allow outgoing

# ★ ufw enable より先にSSHを許可する。ポートは sshd が実際に待ち受けるポートと一致させる
sudo ss -tlnp | grep sshd
sudo ufw allow 2222/tcp comment 'SSH'
sudo ufw allow 80/tcp comment 'HTTP'
sudo ufw allow 443/tcp comment 'HTTPS'

# IPベースの制限（SSHポートは上と同じ 2222）
sudo ufw allow from 192.168.1.0/24 to any port 2222 proto tcp

# 有効化。ロックアウトされたらコンソールから sudo ufw disable
sudo ufw enable
sudo ufw status verbose

マニュアルには、ufw enable はチェーンを空にするため SSH などの既存接続を切断する可能性があると書かれています（ufw(8)）。そのため SSH 許可ルールを enable より先に入れ、そのポートを sshd が実際に待ち受けるポートと合わせます。この記事の旧版は SSH を 2222 に変更しながら IP 制限ルールは 22 番で書いており、互いに矛盾していました。ufw limit ルールは、30秒以内に6回以上接続を試みる IP の接続を拒否します。

4.2 firewalld (RHEL/CentOS)

# デフォルトゾーンの確認
sudo firewall-cmd --get-default-zone

# サービスを許可
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https

# ポートを許可 - sshd を新しい Port で再起動する前に開ける
sudo firewall-cmd --permanent --add-port=2222/tcp

# ルールを適用して確認
sudo firewall-cmd --reload
sudo firewall-cmd --list-all

sshd の Port を変更するときは、ファイアウォールの --permanent ルールと --reload、さらに SELinux ポートラベル（6.1節）まで済ませてから sshd を再起動します。順序が逆だと、新しいポートに接続できないか、sshd が起動しません。

5. 侵入検知システム

5.1 Fail2Ban

# インストール（RHEL系は dnf。提供リポジトリはディストリビューションごとに異なる）
sudo apt install fail2ban

# /etc/fail2ban/jail.local
[DEFAULT]
bantime = 3600
findtime = 600
maxretry = 3
# 自分自身を遮断しないよう管理者IPを追加する
ignoreip = 127.0.0.1/8 ::1

[sshd]
enabled = true
port = 2222
# journald のみのシステム（/var/log/auth.log がない場合）はジャーナルを読ませる
backend = systemd
# ファイルログを使う場合: logpath = /var/log/auth.log

[nginx-http-auth]
enabled = true

# 起動と状態確認
sudo systemctl enable --now fail2ban
sudo fail2ban-client status
sudo fail2ban-client status sshd
# 誤って遮断されたIPの解除
sudo fail2ban-client unban 203.0.113.10

Debian 12 のようにジャーナル（journald）のみを使うシステムには /var/log/auth.log がなく、従来のように logpath だけを書いても sshd jail が読むログがありません。このようなシステムでは backend = systemd を使います。この部分と ignoreip・unban オプションは、fail2ban の公式ドキュメントと直接照合できておらず、二次資料で確認しました。適用後は fail2ban-client status sshd で jail が実際に動作しているか確認します。

5.2 AIDE（整合性検査）

# インストール（Debian/Ubuntu）
sudo apt install aide

# データベースの初期化
sudo aideinit

# チェックの実行
sudo aide --check

# データベースの更新
sudo aide --update

6. SELinux / AppArmor

6.1 SELinux (RHEL/CentOS)

# 状態確認
getenforce
sestatus

# モード変更（再起動まで有効）。Permissive は原因調査用
sudo setenforce 0  # Permissive
sudo setenforce 1  # Enforcing

# 永続設定（/etc/selinux/config）
SELINUX=enforcing

# SSHポートを変えたら sshd 再起動前にラベルを付ける（付けないと bind が Permission denied になる）
sudo semanage port -a -t ssh_port_t -p tcp 2222
sudo semanage port -l | grep ssh_port_t

# トラブルシューティング
sudo ausearch -m avc -ts recent
sudo sealert -a /var/log/audit/audit.log

RHEL系でSSHポートを変更した場合、SELinux は sshd が ssh_port_t とラベル付けされたポートにのみ bind することを許可します。ラベルを付けずに再起動すると、Permission denied で sshd が起動しません。semanage は policycoreutils-python-utils パッケージに含まれます。この手順は公式ドキュメントではなく二次資料で確認しました。sealert は別のパッケージのインストールが必要な場合があります。setenforce 0 は原因切り分けのための診断用で、確認が終わったらすぐ setenforce 1 に戻します。

6.2 AppArmor (Ubuntu)

# 状態確認
sudo aa-status

# プロファイル管理
sudo aa-enforce /etc/apparmor.d/usr.sbin.nginx
sudo aa-complain /etc/apparmor.d/usr.sbin.nginx

# ログ確認
sudo journalctl -fx | grep apparmor

7.2 OpenVAS

# Greenbone Community Edition: 公式のコンテナ導入ガイドに従う
# https://greenbone.github.io/docs/latest/22.4/container/index.html
# （Docker/Podman と docker-compose が必要。公式ドキュメント対応: Debian stable、Ubuntu 24.04 LTS など）
# スキャンは自分が所有する、またはスキャンを許可されたシステムにのみ実行する

この記事の旧版は apt install openvas と gvm-setup を案内していましたが、Greenbone の公式ドキュメントはコンテナ（Docker/Podman + docker-compose）でのインストールを案内しており、ディストリビューションのパッケージによるインストールは扱っていません。公式ドキュメントが対応を明記しているのは Debian stable（bookworm）、Ubuntu 24.04 LTS などで、そのコンテナ手順自体、本番環境向けではないと述べています（Greenbone Community Containers）。スキャンは所有している、または許可を得たシステムにのみ実行します。

8. ログモニタリング

# 不審なアクティビティの監視
# ログイン失敗（Debian/Ubuntu）
sudo grep "Failed password" /var/log/auth.log | tail -20
# ログイン失敗（RHEL系）
sudo grep "Failed password" /var/log/secure | tail -20
# journald のみのシステム（RHEL系は -u sshd）
sudo journalctl -u ssh --since today | grep "Failed password" | tail -20

# sudo の使用記録
sudo grep "sudo" /var/log/auth.log

# システムの起動/停止
last reboot
last shutdown

# 現在ログイン中のユーザー
who
w

# ネットワーク接続
ss -tuln

ログの場所はディストリビューションごとに異なります。Debian/Ubuntu は /var/log/auth.log、RHEL系は /var/log/secure で、ジャーナルのみを使うシステムでは journalctl で確認します。旧版にあった netstat の行は、ss と目的が同じなので削除しました。

9. セキュリティチェックリスト

#!/bin/bash
# security_audit.sh (読み取り専用チェック)

echo "=== Linuxセキュリティ監査 ==="

echo -e "\n[1] システムアップデートの確認"
apt list --upgradable 2>/dev/null | head -10

echo -e "\n[2] rootログインの可否（実効設定）"
sudo sshd -T 2>/dev/null | grep -i "^permitrootlogin"

echo -e "\n[3] パスワード認証の有無（実効設定）"
sudo sshd -T 2>/dev/null | grep -i "^passwordauthentication"

echo -e "\n[4] 開いているポート"
ss -tuln | grep LISTEN

echo -e "\n[5] SUIDファイル（同一ファイルシステムのみ）"
find / -xdev -perm -4000 -type f 2>/dev/null | head -10

echo -e "\n[6] 空パスワードのアカウント（root権限が必要）"
sudo awk -F: '($2 == "") {print $1}' /etc/shadow

echo -e "\n[7] 最近のログイン失敗"
sudo grep "Failed password" /var/log/auth.log /var/log/secure 2>/dev/null | tail -5

echo -e "\n[8] ファイアウォールの状態"
sudo ufw status 2>/dev/null || sudo firewall-cmd --state 2>/dev/null

echo -e "\n監査完了"

# リモートサーバーのセキュリティ変更チェックリスト - SSH・ファイアウォール・PAM

基準日: 2026-09-29
出典: OpenSSH 7.4 リリースノート、sshd(8)、sshd_config(5)、ufw(8)、Linux-PAM 1.5.0 リリースノート、faillock.conf(5)、DNF Automatic ドキュメント、Greenbone Community Containers ドキュメント

---

## 1. 変更前（SSH・ファイアウォール・PAM 共通）

- [ ] 現在接続中のセッションは、テストが終わるまで閉じない
- [ ] コンソール（仮想マシンコンソール・IPMI）へのアクセス手段があることを確認した
- [ ] 編集するファイルをバックアップした（`cp -a ファイル ファイル.bak`）

## 2. SSH 設定変更の順序

| 順序 | 作業 | コマンド |
|---|---|---|
| 1 | バックアップ | `sudo cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak` |
| 2 | 構文チェック（出力がなければ正常） | `sudo sshd -t` |
| 3 | 実効設定の確認 | `sudo sshd -T` |
| 4 | 再起動（Debian/Ubuntu は ssh、RHEL系は sshd） | `sudo systemctl restart ssh` |
| 5 | 実際に待ち受けているポートの確認 | `sudo ss -tlnp` |
| 6 | 新しいターミナルで接続テスト | `ssh -p ポート ユーザー@サーバー` |
| 7 | 失敗したら既存セッションで巻き戻し | `.bak` を戻して再起動 |

- [ ] パスワード認証を無効にする前に、新しいセッションで鍵ログインが成功した
- [ ] `Protocol 2` の行は入れない（OpenSSH 7.4 が SSH v1 サーバーサポートを削除）

## 3. SSH ポートを変更する場合（順序が重要）

- [ ] ファイアウォールに新しいポートを先に開ける（UFW: `ufw allow`、firewalld: `--permanent` の後 `--reload`）
- [ ] RHEL系は SELinux ポートラベルを付ける（`semanage port -a -t ssh_port_t -p tcp ポート`）
- [ ] その後に sshd を再起動する
- [ ] UFW は `ufw enable` より先に SSH 許可ルールを入れる（enable が既存接続を切ることがある）

## 4. ログイン失敗ロック

| 項目 | 値 |
|---|---|
| `pam_tally2` | Linux-PAM 1.5.0 で削除 - 使わない |
| 後継 | `pam_faillock`（設定 `/etc/security/faillock.conf`） |
| 既定値 | deny 3回 / fail_interval 900秒 / unlock_time 600秒 |
| root | 既定ではロックされない（`even_deny_root` で変更） |

- [ ] リモートの root をロックする前にコンソールアクセスを確認した
- [ ] PAM ファイルを編集した後、別のアカウントでログインして試した

## 5. 自動アップデート（RHEL系）

- [ ] インストールまで自動化するには `dnf-automatic-install.timer` を有効にする
- [ ] `dnf-automatic.timer` だけでは `apply_updates` の既定値（False）のためインストールされない

## 6. ディストリビューションで異なる点

| 項目 | Debian/Ubuntu | RHEL系 |
|---|---|---|
| SSH サービス名 | `ssh` | `sshd` |
| 認証ログ | `/var/log/auth.log` | `/var/log/secure` |
| ジャーナルのみのシステム | `journalctl -u ssh` | `journalctl -u sshd` |
| fail2ban のジャーナル利用 | `backend = systemd` | 同じ |

コピーしてメモアプリやAIツールにそのまま貼り付けてください。
