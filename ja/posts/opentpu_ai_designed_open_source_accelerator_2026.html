きっかけ — 「AIが開発したアクセラレータ」という一行が述べている範囲

openTPUリポジトリのREADMEは、最初の行でこのプロジェクトを「AIが開発したオープンソースのAIアクセラレータ(An open-source AI accelerator, developed by AI)」と紹介している。続く文は、プロジェクトが投げかける二つの問いである。AIエージェントはハードウェア設計でどこまで行けるのか、そしてエージェントは自分自身の推論を動かすチップを作れるのか。READMEは、このプロジェクトが前作auto-arch-tournamentで得た教訓をAIアクセラレータに持ち込んだものであると書いている。GeekNewsには2026年10月7日に紹介された。

この一行は広く読まれやすい。READMEが「開発した」という言葉に添えている説明は、上の二つの文がすべてである。エージェントがどの部分を書き、人間が何をしたのか、どのエージェントとモデルを使ったのかは、READMEには出てこない。したがって「AIが単独でチップを設計した」という文はREADMEからは出てこない。READMEに「チップ」という語が現れるのは上の問いの一か所だけであり、結果の節が述べている対象はFPGAカードの上で動く設計である。設計はInspur YPCB-00338カード(Xilinx Kintex-7 xc7k480t、DDR3の2チャネル)の上で、実際の重みを使うモデル10種を動かす。製造されたASICやテープアウトについての記述はREADMEにない。

READMEが実際に示しているものは三つである。

  • リポジトリ: アクセラレータ全体が、最初から最後まで読み通せる小さなモノレポ一つに収まっている。
  • 測定: カードで測ったデコードとプリフィルの速度、DRAM帯域幅が、モデル別・量子化別の表として掲載されている。
  • 検証: カードはシミュレータと同じトークンをビット単位で出す。

リポジトリにあるもの — 設計・命令セット・シミュレータ・コンパイラ・ホスト

READMEはopenTPUを学習用のプロジェクトでもあると紹介している。リポジトリには、ハードウェア設計(SystemVerilog)、命令セット、ビット単位で正確な(bit-exact)シミュレータ、カーネル言語とそのコンパイラ、実際のPCIeカードを駆動するホストソフトウェアが一緒に入っている。Pythonの行列積から配線に至るまで、AIアクセラレータがどのように動くのかを知りたいのであれば良い出発点になる、というのがREADMEの説明である。

構成要素 リポジトリ内の場所 READMEが書いている役割
カーネル opentpu/kernels ol言語で書かれたmlp、attention、モデルの層全体。@ol.jitデコレータが付く

READMEの構造図は、これらの層を上から下へ描いている。

  Kernels in ol              mlp, attention, full model layers
                            |  @ol.jit
                      Language + compiler        layouts, affine loop addressing, fusion
                            |
                      ISA                        8 x 32-bit words per instruction
                            |
                      ISA simulator  <======>  RTL          same bits, checked by the tests
                      (Python)                 (SystemVerilog)
                                                |  Vivado bitstream
                                               FPGA card    Kintex-7 xc7k480t
                                                |  PCIe
                                               Host         otpu-chat, otpu-smi, otpu-lens

このマシンは意図的に単純に作られている、とREADMEは書いている。シーケンサがサイクルごとに一つの命令をいくつかのユニットに発行する。DMAはデータを動かし、行列ユニットはDRAMからストリーミングされるint8の重みを乗算し、ベクトルユニットはfp32の演算を行い、量子化器は結果を再びint8に戻す。キャッシュも隠れたスケジューリングもない。すべてのデータ移動が命令であるため、実行トレースがサイクルの行き先をそのまま示す、という説明である。READMEに掲載されているカーネルの例は次のとおりである(簡略化したものであり、元のコードはkernels/mlp.pyにあるとコメントが述べている)。

from opentpu import language as ol
                    
                    @ol.jit
                    def mlp(h, gamma, w_gate, w_up, w_down, out, eps):   # simplified; see kernels/mlp.py
                        x = ol.load(h)
                        xs = ol.quantize(rmsnorm(x, ol.load(gamma), eps))
                        g = ol.dot(xs, w_gate)
                        u = ol.dot(xs, w_up)
                        a = ol.all_gather(silu(g) * u)
                        y = ol.all_gather(ol.dot(a, w_down))
                        if ol.program_id() == 0:
                            ol.store(out, x + y)

プロファイラのLensは、RTL、シミュレータ、カードのいずれの実行でも記録し、ブラウザでルーフライン、タイムライン、命令ごとの表として開く。ホストのコマンドはREADMEの表で四つにまとめられている。

  • otpu-chat: モデルと対話する。Qwen3-0.6Bが既定であり、--modelでlfm2(LFM2.5-230M)、qwen35(Qwen3.5-0.8B)、lfm2-2.6b、smollm3、phi4-mini、qwen35-2b、qwen35-4bを選ぶ。
  • otpu-smi: 温度、電力、DRAM帯域幅、ユニットごとの使用率を表示する。
  • otpu-lens: 実行を記録してプロファイラで開く。
  • otpu-selftest、otpu-diag: カードが動作するかどうかを点検する。

カードとビルド — Inspur YPCB-00338、Kintex-7、DDR3の2チャネル

測定が行われたハードウェアはFPGAカードである。READMEの結果の節とdocs/board.mdが書いている構成は次のとおりである。

  • カード: Inspur YPCB-00338。FPGAはXilinx Kintex-7 xc7k480t(board.mdの表記ではxc7k480t-ffg1156-2)であり、DDR3が2チャネル、それぞれ2 GiBずつ載っているため、カードのメモリは4 GiBである。
  • イメージ: main e698dcd、133.33 MHzで、すべてのモデルに対してビットストリームは一つである。メモリコア内の小さなCPUが較正するLiteDRAMコントローラ、4列のシストリック行列ユニット、ストリームエンジンが入っている。
  • メモリ速度: DDR3-1066で、ピークは17.1 GB/sである。board.mdはこのピークをx64チャネル二つの合計(ECCビットは数えない)として計算し、17.07 GB/sと書いている。
  • ホスト: カードはopentpuという名前のPC(Intel Core i7-4790)に挿さっており、リンクはXilinx XDMAを使うPCIe Gen2 x8である。
  • タイミング: 設計は133.33 MHzを閉じているが、READMEの表現では「かろうじて」である(WNS +0.032 ns)。133.33 MHzは、128バイトのポートがDDR3の2チャネルと釣り合うクロックである。
  • 較正: イメージが起動すると、コアのCPUがホストの関与なしにDDR3の2チャネルを12秒で較正する。

ビットストリームのビルドには条件が付く。board.mdによれば、xc7k480tを含むライセンスのあるVivado 2026.1が必要であり、無料版にはこのデバイスが含まれていないため、有料ライセンスかAMDの30日間評価ライセンスを使わなければならない。1回のビルドに1.5〜3時間を見込むようにと書かれている。FPGAの上にハードウェアをSystemVerilogで載せた別の事例はFPGAで再現した3dfx Voodoo GraphicsとDOS PCにまとめてある。

「トークン単位の一致」が指すもの — シミュレータ対カード

READMEの結果の節の最初の文は、カードがシミュレータと同じトークンをビット単位で(bit for bit)出すというものである。表の下の注記はこれをさらに絞って書いている。すべての構成が、位置ごとに、そして常駐デコードプログラムで動かした場合にも、シミュレータとトークン単位で一致する。

この文で比べられている二つは、カードとシミュレータである。docs/isa.mdはISAの文書を、コンパイラ、ビット単位で正確な命令セットシミュレータ、RTLの三者のあいだの契約と呼び、三者はTMEMまたはDRAMに書かれるすべてのビットで一致しなければならないと書いている。READMEがシミュレータを「仕様そのもの」と呼ぶ理由はここにある。一致は次の範囲で読む。

  • 何の検証か: ハードウェアの実装(RTLとカード)が仕様(シミュレータ)と同じ結果を出すことの検証である。モデルが出す答えの品質や正確さについての主張ではない。
  • なぜ可能か: isa.mdは、fp32の算術をIEEE-754 binary32、最近接偶数への丸め、ゼロへのフラッシュとして規定し、合成関数をaddとmulの固定された順序として定義することで、あらゆる実装がビット単位で同じになるようにしていると書いている。
  • 別の照合: 一部のモデルには、Hugging Faceの実装との照合が別に書かれている。Gemma 4 E2Bは三つのプロンプトでHugging Faceのグリーディトークンと一致し、Qwen3.5-35B-A3BはHugging Faceのグリーディトークン16個と一致する。書かれているプロンプトの数とトークンの数が、その照合の範囲である。
  • 品質側の数値: 量子化がモデルの出力に与える影響は、docs/quant.mdがパープレキシティとして別に報告している。

貢献の規則も同じ線の上にある。ISA、シミュレータ、RTLへの変更はpython3 -m pytest -qが通る状態を保たなければならず、性能についての主張はどのように測ったのかを述べなければならない。

4ビットの重みと4 GiBを超えるモデル — 速度とその代償

4ビットの重みは、FP4の値に2段階のブロックスケールを付けた形式で、重みあたり4.25ビットになり、精度のためにLMヘッドはint8のまま残される。READMEによれば、トークンあたりのバイト数が約3分の1減り、デコード速度が40%(Qwen3.5)から45%(Qwen3、LFM2)上がる。表の中でLFM2.5-230Mのデバイスデコードが59.0から85.8 tok/sへ、Qwen3-0.6Bが21.6から31.3 tok/sへ上がっているのがその値である。代償はパープレキシティであり、READMEは「測定可能なコスト」と書いて、モデルごとの数値をdocs/quant.mdに委ねている。quant.mdは、Qwen3-0.6Bで書籍サンプルのパープレキシティがfp32とint8の23.5から4ビットの28.3に上がると書いている(シミュレーションで測った値)。

カードが動いているあいだにロジットをストリーミングで返してもらうと(tools/decode_profile.py、96トークン)、4ビットのデコードはさらに速い。デバイス/ウォールのtok/sで、LFM2が89.5/84.5、Qwen3が33.7/33.3、Qwen3.5が24.6/24.2である。

カードの4 GiBより大きいMoE(混合エキスパート)モデルは、エキスパートの重みをホストのストレージからストリーミングして動かす。カードがトークンごとにルーティングを行い、すべてのエキスパートを計算し、エキスパートをDRAM内の層ごとのスロットに保持する。ホストは、欠けているエキスパートをプールファイルからスロットへコピーするだけである。2026年10月1日にビルドBで、カード自身のデコードループがすべてのトークンを選び、エキスパートは4ビット、ヘッドはint8という条件で測った値は次のとおりである。

  • LFM2.5-8B-A1B(8.5Bパラメータ、アクティブ1.7B): 160トークンにわたって10.6 tok/sである。エキスパート使用の98.5%がスロットにヒットし、トークンあたり5.2 MBがストリーミングされた。
  • Qwen3.5-35B-A3B(34.7Bパラメータ、アクティブ3.0B): 3.95 tok/sである。エキスパート使用の62%がヒットし、トークンあたり153 MBがPCIe経由で1.41 GB/sでストリーミングされた。
  • 検証: 二つのモデルはどちらもシミュレータとビット単位で一致する。

ホストの取り分は小さい。LFM2とQwen3では、カードが一度だけコンパイルされた一つのデコードプログラムを動かし、ホストがトークンあたりに加える時間は、開発用PCであるomarchyで0.17〜0.30 ms、opentpuで0.45〜1.3 msである。Qwen3.5もデコードは同じ方式で動くが、プリフィルは今もチャンクごとのプログラムをホスト側でコンパイルしている。

再現手順と前作auto-arch-tournament

READMEは、カードを除くすべてがノートPCで動くと書いている。試してみるための節にあるコマンドは次のとおりである。

pip install -e .
                    pip install pytest torch transformers
                    python3 -m pytest -q          # RTL tests also need Verilator 5
                    
                    hf download LiquidAI/LFM2.5-230M --local-dir models/LFM2.5-230M
                    otpu-chat --model lfm2 --backend isa    # chat on the simulator

カードがある場合は、boards/ypcb-00338でmake bitによりビットストリームをビルドしてJTAGでロードし、そのあとsudo otpu-setupとotpu-chat --backend boardを実行する。手順の全体はdocs/board.mdにある。貢献の節は、作業の大部分がFPGAなしでPythonとVerilatorだけで行えると書いている。ライセンスはApache License 2.0である。

前作auto-arch-tournamentのREADMEは、そのプロジェクトをSystemVerilogのRV32IM CPUに向けた自律的な研究ループとして紹介している。ラウンドごとにエージェントがマイクロアーキテクチャの仮説を出し、隔離されたgitワークツリーで実装し、riscv-formalとVerilatorによる協調シミュレーション、3シードのFPGA配置配線を通す。現在のチャンピオンをCoreMark/MHzで上回った仮説だけがマージされる。そのREADMEが書いている内容は次のとおりである。

  • 結果: 仮説73個、実時間で9時間51分である。基準線の301 iter/s(2.23 CoreMark/MHz)から、チャンピオンの577 iter/s(2.91 CoreMark/MHz)に達した。採用されたものが10個、検証器が棄却したものが63個である。
  • エージェントが触れられる範囲: 対象コアのrtl/とtest/test_*.pyだけである。オーケストレータはハードコードされており、モデルはそれを編集できない。
  • 評価側は範囲外: エージェントがformal/、tools/、fpga/などに触れると、パスのサンドボックスが評価を走らせる前にそのラウンドを棄却する。READMEは、エージェントは自分の採点器を甘くすることができないと書いている。
  • 作者の結論: ループは堀ではなく、63回の棄却を越えて10回の勝利として生き残った成果物は、エージェントではなく検証器だったというものである。
  • エージェント: Codex CLIが既定であり、Claude Codeも使える。

openTPUのREADMEが前作について書いているのは、その教訓をAIアクセラレータに持ち込んだという一文である。同じループと同じサンドボックスの規則でopenTPUを作ったのかどうかは、READMEに書かれていない。ただし、READMEの今後の課題には、Vivadoの実行のトーナメントがタイミングの余裕と面積を引き続き詰めているという文がある。LLMをチップ設計に使った別の事例と、そこでの人間の関与の範囲はOpenAIによる独自LLM活用Jalapeñoチップ分析にまとめてある。

項目 READMEと文書に書かれていること 書かれていないこと
開発の主体 「developed by AI」、エージェントがハードウェア設計でどこまで行けるのかを問うプロジェクト 人間とエージェントの分担、使用したエージェントとモデル、人間が書いた部分の割合
実装の形態 FPGAカード(Inspur YPCB-00338、Kintex-7 xc7k480t)の上で動くSystemVerilogの設計とビットストリーム ASICの製造、テープアウト
検証 すべての構成でのカードとシミュレータのトークン一致、一部のモデルでのHugging Faceのグリーディトークンとの一致 モデルの出力の品質評価(4ビットのパープレキシティのコストはdocs/quant.mdに別途)
性能 230M〜3.8B級のモデルのtok/s、自分の以前のイメージ(se-cand3)との比較 GPUやほかのアクセラレータとの比較、電力あたりの性能
再現 カードなしでノートPC上のシミュレータとテスト、カードがあればビットストリームのビルド ほかのFPGAボードへの移植

確認できなかったこと

  • 人間とエージェントの分担。 README、board.md、isa.md、quant.mdの中に、誰がどの部分を書いたのかについての記述は見つからなかった。使用したエージェントとモデルの名前、開発期間についても同じである。
  • 前作のループをそのまま使ったのかどうか。 openTPUのREADMEは教訓を持ち込んだと書いているだけである。仮説の数や棄却の数のような実行記録は、openTPU側の文書では確認できなかった。
  • 電力。 otpu-smiが電力を表示すると書かれているが、READMEにカードの実測電力の数値はない。board.mdにあるVivadoの電力見積もりは以前のビルドに対する値であり、「信頼度が低い」という但し書きが付いているため、引き写していない。
  • ほかのハードウェアとの比較。 GPU、CPU、ほかのアクセラレータと同じモデルで比べた数値はREADMEにない。
  • モデルごとの品質の数値。 quant.mdにあるモデルごとのパープレキシティの表の全体と、表に出てくるモデルの出力品質の評価は引き写していない。Qwen3-0.6Bの値一つだけを引用した。
  • カードの入手経路と価格。 READMEにもboard.mdにも書かれていない。
