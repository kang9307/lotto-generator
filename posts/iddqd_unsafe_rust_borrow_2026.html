서론: 왜 '값에서 키를 빌리는' 맵이 어려운가

Rust를 어느 정도 써 본 사람이라면 누구나 한 번쯤 빌림 검사기(borrow checker)와 싸워 본 경험이 있습니다. 대부분의 싸움은 코드를 조금 바꾸면 풀립니다. 그런데 어떤 문제는 아무리 코드를 비틀어도 안전한 Rust 문법만으로는 끝내 표현되지 않습니다. iddqd라는 작은 맵 라이브러리가 다루는 문제가 정확히 그 부류입니다. iddqd는 "값 안에 들어 있는 필드를 키로 빌려와 인메모리 인덱싱을 한다"는, 겉보기엔 평범한 요구를 풉니다. 그러나 그 평범함의 이면에는 Rust에서 가장 까다로운 unsafe 주제들 — 자기참조 구조, 이동(move)과 댕글링, Pin, 그리고 안전 캡슐화 — 가 모두 응축되어 있습니다.

이 글은 2026년 6월 초 news.hada.io에서 화제가 된 'iddqd: 가장 어려운 종류의 unsafe Rust' 토픽을 출발점으로 삼되, 원문을 직역하지 않고 본인이 정리한 관점에서 이 문제를 차근차근 해부합니다. 참고로 라이브러리 이름 iddqd는 고전 게임 둠(DOOM)의 무적 치트 코드에서 따온 것으로 보이는데, "버그에 무적인 인덱스"라는 농담 섞인 자부심이 느껴집니다. 정말로 무적인지, 그리고 그 무적이 어떤 대가를 치르고 얻어지는지를 들여다보겠습니다.

1. borrow-from-value - 문제를 정확히 정의하기

먼저 문제를 흐릿하지 않게 정의해야 합니다. 우리가 어떤 객체 목록을 메모리에 들고, 그것을 빠르게 조회하고 싶다고 합시다. 흔한 방법은 키-값 맵입니다. 그런데 많은 실무 상황에서 키는 이미 값 안에 들어 있습니다. 예를 들어 사용자 구조체는 id 필드를 가지고 있고, 우리는 그 id로 사용자를 찾고 싶습니다.

struct User {
    id: u64,        // 이 필드가 곧 키다
    name: String,
    addr: String,
}

일반 HashMap<u64, User>를 쓰면 키 id를 맵의 키 슬롯에 한 번, 값 User.id에 또 한 번 — 같은 값을 두 군데 저장하게 됩니다. 사소해 보이지만 두 가지가 거슬립니다. 첫째, 중복 저장입니다. 둘째, 그리고 더 본질적으로, 키와 값이 따로 놀면 둘이 어긋날 여지가 생깁니다. 누군가 값의 id를 바꾸면 맵의 키와 불일치가 됩니다.

borrow-from-value는 이 중복을 없애려는 발상입니다. 키를 따로 복제해 저장하지 말고, 값 안의 필드를 직접 키로 빌려(borrow) 인덱스를 만들자는 것입니다. 개념적으로는 맵이 User를 소유하고, 동시에 그 User.id를 가리키는 참조로 해시 테이블을 구성합니다. 바로 이 "소유하면서 동시에 내부를 참조한다"가 Rust에서 가장 다루기 까다로운 구조의 씨앗입니다.

2. 일반 HashMap과 무엇이 다른가

표준 라이브러리의 HashMap은 키와 값을 별개의 소유 데이터로 봅니다. 키를 넣을 때 보통 키를 복제하거나 소유권을 넘기죠. 이 모델은 단순하고 안전하지만, 앞서 본 '키가 값 안에 있는' 상황에는 잘 맞지 않습니다.

구분일반 HashMapborrow-from-value 맵(iddqd류)
키 저장값과 별도로 복제·소유값 내부 필드를 빌려서 사용
중복키가 값 안에도 있으면 중복중복 없음(단일 소유)
일관성키-값 어긋날 여지키가 곧 값이라 어긋나지 않음
다중 키인덱스마다 별도 맵 필요한 값에 여러 키 인덱스 부착
구현 난이도안전 Rust로 간단내부 unsafe 필요

핵심 차이는 마지막 두 줄입니다. borrow-from-value 맵은 한 값에 여러 키 인덱스를 동시에 붙일 수 있고(예: id로도 name으로도 조회), 대신 그 편의를 얻기 위해 내부에서 unsafe를 감수합니다. iddqd가 제공하는 가치는 "이 unsafe를 사용자가 직접 쓰지 않도록 라이브러리가 대신 책임지고 캡슐화한다"는 데 있습니다.

3. 자기참조 구조가 위험한 이유

왜 unsafe가 불가피한지 한 단계 더 들어가 봅니다. 맵이 User를 소유하면서 그 User.id를 가리키는 포인터로 해시 버킷을 구성한다는 것은, 데이터 구조 안에 자기 자신을 가리키는 참조가 생긴다는 뜻입니다. 이것이 자기참조 구조(self-referential struct)입니다.

// 개념적 형태 (그대로는 컴파일되지 않는다)
struct Index {
    storage: Vec<User>,        // 값을 소유
    by_id: HashMap<&u64, usize>, // storage 내부의 id를 빌림
}

이 코드가 컴파일되지 않는 이유는 빌림 검사기 입장에서 by_id의 참조 수명을 표현할 방법이 없기 때문입니다. by_id는 storage가 살아 있는 동안만 유효한데, 둘이 같은 구조체 안에 있으면 "이 참조는 같은 구조체의 다른 필드만큼 산다"는 수명을 Rust 타입 시스템으로 적을 수 없습니다. Rust의 수명 표기는 구조체 외부의 데이터를 가리킬 때를 전제로 설계되어 있어서, 자기 내부를 가리키는 순환은 정적으로 증명이 안 됩니다.

안전한 Rust가 자기참조를 거부하는 것은 결함이 아니라 정직함이다. 컴파일러는 "나는 이 참조가 안전하다고 증명할 수 없다"고 솔직하게 말하는 것뿐이다.

그래서 선택지는 둘입니다. 참조 대신 인덱스(usize)를 키로 쓰는 우회(안전하지만 한 단계 간접 비용), 또는 raw 포인터와 unsafe로 자기참조를 직접 표현하되 그 안전을 사람이 책임지는 길. iddqd 같은 라이브러리는 성능과 인체공학을 위해 후자를 택하고, 그 위험을 좁은 unsafe 코어 안에 가둡니다.

4. move와 댕글링 - 가장 미묘한 함정

자기참조의 진짜 무서운 점은 컴파일 시점이 아니라 런타임에 있습니다. 핵심 단어는 이동(move)입니다. Rust에서 값은 기본적으로 이동 가능하고, 이동은 대개 메모리상 바이트 복사로 이뤄집니다. 값이 새 주소로 옮겨지면, 그 값 내부를 가리키던 raw 포인터는 옛 주소를 그대로 가리킨 채 남습니다. 그 순간 포인터는 댕글링(dangling)이 되고, 역참조하면 미정의 동작(UB)입니다.

// 왜 위험한가 - 의사 코드
let mut v = vec![user];          // user가 힙 버퍼 A에 있음
let p: *const u64 = &v[0].id;    // A 내부를 가리킴
v.push(other);                   // 용량 초과 → 힙 버퍼 B로 재할당(이동!)
// 이제 v[0]은 B에 있는데, p는 여전히 A를 가리킨다 → 댕글링
unsafe { let _ = *p; }           // UB: 해제된 메모리 역참조

이 예시가 보여주듯, Vec의 재할당 한 번만으로도 내부 포인터가 통째로 무효화됩니다. 자기참조 자료구조를 만들 때 가장 흔하고 가장 잡기 어려운 버그가 바로 이것입니다. 컴파일은 멀쩡히 되고, 작은 입력에서는 우연히 동작하다가, 특정 크기에서 재할당이 일어나는 순간 메모리 손상이 터집니다.

주의 - 이런 버그는 디버그 빌드에서 운 좋게 살아남고 릴리스 빌드에서 터지거나, 그 반대로 나타나기도 합니다. "내 환경에서는 잘 되는데요"가 가장 위험한 문장이 되는 영역입니다.

5. Pin의 역할과 한계

이동이 문제라면, 해법의 한 축은 명확합니다. 값이 이동하지 못하게 고정하는 것. 이를 위해 Rust 표준 라이브러리는 Pin이라는 타입을 제공합니다. Pin<P>는 가리키는 대상이 메모리상에서 더 이상 옮겨지지 않음을 타입 수준에서 약속합니다. 자기참조 구조가 한 번 올바른 자리에 자리잡으면, Pin이 그 자리를 지켜 내부 포인터가 계속 유효하도록 돕습니다.

다만 본인이 강조하고 싶은 것은 Pin이 만능 안전장치가 아니라는 점입니다. Pin이 보장하는 것은 "안전한 코드에서는 대상을 이동시킬 수 없다"는 제약일 뿐, 자기참조 포인터를 올바르게 설정하고 유지하는 책임은 여전히 unsafe를 쓰는 사람에게 있습니다. Unpin이 아닌 타입을 다루고, get_unchecked_mut 같은 unsafe 통로를 정확한 불변식 아래에서만 쓰는, 까다로운 규칙의 집합입니다.

use std::pin::Pin;
use std::marker::PhantomPinned;

struct SelfRef {
    data: String,
    // data를 가리키는 포인터(개념)
    slice: *const u8,
    _pin: PhantomPinned, // Unpin이 아니게 만들어 이동을 막는 표식
}

실무에서 Pin을 손으로 다루는 코드는 악명 높게 어렵습니다. 그래서 많은 라이브러리가 Pin을 직접 노출하는 대신, 자기참조의 위험을 라이브러리 내부에 숨기고 사용자에게는 평범한 맵 API만 보여 줍니다. iddqd의 가치도 정확히 이 '숨김'에 있습니다. 사용자는 insert·get만 호출하고, Pin과 raw 포인터의 지옥은 라이브러리가 짊어집니다.

6. iddqd의 설계 아이디어

그렇다면 iddqd는 이 문제를 어떻게 푸는가? 공개된 정보와 일반적인 borrow-from-value 맵의 설계 원리를 바탕으로, 본인이 이해한 핵심 아이디어를 정리합니다. (세부 구현은 버전에 따라 다를 수 있으므로 원리 수준으로 봅니다.)

6-1) 값은 한 번만 소유한다

맵은 각 값을 단 한 곳에 안정적으로 보관합니다. 값이 한 번 자리잡으면 그 주소가 흔들리지 않도록 저장 전략을 설계합니다(예: 안정적 주소를 보장하는 할당 방식). 이 '주소 안정성'이 자기참조 포인터를 유효하게 유지하는 토대입니다.

6-2) 키는 값에서 빌려 인덱스를 만든다

사용자는 "이 값에서 키를 어떻게 뽑는가"를 트레이트로 알려 줍니다. 맵은 삽입 시 그 규칙으로 값에서 키를 빌려 해시하고, 내부 인덱스에 등록합니다. 키를 따로 복제·소유하지 않으므로 중복이 사라지고, 키와 값이 어긋날 수 없습니다.

6-3) unsafe는 좁은 코어에 가둔다

raw 포인터와 자기참조의 위험은 라이브러리의 작은 핵심에만 존재하고, 그 위에 100% 안전한 공개 API를 올립니다. 사용자 코드에는 unsafe가 한 글자도 등장하지 않습니다.

// 개념적 사용 예 (API는 버전에 따라 다름)
let mut map = IdHashMap::new();
map.insert(User { id: 1, name: "kim".into(), addr: "10.0.0.1".into() });
map.insert(User { id: 2, name: "lee".into(), addr: "10.0.0.2".into() });

// 값 안의 id를 키로 빌려 조회 - 사용자에겐 평범한 맵
if let Some(u) = map.get(&1) {
    println!("{} @ {}", u.name, u.addr);
}
핵심 - 좋은 unsafe 라이브러리의 미덕은 "위험을 없앤다"가 아니라 "위험을 좁은 곳에 가두고, 그 경계 밖에서는 안전을 보증한다"입니다. iddqd가 노리는 지점이 바로 이 경계 설계입니다.

7. 다중 키 인덱싱과 컨트롤 플레인

borrow-from-value의 진가는 다중 키 인덱싱에서 드러납니다. 같은 값을 여러 키로 동시에 조회하고 싶을 때, 보통은 인덱스마다 별도의 맵을 손으로 유지합니다. 문제는 삽입·삭제·수정 때마다 모든 맵을 빠짐없이 갱신해야 한다는 점이고, 하나라도 빠지면 인덱스가 깨집니다.

// 손으로 다중 인덱스를 유지하면 동기화 지옥
by_id.insert(u.id, u_ref);
by_name.insert(u.name.clone(), u_ref);
by_addr.insert(u.addr.clone(), u_ref);
// 삭제할 때 셋 중 하나라도 빠뜨리면 → 유령 엔트리, 메모리 누수, 잘못된 조회

borrow-from-value 맵은 값을 한 번만 저장하고 여러 키 인덱스를 그 위에 부착하므로, 삽입·삭제가 자동으로 모든 인덱스에 일관되게 반영됩니다. 이 특성이 빛나는 대표 무대가 컨트롤 플레인입니다. 컨트롤 플레인은 클러스터 노드, 서비스, 엔드포인트 같은 메타데이터를 메모리에 들고, 같은 객체를 ID로도·이름으로도·네트워크 주소로도 즉시 찾아야 합니다.

  • 서비스 디스커버리: 서비스 이름과 인스턴스 ID 양쪽으로 동일 객체 조회
  • 노드 레지스트리: 노드 UUID, 호스트명, IP를 모두 키로 사용
  • 스케줄러 상태: 작업 ID와 할당 노드를 교차 조회

이런 시스템은 조회가 매우 빈번하고, 인덱스 불일치가 곧 장애로 이어집니다. 그래서 "한 번 저장, 여러 키, 자동 일관성"이라는 iddqd류의 보증이 단순한 편의가 아니라 정확성의 안전장치가 됩니다. Rust로 컨트롤 플레인을 짜는 팀이 이런 라이브러리에 매력을 느끼는 이유입니다. Rust 시스템 도구의 더 넓은 맥락은 sshc - Rust SSH 매니저 2026에서도 다룹니다.

8. unsafe 캡슐화 - 좋은 unsafe와 나쁜 unsafe

unsafe라는 단어에 과민 반응할 필요는 없습니다. Rust의 표준 라이브러리부터가 내부에 방대한 unsafe를 품고 있고, Vec·String도 raw 포인터 위에 안전 API를 올린 구조입니다. 중요한 것은 unsafe의 유무가 아니라 설계 품질입니다.

본인이 보는 '좋은 unsafe'의 조건은 다음과 같습니다.

  • 좁은 면적: unsafe 블록이 라이브러리의 핵심 몇 곳에만 격리되어 있을 것
  • 명문화된 불변식: 각 unsafe가 의존하는 안전 조건이 주석·문서로 분명히 적혀 있을 것
  • 안전한 경계: 공개 API는 어떤 입력에도 UB를 일으키지 않을 것(soundness)
  • 검증 흔적: Miri·퍼징·테스트로 그 불변식을 실제로 두드려 봤을 것

반대로 '나쁜 unsafe'는 면적이 넓고, 불변식이 머릿속에만 있으며, 공개 API가 특정 사용 패턴에서 UB로 새는 경우입니다. iddqd 같은 라이브러리를 평가할 때 본인이 먼저 보는 것은 기능 목록이 아니라 unsafe 면적과 검증 흔적입니다. 이 관점은 메모리 안전을 위해 C를 Rust로 다시 쓰는 더 큰 흐름과도 맞닿아 있는데, 자세한 맥락은 Rust로 구현한 Zstandard 2026에서 정리했습니다.

9. 검증 도구 - Miri, 퍼징, RustSec

unsafe 코드는 컴파일러가 안전을 보장하지 않으므로, 작성자가 도구로 안전을 입증해야 합니다. 자기참조·raw 포인터를 다루는 라이브러리라면 더더욱 그렇습니다. 본인이 신뢰의 근거로 삼는 세 가지 도구를 정리합니다.

9-1) Miri - 미정의 동작 탐지기

Miri는 Rust 코드를 중간 표현(MIR) 수준에서 해석 실행하며, 댕글링 참조·정렬 위반·해제 후 사용 같은 UB를 잡아냅니다. cargo +nightly miri test 한 줄로 테스트를 Miri 위에서 돌릴 수 있습니다. 자기참조 자료구조의 포인터 규칙 위반은 Miri가 가장 잘 잡는 부류입니다.

# Miri로 테스트 실행 (nightly 필요)
rustup +nightly component add miri
cargo +nightly miri test

9-2) 퍼징과 프로퍼티 테스트

cargo-fuzz로 무작위 입력을 대량 생성해 경계 조건을 두드리고, proptest·quickcheck로 "어떤 삽입·삭제 순서에도 인덱스가 일관되다" 같은 불변식을 자동 검사합니다. 자기참조 맵에서는 특히 재할당을 유발하는 대량 삽입 시나리오를 집중적으로 두드려야 합니다.

9-3) RustSec과 cargo-audit

의존성에 알려진 취약점이 있는지는 cargo audit으로 RustSec 권고 DB와 대조합니다. unsafe를 품은 라이브러리를 채택할 때, 과거에 보고된 soundness 이슈가 있었는지, 어떻게 패치됐는지를 확인하는 것은 기본 위생입니다.

10. 직접 구현할 때의 함정

"별거 아닌 것 같은데 직접 짜면 안 되나?"라는 유혹이 들 수 있습니다. 본인 경험상 자기참조 맵을 직접 구현하려다 빠지는 대표적 함정은 다음과 같습니다.

  1. Vec 재할당 간과: 4장에서 본 그대로입니다. 요소를 더 넣다 용량이 초과되면 버퍼가 통째로 이동해 모든 내부 포인터가 무효화됩니다. Vec 대신 주소가 안정적인 컨테이너가 필요합니다.
  2. drop 순서 오류: 자기참조 구조는 필드의 해제 순서가 잘못되면 이미 해제된 메모리를 가리키는 포인터가 잠깐 살아남습니다. Drop 구현에서 미묘한 UB가 숨습니다.
  3. 가변 별칭(aliasing) 위반: 같은 데이터에 가변 참조와 다른 참조가 동시에 존재하면 Rust의 별칭 규칙(특히 stacked/tree borrows 모델)을 위반해 최적화가 코드를 망가뜨릴 수 있습니다.
  4. 변경 시 인덱스 갱신 누락: 키가 되는 필드가 바뀌면 인덱스도 갱신해야 하는데, 안전 API로 이를 막지 않으면 조용히 깨집니다. 그래서 좋은 설계는 키 필드를 불변으로 다룹니다.

이 목록만 봐도, 이미 검증된 라이브러리를 쓰는 편이 거의 항상 합리적임을 알 수 있습니다. 본인 추천은 "정말로 핫패스이고, 직접 측정해 병목이 확인됐을 때만" 자체 구현을 고려하고, 그 경우에도 반드시 Miri와 퍼징을 붙이라는 것입니다.

11. 한국 개발 환경에서의 시사점

이 주제는 니치하지만, 한국 개발 현실에 비춰도 몇 가지 분명한 시사점이 있습니다.

11-1) Rust 인프라 도입이 늘고 있다

국내에서도 네트워크 프록시, 스토리지 엔진, 쿠버네티스 주변 컨트롤 플레인을 Rust로 작성하는 사례가 늘고 있습니다. 이런 시스템일수록 인메모리 인덱스의 정확성과 성능이 직접 안정성으로 이어지므로, borrow-from-value 맵의 가치를 체감하기 쉽습니다.

11-2) unsafe 리뷰 역량이 자산이 된다

Rust를 쓰는 팀이 늘면서 "unsafe를 읽고 평가하는" 역량의 희소가치가 커집니다. 라이브러리의 unsafe 면적을 가늠하고, Miri·퍼징 흔적을 점검하고, soundness 경계를 따지는 시니어의 안목은 그대로 채용·코드 리뷰의 무기가 됩니다.

11-3) 채택 기준은 '기능'이 아니라 '검증'이다

본인 추천은 unsafe를 품은 라이브러리를 고를 때 별점이나 기능 표가 아니라 검증 성숙도를 1순위로 두라는 것입니다. CI에 Miri가 돌고, 퍼징 타깃이 있고, RustSec 이력이 깨끗하며, unsafe마다 안전 주석이 달려 있다면 — 그 라이브러리는 믿을 만합니다. C에서 Rust로 넘어오는 더 큰 마이그레이션 맥락은 Go에서 Rust로 마이그레이션 가이드 2026에서도 짚었습니다.

12. 결론 + 얻어 갈 교훈 3가지

iddqd를 한 문장으로 요약하면 이렇습니다. "값에서 키를 빌려 인메모리 인덱스를 만드는, 평범해 보이지만 Rust의 가장 어려운 unsafe 영역을 정면으로 캡슐화한 작은 맵"입니다. 자기참조·이동·Pin·별칭이라는 난제를 좁은 코어에 가두고, 사용자에게는 평범한 맵 API만 건넵니다. 본인이 이 주제에서 얻은 세 가지 교훈으로 마무리합니다.

12-1) 교훈 1: '평범한 요구'가 unsafe의 입구일 수 있다

"값 안의 id로 조회하고 싶다"는 지극히 평범한 요구가, 깊이 들어가면 Rust에서 가장 어려운 자기참조 문제로 이어집니다. 어떤 자료구조를 설계할 때 "이게 자기 자신을 참조하게 되는가?"를 일찍 묻는 습관이 큰 사고를 막습니다.

12-2) 교훈 2: unsafe는 없애는 게 아니라 가두는 것이다

좋은 라이브러리는 unsafe를 0으로 만들지 않습니다. 위험을 좁은 코어에 격리하고, 그 경계 밖을 안전하게 보증합니다. 사용자로서 우리가 봐야 할 것은 unsafe의 존재가 아니라 그 면적과 검증입니다.

12-3) 교훈 3: 자기참조를 다룬다면 Miri는 선택이 아니라 필수다

raw 포인터와 자기참조를 건드리는 순간, 일반 테스트는 댕글링·별칭 위반을 놓칠 수 있습니다. Miri·퍼징·프로퍼티 테스트로 불변식을 실제로 두드려 보기 전까지는 "동작한다"고 말하지 마십시오. 본인에게 iddqd의 진짜 교훈은 화려한 트릭이 아니라, 가장 어려운 unsafe일수록 가장 겸손하게 검증해야 한다는 태도입니다.
