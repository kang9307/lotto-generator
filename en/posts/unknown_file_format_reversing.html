A File With No Format Spec - The Order in Which You Read Structure Out of Bytes

What to suspect first, how far each signal actually settles, and the conditions the law attaches

2026-09-05 Dev & Infra

Sooner or later a file lands on your desk with an extension you do not recognise, contents that are clearly not text, and nobody left to ask. Logs from equipment that was decommissioned years ago, save files from software whose vendor has shut down, output from an in-house tool that arrived without a single page of handover documentation. In that situation what you need is not a tool but an order of operations. Whichever editor you open, the same bytes appear on screen, and what you choose to suspect first decides how long the job takes.

This piece lays out that order. It separates the signals that bytes give up, one at a time, and for each one it draws the line between what the signal settles and what it never settles. Then it covers how to put an inferred structure back to the file as a question, and the conditions the law attaches to this kind of work. Tools appear only as instruments of the procedure.

The legal portion of this article is informational and is not legal advice. The statutory text was read at source and quoted, but whether a given act falls under a given provision depends on the target, the purpose and the contract in force. Judgment in any specific case belongs to the competent authority and a qualified lawyer. This article also does not deal with circumventing protective measures, and that territory sits outside the procedure described here.

The trigger - what the phrase unknown format quietly assumes

On 27 August 2026 the developer behind the hex editor ImHex published a walkthrough of reverse engineering an unknown file format. The subject is one game's save file, taken from an opaque blob to a state where every byte has a name, and it was picked up by Korean developer communities shortly after. It is a good piece of writing. But anyone who reads only the title and passes it along drops one assumption that carries the whole thing.

The method in that article is not staring at bytes. It is reading the code of the program that writes the file. The author says so plainly near the start. Opening the file reveals plain-text strings, so it is neither compressed nor encrypted, and that much is clear. But there is no identifying magic, the tool's own detection cannot name the type, and without more information the trail stops right there. Everything after that sentence is decompilation.

The general workflow the article distils at the end has four steps. Check whether the file is in a known format, find the code that parses or generates it, analyse that code to identify the building blocks in use, and write a pattern file that documents and verifies the findings as you go. The order is correct. What deserves attention is that in practice the step where people get stuck is the second one. Sometimes the code does not exist, sometimes it exists but cannot be viewed, and sometimes it can be viewed but should not be.

At that point the bytes are all that is left. That is the territory this article covers: how you narrow structure down without an answer key, and how the conclusions you reach that way differ from conclusions reached with one. If the tooling itself is what interests you, there is a separate piece on an analysis tool built for one specific binary format, and the question of what language models changed about this work is covered in the difference between making something readable and being able to say it is correct. Neither axis is repeated here.

Step zero - rule out a format that is already known

Before inferring structure, the work is to confirm that inference is unnecessary. A large share of mystery files are known formats wearing an unfamiliar extension or sitting inside another format. One of the comments under the source article joked that half of all unknown formats turn out to be an archive containing an embedded database. It is an exaggeration, but the direction is right.

Ruling out happens in three layers. First, put the leading bytes to a signature database. Nearly every hex editor and file identification tool carries this. Second, ask whether it is a container. Archive formats in the ZIP family begin their local file headers with 50 4B 03 04, but the table of contents, the central directory, lives at the end of the file, and the record marking that end begins with 50 4B 05 06. Anyone in the habit of skimming only the first few hundred bytes misses this on a regular basis. Third, look at the tail and the middle. A file with unrelated data prepended will not identify from its front.

There is a reason for putting the index at the end. In a stream written sequentially, the final size of each entry is unknown until it has been written. So the entries are pushed out first and the index is appended afterwards. Knowing this design habit gives you a reason to dig from the back even in an unidentified file. Whether a format was built assuming the whole file is loaded into memory or built to be streamed changes the shape of everything else in it.

If the identity resolves at this stage, the day's work is essentially over. A specification holds the answer and a parser probably already exists. Only when the ruling out fails do you move on.

Signal one - what a magic number actually settles

A fixed byte sequence at the head of a file is the first signal anyone notices. Well designed formats use that space deliberately. In PNG, the first eight bytes of a datastream are always 89 50 4E 47 0D 0A 1A 0A, and the specification states that this signature differentiates a PNG datastream from other types of datastream and allows early detection of some transmission errors. The same specification tells decoders to verify all eight bytes, and adds that a decoder can have additional confidence in the datastream's integrity if the next eight bytes begin a header chunk with the correct length.

In other words, a magic number says this format was intended, not this format is what you have. Here is where that distinction bites in practice.

  • Settled — that the producer intended a particular format, and therefore that there is a reason to go looking for its specification
  • Not settled — whether the content really is that format, which version it is, and whether the tail has been truncated or modified
  • What the absence of a magic tells you — not that there is no format. An internal format that never leaves the building has no reason to carry an identification tag at all
  • Common counterexamples — several formats sharing the same leading bytes, a magic that sits somewhere other than offset zero, and an outer container whose magic is visible while the inner payload's is not
  • If human-readable ASCII sits at the front, search for it first. It is often a format name or a product name, and that one string frequently surfaces a published specification

When the identity has not resolved and the same value keeps appearing at the head of every file you have, you still do not know whether it is a magic or simply a first field whose value is always the same. Telling those two apart takes more than one file. That problem gets its own section further down.

Signal two - endianness shows itself in the shape of values

The byte order of multi-byte integers governs every interpretation that follows. Read 00 00 01 F4 from the front and it is 500; read it from the back and it is 40,894,464. Get this wrong and length fields, offsets and counts all spin uselessly.

You determine it from the shape of the values. Most integers that end up in files are small: counts, lengths, versions, indices. Put a small value in four or eight bytes and the high-order bytes are all zero. So gather several positions that look like integers and see which end the zeros cluster on. Zeros at the front mean the most significant byte comes first; zeros at the back mean the least significant does.

What that settles is the byte order of that field. It does not settle that the whole file uses the same order. Specified formats disagree with each other on this point. The archive family mentioned earlier is little-endian, while the PNG specification requires that all integers requiring more than one byte be in network byte order, most significant byte first. It is also common for a container to use one order while the payload riding inside it uses the other, which happens naturally whenever the code that produced the payload is not the code that produced the container.

The counterexamples are clear enough. Symmetric values cannot be distinguished. A field that turns out to be floating point clusters its zeros differently. What looks like one four-byte slot may be four one-byte fields. So endianness is never settled from a single position, only from several positions agreeing.

Signal three - length fields and offset tables

This is the signal that exposes the skeleton most forcefully. When some four-byte value matches exactly the number of bytes remaining from that point, or matches the position where the next structure begins, that is not coincidence. The moment one value points at another place in the file, it is settled that a human designed a structure here.

There are two broad ways to carry variable-length data: prefix it with a length, or terminate it with a sentinel. Prefixing dominates. It lets the reader allocate up front and it stays safe when the data itself contains a byte equal to the sentinel. When you see a small value such as 0x11 followed by exactly that many readable characters, a length-prefixed string is the obvious first guess.

Once lengths have to cover large values, variable-length integers appear. The widely used scheme uses the most significant bit of each byte as a flag saying another byte follows and the remaining seven bits as the value. The source article ran into exactly this encoding while picking apart the target program's string-writing code, and hex editor data inspectors list it as two entries, signed and unsigned. Small values fit in a single byte, which is a visible win in a format full of short strings.

value = 0
shift = 0
repeat:
    b      = read_u8()               // read one byte
    value |= (b & 0x7F) << shift    // the low 7 bits carry the value
    shift += 7
until (b & 0x80) == 0                // a clear top bit means this was the last byte

What is settled is that the value is used as a length or a position. Rather more is left unsettled: whether the unit is bytes or elements, whether the origin is the start of the file or the start of that structure, and whether the length includes the header describing it. These three are exactly where implementations diverge even in specified formats. The PNG specification takes the trouble to state that the length field counts only the data field, not itself, not the chunk type and not the CRC. The people writing specifications knew this is where readers go wrong.

00000000  4C 4F 47 32 01 00 00 00  20 00 00 00 03 00 00 00
00000010  00 00 00 00 00 00 00 00  0C 00 00 00 48 45 4C 4C

// candidate reading (still a hypothesis)
//   +0x00  4 bytes  'LOG2'    ASCII that looks like a magic
//   +0x04  4 bytes  1         version? read least significant byte first
//   +0x08  4 bytes  32        header size? offset of the first record? 0x20 fits
//   +0x0C  4 bytes  3         record count?
//   +0x18  4 bytes  12        length of the first record? does the data that follows agree?

What decides the example above is that the value 0x20 and the position where data actually starts line up. Finding a point where a value and a position agree is the whole of this stage, and once you have one, the fields around it tend to fall out with it.

Signal four - alignment, padding and repetition

Zeros that appear at regular intervals are usually alignment: dead space inserted to land the next field on a four- or eight-byte boundary. If the format was produced by dumping a structure straight out of memory, the padding the compiler inserted is still sitting there. In that case the padding tells you about the original field sizes. Two dead bytes after a two-byte field suggest the next member wanted four-byte alignment.

A large run of zeros at the end of the file is a different story. It is the mark of a fixed-size buffer. The subject of the source article was exactly that: the save routine always filled 40,960 bytes, padding the remainder with zeros and throwing an exception if the content overflowed. In such a format the fact that the file size never changes is itself the signal. If every sample you hold is byte-for-byte the same length, you are looking at the vessel rather than the contents.

Repetition is the thread that leads to record structure. When the same byte pattern reappears at a fixed interval, that interval may be the record size. Pick a few candidates and check whether the file size minus the apparent header divides evenly by each one. A clean division promotes the hypothesis a step.

  • Settled — candidate sizes for a fixed-length record hypothesis, and a strong suspicion that a structure was dumped verbatim
  • Not settled — the header size. One file size cannot resolve two unknowns. Two samples of different sizes can
  • Counterexample one — zeros that look like padding may be fields whose value is zero. Reserved fields are almost always zero
  • Counterexample two — apparent periodicity may be a property of the data. A list of repeated strings looks periodic
  • Counterexample three — compressed regions throw off accidental periods too, which is why the next signal has to clear them out first

Signal five - the boundaries entropy draws

Information measured per byte has a ceiling of 8 bits, because a byte has 256 possible values. Slice a file into regions and measure, and the boundaries between regions of different character appear. Human-readable text and structural headers sit low, because few byte values are used and their distribution is skewed. Compressed or encrypted regions crowd the ceiling; well compressed data is by definition unpredictable, and the reason compression and prediction are the same problem is set out separately in a piece on why compression is prediction.

The data information view in ImHex carries an entropy graph, highest and average values, a byte type distribution and a compressed-or-encrypted verdict. Other tools have something similar. The look of the screen does not matter. What matters is how far those numbers let you speak.

  • Settled — the boundary between regions where structure can be read and regions where it cannot. That alone earns its keep, because it shows where the header ends and the payload begins
  • Not settled, first — whether a high region is compressed or encrypted. Both look uniform and the number does not separate them
  • Not settled, second — nothing at all about algorithms, keys or parameters
  • Counterexample one — a region carrying an already compressed image or audio stream also reads high. The format itself may be an ordinary container with only the payload compressed
  • Counterexample two — short regions have small samples and the value swings wildly. Entropy over a few dozen bytes means almost nothing
  • Counterexample three — a low value does not guarantee plaintext. Encodings built on fixed tables and repetitive binary data also read low

Put plainly, entropy is a map. It tells you where digging is worthwhile and refuses to say more. Mistake the map for a compass and time starts leaking. And if an unreadable region is unreadable because of a protective measure, that region is not a target for this procedure but the point at which the procedure stops.

All the signals on one page

Laying the five signals in one table makes the order plain. You work down the rows, and the discipline is not to move to the next row until you have read the third column of the current one.

Reading that third column by habit is half the job. Signals are instruments for narrowing hypotheses, not conclusions. The width each one removes is smaller than it feels, and promoting a narrowed hypothesis to a settled fact is the work of the next section.

Putting the hypothesis back to the file

A hypothesis held in your head cannot be falsified. Left vague, it survives contact with evidence that contradicts it, because you never notice the contradiction. So an inferred structure has to be written in a form a machine can read and fail on. That is what tools actually contribute to this work.

Two declarative approaches are in wide use. One is the ImHex pattern language, where you write structs, arrays and conditions in a C++-flavoured syntax and the definition is overlaid on the file. The repository is GPL-2.0, and as queried at 03:26 UTC on 5 September 2026 it showed 54,695 stars, 2,451 forks and 394 open issues. The other is Kaitai Struct, where a YAML declaration is compiled into parser code for a dozen languages; the compiler is GPLv3 or later and the runtimes are mostly MIT. The approaches differ but the property they aim at is identical.

struct Header {
    char magic[4];
    std::assert(magic == "LOG2", "magic does not match");   // hypothesis 1
    u32  version;
    std::assert(version == 1, "unknown version");           // hypothesis 2
    u32  headerSize;
    u32  recordCount;
};

struct Record {
    u32 length;                                            // hypothesis 3
    u8  payload[length];
};

struct File {
    Header header;
    Record records[header.recordCount];                    // hypothesis 4
};

Written this way, a wrong hypothesis fails visibly. Get the record size wrong and bytes are left over or come up short at the end of the file; get the count wrong and it blows up in the middle. How it breaks is itself information.

  • Bytes left over at the end means the record size was too small or the header was taken too large
  • Bytes coming up short means the reverse, or that a trailing structure such as an index exists
  • Blowing up in the middle means a field is conditionally present, and some earlier value decides whether it is there
  • Failing on some files only means there are multiple versions. Find the version field first
  • State hypotheses strongly. Asserting that a value must be a particular number tells you immediately when it is not. A loose definition passes silently while being wrong

The source article shows the same habit. Having confirmed that the target code checks the version value for 6 and throws otherwise, the author put the same assertion into the pattern. A fact read out of code was translated into a check made against the file. Even with an answer key you can mistranscribe it, which is why the habit holds up whether or not the key exists.

What collapses when you only have one sample

With a single file, constants and variables cannot be separated. There is no basis for deciding whether a byte holds a value the format fixes or a value that merely happens to be there. This is why four leading bytes cannot be classified as a magic rather than the value of a first field. No amount of additional staring removes the limit. What is needed is not more observation but a control.

Making a control is simple in principle. Use the program that produces the file, change exactly one value, save again, and diff the two files. The positions that changed are where that value lives. Tooling supports this well; comparing two data sources, highlighting the differences and listing them in a table is standard in hex editors. The method only works if you are able to run that program. From here the question stops being technical and becomes one of entitlement, which is why the last two sections exist.

Two things stay stubborn even with a control. The first is fields that change every time. Timestamps are the archetype: they differ on every save even when you change nothing, so they sit as noise across every diff. The remedy is to make a pair of saves with nothing changed at all and set aside whatever differs as a noise list. Time values need only their epoch and unit identified, but every format picks its own, and a look at how a well-known spreadsheet program stores dates in the way dates end up stored as numbers gives a sense of how arbitrary this corner of the craft is.

The second is check fields. If a checksum or a cyclic redundancy value is present, changing one value moves two places at once. Which, read the other way round, is how you find it: when something other than the position you intended also changes, suspect that. The important property of a check field is what it was computed over, and PNG makes a good example, since the specification places a four-byte check value in every chunk and states that it is calculated over the chunk type and data excluding the length field. Even in specified formats, implementations split when this range is left unstated.

And sometimes no control can be made at all: the program is gone, the equipment is gone, or you have no standing to run it. What comes out then is a description of one file rather than a description of a format. Writing that distinction at the top of the resulting document is what saves you later. Six months on, a reader has no way to tell which parts were verified and which were guessed.

When you do have the code - what the source article actually did

The procedure above assumes no answer key. With one, the picture changes completely, and retracing the source article's order makes the difference obvious.

The author located the target file and opened it in a hex editor. Plain-text strings were visible, so neither compression nor encryption was in play; there was no identifying magic, and the tool's detection could not name the type. That much corresponds to step zero and the first two signals here. And then the article says that without more information the trail stops.

The fork comes next. The game's installation folder contained libraries belonging to a particular runtime, and that language decompiles easily. Using the string that builds the save file's name as a lead, the author found the save routine and saw that it writes a timestamp first, delegates the actual contents to a callback, and pads with zeros up to a fixed size. From that point on it is not inference but transcription.

The building blocks transcribed are the ones this trade meets over and over. A 64-bit time value counting 100-nanosecond intervals from the year 1601, a version field that the reading function checks against a specific number, single-byte booleans, optional values preceded by a flag saying whether anything follows, strings whose length is carried in front as a variable-length integer, lists prefixed by a count, and enumerations laid over integers. Anyone who has designed a format that packs everything into a single file will find that list familiar. The writer's menu was never very long.

Strings drag encodings along with them, which is worth stating separately. Whether the length counts characters or bytes, which encoding is in use and which normalisation form applies are three independent questions. The fact that the same character can be stored as two different byte sequences is covered in a piece on Korean text stored two different ways.

One conclusion remains. That article could put a name on every byte not because the bytes were read well but because the answer was in view. Without that view, the same procedure does not deliver the same confidence. Refusing to acknowledge that gap while publishing a result is the most common mistake in this work.

It is also worth recording what the article does not cover. Entropy analysis, comparison across samples, statistical structure inference and legal conditions are absent from it. The tool has all of those features; they were simply not the subject. Not passing off as the source's claim something the source never claimed is the minimum condition of citation.

A checklist by stage

Folded into an execution order, the material above looks like this. Each stage lists what it yields and what skipping it eventually costs.

StageWhat you doWhat skipping it costs later
0. Establish standingWrite down whether you hold the target legitimately, what the purpose is, and where the output will goYou succeed technically and then cannot use any of it
1. Rule out known formatsSignature lookup, container check, tail checkYou spend days rediscovering an existing specification
2. Gather samplesAs many as possible, especially a pair differing in exactly one valueConstants and variables never separate
3. Segment the fileUse entropy to draw the line between readable and unreadable regionsYou mistake a compressed region for structure and burn days on it
4. Read the headSettle magic candidates, version candidates and byte orderEvery number that follows comes out wrong
5. Find the skeletonLook for points where a value matches a position, meaning lengths and offsetsYou end up with a document listing bytes and no structure
6. Write it and run itState the hypothesis declaratively and run it against every sampleA hypothesis you never learn is wrong hardens into a conclusion
7. Narrow on the breaksRevise the hypothesis wherever bytes are left over, short, or blow upYou ship a parser that only parses the files you had

That stage zero sits at the top is the point of the table. There are eight technical stages, but skipping the one that precedes them makes the output of the other eight unusable. What that stage actually asks is the subject of the next section.

The conditions the statute attaches - Article 101-4

Korean copyright law addresses this work head on. The quotations below follow the Copyright Act, in force 11 August 2026, Act No. 21336, partially amended 10 February 2026. The provision itself was newly inserted on 22 April 2009, with paragraph 1 amended on 8 August 2023.

The definition already carries the purpose

Article 2 subparagraph 34 defines the term first. Program code reverse analysis means reproducing or transforming the code of a computer program work in order to obtain information necessary for interoperability between an independently created computer program work and another computer program.

That definition should not be skimmed. The purpose is built into the name. If the aim is not to obtain information necessary for interoperability, the act does not carry this label to begin with, and therefore is not what the exception was written for. People summarise it as it is fine if the purpose is interoperability, but the order is backwards. Interoperability is not a justification applied afterwards; it is the condition at the door.

The four things paragraph 1 requires

Article 101-4 paragraph 1 stacks its requirements. A person who lawfully uses a program under legitimate authority, or a person who has that person's permission, may carry out program code reverse analysis without the permission of the holder of the author's property rights, where the information necessary for interoperability cannot be readily obtained and obtaining it is unavoidable, limited to the part of the program necessary for interoperability.

One sentence holds four conditions and all four must be satisfied together. Drop any one of them and the exception is not available.

The two exits paragraph 2 closes

Paragraph 2 separately restricts what may be done with the information obtained. First, using it for a purpose other than interoperability, or providing it to a third party. Second, using it to develop, produce or sell a program substantially similar in expression to the analysed program, or otherwise to infringe copyright.

The clause people run into most is the back half of the first. Tidying up an analysis and publishing it can touch providing it to a third party. Whether posting a format description to a blog or a repository falls there depends on what was published, to what extent and for what purpose, and this article cannot make that call. What the structure of the provision does make clear is that performing the analysis and distributing the result are evaluated as separate acts.

The neighbouring provision

Article 101-3 paragraph 1 subparagraph 6 grants an exception from a different angle: reproduction for the purpose of investigating, researching or testing the functions of a program in order to identify the ideas and principles underlying it, limited to a person using the program under legitimate authority while that use is ongoing. A proviso to the same paragraph applies alongside it. Where, in light of the type and purpose of the program, the proportion the reproduced part occupies and the number of copies, it unreasonably prejudices the interests of the rights holder, the exception does not apply.

The two provisions have different textures, and that is worth marking. Article 101-3 paragraph 1 subparagraph 6 is about observing and testing behaviour; Article 101-4 is about reproducing or transforming code. Work aimed at understanding a file structure can resemble either one depending on how it is carried out, or neither.

One further point remains. Both provisions concern programs. A data file may not be a program, and whether reading its structure falls within these provisions turns on the nature of the target and the act. Flattening that distinction and summarising the field as reverse engineering is legal is the most common misreading of this subject.

Beyond the statute, the contract remains

Being able to account for every element of the provision is still not the end. Terms of service and licences frequently restrict analysis on their own, and when a statutory exception collides with a contractual clause, which prevails depends on the jurisdiction and on the character of the clause. That there is an exception in the statute is not a safe basis for ignoring the contract. Equally, that a contract forbids something is not by itself the end of the matter. Either way, the conclusion is reached by whoever examines that specific case, not by this article.

What survives into practice is the record. Write the purpose down first, bind the scope of work to that purpose, and decide in advance where the output will go. Work that has none of those three in writing becomes hard to explain later. And when explanation is called for, the question tends to be what you wrote down before you started. A memo composed afterwards does not carry the same weight.

It is worth listing the cases where another axis attaches. If the target lives on somebody else's server rather than your own machine, regulation of information and communications networks applies separately. Distributing the output attracts its own assessment. Trade secret law operates independently. And a target carrying technical protection measures is an entirely different problem, one that this article does not address. How the picture shifts across multiple jurisdictions is set out in a section comparing requirements jurisdiction by jurisdiction.

One last misconception. The technical weakness of a measure has no bearing on the legal question. A flimsy lock and a lock you are entitled to open are different subjects. The reasoning behind treating obfuscation as a delay device rather than protection is set out in a piece on why obfuscation is not encryption, but that fact never becomes a licence to do anything.

To repeat. This section quotes provisions read at source and is not a judgment on any particular case. The same provision yields different conclusions depending on the target, the purpose, the contract and the use to which the output is put. Before doing the work, guidance from the competent authority and confirmation from a qualified lawyer are the right steps. This article was written for information only.

What could not be confirmed

  • The per-byte design rationale of the eight-byte PNG signature could not be confirmed. The account that the first byte catches transports that strip the high bit and that the newline pair catches line-ending translation is widely repeated, but the specification text read for this article does not carry that reasoning. What the specification states goes as far as differentiating a PNG datastream from other datastreams and allowing early detection of some transmission errors. So the per-byte rationale was left out of the body
  • No Korean case law was confirmed on how Article 101-4 applies to analysis of a data file's structure. The provisions were read at source, but application is a separate question, which is why the table in the body names the decision maker explicitly
  • No settled position was confirmed on which prevails in Korea when a statutory exception collides with a contractual clause. The body therefore asserts neither side
  • The threshold and method behind the compressed-or-encrypted verdict in ImHex could not be confirmed. The feature is listed, but no published description of the criterion was located
  • The per-signal judgments here are a structural account, not measurements. There is no statistical basis on hand for how often each signal holds across real formats
  • Other analysis tools mentioned in the source article were confirmed only by name and were not used directly, which is why the body ranks none of them against another
