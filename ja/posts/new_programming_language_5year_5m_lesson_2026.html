YC スタートアップ Wasp の DSL→TypeScript ピボットが示した5つの教訓と検証チェックリスト

はじめに - 5年と500万ドルを費やして気づいた一つのこと

2026年5月23日、news.hada.io に7点という控えめな点数で上がった一つのトピックが、点数とは裏腹に著者の頭に長く残りました。Yコンビネーターのスタートアップ Wasp が5年と約500万ドルを投じた末、公式の振り返りで「独自 DSL を作ったのは間違いだった」と認め、同じ抽象化を TypeScript ライブラリとして再ローンチすると宣言した記事です。プライドの高いスタートアップがここまで公に自らの失敗を認める例は珍しく、だからこそ価値があります。

Wasp が最初に登場したのは2020年代初頭でした。フルスタックの Web アプリを単一ファイルの宣言で表現できるドメイン特化言語(DSL)であり、「エンジニア一人が数日で SaaS を作る」という強烈な約束とともに YC のシードを得ました。著者も登場初期にデモを見た記憶があり、フルスタック抽象化の次の段階になり得ると一瞬期待しました。しかし5年が経過した今返ってきた答えは「DSL は答えではなかった」というものでした。

本記事は単なる Wasp ニュースの整理ではありません。著者がまとめた12の H2を通じて、(1) Wasp とは何だったか、(2) なぜ DSL を選んだか、(3) DSL が生んだ5つの罠、(4) TypeScript ピボットの理由、(5) 新しい言語を作る前に答えるべき5つの基準、(6) 成功した稀な DSL の共通点(Solidity・Terraform・CUDA)、(7) 失敗したよくある DSL の共通点(CoffeeScript・初期 Dart・Elm)、(8) AI 時代の DSL(Zero・Vercel)は違うか、(9) 開発者が自分のツールを作るときに使える5つの教訓、(10) 日本・韓国スタートアップやオープンソースメンテナー環境への適用法、(11) 今日から使える3つのチェックリスト、(12) 参考資料まで正直に扱います。

1. Wasp とは何だったか - YC スタートアップのフルスタック Web DSL

Wasp はフルスタック Web アプリを宣言的に表現するドメイン特化言語でした。ユーザーが .wasp という拡張子の単一ファイルにルート・ページ・DB モデル・認証・ジョブを宣言すると、Wasp コンパイラが React フロントエンドと Node.js バックエンドのコードを自動生成します。最も印象的だったデモは、一画面の宣言で認証・DB・メール通知を備えた SaaS の基本骨格が即座に生成される場面でした。

著者が見た Wasp の強みは三つです。第一に、ボイラープレートの正直な削減。Next.js・Remix が抽象化した部分の上にもう一層を積み、認証・DB・ジョブのようなフルスタック共通要素を宣言的に表現しました。第二に、学習曲線が短いこと。単一ファイルで始められるのは新しいツールの最大の長所です。第三に、Y コンビネーターの後方支援と明確なコミュニティ構築です。

それでも5年後の結果はピボットでした。強みが明確であったにもかかわらず、ユーザー採用率が臨界点を越えませんでした。著者の見方では、その原因の80%は「DSL という形態」にあります。同じ抽象化をライブラリで提供していれば、結果は違った可能性が高いです。この差を次の節で5つの罠としてまとめます。

2. なぜ DSL を選んだか - 初期選択の合理的な理由

Wasp 創業者の初期選択を「間違った決定」と単純に貶めれば教訓を逃します。著者から見て、彼らが DSL を選んだ理由は当時の文脈で十分に合理的でした。次の四つの理由があります。

2-1) 抽象化の明確さ

フルスタックアプリは本質的に複数の言語(JavaScript・SQL・HTML・CSS)と複数のシステム(フロントエンド・バックエンド・DB・ジョブキュー)が絡む領域です。この複雑性を単一ファイルの宣言で表現するなら、新しい構文が最もきれいです。ライブラリで同じ抽象化を作ろうとすると、JavaScript の制約の中でぎこちないビルダーパターンが生まれます。

2-2) コンパイル時検証

DSL はコンパイラがユーザー宣言を事前に検証できます。ルート衝突、モデル参照エラー、権限漏れのようなフルスタックでよくある間違いをコンパイル時に捕捉できる点は大きな利点です。

2-3) 差別化のシグナル

創業初期のスタートアップには「なぜ我々が特別か」というシグナルが必要です。新しい言語はそれ自体が強力なマーケティング資産です。ユーザーには「この会社はフルスタックを本気で再定義する」というシグナルを、投資家には「他社が簡単に模倣できない堀がある」というシグナルを与えます。

2-4) 学習コストへの楽観

創業者は「ユーザーが1時間投資すれば学習曲線を越えられる」と仮定した可能性が高いです。これはよくある楽観であり、実際の学習コストは常に予想の3〜5倍です。

四つの理由すべて、当時の文脈で合理的でした。著者が同じ立場にいたら同じ決定をした可能性が高いです。だからこそ Wasp の振り返りはより価値があります。合理的な決定でさえ5年後に見れば罠になり得ることを正直に示しているからです。

3. DSL が生む5つの罠 - 著者まとめ

Wasp の振り返りと著者が見た他の DSL 事例を総合して、新しい言語・DSL がよく生む五つの罠を整理します。

3-1) 学習曲線 - すべての開発者が新しい構文を学ばなければならない

どれほど単純な DSL でも、ユーザーは「なぜまたこれを学ばなければならないのか」という抵抗を1秒以内に感じます。JavaScript・TypeScript のようにすでに知っている言語の中でライブラリとして提供されれば、学習コストはライブラリ API をいくつか覚える水準にとどまりますが、新しい DSL は構文・意味論・慣用句・エラーメッセージのパターンまで全てを学び直す必要があります。

3-2) ツールエコシステム不在 - IDE・リンター・デバッガがない

JavaScript は30年積み重ねた IDE サポート(VSCode・WebStorm)、リンター(ESLint・Biome)、デバッガ(Chrome DevTools・Node Inspector)、フォーマッタ(Prettier)を即座に受け取ります。新しい DSL はこの全てを最初から作るか、似せて作るかしなければなりません。ツールがなければユーザーは1週間も耐えられません。 Wasp はこの部分に最も大きな資源を使いましたが、それでも TypeScript 水準には到達できませんでした。

3-3) 採用市場の制限 - Wasp 開発者がいない

スタートアップが Wasp で製品を作り始めると「Wasp 開発者」という職務が生まれますが、採用市場には存在しません。JavaScript 開発者を雇って Wasp を教える追加コストがかかり、その開発者が辞めれば同じコストが繰り返されます。著者が観察した日本・韓国スタートアップでも、独自 DSL を採用した企業の90%以上が3年以内に採用問題で撤退しました。

3-4) ライブラリ互換性 - npm を直接使えない

JavaScript エコシステムの中核資産は npm の200万以上のパッケージです。新しい DSL はこの資産に直接アクセスできないか、FFI(Foreign Function Interface)のようなラッパーを通じて間接的にアクセスする必要があります。決済、メール、分析、データベースクライアントのような日常的なツールを毎回ラッパーで包まなければならないなら、生産性は半分に落ちます。

3-5) 移行コスト - 離脱が難しい

逆説的ですが、DSL の最大のマーケティング上の弱点は「離脱が難しい」という点です。ユーザーは最初の導入時にすでに「これを5年後に他のツールへどう移すか」を計算しています。移行コストが明確でないツールは信頼を得にくいです。 Wasp のユーザーも同じ懸念を持ち、その懸念が採用率の臨界点を越えられなかった大きな理由でした。

4. TypeScript へピボットした理由 - ライブラリの優位

Wasp チームが TypeScript ライブラリへピボットしながら発表した核心理由は、上の五つの罠を一度に解く答えだったからです。著者がまとめた TypeScript ライブラリの優位は次の通りです。

  • 学習曲線ゼロ: ユーザーはすでに TypeScript を知っているので、ライブラリの API のみ覚えればよい。
  • ツールエコシステムを即座に活用: VSCode・ESLint・Prettier・tsc strict がそのまま動く。
  • 採用市場が無限: TypeScript 開発者は溢れている。
  • npm を直接使用: 200万のパッケージを即座に活用。
  • 移行コストが明確: ユーザーはいつでもライブラリを外して通常の TypeScript へ戻れる。

著者の見方では、この五つの優位は DSL が本質的に持ち得ないものであり、ライブラリだけが与えられるものです。「同じ抽象化をライブラリで提供できるなら、常にライブラリが答え」という命題が Wasp 振り返りの最も核心的なメッセージです。

ただしライブラリにも限界はあります。コンパイル時検証の強度、構文の美しさ、差別化シグナルの面では DSL に及びません。Wasp チームの決定は「この限界を受け入れて採用率を取る」というトレードオフであり、著者の視点では正しい選択です。

5. 新しい言語を作るための5つの検証基準 - 著者まとめ

Wasp 振り返りを見た後に著者がまとめた「新しい言語を作る前に必ず答えるべき五つの質問」です。五つすべてに明確な「はい」が出ない限り、新しい言語を作ってはいけません。

5-1) 既存の言語で本当に解けないのか

最も重要な質問です。ライブラリ・フレームワーク・マクロ・組み込み DSL の軽量変形で同じ問題を解けないか先に確認してください。Wasp の場合の答えは「実は解けた」でした。TypeScript ライブラリで同じ抽象化を提供できたのであり、5年の遠回りの末にその答えに到達しました。

5-2) 市場が新しい言語の学習コストを支払う意思があるか

学習コストを正当化するだけの大きな見返りが必要です。Solidity は「イーサリアムスマートコントラクトを書けなければ数十億ドル市場に参入不可能」という見返りがありました。Wasp は「フルスタックボイラープレートを減らす」という見返りでしたが、TypeScript ライブラリでも同じ見返りが可能だったので、学習コストを正当化できませんでした。

5-3) 維持可能なメンテナープールがあるか

5年以上、コア貢献者3〜5人を安定的に維持できるかを見なければなりません。オープンソースメンテナープールは常に予想より小さく、燃え尽きは常に予想より早く来ます。 企業が後方支援しても、コア人物が離れれば言語は急速に停滞します。

5-4) 5年後も生き残れるか

市場構造が5年後もこの言語を必要としているかを点検してください。AI コーディングツール・LLM・新ランタイムの登場が市場をどう変えるかを5年単位で描いてみてください。著者から見て、Wasp が登場した2020年代初頭にはすでに「TypeScript がフルスタックの標準になる」というシグナルが十分にあり、その時点で DSL を選んだのは5年後の市場を過小評価した結果です。

5-5) 企業の中核価値が言語自体か

言語ではなく抽象化・ツール・サービスが中核価値ならライブラリで十分です。企業の中核価値が本当に「この言語なしでは解けない問題」なら新しい言語は正当化されます。Solidity・CUDA がこの条件を満たす代表例です。

6. DSL が成功した稀な事例 - Solidity・Terraform・CUDA の共通点

全ての DSL が失敗したわけではありません。生き残った DSL の共通点を見ると「なぜ新しい言語が必要なのか」という問いに明確な答えがあります。

6-1) Solidity - イーサリアムスマートコントラクト

Solidity はイーサリアム仮想マシン(EVM)上で実行されるスマートコントラクトを書くための言語です。一般の言語では EVM バイトコードを安全に生成できず、取引意味論・ガスコスト・状態変更のようなイーサリアム特化の概念を表現する方法がありません。「既存言語で解けない本質的な問題」が明確です。

6-2) Terraform - インフラコード

Terraform の HCL(HashiCorp Configuration Language)はクラウドインフラを宣言的に表現する DSL です。一般の言語で同じことをできますが、HCL は宣言的表現・差分計算・プラン・適用というインフラコードの4段階ワークフローを自然に表現します。AWS・GCP・Azure のどこでも同じ言語でインフラを表現できる点が採用の核心でした。

6-3) CUDA - GPU 並列計算

CUDA は NVIDIA GPU で並列計算を書くための C 拡張です。CPU 言語では GPU の数千コアを効率的に活用できず、GPU メモリ階層・ワープ・ブロックのようなハードウェア概念を表現する方法がありません。AI・科学計算の爆発的成長が CUDA を事実上の標準にしました。

6-4) 三つの事例の共通点

三つの言語すべてが次の四つの条件を満たします。(1) 既存言語で本質的に解けない問題、(2) 市場が学習コストを正当化するほど大きな見返り、(3) 巨大企業または強力なコミュニティの後方支援、(4) 5年後も消えない市場構造。Wasp が満たせなかった条件をこの三つは全て満たします。

7. DSL が失敗したよくある事例 - CoffeeScript・初期 Dart・Elm

失敗した DSL の共通点も明確です。三つの代表事例を挙げます。

7-1) CoffeeScript - 消えた愛

CoffeeScript は2010年代初頭、JavaScript の不格好な構文を綺麗に書き直した DSL であり、Ruby on Rails 陣営を中心に爆発的人気を得ました。著者も一時期好きでした。しかし ES6 が登場して JavaScript 自体が綺麗になり、CoffeeScript の価値提案が消えました。「既存言語が自らの欠陥を直せる領域」で作った DSL は常に危険です。

7-2) 初期 Dart - Chrome 統合失敗

Dart は Google が JavaScript を置き換えるために作った言語です。Chrome に Dart VM を統合する計画がありましたが、他のブラウザがついて来ず白紙となりました。結果として Dart は Flutter という新しいドメインを発見するまで事実上活動が停滞しました。「単一の企業が標準を強制できない市場」で DSL は生き残りにくいです。

7-3) Elm - 関数型フロントエンドの約束

Elm は React 時代初期に「関数型フロントエンドの約束」で深いファンを得ましたが、メンテナーの後方支援不足、JavaScript エコシステムとの統合コスト、学習曲線に対する見返り不足で採用率が停滞しました。

7-4) 三つの事例の共通点

三つの言語すべてが次の三つの条件のうち一つ以上で弱点を持っていました。(1) 既存言語が欠陥を自ら直せた、(2) 単一企業・コミュニティが標準を強制できなかった、(3) 学習コストを正当化する見返りが不足した。Wasp は三つの条件全てで弱点を持っていました。

8. AI 時代の DSL - Zero(Vercel)のような試みは違うか

2026年5月、Vercel Labs が公開した Zero(zerolang.ai)は「AI エージェントを1番目のユーザーに置く新しい言語」です。著者が別記事で扱ったように、Zero は検査親和・修正親和・決定論的出力のような新しい設計原則を試みます。Wasp の教訓を適用すると Zero はどうでしょうか。

8-1) 学習コスト面 - 部分的に違う

AI エージェントは学習コストを分単位で吸収します。人間の学習曲線が新言語採用の最大の障壁だった時代と比べれば、この部分は大きく緩和されます。Zero の1番目のユーザーがエージェントなら、学習曲線の罠は弱まります。

8-2) ライブラリ互換性・ツールエコシステム - 同じ問題

しかしライブラリ互換性、ツールエコシステム、メンテナープール、5年後の生存可能性という四つの問題はそのまま残ります。Zero コードで決済・メール・分析を呼び出すには依然として npm ラッパーが必要であり、IDE サポートは最初から作らなければなりません。

8-3) 著者の予測

Zero が生き残るには二つの道のうち一つです。(1) Vercel が自社ツール(v0・AI SDK)と Zero を一体化して採用を強制的に牽引するか、(2) 他の巨大企業(Google・Microsoft・Anthropic)が Zero の設計原則を吸収して自社言語にパッチを当てる方式で原則だけが生き残る道です。著者の推定では Zero 自体の生存確率は30%以下ですが、設計原則の生存確率は80%以上です。

結局 AI 時代の DSL も Wasp の教訓から自由ではありません。学習曲線という一つの問題が緩和されるだけで、残り四つの問題はそのままです。

9. 開発者が自分のツールを作るときに使える5つの教訓

Wasp 振り返りが個人開発者に与える教訓を五つにまとめます。著者がサイドプロジェクトとオープンソースを運営しながら直接適用中の原則です。

  1. ライブラリが答えならライブラリで答えよ: 同じ抽象化をライブラリで提供できるなら、常にライブラリが答えです。新しい構文の誘惑を1秒以内に遮断してください。
  2. 学習コストを常に3倍で見積もれ: ユーザーがツールを覚えるのにかかる時間は常に自分の予想の3〜5倍です。1時間と見積もれば3〜5時間に、1日と見積もれば3〜5日に補正してください。
  3. 移行コストを明示せよ: ユーザーに「5年後にこのツールを外すコストはいくらか」を明示的に示してください。明示されない移行コストはユーザーが常に最悪を仮定します。
  4. 採用市場をツール設計の入力にせよ: ツールが採用市場に与える影響をツール設計段階で考慮してください。ユーザーがツール採用時に「このツールを知る人をどう雇うか」を1秒以内に思い浮かべられなければなりません。
  5. 5年単位の市場を描け: ツールの5年後の市場構造を意識的に描いてください。5年後に消える可能性が大きいツールなら、最初から作る価値が減ります。

10. 日本・韓国スタートアップとオープンソースメンテナー環境への適用

日本・韓国の環境で Wasp の教訓を適用する方法を著者の視点で挙げます。

10-1) スタートアップ - ライブラリ優先

日本・韓国スタートアップの資源と採用市場規模を考えれば、独自 DSL はほぼ常に危険です。日本のメルカリや韓国のトス・ダンガン・LINE のようなモダンスタートアップも独自言語を作らず、TypeScript・Kotlin ライブラリ・内部 SDK で抽象化を提供します。著者が見たスタートアップ事例では、独自 DSL を作った企業の90%以上が3年以内に撤退しました。

10-2) オープンソースメンテナー - 組み込み DSL が安全

オープンソースメンテナーが新しいツールを作るときは、既存言語内の組み込み DSL が最も安全です。JavaScript のビルダーパターン、Python のデコレータベース DSL、Ruby のブロックベース DSL がその例です。この方式は学習曲線の罠・ツールエコシステム不在・採用市場制限の罠を全て避けながらも綺麗な表現力を提供します。

10-3) 著者推奨の意思決定順序

著者が新しいツールを作るときに従う優先順位は次の通りです。

  1. 1位: 既存ライブラリ・フレームワーク活用 (作る必要がなければ作るな)
  2. 2位: 内部ライブラリまたは SDK 作成
  3. 3位: 既存言語内のマクロ・組み込み DSL
  4. 4位: 独自のパーサ・コンパイラを持つ外部 DSL
  5. 5位: 本格的な新プログラミング言語

1〜3位で解けないことが明確に証明された後にのみ、4〜5位を検討してください。Wasp は4位から始めて5年と500万ドルを使い、3位へ撤退した事例です。著者推奨の順序を最初から守っていれば、5年を節約できました。

11. 結論 + 今日から使える3つのチェックリスト

Wasp 振り返りが投げた最大のメッセージを著者の一文で整理するとこれです。「新しい言語を作るな。同じ抽象化をライブラリで提供できるなら、常にライブラリが答えだ。」 このメッセージを実務に適用する、今日から使える三つのチェックリストを著者が使用中の形で共有します。

11-1) チェックリスト1: 新しいツールを作る前の5分自己点検

新しいツール・DSL・言語を作りたい衝動が湧いたら5分以内に答えるべき五つの質問です。

  • この問題を既存のライブラリ・フレームワークで本当に解けないのか?(1秒以内に「いや、解ける」が出れば作るな)
  • 同じ抽象化をライブラリ・SDK で提供できないのか?
  • 学習コストを3倍で見積もってもユーザーが支払う意思があるか?
  • 5年後もこのツールを維持するメンテナー3人を安定的に確保できるか?
  • このツールが企業または自分の中核価値か、それとも付属資産か?

11-2) チェックリスト2: 既存ツール採用前の5分リスク点検

外部のツール・DSL・新しい言語を採用するかを決めるときに答えるべき五つの質問です。

  • このツールを外すのにかかる移行コストを明示的に知れるか?
  • このツールを知る人を1週間以内に採用市場で見つけられるか?
  • このツールのライブラリ互換性・ツールエコシステムが1年以内に消えないシグナルがあるか?
  • このツールのメンテナーまたは企業が5年後も活動するシグナルがあるか?
  • このツールを採用するとき得る見返りが採用コストの3倍以上か?

11-3) チェックリスト3: 6か月・5年の2時点での振り返り質問

ツールを作ったり採用したりした後、6か月・5年の時点で自分自身に投げる振り返り質問です。

  • 6か月: このツールが本当に自分の生産性を上げたか、それとも学習コストだけ持って行ったか?
  • 6か月: ユーザーがこのツールを推奨する意思が1点から10点中何点か?
  • 5年: このツールが最初に作るときに想定した市場構造の中に依然としているか?
  • 5年: このツールを作った決定を全く同じくもう一度下すか?
  • 5年: Wasp のように公に「間違いだった」と認めるべき部分があるか?

著者が最後に強調するメッセージはこれです。ツールを作ったり採用したりする決定は、常に5年規模の賭けです。 1年以内に答えが出る決定はほぼなく、5年後に見れば合理的だった決定でさえ罠になります。Wasp チームが5年と500万ドルを使い、正直に振り返った勇気は、同じ罠に陥る次の誰かを5年節約する資産になります。著者がこの記事を書いた理由もそこにあります。
