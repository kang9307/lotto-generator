1. Overview of zSST and the Background of Recreating 3dfx Voodoo SST-1 in Hardware

Released in late 1996, the 3dfx Voodoo Graphics accelerator, internally designated as SST-1, fundamentally redefined the paradigm of real-time three-dimensional computer graphics on personal computers. Prior to its commercial arrival, the vast majority of personal computer gaming experiences were constrained by CPU software rendering. The central processor was forced to calculate every geometric vertex transformation, project coordinates onto a two-dimensional screen plane, perform perspective-correct interpolation across polygon surfaces, execute bilinear texture filtering, and compute depth values entirely within software routines, severely throttling frame rates and graphical complexity.

The Voodoo Graphics hardware eradicated this computational bottleneck by introducing dedicated fixed-function silicon specifically optimized for rasterization, texture filtering, and Z-buffering. Operating through the proprietary Glide API, the SST-1 architecture offered direct, low-overhead register control that enabled PC games to render fluid textured environments with atmospheric fog, alpha blending, and dithering at sustained rates exceeding thirty frames per second. While the core graphics assets of 3dfx Interactive were acquired by NVIDIA in December 2000, the foundational rasterization pipeline established by the SST-1 remains an essential milestone in the evolution of modern graphics processing units.

As decades have elapsed, physical Voodoo hardware has grown increasingly scarce due to component degradation, capacitor failure, and silicon aging. In response to this gradual physical disappearance, developer nand2mario introduced zSST, an open-source hardware recreation project implemented in SystemVerilog. Unlike traditional software emulators that simulate vintage processor instructions using high-level software loops on contemporary operating systems, zSST reconstructs the exact circuit-level behavior, register semantics, and signal pipelines of the SST-1 directly inside field-programmable gate array (FPGA) logic.

Techniques encompassing software-level netplay rollback architectures and bytecode static recompilation have been examined previously in our evaluations of MAME Rollback Netplay Launcher Architecture and GBA Decompilation and WebAssembly Static Recompilation. In contrast to those software virtualization layers, zSST bypasses software interpretation altogether, mapping logical gates, lookup tables, flip-flops, and DSP slices directly within programmable silicon to preserve the authentic hardware timing and bus behaviors of the legendary accelerator.

2. Integration with z486 XL — 100 MHz Pipelined CPU and Retro DOS PC Architecture

A standalone 3D graphics accelerator cannot render interactive imagery in isolation without an accompanying host system capable of dispatching geometric vertex buffers and issuing command packets. The original Voodoo Graphics was not a primary 2D display adapter; it functioned as an auxiliary 3D passthrough card that received analog RGB video from a separate 2D VGA controller via an external VGA loop cable, switching its internal multiplexer to drive the monitor only when a 3D application engaged the Glide runtime.

To establish a fully functional computing environment, developer nand2mario coupled the zSST core with z486, a custom pipelined 486-class soft CPU core, giving rise to the unified z486 XL system. This integrated system-on-chip incorporates the host CPU, motherboard logic, memory controllers, audio synthesis, standard VGA display controller, and the zSST Voodoo accelerator within a singular programmable FPGA device, recreating an entire late-1990s DOS gaming personal computer.

The physical target platform selected for z486 XL is the AMD Kria Xilinx KV260 Vision Starter Kit. Conventional hobbyist FPGA platforms, such as the DE10-Nano widely adopted in retro projects, encounter strict resource limitations when attempting to accommodate a fully pipelined x86 CPU core concurrently with a complex 3D rasterizer and on-chip memory blocks. The Xilinx KV260 board resolves this constraint by providing extensive logic capacity, specialized DSP slices capable of single-cycle integer arithmetic, abundant block RAM, and high-bandwidth access to onboard DDR memory without requiring external SDRAM add-on modules.

The core structural characteristics of the z486 XL architecture encompass the following engineering specifications:

  • Synchronous 100 MHz Clocking: Both the pipelined z486 CPU core and the zSST rendering pipeline close timing cleanly at 100 MHz on the Xilinx KV260 hardware, operating synchronously within a unified frequency domain.
  • Direct Onboard DDR Memory Utilization: The architecture bypasses external memory daughterboards by interfacing directly with the KV260 onboard DDR memory, sharing available bandwidth between system RAM and graphics buffers.
  • 512 KiB Write-Back L2 Cache: A dedicated 512 KiB secondary write-back cache is integrated to alleviate memory latency bottlenecks during intensive vertex matrix transformations and sequential register writes.
  • Comprehensive Legacy PC Peripheral Subsystems: The system incorporates standard VGA video output alongside accelerated zSST rendering, Sound Blaster 16 compatible audio synthesis, USB keyboard and mouse HID input, and automated virtual hard disk (VHD) mounting.

3. Pixel Pipeline and Fixed-Point Rendering — Graphics Features Implemented at Circuit Level

The original 3dfx SST-1 hardware divided its graphics pipeline across two distinct physical application-specific integrated circuits: the Frame Buffer Interface (FBI) and the Texture Mapping Unit (TREX or TMU). The zSST project consolidates the operational responsibilities of both chips into a single cohesive SystemVerilog module, faithfully implementing the register interfaces, pixel data paths, and state machines mandated by the official SST-1 specification document.

At the hardware control boundary, software directs zSST through five foundational command registers. When the host CPU computes polygon vertices and parameter gradients, writing to `triangleCMD` initiates the active rasterization pipeline. Floating-point setup registers route incoming single-precision values through `ftriangleCMD`, while `nopCMD` flushes internal pipeline stages and resets diagnostic statistics counters. Immediate or rectangular screen clears are handled by `fastfillCMD`, and `swapbufferCMD` orchestrates double-buffered display swapping synchronized to vertical retrace intervals.

Beneath its modern-appearing floating-point interface, zSST implements a rigorously defined fixed-point arithmetic pipeline. While contemporary GPUs operate predominantly with IEEE floating-point arithmetic throughout their shader stages, 1990s silicon conserved silicon area by converting single-precision vertex inputs into integer representations with fixed fractional scales upon register receipt. In zSST, screen coordinates utilize a 12.4 format, color and alpha components use 12.12, depth coordinates use 20.12, perspective texture coordinates S/W and T/W use 14.18, and reciprocal W utilizes a 2.30 format.

By relying on fixed-point arithmetic, the rasterization hardware calculates pixel steps across horizontal scanlines by simply accumulating precalculated gradient increments using integer adders. This architectural regularity enables zSST to achieve an optimal throughput target of one completed, textured, and depth-tested pixel per clock cycle whenever memory bus access remains uninhibited.

4. Cross-Checking Empirical Performance Metrics — 78.5 MPix/s vs Software Rendering

The engineering validity of a hardware reproduction cannot be established solely through visual screenshot captures; it requires rigorous quantitative benchmarking under controlled architectural conditions. The empirical throughput figures published by nand2mario demonstrate both the honesty of the implementation and the structural efficiency of the synthesized rasterization pipeline.

Under a 100 MHz operating clock, zSST achieves an empirical fill-rate of 78.5 MPix/s (specifically recorded at 78.47 MPix/s in simulation) during textured triangle rasterization. This metric reveals that even when accounting for texture cache access latencies and memory bus contention, the pipeline yields an average of 0.785 textured pixels per clock cycle. Under heavier rendering workloads with depth testing and alpha blending concurrently engaged, the pipeline sustains a fill-rate of 72.8 MPix/s (empirically 72.83 MPix/s).

To contextualize these throughput numbers, they must be contrasted against pure software rendering benchmarks executed on the very same z486 XL platform without engaging the zSST 3dfx accelerator. Across identical hardware constraints, performance varies dramatically depending on the underlying rendering approach:

Doom, which relies on a two-and-a-half-dimensional raycasting engine and avoids arbitrary 3D matrix mathematics, achieves a playable 38.5 FPS on the 100 MHz z486 core. Conversely, the fully three-dimensional engine of Quake 1.06 plummets to 8.1 FPS under CPU software rendering. This stark divergence highlights the exact computational ceiling of 486-class microprocessors when burdened with floating-point geometry and software span drawing, illustrating precisely why dedicated 3D hardware accelerators became mandatory in late-1990s computing.

5. Running Tomb Raider Level 2 and the Real-World Reality of 12 Buffer Swaps per Second

Among the empirical validations performed on the z486 XL system, the primary benchmark title is the commercial release of Tomb Raider running its original 3dfx Glide renderer. In hardware captures of Level 2, the system recorded approximately 12 buffer swaps per second (`swapbufferCMD`), representing an effective gameplay frame rate of roughly 12 FPS. The title executes without specialized binary patches or emulator wrappers, interfacing directly with zSST's hardware registers.

This raises a crucial technical inquiry: if the zSST hardware pipeline boasts an empirical fill-rate exceeding 72 million pixels per second, why does an actual commercial game yield only 12 buffer swaps per second? The resolution to this apparent paradox lies in the architectural division of labor inherent to first-generation 3D graphics hardware.

Unlike second-generation architectures such as the GeForce 256, the 3dfx SST-1 contains no hardware transform-and-lighting (T&L) execution units. The accelerator is strictly an endpoint rasterizer. It receives screen-space triangles whose vertices, projection matrices, lighting values, and bounding-box clippings have already been calculated and projected by the host CPU.

In Tomb Raider, the host z486 processor must compute the geometric matrices for subterranean chambers, animate the skeletal mesh of Lara Croft, execute camera clipping routines, and calculate per-vertex parameter gradients before dispatching triangle setup commands across the system bus. No matter how swiftly the zSST rasterizer paints textured pixels across its internal pipeline, the aggregate frame rate cannot exceed the rate at which a 100 MHz 486-class CPU can calculate and dispatch geometry. The recorded 12 buffer swaps per second accurately reflects the real-world operational equilibrium of late-1990s computing, capturing the genuine performance envelope of pairing a 486-class processor with first-generation 3D acceleration.

6. Technical Trade-Offs and Clock Considerations in FPGA Hardware Recreation

Synthesizing graphics hardware within an FPGA ensures cycle-accurate state transitions and bus timing that software emulators often approximate, yet this precision demands significant engineering compromises. High-performance x86 desktop processors can leverage gigahertz clock speeds and massive cache hierarchies to emulate vintage logic easily, whereas FPGA synthesis must operate within rigid limits imposed by routing delays and physical block resources.

According to synthesis reports published by nand2mario, the zSST graphics device claims substantial logic resources on the Xilinx XCK26 Zynq UltraScale+ MPSoC:

  • 29,538 Lookup Tables (LUTs): Utilized to construct complex combinational decoding logic, register state machines, and rasterizer math stages.
  • 28,109 Flip-Flops: Synchronous sequential registers maintaining vertex coordinates, texture parameters, and pipeline states across clock boundaries.
  • 14 RAMB36 and 8 RAMB18 Blocks: Dedicated on-chip block RAM instances serving as texture caches, palette lookup tables, and FIFO buffers.
  • 97 DSP Slices: Hardware arithmetic units executing fixed-point multiply-accumulate operations for perspective texture mapping, bilinear interpolation, and fog blending.

This extensive footprint clarifies why mainstream retro computing boards cannot support the full zSST design alongside an x86 CPU. Accommodating both processors concurrently necessitates the advanced logic density and memory bandwidth of an MPSoC platform like the KV260.

Furthermore, operating clock frequencies must be interpreted with technical precision. The zSST and z486 cores close timing at 100 MHz on the KV260. However, the original documentation does not provide a direct numeric frequency comparison against the physical 1996 silicon chip manufactured by 3dfx. Reaching 100 MHz within an FPGA fabric while meeting setup-and-hold constraints across a complex rendering pipeline is an impressive engineering achievement, but this frequency should not be misconstrued as an arbitrary claim of performance superiority over the vintage silicon; it represents the native operational cadence of this specific FPGA synthesis.

7. Verifying Credibility via Open-Source Repositories and Unmodified Binary Execution

When evaluating novel hardware implementations, technical readers must determine how claims of architectural fidelity and benchmark throughput can be independently corroborated. The zSST project establishes its credibility through two transparent verification mechanisms: open-source accessibility and unmodified binary execution.

First, developer nand2mario has published the entirety of the hardware descriptions across public GitHub repositories (`github.com/nand2mario/zSST` and `github.com/nand2mario/z486_XL`). The SystemVerilog modules defining the triangle rasterizer, texture filtering logic, framebuffer interface, Vivado platform constraints, and bootable Linux build recipes are completely accessible. Any digital design engineer can inspect the source code, trace signal transitions, and examine how specific SST-1 register behaviors are implemented.

Second, the project validates its graphics pipeline not merely through synthetic test benches such as the Utah teapot simulation, but by executing commercial, off-the-shelf software binaries. Tomb Raider runs on z486 XL utilizing its original DOS Glide executable without single-instruction patches or custom translation layers.

Commercial game binaries from the late 1990s directly access hardware registers and expect strict adherence to undocumented timing nuances and status flags; any architectural discrepancy typically results in immediate software lockups or severe visual artifacts. The ability of an unmodified commercial binary to execute smoothly, traverse dungeon levels, and swap framebuffers validates the functional fidelity of zSST far more convincingly than synthetic benchmarks alone.

8. Where This Project Delivers Value and Where Its Practical Boundaries Lie

To accurately appreciate the contributions of zSST and z486 XL, one must delineate where the project offers profound engineering value versus where its practical operational boundaries lie.

The project is unequivocally not designed to serve as a practical gaming platform for casual retro enthusiasts. Users seeking to play through classic DOS libraries can achieve superior results using modern software emulators such as DOSBox-X, 86Box, or PCem running on consumer desktop PCs. Those software packages deliver 60 FPS gameplay at 4K resolutions across hundreds of titles without requiring specialized FPGA hardware, Linux kernel configuration, or an acceptance of roughly 12 buffer swaps per second in Tomb Raider.

Instead, the true value of zSST resides in digital preservation and computer architecture research:

  • Permanent Architectural Preservation: As vintage physical chipsets succumb to capacitor degradation and silicon decay, implementing the SST-1 in portable SystemVerilog preserves the exact logic design in an immortal, executable format.
  • Educational Reference for Early 3D Pipelines: The codebase provides an open, documented reference illustrating how first-generation fixed-function accelerators orchestrated texture caching, fixed-point math, and memory scheduling before the advent of unified programmable shaders.
  • System-on-Chip Integration Paradigm: The project serves as an empirical case study in integrating a legacy x86 pipelined CPU with a dedicated 3D accelerator sharing unified onboard DDR memory within an FPGA fabric.

9. Unconfirmed Items and Unresolved Questions

  • Direct Clock Frequency Comparison with Original Silicon: The author's documentation specifies that zSST operates at 100 MHz on the KV260 board, but provides no direct numeric comparison against the physical clock speed of the original 1996 3dfx Voodoo Graphics chip.
  • Compatibility and Frame Rates in Additional Commercial Titles: Verified hardware testing is currently concentrated on Tomb Raider Level 2; performance metrics and compatibility across other Glide releases, such as Need for Speed II SE or GLQuake, remain unconfirmed on physical hardware.
  • Multi-TMU Configurations and SLI Support: The current zSST implementation is strictly bounded to a single Texture Mapping Unit; support for dual-TMU configurations or 3dfx's Scan-Line Interleave multi-card architecture is excluded from the current codebase.
  • Roadmap for Subsequent 3dfx Architectural Generations: While the author noted an interest in exploring subsequent 3dfx generations, concrete delivery milestones or structural plans for Voodoo 2 or Voodoo 3 recreations have not been formally published.
