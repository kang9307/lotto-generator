仕様書のないファイルが手元にあるとき - バイトから構造を読み取る順序

何をまず疑い、各シグナルがどこまで確定させ、法がどんな条件を課しているか

2026-09-05 開発・インフラ

拡張子に見覚えがなく、開いても文字ではなく、作った側に尋ねることもできないファイルが手元に来ることがある。退役した装置が残したログ、サービスの終わったソフトウェアのセーブファイル、引き継ぎ資料のないまま渡された社内ツールの出力がだいたいそれだ。こういうとき必要なのはツールではなく順序である。どのツールを開いても画面に出るのは結局同じバイトであり、そのバイトで何をまず疑うかが、かかる時間を決める。

この記事はその順序を整理する。バイトが漏らすシグナルを一つずつ分け、それぞれについて何を確定させ、何は確定させないかを線引きする。そのうえで、推論した構造をファイルに問い直す方法と、この作業に法が課した条件までを見る。ツールはこの手順を助ける手段としてのみ登場する。

この記事の法律部分は情報提供が目的であり法的助言ではない。条文は原典で確認して引いたが、ある行為がその条文に当たるかは対象と目的と契約によって変わる。具体的な事案の判断は所管機関と法律の専門家の領分である。またこの記事は保護措置を回避する方法を扱わず、その領域はここで整理した手順の範囲外である。

きっかけ - 「未知の形式」という言葉が隠す前提

2026年8月27日、ヘックスエディタImHexを作っている開発者が、未知のファイル形式をリバースエンジニアリングする過程を記事にして公開した。あるゲームのセーブファイルを開き、すべてのバイトに名前をつけるまでが内容で、韓国のコミュニティにも転載された。良い記事だ。ただし題名だけを見て転記すると、重要な前提が一つまるごと抜け落ちる。

その記事の方法はバイトを睨むことではない。そのファイルを書き出すプログラムのコードを読むことである。書き手自身が冒頭近くでこう書いている。ファイルを開くと平文の文字列が見えるので圧縮でも暗号化でもないことは分かる、識別用のマジックもなくツールも種類を当てられない、これ以上の情報がなければここで行き止まりだ、と。その一文の後からが逆コンパイルである。

その記事が最後にまとめた一般手順は四段階だ。すでに知られた形式かを確認し、そのファイルを読み書きするコードを探し、コードで使われている構成要素を特定し、見つけたものをパターンファイルに書いて文書化しながら検証する。順序は正確だ。ところが実務で足が止まる場所は、たいてい二番目の段階である。コードがないか、あっても見られないか、見られても見てはならない場合がある。

その場所に残るのがバイトだけだ。この記事が扱うのはそこである。答案を見られない状態で構造を絞っていく順序と、その順序で得た結論が答案を見た結論とどう違うかという話だ。ツール自体が気になるなら特定のバイナリ形式のために作られた解析ツールを扱った記事が別にあり、言語モデルがこの作業の何を変えたかは読みやすくする仕事と正しいと言える仕事の違いを整理した記事で扱った。ここでは繰り返さない。

0段階 - すでに知られた形式かどうかをまず排除する

構造を推論する前にすべきことは、推論が不要だと確かめることである。正体不明のファイルのかなりの割合は既知の形式であり、ただ拡張子が見慣れないか、別の形式の中に入っているだけだ。きっかけになった記事のコメントに、未知の形式の半分は圧縮ファイルに入った組み込みデータベースだという冗談があったが、誇張ではあっても方向は合っている。

排除は三層で行う。第一に、先頭の数バイトをシグネチャのデータベースに問い合わせる。ほとんどのヘックスエディタとファイル判別ツールがこの機能を持つ。第二に、コンテナかどうかを見る。圧縮アーカイブ形式はローカルファイルヘッダが50 4B 03 04で始まるが、目次にあたる中央ディレクトリはファイルの末尾にあり、その末尾の記録は50 4B 05 06で始まる。先頭だけを流し見る習慣の人が定期的に取りこぼす場所だ。第三に、末尾と中間を見る。前に別のデータを付けたファイルは先頭だけでは正体がつかめない。

目次を末尾に置く設計には理由がある。順次書き出すストリームでは、書き終えるまで各項目の最終的な大きさが分からない。だから項目を先に流し、目次を後から付ける。この設計上の癖を知っていれば、正体不明のファイルでも末尾から探る理由が生まれる。形式がファイルを丸ごとメモリに載せる前提で作られたのか、流し書きできるように作られたのかが、構造全体の形を変える。

この段階で正体がつかめれば、その日の仕事は事実上終わりだ。仕様書が答えを持っており、すでに作られたパーサがある可能性も高い。排除に失敗したときにはじめて次へ進む。

シグナル一 - マジックナンバーが確定させるもの

ファイル先頭の固定バイト列は、真っ先に目に入るシグナルだ。よく設計された形式はこの場所を慎重に使う。PNGを例に取ると、データストリームの最初の八バイトは常に89 50 4E 47 0D 0A 1A 0Aであり、仕様はこのシグネチャがPNGを他の種類のデータストリームと区別し、一部の伝送エラーの早期検出を可能にすると書いている。同じ仕様は、デコーダが八バイトすべてを検査すべきであり、続く八バイトが正しい長さのヘッダチャンクで始まっていればデータストリームの完全性への確信をさらに強められる、と付け加える。

つまりマジックナンバーは「この形式で間違いない」ではなく「この形式を意図した」を語る。この区別が実務で効いてくる場所は次のとおりだ。

  • 確定するもの — 作り手が特定の形式を意図したという事実、そしてその形式の仕様書を探しに行く理由
  • 確定しないもの — 中身が本当にその形式か、バージョンは何か、後半が切れたり変形したりしていないか
  • マジックがないという事実が語ること — 形式がないという意味ではない。 外部とやり取りすることのない内部専用の形式には、識別用の札を置く理由自体がない
  • よくある反例 — 複数の形式が同じ先頭バイトを共有する場合、マジックがファイル先頭ではない場所にある場合、外側コンテナのマジックだけが見えて内側は見えない場合
  • 人間が読めるASCIIが先頭にあれば、まずそれを検索する。形式名や製品名であることが多く、その文字列一つで仕様書が出てくることも珍しくない

正体がつかめない状態で先頭に繰り返し同じ値が見えるとしても、それがマジックなのか、単に最初のフィールドの値がいつも同じなのかはまだ分からない。この二つを分けるにはファイル一つでは足りない。 この問題は後で改めて扱う。

シグナル二 - エンディアンは値の形に現れる

複数バイトからなる整数がどの順で保存されるかは、以後のすべての解釈を左右する。00 00 01 F4を前から読めば500、後ろから読めば40,894,464だ。どちらか分からなければ長さフィールドもオフセットも全部空回りする。

判別は値の形で行う。ファイルに入る整数のかなりは小さい値である。個数、長さ、バージョン、インデックスがそうだ。小さい値を4バイトや8バイトに入れると上位バイトが全部0になる。だから整数に見える場所を何か所か集めて0がどちら側の端に寄っているかを見れば、たいてい分かれる。0が前に寄っていれば大きい側が先に来る順序、後ろに寄っていれば小さい側が先に来る順序だ。

確定するのはそのフィールドのバイト順序までである。ファイル全体が同じ順序だということは確定しない。実際、仕様のある形式どうしでも定め方が違う。先に見た圧縮アーカイブは小さい側が先に来る順序を使い、PNGの仕様は一バイトを超えるすべての整数がネットワークバイト順序、つまり大きい側が先に来る順序でなければならないと明記する。一つのファイルの中でコンテナは一方の順序なのに、中に載ったペイロードは逆の順序という場合もよくある。ペイロードを作ったコードとコンテナを作ったコードが違えば自然にそうなる。

反例もはっきりしている。値が対称なら判別できない。フィールドが実は整数ではなく浮動小数点なら0の寄る位置が違う。四バイトの枠が実際には一バイトのフィールド四つかもしれない。だからエンディアンは一か所で確定させず、複数の場所で同じ結論が出たときに確定させる。

シグナル三 - 長さフィールドとオフセット表

構造の骨格をもっとも強く暴くシグナルだ。ある4バイトの値がその地点から残っているバイト数と正確に一致するか、次の構造が始まる位置と噛み合えば、それは偶然ではない。値一つがファイルの別の地点を指した瞬間、そのファイルには人間が設計した構造があることが確定する。

可変長のデータを収める方法は大きく二つだ。長さを前に付けるか、終わりを知らせる終端子を後ろに付けるか。前に付けるほうが圧倒的に多い。あらかじめ場所を確保でき、データの中に終端子と同じ値が出てきても安全だからだ。文字列が0x11のような小さい値一つの後にちょうどその分の文字で続くパターンが見えたら、長さ前置の文字列である可能性が高い。

長さが大きい値まで扱う必要が出ると可変長整数が登場する。広く使われる方式は、一バイトの最上位ビットを次のバイトがまだあるという旗として使い、残りの七ビットを値に使うものだ。きっかけになった記事も対象プログラムの文字列書き出しコードを解いていて、まさにこのエンコーディングに行き当たった。ヘックスエディタのデータインスペクタにも符号ありとなしの二項目で入っている。小さい値が一バイトに収まるので、短い文字列の多い形式では目に見えて得だ。

value = 0
shift = 0
repeat:
    b      = read_u8()               // 一バイトを読む
    value |= (b & 0x7F) << shift    // 下位7ビットが値である
    shift += 7
until (b & 0x80) == 0                // 最上位ビットが0なら最後のバイト

確定するのはその値が長さや位置として使われているという事実だ。確定しないもののほうが多い。単位がバイトなのか要素数なのか、基準点がファイルの先頭なのかその構造の先頭なのか、そしてその長さにヘッダ自身が含まれるのか。この三つは、仕様のある形式でも明記しなければ実装が割れる場所である。PNGの仕様が長さフィールドについてデータフィールドだけを数え、自分自身もチャンクタイプもCRCも数えないとわざわざ書いている理由がこれだ。仕様を書く人たちも、ここで読み手が間違うと知っていたということである。

00000000  4C 4F 47 32 01 00 00 00  20 00 00 00 03 00 00 00
00000010  00 00 00 00 00 00 00 00  0C 00 00 00 48 45 4C 4C

// 候補となる解釈 (まだ仮説である)
//   +0x00  4バイト  'LOG2'    マジックに見えるASCII
//   +0x04  4バイト  1         バージョン? 小さい側が先に来る順序で読んだ
//   +0x08  4バイト  32        ヘッダの大きさ? 最初のレコードのオフセット? 0x20 が合う
//   +0x0C  4バイト  3         レコード数?
//   +0x18  4バイト  12        最初のレコードの長さ? 後に続くデータと合うか

上の例で決め手になるのは、0x20という値と実際にデータが始まる位置が一致する点だ。値と位置が噛み合う地点を見つけることがこの段階のすべてであり、一つ見つければ隣のフィールドも連鎖して解ける。

シグナル四 - アラインメント、パディング、周期

0が規則的に挟まる場所はたいていアラインメントだ。4バイトや8バイトの境界に合わせるために入れた空きである。構造体をメモリにあった形のままファイルに流し込んだ形式なら、コンパイラが入れたパディングがそのまま残る。 この場合はパディングの位置がむしろ元の構造体のフィールドの大きさを教えてくれる。2バイトのフィールドの後ろに2バイト空いていれば、その次が4バイト境界を要求するフィールドだった可能性が高い。

ファイル末尾の大量の0は別の話だ。固定サイズのバッファを使った痕跡である。きっかけになった記事の対象がまさにそうだった。保存関数が常に40,960バイトを満たすように足りない分を0で埋め、あふれれば例外を投げるようになっていた。こうした形式はファイルサイズがいつも同じという事実そのものがシグナルだ。大きさが常に同一のファイルを複数持っているなら、中身ではなく器を見ていることになる。

周期はレコード構造を探す糸口だ。同じバイトの並びが一定の間隔で現れるなら、その間隔がレコードの大きさかもしれない。候補をいくつか立てたうえで、ファイルサイズからヘッダらしき先頭部分を引いた値がその候補で割り切れるかを確認する。きれいに割り切れれば仮説が一段上がる。

  • 確定するもの — 固定長レコードという仮説の候補サイズ、そして構造体をそのまま流し込んだ形式だという心証
  • 確定しないもの — ヘッダの大きさ。ファイルサイズ一つに未知数が二つあり方程式が解けない。大きさの違うサンプルが二つあれば解ける
  • 反例その一 — アラインメントに見える0が、実は値が0のフィールドかもしれない。予約フィールドはほぼ常に0だ
  • 反例その二 — 周期に見えるものがデータの性質かもしれない。同じ文字列が並ぶ一覧は周期があるように見える
  • 反例その三 — 圧縮された区間にも偶然の周期が生じる。次のシグナルでその区間を先に除いておく必要がある

シグナル五 - エントロピーが描く境界

バイト単位で測った情報量の上限は8ビットだ。一バイトが取りうる値が256通りだからである。ファイルを区間に切ってこの値を測ると、性質の異なる領域の境界が描かれる。人が読むテキストや構造ヘッダは値が低い。使われるバイトの種類が少なく偏っているからだ。圧縮または暗号化された区間は上限に張りつく。よく圧縮されたデータは定義上予測できない形をしており、圧縮と予測が同じことだという事情は圧縮がすなわち予測である理由を扱った記事に別途書いた。

ImHexのデータ情報画面には、エントロピーのグラフ、最高値と平均値、バイト種類の分布、そして圧縮・暗号化の判定が一緒に入っている。他のツールにも似た画面がある。画面の見た目は重要ではなく、その値でどこまで語れるかが重要だ。

  • 確定するもの — 構造を読める区間と読めない区間の境界。これだけでも十分に元が取れる。ヘッダがどこで終わりペイロードがどこから始まるかが見える
  • 確定しないものその一 — 圧縮なのか暗号化なのかの区別。どちらも一様に見え、値だけでは分かれない
  • 確定しないものその二 — アルゴリズム、鍵、パラメータについては何も語らない
  • 反例その一 — すでに圧縮された画像や音声をそのまま抱えている区間も値が高い。形式自体はありふれたコンテナで、中のペイロードだけが圧縮されている場合だ
  • 反例その二 — 区間が短いと標本が小さく値がひどく揺れる。数十バイトの区間のエントロピーはほとんど意味がない
  • 反例その三 — 値が低いから平文だとも言えない。固定表を使うエンコーディングや繰り返しの多いバイナリも低く出る

まとめるとエントロピーは地図だ。どこを掘れば何が出るかを教えてくれ、それ以上は語らない。地図を羅針盤と取り違えると、そこから時間が漏れはじめる。そして読めない区間が保護措置の結果であるなら、その区間はこの手順の対象ではなく手順を止めるべき場所だ。

前の五つのシグナルを一つの表に並べると順序がはっきりする。上から下へ降りていくが、各行の三列目を確認せずに次の行へ行かないのがこつだ。

表の三列目を習慣的に読むことがこの仕事の半分だ。シグナルは仮説を絞る道具であって結論ではない。 各シグナルが絞ってくれる幅は思ったより小さく、絞られた結果を確定へ格上げするのは次の節の作業である。

仮説をファイルに問い直す方法

頭の中にある仮説は反証されない。あいまいなまま置いておくと、食い違う場所を見ても食い違いに気づかない。だから推論した構造は機械が読んで失敗できる形で書かなければならない。これがこの作業でツールが実際にしている仕事だ。

宣言的に書く方式が二つ広く使われている。一つはImHexのパターン言語で、C++に似た文法で構造体と配列と条件を書くと、その定義がファイルの上に重ねて表示される。リポジトリはGPL-2.0で、2026年9月5日03時26分UTC時点でスター54,695、フォーク2,451、オープンな課題394が記録されている。もう一つはKaitai Structで、YAML形式で構造を宣言するとコンパイラが複数言語のパーサコードを生成する。コンパイラはGPLv3以上、ランタイムはおおむねMITだ。アプローチは違うが狙っている性質は同じである。

struct Header {
    char magic[4];
    std::assert(magic == "LOG2", "magic does not match");     // 仮説 1
    u32  version;
    std::assert(version == 1, "unknown version");   // 仮説 2
    u32  headerSize;
    u32  recordCount;
};

struct Record {
    u32 length;                                            // 仮説 3
    u8  payload[length];
};

struct File {
    Header header;
    Record records[header.recordCount];                    // 仮説 4
};

こう書いておけば仮説が間違っていたとき、目に見えて間違う。 レコードの大きさを取り違えればファイル末尾でバイトが余るか足りなくなり、個数を取り違えれば途中で破綻する。崩れ方そのものが情報だ。

  • 末尾で余ればレコードの大きさを小さく取ったか、ヘッダを大きく取った
  • 末尾で足りなければその逆か、最後に目次のような尾の構造が別にある
  • 途中で破綻すれば条件によって有無が変わるフィールドがある。前のどれかの値がその存在を決めている
  • 一部のファイルでだけ破綻するならバージョンが複数ある。まずバージョンフィールドを探す
  • 仮説は強く立てる。値が特定の数だと言い切っておけば、そうでないときに即座に分かる。ゆるい定義は間違っていても静かに通り過ぎる

きっかけになった記事も同じ習慣を見せている。対象のコードがバージョンの値が6かを検査し、そうでなければ例外を投げると確認したうえで、自分のパターンにも同じ断定を入れた。コードから読み取った事実をファイルに対して検査する形に移したのである。答案を見ていても書き写す過程で間違えうるので、この習慣は答案があるときにも有効だ。

サンプルが一つしかないとき崩れるもの

ファイルが一つだけなら定数と変数を分けられない。 あるバイトが形式の定めた固定値なのか、そのファイルでたまたまその値なのかを判断する根拠がない。先頭四バイトがマジックなのか最初のフィールドの値なのかが分かれないのもそのためだ。この限界は観察をいくら増やしても消えない。必要なのは観察ではなく対照群である。

対照群を作る方法は単純だ。そのファイルを作るプログラムで値を一つだけ変えて保存し直し、二つのファイルを比較する。変わったバイトの位置がその値の住所だ。この作業はツールがよく助けてくれる。データソースどうしを比較して差を強調し表で見せる機能は、ほとんどのヘックスエディタにある。ただしこの方法はそのプログラムを使える立場でなければ成立しない。 ここから技術ではなく資格の問題になり、だからこそ後の二節が続く。

対照群を作ってもそのままでは解けない場所が二つある。一つは毎回変わるフィールドだ。タイムスタンプが代表で、何も変えなくても保存のたびに違うので比較結果にノイズとして敷かれる。だから何も変えずに二度保存した対を先に作り、そのとき変わる場所をノイズ一覧として外しておく。時刻の値は基準時刻と単位さえ当てればよいのだが形式ごとにばらばらで、ある表計算ソフトが日付を扱うやり方を整理した日付が数値として保存される事情を見ると、この界隈の慣行がどれほど勝手気ままかが分かる。

もう一つは検査フィールドだ。チェックサムや巡回冗長検査の値が入っていると、値を一つ変えただけでその場所と検査フィールドの二か所が一緒に変わる。逆に言えばこれが検査フィールドを見つける方法である。意図した場所ではなくもう一か所が一緒に変わったらそちらを疑う。検査フィールドは何を対象に計算したかが肝心で、PNGの仕様がチャンクごとに4バイトの検査値を置きつつ長さフィールドを除いてチャンクタイプとデータを対象に計算すると明記しているのが良い例だ。仕様のある形式でも、この範囲を書いておかなければ実装が割れる。

そして対照群をそもそも作れない場合がある。プログラムが消えたか、装置がないか、正当に使う資格がない場合だ。そのとき出てくる結論は形式についての説明ではなく、そのファイル一個についての説明である。この区別を結果文書の冒頭に書いておくことが、後で自分を救う。半年後にその文書を読む人には、どこが検証済みでどこが当て推量かを知る手立てがない。

コードが手元にあるとき - 元記事が実際にしたこと

前の手順は答案がないときの話だ。あればまったく絵が変わる。きっかけになった記事の順序をそのままたどると、その違いがはっきりする。

まず対象のファイルを探してヘックスエディタで開いた。平文の文字列が見えるので圧縮でも暗号化でもないと判断し、識別用のマジックがなく、ツールの判別機能も種類を当てられないことを確認した。ここまでがこの記事で整理した0段階と最初の二つのシグナルに当たる。そしてこれ以上の情報がなければ行き止まりだと書いた。

その次が分かれ道である。対象プログラムのインストールフォルダに特定のランタイムのライブラリが見えており、その言語は逆コンパイルが容易な部類だ。セーブファイル名を組み立てる文字列を手がかりに保存コードを見つけ、そのコードがタイムスタンプを先に書き、実際の内容はコールバックに委ね、決められた大きさになるまで0で埋めることを見た。この時点からは推論ではなく書き写しである。

書き写した構成要素は、この界隈で繰り返し出会うものばかりだ。1601年を基準に100ナノ秒間隔を数える64ビットの時刻値、読み込み関数が特定の数かを検査するバージョンフィールド、真偽一バイト、値があるかを知らせる旗が前に付く任意の値、長さを可変長整数で前置した文字列、個数を前置した一覧、そして整数の上に名前をかぶせた列挙型である。ファイル一つにすべてを収める形式を設計したことのある人なら、この一覧に見覚えがあるはずだ。書く側の選択肢はもともとそう多くない。

文字列が出てくればエンコーディングが付いてくる点も押さえておきたい。長さが文字数なのかバイト数なのか、どのエンコーディングか、正規化形式は何かはすべて別の問題だ。同じ文字が二通りのバイト列で保存されうる事情はハングルが二通りの方式で保存される問題を扱った記事に整理してある。

ここに残る結論は一つだ。その記事がすべてのバイトに名前をつけられた理由は、バイトをよく見たからではなく答えを見たからである。答えを見られない状況では、同じ手順が同じ確信をくれない。その差を認めずに成果物を出すことが、この作業でもっともよくある失敗だ。

その記事が扱っていないことも書いておく。エントロピー分析、複数サンプルの比較、統計的な構造推論、そして法的条件はその記事にない。ツールにはその機能が揃っているが、その記事の主題ではなかった。原文にないものを原文が言ったかのように移さないことが引用の最低条件である。

1. 既知形式の排除シグネチャ照会、コンテナかどうか、末尾の確認すでにある仕様を何日もかけて再発見する

法が課した条件 - 著作権法第101条の4

韓国の著作権法はこの作業を正面から扱う条文を持っている。以下の引用は著作権法 [施行 2026年8月11日] [法律第21336号、2026年2月10日一部改正] に基づくもので、当該条文は2009年4月22日に新設され、第1項が2023年8月8日に改正された状態である。

定義がすでに目的を含んでいる

第2条第34号は用語から定義する。プログラムコード逆分析とは、独立して創作されたコンピュータプログラム著作物と他のコンピュータプログラムとの互換に必要な情報を得るためにコンピュータプログラム著作物コードを複製または変換することをいう。

この定義を素通りしてはいけない。目的が定義の中にすでに入っている。 互換に必要な情報を得ようとするものでなければ、そもそもこの名前がつく行為ではなく、したがってこの条文が用意した例外の対象でもない。よく「互換性目的なら問題ない」と要約されるが順序が逆だ。互換性目的は後から付ける正当化ではなく入口の条件である。

第1項が求める四つ

第101条の4第1項は要件を重ねる。正当な権限によりプログラムを利用する者またはその許諾を受けた者は、互換に必要な情報を容易に得ることができずその取得が不可避である場合には、当該プログラムの互換に必要な部分に限定して、プログラムの著作財産権者の許諾を受けずにプログラムコード逆分析を行うことができる。

一文の中に条件が四つ入っており、四つすべてを満たさなければならない。 一つでも欠ければその例外に頼ることはできない。

第2項が塞ぐ二つの出口

第2項は得た情報の使用を別に制限する。第一に、互換目的以外の他の目的のために利用したり第三者に提供したりする場合だ。第二に、対象プログラムと表現が実質的に類似したプログラムを開発・製作・販売したり、その他著作権を侵害する行為に利用したりする場合である。

実務でもっとも頻繁に引っかかるのが第一の後半だ。解析結果をまとめて公開することが第三者に提供する場合に触れうる。形式の仕様をブログやリポジトリに載せることがこれに当たるかは、何を、どの範囲まで、どんな目的で公開したかによるのであり、この記事が代わりに判断できる問題ではない。ただし解析する行為と結果を配布する行為が別個に評価されることは、条文の構造からはっきり読み取れる。

隣にある別の条文

第101条の3第1項第6号は別の角度から例外を置く。プログラムの基礎をなすアイデアおよび原理を確認するためにプログラムの機能を調査・研究・試験する目的で複製する場合であり、正当な権限によりプログラムを利用する者が当該プログラムを利用中である場合に限定される。ここには同項の但し書きが一緒にかかる。プログラムの種類と用途、複製された部分が占める比重、複製の部数などに照らして著作財産権者の利益を不当に害する場合には適用されない。

二つの条文の肌合いが違う点は押さえておく必要がある。第101条の3第1項第6号は機能を観察し試験する側であり、第101条の4はコードを複製または変換する側だ。ファイル構造を突き止める作業は、やり方次第でどちらに近いこともあれば、どちらでもないこともある。

そしてもう一つ残る。二つの条文はいずれも「プログラム」に関するものである。 データファイル自体はプログラムではないかもしれず、そのファイルの構造を読む行為がこれらの条文の適用対象かは、対象と行為の性格による。この区別をつぶしたまま「逆分析は合法」と要約するのが、この主題でもっともよくある誤読だ。

何を問うか条文の根拠確認すべき事実判断主体
自分にその資格があるか第101条の4第1項正当な権限で利用中か、またはその者の許諾を受けたか事案ごとの判断、最終的には裁判所
目的は何か第2条第34号、第101条の4第1項他のプログラムとの互換に必要な情報を得ようとするものか事案ごとの判断、最終的には裁判所
他の道はあったか第101条の4第1項その情報を容易に得られず、取得が不可避だったか事案ごとの判断、最終的には裁判所
どこまでやったか第101条の4第1項互換に必要な部分に限定したか事案ごとの判断、最終的には裁判所
結果をどこに使ったか第101条の4第2項第1号互換目的の外で使ったり第三者に提供したりしたか事案ごとの判断、最終的には裁判所
何を作ったか第101条の4第2項第2号表現が実質的に類似したプログラムを作ったか事案ごとの判断、最終的には裁判所
機能の調査・試験なのか第101条の3第1項第6号アイデアと原理の確認が目的か、利用中の状態か、但し書きにかからないか事案ごとの判断、最終的には裁判所

法の外に契約が残る

条文の要件をすべて説明できても終わりではない。利用規約やライセンスが別途に解析を制限している場合が多く、法定の例外と契約条項がぶつかったときにどちらが勝つかは、管轄と条項の性格によって分かれる。法に例外があるから契約は無視してよいというのは安全な前提ではない。逆に、契約に禁止と書いてあるから絶対に駄目だというのも同じく断定だ。いずれにせよ結論はこの記事ではなく、その事案を見る人が出す。

実務に残るのは結局記録である。目的をまず文書に書き、作業範囲をその目的に縛り、成果をどこに使うかをあらかじめ決める。この三つが文書に残っていない作業は、後で説明しにくくなる。説明すべきときが来ると、たいてい作業を始める前に何を書いておいたかが問われる。終わった後に書く経緯書は同じ重みを持たない。

軸が一つずつ増える場合も整理しておく価値がある。対象が自分の機械ではなく他人のサーバにあれば情報通信網に関する規律が別にかかる。成果を配布すれば配布に関する評価が別に付く。営業秘密に関する法制も別に働く。そして対象に技術的保護措置がかかっている場合はまったく別の問題であり、この記事はその領域を扱わない。 管轄が複数のときにこの絵がどう変わるかは管轄ごとに異なる要件を比較した節に整理してある。

最後によく誤解されることを一つ。ある措置が技術的に弱いという事実は法的判断とは無関係だ。錠前がお粗末なことと、開けてよいことは別の話である。難読化やエンコーディングが保護というより遅延装置に近い事情は難読化は暗号化ではないを扱った記事で別途整理したが、その事実が何をしてもよい根拠になることはない。

繰り返す。この節の内容は条文を原典で確認して移したものであり、個別の事案についての判断ではない。同じ条文でも対象、目的、契約、成果の用途によって結論が変わる。実際の作業の前には所管機関の案内と法律の専門家の確認を経るのが正しい。 この記事は情報提供の目的でのみ書かれている。

  • PNGシグネチャ八バイトのバイトごとの設計根拠は確認できなかった。最初のバイトが上位ビットを落とす伝送を捉え、途中の改行の組み合わせが改行変換を捉えるという説明が広く語られているが、確認した仕様本文にその根拠は載っていない。仕様が書いているのは、他のデータストリームと区別し一部の伝送エラーの早期検出を可能にするというところまでだ。そのため本文にはバイトごとの根拠を書かなかった
